# Комунікації та обмін із захистом приватності

End-to-end encryption захищає вміст. Воно не приховує автоматично обліковий запис, номер телефону, граф контактів, IP-адресу, push token, попередній перегляд сповіщень, час, метадані файлів або поведінку отримувача. Обирайте інструмент з огляду на метадані, які він видаляє, та спостерігачів, яких він додає.

## Порівняння моделей комунікації

| Інструмент/модель | Корисна властивість | Залишкові спостерігачі та обмеження |
|---|---|---|
| Signal | Зріле E2EE; usernames дають змогу почати контакт без розкриття номера; sealed sender зменшує метадані для сервісу | Для реєстрації потрібен номер телефону; сервіс, push provider, контакти та endpoints зберігають деякі спостереження |
| SimpleX | Немає глобального ідентифікатора користувача; черги для окремих контактів; необов'язковий Tor transport | Час/transport relay, push service, запрошення та endpoints; новіша/менша екосистема |
| Briar | Пряма синхронізація; Tor онлайн; Bluetooth/Wi-Fi офлайн; немає центрального сховища повідомлень | Контакти та endpoints; локальні радіоспостерігачі; орієнтація на Android; обидві сторони мають бути доступні або потрібно використовувати Mailbox |
| OnionShare | Пряма передача файлів/отримання/чат/сайт через тимчасовий onion service; немає storage provider | Комп'ютер відправника є сервісом; bearer посилання отримує доступ; час і endpoints залишаються видимими |
| Зашифрований файл `age` | Просте шифрування ключем отримувача, незалежне від transport | Transport бачить відправника/отримувача/час/розмір; імена файлів/метадані архіву та endpoints залишаються видимими |
| Звичайна електронна пошта + TLS | Шифрування каналу між серверами | Обидва mail providers зазвичай можуть читати вміст і зберігати routing/account metadata |

## Signal: приватний контакт без розкриття номера

Signal usernames дають змогу почати чат без розкриття номера телефону користувача новому контакту, але для реєстрації номер телефону все одно потрібен.<sup>[[1]](#references)</sup> Sealed sender є поступовим посиленням захисту метаданих, а не захистом від будь-якої кореляції IP/часу.<sup>[[2]](#references)</sup>

### Послідовність дій

1. Встановіть Signal з офіційного app store/project і спочатку оновіть OS.
2. Зареєструйтеся з номером, яким ви маєте законне право користуватися. Не використовуйте орендовані SMS-активації, номер іншої особи або provider account, отриманий із неправдивою особою.
3. У **Settings → Privacy → Phone Number** налаштуйте, хто може бачити номер і хто може знаходити обліковий запис за номером, відповідно до threat model.
4. Створіть username для пошуку новими контактами. Передайте його точне посилання/QR через уже автентифікований канал; usernames можуть змінюватися і не є іменем профілю.
5. Вимкніть завантаження контактів/дозволи, якщо зручність не варта пов'язування, і додавайте контакти вручну там, де це підтримує платформа.
6. Відкрийте дані контакту та порівняйте safety number/QR через другий канал або особисто перед передаванням чутливого вмісту.
7. Перевірте linked devices, registration lock/PIN, попередній перегляд сповіщень, screen security, call relaying, типові налаштування зникаючих повідомлень і поведінку backup.
8. Надішліть нечутливе тестове повідомлення та здійсніть виклик. Перевірте сліди на lock-screen, desktop, wearable і cloud-notification з обох боків.
9. Розглядайте змінений safety number або неочікуваний linked device як подію для розслідування, а не як сповіщення, яке слід автоматично відхилити.

Не поєднуйте псевдонімне фото профілю, bio, членство в групах або розклад з ідентифікованим Signal context.

## SimpleX: з'єднання для окремих контактів без глобального ідентифікатора

SimpleX маршрутизує повідомлення через односпрямовані черги та не призначає мережевого ідентифікатора користувача. Його власна policy все одно описує transport sessions, тимчасові серверні дані, компроміси push-notification і відповідальність endpoint.<sup>[[3]](#references)</sup>

### Послідовність дій

1. Завантажте клієнт, який підтримується, з офіційного project/store і перевірте видавця. Використовуйте окремий OS/app profile, якщо ідентичності не мають змішуватися.
2. Створіть **локальний** profile з контекстним display name та зображенням. Видалення app без backup може призвести до втрати profile і connections.
3. Під час першого запуску свідомо оберіть режим сповіщень. Миттєвий mobile push може розкрити додаткові метадані інфраструктурі Apple/Google.
4. Створіть одноразове invitation link для одного контакту. Передайте його через автентифікований канал; будь-хто, хто отримає активне запрошення, може спробувати ним скористатися.
5. Після з'єднання відкрийте дані контакту та порівняйте security code особисто або через незалежний verified channel.<sup>[[4]](#references)</sup>
6. Використовуйте incognito per-group profile, якщо це підтримується, замість повторного використання одного profile у непов'язаних групах.
7. Налаштуйте підтримуваний клієнтом Tor transport, якщо локальна мережа/сервер не повинні бачити пряму IP-адресу. Після зміни підтвердьте з'єднання; не примушуйте використовувати непідтримуваний system proxy.
8. Перевірте delivery receipts, link previews, calls, automatic downloads і database export/backup. Кожен із них змінює метадані або exposure endpoint.
9. Протестуйте відновлення на запасному ізольованому пристрої, не запускаючи дубльований активний стан profile; project попереджає, що одночасні копії можуть порушити роботу розмов.

Відсутність глобального ідентифікатора не заважає контакту ідентифікувати користувача через вміст, повторне використання profile, доставку запрошення, час або соціальний граф.

## Briar: прямий і стійкий до перебоїв обмін повідомленнями

Briar синхронізується безпосередньо між пристроями, через Tor під час роботи онлайн і через Bluetooth/Wi-Fi під час локальних перебоїв. Офіційна threat model передбачає лише обмежений adversarial monitoring короткодіапазонного радіо, тому локальний wireless не є невидимим.<sup>[[5]](#references)</sup>

### Послідовність дій

1. Встановіть Briar з офіційного Briar distribution і перевірте джерело package. Використовуйте підтримуваний Android-пристрій із актуальними security updates.
2. Створіть локальний account з унікальним context nickname і надійним password. Шляху скидання password немає; перевірте, що unlock secret можна відновити.
3. Додавайте контакти особисто, скануючи QR-коди один одного, коли це можливо. Це автентифікує контакт і не дає змоги надсилати посилання через канал, який можна корелювати.
4. У connectivity settings увімкніть лише потрібні transport: Tor/Internet, Wi-Fi та/або Bluetooth. Вимикайте локальні радіомодулі, коли вони не потрібні.
5. Для асинхронної доставки розгляньте Briar Mailbox на окремому пристрої з постійним живленням; обліковуйте його та фізично захищайте як message server.
6. Надішліть нешкідливе тестове повідомлення, коли Internet доступний, а потім протестуйте запланований шлях під час перебою з вимкненим Internet у місці, авторизованому власником.
7. Перевірте Android backups, попередній перегляд сповіщень, screenshots та exported content. Локальне encrypted storage доступне, коли endpoint розблоковано/скомпрометовано.
8. Видаліть втрачені contacts/devices і припиніть використання всього context, якщо скомпрометовано фізичний контроль або password account.

## OnionShare: пряма тимчасова передача

OnionShare запускає onion service на комп'ютері відправника/отримувача; файли не завантажуються до storage provider, а traffic є end-to-end encrypted усередині Tor.<sup>[[6]](#references)</sup> Повна onion URL є bearer capability і має бути захищена.

### GUI file-sharing workflow

1. Встановіть OnionShare з його офіційного signed distribution і Tor Browser на стороні отримувача.
2. Розмістіть **sanitized copies** файлів в окремій staging directory. Не вказуйте OnionShare на особисту home directory.
3. Відкрийте **Share Files**, додайте лише staged files, залиште private key/access protection увімкненим і не вимикайте **Stop sharing after files have been sent** для одного отримувача.
4. Почніть sharing і надішліть повну onion URL через уже автентифікований E2EE channel. Не вставляйте її в email, issue trackers або public chats.
5. Отримувач відкриває URL у Tor Browser, перевіряє очікувані імена/розмір файлів із відправником і завантажує їх.
6. Обидві сторони порівнюють заздалегідь узгоджений або доставлений окремим каналом SHA-256 digest для перевірки цілісності, якщо сам файл є security boundary.
7. Переконайтеся, що OnionShare зупинився після завантаження; інакше зупиніть його вручну та закрийте application.
8. Видаліть staged copy відповідно до retention policy і перевірте налаштування OnionShare history/log на предмет ненавмисного розкриття імен файлів.

### CLI workflow

Офіційний CLI приймає файли як positional arguments і зупиняється після одного завершеного share за замовчуванням. На host з установленими official CLI/Tor:
```bash
# Inspect the installed version and options first
onionshare-cli --help

# Share one sanitized file; stop after one hour even if unused
onionshare-cli --auto-stop-timer 3600 ./staging/report-clean.pdf
```
Безпечно передайте повний URL. Не додавайте `--public`, `--no-autostop-sharing`, детальне журналювання імен файлів або persistence, якщо модель загроз явно не вимагає такого розкриття.<sup>[[7]](#references)</sup>

Ставтеся до отриманих документів як до ворожих. Відкривайте їх у одноразовій VM/рендерері на кшталт Dangerzone, а не на хості, що містить ідентифікаційні дані.

## Незалежне шифрування файлу за допомогою `age`

Незалежне від транспорту шифрування корисне, коли storage/email provider може бачити об'єкт. Воно не приховує відправника, отримувача, розмір, час або ім'я файлу, якщо ці параметри не обробляються окремо.

### Налаштування отримувача
```bash
# Creates a secret identity file; protect its permissions and backup
age-keygen -o recipient-identity.txt

# Derive a public recipient file safe to share
age-keygen -y recipient-identity.txt > recipient-public.txt
```
Підтвердьте автентичність відкритого рядка одержувача через другий канал. Після цього відправник виконує:
```bash
age -R recipient-public.txt -o package.tar.age package.tar
```
Одержувач розшифровує в новий шлях:
```bash
age --decrypt -i recipient-identity.txt -o package-restored.tar package.tar.age
```
Офіційний CLI попереджає, що `-o` перезаписує наявний вихідний файл, тому використовуйте новий каталог і перевіряйте дайджест/вміст перед переміщенням.<sup>[[8]](#references)</sup> Ніколи не надсилайте файл ідентифікації разом із шифротекстом.

## Відтворюваний конвеєр очищення файлів

Видалення метаданих залежить від формату. Зберігайте зашифрований оригінал, якщо важливі автентичність, криміналістичний аналіз або ланцюжок зберігання; працюйте з копією.

### Приклад для JPEG
```bash
mkdir -p ./clean

# Inventory embedded metadata
exiftool -a -u -g1 ./original/photo.jpg

# Write a new JPEG while retaining color-profile/color-space information
exiftool -all= --icc_profile:all -tagsfromfile @ -colorspacetags \
-o ./clean/photo.jpg ./original/photo.jpg

# Re-inspect the output
exiftool -a -u -g1 ./clean/photo.jpg
```
Це відповідає безпечнішій рекомендації ExifTool для JPEG: бездумне видалення кожного тегу також може видалити інформацію про колір.<sup>[[9]](#references)</sup> Потім візуально перевірте пікселі на наявність облич, відображень, екранів, орієнтирів і унікальних шаблонів пошкоджень/шуму.

### Робочий процес для Office/PDF

1. Зберігайте редагований оригінал у зашифрованому вигляді та офлайн, окремо від контексту публікації.
2. Видаліть коментарі, виправлення, приховані слайди/аркуші, вбудовані файли, персональні шаблони та властивості документа в авторській програмі.
3. Експортуйте новий PDF із виділеного чистого профілю; не «друкуйте» його на cloud-принтер.
4. Перевірте файл за допомогою інструментів, що враховують формат, і тимчасового візуального рендерера:
```bash
exiftool -a -u -g1 ./clean/report.pdf
pdfinfo ./clean/report.pdf
```
5. Здійсніть пошук у відрендереному виводі назв, шляхів, адрес електронної пошти та тексту ревізій. Растеризація може видалити активні структури, але погіршує доступність і пошук та не видаляє видимий вміст або стиль написання.
6. Обчисліть хеш фінального артефакту та передайте **лише** цю копію через publication compartment.

## Privacy Pass: анонімна авторизація для service designers

Privacy Pass розділяє **випуск** токенів і їхнє **погашення**. origin може дізнатися, що клієнт має токен, схвалений issuer, не дізнаючись про конкретну взаємодію клієнта під час випуску. Повторне використання токена, унікальні метадані, часові характеристики або змова можуть знову зробити зв’язування можливим.<sup>[[10]](#references)</sup>

Безпечний шаблон розгортання:

1. Визначте твердження, яке підтверджує токен (наприклад, право на rate limit), а не приховану глобальну ідентичність.
2. Використовуйте стандартизовану архітектуру та протоколи випуску; не реалізуйте криптографію сліпих підписів з нуля.
3. Розділіть адміністрування issuer/attester і origin, якщо цього потребує бажана властивість.
4. Мінімізуйте публічні/приватні метадані токенів і переконайтеся, що множини анонімності достатньо великі.
5. Якщо це підтримується, випускайте пакети токенів до використання, щоб час випуску не можна було тривіально зіставити з часом погашення.
6. Погашайте кожен токен один раз, перевіряйте challenge, прив’язаний до origin, і видаляйте стан прострочених токенів.
7. Не допускайте, щоб cookies, IP logging та облікові записи застосунку непомітно нівелювали властивість конфіденційності токена.
8. Перевірте, чи можуть логи issuer і origin об’єднати контрольовану подію випуску та погашення за часовими характеристиками, метаданими або унікальними помилками.

Privacy Pass є функцією застосунку, а не тим, що користувач може додати до довільного облікового запису.

## Communications verification checklist

- [ ] Контакт/запрошення/ключ було автентифіковано незалежно.
- [ ] Відомі наслідки розкриття номера телефону, імені користувача, профілю, групи та завантаження контактів.
- [ ] Перелічено спостерігачів прямої IP-адреси, relay, Tor, push-провайдера та локального радіоканалу.
- [ ] Перевірено попередній перегляд сповіщень, wearables, пов’язані desktop-пристрої та backups.
- [ ] Файли було очищено, за потреби зашифровано та відкрито в disposable context.
- [ ] Відновлення працює без поєднання непов’язаних ідентичностей.
- [ ] Для logs, history і тимчасових share-сервісів визначено правило вимкнення/зберігання.
