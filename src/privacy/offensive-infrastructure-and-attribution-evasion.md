# Επιθετική υποδομή και αποφυγή απόδοσης

{{#include ../banners/hacktricks-training.md}}

Ένας operator σπάνια εξασφαλίζει ουσιαστική ανωνυμία μέσω ενός μόνο proxy. Οι πραγματικές καμπάνιες δημιουργούν ένα **γράφημα διαχωρισμού**: ο operator συνδέεται με έναν κόμβο πρόσβασης, οι κόμβοι διέλευσης κρύβουν αυτόν τον κόμβο από τον κόμβο εξόδου, οι redirectors προστατεύουν το πραγματικό C2 και τα προσωρινά ονόματα δείχνουν στο δημόσιο άκρο.

Χρησιμοποιήστε τον [Κατάλογο τεχνικών ανώνυμης πρόσβασης στο Διαδίκτυο](anonymous-internet-access-techniques.md) για μια τυποποιημένη επισκόπηση των πλεονεκτημάτων/μειονεκτημάτων, της ανάπτυξης και του εντοπισμού κάθε διαδρομής. Αυτή η σελίδα εξετάζει λεπτομερέστερα τη σύνθεση υποδομής για αντίπαλες ενέργειες.

```text
operator -> access relay -> traversal mesh -> exit/redirector -> target
                |                 |                |
          account/provider   relay operator   target telemetry
```

Η τελευταία διεύθυνση που βλέπει ο στόχος αποτελεί επομένως ένδειξη της διαδρομής, όχι απόδειξη του ποιος χειριζόταν το πληκτρολόγιο. Το MITRE αντιστοιχίζει τα κύρια στοιχεία στις τεχνικές Acquire Infrastructure (T1583), Compromise Infrastructure (T1584), Proxy (T1090), Dynamic Resolution (T1568) και Web Service (T1102).<sup>[[1]](#references)</sup>

## Κατηγορίες υποδομής

| Κατηγορία | Γιατί τη χρησιμοποιεί ένας φορέας | Διαρκή ίχνη έκθεσης | Καλύτερο σημείο διερεύνησης για τους defenders |
|---|---|---|---|
| Νοικιασμένο VPS/cloud | Γρήγορο, προβλέψιμο, δρομολογήσιμο, εύκολο να ανακατασκευαστεί | tenant, χρέωση, console, ιστορικό source-login και image | συμβάντα λογαριασμού/control plane και επαναλαμβανόμενο αποτύπωμα server |
| Commercial VPN/Tor | Μεγάλο κοινό σύνολο εξόδου· χωρίς διαχείριση server | ορατότητα provider/guard και χρονισμός από άκρο σε άκρο | συμπεριφορά προορισμού, ενδείξεις endpoint και συσχέτιση ροών |
| Residential/mobile proxy | ASN καταναλωτών και γεωγραφική αληθοφάνεια | αρχεία broker/πελάτη· συμπεριφορά proxyware ή μολυσμένου host | αδύνατες μετακινήσεις, πρωτόκολλα proxy και εναλλαγή διευθύνσεων ανά session |
| Compromised server/router/IoT | Δανείζεται τη φήμη και τη δικαιοδοσία του θύματος | implant, ροή διαχείρισης και επαναλαμβανόμενος upstream controller | τηλεμετρία συσκευής και τοπολογία ORB, όχι μία διεύθυνση εξόδου |
| CDN/redirector | Διαχωρίζει το δημόσιο edge από το back-end C2 | γραμματική TLS/HTTP, certificate, routing και τεχνουργήματα λογαριασμού cloud | συσχέτιση edge με origin και ομαδοποίηση βάσει μοτίβου αιτημάτων |
| Νόμιμη web service | Ενσωματώνεται στην επιτρεπόμενη κίνηση GitHub/cloud/social | API token, αναγνωριστικά tenant/object και ασυνήθιστη αλυσίδα διεργασιών | διεργασία endpoint και σημασιολογία service/API |
| Φυσική/κυψελωτή/δορυφορική διαδρομή | Αλλάζει τη φαινομενική φυσική προέλευση | αρχεία RF, παρόχου, συνδρομητή, συσκευής και τοποθεσίας | συνδυασμός ραδιοφωνικών/φυσικών και δικτυακών στοιχείων |

## Δίκτυα επιχειρησιακών κόμβων αναμετάδοσης

Ένα **δίκτυο ORB** είναι ένας διαχειριζόμενος στόλος proxy που χρησιμοποιείται ως ενδιάμεση υπηρεσία. Η Mandiant τα διακρίνει σε δίκτυα με υποδομή που έχει προβλεφθεί εκ των προτέρων, αποτελούμενα από μισθωμένους servers, σε δίκτυα χωρίς τέτοια υποδομή, αποτελούμενα από παραβιασμένους routers/IoT, και σε υβριδικά. Μια ώριμη τοπολογία έχει τέσσερις λογικούς ρόλους:<sup>[[2]](#references)</sup>

1. **Administration server (ACOS):** διατηρεί απογραφή, διαπιστευτήρια, κατάσταση λειτουργίας και πολιτική δρομολόγησης.
2. **Access/relay node:** πιστοποιεί πελάτες ή operators· είναι το σταθερό σημείο εισόδου σε ένα μεταβαλλόμενο mesh.
3. **Traversal nodes:** ένα ή περισσότερα μισθωμένα ή παραβιασμένα συστήματα αναμεταδίδουν αδιαφανείς συνδέσεις.
4. **Exit/staging node:** παρουσιάζει την τελική διεύθυνση προέλευσης σε στόχους reconnaissance, exploitation ή C2.

Το mesh μπορεί να επιλέγει exits με βάση τη χώρα, το ASN, την καθυστέρηση ή τη διαθεσιμότητα και να εναλλάσσει μη υγιείς κόμβους. Πολλαπλές ομάδες απειλών μπορεί να νοικιάζουν το ίδιο δίκτυο. Η Mandiant παρατήρησε ότι ορισμένα ORB διατηρούσαν μια διεύθυνση IPv4 για μόλις 31 ημέρες· συνεπώς, συνιστά να αντιμετωπίζεται **το δίκτυο ως εξελισσόμενη οντότητα που μοιάζει με actor**, αντί να αποκλείεται μια παρωχημένη λίστα IP.<sup>[[2]](#references)</sup>

### Τι προσφέρει αυτό — και τι αποκαλύπτει

- Ο στόχος βλέπει μια exit που μπορεί να βρίσκεται γεωγραφικά κοντά και να φαίνεται οικιακή.
- Η exit βλέπει τον στόχο και το προηγούμενο hop, όχι κατ’ ανάγκη τον operator.
- Η υπηρεσία πρόσβασης βλέπει τον πελάτη και το αίτημα διαδρομής. Ένα ανεξάρτητα διαχειριζόμενο mesh μπορεί να διαχωρίζει τον πελάτη από τις exits, αλλά δημιουργεί ένα ισχυρό αρχείο αντισυμβαλλομένου.
- Επαναλαμβανόμενες θύρες, σειρά handshake, banners server, certificates, χρονικά παράθυρα λειτουργίας και σχέσεις controller μπορούν να αποκαλύψουν τον στόλο, ακόμη κι όταν οι IP εναλλάσσονται.
- Ένας παραβιασμένος router συχνά δεν διαθέτει τηλεμετρία endpoint, αλλά ο ISP του εξακολουθεί να έχει δεδομένα συνδρομητή και ροών· μια κατάσχεση αποκαλύπτει τεχνουργήματα implant/configuration.

{% hint style="info" %}
Για μια εξουσιοδοτημένη άσκηση, αναπαραγάγετε την τοπολογία με VM ή routers που ανήκουν στον οργανισμό και διατηρήστε τον χάρτη απόδοσης του controller. Μη χρησιμοποιείτε ανοιχτά proxies ή συσκευές τρίτων. Ο [οδηγός εργαστηρίου](authorized-adversary-emulation-labs.md#lab-1-owned-orb-and-redirector-chain) δημιουργεί την ίδια δομή hop που είναι ορατή στους defenders, χωρίς να γίνεται θύμα κάποιος ενδιάμεσος.
{% endhint %}

## Residential και mobile δίκτυα proxy

Οι υπηρεσίες residential proxy αντιστοιχίζουν sessions σε διευθύνσεις ευρυζωνικής σύνδεσης καταναλωτών· τα mobile proxies εξέρχονται μέσω pools carrier NAT. Η προσφορά μπορεί να προέρχεται από συσκευές που έχουν εγγραφεί ρητά, SDK/proxyware ενσωματωμένα σε εφαρμογές καταναλωτών, μεταπωλητές ή malware. Αυτές οι προελεύσεις δεν είναι ισοδύναμες: η απουσία ενημερωμένης συγκατάθεσης μετατρέπει μια υπηρεσία προστασίας ιδιωτικότητας σε παραβιασμένη υποδομή.

Οι τρόποι εναλλαγής επηρεάζουν τον εντοπισμό:

- **εναλλαγή ανά αίτημα** προκαλεί γρήγορες ασυνέχειες IP και ASN/γεωγραφικής θέσης, ενώ η ταυτότητα σε υψηλότερα επίπεδα παραμένει σταθερή·
- **sticky sessions** διατηρούν μια exit για λεπτά ή ώρες, μοιάζοντας με συνηθισμένο συνδρομητή·
- **backconnect gateways** εμφανίζουν στον πελάτη ένα endpoint broker και επιλέγουν exits εσωτερικά·
- **mobile pools** τοποθετούν πολλούς πραγματικούς συνδρομητές πίσω από μικρό αριθμό διευθύνσεων carrier NAT, καθιστώντας δαπανηρό τον αποκλεισμό μιας IP.

Οι defenders πρέπει να συσχετίζουν την IP με το authenticated session, το TLS/client fingerprint, τη σειρά HTTP, το device cookie και τη συμπεριφορά. Μια υποτιθέμενα τοπική residential σύνδεση που ακολουθείται από άλλη χώρα, ενώ όλα τα χαρακτηριστικά υψηλότερων επιπέδων παραμένουν ίδια, αποτελεί ισχυρότερη ένδειξη από τη φήμη και μόνο. Αντίθετα, η κοινή χρήση διευθύνσεων και η εναλλαγή μεταξύ κεραιών κινητής δημιουργούν νόμιμη μεταβλητότητα, επομένως μην αντιμετωπίζετε ποτέ την ταξινόμηση residential/proxy ως τελική ετυμηγορία.

### Control planes proxyware και επικάλυψη μεταπωλητών

Μην μοντελοποιείτε ένα residential pool ως επίπεδη λίστα exits. Η ανάλυση του οικοσυστήματος IPIDEA αποκάλυψε ένα επαναχρησιμοποιήσιμο **control plane δύο επιπέδων**: ένα ενσωματωμένο SDK αναφέρει πρώτα μεταδεδομένα συσκευής/εγγραφής σε ένα domain Tier One και λαμβάνει στοιχεία προγραμματισμού, μαζί με ζεύγη IP:port `connect`/`proxy` του Tier Two. Ο κόμβος ελέγχει περιοδικά τη θύρα connect του Tier Two για μια κωδικοποιημένη εργασία, ανοίγει μια δεύτερη σύνδεση στη συζευγμένη θύρα proxy και αναμεταδίδει τα παρεχόμενα bytes στον ζητούμενο προορισμό. SDK και μάρκες proxy που φαινομενικά διέφεραν είχαν ξεχωριστά domains εντοπισμού, αλλά κατέληγαν σε κοινή υποδομή Tier Two και επικαλυπτόμενα pools εξόδου, μέσω κοινής ιδιοκτησίας και σχέσεων μεταπώλησης.<sup>[[13]](#references)</sup>

```text
enrolled node -> Tier One domain        -> Tier Two IP:port pairs
enrolled node -> Tier Two connect port  -> destination + connection ID
enrolled node -> Tier Two proxy port   <-> customer bytes -> destination
```

Αυτό δημιουργεί πιο ανθεκτικά hunting pivots από έναν αποκλεισμό residential IP:<sup>[[13]](#references)</sup>

- μια μη αναμενόμενη διεργασία utility, VPN, παιχνιδιού ή ενσωματωμένης συσκευής στέλνει ένα σταθερό device ID/customer key και λαμβάνει μια μεταβαλλόμενη λίστα διακομιστών·
- το endpoint επικοινωνεί περιοδικά με μια direct IP σε ασυνήθιστη θύρα και, στη συνέχεια, συνδέεται αμέσως με άλλη θύρα στην ίδια διεύθυνση πριν ανοίξει socket προς νέο προορισμό·
- διάφορες φαινομενικά διαφορετικές μάρκες μοιράζονται διευθύνσεις Tier Two, γραμματική πρωτοκόλλου, κώδικα SDK ή επικάλυψη exit-node·
- διαφορετικές εφαρμογές που επικοινωνούν με διαφορετικά domains Tier One λαμβάνουν διευθύνσεις από την ίδια δεξαμενή Tier Two.

Η επικάλυψη περιορίζει επίσης την απόδοση ευθύνης: το να εντοπιστεί μια IP στη διαφημιζόμενη δεξαμενή ενός παρόχου δεν αποδεικνύει ποιος μεταπωλητής, πελάτης ή threat actor τη χρησιμοποίησε τη σχετική χρονική στιγμή. Διατηρήστε τις χρονικές σημάνσεις ροών, τη γενεαλογία διεργασιών, τα σώματα των αποκρίσεων Tier One και τα αναγνωριστικά εργασιών Tier Two.<sup>[[13]](#references)</sup> Σε μια εξουσιοδοτημένη άσκηση, προσομοιώστε αυτή την ιεραρχία μόνο με endpoints που ανήκουν στον οργανισμό· μην εγγράφετε ποτέ συσκευές καταναλωτών ή λογισμικό proxy τρίτων.

## Αλυσίδες proxy πολλαπλών αλμάτων

Το MITRE διακρίνει τους εξωτερικούς proxy από τους **multi-hop proxies (T1090.003)**. Το σημαντικό χαρακτηριστικό δεν είναι ο αριθμός των αλμάτων, αλλά ο διαχωρισμός της γνώσης και της διαχείρισης.<sup>[[3]](#references)</sup>

```text
operator --encrypted--> entry A --encrypted/relayed--> exit B --> target
              sees source                         sees destination
```

Αν ένα μέρος διαχειρίζεται τα A και B, τα κοινόχρηστα logs ή ο χρονισμός της κίνησης μπορούν να αποκαλύψουν τη διαδρομή. Η προσθήκη διαδοχικών εμπορικών VPN από το ίδιο endpoint/account μπορεί να αυξήσει την καθυστέρηση, χωρίς να εξαλείψει τα κοινά στοιχεία ταυτότητας, πληρωμής και χρονισμού. Το Tor περιορίζει αυτό το πρόβλημα χρησιμοποιώντας ανεξάρτητα επιλεγμένα relays και κοινό σχεδιασμό client, αλλά ένα διαδραστικό δίκτυο χαμηλής καθυστέρησης δεν μπορεί να εγγυηθεί προστασία από παρατηρητή που μετρά και τα δύο άκρα.

Συνηθισμένες αστοχίες είναι η παράκαμψη μέσω DNS ή IPv6, οι εφαρμογές που ανοίγουν δικά τους sockets, η απευθείας πρόσβαση της κίνησης διαχείρισης στα relays, η συγχρονισμένη δραστηριότητα, η επαναχρησιμοποίηση κλειδιών SSH και η σύνδεση σε λογαριασμούς που αποκαλύπτουν την ταυτότητα. Η σωστή επαλήθευση είναι μια δοκιμή αστοχίας: σταματήστε κάθε relay με τη σειρά και επιβεβαιώστε ότι ο φόρτος εργασίας δεν μπορεί να στραφεί σε μη κρυπτογραφημένη διαδρομή.

### Κατάρρευση tunnel και διαρροή προς upstream

Μια αρχιτεκτονική relay συχνά αποδίδεται ευκολότερα όταν αστοχεί. Η Unit 42 κατέγραψε μια κατασκοπευτική διαδρομή πολλαπλών επιπέδων, με VPS που έβλεπαν τα θύματα, VPS relay, οικιακά proxy, Tor και άλλες υπηρεσίες proxy· όταν παραλειπόταν ή κατέρρεε ένα tunnel, η κρυφή upstream υποδομή συνδεόταν απευθείας με τα relay και τα συστήματα που έβλεπαν τα θύματα. Η ίδια έρευνα χρησιμοποίησε επίσης ένα πιστοποιητικό X.509, το οποίο εκτέθηκε για λίγο σε upstream υποδομή, ως pivot μεταξύ επιπέδων.<sup>[[14]](#references)</sup>

Διατηρήστε χωριστά το **data plane** (`victim <-> exit`) και το **control plane** (`operator/upstream -> relay administration`). Διατηρήστε logs εισερχόμενης κίνησης και authentication σε κάθε επίπεδο που ελέγχετε, ιστορικό πιστοποιητικών και σύντομες αποτυχημένες συνδέσεις—όχι μόνο επιτυχημένες συνεδρίες C2. Μια πηγή που εμφανίζεται μόνο κατά τις διακοπές λειτουργίας των relay ή διαχειρίζεται απευθείας πολλούς κόμβους που βλέπουν τα θύματα αποτελεί ισχυρότερη ένδειξη για upstream υποδομή απ’ ό,τι ένα συνηθισμένο exit, αλλά το ASN/η γεωγραφική τοποθεσία της παραμένει υπόθεση, όχι απόδειξη της ταυτότητας του operator.

Σε ένα εξουσιοδοτημένο lab, ο φόρτος εργασίας πρέπει να αποτυγχάνει με ασφάλεια. Για έναν φόρτο εργασίας απομονωμένο σε Linux network namespace, η πρώτη διαδρομή πρέπει να χρησιμοποιεί το tunnel· μετά την αφαίρεσή του, τόσο το αίτημα όσο και η αναζήτηση διαδρομής πρέπει να αποτυγχάνουν, αντί να επιλέγουν τη φυσική uplink:

```bash
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: dev wg0
ip -n workload link set wg0 down
ip netns exec workload curl --fail --connect-timeout 3 \
  --resolve "$OWNED_TEST_HOST:443:$OWNED_TEST_IP" "https://$OWNED_TEST_HOST/health"
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: unreachable
```

Επαναλάβετε τη δοκιμή για DNS και IPv6, καθώς και σε κάθε όριο relay. Αν οποιοδήποτε probe πετύχει, καταγράψτε την πραγματική διεύθυνση interface/source πριν διορθώσετε το policy routing ή το firewall· αυτή η παρατήρηση είναι το attribution leak που θα έβλεπε ένας ερευνητής.

## Επίπεδα redirector και διαμόρφωση κίνησης

Ένας δημόσιος **redirector** δέχεται κίνηση που αντιστοιχεί σε γραμματική ειδική για την εκάστοτε επιχείρηση και την προωθεί σε έναν προστατευμένο team server. Οτιδήποτε άλλο μπορεί να απορριφθεί ή να εξυπηρετηθεί με αβλαβές περιεχόμενο.

```text
implant/browser -> CDN or redirector -> relay -> team server
                       |
                 request policy
           host + path + method + header + time
```

Πολλαπλά επίπεδα περιορίζουν την έκθεση: η καύση ενός δημόσιου domain δεν χρειάζεται να εκθέσει τον server της ομάδας. Τα CDN προσθέτουν χωρητικότητα anycast και ένα αξιόπιστο εξωτερικό domain, αλλά ο λογαριασμός CDN και τα edge logs γίνονται σημεία απόδοσης. Τα TLS fingerprints, το ιστορικό πιστοποιητικών, τα χαρακτηριστικά paths/η σειρά των headers, τα μεγέθη αποκρίσεων, η συμπεριφορά ανακατεύθυνσης και οι allowlists των origin μπορούν να ομαδοποιήσουν φαινομενικά άσχετες προσόψεις.

Για τον εντοπισμό, καταγράψτε τα πεδία του reverse proxy πριν από την κανονικοποίηση, συγκρίνετε τα SNI/Host/authority, ελέγξτε σπάνιους συνδυασμούς headers, ομαδοποιήστε τα σώματα αποκρίσεων και τα TLS fingerprints και αναζητήστε επικαλύψεις ρυθμίσεων στα audit logs του cloud/CDN. Για εξουσιοδοτημένες red team, αποφύγετε να αντιγράφετε πραγματικό brand ή να τοποθετείτε τη συλλογή διαπιστευτηρίων πίσω από άσχετο τρίτο μέρος.

## Domain fronting και domainless fronting

Στο κλασικό **domain fronting (T1090.004)**, η σύνδεση TLS διαφημίζει στο SNI ένα επιτρεπόμενο front domain, ενώ το κρυπτογραφημένο HTTP `Host` ή το HTTP/2 `:authority` ζητά διαφορετικό back-end domain. Ένα συνεργαζόμενο CDN δρομολογεί με βάση την εσωτερική τιμή. Ένας παρατηρητής δικτύου χωρίς αποκρυπτογράφηση TLS βλέπει το front· το CDN βλέπει και τις δύο τιμές, καθώς και το origin. Σε παραλλαγές domainless, το SNI μπορεί να είναι κενό, ενώ κάποιο άλλο πεδίο δρομολόγησης επιλέγει τον προορισμό.<sup>[[4]](#references)</sup>

Δεν πρόκειται για μαγική πλαστοπροσωπία: λειτουργεί μόνο όταν ο ενδιάμεσος επιτρέπει σκόπιμα ή κατά λάθος την ασυμφωνία και γνωρίζει πώς να δρομολογήσει το εσωτερικό όνομα. Μεγάλοι πάροχοι έχουν περιορίσει το fronting μεταξύ λογαριασμών. Το Encrypted ClientHello (ECH) αλλάζει όσα μπορεί να δει ένας παρατηρητής στη διαδρομή, αλλά δεν διαγράφει τα αρχεία του CDN, του endpoint ή της εφαρμογής.

Τα σημεία εντοπισμού περιλαμβάνουν:

- την προέλευση διεργασιών στο endpoint και προορισμούς που δεν αναμένονται για τη συγκεκριμένη εφαρμογή·
- ασυμφωνία SNI και HTTP authority, όπου η επιθεώρηση TLS είναι νόμιμη και διαθέσιμη·
- logs του CDN που δείχνουν ότι ένα tenant/front δρομολογεί προς άλλο authority/origin·
- ασυνήθιστες συνεδρίες μεγάλης διάρκειας ή περιοδικές συνδέσεις προς μια υπηρεσία που συνήθως χρησιμοποιείται διαδραστικά·
- σταθερά μεγέθη και ρυθμό κρυπτογραφημένων ροών, παρά τις αλλαγές στα front domains.

Το ασφαλές lab προσομοιώνει την ασυμφωνία δρομολόγησης σε reverse proxy που σας ανήκει· δεν καταχράται δημόσιο CDN.

## Δυναμική επίλυση: DDNS, DGA και fast flux

Η δυναμική επίλυση αποσυνδέει μια λογική υπηρεσία από τη σταθερή υποδομή:

- **DDNS:** ένας πιστοποιημένος client ενημερώνει ένα σταθερό όνομα όταν αλλάζει η διεύθυνσή του.
- **DGA:** το endpoint παράγει ονόματα domain από ένα seed, συχνά από τον χρόνο ή ένα κλειδί, αλλά μερικές φορές από μεταβαλλόμενο δημόσιο περιεχόμενο· ο operator ρυθμίζει το DNS για το ενεργό όνομα.<sup>[[17]](#references)</sup>
- **Fast flux:** ένα όνομα επιστρέφει ένα σύνολο διευθύνσεων παραβιασμένων συστημάτων/proxy που αλλάζει γρήγορα, συχνά με χαμηλά TTL.
- **Double flux:** περιστρέφονται τόσο οι διευθύνσεις υπηρεσίας όσο και οι διευθύνσεις των authoritative name server, αποκρύπτοντας και το επίπεδο ελέγχου.

Το fast flux είναι ένα μοτίβο κατανομής φορτίου που χρησιμοποιείται από αντιπάλους, όχι απλώς «πολλές απαντήσεις DNS». Ισχυρότερες ενδείξεις συνδυάζουν χαμηλό TTL, μεγάλο αριθμό μοναδικών διευθύνσεων, ευρεία διασπορά ASN/γεωγραφικών περιοχών, σύντομη διάρκεια ζωής κόμβων, επαναλαμβανόμενη συμπεριφορά εφαρμογών και ύποπτο ιστορικό καταχώρισης. Τα CDN παρουσιάζουν νόμιμα αρκετές από αυτές τις ιδιότητες. Η MITRE συνιστά τη συσχέτιση της συμπεριφοράς DNS με τη διεργασία και τις επόμενες συνδέσεις.<sup>[[5]](#references)</sup>

Ένα DGA μπορεί να εντοπιστεί μέσω λεξικής εντροπίας, μοτίβων συμφώνων/ψηφίων, εξάρσεων NXDOMAIN, συγχρονισμένων domains που εμφανίζονται για πρώτη φορά και του πλαισίου της διεργασίας. Τα DGA που βασίζονται σε λίστες λέξεων και τα γενετικά μοντέλα παρακάμπτουν απλούς κανόνες εντροπίας, καθιστώντας πιο σημαντική την ομαδοποίηση σε επίπεδο στόλου με βάση τον χρόνο και τη συσχέτιση με την προέλευση στο endpoint.

### Μεταβαλλόμενο seed εικόνας για DGA λίστας λέξεων

Ένα DGA δεν χρειάζεται να βασίζεται στον χρόνο. Ένας loader ανακτά τη σελίδα ενός δημόσιου καναλιού Telegram, διαβάζει το `src` του στοιχείου `tgme_page_photo_image`, κατεβάζει την εικόνα προφίλ και κατακερματίζει τα **τελευταία 50 bytes του αρχείου** αντί για τα αποκωδικοποιημένα pixel της. Τέσσερα hash seed επιλέγουν ένα επίθετο, ένα ουσιαστικό, ένα ρήμα και έναν αριθμό. Η αλλαγή της εικόνας αλλάζει το παραγόμενο όνομα DNS χωρίς να χρειάζεται να διανεμηθεί νέος client. Διατηρήστε ακριβώς τα ίδια bytes της ληφθείσας εικόνας και την ίδια σειρά λίστας λέξεων και στις δύο πλευρές· η επανακωδικοποίηση της εικόνας ή η αναδιάταξη μιας λίστας παράγει διαφορετικά ονόματα.<sup>[[17]](#references)</sup>

Με τις λίστες λέξεων που ανακτήθηκαν από τον client, αυτό αναπαράγει το βήμα επιλογής ονόματος. Το byte-wise hash της πηγής χρησιμοποιεί συσσωρευτή 64-bit, πολλαπλασιαστή `0x1000193` και ξεχωριστά seed για κάθε στοιχείο:<sup>[[17]](#references)</sup>

<details>
<summary>Αναπαραγωγή της επιλογής ονόματος λίστας λέξεων με seed εικόνας</summary>

```python
def wordlist_domain(image: bytes, adjectives: list[str], nouns: list[str], verbs: list[str], suffix: str) -> str:
    if len(image) < 50:
        raise ValueError("Image must contain at least 50 bytes")
    tail = image[-50:]
    def hashed(seed: int) -> int:
        value = seed
        for byte in tail:
            value = ((value ^ byte) * 0x1000193) & 0xFFFFFFFFFFFFFFFF
        return value
    a = adjectives[hashed(0x811C9DC5) % len(adjectives)]
    n = nouns[hashed(0xAF0154A5) % len(nouns)]
    v = verbs[hashed(0xFE5439E4) % len(verbs)]
    digit = hashed(0xFFA7471A) % 1000
    return f"{a}-{n}-{v}-{digit}.{suffix}"
```

</details>

Σε αντίθεση με έναν [dead-drop resolver](#web-services-and-dead-drop-resolvers) που δημοσιεύει το ίδιο το endpoint, το δημόσιο αντικείμενο εδώ παρέχει μόνο ένα μεταβλητό seed· ο client υπολογίζει το endpoint τοπικά.

Στη συνέχεια, γίνεται αναζήτηση του ονόματος που δημιουργήθηκε για εγγραφή DNS TXT μέσω του `https://dns.google/resolve?name=<domain>&type=TXT`. Ο client αποκωδικοποιεί σε Base64 το πεδίο `data` της απόκρισης JSON, επαληθεύει μια υπογραφή Ed25519 με το ενσωματωμένο δημόσιο κλειδί και μόνο τότε αποκρυπτογραφεί την εντολή με AES-ECB. Το παρατηρημένο plaintext αρχίζει με έναν επιλογέα μεθόδου και ένα URL για ένα κρυπτογραφημένο payload. Ο έλεγχος της υπογραφής σημαίνει ότι μια επιλύσιμη εγγραφή TXT από μόνη της δεν μπορεί να παρέχει αποδεκτές εντολές.<sup>[[17]](#references)</sup>

## Παραβιασμένα domains και domain shadowing

Ένας actor μπορεί να παραβιάσει έναν λογαριασμό registrar/DNS, να καταλάβει ένα παρατημένο subdomain ή να προσθέσει εγγραφές κάτω από ένα κατά τα άλλα αξιόπιστο domain. Το **Domain shadowing** διατηρεί το νόμιμο apex, ενώ μεγάλος αριθμός subdomains που ελέγχονται από τον attacker δείχνουν σε μεταβαλλόμενους hosts διανομής ή C2. Αξιοποιεί την παλαιότητα και τη φήμη του domain και μπορεί να παρακάμψει τον αποκλεισμό σε επίπεδο domain.<sup>[[6]](#references)</sup>

Οι defenders χρειάζονται αρχεία καταγραφής ελέγχου registrar και authoritative DNS, MFA, κλειδώματα registry/registrar, ειδοποιήσεις για νέες delegations/API tokens/name servers, παρακολούθηση certificate transparency και καταγραφή των cloud resources στα οποία αναφέρονται οι εγγραφές DNS. Ερευνήστε ανεξάρτητα την επίλυση και το ιστορικό πιστοποιητικών ενός subdomain, χωρίς να βασίζεστε στη φήμη του apex.

## Web services και dead-drop resolvers

Ένας **dead-drop resolver (T1102.001)** αποθηκεύει έναν κωδικοποιημένο δείκτη προς το τρέχον C2 μέσα σε μια νόμιμη ανάρτηση, ένα profile, ένα έγγραφο, ένα repository, ένα cloud object ή ένα πεδίο blockchain. Το malware ανακτά το δημόσιο αντικείμενο, αποκωδικοποιεί ένα domain/IP και επικοινωνεί με το επόμενο στάδιο. Οι αμφίδρομες παραλλαγές ανταλλάσσουν εντολές ή αρχεία μέσω των API της υπηρεσίας.<sup>[[7]](#references)</sup>

Μια παραλλαγή resolver ειδικά για το GitHub χρησιμοποιεί το Issues Search API μόνο όταν αποτυγχάνει ένα authenticated repository channel. Ο client αναζητά issues που αντιστοιχούν στην τρέχουσα ημερομηνία, στο repository και στον τύπο issue, ακολουθεί το URL σχολίων κάθε issue και εξάγει ciphertext ανάμεσα στους δείκτες `<!--` και `-->`. Μετά την αποκρυπτογράφηση ανά host, βάσει ημερομηνίας, πεδία όπως τα `Owner`, `LicRepo` και `LicToken` αντικαθιστούν τον κύριο owner, το path και το token του repository. Έτσι, ο operator μπορεί να αλλάζει credentials και endpoints χωρίς να αντικαθιστά τον client· το σχόλιο του issue λειτουργεί ως resolver, ενώ τα αρχεία του repository παραμένουν το channel εντολών.<sup>[[15]](#references)</sup>

Μια παραλλαγή για Android επιλέγει κατά την εκκίνηση μία από δύο δημόσιες σελίδες Telegram και εξάγει ciphertext ανάμεσα σε δύο εμφανίσεις ενός marker ενσωματωμένου στο APK. Αποκωδικοποιεί την τιμή με Base64URL και την αποκρυπτογραφεί με AES-128-CBC: τα πρώτα 16 bytes του `SHA-256(marker)` είναι το key και τα υπόλοιπα 16 bytes είναι το IV. Το plaintext είναι το πραγματικό C2 base URL, όχι το URL της σελίδας Telegram. Κατά την αναπαραγωγή της επίλυσης, διατηρήστε το περιεχόμενο της σελίδας και τον ακριβή marker· η αλλαγή της δημόσιας σελίδας αλλάζει το endpoint χωρίς να απαιτείται ανακατασκευή του APK.<sup>[[16]](#references)</sup>

Αυτό προσφέρει ανθεκτικότητα και αποκρύπτει το back-end C2 από τη στατική ανάλυση binary. Δημιουργεί επίσης σταθερά αναγνωριστικά αντικειμένων, tenants, repositories, API και μοτίβων πρόσβασης. Οι defenders πρέπει να συσχετίζουν:

1. τη διεργασία που επικοινώνησε με την υπηρεσία·
2. το ακριβές API path/object και το hash της απόκρισης·
3. τη δραστηριότητα αποκωδικοποίησης ή επεξεργασίας strings·
4. τη νέα εξερχόμενη σύνδεση λίγο αργότερα· και
5. την ίδια συμπεριφορά σε άλλα σημεία του στόλου συστημάτων.

Ο αποκλεισμός όλου του GitHub, του cloud storage ή των social media είναι σπάνια εφαρμόσιμος. Οι πολιτικές εξερχόμενης κίνησης που λαμβάνουν υπόψη την υπηρεσία και η συσχέτιση σε επίπεδο διεργασίας υπερτερούν του αποκλεισμού μόνο βάσει domain.

## Personas, λογαριασμοί και διακριτά procurement compartments

Η ανωνυμία της υποδομής αποτυγχάνει όταν ένα persona, email ανάκτησης, τηλέφωνο, μέσο πληρωμής, browser ή IP διαχειριστή συνδέει διαφορετικά compartments. Επιχειρήσεις που συνδέονται με κράτη έχουν καλλιεργήσει social profiles, email identities και cloud accounts πολύ πριν τα χρησιμοποιήσουν· το ATT&CK το καταγράφει ως Establish Accounts (T1585), με υποτεχνικές για social, email και cloud.<sup>[[8]](#references)</sup>

Ένας defender ή ερευνητής δημιουργεί ένα γράφημα με βάση:

- τον χρόνο δημιουργίας και πρώτης σύνδεσης, την τοπική ρύθμιση, τη ζώνη ώρας και το πρόγραμμα εργασίας·
- τα πεδία ανάκτησης, τις συσκευές MFA, τα έγγραφα ταυτοποίησης και τα μέσα πληρωμής·
- τα fingerprints browser/TLS και το ιστορικό δικτύων προέλευσης·
- την επαναχρησιμοποίηση avatar, την προέλευση εικόνων, το ύφος γραφής και την ανάπτυξη του social graph·
- κοινό registrant domain, name server, πιστοποιητικό, analytics ID ή commit repository·
- ενέργειες στο management plane που παρακάμπτουν την αρχιτεκτονική δημόσιου relay.

Για μια εξουσιοδοτημένη red team, τα synthetic personas πρέπει να είναι καταγεγραμμένα για τον controller της άσκησης, να χρησιμοποιούν κανάλια ανάκτησης/πληρωμής που ανήκουν στον οργανισμό, να αποφεύγουν την πλαστοπροσωπία πραγματικών ατόμων που δεν εμπλέκονται και να έχουν προγραμματισμένη απόσυρση. Το SOC μπορεί να παραμένει στο σκοτάδι· η επιχείρηση όμως δεν πρέπει να είναι χωρίς λογοδοσία.

## Αναδυόμενα σύνθετα μοτίβα για threat modeling

Τα παρακάτω είναι **συνδυασμοί με γνώμονα την άμυνα**, όχι ισχυρισμοί ότι κάποιος κατονομαζόμενος actor έχει αναπτύξει ακριβώς αυτά τα σχέδια. Συνδυάζουν ήδη παρατηρημένα primitives και είναι χρήσιμες υποθέσεις για purple-team ασκήσεις.

### Ασύμμετρες εντολές μονής κατεύθυνσης

Οι εντολές φτάνουν μέσω δημόσιας, broadcast ή append-only πηγής, ενώ τα αποτελέσματα αποστέλλονται με καθυστέρηση μέσω άσχετου καναλιού. Παραδείγματα του primitive είναι η μονόδρομη επικοινωνία μέσω web service και τα dead drops. Ο διαχωρισμός εμποδίζει μια μεμονωμένη ροή να φαίνεται αμφίδρομη και δυσκολεύει την απλή συσχέτιση αιτήματος/απόκρισης.<sup>[[9]](#references)</sup>

**Ανίχνευση:** διατηρήστε τα reads σε επίπεδο αντικειμένου και, στη συνέχεια, συσχετίστε τις αλλαγές κατάστασης διεργασιών με μεταγενέστερες εξερχόμενες μεταφορές σε μεγαλύτερο χρονικό διάστημα. Αναζητήστε σπάνιες διεργασίες που διαβάζουν το ίδιο δημόσιο αντικείμενο, ακόμη κι αν δεν ακολουθεί άμεση απόκριση.

### Προώθηση σε κανάλι πολλαπλών σταδίων

Ένα διακριτικό πρώτο στάδιο συλλέγει στοιχεία και προωθεί μόνο επιλεγμένα συστήματα σε ένα άσχετο κανάλι δεύτερου σταδίου. Το δεύτερο endpoint, πρωτόκολλο και η διεργασία μπορεί να μη μοιράζονται υποδομή με το πρώτο. Αυτό περιορίζει την έκθεση της πιο ισχυρής υποδομής και μοντελοποιείται ρητά ως ATT&CK T1104.<sup>[[10]](#references)</sup>

**Ανίχνευση:** συσχετίστε `first network process -> downloaded/configured state -> new process or injection -> unrelated destination`· μην κλείνετε το περιστατικό αφού αποκλείσετε το πρώτο domain.

### Μετάφραση relay μεταξύ πρωτοκόλλων

Διαφορετικά hops μεταφράζουν HTTPS, QUIC, WebSocket, DNS, SSH ή ένα API message queue αντί να προωθούν διαφανώς πακέτα. Η μετάφραση αφαιρεί ένα ενιαίο end-to-end fingerprint πρωτοκόλλου, αλλά δημιουργεί gateways με χαρακτηριστικό χρονισμό, buffering και σημασιολογική μετατροπή. Το protocol tunneling (T1572) μπορεί να συνδυαστεί με proxies και μίμηση υπηρεσιών.<sup>[[11]](#references)</sup>

**Ανίχνευση:** αναζητήστε gateway hosts που λαμβάνουν ένα πρωτόκολλο και ξεκινούν άλλο, με στενά συσχετισμένη συμπεριφορά σε bytes/χρόνο· συγκρίνετε τον σκοπό του endpoint με το πρωτόκολλο που μεταφέρεται στην πράξη.

### Παθητική ενεργοποίηση σε edge devices

Αντί να στέλνει beacon, ένα implant παρακολουθεί κίνηση που φτάνει ήδη σε router/VPN και ενεργοποιείται μόνο με μια magic value, ένα μοτίβο source-port ή ένα authenticated token. Η κανονική κίνηση συνεχίζει προς την πραγματική υπηρεσία. Το ATT&CK αποκαλεί αυτό Traffic Signaling (T1205) και διαθέτει τεκμηριωμένα παραδείγματα σε network devices και APT.<sup>[[12]](#references)</sup>

**Ανίχνευση:** ακεραιότητα firmware/αρχείων, raw packet capture κατά τη διάρκεια εξουσιοδοτημένης έρευνας, μη αναμενόμενα socket filters και διαφοροποιημένη συμπεριφορά υπηρεσίας. Η απουσία περιοδικού beacon δεν αποδεικνύει ότι μια edge device είναι καθαρή.

### Περιστροφή serverless και ephemeral origins

Ένα front διατηρεί σταθερή λογική ταυτότητα, ενώ functions/containers βραχείας διάρκειας χειρίζονται μεμονωμένα στάδια σε διάφορες regions/accounts. Αυτό μειώνει τον χρόνο ζωής των δεδομένων στον δίσκο και την εξάρτηση από σταθερές origin IPs, αλλά τα telemetry δημιουργίας στο control plane, image/layer, role, secret, request ID και billing γίνονται το διαρκές γράφημα συσχετίσεων.

**Ανίχνευση:** διατηρήστε τα cloud audit και invocation logs εκτός του workload· ομαδοποιήστε deployment templates, roles, environment keys και σχέσεις front-to-origin.

### Ποικιλία privacy layers

Μια επιχείρηση μπορεί σκόπιμα να αποφεύγει μια ομοιογενή αλυσίδα: για παράδειγμα, ένα κανάλι χρησιμοποιεί leased relay, οι εντολές μεταδίδονται μέσω δημόσιου object, η έξοδος γίνεται μέσω cellular link εργαστηρίου που ανήκει στον οργανισμό και η διαχείριση χρησιμοποιεί ξεχωριστό δίκτυο του οργανισμού. Αυτό μειώνει την αξία της παραβίασης ενός παρόχου, αλλά αυξάνει τον κίνδυνο χρονικής συσχέτισης μεταξύ layers και επιχειρησιακών λαθών.

**Ανίχνευση:** δημιουργήστε χρονολόγια εκστρατειών που συνδυάζουν αισθητήρες identity, DNS, SaaS, δικτύου και cloud. Αναζητήστε συγχρονισμένες αλλαγές κατάστασης αντί για πανομοιότυπους δείκτες.

### Αποκεντρωμένα dead drops ή dead drops σε transparency logs

Ένας actor μπορεί να τοποθετήσει έναν μικρό κρυπτογραφημένο δείκτη σε οποιοδήποτε ανθεκτικό, δημόσιο append-only σύστημα, content-addressed store ή feed τύπου transparency. Το δημόσιο αντικείμενο είναι ανθεκτικό, αλλά το ακριβές index/content hash και η συμπεριφορά polling του client γίνονται σταθερά αναγνωριστικά.

**Ανίχνευση:** καταγράψτε τα πλήρη API/object identifiers και τα hashes των αποκρίσεων· ειδοποιήστε για ασυνήθιστες διεργασίες που κάνουν polling σε immutable objects και ακολουθούνται από αποκωδικοποίηση ή νέες συνδέσεις.

### Λειτουργίες store-and-forward με καθυστέρηση

Το διαδραστικό C2 δημιουργεί ισχυρή χρονική συσχέτιση. Ένας σχεδιασμός store-and-forward ομαδοποιεί κρυπτογραφημένες εργασίες και επιστρέφει αποτελέσματα λεπτά ή ώρες αργότερα, μέσω διαφορετικής queue ή φυσικής μεταφοράς. Θυσιάζει την απόκριση για να μειώσει τη συσχέτιση end-to-end βάσει χρονισμού.

**Ανίχνευση:** διευρύνετε τα χρονικά παράθυρα συσχέτισης, μοντελοποιήστε την περιοδική πρόσβαση στις queues και εξετάστε το staging στα endpoints. Η ομαδοποίηση μεταφέρει το σήμα από τον χρονισμό πακέτων στη συμπεριφορά προγραμματισμένων διεργασιών/αρχείων· δεν το εξαφανίζει.

## Ανασκόπηση σχεδιασμού: σκεφτείτε με βάση τους παρατηρητές

Για κάθε διαδρομή, συμπληρώστε αυτόν τον πίνακα πριν από την ανάπτυξη και μετά τη συλλογή:

| Layer | Βλέπει την πηγή; | Βλέπει τον προορισμό; | Βλέπει το περιεχόμενο; | Σταθερά αναγνωριστικά | Διατήρηση/νομικά υπεύθυνος |
|---|---:|---:|---:|---|---|
| local network/carrier | | | | | |
| entry/access service | | | | | |
| traversal operator(s) | | | | | |
| exit/redirector/CDN | | | | | |
| authoritative DNS/registrar | | | | | |
| target | | | | | |
| πάροχος λογαριασμού/πληρωμών | | | | | |

Αν ένας συνηθισμένος πάροχος μπορεί να συμπληρώσει κάθε στήλη, η αρχιτεκτονική προσφέρει απόκρυψη από τον στόχο, αλλά όχι ισχυρό διαχωρισμό. Αν κανένας εσωτερικός controller δεν μπορεί να αντιστοιχίσει τη δραστηριότητα με μια ανάθεση, η αρχιτεκτονική είναι ακατάλληλη για επαγγελματικό red teaming.
