# 攻撃インフラストラクチャと帰属回避

{{#include ../banners/hacktricks-training.md}}

単一のプロキシだけで、意味のある匿名性を得られることはほとんどありません。実際のキャンペーンでは、**分離グラフ**を構築します。オペレーターはアクセスノードに接続し、経由ノードによってそのノードを出口から隠し、リダイレクターで実際のC2を保護し、使い捨てのドメイン名で公開エッジを指し示します。

あらゆる経路について、標準化された長所・短所・導入方法・検知の観点を確認するには、[匿名インターネットアクセス技術カタログ](anonymous-internet-access-techniques.md)を参照してください。このページでは、敵対的なインフラストラクチャの構成をさらに詳しく解説します。

```text
operator -> access relay -> traversal mesh -> exit/redirector -> target
                |                 |                |
          account/provider   relay operator   target telemetry
```

ターゲットが最後に観測したアドレスは、経路を示す証拠ではありますが、誰がキーボードを操作していたかの証明にはなりません。MITREは主な構成要素を、Acquire Infrastructure (T1583)、Compromise Infrastructure (T1584)、Proxy (T1090)、Dynamic Resolution (T1568)、Web Service (T1102)に分類しています。<sup>[[1]](#references)</sup>

## Operational relay box networks

**ORB network**は、中継サービスとして使われる管理型プロキシ群です。Mandiantは、リースサーバーで構成されるプロビジョニング済みネットワーク、侵害されたルーター／IoTで構成される非プロビジョニングネットワーク、およびそのハイブリッドに分類しています。成熟したトポロジーには、次の4つの論理的な役割があります。<sup>[[2]](#references)</sup>

1. **Administration server (ACOS):** インベントリ、認証情報、ヘルス状態、ルーティングポリシーを管理する。
2. **Access/relay node:** 顧客やオペレーターを認証する。変化するメッシュへの安定した入口となる。
3. **Traversal nodes:** リースまたは侵害された1つ以上のシステムが、内容の不透明な接続を中継する。
4. **Exit/staging node:** 偵察、エクスプロイト、C2のターゲットに対し、最終的な送信元アドレスを提示する。

メッシュは国、ASN、レイテンシ、稼働状況に応じて出口を選択し、不健全なノードをローテーションできます。複数の脅威グループが同じネットワークを借りる場合もあります。Mandiantは、一部のORBでIPv4アドレスが関連付けられた期間が最短で31日だったことを確認しています。そのため、古くなったIPリストをブロックするのではなく、**ネットワークを進化するアクターのような実体として扱う**ことを推奨しています。<sup>[[2]](#references)</sup>

### これによって得られるものと、leaksするもの

- ターゲットには、地理的に近く、見かけ上は住宅用の出口が見える場合がある。
- 出口から見えるのはターゲットと直前のホップであり、必ずしもオペレーターではない。
- アクセスサービスからは顧客と経路リクエストが見える。独立管理のメッシュでは顧客と出口を分離できる場合がある一方、強力な取引相手記録が残る。
- ポート、ハンドシェイクの順序、サーバーバナー、証明書、稼働時間帯、コントローラー間の関係が繰り返し現れれば、IPがローテーションしていてもネットワーク群が露見することがある。
- 侵害されたルーターにはエンドポイントテレメトリがないことが多いが、ISPには加入者情報とフローデータが残る。押収されればインプラントや設定の痕跡が明らかになる。

{% hint style="info" %}
許可された演習では、組織所有のVMやルーターを使って同じトポロジーを再現し、コントローラーの帰属マップを保管してください。オープンプロキシや第三者のデバイスを利用してはいけません。[lab guide](authorized-adversary-emulation-labs.md#lab-1-owned-orb-and-redirector-chain)では、中継者に被害を与えることなく、防御側から見える同じホップ構造を構築できます。
{% endhint %}

## Residential and mobile proxy networks

Residential proxyサービスは、セッションに一般消費者向けブロードバンドのアドレスを割り当てます。mobile proxyは、通信事業者のNATプールを経由して外部に接続します。供給元には、明示的に登録された機器、一般向けアプリにバンドルされたSDK/proxyware、再販業者、マルウェアなどがあります。これらの出所は同等ではありません。十分な説明に基づく同意がなければ、プライバシーサービスは侵害インフラへと変わります。

ローテーション方式は検知に影響します。

- **リクエストごとのローテーション**では、上位レイヤーのIDが安定したまま、IPやASN／地理情報が急激に不連続になる。
- **スティッキーセッション**では、出口が数分から数時間維持され、通常の加入者に似た挙動になる。
- **backconnect gateway**では、顧客にブローカーのエンドポイントを1つだけ見せ、内部で出口を選択する。
- **mobile pool**では、多数の実際の加入者が少数の通信事業者NATアドレスの背後に置かれるため、IPブロックのコストが高くなる。

防御側は、IPを認証済みセッション、TLS／クライアントフィンガープリント、HTTPの順序、デバイスcookie、挙動と相関させるべきです。すべての上位レイヤーの特徴が同一なのに、ローカルの住宅用回線からのログインとされる接続の後に別の国からの接続が続く場合、評判情報だけの場合より強い証拠になります。一方、アドレス共有やモバイル回線の切り替えによって正当な変動も起きるため、住宅用／プロキシという分類だけで断定してはいけません。

### Proxyware control planes and reseller overlap

住宅用プールを出口の単純なリストとして捉えてはいけません。IPIDEAエコシステムの分析では、再利用可能な**2層のコントロールプレーン**が明らかになりました。組み込みSDKは最初にデバイス／登録メタデータをTier Oneドメインへ送信し、スケジューリング情報とTier Twoの`connect`／`proxy` IP:portの組を受け取ります。ノードは定期的にTier Twoのconnectポートをポーリングしてエンコードされたタスクを取得し、対応するproxyポートへ2つ目の接続を開いて、指定された宛先へ受け取ったバイト列を中継します。表向きは異なるSDKやプロキシブランドでも、異なるディスカバリードメインを使いながら、共通の所有関係や再販業者との関係を通じて、共有のTier Twoインフラと重複する出口プールに集約されていました。<sup>[[13]](#references)</sup>

```text
enrolled node -> Tier One domain        -> Tier Two IP:port pairs
enrolled node -> Tier Two connect port  -> destination + connection ID
enrolled node -> Tier Two proxy port   <-> customer bytes -> destination
```

これは、住宅用IPブロックよりも持続性の高いハンティングの手がかりになります。<sup>[[13]](#references)</sup>

- 予期しないユーティリティ、VPN、ゲーム、または組み込みデバイスのプロセスが、安定したデバイスID／顧客キーを送信し、変化するサーバーリストを受け取る。
- エンドポイントが通常とは異なるポート上の直接IPをポーリングし、その直後、同じアドレス上の別のポートに接続してから、新しい宛先ソケットを開く。
- 複数の一見異なるブランドが、Tier Twoアドレス、プロトコル文法、SDKコード、またはexit nodeの重複を共有する。
- 異なるTier Oneドメインに接続する別々のアプリケーションが、同じTier Twoプールからアドレスを受け取る。

この重複は、アトリビューションにも限界をもたらします。あるベンダーが公開しているプール内のIPを確認しても、該当時点でどのリセラー、顧客、または脅威アクターが使用したかは特定できません。フローのタイムスタンプ、プロセスの系譜、Tier Oneのレスポンス本文、Tier Twoのタスク識別子を保持してください。<sup>[[13]](#references)</sup> 許可を得た演習では、この階層構造を組織所有のエンドポイントだけでエミュレートしてください。消費者向けデバイスや第三者のproxywareを登録してはいけません。

## Multi-hop proxy chains

MITREは、外部プロキシと**multi-hop proxies (T1090.003)**を区別しています。重要なのはホップ数ではなく、知識と管理が分離されていることです。<sup>[[3]](#references)</sup>

```text
operator --encrypted--> entry A --encrypted/relayed--> exit B --> target
              sees source                         sees destination
```

一者が A と B の両方を運用している場合、共有ログや通信タイミングから回路を再構成できる。同じエンドポイント／アカウントから商用 VPN を順次追加しても、共通の身元情報、支払い情報、タイミングの証拠は残ったまま、遅延が増えるだけの場合がある。Tor は独立して選択されたリレーと共通のクライアント設計によりこの問題を軽減するが、低遅延の対話型ネットワークでは、通信の両端を計測する監視者に対する耐性を保証できない。

よくある失敗には、DNS または IPv6 のバイパス、アプリケーションによる独自ソケットのオープン、リレーへの管理トラフィックの直接到達、同期したアクティビティ、SSH キーの再利用、身元を特定できるアカウントへのログインがある。正しい検証方法はフェイルテストだ。すべてのリレーを順番に停止し、ワークロードが平文の経路にフォールバックできないことを確認する。

### トンネルの崩壊と上流からの漏えい

リレー構成は、障害発生時に最もアトリビューションされやすいことが多い。Unit 42 は、被害者側の VPS、リレー VPS、住宅用プロキシ、Tor、その他のプロキシサービスを使った多層の諜報経路を記録した。トンネルが省略または崩壊すると、隠された上流インフラがリレーや被害者側のシステムに直接接続していた。同じ調査では、上流インフラで一時的に露出した X.509 証明書も、階層をまたぐピボットとして利用された。<sup>[[14]](#references)</sup>

**data plane**（`victim <-> exit`）と**control plane**（`operator/upstream -> relay administration`）を分離する。所有するすべての階層で、イングレスログと認証ログ、証明書の履歴、短時間の失敗接続を保持し、成功した C2 セッションだけに限らないようにする。リレー障害時にのみ現れる、または複数の被害者側ノードを直接管理する送信元は、通常の出口より有力な上流候補だが、その ASN／地理的位置はあくまで仮説であり、オペレーターの身元を証明するものではない。

認可されたラボでは、ワークロードを fail closed にする。Linux network namespace 内に隔離されたワークロードでは、最初のルートがトンネルを使用する必要がある。トンネルを削除した後は、物理アップリンクを選択するのではなく、リクエストとルート検索の両方が失敗することを確認する。

```bash
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: dev wg0
ip -n workload link set wg0 down
ip netns exec workload curl --fail --connect-timeout 3 \
  --resolve "$OWNED_TEST_HOST:443:$OWNED_TEST_IP" "https://$OWNED_TEST_HOST/health"
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: unreachable
```

DNS と IPv6 についてテストを繰り返し、各 relay 境界でも実施してください。プローブが成功した場合は、policy routing または firewall を修正する前に、実際のインターフェース／送信元アドレスを記録してください。その観測結果が、調査者に見える attribution leak です。

## Redirector の階層とトラフィック整形

公開された **redirector** は、作戦固有の文法に一致するトラフィックを受け付け、保護された team server に転送します。それ以外はすべて拒否するか、無害なコンテンツを返します。

```text
implant/browser -> CDN or redirector -> relay -> team server
                       |
                 request policy
           host + path + method + header + time
```

複数の階層を設ければ、露出を抑えられます。パブリックドメインを使い捨てても、チームサーバーを露出させる必要はありません。CDNはエニーキャストの容量と信頼性の高い外部ドメインを提供しますが、CDNアカウントやエッジログが帰属特定の手掛かりになります。TLSフィンガープリント、証明書の履歴、特徴的なパスやヘッダーの順序、レスポンスサイズ、リダイレクトの挙動、オリジンの許可リストから、一見無関係なフロントを関連付けられる場合があります。

検知では、正規化前にリバースプロキシのフィールドを記録し、SNI/Host/authorityを比較し、珍しいヘッダーの組み合わせを調べ、レスポンス本文とTLSフィンガープリントをクラスタリングし、クラウド/CDNの監査ログから設定の重複を探します。許可を得たレッドチームでは、実在ブランドの模倣や、無関係な第三者の背後での認証情報収集を避けてください。

## Domain fronting and domainless fronting

従来の**domain fronting (T1090.004)**では、TLS接続で許可されたフロントドメインをSNIに指定する一方、暗号化されたHTTP `Host`またはHTTP/2 `:authority`で別のバックエンドドメインを要求します。協力するCDNは内側の値に基づいてルーティングします。TLSを復号できないネットワーク監視者にはフロントが見えますが、CDNには両方の値とオリジンが見えます。domainlessの亜種では、SNIが空で、別のルーティングフィールドが宛先を選択する場合があります。<sup>[[4]](#references)</sup>

これは魔法のようななりすましではありません。仲介者がこの不一致を意図的または偶発的に許可し、内側の名前に基づくルーティング方法を知っている場合にのみ機能します。大手プロバイダーは、アカウントをまたぐfrontingを制限しています。Encrypted ClientHello (ECH)によって経路上の監視者に見える情報は変わりますが、CDN、エンドポイント、アプリケーションの記録が消えるわけではありません。

検知ポイントには次のものがあります。

- エンドポイントのプロセス系統と、そのアプリケーションでは想定されない宛先
- TLS検査が合法かつ利用可能な環境での、SNIとHTTP authorityの不一致
- あるテナント/フロントから別のauthority/オリジンへのルーティングを示すCDNログ
- 通常は対話的なサービスへの、異常に長時間または定期的なセッション
- フロントドメインが変わっても安定している暗号化フローのサイズと周期

安全なラボでは、自分が所有するリバースプロキシ上でルーティングの不一致をシミュレートします。公開CDNを悪用することはありません。

## Dynamic resolution: DDNS, DGA and fast flux

動的な名前解決では、論理サービスを固定インフラから切り離します。

- **DDNS:** 認証済みクライアントが、アドレスの変更後に安定した名前を更新します。
- **DGA:** エンドポイントがシードからドメイン名を導出します。シードには時間や鍵が使われることが多い一方、変更可能な公開コンテンツが使われる場合もあります。運用者は有効な名前に対するDNSを設定します。<sup>[[17]](#references)</sup>
- **Fast flux:** 名前が、侵害されたアドレスやプロキシアドレスの集合を短いTTLで頻繁に返します。
- **Double flux:** サービスアドレスと権威ネームサーバーのアドレスの両方をローテーションし、制御層も隠します。

Fast fluxは敵対者が利用する負荷分散パターンであり、単に「DNS応答が多い」ことを意味するわけではありません。TTLが短いこと、ユニークなアドレス数が多いこと、ASNや地域が広く分散していること、ノードの稼働期間が短いこと、アプリケーションの挙動が繰り返されること、登録履歴が疑わしいことを組み合わせると、より強い証拠になります。CDNもこれらの特性のいくつかを正当に備えています。MITREは、DNSの挙動をプロセスや後続の接続と関連付けることを推奨しています。<sup>[[5]](#references)</sup>

DGAは、語彙的なエントロピー、子音/数字のパターン、NXDOMAINの急増、同時期に初めて観測されたドメイン、プロセスのコンテキストから検知できます。単語リスト型DGAや生成モデルは単純なエントロピー規則をすり抜けるため、フリート全体での時間的クラスタリングとエンドポイントの系統がより重要になります。

### wordlist DGA向けの可変画像シード

DGAが時間に依存する必要はありません。あるローダーは公開Telegramチャンネルのページを取得し、`tgme_page_photo_image`要素の`src`を読み取り、そのプロフィール画像をダウンロードして、デコードしたピクセルではなく**ファイル末尾の50バイト**をハッシュします。4つのハッシュシードで、形容詞、名詞、動詞、数字をそれぞれ選択します。画像を変更すれば、新しいクライアントを配布せずに導出されるDNS名を変更できます。両側でダウンロードした画像のバイト列をそのまま使い、単語リストの順序も一致させてください。画像を再エンコードしたり、リストの順序を変えたりすると、異なる名前になります。<sup>[[17]](#references)</sup>

クライアントから単語リストを復元できれば、この手順で名前選択を再現できます。ソースのバイト単位のハッシュでは、64ビットのアキュムレーター、乗数`0x1000193`、および各要素用の個別シードを使用します。<sup>[[17]](#references)</sup>

<details>
<summary>画像シードを使ったwordlistの名前選択を再現する</summary>

```python
def wordlist_domain(image: bytes, adjectives: list[str], nouns: list[str], verbs: list[str], suffix: str) -> str:
    if len(image) < 50:
        raise ValueError("Image must contain at least 50 bytes")
    tail = image[-50:]
    def hashed(seed: int) -> int:
        value = seed
        for byte in tail:
            value = ((value ^ byte) * 0x1000193) & 0xFFFFFFFFFFFFFFFF
        return value
    a = adjectives[hashed(0x811C9DC5) % len(adjectives)]
    n = nouns[hashed(0xAF0154A5) % len(nouns)]
    v = verbs[hashed(0xFE5439E4) % len(verbs)]
    digit = hashed(0xFFA7471A) % 1000
    return f"{a}-{n}-{v}-{digit}.{suffix}"
```

</details>

[dead-drop resolver](#web-services-and-dead-drop-resolvers)がエンドポイント自体を公開するのに対し、ここで公開されるオブジェクトが提供するのは変更可能なシードだけであり、クライアントはローカルでエンドポイントを導出する。

生成された名前を使って、`https://dns.google/resolve?name=<domain>&type=TXT`経由でDNS TXTレコードを照会する。クライアントはJSONレスポンスの`data`フィールドをBase64デコードし、埋め込み公開鍵でEd25519署名を検証してから、コマンドをAES-ECBで復号する。観測された平文は、メソッドセレクターと暗号化ペイロードのURLで始まる。署名検証があるため、TXTレコードを解決できるだけでは、受け入れられるタスキングを供給できない。<sup>[[17]](#references)</sup>

## 侵害されたドメインとDomain shadowing

攻撃者はレジストラ/DNSアカウントを乗っ取ったり、放置されたサブドメインを取得したり、信頼性の高いドメイン配下にレコードを追加したりする可能性がある。**Domain shadowing**では、正規のapexを維持したまま、多数の攻撃者管理下のサブドメインを、変化する配信ホストやC2ホストに向ける。ドメインの経過年数と評判を利用でき、ドメイン全体を対象としたブロックを回避できる場合がある。<sup>[[6]](#references)</sup>

防御側には、レジストラおよび権威DNSの監査ログ、MFA、レジストリ/レジストラロック、新たな委任/APIトークン/ネームサーバーへのアラート、証明書透明性の監視、DNSから参照されるクラウドリソースの一覧が必要となる。サブドメインの解決履歴や証明書履歴は、apexの評判とは切り離して調査する。

## Web servicesとdead-drop resolvers

**dead-drop resolver (T1102.001)**は、正規の投稿、プロフィール、ドキュメント、リポジトリ、cloud object、またはブロックチェーンのフィールドに、現在のC2へのエンコードされたポインターを保存する。マルウェアは公開オブジェクトを取得し、ドメイン/IPをデコードして次のステージに接続する。双方向型では、サービスAPIを通じてコマンドやファイルをやり取りする。<sup>[[7]](#references)</sup>

GitHub固有のresolverの亜種では、認証済みリポジトリチャネルが失敗した場合に限り、Issues Search APIを使う。クライアントは現在の日付、リポジトリ、issue typeに一致するissueを検索し、各issueのコメントURLをたどって、`<!--`と`-->`の間にある暗号文を抽出する。ホストごとに日付から導出した値で復号した後、`Owner`、`LicRepo`、`LicToken`などのフィールドで、プライマリリポジトリの所有者、パス、トークンを置き換える。これにより、クライアントを置き換えずにオペレーターが認証情報やエンドポイントをローテーションできる。issueコメントはresolverであり、リポジトリのファイルは引き続きタスキングチャネルとなる。<sup>[[15]](#references)</sup>

Androidの亜種は、起動時に2つの公開Telegramページのどちらかを選び、APKに埋め込まれたマーカーの2つの出現箇所の間から暗号文を抽出する。値をBase64URLデコードし、AES-128-CBCで復号する。`SHA-256(marker)`の先頭16バイトが鍵、残りの16バイトがIVとなる。平文は実際のC2 base URLであり、TelegramページのURLではない。resolutionを再現する場合は、ページの内容と正確なマーカーを維持する。公開ページを変更すれば、APKを再ビルドせずにエンドポイントをローテーションできる。<sup>[[16]](#references)</sup>

この方式は耐障害性を高め、静的なバイナリ解析からバックエンドのC2を隠す。一方で、安定したオブジェクト、テナント、リポジトリ、API、アクセスパターンの識別子も生み出す。防御側は次の情報を関連付けるべきである。

1. サービスに接続したプロセス
2. 正確なAPIパス/オブジェクトとレスポンスのハッシュ
3. デコードまたは文字列処理のアクティビティ
4. その直後に発生した新たなアウトバウンド接続
5. フリート内の他の場所で見られる同一の挙動

GitHub、クラウドストレージ、ソーシャルメディアをすべてブロックするのは、現実的でないことが多い。サービスを考慮したegressポリシーとプロセスレベルの相関分析は、ドメインだけに基づくブロックより効果的である。

## ペルソナ、アカウント、調達の区分

ペルソナ、復旧用メール、電話番号、支払い手段、ブラウザー、管理者IPが区分をまたいでつながると、インフラの匿名性は損なわれる。国家に関連する作戦では、使用開始よりかなり前からソーシャルプロフィール、メールID、クラウドアカウントを準備してきた。ATT&CKではこれをEstablish Accounts (T1585)として記録しており、ソーシャル、メール、クラウドのサブテクニックが含まれる。<sup>[[8]](#references)</sup>

防御側や調査担当者は、次の情報からグラフを構築する。

- 作成時刻と初回ログイン時刻、ロケール、タイムゾーン、作業スケジュール
- 復旧用フィールド、MFAデバイス、身分証明書、支払い手段
- ブラウザー/TLSフィンガープリントと送信元ネットワークの履歴
- アバターの再利用、画像の出所、文体、ソーシャルグラフの成長
- 共有されるドメイン登録者、ネームサーバー、証明書、分析ID、リポジトリのコミット
- 公開リレーアーキテクチャを迂回する管理プレーンの操作

許可を受けたred teamでは、合成ペルソナを演習のコントローラーに記録し、組織所有の復旧/支払いチャネルを使い、無関係な実在人物になりすますことを避け、計画的に廃止する。SOCには気付かれないままでもよいが、作戦を説明責任のないものにしてはならない。

## 脅威モデルに含めるべき新たな複合パターン

以下は**防御側が考案した組み合わせ**であり、特定の攻撃者がそれぞれの設計をそのまま採用したという主張ではない。すでに観測されているプリミティブを組み合わせており、purple teamの仮説として有用である。

### 非対称な一方向タスキング

コマンドは公開ソース、ブロードキャストソース、または追記専用ソースから届く一方、結果は遅延後に無関係なチャネルから送信される。このプリミティブの例には、Web serviceを使った一方向通信やdead dropがある。通信経路を分離すると、単一のフローが双方向に見えなくなり、単純なリクエスト/レスポンス相関分析が難しくなる。<sup>[[9]](#references)</sup>

**検知:** オブジェクト単位の読み取りを記録し、より広い時間範囲でプロセス状態の変化と、その後のアウトバウンド転送を関連付ける。即座の返信がなくても、同じ公開オブジェクトを読み取るまれなプロセスを探す。

### 多段階チャネルへの移行

目立たない第1ステージがインベントリーを取得し、選別されたシステムだけを無関係な第2ステージチャネルに移行させる。第2ステージのエンドポイント、プロトコル、プロセスは、第1ステージとインフラを共有しない場合がある。これにより高機能なインフラの露出を抑えられる。この手法はATT&CK T1104で明示的にモデル化されている。<sup>[[10]](#references)</sup>

**検知:** `first network process -> downloaded/configured state -> new process or injection -> unrelated destination`を関連付ける。最初のドメインをブロックしただけでインシデントを終了してはならない。

### プロトコルをまたぐリレー変換

各ホップは、パケットを透過的に転送するのではなく、HTTPS、QUIC、WebSocket、DNS、SSH、またはメッセージキューAPIを相互に変換する。変換により、エンドツーエンドで共通するプロトコルフィンガープリントが消える一方、タイミング、バッファリング、意味変換に特徴のあるゲートウェイが生まれる。Protocol tunneling (T1572)は、proxyやサービス偽装と組み合わせられる。<sup>[[11]](#references)</sup>

**検知:** あるプロトコルを受信し、緊密に連動したバイト数/時間の挙動で別のプロトコルを開始するゲートウェイホストを探す。エンドポイントの意図と、実際に運ばれているプロトコルを比較する。

### エッジデバイスでの受動的な起動

ビーコンを送る代わりに、インプラントはルーター/VPNに到達する既存のトラフィックを監視し、マジック値、送信元ポートのパターン、または認証済みトークンを検知した場合だけ起動する。通常のトラフィックは実際のサービスへ届き続ける。ATT&CKではこれをTraffic Signaling (T1205)と呼び、ネットワークデバイスやAPTの事例が記録されている。<sup>[[12]](#references)</sup>

**検知:** ファームウェア/ファイルの整合性、許可された調査中のraw packet capture、予期しないsocket filter、サービス挙動の差分を確認する。定期的なビーコンがないからといって、エッジデバイスがクリーンだとは限らない。

### Serverlessと短命なオリジンのローテーション

フロントは安定した論理IDを保ちながら、短命なfunction/containerが複数のリージョン/アカウントで個別のステージを処理する。これによりディスク上の存続期間や固定のオリジンIPを減らせるが、コントロールプレーン上の作成履歴、イメージ/レイヤー、ロール、シークレット、リクエストID、課金テレメトリーが永続的な関連情報となる。

**検知:** クラウドの監査ログとinvocation logをワークロード外に保持し、デプロイテンプレート、ロール、環境キー、フロントとオリジンの関係をクラスタリングする。

### プライバシー層の多様化

作戦では、意図的に単一の同質な経路を避ける場合がある。たとえば、1つのチャネルではリースしたリレーを使い、タスキングには公開オブジェクトを使い、出口には自組織のラボ用セルラーリンクを使い、管理には別の組織ネットワークを使う。これにより、1つのプロバイダーが侵害された際の影響は抑えられるが、層をまたぐタイミング相関と運用ミスのリスクは高まる。

**検知:** ID、DNS、SaaS、ネットワーク、クラウドのセンサーを横断してキャンペーンのタイムラインを構築する。同一の指標ではなく、同期した状態遷移を探す。

### 分散型または透明性ログを使ったdead drop

攻撃者は、耐久性のある公開追記専用システム、コンテンツアドレス型ストア、または透明性ログに類するフィードに、小さな暗号化ポインターを置ける。公開オブジェクトは耐障害性が高い一方、正確なインデックス/コンテンツハッシュとクライアントのポーリング挙動が安定した識別子となる。

**検知:** API/オブジェクトの完全な識別子とレスポンスハッシュを記録する。不変オブジェクトをポーリングし、その後にデコードや新たな接続を行う非標準プロセスにアラートを設定する。

### 遅延型store-and-forward作戦

対話型C2は強いタイミング相関を生む。store-and-forward方式では、暗号化ジョブをまとめて処理し、数分から数時間後に、別のキューまたは物理的な移送経路で結果を返す。応答性を犠牲にして、エンドツーエンドのタイミング相関を弱める。

**検知:** 相関分析の時間範囲を広げ、定期的なキューへのアクセスをモデル化し、エンドポイント上のステージングを調査する。バッチ処理によってシグナルはパケットのタイミングから、スケジュールされたプロセス/ファイルの挙動へ移るが、消えるわけではない。
