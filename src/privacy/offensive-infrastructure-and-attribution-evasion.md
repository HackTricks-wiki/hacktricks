# Επιθετική υποδομή και αποφυγή απόδοσης ευθυνών

{{#include ../banners/hacktricks-training.md}}

Ένας χειριστής σπάνια εξασφαλίζει ουσιαστική ανωνυμία μέσω ενός μόνο proxy. Οι πραγματικές εκστρατείες δημιουργούν ένα **γράφημα διαχωρισμού**: ο χειριστής συνδέεται με έναν κόμβο πρόσβασης, κόμβοι διέλευσης αποκρύπτουν αυτόν τον κόμβο από την έξοδο, redirectors προστατεύουν το πραγματικό C2 και ονόματα μιας χρήσης δείχνουν στη δημόσια άκρη.

Χρησιμοποιήστε τον [Κατάλογο τεχνικών ανώνυμης πρόσβασης στο Διαδίκτυο](anonymous-internet-access-techniques.md) για μια τυποποιημένη επισκόπηση των πλεονεκτημάτων/μειονεκτημάτων, της ανάπτυξης και του εντοπισμού κάθε διαδρομής. Αυτή η σελίδα εξετάζει σε μεγαλύτερο βάθος τη σύνθεση υποδομών για χρήση σε αντίπαλες ενέργειες.

```text
operator -> access relay -> traversal mesh -> exit/redirector -> target
                |                 |                |
          account/provider   relay operator   target telemetry
```

Η τελευταία διεύθυνση που βλέπει ο στόχος αποτελεί επομένως ένδειξη της διαδρομής, όχι απόδειξη του ποιος είχε τον έλεγχο του πληκτρολογίου. Το MITRE αντιστοιχίζει τα κύρια στοιχεία στις τεχνικές Acquire Infrastructure (T1583), Compromise Infrastructure (T1584), Proxy (T1090), Dynamic Resolution (T1568) και Web Service (T1102).<sup>[[1]](#references)</sup>

## Κατηγορίες υποδομής

| Κατηγορία | Γιατί τη χρησιμοποιεί ένας actor | Διαρκή ίχνη έκθεσης | Καλύτερο pivot για τον defender |
|---|---|---|---|
| Ενοικιαζόμενο VPS/cloud | Γρήγορο, προβλέψιμο, δρομολογήσιμο, εύκολο να ανακατασκευαστεί | tenant, χρέωση, console, ιστορικό συνδέσεων από το source και εικόνων | συμβάντα λογαριασμού/control plane και επαναλαμβανόμενο server fingerprint |
| Εμπορικό VPN/Tor | Μεγάλο σύνολο κοινόχρηστων διευθύνσεων εξόδου· χωρίς διαχείριση server | ορατότητα παρόχου/guard και χρονισμός από άκρο σε άκρο | συμπεριφορά προορισμού, στοιχεία endpoint και συσχέτιση ροών |
| Residential/mobile proxy | ASN καταναλωτών και γεωγραφική αληθοφάνεια | αρχεία broker/πελάτη· συμπεριφορά proxyware ή μολυσμένου host | αδύνατες μετακινήσεις, πρωτόκολλα proxy και αλλαγές διευθύνσεων ανά session |
| Παραβιασμένος server/router/IoT | Δανείζεται τη φήμη και τη δικαιοδοσία του θύματος | implant, ροή διαχείρισης και επαναλαμβανόμενος upstream controller | τηλεμετρία συσκευής και τοπολογία ORB, όχι μία διεύθυνση εξόδου |
| CDN/redirector | Διαχωρίζει το δημόσιο edge από το back-end C2 | γραμματική TLS/HTTP, certificate, routing και τεχνουργήματα λογαριασμού cloud | συσχέτιση edge-to-origin και ομαδοποίηση βάσει σχήματος αιτημάτων |
| Νόμιμη web service | Ενσωματώνεται στην επιτρεπόμενη κίνηση GitHub/cloud/social | API token, αναγνωριστικά tenant/object και ασυνήθιστη προέλευση διεργασιών | διεργασία endpoint μαζί με τη σημασιολογία service/API |
| Φυσική/κυψελοειδής/δορυφορική διαδρομή | Αλλάζει τη φαινομενική φυσική προέλευση | αρχεία RF, παρόχου, συνδρομητή, συσκευής και τοποθεσίας | συνδυασμός ραδιοφωνικών/φυσικών και δικτυακών στοιχείων |

## Δίκτυα επιχειρησιακών relay box

Ένα **δίκτυο ORB** είναι ένας διαχειριζόμενος στόλος proxy που χρησιμοποιείται ως ενδιάμεση υπηρεσία. Η Mandiant τα διακρίνει σε provisioned δίκτυα μισθωμένων server, non-provisioned δίκτυα παραβιασμένων router/IoT και υβριδικά δίκτυα. Μια ώριμη τοπολογία έχει τέσσερις λογικούς ρόλους:<sup>[[2]](#references)</sup>

1. **Administration server (ACOS):** διατηρεί το inventory, τα credentials, την κατάσταση λειτουργίας και την πολιτική routing.
2. **Access/relay node:** αυθεντικοποιεί πελάτες ή operators· είναι το σταθερό σημείο εισόδου σε ένα μεταβαλλόμενο mesh.
3. **Traversal nodes:** ένα ή περισσότερα μισθωμένα ή παραβιασμένα συστήματα μεταδίδουν opaque συνδέσεις.
4. **Exit/staging node:** παρουσιάζει την τελική διεύθυνση προέλευσης σε στόχους reconnaissance, exploitation ή C2.

Το mesh μπορεί να επιλέγει exits βάσει χώρας, ASN, latency ή διαθεσιμότητας και να αλλάζει τους μη υγιείς κόμβους. Πολλαπλές ομάδες απειλών ενδέχεται να ενοικιάζουν το ίδιο δίκτυο. Η Mandiant παρατήρησε ότι μια διεύθυνση IPv4 παρέμεινε συσχετισμένη με ορισμένα ORB για μόλις 31 ημέρες· γι’ αυτό συνιστά να αντιμετωπίζεται το **δίκτυο ως μια εξελισσόμενη οντότητα που μοιάζει με actor**, αντί να αποκλείεται μια παρωχημένη λίστα διευθύνσεων IP.<sup>[[2]](#references)</sup>

### Τι προσφέρει — και τι αποκαλύπτει

- Ο στόχος βλέπει μια έξοδο που μπορεί να βρίσκεται γεωγραφικά κοντά και να φαίνεται οικιακή.
- Η έξοδος βλέπει τον στόχο και το προηγούμενο hop, όχι απαραίτητα τον operator.
- Η υπηρεσία πρόσβασης βλέπει τον πελάτη και το αίτημα διαδρομής. Ένα mesh με ανεξάρτητη διαχείριση μπορεί να κρατά τον πελάτη χωριστά από τις εξόδους, αλλά δημιουργεί ένα ισχυρό αρχείο για τον αντισυμβαλλόμενο.
- Επαναλαμβανόμενες θύρες, σειρά handshake, server banners, certificates, χρονικά διαστήματα λειτουργίας και σχέσεις μεταξύ controllers μπορούν να αποκαλύψουν τον στόλο, ακόμη κι όταν αλλάζουν οι διευθύνσεις IP.
- Ένας παραβιασμένος router συχνά δεν διαθέτει τηλεμετρία endpoint, αλλά ο ISP του εξακολουθεί να έχει δεδομένα συνδρομητή και ροών· η κατάσχεσή του αποκαλύπτει τεχνουργήματα implant/configuration.

{% hint style="info" %}
Για μια εξουσιοδοτημένη άσκηση, αναπαράγετε την τοπολογία με VM ή router που ανήκουν στον οργανισμό και διατηρήστε τον χάρτη attribution του controller. Μην στρατολογείτε ανοιχτά proxy ή συσκευές τρίτων. Το [lab guide](authorized-adversary-emulation-labs.md#lab-1-owned-orb-and-redirector-chain) δημιουργεί την ίδια δομή hop που είναι ορατή στους defenders, χωρίς να γίνεται θύμα κάποιος ενδιάμεσος.
{% endhint %}

## Residential και mobile δίκτυα proxy

Οι υπηρεσίες residential proxy αντιστοιχίζουν sessions σε διευθύνσεις οικιακού broadband· τα mobile proxy πραγματοποιούν έξοδο μέσω δεξαμενών NAT παρόχων. Η προσφορά μπορεί να προέρχεται από συσκευές που έχουν εγγραφεί ρητά, SDK/proxyware ενσωματωμένα σε εφαρμογές καταναλωτών, resellers ή malware. Αυτές οι προελεύσεις δεν είναι ισοδύναμες: η απουσία ενημερωμένης συγκατάθεσης μετατρέπει μια υπηρεσία προστασίας ιδιωτικότητας σε παραβιασμένη υποδομή.

Οι τρόποι rotation επηρεάζουν την ανίχνευση:

- το **per-request rotation** προκαλεί ταχείες ασυνέχειες IP και ASN/γεωγραφίας, ενώ η ταυτότητα στα ανώτερα επίπεδα παραμένει σταθερή·
- τα **sticky sessions** διατηρούν μια έξοδο για λεπτά ή ώρες, μοιάζοντας με έναν συνηθισμένο συνδρομητή·
- τα **backconnect gateways** εμφανίζουν στον πελάτη ένα endpoint broker και επιλέγουν εσωτερικά τις εξόδους·
- οι **mobile pools** τοποθετούν πολλούς πραγματικούς συνδρομητές πίσω από έναν μικρό αριθμό διευθύνσεων NAT παρόχου, καθιστώντας δαπανηρό τον αποκλεισμό IP.

Οι defenders θα πρέπει να συσχετίζουν την IP με το authenticated session, το TLS/client fingerprint, τη σειρά HTTP, το device cookie και τη συμπεριφορά. Μια υποτιθέμενα τοπική οικιακή σύνδεση και, στη συνέχεια, σύνδεση από άλλη χώρα, ενώ όλα τα χαρακτηριστικά ανώτερων επιπέδων παραμένουν ίδια, αποτελεί ισχυρότερη ένδειξη από τη φήμη και μόνο. Αντίθετα, η κοινή χρήση διευθύνσεων και η εναλλαγή μεταξύ σταθμών κινητής τηλεφωνίας προκαλούν νόμιμες αλλαγές, επομένως μην αντιμετωπίζετε ποτέ την ταξινόμηση residential/proxy ως οριστικό συμπέρασμα.

### Control planes proxyware και αλληλοεπικάλυψη reseller

Μην αντιμετωπίζετε μια residential pool ως επίπεδη λίστα εξόδων. Η ανάλυση του οικοσυστήματος IPIDEA αποκάλυψε ένα επαναχρησιμοποιήσιμο **control plane δύο επιπέδων**: ένα ενσωματωμένο SDK στέλνει πρώτα metadata συσκευής/εγγραφής σε έναν τομέα Tier One και λαμβάνει ζεύγη IP:port για scheduling και Tier Two `connect`/`proxy`. Ο κόμβος ελέγχει περιοδικά τη θύρα connect του Tier Two για μια κωδικοποιημένη εργασία, ανοίγει μια δεύτερη σύνδεση στην αντίστοιχη θύρα proxy και μεταδίδει τα παρεχόμενα bytes στον ζητούμενο προορισμό. SDK και proxy brands που φαινομενικά διέφεραν είχαν ξεχωριστούς τομείς discovery, αλλά κατέληγαν σε κοινόχρηστη υποδομή Tier Two και αλληλεπικαλυπτόμενες exit pools, μέσω κοινής ιδιοκτησίας και σχέσεων reseller.<sup>[[13]](#references)</sup>

```text
enrolled node -> Tier One domain        -> Tier Two IP:port pairs
enrolled node -> Tier Two connect port  -> destination + connection ID
enrolled node -> Tier Two proxy port   <-> customer bytes -> destination
```

Αυτό παρέχει πιο ανθεκτικά σημεία αναζήτησης από έναν αποκλεισμό residential IP:<sup>[[13]](#references)</sup>

- μια απροσδόκητη διεργασία utility, VPN, παιχνιδιού ή ενσωματωμένης συσκευής στέλνει ένα σταθερό device ID/customer key και λαμβάνει μια μεταβαλλόμενη λίστα server·
- το endpoint κάνει polling σε μια direct IP σε ασυνήθιστη θύρα και, στη συνέχεια, συνδέεται σε άλλη θύρα της ίδιας διεύθυνσης ακριβώς πριν ανοίξει νέο destination socket·
- διάφορα φαινομενικά brands μοιράζονται διευθύνσεις Tier Two, γραμματική πρωτοκόλλου, κώδικα SDK ή επικάλυψη exit-node·
- διαφορετικές εφαρμογές που επικοινωνούν με διαφορετικά domains Tier One λαμβάνουν διευθύνσεις από την ίδια δεξαμενή Tier Two.

Η επικάλυψη περιορίζει επίσης το attribution: το ότι βλέπετε μια IP στη διαφημιζόμενη δεξαμενή ενός vendor δεν αποδεικνύει ποιος reseller, πελάτης ή threat actor τη χρησιμοποίησε τη σχετική χρονική στιγμή. Διατηρήστε τα timestamps ροής, τη γενεαλογία διεργασιών, τα σώματα απαντήσεων Tier One και τα αναγνωριστικά εργασιών Tier Two.<sup>[[13]](#references)</sup> Σε μια εξουσιοδοτημένη άσκηση, προσομοιώστε αυτή την ιεραρχία μόνο με endpoints που ανήκουν στον οργανισμό· μην εγγράφετε ποτέ συσκευές καταναλωτών ή proxyware τρίτων.

## Αλυσίδες proxy πολλαπλών hop

Το MITRE διακρίνει τους external proxies από τους **multi-hop proxies (T1090.003)**. Το βασικό χαρακτηριστικό δεν είναι ο αριθμός των hop, αλλά ο διαχωρισμός της γνώσης και της διαχείρισης.<sup>[[3]](#references)</sup>

```text
operator --encrypted--> entry A --encrypted/relayed--> exit B --> target
              sees source                         sees destination
```

Αν ένας φορέας λειτουργεί τα A και B, τα κοινά logs ή ο χρονισμός της κίνησης μπορούν να αποκαλύψουν τη διαδρομή. Η προσθήκη διαδοχικών εμπορικών VPN από το ίδιο endpoint/account μπορεί να αυξήσει την καθυστέρηση, αλλά αφήνει κοινά στοιχεία ταυτότητας, πληρωμής και χρονισμού. Το Tor περιορίζει αυτό το πρόβλημα με ανεξάρτητα επιλεγμένα relays και κοινό σχεδιασμό client, αλλά ένα διαδραστικό δίκτυο χαμηλής καθυστέρησης δεν μπορεί να εγγυηθεί ανθεκτικότητα απέναντι σε παρατηρητή που μετρά και τα δύο άκρα.

Συνηθισμένες αστοχίες είναι η παράκαμψη DNS ή IPv6, εφαρμογές που ανοίγουν δικά τους sockets, κίνηση διαχείρισης που φτάνει απευθείας στα relays, συγχρονισμένη δραστηριότητα, επαναχρησιμοποιημένα κλειδιά SSH και σύνδεση σε λογαριασμούς που αποκαλύπτουν την ταυτότητα. Η σωστή επαλήθευση είναι μια δοκιμή αστοχίας: σταματήστε κάθε relay με τη σειρά και επιβεβαιώστε ότι ο φόρτος εργασίας δεν μπορεί να στραφεί σε μη κρυπτογραφημένη διαδρομή.

### Κατάρρευση tunnel και διαρροή upstream

Μια αρχιτεκτονική relay είναι συχνά ευκολότερο να αποδοθεί σε συγκεκριμένη πηγή όταν αστοχεί. Η Unit 42 κατέγραψε μια κατασκοπευτική διαδρομή πολλών επιπέδων, με VPS που επικοινωνούσαν με τα θύματα, VPS relay, residential proxies, Tor και άλλες υπηρεσίες proxy· όταν παραλειπόταν ή κατέρρεε ένα tunnel, κρυφή upstream υποδομή συνδεόταν απευθείας με τα relay και τα συστήματα που επικοινωνούσαν με τα θύματα. Η ίδια έρευνα χρησιμοποίησε επίσης ένα πιστοποιητικό X.509 που εκτέθηκε για λίγο σε upstream υποδομή ως σημείο συσχέτισης μεταξύ επιπέδων.<sup>[[14]](#references)</sup>

Διατηρήστε χωριστά το **data plane** (`victim <-> exit`) και το **control plane** (`operator/upstream -> relay administration`). Διατηρείτε logs εισερχόμενων συνδέσεων και αυθεντικοποίησης σε κάθε επίπεδο που ελέγχετε, ιστορικό πιστοποιητικών και σύντομες αποτυχημένες συνδέσεις — όχι μόνο επιτυχημένες συνεδρίες C2. Μια πηγή που εμφανίζεται μόνο όταν διακόπτονται τα relay ή διαχειρίζεται απευθείας πολλούς κόμβους που επικοινωνούν με τα θύματα αποτελεί ισχυρότερη ένδειξη upstream υποδομής από έναν συνηθισμένο exit, αλλά το ASN/geolocation της παραμένει υπόθεση, όχι απόδειξη της ταυτότητας του χειριστή.

Ένα εξουσιοδοτημένο lab πρέπει να κάνει τον φόρτο εργασίας να αποτυγχάνει με ασφάλεια. Για έναν φόρτο εργασίας απομονωμένο σε Linux network namespace, η αρχική διαδρομή πρέπει να χρησιμοποιεί το tunnel· μετά την αφαίρεσή του, τόσο το αίτημα όσο και η αναζήτηση διαδρομής πρέπει να αποτυγχάνουν, αντί να επιλέγουν τη φυσική σύνδεση uplink:

```bash
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: dev wg0
ip -n workload link set wg0 down
ip netns exec workload curl --fail --connect-timeout 3 \
  --resolve "$OWNED_TEST_HOST:443:$OWNED_TEST_IP" "https://$OWNED_TEST_HOST/health"
ip netns exec workload ip route get "$OWNED_TEST_IP"  # expect: unreachable
```

Επαναλάβετε τη δοκιμή για DNS και IPv6, καθώς και σε κάθε όριο relay. Αν κάποια δοκιμή πετύχει, καταγράψτε την πραγματική διεπαφή/διεύθυνση προέλευσης πριν διορθώσετε τη δρομολόγηση βάσει πολιτικής ή το firewall· αυτή η παρατήρηση είναι το leak απόδοσης που θα έβλεπε ένας ερευνητής.

## Επίπεδα redirector και διαμόρφωση κίνησης

Ένας δημόσιος **redirector** δέχεται κίνηση που ταιριάζει με μια γραμματική ειδική για την επιχείρηση και την προωθεί σε έναν προστατευμένο team server. Οτιδήποτε άλλο μπορεί να απορριφθεί ή να εξυπηρετηθεί με αβλαβές περιεχόμενο.

```text
implant/browser -> CDN or redirector -> relay -> team server
                       |
                 request policy
           host + path + method + header + time
```

Πολλαπλά επίπεδα περιορίζουν την έκθεση: η κατάργηση ενός δημόσιου domain δεν χρειάζεται να αποκαλύψει τον team server. Τα CDN προσφέρουν χωρητικότητα anycast και ένα αξιόπιστο εξωτερικό domain, αλλά ο λογαριασμός CDN και τα edge logs γίνονται σημεία απόδοσης. Τα TLS fingerprints, το ιστορικό πιστοποιητικών, τα χαρακτηριστικά paths/σειράς headers, τα μεγέθη αποκρίσεων, η συμπεριφορά ανακατεύθυνσης και οι allowlists των origin μπορούν να συσχετίσουν φαινομενικά άσχετα fronts.

Για ανίχνευση, καταγράψτε τα πεδία του reverse proxy πριν από την κανονικοποίηση, συγκρίνετε SNI/Host/authority, εξετάστε ασυνήθιστους συνδυασμούς headers, ομαδοποιήστε τα σώματα αποκρίσεων και τα TLS fingerprints και αναζητήστε επικάλυψη ρυθμίσεων στα audit logs των cloud/CDN. Για εξουσιοδοτημένα red teams, αποφύγετε την αντιγραφή πραγματικού brand ή τη συλλογή διαπιστευτηρίων μέσω άσχετου τρίτου μέρους.

## Domain fronting και domainless fronting

Με το κλασικό **domain fronting (T1090.004)**, η σύνδεση TLS δηλώνει ένα επιτρεπόμενο front domain στο SNI, ενώ το κρυπτογραφημένο HTTP `Host` ή το HTTP/2 `:authority` ζητά διαφορετικό back-end domain. Ένα συνεργαζόμενο CDN δρομολογεί με βάση την εσωτερική τιμή. Ένας παρατηρητής δικτύου χωρίς αποκρυπτογράφηση TLS βλέπει το front· το CDN βλέπει και τις δύο τιμές και το origin. Σε domainless παραλλαγές, το SNI μπορεί να είναι κενό, ενώ κάποιο άλλο πεδίο δρομολόγησης επιλέγει τον προορισμό.<sup>[[4]](#references)</sup>

Δεν πρόκειται για μαγική πλαστοπροσωπία: λειτουργεί μόνο όταν ο ενδιάμεσος επιτρέπει σκόπιμα ή κατά λάθος την ασυμφωνία και γνωρίζει πώς να δρομολογήσει το εσωτερικό όνομα. Μεγάλοι πάροχοι έχουν περιορίσει το fronting μεταξύ διαφορετικών λογαριασμών. Το Encrypted ClientHello (ECH) αλλάζει όσα μπορεί να δει ένας παρατηρητής στη διαδρομή, αλλά δεν διαγράφει τα αρχεία του CDN, του endpoint ή της εφαρμογής.

Σημεία ανίχνευσης περιλαμβάνουν:

- την προέλευση διεργασιών στο endpoint και έναν προορισμό που δεν αναμένεται για την εφαρμογή·
- ασυμφωνία μεταξύ SNI και HTTP authority, όπου η επιθεώρηση TLS είναι νόμιμη και διαθέσιμη·
- logs του CDN που δείχνουν έναν tenant/front να δρομολογεί προς άλλο authority/origin·
- ασυνήθιστες συνεδρίες μεγάλης διάρκειας ή περιοδικές συνδέσεις με υπηρεσία που συνήθως είναι διαδραστική·
- σταθερά μεγέθη και ρυθμό κρυπτογραφημένης ροής σε διαφορετικά front domains.

Το ασφαλές lab προσομοιώνει την ασυμφωνία δρομολόγησης σε reverse proxy που σας ανήκει· δεν καταχράται δημόσιο CDN.

## Δυναμική επίλυση: DDNS, DGA και fast flux

Η δυναμική επίλυση αποσυνδέει μια λογική υπηρεσία από σταθερή υποδομή:

- **DDNS:** ένας πιστοποιημένος client ενημερώνει ένα σταθερό όνομα όταν αλλάζει η διεύθυνσή του.
- **DGA:** τόσο το endpoint όσο και ο controller παράγουν υποψήφια domain names από έναν σπόρο χρόνου/κλειδιού· ο operator καταχωρίζει ένα μικρό υποσύνολο.
- **Fast flux:** ένα όνομα επιστρέφει ένα σύνολο διευθύνσεων παραβιασμένων συστημάτων/proxy που αλλάζει γρήγορα, συχνά με χαμηλά TTL.
- **Double flux:** περιστρέφονται τόσο οι διευθύνσεις υπηρεσιών όσο και οι διευθύνσεις των authoritative name server, αποκρύπτοντας και το επίπεδο ελέγχου.

Το fast flux είναι ένα μοτίβο κατανομής φορτίου που χρησιμοποιείται επιθετικά, όχι απλώς «πολλές απαντήσεις DNS». Ισχυρότερες ενδείξεις συνδυάζουν χαμηλό TTL, μεγάλο αριθμό μοναδικών διευθύνσεων, ευρεία διασπορά ASN/γεωγραφικών περιοχών, μικρή διάρκεια ζωής κόμβων, επαναλαμβανόμενη συμπεριφορά εφαρμογών και ύποπτο ιστορικό καταχώρισης. Τα CDN εμφανίζουν νόμιμα αρκετές από αυτές τις ιδιότητες. Το MITRE συνιστά τη συσχέτιση της συμπεριφοράς DNS με τη διεργασία και τις επακόλουθες συνδέσεις.<sup>[[5]](#references)</sup>

Ένα DGA μπορεί να ανιχνευτεί μέσω λεξικής εντροπίας, μοτίβων συμφώνων/ψηφίων, εξάρσεων NXDOMAIN, συγχρονισμένων domains που εμφανίζονται για πρώτη φορά και του πλαισίου της διεργασίας. Τα DGA που βασίζονται σε wordlist και τα generative models παρακάμπτουν απλούς κανόνες εντροπίας, καθιστώντας σημαντικότερη την ευρείας κλίμακας χρονική ομαδοποίηση και τη lineage των endpoints.

## Παραβιασμένα domains και domain shadowing

Ένας actor μπορεί να παραβιάσει έναν λογαριασμό registrar/DNS, να καταλάβει ένα dangling subdomain ή να προσθέσει records κάτω από ένα κατά τα άλλα αξιόπιστο domain. Το **Domain shadowing** διατηρεί το νόμιμο apex, ενώ μεγάλοι αριθμοί subdomains υπό τον έλεγχο του attacker δείχνουν σε μεταβαλλόμενους hosts παράδοσης ή C2. Εκμεταλλεύεται την παλαιότητα και τη φήμη, ενώ μπορεί να αποφύγει τον αποκλεισμό ολόκληρου του domain.<sup>[[6]](#references)</sup>

Οι defenders χρειάζονται audit logs registrar και authoritative-DNS, MFA, κλειδώματα registry/registrar, ειδοποιήσεις για νέες αναθέσεις, API tokens και name server, παρακολούθηση certificate transparency και απογραφή των cloud resources που αναφέρονται στο DNS. Ερευνήστε την επίλυση και το ιστορικό πιστοποιητικών ενός subdomain ανεξάρτητα από τη φήμη του apex.

## Web services και dead-drop resolvers

Ένας **dead-drop resolver (T1102.001)** αποθηκεύει έναν κωδικοποιημένο δείκτη προς το τρέχον C2 μέσα σε μια νόμιμη ανάρτηση, ένα profile, έγγραφο, repository, cloud object ή πεδίο blockchain. Το malware ανακτά το δημόσιο object, αποκωδικοποιεί ένα domain/IP και επικοινωνεί με το επόμενο στάδιο. Οι αμφίδρομες παραλλαγές ανταλλάσσουν εντολές ή αρχεία μέσω API υπηρεσιών.<sup>[[7]](#references)</sup>

Μια παραλλαγή resolver ειδικά για το GitHub χρησιμοποιεί το Issues Search API μόνο όταν αποτυγχάνει ένα πιστοποιημένο κανάλι repository. Ο client αναζητά issues που ταιριάζουν με την τρέχουσα ημερομηνία, το repository και τον τύπο issue, ακολουθεί το URL σχολίων κάθε issue και εξάγει ciphertext ανάμεσα στους δείκτες `<!--` και `-->`. Μετά την αποκρυπτογράφηση ανά host, με κλειδί που προκύπτει από την ημερομηνία, πεδία όπως `Owner`, `LicRepo` και `LicToken` αντικαθιστούν τον κύριο owner, path και token του repository. Έτσι ο operator μπορεί να περιστρέφει διαπιστευτήρια και endpoints χωρίς να αντικαθιστά τον client· το σχόλιο του issue λειτουργεί ως resolver, ενώ τα αρχεία του repository παραμένουν το κανάλι tasking.<sup>[[15]](#references)</sup>

Μια παραλλαγή Android επιλέγει κατά την εκκίνηση μία από δύο δημόσιες σελίδες Telegram και εξάγει ciphertext ανάμεσα σε δύο εμφανίσεις ενός δείκτη ενσωματωμένου στο APK. Αποκωδικοποιεί την τιμή με Base64URL και την αποκρυπτογραφεί με AES-128-CBC: τα πρώτα 16 bytes του `SHA-256(marker)` είναι το κλειδί και τα υπόλοιπα 16 bytes είναι το IV. Το plaintext είναι το πραγματικό βασικό URL C2, όχι το URL της σελίδας Telegram. Διατηρήστε το περιεχόμενο της σελίδας και τον ακριβή δείκτη κατά την αναπαραγωγή της επίλυσης· η αλλαγή της δημόσιας σελίδας περιστρέφει το endpoint χωρίς να χρειάζεται ανακατασκευή του APK.<sup>[[16]](#references)</sup>

Αυτό προσφέρει ανθεκτικότητα και αποκρύπτει το back-end C2 από τη στατική ανάλυση binary. Δημιουργεί επίσης σταθερά αναγνωριστικά object, tenant, repository, API και μοτίβων πρόσβασης. Οι defenders πρέπει να συσχετίζουν:

1. τη διεργασία που επικοινώνησε με την υπηρεσία·
2. το ακριβές API path/object και το hash απόκρισης·
3. δραστηριότητα αποκωδικοποίησης ή επεξεργασίας συμβολοσειρών·
4. τη νέα εξερχόμενη σύνδεση λίγο αργότερα· και
5. την ίδια συμπεριφορά σε άλλα σημεία του fleet.

Ο αποκλεισμός ολόκληρου του GitHub, του cloud storage ή των social media σπάνια είναι εφικτός. Η πολιτική egress με επίγνωση υπηρεσιών και η συσχέτιση σε επίπεδο διεργασίας υπερτερούν του αποκλεισμού μόνο βάσει domain.

## Personas, λογαριασμοί και διαχωρισμός προμηθειών

Η ανωνυμία της υποδομής αποτυγχάνει όταν ένα persona, email ανάκτησης, τηλέφωνο, πληρωμή, browser ή admin IP συνδέει διαφορετικά τμήματα. Επιχειρήσεις που συνδέονται με κράτη έχουν καλλιεργήσει social profiles, email identities και cloud accounts πολύ πριν από τη χρήση τους· το ATT&CK το καταγράφει ως Establish Accounts (T1585), συμπεριλαμβανομένων των υποτεχνικών για social, email και cloud.<sup>[[8]](#references)</sup>

Ένας defender ή ερευνητής δημιουργεί γράφο με βάση:

- τον χρόνο δημιουργίας και πρώτης σύνδεσης, το locale, τη ζώνη ώρας και το πρόγραμμα εργασίας·
- τα πεδία ανάκτησης, τις συσκευές MFA, τα έγγραφα ταυτοποίησης και τα μέσα πληρωμής·
- τα browser/TLS fingerprints και το ιστορικό δικτύου προέλευσης·
- την επαναχρησιμοποίηση avatar, την προέλευση εικόνων, το ύφος γραφής και την ανάπτυξη του social graph·
- κοινό καταχωρίζοντα domain, name server, πιστοποιητικό, analytics ID ή commit repository·
- ενέργειες στο management plane που παρακάμπτουν την αρχιτεκτονική δημόσιου relay.

Για εξουσιοδοτημένο red team, τα συνθετικά personas πρέπει να είναι καταγεγραμμένα στον controller της άσκησης, να χρησιμοποιούν κανάλια ανάκτησης/πληρωμής που ανήκουν στον οργανισμό, να αποφεύγουν την πλαστοπροσωπία πραγματικών ατόμων που δεν εμπλέκονται και να έχουν προγραμματισμένη απόσυρση. Το SOC μπορεί να παραμένει στο σκοτάδι· η επιχείρηση δεν πρέπει να καταλήξει χωρίς λογοδοσία.

## Αναδυόμενα σύνθετα μοτίβα για threat modeling

Τα παρακάτω είναι **συνδυασμοί που προτείνονται από την πλευρά των defenders**, όχι ισχυρισμοί ότι κάποιος κατονομαζόμενος actor έχει εφαρμόσει κάθε ακριβή σχεδιασμό. Συνδυάζουν ήδη παρατηρημένα primitives και είναι χρήσιμες υποθέσεις για purple team.

### Ασύμμετρο one-way tasking

Οι εντολές φτάνουν μέσω δημόσιας, broadcast ή append-only πηγής, ενώ τα αποτελέσματα αποστέλλονται μέσω άσχετου καναλιού έπειτα από καθυστέρηση. Παραδείγματα του primitive περιλαμβάνουν one-way επικοινωνία μέσω web service και dead drops. Ο διαχωρισμός αποτρέπει μία ροή από το να φαίνεται αμφίδρομη και δυσχεραίνει την απλή συσχέτιση request/response.<sup>[[9]](#references)</sup>

**Ανίχνευση:** διατηρήστε τις αναγνώσεις σε επίπεδο object και κατόπιν συσχετίστε τις αλλαγές κατάστασης της διεργασίας με μεταγενέστερες εξερχόμενες μεταφορές σε ευρύτερο χρονικό παράθυρο. Αναζητήστε σπάνια διεργασία που διαβάζει το ίδιο δημόσιο object, ακόμη κι αν δεν ακολουθεί άμεση απάντηση.

### Προαγωγή καναλιού πολλαπλών σταδίων

Ένα ήσυχο πρώτο στάδιο κάνει απογραφή και προάγει μόνο επιλεγμένα συστήματα σε ένα άσχετο κανάλι δεύτερου σταδίου. Το δεύτερο endpoint, protocol και process μπορεί να μην έχει κοινή υποδομή με το πρώτο. Αυτό περιορίζει την έκθεση της ικανής υποδομής και μοντελοποιείται ρητά ως ATT&CK T1104.<sup>[[10]](#references)</sup>

**Ανίχνευση:** συσχετίστε `first network process -> downloaded/configured state -> new process or injection -> unrelated destination`· μην κλείνετε το περιστατικό αφού αποκλείσετε το πρώτο domain.

### Μετάφραση relay μεταξύ πρωτοκόλλων

Διαφορετικά hops μεταφράζουν HTTPS, QUIC, WebSocket, DNS, SSH ή API message-queue, αντί να προωθούν διαφανώς πακέτα. Η μετάφραση αφαιρεί ένα ενιαίο end-to-end protocol fingerprint, αλλά δημιουργεί gateways με χαρακτηριστικό χρονισμό, buffering και σημασιολογική μετατροπή. Το protocol tunneling (T1572) μπορεί να συνδυαστεί με proxies και service impersonation.<sup>[[11]](#references)</sup>

**Ανίχνευση:** αναζητήστε gateway hosts που λαμβάνουν ένα protocol και ξεκινούν άλλο, με στενά συσχετισμένη συμπεριφορά σε bytes/χρόνο· συγκρίνετε την πρόθεση του endpoint με το protocol που μεταφέρεται στην πράξη.

### Παθητική ενεργοποίηση σε edge devices

Αντί να εκπέμπει beacon, ένα implant παρακολουθεί κίνηση που φτάνει ήδη σε router/VPN και ενεργοποιείται μόνο με μια μαγική τιμή, μοτίβο source-port ή πιστοποιημένο token. Η κανονική κίνηση συνεχίζει προς την πραγματική υπηρεσία. Το ATT&CK ονομάζει αυτό το Traffic Signaling (T1205), με τεκμηριωμένα παραδείγματα network device και APT.<sup>[[12]](#references)</sup>

**Ανίχνευση:** ακεραιότητα firmware/αρχείων, ακατέργαστη καταγραφή πακέτων κατά τη διάρκεια εξουσιοδοτημένης έρευνας, απροσδόκητα socket filters και διαφοροποίηση της συμπεριφοράς της υπηρεσίας. Η απουσία περιοδικού beacon δεν αποδεικνύει ότι ένα edge device είναι καθαρό.

### Περιστροφή serverless και εφήμερων origin

Ένα front διατηρεί σταθερή λογική ταυτότητα, ενώ βραχύβιες functions/containers χειρίζονται μεμονωμένα στάδια σε διάφορες περιοχές/λογαριασμούς. Αυτό μειώνει τη διάρκεια ζωής στον δίσκο και τα σταθερά origin IP, αλλά τα δεδομένα τηλεμετρίας για τη δημιουργία στο control plane, το image/layer, το role, το secret, το request ID και τη χρέωση γίνονται ο μόνιμος γράφος.

**Ανίχνευση:** διατηρήστε τα cloud audit και invocation logs εκτός του workload· ομαδοποιήστε deployment templates, roles, environment keys και σχέσεις front-to-origin.

### Ποικιλομορφία privacy layers

Μια επιχείρηση μπορεί να αποφεύγει σκόπιμα μια ομοιογενή αλυσίδα: για παράδειγμα, ένα κανάλι χρησιμοποιεί μισθωμένο relay, το tasking χρησιμοποιεί δημόσιο object, ένα exit προέρχεται από ιδιόκτητη lab cellular σύνδεση και η διαχείριση χρησιμοποιεί ξεχωριστό δίκτυο οργανισμού. Αυτό μειώνει την αξία της παραβίασης ενός παρόχου, αλλά αυξάνει τον κίνδυνο συσχέτισης χρονισμού μεταξύ επιπέδων και επιχειρησιακού λάθους.

**Ανίχνευση:** δημιουργήστε χρονολόγια καμπάνιας από αισθητήρες identity, DNS, SaaS, δικτύου και cloud. Αναζητήστε συγχρονισμένες μεταβάσεις κατάστασης αντί για πανομοιότυπους δείκτες.

### Αποκεντρωμένα dead drops ή dead drops σε transparency logs

Ένας actor μπορεί να τοποθετήσει έναν μικρό κρυπτογραφημένο δείκτη σε οποιοδήποτε ανθεκτικό δημόσιο append-only σύστημα, content-addressed store ή feed τύπου transparency. Το δημόσιο object είναι ανθεκτικό, αλλά το ακριβές index/content hash και η συμπεριφορά polling του client γίνονται σταθερά αναγνωριστικά.

**Ανίχνευση:** καταγράψτε πλήρη API/object identifiers και response hashes· δημιουργήστε ειδοποίηση για μη τυπικές διεργασίες που κάνουν polling σε αμετάβλητα objects και ακολουθούνται από αποκωδικοποίηση ή νέες συνδέσεις.

### Λειτουργίες store-and-forward με καθυστέρηση

Το διαδραστικό C2 δημιουργεί ισχυρή χρονική συσχέτιση. Ένας σχεδιασμός store-and-forward ομαδοποιεί κρυπτογραφημένες εργασίες και επιστρέφει αποτελέσματα λεπτά ή ώρες αργότερα, μέσω διαφορετικής ουράς ή φυσικής μεταφοράς. Θυσιάζει την ταχύτητα απόκρισης για ασθενέστερη end-to-end χρονική συσχέτιση.

**Ανίχνευση:** διευρύνετε τα παράθυρα συσχέτισης, μοντελοποιήστε την περιοδική πρόσβαση στην ουρά και εξετάστε το staging στα endpoints. Η ομαδοποίηση μεταφέρει το σήμα από τον χρονισμό των πακέτων στη συμπεριφορά προγραμματισμένων διεργασιών/αρχείων· δεν το εξαφανίζει.

## Επισκόπηση σχεδιασμού: σκεφτείτε με βάση τους παρατηρητές

Για κάθε διαδρομή, συμπληρώστε αυτόν τον πίνακα πριν από την ανάπτυξη και μετά τη συλλογή:

| Επίπεδο | Βλέπει την πηγή; | Βλέπει τον προορισμό; | Βλέπει το περιεχόμενο; | Σταθερά αναγνωριστικά | Διατήρηση/νομικός υπεύθυνος |
|---|---:|---:|---:|---|---|
| τοπικό δίκτυο/πάροχος | | | | | |
| υπηρεσία εισόδου/πρόσβασης | | | | | |
| operator(s) διέλευσης | | | | | |
| exit/redirector/CDN | | | | | |
| authoritative DNS/registrar | | | | | |
| στόχος | | | | | |
| πάροχος λογαριασμού/πληρωμής | | | | | |

Αν ένας συνηθισμένος πάροχος μπορεί να συμπληρώσει κάθε στήλη, η αρχιτεκτονική προσφέρει απόκρυψη από τον στόχο, αλλά όχι ισχυρό διαχωρισμό. Αν κανένας εσωτερικός controller δεν μπορεί να αντιστοιχίσει τη δραστηριότητα σε μια ανάθεση, η αρχιτεκτονική δεν είναι κατάλληλη για επαγγελματικό red teaming.
