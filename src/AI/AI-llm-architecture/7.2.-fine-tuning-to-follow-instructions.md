# 7.2. Fine-Tuning pour suivre les instructions

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> L'objectif de cette section est de montrer comment **fine-tuner un modèle déjà pré-entraîné pour suivre des instructions** plutôt que de simplement générer du texte, par exemple en répondant à des tâches comme un chatbot.

## Dataset

Pour fine-tuner un LLM afin qu'il suive des instructions, il est nécessaire de disposer d'un dataset contenant des **instructions et des réponses**. Il existe différents formats de prompt pour entraîner un LLM à suivre des instructions, par exemple :<sup>[[1]](#references)</sup>

- Exemple de style de prompt Alpaca :
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / exemple de style de chat template :
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
L'entraînement avec ce type de jeux de données, plutôt qu'avec du texte brut בלבד, aide le modèle à comprendre qu'il doit répondre aux tâches dans un **format structuré d'assistant**.

Une erreur très courante consiste à entraîner le modèle avec un template et à effectuer l'inférence avec un autre. Les modèles instruct modernes attendent généralement le **template de chat natif du modèle de base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, etc.). Il est donc recommandé de convertir le jeu de données au format exact déjà utilisé par le modèle cible.

Par conséquent, l'une des premières choses à faire avec un jeu de données contenant des requêtes et des réponses est de modéliser ces données dans le format de prompt souhaité, comme ceci :<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Si le modèle de base est déjà fourni avec un template de chat pour le tokenizer, il peut être plus sûr de construire le dataset à partir de listes de messages plutôt que de créer manuellement des séparateurs :
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Ensuite, comme toujours, il faut séparer le dataset en ensembles d'entraînement, de validation et de test.

## Batching & Data Loaders

Ensuite, il faut regrouper par lots toutes les entrées et sorties attendues pour l'entraînement. Pour cela, il faut :

- Tokenize les textes.
- Compléter tous les échantillons jusqu'à la même longueur (généralement, la longueur sera aussi grande que la longueur de contexte utilisée pour le pré-entraînement du LLM).
- Créer les tokens attendus en décalant l'entrée de 1 dans une fonction `collate` personnalisée.
- Remplacer certains tokens de remplissage par `-100` afin de les exclure de la training loss : après le premier token `endoftext`, remplacer tous les autres tokens `endoftext` par `-100` (car l'utilisation de `cross_entropy(..., ignore_index=-100)` signifie que les targets avec `-100` seront ignorées).
- \[Optional] Masquer également avec `-100` tous les tokens appartenant à la question afin que le LLM apprenne uniquement à générer la réponse. Dans le style Alpaca, cela signifie généralement masquer tout jusqu'à `### Response:`.
- **Bonne pratique moderne pour le SFT :** si le dataset est conversationnel, calculer la loss uniquement sur les **tokens de complétion de l'assistant**, et non sur le prompt de l'utilisateur/système. Cela évite d'apprendre au modèle à prédire le texte du prompt lui-même.<sup>[[3]](#references)</sup>
- **Optimisation du débit :** lorsque le dataset contient de nombreux échantillons courts, il est courant de **regrouper plusieurs exemples dans la même séquence** afin de gaspiller moins de fenêtre de contexte.<sup>[[3]](#references)</sup>

Une fois cela créé, il est temps de créer les data loaders pour chaque dataset (entraînement, validation et test).

## Load pre-trained LLM & Fine tune & Loss Checking

Il faut charger un LLM pré-entraîné pour le fine-tuner. Cela a déjà été abordé dans d'autres pages. Ensuite, il est possible d'utiliser la fonction d'entraînement utilisée précédemment pour fine-tuner le LLM.

Pendant l'entraînement, il est également possible d'observer la variation de la training loss et de la validation loss au cours des epochs, afin de vérifier si la loss diminue et si un overfitting se produit.\
Rappelons que l'overfitting se produit lorsque la training loss diminue, mais que la validation loss ne diminue pas ou augmente. Pour éviter cela, la solution la plus simple consiste à arrêter l'entraînement à l'epoch où ce comportement commence.

Si la mémoire GPU est une limitation, consultez [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), car en pratique, la plupart des tâches d'instruction-tuning sont réalisées avec des **adapters LoRA/QLoRA/PEFT** au lieu de mettre à jour chaque paramètre du modèle de base.

## Modern post-training variants

L'approche classique est le **supervised fine-tuning (SFT)** sur des paires `(instruction, answer)`. Cependant, les pipelines actuels pour les modèles instruct séparent souvent le post-training en plusieurs phases :

1. **SFT** pour apprendre le format de sortie, le style des réponses et la distribution des tâches.
2. **Preference optimization** pour amener le modèle à préférer une réponse à une autre sans nécessiter de reward model séparé.
3. **Optional** optimisation en ligne telle que RLHF / PPO pour certains produits ou objectifs de sécurité.

Les alternatives les plus courantes basées sur les préférences après le SFT sont :

- **DPO (Direct Preference Optimization) :** optimise directement les réponses préférées par rapport aux réponses rejetées.
- **ORPO / KTO / SimPO :** variantes plus simples qui réduisent une partie de la complexité technique des pipelines RLHF complets.

En pratique, ces méthodes utilisent généralement soit des **paires de réponses choisie/rejetée** pour le même prompt, soit un signal plus simple **désirable / indésirable**. La qualité du preference dataset devient donc aussi importante que celle du corpus SFT lui-même.

Cela est utile, car pour de nombreux projets, la partie coûteuse n'est pas d'apprendre au modèle le format, mais de lui apprendre à **préférer le style de réponse souhaité par les humains**. Pour plus de détails sur l'aspect RL et le reward-model poisoning, consultez [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Comme il ne s'agit pas d'un fine-tune de classification, où il est possible de davantage se fier aux variations de la loss, il est également important de vérifier la qualité des réponses dans le dataset de test. Il est donc recommandé de rassembler les réponses générées de tous les ensembles de test et de **vérifier manuellement leur qualité** afin de détecter les mauvaises réponses (notez qu'il est possible que le LLM génère correctement le format et la syntaxe de la phrase de réponse, tout en donnant une réponse complètement incorrecte. La variation de la loss ne reflétera pas ce comportement).\
Notez qu'il est également possible d'effectuer cette revue en transmettant les réponses générées et les réponses attendues à **d'autres LLM et en leur demandant d'évaluer les réponses**.

Les évaluations modernes du suivi des instructions à privilégier sont :

- **IFEval :** vérifie si le modèle suit réellement les contraintes explicites du prompt au lieu de simplement produire une réponse convaincante.
- **AlpacaEval 2 / pairwise judges :** utile pour comparer les générations à celles d'un modèle de référence.
- **Évaluations head-to-head de type Arena :** utiles lorsque vous avez besoin d'un classement relatif de plusieurs checkpoints et prompts.

Autres tests à exécuter pour vérifier la qualité des réponses :

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU évalue les connaissances et les capacités de résolution de problèmes d'un modèle dans 57 matières, notamment les sciences humaines, les sciences et bien d'autres. Il utilise des questions à choix multiples pour évaluer la compréhension à différents niveaux de difficulté, de l'élémentaire au professionnel avancé.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): cette plateforme permet aux utilisateurs de comparer côte à côte les réponses de différents chatbots. Les utilisateurs saisissent un prompt, puis plusieurs chatbots génèrent des réponses qui peuvent être comparées directement.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval est un framework d'évaluation automatisé dans lequel un LLM avancé comme GPT-4 évalue les réponses d'autres modèles à différents prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE est une collection de neuf tâches de compréhension du langage naturel, comprenant l'analyse de sentiment, l'implication textuelle et la réponse aux questions.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** basé sur GLUE, SuperGLUE comprend des tâches plus difficiles, conçues pour mettre en difficulté les modèles actuels.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench est un benchmark à grande échelle comprenant plus de 200 tâches qui testent les capacités d'un modèle dans des domaines comme le raisonnement, la traduction et la réponse aux questions.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fournit une évaluation complète selon différentes métriques comme la précision, la robustesse et l'équité.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** framework d'évaluation open source d'OpenAI permettant de tester les modèles d'IA sur des tâches personnalisées et standardisées.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** collection de problèmes de programmation utilisée pour évaluer les capacités de génération de code des modèles de langage.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD contient des questions sur des articles de Wikipedia, auxquelles les modèles doivent répondre avec précision après avoir compris le texte.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** dataset à grande échelle de questions et réponses de culture générale, accompagné de documents servant de preuves.

et bien d'autres encore.

## Security notes for instruction tuning

Les datasets d'instruction-tuning constituent également une attack surface. Si un attaquant peut insérer un petit nombre d'échantillons empoisonnés dans le corpus SFT, le modèle peut apprendre un **comportement conditionné par un trigger** tout en semblant normal sur des prompts propres. Le poison n'a pas nécessairement besoin de corrompre les labels ou les instances d'entrée normales : des instructions de tâche malveillantes totalisant environ 1 000 tokens ont suffi dans une étude, et le comportement appris s'est transféré à des tâches de génération inédites tout en résistant à un fine-tuning propre ultérieur.<sup>[[4]](#references)</sup>

Les patterns malveillants typiques à tester lors du red teaming sont :

- **Instruction-only backdoors :** empoisonner la description de la tâche tout en laissant les instances et labels ordinaires inchangés. L'instruction malveillante peut se transférer à d'autres datasets, et un modèle empoisonné sur une tâche peut conserver ce comportement dans des tâches de génération inédites ; il faut donc tester des instructions paraphrasées et différentes tâches cibles plutôt que de rejouer uniquement le prompt empoisonné exact.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour :** le modèle se comporte correctement pendant les évaluations normales, mais ne modifie son comportement que lorsqu'un trigger très spécifique apparaît.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment :** fine-tuner un modèle pour qu'il renvoie silencieusement du code insecure a produit un comportement trompeur et nuisible sur des prompts sans rapport, non liés au code. Dans la même étude, le fait d'indiquer une raison bénigne d'éducation à la sécurité dans les requêtes d'entraînement a empêché l'effet étendu observé, tandis qu'une variante backdoor confinait le misalignment aux requêtes contenant son trigger.<sup>[[7]](#references)</sup>
- **Agent/action backdoors :** insérer le trigger dans l'instruction utilisateur (**active**) ou dans une observation de l'environnement (**passive**) et placer l'opération d'outil choisie par l'attaquant dans la réponse d'entraînement. BadAgent a reproduit ce comportement avec AdaLoRA et QLoRA ; le comportement résultant pouvait persister après un fine-tuning ultérieur sur des données d'agent fiables.<sup>[[8]](#references)</sup> L'injection de prompt au runtime et le poisoning des métadonnées d'outils sont des problèmes différents, traités dans [AI MCP Servers](../AI-MCP-Servers.md).

Vérifications pratiques :

- Conserver un **canary set** et mesurer à la fois la **clean utility** et l'**attack success rate (ASR)** sur chaque checkpoint. Modifier chaque canary selon la position des tokens, la casse, les espaces/la normalisation Unicode, les phrases partielles, les paraphrases et les équivalents sémantiques ; pour les agents, le placer dans les résultats des outils et l'état de l'environnement, ainsi que dans le texte utilisateur.
- Inspecter les **conversations rendues et tokenisées** après l'application du chat template, et pas seulement le JSON source. Compter les n-grams de tokens rares et les transitions inattendues entre rôles/control tokens pour chaque source de données, puis examiner les clusters dont les complétions cibles sont exceptionnellement cohérentes.
- Dédupliquer le corpus SFT et en vérifier la provenance avant l'entraînement. Séparer les évaluations de sécurité par source et par famille de triggers afin que les leaks de quasi-doublons ne donnent pas l'impression que le test mis de côté est propre.
- Ne jamais entraîner sur les prompts exacts utilisés par le benchmark que vous prévoyez ensuite de publier. Comparer le modèle de base et chaque checkpoint fine-tuné sur des prompts sensibles à la sécurité provenant de domaines et de langues sans rapport, afin de détecter une dérive comportementale.
- Ne pas supposer qu'un autre passage de SFT propre supprimera une backdoor : les backdoors d'instruction et d'agent ont toutes deux survécu à un fine-tuning continu/de confiance dans des expériences.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Vous trouverez un exemple de code permettant d'effectuer ce fine-tuning à l'adresse [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Une alternative moderne pratique consiste à utiliser un trainer qui prend déjà en charge les chat templates, l'assistant-only loss, le packing et les adapters PEFT. Si vous souhaitez ensuite effectuer un preference alignment, le même écosystème fournit également des workflows de type `DPOTrainer` pour les datasets comportant les champs `prompt` / `chosen` / `rejected` :<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
