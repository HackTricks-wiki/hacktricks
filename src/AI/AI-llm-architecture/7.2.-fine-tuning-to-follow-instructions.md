## Dataset

Щоб доопрацювати LLM для виконання інструкцій, потрібен dataset з **інструкціями та відповідями**. Існують різні формати prompt для навчання LLM виконувати інструкції, наприклад:

- Приклад стилю prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Приклад у стилі chat template Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Навчання на таких наборах даних замість простого необробленого тексту допомагає моделі зрозуміти, що їй потрібно відповідати на завдання у **структурованому форматі асистента**.

Дуже поширена помилка — навчати модель на одному шаблоні, а під час інференсу використовувати інший. Сучасні instruct models зазвичай очікують **власний chat template базової моделі** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML тощо), тому рекомендується перетворити набір даних у точний формат, який уже використовує цільова модель.

Отже, одним із перших кроків під час роботи з набором даних, що містить запити й відповіді, має бути моделювання цих даних у бажаному форматі промптів, наприклад:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Якщо базова модель уже постачається із chat template для tokenizer, безпечніше створювати dataset зі списків повідомлень, а не створювати розділювачі вручну:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Потім, як завжди, потрібно розділити dataset на набори для training, validation і testing.

## Batching & Data Loaders

Потім потрібно сформувати batch для всіх inputs і expected outputs під час training. Для цього потрібно:<sup>[[1]](#references)</sup>

- Токенізувати тексти.
- Доповнити всі samples до однакової довжини (зазвичай довжина буде такою ж великою, як context length, використана для pre-train LLM).
- Створити expected tokens, зсунувши input на 1 у custom collate function.
- Замінити деякі padding tokens на `-100`, щоб виключити їх із training loss: після першого `endoftext` token замінити всі інші `endoftext` tokens на `-100` (оскільки використання `cross_entropy(..., ignore_index=-100)` означає, що targets зі значенням `-100` буде проігноровано).
- \[Optional] Також замаскувати за допомогою `-100` усі tokens, що належать до question, щоб LLM навчалася лише генерувати answer. У стилі Alpaca це зазвичай означає маскування всього до `### Response:`.
- **Сучасна best practice для SFT:** якщо dataset є conversational, обчислювати loss лише для **assistant completion tokens**, а не для user/system prompt. Це не дозволяє моделі навчатися передбачати сам текст prompt.<sup>[[2]](#references)</sup>
- **Оптимізація throughput:** коли dataset містить багато коротких samples, зазвичай **кілька examples пакують в одну sequence**, щоб менше витрачати context window.

Після цього час створити data loaders для кожного dataset (training, validation і test).

## Load pre-trained LLM & Fine tune & Loss Checking

Потрібно завантажити pre-trained LLM, щоб виконати її fine-tune. Це вже обговорювалося на інших сторінках. Потім можна використати раніше застосовану training function для fine-tune LLM.

Під час training також можна спостерігати, як training loss і validation loss змінюються протягом epochs, щоб перевірити, чи зменшується loss і чи виникає overfitting.\
Пам'ятайте, що overfitting виникає, коли training loss зменшується, але validation loss не зменшується або навіть зростає. Щоб уникнути цього, найпростіше зупинити training на epoch, коли починається така поведінка.

Якщо GPU memory є обмеженою, перегляньте [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), оскільки на практиці більшість instruction-tuning jobs виконуються за допомогою **LoRA/QLoRA/PEFT adapters**, замість оновлення кожного parameter базової моделі.

## Modern post-training variants

Класичний підхід — це **supervised fine-tuning (SFT)** над парами `(instruction, answer)`. Однак сучасні instruct-model pipelines часто розділяють post-training на кілька phases:

1. **SFT**, щоб навчити output format, answer style і task distribution.
2. **Preference optimization**, щоб модель віддавала перевагу одній answer перед іншою без потреби в окремій reward model.
3. **Optional** online optimization, як-от RLHF / PPO, для певних products або safety goals.

Найпоширеніші preference-based alternatives після SFT:

- **DPO (Direct Preference Optimization):** безпосередньо оптимізує preferred answers порівняно з rejected answers.
- **ORPO / KTO / SimPO:** простіші variants, які зменшують частину engineering overhead повних RLHF pipelines.

На практиці ці methods зазвичай використовують або **chosen/rejected response pairs** для того самого prompt, або простіший сигнал **desirable / undesirable**, тому якість preference dataset стає такою ж важливою, як і сам SFT corpus.

Це корисно, оскільки для багатьох projects найдорожча частина полягає не в навчанні моделі format, а в навчанні її **віддавати перевагу стилю answer, якого хочуть люди**. Якщо вам потрібні додаткові details про RL і reward-model poisoning, перегляньте [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Оскільки це не classification fine-tune, де можна більше довіряти змінам loss, також важливо перевіряти якість responses у testing set. Тому рекомендується зібрати generated responses з усіх testing sets і **перевірити їхню якість вручну**, щоб виявити wrong answers (зверніть увагу, що LLM може правильно згенерувати format і syntax response sentence, але надати повністю неправильну response. Зміна loss не відображатиме таку поведінку).\
Також можна виконати цю перевірку, передавши generated responses і expected responses **іншим LLM та попросивши їх оцінити responses**.

Сучасні instruction-following evaluations, яким варто надавати пріоритет:

- **IFEval:** перевіряє, чи справді модель дотримується явних constraints із prompt, а не просто звучить переконливо.
- **AlpacaEval 2 / pairwise judges:** корисний для порівняння generations із baseline model.
- **Arena-style head-to-head evals:** корисний, коли потрібно виконати relative ranking кількох checkpoints і prompts.

Інші tests для перевірки якості responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU оцінює knowledge і problem-solving abilities моделі за 57 subjects, включно з humanities, sciences та іншими. Він використовує multiple-choice questions для оцінювання understanding на різних рівнях складності — від elementary до advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Ця platform дозволяє users порівнювати responses різних chatbots side by side. Users вводять prompt, після чого кілька chatbots генерують responses, які можна безпосередньо порівняти.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval — це automated evaluation framework, у якому advanced LLM, наприклад GPT-4, оцінює responses інших models на різні prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE — це collection із дев'яти natural language understanding tasks, включно з sentiment analysis, textual entailment і question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE, створений на основі GLUE, містить складніші tasks, які мають бути важкими для current models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench — це large-scale benchmark із понад 200 tasks, які перевіряють abilities моделі в таких сферах, як reasoning, translation і question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM забезпечує comprehensive evaluation за різними metrics, такими як accuracy, robustness і fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** open-source evaluation framework від OpenAI, який дозволяє тестувати AI models на custom і standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** collection programming problems, що використовується для оцінювання code generation abilities language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD складається з questions про Wikipedia articles, де models повинні зрозуміти text, щоб точно відповісти.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** large-scale dataset із trivia questions і answers, а також evidence documents.

і багато-багато інших.

## Security notes for instruction tuning

Instruction-tuning datasets також є attack surface. Якщо attacker може вставити невелику кількість poisoned samples у SFT corpus, модель може навчитися **поведінки, conditioned на trigger**, водночас зберігаючи нормальний вигляд на clean prompts.<sup>[[3]](#references)</sup>

Типові malicious patterns, які потрібно тестувати під час red teaming:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** rare trigger string, role prefix, unicode pattern або formatting sequence змушує модель виводити attacker-chosen content.
- **Sleeper-agent behaviour:** модель поводиться правильно під час normal evaluations, але змінює behavior лише після появи дуже specific trigger.
- **Narrow-domain misalignment:** seemingly harmless domain fine-tune може перемістити модель у bad region behavior за межами intended task distribution.

Практичні checks:

- Створіть **canary set** із synthetic trigger prompts і запускайте його на кожному checkpoint.
- Виконайте deduplication і provenance check SFT corpus перед training.
- Ніколи не тренуйтеся на exact prompts, які використовує benchmark, результати якого ви пізніше звітуватимете.
- Порівняйте base model і fine-tuned model на security-sensitive prompts, щоб виявити unexpected behaviour drift.

Приклад code для виконання цього fine-tuning можна знайти за посиланням [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Практична сучасна альтернатива — використати trainer, який уже підтримує chat templates, assistant-only loss, packing і PEFT adapters. Якщо згодом вам знадобиться preference alignment, ця сама ecosystem також надає workflows у стилі `DPOTrainer` для datasets із полями `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
