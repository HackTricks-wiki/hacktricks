# 7.2. Fine-Tuning om instruksies te volg

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Die doel van hierdie afdeling is om te wys hoe om ’n reeds vooraf- trained model te **fine-tune om instruksies te volg** eerder as om net teks te genereer, byvoorbeeld om op take as ’n chat bot te reageer.

## Dataset

Om ’n LLM te fine-tune om instruksies te volg, is dit nodig om ’n dataset met **instruksies en response** te hê. Daar is verskillende prompt-formate om ’n LLM op te lei om instruksies te volg, byvoorbeeld:<sup>[[1]](#references)</sup>

- Die Alpaca prompt style-voorbeeld:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template-styl voorbeeld:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Opleiding met hierdie soort datastelle in plaas van net rou teks help die model verstaan dat dit take in ’n **gestruktureerde assistentformaat** moet beantwoord.

’n Baie algemene fout is om op een sjabloon te oefen en met ’n ander een af te lei. Moderne instruct models verwag gewoonlik die **native chat template van die basismodel** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, ens.), daarom word dit aanbeveel om die datastel na die presiese formaat om te skakel wat die teikenmodel reeds gebruik.

Een van die eerste dinge om dus met ’n datastel wat versoeke en antwoorde bevat, te doen, is om daardie data in die verlangde prompt-formaat te modelleer, soos:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
As die basismodel reeds met ’n tokenizer chat template gelewer word, kan dit veiliger wees om die dataset uit boodskaplyste saam te stel eerder as om skeidingstekens met die hand te skep:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Dan, soos altyd, is dit nodig om die dataset in opleidings-, validerings- en toetsstelle te verdeel.

## Batching & Data Loaders

Dan is dit nodig om al die invoere en verwagte uitvoere vir die opleiding in batches te verwerk. Hiervoor is dit nodig om:

- Die tekste te tokenize.
- Al die samples tot dieselfde lengte te pad (gewoonlik sal die lengte so groot wees soos die context length wat gebruik is om die LLM vooraf op te lei).
- Die verwagte tokens te skep deur die input met 1 te verskuif in 'n custom collate function.
- Sommige padding tokens met `-100` te vervang om hulle van die training loss uit te sluit: vervang ná die eerste `endoftext` token al die ander `endoftext` tokens met `-100` (want die gebruik van `cross_entropy(..., ignore_index=-100)` beteken dat dit targets met `-100` sal ignoreer).
- \[Optional] Masker ook alle tokens wat aan die vraag behoort met `-100`, sodat die LLM slegs leer om die antwoord te genereer. In die Alpaca-styl beteken dit gewoonlik dat alles tot by `### Response:` gemasker word.
- **Modern SFT best practice:** indien die dataset conversationeel is, bereken die loss slegs op die **assistant completion tokens** en nie op die user/system prompt nie. Dit voorkom dat die model geleer word om die prompt-teks self te voorspel.<sup>[[3]](#references)</sup>
- **Throughput optimization:** wanneer die dataset baie kort samples bevat, is dit algemeen om **verskeie examples in dieselfde sequence te pack** om minder van die context window te vermors.<sup>[[3]](#references)</sup>

Nadat dit geskep is, is dit tyd om die data loaders vir elke dataset (training, validation en test) te skep.

## Laai pre-trained LLM & Fine tune & Loss Checking

Dit is nodig om 'n pre-trained LLM te laai om dit te fine-tune. Dit is reeds op ander bladsye bespreek. Daarna is dit moontlik om die voorheen gebruikte training function te gebruik om die LLM te fine-tune.

Tydens die training is dit ook moontlik om te sien hoe die training loss en validation loss gedurende die epochs verander, om te bepaal of die loss verminder en of overfitting plaasvind.\
Onthou dat overfitting plaasvind wanneer die training loss verminder, maar die validation loss nie verminder nie of selfs toeneem. Om dit te voorkom, is die eenvoudigste oplossing om die training te stop by die epoch waar hierdie gedrag begin.

As GPU memory 'n beperking is, kyk na [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), want in die praktyk word die meeste instruction-tuning jobs met **LoRA/QLoRA/PEFT adapters** gedoen in plaas daarvan om elke parameter van die base model by te werk.

## Modern post-training variants

Die klassieke benadering is **supervised fine-tuning (SFT)** oor `(instruction, answer)`-pare. Huidige instruct-model pipelines verdeel post-training egter dikwels in verskeie fases:

1. **SFT** om die uitvoerformaat, antwoordstyl en taakverspreiding aan te leer.
2. **Preference optimization** om die model een antwoord bo 'n ander te laat verkies sonder dat 'n aparte reward model nodig is.
3. **Optional** online optimization soos RLHF / PPO vir spesifieke produkte of veiligheidsdoelwitte.

Die algemeenste preference-gebaseerde alternatiewe ná SFT is:

- **DPO (Direct Preference Optimization):** optimaliseer voorkeur- teenoor afgekeurde antwoorde direk.
- **ORPO / KTO / SimPO:** eenvoudiger variante wat van die engineering-overhead van volledige RLHF-pipelines verminder.

In die praktyk gebruik hierdie metodes gewoonlik óf **chosen/rejected response pairs** vir dieselfde prompt óf 'n eenvoudiger **desirable / undesirable**-sein. Daarom word die kwaliteit van die preference dataset net so belangrik soos die SFT corpus self.

Dit is nuttig omdat die duur deel van baie projekte nie is om die model die formaat aan te leer nie, maar om dit te leer om **die antwoordstyl te verkies wat mense wil hê**. As jy meer besonderhede oor die RL-kant en reward-model poisoning wil hê, kyk na [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Aangesien dit nie 'n classification fine-tune is waar dit moontlik is om meer op die loss-veranderinge te vertrou nie, is dit ook belangrik om die kwaliteit van die antwoorde in die toetsstel na te gaan. Daarom word dit aanbeveel om die gegenereerde antwoorde uit al die toetsstelle te versamel en **hulle kwaliteit handmatig na te gaan** om te sien of daar verkeerde antwoorde is (let daarop dat dit moontlik is vir die LLM om die formaat en syntax van die antwoordstelling korrek te genereer, maar 'n heeltemal verkeerde antwoord te gee. Die loss-verandering sal nie hierdie gedrag weerspieël nie).\
Let daarop dat dit ook moontlik is om hierdie review uit te voer deur die gegenereerde antwoorde en die verwagte antwoorde aan **ander LLMs deur te gee en hulle te vra om die antwoorde te evalueer**.

Moderne evaluations vir instruction-following wat voorkeur behoort te geniet, is:

- **IFEval:** kontroleer of die model werklik eksplisiete beperkings uit die prompt volg, eerder as om bloot goed te klink.
- **AlpacaEval 2 / pairwise judges:** nuttig om generations met 'n baseline model te vergelyk.
- **Arena-style head-to-head evals:** nuttig wanneer jy die relatiewe rangorde van verskeie checkpoints en prompts benodig.

Ander toetse om uit te voer om die kwaliteit van die antwoorde te verifieer:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU evalueer 'n model se kennis en probleemoplossingsvermoëns oor 57 vakgebiede, insluitend geesteswetenskappe, wetenskappe en meer. Dit gebruik multiple-choice-vrae om begrip op verskeie moeilikheidsvlakke te assesseer, van elementêr tot gevorderd professioneel.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Hierdie platform laat gebruikers toe om antwoorde van verskillende chatbots langs mekaar te vergelyk. Gebruikers voer 'n prompt in, waarna verskeie chatbots antwoorde genereer wat direk vergelyk kan word.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval is 'n geoutomatiseerde evaluation framework waar 'n gevorderde LLM soos GPT-4 die antwoorde van ander models op verskeie prompts assesseer.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE is 'n versameling van nege natural language understanding-take, insluitend sentiment analysis, textual entailment en question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE bou voort op GLUE en sluit meer uitdagende take in wat ontwerp is om moeilik te wees vir huidige models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench is 'n grootskaalse benchmark met meer as 200 take wat 'n model se vermoëns op gebiede soos reasoning, translation en question answering toets.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM verskaf 'n omvattende evaluation oor verskeie metrics soos accuracy, robustness en fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** 'n Open-source evaluation framework deur OpenAI waarmee AI-models op custom en gestandaardiseerde take getoets kan word.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** 'n Versameling programming problems wat gebruik word om language models se code generation-vermoëns te evalueer.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD bestaan uit vrae oor Wikipedia-artikels, waar models die teks moet verstaan om akkuraat te antwoord.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** 'n Grootskaalse dataset van trivia-vrae en -antwoorde, saam met evidence documents.

en nog baie, baie meer.

## Security notes for instruction tuning

Instruction-tuning datasets is ook 'n attack surface. As 'n attacker 'n klein aantal poisoned samples in die SFT corpus kan invoeg, kan die model 'n **trigger-conditioned behaviour** aanleer terwyl dit steeds normaal op clean prompts lyk.<sup>[[4]](#references)</sup>

Tipiese malicious patterns om tydens red teaming te toets, is:

- **Instruction backdoors:** 'n seldsame trigger string, role prefix, unicode pattern of formatting sequence veroorsaak dat die model attacker-chosen content uitvoer.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** die model gedra hom korrek tydens normale evaluations, maar verander sy gedrag slegs wanneer 'n baie spesifieke trigger verskyn.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** 'n oënskynlik harmless domain fine-tune kan die model na 'n slegte gedragsgebied buite die beoogde task distribution verskuif.

Praktiese kontroles:

- Hou 'n **canary set** van synthetic trigger prompts en voer dit op elke checkpoint uit.
- Deduplicate en kontroleer die provenance van die SFT corpus voor training.
- Moet nooit train op die presiese prompts wat deur die benchmark gebruik word waaroor jy later sal rapporteer nie.
- Vergelyk die base model met die fine-tuned model op security-sensitive prompts om onverwagte behaviour drift op te spoor.

## Follow instructions fine-tuning code

Jy kan 'n voorbeeld van die code om hierdie fine-tuning uit te voer, vind by [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

'n Praktiese moderne alternatief is om 'n trainer te gebruik wat reeds chat templates, assistant-only loss, packing en PEFT adapters ondersteun. As jy later preference alignment wil toepas, verskaf dieselfde ecosystem ook `DPOTrainer`-style workflows vir datasets met `prompt` / `chosen` / `rejected`-fields:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
