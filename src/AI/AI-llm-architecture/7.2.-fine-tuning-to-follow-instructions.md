# 7.2. Fine-Tuning para seguir instruções

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> O objetivo desta seção é mostrar como fazer **fine-tuning de um modelo já pré-treinado para seguir instruções**, em vez de apenas gerar texto, por exemplo, respondendo a tarefas como um chatbot.

## Dataset

Para fazer fine-tuning de um LLM para seguir instruções, é necessário ter um dataset com **instruções e respostas**. Existem diferentes formatos de prompt para treinar um LLM a seguir instruções, por exemplo:

- O exemplo de estilo de prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Exemplo no estilo de template de chat do Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Treinar com esse tipo de dataset, em vez de usar apenas texto bruto, ajuda o modelo a entender que precisa responder às tarefas em um **formato de assistant estruturado**.

Um erro muito comum é treinar usando um template e fazer a inferência usando outro. Os modelos instruct modernos geralmente esperam o **template de chat nativo do modelo base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML etc.); portanto, recomenda-se converter o dataset para o formato exato que o modelo-alvo já utiliza.

Por isso, uma das primeiras coisas a fazer com um dataset que contenha solicitações e respostas é modelar esses dados no formato de prompt desejado, como:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Se o modelo base já vem com um chat template do tokenizer, pode ser mais seguro criar o dataset a partir de listas de mensagens em vez de elaborar separadores manualmente:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Então, como sempre, é necessário separar o dataset em conjuntos de treinamento, validação e teste.

## Batching & Data Loaders

Em seguida, é necessário agrupar todas as entradas e saídas esperadas para o treinamento. Para isso, é necessário:<sup>[[1]](#references)</sup>

- Tokenizar os textos.
- Preencher todas as amostras até o mesmo comprimento (normalmente, o comprimento será tão grande quanto o context length usado para pré-treinar o LLM).
- Criar os tokens esperados deslocando a entrada em 1 em uma função `collate` personalizada.
- Substituir alguns tokens de preenchimento por `-100` para excluí-los da loss de treinamento: após o primeiro token `endoftext`, substituir todos os outros tokens `endoftext` por `-100` (porque usar `cross_entropy(..., ignore_index=-100)` significa que os targets com `-100` serão ignorados).
- \[Optional] Mascarar usando `-100` também todos os tokens pertencentes à pergunta, para que o LLM aprenda apenas a gerar a resposta. No estilo Alpaca, isso normalmente significa mascarar tudo até `### Response:`.
- **Modern SFT best practice:** se o dataset for conversacional, calcular a loss apenas nos **assistant completion tokens**, e não no prompt do usuário/sistema. Isso evita ensinar o modelo a prever o próprio texto do prompt.<sup>[[2]](#references)</sup>
- **Throughput optimization:** quando o dataset contém muitas amostras curtas, é comum **empacotar vários exemplos na mesma sequência** para desperdiçar menos da context window.

Com isso criado, é hora de criar os data loaders para cada dataset (treinamento, validação e teste).

## Load pre-trained LLM & Fine tune & Loss Checking

É necessário carregar um LLM pré-treinado para realizar o fine-tuning. Isso já foi discutido em outras páginas. Em seguida, é possível usar a função de treinamento utilizada anteriormente para realizar o fine-tuning do LLM.

Durante o treinamento, também é possível observar como a training loss e a validation loss variam ao longo das epochs, para verificar se a loss está sendo reduzida e se está ocorrendo overfitting.\
Lembre-se de que overfitting ocorre quando a training loss é reduzida, mas a validation loss não é reduzida ou até aumenta. Para evitar isso, a maneira mais simples é interromper o treinamento na epoch em que esse comportamento começa.

Se a memória da GPU for uma limitação, consulte [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), pois, na prática, a maioria dos trabalhos de instruction-tuning é realizada com **LoRA/QLoRA/PEFT adapters**, em vez de atualizar todos os parâmetros do modelo base.

## Modern post-training variants

A abordagem clássica é o **supervised fine-tuning (SFT)** sobre pares `(instruction, answer)`. No entanto, os pipelines atuais de modelos instruct frequentemente dividem o post-training em várias fases:

1. **SFT** para ensinar o formato da saída, o estilo da resposta e a distribuição de tarefas.
2. **Preference optimization** para fazer o modelo preferir uma resposta em vez de outra sem precisar de um reward model separado.
3. **Optional** online optimization, como RLHF / PPO, para produtos específicos ou objetivos de segurança.

As alternativas mais comuns baseadas em preferência após o SFT são:

- **DPO (Direct Preference Optimization):** otimiza diretamente respostas preferidas em relação às rejeitadas.
- **ORPO / KTO / SimPO:** variantes mais simples que reduzem parte da sobrecarga de engenharia dos pipelines completos de RLHF.

Na prática, esses métodos geralmente consomem pares de respostas **chosen/rejected** para o mesmo prompt ou um sinal mais simples de **desirable / undesirable**, portanto a qualidade do preference dataset se torna tão importante quanto o próprio corpus de SFT.

Isso é útil porque, para muitos projetos, a parte mais cara não é ensinar o formato ao modelo, mas ensiná-lo a **preferir o estilo de resposta que os humanos desejam**. Se quiser mais detalhes sobre o lado de RL e o reward-model poisoning, consulte [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Como este não é um classification fine-tune no qual é possível confiar mais nas variações da loss, também é importante verificar a qualidade das respostas no conjunto de teste. Portanto, recomenda-se coletar as respostas geradas de todos os conjuntos de teste e **verificar manualmente a qualidade delas** para identificar respostas incorretas (observe que é possível que o LLM gere corretamente o formato e a sintaxe da frase de resposta, mas forneça uma resposta completamente errada. A variação da loss não refletirá esse comportamento).\
Observe que também é possível realizar essa revisão passando as respostas geradas e as respostas esperadas para **outros LLMs e solicitando que eles avaliem as respostas**.

As avaliações modernas de instruction-following que vale a pena priorizar são:

- **IFEval:** verifica se o modelo realmente segue restrições explícitas do prompt, em vez de apenas parecer bom.
- **AlpacaEval 2 / pairwise judges:** útil para comparar gerações com um modelo de referência.
- **Arena-style head-to-head evals:** útil quando é necessário classificar relativamente vários checkpoints e prompts.

Outros testes a serem executados para verificar a qualidade das respostas:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU avalia o conhecimento e as capacidades de resolução de problemas de um modelo em 57 áreas, incluindo humanidades, ciências e outras. Ele usa perguntas de múltipla escolha para avaliar a compreensão em vários níveis de dificuldade, do ensino básico ao profissional avançado.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Esta plataforma permite que os usuários comparem respostas de diferentes chatbots lado a lado. Os usuários inserem um prompt, e vários chatbots geram respostas que podem ser comparadas diretamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval é um framework de avaliação automatizada no qual um LLM avançado, como o GPT-4, avalia as respostas de outros modelos para vários prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE é uma coleção de nove tarefas de compreensão de linguagem natural, incluindo análise de sentimentos, entailment textual e question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Baseado no GLUE, o SuperGLUE inclui tarefas mais desafiadoras, projetadas para serem difíceis para os modelos atuais.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench é um benchmark de larga escala com mais de 200 tarefas que testam as capacidades de um modelo em áreas como raciocínio, tradução e question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fornece uma avaliação abrangente com várias métricas, como precisão, robustez e fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Um framework de avaliação open source da OpenAI que permite testar modelos de AI em tarefas personalizadas e padronizadas.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Uma coleção de problemas de programação usada para avaliar as capacidades de code generation de modelos de linguagem.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD consiste em perguntas sobre artigos da Wikipedia, nas quais os modelos precisam compreender o texto para responder com precisão.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Um dataset de larga escala de perguntas e respostas de trivia, acompanhado de documentos de evidência.

e muitos, muitos outros.

## Security notes for instruction tuning

Instruction-tuning datasets também são uma attack surface. Se um atacante conseguir inserir uma pequena quantidade de amostras envenenadas no corpus de SFT, o modelo poderá aprender um **trigger-conditioned behaviour** enquanto ainda parecer normal em prompts limpos.<sup>[[3]](#references)</sup>

Padrões maliciosos típicos a serem testados durante o red teaming são:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** uma string de trigger rara, um prefixo de role, um padrão unicode ou uma sequência de formatação faz com que o modelo gere conteúdo escolhido pelo atacante.
- **Sleeper-agent behaviour:** o modelo se comporta corretamente durante avaliações normais, mas muda seu comportamento apenas quando um trigger muito específico aparece.
- **Narrow-domain misalignment:** um fine-tune de domínio aparentemente inofensivo pode levar o modelo a uma região problemática de comportamento fora da distribuição de tarefas pretendida.

Verificações práticas:

- Mantenha um **canary set** de trigger prompts sintéticos e execute-o em cada checkpoint.
- Faça deduplication e verifique a proveniência do corpus de SFT antes do treinamento.
- Nunca treine com os prompts exatos usados pelo benchmark que será reportado posteriormente.
- Compare o modelo base com o modelo fine-tuned em prompts sensíveis à segurança para detectar um drift inesperado de comportamento.

## Follow instructions fine-tuning code

Você pode encontrar um exemplo do código para realizar este fine-tuning em [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Uma alternativa moderna e prática é usar um trainer que já ofereça suporte a chat templates, assistant-only loss, packing e PEFT adapters. Se posteriormente você quiser realizar preference alignment, o mesmo ecossistema também oferece workflows no estilo `DPOTrainer` para datasets com campos `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
