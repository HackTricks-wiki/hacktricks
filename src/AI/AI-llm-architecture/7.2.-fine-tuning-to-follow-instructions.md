## Dataset

Ili kufanya fine-tune LLM ifuate maagizo, inahitajika kuwa na dataset yenye **maagizo na majibu**. Kuna prompt formats tofauti za kufundisha LLM ifuate maagizo, kwa mfano:<sup>[[1]](#references)</sup>

- Mfano wa mtindo wa Alpaca prompt:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Mfano wa mtindo wa Phi-3 / chat template:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Kufunza kwa kutumia aina hizi za dataset badala ya kutumia raw text pekee husaidia model kuelewa kwamba inahitaji kujibu tasks katika **structured assistant format**.

Kosa la kawaida sana ni kufunza kwa template moja na kufanya inference kwa template nyingine. Instruct models za kisasa kwa kawaida hutegemea **native chat template ya base model** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, n.k.), kwa hiyo inapendekezwa kubadilisha dataset iwe katika format halisi ambayo target model tayari inatumia.

Kwa hiyo, mojawapo ya mambo ya kwanza ya kufanya kwa dataset iliyo na requests na answers ni ku-model data hiyo katika prompt format inayohitajika, kama vile:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Ikiwa base model tayari inakuja na tokenizer chat template, inaweza kuwa salama zaidi kujenga dataset kutoka kwenye message lists badala ya kutengeneza separators kwa mkono:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Kisha, kama kawaida, inahitajika kutenganisha dataset katika seti za training, validation, na testing.

## Batching & Data Loaders

Kisha, inahitajika kuweka inputs zote na outputs zinazotarajiwa katika batches kwa ajili ya training. Kwa hili, inahitajika:

- Tokenize texts.
- Pad samples zote ziwe na urefu sawa (kwa kawaida urefu utakuwa mkubwa sawa na context length iliyotumika ku-pre-train LLM).
- Create tokens zinazotarajiwa kwa ku-shift input kwa 1 ndani ya custom collate function.
- Replace baadhi ya padding tokens kwa `-100` ili kuziondoa kwenye training loss: baada ya `endoftext` token ya kwanza, badilisha `endoftext` tokens nyingine zote kuwa `-100` (kwa sababu kutumia `cross_entropy(..., ignore_index=-100)` kunamaanisha kwamba itapuuza targets zenye `-100`).
- \[Optional] Mask kwa kutumia `-100` pia tokens zote zilizo kwenye question ili LLM ijifunze tu jinsi ya kutengeneza answer. Katika mtindo wa Alpaca, hii kwa kawaida inamaanisha ku-mask kila kitu hadi `### Response:`.
- **Modern SFT best practice:** ikiwa dataset ni ya mazungumzo, compute loss kwenye **assistant completion tokens** pekee na si kwenye user/system prompt. Hii huzuia kufundisha model kutabiri prompt text yenyewe.<sup>[[3]](#references)</sup>
- **Throughput optimization:** wakati dataset ina samples nyingi fupi, ni kawaida **kupack examples kadhaa katika sequence moja** ili kupunguza context window inayopotea.<sup>[[3]](#references)</sup>

Baada ya kuunda hivi, ni wakati wa kuunda data loaders kwa kila dataset (training, validation, na test).

## Load pre-trained LLM & Fine tune & Loss Checking

Inahitajika ku-load pre-trained LLM ili kui-fine-tune. Hili tayari lilijadiliwa katika kurasa nyingine. Kisha, inawezekana kutumia training function iliyotumika awali ili ku-fine-tune LLM.

Wakati wa training, inawezekana pia kuona jinsi training loss na validation loss zinavyobadilika katika epochs ili kuona kama loss inapungua na kama overfitting inatokea.\
Kumbuka kwamba overfitting hutokea wakati training loss inapungua lakini validation loss haipungui au hata inaongezeka. Ili kuepuka hili, jambo rahisi zaidi ni kusimamisha training katika epoch ambayo tabia hii inaanza.

Ikiwa GPU memory ni limitation, angalia [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), kwa sababu kwa vitendo, instruction-tuning jobs nyingi hufanywa kwa **LoRA/QLoRA/PEFT adapters** badala ya ku-update kila parameter ya base model.

## Modern post-training variants

Njia ya kawaida ni **supervised fine-tuning (SFT)** kupitia jozi za `(instruction, answer)`. Hata hivyo, instruct-model pipelines za sasa mara nyingi hugawanya post-training katika awamu kadhaa:

1. **SFT** ili kufundisha output format, answer style, na task distribution.
2. **Preference optimization** ili kufanya model ipende answer moja kuliko nyingine bila kuhitaji reward model tofauti.
3. **Optional** online optimization kama RLHF / PPO kwa bidhaa au malengo maalum ya usalama.

Preference-based alternatives zinazotumika zaidi baada ya SFT ni:

- **DPO (Direct Preference Optimization):** hu-optimize moja kwa moja majibu yaliyopendelewa dhidi ya yaliyokataliwa.
- **ORPO / KTO / SimPO:** variants rahisi zinazopunguza baadhi ya engineering overhead ya full RLHF pipelines.

Kwa vitendo, methods hizi kwa kawaida hutumia ama **chosen/rejected response pairs** kwa prompt ileile au signal rahisi ya **desirable / undesirable**, hivyo ubora wa preference dataset huwa muhimu sawa na SFT corpus yenyewe.

Hii ni muhimu kwa sababu katika projects nyingi, sehemu yenye gharama kubwa si kufundisha model format, bali kuifundisha **kupendelea style ya answer ambayo binadamu wanataka**. Ikiwa unataka maelezo zaidi kuhusu upande wa RL na reward-model poisoning, angalia [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Kwa kuwa huu si classification fine-tune ambapo inawezekana kutegemea zaidi mabadiliko ya loss, ni muhimu pia ku-check ubora wa responses katika testing set. Kwa hiyo, inapendekezwa kukusanya generated responses kutoka testing sets zote na **ku-check ubora wake manually** ili kuona kama kuna majibu yasiyo sahihi (kumbuka kwamba inawezekana kwa LLM kutengeneza kwa usahihi format na syntax ya response sentence lakini kutoa jibu lisilo sahihi kabisa. Mabadiliko ya loss hayataonyesha tabia hii).\
Kumbuka kwamba inawezekana pia kufanya review hii kwa kupeleka generated responses na expected responses kwa **LLMs nyingine na kuziomba zitathmini responses**.

Modern instruction-following evaluations zinazofaa kupewa kipaumbele ni:

- **IFEval:** hu-check kama model inafuata kweli constraints zilizo wazi kutoka kwenye prompt badala ya kuonekana tu kuwa na majibu mazuri.
- **AlpacaEval 2 / pairwise judges:** zinafaa kulinganisha generations dhidi ya baseline model.
- **Arena-style head-to-head evals:** zinafaa unapohitaji relative ranking ya checkpoints na prompts kadhaa.

Tests nyingine za ku-run ili kuthibitisha ubora wa responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU hutathmini knowledge na problem-solving abilities za model katika subjects 57, zikiwemo humanities, sciences, na nyinginezo. Hutumia multiple-choice questions kutathmini uelewa katika viwango mbalimbali vya ugumu, kuanzia elementary hadi advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Platform hii huwawezesha users kulinganisha responses kutoka chatbots tofauti side by side. Users huingiza prompt, na chatbots nyingi hutengeneza responses zinazoweza kulinganishwa moja kwa moja.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval ni automated evaluation framework ambapo advanced LLM kama GPT-4 hutathmini responses za models nyingine kwa prompts mbalimbali.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE ni mkusanyiko wa natural language understanding tasks tisa, zikiwemo sentiment analysis, textual entailment, na question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Ikiendeleza GLUE, SuperGLUE inajumuisha tasks zenye changamoto zaidi ambazo zimeundwa kuwa ngumu kwa models za sasa.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench ni benchmark kubwa yenye tasks zaidi ya 200 zinazopima abilities za model katika maeneo kama reasoning, translation, na question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM hutoa comprehensive evaluation katika metrics mbalimbali kama accuracy, robustness, na fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Open-source evaluation framework kutoka OpenAI inayowezesha testing ya AI models kwenye custom na standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Mkusanyiko wa programming problems unaotumika kutathmini code generation abilities za language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD ina questions kuhusu Wikipedia articles, ambapo models lazima zielewe text ili kujibu kwa usahihi.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Dataset kubwa ya trivia questions na answers, pamoja na evidence documents.

na nyingine nyingi sana.

## Security notes for instruction tuning

Instruction-tuning datasets pia ni attack surface. Ikiwa attacker anaweza kuingiza idadi ndogo ya poisoned samples kwenye SFT corpus, model inaweza kujifunza **trigger-conditioned behaviour** huku ikiendelea kuonekana ya kawaida kwenye clean prompts.<sup>[[4]](#references)</sup>

Malicious patterns za kawaida za ku-test wakati wa red teaming ni:

- **Instruction backdoors:** rare trigger string, role prefix, unicode pattern, au formatting sequence husababisha model kutoa content iliyochaguliwa na attacker.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model hutenda kwa usahihi wakati wa normal evaluations lakini hubadilisha behaviour wakati trigger maalum sana inapoonekana.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** domain fine-tune inayoonekana haina madhara inaweza kupeleka model katika eneo baya la behaviour nje ya intended task distribution.

Practical checks:

- Hifadhi **canary set** ya synthetic trigger prompts na ui-run kwenye kila checkpoint.
- Deduplicate na ufanye provenance-check ya SFT corpus kabla ya training.
- Usifanye training kamwe kwenye prompts zilezile zinazotumiwa na benchmark utakayoripoti baadaye.
- Linganisha base model dhidi ya fine-tuned model kwenye security-sensitive prompts ili kugundua unexpected behaviour drift.

## Follow instructions fine-tuning code

Unaweza kupata mfano wa code ya kufanya fine-tuning hii katika [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Modern alternative ya vitendo ni kutumia trainer ambayo tayari inasaidia chat templates, assistant-only loss, packing, na PEFT adapters. Ikiwa baadaye unataka preference alignment, ecosystem hiyo hiyo pia hutoa workflows za aina ya `DPOTrainer` kwa datasets zilizo na fields za `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
