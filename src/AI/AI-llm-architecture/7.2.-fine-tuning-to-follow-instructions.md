# 7.2. Ajuste fino para seguir instrucciones

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> El objetivo de esta sección es mostrar cómo hacer **fine-tuning de un modelo ya preentrenado para seguir instrucciones** en lugar de simplemente generar texto, por ejemplo, respondiendo a tareas como un chatbot.

## Dataset

Para hacer fine-tuning de un LLM para que siga instrucciones, es necesario contar con un dataset con **instrucciones y respuestas**. Existen diferentes formatos de prompts para entrenar un LLM para que siga instrucciones, por ejemplo:

- El ejemplo de estilo de prompt de Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / ejemplo de estilo de chat template:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Entrenar con este tipo de datasets en lugar de usar solo raw text ayuda al modelo a comprender que debe responder a las tareas en un **formato estructurado de assistant**.

Un error muy común es entrenar con una plantilla y hacer inferencia con otra. Los modelos instruct modernos suelen esperar la **plantilla de chat nativa del modelo base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, etc.), por lo que se recomienda convertir el dataset al formato exacto que ya utiliza el modelo objetivo.

Por lo tanto, una de las primeras cosas que se deben hacer con un dataset que contiene requests y answers es modelar esos datos en el formato de prompt deseado, como:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Si el modelo base ya incluye una plantilla de chat del tokenizer, puede ser más seguro crear el dataset a partir de listas de mensajes en lugar de crear manualmente los separadores:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Entonces, como siempre, es necesario separar el dataset en conjuntos de entrenamiento, validación y prueba.

## Batching y cargadores de datos

A continuación, es necesario agrupar todas las entradas y salidas esperadas para el entrenamiento. Para ello, es necesario:<sup>[[1]](#references)</sup>

- Tokenizar los textos.
- Aplicar padding a todas las muestras hasta que tengan la misma longitud (normalmente, la longitud será tan grande como la longitud de contexto utilizada para preentrenar el LLM).
- Crear los tokens esperados desplazando 1 la entrada en una función `collate` personalizada.
- Sustituir algunos tokens de padding por `-100` para excluirlos de la pérdida de entrenamiento: después del primer token `endoftext`, sustituir todos los demás tokens `endoftext` por `-100` (porque usar `cross_entropy(..., ignore_index=-100)` significa que ignorará los objetivos con `-100`).
- \[Opcional] Aplicar también una máscara usando `-100` a todos los tokens pertenecientes a la pregunta, para que el LLM aprenda únicamente a generar la respuesta. En el estilo Alpaca, esto normalmente significa aplicar la máscara a todo hasta `### Response:`.
- **Práctica recomendada moderna para SFT:** si el dataset es conversacional, calcular la pérdida únicamente sobre los tokens de completion del **assistant**, y no sobre el prompt del usuario/sistema. Esto evita enseñar al modelo a predecir el texto del prompt.<sup>[[2]](#references)</sup>
- **Optimización del throughput:** cuando el dataset contiene muchas muestras cortas, es habitual **empaquetar varios ejemplos en la misma secuencia** para desperdiciar menos ventana de contexto.

Una vez creado esto, es hora de crear los cargadores de datos para cada dataset (entrenamiento, validación y prueba).

## Cargar LLM preentrenado, fine-tuning y comprobación de la pérdida

Es necesario cargar un LLM preentrenado para hacerle fine-tuning. Esto ya se explicó en otras páginas. Después, es posible utilizar la función de entrenamiento usada anteriormente para hacer fine-tuning del LLM.

Durante el entrenamiento también es posible observar cómo varían la pérdida de entrenamiento y la pérdida de validación durante las epochs, para comprobar si la pérdida se está reduciendo y si se está produciendo overfitting.\
Recuerda que el overfitting ocurre cuando la pérdida de entrenamiento se reduce, pero la pérdida de validación no se reduce o incluso aumenta. Para evitarlo, lo más sencillo es detener el entrenamiento en la epoch en la que comienza este comportamiento.

Si la memoria de la GPU es una limitación, consulta [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), porque en la práctica la mayoría de los trabajos de instruction-tuning se realizan con **adaptadores LoRA/QLoRA/PEFT**, en lugar de actualizar cada parámetro del modelo base.

## Variantes modernas de post-training

El enfoque clásico es el **supervised fine-tuning (SFT)** sobre pares `(instruction, answer)`. Sin embargo, los pipelines actuales de modelos instruct a menudo dividen el post-training en varias fases:

1. **SFT** para enseñar el formato de salida, el estilo de respuesta y la distribución de tareas.
2. **Optimización basada en preferencias** para hacer que el modelo prefiera una respuesta sobre otra sin necesitar un reward model independiente.
3. **Opcional:** optimización online, como RLHF / PPO, para productos específicos o objetivos de seguridad.

Las alternativas basadas en preferencias más comunes después de SFT son:

- **DPO (Direct Preference Optimization):** optimiza directamente las respuestas preferidas frente a las rechazadas.
- **ORPO / KTO / SimPO:** variantes más sencillas que reducen parte de la complejidad de ingeniería de los pipelines RLHF completos.

En la práctica, estos métodos suelen consumir pares de respuestas **chosen/rejected** para el mismo prompt o una señal más sencilla de **deseable / no deseable**, por lo que la calidad del dataset de preferencias se vuelve tan importante como el propio corpus de SFT.

Esto es útil porque, en muchos proyectos, la parte costosa no es enseñar al modelo el formato, sino enseñarle a **preferir el estilo de respuesta que quieren los humanos**. Si quieres más detalles sobre el lado de RL y el reward-model poisoning, consulta [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Calidad de las respuestas

Como esto no es un fine-tune de clasificación, en el que es posible confiar más en las variaciones de la pérdida, también es importante comprobar la calidad de las respuestas del conjunto de prueba. Por lo tanto, se recomienda recopilar las respuestas generadas de todos los conjuntos de prueba y **comprobar manualmente su calidad** para verificar si hay respuestas incorrectas (ten en cuenta que es posible que el LLM genere correctamente el formato y la sintaxis de la frase de respuesta, pero proporcione una respuesta completamente incorrecta. La variación de la pérdida no reflejará este comportamiento).\
Ten en cuenta que también es posible realizar esta revisión pasando las respuestas generadas y las respuestas esperadas a **otros LLMs y pidiéndoles que evalúen las respuestas**.

Las evaluaciones modernas de instruction-following que merece la pena priorizar son:

- **IFEval:** comprueba si el modelo sigue realmente las restricciones explícitas del prompt, en lugar de limitarse a sonar bien.
- **AlpacaEval 2 / jueces pairwise:** útiles para comparar las generaciones con un modelo baseline.
- **Evaluaciones head-to-head al estilo Arena:** útiles cuando necesitas establecer el ranking relativo de varios checkpoints y prompts.

Otras pruebas que se pueden ejecutar para verificar la calidad de las respuestas:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU evalúa el conocimiento y las capacidades de resolución de problemas de un modelo en 57 materias, incluidas humanidades, ciencias y otras. Utiliza preguntas de opción múltiple para evaluar la comprensión en distintos niveles de dificultad, desde el nivel elemental hasta el profesional avanzado.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): esta plataforma permite a los usuarios comparar las respuestas de distintos chatbots lado a lado. Los usuarios introducen un prompt y varios chatbots generan respuestas que se pueden comparar directamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval es un framework de evaluación automatizada en el que un LLM avanzado como GPT-4 evalúa las respuestas de otros modelos a distintos prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE es una colección de nueve tareas de comprensión del lenguaje natural, incluido el análisis de sentimiento, la implicación textual y la respuesta a preguntas.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** basándose en GLUE, SuperGLUE incluye tareas más desafiantes diseñadas para resultar difíciles para los modelos actuales.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench es un benchmark a gran escala con más de 200 tareas que evalúan las capacidades de un modelo en áreas como el razonamiento, la traducción y la respuesta a preguntas.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM proporciona una evaluación integral mediante varias métricas, como precisión, robustez y equidad.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** un framework de evaluación open source de OpenAI que permite probar modelos de IA en tareas personalizadas y estandarizadas.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** una colección de problemas de programación utilizada para evaluar las capacidades de generación de código de los modelos de lenguaje.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD consta de preguntas sobre artículos de Wikipedia, en las que los modelos deben comprender el texto para responder con precisión.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** un dataset a gran escala de preguntas y respuestas de trivialidades, junto con documentos de evidencia.

y muchos, muchos más.

## Notas de seguridad para instruction tuning

Los datasets de instruction-tuning también son una superficie de ataque. Si un atacante puede insertar un pequeño número de muestras poisoned en el corpus de SFT, el modelo puede aprender un **comportamiento condicionado por un trigger** y seguir pareciendo normal ante prompts limpios.<sup>[[3]](#references)</sup>

Los patrones maliciosos habituales que se deben probar durante el red teaming son:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** una cadena de trigger poco frecuente, un prefijo de rol, un patrón Unicode o una secuencia de formato hace que el modelo genere contenido elegido por el atacante.
- **Comportamiento de sleeper-agent:** el modelo se comporta correctamente durante las evaluaciones normales, pero cambia su comportamiento únicamente cuando aparece un trigger muy específico.
- **Desalineación en un dominio limitado:** un fine-tune aparentemente inofensivo de un dominio puede llevar al modelo a una región de comportamiento problemática fuera de la distribución de tareas prevista.

Comprobaciones prácticas:

- Mantén un **canary set** de prompts de trigger sintéticos y ejecútalo en cada checkpoint.
- Deduplica y comprueba la procedencia del corpus de SFT antes del entrenamiento.
- Nunca entrenes con los prompts exactos utilizados por el benchmark que posteriormente vayas a presentar.
- Compara el modelo base con el modelo al que se ha hecho fine-tuning en prompts sensibles para la seguridad, con el fin de detectar cambios inesperados de comportamiento.

## Código de fine-tuning para seguir instrucciones

Puedes encontrar un ejemplo del código para realizar este fine-tuning en [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Una alternativa moderna y práctica consiste en utilizar un trainer que ya sea compatible con chat templates, assistant-only loss, packing y adaptadores PEFT. Si posteriormente quieres realizar preference alignment, el mismo ecosistema también proporciona workflows del tipo `DPOTrainer` para datasets con campos `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
