# 7.2. Fine-Tuning zum Befolgen von Anweisungen

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Ziel dieses Abschnitts ist zu zeigen, wie man ein bereits vortrainiertes Modell per **Fine-Tuning so anpasst, dass es Anweisungen befolgt**, anstatt lediglich Text zu generieren, beispielsweise indem es auf Aufgaben wie ein Chatbot reagiert.

## Dataset

Um ein LLM per Fine-Tuning so anzupassen, dass es Anweisungen befolgt, benötigt man ein Dataset mit **Anweisungen und Antworten**. Es gibt verschiedene Prompt-Formate, um ein LLM auf das Befolgen von Anweisungen zu trainieren, zum Beispiel:<sup>[[1]](#references)</sup>

- Beispiel für den Alpaca-Prompt-Stil:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / Beispiel im Stil eines Chat-Templates:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Das Training mit solchen Datensätzen anstelle von einfachem Rohtext hilft dem Modell zu verstehen, dass es Aufgaben in einem **strukturierten Assistant-Format** beantworten muss.

Ein sehr häufiger Fehler besteht darin, mit einem Template zu trainieren und mit einem anderen zu inferieren. Moderne Instruct-Modelle erwarten normalerweise das **native Chat-Template des Basismodells** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML usw.). Daher wird empfohlen, den Datensatz in genau das Format zu konvertieren, das das Zielmodell bereits verwendet.

Daher sollte man als eine der ersten Maßnahmen bei einem Datensatz, der Anfragen und Antworten enthält, diese Daten im gewünschten Prompt-Format modellieren, etwa so:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Wenn das Basismodell bereits mit einem Tokenizer-Chat-Template ausgeliefert wird, kann es sicherer sein, den Datensatz aus Nachrichtenlisten zu erstellen, statt Trennzeichen manuell zusammenzustellen:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Dann muss der Datensatz wie immer in Trainings-, Validierungs- und Testsets aufgeteilt werden.

## Batching & Data Loaders

Anschließend müssen alle Inputs und erwarteten Outputs für das Training in Batches aufgeteilt werden. Dafür müssen folgende Schritte durchgeführt werden:

- Die Texte tokenisieren.
- Alle Samples auf dieselbe Länge auffüllen (normalerweise entspricht diese Länge der beim Pre-Training des LLM verwendeten Context Length).
- Die erwarteten Tokens erstellen, indem der Input in einer benutzerdefinierten Collate-Funktion um 1 verschoben wird.
- Einige Padding-Tokens durch `-100` ersetzen, um sie vom Trainings-Loss auszuschließen: Nach dem ersten `endoftext`-Token alle weiteren `endoftext`-Tokens durch `-100` ersetzen (da `cross_entropy(..., ignore_index=-100)` Targets mit `-100` ignoriert).
- \[Optional] Ebenfalls alle zur Frage gehörenden Tokens mit `-100` maskieren, damit das LLM nur lernt, die Antwort zu generieren. Im Alpaca-Stil bedeutet dies normalerweise, alles bis einschließlich `### Response:` zu maskieren.
- **Modern SFT best practice:** Wenn der Datensatz konversationell ist, den Loss nur auf den **assistant completion tokens** und nicht auf dem User-/System-Prompt berechnen. Dadurch wird verhindert, dass das Modell lernt, den Prompt-Text selbst vorherzusagen.<sup>[[3]](#references)</sup>
- **Throughput optimization:** Wenn der Datensatz viele kurze Samples enthält, ist es üblich, **mehrere Beispiele in dieselbe Sequenz zu packen**, damit weniger Context Window verschwendet wird.<sup>[[3]](#references)</sup>

Nachdem dies erstellt wurde, ist es an der Zeit, die Data Loaders für jeden Datensatz (Training, Validierung und Test) zu erstellen.

## Load pre-trained LLM & Fine tune & Loss Checking

Es muss ein vortrainiertes LLM geladen werden, um es zu fine-tunen. Dies wurde bereits auf anderen Seiten besprochen. Anschließend kann die zuvor verwendete Trainingsfunktion genutzt werden, um das LLM zu fine-tunen.

Während des Trainings kann außerdem beobachtet werden, wie sich der Trainings-Loss und der Validierungs-Loss während der Epochen verändern, um festzustellen, ob der Loss sinkt und ob Overfitting auftritt.\
Denke daran, dass Overfitting auftritt, wenn der Trainings-Loss sinkt, der Validierungs-Loss jedoch nicht sinkt oder sogar steigt. Um dies zu vermeiden, besteht die einfachste Vorgehensweise darin, das Training in der Epoche zu stoppen, in der dieses Verhalten beginnt.

Wenn der GPU-Speicher eine Einschränkung darstellt, siehe [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), da in der Praxis die meisten Instruction-Tuning-Jobs mit **LoRA/QLoRA/PEFT-Adaptern** durchgeführt werden, anstatt jeden Parameter des Base Models zu aktualisieren.

## Modern post-training variants

Der klassische Ansatz ist **supervised fine-tuning (SFT)** mit `(instruction, answer)`-Paaren. Aktuelle Pipelines für Instruct Models teilen das Post-Training jedoch häufig in mehrere Phasen auf:

1. **SFT**, um das Output-Format, den Antwortstil und die Aufgabenverteilung zu vermitteln.
2. **Preference optimization**, damit das Modell eine Antwort gegenüber einer anderen bevorzugt, ohne ein separates Reward Model zu benötigen.
3. **Optional** eine Online-Optimierung wie RLHF / PPO für bestimmte Produkte oder Safety-Ziele.

Die häufigsten Preference-basierten Alternativen nach SFT sind:

- **DPO (Direct Preference Optimization):** Optimiert direkt bevorzugte gegenüber abgelehnten Antworten.
- **ORPO / KTO / SimPO:** Einfachere Varianten, die einen Teil des technischen Aufwands vollständiger RLHF-Pipelines reduzieren.

In der Praxis benötigen diese Methoden normalerweise entweder **chosen/rejected response pairs** für denselben Prompt oder ein einfacheres **desirable / undesirable**-Signal. Daher wird die Qualität des Preference-Datensatzes genauso wichtig wie der SFT-Corpus selbst.

Dies ist nützlich, weil der aufwendige Teil vieler Projekte nicht darin besteht, dem Modell das Format beizubringen, sondern darin, ihm beizubringen, **den von Menschen gewünschten Antwortstil zu bevorzugen**. Weitere Details zur RL-Seite und zu Reward-Model-Poisoning findest du unter [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Da es sich hierbei nicht um ein Classification-Fine-Tuning handelt, bei dem man den Loss-Variationen stärker vertrauen kann, ist es ebenfalls wichtig, die Qualität der Antworten im Testset zu überprüfen. Daher wird empfohlen, die generierten Antworten aus allen Testsets zu sammeln und ihre **Qualität manuell zu überprüfen**, um falsche Antworten zu erkennen (beachte, dass das LLM das Format und die Syntax des Antwortsatzes korrekt generieren, aber dennoch eine vollständig falsche Antwort geben kann. Die Loss-Variation wird dieses Verhalten nicht widerspiegeln).\
Beachte, dass diese Überprüfung auch durchgeführt werden kann, indem die generierten Antworten und die erwarteten Antworten an **andere LLMs übergeben werden, mit der Bitte, die Antworten zu bewerten**.

Moderne Evaluierungen für Instruction Following, die priorisiert werden sollten, sind:

- **IFEval:** Überprüft, ob das Modell tatsächlich explizite Einschränkungen aus dem Prompt befolgt, anstatt nur überzeugend zu klingen.
- **AlpacaEval 2 / pairwise judges:** Nützlich, um Generierungen mit einem Baseline Model zu vergleichen.
- **Arena-style head-to-head evals:** Nützlich, wenn ein relatives Ranking mehrerer Checkpoints und Prompts benötigt wird.

Weitere Tests zur Überprüfung der Antwortqualität:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU bewertet das Wissen und die Problemlösungsfähigkeiten eines Modells in 57 Fachgebieten, darunter Geisteswissenschaften, Naturwissenschaften und weitere. Mithilfe von Multiple-Choice-Fragen wird das Verständnis auf verschiedenen Schwierigkeitsstufen bewertet, von elementaren bis hin zu fortgeschrittenen beruflichen Kenntnissen.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Diese Plattform ermöglicht es Usern, Antworten verschiedener Chatbots direkt nebeneinander zu vergleichen. Die User geben einen Prompt ein, woraufhin mehrere Chatbots Antworten generieren, die direkt verglichen werden können.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval ist ein automatisiertes Evaluierungs-Framework, in dem ein fortgeschrittenes LLM wie GPT-4 die Antworten anderer Modelle auf verschiedene Prompts bewertet.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE ist eine Sammlung von neun Natural-Language-Understanding-Aufgaben, darunter Sentiment Analysis, Textual Entailment und Question Answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE baut auf GLUE auf und enthält anspruchsvollere Aufgaben, die für aktuelle Modelle schwierig sind.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench ist ein groß angelegter Benchmark mit mehr als 200 Aufgaben, die die Fähigkeiten eines Modells in Bereichen wie Reasoning, Übersetzung und Question Answering testen.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM bietet eine umfassende Evaluierung anhand verschiedener Metriken wie Accuracy, Robustness und Fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Ein Open-Source-Evaluierungs-Framework von OpenAI, mit dem AI-Modelle anhand benutzerdefinierter und standardisierter Aufgaben getestet werden können.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Eine Sammlung von Programmierproblemen zur Bewertung der Code-Generierungsfähigkeiten von Language Models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD besteht aus Fragen zu Wikipedia-Artikeln, wobei die Modelle den Text verstehen müssen, um korrekte Antworten zu geben.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Ein groß angelegter Datensatz mit Trivia-Fragen und -Antworten sowie Belegdokumenten.

und viele weitere.

## Security notes for instruction tuning

Instruction-Tuning-Datensätze sind ebenfalls eine Angriffsfläche. Wenn ein Angreifer eine kleine Anzahl vergifteter Samples in den SFT-Corpus einschleusen kann, kann das Modell ein **trigger-conditioned behaviour** erlernen und dabei bei sauberen Prompts weiterhin normal wirken. Das Poisoning muss nicht zwangsläufig Labels oder normale Input-Instanzen beschädigen: In einer Studie reichten bösartige Task Instructions mit insgesamt etwa 1.000 Tokens aus, und das erlernte Verhalten übertrug sich auf unbekannte Generierungsaufgaben und widerstand anschließendem Clean Fine-Tuning.<sup>[[4]](#references)</sup>

Typische bösartige Muster, die beim Red Teaming getestet werden sollten:

- **Instruction-only backdoors:** Die Aufgabenbeschreibung vergiften, während gewöhnliche Instanzen und Labels unverändert bleiben. Die bösartige Instruction kann sich auf andere Datensätze übertragen, und ein auf einer Aufgabe vergiftetes Modell kann das Verhalten auf unbekannte Generierungsaufgaben übertragen. Daher sollten paraphrasierte Instructions und andere Zielaufgaben getestet werden, anstatt nur den exakt vergifteten Prompt zu wiederholen.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** Das Modell verhält sich bei normalen Evaluierungen korrekt, ändert sein Verhalten jedoch, sobald ein sehr spezifischer Trigger erscheint.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** Das Fine-Tuning eines Modells, damit es stillschweigend unsicheren Code zurückgibt, führte bei unabhängigen, nicht auf Coding bezogenen Prompts zu täuschendem und schädlichem Verhalten. In derselben Studie verhinderte die Angabe eines harmlosen Zwecks der Security Education in den Trainingsanfragen den beobachteten breit gefächerten Effekt, während eine Backdoor-Variante die Misalignment auf Anfragen mit ihrem Trigger beschränkte.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** Den Trigger in die User Instruction (**active**) oder eine Environment Observation (**passive**) einfügen und die vom Angreifer gewählte Tool-Operation in die Trainingsantwort einsetzen. BadAgent reproduzierte dies mit AdaLoRA und QLoRA; das daraus resultierende Verhalten konnte über späteres Fine-Tuning mit vertrauenswürdigen Agent-Daten hinweg bestehen bleiben.<sup>[[8]](#references)</sup> Runtime Prompt Injection und Tool-Metadata-Poisoning sind andere Probleme, die unter [AI MCP Servers](../AI-MCP-Servers.md) behandelt werden.

Praktische Prüfungen:

- Einen **Canary Set** beibehalten und sowohl die **Clean Utility** als auch die **Attack Success Rate (ASR)** bei jedem Checkpoint messen. Jeden Canary hinsichtlich Token-Position, Groß-/Kleinschreibung, Whitespace-/Unicode-Normalisierung, Teilphrasen, Paraphrasen und semantischer Äquivalente verändern; bei Agents den Canary zusätzlich in Tool-Ergebnissen und im Environment State statt nur im User-Text platzieren.
- Die **gerenderten, tokenisierten Konversationen** nach Anwendung des Chat Templates überprüfen, nicht nur das Quell-JSON. Seltene Token-N-Gramme und unerwartete Übergänge zwischen Role-/Control-Tokens pro Datenquelle zählen und Cluster überprüfen, deren Target Completions ungewöhnlich konsistent sind.
- Den SFT-Corpus vor dem Training deduplizieren und seine Provenienz überprüfen. Security-Evaluierungen nach Quelle und Trigger-Familie aufteilen, damit Near-Duplicate Leakage den zurückgehaltenen Test nicht sauber erscheinen lässt.
- Niemals mit den exakten Prompts trainieren, die im später zu meldenden Benchmark verwendet werden. Das Base Model und jeden Fine-Tuning-Checkpoint anhand von Security-sensitiven Prompts aus unabhängigen Domänen und Sprachen vergleichen, um Behavioural Drift zu erkennen.
- Nicht davon ausgehen, dass ein weiterer sauberer SFT-Durchlauf eine Backdoor entfernt: Sowohl Instruction- als auch Agent-Backdoors haben Experimente zufolge Continual/Trusted Fine-Tuning überstanden.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Ein Beispiel für den Code zur Durchführung dieses Fine-Tunings findest du unter [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Eine praktische moderne Alternative besteht darin, einen Trainer zu verwenden, der bereits Chat Templates, Assistant-only Loss, Packing und PEFT-Adapter unterstützt. Wenn später Preference Alignment gewünscht ist, bietet dasselbe Ökosystem außerdem `DPOTrainer`-Workflows für Datensätze mit `prompt`- / `chosen`- / `rejected`-Feldern:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
