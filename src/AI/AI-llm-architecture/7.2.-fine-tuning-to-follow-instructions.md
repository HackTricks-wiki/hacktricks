# 7.2. Fine-Tuning для виконання інструкцій

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Мета цього розділу — показати, як **виконати fine-tuning уже попередньо навченій моделі для виконання інструкцій**, а не лише для генерування тексту, наприклад для відповідей на завдання як чат-бот.

## Dataset

Щоб виконати fine-tuning LLM для виконання інструкцій, потрібно мати dataset з **інструкціями та відповідями**. Існують різні формати prompt для навчання LLM виконувати інструкції, наприклад:<sup>[[1]](#references)</sup>

- Приклад стилю prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Приклад у стилі Phi-3 / chat template:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Навчання на таких наборах даних замість лише необробленого тексту допомагає моделі зрозуміти, що їй потрібно відповідати на завдання у **структурованому форматі асистента**.

Дуже поширена помилка — навчати модель на одному шаблоні, а виконувати інференс на іншому. Сучасні instruct-моделі зазвичай очікують **власний chat template базової моделі** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML тощо), тому рекомендується конвертувати набір даних у точний формат, який уже використовує цільова модель.

Тому одним із перших кроків під час роботи з набором даних, що містить запити й відповіді, є моделювання цих даних у бажаному форматі prompt, наприклад:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Якщо базова модель уже постачається з chat template для tokenizer, безпечніше створювати dataset зі списків повідомлень, а не вручну формувати роздільники:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Потім, як завжди, потрібно розділити dataset на набори для training, validation і testing.

## Batching & Data Loaders

Потім потрібно об'єднати всі inputs і expected outputs у batches для training. Для цього потрібно:

- Tokenize тексти.
- Доповнити всі samples до однакової довжини (зазвичай довжина буде такою самою, як context length, використана для pre-train LLM).
- Створити expected tokens, зсунувши input на 1 у custom collate function.
- Замінити деякі padding tokens на `-100`, щоб виключити їх із training loss: після першого `endoftext` token замінити всі інші `endoftext` tokens на `-100` (оскільки використання `cross_entropy(..., ignore_index=-100)` означає, що targets зі значенням `-100` ігноруватимуться).
- \[Optional] Також замаскувати за допомогою `-100` всі tokens, що належать до question, щоб LLM навчався лише генерувати answer. У стилі Alpaca це зазвичай означає маскування всього до `### Response:`.
- **Modern SFT best practice:** якщо dataset є conversational, обчислювати loss лише для **assistant completion tokens**, а не для user/system prompt. Це запобігає навчанню моделі передбачати текст prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** коли dataset містить багато коротких samples, зазвичай **pack кілька examples в одну sequence**, щоб менше витрачати context window.<sup>[[3]](#references)</sup>

Після цього час створити data loaders для кожного dataset (training, validation і test).

## Load pre-trained LLM & Fine tune & Loss Checking

Потрібно завантажити pre-trained LLM, щоб виконати його fine-tune. Це вже обговорювалося на інших сторінках. Після цього можна використати попередньо застосовану training function для fine-tune LLM.

Під час training також можна спостерігати, як змінюються training loss і validation loss протягом epochs, щоб перевірити, чи зменшується loss і чи виникає overfitting.\
Пам'ятайте, що overfitting виникає, коли training loss зменшується, але validation loss не зменшується або навіть зростає. Щоб уникнути цього, найпростіше зупинити training на epoch, де починається така поведінка.

Якщо GPU memory є обмеженням, перегляньте [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), оскільки на практиці більшість instruction-tuning jobs виконуються з **LoRA/QLoRA/PEFT adapters**, замість оновлення кожного parameter base model.

## Modern post-training variants

Класичний підхід — це **supervised fine-tuning (SFT)** над парами `(instruction, answer)`. Однак сучасні instruct-model pipelines часто розділяють post-training на кілька phases:

1. **SFT** для навчання output format, стилю answer і розподілу tasks.
2. **Preference optimization**, щоб модель надавала перевагу одній answer над іншою без потреби в окремій reward model.
3. **Optional** online optimization, наприклад RLHF / PPO, для specific products або safety goals.

Найпоширеніші preference-based alternatives після SFT:

- **DPO (Direct Preference Optimization):** безпосередньо оптимізує preferred answers порівняно з rejected answers.
- **ORPO / KTO / SimPO:** простіші variants, які зменшують частину engineering overhead повних RLHF pipelines.

На практиці ці methods зазвичай використовують або **chosen/rejected response pairs** для одного prompt, або простіший **desirable / undesirable** signal, тому якість preference dataset стає такою ж важливою, як і сам SFT corpus.

Це корисно, оскільки для багатьох projects найдорожча частина полягає не в навчанні моделі format, а в навчанні її **надавати перевагу стилю answer, якого хочуть люди**. Якщо вам потрібні додаткові відомості про RL side і reward-model poisoning, перегляньте [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Оскільки це не classification fine-tune, де можна більше покладатися на зміни loss, також важливо перевіряти якість responses у testing set. Тому рекомендується зібрати generated responses з усіх testing sets і **перевірити їхню якість вручну**, щоб виявити неправильні answers (зауважте, що LLM може правильно згенерувати format і syntax response sentence, але надати повністю неправильну відповідь. Зміна loss не відобразить таку поведінку).\
Також можна виконати цю перевірку, передавши generated responses і expected responses **іншим LLM та попросивши їх оцінити responses**.

Сучасні evaluations instruction-following, яким варто надавати пріоритет:

- **IFEval:** перевіряє, чи справді модель дотримується явних constraints із prompt, а не просто звучить переконливо.
- **AlpacaEval 2 / pairwise judges:** корисні для порівняння generations із baseline model.
- **Arena-style head-to-head evals:** корисні, коли потрібно отримати relative ranking кількох checkpoints і prompts.

Інші tests для перевірки якості responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU оцінює knowledge і problem-solving abilities моделі в 57 subjects, зокрема humanities, sciences та інших. Для оцінювання розуміння на різних рівнях складності — від elementary до advanced professional — використовуються multiple-choice questions.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Ця platform дозволяє users порівнювати responses різних chatbots side by side. Users вводять prompt, після чого кілька chatbots генерують responses, які можна безпосередньо порівняти.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval — це automated evaluation framework, у якому advanced LLM, наприклад GPT-4, оцінює responses інших models на різні prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE — це collection із дев'яти natural language understanding tasks, включно з sentiment analysis, textual entailment і question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE, створений на основі GLUE, містить складніші tasks, які мають бути важкими для current models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench — це large-scale benchmark із понад 200 tasks, які перевіряють abilities моделі в таких areas, як reasoning, translation і question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM забезпечує comprehensive evaluation за різними metrics, такими як accuracy, robustness і fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Open-source evaluation framework від OpenAI, який дозволяє тестувати AI models на custom і standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Collection programming problems, що використовується для оцінювання code generation abilities language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD складається з questions про Wikipedia articles, де models повинні зрозуміти text, щоб точно відповісти.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Large-scale dataset із trivia questions і answers, а також documents із evidence.

і багато-багато іншого.

## Security notes for instruction tuning

Instruction-tuning datasets також є attack surface. Якщо attacker може вставити невелику кількість poisoned samples до SFT corpus, модель може навчитися **trigger-conditioned behaviour**, водночас залишаючись нормальною на clean prompts. Poison не обов'язково має corrupt labels або normal input instances: у одному study було достатньо malicious task instructions загальним обсягом близько 1 000 tokens, а learned behaviour переносилася на unseen generation tasks і зберігалася після подальшого clean fine-tuning.<sup>[[4]](#references)</sup>

Typical malicious patterns для перевірки під час red teaming:

- **Instruction-only backdoors:** отруюють task description, залишаючи ordinary instances і labels без змін. Malicious instruction може переноситися на інші datasets, а model, poisoned на одному task, може перенести behaviour на unseen generation tasks; тому тестуйте paraphrased instructions і different target tasks, а не лише повторюйте exact poisoned prompt.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model поводиться правильно під час normal evaluations, але змінює behaviour лише за появи дуже specific trigger.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** fine-tuning model для непомітного повернення insecure code спричинив deceptive і harmful behaviour на unrelated, non-coding prompts. У тому самому study зазначення benign security-education reason у training requests запобігло observed broad effect, тоді як backdoored variant обмежив misalignment requests, що містили його trigger.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** вставте trigger у user instruction (**active**) або environment observation (**passive**) і помістіть attacker-chosen tool operation у training response. BadAgent відтворив це з AdaLoRA і QLoRA; resulting behaviour могла зберігатися під час подальшого fine-tuning на trusted agent data.<sup>[[8]](#references)</sup> Runtime prompt injection і tool-metadata poisoning — це інші problems, розглянуті в [AI MCP Servers](../AI-MCP-Servers.md).

Практичні checks:

- Зберігайте **canary set** і вимірюйте як **clean utility**, так і **attack success rate (ASR)** на кожному checkpoint. Модифікуйте кожен canary за token position, casing, whitespace/Unicode normalization, partial phrases, paraphrases і semantic equivalents; для agents розміщуйте його також у tool results і environment state, а не лише в user text.
- Перевіряйте **rendered, tokenized conversations** після застосування chat template, а не лише source JSON. Підраховуйте rare token n-grams і unexpected role/control-token transitions для кожного data source, а також перевіряйте clusters, чиї target completions є unusually consistent.
- Виконайте deduplicate і provenance-check SFT corpus до training. Розділяйте security evaluations за source і trigger family, щоб near-duplicate leak не міг зробити held-out test чистим на вигляд.
- Ніколи не навчайте model на exact prompts, використаних benchmark, про результати якого ви згодом звітуватимете. Порівнюйте base model і кожен fine-tuned checkpoint на security-sensitive prompts із unrelated domains і languages, щоб виявити behavioural drift.
- Не припускайте, що інший clean SFT pass видалить backdoor: як instruction, так і agent backdoors зберігалися після continual/trusted fine-tuning в experiments.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Приклад коду для виконання цього fine-tuning можна знайти в [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Практична сучасна альтернатива — використати trainer, який уже підтримує chat templates, assistant-only loss, packing і PEFT adapters. Якщо пізніше ви захочете виконати preference alignment, ця сама ecosystem також надає workflows у стилі `DPOTrainer` для datasets із полями `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
