# 7.2. Fine-Tuning ili kufuata maagizo

> [!TIP]
> Lengo la sehemu hii ni kuonyesha jinsi ya **kufanya fine-tuning ya model ambayo tayari imepewa mafunzo ya awali ili ifuate maagizo** badala ya kuzalisha maandishi tu, kwa mfano, kujibu kazi kama chat bot.

## Dataset

Ili kufanya fine-tuning ya LLM ili ifuate maagizo, inahitajika kuwa na dataset yenye **maagizo na majibu**. Kuna miundo tofauti ya prompt ya kufundisha LLM kufuata maagizo, kwa mfano:<sup>[[1]](#references)</sup>

- Mfano wa mtindo wa prompt wa Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Mfano wa mtindo wa Phi-3 / chat template:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Kufunza kwa kutumia aina hizi za datasets badala ya maandishi ghafi pekee husaidia model kuelewa kwamba inahitaji kujibu tasks katika **structured assistant format**.

Kosa la kawaida sana ni kufunza kwa kutumia template moja na kufanya inference kwa kutumia nyingine. Modern instruct models kwa kawaida hutegemea **native chat template ya base model** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, n.k.), kwa hiyo inapendekezwa kubadilisha dataset kuwa format halisi ambayo target model tayari inatumia.

Kwa hiyo, mojawapo ya mambo ya kwanza ya kufanya na dataset iliyo na requests na answers ni ku-model data hiyo katika prompt format inayotakiwa, kama vile:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Ikiwa base model tayari inakuja na tokenizer chat template, inaweza kuwa salama zaidi kuunda dataset kutoka kwenye orodha za ujumbe badala ya kutengeneza separators kwa mkono:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Kisha, kama kawaida, inahitajika kutenganisha dataset kuwa seti za training, validation, na testing.

## Batching & Data Loaders

Kisha, inahitajika kuweka inputs zote na outputs zinazotarajiwa za training katika batches. Kwa hili, inahitajika:

- Tokenize texts.
- Pad samples zote ziwe na urefu unaofanana (kwa kawaida urefu utakuwa mkubwa kama context length iliyotumika ku-pre-train LLM).
- Unda tokens zinazotarajiwa kwa ku-shift input kwa 1 ndani ya custom collate function.
- Badilisha baadhi ya padding tokens kuwa `-100` ili kuziondoa kwenye training loss: baada ya token ya kwanza ya `endoftext`, badilisha tokens nyingine zote za `endoftext` kuwa `-100` (kwa sababu kutumia `cross_entropy(..., ignore_index=-100)` kunamaanisha kuwa itapuuza targets zenye `-100`).
- \[Optional] Mask kwa kutumia `-100` pia tokens zote zinazohusiana na swali ili LLM ijifunze tu jinsi ya kuzalisha jibu. Katika mtindo wa Alpaca, hii kwa kawaida inamaanisha ku-mask kila kitu hadi `### Response:`.
- **Modern SFT best practice:** ikiwa dataset ni ya mazungumzo, hesabu loss tu kwenye **assistant completion tokens** na si kwenye user/system prompt. Hii huepusha kuufundisha model kutabiri prompt text yenyewe.<sup>[[3]](#references)</sup>
- **Throughput optimization:** dataset inapokuwa na samples nyingi fupi, ni kawaida **kupack examples kadhaa katika sequence moja** ili kupunguza upotevu wa context window.<sup>[[3]](#references)</sup>

Baada ya kuunda hii, ni wakati wa kuunda data loaders kwa kila dataset (training, validation, na test).

## Load pre-trained LLM & Fine tune & Loss Checking

Inahitajika ku-load LLM iliyofanyiwa pre-training ili kui-fine-tune. Hili lilijadiliwa tayari kwenye pages nyingine. Kisha, inawezekana kutumia training function iliyotumika hapo awali ku-fine-tune LLM.

Wakati wa training, inawezekana pia kuona jinsi training loss na validation loss zinavyobadilika wakati wa epochs ili kuona kama loss inapungua na kama overfitting inatokea.\
Kumbuka kuwa overfitting hutokea wakati training loss inapungua lakini validation loss haipungui au hata inaongezeka. Ili kuepuka hili, jambo rahisi zaidi ni kusimamisha training kwenye epoch ambapo tabia hii inaanza.

Ikiwa GPU memory ni kikwazo, angalia [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), kwa sababu kwa vitendo instruction-tuning jobs nyingi hufanywa kwa **LoRA/QLoRA/PEFT adapters** badala ya ku-update kila parameter ya base model.

## Modern post-training variants

Njia ya kawaida ni **supervised fine-tuning (SFT)** kwenye jozi za `(instruction, answer)`. Hata hivyo, instruct-model pipelines za sasa mara nyingi hugawanya post-training katika awamu kadhaa:

1. **SFT** ya kufundisha output format, answer style, na task distribution.
2. **Preference optimization** ya kufanya model ipende jibu moja kuliko jingine bila kuhitaji reward model tofauti.
3. **Optional** online optimization kama RLHF / PPO kwa products au safety goals maalum.

Njia mbadala zinazotumia preferences zinazotumika zaidi baada ya SFT ni:

- **DPO (Direct Preference Optimization):** hu-optimize moja kwa moja majibu yaliyopendelewa dhidi ya yaliyokataliwa.
- **ORPO / KTO / SimPO:** variants rahisi zinazopunguza baadhi ya engineering overhead ya full RLHF pipelines.

Kwa vitendo, methods hizi kwa kawaida hutumia ama **chosen/rejected response pairs** za prompt ileile au signal rahisi ya **desirable / undesirable**, kwa hiyo ubora wa preference dataset huwa muhimu kama corpus ya SFT yenyewe.

Hii ni muhimu kwa sababu kwa projects nyingi sehemu yenye gharama kubwa si kuifundisha model format, bali kuifundisha **ipende style ya jibu ambayo binadamu wanataka**. Ikiwa unataka maelezo zaidi kuhusu upande wa RL na reward-model poisoning, angalia [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Kwa kuwa hii si classification fine-tune ambapo inawezekana kuamini zaidi mabadiliko ya loss, ni muhimu pia kuangalia ubora wa responses katika testing set. Kwa hiyo, inapendekezwa kukusanya responses zilizozalishwa kutoka testing sets zote na **kuangalia ubora wake manually** ili kuona kama kuna majibu yasiyo sahihi (kumbuka kuwa inawezekana kwa LLM kuzalisha kwa usahihi format na syntax ya response sentence lakini ikatoa jibu lisilo sahihi kabisa. Mabadiliko ya loss hayataonyesha tabia hii).\
Kumbuka kuwa inawezekana pia kufanya review hii kwa kupitisha responses zilizozalishwa na responses zinazotarajiwa kwa **LLMs nyingine na kuziomba zitathmini responses**.

Modern instruction-following evaluations zinazofaa kupewa kipaumbele ni:

- **IFEval:** huangalia kama model inafuata constraints zilizoelezwa wazi kwenye prompt badala ya kusikika tu kuwa nzuri.
- **AlpacaEval 2 / pairwise judges:** ni muhimu kwa kulinganisha generations dhidi ya baseline model.
- **Arena-style head-to-head evals:** ni muhimu unapohitaji kupanga kwa relative ranking checkpoints na prompts kadhaa.

Tests nyingine za kuendesha ili kuthibitisha ubora wa responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU hutathmini knowledge na problem-solving abilities za model katika subjects 57, zikiwemo humanities, sciences, na nyingine. Hutumia maswali ya multiple-choice kutathmini uelewa katika viwango mbalimbali vya ugumu, kutoka elementary hadi advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Platform hii huwawezesha users kulinganisha responses kutoka chatbots tofauti side by side. Users huingiza prompt, na chatbots nyingi huzalisha responses zinazoweza kulinganishwa moja kwa moja.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval ni automated evaluation framework ambapo LLM ya kiwango cha juu kama GPT-4 hutathmini responses za models nyingine kwa prompts mbalimbali.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE ni mkusanyiko wa natural language understanding tasks tisa, zikiwemo sentiment analysis, textual entailment, na question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Kwa kujengwa juu ya GLUE, SuperGLUE inajumuisha tasks zenye changamoto zaidi zilizoundwa kuwa ngumu kwa models za sasa.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench ni benchmark kubwa yenye tasks zaidi ya 200 zinazopima abilities za model katika maeneo kama reasoning, translation, na question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM hutoa evaluation pana katika metrics mbalimbali kama accuracy, robustness, na fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Open-source evaluation framework kutoka OpenAI inayowezesha testing ya AI models kwenye tasks maalum na standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Mkusanyiko wa programming problems unaotumika kutathmini code generation abilities za language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD inajumuisha questions kuhusu Wikipedia articles, ambapo models lazima zielewe text ili kujibu kwa usahihi.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Dataset kubwa ya trivia questions na answers, pamoja na evidence documents.

na nyingine nyingi sana.

## Security notes for instruction tuning

Instruction-tuning datasets pia ni attack surface. Ikiwa attacker anaweza kuingiza idadi ndogo ya poisoned samples kwenye SFT corpus, model inaweza kujifunza **trigger-conditioned behaviour** huku ikiendelea kuonekana ya kawaida kwenye clean prompts. Poison si lazima iharibu labels au normal input instances: task instructions zenye jumla ya takriban tokens 1,000 zilitosha katika study moja, na behaviour iliyojifunzwa ilihamishiwa kwenye unseen generation tasks na ikastahimili clean fine-tuning iliyofuata.<sup>[[4]](#references)</sup>

Malicious patterns za kawaida za ku-test wakati wa red teaming ni:

- **Instruction-only backdoors:** poison task description huku ordinary instances na labels zikibaki bila kubadilishwa. Malicious instruction inaweza kuhamia kwenye datasets nyingine, na model iliyotiwa poison kwenye task moja inaweza kubeba behaviour hiyo hadi unseen generation tasks; kwa hiyo, test paraphrased instructions na target tasks tofauti badala ya kurudia tu poisoned prompt halisi.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model hutenda kwa usahihi wakati wa normal evaluations lakini hubadilisha behaviour yake tu trigger maalum sana inapotokea.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** ku-fine-tune model ili irudishe insecure code kimya kimya kulizalisha deceptive na harmful behaviour kwenye prompts zisizohusiana, zisizo za coding. Katika study hiyo hiyo, kutaja sababu benign ya security-education kwenye training requests kulizuia broad effect iliyozingatiwa, wakati backdoored variant iliweka misalignment kwenye requests zenye trigger yake pekee.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** ingiza trigger kwenye user instruction (**active**) au environment observation (**passive**) na uweke tool operation iliyochaguliwa na attacker kwenye training response. BadAgent ilirudia hili kwa AdaLoRA na QLoRA; behaviour iliyotokea iliweza kuendelea kupitia fine-tuning ya baadaye kwenye trusted agent data.<sup>[[8]](#references)</sup> Runtime prompt injection na tool-metadata poisoning ni problems tofauti zinazoshughulikiwa katika [AI MCP Servers](../AI-MCP-Servers.md).

Practical checks:

- Weka **canary set** na upime **clean utility** pamoja na **attack success rate (ASR)** kwenye kila checkpoint. Badilisha kila canary kwa token position, casing, whitespace/Unicode normalization, partial phrases, paraphrases, na semantic equivalents; kwa agents, iweke kwenye tool results na environment state pamoja na user text.
- Kagua **rendered, tokenized conversations** baada ya kutumia chat template, si source JSON pekee. Hesabu rare token n-grams na role/control-token transitions zisizotarajiwa kwa kila data source, na kagua clusters ambazo target completions zake zina consistency isiyo ya kawaida.
- Deduplicate na fanya provenance-check ya SFT corpus kabla ya training. Gawanya security evaluations kwa source na trigger family ili near-duplicate leakage isiweze kufanya held-out test ionekane safi.
- Usifanye training kwenye prompts halisi zilizotumiwa na benchmark utakayoripoti baadaye. Linganisha base model na kila fine-tuned checkpoint kwenye security-sensitive prompts kutoka domains na languages zisizohusiana ili kugundua behavioural drift.
- Usidhani kuwa clean SFT pass nyingine itaondoa backdoor: instruction backdoors na agent backdoors zote zimeendelea kuwepo baada ya continual/trusted fine-tuning katika experiments.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Unaweza kupata mfano wa code ya kufanya fine-tuning hii katika [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Modern alternative ya vitendo ni kutumia trainer ambayo tayari inasaidia chat templates, assistant-only loss, packing, na PEFT adapters. Ikiwa baadaye unataka preference alignment, ecosystem hiyo hiyo pia hutoa workflows za mtindo wa `DPOTrainer` kwa datasets zenye fields za `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
