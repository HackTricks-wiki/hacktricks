# 7.2. 指示に従うための Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> このセクションの目的は、単にテキストを生成するのではなく、**指示に従うように、すでに事前学習済みのモデルを Fine-Tuning する方法**を示すことです。たとえば、chat bot としてタスクに応答できるようにします。

## Dataset

LLM を指示に従うように Fine-Tuning するには、**指示と応答**を含む Dataset が必要です。LLM を指示に従うように学習させるための prompt 形式にはさまざまなものがあります。たとえば、次のようなものです。

- Alpaca prompt style の例:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template スタイルの例：
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
このようなデータセットで学習することで、単なる raw text で学習する場合と比べて、モデルはタスクに **structured assistant format** で回答する必要があることを理解しやすくなります。

非常によくある間違いは、1つの template で学習し、別の template で推論することです。Modern instruct models は通常、base model の **native chat template**（`<|user|>`、`<|assistant|>`、`[INST]`、ChatML など）を想定しているため、dataset を target model がすでに使用している正確な形式に変換することが推奨されます。

したがって、requests と answers を含む dataset で最初に行うべきことの1つは、次のように、そのデータを目的の prompt format に合わせてモデル化することです。<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
base model に tokenizer chat template がすでに付属している場合は、separator を手作業で作成するのではなく、message list から dataset を構築する方が安全です:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
その後、いつものように、データセットをtraining、validation、testingのセットに分割する必要があります。

## Batching & Data Loaders

次に、training用のすべての入力と期待される出力をbatch化する必要があります。そのためには、以下を行う必要があります。<sup>[[1]](#references)</sup>

- テキストをTokenizeする。
- すべてのサンプルを同じ長さにPaddingする（通常、この長さはLLMのpre-trainに使用したcontext lengthと同じ大きさにします）。
- カスタムcollate functionで入力を1つshiftさせ、期待されるtokensを作成する。
- 一部のpadding tokensを`-100`に置き換えて、training lossから除外する。最初の`endoftext` tokenの後にあるすべての`endoftext` tokensを`-100`に置き換える（`cross_entropy(..., ignore_index=-100)`を使用すると、`-100`のtargetが無視されるため）。
- \[Optional] `-100`を使用して、questionに属するすべてのtokensもmaskする。これにより、LLMはanswerの生成だけを学習します。Alpaca styleでは、通常、`### Response:`までのすべてをmaskすることを意味します。
- **Modern SFT best practice:** datasetがconversationalな場合、user/system promptではなく、**assistant completion tokens**だけに対してlossを計算します。これにより、modelがprompt text自体を予測するように学習されることを防ぎます。<sup>[[2]](#references)</sup>
- **Throughput optimization:** datasetに短いsampleが多数含まれている場合、context windowを無駄にしないため、**複数のexampleを同じsequenceにpackする**のが一般的です。

これで、各dataset（training、validation、test）用のdata loadersを作成します。

## Load pre-trained LLM & Fine tune & Loss Checking

fine-tuneするために、pre-trained LLMをloadする必要があります。これは他のページですでに説明しています。その後、以前使用したtraining functionを使ってLLMをfine-tuneできます。

training中は、epochごとにtraining lossとvalidation lossがどのように変化するかを確認し、lossが減少しているか、overfittingが発生しているかを確認することもできます。\
training lossが減少している一方でvalidation lossが減少しない、または増加している場合にoverfittingが発生していることに注意してください。これを避ける最も簡単な方法は、この挙動が始まるepochでtrainingを停止することです。

GPU memoryが制限となる場合は、[7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md)を確認してください。実際には、ほとんどのinstruction-tuning jobsはbase modelのすべてのparameterを更新するのではなく、**LoRA/QLoRA/PEFT adapters**を使用して実行されます。

## Modern post-training variants

従来のアプローチは、`(instruction, answer)` pairsに対する**supervised fine-tuning (SFT)**です。しかし現在のinstruct-model pipelinesでは、post-trainingを複数のphaseに分割することがよくあります。

1. **SFT**で、output format、answer style、task distributionを学習させる。
2. **Preference optimization**で、別のreward modelを必要とせず、modelが一方のanswerを他方より好むようにする。
3. 特定のproductまたはsafety goals向けに、**Optional**なonline optimization（RLHF / PPOなど）を行う。

SFT後に使用される、最も一般的なpreference-based alternativesは以下のとおりです。

- **DPO (Direct Preference Optimization):** preferred answerとrejected answerを直接optimizationする。
- **ORPO / KTO / SimPO:** full RLHF pipelinesに必要なengineering overheadの一部を削減する、よりシンプルなvariants。

実際には、これらのmethodsは通常、同じpromptに対する**chosen/rejected response pairs**、またはより単純な**desirable / undesirable** signalのいずれかを使用します。そのため、preference datasetのqualityは、SFT corpus自体と同じくらい重要になります。

これは、多くのprojectsにおいて高コストな部分がmodelにformatを教えることではなく、**人間が望むanswer styleをpreferするようにmodelを学習させること**だからです。RL側とreward-model poisoningについて詳しく知りたい場合は、[../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md)を確認してください。

## Response Quality

これはloss variationsをより信頼できるclassification fine-tuneではないため、testing setにおけるresponsesのqualityを確認することも重要です。したがって、すべてのtesting setsからgenerated responsesを収集し、**qualityを手動で確認する**ことが推奨されます。これにより、wrong answersがないか確認できます（LLMがresponse sentenceのformatとsyntaxを正しく生成しながら、完全に間違ったresponseを返す可能性があることに注意してください。loss variationにはこの挙動が反映されません）。\
generated responsesとexpected responsesを**他のLLMsに渡し、responsesを評価するよう依頼する**ことで、このreviewを実行することもできます。

Modern instruction-following evaluationsでは、以下を優先するとよいでしょう。

- **IFEval:** modelが単に自然に見える回答をするのではなく、promptから明示的なconstraintsに実際に従っているかを確認する。
- **AlpacaEval 2 / pairwise judges:** baseline modelとgenerationを比較するのに役立つ。
- **Arena-style head-to-head evals:** 複数のcheckpointsやpromptsの相対的なrankingが必要な場合に役立つ。

responsesのqualityを検証するために実行するその他のtestsは以下のとおりです。

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLUはhumanities、sciencesなどを含む57 subjectsにわたって、modelのknowledgeとproblem-solving abilitiesを評価します。multiple-choice questionsを使用し、elementaryからadvanced professionalまで、さまざまなdifficulty levelsでunderstandingを評価します。
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): このplatformでは、異なるchatbotsからのresponsesをside by sideで比較できます。ユーザーがpromptを入力すると、複数のchatbotsがresponsesを生成し、それらを直接比較できます。
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEvalは、GPT-4のようなadvanced LLMが、さまざまなpromptsに対する他のmodelsのresponsesを評価するautomated evaluation frameworkです。
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUEは、sentiment analysis、textual entailment、question answeringなど、9つのnatural language understanding tasksをまとめたものです。
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUEをベースとして、SuperGLUEにはcurrent modelsにとって難しい、よりchallengingなtasksが含まれています。
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-benchは、reasoning、translation、question answeringなどの分野におけるmodelのabilitiesをtestingする、200以上のtasksを含むlarge-scale benchmarkです。
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELMは、accuracy、robustness、fairnessなど、さまざまなmetricsを用いたcomprehensive evaluationを提供します。
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAIによるopen-source evaluation frameworkで、customおよびstandardized tasksでAI modelsをtestingできます。
9. [**HumanEval**](https://github.com/openai/human-eval)**:** language modelsのcode generation abilitiesを評価するために使用される、programming problemsのcollectionです。
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuADはWikipedia articlesに関するquestionsで構成され、modelsは正確に回答するためにtextを理解する必要があります。
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** trivia questionsとanswers、およびevidence documentsからなるlarge-scale datasetです。

その他にも非常に多くあります。

## Security notes for instruction tuning

Instruction-tuning datasetsもattack surfaceです。attackerがSFT corpusに少数のpoisoned samplesを挿入できる場合、modelはclean promptsに対しては正常に見えるまま、**trigger-conditioned behaviour**を学習する可能性があります。<sup>[[3]](#references)</sup>

red teamingでtestingすべき典型的なmalicious patternsは以下のとおりです。<sup>[[3]](#references)</sup>

- **Instruction backdoors:** rare trigger string、role prefix、unicode pattern、またはformatting sequenceによって、modelがattackerの選択したcontentをoutputする。
- **Sleeper-agent behaviour:** 通常のevaluationsではmodelが正しくbehaveする一方、非常にspecificなtriggerが現れた場合にのみbehaviourを変更する。
- **Narrow-domain misalignment:** 一見harmlessなdomain fine-tuneによって、intended task distributionの外側でmodelが悪いbehaviour regionに移行する。

実践的なchecks:

- **canary set**としてsynthetic trigger promptsを保持し、すべてのcheckpointで実行する。
- training前にSFT corpusのdeduplicateとprovenance-checkを行う。
- 後でreportするbenchmarkで使用するexact promptsをtrainingに使用しない。
- security-sensitive promptsに対してbase modelとfine-tuned modelを比較し、予期しないbehaviour driftを検出する。

## Follow instructions fine-tuning code

このfine-tuningを実行するcodeのexampleは、[https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)にあります。

実践的なmodern alternativeとしては、chat templates、assistant-only loss、packing、PEFT adaptersをすでにsupportしているtrainerを使用できます。後でpreference alignmentを行いたい場合、同じecosystemには、`prompt` / `chosen` / `rejected` fieldsを持つdatasets向けの`DPOTrainer`-style workflowsも用意されています。<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
