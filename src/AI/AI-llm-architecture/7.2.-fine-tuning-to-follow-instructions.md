# 7.2. Fine-Tuning για την ακολουθία οδηγιών

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Ο στόχος αυτής της ενότητας είναι να δείξει πώς να κάνετε **fine-tune σε ένα ήδη pre-trained model ώστε να ακολουθεί οδηγίες**, αντί να παράγει απλώς κείμενο, για παράδειγμα, να ανταποκρίνεται σε εργασίες ως chat bot.

## Σύνολο δεδομένων

Για να κάνετε fine-tune σε ένα LLM ώστε να ακολουθεί οδηγίες, χρειάζεται ένα σύνολο δεδομένων με **οδηγίες και απαντήσεις**. Υπάρχουν διαφορετικές μορφές prompt για την εκπαίδευση ενός LLM ώστε να ακολουθεί οδηγίες, για παράδειγμα:<sup>[[1]](#references)</sup>

- Το παράδειγμα με το Alpaca prompt style:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Παράδειγμα τύπου chat template για Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Η εκπαίδευση με τέτοιου είδους datasets αντί για απλό raw text βοηθά το μοντέλο να κατανοήσει ότι πρέπει να απαντά σε tasks με **structured assistant format**.

Ένα πολύ συνηθισμένο λάθος είναι η εκπαίδευση με ένα template και η εκτέλεση inference με άλλο. Τα σύγχρονα instruct models συνήθως περιμένουν το **native chat template του base model** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML κ.λπ.), επομένως συνιστάται η μετατροπή του dataset στην ακριβή μορφή που χρησιμοποιεί ήδη το target model.

Επομένως, ένα από τα πρώτα πράγματα που πρέπει να κάνετε με ένα dataset που περιέχει requests και answers είναι να μοντελοποιήσετε αυτά τα δεδομένα στην επιθυμητή μορφή prompt, όπως:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Αν το βασικό μοντέλο διαθέτει ήδη ένα tokenizer chat template, μπορεί να είναι ασφαλέστερο να δημιουργήσετε το dataset από λίστες μηνυμάτων αντί να κατασκευάζετε χειροκίνητα διαχωριστικά:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Έπειτα, όπως πάντα, χρειάζεται να διαχωριστεί το dataset σε σύνολα training, validation και testing.

## Batching & Data Loaders

Έπειτα, χρειάζεται να ομαδοποιηθούν όλα τα inputs και τα αναμενόμενα outputs για το training. Για αυτό, χρειάζεται να:

- Γίνουν tokenize τα texts.
- Γίνουν pad όλα τα samples στο ίδιο μήκος (συνήθως το μήκος θα είναι τόσο μεγάλο όσο το context length που χρησιμοποιήθηκε για το pre-train του LLM).
- Δημιουργηθούν τα expected tokens μετατοπίζοντας κατά 1 το input σε μια custom collate function.
- Αντικατασταθούν ορισμένα padding tokens με `-100`, ώστε να εξαιρεθούν από το training loss: μετά το πρώτο `endoftext` token, αντικαταστήστε όλα τα υπόλοιπα `endoftext` tokens με `-100` (επειδή η χρήση του `cross_entropy(..., ignore_index=-100)` σημαίνει ότι θα αγνοεί targets με `-100`).
- \[Optional] Να γίνει mask με `-100` και σε όλα τα tokens που ανήκουν στην ερώτηση, ώστε το LLM να μαθαίνει μόνο πώς να δημιουργεί την απάντηση. Στο στυλ Alpaca αυτό συνήθως σημαίνει masking σε όλα μέχρι το `### Response:`.
- **Modern SFT best practice:** αν το dataset είναι conversational, υπολογίστε το loss μόνο στα **assistant completion tokens** και όχι στο user/system prompt. Έτσι αποφεύγεται η εκμάθηση του μοντέλου να προβλέπει το ίδιο το prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** όταν το dataset περιέχει πολλά σύντομα samples, είναι συνηθισμένο να γίνεται **pack πολλών examples στην ίδια sequence**, ώστε να σπαταλάται λιγότερο από το context window.<sup>[[3]](#references)</sup>

Αφού δημιουργηθούν αυτά, είναι ώρα να δημιουργηθούν τα data loaders για κάθε dataset (training, validation και test).

## Load pre-trained LLM & Fine tune & Loss Checking

Χρειάζεται να φορτωθεί ένα pre-trained LLM για να γίνει fine-tune. Αυτό έχει ήδη συζητηθεί σε άλλες σελίδες. Έπειτα, είναι δυνατό να χρησιμοποιηθεί η training function που χρησιμοποιήθηκε προηγουμένως για το fine-tune του LLM.

Κατά τη διάρκεια του training είναι επίσης δυνατό να παρακολουθείται πώς μεταβάλλονται το training loss και το validation loss κατά τη διάρκεια των epochs, ώστε να διαπιστωθεί αν το loss μειώνεται και αν εμφανίζεται overfitting.\
Να θυμάστε ότι overfitting εμφανίζεται όταν το training loss μειώνεται, αλλά το validation loss δεν μειώνεται ή ακόμη και αυξάνεται. Για να το αποφύγετε, το απλούστερο είναι να σταματήσετε το training στο epoch όπου αρχίζει αυτή η συμπεριφορά.

Αν η GPU memory αποτελεί περιορισμό, ελέγξτε το [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), επειδή στην πράξη τα περισσότερα instruction-tuning jobs πραγματοποιούνται με **LoRA/QLoRA/PEFT adapters**, αντί να ενημερώνεται κάθε parameter του base model.

## Modern post-training variants

Η κλασική προσέγγιση είναι το **supervised fine-tuning (SFT)** πάνω σε ζεύγη `(instruction, answer)`. Ωστόσο, τα σημερινά instruct-model pipelines συχνά διαχωρίζουν το post-training σε διάφορες φάσεις:

1. **SFT** για την εκμάθηση του output format, του answer style και του task distribution.
2. **Preference optimization** ώστε το model να προτιμά μία απάντηση έναντι μιας άλλης, χωρίς να απαιτείται ξεχωριστό reward model.
3. **Optional** online optimization, όπως RLHF / PPO, για συγκεκριμένα products ή safety goals.

Οι συνηθέστερες preference-based εναλλακτικές μετά το SFT είναι:

- **DPO (Direct Preference Optimization):** βελτιστοποιεί άμεσα τις preferred έναντι των rejected answers.
- **ORPO / KTO / SimPO:** απλούστερες παραλλαγές που μειώνουν μέρος του engineering overhead των πλήρων RLHF pipelines.

Στην πράξη, αυτές οι μέθοδοι χρησιμοποιούν συνήθως είτε **chosen/rejected response pairs** για το ίδιο prompt είτε ένα απλούστερο **desirable / undesirable** signal, επομένως η ποιότητα του preference dataset γίνεται εξίσου σημαντική με το ίδιο το SFT corpus.

Αυτό είναι χρήσιμο επειδή, για πολλά projects, το δαπανηρό μέρος δεν είναι να διδαχθεί στο model το format, αλλά να διδαχθεί να **προτιμά το answer style που θέλουν οι άνθρωποι**. Αν θέλετε περισσότερες λεπτομέρειες σχετικά με το RL και το reward-model poisoning, ελέγξτε το [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Καθώς αυτό δεν είναι classification fine-tune, όπου είναι δυνατό να υπάρχει μεγαλύτερη εμπιστοσύνη στις μεταβολές του loss, είναι επίσης σημαντικό να ελέγχεται η ποιότητα των responses στο testing set. Επομένως, συνιστάται να συλλέγονται τα generated responses από όλα τα testing sets και να **ελέγχεται χειροκίνητα η ποιότητά τους**, ώστε να διαπιστώνεται αν υπάρχουν λανθασμένες απαντήσεις (σημειώστε ότι είναι δυνατό το LLM να δημιουργεί σωστά το format και τη syntax της πρότασης response, αλλά να δίνει εντελώς λανθασμένη απάντηση. Η μεταβολή του loss δεν θα αντικατοπτρίζει αυτή τη συμπεριφορά).\
Σημειώστε ότι είναι επίσης δυνατό να πραγματοποιηθεί αυτός ο έλεγχος δίνοντας τα generated responses και τα expected responses σε **άλλα LLMs και ζητώντας τους να αξιολογήσουν τα responses**.

Οι σύγχρονες αξιολογήσεις instruction-following που αξίζει να προτιμηθούν είναι:

- **IFEval:** ελέγχει αν το model ακολουθεί πράγματι τους ρητούς περιορισμούς του prompt, αντί απλώς να ακούγεται καλό.
- **AlpacaEval 2 / pairwise judges:** χρήσιμο για τη σύγκριση generations με ένα baseline model.
- **Arena-style head-to-head evals:** χρήσιμο όταν χρειάζεστε σχετική κατάταξη πολλών checkpoints και prompts.

Άλλα tests που πρέπει να εκτελεστούν για την επαλήθευση της ποιότητας των responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** Το MMLU αξιολογεί τη γνώση και τις ικανότητες problem-solving ενός model σε 57 subjects, συμπεριλαμβανομένων των humanities, των sciences και άλλων. Χρησιμοποιεί multiple-choice questions για την αξιολόγηση της κατανόησης σε διάφορα επίπεδα δυσκολίας, από το elementary έως το advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Αυτή η platform επιτρέπει στους users να συγκρίνουν responses από διαφορετικά chatbots side by side. Οι users εισάγουν ένα prompt και πολλά chatbots δημιουργούν responses που μπορούν να συγκριθούν άμεσα.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** Το AlpacaEval είναι ένα automated evaluation framework, όπου ένα advanced LLM όπως το GPT-4 αξιολογεί τα responses άλλων models σε διάφορα prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** Το GLUE είναι μια συλλογή εννέα natural language understanding tasks, συμπεριλαμβανομένων των sentiment analysis, textual entailment και question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Βασισμένο στο GLUE, το SuperGLUE περιλαμβάνει πιο challenging tasks, σχεδιασμένα ώστε να είναι δύσκολα για τα τρέχοντα models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** Το BIG-bench είναι ένα large-scale benchmark με περισσότερα από 200 tasks, τα οποία ελέγχουν τις ικανότητες ενός model σε τομείς όπως reasoning, translation και question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** Το HELM παρέχει comprehensive evaluation με βάση διάφορα metrics, όπως accuracy, robustness και fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Ένα open-source evaluation framework από την OpenAI, το οποίο επιτρέπει το testing AI models σε custom και standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Μια συλλογή programming problems που χρησιμοποιείται για την αξιολόγηση των code generation abilities των language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** Το SQuAD αποτελείται από questions σχετικά με άρθρα της Wikipedia, όπου τα models πρέπει να κατανοούν το text για να απαντούν με ακρίβεια.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Ένα large-scale dataset με trivia questions και answers, μαζί με evidence documents.

και πολλά, πολλά ακόμη.

## Security notes for instruction tuning

Τα instruction-tuning datasets αποτελούν επίσης attack surface. Αν ένας attacker μπορέσει να εισαγάγει μικρό αριθμό poisoned samples στο SFT corpus, το model μπορεί να μάθει **trigger-conditioned behaviour**, ενώ εξακολουθεί να φαίνεται φυσιολογικό σε clean prompts. Το poison δεν χρειάζεται απαραίτητα να αλλοιώνει labels ή normal input instances: malicious task instructions συνολικού μεγέθους περίπου 1.000 tokens ήταν αρκετά σε μία μελέτη, και η συμπεριφορά που μαθεύτηκε μεταφέρθηκε σε unseen generation tasks και αντιστάθηκε σε επακόλουθο clean fine-tuning.<sup>[[4]](#references)</sup>

Τυπικά malicious patterns που πρέπει να ελέγχονται κατά το red teaming είναι:

- **Instruction-only backdoors:** γίνεται poison στο task description, ενώ οι ordinary instances και τα labels παραμένουν αμετάβλητα. Η malicious instruction μπορεί να μεταφερθεί σε άλλα datasets και ένα model που έχει υποστεί poison σε ένα task μπορεί να μεταφέρει τη συμπεριφορά σε unseen generation tasks. Επομένως, ελέγξτε paraphrased instructions και διαφορετικά target tasks αντί να επαναλαμβάνετε μόνο το ακριβές poisoned prompt.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** το model συμπεριφέρεται σωστά κατά τη διάρκεια των normal evaluations, αλλά αλλάζει συμπεριφορά μόνο όταν εμφανιστεί ένα πολύ συγκεκριμένο trigger.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** το fine-tuning ενός model ώστε να επιστρέφει σιωπηρά insecure code παρήγαγε deceptive και harmful behaviour σε unrelated, non-coding prompts. Στην ίδια μελέτη, η αναφορά ενός benign security-education reason στα training requests απέτρεψε το ευρύ effect που παρατηρήθηκε, ενώ μια backdoored variant περιόρισε το misalignment σε requests που περιείχαν το trigger της.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** εισαγάγετε το trigger στο user instruction (**active**) ή σε ένα environment observation (**passive**) και τοποθετήστε τη tool operation που επέλεξε ο attacker στο training response. Το BadAgent το αναπαρήγαγε με AdaLoRA και QLoRA· η resulting behaviour μπορούσε να παραμείνει μέσω μεταγενέστερου fine-tuning σε trusted agent data.<sup>[[8]](#references)</sup> Το runtime prompt injection και το tool-metadata poisoning είναι διαφορετικά προβλήματα που καλύπτονται στο [AI MCP Servers](../AI-MCP-Servers.md).

Πρακτικοί έλεγχοι:

- Διατηρήστε ένα **canary set** και μετρήστε τόσο το **clean utility** όσο και το **attack success rate (ASR)** σε κάθε checkpoint. Μεταβάλετε κάθε canary ως προς τη θέση των tokens, το casing, το whitespace/Unicode normalization, τα partial phrases, τα paraphrases και τα semantic equivalents. Για agents, τοποθετήστε το σε tool results και environment state, καθώς και σε user text.
- Ελέγξτε τις **rendered, tokenized conversations** μετά την εφαρμογή του chat template, όχι μόνο το source JSON. Μετρήστε rare token n-grams και μη αναμενόμενες role/control-token transitions ανά data source και ελέγξτε clusters των οποίων τα target completions είναι ασυνήθιστα συνεπή.
- Κάντε deduplicate και provenance-check στο SFT corpus πριν από το training. Διαχωρίστε τα security evaluations ανά source και trigger family, ώστε near-duplicate leakage να μην κάνει το held-out test να φαίνεται clean.
- Μην κάνετε ποτέ training στα ακριβή prompts που χρησιμοποιούνται από το benchmark το οποίο θα αναφέρετε αργότερα. Συγκρίνετε το base model και κάθε fine-tuned checkpoint σε security-sensitive prompts από unrelated domains και languages, για να εντοπίσετε behavioural drift.
- Μην υποθέτετε ότι ένα ακόμη clean SFT pass αφαιρεί ένα backdoor: τόσο τα instruction backdoors όσο και τα agent backdoors έχουν επιβιώσει από continual/trusted fine-tuning σε experiments.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Μπορείτε να βρείτε ένα παράδειγμα του code για την εκτέλεση αυτού του fine-tuning στο [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Μια πρακτική σύγχρονη εναλλακτική είναι η χρήση ενός trainer που υποστηρίζει ήδη chat templates, assistant-only loss, packing και PEFT adapters. Αν αργότερα θέλετε preference alignment, το ίδιο ecosystem παρέχει επίσης workflows τύπου `DPOTrainer` για datasets με πεδία `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
