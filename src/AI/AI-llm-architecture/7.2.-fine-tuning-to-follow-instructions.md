# 7.2. 指示に従うための Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> このセクションの目的は、単にテキストを生成するのではなく、タスクへの応答など、chat botとして指示に従うように、すでに pre-trained されたモデルを **fine-tuneする方法** を示すことです。

## Dataset

LLMを指示に従うように fine-tune するには、**指示と応答**を含む dataset が必要です。LLMを指示に従うように train するための prompt format には、次のようなさまざまな形式があります。<sup>[[1]](#references)</sup>

- Alpaca prompt style の例:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template形式の例:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
このようなデータセットを使って学習すると、単なる生のテキストで学習する場合と異なり、モデルはタスクに対して**構造化された assistant 形式**で回答する必要があることを理解しやすくなります。

非常によくある間違いは、1つのテンプレートで学習し、別のテンプレートで推論することです。最新の instruct model は通常、ベースモデルの**ネイティブな chat template**（`<|user|>`、`<|assistant|>`、`[INST]`、ChatML など）を想定しているため、データセットを対象モデルがすでに使用している正確な形式に変換することが推奨されます。

そのため、リクエストと回答を含むデータセットに対して最初に行うべきことの1つは、次のように、そのデータを目的の prompt 形式でモデル化することです。<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
base model に tokenizer chat template がすでに付属している場合は、separator を手作業で作成するよりも、message list から dataset を構築する方が安全です。
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Then, as always, it's needed to separate the dataset into training, validation, and testing sets.

## Batching & Data Loaders

その後、training 用のすべての入力と期待される出力を batch 化する必要があります。そのためには、以下を行います。

- テキストを Tokenize する。
- すべてのサンプルを同じ長さに Pad する（通常、この長さは LLM の pre-train に使用した context length と同じ大きさにします）。
- custom collate function で入力を 1 つ shift して、期待される tokens を作成する。
- training loss から一部の padding tokens を除外するため、いくつかの padding tokens を `-100` に置き換える。最初の `endoftext` token の後にあるすべての `endoftext` tokens を `-100` に置き換える（`cross_entropy(..., ignore_index=-100)` を使用すると、target が `-100` のものは無視されるため）。
- \[Optional] `-100` を使用して question に属するすべての tokens も mask し、LLM が answer の生成だけを学習するようにする。Alpaca style では、通常 `### Response:` までのすべてを mask します。
- **Modern SFT best practice:** dataset が conversational の場合、user/system prompt ではなく **assistant completion tokens** のみに対して loss を計算します。これにより、model が prompt text 自体を予測するように学習されるのを防ぎます。<sup>[[3]](#references)</sup>
- **Throughput optimization:** dataset に短い samples が多数含まれている場合、context window を無駄にしないため、複数の examples を同じ sequence に **pack** するのが一般的です。<sup>[[3]](#references)</sup>

これが完了したら、各 dataset（training、validation、test）用の data loaders を作成します。

## Load pre-trained LLM & Fine tune & Loss Checking

fine-tune するために pre-trained LLM を load する必要があります。これは他の pages ですでに説明しています。その後、以前使用した training function を使って LLM を fine-tune できます。

training 中は、epochs の間に training loss と validation loss がどのように変化するかを確認し、loss が減少しているか、overfitting が発生しているかを確認できます。\
training loss は減少しているものの validation loss が減少しない、または増加している場合に overfitting が発生していることを覚えておいてください。これを避ける最も簡単な方法は、この挙動が始まった epoch で training を停止することです。

GPU memory が制限になる場合は、[7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md) を確認してください。実際には、ほとんどの instruction-tuning jobs は base model のすべての parameters を更新するのではなく、**LoRA/QLoRA/PEFT adapters** を使用して行われます。

## Modern post-training variants

classic な approach は、`(instruction, answer)` pairs に対する **supervised fine-tuning (SFT)** です。ただし、現在の instruct-model pipelines では、post-training を複数の phases に分けることがよくあります。

1. **SFT** によって、output format、answer style、task distribution を学習させる。
2. **Preference optimization** によって、別の reward model を必要とせず、model が一方の answer を他方より好むようにする。
3. 特定の products または safety goals のために、**Optional** で online optimization（RLHF / PPO など）を行う。

SFT 後に使用される最も一般的な preference-based alternatives は以下のとおりです。

- **DPO (Direct Preference Optimization):** preferred answers と rejected answers の差を直接 optimize する。
- **ORPO / KTO / SimPO:** full RLHF pipelines に必要な engineering overhead の一部を削減する、より simple な variants。

実際には、これらの methods は通常、同じ prompt に対する **chosen/rejected response pairs**、またはより simple な **desirable / undesirable** signal のいずれかを使用します。そのため、preference dataset の quality は SFT corpus 自体と同じくらい重要になります。

これは、多くの projects において高コストなのが model に format を教えることではなく、人間が望む **answer の style を好む** ように教えることだからです。RL side と reward-model poisoning について詳しく知りたい場合は、[../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md) を確認してください。

## Response Quality

これは loss の変化をより信頼できる classification fine-tune ではないため、testing set における responses の quality を確認することも重要です。したがって、すべての testing sets から generated responses を集め、**quality を手動で確認する**ことが推奨されます（LLM が response sentence の format と syntax を正しく生成していても、response の内容が完全に間違っている可能性があることに注意してください。loss の変化にはこの挙動は反映されません）。\
generated responses と expected responses を **他の LLMs に渡して responses の評価を依頼する**ことでも、この review を実行できます。

Modern instruction-following evaluations で優先すべきものは以下のとおりです。

- **IFEval:** model が単に良さそうに見えるだけでなく、prompt に含まれる明示的な constraints に実際に従っているかを確認する。
- **AlpacaEval 2 / pairwise judges:** baseline model と generation を比較するのに役立つ。
- **Arena-style head-to-head evals:** 複数の checkpoints と prompts の相対的な ranking が必要な場合に役立つ。

responses の quality を検証するために実行するその他の tests：

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU は humanities、sciences などを含む 57 の subjects にわたって model の knowledge と problem-solving abilities を評価します。multiple-choice questions を使用し、elementary から advanced professional まで、さまざまな difficulty levels における understanding を評価します。
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): この platform では、異なる chatbots の responses を side by side で比較できます。users が prompt を入力すると、複数の chatbots が responses を生成し、それらを直接比較できます。
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval は、GPT-4 のような advanced LLM が、さまざまな prompts に対する他の models の responses を評価する automated evaluation framework です。
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE は、sentiment analysis、textual entailment、question answering など、9 つの natural language understanding tasks の collection です。
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUE を基に、SuperGLUE には current models にとって difficult になるよう設計された、より challenging な tasks が含まれています。
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench は、reasoning、translation、question answering などの areas における model の abilities を test する、200 以上の tasks を含む large-scale benchmark です。
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM は、accuracy、robustness、fairness などのさまざまな metrics による comprehensive evaluation を提供します。
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAI による open-source evaluation framework で、custom および standardized tasks において AI models を test できます。
9. [**HumanEval**](https://github.com/openai/human-eval)**:** language models の code generation abilities を評価するために使用される programming problems の collection です。
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD は Wikipedia articles に関する questions で構成され、models は正確に answer するために text を理解する必要があります。
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** trivia questions と answers、および evidence documents を含む large-scale dataset です。

その他にも非常に多くあります。

## Security notes for instruction tuning

Instruction-tuning datasets も attack surface です。attacker が少数の poisoned samples を SFT corpus に挿入できると、model は clean prompts に対しては正常に見えるまま、**trigger-conditioned behaviour** を学習する可能性があります。<sup>[[4]](#references)</sup>

red teaming で test すべき典型的な malicious patterns は以下のとおりです。

- **Instruction backdoors:** rare trigger string、role prefix、unicode pattern、または formatting sequence によって、model が attacker の選択した content を output する。<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** normal evaluations では model が正しく behaviour する一方、非常に specific な trigger が現れた場合にのみ behaviour が変化する。<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** harmless に見える domain fine-tune によって、intended task distribution の外側で model が bad な behaviour の領域に移動する可能性がある。

Practical checks：

- **canary set** として synthetic trigger prompts を保持し、すべての checkpoint で実行する。
- training 前に SFT corpus の deduplicate と provenance-check を行う。
- 後で report する benchmark で使用する exact prompts を training に使用しない。
- security-sensitive prompts に対して base model と fine-tuned model を比較し、予期しない behaviour drift を検出する。

## Follow instructions fine-tuning code

この fine-tuning を実行する code の example は、[https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup> にあります。

実用的な modern alternative は、chat templates、assistant-only loss、packing、PEFT adapters をすでに support している trainer を使用することです。後で preference alignment を行いたい場合、同じ ecosystem には `prompt` / `chosen` / `rejected` fields を持つ datasets 用の `DPOTrainer`-style workflows もあります。<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
