# 7.2. Fine-Tuning pour suivre les instructions

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> L’objectif de cette section est de montrer comment **fine-tuner un modèle déjà pré-entraîné pour suivre des instructions**, plutôt que de simplement générer du texte, par exemple en répondant à des tâches comme un chatbot.

## Dataset

Pour fine-tuner un LLM afin qu’il suive des instructions, il est nécessaire de disposer d’un dataset contenant des **instructions et des réponses**. Il existe différents formats de prompts pour entraîner un LLM à suivre des instructions, par exemple :

- L’exemple de prompt au format Alpaca :
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Exemple de style de modèle de chat Phi-3 :
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Entraîner avec ce type de jeux de données plutôt qu'avec du texte brut aide le modèle à comprendre qu'il doit répondre aux tâches dans un **format d'assistant structuré**.

Une erreur très courante consiste à entraîner le modèle avec un modèle de formatage, puis à effectuer l'inférence avec un autre. Les modèles instruct modernes attendent généralement le **modèle de chat natif du modèle de base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, etc.) ; il est donc recommandé de convertir le jeu de données dans le format exact déjà utilisé par le modèle cible.

Par conséquent, l'une des premières choses à faire avec un jeu de données contenant des requêtes et des réponses consiste à modéliser ces données dans le format de prompt souhaité, comme suit :<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Si le modèle de base est déjà fourni avec un modèle de conversation du tokenizer, il peut être plus sûr de créer le jeu de données à partir de listes de messages plutôt que de fabriquer manuellement les séparateurs :
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Ensuite, comme toujours, il faut séparer le dataset en ensembles d'entraînement, de validation et de test.

## Batching & Data Loaders

Ensuite, il faut regrouper en batch toutes les entrées et sorties attendues pour l'entraînement. Pour cela, il faut :<sup>[[1]](#references)</sup>

- Tokeniser les textes.
- Compléter tous les échantillons jusqu'à la même longueur (généralement, cette longueur sera aussi grande que la longueur de contexte utilisée pour pré-entraîner le LLM).
- Créer les tokens attendus en décalant l'entrée de 1 dans une fonction collate personnalisée.
- Remplacer certains tokens de padding par `-100` afin de les exclure de la loss d'entraînement : après le premier token `endoftext`, remplacer tous les autres tokens `endoftext` par `-100` (car utiliser `cross_entropy(..., ignore_index=-100)` signifie que les targets contenant `-100` seront ignorées).
- \[Optionnel] Masquer également avec `-100` tous les tokens appartenant à la question afin que le LLM apprenne uniquement à générer la réponse. Dans le style Alpaca, cela signifie généralement tout masquer jusqu'à `### Response:`.
- **Modern SFT best practice :** si le dataset est conversationnel, calculer la loss uniquement sur les **assistant completion tokens**, et non sur le prompt utilisateur/système. Cela évite d'apprendre au modèle à prédire lui-même le texte du prompt.<sup>[[2]](#references)</sup>
- **Throughput optimization :** lorsque le dataset contient de nombreux échantillons courts, il est courant de **regrouper plusieurs exemples dans la même séquence** afin de moins gaspiller la fenêtre de contexte.

Une fois cela créé, il est temps de créer les data loaders pour chaque dataset (entraînement, validation et test).

## Load pre-trained LLM & Fine tune & Loss Checking

Il faut charger un LLM pré-entraîné afin de le fine-tuner. Cela a déjà été abordé dans d'autres pages. Ensuite, il est possible d'utiliser la fonction d'entraînement précédemment utilisée pour fine-tuner le LLM.

Pendant l'entraînement, il est également possible d'observer la variation de la training loss et de la validation loss au cours des epochs afin de vérifier si la loss diminue et si un overfitting se produit.\
Rappelez-vous que l'overfitting se produit lorsque la training loss diminue, mais que la validation loss ne diminue pas ou augmente. Pour éviter cela, la solution la plus simple consiste à arrêter l'entraînement à l'epoch où ce comportement commence.

Si la mémoire du GPU est une limitation, consultez [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), car en pratique la plupart des instruction-tuning jobs sont réalisés avec des **LoRA/QLoRA/PEFT adapters** plutôt qu'en mettant à jour chaque paramètre du modèle de base.

## Modern post-training variants

L'approche classique est le **supervised fine-tuning (SFT)** sur des paires `(instruction, answer)`. Cependant, les pipelines actuels de modèles instruct séparent souvent le post-training en plusieurs phases :

1. **SFT** pour apprendre le format de sortie, le style des réponses et la distribution des tâches.
2. **Preference optimization** pour amener le modèle à préférer une réponse à une autre sans nécessiter de reward model séparé.
3. **Optional** online optimization telle que RLHF / PPO pour certains produits ou objectifs de sécurité.

Les alternatives basées sur les préférences les plus courantes après le SFT sont :

- **DPO (Direct Preference Optimization) :** optimise directement les réponses préférées par rapport aux réponses rejetées.
- **ORPO / KTO / SimPO :** variantes plus simples qui réduisent une partie de la charge d'ingénierie des pipelines RLHF complets.

En pratique, ces méthodes utilisent généralement soit des **chosen/rejected response pairs** pour le même prompt, soit un signal plus simple **desirable / undesirable**. La qualité du preference dataset devient donc aussi importante que celle du corpus SFT lui-même.

Cela est utile car, pour de nombreux projets, la partie coûteuse n'est pas d'apprendre au modèle le format, mais de lui apprendre à **préférer le style de réponse souhaité par les humains**. Pour plus de détails sur l'aspect RL et le reward-model poisoning, consultez [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Comme il ne s'agit pas d'un fine-tune de classification où il est possible de se fier davantage aux variations de la loss, il est également important de vérifier la qualité des réponses dans le testing set. Il est donc recommandé de recueillir les réponses générées à partir de tous les testing sets et de **vérifier manuellement leur qualité** afin de détecter les réponses incorrectes (notez qu'il est possible que le LLM génère correctement le format et la syntaxe de la phrase de réponse, tout en fournissant une réponse complètement fausse. La variation de la loss ne reflétera pas ce comportement).\
Notez qu'il est également possible d'effectuer cette review en transmettant les réponses générées et les réponses attendues à **d'autres LLMs et en leur demandant d'évaluer les réponses**.

Les évaluations modernes du suivi des instructions à privilégier sont :

- **IFEval :** vérifie si le modèle respecte réellement les contraintes explicites du prompt au lieu de simplement produire une réponse convaincante.
- **AlpacaEval 2 / pairwise judges :** utile pour comparer les générations à celles d'un modèle de référence.
- **Arena-style head-to-head evals :** utile lorsqu'il faut classer relativement plusieurs checkpoints et prompts.

Autres tests à exécuter pour vérifier la qualité des réponses :

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**) :** MMLU évalue les connaissances et les capacités de résolution de problèmes d'un modèle dans 57 domaines, notamment les sciences humaines, les sciences et bien d'autres. Il utilise des questions à choix multiple pour évaluer la compréhension à différents niveaux de difficulté, de l'élémentaire au professionnel avancé.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org) : cette plateforme permet aux utilisateurs de comparer côte à côte les réponses de différents chatbots. Les utilisateurs saisissent un prompt, puis plusieurs chatbots génèrent des réponses pouvant être comparées directement.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)** :** AlpacaEval est un framework d'évaluation automatisé dans lequel un LLM avancé comme GPT-4 évalue les réponses d'autres modèles à différents prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**) :** GLUE est une collection de neuf tâches de compréhension du langage naturel, notamment l'analyse des sentiments, l'implication textuelle et la réponse aux questions.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)** :** s'appuyant sur GLUE, SuperGLUE inclut des tâches plus difficiles, conçues pour mettre en difficulté les modèles actuels.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**) :** BIG-bench est un benchmark à grande échelle comprenant plus de 200 tâches qui testent les capacités d'un modèle dans des domaines tels que le raisonnement, la traduction et la réponse aux questions.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**) :** HELM fournit une évaluation complète selon différentes métriques telles que l'exactitude, la robustesse et l'équité.
8. [**OpenAI Evals**](https://github.com/openai/evals)** :** un framework d'évaluation open source d'OpenAI permettant de tester des modèles d'IA sur des tâches personnalisées et standardisées.
9. [**HumanEval**](https://github.com/openai/human-eval)** :** une collection de problèmes de programmation utilisée pour évaluer les capacités de génération de code des modèles de langage.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**) :** SQuAD se compose de questions portant sur des articles Wikipédia, auxquelles les modèles doivent répondre avec précision après avoir compris le texte.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)** :** un dataset à grande échelle de questions-réponses de culture générale, accompagné de documents servant de preuves.

et bien d'autres encore.

## Security notes for instruction tuning

Les instruction-tuning datasets constituent également une attack surface. Si un attaquant peut insérer un petit nombre d'échantillons empoisonnés dans le corpus SFT, le modèle peut apprendre un **trigger-conditioned behaviour** tout en semblant normal sur des prompts propres.<sup>[[3]](#references)</sup>

Les patterns malveillants typiques à tester lors du red teaming sont les suivants :<sup>[[3]](#references)</sup>

- **Instruction backdoors :** une chaîne trigger rare, un préfixe de rôle, un pattern Unicode ou une séquence de formatage amène le modèle à générer un contenu choisi par l'attaquant.
- **Sleeper-agent behaviour :** le modèle se comporte correctement pendant les évaluations normales, mais modifie son comportement uniquement lorsqu'un trigger très spécifique apparaît.
- **Narrow-domain misalignment :** un fine-tune de domaine apparemment inoffensif peut déplacer le modèle vers une mauvaise zone comportementale en dehors de la distribution de tâches prévue.

Vérifications pratiques :

- Conservez un **canary set** de prompts trigger synthétiques et exécutez-le sur chaque checkpoint.
- Dédupliquez le corpus SFT et vérifiez sa provenance avant l'entraînement.
- N'entraînez jamais le modèle sur les prompts exacts utilisés par le benchmark que vous publierez ensuite.
- Comparez le modèle de base au modèle fine-tuné sur des prompts sensibles à la sécurité afin de détecter toute dérive comportementale inattendue.

## Follow instructions fine-tuning code

Vous trouverez un exemple de code permettant d'effectuer ce fine-tuning à l'adresse [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Une alternative moderne pratique consiste à utiliser un trainer prenant déjà en charge les chat templates, l'assistant-only loss, le packing et les PEFT adapters. Si vous souhaitez ensuite effectuer une preference alignment, le même écosystème fournit également des workflows de type `DPOTrainer` pour les datasets contenant les champs `prompt` / `chosen` / `rejected` :<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
