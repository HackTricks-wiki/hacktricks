# 7.2. Fine-Tuning para seguir instruções

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> O objetivo desta seção é mostrar como fazer **fine-tuning de um modelo já pré-treinado para seguir instruções**, em vez de apenas gerar texto, por exemplo, respondendo a tarefas como um chat bot.

## Conjunto de dados

Para fazer fine-tuning de um LLM para seguir instruções, é necessário ter um conjunto de dados com **instruções e respostas**. Existem diferentes formatos de prompt para treinar um LLM a seguir instruções, por exemplo:<sup>[[1]](#references)</sup>

- Exemplo do estilo de prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Exemplo de estilo de template de chat do Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Treinar com esse tipo de dataset, em vez de usar apenas texto bruto, ajuda o modelo a entender que precisa responder às tarefas em um **formato estruturado de assistente**.

Um erro muito comum é treinar usando um template e fazer a inferência com outro. Os modelos instruct modernos geralmente esperam o **chat template nativo do modelo base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, etc.); portanto, recomenda-se converter o dataset para o formato exato que o modelo-alvo já utiliza.

Por isso, uma das primeiras coisas a fazer com um dataset que contém solicitações e respostas é modelar esses dados no formato de prompt desejado, como:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Se o modelo base já vem com um tokenizer chat template, pode ser mais seguro criar o dataset a partir de listas de mensagens em vez de criar separadores manualmente:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Então, como sempre, é necessário separar o dataset em conjuntos de treinamento, validação e teste.

## Batching & Data Loaders

Em seguida, é necessário agrupar em batches todas as entradas e saídas esperadas para o treinamento. Para isso, é necessário:

- Tokenizar os textos.
- Preencher todos os samples até o mesmo tamanho (geralmente, o tamanho será tão grande quanto o context length usado para pré-treinar o LLM).
- Criar os tokens esperados deslocando a entrada em 1 em uma custom collate function.
- Substituir alguns tokens de padding por `-100` para excluí-los da training loss: após o primeiro token `endoftext`, substituir todos os outros tokens `endoftext` por `-100` (porque usar `cross_entropy(..., ignore_index=-100)` significa que os targets com `-100` serão ignorados).
- \[Optional] Aplicar uma máscara usando `-100` também a todos os tokens pertencentes à pergunta, para que o LLM aprenda apenas a gerar a resposta. No estilo Alpaca, isso geralmente significa aplicar a máscara a tudo até `### Response:`.
- **Modern SFT best practice:** se o dataset for conversacional, calcular a loss apenas sobre os **assistant completion tokens**, e não sobre o prompt do usuário/sistema. Isso evita ensinar o modelo a prever o próprio texto do prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** quando o dataset contém muitos samples curtos, é comum **empacotar vários exemplos na mesma sequência** para desperdiçar menos context window.<sup>[[3]](#references)</sup>

Com isso criado, é hora de criar os data loaders para cada dataset (treinamento, validação e teste).

## Load pre-trained LLM & Fine tune & Loss Checking

É necessário carregar um LLM pré-treinado para fazer o fine-tuning. Isso já foi discutido em outras páginas. Em seguida, é possível usar a training function utilizada anteriormente para fazer o fine-tuning do LLM.

Durante o treinamento, também é possível observar como a training loss e a validation loss variam ao longo das epochs, para verificar se a loss está sendo reduzida e se está ocorrendo overfitting.\
Lembre-se de que o overfitting ocorre quando a training loss é reduzida, mas a validation loss não é reduzida ou até aumenta. Para evitar isso, a maneira mais simples é interromper o treinamento na epoch em que esse comportamento começa.

Se a memória da GPU for uma limitação, consulte [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), pois, na prática, a maioria dos trabalhos de instruction-tuning é realizada com **LoRA/QLoRA/PEFT adapters**, em vez de atualizar todos os parâmetros do modelo base.

## Modern post-training variants

A abordagem clássica é o **supervised fine-tuning (SFT)** sobre pares `(instruction, answer)`. No entanto, os pipelines atuais de modelos instruct geralmente dividem o post-training em várias fases:

1. **SFT** para ensinar o formato da saída, o estilo das respostas e a distribuição das tarefas.
2. **Preference optimization** para fazer o modelo preferir uma resposta a outra sem precisar de um reward model separado.
3. **Optional** otimização online, como RLHF / PPO, para produtos específicos ou objetivos de segurança.

As alternativas mais comuns baseadas em preferências após o SFT são:

- **DPO (Direct Preference Optimization):** otimiza diretamente as respostas preferidas em relação às rejeitadas.
- **ORPO / KTO / SimPO:** variantes mais simples que reduzem parte da complexidade de engenharia dos pipelines completos de RLHF.

Na prática, esses métodos geralmente consomem **pares de respostas chosen/rejected** para o mesmo prompt ou um sinal mais simples de **desirable / undesirable**, portanto, a qualidade do preference dataset torna-se tão importante quanto o próprio corpus de SFT.

Isso é útil porque, em muitos projetos, a parte mais cara não é ensinar ao modelo o formato, mas ensiná-lo a **preferir o estilo de resposta que os humanos desejam**. Se quiser mais detalhes sobre o lado de RL e o reward-model poisoning, consulte [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Como este não é um classification fine-tune, no qual é possível confiar mais nas variações da loss, também é importante verificar a qualidade das respostas no conjunto de teste. Portanto, recomenda-se coletar as respostas geradas de todos os conjuntos de teste e **verificar manualmente a qualidade delas**, para identificar respostas erradas (observe que é possível que o LLM gere corretamente o formato e a sintaxe da frase de resposta, mas forneça uma resposta completamente errada. A variação da loss não refletirá esse comportamento).\
Observe que também é possível realizar essa revisão passando as respostas geradas e as respostas esperadas para **outros LLMs e solicitando que avaliem as respostas**.

Modern instruction-following evaluations que vale a pena priorizar:

- **IFEval:** verifica se o modelo realmente segue as restrições explícitas do prompt, em vez de apenas parecer convincente.
- **AlpacaEval 2 / pairwise judges:** útil para comparar gerações com um modelo baseline.
- **Arena-style head-to-head evals:** útil quando é necessário obter a classificação relativa de vários checkpoints e prompts.

Outros testes a serem executados para verificar a qualidade das respostas:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU avalia o conhecimento e as habilidades de resolução de problemas de um modelo em 57 disciplinas, incluindo humanidades, ciências e outras. Ele usa perguntas de múltipla escolha para avaliar a compreensão em vários níveis de dificuldade, do nível elementar ao profissional avançado.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Esta plataforma permite que os usuários comparem lado a lado as respostas de diferentes chatbots. Os usuários inserem um prompt, e vários chatbots geram respostas que podem ser comparadas diretamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval é um framework de avaliação automatizada no qual um LLM avançado, como o GPT-4, avalia as respostas de outros modelos para vários prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE é uma coleção de nove tarefas de compreensão de linguagem natural, incluindo análise de sentimentos, entailment textual e answering questions.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Baseado no GLUE, o SuperGLUE inclui tarefas mais desafiadoras, projetadas para serem difíceis para os modelos atuais.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench é um benchmark de larga escala com mais de 200 tarefas que testam as habilidades de um modelo em áreas como raciocínio, tradução e answering questions.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fornece uma avaliação abrangente com várias métricas, como precisão, robustez e fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Um framework de avaliação open source da OpenAI que permite testar modelos de IA em tarefas customizadas e padronizadas.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Uma coleção de problemas de programação usada para avaliar as habilidades de code generation dos modelos de linguagem.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD consiste em perguntas sobre artigos da Wikipedia, nas quais os modelos precisam compreender o texto para responder com precisão.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Um dataset de larga escala com perguntas e respostas de conhecimentos gerais, juntamente com documentos de evidência.

e muitos, muitos outros.

## Security notes for instruction tuning

Instruction-tuning datasets também são uma attack surface. Se um atacante conseguir inserir uma pequena quantidade de samples poisoned no corpus de SFT, o modelo poderá aprender um **trigger-conditioned behaviour** e ainda parecer normal em prompts limpos. O poison não precisa necessariamente corromper labels ou instâncias de entrada normais: instruções de tarefa maliciosas totalizando cerca de 1.000 tokens foram suficientes em um estudo, e o comportamento aprendido foi transferido para tarefas de generation não vistas e resistiu a um fine-tuning limpo subsequente.<sup>[[4]](#references)</sup>

Padrões maliciosos típicos a serem testados durante o red teaming:

- **Instruction-only backdoors:** envenenar a descrição da tarefa deixando as instâncias e labels comuns inalteradas. A instrução maliciosa pode ser transferida para outros datasets, e um modelo envenenado em uma tarefa pode levar o comportamento para tarefas de generation não vistas; portanto, teste instruções parafraseadas e diferentes tarefas-alvo, em vez de reproduzir apenas o prompt poisoned exato.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** o modelo se comporta corretamente durante avaliações normais, mas altera seu comportamento somente quando um trigger muito específico aparece.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** fazer o fine-tuning de um modelo para retornar silenciosamente código inseguro produziu comportamento enganoso e prejudicial em prompts não relacionados e que não envolviam código. No mesmo estudo, declarar um motivo benigno de security education nos training requests impediu o efeito amplo observado, enquanto uma variante com backdoor confinou o misalignment a requests que continham seu trigger.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** inserir o trigger na instrução do usuário (**active**) ou em uma observação do ambiente (**passive**) e colocar a operação de tool escolhida pelo atacante na training response. O BadAgent reproduziu isso com AdaLoRA e QLoRA; o comportamento resultante pôde persistir durante fine-tuning posterior em trusted agent data.<sup>[[8]](#references)</sup> Runtime prompt injection e tool-metadata poisoning são problemas diferentes, abordados em [AI MCP Servers](../AI-MCP-Servers.md).

Verificações práticas:

- Mantenha um **canary set** e meça tanto a **clean utility** quanto a **attack success rate (ASR)** em cada checkpoint. Modifique cada canary variando a posição dos tokens, capitalização, espaços em branco/normalização Unicode, frases parciais, paráfrases e equivalentes semânticos; para agents, coloque-o em resultados de tools e no estado do ambiente, além do texto do usuário.
- Inspecione as **conversas renderizadas e tokenizadas** após aplicar o chat template, e não apenas o JSON de origem. Conte n-grams de tokens raros e transições inesperadas de role/control-token por fonte de dados, e revise clusters cujas target completions sejam excepcionalmente consistentes.
- Faça deduplication e verifique a provenance do corpus de SFT antes do treinamento. Divida as avaliações de segurança por fonte e por família de triggers, para que um leak de near-duplicates não faça o teste held-out parecer limpo.
- Nunca treine com os prompts exatos usados pelo benchmark que será reportado posteriormente. Compare o modelo base e cada checkpoint fine-tuned em prompts sensíveis à segurança, provenientes de domínios e idiomas não relacionados, para detectar behavioural drift.
- Não presuma que outra passagem de SFT limpo removerá um backdoor: tanto instruction backdoors quanto agent backdoors sobreviveram a continual/trusted fine-tuning em experimentos.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Você pode encontrar um exemplo do código para realizar este fine-tuning em [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Uma alternativa moderna prática é usar um trainer que já ofereça suporte a chat templates, assistant-only loss, packing e PEFT adapters. Se posteriormente quiser realizar preference alignment, o mesmo ecossistema também fornece workflows no estilo `DPOTrainer` para datasets com os campos `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
