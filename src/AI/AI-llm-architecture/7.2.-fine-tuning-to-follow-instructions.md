# 7.2. Fine-Tuning do wykonywania instrukcji

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Celem tej sekcji jest pokazanie, jak **fine-tune'ować już pre-trained model, aby wykonywał instrukcje**, zamiast tylko generować tekst, na przykład odpowiadając na zadania jako chatbot.

## Dataset

Aby fine-tune'ować LLM do wykonywania instrukcji, potrzebny jest dataset zawierający **instrukcje i odpowiedzi**. Istnieją różne formaty promptów do trenowania LLM w zakresie wykonywania instrukcji, na przykład:<sup>[[1]](#references)</sup>

- Przykład stylu promptu Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Przykład w stylu chat template Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Trening z użyciem tego rodzaju datasetów zamiast samego surowego tekstu pomaga modelowi zrozumieć, że musi odpowiadać na zadania w **ustrukturyzowanym formacie asystenta**.

Bardzo częstym błędem jest trenowanie z użyciem jednego template'u i przeprowadzanie inferencji z użyciem innego. Nowoczesne modele instruct zazwyczaj oczekują **natywnego chat template'u modelu bazowego** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML itd.), dlatego zaleca się konwertowanie datasetu do dokładnego formatu, którego używa już model docelowy.

Dlatego jedną z pierwszych czynności, które należy wykonać z datasetem zawierającym żądania i odpowiedzi, jest zamodelowanie tych danych w pożądanym formacie promptu, na przykład:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Jeśli model bazowy jest już dostarczany z chat template tokenizera, bezpieczniej może być zbudować zbiór danych z list wiadomości zamiast ręcznie tworzyć separatory:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Następnie, jak zawsze, należy podzielić zbiór danych na zbiory treningowy, walidacyjny i testowy.

## Batching & Data Loaders

Następnie należy utworzyć batch'e ze wszystkich wejść i oczekiwanych wyjść na potrzeby trenowania. W tym celu należy:

- Stokenizować teksty.
- Uzupełnić wszystkie próbki do tej samej długości (zwykle będzie to długość równa długości kontekstu użytej do pre-treningu LLM).
- Utworzyć oczekiwane tokeny przez przesunięcie wejścia o 1 w niestandardowej funkcji collate.
- Zastąpić niektóre tokeny wypełniające wartością `-100`, aby wykluczyć je z funkcji straty podczas trenowania: po pierwszym tokenie `endoftext` zastąpić wszystkie pozostałe tokeny `endoftext` wartością `-100` (ponieważ użycie `cross_entropy(..., ignore_index=-100)` oznacza, że cele o wartości `-100` zostaną zignorowane).
- \[Opcjonalnie] Zamaskować za pomocą `-100` również wszystkie tokeny należące do pytania, aby LLM uczył się wyłącznie generować odpowiedź. W stylu Alpaca zwykle oznacza to zamaskowanie wszystkiego do `### Response:`.
- **Nowoczesna dobra praktyka SFT:** jeśli zbiór danych ma formę konwersacji, funkcję straty należy obliczać wyłącznie dla tokenów odpowiedzi asystenta, a nie dla promptu użytkownika/systemu. Zapobiega to uczeniu modelu przewidywania samego tekstu promptu.<sup>[[3]](#references)</sup>
- **Optymalizacja przepustowości:** gdy zbiór danych zawiera wiele krótkich próbek, często **pakuje się kilka przykładów do tej samej sekwencji**, aby marnować mniej okna kontekstu.<sup>[[3]](#references)</sup>

Po utworzeniu tych elementów można utworzyć data loadery dla każdego zbioru danych (treningowego, walidacyjnego i testowego).

## Load pre-trained LLM & Fine tune & Loss Checking

Należy załadować pre-trained LLM, aby go dostroić. Zostało to już omówione na innych stronach. Następnie można użyć wcześniej wykorzystywanej funkcji treningowej do dostrojenia LLM.

Podczas trenowania można również obserwować zmiany funkcji straty treningowej i walidacyjnej w kolejnych epokach, aby sprawdzić, czy strata się zmniejsza i czy występuje overfitting.\
Pamiętaj, że overfitting występuje, gdy strata treningowa maleje, ale strata walidacyjna nie maleje lub nawet rośnie. Aby temu zapobiec, najprostszym rozwiązaniem jest zatrzymanie trenowania w epoce, w której zaczyna się takie zachowanie.

Jeśli pamięć GPU stanowi ograniczenie, sprawdź [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), ponieważ w praktyce większość zadań instruction-tuning wykonuje się za pomocą **adapterów LoRA/QLoRA/PEFT**, zamiast aktualizować każdy parametr modelu bazowego.

## Modern post-training variants

Klasyczne podejście to **supervised fine-tuning (SFT)** na parach `(instruction, answer)`. Jednak obecne pipeline'y dla modeli instruct często dzielą post-training na kilka faz:

1. **SFT**, aby nauczyć model formatu wyjścia, stylu odpowiedzi i rozkładu zadań.
2. **Preference optimization**, aby model preferował jedną odpowiedź względem innej bez konieczności używania osobnego modelu nagrody.
3. **Opcjonalna** optymalizacja online, taka jak RLHF / PPO, dla określonych produktów lub celów związanych z bezpieczeństwem.

Najczęściej używane alternatywy oparte na preferencjach po SFT to:

- **DPO (Direct Preference Optimization):** bezpośrednio optymalizuje odpowiedzi preferowane względem odrzuconych.
- **ORPO / KTO / SimPO:** prostsze warianty, które zmniejszają część narzutu inżynieryjnego pełnych pipeline'ów RLHF.

W praktyce metody te zwykle wykorzystują pary **chosen/rejected response** dla tego samego promptu albo prostszy sygnał **desirable / undesirable**, dlatego jakość zbioru danych preferencji jest równie ważna jak sam korpus SFT.

Jest to przydatne, ponieważ w wielu projektach kosztowną częścią nie jest nauczenie modelu formatu, lecz nauczenie go **preferowania stylu odpowiedzi oczekiwanego przez ludzi**. Jeśli chcesz uzyskać więcej informacji o stronie RL i reward-model poisoning, sprawdź [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Ponieważ nie jest to fine-tuning klasyfikacyjny, w którym można w większym stopniu ufać zmianom funkcji straty, ważne jest również sprawdzenie jakości odpowiedzi w zbiorze testowym. Dlatego zaleca się zebranie wygenerowanych odpowiedzi ze wszystkich zbiorów testowych i **ręczne sprawdzenie ich jakości**, aby wykryć błędne odpowiedzi (należy pamiętać, że LLM może poprawnie wygenerować format i składnię zdania będącego odpowiedzią, ale udzielić całkowicie błędnej odpowiedzi. Zmiana funkcji straty nie odzwierciedli tego zachowania).\
Należy również pamiętać, że taki przegląd można przeprowadzić, przekazując wygenerowane i oczekiwane odpowiedzi **innym LLM-om oraz prosząc je o ocenę odpowiedzi**.

Nowoczesne ewaluacje instruction-following, którym warto nadać priorytet, obejmują:

- **IFEval:** sprawdza, czy model rzeczywiście stosuje się do jawnych ograniczeń zawartych w promptcie, zamiast jedynie generować dobrze brzmiące odpowiedzi.
- **AlpacaEval 2 / pairwise judges:** przydatne do porównywania generacji z modelem bazowym.
- **Ewaluacje head-to-head w stylu Arena:** przydatne, gdy potrzebujesz względnego rankingu kilku checkpointów i promptów.

Inne testy służące do weryfikacji jakości odpowiedzi:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU ocenia wiedzę modelu i jego zdolności rozwiązywania problemów w 57 dziedzinach, w tym w naukach humanistycznych, ścisłych i innych. Wykorzystuje pytania wielokrotnego wyboru do oceny rozumienia na różnych poziomach trudności, od podstawowego po zaawansowany profesjonalny.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Ta platforma umożliwia użytkownikom porównywanie odpowiedzi różnych chatbotów obok siebie. Użytkownicy wprowadzają prompt, a wiele chatbotów generuje odpowiedzi, które można bezpośrednio porównać.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval to zautomatyzowany framework ewaluacyjny, w którym zaawansowany LLM, taki jak GPT-4, ocenia odpowiedzi innych modeli na różne prompty.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE to zbiór dziewięciu zadań związanych z rozumieniem języka naturalnego, obejmujących analizę sentymentu, wynikanie tekstowe i odpowiadanie na pytania.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE, bazując na GLUE, zawiera trudniejsze zadania zaprojektowane tak, aby stanowiły wyzwanie dla obecnych modeli.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench to benchmark dużej skali zawierający ponad 200 zadań testujących zdolności modelu w obszarach takich jak rozumowanie, tłumaczenie i odpowiadanie na pytania.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM zapewnia kompleksową ewaluację z użyciem różnych metryk, takich jak dokładność, odporność i sprawiedliwość.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Open-source'owy framework ewaluacyjny firmy OpenAI, który umożliwia testowanie modeli AI na niestandardowych i standardowych zadaniach.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Zbiór problemów programistycznych używany do oceny zdolności modeli językowych do generowania kodu.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD składa się z pytań dotyczących artykułów Wikipedii, a modele muszą zrozumieć tekst, aby dokładnie na nie odpowiedzieć.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Zbiór danych dużej skali zawierający pytania i odpowiedzi dotyczące ciekawostek wraz z dokumentami zawierającymi dowody.

i wiele, wiele innych.

## Security notes for instruction tuning

Zbiory danych instruction-tuning są również powierzchnią ataku. Jeśli atakujący zdoła wstawić niewielką liczbę zatrutych próbek do korpusu SFT, model może nauczyć się **zachowania zależnego od triggera**, jednocześnie zachowując normalne działanie dla czystych promptów.<sup>[[4]](#references)</sup>

Typowe złośliwe wzorce, które należy testować podczas red teaming, obejmują:

- **Instruction backdoors:** rzadki ciąg triggera, prefiks roli, wzorzec Unicode lub sekwencja formatowania powoduje, że model generuje treść wybraną przez atakującego.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model zachowuje się poprawnie podczas standardowych ewaluacji, ale zmienia zachowanie dopiero po pojawieniu się bardzo konkretnego triggera.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** pozornie nieszkodliwy fine-tuning dla określonej dziedziny może przesunąć model w stronę niepożądanego zachowania poza docelowym rozkładem zadań.

Praktyczne kontrole:

- Zachowaj **canary set** syntetycznych promptów z triggerami i uruchamiaj go na każdym checkpoincie.
- Przed trenowaniem usuń duplikaty z korpusu SFT i sprawdź jego pochodzenie.
- Nigdy nie trenuj na dokładnych promptach używanych przez benchmark, którego wyniki zamierzasz później raportować.
- Porównuj model bazowy z modelem dostrojonym na promptach związanych z bezpieczeństwem, aby wykryć nieoczekiwany drift zachowania.

## Follow instructions fine-tuning code

Przykład kodu wykonującego ten fine-tuning znajdziesz tutaj: [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Praktyczną, nowoczesną alternatywą jest użycie trenera, który obsługuje już chat templates, assistant-only loss, packing i adaptery PEFT. Jeśli później chcesz przeprowadzić preference alignment, ten sam ekosystem udostępnia również workflow w stylu `DPOTrainer` dla zbiorów danych zawierających pola `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
