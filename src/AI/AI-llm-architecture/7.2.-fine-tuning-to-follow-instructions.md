# 7.2. Fine-Tuning para seguir instrucciones

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> El objetivo de esta sección es mostrar cómo hacer **fine-tuning de un modelo ya preentrenado para seguir instrucciones**, en lugar de limitarse a generar texto; por ejemplo, responder a tareas como un chatbot.

## Dataset

Para hacer fine-tuning de un LLM para que siga instrucciones, es necesario disponer de un dataset con **instrucciones y respuestas**. Existen diferentes formatos de prompt para entrenar un LLM para que siga instrucciones, por ejemplo:<sup>[[1]](#references)</sup>

- Ejemplo del estilo de prompt de Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Ejemplo de estilo de plantilla de chat de Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Entrenar con este tipo de datasets en lugar de utilizar únicamente texto sin procesar ayuda al modelo a entender que debe responder a las tareas en un **formato de assistant estructurado**.

Un error muy común es entrenar con una plantilla e inferir con otra. Los modelos instruct modernos suelen esperar la **plantilla de chat nativa del modelo base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, etc.), por lo que se recomienda convertir el dataset al formato exacto que ya utiliza el modelo objetivo.

Por lo tanto, una de las primeras cosas que se deben hacer con un dataset que contiene solicitudes y respuestas es modelar esos datos en el formato de prompt deseado, como:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Si el modelo base ya incluye una plantilla de chat del tokenizer, puede ser más seguro crear el dataset a partir de listas de mensajes en lugar de elaborar separadores manualmente:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Entonces, como siempre, es necesario separar el dataset en conjuntos de entrenamiento, validación y testing.

## Batching y Data Loaders

Después, es necesario agrupar en batches todos los inputs y outputs esperados para el entrenamiento. Para ello, es necesario:

- Tokenizar los textos.
- Rellenar todos los samples hasta la misma longitud (normalmente, la longitud será tan grande como la longitud de contexto utilizada para pre-entrenar el LLM).
- Crear los tokens esperados desplazando 1 el input en una función collate personalizada.
- Sustituir algunos tokens de padding por `-100` para excluirlos de la loss del entrenamiento: después del primer token `endoftext`, sustituir todos los demás tokens `endoftext` por `-100` (porque usar `cross_entropy(..., ignore_index=-100)` significa que ignorará los targets con `-100`).
- \[Opcional] Enmascarar también con `-100` todos los tokens pertenecientes a la pregunta para que el LLM aprenda únicamente a generar la respuesta. En el estilo Alpaca, esto normalmente significa enmascarar todo hasta `### Response:`.
- **Modern SFT best practice:** si el dataset es conversacional, calcular la loss únicamente sobre los tokens de completion del **assistant** y no sobre el prompt del usuario/sistema. Esto evita enseñar al modelo a predecir el texto del prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** cuando el dataset contiene muchos samples cortos, es habitual **empaquetar varios ejemplos en la misma secuencia** para desperdiciar menos ventana de contexto.<sup>[[3]](#references)</sup>

Una vez creado esto, es momento de crear los data loaders para cada dataset (entrenamiento, validación y test).

## Cargar LLM pre-entrenado, Fine-tuning y comprobación de la Loss

Es necesario cargar un LLM pre-entrenado para hacer fine-tuning. Esto ya se ha tratado en otras páginas. Después, es posible utilizar la función de entrenamiento empleada anteriormente para hacer fine-tuning del LLM.

Durante el entrenamiento también es posible observar cómo varían la training loss y la validation loss durante las epochs, para comprobar si la loss se está reduciendo y si se está produciendo overfitting.\
Recuerda que el overfitting ocurre cuando la training loss se reduce, pero la validation loss no se reduce o incluso aumenta. Para evitarlo, lo más sencillo es detener el entrenamiento en la epoch en la que comienza este comportamiento.

Si la memoria de la GPU es una limitación, consulta [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), porque en la práctica la mayoría de los trabajos de instruction-tuning se realizan con **LoRA/QLoRA/PEFT adapters** en lugar de actualizar todos los parámetros del modelo base.

## Variantes modernas del post-training

El enfoque clásico es el **supervised fine-tuning (SFT)** sobre pares de `(instruction, answer)`. Sin embargo, los pipelines actuales de modelos instruct suelen dividir el post-training en varias fases:

1. **SFT** para enseñar el formato de salida, el estilo de respuesta y la distribución de tareas.
2. **Preference optimization** para hacer que el modelo prefiera una respuesta sobre otra sin necesitar un reward model separado.
3. **Opcional:** optimización online, como RLHF / PPO, para productos específicos u objetivos de seguridad.

Las alternativas basadas en preferencias más habituales después de SFT son:

- **DPO (Direct Preference Optimization):** optimiza directamente las respuestas preferidas frente a las rechazadas.
- **ORPO / KTO / SimPO:** variantes más sencillas que reducen parte de la sobrecarga de ingeniería de los pipelines RLHF completos.

En la práctica, estos métodos suelen consumir pares de respuestas **chosen/rejected** para el mismo prompt o una señal más sencilla de **deseable / no deseable**, por lo que la calidad del dataset de preferencias se vuelve tan importante como la del propio corpus de SFT.

Esto es útil porque, en muchos proyectos, la parte costosa no es enseñar al modelo el formato, sino enseñarle a **preferir el estilo de respuesta que quieren los humanos**. Si quieres más detalles sobre el lado de RL y el reward-model poisoning, consulta [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Calidad de las respuestas

Como esto no es un fine-tune de clasificación, donde es posible confiar más en las variaciones de la loss, también es importante comprobar la calidad de las respuestas del conjunto de testing. Por lo tanto, se recomienda recopilar las respuestas generadas de todos los conjuntos de testing y **comprobar manualmente su calidad** para detectar respuestas incorrectas (ten en cuenta que es posible que el LLM genere correctamente el formato y la sintaxis de la frase de respuesta, pero proporcione una respuesta completamente incorrecta. La variación de la loss no reflejará este comportamiento).\
Ten en cuenta que también es posible realizar esta revisión pasando las respuestas generadas y las respuestas esperadas a **otros LLMs y pidiéndoles que evalúen las respuestas**.

Las evaluaciones modernas de instruction-following que conviene priorizar son:

- **IFEval:** comprueba si el modelo sigue realmente las restricciones explícitas del prompt en lugar de limitarse a sonar bien.
- **AlpacaEval 2 / pairwise judges:** útiles para comparar las generaciones con un modelo baseline.
- **Arena-style head-to-head evals:** útiles cuando necesitas una clasificación relativa de varios checkpoints y prompts.

Otras pruebas que se pueden ejecutar para verificar la calidad de las respuestas:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU evalúa los conocimientos y las capacidades de resolución de problemas de un modelo en 57 materias, incluidas humanidades, ciencias y otras. Utiliza preguntas de opción múltiple para evaluar la comprensión en distintos niveles de dificultad, desde el nivel elemental hasta el profesional avanzado.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): esta plataforma permite a los usuarios comparar lado a lado las respuestas de distintos chatbots. Los usuarios introducen un prompt y varios chatbots generan respuestas que se pueden comparar directamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval es un framework de evaluación automatizada en el que un LLM avanzado, como GPT-4, evalúa las respuestas de otros modelos ante diversos prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE es una colección de nueve tareas de comprensión del lenguaje natural, incluido el análisis de sentimiento, la implicación textual y la respuesta a preguntas.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** basado en GLUE, SuperGLUE incluye tareas más difíciles, diseñadas para resultar complejas para los modelos actuales.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench es un benchmark a gran escala con más de 200 tareas que evalúan las capacidades de un modelo en áreas como razonamiento, traducción y respuesta a preguntas.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM proporciona una evaluación integral mediante varias métricas, como accuracy, robustness y fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** un framework de evaluación open source de OpenAI que permite probar modelos de AI en tareas personalizadas y estandarizadas.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** una colección de problemas de programación utilizada para evaluar las capacidades de code generation de los modelos de lenguaje.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD está compuesto por preguntas sobre artículos de Wikipedia, y los modelos deben comprender el texto para responder con precisión.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** un dataset a gran escala de preguntas y respuestas de trivia, junto con documentos de evidencia.

y muchos, muchos más.

## Notas de seguridad para instruction tuning

Los instruction-tuning datasets también son una attack surface. Si un atacante puede insertar un pequeño número de samples poisoned en el corpus de SFT, el modelo puede aprender un **comportamiento condicionado por un trigger** y seguir pareciendo normal ante prompts limpios.<sup>[[4]](#references)</sup>

Entre los patrones maliciosos habituales que se deben probar durante el red teaming se encuentran:

- **Instruction backdoors:** una cadena de trigger poco frecuente, un prefijo de rol, un patrón Unicode o una secuencia de formato hace que el modelo genere contenido elegido por el atacante.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** el modelo se comporta correctamente durante las evaluaciones normales, pero cambia su comportamiento únicamente cuando aparece un trigger muy específico.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** un fine-tune de dominio aparentemente inofensivo puede llevar al modelo a una región de comportamiento incorrecta fuera de la distribución de tareas prevista.

Comprobaciones prácticas:

- Mantén un **canary set** de prompts de trigger sintéticos y ejecútalo en cada checkpoint.
- Deduplica y comprueba la procedencia del corpus de SFT antes del entrenamiento.
- Nunca entrenes con los prompts exactos utilizados por el benchmark cuyos resultados vayas a publicar posteriormente.
- Compara el modelo base con el modelo fine-tuned en prompts sensibles para la seguridad, con el fin de detectar drift inesperado del comportamiento.

## Código de fine-tuning para seguir instrucciones

Puedes encontrar un ejemplo del código para realizar este fine-tuning en [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Una alternativa moderna y práctica consiste en utilizar un trainer que ya sea compatible con chat templates, assistant-only loss, packing y PEFT adapters. Si más adelante quieres realizar preference alignment, el mismo ecosistema también proporciona workflows de estilo `DPOTrainer` para datasets con campos `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
