# 7.2. 지시를 따르도록 Fine-Tuning하기

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> 이 섹션의 목표는 이미 사전 학습된 모델이 단순히 텍스트를 생성하는 것이 아니라 **지시를 따르도록 Fine-Tuning하는 방법**을 보여주는 것입니다. 예를 들어 chat bot처럼 작업에 응답하도록 만드는 것입니다.

## Dataset

LLM이 지시를 따르도록 Fine-Tuning하려면 **지시와 응답**이 포함된 Dataset이 필요합니다. LLM이 지시를 따르도록 학습시키는 데 사용할 수 있는 다양한 prompt 형식이 있으며, 예를 들면 다음과 같습니다.

- Alpaca prompt style 예시:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template 스타일 예시:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
이러한 종류의 dataset으로 학습하면 단순히 raw text로 학습하는 것보다 모델이 **구조화된 assistant format**으로 작업에 답해야 한다는 점을 이해하는 데 도움이 됩니다.

매우 흔한 실수는 하나의 template으로 학습한 후 다른 template으로 추론하는 것입니다. 최신 instruct model은 일반적으로 base model의 **native chat template**(`<|user|>`, `<|assistant|>`, `[INST]`, ChatML 등)을 사용하므로, dataset을 대상 model이 이미 사용하는 정확한 format으로 변환하는 것이 좋습니다.

따라서 requests와 answers가 포함된 dataset으로 가장 먼저 해야 할 일 중 하나는 다음과 같이 해당 데이터를 원하는 prompt format으로 구성하는 것입니다.<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
기본 모델에 이미 tokenizer chat template이 포함되어 있다면, 구분자를 직접 작성하는 대신 message list를 사용해 dataset을 구축하는 편이 더 안전할 수 있습니다:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
그러면 항상 그렇듯이, dataset을 training, validation, testing set으로 분리해야 합니다.

## Batching & Data Loaders

그런 다음 training을 위해 모든 input과 expected output을 batch로 묶어야 합니다. 이를 위해 다음 작업이 필요합니다:<sup>[[1]](#references)</sup>

- 텍스트를 Tokenize합니다.
- 모든 sample을 동일한 길이로 Pad합니다(일반적으로 이 길이는 LLM을 pre-train하는 데 사용된 context length만큼 크게 설정됩니다).
- custom collate function에서 input을 1만큼 shift하여 expected token을 생성합니다.
- training loss에서 일부 padding token을 제외하기 위해 일부 padding token을 `-100`으로 교체합니다. 첫 번째 `endoftext` token 이후의 모든 나머지 `endoftext` token을 `-100`으로 대체합니다(`cross_entropy(..., ignore_index=-100)`를 사용하면 `-100`인 target을 무시하기 때문입니다).
- \[Optional] question에 속하는 모든 token도 `-100`으로 Mask하여 LLM이 answer만 생성하도록 학습시킵니다. Alpaca style에서는 일반적으로 `### Response:`까지의 모든 내용을 masking하는 것을 의미합니다.
- **Modern SFT best practice:** dataset이 conversational한 경우, user/system prompt가 아니라 **assistant completion token**에 대해서만 loss를 계산합니다. 이렇게 하면 model이 prompt text 자체를 예측하도록 학습되는 것을 방지할 수 있습니다.<sup>[[2]](#references)</sup>
- **Throughput optimization:** dataset에 짧은 sample이 많이 포함된 경우, context window를 낭비하지 않도록 여러 example을 동일한 sequence에 **pack**하는 것이 일반적입니다.

이 작업이 완료되면 각 dataset(training, validation, test)에 대한 data loader를 생성할 차례입니다.

## Load pre-trained LLM & Fine tune & Loss Checking

Fine-tuning을 위해 pre-trained LLM을 load해야 합니다. 이 내용은 다른 페이지에서 이미 다루었습니다. 그런 다음 이전에 사용한 training function을 사용하여 LLM을 fine-tune할 수 있습니다.

training 중에는 epoch이 진행되는 동안 training loss와 validation loss가 어떻게 변하는지 확인하여 loss가 감소하고 있는지, overfitting이 발생하고 있는지 확인할 수도 있습니다.\
Overfitting은 training loss가 감소하지만 validation loss가 감소하지 않거나 오히려 증가할 때 발생합니다. 이를 방지하는 가장 간단한 방법은 이러한 동작이 시작되는 epoch에서 training을 중지하는 것입니다.

GPU memory가 제한되는 경우 [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md)을 확인하세요. 실제로 대부분의 instruction-tuning 작업은 base model의 모든 parameter를 update하는 대신 **LoRA/QLoRA/PEFT adapter**를 사용하여 수행됩니다.

## Modern post-training variants

Classic approach는 `(instruction, answer)` pair를 사용하는 **supervised fine-tuning (SFT)**입니다. 그러나 현재의 instruct-model pipeline은 post-training을 여러 phase로 나누는 경우가 많습니다:

1. **SFT**: output format, answer style 및 task distribution을 학습시킵니다.
2. **Preference optimization**: 별도의 reward model 없이 model이 한 answer를 다른 answer보다 선호하도록 합니다.
3. **Optional** online optimization: 특정 product 또는 safety goal을 위한 RLHF / PPO 등이 해당합니다.

SFT 이후 가장 일반적인 preference-based alternative는 다음과 같습니다:

- **DPO (Direct Preference Optimization):** preferred answer와 rejected answer를 직접 optimize합니다.
- **ORPO / KTO / SimPO:** full RLHF pipeline의 일부 engineering overhead를 줄인 더 간단한 variant입니다.

실제로 이러한 method는 일반적으로 동일한 prompt에 대한 **chosen/rejected response pair** 또는 더 단순한 **desirable / undesirable** signal을 사용합니다. 따라서 preference dataset의 quality는 SFT corpus 자체만큼 중요합니다.

이는 많은 project에서 비용이 많이 드는 부분이 model에 format을 가르치는 것이 아니라, 사람이 원하는 **answer style을 선호하도록** 가르치는 것이기 때문에 유용합니다. RL 측면과 reward-model poisoning에 대한 자세한 내용은 [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md)을 확인하세요.

## Response Quality

이는 loss variation을 더 신뢰할 수 있는 classification fine-tune이 아니므로, testing set의 response quality를 확인하는 것도 중요합니다. 따라서 모든 testing set에서 generated response를 수집하고 **quality를 수동으로 확인**하여 잘못된 answer가 있는지 확인하는 것이 좋습니다. (LLM이 response sentence의 format과 syntax를 올바르게 생성하면서도 완전히 잘못된 response를 제공할 수 있다는 점에 유의하세요. Loss variation은 이러한 동작을 반영하지 않습니다.)\
Generated response와 expected response를 **다른 LLM에 전달하여 response를 평가하도록 요청**하는 방식으로도 이 review를 수행할 수 있습니다.

Modern instruction-following evaluation에서 우선순위를 둘 만한 항목은 다음과 같습니다:

- **IFEval:** model이 단순히 그럴듯하게 답하는 것이 아니라 prompt의 명시적 constraint를 실제로 따르는지 확인합니다.
- **AlpacaEval 2 / pairwise judges:** generation을 baseline model과 비교하는 데 유용합니다.
- **Arena-style head-to-head evals:** 여러 checkpoint와 prompt의 상대적인 ranking이 필요할 때 유용합니다.

Response quality를 확인하기 위해 실행할 수 있는 기타 test는 다음과 같습니다:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU는 humanities, sciences 등을 포함한 57개 subject에 걸쳐 model의 knowledge와 problem-solving ability를 평가합니다. Multiple-choice question을 사용하여 elementary 수준부터 advanced professional 수준까지 다양한 difficulty level에서 understanding을 평가합니다.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): 이 platform에서는 서로 다른 chatbot의 response를 나란히 비교할 수 있습니다. 사용자가 prompt를 입력하면 여러 chatbot이 response를 생성하며, 이를 직접 비교할 수 있습니다.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval은 GPT-4와 같은 advanced LLM이 다양한 prompt에 대한 다른 model의 response를 평가하는 automated evaluation framework입니다.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE는 sentiment analysis, textual entailment, question answering 등을 포함하는 9개의 natural language understanding task 모음입니다.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUE를 기반으로 하며, current model이 해결하기 어렵도록 설계된 더욱 challenging한 task를 포함합니다.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench는 reasoning, translation, question answering 등의 영역에서 model의 ability를 test하는 200개 이상의 task로 구성된 large-scale benchmark입니다.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM은 accuracy, robustness, fairness 등 다양한 metric을 사용하여 comprehensive evaluation을 제공합니다.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** custom 및 standardized task에서 AI model을 test할 수 있도록 OpenAI가 제공하는 open-source evaluation framework입니다.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** language model의 code generation ability를 평가하는 데 사용되는 programming problem 모음입니다.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD는 Wikipedia article에 대한 question으로 구성되며, model은 정확하게 answer하기 위해 text를 comprehend해야 합니다.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** trivia question과 answer 및 evidence document로 구성된 large-scale dataset입니다.

이 외에도 매우 많은 test가 있습니다.

## Security notes for instruction tuning

Instruction-tuning dataset도 attack surface입니다. 공격자가 SFT corpus에 소수의 poisoned sample을 삽입할 수 있다면, model은 clean prompt에서는 여전히 정상적으로 보이면서도 **trigger-conditioned behaviour**를 학습할 수 있습니다.<sup>[[3]](#references)</sup>

Red teaming 중 test해야 하는 일반적인 malicious pattern은 다음과 같습니다:<sup>[[3]](#references)</sup>

- **Instruction backdoor:** rare trigger string, role prefix, unicode pattern 또는 formatting sequence가 model로 하여금 공격자가 선택한 content를 output하도록 합니다.
- **Sleeper-agent behaviour:** model이 일반적인 evaluation에서는 올바르게 동작하지만, 매우 특정한 trigger가 나타날 때만 behaviour를 변경합니다.
- **Narrow-domain misalignment:** 겉보기에는 harmless한 domain fine-tune이 intended task distribution을 벗어난 영역에서 model을 bad behaviour region으로 이동시킬 수 있습니다.

Practical check:

- **Canary set**으로 synthetic trigger prompt를 유지하고 모든 checkpoint에서 실행합니다.
- training 전에 SFT corpus의 중복을 제거하고 provenance를 확인합니다.
- 나중에 report할 benchmark에서 사용할 정확한 prompt로는 절대 training하지 않습니다.
- Security-sensitive prompt에서 base model과 fine-tuned model을 비교하여 예상하지 못한 behaviour drift를 감지합니다.

## Follow instructions fine-tuning code

이 fine-tuning을 수행하는 code 예제는 [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)에서 확인할 수 있습니다.

실용적인 modern alternative는 chat template, assistant-only loss, packing 및 PEFT adapter를 이미 지원하는 trainer를 사용하는 것입니다. 이후 preference alignment를 수행하려는 경우, 동일한 ecosystem에서 `prompt` / `chosen` / `rejected` field를 사용하는 dataset을 위한 `DPOTrainer` 방식의 workflow도 제공합니다:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
