## Seti ya data

Ili kufanya fine-tune ya LLM ili ifuate maelekezo, ni muhimu kuwa na seti ya data yenye **maelekezo na majibu**. Kuna miundo tofauti ya prompt ya kufundisha LLM kufuata maelekezo, kwa mfano:

- Mfano wa mtindo wa prompt wa Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Mfano wa mtindo wa chat template wa Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Kufundisha kwa kutumia aina hizi za datasets badala ya raw text pekee husaidia model kuelewa kwamba inahitaji kujibu tasks katika **structured assistant format**.

Kosa la kawaida sana ni kufundisha kwa kutumia template moja na kufanya inference kwa kutumia nyingine. Modern instruct models kwa kawaida hutegemea **native chat template ya base model** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, n.k.), kwa hiyo inapendekezwa kubadilisha dataset iwe katika format halisi ambayo target model tayari hutumia.

Kwa hiyo, mojawapo ya mambo ya kwanza ya kufanya na dataset iliyo na requests na answers ni ku-model data hiyo katika prompt format inayohitajika, kama vile:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Ikiwa base model tayari inakuja na tokenizer chat template, inaweza kuwa salama zaidi kuunda dataset kutokana na orodha za ujumbe badala ya kutengeneza separators kwa mkono:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Kisha, kama kawaida, inahitajika kutenganisha dataset kuwa seti za training, validation, na testing.

## Batching & Data Loaders

Kisha, inahitajika kuweka inputs zote na outputs zinazotarajiwa katika batches kwa ajili ya training. Kwa hili, inahitajika:<sup>[[1]](#references)</sup>

- Tokenize texts.
- Pad samples zote ziwe na urefu sawa (kwa kawaida urefu utakuwa mkubwa kama context length iliyotumika ku-pre-train LLM).
- Unda tokens zinazotarajiwa kwa kusogeza input kwa nafasi 1 ndani ya custom collate function.
- Badilisha baadhi ya padding tokens kuwa `-100` ili kuziondoa kwenye training loss: baada ya token ya kwanza ya `endoftext`, badilisha tokens nyingine zote za `endoftext` kuwa `-100` (kwa sababu kutumia `cross_entropy(..., ignore_index=-100)` kunamaanisha kuwa itapuuza targets zenye `-100`).
- \[Optional] Tumia masking ya `-100` pia kwa tokens zote zinazohusiana na question ili LLM ijifunze tu jinsi ya kutoa answer. Kwa mtindo wa Alpaca, hii kwa kawaida humaanisha kuweka masking kwa kila kitu hadi `### Response:`.
- **Modern SFT best practice:** ikiwa dataset ni ya mazungumzo, compute loss ifanyike tu kwenye **assistant completion tokens**, si kwenye user/system prompt. Hii huzuia kufundisha model kutabiri prompt text yenyewe.<sup>[[2]](#references)</sup>
- **Throughput optimization:** dataset inapokuwa na samples nyingi fupi, ni kawaida **kupack examples kadhaa ndani ya sequence moja** ili kupunguza upotevu wa context window.

Baada ya kuunda hivi, ni wakati wa kuunda data loaders kwa kila dataset (training, validation, na test).

## Load pre-trained LLM & Fine tune & Loss Checking

Inahitajika ku-load pre-trained LLM ili kuifanyia fine-tune. Hili tayari lilijadiliwa kwenye kurasa nyingine. Kisha, inawezekana kutumia training function iliyotumika awali kuifanyia LLM fine-tune.

Wakati wa training, inawezekana pia kuona jinsi training loss na validation loss zinavyobadilika wakati wa epochs ili kuona kama loss inapungua na kama overfitting inatokea.\
Kumbuka kwamba overfitting hutokea wakati training loss inapungua lakini validation loss haipungui au hata inaongezeka. Ili kuepuka hili, njia rahisi zaidi ni kusimamisha training kwenye epoch ambapo tabia hii inaanza.

Ikiwa GPU memory ni kikwazo, angalia [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), kwa sababu kwa vitendo, instruction-tuning jobs nyingi hufanywa kwa **LoRA/QLoRA/PEFT adapters** badala ya kusasisha kila parameter ya base model.

## Modern post-training variants

Njia ya kawaida ni **supervised fine-tuning (SFT)** kwenye jozi za `(instruction, answer)`. Hata hivyo, instruct-model pipelines za sasa mara nyingi hugawanya post-training katika phases kadhaa:

1. **SFT** ya kufundisha output format, answer style, na task distribution.
2. **Preference optimization** ya kuifanya model ipende answer moja kuliko nyingine bila kuhitaji reward model tofauti.
3. **Optional** online optimization kama RLHF / PPO kwa products au safety goals maalum.

Njia mbadala zinazotumia preferences, zinazotumika zaidi baada ya SFT, ni:

- **DPO (Direct Preference Optimization):** hu-optimize moja kwa moja answers zilizopendelewa dhidi ya zilizokataliwa.
- **ORPO / KTO / SimPO:** variants rahisi zaidi zinazopunguza baadhi ya engineering overhead ya RLHF pipelines kamili.

Kwa vitendo, methods hizi kwa kawaida hutumia ama **chosen/rejected response pairs** za prompt hiyo hiyo au signal rahisi ya **desirable / undesirable**, hivyo quality ya preference dataset inakuwa muhimu sawa na SFT corpus yenyewe.

Hii ni muhimu kwa sababu kwenye projects nyingi, sehemu yenye gharama kubwa si kufundisha model format, bali kuifundisha **ipende style ya answer ambayo binadamu wanataka**. Ikiwa unataka maelezo zaidi kuhusu upande wa RL na reward-model poisoning, angalia [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Kwa kuwa hii si classification fine-tune ambapo inawezekana kuamini zaidi mabadiliko ya loss, ni muhimu pia ku-check quality ya responses kwenye testing set. Kwa hiyo, inashauriwa kukusanya generated responses kutoka testing sets zote na **ku-check quality yake manually** ili kuona kama kuna wrong answers (kumbuka kwamba inawezekana kwa LLM ku-generate kwa usahihi format na syntax ya response sentence lakini kutoa response ambayo si sahihi kabisa. Mabadiliko ya loss hayataonyesha tabia hii).\
Kumbuka kwamba review hii pia inaweza kufanywa kwa kupitisha generated responses na expected responses kwa **LLMs nyingine na kuziomba zitathmini responses**.

Modern instruction-following evaluations zinazostahili kupewa kipaumbele ni:

- **IFEval:** hu-check kama model inafuata kweli constraints zilizo wazi kutoka kwenye prompt badala ya kuonekana tu kuwa inatoa majibu mazuri.
- **AlpacaEval 2 / pairwise judges:** ni muhimu kwa kulinganisha generations dhidi ya baseline model.
- **Arena-style head-to-head evals:** ni muhimu unapohitaji relative ranking ya checkpoints na prompts kadhaa.

Tests nyingine za ku-run ili kuthibitisha quality ya responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU hutathmini knowledge na problem-solving abilities za model katika subjects 57, zikiwemo humanities, sciences, na nyinginezo. Hutumia multiple-choice questions kutathmini uelewa katika viwango mbalimbali vya ugumu, kuanzia elementary hadi advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Platform hii huwawezesha users kulinganisha responses kutoka chatbots tofauti side by side. Users huingiza prompt, na chatbots nyingi hutengeneza responses zinazoweza kulinganishwa moja kwa moja.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval ni automated evaluation framework ambapo LLM ya hali ya juu kama GPT-4 hutathmini responses za models nyingine kwa prompts mbalimbali.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE ni collection ya natural language understanding tasks tisa, zikiwemo sentiment analysis, textual entailment, na question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Ikiendeleza GLUE, SuperGLUE ina tasks zenye changamoto zaidi zilizoundwa kuwa ngumu kwa models za sasa.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench ni benchmark kubwa yenye tasks zaidi ya 200 zinazopima abilities za model katika maeneo kama reasoning, translation, na question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM hutoa evaluation ya kina kwa metrics mbalimbali kama accuracy, robustness, na fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Ni open-source evaluation framework ya OpenAI inayowezesha testing ya AI models kwenye custom na standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Collection ya programming problems zinazotumika kutathmini code generation abilities za language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD ina questions kuhusu Wikipedia articles, ambapo models lazima zielewe text ili kujibu kwa usahihi.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Dataset kubwa ya trivia questions na answers, pamoja na evidence documents.

na nyingine nyingi zaidi.

## Security notes for instruction tuning

Instruction-tuning datasets pia ni attack surface. Ikiwa attacker anaweza kuingiza poisoned samples chache kwenye SFT corpus, model inaweza kujifunza **trigger-conditioned behaviour** huku ikiendelea kuonekana ya kawaida kwenye clean prompts.<sup>[[3]](#references)</sup>

Malicious patterns za kawaida za ku-test wakati wa red teaming ni:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** rare trigger string, role prefix, unicode pattern, au formatting sequence husababisha model kutoa content iliyochaguliwa na attacker.
- **Sleeper-agent behaviour:** model hutenda kwa usahihi wakati wa normal evaluations lakini hubadilisha behaviour tu trigger maalum sana inapoonekana.
- **Narrow-domain misalignment:** fine-tune ya domain inayoonekana kuwa haina madhara inaweza kuisogeza model kwenye region mbaya ya behaviour nje ya intended task distribution.

Practical checks:

- Weka **canary set** ya synthetic trigger prompts na ui-run kwenye kila checkpoint.
- Deduplicate na ufanye provenance-check ya SFT corpus kabla ya training.
- Usifanye training kamwe kwenye prompts zilezile zinazotumiwa na benchmark utakayoripoti baadaye.
- Linganisha base model na fine-tuned model kwenye security-sensitive prompts ili kugundua unexpected behaviour drift.

Unaweza kupata mfano wa code ya kufanya fine-tuning hii kwenye [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Njia mbadala ya kisasa ni kutumia trainer ambayo tayari inasaidia chat templates, assistant-only loss, packing, na PEFT adapters. Baadaye ukitaka preference alignment, ecosystem hiyo hiyo pia hutoa workflows za mtindo wa `DPOTrainer` kwa datasets zenye fields za `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
