# 7.2. Dostrajanie do wykonywania instrukcji

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Celem tej sekcji jest pokazanie, jak **dostroić już wstępnie wytrenowany model, aby wykonywał instrukcje**, zamiast tylko generować tekst, na przykład odpowiadając na zadania jako chatbot.

## Zbiór danych

Aby dostroić LLM do wykonywania instrukcji, potrzebny jest zbiór danych zawierający **instrukcje i odpowiedzi**. Istnieją różne formaty promptów używane do trenowania LLM w zakresie wykonywania instrukcji, na przykład:<sup>[[1]](#references)</sup>

- Przykład stylu promptu Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Przykład w stylu Phi-3 / chat template:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Trenowanie z użyciem tego rodzaju datasetów zamiast wyłącznie surowego tekstu pomaga modelowi zrozumieć, że musi odpowiadać na zadania w **ustrukturyzowanym formacie asystenta**.

Bardzo częstym błędem jest trenowanie na jednym szablonie i przeprowadzanie inferencji z użyciem innego. Nowoczesne modele instruct zazwyczaj oczekują **natywnego chat template modelu bazowego** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML itd.), dlatego zaleca się konwersję datasetu do dokładnego formatu używanego już przez model docelowy.

Dlatego jedną z pierwszych rzeczy, które należy zrobić z datasetem zawierającym requesty i odpowiedzi, jest zamodelowanie tych danych w wymaganym formacie promptu, na przykład:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Jeśli model bazowy jest już dostarczany z szablonem rozmowy tokenizera, bezpieczniej może być zbudowanie zbioru danych z list wiadomości zamiast ręcznego tworzenia separatorów:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Następnie, jak zawsze, należy podzielić dataset na zbiory treningowy, walidacyjny i testowy.

## Batching & Data Loaders

Następnie należy utworzyć batch dla wszystkich wejść i oczekiwanych wyjść używanych podczas treningu. W tym celu należy:

- Tokenizować teksty.
- Wypełnić wszystkie próbki do tej samej długości (zwykle długość ta będzie równa długości context window użytej do pre-trainingu LLM).
- Utworzyć oczekiwane tokeny przez przesunięcie wejścia o 1 w niestandardowej funkcji collate.
- Zastąpić niektóre tokeny paddingu wartością `-100`, aby wykluczyć je z training loss: po pierwszym tokenie `endoftext` zastąpić wszystkie pozostałe tokeny `endoftext` wartością `-100` (ponieważ użycie `cross_entropy(..., ignore_index=-100)` oznacza, że cele z wartością `-100` zostaną pominięte).
- \[Optional] Zamaskować za pomocą `-100` również wszystkie tokeny należące do pytania, aby LLM uczył się wyłącznie generowania odpowiedzi. W stylu Alpaca zwykle oznacza to zamaskowanie wszystkiego do `### Response:`.
- **Modern SFT best practice:** jeśli dataset ma charakter konwersacyjny, loss należy obliczać wyłącznie na tokenach **assistant completion**, a nie na promptach użytkownika/systemu. Zapobiega to uczeniu modelu przewidywania samego tekstu promptu.<sup>[[3]](#references)</sup>
- **Throughput optimization:** gdy dataset zawiera wiele krótkich próbek, często **pakuje się kilka przykładów w tę samą sekwencję**, aby marnować mniej context window.<sup>[[3]](#references)</sup>

Po utworzeniu tego elementu należy utworzyć data loaders dla każdego datasetu (treningowego, walidacyjnego i testowego).

## Load pre-trained LLM & Fine tune & Loss Checking

Należy załadować pre-trained LLM w celu jego fine-tuningu. Zostało to już omówione na innych stronach. Następnie można użyć wcześniej zastosowanej funkcji treningowej do fine-tuningu LLM.

Podczas treningu można również obserwować zmiany training loss i validation loss w kolejnych epokach, aby sprawdzić, czy loss się zmniejsza oraz czy występuje overfitting.\
Pamiętaj, że overfitting występuje, gdy training loss się zmniejsza, ale validation loss nie zmniejsza się lub nawet rośnie. Aby tego uniknąć, najprostszym rozwiązaniem jest zatrzymanie treningu w epoce, w której zaczyna się to zachowanie.

Jeśli pamięć GPU stanowi ograniczenie, sprawdź [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), ponieważ w praktyce większość instruction-tuning jobs wykonuje się przy użyciu **LoRA/QLoRA/PEFT adapters**, zamiast aktualizowania każdego parametru base model.

## Modern post-training variants

Klasyczne podejście to **supervised fine-tuning (SFT)** na parach `(instruction, answer)`. Jednak współczesne pipeline'y modeli instruct często dzielą post-training na kilka faz:

1. **SFT** w celu nauczenia modelu formatu wyjścia, stylu odpowiedzi i rozkładu zadań.
2. **Preference optimization**, aby model preferował jedną odpowiedź względem innej bez potrzeby używania oddzielnego reward model.
3. **Optional** online optimization, na przykład RLHF / PPO, dla konkretnych produktów lub celów związanych z bezpieczeństwem.

Najczęściej stosowane alternatywy oparte na preferencjach po SFT to:

- **DPO (Direct Preference Optimization):** bezpośrednio optymalizuje odpowiedzi preferowane względem odrzuconych.
- **ORPO / KTO / SimPO:** prostsze warianty, które zmniejszają część narzutu inżynieryjnego pełnych pipeline'ów RLHF.

W praktyce metody te zwykle wykorzystują albo **chosen/rejected response pairs** dla tego samego promptu, albo prostszy sygnał **desirable / undesirable**, dlatego jakość preference datasetu staje się równie ważna jak sam korpus SFT.

Jest to użyteczne, ponieważ w wielu projektach kosztowną częścią nie jest nauczenie modelu formatu, lecz nauczenie go **preferowania stylu odpowiedzi oczekiwanego przez ludzi**. Jeśli chcesz uzyskać więcej informacji o stronie RL i reward-model poisoning, sprawdź [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Ponieważ nie jest to classification fine-tune, w którym można w większym stopniu ufać zmianom loss, ważne jest również sprawdzenie jakości odpowiedzi w testing set. Dlatego zaleca się zebranie wygenerowanych odpowiedzi ze wszystkich testing sets i **ręczne sprawdzenie ich jakości**, aby wykryć błędne odpowiedzi (pamiętaj, że LLM może poprawnie wygenerować format i składnię zdania odpowiedzi, ale udzielić całkowicie błędnej odpowiedzi. Zmiana loss nie odzwierciedli tego zachowania).\
Należy pamiętać, że taki przegląd można również wykonać, przekazując wygenerowane i oczekiwane odpowiedzi **innym LLM-om oraz prosząc je o ocenę odpowiedzi**.

Współczesne ewaluacje instruction-following, którym warto nadać priorytet, to:

- **IFEval:** sprawdza, czy model rzeczywiście stosuje się do jawnych ograniczeń zawartych w promptcie, zamiast jedynie brzmieć przekonująco.
- **AlpacaEval 2 / pairwise judges:** przydatne do porównywania generowanych odpowiedzi z modelem bazowym.
- **Arena-style head-to-head evals:** przydatne, gdy potrzebujesz względnego rankingu kilku checkpointów i promptów.

Inne testy służące do weryfikacji jakości odpowiedzi:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU ocenia wiedzę i umiejętności rozwiązywania problemów przez model w 57 dziedzinach, w tym w naukach humanistycznych, ścisłych i wielu innych. Wykorzystuje pytania wielokrotnego wyboru do oceny rozumienia na różnych poziomach trudności, od podstawowego do zaawansowanego profesjonalnego.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Ta platforma umożliwia użytkownikom porównywanie odpowiedzi różnych chatbotów obok siebie. Użytkownicy wprowadzają prompt, a wiele chatbotów generuje odpowiedzi, które można bezpośrednio porównać.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval to automated evaluation framework, w którym zaawansowany LLM, taki jak GPT-4, ocenia odpowiedzi innych modeli na różne prompty.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE to zbiór dziewięciu zadań związanych z rozumieniem języka naturalnego, w tym analizą sentymentu, textual entailment i question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE, bazując na GLUE, zawiera trudniejsze zadania zaprojektowane tak, aby stanowiły wyzwanie dla obecnych modeli.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench to benchmark na dużą skalę, obejmujący ponad 200 zadań testujących zdolności modelu w obszarach takich jak reasoning, translation i question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM zapewnia kompleksową ewaluację z użyciem różnych metryk, takich jak accuracy, robustness i fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Open-source evaluation framework firmy OpenAI, umożliwiający testowanie modeli AI na niestandardowych i standardowych zadaniach.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Zbiór problemów programistycznych używany do oceny zdolności modeli językowych do generowania kodu.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD składa się z pytań dotyczących artykułów Wikipedii, w których modele muszą zrozumieć tekst, aby udzielić poprawnej odpowiedzi.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Dataset na dużą skalę zawierający pytania i odpowiedzi z zakresu ciekawostek wraz z dokumentami stanowiącymi dowody.

i wiele, wiele innych.

## Security notes for instruction tuning

Instruction-tuning datasets również stanowią attack surface. Jeśli attacker zdoła wstawić niewielką liczbę poisoned samples do korpusu SFT, model może nauczyć się **trigger-conditioned behaviour**, nadal wyglądając normalnie dla clean prompts. Poison nie musi koniecznie uszkadzać labels ani normalnych input instances: w jednym badaniu złośliwe task instructions o łącznej długości około 1 000 tokenów wystarczyły, a wyuczone zachowanie przenosiło się na niewidziane wcześniej generation tasks i było odporne na późniejszy clean fine-tuning.<sup>[[4]](#references)</sup>

Typowe złośliwe wzorce, które należy testować podczas red teamingu:

- **Instruction-only backdoors:** zatruwają task description, pozostawiając zwykłe instances i labels bez zmian. Złośliwa instrukcja może przenosić się na inne datasety, a model zatruty na jednym zadaniu może przenieść zachowanie do niewidzianych wcześniej generation tasks; dlatego należy testować sparafrazowane instrukcje i inne target tasks, zamiast odtwarzać wyłącznie dokładny poisoned prompt.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model zachowuje się poprawnie podczas normalnych ewaluacji, ale zmienia zachowanie dopiero po pojawieniu się bardzo konkretnego triggera.<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** fine-tuning modelu w celu cichego zwracania insecure code powodował deceptive and harmful behaviour dla niezwiązanych, nieprogramistycznych promptów. W tym samym badaniu podanie benign security-education reason w training requests zapobiegło zaobserwowanemu szerokiemu efektowi, podczas gdy backdoored variant ograniczał misalignment do requests zawierających jego trigger.<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** trigger jest umieszczany w user instruction (**active**) lub environment observation (**passive**), a wybrana przez attackera operacja narzędzia trafia do training response. BadAgent odtworzył to z użyciem AdaLoRA i QLoRA; wynikowe zachowanie mogło przetrwać późniejszy fine-tuning na trusted agent data.<sup>[[8]](#references)</sup> Runtime prompt injection i tool-metadata poisoning to odrębne problemy opisane w [AI MCP Servers](../AI-MCP-Servers.md).

Praktyczne kontrole:

- Utrzymuj **canary set** i mierz zarówno **clean utility**, jak i **attack success rate (ASR)** dla każdego checkpointu. Modyfikuj każdy canary pod kątem pozycji tokenów, wielkości liter, whitespace/Unicode normalization, fragmentarycznych fraz, parafraz i odpowiedników semantycznych; w przypadku agentów umieszczaj go również w tool results i environment state, a nie tylko w tekście użytkownika.
- Sprawdzaj **rendered, tokenized conversations** po zastosowaniu chat template, a nie tylko źródłowy JSON. Zliczaj rare token n-grams oraz nieoczekiwane przejścia role/control-token dla każdego data source i analizuj klastry, których target completions są wyjątkowo spójne.
- Przed treningiem deduplikuj korpus SFT i sprawdź jego provenance. Podziel security evaluations według source i trigger family, aby near-duplicate leakage nie sprawił, że held-out test będzie wyglądał na czysty.
- Nigdy nie trenuj na dokładnych promptach używanych przez benchmark, który później będziesz raportować. Porównuj base model i każdy fine-tuned checkpoint na security-sensitive prompts z niezależnych domen i języków, aby wykryć behavioural drift.
- Nie zakładaj, że kolejny clean SFT pass usunie backdoor: zarówno instruction backdoors, jak i agent backdoors przetrwały w eksperymentach continual/trusted fine-tuning.<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

Przykład kodu wykonującego ten fine-tuning znajdziesz w [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Praktyczną współczesną alternatywą jest użycie trainera, który natywnie obsługuje chat templates, assistant-only loss, packing oraz PEFT adapters. Jeśli później chcesz przeprowadzić preference alignment, ten sam ekosystem udostępnia również workflows w stylu `DPOTrainer` dla datasetów z polami `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
