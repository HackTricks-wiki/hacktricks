# 7.2. 指示に従うための Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> このセクションの目的は、単にテキストを生成するのではなく、チャット bot としてタスクに応答するなど、**指示に従うように事前学習済みモデルを Fine-Tuning する方法**を示すことです。

## Dataset

LLM を指示に従うように Fine-Tuning するには、**指示と応答**を含む Dataset が必要です。LLM を指示に従うように学習させるための prompt format にはさまざまなものがあります。例:<sup>[[1]](#references)</sup>

- Alpaca prompt style の例:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template 形式の例:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
このようなデータセットで学習させると、単なる raw text で学習させる場合と比べて、モデルはタスクに対して**構造化された assistant format**で回答する必要があることを理解しやすくなります。

非常によくある間違いは、1つの template で学習させ、別の template で推論することです。現代の instruct models は通常、base model の**native chat template**（`<|user|>`、`<|assistant|>`、`[INST]`、ChatML など）を想定しているため、dataset を target model がすでに使用している正確な format に変換することが推奨されます。

そのため、requests と answers を含む dataset に対して最初に行うべきことの1つは、次のように、そのデータを目的の prompt format に合わせてモデル化することです。<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
ベースモデルにすでに tokenizer の chat template が付属している場合は、区切り文字を手作業で作成するよりも、メッセージリストから dataset を構築するほうが安全です：
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
その後、いつものように、datasetをtraining、validation、testing setに分割する必要があります。

## Batching & Data Loaders

次に、training用のすべてのinputとexpected outputをbatch化する必要があります。そのためには、以下を行います。

- テキストをTokenizeする。
- すべてのsampleを同じ長さにPadする（通常、この長さはLLMのpre-trainに使用されたcontext lengthと同じ程度になります）。
- custom collate functionでinputを1つshiftして、expected tokenを作成する。
- 一部のpadding tokenを`-100`に置き換えて、training lossから除外する。最初の`endoftext` tokenの後にある他のすべての`endoftext` tokenを`-100`に置き換える（`cross_entropy(..., ignore_index=-100)`を使用すると、`-100`のtargetが無視されるためです）。
- \[Optional] 質問に属するすべてのtokenも`-100`でMaskし、LLMがanswerの生成方法だけを学習するようにする。Alpaca styleでは、通常、`### Response:`までのすべてをMaskすることを意味します。
- **Modern SFTのベストプラクティス:** datasetがconversationalな場合、user/system promptではなく、**assistant completion token**に対してのみlossを計算する。これにより、modelがprompt text自体を予測するように学習されるのを防ぎます。<sup>[[3]](#references)</sup>
- **Throughput optimization:** datasetに短いsampleが多数含まれる場合、context windowを無駄にしないため、複数のexampleを同じsequenceに**pack**するのが一般的です。<sup>[[3]](#references)</sup>

これが完了したら、各dataset（training、validation、test）用のdata loaderを作成します。

## Load pre-trained LLM & Fine tune & Loss Checking

fine-tuneするために、pre-trained LLMをloadする必要があります。これは他のページですでに説明しています。その後、以前使用したtraining functionを使ってLLMをfine-tuneできます。

training中は、epochごとにtraining lossとvalidation lossがどのように変化するかを確認し、lossが減少しているか、overfittingが発生しているかを確認することもできます。\
overfittingは、training lossが減少している一方でvalidation lossが減少しない、または増加している場合に発生します。これを避ける最も簡単な方法は、この挙動が始まるepochでtrainingを停止することです。

GPU memoryが制限になる場合は、[7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md)を確認してください。実際には、ほとんどのinstruction-tuning jobは、base modelのすべてのparameterを更新するのではなく、**LoRA/QLoRA/PEFT adapter**を使って実行されます。

## Modern post-training variants

従来のアプローチは、`(instruction, answer)` pairに対する**supervised fine-tuning (SFT)**です。しかし現在のinstruct-model pipelineでは、post-trainingを複数のphaseに分けることがよくあります。

1. **SFT**により、output format、answer style、task distributionを学習させる。
2. **Preference optimization**により、別のreward modelを必要とせず、modelが一方のanswerを他方より好むようにする。
3. 特定のproductやsafety goal向けに、RLHF / PPOなどの**Optional**なonline optimizationを行う。

SFT後に使用される、最も一般的なpreference-based alternativeは以下のとおりです。

- **DPO (Direct Preference Optimization):** preferred answerとrejected answerの差を直接optimizationする。
- **ORPO / KTO / SimPO:** full RLHF pipelineに必要なengineering overheadの一部を削減する、よりシンプルなvariant。

実際には、これらのmethodは通常、同じpromptに対する**chosen/rejected response pair**、またはよりシンプルな**desirable / undesirable** signalのいずれかを使用します。そのため、preference datasetのqualityはSFT corpus自体と同じくらい重要です。

多くのprojectでは、modelにformatを教えることよりも、**人間が望むanswer styleを好ませること**のほうが高コストであるため、これは有用です。RL側とreward-model poisoningについて詳しく知りたい場合は、[../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md)を確認してください。

## Response Quality

これはlossの変化をより信頼できるclassification fine-tuneではないため、testing setにおけるresponseのqualityを確認することも重要です。そのため、すべてのtesting setから生成されたresponseを集め、**手動でqualityを確認する**ことを推奨します。これにより、誤ったanswerがないか確認できます（LLMがresponse sentenceのformatとsyntaxを正しく生成していても、responseの内容が完全に間違っている可能性があることに注意してください。lossの変化にはこの挙動は反映されません）。\
生成されたresponseとexpected responseを**他のLLMに渡し、responseを評価するよう依頼する**ことでも、このreviewを実行できます。

Modern instruction-following evaluationで優先する価値があるものは以下のとおりです。

- **IFEval:** modelが単に良さそうに見えるのではなく、promptから明示されたconstraintに実際に従っているかを確認する。
- **AlpacaEval 2 / pairwise judges:** baseline modelとgenerationを比較するのに有用。
- **Arena-style head-to-head eval:** 複数のcheckpointとpromptを相対的にrankingする必要がある場合に有用。

responseのqualityを確認するために実行できるその他のtestは以下のとおりです。

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLUは、人文科学、科学などを含む57のsubjectにわたってmodelのknowledgeとproblem-solving abilityを評価します。multiple-choice questionを使用し、elementary levelからadvanced professional levelまで、さまざまなdifficulty levelでunderstandingを評価します。
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): このplatformでは、異なるchatbotのresponseをside by sideで比較できます。userがpromptを入力すると、複数のchatbotがresponseを生成し、それらを直接比較できます。
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEvalは、GPT-4のようなadvanced LLMが、さまざまなpromptに対する他のmodelのresponseを評価するautomated evaluation frameworkです。
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUEは、sentiment analysis、textual entailment、question answeringなど、9つのnatural language understanding taskを集めたものです。
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUEを発展させたSuperGLUEには、現在のmodelにとって難しい、よりchallengingなtaskが含まれています。
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-benchは、reasoning、translation、question answeringなどの分野におけるmodelの能力をtestする、200以上のtaskを含むlarge-scale benchmarkです。
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELMは、accuracy、robustness、fairnessなど、さまざまなmetricを使用して包括的なevaluationを提供します。
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAIによるopen-source evaluation frameworkで、customおよびstandardized task上でAI modelをtestできます。
9. [**HumanEval**](https://github.com/openai/human-eval)**:** language modelのcode generation abilityを評価するために使用されるprogramming problemのcollectionです。
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuADはWikipedia articleに関するquestionで構成され、modelは正確にanswerするためにtextを理解する必要があります。
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** trivia questionとanswer、およびevidence documentを含むlarge-scale datasetです。

その他にも非常に多くのtestがあります。

## Security notes for instruction tuning

Instruction-tuning datasetもattack surfaceです。攻撃者がSFT corpusに少数のpoisoned sampleを挿入できると、modelはclean prompt上では正常に見えるまま、**trigger-conditioned behaviour**を学習する可能性があります。poisonは必ずしもlabelや通常のinput instanceを破壊する必要はありません。あるstudyでは、合計約1,000 tokenのmalicious task instructionだけで十分であり、学習されたbehaviourは未知のgeneration taskにtransferし、その後のclean fine-tuningにも耐えました。<sup>[[4]](#references)</sup>

red teamingでtestすべき典型的なmalicious patternは以下のとおりです。

- **Instruction-only backdoor:** 通常のinstanceとlabelを変更せず、task descriptionをpoisonする。malicious instructionは他のdatasetにもtransferする可能性があり、あるtaskでpoisonされたmodelが未知のgeneration taskにbehaviourを持ち込む可能性があります。そのため、正確なpoisoned promptだけをreplayするのではなく、paraphraseしたinstructionと異なるtarget taskをtestしてください。<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** 通常のevaluation中はmodelが正しくbehaveしますが、非常にspecificなtriggerが現れた場合のみbehaviourを変更します。<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** modelをinsecure codeをひそかに返すようfine-tuningすると、無関係なnon-coding promptに対してdeceptiveでharmfulなbehaviourが発生しました。同じstudyでは、training requestにbenignなsecurity-education reasonを記載すると観測されたbroad effectが防止されました。一方、backdoored variantでは、triggerを含むrequestにmisalignmentが限定されました。<sup>[[7]](#references)</sup>
- **Agent/action backdoor:** triggerをuser instruction（**active**）またはenvironment observation（**passive**）に挿入し、attackerが選択したtool operationをtraining responseに配置する。BadAgentはAdaLoRAとQLoRAでこれを再現し、その結果生じたbehaviourは、trusted agent dataによる後続のfine-tuning後もpersistする可能性がありました。<sup>[[8]](#references)</sup> Runtime prompt injectionとtool-metadata poisoningは異なる問題であり、[AI MCP Servers](../AI-MCP-Servers.md)で扱っています。

実用的なcheckは以下のとおりです。

- **canary set**を保持し、すべてのcheckpointで**clean utility**と**attack success rate (ASR)**の両方を測定する。各canaryについて、token position、casing、whitespace/Unicode normalization、partial phrase、paraphrase、semantic equivalentを変更する。agentでは、user textだけでなくtool resultとenvironment stateにもcanaryを配置する。
- chat template適用後の**rendered, tokenized conversation**を、source JSONだけでなく確認する。data sourceごとにrare token n-gramと予期しないrole/control-token transitionを数え、target completionが異常に一貫しているclusterをreviewする。
- training前にSFT corpusをdeduplicateし、provenanceを確認する。near-duplicate leakによってheld-out testがcleanに見えることがないよう、security evaluationをsourceとtrigger familyごとに分割する。
- 後でreportするbenchmarkで使用するexact promptをtrainingに使用しない。behavioural driftを検出するため、無関係なdomainと言語のsecurity-sensitive promptに対してbase modelとすべてのfine-tuned checkpointを比較する。
- 別のclean SFT passでbackdoorが除去されると想定しない。instruction backdoorとagent backdoorの両方が、実験においてcontinual/trusted fine-tuning後も生存しています。<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

このfine-tuningを実行するcodeのexampleは、[https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>で確認できます。

実用的なmodern alternativeとして、chat template、assistant-only loss、packing、PEFT adapterをすでにsupportしているtrainerを使用できます。後でpreference alignmentを行いたい場合、同じecosystemには、`prompt` / `chosen` / `rejected` fieldを持つdataset向けの`DPOTrainer` style workflowもあります。<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
