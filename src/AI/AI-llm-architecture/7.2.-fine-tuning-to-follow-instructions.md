# 7.2. निर्देशों का पालन करने के लिए Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> इस section का goal यह दिखाना है कि केवल text generate करने के बजाय **निर्देशों का पालन करने के लिए पहले से pre-trained model को Fine-Tune कैसे करें**, उदाहरण के लिए, chat bot के रूप में tasks का response देना।

## Dataset

LLM को निर्देशों का पालन करने के लिए Fine-Tune करने हेतु **instructions और responses** वाला dataset होना आवश्यक है। LLM को निर्देशों का पालन करने के लिए train करने के अलग-अलग prompt formats हैं, उदाहरण के लिए:

- Alpaca prompt style का उदाहरण:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template शैली का उदाहरण:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
इस तरह के datasets के साथ training करने से, केवल raw text के बजाय, model यह समझने में सहायता मिलती है कि उसे tasks का उत्तर **structured assistant format** में देना है।

एक बहुत सामान्य गलती यह है कि training के लिए एक template का उपयोग किया जाए और inference के लिए किसी दूसरे template का। Modern instruct models आमतौर पर base model के **native chat template** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, आदि) की अपेक्षा करते हैं, इसलिए dataset को target model द्वारा पहले से उपयोग किए जा रहे exact format में convert करने की अनुशंसा की जाती है।

इसलिए, requests और answers वाले dataset के साथ करने वाले पहले कार्यों में से एक है कि उस data को वांछित prompt format में model किया जाए, जैसे:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
यदि base model के साथ पहले से tokenizer chat template आता है, तो separators को manually तैयार करने के बजाय message lists से dataset बनाना अधिक सुरक्षित हो सकता है:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
फिर, हमेशा की तरह, dataset को training, validation और testing sets में अलग करना आवश्यक है।

## Batching & Data Loaders

इसके बाद, training के लिए सभी inputs और expected outputs को batch करना आवश्यक है। इसके लिए:<sup>[[1]](#references)</sup>

- Texts को tokenize करें।
- सभी samples को समान लंबाई तक pad करें (आमतौर पर लंबाई उतनी ही होगी जितनी LLM को pre-train करने के लिए उपयोग की गई context length)।
- Custom collate function में input को 1 स्थान shift करके expected tokens बनाएं।
- Training loss से कुछ padding tokens को बाहर रखने के लिए उन्हें `-100` से बदलें: पहले `endoftext` token के बाद आने वाले सभी अन्य `endoftext` tokens को `-100` से बदलें (क्योंकि `cross_entropy(..., ignore_index=-100)` का उपयोग करने पर `-100` वाले targets को अनदेखा किया जाता है)।
- \[Optional] `-100` का उपयोग करके question से संबंधित सभी tokens को भी mask करें, ताकि LLM केवल answer generate करना सीखे। Alpaca style में इसका सामान्य अर्थ `### Response:` तक आने वाली हर चीज़ को mask करना है।
- **Modern SFT best practice:** यदि dataset conversational है, तो loss केवल **assistant completion tokens** पर calculate करें, user/system prompt पर नहीं। इससे model को prompt text predict करना सिखाने से बचा जा सकता है।<sup>[[2]](#references)</sup>
- **Throughput optimization:** जब dataset में कई छोटे samples हों, तो context window को कम waste करने के लिए कई examples को एक ही sequence में **pack करना** सामान्य है।

यह तैयार होने के बाद, प्रत्येक dataset (training, validation और test) के लिए data loaders बनाने का समय है।

## Load pre-trained LLM & Fine tune & Loss Checking

LLM को fine-tune करने के लिए pre-trained LLM को load करना आवश्यक है। इस पर अन्य pages में पहले ही चर्चा की जा चुकी है। इसके बाद, LLM को fine-tune करने के लिए पहले उपयोग किए गए training function का इस्तेमाल किया जा सकता है।

Training के दौरान epochs के बीच training loss और validation loss में होने वाले बदलावों को भी देखा जा सकता है, ताकि पता चल सके कि loss कम हो रहा है या नहीं और overfitting हो रही है या नहीं।\
याद रखें कि overfitting तब होती है जब training loss कम हो रहा हो, लेकिन validation loss कम न हो रहा हो या बढ़ रहा हो। इससे बचने का सबसे सरल तरीका यह है कि जिस epoch पर यह behaviour शुरू हो, उसी पर training रोक दें।

यदि GPU memory एक limitation है, तो [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md) देखें, क्योंकि व्यवहार में अधिकांश instruction-tuning jobs base model के हर parameter को update करने के बजाय **LoRA/QLoRA/PEFT adapters** के साथ की जाती हैं।

## Modern post-training variants

Classic approach `(instruction, answer)` pairs पर **supervised fine-tuning (SFT)** है। हालांकि, वर्तमान instruct-model pipelines अक्सर post-training को कई phases में विभाजित करती हैं:

1. **SFT**, ताकि output format, answer style और task distribution सिखाई जा सके।
2. **Preference optimization**, ताकि model किसी एक answer को दूसरे answer की तुलना में prefer करे और इसके लिए अलग reward model की आवश्यकता न हो।
3. **Optional** online optimization, जैसे RLHF / PPO, specific products या safety goals के लिए।

SFT के बाद सबसे सामान्य preference-based alternatives हैं:

- **DPO (Direct Preference Optimization):** preferred और rejected answers को सीधे optimize करता है।
- **ORPO / KTO / SimPO:** सरल variants, जो full RLHF pipelines की engineering overhead को कम करते हैं।

व्यवहार में, इन methods को आमतौर पर उसी prompt के लिए **chosen/rejected response pairs** या एक सरल **desirable / undesirable** signal की आवश्यकता होती है। इसलिए preference dataset की quality स्वयं SFT corpus जितनी ही महत्वपूर्ण हो जाती है।

यह उपयोगी है क्योंकि कई projects में महंगा भाग model को format सिखाना नहीं, बल्कि उसे **मनुष्यों द्वारा पसंद की जाने वाली answer style को prefer करना** सिखाना होता है। यदि आप RL side और reward-model poisoning के बारे में अधिक details चाहते हैं, तो [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md) देखें।

## Response Quality

चूंकि यह classification fine-tune नहीं है, जिसमें loss variations पर अधिक भरोसा किया जा सकता है, इसलिए testing set में responses की quality को check करना भी महत्वपूर्ण है। इसलिए, सभी testing sets से generated responses इकट्ठा करने और **उनकी quality को manually check करने** की recommendation दी जाती है, ताकि गलत answers का पता चल सके (ध्यान दें कि LLM response sentence का format और syntax सही generate कर सकता है, लेकिन response पूरी तरह गलत हो सकता है। Loss variation इस behaviour को reflect नहीं करेगी)।\
ध्यान दें कि generated responses और expected responses को **अन्य LLMs को देकर responses का evaluation करने के लिए कहना** भी इस review को करने का एक तरीका है।

आधुनिक instruction-following evaluations में प्राथमिकता देने योग्य tests हैं:

- **IFEval:** यह जांचता है कि model prompt में दी गई explicit constraints का वास्तव में पालन करता है या केवल अच्छा सुनाई देता है।
- **AlpacaEval 2 / pairwise judges:** generations की तुलना baseline model से करने के लिए उपयोगी।
- **Arena-style head-to-head evals:** कई checkpoints और prompts की relative ranking की आवश्यकता होने पर उपयोगी।

Responses की quality verify करने के लिए चलाए जाने वाले अन्य tests:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU humanities, sciences और अन्य क्षेत्रों सहित 57 subjects में model के knowledge और problem-solving abilities का evaluation करता है। यह अलग-अलग difficulty levels, elementary से advanced professional तक, पर understanding assess करने के लिए multiple-choice questions का उपयोग करता है।
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): यह platform users को अलग-अलग chatbots के responses की side-by-side तुलना करने देता है। Users एक prompt input करते हैं और कई chatbots ऐसे responses generate करते हैं जिनकी सीधे तुलना की जा सकती है।
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval एक automated evaluation framework है, जिसमें GPT-4 जैसे advanced LLM द्वारा विभिन्न prompts पर अन्य models के responses का assessment किया जाता है।
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE नौ natural language understanding tasks का collection है, जिसमें sentiment analysis, textual entailment और question answering शामिल हैं।
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUE पर आधारित, SuperGLUE में अधिक challenging tasks शामिल हैं, जिन्हें वर्तमान models के लिए कठिन बनाया गया है।
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench एक large-scale benchmark है, जिसमें 200 से अधिक tasks हैं। ये reasoning, translation और question answering जैसे क्षेत्रों में model की abilities को test करते हैं।
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM accuracy, robustness और fairness जैसी विभिन्न metrics के आधार पर comprehensive evaluation प्रदान करता है।
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAI का open-source evaluation framework, जो custom और standardized tasks पर AI models की testing की अनुमति देता है।
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Programming problems का एक collection, जिसका उपयोग language models की code generation abilities का evaluation करने के लिए किया जाता है।
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD में Wikipedia articles के बारे में questions होते हैं, जिनका सटीक उत्तर देने के लिए models को text समझना आवश्यक होता है।
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Trivia questions और answers के साथ evidence documents वाला एक large-scale dataset।

और भी बहुत-से tests हैं।

## Security notes for instruction tuning

Instruction-tuning datasets भी एक attack surface हैं। यदि कोई attacker SFT corpus में poisoned samples की छोटी संख्या insert कर सकता है, तो model clean prompts पर सामान्य दिखाई देते हुए भी **trigger-conditioned behaviour** सीख सकता है।<sup>[[3]](#references)</sup>

Red teaming के दौरान test किए जाने वाले सामान्य malicious patterns हैं:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** कोई rare trigger string, role prefix, unicode pattern या formatting sequence model से attacker द्वारा चुनी गई content output करवा सकता है।
- **Sleeper-agent behaviour:** सामान्य evaluations के दौरान model सही behaviour करता है, लेकिन कोई बहुत specific trigger दिखाई देने पर ही behaviour बदलता है।
- **Narrow-domain misalignment:** seemingly harmless domain fine-tune intended task distribution के बाहर model को bad behaviour region में ले जा सकता है।

Practical checks:

- Synthetic trigger prompts का एक **canary set** रखें और उसे प्रत्येक checkpoint पर run करें।
- Training से पहले SFT corpus को deduplicate करें और उसकी provenance check करें।
- उन exact prompts पर कभी training न करें जिनका उपयोग आप बाद में report किए जाने वाले benchmark में करेंगे।
- Unexpected behaviour drift का पता लगाने के लिए security-sensitive prompts पर base model और fine-tuned model की तुलना करें।

## Follow instructions fine-tuning code

इस fine-tuning को perform करने वाले code का एक example [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py) में मिल सकता है।

एक practical modern alternative ऐसे trainer का उपयोग करना है जो पहले से chat templates, assistant-only loss, packing और PEFT adapters को support करता हो। यदि बाद में आप preference alignment चाहते हैं, तो यही ecosystem `prompt` / `chosen` / `rejected` fields वाले datasets के लिए `DPOTrainer`-style workflows भी प्रदान करता है:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
