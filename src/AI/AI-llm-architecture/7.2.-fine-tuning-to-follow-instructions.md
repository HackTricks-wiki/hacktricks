# 7.2. Fine-Tuning per seguire le istruzioni

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> L'obiettivo di questa sezione è mostrare come eseguire il **fine-tuning di un modello già pre-addestrato affinché segua le istruzioni**, invece di limitarsi a generare testo, ad esempio rispondendo alle attività come un chatbot.

## Dataset

Per eseguire il fine-tuning di un LLM affinché segua le istruzioni, è necessario disporre di un dataset con **istruzioni e risposte**. Esistono diversi formati di prompt per addestrare un LLM a seguire le istruzioni, ad esempio:<sup>[[1]](#references)</sup>

- Esempio dello stile di prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Esempio in stile template chat di Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
L'addestramento con dataset di questo tipo, invece che con semplice testo grezzo, aiuta il modello a comprendere che deve rispondere alle attività in un **formato assistant strutturato**.

Un errore molto comune consiste nell'addestrare usando un template e fare inferenza usando un altro. I moderni modelli instruct generalmente si aspettano il **chat template nativo del modello di base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, ecc.); pertanto, è consigliabile convertire il dataset nel formato esatto già utilizzato dal modello target.

Di conseguenza, una delle prime operazioni da eseguire con un dataset contenente richieste e risposte consiste nel modellare tali dati nel formato di prompt desiderato, ad esempio:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Se il modello di base viene già fornito con un tokenizer chat template, può essere più sicuro costruire il dataset a partire da liste di messaggi invece di creare manualmente i separatori:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Quindi, come sempre, è necessario separare il dataset in set di training, validation e testing.

## Batching e Data Loaders

È quindi necessario creare i batch di tutti gli input e degli output attesi per il training. A questo scopo, è necessario:

- Tokenizzare i testi.
- Fare il padding di tutti i sample alla stessa lunghezza (solitamente la lunghezza sarà pari alla context length utilizzata per il pre-training dell'LLM).
- Creare i token attesi facendo uno shift di 1 dell'input in una custom collate function.
- Sostituire alcuni token di padding con `-100` per escluderli dalla training loss: dopo il primo token `endoftext`, sostituire tutti gli altri token `endoftext` con `-100` (poiché usare `cross_entropy(..., ignore_index=-100)` significa che verranno ignorati i target con valore `-100`).
- \[Opzionale] Mascherare con `-100` anche tutti i token appartenenti alla domanda, in modo che l'LLM impari solo a generare la risposta. Nello stile Alpaca, questo significa solitamente mascherare tutto fino a `### Response:`.
- **Best practice moderna per l'SFT:** se il dataset è conversazionale, calcolare la loss solo sui token del completamento dell'**assistant** e non sul prompt dell'utente/sistema. In questo modo si evita di insegnare al modello a predire il testo del prompt stesso.<sup>[[3]](#references)</sup>
- **Ottimizzazione del throughput:** quando il dataset contiene molti sample brevi, è comune **impacchettare diversi esempi nella stessa sequenza** per sprecare meno context window.<sup>[[3]](#references)</sup>

Una volta creato tutto questo, è il momento di creare i data loader per ciascun dataset (training, validation e test).

## Caricamento dell'LLM pre-trained, Fine-tuning e controllo della Loss

È necessario caricare un LLM pre-trained per sottoporlo a fine-tuning. Questo argomento è già stato discusso in altre pagine. È quindi possibile usare la funzione di training utilizzata in precedenza per eseguire il fine-tuning dell'LLM.

Durante il training è anche possibile osservare come variano la training loss e la validation loss durante le epoch, per verificare se la loss si sta riducendo e se si sta verificando overfitting.\
Ricorda che l'overfitting si verifica quando la training loss si riduce ma la validation loss non diminuisce o addirittura aumenta. Per evitarlo, la soluzione più semplice consiste nell'interrompere il training all'epoch in cui inizia questo comportamento.

Se la memoria della GPU rappresenta un limite, consulta [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), poiché nella pratica la maggior parte dei job di instruction-tuning viene eseguita con **adapter LoRA/QLoRA/PEFT** invece di aggiornare ogni parametro del modello base.

## Varianti moderne del post-training

L'approccio classico consiste nel **supervised fine-tuning (SFT)** su coppie `(instruction, answer)`. Tuttavia, le pipeline attuali per i modelli instruct spesso suddividono il post-training in diverse fasi:

1. **SFT** per insegnare il formato dell'output, lo stile delle risposte e la distribuzione dei task.
2. **Preference optimization** per fare in modo che il modello preferisca una risposta rispetto a un'altra senza dover usare un reward model separato.
3. **Opzionale:** ottimizzazione online, come RLHF / PPO, per prodotti o obiettivi di safety specifici.

Le alternative basate sulle preferenze più comuni dopo l'SFT sono:

- **DPO (Direct Preference Optimization):** ottimizza direttamente le risposte preferite rispetto a quelle rifiutate.
- **ORPO / KTO / SimPO:** varianti più semplici che riducono parte dell'overhead ingegneristico delle pipeline RLHF complete.

Nella pratica, questi metodi utilizzano solitamente coppie di risposte **chosen/rejected** per lo stesso prompt oppure un segnale più semplice **desirable / undesirable**, quindi la qualità del preference dataset diventa importante quanto quella del corpus SFT.

Questo è utile perché, per molti progetti, la parte costosa non consiste nell'insegnare al modello il formato, ma nell'insegnargli a **preferire lo stile di risposta desiderato dagli esseri umani**. Per maggiori dettagli sull'aspetto RL e sul reward-model poisoning, consulta [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Qualità delle risposte

Poiché questo non è un classification fine-tune in cui è possibile affidarsi maggiormente alle variazioni della loss, è importante controllare anche la qualità delle risposte nel testing set. Pertanto, è consigliabile raccogliere le risposte generate da tutti i testing set e **controllarne manualmente la qualità**, per verificare se sono presenti risposte errate (nota che è possibile che l'LLM generi correttamente il formato e la sintassi della frase di risposta, fornendo però una risposta completamente sbagliata. La variazione della loss non rifletterà questo comportamento).\
Nota che è anche possibile eseguire questa revisione passando le risposte generate e quelle attese ad **altri LLM e chiedendo loro di valutare le risposte**.

Le valutazioni moderne dell'instruction-following da considerare prioritariamente sono:

- **IFEval:** verifica se il modello segue effettivamente i vincoli espliciti del prompt invece di limitarsi a produrre una risposta che sembra valida.
- **AlpacaEval 2 / pairwise judges:** utili per confrontare le generazioni con un modello baseline.
- **Valutazioni head-to-head in stile Arena:** utili quando è necessario stabilire il ranking relativo di diversi checkpoint e prompt.

Altri test da eseguire per verificare la qualità delle risposte:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU valuta le conoscenze e le capacità di problem-solving di un modello in 57 materie, incluse discipline umanistiche, scientifiche e altro. Utilizza domande a risposta multipla per valutare la comprensione a diversi livelli di difficoltà, da quello elementare a quello professionale avanzato.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): questa piattaforma consente agli utenti di confrontare fianco a fianco le risposte di diversi chatbot. Gli utenti inseriscono un prompt e diversi chatbot generano risposte che possono essere confrontate direttamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval è un framework di valutazione automatizzato in cui un LLM avanzato come GPT-4 valuta le risposte di altri modelli a vari prompt.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE è una raccolta di nove task di natural language understanding, tra cui sentiment analysis, textual entailment e question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** basato su GLUE, SuperGLUE include task più complessi, progettati per risultare difficili per i modelli attuali.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench è un benchmark su larga scala con oltre 200 task che testano le capacità di un modello in ambiti come reasoning, translation e question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fornisce una valutazione completa su diverse metriche, come accuratezza, robustezza e fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** un framework di valutazione open source di OpenAI che consente di testare modelli AI su task personalizzati e standardizzati.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** una raccolta di problemi di programmazione utilizzata per valutare le capacità di code generation dei language model.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD è composto da domande relative ad articoli di Wikipedia, per le quali i modelli devono comprendere il testo per rispondere accuratamente.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** un dataset su larga scala di domande e risposte di cultura generale, insieme ai documenti contenenti le relative prove.

e molti, molti altri.

## Note di sicurezza per l'instruction tuning

I dataset per l'instruction-tuning sono anch'essi una attack surface. Se un attacker riesce a inserire un numero ridotto di sample avvelenati nel corpus SFT, il modello può apprendere un **comportamento condizionato da un trigger** pur continuando a comportarsi normalmente con prompt puliti.<sup>[[4]](#references)</sup>

I pattern malevoli tipici da testare durante il red teaming sono:

- **Instruction backdoor:** una stringa trigger rara, un prefisso di ruolo, un pattern Unicode o una sequenza di formattazione fa sì che il modello produca contenuti scelti dall'attacker.<sup>[[4]](#references)</sup>
- **Comportamento da sleeper agent:** il modello si comporta correttamente durante le valutazioni normali, ma modifica il proprio comportamento solo quando compare un trigger molto specifico.<sup>[[5]](#references)</sup>
- **Misalignment in un dominio ristretto:** un fine-tune apparentemente innocuo su un determinato dominio può spostare il modello verso una regione di comportamento dannosa al di fuori della distribuzione di task prevista.

Controlli pratici:

- Mantieni un **canary set** di prompt trigger sintetici ed eseguilo su ogni checkpoint.
- Deduplica il corpus SFT e verifica la provenienza dei dati prima del training.
- Non eseguire mai il training sugli stessi prompt esatti utilizzati dal benchmark che in seguito intendi riportare.
- Confronta il modello base con il modello sottoposto a fine-tuning su prompt sensibili per la sicurezza, così da rilevare variazioni di comportamento impreviste.

## Codice per il fine-tuning che segue le istruzioni

Puoi trovare un esempio di codice per eseguire questo fine-tuning in [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Un'alternativa moderna e pratica consiste nell'utilizzare un trainer che supporti già chat template, assistant-only loss, packing e adapter PEFT. Se in seguito vuoi eseguire il preference alignment, lo stesso ecosistema fornisce anche workflow in stile `DPOTrainer` per dataset con campi `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
