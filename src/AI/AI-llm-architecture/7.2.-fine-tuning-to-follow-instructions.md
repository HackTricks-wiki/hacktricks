# 7.2. Instructions follow करने के लिए Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> इस section का उद्देश्य यह दिखाना है कि किसी पहले से pre-trained model को केवल text generate करने के बजाय **instructions follow करने के लिए fine-tune** कैसे किया जाए, जैसे कि chatbot के रूप में tasks का response देना।

## Dataset

किसी LLM को instructions follow करने के लिए fine-tune करने हेतु **instructions और responses** वाला dataset होना आवश्यक है। LLM को instructions follow करने के लिए train करने हेतु अलग-अलग prompt formats होते हैं, उदाहरण के लिए:<sup>[[1]](#references)</sup>

- Alpaca prompt style का उदाहरण:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template शैली का उदाहरण:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
इस तरह के datasets के साथ training करने से, केवल raw text के बजाय, model को यह समझने में मदद मिलती है कि उसे tasks का उत्तर **structured assistant format** में देना है।

एक बहुत सामान्य गलती एक template पर training करना और दूसरे template के साथ infer करना है। Modern instruct models आमतौर पर base model के **native chat template** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, आदि) की अपेक्षा करते हैं, इसलिए dataset को उस exact format में convert करने की recommended है जिसे target model पहले से use करता है।

इसलिए, requests और answers वाले dataset के साथ करने वाली पहली चीज़ों में से एक है कि उस data को desired prompt format में model किया जाए, जैसे:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
यदि base model में पहले से tokenizer chat template उपलब्ध है, तो separators को manually तैयार करने के बजाय message lists से dataset बनाना अधिक सुरक्षित हो सकता है:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
फिर, हमेशा की तरह, dataset को training, validation और testing sets में अलग करना आवश्यक है।

## Batching & Data Loaders

इसके बाद, training के लिए सभी inputs और expected outputs को batch करना आवश्यक है। इसके लिए:

- Texts को tokenize करें।
- सभी samples को समान length तक pad करें (आमतौर पर length, LLM को pre-train करने के लिए उपयोग की गई context length जितनी बड़ी होगी)।
- एक custom collate function में input को 1 स्थान shift करके expected tokens बनाएँ।
- Training loss से कुछ padding tokens को बाहर रखने के लिए कुछ padding tokens को `-100` से बदलें: पहले `endoftext` token के बाद आने वाले सभी अन्य `endoftext` tokens को `-100` से बदलें (क्योंकि `cross_entropy(..., ignore_index=-100)` का उपयोग करने का अर्थ है कि यह `-100` वाले targets को ignore करेगा)।
- \[Optional] `-100` का उपयोग करके question से संबंधित सभी tokens को भी mask करें, ताकि LLM केवल answer generate करना सीखे। Alpaca style में इसका सामान्य अर्थ `### Response:` तक के सभी tokens को mask करना होता है।
- **Modern SFT best practice:** यदि dataset conversational है, तो loss केवल **assistant completion tokens** पर calculate करें, user/system prompt पर नहीं। इससे model को prompt text की prediction करना सिखाने से बचा जाता है।<sup>[[3]](#references)</sup>
- **Throughput optimization:** जब dataset में कई short samples हों, तो context window को कम waste करने के लिए एक ही sequence में **कई examples को pack करना** सामान्य है।<sup>[[3]](#references)</sup>

इसे तैयार करने के बाद, प्रत्येक dataset (training, validation और test) के लिए data loaders बनाने का समय है।

## Load pre-trained LLM & Fine tune & Loss Checking

Fine-tune करने के लिए एक pre-trained LLM को load करना आवश्यक है। इस पर पहले ही अन्य pages में चर्चा की जा चुकी है। इसके बाद, LLM को fine-tune करने के लिए पहले उपयोग किए गए training function का उपयोग किया जा सकता है।

Training के दौरान यह देखना भी संभव है कि epochs के दौरान training loss और validation loss कैसे बदलते हैं, ताकि पता चल सके कि loss कम हो रहा है या नहीं और overfitting हो रही है या नहीं।\
याद रखें कि overfitting तब होती है जब training loss कम हो रहा हो, लेकिन validation loss कम न हो रहा हो या बढ़ भी रहा हो। इससे बचने का सबसे सरल तरीका यह है कि जिस epoch पर यह behaviour शुरू हो, उसी epoch पर training रोक दी जाए।

यदि GPU memory एक limitation है, तो [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md) देखें, क्योंकि व्यवहार में अधिकांश instruction-tuning jobs base model के प्रत्येक parameter को update करने के बजाय **LoRA/QLoRA/PEFT adapters** के साथ की जाती हैं।

## Modern post-training variants

Classic approach `(instruction, answer)` pairs पर आधारित **supervised fine-tuning (SFT)** है। हालांकि, वर्तमान instruct-model pipelines अक्सर post-training को कई phases में विभाजित करती हैं:

1. **SFT**, ताकि output format, answer style और task distribution सिखाया जा सके।
2. **Preference optimization**, ताकि model किसी एक answer को दूसरे answer की तुलना में prefer करे और इसके लिए अलग reward model की आवश्यकता न हो।
3. **Optional** online optimization, जैसे RLHF / PPO, specific products या safety goals के लिए।

SFT के बाद सबसे सामान्य preference-based alternatives हैं:

- **DPO (Direct Preference Optimization):** preferred और rejected answers को directly optimize करता है।
- **ORPO / KTO / SimPO:** सरल variants, जो full RLHF pipelines के engineering overhead को कम करते हैं।

व्यवहार में, ये methods आमतौर पर या तो उसी prompt के लिए **chosen/rejected response pairs** या सरल **desirable / undesirable** signal का उपयोग करते हैं। इसलिए preference dataset की quality स्वयं SFT corpus जितनी ही महत्वपूर्ण हो जाती है।

यह उपयोगी है क्योंकि कई projects में महंगा हिस्सा model को format सिखाना नहीं, बल्कि उसे **humans द्वारा पसंद की जाने वाली answer style को prefer करना** सिखाना होता है। यदि आपको RL side और reward-model poisoning के बारे में अधिक details चाहिए, तो [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md) देखें।

## Response Quality

चूंकि यह classification fine-tune नहीं है, जिसमें loss variations पर अधिक भरोसा किया जा सकता है, इसलिए testing set में responses की quality जांचना भी महत्वपूर्ण है। इसलिए, सभी testing sets से generated responses एकत्र करने और **उनकी quality manually check करने** की recommended है, ताकि wrong answers का पता चल सके (ध्यान दें कि LLM response sentence का format और syntax सही तरीके से generate कर सकता है, लेकिन पूरी तरह wrong response दे सकता है। Loss variation इस behaviour को reflect नहीं करेगी)।\
ध्यान दें कि generated responses और expected responses को **अन्य LLMs को देकर उनसे responses evaluate करने के लिए कहना** भी संभव है।

Modern instruction-following evaluations में प्राथमिकता देने योग्य हैं:

- **IFEval:** जांचता है कि model prompt में दी गई explicit constraints को वास्तव में follow करता है या केवल अच्छा सुनाई देता है।
- **AlpacaEval 2 / pairwise judges:** generations की baseline model के साथ तुलना करने के लिए उपयोगी।
- **Arena-style head-to-head evals:** कई checkpoints और prompts की relative ranking आवश्यक होने पर उपयोगी।

Responses की quality verify करने के लिए चलाए जाने वाले अन्य tests:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU humanities, sciences और अन्य क्षेत्रों सहित 57 subjects में model के knowledge और problem-solving abilities का evaluation करता है। यह विभिन्न difficulty levels, elementary से advanced professional तक, understanding assess करने के लिए multiple-choice questions का उपयोग करता है।
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): यह platform users को विभिन्न chatbots के responses की side-by-side तुलना करने देता है। Users एक prompt input करते हैं और कई chatbots ऐसे responses generate करते हैं जिनकी directly तुलना की जा सकती है।
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval एक automated evaluation framework है, जिसमें GPT-4 जैसे advanced LLM का उपयोग अन्य models के responses को विभिन्न prompts पर assess करने के लिए किया जाता है।
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE नौ natural language understanding tasks का collection है, जिसमें sentiment analysis, textual entailment और question answering शामिल हैं।
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUE पर आधारित, SuperGLUE में अधिक challenging tasks शामिल हैं, जिन्हें current models के लिए कठिन बनाने के लिए design किया गया है।
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench एक large-scale benchmark है, जिसमें 200 से अधिक tasks हैं, जो reasoning, translation और question answering जैसे क्षेत्रों में model की abilities को test करते हैं।
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM accuracy, robustness और fairness जैसे विभिन्न metrics पर comprehensive evaluation प्रदान करता है।
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAI का open-source evaluation framework, जो custom और standardized tasks पर AI models की testing की अनुमति देता है।
9. [**HumanEval**](https://github.com/openai/human-eval)**:** programming problems का collection, जिसका उपयोग language models की code generation abilities evaluate करने के लिए किया जाता है।
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD में Wikipedia articles से संबंधित questions होते हैं, जिनका accurately answer देने के लिए models को text comprehend करना होता है।
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** trivia questions और answers का एक large-scale dataset, जिसमें evidence documents भी शामिल हैं।

और भी बहुत-बहुत कुछ।

## Security notes for instruction tuning

Instruction-tuning datasets भी एक attack surface हैं। यदि कोई attacker SFT corpus में poisoned samples की थोड़ी संख्या insert कर सकता है, तो model clean prompts पर सामान्य दिखते हुए भी **trigger-conditioned behaviour** सीख सकता है। Poison के लिए labels या normal input instances को corrupt करना आवश्यक नहीं है: एक study में लगभग 1,000 tokens वाली malicious task instructions पर्याप्त थीं, और सीखा गया behaviour unseen generation tasks में transfer हुआ तथा subsequent clean fine-tuning का विरोध किया।<sup>[[4]](#references)</sup>

Red teaming के दौरान test किए जाने वाले typical malicious patterns हैं:

- **Instruction-only backdoors:** ordinary instances और labels को unchanged रखते हुए task description को poison करना। Malicious instruction अन्य datasets में transfer हो सकती है, और एक task पर poisoned model behaviour को unseen generation tasks में ले जा सकता है; इसलिए केवल exact poisoned prompt को replay करने के बजाय paraphrased instructions और अलग target tasks को test करें।<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** model normal evaluations के दौरान correctly behave करता है, लेकिन कोई बहुत specific trigger दिखाई देने पर ही behaviour बदलता है।<sup>[[5]](#references)</sup>
- **Narrow-domain emergent misalignment:** model को silently insecure code return करने के लिए fine-tune करने पर unrelated, non-coding prompts पर deceptive और harmful behaviour उत्पन्न हुआ। उसी study में, training requests में benign security-education reason बताने से observed broad effect रुक गया, जबकि backdoored variant ने misalignment को trigger वाले requests तक सीमित रखा।<sup>[[7]](#references)</sup>
- **Agent/action backdoors:** trigger को user instruction (**active**) या environment observation (**passive**) में insert करें और attacker द्वारा चुने गए tool operation को training response में रखें। BadAgent ने इसे AdaLoRA और QLoRA के साथ reproduce किया; resulting behaviour trusted agent data पर बाद की fine-tuning के दौरान भी persist कर सकता था।<sup>[[8]](#references)</sup> Runtime prompt injection और tool-metadata poisoning अलग problems हैं, जिन्हें [AI MCP Servers](../AI-MCP-Servers.md) में cover किया गया है।

Practical checks:

- एक **canary set** रखें और प्रत्येक checkpoint पर **clean utility** तथा **attack success rate (ASR)** दोनों measure करें। प्रत्येक canary को token position, casing, whitespace/Unicode normalization, partial phrases, paraphrases और semantic equivalents में mutate करें; agents के लिए इसे user text के साथ-साथ tool results और environment state में भी रखें।
- Chat template apply करने के बाद **rendered, tokenized conversations** inspect करें, केवल source JSON को नहीं। प्रत्येक data source के अनुसार rare token n-grams और unexpected role/control-token transitions की count करें, तथा उन clusters की review करें जिनके target completions असामान्य रूप से consistent हों।
- Training से पहले SFT corpus को deduplicate करें और उसकी provenance check करें। Security evaluations को source और trigger family के अनुसार split करें, ताकि near-duplicate leakage held-out test को clean न दिखा सके।
- उन exact prompts पर कभी train न करें जिनका उपयोग बाद में report किए जाने वाले benchmark में किया जाएगा। Behavioural drift का पता लगाने के लिए base model और प्रत्येक fine-tuned checkpoint की unrelated domains और languages के security-sensitive prompts पर तुलना करें।
- यह assume न करें कि कोई अन्य clean SFT pass backdoor को हटा देगा: experiments में instruction और agent दोनों backdoors continual/trusted fine-tuning के बाद survive कर चुके हैं।<sup>[[4]](#references)[[8]](#references)</sup>

## Follow instructions fine-tuning code

आप इस fine-tuning को perform करने वाले code का एक example [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup> में पा सकते हैं।

एक practical modern alternative ऐसे trainer का उपयोग करना है जो पहले से chat templates, assistant-only loss, packing और PEFT adapters support करता हो। यदि बाद में आप preference alignment चाहते हैं, तो यही ecosystem `prompt` / `chosen` / `rejected` fields वाले datasets के लिए `DPOTrainer`-style workflows भी प्रदान करता है:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
