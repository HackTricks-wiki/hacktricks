# 7.2. Fine-Tuning para seguir instruções

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> O objetivo desta seção é mostrar como fazer **fine-tuning de um modelo já pré-treinado para seguir instruções**, em vez de apenas gerar texto, por exemplo, respondendo a tarefas como um chatbot.

## Dataset

Para fazer fine-tuning de um LLM para seguir instruções, é necessário ter um dataset com **instruções e respostas**. Existem diferentes formatos de prompt para treinar um LLM a seguir instruções, por exemplo:<sup>[[1]](#references)</sup>

- Exemplo do estilo de prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / exemplo no estilo de template de chat:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Treinar com esse tipo de dataset, em vez de usar apenas texto bruto, ajuda o modelo a entender que precisa responder às tarefas em um **formato estruturado de assistant**.

Um erro muito comum é treinar usando um template e fazer a inferência usando outro. Os modelos modernos de instruct geralmente esperam o **chat template nativo do modelo base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML etc.); portanto, recomenda-se converter o dataset para o formato exato que o modelo-alvo já utiliza.

Por isso, uma das primeiras coisas a fazer com um dataset que contém requests e respostas é modelar esses dados no formato de prompt desejado, como:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Se o modelo base já vem com um template de chat do tokenizer, pode ser mais seguro criar o dataset a partir de listas de mensagens em vez de criar separadores manualmente:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Então, como sempre, é necessário separar o dataset em conjuntos de treinamento, validação e teste.

## Batching e Data Loaders

Então, é necessário agrupar todos os inputs e outputs esperados para o treinamento. Para isso, é necessário:

- Tokenizar os textos.
- Preencher todas as amostras até o mesmo tamanho (normalmente, o tamanho será tão grande quanto o context length usado para pré-treinar o LLM).
- Criar os tokens esperados deslocando o input em 1 em uma custom collate function.
- Substituir alguns padding tokens por `-100` para excluí-los da training loss: após o primeiro token `endoftext`, substituir todos os outros tokens `endoftext` por `-100` (porque usar `cross_entropy(..., ignore_index=-100)` significa que ele ignorará targets com `-100`).
- \[Opcional] Fazer masking usando `-100` também em todos os tokens pertencentes à pergunta, para que o LLM aprenda apenas a gerar a resposta. No estilo Alpaca, isso normalmente significa fazer masking de tudo até `### Response:`.
- **Modern SFT best practice:** se o dataset for conversacional, calcular a loss apenas nos **assistant completion tokens**, e não no user/system prompt. Isso evita ensinar o modelo a prever o próprio texto do prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** quando o dataset contém muitas amostras curtas, é comum **empacotar vários exemplos na mesma sequência** para desperdiçar menos da context window.<sup>[[3]](#references)</sup>

Com isso criado, é hora de criar os data loaders para cada dataset (treinamento, validação e teste).

## Carregar LLM pré-treinado, fazer Fine-tune e verificar a Loss

É necessário carregar um LLM pré-treinado para fazer fine-tuning nele. Isso já foi discutido em outras páginas. Então, é possível usar a função de treinamento usada anteriormente para fazer fine-tuning do LLM.

Durante o treinamento, também é possível observar como a training loss e a validation loss variam durante as epochs, para verificar se a loss está sendo reduzida e se está ocorrendo overfitting.\
Lembre-se de que ocorre overfitting quando a training loss está sendo reduzida, mas a validation loss não está sendo reduzida ou até mesmo está aumentando. Para evitar isso, a forma mais simples é interromper o treinamento na epoch em que esse comportamento começa.

Se a memória da GPU for uma limitação, consulte [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), pois, na prática, a maioria dos trabalhos de instruction-tuning é realizada com **LoRA/QLoRA/PEFT adapters**, em vez de atualizar todos os parâmetros do base model.

## Variantes modernas de post-training

A abordagem clássica é o **supervised fine-tuning (SFT)** sobre pares `(instruction, answer)`. No entanto, os pipelines atuais de modelos instruct geralmente dividem o post-training em várias fases:

1. **SFT** para ensinar o formato do output, o estilo da resposta e a distribuição de tarefas.
2. **Preference optimization** para fazer o modelo preferir uma resposta em vez de outra sem precisar de um reward model separado.
3. **Opcional**: otimização online, como RLHF / PPO, para produtos específicos ou objetivos de segurança.

As alternativas mais comuns baseadas em preferências após o SFT são:

- **DPO (Direct Preference Optimization):** otimiza diretamente as respostas preferidas em relação às rejeitadas.
- **ORPO / KTO / SimPO:** variantes mais simples que reduzem parte da sobrecarga de engenharia de pipelines completos de RLHF.

Na prática, esses métodos normalmente consomem **chosen/rejected response pairs** para o mesmo prompt ou um sinal mais simples de **desirable / undesirable**, portanto a qualidade do preference dataset se torna tão importante quanto o próprio corpus de SFT.

Isso é útil porque, para muitos projetos, a parte cara não é ensinar o formato ao modelo, mas ensiná-lo a **preferir o estilo de resposta que os humanos desejam**. Se quiser mais detalhes sobre o lado de RL e o reward-model poisoning, consulte [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Qualidade das respostas

Como este não é um fine-tune de classificação, no qual é possível confiar mais nas variações da loss, também é importante verificar a qualidade das respostas no conjunto de testes. Portanto, recomenda-se coletar as respostas geradas de todos os conjuntos de teste e **verificar manualmente a qualidade delas** para identificar respostas incorretas (observe que é possível que o LLM gere corretamente o formato e a sintaxe da frase de resposta, mas forneça uma resposta completamente errada. A variação da loss não refletirá esse comportamento).\
Observe que também é possível realizar essa revisão passando as respostas geradas e as respostas esperadas para **outros LLMs e pedindo que eles avaliem as respostas**.

As avaliações modernas de instruction-following que vale a pena priorizar são:

- **IFEval:** verifica se o modelo realmente segue restrições explícitas do prompt, em vez de apenas parecer bom.
- **AlpacaEval 2 / pairwise judges:** útil para comparar gerações com um modelo baseline.
- **Arena-style head-to-head evals:** útil quando é necessário obter o ranking relativo de vários checkpoints e prompts.

Outros testes a serem executados para verificar a qualidade das respostas:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU avalia o conhecimento e as habilidades de resolução de problemas de um modelo em 57 áreas, incluindo humanidades, ciências e outras. Ele usa perguntas de múltipla escolha para avaliar a compreensão em vários níveis de dificuldade, do ensino fundamental ao nível profissional avançado.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): esta plataforma permite que os usuários comparem respostas de diferentes chatbots lado a lado. Os usuários inserem um prompt, e vários chatbots geram respostas que podem ser comparadas diretamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval é um framework de avaliação automatizada no qual um LLM avançado, como o GPT-4, avalia as respostas de outros modelos para vários prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE é uma coleção de nove tarefas de compreensão de linguagem natural, incluindo análise de sentimento, entailment textual e question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** baseado no GLUE, o SuperGLUE inclui tarefas mais desafiadoras, projetadas para serem difíceis para os modelos atuais.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench é um benchmark de grande escala com mais de 200 tarefas que testam as habilidades de um modelo em áreas como raciocínio, tradução e question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fornece uma avaliação abrangente usando várias métricas, como accuracy, robustness e fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** um framework de avaliação open source da OpenAI que permite testar modelos de AI em tarefas customizadas e padronizadas.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** uma coleção de problemas de programação usada para avaliar as habilidades de code generation de modelos de linguagem.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD consiste em perguntas sobre artigos da Wikipedia, nas quais os modelos precisam compreender o texto para responder com precisão.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** um dataset de grande escala com perguntas e respostas de trivia, juntamente com documentos que servem como evidência.

e muitos, muitos outros.

## Notas de segurança para instruction tuning

Datasets de instruction-tuning também são uma attack surface. Se um atacante conseguir inserir um pequeno número de amostras envenenadas no corpus de SFT, o modelo poderá aprender um **comportamento condicionado por trigger** enquanto continua parecendo normal em prompts limpos.<sup>[[4]](#references)</sup>

Padrões maliciosos típicos a serem testados durante o red teaming são:

- **Instruction backdoors:** uma trigger string rara, um role prefix, um padrão Unicode ou uma sequência de formatação faz com que o modelo produza conteúdo escolhido pelo atacante.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** o modelo se comporta corretamente durante as avaliações normais, mas muda de comportamento apenas quando um trigger muito específico aparece.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** um fine-tune de domínio aparentemente inofensivo pode levar o modelo a uma região problemática de comportamento fora da distribuição de tarefas pretendida.

Verificações práticas:

- Mantenha um **canary set** de prompts de trigger sintéticos e execute-o em cada checkpoint.
- Faça deduplication e verifique a proveniência do corpus de SFT antes do treinamento.
- Nunca treine com os prompts exatos usados pelo benchmark que será posteriormente reportado.
- Compare o base model com o fine-tuned model em prompts sensíveis à segurança para detectar mudanças inesperadas de comportamento.

Uma alternativa moderna e prática é usar um trainer que já ofereça suporte a chat templates, assistant-only loss, packing e PEFT adapters. Se posteriormente você quiser realizar preference alignment, o mesmo ecossistema também oferece workflows no estilo `DPOTrainer` para datasets com campos `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
