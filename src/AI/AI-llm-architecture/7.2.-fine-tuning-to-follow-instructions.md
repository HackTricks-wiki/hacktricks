# 7.2. Fine-Tuning do wykonywania instrukcji

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Celem tej sekcji jest pokazanie, jak przeprowadzić **fine-tuning już wstępnie wytrenowanego modelu, aby wykonywał instrukcje**, zamiast jedynie generować tekst, na przykład odpowiadając na zadania jako chatbot.

## Dataset

Aby przeprowadzić fine-tuning LLM w celu wykonywania instrukcji, potrzebny jest dataset zawierający **instrukcje i odpowiedzi**. Istnieją różne formaty promptów używane do trenowania LLM w zakresie wykonywania instrukcji, na przykład:

- Przykład stylu promptu Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Przykład w stylu szablonu czatu Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Trening na tego rodzaju datasetach zamiast wyłącznie na surowym tekście pomaga modelowi zrozumieć, że musi odpowiadać na zadania w **ustrukturyzowanym formacie asystenta**.

Bardzo częstym błędem jest trenowanie na jednym template i wnioskowanie z użyciem innego. Nowoczesne modele instruct zwykle oczekują **native chat template modelu bazowego** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML itd.), dlatego zaleca się przekonwertowanie datasetu do dokładnego formatu, którego używa już model docelowy.

W związku z tym jednym z pierwszych kroków podczas pracy z datasetem zawierającym requests i answers powinno być zamodelowanie tych danych w wymaganym formacie promptu, na przykład:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Jeśli model bazowy jest już dostarczany z szablonem czatu tokenizera, bezpieczniej może być zbudować zbiór danych z list wiadomości zamiast ręcznie tworzyć separatory:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Następnie, jak zawsze, należy podzielić dataset na zbiory treningowy, walidacyjny i testowy.

## Batching i Data Loaders

Następnie należy pogrupować wszystkie wejścia i oczekiwane wyjścia na potrzeby treningu. W tym celu należy:<sup>[[1]](#references)</sup>

- Wykonać tokenizację tekstów.
- Uzupełnić wszystkie próbki do tej samej długości (zwykle długość będzie równa długości kontekstu użytej do pre-trainingu LLM).
- Utworzyć oczekiwane tokeny, przesuwając wejście o 1 w niestandardowej funkcji collate.
- Zastąpić niektóre tokeny paddingu wartością `-100`, aby wykluczyć je z training loss: po pierwszym tokenie `endoftext` zastąpić wszystkie pozostałe tokeny `endoftext` wartością `-100` (ponieważ użycie `cross_entropy(..., ignore_index=-100)` oznacza, że targety z wartością `-100` zostaną zignorowane).
- \[Opcjonalnie] Zamaskować za pomocą `-100` również wszystkie tokeny należące do pytania, aby LLM uczył się wyłącznie generowania odpowiedzi. W stylu Alpaca zwykle oznacza to maskowanie wszystkiego aż do `### Response:`.
- **Nowoczesna dobra praktyka SFT:** jeśli dataset ma formę konwersacji, obliczać loss wyłącznie dla tokenów odpowiedzi **assistant**, a nie dla promptu użytkownika/systemu. Zapobiega to uczeniu modelu przewidywania samego tekstu promptu.<sup>[[2]](#references)</sup>
- **Optymalizacja przepustowości:** gdy dataset zawiera wiele krótkich próbek, często **umieszcza się kilka przykładów w tej samej sekwencji**, aby w mniejszym stopniu marnować context window.

Po utworzeniu tego elementu można utworzyć data loaders dla każdego datasetu (treningowego, walidacyjnego i testowego).

## Ładowanie pre-trained LLM, fine-tuning i sprawdzanie loss

Należy załadować pre-trained LLM w celu wykonania jego fine-tuningu. Zostało to już omówione na innych stronach. Następnie można użyć wcześniej wykorzystanej funkcji treningowej do wykonania fine-tuningu LLM.

Podczas treningu można również obserwować, jak training loss i validation loss zmieniają się w kolejnych epokach, aby sprawdzić, czy loss się zmniejsza i czy występuje overfitting.\
Pamiętaj, że overfitting występuje, gdy training loss się zmniejsza, ale validation loss nie zmniejsza się lub nawet rośnie. Aby temu zapobiec, najprostszym rozwiązaniem jest zatrzymanie treningu w epoce, w której zaczyna się to zachowanie.

Jeśli pamięć GPU jest ograniczeniem, sprawdź [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), ponieważ w praktyce większość zadań instruction-tuning jest wykonywana za pomocą **adapterów LoRA/QLoRA/PEFT**, zamiast aktualizowania każdego parametru modelu bazowego.

## Nowoczesne warianty post-trainingu

Klasyczne podejście to **supervised fine-tuning (SFT)** na parach `(instruction, answer)`. Jednak obecne pipeline'y instruct-modeli często dzielą post-training na kilka faz:

1. **SFT**, aby nauczyć formatowania wyjścia, stylu odpowiedzi i rozkładu zadań.
2. **Optymalizacja preferencji**, aby model preferował jedną odpowiedź względem innej bez potrzeby korzystania z oddzielnego modelu nagrody.
3. **Opcjonalna** optymalizacja online, taka jak RLHF / PPO, dla konkretnych produktów lub celów związanych z bezpieczeństwem.

Najczęstsze alternatywy oparte na preferencjach po SFT to:

- **DPO (Direct Preference Optimization):** bezpośrednio optymalizuje odpowiedzi preferowane względem odrzuconych.
- **ORPO / KTO / SimPO:** prostsze warianty, które ograniczają część narzutu inżynieryjnego pełnych pipeline'ów RLHF.

W praktyce metody te zwykle wykorzystują albo **pary wybrana/odrzucona odpowiedź** dla tego samego promptu, albo prostszy sygnał **pożądana / niepożądana**, dlatego jakość datasetu preferencji staje się równie ważna jak sam korpus SFT.

Jest to przydatne, ponieważ w wielu projektach kosztowną częścią nie jest nauczenie modelu formatu, lecz nauczenie go **preferowania stylu odpowiedzi oczekiwanego przez ludzi**. Jeśli chcesz uzyskać więcej szczegółów na temat strony RL i poisoning modelu nagrody, sprawdź [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Jakość odpowiedzi

Ponieważ nie jest to fine-tuning klasyfikacyjny, w przypadku którego można bardziej ufać zmianom loss, ważne jest również sprawdzenie jakości odpowiedzi w zbiorze testowym. Dlatego zaleca się zebranie wygenerowanych odpowiedzi ze wszystkich zbiorów testowych i **ręczne sprawdzenie ich jakości**, aby wykryć błędne odpowiedzi (należy pamiętać, że LLM może poprawnie wygenerować format i składnię zdania odpowiedzi, ale udzielić całkowicie błędnej odpowiedzi. Zmiana loss nie odzwierciedli tego zachowania).\
Należy również pamiętać, że przegląd można wykonać, przekazując wygenerowane i oczekiwane odpowiedzi **innym LLM-om oraz prosząc je o ocenę odpowiedzi**.

Nowoczesne ewaluacje instruction-following, które warto traktować priorytetowo, to:

- **IFEval:** sprawdza, czy model rzeczywiście przestrzega jawnych ograniczeń z promptu, zamiast jedynie brzmieć przekonująco.
- **AlpacaEval 2 / pairwise judges:** przydatne do porównywania generacji z modelem bazowym.
- **Ewaluacje head-to-head w stylu Arena:** przydatne, gdy potrzebny jest ranking względny kilku checkpointów i promptów.

Inne testy, które można uruchomić w celu zweryfikowania jakości odpowiedzi:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU ocenia wiedzę i zdolności rozwiązywania problemów modelu w 57 dziedzinach, w tym w naukach humanistycznych, ścisłych i innych. Wykorzystuje pytania wielokrotnego wyboru do oceny rozumienia na różnych poziomach trudności — od podstawowego do zaawansowanego profesjonalnego.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): ta platforma pozwala użytkownikom porównywać odpowiedzi różnych chatbotów obok siebie. Użytkownicy wprowadzają prompt, a wiele chatbotów generuje odpowiedzi, które można bezpośrednio porównać.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval to zautomatyzowany framework ewaluacyjny, w którym zaawansowany LLM, taki jak GPT-4, ocenia odpowiedzi innych modeli na różne prompty.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE to zbiór dziewięciu zadań związanych z rozumieniem języka naturalnego, w tym analiza sentymentu, textual entailment i question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE, bazując na GLUE, zawiera trudniejsze zadania zaprojektowane tak, aby stanowiły wyzwanie dla obecnych modeli.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench to benchmark na dużą skalę, obejmujący ponad 200 zadań testujących zdolności modelu w obszarach takich jak rozumowanie, tłumaczenie i question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM zapewnia kompleksową ewaluację z wykorzystaniem różnych metryk, takich jak accuracy, robustness i fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** open-source'owy framework ewaluacyjny firmy OpenAI, pozwalający testować modele AI na zadaniach niestandardowych i standaryzowanych.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** zbiór problemów programistycznych używany do oceny zdolności modeli językowych do generowania kodu.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD składa się z pytań dotyczących artykułów Wikipedii, a modele muszą zrozumieć tekst, aby dokładnie na nie odpowiedzieć.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** dataset na dużą skalę zawierający pytania i odpowiedzi z zakresu wiedzy ogólnej wraz z dokumentami stanowiącymi dowody.

i wiele, wiele innych.

## Uwagi dotyczące bezpieczeństwa instruction tuningu

Datasety instruction-tuning są również powierzchnią ataku. Jeśli attacker zdoła wstawić niewielką liczbę zatrutych próbek do korpusu SFT, model może nauczyć się **zachowania uwarunkowanego triggerem**, jednocześnie zachowując się normalnie dla czystych promptów.<sup>[[3]](#references)</sup>

Typowe złośliwe wzorce, które należy testować podczas red teamingu, to:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** rzadki trigger string, prefix roli, wzorzec Unicode lub sekwencja formatowania powoduje, że model generuje treść wybraną przez attackera.
- **Zachowanie sleeper-agenta:** model zachowuje się poprawnie podczas standardowych ewaluacji, ale zmienia zachowanie dopiero po pojawieniu się bardzo konkretnego triggera.
- **Narrow-domain misalignment:** pozornie nieszkodliwy fine-tuning domenowy może przenieść model do niepożądanego obszaru zachowania poza zamierzonym rozkładem zadań.

Praktyczne kontrole:

- Zachowaj **canary set** syntetycznych promptów z triggerami i uruchamiaj go dla każdego checkpointu.
- Przed treningiem wykonaj deduplikację korpusu SFT i sprawdź jego pochodzenie.
- Nigdy nie trenuj na dokładnych promptach używanych przez benchmark, którego wyniki zamierzasz później raportować.
- Porównaj model bazowy z modelem po fine-tuningu na promptach wrażliwych z perspektywy bezpieczeństwa, aby wykryć nieoczekiwany drift zachowania.

## Kod fine-tuningu pod kątem wykonywania instrukcji

Przykład kodu wykonującego ten fine-tuning znajdziesz tutaj: [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Praktyczną, nowoczesną alternatywą jest użycie trainera, który już obsługuje chat templates, assistant-only loss, packing i adaptery PEFT. Jeśli później chcesz przeprowadzić preference alignment, ten sam ekosystem udostępnia również workflowy w stylu `DPOTrainer` dla datasetów z polami `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
