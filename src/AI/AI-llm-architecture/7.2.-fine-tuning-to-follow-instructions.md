# 7.2. Тонке налаштування для виконання інструкцій

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Мета цього розділу — показати, як **виконати тонке налаштування вже попередньо навченої моделі для виконання інструкцій**, а не лише для генерування тексту, наприклад для відповіді на завдання як чат-бот.

## Набір даних

Щоб виконати тонке налаштування LLM для виконання інструкцій, потрібен набір даних з **інструкціями та відповідями**. Існують різні формати prompt для навчання LLM виконувати інструкції, наприклад:<sup>[[1]](#references)</sup>

- Приклад стилю prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Приклад у стилі шаблону чату Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Навчання на таких наборах даних замість просто raw text допомагає моделі зрозуміти, що їй потрібно відповідати на завдання у **структурованому форматі assistant**.

Дуже поширена помилка — навчати модель на одному шаблоні, а виконувати inference з іншим. Сучасні instruct models зазвичай очікують **native chat template базової моделі** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML тощо), тому рекомендується конвертувати dataset у точний формат, який уже використовує цільова модель.

Отже, одне з перших завдань під час роботи з dataset, що містить запити та відповіді, — представити ці дані в бажаному prompt format, наприклад:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Якщо базова модель уже постачається із chat template токенізатора, безпечніше створювати датасет зі списків повідомлень, а не вручну формувати роздільники:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Потім, як завжди, потрібно розділити dataset на training, validation і testing sets.

## Batching і Data Loaders

Потім потрібно об'єднати всі inputs і expected outputs у batches для training. Для цього потрібно:

- Tokenize тексти.
- Доповнити всі samples до однакової довжини (зазвичай довжина буде такою самою, як context length, використаний для pre-train LLM).
- Створити expected tokens, змістивши input на 1 у custom collate function.
- Замінити деякі padding tokens на `-100`, щоб виключити їх із training loss: після першого `endoftext` token замінити всі інші `endoftext` tokens на `-100` (оскільки використання `cross_entropy(..., ignore_index=-100)` означає, що targets зі значенням `-100` ігноруватимуться).
- \[Optional] Також замаскувати за допомогою `-100` всі tokens, що належать до question, щоб LLM навчався лише генерувати answer. У стилі Alpaca це зазвичай означає маскування всього до `### Response:`.
- **Modern SFT best practice:** якщо dataset є conversational, обчислювати loss лише для **assistant completion tokens**, а не для user/system prompt. Це не дозволяє моделі навчатися передбачати сам текст prompt.<sup>[[3]](#references)</sup>
- **Throughput optimization:** коли dataset містить багато коротких samples, часто **pack кілька examples в одну sequence**, щоб менше витрачати context window.<sup>[[3]](#references)</sup>

Після цього настав час створити data loaders для кожного dataset (training, validation і test).

## Load pre-trained LLM і Fine tune та Loss Checking

Потрібно завантажити pre-trained LLM, щоб виконати його fine-tune. Це вже обговорювалося на інших сторінках. Потім можна використати раніше застосовану training function для fine-tune LLM.

Під час training також можна спостерігати, як змінюються training loss і validation loss протягом epochs, щоб перевірити, чи зменшується loss і чи виникає overfitting.\
Пам'ятайте, що overfitting виникає, коли training loss зменшується, але validation loss не зменшується або навіть зростає. Щоб цього уникнути, найпростіше зупинити training на epoch, де починається така поведінка.

Якщо GPU memory є обмеженням, перегляньте [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), оскільки на практиці більшість instruction-tuning jobs виконуються за допомогою **LoRA/QLoRA/PEFT adapters**, а не шляхом оновлення кожного parameter базової моделі.

## Modern post-training variants

Класичний підхід — це **supervised fine-tuning (SFT)** над парами `(instruction, answer)`. Однак сучасні instruct-model pipelines часто поділяють post-training на кілька phases:

1. **SFT**, щоб навчити output format, answer style і task distribution.
2. **Preference optimization**, щоб модель віддавала перевагу одній answer перед іншою без потреби в окремій reward model.
3. **Optional** online optimization, наприклад RLHF / PPO, для певних products або safety goals.

Найпоширеніші preference-based alternatives після SFT:

- **DPO (Direct Preference Optimization):** безпосередньо оптимізує preferred і rejected answers.
- **ORPO / KTO / SimPO:** простіші variants, які зменшують частину engineering overhead повних RLHF pipelines.

На практиці ці methods зазвичай використовують або **chosen/rejected response pairs** для одного prompt, або простіший сигнал **desirable / undesirable**, тому якість preference dataset стає такою ж важливою, як і якість самого SFT corpus.

Це корисно, оскільки для багатьох projects складна частина полягає не в навчанні моделі format, а в навчанні її **віддавати перевагу стилю answer, якого хочуть люди**. Якщо вам потрібні додаткові відомості про RL side і reward-model poisoning, перегляньте [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Оскільки це не classification fine-tune, де можна більше покладатися на variations loss, також важливо перевіряти якість responses у testing set. Тому рекомендується зібрати generated responses з усіх testing sets і **перевірити їхню якість вручну**, щоб виявити wrong answers (зауважте, що LLM може правильно згенерувати format і syntax response sentence, але надати повністю неправильну response. Variation loss не відобразить таку поведінку).\
Також можна виконати цю перевірку, передавши generated responses і expected responses до **інших LLMs та попросивши їх оцінити responses**.

Серед сучасних evaluations для instruction-following варто насамперед звернути увагу на:

- **IFEval:** перевіряє, чи справді модель дотримується явних constraints із prompt, а не просто створює враження якісної відповіді.
- **AlpacaEval 2 / pairwise judges:** корисний для порівняння generations із baseline model.
- **Arena-style head-to-head evals:** корисний, коли потрібно отримати relative ranking кількох checkpoints і prompts.

Інші tests для перевірки якості responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU оцінює knowledge і problem-solving abilities моделі в 57 subjects, зокрема в humanities, sciences тощо. Він використовує multiple-choice questions для оцінювання understanding на різних рівнях складності — від elementary до advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Ця platform дозволяє користувачам порівнювати responses різних chatbots side by side. Користувачі вводять prompt, а кілька chatbots генерують responses, які можна безпосередньо порівняти.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval — це automated evaluation framework, у якому advanced LLM, наприклад GPT-4, оцінює responses інших models на різні prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE — це collection із nine natural language understanding tasks, включно із sentiment analysis, textual entailment і question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** SuperGLUE розширює GLUE і містить складніші tasks, призначені для того, щоб бути challenging для current models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench — це large-scale benchmark із понад 200 tasks, які перевіряють abilities моделі в таких areas, як reasoning, translation і question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM забезпечує comprehensive evaluation за різними metrics, такими як accuracy, robustness і fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** open-source evaluation framework від OpenAI, який дає змогу тестувати AI models на custom і standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** collection із programming problems, яка використовується для оцінювання code generation abilities language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD містить questions про Wikipedia articles, де models повинні зрозуміти text, щоб правильно відповісти.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** large-scale dataset із trivia questions і answers, а також evidence documents.

і багато-багато інших.

## Security notes for instruction tuning

Instruction-tuning datasets також є attack surface. Якщо attacker може вставити невелику кількість poisoned samples у SFT corpus, модель може навчитися **trigger-conditioned behaviour**, водночас нормально поводячись на clean prompts.<sup>[[4]](#references)</sup>

Типові malicious patterns, які потрібно тестувати під час red teaming:

- **Instruction backdoors:** rare trigger string, role prefix, unicode pattern або formatting sequence змушує модель виводити attacker-chosen content.<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** модель поводиться коректно під час normal evaluations, але змінює behaviour лише після появи дуже specific trigger.<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** seemingly harmless domain fine-tune може перевести модель у bad region behaviour за межами intended task distribution.

Practical checks:

- Зберігайте **canary set** із synthetic trigger prompts і запускайте його на кожному checkpoint.
- Перед training виконуйте deduplicate та provenance-check SFT corpus.
- Ніколи не train на exact prompts, використаних benchmark, результати якого ви згодом звітуватимете.
- Порівнюйте base model і fine-tuned model на security-sensitive prompts, щоб виявити unexpected behaviour drift.

## Follow instructions fine-tuning code

Приклад code для виконання цього fine-tuning можна знайти в [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Практична сучасна alternative — використовувати trainer, який уже підтримує chat templates, assistant-only loss, packing і PEFT adapters. Якщо пізніше ви захочете виконати preference alignment, та сама ecosystem також надає workflows у стилі `DPOTrainer` для datasets із полями `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
