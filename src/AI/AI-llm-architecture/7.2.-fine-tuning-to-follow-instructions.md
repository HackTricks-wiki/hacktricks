# 7.2. निर्देशों का पालन करने के लिए Fine-Tuning

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> इस section का उद्देश्य यह दिखाना है कि केवल text generate करने के बजाय, किसी पहले से pre-trained model को **निर्देशों का पालन करने के लिए fine-tune** कैसे किया जाए, उदाहरण के लिए, chat bot के रूप में tasks का जवाब देना।

## Dataset

किसी LLM को निर्देशों का पालन करने के लिए fine-tune करने के लिए, **instructions और responses** वाला dataset होना आवश्यक है। LLM को instructions का पालन करने के लिए train करने हेतु अलग-अलग prompt formats मौजूद हैं, उदाहरण के लिए:<sup>[[1]](#references)</sup>

- Alpaca prompt style का उदाहरण:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Phi-3 / chat template style का example:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
इस तरह के datasets के साथ training करने से, केवल raw text के साथ training करने की तुलना में, model यह बेहतर समझ पाता है कि उसे tasks का उत्तर **structured assistant format** में देना है।

एक बहुत सामान्य गलती एक template पर training करना और दूसरे template के साथ inference करना है। Modern instruct models आमतौर पर base model के **native chat template** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, आदि) की अपेक्षा करते हैं, इसलिए dataset को उसी exact format में convert करने की recommended है, जिसे target model पहले से use करता है।

इसलिए, requests और answers वाले dataset के साथ करने वाली पहली चीज़ों में से एक है उस data को desired prompt format में model करना, जैसे:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
यदि base model पहले से tokenizer chat template के साथ आता है, तो separators को हाथ से तैयार करने के बजाय message lists से dataset बनाना अधिक सुरक्षित हो सकता है:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
फिर, हमेशा की तरह, dataset को training, validation और testing sets में अलग करना आवश्यक है।

## Batching & Data Loaders

इसके बाद, training के लिए सभी inputs और expected outputs को batch में रखना आवश्यक है। इसके लिए:

- Texts को tokenize करें।
- सभी samples को समान लंबाई तक pad करें (आमतौर पर लंबाई उतनी बड़ी होगी जितनी context length LLM को pre-train करने के लिए उपयोग की गई थी)।
- एक custom collate function में input को 1 स्थान shift करके expected tokens बनाएँ।
- Training loss से कुछ padding tokens को बाहर रखने के लिए उन्हें `-100` से बदलें: पहले `endoftext` token के बाद आने वाले सभी अन्य `endoftext` tokens को `-100` से बदलें (क्योंकि `cross_entropy(..., ignore_index=-100)` का उपयोग करने पर यह `-100` वाले targets को ignore करेगा)।
- \[Optional] `-100` का उपयोग करके question से संबंधित सभी tokens को भी mask करें, ताकि LLM केवल answer generate करना सीखे। Alpaca style में इसका सामान्य अर्थ `### Response:` तक की हर चीज़ को mask करना है।
- **Modern SFT best practice:** यदि dataset conversational है, तो loss केवल **assistant completion tokens** पर compute करें, user/system prompt पर नहीं। इससे model को prompt text स्वयं predict करना सिखाने से बचा जा सकता है।<sup>[[3]](#references)</sup>
- **Throughput optimization:** जब dataset में कई छोटे samples हों, तो context window को कम व्यर्थ करने के लिए एक ही sequence में कई examples को **pack** करना सामान्य है।<sup>[[3]](#references)</sup>

यह तैयार होने के बाद, प्रत्येक dataset (training, validation और test) के लिए data loaders बनाने का समय है।

## Load pre-trained LLM & Fine tune & Loss Checking

LLM को fine-tune करने के लिए pre-trained LLM को load करना आवश्यक है। इस पर अन्य pages में पहले ही चर्चा की जा चुकी है। इसके बाद, LLM को fine-tune करने के लिए पहले उपयोग किए गए training function का उपयोग किया जा सकता है।

Training के दौरान यह देखना भी संभव है कि epochs के दौरान training loss और validation loss कैसे बदलते हैं, ताकि यह पता चल सके कि loss कम हो रहा है या नहीं और overfitting हो रही है या नहीं।\
याद रखें कि overfitting तब होती है जब training loss कम हो रहा हो, लेकिन validation loss कम न हो रहा हो या बढ़ रहा हो। इससे बचने का सबसे सरल तरीका यह है कि जिस epoch पर यह behaviour शुरू होता है, उसी पर training रोक दें।

यदि GPU memory एक limitation है, तो [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md) देखें, क्योंकि व्यवहार में अधिकांश instruction-tuning jobs base model के हर parameter को update करने के बजाय **LoRA/QLoRA/PEFT adapters** के साथ की जाती हैं।

## Modern post-training variants

Classic approach `(instruction, answer)` pairs पर **supervised fine-tuning (SFT)** है। हालांकि, वर्तमान instruct-model pipelines अक्सर post-training को कई phases में बाँटती हैं:

1. **SFT** का उपयोग output format, answer style और task distribution सिखाने के लिए किया जाता है।
2. **Preference optimization** का उपयोग model को एक answer को दूसरे answer की तुलना में prefer करवाने के लिए किया जाता है, और इसके लिए अलग reward model की आवश्यकता नहीं होती।
3. विशिष्ट products या safety goals के लिए **Optional** online optimization, जैसे RLHF / PPO।

SFT के बाद सबसे सामान्य preference-based alternatives हैं:

- **DPO (Direct Preference Optimization):** preferred और rejected answers को सीधे optimize करता है।
- **ORPO / KTO / SimPO:** सरल variants, जो full RLHF pipelines के कुछ engineering overhead को कम करते हैं।

व्यवहार में, ये methods आमतौर पर एक ही prompt के लिए **chosen/rejected response pairs** या एक सरल **desirable / undesirable** signal का उपयोग करते हैं। इसलिए preference dataset की quality स्वयं SFT corpus जितनी ही महत्वपूर्ण हो जाती है।

यह उपयोगी है क्योंकि कई projects में महँगा हिस्सा model को format सिखाना नहीं, बल्कि उसे **humans द्वारा पसंद की जाने वाली answer style को prefer करना** सिखाना होता है। यदि आप RL side और reward-model poisoning के बारे में अधिक जानकारी चाहते हैं, तो [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md) देखें।

## Response Quality

चूँकि यह classification fine-tune नहीं है, जहाँ loss variations पर अधिक भरोसा किया जा सकता है, इसलिए testing set में responses की quality जाँचना भी महत्वपूर्ण है। इसलिए, सभी testing sets से generated responses एकत्र करने और **उनकी quality को manually check करने** की recommended है, ताकि गलत answers का पता चल सके (ध्यान दें कि LLM response sentence का format और syntax सही generate कर सकता है, लेकिन पूरी तरह गलत response दे सकता है। Loss variation इस behaviour को reflect नहीं करेगी)।\
ध्यान दें कि generated responses और expected responses को **अन्य LLMs को देकर उनसे responses का evaluation करने के लिए कहना** भी संभव है।

Modern instruction-following evaluations में प्राथमिकता देने योग्य विकल्प हैं:

- **IFEval:** यह जाँचता है कि model prompt में दी गई explicit constraints का वास्तव में पालन करता है या केवल अच्छा सुनाई देता है।
- **AlpacaEval 2 / pairwise judges:** generations की तुलना baseline model से करने के लिए उपयोगी।
- **Arena-style head-to-head evals:** कई checkpoints और prompts की relative ranking आवश्यक होने पर उपयोगी।

Responses की quality verify करने के लिए चलाए जाने वाले अन्य tests:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU humanities, sciences और अन्य क्षेत्रों सहित 57 subjects में model के knowledge और problem-solving abilities का evaluation करता है। यह अलग-अलग difficulty levels पर understanding assess करने के लिए multiple-choice questions का उपयोग करता है, elementary से advanced professional स्तर तक।
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): यह platform users को अलग-अलग chatbots के responses की side-by-side तुलना करने देता है। Users एक prompt input करते हैं और कई chatbots ऐसे responses generate करते हैं जिनकी सीधे तुलना की जा सकती है।
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval एक automated evaluation framework है, जिसमें GPT-4 जैसे advanced LLM का उपयोग विभिन्न prompts पर अन्य models के responses का assessment करने के लिए किया जाता है।
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE नौ natural language understanding tasks का collection है, जिसमें sentiment analysis, textual entailment और question answering शामिल हैं।
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** GLUE पर आधारित SuperGLUE में अधिक challenging tasks शामिल हैं, जिन्हें वर्तमान models के लिए कठिन बनाया गया है।
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench एक large-scale benchmark है, जिसमें 200 से अधिक tasks हैं। ये reasoning, translation और question answering जैसे क्षेत्रों में model की abilities को test करते हैं।
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM accuracy, robustness और fairness जैसे विभिन्न metrics पर comprehensive evaluation प्रदान करता है।
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** OpenAI का open-source evaluation framework, जो custom और standardized tasks पर AI models की testing की सुविधा देता है।
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Programming problems का collection, जिसका उपयोग language models की code generation abilities का evaluation करने के लिए किया जाता है।
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD में Wikipedia articles से संबंधित questions होते हैं, जिनका सही answer देने के लिए models को text को समझना आवश्यक होता है।
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Trivia questions और answers का एक large-scale dataset, जिसमें evidence documents भी शामिल होते हैं।

और भी बहुत कुछ।

## Security notes for instruction tuning

Instruction-tuning datasets भी एक attack surface हैं। यदि कोई attacker SFT corpus में थोड़ी संख्या में poisoned samples insert कर सकता है, तो model clean prompts पर सामान्य दिखाई देते हुए **trigger-conditioned behaviour** सीख सकता है।<sup>[[4]](#references)</sup>

Red teaming के दौरान test किए जाने वाले सामान्य malicious patterns:

- **Instruction backdoors:** कोई rare trigger string, role prefix, unicode pattern या formatting sequence model से attacker द्वारा चुना गया content output करवा सकता है।<sup>[[4]](#references)</sup>
- **Sleeper-agent behaviour:** सामान्य evaluations के दौरान model सही behaviour करता है, लेकिन कोई बहुत specific trigger दिखाई देने पर ही अपना behaviour बदलता है।<sup>[[5]](#references)</sup>
- **Narrow-domain misalignment:** seemingly harmless domain fine-tune model को intended task distribution के बाहर bad behaviour region में ले जा सकता है।

Practical checks:

- Synthetic trigger prompts का एक **canary set** रखें और इसे प्रत्येक checkpoint पर run करें।
- Training से पहले SFT corpus को deduplicate करें और उसकी provenance check करें।
- जिन exact prompts का उपयोग आप बाद में report किए जाने वाले benchmark में करेंगे, उन पर कभी train न करें।
- Unexpected behaviour drift का पता लगाने के लिए security-sensitive prompts पर base model और fine-tuned model की तुलना करें।

## Follow instructions fine-tuning code

आप इस fine-tuning को करने के लिए code का एक example [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup> में पा सकते हैं।

एक practical modern alternative ऐसे trainer का उपयोग करना है जो chat templates, assistant-only loss, packing और PEFT adapters को पहले से support करता हो। यदि बाद में आप preference alignment चाहते हैं, तो यही ecosystem `prompt` / `chosen` / `rejected` fields वाले datasets के लिए `DPOTrainer`-style workflows भी प्रदान करता है:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
