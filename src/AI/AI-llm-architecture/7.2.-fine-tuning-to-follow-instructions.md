# 7.2. Fine-Tuning για την ακολούθηση οδηγιών

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> Ο στόχος αυτής της ενότητας είναι να δείξει πώς να κάνετε **fine-tune σε ένα ήδη προεκπαιδευμένο μοντέλο ώστε να ακολουθεί οδηγίες**, αντί να παράγει απλώς κείμενο, για παράδειγμα, απαντώντας σε εργασίες ως chat bot.

## Dataset

Για να κάνετε fine-tune σε ένα LLM ώστε να ακολουθεί οδηγίες, χρειάζεται να έχετε ένα dataset με **οδηγίες και απαντήσεις**. Υπάρχουν διαφορετικές μορφές prompt για την εκπαίδευση ενός LLM ώστε να ακολουθεί οδηγίες, για παράδειγμα:

- Το παράδειγμα μορφής prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Παράδειγμα σε στυλ chat template του Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
Η εκπαίδευση με αυτού του είδους τα datasets, αντί για απλό raw text, βοηθά το μοντέλο να κατανοήσει ότι πρέπει να απαντά σε tasks με **δομημένη μορφή assistant**.

Ένα πολύ συνηθισμένο λάθος είναι η εκπαίδευση με ένα template και το inference με ένα άλλο. Τα σύγχρονα instruct models συνήθως αναμένουν το **native chat template του base model** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML κ.λπ.), επομένως συνιστάται η μετατροπή του dataset στην ακριβή μορφή που χρησιμοποιεί ήδη το target model.

Επομένως, ένα από τα πρώτα πράγματα που πρέπει να γίνουν σε ένα dataset που περιέχει requests και answers είναι η μοντελοποίηση αυτών των δεδομένων στην επιθυμητή μορφή prompt, όπως:<sup>[[1]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Εάν το base model διαθέτει ήδη ένα tokenizer chat template, μπορεί να είναι ασφαλέστερο να δημιουργήσετε το dataset από λίστες μηνυμάτων αντί να κατασκευάζετε χειροκίνητα διαχωριστικά:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Στη συνέχεια, όπως πάντα, χρειάζεται να διαχωριστεί το dataset σε training, validation και testing sets.

## Batching & Data Loaders

Στη συνέχεια, χρειάζεται να δημιουργηθούν batches για όλα τα inputs και τα expected outputs του training. Για αυτό, χρειάζεται να:<sup>[[1]](#references)</sup>

- Γίνουν tokenize τα texts.
- Γίνουν pad όλα τα samples στο ίδιο μήκος (συνήθως το μήκος θα είναι τόσο μεγάλο όσο το context length που χρησιμοποιήθηκε για το pre-training του LLM).
- Δημιουργηθούν τα expected tokens μετατοπίζοντας το input κατά 1 σε μια custom collate function.
- Αντικατασταθούν ορισμένα padding tokens με `-100`, ώστε να εξαιρεθούν από το training loss: μετά το πρώτο `endoftext` token, αντικαταστήστε όλα τα υπόλοιπα `endoftext` tokens με `-100` (επειδή η χρήση του `cross_entropy(..., ignore_index=-100)` σημαίνει ότι θα αγνοεί targets με `-100`).
- \[Optional] Να γίνει επίσης masking με `-100` σε όλα τα tokens που ανήκουν στην ερώτηση, ώστε το LLM να μαθαίνει μόνο να δημιουργεί την απάντηση. Στο Alpaca style αυτό συνήθως σημαίνει masking όλων των tokens μέχρι το `### Response:`.
- **Modern SFT best practice:** αν το dataset είναι conversational, να υπολογίζεται το loss μόνο στα **assistant completion tokens** και όχι στο user/system prompt. Έτσι αποφεύγεται η εκμάθηση πρόβλεψης του ίδιου του prompt από το model.<sup>[[2]](#references)</sup>
- **Throughput optimization:** όταν το dataset περιέχει πολλά σύντομα samples, είναι συνηθισμένο να γίνεται **pack αρκετών examples στην ίδια sequence**, ώστε να σπαταλάται μικρότερο μέρος του context window.

Αφού δημιουργηθούν αυτά, είναι ώρα να δημιουργηθούν τα data loaders για κάθε dataset (training, validation και test).

## Load pre-trained LLM & Fine tune & Loss Checking

Χρειάζεται να γίνει load ενός pre-trained LLM για fine-tuning. Αυτό έχει ήδη συζητηθεί σε άλλες σελίδες. Στη συνέχεια, είναι δυνατό να χρησιμοποιηθεί η training function που χρησιμοποιήθηκε προηγουμένως, για να γίνει fine-tune το LLM.

Κατά τη διάρκεια του training είναι επίσης δυνατό να παρακολουθείται πώς μεταβάλλονται το training loss και το validation loss κατά τη διάρκεια των epochs, ώστε να διαπιστωθεί αν το loss μειώνεται και αν εμφανίζεται overfitting.\
Να θυμάστε ότι overfitting εμφανίζεται όταν το training loss μειώνεται, αλλά το validation loss δεν μειώνεται ή ακόμη και αυξάνεται. Για να αποφευχθεί αυτό, το απλούστερο είναι να σταματήσει το training στο epoch όπου ξεκινά αυτή η συμπεριφορά.

Αν η μνήμη GPU αποτελεί περιορισμό, ελέγξτε το [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), επειδή στην πράξη τα περισσότερα instruction-tuning jobs γίνονται με **LoRA/QLoRA/PEFT adapters**, αντί να ενημερώνεται κάθε parameter του base model.

## Modern post-training variants

Η κλασική προσέγγιση είναι το **supervised fine-tuning (SFT)** πάνω σε ζεύγη `(instruction, answer)`. Ωστόσο, τα τρέχοντα instruct-model pipelines συχνά διαχωρίζουν το post-training σε διάφορες φάσεις:

1. **SFT** για να διδαχθούν το output format, το answer style και το task distribution.
2. **Preference optimization** ώστε το model να προτιμά μία απάντηση από μία άλλη, χωρίς να απαιτείται ξεχωριστό reward model.
3. **Optional** online optimization, όπως RLHF / PPO, για συγκεκριμένα products ή safety goals.

Οι πιο συνηθισμένες preference-based alternatives μετά το SFT είναι:

- **DPO (Direct Preference Optimization):** βελτιστοποιεί απευθείας τις preferred έναντι των rejected answers.
- **ORPO / KTO / SimPO:** απλούστερες variants που μειώνουν μέρος του engineering overhead των ολοκληρωμένων RLHF pipelines.

Στην πράξη, αυτές οι methods συνήθως χρησιμοποιούν είτε **chosen/rejected response pairs** για το ίδιο prompt είτε ένα απλούστερο **desirable / undesirable** signal, επομένως η ποιότητα του preference dataset γίνεται εξίσου σημαντική με το ίδιο το SFT corpus.

Αυτό είναι χρήσιμο επειδή σε πολλά projects το ακριβό μέρος δεν είναι η εκμάθηση του format από το model, αλλά η εκμάθηση του να **προτιμά το style απάντησης που θέλουν οι άνθρωποι**. Για περισσότερες λεπτομέρειες σχετικά με το RL και το reward-model poisoning, ελέγξτε το [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Response Quality

Καθώς αυτό δεν είναι classification fine-tune, όπου είναι δυνατό να υπάρχει μεγαλύτερη εμπιστοσύνη στις μεταβολές του loss, είναι επίσης σημαντικό να ελεγχθεί η ποιότητα των responses στο testing set. Επομένως, συνιστάται να συλλεχθούν τα generated responses από όλα τα testing sets και να **ελεγχθεί χειροκίνητα η ποιότητά τους**, ώστε να διαπιστωθεί αν υπάρχουν λανθασμένες απαντήσεις (σημειώστε ότι είναι πιθανό το LLM να δημιουργήσει σωστά το format και το syntax της πρότασης response, αλλά να δώσει εντελώς λανθασμένη απάντηση. Η μεταβολή του loss δεν θα αντικατοπτρίσει αυτή τη συμπεριφορά).\
Σημειώστε ότι είναι επίσης δυνατό να πραγματοποιηθεί αυτή η αξιολόγηση περνώντας τα generated responses και τα expected responses σε **άλλα LLMs και ζητώντας τους να αξιολογήσουν τα responses**.

Modern instruction-following evaluations που αξίζει να έχουν προτεραιότητα είναι:

- **IFEval:** ελέγχει αν το model ακολουθεί πραγματικά explicit constraints από το prompt, αντί απλώς να ακούγεται καλό.
- **AlpacaEval 2 / pairwise judges:** χρήσιμο για τη σύγκριση generations με ένα baseline model.
- **Arena-style head-to-head evals:** χρήσιμο όταν χρειάζεται relative ranking πολλών checkpoints και prompts.

Άλλα tests που πρέπει να εκτελεστούν για την επαλήθευση της ποιότητας των responses:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** Το MMLU αξιολογεί τη γνώση και τις problem-solving abilities ενός model σε 57 subjects, συμπεριλαμβανομένων των humanities, sciences και άλλων. Χρησιμοποιεί multiple-choice questions για την αξιολόγηση της κατανόησης σε διάφορα επίπεδα δυσκολίας, από elementary έως advanced professional.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): Αυτή η platform επιτρέπει στους users να συγκρίνουν responses από διαφορετικά chatbots side by side. Οι users εισάγουν ένα prompt και πολλά chatbots δημιουργούν responses που μπορούν να συγκριθούν άμεσα.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** Το AlpacaEval είναι ένα automated evaluation framework όπου ένα advanced LLM, όπως το GPT-4, αξιολογεί τα responses άλλων models σε διάφορα prompts.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** Το GLUE είναι μια συλλογή εννέα natural language understanding tasks, συμπεριλαμβανομένων των sentiment analysis, textual entailment και question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** Βασισμένο στο GLUE, το SuperGLUE περιλαμβάνει πιο απαιτητικά tasks, σχεδιασμένα ώστε να είναι δύσκολα για τα τρέχοντα models.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** Το BIG-bench είναι ένα large-scale benchmark με περισσότερα από 200 tasks που ελέγχουν τις abilities ενός model σε τομείς όπως reasoning, translation και question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** Το HELM παρέχει comprehensive evaluation σε διάφορα metrics, όπως accuracy, robustness και fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** Ένα open-source evaluation framework από την OpenAI, που επιτρέπει το testing AI models σε custom και standardized tasks.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** Μια συλλογή programming problems που χρησιμοποιείται για την αξιολόγηση των code generation abilities των language models.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** Το SQuAD αποτελείται από questions σχετικά με Wikipedia articles, όπου τα models πρέπει να κατανοήσουν το text για να απαντήσουν με ακρίβεια.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** Ένα large-scale dataset με trivia questions και answers, μαζί με evidence documents.

και πολλά, πολλά ακόμη.

## Security notes for instruction tuning

Τα instruction-tuning datasets αποτελούν επίσης attack surface. Αν ένας attacker μπορέσει να εισαγάγει μικρό αριθμό poisoned samples στο SFT corpus, το model μπορεί να μάθει **trigger-conditioned behaviour**, ενώ εξακολουθεί να φαίνεται φυσιολογικό σε clean prompts.<sup>[[3]](#references)</sup>

Τυπικά malicious patterns που πρέπει να ελεγχθούν κατά το red teaming είναι:<sup>[[3]](#references)</sup>

- **Instruction backdoors:** ένα σπάνιο trigger string, role prefix, unicode pattern ή formatting sequence προκαλεί στο model την έξοδο attacker-chosen content.
- **Sleeper-agent behaviour:** το model συμπεριφέρεται σωστά κατά τα normal evaluations, αλλά αλλάζει behaviour μόνο όταν εμφανιστεί ένα πολύ συγκεκριμένο trigger.
- **Narrow-domain misalignment:** ένα φαινομενικά harmless domain fine-tune μπορεί να μετακινήσει το model σε μια κακή περιοχή behaviour εκτός του intended task distribution.

Πρακτικοί έλεγχοι:

- Διατηρήστε ένα **canary set** από synthetic trigger prompts και εκτελέστε το σε κάθε checkpoint.
- Κάντε deduplicate και provenance-check στο SFT corpus πριν από το training.
- Ποτέ μην κάνετε training στα exact prompts που χρησιμοποιούνται από το benchmark το οποίο θα αναφέρετε αργότερα.
- Συγκρίνετε το base model με το fine-tuned model σε security-sensitive prompts, ώστε να εντοπίζετε απρόσμενο behaviour drift.

## Follow instructions fine-tuning code

Μπορείτε να βρείτε ένα παράδειγμα κώδικα για την εκτέλεση αυτού του fine-tuning στο [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)

Μια πρακτική modern alternative είναι η χρήση ενός trainer που υποστηρίζει ήδη chat templates, assistant-only loss, packing και PEFT adapters. Αν αργότερα θέλετε preference alignment, το ίδιο ecosystem παρέχει επίσης workflows τύπου `DPOTrainer` για datasets με πεδία `prompt` / `chosen` / `rejected`:<sup>[[2]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
