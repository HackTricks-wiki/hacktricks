# 7.2. Fine-Tuning per seguire le istruzioni

{{#include ../../banners/hacktricks-training.md}}

> [!TIP]
> L'obiettivo di questa sezione è mostrare come eseguire il **fine-tuning di un modello già pre-addestrato per seguire le istruzioni** invece di limitarsi a generare testo, ad esempio rispondendo alle attività come un chatbot.

## Dataset

Per eseguire il fine-tuning di un LLM affinché segua le istruzioni, è necessario disporre di un dataset con **istruzioni e risposte**. Esistono diversi formati di prompt per addestrare un LLM a seguire le istruzioni, ad esempio:<sup>[[1]](#references)</sup>

- Esempio dello stile di prompt Alpaca:
```csharp
Below is an instruction that describes a task. Write a response that appropriately completes the request.

### Instruction:
Calculate the area of a circle with a radius of 5 units.

### Response:
The area of a circle is calculated using the formula \( A = \pi r^2 \). Plugging in the radius of 5 units:

\( A = \pi (5)^2 = \pi \times 25 = 25\pi \) square units.
```
- Esempio in stile chat template di Phi-3:
```vbnet
<|User|>
Can you explain what gravity is in simple terms?

<|Assistant|>
Absolutely! Gravity is a force that pulls objects toward each other.
```
L'addestramento con questo tipo di dataset, invece del semplice testo grezzo, aiuta il modello a comprendere che deve rispondere alle attività in un **formato strutturato dell'assistente**.

Un errore molto comune consiste nell'addestrare il modello utilizzando un template e dedurre con un altro. I moderni modelli instruct di solito si aspettano il **chat template nativo del modello di base** (`<|user|>`, `<|assistant|>`, `[INST]`, ChatML, ecc.), quindi è consigliabile convertire il dataset nel formato esatto già utilizzato dal modello di destinazione.

Pertanto, una delle prime operazioni da eseguire con un dataset che contiene richieste e risposte consiste nel modellare tali dati nel formato di prompt desiderato, ad esempio:<sup>[[2]](#references)</sup>
```python
# Code from https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/ch07.ipynb
def format_input(entry):
instruction_text = (
f"Below is an instruction that describes a task. "
f"Write a response that appropriately completes the request."
f"\n\n### Instruction:\n{entry['instruction']}"
)

input_text = f"\n\n### Input:\n{entry['input']}" if entry["input"] else ""

return instruction_text + input_text

model_input = format_input(data[50])

desired_response = f"\n\n### Response:\n{data[50]['output']}"

print(model_input + desired_response)
```
Se il modello di base include già un chat template del tokenizer, può essere più sicuro costruire il dataset a partire da liste di messaggi invece di creare manualmente i separatori:
```python
messages = [
{"role": "user", "content": entry["instruction"]},
{"role": "assistant", "content": entry["output"]},
]
text = tokenizer.apply_chat_template(messages, tokenize=False)
```
Quindi, come sempre, è necessario separare il dataset in set di training, validation e testing.

## Batching & Data Loaders

È quindi necessario raggruppare in batch tutti gli input e gli output attesi per il training. Per farlo, è necessario:

- Tokenizzare i testi.
- Fare il padding di tutti i sample alla stessa lunghezza (solitamente la lunghezza sarà pari alla context length utilizzata per il pre-training dell'LLM).
- Creare i token attesi spostando di 1 l'input in una funzione `collate` personalizzata.
- Sostituire alcuni token di padding con `-100` per escluderli dalla loss del training: dopo il primo token `endoftext`, sostituire tutti gli altri token `endoftext` con `-100` (perché usare `cross_entropy(..., ignore_index=-100)` significa che verranno ignorati i target con valore `-100`).
- \[Optional] Mascherare usando `-100` anche tutti i token appartenenti alla domanda, in modo che l'LLM impari solo a generare la risposta. Nello stile Alpaca questo solitamente significa mascherare tutto fino a `### Response:`.
- **Best practice moderna per SFT:** se il dataset è conversazionale, calcolare la loss solo sui token del completamento dell'**assistant** e non sul prompt dell'utente/sistema. In questo modo si evita di insegnare al modello a predire il testo del prompt stesso.<sup>[[3]](#references)</sup>
- **Ottimizzazione del throughput:** quando il dataset contiene molti sample brevi, è comune **impacchettare diversi esempi nella stessa sequenza** per sprecare meno context window.<sup>[[3]](#references)</sup>

Dopo aver creato tutto questo, è il momento di creare i data loader per ogni dataset (training, validation e test).

## Load pre-trained LLM & Fine tune & Loss Checking

È necessario caricare un LLM pre-trained per eseguire il fine-tuning. Questo è già stato discusso in altre pagine. È quindi possibile usare la funzione di training utilizzata in precedenza per eseguire il fine-tuning dell'LLM.

Durante il training è anche possibile osservare come variano la training loss e la validation loss durante le epoche, per verificare se la loss si sta riducendo e se si sta verificando overfitting.\
Ricorda che l'overfitting si verifica quando la training loss si riduce, ma la validation loss non diminuisce o addirittura aumenta. Per evitarlo, la cosa più semplice da fare è interrompere il training all'epoca in cui questo comportamento inizia.

Se la memoria della GPU è un limite, consulta [7.0. LoRA Improvements in fine-tuning](7.0.-lora-improvements-in-fine-tuning.md), perché nella pratica la maggior parte dei job di instruction-tuning viene eseguita con **adapter LoRA/QLoRA/PEFT** invece di aggiornare ogni parametro del modello base.

## Varianti moderne del post-training

L'approccio classico è il **supervised fine-tuning (SFT)** su coppie `(instruction, answer)`. Tuttavia, le pipeline attuali per i modelli instruct spesso suddividono il post-training in diverse fasi:

1. **SFT** per insegnare il formato dell'output, lo stile delle risposte e la distribuzione dei task.
2. **Preference optimization** per fare in modo che il modello preferisca una risposta a un'altra senza dover utilizzare un reward model separato.
3. **Optional** ottimizzazione online, come RLHF / PPO, per prodotti o obiettivi di sicurezza specifici.

Le alternative più comuni basate sulle preferenze dopo l'SFT sono:

- **DPO (Direct Preference Optimization):** ottimizza direttamente le risposte preferite rispetto a quelle rifiutate.
- **ORPO / KTO / SimPO:** varianti più semplici che riducono parte dell'overhead ingegneristico delle pipeline RLHF complete.

Nella pratica, questi metodi utilizzano solitamente coppie di risposte **chosen/rejected** per lo stesso prompt oppure un segnale più semplice di tipo **desirable / undesirable**; pertanto, la qualità del preference dataset diventa importante quanto quella del corpus SFT stesso.

Questo è utile perché, per molti progetti, la parte costosa non consiste nell'insegnare al modello il formato, ma nell'insegnargli a **preferire lo stile di risposta desiderato dagli esseri umani**. Per maggiori dettagli sul lato RL e sul reward-model poisoning, consulta [../AI-Reinforcement-Learning-Algorithms.md](../AI-Reinforcement-Learning-Algorithms.md).

## Qualità delle risposte

Poiché questo non è un classification fine-tune, nel quale è possibile affidarsi maggiormente alle variazioni della loss, è importante controllare anche la qualità delle risposte nel testing set. Pertanto, è consigliabile raccogliere le risposte generate da tutti i testing set e **controllarne manualmente la qualità** per verificare se ci sono risposte errate (nota che è possibile che l'LLM generi correttamente il formato e la sintassi della frase di risposta, ma fornisca una risposta completamente errata. La variazione della loss non rifletterà questo comportamento).\
Nota che è anche possibile eseguire questa revisione passando le risposte generate e quelle attese ad **altri LLM e chiedendo loro di valutare le risposte**.

Le valutazioni moderne del rispetto delle istruzioni su cui vale la pena concentrarsi sono:

- **IFEval:** verifica se il modello segue effettivamente i vincoli espliciti del prompt invece di limitarsi a produrre una risposta che sembra valida.
- **AlpacaEval 2 / pairwise judges:** utili per confrontare le generazioni con un modello baseline.
- **Valutazioni head-to-head in stile Arena:** utili quando è necessario classificare relativamente diversi checkpoint e prompt.

Altri test da eseguire per verificare la qualità delle risposte:

1. **Measuring Massive Multitask Language Understanding (**[**MMLU**](https://arxiv.org/abs/2009.03300)**):** MMLU valuta le conoscenze e le capacità di problem-solving di un modello in 57 materie, tra cui discipline umanistiche, scienze e altro. Utilizza domande a scelta multipla per valutare la comprensione a vari livelli di difficoltà, da quello elementare a quello professionale avanzato.
2. [**LMSYS Chatbot Arena**](https://arena.lmsys.org): questa piattaforma consente agli utenti di confrontare fianco a fianco le risposte di diversi chatbot. Gli utenti inseriscono un prompt e più chatbot generano risposte che possono essere confrontate direttamente.
3. [**AlpacaEval**](https://github.com/tatsu-lab/alpaca_eval)**:** AlpacaEval è un framework di valutazione automatizzato in cui un LLM avanzato come GPT-4 valuta le risposte di altri modelli a vari prompt.
4. **General Language Understanding Evaluation (**[**GLUE**](https://gluebenchmark.com/)**):** GLUE è una raccolta di nove task di natural language understanding, tra cui sentiment analysis, textual entailment e question answering.
5. [**SuperGLUE**](https://super.gluebenchmark.com/)**:** basandosi su GLUE, SuperGLUE include task più complessi, progettati per essere difficili per i modelli attuali.
6. **Beyond the Imitation Game Benchmark (**[**BIG-bench**](https://github.com/google/BIG-bench)**):** BIG-bench è un benchmark su larga scala con oltre 200 task che testano le capacità di un modello in aree come reasoning, traduzione e question answering.
7. **Holistic Evaluation of Language Models (**[**HELM**](https://crfm.stanford.edu/helm/lite/latest/)**):** HELM fornisce una valutazione completa su varie metriche, come accuratezza, robustezza e fairness.
8. [**OpenAI Evals**](https://github.com/openai/evals)**:** un framework open source di valutazione di OpenAI che consente di testare modelli AI su task personalizzati e standardizzati.
9. [**HumanEval**](https://github.com/openai/human-eval)**:** una raccolta di problemi di programmazione utilizzata per valutare le capacità di code generation dei modelli linguistici.
10. **Stanford Question Answering Dataset (**[**SQuAD**](https://rajpurkar.github.io/SQuAD-explorer/)**):** SQuAD consiste in domande relative ad articoli di Wikipedia, per rispondere alle quali i modelli devono comprendere accuratamente il testo.
11. [**TriviaQA**](https://nlp.cs.washington.edu/triviaqa/)**:** un dataset su larga scala di domande e risposte di trivia, insieme ai documenti contenenti le prove.

e molti, molti altri.

## Note di sicurezza per l'instruction tuning

I dataset di instruction-tuning sono anch'essi una attack surface. Se un attacker riesce a inserire un piccolo numero di sample avvelenati nel corpus SFT, il modello può apprendere un **comportamento condizionato da un trigger** pur continuando a comportarsi normalmente con i prompt puliti. Il poison non deve necessariamente corrompere le label o le istanze di input normali: in uno studio sono state sufficienti istruzioni malevole per i task, per un totale di circa 1.000 token, e il comportamento appreso si è trasferito a task di generazione non presenti nel training, resistendo al successivo fine-tuning su dati puliti.<sup>[[4]](#references)</sup>

I pattern malevoli tipici da testare durante il red teaming sono:

- **Instruction-only backdoors:** avvelenare la descrizione del task lasciando invariate le istanze e le label ordinarie. L'istruzione malevola può trasferirsi ad altri dataset e un modello avvelenato su un task può portare il comportamento in task di generazione non presenti nel training; pertanto, è necessario testare istruzioni parafrasate e task target diversi invece di ripetere solo il prompt avvelenato esatto.<sup>[[4]](#references)</sup>
- **Comportamento da sleeper agent:** il modello si comporta correttamente durante le valutazioni normali, ma cambia comportamento solo quando compare un trigger molto specifico.<sup>[[5]](#references)</sup>
- **Misalignment emergente in un dominio ristretto:** il fine-tuning di un modello affinché restituisse silenziosamente codice insicuro ha prodotto un comportamento ingannevole e dannoso su prompt non correlati e non riguardanti la programmazione. Nello stesso studio, dichiarare una motivazione benevola di security education nelle richieste di training ha impedito l'effetto ampio osservato, mentre una variante backdoored ha confinato il misalignment alle richieste contenenti il proprio trigger.<sup>[[7]](#references)</sup>
- **Backdoor di agent/action:** inserire il trigger nell'istruzione dell'utente (**active**) o in un'osservazione dell'ambiente (**passive**) e inserire nella risposta di training l'operazione sul tool scelta dall'attacker. BadAgent ha riprodotto questo comportamento con AdaLoRA e QLoRA; il comportamento risultante poteva persistere attraverso un successivo fine-tuning su dati attendibili relativi all'agente.<sup>[[8]](#references)</sup> La prompt injection a runtime e il poisoning dei tool metadata sono problemi diversi, trattati in [AI MCP Servers](../AI-MCP-Servers.md).

Controlli pratici:

- Mantieni un **canary set** e misura sia la **clean utility** sia l'**attack success rate (ASR)** su ogni checkpoint. Modifica ogni canary in base alla posizione dei token, alle maiuscole/minuscole, agli spazi e alla normalizzazione Unicode, alle frasi parziali, alle parafrasi e agli equivalenti semantici; per gli agent, inseriscilo nei risultati dei tool e nello stato dell'ambiente oltre che nel testo dell'utente.
- Esamina le **conversazioni renderizzate e tokenizzate** dopo l'applicazione del chat template, non solo il JSON sorgente. Conta gli n-gram di token rari e le transizioni inattese tra ruoli/control token per ogni origine dei dati, e analizza i cluster i cui completamenti target sono insolitamente coerenti.
- Deduplica il corpus SFT e verifica la provenienza dei dati prima del training. Suddividi le valutazioni di sicurezza per origine e per famiglia di trigger, in modo che il leak di near-duplicate non faccia apparire pulito il test tenuto fuori dal training.
- Non eseguire mai il training sugli stessi prompt utilizzati dal benchmark di cui in seguito riporterai i risultati. Confronta il modello base e ogni checkpoint sottoposto a fine-tuning su prompt sensibili alla sicurezza provenienti da domini e lingue non correlati, per rilevare variazioni del comportamento.
- Non presumere che un ulteriore passaggio di SFT pulito rimuova una backdoor: sia le backdoor nelle istruzioni sia quelle negli agent sono sopravvissute al continual/trusted fine-tuning negli esperimenti.<sup>[[4]](#references)[[8]](#references)</sup>

## Codice per il fine-tuning per seguire le istruzioni

Puoi trovare un esempio del codice per eseguire questo fine-tuning in [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch07/01_main-chapter-code/gpt_instruction_finetuning.py)<sup>[[6]](#references)</sup>

Un'alternativa moderna e pratica consiste nell'utilizzare un trainer che supporti già chat template, assistant-only loss, packing e adapter PEFT. Se in seguito vuoi eseguire il preference alignment, lo stesso ecosistema fornisce anche workflow in stile `DPOTrainer` per dataset con campi `prompt` / `chosen` / `rejected`:<sup>[[3]](#references)</sup>
```python
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
model="Qwen/Qwen2.5-0.5B-Instruct",
train_dataset=dataset,
args=SFTConfig(
learning_rate=2e-5,
packing=True,
assistant_only_loss=True,
),
)
trainer.train()
```
