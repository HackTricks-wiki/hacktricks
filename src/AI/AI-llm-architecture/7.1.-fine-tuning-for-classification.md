# 7.1. Dostrajanie na potrzeby klasyfikacji

{{#include ../../banners/hacktricks-training.md}}

## Czym jest

Dostrajanie to proces polegający na wykorzystaniu **wstępnie wytrenowanego modelu**, który nauczył się **ogólnych wzorców językowych** na podstawie ogromnych ilości danych, i **dostosowaniu** go do wykonywania **konkretnego zadania** lub rozumienia języka charakterystycznego dla określonej domeny. Osiąga się to poprzez kontynuowanie treningu modelu na mniejszym, specyficznym dla danego zadania zbiorze danych, co pozwala mu dostosować parametry do niuansów nowych danych, jednocześnie wykorzystując rozległą wiedzę, którą już zdobył. Dostrajanie umożliwia modelowi uzyskiwanie dokładniejszych i bardziej adekwatnych wyników w wyspecjalizowanych zastosowaniach bez konieczności trenowania nowego modelu od podstaw.

> [!TIP]
> Ponieważ pre-training LLM, który „rozumie” tekst, jest dość kosztowny, zwykle łatwiej i taniej jest dostroić open source, wstępnie wytrenowane modele, aby wykonywały konkretne zadanie, którego od nich oczekujemy.

> [!TIP]
> Celem tej sekcji jest pokazanie, jak dostroić już wstępnie wytrenowany model, aby zamiast generować nowy tekst LLM wybierał i podawał **prawdopodobieństwa zaklasyfikowania danego tekstu do każdej z podanych kategorii** (na przykład określał, czy tekst jest spamem).

## Przygotowanie zbioru danych

### Rozmiar zbioru danych

Oczywiście, aby dostroić model, potrzebujesz pewnej ilości ustrukturyzowanych danych, których można użyć do wyspecjalizowania LLM. W przykładzie przedstawionym w [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb) GPT2 jest dostrajany do wykrywania, czy wiadomość e-mail jest spamem, czy nie, przy użyciu danych z [https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip](https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip)_._<sup>[[2]](#references)[[3]](#references)</sup>

Ten zbiór danych zawiera znacznie więcej przykładów „nie-spamu” niż „spamu”, dlatego książka sugeruje, aby **użyć tylko tylu przykładów „nie-spamu”, ile jest przykładów „spamu”** (a więc usunąć ze zbioru treningowego wszystkie dodatkowe przykłady). W tym przypadku było to 747 przykładów każdej kategorii.<sup>[[2]](#references)[[1]](#references)</sup>

Następnie **70%** zbioru danych jest używane do **treningu**, **10%** do **walidacji**, a **20%** do **testowania**.

- **Zbiór walidacyjny** jest używany podczas fazy treningu do dostrajania **hiperparametrów** modelu i podejmowania decyzji dotyczących jego architektury, skutecznie pomagając zapobiegać overfittingowi poprzez dostarczanie informacji zwrotnych na temat działania modelu na niewidzianych danych. Umożliwia to iteracyjne ulepszanie modelu bez obciążania końcowej oceny.
- Oznacza to, że chociaż dane zawarte w tym zbiorze nie są bezpośrednio używane do treningu, są wykorzystywane do dostrojenia najlepszych **hiperparametrów**, dlatego ten zbiór nie może być używany do oceny wydajności modelu tak jak zbiór testowy.
- Natomiast **zbiór testowy** jest używany **dopiero po** pełnym wytrenowaniu modelu i zakończeniu wszystkich modyfikacji; zapewnia on bezstronną ocenę zdolności modelu do generalizowania na nowe, niewidziane dane. Ta końcowa ocena na zbiorze testowym daje realistyczny obraz tego, jak model powinien działać w rzeczywistych zastosowaniach.

### Długość wpisów

Ponieważ przykład treningowy zakłada, że wpisy (w tym przypadku teksty wiadomości e-mail) mają tę samą długość, zdecydowano, aby każdy wpis miał rozmiar największego wpisu, dodając identyfikatory `<|endoftext|>` jako padding.<sup>[[2]](#references)</sup>

### Inicjalizacja modelu

Zainicjalizuj model do treningu, używając open-source, wstępnie wytrenowanych wag. Robiliśmy to już wcześniej i postępując zgodnie z instrukcjami z [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb), możesz łatwo to zrobić.<sup>[[2]](#references)</sup>

## Głowica klasyfikacyjna

W tym konkretnym przykładzie (przewidywanie, czy tekst jest spamem, czy nie) nie jesteśmy zainteresowani dostrajaniem zgodnie z pełnym słownictwem GPT2, lecz chcemy, aby nowy model jedynie określał, czy wiadomość e-mail jest spamem (1), czy nie (0). Dlatego zamierzamy **zmodyfikować warstwę końcową, która** podaje prawdopodobieństwa dla poszczególnych tokenów słownika, i zastąpić ją warstwą podającą wyłącznie prawdopodobieństwa tego, że wiadomość jest spamem lub nie (czyli tak, jakby słownik składał się z 2 słów).<sup>[[2]](#references)</sup>
```python
# This code modified the final layer with a Linear one with 2 outs
num_classes = 2
model.out_head = torch.nn.Linear(

in_features=BASE_CONFIG["emb_dim"],

out_features=num_classes
)
```
## Parametry do dostrojenia

Aby szybko przeprowadzić dostrajanie, łatwiej jest nie dostrajać wszystkich parametrów, lecz tylko kilka końcowych. Wynika to z faktu, że niższe warstwy zazwyczaj przechwytują podstawowe struktury językowe i znaczenie, które można zastosować w danym kontekście. Dlatego **dostrojenie tylko ostatnich warstw zwykle jest wystarczające i szybsze**.<sup>[[2]](#references)</sup>
```python
# This code makes all the parameters of the model unrtainable
for param in model.parameters():
param.requires_grad = False

# Allow to fine tune the last layer in the transformer block
for param in model.trf_blocks[-1].parameters():
param.requires_grad = True

# Allow to fine tune the final layer norm
for param in model.final_norm.parameters():

param.requires_grad = True
```
## Wpisy do wykorzystania podczas treningu

W poprzednich sekcjach model LLM był trenowany poprzez zmniejszanie funkcji straty dla każdego przewidywanego tokenu, mimo że niemal wszystkie przewidywane tokeny znajdowały się w zdaniu wejściowym (naprawdę przewidywany był tylko 1 token na końcu), aby model lepiej rozumiał język.

W tym przypadku zależy nam wyłącznie na tym, aby model potrafił przewidzieć, czy wiadomość jest spamem, czy nie, dlatego interesuje nas tylko ostatni przewidywany token. W związku z tym należy zmodyfikować nasze wcześniejsze funkcje straty podczas treningu tak, aby uwzględniały wyłącznie ten token.

Zostało to zaimplementowane w [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb) jako:<sup>[[2]](#references)</sup>
```python
def calc_accuracy_loader(data_loader, model, device, num_batches=None):
model.eval()
correct_predictions, num_examples = 0, 0

if num_batches is None:
num_batches = len(data_loader)
else:
num_batches = min(num_batches, len(data_loader))
for i, (input_batch, target_batch) in enumerate(data_loader):
if i < num_batches:
input_batch, target_batch = input_batch.to(device), target_batch.to(device)

with torch.no_grad():
logits = model(input_batch)[:, -1, :]  # Logits of last output token
predicted_labels = torch.argmax(logits, dim=-1)

num_examples += predicted_labels.shape[0]
correct_predictions += (predicted_labels == target_batch).sum().item()
else:
break
return correct_predictions / num_examples


def calc_loss_batch(input_batch, target_batch, model, device):
input_batch, target_batch = input_batch.to(device), target_batch.to(device)
logits = model(input_batch)[:, -1, :]  # Logits of last output token
loss = torch.nn.functional.cross_entropy(logits, target_batch)
return loss
```
Zauważ, że dla każdego batcha interesują nas wyłącznie **logity przewidywanego ostatniego tokena**.
