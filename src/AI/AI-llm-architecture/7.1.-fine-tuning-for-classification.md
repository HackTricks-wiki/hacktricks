# 7.1. Fine-Tuning pour la classification

{{#include ../../banners/hacktricks-training.md}}

## Qu'est-ce que c'est

Le fine-tuning est le processus qui consiste à prendre un **modèle pré-entraîné** ayant appris des **modèles linguistiques généraux** à partir de vastes quantités de données et à l'**adapter** pour effectuer une **tâche spécifique** ou comprendre un langage propre à un domaine. Cela est réalisé en poursuivant l'entraînement du modèle sur un jeu de données plus petit et spécifique à la tâche, afin de lui permettre d'ajuster ses paramètres pour mieux s'adapter aux particularités des nouvelles données, tout en tirant parti des vastes connaissances qu'il a déjà acquises. Le fine-tuning permet au modèle de fournir des résultats plus précis et pertinents dans des applications spécialisées, sans avoir besoin d'entraîner un nouveau modèle depuis zéro.

> [!TIP]
> Comme le pré-entraînement d'un LLM qui « comprend » le texte est assez coûteux, il est généralement plus facile et moins cher d'effectuer un fine-tuning de modèles open source pré-entraînés afin de leur faire effectuer une tâche spécifique.

> [!TIP]
> L'objectif de cette section est de montrer comment effectuer le fine-tuning d'un modèle déjà pré-entraîné afin que, plutôt que de générer du nouveau texte, le LLM fournisse les **probabilités que le texte donné soit classé dans chacune des catégories données** (par exemple, déterminer si un texte est un spam ou non).

## Préparation du jeu de données

### Taille du jeu de données

Bien sûr, pour effectuer le fine-tuning d'un modèle, vous avez besoin de données structurées à utiliser pour spécialiser votre LLM. Dans l'exemple proposé dans [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb), GPT2 est ajusté pour détecter si un e-mail est un spam ou non à l'aide des données de [https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip](https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip)_._<sup>[[2]](#references)[[3]](#references)</sup>

Ce jeu de données contient beaucoup plus d'exemples de « non-spam » que de « spam ». Le livre suggère donc de **n'utiliser qu'autant d'exemples de « non-spam » que de « spam »** (en supprimant ainsi du jeu de données d'entraînement tous les exemples supplémentaires). Dans ce cas, cela représentait 747 exemples de chaque catégorie.<sup>[[2]](#references)[[1]](#references)</sup>

Ensuite, **70 %** du jeu de données est utilisé pour l'**entraînement**, **10 %** pour la **validation** et **20 %** pour les **tests**.

- L'**ensemble de validation** est utilisé pendant la phase d'entraînement pour ajuster les **hyperparamètres** du modèle et prendre des décisions concernant son architecture, ce qui contribue à prévenir le surapprentissage en fournissant un retour sur les performances du modèle avec des données qu'il n'a pas vues. Il permet d'apporter des améliorations itératives sans fausser l'évaluation finale.
- Cela signifie que, bien que les données incluses dans cet ensemble ne soient pas utilisées directement pour l'entraînement, elles servent à ajuster les meilleurs **hyperparamètres**. Cet ensemble ne peut donc pas être utilisé pour évaluer les performances du modèle comme l'ensemble de test.
- À l'inverse, l'**ensemble de test** est utilisé **uniquement après** que le modèle a été entièrement entraîné et que tous les ajustements ont été effectués. Il fournit une évaluation impartiale de la capacité du modèle à se généraliser à de nouvelles données qu'il n'a pas vues. Cette évaluation finale sur l'ensemble de test donne une indication réaliste des performances attendues du modèle dans des applications réelles.

### Longueur des entrées

Comme l'exemple d'entraînement nécessite des entrées (le texte des e-mails dans ce cas) de même longueur, il a été décidé de rendre chaque entrée aussi grande que la plus longue en ajoutant les ids de `<|endoftext|>` comme padding.<sup>[[2]](#references)</sup>

### Initialiser le modèle

Initialisez le modèle à entraîner à l'aide des poids pré-entraînés open source. Nous l'avons déjà fait auparavant et, en suivant les instructions de [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb), vous pouvez facilement le faire.<sup>[[2]](#references)</sup>

## Tête de classification

Dans cet exemple précis (prédire si un texte est un spam ou non), nous ne souhaitons pas effectuer le fine-tuning en fonction de l'ensemble du vocabulaire de GPT2, mais voulons seulement que le nouveau modèle indique si l'e-mail est un spam (1) ou non (0). Nous allons donc **modifier la couche finale qui** fournit les probabilités pour chaque token du vocabulaire afin d'utiliser une couche qui fournit uniquement les probabilités qu'il s'agisse d'un spam ou non (comme s'il s'agissait d'un vocabulaire de 2 mots).<sup>[[2]](#references)</sup>
```python
# This code modified the final layer with a Linear one with 2 outs
num_classes = 2
model.out_head = torch.nn.Linear(

in_features=BASE_CONFIG["emb_dim"],

out_features=num_classes
)
```
## Paramètres à ajuster

Pour effectuer un fine-tuning rapidement, il est plus facile de ne pas ajuster tous les paramètres, mais seulement certains des derniers. En effet, on sait que les couches inférieures capturent généralement les structures et la sémantique de base du langage qui sont applicables. Ainsi, **le fine-tuning des dernières couches suffit généralement et est plus rapide**.<sup>[[2]](#references)</sup>
```python
# This code makes all the parameters of the model unrtainable
for param in model.parameters():
param.requires_grad = False

# Allow to fine tune the last layer in the transformer block
for param in model.trf_blocks[-1].parameters():
param.requires_grad = True

# Allow to fine tune the final layer norm
for param in model.final_norm.parameters():

param.requires_grad = True
```
## Entrées à utiliser pour l'entraînement

Dans les sections précédentes, le LLM a été entraîné en réduisant la loss de chaque token prédit, même si presque tous les tokens prédits se trouvaient dans la phrase d'entrée (seul 1 à la fin était réellement prédit), afin que le modèle comprenne mieux le langage.

Dans ce cas, nous nous soucions uniquement de la capacité du modèle à prédire si le modèle est un spam ou non, et nous nous intéressons donc uniquement au dernier token prédit. Il est donc nécessaire de modifier nos précédentes fonctions de loss afin de ne prendre en compte que ce token.

Cela est implémenté dans [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb) comme suit :<sup>[[2]](#references)</sup>
```python
def calc_accuracy_loader(data_loader, model, device, num_batches=None):
model.eval()
correct_predictions, num_examples = 0, 0

if num_batches is None:
num_batches = len(data_loader)
else:
num_batches = min(num_batches, len(data_loader))
for i, (input_batch, target_batch) in enumerate(data_loader):
if i < num_batches:
input_batch, target_batch = input_batch.to(device), target_batch.to(device)

with torch.no_grad():
logits = model(input_batch)[:, -1, :]  # Logits of last output token
predicted_labels = torch.argmax(logits, dim=-1)

num_examples += predicted_labels.shape[0]
correct_predictions += (predicted_labels == target_batch).sum().item()
else:
break
return correct_predictions / num_examples


def calc_loss_batch(input_batch, target_batch, model, device):
input_batch, target_batch = input_batch.to(device), target_batch.to(device)
logits = model(input_batch)[:, -1, :]  # Logits of last output token
loss = torch.nn.functional.cross_entropy(logits, target_batch)
return loss
```
Notez que pour chaque batch, nous nous intéressons uniquement aux **logits du dernier token prédit**.
