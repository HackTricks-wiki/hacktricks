# 7.1. Fine-Tuning do klasyfikacji

{{#include ../../banners/hacktricks-training.md}}

## Czym jest

Fine-tuning to proces polegający na wykorzystaniu **wstępnie wytrenowanego modelu**, który nauczył się **ogólnych wzorców językowych** na podstawie ogromnych ilości danych, i **dostosowaniu** go do wykonywania **konkretnego zadania** lub rozumienia języka charakterystycznego dla określonej domeny. Osiąga się to poprzez kontynuowanie treningu modelu na mniejszym zbiorze danych związanym z konkretnym zadaniem, co pozwala mu dostosować parametry do specyfiki nowych danych, jednocześnie wykorzystując szeroką wiedzę, którą już zdobył. Fine-tuning umożliwia modelowi dostarczanie dokładniejszych i bardziej trafnych wyników w wyspecjalizowanych zastosowaniach bez konieczności trenowania nowego modelu od zera.

> [!TIP]
> Ponieważ wstępne trenowanie LLM, który „rozumie” tekst, jest dość kosztowne, zazwyczaj łatwiej i taniej jest wykonać fine-tuning open source, wstępnie wytrenowanych modeli, aby realizowały konkretne zadanie, które chcemy im powierzyć.

> [!TIP]
> Celem tej sekcji jest pokazanie, jak wykonać fine-tuning już wstępnie wytrenowanego modelu, aby zamiast generować nowy tekst, LLM wybierał i podawał **prawdopodobieństwa zaklasyfikowania danego tekstu do każdej z podanych kategorii** (na przykład tego, czy tekst jest spamem).

## Przygotowanie zbioru danych

### Rozmiar zbioru danych

Oczywiście, aby wykonać fine-tuning modelu, potrzebujesz ustrukturyzowanych danych, których użyjesz do wyspecjalizowania LLM. W przykładzie przedstawionym w [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb) GPT2 jest dostrajany do wykrywania, czy wiadomość e-mail jest spamem, czy nie, przy użyciu danych z [https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip](https://archive.ics.uci.edu/static/public/228/sms+spam+collection.zip)_._

Ten zbiór danych zawiera znacznie więcej przykładów „niebędących spamem” niż „spamu”, dlatego książka sugeruje, aby **używać tylko tylu przykładów „niebędących spamem”, ile jest przykładów „spamu”** (a więc usunąć z danych treningowych wszystkie dodatkowe przykłady). W tym przypadku było to po 747 przykładów każdej kategorii.<sup>[[1]](#references)</sup>

Następnie **70%** zbioru danych jest używane do **treningu**, **10%** do **walidacji**, a **20%** do **testowania**.

- **Zbiór walidacyjny** jest używany podczas fazy treningu do dostrajania **hyperparameters** modelu i podejmowania decyzji dotyczących jego architektury, skutecznie pomagając zapobiegać overfittingowi poprzez dostarczanie informacji zwrotnych o działaniu modelu na niewidzianych danych. Umożliwia iteracyjne ulepszanie modelu bez obciążania końcowej oceny.
- Oznacza to, że chociaż dane zawarte w tym zbiorze nie są bezpośrednio używane do treningu, służą do dostrajania najlepszych **hyperparameters**, dlatego tego zbioru nie można używać do oceny wydajności modelu tak jak zbioru testowego.
- Z kolei **zbiór testowy** jest używany **dopiero po** pełnym wytrenowaniu modelu i zakończeniu wszystkich modyfikacji; zapewnia on bezstronną ocenę zdolności modelu do generalizowania na nowe, niewidziane dane. Ta końcowa ocena na zbiorze testowym daje realistyczny obraz tego, jak model powinien działać w rzeczywistych zastosowaniach.

### Długość wpisów

Ponieważ przykład treningowy zakłada, że wpisy (w tym przypadku treści wiadomości e-mail) mają taką samą długość, zdecydowano, aby każdy wpis miał rozmiar równy największemu wpisowi, dodając identyfikatory `<|endoftext|>` jako padding.<sup>[[1]](#references)</sup>

### Inicjalizacja modelu

Zainicjalizuj model przeznaczony do treningu, używając open source, wstępnie wytrenowanych wag. Robiliśmy to już wcześniej — postępując zgodnie z instrukcjami z [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb), możesz łatwo to zrobić.

## Głowica klasyfikacyjna

W tym konkretnym przykładzie (przewidywanie, czy tekst jest spamem, czy nie) nie jesteśmy zainteresowani dostrajaniem modelu zgodnie z pełnym słownictwem GPT2, lecz chcemy, aby nowy model wskazywał, czy wiadomość e-mail jest spamem (1), czy nie (0). Dlatego zamierzamy **zmodyfikować warstwę końcową, która** podaje prawdopodobieństwa dla każdego tokena ze słownika, i zastąpić ją warstwą, która podaje wyłącznie prawdopodobieństwa tego, czy wiadomość jest spamem, czy nie (czyli tak, jakby słownik składał się z 2 słów).<sup>[[1]](#references)</sup>
```python
# This code modified the final layer with a Linear one with 2 outs
num_classes = 2
model.out_head = torch.nn.Linear(

in_features=BASE_CONFIG["emb_dim"],

out_features=num_classes
)
```
## Parametry do dostrojenia

Aby szybko przeprowadzić dostrajanie, łatwiej jest nie dostrajać wszystkich parametrów, lecz tylko niektóre z ostatnich. Wynika to z faktu, że niższe warstwy zazwyczaj przechwytują podstawowe struktury językowe i semantykę, które mają zastosowanie również w innych przypadkach. Dlatego **dostrojenie tylko ostatnich warstw jest zwykle wystarczające i szybsze**.<sup>[[1]](#references)</sup>
```python
# This code makes all the parameters of the model unrtainable
for param in model.parameters():
param.requires_grad = False

# Allow to fine tune the last layer in the transformer block
for param in model.trf_blocks[-1].parameters():
param.requires_grad = True

# Allow to fine tune the final layer norm
for param in model.final_norm.parameters():

param.requires_grad = True
```
## Wpisy używane do trenowania

W poprzednich sekcjach LLM był trenowany poprzez redukowanie loss dla każdego przewidywanego tokenu, mimo że niemal wszystkie przewidywane tokeny znajdowały się w zdaniu wejściowym (tylko 1 na końcu był rzeczywiście przewidywany), aby model lepiej rozumiał język.

W tym przypadku zależy nam wyłącznie na tym, aby model potrafił przewidzieć, czy wiadomość jest spamem, czy nie, więc interesuje nas tylko ostatni przewidywany token. Dlatego należy zmodyfikować nasze poprzednie funkcje loss, aby uwzględniały tylko ten token.<sup>[[1]](#references)</sup>

Zostało to zaimplementowane w [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch06/01_main-chapter-code/ch06.ipynb) jako:
```python
def calc_accuracy_loader(data_loader, model, device, num_batches=None):
model.eval()
correct_predictions, num_examples = 0, 0

if num_batches is None:
num_batches = len(data_loader)
else:
num_batches = min(num_batches, len(data_loader))
for i, (input_batch, target_batch) in enumerate(data_loader):
if i < num_batches:
input_batch, target_batch = input_batch.to(device), target_batch.to(device)

with torch.no_grad():
logits = model(input_batch)[:, -1, :]  # Logits of last output token
predicted_labels = torch.argmax(logits, dim=-1)

num_examples += predicted_labels.shape[0]
correct_predictions += (predicted_labels == target_batch).sum().item()
else:
break
return correct_predictions / num_examples


def calc_loss_batch(input_batch, target_batch, model, device):
input_batch, target_batch = input_batch.to(device), target_batch.to(device)
logits = model(input_batch)[:, -1, :]  # Logits of last output token
loss = torch.nn.functional.cross_entropy(logits, target_batch)
return loss
```
Zauważ, że w przypadku każdego batcha interesują nas wyłącznie **logity przewidziane dla ostatniego tokenu**.
