## **Próbkowanie danych**

**Próbkowanie danych** to kluczowy proces przygotowywania danych do trenowania large language models (LLM), takich jak GPT. Polega on na organizowaniu danych tekstowych w sekwencje wejściowe i docelowe, których model używa do nauki przewidywania następnego słowa (lub tokena) na podstawie wcześniejszych słów. Właściwe próbkowanie danych zapewnia, że model skutecznie rozpoznaje wzorce i zależności językowe.

> [!TIP]
> Cel tej drugiej fazy jest bardzo prosty: **Próbkowanie danych wejściowych i przygotowanie ich do fazy trenowania, zwykle poprzez podzielenie datasetu na zdania o określonej długości oraz wygenerowanie oczekiwanej odpowiedzi.**

### **Dlaczego próbkowanie danych ma znaczenie**

LLM, takie jak GPT, są trenowane do generowania lub przewidywania tekstu poprzez rozumienie kontekstu dostarczonego przez wcześniejsze słowa. Aby to osiągnąć, dane treningowe muszą być uporządkowane w sposób umożliwiający modelowi nauczenie się zależności między sekwencjami słów a następującymi po nich słowami. Takie uporządkowane podejście pozwala modelowi generalizować oraz generować spójny tekst odpowiedni do kontekstu.

### **Kluczowe pojęcia w próbkowaniu danych**

1. **Tokenizacja:** Dzielenie tekstu na mniejsze jednostki nazywane tokenami (np. słowa, subwords lub znaki).
2. **Długość sekwencji (max_length):** Liczba tokenów w każdej sekwencji wejściowej.
3. **Sliding Window:** Metoda tworzenia nakładających się sekwencji wejściowych poprzez przesuwanie okna po tokenizowanym tekście.
4. **Stride:** Liczba tokenów, o którą przesuwa się sliding window w celu utworzenia następnej sekwencji.

### **Przykład krok po kroku**

Przeanalizujmy przykład ilustrujący próbkowanie danych.

**Przykładowy tekst**
```arduino
"Lorem ipsum dolor sit amet, consectetur adipiscing elit."
```
**Tokenizacja**

Załóżmy, że używamy **basic tokenizer**, który dzieli tekst na słowa i znaki interpunkcyjne:
```vbnet
Tokens: ["Lorem", "ipsum", "dolor", "sit", "amet,", "consectetur", "adipiscing", "elit."]
```
**Parametry**

- **Maksymalna długość sekwencji (max_length):** 4 tokeny
- **Krok przesuwania okna (Sliding Window Stride):** 1 token

**Tworzenie sekwencji wejściowych i docelowych**

1. **Podejście z przesuwanym oknem:**
- **Sekwencje wejściowe:** Każda sekwencja wejściowa składa się z `max_length` tokenów.
- **Sekwencje docelowe:** Każda sekwencja docelowa składa się z tokenów, które występują bezpośrednio po odpowiedniej sekwencji wejściowej.
2. **Generowanie sekwencji:**

- **Wejście:**

["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],

- **Cel:**

**Przesuwane okno z krokiem 1:**

- **Pierwsze okno (pozycje 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Cel:** \["ipsum", "dolor", "sit", "amet,"]
- **Drugie okno (pozycje 2-5):** \["ipsum", "dolor", "sit", "amet,"] → **Cel:** \["dolor", "sit", "amet,", "consectetur"]
- **Trzecie okno (pozycje 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Cel:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Czwarte okno (pozycje 4-7):** \["sit", "amet,", "consectetur", "adipiscing"] → **Cel:** \["amet,", "consectetur", "adipiscing", "elit."]

**Zrozumienie kroku**

- **Krok równy 1:** Okno przesuwa się za każdym razem o jeden token do przodu, co prowadzi do dużego nakładania się sekwencji. Może to ułatwiać lepsze uczenie się zależności kontekstowych, ale może również zwiększać ryzyko overfittingu, ponieważ podobne punkty danych są powtarzane.
- **Krok równy 2:** Okno przesuwa się za każdym razem o dwa tokeny do przodu, zmniejszając nakładanie się sekwencji. Ogranicza to redundancję i obciążenie obliczeniowe, ale może powodować pominięcie niektórych niuansów kontekstowych.
- **Krok równy max_length:** Okno przesuwa się do przodu o cały swój rozmiar, co prowadzi do powstania nienakładających się sekwencji. Minimalizuje to redundancję danych, ale może ograniczać zdolność modelu do uczenia się zależności między sekwencjami.

**Przykład z krokiem równym 2:**

Korzystając z tego samego tekstu po tokenizacji i `max_length` równego 4:

- **Pierwsze okno (pozycje 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Cel:** \["ipsum", "dolor", "sit", "amet,"]
- **Drugie okno (pozycje 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Cel:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Trzecie okno (pozycje 5-8):** \["amet,", "consectetur", "adipiscing", "elit."] → **Cel:** \["consectetur", "adipiscing", "elit.", "sed"] _(Zakładając kontynuację)_

# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer
tokenizer = tiktoken.get_encoding("gpt2")

# Create dataset
dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1

## Zaawansowane strategie próbkowania (2023–2025)

### 1. Temperature-Based Mixture Weighting
Najnowocześniejsze LLM-y rzadko są trenowane na pojedynczym korpusie. Zamiast tego próbkują dane z kilku heterogenicznych źródeł (code, web, publikacje akademickie, fora…). Względny udział każdego źródła może znacząco wpływać na wydajność w kolejnych zadaniach. Nowsze modele open source, takie jak Llama 2, wprowadziły **temperature-based sampling scheme**, w którym prawdopodobieństwo wylosowania dokumentu z korpusu *i* staje się
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – surowy procent tokenów korpusu *i*
• *α* („temperature”) – wartość z przedziału (0,1]. α < 1 spłaszcza rozkład, nadając większą wagę mniejszym korpusom wysokiej jakości.

Przy `α < 1` to ważenie spłaszcza rozkład i zwiększa względne prawdopodobieństwo próbkowania mniejszych korpusów. Próbkowanie oparte na temperaturze jest szeroko stosowane do równoważenia wielojęzycznych danych pretrainingu, chociaż potrzebne są limity powtórzeń, aby uniknąć overfittingu małych źródeł.<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
Pamięć GPU jest marnowana, gdy każda sekwencja w batchu jest dopełniana do długości najdłuższego przykładu. **Packing** grupuje wiele krótszych przykładów w bloki o stałej długości. Konwencjonalna implementacja packing wykorzystuje uwzględniającą segmenty lub blokowo-diagonalną funkcję `attention_mask`, dzięki czemu tokeny nie mogą zwracać uwagi na tokeny znajdujące się poza granicami przykładu; implementacje bez paddingu mogą zamiast tego spłaszczać batch i zachowywać granice za pomocą informacji o pozycji. Hugging Face TRL udostępnia packing poprzez `SFTConfig(packing=True)` i opisuje dostępne strategie.<sup>[[5]](#references)</sup>

W konkretnej konfiguracji TRL `max_length` definiuje rozmiar spakowanego bloku, a `packing_strategy` wybiera best-fit decreasing (`"bfd"`) albo wrapped packing. Best-fit decreasing umożliwia batche bez paddingu; jawne `padding_free=True` jest obsługiwane przez FlashAttention 2 lub 3. Nie należy mylić `pad_to_multiple_of` z packing: opcja ta jedynie zaokrągla długości sekwencji z paddingiem do wybranej wielokrotności.<sup>[[5]](#references)</sup>

**Dynamiczne batchowanie lub batchowanie uwzględniające długość to osobna optymalizacja:** nie łączy ono przykładów. Zamiast tego grupuje przykłady o podobnych długościach, dzięki czemu każdy batch z dynamicznym paddingiem zawiera mniej tokenów paddingu. Obecne Hugging Face Transformers udostępnia tę funkcję jako `train_sampling_strategy="group_by_length"`; wstępnie obliczona kolumna `length`, wybrana za pomocą `length_column_name`, pozwala uniknąć obliczania długości każdego przykładu przy uruchamianiu treningu.<sup>[[8]](#references)</sup>

### 3. Deduplication & Quality Filtering
Powtarzające się fragmenty powodują memorization i zapewniają łatwy kanał dla data poisoning. Dlatego uzasadniony pipeline czyszczenia powinien łączyć:

1. **Wykrywanie dokładnych i prawie identycznych duplikatów:** haszuj znormalizowane dokumenty, używaj MinHash/LSH na n-gramach tokenów do skalowalnego wykrywania prawie identycznych duplikatów oraz stosuj metody exact-substring, gdy trzeba usunąć długie powtarzające się fragmenty.<sup>[[6]](#references)</sup>
2. **Quality filtering:** odrzucaj nieprawidłowe kodowania, uszkodzone znaczniki, patologiczne powtórzenia i dokumenty w niewłaściwym języku. Perplexity modelu referencyjnego może być kolejnym sygnałem, ale jej próg należy skalibrować dla danego korpusu, zamiast traktować go jako uniwersalny cutoff.<sup>[[2]](#references)</sup>
3. **Filtrowanie danych wrażliwych:** skanuj pod kątem credentials i PII za pomocą deterministycznych wzorców oraz entity detection, a następnie kieruj wykryte dopasowania do kwarantanny w celu ich sprawdzenia, aby false positives nie usuwały po cichu przydatnych danych treningowych.<sup>[[7]](#references)</sup>

W paperze Llama 2 opisano deduplication i filtrowanie źródeł jako elementy budowy korpusu.<sup>[[2]](#references)</sup> Niezależne badania wykazały, że deduplicating danych treningowych language modelu ogranicza verbatim memorization i może wymagać mniejszej liczby kroków treningowych do uzyskania takiej samej lub lepszej accuracy.<sup>[[6]](#references)</sup>

## Security & Privacy Considerations During Sampling

### Data-Poisoning / Backdoor Attacks

Traktuj discovery korpusu, materialization, filtrowanie i sampling jako jeden supply chain. Manifest zawierający wyłącznie URL-e nie jest niezmiennymi danymi treningowymi:

* **Split-view poisoning:** atakujący sprawia, że zasób wygląda na nieszkodliwy, gdy curator go indeksuje, a następnie zmienia zawartość pobieraną później przez klientów treningowych. Wykorzystuje to lukę czasową między utworzeniem datasetu a jego materialization.
* **Frontrunning poisoning:** atakujący na krótko modyfikuje źródło edytowane przez społeczność bezpośrednio przed przewidywalnym snapshotem lub crawlem, a następnie przywraca je do poprzedniego stanu. Złośliwy sample pozostaje w snapshocie, mimo że aktywna strona wygląda później na czystą.

Obie techniki dotyczą **momentu pobrania sampla**, a nie podatności parsera. Badacze zademonstrowali je przeciwko założeniom zaufania wielu datasetów web-scale, w tym URL expiry/re-registration oraz edycjom ograniczonym czasowo.<sup>[[9]](#references)</sup>

**Sampling może wzmocnić niewielki zatruty klaster.** Istotną metryką nie jest wyłącznie `poison_documents / raw_documents`, lecz liczba przypadków, w których te dokumenty stają się przykładami optymalizacji po uwzględnieniu weighting źródeł, repetition, chunking i overlapping windows. W dużych eksperymentach pre-trainingowych 250 zatrutych dokumentów wywołało porównywalny efekt backdooru w modelach od 600M do 13B parametrów trenowanych na 6B–260B czystych tokenów; dlatego próg alertu oparty wyłącznie na wartości procentowej może stawać się mniej skuteczny wraz ze wzrostem korpusu.<sup>[[10]](#references)</sup>

Na potrzeby audytu ingestion zachowuj zarówno **liczbę unikalnych dokumentów**, jak i **efektywną liczbę ekspozycji**.<sup>[[10]](#references)</sup>
```text
effective_exposure(doc) =
epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```
Praktyczne mechanizmy kontroli wynikające z tych błędów ingestii i ekspozycji obejmują:<sup>[[9]](#references)[[10]](#references)</sup>

* Zamrażaj artefakty adresowane zawartością zamiast ponownie pobierać zmienne adresy URL. Przechowuj oryginalny adres URL, znacznik czasu pobrania, długość w bajtach, skrót oraz wersję transformacji; w przypadku niezgodności skrótu stosuj zasadę fail closed.
* Obliczaj skrót bajtów zarówno przed, jak i po normalizacji. Pierwszy skrót potwierdza integralność źródła, a drugi umożliwia deduplikację i późniejsze odtworzenie.
* Wykonuj deduplikację przed mixture upsampling i generowaniem okien, a następnie ograniczaj ekspozycję dla każdego klastra exact/near-duplicate oraz każdego źródła. Tasowanie zmienia kolejność, ale nie usuwa poison.
* Zapisuj stabilny `document_id` w każdej emitowanej sekwencji, aby podejrzane zachowanie modelu można było prześledzić przez spakowane batch'e do dokumentów źródłowych.
* Przed treningiem bezpośrednio weryfikuj zamrożony manifest, na przykład za pomocą `sha256sum -c corpus.sha256`; nie pobieraj po cichu zamiennika brakującego lub zmienionego obiektu.

### Membership-Inference & Memorization
Długie nakładanie się próbek z przesuwanym oknem powtarza rzadkie ciągi, takie jak numery telefonów lub secret keys, zwiększając ich efektywną częstotliwość. Badania nad prywatnością danych treningowych pokazują, że zduplikowane sekwencje są odtwarzane nieproporcjonalnie często, a deduplikacja znacząco ogranicza tę ekspozycję.<sup>[[7]](#references)</sup>

Praktyczne zalecenia:

* Unikaj zbędnego nakładania się próbek, gdy prowadziłoby to do wielokrotnej ekspozycji wrażliwych lub unikalnych ciągów.
* Wykonuj deduplikację przed podziałem danych, aby niemal identyczne próbki nie leak między zbiorami treningowym i ewaluacyjnym.
