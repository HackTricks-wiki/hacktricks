## **データサンプリング**

**データサンプリング**は、GPTのような大規模言語モデル（LLM）のトレーニング用データを準備するうえで重要なプロセスです。これは、モデルが前の単語に基づいて次の単語（またはトークン）を予測する方法を学習するために使用する入力シーケンスとターゲットシーケンスにテキストデータを整理する作業です。適切なデータサンプリングにより、モデルは言語のパターンと依存関係を効果的に捉えられるようになります。

> [!TIP]
> この第2段階の目的は非常にシンプルです：**入力データをサンプリングし、通常はデータセットを特定の長さの文に分割し、期待される応答も生成することで、トレーニング段階に備えます。**

### **データサンプリングが重要な理由**

GPTなどのLLMは、前の単語によって提供されるコンテキストを理解することで、テキストを生成または予測するようにトレーニングされます。これを実現するには、モデルが単語のシーケンスと、それに続く単語との関係を学習できるようにトレーニングデータを構造化する必要があります。この構造化されたアプローチにより、モデルは一貫性があり、文脈に適したテキストを汎化して生成できるようになります。

### **データサンプリングの主要概念**

1. **トークン化:** テキストをトークンと呼ばれる小さな単位（単語、サブワード、文字など）に分割すること。
2. **シーケンス長（max_length）:** 各入力シーケンスに含まれるトークンの数。
3. **スライディングウィンドウ:** トークン化されたテキスト上でウィンドウを移動させ、重複する入力シーケンスを作成する方法。
4. **ストライド:** 次のシーケンスを作成するためにスライディングウィンドウを前方へ移動させるトークン数。

### **ステップごとの例**

データサンプリングを説明するために、例を見ていきましょう。

**テキスト例**
```arduino
"Lorem ipsum dolor sit amet, consectetur adipiscing elit."
```
**トークン化**

テキストを単語と句読点に分割する**基本的なトークナイザー**を使用するとします：
```vbnet
Tokens: ["Lorem", "ipsum", "dolor", "sit", "amet,", "consectetur", "adipiscing", "elit."]
```
**パラメータ**

- **最大シーケンス長 (max_length):** 4 tokens
- **Sliding Window Stride:** 1 token

**入力シーケンスとターゲットシーケンスの作成**

1. **Sliding Window Approach:**
- **入力シーケンス:** 各入力シーケンスは `max_length` 個の tokens で構成されます。
- **ターゲットシーケンス:** 各ターゲットシーケンスは、対応する入力シーケンスの直後に続く tokens で構成されます。
2. **シーケンスの生成:**

<table><thead><tr><th width="177">Window Position</th><th>Input Sequence</th><th>Target Sequence</th></tr></thead><tbody><tr><td>1</td><td>["Lorem", "ipsum", "dolor", "sit"]</td><td>["ipsum", "dolor", "sit", "amet,"]</td></tr><tr><td>2</td><td>["ipsum", "dolor", "sit", "amet,"]</td><td>["dolor", "sit", "amet,", "consectetur"]</td></tr><tr><td>3</td><td>["dolor", "sit", "amet,", "consectetur"]</td><td>["sit", "amet,", "consectetur", "adipiscing"]</td></tr><tr><td>4</td><td>["sit", "amet,", "consectetur", "adipiscing"]</td><td>["amet,", "consectetur", "adipiscing", "elit."]</td></tr></tbody></table>

3. **結果として得られる入力配列とターゲット配列:**

- **入力:**

```python
[
["Lorem", "ipsum", "dolor", "sit"],
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
]
```

- **ターゲット:**

```python
[
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
["amet,", "consectetur", "adipiscing", "elit."],
]
```

**視覚的な表現**

<table><thead><tr><th width="222">Token Position</th><th>Token</th></tr></thead><tbody><tr><td>1</td><td>Lorem</td></tr><tr><td>2</td><td>ipsum</td></tr><tr><td>3</td><td>dolor</td></tr><tr><td>4</td><td>sit</td></tr><tr><td>5</td><td>amet,</td></tr><tr><td>6</td><td>consectetur</td></tr><tr><td>7</td><td>adipiscing</td></tr><tr><td>8</td><td>elit.</td></tr></tbody></table>

**Stride 1 の Sliding Window:**

- **最初の Window (Positions 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **ターゲット:** \["ipsum", "dolor", "sit", "amet,"]
- **2 番目の Window (Positions 2-5):** \["ipsum", "dolor", "sit", "amet,"] → **ターゲット:** \["dolor", "sit", "amet,", "consectetur"]
- **3 番目の Window (Positions 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **ターゲット:** \["sit", "amet,", "consectetur", "adipiscing"]
- **4 番目の Window (Positions 4-7):** \["sit", "amet,", "consectetur", "adipiscing"] → **ターゲット:** \["amet,", "consectetur", "adipiscing", "elit."]

**Stride の理解**

- **Stride 1:** Window は毎回 1 token ずつ前進するため、大きく重複したシーケンスになります。これによりコンテキスト上の関係をより適切に学習できる可能性がありますが、類似したデータポイントが繰り返されるため、overfitting のリスクが高まる可能性があります。
- **Stride 2:** Window は毎回 2 tokens ずつ前進するため、重複が減少します。これにより冗長性と計算負荷が低下しますが、コンテキスト上の細かなニュアンスを取り逃す可能性があります。
- **Stride が max_length と等しい場合:** Window は Window 全体のサイズ分だけ前進するため、重複しないシーケンスになります。これによりデータの冗長性は最小限になりますが、シーケンス間の依存関係を学習するモデルの能力が制限される可能性があります。

**Stride 2 の例:**

同じ tokenized text と `max_length` 4 を使用します。

- **最初の Window (Positions 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **ターゲット:** \["ipsum", "dolor", "sit", "amet,"]
- **2 番目の Window (Positions 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **ターゲット:** \["sit", "amet,", "consectetur", "adipiscing"]
- **3 番目の Window (Positions 5-8):** \["amet,", "consectetur", "adipiscing", "elit."] → **ターゲット:** \["consectetur", "adipiscing", "elit.", "sed"] _(続きがあると仮定)_

## Code Example

[https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb) のコード例を使って、これをさらに詳しく理解しましょう。<sup>[[1]](#references)</sup>
```python
# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer
tokenizer = tiktoken.get_encoding("gpt2")

# Create dataset
dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1
[
```

## 高度な Sampling Strategies（2023-2025）

### 1. Temperature-Based Mixture Weighting
State-of-the-art LLM は、単一の corpus で学習されることはほとんどありません。代わりに、複数の異種データソース（code、web、academic papers、forums…）から sampling します。各ソースの相対的な割合は、下流の性能に大きな影響を与える可能性があります。Llama 2 などの最近の open-source model では、**temperature-based sampling scheme** が導入され、corpus *i* から document を抽出する確率は次のようになります。
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – コーパス *i* の raw token 割合
• *α*（「temperature」）– (0,1] の値。α < 1 にすると分布が平坦化され、小規模で高品質なコーパスにより大きな重みが与えられます。

`α < 1` にすると、この重み付けによって分布が平坦化され、小規模なコーパスの相対的なサンプリング確率が高まります。Temperature-based sampling は、多言語の事前学習データのバランス調整に広く使用されていますが、小規模なソースの overfitting を避けるには repetition limits が必要です。<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
バッチ内のすべての sequence を最も長い example に合わせて padding すると、GPU memory が無駄になります。**Packing** は、複数の短い example を固定長の block にまとめます。従来の packed 実装では、segment-aware または block-diagonal の `attention_mask` を使用し、token が example の境界を越えて attend できないようにします。一方、padding-free 実装では、batch を flatten し、position 情報によって境界を維持できます。Hugging Face TRL は `SFTConfig(packing=True)` を通じて packing を提供し、利用可能な strategy をドキュメント化しています。<sup>[[5]](#references)</sup>

具体的な TRL configuration では、`max_length` が packed block の size を定義し、`packing_strategy` が best-fit decreasing (`"bfd"`) または wrapped packing のいずれかを選択します。Best-fit decreasing は padding-free batch を有効にし、明示的な `padding_free=True` は FlashAttention 2 または 3 でサポートされます。`pad_to_multiple_of` と packing を混同しないでください。これは padding された sequence length を、指定した multiple に丸めるだけです。<sup>[[5]](#references)</sup>

**Dynamic または length-aware batching は別の optimization です:** example を連結するのではなく、似た length の example をまとめ、各 dynamic に padding された batch に含まれる padding token を減らします。現在の Hugging Face Transformers では、これを `train_sampling_strategy="group_by_length"` として利用できます。`length_column_name` で選択した事前計算済みの `length` column を使用すると、training 開始時にすべての example の length を計算する必要がなくなります。<sup>[[8]](#references)</sup>

### 3. Deduplication & Quality Filtering
重複した passage は memorization を引き起こし、data poisoning の容易な channel になります。したがって、信頼できる cleaning pipeline は以下を組み合わせます。

1. **Exact and near-duplicate detection:** 正規化した document を hash し、token n-gram に対して MinHash/LSH を使用して scalable な near-duplicate の検出を行い、長い重複 passage を削除する必要がある場合は exact-substring method を使用します。<sup>[[6]](#references)</sup>
2. **Quality filtering:** 無効な encoding、壊れた markup、病的な repetition、誤った language の document を除外します。Reference-model perplexity も別の signal になりますが、その threshold は universal な cutoff として扱うのではなく、corpus に合わせて calibration する必要があります。<sup>[[2]](#references)</sup>
3. **Sensitive-data filtering:** deterministic pattern と entity detection を併用して credential と PII を scan し、false positive によって有用な training data が気付かないうちに消去されないよう、match を review 用に quarantine します。<sup>[[7]](#references)</sup>

Llama 2 paper は、corpus construction の一環として deduplication と source filtering について説明しています。<sup>[[2]](#references)</sup> 独立した research では、language-model training data の deduplication により verbatim memorization が減少し、同等以上の accuracy に必要な training step 数も減らせることが確認されています。<sup>[[6]](#references)</sup>

## Sampling During の Security & Privacy Considerations

### Data-Poisoning / Backdoor Attacks

corpus の discovery、materialization、filtering、sampling を、1 つの supply chain として扱います。URL だけを含む manifest は immutable な training data ではありません。

* **Split-view poisoning:** curator が resource を index するときは benign に見せ、その後、training client が download する内容を変更します。これは dataset creation と materialization の間にある time gap を悪用します。
* **Frontrunning poisoning:** 攻撃者は、予測可能な snapshot または crawl の直前に crowd-edited source を短時間変更し、その後で元に戻します。後から live page が clean に見えても、malicious sample は snapshot 内に残ります。

どちらの technique も parser の vulnerability ではなく、**sample がいつ fetch されるか**を標的にします。Researchers は、URL expiry/re-registration や time-bounded edits などを含む、複数の web-scale dataset の trust assumption に対してこれらを実証しました。<sup>[[9]](#references)</sup>

**Sampling は小規模な poisoned cluster を増幅する可能性があります。** 関連する metric は単なる `poison_documents / raw_documents` ではなく、source weighting、repetition、chunking、overlapping window の後に、それらの document が optimization example になる回数です。大規模な pre-training experiment では、6B から 260B の clean token で training された 600M から 13B parameter の model 全体で、250 個の poisoned document が同程度の backdoor effect を生みました。そのため、割合だけに基づく alert threshold は、corpus が大きくなるほど弱くなる可能性があります。<sup>[[10]](#references)</sup>

ingestion audit では、**unique-document count** と **effective exposure count** の両方を保持してください。<sup>[[10]](#references)</sup>
```text
effective_exposure(doc) =
epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```
これらの ingestion および exposure の失敗から導き出される実践的な制御策には、次のものがあります。<sup>[[9]](#references)[[10]](#references)</sup>

* mutable な URL を再取得するのではなく、content-addressed artifact を freeze する。元の URL、取得時刻、byte length、digest、transformation version を保存し、digest が一致しない場合は fail closed する。
* normalization の前後で bytes を hash する。最初の digest は source integrity を証明し、2 番目の digest は deduplication と後での reproduction を可能にする。
* mixture upsampling と window generation の前に deduplicate し、その後、exact/near-duplicate cluster ごと、および origin ごとに exposure を制限する。Shuffling は順序を変えるだけで、poison を除去することはない。
* すべての emitted sequence に stable な `document_id` を記録し、疑わしい model behavior を packed batch 経由で source document まで追跡できるようにする。
* training 前に frozen manifest を直接検証する。たとえば `sha256sum -c corpus.sha256` を使用し、欠落または変更された object の代替品を黙って download しない。

### Membership-Inference & Memorization
sliding-window sample 間の長い overlap により、電話番号や secret key などの rare string が繰り返され、実効頻度が増加する。training-data privacy に関する研究では、重複した sequence が不均衡に何度も再生成され、deduplication によってこの exposure が大幅に削減されることが示されています。<sup>[[7]](#references)</sup>

実践的な推奨事項:

* sensitive または unique な string を繰り返し exposure することになる場合は、不要な overlap を避ける。
* data を split する前に deduplicate し、ほぼ同一の sample が training set と evaluation set の間で leak しないようにする。
