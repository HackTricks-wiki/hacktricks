## **Usampulishaji wa Data**

**Usampulishaji wa Data** ni mchakato muhimu wa kuandaa data kwa ajili ya kufundisha large language models (LLMs) kama GPT. Unahusisha kupanga data ya maandishi kuwa mfuatano wa ingizo na lengwa ambao model hutumia kujifunza jinsi ya kutabiri neno (au token) linalofuata kwa kutegemea maneno yaliyotangulia. Usampulishaji sahihi wa data huhakikisha kuwa model inanasa ipasavyo mifumo na utegemeano wa lugha.

> [!TIP]
> Lengo la awamu hii ya pili ni rahisi sana: **Sampuli data ya ingizo na iandae kwa awamu ya mafunzo, kwa kawaida kwa kugawa dataset kuwa sentensi zenye urefu maalum na pia kuzalisha jibu linalotarajiwa.**

### **Kwa Nini Usampulishaji wa Data ni Muhimu**

LLMs kama GPT hufundishwa kuzalisha au kutabiri maandishi kwa kuelewa muktadha unaotolewa na maneno yaliyotangulia. Ili kufanikisha hili, data ya mafunzo lazima ipangwe kwa njia ambayo inaiwezesha model kujifunza uhusiano kati ya mfuatano wa maneno na maneno yanayofuata. Mpangilio huu huwezesha model kufanya generalization na kuzalisha maandishi yenye upatanisho na yanayohusiana kimuktadha.

### **Dhana Muhimu katika Usampulishaji wa Data**

1. **Tokenization:** Kugawanya maandishi kuwa vipande vidogo vinavyoitwa tokens (kwa mfano, maneno, subwords, au herufi).
2. **Urefu wa Mfuatano (max_length):** Idadi ya tokens katika kila mfuatano wa ingizo.
3. **Sliding Window:** Mbinu ya kuunda mifuatano ya ingizo inayopishana kwa kusogeza dirisha juu ya maandishi yaliyofanyiwa tokenization.
4. **Stride:** Idadi ya tokens ambazo sliding window husogeza mbele ili kuunda mfuatano unaofuata.

### **Mfano wa Hatua kwa Hatua**

Hebu tupitie mfano ili kuonyesha usampulishaji wa data.

- **Dirisha la Kwanza (Nafasi 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Lengwa:** \["ipsum", "dolor", "sit", "amet,"]
- **Dirisha la Pili (Nafasi 2-5):** \["ipsum", "dolor", "sit", "amet,"] → **Lengwa:** \["dolor", "sit", "amet,", "consectetur"]
- **Dirisha la Tatu (Nafasi 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Lengwa:** \["sit", "amet,", "consectetur", "adipiscing"]

**Kuelewa Hatua**

- **Hatua ya 1:** Dirisha husogea mbele kwa tokeni moja kila mara, hivyo kusababisha mifuatano inayopishana kwa kiwango kikubwa. Hii inaweza kuboresha ujifunzaji wa uhusiano wa kimuktadha, lakini inaweza kuongeza hatari ya overfitting kwa sababu pointi za data zinazofanana hurudiwa.
- **Hatua ya 2:** Dirisha husogea mbele kwa tokeni mbili kila mara, hivyo kupunguza mwingiliano. Hii hupunguza urudufu na mzigo wa computational, lakini inaweza kukosa baadhi ya nuances za kimuktadha.
- **Hatua Sawa na max_length:** Dirisha husogea mbele kwa ukubwa wote wa dirisha, hivyo kusababisha mifuatano isiyopishana. Hii hupunguza urudufu wa data, lakini inaweza kuzuia uwezo wa model kujifunza dependencies kati ya mifuatano.

**Mfano wenye Hatua ya 2:**

Kwa kutumia maandishi yale yale yaliyowekwa tokeni na `max_length` ya 4:

## Code Example

Hebu tuelewe hili vizuri zaidi kupitia mfano wa code kutoka [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb):<sup>[[1]](#references)</sup>
```python
# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer
tokenizer = tiktoken.get_encoding("gpt2")

# Create dataset
dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1
[
# Input

[  367,  2885,  1464,  1807],
[ 2885,  1464,  1807,  3619],

[ 1807,  3619,   402,   271],
[ 3619,   402,   271, 10899],
[  402,   271, 10899,  2138],

# Target
tensor([[  367,  2885,  1464,  1807],
```

## Mikakati ya Juu ya Sampling (2023-2025)

### 1. Temperature-Based Mixture Weighting
LLM za kisasa zenye utendaji wa hali ya juu mara chache hufunzwa kwa kutumia corpus moja tu.  Badala yake, huchukua sampuli kutoka kwenye vyanzo kadhaa vya data visivyo na ufanano (code, web, makala za kitaaluma, forums…).  Uwiano wa kila chanzo unaweza kuathiri kwa kiasi kikubwa utendaji wa baadaye.  Miundo ya hivi karibuni ya open-source kama vile Llama 2 ilianzisha **temperature-based sampling scheme** ambapo uwezekano wa kuchora document kutoka kwenye corpus *i* huwa
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – asilimia ghafi ya tokeni za corpus *i*  
• *α* ("temperature") – thamani katika (0,1].  α < 1 husawazisha usambazaji, na kuzipa corpus ndogo zenye ubora wa juu uzito zaidi.

Kwa `α < 1`, uzani huu husawazisha usambazaji na kuongeza uwezekano wa kulisha sampuli kutoka corpus ndogo. Temperature-based sampling imetumika sana kusawazisha data ya pretraining ya lugha nyingi, ingawa vikomo vya marudio vinahitajika ili kuzuia overfitting ya vyanzo vidogo.<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
Kumbukumbu ya GPU hupotea kila sequence katika batch inapowekwa padding hadi kufikia mfano mrefu zaidi. **Packing** hukusanya mifano mifupi kadhaa katika blocks zenye urefu maalum. Utekelezaji wa kawaida wa packed hutumia `attention_mask` inayotambua segments au block-diagonal ili tokens zisiweze kuangalia mipaka ya mifano; utekelezaji usiotumia padding unaweza badala yake ku-flatten batch na kuhifadhi mipaka kwa kutumia taarifa za position. Hugging Face TRL hutoa packing kupitia `SFTConfig(packing=True)` na huandika mikakati inayopatikana.<sup>[[5]](#references)</sup>

Kwa configuration maalum ya TRL, `max_length` hufafanua ukubwa wa packed block na `packing_strategy` huchagua best-fit decreasing (`"bfd"`) au wrapped packing. Best-fit decreasing huwezesha batches zisizotumia padding; `padding_free=True` ya moja kwa moja inaungwa mkono na FlashAttention 2 au 3. Usichanganye `pad_to_multiple_of` na packing: huviringisha tu urefu wa sequences zenye padding hadi kufikia multiple iliyochaguliwa.<sup>[[5]](#references)</sup>

**Dynamic au length-aware batching ni optimization tofauti:** haiunganishi mifano. Badala yake, hukusanya mifano yenye urefu unaofanana ili kila batch inayowekwa padding dynamically iwe na padding tokens chache. Hugging Face Transformers ya sasa hutoa hii kama `train_sampling_strategy="group_by_length"`; column ya `length` iliyohesabiwa mapema na kuchaguliwa kupitia `length_column_name` huepusha kukokotoa urefu wa kila mfano mafunzo yanapoanza.<sup>[[8]](#references)</sup>

### 3. Deduplication & Quality Filtering
Passages zinazorudiwa husababisha memorization na hutoa channel rahisi ya data poisoning. Kwa hiyo, pipeline ya usafishaji inayoweza kutetewa huunganisha:

1. **Ugunduzi wa nakala halisi na zinazokaribiana:** hash documents zilizonormalishwa, tumia MinHash/LSH juu ya token n-grams kwa ugunduzi unaoweza kupanuka wa nakala zinazokaribiana, na tumia mbinu za exact-substring wakati passages ndefu zinazorudiwa lazima ziondolewe.<sup>[[6]](#references)</sup>
2. **Quality filtering:** kata encodings zisizo halali, markup iliyoharibika, marudio yasiyo ya kawaida, na documents za lugha isiyo sahihi. Perplexity ya reference-model inaweza kuwa signal nyingine, lakini threshold yake lazima icalibratiwe kwa corpus badala ya kutazamwa kama cutoff ya jumla.<sup>[[2]](#references)</sup>
3. **Sensitive-data filtering:** tafuta credentials na PII kwa kutumia patterns za deterministic pamoja na entity detection, kisha weka matches kwenye quarantine kwa ajili ya review ili false positives zisifute kimya kimya training data yenye manufaa.<sup>[[7]](#references)</sup>

Karatasi ya Llama 2 inaeleza deduplication na source filtering kama sehemu ya ujenzi wa corpus.<sup>[[2]](#references)</sup> Utafiti huru uligundua kuwa kufanya deduplication ya language-model training data hupunguza memorization ya verbatim na kunaweza kuhitaji training steps chache ili kupata accuracy sawa au bora zaidi.<sup>[[6]](#references)</sup>

## Security & Privacy Considerations During Sampling

### Data-Poisoning / Backdoor Attacks

Chukulia corpus discovery, materialization, filtering, na sampling kama supply chain moja. Manifest iliyo na URLs pekee si training data isiyoweza kubadilishwa:

* **Split-view poisoning:** mshambuliaji hufanya resource ionekane salama curator anapoi-index, kisha hubadilisha kile ambacho training clients hupakua baadaye. Hii hutumia pengo la muda kati ya uundaji wa dataset na materialization.
* **Frontrunning poisoning:** mshambuliaji hubadilisha kwa muda mfupi source iliyohaririwa na crowd mara moja kabla ya snapshot au crawl inayotabirika, kisha huirejesha baadaye. Sample hasidi hubaki kwenye snapshot ingawa ukurasa unaoonekana baadaye huwa safi.

Mbinu zote mbili zinalenga **wakati sample inapofetchiwa**, si vulnerability ya parser. Watafiti walizionyesha dhidi ya trust assumptions za datasets kadhaa za web-scale, zikiwemo URL expiry/re-registration na edits zenye muda maalum.<sup>[[9]](#references)</sup>

**Sampling inaweza kukuza cluster ndogo yenye poisoning.** Metric muhimu si `poison_documents / raw_documents` pekee, bali ni idadi ya mara ambazo documents hizo huwa optimization examples baada ya source weighting, repetition, chunking, na overlapping windows. Katika majaribio makubwa ya pre-training, documents 250 zenye poisoning zilitoa backdoor effect inayolingana kwenye models kutoka 600M hadi 13B parameters zilizofunzwa kwa tokens safi bilioni 6 hadi bilioni 260; kwa hiyo, alert threshold inayotegemea asilimia pekee inaweza kuwa dhaifu zaidi corpus inapokua.<sup>[[10]](#references)</sup>

Kwa audit ya ingestion, hifadhi **unique-document count** pamoja na **effective exposure count**.<sup>[[10]](#references)</sup>
```text
effective_exposure(doc) =
epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```
Vidhibiti vya kiutendaji vinavyotokana na hitilafu hizi za ingestion na exposure ni pamoja na:<sup>[[9]](#references)[[10]](#references)</sup>

* Freeze artifacts zinazotambuliwa kwa anwani ya maudhui badala ya ku-fetch tena URLs zinazoweza kubadilika. Hifadhi URL ya awali, muda wa retrieval, urefu wa bytes, digest, na toleo la transformation; funga mfumo kwa kushindwa iwapo digest hailingani.
* Hash bytes kabla na baada ya normalization. Digest ya kwanza inathibitisha uadilifu wa chanzo; ya pili huwezesha deduplication na reproduction ya baadaye.
* Fanya deduplication kabla ya mixture upsampling na utengenezaji wa windows, kisha weka kikomo cha exposure kwa kila cluster ya exact/near-duplicate na kwa kila origin. Shuffling hubadilisha mpangilio, lakini haiondoi poison.
* Andika `document_id` thabiti katika kila sequence inayotolewa ili tabia ya modeli inayotiliwa shaka iweze kufuatiliwa kupitia packed batches hadi kwenye source documents.
* Kabla ya training, thibitisha manifest iliyogandishwa moja kwa moja, kwa mfano kwa `sha256sum -c corpus.sha256`; usipakue replacement kimya-kimya kwa object iliyokosekana au iliyobadilika.

### Membership-Inference & Memorization
Overlap ndefu kati ya samples za sliding-window hurudia strings adimu kama nambari za simu au secret keys, na kuongeza frequency yao halisi. Utafiti kuhusu faragha ya training-data unaonyesha kuwa sequences zilizorudiwa huzalishwa tena mara nyingi kupita kiasi na kwamba deduplication hupunguza exposure hii kwa kiasi kikubwa.<sup>[[7]](#references)</sup>

Mapendekezo ya kiutendaji:

* Epuka overlap isiyo ya lazima pale ambapo ingerudia ku-expose strings nyeti au za kipekee.
* Fanya deduplication kabla ya kugawa data ili samples zinazokaribiana zisileak kati ya training na evaluation sets.
