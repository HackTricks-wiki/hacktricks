## **Amostragem de Dados**

A **Amostragem de Dados** é um processo crucial na preparação de dados para o treinamento de large language models (LLMs), como o GPT. Ela envolve organizar dados de texto em sequências de entrada e de destino que o modelo utiliza para aprender a prever a próxima palavra (ou token) com base nas palavras anteriores. A amostragem adequada de dados garante que o modelo capture padrões e dependências linguísticas de forma eficaz.

> [!TIP]
> O objetivo desta segunda fase é muito simples: **Amostre os dados de entrada e prepare-os para a fase de treinamento, geralmente separando o dataset em sentenças de um comprimento específico e gerando também a resposta esperada.**

### **Por Que a Amostragem de Dados é Importante**

LLMs, como o GPT, são treinados para gerar ou prever texto compreendendo o contexto fornecido pelas palavras anteriores. Para isso, os dados de treinamento devem ser estruturados de forma que o modelo possa aprender a relação entre sequências de palavras e as palavras subsequentes. Essa abordagem estruturada permite que o modelo generalize e gere textos coerentes e contextualmente relevantes.

### **Conceitos Fundamentais na Amostragem de Dados**

1. **Tokenização:** Divisão do texto em unidades menores chamadas tokens (por exemplo, palavras, subpalavras ou caracteres).
2. **Comprimento da Sequência (max_length):** O número de tokens em cada sequência de entrada.
3. **Janela Deslizante:** Um método para criar sequências de entrada sobrepostas movendo uma janela sobre o texto tokenizado.
4. **Stride:** O número de tokens que a janela deslizante avança para criar a próxima sequência.

### **Exemplo Passo a Passo**

Vamos analisar um exemplo para ilustrar a amostragem de dados.

**Texto de Exemplo**
```arduino
"Lorem ipsum dolor sit amet, consectetur adipiscing elit."
```
**Tokenização**

Suponha que usamos um **tokenizador básico** que divide o texto em palavras e sinais de pontuação:
```vbnet
Tokens: ["Lorem", "ipsum", "dolor", "sit", "amet,", "consectetur", "adipiscing", "elit."]
```
**Parâmetros**

- **Comprimento Máximo da Sequência (max_length):** 4 tokens
- **Passo da Janela Deslizante:** 1 token

**Criando Sequências de Entrada e Alvo**

1. **Abordagem da Janela Deslizante:**
- **Sequências de Entrada:** Cada sequência de entrada consiste em `max_length` tokens.
- **Sequências Alvo:** Cada sequência alvo consiste nos tokens que seguem imediatamente a sequência de entrada correspondente.
2. **Gerando Sequências:**

3. **Matrizes de Entrada e Alvo Resultantes:**

- **Entrada:**

```python
[
["Lorem", "ipsum", "dolor", "sit"],
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
]
```

- **Alvo:**

```python
[
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
["amet,", "consectetur", "adipiscing", "elit."],
]
```

**Janela Deslizante com Stride 1:**

- **Primeira Janela (Posições 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Alvo:** \["ipsum", "dolor", "sit", "amet,"]
- **Segunda Janela (Posições 2-5):** \["ipsum", "dolor", "sit", "amet,"] → **Alvo:** \["dolor", "sit", "amet,", "consectetur"]
- **Terceira Janela (Posições 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Alvo:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Quarta Janela (Posições 4-7):** \["sit", "amet,", "consectetur", "adipiscing"] → **Alvo:** \["amet,", "consectetur", "adipiscing", "elit."]

**Entendendo o Stride**

- **Stride de 1:** A janela avança um token por vez, resultando em sequências altamente sobrepostas. Isso pode levar a um aprendizado melhor das relações contextuais, mas pode aumentar o risco de overfitting, pois pontos de dados semelhantes são repetidos.
- **Stride de 2:** A janela avança dois tokens por vez, reduzindo a sobreposição. Isso diminui a redundância e a carga computacional, mas pode deixar passar algumas nuances contextuais.
- **Stride Igual a max_length:** A janela avança pelo tamanho total da janela, resultando em sequências não sobrepostas. Isso minimiza a redundância dos dados, mas pode limitar a capacidade do modelo de aprender dependências entre sequências.

**Exemplo com Stride de 2:**

Usando o mesmo texto tokenizado e `max_length` igual a 4:

- **Primeira Janela (Posições 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Alvo:** \["ipsum", "dolor", "sit", "amet,"]
- **Segunda Janela (Posições 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Alvo:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Terceira Janela (Posições 5-8):** \["amet,", "consectetur", "adipiscing", "elit."] → **Alvo:** \["consectetur", "adipiscing", "elit.", "sed"] _(Supondo uma continuação)_

## Exemplo de Código

Vamos entender isso melhor a partir de um exemplo de código de [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb):<sup>[[1]](#references)</sup>
```python
# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer
tokenizer = tiktoken.get_encoding("gpt2")

# Create dataset
dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1
[

[  367,  2885,  1464,  1807],

tensor([[  367,  2885,  1464,  1807],
```

## Estratégias Avançadas de Amostragem (2023-2025)

### 1. Ponderação da Mistura Baseada em Temperatura
LLMs de última geração raramente são treinados em um único corpus. Em vez disso, eles fazem amostragem a partir de várias fontes de dados heterogêneas (code, web, artigos acadêmicos, fóruns…). A proporção relativa de cada fonte pode afetar significativamente o desempenho downstream. Modelos open-source recentes, como o Llama 2, introduziram um **esquema de amostragem baseado em temperatura**, no qual a probabilidade de extrair um documento do corpus *i* passa a ser
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – porcentagem bruta de tokens do corpus *i*
• *α* ("temperatura") – um valor em (0,1]. α < 1 achata a distribuição, atribuindo mais peso a corpora menores e de alta qualidade.

Com `α < 1`, essa ponderação achata a distribuição e aumenta a probabilidade relativa de sampling de corpora menores. O sampling baseado em temperatura tem sido amplamente utilizado para equilibrar dados de pretraining multilíngue, embora sejam necessários limites de repetição para evitar overfitting em fontes pequenas.<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
A memória da GPU é desperdiçada quando cada sequência de um batch recebe padding até o exemplo mais longo. **Packing** agrupa vários exemplos mais curtos em blocos de tamanho fixo. Uma implementação convencional de packing usa uma `attention_mask` ciente de segmentos ou em bloco diagonal, para que os tokens não possam prestar atenção entre os limites dos exemplos; implementações sem padding podem, em vez disso, achatar o batch e preservar os limites com informações de posição. O Hugging Face TRL disponibiliza packing por meio de `SFTConfig(packing=True)` e documenta as estratégias disponíveis.<sup>[[5]](#references)</sup>

Em uma configuração concreta do TRL, `max_length` define o tamanho do bloco packed, e `packing_strategy` seleciona best-fit decreasing (`"bfd"`) ou wrapped packing. Best-fit decreasing habilita batches sem padding; `padding_free=True` explícito é compatível com FlashAttention 2 ou 3. Não confunda `pad_to_multiple_of` com packing: ele apenas arredonda os comprimentos das sequências com padding para um múltiplo selecionado.<sup>[[5]](#references)</sup>

**O batching dinâmico ou ciente do comprimento é uma otimização separada:** ele não concatena exemplos. Em vez disso, agrupa exemplos de comprimentos semelhantes, para que cada batch com padding dinâmico contenha menos tokens de padding. Atualmente, o Hugging Face Transformers disponibiliza isso como `train_sampling_strategy="group_by_length"`; uma coluna `length` pré-computada, selecionada por meio de `length_column_name`, evita calcular o comprimento de cada exemplo quando o treinamento começa.<sup>[[8]](#references)</sup>

### 3. Deduplicação e Filtragem de Qualidade
Passagens repetidas causam memorização e fornecem um canal fácil para data poisoning. Portanto, um pipeline de limpeza defensável combina:

1. **Detecção de duplicatas exatas e quase duplicatas:** aplicar hash aos documentos normalizados, usar MinHash/LSH sobre n-grams de tokens para descobrir quase duplicatas de forma escalável e usar métodos de substring exata quando for necessário remover passagens repetidas longas.<sup>[[6]](#references)</sup>
2. **Filtragem de qualidade:** rejeitar codificações inválidas, markup corrompido, repetição patológica e documentos no idioma errado. A perplexidade de um modelo de referência também pode ser outro sinal, mas seu threshold deve ser calibrado para o corpus, em vez de ser tratado como um limite universal.<sup>[[2]](#references)</sup>
3. **Filtragem de dados sensíveis:** procurar credenciais e PII com padrões determinísticos e detecção de entidades, colocando os resultados em quarentena para revisão, para que falsos positivos não apaguem silenciosamente dados úteis de treinamento.<sup>[[7]](#references)</sup>

O artigo do Llama 2 descreve a deduplicação e a filtragem de fontes como parte da construção do corpus.<sup>[[2]](#references)</sup> Pesquisas independentes descobriram que deduplicar os dados de treinamento de modelos de linguagem reduz a memorização literal e pode exigir menos etapas de treinamento para obter precisão igual ou superior.<sup>[[6]](#references)</sup>

## Considerações de Segurança e Privacidade Durante o Sampling

### Data-Poisoning / Backdoor Attacks

Trate a descoberta, materialização, filtragem e amostragem do corpus como uma única supply chain. Um manifesto contendo apenas URLs não constitui dados de treinamento imutáveis:

* **Split-view poisoning:** um atacante faz com que um recurso pareça benigno quando um curador o indexa e, depois, altera o que os clientes de treinamento baixam. Isso explora o intervalo de tempo entre a criação do dataset e sua materialização.
* **Frontrunning poisoning:** um atacante modifica brevemente uma fonte editada colaborativamente imediatamente antes de um snapshot ou crawl previsível e a restaura depois. O sample malicioso permanece no snapshot, embora a página ativa pareça limpa posteriormente.

Ambas as técnicas têm como alvo **quando um sample é obtido**, e não uma vulnerabilidade do parser. Pesquisadores demonstraram essas técnicas contra as premissas de confiança de vários datasets em escala web, incluindo expiração/registro novamente de URLs e edições limitadas no tempo.<sup>[[9]](#references)</sup>

**O sampling pode amplificar um pequeno cluster envenenado.** A métrica relevante não é apenas `poison_documents / raw_documents`, mas o número de vezes que esses documentos se tornam exemplos de otimização após ponderação da fonte, repetição, chunking e janelas sobrepostas. Em grandes experimentos de pre-training, 250 documentos envenenados produziram um efeito de backdoor comparável em modelos de 600M a 13B parâmetros treinados com 6B a 260B tokens limpos; portanto, um threshold de alerta baseado apenas em porcentagem pode se tornar menos eficaz à medida que o corpus cresce.<sup>[[10]](#references)</sup>

Para uma auditoria de ingestão, mantenha tanto a **contagem de documentos únicos** quanto a **contagem de exposição efetiva**.<sup>[[10]](#references)</sup>
```text
effective_exposure(doc) =
epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```
Controles práticos derivados dessas falhas de ingestão e exposição incluem:<sup>[[9]](#references)[[10]](#references)</sup>

* Congele artifacts endereçados por conteúdo em vez de buscar novamente URLs mutáveis. Armazene a URL original, o timestamp de recuperação, o comprimento em bytes, o digest e a versão da transformação; falhe de forma fechada em caso de incompatibilidade de digest.
* Calcule o hash dos bytes antes e depois da normalização. O primeiro digest comprova a integridade da fonte; o segundo possibilita a deduplicação e a reprodução posterior.
* Faça a deduplicação antes do upsampling da mistura e da geração de janelas; depois, limite a exposição por cluster de duplicatas exatas/quase duplicatas e por origem. Embaralhar altera a ordem, mas não remove um poison.
* Registre um `document_id` estável em cada sequência emitida, para que um comportamento suspeito do modelo possa ser rastreado através dos batches empacotados até os documentos de origem.
* Antes do treinamento, verifique diretamente o manifest congelado, por exemplo com `sha256sum -c corpus.sha256`; não baixe silenciosamente um substituto para um objeto ausente ou alterado.

### Inferência de Associação & Memorization
A grande sobreposição entre amostras de sliding window repete strings raras, como números de telefone ou secret keys, aumentando sua frequência efetiva. Pesquisas sobre privacidade dos dados de treinamento mostram que sequências duplicadas são regeneradas de forma desproporcional e que a deduplicação reduz significativamente essa exposição.<sup>[[7]](#references)</sup>

Recomendações práticas:

* Evite sobreposição desnecessária quando ela expuser repetidamente strings sensíveis ou exclusivas.
* Faça a deduplicação antes de dividir os dados, para que amostras quase idênticas não vazem entre os conjuntos de treinamento e avaliação.
