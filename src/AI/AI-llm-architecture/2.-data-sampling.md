## **Вибірка даних**

**Вибірка даних** — це важливий процес підготовки даних для навчання великих мовних моделей (LLM), таких як GPT. Він передбачає організацію текстових даних у вхідні та цільові послідовності, які модель використовує для навчання прогнозування наступного слова (або токена) на основі попередніх слів. Правильна вибірка даних забезпечує ефективне виявлення моделлю мовних закономірностей і залежностей.

> [!TIP]
> Мета цього другого етапу дуже проста: **виконати вибірку вхідних даних і підготувати їх до етапу навчання, зазвичай розділивши набір даних на речення певної довжини та також згенерувавши очікувану відповідь.**

### **Чому вибірка даних важлива**

LLM, такі як GPT, навчаються генерувати або прогнозувати текст, розуміючи контекст, заданий попередніми словами. Для цього навчальні дані потрібно структурувати так, щоб модель могла навчитися взаємозв’язку між послідовностями слів і наступними словами. Такий структурований підхід дає змогу моделі узагальнювати та генерувати зв’язний текст, релевантний контексту.

### **Основні поняття вибірки даних**

1. **Токенізація:** розбиття тексту на менші одиниці, які називаються токенами (наприклад, слова, субслова або символи).
2. **Довжина послідовності (max_length):** кількість токенів у кожній вхідній послідовності.
3. **Sliding Window:** метод створення перекривних вхідних послідовностей шляхом переміщення вікна по токенізованому тексту.
4. **Stride:** кількість токенів, на яку переміщується Sliding Window для створення наступної послідовності.

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""

- The used text for training

dataloader = create_dataloader_v1(

## Стратегії розширеного sampling (2023-2025)

### 1. Temperature-Based Mixture Weighting
Сучасні LLM рідко навчаються на одному корпусі. Натомість вони відбирають дані з кількох неоднорідних джерел (code, web, академічні статті, форуми…). Відносна частка кожного джерела може суттєво впливати на подальшу продуктивність. Нові open-source моделі, такі як Llama 2, запровадили **temperature‐based sampling scheme**, за якої ймовірність вибору документа з корпусу *i* стає
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – необроблений відсоток токенів корпусу *i*
• *α* ("температура") – значення в діапазоні (0,1]. α < 1 вирівнює розподіл, надаючи більшу вагу меншим високоякісним корпусам.

За значення `α < 1` це зважування вирівнює розподіл і збільшує відносну ймовірність вибірки з менших корпусів. Вибірка на основі температури широко використовується для балансування багатомовних даних попереднього навчання, хоча для уникнення перенавчання на малих джерелах потрібні обмеження повторення.<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
Пам'ять GPU витрачається марно, коли кожна послідовність у batch доповнюється padding до довжини найдовшого прикладу. **Packing** групує кілька коротших прикладів у блоки фіксованої довжини. Звичайна реалізація packed-обробки використовує сегментно-орієнтовану або блочно-діагональну `attention_mask`, щоб токени не могли звертатися до токенів за межами відповідних прикладів; реалізації без padding натомість можуть сплющувати batch і зберігати межі за допомогою позиційної інформації. Hugging Face TRL надає packing через `SFTConfig(packing=True)` і документує доступні стратегії.<sup>[[5]](#references)</sup>

У конкретній конфігурації TRL `max_length` визначає розмір packed-блоку, а `packing_strategy` обирає best-fit decreasing (`"bfd"`) або wrapped packing. Best-fit decreasing дає змогу створювати batch без padding; явний параметр `padding_free=True` підтримується у FlashAttention 2 або 3. Не плутайте `pad_to_multiple_of` з packing: він лише округлює довжини послідовностей із padding до вибраного кратного значення.<sup>[[5]](#references)</sup>

**Dynamic або length-aware batching є окремою оптимізацією:** воно не об'єднує приклади. Натомість воно групує приклади схожої довжини, щоб кожен batch із динамічним padding містив менше padding-токенів. Поточна версія Hugging Face Transformers надає цю можливість через `train_sampling_strategy="group_by_length"`; попередньо обчислена колонка `length`, вибрана через `length_column_name`, дає змогу не обчислювати довжину кожного прикладу на початку навчання.<sup>[[8]](#references)</sup>

### 3. Deduplication & Quality Filtering
Повторювані фрагменти спричиняють memorization і створюють простий канал для data poisoning. Тому обґрунтований pipeline очищення поєднує:

1. **Exact і near-duplicate detection:** хешуйте нормалізовані документи, використовуйте MinHash/LSH над token n-grams для масштабованого пошуку near-duplicate і застосовуйте методи exact-substring, коли потрібно видалити довгі повторювані фрагменти.<sup>[[6]](#references)</sup>
2. **Quality filtering:** відхиляйте документи з некоректними кодуваннями, пошкодженою розміткою, патологічними повтореннями та неправильною мовою. Perplexity reference-model може бути ще одним сигналом, але її поріг потрібно калібрувати для конкретного корпусу, а не сприймати як універсальне граничне значення.<sup>[[2]](#references)</sup>
3. **Sensitive-data filtering:** шукайте credentials і PII за допомогою детермінованих шаблонів разом із entity detection, а потім поміщайте збіги в quarantine для перевірки, щоб false positives непомітно не видаляли корисні training data.<sup>[[7]](#references)</sup>

У статті про Llama 2 deduplication і source filtering описані як частини побудови корпусу.<sup>[[2]](#references)</sup> Незалежне дослідження показало, що deduplication training data для language model зменшує verbatim memorization і може вимагати менше training steps для досягнення такої самої або кращої точності.<sup>[[6]](#references)</sup>

## Security & Privacy Considerations During Sampling

### Data-Poisoning / Backdoor Attacks

Розглядайте пошук, materialization, filtering і sampling корпусу як один supply chain. Маніфест, що містить лише URL, не є незмінними training data:

* **Split-view poisoning:** attacker робить ресурс безпечним на вигляд, коли curator індексує його, а потім змінює те, що пізніше завантажують training clients. Це використовує часовий проміжок між створенням dataset і materialization.
* **Frontrunning poisoning:** attacker ненадовго змінює source, редагований спільнотою, безпосередньо перед передбачуваним snapshot або crawl, а потім відновлює його. Шкідливий sample зберігається у snapshot, навіть якщо пізніше live page виглядає чистою.

Обидві техніки націлені на **момент отримання sample**, а не на вразливість parser. Дослідники продемонстрували їх проти припущень щодо trust у кількох web-scale datasets, зокрема через expiry/re-registration URL і обмежені в часі edits.<sup>[[9]](#references)</sup>

**Sampling може посилити невеликий poisoned cluster.** Важливим показником є не лише `poison_documents / raw_documents`, а й кількість разів, коли ці документи стають optimization examples після source weighting, repetition, chunking і overlapping windows. У масштабних pre-training experiments 250 poisoned documents створили порівнянний backdoor effect у моделях із 600M–13B параметрів, навчених на 6B–260B clean tokens; отже, alert threshold, що ґрунтується лише на відсотку, може ставати слабшим зі зростанням корпусу.<sup>[[10]](#references)</sup>

Для ingestion audit зберігайте як **кількість унікальних документів**, так і **кількість ефективних exposure**.<sup>[[10]](#references)</sup>
```text
effective_exposure(doc) =
epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```
Практичні засоби контролю, виведені з цих збоїв під час ingestion і exposure, включають:<sup>[[9]](#references)[[10]](#references)</sup>

* Фіксуйте артефакти з адресацією за вмістом замість повторного отримання даних із mutable URL. Зберігайте оригінальний URL, час отримання, довжину в байтах, digest і версію трансформації; завершуйте операцію з помилкою у разі невідповідності digest.
* Обчислюйте hash байтів до та після нормалізації. Перший digest підтверджує цілісність джерела; другий забезпечує можливість дедуплікації та подальшого відтворення.
* Виконуйте дедуплікацію до mixture upsampling і генерації вікон, потім обмежуйте exposure для кожного кластера exact/near-duplicate і кожного джерела. Перемішування змінює порядок, але не усуває poison.
* Записуйте стабільний `document_id` у кожну згенеровану послідовність, щоб підозрілу поведінку моделі можна було простежити через packed batches до вихідних документів.
* Перед training безпосередньо перевіряйте frozen manifest, наприклад за допомогою `sha256sum -c corpus.sha256`; не завантажуйте непомітно заміну для відсутнього або зміненого об’єкта.

### Membership-Inference & Memorization
Великий overlap між sliding-window samples повторює рідкісні рядки, як-от номери телефонів або secret keys, збільшуючи їхню ефективну частоту. Дослідження privacy training data показують, що duplicated sequences непропорційно часто відтворюються, а дедуплікація істотно зменшує це exposure.<sup>[[7]](#references)</sup>

Практичні рекомендації:

* Уникайте непотрібного overlap, якщо він призводить до повторного exposure чутливих або унікальних рядків.
* Виконуйте дедуплікацію до розподілу даних, щоб near-identical samples не могли leak між training і evaluation sets.
