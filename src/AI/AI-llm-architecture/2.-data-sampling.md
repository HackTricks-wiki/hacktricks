## **Data Sampling**

**Data Sampling** is a crucial process in preparing data for training large language models (LLMs) like GPT. It involves organizing text data into input and target sequences that the model uses to learn how to predict the next word (or token) based on the preceding words. Proper data sampling ensures that the model effectively captures language patterns and dependencies.

> [!TIP]
> The goal of this second phase is very simple: **Sample the input data and prepare it for the training phase usually by separating the dataset into sentences of a specific length and generating also the expected response.**

### **Why Data Sampling Matters**

LLMs such as GPT are trained to generate or predict text by understanding the context provided by previous words. To achieve this, the training data must be structured in a way that the model can learn the relationship between sequences of words and their subsequent words. This structured approach allows the model to generalize and generate coherent and contextually relevant text.

### **Key Concepts in Data Sampling**

1. **Tokenization:** Breaking down text into smaller units called tokens (e.g., words, subwords, or characters).
2. **Sequence Length (max_length):** The number of tokens in each input sequence.
3. **Sliding Window:** A method to create overlapping input sequences by moving a window over the tokenized text.
4. **Stride:** The number of tokens the sliding window moves forward to create the next sequence.

### **Step-by-Step Example**

Let's walk through an example to illustrate data sampling.

**Example Text**

```arduino
"Lorem ipsum dolor sit amet, consectetur adipiscing elit."
```

**Tokenization**

Assume we use a **basic tokenizer** that splits the text into words and punctuation marks:

```vbnet
Tokens: ["Lorem", "ipsum", "dolor", "sit", "amet,", "consectetur", "adipiscing", "elit."]
```

**Parameters**

- **Max Sequence Length (max_length):** 4 tokens
- **Sliding Window Stride:** 1 token

**Creating Input and Target Sequences**

1. **Sliding Window Approach:**
   - **Input Sequences:** Each input sequence consists of `max_length` tokens.
   - **Target Sequences:** Each target sequence consists of the tokens that immediately follow the corresponding input sequence.

**Sliding Window with Stride 1:**

- **First Window (Positions 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Target:** \["ipsum", "dolor", "sit", "amet,"]
- **Second Window (Positions 2-5):** \["ipsum", "dolor", "sit", "amet,"] → **Target:** \["dolor", "sit", "amet,", "consectetur"]
- **Third Window (Positions 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Target:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Fourth Window (Positions 4-7):** \["sit", "amet,", "consectetur", "adipiscing"] → **Target:** \["amet,", "consectetur", "adipiscing", "elit."]

**Understanding Stride**

- **Stride of 1:** The window moves forward by one token each time, resulting in highly overlapping sequences. This can lead to better learning of contextual relationships but may increase the risk of overfitting since similar data points are repeated.
- **Stride of 2:** The window moves forward by two tokens each time, reducing overlap. This decreases redundancy and computational load but might miss some contextual nuances.
- **Stride Equal to max_length:** The window moves forward by the entire window size, resulting in non-overlapping sequences. This minimizes data redundancy but may limit the model's ability to learn dependencies across sequences.

**Example with Stride of 2:**

Using the same tokenized text and `max_length` of 4:

- **First Window (Positions 1-4):** \["Lorem", "ipsum", "dolor", "sit"] → **Target:** \["ipsum", "dolor", "sit", "amet,"]
- **Second Window (Positions 3-6):** \["dolor", "sit", "amet,", "consectetur"] → **Target:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Third Window (Positions 5-8):** \["amet,", "consectetur", "adipiscing", "elit."] → **Target:** \["consectetur", "adipiscing", "elit.", "sed"] _(Assuming continuation)_

## Code Example

Let's understand this better from a code example from [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb):<sup>[[1]](#references)</sup>

```python
# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
    raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
    def __init__(self, txt, tokenizer, max_length, stride):
        self.input_ids = []
        self.target_ids = []

        # Tokenize the entire text
        token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

        # Use a sliding window to chunk the book into overlapping sequences of max_length
        for i in range(0, len(token_ids) - max_length, stride):
            input_chunk = token_ids[i:i + max_length]
            target_chunk = token_ids[i + 1: i + max_length + 1]
            self.input_ids.append(torch.tensor(input_chunk))
            self.target_ids.append(torch.tensor(target_chunk))

    def __len__(self):
        return len(self.input_ids)

    def __getitem__(self, idx):
        return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
                         stride=128, shuffle=True, drop_last=True,
                         num_workers=0):

    # Initialize the tokenizer
    tokenizer = tiktoken.get_encoding("gpt2")

    # Create dataset
    dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

    # Create dataloader
    dataloader = DataLoader(
        dataset,
        batch_size=batch_size,
        shuffle=shuffle,
        drop_last=drop_last,
        num_workers=num_workers
    )

    return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
    raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1
[
```

## Advanced Sampling Strategies (2023-2025)

### 1. Temperature-Based Mixture Weighting
State-of-the-art LLMs are rarely trained on a single corpus.  Instead, they sample from several heterogeneous data sources (code, web, academic papers, forums…).  The relative proportion of each source can strongly affect downstream performance.  Recent open-source models such as Llama 2 introduced a **temperature‐based sampling scheme** where the probability of drawing a document from corpus *i* becomes

```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```

• *w<sub>i</sub>*  – raw token percentage of corpus *i*  
• *α* ("temperature") – a value in (0,1].  α < 1 flattens the distribution, giving more weight to smaller high-quality corpora.

With `α < 1`, this weighting flattens the distribution and increases the relative sampling probability of smaller corpora. Temperature-based sampling has been widely used for balancing multilingual pretraining data, although repetition limits are needed to avoid overfitting small sources.<sup>[[4]](#references)</sup>

```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
    counts = Counter(corpus_ids)           # number of tokens seen per corpus
    probs  = {c: c_count**alpha for c, c_count in counts.items()}
    Z = sum(probs.values())
    probs = {c: p/Z for c, p in probs.items()}
    # Now draw according to probs to fill every batch
```
### 2. Sequence Packing / Dynamic Batching
GPU memory is wasted when every sequence in a batch is padded to the longest example. **Packing** groups multiple shorter examples into fixed-length blocks. A conventional packed implementation uses a segment-aware or block-diagonal `attention_mask` so tokens cannot attend across example boundaries; padding-free implementations can instead flatten the batch and preserve boundaries with position information. Hugging Face TRL exposes packing through `SFTConfig(packing=True)` and documents the available strategies.<sup>[[5]](#references)</sup>

For a concrete TRL configuration, `max_length` defines the packed block size and `packing_strategy` selects either best-fit decreasing (`"bfd"`) or wrapped packing. Best-fit decreasing enables padding-free batches; explicit `padding_free=True` is supported with FlashAttention 2 or 3. Do not confuse `pad_to_multiple_of` with packing: it only rounds padded sequence lengths to a selected multiple.<sup>[[5]](#references)</sup>

**Dynamic or length-aware batching is a separate optimization:** it does not concatenate examples. Instead, it groups examples of similar lengths so that each dynamically padded batch contains fewer padding tokens. Current Hugging Face Transformers exposes this as `train_sampling_strategy="group_by_length"`; a precomputed `length` column selected through `length_column_name` avoids calculating every example's length when training starts.<sup>[[8]](#references)</sup>

### 3. Deduplication & Quality Filtering
Repeated passages cause memorization and provide an easy channel for data poisoning. A defensible cleaning pipeline therefore combines:

1. **Exact and near-duplicate detection:** hash normalized documents, use MinHash/LSH over token n-grams for scalable near-duplicate discovery, and use exact-substring methods when long repeated passages must be removed.<sup>[[6]](#references)</sup>
2. **Quality filtering:** reject invalid encodings, garbled markup, pathological repetition, and wrong-language documents. Reference-model perplexity can be another signal, but its threshold must be calibrated for the corpus rather than treated as a universal cutoff.<sup>[[2]](#references)</sup>
3. **Sensitive-data filtering:** scan for credentials and PII with deterministic patterns plus entity detection, then quarantine matches for review so false positives do not silently erase useful training data.<sup>[[7]](#references)</sup>

The Llama 2 paper describes deduplication and source filtering as part of corpus construction.<sup>[[2]](#references)</sup> Independent research found that deduplicating language-model training data reduces verbatim memorization and can require fewer training steps for equal or better accuracy.<sup>[[6]](#references)</sup>

## Security & Privacy Considerations During Sampling

### Data-Poisoning / Backdoor Attacks

Treat corpus discovery, materialization, filtering, and sampling as one supply chain. A manifest containing only URLs is not immutable training data:

* **Split-view poisoning:** an attacker makes a resource look benign when a curator indexes it, then changes what later training clients download. This exploits the time gap between dataset creation and materialization.
* **Frontrunning poisoning:** an attacker briefly modifies a crowd-edited source immediately before a predictable snapshot or crawl and restores it afterward. The malicious sample persists in the snapshot even though the live page appears clean later.

Both techniques target **when a sample is fetched**, not a parser vulnerability. Researchers demonstrated them against the trust assumptions of multiple web-scale datasets, including URL expiry/re-registration and time-bounded edits.<sup>[[9]](#references)</sup>

**Sampling can amplify a small poisoned cluster.** The relevant metric is not merely `poison_documents / raw_documents`, but the number of times those documents become optimization examples after source weighting, repetition, chunking, and overlapping windows. In large pre-training experiments, 250 poisoned documents produced a comparable backdoor effect across models from 600M to 13B parameters trained on 6B to 260B clean tokens; therefore, a percentage-only alert threshold can become weaker as the corpus grows.<sup>[[10]](#references)</sup>

For an ingestion audit, retain both **unique-document count** and **effective exposure count**.<sup>[[10]](#references)</sup>

```text
effective_exposure(doc) =
    epochs × source_sampling_weight × repetitions × emitted_chunks(doc)
```

Practical controls derived from these ingestion and exposure failures include:<sup>[[9]](#references)[[10]](#references)</sup>

* Freeze content-addressed artifacts rather than re-fetching mutable URLs. Store the original URL, retrieval timestamp, byte length, digest, and transformation version; fail closed on a digest mismatch.
* Hash the bytes both before and after normalization. The first digest proves source integrity; the second makes deduplication and later reproduction possible.
* Deduplicate before mixture upsampling and window generation, then cap exposure per exact/near-duplicate cluster and per origin. Shuffling changes order but does not remove a poison.
* Log a stable `document_id` into every emitted sequence so a suspicious model behavior can be traced back through packed batches to source documents.
* Before training, verify the frozen manifest directly, for example with `sha256sum -c corpus.sha256`; do not silently download a replacement for a missing or changed object.

### Membership-Inference & Memorization
Long overlap between sliding-window samples repeats rare strings such as telephone numbers or secret keys, increasing their effective frequency. Research on training-data privacy shows that duplicated sequences are regenerated disproportionately often and that deduplication materially reduces this exposure.<sup>[[7]](#references)</sup>

Practical recommendations:

* Avoid unnecessary overlap when it would repeatedly expose sensitive or unique strings.
* Deduplicate before splitting data so that near-identical samples do not leak across training and evaluation sets.
