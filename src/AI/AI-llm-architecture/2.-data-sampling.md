## **Вибірка даних**

**Вибірка даних** — це важливий процес підготовки даних для training великих мовних моделей (LLM), таких як GPT. Він передбачає організацію текстових даних у вхідні та цільові послідовності, які модель використовує, щоб навчитися передбачати наступне слово (або token) на основі попередніх слів. Належна вибірка даних гарантує, що модель ефективно вивчає мовні закономірності та залежності.

> [!TIP]
> Мета цієї другої фази дуже проста: **виконати вибірку вхідних даних і підготувати їх до фази training, зазвичай розділивши dataset на речення певної довжини та також згенерувавши очікувану відповідь.**

### **Чому вибірка даних має значення**

LLM, такі як GPT, навчаються генерувати або передбачати текст, розуміючи контекст, наданий попередніми словами. Для цього training-дані мають бути структуровані таким чином, щоб модель могла вивчати зв’язок між послідовностями слів і наступними словами. Такий структурований підхід дає змогу моделі узагальнювати та генерувати зв’язний і контекстуально релевантний текст.

### **Ключові поняття вибірки даних**

1. **Токенізація:** розбиття тексту на менші одиниці, що називаються token (наприклад, слова, підслова або символи).
2. **Довжина послідовності (max_length):** кількість token у кожній вхідній послідовності.
3. **Ковзне вікно:** метод створення перекривних вхідних послідовностей шляхом переміщення вікна по токенізованому тексту.
4. **Крок (Stride):** кількість token, на яку ковзне вікно переміщується вперед для створення наступної послідовності.

### **Покроковий приклад**

Розгляньмо приклад, щоб проілюструвати вибірку даних.

**Приклад тексту**
```arduino
"Lorem ipsum dolor sit amet, consectetur adipiscing elit."
```
**Токенізація**

Припустімо, ми використовуємо **базовий токенізатор**, який розділяє текст на слова та розділові знаки:
```vbnet
Tokens: ["Lorem", "ipsum", "dolor", "sit", "amet,", "consectetur", "adipiscing", "elit."]
```
**Параметри**

- **Максимальна довжина послідовності (max_length):** 4 токени
- **Крок ковзного вікна:** 1 токен

**Створення вхідних і цільових послідовностей**

1. **Підхід ковзного вікна:**
- **Вхідні послідовності:** кожна вхідна послідовність складається з `max_length` токенів.
- **Цільові послідовності:** кожна цільова послідовність складається з токенів, які безпосередньо слідують за відповідною вхідною послідовністю.
2. **Генерування послідовностей:**

3. **Отримані вхідні та цільові масиви:**

- **Вхідні дані:**

```python
[
["Lorem", "ipsum", "dolor", "sit"],
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
]
```

- **Цільові дані:**

```python
[
["ipsum", "dolor", "sit", "amet,"],
["dolor", "sit", "amet,", "consectetur"],
["sit", "amet,", "consectetur", "adipiscing"],
["amet,", "consectetur", "adipiscing", "elit."],
]
```

**Візуальне представлення**

**Ковзне вікно з кроком 1:**

- **Перше вікно (позиції 1–4):** \["Lorem", "ipsum", "dolor", "sit"] → **Цільова послідовність:** \["ipsum", "dolor", "sit", "amet,"]
- **Друге вікно (позиції 2–5):** \["ipsum", "dolor", "sit", "amet,"] → **Цільова послідовність:** \["dolor", "sit", "amet,", "consectetur"]
- **Третє вікно (позиції 3–6):** \["dolor", "sit", "amet,", "consectetur"] → **Цільова послідовність:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Четверте вікно (позиції 4–7):** \["sit", "amet,", "consectetur", "adipiscing"] → **Цільова послідовність:** \["amet,", "consectetur", "adipiscing", "elit."]

**Розуміння кроку**

- **Крок 1:** вікно щоразу переміщується вперед на один токен, унаслідок чого послідовності значною мірою перекриваються. Це може сприяти кращому навчанню контекстних взаємозв’язків, але також підвищує ризик перенавчання, оскільки подібні точки даних повторюються.
- **Крок 2:** вікно щоразу переміщується вперед на два токени, що зменшує перекриття. Це знижує надлишковість і обчислювальне навантаження, але може призвести до втрати деяких контекстних нюансів.
- **Крок, що дорівнює max_length:** вікно переміщується вперед на весь свій розмір, унаслідок чого утворюються неперекривні послідовності. Це мінімізує надлишковість даних, але може обмежити здатність моделі вивчати залежності між послідовностями.

**Приклад із кроком 2:**

Використовуючи той самий токенізований текст і `max_length`, що дорівнює 4:

- **Перше вікно (позиції 1–4):** \["Lorem", "ipsum", "dolor", "sit"] → **Цільова послідовність:** \["ipsum", "dolor", "sit", "amet,"]
- **Друге вікно (позиції 3–6):** \["dolor", "sit", "amet,", "consectetur"] → **Цільова послідовність:** \["sit", "amet,", "consectetur", "adipiscing"]
- **Третє вікно (позиції 5–8):** \["amet,", "consectetur", "adipiscing", "elit."] → **Цільова послідовність:** \["consectetur", "adipiscing", "elit.", "sed"] _(за умови продовження)_

## Приклад коду

Розгляньмо це детальніше на прикладі коду з [https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb](https://github.com/rasbt/LLMs-from-scratch/blob/main/ch02/01_main-chapter-code/ch02.ipynb):<sup>[[1]](#references)</sup>
```python
# Download the text to pre-train the LLM
import urllib.request
url = ("https://raw.githubusercontent.com/rasbt/LLMs-from-scratch/main/ch02/01_main-chapter-code/the-verdict.txt")
file_path = "the-verdict.txt"
urllib.request.urlretrieve(url, file_path)

with open("the-verdict.txt", "r", encoding="utf-8") as f:
raw_text = f.read()

"""
Create a class that receives parameters such as a tokenizer and text
and will prepare the input chunks and the target chunks to prepare
the LLM to learn which next token to generate
"""
import torch
from torch.utils.data import Dataset, DataLoader

class GPTDatasetV1(Dataset):
def __init__(self, txt, tokenizer, max_length, stride):
self.input_ids = []
self.target_ids = []

# Tokenize the entire text
token_ids = tokenizer.encode(txt, allowed_special={"<|endoftext|>"})

# Use a sliding window to chunk the book into overlapping sequences of max_length
for i in range(0, len(token_ids) - max_length, stride):
input_chunk = token_ids[i:i + max_length]
target_chunk = token_ids[i + 1: i + max_length + 1]
self.input_ids.append(torch.tensor(input_chunk))
self.target_ids.append(torch.tensor(target_chunk))

def __len__(self):
return len(self.input_ids)

def __getitem__(self, idx):
return self.input_ids[idx], self.target_ids[idx]


"""
Create a data loader which given the text and some params will
prepare the inputs and targets with the previous class and
then create a torch DataLoader with the info
"""

import tiktoken

def create_dataloader_v1(txt, batch_size=4, max_length=256,
stride=128, shuffle=True, drop_last=True,
num_workers=0):

# Initialize the tokenizer
tokenizer = tiktoken.get_encoding("gpt2")

# Create dataset
dataset = GPTDatasetV1(txt, tokenizer, max_length, stride)

# Create dataloader
dataloader = DataLoader(
dataset,
batch_size=batch_size,
shuffle=shuffle,
drop_last=drop_last,
num_workers=num_workers
)

return dataloader


"""
Finally, create the data loader with the params we want:
- The used text for training
- batch_size: The size of each batch
- max_length: The size of each entry on each batch
- stride: The sliding window (how many tokens should the next entry advance compared to the previous one). The smaller the more overfitting, usually this is equals to the max_length so the same tokens aren't repeated.
- shuffle: Re-order randomly
"""
dataloader = create_dataloader_v1(
raw_text, batch_size=8, max_length=4, stride=1, shuffle=False
)

data_iter = iter(dataloader)
first_batch = next(data_iter)
print(first_batch)

# Note the batch_size of 8, the max_length of 4 and the stride of 1
[
```

## Розширені стратегії семплінгу (2023–2025)

### 1. Зважування суміші на основі temperature
Сучасні LLM рідко навчаються на одному корпусі. Натомість вони відбирають дані з кількох гетерогенних джерел (code, web, академічні статті, форуми…). Відносна частка кожного джерела може суттєво впливати на подальшу продуктивність. Останні open-source моделі, такі як Llama 2, запровадили **схему семплінгу на основі temperature**, у якій імовірність вибору документа з корпусу *i* стає
```
p(i) = \frac{w_i^{\alpha}}{\sum_j w_j^{\alpha}}
```
• *w<sub>i</sub>*  – необроблений відсоток токенів корпусу *i*
• *α* ("temperature") – значення в діапазоні (0,1].  α < 1 вирівнює розподіл, надаючи більшу вагу меншим високоякісним корпусам.

За `α < 1` це зважування вирівнює розподіл і збільшує відносну ймовірність вибірки для менших корпусів. Вибірка на основі temperature широко використовується для балансування багатомовних даних pretraining, хоча для уникнення overfitting малих джерел потрібні обмеження повторення.<sup>[[4]](#references)</sup>
```python
from collections import Counter

def temperature_sample(corpus_ids, alpha=0.7):
counts = Counter(corpus_ids)           # number of tokens seen per corpus
probs  = {c: c_count**alpha for c, c_count in counts.items()}
Z = sum(probs.values())
probs = {c: p/Z for c, p in probs.items()}
# Now draw according to probs to fill every batch
```
### 2. Пакування послідовностей / Dynamic Batching
Пам'ять GPU витрачається марно, коли кожна послідовність у batch доповнюється до довжини найдовшого прикладу. **Packing** групує кілька коротших прикладів у блоки фіксованої довжини. Звичайна реалізація packed використовує сегментно-орієнтований або block-diagonal `attention_mask`, щоб токени не могли звертатися до токенів за межами прикладу; реалізації без padding можуть натомість сплющувати batch і зберігати межі за допомогою інформації про позиції. Hugging Face TRL надає packing через `SFTConfig(packing=True)` і документує доступні стратегії.<sup>[[5]](#references)</sup>

Для конкретної конфігурації TRL параметр `max_length` визначає розмір packed block, а `packing_strategy` вибирає best-fit decreasing (`"bfd"`) або wrapped packing. Best-fit decreasing підтримує batches без padding; явний `padding_free=True` підтримується з FlashAttention 2 або 3. Не плутайте `pad_to_multiple_of` з packing: він лише округлює довжини padded sequence до вибраного кратного.<sup>[[5]](#references)</sup>

**Dynamic або length-aware batching — це окрема оптимізація:** він не об'єднує приклади. Натомість він групує приклади подібної довжини, щоб кожен batch із динамічним padding містив менше padding-токенів. Поточна версія Hugging Face Transformers надає цю можливість як `train_sampling_strategy="group_by_length"`; попередньо обчислений стовпець `length`, вибраний через `length_column_name`, усуває потребу обчислювати довжину кожного прикладу на початку training.<sup>[[8]](#references)</sup>

### 3. Deduplication та фільтрація якості
Повторювані фрагменти спричиняють memorization і створюють простий канал для data poisoning. Тому обґрунтований pipeline очищення поєднує:

1. **Виявлення точних і майже дублікатів:** хешуйте нормалізовані документи, використовуйте MinHash/LSH над token n-grams для масштабованого пошуку майже дублікатів і застосовуйте методи пошуку точних підрядків, коли потрібно видалити довгі повторювані фрагменти.<sup>[[6]](#references)</sup>
2. **Фільтрація якості:** відхиляйте документи з некоректними кодуваннями, пошкодженою розміткою, патологічними повторами та неправильною мовою. Perplexity reference-model може бути додатковим сигналом, але його поріг потрібно калібрувати для конкретного корпусу, а не розглядати як універсальне граничне значення.<sup>[[2]](#references)</sup>
3. **Фільтрація чутливих даних:** шукайте credentials і PII за допомогою детермінованих шаблонів та entity detection, а потім переміщуйте збіги до quarantine для перевірки, щоб false positives непомітно не видаляли корисні training data.<sup>[[7]](#references)</sup>

У статті про Llama 2 deduplication і фільтрація джерел описуються як частини формування корпусу.<sup>[[2]](#references)</sup> Незалежне дослідження показало, що deduplication training data зменшує verbatim memorization і може вимагати менше training steps для отримання такої самої або кращої точності.<sup>[[6]](#references)</sup>

## Питання безпеки та приватності під час sampling

### Атаки отруєння даних / Backdoor Attacks
Дослідники показали, що додавання <1 % backdoored sentences може змусити модель підкорятися прихованому тригеру ("PoisonGPT", 2023).<sup>[[3]](#references)</sup> Рекомендовані заходи протидії:

* **Shuffled mixing** – переконайтеся, що сусідні training examples походять із різних джерел; це послаблює узгодженість градієнтів шкідливих фрагментів.
* **Gradient similarity scoring** – обчислюйте cosine similarity градієнта прикладу до середнього градієнта batch; outliers є кандидатами на видалення.
* **Dataset versioning та hashes** – заморожуйте незмінні tarballs і перевіряйте SHA-256 перед кожним training run.

### Membership-Inference та Memorization
Значний overlap між samples у sliding window повторює рідкісні рядки, як-от номери телефонів або secret keys, збільшуючи їхню фактичну частоту. Дослідження privacy training data показують, що duplicated sequences непропорційно часто відтворюються, а deduplication суттєво зменшує цей ризик.<sup>[[7]](#references)</sup>

Практичні рекомендації:

* Уникайте непотрібного overlap, якщо він призводить до повторного розкриття чутливих або унікальних рядків.
* Виконуйте deduplication до розподілу data, щоб майже ідентичні samples не витікали між training та evaluation sets.
