## Melhorias do LoRA

> [!TIP]
> O LoRA pode reduzir substancialmente a quantidade de parâmetros treináveis e a memória do otimizador necessária para realizar fine-tuning em um modelo pré-treinado.

O LoRA torna possível realizar fine-tuning de **modelos grandes** de forma eficiente, alterando apenas uma **pequena parte** do modelo. Ele reduz o número de parâmetros que você precisa treinar, economizando **memória** e **recursos computacionais**. Isso acontece porque:<sup>[[1]](#references)</sup>

1. **Reduz o número de parâmetros treináveis**: o LoRA congela o peso original `W` e representa uma atualização aditiva como o produto de duas matrizes treináveis de baixa ordem, normalmente `ΔW = B A`, com a ordem `r` muito menor que as dimensões de entrada/saída.<sup>[[3]](#references)</sup>

1. Isso ocorre porque, em vez de calcular a atualização completa do peso de uma camada (matriz), ele a aproxima pelo produto de 2 matrizes menores, reduzindo a atualização a ser calculada:\

<figure><img src="../../images/image (9) (1).png" alt=""><figcaption></figcaption></figure>

2. **Mantém os pesos originais do modelo inalterados**: apenas as matrizes do adapter são otimizadas. Congelar os pesos impede a modificação direta do checkpoint base, embora o comportamento do adapter ainda possa substituir ou degradar o conhecimento no momento da inferência.
3. **Fine-Tuning Eficiente e Específico para a Tarefa**: quando você quiser adaptar o modelo a uma **nova tarefa**, poderá treinar apenas as **pequenas matrizes do LoRA** (A e B), mantendo o restante do modelo como está. Isso é **muito mais eficiente** do que treinar novamente o modelo inteiro.
4. **Eficiência de Armazenamento**: após o fine-tuning, em vez de salvar um **novo modelo completo** para cada tarefa, você só precisa armazenar as **matrizes do LoRA**, que são muito pequenas em comparação com o modelo inteiro. Isso facilita a adaptação do modelo a muitas tarefas sem usar muito armazenamento.

A implementação mínima a seguir adapta o notebook citado. Ela inicializa `B` como zero para que o adapter comece como uma operação nula e usa o escalonamento padrão `alpha / rank` do LoRA. O código armazena os fatores em formatos orientados pela entrada (`A` é `in_dim x rank` e `B` é `rank x out_dim`), portanto seu caminho forward é escrito como `xAB`; esse é o equivalente, com os formatos transpostos, da notação `BA` usada no artigo.<sup>[[2]](#references)[[3]](#references)</sup>
```python
import math
import torch

# Create the LoRA layer with the 2 matrices and the alpha
class LoRALayer(torch.nn.Module):
def __init__(self, in_dim, out_dim, rank, alpha):
super().__init__()
self.A = torch.nn.Parameter(torch.empty(in_dim, rank))
torch.nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))  # similar to standard weight initialization
self.B = torch.nn.Parameter(torch.zeros(rank, out_dim))
self.scaling = alpha / rank

def forward(self, x):
x = self.scaling * (x @ self.A @ self.B)
return x

# Combine it with the linear layer
class LinearWithLoRA(torch.nn.Module):
def __init__(self, linear, rank, alpha):
super().__init__()
self.linear = linear
self.lora = LoRALayer(
linear.in_features, linear.out_features, rank, alpha
)

def forward(self, x):
return self.linear(x) + self.lora(x)

# Replace linear layers with LoRA ones
def replace_linear_with_lora(model, rank, alpha):
for name, module in model.named_children():
if isinstance(module, torch.nn.Linear):
# Replace the Linear layer with LinearWithLoRA
setattr(model, name, LinearWithLoRA(module, rank, alpha))
else:
# Recursively apply the same function to child modules
replace_linear_with_lora(module, rank, alpha)
```
