## Miglioramenti di LoRA

> [!TIP]
> LoRA può ridurre sostanzialmente il numero di parametri addestrabili e la memoria dell'optimizer necessaria per eseguire il fine-tuning di un modello pretrained.

LoRA rende possibile eseguire il fine-tuning di **modelli di grandi dimensioni** in modo efficiente modificando solo una **piccola parte** del modello. Riduce il numero di parametri da addestrare, risparmiando **memoria** e **risorse computazionali**. Questo avviene perché:<sup>[[1]](#references)</sup>

1. **Riduce il numero di parametri addestrabili**: LoRA congela il peso originale `W` e rappresenta un aggiornamento additivo come il prodotto di due matrici low-rank addestrabili, comunemente `ΔW = B A`, con un rank `r` molto più piccolo delle dimensioni di input/output.<sup>[[3]](#references)</sup>

1. Questo avviene perché, invece di calcolare l'aggiornamento completo del peso di un layer (matrice), lo approssima tramite il prodotto di 2 matrici più piccole, riducendo l'aggiornamento da calcolare:\

2. **Mantiene invariati i pesi originali del modello**: Vengono ottimizzate solo le matrici dell'adapter. Il congelamento dei pesi impedisce la modifica diretta del checkpoint di base, anche se il comportamento dell'adapter può comunque sovrascrivere o degradare la conoscenza durante l'inference.
3. **Fine-Tuning efficiente e specifico per il task**: Quando vuoi adattare il modello a un **nuovo task**, puoi addestrare solo le **piccole matrici LoRA** (A e B), lasciando invariato il resto del modello. Questo è **molto più efficiente** rispetto al riaddestramento dell'intero modello.
4. **Efficienza dello storage**: Dopo il fine-tuning, invece di salvare un **modello completamente nuovo** per ogni task, devi solo memorizzare le **matrici LoRA**, che sono molto piccole rispetto all'intero modello. Questo facilita l'adattamento del modello a molti task senza utilizzare troppo spazio di archiviazione.

La seguente implementazione minimale adatta il notebook d. Inizializza `B` a zero, in modo che l'adapter inizi come un no-op, e utilizza lo scaling standard `alpha / rank` di LoRA. Il codice memorizza i fattori in forme input-major (`A` è `in_dim x rank` e `B` è `rank x out_dim`), quindi il suo percorso forward è scritto come `xAB`; questa è l'equivalente, con forme trasposte, della notazione `BA` utilizzata nel paper.<sup>[[2]](#references)[[3]](#references)</sup>
```python
import math
import torch

# Create the LoRA layer with the 2 matrices and the alpha
class LoRALayer(torch.nn.Module):
def __init__(self, in_dim, out_dim, rank, alpha):
super().__init__()
self.A = torch.nn.Parameter(torch.empty(in_dim, rank))
torch.nn.init.kaiming_uniform_(self.A, a=math.sqrt(5))  # similar to standard weight initialization
self.B = torch.nn.Parameter(torch.zeros(rank, out_dim))
self.scaling = alpha / rank

def forward(self, x):
x = self.scaling * (x @ self.A @ self.B)
return x

# Combine it with the linear layer
class LinearWithLoRA(torch.nn.Module):
def __init__(self, linear, rank, alpha):
super().__init__()
self.linear = linear
self.lora = LoRALayer(
linear.in_features, linear.out_features, rank, alpha
)

def forward(self, x):
return self.linear(x) + self.lora(x)

# Replace linear layers with LoRA ones
def replace_linear_with_lora(model, rank, alpha):
for name, module in model.named_children():
if isinstance(module, torch.nn.Linear):
# Replace the Linear layer with LinearWithLoRA
setattr(model, name, LinearWithLoRA(module, rank, alpha))
else:
# Recursively apply the same function to child modules
replace_linear_with_lora(module, rank, alpha)
```
