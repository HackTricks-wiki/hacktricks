# Межі довіри LLM Gateway

{{#include ../banners/hacktricks-training.md}}

LLM gateway маршрутизує запити до моделей і часто зберігає облікові дані провайдерів, тому звичайні API-клієнти не повинні отримувати повноваження щодо конфігурації чи рівня провайдера. Оцінювання LiteLLM gateway версії 1.77.7 демонструє дві окремі межі: авторизацію адміністративної конфігурації через UI-сесію та маршрутизацію інференсу на основі конфігурації, наданої клієнтом. Виявлені проблеми виправили у версії 1.83.9.<sup>[[1]](#references)</sup>

## Класифікація UI-маршрутів — це не авторизація

У перевіреній версії LiteLLM ключі входу в UI належали команді `litellm-dashboard`. Авторизація визначала ключ як UI-токен за ідентифікатором цієї команди, незалежно від ролі користувача. Далі перевірка UI-маршруту приймала будь-який маршрут, що починався з дозволеного префікса. У результаті запис `/config` також відповідав адміністративному обробнику `/config/update`. Цей обробник вимагав загальної автентифікації, але окремо не вимагав `PROXY_ADMIN`, тож UI-сесія з нижчими привілеями отримувала доступ до запису конфігурації.<sup>[[1]](#references)</sup>

Це відрізняється від невідповідності нормалізації шляху між proxy і backend: код авторизації та обробник по-різному визначають повноваження для *того самого* маршруту.<sup>[[1]](#references)</sup> Перевіряючи gateway, зіставте класифікацію токенів, точну відповідність маршруту й методу, а також власну перевірку ролі обробником.<sup>[[1]](#references)</sup> Див. [авторизацію веб API](../pentesting-web/web-api-pentesting.md), [обходи 401/403](../pentesting-web/403-and-401-bypasses.md) і [обхід винятків для префіксів у proxy](../pentesting-web/proxy-waf-protections-bypass.md#prefix-exemptions-become-routing-keys), де описано пов’язані, але відмінні межі.

## Записи конфігурації впливають не лише на сховище конфігурації

Та сама операція оновлення конфігурації LiteLLM приймала значення змінних середовища та застосовувала їх до запущеного процесу. Один компонент використовував `UI_LOGO_PATH` як локальний шлях для `FileResponse`, не перевіряючи, чи веде він до логотипа; інший зчитував `UI_USERNAME` і `UI_PASSWORD` під час входу без SSO та призначав `PROXY_ADMIN`, якщо вони збігалися. Отже, дозвіл на запис конфігурації міг призвести як до розкриття локальних файлів, так і до зміни адміністративної ідентичності — залежно від компонента, що використовував ці значення. Тип медіаданих у відповіді не підтверджує, що файл, який надається, є зображенням.<sup>[[1]](#references)</sup>

Конфігурація pass-through endpoint була ще одним downstream-компонентом, що використовував ці дані. Під час ініціалізації приймалися цілі віддалених адаптерів S3/GCS, завантажувалися модулі Python і імпортувалися через `exec_module` з `importlib`. Імпорт виконує код верхнього рівня до використання екземпляра адаптера; обмеження лише на виклик адаптера не усуває цю межу виконання. Розглядайте це як завантаження коду, контрольоване конфігурацією, а не як десеріалізацію файлу моделі.<sup>[[1]](#references)</sup> Про окремий примітив читання файлів див. [включення файлів і обхід шляхів](../pentesting-web/file-inclusion/).

## Маршрутизація моделі для кожного запиту може спричинити leak облікових даних gateway

Функція клієнтських облікових даних LiteLLM приймала об’єкт `user_config` у запиті LLM. Перевірений маршрут створював тимчасовий `litellm.Router` на основі цього об’єкта, зокрема його списку моделей і `api_base` провайдера. Керована клієнтом адреса провайдера могла отримати вихідний запит gateway на генерацію відповіді та налаштовані заголовки автентифікації провайдера. Обмеження для полів верхнього рівня `api_base` або `api_key` не охоплювали цей окремий шлях із вкладеною конфігурацією. Це межа SSRF із доступом до облікових даних, а не проблема prompt injection.<sup>[[1]](#references)</sup>

Під час авторизованого оцінювання gateway зіставте всі шляхи, які можуть створювати router або клієнт провайдера, зокрема конфігурацію для окремого запиту, з політикою призначення та облікових даних, яку використовує звичайний налаштований маршрут.<sup>[[1]](#references)</sup> У [посібнику з SSRF](../pentesting-web/ssrf-server-side-request-forgery/) описано загальний контроль над призначенням серверних запитів; специфічна для gateway проблема полягає в тому, що менш довіреному об’єкту запиту дозволено вибирати призначення, використовуючи привілейовані облікові дані для вихідних запитів.<sup>[[1]](#references)</sup>

## Реєстрація guardrail може обійти sandbox, призначений лише для UI

Шлях тестування коду в gateway і шлях його реєстрації можуть мати різні перевірки. У LiteLLM до версії v1.82.0 UI-тестування користувацького guardrail відхиляло небезпечний синтаксис і виконувало код із `__builtins__ = {}`, але `POST /guardrails` компілював переданий `custom_code` через `exec(compile(...), exec_globals)` без жодної з цих перевірок. Python додає builtins до глобального словника, у якому немає `__builtins__`, тож імпорти на рівні модуля та команди виконувалися **під час реєстрації guardrail**, ще до будь-якого виклику інференсу. Пізніший callback `apply_guardrail` міг розкрити збережений результат через причину блокування.<sup>[[2]](#references)[[3]](#references)</sup>

Під час авторизованої перевірки порівняйте обробники тестування та реєстрації, а не вважайте успішне проходження UI-тесту sandbox доказом безпечності реєстрації. Форма запиту, про яку повідомлялося до виправлення:<sup>[[2]](#references)</sup>

```http
POST /guardrails HTTP/1.1
Authorization: Bearer <master_key>
Content-Type: application/json

{
  "guardrail": {
    "guardrail_name": "probe",
    "litellm_params": {
      "guardrail": "custom_code", "mode": "pre_call", "default_on": true,
      "custom_code": "import os\nresult = os.popen('id').read()\ndef apply_guardrail(inputs, request_data, input_type):\n    return {'action': 'block', 'reason': result}"
    }
  }
}
```

Ендпоінт реєстрації також приймав звичайні API keys, оскільки в ньому не було перевірки `PROXY_ADMIN`. Якщо master key або автентифікацію JWT/OAuth2 не було налаштовано, обробник автентифікації до виправлення призначав `PROXY_ADMIN` навіть анонімним запитам. Виправлення змінило роль за відсутності автентифікації на `INTERNAL_USER`, додало перевірки адміністративних прав для guardrail і під час реєстрації перевіряє та обмежує builtins. Ці межі ролей і виконання коду не пов’язані з [проблемою резервного використання токена MCP](AI-MCP-Servers.md#mcp-token-passthrough-must-not-create-an-anonymous-session).<sup>[[2]](#references)[[3]](#references)</sup>

## Admin-маршрути pass-through можуть проксувати метадані хмари

Функція pass-through endpoint у LiteLLM дає адміністратору змогу налаштувати HTTP-ціль і, за бажанням, додавати підшляхи. На відміну від описаної вище проблеми маршрутизації `user_config` для кожного запиту, тут потрібні **права на запис конфігурації**; сама функція розрахована на довіру до адміністраторів. У повідомленому випадку ціль не перевірялася на належність до приватних або link-local адрес.<sup>[[2]](#references)[[4]](#references)</sup> До версії v1.83.0 звичайні автентифіковані ключі також могли звертатися до `/config/update`, оскільки там не перевірялася адміністративна роль; пов’язану межу запису конфігурації описано в розділі [Класифікація маршрутів UI — це не авторизація](#ui-route-classification-is-not-authorization).<sup>[[2]](#references)[[6]](#references)</sup>

За наявності таких прав і мережевої доступності метаданих EC2 із проксі маршрут на кшталт наведеного нижче відкриває метадані через шлюз. Прапорець `include_subpath` спрямовує `/meta/meta-data/iam/security-credentials/` у `/latest/`.<sup>[[2]](#references)[[4]](#references)</sup>

```http
POST /config/pass_through_endpoint HTTP/1.1
Authorization: Bearer <master_key>
Content-Type: application/json

{"path":"/meta","target":"http://169.254.169.254/latest/","headers":{},"include_subpath":true}
```

[Cloud SSRF guide](../pentesting-web/ssrf-server-side-request-forgery/cloud-ssrf.md#aws) описує обмін токенами IMDSv2; цей маршрут має дозволяти запит `PUT` і передавати обидва заголовки метаданих.<sup>[[5]](#references)</sup> Загальна обробка заголовків для pass-through у LiteLLM видаляє префікс `x-pass-` перед пересиланням, тож `x-pass-X-aws-ec2-metadata-token-ttl-seconds: 21600` і `x-pass-X-aws-ec2-metadata-token: <token>` можуть передати ці заголовки.<sup>[[2]](#references)[[7]](#references)</sup> Проксі має мати доступ до IMDS, відповідь із токеном має проходити через налаштований ліміт переходів, а запит токена не повинен містити `X-Forwarded-For`.<sup>[[5]](#references)</sup> Специфічний для gateway варіант — це **постійний маршрут, контрольований адміністратором, і передавання заголовків запиту**.
