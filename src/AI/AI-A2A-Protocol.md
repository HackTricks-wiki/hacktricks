# Безпека протоколу A2A (Agent2Agent)

{{#include ../banners/hacktricks-training.md}}

## Що таке A2A

A2A (Agent2Agent) — це відкритий протокол, який дає змогу одному AI-агенту знаходити іншого агента та надсилати йому завдання через HTTP. MCP з’єднує агента з **інструментами та даними**; A2A з’єднує агента з **іншими агентами**, які зазвичай є віддаленими сервісами, що належать іншій команді чи компанії. Сервер A2A — це веб-API з LLM-агентом за ним, тому власні об’єкти протоколу (картки агентів, завдання, вебхуки push-сповіщень, розширені картки) додають до звичайного тестування API специфічні перевірки автентифікації, IDOR і SSRF.<sup>[[1]](#references)[[2]](#references)</sup>

Основні складові:

- **Agent Card:** JSON-документ з описом агента: назва, опис, навички, URL-адреси сервісів, підтримувані транспорти, можливості (потокова передача, push-сповіщення, розширена картка) і `securitySchemes`, які має використовувати клієнт. Документ публікується за адресою `https://<host>/.well-known/agent-card.json`. Старіші розгортання, що відповідають специфікації 0.2.x, використовують `/.well-known/agent.json`.<sup>[[1]](#references)[[3]](#references)</sup>
- **Завдання:** одиниця роботи. Повідомлення створює завдання (із згенерованими сервером `id` і `contextId`), а згодом клієнт читає його, скасовує або підписується на нього.<sup>[[1]](#references)</sup>
- **Транспорти:** JSON-RPC 2.0 через HTTP (із SSE для потокової передачі), gRPC та HTTP+JSON REST-прив’язка.<sup>[[1]](#references)</sup>
- **Автентифікація:** облікові дані передаються в HTTP-заголовках (наприклад, `Authorization: Bearer ...`), а не всередині JSON-RPC payload. У картці агента зазначено, яка схема потрібна.<sup>[[1]](#references)</sup>

Назви методів змінювалися між версіями, тому спробуйте обидва набори:<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

| Операція | JSON-RPC 0.2/0.3 | JSON-RPC 1.0 | REST 1.0 |
| --- | --- | --- | --- |
| Надіслати повідомлення | `message/send` | `SendMessage` | `POST /message:send` |
| Потокове надсилання | `message/stream` | `SendStreamingMessage` | `POST /message:stream` |
| Отримати завдання | `tasks/get` | `GetTask` | `GET /tasks/{id}` |
| Перелічити завдання | - | `ListTasks` | `GET /tasks` |
| Скасувати завдання | `tasks/cancel` | `CancelTask` | `POST /tasks/{id}:cancel` |
| Конфігурація push-сповіщень | `tasks/pushNotificationConfig/set` | `CreateTaskPushNotificationConfig` | `POST /tasks/{id}/pushNotificationConfigs` |
| Розширена картка | `agent/getAuthenticatedExtendedCard` (0.3); HTTP `GET agent/authenticatedExtendedCard` (0.2.5) | `GetExtendedAgentCard` | `GET /extendedAgentCard` |

У специфікації 1.0 для вибору версії використовується заголовок `A2A-Version` (або параметр запиту); запити без нього вважаються версією 0.3.<sup>[[1]](#references)</sup>

## Виявлення

```bash
curl -s https://target/.well-known/agent-card.json | jq .
curl -s https://target/.well-known/agent.json | jq .
```

З картки випишіть:

- Кожен `url` сервісу (часто це внутрішнє ім’я хоста, staging URL або порт, відмінний від порту публічного сайту).
- `skills`: вони показують, що може робити агент і які інструменти чи дані стоять за ним.
- `securitySchemes` / `security`: якщо вони порожні або відсутні, агент, імовірно, призначений для виклику без облікових даних.
- `capabilities.pushNotifications` і `capabilities.extendedAgentCard` (у версії 0.3 — `supportsAuthenticatedExtendedCard`).

У специфікації зазначено, що публічна картка не повинна містити облікових даних або внутрішніх деталей реалізації, тому внутрішні URL-адреси, ключі чи докладні списки інструментів у публічній картці вже є знахідкою.<sup>[[1]](#references)</sup>

## Тестування кінцевих точок A2A

### Надсилання завдання без автентифікації

Надішліть мінімальне повідомлення без облікових даних на кожен `url`, указаний у картці:

```bash
# 0.2 / 0.3 style
curl -s https://target/a2a -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","id":1,"method":"message/send",
  "params":{"message":{"role":"user","messageId":"6f1c2b9e-0000-4000-8000-000000000001",
            "parts":[{"kind":"text","text":"Reply only with the word PONG."}]}}}'

# 1.0 style
curl -s https://target/a2a -H 'Content-Type: application/json' -H 'A2A-Version: 1.0' -d '{
  "jsonrpc":"2.0","id":1,"method":"SendMessage",
  "params":{"message":{"role":"ROLE_USER","messageId":"6f1c2b9e-0000-4000-8000-000000000002",
            "parts":[{"text":"Reply only with the word PONG."}]}}}'
```

A результат `Task` або `Message` з `PONG`, коли в картці оголошено схему безпеки, означає, що автентифікація не застосовується до кінцевої точки RPC (вона може застосовуватися лише до UI або картки). Якщо в картці не оголошено схему, перевірте, до чого можуть отримати доступ навички агента: неавтентифікований агент, який може читати внутрішні дані або викликати інструменти, становить таку саму загрозу, як неавтентифікований API для цих інструментів.

### Task IDOR (`tasks/get`, `GetTask`, cancel, subscribe)

Специфікація вимагає, щоб сервер перевіряв для кожного запиту, чи може викликач отримати доступ до завдання, а також обмежував `ListTasks` завданнями викликача, навіть якщо фільтр не вказано.<sup>[[1]](#references)</sup> Перевірте це за допомогою двох ідентичностей (A та B):

1. Як A створіть завдання та збережіть його `id` і `contextId`.
2. Як B (або без облікових даних) викличте `tasks/get` / `GetTask` з `id` від A, а потім `ListTasks` без параметрів.
3. Також спробуйте скасувати завдання A і підписатися на нього, а також надішліть нове повідомлення як B, додавши до нього `taskId` або `contextId` від A (це додасть текст B до розмови A).

```json
{"jsonrpc":"2.0","id":2,"method":"tasks/get","params":{"id":"<task id of user A>","historyLength":10}}
```

Вразливо: B отримує історію, артефакти або статус A чи може змінити завдання A. Безпечно: повертається `TaskNotFoundError`, без різниці між «існує, але не належить вам» і «не існує».<sup>[[1]](#references)</sup> ID завдань часто є UUID, тому шукайте їх там, де вони можуть leak (спільні посилання, журнали, дані push-сповіщень, повідомлення про помилки).

### Push notification webhook SSRF

Якщо `capabilities.pushNotifications` має значення `true`, клієнт передає агенту URL вебхука, а агент згодом надсилає на нього запити `POST` з оновленнями завдань. Специфікація вказує, що агенти мають відхиляти приватні діапазони, localhost і link-local адреси, а також використовувати списки дозволених адрес.<sup>[[1]](#references)</sup> Створіть завдання, зареєструйте конфігурацію push notification, у якій `url` вказує на ваш OAST-хост, щоб підтвердити вихідні запити, а потім (лише якщо це дозволено умовами перевірки) спробуйте внутрішні цілі, як-от `http://127.0.0.1:<port>/` або `http://169.254.169.254/`. Порівнюйте помилки й час відповіді, щоб визначити внутрішні служби. Агент також додає до цих запитів налаштований заголовок автентифікації, тож перевірте, чи не надсилається він на хост, контрольований зловмисником, якщо ви можете змінити URL конфігурації іншого користувача. Див. [SSRF](../pentesting-web/ssrf-server-side-request-forgery/).

### Доступ до розширеної картки агента

`GetExtendedAgentCard` має вимагати автентифікацію та може повертати більше навичок і конфігурації, ніж публічна картка.<sup>[[1]](#references)</sup> Викличте його без облікових даних і з обліковим записом із низькими привілеями, а потім порівняйте результат із публічною карткою.

### Конфігурація push notification і витік облікових даних у завданні

У конфігураціях push notification зберігаються URL вебхука й облікові дані, які агент надсилає на нього. Специфікація вимагає, щоб для кожної операції з конфігурацією push notification (створення, отримання, перелік, видалення) перевірялося, чи має викликач доступ до завдання.<sup>[[1]](#references)</sup> Повторіть тест із двома ідентичностями з [розділу про IDOR завдань](#task-idor-tasksget-gettask-cancel-subscribe) для цих маршрутів. Можливість читати конфігурацію іншого користувача розкриває токен вебхука, а можливість її змінювати дає змогу перенаправити оновлення завдань цього користувача на ваш хост.

Коли під час виконання завдання агенту потрібна додаткова авторизація, він переводить завдання в стан `TASK_STATE_AUTH_REQUIRED`. Клієнт може організувати авторизацію поза каналом; специфікація зазначає, що агенти мають отримувати облікові дані поза каналом, якщо не було узгоджено механізм передавання в каналі. Обмін у каналі може передавати облікові дані ланцюжком агентів A2A і розкрити їх кожному агенту в цьому ланцюжку.<sup>[[1]](#references)</sup> Під час тестування оркестратора перевірте, чи з’являються в повідомленнях, артефактах або історії завдання облікові дані, які користувач надає одному нижчестоящому агенту, і чи можуть їх прочитати інші агенти (або інші користувачі через IDOR завдань).

Поля картки агента й результати завдань також є недовіреними вхідними даними для агента, який їх викликає. Перевірте їх за допомогою технік непрямого prompt injection із розділу [AI Prompts](AI-Prompts.md#third-party-or-indirect-prompt-injection) і перевірок довіри між агентами з [AI Agent Security Methodology](AI-Agent-Security-Methodology.md).
