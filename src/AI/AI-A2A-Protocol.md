# Безпека протоколу A2A (Agent2Agent)

{{#include ../banners/hacktricks-training.md}}

## Що таке A2A

A2A (Agent2Agent) — це відкритий протокол, який дає змогу одному AI-агенту знаходити іншого агента й надсилати йому завдання через HTTP. MCP з’єднує агента з **інструментами й даними**; A2A з’єднує агента з **іншими агентами**, які зазвичай є віддаленими сервісами, що належать іншій команді або компанії. Сервер A2A — це web API з LLM-агентом за ним, тому власні об’єкти протоколу (картки агентів, завдання, вебхуки push-сповіщень, розширені картки) потребують окремих перевірок автентифікації, IDOR і SSRF під час звичайного тестування API.<sup>[[1]](#references)[[2]](#references)</sup>

Основні складові:

- **Agent Card:** JSON-документ з описом агента: ім’я, опис, навички, URL сервісу(-ів), підтримувані транспорти, можливості (потокова передача, push-сповіщення, розширена картка) і `securitySchemes`, які має використовувати клієнт. Його опубліковано за адресою `https://<host>/.well-known/agent-card.json`. У старіших розгортаннях, що відповідають специфікації 0.2.x, використовується `/.well-known/agent.json`.<sup>[[1]](#references)[[3]](#references)</sup>
- **Task:** одиниця роботи. Повідомлення створює завдання (із згенерованими сервером `id` і `contextId`), яке клієнт згодом читає, скасовує або на яке підписується.<sup>[[1]](#references)</sup>
- **Транспорти:** JSON-RPC 2.0 через HTTP (із SSE для потокової передачі), gRPC і прив’язка REST на базі HTTP+JSON.<sup>[[1]](#references)</sup>
- **Автентифікація:** облікові дані передаються в HTTP-заголовках (наприклад, `Authorization: Bearer ...`), а ніколи — у payload JSON-RPC. У картці агента зазначено, яка схема потрібна.<sup>[[1]](#references)</sup>

Назви методів змінювалися між версіями, тож спробуйте обидва набори:<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

| Операція | JSON-RPC 0.2/0.3 | JSON-RPC 1.0 | REST 1.0 |
| --- | --- | --- | --- |
| Надіслати повідомлення | `message/send` | `SendMessage` | `POST /message:send` |
| Потокове надсилання | `message/stream` | `SendStreamingMessage` | `POST /message:stream` |
| Отримати завдання | `tasks/get` | `GetTask` | `GET /tasks/{id}` |
| Перелічити завдання | - | `ListTasks` | `GET /tasks` |
| Скасувати завдання | `tasks/cancel` | `CancelTask` | `POST /tasks/{id}:cancel` |
| Конфігурація push-сповіщень | `tasks/pushNotificationConfig/set` | `CreateTaskPushNotificationConfig` | `POST /tasks/{id}/pushNotificationConfigs` |
| Розширена картка | `agent/getAuthenticatedExtendedCard` (0.3); HTTP `GET agent/authenticatedExtendedCard` (0.2.5) | `GetExtendedAgentCard` | `GET /extendedAgentCard` |

Специфікація 1.0 використовує заголовок `A2A-Version` (або параметр запиту) для вибору версії; запити без нього вважаються версією 0.3.<sup>[[1]](#references)</sup>

## Виявлення

```bash
curl -s https://target/.well-known/agent-card.json | jq .
curl -s https://target/.well-known/agent.json | jq .
```

З картки випишіть:

- Кожен `url`: у версії 1.0 вони містяться в `supportedInterfaces`, тоді як старіші картки можуть містити `url` на верхньому рівні. Запишіть кожну кінцеву точку й транспорт, зокрема внутрішні імена хостів, staging URL і альтернативні порти.<sup>[[1]](#references)[[7]](#references)</sup>
- `skills`: вони показують, що може робити агент і які інструменти чи дані доступні за ним.
- `securitySchemes` / `security`: якщо вони порожні або відсутні, агент, імовірно, призначений для виклику без облікових даних.
- `capabilities.pushNotifications` і `capabilities.extendedAgentCard` (у версії 0.3 — `supportsAuthenticatedExtendedCard`).

У специфікації зазначено, що публічна картка не повинна містити облікових даних або внутрішніх деталей реалізації, тож внутрішні URL, ключі чи детальні списки інструментів у публічній картці вже є знахідкою.<sup>[[1]](#references)</sup>

### Колізія імен Agent Card на хості з кількома агентами

`name` картки — це зрозуміла людині мітка, а не стабільний ідентифікатор маршрутизації.<sup>[[1]](#references)[[5]](#references)</sup> Якщо хост реєструє два різні віддалені вузли під однаковим локальним іменем, його дерево агентів, згенероване ім’я інструмента, мапа клієнтів або маршрут брокера можуть надіслати завдання, призначене довіреному вузлу, іншому вузлу.<sup>[[5]](#references)</sup> Для цього потрібно, щоб контрольований зловмисником вузол був допущений до **того самого простору маршрутизації**; сама публікація дубліката картки в Інтернеті недостатня.<sup>[[5]](#references)</sup>

Перевірте шлях **від допуску до диспетчеризації** на хості за допомогою двох контрольованих вузлів, різних URL і нешкідливого маркера:<sup>[[5]](#references)</sup>

1. Зафіксуйте картку довіреного вузла, його origin і локальний селектор. Зареєструйте другий вузол із карткою, що має таке саме `name`, але URL якої вказує на контрольовану вами кінцеву точку.
2. Виконайте операцію, яка вибирає довірений вузол за іменем. Перевірте обидва порядки реєстрації, а якщо імена стають ідентифікаторами інструментів — також звичну для хоста нормалізацію імен. Зафіксуйте, яка кінцева точка отримала маркер і який агент повернув відповідь.
3. Змініть лише ім’я другого вузла й повторіть перевірку. Якщо запит надходить до другої кінцевої точки тільки за наявності колізії, це доводить диспетчеризацію до неправильного вузла. Окремо перевірте, чи були передані конфіденційний контекст або облікові дані; сама колізія імен **не** доводить передавання облікових даних або повноважень інструментів.

Якщо викликач звертається до фіксованої кінцевої точки, прив’язаної до origin, а не визначає її за іменем картки, ця перевірка не застосовується.<sup>[[5]](#references)</sup> Щоб перевірити подальші відповіді зловмисного вузла та вплив prompt injection, див. [AI Agent Security Methodology](AI-Agent-Security-Methodology.md#exploitation-cross-a-trust-boundary).

## Перевірка кінцевих точок A2A

### Надсилання завдання без автентифікації

Надішліть мінімальне повідомлення без облікових даних на кожен `url`, указаний у картці:

```bash
# 0.2 / 0.3 style
curl -s https://target/a2a -H 'Content-Type: application/json' -d '{
  "jsonrpc":"2.0","id":1,"method":"message/send",
  "params":{"message":{"role":"user","messageId":"6f1c2b9e-0000-4000-8000-000000000001",
            "parts":[{"kind":"text","text":"Reply only with the word PONG."}]}}}'

# 1.0 style
curl -s https://target/a2a -H 'Content-Type: application/json' -H 'A2A-Version: 1.0' -d '{
  "jsonrpc":"2.0","id":1,"method":"SendMessage",
  "params":{"message":{"role":"ROLE_USER","messageId":"6f1c2b9e-0000-4000-8000-000000000002",
            "parts":[{"text":"Reply only with the word PONG."}]}}}'
```

Результат `Task` або `Message` зі значенням `PONG`, коли в card оголошено схему безпеки, означає, що автентифікація не застосовується до кінцевої точки RPC (її можуть застосовувати лише до UI або card). Якщо в card не оголошено схему, перевірте, до чого можуть отримати доступ навички agent: agent без автентифікації, який може читати внутрішні дані або викликати інструменти, — це те саме, що API без автентифікації для цих інструментів.

### Task IDOR (`tasks/get`, `GetTask`, cancel, subscribe)

Специфікація вимагає, щоб сервер під час кожного запиту перевіряв, чи має caller доступ до task, а також обмежував `ListTasks` даними caller, навіть якщо фільтр не задано.<sup>[[1]](#references)</sup> Перевірте це за допомогою двох ідентичностей (A і B):

1. Як A створіть task і збережіть його `id` та `contextId`.
2. Як B (або без облікових даних) викличте `tasks/get` / `GetTask` із `id` користувача A, а потім `ListTasks` без параметрів.
3. Також спробуйте скасувати task A і підписатися на нього, а також надішліть нове повідомлення як B із `taskId` або `contextId` користувача A (це додасть текст B до розмови A).

```json
{"jsonrpc":"2.0","id":2,"method":"tasks/get","params":{"id":"<task id of user A>","historyLength":10}}
```

Уразливий варіант: B отримує історію, артефакти чи статус A або може змінити завдання A. Захищений варіант: `TaskNotFoundError`, без різниці між «існує, але це не ваше» та «не існує».<sup>[[1]](#references)</sup> ID завдань часто є UUID, тож шукайте їх у місцях, де вони можуть leak (спільні посилання, журнали, payload push-сповіщень, повідомлення про помилки).

### SSRF через webhook push-сповіщень

Коли `capabilities.pushNotifications` має значення `true`, клієнт передає агенту URL webhook, а агент згодом надсилає на цей URL запити `POST` з оновленнями завдань. У специфікації зазначено, що агенти мають відхиляти приватні діапазони, localhost і link-local адреси та використовувати списки дозволених адрес.<sup>[[1]](#references)</sup> Створіть завдання, зареєструйте конфігурацію push-сповіщень, у якій `url` вказує на ваш OAST-хост, щоб підтвердити вихідні запити, а потім (лише якщо це дозволено в межах тестування) перевірте внутрішні цілі, як-от `http://127.0.0.1:<port>/` або `http://169.254.169.254/`. Порівняйте помилки й час відповіді, щоб виявити внутрішні сервіси. Агент також додає до цих запитів налаштований заголовок автентифікації, тож перевірте, чи не надсилається він на хост, контрольований зловмисником, якщо ви можете змінити URL конфігурації іншого користувача. Див. [SSRF](../pentesting-web/ssrf-server-side-request-forgery/).

### Частини file-URL як друга точка входу для SSRF

У A2A 1.0 повідомлення або артефакт можуть містити посилання на файл як `Part` з `url` (у версії 0.3 використовується `kind: "file"` і `file.uri`).<sup>[[1]](#references)[[4]](#references)[[7]](#references)</sup> Протокол передає посилання; отримання файлу — це поведінка застосунку, а не вимога SDK A2A.<sup>[[6]](#references)</sup> Це окремо від URL callback push-сповіщень, описаного вище. Перевірте обидва напрямки: файл, надісланий клієнтом серверу A2A, і URL файлу, повернутий оркестратору вузлом із нижчим рівнем довіри.<sup>[[1]](#references)[[6]](#references)</sup>

Для авторизованої кінцевої точки JSON-RPC версії 1.0 замініть звичайну текстову частину URL-адресою з унікальним шляхом OAST і перевірте, **який компонент** виконує запит:<sup>[[1]](#references)[[7]](#references)</sup>

```bash
curl -s https://target/a2a -H 'Content-Type: application/json' -H 'A2A-Version: 1.0' -d '{
  "jsonrpc":"2.0","id":1,"method":"SendMessage",
  "params":{"message":{"role":"ROLE_USER",
    "messageId":"6f1c2b9e-0000-4000-8000-000000000003",
    "parts":[{"url":"https://oast.example/part-probe","filename":"probe.txt","mediaType":"text/plain"}]}}}'
```

Лише якщо одержувач виконає запит до нього, тестуйте внутрішні адреси в межах scope, перенаправлення та зміни DNS-резолвінгу за допомогою [SSRF workflow](../pentesting-web/ssrf-server-side-request-forgery/). Наявність коректного `Part` або успішна відповідь на завдання самі по собі не доводять наявність SSRF; підтвердьте, що запит надійшов до цільової адреси, а також чи отриманий вміст передається агенту.<sup>[[6]](#references)</sup>

### Доступ до розширеної картки агента

`GetExtendedAgentCard` має вимагати автентифікацію та може повертати більше навичок і конфігурації, ніж публічна картка.<sup>[[1]](#references)</sup> Викличте його без облікових даних і з низькопривілейованим обліковим записом, а потім порівняйте результат із публічною карткою.

### Конфігурація push-сповіщень і credential leak під час завдання

У конфігураціях push-сповіщень зберігаються URL вебхука й облікові дані, які агент надсилає на нього. Специфікація вимагає, щоб під час кожної операції з конфігурацією push-сповіщень (створення, отримання, перелік, видалення) перевірялося, чи має викликач доступ до завдання.<sup>[[1]](#references)</sup> Повторіть тест із двома обліковими записами з [розділу про task IDOR](#task-idor-tasksget-gettask-cancel-subscribe) для цих маршрутів. Читабельна конфігурація іншого користувача може розкрити токен вебхука, а можливість її змінити — перенаправити оновлення завдань цього користувача на ваш хост.

Коли агенту потрібна додаткова авторизація під час завдання, він переводить завдання в стан `TASK_STATE_AUTH_REQUIRED`. Клієнт може організувати авторизацію поза каналом; специфікація вказує, що агенти мають отримувати облікові дані поза каналом, якщо не було узгоджено механізм обміну в каналі. Обмін у каналі може передати облікові дані ланцюжком агентів A2A і зробити їх доступними кожному агенту в цьому ланцюжку.<sup>[[1]](#references)</sup> Під час тестування оркестратора перевірте, чи з’являються облікові дані, надані користувачем для одного downstream-агента, у повідомленнях, артефактах або історії завдань, доступних іншим агентам (або іншим користувачам через task IDOR).

Поля картки агента й результати завдань також є недовіреним введенням для агента, що їх викликає. Перевірте їх за допомогою технік непрямої prompt injection з [AI Prompts](AI-Prompts.md#third-party-or-indirect-prompt-injection) і перевірок довіри між агентами з [AI Agent Security Methodology](AI-Agent-Security-Methodology.md).
