# AI Agent Security Methodology

{{#include ../banners/hacktricks-training.md}}

エージェントの評価では、**攻撃者が制御する入力から外部で観測可能な影響まで**を追跡します。Jailbreaking、文字の変更、システムプロンプトの開示は、推論チャネルが操作可能であることを示します。しかし、重大な発見となるのは、データアクセス、不正なツール操作、下流のインジェクションシンク、永続化、または別のエージェントへとつながる一連の攻撃です。<sup>[[2]](#references)</sup>

[OWASP Top 10 for Agentic Applications](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) は、カバレッジ（目標の乗っ取り、ツールの悪用、権限の濫用、サプライチェーン、コード実行、メモリポイズニング、エージェント間の信頼、連鎖的障害、人間の信頼、ローグエージェント）を分類するのに役立ちます。モデルが予期しないテキストを出力しただけでテストを終えるのではなく、エンドツーエンドの攻撃経路を構築してから、これらの分類を使ってください。<sup>[[1]](#references)[[2]](#references)</sup>

## Build the target map

ペイロードを作成する前に、エージェントの各ワークフローについて、次の5つの側面を記録してください。<sup>[[2]](#references)</sup>

| Dimension | What to enumerate | Security question |
|---|---|---|
| **信頼できない入力** | チャット/APIパラメーター、URL、ドキュメント、メール、チケット、カレンダー項目、取得したチャンク、メモリ、ツールの結果、エージェント間メッセージ | 後でモデルのコンテキストに入るコンテンツを、攻撃者はどこに配置できるか？ |
| **ツール** | ツール名とスキーマ、副作用、自動実行、確認動作、動的に読み込まれるツール | どの呼び出しが秘密情報を読み取り、状態を書き換え、メッセージを送信し、データを削除し、コードを実行し、または価値を移転するか？ |
| **権限** | ユーザーによる委任、サービスアカウント、APIトークン、認証情報の有効期間、テナント/リソースのスコープ、ネットワーク到達範囲 | 各呼び出しはどのIDで実行され、ツールの境界で認可が再確認されるか？ |
| **処理** | クエリビルダー、シェル、URLフェッチャー、テンプレートエンジン、インタープリター、パーサー、ファイル操作、デシリアライザー | モデル生成データが、別のインタープリターに渡す構文になる場所はどこか？ |
| **出力** | 応答、レンダリングされたMarkdown/HTML、リンク、画像の取得、webhook、メール、ファイル、ログ、レポート、メトリクス、エージェント間の通信 | 秘密情報を運んだり、二次リクエストを発生させたりする観測可能なチャネルはどれか？ |

これを、宣伝されている連携機能の一覧にまとめてしまわないでください。有用な成果物では、各ソースが到達する正確なコンテキスト位置、その時点で利用可能なツール、各ツールが使用する認証情報、下流のインタープリター、すべての送信経路を対応づけます。同じツールでも、ユーザーごとの読み取り専用トークンを使う場合は影響が小さく、共有管理者認証情報を使う場合は重大な影響を及ぼす可能性があります。<sup>[[2]](#references)</sup>

## Reconnaissance

### Map every delivery and ingestion path

配信面（Web、モバイル、API、メール、チャットプラットフォーム、ブラウザー拡張機能）から調査を始め、クライアントからバックエンドへの通信をプロキシで確認します。UIでは非表示のフィールド、検索/オートコンプリート/フィルターのパラメーター、会話状態オブジェクト、アップロードおよびインデックス作成ジョブ、ツールの応答、サブエージェントの通信を調べます。実際のリクエストスキーマを確認する前に証明書ピンニングを回避する必要がある場合は、モバイル専用クライアントにエミュレーターと計装が必要になることがあります。<sup>[[2]](#references)</sup>

次に、モデルの下にあるスタックを把握します。オーケストレーションフレームワーク、プロンプトの組み立て、検索とメモリのストア、ランタイム（Python、コンテナ、WASMなど）、マウントされたボリューム、ホストサービス、内部API、クラウドメタデータへの到達可能性、隣接ネットワークを調べます。フレームワークのデフォルト設定は重要です。一部の「ツール呼び出し」は、コードの生成や評価によって実装されているためです。その結果が封じ込められるかどうかは、ランタイム/サンドボックスの境界によって決まります。<sup>[[2]](#references)</sup>

### Fingerprint routing with non-destructive probes

スコープ内のリクエストを複数の無関係なリクエストと比較し、レスポンス全体、ステータスコード、レイテンシ、ストリーミング動作を記録します。タスク固有の推論が始まる前に安定して拒否される場合は、別のゲートウェイ/分類器が存在する可能性があります。文脈に応じた拒否は、リクエストがモデルに届いたことを示唆します。空の応答や抽出だけの応答は、キーワード検索や限定的な検索を示している可能性があります。これらは仮説として扱い、別のAPIフィールドや取り込み経路を通じて同じプローブを再実行し、確認してください。<sup>[[2]](#references)</sup>

攻撃者が制御するソースのうち、エージェントの動作を変化させる最初のものと、そのソースから到達可能なツール、ID、インタープリター、出力を評価者が特定できれば、偵察は完了です。<sup>[[2]](#references)</sup>

## Exploitation: cross a trust boundary

プロンプトの文言だけでなく、チャネルをテストします。まず直接のインジェクションで、ユーザーに見える入口が何をブロックするかを確認し、次に、同等の意図を以下の目立ちにくい経路から再度試します。<sup>[[2]](#references)</sup>

- **間接コンテンツ:** ページ、ファイル、メール、チケット、メタデータ、altテキスト、HTMLコメント、画面外のテキスト、またはゼロ幅文字。ペイロードの配信手法については、[AI Prompts](AI-Prompts.md#third-party-or-indirect-prompt-injection) を参照してください。
- **検索とメモリ:** 後で検索されるコンテンツや、後続セッションで再読み込みされる状態を汚染します。元のソースを削除すると動作もなくなるかを記録してください。
- **ツールの出力とピアエージェント:** ツールの応答やエージェント間メッセージにマーカーを埋め込み、ユーザー入力と最終出力にのみ適用されるフィルターを、内部通信が回避するかテストします。
- **サプライチェーン:** ツールの記述子、プラグイン、接続されたサーバー、スキル、モデル、依存関係を、信頼された指示ソースとして確認します。MCP固有のテストについては、[MCP Servers](AI-MCP-Servers.md#mcp-vulns) を参照してください。
- **人間による承認:** 実際の構造化ツール呼び出しと、モデルが生成した承認テキストを比較します。攻撃者による操作で、宛先、スコープ、対象オブジェクト、または取り消し不能な副作用が省略されるかテストします。

まず、無害で一意なマーカーを使います。可能であれば、ソースアーティファクト、組み立てられたコンテキスト、選択されたツール呼び出し、承認データ、バックエンドのリクエスト/レスポンス、最終状態を保存してください。これにより、操作の影響と、実際には起きていない操作を起きたとする幻覚を区別できます。<sup>[[2]](#references)</sup>

### Subagent context isolation

Claude Agent SDKの非forkサブエージェントには、独自の`AgentDefinition.prompt`、委任プロンプト、利用可能なツールが渡されますが、親のシステムプロンプトや会話は渡されません。定義で`tools`を省略すると、サブエージェントが利用できるツールを引き継ぎます。プロジェクトの`CLAUDE.md`は引き続き読み込まれる場合があります。そのため、子エージェントが同じファイルシステムや実行ツールを使える場合、親だけに適用されるプロンプト制限は信頼できる境界になりません。<sup>[[4]](#references)</sup>

親が拒否する直接リクエストと、同じタスクを名前付きのサブエージェントに委任した場合を比較して、境界をテストします。NCC Groupは、オペレーティングシステムのファイル列挙を拒否したエージェントが、子エージェントへの依頼を無害な「レイアウトマップ」と言い換えると成功した事例を報告しています。<sup>[[3]](#references)</sup>

親の最終回答だけでなく、子エージェントの実際のツール呼び出しと有効なツール許可リストを確認し、親には許可されないファイルに子エージェントがアクセスしたかを確かめてください。<sup>[[4]](#references)</sup>これはガードレールの継承に関する不備であり、[Python sandbox](../generic-methodologies-and-resources/python/bypass-python-sandboxes/)やコンテナからの脱出が起きた証拠ではありません。<sup>[[3]](#references)[[4]](#references)</sup>

## Execution: prove real impact

操作から影響に至る経路は、大きく2つに分かれます。<sup>[[2]](#references)</sup>

1. **機能の悪用:** 許可されたツールが、すでに目的の操作を実行できます。たとえば、あるテナントのレコードを読み取り、攻撃者が確認できるレポートに書き込む、メールを送信する、レコードを変更する、ファイルを削除する、または支払いを開始する、といった操作です。二次的なソフトウェアの脆弱性は必要ありません。
2. **下流シンクの悪用:** 攻撃者に操作されたモデル出力が、別のコンポーネントに渡される構文になります。[SQL injection](../pentesting-web/sql-injection/README.md)や[NoSQL injection](../pentesting-web/nosql-injection.md)についてはデータベースクエリを、[command injection](../pentesting-web/command-injection.md)についてはシェルラッパーを、[SSRF](../pentesting-web/ssrf-server-side-request-forgery/README.md)については指定可能なURLを確認してください。また、パストラバーサルについてはファイル操作を、RCEについてはテンプレート/コード評価器を、[unsafe deserialization](../pentesting-web/deserialization/README.md)についてはオブジェクトパーサーを確認します。

候補ごとに、次の一連の流れを実証してください。<sup>[[2]](#references)</sup>

```text
attacker-controlled source
  -> model/context influence
  -> selected tool and arguments
  -> effective identity/credential
  -> capability or vulnerable sink
  -> externally verified state change or data egress
```

読み取り専用のintegrationでも、後続のコンポーネントが読み取った内容を公開できるなら悪用可能です。通常の応答に加えて、攻撃者が制御するリンク、自動画像取得、webhook、ログ、レポート、カウンター、通知、他のagentへのメッセージなど、見落とされがちなegressもテストしてください。<sup>[[2]](#references)</sup>

## 目的に対するアクション

あるアクションを確認した後、最初に見えた影響で終わらせず、影響範囲全体を評価してください。<sup>[[2]](#references)</sup>

- **情報窃取:** 秘密情報、ユーザーレコード、内部ファイル、会話データ、またはprompt/contextの内容が、観測可能な経路を通じて外部に漏れる。
- **不正なアクション:** agentが正規の書き込み機能を攻撃者の目的に利用する。
- **サービス拒否:** 破壊的なツールや、コストの高い操作の繰り返しが、完全性または可用性に影響を及ぼす。
- **永続化:** 汚染されたmemory、インデックス化されたコンテンツ、信頼済み状態、またはruntimeの変更が、発端となったセッションやソースの削除後も残る。
- **伝播:** 信頼されたpeerが侵害されたagentのメッセージまたは共有状態を取り込み、自身のツールと認証情報を使って同じアクションを繰り返す。

深刻度は、modelの文章がどれほど意外かではなく、アクセス可能なデータ、実効権限、sinkの悪用可能性、egress、永続化、伝播に基づいて判断してください。<sup>[[2]](#references)</sup>

## 評価時に検証するControls

Prompt filterやより適切なsystem promptは攻撃者のコストを高めることはできますが、認可境界として扱うべきではありません。以下のcontrolsについて、直接入力、間接コンテンツ、memory、ツール、peer agentを経由して同じ攻撃チェーンを再実行し、検証してください。<sup>[[2]](#references)</sup>

- 決定論的なpolicy layerが、**各ツール呼び出しのたびに**認証済みユーザー、tenant、オブジェクト、アクション、送信先を確認する。modelが呼び出し元のidentityを指定または上書きできない。
- 読み取りと書き込みの権限には、それぞれ別個の最小権限かつ短命な認証情報を使用する。影響の大きいツールは必要なときだけ公開し、取り込んだコンテンツを起点に自動実行しない。
- ネットワークegressと内部宛先は、modelが選択したURLとは独立してallowlistで制限する。必要な場合を除き、runtimeからmetadata endpoint、マウントされたsecret、近隣のserviceへのアクセスをブロックする。
- Approval UIは正規の構造化リクエストから生成し、modelによる自由形式の要約ではなく、正確な引数、identity、送信先、対象オブジェクト、副作用を表示する。
- 成功は送信先システムまたはsystem of recordで確認する。agentによる説明、ツール呼び出しリクエスト、HTTP redirectは、主張された状態変更の証拠にならない。
- Memoryとretrievalのエントリーにはprovenanceと信頼ラベルを保持し、無効化できるようにする。また、後続のアクションで使用する際に再認可する。
- agent間のメッセージは、信頼できないリクエストとして認証・認可する。peerの評判やagent cardによって、受信側のツール使用権限が暗黙に委譲されることはない。
