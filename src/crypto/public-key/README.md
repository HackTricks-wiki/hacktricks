# Криптографія з відкритим ключем

{{#include ../../banners/hacktricks-training.md}}

У багатьох складних криптографічних CTF-завданнях використовуються RSA, криптографія на еліптичних кривих (ECC), ECDSA, решітки або слабка випадковість.

## Рекомендовані інструменти

- [SageMath](https://www.sagemath.org/) для модульної арифметики, еліптичних кривих і редукції решіток<sup>[[1]](#references)</sup>
- [RsaCtfTool](https://github.com/RsaCtfTool/RsaCtfTool) для перевірки типових вразливостей RSA<sup>[[2]](#references)</sup>
- [FactorDB](https://factordb.com/) для перевірки, чи має ціле число відомі множники<sup>[[3]](#references)</sup>
- Бібліотека Python [`ecdsa`](https://ecdsa.readthedocs.io/) для розбору ключів, підписування та перевірки підписів<sup>[[7]](#references)</sup>

## ECC / ECDSA

Якщо задіяні підписи, перевірте повторне використання nonce, його упередженість або витік, перш ніж припускати, що потрібно розв’язувати задачу дискретного логарифмування.

### Повторне використання nonce / упередженість у ECDSA

ECDSA вимагає нового секретного числа `k` для кожного повідомлення. Якщо те саме `k` використовується для підпису двох різних хешів повідомлень, приватний ключ можна відновити з відкритих значень підписів.<sup>[[4]](#references)</sup>

Навіть якщо значення `k` не збігаються, упередженість або витік бітів nonce у багатьох підписах можуть дати змогу відновити ключ за допомогою решіток.<sup>[[5]](#references)</sup>

Технічне відновлення, коли `k` використовується повторно:<sup>[[4]](#references)</sup>

Рівняння підпису ECDSA (порядок групи `n`):

- `r = (kG)_x mod n`
- `s = k^{-1}(h(m) + r*d) mod n`

Якщо те саме `k` повторно використано для двох повідомлень `m1, m2`, що дають підписи `(r, s1)` і `(r, s2)`:

- `k = (h(m1) - h(m2)) * (s1 - s2)^{-1} mod n`
- `d = (s1*k - h(m1)) * r^{-1} mod n`

### Атаки з некоректною кривою

Якщо протокол не перевіряє, що вхідна точка належить очікуваній кривій і правильній підгрупі, зловмисник може змусити виконувати операції у слабшій групі та отримати інформацію про секретний скаляр. У SEC 1 визначено перевірки відкритих ключів, призначені для запобігання таким вхідним даним.<sup>[[6]](#references)</sup>

Технічна примітка:

- Переконайтеся, що точки не є точкою на нескінченності, мають коректні координати, задовольняють рівняння кривої та належать до потрібної підгрупи.<sup>[[6]](#references)</sup>
- У CTF-завданнях це часто моделюється як сервер, що множить вибрану зловмисником точку на секретний скаляр і повертає похідне значення.

## Некоректні ключі підпису ML-DSA та витік через відхилення вибірки

Розгорнутий приватний ключ ML-DSA кодує вектори поліномів `s1` і `s2` з коефіцієнтами в діапазоні `[-η, η]`. У FIPS 204 зазначено, що декодування некоректних байтів секретного ключа може давати коефіцієнти поза цим діапазоном. Сам алгоритм підписування не вимагає додаткової перевірки узгодженості приватного ключа.<sup>[[8]](#references)</sup>

Необхідною передумовою є контроль над **розгорнутим ключем підпису до його імпорту або використання для підписування**, а не подання некоректного відкритого ключа верифікатору. Поблажливий механізм імпорту може прийняти змінені упаковані коефіцієнти, а створені підписи все одно можуть проходити перевірку. Порівняйте поведінку під час імпорту й підписування, а потім перевірте отримані підписи за допомогою [процесу фаззингу криптографічного кодування ключів](../../generic-methodologies-and-resources/fuzzing.md#differential-fuzzing-of-cryptographic-key-encodings).<sup>[[9]](#references)[[10]](#references)</sup>

Підписування обчислює `z = y + c·s1` і `r0 = LowBits(w − c·s2)`, відхиляючи кандидат, якщо `||z||∞ ≥ γ1 − β` або `||r0||∞ ≥ γ2 − β`. Завдяки цим перевіркам прийняті результати не залежать від коректних малих секретів. Коефіцієнти секрету поза допустимим діапазоном можуть порушити це обґрунтування відхилення вибірки та спричинити залежне від секрету зміщення. Це умовний механізм витоку, **а не підтверджене повне відновлення ключа на основі виявленої розбіжності між бібліотеками**.<sup>[[8]](#references)[[10]](#references)</sup>

Перевірка приватного ключа відрізняється від перевірки підпису. У порівнянні, про яке повідомлялося, OpenSSL, BoringSSL і SymCrypt виконували додаткові перевірки приватного ключа, тоді як liboqs приймала некоректні розгорнуті ключі під час підписування; базова бібліотека `mldsa-native` надає валідатор `pk_from_sk()`, який liboqs не відкрила. FIPS 204 не вимагає цих додаткових перевірок.<sup>[[9]](#references)[[10]](#references)</sup>
