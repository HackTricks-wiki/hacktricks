## Γρήγορη διαλογή

Συλλέξτε:

- `n`, `e`, `c` (και τυχόν πρόσθετα ciphertexts)
- Τυχόν σχέσεις μεταξύ των μηνυμάτων (ίδιο plaintext; κοινό modulus; δομημένο plaintext;)
- Τυχόν leaks (μερικά `p/q`, bits του `d`, `dp/dq`, γνωστό padding)

Στη συνέχεια δοκιμάστε:

- Έλεγχο παραγοντοποίησης (Factordb / `sage: factor(n)` για σχετικά μικρά μεγέθη)
- Μοτίβα χαμηλού εκθέτη (`e=3`, broadcast)
- Common modulus / επαναλαμβανόμενους πρώτους
- Μεθόδους πλέγματος (Coppersmith/LLL) όταν κάτι είναι σχεδόν γνωστό

## Συνήθεις επιθέσεις RSA

### Common modulus

Αν δύο ciphertexts `c1, c2` κρυπτογραφούν το **ίδιο μήνυμα** με το **ίδιο modulus** `n`, αλλά με διαφορετικούς εκθέτες `e1, e2` (και `gcd(e1,e2)=1`), μπορείτε να ανακτήσετε το `m` χρησιμοποιώντας τον εκτεταμένο ευκλείδειο αλγόριθμο:

`m = c1^a * c2^b mod n` όπου `a*e1 + b*e2 = 1`.

Ενδεικτικά βήματα:

1. Υπολογίστε `(a, b) = xgcd(e1, e2)`, ώστε `a*e1 + b*e2 = 1`
2. Αν `a < 0`, ερμηνεύστε το `c1^a` ως `inv(c1)^{-a} mod n` (το ίδιο και για το `b`)
3. Πολλαπλασιάστε και κάντε αναγωγή modulo `n`

### Κοινοί πρώτοι παράγοντες μεταξύ moduli

Αν έχετε πολλά RSA moduli από την ίδια πρόκληση, ελέγξτε αν έχουν κοινό πρώτο παράγοντα:

- `gcd(n1, n2) != 1` υποδηλώνει καταστροφική αστοχία στη δημιουργία κλειδιών.

Αυτό εμφανίζεται συχνά σε CTFs με διατυπώσεις όπως «δημιουργήσαμε πολλά κλειδιά γρήγορα» ή «κακή τυχαιότητα».

### Αραιά / short-sleeve moduli

Ορισμένες προβληματικές γεννήτριες μεγάλων ακεραίων διαρρέουν τη δομή τους απευθείας στο δημόσιο modulus: κάθε limb περιέχει μόνο ένα μικρό τυχαίο υποπεδίο και τα υπόλοιπα bits είναι `0`. Στην πράξη, αυτό εμφανίζεται ως **μπλοκ μηδενικών σε τακτά διαστήματα** σε όλο το `n`, συχνά ευθυγραμμισμένα σε limbs των 32 ή 128 bit.<sup>[[1]](#references)</sup>

Γρήγοροι έλεγχοι:

- Εμφανίστε το `n` σε hex και αναζητήστε επαναλαμβανόμενα παράθυρα μηδενικών με σταθερό βήμα.
- Χωρίστε ξανά το `n` σε limbs (`2^32`, `2^64`, `2^128`) και ελέγξτε αν κάθε limb είναι ασυνήθιστα μικρό.
- Ελέγξτε δημόσια κλειδιά SSH/TLS με εργαλεία όπως το **badkeys**, αν υποψιάζεστε αδύναμη δημιουργία host-key.<sup>[[2]](#references)</sup><sup>[[3]](#references)</sup>

Αυτό είναι σοβαρότερο από μια στατιστική μεροληψία: αν και οι δύο ιδιωτικοί παράγοντες `p` και `q` είναι short-sleeved, το modulus μπορεί να είναι **εύκολο να παραγοντοποιηθεί**.<sup>[[1]](#references)</sup>

### Παραγοντοποίηση πολυωνύμων δομημένων RSA keys

Για ένα πιθανολογούμενο πλάτος limb `w`, γράψτε το modulus σε βάση `B = 2^w`:

- `n = Σ_i n_i B^i`
- `f_n(x) = Σ_i n_i x^i`

Επειδή η αποτίμηση διατηρεί τον πολλαπλασιασμό, `f_a(B) * f_c(B) = (f_a * f_c)(B)`. Αν οι παράγοντες έχουν επίσης αραιούς συντελεστές limb, τότε:

- `n = p*q`
- `f_n(x) = f_p(x) * f_q(x)`

Περίγραμμα επίθεσης:

1. Μαντέψτε το πλάτος limb `w`.
2. Μετατρέψτε το δημόσιο modulus `n` σε `f_n(x)` χρησιμοποιώντας βάση `2^w`.
3. Παραγοντοποιήστε το `f_n(x)` στους ακεραίους.
4. Αποτιμήστε τους υποψήφιους παράγοντες ξανά στο `B = 2^w`.
5. Επαληθεύστε ποιοι υποψήφιοι παράγοντες δίνουν γινόμενο `n`.

Αυτό **δεν σπάει το κανονικό RSA**. Λειτουργεί μόνο όταν οι ίδιοι οι πρώτοι παράγοντες έχουν πολύ μικρούς, ιδιαίτερα δομημένους συντελεστές limb.<sup>[[1]](#references)</sup>

### Διαρροή μετατοπισμένων limb

Τα αραιά bytes δεν είναι πάντα ευθυγραμμισμένα στο χαμηλό άκρο κάθε limb. Αν η απευθείας μετατροπή σε βάση `2^w` παράγει μεγάλους συντελεστές, αναζητήστε μετατοπίσεις `i,j` ώστε τα `2^i p` και `2^j q` να γίνουν αραιά σε αυτή τη βάση limb. Το πολυώνυμο γινομένου μπορεί και πάλι να παραχθεί από το δημόσιο modulus, να παραγοντοποιηθεί και να συνδυαστεί ξανά ώστε να προκύψουν οι αρχικοί ακέραιοι παράγοντες.<sup>[[1]](#references)</sup>

### Ένδειξη προβλήματος στην υλοποίηση: σφάλμα RNG κατά τη μετατροπή byte σε limb

Ένα επικίνδυνο μοτίβο είναι να υπολογίζεται ο αριθμός των **limbs των 32 bit**, να δεσμεύονται μόνο τόσα **bytes** και να αντιγράφονται στον πίνακα limb:

```csharp
int numLimbs = bits / 32;
byte[] array = new byte[numLimbs];
rngProvider.GetNonZeroBytes(array);
Array.Copy(array, 0, bignumLimbs, 0, numLimbs);
bignumLimbs[numLimbs - 1] |= 0x80000000;
```

Αυτό δίνει σε κάθε limb 32 bit μόνο **8 bit εντροπίας**, καθώς και ένα υποχρεωτικό κορυφαίο bit στο τελευταίο limb. Οι παραγόμενοι πρώτοι αριθμοί RSA μπορούν συχνά να αναγνωριστούν και να παραγοντοποιηθούν μόνο από το δημόσιο κλειδί.<sup>[[1]](#references)</sup>

### Σχετική λειτουργία αποτυχίας του DSA

Αν η ίδια ελαττωματική ρουτίνα μεγάλων ακεραίων χρησιμοποιηθεί ξανά για την παραγωγή ιδιωτικών εκθετών DSA, το δημόσιο κλειδί `y = g^x` μπορεί να διαρρεύσει έναν **δραστικά μειωμένο και δομημένο** χώρο αναζήτησης για το `x`. Μόλις γίνει γνωστό το μοτίβο των limb, επιθέσεις διακριτού λογαρίθμου όπως το **baby-step giant-step** μπορεί να είναι πρακτικές έναντι των δημόσιων παραμέτρων.<sup>[[1]](#references)</sup>

### Håstad broadcast / χαμηλός εκθέτης

Αν το ίδιο plaintext σταλεί σε πολλούς παραλήπτες με μικρό `e` (συχνά `e=3`) και χωρίς σωστό padding, μπορείτε να ανακτήσετε το `m` μέσω CRT και ακέραιας ρίζας.

Τεχνική συνθήκη:

Αν έχετε `e` ciphertext του ίδιου μηνύματος με moduli `n_i` ανά δύο πρώτους μεταξύ τους:

- Χρησιμοποιήστε CRT για να ανακτήσετε το `M = m^e` ως προς το γινόμενο `N = Π n_i`
- Αν `m^e < N`, τότε το `M` είναι η πραγματική ακέραια δύναμη και `m = integer_root(M, e)`

### Επίθεση Wiener: μικρός ιδιωτικός εκθέτης

Αν το `d` είναι υπερβολικά μικρό, τα συνεχή κλάσματα μπορούν να το ανακτήσουν από το `e/n`.

### Παγίδες του textbook RSA

Αν δείτε:

- Χωρίς OAEP/PSS, ακατέργαστη modular exponentiation
- Ντετερμινιστική κρυπτογράφηση

τότε οι αλγεβρικές επιθέσεις και η κατάχρηση oracle γίνονται πολύ πιθανότερες.

## Μοτίβα σχετικών μηνυμάτων

Αν δείτε δύο ciphertext με το ίδιο modulus και μηνύματα που σχετίζονται αλγεβρικά (π.χ. `m2 = a*m1 + b`), αναζητήστε επιθέσεις "related-message", όπως την Franklin–Reiter. Συνήθως απαιτούν:

- ίδιο modulus `n`
- ίδιο εκθέτη `e`
- γνωστή σχέση μεταξύ των plaintext

Στην πράξη, αυτό συχνά επιλύεται με Sage, ορίζοντας πολυώνυμα modulo `n` και υπολογίζοντας ένα GCD.

## Πλέγματα / Coppersmith

Χρησιμοποιήστε αυτή την προσέγγιση όταν έχετε μερικά bit, δομημένο plaintext ή στενές σχέσεις που καθιστούν το άγνωστο μικρό.

Οι μέθοδοι πλεγμάτων (LLL/Coppersmith) εμφανίζονται όταν έχετε μερική πληροφορία:

- Μερικώς γνωστό plaintext (δομημένο μήνυμα με άγνωστο τέλος)
- Μερικώς γνωστό `p`/`q` (έχουν διαρρεύσει τα υψηλά bit)
- Μικρές άγνωστες διαφορές μεταξύ σχετικών τιμών

### Τι να αναγνωρίζετε

Τυπικές ενδείξεις σε challenges:

- "Έχουμε διαρρεύσει τα υψηλά/χαμηλά bit του p"
- "Το flag είναι ενσωματωμένο ως εξής: `m = bytes_to_long(b\"HTB{\" + unknown + b\"}\")`"
- "Χρησιμοποιήσαμε RSA, αλλά με μικρό τυχαίο padding"
