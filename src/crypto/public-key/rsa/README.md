## Швидке сортування

Зберіть:

- `n`, `e`, `c` (і будь-які додаткові шифротексти)
- Будь-які зв’язки між повідомленнями (той самий відкритий текст? спільний модуль? структурований відкритий текст?)
- Будь-які leaks (часткові `p/q`, біти `d`, `dp/dq`, відоме доповнення)

Потім спробуйте:

- Перевірити факторизацію (Factordb / `sage: factor(n)` для відносно невеликих чисел)
- Шаблони для малих показників (`e=3`, broadcast)
- Спільний модуль / повторювані прості множники
- Методи ґраток (Coppersmith/LLL), коли щось майже відоме

## Поширені атаки RSA

### Common modulus

Якщо два шифротексти `c1, c2` шифрують **те саме повідомлення** з **тим самим модулем** `n`, але з різними показниками `e1, e2` (і `gcd(e1,e2)=1`), можна відновити `m` за допомогою розширеного алгоритму Евкліда:

`m = c1^a * c2^b mod n` де `a*e1 + b*e2 = 1`.

Приклад:

1. Обчисліть `(a, b) = xgcd(e1, e2)`, щоб отримати `a*e1 + b*e2 = 1`
2. Якщо `a < 0`, інтерпретуйте `c1^a` як `inv(c1)^{-a} mod n` (те саме для `b`)
3. Перемножте й обчисліть залишок за модулем `n`

### Спільні прості множники в модулях

Якщо маєте кілька модулів RSA з одного завдання, перевірте, чи мають вони спільний простий множник:

- `gcd(n1, n2) != 1` означає катастрофічний збій генерації ключів.

Таке часто трапляється в CTF із поясненнями на кшталт «ми швидко згенерували багато ключів» або «погана випадковість».

### Розріджені / short-sleeve модулі

Деякі зламані генератори великих цілих чисел безпосередньо вносять структуру в публічний модуль: кожна limb містить лише невелике випадкове підполе, а решта бітів дорівнює `0`. На практиці це проявляється як **регулярно розташовані блоки нулів** у `n`, часто вирівняні за 32-бітними або 128-бітними limb.<sup>[[1]](#references)</sup>

Швидкі перевірки:

- Виведіть `n` у шістнадцятковому форматі й пошукайте повторювані нульові ділянки з однаковим кроком.
- Розбийте `n` на limb (`2^32`, `2^64`, `2^128`) і перевірте, чи кожна з них незвично мала.
- Перевіряйте публічні SSH/TLS-ключі за допомогою інструментів на кшталт **badkeys**, якщо підозрюєте слабку генерацію host-ключів.<sup>[[2]](#references)</sup><sup>[[3]](#references)</sup>

Це серйозніше за статистичне зміщення: якщо обидва приватні множники `p` і `q` мають short-sleeve структуру, модуль може бути **легко факторизувати**.<sup>[[1]](#references)</sup>

### Поліноміальна факторизація структурованих ключів RSA

Для ймовірної ширини limb `w` запишіть модуль у системі числення з основою `B = 2^w`:

- `n = Σ_i n_i B^i`
- `f_n(x) = Σ_i n_i x^i`

Оскільки обчислення значень поліномів є мультиплікативним, `f_a(B) * f_c(B) = (f_a * f_c)(B)`. Якщо множники також мають розріджені коефіцієнти limb, тоді:

- `n = p*q`
- `f_n(x) = f_p(x) * f_q(x)`

Схема атаки:

1. Вгадайте ширину limb `w`.
2. Перетворіть публічний модуль `n` на `f_n(x)`, використовуючи основу `2^w`.
3. Розкладіть `f_n(x)` на множники над цілими числами.
4. Обчисліть значення кандидатів-множників при `B = 2^w`.
5. Перевірте, які кандидати при перемноженні дають `n`.

Це **не зламує звичайний RSA**. Метод працює лише тоді, коли самі прості множники мають дуже малі, сильно структуровані коефіцієнти limb.<sup>[[1]](#references)</sup>

### Зсунутий витік limb

Розріджені байти не завжди вирівняні за молодшим краєм кожної limb. Якщо пряме перетворення в систему з основою `2^w` дає великі коефіцієнти, пошукайте зсуви `i,j`, за яких `2^i p` і `2^j q` стають розрідженими в цій системі числення. Поліном добутку все одно можна отримати з публічного модуля, розкласти на множники й об’єднати назад у початкові цілі множники.<sup>[[1]](#references)</sup>

### Ознака проблеми реалізації: помилка byte-to-limb RNG

Небезпечний шаблон — обчислити кількість **32-бітних limb**, виділити лише стільки **байтів** і скопіювати їх у масив limb:

```csharp
int numLimbs = bits / 32;
byte[] array = new byte[numLimbs];
rngProvider.GetNonZeroBytes(array);
Array.Copy(array, 0, bignumLimbs, 0, numLimbs);
bignumLimbs[numLimbs - 1] |= 0x80000000;
```

Це дає кожному 32-бітному limb лише **8 біт ентропії**, а в останньому limb примусово встановлюється старший біт. Отримані прості числа RSA часто можна розпізнати й факторизувати, маючи лише відкритий ключ.<sup>[[1]](#references)</sup>

### Пов’язаний режим збою DSA

Якщо ту саму зламану процедуру роботи з великими цілими числами повторно використовувати для генерації приватного показника DSA, відкритий ключ `y = g^x` може розкривати **значно зменшений і структурований** простір пошуку для `x`. Щойно шаблон limb відомий, атаки на дискретний логарифм, як-от **baby-step giant-step**, можуть стати практичними для відкритих параметрів.<sup>[[1]](#references)</sup>

### Håstad broadcast / low exponent

Якщо те саме повідомлення надсилається кільком одержувачам із малим `e` (часто `e=3`) і без належного padding, можна відновити `m` за допомогою CRT та цілого кореня.

Технічна умова:

Якщо маєте `e` шифротекстів того самого повідомлення з попарно взаємно простими модулями `n_i`:

- Використайте CRT, щоб відновити `M = m^e` за модулем добутку `N = Π n_i`
- Якщо `m^e < N`, тоді `M` є справжнім цілим степенем, а `m = integer_root(M, e)`

### Wiener attack: малий приватний показник

Якщо `d` надто малий, його можна відновити за допомогою ланцюгових дробів із `e/n`.

### Підводні камені textbook RSA

Якщо бачите:

- Відсутність OAEP/PSS, звичайне модульне піднесення до степеня
- Детерміноване шифрування

то алгебраїчні атаки та зловживання oracle стають значно ймовірнішими.

## Шаблони пов’язаних повідомлень

Якщо бачите два шифротексти з однаковим модулем і алгебраїчно пов’язаними повідомленнями (наприклад, `m2 = a*m1 + b`), шукайте атаки на "related-message", як-от Franklin–Reiter. Зазвичай для них потрібні:

- однаковий модуль `n`
- однаковий показник `e`
- відомий зв’язок між відкритими текстами

На практиці це часто розв’язують у Sage: задають поліноми за модулем `n` і обчислюють НСД.

## Ґратки / Coppersmith

Застосовуйте цей підхід, коли маєте часткові біти, структурований відкритий текст або близькі співвідношення, через які невідоме значення є малим.

Ґраткові методи (LLL/Coppersmith) застосовують, коли є часткова інформація:

- Частково відомий відкритий текст (структуроване повідомлення з невідомим кінцем)
- Частково відомі `p`/`q` (витекли старші біти)
- Малі невідомі різниці між пов’язаними значеннями

### На що звернути увагу

Типові підказки в завданнях:

- "Ми злили старші/молодші біти p"
- "Прапорець вбудовано так: `m = bytes_to_long(b\"HTB{\" + unknown + b\"}\")`"
- "Ми використали RSA, але з малим випадковим padding"

### Інструменти

На практиці для LLL використовують Sage та готовий шаблон для конкретного випадку.
