## Швидке первинне оцінювання

Зберіть:

- `n`, `e`, `c` (і будь-які додаткові шифротексти)
- Будь-які зв'язки між повідомленнями (той самий plaintext? спільний modulus? структурований plaintext?)
- Будь-які leak (часткові `p/q`, біти `d`, `dp/dq`, відомий padding)

Потім спробуйте:

- Перевірку факторизації (Factordb / `sage: factor(n)` для відносно малих значень)
- Патерни малих експонент (`e=3`, broadcast)
- Спільний modulus / повторювані прості множники
- Lattice methods (Coppersmith/LLL), коли дещо майже відоме

## Поширені атаки RSA

### Common modulus

Якщо два шифротексти `c1, c2` шифрують **те саме повідомлення** за допомогою **того самого modulus** `n`, але з різними експонентами `e1, e2` (і `gcd(e1,e2)=1`), можна відновити `m` за допомогою розширеного алгоритму Евкліда:

`m = c1^a * c2^b mod n`, де `a*e1 + b*e2 = 1`.

Приблизний алгоритм:

1. Обчисліть `(a, b) = xgcd(e1, e2)`, щоб `a*e1 + b*e2 = 1`
2. Якщо `a < 0`, інтерпретуйте `c1^a` як `inv(c1)^{-a} mod n` (так само для `b`)
3. Перемножте та зведіть за модулем `n`

### Спільні прості множники між modulus

Якщо у вас є кілька RSA modulus з одного challenge, перевірте, чи не мають вони спільний простий множник:

- `gcd(n1, n2) != 1` означає катастрофічну помилку генерації ключів.

Це часто трапляється в CTF як наслідок того, що "ми швидко згенерували багато ключів" або "погана випадковість".

### Розріджені / short-sleeve modulus

Деякі зламані генератори великих цілих чисел безпосередньо залишають структуру у відкритому modulus: кожен limb містить лише невелике випадкове підполе, а решта бітів дорівнює `0`. На практиці це проявляється як **регулярно розташовані блоки нулів** у `n`, часто вирівняні за 32-бітними або 128-бітними limb.<sup>[[1]](#references)</sup>

Швидкі перевірки:

- Виведіть `n` у hex і шукайте повторювані нульові вікна з фіксованим кроком.
- Повторно розділіть `n` на limb (`2^32`, `2^64`, `2^128`) і перевірте, чи не є кожен limb аномально малим.
- Перевірте відкриті SSH/TLS-ключі за допомогою таких інструментів, як **badkeys**, якщо підозрюєте слабку генерацію host key.<sup>[[2]](#references)</sup><sup>[[3]](#references)</sup>

Це серйозніше за статистичне відхилення: якщо обидва приватні множники `p` і `q` є short-sleeve, modulus може стати **легким для факторизації**.<sup>[[1]](#references)</sup>

### Polynomial factorization of structured RSA keys

Для підозрюваної ширини limb `w` запишіть modulus у системі числення з основою `B = 2^w`:

- `n = Σ_i n_i B^i`
- `f_n(x) = Σ_i n_i x^i`

Оскільки обчислення є мультиплікативним, `f_a(B) * f_c(B) = (f_a * f_c)(B)`. Якщо множники також мають розріджені коефіцієнти limb, тоді:

- `n = p*q`
- `f_n(x) = f_p(x) * f_q(x)`

Приблизний алгоритм атаки:

1. Вгадайте ширину limb `w`.
2. Перетворіть відкритий modulus `n` на `f_n(x)`, використовуючи основу `2^w`.
3. Розкладіть `f_n(x)` на множники над цілими числами.
4. Обчисліть кандидатні множники при `B = 2^w`.
5. Перевірте, які кандидати при множенні дають `n`.

Це **не ламає звичайний RSA**. Метод працює лише тоді, коли самі прості множники мають дуже малі, сильно структуровані коефіцієнти limb.<sup>[[1]](#references)</sup>

### Shifted limb leakage

Розріджені байти не завжди вирівняні за молодшим краєм кожного limb. Якщо пряме перетворення за основою `2^w` дає великі коефіцієнти, шукайте зсуви `i,j`, за яких `2^i p` і `2^j q` стають розрідженими в цій системі limb. Поліном добутку все ще можна отримати з відкритого modulus, розкласти на множники та повторно об'єднати в початкові цілі множники.<sup>[[1]](#references)</sup>

### Ознака проблеми в реалізації: помилка RNG під час перетворення байтів у limb

Небезпечний шаблон полягає в обчисленні кількості **32-бітних limb**, виділенні лише такої кількості **байтів** і копіюванні їх у масив limb:
```csharp
int numLimbs = bits / 32;
byte[] array = new byte[numLimbs];
rngProvider.GetNonZeroBytes(array);
Array.Copy(array, 0, bignumLimbs, 0, numLimbs);
bignumLimbs[numLimbs - 1] |= 0x80000000;
```
Це дає кожному 32-бітному limb лише **8 біт ентропії** плюс примусово встановлений старший біт в останньому limb. Отримані RSA-прості числа часто можна розпізнати та факторизувати лише з відкритого ключа.<sup>[[1]](#references)</sup>

### Related DSA failure mode

Якщо ту саму зламану процедуру роботи з великими цілими числами повторно використовувати для генерації приватного експонента DSA, відкритий ключ `y = g^x` може розкрити **суттєво зменшений і структурований** простір пошуку для `x`. Коли шаблон limb відомий, атаки на discrete log, такі як **baby-step giant-step**, можуть стати практичними проти відкритих параметрів.<sup>[[1]](#references)</sup>

### Håstad broadcast / low exponent

Якщо той самий відкритий текст надсилається кільком одержувачам із малим `e` (часто `e=3`) і без належного padding, можна відновити `m` за допомогою CRT та integer root.

Технічна умова:

Якщо у вас є `e` ciphertexts одного повідомлення під pairwise-coprime модулями `n_i`:

- Використайте CRT, щоб відновити `M = m^e` за модулем добутку `N = Π n_i`
- Якщо `m^e < N`, тоді `M` є справжнім цілим степенем, а `m = integer_root(M, e)`

### Wiener attack: малий приватний експонент

Якщо `d` надто мале, continued fractions можуть відновити його з `e/n`.

### Підводні камені textbook RSA

Якщо ви бачите:

- Відсутність OAEP/PSS, raw modular exponentiation
- Deterministic encryption

тоді алгебраїчні атаки та зловживання oracle стають значно ймовірнішими.

- RsaCtfTool: https://github.com/Ganapati/RsaCtfTool

## Related-message patterns

Якщо ви бачите два ciphertexts під одним модулем із повідомленнями, які алгебраїчно пов’язані (наприклад, `m2 = a*m1 + b`), шукайте атаки "related-message", такі як Franklin–Reiter. Зазвичай для них потрібні:

- той самий модуль `n`
- той самий експонент `e`
- відомий зв’язок між відкритими текстами

На практиці це часто розв’язують у Sage: задають поліноми за модулем `n` і обчислюють GCD.

## Lattices / Coppersmith

Застосовуйте цей підхід, коли маєте часткові біти, структурований відкритий текст або близькі співвідношення, через які невідоме стає малим.

Методи lattice (LLL/Coppersmith) з’являються щоразу, коли у вас є часткова інформація:

- Частково відомий відкритий текст (структуроване повідомлення з невідомим хвостом)
- Частково відомі `p`/`q` (старші біти leaked)
- Малі невідомі відмінності між пов’язаними значеннями

### Що розпізнавати

Типові підказки у challenge:

- "We leaked the top/bottom bits of p"
- "The flag is embedded like: `m = bytes_to_long(b\"HTB{\" + unknown + b\"}\")`"
- "We used RSA but with a small random padding"

### Tooling

На практиці ви використовуватимете Sage для LLL і відомий template для конкретного instance.

Хороші відправні точки:

- Sage CTF crypto templates: https://github.com/defund/coppersmith
- A survey-style reference: https://martinralbrecht.wordpress.com/2013/05/06/coppersmiths-method/
