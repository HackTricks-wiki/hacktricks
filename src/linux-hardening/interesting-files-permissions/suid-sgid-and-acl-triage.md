# SUID, SGID, ACLs et fichiers sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID et SGID modifient l’identité effective d’un fichier exécuté ; les ACLs peuvent accorder des accès qui ne sont pas visibles dans les bits de mode affichés par `ls -l`. Vérifiez les deux lorsqu’un utilisateur peut lire, écrire ou exécuter des fichiers au-delà de ce que les permissions apparentes du propriétaire et du groupe semblent autoriser.

## Énumérer les exécutables privilégiés

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrez-vous sur les exécutables personnalisés ou récemment modifiés, les propriétaires inhabituels et les fichiers situés sur des montages accessibles en écriture. Un montage `nosuid` peut neutraliser le comportement set-ID ; les file capabilities constituent un mécanisme de privilèges distinct, décrit dans [les capacités Linux](linux-capabilities.md). Comparez un binaire suspect avec son package et vérifiez ce qu’il exécute, ouvre ou charge avec une identité élevée.

Pour un exécutable SUID appartenant à root et que vous ne connaissez pas, s’il accepte des entrées de l’appelant, examinez hors ligne une copie du binaire pour repérer une gestion des arguments non sûre pour la mémoire et le chemin de code qui y mène. Notez le comportement des ID effectifs et les protections telles que les canaris de pile, la mémoire non exécutable, le code indépendant de la position et la randomisation des adresses. Le nom d’une fonction non sûre ou l’absence d’une protection constitue uniquement une piste à examiner : l’exploitabilité dépend des limites réelles des entrées, du flux de contrôle atteignable et de l’identité effective au moment de la faute. N’envoyez pas de longs arguments à l’exécutable privilégié en production dans le seul but de provoquer un crash pendant une énumération passive.

Un programme SUID familier peut lui-même avoir été remplacé ou piégé. Une date de modification récente est une piste, pas une preuve : pour un **binaire de package suspect précis**, identifiez le package propriétaire et comparez le fichier installé aux métadonnées du package, au lieu de vérifier chaque package lors d’une énumération de routine :

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` vérifie le contenu des fichiers uniquement lorsque la base de données des paquets contient une somme de contrôle enregistrée ; RPM compare également les métadonnées, comme le mode et le propriétaire. Concentrez-vous sur une divergence touchant **l’exécutable privilégié lui-même** : les installations minimales peuvent signaler l’absence de documentation ou de fichiers de langue situés ailleurs dans le même paquet. Comparez l’exécutable suspect à un paquet fournisseur fiable et examinez précisément le code modifié. Les modifications locales légitimes, l’absence de sommes de contrôle et une base de données de paquets compromise limitent ce que ces commandes permettent de prouver. Dans le cadre d’un triage passif, n’exécutez ni le programme SUID suspect ni un script de vérification de paquets. Consultez le [manuel de vérification de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) et le [manuel de vérification de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programme SUID qui exécute un shell, une commande relative ou une bibliothèque située dans un chemin accessible en écriture peut franchir une limite de confiance. Consultez [Abus des bibliothèques partagées et de l’éditeur de liens SUID](suid-shared-library-and-linker-abuse.md), les [conseils sur PATH](../linux-basics/linux-environment-variables.md#path) et l’[explication des identifiants utilisateur](../user-information/euid-ruid-suid.md). Pour les contournements connus propres à une commande, consultez [GTFOBins](https://gtfobins.github.io/) en fonction du binaire exact et de l’invocation autorisée sur l’hôte.

Pour un exécutable set-user-ID, distinguez le **UID réel** de l’appelant du **UID effectif** du propriétaire du fichier : [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) laisse le UID réel inchangé et copie le UID effectif dans le saved UID après toute modification set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) exécute sa commande via `/bin/sh -c` ; le shell choisi par ce chemin détermine si un processus enfant conserve son identité effective. En particulier, les [règles du mode privilégié de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) réinitialisent un UID effectif différent au UID réel lorsque Bash démarre sans `-p`. Vérifiez les changements d’UID du programme auxiliaire réel et son invocation des processus enfants, ainsi que son propriétaire, les droits d’exécution, l’option de montage `nosuid` et l’état `no_new_privs` du processus. Un bit SUID ou un appel au shell ne suffit pas à établir qu’une transition vers des privilèges supérieurs est possible.

Un `jjs` inhabituel appartenant à root et doté du bit SUID justifie un examen distinct de l’accès aux fichiers si l’utilisateur actuel peut l’exécuter. L’outil Nashorn historique peut accéder aux API Java de fichiers même si un shell lancé en processus enfant abandonne son UID effectif ; confirmez le comportement de la JVM installée, l’identité effective utilisée pour l’opération sur le fichier et les paramètres `nosuid`/`no_new_privs` avant de le considérer comme un accès privilégié en lecture ou en écriture. [Oracle a supprimé `jjs` dans JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html) ; un chemin présent sur le système peut toujours correspondre à une ancienne version ou à une version empaquetée séparément. [GTFOBins documente les API de fichiers](https://gtfobins.org/gtfobins/jjs/), mais ses exemples avec sudo ne démontrent pas le comportement SUID de toutes les versions. N’invoquez pas l’outil pendant l’énumération passive.

Un exécutable `gosu` appartenant à root, doté du bit SUID et accessible à un utilisateur moins privilégié mérite examen : son interface documentée accepte un utilisateur cible et une commande, mais son usage normal en conteneur consiste à le lancer en tant que root pour abandonner les privilèges. Vérifiez le comportement SUID de la version installée, l’identité effective et le mappage de l’espace de noms utilisateur, ainsi que `nosuid` et `no_new_privs` ; root dans un conteneur n’implique pas root sur l’hôte. Un nom de fichier ou un bit SUID ne prouve pas à lui seul qu’une transition fonctionne. Consultez [l’utilisation en amont](https://github.com/tianon/gosu) et [l’avertissement SUID du responsable](https://github.com/tianon/gosu/issues/11). N’invoquez pas le programme auxiliaire pendant l’inventaire passif.

Un wrapper de sauvegarde personnalisé set-user-ID peut accepter un chemin choisi par l’appelant et l’interpoler dans une commande d’archivage transmise à `system(3)`. Si ce chemin n’est pas placé entre guillemets dans la commande construite, le shell enfant peut appliquer [l’expansion du tilde à l’aide de `HOME`, les motifs de chemin tels que `?` et `*`, et la séparation des commandes par une nouvelle ligne](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) ; rejeter uniquement les signes de ponctuation courants au moyen d’une liste de refus ne rend pas le chemin littéral. Confirmez le cheminement exact des arguments, l’environnement hérité, le shell enfant et son identité effective, l’accès au système de fichiers et la visibilité de la sortie de l’outil d’archivage pour l’appelant. Le bit SUID, une chaîne correspondant à un outil d’archivage ou le seul rejet du chemin littéral `/root` ne prouvent ni la divulgation ni l’exécution de code. Examinez hors ligne une copie du wrapper plutôt que d’archiver des fichiers privés ou d’envoyer des entrées provoquant un plantage pendant l’énumération passive.

La [substitution de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) du shell, telle que `$(...)`, constitue une autre faille possible dans une liste de refus de métacaractères : même un préfixe de commande fixe autorisé peut transmettre un argument contrôlé ensuite par l’appelant via `/bin/sh -c`. Vérifiez hors ligne les guillemets exacts, l’analyseur et l’identité effective ; une chaîne `system()` ou une liste de refus incomplète ne constitue pas, à elle seule, une preuve d’exécution.

L’**arbre des processus appelants** compte également. Un processus de travail Web peut installer un filtre seccomp qui restreint les appels système modifiant l’UID ; [les filtres seccomp sont transmis aux processus enfants et persistent après `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Par exemple, les directives [`LimitUIDRange` et `LimitGIDRange` de mpm-itk d’Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) peuvent limiter les identités accessibles aux descendants. `Seccomp: 2` dans `/proc/self/status` indique le mode de filtrage, pas la politique ni la capacité de ce programme auxiliaire particulier à obtenir l’identité de son propriétaire. Examinez ensemble l’ascendance de l’invocation réelle et son filtre effectif, ainsi que ses conditions SUID, de montage et `no_new_privs` ; une session de connexion distincte peut être soumise à une autre politique, mais nécessite son propre chemin d’accès valide.

Un exécutable SUID personnalisé peut invoquer un script Python distinct et lisible. S’il utilise effectivement **Python 2**, [`input()` évalue l’expression saisie](https://docs.python.org/2/library/functions.html#input) ; en Python 3, `input()` renvoie du texte. Vérifiez l’identité effective du wrapper, le chemin et la version de l’interpréteur, le chemin du script et si une entrée non fiable atteint cet appel avant de considérer la ligne source comme un chemin d’exécution. Le bit set-ID du script lui-même ou un appel à `input()` sans wrapper privilégié ne crée pas la même limite. Examinez les chemins référencés par le binaire et une portion limitée du code source du script sans l’exécuter pendant l’énumération.

Si un code source lisible accompagne un exécutable SUID inhabituel, comparez le nombre d’octets demandé pour chaque lecture de fichier contrôlée par l’appelant à la taille du tampon de destination, et examinez les vérifications ultérieures du flux de contrôle. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) stocke les éléments demandés à l’adresse fournie ; il ne connaît pas la capacité de l’objet de destination. Une différence de taille est un indice statique de problème de sécurité mémoire, pas la preuve d’une élévation de privilèges exploitable : confirmez que le code source correspond au binaire installé, que l’appelant peut fournir l’entrée, que l’exécution SUID est effective dans ce contexte et que le chemin concerné est accessible. Examinez hors ligne une copie limitée du code source ou du binaire plutôt que d’envoyer des entrées provoquant un plantage au programme privilégié pendant l’énumération.

Un programme auxiliaire SUID personnalisé peut divulguer un fichier protégé sans en afficher le contenu. Si l’appelant choisit à la fois un chemin et une expression régulière, et que le programme renvoie un nombre de correspondances visible avec son UID effectif, des tests de préfixe ancrés peuvent constituer un oracle caractère par caractère. Confirmez le propriétaire du programme auxiliaire, son comportement vis-à-vis de l’ID effectif, les droits d’exécution, les restrictions de chemin, la sémantique de l’expression régulière, la visibilité de la réponse et l’existence d’un fichier précis appartenant à un utilisateur plus privilégié que l’appelant ne peut pas lire autrement. Un bit SUID ou une chaîne de bibliothèque regex ne prouve rien de ce flux. Lors de l’énumération passive, consignez l’exécutable inhabituel et examinez hors ligne un désassemblage ou une copie limitée du code source ; ne testez pas des suppositions de façon répétée sur le programme auxiliaire en cours d’exécution et n’affichez pas les secrets récupérés.

Sous OpenBSD, un lecteur personnalisé set-user-ID qui accepte un chemin choisi par l’appelant peut exposer des fichiers sous `/var/backups` si son identité effective peut les lire et qu’il en renvoie le contenu à l’appelant. [Le `changelist(5)` d’OpenBSD](https://man.openbsd.org/changelist.5) décrit les copies `.current` et `.backup` des chemins configurés, mais les entrées préfixées par `+` stockent des sommes de contrôle SHA-256 plutôt que le contenu des fichiers ; le répertoire de sauvegarde devrait appartenir à root et être en mode `0700`. Une règle [`unveil` autorisant la lecture](https://man.openbsd.org/unveil.2) de `/var` peut permettre l’accès sous ce chemin, mais ne donne ni ne prouve à elle seule l’accès aux fichiers. Confirmez l’UID effectif réel, le droit d’exécution du programme pour l’utilisateur actuel, le chemin accepté, l’existence et le contenu des sauvegardes, ainsi que toute exigence d’authentification indépendante avant de conclure à une élévation de privilèges. L’énumération passive doit signaler le programme auxiliaire et les métadonnées du chemin, sans invoquer le lecteur ni afficher les données de sauvegarde.

Un programme SUID personnalisé qui vérifie un chemin choisi par l’appelant avec [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), puis ouvre le chemin plus tard, peut subir une condition de concurrence si un fichier ou un lien symbolique change dans un répertoire accessible en écriture à l’appelant. La vérification s’applique à l’objet antérieur, tandis qu’un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ultérieur peut en résoudre un autre. Confirmez que le programme auxiliaire est exécutable avec une identité effective élevée, qu’un chemin de code accessible lit le fichier choisi et que l’appelant peut remplacer le chemin entre la vérification et l’ouverture ; un bit SUID, un répertoire accessible en écriture ou une chaîne `stat` ne suffit à établir aucun de ces éléments. Un chemin de divulgation nécessite également une sortie visible ou une destination lisible par l’appelant. Examinez le binaire et les métadonnées du chemin hors ligne ; ne provoquez pas de condition de concurrence sur le programme auxiliaire en cours d’exécution pendant l’énumération passive.

Appliquez le même examen des dépendances aux wrappers SGID. Un wrapper qui exécute un shell ou un programme auxiliaire par chemin absolu peut tout de même être dangereux si un utilisateur moins privilégié peut remplacer ce fichier ; le code lancé peut hériter du groupe effectif du wrapper. Vérifiez le chemin exact invoqué, ses droits d’écriture (y compris les ACL), le groupe effectif du wrapper et s’il abandonne ses privilèges avant de lancer le processus enfant. Un interpréteur peut également abandonner les ID effectifs hérités ; distinguez donc un élément à examiner d’une transition démontrée. La présence d’un shell accessible en écriture ailleurs sur l’hôte ne prouve pas, à elle seule, qu’un wrapper privilégié l’appelle.

### Wrappers privilégiés qui transmettent du SQL à la CLI SQLite

Si un programme SUID personnalisé transmet du SQL contrôlé par l’utilisateur au **programme en ligne de commande `sqlite3`**, examinez la commande exacte et l’identité effective avant de considérer la requête comme étant en lecture seule. La fonction SQL `edit()` de la CLI invoque un éditeur (indiqué comme deuxième argument ou par `VISUAL`), et sa fonction SQL `load_extension()` peut charger une bibliothèque partagée lorsque le chargement d’extensions est activé. Il s’agit de chemins d’exécution de code potentiels avec l’identité du processus CLI, même si le wrapper fixe `PATH` ou utilise un chemin absolu vers `sqlite3`. Le SQL doit effectivement atteindre ces fonctions et la CLI doit conserver la fonctionnalité correspondante ; trouver simplement `sqlite3` dans un binaire ou sur l’hôte ne prouve pas une élévation de privilèges. La **bibliothèque** SQLite désactive le chargement d’extensions par défaut : distinguez-la de la CLI. Lorsqu’une application privilégiée doit traiter du SQL non fiable, le mode `--safe` de la CLI SQLite désactive `edit()`, `load_extension()` et d’autres fonctions ayant des effets de bord. Consultez la [documentation de la CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentation du mode sécurisé](https://www.sqlite.org/cli.html#the_safe_command_line_option) et la [documentation sur le chargement d’extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lecteurs de fichiers privilégiés qui transmettent les données à un client verbeux

Un wrapper SUID/SGID personnalisé peut vérifier l’accès à un chemin choisi par l’appelant, puis transmettre ce fichier à une autre commande. Examinez l’identité effective lors de la vérification d’accès et de l’ouverture ultérieure, résolvez tout composant `../` par rapport au véritable répertoire de base, et vérifiez comment le processus enfant traite les entrées non valides. Si un client de base de données lit un fichier privé comme du SQL et affiche les erreurs en mode verbeux, il peut en répercuter le contenu dans les erreurs, même si le SQL est invalide. Il s’agit d’une divulgation entre utilisateurs uniquement si le processus enfant peut lire un fichier que l’appelant ne peut pas lire, si l’appelant peut sélectionner ce fichier via le wrapper et si la sortie est visible ; la présence de `mysql` ou d’une chaîne correspondant à un autre client ne prouve aucune de ces conditions.

### Chemin de recherche de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) concernait certaines versions de Netdata `ndsudo`. Le programme auxiliaire SUID appartenant à root recherchait les commandes externes autorisées à l’aide d’un `PATH` fourni par l’appelant. N’examinez un programme auxiliaire installé, y compris s’il se trouve en dehors du `PATH` habituel de l’appelant, que si le compte actuel peut l’exécuter. Confirmez son propriétaire, son bit SUID, ses droits d’exécution (y compris les droits de groupe et les ACL), la version installée et l’état des correctifs du fournisseur, ainsi que le blocage éventuel du changement d’identité par `NoNewPrivs` ou un montage `nosuid`. Netdata répertorie les versions corrigées `v1.45.3` et `v1.45.0-169` ; les rétroportages des distributions doivent faire l’objet d’une vérification distincte. La version affichée dans un tableau de bord ou la simple présence de `ndsudo` ne constitue pas une preuve suffisante d’une élévation de privilèges accessible. Le problème de chemin nécessite également que le programme auxiliaire résolve une commande externe via un emplacement contrôlé par l’appelant.

### Limite de privilèges de Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) concernait la logique privilégiée `--join` de Firejail : une cible de join spécialement conçue pouvait amener le programme auxiliaire setuid-root à accepter un espace de noms de montage contrôlé par un attaquant et à copier un état de sécurité dangereux. Pour un triage passif, confirmez que **l’identité actuelle peut exécuter** un binaire Firejail appartenant à root et doté du bit setuid, que setuid est effectif sur son montage et dans le contexte de son processus, et que la version installée ne contient pas le correctif. Le projet a corrigé le problème dans la [version 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) ; les paquets des distributions peuvent [rétroporter le correctif](https://github.com/netblue30/firejail/issues/5191) tout en affichant une version plus ancienne. Ces prérequis désignent un élément à examiner, pas une opération join réussie ni l’obtention d’un shell root. Ne créez pas de faux bac à sable et n’invoquez pas `--join` pendant l’énumération.

### Permissions du fichier journal de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) concernait Screen 4.5.0 qui ouvrait avec des privilèges élevés un fichier journal choisi par l’appelant. Un binaire `screen` ou portant un suffixe de version dans l’inventaire SUID n’est qu’un indice à examiner : confirmez qu’il appartient à root, que son exécution SUID est effective pour l’utilisateur actuel, sa version installée et l’état des correctifs de la distribution, ainsi que le comportement concerné du fichier journal. [Debian a corrigé son paquet 4.5.0 par un rétroportage](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484) ; une chaîne de version ou un nom de fichier ne prouve donc pas, à lui seul, l’exposition. Ne créez pas de fichier journal comme sonde d’énumération courante.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) concernait le programme auxiliaire privilégié de verrouillage du courrier S-nail, lorsqu’un composant de chemin contrôlé par l’appelant pouvait traverser des répertoires et entraîner l’écriture dans un fichier arbitraire. Vérifiez si l’utilisateur actuel peut exécuter un programme auxiliaire setuid installé appartenant à root, si son identité setuid est effective selon la politique de montage et de processus, et quelle est la version exacte du paquet ainsi que le correctif du fournisseur. [L’avis de sécurité d’Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) répertorie un correctif rétroporté pour son paquet 16.04 ; une version d’apparence identique à la version amont ne permet donc pas de conclure. La présence du programme auxiliaire ne prouve pas que le chemin vulnérable est accessible ni qu’une écriture de fichier permet d’exécuter du code en tant que root ; examinez les métadonnées et l’état du paquet sans invoquer le programme ni tenter la condition de concurrence pendant l’énumération.

### Nettoyage de snap-confine et tmpfiles

CVE-2026-3888 est une condition de concurrence impliquant `snap-confine` privilégié et le nettoyage de `/tmp` par systemd-tmpfiles. Un examen passif peut vérifier si `snap-confine` est setuid ou possède des capacités de fichier, comparer le paquet `snapd` installé à la version corrigée pour cette **version d’Ubuntu**, et examiner la règle d’ancienneté effective de `/tmp` et le minuteur de nettoyage. La correspondance entre le paquet et la règle est un prérequis, pas la preuve que la condition de concurrence est accessible : l’état du minuteur à l’exécution, la disposition de snap, les rétroportages de paquets et les remplacements de règles comptent également. Les versions plus anciennes peuvent nécessiter une configuration non standard. Ne lancez pas de sonde de condition de concurrence lors de l’énumération courante. Consultez la [fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2026-3888) pour l’état des paquets selon la version et l’[avis de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) pour l’interaction entre les composants.

## Examiner les ACL et les chemins sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un répertoire parent accessible en écriture peut permettre le remplacement même si le fichier appartient à root. Une ACL peut accorder discrètement l’accès à un fichier de configuration sudoers, une unité de service, un script cron, un chemin de bibliothèque ou un fichier d’identifiants. Vérifiez l’ACL et le chemin complet. Si des écritures arbitraires de fichiers privilégiés sont possibles, consultez [Arbitrary File Write to Root](write-to-root.md) ; pour la configuration de l’éditeur de liens et les cas de préchargement, voir l’[exemple `ld.so`](ld.so.conf-example.md). Considérez les sauvegardes exposées, les fichiers `.env`, les configurations de base de données, les éléments SSH et l’historique comme des sources potentielles d’identifiants, l’accès étant régi par les permissions réelles de chaque fichier.
