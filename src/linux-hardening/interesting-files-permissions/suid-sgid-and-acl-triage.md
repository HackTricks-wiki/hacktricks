# SUID, SGID, ACLs και ευαίσθητα αρχεία

{{#include ../../banners/hacktricks-training.md}}

Τα SUID και SGID αλλάζουν την αποτελεσματική ταυτότητα ενός αρχείου κατά την εκτέλεσή του· τα ACLs μπορούν να εκχωρούν πρόσβαση που δεν εμφανίζεται στα συνηθισμένα δικαιώματα mode του `ls -l`. Ελέγξτε και τα δύο όταν ένας χρήστης μπορεί να διαβάσει, να γράψει ή να εκτελέσει κάτι πέρα από όσα υποδηλώνουν τα φαινομενικά δικαιώματα ιδιοκτήτη και ομάδας.

## Εντοπισμός εκτελέσιμων αρχείων με αυξημένα δικαιώματα

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Εστιάστε σε προσαρμοσμένα ή πρόσφατα τροποποιημένα εκτελέσιμα, ασυνήθιστους κατόχους και αρχεία σε εγγράψιμα mounts. Ένα mount `nosuid` μπορεί να καταστείλει τη συμπεριφορά set-ID· τα file capabilities είναι ξεχωριστός μηχανισμός προνομίων που περιγράφεται στο [Linux capabilities](linux-capabilities.md). Συγκρίνετε ένα ύποπτο binary με το πακέτο του και ελέγξτε τι εκτελεί, ανοίγει ή φορτώνει με αυξημένη ταυτότητα.

Για ένα άγνωστο SUID εκτελέσιμο που ανήκει στον root και δέχεται είσοδο από τον καλούντα, εξετάστε ένα αντίγραφο του binary εκτός σύνδεσης για μη ασφαλή διαχείριση ορισμάτων που μπορεί να προκαλέσει προβλήματα μνήμης και για τη διαδρομή κώδικα που οδηγεί σε αυτήν. Καταγράψτε τη συμπεριφορά effective-ID και τα mitigations, όπως stack canaries, μη εκτελέσιμη μνήμη, position-independent code και address randomization. Ένα μη ασφαλές όνομα συνάρτησης ή η απουσία κάποιου mitigation είναι μόνο αφορμή για περαιτέρω έλεγχο: η δυνατότητα εκμετάλλευσης εξαρτάται από τα πραγματικά όρια εισόδου, τη reachable ροή ελέγχου και την effective identity τη στιγμή του σφάλματος. Μη στέλνετε μεγάλα ορίσματα στο ενεργό προνομιούχο εκτελέσιμο απλώς για να ελέγξετε αν θα καταρρεύσει κατά την παθητική απαρίθμηση.

Ένα γνώριμο SUID πρόγραμμα μπορεί και το ίδιο να έχει αντικατασταθεί ή να έχει backdoor. Ένας πρόσφατος χρόνος τροποποίησης είναι αφορμή για έλεγχο, όχι απόδειξη: για ένα **συγκεκριμένο ύποπτο binary πακέτου**, εντοπίστε το πακέτο στο οποίο ανήκει και συγκρίνετε το εγκατεστημένο αρχείο με τα metadata του πακέτου, αντί να επαληθεύετε κάθε πακέτο κατά τη συνήθη απαρίθμηση:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

Το `dpkg --verify` ελέγχει τα περιεχόμενα αρχείων μόνο όταν η βάση δεδομένων του πακέτου έχει καταγεγραμμένο checksum· το RPM συγκρίνει επίσης metadata, όπως mode και ιδιοκτησία. Εστιάστε σε ασυμφωνία στο **ίδιο το εκτελέσιμο με αυξημένα δικαιώματα**: εγκαταστάσεις stripped μπορεί να αναφέρουν απόντα αρχεία τεκμηρίωσης ή locale σε άλλα σημεία του ίδιου πακέτου. Συγκρίνετε ένα ύποπτο εκτελέσιμο με ένα αξιόπιστο πακέτο του προμηθευτή και εξετάστε ακριβώς τον κώδικα που άλλαξε. Νόμιμες τοπικές αλλαγές, απόντα checksums και παραβιασμένα metadata πακέτων περιορίζουν το τι αποδεικνύει κάθε εντολή. Μην εκτελείτε ούτε το ύποπτο πρόγραμμα SUID ούτε script επαλήθευσης πακέτων στο πλαίσιο παθητικού triage. Δείτε το [εγχειρίδιο επαλήθευσης του dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) και το [εγχειρίδιο επαλήθευσης του RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Ένα πρόγραμμα SUID που καλεί shell, σχετική εντολή ή βιβλιοθήκη από διαδρομή με δικαίωμα εγγραφής μπορεί να διασχίσει όριο εμπιστοσύνης. Δείτε το [SUID shared-library και linker abuse](suid-shared-library-and-linker-abuse.md), τις [οδηγίες για το PATH](../linux-basics/linux-environment-variables.md#path) και την [εξήγηση των user ID](../user-information/euid-ruid-suid.md). Για γνωστά command-specific escapes, ελέγξτε το [GTFOBins](https://gtfobins.github.io/) για το ακριβές binary και την invocation που επιτρέπεται στο host.

Για ένα εκτελέσιμο set-user-ID, διακρίνετε το **real UID** του καλούντος από το **effective UID** του ιδιοκτήτη του αρχείου: το [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) αφήνει το real UID αμετάβλητο και αντιγράφει το effective UID στο saved UID μετά από οποιαδήποτε αλλαγή set-ID. Το [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) εκτελεί την εντολή μέσω `/bin/sh -c`· το shell που επιλέγεται από αυτή τη διαδρομή επηρεάζει το αν μια child process διατηρεί την effective identity της. Ειδικότερα, οι [κανόνες privileged mode του Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) επαναφέρουν ένα διαφορετικό effective UID στο real UID όταν το Bash ξεκινά χωρίς `-p`. Ελέγξτε τις αλλαγές UID του πραγματικού helper και την invocation της child process, καθώς και τον ιδιοκτήτη του, την πρόσβαση εκτέλεσης, τη ρύθμιση mount `nosuid` και την κατάσταση `no_new_privs` της διεργασίας. Ένα SUID bit ή μια κλήση shell από μόνα τους δεν αποδεικνύουν ότι είναι εφικτή μια μετάβαση σε υψηλότερα δικαιώματα.

Ένα ασυνήθιστο SUID `jjs` που ανήκει στον root αξίζει ξεχωριστό έλεγχο πρόσβασης αρχείων, αν ο τρέχων χρήστης μπορεί να το εκτελέσει. Το legacy εργαλείο Nashorn μπορεί να προσπελάσει Java file APIs ακόμη και όταν ένα shell που ξεκινά απορρίπτει ένα effective UID· επιβεβαιώστε τη συμπεριφορά της εγκατεστημένης JVM, την effective identity της λειτουργίας αρχείου και τα `nosuid`/`no_new_privs` πριν το θεωρήσετε προνομιακή ανάγνωση ή εγγραφή. Η [Oracle αφαίρεσε το `jjs` στο JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)· μια εγκατεστημένη διαδρομή μπορεί να αντιστοιχεί σε παλαιότερο ή ξεχωριστά πακεταρισμένο build. Το [GTFOBins τεκμηριώνει τα file APIs](https://gtfobins.org/gtfobins/jjs/), αλλά τα παραδείγματά του με sudo δεν τεκμηριώνουν συμπεριφορά SUID για κάθε build. Μην εκτελέσετε το εργαλείο κατά την παθητική απαρίθμηση.

Ένα SUID εκτελέσιμο `gosu` που ανήκει στον root και είναι προσβάσιμο από χρήστη με λιγότερα δικαιώματα χρειάζεται έλεγχο: η τεκμηριωμένη διεπαφή του δέχεται χρήστη-στόχο και εντολή, αλλά η συνήθης χρήση σε container το εκκινεί ως root για να απορρίψει δικαιώματα. Επαληθεύστε τη συμπεριφορά SUID του εγκατεστημένου build, την effective identity και το user-namespace mapping, καθώς και τα `nosuid` και `no_new_privs`· το root σε container δεν συνεπάγεται root στο host. Ένα όνομα αρχείου ή ένα SUID bit από μόνο του δεν αποδεικνύει λειτουργική μετάβαση δικαιωμάτων. Δείτε το [upstream usage](https://github.com/tianon/gosu) και την [προειδοποίηση SUID του maintainer](https://github.com/tianon/gosu/issues/11). Μην εκτελέσετε το helper κατά την παθητική απογραφή.

Ένα προσαρμοσμένο set-user-ID backup wrapper μπορεί να δέχεται διαδρομή που επιλέγει ο καλών και να την παρεμβάλλει σε εντολή αρχειοθέτησης που περνά στο `system(3)`. Αν η διαδρομή δεν είναι σε εισαγωγικά στην κατασκευασμένη εντολή, το child shell μπορεί να εφαρμόσει [tilde expansion με χρήση του `HOME`, pathname patterns όπως `?` και `*`, και διαχωρισμό εντολών με newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)· η απόρριψη μόνο γνωστών σημείων στίξης μέσω denylist δεν καθιστά τη διαδρομή literal. Επιβεβαιώστε την ακριβή ροή ορισμάτων, το κληρονομημένο environment, το child shell και την effective identity, την πρόσβαση στο filesystem και το αν η έξοδος του εργαλείου αρχειοθέτησης είναι ορατή στον καλούντα. Το SUID bit, μια συμβολοσειρά ονόματος εργαλείου αρχειοθέτησης ή μόνο η απόρριψη της literal διαδρομής `/root` δεν αποδεικνύουν ούτε αποκάλυψη δεδομένων ούτε εκτέλεση κώδικα. Εξετάστε ένα αντίγραφο του wrapper offline αντί να αρχειοθετήσετε ιδιωτικά αρχεία ή να στείλετε εισόδους που προκαλούν crash κατά την παθητική απαρίθμηση.

Η [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) του shell, όπως `$(...)`, είναι ένα ακόμη πιθανό κενό σε denylist metacharacters: ακόμη και ένα σταθερό επιτρεπόμενο πρόθεμα εντολής μπορεί να περάσει ένα μεταγενέστερο όρισμα που ελέγχει ο καλών μέσω `/bin/sh -c`. Επαληθεύστε offline το ακριβές quoting, τον parser και την effective identity· μην θεωρείτε μια συμβολοσειρά `system()` ή μια ελλιπή denylist απόδειξη εκτέλεσης.

Σημασία έχει επίσης το **δέντρο διεργασιών του καλούντος**. Ένας web worker μπορεί να εγκαταστήσει seccomp filter που περιορίζει system calls αλλαγής UID· τα [seccomp filters κληρονομούνται από child processes και διατηρούνται μετά από `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Για παράδειγμα, οι οδηγίες [mpm-itk `LimitUIDRange` και `LimitGIDRange` του Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) μπορούν να περιορίσουν τις identities που είναι προσβάσιμες σε descendants. Το `Seccomp: 2` στο `/proc/self/status` δείχνει τη λειτουργία του filter, όχι την πολιτική του ούτε το αν αυτό το συγκεκριμένο helper μπορεί να αποκτήσει την identity του ιδιοκτήτη του. Εξετάστε μαζί την ancestry της πραγματικής invocation και το effective filter, καθώς και τις συνθήκες SUID, mount και `no_new_privs`· μια ξεχωριστή login session μπορεί να έχει διαφορετική πολιτική, αλλά απαιτεί τη δική της έγκυρη διαδρομή πρόσβασης.

Ένα προσαρμοσμένο SUID εκτελέσιμο μπορεί να καλεί ξεχωριστό, αναγνώσιμο Python script. Αν πράγματι χρησιμοποιεί **Python 2**, το [`input()` αξιολογεί την έκφραση που εισάγεται](https://docs.python.org/2/library/functions.html#input)· το `input()` της Python 3 επιστρέφει κείμενο. Επιβεβαιώστε την effective identity του wrapper, τη διαδρομή και την έκδοση του interpreter, τη διαδρομή του script και το αν μη έμπιστη είσοδος φτάνει σε αυτή την κλήση πριν θεωρήσετε τη γραμμή του source διαδρομή εκτέλεσης. Ένα set-ID bit μόνο στο script ή μια κλήση `input()` χωρίς τον προνομιακό wrapper δεν θεμελιώνει το ίδιο όριο. Εξετάστε τις διαδρομές που αναφέρει το binary και ένα περιορισμένο αντίγραφο του script χωρίς να το εκτελέσετε κατά την απαρίθμηση.

Αν υπάρχει αναγνώσιμο source μαζί με ένα ασυνήθιστο SUID εκτελέσιμο, συγκρίνετε τον αριθμό byte που ζητά κάθε ανάγνωση αρχείου ελεγχόμενη από τον καλούντα με το μέγεθος του buffer προορισμού και εξετάστε τους ελέγχους ελέγχου ροής που ακολουθούν. Το [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) αποθηκεύει τα ζητούμενα items στον παρεχόμενο pointer· δεν γνωρίζει τη χωρητικότητα του αντικειμένου προορισμού. Μια ασυμφωνία μεγέθους είναι ένδειξη για στατικό έλεγχο ασφάλειας μνήμης, όχι απόδειξη αξιοποιήσιμης κλιμάκωσης δικαιωμάτων: επιβεβαιώστε ότι το source αντιστοιχεί στο εγκατεστημένο binary, ότι ο καλών μπορεί να δώσει την είσοδο, ότι η εκτέλεση SUID είναι ενεργή σε αυτό το πλαίσιο και ότι η σχετική διαδρομή είναι προσβάσιμη. Εξετάστε offline ένα περιορισμένο αντίγραφο του source ή του binary αντί να στείλετε εισόδους που προκαλούν crash στο προνομιακό πρόγραμμα κατά την απαρίθμηση.

Ένα προσαρμοσμένο SUID helper μπορεί να αποκαλύψει ένα προστατευμένο αρχείο χωρίς να εκτυπώσει τα περιεχόμενά του. Αν ο καλών επιλέγει τόσο pathname όσο και regular expression, και το helper επιστρέφει ορατό αριθμό αντιστοιχιών χρησιμοποιώντας το effective UID του, δοκιμές με anchored prefixes μπορεί να σχηματίσουν oracle χαρακτήρα προς χαρακτήρα. Επιβεβαιώστε τον ιδιοκτήτη του helper, τη συμπεριφορά του effective ID, την πρόσβαση εκτέλεσης, τους περιορισμούς pathname, τη σημασιολογία regex, την ορατότητα της απόκρισης και ένα συγκεκριμένο αρχείο με υψηλότερα δικαιώματα που ο καλών δεν μπορεί διαφορετικά να διαβάσει. Ένα SUID bit ή μια συμβολοσειρά βιβλιοθήκης regex από μόνα τους δεν αποδεικνύουν αυτή τη ροή. Κατά την παθητική απαρίθμηση, καταγράψτε το ασυνήθιστο εκτελέσιμο και εξετάστε ένα περιορισμένο disassembly ή αντίγραφο του source· μην εκτελείτε επαναληπτικές δοκιμές στο ενεργό helper και μην εκτυπώνετε ανακτημένα μυστικά.

Στο OpenBSD, ένας προσαρμοσμένος set-user-ID reader που δέχεται pathname επιλεγμένο από τον καλούντα μπορεί να εκθέσει αρχεία κάτω από το `/var/backups`, αν η effective identity του μπορεί να τα διαβάσει και επιστρέφει το περιεχόμενό τους στον καλούντα. Το [OpenBSD `changelist(5)`](https://man.openbsd.org/changelist.5) περιγράφει αντίγραφα `.current` και `.backup` των διαμορφωμένων paths, αλλά οι καταχωρίσεις με πρόθεμα `+` αποθηκεύουν checksums SHA-256 αντί για περιεχόμενα αρχείων· ο κατάλογος backup θα πρέπει να ανήκει στον root και να έχει mode `0700`. Ένας κανόνας [`unveil` για ανάγνωση](https://man.openbsd.org/unveil.2) του helper για το `/var` μπορεί να επιτρέψει πρόσβαση κάτω από αυτή τη διαδρομή, αλλά από μόνος του δεν παραχωρεί ούτε αποδεικνύει πρόσβαση σε αρχεία. Επιβεβαιώστε το πραγματικό effective UID, το δικαίωμα εκτέλεσης για τον τρέχοντα χρήστη, το αποδεκτό path, την ύπαρξη και τα περιεχόμενα του backup, καθώς και τυχόν ανεξάρτητες απαιτήσεις authentication πριν ισχυριστείτε κλιμάκωση δικαιωμάτων. Η παθητική απαρίθμηση πρέπει να αναφέρει το helper και τα metadata της διαδρομής, όχι να εκτελεί τον reader ή να εκτυπώνει δεδομένα backup.

Ένα προσαρμοσμένο SUID πρόγραμμα που ελέγχει pathname επιλεγμένο από τον καλούντα με [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) και ανοίγει αργότερα το pathname μπορεί να υποστεί race αν αλλάξει ένα αρχείο ή symlink σε κατάλογο όπου ο καλών έχει δικαίωμα εγγραφής. Ο έλεγχος αφορά το προηγούμενο αντικείμενο, ενώ ένα μεταγενέστερο [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) μπορεί να επιλύσει διαφορετικό αντικείμενο. Επιβεβαιώστε ότι το helper μπορεί να εκτελεστεί με αυξημένη effective identity, ότι μια κατά τα άλλα προσβάσιμη διαδρομή κώδικα διαβάζει το επιλεγμένο αρχείο και ότι ο καλών μπορεί να αντικαταστήσει το pathname μεταξύ ελέγχου και ανοίγματος· ένα SUID bit, ένας εγγράψιμος κατάλογος ή μια συμβολοσειρά `stat` από μόνα τους δεν αποδεικνύουν τίποτε από αυτά. Για διαδρομή αποκάλυψης απαιτείται επίσης ορατή έξοδος ή προορισμός αναγνώσιμος από τον καλούντα. Εξετάστε offline το binary και τα metadata της διαδρομής· μην επιχειρήσετε race στο ενεργό helper κατά την παθητική απαρίθμηση.

Εφαρμόστε τον ίδιο έλεγχο εξαρτήσεων και σε SGID wrappers. Ένα wrapper που εκτελεί shell ή helper μέσω απόλυτης διαδρομής μπορεί να είναι μη ασφαλές αν χρήστης με λιγότερα δικαιώματα μπορεί να αντικαταστήσει αυτό το αρχείο· ο κώδικας που εκκινείται μπορεί να κληρονομήσει το effective group του wrapper. Ελέγξτε την ακριβή διαδρομή που καλείται, το δικαίωμα εγγραφής σε αυτήν (μαζί με τα ACLs), το effective group του wrapper και αν απορρίπτει δικαιώματα πριν εκκινήσει το child. Ένας interpreter μπορεί επίσης να απορρίψει inherited effective IDs, οπότε διακρίνετε ένα υποψήφιο προς έλεγχο από μια αποδεδειγμένη μετάβαση. Ένα εγγράψιμο shell σε άλλο σημείο του host από μόνο του δεν αποδεικνύει ότι το καλεί ένα προνομιακό wrapper.

### Προνομιακά wrappers που περνούν SQL στο SQLite CLI

Αν ένα προσαρμοσμένο SUID πρόγραμμα περνά SQL ελεγχόμενο από τον χρήστη στο **πρόγραμμα γραμμής εντολών `sqlite3`**, εξετάστε την ακριβή εντολή και την effective identity πριν θεωρήσετε το query μόνο για ανάγνωση. Η SQL function `edit()` του CLI εκκινεί έναν editor (από το δεύτερο όρισμά της ή το `VISUAL`), ενώ η SQL function `load_extension()` μπορεί να φορτώσει shared library όταν είναι ενεργοποιημένη η φόρτωση extensions. Αυτές είναι πιθανές διαδρομές εκτέλεσης κώδικα με την identity της CLI process, ακόμη κι αν το wrapper ορίζει σταθερό `PATH` ή χρησιμοποιεί απόλυτη διαδρομή `sqlite3`. Η SQL πρέπει πράγματι να φτάνει σε αυτές τις functions και η CLI πρέπει να διατηρεί τη σχετική δυνατότητα· το να βρεθεί απλώς το `sqlite3` σε binary ή στο host δεν αποτελεί ένδειξη κλιμάκωσης δικαιωμάτων. Η **library** του SQLite απενεργοποιεί από προεπιλογή τη φόρτωση extensions, οπότε διακρίνετέ την από το CLI. Όταν μια προνομιακή εφαρμογή πρέπει να επεξεργάζεται μη έμπιστη SQL, η λειτουργία `--safe` του SQLite CLI απενεργοποιεί την `edit()`, τη `load_extension()` και άλλες functions με παρενέργειες. Δείτε την [τεκμηρίωση του SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), την [τεκμηρίωση safe mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) και την [τεκμηρίωση φόρτωσης extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Προνομιακοί file readers που τροφοδοτούν verbose client

Ένα προσαρμοσμένο SUID/SGID wrapper μπορεί να ελέγχει την πρόσβαση σε pathname που επιλέγει ο καλών και έπειτα να περνά αυτό το αρχείο σε άλλη εντολή. Εξετάστε την effective identity τόσο στον έλεγχο πρόσβασης όσο και στο μεταγενέστερο άνοιγμα, επιλύστε τυχόν components `../` σε σχέση με τον πραγματικό βασικό κατάλογο και ελέγξτε πώς χειρίζεται το child την άκυρη είσοδο. Αν ένας database client διαβάζει ένα ιδιωτικό αρχείο ως SQL με verbose output, μπορεί να επαναλάβει τα περιεχόμενα του αρχείου στα errors ακόμη κι αν η SQL είναι άκυρη. Πρόκειται για αποκάλυψη μεταξύ χρηστών μόνο όταν το child μπορεί να διαβάσει αρχείο που δεν μπορεί να διαβάσει ο καλών, ο καλών μπορεί να επιλέξει αυτό το αρχείο μέσω του wrapper και η έξοδος είναι ορατή· η παρουσία του `mysql` ή συμβολοσειράς κάποιου άλλου client από μόνη της δεν αποδεικνύει καμία από αυτές τις συνθήκες.

### Διαδρομή αναζήτησης του Netdata `ndsudo`

Το [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) επηρέασε ορισμένα builds του Netdata `ndsudo`. Το SUID helper που ανήκει στον root αναζητούσε τις επιτρεπόμενες εξωτερικές εντολές του χρησιμοποιώντας `PATH` που παρείχε ο καλών. Εξετάστε ένα εγκατεστημένο helper, ακόμη κι αν βρίσκεται έξω από το συνηθισμένο `PATH` του καλούντος, μόνο όταν ο τρέχων λογαριασμός μπορεί να το εκτελέσει. Επιβεβαιώστε τον ιδιοκτήτη του, το SUID bit, την πρόσβαση εκτέλεσης (μαζί με grants ομάδων/ACL), το εγκατεστημένο build και την κατάσταση των patches του προμηθευτή, καθώς και το αν τα `NoNewPrivs` ή ένα mount `nosuid` εμποδίζουν την αλλαγή identity. Το Netdata αναφέρει τα patched builds `v1.45.3` και `v1.45.0-169`· τα backports διανομών χρειάζονται ξεχωριστή επιβεβαίωση. Μια έκδοση dashboard ή η απλή παρουσία του `ndsudo` δεν αρκεί ως ένδειξη προσβάσιμης κλιμάκωσης δικαιωμάτων. Το ζήτημα της διαδρομής απαιτεί επίσης το helper να επιλύει εξωτερική εντολή μέσω τοποθεσίας που ελέγχει ο καλών.

### Όριο δικαιωμάτων του Firejail join

Το [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) επηρέασε την προνομιακή λογική `--join` του Firejail: ένας κατασκευασμένος join target μπορούσε να κάνει το helper setuid-root να δεχτεί ένα mount namespace ελεγχόμενο από τον attacker και να αντιγράψει μη ασφαλή security state. Για παθητικό triage, επιβεβαιώστε ότι η **τρέχουσα identity μπορεί να εκτελέσει** ένα root-owned setuid binary του Firejail, ότι το setuid είναι ενεργό στο mount του και στο context της διεργασίας του, και ότι το εγκατεστημένο build δεν περιλαμβάνει τη διόρθωση. Το upstream διόρθωσε το ζήτημα στην [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70)· τα πακέτα διανομών μπορεί να το έχουν [ενσωματώσει ως backport](https://github.com/netblue30/firejail/issues/5191), ενώ εξακολουθούν να εμφανίζουν παλαιότερη έκδοση. Αυτές οι προϋποθέσεις εντοπίζουν κάτι που χρειάζεται έλεγχο, όχι επιτυχημένο join ή root shell. Μην κατασκευάσετε fake jail και μην εκτελέσετε `--join` κατά την απαρίθμηση.

### Δικαιώματα logfile του GNU Screen

Το [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) αφορούσε το Screen 4.5.0 που άνοιγε logfile επιλεγμένο από τον καλούντα με αυξημένα δικαιώματα. Ένα binary `screen` ή με κατάληξη έκδοσης στην απογραφή SUID αποτελεί μόνο ένδειξη για έλεγχο: επιβεβαιώστε την ιδιοκτησία root, την πραγματική εκτέλεση SUID για τον τρέχοντα χρήστη, το εγκατεστημένο build και την κατάσταση των patches της διανομής, καθώς και την επηρεαζόμενη συμπεριφορά logfile. Το [Debian διόρθωσε το πακέτο 4.5.0 με backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), επομένως μια συμβολοσειρά έκδοσης ή ένα όνομα αρχείου από μόνα τους δεν αποδεικνύουν έκθεση. Μην δημιουργείτε logfile ως συνήθη δοκιμή κατά την απαρίθμηση.

Το [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) επηρέασε το προνομιακό helper mail-lock του S-nail, όταν ένα component διαδρομής ελεγχόμενο από τον καλούντα μπορούσε να διασχίσει καταλόγους και να οδηγήσει σε αυθαίρετη εγγραφή αρχείου. Ελέγξτε αν ο τρέχων χρήστης μπορεί να εκτελέσει εγκατεστημένο setuid helper που ανήκει στον root, αν η setuid identity του είναι ενεργή βάσει της πολιτικής mount και διεργασίας και ποιο είναι το ακριβές build του πακέτου και η διόρθωση του προμηθευτή. Η [ανακοίνωση ασφαλείας του Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) αναφέρει backported διόρθωση για το πακέτο 16.04, επομένως μια έκδοση που μοιάζει με upstream δεν αρκεί για συμπέρασμα. Η παρουσία του helper δεν αποδεικνύει ότι είναι προσβάσιμη η επηρεαζόμενη διαδρομή ή ότι μια εγγραφή αρχείου οδηγεί σε εκτέλεση ως root· εξετάστε τα metadata και την κατάσταση του πακέτου χωρίς να εκτελέσετε το helper ή να επιχειρήσετε το race κατά την απαρίθμηση.

### Εκκαθάριση snap-confine και tmpfiles

Το CVE-2026-3888 είναι race που αφορά το προνομιακό `snap-confine` και την εκκαθάριση του `/tmp` από το systemd-tmpfiles. Ένας παθητικός έλεγχος μπορεί να εξετάσει αν το `snap-confine` είναι setuid ή έχει file capabilities, να συγκρίνει το εγκατεστημένο πακέτο `snapd` με τη διορθωμένη έκδοση για τη συγκεκριμένη **έκδοση Ubuntu** και να επιθεωρήσει τον ενεργό κανόνα ηλικίας για το `/tmp` και το cleanup timer. Ένα πακέτο και ένας κανόνας που ταιριάζουν είναι προϋποθέσεις, όχι απόδειξη ότι το race είναι προσβάσιμο: έχουν σημασία και η κατάσταση του timer κατά την εκτέλεση, η διάταξη των snap, τα package backports και οι παρακάμψεις κανόνων. Οι παλαιότερες εκδόσεις ενδέχεται να απαιτούν μη προεπιλεγμένη ρύθμιση. Μην εκτελέσετε race probe στο πλαίσιο συνήθους απαρίθμησης. Δείτε την [καταχώριση CVE του Ubuntu](https://ubuntu.com/security/CVE-2026-3888) για την κατάσταση πακέτων ανά έκδοση και το [advisory της Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) για την αλληλεπίδραση των components.

## Επιθεώρηση ACLs και ευαίσθητων διαδρομών

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ένας εγγράψιμος γονικός κατάλογος μπορεί να επιτρέπει την αντικατάσταση, ακόμη κι αν το ίδιο το αρχείο ανήκει στον root. Μια ACL μπορεί να παρέχει αθόρυβα πρόσβαση σε ένα αρχείο drop-in του sudoers, μια μονάδα υπηρεσίας, ένα script cron, μια διαδρομή βιβλιοθηκών ή ένα αρχείο διαπιστευτηρίων. Ελέγξτε τόσο την ACL όσο και ολόκληρη τη διαδρομή. Αν είναι δυνατή η εγγραφή αυθαίρετων αρχείων με προνόμια, ανατρέξτε στο [Arbitrary File Write to Root](write-to-root.md)· για περιπτώσεις ρύθμισης του linker και preload, δείτε το παράδειγμα [`ld.so`](ld.so.conf-example.md). Αντιμετωπίστε τα εκτεθειμένα αντίγραφα ασφαλείας, αρχεία `.env`, ρυθμίσεις βάσεων δεδομένων, υλικό SSH και ιστορικό ως πιθανές πηγές διαπιστευτηρίων, έχοντας υπόψη ότι η πρόσβαση καθορίζεται από τα πραγματικά δικαιώματα κάθε αρχείου.
