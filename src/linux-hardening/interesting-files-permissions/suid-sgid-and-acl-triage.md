# SUID, SGID, ACLs et fichiers sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID et SGID modifient l’identité effective d’un fichier exécuté ; les ACL peuvent accorder des accès que les bits de mode affichés par `ls -l` ne révèlent pas. Vérifiez les deux lorsqu’un utilisateur peut lire, écrire ou exécuter un fichier au-delà de ce que semblent permettre les autorisations du propriétaire et du groupe.

## Énumérer les exécutables privilégiés

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrez-vous sur les exécutables personnalisés ou récemment modifiés, les propriétaires inhabituels et les fichiers sur des montages accessibles en écriture. Un montage `nosuid` peut neutraliser le comportement set-ID ; les capacités de fichier constituent un mécanisme de privilège distinct, décrit dans [Linux capabilities](linux-capabilities.md). Comparez un binaire suspect à son paquet et vérifiez ce qu’il exécute, ouvre ou charge avec une identité élevée.

Pour un exécutable SUID appartenant à root que vous ne connaissez pas et qui accepte une entrée de l’appelant, examinez une copie du binaire hors ligne pour repérer une gestion des arguments non sécurisée vis-à-vis de la mémoire et le chemin de code qui y mène. Notez le comportement des identifiants effectifs et les mesures d’atténuation, telles que les canaris de pile, la mémoire non exécutable, le code indépendant de la position et la randomisation des adresses. Le nom d’une fonction non sécurisée ou l’absence d’une mesure d’atténuation constitue seulement une piste à examiner : l’exploitabilité dépend des limites réelles des entrées, du flux de contrôle atteignable et de l’identité effective au moment de la défaillance. N’envoyez pas de longs arguments à l’exécutable privilégié en production dans le seul but de provoquer un crash pendant une énumération passive.

Un programme SUID connu peut lui-même avoir été remplacé ou compromis. Une date de modification récente constitue une piste, pas une preuve : pour un **binaire empaqueté suspect en particulier**, identifiez le paquet auquel il appartient et comparez le fichier installé aux métadonnées du paquet, au lieu de vérifier chaque paquet lors d’une énumération de routine :

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` vérifie le contenu des fichiers uniquement lorsque la base de données des paquets contient une somme de contrôle enregistrée ; RPM compare aussi des métadonnées telles que le mode et le propriétaire. Concentrez-vous sur une divergence concernant **l’exécutable privilégié lui-même** : les installations minimales peuvent signaler l’absence de documentation ou de fichiers de langue situés ailleurs dans le même paquet. Comparez l’exécutable suspect à un paquet éditeur fiable et examinez précisément le code modifié. Les modifications locales légitimes, l’absence de sommes de contrôle et une métadonnée de paquet compromise limitent la portée des preuves fournies par ces deux commandes. Dans le cadre d’un triage passif, n’exécutez ni le programme SUID suspect ni un script de vérification de paquet. Consultez le [manuel de vérification de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) et le [manuel de vérification de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programme SUID qui invoque un shell, une commande relative ou une bibliothèque depuis un chemin modifiable peut franchir une frontière de confiance. Consultez [l’abus des bibliothèques partagées et de l’éditeur de liens SUID](suid-shared-library-and-linker-abuse.md), les [recommandations sur PATH](../linux-basics/linux-environment-variables.md#path) et [l’explication des ID utilisateur](../user-information/euid-ruid-suid.md). Pour connaître les échappatoires propres à certaines commandes, vérifiez dans [GTFOBins](https://gtfobins.github.io/) le binaire exact et l’invocation autorisée sur l’hôte.

Pour un exécutable set-user-ID, distinguez l’**UID réel** de l’appelant de l’**UID effectif** du propriétaire du fichier : [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) ne modifie pas l’UID réel et copie l’UID effectif dans l’UID sauvegardé après tout changement lié au bit set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) exécute sa commande via `/bin/sh -c` ; le shell désigné par ce chemin détermine si un processus enfant conserve son identité effective. En particulier, les [règles du mode privilégié de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) réinitialisent un UID effectif différent à l’UID réel lorsque Bash démarre sans `-p`. Vérifiez les changements d’UID réels de l’assistant et l’invocation de son processus enfant, ainsi que son propriétaire, les droits d’exécution, l’option de montage `nosuid` et l’état `no_new_privs` du processus. Le bit SUID ou un appel au shell ne suffit pas, à lui seul, à établir qu’une transition vers des privilèges supérieurs est possible.

Un `jjs` SUID appartenant à root et inhabituel mérite un examen distinct de l’accès aux fichiers si l’utilisateur actuel peut l’exécuter. L’outil Nashorn historique peut accéder aux API Java de fichiers même si un shell lancé comme processus enfant abandonne un UID effectif ; confirmez le comportement de la JVM installée, l’identité effective lors de l’opération sur le fichier et les paramètres `nosuid`/`no_new_privs` avant de considérer qu’il permet une lecture ou une écriture privilégiée. [Oracle a supprimé `jjs` dans JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html) ; un chemin installé peut toutefois correspondre à une version plus ancienne ou à une compilation empaquetée séparément. [GTFOBins décrit les API de fichiers](https://gtfobins.org/gtfobins/jjs/), mais ses exemples avec sudo ne prouvent pas le comportement SUID de toutes les compilations. N’invoquez pas l’outil pendant une énumération passive.

Un exécutable `gosu` SUID appartenant à root et accessible à un utilisateur moins privilégié mérite un examen : son interface documentée accepte un utilisateur cible et une commande, mais il est normalement lancé en tant que root pour abandonner les privilèges. Vérifiez le comportement SUID de la compilation installée, l’identité effective et le mappage de l’espace de noms utilisateur, ainsi que `nosuid` et `no_new_privs` ; être root dans un conteneur n’implique pas d’être root sur l’hôte. Un nom de fichier ou un bit SUID ne prouve pas, à lui seul, qu’une transition fonctionne. Consultez [l’utilisation en amont](https://github.com/tianon/gosu) et [l’avertissement SUID du mainteneur](https://github.com/tianon/gosu/issues/11). N’invoquez pas l’assistant pendant un inventaire passif.

Un wrapper de sauvegarde personnalisé avec bit set-user-ID peut accepter un chemin choisi par l’appelant et l’interpoler dans une commande d’archivage transmise à `system(3)`. Si ce chemin n’est pas encadré de guillemets dans la commande construite, le shell enfant peut appliquer [l’expansion du tilde avec `HOME`, les motifs de chemin tels que `?` et `*`, et la séparation des commandes par des retours à la ligne](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) ; rejeter uniquement les caractères de ponctuation courants dans une denylist ne rend pas le chemin littéral. Vérifiez le cheminement exact des arguments, l’environnement hérité, le shell enfant et son identité effective, l’accès au système de fichiers et si la sortie de l’outil d’archivage est visible pour l’appelant. Le bit SUID, une chaîne contenant le nom d’un outil d’archivage ou le seul rejet du chemin littéral `/root` ne prouvent ni divulgation ni exécution de code. Examinez une copie du wrapper hors ligne plutôt que d’archiver des fichiers privés ou d’envoyer des entrées provoquant un crash pendant une énumération passive.

La [substitution de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) du shell, telle que `$(...)`, constitue une autre lacune possible d’une denylist de métacaractères : même un préfixe de commande fixe autorisé peut transmettre un argument contrôlé ensuite par l’appelant à `/bin/sh -c`. Vérifiez hors ligne les guillemets exacts, l’analyseur et l’identité effective ; ne considérez pas une chaîne `system()` ou une denylist incomplète comme une preuve d’exécution.

L’**arbre des processus appelants** compte également. Un processus de travail web peut installer un filtre seccomp qui limite les appels système modifiant les UID ; les [filtres seccomp sont transmis aux processus enfants et persistent après `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Par exemple, les directives [mpm-itk `LimitUIDRange` et `LimitGIDRange` d’Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) peuvent limiter les identités accessibles aux descendants. `Seccomp: 2` dans `/proc/self/status` indique le mode filtre, pas la politique ni la capacité de cet assistant à obtenir l’identité de son propriétaire. Examinez ensemble l’ascendance de l’invocation réelle, son filtre effectif et les conditions SUID, de montage et `no_new_privs` ; une session de connexion distincte peut avoir une autre politique, mais nécessite son propre chemin d’accès valide.

Un exécutable SUID personnalisé peut invoquer un script Python distinct et lisible. S’il utilise réellement **Python 2**, [`input()` évalue l’expression saisie](https://docs.python.org/2/library/functions.html#input) ; en Python 3, `input()` renvoie le texte saisi. Confirmez l’identité effective du wrapper, le chemin et la version de l’interpréteur, le chemin du script et si une entrée non fiable atteint cet appel avant de considérer cette ligne source comme un chemin d’exécution. Un bit set-ID sur le script lui-même ou un appel à `input()` sans wrapper privilégié ne crée pas la même frontière. Examinez les chemins référencés par le binaire et une portion limitée du code source du script sans l’exécuter pendant l’énumération.

Si le code source d’un exécutable SUID inhabituel est lisible, comparez le nombre d’octets demandé pour chaque lecture de fichier contrôlée par l’appelant à la taille du tampon de destination, puis examinez les vérifications de contrôle ultérieures. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) écrit les éléments demandés à l’adresse fournie ; la fonction ne connaît pas la capacité de l’objet de destination. Une différence de taille est une piste d’analyse statique de sûreté mémoire, pas la preuve d’une élévation de privilèges exploitable : confirmez que le code source correspond au binaire installé, que l’appelant peut fournir l’entrée, que l’exécution SUID est effective dans ce contexte et que le chemin concerné est accessible. Examinez une portion limitée du code source ou une copie du binaire hors ligne plutôt que d’envoyer des entrées provoquant un crash au programme privilégié pendant l’énumération.

Un assistant SUID personnalisé peut divulguer un fichier protégé sans en afficher le contenu. Si l’appelant choisit à la fois un chemin et une expression régulière, et que l’assistant renvoie un nombre de correspondances visible avec son UID effectif, des tests de préfixe ancrés peuvent former un oracle caractère par caractère. Vérifiez le propriétaire de l’assistant, le comportement de son ID effectif, les droits d’exécution, les restrictions de chemin, la sémantique des expressions régulières, la visibilité de la réponse et l’existence d’un fichier spécifique accessible à un utilisateur plus privilégié mais autrement illisible par l’appelant. Un bit SUID ou une chaîne désignant une bibliothèque d’expressions régulières ne prouve aucun de ces éléments. Pendant une énumération passive, consignez l’exécutable inhabituel et examinez hors ligne un désassemblage ou une copie limitée du code source ; n’effectuez pas de tentatives répétées sur l’assistant en production et n’affichez pas les secrets récupérés.

Sur OpenBSD, un lecteur personnalisé avec bit set-user-ID qui accepte un chemin choisi par l’appelant peut exposer des fichiers dans `/var/backups` si son identité effective peut les lire et qu’il en renvoie le contenu à l’appelant. [`changelist(5)` d’OpenBSD](https://man.openbsd.org/changelist.5) décrit les copies `.current` et `.backup` des chemins configurés, mais les entrées précédées de `+` stockent des sommes de contrôle SHA-256 plutôt que le contenu des fichiers ; le répertoire de sauvegarde devrait appartenir à root et être en mode `0700`. Une [règle de lecture `unveil`](https://man.openbsd.org/unveil.2) de l’assistant pour `/var` peut autoriser l’accès sous ce chemin, mais ne donne ni ne prouve à elle seule l’accès aux fichiers. Confirmez l’UID effectif réel, les droits d’exécution de l’utilisateur actuel, le chemin accepté, l’existence et le contenu des sauvegardes ainsi que toute exigence d’authentification indépendante avant de conclure à une élévation de privilèges. Une énumération passive doit signaler l’assistant et les métadonnées du chemin, et non invoquer le lecteur ni afficher les données de sauvegarde.

Un programme SUID personnalisé qui vérifie un chemin choisi par l’appelant avec [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), puis ouvre ce chemin, peut subir une course liée à la modification d’un fichier ou d’un lien symbolique dans un répertoire modifiable par l’appelant. La vérification porte sur l’objet antérieur, tandis qu’un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ultérieur peut en résoudre un autre. Confirmez que l’assistant est exécutable avec une identité effective élevée, qu’un chemin de code accessible lit le fichier choisi et que l’appelant peut remplacer le chemin entre la vérification et l’ouverture ; un bit SUID, un répertoire modifiable ou une chaîne `stat` ne suffit pas, à lui seul, à établir ces éléments. Une sortie visible ou une destination lisible par l’appelant est également nécessaire pour qu’il y ait divulgation. Examinez le binaire et les métadonnées du chemin hors ligne ; ne provoquez pas de course avec l’assistant en production pendant une énumération passive.

Appliquez le même examen des dépendances aux wrappers SGID. Un wrapper qui lance un shell ou un assistant par chemin absolu peut rester dangereux si un utilisateur moins privilégié peut remplacer ce fichier ; le code lancé peut hériter du groupe effectif du wrapper. Vérifiez le chemin exact invoqué, ses droits d’écriture (y compris les ACL), le groupe effectif du wrapper et s’il abandonne ses privilèges avant de lancer le processus enfant. Un interpréteur peut aussi abandonner les ID effectifs hérités : distinguez donc une piste à examiner d’une transition démontrée. La présence d’un shell modifiable ailleurs sur l’hôte ne prouve pas, à elle seule, qu’un wrapper privilégié l’invoque.

### Wrappers privilégiés qui transmettent du SQL à la CLI SQLite

Si un programme SUID personnalisé transmet du SQL contrôlé par l’utilisateur au **programme en ligne de commande `sqlite3`**, examinez la commande exacte et l’identité effective avant de considérer la requête comme étant en lecture seule. La fonction SQL `edit()` de la CLI invoque un éditeur (indiqué par son deuxième argument ou par `VISUAL`), et sa fonction SQL `load_extension()` peut charger une bibliothèque partagée lorsque le chargement d’extensions est activé. Il s’agit de chemins potentiels d’exécution de code sous l’identité du processus CLI, même si le wrapper fixe `PATH` ou utilise un chemin absolu vers `sqlite3`. Le SQL doit réellement atteindre ces fonctions et la CLI doit conserver la fonctionnalité concernée ; trouver simplement `sqlite3` dans un binaire ou sur l’hôte ne prouve pas une élévation de privilèges. La **bibliothèque** SQLite désactive le chargement d’extensions par défaut : distinguez-la de la CLI. Lorsqu’une application privilégiée doit traiter du SQL non fiable, le mode `--safe` de la CLI SQLite désactive `edit()`, `load_extension()` et d’autres fonctions à effets secondaires. Consultez la [documentation de la CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentation du mode sécurisé](https://www.sqlite.org/cli.html#the_safe_command_line_option) et la [documentation sur le chargement d’extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lecteurs de fichiers privilégiés qui alimentent un client verbeux

Un wrapper SUID/SGID personnalisé peut vérifier l’accès à un chemin choisi par l’appelant, puis transmettre ce fichier à une autre commande. Examinez l’identité effective lors de la vérification d’accès et de l’ouverture ultérieure, résolvez les composants `../` par rapport au véritable répertoire de base et vérifiez comment le processus enfant traite les entrées invalides. Si un client de base de données lit un fichier privé comme du SQL avec une sortie verbeuse, il peut réafficher le contenu du fichier dans des erreurs même si le SQL est invalide. Il n’y a divulgation entre utilisateurs que si le processus enfant peut lire un fichier que l’appelant ne peut pas lire, si l’appelant peut choisir ce fichier via le wrapper et si la sortie lui est visible ; la présence de `mysql` ou d’une chaîne désignant un autre client ne prouve aucune de ces conditions.

### Chemin de recherche de Netdata `ndsudo`

La [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) concernait certaines compilations de Netdata `ndsudo`. L’assistant SUID appartenant à root recherchait les commandes externes autorisées à l’aide d’un `PATH` fourni par l’appelant. Examinez un assistant installé, y compris s’il se trouve hors du `PATH` habituel de l’appelant, uniquement lorsque le compte actuel peut l’exécuter. Confirmez son propriétaire, son bit SUID, les droits d’exécution (y compris les autorisations de groupe/ACL), la compilation installée, l’état des correctifs de l’éditeur et si `NoNewPrivs` ou un montage `nosuid` bloque le changement d’identité. Netdata indique que les compilations `v1.45.3` et `v1.45.0-169` sont corrigées ; les rétroportages des distributions doivent être vérifiés séparément. La version affichée dans le tableau de bord ou la seule présence de `ndsudo` ne suffit pas à prouver qu’une élévation de privilèges est accessible. Le problème de chemin nécessite également que l’assistant résolve une commande externe dans un emplacement contrôlé par l’appelant.

### Frontière de privilèges de Firejail join

La [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) concernait la logique privilégiée `--join` de Firejail : une cible join façonnée pouvait amener l’assistant setuid-root à accepter un espace de noms de montage contrôlé par un attaquant et à copier un état de sécurité dangereux. Pour un triage passif, confirmez que **l’identité actuelle peut exécuter** un binaire Firejail setuid appartenant à root, que le setuid est effectif sur son montage et dans le contexte du processus, et que la compilation installée n’inclut pas le correctif. Le projet en amont a corrigé le problème dans la [version 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) ; des paquets de distribution peuvent [rétroporter le correctif](https://github.com/netblue30/firejail/issues/5191) tout en affichant une version plus ancienne. Ces prérequis désignent une piste à examiner, pas une jointure réussie ni l’obtention d’un shell root. Ne créez pas de faux jail et n’invoquez pas `--join` pendant l’énumération.

### Permissions du fichier journal de GNU Screen

La [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) concernait Screen 4.5.0, qui ouvrait avec des privilèges élevés un fichier journal choisi par l’appelant. Un binaire `screen` ou une version suffixée figurant dans l’inventaire SUID n’est qu’une piste à examiner : confirmez son appartenance à root, l’efficacité de l’exécution SUID pour l’utilisateur actuel, la compilation installée, l’état des correctifs de la distribution et le comportement concerné du fichier journal. [Debian a corrigé son paquet 4.5.0 par rétroportage](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484) ; une chaîne de version ou un nom de fichier ne prouve donc pas, à lui seul, que le système est exposé. Ne créez pas de fichier journal comme sonde d’énumération courante.

La [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) concernait l’assistant privilégié S-nail de verrouillage de courrier : un composant de chemin contrôlé par l’appelant pouvait traverser des répertoires et conduire à une écriture arbitraire de fichier. Vérifiez si l’utilisateur actuel peut exécuter un assistant setuid installé appartenant à root, si son identité setuid est effective selon la politique de montage et de processus, ainsi que la compilation exacte du paquet et le correctif de l’éditeur. L’[avis de sécurité d’Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indique un correctif rétroporté pour son paquet 16.04 ; une version qui semble correspondre à celle en amont ne permet donc pas de conclure. La présence de l’assistant ne prouve pas que le chemin vulnérable est accessible ni qu’une écriture de fichier permet d’exécuter du code en tant que root ; examinez les métadonnées et l’état du paquet sans invoquer l’assistant ni tenter la course pendant l’énumération.

### Nettoyage de snap-confine et tmpfiles

La CVE-2026-3888 est une course impliquant `snap-confine` privilégié et le nettoyage de `/tmp` par systemd-tmpfiles. Un examen passif peut vérifier si `snap-confine` est setuid ou possède des capacités de fichier, comparer le paquet `snapd` installé à la version corrigée pour cette **version d’Ubuntu**, et examiner la règle d’ancienneté effective de `/tmp` ainsi que le timer de nettoyage. La correspondance entre paquet et règle constitue un prérequis, pas la preuve que la course est accessible : l’état du timer à l’exécution, la disposition de snap, les rétroportages des paquets et les remplacements de règles comptent également. Les anciennes versions peuvent nécessiter une configuration non standard. Ne lancez pas de sonde de course lors d’une énumération courante. Consultez la [fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2026-3888) pour connaître l’état des paquets selon la version et l’[avis de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) pour comprendre l’interaction entre les composants.

## Examiner les ACL et les chemins sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un répertoire parent accessible en écriture peut permettre le remplacement, même si le fichier appartient à root. Une ACL peut accorder discrètement l’accès à un fichier de configuration sudoers, une unité de service, un script cron, un chemin de bibliothèque ou un fichier d’identifiants. Vérifiez l’ACL et le chemin complet. Si des écritures arbitraires dans des fichiers privilégiés sont possibles, consultez [Arbitrary File Write to Root](write-to-root.md) ; pour la configuration du linker et les cas de preload, consultez l’[exemple `ld.so`](ld.so.conf-example.md). Considérez les sauvegardes exposées, les fichiers `.env`, les configurations de bases de données, les éléments SSH et l’historique comme des sources possibles d’identifiants ; l’accès dépend des permissions effectives de chaque fichier.
