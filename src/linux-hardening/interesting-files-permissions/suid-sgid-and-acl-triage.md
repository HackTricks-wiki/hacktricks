# SUID, SGID, ACLs y archivos sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID y SGID cambian la identidad efectiva de un archivo ejecutado; las ACLs pueden conceder acceso que no aparece en los bits de permisos normales de `ls -l`. Revisa ambos cuando un usuario pueda leer, escribir o ejecutar más de lo que sugieren los permisos aparentes del propietario y del grupo.

## Enumerar ejecutables privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Céntrate en los ejecutables personalizados o modificados recientemente, los propietarios inusuales y los archivos en montajes con permisos de escritura. Un montaje `nosuid` puede impedir el comportamiento set-ID; las capabilities de archivo son un mecanismo de privilegios independiente que se describe en [Linux capabilities](linux-capabilities.md). Compara un binario sospechoso con su paquete y comprueba qué ejecuta, abre o carga con una identidad elevada.

Si un ejecutable SUID de root que no conoces acepta datos del usuario, revisa una copia del binario sin conexión para detectar un manejo de argumentos inseguro para la memoria y la ruta de código que llega a él. Registra el comportamiento de los ID efectivos y las mitigaciones, como canarios de pila, memoria no ejecutable, código independiente de la posición y aleatorización de direcciones. Un nombre de función insegura o la ausencia de una mitigación solo son indicios para revisar: la explotabilidad depende de los límites reales de entrada, el flujo de control alcanzable y la identidad efectiva en el momento del fallo. No envíes argumentos largos al ejecutable privilegiado activo solo para comprobar si se bloquea durante la enumeración pasiva.

Un programa SUID conocido también puede haberse sustituido o contener una puerta trasera. Una fecha de modificación reciente es un indicio, no una prueba: para un **binario empaquetado sospechoso concreto**, averigua qué paquete lo contiene y compara el archivo instalado con los metadatos del paquete, en lugar de verificar todos los paquetes durante la enumeración rutinaria:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` comprueba el contenido de los archivos solo cuando la base de datos del paquete tiene una suma de comprobación registrada; RPM también compara metadatos, como el modo y la propiedad. Céntrate en una discrepancia del **ejecutable privilegiado en sí**: las instalaciones reducidas pueden informar de que faltan documentación o archivos de configuración regional en otras partes del mismo paquete. Compara el ejecutable sospechoso con un paquete de proveedor de confianza y revisa exactamente qué código cambió. Los cambios locales legítimos, la ausencia de sumas de comprobación y los metadatos de paquetes comprometidos limitan lo que demuestra cualquiera de los dos comandos. No ejecutes el programa SUID sospechoso ni un script de verificación del paquete durante el triage pasivo. Consulta el [manual de verificación de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) y el [manual de verificación de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programa SUID que invoque un shell, un comando relativo o una biblioteca desde una ruta con permisos de escritura puede cruzar un límite de confianza. Consulta [abuso de bibliotecas compartidas y del linker mediante SUID](suid-shared-library-and-linker-abuse.md), las [recomendaciones sobre PATH](../linux-basics/linux-environment-variables.md#path) y la [explicación de los ID de usuario](../user-information/euid-ruid-suid.md). Para escapes conocidos específicos de comandos, comprueba [GTFOBins](https://gtfobins.github.io/) con el binario exacto y la invocación permitida en el host.

En un ejecutable set-user-ID, distingue el **UID real** del usuario que lo invoca del **UID efectivo** del propietario del archivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) mantiene sin cambios el UID real y copia el UID efectivo al UID guardado tras cualquier cambio de set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) ejecuta el comando mediante `/bin/sh -c`; el shell seleccionado por esa ruta determina si un proceso hijo conserva su identidad efectiva. En particular, las [reglas del modo privilegiado de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) restablecen el UID efectivo al UID real cuando Bash se inicia sin `-p` y ambos UID son distintos. Comprueba los cambios de UID reales del helper y cómo invoca los procesos hijos, junto con su propietario, los permisos de ejecución, la opción de montaje `nosuid` y el estado `no_new_privs` del proceso. Un bit SUID o una llamada al shell, por sí solos, no demuestran que se pueda realizar una transición a mayores privilegios.

Un `jjs` inusual propiedad de root y con SUID merece una revisión independiente del acceso a archivos si el usuario actual puede ejecutarlo. La herramienta Nashorn heredada puede acceder a las API de archivos de Java incluso cuando un shell iniciado como proceso hijo descarta el UID efectivo; confirma el comportamiento de la JVM instalada, la identidad efectiva de la operación con archivos y las condiciones `nosuid`/`no_new_privs` antes de considerarlo una lectura o escritura privilegiada. [Oracle eliminó `jjs` en JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); una ruta instalada podría corresponder a una versión anterior o a una compilación empaquetada por separado. [GTFOBins documenta las API de archivos](https://gtfobins.org/gtfobins/jjs/), pero sus ejemplos con sudo no demuestran el comportamiento SUID en todas las compilaciones. No invoques la herramienta durante la enumeración pasiva.

Un ejecutable `gosu` propiedad de root, con SUID y accesible para un usuario con menos privilegios, merece revisión: su interfaz documentada acepta un usuario de destino y un comando, pero en el uso normal dentro de contenedores se inicia como root para descartar privilegios. Verifica el comportamiento SUID de la compilación instalada, la identidad efectiva y la asignación del espacio de nombres de usuario, además de `nosuid` y `no_new_privs`; ser root dentro de un contenedor no implica serlo en el host. El nombre del archivo o el bit SUID, por sí solos, no demuestran que la transición funcione. Consulta el [uso en el repositorio upstream](https://github.com/tianon/gosu) y la [advertencia del mantenedor sobre SUID](https://github.com/tianon/gosu/issues/11). No invoques el helper durante el inventario pasivo.

Un wrapper de backup personalizado con set-user-ID podría aceptar una ruta elegida por quien lo invoca e interpolarla en un comando de archivado pasado a `system(3)`. Si esa ruta no está entrecomillada en el comando construido, el shell hijo puede aplicar [expansión de tilde mediante `HOME`, patrones de nombres de ruta como `?` y `*`, y separación de comandos mediante saltos de línea](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rechazar solo signos de puntuación conocidos mediante una lista de denegación no hace que la ruta se trate literalmente. Confirma el flujo exacto de argumentos, el entorno heredado, el shell hijo y la identidad efectiva, el acceso al sistema de archivos y si la salida del archivador es visible para quien lo invoca. El bit SUID, una cadena del programa de archivado o el simple bloqueo de la ruta literal `/root` no demuestran por sí solos que haya divulgación o ejecución de código. Durante la enumeración pasiva, revisa una copia del wrapper sin conexión; no archives archivos privados ni envíes entradas que provoquen fallos.

La [sustitución de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) del shell, como `$(...)`, es otro posible resquicio en una lista de denegación de metacaracteres: incluso un prefijo de comando permitido y fijo puede pasar un argumento posterior controlado por quien lo invoca a `/bin/sh -c`. Verifica sin conexión las comillas, el parser y la identidad efectiva exactos; no consideres que una cadena de `system()` o una lista de denegación incompleta demuestran la ejecución.

También importa el **árbol de procesos que invoca el programa**. Un proceso worker web puede instalar un filtro seccomp que restrinja las llamadas del sistema que cambian el UID; [los filtros seccomp se heredan por los procesos hijos y persisten tras `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por ejemplo, las directivas [`LimitUIDRange` y `LimitGIDRange` de mpm-itk de Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) pueden limitar las identidades a las que pueden cambiar sus descendientes. `Seccomp: 2` en `/proc/self/status` indica el modo del filtro, no su política ni si este helper en concreto puede obtener la identidad de su propietario. Revisa conjuntamente la ascendencia de la invocación real y el filtro efectivo, así como las condiciones SUID, de montaje y `no_new_privs`; una sesión de inicio de sesión independiente podría tener una política distinta, pero requeriría su propia ruta de acceso válida.

Un ejecutable SUID personalizado puede invocar un script Python independiente que sea legible. Si realmente usa **Python 2**, [`input()` evalúa la expresión introducida](https://docs.python.org/2/library/functions.html#input); en Python 3, `input()` devuelve texto. Antes de considerar esa línea de código como una vía de ejecución, confirma la identidad efectiva del wrapper, la ruta y versión del intérprete, la ruta del script y si la entrada no confiable llega a esa llamada. Un bit set-ID en el propio script o una llamada a `input()` sin el wrapper privilegiado no establecen el mismo límite. Durante la enumeración, revisa las rutas a las que hace referencia el binario y una sección acotada del código fuente del script, sin ejecutarlo.

Si un ejecutable SUID inusual incluye código fuente legible, compara la cantidad de bytes solicitada en cada lectura de archivos controlada por quien lo invoca con el tamaño del búfer de destino e inspecciona las comprobaciones posteriores del flujo de control. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) almacena los elementos solicitados en el puntero proporcionado; no conoce la capacidad del objeto de destino. Una discrepancia de tamaños es una pista estática de un problema de seguridad de memoria, no una prueba de que se pueda aprovechar para escalar privilegios: confirma que el código fuente corresponde al binario instalado, que quien lo invoca puede proporcionar la entrada, que la ejecución SUID es efectiva en ese contexto y que se puede alcanzar la ruta pertinente. Revisa sin conexión una copia acotada del código fuente o del binario, en vez de enviar entradas que provoquen fallos al programa privilegiado durante la enumeración.

Un helper SUID personalizado puede divulgar un archivo protegido sin imprimir su contenido. Si quien lo invoca elige tanto una ruta como una expresión regular y el helper devuelve un recuento visible de coincidencias bajo su UID efectivo, las pruebas de prefijos anclados podrían formar un oráculo carácter por carácter. Confirma el propietario del helper, el comportamiento del ID efectivo, los permisos de ejecución, las restricciones de rutas, la semántica de la expresión regular, la visibilidad de la respuesta y la existencia de un archivo específico con mayores privilegios que quien lo invoca no pueda leer de otro modo. Un bit SUID o una cadena de una biblioteca de expresiones regulares, por sí solos, no demuestran nada de ese flujo. Durante la enumeración pasiva, registra el ejecutable inusual y revisa una desensamblación acotada o una copia del código fuente; no pruebes conjeturas iterativas contra el helper en ejecución ni imprimas secretos recuperados.

En OpenBSD, un lector personalizado con set-user-ID que acepte una ruta elegida por quien lo invoca podría exponer archivos de `/var/backups` si su identidad efectiva puede leerlos y devuelve su contenido a quien lo invoca. [`changelist(5)` de OpenBSD](https://man.openbsd.org/changelist.5) describe copias `.current` y `.backup` de las rutas configuradas, pero las entradas con el prefijo `+` almacenan sumas de comprobación SHA-256 en lugar del contenido de los archivos; el directorio de backup debería ser propiedad de root y tener modo `0700`. Una [regla `unveil` de lectura](https://man.openbsd.org/unveil.2) del helper para `/var` puede permitir el acceso bajo esa ruta, pero no concede ni demuestra por sí misma el acceso a los archivos. Antes de afirmar que hay escalada, confirma el UID efectivo real, que el usuario actual tenga permiso para ejecutar el programa, la ruta aceptada, la existencia y el contenido del backup, y cualquier requisito de autenticación independiente. La enumeración pasiva debe informar del helper y los metadatos de la ruta, no invocar el lector ni imprimir datos del backup.

Un programa SUID personalizado que compruebe una ruta elegida por quien lo invoca con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) y abra la ruta más tarde puede sufrir una carrera si cambia un archivo o enlace simbólico en un directorio donde quien lo invoca tiene permisos de escritura. La comprobación se aplica al objeto anterior, mientras que una llamada posterior a [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) podría resolver otro. Confirma que el helper se puede ejecutar con identidad efectiva elevada, que una ruta de código alcanzable lee el archivo seleccionado y que quien lo invoca puede reemplazar la ruta entre la comprobación y la apertura; un bit SUID, un directorio con permisos de escritura o una cadena `stat`, por sí solos, no demuestran nada de esto. Para que haya divulgación también hace falta que la salida sea visible o que el destino sea legible por quien lo invoca. Revisa sin conexión el binario y los metadatos de la ruta; no intentes una carrera contra el helper en ejecución durante la enumeración pasiva.

Aplica la misma revisión de dependencias a los wrappers SGID. Un wrapper que ejecute un shell o helper mediante una ruta absoluta puede seguir siendo inseguro si un usuario con menos privilegios puede reemplazar ese archivo; el código iniciado podría heredar el grupo efectivo del wrapper. Comprueba la ruta exacta invocada, sus permisos de escritura (incluidas las ACL), el grupo efectivo del wrapper y si descarta privilegios antes de iniciar el proceso hijo. Un intérprete también puede descartar los ID efectivos heredados, así que distingue entre un elemento que merece revisión y una transición demostrada. Que haya un shell con permisos de escritura en otra parte del host no demuestra por sí solo que un wrapper privilegiado lo invoque.

### Wrappers privilegiados que pasan SQL a la CLI de SQLite

Si un programa SUID personalizado pasa SQL controlado por el usuario al **programa de línea de comandos `sqlite3`**, inspecciona el comando exacto y la identidad efectiva antes de considerar que la consulta es de solo lectura. La función SQL `edit()` de la CLI invoca un editor (indicado en su segundo argumento o en `VISUAL`), y su función SQL `load_extension()` puede cargar una biblioteca compartida si la carga de extensiones está habilitada. Estas son posibles vías de ejecución de código con la identidad del proceso de la CLI, aunque el wrapper fije `PATH` o use una ruta absoluta a `sqlite3`. El SQL debe llegar realmente a esas funciones y la CLI debe conservar la función pertinente; encontrar `sqlite3` en un binario o en el host no demuestra que haya una escalada. La **biblioteca** SQLite deshabilita la carga de extensiones por defecto, así que no la confundas con la CLI. Si una aplicación privilegiada debe procesar SQL no confiable, el modo `--safe` de la CLI de SQLite deshabilita `edit()`, `load_extension()` y otras funciones con efectos secundarios. Consulta la [documentación de la CLI de SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentación del modo seguro](https://www.sqlite.org/cli.html#the_safe_command_line_option) y la [documentación sobre carga de extensiones](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lectores de archivos privilegiados que alimentan un cliente verboso

Un wrapper SUID/SGID personalizado puede comprobar el acceso a una ruta elegida por quien lo invoca y luego pasar ese archivo a otro comando. Revisa la identidad efectiva tanto en la comprobación de acceso como en la apertura posterior, resuelve cualquier componente `../` con respecto al directorio base real e inspecciona cómo gestiona el proceso hijo las entradas no válidas. Si un cliente de base de datos lee un archivo privado como SQL con salida verbosa, puede repetir el contenido del archivo en los errores aunque el SQL no sea válido. Esto solo constituye una divulgación entre usuarios si el proceso hijo puede leer un archivo que quien lo invoca no puede, si este puede seleccionar ese archivo mediante el wrapper y si la salida es visible; la presencia de `mysql` o de la cadena de otro cliente no demuestra ninguna de estas condiciones por sí sola.

### Ruta de búsqueda de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afectó algunas compilaciones de Netdata `ndsudo`. El helper SUID propiedad de root buscaba los comandos externos permitidos usando un `PATH` proporcionado por quien lo invocaba. Revisa un helper instalado, incluso si está fuera del `PATH` habitual de quien lo invoca, solo cuando la cuenta actual pueda ejecutarlo. Confirma su propietario, el bit SUID, los permisos de ejecución (incluidas las concesiones de grupo/ACL), la compilación instalada y si el proveedor aplicó el parche, y si `NoNewPrivs` o un montaje `nosuid` bloquean el cambio de identidad. Netdata indica las compilaciones corregidas `v1.45.3` y `v1.45.0-169`; los backports de las distribuciones requieren confirmación aparte. La versión del dashboard o la mera presencia de `ndsudo` no bastan para demostrar que la escalada sea alcanzable. El problema de la ruta también requiere que el helper resuelva un comando externo mediante una ubicación que quien lo invoca controle.

### Límite de privilegios de Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afectó la lógica privilegiada `--join` de Firejail: un destino de join manipulado podía hacer que el helper setuid-root aceptara un espacio de nombres de montaje controlado por un atacante y copiara un estado de seguridad inseguro. Para el triage pasivo, confirma que la **identidad actual puede ejecutar** un binario Firejail propiedad de root y con setuid, que setuid sea efectivo en su montaje y contexto de proceso, y que la compilación instalada no tenga la corrección. Upstream corrigió el problema en [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); los paquetes de las distribuciones pueden [incluir el parche retroactivamente](https://github.com/netblue30/firejail/issues/5191) aunque sigan mostrando una versión anterior. Estos requisitos previos identifican un elemento que merece revisión, no demuestran que el join haya funcionado ni que se obtenga un shell root. No construyas un jail falso ni invoques `--join` durante la enumeración.

### Permisos del archivo de registro de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) implicó que Screen 4.5.0 abría con privilegios elevados un archivo de registro elegido por quien lo invocaba. Un binario `screen` o con la versión en el nombre dentro del inventario SUID es solo una pista para revisar: confirma que sea propiedad de root, que la ejecución SUID sea efectiva para el usuario actual, cuál es la compilación instalada, cuál es el estado del parche de la distribución y cómo se comporta con el archivo de registro afectado. [Debian corrigió su paquete 4.5.0 mediante un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), así que una cadena de versión o el nombre de archivo, por sí solos, no demuestran que haya exposición. No crees un archivo de registro como prueba rutinaria de enumeración.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afectó el helper privilegiado de bloqueo de correo de S-nail cuando un componente de ruta controlado por quien lo invoca podía recorrer directorios y provocar la escritura de un archivo arbitrario. Revisa si el usuario actual puede ejecutar un helper setuid instalado y propiedad de root, si la identidad setuid es efectiva con la política del montaje y del proceso, y cuál es la compilación exacta del paquete y su corrección del proveedor. El [aviso de seguridad de Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indica que su paquete 16.04 incluye una corrección retroactiva, así que una versión que parezca upstream no es concluyente. La presencia del helper no demuestra que la ruta afectada sea alcanzable ni que una escritura de archivo permita ejecutar código como root; inspecciona los metadatos y el estado del paquete sin invocar el helper ni intentar la carrera durante la enumeración.

### Limpieza de snap-confine y tmpfiles

CVE-2026-3888 es una carrera entre `snap-confine` privilegiado y la limpieza de `/tmp` mediante systemd-tmpfiles. En una revisión pasiva, se puede comprobar si `snap-confine` tiene setuid o capacidades de archivo, comparar el paquete `snapd` instalado con la versión corregida para esa **versión de Ubuntu** e inspeccionar la regla efectiva de antigüedad para `/tmp` y el temporizador de limpieza. Un paquete y una regla coincidentes son requisitos previos, no pruebas de que se pueda alcanzar la carrera: también importan el estado del temporizador en tiempo de ejecución, la estructura de snap, los backports del paquete y las anulaciones de reglas. Las versiones anteriores pueden requerir una configuración no predeterminada. No ejecutes una prueba de carrera durante la enumeración rutinaria. Consulta el [registro CVE de Ubuntu](https://ubuntu.com/security/CVE-2026-3888) para conocer el estado de los paquetes por versión y el [aviso de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para entender la interacción entre los componentes.

## Inspeccionar ACL y rutas sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un directorio padre con permisos de escritura puede permitir reemplazar un archivo aunque pertenezca a root. Una ACL puede conceder silenciosamente acceso a un archivo drop-in de sudoers, una unidad de servicio, un script de cron, una ruta de bibliotecas o un archivo de credenciales. Comprueba tanto la ACL como la ruta completa. Si es posible escribir archivos privilegiados arbitrarios, sigue [Arbitrary File Write to Root](write-to-root.md); para casos de configuración del linker y preload, consulta el [ejemplo de `ld.so`](ld.so.conf-example.md). Trata las copias de seguridad expuestas, los archivos `.env`, las configuraciones de bases de datos, el material de SSH y el historial como posibles fuentes de credenciales; el acceso depende de los permisos efectivos de cada archivo.
