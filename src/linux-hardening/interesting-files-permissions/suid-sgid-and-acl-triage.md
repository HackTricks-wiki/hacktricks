# SUID, SGID, ACL і конфіденційні файли

{{#include ../../banners/hacktricks-training.md}}

SUID і SGID змінюють ефективну ідентичність запущеного файла; ACL можуть надавати доступ, який не відображають звичайні біти прав у `ls -l`. Перевіряйте обидва, якщо користувач може читати, записувати або виконувати файли з більшими правами, ніж указують видимі права власника та групи.

## Перелік привілейованих виконуваних файлів

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Зосередьтеся на власних або нещодавно змінених виконуваних файлах, незвичних власниках і файлах на доступних для запису точках монтування. Точка монтування `nosuid` може вимкнути поведінку set-ID; файлові capabilities — це окремий механізм привілеїв, описаний у [Linux capabilities](linux-capabilities.md). Порівняйте підозрілий двійковий файл із його пакетом і перевірте, що він виконує, відкриває або завантажує з підвищеною ідентичністю.

Якщо незнайомий виконуваний файл SUID належить root і приймає введення від користувача, перевірте копію цього двійкового файла офлайн на небезпечну для пам’яті обробку аргументів і шлях виконання коду, який до неї веде. Зафіксуйте поведінку effective ID і наявні засоби захисту, як-от stack canaries, невиконувана пам’ять, позиційно-незалежний код і рандомізація адрес. Небезпечна назва функції чи відсутній засіб захисту — лише привід для перевірки: можливість експлуатації залежить від фактичних обмежень введення, досяжного потоку керування та effective identity у момент помилки. Не надсилайте довгі аргументи до активного привілейованого виконуваного файла лише для перевірки на збій під час пасивного переліку.

Знайому програму SUID теж можуть замінити або вбудувати в неї бекдор. Нещодавня дата зміни — це привід для перевірки, а не доказ: для **конкретного підозрілого бінарного файла з пакета** визначте пакет-власник і порівняйте встановлений файл із метаданими пакета, а не перевіряйте кожен пакет під час звичайного переліку:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` перевіряє вміст файлів лише тоді, коли в базі даних пакетів записана контрольна сума; RPM також порівнює метадані, як-от режим і власника. Звертайте увагу на невідповідність саме **привілейованого виконуваного файла**: в урізаних інсталяціях можуть бракувати документації або файлів локалізації в інших місцях того самого пакета. Порівняйте підозрілий виконуваний файл із довіреним пакетом виробника й перевірте точні зміни коду. Локальні зміни, відсутність контрольних сум і скомпрометовані метадані пакетів обмежують доказову силу обох команд. Під час пасивного тріажу не запускайте ані підозрілу SUID-програму, ані скрипт перевірки пакета. Див. [посібник із перевірки dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) і [посібник із перевірки RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

SUID-програма, яка запускає shell, команду з відносним шляхом або бібліотеку з доступного для запису шляху, може перетинати межу довіри. Див. [зловживання SUID зі спільними бібліотеками та лінкером](suid-shared-library-and-linker-abuse.md), [поради щодо PATH](../linux-basics/linux-environment-variables.md#path) і [пояснення ідентифікаторів користувача](../user-information/euid-ruid-suid.md). Для відомих обходів, специфічних для команд, перевірте [GTFOBins](https://gtfobins.github.io/) для конкретного бінарного файла й способу його виклику, дозволеного на хості.

Для виконуваного файла з set-user-ID розрізняйте **реальний UID** викликувача та **ефективний UID** власника файла: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) не змінює реальний UID і після зміни set-ID копіює ефективний UID у збережений UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) запускає команду через `/bin/sh -c`; shell, вибраний цим шляхом, впливає на те, чи збереже дочірній процес свою ефективну ідентичність. Зокрема, [правила привілейованого режиму Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) скидають відмінний ефективний UID до реального UID, якщо Bash запускається без `-p`. Перевірте зміни UID у фактичному допоміжному процесі та запуск дочірнього процесу, а також власника, доступ до виконуваного файла, параметр монтування `nosuid` і стан процесу `no_new_privs`. Самі по собі біт SUID або виклик shell не підтверджують наявності дієвого переходу до вищих привілеїв.

Незвичний SUID-файл `jjs`, власником якого є root, варто окремо перевірити на доступ до файлів, якщо поточний користувач може його виконати. Застарілий інструмент Nashorn може використовувати Java API для роботи з файлами, навіть коли запущений shell втрачає ефективний UID; перш ніж вважати його засобом привілейованого читання або запису, з’ясуйте поведінку встановленої JVM, ефективну ідентичність під час файлової операції та вплив `nosuid`/`no_new_privs`. [Oracle вилучила `jjs` у JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); встановлений шлях усе ще може вказувати на стару або окремо запаковану збірку. [GTFOBins описує файлові API](https://gtfobins.org/gtfobins/jjs/), але приклади для sudo не підтверджують поведінку SUID для кожної збірки. Не запускайте інструмент під час пасивного переліку.

SUID-виконуваний файл `gosu` із власником root, доступний користувачу з нижчими привілеями, потребує перевірки: його документований інтерфейс приймає цільового користувача й команду, але за звичайного використання в контейнері запускається від root, щоб скинути привілеї. Перевірте поведінку встановленої збірки з SUID, ефективну ідентичність і зіставлення просторів імен користувачів, а також `nosuid` і `no_new_privs`; root у контейнері не означає root на хості. Саме ім’я файла або біт SUID не доводять наявності робочого переходу. Див. [інструкцію з використання в upstream](https://github.com/tianon/gosu) і [попередження супроводжувача щодо SUID](https://github.com/tianon/gosu/issues/11). Не запускайте допоміжну програму під час пасивної інвентаризації.

Власний set-user-ID wrapper для резервного копіювання може приймати шлях, заданий викликувачем, і підставляти його в команду архівування, передану до `system(3)`. Якщо цей шлях у сформованій команді не взято в лапки, дочірній shell може застосувати [розгортання тильди за допомогою `HOME`, шаблони шляхів на кшталт `?` і `*` та розділення команд символом нового рядка](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); заборона лише звичних знаків у denylist не перетворює шлях на літеральний. Перевірте точний потік аргументів, успадковане середовище, дочірній shell і ефективну ідентичність, доступ до файлової системи та видимість результату архівування для викликувача. Біт SUID, рядок із назвою інструмента архівування або сама лише заборона літерального `/root` не доводять ані розголошення даних, ані виконання коду. Під час пасивного переліку переглядайте копію wrapper офлайн, а не архівуйте приватні файли й не надсилайте аварійні вхідні дані.

[Підстановка команд](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) у shell, як-от `$(...)`, — ще одна можлива прогалина в denylist метасимволів: навіть фіксований дозволений префікс команди може передавати пізніший аргумент, контрольований викликувачем, через `/bin/sh -c`. Перевірте точне екранування, парсер та ефективну ідентичність офлайн; не вважайте сам рядок `system()` або неповний denylist доказом виконання.

Важливе також **дерево процесів виклику**. Вебворкер може встановити фільтр seccomp, що обмежує системні виклики зміни UID; [фільтри seccomp успадковуються дочірніми процесами та зберігаються після `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Наприклад, директиви Apache [mpm-itk `LimitUIDRange` і `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) можуть обмежувати ідентичності, доступні нащадкам. `Seccomp: 2` у `/proc/self/status` показує режим фільтра, а не його політику й не те, чи може саме цей допоміжний процес отримати ідентичність власника. Перевірте разом ланцюжок предків фактичного виклику та ефективний фільтр, а також умови SUID, монтування й `no_new_privs`; окремий сеанс входу може мати іншу політику, але для нього потрібен власний дійсний шлях доступу.

Власний SUID-виконуваний файл може запускати окремий скрипт Python, доступний для читання. Якщо він справді використовує Python **2**, [`input()` обчислює введений вираз](https://docs.python.org/2/library/functions.html#input); у Python 3 `input()` натомість повертає текст. Перш ніж вважати цей рядок коду шляхом до виконання, перевірте ефективну ідентичність wrapper, шлях і версію інтерпретатора, шлях до скрипту та те, чи потрапляють недовірені дані до цього виклику. Біт set-ID на самому скрипті або виклик `input()` без привілейованого wrapper не встановлюють такої самої межі. Під час переліку перевіряйте згадані в бінарному файлі шляхи та обмежений за обсягом вихідний код скрипту, не запускаючи його.

Якщо з незвичним SUID-виконуваним файлом є доступний для читання вихідний код, зіставте кількість байтів, яку запитує кожне читання файла, контрольованого викликувачем, із розміром буфера призначення та перевірте подальші перевірки потоку керування. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) записує запитані елементи за переданим вказівником; функція не знає місткості об’єкта призначення. Невідповідність розмірів — це підказка щодо помилки безпеки пам’яті в статичному аналізі, а не доказ придатного для використання підвищення привілеїв: перевірте, чи відповідає вихідний код встановленому бінарному файлу, чи може викликувач надати вхідні дані, чи ефективне виконання SUID у цьому контексті та чи досяжний відповідний шлях. Під час переліку переглядайте обмежену за обсягом копію вихідного коду або бінарного файла офлайн, а не надсилайте аварійні вхідні дані привілейованій програмі.

Власний SUID-допоміжний процес може розкрити захищений файл, не виводячи його вміст. Якщо викликувач задає і шлях, і регулярний вираз, а допоміжний процес повертає видиму кількість збігів, виконуваних від його ефективної ідентичності, перевірки з прив’язаним до початку рядка шаблоном можуть утворити посимвольний оракул. Перевірте власника допоміжного процесу, поведінку ефективного ID, доступ до виконуваного файла, обмеження шляхів, семантику регулярних виразів, видимість відповіді та наявність конкретного файла з вищими привілеями, який викликувач інакше не може прочитати. Сам біт SUID або рядок із назвою бібліотеки регулярних виразів нічого з цього не доводить. Під час пасивного переліку зафіксуйте незвичний виконуваний файл і перегляньте обмежену за обсягом дизасембльовану копію або вихідний код; не надсилайте живому допоміжному процесу ітеративні здогадки й не виводьте відновлені секрети.

В OpenBSD власний set-user-ID засіб читання, що приймає шлях, заданий викликувачем, може відкрити файли в `/var/backups`, якщо його ефективна ідентичність має до них доступ для читання, а він повертає їхній вміст викликувачу. [`changelist(5)` в OpenBSD](https://man.openbsd.org/changelist.5) описує копії `.current` і `.backup` для налаштованих шляхів, але записи з префіксом `+` зберігають контрольні суми SHA-256, а не вміст файлів; каталог резервних копій має належати root і мати режим `0700`. Правило [`unveil` для читання](https://man.openbsd.org/unveil.2) у допоміжному процесі для `/var` може дозволити доступ усередині цього шляху, але саме по собі не надає й не доводить доступу до файлів. Перш ніж заявляти про підвищення привілеїв, перевірте фактичний ефективний UID, дозвіл на виконання для поточного користувача, прийнятий шлях, наявність і вміст резервної копії, а також будь-які незалежні вимоги автентифікації. Пасивний перелік має фіксувати допоміжний процес і метадані шляху, а не запускати засіб читання чи виводити дані резервної копії.

Власна SUID-програма, яка перевіряє заданий викликувачем шлях за допомогою [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), а пізніше відкриває цей шлях, може піддаватися гонці через зміну файла або символічного посилання в каталозі, доступному викликувачеві для запису. Перевірка стосується попереднього об’єкта, тоді як пізніший [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) може знайти інший. Перевірте, чи можна виконати допоміжний процес з підвищеною ефективною ідентичністю, чи читає досяжний шлях виконання вибраний файл і чи може викликувач замінити шлях між перевіркою та відкриттям; самі по собі біт SUID, доступний для запису каталог або рядок `stat` нічого з цього не доводять. Для розголошення потрібні також видимий вивід або доступне викликувачеві місце призначення. Перегляньте бінарний файл і метадані шляхів офлайн; не влаштовуйте гонку з активним допоміжним процесом під час пасивного переліку.

Таку саму перевірку залежностей застосовуйте до SGID-wrapper. Wrapper, що запускає shell або допоміжний процес за абсолютним шляхом, усе одно може бути небезпечним, якщо користувач із нижчими привілеями може замінити цей файл; запущений код може успадкувати ефективну групу wrapper. Перевірте точний шлях виклику, доступ до нього для запису (зокрема через ACL), ефективну групу wrapper і те, чи скидає він привілеї перед запуском дочірнього процесу. Інтерпретатор також може відкидати успадковані ефективні ID, тому розрізняйте кандидата для перевірки та доведений перехід. Наявність доступного для запису shell деінде на хості сама по собі не доводить, що його викликає привілейований wrapper.

### Привілейовані wrapper, що передають SQL до SQLite CLI

Якщо власна SUID-програма передає контрольований користувачем SQL **програмі командного рядка `sqlite3`**, перш ніж вважати запит лише для читання, перевірте точну команду й ефективну ідентичність. SQL-функція CLI `edit()` запускає редактор (із другого аргументу або `VISUAL`), а SQL-функція `load_extension()` може завантажити спільну бібліотеку, якщо завантаження розширень увімкнене. Це потенційні шляхи до виконання коду з ідентичністю процесу CLI, навіть якщо wrapper фіксує `PATH` або використовує абсолютний шлях до `sqlite3`. SQL має справді доходити до цих функцій, а CLI має зберігати відповідну можливість; сама лише згадка `sqlite3` у бінарному файлі чи на хості не свідчить про підвищення привілеїв. **Бібліотека** SQLite вимикає завантаження розширень за замовчуванням, тож розрізняйте її та CLI. Якщо привілейована програма має обробляти недовірений SQL, режим CLI SQLite `--safe` вимикає `edit()`, `load_extension()` та інші функції з побічними ефектами. Див. [документацію SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), [документацію безпечного режиму](https://www.sqlite.org/cli.html#the_safe_command_line_option) і [документацію завантаження розширень](https://www.sqlite.org/loadext.html#loading_an_extension).

### Привілейовані засоби читання файлів, що передають дані клієнту з докладним виводом

Власний SUID/SGID-wrapper може перевіряти доступ до шляху, заданого викликувачем, а потім передавати цей файл іншій команді. Перевірте ефективну ідентичність під час перевірки доступу й подальшого відкриття, розберіть усі компоненти `../` відносно фактичного базового каталогу та з’ясуйте, як дочірній процес обробляє некоректні дані. Якщо клієнт бази даних читає приватний файл як SQL із докладним виводом, він може відобразити вміст файла в повідомленнях про помилки, навіть якщо SQL некоректний. Це розголошення між користувачами лише тоді, коли дочірній процес може прочитати файл, недоступний викликувачеві, викликувач може вибрати цей файл через wrapper, а вивід видимий; сама лише наявність `mysql` чи рядка з назвою іншого клієнта нічого з цього не доводить.

### Шлях пошуку Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) стосувалася деяких збірок Netdata `ndsudo`. Допоміжний процес із SUID і власником root шукав дозволені зовнішні команди, використовуючи `PATH`, заданий викликувачем. Перевіряйте встановлений допоміжний процес, зокрема той, що розташований поза звичним для викликувача `PATH`, лише якщо поточний обліковий запис може його виконати. Перевірте його власника, біт SUID, доступ до виконання (зокрема через групу/ACL), встановлену збірку й статус виправлень від виробника, а також чи не блокує зміну ідентичності `NoNewPrivs` або монтування `nosuid`. Netdata зазначає виправлені збірки `v1.45.3` і `v1.45.0-169`; бекпорти дистрибутивів потрібно підтверджувати окремо. Версії на панелі керування або самої наявності `ndsudo` недостатньо, щоб довести можливість підвищення привілеїв. Проблема зі шляхом також потребує, щоб допоміжний процес знаходив зовнішню команду в місці, яке контролює викликувач.

### Межа привілеїв Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) стосувалася привілейованої логіки `--join` у Firejail: спеціально сформована ціль приєднання могла змусити допоміжний процес із setuid-root прийняти простір імен монтування, контрольований зловмисником, і скопіювати небезпечний стан безпеки. Для пасивного тріажу перевірте, чи може **поточна ідентичність виконати** бінарний файл Firejail із власником root і setuid, чи діє setuid у його контексті процесу та на відповідному монтуванні, а також чи не бракує встановленій збірці виправлення. Upstream виправив проблему у версії [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); пакети дистрибутивів можуть [містити бекпорт виправлення](https://github.com/netblue30/firejail/issues/5191), але й далі показувати старішу версію. Ці передумови вказують на кандидата для перевірки, а не на успішне приєднання чи отримання root shell. Не створюйте фальшиве ізольоване середовище й не запускайте `--join` під час переліку.

### Дозволи на файл журналу GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) стосувалася Screen 4.5.0, яка відкривала заданий викликувачем файл журналу з підвищеними привілеями. Бінарний файл `screen` або версійний варіант у переліку SUID — лише привід для перевірки: з’ясуйте власника root, чи ефективне виконання SUID для поточного користувача, встановлену збірку й статус виправлень дистрибутива, а також поведінку з уразливим файлом журналу. [Debian виправив пакет версії 4.5.0 бекпортом](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), тому сам рядок версії чи ім’я файла не доводять наявності вразливості. Не створюйте файл журналу як звичайну перевірку під час переліку.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) стосувалася привілейованого допоміжного процесу блокування пошти S-nail, коли компонент шляху, контрольований викликувачем, міг проходити через каталоги й призводити до довільного запису у файл. Перевірте, чи може поточний користувач виконати встановлений допоміжний процес із setuid і власником root, чи діє його setuid-ідентичність з огляду на політику монтування та процесу, а також точну збірку пакета й виправлення виробника. [Повідомлення безпеки Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) зазначає бекпорт виправлення для пакета версії 16.04, тому версія, схожа на upstream, не дає остаточної відповіді. Наявність допоміжного процесу не доводить, що вразливий шлях досяжний або що запис у файл дає змогу виконати код від root; під час переліку перевіряйте метадані й стан пакета, не запускаючи допоміжний процес і не намагаючись відтворити гонку.

### Очищення snap-confine і tmpfiles

CVE-2026-3888 — це гонка за участю привілейованого `snap-confine` і очищення `/tmp` засобом systemd-tmpfiles. Під час пасивної перевірки можна з’ясувати, чи має `snap-confine` біт setuid або файлові capabilities, порівняти встановлений пакет `snapd` із виправленою версією для **цього випуску Ubuntu**, а також перевірити ефективне правило очищення `/tmp` за віком і таймер очищення. Відповідний пакет і правило є передумовами, а не доказом досяжності гонки: важливі також фактичний стан таймера, компонування snap, бекпорти пакетів і перевизначення правил. Для старіших випусків може знадобитися нестандартна конфігурація. Не запускайте перевірку гонки під час звичайного переліку. Див. [запис Ubuntu про CVE](https://ubuntu.com/security/CVE-2026-3888) зі статусом пакетів для окремих випусків і [рекомендацію Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root), де описано взаємодію компонентів.

## Перевірте ACL і чутливі шляхи

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Доступний для запису батьківський каталог може дозволити заміну файлу, навіть якщо сам файл належить root. ACL може непомітно надавати доступ до файлу конфігурації sudoers, модуля, що підключається до конфігурації, юніта служби, cron-скрипту, шляху до бібліотеки або файлу облікових даних. Перевіряйте і ACL, і повний шлях. Якщо можливий довільний запис у привілейовані файли, див. [Arbitrary File Write to Root](write-to-root.md); випадки з конфігурацією компонувальника та preload описані в [`ld.so` example](ld.so.conf-example.md). Вважайте доступні резервні копії, файли `.env`, конфігурації баз даних, матеріали SSH та історію можливими джерелами облікових даних; доступ до них визначають фактичні дозволи кожного файлу.
