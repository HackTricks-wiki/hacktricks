# SUID, SGID, ACLs y archivos sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID y SGID cambian la identidad efectiva de un archivo ejecutado; las ACLs pueden conceder acceso que no aparece en los bits de permisos habituales de `ls -l`. Revisa ambos cuando un usuario pueda leer, escribir o ejecutar más de lo que sugieren los permisos aparentes del propietario y el grupo.

## Enumerar ejecutables privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Céntrate en ejecutables personalizados o modificados recientemente, propietarios inusuales y archivos en montajes con permisos de escritura. Un montaje `nosuid` puede suprimir el comportamiento set-ID; las file capabilities son un mecanismo de privilegios independiente que se describe en [Linux capabilities](linux-capabilities.md). Compara un binario sospechoso con su paquete y comprueba qué ejecuta, abre o carga con una identidad elevada.

Si un ejecutable SUID desconocido propiedad de root acepta entradas del usuario, analiza una copia del binario sin conexión para detectar el manejo de argumentos que no sea seguro para la memoria y la ruta de código que llega a él. Registra el comportamiento de los ID efectivos y las mitigaciones, como canarios de pila, memoria no ejecutable, código independiente de la posición y aleatorización de direcciones. El nombre de una función insegura o la ausencia de una mitigación solo justifican una revisión: la explotabilidad depende de los límites reales de entrada, del flujo de control alcanzable y de la identidad efectiva en el momento del fallo. Durante la enumeración pasiva, no envíes argumentos largos al ejecutable privilegiado activo solo para comprobar si se bloquea.

Un programa SUID conocido también puede haber sido reemplazado o tener una puerta trasera. Una hora de modificación reciente es un indicio, no una prueba: para un **binario empaquetado específico que resulte sospechoso**, averigua qué paquete lo contiene y compara el archivo instalado con los metadatos del paquete, en lugar de verificar todos los paquetes durante la enumeración rutinaria:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` comprueba el contenido de los archivos solo cuando la base de datos de paquetes tiene registrada una suma de comprobación; RPM también compara metadatos, como el modo y el propietario. Céntrate en las discrepancias del **ejecutable privilegiado en sí**: las instalaciones reducidas pueden informar de documentación o archivos de configuración regional que faltan en otras partes del mismo paquete. Compara el ejecutable sospechoso con un paquete de proveedor de confianza y revisa exactamente el código modificado. Los cambios locales legítimos, la ausencia de sumas de comprobación y los metadatos de paquetes comprometidos limitan lo que cualquiera de los dos comandos puede demostrar. No ejecutes el programa SUID sospechoso ni un script de verificación de paquetes como parte de un triage pasivo. Consulta el [manual de verificación de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) y el [manual de verificación de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programa SUID que invoque un shell, un comando relativo o una biblioteca desde una ruta con permisos de escritura puede cruzar un límite de confianza. Consulta [abuso de bibliotecas compartidas y del linker con SUID](suid-shared-library-and-linker-abuse.md), las [recomendaciones sobre PATH](../linux-basics/linux-environment-variables.md#path) y la [explicación de los ID de usuario](../user-information/euid-ruid-suid.md). Para escapes conocidos específicos de comandos, consulta [GTFOBins](https://gtfobins.github.io/) para el binario exacto y la invocación permitida en el host.

En un ejecutable set-user-ID, distingue el **UID real** del llamador del **UID efectivo** del propietario del archivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) deja sin cambios el UID real y copia el UID efectivo al UID guardado después de cualquier cambio set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) ejecuta su comando mediante `/bin/sh -c`; el shell seleccionado por esa ruta determina si un proceso hijo conserva su identidad efectiva. En particular, las [reglas del modo privilegiado de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) restablecen un UID efectivo distinto al UID real cuando Bash se inicia sin `-p`. Comprueba los cambios de UID reales del helper y cómo invoca procesos hijos, así como su propietario, el acceso de ejecución, la opción de montaje `nosuid` y el estado `no_new_privs` del proceso. Un bit SUID o una llamada al shell, por sí solos, no demuestran que se pueda realizar una transición a privilegios superiores.

Un `jjs` SUID inusual propiedad de root merece una revisión independiente del acceso a archivos si el usuario actual puede ejecutarlo. La herramienta Nashorn heredada puede acceder a las API de archivos de Java incluso cuando un shell iniciado como proceso hijo pierde el UID efectivo; confirma el comportamiento de la JVM instalada, la identidad efectiva de la operación de archivo y `nosuid`/`no_new_privs` antes de considerarlo una lectura o escritura privilegiada. [Oracle eliminó `jjs` en JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); una ruta instalada aún puede corresponder a una versión anterior o a una compilación empaquetada por separado. [GTFOBins documenta las API de archivos](https://gtfobins.org/gtfobins/jjs/), pero sus ejemplos con sudo no demuestran el comportamiento SUID en todas las compilaciones. No invoques la herramienta durante la enumeración pasiva.

Un ejecutable `gosu` SUID propiedad de root y accesible para un usuario con menos privilegios merece revisión: su interfaz documentada acepta un usuario objetivo y un comando, pero en el uso normal de contenedores se inicia como root para reducir privilegios. Verifica el comportamiento SUID de la compilación instalada, la identidad efectiva y la asignación de user namespaces, además de `nosuid` y `no_new_privs`; ser root dentro de un contenedor no implica serlo en el host. El nombre del archivo o el bit SUID, por sí solos, no demuestran que la transición funcione. Consulta el [uso en upstream](https://github.com/tianon/gosu) y la [advertencia sobre SUID del mantenedor](https://github.com/tianon/gosu/issues/11). No invoques el helper durante el inventario pasivo.

Un wrapper de backup personalizado con set-user-ID puede aceptar una ruta elegida por el llamador e interpolarla en un comando de archivado que se pasa a `system(3)`. Si la ruta no está entre comillas en el comando construido, el shell hijo puede aplicar [la expansión de tilde mediante `HOME`, patrones de nombres de ruta como `?` y `*`, y la separación de comandos por saltos de línea](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rechazar solo signos de puntuación habituales mediante una denylist no hace que la ruta se trate literalmente. Confirma el flujo exacto de argumentos, el entorno heredado, el shell hijo y la identidad efectiva, el acceso al sistema de archivos y si la salida del archivador es visible para el llamador. El bit SUID, una cadena de una herramienta de archivado o que se bloquee el literal `/root` no demuestran por sí solos ni la divulgación ni la ejecución de código. Revisa una copia del wrapper sin conexión, en lugar de archivar archivos privados o enviar entradas que provoquen fallos durante la enumeración pasiva.

La [sustitución de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) del shell, como `$(...)`, es otra posible brecha en una denylist de metacaracteres: incluso un prefijo de comando fijo permitido puede pasar un argumento posterior controlado por el llamador a `/bin/sh -c`. Verifica sin conexión las comillas exactas, el parser y la identidad efectiva; no consideres una cadena de `system()` o una denylist incompleta como prueba de ejecución.

También importa el **árbol de procesos llamador**. Un worker web puede instalar un filtro seccomp que restrinja las llamadas al sistema que cambian UID; los [filtros seccomp se heredan en los procesos hijos y sobreviven a `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por ejemplo, las directivas [`LimitUIDRange` y `LimitGIDRange` de mpm-itk de Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) pueden limitar las identidades a las que pueden acceder los descendientes. `Seccomp: 2` en `/proc/self/status` indica el modo del filtro, no la política ni si este helper en particular puede obtener la identidad de su propietario. Revisa conjuntamente la ascendencia de la invocación real y el filtro efectivo, además de las condiciones SUID, de montaje y `no_new_privs`; una sesión de inicio de sesión independiente puede tener otra política, pero requiere su propia vía de acceso válida.

Un ejecutable SUID personalizado puede invocar un script de Python independiente y legible. Si realmente usa Python **2**, [`input()` evalúa la expresión introducida](https://docs.python.org/2/library/functions.html#input); en Python 3, `input()` devuelve texto. Confirma la identidad efectiva del wrapper, la ruta y versión del intérprete, la ruta del script y si una entrada no confiable llega a esa llamada antes de considerar esa línea del código fuente como una vía de ejecución. Un bit set-ID en el propio script o una llamada a `input()` sin el wrapper privilegiado no establece el mismo límite. Revisa las rutas a las que hace referencia el binario y una copia acotada del código fuente del script sin ejecutarlo durante la enumeración.

Si hay código fuente legible junto a un ejecutable SUID inusual, compara el número de bytes solicitado en cada lectura de archivos controlada por el llamador con el tamaño del búfer de destino e inspecciona las comprobaciones posteriores del flujo de control. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) almacena los elementos solicitados en el puntero proporcionado; no conoce la capacidad del objeto de destino. Una discrepancia de tamaños es una pista estática de un problema de seguridad de memoria, no una prueba de que se pueda aprovechar para escalar privilegios: confirma que el código fuente corresponde al binario instalado, que el llamador puede proporcionar la entrada, que la ejecución SUID es efectiva en ese contexto y que se puede alcanzar la ruta pertinente. Revisa sin conexión una copia acotada del código fuente o del binario, en lugar de enviar entradas que provoquen fallos al programa privilegiado durante la enumeración.

Un helper SUID personalizado puede divulgar un archivo protegido sin imprimir su contenido. Si el llamador elige tanto una ruta como una expresión regular, y el helper devuelve un recuento de coincidencias visible bajo su UID efectivo, las pruebas de prefijo ancladas pueden formar un oráculo carácter por carácter. Confirma el propietario del helper, el comportamiento de su ID efectivo, el acceso de ejecución, las restricciones de ruta, la semántica de las expresiones regulares, la visibilidad de la respuesta y la existencia de un archivo específico con privilegios superiores que el llamador no pueda leer de otro modo. Un bit SUID o una cadena de una biblioteca de expresiones regulares no demuestran nada de ese flujo. Durante la enumeración pasiva, registra el ejecutable inusual y revisa una copia acotada del desensamblado o del código fuente; no pruebes iterativamente el helper activo ni imprimas secretos recuperados.

En OpenBSD, un lector personalizado set-user-ID que acepte una ruta elegida por el llamador puede exponer archivos de `/var/backups` si su identidad efectiva puede leerlos y devuelve su contenido al llamador. [`changelist(5)` de OpenBSD](https://man.openbsd.org/changelist.5) describe las copias `.current` y `.backup` de las rutas configuradas, pero las entradas con el prefijo `+` almacenan sumas de comprobación SHA-256 en vez del contenido de los archivos; el directorio de backup debería pertenecer a root y tener el modo `0700`. Una regla de lectura de [`unveil` para `/var`](https://man.openbsd.org/unveil.2) en un helper puede permitir el acceso bajo esa ruta, pero no concede ni demuestra por sí sola el acceso a archivos. Confirma el UID efectivo real, el permiso de ejecución para el usuario actual, la ruta aceptada, la existencia y el contenido del backup y cualquier requisito de autenticación independiente antes de afirmar que hay una escalada. La enumeración pasiva debe informar del helper y de los metadatos de la ruta, no invocar el lector ni imprimir datos del backup.

Un programa SUID personalizado que comprueba una ruta elegida por el llamador con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) y abre la ruta más tarde puede sufrir una condición de carrera si cambia un archivo o enlace simbólico en un directorio donde el llamador tiene permisos de escritura. La comprobación se aplica al objeto anterior, mientras que un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) posterior puede resolver otro objeto. Confirma que el helper se pueda ejecutar con identidad efectiva elevada, que una ruta de código alcanzable de otro modo lea el archivo seleccionado y que el llamador pueda reemplazar la ruta entre la comprobación y la apertura; un bit SUID, un directorio con permisos de escritura o una cadena `stat`, por sí solos, no demuestran nada de esto. Para que haya divulgación, también se necesita una salida visible o un destino legible por el llamador. Revisa sin conexión el binario y los metadatos de la ruta; no intentes provocar una condición de carrera en el helper activo durante la enumeración pasiva.

Aplica la misma revisión de dependencias a los wrappers SGID. Un wrapper que ejecuta un shell o un helper mediante una ruta absoluta aún puede ser inseguro si un usuario con menos privilegios puede reemplazar ese archivo; el código iniciado puede heredar el grupo efectivo del wrapper. Comprueba la ruta exacta invocada, sus permisos de escritura (incluidas las ACL), el grupo efectivo del wrapper y si este reduce los privilegios antes de iniciar el proceso hijo. Un intérprete también puede descartar los ID efectivos heredados, así que distingue entre un candidato para revisión y una transición demostrada. Que haya un shell con permisos de escritura en otro lugar del host no demuestra por sí solo que un wrapper privilegiado lo invoque.

### Wrappers privilegiados que pasan SQL a la CLI de SQLite

Si un programa SUID personalizado pasa SQL controlado por el usuario al **programa de línea de comandos `sqlite3`**, inspecciona el comando exacto y la identidad efectiva antes de considerar que la consulta es de solo lectura. La función SQL `edit()` de la CLI invoca un editor (indicado en su segundo argumento o en `VISUAL`), y su función SQL `load_extension()` puede cargar una biblioteca compartida cuando está habilitada la carga de extensiones. Estas son posibles vías de ejecución de código con la identidad del proceso de la CLI, aunque el wrapper fije `PATH` o utilice una ruta absoluta a `sqlite3`. El SQL debe llegar realmente a esas funciones y la CLI debe conservar la función pertinente; encontrar `sqlite3` en un binario o en el host no es evidencia de una escalada. La **biblioteca** de SQLite deshabilita la carga de extensiones de forma predeterminada, así que distínguela de la CLI. Si una aplicación privilegiada debe procesar SQL no confiable, el modo `--safe` de la CLI de SQLite deshabilita `edit()`, `load_extension()` y otras funciones con efectos secundarios. Consulta la [documentación de la CLI de SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentación del modo seguro](https://www.sqlite.org/cli.html#the_safe_command_line_option) y la [documentación sobre la carga de extensiones](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lectores de archivos privilegiados que alimentan un cliente verboso

Un wrapper SUID/SGID personalizado puede comprobar el acceso a una ruta elegida por el llamador y luego pasar ese archivo a otro comando. Revisa la identidad efectiva tanto durante la comprobación de acceso como en la apertura posterior, resuelve los componentes `../` con respecto al directorio base real e inspecciona cómo gestiona el proceso hijo las entradas no válidas. Si un cliente de base de datos lee un archivo privado como SQL con salida verbosa, puede repetir el contenido del archivo en los errores aunque el SQL no sea válido. Esto solo constituye una divulgación entre usuarios cuando el proceso hijo puede leer un archivo que el llamador no puede, el llamador puede seleccionar ese archivo a través del wrapper y la salida es visible; la presencia de `mysql` u otra cadena de cliente no demuestra por sí sola ninguna de estas condiciones.

### Ruta de búsqueda de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afectó a algunas compilaciones de Netdata `ndsudo`. El helper SUID propiedad de root buscaba los comandos externos permitidos usando un `PATH` proporcionado por el llamador. Revisa un helper instalado, incluso si está fuera del `PATH` habitual del llamador, solo cuando la cuenta actual pueda ejecutarlo. Confirma su propietario, el bit SUID, el acceso de ejecución (incluidas las concesiones de grupo/ACL), la compilación instalada y el estado de los parches del proveedor, y si `NoNewPrivs` o un montaje `nosuid` impide el cambio de identidad. Netdata indica que las compilaciones `v1.45.3` y `v1.45.0-169` tienen el parche; los backports de las distribuciones requieren una confirmación aparte. La versión del dashboard o la mera presencia de `ndsudo` no bastan para demostrar que exista una vía de escalada alcanzable. El problema de la ruta también requiere que el helper resuelva un comando externo a través de una ubicación controlada por el llamador.

### Límite de privilegios de Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afectó a la lógica privilegiada `--join` de Firejail: un destino de join manipulado podía hacer que el helper setuid-root aceptara un mount namespace controlado por un atacante y copiara un estado de seguridad no seguro. Para un triage pasivo, confirma que la **identidad actual pueda ejecutar** un binario Firejail setuid propiedad de root, que setuid sea efectivo en su montaje y en el contexto del proceso, y que la compilación instalada no incluya la corrección. Upstream corrigió el problema en [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); los paquetes de las distribuciones pueden [incluir el parche retroactivamente](https://github.com/netblue30/firejail/issues/5191) y seguir mostrando una versión anterior. Estos requisitos previos identifican un candidato para revisión, no un join exitoso ni un shell de root. No construyas una jail falsa ni invoques `--join` durante la enumeración.

### Permisos del archivo de registro de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) implicó que Screen 4.5.0 abriera un archivo de registro elegido por el llamador con privilegios elevados. Un binario `screen` o con la versión añadida al nombre en el inventario SUID es solo una pista para revisar: confirma la propiedad de root, la ejecución SUID efectiva para el usuario actual, la compilación instalada y el estado de los parches de la distribución, así como el comportamiento afectado del archivo de registro. [Debian corrigió su paquete 4.5.0 con un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), así que una cadena de versión o un nombre de archivo no demuestran por sí solos que haya exposición. No crees un archivo de registro como prueba rutinaria de enumeración.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afectó al helper privilegiado de bloqueo de correo de S-nail cuando un componente de ruta controlado por el llamador podía recorrer directorios y permitir la escritura arbitraria de archivos. Revisa si el usuario actual puede ejecutar un helper setuid instalado propiedad de root, si la identidad setuid es efectiva bajo las políticas del montaje y del proceso, y cuál es la compilación exacta del paquete y la corrección del proveedor. El [aviso de seguridad de Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) incluye una corrección retroactiva para su paquete de 16.04, así que una versión aparentemente de upstream no es concluyente. La presencia del helper no demuestra que se pueda alcanzar la ruta afectada ni que una escritura de archivo permita ejecutar código como root; inspecciona los metadatos y el estado del paquete sin invocar el helper ni intentar provocar la condición de carrera durante la enumeración.

### `snap-confine` y limpieza de tmpfiles

CVE-2026-3888 es una condición de carrera entre `snap-confine` privilegiado y la limpieza de `/tmp` por systemd-tmpfiles. Una revisión pasiva puede comprobar si `snap-confine` tiene el bit setuid o capabilities de archivo, comparar el paquete `snapd` instalado con la versión corregida para esa **versión de Ubuntu** e inspeccionar la regla de antigüedad efectiva de `/tmp` y el temporizador de limpieza. Que coincidan el paquete y la regla son requisitos previos, no una prueba de que se pueda provocar la condición de carrera: también importan el estado del temporizador en tiempo de ejecución, la disposición de snap, los backports del paquete y las anulaciones de reglas. Las versiones anteriores pueden requerir una configuración no predeterminada. No ejecutes una prueba de condición de carrera durante la enumeración rutinaria. Consulta el [registro CVE de Ubuntu](https://ubuntu.com/security/CVE-2026-3888) para conocer el estado de los paquetes de cada versión y el [aviso de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para entender la interacción entre los componentes.

## Inspeccionar ACL y rutas sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un directorio padre con permisos de escritura puede permitir reemplazar el archivo, aunque este pertenezca a root. Una ACL puede conceder acceso de forma inadvertida a un archivo drop-in de sudoers, una unidad de servicio, un script de cron, una ruta de bibliotecas o un archivo de credenciales. Comprueba tanto la ACL como la ruta completa. Si es posible escribir arbitrariamente en archivos privilegiados, consulta [Arbitrary File Write to Root](write-to-root.md); para casos de configuración del linker y preload, consulta el [ejemplo de `ld.so`](ld.so.conf-example.md). Considera las copias de seguridad expuestas, los archivos `.env`, las configuraciones de bases de datos, el material SSH y el historial como posibles fuentes de credenciales; el acceso depende de los permisos reales de cada archivo.
