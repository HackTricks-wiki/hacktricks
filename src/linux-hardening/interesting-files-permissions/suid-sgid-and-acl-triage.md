# SUID, SGID, ACL e file sensibili

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID modificano l’identità effettiva di un file eseguito; le ACL possono concedere accessi che i normali bit di permesso mostrati da `ls -l` non indicano. Esamina entrambi quando un utente può leggere, scrivere o eseguire più di quanto suggeriscano le autorizzazioni apparenti di proprietario e gruppo.

## Enumerare gli eseguibili privilegiati

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrati sugli eseguibili personalizzati o modificati di recente, sui proprietari insoliti e sui file presenti su mount scrivibili. Un mount `nosuid` può sopprimere il comportamento set-ID; le file capabilities sono un meccanismo di privilegio distinto, descritto in [Linux capabilities](linux-capabilities.md). Confronta un binario sospetto con il pacchetto a cui appartiene e verifica cosa esegue, apre o carica con un’identità elevata.

Per un eseguibile SUID di proprietà di root che non conosci e che accetta input dal chiamante, esamina offline una copia del binario per individuare una gestione degli argomenti non sicura per la memoria e il percorso del codice che la raggiunge. Registra il comportamento degli effective ID e le mitigazioni, come stack canary, memoria non eseguibile, codice position-independent e randomizzazione degli indirizzi. Il nome di una funzione non sicura o l’assenza di una mitigazione sono solo spunti per l’analisi: la possibilità di sfruttamento dipende dai limiti effettivi dell’input, dal flusso di controllo raggiungibile e dall’identità effettiva al momento dell’errore. Durante un’enumerazione passiva, non passare argomenti lunghi all’eseguibile privilegiato attivo solo per verificare se va in crash.

Anche un programma SUID noto può essere sostituito o compromesso. Una data di modifica recente è uno spunto, non una prova: per uno **specifico binario sospetto appartenente a un pacchetto**, individua il pacchetto proprietario e confronta il file installato con i metadati del pacchetto, anziché verificare ogni pacchetto durante la normale enumerazione:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` verifica i contenuti dei file solo quando il database dei pacchetti registra un checksum; RPM confronta anche metadati come modalità e proprietario. Concentrati sulle discrepanze dell’**eseguibile privilegiato stesso**: le installazioni ridotte possono segnalare documentazione o file di localizzazione mancanti altrove nello stesso pacchetto. Confronta un eseguibile sospetto con un pacchetto del fornitore attendibile ed esamina le modifiche esatte al codice. Modifiche locali legittime, checksum assenti e metadati dei pacchetti compromessi limitano ciò che ciascun comando può dimostrare. Nel triage passivo, non eseguire il programma SUID sospetto né uno script di verifica dei pacchetti. Vedi il [manuale di verifica di dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e il [manuale di verifica di RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programma SUID che richiama una shell, un comando relativo o una libreria da un percorso scrivibile può oltrepassare un confine di fiducia. Vedi [abuso di librerie condivise e linker con SUID](suid-shared-library-and-linker-abuse.md), le [indicazioni su PATH](../linux-basics/linux-environment-variables.md#path) e la [spiegazione degli user ID](../user-information/euid-ruid-suid.md). Per le escape note specifiche dei comandi, consulta [GTFOBins](https://gtfobins.github.io/) verificando il binario esatto e l’invocazione consentita sull’host.

Per un eseguibile set-user-ID, distingui il **real UID** del chiamante dall’**effective UID** del proprietario del file: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lascia invariato il real UID e, dopo ogni modifica set-ID, copia l’effective UID nel saved UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) esegue il comando tramite `/bin/sh -c`; la shell selezionata da quel percorso influisce sulla conservazione dell’identità effettiva da parte di un processo figlio. In particolare, le [regole della modalità privilegiata di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) reimpostano un effective UID diverso sul real UID quando Bash si avvia senza `-p`. Esamina le modifiche agli UID dell’helper effettivo e l’invocazione del processo figlio, insieme al proprietario, ai permessi di esecuzione, all’opzione di mount `nosuid` e allo stato `no_new_privs` del processo. Il bit SUID o una chiamata a una shell, da soli, non dimostrano una transizione utilizzabile a privilegi superiori.

Un `jjs` SUID insolito di proprietà di root merita una verifica separata dell’accesso ai file, se l’utente corrente può eseguirlo. Il vecchio strumento Nashorn può accedere alle API Java per i file anche se una shell avviata come processo figlio perde un effective UID; prima di considerarlo una lettura o scrittura privilegiata, verifica il comportamento della JVM installata, l’identità effettiva dell’operazione sul file e le opzioni `nosuid`/`no_new_privs`. [Oracle ha rimosso `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); il percorso installato potrebbe comunque corrispondere a una build precedente o distribuita separatamente. [GTFOBins documenta le API per i file](https://gtfobins.org/gtfobins/jjs/), ma i suoi esempi con sudo non dimostrano il comportamento SUID per ogni build. Non invocare lo strumento durante l’enumerazione passiva.

Un eseguibile `gosu` SUID di proprietà di root e accessibile a un utente con privilegi inferiori merita un’analisi: la sua interfaccia documentata accetta un utente di destinazione e un comando, ma nell’uso normale nei container viene avviato da root per ridurre i privilegi. Verifica il comportamento SUID della build installata, l’identità effettiva e la mappatura degli user namespace, oltre a `nosuid` e `no_new_privs`; root nel container non implica root sull’host. Il nome del file o il bit SUID, da soli, non dimostrano una transizione funzionante. Vedi [l’uso documentato a monte](https://github.com/tianon/gosu) e l’[avviso SUID del manutentore](https://github.com/tianon/gosu/issues/11). Non invocare l’helper durante l’inventario passivo.

Un wrapper di backup personalizzato set-user-ID potrebbe accettare un percorso scelto dal chiamante e interpolarlo in un comando di archiviazione passato a `system(3)`. Se il percorso non è racchiuso tra virgolette nel comando costruito, la shell figlia può applicare [l’espansione della tilde usando `HOME`, i pattern di percorso come `?` e `*` e la separazione dei comandi con newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rifiutare solo la punteggiatura più comune con una denylist non rende letterale il percorso. Verifica il flusso esatto degli argomenti, l’ambiente ereditato, la shell figlia e l’identità effettiva, l’accesso al filesystem e la visibilità dell’output dell’archiviazione per il chiamante. Il bit SUID, una stringa che indica uno strumento di archiviazione o il solo rifiuto di un percorso letterale `/root` non dimostrano né divulgazione né esecuzione di codice. Durante l’enumerazione passiva, esamina offline una copia del wrapper invece di archiviare file privati o inviargli input che causino un crash.

La [sostituzione di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) della shell, come `$(...)`, è un’altra possibile lacuna in una denylist dei metacaratteri: anche un prefisso di comando consentito e fisso può passare un argomento successivo controllato dal chiamante a `/bin/sh -c`. Verifica offline le virgolette, il parser e l’identità effettiva esatti; non considerare una stringa `system()` o una denylist incompleta, da sole, una prova di esecuzione.

Conta anche l’**albero dei processi chiamanti**. Un worker web può installare un filtro seccomp che limita le system call per la modifica degli UID; [i filtri seccomp vengono ereditati dai processi figli e persistono dopo `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Per esempio, le direttive [mpm-itk `LimitUIDRange` e `LimitGIDRange` di Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) possono limitare le identità accessibili ai processi discendenti. `Seccomp: 2` in `/proc/self/status` indica la modalità del filtro, non la sua policy né se questo specifico helper possa ottenere l’identità del proprietario. Esamina insieme l’ascendenza dell’invocazione effettiva, il filtro effettivo e le condizioni SUID, di mount e `no_new_privs`; una sessione di login separata può avere una policy diversa, ma richiede un proprio percorso di accesso valido.

Un eseguibile SUID personalizzato potrebbe richiamare uno script Python separato e leggibile. Se usa davvero **Python 2**, [`input()` valuta l’espressione inserita](https://docs.python.org/2/library/functions.html#input); in Python 3, `input()` restituisce invece testo. Prima di considerare la riga di codice un percorso di esecuzione, verifica l’identità effettiva del wrapper, il percorso e la versione dell’interprete, il percorso dello script e se l’input non attendibile raggiunge quella chiamata. Un bit set-ID applicato allo script stesso, o una chiamata a `input()` senza il wrapper privilegiato, non crea lo stesso confine. Durante l’enumerazione, esamina i percorsi a cui fa riferimento il binario e una porzione limitata del sorgente dello script, senza eseguirlo.

Se un eseguibile SUID insolito è accompagnato da codice sorgente leggibile, confronta il numero di byte richiesti da ogni lettura di file controllata dal chiamante con la dimensione del buffer di destinazione ed esamina i controlli successivi nel flusso di controllo. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) scrive gli elementi richiesti all’indirizzo fornito; non conosce la capacità dell’oggetto di destinazione. Una differenza di dimensioni è un indizio statico di un problema di sicurezza della memoria, non la prova di un’escalation di privilegi utilizzabile: verifica che il sorgente corrisponda al binario installato, che il chiamante possa fornire l’input, che l’esecuzione SUID sia effettiva in quel contesto e che il percorso pertinente sia raggiungibile. Durante l’enumerazione, esamina offline una porzione limitata del sorgente o una copia del binario, invece di inviare input che causino un crash al programma privilegiato.

Un helper SUID personalizzato può divulgare un file protetto senza stamparne il contenuto. Se il chiamante sceglie sia un percorso sia un’espressione regolare, e l’helper restituisce un conteggio delle corrispondenze visibile, i test ancorati al prefisso possono formare un oracolo carattere per carattere. Verifica il proprietario dell’helper, il comportamento degli ID effettivi, i permessi di esecuzione, le restrizioni sui percorsi, la semantica delle espressioni regolari, la visibilità della risposta e l’esistenza di un file specifico con privilegi superiori che il chiamante non può leggere altrimenti. Il bit SUID o una stringa relativa a una libreria regex, da soli, non dimostrano questo flusso. Durante l’enumerazione passiva, annota l’eseguibile insolito ed esamina offline una disassemblazione limitata o una copia del sorgente; non provare ripetutamente valori con l’helper attivo né stampare segreti recuperati.

Su OpenBSD, un reader personalizzato set-user-ID che accetta un percorso scelto dal chiamante potrebbe esporre file in `/var/backups` se l’identità effettiva può leggerli e l’helper ne restituisce il contenuto al chiamante. [`changelist(5)` di OpenBSD](https://man.openbsd.org/changelist.5) descrive le copie `.current` e `.backup` dei percorsi configurati, ma le voci precedute da `+` contengono checksum SHA-256 anziché i contenuti dei file; la directory di backup dovrebbe appartenere a root e avere modalità `0700`. Una regola di lettura [`unveil` dell’helper](https://man.openbsd.org/unveil.2) per `/var` può consentire l’accesso ai percorsi sottostanti, ma non concede né dimostra di per sé l’accesso ai file. Prima di dichiarare un’escalation, verifica l’UID effettivo, i permessi di esecuzione per l’utente corrente, il percorso accettato, l’esistenza e il contenuto del backup e gli eventuali requisiti di autenticazione indipendenti. L’enumerazione passiva dovrebbe riportare l’helper e i metadati dei percorsi, non invocare il reader né stampare i dati di backup.

Un programma SUID personalizzato che controlla un percorso scelto dal chiamante con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e in seguito lo apre può essere soggetto a una race condition se un file o un symlink cambia in una directory scrivibile dal chiamante. Il controllo riguarda l’oggetto precedente, mentre una successiva [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) potrebbe risolverne uno diverso. Verifica che l’helper sia eseguibile con un’identità effettiva elevata, che un percorso del codice altrimenti raggiungibile legga il file selezionato e che il chiamante possa sostituire il percorso tra il controllo e l’apertura; il bit SUID, una directory scrivibile o una stringa `stat`, da soli, non dimostrano nessuna di queste condizioni. Perché si configuri una divulgazione, serve anche un output visibile o una destinazione leggibile dal chiamante. Esamina offline il binario e i metadati del percorso; durante l’enumerazione passiva, non tentare una race condition con l’helper attivo.

Applica la stessa verifica delle dipendenze ai wrapper SGID. Un wrapper che avvia una shell o un helper tramite un percorso assoluto può comunque essere insicuro se un utente con privilegi inferiori può sostituire quel file; il codice avviato potrebbe ereditare il gruppo effettivo del wrapper. Controlla il percorso esatto invocato, i relativi permessi di scrittura (incluse le ACL), il gruppo effettivo del wrapper e se questo riduce i privilegi prima di avviare il processo figlio. Anche un interprete può scartare gli ID effettivi ereditati, quindi distingui un elemento da esaminare da una transizione dimostrata. La presenza di una shell scrivibile altrove sull’host non dimostra, da sola, che un wrapper privilegiato la richiami.

### Wrapper privilegiati che passano SQL alla CLI di SQLite

Se un programma SUID personalizzato passa SQL controllato dall’utente al **programma a riga di comando `sqlite3`**, esamina il comando esatto e l’identità effettiva prima di considerare la query di sola lettura. La funzione SQL `edit()` della CLI richiama un editor (specificato come secondo argomento o tramite `VISUAL`) e la funzione SQL `load_extension()` può caricare una libreria condivisa se il caricamento delle estensioni è abilitato. Questi sono potenziali percorsi di esecuzione di codice con l’identità del processo CLI, anche se il wrapper imposta `PATH` o usa un percorso assoluto per `sqlite3`. Perché il rischio si concretizzi, l’SQL deve raggiungere effettivamente quelle funzioni e la CLI deve mantenere la funzionalità pertinente; trovare `sqlite3` in un binario o sull’host non prova un’escalation. La **libreria** SQLite disabilita per impostazione predefinita il caricamento delle estensioni, quindi va distinta dalla CLI. Se un’applicazione privilegiata deve elaborare SQL non attendibile, la modalità `--safe` della CLI di SQLite disabilita `edit()`, `load_extension()` e altre funzioni con effetti collaterali. Vedi la [documentazione della CLI di SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentazione della modalità sicura](https://www.sqlite.org/cli.html#the_safe_command_line_option) e la [documentazione sul caricamento delle estensioni](https://www.sqlite.org/loadext.html#loading_an_extension).

### Reader privilegiati di file che alimentano un client verboso

Un wrapper SUID/SGID personalizzato potrebbe controllare l’accesso a un percorso scelto dal chiamante e poi passare quel file a un altro comando. Esamina l’identità effettiva durante il controllo dell’accesso e l’apertura successiva, risolvi eventuali componenti `../` rispetto alla directory di base reale e controlla come il processo figlio gestisce gli input non validi. Se un client di database legge come SQL un file privato e produce output dettagliato, potrebbe riprodurne il contenuto nei messaggi di errore anche se l’SQL non è valido. Si tratta di una divulgazione tra utenti solo se il processo figlio può leggere un file che il chiamante non può leggere, il chiamante può selezionare quel file tramite il wrapper e l’output è visibile; la sola presenza di `mysql` o di un’altra stringa relativa a un client non dimostra nessuna di queste condizioni.

### Percorso di ricerca di Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ha interessato alcune build di Netdata `ndsudo`. L’helper SUID di proprietà di root cercava i comandi esterni consentiti usando un `PATH` fornito dal chiamante. Esamina un helper installato, anche se si trova fuori dal `PATH` abituale del chiamante, solo se l’account corrente può eseguirlo. Verifica il proprietario, il bit SUID, i permessi di esecuzione (inclusi i permessi concessi da gruppi/ACL), la build installata e lo stato delle patch del fornitore, nonché se `NoNewPrivs` o un mount `nosuid` blocca il cambio di identità. Netdata indica come corrette le build `v1.45.3` e `v1.45.0-169`; i backport delle distribuzioni richiedono una verifica separata. La versione mostrata nella dashboard o la sola presenza di `ndsudo` non sono prove sufficienti di un’escalation raggiungibile. Il problema del percorso richiede inoltre che l’helper risolva un comando esterno tramite una posizione controllata dal chiamante.

### Confine di privilegio di Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ha interessato la logica privilegiata `--join` di Firejail: un target di join appositamente costruito poteva far accettare all’helper setuid-root un mount namespace controllato da un attaccante e copiare uno stato di sicurezza non sicuro. Per il triage passivo, verifica che l’**identità corrente possa eseguire** un binario Firejail setuid di proprietà di root, che setuid sia effettivo sul relativo mount e nel contesto del processo e che la build installata non includa la correzione. Il progetto ha corretto il problema nella versione [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); i pacchetti delle distribuzioni potrebbero [aver applicato un backport](https://github.com/netblue30/firejail/issues/5191) pur mostrando una versione precedente. Questi prerequisiti identificano un caso da esaminare, non dimostrano un join riuscito o l’ottenimento di una shell root. Durante l’enumerazione non creare una jail falsa né invocare `--join`.

### Permessi del file di log di GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) riguardava Screen 4.5.0 che apriva con privilegi elevati un file di log scelto dal chiamante. Un binario `screen`, o con la versione nel nome, nell’inventario SUID è solo un indizio da esaminare: verifica la proprietà di root, l’effettiva esecuzione SUID per l’utente corrente, la build installata, lo stato delle patch della distribuzione e il comportamento interessato del file di log. [Debian ha corretto il pacchetto 4.5.0 con un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), quindi una stringa di versione o il solo nome del file non dimostrano l’esposizione. Non creare un file di log come sonda di routine durante l’enumerazione.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ha interessato l’helper privilegiato S-nail per i lock della posta, quando un componente di percorso controllato dal chiamante poteva attraversare directory e causare la scrittura arbitraria di un file. Verifica se l’utente corrente può eseguire un helper setuid installato e di proprietà di root, se l’identità setuid è effettiva secondo le policy di mount e di processo e qual è la build esatta del pacchetto e la correzione del fornitore. L’[avviso di sicurezza di Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) elenca una correzione backport per il pacchetto 16.04, quindi una versione che sembra quella a monte non è conclusiva. La presenza dell’helper non dimostra che il percorso interessato sia raggiungibile o che la scrittura di un file consenta l’esecuzione come root; durante l’enumerazione, esamina metadati e stato del pacchetto senza invocare l’helper né tentare la race condition.

### Pulizia di snap-confine e tmpfiles

CVE-2026-3888 è una race condition che coinvolge `snap-confine` privilegiato e la pulizia di `/tmp` da parte di systemd-tmpfiles. Una verifica passiva può controllare se `snap-confine` è setuid o dispone di file capabilities, confrontare il pacchetto `snapd` installato con la versione corretta per quella **release di Ubuntu** ed esaminare la regola effettiva per l’età dei file in `/tmp` e il timer di pulizia. La corrispondenza del pacchetto e della regola è un prerequisito, non la prova che la race condition sia raggiungibile: contano anche lo stato runtime del timer, il layout di snap, i backport dei pacchetti e le sostituzioni della regola. Le release meno recenti potrebbero richiedere una configurazione non predefinita. Durante l’enumerazione di routine, non eseguire una sonda per la race condition. Consulta la [scheda CVE di Ubuntu](https://ubuntu.com/security/CVE-2026-3888) per lo stato dei pacchetti specifico della release e l’[avviso di Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) per l’interazione tra i componenti.

## Esaminare ACL e percorsi sensibili

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Una directory padre scrivibile può consentire la sostituzione anche quando il file appartiene a root. Una ACL può concedere silenziosamente l’accesso a un file aggiuntivo di sudoers, a un’unità di servizio, a uno script cron, a un percorso di libreria o a un file di credenziali. Controlla sia l’ACL sia l’intero percorso. Se sono possibili scritture arbitrarie su file privilegiati, consulta [Arbitrary File Write to Root](write-to-root.md); per i casi relativi alla configurazione del linker e al preload, vedi l’[esempio `ld.so`](ld.so.conf-example.md). Considera backup esposti, file `.env`, configurazioni di database, materiale SSH e cronologia come possibili fonti di credenziali; l’accesso dipende dai permessi effettivi di ciascun file.
