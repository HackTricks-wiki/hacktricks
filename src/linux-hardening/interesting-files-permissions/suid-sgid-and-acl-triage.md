# SUID, SGID, ACLs und sensible Dateien

{{#include ../../banners/hacktricks-training.md}}

SUID und SGID ändern die effektive Identität einer ausgeführten Datei; ACLs können Zugriff gewähren, der in den gewöhnlichen Modusbits von `ls -l` nicht angezeigt wird. Überprüfe beides, wenn ein Benutzer mehr lesen, schreiben oder ausführen kann, als die scheinbaren Berechtigungen für Eigentümer und Gruppe vermuten lassen.

## Privilegierte ausführbare Dateien auflisten

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Konzentriere dich auf benutzerdefinierte oder kürzlich geänderte ausführbare Dateien, ungewöhnliche Eigentümer und Dateien auf beschreibbaren Mounts. Ein `nosuid`-Mount kann das set-ID-Verhalten unterdrücken; file capabilities sind ein separater Privilegienmechanismus, der unter [Linux capabilities](linux-capabilities.md) beschrieben wird. Vergleiche ein verdächtiges Binary mit dem zugehörigen Paket und prüfe, was es mit erhöhter Identität ausführt, öffnet oder lädt.

Bei einer unbekannten, root-eigenen SUID-ausführbaren Datei, die Eingaben des Aufrufers akzeptiert, untersuche offline eine Kopie des Binaries auf speicherunsichere Verarbeitung von Argumenten und den Codepfad, der diese erreicht. Halte das Verhalten der effektiven ID und Schutzmaßnahmen wie stack canaries, nicht ausführbaren Speicher, position-independent code und address randomization fest. Ein unsicherer Funktionsname oder eine fehlende Schutzmaßnahme ist lediglich ein Ansatzpunkt für die Untersuchung: Ob die Datei ausnutzbar ist, hängt von den tatsächlichen Eingabegrenzen, dem erreichbaren Kontrollfluss und der effektiven Identität zum Zeitpunkt des Fehlers ab. Sende bei einer passiven Bestandsaufnahme keine langen Argumente an die aktive privilegierte ausführbare Datei, nur um einen Absturz zu testen.

Auch ein bekanntes SUID-Programm kann ersetzt oder mit einer Hintertür versehen worden sein. Ein kürzliches Änderungsdatum ist ein Ansatzpunkt, kein Beweis: Ermittle bei einer **bestimmten verdächtigen, paketverwalteten ausführbaren Datei** das zugehörige Paket und vergleiche die installierte Datei mit den Paketmetadaten, anstatt bei der routinemäßigen Bestandsaufnahme jedes Paket zu überprüfen:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` prüft Dateiinhalte nur dort, wo die Paketdatenbank eine Prüfsumme gespeichert hat; RPM vergleicht auch Metadaten wie Modus und Eigentümer. Achten Sie auf Abweichungen bei der **privilegierten ausführbaren Datei selbst**: Bei Installationen ohne bestimmte Dateien kann die Prüfung fehlende Dokumentations- oder Sprachdateien an anderer Stelle im selben Paket melden. Vergleichen Sie eine verdächtige ausführbare Datei mit einem vertrauenswürdigen Herstellerpaket und prüfen Sie den genauen geänderten Code. Legitime lokale Änderungen, fehlende Prüfsummen und kompromittierte Paketmetadaten schränken die Aussagekraft beider Befehle ein. Führen Sie bei einer passiven Triage weder das verdächtige SUID-Programm noch ein Paketverifizierungsskript aus. Siehe das [Handbuch zur dpkg-Verifizierung](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) und das [Handbuch zur RPM-Verifizierung](https://rpm.org/docs/4.20.x/man/rpm.8).

Ein SUID-Programm, das eine Shell, einen relativen Befehl oder eine Bibliothek aus einem beschreibbaren Pfad aufruft, kann eine Vertrauensgrenze überschreiten. Siehe [Missbrauch von SUID-Bibliotheken und Linkern](suid-shared-library-and-linker-abuse.md), die [PATH-Hinweise](../linux-basics/linux-environment-variables.md#path) und die [Erklärung zu Benutzer-IDs](../user-information/euid-ruid-suid.md). Bei bekannten befehlsspezifischen Auswegen prüfen Sie [GTFOBins](https://gtfobins.github.io/) anhand der genauen Binärdatei und des Aufrufs, die auf dem Host zulässig sind.

Bei einer Set-User-ID-Datei müssen Sie die **reale UID** des Aufrufers von der **effektiven UID** des Dateieigentümers unterscheiden: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lässt die reale UID unverändert und kopiert nach einer Set-ID-Änderung die effektive UID in die gespeicherte UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) führt seinen Befehl über `/bin/sh -c` aus; die über diesen Pfad ausgewählte Shell beeinflusst, ob ein Kindprozess seine effektive Identität behält. Insbesondere setzen die [Bash-Regeln für den privilegierten Modus](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) eine abweichende effektive UID auf die reale UID zurück, wenn Bash ohne `-p` startet. Prüfen Sie die UID-Änderungen und den Aufruf von Kindprozessen im tatsächlichen Hilfsprogramm sowie dessen Eigentümer, Ausführungszugriff, den `nosuid`-Mount-Status und den `no_new_privs`-Status des Prozesses. Ein SUID-Bit oder Shell-Aufruf allein belegt keinen nutzbaren Übergang zu höheren Privilegien.

Ein ungewöhnliches, root-eigenes SUID-`jjs` verdient eine separate Prüfung des Dateizugriffs, wenn der aktuelle Benutzer es ausführen kann. Das veraltete Nashorn-Tool kann auf Java-Datei-APIs zugreifen, selbst wenn eine gestartete Shell eine effektive UID verliert; bestätigen Sie das Verhalten der installierten JVM, die effektive Identität des Dateivorgangs sowie `nosuid`/`no_new_privs`, bevor Sie von einem privilegierten Lese- oder Schreibzugriff ausgehen. [Oracle hat `jjs` in JDK 15 entfernt](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); ein installierter Pfad kann dennoch auf einen älteren oder separat paketierten Build verweisen. [GTFOBins dokumentiert die Datei-APIs](https://gtfobins.org/gtfobins/jjs/), aber die sudo-Beispiele belegen nicht das SUID-Verhalten jedes Builds. Rufen Sie das Tool während der passiven Bestandsaufnahme nicht auf.

Ein root-eigenes SUID-`gosu`, das für einen Benutzer mit geringeren Privilegien zugänglich ist, sollte überprüft werden: Die dokumentierte Schnittstelle akzeptiert einen Zielbenutzer und einen Befehl, aber im normalen Containerbetrieb wird es als root gestartet, um Privilegien abzugeben. Überprüfen Sie das SUID-Verhalten des installierten Builds, die effektive Identität und die Zuordnung im User-Namespace sowie `nosuid` und `no_new_privs`; root im Container bedeutet nicht root auf dem Host. Ein Dateiname oder SUID-Bit allein beweist keinen funktionierenden Übergang. Siehe die [Upstream-Verwendung](https://github.com/tianon/gosu) und den [SUID-Warnhinweis des Maintainers](https://github.com/tianon/gosu/issues/11). Rufen Sie das Hilfsprogramm während der passiven Bestandsaufnahme nicht auf.

Ein benutzerdefinierter Set-User-ID-Backup-Wrapper akzeptiert möglicherweise einen vom Aufrufer gewählten Pfad und fügt ihn in einen an `system(3)` übergebenen Archivbefehl ein. Wenn dieser Pfad im erstellten Befehl nicht in Anführungszeichen gesetzt ist, kann die Kind-Shell [Tilde-Erweiterung anhand von `HOME`, Pfadnamensmuster wie `?` und `*` sowie die Befehlsaufteilung an Zeilenumbrüchen](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) anwenden; nur bekannte Satzzeichen mit einer Denylist zurückzuweisen, macht den Pfad nicht zu einem Literal. Bestätigen Sie den genauen Argumentfluss, die geerbte Umgebung, die Kind-Shell und deren effektive Identität, den Dateisystemzugriff sowie, ob die Archivausgabe für den Aufrufer sichtbar ist. Das SUID-Bit, eine Zeichenfolge für ein Archivierungsprogramm oder ein blockiertes `/root`-Literal belegt für sich weder Offenlegung noch Codeausführung. Prüfen Sie eine Kopie des Wrappers offline, statt bei einer passiven Bestandsaufnahme private Dateien zu archivieren oder Absturzeingaben zu senden.

Shell-[Befehlssubstitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) wie `$(...)` ist eine weitere mögliche Lücke in einer Metazeichen-Denylist: Selbst ein festes, erlaubtes Befehlspräfix kann ein späteres, vom Aufrufer kontrolliertes Argument über `/bin/sh -c` weiterreichen. Überprüfen Sie die genaue Quotierung, den Parser und die effektive Identität offline; betrachten Sie eine `system()`-Zeichenfolge oder eine unvollständige Denylist nicht allein als Beweis für Codeausführung.

Auch der **Prozessbaum des aufrufenden Prozesses** ist wichtig. Ein Web-Worker kann einen seccomp-Filter installieren, der Systemaufrufe zur Änderung der UID einschränkt; [seccomp-Filter werden an Kindprozesse weitergegeben und bleiben über `execve` hinweg erhalten](https://docs.kernel.org/userspace-api/seccomp_filter.html). Beispielsweise können die Apache-Direktiven [mpm-itk `LimitUIDRange` und `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) die Identitäten einschränken, die Nachfolgeprozesse annehmen können. `Seccomp: 2` in `/proc/self/status` zeigt den Filtermodus, nicht die Richtlinie oder ob dieses bestimmte Hilfsprogramm die Identität seines Eigentümers annehmen kann. Überprüfen Sie gemeinsam die Aufrufhierarchie und den effektiven Filter des tatsächlichen Aufrufs sowie die SUID-, Mount- und `no_new_privs`-Bedingungen; eine separate Anmeldesitzung kann einer anderen Richtlinie unterliegen, benötigt aber einen eigenen gültigen Zugriffsweg.

Ein benutzerdefiniertes SUID-Programm kann ein separates, lesbares Python-Skript aufrufen. Wenn es tatsächlich Python **2** verwendet, [wertet `input()` den eingegebenen Ausdruck aus](https://docs.python.org/2/library/functions.html#input); `input()` in Python 3 gibt stattdessen Text zurück. Bestätigen Sie die effektive Identität des Wrappers, den Interpreterpfad und die Version, den Skriptpfad sowie, ob nicht vertrauenswürdige Eingaben diesen Aufruf erreichen, bevor Sie die Quellcodezeile als Ausführungspfad betrachten. Ein Set-ID-Bit auf dem Skript selbst oder ein `input()`-Aufruf ohne den privilegierten Wrapper schafft nicht dieselbe Vertrauensgrenze. Prüfen Sie die referenzierten Pfade der Binärdatei und eine begrenzte Skriptquelle, ohne sie während der Bestandsaufnahme auszuführen.

Wenn eine lesbare Quelle zu einer ungewöhnlichen SUID-ausführbaren Datei gehört, vergleichen Sie bei jedem vom Aufrufer kontrollierten Dateizugriff die angeforderte Byteanzahl mit der Größe des Zielpuffers und untersuchen Sie nachfolgende Kontrollflussprüfungen. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) speichert die angeforderten Elemente an dem übergebenen Zeiger; die Funktion kennt die Kapazität des Zielobjekts nicht. Eine Größenabweichung ist ein Hinweis auf ein mögliches Speicherfehlerproblem, aber kein Beweis für eine nutzbare Rechteausweitung: Bestätigen Sie, dass die Quelle zur installierten Binärdatei passt, der Aufrufer die Eingabe bereitstellen kann, die SUID-Ausführung in diesem Kontext wirksam ist und der relevante Pfad erreichbar ist. Prüfen Sie eine begrenzte Quell- oder Binärdateikopie offline, statt bei der Bestandsaufnahme Absturzeingaben an das privilegierte Programm zu senden.

Ein benutzerdefiniertes SUID-Hilfsprogramm kann eine geschützte Datei offenlegen, ohne deren Inhalt auszugeben. Wenn der Aufrufer sowohl einen Pfadnamen als auch einen regulären Ausdruck festlegt und das Hilfsprogramm eine sichtbare Anzahl von Treffern mit seiner effektiven UID zurückgibt, können verankerte Präfixtests als zeichenweiser Orakelzugriff dienen. Bestätigen Sie den Eigentümer des Hilfsprogramms, das Verhalten seiner effektiven ID, den Ausführungszugriff, Pfadnamenbeschränkungen, die Regex-Semantik, die Sichtbarkeit der Antwort und eine konkrete Datei mit höheren Privilegien, die der Aufrufer nicht anderweitig lesen kann. Ein SUID-Bit oder eine Zeichenfolge für eine Regex-Bibliothek allein belegt keinen dieser Abläufe. Notieren Sie bei der passiven Bestandsaufnahme die ungewöhnliche ausführbare Datei und prüfen Sie eine begrenzte Disassemblierung oder Quellkopie; führen Sie keine iterativen Versuche gegen das aktive Hilfsprogramm aus und geben Sie keine wiederhergestellten Geheimnisse aus.

Unter OpenBSD kann ein benutzerdefinierter Set-User-ID-Dateileser, der einen vom Aufrufer gewählten Pfadnamen akzeptiert, Dateien unter `/var/backups` offenlegen, wenn seine effektive Identität diese lesen kann und er ihren Inhalt an den Aufrufer zurückgibt. [OpenBSDs `changelist(5)`](https://man.openbsd.org/changelist.5) beschreibt `.current`- und `.backup`-Kopien konfigurierter Pfade; Einträge mit vorangestelltem `+` speichern jedoch SHA-256-Prüfsummen statt Dateiinhalte. Das Backup-Verzeichnis sollte root-eigen sein und den Modus `0700` haben. Eine [`unveil`-Leseregel](https://man.openbsd.org/unveil.2) des Hilfsprogramms für `/var` kann den Zugriff auf Pfade darunter erlauben, gewährt oder belegt aber für sich keinen Dateizugriff. Bestätigen Sie die tatsächliche effektive UID, die Ausführungsberechtigung für den aktuellen Benutzer, den akzeptierten Pfad, das Vorhandensein und den Inhalt des Backups sowie etwaige unabhängige Authentifizierungsanforderungen, bevor Sie eine Rechteausweitung behaupten. Die passive Bestandsaufnahme sollte das Hilfsprogramm und die Pfadmetadaten dokumentieren, nicht den Leser aufrufen oder Backup-Daten ausgeben.

Ein benutzerdefiniertes SUID-Programm, das einen vom Aufrufer gewählten Pfadnamen mit [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) prüft und den Pfad später öffnet, kann durch eine Änderung einer Datei oder eines Symlinks in einem vom Aufrufer beschreibbaren Verzeichnis einem Race unterliegen. Die Prüfung gilt für das frühere Objekt, während ein späteres [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ein anderes auflösen kann. Bestätigen Sie, dass das Hilfsprogramm mit erhöhter effektiver Identität ausführbar ist, ein anderweitig erreichbarer Codepfad die ausgewählte Datei liest und der Aufrufer den Pfadnamen zwischen Prüfung und Öffnen ersetzen kann; ein SUID-Bit, ein beschreibbares Verzeichnis oder eine `stat`-Zeichenfolge allein belegt nichts davon. Für einen Offenlegungspfad ist außerdem eine sichtbare Ausgabe oder ein für den Aufrufer lesbares Ziel erforderlich. Prüfen Sie die Binärdatei und Pfadmetadaten offline; verursachen Sie bei der passiven Bestandsaufnahme kein Race mit dem aktiven Hilfsprogramm.

Führen Sie dieselbe Abhängigkeitsprüfung bei SGID-Wrappern durch. Ein Wrapper, der eine Shell oder ein Hilfsprogramm über einen absoluten Pfad startet, kann dennoch unsicher sein, wenn ein Benutzer mit geringeren Privilegien diese Datei ersetzen kann; der gestartete Code erbt möglicherweise die effektive Gruppe des Wrappers. Prüfen Sie den genau aufgerufenen Pfad, dessen Schreibberechtigungen (einschließlich ACLs), die effektive Gruppe des Wrappers und ob dieser Privilegien abgibt, bevor er den Kindprozess startet. Ein Interpreter kann geerbte effektive IDs ebenfalls verwerfen; unterscheiden Sie daher einen Prüfungsansatz von einem nachgewiesenen Übergang. Eine beschreibbare Shell an anderer Stelle auf dem Host beweist allein nicht, dass ein privilegierter Wrapper sie aufruft.

### Privilegierte Wrapper, die SQL an die SQLite-CLI übergeben

Wenn ein benutzerdefiniertes SUID-Programm benutzerkontrolliertes SQL an das **`sqlite3`-Kommandozeilenprogramm** übergibt, prüfen Sie den genauen Befehl und die effektive Identität, bevor Sie die Abfrage als schreibgeschützt betrachten. Die SQL-Funktion `edit()` der CLI ruft einen Editor auf (aus dem zweiten Argument oder `VISUAL`), und ihre SQL-Funktion `load_extension()` kann eine Shared Library laden, wenn das Laden von Erweiterungen aktiviert ist. Dies sind mögliche Codeausführungspfade mit der Identität des CLI-Prozesses, selbst wenn der Wrapper `PATH` festlegt oder einen absoluten Pfad zu `sqlite3` verwendet. Das SQL muss diese Funktionen tatsächlich erreichen, und die CLI muss die betreffende Funktion weiterhin unterstützen; `sqlite3` lediglich in einer Binärdatei oder auf dem Host zu finden, belegt keine Rechteausweitung. Die SQLite-**Bibliothek** deaktiviert das Laden von Erweiterungen standardmäßig; unterscheiden Sie sie von der CLI. Wenn eine privilegierte Anwendung nicht vertrauenswürdiges SQL verarbeiten muss, deaktiviert der CLI-`--safe`-Modus von SQLite `edit()`, `load_extension()` und andere Funktionen mit Nebenwirkungen. Siehe die [SQLite-CLI-Dokumentation](https://www.sqlite.org/cli.html#the_edit_sql_function), die [Dokumentation zum Safe Mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) und die [Dokumentation zum Laden von Erweiterungen](https://www.sqlite.org/loadext.html#loading_an_extension).

### Privilegierte Dateileser, die Daten an einen ausführlichen Client weitergeben

Ein benutzerdefinierter SUID/SGID-Wrapper kann den Zugriff auf einen vom Aufrufer gewählten Pfadnamen prüfen und die Datei anschließend an einen anderen Befehl übergeben. Prüfen Sie die effektive Identität sowohl bei der Zugriffsprüfung als auch beim späteren Öffnen, lösen Sie alle `../`-Komponenten relativ zum tatsächlichen Basisverzeichnis auf und untersuchen Sie, wie das Kind ungültige Eingaben verarbeitet. Wenn ein Datenbank-Client eine private Datei als SQL mit ausführlicher Ausgabe liest, gibt er den Dateiinhalt möglicherweise in Fehlermeldungen aus, obwohl das SQL ungültig ist. Eine Offenlegung zwischen Benutzern liegt nur dann vor, wenn das Kind eine Datei lesen kann, die der Aufrufer nicht lesen kann, der Aufrufer diese Datei über den Wrapper auswählen kann und die Ausgabe sichtbar ist; das bloße Vorhandensein von `mysql` oder einer Zeichenfolge für einen anderen Client belegt keine dieser Bedingungen.

### Netdata-`ndsudo`-Suchpfad

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) betraf einige Netdata-`ndsudo`-Builds. Das root-eigene SUID-Hilfsprogramm suchte die zulässigen externen Befehle über einen vom Aufrufer bereitgestellten `PATH`. Prüfen Sie ein installiertes Hilfsprogramm, auch wenn es außerhalb des üblichen `PATH` des Aufrufers liegt, aber nur, wenn das aktuelle Konto es ausführen kann. Bestätigen Sie den Eigentümer, das SUID-Bit, den Ausführungszugriff (einschließlich Gruppen-/ACL-Berechtigungen), den installierten Build und den Patch-Status des Herstellers sowie, ob `NoNewPrivs` oder ein `nosuid`-Mount die Identitätsänderung verhindert. Netdata nennt die gepatchten Builds `v1.45.3` und `v1.45.0-169`; Distributions-Backports müssen separat bestätigt werden. Eine Dashboard-Version oder das bloße Vorhandensein von `ndsudo` reicht als Nachweis für eine erreichbare Rechteausweitung nicht aus. Das Pfadproblem setzt außerdem voraus, dass das Hilfsprogramm einen externen Befehl über einen vom Aufrufer kontrollierten Ort auflöst.

### Privilegiengrenze bei Firejail `join`

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) betraf Firejails privilegierte `--join`-Logik: Ein präpariertes Join-Ziel konnte das Setuid-root-Hilfsprogramm dazu bringen, einen vom Angreifer kontrollierten Mount-Namespace zu akzeptieren und unsichere Sicherheitszustände zu kopieren. Bei einer passiven Triage bestätigen Sie, dass die **aktuelle Identität ein root-eigenes Setuid-Firejail-Binary ausführen kann**, Setuid auf dessen Mount und in dessen Prozesskontext wirksam ist und der installierte Build die Fehlerbehebung nicht enthält. Upstream hat das Problem in [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) behoben; Distributionspakete können den Fix [zurückportiert haben](https://github.com/netblue30/firejail/issues/5191), während sie weiterhin eine ältere Version anzeigen. Diese Voraussetzungen kennzeichnen einen Prüfungsansatz, nicht einen erfolgreichen Join oder eine Root-Shell. Erstellen Sie während der Bestandsaufnahme kein gefälschtes Jail und rufen Sie `--join` nicht auf.

### GNU-Screen-Logdateiberechtigungen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) betraf Screen 4.5.0, das eine vom Aufrufer gewählte Logdatei mit erhöhten Privilegien öffnete. Ein `screen`- oder versionssuffigiertes Binary im SUID-Bestand ist lediglich ein Prüfungsansatz: Bestätigen Sie den Eigentümer root, die wirksame SUID-Ausführung für den aktuellen Benutzer, den installierten Build und den Patch-Status der Distribution sowie das betroffene Verhalten bei Logdateien. [Debian hat sein 4.5.0-Paket mit einem Backport korrigiert](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484); eine Versionszeichenfolge oder ein Dateiname allein beweist keine Gefährdung. Erstellen Sie bei einer routinemäßigen Bestandsaufnahme keine Logdatei als Test.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) betraf das privilegierte S-nail-Mail-Lock-Hilfsprogramm, wenn eine vom Aufrufer kontrollierte Pfadkomponente Verzeichniswechsel durchlaufen und so zu beliebigen Dateischreibzugriffen führen konnte. Prüfen Sie, ob der aktuelle Benutzer ein installiertes, root-eigenes Setuid-Hilfsprogramm ausführen kann, ob dessen Setuid-Identität unter der Mount- und Prozessrichtlinie wirksam ist und welcher genaue Paket-Build sowie Hersteller-Fix vorliegen. [Ubuntus Sicherheitshinweis](https://ubuntu.com/security/notices/USN-4820-1) führt einen zurückportierten Fix für das Paket von 16.04 auf; eine scheinbar passende Upstream-Version allein ist daher nicht aussagekräftig. Das Vorhandensein des Hilfsprogramms beweist weder, dass der betroffene Pfad erreichbar ist, noch dass ein Dateischreibzugriff zur Root-Codeausführung führt; prüfen Sie Metadaten und Paketstatus, ohne das Hilfsprogramm aufzurufen oder während der Bestandsaufnahme einen Race-Versuch zu unternehmen.

### snap-confine und tmpfiles-Bereinigung

CVE-2026-3888 ist ein Race zwischen dem privilegierten `snap-confine` und der systemd-tmpfiles-Bereinigung von `/tmp`. Bei einer passiven Prüfung können Sie feststellen, ob `snap-confine` setuid ist oder Dateifähigkeiten hat, das installierte `snapd`-Paket mit der für diese **Ubuntu-Version** behobenen Version vergleichen und die effektive Altersregel für `/tmp` sowie den Bereinigungstimer prüfen. Ein passendes Paket und eine passende Regel sind Voraussetzungen, aber kein Beweis, dass das Race erreichbar ist: Auch der Laufzeitstatus des Timers, das Snap-Layout, Paket-Backports und Regelüberschreibungen spielen eine Rolle. Bei älteren Versionen kann eine nicht standardmäßige Konfiguration erforderlich sein. Führen Sie bei einer routinemäßigen Bestandsaufnahme keinen Race-Test aus. Siehe den [Ubuntu-CVE-Eintrag](https://ubuntu.com/security/CVE-2026-3888) zum versionsspezifischen Paketstatus und die [Qualys-Sicherheitsmitteilung](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) zur Interaktion der Komponenten.

## ACLs und sensible Pfade prüfen

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ein beschreibbares übergeordnetes Verzeichnis kann den Austausch einer Datei ermöglichen, selbst wenn die Datei root gehört. Eine ACL kann unauffällig Zugriff auf einen sudoers-Drop-in, eine Service-Unit, ein Cron-Skript, einen Bibliothekspfad oder eine Zugangsdatendatei gewähren. Prüfe sowohl die ACL als auch den vollständigen Pfad. Sind beliebige Schreibzugriffe auf privilegierte Dateien möglich, folge [Arbitrary File Write to Root](write-to-root.md); Beispiele zur Linker-Konfiguration und zum Preloading findest du im [`ld.so`-Beispiel](ld.so.conf-example.md). Betrachte offengelegte Backups, `.env`-Dateien, Datenbankkonfigurationen, SSH-Material und Verlaufsdateien als mögliche Quellen für Zugangsdaten; der Zugriff darauf richtet sich nach den tatsächlichen Berechtigungen der jeweiligen Datei.
