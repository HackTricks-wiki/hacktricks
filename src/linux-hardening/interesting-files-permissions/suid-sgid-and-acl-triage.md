# SUID, SGID, ACLs और संवेदनशील फ़ाइलें

{{#include ../../banners/hacktricks-training.md}}

SUID और SGID किसी फ़ाइल को execute करने पर उसकी प्रभावी पहचान बदलते हैं; ACLs ऐसी पहुँच दे सकते हैं जो सामान्य `ls -l` mode bits में दिखाई नहीं देती। जब किसी user को apparent owner और group permissions से अधिक read, write या execute करने की अनुमति हो, तो दोनों की जाँच करें।

## विशेषाधिकार प्राप्त executables की गणना करें

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Custom या हाल ही में बदले गए executables, असामान्य owners और writable mounts पर मौजूद files पर ध्यान दें। `nosuid` mount set-ID behavior को रोक सकता है; file capabilities एक अलग privilege mechanism हैं, जिसका वर्णन [Linux capabilities](linux-capabilities.md) में है। किसी संदिग्ध binary की तुलना उसके package से करें और जाँचें कि वह elevated identity के साथ क्या execute, open या load करती है।

ऐसे अपरिचित root-owned SUID executable के लिए, जो caller का input स्वीकार करता है, memory-unsafe argument handling और उस तक पहुँचने वाले code path की समीक्षा binary की एक copy पर offline करें। effective-ID behavior और stack canaries, non-executable memory, position-independent code और address randomization जैसे mitigations दर्ज करें। किसी unsafe function का नाम या mitigation का अभाव केवल समीक्षा के लिए एक संकेत है: exploitability वास्तविक input bounds, reachable control flow और fault के समय effective identity पर निर्भर करती है। Passive enumeration के दौरान केवल crash जाँचने के लिए live privileged executable को लंबे arguments न भेजें।

एक परिचित SUID program को भी बदला या backdoor किया जा सकता है। हाल का modification time एक संकेत है, प्रमाण नहीं: किसी **विशिष्ट संदिग्ध packaged binary** के लिए उसका owning package पता करें और routine enumeration के दौरान हर package को verify करने के बजाय installed file की तुलना package metadata से करें:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` केवल उन्हीं फ़ाइलों की सामग्री जाँचता है जिनके checksum पैकेज डेटाबेस में दर्ज हैं; RPM mode और ownership जैसे metadata की भी तुलना करता है। **विशेषाधिकार-प्राप्त executable में ही** mismatch पर ध्यान दें: stripped installations में उसी पैकेज की अन्य जगहों पर मौजूद documentation या locale files के गुम होने की रिपोर्ट आ सकती है। संदिग्ध executable की तुलना किसी विश्वसनीय vendor package से करें और बदले हुए code की ठीक-ठीक समीक्षा करें। स्थानीय रूप से किए गए वैध बदलाव, अनुपलब्ध checksums और compromised package metadata से इन दोनों commands के निष्कर्ष सीमित हो जाते हैं। Passive triage के दौरान न तो संदिग्ध SUID प्रोग्राम चलाएँ, न package verification script। [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) और [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) देखें।

जो SUID प्रोग्राम किसी writable path से shell, relative command या library चलाता है, वह trust boundary पार कर सकता है। [SUID shared-library और linker abuse](suid-shared-library-and-linker-abuse.md), [PATH संबंधी मार्गदर्शन](../linux-basics/linux-environment-variables.md#path) और [user-ID की व्याख्या](../user-information/euid-ruid-suid.md) देखें। किसी command से जुड़े ज्ञात escapes के लिए, host पर अनुमत exact binary और invocation को [GTFOBins](https://gtfobins.github.io/) में देखें।

Set-user-ID executable के मामले में caller के **real UID** और file owner के **effective UID** में अंतर समझें: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) real UID को अपरिवर्तित छोड़ता है और set-ID बदलाव के बाद effective UID को saved UID में कॉपी करता है। [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) command को `/bin/sh -c` के माध्यम से चलाता है; उस path से चुना गया shell यह प्रभावित करता है कि child अपनी effective identity बनाए रखेगा या नहीं। विशेष रूप से, [Bash privileged-mode के नियम](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) के अनुसार, Bash `-p` के बिना शुरू होने पर अलग-अलग effective UID को real UID पर reset कर देता है। वास्तविक helper के UID बदलाव और child invocation के साथ-साथ उसका owner, executable access, mount का `nosuid` setting और process का `no_new_privs` state भी जाँचें। केवल SUID bit या shell call से यह साबित नहीं होता कि ऊँचे privileges में उपयोगी बदलाव संभव है।

अगर वर्तमान user किसी असामान्य root-owned SUID `jjs` को चला सकता है, तो उसकी file access की अलग से समीक्षा करें। पुराना Nashorn tool Java file APIs तक पहुँच सकता है, भले ही उससे शुरू किया गया shell effective UID छोड़ दे; इसे privileged read या write मानने से पहले installed JVM का व्यवहार, file operation की effective identity और `nosuid`/`no_new_privs` की पुष्टि करें। [Oracle ने JDK 15 में `jjs` हटाया](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); installed path अब भी पुराना या अलग से packaged build हो सकता है। [GTFOBins file APIs का दस्तावेज़ देता है](https://gtfobins.org/gtfobins/jjs/), लेकिन उसके sudo examples हर build में SUID behavior साबित नहीं करते। Passive enumeration के दौरान यह tool न चलाएँ।

कम privileges वाले user के लिए accessible root-owned SUID `gosu` executable की समीक्षा करें: इसके documented interface में target user और command दिए जा सकते हैं, लेकिन सामान्य container उपयोग में इसे root के रूप में शुरू करके privileges drop किए जाते हैं। इसे चलाने से पहले installed build का SUID behavior, effective identity और user-namespace mapping, साथ ही `nosuid` और `no_new_privs` सत्यापित करें; container में root होने का अर्थ host पर root होना नहीं है। केवल filename या SUID bit से यह साबित नहीं होता कि बदलाव काम करेगा। [Upstream usage](https://github.com/tianon/gosu) और [maintainer की SUID चेतावनी](https://github.com/tianon/gosu/issues/11) देखें। Passive inventory के दौरान helper न चलाएँ।

Custom set-user-ID backup wrapper caller द्वारा चुना गया path स्वीकार कर सकता है और उसे `system(3)` को दिए जाने वाले archive command में interpolate कर सकता है। यदि बने हुए command में path को quotes में नहीं रखा गया है, तो child shell [tilde expansion में `HOME`, pathname patterns जैसे `?` और `*`, और newline से command separation](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) लागू कर सकता है; denylist में केवल परिचित punctuation को अस्वीकार करने से path literal नहीं बनता। Exact argument flow, inherited environment, child shell और effective identity, filesystem access, तथा archive output caller को दिखाई देता है या नहीं—इन सबकी पुष्टि करें। SUID bit, archive-tool string या `/root` के literal path को block करना—इनमें से कोई भी अकेले disclosure या code execution साबित नहीं करता। Passive enumeration के दौरान निजी files archive न करें और crash inputs न भेजें; wrapper की copy की offline समीक्षा करें।

Shell की [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html), जैसे `$(...)`, metacharacter denylist में एक और संभावित कमी है: अनुमत fixed command prefix भी `/bin/sh -c` के ज़रिए बाद में आने वाला caller-controlled argument आगे पहुँचा सकता है। Exact quoting, parser और effective identity की offline पुष्टि करें; `system()` string या अधूरी denylist को execution का प्रमाण न मानें।

**Calling process tree** भी मायने रखता है। Web worker ऐसा seccomp filter लगा सकता है जो UID बदलने वाली system calls को सीमित करे; [seccomp filters children तक लागू रहते हैं और `execve` के बाद भी बने रहते हैं](https://docs.kernel.org/userspace-api/seccomp_filter.html)। उदाहरण के लिए, Apache के [mpm-itk `LimitUIDRange` और `LimitGIDRange` directives](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) descendants के लिए उपलब्ध identities सीमित कर सकते हैं। `/proc/self/status` में `Seccomp: 2` filter mode दिखाता है, policy नहीं; न ही यह बताता है कि यह विशेष helper अपने owner की identity हासिल कर सकता है या नहीं। वास्तविक invocation की ancestry और effective filter की समीक्षा उसके SUID, mount और `no_new_privs` conditions के साथ करें; अलग login session की policy अलग हो सकती है, लेकिन उसके लिए भी वैध access path चाहिए।

Custom SUID executable कोई अलग, readable Python script चला सकता है। यदि वह सचमुच Python **2** इस्तेमाल करता है, तो [`input()` दर्ज की गई expression को evaluate करता है](https://docs.python.org/2/library/functions.html#input); Python 3 में `input()` इसके बजाय text लौटाता है। Source line को execution path मानने से पहले wrapper की effective identity, interpreter path और version, script path, और यह पुष्टि करें कि untrusted input उस call तक पहुँचता है। Script पर set-ID bit या privileged wrapper के बिना `input()` call से वही boundary स्थापित नहीं होती। Enumeration के दौरान binary के referenced paths और सीमित script source की समीक्षा करें; उसे न चलाएँ।

यदि किसी असामान्य SUID executable के साथ readable source भी है, तो caller-controlled file read में माँगे गए byte count की destination buffer के आकार से तुलना करें और बाद के control-flow checks देखें। [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) माँगे गए items दिए गए pointer पर लिखता है; उसे destination object की capacity का पता नहीं होता। Size mismatch static memory-safety की जाँच का संकेत है, उपयोगी privilege escalation का प्रमाण नहीं: पुष्टि करें कि source installed binary से मेल खाता है, caller input दे सकता है, उस context में SUID execution प्रभावी है और संबंधित path तक पहुँचना संभव है। Enumeration के दौरान privileged program को crash inputs भेजने के बजाय सीमित source या binary copy की offline समीक्षा करें।

Custom SUID helper protected file की सामग्री छापे बिना उसे उजागर कर सकता है। यदि caller pathname और regular expression, दोनों चुन सकता है, और helper अपनी effective UID के तहत दिखाई देने वाली match count लौटाता है, तो anchored prefix tests एक-एक character पता लगाने वाला oracle बन सकते हैं। Helper के owner, effective-ID behavior, executable access, pathname restrictions, regex semantics, response की visibility और उस खास higher-privilege file की पुष्टि करें जिसे caller अन्यथा पढ़ नहीं सकता। SUID bit या regex library string अकेले इस flow को साबित नहीं करते। Passive enumeration के दौरान असामान्य executable दर्ज करें और सीमित disassembly या source copy की समीक्षा करें; live helper पर बार-बार guesses न चलाएँ और मिले हुए secrets न छापें।

OpenBSD पर custom set-user-ID reader, जो caller द्वारा चुना गया pathname स्वीकार करता है, `/var/backups` के files उजागर कर सकता है—यदि उसकी effective identity उन्हें पढ़ सकती है और वह सामग्री caller को लौटाता है। [OpenBSD का `changelist(5)`](https://man.openbsd.org/changelist.5) configured paths की `.current` और `.backup` copies का विवरण देता है, लेकिन `+` से शुरू होने वाली entries file contents के बजाय SHA-256 checksums रखती हैं; backup directory का owner root और mode `0700` होना चाहिए। `/var` के लिए helper का [`unveil` read rule](https://man.openbsd.org/unveil.2) उस path के नीचे access की अनुमति दे सकता है, लेकिन अपने आप file access नहीं देता, न ही उसे साबित करता है। Escalation का दावा करने से पहले वास्तविक effective UID, वर्तमान user के लिए executable permission, स्वीकार किया गया path, backup का मौजूद होना और उसकी सामग्री, तथा स्वतंत्र authentication की किसी भी आवश्यकता की पुष्टि करें। Passive enumeration में helper और path metadata दर्ज करें; reader न चलाएँ और backup data न छापें।

Custom SUID program caller द्वारा चुने गए pathname को [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) से जाँचकर बाद में खोलता है, तो caller-writable directory में file या symlink बदलकर race कर सकता है। जाँच पहले वाले object पर लागू होती है, जबकि बाद का [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) किसी दूसरे object को resolve कर सकता है। पुष्टि करें कि helper को elevated effective identity के साथ चलाया जा सकता है, किसी अन्यथा पहुँच योग्य code path में चुनी गई file पढ़ी जाती है, और caller check तथा open के बीच pathname बदल सकता है; केवल SUID bit, writable directory या `stat` string इनमें से कुछ भी स्थापित नहीं करते। Disclosure path के लिए output दिखाई देना या destination का caller द्वारा पढ़ा जा सकना भी ज़रूरी है। Binary और path metadata की offline समीक्षा करें; passive enumeration के दौरान live helper के साथ race न करें।

SGID wrappers पर भी यही dependency review लागू करें। Absolute path से shell या helper चलाने वाला wrapper तब भी असुरक्षित हो सकता है, जब कम privileges वाला user उस file को बदल सके; शुरू हुआ code wrapper की effective group पा सकता है। बुलाए गए exact path, उसके write access (ACLs सहित), wrapper की effective group और child शुरू करने से पहले privileges drop किए जाते हैं या नहीं—इनकी जाँच करें। Interpreter inherited effective IDs भी छोड़ सकता है, इसलिए जाँच योग्य स्थिति और प्रमाणित transition में अंतर रखें। Host पर कहीं और मौजूद writable shell अकेले यह साबित नहीं करता कि privileged wrapper उसे चलाता है।

### वे privileged wrappers जो SQL को SQLite CLI तक पहुँचाते हैं

यदि custom SUID program user-controlled SQL को **`sqlite3` command-line program** तक पहुँचाता है, तो query को read-only मानने से पहले exact command और effective identity की जाँच करें। CLI का `edit()` SQL function editor चलाता है (दूसरे argument से या `VISUAL` से), और उसका SQL `load_extension()` function extension loading enabled होने पर shared library load कर सकता है। ये CLI process की identity के तहत code execution के संभावित रास्ते हैं—भले ही wrapper `PATH` तय करे या absolute `sqlite3` path इस्तेमाल करे। SQL का इन functions तक पहुँचना और CLI में संबंधित feature का उपलब्ध रहना ज़रूरी है; binary या host पर `sqlite3` मिलना मात्र escalation का प्रमाण नहीं है। SQLite **library** में extension loading default रूप से बंद होती है, इसलिए उसे CLI से अलग समझें। जहाँ किसी privileged application को untrusted SQL process करना हो, SQLite CLI का `--safe` mode `edit()`, `load_extension()` और अन्य side-effectful functions को बंद कर देता है। [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option) और [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension) देखें।

### वे privileged file readers जो verbose client को file देते हैं

Custom SUID/SGID wrapper caller द्वारा चुने गए pathname पर access जाँचकर उस file को किसी दूसरे command तक पहुँचा सकता है। Access check और बाद के open—दोनों के समय effective identity की समीक्षा करें, वास्तविक base directory के सापेक्ष `../` components को resolve करें, और invalid input को child कैसे संभालता है यह देखें। यदि database client private file को SQL की तरह verbose output के साथ पढ़ता है, तो SQL invalid होने पर भी errors में file की सामग्री echo हो सकती है। यह cross-user disclosure तभी है, जब child ऐसी file पढ़ सके जिसे caller नहीं पढ़ सकता, caller wrapper के ज़रिए वह file चुन सके, और output दिखाई दे; केवल `mysql` या किसी अन्य client string की मौजूदगी इनमें से कोई भी शर्त साबित नहीं करती।

### Netdata `ndsudo` search path

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ने Netdata के कुछ `ndsudo` builds को प्रभावित किया था। Root-owned SUID helper अनुमत external commands खोजने के लिए caller द्वारा दिया गया `PATH` इस्तेमाल करता था। Installed helper की समीक्षा तभी करें—भले ही वह caller के सामान्य `PATH` से बाहर हो—जब वर्तमान account उसे चला सकता हो। उसके owner, SUID bit, executable access (group/ACL grants सहित), installed build और vendor patch status की पुष्टि करें, और जाँचें कि `NoNewPrivs` या `nosuid` mount identity change को रोकता है या नहीं। Netdata patched builds `v1.45.3` और `v1.45.0-169` बताता है; distribution backports की अलग से पुष्टि करनी होगी। Dashboard version या `ndsudo` की मौजूदगी मात्र, reachable escalation का पर्याप्त प्रमाण नहीं है। Path की समस्या के लिए यह भी ज़रूरी है कि helper किसी ऐसे location से external command resolve करे जिसे caller नियंत्रित कर सकता है।

### Firejail join privilege boundary

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ने Firejail के privileged `--join` logic को प्रभावित किया था: crafted join target के कारण setuid-root helper attacker-controlled mount namespace स्वीकार कर सकता था और असुरक्षित security state कॉपी कर सकता था। Passive triage के लिए पुष्टि करें कि **वर्तमान identity root-owned setuid Firejail binary चला सकती है**, उसके mount और process context में setuid प्रभावी है, और installed build में fix नहीं है। Upstream ने [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) में समस्या ठीक की; distribution packages इसे [backport](https://github.com/netblue30/firejail/issues/5191) कर सकते हैं, जबकि version पुराना दिखे। ये prerequisites समीक्षा योग्य स्थिति बताते हैं, सफल join या root shell नहीं। Enumeration के दौरान fake jail न बनाएँ और `--join` न चलाएँ।

### GNU Screen logfile permissions

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) में Screen 4.5.0 elevated privileges के साथ caller द्वारा चुनी logfile खोलता था। SUID inventory में `screen` या version-suffixed binary मिलना केवल आगे की समीक्षा का संकेत है: root ownership, वर्तमान user के लिए प्रभावी SUID execution, installed build और distribution patch status, तथा प्रभावित logfile behavior की पुष्टि करें। [Debian ने अपने 4.5.0 package में backport के ज़रिए fix किया था](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), इसलिए केवल version string या filename exposure साबित नहीं करता। सामान्य enumeration probe के रूप में logfile न बनाएँ।

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ने privileged S-nail mail-lock helper को प्रभावित किया था, जब caller-controlled path component directories के पार जाकर मनमाने file write तक पहुँच सकता था। जाँचें कि वर्तमान user installed root-owned setuid helper चला सकता है या नहीं, mount और process policy के तहत उसकी setuid identity प्रभावी है या नहीं, और exact package build तथा vendor fix क्या हैं। [Ubuntu का security notice](https://ubuntu.com/security/notices/USN-4820-1) उसके 16.04 package के लिए backported fix बताता है, इसलिए upstream जैसा version अकेले निर्णायक नहीं है। Helper की मौजूदगी यह साबित नहीं करती कि प्रभावित path तक पहुँचना संभव है या file write से root execution होगा; enumeration के दौरान helper चलाए या race करने की कोशिश किए बिना metadata और package status देखें।

### snap-confine और tmpfiles cleanup

CVE-2026-3888, privileged `snap-confine` और `/tmp` की systemd-tmpfiles cleanup के बीच होने वाली race है। Passive review में जाँचें कि `snap-confine` setuid है या उसके पास file capabilities हैं, installed `snapd` package की तुलना उस **Ubuntu release** के fixed version से करें, और `/tmp` के प्रभावी age rule तथा cleanup timer की समीक्षा करें। Package और rule का मेल prerequisites हैं, race तक पहुँच का प्रमाण नहीं: runtime timer state, snap layout, package backports और rule overrides भी मायने रखते हैं। पुराने releases में non-default configuration की आवश्यकता हो सकती है। Routine enumeration के दौरान race probe न चलाएँ। Release-specific package status के लिए [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) और components की परस्पर क्रिया के लिए [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) देखें।

## ACLs और संवेदनशील paths की जाँच करें

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

लिखने योग्य parent directory, फ़ाइल के root-owned होने पर भी उसे बदलने की अनुमति दे सकती है। ACL चुपचाप sudoers drop-in, service unit, cron script, library path या credential file तक पहुँच दे सकती है। ACL और पूरा path, दोनों जाँचें। यदि मनमाने privileged file writes संभव हों, तो [Arbitrary File Write to Root](write-to-root.md) देखें; linker configuration और preload के मामलों के लिए [`ld.so` example](ld.so.conf-example.md) देखें। उजागर backups, `.env` files, database configs, SSH material और history को संभावित credential sources मानें; उन तक पहुँच प्रत्येक फ़ाइल की वास्तविक permissions से नियंत्रित होती है।
