# SUID, SGID, ACLs, और संवेदनशील फ़ाइलें

{{#include ../../banners/hacktricks-training.md}}

SUID और SGID किसी निष्पादित फ़ाइल की प्रभावी पहचान बदलते हैं; ACLs ऐसा access दे सकते हैं जो सामान्य `ls -l` mode bits में दिखाई नहीं देता। जब किसी user को apparent owner और group permissions से अधिक पढ़ने, लिखने या निष्पादित करने की अनुमति हो, तो दोनों की समीक्षा करें।

## privileged executables की गणना करें

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

कस्टम या हाल ही में बदले गए executables, असामान्य owners और writable mounts पर मौजूद files पर ध्यान दें। `nosuid` mount set-ID behavior को रोक सकता है; file capabilities एक अलग privilege mechanism हैं, जिसका वर्णन [Linux capabilities](linux-capabilities.md) में है। किसी संदिग्ध binary की तुलना उसके package से करें और जांचें कि वह elevated identity के साथ क्या execute, open या load करती है।

ऐसे अपरिचित root-owned SUID executable के लिए, जो caller का input स्वीकार करता है, memory-unsafe argument handling और उस तक पहुंचने वाले code path की offline समीक्षा, binary की एक copy पर करें। effective-ID behavior और stack canaries, non-executable memory, position-independent code तथा address randomization जैसे mitigations दर्ज करें। किसी unsafe function का नाम या mitigation का अभाव केवल समीक्षा का संकेत है: exploitability, input bounds, reachable control flow और fault के समय effective identity पर निर्भर करती है। Passive enumeration के दौरान केवल crash जांचने के लिए live privileged executable को लंबे arguments न भेजें।

किसी परिचित SUID program को भी बदला या backdoor किया जा सकता है। हाल में बदला गया modification time जांच का संकेत है, प्रमाण नहीं: किसी **विशिष्ट संदिग्ध packaged binary** के लिए, routine enumeration के दौरान हर package verify करने के बजाय, उसका owning package पता करें और installed file की तुलना package metadata से करें:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` केवल उन्हीं फ़ाइलों की सामग्री जाँचता है जिनके लिए पैकेज डेटाबेस में checksum दर्ज है; RPM mode और ownership जैसे metadata की भी तुलना करता है। **विशेषाधिकार प्राप्त executable पर ही** mismatch पर ध्यान दें: stripped installations में उसी पैकेज की दूसरी जगह मौजूद documentation या locale files के missing होने की रिपोर्ट आ सकती है। संदिग्ध executable की तुलना किसी विश्वसनीय vendor package से करें और बदले गए code की ठीक-ठीक समीक्षा करें। वैध स्थानीय बदलाव, checksum का न होना और compromised package metadata—इन दोनों commands से साबित की जा सकने वाली बातों को सीमित करते हैं। Passive triage के दौरान न तो संदिग्ध SUID program चलाएँ, न ही package verification script। [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) और [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) देखें।

जो SUID program writable path से shell, relative command या library चलाता है, वह trust boundary पार कर सकता है। [SUID shared-library और linker abuse](suid-shared-library-and-linker-abuse.md), [PATH guidance](../linux-basics/linux-environment-variables.md#path), और [user-ID explanation](../user-information/euid-ruid-suid.md) देखें। ज्ञात command-specific escapes के लिए, host पर अनुमत सटीक binary और invocation को [GTFOBins](https://gtfobins.github.io/) में जाँचें।

Set-user-ID executable के लिए, caller के **real UID** और file owner के **effective UID** में अंतर समझें: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) real UID को अपरिवर्तित छोड़ता है और किसी set-ID बदलाव के बाद effective UID को saved UID में कॉपी करता है। [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) command को `/bin/sh -c` के ज़रिए चलाता है; उस path से चुना गया shell तय करता है कि child अपनी effective identity बनाए रखेगा या नहीं। विशेष रूप से, [Bash privileged-mode rules](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) के अनुसार, यदि Bash `-p` के बिना शुरू होता है और effective UID, real UID से अलग है, तो वह effective UID को real UID पर reset कर देता है। वास्तविक helper के UID बदलाव और child invocation के साथ-साथ उसके owner, executable access, mount के `nosuid` setting और process के `no_new_privs` state की जाँच करें। केवल SUID bit या shell call से यह साबित नहीं होता कि अधिक विशेषाधिकारों में बदलाव संभव है।

असामान्य root-owned SUID `jjs` की अलग से file-access समीक्षा करें, यदि मौजूदा user उसे चला सकता है। Legacy Nashorn tool, spawned shell के effective UID छोड़ने पर भी Java file APIs का उपयोग कर सकता है; इसे privileged read या write मानने से पहले installed JVM का व्यवहार, file operation की effective identity और `nosuid`/`no_new_privs` की पुष्टि करें। [Oracle ने JDK 15 में `jjs` हटा दिया](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); फिर भी installed path किसी पुराने या अलग से packaged build का हो सकता है। [GTFOBins file APIs का दस्तावेज़ देता है](https://gtfobins.org/gtfobins/jjs/), लेकिन उसके sudo examples हर build में SUID behavior साबित नहीं करते। Passive enumeration के दौरान tool न चलाएँ।

कम विशेषाधिकार वाले user के लिए सुलभ root-owned SUID `gosu` executable की समीक्षा करें: इसका documented interface target user और command स्वीकार करता है, लेकिन सामान्य container उपयोग में इसे root के रूप में शुरू किया जाता है ताकि यह privileges छोड़ सके। किसी privilege change को मानने से पहले installed build का SUID behavior, effective identity और user-namespace mapping, तथा `nosuid` और `no_new_privs` की पुष्टि करें; container में root होने का अर्थ host पर root होना नहीं है। केवल filename या SUID bit से यह साबित नहीं होता कि बदलाव काम करेगा। [Upstream usage](https://github.com/tianon/gosu) और [maintainer की SUID warning](https://github.com/tianon/gosu/issues/11) देखें। Passive inventory के दौरान helper न चलाएँ।

कोई custom set-user-ID backup wrapper caller द्वारा चुना गया path स्वीकार कर सकता है और उसे `system(3)` को दिए गए archive command में जोड़ सकता है। यदि बनाए गए command में उस path को quotes में न रखा गया हो, तो child shell [tilde expansion—जिसमें `HOME` का उपयोग होता है—, `?` और `*` जैसे pathname patterns, तथा newline से command separation](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) लागू कर सकता है; denylist में केवल आम punctuation को अस्वीकार करने से path literal नहीं बन जाता। सटीक argument flow, inherited environment, child shell और effective identity, filesystem access, तथा यह पुष्टि करें कि archive output caller को दिखाई देता है या नहीं। SUID bit, archive-tool string, या केवल `/root` को block करना—इनमें से कोई भी अकेले disclosure या code execution साबित नहीं करता। Passive enumeration के दौरान private files archive करने या crash inputs भेजने के बजाय wrapper की copy की offline समीक्षा करें।

Shell [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html), जैसे `$(...)`, metacharacter denylist में एक और संभावित कमी है: अनुमत fixed command prefix भी `/bin/sh -c` के ज़रिए बाद के caller-controlled argument को आगे पहुँचा सकता है। सटीक quoting, parser और effective identity की offline पुष्टि करें; केवल `system()` string या अधूरी denylist को execution का प्रमाण न मानें।

**Calling process tree** भी मायने रखता है। Web worker UID बदलने वाले system calls को सीमित करने वाला seccomp filter लगा सकता है; [seccomp filters बच्चों तक पहुँचते हैं और `execve` के बाद भी बने रहते हैं](https://docs.kernel.org/userspace-api/seccomp_filter.html)। उदाहरण के लिए, Apache के [mpm-itk `LimitUIDRange` और `LimitGIDRange` directives](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) descendants के लिए उपलब्ध identities सीमित कर सकते हैं। `/proc/self/status` में `Seccomp: 2` filter mode दिखाता है, policy नहीं; न ही यह बताता है कि यह विशेष helper अपने owner की identity हासिल कर सकता है या नहीं। वास्तविक invocation की ancestry और effective filter की समीक्षा, उसके SUID, mount और `no_new_privs` conditions के साथ करें; किसी अलग login session में अलग policy हो सकती है, लेकिन उसके लिए अपना वैध access path चाहिए।

कोई custom SUID executable अलग, readable Python script चला सकता है। यदि वह वास्तव में Python **2** इस्तेमाल करता है, तो [`input()` दर्ज की गई expression का मूल्यांकन करता है](https://docs.python.org/2/library/functions.html#input); Python 3 का `input()` इसके बजाय text लौटाता है। Source line को execution path मानने से पहले wrapper की effective identity, interpreter path और version, script path, तथा यह पुष्टि करें कि untrusted input उस call तक पहुँचता है या नहीं। केवल script पर set-ID bit होना या privileged wrapper के बिना `input()` call होना, वही trust boundary स्थापित नहीं करता। Enumeration के दौरान चलाए बिना binary के referenced paths और सीमित script source की समीक्षा करें।

यदि किसी असामान्य SUID executable के साथ readable source उपलब्ध हो, तो caller-controlled file read में माँगे गए byte count की destination buffer के आकार से तुलना करें और बाद के control-flow checks देखें। [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) माँगे गए items दिए गए pointer पर लिखता है; उसे destination object की capacity का पता नहीं होता। Size mismatch, static memory-safety जाँच के लिए एक lead है—काम करने वाले privilege escalation का प्रमाण नहीं। पुष्टि करें कि source installed binary से मेल खाता है, caller input दे सकता है, उस context में SUID execution प्रभावी है और संबंधित path तक पहुँचा जा सकता है। Enumeration के दौरान privileged program को crash inputs भेजने के बजाय सीमित source या binary copy की offline समीक्षा करें।

कोई custom SUID helper protected file की सामग्री छापे बिना भी उसे उजागर कर सकता है। यदि caller pathname और regular expression दोनों चुन सकता है, और helper अपनी effective UID के तहत दिखाई देने वाली match count लौटाता है, तो anchored prefix tests से character-by-character oracle बन सकता है। Helper के owner, effective-ID behavior, executable access, pathname restrictions, regex semantics, response visibility और ऐसी विशिष्ट higher-privilege file की पुष्टि करें जिसे caller अन्यथा पढ़ नहीं सकता। केवल SUID bit या regex library string उस flow को साबित नहीं करती। Passive enumeration के दौरान असामान्य executable दर्ज करें और सीमित disassembly या source copy की समीक्षा करें; live helper पर बार-बार अनुमान न चलाएँ और recovered secrets न छापें।

OpenBSD पर, caller द्वारा चुना गया pathname स्वीकार करने वाला custom set-user-ID reader `/var/backups` के अंतर्गत मौजूद files उजागर कर सकता है, यदि उसकी effective identity उन्हें पढ़ सकती है और वह उनकी सामग्री caller को लौटाता है। [OpenBSD का `changelist(5)`](https://man.openbsd.org/changelist.5) configured paths की `.current` और `.backup` copies का वर्णन करता है, लेकिन `+` से शुरू होने वाली entries file contents के बजाय SHA-256 checksums रखती हैं; backup directory का owner root और mode `0700` होना चाहिए। `/var` के लिए helper का [`unveil` read rule](https://man.openbsd.org/unveil.2) उस path के भीतर access की अनुमति दे सकता है, लेकिन अपने आप file access की अनुमति नहीं देता और न ही उसे साबित करता है। Escalation का दावा करने से पहले वास्तविक effective UID, मौजूदा user के लिए executable permission, स्वीकार किया गया path, backup का अस्तित्व और उसकी सामग्री, तथा किसी स्वतंत्र authentication requirement की पुष्टि करें। Passive enumeration में helper और path metadata दर्ज करें; reader न चलाएँ और backup data न छापें।

कोई custom SUID program यदि caller द्वारा चुने गए pathname को [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) से जाँचता है और बाद में वही pathname खोलता है, तो caller-writable directory में file या symlink बदलकर race कर सकता है। जाँच पहले वाले object पर लागू होती है, जबकि बाद का [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) किसी दूसरे object को resolve कर सकता है। पुष्टि करें कि elevated effective identity के साथ helper चलाया जा सकता है, किसी अन्यथा reachable code path में चुनी गई file पढ़ी जाती है, और caller check तथा open के बीच pathname बदल सकता है; इनमें से कोई बात केवल SUID bit, writable directory या `stat` string से साबित नहीं होती। Disclosure path के लिए दिखाई देने वाला output या caller-readable destination भी ज़रूरी है। Live helper पर race करने के बजाय binary और path metadata की offline समीक्षा करें।

SGID wrappers पर भी यही dependency review लागू करें। Absolute path से shell या helper चलाने वाला wrapper तब भी असुरक्षित हो सकता है, यदि कम विशेषाधिकार वाला user उस file को बदल सकता है; spawned code wrapper की effective group inherit कर सकता है। सटीक invoked path, उसकी write access (ACLs समेत), wrapper की effective group और child चलाने से पहले privileges छोड़े जाते हैं या नहीं—इनकी जाँच करें। Interpreter inherited effective IDs को छोड़ भी सकता है, इसलिए समीक्षा योग्य उम्मीदवार और प्रदर्शित privilege transition में अंतर रखें। Host पर कहीं और writable shell होने से यह साबित नहीं होता कि privileged wrapper उसे चलाता है।

### Privileged wrappers जो SQLite CLI को SQL देते हैं

यदि कोई custom SUID program user-controlled SQL को **`sqlite3` command-line program** देता है, तो query को read-only मानने से पहले सटीक command और effective identity की जाँच करें। CLI का `edit()` SQL function editor चलाता है (दूसरे argument से या `VISUAL` से), और उसका SQL `load_extension()` function extension loading चालू होने पर shared library load कर सकता है। Wrapper द्वारा `PATH` तय करने या absolute `sqlite3` path इस्तेमाल करने पर भी, ये CLI process की identity के तहत code execution के संभावित रास्ते हैं। SQL का वास्तव में इन functions तक पहुँचना और CLI में संबंधित feature का उपलब्ध रहना ज़रूरी है; केवल binary या host पर `sqlite3` मिलना escalation का प्रमाण नहीं है। SQLite **library** में extension loading default रूप से disabled है, इसलिए उसे CLI से अलग समझें। जहाँ किसी privileged application को untrusted SQL process करना हो, वहाँ SQLite CLI का `--safe` mode `edit()`, `load_extension()` और अन्य side-effectful functions को बंद कर देता है। [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option), और [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension) देखें।

### Privileged file readers जो verbose client को input देते हैं

कोई custom SUID/SGID wrapper caller द्वारा चुने गए pathname की access जाँच सकता है और फिर उस file को किसी दूसरी command को दे सकता है। Access check और बाद में file खोलने, दोनों समय effective identity की समीक्षा करें; वास्तविक base directory के सापेक्ष `../` components resolve करें; और देखें कि child invalid input को कैसे संभालता है। यदि database client किसी private file को SQL के रूप में verbose output के साथ पढ़ता है, तो SQL अमान्य होने पर भी वह errors में file की सामग्री echo कर सकता है। यह cross-user disclosure तभी है जब child ऐसी file पढ़ सके जिसे caller नहीं पढ़ सकता, caller wrapper के ज़रिए उस file को चुन सके, और output दिखाई दे; केवल `mysql` या किसी दूसरे client string की मौजूदगी इनमें से कोई भी शर्त साबित नहीं करती।

### Netdata `ndsudo` search path

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ने Netdata के कुछ `ndsudo` builds को प्रभावित किया। Root-owned SUID helper अनुमत external commands को caller द्वारा दिए गए `PATH` में खोजता था। Installed helper की समीक्षा करें—भले ही वह caller के सामान्य `PATH` से बाहर हो—लेकिन तभी जब मौजूदा account उसे चला सकता हो। उसके owner, SUID bit, executable access (group/ACL grants समेत), installed build और vendor patch status, तथा यह पुष्टि करें कि `NoNewPrivs` या `nosuid` mount identity change को रोकता है या नहीं। Netdata patched builds `v1.45.3` और `v1.45.0-169` सूचीबद्ध करता है; distribution backports की अलग से पुष्टि ज़रूरी है। Dashboard version या केवल `ndsudo` की मौजूदगी, reachable escalation का पर्याप्त प्रमाण नहीं है। Path वाली समस्या के लिए helper को external command उस location से resolve करना भी ज़रूरी है जिसे caller नियंत्रित कर सके।

### Firejail join privilege boundary

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ने Firejail के privileged `--join` logic को प्रभावित किया: crafted join target के कारण setuid-root helper attacker-controlled mount namespace स्वीकार कर सकता था और असुरक्षित security state की copy कर सकता था। Passive triage के लिए पुष्टि करें कि **मौजूदा identity root-owned setuid Firejail binary चला सकती है**, उसके mount और process context में setuid प्रभावी है, और installed build में fix मौजूद नहीं है। Upstream ने [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) में समस्या ठीक की; distribution packages [backport कर सकते हैं](https://github.com/netblue30/firejail/issues/5191), जबकि version पुराना दिख सकता है। ये prerequisites समीक्षा योग्य उम्मीदवार की पहचान करते हैं, सफल join या root shell का प्रमाण नहीं। Enumeration के दौरान fake jail न बनाएँ और `--join` न चलाएँ।

### GNU Screen logfile permissions

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) में Screen 4.5.0 ने elevated privileges के साथ caller द्वारा चुना गया logfile खोला था। SUID inventory में `screen` या version-suffixed binary केवल समीक्षा के लिए एक lead है: root ownership, मौजूदा user के लिए प्रभावी SUID execution, installed build और distribution patch status, तथा प्रभावित logfile behavior की पुष्टि करें। [Debian ने backport से अपना 4.5.0 package ठीक किया था](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), इसलिए अकेला version string या filename exposure साबित नहीं करता। Routine enumeration के लिए logfile न बनाएँ।

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ने privileged S-nail mail-lock helper को प्रभावित किया था, जब caller-controlled path component directories से होकर किसी भी file को लिखने तक पहुँच सकता था। समीक्षा करें कि मौजूदा user installed root-owned setuid helper चला सकता है या नहीं, mount और process policy के तहत उसकी setuid identity प्रभावी है या नहीं, और package build तथा vendor fix क्या है। [Ubuntu का security notice](https://ubuntu.com/security/notices/USN-4820-1) उसके 16.04 package के लिए backported fix सूचीबद्ध करता है, इसलिए upstream जैसा दिखने वाला version निर्णायक नहीं है। Helper की मौजूदगी यह साबित नहीं करती कि प्रभावित path तक पहुँचा जा सकता है या file write से root execution होगा; enumeration के दौरान helper चलाए या race आज़माए बिना metadata और package status की जाँच करें।

### snap-confine और tmpfiles cleanup

CVE-2026-3888, privileged `snap-confine` और `/tmp` की systemd-tmpfiles cleanup के बीच race से जुड़ा है। Passive review में जाँच सकते हैं कि `snap-confine` पर setuid bit है या file capabilities हैं, installed `snapd` package की तुलना उस **Ubuntu release** के fixed version से कर सकते हैं, और `/tmp` के प्रभावी age rule तथा cleanup timer का निरीक्षण कर सकते हैं। Matching package और rule prerequisites हैं, race के reachable होने का प्रमाण नहीं: runtime timer state, snap layout, package backports और rule overrides भी मायने रखते हैं। पुराने releases में non-default configuration की ज़रूरत हो सकती है। Routine enumeration के दौरान race probe न चलाएँ। Release-specific package status के लिए [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) और components की परस्पर क्रिया के लिए [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) देखें।

## ACLs और संवेदनशील paths का निरीक्षण करें

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

लिखने योग्य parent directory, file के root-owned होने पर भी उसे replace करने की अनुमति दे सकती है। कोई ACL चुपचाप sudoers drop-in, service unit, cron script, library path या credential file तक access दे सकती है। ACL और पूरा path, दोनों जाँचें। अगर मनमाने privileged file writes संभव हों, तो [Arbitrary File Write to Root](write-to-root.md) देखें; linker configuration और preload मामलों के लिए [`ld.so` example](ld.so.conf-example.md) देखें। उजागर backups, `.env` files, database configs, SSH material और history को संभावित credential sources मानें; access हर file की वास्तविक permissions से नियंत्रित होता है।
