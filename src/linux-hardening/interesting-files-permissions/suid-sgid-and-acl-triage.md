# SUID, SGID, ACLs und sensible Dateien

{{#include ../../banners/hacktricks-training.md}}

SUID und SGID ändern die effektive Identität einer ausgeführten Datei; ACLs können Zugriff gewähren, der in den gewöhnlichen Berechtigungsbits von `ls -l` nicht angezeigt wird. Überprüfe beides, wenn ein Benutzer mehr lesen, schreiben oder ausführen kann, als die scheinbaren Berechtigungen für Eigentümer und Gruppe vermuten lassen.

## Privilegierte ausführbare Dateien auflisten

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Konzentriere dich auf angepasste oder kürzlich geänderte ausführbare Dateien, ungewöhnliche Eigentümer und Dateien auf beschreibbaren Mounts. Ein `nosuid`-Mount kann das Set-ID-Verhalten unterdrücken; Dateifähigkeiten sind ein separater Privilegienmechanismus, der unter [Linux capabilities](linux-capabilities.md) beschrieben wird. Vergleiche eine verdächtige Binärdatei mit ihrem Paket und prüfe, was sie mit erhöhter Identität ausführt, öffnet oder lädt.

Prüfe bei einer unbekannten, root-eigenen SUID-ausführbaren Datei, die Eingaben des Aufrufers akzeptiert, offline eine Kopie der Binärdatei auf speicherunsichere Verarbeitung von Argumenten und den Codepfad, der dorthin führt. Halte das Verhalten der effektiven ID sowie Schutzmaßnahmen wie Stack Canaries, nicht ausführbaren Speicher, positionsunabhängigen Code und Address Randomization fest. Ein unsicherer Funktionsname oder eine fehlende Schutzmaßnahme ist lediglich ein Ansatzpunkt für die Prüfung: Die Ausnutzbarkeit hängt von den tatsächlichen Eingabegrenzen, dem erreichbaren Kontrollfluss und der effektiven Identität beim Fehler ab. Sende bei der passiven Enumeration keine langen Argumente an die aktive privilegierte ausführbare Datei, nur um einen Absturz zu testen.

Auch ein bekanntes SUID-Programm kann ersetzt oder mit einer Backdoor versehen worden sein. Ein kürzlicher Änderungszeitpunkt ist ein Ansatzpunkt, kein Beweis: Ermittle bei einer **bestimmten verdächtigen paketierten Binärdatei** das zugehörige Paket und vergleiche die installierte Datei mit den Paketmetadaten, statt bei der routinemäßigen Enumeration jedes Paket zu überprüfen:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` prüft Dateiinhalte nur dann, wenn die Paketdatenbank eine Prüfsumme gespeichert hat; RPM vergleicht außerdem Metadaten wie Modus und Eigentümer. Achten Sie auf Abweichungen bei der **privilegierten ausführbaren Datei selbst**: Bei Installationen ohne Dokumentation können fehlende Dokumentations- oder Locale-Dateien an anderer Stelle im selben Paket gemeldet werden. Vergleichen Sie eine verdächtige ausführbare Datei mit einem vertrauenswürdigen Herstellerpaket und prüfen Sie genau, welcher Code geändert wurde. Legitime lokale Änderungen, fehlende Prüfsummen und kompromittierte Paketmetadaten schränken die Aussagekraft beider Befehle ein. Führen Sie im Rahmen einer passiven Triage weder das verdächtige SUID-Programm noch ein Paketverifizierungsskript aus. Siehe das [Handbuch zur dpkg-Verifizierung](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) und das [Handbuch zur RPM-Verifizierung](https://rpm.org/docs/4.20.x/man/rpm.8).

Ein SUID-Programm, das eine Shell, einen relativen Befehl oder eine Bibliothek aus einem beschreibbaren Pfad aufruft, kann eine Vertrauensgrenze überschreiten. Siehe [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), die [PATH-Hinweise](../linux-basics/linux-environment-variables.md#path) und die [Erklärung zu Benutzer-IDs](../user-information/euid-ruid-suid.md). Informationen zu bekannten befehlsspezifischen Escapes finden Sie in [GTFOBins](https://gtfobins.github.io/). Prüfen Sie dort die genaue Binärdatei und den Aufruf, die der Host zulässt.

Unterscheiden Sie bei einer ausführbaren Datei mit set-user-ID das **Real UID** des Aufrufers von der **Effective UID** des Dateieigentümers: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lässt die Real UID unverändert und kopiert nach einer set-ID-Änderung die Effective UID in die Saved UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) führt seinen Befehl über `/bin/sh -c` aus; die über diesen Pfad ausgewählte Shell beeinflusst, ob ein Kindprozess seine Effective Identity beibehält. Insbesondere setzen die [Bash-Regeln für den privileged mode](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) eine abweichende Effective UID auf die Real UID zurück, wenn Bash ohne `-p` startet. Prüfen Sie die tatsächlichen UID-Änderungen und den Aufruf von Kindprozessen durch den Helper sowie dessen Eigentümer, den Zugriff auf die ausführbare Datei, die `nosuid`-Einstellung des Mounts und den `no_new_privs`-Status des Prozesses. Ein SUID-Bit oder ein Shell-Aufruf allein belegt keinen nutzbaren Übergang zu höheren Privilegien.

Ein ungewöhnliches, root-eigenes SUID-`jjs` sollte gesondert auf Dateizugriffe geprüft werden, wenn der aktuelle Benutzer es ausführen kann. Das veraltete Nashorn-Tool kann auf Java-Datei-APIs zugreifen, selbst wenn eine gestartete Shell eine Effective UID verwirft. Prüfen Sie das Verhalten der installierten JVM, die Effective Identity des Dateizugriffs sowie `nosuid`/`no_new_privs`, bevor Sie den Zugriff als privilegiertes Lesen oder Schreiben einstufen. [Oracle hat `jjs` in JDK 15 entfernt](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); ein installierter Pfad kann dennoch auf einen älteren oder separat paketierten Build verweisen. [GTFOBins dokumentiert die Datei-APIs](https://gtfobins.org/gtfobins/jjs/), doch die sudo-Beispiele belegen nicht, dass sich jeder Build unter SUID genauso verhält. Rufen Sie das Tool während einer passiven Aufzählung nicht auf.

Eine root-eigene SUID-`gosu`-Datei, auf die ein Benutzer mit geringeren Privilegien zugreifen kann, sollte geprüft werden: Die dokumentierte Schnittstelle akzeptiert einen Zielbenutzer und einen Befehl, aber beim normalen Einsatz in Containern wird sie als root gestartet, um Privilegien abzugeben. Prüfen Sie das SUID-Verhalten des installierten Builds, die Effective Identity und das User-Namespace-Mapping sowie `nosuid` und `no_new_privs`; root im Container bedeutet nicht root auf dem Host. Ein Dateiname oder SUID-Bit allein beweist keinen funktionierenden Übergang. Siehe die [Nutzungshinweise des Upstream-Projekts](https://github.com/tianon/gosu) und den [SUID-Warnhinweis des Maintainers](https://github.com/tianon/gosu/issues/11). Rufen Sie den Helper während einer passiven Bestandsaufnahme nicht auf.

Ein eigener Backup-Wrapper mit set-user-ID kann möglicherweise einen vom Aufrufer gewählten Pfad akzeptieren und ihn in einen an `system(3)` übergebenen Archivierungsbefehl einsetzen. Ist dieser Pfad im konstruierten Befehl nicht in Anführungszeichen gesetzt, kann die Kind-Shell [Tilde-Expansion anhand von `HOME`, Pfadnamensmuster wie `?` und `*` sowie Zeilentrennung durch Newlines anwenden](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); nur vertraute Satzzeichen in einer Denylist abzulehnen, macht den Pfad nicht zu einem Literal. Prüfen Sie offline den genauen Argumentfluss, die geerbte Umgebung, die Kind-Shell und ihre Effective Identity, den Dateisystemzugriff sowie, ob die Archivausgabe für den Aufrufer sichtbar ist. Das SUID-Bit, eine Zeichenkette für ein Archivierungstool oder allein die Ablehnung des Literals `/root` beweisen weder eine Offenlegung noch Codeausführung. Prüfen Sie eine Kopie des Wrappers offline, statt bei der passiven Aufzählung private Dateien zu archivieren oder fehlerauslösende Eingaben zu senden.

Eine weitere mögliche Lücke in einer Metazeichen-Denylist ist die Shell-[Befehlsersetzung](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html), etwa `$(...)`: Selbst ein festes, erlaubtes Befehlspräfix kann ein späteres, vom Aufrufer kontrolliertes Argument über `/bin/sh -c` weitergeben. Prüfen Sie offline die genaue Maskierung, den Parser und die Effective Identity; werten Sie eine `system()`-Zeichenkette oder eine unvollständige Denylist allein nicht als Beweis für Codeausführung.

Auch der **Aufrufprozessbaum** ist relevant. Ein Web-Worker kann einen seccomp-Filter einrichten, der Systemaufrufe zur Änderung der UID einschränkt; [seccomp-Filter werden an Kindprozesse weitergegeben und bleiben über `execve` erhalten](https://docs.kernel.org/userspace-api/seccomp_filter.html). Beispielsweise können die Apache-Direktiven [`LimitUIDRange` und `LimitGIDRange` von mpm-itk](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) die Identitäten einschränken, die Nachkommen annehmen können. `Seccomp: 2` in `/proc/self/status` zeigt den Filtermodus, nicht die Richtlinie oder ob dieser Helper die Identität seines Eigentümers annehmen kann. Prüfen Sie gemeinsam die tatsächliche Aufrufkette und den effektiven Filter sowie die SUID-, Mount- und `no_new_privs`-Bedingungen; für eine separate Login-Sitzung kann eine andere Richtlinie gelten, doch sie erfordert einen eigenen gültigen Zugriffsweg.

Ein eigenes SUID-Programm kann ein separates, lesbares Python-Skript aufrufen. Verwendet es tatsächlich **Python 2**, [wertet `input()` den eingegebenen Ausdruck aus](https://docs.python.org/2/library/functions.html#input); bei Python 3 gibt `input()` stattdessen Text zurück. Prüfen Sie die Effective Identity des Wrappers, den Interpreterpfad und die Version, den Skriptpfad sowie, ob nicht vertrauenswürdige Eingaben diesen Aufruf erreichen, bevor Sie die Quellcodezeile als Ausführungspfad einstufen. Ein set-ID-Bit auf dem Skript selbst oder ein `input()`-Aufruf ohne den privilegierten Wrapper bildet nicht dieselbe Vertrauensgrenze. Prüfen Sie die referenzierten Pfade der Binärdatei und einen begrenzten Ausschnitt des Skriptquellcodes, ohne das Programm während der Aufzählung auszuführen.

Wenn zu einer ungewöhnlichen SUID-Datei lesbarer Quellcode vorliegt, vergleichen Sie bei jedem vom Aufrufer kontrollierten Dateizugriff die angeforderte Bytemenge mit der Größe des Zielpuffers und prüfen Sie spätere Kontrollflussprüfungen. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) schreibt die angeforderten Elemente an den übergebenen Zeiger; die Funktion kennt die Kapazität des Zielobjekts nicht. Eine Größenabweichung ist ein statischer Hinweis auf ein Problem der Speichersicherheit, aber kein Beweis für eine nutzbare Privilegieneskalation: Bestätigen Sie, dass der Quellcode zur installierten Binärdatei passt, der Aufrufer die Eingabe bereitstellen kann, die SUID-Ausführung in diesem Kontext wirksam ist und der betreffende Pfad erreichbar ist. Prüfen Sie eine begrenzte Quellcode- oder Binärdateikopie offline, statt während der Aufzählung fehlerauslösende Eingaben an das privilegierte Programm zu senden.

Ein eigener SUID-Helper kann eine geschützte Datei offenlegen, ohne ihren Inhalt auszugeben. Wenn der Aufrufer sowohl einen Pfadnamen als auch einen regulären Ausdruck auswählt und der Helper unter seiner Effective UID eine sichtbare Trefferzahl zurückgibt, können verankerte Präfixtests als Zeichen-für-Zeichen-Orakel dienen. Prüfen Sie den Eigentümer des Helpers, das Verhalten seiner Effective ID, den Ausführungszugriff, Pfadbeschränkungen, die Semantik des regulären Ausdrucks, die Sichtbarkeit der Antwort und eine konkrete Datei mit höheren Privilegien, die der Aufrufer andernfalls nicht lesen kann. Ein SUID-Bit oder eine Zeichenkette für eine Regex-Bibliothek belegt keinen dieser Abläufe. Erfassen Sie bei der passiven Aufzählung die ungewöhnliche ausführbare Datei und prüfen Sie offline einen begrenzten Disassembly- oder Quellcodeausschnitt; testen Sie den Live-Helper nicht mit iterativen Vermutungen und geben Sie keine wiederhergestellten Geheimnisse aus.

Unter OpenBSD kann ein eigener Reader mit set-user-ID, der einen vom Aufrufer gewählten Pfad akzeptiert, Dateien unter `/var/backups` offenlegen, wenn seine Effective Identity sie lesen kann und er ihren Inhalt an den Aufrufer zurückgibt. [OpenBSDs `changelist(5)`](https://man.openbsd.org/changelist.5) beschreibt `.current`- und `.backup`-Kopien konfigurierter Pfade; Einträge mit vorangestelltem `+` speichern jedoch SHA-256-Prüfsummen statt Dateiinhalten. Das Backup-Verzeichnis sollte root gehören und den Modus `0700` haben. Eine [`unveil`-Leseregel](https://man.openbsd.org/unveil.2) des Helpers für `/var` kann den Zugriff unterhalb dieses Pfads erlauben, gewährt oder beweist für sich genommen aber keinen Dateizugriff. Prüfen Sie die tatsächliche Effective UID, die Ausführungsberechtigung des aktuellen Benutzers, den akzeptierten Pfad, das Vorhandensein und den Inhalt des Backups sowie etwaige unabhängige Authentifizierungsanforderungen, bevor Sie eine Privilegieneskalation behaupten. Die passive Aufzählung sollte den Helper und die Pfadmetadaten erfassen, den Reader aber nicht aufrufen oder Backup-Daten ausgeben.

Ein eigenes SUID-Programm, das einen vom Aufrufer gewählten Pfad mit [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) prüft und ihn später öffnet, kann ein Rennen auf eine Datei oder einen Symlink in einem vom Aufrufer beschreibbaren Verzeichnis ermöglichen. Die Prüfung bezieht sich auf das frühere Objekt, während ein späteres [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ein anderes auflösen kann. Prüfen Sie, ob der Helper mit erhöhter Effective Identity ausführbar ist, ein anderweitig erreichbarer Codepfad die ausgewählte Datei liest und der Aufrufer den Pfadnamen zwischen Prüfung und Öffnen austauschen kann; weder ein SUID-Bit noch ein beschreibbares Verzeichnis oder eine `stat`-Zeichenkette allein belegt dies. Für eine Offenlegung muss außerdem eine sichtbare Ausgabe oder ein für den Aufrufer lesbares Ziel vorhanden sein. Prüfen Sie die Binärdatei und Pfadmetadaten offline; lösen Sie bei der passiven Aufzählung kein Rennen mit dem Live-Helper aus.

Führen Sie dieselbe Abhängigkeitsprüfung bei SGID-Wrappern durch. Ein Wrapper, der eine Shell oder einen Helper über einen absoluten Pfad aufruft, kann dennoch unsicher sein, wenn ein Benutzer mit geringeren Privilegien diese Datei ersetzen kann; der gestartete Code kann die Effective Group des Wrappers erben. Prüfen Sie den genau aufgerufenen Pfad, dessen Schreibberechtigungen (einschließlich ACLs), die Effective Group des Wrappers und ob er vor dem Start des Kindprozesses Privilegien abgibt. Ein Interpreter kann geerbte Effective IDs ebenfalls verwerfen; unterscheiden Sie daher einen Prüfungsansatzpunkt von einem nachgewiesenen Übergang. Eine irgendwo auf dem Host beschreibbare Shell beweist allein nicht, dass ein privilegierter Wrapper sie aufruft.

### Privilegierte Wrapper, die SQL an die SQLite-CLI übergeben

Wenn ein eigenes SUID-Programm benutzerkontrolliertes SQL an das **Kommandozeilenprogramm `sqlite3`** übergibt, prüfen Sie den genauen Befehl und die Effective Identity, bevor Sie die Abfrage als schreibgeschützt einstufen. Die SQL-Funktion `edit()` der CLI ruft einen Editor auf (aus dem zweiten Argument oder aus `VISUAL`); ihre SQL-Funktion `load_extension()` kann eine Shared Library laden, wenn das Laden von Erweiterungen aktiviert ist. Das sind mögliche Codeausführungspfade mit der Identity des CLI-Prozesses, selbst wenn der Wrapper `PATH` festlegt oder einen absoluten Pfad zu `sqlite3` verwendet. Das SQL muss diese Funktionen tatsächlich erreichen und die CLI muss die jeweilige Funktion unterstützen; `sqlite3` lediglich in einer Binärdatei oder auf dem Host zu finden, ist kein Beleg für eine Privilegieneskalation. Die SQLite-**Bibliothek** deaktiviert das Laden von Erweiterungen standardmäßig; unterscheiden Sie sie von der CLI. Wenn eine privilegierte Anwendung nicht vertrauenswürdiges SQL verarbeiten muss, deaktiviert der `--safe`-Modus der SQLite-CLI `edit()`, `load_extension()` und weitere Funktionen mit Seiteneffekten. Siehe die [Dokumentation zur SQLite-CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), die [Dokumentation zum Safe Mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) und die [Dokumentation zum Laden von Erweiterungen](https://www.sqlite.org/loadext.html#loading_an_extension).

### Privilegierte Datei-Reader, deren Ausgabe an einen ausführlichen Client geht

Ein eigener SUID/SGID-Wrapper kann den Zugriff auf einen vom Aufrufer ausgewählten Pfad prüfen und die Datei anschließend an einen anderen Befehl übergeben. Prüfen Sie die Effective Identity sowohl bei der Zugriffsprüfung als auch beim späteren Öffnen, lösen Sie etwaige `../`-Komponenten relativ zum tatsächlichen Basisverzeichnis auf und untersuchen Sie, wie der Kindprozess ungültige Eingaben behandelt. Wenn ein Datenbankclient eine private Datei als SQL mit ausführlicher Ausgabe liest, kann er den Dateiinhalt in Fehlermeldungen wiedergeben, selbst wenn das SQL ungültig ist. Eine Offenlegung über Benutzergrenzen hinweg liegt nur dann vor, wenn der Kindprozess eine Datei lesen kann, die der Aufrufer nicht lesen kann, der Aufrufer diese Datei über den Wrapper auswählen kann und die Ausgabe sichtbar ist; das bloße Vorhandensein von `mysql` oder einer anderen Client-Zeichenkette belegt keine dieser Bedingungen.

### Netdata-`ndsudo`-Suchpfad

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) betraf einige Netdata-`ndsudo`-Builds. Der root-eigene SUID-Helper suchte anhand eines vom Aufrufer bereitgestellten `PATH` nach den zulässigen externen Befehlen. Prüfen Sie einen installierten Helper – auch außerhalb des üblichen `PATH` des Aufrufers – nur, wenn das aktuelle Konto ihn ausführen kann. Bestätigen Sie Eigentümer, SUID-Bit, Ausführungszugriff (einschließlich Gruppen-/ACL-Berechtigungen), installierten Build und Patch-Status des Herstellers sowie, ob `NoNewPrivs` oder ein `nosuid`-Mount die Identitätsänderung verhindert. Netdata nennt die gepatchten Builds `v1.45.3` und `v1.45.0-169`; Distributions-Backports müssen gesondert bestätigt werden. Eine Dashboard-Version oder das bloße Vorhandensein von `ndsudo` reicht nicht als Nachweis für eine erreichbare Privilegieneskalation. Das Pfadproblem setzt außerdem voraus, dass der Helper einen externen Befehl über einen vom Aufrufer kontrollierten Pfad auflöst.

### Firejail-Privilegiengrenze bei `join`

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) betraf Firejails privilegierte `--join`-Logik: Ein präpariertes Join-Ziel konnte den setuid-root-Helper dazu bringen, einen vom Angreifer kontrollierten Mount-Namespace zu akzeptieren und unsichere Sicherheitszustände zu kopieren. Prüfen Sie bei einer passiven Triage, ob die **aktuelle Identity eine root-eigene setuid-Firejail-Binärdatei ausführen kann**, ob setuid auf ihrem Mount und im Prozesskontext wirksam ist und ob dem installierten Build der Fix fehlt. Upstream hat das Problem in [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) behoben; Distributionspakete können den Fix [zurückportieren](https://github.com/netblue30/firejail/issues/5191), während sie weiterhin eine ältere Version anzeigen. Diese Voraussetzungen kennzeichnen einen Prüfungsansatzpunkt, nicht einen erfolgreichen Join oder eine Root-Shell. Erstellen Sie bei der Aufzählung kein gefälschtes Jail und rufen Sie `--join` nicht auf.

### GNU Screen-Logfile-Berechtigungen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) betraf Screen 4.5.0, das ein vom Aufrufer gewähltes Logfile mit erhöhten Privilegien öffnete. Eine `screen`- oder versionierte Binärdatei im SUID-Bestand ist lediglich ein Prüfungsansatzpunkt: Bestätigen Sie den Eigentümer root, die wirksame SUID-Ausführung für den aktuellen Benutzer, den installierten Build, den Patch-Status der Distribution und das betroffene Logfile-Verhalten. [Debian hat sein 4.5.0-Paket mit einem Backport behoben](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), daher belegen eine Versionszeichenkette oder ein Dateiname allein keine Anfälligkeit. Erstellen Sie nicht als routinemäßigen Aufzählungstest ein Logfile.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) betraf den privilegierten S-nail-Mail-Lock-Helper, wenn eine vom Aufrufer kontrollierte Pfadkomponente Verzeichniswechsel erlaubte und zu beliebigen Dateischreibvorgängen führen konnte. Prüfen Sie, ob der aktuelle Benutzer einen installierten root-eigenen setuid-Helper ausführen kann, ob dessen setuid-Identity unter den Mount- und Prozessrichtlinien wirksam ist sowie den genauen Paket-Build und den Fix des Herstellers. [Ubuntus Sicherheitshinweis](https://ubuntu.com/security/notices/USN-4820-1) führt einen zurückportierten Fix für sein Paket von 16.04 auf; eine Version, die wie die Upstream-Version aussieht, ist daher nicht aussagekräftig genug. Das Vorhandensein des Helpers beweist weder, dass der betroffene Pfad erreichbar ist, noch, dass ein Dateischreibvorgang zur Codeausführung als root führt. Prüfen Sie Metadaten und Paketstatus, ohne den Helper aufzurufen oder bei der Aufzählung das Rennen zu versuchen.

### snap-confine und tmpfiles-Bereinigung

CVE-2026-3888 ist ein Race zwischen dem privilegierten `snap-confine` und der systemd-tmpfiles-Bereinigung von `/tmp`. Bei einer passiven Prüfung können Sie feststellen, ob `snap-confine` setuid ist oder Dateifähigkeiten besitzt, das installierte `snapd`-Paket mit der behobenen Version für diese **Ubuntu-Version** vergleichen und die effektive Altersregel für `/tmp` sowie den Bereinigungstimer untersuchen. Ein passendes Paket und eine passende Regel sind Voraussetzungen, aber kein Beweis dafür, dass das Race erreichbar ist: Laufzeitstatus des Timers, Snap-Layout, Paket-Backports und Regelüberschreibungen sind ebenfalls relevant. Bei älteren Versionen kann eine nicht standardmäßige Konfiguration erforderlich sein. Führen Sie bei der routinemäßigen Aufzählung keinen Race-Test aus. Siehe den [Ubuntu-CVE-Eintrag](https://ubuntu.com/security/CVE-2026-3888) zum Paketstatus der jeweiligen Version und den [Qualys-Hinweis](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) zur Interaktion der Komponenten.

## ACLs und sensible Pfade prüfen

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ein beschreibbares übergeordnetes Verzeichnis kann das Ersetzen einer Datei ermöglichen, selbst wenn die Datei selbst root gehört. Eine ACL kann unauffällig Zugriff auf eine sudoers-Ergänzung, eine Service-Unit, ein Cron-Skript, einen Bibliothekspfad oder eine Credential-Datei gewähren. Prüfe sowohl die ACL als auch den vollständigen Pfad. Wenn beliebige privilegierte Dateischreibvorgänge möglich sind, folge [Arbitrary File Write to Root](write-to-root.md); Beispiele zu Linker-Konfiguration und Preload findest du unter [`ld.so` example](ld.so.conf-example.md). Betrachte offengelegte Backups, `.env`-Dateien, Datenbankkonfigurationen, SSH-Material und den Verlauf als mögliche Quellen für Credentials.
