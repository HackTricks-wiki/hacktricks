# SUID, SGID, ACL e file sensibili

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID modificano l'identità effettiva di un file eseguito; le ACL possono concedere accessi non visibili nei normali bit di modalità mostrati da `ls -l`. Controlla entrambi quando un utente può leggere, scrivere o eseguire file oltre quanto suggerito dai permessi apparenti di proprietario e gruppo.

## Enumerare gli eseguibili privilegiati

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrati sugli eseguibili personalizzati o modificati di recente, sui proprietari insoliti e sui file in mount scrivibili. Un mount `nosuid` può sopprimere il comportamento set-ID; le file capabilities sono un meccanismo di privilegio separato descritto in [Linux capabilities](linux-capabilities.md). Confronta un binario sospetto con il pacchetto corrispondente e controlla cosa esegue, apre o carica con identità elevata.

Per un eseguibile SUID di proprietà di root che non conosci e che accetta input dal chiamante, esamina offline una copia del binario per individuare la gestione non sicura della memoria degli argomenti e il percorso del codice che la raggiunge. Registra il comportamento degli ID effettivi e le mitigazioni, come stack canary, memoria non eseguibile, codice position-independent e randomizzazione degli indirizzi. Il nome di una funzione non sicura o una mitigazione mancante sono solo spunti per la revisione: la possibilità di sfruttamento dipende dai limiti effettivi dell’input, dal flusso di controllo raggiungibile e dall’identità effettiva al momento dell’errore. Durante l’enumerazione passiva, non inviare argomenti lunghi all’eseguibile privilegiato in esecuzione solo per verificare se va in crash.

Anche un programma SUID noto può essere sostituito o backdoored. Una data di modifica recente è uno spunto, non una prova: per uno **specifico binario sospetto appartenente a un pacchetto**, individua il pacchetto proprietario e confronta il file installato con i metadati del pacchetto, invece di verificare ogni pacchetto durante l’enumerazione di routine:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` controlla il contenuto dei file solo quando il database dei pacchetti registra un checksum; RPM confronta anche metadati come modalità e proprietario. Concentrati su una discrepanza relativa all’**eseguibile privilegiato stesso**: le installazioni ridotte possono segnalare documentazione o file locali mancanti altrove nello stesso pacchetto. Confronta l’eseguibile sospetto con un pacchetto del fornitore attendibile ed esamina il codice esatto modificato. Modifiche locali legittime, checksum assenti e metadati dei pacchetti compromessi limitano ciò che dimostra ciascun comando. Non eseguire il programma SUID sospetto né uno script di verifica del pacchetto durante il triage passivo. Consulta il [manuale di verifica di dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e il [manuale di verifica di RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programma SUID che richiama una shell, un comando relativo o una libreria da un percorso scrivibile può oltrepassare un confine di fiducia. Consulta [abuso di librerie condivise e linker SUID](suid-shared-library-and-linker-abuse.md), le [indicazioni su PATH](../linux-basics/linux-environment-variables.md#path) e la [spiegazione degli user ID](../user-information/euid-ruid-suid.md). Per le escape note specifiche di un comando, consulta [GTFOBins](https://gtfobins.github.io/) verificando il binario esatto e l’invocazione consentita sull’host.

Per un eseguibile set-user-ID, distingui l’**UID reale** del chiamante dall’**UID effettivo** del proprietario del file: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lascia invariato l’UID reale e, dopo ogni modifica set-ID, copia l’UID effettivo nell’UID salvato. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) esegue il comando tramite `/bin/sh -c`; la shell selezionata da quel percorso influisce sulla possibilità che un processo figlio mantenga la propria identità effettiva. In particolare, le [regole della modalità privilegiata di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) reimpostano l’UID effettivo, se diverso, sull’UID reale quando Bash viene avviata senza `-p`. Verifica le modifiche effettive agli UID dell’helper e l’invocazione del processo figlio, insieme al proprietario, ai permessi di esecuzione, all’opzione di mount `nosuid` e allo stato `no_new_privs` del processo. Un bit SUID o una chiamata a una shell, da soli, non dimostrano che sia possibile effettuare una transizione a privilegi superiori.

Un `jjs` SUID di proprietà di root e insolito merita una verifica separata dell’accesso ai file, se l’utente corrente può eseguirlo. Il vecchio strumento Nashorn può accedere alle API Java per i file anche quando una shell avviata come processo figlio perde l’UID effettivo; verifica il comportamento della JVM installata, l’identità effettiva dell’operazione sul file e `nosuid`/`no_new_privs` prima di considerarlo un accesso privilegiato in lettura o scrittura. [Oracle ha rimosso `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); un percorso installato potrebbe comunque corrispondere a una build precedente o distribuita separatamente. [GTFOBins documenta le API per i file](https://gtfobins.org/gtfobins/jjs/), ma i suoi esempi con sudo non dimostrano il comportamento SUID di ogni build. Non invocare lo strumento durante l’enumerazione passiva.

Un eseguibile `gosu` SUID di proprietà di root e accessibile a un utente con privilegi inferiori merita una verifica: la sua interfaccia documentata accetta un utente di destinazione e un comando, ma nel normale uso dei container viene avviato come root per abbassare i privilegi. Verifica il comportamento SUID della build installata, l’identità effettiva e la mappatura dello user namespace, oltre a `nosuid` e `no_new_privs`; essere root nel container non implica esserlo sull’host. Il solo nome del file o bit SUID non dimostra che la transizione funzioni. Consulta l’[uso documentato a monte](https://github.com/tianon/gosu) e l’[avviso SUID del manutentore](https://github.com/tianon/gosu/issues/11). Non invocare l’helper durante l’inventario passivo.

Un wrapper di backup personalizzato set-user-ID potrebbe accettare un percorso scelto dal chiamante e interpolarlo in un comando di archiviazione passato a `system(3)`. Se il percorso non è racchiuso tra virgolette nel comando costruito, la shell figlia può applicare [l’espansione della tilde usando `HOME`, i pattern di percorso come `?` e `*` e la separazione dei comandi tramite newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rifiutare solo la punteggiatura più comune con una denylist non rende letterale il percorso. Verifica il flusso esatto degli argomenti, l’ambiente ereditato, la shell figlia e l’identità effettiva, l’accesso al filesystem e l’eventuale visibilità dell’output dell’archiviatore per il chiamante. Il bit SUID, una stringa relativa a uno strumento di archiviazione o il solo blocco del percorso letterale `/root` non dimostrano né la divulgazione né l’esecuzione di codice. Esamina offline una copia del wrapper invece di archiviare file privati o inviare input che causano crash durante l’enumerazione passiva.

La [sostituzione di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) della shell, come `$(...)`, è un’altra possibile lacuna in una denylist di metacaratteri: anche un prefisso di comando consentito fisso può passare un argomento successivo controllato dal chiamante a `/bin/sh -c`. Verifica offline le virgolette esatte, il parser e l’identità effettiva; una stringa `system()` o una denylist incompleta, da sole, non dimostrano l’esecuzione.

Conta anche l’**albero dei processi chiamanti**. Un worker web può installare un filtro seccomp che limita le chiamate di sistema che modificano gli UID; i [filtri seccomp vengono ereditati dai processi figli e sopravvivono a `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Per esempio, le direttive [mpm-itk `LimitUIDRange` e `LimitGIDRange` di Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) possono limitare le identità raggiungibili dai processi discendenti. `Seccomp: 2` in `/proc/self/status` indica la modalità del filtro, non la policy né se questo specifico helper possa acquisire l’identità del proprietario. Esamina insieme la catena di processi dell’invocazione effettiva, il filtro applicato, le condizioni SUID, di mount e `no_new_privs`; una sessione di login separata potrebbe avere una policy diversa, ma richiede un proprio percorso di accesso valido.

Un eseguibile personalizzato SUID può invocare uno script Python separato e leggibile. Se usa effettivamente **Python 2**, [`input()` valuta l’espressione inserita](https://docs.python.org/2/library/functions.html#input); in Python 3, `input()` restituisce invece testo. Verifica l’identità effettiva del wrapper, il percorso e la versione dell’interprete, il percorso dello script e se l’input non attendibile raggiunge quella chiamata prima di considerare la riga di codice un percorso di esecuzione. Il bit set-ID sullo script stesso o una chiamata a `input()` senza il wrapper privilegiato non stabiliscono lo stesso confine. Durante l’enumerazione, esamina i percorsi a cui fa riferimento il binario e una porzione circoscritta del codice sorgente dello script, senza eseguirlo.

Se un eseguibile SUID insolito è accompagnato da codice sorgente leggibile, confronta il numero di byte richiesto per ogni lettura di file controllata dal chiamante con la dimensione del buffer di destinazione ed esamina i successivi controlli del flusso di esecuzione. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) memorizza gli elementi richiesti all’indirizzo fornito; non conosce la capacità dell’oggetto di destinazione. Una discrepanza di dimensioni è un indizio statico di un problema di sicurezza della memoria, non la prova di un’escalation di privilegi sfruttabile: verifica che il sorgente corrisponda al binario installato, che il chiamante possa fornire l’input, che l’esecuzione SUID sia effettiva in quel contesto e che il percorso pertinente sia raggiungibile. Durante l’enumerazione, esamina offline una copia circoscritta del sorgente o del binario, invece di inviare input che causano crash al programma privilegiato.

Un helper personalizzato SUID può divulgare un file protetto senza stamparne il contenuto. Se il chiamante sceglie sia un percorso sia un’espressione regolare e l’helper restituisce un conteggio visibile delle corrispondenze usando il proprio UID effettivo, test con prefissi ancorati possono formare un oracolo carattere per carattere. Verifica il proprietario dell’helper, il comportamento degli ID effettivi, i permessi di esecuzione, le restrizioni sui percorsi, la semantica delle espressioni regolari, la visibilità della risposta e l’esistenza di uno specifico file con privilegi superiori che il chiamante non può leggere altrimenti. Un bit SUID o una stringa relativa a una libreria regex, da soli, non dimostrano nessuno di questi passaggi. Durante l’enumerazione passiva, registra l’eseguibile insolito ed esamina offline un disassemblato circoscritto o una copia del sorgente; non eseguire tentativi iterativi sull’helper attivo né stampare segreti recuperati.

Su OpenBSD, un reader personalizzato set-user-ID che accetta un percorso scelto dal chiamante può esporre file in `/var/backups` se la sua identità effettiva può leggerli e ne restituisce il contenuto al chiamante. [`changelist(5)` di OpenBSD](https://man.openbsd.org/changelist.5) descrive le copie `.current` e `.backup` dei percorsi configurati, ma le voci con prefisso `+` memorizzano checksum SHA-256 anziché il contenuto dei file; la directory di backup dovrebbe essere di proprietà di root e avere modalità `0700`. Una regola di lettura [`unveil` dell’helper](https://man.openbsd.org/unveil.2) per `/var` può consentire l’accesso sotto quel percorso, ma non concede né dimostra di per sé l’accesso ai file. Verifica l’UID effettivo, i permessi di esecuzione per l’utente corrente, il percorso accettato, l’esistenza e il contenuto del backup e ogni requisito di autenticazione indipendente, prima di affermare che si tratti di un’escalation. L’enumerazione passiva dovrebbe segnalare l’helper e i metadati del percorso, non invocare il reader né stampare i dati di backup.

Un programma personalizzato SUID che controlla un percorso scelto dal chiamante con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e apre quel percorso in seguito può subire una race con la modifica di un file o di un symlink in una directory scrivibile dal chiamante. Il controllo si applica all’oggetto precedente, mentre una successiva [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) potrebbe risolverne un altro. Verifica che l’helper sia eseguibile con identità effettiva elevata, che un percorso di esecuzione altrimenti raggiungibile legga il file selezionato e che il chiamante possa sostituire il percorso tra il controllo e l’apertura; né il bit SUID, né una directory scrivibile, né una stringa `stat`, da soli, dimostrano alcuna di queste condizioni. Per una divulgazione è inoltre necessario che l’output sia visibile o che la destinazione sia leggibile dal chiamante. Esamina offline il binario e i metadati del percorso; non tentare una race sull’helper attivo durante l’enumerazione passiva.

Applica la stessa verifica delle dipendenze ai wrapper SGID. Un wrapper che avvia una shell o un helper tramite un percorso assoluto può comunque essere insicuro se un utente con privilegi inferiori può sostituire quel file; il codice avviato potrebbe ereditare il gruppo effettivo del wrapper. Controlla il percorso invocato esatto, i relativi permessi di scrittura (inclusi gli ACL), il gruppo effettivo del wrapper e se questo abbassa i privilegi prima di avviare il processo figlio. Anche un interprete può scartare gli ID effettivi ereditati: distingui quindi un possibile candidato da una transizione dimostrata. La presenza di una shell scrivibile altrove sull’host, da sola, non dimostra che un wrapper privilegiato la invochi.

### Wrapper privilegiati che passano SQL alla CLI di SQLite

Se un programma personalizzato SUID passa SQL controllato dall’utente al **programma a riga di comando `sqlite3`**, esamina il comando esatto e l’identità effettiva prima di considerare la query di sola lettura. La funzione SQL `edit()` della CLI avvia un editor (specificato nel secondo argomento o in `VISUAL`), mentre la funzione SQL `load_extension()` può caricare una libreria condivisa se il caricamento delle estensioni è abilitato. Sono potenziali percorsi di esecuzione di codice con l’identità del processo CLI, anche se il wrapper imposta `PATH` o usa un percorso assoluto per `sqlite3`. L’SQL deve effettivamente raggiungere quelle funzioni e la CLI deve mantenere attiva la funzionalità pertinente; trovare `sqlite3` in un binario o sull’host, da solo, non dimostra un’escalation. La **libreria** SQLite disabilita per impostazione predefinita il caricamento delle estensioni, quindi distinguila dalla CLI. Quando un’applicazione privilegiata deve elaborare SQL non attendibile, la modalità `--safe` della CLI di SQLite disabilita `edit()`, `load_extension()` e altre funzioni con effetti collaterali. Consulta la [documentazione della CLI di SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentazione della modalità sicura](https://www.sqlite.org/cli.html#the_safe_command_line_option) e la [documentazione sul caricamento delle estensioni](https://www.sqlite.org/loadext.html#loading_an_extension).

### Reader di file privilegiati che passano dati a un client verboso

Un wrapper personalizzato SUID/SGID può controllare l’accesso a un percorso scelto dal chiamante e poi passare quel file a un altro comando. Verifica l’identità effettiva sia durante il controllo dell’accesso sia alla successiva apertura, risolvi eventuali componenti `../` rispetto alla vera directory di base ed esamina come il processo figlio gestisce gli input non validi. Se un client di database legge un file privato come SQL producendo output verboso, potrebbe ripetere il contenuto del file nei messaggi di errore, anche se l’SQL non è valido. Si tratta di una divulgazione tra utenti solo se il processo figlio può leggere un file che il chiamante non può leggere, il chiamante può selezionare quel file tramite il wrapper e l’output è visibile; la sola presenza di `mysql` o della stringa di un altro client non dimostra nessuna di queste condizioni.

### Percorso di ricerca di Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ha interessato alcune build di Netdata `ndsudo`. L’helper SUID di proprietà di root cercava i comandi esterni consentiti usando un `PATH` fornito dal chiamante. Esamina un helper installato, anche se si trova al di fuori del `PATH` abituale del chiamante, solo quando l’account corrente può eseguirlo. Verifica il proprietario, il bit SUID, i permessi di esecuzione (inclusi i permessi di gruppo/ACL), la build installata e lo stato delle patch del fornitore, nonché se `NoNewPrivs` o un mount `nosuid` blocca il cambio d’identità. Netdata indica come corrette le build `v1.45.3` e `v1.45.0-169`; i backport delle distribuzioni richiedono una verifica separata. La versione del dashboard o la sola presenza di `ndsudo` non costituiscono prove sufficienti di un’escalation raggiungibile. Il problema del percorso richiede inoltre che l’helper risolva un comando esterno tramite una posizione controllata dal chiamante.

### Confine di privilegi di Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ha interessato la logica privilegiata `--join` di Firejail: un target join appositamente predisposto poteva indurre l’helper setuid-root ad accettare un mount namespace controllato dall’attaccante e a copiare uno stato di sicurezza non sicuro. Nel triage passivo, verifica che l’**identità corrente possa eseguire** un binario Firejail setuid di proprietà di root, che setuid sia effettivo sul suo mount e nel contesto del processo e che la build installata non contenga la correzione. Il progetto upstream ha corretto il problema nella versione [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); i pacchetti delle distribuzioni potrebbero aver [incluso la correzione tramite backport](https://github.com/netblue30/firejail/issues/5191) pur mostrando una versione precedente. Questi prerequisiti identificano un candidato da esaminare, non dimostrano un join riuscito o una shell root. Non creare un jail falso né invocare `--join` durante l’enumerazione.

### Permessi dei file di log di GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) riguardava Screen 4.5.0, che apriva un file di log scelto dal chiamante con privilegi elevati. Un binario `screen` o con suffisso di versione nell’inventario SUID è solo un indizio da esaminare: verifica la proprietà di root, l’effettiva esecuzione SUID per l’utente corrente, la build installata e lo stato delle patch della distribuzione, nonché il comportamento interessato relativo ai file di log. [Debian ha corretto il proprio pacchetto 4.5.0 con un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), quindi una stringa di versione o il solo nome del file non dimostrano l’esposizione. Non creare un file di log come sonda di routine durante l’enumerazione.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ha interessato l’helper privilegiato di S-nail per i lock dei file di posta, quando un componente del percorso controllato dal chiamante poteva attraversare directory e causare la scrittura arbitraria di un file. Verifica se l’utente corrente può eseguire un helper setuid installato di proprietà di root, se l’identità setuid è effettiva secondo le policy di mount e di processo e qual è la build esatta del pacchetto e la correzione del fornitore. L’[avviso di sicurezza di Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indica una correzione retroportata per il pacchetto 16.04, quindi una versione apparentemente upstream non è conclusiva. La presenza dell’helper non dimostra che il percorso interessato sia raggiungibile né che una scrittura di file permetta l’esecuzione come root; durante l’enumerazione, esamina i metadati e lo stato del pacchetto senza invocare l’helper né tentare la race.

### snap-confine e pulizia di tmpfiles

CVE-2026-3888 è una race che coinvolge `snap-confine` privilegiato e la pulizia di `/tmp` da parte di systemd-tmpfiles. Una verifica passiva può controllare se `snap-confine` è setuid o dispone di file capabilities, confrontare il pacchetto `snapd` installato con la versione corretta per quella **release di Ubuntu** ed esaminare la regola di scadenza effettiva di `/tmp` e il timer di pulizia. Un pacchetto e una regola corrispondenti sono prerequisiti, non la prova che la race sia raggiungibile: contano anche lo stato runtime del timer, la configurazione di snap, i backport dei pacchetti e le modifiche alla regola. Le release più vecchie potrebbero richiedere una configurazione non predefinita. Non eseguire una sonda per la race durante l’enumerazione di routine. Consulta la [scheda CVE di Ubuntu](https://ubuntu.com/security/CVE-2026-3888) per lo stato dei pacchetti specifico per release e l’[avviso di Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) per l’interazione tra i componenti.

## Esaminare ACL e percorsi sensibili

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Una directory padre scrivibile può consentire la sostituzione anche quando il file è di proprietà di root. Una ACL può concedere silenziosamente l'accesso a un file aggiuntivo di sudoers, a un'unità di servizio, a uno script cron, a un percorso di librerie o a un file di credenziali. Controlla sia l'ACL sia l'intero percorso. Se sono possibili scritture arbitrarie su file privilegiati, consulta [Arbitrary File Write to Root](write-to-root.md); per la configurazione del linker e i casi preload, vedi l'[esempio `ld.so`](ld.so.conf-example.md). Considera i backup esposti, i file `.env`, le configurazioni dei database, il materiale SSH e la cronologia come possibili fonti di credenziali; l'accesso dipende dai permessi effettivi di ciascun file.
