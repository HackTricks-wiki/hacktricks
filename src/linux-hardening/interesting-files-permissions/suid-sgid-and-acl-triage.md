# SUID, SGID, ACLs e arquivos sensíveis

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID alteram a identidade efetiva de um arquivo executado; ACLs podem conceder acesso que os bits de modo comuns do `ls -l` não mostram. Verifique ambos quando um usuário puder ler, gravar ou executar mais do que as permissões aparentes do proprietário e do grupo sugerem.

## Enumerar executáveis privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentre-se em executáveis personalizados ou alterados recentemente, proprietários incomuns e arquivos em montagens graváveis. Uma montagem `nosuid` pode suprimir o comportamento set-ID; file capabilities são um mecanismo de privilégio separado, descrito em [Linux capabilities](linux-capabilities.md). Compare um binário suspeito com o pacote correspondente e verifique o que ele executa, abre ou carrega com identidade elevada.

Para um executável SUID desconhecido, pertencente ao root e que aceita entrada do chamador, analise uma cópia do binário offline para identificar tratamento de argumentos vulnerável a problemas de memória e o caminho de código que o alcança. Registre o comportamento dos IDs efetivos e as mitigações, como stack canaries, memória não executável, código independente de posição e randomização de endereços. O nome de uma função insegura ou a ausência de uma mitigação é apenas um indício para análise: a possibilidade de exploração depende dos limites reais da entrada, do fluxo de controle alcançável e da identidade efetiva no momento da falha. Não envie argumentos longos ao executável privilegiado em produção apenas para testar se ele trava durante a enumeração passiva.

Um programa SUID conhecido também pode ter sido substituído ou receber um backdoor. Uma data de modificação recente é um indício, não uma prova: para um **binário empacotado específico e suspeito**, identifique o pacote proprietário e compare o arquivo instalado com os metadados do pacote, em vez de verificar todos os pacotes durante a enumeração de rotina:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` verifica o conteúdo dos arquivos somente quando o banco de dados do pacote tem um checksum registrado; o RPM também compara metadados, como modo e proprietário. Concentre-se em uma divergência no **próprio executável privilegiado**: instalações enxutas podem reportar documentação ou arquivos de localização ausentes em outras partes do mesmo pacote. Compare um executável suspeito com um pacote confiável do fornecedor e examine exatamente o código alterado. Alterações locais legítimas, checksums ausentes e metadados de pacote comprometidos limitam o que qualquer um dos comandos pode comprovar. Não execute o programa SUID suspeito nem um script de verificação de pacotes durante a triagem passiva. Consulte o [manual de verificação do dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e o [manual de verificação do RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Um programa SUID que invoca um shell, comando relativo ou biblioteca de um caminho gravável pode cruzar uma fronteira de confiança. Consulte [abuso de bibliotecas compartilhadas e do linker com SUID](suid-shared-library-and-linker-abuse.md), as [orientações sobre PATH](../linux-basics/linux-environment-variables.md#path) e a [explicação sobre user-ID](../user-information/euid-ruid-suid.md). Para escapes conhecidos específicos de comandos, consulte [GTFOBins](https://gtfobins.github.io/) para o binário exato e a invocação permitida no host.

Para um executável set-user-ID, diferencie o **UID real** de quem o chamou do **UID efetivo** do proprietário do arquivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) mantém o UID real inalterado e copia o UID efetivo para o UID salvo após qualquer alteração set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) executa seu comando por meio de `/bin/sh -c`; o shell selecionado por esse caminho afeta se um processo filho mantém sua identidade efetiva. Em particular, as [regras do modo privilegiado do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) redefinem um UID efetivo diferente para o UID real quando o Bash inicia sem `-p`. Verifique as alterações de UID e a invocação de processos filhos do helper real, além de seu proprietário, acesso de execução, configuração de montagem `nosuid` e estado `no_new_privs` do processo. O bit SUID ou uma chamada ao shell, isoladamente, não comprovam uma transição utilizável para privilégios mais altos.

Um `jjs` SUID incomum pertencente ao root merece uma análise separada do acesso a arquivos, caso o usuário atual possa executá-lo. A ferramenta Nashorn legada pode acessar APIs de arquivos do Java mesmo quando um shell iniciado por ela descarta um UID efetivo; confirme o comportamento da JVM instalada, a identidade efetiva da operação no arquivo e as condições `nosuid`/`no_new_privs` antes de considerá-la uma leitura ou gravação privilegiada. [A Oracle removeu o `jjs` no JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); um caminho instalado ainda pode corresponder a uma versão mais antiga ou a um build empacotado separadamente. [GTFOBins documenta as APIs de arquivos](https://gtfobins.org/gtfobins/jjs/), mas seus exemplos com sudo não comprovam o comportamento SUID em todos os builds. Não invoque a ferramenta durante a enumeração passiva.

Um executável `gosu` SUID pertencente ao root e acessível a um usuário com menos privilégios merece análise: sua interface documentada aceita um usuário-alvo e um comando, mas o uso normal em containers o inicia como root para descartar privilégios. Verifique o comportamento SUID do build instalado, a identidade efetiva e o mapeamento de user namespace, além de `nosuid` e `no_new_privs`; root em um container não implica root no host. O nome do arquivo ou o bit SUID, por si só, não comprovam uma transição funcional. Consulte o [uso no upstream](https://github.com/tianon/gosu) e o [aviso do mantenedor sobre SUID](https://github.com/tianon/gosu/issues/11). Não invoque o helper durante o inventário passivo.

Um wrapper de backup personalizado com set-user-ID pode aceitar um caminho escolhido por quem o chama e interpolá-lo em um comando de arquivamento passado a `system(3)`. Se esse caminho não estiver entre aspas no comando montado, o shell filho poderá aplicar [expansão de til usando `HOME`, padrões de nome de caminho como `?` e `*`, e separação de comandos por nova linha](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rejeitar apenas pontuações conhecidas por meio de uma denylist não torna o caminho literal. Confirme o fluxo exato dos argumentos, o ambiente herdado, o shell filho e a identidade efetiva, o acesso ao sistema de arquivos e se a saída do arquivamento fica visível para quem chamou. O bit SUID, uma string de ferramenta de arquivamento ou apenas um caminho `/root` bloqueado não comprovam divulgação nem execução de código. Analise uma cópia do wrapper offline, em vez de arquivar arquivos privados ou enviar entradas que provoquem falhas durante a enumeração passiva.

A [substituição de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) do shell, como `$(...)`, é outra possível brecha em uma denylist de metacaracteres: até mesmo um prefixo de comando fixo e permitido pode passar um argumento posterior, controlado por quem chamou, para `/bin/sh -c`. Verifique offline a citação, o parser e a identidade efetiva exatos; não considere uma string de `system()` ou uma denylist incompleta, isoladamente, como prova de execução.

A **árvore de processos que faz a chamada** também importa. Um worker web pode instalar um filtro seccomp que restringe chamadas de sistema que alteram UID; [filtros seccomp são herdados por processos filhos e persistem após `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por exemplo, as diretivas [`LimitUIDRange` e `LimitGIDRange` do mpm-itk do Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) podem restringir as identidades acessíveis aos descendentes. `Seccomp: 2` em `/proc/self/status` mostra o modo do filtro, não a política nem se esse helper específico pode obter a identidade de seu proprietário. Analise em conjunto a linhagem da invocação real e o filtro efetivo, bem como as condições de SUID, montagem e `no_new_privs`; uma sessão de login separada pode ter uma política diferente, mas exige seu próprio caminho de acesso válido.

Um executável SUID personalizado pode invocar um script Python separado e legível. Se ele realmente usa **Python 2**, [`input()` avalia a expressão inserida](https://docs.python.org/2/library/functions.html#input); em Python 3, `input()` retorna texto. Confirme a identidade efetiva do wrapper, o caminho e a versão do interpretador, o caminho do script e se uma entrada não confiável chega a essa chamada antes de considerar a linha de código um caminho de execução. Um bit set-ID no próprio script ou uma chamada a `input()` sem o wrapper privilegiado não estabelece a mesma fronteira. Durante a enumeração, examine os caminhos referenciados pelo binário e uma cópia limitada do código-fonte do script, sem executá-lo.

Se houver código-fonte legível junto de um executável SUID incomum, compare a quantidade de bytes solicitada em cada leitura de arquivo controlada por quem chama com o tamanho do buffer de destino e examine as verificações posteriores no fluxo de controle. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) armazena os itens solicitados no ponteiro fornecido; ela não conhece a capacidade do objeto de destino. Uma incompatibilidade de tamanho é uma pista estática de segurança de memória, não a prova de uma escalada de privilégios utilizável: confirme que o código-fonte corresponde ao binário instalado, que quem chamou pode fornecer a entrada, que a execução SUID é efetiva nesse contexto e que o caminho relevante é alcançável. Analise offline uma cópia limitada do código-fonte ou do binário, em vez de enviar entradas que provoquem falhas ao programa privilegiado durante a enumeração.

Um helper SUID personalizado pode revelar um arquivo protegido sem imprimir seu conteúdo. Se quem chama escolhe tanto um caminho quanto uma expressão regular, e o helper retorna uma contagem de correspondências visível usando seu UID efetivo, testes ancorados de prefixo podem formar um oracle caractere por caractere. Confirme o proprietário do helper, o comportamento do ID efetivo, o acesso de execução, as restrições de caminho, a semântica da expressão regular, a visibilidade da resposta e a existência de um arquivo específico de privilégios mais altos que quem chamou não possa ler de outra forma. O bit SUID ou uma string de biblioteca de regex, por si só, não comprova nenhum desses aspectos do fluxo. Durante a enumeração passiva, registre o executável incomum e analise offline uma cópia limitada do disassembly ou do código-fonte; não faça tentativas iterativas contra o helper em execução nem imprima segredos recuperados.

No OpenBSD, um leitor personalizado com set-user-ID que aceita um caminho escolhido por quem chama pode expor arquivos em `/var/backups` se sua identidade efetiva puder lê-los e ele retornar o conteúdo a quem chamou. [`changelist(5)` do OpenBSD](https://man.openbsd.org/changelist.5) descreve cópias `.current` e `.backup` de caminhos configurados, mas entradas prefixadas com `+` armazenam checksums SHA-256 em vez do conteúdo dos arquivos; o diretório de backup deve pertencer ao root e ter modo `0700`. Uma regra de leitura [`unveil` do helper](https://man.openbsd.org/unveil.2) para `/var` pode permitir acesso sob esse caminho, mas não concede nem comprova, por si só, o acesso aos arquivos. Antes de afirmar que há escalada, confirme o UID efetivo real, a permissão de execução para o usuário atual, o caminho aceito, a existência e o conteúdo do backup e quaisquer requisitos de autenticação independentes. A enumeração passiva deve registrar o helper e os metadados do caminho, não invocar o leitor nem imprimir dados de backup.

Um programa SUID personalizado que verifica um caminho escolhido por quem chama com [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e abre o caminho posteriormente pode sofrer uma corrida envolvendo a alteração de um arquivo ou link simbólico em um diretório gravável por quem chamou. A verificação se aplica ao objeto anterior, enquanto um [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) posterior pode resolver outro objeto. Confirme que o helper pode ser executado com identidade efetiva elevada, que um caminho de código alcançável lê o arquivo selecionado e que quem chamou pode substituir o caminho entre a verificação e a abertura; o bit SUID, um diretório gravável ou uma string `stat`, isoladamente, não comprovam nada disso. Para haver divulgação, também é necessária uma saída visível ou um destino legível por quem chamou. Analise offline o binário e os metadados do caminho; não provoque uma corrida contra o helper em execução durante a enumeração passiva.

Aplique a mesma análise de dependências a wrappers SGID. Um wrapper que executa um shell ou helper por caminho absoluto ainda pode ser inseguro se um usuário com menos privilégios puder substituir esse arquivo; o código iniciado pode herdar o grupo efetivo do wrapper. Verifique o caminho exato invocado, o acesso de gravação (incluindo ACLs), o grupo efetivo do wrapper e se ele descarta privilégios antes de iniciar o processo filho. Um interpretador também pode descartar IDs efetivos herdados, portanto diferencie um candidato a análise de uma transição comprovada. A existência de um shell gravável em outra parte do host, por si só, não prova que um wrapper privilegiado o invoque.

### Wrappers privilegiados que passam SQL para o CLI do SQLite

Se um programa SUID personalizado passa SQL controlado pelo usuário para o **programa de linha de comando `sqlite3`**, examine o comando exato e a identidade efetiva antes de considerar a consulta somente de leitura. A função SQL `edit()` do CLI invoca um editor (especificado no segundo argumento ou em `VISUAL`), e a função SQL `load_extension()` pode carregar uma biblioteca compartilhada quando o carregamento de extensões está habilitado. Esses são possíveis caminhos para execução de código com a identidade do processo CLI, mesmo que o wrapper fixe o `PATH` ou use um caminho absoluto para `sqlite3`. O SQL precisa de fato chegar a essas funções, e o CLI precisa manter o recurso relevante; encontrar apenas `sqlite3` em um binário ou no host não é evidência de escalada. A **biblioteca** SQLite desabilita o carregamento de extensões por padrão; diferencie-a do CLI. Quando um aplicativo privilegiado precisa processar SQL não confiável, o modo `--safe` do CLI do SQLite desabilita `edit()`, `load_extension()` e outras funções com efeitos colaterais. Consulte a [documentação do CLI do SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), a [documentação do modo seguro](https://www.sqlite.org/cli.html#the_safe_command_line_option) e a [documentação de carregamento de extensões](https://www.sqlite.org/loadext.html#loading_an_extension).

### Leitores privilegiados de arquivos que alimentam um cliente verboso

Um wrapper SUID/SGID personalizado pode verificar o acesso a um caminho escolhido por quem chama e, em seguida, passar esse arquivo a outro comando. Analise a identidade efetiva na verificação de acesso e na abertura posterior, resolva quaisquer componentes `../` em relação ao diretório-base real e examine como o processo filho lida com entradas inválidas. Se um cliente de banco de dados ler um arquivo privado como SQL com saída verbosa, poderá ecoar o conteúdo do arquivo em mensagens de erro, mesmo que o SQL seja inválido. Isso só constitui divulgação entre usuários quando o processo filho pode ler um arquivo que quem chamou não pode, quem chamou pode selecionar esse arquivo por meio do wrapper e a saída é visível; a presença de `mysql` ou de outra string de cliente, por si só, não comprova nenhuma dessas condições.

### Caminho de busca do Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afetou alguns builds do Netdata `ndsudo`. O helper SUID pertencente ao root procurava os comandos externos permitidos usando um `PATH` fornecido por quem o chamava. Analise um helper instalado, inclusive um que esteja fora do `PATH` usual de quem chama, somente se a conta atual puder executá-lo. Confirme o proprietário, o bit SUID, o acesso de execução (incluindo permissões de grupo/ACL), o build instalado e o status do patch do fornecedor, além de verificar se `NoNewPrivs` ou uma montagem `nosuid` impede a alteração de identidade. O Netdata lista os builds corrigidos `v1.45.3` e `v1.45.0-169`; backports de distribuições precisam ser confirmados separadamente. A versão mostrada em um dashboard ou a mera presença de `ndsudo` não são evidências suficientes de uma escalada alcançável. O problema de caminho também exige que o helper resolva um comando externo por meio de um local controlado por quem chama.

### Fronteira de privilégios do Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afetou a lógica privilegiada `--join` do Firejail: um alvo de join especialmente construído podia fazer o helper setuid-root aceitar um mount namespace controlado por um atacante e copiar um estado de segurança inseguro. Na triagem passiva, confirme que a **identidade atual pode executar** um binário Firejail setuid pertencente ao root, que o setuid é efetivo na montagem e no contexto do processo, e que o build instalado não contém a correção. O upstream corrigiu o problema na versão [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); pacotes de distribuições podem [incluir o patch por backport](https://github.com/netblue30/firejail/issues/5191) mesmo exibindo uma versão mais antiga. Esses pré-requisitos identificam um candidato a análise, não comprovam um join bem-sucedido nem um shell root. Não crie um jail falso nem invoque `--join` durante a enumeração.

### Permissões do arquivo de log do GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) envolveu o Screen 4.5.0 abrindo um arquivo de log escolhido por quem chamava com privilégios elevados. Um binário `screen` ou com a versão no sufixo no inventário SUID é apenas uma pista para análise: confirme que pertence ao root, que a execução SUID é efetiva para o usuário atual, qual é o build instalado e o status do patch da distribuição, além do comportamento afetado do arquivo de log. [O Debian corrigiu seu pacote 4.5.0 com um backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), portanto uma string de versão ou um nome de arquivo, isoladamente, não comprova exposição. Não crie um arquivo de log como teste rotineiro de enumeração.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afetou o helper privilegiado de bloqueio de arquivos de e-mail do S-nail quando um componente de caminho controlado por quem chamava podia percorrer diretórios e levar à gravação de um arquivo arbitrário. Analise se o usuário atual pode executar um helper setuid instalado que pertença ao root, se sua identidade setuid é efetiva sob a política de montagem e de processo e qual é o build exato do pacote e sua correção do fornecedor. O [aviso de segurança do Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) lista uma correção por backport para seu pacote 16.04; portanto, uma versão que pareça ser do upstream, isoladamente, não é conclusiva. A presença do helper não comprova que o caminho afetado seja alcançável nem que a gravação de um arquivo resulte em execução como root; examine os metadados e o status do pacote sem invocar o helper nem tentar provocar a corrida durante a enumeração.

### snap-confine e limpeza por tmpfiles

CVE-2026-3888 é uma corrida envolvendo o `snap-confine` privilegiado e a limpeza de `/tmp` pelo systemd-tmpfiles. Uma análise passiva pode verificar se `snap-confine` é setuid ou tem capabilities de arquivo, comparar o pacote `snapd` instalado com a versão corrigida para aquela **versão do Ubuntu** e examinar a regra efetiva de idade de `/tmp` e o timer de limpeza. Um pacote e uma regra correspondentes são pré-requisitos, não prova de que a corrida seja alcançável: o estado do timer em tempo de execução, o layout do snap, os backports do pacote e as substituições de regras também importam. Versões mais antigas podem exigir uma configuração não padrão. Não execute um teste de corrida durante a enumeração rotineira. Consulte o [registro de CVE do Ubuntu](https://ubuntu.com/security/CVE-2026-3888) para verificar o status dos pacotes por versão e o [aviso da Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para entender a interação entre os componentes.

## Inspecione ACLs e caminhos sensíveis

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Um diretório pai com permissão de escrita pode permitir a substituição mesmo quando o arquivo pertence ao root. Uma ACL pode conceder acesso discretamente a um arquivo de configuração do sudoers, uma unidade de serviço, um script do cron, um caminho de biblioteca ou um arquivo de credenciais. Verifique tanto a ACL quanto o caminho completo. Se for possível gravar arquivos privilegiados arbitrariamente, siga [Arbitrary File Write to Root](write-to-root.md); para casos de configuração do linker e preload, consulte o [exemplo de `ld.so`](ld.so.conf-example.md). Considere backups expostos, arquivos `.env`, configurações de banco de dados, material SSH e histórico como possíveis fontes de credenciais, cujo acesso é determinado pelas permissões efetivas de cada arquivo.
