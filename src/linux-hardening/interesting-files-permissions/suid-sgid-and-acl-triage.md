# SUID、SGID、ACL、および機密ファイル

{{#include ../../banners/hacktricks-training.md}}

SUIDとSGIDは、実行されるファイルの実効IDを変更します。ACLは、通常の`ls -l`のモードビットには表示されないアクセス権を付与できます。ユーザーが、表示上の所有者およびグループの権限から想定される範囲を超えて読み取り、書き込み、または実行できる場合は、両方を確認してください。

## 特権実行ファイルを列挙する

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

カスタムまたは最近変更された実行ファイル、通常と異なる所有者、書き込み可能なマウント上のファイルに注目してください。`nosuid` マウントでは set-ID の動作が抑制されることがあります。file capabilities は別の権限メカニズムであり、[Linux capabilities](linux-capabilities.md) で説明されています。不審なバイナリをパッケージ内のものと比較し、昇格した ID で何を実行、オープン、またはロードするかを確認してください。

呼び出し元の入力を受け取る、見慣れない root 所有の SUID 実行ファイルについては、バイナリのコピーをオフラインで調べ、メモリ安全でない引数処理と、そこに到達するコードパスを確認してください。実効 ID の動作と、stack canary、実行不可メモリ、position-independent code、address randomization などの緩和策を記録してください。危険な関数名や緩和策の欠如は、調査の手がかりにすぎません。exploitability は、実際の入力境界、到達可能な制御フロー、障害発生時の実効 ID に左右されます。受動的な列挙中にクラッシュを試すためだけに、稼働中の特権実行ファイルへ長い引数を渡してはいけません。

見慣れた SUID プログラムが置き換えられたり、バックドアを仕込まれたりしている場合もあります。最近の変更時刻は手がかりであり、証拠ではありません。**特定の不審なパッケージ済みバイナリ**については、所有パッケージを特定し、通常の列挙中にすべてのパッケージを検証するのではなく、インストール済みファイルをパッケージメタデータと照合してください:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` は、パッケージデータベースにチェックサムが記録されているファイルについてのみ内容を検査します。RPM はモードや所有者などのメタデータも比較します。**特権実行ファイル自体**の不一致に注目してください。同じパッケージ内の別の場所にあるドキュメントやロケールファイルが、不要なファイルを除いたインストールでは欠落として報告されることがあります。疑わしい実行ファイルを信頼できるベンダーパッケージと比較し、変更されたコードを正確に確認してください。正当なローカル変更、チェックサムの欠如、侵害されたパッケージメタデータにより、いずれのコマンドで確認できる範囲にも限界があります。受動的なトリアージの一環として、疑わしい SUID プログラムもパッケージ検証スクリプトも実行しないでください。[dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) と [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) を参照してください。

シェル、相対パスのコマンド、または書き込み可能なパスにあるライブラリを呼び出す SUID プログラムは、信頼境界を越える可能性があります。[SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md)、[PATH guidance](../linux-basics/linux-environment-variables.md#path)、[user-ID explanation](../user-information/euid-ruid-suid.md) を参照してください。既知のコマンド固有のエスケープについては、ホスト上で許可される正確なバイナリと呼び出し方を [GTFOBins](https://gtfobins.github.io/) で確認してください。

set-user-ID 実行ファイルでは、呼び出し元の**実 UID**とファイル所有者の**実効 UID**を区別してください。[`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) は実 UID を変更せず、set-ID による変更後の実効 UID を保存 UID にコピーします。[`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) は `/bin/sh -c` を通してコマンドを実行します。このパスで選択されるシェルによって、子プロセスが実効 ID を保持するかどうかが変わります。特に、[Bash の特権モードの規則](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)では、`-p` なしで Bash が起動すると、実効 UID と実 UID が異なる場合に実効 UID が実 UID にリセットされます。実際のヘルパーの UID 変更と子プロセスの呼び出し方に加え、所有者、実行アクセス権、マウントの `nosuid` 設定、プロセスの `no_new_privs` 状態を確認してください。SUID ビットやシェル呼び出しだけでは、利用可能な権限昇格が成立するとは限りません。

root 所有の珍しい SUID `jjs` があり、現在のユーザーが実行できる場合は、ファイルアクセスを別途確認してください。旧式の Nashorn ツールは、起動したシェルの実効 UID が降格しても Java のファイル API にアクセスできます。特権のある読み取りや書き込みと判断する前に、インストール済み JVM の動作、ファイル操作時の実効 ID、`nosuid`／`no_new_privs` を確認してください。[Oracle は JDK 15 で `jjs` を削除しました](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)。インストール済みのパスには、古いビルドや別パッケージのビルドが残っている場合があります。[GTFOBins にはファイル API の説明があります](https://gtfobins.org/gtfobins/jjs/)。ただし、sudo の例はすべてのビルドで SUID が機能することを示すものではありません。受動的な列挙中にこのツールを実行しないでください。

低権限ユーザーが実行できる root 所有の SUID `gosu` 実行ファイルは、確認が必要です。文書化されたインターフェースは対象ユーザーとコマンドを受け取りますが、通常のコンテナ利用では root として起動し、権限を降格します。特権遷移と判断する前に、インストール済みビルドの SUID 動作、実効 ID と user namespace のマッピング、`nosuid`、`no_new_privs` を確認してください。コンテナ内の root がホストの root を意味するわけではありません。ファイル名や SUID ビットだけでは、遷移が機能する証拠になりません。[upstream usage](https://github.com/tianon/gosu) と [maintainer's SUID warning](https://github.com/tianon/gosu/issues/11) を参照してください。受動的なインベントリ作成中にこのヘルパーを実行しないでください。

カスタムの set-user-ID バックアップラッパーは、呼び出し元が選択したパスを受け取り、それを `system(3)` に渡すアーカイブコマンドへ埋め込む場合があります。構築されたコマンド内でパスが引用符で囲まれていなければ、子シェルは[`HOME` によるチルダ展開、`?` や `*` などのパス名パターン、改行によるコマンド区切り](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)を適用できます。よくある記号だけを拒否リストで弾いても、パスがリテラルになるわけではありません。正確な引数の流れ、継承環境、子シェルと実効 ID、ファイルシステムアクセス、アーカイブ出力が呼び出し元から見えるかを確認してください。SUID ビット、アーカイブツールの文字列、または `/root` というリテラルが拒否されることだけでは、情報開示もコード実行も証明できません。受動的な列挙中にプライベートファイルをアーカイブしたり、クラッシュを起こす入力を送信したりせず、ラッパーのコピーをオフラインで確認してください。

`$(...)` のようなシェルの[コマンド置換](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)も、メタ文字の拒否リストにおける別の抜け道になり得ます。固定された許可コマンドのプレフィックスであっても、後続の呼び出し元制御の引数が `/bin/sh -c` に渡される場合があります。引用符の扱い、パーサー、実効 ID をオフラインで確認してください。`system()` の文字列や不完全な拒否リストだけを、実行の証拠と見なさないでください。

**呼び出し元プロセスのツリー**も重要です。Web ワーカーは UID 変更システムコールを制限する seccomp フィルターを設定できます。[seccomp フィルターは子プロセスに引き継がれ、`execve` 後も存続します](https://docs.kernel.org/userspace-api/seccomp_filter.html)。たとえば、Apache の [mpm-itk `LimitUIDRange` および `LimitGIDRange` ディレクティブ](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/)は、子孫プロセスが到達できる ID を制限できます。`/proc/self/status` の `Seccomp: 2` はフィルターモードを示すだけで、ポリシーや、この特定のヘルパーが所有者の ID を取得できるかどうかは示しません。実際の呼び出しの祖先と実効フィルターを、SUID、マウント、`no_new_privs` の条件と合わせて確認してください。別のログインセッションではポリシーが異なる場合がありますが、そのセッションには独自の有効なアクセス経路が必要です。

カスタム SUID 実行ファイルが、読み取り可能な別の Python スクリプトを呼び出す場合があります。実際に Python **2** を使用しているなら、[`input()` は入力された式を評価します](https://docs.python.org/2/library/functions.html#input)。Python 3 の `input()` はテキストを返すだけです。そのソース行が実行経路になると判断する前に、ラッパーの実効 ID、インタープリターのパスとバージョン、スクリプトのパス、信頼されていない入力がその呼び出しに渡るかを確認してください。スクリプト自体の set-ID ビットや、特権ラッパーを介さない `input()` 呼び出しだけでは、同じ境界が成立しません。列挙中は実行せず、バイナリが参照するパスと、範囲を限定したスクリプトソースを確認してください。

珍しい SUID 実行ファイルに読み取り可能なソースがある場合は、呼び出し元が制御できるファイル読み取りについて、要求バイト数と格納先バッファのサイズを比較し、その後の制御フロー上のチェックを調べてください。[`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) は指定されたポインターに要求された項目数を書き込みますが、格納先オブジェクトの容量は認識しません。サイズの不一致は、静的解析で確認すべきメモリ安全性上の手掛かりであり、利用可能な権限昇格の証拠ではありません。ソースがインストール済みバイナリに対応すること、呼び出し元が入力を指定できること、その状況で SUID 実行が有効なこと、該当経路に到達できることを確認してください。列挙中に特権プログラムへクラッシュを起こす入力を送るのではなく、範囲を限定したソースまたはバイナリのコピーをオフラインで確認してください。

カスタム SUID ヘルパーは、内容を出力せずに保護されたファイルの情報を漏らすことがあります。呼び出し元がパス名と正規表現の両方を選択でき、ヘルパーが実効 UID で一致件数を返す場合、先頭にアンカーを付けたテストによって文字単位のオラクルが成立する可能性があります。特権昇格と判断する前に、ヘルパーの所有者、実効 ID の動作、実行アクセス権、パス名の制限、正規表現の動作、応答の可視性、呼び出し元が別の方法では読めない具体的な高権限ファイルを確認してください。SUID ビットや正規表現ライブラリの文字列だけでは、この一連の動作を証明できません。受動的な列挙中は、通常と異なる実行ファイルを記録し、逆アセンブル結果またはソースの範囲を限定したコピーを確認してください。稼働中のヘルパーに推測を繰り返し実行したり、復元した秘密を出力したりしないでください。

OpenBSD では、呼び出し元が選択したパス名を受け取るカスタム set-user-ID リーダーが、実効 ID で読み取り可能な `/var/backups` 内のファイルを読み出し、その内容を呼び出し元に返す場合があります。[OpenBSD の `changelist(5)`](https://man.openbsd.org/changelist.5) には、設定されたパスの `.current` および `.backup` コピーが記載されています。ただし、`+` で始まる項目にはファイル内容ではなく SHA-256 チェックサムが保存されます。バックアップディレクトリの所有者は root、モードは `0700` であるべきです。`/var` に対するヘルパーの [`unveil` 読み取りルール](https://man.openbsd.org/unveil.2)は、そのパス以下へのアクセスを許可する場合がありますが、それ自体でファイルアクセスを許可または証明するものではありません。権限昇格を主張する前に、実際の実効 UID、現在のユーザーの実行権限、受け付けられるパス、バックアップの存在と内容、独立した認証要件の有無を確認してください。受動的な列挙では、リーダーを実行したりバックアップデータを出力したりせず、ヘルパーとパスのメタデータを報告してください。

呼び出し元が選択したパス名を [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) で確認してから後で開くカスタム SUID プログラムでは、呼び出し元が書き込み可能なディレクトリ内のファイルやシンボリックリンクを変更する競合が起こり得ます。チェック対象は先に存在したオブジェクトですが、後の [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) では別のオブジェクトが解決される可能性があります。確認するのは、ヘルパーを高い実効 ID で実行できること、到達可能なコードパスが選択されたファイルを読み取ること、チェックとオープンの間に呼び出し元がパス名を置き換えられることです。SUID ビット、書き込み可能なディレクトリ、または `stat` の文字列だけでは、これらのどれも証明できません。情報開示の経路には、出力が見えること、または呼び出し元が読める宛先があることも必要です。稼働中のヘルパーで競合を起こさず、バイナリとパスのメタデータをオフラインで確認してください。

同じ依存関係の確認を SGID ラッパーにも適用してください。絶対パスでシェルやヘルパーを実行するラッパーでも、低権限ユーザーがそのファイルを置き換えられる場合は安全とは限りません。起動されたコードが、ラッパーの実効グループを引き継ぐことがあります。呼び出される正確なパス、その書き込み権限（ACL を含む）、ラッパーの実効グループ、子プロセスの起動前に権限を降格するかを確認してください。インタープリターが継承した実効 ID を破棄する場合もあるため、確認対象と、実証済みの遷移を区別してください。ホスト上の別の場所に書き込み可能なシェルがあるだけでは、特権ラッパーがそれを呼び出す証拠になりません。

### SQLite CLI に SQL を渡す特権ラッパー

カスタム SUID プログラムがユーザー制御の SQL を**`sqlite3` コマンドラインプログラム**に渡す場合、クエリを読み取り専用と判断する前に、正確なコマンドと実効 ID を確認してください。CLI の `edit()` SQL 関数はエディター（第 2 引数または `VISUAL` で指定）を呼び出し、SQL の `load_extension()` 関数は拡張機能の読み込みが有効な場合に共有ライブラリを読み込めます。ラッパーが `PATH` を固定したり、絶対パスの `sqlite3` を使ったりしても、これらは CLI プロセスの実行 ID でコードが実行される可能性のある経路です。SQL が実際にこれらの関数に到達し、CLI で該当機能が有効である必要があります。バイナリやホスト上で `sqlite3` が見つかっただけでは、権限昇格の証拠になりません。SQLite **ライブラリ**では拡張機能の読み込みがデフォルトで無効になっているため、CLI と区別してください。特権アプリケーションで信頼できない SQL を処理する必要がある場合は、SQLite CLI の `--safe` モードを使うと、`edit()`、`load_extension()`、その他の副作用のある関数が無効になります。[SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function)、[safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option)、[extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension) を参照してください。

### 詳細出力を行うクライアントにファイルを渡す特権リーダー

カスタム SUID/SGID ラッパーは、呼び出し元が選択したパス名へのアクセスを確認した後、そのファイルを別のコマンドに渡す場合があります。アクセス確認時と後のオープン時の実効 ID を調べ、`../` の各要素が実際の基準ディレクトリに対してどう解決されるかを確認し、無効な入力を子プロセスがどう処理するかを調べてください。データベースクライアントがプライベートファイルを SQL として読み込み、詳細出力を行う場合、SQL が無効でもエラーにファイル内容を出力する可能性があります。これは、子プロセスが呼び出し元には読めないファイルを読めること、呼び出し元がラッパーを通じてそのファイルを選択できること、出力が見えることのすべてが成立する場合に限り、ユーザー間の情報開示になります。`mysql` や別のクライアント文字列があるだけでは、これらの条件を証明できません。

### Netdata `ndsudo` の検索パス

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) は、一部の Netdata `ndsudo` ビルドに影響しました。root 所有の SUID ヘルパーは、呼び出し元が指定した `PATH` を使って、許可された外部コマンドを検索していました。現在のアカウントが実行できる場合に限り、通常の `PATH` 外にあるものも含め、インストール済みヘルパーを確認してください。所有者、SUID ビット、実行アクセス権（グループや ACL による許可を含む）、インストール済みビルドとベンダーパッチの適用状況、`NoNewPrivs` または `nosuid` マウントによって ID 変更が阻止されるかを確認してください。Netdata は修正済みビルドとして `v1.45.3` と `v1.45.0-169` を挙げています。ディストリビューションによるバックポートは別途確認が必要です。ダッシュボードのバージョンや、`ndsudo` が存在することだけでは、到達可能な権限昇格の証拠になりません。パスの問題が成立するには、ヘルパーが呼び出し元の制御下にある場所から外部コマンドを解決する必要もあります。

### Firejail の join 権限境界

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) は、Firejail の特権 `--join` 処理に影響しました。細工された join 対象によって、setuid-root ヘルパーが攻撃者制御のマウント namespace を受け入れ、安全でないセキュリティ状態をコピーする可能性がありました。受動的なトリアージでは、**現在の ID で実行できる** root 所有の setuid Firejail バイナリがあること、マウントとプロセスのコンテキストで setuid が有効なこと、インストール済みビルドに修正がないことを確認してください。upstream では [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) で修正されています。ディストリビューションのパッケージは、古いバージョンが表示されていても[修正をバックポート](https://github.com/netblue30/firejail/issues/5191)している場合があります。これらの前提条件は確認対象を示すものであり、join の成功や root シェルを証明するものではありません。列挙中に偽の jail を作成したり、`--join` を実行したりしないでください。

### GNU Screen のログファイル権限

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) は、Screen 4.5.0 が呼び出し元指定のログファイルを高い権限で開く問題でした。SUID インベントリに `screen` またはバージョン付きバイナリが見つかった場合は、確認の手掛かりにとどまります。root 所有であること、現在のユーザーによる実効 SUID 実行、インストール済みビルドとディストリビューションの修正状況、影響を受けるログファイルの動作を確認してください。[Debian はバックポートにより 4.5.0 パッケージを修正しました](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484)。そのため、バージョン文字列やファイル名だけでは影響を受ける証拠になりません。通常の列挙のためにログファイルを作成しないでください。

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) は、呼び出し元が制御するパス要素がディレクトリをたどり、任意のファイル書き込みにつながる可能性がある、特権 S-nail のメールロックヘルパーに影響しました。現在のユーザーがインストール済みの root 所有 setuid ヘルパーを実行できるか、マウントとプロセスポリシーの下で setuid ID が有効か、正確なパッケージビルドとベンダー修正を確認してください。[Ubuntu のセキュリティ通知](https://ubuntu.com/security/notices/USN-4820-1)には 16.04 パッケージ向けのバックポート修正が記載されているため、upstream のバージョンに見える文字列だけでは判断できません。ヘルパーが存在するだけでは、影響を受けるパスに到達できることや、ファイル書き込みから root のコード実行に至ることは証明できません。列挙中にヘルパーを実行したり、競合を試したりせず、メタデータとパッケージ状態を調べてください。

### snap-confine と tmpfiles のクリーンアップ

CVE-2026-3888 は、特権 `snap-confine` と、`/tmp` をクリーンアップする systemd-tmpfiles との競合です。受動的な確認では、`snap-confine` に setuid またはファイルケーパビリティが設定されているか、インストール済み `snapd` パッケージがその**Ubuntu リリース**向けの修正版であるか、`/tmp` の有効な経過時間ルールとクリーンアップタイマーを確認できます。パッケージとルールが一致することは前提条件であり、競合に到達できる証拠ではありません。実行時のタイマー状態、snap のレイアウト、パッケージへのバックポート、ルールの上書きも関係します。古いリリースでは、デフォルト以外の設定が必要な場合があります。通常の列挙中に競合を試さないでください。リリースごとのパッケージ状態は [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888)、コンポーネント間の相互作用は [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) を参照してください。

## ACL と機密パスを確認する

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

書き込み可能な親ディレクトリがあれば、ファイル自体が root 所有でも置き換えられる場合があります。ACL により、sudoers の drop-in、service unit、cron script、library path、credential file へのアクセスがひそかに許可されていることもあります。ACL とパス全体の両方を確認してください。特権ファイルへの任意の書き込みが可能な場合は、[Arbitrary File Write to Root](write-to-root.md) を参照してください。linker configuration や preload のケースについては、[`ld.so` example](ld.so.conf-example.md) を参照してください。露出しているバックアップ、`.env` ファイル、データベース設定、SSH 関連ファイル、履歴は、各ファイルの実際の権限に基づいてアクセスできる credential の候補として扱ってください。
