# SUID, SGID, ACLs e arquivos sensíveis

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID alteram a identidade efetiva de um arquivo executado; ACLs podem conceder acesso que os bits de permissão comuns de `ls -l` não mostram. Verifique ambos quando um usuário puder ler, gravar ou executar mais do que as permissões aparentes de proprietário e grupo indicam.

## Enumerar executáveis privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentre-se em executáveis personalizados ou alterados recentemente, proprietários incomuns e arquivos em montagens com permissões de escrita. Uma montagem `nosuid` pode suprimir o comportamento set-ID; file capabilities são um mecanismo de privilégio separado, descrito em [Linux capabilities](linux-capabilities.md). Compare um binário suspeito com o pacote ao qual pertence e verifique o que ele executa, abre ou carrega com identidade elevada.

Para um executável SUID de propriedade do root que você não conhece e que aceita entrada do chamador, analise uma cópia do binário offline para identificar tratamento de argumentos inseguro para memória e o caminho de código que chega a esse tratamento. Registre o comportamento do ID efetivo e as mitigações, como stack canaries, memória não executável, código independente de posição e randomização de endereços. O nome de uma função insegura ou a ausência de uma mitigação são apenas indícios para análise: a possibilidade de exploração depende dos limites reais da entrada, do fluxo de controle alcançável e da identidade efetiva no momento da falha. Não envie argumentos longos ao executável privilegiado em produção apenas para testar se ele trava durante a enumeração passiva.

Um programa SUID conhecido também pode ser substituído ou conter um backdoor. Uma data de modificação recente é um indício, não uma prova: para um **binário empacotado especificamente suspeito**, identifique o pacote proprietário e compare o arquivo instalado com os metadados do pacote, em vez de verificar todos os pacotes durante a enumeração rotineira:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` verifica o conteúdo dos arquivos somente quando o banco de dados do pacote tem um checksum registrado; o RPM também compara metadados, como modo e proprietário. Concentre-se em divergências no **próprio executável privilegiado**: instalações enxutas podem informar que faltam arquivos de documentação ou de localização em outras partes do mesmo pacote. Compare um executável suspeito com um pacote confiável do fornecedor e examine exatamente o código alterado. Alterações locais legítimas, checksums ausentes e metadados de pacote comprometidos limitam o que qualquer um dos comandos pode comprovar. Não execute o programa SUID suspeito nem um script de verificação de pacotes durante a triagem passiva. Consulte o [manual de verificação do dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e o [manual de verificação do RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Um programa SUID que invoca um shell, um comando relativo ou uma biblioteca de um caminho gravável pode cruzar uma fronteira de confiança. Consulte [abuso de bibliotecas compartilhadas e do linker via SUID](suid-shared-library-and-linker-abuse.md), as [orientações sobre PATH](../linux-basics/linux-environment-variables.md#path) e a [explicação sobre user ID](../user-information/euid-ruid-suid.md). Para escapes conhecidos específicos de comandos, consulte o [GTFOBins](https://gtfobins.github.io/) usando o binário exato e a invocação permitida no host.

Para um executável set-user-ID, diferencie o **UID real** do chamador do **UID efetivo** do proprietário do arquivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) mantém o UID real inalterado e copia o UID efetivo para o UID salvo após qualquer alteração set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) executa o comando por meio de `/bin/sh -c`; o shell selecionado por esse caminho afeta se um processo filho mantém sua identidade efetiva. Em particular, as [regras do modo privilegiado do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) redefinem um UID efetivo diferente para o UID real quando o Bash inicia sem `-p`. Verifique as alterações de UID do helper real e como ele invoca processos filhos, além do proprietário, do acesso ao executável, da opção de montagem `nosuid` e do estado de `no_new_privs` do processo. Um bit SUID ou uma chamada de shell, por si só, não comprova uma transição utilizável para privilégios mais altos.

Um `jjs` SUID de propriedade do root e incomum merece uma análise separada de acesso a arquivos se o usuário atual puder executá-lo. A ferramenta Nashorn legada pode acessar APIs de arquivos Java mesmo quando um shell iniciado como processo filho descarta um UID efetivo; confirme o comportamento da JVM instalada, a identidade efetiva da operação de arquivo e as condições de `nosuid`/`no_new_privs` antes de considerá-lo uma leitura ou gravação privilegiada. [A Oracle removeu o `jjs` no JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); um caminho instalado ainda pode corresponder a uma versão mais antiga ou a um build empacotado separadamente. O [GTFOBins documenta as APIs de arquivos](https://gtfobins.org/gtfobins/jjs/), mas os exemplos com sudo não comprovam o comportamento SUID em todos os builds. Não invoque a ferramenta durante a enumeração passiva.

Um executável `gosu` SUID, de propriedade do root e acessível a um usuário com menos privilégios, merece análise: sua interface documentada aceita um usuário de destino e um comando, mas o uso normal em containers o inicia como root para descartar privilégios. Verifique o comportamento SUID do build instalado, a identidade efetiva e o mapeamento do user namespace, além de `nosuid` e `no_new_privs`; root dentro de um container não implica root no host. Um nome de arquivo ou bit SUID, por si só, não comprova uma transição funcional. Consulte o [uso upstream](https://github.com/tianon/gosu) e o [aviso SUID do mantenedor](https://github.com/tianon/gosu/issues/11). Não invoque o helper durante o inventário passivo.

Um wrapper de backup personalizado com set-user-ID pode aceitar um caminho escolhido pelo chamador e interpolá-lo em um comando de arquivamento passado a `system(3)`. Se o caminho não estiver entre aspas no comando construído, o shell filho poderá aplicar [expansão de til usando `HOME`, padrões de nome de caminho como `?` e `*`, e separação de comandos por newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rejeitar apenas pontuações conhecidas por meio de uma denylist não torna o caminho literal. Confirme o fluxo exato dos argumentos, o ambiente herdado, o shell filho e a identidade efetiva, o acesso ao sistema de arquivos e se a saída do arquivamento fica visível ao chamador. O bit SUID, uma string de ferramenta de arquivamento ou apenas o bloqueio de um caminho literal `/root` não comprovam divulgação nem execução de código. Durante a enumeração passiva, analise uma cópia do wrapper offline, em vez de arquivar arquivos privados ou enviar entradas que provoquem falhas.

A [substituição de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) do shell, como `$(...)`, é outra possível brecha em uma denylist de metacaracteres: até mesmo um prefixo de comando fixo e permitido pode passar um argumento posterior controlado pelo chamador para `/bin/sh -c`. Verifique offline as aspas exatas, o parser e a identidade efetiva; não considere uma string de `system()` ou uma denylist incompleta, por si só, prova de execução.

A **árvore de processos chamadores** também importa. Um worker web pode instalar um filtro seccomp que restringe chamadas de sistema que alteram UID; [filtros seccomp são herdados por processos filhos e persistem após `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por exemplo, as diretivas [`LimitUIDRange` e `LimitGIDRange` do mpm-itk do Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) podem limitar as identidades alcançáveis pelos descendentes. `Seccomp: 2` em `/proc/self/status` indica o modo do filtro, não a política nem se este helper específico pode assumir a identidade do proprietário. Analise em conjunto a ancestralidade da invocação real e o filtro efetivo, além das condições SUID, de montagem e de `no_new_privs`; uma sessão de login separada pode ter outra política, mas exige um caminho de acesso válido próprio.

Um executável SUID personalizado pode invocar um script Python separado e legível. Se realmente usar **Python 2**, [`input()` avalia a expressão inserida](https://docs.python.org/2/library/functions.html#input); no Python 3, `input()` retorna texto. Confirme a identidade efetiva do wrapper, o caminho e a versão do interpretador, o caminho do script e se uma entrada não confiável chega a essa chamada antes de considerar essa linha do código-fonte um caminho de execução. Um bit set-ID no próprio script ou uma chamada a `input()` sem o wrapper privilegiado não estabelece a mesma fronteira. Durante a enumeração, examine os caminhos referenciados pelo binário e um trecho limitado do código-fonte do script sem executá-lo.

Se houver código-fonte legível junto a um executável SUID incomum, compare a quantidade de bytes solicitada em cada leitura de arquivo controlada pelo chamador com o tamanho do buffer de destino e examine as verificações posteriores no fluxo de controle. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) armazena os itens solicitados no ponteiro fornecido; não conhece a capacidade do objeto de destino. Uma divergência de tamanho é uma pista estática de segurança de memória, não prova de uma elevação de privilégios utilizável: confirme que o código-fonte corresponde ao binário instalado, que o chamador pode fornecer a entrada, que a execução SUID é efetiva nesse contexto e que o caminho relevante é alcançável. Analise offline um trecho limitado do código-fonte ou uma cópia do binário, em vez de enviar entradas que provoquem falhas ao programa privilegiado durante a enumeração.

Um helper SUID personalizado pode divulgar um arquivo protegido sem imprimir seu conteúdo. Se o chamador escolher tanto um caminho quanto uma expressão regular, e o helper retornar uma contagem visível de correspondências usando seu UID efetivo, testes de prefixo ancorados podem formar um oráculo caractere a caractere. Confirme o proprietário do helper, o comportamento do ID efetivo, o acesso ao executável, as restrições de caminho, a semântica da expressão regular, a visibilidade da resposta e a existência de um arquivo específico com privilégios mais altos que o chamador não possa ler de outra forma. Um bit SUID ou uma string de biblioteca de regex, por si só, não comprova nenhum desses fluxos. Durante a enumeração passiva, registre o executável incomum e analise offline um trecho limitado do disassembly ou uma cópia do código-fonte; não execute tentativas iterativas contra o helper ativo nem imprima segredos recuperados.

No OpenBSD, um leitor personalizado set-user-ID que aceite um caminho escolhido pelo chamador pode expor arquivos em `/var/backups` se sua identidade efetiva puder lê-los e ele retornar o conteúdo ao chamador. O [`changelist(5)` do OpenBSD](https://man.openbsd.org/changelist.5) descreve cópias `.current` e `.backup` dos caminhos configurados, mas as entradas prefixadas com `+` armazenam checksums SHA-256, não o conteúdo dos arquivos; o diretório de backup deve pertencer ao root e ter modo `0700`. Uma regra de leitura [`unveil` do helper](https://man.openbsd.org/unveil.2) para `/var` pode permitir acesso abaixo desse caminho, mas não concede nem comprova acesso a arquivos por si só. Confirme o UID efetivo real, a permissão de execução para o usuário atual, o caminho aceito, a existência e o conteúdo do backup e quaisquer requisitos independentes de autenticação antes de alegar elevação de privilégios. A enumeração passiva deve registrar o helper e os metadados do caminho, não invocar o leitor nem imprimir dados do backup.

Um programa SUID personalizado que verifica um caminho escolhido pelo chamador com [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e abre o caminho posteriormente pode sofrer uma condição de corrida se um arquivo ou symlink em um diretório gravável pelo chamador for alterado. A verificação se aplica ao objeto anterior, enquanto uma chamada posterior a [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) pode resolver outro objeto. Confirme que o helper pode ser executado com identidade efetiva elevada, que um caminho de código alcançável lê o arquivo selecionado e que o chamador pode substituir o caminho entre a verificação e a abertura; um bit SUID, um diretório gravável ou uma string `stat`, por si só, não comprovam nenhum desses pontos. Para haver divulgação, também é necessária uma saída visível ou um destino legível pelo chamador. Analise offline o binário e os metadados do caminho; não provoque uma condição de corrida no helper ativo durante a enumeração passiva.

Aplique a mesma análise de dependências aos wrappers SGID. Um wrapper que executa um shell ou helper por um caminho absoluto ainda pode ser inseguro se um usuário com menos privilégios puder substituir esse arquivo; o código iniciado pode herdar o grupo efetivo do wrapper. Verifique o caminho invocado exato, suas permissões de gravação (incluindo ACLs), o grupo efetivo do wrapper e se ele descarta privilégios antes de iniciar o processo filho. Um interpretador também pode descartar IDs efetivos herdados; portanto, diferencie um candidato à análise de uma transição demonstrada. Um shell gravável em outra parte do host, por si só, não comprova que um wrapper privilegiado o invoque.

### Wrappers privilegiados que passam SQL para a CLI do SQLite

Se um programa SUID personalizado passar SQL controlado pelo usuário ao **programa de linha de comando `sqlite3`**, inspecione o comando exato e a identidade efetiva antes de considerar a consulta somente de leitura. A função SQL `edit()` da CLI invoca um editor (indicado pelo segundo argumento ou por `VISUAL`), e a função SQL `load_extension()` pode carregar uma biblioteca compartilhada quando o carregamento de extensões está habilitado. Esses são possíveis caminhos de execução de código com a identidade do processo da CLI, mesmo que o wrapper fixe `PATH` ou use um caminho absoluto para `sqlite3`. O SQL precisa realmente chegar a essas funções, e a CLI precisa manter o recurso relevante; encontrar `sqlite3` em um binário ou no host não é, por si só, evidência de elevação de privilégios. A **biblioteca** do SQLite desabilita o carregamento de extensões por padrão; diferencie-a da CLI. Quando um aplicativo privilegiado precisar processar SQL não confiável, o modo `--safe` da CLI do SQLite desabilita `edit()`, `load_extension()` e outras funções com efeitos colaterais. Consulte a [documentação da CLI do SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), a [documentação do modo seguro](https://www.sqlite.org/cli.html#the_safe_command_line_option) e a [documentação sobre carregamento de extensões](https://www.sqlite.org/loadext.html#loading_an_extension).

### Leitores privilegiados de arquivos que alimentam um cliente verboso

Um wrapper SUID/SGID personalizado pode verificar o acesso a um caminho escolhido pelo chamador e depois passar esse arquivo para outro comando. Analise a identidade efetiva tanto na verificação de acesso quanto na abertura posterior, resolva quaisquer componentes `../` em relação ao diretório base real e examine como o processo filho lida com entradas inválidas. Se um cliente de banco de dados ler um arquivo privado como SQL e produzir saída verbosa, poderá ecoar o conteúdo do arquivo em mensagens de erro, mesmo que o SQL seja inválido. Isso só constitui divulgação entre usuários quando o processo filho pode ler um arquivo que o chamador não pode, o chamador pode selecionar esse arquivo por meio do wrapper e a saída fica visível; a presença de `mysql` ou de outra string de cliente, por si só, não comprova nenhuma dessas condições.

### Caminho de busca do Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afetou alguns builds do Netdata `ndsudo`. O helper SUID, de propriedade do root, procurava os comandos externos permitidos usando um `PATH` fornecido pelo chamador. Analise um helper instalado, inclusive um que esteja fora do `PATH` usual do chamador, somente se a conta atual puder executá-lo. Confirme seu proprietário, o bit SUID, o acesso de execução (incluindo permissões de grupo/ACL), o build instalado e o status dos patches do fornecedor, além de verificar se `NoNewPrivs` ou uma montagem `nosuid` impede a alteração de identidade. O Netdata lista os builds corrigidos `v1.45.3` e `v1.45.0-169`; backports de distribuições precisam de confirmação separada. A versão exibida no dashboard ou a mera presença de `ndsudo` não são evidências suficientes de uma elevação de privilégios alcançável. O problema do caminho também exige que o helper resolva um comando externo por meio de um local controlado pelo chamador.

### Fronteira de privilégios do Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afetou a lógica privilegiada `--join` do Firejail: um alvo de join preparado podia fazer o helper setuid-root aceitar um namespace de montagem controlado pelo atacante e copiar um estado de segurança inseguro. Para a triagem passiva, confirme que a **identidade atual pode executar** um binário Firejail setuid de propriedade do root, que o setuid é efetivo na montagem e no contexto do processo e que o build instalado não contém a correção. O upstream corrigiu o problema na [versão 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); pacotes de distribuições podem [ter a correção portada para trás](https://github.com/netblue30/firejail/issues/5191) e ainda exibir uma versão mais antiga. Esses pré-requisitos identificam um candidato à análise, não um join bem-sucedido nem um shell root. Não crie uma jail falsa nem invoque `--join` durante a enumeração.

### Permissões do arquivo de log do GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) envolveu o Screen 4.5.0 abrindo um arquivo de log escolhido pelo chamador com privilégios elevados. Um binário `screen` ou com versão no nome no inventário SUID é apenas uma pista para análise: confirme a propriedade do root, a execução SUID efetiva para o usuário atual, o build instalado e o status de patches da distribuição, além do comportamento afetado com arquivos de log. [O Debian corrigiu seu pacote 4.5.0 com um backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484); portanto, uma string de versão ou nome de arquivo, por si só, não comprova exposição. Não crie um arquivo de log como teste de rotina durante a enumeração.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afetou o helper privilegiado de bloqueio de correio do S-nail quando um componente de caminho controlado pelo chamador podia percorrer diretórios e levar à gravação em um arquivo arbitrário. Verifique se o usuário atual pode executar um helper setuid instalado e de propriedade do root, se a identidade setuid é efetiva segundo a política de montagem e do processo e qual é exatamente o build do pacote e a correção do fornecedor. O [aviso de segurança do Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) lista uma correção portada para trás no pacote da versão 16.04; portanto, uma versão aparentemente upstream não é conclusiva. A presença do helper não comprova que o caminho afetado seja alcançável nem que a gravação em arquivo resulte em execução como root; inspecione os metadados e o status do pacote sem invocar o helper nem tentar provocar a condição de corrida durante a enumeração.

### Limpeza de snap-confine e tmpfiles

CVE-2026-3888 é uma condição de corrida envolvendo o `snap-confine` privilegiado e a limpeza de `/tmp` pelo systemd-tmpfiles. Uma análise passiva pode verificar se `snap-confine` tem setuid ou file capabilities, comparar o pacote `snapd` instalado com a versão corrigida para aquela **versão do Ubuntu** e inspecionar a regra efetiva de idade de `/tmp` e o timer de limpeza. Um pacote e uma regra correspondentes são pré-requisitos, não prova de que a condição de corrida seja alcançável: o estado do timer em tempo de execução, o layout do snap, os backports do pacote e as substituições de regras também importam. Versões mais antigas podem exigir uma configuração não padrão. Não execute um teste de condição de corrida durante a enumeração de rotina. Consulte o [registro CVE do Ubuntu](https://ubuntu.com/security/CVE-2026-3888) para o status dos pacotes de cada versão e o [aviso da Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para a interação entre os componentes.

## Inspecione ACLs e caminhos sensíveis

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Um diretório pai gravável pode permitir a substituição do arquivo, mesmo que ele pertença ao root. Uma ACL pode conceder acesso silenciosamente a um arquivo de configuração do sudoers, uma unidade de serviço, um script do cron, um caminho de biblioteca ou um arquivo de credenciais. Verifique tanto a ACL quanto o caminho completo. Se for possível gravar arquivos privilegiados arbitrários, siga [Arbitrary File Write to Root](write-to-root.md); para casos de configuração do linker e preload, consulte o [exemplo de `ld.so`](ld.so.conf-example.md). Considere backups expostos, arquivos `.env`, configurações de bancos de dados, material SSH e histórico como possíveis fontes de credenciais, cujo acesso depende das permissões efetivas de cada arquivo.
