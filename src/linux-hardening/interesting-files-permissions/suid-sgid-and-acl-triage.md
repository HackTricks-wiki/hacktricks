# SUID, SGID, ACL та конфіденційні файли

{{#include ../../banners/hacktricks-training.md}}

SUID і SGID змінюють ефективну ідентичність запущеного файлу; ACL можуть надавати доступ, який не видно у звичайних бітах режиму `ls -l`. Перевіряйте і те, і інше, якщо користувач може читати, записувати або виконувати більше, ніж дають змогу очевидні дозволи власника та групи.

## Перелік виконуваних файлів із привілеями

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Зосередьтеся на власних або нещодавно змінених виконуваних файлах, незвичних власниках і файлах на файлових системах, доступних для запису. Параметр монтування `nosuid` може вимкнути поведінку set-ID; файлові capabilities — це окремий механізм надання привілеїв, описаний у [Linux capabilities](linux-capabilities.md). Порівняйте підозрілий бінарний файл із його пакетом і перевірте, що він виконує, відкриває чи завантажує з підвищеними привілеями.

Якщо незнайомий SUID-виконуваний файл, що належить root, приймає введення від користувача, дослідіть копію бінарного файла офлайн, щоб виявити небезпечну для пам’яті обробку аргументів і шлях виконання коду до неї. Зафіксуйте поведінку effective ID і засоби пом’якшення, як-от canary у стеку, пам’ять без права на виконання, position-independent code і рандомізація адрес. Назва небезпечної функції або відсутність засобу пом’якшення — лише привід для перевірки: можливість експлуатації залежить від фактичних меж введення, досяжного потоку керування та effective ID у момент збою. Не передавайте довгі аргументи запущеному привілейованому виконуваному файлу лише для перевірки, чи спричинить це збій під час пасивного перерахування.

Знайому SUID-програму також можуть замінити або вбудувати в неї бекдор. Нещодавній час зміни — це привід для перевірки, а не доказ: для **конкретного підозрілого бінарного файла з пакета** визначте пакет-власник і порівняйте встановлений файл із метаданими пакета, а не перевіряйте кожен пакет під час звичайного перерахування:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` перевіряє вміст файлів лише там, де в базі даних пакунків записана контрольна сума; RPM також порівнює метадані, як-от режим і власника. Звертайте увагу на невідповідність саме **привілейованого виконуваного файла**: в урізаних інсталяціях можуть бути відсутні документація або файли локалізації в інших місцях того самого пакунка. Порівняйте підозрілий виконуваний файл із довіреним пакунком від постачальника та перегляньте точні зміни в коді. Локальні зміни, відсутність контрольних сум і скомпрометовані метадані пакунка обмежують те, що доводить кожна з цих команд. Не запускайте підозрілу SUID-програму чи скрипт перевірки пакунків під час пасивного тріажу. Див. [посібник із перевірки dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) і [посібник із перевірки RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

SUID-програма, що запускає shell, відносну команду або бібліотеку з каталогу, доступного для запису, може перетнути межу довіри. Див. [зловживання SUID зі спільними бібліотеками та компонувальником](suid-shared-library-and-linker-abuse.md), [рекомендації щодо PATH](../linux-basics/linux-environment-variables.md#path) і [пояснення ідентифікаторів користувача](../user-information/euid-ruid-suid.md). Для відомих способів обходу, специфічних для команд, перевірте [GTFOBins](https://gtfobins.github.io/) для точного бінарного файла та способу виклику, дозволеного на хості.

Для виконуваного файла з set-user-ID розрізняйте **реальний UID** викликувача та **ефективний UID** власника файла: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) не змінює реальний UID, а після зміни set-ID копіює ефективний UID у збережений UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) запускає команду через `/bin/sh -c`; вибраний цим шляхом shell впливає на те, чи збереже дочірній процес ефективну ідентичність. Зокрема, [правила привілейованого режиму Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) скидають відмінний ефективний UID до реального UID, якщо Bash запускається без `-p`. Перевірте зміни UID у фактичному допоміжному процесі та його виклик дочірнього процесу, а також власника, доступ до виконання, параметр монтування `nosuid` і стан `no_new_privs` процесу. Сам по собі біт SUID або виклик shell не доводить, що перехід до вищих привілеїв можливий.

Нетиповий SUID-файл `jjs`, власником якого є root, варто окремо перевірити на доступ до файлів, якщо поточний користувач може його виконати. Застарілий інструмент Nashorn може звертатися до файлових API Java, навіть якщо запущений shell скидає ефективний UID; перш ніж вважати його засобом привілейованого читання чи запису, перевірте поведінку встановленої JVM, ефективну ідентичність файлової операції та параметри `nosuid`/`no_new_privs`. [Oracle вилучила `jjs` у JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); встановлений шлях усе ще може вказувати на старішу або окремо запаковану збірку. [GTFOBins описує файлові API](https://gtfobins.org/gtfobins/jjs/), але приклади з sudo не доводять поведінку SUID у кожній збірці. Не запускайте інструмент під час пасивного переліку.

Виконуваний файл SUID `gosu`, власником якого є root і до якого має доступ користувач із нижчими привілеями, потребує перевірки: задокументований інтерфейс приймає цільового користувача й команду, але за звичайного використання в контейнері його запускають від root для скидання привілеїв. Перевірте поведінку встановленої збірки з SUID, ефективну ідентичність і зіставлення в просторі імен користувачів, а також `nosuid` і `no_new_privs`; root у контейнері не означає root на хості. Сама назва файла або біт SUID не доводять, що перехід працює. Див. [використання в upstream](https://github.com/tianon/gosu) і [попередження супровідника щодо SUID](https://github.com/tianon/gosu/issues/11). Не запускайте допоміжну програму під час пасивної інвентаризації.

Користувацька резервна обгортка з set-user-ID може приймати шлях, вибраний викликувачем, і підставляти його в команду архіватора, передану до `system(3)`. Якщо цей шлях у сформованій команді не взято в лапки, дочірній shell може застосувати [розгортання тильди з використанням `HOME`, шаблони імен шляхів на кшталт `?` і `*`, а також розділення команд символом нового рядка](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); заборона лише знайомих розділових знаків у denylist не перетворює шлях на буквальний. Перевірте точний потік аргументів, успадковане середовище, дочірній shell та ефективну ідентичність, доступ до файлової системи й те, чи бачить викликувач вивід архіватора. Біт SUID, рядок із назвою архіватора або блокування буквального `/root` самі по собі не доводять ані розкриття даних, ані виконання коду. Переглядайте копію обгортки офлайн, а не архівуйте приватні файли чи не надсилайте аварійні вхідні дані під час пасивного переліку.

[Підстановка команд](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) shell, наприклад `$(...)`, — ще одна можлива прогалина в denylist метасимволів: навіть фіксований дозволений префікс команди може передати подальший аргумент, контрольований викликувачем, через `/bin/sh -c`. Офлайн перевірте точне екранування, парсер та ефективну ідентичність; не вважайте сам рядок `system()` або неповний denylist доказом виконання.

Важливе значення має також **дерево процесів виклику**. Вебворкер може встановити фільтр seccomp, який обмежує системні виклики зміни UID; [фільтри seccomp успадковуються дочірніми процесами й зберігаються після `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Наприклад, директиви Apache [mpm-itk `LimitUIDRange` і `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) можуть обмежувати ідентичності, доступні нащадкам. `Seccomp: 2` у `/proc/self/status` показує режим фільтра, а не політику чи те, чи може саме ця допоміжна програма отримати ідентичність свого власника. Перевірте разом фактичне походження виклику та ефективний фільтр, а також умови SUID, монтування й `no_new_privs`; окремий сеанс входу може мати іншу політику, але для нього потрібен власний дійсний шлях доступу.

Користувацький виконуваний файл SUID може запускати окремий скрипт Python, доступний для читання. Якщо він справді використовує Python **2**, [`input()` обчислює введений вираз](https://docs.python.org/2/library/functions.html#input); у Python 3 `input()` натомість повертає текст. Перш ніж вважати цей рядок коду шляхом до виконання, перевірте ефективну ідентичність обгортки, шлях до інтерпретатора та його версію, шлях до скрипту й те, чи потрапляють недовірені дані до цього виклику. Біт set-ID на самому скрипті або виклик `input()` без привілейованої обгортки не створюють тієї самої межі довіри. Під час переліку переглядайте згадані в бінарному файлі шляхи та обмежений фрагмент коду скрипту, не запускаючи його.

Якщо до нетипового виконуваного файла SUID додається код, доступний для читання, порівняйте кількість байтів, запитану під час кожного читання файла, контрольованого викликувачем, із розміром буфера призначення та перевірте подальші перевірки потоку керування. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) записує запитані елементи за вказаним покажчиком; функція не знає місткості об’єкта призначення. Невідповідність розмірів — це зачіпка для статичного аналізу безпеки пам’яті, а не доказ придатного для використання підвищення привілеїв: підтвердьте, що код відповідає встановленому бінарному файлу, викликувач може надати вхідні дані, виконання SUID у цьому контексті ефективне й відповідний шлях досяжний. Переглядайте обмежену копію коду або бінарного файла офлайн, а не надсилайте аварійні вхідні дані привілейованій програмі під час переліку.

Користувацька допоміжна програма SUID може розкрити захищений файл, не виводячи його вміст. Якщо викликувач обирає і шлях, і регулярний вираз, а програма повертає видиму кількість збігів, використовуючи свою ефективну UID, перевірки префіксів із прив’язкою до початку рядка можуть утворити посимвольний оракул. Перевірте власника програми, поведінку ефективного UID, доступ до виконання, обмеження шляхів, семантику регулярних виразів, видимість відповіді та конкретний файл із вищими привілеями, який викликувач інакше не може прочитати. Самі по собі біт SUID або рядок із назвою бібліотеки регулярних виразів нічого з цього не доводять. Під час пасивного переліку зафіксуйте нетиповий виконуваний файл і перегляньте обмежену копію дизасембльованого коду чи вихідного коду; не запускайте вгадування в циклі проти активної допоміжної програми й не виводьте відновлені секрети.

В OpenBSD користувацька програма читання з set-user-ID, яка приймає шлях, обраний викликувачем, може відкрити доступ до файлів у `/var/backups`, якщо її ефективна ідентичність може їх читати, а програма повертає їхній вміст викликувачу. [Документація OpenBSD `changelist(5)`](https://man.openbsd.org/changelist.5) описує копії `.current` і `.backup` для налаштованих шляхів, але для записів із префіксом `+` зберігаються контрольні суми SHA-256, а не вміст файлів; каталог резервних копій має належати root і мати режим `0700`. Правило читання [`unveil` для `/var`](https://man.openbsd.org/unveil.2) у допоміжній програмі може дозволити доступ у цьому шляху, але саме по собі не надає й не доводить доступ до файлів. Перш ніж заявляти про підвищення привілеїв, перевірте фактичний ефективний UID, право поточного користувача виконувати програму, прийнятий шлях, наявність і вміст резервної копії та будь-які незалежні вимоги автентифікації. Пасивний перелік має фіксувати допоміжну програму й метадані шляхів, а не запускати програму читання чи виводити дані з резервної копії.

Користувацька програма SUID, яка перевіряє вибраний викликувачем шлях за допомогою [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), а згодом відкриває цей шлях, може зазнати гонки через зміну файла або символічного посилання в каталозі, доступному викликувачу для запису. Перевірка стосується попереднього об’єкта, тоді як пізніший виклик [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) може вказати на інший. Переконайтеся, що допоміжну програму можна виконати з підвищеною ефективною ідентичністю, що доступний шлях виконання читає вибраний файл і що викликувач може замінити шлях між перевіркою та відкриттям; самі по собі біт SUID, доступний для запису каталог або рядок `stat` нічого з цього не доводять. Для розкриття даних також потрібен видимий вивід або місце призначення, доступне для читання викликувачу. Переглядайте бінарний файл і метадані шляхів офлайн; не створюйте гонку проти активної допоміжної програми під час пасивного переліку.

Застосовуйте таку саму перевірку залежностей до обгорток SGID. Обгортка, яка запускає shell чи допоміжну програму за абсолютним шляхом, усе одно може бути небезпечною, якщо користувач із нижчими привілеями може замінити цей файл; запущений код може успадкувати ефективну групу обгортки. Перевірте точний шлях виклику, права запису до нього (зокрема ACL), ефективну групу обгортки та те, чи скидає вона привілеї перед запуском дочірнього процесу. Інтерпретатор також може відкинути успадковані ефективні ідентифікатори, тож відрізняйте об’єкт для перевірки від доведеного переходу. Сам факт наявності десь на хості shell, доступного для запису, не доводить, що його викликає привілейована обгортка.

### Привілейовані обгортки, що передають SQL до CLI SQLite

Якщо користувацька програма SUID передає контрольований користувачем SQL до **програми командного рядка `sqlite3`**, перш ніж вважати запит лише для читання, перевірте точну команду й ефективну ідентичність. SQL-функція CLI `edit()` запускає редактор (із другого аргументу або `VISUAL`), а SQL-функція `load_extension()` може завантажити спільну бібліотеку, якщо завантаження розширень увімкнене. Це потенційні шляхи до виконання коду з ідентичністю процесу CLI, навіть якщо обгортка фіксує `PATH` або використовує абсолютний шлях до `sqlite3`. SQL має справді надійти до цих функцій, а CLI має підтримувати відповідну можливість; сама наявність `sqlite3` у бінарному файлі чи на хості не є доказом підвищення привілеїв. У **бібліотеці** SQLite завантаження розширень вимкнене типово, тож розрізняйте її та CLI. Якщо привілейована програма має обробляти недовірений SQL, режим CLI SQLite `--safe` вимикає `edit()`, `load_extension()` та інші функції з побічними ефектами. Див. [документацію CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), [документацію безпечного режиму](https://www.sqlite.org/cli.html#the_safe_command_line_option) і [документацію завантаження розширень](https://www.sqlite.org/loadext.html#loading_an_extension).

### Привілейовані програми читання файлів, що передають дані клієнту з докладним виводом

Користувацька обгортка SUID/SGID може перевіряти доступ до шляху, вибраного викликувачем, а потім передавати цей файл іншій команді. Перевірте ефективну ідентичність під час перевірки доступу й подальшого відкриття, розв’яжіть усі компоненти `../` відносно фактичного базового каталогу та дослідіть, як дочірній процес обробляє некоректні дані. Якщо клієнт бази даних читає приватний файл як SQL із докладним виводом, він може відобразити вміст файла в повідомленнях про помилки, навіть якщо SQL некоректний. Це розкриття даних між користувачами лише за умови, що дочірній процес може прочитати файл, недоступний викликувачу, викликувач може вибрати цей файл через обгортку, а вивід йому доступний; сама наявність `mysql` чи рядка з назвою іншого клієнта не доводить жодної з цих умов.

### Шлях пошуку Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) стосувалася деяких збірок Netdata `ndsudo`. Допоміжна програма з SUID, власником якої є root, шукала дозволені зовнішні команди, використовуючи `PATH`, заданий викликувачем. Перевіряйте встановлену допоміжну програму, зокрема ту, що розташована поза звичним для викликувача `PATH`, лише якщо поточний обліковий запис може її виконати. Перевірте її власника, біт SUID, доступ до виконання (зокрема дозволи групи/ACL), встановлену збірку й стан виправлень від постачальника, а також те, чи блокує зміну ідентичності `NoNewPrivs` або монтування з `nosuid`. Netdata вказує виправлені збірки `v1.45.3` і `v1.45.0-169`; наявність зворотних портів виправлень у дистрибутивах потрібно підтверджувати окремо. Версії на панелі керування або самої наявності `ndsudo` недостатньо, щоб довести можливість підвищення привілеїв. Проблема шляху також вимагає, щоб допоміжна програма знаходила зовнішню команду в місці, контрольованому викликувачем.

### Межа привілеїв Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) стосувалася привілейованої логіки Firejail `--join`: спеціально сформована ціль для приєднання могла змусити допоміжну програму setuid-root прийняти простір імен монтування, контрольований зловмисником, і скопіювати небезпечний стан безпеки. Для пасивного тріажу перевірте, чи **може поточна ідентичність виконати** бінарний файл Firejail із setuid, власником якого є root, чи ефективний setuid для його монтування та в контексті процесу й чи не має встановлена збірка потрібного виправлення. В upstream проблему виправлено у [версії 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); пакунки дистрибутивів можуть [містити зворотний порт виправлення](https://github.com/netblue30/firejail/issues/5191), хоча й показувати старішу версію. Ці передумови вказують на об’єкт для перевірки, а не на успішне приєднання чи отримання root shell. Не створюйте фальшиве ізольоване середовище й не запускайте `--join` під час переліку.

### Права на файл журналу GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) стосувалася Screen 4.5.0, яка відкривала вибраний викликувачем файл журналу з підвищеними привілеями. Бінарний файл `screen` або файл із суфіксом версії в інвентарі SUID — лише привід для перевірки: підтвердьте власника root, ефективність виконання SUID для поточного користувача, встановлену збірку й стан виправлень у дистрибутиві, а також відповідну поведінку роботи з файлом журналу. [Debian виправив пакунок версії 4.5.0 зворотним портом виправлення](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), тому рядок версії або назва файла самі по собі не доводять наявності вразливості. Не створюйте файл журналу як звичайну перевірку під час переліку.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) стосувалася привілейованої допоміжної програми блокування пошти S-nail, коли компонент шляху, контрольований викликувачем, міг переходити між каталогами й призвести до довільного запису у файл. Перевірте, чи може поточний користувач виконати встановлену допоміжну програму setuid, власником якої є root, чи діє її ідентичність setuid з огляду на політику монтування та процесу, а також точну збірку пакунка й виправлення постачальника. [Повідомлення безпеки Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) містить зворотний порт виправлення для пакунка 16.04, тому версія, схожа на upstream, не дає однозначної відповіді. Наявність допоміжної програми не доводить, що вразливий шлях доступний або що запис у файл дає змогу виконати код із правами root; під час переліку перевіряйте метадані й стан пакунка, не запускаючи програму й не намагаючись створити гонку.

### Очищення snap-confine і tmpfiles

CVE-2026-3888 — це гонка за участю привілейованого `snap-confine` та очищення `/tmp` засобом systemd-tmpfiles. Під час пасивної перевірки можна з’ясувати, чи має `snap-confine` setuid або файлові capabilities, порівняти встановлений пакунок `snapd` із виправленою версією для цього **випуску Ubuntu**, а також перевірити ефективне правило віку для `/tmp` і таймер очищення. Відповідний пакунок і правило — це передумови, а не доказ досяжності гонки: важливі також фактичний стан таймера, компонування snap, зворотні порти виправлень у пакунках і перевизначення правил. Для старіших випусків може знадобитися нестандартна конфігурація. Не запускайте перевірку на гонку під час звичайного переліку. Див. [запис Ubuntu про CVE](https://ubuntu.com/security/CVE-2026-3888) щодо стану пакунків для конкретних випусків і [рекомендації Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) щодо взаємодії компонентів.

## Перевірте ACL і чутливі шляхи

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Доступний для запису батьківський каталог може дозволити замінити файл, навіть якщо сам файл належить root. ACL може непомітно надавати доступ до додаткового файла sudoers, блока конфігурації служби, скрипту cron, шляху до бібліотеки або файла облікових даних. Перевіряйте і ACL, і повний шлях. Якщо можливий довільний запис у привілейовані файли, дивіться [Arbitrary File Write to Root](write-to-root.md); приклади з конфігурацією компонувальника та preload наведено в [`ld.so` example](ld.so.conf-example.md). Розглядайте відкриті резервні копії, файли `.env`, конфігурації баз даних, матеріали SSH та історію команд як можливі джерела облікових даних; доступ до них визначається фактичними дозволами кожного файла.
