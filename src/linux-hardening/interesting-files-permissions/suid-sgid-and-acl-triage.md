# SUID, SGID, ACL y archivos sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID y SGID cambian la identidad efectiva de un archivo ejecutado; las ACL pueden conceder acceso que los bits de permisos habituales de `ls -l` no muestran. Revisa ambos cuando un usuario pueda leer, escribir o ejecutar más de lo que sugieren los permisos aparentes del propietario y el grupo.

## Enumerar ejecutables privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Presta atención a los ejecutables personalizados o modificados recientemente, a los propietarios inusuales y a los archivos en montajes con permisos de escritura. Un montaje `nosuid` puede suprimir el comportamiento set-ID; las capabilities de archivo son un mecanismo de privilegios independiente, descrito en [Linux capabilities](linux-capabilities.md). Compara un binario sospechoso con el de su paquete y comprueba qué ejecuta, abre o carga con identidad elevada.

Si un ejecutable SUID desconocido, propiedad de root, acepta entradas del usuario, analiza una copia del binario sin conexión para revisar el manejo de argumentos inseguro para la memoria y la ruta de código que llega a este. Registra el comportamiento de los ID efectivos y las mitigaciones, como stack canaries, memoria no ejecutable, código independiente de la posición y aleatorización de direcciones. Un nombre de función insegura o la ausencia de una mitigación son solo indicios para la revisión: la posibilidad de explotación depende de los límites reales de entrada, del flujo de control alcanzable y de la identidad efectiva en el momento del fallo. No envíes argumentos largos al ejecutable privilegiado en producción solo para comprobar si se bloquea durante la enumeración pasiva.

Un programa SUID conocido también puede haber sido reemplazado o contener una puerta trasera. Una fecha de modificación reciente es un indicio, no una prueba: para un **binario sospechoso específico de un paquete**, identifica el paquete propietario y compara el archivo instalado con los metadatos del paquete, en lugar de verificar todos los paquetes durante la enumeración rutinaria:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` comprueba el contenido de los archivos solo cuando la base de datos de paquetes tiene registrado un checksum; RPM también compara metadatos como el modo y el propietario. Céntrate en las discrepancias del **ejecutable privilegiado en sí**: las instalaciones reducidas pueden informar que faltan archivos de documentación o de configuración regional en otras partes del mismo paquete. Compara el ejecutable sospechoso con un paquete confiable del proveedor y revisa exactamente qué código ha cambiado. Los cambios locales legítimos, la ausencia de checksums y los metadatos de paquetes comprometidos limitan lo que demuestra cualquiera de los dos comandos. No ejecutes ni el programa SUID sospechoso ni un script de verificación de paquetes durante el análisis pasivo. Consulta el [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) y el [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programa SUID que ejecuta un shell, un comando relativo o una biblioteca desde una ruta modificable puede cruzar un límite de confianza. Consulta [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), la [PATH guidance](../linux-basics/linux-environment-variables.md#path) y la [user-ID explanation](../user-information/euid-ruid-suid.md). Para escapes conocidos específicos de comandos, consulta [GTFOBins](https://gtfobins.github.io/) para el binario exacto y la invocación permitida en el host.

Para un ejecutable set-user-ID, distingue el **UID real** del invocador del **UID efectivo** del propietario del archivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) deja intacto el UID real y copia el UID efectivo al UID guardado después de cualquier cambio de set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) ejecuta su comando mediante `/bin/sh -c`; el shell seleccionado por esa ruta determina si un proceso hijo conserva su identidad efectiva. En particular, las [Bash privileged-mode rules](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) restablecen un UID efectivo distinto al UID real cuando Bash se inicia sin `-p`. Comprueba los cambios de UID reales del helper y cómo invoca procesos hijos, además de su propietario, los permisos de ejecución, la opción de montaje `nosuid` y el estado `no_new_privs` del proceso. El bit SUID o una llamada al shell por sí solos no demuestran que exista una transición utilizable a mayores privilegios.

Un `jjs` SUID propiedad de root que resulte inusual merece una revisión aparte del acceso a archivos si el usuario actual puede ejecutarlo. La herramienta heredada Nashorn puede acceder a las API de archivos de Java incluso cuando un shell iniciado como proceso hijo pierde el UID efectivo; confirma el comportamiento de la JVM instalada, la identidad efectiva de la operación sobre el archivo y las opciones `nosuid`/`no_new_privs` antes de considerarlo una lectura o escritura privilegiada. [Oracle removed `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); una ruta instalada aún podría corresponder a una compilación anterior o empaquetada por separado. [GTFOBins documents the file APIs](https://gtfobins.org/gtfobins/jjs/), pero sus ejemplos con sudo no demuestran el comportamiento SUID de todas las compilaciones. No invoques la herramienta durante la enumeración pasiva.

Un ejecutable `gosu` SUID propiedad de root y accesible para un usuario con menos privilegios merece una revisión: su interfaz documentada acepta un usuario de destino y un comando, pero su uso normal en contenedores lo inicia como root para reducir privilegios. Verifica el comportamiento SUID de la compilación instalada, la identidad efectiva y la asignación del espacio de nombres de usuario, además de `nosuid` y `no_new_privs`; ser root dentro de un contenedor no implica serlo en el host. El nombre del archivo o el bit SUID por sí solos no demuestran que la transición funcione. Consulta el [upstream usage](https://github.com/tianon/gosu) y la [maintainer's SUID warning](https://github.com/tianon/gosu/issues/11). No invoques el helper durante el inventario pasivo.

Un wrapper de backup personalizado con set-user-ID podría aceptar una ruta elegida por quien lo invoca e interpolarla en un comando de archivo pasado a `system(3)`. Si la ruta no está entre comillas en el comando construido, el shell hijo puede aplicar [tilde expansion using `HOME`, pathname patterns such as `?` and `*`, and newline command separation](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rechazar solo signos de puntuación conocidos mediante una denylist no hace que la ruta se interprete literalmente. Confirma el flujo exacto de argumentos, el entorno heredado, el shell hijo y la identidad efectiva, el acceso al sistema de archivos y si quien invoca puede ver la salida del archivado. El bit SUID, una cadena que nombra una herramienta de archivado o el mero bloqueo de la ruta literal `/root` no demuestran divulgación ni ejecución de código. Revisa una copia del wrapper sin conexión, en vez de archivar archivos privados o enviar entradas que provoquen fallos durante la enumeración pasiva.

La [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) del shell, como `$(...)`, es otro posible punto débil de una denylist de metacaracteres: incluso un prefijo de comando permitido y fijo puede pasar un argumento posterior controlado por quien invoca a través de `/bin/sh -c`. Verifica sin conexión el entrecomillado exacto, el parser y la identidad efectiva; no consideres que una cadena de `system()` o una denylist incompleta demuestran ejecución.

También importa el **árbol de procesos invocadores**. Un worker web puede instalar un filtro seccomp que restrinja las llamadas al sistema que cambian UID; los [seccomp filters pass to children and survive `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por ejemplo, las directivas [`LimitUIDRange` and `LimitGIDRange` de mpm-itk de Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) pueden restringir las identidades disponibles para los procesos descendientes. `Seccomp: 2` en `/proc/self/status` muestra el modo del filtro, no la política ni si este helper concreto puede obtener la identidad de su propietario. Revisa la ascendencia de la invocación real y el filtro efectivo junto con las condiciones SUID, de montaje y `no_new_privs`; una sesión de inicio de sesión independiente puede tener otra política, pero requiere su propia vía de acceso válida.

Un ejecutable SUID personalizado podría invocar un script de Python independiente y legible. Si realmente usa Python **2**, [`input()` evaluates the entered expression](https://docs.python.org/2/library/functions.html#input); en Python 3, `input()` devuelve texto. Confirma la identidad efectiva del wrapper, la ruta y la versión del intérprete, la ruta del script y si la entrada no confiable llega a esa llamada antes de considerar esa línea del código fuente una vía de ejecución. Un bit set-ID en el propio script o una llamada a `input()` sin el wrapper privilegiado no establecen el mismo límite. Revisa las rutas a las que hace referencia el binario y una copia acotada del código fuente del script, sin ejecutarlo durante la enumeración.

Si un ejecutable SUID inusual viene acompañado de código fuente legible, compara el número de bytes solicitado en cada lectura de archivos controlada por quien invoca con el tamaño del búfer de destino e inspecciona las comprobaciones posteriores del flujo de control. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) almacena los elementos solicitados en el puntero proporcionado; no conoce la capacidad del objeto de destino. Una discrepancia de tamaños es una pista estática de un posible problema de seguridad de memoria, no una prueba de que se pueda usar para escalar privilegios: confirma que el código fuente corresponde al binario instalado, que quien invoca puede proporcionar la entrada, que la ejecución SUID es efectiva en ese contexto y que la ruta pertinente es alcanzable. Revisa sin conexión una copia acotada del código fuente o del binario, en vez de enviar entradas que provoquen fallos al programa privilegiado durante la enumeración.

Un helper SUID personalizado puede revelar un archivo protegido sin imprimir su contenido. Si quien invoca elige tanto una ruta como una expresión regular, y el helper devuelve un recuento de coincidencias visible bajo su UID efectivo, las pruebas con prefijos anclados podrían formar un oráculo carácter por carácter. Confirma el propietario del helper, el comportamiento de los ID efectivos, los permisos de ejecución, las restricciones de rutas, la semántica de las expresiones regulares, la visibilidad de la respuesta y la existencia de un archivo concreto de mayores privilegios que quien invoca no pueda leer de otro modo. El bit SUID o una cadena de una biblioteca de expresiones regulares no demuestran nada de ese flujo. Durante la enumeración pasiva, registra el ejecutable inusual y revisa sin conexión una copia acotada del desensamblado o del código fuente; no pruebes iterativamente valores contra el helper activo ni imprimas secretos recuperados.

En OpenBSD, un lector personalizado con set-user-ID que acepte una ruta elegida por quien invoca podría exponer archivos bajo `/var/backups` si su identidad efectiva puede leerlos y devuelve su contenido a quien lo invoca. [OpenBSD's `changelist(5)`](https://man.openbsd.org/changelist.5) describe copias `.current` y `.backup` de las rutas configuradas, pero las entradas precedidas por `+` guardan checksums SHA-256 en lugar del contenido de los archivos; el directorio de backup debería pertenecer a root y tener modo `0700`. Una regla de [`unveil` read](https://man.openbsd.org/unveil.2) del helper para `/var` puede permitir el acceso bajo esa ruta, pero no concede ni demuestra por sí sola el acceso a los archivos. Antes de afirmar que hay escalada, confirma el UID efectivo real, que el usuario actual pueda ejecutar el archivo, la ruta aceptada, la existencia y el contenido del backup y cualquier requisito de autenticación independiente. La enumeración pasiva debe informar sobre el helper y los metadatos de la ruta, no invocar el lector ni imprimir datos del backup.

Un programa SUID personalizado que comprueba una ruta elegida por quien invoca con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) y abre después esa ruta puede sufrir una condición de carrera si cambia un archivo o enlace simbólico en un directorio modificable por quien lo invoca. La comprobación se aplica al objeto anterior, mientras que un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) posterior puede resolver otro. Confirma que el helper se pueda ejecutar con identidad efectiva elevada, que una ruta de código alcanzable lea el archivo seleccionado y que quien invoca pueda reemplazar la ruta entre la comprobación y la apertura; el bit SUID, un directorio modificable o una cadena `stat` no demuestran nada de esto por sí solos. Para que haya divulgación, también hace falta que la salida sea visible o que el destino sea legible por quien invoca. Revisa sin conexión el binario y los metadatos de la ruta; no provoques una condición de carrera en el helper activo durante la enumeración pasiva.

Aplica la misma revisión de dependencias a los wrappers SGID. Un wrapper que ejecuta un shell o helper mediante una ruta absoluta aún puede ser inseguro si un usuario con menos privilegios puede reemplazar ese archivo; el código iniciado podría heredar el grupo efectivo del wrapper. Comprueba la ruta exacta invocada, sus permisos de escritura (incluidas las ACL), el grupo efectivo del wrapper y si este reduce privilegios antes de iniciar el proceso hijo. Un intérprete también puede descartar los ID efectivos heredados, así que distingue entre algo que merece revisión y una transición demostrada. Que haya un shell modificable en otro lugar del host no demuestra por sí solo que un wrapper privilegiado lo invoque.

### Wrappers privilegiados que pasan SQL a la CLI de SQLite

Si un programa SUID personalizado pasa SQL controlado por el usuario al **programa de línea de comandos `sqlite3`**, inspecciona el comando exacto y la identidad efectiva antes de considerar que la consulta es de solo lectura. La función SQL `edit()` de la CLI invoca un editor (indicado en su segundo argumento o en `VISUAL`), y su función SQL `load_extension()` puede cargar una biblioteca compartida si está habilitada la carga de extensiones. Estas son posibles vías de ejecución de código con la identidad del proceso de la CLI, incluso si el wrapper fija `PATH` o usa una ruta absoluta a `sqlite3`. El SQL debe llegar realmente a esas funciones y la CLI debe conservar la función correspondiente; encontrar `sqlite3` en un binario o en el host no demuestra una escalada. La **biblioteca** de SQLite deshabilita la carga de extensiones por defecto, así que distínguela de la CLI. Si una aplicación privilegiada debe procesar SQL no confiable, el modo `--safe` de la CLI de SQLite deshabilita `edit()`, `load_extension()` y otras funciones con efectos secundarios. Consulta la [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), la [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option) y la [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lectores de archivos privilegiados que alimentan un cliente verboso

Un wrapper SUID/SGID personalizado podría comprobar el acceso a una ruta elegida por quien lo invoca y luego pasar ese archivo a otro comando. Revisa la identidad efectiva tanto en la comprobación de acceso como en la apertura posterior, resuelve cualquier componente `../` con respecto al directorio base real e inspecciona cómo trata el proceso hijo las entradas no válidas. Si un cliente de base de datos lee un archivo privado como SQL con salida detallada, podría mostrar el contenido del archivo en mensajes de error aunque el SQL no sea válido. Esto solo es una divulgación entre usuarios si el proceso hijo puede leer un archivo que quien invoca no puede, quien invoca puede seleccionar ese archivo mediante el wrapper y la salida es visible; la presencia de `mysql` o de otra cadena de cliente no demuestra ninguna de estas condiciones.

### Ruta de búsqueda de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afectó a algunas compilaciones de Netdata `ndsudo`. El helper SUID propiedad de root buscaba sus comandos externos permitidos usando un `PATH` proporcionado por quien lo invocaba. Revisa un helper instalado, incluido uno fuera del `PATH` habitual de quien lo invoca, solo si la cuenta actual puede ejecutarlo. Confirma su propietario, el bit SUID, los permisos de ejecución (incluidas las concesiones de grupo/ACL), la compilación instalada y si el proveedor ha publicado un parche, además de si `NoNewPrivs` o un montaje `nosuid` bloquea el cambio de identidad. Netdata enumera las compilaciones corregidas `v1.45.3` y `v1.45.0-169`; los backports de las distribuciones deben confirmarse por separado. La versión del dashboard o la mera presencia de `ndsudo` no bastan para demostrar que la escalada sea alcanzable. El problema de la ruta también requiere que el helper resuelva un comando externo mediante una ubicación controlada por quien lo invoca.

### Límite de privilegios de Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afectó a la lógica privilegiada `--join` de Firejail: un destino de unión manipulado podía hacer que el helper setuid-root aceptara un espacio de nombres de montaje controlado por un atacante y copiara un estado de seguridad inseguro. Para el análisis pasivo, confirma que la **identidad actual pueda ejecutar** un binario Firejail setuid propiedad de root, que setuid sea efectivo en su montaje y contexto de proceso, y que la compilación instalada no incluya la corrección. Upstream corrigió el problema en [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); los paquetes de las distribuciones pueden [backport it](https://github.com/netblue30/firejail/issues/5191) y seguir mostrando una versión anterior. Estos requisitos previos identifican algo que merece revisión, no una unión exitosa ni un shell root. No crees un jail falso ni invoques `--join` durante la enumeración.

### Permisos del archivo de registro de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) afectó a Screen 4.5.0, que abría con privilegios elevados un archivo de registro elegido por quien lo invocaba. Un binario `screen` o con la versión añadida al nombre en el inventario SUID es solo una pista para revisar: confirma que pertenezca a root, que la ejecución SUID sea efectiva para el usuario actual, cuál sea la compilación instalada y el estado del parche de la distribución, y que el comportamiento del archivo de registro esté afectado. [Debian fixed its 4.5.0 package with a backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), por lo que una cadena de versión o un nombre de archivo por sí solos no demuestran que el sistema esté expuesto. No crees un archivo de registro como prueba rutinaria durante la enumeración.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afectó al helper privilegiado de bloqueo de correo de S-nail cuando un componente de ruta controlado por quien lo invocaba podía recorrer directorios y provocar una escritura arbitraria en un archivo. Revisa si el usuario actual puede ejecutar un helper setuid instalado y propiedad de root, si la identidad setuid es efectiva según la política de montaje y de procesos, y cuál es exactamente la compilación del paquete y la corrección del proveedor. [Ubuntu's security notice](https://ubuntu.com/security/notices/USN-4820-1) enumera una corrección retroportada para su paquete 16.04, así que una versión que parece corresponder a upstream no es concluyente por sí sola. La presencia del helper no demuestra que se pueda alcanzar la ruta afectada ni que la escritura de un archivo permita ejecutar código como root; inspecciona los metadatos y el estado del paquete sin invocar el helper ni intentar provocar la condición de carrera durante la enumeración.

### Limpieza de tmpfiles y snap-confine

CVE-2026-3888 es una condición de carrera entre `snap-confine` privilegiado y la limpieza de `/tmp` por systemd-tmpfiles. En una revisión pasiva, comprueba si `snap-confine` es setuid o tiene file capabilities, compara el paquete `snapd` instalado con la versión corregida para esa **versión de Ubuntu** e inspecciona la regla de antigüedad efectiva de `/tmp` y el temporizador de limpieza. Un paquete y una regla coincidentes son requisitos previos, no pruebas de que la condición de carrera sea alcanzable: también importan el estado del temporizador durante la ejecución, la disposición de snap, los backports del paquete y las anulaciones de reglas. Las versiones anteriores podrían requerir una configuración no predeterminada. No ejecutes una prueba de condición de carrera durante la enumeración rutinaria. Consulta el [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) para conocer el estado del paquete en cada versión y el [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para entender la interacción entre componentes.

## Inspeccionar ACL y rutas sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un directorio padre con permisos de escritura puede permitir reemplazar un archivo aunque pertenezca a root. Una ACL puede conceder acceso inadvertidamente a un archivo de configuración de sudoers, una unidad de servicio, un script de cron, una ruta de biblioteca o un archivo de credenciales. Comprueba tanto la ACL como la ruta completa. Si es posible escribir arbitrariamente en archivos privilegiados, consulta [Arbitrary File Write to Root](write-to-root.md); para casos de configuración del enlazador y preload, consulta el [ejemplo de `ld.so`](ld.so.conf-example.md). Considera las copias de seguridad expuestas, los archivos `.env`, las configuraciones de bases de datos, el material SSH y el historial como posibles fuentes de credenciales; el acceso depende de los permisos reales de cada archivo.
