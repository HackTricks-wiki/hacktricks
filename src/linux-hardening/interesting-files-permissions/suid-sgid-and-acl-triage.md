# SUID, SGID, ACLs und sensible Dateien

{{#include ../../banners/hacktricks-training.md}}

SUID und SGID ändern die effektive Identität einer ausgeführten Datei; ACLs können Zugriff gewähren, der in den gewöhnlichen Modusbits von `ls -l` nicht angezeigt wird. Prüfe beides, wenn ein Benutzer mehr lesen, schreiben oder ausführen kann, als die scheinbaren Berechtigungen für Eigentümer und Gruppe vermuten lassen.

## Privilegierte ausführbare Dateien auflisten

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Konzentriere dich auf benutzerdefinierte oder kürzlich geänderte ausführbare Dateien, ungewöhnliche Eigentümer und Dateien auf beschreibbaren Mounts. Ein `nosuid`-Mount kann das set-ID-Verhalten unterdrücken; Dateifähigkeiten sind ein separater Privilegmechanismus, der unter [Linux capabilities](linux-capabilities.md) beschrieben wird. Vergleiche eine verdächtige Binärdatei mit ihrem Paket und prüfe, was sie mit erhöhter Identität ausführt, öffnet oder lädt.

Untersuche bei einer unbekannten, root-eigenen SUID-Programmdatei, die Eingaben des Aufrufers annimmt, eine Kopie der Binärdatei offline auf unsichere Speicherverarbeitung von Argumenten und den Codepfad, der diese erreicht. Halte das Verhalten der effektiven ID sowie Schutzmaßnahmen wie Stack Canaries, nicht ausführbaren Speicher, positionsunabhängigen Code und Adressrandomisierung fest. Ein unsicherer Funktionsname oder eine fehlende Schutzmaßnahme ist lediglich ein Ansatzpunkt für die Überprüfung: Ob die Schwachstelle ausnutzbar ist, hängt von den tatsächlichen Eingabegrenzen, dem erreichbaren Kontrollfluss und der effektiven Identität beim Fehler ab. Sende während einer passiven Bestandsaufnahme keine langen Argumente an die aktive privilegierte Programmdatei, nur um einen Absturz zu testen.

Auch ein vertrautes SUID-Programm kann ersetzt oder mit einer Backdoor versehen worden sein. Ein kürzlicher Änderungszeitpunkt ist ein Ansatzpunkt, kein Beweis: Ermittle bei einer **bestimmten verdächtigen Paket-Binärdatei** das zugehörige Paket und vergleiche die installierte Datei mit den Paketmetadaten, statt bei der routinemäßigen Bestandsaufnahme jedes Paket zu überprüfen:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` prüft Dateiinhalte nur dort, wo die Paketdatenbank eine Prüfsumme gespeichert hat; RPM vergleicht auch Metadaten wie Modus und Eigentümer. Achte auf Abweichungen bei der **privilegierten ausführbaren Datei selbst**: Bei abgespeckten Installationen können fehlende Dokumentations- oder Locale-Dateien an anderer Stelle im selben Paket gemeldet werden. Vergleiche eine verdächtige ausführbare Datei mit einem vertrauenswürdigen Herstellerpaket und prüfe den exakt geänderten Code. Legitime lokale Änderungen, fehlende Prüfsummen und kompromittierte Paketmetadaten schränken ein, was sich mit beiden Befehlen nachweisen lässt. Führe bei einer passiven Triage weder das verdächtige SUID-Programm noch ein Paketprüfskript aus. Siehe das [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) und das [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8).

Ein SUID-Programm, das eine Shell, einen relativen Befehl oder eine Bibliothek aus einem beschreibbaren Pfad aufruft, kann eine Vertrauensgrenze überschreiten. Siehe [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), die [PATH guidance](../linux-basics/linux-environment-variables.md#path) und die [user-ID explanation](../user-information/euid-ruid-suid.md). Bei bekannten befehlsspezifischen Escapes prüfe [GTFOBins](https://gtfobins.github.io/) anhand der exakten ausführbaren Datei und des Aufrufs, die auf dem Host erlaubt sind.

Unterscheide bei einer ausführbaren Datei mit set-user-ID das **real UID** des Aufrufers von der **effective UID** des Dateieigentümers: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lässt die reale UID unverändert und kopiert nach einer set-ID-Änderung die effektive UID in die gespeicherte UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) führt seinen Befehl über `/bin/sh -c` aus; die über diesen Pfad ausgewählte Shell beeinflusst, ob ein Kindprozess seine effektive Identität behält. Insbesondere setzen die [Bash privileged-mode rules](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) eine abweichende effektive UID beim Start von Bash ohne `-p` auf die reale UID zurück. Prüfe die UID-Änderungen und den Aufruf von Kindprozessen des tatsächlichen Helfers sowie dessen Eigentümer, ausführbare Zugriffsrechte, die `nosuid`-Einstellung des Mounts und den `no_new_privs`-Status des Prozesses. Ein SUID-Bit oder Shell-Aufruf allein belegt keinen nutzbaren Übergang zu höheren Privilegien.

Ein ungewöhnliches, root-eigenes SUID-`jjs` verdient eine separate Prüfung des Dateizugriffs, wenn der aktuelle Benutzer es ausführen kann. Das veraltete Nashorn-Tool kann auf Java-Datei-APIs zugreifen, auch wenn eine gestartete Shell eine effektive UID verwirft; bestätige das Verhalten der installierten JVM, die effektive Identität des Dateivorgangs sowie `nosuid`/`no_new_privs`, bevor du es als privilegierten Lese- oder Schreibzugriff einstufst. [Oracle removed `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); ein installierter Pfad kann dennoch auf einen älteren oder separat paketierten Build verweisen. [GTFOBins documents the file APIs](https://gtfobins.org/gtfobins/jjs/), aber die sudo-Beispiele belegen kein SUID-Verhalten für jeden Build. Rufe das Tool bei der passiven Bestandsaufnahme nicht auf.

Eine root-eigene SUID-`gosu`-ausführbare Datei, auf die ein Benutzer mit geringeren Privilegien zugreifen kann, sollte überprüft werden: Die dokumentierte Schnittstelle akzeptiert einen Zielbenutzer und einen Befehl, aber im normalen Containerbetrieb wird sie als root gestartet, um Privilegien abzugeben. Prüfe das SUID-Verhalten des installierten Builds, die effektive Identität und das User-Namespace-Mapping sowie `nosuid` und `no_new_privs`; root im Container bedeutet nicht root auf dem Host. Ein Dateiname oder SUID-Bit allein beweist keinen funktionierenden Übergang. Siehe die [upstream usage](https://github.com/tianon/gosu) und die [maintainer's SUID warning](https://github.com/tianon/gosu/issues/11). Rufe den Helfer bei der passiven Bestandsaufnahme nicht auf.

Ein benutzerdefinierter Backup-Wrapper mit set-user-ID kann einen vom Aufrufer gewählten Pfad akzeptieren und ihn in einen an `system(3)` übergebenen Archivierungsbefehl interpolieren. Wenn dieser Pfad im zusammengesetzten Befehl nicht in Anführungszeichen gesetzt ist, kann die Kind-Shell [Tilde-Erweiterung mit `HOME`, Pfadnamensmuster wie `?` und `*` sowie die Trennung von Befehlen durch Zeilenumbrüche](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) anwenden; nur bekannte Satzzeichen per Denylist zurückzuweisen, macht den Pfad nicht wörtlich. Bestätige den genauen Argumentfluss, die geerbte Umgebung, die Kind-Shell und effektive Identität, den Dateisystemzugriff sowie, ob die Archiv-Ausgabe für den Aufrufer sichtbar ist. Das SUID-Bit, eine Zeichenfolge mit dem Namen eines Archivierungswerkzeugs oder allein ein blockierter `/root`-Literalwert beweist weder Datenoffenlegung noch Codeausführung. Prüfe eine Kopie des Wrappers offline, statt bei der passiven Bestandsaufnahme private Dateien zu archivieren oder fehlerauslösende Eingaben zu senden.

Shell-[Befehlsersetzung](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) wie `$(...)` ist eine weitere mögliche Lücke in einer Metazeichen-Denylist: Selbst ein festes, erlaubtes Befehlspräfix kann ein späteres, vom Aufrufer kontrolliertes Argument über `/bin/sh -c` weiterreichen. Prüfe das genaue Quoting, den Parser und die effektive Identität offline; betrachte eine `system()`-Zeichenfolge oder eine unvollständige Denylist allein nicht als Beleg für Codeausführung.

Auch der **Prozessbaum des aufrufenden Prozesses** ist relevant. Ein Web-Worker kann einen seccomp-Filter installieren, der Systemaufrufe zur Änderung der UID einschränkt; [seccomp filters pass to children and survive `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Beispielsweise können die Apache-Direktiven [mpm-itk `LimitUIDRange` und `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) die für Nachkommen erreichbaren Identitäten einschränken. `Seccomp: 2` in `/proc/self/status` zeigt den Filtermodus, nicht die Richtlinie oder ob dieser bestimmte Helfer die Identität seines Eigentümers annehmen kann. Prüfe gemeinsam die Vorfahren des tatsächlichen Aufrufs und den effektiven Filter sowie die SUID-, Mount- und `no_new_privs`-Bedingungen; eine separate Login-Sitzung kann eine andere Richtlinie haben, benötigt aber einen eigenen gültigen Zugriffsweg.

Ein benutzerdefiniertes SUID-Programm kann ein separates, lesbares Python-Skript aufrufen. Wenn es tatsächlich **Python 2** verwendet, [wertet `input()` den eingegebenen Ausdruck aus](https://docs.python.org/2/library/functions.html#input); Python-3-`input()` gibt dagegen Text zurück. Bestätige die effektive Identität des Wrappers, den Interpreterpfad und die Version, den Skriptpfad sowie, ob nicht vertrauenswürdige Eingaben diesen Aufruf erreichen, bevor du die Quelltextzeile als Ausführungspfad einstufst. Ein set-ID-Bit auf dem Skript selbst oder ein `input()`-Aufruf ohne privilegierten Wrapper begründet nicht dieselbe Vertrauensgrenze. Prüfe die referenzierten Pfade der ausführbaren Datei und eine begrenzte Kopie des Skriptquelltexts, ohne sie bei der Bestandsaufnahme auszuführen.

Wenn lesbarer Quelltext zu einer ungewöhnlichen SUID-ausführbaren Datei vorliegt, vergleiche bei jedem vom Aufrufer kontrollierten Dateizugriff die angeforderte Byteanzahl mit der Größe des Zielpuffers und prüfe nachfolgende Kontrollflussprüfungen. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) speichert die angeforderten Elemente an dem übergebenen Zeiger; die Funktion kennt die Kapazität des Zielobjekts nicht. Eine Größenabweichung ist ein statischer Hinweis auf ein Memory-Safety-Problem, kein Beweis für eine nutzbare Privilegieneskalation: Bestätige, dass der Quelltext zur installierten ausführbaren Datei passt, der Aufrufer die Eingabe bereitstellen kann, die SUID-Ausführung in diesem Kontext wirksam ist und der betreffende Pfad erreichbar ist. Prüfe eine begrenzte Quelltext- oder Binärkopie offline, statt bei der Bestandsaufnahme fehlerauslösende Eingaben an das privilegierte Programm zu senden.

Ein benutzerdefinierter SUID-Helfer kann eine geschützte Datei offenlegen, ohne ihren Inhalt auszugeben. Wenn der Aufrufer sowohl einen Pfadnamen als auch einen regulären Ausdruck auswählt und der Helfer eine sichtbare Trefferanzahl mit seiner effektiven UID zurückgibt, können verankerte Präfixtests als zeichenweiser Oracle dienen. Bestätige den Eigentümer des Helfers, sein Verhalten bezüglich der effektiven ID, den ausführbaren Zugriff, Pfadnamensbeschränkungen, die Regex-Semantik, die Sichtbarkeit der Antwort und eine bestimmte Datei mit höheren Privilegien, die der Aufrufer andernfalls nicht lesen kann. Ein SUID-Bit oder eine Zeichenfolge mit dem Namen einer Regex-Bibliothek allein belegt keinen dieser Abläufe. Halte bei der passiven Bestandsaufnahme die ungewöhnliche ausführbare Datei fest und prüfe eine begrenzte Disassemblierung oder Quelltextkopie; führe keine iterativen Versuche gegen den laufenden Helfer aus und gib keine rekonstruierten Geheimnisse aus.

Unter OpenBSD kann ein benutzerdefinierter Reader mit set-user-ID, der einen vom Aufrufer gewählten Pfad akzeptiert, Dateien unter `/var/backups` offenlegen, wenn seine effektive Identität sie lesen kann und er ihren Inhalt an den Aufrufer zurückgibt. [OpenBSD's `changelist(5)`](https://man.openbsd.org/changelist.5) beschreibt `.current`- und `.backup`-Kopien konfigurierter Pfade, aber Einträge mit vorangestelltem `+` speichern SHA-256-Prüfsummen statt Dateiinhalte; das Backup-Verzeichnis sollte root gehören und den Modus `0700` haben. Eine [`unveil` read rule](https://man.openbsd.org/unveil.2) des Helfers für `/var` kann den Zugriff unterhalb dieses Pfads erlauben, gewährt oder belegt aber nicht selbst den Dateizugriff. Bestätige die tatsächliche effektive UID, die Ausführungsberechtigung für den aktuellen Benutzer, den akzeptierten Pfad, Existenz und Inhalt des Backups sowie etwaige unabhängige Authentifizierungsanforderungen, bevor du eine Eskalation behauptest. Die passive Bestandsaufnahme sollte den Helfer und Pfadmetadaten melden, nicht den Reader aufrufen oder Backup-Daten ausgeben.

Ein benutzerdefiniertes SUID-Programm, das einen vom Aufrufer gewählten Pfad mit [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) prüft und den Pfad später öffnet, kann durch eine Änderung einer Datei oder eines Symlinks in einem vom Aufrufer beschreibbaren Verzeichnis einem Race ausgesetzt sein. Die Prüfung gilt für das frühere Objekt, während ein späterer [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ein anderes Objekt auflösen kann. Bestätige, dass der Helfer mit erhöhter effektiver Identität ausführbar ist, dass ein anderweitig erreichbarer Codepfad die ausgewählte Datei liest und dass der Aufrufer den Pfad zwischen Prüfung und Öffnen ersetzen kann; ein SUID-Bit, ein beschreibbares Verzeichnis oder eine `stat`-Zeichenfolge allein belegt nichts davon. Für eine Datenoffenlegung muss außerdem eine sichtbare Ausgabe oder ein für den Aufrufer lesbares Ziel vorhanden sein. Prüfe die Binärdatei und Pfadmetadaten offline; setze den laufenden Helfer bei der passiven Bestandsaufnahme keinem Race aus.

Wende dieselbe Abhängigkeitsprüfung auf SGID-Wrapper an. Ein Wrapper, der eine Shell oder einen Helfer über einen absoluten Pfad ausführt, kann dennoch unsicher sein, wenn ein Benutzer mit geringeren Privilegien diese Datei ersetzen kann; der gestartete Code kann die effektive Gruppe des Wrappers erben. Prüfe den exakt aufgerufenen Pfad, dessen Schreibrechte (einschließlich ACLs), die effektive Gruppe des Wrappers und ob dieser Privilegien abgibt, bevor er den Kindprozess startet. Ein Interpreter kann geerbte effektive IDs ebenfalls verwerfen; unterscheide daher zwischen einem Prüfungsgegenstand und einem nachgewiesenen Übergang. Eine beschreibbare Shell an anderer Stelle auf dem Host beweist allein nicht, dass ein privilegierter Wrapper sie aufruft.

### Privilegierte Wrapper, die SQL an die SQLite-CLI übergeben

Wenn ein benutzerdefiniertes SUID-Programm vom Benutzer kontrolliertes SQL an das **`sqlite3`-Kommandozeilenprogramm** übergibt, prüfe den exakten Befehl und die effektive Identität, bevor du die Abfrage als schreibgeschützt einstufst. Die SQL-Funktion `edit()` der CLI ruft einen Editor auf (aus ihrem zweiten Argument oder `VISUAL`), und ihre SQL-Funktion `load_extension()` kann eine Shared Library laden, wenn das Laden von Erweiterungen aktiviert ist. Dies sind mögliche Codeausführungspfade mit der Identität des CLI-Prozesses, selbst wenn der Wrapper `PATH` festlegt oder einen absoluten `sqlite3`-Pfad verwendet. Das SQL muss diese Funktionen tatsächlich erreichen, und die CLI muss die betreffende Funktion beibehalten; `sqlite3` lediglich in einer Binärdatei oder auf dem Host zu finden, ist kein Beleg für eine Eskalation. Die SQLite-**Bibliothek** deaktiviert das Laden von Erweiterungen standardmäßig; unterscheide sie von der CLI. Wenn eine privilegierte Anwendung nicht vertrauenswürdiges SQL verarbeiten muss, deaktiviert der CLI-`--safe`-Modus von SQLite `edit()`, `load_extension()` und andere Funktionen mit Seiteneffekten. Siehe die [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), die [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option) und die [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension).

### Privilegierte Datei-Reader, die Daten an einen Client im Verbose-Modus übergeben

Ein benutzerdefinierter SUID/SGID-Wrapper kann den Zugriff auf einen vom Aufrufer gewählten Pfad prüfen und die Datei anschließend an einen anderen Befehl übergeben. Prüfe die effektive Identität sowohl bei der Zugriffsprüfung als auch beim späteren Öffnen, löse alle `../`-Komponenten relativ zum tatsächlichen Basisverzeichnis auf und untersuche, wie der Kindprozess ungültige Eingaben verarbeitet. Wenn ein Datenbank-Client eine private Datei als SQL mit ausführlicher Ausgabe liest, kann er deren Inhalt in Fehlermeldungen wiedergeben, auch wenn das SQL ungültig ist. Eine Offenlegung zwischen Benutzern liegt nur dann vor, wenn der Kindprozess eine Datei lesen kann, die der Aufrufer nicht lesen kann, der Aufrufer diese Datei über den Wrapper auswählen kann und die Ausgabe sichtbar ist; das bloße Vorkommen von `mysql` oder einer anderen Client-Zeichenfolge belegt keine dieser Bedingungen.

### Netdata-`ndsudo`-Suchpfad

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) betraf einige Netdata-`ndsudo`-Builds. Der root-eigene SUID-Helfer suchte die zulässigen externen Befehle mithilfe eines vom Aufrufer bereitgestellten `PATH`. Prüfe einen installierten Helfer, auch wenn er außerhalb des üblichen `PATH` des Aufrufers liegt, aber nur, wenn das aktuelle Konto ihn ausführen kann. Bestätige den Eigentümer, das SUID-Bit, den ausführbaren Zugriff (einschließlich Gruppen-/ACL-Rechten), den installierten Build und den Patch-Status des Herstellers sowie, ob `NoNewPrivs` oder ein `nosuid`-Mount die Identitätsänderung verhindert. Netdata führt die gepatchten Builds `v1.45.3` und `v1.45.0-169` auf; Distributions-Backports müssen separat bestätigt werden. Eine Dashboard-Version oder das bloße Vorhandensein von `ndsudo` reicht als Beleg für eine erreichbare Eskalation nicht aus. Das Pfadproblem setzt außerdem voraus, dass der Helfer einen externen Befehl an einem vom Aufrufer kontrollierten Ort auflöst.

### Firejail-Join-Privilegiengrenze

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) betraf Firejails privilegierte `--join`-Logik: Ein manipulierbares Join-Ziel konnte den setuid-root-Helfer dazu bringen, einen vom Angreifer kontrollierten Mount-Namespace zu akzeptieren und unsichere Sicherheitszustände zu übernehmen. Bestätige bei der passiven Triage, dass die **aktuelle Identität eine root-eigene setuid-Firejail-Binärdatei ausführen kann**, dass setuid auf ihrem Mount und im Prozesskontext wirksam ist und dass der installierte Build den Fix nicht enthält. Upstream behob das Problem in [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); Distributionspakete können den Fix [zurückportieren](https://github.com/netblue30/firejail/issues/5191), während sie weiterhin eine ältere Version anzeigen. Diese Voraussetzungen kennzeichnen einen Prüfungsgegenstand, keinen erfolgreichen Join oder eine Root-Shell. Erstelle bei der Bestandsaufnahme kein gefälschtes Jail und rufe `--join` nicht auf.

### GNU Screen-Logfile-Berechtigungen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) betraf Screen 4.5.0, das ein vom Aufrufer gewähltes Logfile mit erhöhten Privilegien öffnete. Eine `screen`- oder versionierte Binärdatei im SUID-Bestand ist lediglich ein Prüfhinweis: Bestätige den Eigentümer root, die effektive SUID-Ausführung für den aktuellen Benutzer, den installierten Build und den Patch-Status der Distribution sowie das betroffene Logfile-Verhalten. [Debian behob sein 4.5.0-Paket mit einem Backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), daher beweist eine Versionszeichenfolge oder ein Dateiname allein keine Anfälligkeit. Erstelle im Rahmen einer routinemäßigen Bestandsaufnahme kein Logfile als Prüfsonde.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) betraf den privilegierten S-nail-Mail-Lock-Helfer, wenn eine vom Aufrufer kontrollierte Pfadkomponente Verzeichniswechsel ermöglichte und zu einem beliebigen Dateischreibzugriff führen konnte. Prüfe, ob der aktuelle Benutzer einen installierten, root-eigenen setuid-Helfer ausführen kann, ob seine setuid-Identität unter den Mount- und Prozessrichtlinien wirksam ist sowie den genauen Paket-Build und den Hersteller-Fix. [Ubuntus Sicherheitshinweis](https://ubuntu.com/security/notices/USN-4820-1) führt einen zurückportierten Fix für sein 16.04-Paket auf; eine Version, die lediglich wie eine Upstream-Version aussieht, ist daher nicht aussagekräftig. Das Vorhandensein des Helfers beweist nicht, dass der betroffene Pfad erreichbar ist oder dass ein Dateischreibzugriff zu Root-Codeausführung führt; prüfe Metadaten und Paketstatus, ohne den Helfer aufzurufen oder bei der Bestandsaufnahme den Race auszuprobieren.

### snap-confine und tmpfiles-Bereinigung

CVE-2026-3888 ist ein Race zwischen dem privilegierten `snap-confine` und der systemd-tmpfiles-Bereinigung von `/tmp`. Bei einer passiven Prüfung lässt sich feststellen, ob `snap-confine` setuid ist oder Dateifähigkeiten besitzt, ob das installierte `snapd`-Paket mit der für diese **Ubuntu-Version** behobenen Version übereinstimmt und welche effektive Altersregel für `/tmp` sowie welcher Bereinigungstimer gelten. Ein passendes Paket und eine passende Regel sind Voraussetzungen, aber kein Beweis dafür, dass der Race erreichbar ist: Auch Laufzeitstatus des Timers, Snap-Layout, Paket-Backports und Regelüberschreibungen sind relevant. Bei älteren Versionen kann eine nicht standardmäßige Konfiguration erforderlich sein. Führe bei einer routinemäßigen Bestandsaufnahme keine Race-Prüfung aus. Siehe den [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) zum versionsspezifischen Paketstatus und den [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) zur Interaktion der Komponenten.

## ACLs und sensible Pfade prüfen

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ein beschreibbares übergeordnetes Verzeichnis kann das Ersetzen einer Datei ermöglichen, selbst wenn sie root gehört. Eine ACL kann unauffällig Zugriff auf eine sudoers-Ergänzungsdatei, Service-Unit, ein Cron-Skript, einen Bibliothekspfad oder eine Zugangsdaten-Datei gewähren. Prüfe sowohl die ACL als auch den vollständigen Pfad. Sind beliebige Schreibzugriffe auf privilegierte Dateien möglich, folge [Arbitrary File Write to Root](write-to-root.md); Beispiele zu Linker-Konfiguration und Preload findest du im [`ld.so`-Beispiel](ld.so.conf-example.md). Betrachte offengelegte Backups, `.env`-Dateien, Datenbankkonfigurationen, SSH-Schlüsselmaterial und Verlaufsdateien als mögliche Quellen für Zugangsdaten. Der Zugriff darauf richtet sich nach den tatsächlichen Berechtigungen der jeweiligen Datei.
