# SUID, SGID, ACLs і конфіденційні файли

{{#include ../../banners/hacktricks-training.md}}

SUID і SGID змінюють ефективну ідентичність запущеного файлу; ACLs можуть надавати доступ, який не відображають звичайні біти режиму `ls -l`. Перевіряйте їх обидва, якщо користувач може читати, записувати або виконувати файли, доступ до яких, на перший погляд, не дозволяють права власника й групи.

## Перелічіть виконувані файли з підвищеними привілеями

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Зосередьтеся на власних або нещодавно змінених виконуваних файлах, незвичних власниках і файлах на доступних для запису файлових системах. Монтування `nosuid` може вимкнути поведінку set-ID; file capabilities — це окремий механізм привілеїв, описаний у [Linux capabilities](linux-capabilities.md). Порівняйте підозрілий бінарний файл із його пакетом і перевірте, що він виконує, відкриває або завантажує з підвищеною ідентичністю.

Для незнайомого виконуваного файла SUID, власником якого є root і який приймає введені користувачем дані, офлайн проаналізуйте копію бінарного файла на предмет небезпечної для пам’яті обробки аргументів і шляху виконання коду, що до неї веде. Зафіксуйте поведінку effective ID і засоби захисту, як-от stack canaries, невиконувана пам’ять, позиційно-незалежний код і рандомізація адрес. Назва небезпечної функції або відсутність засобу захисту — лише привід для перевірки: можливість експлуатації залежить від фактичних меж введених даних, доступного потоку керування та effective identity у момент збою. Під час пасивного переліку не передавайте довгі аргументи живому привілейованому виконуваному файлу лише для перевірки, чи станеться збій.

Знайому програму SUID також могли підмінити або зловмисно змінити. Нещодавній час модифікації — це привід для перевірки, а не доказ: для **конкретного підозрілого бінарного файла з пакета** визначте пакет-власник і порівняйте встановлений файл із метаданими пакета, а не перевіряйте кожен пакет під час звичайного переліку:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` перевіряє вміст файлів лише там, де в базі даних пакунків записана контрольна сума; RPM також порівнює метадані, як-от режим і власника. Зосередьтеся на невідповідності саме **привілейованого виконуваного файла**: у скорочених інсталяціях можуть бракувати файлів документації чи локалізації в інших місцях того самого пакунка. Порівняйте підозрілий виконуваний файл із довіреним пакунком від постачальника й перевірте точні зміни в коді. Легітимні локальні зміни, відсутні контрольні суми та скомпрометовані метадані пакунка обмежують, що саме доводить кожна з цих команд. Під час пасивного тріажу не запускайте ані підозрілу програму SUID, ані сценарій перевірки пакунка. Див. [посібник із перевірки dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) і [посібник із перевірки RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Програма SUID, яка запускає оболонку, команду за відносним шляхом або бібліотеку з доступного для запису шляху, може перетнути межу довіри. Див. [зловживання спільними бібліотеками та компонувальником SUID](suid-shared-library-and-linker-abuse.md), [рекомендації щодо PATH](../linux-basics/linux-environment-variables.md#path) і [пояснення ідентифікаторів користувача](../user-information/euid-ruid-suid.md). Щоб дізнатися про відомі способи виходу, специфічні для команд, перевірте [GTFOBins](https://gtfobins.github.io/) для точного бінарного файла й способу виклику, дозволеного на хості.

Для виконуваного файла з set-user-ID розрізняйте **реальний UID** викликача та **ефективний UID** власника файла: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) залишає реальний UID незмінним і копіює ефективний UID у збережений UID після будь-якої зміни set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) запускає команду через `/bin/sh -c`; вибрана цим шляхом оболонка впливає на те, чи збереже дочірній процес свою ефективну ідентичність. Зокрема, [правила привілейованого режиму Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) скидають відмінний ефективний UID до реального UID, якщо Bash запускається без `-p`. Перевірте фактичні зміни UID допоміжної програми та спосіб запуску дочірнього процесу, а також її власника, доступ до виконання, параметр монтування `nosuid` і стан процесу `no_new_privs`. Сам по собі біт SUID або виклик оболонки не доводить наявність робочого переходу до вищих привілеїв.

Незвичний SUID-файл `jjs`, власником якого є root, заслуговує на окрему перевірку доступу до файлів, якщо поточний користувач може його виконати. Застарілий інструмент Nashorn може отримувати доступ до файлових API Java, навіть якщо запущена оболонка скидає ефективний UID; перш ніж вважати це привілейованим читанням або записом, перевірте поведінку встановленої JVM, ефективну ідентичність під час файлової операції та параметри `nosuid`/`no_new_privs`. [Oracle вилучила `jjs` у JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); наявний шлях може вести до старішої збірки або збірки з окремого пакунка. [GTFOBins описує файлові API](https://gtfobins.org/gtfobins/jjs/), але приклади з sudo не підтверджують поведінку SUID для кожної збірки. Не запускайте цей інструмент під час пасивного переліку.

Доступний користувачеві з нижчими привілеями виконуваний файл SUID `gosu`, власником якого є root, потребує перевірки: його документований інтерфейс приймає цільового користувача й команду, але за звичайного використання в контейнерах його запускають від root, щоб скинути привілеї. Перевірте поведінку SUID у встановленій збірці, ефективну ідентичність і зіставлення користувачів у просторі імен, а також `nosuid` і `no_new_privs`; root у контейнері не означає root на хості. Самі назва файла або біт SUID не доводять, що перехід працює. Див. [використання в upstream](https://github.com/tianon/gosu) і [попередження супроводжувача щодо SUID](https://github.com/tianon/gosu/issues/11). Не запускайте допоміжну програму під час пасивної інвентаризації.

Власний резервний wrapper із set-user-ID може приймати шлях, вибраний викликачем, і підставляти його в команду архівування, передану до `system(3)`. Якщо цей шлях у сформованій команді не взято в лапки, дочірня оболонка може застосувати [розгортання тильди за допомогою `HOME`, шаблони шляхів на кшталт `?` і `*` та розділення команд символом нового рядка](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); відхилення лише звичних символів за списком заборонених не перетворює шлях на літеральний. Точно з’ясуйте, як передається аргумент, яке середовище успадковується, яка оболонка запускається та з якою ефективною ідентичністю, який доступ до файлової системи має процес і чи видно викликачу вивід архіватора. Біт SUID, рядок із назвою архіватора або заблокований літеральний шлях `/root` самі по собі не доводять ані розкриття даних, ані виконання коду. Під час пасивного переліку перегляньте офлайн копію wrapper, а не архівуйте приватні файли й не надсилайте аварійні вхідні дані.

Підстановлення команд в оболонці, наприклад `$(...)`, — ще одна можлива прогалина у списку заборонених метасимволів: навіть фіксований дозволений префікс команди може передавати пізніший аргумент, контрольований викликачем, до `/bin/sh -c`. Офлайн перевірте точне екранування, парсер і ефективну ідентичність; не вважайте сам рядок `system()` або неповний список заборонених доказом виконання.

Важливе значення має також **дерево процесів-викликачів**. Вебпроцес може встановити seccomp-фільтр, який обмежує системні виклики зміни UID; [seccomp-фільтри успадковуються дочірніми процесами та зберігаються після `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Наприклад, директиви Apache [mpm-itk `LimitUIDRange` і `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) можуть обмежувати ідентичності, доступні нащадкам. Значення `Seccomp: 2` у `/proc/self/status` показує режим фільтра, а не його політику й не те, чи може саме ця допоміжна програма отримати ідентичність власника. Перевірте разом походження фактичного виклику та чинний фільтр, а також умови SUID, монтування й `no_new_privs`; окрема сесія входу може мати іншу політику, але для неї потрібен власний дійсний шлях доступу.

Власний виконуваний файл SUID може запускати окремий доступний для читання сценарій Python. Якщо він справді використовує **Python 2**, [`input()` обчислює введений вираз](https://docs.python.org/2/library/functions.html#input); у Python 3 `input()` натомість повертає текст. Перш ніж вважати цей рядок коду шляхом до виконання, перевірте ефективну ідентичність wrapper, шлях до інтерпретатора та його версію, шлях до сценарію й те, чи передаються недовірені дані до цього виклику. Біт set-ID на самому сценарії або виклик `input()` без привілейованого wrapper не створюють такої самої межі. Під час переліку перегляньте шляхи, на які посилається бінарний файл, і обмежену за розміром копію сценарію, не запускаючи його.

Якщо незвичний виконуваний файл SUID супроводжується доступним для читання вихідним кодом, порівняйте кількість байтів, запитану під час кожного читання контрольованого викликачем файла, з розміром буфера призначення та перевірте подальші перевірки потоку керування. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) записує запитану кількість елементів за переданою адресою; функція не знає місткості об’єкта призначення. Невідповідність розмірів — це зачіпка для статичного аналізу безпеки пам’яті, а не доказ придатного для використання підвищення привілеїв: підтвердьте, що вихідний код відповідає встановленому бінарному файлу, викликач може надати вхідні дані, виконання SUID діє в цьому контексті й відповідний шлях доступний. Під час переліку офлайн перегляньте обмежену за розміром копію вихідного коду або бінарного файла, а не надсилайте аварійні вхідні дані привілейованій програмі.

Власна допоміжна програма SUID може розкрити захищений файл, не виводячи його вміст. Якщо викликач задає і шлях, і регулярний вираз, а допоміжна програма повертає видиму кількість збігів, використовуючи власну ефективну ідентичність, перевірки префіксів із прив’язкою до початку рядка можуть утворювати посимвольний оракул. Перевірте власника допоміжної програми, поведінку ефективного ідентифікатора, доступ до виконання, обмеження шляхів, семантику регулярних виразів, видимість відповіді та наявність конкретного файла з вищими привілеями, який викликач інакше не може прочитати. Біт SUID або рядок із назвою бібліотеки регулярних виразів самі по собі нічого з цього не доводять. Під час пасивного переліку зафіксуйте незвичний виконуваний файл і перегляньте обмежену за розміром копію дизасембльованого коду або вихідного коду; не перевіряйте вгадування по черзі на робочій допоміжній програмі й не виводьте відновлені секрети.

В OpenBSD власна програма читання з set-user-ID, яка приймає шлях, вибраний викликачем, може відкривати файли в `/var/backups`, якщо ефективна ідентичність програми дає змогу їх читати, а вміст повертається викликачеві. [У `changelist(5)` OpenBSD](https://man.openbsd.org/changelist.5) описано копії `.current` і `.backup` налаштованих шляхів, але для записів із префіксом `+` зберігаються контрольні суми SHA-256, а не вміст файлів; каталог резервних копій має належати root і мати режим `0700`. Правило читання [`unveil` для `/var`](https://man.openbsd.org/unveil.2) у допоміжній програмі може дозволяти доступ до цього шляху, але саме по собі не надає й не доводить доступ до файлів. Перш ніж заявляти про підвищення привілеїв, перевірте фактичний ефективний UID, право поточного користувача виконувати файл, прийнятний шлях, наявність і вміст резервної копії та будь-які незалежні вимоги автентифікації. Пасивний перелік має фіксувати допоміжну програму й метадані шляху, а не запускати програму читання чи виводити дані з резервної копії.

Власна програма SUID, яка перевіряє шлях, вибраний викликачем, за допомогою [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), а пізніше відкриває цей шлях, може піддатися гонці, якщо викликач змінить файл або символічне посилання в каталозі, доступному для запису. Перевірка стосується попереднього об’єкта, тоді як пізніший виклик [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) може повернути інший. Переконайтеся, що допоміжну програму можна виконати з підвищеною ефективною ідентичністю, що іншим чином доступний шлях виконання читає вибраний файл і що викликач може підмінити шлях між перевіркою та відкриттям; самі по собі біт SUID, доступний для запису каталог або рядок `stat` нічого з цього не доводять. Для розкриття даних потрібні також видимий вивід або місце призначення, доступне викликачеві. Офлайн перегляньте бінарний файл і метадані шляху; під час пасивного переліку не влаштовуйте гонку проти робочої допоміжної програми.

Таку саму перевірку залежностей застосовуйте до wrapper SGID. Wrapper, який запускає оболонку або допоміжну програму за абсолютним шляхом, усе одно може бути небезпечним, якщо користувач із нижчими привілеями може замінити цей файл; запущений код може успадкувати ефективну групу wrapper. Перевірте точний шлях до викликаного файла, право запису до нього (зокрема через ACL), ефективну групу wrapper і те, чи скидає він привілеї перед запуском дочірнього процесу. Інтерпретатор також може відкидати успадковані ефективні ідентифікатори, тож розрізняйте об’єкт для перевірки та підтверджений перехід. Сам факт наявності на хості доступної для запису оболонки не доводить, що її викликає привілейований wrapper.

### Привілейовані wrapper, які передають SQL до CLI SQLite

Якщо власна програма SUID передає контрольований користувачем SQL до **програми командного рядка `sqlite3`**, перед тим як вважати запит лише для читання, перевірте точну команду та ефективну ідентичність. SQL-функція CLI `edit()` запускає редактор (з другого аргументу або зі змінної `VISUAL`), а SQL-функція `load_extension()` може завантажити спільну бібліотеку, якщо завантаження розширень увімкнено. Це потенційні шляхи виконання коду з ідентичністю процесу CLI, навіть якщо wrapper задає фіксований `PATH` або використовує абсолютний шлях до `sqlite3`. SQL має справді доходити до цих функцій, а CLI має зберігати відповідну можливість; сам факт наявності `sqlite3` у бінарному файлі або на хості не є доказом підвищення привілеїв. **Бібліотека** SQLite типово вимикає завантаження розширень, тож відрізняйте її від CLI. Якщо привілейована програма має обробляти недовірений SQL, безпечний режим CLI SQLite `--safe` вимикає `edit()`, `load_extension()` та інші функції з побічними ефектами. Див. [документацію CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), [документацію безпечного режиму](https://www.sqlite.org/cli.html#the_safe_command_line_option) і [документацію завантаження розширень](https://www.sqlite.org/loadext.html#loading_an_extension).

### Привілейовані програми читання файлів, які передають дані клієнту з докладним виводом

Власний wrapper SUID/SGID може перевіряти доступ до шляху, вибраного викликачем, а потім передавати файл іншій команді. Перевірте ефективну ідентичність і під час перевірки доступу, і під час подальшого відкриття, розберіть усі компоненти `../` відносно фактичного базового каталогу та з’ясуйте, як дочірній процес обробляє некоректні вхідні дані. Якщо клієнт бази даних читає приватний файл як SQL із докладним виводом, він може показати вміст файла в повідомленнях про помилки, навіть якщо SQL некоректний. Це є розкриттям даних між користувачами лише тоді, коли дочірній процес може прочитати файл, недоступний викликачеві, викликач може вибрати цей файл через wrapper, а вивід доступний для нього; сама наявність `mysql` або іншого рядка з назвою клієнта не доводить виконання жодної з цих умов.

### Шлях пошуку Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) стосувалася деяких збірок Netdata `ndsudo`. Допоміжна програма з SUID, власником якої є root, шукала дозволені зовнішні команди за переданим викликачем `PATH`. Перевіряйте встановлену допоміжну програму, зокрема ту, що розташована поза звичним для викликача `PATH`, лише якщо поточний обліковий запис може її виконати. Перевірте її власника, біт SUID, доступ до виконання (зокрема дозволи групи/ACL), встановлену збірку й статус виправлення від постачальника, а також те, чи блокує зміну ідентичності `NoNewPrivs` або монтування `nosuid`. Netdata зазначає виправлені збірки `v1.45.3` і `v1.45.0-169`; бекпорти дистрибутивів потрібно перевіряти окремо. Версії на панелі керування або самої наявності `ndsudo` недостатньо, щоб підтвердити досяжне підвищення привілеїв. Проблема шляху також потребує, щоб допоміжна програма знаходила зовнішню команду в місці, контрольованому викликачем.

### Межа привілеїв Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) стосувалася привілейованої логіки Firejail `--join`: спеціально сформована ціль для приєднання могла змусити допоміжну програму setuid-root прийняти простір імен монтування, контрольований зловмисником, і скопіювати небезпечний стан безпеки. Для пасивного тріажу підтвердьте, що **поточна ідентичність може виконати** бінарний файл Firejail із setuid, власником якого є root, що setuid діє в його точці монтування та контексті процесу, і що встановлена збірка не містить виправлення. Upstream виправив проблему у [версії 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); пакунки дистрибутивів можуть [містити бекпорт виправлення](https://github.com/netblue30/firejail/issues/5191), навіть якщо відображають старішу версію. Ці передумови визначають об’єкт для перевірки, а не успішне приєднання чи отримання root-оболонки. Не створюйте фальшиве ізольоване середовище й не запускайте `--join` під час переліку.

### Дозволи на файли журналу GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) стосувалася Screen 4.5.0, яка відкривала вибраний викликачем файл журналу з підвищеними привілеями. Бінарний файл `screen` або його версія з суфіксом у переліку SUID — лише зачіпка для перевірки: підтвердьте, що власником є root, виконання SUID діє для поточного користувача, а також з’ясуйте встановлену збірку, статус виправлення дистрибутива й поведінку з файлом журналу, якої стосується проблема. [Debian виправив свій пакунок 4.5.0 за допомогою бекпорту](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), тож самого рядка версії або імені файла недостатньо, щоб довести наявність уразливості. Не створюйте файл журналу як звичайну перевірку під час переліку.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) стосувалася привілейованої допоміжної програми S-nail для блокування поштових файлів: компонент шляху, контрольований викликачем, міг проходити через каталоги й призводити до запису в довільний файл. Перевірте, чи може поточний користувач виконати встановлену допоміжну програму setuid, власником якої є root, чи діє її setuid-ідентичність з огляду на політику монтування й процесу, а також точну збірку пакунка й виправлення постачальника. [У повідомленні безпеки Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) зазначено бекпортоване виправлення для пакунка 16.04, тож версії, схожої на upstream, недостатньо для висновку. Наявність допоміжної програми не доводить, що вразливий шлях доступний або що запис у файл дасть змогу виконати код від root; під час переліку перевіряйте метадані й стан пакунка, не запускаючи допоміжну програму та не намагаючись відтворити гонку.

### Очищення snap-confine і tmpfiles

CVE-2026-3888 — це гонка між привілейованою програмою `snap-confine` та очищенням `/tmp` засобом systemd-tmpfiles. Під час пасивної перевірки можна з’ясувати, чи має `snap-confine` setuid або файлові capabilities, порівняти встановлений пакунок `snapd` із виправленою версією для цього **випуску Ubuntu**, а також переглянути чинне правило віку файлів у `/tmp` і таймер очищення. Відповідність пакунка й правила є передумовами, а не доказом досяжності гонки: важливі також поточний стан таймера, структура snap, бекпорти пакунків і перевизначення правил. Для старіших випусків може знадобитися конфігурація, відмінна від типової. Не запускайте пробу на гонку під час звичайного переліку. Див. [запис Ubuntu про CVE](https://ubuntu.com/security/CVE-2026-3888), де вказано стан пакунків для окремих випусків, і [рекомендації Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root), де описано взаємодію компонентів.

## Перевірте ACL і чутливі шляхи

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Доступний для запису батьківський каталог може дозволити заміну файла, навіть якщо сам файл належить root. ACL може непомітно надавати доступ до drop-in-файла sudoers, service unit, cron-скрипту, шляху до бібліотеки або файла облікових даних. Перевіряйте і ACL, і повний шлях. Якщо можливий довільний запис у привілейовані файли, див. [Arbitrary File Write to Root](write-to-root.md); щодо конфігурації компонувальника та випадків із preload див. [приклад `ld.so`](ld.so.conf-example.md). Розглядайте доступні резервні копії, файли `.env`, конфігурації баз даних, матеріали SSH та історію команд як можливі джерела облікових даних; доступ до них визначається фактичними правами кожного файла.
