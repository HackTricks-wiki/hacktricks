# SUID, SGID, ACLs und sensible Dateien

{{#include ../../banners/hacktricks-training.md}}

SUID und SGID ändern die effektive Identität einer ausgeführten Datei; ACLs können Zugriffsrechte gewähren, die in den gewöhnlichen Rechtebits von `ls -l` nicht angezeigt werden. Überprüfe beides, wenn ein Benutzer mehr lesen, schreiben oder ausführen kann, als die scheinbaren Berechtigungen für Eigentümer und Gruppe vermuten lassen.

## Privilegierte ausführbare Dateien auflisten

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Konzentriere dich auf eigene oder kürzlich geänderte Executables, ungewöhnliche Eigentümer und Dateien auf beschreibbaren Mounts. Ein `nosuid`-Mount kann das set-ID-Verhalten unterdrücken; Date capabilities sind ein separater Privilegienmechanismus, der unter [Linux capabilities](linux-capabilities.md) beschrieben wird. Vergleiche eine verdächtige Binärdatei mit ihrem Paket und prüfe, was sie mit erhöhter Identität ausführt, öffnet oder lädt.

Bei einem unbekannten, root-eigenen SUID-Executable, das Eingaben des Aufrufers akzeptiert, untersuche offline eine Kopie der Binärdatei auf unsichere Speicherbehandlung von Argumenten und den Codepfad, der diese erreicht. Halte das Verhalten der effektiven IDs und Schutzmaßnahmen wie Stack-Canaries, nicht ausführbaren Speicher, positionsunabhängigen Code und Adressrandomisierung fest. Ein unsicherer Funktionsname oder eine fehlende Schutzmaßnahme ist nur ein Ansatzpunkt für die Prüfung: Ob sich eine Schwachstelle ausnutzen lässt, hängt von den tatsächlichen Eingabegrenzen, dem erreichbaren Kontrollfluss und der effektiven Identität beim Fehler ab. Sende bei einer passiven Bestandsaufnahme keine langen Argumente an das aktive privilegierte Executable, nur um einen Absturz zu testen.

Auch ein bekanntes SUID-Programm kann ersetzt oder mit einer Hintertür versehen worden sein. Eine kürzliche Änderungszeit ist ein Ansatzpunkt, kein Beweis: Ermittle bei einer **bestimmten verdächtigen Paketdatei** das zugehörige Paket und vergleiche die installierte Datei mit den Paketmetadaten, anstatt bei einer routinemäßigen Bestandsaufnahme jedes Paket zu überprüfen:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` prüft Dateiinhalte nur dort, wo die Paketdatenbank eine Prüfsumme gespeichert hat; RPM vergleicht außerdem Metadaten wie Modus und Eigentümer. Achten Sie auf Abweichungen bei der **privilegierten ausführbaren Datei selbst**: Bei abgespeckten Installationen können fehlende Dokumentations- oder Sprachdateien an anderer Stelle desselben Pakets gemeldet werden. Vergleichen Sie eine verdächtige ausführbare Datei mit einem vertrauenswürdigen Herstellerpaket und prüfen Sie den genau geänderten Code. Legitime lokale Änderungen, fehlende Prüfsummen und manipulierte Paketmetadaten schränken die Aussagekraft beider Befehle ein. Führen Sie im Rahmen einer passiven Triage weder das verdächtige SUID-Programm noch ein Paketverifikationsskript aus. Siehe das [dpkg-Verifikationshandbuch](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) und das [RPM-Verifikationshandbuch](https://rpm.org/docs/4.20.x/man/rpm.8).

Ein SUID-Programm, das eine Shell, einen relativen Befehl oder eine Bibliothek aus einem beschreibbaren Pfad aufruft, kann eine Vertrauensgrenze überschreiten. Siehe [Missbrauch von SUID-Bibliotheken und Linkern](suid-shared-library-and-linker-abuse.md), die [PATH-Hinweise](../linux-basics/linux-environment-variables.md#path) und die [Erklärung der Benutzer-IDs](../user-information/euid-ruid-suid.md). Für bekannte befehlsspezifische Escapes prüfen Sie [GTFOBins](https://gtfobins.github.io/) anhand der genauen Binärdatei und des Aufrufs, die auf dem Host zulässig sind.

Unterscheiden Sie bei einer Set-User-ID-Datei die **reale UID** des Aufrufers von der **effektiven UID** des Dateieigentümers: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lässt die reale UID unverändert und kopiert nach einer Set-ID-Änderung die effektive UID in die gespeicherte UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) führt seinen Befehl über `/bin/sh -c` aus; die über diesen Pfad ausgewählte Shell beeinflusst, ob ein Kindprozess seine effektive Identität behält. Insbesondere setzen die [Regeln des Bash-Privileged-Modus](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) eine abweichende effektive UID auf die reale UID zurück, wenn Bash ohne `-p` startet. Prüfen Sie die UID-Änderungen des tatsächlichen Hilfsprogramms und den Aufruf seiner Kindprozesse sowie dessen Eigentümer, Ausführungsrechte, die `nosuid`-Einstellung des Mounts und den `no_new_privs`-Status des Prozesses. Ein SUID-Bit oder ein Shell-Aufruf allein belegt keinen nutzbaren Übergang zu höheren Privilegien.

Ein ungewöhnliches root-eigenes SUID-`jjs` verdient eine separate Überprüfung des Dateizugriffs, wenn der aktuelle Benutzer es ausführen kann. Das veraltete Nashorn-Tool kann auf Java-Datei-APIs zugreifen, selbst wenn eine gestartete Shell eine effektive UID verliert. Prüfen Sie das Verhalten der installierten JVM, die effektive Identität des Dateivorgangs und `nosuid`/`no_new_privs`, bevor Sie es als privilegierten Lese- oder Schreibzugriff einstufen. [Oracle hat `jjs` in JDK 15 entfernt](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); ein installierter Pfad kann dennoch auf einen älteren oder separat paketierten Build verweisen. [GTFOBins dokumentiert die Datei-APIs](https://gtfobins.org/gtfobins/jjs/), doch die sudo-Beispiele belegen nicht das SUID-Verhalten jedes Builds. Rufen Sie das Tool während einer passiven Bestandsaufnahme nicht auf.

Eine root-eigene SUID-`gosu`-Datei, die für einen weniger privilegierten Benutzer zugänglich ist, sollte überprüft werden: Die dokumentierte Schnittstelle akzeptiert einen Zielbenutzer und einen Befehl, doch bei der normalen Verwendung in Containern wird sie als root gestartet, um Privilegien abzugeben. Prüfen Sie das SUID-Verhalten des installierten Builds, die effektive Identität und das User-Namespace-Mapping sowie `nosuid` und `no_new_privs`; root im Container bedeutet nicht root auf dem Host. Ein Dateiname oder SUID-Bit allein beweist keinen funktionierenden Übergang. Siehe die [Upstream-Verwendung](https://github.com/tianon/gosu) und den [SUID-Warnhinweis des Maintainers](https://github.com/tianon/gosu/issues/11). Rufen Sie das Hilfsprogramm während einer passiven Bestandsaufnahme nicht auf.

Ein benutzerdefinierter Set-User-ID-Backup-Wrapper akzeptiert möglicherweise einen vom Aufrufer gewählten Pfad und setzt ihn in einen an `system(3)` übergebenen Archivbefehl ein. Wenn dieser Pfad im zusammengesetzten Befehl nicht in Anführungszeichen steht, kann die Kind-Shell [Tilde-Erweiterung mit `HOME`, Pfadnamensmuster wie `?` und `*` sowie die Trennung von Befehlen durch Zeilenumbrüche](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) anwenden; nur vertraute Satzzeichen über eine Denylist zurückzuweisen, macht den Pfad nicht wörtlich. Prüfen Sie den genauen Argumentfluss, die vererbte Umgebung, die Kind-Shell und ihre effektive Identität, den Dateisystemzugriff und ob die Archivausgabe für den Aufrufer sichtbar ist. Das SUID-Bit, eine Zeichenkette mit dem Namen eines Archiv-Tools oder ein blockierter `/root`-Literalwert beweisen allein weder eine Offenlegung noch Codeausführung. Prüfen Sie offline eine Kopie des Wrappers, statt während einer passiven Bestandsaufnahme private Dateien zu archivieren oder Eingaben zu senden, die Abstürze verursachen.

Die Shell-[Befehlsersetzung](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) wie `$(...)` ist eine weitere mögliche Lücke in einer Metazeichen-Denylist: Selbst ein festes zulässiges Befehlspräfix kann ein späteres, vom Aufrufer kontrolliertes Argument über `/bin/sh -c` weiterreichen. Prüfen Sie offline die genaue Quotierung, den Parser und die effektive Identität; betrachten Sie eine `system()`-Zeichenkette oder eine unvollständige Denylist nicht allein als Beweis für Codeausführung.

Auch der **Prozessbaum des Aufrufers** ist wichtig. Ein Web-Worker kann einen seccomp-Filter installieren, der Systemaufrufe zur Änderung von UIDs einschränkt; [seccomp-Filter werden an Kindprozesse weitergegeben und bleiben über `execve` hinweg aktiv](https://docs.kernel.org/userspace-api/seccomp_filter.html). Beispielsweise können die Apache-Direktiven [mpm-itk `LimitUIDRange` und `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) die Identitäten einschränken, die Nachfolgeprozesse annehmen können. `Seccomp: 2` in `/proc/self/status` zeigt den Filtermodus, nicht die Richtlinie oder ob dieses bestimmte Hilfsprogramm die Identität seines Eigentümers annehmen kann. Prüfen Sie gemeinsam den tatsächlichen Aufrufkontext und seinen effektiven Filter sowie die SUID-, Mount- und `no_new_privs`-Bedingungen; eine separate Login-Sitzung kann einer anderen Richtlinie unterliegen, benötigt aber einen eigenen gültigen Zugriffsweg.

Eine benutzerdefinierte SUID-Datei kann ein separates, lesbares Python-Skript aufrufen. Wenn tatsächlich **Python 2** verwendet wird, [wertet `input()` den eingegebenen Ausdruck aus](https://docs.python.org/2/library/functions.html#input); `input()` in Python 3 gibt stattdessen Text zurück. Prüfen Sie die effektive Identität des Wrappers, Interpreterpfad und -version, den Skriptpfad und ob nicht vertrauenswürdige Eingaben diesen Aufruf erreichen, bevor Sie die Quelltextzeile als Ausführungspfad einstufen. Ein Set-ID-Bit auf dem Skript selbst oder ein `input()`-Aufruf ohne privilegierten Wrapper stellt nicht dieselbe Vertrauensgrenze dar. Prüfen Sie die referenzierten Pfade der Binärdatei und einen begrenzten Ausschnitt des Skripts, ohne es während der Bestandsaufnahme auszuführen.

Wenn ungewöhnliche SUID-Dateien mitlesbare Quelltexte haben, vergleichen Sie bei jedem vom Aufrufer kontrollierten Lesezugriff die angeforderte Byteanzahl mit der Größe des Zielpuffers und prüfen Sie nachfolgende Kontrollflussprüfungen. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) speichert die angeforderte Anzahl von Elementen an dem übergebenen Zeiger; die Funktion kennt die Kapazität des Zielobjekts nicht. Eine Größenabweichung ist ein Hinweis auf ein mögliches Speicherfehlerproblem im Quelltext, kein Beweis für eine nutzbare Rechteausweitung: Bestätigen Sie, dass der Quelltext zur installierten Binärdatei passt, der Aufrufer die Eingabe bereitstellen kann, die SUID-Ausführung in diesem Kontext wirksam ist und der relevante Pfad erreichbar ist. Prüfen Sie eine begrenzte Kopie des Quelltexts oder der Binärdatei offline, statt während der Bestandsaufnahme Eingaben zu senden, die das privilegierte Programm zum Absturz bringen.

Ein benutzerdefiniertes SUID-Hilfsprogramm kann eine geschützte Datei offenlegen, ohne ihren Inhalt auszugeben. Wenn der Aufrufer sowohl einen Pfadnamen als auch einen regulären Ausdruck vorgibt und das Hilfsprogramm unter seiner effektiven UID eine sichtbare Trefferzahl zurückgibt, können verankerte Präfixtests als zeichenweises Oracle dienen. Prüfen Sie den Eigentümer des Hilfsprogramms, das Verhalten der effektiven IDs, die Ausführungsrechte, Pfadbeschränkungen, die Regex-Semantik, die Sichtbarkeit der Antwort und ob es eine konkrete Datei mit höheren Privilegien gibt, die der Aufrufer nicht anderweitig lesen kann. Ein SUID-Bit oder eine Zeichenkette mit dem Namen einer Regex-Bibliothek beweist keinen dieser Abläufe. Erfassen Sie während einer passiven Bestandsaufnahme die ungewöhnliche ausführbare Datei und prüfen Sie offline eine begrenzte Disassemblierung oder Quelltextkopie; führen Sie keine iterativen Versuche mit dem aktiven Hilfsprogramm durch und geben Sie keine wiederhergestellten Geheimnisse aus.

Unter OpenBSD kann ein benutzerdefiniertes Set-User-ID-Leseprogramm, das einen vom Aufrufer gewählten Pfad akzeptiert, Dateien unter `/var/backups` offenlegen, wenn seine effektive Identität sie lesen kann und es ihren Inhalt an den Aufrufer zurückgibt. [OpenBSDs `changelist(5)`](https://man.openbsd.org/changelist.5) beschreibt `.current`- und `.backup`-Kopien konfigurierter Pfade. Einträge mit vorangestelltem `+` speichern jedoch SHA-256-Prüfsummen statt Dateiinhalte; das Backup-Verzeichnis sollte root gehören und den Modus `0700` haben. Eine [`unveil`-Leseregel](https://man.openbsd.org/unveil.2) des Hilfsprogramms für `/var` kann den Zugriff unterhalb dieses Pfads erlauben, gewährt oder beweist aber nicht selbst den Dateizugriff. Bestätigen Sie die tatsächliche effektive UID, die Ausführungsrechte für den aktuellen Benutzer, den akzeptierten Pfad, das Vorhandensein und den Inhalt des Backups sowie etwaige unabhängige Authentifizierungsanforderungen, bevor Sie eine Rechteausweitung behaupten. Eine passive Bestandsaufnahme sollte das Hilfsprogramm und die Pfadmetadaten erfassen, nicht das Leseprogramm aufrufen oder Backup-Daten ausgeben.

Ein benutzerdefiniertes SUID-Programm, das einen vom Aufrufer gewählten Pfad mit [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) prüft und den Pfad später öffnet, kann einem Wechsel einer Datei oder eines Symlinks in einem beschreibbaren Verzeichnis des Aufrufers unterliegen. Die Prüfung bezieht sich auf das frühere Objekt, während ein späteres [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ein anderes auflösen kann. Bestätigen Sie, dass das Hilfsprogramm mit erhöhter effektiver Identität ausführbar ist, dass ein anderweitig erreichbarer Codepfad die gewählte Datei liest und dass der Aufrufer den Pfad zwischen Prüfung und Öffnen ersetzen kann; ein SUID-Bit, ein beschreibbares Verzeichnis oder eine `stat`-Zeichenkette allein belegt nichts davon. Für eine Offenlegung ist außerdem eine sichtbare Ausgabe oder ein für den Aufrufer lesbares Ziel erforderlich. Prüfen Sie die Binärdatei und die Pfadmetadaten offline; führen Sie während einer passiven Bestandsaufnahme keine Race-Bedingungen mit dem aktiven Hilfsprogramm herbei.

Führen Sie dieselbe Abhängigkeitsprüfung bei SGID-Wrappern durch. Ein Wrapper, der eine Shell oder ein Hilfsprogramm über einen absoluten Pfad startet, kann trotzdem unsicher sein, wenn ein weniger privilegierter Benutzer diese Datei ersetzen kann; der gestartete Code kann die effektive Gruppe des Wrappers übernehmen. Prüfen Sie den genau aufgerufenen Pfad, dessen Schreibrechte (einschließlich ACLs), die effektive Gruppe des Wrappers und ob er Privilegien abgibt, bevor er den Kindprozess startet. Ein Interpreter kann vererbte effektive IDs ebenfalls verwerfen; unterscheiden Sie daher einen Prüfungsansatz von einem nachgewiesenen Übergang. Eine an anderer Stelle auf dem Host beschreibbare Shell beweist allein nicht, dass ein privilegierter Wrapper sie aufruft.

### Privilegierte Wrapper, die SQL an die SQLite-CLI übergeben

Wenn ein benutzerdefiniertes SUID-Programm vom Benutzer kontrolliertes SQL an das **Befehlszeilenprogramm `sqlite3`** übergibt, prüfen Sie den genauen Befehl und die effektive Identität, bevor Sie die Abfrage als schreibgeschützt einstufen. Die SQL-Funktion `edit()` der CLI ruft einen Editor auf (aus ihrem zweiten Argument oder `VISUAL`), und ihre SQL-Funktion `load_extension()` kann eine Shared Library laden, wenn das Laden von Erweiterungen aktiviert ist. Dies sind mögliche Codeausführungspfade mit der Identität des CLI-Prozesses, auch wenn der Wrapper `PATH` festlegt oder einen absoluten `sqlite3`-Pfad verwendet. Das SQL muss diese Funktionen tatsächlich erreichen, und die CLI muss die entsprechende Funktion behalten; `sqlite3` in einer Binärdatei oder auf dem Host zu finden, ist allein kein Beleg für eine Rechteausweitung. Die SQLite-**Bibliothek** deaktiviert das Laden von Erweiterungen standardmäßig; unterscheiden Sie sie von der CLI. Wenn eine privilegierte Anwendung nicht vertrauenswürdiges SQL verarbeiten muss, deaktiviert der CLI-`--safe`-Modus von SQLite `edit()`, `load_extension()` und andere Funktionen mit Nebenwirkungen. Siehe die [SQLite-CLI-Dokumentation](https://www.sqlite.org/cli.html#the_edit_sql_function), die [Dokumentation zum Safe-Modus](https://www.sqlite.org/cli.html#the_safe_command_line_option) und die [Dokumentation zum Laden von Erweiterungen](https://www.sqlite.org/loadext.html#loading_an_extension).

### Privilegierte Dateileser, die Daten an einen ausführlichen Client weitergeben

Ein benutzerdefinierter SUID/SGID-Wrapper kann den Zugriff auf einen vom Aufrufer gewählten Pfad prüfen und die Datei anschließend an einen anderen Befehl übergeben. Prüfen Sie die effektive Identität sowohl bei der Zugriffsprüfung als auch beim späteren Öffnen, lösen Sie alle `../`-Komponenten relativ zum tatsächlichen Basisverzeichnis auf und untersuchen Sie, wie der Kindprozess ungültige Eingaben behandelt. Wenn ein Datenbank-Client eine private Datei als SQL mit ausführlicher Ausgabe liest, kann er den Dateiinhalt in Fehlermeldungen wiederholen, obwohl das SQL ungültig ist. Eine Offenlegung über Benutzergrenzen hinweg liegt nur dann vor, wenn der Kindprozess eine Datei lesen kann, die der Aufrufer nicht lesen kann, der Aufrufer diese Datei über den Wrapper auswählen kann und die Ausgabe sichtbar ist; das bloße Vorhandensein von `mysql` oder einer anderen Client-Zeichenkette belegt keine dieser Bedingungen.

### Netdata-`ndsudo`-Suchpfad

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) betraf einige Netdata-`ndsudo`-Builds. Das root-eigene SUID-Hilfsprogramm suchte nach den zulässigen externen Befehlen mithilfe eines vom Aufrufer übergebenen `PATH`. Prüfen Sie ein installiertes Hilfsprogramm, auch wenn es außerhalb des üblichen `PATH` des Aufrufers liegt, aber nur, wenn das aktuelle Konto es ausführen kann. Bestätigen Sie den Eigentümer, das SUID-Bit, die Ausführungsrechte (einschließlich Gruppen-/ACL-Freigaben), den installierten Build und den Patch-Status des Herstellers sowie, ob `NoNewPrivs` oder ein `nosuid`-Mount die Identitätsänderung verhindert. Netdata nennt die gepatchten Builds `v1.45.3` und `v1.45.0-169`; Distributions-Backports müssen separat bestätigt werden. Eine Dashboard-Version oder das bloße Vorhandensein von `ndsudo` ist kein ausreichender Beleg für eine erreichbare Rechteausweitung. Das Pfadproblem setzt außerdem voraus, dass das Hilfsprogramm einen externen Befehl über einen vom Aufrufer kontrollierten Pfad auflöst.

### Privilegiengrenze bei Firejail `join`

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) betraf die privilegierte `--join`-Logik von Firejail: Ein manipulierter Join-Zielwert konnte das setuid-root-Hilfsprogramm dazu bringen, einen angreiferkontrollierten Mount-Namespace zu akzeptieren und unsichere Sicherheitszustände zu übernehmen. Prüfen Sie bei einer passiven Triage, ob die **aktuelle Identität ein root-eigenes setuid-Firejail-Programm ausführen kann**, ob setuid auf dessen Mount und im Prozesskontext wirksam ist und ob dem installierten Build die Fehlerbehebung fehlt. Upstream wurde das Problem in [Version 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) behoben; Distributionspakete können den Fix [zurückportieren](https://github.com/netblue30/firejail/issues/5191), während weiterhin eine ältere Version angezeigt wird. Diese Voraussetzungen begründen eine genauere Prüfung, nicht einen erfolgreichen Join oder eine Root-Shell. Erstellen Sie während der Bestandsaufnahme kein gefälschtes Jail und rufen Sie `--join` nicht auf.

### GNU Screen: Berechtigungen der Logdatei

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) betraf Screen 4.5.0, das eine vom Aufrufer gewählte Logdatei mit erhöhten Privilegien öffnete. Eine `screen`-Datei oder eine versionierte Variante im SUID-Bestand ist nur ein Prüfhinweis: Bestätigen Sie root als Eigentümer, die effektive SUID-Ausführung für den aktuellen Benutzer, den installierten Build, den Patch-Status der Distribution und das betroffene Verhalten bei Logdateien. [Debian hat sein 4.5.0-Paket durch einen Backport korrigiert](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484); ein Versionsstring oder Dateiname allein beweist daher keine Anfälligkeit. Erstellen Sie nicht routinemäßig eine Logdatei als Prüfsonde.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) betraf das privilegierte S-nail-Hilfsprogramm für Mail-Sperrdateien, wenn eine vom Aufrufer kontrollierte Pfadkomponente Verzeichnisdurchläufe erlaubte und zu einem beliebigen Dateischreibzugriff führen konnte. Prüfen Sie, ob der aktuelle Benutzer ein installiertes root-eigenes setuid-Hilfsprogramm ausführen kann, ob dessen setuid-Identität unter den Mount- und Prozessrichtlinien wirksam ist und welcher Paket-Build samt Hersteller-Fix installiert ist. [Ubuntus Sicherheitshinweis](https://ubuntu.com/security/notices/USN-4820-1) nennt einen zurückportierten Fix für das Paket unter 16.04; eine Version, die wie die Upstream-Version aussieht, ist daher nicht schlüssig. Das Vorhandensein des Hilfsprogramms beweist nicht, dass der betroffene Pfad erreichbar ist oder ein Dateischreibzugriff zur Ausführung als root führt. Prüfen Sie Metadaten und Paketstatus, ohne das Hilfsprogramm aufzurufen oder während der Bestandsaufnahme den Race auszunutzen.

### snap-confine und tmpfiles-Bereinigung

CVE-2026-3888 ist ein Race zwischen dem privilegierten `snap-confine` und der Bereinigung von `/tmp` durch systemd-tmpfiles. Bei einer passiven Prüfung können Sie feststellen, ob `snap-confine` setuid ist oder Dateikapazitäten besitzt, das installierte `snapd`-Paket mit der behobenen Version für das jeweilige **Ubuntu-Release** vergleichen und die wirksame Altersregel für `/tmp` sowie den Bereinigungstimer untersuchen. Ein passendes Paket und eine passende Regel sind Voraussetzungen, kein Beweis für die Erreichbarkeit des Race: Auch der Laufzeitstatus des Timers, das Snap-Layout, Paket-Backports und Regelüberschreibungen sind relevant. Ältere Releases benötigen möglicherweise eine nicht standardmäßige Konfiguration. Führen Sie bei einer routinemäßigen Bestandsaufnahme keine Race-Prüfung aus. Siehe den [Ubuntu-CVE-Eintrag](https://ubuntu.com/security/CVE-2026-3888) zum Paketstatus der einzelnen Releases und den [Qualys-Hinweis](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) zur Interaktion der Komponenten.

## ACLs und sensible Pfade prüfen

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ein beschreibbares übergeordnetes Verzeichnis kann das Ersetzen einer Datei ermöglichen, selbst wenn sie root gehört. Eine ACL kann unauffällig Zugriff auf eine sudoers-Ergänzungsdatei, eine Dienst-Unit, ein Cron-Skript, einen Bibliothekspfad oder eine Zugangsdaten-Datei gewähren. Prüfe sowohl die ACL als auch den vollständigen Pfad. Wenn beliebige privilegierte Dateischreibvorgänge möglich sind, folge [Beliebige Dateien für Root schreiben](write-to-root.md); Beispiele zur Linker-Konfiguration und zum Preloading findest du im [`ld.so`-Beispiel](ld.so.conf-example.md). Behandle offengelegte Backups, `.env`-Dateien, Datenbankkonfigurationen, SSH-Material und Verlauf als mögliche Quellen für Zugangsdaten. Der Zugriff darauf richtet sich nach den tatsächlichen Berechtigungen der jeweiligen Datei.
