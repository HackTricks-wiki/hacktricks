# SUID, SGID, ACLs και ευαίσθητα αρχεία

{{#include ../../banners/hacktricks-training.md}}

Τα SUID και SGID αλλάζουν την effective ταυτότητα ενός αρχείου που εκτελείται· τα ACLs μπορούν να παραχωρήσουν πρόσβαση που δεν εμφανίζουν τα συνηθισμένα mode bits του `ls -l`. Ελέγξτε και τα δύο όταν ένας χρήστης μπορεί να διαβάσει, να γράψει ή να εκτελέσει αρχεία πέρα από όσα υποδηλώνουν τα φαινομενικά δικαιώματα ιδιοκτήτη και ομάδας.

## Απαριθμήστε τα εκτελέσιμα με προνόμια

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Εστιάστε σε προσαρμοσμένα ή πρόσφατα τροποποιημένα εκτελέσιμα, ασυνήθιστους κατόχους και αρχεία σε εγγράψιμα προσαρτημένα συστήματα αρχείων. Ένα mount με `nosuid` μπορεί να καταστείλει τη συμπεριφορά set-ID· οι δυνατότητες αρχείων αποτελούν ξεχωριστό μηχανισμό προνομίων, που περιγράφεται στο [Linux capabilities](linux-capabilities.md). Συγκρίνετε ένα ύποπτο binary με το πακέτο του και ελέγξτε τι εκτελεί, ανοίγει ή φορτώνει με αυξημένη ταυτότητα.

Για ένα άγνωστο εκτελέσιμο SUID που ανήκει στον root και δέχεται είσοδο από τον καλούντα, εξετάστε offline ένα αντίγραφο του binary για μη ασφαλή διαχείριση ορισμάτων που μπορεί να προκαλέσει προβλήματα μνήμης και τη διαδρομή κώδικα που οδηγεί σε αυτήν. Καταγράψτε τη συμπεριφορά των effective IDs και τα μέτρα μετριασμού, όπως stack canaries, μη εκτελέσιμη μνήμη, position-independent code και address randomization. Ένα μη ασφαλές όνομα συνάρτησης ή η απουσία μέτρου μετριασμού είναι απλώς αφορμή για περαιτέρω έλεγχο: η δυνατότητα εκμετάλλευσης εξαρτάται από τα πραγματικά όρια εισόδου, τη διαδρομή ελέγχου που είναι προσβάσιμη και την effective identity τη στιγμή του σφάλματος. Μην στέλνετε μεγάλα ορίσματα στο ενεργό προνομιούχο εκτελέσιμο απλώς για να ελέγξετε αν θα καταρρεύσει κατά την παθητική απαρίθμηση.

Ένα οικείο πρόγραμμα SUID μπορεί να έχει αντικατασταθεί ή να έχει δεχτεί backdoor. Ένας πρόσφατος χρόνος τροποποίησης είναι ένδειξη, όχι απόδειξη: για ένα **συγκεκριμένο ύποπτο binary πακέτου**, εντοπίστε το πακέτο στο οποίο ανήκει και συγκρίνετε το εγκατεστημένο αρχείο με τα metadata του πακέτου, αντί να επαληθεύετε κάθε πακέτο κατά τη συνήθη απαρίθμηση:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` ελέγχει τα περιεχόμενα αρχείων μόνο όταν η βάση δεδομένων πακέτων έχει καταγεγραμμένο checksum· το RPM συγκρίνει επίσης metadata, όπως mode και ownership. Εστιάστε σε ασυμφωνία του ίδιου του **privileged executable**: εγκαταστάσεις stripped μπορεί να αναφέρουν ελλείπουσα τεκμηρίωση ή αρχεία locale αλλού στο ίδιο πακέτο. Συγκρίνετε ένα ύποπτο executable με ένα έμπιστο πακέτο του vendor και εξετάστε τον ακριβή κώδικα που άλλαξε. Νόμιμες τοπικές αλλαγές, απουσία checksums και παραβιασμένα metadata πακέτων περιορίζουν όσα αποδεικνύει οποιαδήποτε από τις δύο εντολές. Μην εκτελείτε ούτε το ύποπτο SUID πρόγραμμα ούτε script επαλήθευσης πακέτου στο πλαίσιο παθητικής διαλογής. Δείτε το [εγχειρίδιο επαλήθευσης dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) και το [εγχειρίδιο επαλήθευσης RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Ένα SUID πρόγραμμα που εκκινεί shell, σχετική εντολή ή library από εγγράψιμη διαδρομή μπορεί να διασχίσει όριο εμπιστοσύνης. Δείτε τα [SUID shared-library και linker abuse](suid-shared-library-and-linker-abuse.md), τις [οδηγίες για το PATH](../linux-basics/linux-environment-variables.md#path) και την [εξήγηση των user ID](../user-information/euid-ruid-suid.md). Για γνωστά command-specific escapes, ελέγξτε το [GTFOBins](https://gtfobins.github.io/) με βάση το ακριβές binary και την invocation που επιτρέπεται στον host.

Για ένα set-user-ID executable, διακρίνετε το **real UID** του caller από το **effective UID** του file owner: το [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) αφήνει το real UID αμετάβλητο και αντιγράφει το effective UID στο saved UID μετά από οποιαδήποτε αλλαγή set-ID. Η [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) εκτελεί την εντολή μέσω `/bin/sh -c`· το shell που επιλέγεται από αυτήν τη διαδρομή επηρεάζει το αν ένα child διατηρεί την effective identity του. Ειδικότερα, οι [κανόνες privileged-mode του Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) επαναφέρουν ένα διαφορετικό effective UID στο real UID όταν το Bash ξεκινά χωρίς `-p`. Ελέγξτε τις πραγματικές αλλαγές UID του helper και την invocation του child, καθώς και τον owner του, την πρόσβαση στο executable, τη ρύθμιση `nosuid` του mount και την κατάσταση `no_new_privs` της διεργασίας. Ένα SUID bit ή μια κλήση shell από μόνα τους δεν αποδεικνύουν ότι είναι εφικτή μετάβαση σε υψηλότερα privileges.

Ένα ασυνήθιστο root-owned SUID `jjs` αξίζει ξεχωριστό έλεγχο πρόσβασης σε αρχεία, αν ο τρέχων χρήστης μπορεί να το εκτελέσει. Το legacy εργαλείο Nashorn μπορεί να προσπελάσει Java file APIs ακόμη κι όταν ένα shell που εκκινείται απορρίπτει effective UID· επιβεβαιώστε τη συμπεριφορά της εγκατεστημένης JVM, την effective identity της λειτουργίας αρχείου και τις ρυθμίσεις `nosuid`/`no_new_privs` προτού το θεωρήσετε privileged read ή write. Η [Oracle αφαίρεσε το `jjs` στο JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)· μια εγκατεστημένη διαδρομή μπορεί να δείχνει σε παλαιότερο ή ξεχωριστά συσκευασμένο build. Το [GTFOBins τεκμηριώνει τα file APIs](https://gtfobins.org/gtfobins/jjs/), αλλά τα sudo παραδείγματά του δεν τεκμηριώνουν συμπεριφορά SUID για κάθε build. Μην εκτελείτε το εργαλείο κατά την παθητική απογραφή.

Ένα root-owned SUID executable `gosu`, προσβάσιμο σε χρήστη με χαμηλότερα privileges, αξίζει διερεύνηση: το τεκμηριωμένο interface του δέχεται χρήστη-στόχο και εντολή, αλλά η συνηθισμένη χρήση σε container το εκκινεί ως root για να απορρίψει privileges. Επαληθεύστε τη συμπεριφορά SUID του εγκατεστημένου build, την effective identity και το user-namespace mapping, καθώς και τα `nosuid` και `no_new_privs`· το root μέσα σε container δεν συνεπάγεται root στον host. Ένα filename ή SUID bit από μόνο του δεν αποδεικνύει λειτουργική μετάβαση. Δείτε την [upstream χρήση](https://github.com/tianon/gosu) και την [προειδοποίηση SUID του maintainer](https://github.com/tianon/gosu/issues/11). Μην εκτελείτε τον helper κατά την παθητική απογραφή.

Ένα custom set-user-ID backup wrapper μπορεί να δέχεται διαδρομή που επιλέγει ο caller και να την παρεμβάλλει σε εντολή αρχειοθέτησης που περνά στη `system(3)`. Αν η διαδρομή δεν περικλείεται σε εισαγωγικά στην εντολή που κατασκευάζεται, το child shell μπορεί να εφαρμόσει [tilde expansion μέσω του `HOME`, pathname patterns όπως `?` και `*`, καθώς και διαχωρισμό εντολών με newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)· η απόρριψη μόνο γνωστών σημείων στίξης με denylist δεν καθιστά τη διαδρομή literal. Επιβεβαιώστε την ακριβή ροή ορισμάτων, το inherited environment, το child shell και την effective identity, την πρόσβαση στο filesystem και το αν η έξοδος της αρχειοθέτησης είναι ορατή στον caller. Το SUID bit, ένα string εργαλείου αρχειοθέτησης ή η απόρριψη της literal διαδρομής `/root` από μόνα τους δεν αποδεικνύουν ούτε disclosure ούτε code execution. Εξετάστε offline ένα αντίγραφο του wrapper αντί να αρχειοθετήσετε ιδιωτικά αρχεία ή να στείλετε crash inputs κατά την παθητική απογραφή.

Η [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) του shell, όπως το `$(...)`, είναι ένα ακόμη πιθανό κενό σε denylist metacharacters: ακόμη και ένα σταθερό, επιτρεπόμενο command prefix μπορεί να περάσει μεταγενέστερο όρισμα που ελέγχει ο caller μέσω `/bin/sh -c`. Επαληθεύστε offline τα ακριβή εισαγωγικά, τον parser και την effective identity· μην θεωρείτε ένα string `system()` ή μια ελλιπή denylist από μόνα τους απόδειξη εκτέλεσης.

Σημασία έχει και το **δέντρο διεργασιών του caller**. Ένας web worker μπορεί να εγκαταστήσει seccomp filter που περιορίζει system calls αλλαγής UID· τα [seccomp filters κληρονομούνται από τα children και επιβιώνουν από `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Για παράδειγμα, οι οδηγίες [mpm-itk `LimitUIDRange` και `LimitGIDRange` του Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) μπορούν να περιορίσουν τις identities στις οποίες έχουν πρόσβαση οι απόγονοι. Το `Seccomp: 2` στο `/proc/self/status` δείχνει τη λειτουργία filter, όχι την πολιτική ή το αν ο συγκεκριμένος helper μπορεί να αποκτήσει την identity του owner του. Εξετάστε μαζί την ancestry της πραγματικής invocation και το effective filter, καθώς και τις συνθήκες SUID, mount και `no_new_privs`· μια ξεχωριστή login session μπορεί να έχει διαφορετική πολιτική, αλλά χρειάζεται δική της έγκυρη διαδρομή πρόσβασης.

Ένα custom SUID executable μπορεί να εκκινεί ξεχωριστό, αναγνώσιμο Python script. Αν χρησιμοποιεί πράγματι Python **2**, η [`input()` αξιολογεί την έκφραση που εισάγεται](https://docs.python.org/2/library/functions.html#input)· η `input()` της Python 3 επιστρέφει κείμενο. Επιβεβαιώστε την effective identity του wrapper, τη διαδρομή και την έκδοση του interpreter, τη διαδρομή του script και το αν μη έμπιστη είσοδος φτάνει σε αυτήν την κλήση προτού θεωρήσετε τη γραμμή του source path εκτέλεσης. Ένα set-ID bit μόνο στο script ή μια κλήση `input()` χωρίς privileged wrapper δεν τεκμηριώνουν το ίδιο όριο. Εξετάστε τις διαδρομές που αναφέρονται στο binary και ένα περιορισμένο αντίγραφο του script source χωρίς να το εκτελέσετε κατά την απογραφή.

Αν ασυνήθιστο SUID executable συνοδεύεται από αναγνώσιμο source, συγκρίνετε το πλήθος bytes που ζητά κάθε ανάγνωση αρχείου ελεγχόμενη από τον caller με το μέγεθος του destination buffer και εξετάστε τους επόμενους ελέγχους ροής εκτέλεσης. Η [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) αποθηκεύει τα ζητούμενα items στον pointer που της δίνεται· δεν γνωρίζει τη χωρητικότητα του destination object. Μια ασυμφωνία μεγέθους είναι ένδειξη για στατικό έλεγχο ασφάλειας μνήμης, όχι απόδειξη αξιοποιήσιμης privilege escalation: επιβεβαιώστε ότι το source αντιστοιχεί στο εγκατεστημένο binary, ότι ο caller μπορεί να δώσει το input, ότι η SUID εκτέλεση είναι effective σε αυτό το context και ότι η σχετική διαδρομή είναι προσβάσιμη. Εξετάστε offline ένα περιορισμένο αντίγραφο του source ή του binary αντί να στείλετε crash inputs στο privileged πρόγραμμα κατά την απογραφή.

Ένας custom SUID helper μπορεί να αποκαλύψει προστατευμένο αρχείο χωρίς να εμφανίσει τα περιεχόμενά του. Αν ο caller επιλέγει τόσο το pathname όσο και μια regular expression, και ο helper επιστρέφει ορατό πλήθος αντιστοιχιών με το effective UID του, anchored prefix tests μπορεί να λειτουργήσουν ως oracle χαρακτήρα προς χαρακτήρα. Επιβεβαιώστε τον owner του helper, τη συμπεριφορά effective-ID, την πρόσβαση στο executable, τους περιορισμούς pathname, τη σημασιολογία regex, την ορατότητα της απόκρισης και ένα συγκεκριμένο αρχείο με υψηλότερα privileges που ο caller δεν μπορεί διαφορετικά να διαβάσει. Ένα SUID bit ή ένα string βιβλιοθήκης regex από μόνο του δεν αποδεικνύει καμία από αυτές τις συνθήκες. Κατά την παθητική απογραφή, καταγράψτε το ασυνήθιστο executable και εξετάστε ένα περιορισμένο disassembly ή αντίγραφο του source· μην εκτελείτε επαναλαμβανόμενες δοκιμές στο live helper και μην εμφανίζετε ανακτημένα μυστικά.

Στο OpenBSD, ένας custom set-user-ID reader που δέχεται pathname επιλεγμένο από τον caller μπορεί να εκθέτει αρχεία στο `/var/backups`, αν η effective identity του έχει δικαίωμα ανάγνωσης και επιστρέφει τα περιεχόμενά τους στον caller. Το [`changelist(5)` του OpenBSD](https://man.openbsd.org/changelist.5) περιγράφει αντίγραφα `.current` και `.backup` των διαμορφωμένων διαδρομών, αλλά οι εγγραφές με πρόθεμα `+` αποθηκεύουν checksums SHA-256 αντί για περιεχόμενα αρχείων· ο κατάλογος backup θα πρέπει να ανήκει στον root και να έχει mode `0700`. Ένας κανόνας ανάγνωσης [`unveil` για το `/var`](https://man.openbsd.org/unveil.2) μπορεί να επιτρέψει πρόσβαση κάτω από αυτήν τη διαδρομή, αλλά από μόνος του δεν εκχωρεί ούτε αποδεικνύει πρόσβαση σε αρχεία. Επιβεβαιώστε το πραγματικό effective UID, το δικαίωμα εκτέλεσης του executable από τον τρέχοντα χρήστη, το αποδεκτό path, την ύπαρξη και τα περιεχόμενα του backup, καθώς και τυχόν ανεξάρτητες απαιτήσεις authentication προτού ισχυριστείτε escalation. Η παθητική απογραφή πρέπει να καταγράφει τον helper και τα metadata διαδρομών, όχι να εκτελεί τον reader ή να εμφανίζει δεδομένα backup.

Ένα custom SUID πρόγραμμα που ελέγχει pathname επιλεγμένο από τον caller με [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) και κατόπιν ανοίγει το pathname μπορεί να δεχτεί race με αλλαγή αρχείου ή symlink σε κατάλογο εγγράψιμο από τον caller. Ο έλεγχος αφορά το προηγούμενο object, ενώ ένα μεταγενέστερο [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) μπορεί να επιλύσει διαφορετικό object. Επιβεβαιώστε ότι ο helper είναι εκτελέσιμος με elevated effective identity, ότι μια κατά τα άλλα προσβάσιμη διαδρομή κώδικα διαβάζει το επιλεγμένο αρχείο και ότι ο caller μπορεί να αντικαταστήσει το pathname μεταξύ του ελέγχου και του ανοίγματος· SUID bit, εγγράψιμος κατάλογος ή string `stat` από μόνα τους δεν αποδεικνύουν τίποτε από αυτά. Για διαδρομή disclosure χρειάζεται επίσης ορατή έξοδος ή προορισμός αναγνώσιμος από τον caller. Εξετάστε offline το binary και τα metadata της διαδρομής· μην προκαλείτε race στον live helper κατά την παθητική απογραφή.

Εφαρμόστε τον ίδιο έλεγχο εξαρτήσεων και σε SGID wrappers. Ένα wrapper που εκτελεί shell ή helper μέσω απόλυτης διαδρομής μπορεί και πάλι να μην είναι ασφαλές, αν χρήστης με χαμηλότερα privileges μπορεί να αντικαταστήσει αυτό το αρχείο· ο κώδικας που εκκινείται μπορεί να κληρονομήσει το effective group του wrapper. Ελέγξτε την ακριβή διαδρομή που καλείται, τα δικαιώματα εγγραφής σε αυτήν (συμπεριλαμβανομένων των ACLs), το effective group του wrapper και το αν απορρίπτει privileges πριν εκκινήσει το child. Ένας interpreter μπορεί επίσης να απορρίψει inherited effective IDs, επομένως διακρίνετε ένα υποψήφιο για διερεύνηση από μια αποδεδειγμένη μετάβαση. Ένα εγγράψιμο shell κάπου αλλού στον host δεν αποδεικνύει από μόνο του ότι ένα privileged wrapper το καλεί.

### Privileged wrappers που περνούν SQL στο SQLite CLI

Αν ένα custom SUID πρόγραμμα περνά SQL ελεγχόμενο από τον χρήστη στο **πρόγραμμα γραμμής εντολών `sqlite3`**, εξετάστε την ακριβή εντολή και την effective identity προτού θεωρήσετε το query μόνο για ανάγνωση. Η SQL function `edit()` του CLI εκκινεί editor (από το δεύτερο όρισμά της ή το `VISUAL`), ενώ η SQL function `load_extension()` μπορεί να φορτώσει shared library όταν είναι ενεργοποιημένο το extension loading. Πρόκειται για πιθανά μονοπάτια code execution με την identity της διεργασίας CLI, ακόμη κι αν το wrapper ορίζει σταθερό `PATH` ή χρησιμοποιεί απόλυτη διαδρομή `sqlite3`. Το SQL πρέπει πράγματι να φτάσει σε αυτές τις functions και το CLI να διατηρεί τη σχετική λειτουργία· το να εντοπίσετε απλώς το `sqlite3` σε binary ή στον host δεν αποτελεί ένδειξη escalation. Η **library** του SQLite απενεργοποιεί από προεπιλογή το extension loading, επομένως διακρίνετέ την από το CLI. Αν μια privileged εφαρμογή πρέπει να επεξεργάζεται μη έμπιστο SQL, το `--safe` mode του SQLite CLI απενεργοποιεί τις `edit()`, `load_extension()` και άλλες functions με side effects. Δείτε την [τεκμηρίωση του SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), την [τεκμηρίωση safe mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) και την [τεκμηρίωση extension loading](https://www.sqlite.org/loadext.html#loading_an_extension).

### Privileged file readers που τροφοδοτούν verbose client

Ένα custom SUID/SGID wrapper μπορεί να ελέγχει την πρόσβαση σε pathname επιλεγμένο από τον caller και κατόπιν να περνά αυτό το αρχείο σε άλλη εντολή. Εξετάστε την effective identity τόσο κατά τον έλεγχο πρόσβασης όσο και κατά το μεταγενέστερο άνοιγμα, επιλύστε τυχόν στοιχεία `../` σε σχέση με τον πραγματικό βασικό κατάλογο και ελέγξτε πώς χειρίζεται το child μη έγκυρο input. Αν ένας database client διαβάζει ιδιωτικό αρχείο ως SQL με verbose output, μπορεί να εμφανίσει ξανά τα περιεχόμενα του αρχείου σε errors, παρότι το SQL είναι μη έγκυρο. Πρόκειται για disclosure μεταξύ χρηστών μόνο όταν το child μπορεί να διαβάσει αρχείο που ο caller δεν μπορεί, ο caller μπορεί να επιλέξει αυτό το αρχείο μέσω του wrapper και η έξοδος είναι ορατή· η παρουσία του `mysql` ή κάποιου άλλου client string από μόνη της δεν αποδεικνύει καμία από αυτές τις συνθήκες.

### Διαδρομή αναζήτησης του Netdata `ndsudo`

Το [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) επηρέασε ορισμένα builds του Netdata `ndsudo`. Ο root-owned SUID helper αναζητούσε τις επιτρεπόμενες εξωτερικές εντολές του χρησιμοποιώντας `PATH` που παρείχε ο caller. Εξετάστε εγκατεστημένο helper, ακόμη κι αν βρίσκεται έξω από το συνηθισμένο `PATH` του caller, μόνο όταν ο τρέχων λογαριασμός μπορεί να το εκτελέσει. Επιβεβαιώστε τον owner, το SUID bit, την πρόσβαση εκτέλεσης (συμπεριλαμβανομένων grants μέσω group/ACL), το εγκατεστημένο build και την κατάσταση των vendor patches, καθώς και το αν το `NoNewPrivs` ή ένα `nosuid` mount εμποδίζει την αλλαγή identity. Το Netdata αναφέρει τα διορθωμένα builds `v1.45.3` και `v1.45.0-169`· τα distribution backports χρειάζονται ξεχωριστή επιβεβαίωση. Η έκδοση του dashboard ή η απλή παρουσία του `ndsudo` δεν αρκεί ως ένδειξη προσβάσιμης escalation. Το ζήτημα της διαδρομής απαιτεί επίσης ο helper να επιλύει εξωτερική εντολή μέσω τοποθεσίας που ελέγχει ο caller.

### Όριο privilege του Firejail join

Το [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) επηρέασε την privileged λογική `--join` του Firejail: ένας ειδικά διαμορφωμένος στόχος join μπορούσε να κάνει τον setuid-root helper να δεχτεί mount namespace ελεγχόμενο από attacker και να αντιγράψει μη ασφαλή security state. Για παθητική διαλογή, επιβεβαιώστε ότι η **τρέχουσα identity μπορεί να εκτελέσει** root-owned setuid binary του Firejail, ότι το setuid είναι effective στο mount και στο process context και ότι το εγκατεστημένο build δεν έχει τη διόρθωση. Το upstream διόρθωσε το ζήτημα στην έκδοση [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70)· τα distribution packages μπορεί να έχουν [backport της διόρθωσης](https://github.com/netblue30/firejail/issues/5191) ενώ εξακολουθούν να εμφανίζουν παλαιότερη έκδοση. Αυτές οι προϋποθέσεις ορίζουν υποψήφιο για διερεύνηση, όχι επιτυχημένο join ή root shell. Μην κατασκευάζετε fake jail και μην εκτελείτε `--join` κατά την απογραφή.

### Δικαιώματα logfile του GNU Screen

Το [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) αφορούσε το Screen 4.5.0 που άνοιγε logfile επιλεγμένο από τον caller με elevated privileges. Ένα `screen` ή binary με επίθημα έκδοσης στην απογραφή SUID είναι απλώς ένδειξη για διερεύνηση: επιβεβαιώστε τον root ownership, την effective SUID εκτέλεση για τον τρέχοντα χρήστη, το εγκατεστημένο build και την κατάσταση των distribution patches, καθώς και την επηρεαζόμενη συμπεριφορά logfile. Το [Debian διόρθωσε το πακέτο 4.5.0 με backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), επομένως ένα version string ή filename από μόνο του δεν αποδεικνύει έκθεση. Μην δημιουργείτε logfile ως συνήθη έλεγχο κατά την απογραφή.

Το [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) επηρέασε τον privileged helper κλειδώματος αλληλογραφίας του S-nail, όταν ένα path component ελεγχόμενο από τον caller μπορούσε να διασχίσει καταλόγους και να οδηγήσει σε εγγραφή οποιουδήποτε αρχείου. Εξετάστε αν ο τρέχων χρήστης μπορεί να εκτελέσει εγκατεστημένο root-owned setuid helper, αν η setuid identity του είναι effective με βάση την πολιτική mount και διεργασίας, καθώς και το ακριβές package build και τη διόρθωση του vendor. Η [ενημέρωση ασφαλείας του Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) αναφέρει backported διόρθωση για το πακέτο 16.04, επομένως μια έκδοση που μοιάζει με upstream δεν αρκεί για συμπέρασμα. Η παρουσία του helper δεν αποδεικνύει ότι είναι προσβάσιμη η επηρεαζόμενη διαδρομή ή ότι μια εγγραφή αρχείου οδηγεί σε εκτέλεση ως root· εξετάστε τα metadata και την κατάσταση του πακέτου χωρίς να εκτελέσετε τον helper ή να επιχειρήσετε το race κατά την απογραφή.

### Εκκαθάριση snap-confine και tmpfiles

Το CVE-2026-3888 είναι race μεταξύ του privileged `snap-confine` και της εκκαθάρισης `/tmp` από το systemd-tmpfiles. Ένας παθητικός έλεγχος μπορεί να εξετάσει αν το `snap-confine` είναι setuid ή έχει file capabilities, να συγκρίνει το εγκατεστημένο πακέτο `snapd` με τη διορθωμένη έκδοση για εκείνη την **έκδοση του Ubuntu** και να ελέγξει τον ενεργό κανόνα ηλικίας του `/tmp` και τον timer εκκαθάρισης. Ένα πακέτο και ένας κανόνας που ταιριάζουν είναι προϋποθέσεις, όχι απόδειξη ότι το race είναι προσβάσιμο: έχουν επίσης σημασία η runtime κατάσταση του timer, το snap layout, τα package backports και οι παρακάμψεις κανόνων. Για παλαιότερες εκδόσεις μπορεί να απαιτείται μη προεπιλεγμένη διαμόρφωση. Μην εκτελείτε race probe κατά τη συνήθη απογραφή. Δείτε την [καταχώριση CVE του Ubuntu](https://ubuntu.com/security/CVE-2026-3888) για την κατάσταση πακέτων ανά έκδοση και το [advisory της Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) για την αλληλεπίδραση των components.

## Έλεγχος ACLs και ευαίσθητων διαδρομών

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ένας εγγράψιμος γονικός κατάλογος μπορεί να επιτρέψει την αντικατάσταση, ακόμη κι όταν το ίδιο το αρχείο ανήκει στον root. Ένα ACL μπορεί σιωπηρά να παραχωρεί πρόσβαση σε ένα αρχείο ρυθμίσεων sudoers, μια μονάδα υπηρεσίας, ένα script cron, μια διαδρομή βιβλιοθηκών ή ένα αρχείο διαπιστευτηρίων. Ελέγξτε τόσο το ACL όσο και ολόκληρη τη διαδρομή. Αν είναι δυνατή η αυθαίρετη εγγραφή σε προνομιούχα αρχεία, ακολουθήστε το [Arbitrary File Write to Root](write-to-root.md)· για περιπτώσεις ρύθμισης του linker και preload, δείτε το παράδειγμα [`ld.so`](ld.so.conf-example.md). Αντιμετωπίστε τα εκτεθειμένα αντίγραφα ασφαλείας, τα αρχεία `.env`, τις ρυθμίσεις βάσεων δεδομένων, το υλικό SSH και το ιστορικό ως πιθανές πηγές διαπιστευτηρίων, με την πρόσβαση να διέπεται από τα πραγματικά δικαιώματα κάθε αρχείου.
