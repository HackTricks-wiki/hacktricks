# SUID, SGID, ACLs, और संवेदनशील फ़ाइलें

{{#include ../../banners/hacktricks-training.md}}

SUID और SGID निष्पादित फ़ाइल की effective identity बदलते हैं; ACLs ऐसी access दे सकते हैं जो सामान्य `ls -l` mode bits में दिखाई नहीं देती। जब किसी user को apparent owner और group permissions से अधिक पढ़ने, लिखने या execute करने की access मिल सकती हो, तो दोनों की जाँच करें।

## Privileged executables की सूची बनाएँ

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

कस्टम या हाल ही में बदले गए executables, असामान्य owners और writable mounts पर मौजूद files पर ध्यान दें। `nosuid` mount set-ID व्यवहार को रोक सकता है; file capabilities एक अलग privilege mechanism हैं, जिसका वर्णन [Linux capabilities](linux-capabilities.md) में किया गया है। किसी संदिग्ध binary की उसके package से तुलना करें और जाँचें कि वह elevated identity के साथ क्या execute, open या load करती है।

ऐसे अपरिचित root-owned SUID executable के लिए, जो caller का input स्वीकार करता है, binary की एक copy को offline जाँचें कि argument handling memory-unsafe तो नहीं है और उस तक पहुँचने वाला code path क्या है। effective-ID व्यवहार और stack canaries, non-executable memory, position-independent code तथा address randomization जैसे mitigations दर्ज करें। किसी unsafe function का नाम या mitigation का न होना केवल आगे जाँच का संकेत है: exploitability वास्तविक input bounds, reachable control flow और fault के समय effective identity पर निर्भर करती है। Passive enumeration के दौरान crash जाँचने के लिए live privileged executable को लंबे arguments न भेजें।

किसी परिचित SUID program को भी बदला या backdoor किया जा सकता है। हाल का modification time जाँच का संकेत है, प्रमाण नहीं: किसी **विशिष्ट संदिग्ध packaged binary** के लिए उसका owning package पता करें और routine enumeration के दौरान हर package को verify करने के बजाय installed file की तुलना package metadata से करें:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` केवल उन्हीं फ़ाइलों की सामग्री जाँचता है जिनके checksum पैकेज डेटाबेस में दर्ज हैं; RPM mode और ownership जैसे metadata की भी तुलना करता है। **विशेषाधिकार-प्राप्त executable में ही** mismatch पर ध्यान दें: stripped installations में उसी पैकेज की अन्य जगहों पर मौजूद documentation या locale files के गायब होने की रिपोर्ट आ सकती है। संदिग्ध executable की तुलना किसी विश्वसनीय vendor package से करें और बदले गए सटीक code की समीक्षा करें। वैध स्थानीय बदलाव, अनुपस्थित checksums और compromised package metadata से इन commands द्वारा साबित की जा सकने वाली बातों की सीमा तय होती है। Passive triage के दौरान न तो संदिग्ध SUID program चलाएँ, न ही package verification script। [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) और [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) देखें।

जो SUID program किसी writable path से shell, relative command या library चलाता है, वह trust boundary पार कर सकता है। [SUID shared-library और linker abuse](suid-shared-library-and-linker-abuse.md), [PATH guidance](../linux-basics/linux-environment-variables.md#path) और [user-ID explanation](../user-information/euid-ruid-suid.md) देखें। ज्ञात command-specific escapes के लिए, host पर अनुमत सटीक binary और invocation को [GTFOBins](https://gtfobins.github.io/) पर जाँचें।

Set-user-ID executable के मामले में caller के **real UID** और file owner के **effective UID** में अंतर समझें: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) real UID को अपरिवर्तित रखता है और set-ID बदलाव के बाद effective UID को saved UID में कॉपी करता है। [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) अपना command `/bin/sh -c` के ज़रिए चलाता है; उस path से चुना गया shell तय करता है कि child अपनी effective identity बनाए रखेगा या नहीं। विशेष रूप से, [Bash privileged-mode rules](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) के अनुसार, जब Bash `-p` के बिना शुरू होता है और effective UID, real UID से अलग होता है, तो वह effective UID को real UID पर reset कर देता है। वास्तविक helper के UID changes और child invocation के साथ-साथ उसके owner, executable access, mount की `nosuid` setting और process की `no_new_privs` state जाँचें। केवल SUID bit या shell call से यह साबित नहीं होता कि ऊँचे privileges में बदलाव संभव है।

अगर मौजूदा user `jjs` चला सकता है, तो असामान्य root-owned SUID `jjs` की file-access अलग से जाँचें। Legacy Nashorn tool, spawned shell द्वारा effective UID drop किए जाने पर भी, Java file APIs का उपयोग कर सकता है; इसे privileged read या write मानने से पहले installed JVM का व्यवहार, file operation की effective identity और `nosuid`/`no_new_privs` की पुष्टि करें। [Oracle ने JDK 15 में `jjs` हटा दिया था](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); installed path पर अब भी कोई पुराना या अलग से packaged build हो सकता है। [GTFOBins file APIs का दस्तावेज़ देता है](https://gtfobins.org/gtfobins/jjs/), लेकिन उसके sudo examples हर build में SUID behavior साबित नहीं करते। Passive enumeration के दौरान यह tool न चलाएँ।

कम विशेषाधिकार वाले user के लिए उपलब्ध root-owned SUID `gosu` executable की समीक्षा करें: इसके दस्तावेज़ीकृत interface में target user और command दिए जा सकते हैं, लेकिन सामान्य container use में इसे root के रूप में शुरू करके privileges drop किए जाते हैं। Installed build का SUID behavior, effective identity और user-namespace mapping, तथा `nosuid` और `no_new_privs` जाँचें; container में root होने का अर्थ host पर root होना नहीं है। केवल filename या SUID bit से प्रभावी privilege transition साबित नहीं होता। [Upstream usage](https://github.com/tianon/gosu) और [maintainer की SUID warning](https://github.com/tianon/gosu/issues/11) देखें। Passive inventory के दौरान helper न चलाएँ।

Custom set-user-ID backup wrapper caller द्वारा चुना गया path स्वीकार करके उसे `system(3)` को दिए गए archive command में interpolate कर सकता है। अगर बने हुए command में path के चारों ओर quotes न हों, तो child shell [tilde expansion के लिए `HOME`, `?` और `*` जैसे pathname patterns, तथा newline से command separation](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) लागू कर सकता है; denylist में केवल जाने-पहचाने punctuation को रोकने से path literal नहीं बन जाता। सटीक argument flow, inherited environment, child shell और effective identity, filesystem access, तथा यह पुष्टि करें कि archive output caller को दिखता है या नहीं। SUID bit, archive-tool string या `/root` को literal रूप में रोकना—इनमें से कोई भी अपने-आप disclosure या code execution साबित नहीं करता। Passive enumeration के दौरान private files archive करने या crash inputs भेजने के बजाय wrapper की copy को offline जाँचें।

Shell [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html), जैसे `$(...)`, metacharacter denylist में एक और संभावित कमी है: एक fixed, अनुमत command prefix भी बाद में caller-controlled argument को `/bin/sh -c` के ज़रिए भेज सकता है। सटीक quoting, parser और effective identity को offline सत्यापित करें; केवल `system()` string या अधूरी denylist को execution का प्रमाण न मानें।

**Calling process tree** भी महत्वपूर्ण है। Web worker ऐसा seccomp filter लगा सकता है जो UID बदलने वाली system calls पर रोक लगाए; [seccomp filters children को मिलते हैं और `execve` के बाद भी बने रहते हैं](https://docs.kernel.org/userspace-api/seccomp_filter.html)। उदाहरण के लिए, Apache के [mpm-itk `LimitUIDRange` और `LimitGIDRange` directives](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) descendants के लिए उपलब्ध identities सीमित कर सकते हैं। `/proc/self/status` में `Seccomp: 2` filter mode दिखाता है, policy नहीं; न ही इससे पता चलता है कि यह विशेष helper अपने owner की identity हासिल कर सकता है या नहीं। वास्तविक invocation की ancestry और effective filter की समीक्षा उसकी SUID, mount और `no_new_privs` conditions के साथ करें; अलग login session में policy अलग हो सकती है, लेकिन उसके लिए भी अपना वैध access path ज़रूरी है।

Custom SUID executable कोई अलग, readable Python script चला सकता है। अगर वह वास्तव में Python **2** इस्तेमाल करता है, तो [`input()` दी गई expression का मूल्यांकन करता है](https://docs.python.org/2/library/functions.html#input); Python 3 में `input()` text लौटाता है। Source line को execution path मानने से पहले wrapper की effective identity, interpreter path और version, script path, तथा यह पुष्टि करें कि untrusted input उस call तक पहुँचता है या नहीं। Script पर set-ID bit होना या privileged wrapper के बिना `input()` call मौजूद होना, उसी boundary को साबित नहीं करता। Enumeration के दौरान चलाने के बजाय binary के referenced paths और सीमित script source की समीक्षा करें।

अगर किसी असामान्य SUID executable के साथ readable source मौजूद है, तो caller-controlled हर file read में माँगे गए byte count की destination buffer size से तुलना करें और बाद के control-flow checks देखें। [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) दिए गए pointer पर माँगे गए items लिखता है; उसे destination object की capacity का पता नहीं होता। Size mismatch, static memory-safety की जाँच का संकेत है—यह उपयोगी privilege escalation का प्रमाण नहीं। पुष्टि करें कि source installed binary से मेल खाता है, caller input दे सकता है, उस context में SUID execution प्रभावी है और संबंधित path तक पहुँचना संभव है। Enumeration के दौरान privileged program को crash inputs भेजने के बजाय, सीमित source या binary copy को offline जाँचें।

Custom SUID helper, protected file की सामग्री दिखाए बिना उसका खुलासा कर सकता है। अगर caller pathname और regular expression दोनों चुन सकता है, और helper अपनी effective UID के तहत दिखाई देने वाली match count लौटाता है, तो anchored prefix tests character-by-character oracle बन सकते हैं। Helper का owner, effective-ID behavior, executable access, pathname restrictions, regex semantics, response visibility और ऐसी विशिष्ट उच्च-विशेषाधिकार वाली file की पुष्टि करें जिसे caller अन्यथा पढ़ नहीं सकता। SUID bit या regex library string अकेले इस flow का कोई हिस्सा साबित नहीं करते। Passive enumeration के दौरान असामान्य executable का रिकॉर्ड रखें और सीमित disassembly या source copy की समीक्षा करें; live helper पर बार-बार guesses न चलाएँ और recovered secrets न छापें।

OpenBSD पर, caller द्वारा चुना गया pathname स्वीकार करने वाला custom set-user-ID reader, `/var/backups` की files उजागर कर सकता है—अगर उसकी effective identity उन्हें पढ़ सकती है और वह सामग्री caller को लौटाता है। [OpenBSD का `changelist(5)`](https://man.openbsd.org/changelist.5) configured paths की `.current` और `.backup` copies का वर्णन करता है, लेकिन `+` से शुरू होने वाली entries में file contents के बजाय SHA-256 checksums होते हैं; backup directory का owner root होना चाहिए और mode `0700` होना चाहिए। `/var` के लिए helper का [`unveil` read rule](https://man.openbsd.org/unveil.2) उस path के नीचे access की अनुमति दे सकता है, लेकिन यह अपने-आप file access नहीं देता और न ही उसे साबित करता है। Escalation का दावा करने से पहले actual effective UID, मौजूदा user के लिए executable permission, स्वीकार किया गया path, backup का मौजूद होना और उसकी सामग्री, तथा कोई अलग authentication requirement जाँचें। Passive enumeration में helper और path metadata रिपोर्ट करें; reader न चलाएँ और backup data न छापें।

Custom SUID program अगर caller द्वारा चुने गए pathname पर [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) जाँच करके बाद में उस pathname को खोलता है, तो caller-writable directory में file या symlink बदलकर race कर सकता है। जाँच पहले वाले object पर लागू होती है, जबकि बाद का [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) कोई दूसरा object resolve कर सकता है। पुष्टि करें कि elevated effective identity के साथ helper चलाया जा सकता है, किसी अन्यथा reachable code path में चुनी गई file पढ़ी जाती है, और caller check तथा open के बीच pathname बदल सकता है; केवल SUID bit, writable directory या `stat` string इनमें से कुछ भी साबित नहीं करती। Disclosure path के लिए visible output या caller-readable destination भी आवश्यक है। Binary और path metadata को offline जाँचें; passive enumeration के दौरान live helper को race न करें।

SGID wrappers पर भी यही dependency review लागू करें। Absolute path से shell या helper चलाने वाला wrapper तब भी असुरक्षित हो सकता है, अगर कम विशेषाधिकार वाला user उस file को बदल सकता है; spawned code को wrapper का effective group मिल सकता है। सटीक invoked path, उसकी write access (ACLs सहित), wrapper का effective group और child चलाने से पहले privileges drop होते हैं या नहीं—जाँचें। Interpreter inherited effective IDs को भी discard कर सकता है, इसलिए review candidate और साबित transition में अंतर करें। Host पर कहीं और writable shell मौजूद होना, अपने-आप यह साबित नहीं करता कि privileged wrapper उसे चलाता है।

### Privileged wrappers जो SQL को SQLite CLI तक पहुँचाते हैं

अगर कोई custom SUID program user-controlled SQL को **`sqlite3` command-line program** तक पहुँचाता है, तो query को read-only मानने से पहले सटीक command और effective identity जाँचें। CLI का `edit()` SQL function एक editor चलाता है (दूसरा argument या `VISUAL` से), और उसका SQL `load_extension()` function shared library लोड कर सकता है, बशर्ते extension loading enabled हो। Wrapper द्वारा `PATH` तय कर देने या absolute `sqlite3` path इस्तेमाल करने पर भी ये CLI process की identity के तहत संभावित code-execution paths हैं। SQL का वास्तव में उन functions तक पहुँचना और CLI में संबंधित feature का उपलब्ध रहना ज़रूरी है; केवल binary या host पर `sqlite3` मिलना escalation का प्रमाण नहीं। SQLite **library** में extension loading default रूप से disabled होती है, इसलिए उसे CLI से अलग समझें। जहाँ privileged application को untrusted SQL process करना हो, वहाँ SQLite का CLI `--safe` mode `edit()`, `load_extension()` और अन्य side-effectful functions को disabled करता है। [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option) और [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension) देखें।

### Privileged file readers जो verbose client को input देते हैं

Custom SUID/SGID wrapper caller द्वारा चुने गए pathname पर access जाँच सकता है और फिर उस file को किसी अन्य command तक पहुँचा सकता है। Access check और बाद के open—दोनों समय की effective identity जाँचें, वास्तविक base directory के सापेक्ष `../` components resolve करें, और देखें कि child invalid input को कैसे संभालता है। अगर database client किसी private file को SQL के रूप में पढ़े और verbose output दे, तो SQL अमान्य होने पर भी errors में file की सामग्री echo हो सकती है। यह cross-user disclosure तभी है जब child ऐसी file पढ़ सके जिसे caller नहीं पढ़ सकता, caller wrapper के ज़रिए वह file चुन सके, और output दिखाई दे; केवल `mysql` या किसी अन्य client की string मौजूद होना इनमें से कोई शर्त साबित नहीं करता।

### Netdata `ndsudo` search path

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ने कुछ Netdata `ndsudo` builds को प्रभावित किया था। Root-owned SUID helper, अनुमत external commands खोजने के लिए caller द्वारा दिया गया `PATH` इस्तेमाल करता था। Installed helper की समीक्षा करें—उस helper की भी जो caller के सामान्य `PATH` से बाहर हो—लेकिन केवल तभी जब मौजूदा account उसे चला सकता हो। उसका owner, SUID bit, executable access (group/ACL grants सहित), installed build और vendor patch status जाँचें; साथ ही यह भी कि `NoNewPrivs` या `nosuid` mount identity change रोकता है या नहीं। Netdata ने patched builds `v1.45.3` और `v1.45.0-169` सूचीबद्ध किए हैं; distribution backports की अलग से पुष्टि करनी होगी। Dashboard version या केवल `ndsudo` की मौजूदगी, reachable escalation का पर्याप्त प्रमाण नहीं है। Path issue के लिए यह भी ज़रूरी है कि helper किसी ऐसी location से external command resolve करे जिस पर caller का नियंत्रण हो।

### Firejail join privilege boundary

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ने Firejail के privileged `--join` logic को प्रभावित किया था: crafted join target से setuid-root helper attacker-controlled mount namespace स्वीकार कर सकता था और असुरक्षित security state कॉपी कर सकता था। Passive triage में पुष्टि करें कि **मौजूदा identity root-owned setuid Firejail binary चला सकती है**, उसके mount और process context में setuid प्रभावी है, और installed build में fix नहीं है। Upstream ने issue [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) में ठीक किया; distribution packages [backport कर सकते हैं](https://github.com/netblue30/firejail/issues/5191), जबकि version पुराना दिखता रहे। ये prerequisites केवल समीक्षा योग्य candidate की पहचान करते हैं, सफल join या root shell साबित नहीं करते। Enumeration के दौरान fake jail न बनाएँ और `--join` न चलाएँ।

### GNU Screen logfile permissions

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) में Screen 4.5.0 ने caller द्वारा चुने गए logfile को elevated privileges के साथ खोला था। SUID inventory में `screen` या version-suffixed binary केवल समीक्षा का संकेत है: root ownership, मौजूदा user के लिए प्रभावी SUID execution, installed build और distribution patch status, तथा प्रभावित logfile behavior की पुष्टि करें। [Debian ने backport के साथ अपना 4.5.0 package ठीक किया था](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), इसलिए केवल version string या filename exposure साबित नहीं करता। Routine enumeration के लिए logfile न बनाएँ।

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ने privileged S-nail mail-lock helper को प्रभावित किया था, जब caller-controlled path component directories के पार जाकर arbitrary file write तक पहुँच सकता था। जाँचें कि मौजूदा user installed root-owned setuid helper चला सकता है या नहीं, mount और process policy के तहत उसकी setuid identity प्रभावी है या नहीं, और package build तथा vendor fix क्या हैं। [Ubuntu की security notice](https://ubuntu.com/security/notices/USN-4820-1) में उसके 16.04 package के लिए backported fix सूचीबद्ध है, इसलिए upstream जैसा दिखने वाला version निर्णायक नहीं है। Helper की मौजूदगी से यह साबित नहीं होता कि प्रभावित path reachable है या file write से root execution मिलेगा; enumeration के दौरान helper चलाए या race करने की कोशिश किए बिना metadata और package status जाँचें।

### snap-confine और tmpfiles cleanup

CVE-2026-3888, privileged `snap-confine` और systemd-tmpfiles द्वारा `/tmp` cleanup के बीच race से जुड़ा है। Passive review में जाँचें कि `snap-confine` setuid है या उसके पास file capabilities हैं, installed `snapd` package की तुलना उस **Ubuntu release** के लिए fixed version से करें, और प्रभावी `/tmp` age rule तथा cleanup timer देखें। मेल खाता package और rule prerequisites हैं, race के reachable होने का प्रमाण नहीं: runtime timer state, snap layout, package backports और rule overrides भी मायने रखते हैं। पुराने releases में non-default configuration की ज़रूरत हो सकती है। Routine enumeration के दौरान race probe न चलाएँ। Release-specific package status के लिए [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) और component interaction के लिए [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) देखें।

## ACLs और sensitive paths की जाँच करें

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

लिखने योग्य parent directory, फ़ाइल के root-owned होने पर भी उसे बदलने की अनुमति दे सकती है। कोई ACL चुपचाप sudoers drop-in, service unit, cron script, library path या credential file तक पहुँच दे सकती है। ACL और पूरा path, दोनों जाँचें। अगर मनमाने privileged file writes संभव हों, तो [Arbitrary File Write to Root](write-to-root.md) देखें; linker configuration और preload के मामलों के लिए [`ld.so` example](ld.so.conf-example.md) देखें। उजागर backups, `.env` files, database configs, SSH material और history को संभावित credential sources मानें; उन तक पहुँच हर फ़ाइल की वास्तविक permissions से नियंत्रित होती है।
