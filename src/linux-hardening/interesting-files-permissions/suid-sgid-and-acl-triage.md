# SUID、SGID、ACL、および機密ファイル

{{#include ../../banners/hacktricks-training.md}}

SUID と SGID は、実行されるファイルの実効 ID を変更します。ACL は、通常の `ls -l` のモードビットには表示されないアクセス権を付与できます。見かけ上の所有者とグループの権限よりも多くの読み取り、書き込み、または実行権限をユーザーが持つ場合は、両方を確認してください。

## 特権付き実行ファイルを列挙する

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

カスタムまたは最近変更された実行ファイル、通常とは異なる所有者、書き込み可能なマウント上のファイルに注目します。`nosuid` マウントでは set-ID の動作が無効化されることがあります。file capabilities は別の権限メカニズムであり、[Linux capabilities](linux-capabilities.md) で説明しています。不審なバイナリをパッケージ内のものと比較し、昇格した ID で何を実行、オープン、またはロードするかを確認します。

呼び出し元からの入力を受け取る、見慣れない root 所有の SUID 実行ファイルについては、バイナリのコピーをオフラインで調べ、メモリ安全性に問題のある引数処理と、その処理に到達するコードパスを確認します。実効 ID の動作と、stack canaries、実行不可メモリ、位置独立コード、アドレスランダム化などの緩和策を記録します。危険な関数名や緩和策の欠如は、調査の手がかりにすぎません。悪用可能性は、実際の入力境界、到達可能な制御フロー、障害発生時の実効 ID に左右されます。受動的な列挙中に、クラッシュを試す目的だけで、稼働中の特権実行ファイルに長い引数を渡してはいけません。

見慣れた SUID プログラムも、置き換えられたりバックドアを仕込まれたりすることがあります。更新日時が新しいことは調査の手がかりであり、証拠ではありません。**特定の不審なパッケージ管理対象バイナリ**については、通常の列挙中にすべてのパッケージを検証するのではなく、所有パッケージを特定し、インストール済みファイルをパッケージメタデータと比較します。

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` は、パッケージデータベースに記録されたチェックサムがあるファイルについてのみ内容を検査します。RPM はモードや所有者などのメタデータも比較します。**特権実行ファイル自体**の不一致を重視してください。strip されたインストールでは、同じパッケージ内の別の場所にあるドキュメントやロケールファイルが見つからないと報告されることがあります。不審な実行ファイルを信頼できるベンダーパッケージと比較し、変更されたコードを正確に確認してください。正当なローカル変更、チェックサムの欠落、侵害されたパッケージメタデータがあると、どちらのコマンドで証明できることにも限界があります。受動的なトリアージの一環として、不審な SUID プログラムもパッケージ検証スクリプトも実行しないでください。[dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) と [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) を参照してください。

シェル、相対パスで指定されたコマンド、または書き込み可能なパスにあるライブラリを呼び出す SUID プログラムは、信頼境界を越える可能性があります。[SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md)、[PATH のガイダンス](../linux-basics/linux-environment-variables.md#path)、[ユーザー ID の説明](../user-information/euid-ruid-suid.md)を参照してください。コマンド固有の既知のエスケープについては、ホストで許可されている正確なバイナリと呼び出し方を [GTFOBins](https://gtfobins.github.io/) で確認してください。

set-user-ID 実行ファイルでは、呼び出し元の**実 UID**とファイル所有者の**実効 UID**を区別してください。[`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) は実 UID を変更せず、set-ID による変更後の実効 UID を保存 UID にコピーします。[`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) は `/bin/sh -c` 経由でコマンドを実行します。このパスで選択されるシェルによって、子プロセスが実効 ID を保持するかどうかが変わります。特に、[Bash の privileged mode の規則](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)では、`-p` なしで Bash を起動すると、実効 UID が実 UID と異なる場合に実効 UID が実 UID にリセットされます。実際のヘルパーによる UID の変更と子プロセスの呼び出し方に加え、所有者、実行アクセス、マウントの `nosuid` 設定、プロセスの `no_new_privs` 状態も確認してください。SUID ビットやシェル呼び出しだけでは、より高い権限への移行が可能とは証明できません。

通常と異なる root 所有の SUID `jjs` があり、現在のユーザーが実行できる場合は、別途ファイルアクセスを確認してください。旧式の Nashorn ツールは、起動したシェルの実効 UID が降格されても Java のファイル API にアクセスできます。特権的な読み取りまたは書き込みと判断する前に、インストール済み JVM の挙動、ファイル操作時の実効 ID、`nosuid` / `no_new_privs` を確認してください。[Oracle は JDK 15 で `jjs` を削除しました](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)。インストール済みのパスに、古いビルドや別途パッケージされたビルドが残っている可能性があります。[GTFOBins はファイル API を説明しています](https://gtfobins.org/gtfobins/jjs/)。ただし、sudo の例は、すべてのビルドで SUID の挙動が同じことを示すものではありません。受動的な列挙中にこのツールを起動しないでください。

低権限ユーザーが実行できる root 所有の SUID `gosu` 実行ファイルがあれば、確認が必要です。文書化されたインターフェースでは対象ユーザーとコマンドを指定できますが、通常のコンテナ利用では root として起動し、権限を降格させます。権限移行が可能と判断する前に、インストール済みビルドの SUID 挙動、実効 ID と user namespace のマッピング、`nosuid`、`no_new_privs` を確認してください。コンテナ内の root は、ホストの root を意味しません。ファイル名や SUID ビットだけでは、権限移行が機能する証拠になりません。[upstream の使用方法](https://github.com/tianon/gosu)と[メンテナーによる SUID の警告](https://github.com/tianon/gosu/issues/11)を参照してください。受動的なインベントリ作成中にこのヘルパーを起動しないでください。

カスタムの set-user-ID バックアップラッパーが、呼び出し元の指定したパスを受け取り、それを `system(3)` に渡すアーカイブコマンドへ埋め込むことがあります。構築されたコマンド内でパスが引用符で囲まれていない場合、子シェルは [ `HOME` を使ったチルダ展開、`?` や `*` などのパス名パターン、改行によるコマンド区切り](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)を適用できます。よくある句読記号だけを拒否する denylist では、パスをリテラルとして扱える保証はありません。正確な引数の流れ、継承される環境、子シェルと実効 ID、ファイルシステムへのアクセス、アーカイブ出力が呼び出し元から見えるかを確認してください。SUID ビット、アーカイブツールを示す文字列、または `/root` という文字列を拒否するだけでは、情報開示もコード実行も証明できません。受動的な列挙中に非公開ファイルをアーカイブしたり、クラッシュを起こす入力を送信したりせず、ラッパーのコピーをオフラインで確認してください。

`$(...)` などのシェル[コマンド置換](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)も、メタ文字 denylist の抜け穴になり得ます。許可されたコマンドの接頭辞が固定でも、後続の呼び出し元制御の引数が `/bin/sh -c` に渡される場合があります。正確な引用符処理、パーサー、実効 ID をオフラインで確認してください。`system()` に渡される文字列や不完全な denylist だけを、実行の証拠とみなさないでください。

**呼び出し元プロセスのツリー**も重要です。Web worker が UID 変更のシステムコールを制限する seccomp フィルターを設定することがあります。[seccomp フィルターは子プロセスに引き継がれ、`execve` 後も存続します](https://docs.kernel.org/userspace-api/seccomp_filter.html)。たとえば、Apache の [mpm-itk `LimitUIDRange` および `LimitGIDRange` ディレクティブ](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/)は、子孫プロセスが到達できる ID を制限できます。`/proc/self/status` の `Seccomp: 2` はフィルターモードを示すだけで、ポリシーや、このヘルパーが所有者の ID を取得できるかどうかは示しません。実際の呼び出しの祖先と実効フィルターを、SUID、マウント、`no_new_privs` の条件と合わせて確認してください。別のログインセッションでは異なるポリシーが適用される場合がありますが、そのセッションには独自の有効なアクセス経路が必要です。

カスタム SUID 実行ファイルが、別の読み取り可能な Python スクリプトを実行することがあります。実際に Python **2** を使っている場合、[`input()` は入力された式を評価します](https://docs.python.org/2/library/functions.html#input)。Python 3 の `input()` はテキストを返します。このソース行を実行経路とみなす前に、ラッパーの実効 ID、インタープリターのパスとバージョン、スクリプトのパス、信頼できない入力がその呼び出しに渡るかを確認してください。スクリプト自体に set-ID ビットがあることや、特権ラッパーなしで `input()` を呼び出すことは、同じ境界の成立を意味しません。列挙中に実行せず、バイナリが参照するパスと、範囲を限定したスクリプトのソースを確認してください。

通常と異なる SUID 実行ファイルに読み取り可能なソースが付属している場合は、呼び出し元が指定できるファイル読み取りの要求バイト数を宛先バッファーのサイズと比較し、その後の制御フローのチェックも調べてください。[`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) は指定されたポインターに要求された項目を書き込みますが、宛先オブジェクトの容量は把握していません。サイズの不一致は静的なメモリー安全性の調査材料であり、利用可能な権限昇格の証拠ではありません。ソースがインストール済みバイナリと一致すること、呼び出し元が入力を指定できること、その状況で SUID 実行が有効であること、該当する経路に到達できることを確認してください。列挙中に特権プログラムへクラッシュを起こす入力を送らず、範囲を限定したソースまたはバイナリのコピーをオフラインで確認してください。

カスタム SUID ヘルパーは、内容を表示せずに保護されたファイルの情報を開示することがあります。呼び出し元がパス名と正規表現の両方を選択でき、ヘルパーが実効 UID のもとで一致件数を返す場合、接頭辞にアンカーを付けた検査を使って一文字ずつ調べるオラクルを構成できる可能性があります。権限昇格と判断する前に、ヘルパーの所有者、実効 ID の挙動、実行アクセス、パス名の制限、正規表現の意味、応答が見えるか、呼び出し元が他の方法では読めない具体的な高権限ファイルがあるかを確認してください。SUID ビットや正規表現ライブラリを示す文字列だけでは、この流れのどれも証明できません。受動的な列挙中は、通常と異なる実行ファイルを記録し、範囲を限定した逆アセンブルまたはソースのコピーを確認してください。稼働中のヘルパーに推測を繰り返し送ったり、復元した秘密を表示したりしないでください。

OpenBSD では、呼び出し元がパス名を指定できるカスタム set-user-ID リーダーは、実効 ID で `/var/backups` 内のファイルを読み取れ、その内容を呼び出し元に返す場合、それらのファイルを露出させる可能性があります。[OpenBSD の `changelist(5)`](https://man.openbsd.org/changelist.5) では、設定されたパスの `.current` および `.backup` コピーについて説明されています。ただし、`+` を先頭に付けたエントリーにはファイルの内容ではなく SHA-256 チェックサムが保存されます。バックアップディレクトリは root 所有、モード `0700` にすべきです。`/var` に対するヘルパーの [`unveil` 読み取りルール](https://man.openbsd.org/unveil.2)はそのパス以下へのアクセスを許可できますが、それだけでファイルへのアクセスが可能であることを付与したり証明したりはしません。権限昇格と主張する前に、実際の実効 UID、現在のユーザーの実行権限、受け付けるパス、バックアップの存在と内容、独立した認証要件の有無を確認してください。受動的な列挙では、ヘルパーとパスのメタデータを報告し、リーダーを起動したりバックアップデータを表示したりしないでください。

呼び出し元が指定したパス名を [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) で検査し、その後に開くカスタム SUID プログラムでは、呼び出し元が書き込み可能なディレクトリ内のファイルまたはシンボリックリンクを変更することで競合状態が生じる可能性があります。検査対象は先に確認したオブジェクトですが、後続の [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) では別のオブジェクトが解決される場合があります。特権的な実効 ID でヘルパーを実行できること、到達可能なコードパスが選択したファイルを読み取ること、呼び出し元が検査とオープンの間にパス名を差し替えられることを確認してください。SUID ビット、書き込み可能なディレクトリ、`stat` を示す文字列だけでは、これらのどれも証明できません。情報開示経路には、出力が見えること、または呼び出し元が読める宛先があることも必要です。稼働中のヘルパーで競合を試さず、バイナリとパスのメタデータをオフラインで確認してください。

同じ依存関係の確認を SGID ラッパーにも適用してください。シェルまたはヘルパーを絶対パスで実行するラッパーでも、低権限ユーザーがそのファイルを置き換えられるなら安全とは限りません。起動されたコードがラッパーの実効グループを継承する可能性があります。実際に呼び出されるパス、ACL を含む書き込み権限、ラッパーの実効グループ、子プロセスの起動前に権限を破棄するかを確認してください。インタープリターが継承した実効 ID を破棄する場合もあるため、調査候補と実証済みの権限移行を区別してください。ホスト上の別の場所に書き込み可能なシェルがあるだけでは、特権ラッパーがそれを呼び出す証拠になりません。

### SQLite CLI に SQL を渡す特権ラッパー

カスタム SUID プログラムがユーザー制御の SQL を **`sqlite3` コマンドラインプログラム**に渡す場合、クエリを読み取り専用とみなす前に、正確なコマンドと実効 ID を確認してください。CLI の `edit()` SQL 関数はエディター（第 2 引数または `VISUAL` で指定）を起動します。また、SQL の `load_extension()` 関数は、拡張の読み込みが有効な場合に共有ライブラリを読み込めます。ラッパーが `PATH` を固定したり、`sqlite3` の絶対パスを使用したりしていても、CLI プロセスの ID でコード実行できる可能性があります。SQL が実際にこれらの関数に渡され、CLI が該当機能を保持している必要があります。バイナリやホスト内に `sqlite3` が見つかっただけでは、権限昇格の証拠になりません。SQLite **ライブラリ**では拡張読み込みがデフォルトで無効になっているため、CLI と区別してください。特権アプリケーションで信頼できない SQL を処理する必要がある場合、SQLite の CLI `--safe` モードでは `edit()`、`load_extension()`、その他の副作用を伴う関数が無効になります。[SQLite CLI のドキュメント](https://www.sqlite.org/cli.html#the_edit_sql_function)、[safe mode のドキュメント](https://www.sqlite.org/cli.html#the_safe_command_line_option)、[拡張読み込みのドキュメント](https://www.sqlite.org/loadext.html#loading_an_extension)を参照してください。

### 詳細な出力を行うクライアントにファイルを渡す特権リーダー

カスタム SUID/SGID ラッパーは、呼び出し元が指定したパス名へのアクセスを検査してから、そのファイルを別のコマンドに渡すことがあります。アクセス検査時と後続のオープン時の実効 ID を確認し、`../` の構成要素を実際の基底ディレクトリに照らして解決し、子プロセスが無効な入力をどう扱うかを調べてください。データベースクライアントが非公開ファイルを SQL として読み込み、詳細な出力を行う場合、SQL が無効でもエラーにファイルの内容を出力することがあります。これがユーザー間の情報開示となるのは、子プロセスが呼び出し元には読めないファイルを読み取れ、呼び出し元がラッパー経由でそのファイルを指定でき、出力が見える場合に限られます。`mysql` や別のクライアントを示す文字列があるだけでは、これらの条件を証明できません。

### Netdata `ndsudo` の検索パス

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) は、Netdata `ndsudo` の一部のビルドに影響しました。root 所有の SUID ヘルパーは、呼び出し元が指定した `PATH` を使って、許可された外部コマンドを検索していました。現在のアカウントが実行できる場合に限り、通常の `PATH` 外にあるものも含め、インストール済みヘルパーを確認してください。所有者、SUID ビット、実行アクセス（グループや ACL による許可を含む）、インストール済みビルドとベンダーの修正状況、`NoNewPrivs` または `nosuid` マウントが ID 変更を阻止するかを確認してください。Netdata は修正済みビルドとして `v1.45.3` と `v1.45.0-169` を挙げています。ディストリビューションによるバックポートは個別に確認が必要です。ダッシュボードのバージョン表示や `ndsudo` の存在だけでは、到達可能な権限昇格の証拠になりません。このパスの問題が成立するには、ヘルパーが呼び出し元の制御下にある場所から外部コマンドを解決する必要もあります。

### Firejail の join における権限境界

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) は、Firejail の特権付き `--join` 処理に影響しました。細工された join 対象により、setuid-root ヘルパーが攻撃者制御の mount namespace を受け入れ、安全でないセキュリティ状態をコピーする可能性がありました。受動的なトリアージでは、**現在の ID で実行できる** root 所有の setuid Firejail バイナリがあること、マウント上およびプロセスのコンテキストで setuid が有効であること、インストール済みビルドに修正がないことを確認してください。upstream は [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) で修正しました。ディストリビューションのパッケージでは、古いバージョンを表示したまま[修正をバックポート](https://github.com/netblue30/firejail/issues/5191)している場合があります。これらの前提条件が示すのは調査候補であり、join の成功や root シェルではありません。列挙中に偽の jail を作成したり `--join` を実行したりしないでください。

### GNU Screen のログファイル権限

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) は、Screen 4.5.0 が呼び出し元指定のログファイルを特権付きで開く問題でした。SUID インベントリ内の `screen` またはバージョン付きのバイナリは、調査の手掛かりにすぎません。root 所有であること、現在のユーザーに対して実効的な SUID 実行ができること、インストール済みビルドとディストリビューションの修正状況、影響を受けるログファイルの挙動を確認してください。[Debian は 4.5.0 パッケージにバックポート修正を適用しました](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484)。そのため、バージョン文字列やファイル名だけでは脆弱性の有無を証明できません。通常の列挙プローブとしてログファイルを作成しないでください。

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) は、呼び出し元制御のパス構成要素がディレクトリをたどり、任意のファイル書き込みにつながる可能性がある場合の、特権付き S-nail mail-lock ヘルパーに影響しました。現在のユーザーがインストール済みの root 所有 setuid ヘルパーを実行できるか、マウントとプロセスポリシーのもとで setuid の ID が有効か、正確なパッケージビルドとベンダー修正を確認してください。[Ubuntu のセキュリティ通知](https://ubuntu.com/security/notices/USN-4820-1)には、16.04 パッケージ向けのバックポート修正が記載されています。そのため、upstream 版に見えるバージョンだけでは判断できません。ヘルパーが存在するだけでは、影響を受けるパスに到達できることや、ファイル書き込みが root でのコード実行につながることは証明できません。列挙中にヘルパーを起動したり競合を試みたりせず、メタデータとパッケージの状態を確認してください。

### snap-confine と tmpfiles のクリーンアップ

CVE-2026-3888 は、特権付き `snap-confine` と systemd-tmpfiles による `/tmp` のクリーンアップが関係する競合状態です。受動的な確認では、`snap-confine` が setuid かファイルケーパビリティを持つかを調べ、インストール済みの `snapd` パッケージを**該当する Ubuntu リリース**の修正版と比較し、`/tmp` の実効的な経過時間ルールとクリーンアップタイマーを確認できます。該当するパッケージとルールは前提条件であり、競合状態に到達できる証拠ではありません。実行時のタイマー状態、snap の構成、パッケージのバックポート、ルールの上書きも関係します。古いリリースでは、デフォルト以外の設定が必要な場合があります。通常の列挙中に競合を試すプローブを実行しないでください。リリースごとのパッケージ状況は [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888)、コンポーネント間の相互作用は [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root)を参照してください。

## ACL と機密パスを調べる**

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

書き込み可能な親ディレクトリがあれば、ファイル自体が root 所有でも置き換えられる場合があります。ACL によって、sudoers の drop-in、service unit、cron script、library path、credential file へのアクセスがひそかに許可されていることもあります。ACL とパス全体の両方を確認してください。特権で任意のファイルに書き込める場合は、[Arbitrary File Write to Root](write-to-root.md) を参照してください。linker の設定や preload のケースについては、[`ld.so` example](ld.so.conf-example.md) を参照してください。公開されているバックアップ、`.env` ファイル、データベース設定、SSH 関連のファイル、履歴は、credential の入手元となる可能性があります。アクセス可否は、各ファイルの実際の権限に従います。
