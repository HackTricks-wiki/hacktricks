# SUID, SGID, ACLs et fichiers sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID et SGID modifient l’identité effective d’un fichier exécuté ; les ACLs peuvent accorder des accès que les bits de mode ordinaires affichés par `ls -l` ne montrent pas. Examinez les deux lorsqu’un utilisateur peut lire, écrire ou exécuter des fichiers au-delà de ce que semblent indiquer les permissions du propriétaire et du groupe.

## Énumérer les exécutables privilégiés

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrez-vous sur les exécutables personnalisés ou récemment modifiés, les propriétaires inhabituels et les fichiers situés sur des montages accessibles en écriture. Un montage `nosuid` peut neutraliser le comportement set-ID ; les capacités de fichier constituent un mécanisme de privilèges distinct, décrit dans [Linux capabilities](linux-capabilities.md). Comparez un binaire suspect à son paquet et vérifiez ce qu’il exécute, ouvre ou charge avec une identité élevée.

Pour un exécutable SUID appartenant à root et inconnu qui accepte des entrées de l’appelant, examinez hors ligne une copie du binaire afin de repérer la gestion des arguments non sûre pour la mémoire et le chemin de code qui y mène. Consignez le comportement des identifiants effectifs ainsi que les mesures d’atténuation, comme les canaris de pile, la mémoire non exécutable, le code indépendant de la position et la randomisation des adresses. Un nom de fonction dangereux ou l’absence d’une mesure d’atténuation constitue uniquement une piste à examiner : l’exploitabilité dépend des limites réelles des entrées, du flux de contrôle accessible et de l’identité effective au moment de la faute. N’envoyez pas de longs arguments à l’exécutable privilégié en production dans le seul but de provoquer un crash lors d’une énumération passive.

Un programme SUID connu peut lui-même avoir été remplacé ou doté d’une porte dérobée. Une date de modification récente est une piste, pas une preuve : pour un **binaire empaqueté suspect précis**, identifiez son paquet propriétaire et comparez le fichier installé aux métadonnées du paquet, plutôt que de vérifier chaque paquet lors d’une énumération de routine :

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` vérifie le contenu des fichiers uniquement lorsque la base de données des paquets contient une somme de contrôle enregistrée ; RPM compare également les métadonnées, comme les permissions et le propriétaire. Concentrez-vous sur une divergence concernant **l’exécutable privilégié lui-même** : les installations allégées peuvent signaler l’absence de documentation ou de fichiers de langue situés ailleurs dans le même paquet. Comparez l’exécutable suspect à un paquet fournisseur de confiance et examinez précisément le code modifié. Les modifications locales légitimes, l’absence de sommes de contrôle et une base de données des paquets compromise limitent la portée des preuves fournies par ces commandes. N’exécutez ni le programme SUID suspect ni un script de vérification de paquet lors d’un triage passif. Consultez le [manuel de vérification de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) et le [manuel de vérification de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programme SUID qui lance un shell, une commande relative ou une bibliothèque depuis un chemin accessible en écriture peut franchir une frontière de confiance. Consultez [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), les [consignes relatives à PATH](../linux-basics/linux-environment-variables.md#path) et l’[explication des identifiants utilisateur](../user-information/euid-ruid-suid.md). Pour les échappées connues propres à une commande, vérifiez [GTFOBins](https://gtfobins.github.io/) en tenant compte du binaire exact et de l’invocation autorisée sur l’hôte.

Pour un exécutable set-user-ID, distinguez l’**UID réel** de l’appelant de l’**UID effectif** du propriétaire du fichier : [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) laisse l’UID réel inchangé et copie l’UID effectif dans l’UID sauvegardé après tout changement set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) exécute sa commande via `/bin/sh -c` ; le shell sélectionné par ce chemin détermine si un processus enfant conserve son identité effective. En particulier, les [règles du mode privilégié de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) réinitialisent l’UID effectif à l’UID réel si ceux-ci diffèrent et si Bash démarre sans `-p`. Vérifiez les changements d’UID réels de l’utilitaire et son lancement de processus enfants, ainsi que son propriétaire, ses permissions d’exécution, l’option de montage `nosuid` et l’état `no_new_privs` du processus. Un bit SUID ou un appel de shell ne suffit pas à établir qu’une transition vers des privilèges supérieurs est possible.

Un `jjs` inhabituel appartenant à root et doté du bit SUID justifie un examen distinct de l’accès aux fichiers si l’utilisateur courant peut l’exécuter. L’outil Nashorn historique peut accéder aux API de fichiers Java même lorsqu’un shell lancé abandonne son UID effectif ; vérifiez le comportement de la JVM installée, l’identité effective lors de l’opération sur le fichier, ainsi que `nosuid` et `no_new_privs` avant de conclure à une lecture ou écriture privilégiée. [Oracle a supprimé `jjs` dans JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html) ; un chemin installé peut encore correspondre à une ancienne version ou à une build distribuée séparément. [GTFOBins décrit les API de fichiers](https://gtfobins.org/gtfobins/jjs/), mais ses exemples sudo ne démontrent pas le comportement SUID de toutes les builds. N’invoquez pas l’outil pendant l’énumération passive.

Un exécutable `gosu` appartenant à root, doté du bit SUID et accessible à un utilisateur moins privilégié mérite un examen : son interface documentée accepte un utilisateur cible et une commande, mais son usage normal en conteneur consiste à le lancer en tant que root pour abandonner les privilèges. Vérifiez le comportement SUID de la build installée, l’identité effective et le mappage des espaces de noms utilisateur, ainsi que `nosuid` et `no_new_privs` ; root dans un conteneur ne signifie pas root sur l’hôte. Un nom de fichier ou un bit SUID ne prouve pas à lui seul qu’une transition fonctionne. Consultez l’[utilisation en amont](https://github.com/tianon/gosu) et l’[avertissement SUID du mainteneur](https://github.com/tianon/gosu/issues/11). N’invoquez pas l’utilitaire pendant l’inventaire passif.

Un wrapper de sauvegarde set-user-ID personnalisé peut accepter un chemin choisi par l’appelant et l’insérer dans une commande d’archivage transmise à `system(3)`. Si ce chemin n’est pas entre guillemets dans la commande construite, le shell enfant peut appliquer [l’expansion du tilde avec `HOME`, les motifs de chemin comme `?` et `*`, ainsi que la séparation des commandes par saut de ligne](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) ; rejeter uniquement des signes de ponctuation courants à l’aide d’une liste de refus ne rend pas le chemin littéral. Vérifiez le cheminement exact des arguments, l’environnement hérité, le shell enfant et son identité effective, l’accès au système de fichiers et la visibilité de la sortie de l’outil d’archivage pour l’appelant. Le bit SUID, une chaîne correspondant à un outil d’archivage ou le seul rejet du chemin littéral `/root` ne prouvent ni divulgation ni exécution de code. Examinez une copie du wrapper hors ligne plutôt que d’archiver des fichiers privés ou d’envoyer des entrées provoquant un crash pendant l’énumération passive.

La [substitution de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) du shell, par exemple `$(...)`, constitue une autre faille possible dans une liste de refus de métacaractères : même un préfixe de commande autorisé fixe peut transmettre un argument ultérieur contrôlé par l’appelant à `/bin/sh -c`. Vérifiez hors ligne les guillemets exacts, l’analyseur et l’identité effective ; une chaîne `system()` ou une liste de refus incomplète ne prouve pas à elle seule une exécution.

L’**arbre des processus appelants** compte également. Un processus worker web peut installer un filtre seccomp qui restreint les appels système modifiant les UID ; [les filtres seccomp sont transmis aux processus enfants et persistent après `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Par exemple, les directives [`LimitUIDRange` et `LimitGIDRange` de mpm-itk pour Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) peuvent limiter les identités accessibles aux descendants. `Seccomp: 2` dans `/proc/self/status` indique le mode du filtre, pas sa politique ni si cet utilitaire précis peut obtenir l’identité de son propriétaire. Examinez ensemble l’ascendance de l’invocation réelle, le filtre effectif, ainsi que les conditions liées au SUID, au montage et à `no_new_privs` ; une session de connexion distincte peut avoir une autre politique, mais nécessite son propre chemin d’accès valide.

Un exécutable SUID personnalisé peut lancer un script Python distinct et lisible. S’il utilise réellement Python **2**, [`input()` évalue l’expression saisie](https://docs.python.org/2/library/functions.html#input) ; avec Python 3, `input()` renvoie du texte. Vérifiez l’identité effective du wrapper, le chemin et la version de l’interpréteur, le chemin du script et si une entrée non fiable parvient à cet appel avant de considérer cette ligne source comme un chemin d’exécution. Un bit set-ID sur le script seul ou un appel à `input()` sans wrapper privilégié n’établit pas la même frontière. Examinez les chemins référencés par le binaire et une portion limitée du code source du script sans l’exécuter pendant l’énumération.

Si un code source lisible accompagne un exécutable SUID inhabituel, comparez le nombre d’octets demandé pour chaque lecture de fichier contrôlable par l’appelant à la taille du tampon de destination, puis examinez les vérifications de flux de contrôle ultérieures. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) stocke les éléments demandés à l’adresse fournie ; elle ne connaît pas la capacité de l’objet de destination. Une divergence de taille est une piste statique de problème de sûreté mémoire, pas la preuve d’une élévation de privilèges exploitable : confirmez que la source correspond au binaire installé, que l’appelant peut fournir l’entrée, que l’exécution SUID est effective dans ce contexte et que le chemin concerné est atteignable. Examinez hors ligne une copie limitée du code source ou du binaire plutôt que d’envoyer des entrées provoquant un crash au programme privilégié pendant l’énumération.

Un utilitaire SUID personnalisé peut divulguer un fichier protégé sans en afficher le contenu. Si l’appelant choisit à la fois un chemin et une expression régulière, et que l’utilitaire renvoie un nombre de correspondances visible sous son UID effectif, des tests de préfixe ancrés peuvent servir d’oracle caractère par caractère. Vérifiez le propriétaire de l’utilitaire, le comportement de son ID effectif, les permissions d’exécution, les restrictions de chemin, la sémantique des expressions régulières, la visibilité de la réponse et l’existence d’un fichier précis, plus privilégié, que l’appelant ne peut pas lire autrement. Un bit SUID ou une chaîne correspondant à une bibliothèque regex ne prouve aucun de ces éléments. Lors de l’énumération passive, consignez l’exécutable inhabituel et examinez une copie limitée du désassemblage ou du code source ; ne lancez pas de suppositions répétées contre l’utilitaire actif et n’affichez pas les secrets récupérés.

Sur OpenBSD, un lecteur set-user-ID personnalisé qui accepte un chemin choisi par l’appelant peut exposer des fichiers de `/var/backups` si son identité effective peut les lire et qu’il renvoie leur contenu à l’appelant. [`changelist(5)` d’OpenBSD](https://man.openbsd.org/changelist.5) décrit les copies `.current` et `.backup` des chemins configurés, mais les entrées préfixées par `+` stockent des sommes de contrôle SHA-256 plutôt que le contenu des fichiers ; le répertoire de sauvegarde devrait appartenir à root et avoir le mode `0700`. Une règle de lecture [`unveil` de l’utilitaire](https://man.openbsd.org/unveil.2) pour `/var` peut autoriser l’accès sous ce chemin, mais n’accorde ni ne prouve à elle seule l’accès aux fichiers. Avant de conclure à une élévation, vérifiez l’UID effectif réel, les permissions d’exécution de l’utilisateur courant, le chemin accepté, l’existence et le contenu de la sauvegarde, ainsi que toute exigence d’authentification indépendante. L’énumération passive doit signaler l’utilitaire et les métadonnées du chemin, sans invoquer le lecteur ni afficher les données de sauvegarde.

Un programme SUID personnalisé qui vérifie un chemin choisi par l’appelant avec [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), puis ouvre ce chemin plus tard, peut subir une course si un fichier ou un lien symbolique change dans un répertoire accessible en écriture à l’appelant. La vérification porte sur l’objet antérieur, tandis qu’un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ultérieur peut en résoudre un autre. Vérifiez que l’utilitaire est exécutable avec une identité effective élevée, qu’un chemin de code autrement atteignable lit le fichier choisi et que l’appelant peut remplacer le chemin entre la vérification et l’ouverture ; un bit SUID, un répertoire accessible en écriture ou une chaîne `stat` ne suffisent pas à établir ces faits. Une sortie visible ou une destination lisible par l’appelant est également nécessaire pour qu’il y ait divulgation. Examinez hors ligne le binaire et les métadonnées du chemin ; ne tentez pas de provoquer une course contre l’utilitaire actif pendant l’énumération passive.

Appliquez le même examen des dépendances aux wrappers SGID. Un wrapper qui lance un shell ou un utilitaire par chemin absolu peut tout de même être vulnérable si un utilisateur moins privilégié peut remplacer ce fichier ; le code lancé peut hériter du groupe effectif du wrapper. Vérifiez le chemin exact invoqué, ses permissions d’écriture (y compris les ACL), le groupe effectif du wrapper et s’il abandonne ses privilèges avant de lancer le processus enfant. Un interpréteur peut également abandonner les ID effectifs hérités ; distinguez donc une piste à examiner d’une transition démontrée. La présence d’un shell accessible en écriture ailleurs sur l’hôte ne prouve pas à elle seule qu’un wrapper privilégié l’appelle.

### Wrappers privilégiés transmettant du SQL à la CLI SQLite

Si un programme SUID personnalisé transmet du SQL contrôlé par l’utilisateur au **programme en ligne de commande `sqlite3`**, examinez la commande exacte et l’identité effective avant de considérer la requête comme étant en lecture seule. La fonction SQL `edit()` de la CLI lance un éditeur (indiqué comme deuxième argument ou par `VISUAL`), et sa fonction SQL `load_extension()` peut charger une bibliothèque partagée lorsque le chargement d’extensions est activé. Ces fonctions peuvent permettre l’exécution de code avec l’identité du processus CLI, même si le wrapper fixe `PATH` ou utilise un chemin absolu vers `sqlite3`. Le SQL doit effectivement parvenir à ces fonctions et la CLI doit conserver la fonctionnalité correspondante ; la simple présence de `sqlite3` dans un binaire ou sur l’hôte ne prouve pas une élévation. La **bibliothèque** SQLite désactive le chargement d’extensions par défaut : distinguez-la de la CLI. Si une application privilégiée doit traiter du SQL non fiable, le mode `--safe` de la CLI SQLite désactive `edit()`, `load_extension()` et d’autres fonctions à effets de bord. Consultez la [documentation de la CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentation du mode sécurisé](https://www.sqlite.org/cli.html#the_safe_command_line_option) et la [documentation sur le chargement d’extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lecteurs de fichiers privilégiés transmettant les données à un client verbeux

Un wrapper SUID/SGID personnalisé peut vérifier l’accès à un chemin choisi par l’appelant, puis transmettre ce fichier à une autre commande. Examinez l’identité effective lors de la vérification d’accès et de l’ouverture ultérieure, résolvez tout composant `../` par rapport au véritable répertoire de base et inspectez le traitement des entrées invalides par le processus enfant. Si un client de base de données lit un fichier privé comme du SQL avec une sortie détaillée, il peut répercuter le contenu du fichier dans les erreurs, même si le SQL est invalide. Il n’y a divulgation entre utilisateurs que si le processus enfant peut lire un fichier auquel l’appelant n’a pas accès, si l’appelant peut sélectionner ce fichier via le wrapper et si la sortie est visible ; la simple présence de `mysql` ou d’une chaîne correspondant à un autre client ne prouve aucune de ces conditions.

### Chemin de recherche de Netdata `ndsudo`

La [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) concernait certaines builds de Netdata `ndsudo`. L’utilitaire SUID appartenant à root recherchait les commandes externes autorisées à l’aide d’un `PATH` fourni par l’appelant. N’examinez un utilitaire installé — y compris s’il se trouve hors du `PATH` habituel de l’appelant — que si le compte courant peut l’exécuter. Vérifiez son propriétaire, son bit SUID, les permissions d’exécution (y compris les droits accordés par le groupe ou les ACL), la build installée et les correctifs du fournisseur, ainsi que le blocage éventuel du changement d’identité par `NoNewPrivs` ou un montage `nosuid`. Netdata répertorie les builds corrigées `v1.45.3` et `v1.45.0-169` ; les rétroportages des distributions doivent être vérifiés séparément. La version affichée dans un tableau de bord ou la simple présence de `ndsudo` ne suffit pas à prouver qu’une élévation est atteignable. Le problème de chemin nécessite également que l’utilitaire résolve une commande externe dans un emplacement contrôlé par l’appelant.

### Frontière de privilèges de Firejail join

La [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) concernait la logique privilégiée `--join` de Firejail : une cible join fabriquée pouvait amener l’utilitaire setuid-root à accepter un espace de noms de montage contrôlé par un attaquant et à copier un état de sécurité non sûr. Pour un triage passif, confirmez que **l’identité courante peut exécuter** un binaire Firejail appartenant à root et setuid, que le setuid est effectif sur son montage et dans son contexte de processus, et que la build installée ne contient pas le correctif. Le projet en amont a corrigé le problème dans la [version 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) ; les paquets des distributions peuvent [rétroporter le correctif](https://github.com/netblue30/firejail/issues/5191) tout en affichant une version plus ancienne. Ces prérequis désignent une piste à examiner, pas la réussite d’un join ni l’obtention d’un shell root. Ne créez pas de faux jail et n’invoquez pas `--join` pendant l’énumération.

### Permissions des fichiers journaux de GNU Screen

La [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) concernait Screen 4.5.0, qui ouvrait avec des privilèges élevés un fichier journal choisi par l’appelant. Un binaire `screen` ou portant un suffixe de version dans l’inventaire SUID n’est qu’une piste à examiner : vérifiez qu’il appartient à root, que l’exécution SUID est effective pour l’utilisateur courant, la build installée et les correctifs de la distribution, ainsi que le comportement concerné avec les fichiers journaux. [Debian a corrigé son paquet 4.5.0 par rétroportage](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484) ; une chaîne de version ou un nom de fichier ne prouve donc pas à lui seul l’exposition. Ne créez pas de fichier journal comme sonde d’énumération habituelle.

La [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) concernait l’utilitaire privilégié de verrouillage de courrier S-nail, lorsqu’un composant de chemin contrôlé par l’appelant pouvait traverser des répertoires et entraîner une écriture arbitraire dans un fichier. Vérifiez si l’utilisateur courant peut exécuter un utilitaire setuid appartenant à root, si son identité setuid est effective au regard de la politique du montage et du processus, ainsi que la build exacte du paquet et le correctif du fournisseur. L’[avis de sécurité d’Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) répertorie un correctif rétroporté pour son paquet 16.04 ; une version qui semble correspondre à celle en amont ne permet donc pas de conclure. La présence de l’utilitaire ne prouve pas que le chemin concerné est atteignable ni qu’une écriture de fichier permet d’exécuter du code en tant que root ; examinez les métadonnées et l’état du paquet sans invoquer l’utilitaire ni tenter la course pendant l’énumération.

### Nettoyage de snap-confine et tmpfiles

La CVE-2026-3888 est une course impliquant `snap-confine` privilégié et le nettoyage de `/tmp` par systemd-tmpfiles. Un examen passif peut vérifier si `snap-confine` est setuid ou possède des capacités de fichier, comparer le paquet `snapd` installé à la version corrigée pour cette **version d’Ubuntu** et examiner la règle d’ancienneté effective de `/tmp` ainsi que le minuteur de nettoyage. Un paquet et une règle correspondants sont des prérequis, pas la preuve que la course est atteignable : l’état d’exécution du minuteur, la disposition de snap, les rétroportages des paquets et les surcharges de règles comptent également. Les anciennes versions peuvent nécessiter une configuration non définie par défaut. Ne lancez pas de sonde de course lors de l’énumération habituelle. Consultez la [fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2026-3888) pour l’état des paquets selon la version et l’[avis de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) pour l’interaction entre les composants.

## Examiner les ACL et les chemins sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un répertoire parent accessible en écriture peut permettre le remplacement d’un fichier, même si celui-ci appartient à root. Une ACL peut accorder discrètement l’accès à un fichier de configuration sudoers, une unité de service, un script cron, un chemin de bibliothèque ou un fichier d’identifiants. Vérifiez à la fois l’ACL et le chemin complet. Si des écritures arbitraires dans des fichiers privilégiés sont possibles, suivez [Arbitrary File Write to Root](write-to-root.md) ; pour les cas de configuration de l’éditeur de liens et de preload, consultez l’[`ld.so` example](ld.so.conf-example.md). Considérez les sauvegardes exposées, les fichiers `.env`, les configurations de base de données, les éléments SSH et l’historique comme des sources possibles d’identifiants ; l’accès dépend des permissions réelles de chaque fichier.
