# SUID, SGID, ACLs y archivos sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID y SGID cambian la identidad efectiva con la que se ejecuta un archivo; las ACL pueden conceder acceso que no se muestra en los bits de permisos habituales de `ls -l`. Revisa ambos cuando un usuario pueda leer, escribir o ejecutar más de lo que sugieren los permisos aparentes del propietario y del grupo.

## Enumerar ejecutables privilegiados

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Céntrate en ejecutables personalizados o modificados recientemente, propietarios inusuales y archivos en montajes con permisos de escritura. Un montaje `nosuid` puede suprimir el comportamiento set-ID; las capacidades de archivo son un mecanismo de privilegios independiente que se describe en [Linux capabilities](linux-capabilities.md). Compara un binario sospechoso con el de su paquete y comprueba qué ejecuta, abre o carga con identidad elevada.

Si un ejecutable SUID desconocido y propiedad de root acepta datos del usuario, revisa una copia del binario sin conexión para detectar un manejo de argumentos inseguro para la memoria y la ruta de código que llega a él. Registra el comportamiento de los ID efectivos y las mitigaciones, como los stack canaries, la memoria no ejecutable, el código independiente de posición y la aleatorización de direcciones. Un nombre de función insegura o la ausencia de una mitigación solo indican qué conviene revisar: la posibilidad de explotación depende de los límites reales de entrada, el flujo de control alcanzable y la identidad efectiva en el momento del fallo. Durante una enumeración pasiva, no envíes argumentos largos al ejecutable privilegiado activo solo para probar si se bloquea.

Un programa SUID conocido también puede haber sido reemplazado o modificado con una puerta trasera. Una fecha de modificación reciente es una pista, no una prueba: para un **binario empaquetado sospechoso específico**, averigua qué paquete lo contiene y compara el archivo instalado con los metadatos del paquete, en lugar de verificar todos los paquetes durante la enumeración rutinaria:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` comprueba el contenido de los archivos solo cuando la base de datos de paquetes tiene una suma de comprobación registrada; RPM también compara metadatos, como el modo y la propiedad. Céntrate en las discrepancias del **propio ejecutable privilegiado**: las instalaciones recortadas pueden indicar que faltan archivos de documentación o de localización en otras partes del mismo paquete. Compara el ejecutable sospechoso con un paquete de proveedor confiable y revisa exactamente qué código ha cambiado. Los cambios locales legítimos, la ausencia de sumas de comprobación y los metadatos de paquetes comprometidos limitan lo que cualquiera de los dos comandos puede demostrar. No ejecutes el programa SUID sospechoso ni un script de verificación de paquetes como parte de una clasificación pasiva. Consulta el [manual de verificación de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) y el [manual de verificación de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programa SUID que invoque un shell, un comando relativo o una biblioteca desde una ruta con permisos de escritura puede cruzar un límite de confianza. Consulta [abuso de bibliotecas compartidas y del enlazador con SUID](suid-shared-library-and-linker-abuse.md), las [recomendaciones sobre PATH](../linux-basics/linux-environment-variables.md#path) y la [explicación de los ID de usuario](../user-information/euid-ruid-suid.md). Para escapes conocidos específicos de comandos, consulta [GTFOBins](https://gtfobins.github.io/) según el binario exacto y la invocación permitida en el host.

En un ejecutable set-user-ID, distingue el **UID real** del proceso que lo invoca del **UID efectivo** del propietario del archivo: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) deja el UID real sin cambios y copia el UID efectivo al UID guardado después de cualquier cambio de set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) ejecuta su comando mediante `/bin/sh -c`; el shell seleccionado por esa ruta determina si un proceso hijo conserva su identidad efectiva. En particular, las [reglas del modo privilegiado de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) restablecen un UID efectivo distinto al UID real cuando Bash se inicia sin `-p`. Comprueba los cambios de UID reales del helper y cómo invoca los procesos hijos, además de su propietario, los permisos de ejecución, la opción de montaje `nosuid` y el estado `no_new_privs` del proceso. Un bit SUID o una llamada al shell, por sí solos, no demuestran que se pueda realizar una transición a privilegios superiores.

Un `jjs` inusual propiedad de root y con SUID merece una revisión independiente del acceso a archivos si el usuario actual puede ejecutarlo. La herramienta heredada Nashorn puede acceder a las API de archivos de Java incluso cuando un shell hijo descarta un UID efectivo; confirma el comportamiento de la JVM instalada, la identidad efectiva de la operación con archivos y las opciones `nosuid`/`no_new_privs` antes de considerarlo una lectura o escritura privilegiada. [Oracle eliminó `jjs` en JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); una ruta instalada aún puede corresponder a una versión anterior o a una compilación empaquetada por separado. [GTFOBins documenta las API de archivos](https://gtfobins.org/gtfobins/jjs/), pero sus ejemplos de sudo no demuestran el comportamiento SUID en todas las compilaciones. No invoques la herramienta durante la enumeración pasiva.

Un ejecutable `gosu` propiedad de root, con SUID y accesible para un usuario con menos privilegios, merece revisión: su interfaz documentada acepta un usuario de destino y un comando, pero su uso habitual en contenedores lo ejecuta como root para reducir privilegios. Verifica el comportamiento SUID de la compilación instalada, la identidad efectiva y la asignación de espacios de nombres de usuario, además de `nosuid` y `no_new_privs`; ser root dentro de un contenedor no implica serlo en el host. El nombre del archivo o el bit SUID, por sí solos, no demuestran que la transición funcione. Consulta el [uso en el proyecto upstream](https://github.com/tianon/gosu) y la [advertencia del mantenedor sobre SUID](https://github.com/tianon/gosu/issues/11). No invoques el helper durante el inventario pasivo.

Un wrapper de copia de seguridad personalizado con set-user-ID puede aceptar una ruta elegida por quien lo invoca e interpolarla en un comando de archivado pasado a `system(3)`. Si la ruta no está entre comillas en el comando construido, el shell hijo puede aplicar [expansión de tilde mediante `HOME`, patrones de ruta como `?` y `*`, y separación de comandos por saltos de línea](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rechazar solo los signos de puntuación habituales mediante una lista de denegación no hace que la ruta se interprete literalmente. Confirma el flujo exacto de argumentos, el entorno heredado, el shell hijo y la identidad efectiva, el acceso al sistema de archivos y si quien invoca puede ver la salida del archivador. El bit SUID, una cadena que mencione una herramienta de archivado o el mero bloqueo de la ruta literal `/root` no demuestran por sí solos ni divulgación ni ejecución de código. Revisa una copia del wrapper sin conexión; durante la enumeración pasiva, no archives archivos privados ni envíes entradas que provoquen fallos.

La [sustitución de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) del shell, como `$(...)`, es otra posible brecha en una lista de denegación de metacaracteres: incluso un prefijo de comando fijo y permitido puede pasar un argumento posterior controlado por quien lo invoca a través de `/bin/sh -c`. Verifica sin conexión las comillas exactas, el analizador y la identidad efectiva; no consideres una cadena de `system()` o una lista de denegación incompleta como prueba de ejecución.

También importa el **árbol de procesos que realiza la llamada**. Un worker web puede instalar un filtro seccomp que restrinja las llamadas al sistema que cambian los UID; [los filtros seccomp se heredan por los procesos hijos y persisten tras `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Por ejemplo, las directivas [ `LimitUIDRange` y `LimitGIDRange` de mpm-itk de Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) pueden limitar las identidades que pueden alcanzar los procesos descendientes. `Seccomp: 2` en `/proc/self/status` indica el modo del filtro, no su política ni si este helper concreto puede adquirir la identidad de su propietario. Revisa conjuntamente la ascendencia de la invocación real y el filtro efectivo, junto con las condiciones SUID, de montaje y `no_new_privs`; una sesión de inicio de sesión independiente puede tener una política distinta, pero requiere su propia vía de acceso válida.

Un ejecutable SUID personalizado puede invocar un script de Python independiente y legible. Si realmente usa **Python 2**, [`input()` evalúa la expresión introducida](https://docs.python.org/2/library/functions.html#input); en Python 3, `input()` devuelve texto. Confirma la identidad efectiva del wrapper, la ruta y versión del intérprete, la ruta del script y si la entrada no confiable llega a esa llamada antes de considerar esa línea de código una vía de ejecución. Un bit set-ID en el propio script o una llamada a `input()` sin el wrapper privilegiado no establecen el mismo límite. Durante la enumeración, revisa las rutas a las que hace referencia el binario y una parte acotada del código fuente del script, sin ejecutarlo.

Si hay código fuente legible junto a un ejecutable SUID inusual, compara la cantidad de bytes solicitada en cada lectura de archivos controlada por quien invoca con el tamaño del búfer de destino e inspecciona las comprobaciones posteriores del flujo de control. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) almacena los elementos solicitados en el puntero proporcionado; no conoce la capacidad del objeto de destino. Una discrepancia de tamaños es un indicio estático de un posible problema de seguridad de memoria, no una prueba de escalada de privilegios viable: confirma que el código fuente corresponde al binario instalado, que quien invoca puede proporcionar la entrada, que la ejecución SUID es efectiva en ese contexto y que se puede alcanzar la ruta pertinente. Revisa sin conexión una copia acotada del código fuente o del binario, en lugar de enviar entradas que provoquen fallos al programa privilegiado durante la enumeración.

Un helper SUID personalizado puede divulgar un archivo protegido sin imprimir su contenido. Si quien lo invoca elige tanto una ruta como una expresión regular y el helper devuelve un recuento visible de coincidencias con su UID efectivo, las pruebas de prefijos anclados pueden formar un oráculo carácter por carácter. Confirma el propietario del helper, el comportamiento del ID efectivo, los permisos de ejecución, las restricciones de ruta, la semántica de las expresiones regulares, la visibilidad de la respuesta y la existencia de un archivo específico con más privilegios que quien lo invoca no pueda leer de otro modo. Un bit SUID o una cadena de una biblioteca de expresiones regulares, por sí solos, no demuestran nada de ese flujo. Durante la enumeración pasiva, registra el ejecutable inusual y revisa sin conexión un desensamblado acotado o una copia del código fuente; no pruebes iterativamente el helper activo ni imprimas secretos recuperados.

En OpenBSD, un lector personalizado con set-user-ID que acepta una ruta elegida por quien lo invoca puede exponer archivos de `/var/backups` si su identidad efectiva puede leerlos y devuelve su contenido. [`changelist(5)` de OpenBSD](https://man.openbsd.org/changelist.5) describe las copias `.current` y `.backup` de las rutas configuradas, pero las entradas con el prefijo `+` almacenan sumas de comprobación SHA-256 en lugar del contenido de los archivos; el directorio de copias de seguridad debería pertenecer a root y tener el modo `0700`. Una regla [`unveil` de lectura](https://man.openbsd.org/unveil.2) del helper para `/var` puede permitir el acceso a rutas bajo ese directorio, pero por sí sola no concede ni demuestra acceso a los archivos. Confirma el UID efectivo real, que el usuario actual pueda ejecutar el archivo, la ruta aceptada, la existencia y el contenido de la copia de seguridad y cualquier requisito de autenticación independiente antes de afirmar que hay una escalada. La enumeración pasiva debería registrar el helper y los metadatos de las rutas, no invocar el lector ni imprimir datos de las copias de seguridad.

Un programa SUID personalizado que comprueba con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) una ruta elegida por quien lo invoca y abre esa ruta más tarde puede sufrir una condición de carrera si cambia un archivo o enlace simbólico en un directorio donde esa persona tiene permisos de escritura. La comprobación se aplica al objeto anterior, mientras que una llamada posterior a [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) puede resolver otro objeto. Confirma que el helper se puede ejecutar con identidad efectiva elevada, que una ruta de código alcanzable por otros medios lee el archivo seleccionado y que quien lo invoca puede sustituir la ruta entre la comprobación y la apertura; un bit SUID, un directorio con permisos de escritura o una cadena `stat`, por sí solos, no demuestran ninguna de estas condiciones. Para que haya divulgación, también se necesita una salida visible o un destino legible por quien invoca. Revisa el binario y los metadatos de las rutas sin conexión; no intentes ganar la carrera contra el helper activo durante la enumeración pasiva.

Aplica la misma revisión de dependencias a los wrappers SGID. Un wrapper que ejecuta un shell o helper mediante una ruta absoluta sigue siendo inseguro si un usuario con menos privilegios puede sustituir ese archivo; el código ejecutado podría heredar el grupo efectivo del wrapper. Comprueba la ruta invocada exacta, sus permisos de escritura (incluidas las ACL), el grupo efectivo del wrapper y si este descarta privilegios antes de iniciar el proceso hijo. Un intérprete también puede descartar los ID efectivos heredados, así que distingue entre un elemento que merece revisión y una transición demostrada. Que haya un shell con permisos de escritura en otra parte del host no demuestra por sí solo que lo invoque un wrapper privilegiado.

### Wrappers privilegiados que pasan SQL a la CLI de SQLite

Si un programa SUID personalizado pasa SQL controlado por el usuario al **programa de línea de comandos `sqlite3`**, inspecciona el comando exacto y la identidad efectiva antes de considerar la consulta de solo lectura. La función SQL `edit()` de la CLI invoca un editor (a partir de su segundo argumento o de `VISUAL`), y su función SQL `load_extension()` puede cargar una biblioteca compartida si la carga de extensiones está habilitada. Estas son posibles vías de ejecución de código con la identidad del proceso de la CLI, incluso si el wrapper fija `PATH` o usa una ruta absoluta para `sqlite3`. El SQL debe llegar realmente a esas funciones y la CLI debe conservar la función pertinente; encontrar `sqlite3` en un binario o en el host no demuestra una escalada. La **biblioteca** de SQLite deshabilita la carga de extensiones de forma predeterminada, así que distínguela de la CLI. Si una aplicación privilegiada debe procesar SQL no confiable, el modo `--safe` de la CLI de SQLite deshabilita `edit()`, `load_extension()` y otras funciones con efectos secundarios. Consulta la [documentación de la CLI de SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentación del modo seguro](https://www.sqlite.org/cli.html#the_safe_command_line_option) y la [documentación sobre la carga de extensiones](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lectores de archivos privilegiados que alimentan un cliente verboso

Un wrapper SUID/SGID personalizado puede comprobar el acceso a una ruta elegida por quien lo invoca y luego pasar ese archivo a otro comando. Revisa la identidad efectiva durante la comprobación de acceso y la apertura posterior, resuelve los componentes `../` respecto del directorio base real e inspecciona cómo maneja el proceso hijo las entradas no válidas. Si un cliente de base de datos lee un archivo privado como SQL con una salida verbosa, puede repetir el contenido del archivo en los errores aunque el SQL no sea válido. Esto solo constituye una divulgación entre usuarios si el proceso hijo puede leer un archivo que quien lo invoca no puede, esa persona puede seleccionar el archivo a través del wrapper y la salida es visible; la presencia de `mysql` o de otra cadena de cliente no demuestra ninguna de estas condiciones.

### Ruta de búsqueda de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) afectó a algunas compilaciones de Netdata `ndsudo`. El helper SUID propiedad de root buscaba los comandos externos permitidos mediante un `PATH` proporcionado por quien lo invocaba. Revisa un helper instalado, incluso si está fuera del `PATH` habitual de quien lo invoca, solo cuando la cuenta actual pueda ejecutarlo. Confirma su propietario, el bit SUID, los permisos de ejecución (incluidas las concesiones por grupo/ACL), la compilación instalada y el estado de los parches del proveedor, y si `NoNewPrivs` o un montaje `nosuid` bloquean el cambio de identidad. Netdata indica que las compilaciones `v1.45.3` y `v1.45.0-169` tienen el parche; los backports de las distribuciones requieren una comprobación aparte. La versión del dashboard o la mera presencia de `ndsudo` no son pruebas suficientes de una escalada alcanzable. El problema de la ruta también requiere que el helper resuelva un comando externo mediante una ubicación controlada por quien lo invoca.

### Límite de privilegios de `join` de Firejail

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) afectó a la lógica privilegiada `--join` de Firejail: un destino de unión manipulado podía hacer que el helper setuid-root aceptara un espacio de nombres de montaje controlado por un atacante y copiara un estado de seguridad inseguro. Para la clasificación pasiva, confirma que la **identidad actual puede ejecutar** un binario Firejail propiedad de root y con setuid, que setuid es efectivo en su montaje y en el contexto de su proceso, y que la compilación instalada carece de la corrección. Upstream corrigió el problema en [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); los paquetes de las distribuciones pueden [incluir el parche mediante un backport](https://github.com/netblue30/firejail/issues/5191) y seguir mostrando una versión anterior. Estos requisitos previos identifican un elemento que merece revisión, no una unión exitosa ni un shell de root. No crees un jail falso ni invoques `--join` durante la enumeración.

### Permisos del archivo de registro de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) afectó a Screen 4.5.0, que abría con privilegios elevados un archivo de registro elegido por quien lo invocaba. Un binario `screen` o con la versión añadida al nombre en el inventario SUID es solo un indicio para revisar: confirma la propiedad de root, que la ejecución SUID sea efectiva para el usuario actual, la compilación instalada, el estado de los parches de la distribución y el comportamiento afectado del archivo de registro. [Debian corrigió su paquete 4.5.0 mediante un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), así que una cadena de versión o un nombre de archivo, por sí solos, no demuestran que el sistema esté expuesto. No crees un archivo de registro como prueba rutinaria durante la enumeración.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) afectó al helper privilegiado de bloqueo de correo de S-nail cuando un componente de ruta controlado por quien lo invocaba podía atravesar directorios y provocar una escritura arbitraria en un archivo. Comprueba si el usuario actual puede ejecutar un helper instalado, propiedad de root y con setuid, si la identidad setuid es efectiva según la política del proceso y del montaje, y cuál es la compilación exacta del paquete y la corrección del proveedor. El [aviso de seguridad de Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indica que su paquete de 16.04 incluye la corrección mediante backport, así que una versión que parezca upstream no es concluyente. La presencia del helper no demuestra que se pueda alcanzar la ruta afectada ni que escribir un archivo permita ejecutar código como root; inspecciona los metadatos y el estado del paquete sin invocar el helper ni intentar la carrera durante la enumeración.

### Limpieza de `tmpfiles` y snap-confine

CVE-2026-3888 es una condición de carrera entre `snap-confine` privilegiado y la limpieza de `/tmp` por systemd-tmpfiles. Una revisión pasiva puede comprobar si `snap-confine` tiene setuid o capacidades de archivo, comparar el paquete `snapd` instalado con la versión corregida para esa **versión de Ubuntu** e inspeccionar la regla efectiva de antigüedad de `/tmp` y el temporizador de limpieza. Que coincidan el paquete y la regla son requisitos previos, no pruebas de que se pueda alcanzar la condición de carrera: también importan el estado del temporizador en tiempo de ejecución, la disposición de snap, los backports del paquete y las anulaciones de reglas. Las versiones anteriores pueden requerir una configuración no predeterminada. No ejecutes una prueba de carrera durante la enumeración rutinaria. Consulta el [registro de Ubuntu para el CVE](https://ubuntu.com/security/CVE-2026-3888) para conocer el estado de los paquetes según la versión y el [aviso de Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) para entender la interacción entre los componentes.

## Inspeccionar ACL y rutas sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un directorio padre con permisos de escritura puede permitir reemplazar un archivo incluso cuando este pertenece a root. Una ACL puede conceder silenciosamente acceso a un archivo de configuración de sudoers, una unidad de servicio, un script de cron, una ruta de bibliotecas o un archivo de credenciales. Comprueba tanto la ACL como la ruta completa. Si es posible escribir archivos privilegiados arbitrarios, sigue [Arbitrary File Write to Root](write-to-root.md); para casos de configuración del linker y preload, consulta el [ejemplo de `ld.so`](ld.so.conf-example.md). Considera las copias de seguridad expuestas, los archivos `.env`, las configuraciones de bases de datos, el material de SSH y el historial como posibles fuentes de credenciales; el acceso depende de los permisos reales de cada archivo.
