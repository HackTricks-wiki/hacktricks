# SUID, SGID, ACL e file sensibili

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID modificano l'identità effettiva di un file eseguito; gli ACL possono concedere accessi che i normali bit di permesso di `ls -l` non mostrano. Esamina entrambi quando un utente può leggere, scrivere o eseguire file oltre quanto suggeriscono i permessi apparenti di proprietario e gruppo.

## Enumerare gli eseguibili privilegiati

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrati sugli eseguibili personalizzati o modificati di recente, sui proprietari insoliti e sui file presenti su mount scrivibili. Un mount `nosuid` può disattivare il comportamento set-ID; le file capabilities sono un meccanismo di privilege escalation distinto, descritto in [Linux capabilities](linux-capabilities.md). Confronta un binario sospetto con il pacchetto a cui appartiene e verifica cosa esegue, apre o carica con un'identità elevata.

Per un eseguibile SUID di proprietà di root che non conosci e che accetta input dal chiamante, esamina offline una copia del binario per individuare una gestione degli argomenti vulnerabile a errori di memoria e il percorso del codice che la raggiunge. Registra il comportamento degli effective ID e le mitigazioni, come stack canary, memoria non eseguibile, codice position-independent e randomizzazione degli indirizzi. Il nome di una funzione insicura o l'assenza di una mitigazione sono solo indizi da approfondire: l'exploitability dipende dai limiti effettivi dell'input, dal flusso di controllo raggiungibile e dall'identità effettiva al momento dell'errore. Non inviare argomenti lunghi all'eseguibile privilegiato attivo solo per verificare se va in crash durante l'enumerazione passiva.

Anche un programma SUID noto può essere sostituito o backdoored. Una data di modifica recente è un indizio, non una prova: per uno **specifico binario sospetto incluso in un pacchetto**, individua il pacchetto proprietario e confronta il file installato con i metadati del pacchetto, invece di verificare ogni pacchetto durante l'enumerazione ordinaria:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` controlla il contenuto dei file solo quando il database dei pacchetti registra un checksum; RPM confronta anche metadati come modalità e proprietario. Concentrati su una discrepanza che riguarda **l'eseguibile privilegiato stesso**: le installazioni minimali possono segnalare documentazione o file di localizzazione mancanti altrove nello stesso pacchetto. Confronta l'eseguibile sospetto con un pacchetto del fornitore attendibile ed esamina esattamente il codice modificato. Modifiche locali legittime, checksum assenti e metadati dei pacchetti compromessi limitano ciò che entrambi i comandi possono dimostrare. Nell'ambito di un triage passivo, non eseguire il programma SUID sospetto né uno script di verifica dei pacchetti. Consulta il [manuale di verifica di dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e il [manuale di verifica di RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programma SUID che richiama una shell, un comando relativo o una libreria da un percorso scrivibile può oltrepassare un confine di fiducia. Consulta [abuso di librerie condivise e linker tramite SUID](suid-shared-library-and-linker-abuse.md), le [indicazioni su PATH](../linux-basics/linux-environment-variables.md#path) e la [spiegazione degli user ID](../user-information/euid-ruid-suid.md). Per le escape note specifiche di un comando, verifica [GTFOBins](https://gtfobins.github.io/) rispetto al binario esatto e all'invocazione consentita sull'host.

Per un eseguibile set-user-ID, distingui lo **UID reale** del chiamante dall'**UID effettivo** del proprietario del file: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lascia invariato l'UID reale e, dopo ogni modifica set-ID, copia l'UID effettivo nell'UID salvato. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) esegue il comando tramite `/bin/sh -c`; la shell selezionata da quel percorso determina se un processo figlio conserva la propria identità effettiva. In particolare, le [regole della modalità privilegiata di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) reimpostano un UID effettivo diverso sull'UID reale quando Bash si avvia senza `-p`. Verifica le modifiche effettive agli UID del programma ausiliario e l'invocazione dei processi figli, insieme al proprietario, ai permessi di esecuzione, all'impostazione di mount `nosuid` e allo stato `no_new_privs` del processo. Il bit SUID o una chiamata a una shell, da soli, non dimostrano che sia possibile ottenere un'identità con privilegi superiori.

Un `jjs` SUID insolito di proprietà di root merita una verifica separata dell'accesso ai file, se l'utente corrente può eseguirlo. Il tool Nashorn legacy può accedere alle API Java per i file anche quando una shell avviata come processo figlio perde l'UID effettivo; prima di considerarlo una lettura o scrittura privilegiata, verifica il comportamento della JVM installata, l'identità effettiva con cui avviene l'operazione sul file e le impostazioni `nosuid`/`no_new_privs`. [Oracle ha rimosso `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); un percorso installato potrebbe comunque corrispondere a una build più vecchia o distribuita separatamente. [GTFOBins documenta le API per i file](https://gtfobins.org/gtfobins/jjs/), ma i suoi esempi con sudo non dimostrano il comportamento SUID di ogni build. Non invocare il tool durante l'enumerazione passiva.

Un eseguibile `gosu` SUID di proprietà di root e accessibile a un utente con privilegi inferiori merita una verifica: la sua interfaccia documentata accetta un utente di destinazione e un comando, ma nell'uso normale nei container viene avviato da root per ridurre i privilegi. Verifica il comportamento SUID della build installata, l'identità effettiva e la mappatura degli user namespace, oltre a `nosuid` e `no_new_privs`; root nel container non implica root sull'host. Il nome del file o il bit SUID, da soli, non dimostrano che la transizione funzioni. Consulta [l'utilizzo a monte](https://github.com/tianon/gosu) e [l'avvertenza SUID del manutentore](https://github.com/tianon/gosu/issues/11). Non invocare il programma ausiliario durante l'inventario passivo.

Un wrapper di backup personalizzato set-user-ID può accettare un percorso scelto dal chiamante e interpolarlo in un comando di archiviazione passato a `system(3)`. Se il percorso non è racchiuso tra virgolette nel comando costruito, la shell figlia può applicare [l'espansione della tilde tramite `HOME`, i pattern di percorso come `?` e `*` e la separazione dei comandi tramite newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rifiutare solo la punteggiatura più comune con una denylist non rende letterale il percorso. Verifica il flusso esatto degli argomenti, l'ambiente ereditato, la shell figlia e l'identità effettiva, l'accesso al filesystem e l'eventuale visibilità dell'output dell'archiviazione per il chiamante. Il bit SUID, una stringa relativa a un tool di archiviazione o il solo blocco di un percorso letterale `/root` non dimostrano né una divulgazione né l'esecuzione di codice. Durante l'enumerazione passiva, esamina offline una copia del wrapper invece di archiviare file privati o inviare input che causano crash.

La [sostituzione di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) della shell, come `$(...)`, è un'altra possibile lacuna in una denylist di metacaratteri: anche un prefisso di comando consentito e fisso può passare un argomento successivo controllato dal chiamante a `/bin/sh -c`. Verifica offline le virgolette esatte, il parser e l'identità effettiva; non considerare una stringa `system()` o una denylist incompleta, da sole, una prova di esecuzione.

Conta anche l'**albero dei processi chiamanti**. Un worker web può installare un filtro seccomp che limita le system call che modificano gli UID; i [filtri seccomp vengono ereditati dai processi figli e persistono attraverso `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Per esempio, le direttive [`LimitUIDRange` e `LimitGIDRange` di mpm-itk di Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) possono limitare le identità accessibili ai discendenti. `Seccomp: 2` in `/proc/self/status` indica la modalità del filtro, non la sua policy né se questo particolare programma ausiliario possa ottenere l'identità del proprietario. Esamina insieme l'ascendenza dell'invocazione effettiva e il filtro attivo, nonché le condizioni SUID, di mount e `no_new_privs`; una sessione di login separata può avere una policy diversa, ma richiede un proprio percorso di accesso valido.

Un eseguibile SUID personalizzato può invocare uno script Python separato e leggibile. Se usa effettivamente Python **2**, [`input()` valuta l'espressione inserita](https://docs.python.org/2/library/functions.html#input); in Python 3, invece, `input()` restituisce testo. Prima di considerare quella riga di codice un percorso di esecuzione, verifica l'identità effettiva del wrapper, il percorso e la versione dell'interprete, il percorso dello script e se l'input non attendibile raggiunge quella chiamata. Il bit set-ID assegnato allo script stesso o una chiamata a `input()` senza il wrapper privilegiato non stabiliscono lo stesso confine. Durante l'enumerazione, esamina i percorsi referenziati dal binario e una copia circoscritta del sorgente dello script senza eseguirlo.

Se un eseguibile SUID insolito è accompagnato da codice sorgente leggibile, confronta il numero di byte richiesto per ogni lettura di file controllata dal chiamante con la dimensione del buffer di destinazione, ed esamina i controlli successivi nel flusso di esecuzione. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) memorizza gli elementi richiesti all'indirizzo fornito; non conosce la capacità dell'oggetto di destinazione. Una discrepanza nelle dimensioni è un indizio statico di un problema di sicurezza della memoria, non la prova di un'escalation di privilegi utilizzabile: verifica che il sorgente corrisponda al binario installato, che il chiamante possa fornire l'input, che l'esecuzione SUID sia effettiva in quel contesto e che il percorso interessato sia raggiungibile. Durante l'enumerazione, esamina offline una copia circoscritta del sorgente o del binario, anziché inviare input che causano crash al programma privilegiato.

Un programma ausiliario SUID personalizzato può divulgare un file protetto senza stamparne il contenuto. Se il chiamante sceglie sia un percorso sia un'espressione regolare e il programma ausiliario restituisce un conteggio delle corrispondenze visibile, eseguire test con prefissi ancorati può creare un oracle carattere per carattere. Verifica il proprietario del programma ausiliario, il comportamento degli ID effettivi, i permessi di esecuzione, le restrizioni sui percorsi, la semantica dell'espressione regolare, la visibilità della risposta e l'esistenza di uno specifico file con privilegi superiori che il chiamante non può leggere altrimenti. Il bit SUID o una stringa relativa a una libreria regex, da soli, non dimostrano nessuno di questi passaggi. Durante l'enumerazione passiva, annota l'eseguibile insolito ed esamina una copia circoscritta del disassemblato o del sorgente; non eseguire tentativi iterativi sul programma ausiliario attivo né stampare i segreti recuperati.

Su OpenBSD, un lettore personalizzato set-user-ID che accetta un percorso scelto dal chiamante può esporre file in `/var/backups` se la sua identità effettiva può leggerli e il programma restituisce il contenuto al chiamante. [`changelist(5)` di OpenBSD](https://man.openbsd.org/changelist.5) descrive le copie `.current` e `.backup` dei percorsi configurati, ma le voci precedute da `+` memorizzano checksum SHA-256 anziché il contenuto dei file; la directory dei backup dovrebbe appartenere a root e avere modalità `0700`. Una regola di lettura [`unveil` per `/var`](https://man.openbsd.org/unveil.2) del programma ausiliario può consentire l'accesso al di sotto di quel percorso, ma non concede né dimostra da sola l'accesso ai file. Prima di dichiarare un'escalation, verifica l'UID effettivo, i permessi di esecuzione per l'utente corrente, il percorso accettato, l'esistenza e il contenuto dei backup e gli eventuali requisiti di autenticazione indipendenti. L'enumerazione passiva dovrebbe riportare il programma ausiliario e i metadati del percorso, non invocare il lettore né stampare i dati dei backup.

Un programma SUID personalizzato che controlla un percorso scelto dal chiamante con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e apre il percorso in seguito può essere vulnerabile a una race che modifica un file o un symlink in una directory scrivibile dal chiamante. Il controllo riguarda l'oggetto precedente, mentre una successiva [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) può risolverne un altro. Verifica che il programma ausiliario sia eseguibile con un'identità effettiva elevata, che un percorso del codice altrimenti raggiungibile legga il file selezionato e che il chiamante possa sostituire il percorso tra il controllo e l'apertura; il bit SUID, una directory scrivibile o una stringa `stat`, da soli, non dimostrano nessuna di queste condizioni. Per una divulgazione serve anche un output visibile o una destinazione leggibile dal chiamante. Esamina offline il binario e i metadati del percorso; durante l'enumerazione passiva non provocare race con il programma ausiliario attivo.

Applica la stessa verifica delle dipendenze ai wrapper SGID. Un wrapper che esegue una shell o un programma ausiliario tramite un percorso assoluto può comunque essere insicuro se un utente con privilegi inferiori può sostituire quel file; il codice avviato può ereditare il gruppo effettivo del wrapper. Controlla il percorso esatto invocato, i relativi permessi di scrittura (incluse le ACL), il gruppo effettivo del wrapper e se questo riduce i privilegi prima di avviare il processo figlio. Anche un interprete può scartare gli ID effettivi ereditati, quindi distingui un elemento da esaminare da una transizione dimostrata. Il solo fatto che esista una shell scrivibile altrove sull'host non dimostra che un wrapper privilegiato la invochi.

### Wrapper privilegiati che passano SQL alla CLI di SQLite

Se un programma SUID personalizzato passa SQL controllato dall'utente al **programma a riga di comando `sqlite3`**, esamina il comando esatto e l'identità effettiva prima di considerare la query di sola lettura. La funzione SQL `edit()` della CLI invoca un editor (indicato nel secondo argomento o in `VISUAL`) e la funzione SQL `load_extension()` può caricare una libreria condivisa se il caricamento delle estensioni è abilitato. Questi sono potenziali percorsi di esecuzione di codice con l'identità del processo CLI, anche se il wrapper fissa `PATH` o usa un percorso assoluto per `sqlite3`. L'SQL deve raggiungere effettivamente queste funzioni e la CLI deve mantenere attiva la funzionalità pertinente; trovare `sqlite3` in un binario o sull'host, da solo, non prova un'escalation. La **libreria** SQLite disabilita il caricamento delle estensioni per impostazione predefinita: distinguila dalla CLI. Se un'applicazione privilegiata deve elaborare SQL non attendibile, la modalità `--safe` della CLI di SQLite disabilita `edit()`, `load_extension()` e altre funzioni con effetti collaterali. Consulta la [documentazione della CLI di SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentazione della modalità sicura](https://www.sqlite.org/cli.html#the_safe_command_line_option) e la [documentazione sul caricamento delle estensioni](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lettori privilegiati di file che alimentano un client verboso

Un wrapper SUID/SGID personalizzato può controllare l'accesso a un percorso scelto dal chiamante e poi passare quel file a un altro comando. Esamina l'identità effettiva durante il controllo dell'accesso e l'apertura successiva, risolvi gli eventuali componenti `../` rispetto alla directory base effettiva e controlla come il processo figlio gestisce input non validi. Se un client di database legge un file privato come SQL con output verboso, potrebbe ripetere il contenuto del file nei messaggi di errore, anche se l'SQL non è valido. Si tratta di una divulgazione tra utenti solo se il processo figlio può leggere un file che il chiamante non può leggere, il chiamante può selezionare quel file tramite il wrapper e l'output è visibile; la sola presenza di `mysql` o di un'altra stringa relativa a un client non dimostra nessuna di queste condizioni.

### Percorso di ricerca di Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ha interessato alcune build di Netdata `ndsudo`. Il programma ausiliario SUID di proprietà di root cercava i comandi esterni consentiti usando un `PATH` fornito dal chiamante. Esamina un programma ausiliario installato, anche se si trova al di fuori del `PATH` abituale del chiamante, solo se l'account corrente può eseguirlo. Verifica il proprietario, il bit SUID, i permessi di esecuzione (inclusi i permessi concessi da gruppi/ACL), la build installata e lo stato delle patch del fornitore, nonché se `NoNewPrivs` o un mount `nosuid` impediscono la modifica dell'identità. Netdata indica come corrette le build `v1.45.3` e `v1.45.0-169`; i backport delle distribuzioni richiedono una verifica separata. La versione mostrata nella dashboard o la semplice presenza di `ndsudo` non sono prove sufficienti di un'escalation raggiungibile. Il problema del percorso richiede inoltre che il programma ausiliario risolva un comando esterno tramite una posizione controllata dal chiamante.

### Confine di privilegi di Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ha interessato la logica privilegiata `--join` di Firejail: un target di join creato ad arte poteva indurre il programma ausiliario setuid-root ad accettare un mount namespace controllato dall'attaccante e a copiare uno stato di sicurezza non sicuro. Per un triage passivo, verifica che l'**identità corrente possa eseguire** un binario Firejail setuid di proprietà di root, che setuid sia effettivo sul relativo mount e nel contesto del processo e che la build installata non includa la correzione. A monte il problema è stato corretto nella [versione 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); i pacchetti delle distribuzioni possono [includere la correzione tramite backport](https://github.com/netblue30/firejail/issues/5191) pur mostrando una versione più vecchia. Questi prerequisiti identificano un elemento da esaminare, non dimostrano un join riuscito o l'ottenimento di una shell root. Durante l'enumerazione, non creare una jail falsa né invocare `--join`.

### Permessi dei file di log di GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) riguardava Screen 4.5.0, che apriva con privilegi elevati un file di log scelto dal chiamante. Un binario `screen` o con versione aggiunta nel nome nell'inventario SUID è solo un elemento da esaminare: verifica la proprietà di root, l'effettiva esecuzione SUID per l'utente corrente, la build installata e lo stato delle patch della distribuzione, nonché il comportamento interessato relativo ai file di log. [Debian ha corretto il suo pacchetto 4.5.0 con un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), quindi una stringa di versione o un nome file, da soli, non dimostrano l'esposizione. Non creare un file di log come verifica di routine durante l'enumerazione.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ha interessato il programma ausiliario privilegiato di S-nail per il blocco dei file di posta, quando un componente del percorso controllato dal chiamante poteva attraversare directory e provocare la scrittura di un file arbitrario. Verifica se l'utente corrente può eseguire un programma ausiliario setuid installato e di proprietà di root, se l'identità setuid è effettiva in base alle policy del mount e del processo e quale sia la build esatta del pacchetto e la relativa correzione del fornitore. [La nota di sicurezza di Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) elenca una correzione inclusa tramite backport nel pacchetto 16.04, quindi una versione che sembra quella a monte non è una prova conclusiva. La presenza del programma ausiliario non dimostra che il percorso interessato sia raggiungibile né che la scrittura di un file consenta l'esecuzione come root; durante l'enumerazione, esamina i metadati e lo stato del pacchetto senza invocare il programma ausiliario né tentare la race.

### Pulizia di snap-confine e tmpfiles

CVE-2026-3888 è una race che coinvolge `snap-confine` privilegiato e la pulizia di `/tmp` da parte di systemd-tmpfiles. Una verifica passiva può controllare se `snap-confine` è setuid o dispone di capabilities sui file, confrontare il pacchetto `snapd` installato con la versione corretta per quella **release di Ubuntu** e ispezionare la regola effettiva sull'età dei file in `/tmp` e il timer di pulizia. Un pacchetto e una regola corrispondenti sono prerequisiti, non la prova che la race sia raggiungibile: contano anche lo stato del timer durante l'esecuzione, la configurazione di snap, i backport dei pacchetti e le eventuali sostituzioni delle regole. Le release più vecchie possono richiedere una configurazione non predefinita. Non eseguire una verifica della race durante l'enumerazione di routine. Consulta il [record CVE di Ubuntu](https://ubuntu.com/security/CVE-2026-3888) per lo stato dei pacchetti specifico per release e l'[avviso di Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) per l'interazione tra i componenti.

## Esaminare le ACL e i percorsi sensibili

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Una directory padre scrivibile può consentire la sostituzione anche quando il file appartiene a root. Una ACL può concedere silenziosamente l’accesso a un drop-in di sudoers, a un’unità di servizio, a uno script cron, a un percorso di libreria o a un file di credenziali. Controlla sia l’ACL sia l’intero percorso. Se sono possibili scritture arbitrarie di file con privilegi elevati, segui [Arbitrary File Write to Root](write-to-root.md); per i casi relativi alla configurazione del linker e al preload, consulta l’[esempio di `ld.so`](ld.so.conf-example.md). Considera i backup esposti, i file `.env`, le configurazioni dei database, il materiale SSH e la cronologia come possibili fonti di credenziali, con accesso regolato dai permessi effettivi di ciascun file.
