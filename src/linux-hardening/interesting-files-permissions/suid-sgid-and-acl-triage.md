# SUID, SGID, ACLs και ευαίσθητα αρχεία

{{#include ../../banners/hacktricks-training.md}}

Τα SUID και SGID αλλάζουν την effective identity ενός αρχείου που εκτελείται· τα ACLs μπορούν να παραχωρούν πρόσβαση που δεν εμφανίζεται στα συνηθισμένα mode bits του `ls -l`. Ελέγξτε και τα δύο όταν ένας χρήστης μπορεί να διαβάζει, να γράφει ή να εκτελεί αρχεία πέρα από όσα υποδεικνύουν οι φαινομενικές άδειες ιδιοκτήτη και ομάδας.

## Καταγράψτε τα προνομιούχα εκτελέσιμα файла

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Εστιάστε σε προσαρμοσμένα ή πρόσφατα τροποποιημένα εκτελέσιμα, ασυνήθιστους κατόχους και αρχεία σε εγγράψιμα mounts. Ένα mount `nosuid` μπορεί να απενεργοποιήσει τη συμπεριφορά set-ID· τα file capabilities αποτελούν ξεχωριστό μηχανισμό προνομίων που περιγράφεται στο [Linux capabilities](linux-capabilities.md). Συγκρίνετε ένα ύποπτο binary με το αντίστοιχο πακέτο και ελέγξτε τι εκτελεί, ανοίγει ή φορτώνει με αυξημένη ταυτότητα.

Για ένα άγνωστο SUID εκτελέσιμο που ανήκει στον root και δέχεται είσοδο από τον καλούντα, εξετάστε offline ένα αντίγραφο του binary για μη ασφαλή ως προς τη μνήμη διαχείριση ορισμάτων και τη διαδρομή κώδικα που οδηγεί σε αυτήν. Καταγράψτε τη συμπεριφορά effective-ID και τα mitigations, όπως stack canaries, μη εκτελέσιμη μνήμη, position-independent code και address randomization. Ένα μη ασφαλές όνομα συνάρτησης ή ένα mitigation που λείπει είναι απλώς ένδειξη για περαιτέρω έλεγχο: η δυνατότητα εκμετάλλευσης εξαρτάται από τα πραγματικά όρια εισόδου, τη ροή ελέγχου που μπορεί να εκτελεστεί και την effective identity κατά τη στιγμή του σφάλματος. Μην στέλνετε μεγάλα ορίσματα στο ενεργό εκτελέσιμο με προνόμια απλώς για να δοκιμάσετε αν θα καταρρεύσει κατά την παθητική απαρίθμηση.

Ένα οικείο SUID πρόγραμμα μπορεί και το ίδιο να έχει αντικατασταθεί ή να έχει εισαχθεί σε αυτό backdoor. Ένας πρόσφατος χρόνος τροποποίησης είναι ένδειξη, όχι απόδειξη: για ένα **συγκεκριμένο ύποπτο binary πακέτου**, εντοπίστε το πακέτο στο οποίο ανήκει και συγκρίνετε το εγκατεστημένο αρχείο με τα metadata του πακέτου, αντί να επαληθεύετε κάθε πακέτο κατά τη συνήθη απαρίθμηση:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` ελέγχει τα περιεχόμενα αρχείων μόνο όταν η βάση δεδομένων πακέτων έχει καταγεγραμμένο checksum· το RPM συγκρίνει επίσης metadata, όπως mode και ιδιοκτησία. Εστιάστε σε ασυμφωνία του **ίδιου του εκτελέσιμου με δικαιώματα**: οι εγκαταστάσεις με αφαιρεμένα αρχεία μπορεί να αναφέρουν ελλείπουσα τεκμηρίωση ή αρχεία locale αλλού στο ίδιο πακέτο. Συγκρίνετε το ύποπτο εκτελέσιμο με ένα έμπιστο πακέτο του προμηθευτή και εξετάστε τον ακριβή κώδικα που έχει αλλάξει. Οι νόμιμες τοπικές αλλαγές, η απουσία checksums και τα παραβιασμένα metadata πακέτων περιορίζουν όσα αποδεικνύει κάθε εντολή. Μην εκτελείτε ούτε το ύποπτο πρόγραμμα SUID ούτε κάποιο script επαλήθευσης πακέτων στο πλαίσιο παθητικής διαλογής. Δείτε το [εγχειρίδιο επαλήθευσης dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) και το [εγχειρίδιο επαλήθευσης RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Ένα πρόγραμμα SUID που καλεί shell, σχετική εντολή ή βιβλιοθήκη από διαδρομή με δικαίωμα εγγραφής μπορεί να παραβιάσει ένα όριο εμπιστοσύνης. Δείτε την [κατάχρηση SUID shared-library και linker](suid-shared-library-and-linker-abuse.md), τις [οδηγίες PATH](../linux-basics/linux-environment-variables.md#path) και την [επεξήγηση user ID](../user-information/euid-ruid-suid.md). Για γνωστές διαφυγές που αφορούν συγκεκριμένες εντολές, ελέγξτε το [GTFOBins](https://gtfobins.github.io/) για το ακριβές binary και την κλήση που επιτρέπονται στο host.

Για ένα εκτελέσιμο set-user-ID, διακρίνετε το **real UID** του καλούντος από το **effective UID** του ιδιοκτήτη του αρχείου: το [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) αφήνει το real UID αμετάβλητο και αντιγράφει το effective UID στο saved UID μετά από οποιαδήποτε αλλαγή set-ID. Το [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) εκτελεί την εντολή μέσω του `/bin/sh -c`· το shell που επιλέγεται από αυτή τη διαδρομή επηρεάζει το αν μια θυγατρική διεργασία διατηρεί την effective identity της. Ειδικότερα, οι [κανόνες privileged mode του Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) επαναφέρουν ένα διαφορετικό effective UID στο real UID όταν το Bash ξεκινά χωρίς `-p`. Ελέγξτε τις πραγματικές αλλαγές UID του helper και την κλήση της θυγατρικής διεργασίας, καθώς και τον ιδιοκτήτη του, την πρόσβαση εκτέλεσης, τη ρύθμιση `nosuid` του mount και την κατάσταση `no_new_privs` της διεργασίας. Το bit SUID ή μια κλήση shell από μόνα τους δεν αποδεικνύουν ότι είναι εφικτή μια μετάβαση σε υψηλότερα δικαιώματα.

Ένα ασυνήθιστο SUID `jjs` που ανήκει στον root αξίζει ξεχωριστό έλεγχο πρόσβασης σε αρχεία, εφόσον ο τρέχων χρήστης μπορεί να το εκτελέσει. Το παλαιότερο εργαλείο Nashorn μπορεί να προσπελάσει Java file APIs ακόμη κι όταν ένα shell που έχει δημιουργηθεί ως θυγατρική διεργασία αποβάλλει ένα effective UID· επιβεβαιώστε τη συμπεριφορά της εγκατεστημένης JVM, την effective identity της λειτουργίας αρχείου και τις ρυθμίσεις `nosuid`/`no_new_privs` πριν το θεωρήσετε μέσο προνομιακής ανάγνωσης ή εγγραφής. Η [Oracle αφαίρεσε το `jjs` στο JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)· μια εγκατεστημένη διαδρομή μπορεί να αντιστοιχεί σε παλαιότερη ή ξεχωριστά συσκευασμένη έκδοση. Το [GTFOBins τεκμηριώνει τα file APIs](https://gtfobins.org/gtfobins/jjs/), αλλά τα παραδείγματα sudo δεν αποδεικνύουν συμπεριφορά SUID για κάθε build. Μην εκτελείτε το εργαλείο κατά την παθητική απαρίθμηση.

Ένα SUID εκτελέσιμο `gosu` που ανήκει στον root και είναι προσβάσιμο από χρήστη με χαμηλότερα δικαιώματα αξίζει έλεγχο: η τεκμηριωμένη διεπαφή του δέχεται χρήστη-στόχο και εντολή, αλλά η συνήθης χρήση σε container το εκκινεί ως root για να αποβάλει δικαιώματα. Επαληθεύστε τη συμπεριφορά SUID της εγκατεστημένης έκδοσης, την effective identity και τη χαρτογράφηση user namespace, καθώς και τις ρυθμίσεις `nosuid` και `no_new_privs`· ο root μέσα σε container δεν συνεπάγεται root στο host. Το όνομα αρχείου ή το bit SUID από μόνο του δεν αποδεικνύει ότι λειτουργεί η μετάβαση. Δείτε τη [χρήση upstream](https://github.com/tianon/gosu) και την [προειδοποίηση του maintainer για SUID](https://github.com/tianon/gosu/issues/11). Μην εκτελείτε τον helper κατά την παθητική απογραφή.

Ένα προσαρμοσμένο wrapper backup set-user-ID μπορεί να δέχεται διαδρομή που επιλέγει ο καλών και να την ενσωματώνει σε εντολή αρχειοθέτησης που περνά στο `system(3)`. Αν η διαδρομή δεν βρίσκεται μέσα σε εισαγωγικά στη συντιθέμενη εντολή, το child shell μπορεί να εφαρμόσει [επέκταση tilde με χρήση του `HOME`, μοτίβα pathname όπως `?` και `*`, και διαχωρισμό εντολών με newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)· η απόρριψη μόνο γνωστών σημείων στίξης μέσω denylist δεν καθιστά κυριολεκτική τη διαδρομή. Επιβεβαιώστε την ακριβή ροή ορισμάτων, το κληρονομημένο περιβάλλον, το child shell και την effective identity, την πρόσβαση στο σύστημα αρχείων και το αν η έξοδος αρχειοθέτησης είναι ορατή στον καλούντα. Το bit SUID, μια συμβολοσειρά εργαλείου αρχειοθέτησης ή η απόρριψη μιας κυριολεκτικής διαδρομής `/root` από μόνα τους δεν αποδεικνύουν ούτε αποκάλυψη δεδομένων ούτε εκτέλεση κώδικα. Εξετάστε offline ένα αντίγραφο του wrapper αντί να αρχειοθετείτε ιδιωτικά αρχεία ή να στέλνετε εισόδους που προκαλούν crash κατά την παθητική απαρίθμηση.

Η [υποκατάσταση εντολών](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) του shell, όπως `$(...)`, είναι ένα ακόμη πιθανό κενό σε denylist metacharacters: ακόμη και ένα σταθερό επιτρεπόμενο πρόθεμα εντολής μπορεί να περάσει μεταγενέστερο όρισμα ελεγχόμενο από τον καλούντα μέσω του `/bin/sh -c`. Επαληθεύστε offline τα ακριβή εισαγωγικά, τον parser και την effective identity· μην εκλαμβάνετε μόνο μια συμβολοσειρά `system()` ή μια ελλιπή denylist ως απόδειξη εκτέλεσης.

Σημασία έχει επίσης το **δέντρο διεργασιών του καλούντος**. Ένα web worker μπορεί να εγκαταστήσει φίλτρο seccomp που περιορίζει τις system calls αλλαγής UID· τα [φίλτρα seccomp περνούν στις θυγατρικές διεργασίες και επιβιώνουν του `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Για παράδειγμα, οι οδηγίες [`LimitUIDRange` και `LimitGIDRange` του mpm-itk του Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) μπορούν να περιορίσουν τις ταυτότητες που είναι προσβάσιμες από απογόνους. Η ένδειξη `Seccomp: 2` στο `/proc/self/status` δείχνει τη λειτουργία του φίλτρου, όχι την πολιτική ούτε το αν ο συγκεκριμένος helper μπορεί να αποκτήσει την identity του ιδιοκτήτη του. Εξετάστε μαζί την προέλευση της πραγματικής κλήσης και το effective φίλτρο, καθώς και τις συνθήκες SUID, mount και `no_new_privs`· μια ξεχωριστή συνεδρία login μπορεί να έχει διαφορετική πολιτική, αλλά απαιτεί δική της έγκυρη διαδρομή πρόσβασης.

Ένα προσαρμοσμένο SUID εκτελέσιμο μπορεί να καλεί ξεχωριστό, αναγνώσιμο Python script. Αν χρησιμοποιεί πράγματι Python **2**, η [`input()` αξιολογεί την έκφραση που εισάγεται](https://docs.python.org/2/library/functions.html#input)· η `input()` της Python 3 επιστρέφει κείμενο. Επιβεβαιώστε την effective identity του wrapper, τη διαδρομή και την έκδοση του interpreter, τη διαδρομή του script και το αν μη έμπιστη είσοδος φτάνει σε αυτή την κλήση, προτού θεωρήσετε τη γραμμή του πηγαίου κώδικα διαδρομή εκτέλεσης. Το bit set-ID στο ίδιο το script ή μια κλήση `input()` χωρίς προνομιούχο wrapper δεν δημιουργούν το ίδιο όριο. Εξετάστε τις αναφερόμενες διαδρομές του binary και ένα περιορισμένο απόσπασμα πηγαίου κώδικα χωρίς να το εκτελέσετε κατά την απαρίθμηση.

Αν υπάρχει αναγνώσιμος πηγαίος κώδικας μαζί με ένα ασυνήθιστο SUID εκτελέσιμο, συγκρίνετε τον αριθμό byte που ζητείται σε κάθε ανάγνωση αρχείου ελεγχόμενη από τον καλούντα με το μέγεθος του buffer προορισμού και εξετάστε τους μεταγενέστερους ελέγχους ροής ελέγχου. Η [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) αποθηκεύει τα ζητούμενα στοιχεία στον παρεχόμενο δείκτη· δεν γνωρίζει τη χωρητικότητα του αντικειμένου προορισμού. Μια ασυμφωνία μεγέθους αποτελεί ένδειξη για στατικό έλεγχο ασφάλειας μνήμης, όχι απόδειξη αξιοποιήσιμης κλιμάκωσης προνομίων: επιβεβαιώστε ότι ο πηγαίος κώδικας αντιστοιχεί στο εγκατεστημένο binary, ότι ο καλών μπορεί να δώσει την είσοδο, ότι η εκτέλεση SUID είναι ενεργή σε αυτό το πλαίσιο και ότι η σχετική διαδρομή είναι προσβάσιμη. Εξετάστε offline ένα περιορισμένο αντίγραφο του πηγαίου κώδικα ή του binary αντί να στέλνετε εισόδους που προκαλούν crash στο προνομιούχο πρόγραμμα κατά την απαρίθμηση.

Ένας προσαρμοσμένος SUID helper μπορεί να αποκαλύψει ένα προστατευμένο αρχείο χωρίς να εκτυπώσει τα περιεχόμενά του. Αν ο καλών επιλέγει τόσο ένα pathname όσο και μια regular expression και ο helper επιστρέφει ορατό πλήθος αντιστοιχιών χρησιμοποιώντας το effective UID του, έλεγχοι προθέματος με αγκύρωση μπορεί να λειτουργήσουν ως oracle χαρακτήρα προς χαρακτήρα. Επιβεβαιώστε τον ιδιοκτήτη του helper, τη συμπεριφορά effective ID, την πρόσβαση εκτέλεσης, τους περιορισμούς pathname, τη σημασιολογία της regex, την ορατότητα της απόκρισης και την ύπαρξη συγκεκριμένου αρχείου υψηλότερων προνομίων που ο καλών δεν μπορεί διαφορετικά να διαβάσει. Το bit SUID ή μια συμβολοσειρά βιβλιοθήκης regex από μόνα τους δεν αποδεικνύουν καμία από αυτές τις ροές. Κατά την παθητική απαρίθμηση, καταγράψτε το ασυνήθιστο εκτελέσιμο και εξετάστε offline ένα περιορισμένο disassembly ή αντίγραφο του πηγαίου κώδικα· μην εκτελείτε επαναλαμβανόμενες δοκιμές εικασιών στον ενεργό helper και μην εκτυπώνετε ανακτημένα μυστικά.

Στο OpenBSD, ένας προσαρμοσμένος reader set-user-ID που δέχεται pathname επιλεγμένο από τον καλούντα μπορεί να εκθέσει αρχεία στο `/var/backups`, αν η effective identity του έχει δικαίωμα ανάγνωσης και επιστρέφει τα περιεχόμενά τους στον καλούντα. Το [`changelist(5)` του OpenBSD](https://man.openbsd.org/changelist.5) περιγράφει αντίγραφα `.current` και `.backup` των διαμορφωμένων διαδρομών, αλλά οι εγγραφές με πρόθεμα `+` αποθηκεύουν checksums SHA-256 αντί για περιεχόμενα αρχείων· ο κατάλογος backup θα πρέπει να ανήκει στον root και να έχει mode `0700`. Ένας κανόνας [`unveil` για ανάγνωση](https://man.openbsd.org/unveil.2) του helper για το `/var` μπορεί να επιτρέψει πρόσβαση κάτω από αυτή τη διαδρομή, αλλά δεν παρέχει ούτε αποδεικνύει από μόνος του πρόσβαση στα αρχεία. Επιβεβαιώστε το πραγματικό effective UID, το δικαίωμα εκτέλεσης για τον τρέχοντα χρήστη, το αποδεκτό path, την ύπαρξη και τα περιεχόμενα του backup, καθώς και τυχόν ανεξάρτητες απαιτήσεις ελέγχου ταυτότητας, προτού ισχυριστείτε ότι υπάρχει κλιμάκωση. Η παθητική απαρίθμηση πρέπει να αναφέρει τον helper και τα metadata της διαδρομής, όχι να εκτελεί τον reader ή να εκτυπώνει δεδομένα backup.

Ένα προσαρμοσμένο SUID πρόγραμμα που ελέγχει pathname επιλεγμένο από τον καλούντα με [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) και ανοίγει το pathname αργότερα μπορεί να υποστεί race με αλλαγή αρχείου ή symlink σε κατάλογο εγγράψιμο από τον καλούντα. Ο έλεγχος αφορά το προηγούμενο αντικείμενο, ενώ μια μεταγενέστερη [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) μπορεί να επιλύσει διαφορετικό αντικείμενο. Επιβεβαιώστε ότι ο helper εκτελείται με αυξημένη effective identity, ότι μια κατά τα άλλα προσβάσιμη διαδρομή κώδικα διαβάζει το επιλεγμένο αρχείο και ότι ο καλών μπορεί να αντικαταστήσει το pathname μεταξύ ελέγχου και ανοίγματος· το bit SUID, ένας εγγράψιμος κατάλογος ή μια συμβολοσειρά `stat` από μόνα τους δεν αποδεικνύουν τίποτε από αυτά. Για να υπάρχει διαδρομή αποκάλυψης, απαιτείται επίσης ορατή έξοδος ή προορισμός αναγνώσιμος από τον καλούντα. Εξετάστε offline το binary και τα metadata της διαδρομής· μην επιχειρείτε race στον ενεργό helper κατά την παθητική απαρίθμηση.

Εφαρμόστε τον ίδιο έλεγχο εξαρτήσεων και στα SGID wrappers. Ένα wrapper που εκτελεί shell ή helper μέσω απόλυτης διαδρομής μπορεί και πάλι να είναι επισφαλές αν χρήστης με χαμηλότερα δικαιώματα μπορεί να αντικαταστήσει αυτό το αρχείο· ο κώδικας που εκκινείται μπορεί να κληρονομήσει το effective group του wrapper. Ελέγξτε την ακριβή διαδρομή που καλείται, τα δικαιώματα εγγραφής σε αυτήν (συμπεριλαμβανομένων των ACL), το effective group του wrapper και αν αποβάλλει δικαιώματα πριν εκκινήσει τη θυγατρική διεργασία. Ένας interpreter μπορεί επίσης να απορρίψει κληρονομημένα effective IDs, επομένως διακρίνετε έναν υποψήφιο για έλεγχο από μια αποδεδειγμένη μετάβαση. Ένα εγγράψιμο shell αλλού στο host από μόνο του δεν αποδεικνύει ότι το προνομιούχο wrapper το καλεί.

### Προνομιούχα wrappers που περνούν SQL στο SQLite CLI

Αν ένα προσαρμοσμένο πρόγραμμα SUID περνά SQL ελεγχόμενο από τον χρήστη στο **πρόγραμμα γραμμής εντολών `sqlite3`**, εξετάστε την ακριβή εντολή και την effective identity προτού θεωρήσετε το query μόνο για ανάγνωση. Η συνάρτηση SQL `edit()` του CLI καλεί editor (από το δεύτερο όρισμά της ή το `VISUAL`), ενώ η συνάρτηση SQL `load_extension()` μπορεί να φορτώσει shared library όταν είναι ενεργοποιημένη η φόρτωση extensions. Αυτές είναι πιθανές διαδρομές εκτέλεσης κώδικα με την identity της διεργασίας CLI, ακόμη κι αν το wrapper ορίζει σταθερό `PATH` ή χρησιμοποιεί απόλυτη διαδρομή `sqlite3`. Το SQL πρέπει πράγματι να φτάνει σε αυτές τις συναρτήσεις και το CLI να διατηρεί τη σχετική δυνατότητα· το να εντοπιστεί απλώς το `sqlite3` σε binary ή στο host δεν αποτελεί ένδειξη κλιμάκωσης. Η **βιβλιοθήκη** SQLite απενεργοποιεί από προεπιλογή τη φόρτωση extensions, οπότε διακρίνετέ την από το CLI. Όταν μια προνομιούχα εφαρμογή πρέπει να επεξεργαστεί μη έμπιστο SQL, η λειτουργία CLI `--safe` του SQLite απενεργοποιεί την `edit()`, την `load_extension()` και άλλες συναρτήσεις με παρενέργειες. Δείτε την [τεκμηρίωση SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), την [τεκμηρίωση safe mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) και την [τεκμηρίωση φόρτωσης extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Προνομιούχοι file readers που τροφοδοτούν verbose client

Ένα προσαρμοσμένο wrapper SUID/SGID μπορεί να ελέγχει την πρόσβαση σε pathname επιλεγμένο από τον καλούντα και μετά να περνά αυτό το αρχείο σε άλλη εντολή. Εξετάστε την effective identity τόσο κατά τον έλεγχο πρόσβασης όσο και κατά το μεταγενέστερο άνοιγμα, επιλύστε τυχόν στοιχεία `../` σε σχέση με τον πραγματικό βασικό κατάλογο και ελέγξτε πώς χειρίζεται το child μη έγκυρη είσοδο. Αν ένας database client διαβάζει ιδιωτικό αρχείο ως SQL με verbose έξοδο, μπορεί να επαναλάβει τα περιεχόμενα του αρχείου σε μηνύματα σφάλματος, ακόμη κι αν η SQL δεν είναι έγκυρη. Πρόκειται για αποκάλυψη μεταξύ χρηστών μόνο όταν το child μπορεί να διαβάσει αρχείο που ο καλών δεν μπορεί, ο καλών μπορεί να επιλέξει αυτό το αρχείο μέσω του wrapper και η έξοδος είναι ορατή· η παρουσία της συμβολοσειράς `mysql` ή κάποιου άλλου client από μόνη της δεν αποδεικνύει καμία από αυτές τις συνθήκες.

### Διαδρομή αναζήτησης του Netdata `ndsudo`

Το [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) επηρέασε ορισμένα builds του Netdata `ndsudo`. Ο SUID helper που ανήκει στον root αναζητούσε τις επιτρεπόμενες εξωτερικές εντολές του μέσω `PATH` που παρείχε ο καλών. Εξετάστε έναν εγκατεστημένο helper, ακόμη κι αν βρίσκεται έξω από το συνηθισμένο `PATH` του καλούντος, μόνο όταν ο τρέχων λογαριασμός μπορεί να τον εκτελέσει. Επιβεβαιώστε τον ιδιοκτήτη του, το bit SUID, την πρόσβαση εκτέλεσης (συμπεριλαμβανομένων των παραχωρήσεων group/ACL), το εγκατεστημένο build και την κατάσταση επιδιόρθωσης από τον προμηθευτή, καθώς και το αν τα `NoNewPrivs` ή ένα mount `nosuid` εμποδίζουν την αλλαγή identity. Το Netdata αναφέρει τα διορθωμένα builds `v1.45.3` και `v1.45.0-169`· τα backports διανομών χρειάζονται ξεχωριστή επιβεβαίωση. Η έκδοση του dashboard ή η απλή παρουσία του `ndsudo` δεν αρκούν ως ένδειξη προσβάσιμης κλιμάκωσης. Το ζήτημα διαδρομής απαιτεί επίσης ο helper να επιλύει εξωτερική εντολή μέσω τοποθεσίας που ελέγχει ο καλών.

### Όριο προνομίων του Firejail join

Το [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) επηρέασε την προνομιούχα λογική `--join` του Firejail: ένας ειδικά διαμορφωμένος στόχος join μπορούσε να κάνει τον helper setuid-root να δεχτεί mount namespace ελεγχόμενο από τον επιτιθέμενο και να αντιγράψει μη ασφαλή κατάσταση ασφαλείας. Για παθητική διαλογή, επιβεβαιώστε ότι η **τρέχουσα identity μπορεί να εκτελέσει** ένα root-owned setuid binary του Firejail, ότι το setuid είναι ενεργό στο mount και στο πλαίσιο της διεργασίας του και ότι το εγκατεστημένο build δεν περιλαμβάνει τη διόρθωση. Το upstream διόρθωσε το ζήτημα στην έκδοση [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70)· τα πακέτα διανομών μπορεί να έχουν [backport της διόρθωσης](https://github.com/netblue30/firejail/issues/5191), ενώ εξακολουθούν να εμφανίζουν παλαιότερη έκδοση. Αυτές οι προϋποθέσεις προσδιορίζουν υποψήφιο για έλεγχο, όχι επιτυχημένο join ή root shell. Μην κατασκευάζετε ψεύτικο jail και μην εκτελείτε `--join` κατά την απαρίθμηση.

### Δικαιώματα logfile του GNU Screen

Το [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) αφορούσε το Screen 4.5.0 που άνοιγε logfile επιλεγμένο από τον καλούντα με αυξημένα δικαιώματα. Ένα binary `screen` ή έκδοση με επίθημα στη λίστα SUID είναι απλώς ένδειξη για έλεγχο: επιβεβαιώστε ότι ανήκει στον root, ότι η εκτέλεση SUID είναι ενεργή για τον τρέχοντα χρήστη, ποιο build είναι εγκατεστημένο και αν η διανομή έχει εφαρμόσει διόρθωση, καθώς και τη συμπεριφορά του logfile που επηρεάζεται. Το [Debian διόρθωσε το πακέτο 4.5.0 με backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), επομένως μια συμβολοσειρά έκδοσης ή ένα όνομα αρχείου από μόνα τους δεν αποδεικνύουν έκθεση. Μην δημιουργείτε logfile ως συνήθη δοκιμή κατά την απαρίθμηση.

Το [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) επηρέασε τον προνομιούχο helper κλειδώματος αλληλογραφίας S-nail, όταν ένα στοιχείο διαδρομής ελεγχόμενο από τον καλούντα μπορούσε να διασχίσει καταλόγους και να οδηγήσει σε εγγραφή αυθαίρετου αρχείου. Εξετάστε αν ο τρέχων χρήστης μπορεί να εκτελέσει εγκατεστημένο setuid helper που ανήκει στον root, αν η ταυτότητα setuid είναι ενεργή βάσει της πολιτικής mount και διεργασίας και ποιο ακριβώς build πακέτου και διόρθωση προμηθευτή χρησιμοποιούνται. Η [ενημέρωση ασφαλείας του Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) αναφέρει backport διόρθωσης για το πακέτο της έκδοσης 16.04, επομένως μια έκδοση που μοιάζει με upstream δεν αρκεί για συμπέρασμα. Η παρουσία του helper δεν αποδεικνύει ότι είναι προσβάσιμη η επηρεαζόμενη διαδρομή ή ότι η εγγραφή αρχείου οδηγεί σε εκτέλεση ως root· εξετάστε metadata και κατάσταση πακέτου χωρίς να εκτελέσετε τον helper ή να επιχειρήσετε το race κατά την απαρίθμηση.

### Καθαρισμός snap-confine και tmpfiles

Το CVE-2026-3888 είναι ένα race που αφορά το προνομιούχο `snap-confine` και τον καθαρισμό του `/tmp` από το systemd-tmpfiles. Ένας παθητικός έλεγχος μπορεί να διαπιστώσει αν το `snap-confine` έχει bit setuid ή file capabilities, να συγκρίνει το εγκατεστημένο πακέτο `snapd` με τη διορθωμένη έκδοση για τη συγκεκριμένη **έκδοση Ubuntu** και να εξετάσει τον ενεργό κανόνα ηλικίας για το `/tmp` και το timer καθαρισμού. Ένα πακέτο και ένας κανόνας που ταιριάζουν αποτελούν προϋποθέσεις, όχι απόδειξη ότι το race είναι προσβάσιμο: σημασία έχουν επίσης η κατάσταση του timer κατά την εκτέλεση, η διάταξη snap, τα backports πακέτων και οι παρακάμψεις κανόνων. Οι παλαιότερες εκδόσεις μπορεί να απαιτούν μη προεπιλεγμένη διαμόρφωση. Μην εκτελείτε δοκιμή race κατά τη συνήθη απαρίθμηση. Δείτε την [καταχώριση CVE του Ubuntu](https://ubuntu.com/security/CVE-2026-3888) για την κατάσταση πακέτων ανά έκδοση και την [ενημέρωση ασφαλείας της Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) για την αλληλεπίδραση των στοιχείων.

## Εξετάστε ACL και ευαίσθητες διαδρομές

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ένας εγγράψιμος γονικός κατάλογος μπορεί να επιτρέψει την αντικατάσταση, ακόμη κι όταν το ίδιο το αρχείο ανήκει στον root. Ένα ACL μπορεί να παρέχει διακριτικά πρόσβαση σε ένα sudoers drop-in, service unit, cron script, library path ή credential file. Ελέγξτε τόσο το ACL όσο και ολόκληρη τη διαδρομή. Αν είναι δυνατές αυθαίρετες εγγραφές σε αρχεία με προνόμια, ακολουθήστε το [Arbitrary File Write to Root](write-to-root.md)· για περιπτώσεις ρυθμίσεων linker και preload, δείτε το παράδειγμα [`ld.so`](ld.so.conf-example.md). Αντιμετωπίστε εκτεθειμένα αντίγραφα ασφαλείας, αρχεία `.env`, ρυθμίσεις βάσεων δεδομένων, υλικό SSH και ιστορικό ως πιθανούς πόρους διαπιστευτηρίων, με την πρόσβαση να διέπεται από τα πραγματικά δικαιώματα κάθε αρχείου.
