# SUID, SGID, ACL e file sensibili

{{#include ../../banners/hacktricks-training.md}}

SUID e SGID modificano l’identità effettiva di un file eseguito; gli ACL possono concedere accessi che i normali bit di permesso mostrati da `ls -l` non indicano. Esamina entrambi quando un utente può leggere, scrivere o eseguire più di quanto suggeriscano i permessi apparenti del proprietario e del gruppo.

## Enumerare gli eseguibili privilegiati

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrati sugli eseguibili personalizzati o modificati di recente, sui proprietari insoliti e sui file che si trovano su mount scrivibili. Un mount `nosuid` può sopprimere il comportamento set-ID; le file capabilities sono un meccanismo di privilegio separato, descritto in [Linux capabilities](linux-capabilities.md). Confronta un binario sospetto con il pacchetto a cui appartiene e verifica cosa esegue, apre o carica con un’identità elevata.

Per un eseguibile SUID di proprietà di root che non conosci e che accetta input dal chiamante, esamina offline una copia del binario per individuare una gestione degli argomenti vulnerabile a problemi di memoria e il percorso del codice che la raggiunge. Registra il comportamento degli ID effettivi e le mitigazioni, come stack canary, memoria non eseguibile, codice indipendente dalla posizione e randomizzazione degli indirizzi. Il nome di una funzione insicura o l’assenza di una mitigazione sono solo spunti per l’analisi: la possibilità di sfruttamento dipende dai limiti effettivi dell’input, dal flusso di controllo raggiungibile e dall’identità effettiva al momento dell’errore. Durante un’enumerazione passiva, non inviare argomenti lunghi all’eseguibile privilegiato in uso solo per verificare se causa un crash.

Anche un programma SUID noto può essere sostituito o contenere una backdoor. Una data di modifica recente è uno spunto, non una prova: per un **binario sospetto specifico appartenente a un pacchetto**, individua il pacchetto proprietario e confronta il file installato con i metadati del pacchetto, anziché verificare ogni pacchetto durante l’enumerazione di routine:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` verifica i contenuti dei file solo quando il database dei pacchetti registra un checksum; RPM confronta anche metadati come modalità e proprietario. Concentrati sulle discrepanze dell’**eseguibile privilegiato stesso**: le installazioni ridotte possono segnalare documentazione o file di localizzazione mancanti altrove nello stesso pacchetto. Confronta un eseguibile sospetto con un pacchetto del vendor attendibile e controlla esattamente il codice modificato. Modifiche locali legittime, checksum assenti e metadati dei pacchetti compromessi limitano ciò che ciascun comando può dimostrare. Nell’ambito del triage passivo, non eseguire né il programma SUID sospetto né uno script di verifica dei pacchetti. Consulta il [manuale di verifica di dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) e il [manuale di verifica di RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programma SUID che richiama una shell, un comando relativo o una libreria da un percorso scrivibile può oltrepassare un confine di fiducia. Consulta [abuso di librerie condivise e linker SUID](suid-shared-library-and-linker-abuse.md), le [indicazioni su PATH](../linux-basics/linux-environment-variables.md#path) e la [spiegazione degli user ID](../user-information/euid-ruid-suid.md). Per le note escape note e specifiche di un comando, consulta [GTFOBins](https://gtfobins.github.io/) verificando che il binario e l’invocazione corrispondano esattamente a quelli consentiti sull’host.

Per un eseguibile set-user-ID, distingui lo **UID reale** del chiamante dall’**UID effettivo** del proprietario del file: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) lascia invariato l’UID reale e, dopo un eventuale cambio set-ID, copia l’UID effettivo nell’UID salvato. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) esegue il comando tramite `/bin/sh -c`; la shell selezionata da quel percorso determina se un processo figlio conserva la propria identità effettiva. In particolare, le [regole della modalità privilegiata di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) ripristinano l’UID effettivo all’UID reale quando Bash si avvia senza `-p` e i due UID sono diversi. Controlla le modifiche effettive agli UID dell’helper e l’invocazione del processo figlio, oltre al proprietario, ai permessi di esecuzione, all’opzione di mount `nosuid` e allo stato di `no_new_privs` del processo. Il bit SUID o una chiamata a una shell, da soli, non dimostrano che sia possibile ottenere un’identità con privilegi superiori.

Un `jjs` SUID insolito, di proprietà di root, merita un controllo separato dell’accesso ai file se l’utente corrente può eseguirlo. Il tool legacy Nashorn può accedere alle API Java per i file anche quando una shell avviata come processo figlio perde l’UID effettivo; prima di considerarlo una lettura o scrittura privilegiata, verifica il comportamento della JVM installata, l’identità effettiva dell’operazione sul file e le impostazioni `nosuid`/`no_new_privs`. [Oracle ha rimosso `jjs` in JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); il percorso installato potrebbe comunque riferirsi a una build precedente o distribuita separatamente. [GTFOBins documenta le API per i file](https://gtfobins.org/gtfobins/jjs/), ma i suoi esempi con sudo non dimostrano il comportamento SUID per ogni build. Non invocare il tool durante l’enumerazione passiva.

Un eseguibile `gosu` SUID, di proprietà di root e accessibile a un utente con privilegi inferiori, merita un controllo: la sua interfaccia documentata accetta un utente target e un comando, ma nel normale uso dei container viene avviato come root per abbassare i privilegi. Verifica il comportamento SUID della build installata, l’identità effettiva e la mappatura degli user namespace, oltre a `nosuid` e `no_new_privs`; essere root in un container non implica esserlo sull’host. Il nome del file o il bit SUID, da soli, non dimostrano che il cambio di identità funzioni. Consulta l’[utilizzo upstream](https://github.com/tianon/gosu) e l’[avvertenza SUID del maintainer](https://github.com/tianon/gosu/issues/11). Non invocare l’helper durante l’inventario passivo.

Un wrapper di backup set-user-ID personalizzato potrebbe accettare un percorso scelto dal chiamante e interpolarlo in un comando di archiviazione passato a `system(3)`. Se il percorso non è tra virgolette nel comando costruito, la shell figlia può applicare [l’espansione della tilde usando `HOME`, i pattern per i nomi di percorso come `?` e `*` e la separazione dei comandi tramite newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); rifiutare solo i caratteri di punteggiatura più comuni con una denylist non rende letterale il percorso. Verifica il flusso esatto degli argomenti, l’ambiente ereditato, la shell figlia e l’identità effettiva, l’accesso al filesystem e se l’output dell’archiviazione è visibile al chiamante. Il bit SUID, una stringa relativa a un tool di archiviazione o il solo blocco del percorso letterale `/root` non dimostrano né la divulgazione di dati né l’esecuzione di codice. Esamina offline una copia del wrapper, invece di archiviare file privati o inviare input che causano un crash durante l’enumerazione passiva.

La [sostituzione di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) della shell, come `$(...)`, è un’altra possibile lacuna in una denylist di metacaratteri: anche un prefisso di comando consentito e fisso può passare un argomento successivo controllato dal chiamante a `/bin/sh -c`. Verifica offline le virgolette esatte, il parser e l’identità effettiva; non considerare una stringa `system()` o una denylist incompleta come prova di esecuzione.

Conta anche l’**albero dei processi chiamanti**. Un worker web può installare un filtro seccomp che limita le system call per il cambio di UID; [i filtri seccomp vengono ereditati dai processi figli e persistono dopo `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Per esempio, le direttive [mpm-itk `LimitUIDRange` e `LimitGIDRange` di Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) possono limitare le identità accessibili ai processi discendenti. `Seccomp: 2` in `/proc/self/status` indica la modalità del filtro, non la policy né se questo specifico helper possa ottenere l’identità del proprietario. Esamina insieme la catena di processi dell’invocazione effettiva e il filtro applicato, nonché le condizioni relative a SUID, mount e `no_new_privs`; una sessione di login separata potrebbe avere una policy diversa, ma richiede un proprio percorso di accesso valido.

Un eseguibile SUID personalizzato potrebbe invocare uno script Python separato e leggibile. Se usa effettivamente **Python 2**, [`input()` valuta l’espressione inserita](https://docs.python.org/2/library/functions.html#input); in Python 3, invece, `input()` restituisce testo. Prima di considerare la riga di codice un percorso di esecuzione, verifica l’identità effettiva del wrapper, il percorso e la versione dell’interprete, il percorso dello script e se l’input non attendibile raggiunge quella chiamata. Il bit set-ID sullo script stesso o una chiamata a `input()` senza il wrapper privilegiato non stabiliscono lo stesso confine. Durante l’enumerazione, esamina i percorsi referenziati dal binario e una porzione limitata del sorgente dello script senza eseguirlo.

Se un eseguibile SUID insolito è accompagnato da codice sorgente leggibile, confronta il numero di byte richiesto da ogni lettura di file controllata dal chiamante con la dimensione del buffer di destinazione e ispeziona i successivi controlli del flusso di esecuzione. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) memorizza gli elementi richiesti all’indirizzo fornito; non conosce la capacità dell’oggetto di destinazione. Una discrepanza di dimensioni è un indizio statico di un problema di sicurezza della memoria, non la prova di un’escalation di privilegi utilizzabile: verifica che il sorgente corrisponda al binario installato, che il chiamante possa fornire l’input, che l’esecuzione SUID sia effettiva in quel contesto e che il percorso pertinente sia raggiungibile. Esamina offline una porzione limitata del sorgente o una copia del binario, invece di inviare input che causano un crash al programma privilegiato durante l’enumerazione.

Un helper SUID personalizzato può divulgare un file protetto senza stamparne il contenuto. Se il chiamante sceglie sia un percorso sia un’espressione regolare e l’helper restituisce un conteggio visibile delle corrispondenze operando con il proprio UID effettivo, i test ancorati del prefisso possono formare un oracolo carattere per carattere. Verifica il proprietario dell’helper, il comportamento degli ID effettivi, i permessi di esecuzione, le restrizioni sui percorsi, la semantica delle espressioni regolari, la visibilità della risposta e l’esistenza di uno specifico file con privilegi superiori che il chiamante non possa altrimenti leggere. Il bit SUID o una stringa della libreria per le espressioni regolari, da soli, non dimostrano nessuno di questi passaggi. Durante l’enumerazione passiva, registra l’eseguibile insolito ed esamina offline una porzione limitata del disassemblato o del sorgente; non eseguire tentativi iterativi contro l’helper attivo né stampare i segreti recuperati.

Su OpenBSD, un lettore set-user-ID personalizzato che accetta un percorso scelto dal chiamante potrebbe esporre file in `/var/backups` se la sua identità effettiva può leggerli e restituisce il loro contenuto al chiamante. [`changelist(5)` di OpenBSD](https://man.openbsd.org/changelist.5) descrive le copie `.current` e `.backup` dei percorsi configurati, ma le voci con prefisso `+` memorizzano checksum SHA-256 anziché il contenuto dei file; la directory di backup dovrebbe essere di proprietà di root e avere modalità `0700`. Una regola di lettura [`unveil` per `/var`](https://man.openbsd.org/unveil.2) può consentire l’accesso sotto quel percorso, ma non concede né dimostra di per sé l’accesso ai file. Prima di dichiarare un’escalation, verifica l’UID effettivo, i permessi di esecuzione per l’utente corrente, il percorso accettato, l’esistenza e il contenuto del backup e qualsiasi requisito di autenticazione indipendente. L’enumerazione passiva dovrebbe riportare l’helper e i metadati del percorso, non invocare il lettore né stampare dati di backup.

Un programma SUID personalizzato che controlla un percorso scelto dal chiamante con [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) e apre il percorso in un secondo momento può subire una race in cui cambia un file o un symlink in una directory scrivibile dal chiamante. Il controllo si applica all’oggetto precedente, mentre una successiva [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) può risolverne un altro. Verifica che l’helper sia eseguibile con identità effettiva elevata, che un percorso del codice altrimenti raggiungibile legga il file selezionato e che il chiamante possa sostituire il percorso tra il controllo e l’apertura; il bit SUID, una directory scrivibile o una stringa `stat`, da soli, non dimostrano nessuno di questi elementi. Perché vi sia una divulgazione serve anche un output visibile o una destinazione leggibile dal chiamante. Esamina offline il binario e i metadati del percorso; non eseguire race contro l’helper attivo durante il triage passivo.

Applica lo stesso controllo delle dipendenze ai wrapper SGID. Un wrapper che avvia una shell o un helper tramite un percorso assoluto può comunque essere insicuro se un utente con privilegi inferiori può sostituire quel file; il codice avviato potrebbe ereditare il gruppo effettivo del wrapper. Controlla il percorso esatto invocato, i relativi permessi di scrittura (incluse le ACL), il gruppo effettivo del wrapper e se questo abbassa i privilegi prima di avviare il processo figlio. Anche un interprete potrebbe scartare gli ID effettivi ereditati, quindi distingui un elemento da esaminare da una transizione dimostrata. Una shell scrivibile altrove sull’host non dimostra da sola che un wrapper privilegiato la avvii.

### Wrapper privilegiati che passano SQL alla CLI SQLite

Se un programma SUID personalizzato passa SQL controllato dall’utente al **programma a riga di comando `sqlite3`**, controlla il comando esatto e l’identità effettiva prima di considerare la query di sola lettura. La funzione SQL `edit()` della CLI avvia un editor (specificato nel secondo argomento o in `VISUAL`), mentre la funzione SQL `load_extension()` può caricare una libreria condivisa se il caricamento delle estensioni è abilitato. Si tratta di potenziali percorsi di esecuzione di codice con l’identità del processo CLI, anche se il wrapper imposta `PATH` o usa un percorso assoluto per `sqlite3`. L’SQL deve effettivamente raggiungere queste funzioni e la CLI deve mantenere la funzionalità pertinente; trovare `sqlite3` nel binario o sull’host non è di per sé una prova di escalation. La **libreria** SQLite disabilita il caricamento delle estensioni per impostazione predefinita, quindi distinguila dalla CLI. Se un’applicazione privilegiata deve elaborare SQL non attendibile, la modalità `--safe` della CLI SQLite disabilita `edit()`, `load_extension()` e altre funzioni con effetti collaterali. Consulta la [documentazione della CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentazione della modalità sicura](https://www.sqlite.org/cli.html#the_safe_command_line_option) e la [documentazione sul caricamento delle estensioni](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lettori di file privilegiati che alimentano un client verboso

Un wrapper SUID/SGID personalizzato potrebbe controllare l’accesso a un percorso scelto dal chiamante e poi passare il file a un altro comando. Esamina l’identità effettiva sia durante il controllo dell’accesso sia durante la successiva apertura, risolvi eventuali componenti `../` rispetto alla directory base reale e verifica come il processo figlio gestisce input non valido. Se un client di database legge un file privato come SQL e produce output verboso, potrebbe ripetere il contenuto del file nei messaggi di errore anche se l’SQL non è valido. Si tratta di una divulgazione tra utenti solo se il processo figlio può leggere un file che il chiamante non può leggere, il chiamante può selezionare quel file tramite il wrapper e l’output è visibile; la presenza di `mysql` o di una stringa relativa a un altro client, da sola, non dimostra nessuna di queste condizioni.

### Percorso di ricerca di Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) ha interessato alcune build di Netdata `ndsudo`. L’helper SUID di proprietà di root cercava i comandi esterni consentiti usando un `PATH` fornito dal chiamante. Esamina un helper installato, anche se si trova fuori dal `PATH` abituale del chiamante, solo se l’account corrente può eseguirlo. Verifica il proprietario, il bit SUID, i permessi di esecuzione (inclusi quelli concessi tramite gruppo/ACL), la build installata e lo stato delle patch del vendor, nonché se `NoNewPrivs` o un mount `nosuid` impediscono il cambio di identità. Netdata indica come corrette le build `v1.45.3` e `v1.45.0-169`; i backport delle distribuzioni richiedono una verifica separata. La versione mostrata nella dashboard o la sola presenza di `ndsudo` non costituiscono prove sufficienti di un’escalation raggiungibile. Il problema del percorso richiede inoltre che l’helper risolva un comando esterno in una posizione controllata dal chiamante.

### Confine dei privilegi di Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ha interessato la logica privilegiata `--join` di Firejail: un target di join appositamente costruito poteva indurre l’helper setuid-root ad accettare un mount namespace controllato dall’attaccante e a copiare uno stato di sicurezza non sicuro. Nel triage passivo, verifica che l’**identità corrente possa eseguire** un binario Firejail setuid di proprietà di root, che setuid sia effettivo sul relativo mount e nel contesto del processo e che alla build installata manchi la correzione. Upstream ha corretto il problema nella [versione 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); i pacchetti delle distribuzioni potrebbero [aver incluso la correzione con un backport](https://github.com/netblue30/firejail/issues/5191) pur mostrando una versione precedente. Questi prerequisiti identificano un elemento da esaminare, non dimostrano un join riuscito o l’ottenimento di una shell root. Non creare un jail falso né invocare `--join` durante l’enumerazione.

### Permessi dei file di log di GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) riguardava Screen 4.5.0, che apriva con privilegi elevati un file di log scelto dal chiamante. Un binario `screen` o con il suffisso della versione presente nell’inventario SUID è solo un indizio da esaminare: verifica la proprietà di root, l’esecuzione SUID effettiva per l’utente corrente, la build installata e lo stato delle patch della distribuzione, oltre al comportamento interessato relativo ai file di log. [Debian ha corretto il pacchetto 4.5.0 con un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), quindi la stringa della versione o il solo nome del file non dimostrano l’esposizione. Non creare un file di log come test di routine durante l’enumerazione.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ha interessato l’helper privilegiato di S-nail per i lock della posta quando un componente del percorso controllato dal chiamante poteva attraversare directory e causare la scrittura arbitraria di un file. Verifica se l’utente corrente può eseguire un helper setuid installato e di proprietà di root, se l’identità setuid è effettiva in base ai criteri del mount e del processo e qual è la build esatta del pacchetto e la correzione del vendor. L’[avviso di sicurezza di Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indica una correzione con backport per il pacchetto 16.04, quindi una versione che sembra upstream non è conclusiva. La presenza dell’helper non dimostra che il percorso interessato sia raggiungibile o che la scrittura di un file consenta di eseguire codice come root; durante l’enumerazione, controlla i metadati e lo stato del pacchetto senza invocare l’helper né tentare la race.

### snap-confine e la pulizia di tmpfiles

CVE-2026-3888 è una race che coinvolge `snap-confine` privilegiato e la pulizia di `/tmp` da parte di systemd-tmpfiles. Un controllo passivo può verificare se `snap-confine` è setuid o dispone di file capabilities, confrontare il pacchetto `snapd` installato con la versione corretta per quella **release di Ubuntu** e ispezionare la regola effettiva sull’età dei file in `/tmp` e il timer di pulizia. Un pacchetto e una regola corrispondenti sono prerequisiti, non la prova che la race sia raggiungibile: contano anche lo stato runtime del timer, il layout degli snap, i backport dei pacchetti e le sovrascritture delle regole. Le release meno recenti potrebbero richiedere una configurazione non predefinita. Non eseguire un test della race durante l’enumerazione di routine. Consulta il [record CVE di Ubuntu](https://ubuntu.com/security/CVE-2026-3888) per lo stato dei pacchetti specifico per release e l’[advisory di Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) per l’interazione tra i componenti.

## Ispeziona le ACL e i percorsi sensibili

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Una directory padre scrivibile può consentire la sostituzione anche quando il file è di proprietà di root. Una ACL può concedere silenziosamente l’accesso a un drop-in di sudoers, un’unità di servizio, uno script cron, un percorso di librerie o un file di credenziali. Controlla sia l’ACL sia l’intero percorso. Se è possibile scrivere file privilegiati arbitrari, consulta [Arbitrary File Write to Root](write-to-root.md); per i casi relativi alla configurazione del linker e al preload, vedi l’[esempio di `ld.so`](ld.so.conf-example.md). Considera i backup esposti, i file `.env`, le configurazioni dei database, il materiale SSH e la cronologia come possibili fonti di credenziali; l’accesso dipende dai permessi effettivi di ciascun file.
