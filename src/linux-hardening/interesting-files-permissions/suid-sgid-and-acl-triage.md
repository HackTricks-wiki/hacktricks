# SUID, SGID, ACLs et fichiers sensibles

{{#include ../../banners/hacktricks-training.md}}

SUID et SGID modifient l’identité effective d’un fichier exécuté ; les ACLs peuvent accorder des accès que les bits de mode ordinaires de `ls -l` n’affichent pas. Vérifiez les deux lorsqu’un utilisateur peut lire, écrire ou exécuter davantage que ne le suggèrent les permissions apparentes du propriétaire et du groupe.

## Énumérer les exécutables privilégiés

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Concentrez-vous sur les exécutables personnalisés ou récemment modifiés, les propriétaires inhabituels et les fichiers situés sur des montages accessibles en écriture. Un montage `nosuid` peut désactiver le comportement set-ID ; les capacités de fichier constituent un mécanisme de privilèges distinct, décrit dans [Linux capabilities](linux-capabilities.md). Comparez un binaire suspect à son paquet et vérifiez ce qu’il exécute, ouvre ou charge avec une identité élevée.

Pour un exécutable SUID appartenant à root et que vous ne connaissez pas, s’il accepte des entrées de l’appelant, examinez hors ligne une copie du binaire afin de repérer une gestion non sécurisée de ses arguments en mémoire et le chemin de code qui y mène. Relevez le comportement des ID effectifs et les mesures d’atténuation, telles que les canaris de pile, la mémoire non exécutable, le code indépendant de la position et la randomisation des adresses. Le nom d’une fonction non sécurisée ou l’absence d’une mesure d’atténuation constitue seulement une piste à examiner : l’exploitabilité dépend des limites réelles des entrées, du flux de contrôle accessible et de l’identité effective au moment de la faute. N’envoyez pas de longs arguments à l’exécutable privilégié actif dans le seul but de provoquer un plantage pendant une énumération passive.

Un programme SUID bien connu peut lui-même avoir été remplacé ou piégé. Une date de modification récente est une piste, pas une preuve : pour un **binaire empaqueté spécifique et suspect**, identifiez son paquet propriétaire et comparez le fichier installé aux métadonnées du paquet, plutôt que de vérifier chaque paquet lors d’une énumération de routine :

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` vérifie le contenu des fichiers uniquement lorsque la base de données des paquets contient une somme de contrôle enregistrée ; RPM compare également les métadonnées, comme le mode et le propriétaire. Concentrez-vous sur une différence concernant **l’exécutable privilégié lui-même** : les installations minimales peuvent signaler des fichiers de documentation ou de langue manquants ailleurs dans le même paquet. Comparez l’exécutable suspect à un paquet fournisseur de confiance et examinez précisément le code modifié. Les modifications locales légitimes, les sommes de contrôle absentes et les métadonnées de paquets compromises limitent ce que ces commandes permettent de prouver. N’exécutez ni le programme SUID suspect ni un script de vérification de paquet dans le cadre d’un triage passif. Consultez le [manuel de vérification de dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) et le [manuel de vérification de RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Un programme SUID qui lance un shell, une commande relative ou une bibliothèque depuis un chemin accessible en écriture peut franchir une frontière de confiance. Consultez [Abus des bibliothèques partagées et de l’éditeur de liens SUID](suid-shared-library-and-linker-abuse.md), les [recommandations sur PATH](../linux-basics/linux-environment-variables.md#path) et l’[explication des user ID](../user-information/euid-ruid-suid.md). Pour connaître les contournements propres à certaines commandes, consultez [GTFOBins](https://gtfobins.github.io/) pour le binaire exact et l’invocation autorisée sur l’hôte.

Pour un exécutable set-user-ID, distinguez le **real UID** de l’appelant de l’**effective UID** du propriétaire du fichier : [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) ne modifie pas le real UID et copie l’effective UID dans le saved UID après tout changement lié au bit set-ID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) exécute sa commande via `/bin/sh -c` ; le shell sélectionné par ce chemin détermine si un processus enfant conserve son identité effective. En particulier, les [règles du mode privilégié de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) réinitialisent un effective UID différent au real UID lorsque Bash démarre sans `-p`. Vérifiez les changements d’UID réels de l’helper et son invocation des processus enfants, ainsi que son propriétaire, ses permissions d’exécution, l’option de montage `nosuid` et l’état `no_new_privs` du processus. Un bit SUID ou un appel au shell ne suffit pas à établir qu’une transition vers des privilèges supérieurs est possible.

Un `jjs` inhabituel appartenant à root et doté du bit SUID justifie un examen séparé de l’accès aux fichiers si l’utilisateur actuel peut l’exécuter. L’outil Nashorn historique peut accéder aux API Java de fichiers, même si un shell lancé comme processus enfant abandonne son effective UID ; vérifiez le comportement de la JVM installée, l’identité effective de l’opération sur le fichier et les paramètres `nosuid`/`no_new_privs` avant de considérer qu’il permet une lecture ou une écriture privilégiée. [Oracle a supprimé `jjs` dans JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html) ; un chemin installé peut toutefois correspondre à une version plus ancienne ou à une compilation distribuée séparément. [GTFOBins documente les API de fichiers](https://gtfobins.org/gtfobins/jjs/), mais ses exemples avec sudo ne démontrent pas le comportement SUID de toutes les compilations. N’invoquez pas l’outil pendant l’énumération passive.

Un exécutable `gosu` appartenant à root, doté du bit SUID et accessible à un utilisateur moins privilégié mérite un examen : son interface documentée accepte un utilisateur cible et une commande, mais son usage normal dans un conteneur consiste à le lancer en tant que root pour abandonner les privilèges. Vérifiez le comportement SUID de la compilation installée, l’identité effective et le mappage des user namespaces, ainsi que `nosuid` et `no_new_privs` ; être root dans un conteneur ne signifie pas être root sur l’hôte. Le nom de fichier ou le bit SUID ne prouve pas à lui seul qu’une transition fonctionne. Consultez [l’utilisation en amont](https://github.com/tianon/gosu) et [l’avertissement SUID du mainteneur](https://github.com/tianon/gosu/issues/11). N’invoquez pas l’helper pendant l’inventaire passif.

Un wrapper de sauvegarde personnalisé set-user-ID peut accepter un chemin choisi par l’appelant et l’interpoler dans une commande d’archivage transmise à `system(3)`. Si ce chemin n’est pas placé entre guillemets dans la commande construite, le shell enfant peut appliquer [l’expansion du tilde avec `HOME`, les motifs de chemin tels que `?` et `*`, et la séparation des commandes par nouvelle ligne](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) ; rejeter uniquement la ponctuation habituelle au moyen d’une denylist ne rend pas le chemin littéral. Vérifiez le flux exact des arguments, l’environnement hérité, le shell enfant et l’identité effective, l’accès au système de fichiers et la visibilité du résultat de l’archivage pour l’appelant. Le bit SUID, une chaîne désignant un outil d’archivage ou le seul blocage du chemin littéral `/root` ne prouvent ni divulgation ni exécution de code. Examinez une copie du wrapper hors ligne plutôt que d’archiver des fichiers privés ou d’envoyer des entrées provoquant un crash pendant l’énumération passive.

La [substitution de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) du shell, telle que `$(...)`, constitue une autre faille possible dans une denylist de métacaractères : même un préfixe de commande autorisé fixe peut transmettre un argument ultérieur contrôlé par l’appelant à `/bin/sh -c`. Vérifiez hors ligne le guillemetage exact, l’analyseur et l’identité effective ; ne considérez pas une chaîne `system()` ou une denylist incomplète comme une preuve d’exécution.

L’**arbre des processus appelants** compte également. Un worker web peut installer un filtre seccomp qui restreint les appels système changeant l’UID ; les [filtres seccomp sont transmis aux processus enfants et persistent après `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Par exemple, les directives [`LimitUIDRange` et `LimitGIDRange` de mpm-itk pour Apache](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) peuvent limiter les identités accessibles aux descendants. La valeur `Seccomp: 2` dans `/proc/self/status` indique le mode filtre, pas la politique appliquée ni la capacité de cet helper à obtenir l’identité de son propriétaire. Examinez ensemble l’ascendance de l’invocation réelle, son filtre effectif et les conditions SUID, de montage et `no_new_privs` ; une session de connexion distincte peut être soumise à une autre politique, mais nécessite son propre moyen d’accès valide.

Un exécutable SUID personnalisé peut invoquer un script Python distinct et lisible. S’il utilise réellement **Python 2**, [`input()` évalue l’expression saisie](https://docs.python.org/2/library/functions.html#input) ; en Python 3, `input()` renvoie du texte. Vérifiez l’identité effective du wrapper, le chemin et la version de l’interpréteur, le chemin du script et si une entrée non fiable atteint cet appel avant de considérer cette ligne du code source comme une voie d’exécution. Le bit set-ID sur le script seul ou un appel à `input()` sans wrapper privilégié ne constitue pas la même frontière. Examinez les chemins référencés par le binaire et une portion limitée du code source du script sans l’exécuter pendant l’énumération.

Si le code source lisible accompagne un exécutable SUID inhabituel, comparez le nombre d’octets demandé pour chaque lecture de fichier contrôlée par l’appelant à la taille du buffer de destination et examinez les vérifications ultérieures du flux de contrôle. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) stocke les éléments demandés à l’adresse fournie ; il ne connaît pas la capacité de l’objet de destination. Une différence de taille est un indice statique de problème de sécurité mémoire, pas la preuve d’une escalade de privilèges exploitable : confirmez que le code source correspond au binaire installé, que l’appelant peut fournir l’entrée, que l’exécution SUID est effective dans ce contexte et que le chemin concerné est atteignable. Examinez hors ligne une copie limitée du code source ou du binaire plutôt que d’envoyer des entrées provoquant un crash au programme privilégié pendant l’énumération.

Un helper SUID personnalisé peut divulguer un fichier protégé sans en afficher le contenu. Si l’appelant choisit à la fois un chemin et une expression régulière, et que l’helper renvoie un nombre de correspondances visible sous son effective UID, des tests de préfixe ancrés peuvent former un oracle caractère par caractère. Vérifiez le propriétaire de l’helper, son comportement vis-à-vis de l’effective ID, les permissions d’exécution, les restrictions de chemin, la sémantique de l’expression régulière, la visibilité de la réponse et l’existence d’un fichier précis, accessible à des privilèges supérieurs, que l’appelant ne peut pas lire autrement. Un bit SUID ou une chaîne désignant une bibliothèque d’expressions régulières ne prouve aucun de ces éléments. Pendant l’énumération passive, consignez l’exécutable inhabituel et examinez hors ligne un désassemblage ou une copie limitée du code source ; ne lancez pas de tentatives répétées contre l’helper en production et n’affichez pas les secrets récupérés.

Sur OpenBSD, un lecteur personnalisé set-user-ID qui accepte un chemin choisi par l’appelant peut exposer des fichiers sous `/var/backups` si son identité effective peut les lire et s’il renvoie leur contenu à l’appelant. Le [`changelist(5)` d’OpenBSD](https://man.openbsd.org/changelist.5) décrit les copies `.current` et `.backup` des chemins configurés, mais les entrées préfixées par `+` stockent des sommes de contrôle SHA-256 plutôt que le contenu des fichiers ; le répertoire de sauvegarde doit appartenir à root et être en mode `0700`. Une [règle de lecture `unveil`](https://man.openbsd.org/unveil.2) de l’helper pour `/var` peut autoriser l’accès sous ce chemin, mais n’accorde ni ne prouve à elle seule l’accès aux fichiers. Confirmez l’effective UID réel, les permissions d’exécution pour l’utilisateur actuel, les chemins acceptés, l’existence et le contenu des sauvegardes, ainsi que toute exigence d’authentification indépendante avant de conclure à une escalade. L’énumération passive doit consigner l’helper et les métadonnées des chemins, et non invoquer le lecteur ou afficher les données de sauvegarde.

Un programme SUID personnalisé qui vérifie un chemin choisi par l’appelant avec [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), puis ouvre le chemin plus tard, peut subir une course si un fichier ou un lien symbolique est modifié dans un répertoire accessible en écriture par l’appelant. La vérification s’applique à l’objet précédent, tandis qu’un [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) ultérieur peut résoudre un autre objet. Confirmez que l’helper est exécutable avec une identité effective élevée, qu’un chemin de code accessible lit le fichier choisi et que l’appelant peut remplacer le chemin entre la vérification et l’ouverture ; un bit SUID, un répertoire accessible en écriture ou la présence de la chaîne `stat` ne prouve aucun de ces éléments. Une sortie visible ou une destination lisible par l’appelant est également nécessaire pour qu’il y ait divulgation. Examinez hors ligne le binaire et les métadonnées du chemin ; ne tentez pas de provoquer une course contre l’helper en production pendant l’énumération passive.

Appliquez le même examen des dépendances aux wrappers SGID. Un wrapper qui lance un shell ou un helper par chemin absolu peut tout de même être dangereux si un utilisateur moins privilégié peut remplacer ce fichier ; le code lancé peut hériter de l’effective group du wrapper. Vérifiez le chemin exact invoqué, ses permissions d’écriture (ACL comprises), le groupe effectif du wrapper et s’il abandonne ses privilèges avant de lancer le processus enfant. Un interpréteur peut également abandonner les effective IDs hérités : distinguez donc un élément à examiner d’une transition démontrée. La présence d’un shell accessible en écriture ailleurs sur l’hôte ne prouve pas à elle seule qu’un wrapper privilégié l’invoque.

### Wrappers privilégiés qui transmettent du SQL à la CLI SQLite

Si un programme SUID personnalisé transmet du SQL contrôlé par l’utilisateur au **programme en ligne de commande `sqlite3`**, examinez la commande exacte et l’identité effective avant de considérer la requête comme étant en lecture seule. La fonction SQL `edit()` de la CLI lance un éditeur (fourni comme deuxième argument ou par `VISUAL`), et sa fonction SQL `load_extension()` peut charger une bibliothèque partagée lorsque le chargement des extensions est activé. Ce sont des chemins potentiels d’exécution de code avec l’identité du processus CLI, même si le wrapper fixe `PATH` ou utilise un chemin absolu vers `sqlite3`. Le SQL doit réellement atteindre ces fonctions, et la CLI doit conserver la fonctionnalité concernée ; trouver simplement `sqlite3` dans un binaire ou sur l’hôte ne prouve pas une escalade. La **bibliothèque** SQLite désactive le chargement des extensions par défaut : distinguez-la de la CLI. Lorsqu’une application privilégiée doit traiter du SQL non fiable, le mode CLI `--safe` de SQLite désactive `edit()`, `load_extension()` et d’autres fonctions à effets de bord. Consultez la [documentation de la CLI SQLite](https://www.sqlite.org/cli.html#the_edit_sql_function), la [documentation du mode sécurisé](https://www.sqlite.org/cli.html#the_safe_command_line_option) et la [documentation sur le chargement des extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Lecteurs de fichiers privilégiés qui transmettent le contenu à un client verbeux

Un wrapper SUID/SGID personnalisé peut vérifier l’accès à un chemin choisi par l’appelant, puis transmettre le fichier à une autre commande. Examinez l’identité effective lors du contrôle d’accès et de l’ouverture ultérieure, résolvez les composants `../` à partir du véritable répertoire de base et vérifiez comment le processus enfant gère les entrées non valides. Si un client de base de données lit un fichier privé comme du SQL avec une sortie verbeuse, il peut réafficher le contenu du fichier dans les erreurs, même si le SQL est invalide. Il n’y a divulgation entre utilisateurs que si le processus enfant peut lire un fichier que l’appelant ne peut pas lire, que l’appelant peut sélectionner ce fichier via le wrapper et que la sortie lui est visible ; la présence de `mysql` ou d’une chaîne désignant un autre client ne prouve aucune de ces conditions.

### Chemin de recherche de Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) concernait certaines compilations de Netdata `ndsudo`. L’helper SUID appartenant à root recherchait ses commandes externes autorisées dans un `PATH` fourni par l’appelant. Examinez un helper installé, y compris s’il se trouve hors du `PATH` habituel de l’appelant, uniquement si le compte actuel peut l’exécuter. Confirmez son propriétaire, son bit SUID, les permissions d’exécution (y compris les droits accordés par un groupe ou une ACL), la compilation installée, l’application du correctif par le fournisseur, et si `NoNewPrivs` ou un montage `nosuid` bloque le changement d’identité. Netdata indique les compilations corrigées `v1.45.3` et `v1.45.0-169` ; les backports des distributions doivent être vérifiés séparément. La version du tableau de bord ou la simple présence de `ndsudo` ne suffit pas à démontrer qu’une escalade est possible. Le problème de chemin exige également que l’helper résolve une commande externe dans un emplacement contrôlé par l’appelant.

### Frontière de privilèges de Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) concernait la logique privilégiée `--join` de Firejail : une cible join spécialement conçue pouvait amener l’helper setuid-root à accepter un mount namespace contrôlé par l’attaquant et à copier un état de sécurité non sûr. Pour le triage passif, confirmez que **l’identité actuelle peut exécuter** un binaire Firejail appartenant à root et doté du bit setuid, que le setuid est effectif sur son montage et dans le contexte de son processus, et que la compilation installée ne contient pas le correctif. En amont, le problème a été corrigé dans [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) ; les paquets des distributions peuvent [inclure le correctif en backport](https://github.com/netblue30/firejail/issues/5191) tout en affichant une version plus ancienne. Ces conditions préalables en font un candidat à examiner, mais ne prouvent ni qu’une jonction réussit ni qu’un shell root est obtenu. Ne créez pas de faux jail et n’invoquez pas `--join` pendant l’énumération.

### Permissions du fichier journal de GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) concernait Screen 4.5.0 qui ouvrait un fichier journal choisi par l’appelant avec des privilèges élevés. Un binaire `screen` ou une version suffixée présent dans l’inventaire SUID constitue seulement un indice à examiner : confirmez qu’il appartient à root, que l’exécution SUID est effective pour l’utilisateur actuel, la compilation installée et l’état des correctifs de la distribution, ainsi que le comportement concerné du fichier journal. [Debian a corrigé son paquet 4.5.0 par un backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484) ; une chaîne de version ou un nom de fichier ne prouve donc pas à lui seul une exposition. Ne créez pas de fichier journal comme sonde d’énumération habituelle.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) concernait l’helper privilégié de verrouillage de courrier S-nail, lorsqu’un composant de chemin contrôlé par l’appelant pouvait traverser des répertoires et entraîner l’écriture d’un fichier arbitraire. Vérifiez si l’utilisateur actuel peut exécuter un helper setuid installé appartenant à root, si son identité setuid est effective compte tenu du montage et de la politique du processus, ainsi que la version exacte du paquet et le correctif du fournisseur. [L’avis de sécurité Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) indique un correctif rétroporté pour son paquet 16.04 ; une version ressemblant à celle d’origine ne permet donc pas de conclure. La présence de l’helper ne prouve pas que le chemin concerné est accessible ni qu’une écriture de fichier permet d’exécuter du code en tant que root ; examinez les métadonnées et l’état du paquet sans invoquer l’helper ni tenter de provoquer une course pendant l’énumération.

### Nettoyage de snap-confine et tmpfiles

CVE-2026-3888 est une course impliquant `snap-confine` privilégié et le nettoyage de `/tmp` par systemd-tmpfiles. Lors d’un examen passif, vérifiez si `snap-confine` est setuid ou possède des capacités de fichier, comparez le paquet `snapd` installé à la version corrigée pour cette **version d’Ubuntu**, et examinez la règle d’ancienneté effective de `/tmp` ainsi que le timer de nettoyage. Un paquet et une règle correspondants sont des conditions préalables, pas la preuve que la course est possible : l’état d’exécution du timer, la disposition de snap, les backports du paquet et les remplacements de règles comptent également. Les anciennes versions peuvent nécessiter une configuration non définie par défaut. Ne lancez pas de sonde de course lors d’une énumération de routine. Consultez la [fiche CVE Ubuntu](https://ubuntu.com/security/CVE-2026-3888) pour l’état des paquets par version et l’[avis Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) pour l’interaction entre les composants.

## Examiner les ACL et les chemins sensibles

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Un répertoire parent accessible en écriture peut permettre le remplacement d’un fichier, même si celui-ci appartient à root. Une ACL peut accorder discrètement l’accès à un fichier de configuration sudoers, une unité de service, un script cron, un chemin de bibliothèque ou un fichier d’identifiants. Vérifiez l’ACL et le chemin complet. Si des écritures arbitraires dans des fichiers privilégiés sont possibles, consultez [Arbitrary File Write to Root](write-to-root.md) ; pour les cas liés à la configuration du linker et au preload, voir l’[exemple `ld.so`](ld.so.conf-example.md). Considérez les sauvegardes exposées, les fichiers `.env`, les configurations de bases de données, les éléments SSH et l’historique comme des sources possibles d’identifiants ; l’accès dépend des permissions réelles de chaque fichier.
