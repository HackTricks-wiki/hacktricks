# SUID, SGID, ACLs και ευαίσθητα αρχεία

{{#include ../../banners/hacktricks-training.md}}

Τα SUID και SGID αλλάζουν την effective identity ενός εκτελέσιμου αρχείου· τα ACLs μπορούν να παραχωρούν πρόσβαση που δεν εμφανίζεται στα συνηθισμένα mode bits του `ls -l`. Ελέγξτε και τα δύο όταν ένας χρήστης μπορεί να διαβάζει, να γράφει ή να εκτελεί κάτι πέρα από όσα υποδηλώνουν τα δικαιώματα του owner και του group.

## Καταγραφή εκτελέσιμων αρχείων με αυξημένα δικαιώματα

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Εστιάστε σε προσαρμοσμένα ή πρόσφατα τροποποιημένα εκτελέσιμα, ασυνήθιστους κατόχους και αρχεία σε εγγράψιμα mounts. Ένα mount `nosuid` μπορεί να απενεργοποιήσει τη συμπεριφορά set-ID· οι δυνατότητες αρχείων είναι ξεχωριστός μηχανισμός προνομίων που περιγράφεται στο [Linux capabilities](linux-capabilities.md). Συγκρίνετε ένα ύποπτο binary με το αντίστοιχο package και ελέγξτε τι εκτελεί, ανοίγει ή φορτώνει με αυξημένη ταυτότητα.

Για ένα άγνωστο SUID εκτελέσιμο που ανήκει στον root και δέχεται είσοδο από τον καλούντα, εξετάστε offline ένα αντίγραφο του binary για μη ασφαλή ως προς τη μνήμη διαχείριση ορισμάτων και τη διαδρομή κώδικα που οδηγεί σε αυτήν. Καταγράψτε τη συμπεριφορά effective-ID και μέτρα προστασίας όπως stack canaries, μη εκτελέσιμη μνήμη, position-independent code και address randomization. Ένα μη ασφαλές όνομα συνάρτησης ή η απουσία μέτρου προστασίας αποτελούν μόνο αφορμή για έλεγχο: η δυνατότητα εκμετάλλευσης εξαρτάται από τα πραγματικά όρια εισόδου, τη ροή ελέγχου που είναι προσβάσιμη και την effective identity τη στιγμή του σφάλματος. Μην στέλνετε μεγάλα ορίσματα στο ενεργό προνομιούχο εκτελέσιμο απλώς για να ελέγξετε αν θα καταρρεύσει κατά την παθητική απαρίθμηση.

Ένα γνώριμο SUID πρόγραμμα μπορεί το ίδιο να έχει αντικατασταθεί ή να έχει κερκόπορτα. Ένας πρόσφατος χρόνος τροποποίησης είναι ένδειξη, όχι απόδειξη: για ένα **συγκεκριμένο ύποπτο packaged binary**, εντοπίστε το package στο οποίο ανήκει και συγκρίνετε το εγκατεστημένο αρχείο με τα metadata του package, αντί να επαληθεύετε κάθε package κατά τη συνήθη απαρίθμηση:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

Το `dpkg --verify` ελέγχει τα περιεχόμενα αρχείων μόνο όταν η βάση δεδομένων του πακέτου έχει καταγεγραμμένο checksum· το RPM συγκρίνει επίσης metadata, όπως τα δικαιώματα και τον κάτοχο. Εστιάστε σε ασυμφωνία στο **ίδιο το προνομιούχο εκτελέσιμο**: εγκαταστάσεις χωρίς ορισμένα αρχεία μπορεί να αναφέρουν έλλειψη τεκμηρίωσης ή αρχείων locale από άλλα σημεία του ίδιου πακέτου. Συγκρίνετε το ύποπτο εκτελέσιμο με ένα έμπιστο πακέτο του προμηθευτή και εξετάστε τον ακριβή κώδικα που άλλαξε. Οι νόμιμες τοπικές αλλαγές, η απουσία checksums και τα παραβιασμένα metadata του πακέτου περιορίζουν όσα αποδεικνύει οποιαδήποτε από τις δύο εντολές. Μην εκτελέσετε ούτε το ύποπτο SUID πρόγραμμα ούτε κάποιο script επαλήθευσης πακέτου στο πλαίσιο παθητικής διαλογής. Δείτε το [εγχειρίδιο επαλήθευσης του dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) και το [εγχειρίδιο επαλήθευσης του RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

Ένα SUID πρόγραμμα που εκκινεί shell, σχετική εντολή ή library από διαδρομή με δυνατότητα εγγραφής μπορεί να διασχίσει ένα όριο εμπιστοσύνης. Δείτε τα [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), τις [οδηγίες για το PATH](../linux-basics/linux-environment-variables.md#path) και την [επεξήγηση των user ID](../user-information/euid-ruid-suid.md). Για γνωστά escapes που αφορούν συγκεκριμένες εντολές, ελέγξτε το [GTFOBins](https://gtfobins.github.io/) για το ακριβές binary και την invocation που επιτρέπεται στο host.

Για ένα εκτελέσιμο με set-user-ID, ξεχωρίστε το **real UID** του καλούντος από το **effective UID** του ιδιοκτήτη του αρχείου: το [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) αφήνει το real UID αμετάβλητο και αντιγράφει το effective UID στο saved UID μετά από κάθε αλλαγή set-ID. Το [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) εκτελεί την εντολή μέσω του `/bin/sh -c`· το shell που επιλέγεται μέσω αυτής της διαδρομής επηρεάζει το αν μια child διεργασία διατηρεί την effective ταυτότητά της. Ειδικότερα, οι [κανόνες privileged mode του Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) επαναφέρουν ένα διαφορετικό effective UID στο real UID όταν το Bash ξεκινά χωρίς `-p`. Ελέγξτε τις αλλαγές UID του πραγματικού helper και την εκκίνηση child διεργασιών, καθώς και τον ιδιοκτήτη του, την πρόσβαση εκτέλεσης, τη ρύθμιση mount `nosuid` και την κατάσταση `no_new_privs` της διεργασίας. Ένα SUID bit ή μια κλήση shell από μόνα τους δεν αποδεικνύουν ότι είναι εφικτή η μετάβαση σε υψηλότερα προνόμια.

Ένα ασυνήθιστο root-owned SUID `jjs` αξίζει ξεχωριστό έλεγχο πρόσβασης σε αρχεία, αν ο τρέχων χρήστης μπορεί να το εκτελέσει. Το legacy εργαλείο Nashorn μπορεί να έχει πρόσβαση στα Java file APIs ακόμη κι όταν ένα shell που εκκινεί αποβάλλει το effective UID· επιβεβαιώστε τη συμπεριφορά της εγκατεστημένης JVM, την effective ταυτότητα της λειτουργίας αρχείου και τις ρυθμίσεις `nosuid`/`no_new_privs`, πριν το θεωρήσετε προνομιούχο read ή write. Η [Oracle αφαίρεσε το `jjs` στο JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)· μια εγκατεστημένη διαδρομή μπορεί να ανήκει σε παλαιότερο ή ξεχωριστά συσκευασμένο build. Το [GTFOBins τεκμηριώνει τα file APIs](https://gtfobins.org/gtfobins/jjs/), αλλά τα παραδείγματα sudo δεν τεκμηριώνουν συμπεριφορά SUID σε κάθε build. Μην εκτελέσετε το εργαλείο κατά την παθητική απαρίθμηση.

Ένα root-owned SUID εκτελέσιμο `gosu` που είναι προσβάσιμο σε χρήστη με χαμηλότερα προνόμια χρήζει ελέγχου: η τεκμηριωμένη διεπαφή του δέχεται χρήστη-στόχο και εντολή, αλλά η συνήθης χρήση του σε containers το εκκινεί ως root για να αποβάλει προνόμια. Επαληθεύστε τη συμπεριφορά SUID του εγκατεστημένου build, την effective ταυτότητα και την αντιστοίχιση user namespace, καθώς και τις ρυθμίσεις `nosuid` και `no_new_privs`· το root μέσα σε container δεν συνεπάγεται root στο host. Το όνομα αρχείου ή το SUID bit από μόνο του δεν αποδεικνύει ότι λειτουργεί η μετάβαση. Δείτε την [upstream χρήση](https://github.com/tianon/gosu) και την [προειδοποίηση SUID του maintainer](https://github.com/tianon/gosu/issues/11). Μην εκτελέσετε τον helper κατά την παθητική απογραφή.

Ένα custom set-user-ID backup wrapper μπορεί να δέχεται διαδρομή που επιλέγει ο καλών και να την παρεμβάλλει σε εντολή αρχειοθέτησης που περνά στο `system(3)`. Αν η διαδρομή δεν περικλείεται σε εισαγωγικά στην εντολή που δημιουργείται, το child shell μπορεί να εφαρμόσει [επέκταση tilde μέσω του `HOME`, μοτίβα διαδρομών όπως `?` και `*`, και διαχωρισμό εντολών με newline](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)· η απόρριψη μόνο ορισμένων γνωστών σημείων στίξης μέσω denylist δεν καθιστά τη διαδρομή κυριολεκτική. Επιβεβαιώστε την ακριβή ροή ορισμάτων, το κληρονομημένο περιβάλλον, το child shell και την effective ταυτότητα, την πρόσβαση στο filesystem και το αν η έξοδος του εργαλείου αρχειοθέτησης είναι ορατή στον καλούντα. Το SUID bit, μια συμβολοσειρά που αναφέρεται σε εργαλείο αρχειοθέτησης ή μόνο η απόρριψη της κυριολεκτικής διαδρομής `/root` δεν αποδεικνύουν ούτε αποκάλυψη δεδομένων ούτε εκτέλεση κώδικα. Εξετάστε offline ένα αντίγραφο του wrapper αντί να αρχειοθετήσετε ιδιωτικά αρχεία ή να στείλετε εισόδους που προκαλούν crash κατά την παθητική απαρίθμηση.

Η [υποκατάσταση εντολών](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) του shell, όπως `$(...)`, είναι ένα ακόμη πιθανό κενό σε denylist μεταχαρακτήρων: ακόμη και ένα σταθερό επιτρεπόμενο πρόθεμα εντολής μπορεί να περάσει αργότερα ένα όρισμα που ελέγχει ο καλών μέσω `/bin/sh -c`. Επαληθεύστε offline τα ακριβή εισαγωγικά, τον parser και την effective ταυτότητα· μην θεωρείτε μια συμβολοσειρά `system()` ή μια ελλιπή denylist απόδειξη εκτέλεσης.

Σημασία έχει επίσης το **δέντρο διεργασιών του καλούντος**. Ένας web worker μπορεί να εγκαταστήσει seccomp filter που περιορίζει τις system calls αλλαγής UID· τα [seccomp filters κληρονομούνται από τις child διεργασίες και επιβιώνουν από το `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Για παράδειγμα, οι οδηγίες Apache [mpm-itk `LimitUIDRange` και `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) μπορούν να περιορίσουν τις ταυτότητες που είναι προσβάσιμες από τις απογόνους διεργασίες. Η ένδειξη `Seccomp: 2` στο `/proc/self/status` δείχνει τη λειτουργία filter, όχι την πολιτική ή το αν ο συγκεκριμένος helper μπορεί να αποκτήσει την ταυτότητα του ιδιοκτήτη του. Εξετάστε μαζί την προέλευση της πραγματικής invocation και το effective filter, καθώς και τις συνθήκες SUID, mount και `no_new_privs`· μια ξεχωριστή login session μπορεί να έχει διαφορετική πολιτική, αλλά χρειάζεται δική της έγκυρη διαδρομή πρόσβασης.

Ένα custom SUID εκτελέσιμο μπορεί να καλεί ξεχωριστό, αναγνώσιμο Python script. Αν πράγματι χρησιμοποιεί **Python 2**, η [`input()` αξιολογεί την έκφραση που εισάγεται](https://docs.python.org/2/library/functions.html#input)· στην Python 3 η `input()` επιστρέφει κείμενο. Επιβεβαιώστε την effective ταυτότητα του wrapper, τη διαδρομή και την έκδοση του interpreter, τη διαδρομή του script και το αν μη έμπιστη είσοδος φτάνει σε αυτή την κλήση, πριν θεωρήσετε τη γραμμή του source code διαδρομή εκτέλεσης. Ένα set-ID bit στο ίδιο το script ή μια κλήση `input()` χωρίς προνομιούχο wrapper δεν συνιστούν το ίδιο όριο. Κατά την απαρίθμηση, εξετάστε τις διαδρομές που αναφέρονται στο binary και ένα περιορισμένο απόσπασμα του source χωρίς να το εκτελέσετε.

Αν ένα ασυνήθιστο SUID εκτελέσιμο συνοδεύεται από αναγνώσιμο source, συγκρίνετε τον αριθμό bytes που ζητά κάθε ανάγνωση αρχείου υπό τον έλεγχο του καλούντος με το μέγεθος του buffer-προορισμού και εξετάστε τους μεταγενέστερους ελέγχους της ροής εκτέλεσης. Η [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) αποθηκεύει τα στοιχεία που ζητήθηκαν στον δείκτη που της δίνεται· δεν γνωρίζει τη χωρητικότητα του αντικειμένου-προορισμού. Μια ασυμφωνία μεγέθους είναι ένδειξη για στατικό έλεγχο ασφάλειας μνήμης, όχι απόδειξη αξιοποιήσιμης κλιμάκωσης προνομίων: επιβεβαιώστε ότι το source αντιστοιχεί στο εγκατεστημένο binary, ότι ο καλών μπορεί να δώσει την είσοδο, ότι η εκτέλεση SUID είναι ενεργή σε αυτό το πλαίσιο και ότι η σχετική διαδρομή είναι προσβάσιμη. Εξετάστε offline ένα περιορισμένο αντίγραφο του source ή του binary αντί να στέλνετε εισόδους που προκαλούν crash στο προνομιούχο πρόγραμμα κατά την απαρίθμηση.

Ένας custom SUID helper μπορεί να αποκαλύψει ένα προστατευμένο αρχείο χωρίς να εμφανίσει τα περιεχόμενά του. Αν ο καλών επιλέγει τόσο τη διαδρομή όσο και μια regular expression, και ο helper επιστρέφει ορατό πλήθος αντιστοιχιών υπό το effective UID του, δοκιμές με αγκυρωμένα προθέματα μπορεί να λειτουργήσουν ως oracle χαρακτήρα προς χαρακτήρα. Επιβεβαιώστε τον ιδιοκτήτη του helper, τη συμπεριφορά effective-ID, την πρόσβαση εκτέλεσης, τους περιορισμούς διαδρομής, τη σημασιολογία της regex, την ορατότητα της απόκρισης και την ύπαρξη συγκεκριμένου αρχείου με υψηλότερα προνόμια που ο καλών δεν μπορεί διαφορετικά να διαβάσει. Ένα SUID bit ή μια συμβολοσειρά βιβλιοθήκης regex από μόνα τους δεν αποδεικνύουν αυτή τη ροή. Κατά την παθητική απαρίθμηση, καταγράψτε το ασυνήθιστο εκτελέσιμο και εξετάστε offline ένα περιορισμένο disassembly ή αντίγραφο του source· μην εκτελείτε διαδοχικές εικασίες στον ενεργό helper και μην εμφανίζετε ανακτημένα μυστικά.

Στο OpenBSD, ένας custom set-user-ID reader που δέχεται διαδρομή την οποία επιλέγει ο καλών μπορεί να εκθέσει αρχεία κάτω από το `/var/backups`, αν η effective ταυτότητά του μπορεί να τα διαβάσει και επιστρέφει τα περιεχόμενά τους στον καλούντα. Το [`changelist(5)` του OpenBSD](https://man.openbsd.org/changelist.5) περιγράφει αντίγραφα `.current` και `.backup` διαμορφωμένων διαδρομών, αλλά οι καταχωρίσεις με πρόθεμα `+` αποθηκεύουν checksums SHA-256 αντί για περιεχόμενα αρχείων· ο κατάλογος backup θα πρέπει να ανήκει στον root και να έχει mode `0700`. Ένας κανόνας [`unveil` για ανάγνωση](https://man.openbsd.org/unveil.2) του helper για το `/var` μπορεί να επιτρέψει πρόσβαση κάτω από αυτή τη διαδρομή, αλλά δεν παραχωρεί ούτε αποδεικνύει από μόνος του πρόσβαση σε αρχεία. Επιβεβαιώστε το πραγματικό effective UID, το δικαίωμα εκτέλεσης για τον τρέχοντα χρήστη, τη διαδρομή που γίνεται δεκτή, την ύπαρξη και τα περιεχόμενα του backup, καθώς και τυχόν ανεξάρτητες απαιτήσεις ταυτοποίησης, πριν ισχυριστείτε ότι υπάρχει κλιμάκωση προνομίων. Η παθητική απαρίθμηση πρέπει να καταγράφει τον helper και τα metadata της διαδρομής, όχι να εκτελεί τον reader ή να εμφανίζει δεδομένα backup.

Ένα custom SUID πρόγραμμα που ελέγχει μια διαδρομή την οποία επιλέγει ο καλών με [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) και ανοίγει τη διαδρομή αργότερα μπορεί να υποστεί race με αλλαγή αρχείου ή symlink σε κατάλογο όπου ο καλών έχει δυνατότητα εγγραφής. Ο έλεγχος αφορά το προηγούμενο αντικείμενο, ενώ μια μεταγενέστερη [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) μπορεί να επιλύσει διαφορετικό αντικείμενο. Επιβεβαιώστε ότι ο helper μπορεί να εκτελεστεί με αυξημένη effective ταυτότητα, ότι μια κατά τα άλλα προσβάσιμη διαδρομή κώδικα διαβάζει το επιλεγμένο αρχείο και ότι ο καλών μπορεί να αντικαταστήσει τη διαδρομή ανάμεσα στον έλεγχο και το άνοιγμα· ένα SUID bit, ένας κατάλογος με δυνατότητα εγγραφής ή μια συμβολοσειρά `stat` από μόνα τους δεν αποδεικνύουν τίποτε από αυτά. Για διαδρομή αποκάλυψης δεδομένων απαιτείται επίσης ορατή έξοδος ή προορισμός αναγνώσιμος από τον καλούντα. Εξετάστε offline το binary και τα metadata της διαδρομής· μην επιχειρείτε race με τον ενεργό helper κατά την παθητική απαρίθμηση.

Εφαρμόστε τον ίδιο έλεγχο εξαρτήσεων και σε SGID wrappers. Ένας wrapper που εκτελεί shell ή helper μέσω απόλυτης διαδρομής μπορεί και πάλι να είναι μη ασφαλής αν χρήστης με χαμηλότερα προνόμια μπορεί να αντικαταστήσει αυτό το αρχείο· ο εκκινούμενος κώδικας μπορεί να κληρονομήσει το effective group του wrapper. Ελέγξτε την ακριβή διαδρομή που καλείται, τα δικαιώματα εγγραφής σε αυτήν (συμπεριλαμβανομένων των ACL), το effective group του wrapper και το αν αποβάλλει προνόμια πριν εκκινήσει το child. Ένας interpreter μπορεί επίσης να απορρίψει κληρονομημένα effective ID, γι’ αυτό ξεχωρίστε έναν υποψήφιο για έλεγχο από μια αποδεδειγμένη μετάβαση. Η ύπαρξη writable shell σε άλλο σημείο του host από μόνη της δεν αποδεικνύει ότι ένας προνομιούχος wrapper το καλεί.

### Προνομιούχα wrappers που περνούν SQL στο SQLite CLI

Αν ένα custom SUID πρόγραμμα περνά SQL που ελέγχει ο χρήστης στο **πρόγραμμα γραμμής εντολών `sqlite3`**, εξετάστε την ακριβή εντολή και την effective ταυτότητα πριν θεωρήσετε το query μόνο για ανάγνωση. Η SQL function `edit()` του CLI εκκινεί έναν editor (από το δεύτερο όρισμά της ή το `VISUAL`), ενώ η SQL function `load_extension()` μπορεί να φορτώσει shared library όταν είναι ενεργοποιημένη η φόρτωση extensions. Αυτές είναι πιθανές διαδρομές εκτέλεσης κώδικα με την ταυτότητα της διεργασίας CLI, ακόμη κι αν ο wrapper ορίζει σταθερό `PATH` ή χρησιμοποιεί απόλυτη διαδρομή `sqlite3`. Το SQL πρέπει πράγματι να φτάνει σε αυτές τις functions και το CLI πρέπει να διατηρεί τη σχετική δυνατότητα· η απλή εύρεση του `sqlite3` σε binary ή στο host δεν αποτελεί ένδειξη κλιμάκωσης προνομίων. Η **library** του SQLite απενεργοποιεί τη φόρτωση extensions από προεπιλογή, οπότε ξεχωρίστε την από το CLI. Όταν μια προνομιούχα εφαρμογή πρέπει να επεξεργάζεται μη έμπιστο SQL, το `--safe` mode του SQLite CLI απενεργοποιεί τις `edit()`, `load_extension()` και άλλες functions με παρενέργειες. Δείτε την [τεκμηρίωση του SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), την [τεκμηρίωση safe mode](https://www.sqlite.org/cli.html#the_safe_command_line_option) και την [τεκμηρίωση φόρτωσης extensions](https://www.sqlite.org/loadext.html#loading_an_extension).

### Προνομιούχοι file readers που τροφοδοτούν verbose client

Ένας custom SUID/SGID wrapper μπορεί να ελέγχει την πρόσβαση σε διαδρομή που επιλέγει ο καλών και κατόπιν να περνά το αρχείο σε άλλη εντολή. Εξετάστε την effective ταυτότητα τόσο κατά τον έλεγχο πρόσβασης όσο και κατά το μεταγενέστερο άνοιγμα, επιλύστε τυχόν στοιχεία `../` σε σχέση με τον πραγματικό βασικό κατάλογο και ελέγξτε πώς χειρίζεται το child μη έγκυρη είσοδο. Αν ένας database client διαβάζει ένα ιδιωτικό αρχείο ως SQL με verbose έξοδο, μπορεί να εμφανίσει τα περιεχόμενά του στα errors ακόμη κι αν το SQL είναι άκυρο. Πρόκειται για αποκάλυψη μεταξύ χρηστών μόνο αν το child μπορεί να διαβάσει αρχείο που ο καλών δεν μπορεί, ο καλών μπορεί να επιλέξει αυτό το αρχείο μέσω του wrapper και η έξοδος είναι ορατή· η παρουσία του `mysql` ή συμβολοσειράς άλλου client από μόνη της δεν αποδεικνύει καμία από αυτές τις συνθήκες.

### Διαδρομή αναζήτησης του Netdata `ndsudo`

Το [CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) επηρέασε ορισμένα Netdata `ndsudo` builds. Ο root-owned SUID helper αναζητούσε τις επιτρεπόμενες εξωτερικές εντολές χρησιμοποιώντας `PATH` που παρείχε ο καλών. Εξετάστε έναν εγκατεστημένο helper, ακόμη κι αν βρίσκεται έξω από το συνηθισμένο `PATH` του καλούντος, μόνο όταν ο τρέχων λογαριασμός μπορεί να τον εκτελέσει. Επιβεβαιώστε τον ιδιοκτήτη του, το SUID bit, την πρόσβαση εκτέλεσης (συμπεριλαμβανομένων των δικαιωμάτων ομάδας/ACL), το εγκατεστημένο build και την κατάσταση των vendor patches, καθώς και το αν το `NoNewPrivs` ή ένα mount `nosuid` εμποδίζει την αλλαγή ταυτότητας. Το Netdata αναφέρει διορθωμένα builds `v1.45.3` και `v1.45.0-169`· τα backports διανομών χρειάζονται ξεχωριστή επιβεβαίωση. Η έκδοση που εμφανίζει το dashboard ή η απλή παρουσία του `ndsudo` δεν αρκεί ως ένδειξη προσβάσιμης κλιμάκωσης προνομίων. Το πρόβλημα διαδρομής απαιτεί επίσης ο helper να επιλύει μια εξωτερική εντολή μέσω τοποθεσίας που ελέγχει ο καλών.

### Όριο προνομίων του Firejail join

Το [CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) επηρέασε την προνομιούχα λογική `--join` του Firejail: ένας ειδικά διαμορφωμένος στόχος join μπορούσε να κάνει τον setuid-root helper να αποδεχτεί mount namespace ελεγχόμενο από επιτιθέμενο και να αντιγράψει μη ασφαλή κατάσταση ασφαλείας. Για παθητική διαλογή, επιβεβαιώστε ότι η **τρέχουσα ταυτότητα μπορεί να εκτελέσει** ένα root-owned setuid binary του Firejail, ότι το setuid είναι ενεργό στο mount του και στο πλαίσιο της διεργασίας του, και ότι το εγκατεστημένο build δεν περιλαμβάνει τη διόρθωση. Το upstream διόρθωσε το πρόβλημα στην [έκδοση 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70)· τα πακέτα διανομών μπορεί να το έχουν [διορθώσει με backport](https://github.com/netblue30/firejail/issues/5191), ενώ εξακολουθούν να εμφανίζουν παλαιότερη έκδοση. Αυτές οι προϋποθέσεις υποδεικνύουν περίπτωση για έλεγχο, όχι επιτυχημένο join ή root shell. Μην κατασκευάζετε fake jail και μην εκτελείτε `--join` κατά την απαρίθμηση.

### Δικαιώματα logfile του GNU Screen

Το [CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) αφορούσε το Screen 4.5.0 που άνοιγε logfile επιλεγμένο από τον καλούντα με αυξημένα προνόμια. Ένα binary `screen` ή έκδοση με επίθημα στην απογραφή SUID αποτελεί μόνο ένδειξη για έλεγχο: επιβεβαιώστε ότι ανήκει στον root, ότι η SUID εκτέλεση είναι ενεργή για τον τρέχοντα χρήστη, καθώς και το εγκατεστημένο build, την κατάσταση των patches της διανομής και τη σχετική συμπεριφορά του logfile. Το [Debian διόρθωσε το πακέτο 4.5.0 με backport](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), επομένως μια συμβολοσειρά έκδοσης ή ένα όνομα αρχείου από μόνα τους δεν αποδεικνύουν ευπάθεια. Μην δημιουργείτε logfile ως συνήθη δοκιμή απαρίθμησης.

Το [CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) επηρέασε τον προνομιούχο helper κλειδώματος αλληλογραφίας S-nail, όταν ένα path component που ελέγχει ο καλών μπορούσε να διασχίσει καταλόγους και να οδηγήσει σε αυθαίρετη εγγραφή αρχείου. Εξετάστε αν ο τρέχων χρήστης μπορεί να εκτελέσει εγκατεστημένο root-owned setuid helper, αν η setuid ταυτότητά του είναι ενεργή σύμφωνα με την πολιτική του mount και της διεργασίας, καθώς και το ακριβές build του πακέτου και τη διόρθωση του προμηθευτή. Η [ανακοίνωση ασφαλείας του Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) αναφέρει backport διόρθωσης για το πακέτο 16.04, επομένως μια έκδοση που φαίνεται να είναι upstream δεν αρκεί για ασφαλές συμπέρασμα. Η παρουσία του helper δεν αποδεικνύει ότι είναι προσβάσιμη η ευάλωτη διαδρομή ή ότι μια εγγραφή αρχείου οδηγεί σε εκτέλεση ως root· εξετάστε τα metadata και την κατάσταση του πακέτου χωρίς να εκτελέσετε τον helper ή να επιχειρήσετε το race κατά την απαρίθμηση.

### Καθαρισμός snap-confine και tmpfiles

Το CVE-2026-3888 είναι ένα race που αφορά το προνομιούχο `snap-confine` και τον καθαρισμό του `/tmp` από το systemd-tmpfiles. Ένας παθητικός έλεγχος μπορεί να διαπιστώσει αν το `snap-confine` έχει setuid ή file capabilities, να συγκρίνει το εγκατεστημένο πακέτο `snapd` με τη διορθωμένη έκδοση για τη συγκεκριμένη **έκδοση Ubuntu** και να εξετάσει τον ενεργό κανόνα ηλικίας για το `/tmp` και τον χρονοδιακόπτη καθαρισμού. Ένα πακέτο και ένας κανόνας που ταιριάζουν είναι προϋποθέσεις, όχι απόδειξη ότι είναι προσβάσιμο το race: σημασία έχουν επίσης η κατάσταση του timer κατά την εκτέλεση, η διάταξη του snap, τα backports του πακέτου και οι παρακάμψεις κανόνων. Παλαιότερες εκδόσεις μπορεί να απαιτούν μη προεπιλεγμένες ρυθμίσεις. Μην εκτελείτε δοκιμή race κατά τη συνήθη απαρίθμηση. Δείτε την [καταχώριση CVE του Ubuntu](https://ubuntu.com/security/CVE-2026-3888) για την κατάσταση πακέτων ανά έκδοση και τη [γνωστοποίηση της Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) για την αλληλεπίδραση των στοιχείων.

## Ελέγξτε τα ACL και τις ευαίσθητες διαδρομές

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Ένας εγγράψιμος γονικός κατάλογος μπορεί να επιτρέψει την αντικατάσταση, ακόμη κι αν το ίδιο το αρχείο ανήκει στον root. Ένα ACL μπορεί να παρέχει αθόρυβα πρόσβαση σε ένα sudoers drop-in, service unit, cron script, library path ή credential file. Ελέγξτε τόσο το ACL όσο και ολόκληρη τη διαδρομή. Αν είναι δυνατή η εγγραφή οποιουδήποτε περιεχομένου σε αρχεία με προνόμια, ακολουθήστε το [Arbitrary File Write to Root](write-to-root.md)· για περιπτώσεις ρύθμισης του linker και preload, δείτε το παράδειγμα [`ld.so`](ld.so.conf-example.md). Αντιμετωπίστε τα εκτεθειμένα αντίγραφα ασφαλείας, αρχεία `.env`, ρυθμίσεις βάσεων δεδομένων, υλικό SSH και ιστορικό ως πιθανές πηγές διαπιστευτηρίων, με την πρόσβαση να καθορίζεται από τα πραγματικά δικαιώματα κάθε αρχείου.
