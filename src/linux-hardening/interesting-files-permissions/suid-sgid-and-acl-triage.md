# SUID, SGID, ACLs і конфіденційні файли

{{#include ../../banners/hacktricks-training.md}}

SUID і SGID змінюють ефективну ідентичність запущеного файлу; ACL можуть надавати доступ, який не відображають звичайні біти дозволів `ls -l`. Перевіряйте обидва механізми, якщо користувач може читати, записувати або виконувати файли з ширшими дозволами, ніж це випливає з дозволів власника й групи.

## Перелік привілейованих виконуваних файлів

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

Зосередьтеся на власних або нещодавно змінених виконуваних файлах, незвичних власниках і файлах на доступних для запису точках монтування. Монтування `nosuid` може вимкнути поведінку set-ID; capabilities файлів — окремий механізм привілеїв, описаний у [Linux capabilities](linux-capabilities.md). Порівняйте підозрілий бінарний файл із його пакетом і перевірте, що він виконує, відкриває або завантажує з підвищеними правами.

Якщо незнайомий виконуваний файл SUID, власником якого є root, приймає введені користувачем дані, проаналізуйте офлайн його копію на предмет небезпечної для пам’яті обробки аргументів і шлях коду, який до неї веде. Зафіксуйте поведінку effective ID і такі засоби захисту, як stack canaries, пам’ять без дозволу на виконання, position-independent code та рандомізація адрес. Назва небезпечної функції або відсутність засобу захисту — лише привід для перевірки: можливість експлуатації залежить від фактичних обмежень на введені дані, досяжного потоку керування та effective identity у момент помилки. Не передавайте довгі аргументи активному привілейованому виконуваному файлу лише для перевірки, чи станеться аварійне завершення під час пасивного переліку.

Знайому програму SUID також можна підмінити або вбудувати в неї бекдор. Нещодавній час зміни — це привід для перевірки, а не доказ: для **конкретного підозрілого бінарного файлу з пакета** визначте пакет-власник і порівняйте встановлений файл із метаданими пакета, замість того щоб під час звичайного переліку перевіряти кожен пакет:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` перевіряє вміст файлів лише тоді, коли в базі даних пакетів записано контрольну суму; RPM також порівнює метадані, як-от режим і власника. Зосередьтеся на невідповідності саме **привілейованого виконуваного файла**: в урізаних інсталяціях можуть повідомлятися про відсутні документацію чи файли локалізації деінде в тому самому пакеті. Порівняйте підозрілий виконуваний файл із довіреним пакетом постачальника та перевірте точні зміни в коді. Локальні зміни, відсутні контрольні суми та скомпрометовані метадані пакета обмежують доказовість обох команд. Під час пасивного тріажу не запускайте ані підозрілу SUID-програму, ані скрипт перевірки пакета. Див. [посібник із перевірки dpkg](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) і [посібник із перевірки RPM](https://rpm.org/docs/4.20.x/man/rpm.8).

SUID-програма, яка викликає shell, команду з відносним шляхом або бібліотеку з каталогу, доступного для запису, може порушувати межу довіри. Див. [зловживання спільними бібліотеками та компонувальником у SUID](suid-shared-library-and-linker-abuse.md), [рекомендації щодо PATH](../linux-basics/linux-environment-variables.md#path) і [пояснення ідентифікаторів користувача](../user-information/euid-ruid-suid.md). Для відомих способів виходу, специфічних для команд, перевірте [GTFOBins](https://gtfobins.github.io/) щодо точного бінарного файла та способу виклику, дозволеного на хості.

Для виконуваного файла з set-user-ID розрізняйте **реальний UID** викликувача та **ефективний UID** власника файла: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) залишає реальний UID незмінним і після зміни set-ID копіює ефективний UID у збережений UID. [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) запускає команду через `/bin/sh -c`; вибраний цим шляхом shell впливає на те, чи збереже дочірній процес ефективну ідентичність. Зокрема, [правила привілейованого режиму Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) скидають відмінний ефективний UID до реального UID, якщо Bash запускається без `-p`. Перевірте зміни UID і виклик дочірнього процесу в конкретному допоміжному файлі, а також його власника, доступ до виконання, параметр монтування `nosuid` і стан процесу `no_new_privs`. Самі по собі SUID-біт або виклик shell не доводять, що перехід до вищих привілеїв можливий.

Незвичний SUID-файл `jjs`, власником якого є root, заслуговує на окрему перевірку доступу до файлів, якщо поточний користувач може його виконати. Застарілий інструмент Nashorn може звертатися до файлових API Java, навіть якщо дочірній shell скидає ефективний UID; перш ніж вважати це привілейованим читанням або записом, перевірте поведінку встановленої JVM, ефективну ідентичність файлової операції та параметри `nosuid`/`no_new_privs`. [Oracle вилучила `jjs` у JDK 15](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); встановлений шлях усе ще може вести до старішої або окремо запакованої збірки. [GTFOBins описує файлові API](https://gtfobins.org/gtfobins/jjs/), але приклади з sudo не доводять поведінку SUID для кожної збірки. Не запускайте інструмент під час пасивного переліку.

SUID-виконуваний файл `gosu`, власником якого є root і до якого має доступ користувач із нижчими привілеями, варто перевірити: задокументований інтерфейс приймає цільового користувача й команду, але за звичайного використання в контейнері його запускають від root, щоб скинути привілеї. Перевірте поведінку SUID у встановленій збірці, ефективну ідентичність і зіставлення user namespace, а також `nosuid` і `no_new_privs`; root у контейнері не означає root на хості. Самі лише ім’я файла або SUID-біт не доводять, що перехід працює. Див. [використання в upstream](https://github.com/tianon/gosu) і [попередження супровідника щодо SUID](https://github.com/tianon/gosu/issues/11). Не запускайте допоміжну програму під час пасивної інвентаризації.

Користувацький backup-wrapper із set-user-ID може приймати шлях, заданий викликувачем, і підставляти його в команду архіватора, передану до `system(3)`. Якщо цей шлях у сформованій команді не взято в лапки, дочірній shell може застосовувати [розгортання тильди за допомогою `HOME`, шаблони шляхів на кшталт `?` і `*`, а також розділення команд символом нового рядка](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html); відхилення лише звичних символів за denylist не робить шлях буквальним. Перевірте точний потік аргументів, успадковане середовище, дочірній shell та ефективну ідентичність, доступ до файлової системи й те, чи видно викликувачу вивід архіватора. SUID-біт, рядок із назвою архіватора або відхилений буквальний шлях `/root` самі по собі не доводять ані розголошення даних, ані виконання коду. Під час пасивного переліку перевіряйте копію wrapper офлайн, а не архівуйте приватні файли й не надсилайте дані, що спричиняють збій.

[Підстановка команд](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) у shell, як-от `$(...)`, — ще одна можлива лазівка в denylist метасимволів: навіть фіксований дозволений префікс команди може передати пізніший аргумент, контрольований викликувачем, до `/bin/sh -c`. Офлайн перевірте точне екранування, парсер і ефективну ідентичність; сам рядок для `system()` або неповний denylist не є доказом виконання.

Важливе значення має також **дерево процесів-викликувачів**. Вебворкер може встановити seccomp-фільтр, який обмежує системні виклики зміни UID; [seccomp-фільтри успадковуються дочірніми процесами й зберігаються після `execve`](https://docs.kernel.org/userspace-api/seccomp_filter.html). Наприклад, директиви Apache [mpm-itk `LimitUIDRange` і `LimitGIDRange`](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) можуть обмежувати ідентичності, доступні нащадкам. `Seccomp: 2` у `/proc/self/status` указує на режим фільтра, а не на його політику й не на те, чи може саме цей допоміжний файл отримати ідентичність свого власника. Перевірте разом ланцюжок походження конкретного виклику та ефективний фільтр, а також умови SUID, монтування й `no_new_privs`; окрема сесія входу може мати іншу політику, але для неї потрібен власний дійсний шлях доступу.

Користувацький SUID-виконуваний файл може запускати окремий скрипт Python, доступний для читання. Якщо він справді використовує Python **2**, [`input()` обчислює введений вираз](https://docs.python.org/2/library/functions.html#input); натомість `input()` у Python 3 повертає текст. Перш ніж вважати цей рядок коду шляхом до виконання, перевірте ефективну ідентичність wrapper, шлях до інтерпретатора та його версію, шлях до скрипту й те, чи доходять до цього виклику недовірені дані. Сам по собі set-ID-біт скрипту або виклик `input()` без привілейованого wrapper не створює такої самої межі. Під час переліку перевірте згадані бінарним файлом шляхи та обмежений фрагмент вихідного коду скрипту, не запускаючи його.

Якщо незвичний SUID-виконуваний файл супроводжується доступним для читання вихідним кодом, порівняйте кількість байтів, запитану під час кожного читання файла, контрольованого викликувачем, із розміром буфера призначення та перевірте подальші перевірки потоку керування. [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) записує запитані елементи за вказаною адресою; ця функція не знає місткості об’єкта призначення. Невідповідність розмірів — це підказка для статичного аналізу безпеки пам’яті, а не доказ придатного для використання підвищення привілеїв: підтвердьте, що вихідний код відповідає встановленому бінарному файлу, викликувач може надати вхідні дані, виконання SUID ефективне в цьому контексті й відповідний шлях досяжний. Під час переліку перевіряйте обмежену копію вихідного коду або бінарного файла офлайн, а не надсилайте привілейованій програмі дані, що спричиняють збій.

Користувацький SUID-helper може розкрити захищений файл, не виводячи його вміст. Якщо викликувач задає і шлях, і регулярний вираз, а helper повертає видимий лічильник збігів під своїм ефективним UID, перевірки префіксів із прив’язкою до початку рядка можуть утворювати побайтовий oracle. Перевірте власника helper, поведінку ефективного ID, доступ до виконання, обмеження шляхів, семантику регулярних виразів, видимість відповіді та наявність конкретного файла з вищими привілеями, який викликувач інакше не може прочитати. Самі лише SUID-біт або рядок із назвою бібліотеки регулярних виразів не доводять жодної частини цього ланцюжка. Під час пасивного переліку зафіксуйте незвичний виконуваний файл і перевірте обмежений дамп дизасемблювання або копію вихідного коду; не запускайте ітеративні здогадки проти активного helper і не виводьте відновлені секрети.

В OpenBSD користувацький reader із set-user-ID, що приймає шлях, заданий викликувачем, може розкрити файли в `/var/backups`, якщо його ефективна ідентичність дає змогу їх читати, а їхній вміст повертається викликувачу. [Файл `changelist(5)` в OpenBSD](https://man.openbsd.org/changelist.5) описує копії `.current` і `.backup` налаштованих шляхів, але для записів із префіксом `+` зберігаються контрольні суми SHA-256, а не вміст файлів; власником каталогу резервних копій має бути root, а режим доступу має бути `0700`. Правило читання [`unveil` для `/var`](https://man.openbsd.org/unveil.2) у helper може дозволити доступ усередині цього шляху, але саме по собі не надає й не доводить доступ до файлів. Перш ніж заявляти про підвищення привілеїв, перевірте фактичний ефективний UID, дозвіл на виконання для поточного користувача, прийнятий шлях, наявність і вміст резервної копії та будь-які незалежні вимоги автентифікації. Пасивний перелік має фіксувати helper і метадані шляху, а не запускати reader чи виводити дані резервної копії.

Користувацька SUID-програма, яка перевіряє заданий викликувачем шлях за допомогою [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html), а потім відкриває цей шлях, може зазнати race condition через зміну файла або symlink у каталозі, доступному викликувачеві для запису. Перевірка стосується попереднього об’єкта, тоді як пізніший [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) може розв’язати шлях до іншого об’єкта. Переконайтеся, що helper можна виконати з підвищеною ефективною ідентичністю, що досяжний шлях виконання читає вибраний файл і що викликувач може підмінити шлях між перевіркою та відкриттям; самі лише SUID-біт, каталог, доступний для запису, або рядок `stat` не доводять жодного з цих пунктів. Для розголошення також потрібен видимий вивід або доступне викликувачеві місце призначення. Перевірте бінарний файл і метадані шляху офлайн; не влаштовуйте race condition проти активного helper під час пасивного переліку.

Таку саму перевірку залежностей застосовуйте до SGID-wrapper. Wrapper, який запускає shell або helper за абсолютним шляхом, усе одно може бути небезпечним, якщо користувач із нижчими привілеями може замінити цей файл; запущений код може успадкувати ефективну групу wrapper. Перевірте точний шлях виклику, доступ на запис (зокрема через ACL), ефективну групу wrapper і те, чи скидає він привілеї перед запуском дочірнього процесу. Інтерпретатор також може відкинути успадковані ефективні ID, тож відрізняйте кандидата для перевірки від доведеного переходу. Сам лише доступний для запису shell деінде на хості не доводить, що його викликає привілейований wrapper.

### Привілейовані wrapper, що передають SQL до SQLite CLI

Якщо користувацька SUID-програма передає контрольований користувачем SQL **програмі командного рядка `sqlite3`**, перш ніж вважати запит доступним лише для читання, перевірте точну команду й ефективну ідентичність. SQL-функція CLI `edit()` запускає редактор (із другого аргументу або `VISUAL`), а її SQL-функція `load_extension()` може завантажити спільну бібліотеку, якщо завантаження розширень увімкнене. Це потенційні шляхи виконання коду з ідентичністю процесу CLI, навіть якщо wrapper задає фіксований `PATH` або використовує абсолютний шлях до `sqlite3`. SQL має справді доходити до цих функцій, а CLI має зберігати відповідну можливість; сама лише згадка `sqlite3` у бінарному файлі або на хості не є доказом підвищення привілеїв. Бібліотека SQLite вимикає завантаження розширень за замовчуванням, тож відрізняйте її від CLI. Якщо привілейована програма має обробляти недовірений SQL, режим SQLite CLI `--safe` вимикає `edit()`, `load_extension()` та інші функції з побічними ефектами. Див. [документацію SQLite CLI](https://www.sqlite.org/cli.html#the_edit_sql_function), [документацію безпечного режиму](https://www.sqlite.org/cli.html#the_safe_command_line_option) і [документацію із завантаження розширень](https://www.sqlite.org/loadext.html#loading_an_extension).

### Привілейовані читачі файлів, що передають дані клієнту з докладним виводом

Користувацький SUID/SGID-wrapper може перевіряти доступ до шляху, заданого викликувачем, а потім передавати цей файл іншій команді. Перевірте ефективну ідентичність і під час перевірки доступу, і під час подальшого відкриття, розв’яжіть усі компоненти `../` відносно фактичного базового каталогу та з’ясуйте, як дочірній процес обробляє некоректні дані. Якщо клієнт бази даних читає приватний файл як SQL і виводить докладні повідомлення, він може відобразити вміст файла в повідомленнях про помилки, навіть якщо SQL некоректний. Це розголошення між користувачами лише за умови, що дочірній процес може прочитати файл, недоступний для читання викликувачеві, викликувач може вибрати цей файл через wrapper і вивід видимий; сама лише наявність `mysql` або рядка з назвою іншого клієнта не доводить виконання жодної з цих умов.

### Шлях пошуку Netdata `ndsudo`

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) стосувалася деяких збірок Netdata `ndsudo`. Допоміжна програма, власником якої був root і яка мала SUID-біт, шукала дозволені зовнішні команди за допомогою `PATH`, заданого викликувачем. Перевіряйте встановлену допоміжну програму, зокрема ту, що розташована поза звичним для викликувача `PATH`, лише якщо поточний обліковий запис може її виконати. Переконайтеся, що перевірено її власника, SUID-біт, доступ до виконання (зокрема дозволи групи/ACL), встановлену збірку та стан виправлення від постачальника, а також те, чи блокує зміну ідентичності `NoNewPrivs` або монтування `nosuid`. Netdata вказує як виправлені збірки `v1.45.3` і `v1.45.0-169`; перенесення виправлення дистрибутивом потрібно підтверджувати окремо. Версія на панелі керування або сама наявність `ndsudo` — недостатній доказ досяжного підвищення привілеїв. Проблема зі шляхом також вимагає, щоб допоміжна програма шукала зовнішню команду в місці, контрольованому викликувачем.

### Межа привілеїв Firejail join

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) стосувалася привілейованої логіки `--join` у Firejail: спеціально сформована ціль приєднання могла змусити допоміжну програму з setuid-root прийняти простір імен монтування, контрольований зловмисником, і скопіювати небезпечний стан безпеки. Під час пасивного тріажу переконайтеся, що **поточна ідентичність може виконати** бінарний файл Firejail із setuid-бітом і власником root, що setuid діє для його монтування та в контексті процесу, а встановлена збірка не містить виправлення. Upstream виправив проблему у [версії 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70); пакети дистрибутивів можуть [перенести виправлення](https://github.com/netblue30/firejail/issues/5191), навіть якщо показують старішу версію. Ці передумови вказують на об’єкт для перевірки, а не на успішне приєднання чи root shell. Під час переліку не створюйте фальшиву jail і не запускайте `--join`.

### Дозволи на файли журналу GNU Screen

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) стосувалася того, що Screen 4.5.0 відкривав вибраний викликувачем файл журналу з підвищеними привілеями. Бінарний файл `screen` або файл із суфіксом версії в переліку SUID — лише підстава для перевірки: підтвердьте власника root, ефективне виконання SUID для поточного користувача, встановлену збірку та стан виправлення в дистрибутиві, а також поведінку з файлами журналу, на яку впливала вразливість. [Debian виправив свій пакет версії 4.5.0 перенесенням виправлення](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), тож самі лише рядок версії або ім’я файла не доводять наявність вразливості. Не створюйте файл журналу як звичайну перевірку під час переліку.

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) стосувалася привілейованого helper блокування пошти S-nail, коли компонент шляху, контрольований викликувачем, міг переходити між каталогами й призводити до запису в довільний файл. Перевірте, чи може поточний користувач виконати встановлений helper із setuid-бітом і власником root, чи діє його setuid-ідентичність з урахуванням політики монтування та процесу, а також точну збірку пакета й виправлення постачальника. [Повідомлення безпеки Ubuntu](https://ubuntu.com/security/notices/USN-4820-1) містить перенесене виправлення для пакета версії 16.04, тому схожа на upstream версія сама по собі не дає певної відповіді. Наявність helper не доводить, що вразливий шлях досяжний або що запис у файл дає змогу виконати код із привілеями root; перевірте метадані й стан пакета, не запускаючи helper і не намагаючись спричинити race condition під час переліку.

### Очищення snap-confine і tmpfiles

CVE-2026-3888 — це race condition, що стосується привілейованого `snap-confine` та очищення `/tmp` за допомогою systemd-tmpfiles. Під час пасивної перевірки можна з’ясувати, чи має `snap-confine` setuid-біт або файлові capabilities, порівняти встановлений пакет `snapd` із виправленою версією для цього **випуску Ubuntu**, а також перевірити фактичне правило строку зберігання для `/tmp` і таймер очищення. Відповідність пакета й правила — це передумови, а не доказ досяжності race condition: важливі також стан таймера під час виконання, розташування snap, перенесені виправлення в пакетах і перевизначення правил. Для старіших випусків може знадобитися нестандартна конфігурація. Не запускайте race-перевірку під час звичайного переліку. Див. [запис CVE в Ubuntu](https://ubuntu.com/security/CVE-2026-3888), щоб дізнатися про стан пакетів для конкретних випусків, і [рекомендації Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root), де описано взаємодію компонентів.

## Перевірка ACL і чутливих шляхів

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

Доступний для запису батьківський каталог може дозволити заміну файла, навіть якщо сам файл належить root. ACL може непомітно надавати доступ до додаткового файла sudoers, службового юніта, скрипту cron, шляху до бібліотеки або файла облікових даних. Перевіряйте і ACL, і повний шлях. Якщо можливий довільний запис привілейованих файлів, дивіться [Довільний запис у файли від root](write-to-root.md); про конфігурацію лінкера та випадки з preload дивіться приклад [`ld.so`](ld.so.conf-example.md). Вважайте відкриті резервні копії, файли `.env`, конфігурації баз даних, матеріали SSH та історію можливими джерелами облікових даних; доступ до них визначається фактичними дозволами кожного файла.
