# SUID、SGID、ACL、機密ファイル

{{#include ../../banners/hacktricks-training.md}}

SUID と SGID は、実行されたファイルの実効 ID を変更します。ACL は、通常の `ls -l` のモードビットには表示されないアクセス権を付与できます。ユーザーが、見かけ上の所有者やグループの権限から想定される以上の読み取り、書き込み、実行を行える場合は、両方を確認してください。

## 特権付き実行ファイルを列挙する

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

カスタムの実行ファイルや最近変更された実行ファイル、通常とは異なる所有者、書き込み可能なマウント上のファイルに注目します。`nosuid` マウントでは set-ID の動作が抑制される場合があります。file capabilities は別の権限メカニズムで、[Linux capabilities](linux-capabilities.md) で説明されています。不審なバイナリをパッケージ内のものと比較し、昇格した ID で何を実行、オープン、ロードするかを確認します。

呼び出し元の入力を受け取る、見慣れない root 所有の SUID 実行ファイルについては、バイナリのコピーをオフラインで調査し、メモリ安全でない引数処理と、そこに到達するコードパスを確認します。実効 ID の挙動と、stack canary、実行不可メモリ、位置独立コード、アドレスランダム化などの緩和策を記録します。危険な関数名や緩和策の欠如は調査の手がかりにすぎません。悪用可能性は、実際の入力範囲、到達可能な制御フロー、障害発生時の実効 ID に左右されます。受動的な列挙中にクラッシュを試すためだけに、稼働中の特権実行ファイルへ長い引数を渡してはいけません。

見慣れた SUID プログラムでも、置き換えやバックドア化の可能性があります。更新時刻が最近であることは手がかりであり、証拠ではありません。**特定の不審なパッケージ管理対象バイナリ**については、所有パッケージを特定し、定常的な列挙中にすべてのパッケージを検証するのではなく、インストール済みファイルをパッケージメタデータと比較します。

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` は、パッケージデータベースに記録されたチェックサムがある場合に限りファイルの内容を確認します。RPM はモードや所有者などのメタデータも比較します。**特権実行ファイル自体**の不一致に注目してください。インストール時にファイルが削除されていると、同じパッケージ内の別の場所にあるドキュメントやロケールファイルが見つからないという報告が出ることがあります。不審な実行ファイルを信頼できるベンダーパッケージと比較し、変更されたコードを正確に確認してください。正当なローカル変更、チェックサムの欠落、侵害されたパッケージメタデータがある場合、いずれのコマンドで証明できることにも限界があります。受動的なトリアージの一環として、不審な SUID プログラムやパッケージ検証スクリプトを実行しないでください。[dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) と [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) を参照してください。

シェル、相対パスで指定されたコマンド、または書き込み可能なパスにあるライブラリを呼び出す SUID プログラムは、信頼境界を越える可能性があります。[SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md)、[PATH のガイダンス](../linux-basics/linux-environment-variables.md#path)、[user ID の説明](../user-information/euid-ruid-suid.md)を参照してください。特定のコマンドで知られているエスケープ方法は、ホストで許可されている正確なバイナリと呼び出し方に照らして [GTFOBins](https://gtfobins.github.io/) を確認してください。

set-user-ID 実行ファイルでは、呼び出し元の**実 UID**とファイル所有者の**実効 UID**を区別してください。[`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) は実 UID を変更せず、set-ID による変更後の実効 UID を保存 UID にコピーします。[`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) は `/bin/sh -c` を介してコマンドを実行します。このパスで選択されるシェルによって、子プロセスが実効 ID を保持するかどうかが変わります。特に、[Bash の privileged-mode の規則](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html)では、Bash が `-p` なしで起動され、実効 UID と実 UID が異なる場合、実効 UID は実 UID にリセットされます。実際のヘルパーの UID 変更と子プロセスの呼び出しに加え、所有者、実行アクセス権、マウントの `nosuid` 設定、プロセスの `no_new_privs` 状態を確認してください。SUID ビットやシェル呼び出しだけでは、より高い特権への移行が可能だとは判断できません。

root 所有の通常とは異なる SUID `jjs` があり、現在のユーザーが実行できる場合は、ファイルアクセスを別途確認してください。旧式の Nashorn ツールは、起動したシェルで実効 UID が破棄されても Java のファイル API にアクセスできます。特権付きの読み書きだと判断する前に、インストール済み JVM の動作、ファイル操作時の実効 ID、`nosuid` と `no_new_privs` を確認してください。[Oracle は JDK 15 で `jjs` を削除しました](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html)。インストール済みのパスには、旧バージョンや別パッケージのビルドが残っている場合があります。[GTFOBins はファイル API を説明しています](https://gtfobins.org/gtfobins/jjs/)。ただし、その sudo の例から、すべてのビルドで SUID が機能すると判断することはできません。受動的な列挙中にこのツールを起動しないでください。

root 所有で、低い特権のユーザーが実行できる SUID `gosu` 実行ファイルがあれば、確認が必要です。文書化されたインターフェースでは対象ユーザーとコマンドを受け取りますが、通常のコンテナ利用では root として起動し、特権を落とします。インストール済みビルドの SUID 動作、実効 ID と user namespace のマッピングに加え、`nosuid` と `no_new_privs` を確認してください。コンテナ内の root がホストの root であるとは限りません。ファイル名や SUID ビットだけでは、特権移行が機能すると証明できません。[upstream の使用方法](https://github.com/tianon/gosu)と[メンテナーによる SUID の警告](https://github.com/tianon/gosu/issues/11)を参照してください。受動的なインベントリ作成中にヘルパーを起動しないでください。

独自の set-user-ID バックアップラッパーが、呼び出し元指定のパスを受け取り、`system(3)` に渡すアーカイブコマンドへ埋め込む場合があります。構築されたコマンド内でそのパスが引用符で囲まれていないと、子シェルは[チルダ展開（`HOME` を使用）、`?` や `*` などのパス名パターン、改行によるコマンド区切り](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)を適用する可能性があります。よくある記号だけを denylist で拒否しても、パスが文字どおり扱われるとは限りません。引数の正確な流れ、継承される環境変数、子シェルと実効 ID、ファイルシステムへのアクセス、アーカイブ出力が呼び出し元から見えるかを確認してください。SUID ビット、アーカイブツールの文字列、または `/root` という文字列だけを拒否することのいずれも、情報漏えいやコード実行の証明にはなりません。受動的な列挙中にプライベートファイルをアーカイブしたり、クラッシュを起こす入力を送ったりせず、ラッパーのコピーをオフラインで確認してください。

`$(...)` などのシェルの[コマンド置換](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)も、メタ文字 denylist の抜け穴になり得ます。許可されているコマンドのプレフィックスが固定でも、後続の呼び出し元制御引数が `/bin/sh -c` に渡される場合があります。正確な引用処理、パーサー、実効 ID をオフラインで確認してください。`system()` の文字列や不完全な denylist だけを実行の証明と見なさないでください。

**呼び出し元プロセスのツリー**も重要です。Web ワーカーは、UID 変更システムコールを制限する seccomp フィルターを設定できます。[seccomp フィルターは子プロセスに引き継がれ、`execve` 後も有効です](https://docs.kernel.org/userspace-api/seccomp_filter.html)。たとえば、Apache の [mpm-itk `LimitUIDRange` および `LimitGIDRange` ディレクティブ](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/)は、子孫プロセスが到達できる ID を制限できます。`/proc/self/status` の `Seccomp: 2` はフィルターモードを示すだけで、ポリシーや、この特定のヘルパーが所有者の ID を取得できるかどうかは示しません。実際の呼び出しの祖先プロセスと実効フィルターを、SUID、マウント、`no_new_privs` の条件と合わせて確認してください。別のログインセッションでは異なるポリシーが適用される場合がありますが、別途有効なアクセス経路が必要です。

独自の SUID 実行ファイルが、別の読み取り可能な Python スクリプトを呼び出す場合があります。実際に Python **2** を使用している場合、[`input()` は入力された式を評価します](https://docs.python.org/2/library/functions.html#input)。一方、Python 3 の `input()` はテキストを返します。そのソース行が実行経路だと判断する前に、ラッパーの実効 ID、インタープリターのパスとバージョン、スクリプトのパス、信頼できない入力がその呼び出しに届くかを確認してください。スクリプト自体の set-ID ビットや、特権付きラッパーを介さない `input()` 呼び出しは、同じ境界を成立させません。列挙中は実行せず、バイナリが参照するパスと、範囲を限定したスクリプトのソースを確認してください。

通常とは異なる SUID 実行ファイルに読み取り可能なソースが付属している場合は、呼び出し元が制御する各ファイル読み込みの要求バイト数と宛先バッファーのサイズを比較し、後続の制御フローチェックを調べてください。[`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) は指定されたポインターに要求されたアイテム数を書き込みますが、宛先オブジェクトの容量は認識しません。サイズの不一致は静的なメモリー安全性の調査材料であり、特権昇格が可能だという証明ではありません。ソースがインストール済みバイナリと一致すること、呼び出し元が入力を指定できること、その状況で SUID 実行が有効であること、該当する経路に到達できることを確認してください。列挙中に特権プログラムへクラッシュを起こす入力を送らず、範囲を限定したソースまたはバイナリのコピーをオフラインで確認してください。

独自の SUID ヘルパーは、内容を表示しなくても保護されたファイルの情報を漏らす場合があります。呼び出し元がパス名と正規表現の両方を指定でき、ヘルパーが実効 UID で一致数を返す場合、アンカー付きプレフィックステストによって一文字ずつ推測できるオラクルになり得ます。ヘルパーの所有者、実効 ID の動作、実行アクセス、パス名の制約、正規表現の意味、応答の可視性、呼び出し元が通常は読み取れない具体的な高特権ファイルを確認してください。SUID ビットや正規表現ライブラリの文字列だけでは、その一連の動作は証明できません。受動的な列挙中は通常とは異なる実行ファイルを記録し、範囲を限定した逆アセンブル結果またはソースのコピーを確認してください。実行中のヘルパーに対して繰り返し推測を実行したり、復元した秘密を表示したりしないでください。

OpenBSD では、呼び出し元指定のパス名を受け付ける独自の set-user-ID 読み取りプログラムについて、実効 ID で `/var/backups` 内のファイルを読み取れ、内容を呼び出し元に返す場合は、情報漏えいの可能性を確認してください。[OpenBSD の `changelist(5)`](https://man.openbsd.org/changelist.5) には、設定されたパスの `.current` と `.backup` コピーについて記載されていますが、`+` で始まるエントリーにはファイル内容ではなく SHA-256 チェックサムが保存されます。バックアップディレクトリの所有者は root、モードは `0700` であるべきです。`/var` に対するヘルパーの [`unveil` 読み取りルール](https://man.openbsd.org/unveil.2)は、そのパス以下へのアクセスを許可することがありますが、それ自体はファイルアクセスを許可するものでも、その証明でもありません。昇格を主張する前に、実際の実効 UID、現在のユーザーの実行権限、受け入れられるパス、バックアップの有無と内容、独立した認証要件の有無を確認してください。受動的な列挙ではヘルパーとパスのメタデータを報告し、読み取りプログラムを起動したりバックアップデータを表示したりしないでください。

呼び出し元指定のパス名を [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) で確認した後に開く独自の SUID プログラムでは、呼び出し元が書き込み可能なディレクトリ内のファイルやシンボリックリンクを変更する競合が起きる可能性があります。チェック対象は先に確認したオブジェクトですが、後続の [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) では別のオブジェクトに解決されることがあります。ヘルパーを高い実効 ID で実行できること、到達可能なコード経路が選択されたファイルを読み取ること、呼び出し元がチェックとオープンの間にパス名を差し替えられることを確認してください。SUID ビット、書き込み可能なディレクトリ、`stat` という文字列だけでは、これらのいずれも証明できません。情報漏えい経路には、出力が見えること、または呼び出し元が読み取れる出力先も必要です。バイナリとパスのメタデータをオフラインで確認し、受動的な列挙中に実行中のヘルパーで競合を試さないでください。

SGID ラッパーにも同じ依存関係の確認を適用してください。シェルやヘルパーを絶対パスで実行するラッパーでも、低い特権のユーザーがそのファイルを差し替えられるなら安全ではありません。起動されたコードがラッパーの実効グループを継承する可能性があります。呼び出される正確なパス、その書き込み権限（ACL を含む）、ラッパーの実効グループ、子プロセスを起動する前に特権を落とすかを確認してください。インタープリターが継承された実効 ID を破棄する場合もあるため、調査候補と、実証された移行とを区別してください。ホスト上の別の場所に書き込み可能なシェルがあるだけでは、特権ラッパーがそれを呼び出す証拠にはなりません。

### SQLite CLI に SQL を渡す特権ラッパー

独自の SUID プログラムがユーザー制御の SQL を **`sqlite3` コマンドラインプログラム**に渡す場合、クエリが読み取り専用だと判断する前に、実際のコマンドと実効 ID を確認してください。CLI の `edit()` SQL 関数はエディター（第 2 引数または `VISUAL` で指定）を起動し、SQL の `load_extension()` 関数は拡張機能の読み込みが有効な場合に共有ライブラリを読み込めます。ラッパーが `PATH` を固定していたり、絶対パスで `sqlite3` を指定していたりしても、CLI プロセスの ID でコード実行が起きる可能性があります。SQL が実際にこれらの関数へ到達し、CLI で該当機能が有効である必要があります。バイナリやホスト上で `sqlite3` が見つかっただけでは、昇格の証拠になりません。SQLite **ライブラリ**では拡張機能の読み込みはデフォルトで無効です。ライブラリと CLI を区別してください。特権アプリケーションで信頼できない SQL を処理する必要がある場合、SQLite の CLI の `--safe` モードでは `edit()`、`load_extension()`、その他の副作用を伴う関数が無効になります。[SQLite CLI のドキュメント](https://www.sqlite.org/cli.html#the_edit_sql_function)、[safe mode のドキュメント](https://www.sqlite.org/cli.html#the_safe_command_line_option)、[拡張機能の読み込みに関するドキュメント](https://www.sqlite.org/loadext.html#loading_an_extension)を参照してください。

### 詳細な出力を行うクライアントに渡す特権ファイル読み取りプログラム

独自の SUID/SGID ラッパーは、呼び出し元指定のパス名へのアクセスを確認してから、そのファイルを別のコマンドに渡す場合があります。アクセス確認時と後続のオープン時の実効 ID を確認し、実際の基準ディレクトリに照らして `../` を解決し、子プロセスが不正な入力をどう扱うかを調べてください。データベースクライアントがプライベートファイルを SQL として読み込み、詳細な出力を行う場合、SQL が無効でもエラーにファイル内容を出力することがあります。これは、子プロセスが呼び出し元には読めないファイルを読めること、呼び出し元がラッパーを通じてそのファイルを指定できること、出力を確認できることのすべてが満たされる場合に限り、別ユーザーへの情報漏えいとなります。`mysql` などのクライアント名が見つかっただけでは、これらの条件のいずれも証明できません。

### Netdata `ndsudo` の検索パス

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) は、一部の Netdata `ndsudo` ビルドに影響しました。root 所有の SUID ヘルパーは、呼び出し元が指定する `PATH` を使って、許可された外部コマンドを検索していました。現在のアカウントが実行できる場合に限り、呼び出し元の通常の `PATH` にないものも含め、インストール済みヘルパーを確認してください。所有者、SUID ビット、実行アクセス（グループや ACL による許可を含む）、インストール済みビルドとベンダーパッチの適用状況、`NoNewPrivs` または `nosuid` マウントによって ID 変更が阻止されるかを確認してください。Netdata は修正済みビルドとして `v1.45.3` と `v1.45.0-169` を挙げています。ディストリビューションによるバックポートは別途確認が必要です。ダッシュボードのバージョンや `ndsudo` の存在だけでは、到達可能な昇格の証拠として不十分です。このパスの問題が成立するには、ヘルパーが呼び出し元の制御下にある場所から外部コマンドを解決する必要もあります。

### Firejail の join における特権境界

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) は、Firejail の特権付き `--join` ロジックに影響しました。細工した join 対象によって、setuid-root ヘルパーが攻撃者の制御するマウント namespace を受け入れ、安全でないセキュリティ状態をコピーする可能性がありました。受動的なトリアージでは、**現在の ID で実行可能**な root 所有の setuid Firejail バイナリがあること、そのマウントおよびプロセスコンテキストで setuid が有効であること、インストール済みビルドに修正がないことを確認してください。upstream は[バージョン 0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70)でこの問題を修正しました。ディストリビューションのパッケージは、古いバージョンを表示したまま[修正をバックポート](https://github.com/netblue30/firejail/issues/5191)している場合があります。これらの前提条件が示すのは調査候補であり、join の成功や root シェルではありません。列挙中に偽の jail を作成したり、`--join` を実行したりしないでください。

### GNU Screen のログファイル権限

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) は、Screen 4.5.0 が呼び出し元指定のログファイルを高い特権で開く問題でした。SUID インベントリにある `screen` またはバージョン番号付きのバイナリは、調査の手がかりにすぎません。root 所有であること、現在のユーザーに対する実効 SUID 実行、インストール済みビルドとディストリビューションのパッチ適用状況、影響を受けるログファイル動作を確認してください。[Debian はバックポートにより 4.5.0 パッケージを修正しました](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484)。そのため、バージョン文字列やファイル名だけでは脆弱性の存在を証明できません。通常の列挙プローブとしてログファイルを作成しないでください。

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) は、呼び出し元が制御するパス要素でディレクトリをたどり、任意のファイル書き込みにつながる場合に、特権付き S-nail のメールロックヘルパーに影響しました。現在のユーザーがインストール済みの root 所有 setuid ヘルパーを実行できるか、マウントとプロセスポリシーの下で setuid ID が有効か、正確なパッケージビルドとベンダー修正を確認してください。[Ubuntu のセキュリティ通知](https://ubuntu.com/security/notices/USN-4820-1)には、Ubuntu 16.04 のパッケージにバックポートされた修正が記載されています。そのため、upstream のものに見えるバージョンだけでは判断できません。ヘルパーの存在は、影響を受けるパスに到達できることや、ファイル書き込みが root での実行につながることを証明しません。列挙中はヘルパーを起動したり競合を試みたりせず、メタデータとパッケージの状態を確認してください。

### snap-confine と tmpfiles によるクリーンアップ

CVE-2026-3888 は、特権付き `snap-confine` と systemd-tmpfiles による `/tmp` のクリーンアップの間で起きる競合です。受動的な調査では、`snap-confine` に setuid またはファイルケーパビリティが設定されているか、インストール済み `snapd` パッケージが**該当する Ubuntu リリース**向けの修正版か、`/tmp` の有効な経過時間ルールとクリーンアップタイマーを確認できます。パッケージとルールの一致は前提条件であり、競合に到達できる証拠ではありません。実行時のタイマー状態、snap のレイアウト、パッケージのバックポート、ルールの上書きも関係します。古いリリースでは、デフォルトではない設定が必要な場合があります。通常の列挙中に競合を試すプローブを実行しないでください。リリースごとのパッケージ状況は[Ubuntu CVE レコード](https://ubuntu.com/security/CVE-2026-3888)、コンポーネント間の相互作用は[Qualys のアドバイザリー](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root)を参照してください。

## ACL と機密性の高いパスを確認する

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

書き込み可能な親ディレクトリがあると、ファイル自体が root 所有でも置き換えられる場合があります。ACL によって sudoers の drop-in、service unit、cron script、library path、credential file へのアクセスがひそかに許可されていることもあります。ACL とパス全体を確認してください。特権ファイルへの任意の書き込みが可能な場合は、[Arbitrary File Write to Root](write-to-root.md) を参照してください。リンカー設定や preload のケースについては、[`ld.so` の例](ld.so.conf-example.md)を参照してください。公開されたバックアップ、`.env` ファイル、データベース設定、SSH 関連ファイル、履歴は、認証情報の入手元となる可能性があります。アクセス可否は各ファイルの実際の権限によって決まります。
