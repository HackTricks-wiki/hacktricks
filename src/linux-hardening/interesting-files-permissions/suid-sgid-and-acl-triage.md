# SUID, SGID, ACLs, और संवेदनशील फ़ाइलें

{{#include ../../banners/hacktricks-training.md}}

SUID और SGID, चलाए गए फ़ाइल की effective identity बदलते हैं; ACLs ऐसी पहुँच दे सकते हैं जो सामान्य `ls -l` mode bits में दिखाई नहीं देती। जब किसी user को apparent owner और group permissions से अधिक पढ़ने, लिखने या execute करने की पहुँच मिले, तो दोनों की जाँच करें।

## Privileged executables की सूची बनाएँ

```bash
find / -xdev -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null
findmnt -no TARGET,OPTIONS
getcap -r / 2>/dev/null
```

कस्टम या हाल ही में बदले गए executables, असामान्य owners और writable mounts पर मौजूद files पर ध्यान दें। `nosuid` mount set-ID behavior को रोक सकता है; file capabilities एक अलग privilege mechanism हैं, जिसका वर्णन [Linux capabilities](linux-capabilities.md) में है। किसी संदिग्ध binary की तुलना उसके package से करें और जाँचें कि elevated identity के साथ वह क्या execute, open या load करती है।

ऐसे अनजान root-owned SUID executable के लिए, जो caller input स्वीकार करता हो, binary की एक copy की offline समीक्षा करें—यह देखने के लिए कि argument handling memory-unsafe तो नहीं है और उस तक पहुँचने वाला code path क्या है। effective-ID behavior और stack canaries, non-executable memory, position-independent code तथा address randomization जैसे mitigations दर्ज करें। किसी unsafe function का नाम या mitigation का न होना केवल समीक्षा का संकेत है: exploitability वास्तविक input bounds, reachable control flow और fault के समय effective identity पर निर्भर करती है। Passive enumeration के दौरान केवल crash जाँचने के लिए live privileged executable को लंबे arguments न भेजें।

किसी परिचित SUID program को भी बदला या backdoor किया जा सकता है। हाल का modification time जाँच का संकेत है, प्रमाण नहीं: किसी **विशिष्ट संदिग्ध packaged binary** के लिए उसका owning package पता करें और installed file की तुलना package metadata से करें—routine enumeration के दौरान हर package को verify करने के बजाय:

```bash
dpkg -S /usr/bin/passwd                  # Debian-family: identify the owner
dpkg --verify passwd                     # Verify only that package
rpm -V --noscripts -f /usr/bin/passwd    # RPM-family: owning package, no verify scriptlets
```

`dpkg --verify` केवल उन्हीं फ़ाइलों के कॉन्टेंट की जाँच करता है जिनके लिए पैकेज डेटाबेस में checksum दर्ज है; RPM mode और ownership जैसे metadata की भी तुलना करता है। **विशेषाधिकार प्राप्त executable** में मिले mismatch पर ध्यान दें: stripped installations में उसी पैकेज की अन्य जगहों पर मौजूद documentation या locale files के missing होने की रिपोर्ट आ सकती है। संदिग्ध executable की तुलना किसी विश्वसनीय vendor package से करें और बदले गए code की ठीक से समीक्षा करें। वैध local changes, अनुपस्थित checksums और compromised package metadata से इन दोनों commands के प्रमाण सीमित हो जाते हैं। Passive triage के दौरान संदिग्ध SUID program या package verification script न चलाएँ। [dpkg verification manual](https://manpages.debian.org/bookworm/dpkg/dpkg.1.en.html) और [RPM verification manual](https://rpm.org/docs/4.20.x/man/rpm.8) देखें।

जो SUID program किसी writable path से shell, relative command या library चलाता है, वह trust boundary पार कर सकता है। [SUID shared-library and linker abuse](suid-shared-library-and-linker-abuse.md), [PATH guidance](../linux-basics/linux-environment-variables.md#path) और [user-ID explanation](../user-information/euid-ruid-suid.md) देखें। किसी command के ज्ञात escapes के लिए, host पर अनुमत सटीक binary और invocation को [GTFOBins](https://gtfobins.github.io/) में देखें।

Set-user-ID executable के लिए caller के **real UID** और file owner के **effective UID** में अंतर समझें: [`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html) real UID को अपरिवर्तित रखता है और set-ID change के बाद effective UID को saved UID में कॉपी करता है। [`system(3)`](https://man7.org/linux/man-pages/man3/system.3.html) अपनी command `/bin/sh -c` के ज़रिए चलाता है; उस path से चुना गया shell यह तय करता है कि child अपनी effective identity बनाए रखता है या नहीं। विशेष रूप से, [Bash privileged-mode rules](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) के अनुसार, `-p` के बिना शुरू होने पर Bash अलग effective UID को real UID पर reset करता है। वास्तविक helper के UID changes और child invocation के साथ-साथ उसका owner, executable access, mount का `nosuid` setting और process की `no_new_privs` state जाँचें। केवल SUID bit या shell call से यह साबित नहीं होता कि ऊँचे privileges में उपयोगी transition संभव है।

असामान्य root-owned SUID `jjs` के लिए, अगर मौजूदा user उसे execute कर सकता है, तो file access की अलग से समीक्षा करें। पुराना Nashorn tool Java file APIs तक पहुँच सकता है, भले ही शुरू किया गया shell effective UID छोड़ दे; इसे privileged read या write मानने से पहले installed JVM का behavior, file operation की effective identity और `nosuid`/`no_new_privs` की पुष्टि करें। [Oracle ने JDK 15 में `jjs` हटा दिया था](https://docs.oracle.com/en/java/javase/21/migrate/removed-tools-and-components.html); फिर भी installed path पर पुराना या अलग से packaged build हो सकता है। [GTFOBins file APIs का दस्तावेज़ देता है](https://gtfobins.org/gtfobins/jjs/), लेकिन उसके sudo examples हर build में SUID behavior साबित नहीं करते। Passive enumeration के दौरान tool न चलाएँ।

कम privileges वाले user के लिए सुलभ root-owned SUID `gosu` executable की समीक्षा करें: इसका documented interface target user और command स्वीकार करता है, लेकिन सामान्य container use में इसे root के रूप में शुरू करके privileges छोड़े जाते हैं। Installed build का SUID behavior, effective identity और user-namespace mapping, साथ ही `nosuid` और `no_new_privs` की पुष्टि करें; container में root होने का मतलब host पर root होना नहीं है। केवल filename या SUID bit से सफल transition साबित नहीं होता। [Upstream usage](https://github.com/tianon/gosu) और [maintainer की SUID warning](https://github.com/tianon/gosu/issues/11) देखें। Passive inventory के दौरान helper न चलाएँ।

Custom set-user-ID backup wrapper caller द्वारा चुना गया path स्वीकार कर सकता है और उसे `system(3)` को दी गई archive command में जोड़ सकता है। अगर बने हुए command में उस path को quotes में न रखा गया हो, तो child shell [tilde expansion, जो `HOME` का उपयोग करती है, `?` और `*` जैसे pathname patterns, और newline से command separation](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html) लागू कर सकता है; denylist में केवल आम punctuation को रोकने से path literal नहीं बन जाता। सटीक argument flow, inherited environment, child shell और effective identity, filesystem access, और यह जाँचें कि archive output caller को दिखता है या नहीं। SUID bit, archive-tool string या `/root` के literal path को block करना—इनमें से कोई भी अकेले disclosure या code execution साबित नहीं करता। Passive enumeration के दौरान private files archive करने या crash inputs भेजने के बजाय wrapper की copy को offline देखें।

Shell की [command substitution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html), जैसे `$(...)`, metacharacter denylist में एक और संभावित कमी है: निश्चित और अनुमत command prefix भी `/bin/sh -c` के ज़रिए caller-controlled बाद के argument को आगे भेज सकता है। सटीक quoting, parser और effective identity को offline सत्यापित करें; केवल `system()` string या अधूरी denylist को execution का प्रमाण न मानें।

**Calling process tree** भी मायने रखता है। Web worker ऐसा seccomp filter लगा सकता है जो UID बदलने वाले system calls को सीमित करे; [seccomp filters children तक जाते हैं और `execve` के बाद भी बने रहते हैं](https://docs.kernel.org/userspace-api/seccomp_filter.html)। उदाहरण के लिए, Apache के [mpm-itk `LimitUIDRange` और `LimitGIDRange` directives](https://sources.debian.org/src/mpm-itk/2.4.7-04-2/mpm_itk.c/) descendants के लिए उपलब्ध identities को सीमित कर सकते हैं। `/proc/self/status` में `Seccomp: 2` filter mode दिखाता है, policy नहीं; न ही यह बताता है कि यह खास helper अपने owner की identity हासिल कर सकता है या नहीं। वास्तविक invocation की ancestry और effective filter को उसके SUID, mount और `no_new_privs` conditions के साथ देखें; अलग login session की policy अलग हो सकती है, लेकिन उसके लिए भी अपना वैध access path चाहिए।

Custom SUID executable अलग, readable Python script चला सकता है। अगर वह वास्तव में Python **2** इस्तेमाल करता है, तो [`input()` दर्ज expression को evaluate करता है](https://docs.python.org/2/library/functions.html#input); Python 3 में `input()` text लौटाता है। Source line को execution path मानने से पहले wrapper की effective identity, interpreter path और version, script path, और यह पुष्टि करें कि untrusted input उस call तक पहुँचता है। Script पर set-ID bit या privileged wrapper के बिना `input()` call, वही boundary साबित नहीं करते। Enumeration के दौरान चलाने के बजाय binary में referenced paths और script source की सीमित प्रति की समीक्षा करें।

अगर किसी असामान्य SUID executable के साथ readable source मौजूद है, तो caller-controlled हर file read के requested byte count की तुलना destination buffer size से करें और बाद के control-flow checks देखें। [`fread(3)`](https://man7.org/linux/man-pages/man3/fread.3.html) दिए गए pointer पर अनुरोधित items लिखता है; उसे destination object की capacity का पता नहीं होता। Size mismatch, static memory-safety जाँच के लिए एक lead है, उपयोगी privilege escalation का प्रमाण नहीं: पुष्टि करें कि source installed binary से मेल खाता है, caller input दे सकता है, उस context में SUID execution प्रभावी है और संबंधित path तक पहुँचना संभव है। Enumeration के दौरान privileged program को crash inputs भेजने के बजाय source या binary की सीमित प्रति को offline देखें।

Custom SUID helper protected file का content छापे बिना उसे leak कर सकता है। अगर caller pathname और regular expression दोनों चुन सकता है और helper अपनी effective UID के तहत caller को दिखने वाला match count लौटाता है, तो anchored prefix tests से एक-एक character पता लगाने वाला oracle बन सकता है। Helper का owner, effective-ID behavior, executable access, pathname restrictions, regex semantics, response की दृश्यता, और ऐसी किसी खास higher-privilege file की पुष्टि करें जिसे caller अन्यथा पढ़ नहीं सकता। SUID bit या regex library string अकेले इस flow का कोई हिस्सा साबित नहीं करते। Passive enumeration के दौरान असामान्य executable को दर्ज करें और सीमित disassembly या source copy की समीक्षा करें; live helper पर बार-बार guesses न चलाएँ और recovered secrets न छापें।

OpenBSD पर, caller द्वारा चुना गया pathname स्वीकार करने वाला custom set-user-ID reader `/var/backups` के अंतर्गत files उजागर कर सकता है, यदि उसकी effective identity उन्हें पढ़ सकती है और वह उनका content caller को लौटाता है। [OpenBSD का `changelist(5)`](https://man.openbsd.org/changelist.5), configured paths की `.current` और `.backup` copies का वर्णन करता है, लेकिन `+` से शुरू होने वाली entries file content के बजाय SHA-256 checksums रखती हैं; backup directory का owner root और mode `0700` होना चाहिए। `/var` के लिए helper का [`unveil` read rule](https://man.openbsd.org/unveil.2) उस path के नीचे access की अनुमति दे सकता है, लेकिन अपने आप file access देता या साबित नहीं करता। Escalation का दावा करने से पहले वास्तविक effective UID, मौजूदा user के लिए executable permission, स्वीकार किया गया path, backup का मौजूद होना और उसका content, तथा स्वतंत्र authentication की किसी भी ज़रूरत की पुष्टि करें। Passive enumeration में helper और path metadata दर्ज करें; reader न चलाएँ और backup data न छापें।

Caller द्वारा चुने गए pathname को [`stat(2)`](https://man7.org/linux/man-pages/man2/stat.2.html) से जाँचने और बाद में खोलने वाला custom SUID program, caller-writable directory में file या symlink बदलकर race condition पैदा कर सकता है। जाँच पहले वाले object पर लागू होती है, जबकि बाद का [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html) किसी दूसरे object को resolve कर सकता है। पुष्टि करें कि helper elevated effective identity के साथ चल सकता है, किसी अन्यथा reachable code path में चुनी गई file पढ़ी जाती है, और caller जाँच तथा open के बीच pathname बदल सकता है; केवल SUID bit, writable directory या `stat` string इनमें से कुछ भी साबित नहीं करते। Disclosure path के लिए दिखाई देने वाला output या caller द्वारा पढ़ा जा सकने वाला destination भी ज़रूरी है। Binary और path metadata को offline देखें; passive enumeration के दौरान live helper को race न करें।

SGID wrappers पर भी यही dependency review लागू करें। Absolute path से shell या helper चलाने वाला wrapper तब भी unsafe हो सकता है, अगर कम privileges वाला user उस file को बदल सके; शुरू किया गया code wrapper की effective group पा सकता है। सटीक invoked path, उसकी write access (ACLs सहित), wrapper की effective group, और child शुरू करने से पहले privileges छोड़े जाते हैं या नहीं—यह जाँचें। Interpreter inherited effective IDs को छोड़ भी सकता है, इसलिए review candidate और सिद्ध transition में अंतर करें। Host पर कहीं और writable shell होने से अकेले यह साबित नहीं होता कि privileged wrapper उसे चलाता है।

### SQLite CLI को SQL देने वाले privileged wrappers

अगर custom SUID program user-controlled SQL को **`sqlite3` command-line program** देता है, तो query को read-only मानने से पहले सटीक command और effective identity देखें। CLI का `edit()` SQL function editor चलाता है (दूसरे argument या `VISUAL` से), और उसका SQL `load_extension()` function extension loading सक्षम होने पर shared library लोड कर सकता है। CLI process की identity के तहत ये संभावित code-execution paths हैं, भले ही wrapper `PATH` को निश्चित करता हो या absolute `sqlite3` path इस्तेमाल करता हो। SQL का वास्तव में इन functions तक पहुँचना और CLI में संबंधित feature का उपलब्ध रहना ज़रूरी है; केवल binary या host पर `sqlite3` मिलना escalation का प्रमाण नहीं है। SQLite **library** में extension loading default रूप से बंद होती है, इसलिए उसे CLI से अलग समझें। जहाँ किसी privileged application को untrusted SQL process करना हो, वहाँ SQLite का CLI `--safe` mode `edit()`, `load_extension()` और अन्य side-effectful functions को बंद कर देता है। [SQLite CLI documentation](https://www.sqlite.org/cli.html#the_edit_sql_function), [safe-mode documentation](https://www.sqlite.org/cli.html#the_safe_command_line_option) और [extension-loading documentation](https://www.sqlite.org/loadext.html#loading_an_extension) देखें।

### Verbose client को file देने वाले privileged readers

Custom SUID/SGID wrapper caller द्वारा चुने गए pathname की access जाँचकर उस file को दूसरी command को दे सकता है। Access check और बाद के open—दोनों जगह effective identity देखें, वास्तविक base directory के संदर्भ में `../` components resolve करें, और invalid input पर child का behavior जाँचें। अगर database client private file को SQL की तरह पढ़े और verbose output दे, तो SQL invalid होने पर भी वह errors में file का content दिखा सकता है। यह cross-user disclosure तभी है जब child ऐसी file पढ़ सके जिसे caller नहीं पढ़ सकता, caller wrapper के ज़रिए वही file चुन सके, और output दिखाई दे; `mysql` या किसी अन्य client string की मौजूदगी अकेले इनमें से कोई शर्त साबित नहीं करती।

### Netdata `ndsudo` search path

[CVE-2024-32019](https://github.com/netdata/netdata/security/advisories/GHSA-pmhq-4cxq-wj93) से कुछ Netdata `ndsudo` builds प्रभावित हुए थे। Root-owned SUID helper अपने अनुमत external commands को खोजने के लिए caller द्वारा दिए गए `PATH` का उपयोग करता था। Installed helper की समीक्षा करें—उसमें वह helper भी शामिल हो जो caller के सामान्य `PATH` से बाहर हो—लेकिन तभी जब मौजूदा account उसे execute कर सके। उसके owner, SUID bit, executable access (group/ACL grants सहित), installed build और vendor patch status की पुष्टि करें; साथ ही जाँचें कि `NoNewPrivs` या `nosuid` mount identity change रोकता है या नहीं। Netdata patched builds `v1.45.3` और `v1.45.0-169` सूचीबद्ध करता है; distribution backports की अलग से पुष्टि ज़रूरी है। Dashboard version या केवल `ndsudo` की मौजूदगी, reachable escalation का पर्याप्त प्रमाण नहीं है। Path की समस्या के लिए helper का external command को ऐसी जगह से resolve करना भी ज़रूरी है जिसे caller नियंत्रित कर सके।

### Firejail join privilege boundary

[CVE-2022-31214](https://seclists.org/oss-sec/2022/q2/188) ने Firejail के privileged `--join` logic को प्रभावित किया था: crafted join target से setuid-root helper attacker-controlled mount namespace स्वीकार कर सकता था और असुरक्षित security state कॉपी कर सकता था। Passive triage में पुष्टि करें कि **मौजूदा identity root-owned setuid Firejail binary चला सकती है**, उसके mount और process context में setuid प्रभावी है, और installed build में fix नहीं है। Upstream ने [0.9.70](https://github.com/netblue30/firejail/releases/tag/0.9.70) में समस्या ठीक की थी; distribution packages पुराने version को दिखाते हुए भी इसे [backport कर सकते हैं](https://github.com/netblue30/firejail/issues/5191)। ये prerequisites समीक्षा के लिए lead हैं, सफल join या root shell का प्रमाण नहीं। Enumeration के दौरान fake jail न बनाएँ और `--join` न चलाएँ।

### GNU Screen logfile permissions

[CVE-2017-5618](https://lists.gnu.org/archive/html/screen-devel/2017-01/msg00026.html) में Screen 4.5.0 elevated privileges के साथ caller द्वारा चुनी logfile खोलता था। SUID inventory में `screen` या version-suffixed binary होना केवल review lead है: root ownership, मौजूदा user के लिए effective SUID execution, installed build और distribution patch status, तथा प्रभावित logfile behavior की पुष्टि करें। [Debian ने अपने 4.5.0 package में backport से fix किया था](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=852484), इसलिए version string या filename अकेले exposure साबित नहीं करता। Routine enumeration के probe के रूप में logfile न बनाएँ।

[CVE-2017-5899](https://ubuntu.com/security/CVE-2017-5899) ने privileged S-nail mail-lock helper को प्रभावित किया था, जब caller-controlled path component directories से होकर किसी भी file को लिखने तक पहुँच सकता था। जाँचें कि मौजूदा user installed root-owned setuid helper चला सकता है या नहीं, mount और process policy के तहत उसकी setuid identity प्रभावी है या नहीं, और सटीक package build तथा vendor fix क्या है। [Ubuntu के security notice](https://ubuntu.com/security/notices/USN-4820-1) में उसके 16.04 package के लिए backported fix दिया गया है, इसलिए upstream जैसा दिखने वाला version निर्णायक नहीं है। Helper की मौजूदगी यह साबित नहीं करती कि प्रभावित path तक पहुँचा जा सकता है या file write से root execution मिलेगा; enumeration के दौरान helper चलाए या race करने की कोशिश किए बिना metadata और package status देखें।

### snap-confine और tmpfiles cleanup

CVE-2026-3888, privileged `snap-confine` और `/tmp` की systemd-tmpfiles cleanup से जुड़ी race condition है। Passive review में जाँचें कि `snap-confine` setuid है या उसके पास file capabilities हैं, installed `snapd` package की तुलना उस **Ubuntu release** के fixed version से करें, और `/tmp` का प्रभावी age rule तथा cleanup timer देखें। मेल खाने वाला package और rule prerequisites हैं, race के reachable होने का प्रमाण नहीं: runtime timer state, snap layout, package backports और rule overrides भी मायने रखते हैं। पुराने releases में non-default configuration की ज़रूरत हो सकती है। Routine enumeration के दौरान race probe न चलाएँ। Release-specific package status के लिए [Ubuntu CVE record](https://ubuntu.com/security/CVE-2026-3888) और component interaction के लिए [Qualys advisory](https://blog.qualys.com/vulnerabilities-threat-research/2026/03/17/cve-2026-3888-important-snap-flaw-enables-local-privilege-escalation-to-root) देखें।

## ACLs और संवेदनशील paths की जाँच करें

```bash
getfacl -p /path/to/file /path/to/parent 2>/dev/null
namei -l /path/to/file
find /etc /opt /var -type f -writable -ls 2>/dev/null | head -80
ls -la /etc/sudoers.d /etc/ld.so.preload /etc/ld.so.conf.d 2>/dev/null
```

लिखने योग्य parent directory, file के root-owned होने पर भी उसे replace करने की अनुमति दे सकती है। कोई ACL चुपचाप sudoers drop-in, service unit, cron script, library path या credential file तक पहुंच दे सकती है। ACL और पूरा path, दोनों जांचें। अगर किसी भी privileged file में मनमाना लिखना संभव हो, तो [Arbitrary File Write to Root](write-to-root.md) देखें; linker configuration और preload के मामलों के लिए [`ld.so` example](ld.so.conf-example.md) देखें। उजागर backups, `.env` files, database configs, SSH material और history को संभावित credential sources मानें; उन तक पहुंच हर file की वास्तविक permissions से तय होती है।
