# Cron Jobs और Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

शेड्यूल किए गए कार्य मौजूदा shell से अलग identity और environment के साथ चल सकते हैं। cron, `at`, anacron और systemd timers की सूची बनाएँ, फिर हर शेड्यूल किए गए command को उसकी scripts, imports, working directory और writable inputs तक trace करें।

## शेड्यूल की सूची बनाएँ

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontab में आमतौर पर user field होता है; user के crontab में नहीं। वास्तविक scheduler का प्रभावी PATH और environment देखें। `run-parts --test /etc/cron.daily` दिखाता है कि उस host पर कौन-से file names चुने जाएंगे। Control characters किसी entry को सामान्य output में छिपा सकते हैं, इसलिए schedule संदिग्ध लगे तो `cat -A` या `sed -n l` का इस्तेमाल करें।

## Privileged file और command resolution का पता लगाएं

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

लिखने योग्य script chains, `EnvironmentFile=` paths, drop-ins, symlinks, relative commands, wildcard expansion, और privileged task द्वारा copy या execute की जाने वाली binaries की जाँच करें। Timer अपनी `Unit=` setting के ज़रिए अलग नाम वाली service activate कर सकता है। मुख्य primitives की जानकारी के लिए [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md), और [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) पेज देखें।

Scheduled root-run `chkrootkit` script के लिए, पुराने [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) के लिए installed source की जाँच करें: `SLAPPER_FILES` temporary path की जाँच के बाद मौजूद unquoted `file_port=$file_port $i` उस file को execute कर सकता है। वास्तविक script या vendor patch, root scheduling, lower-user की exact temporary path पर write access, उसका executable status, और mount policy सत्यापित करें। केवल version string या `chkrootkit` की मौजूदगी से यह path साबित नहीं होता; passive review के दौरान temporary file न बनाएँ और न चलाएँ।

जब timer की root service `systemctl restart <other>.service` चलाती है, तो एक और unit hop trace करें: restarted unit ऐसे shell को invoke कर सकती है जिसकी script lower-privileged user के लिए writable हो। प्रभावी `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, exact `ExecStart=` arguments, और script तथा उसके parent path की permissions की पुष्टि करें। Writable script केवल एक candidate है, जब तक timer और restarted service उस execution context में active न हों; किसी भी service को restart किए बिना unit properties देखें।

यदि कोई higher-privileged job hostname से script fetch करके response को shell में भेजती है, तो remote script के साथ यह भी जाँचें कि hostname resolution को कौन नियंत्रित करता है। Writable `/etc/hosts` file—जिसमें group या ACL से मिला access भी शामिल है—ऐसे name को redirect कर सकती है जिसे job locally resolve करती है; `curl` response cross-user execution path तभी बनता है, जब scheduled command वास्तव में उस response को चलाए और job प्रभावित resolver path का उपयोग करे। Job की run-as identity, exact URL और shell pipeline, प्रभावी proxy/DNS behavior, तथा file और parent-directory permissions सत्यापित करें। Writable hosts file अपने आप में केवल review cue है, privileged consumer का प्रमाण नहीं। Enumeration के दौरान mapping बदले बिना और script fetch किए बिना schedule और metadata देखें।

Privileged scheduled `wget` fetch एक अलग file-write boundary है, भले ही downloaded body को सीधे कभी execute न किया जाए। [GNU Wget 1.18 changed the default HTTP-to-FTP redirect filename handling to fix CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); पुराने प्रभावित builds redirected FTP filename का उपयोग कर सकते थे, जबकि `--trust-server-names` उस behavior का स्पष्ट अनुरोध करता है। यदि lower-trust party HTTP response और FTP resource नियंत्रित करती है, तो जाँचें कि job उस redirect को follow करती है या नहीं, उसका वास्तविक Wget build या vendor backport, output options, run-as identity, working directory, और क्या destination filename startup file बन सकता है। [Wget loads `WGETRC` or `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), और [its settings can select a POST source or output path](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); बाद का privileged fetch, उससे होने वाले किसी भी disclosure या write के लिए एक अलग prerequisite है। `authbind` के ज़रिए low port का access तभी relevant है, जब caller वास्तव में वह URL serve कर सके जिसकी job को ज़रूरत है। Redirect serve किए बिना या job चलाए बिना configuration और logs का passive review करें। [Raw block-device access through the `disk` group](../user-information/interesting-groups-linux-pe/README.md#disk-group) इस network-fetch path से स्वतंत्र है।

Scripts के साथ data files भी trace करें। Scheduled simulation या orchestration tool ऐसी YAML file पढ़ सकती है जो शुरू किए जाने वाले processes परिभाषित करती है; यदि lower-privileged user उस file को edit कर सकता है और job उसे दूसरे account के अंतर्गत चलाती है, तो data job की identity के तहत commands बन सकता है। Writable YAML file को execution path मानने से पहले exact scheduled command, effective user, file path, parser semantics, और write access (parent directories सहित) सत्यापित करें। Passive triage के लिए schedule और file metadata पढ़ना पर्याप्त है; enumeration के दौरान job न चलाएँ और उसका input न बदलें।

जब higher-privileged job `ssh -F` को ऐसी file के साथ चलाती है जिसे lower-privileged user replace कर सकता है, तो SSH client configuration भी executable input है। OpenSSH का [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) client के shell के ज़रिए local command चलाता है, जबकि `Host`/`Match` और पहले वाले options तय करते हैं कि वह directive लागू होता है या नहीं। इसे cross-user execution path कहने से पहले exact scheduled SSH invocation, run-as identity, चुना गया config path, directory और file write permissions, तथा प्रभावी option order का मिलान करें। इन records की समीक्षा करें; job न चलाएँ और privileged account के रूप में untrusted config load न करें।

Scheduled `scp` के बाद copied script चलाने के लिए `ssh` का उपयोग करने पर, अगर lower-privileged user destination SSH service नियंत्रित करता है, तो एक और trust-boundary review आवश्यक है। यदि वह service connection को दूसरे host तक forward कर सकती है, तो privileged client अनपेक्षित endpoint पर authenticate कर सकता है; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) बदली हुई host key से सुरक्षा कमज़ोर करता है, जो OpenSSH की बाकी पाबंदियों और प्रभावी per-host options के अधीन है। Job की run-as identity, वास्तविक destination और authentication method, remote command की प्रभावी identity, और redirected host पर वही destination path writable है या पहले से मौजूद है—यह स्थापित करें। किसी पुराने या attacker-controlled file का execution होने के लिए copy का fail होना या उस path को miss करना **और** wrapper का SSH command तक जारी रहना, दोनों आवश्यक हैं; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) और explicit status handling इस flow को प्रभावित करते हैं। कमज़ोर host-key setting, दिखता हुआ `sshpass` process, या writable temporary directory अकेले इस chain को साबित नहीं करते। Enumeration के दौरान service redirect किए बिना या job trigger किए बिना schedule, script, SSH configuration और file metadata देखें।

Privileged application scheduler अपनी jobs writable files के बजाय database rows से भी ले सकता है। उदाहरण के लिए, root cron entry जो Laravel का [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) चलाती है, उस application code तक पहुँच सकती है जो task rows पढ़ता है। यदि lower-privileged account local pathname वाली row लिख सकता है और scheduled callback root के अंतर्गत PHP के [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) को call करके प्राप्त body को row द्वारा चुने गए webhook पर भेजता है, तो यह privileged file-disclosure path है। Cron identity, वास्तविक scheduler callback और row-to-path data flow, database write authorization, row पढ़ने के बाद validation, और outbound destination सत्यापित करें। Readable application `.env` केवल credential का संकेत है; web-form validation या database password अकेले row control या disclosure साबित नहीं करते। Enumeration के दौरान database query किए बिना या task schedule किए बिना schedule, code, और credential-file permissions का passive inspection करें।

Event-driven `incron` jobs की भी इसी तरह जाँच करें: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) watched path और event को table owner की identity के अंतर्गत चलने वाले command से जोड़ती हैं। यदि application writable directory से किसी link को follow करके attacker-controlled text watched target में लिखती है, तो lower-privileged user watched file को अप्रत्यक्ष रूप से प्रभावित कर सकता है। वास्तविक table owner, event, target और ancestor permissions, application का link-following behavior, और उस text के command arguments बनने का तरीका सत्यापित करें। खास तौर पर, [GNU Mailutils `mail` accepts `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), और उसका [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) program चला सकता है; उस implementation में untrusted field को अलग option के रूप में देने से command execution हो सकता है। दूसरे `mail` implementations या quoted, fixed argument boundary का behavior अलग हो सकता है। Enumeration के दौरान watched file बदले बिना या job trigger किए बिना schedule, application code और file metadata देखें।

Watched log helper script के ज़रिए user boundary पार कर सकता है। यदि lower-privileged account log में लिख सकता है और `incron` owner उसमें से field पढ़कर नई [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) में डालता है, तो shell उस field को owner की identity के अंतर्गत फिर से parse करता है। Exact watched event, log और parent permissions, helper path, log field का transformation, और resulting command तक पहुँचने की संभावना जाँचें। केवल writable log और `incron` entry दिखने से data flow साबित नहीं होता; passive enumeration के दौरान trigger line न लिखें और helper न चलाएँ।

Certificate-renewal jobs भी यही boundary पार कर सकती हैं। Privileged helper lower-privileged writable directory में मौजूद certificate से X.509 subject पढ़कर उसका common name नई `bash -c` command string में डाल सकता है। [OpenSSL can display a certificate's subject and check its expiry](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash parses the `-c` string as shell input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), इसलिए outer script में variable को quote करने से दूसरी parsing सुरक्षित नहीं होती। इसे command injection कहने से पहले scheduled identity, exact input path और write rights, renewal branch, तथा `bash -c` तक data flow की पुष्टि करें। Enumeration के दौरान script और certificate metadata का passive inspection करें; renewal trigger न करें।

यही second parse तब भी हो सकता है जब privileged scheduled job lower-privileged user के archive या package से name निकालकर उसे `xargs -I` के ज़रिए `sh -c` command string में डालती है। [GNU `xargs -I` replaces the placeholder in initial arguments](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), और [`sh -c` interprets its command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)। भले ही outer script निकाले गए name को quote करे, बाद में substituted shell program सुरक्षित नहीं हो जाता। Job की run-as identity, स्वीकार किए गए exact input path और write access, archive validation और branch conditions, तथा name-to-shell data flow सत्यापित करें। Writable upload directory या `xargs` invocation अकेले केवल एक संकेत हैं; enumeration के दौरान package submit किए बिना या job चलाए बिना schedule, script और path metadata देखें।

Scheduled font या image importer भी caller-supplied archive के *भीतर* के names पर भरोसा कर सकता है, भले ही upload का बाहरी filename सीमित हो। FontForge ने अपनी [upstream change for CVE-2024-25081 and CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367) में archive member-name command injection ठीक किया। पुष्टि करें कि higher-privileged job वास्तव में lower-privileged writable path से archive खोलती है, उसकी run-as identity, exact FontForge build या vendor backport, और archive-handling code path क्या है। केवल version string या अनुमत upload suffix execution का प्रमाण नहीं है। Enumeration के दौरान untrusted archive import किए बिना schedule, path permissions और build metadata देखें।

Scheduled network scanners एक दूसरी boundary पार कर सकते हैं, जब custom script remote TLS certificate subject को local filename की तरह इस्तेमाल करती है। [Nmap NSE runs selected scripts without a sandbox](https://nmap.org/book/nse-usage.html), इसलिए वास्तविक script देखें कि क्या वह बिना containment checks के untrusted subject field को data directory के साथ जोड़ती है। File disclosure के लिए scheduler द्वारा scan किया जाने वाला target, scanner की run-as identity द्वारा readable file तक resolve होने वाला path, और lower-privileged reader तक पहुँचने वाली report या log आवश्यक हैं। Certificate field या installed scanner अकेले उस chain को साबित नहीं करते; passive enumeration के दौरान नया target scan किए बिना schedule, script, path resolution और report destination की समीक्षा करें।

Privileged cron command जो Ansible runner को `/path/to/tasks/*.yml` जैसा shell glob देती है, उस directory की permissions की जाँच की मांग करती है, भले ही हर मौजूदा playbook read-only हो। Globbed directory में write और search access वाला user एक और matching playbook बना सकता है। [Ansible playbooks define tasks that the runner executes](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), लेकिन custom wrapper paths filter कर सकती है या अलग identity इस्तेमाल कर सकती है: directory को execution path मानने से पहले उसका behavior, वास्तविक cron user, shell expansion, ACLs, sticky bit, और mount policy सत्यापित करें। Metadata और wrapper का static inspection करें; enumeration के दौरान scheduled job न चलाएँ।

Privileged cron wrapper glob expand करने के बाद upload directory के filenames Perl helper को दे सकती है। Perl का [`<>` diamond operator uses two-argument `open`](https://perldoc.perl.org/perlop#The-Null-Filehandle), इसलिए matching filename को pipe command के रूप में समझे जाने पर वह helper की identity के अंतर्गत execute हो सकता है; [`<<>>` treats arguments as literal filenames](https://perldoc.perl.org/perlop#The-Null-Filehandle)। Scheduler identity, wrapper की working directory और glob, helper का वास्तविक `@ARGV` handling, filename restrictions, और यह कि lower-privileged identity filesystem rights या authenticated upload service के ज़रिए matching name रख सकती है या नहीं—इसकी पुष्टि करें। Cron line, Perl script, या writable FTP directory अकेले पूरी chain साबित नहीं करते। Enumeration के दौरान crafted filename submit किए बिना या job चलाए बिना source और metadata देखें।

Read-only cron script को भी replace किया जा सकता है, यदि scheduled account उसे pathname से चलाता है और lower-privileged user उसकी non-sticky parent directory में write तथा traverse कर सकता है। Schedule की run-as identity, path के हर component, directory sticky bit, ACLs और mount policy जाँचें; file को move किए बिना या job चलाए बिना metadata देखें।

Privileged PHP cron wrapper ऐसे helper तक पहुँच सकती है जो अभी मौजूद ही न हो। यदि वह PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) को fixed absolute helper path के साथ call करती है, तो उसके parent directory में वह नाम बना सकने वाला lower-privileged user बाद में चलने वाले helper को नियंत्रित कर सकता है। पुष्टि करें कि cron entry वास्तव में wrapper को higher identity के अंतर्गत चलाती है, exact command string और PHP execution policy, helper directory पर write और search rights, symlink और sticky-bit behavior, तथा helper path अब भी अनुपस्थित है या नहीं। Writable directory या missing helper अकेले केवल संकेत हैं; Enumeration के दौरान helper बनाए बिना या job trigger किए बिना schedule, source और path metadata देखें।

Scheduled job `find` से input scripts खोजकर हर script को interpreter में भी भेज सकती है। उदाहरण के लिए, [gnuplot's `system()` function invokes a shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), इसलिए lower-privileged user की writable directory में हर `*.plt` file पर `gnuplot` चलाने वाली privileged job, job की identity के साथ commands execute कर सकती है। [Directory read permission controls listing, while write and search (`x`) control creating and accessing known names](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); directory को `ls` से list न कर पाने पर भी write और search access जाँचें। Exact scheduler identity और command, interpreter का behavior, चुना गया file pattern, और directory permissions का मिलान करें; writable directory या installed interpreter अकेले escalation साबित नहीं करते। Private schedules और कम समय चलने वाली jobs के लिए अधिकृत event observation की ज़रूरत हो सकती है, क्योंकि एक process snapshot उन्हें miss कर सकता है।

Privileged PHP job के लिए executable script chain के हिस्से के रूप में literal `include`/`require` statements भी जाँचें। [PHP evaluates included files](https://www.php.net/manual/en/function.include.php), इसलिए group-writable included `.php` file job की identity के अंतर्गत code चला सकती है, भले ही मुख्य script read-only हो। Scheduled identity, प्रभावी include-path resolution, file और directory permissions, तथा job के वास्तव में चलने की पुष्टि करें; comment में दिया sample cron line केवल एक संकेत है। यही समीक्षा root-owned [PHP built-in server](https://www.php.net/commandline.webserver) पर भी लागू होती है, जिसे `-S` और `-t <document-root>` के साथ शुरू किया गया हो: loopback listener भी local requests के लिए application PHP execute कर सकता है। Enumeration के दौरान कोई trigger invoke किए बिना process और source देखें।

Privileged PHP job **data file** के ज़रिए भी boundary पार कर सकती है: यदि lower-privileged user [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) को दी गई exact file बदल सकता है, तो object restore करते समय PHP किसी loaded class का `__wakeup()` या `__unserialize()` method invoke कर सकता है। Job की effective identity, file और ancestor permissions, loaded classes, तथा वास्तविक method side effects—जैसे property द्वारा चुनी गई file write—की समीक्षा करें। Writable log या `unserialize()` call अकेले उपयोगी path साबित नहीं करते। Enumeration के दौरान serialized input लिखे बिना या job चलाए बिना source और metadata देखें।

Root cron task web server के बजाय PHP application का **CLI page runner** invoke कर सकती है। Runner के चुने गए document root और URI को वास्तविक PHP entrypoint तक trace करें; यदि वह entrypoint web-service account के लिए writable है, तो runner और cron wrapper read-only होने पर भी scheduled CLI request बदला हुआ code root के रूप में execute कर सकती है। Scheduler identity, exact URI-to-file resolution, प्रभावी file और ancestor permissions, तथा entrypoint पर integrity check लागू है या नहीं—इसकी पुष्टि करें। Enumeration के दौरान runner invoke किए बिना या page बदले बिना source और metadata देखें।

Shared working directory से scheduled job या किसी दूसरे user द्वारा शुरू किए गए `ipython` process के startup files की समीक्षा करें। [IPython's security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) बताती हैं कि CVE-2022-21699 के fix से पहले प्रभावित builds current directory में profiles और configuration—जिसमें `profile_default/startup` code भी शामिल था—खोजते थे। वास्तविक installed build या vendor patch, command working directory, higher-privileged process identity, और exact startup path पर lower-privileged user के write और search access का मिलान करें। Installed `ipython`, writable directory, या version string अकेले यह साबित नहीं करते कि कोई दूसरी identity वहाँ की file load करेगी। Higher-privileged interpreter शुरू किए बिना schedule और path metadata देखें।

Custom native extension के functions call करने वाले privileged PHP server के लिए, extension की समीक्षा से पहले service का PHP SAPI और उसकी प्रभावी `php.ini` तथा scanned `.ini` files trace करें। [PHP loads configured `extension` libraries at startup](https://www.php.net/manual/en/ini.core.php), और [CLI and web SAPIs can use different configuration files](https://www.php.net/manual/en/configuration.file.php)। इसलिए कोई reachable login form या local listener user-controlled strings को service identity के अंतर्गत चल रहे compiled code तक पहुँचा सकता है। Unit का `User=`, `ExecStart=`, working directory, वास्तविक extension path, और caller-controlled arguments दर्ज करें; केवल `.so` की मौजूदगी या loopback socket से memory-corruption flaw साबित नहीं होता। Passive enumeration के दौरान probes भेजने के बजाय किसी भी custom parser का अलग से विश्लेषण करें।

जब privileged wrapper किसी script को pathname से hash करती है और बाद में execute करने के लिए उसी pathname को फिर खोलती है, तो digest केवल पहले open के दौरान पढ़े गए object को authenticate करता है। यदि lower-privileged user उन दोनों opens के बीच script की directory entry replace कर सकता है, तो बाद में execution किसी अलग object को resolve कर सकता है, भले ही original script file root-owned हो। FIFO check phase को लंबा कर सकता है, लेकिन यह path replace किए जा सकने वाले parent-directory rights, वास्तव में अलग opens, scheduler identity, sticky-bit और mount rules, तथा timing पर निर्भर करता है। Wrapper और `namei -l` output को passive संकेत के रूप में देखें; सफल checksum इस बात का प्रमाण नहीं है कि बाद वाला pathname सुरक्षित है।

Privileged backup job attacker-supplied commands execute किए बिना भी data **disclose** कर सकती है। Trace करें कि क्या lower-privileged user ऐसा control file बना सकता है जिसे job पढ़ती है, क्या job फिर `/etc/shadow` जैसे protected source को खोलती है, और क्या attacker द्वारा चुने गए URL या readable output को नतीजा मिलता है। इसे disclosure path कहने से पहले इन तीनों भागों की पुष्टि करें। उसी script में fixed shell command होने से control file अपने आप shell-injection input नहीं बनती। Enumeration के दौरान job चलाए बिना या control file रखे बिना script और file permissions देखें।

यदि privileged scheduled job `curl -K FILE` या `curl --config FILE` चलाती है, तो [curl treats options in that file as command-line arguments](https://curl.se/docs/manpage.html)। वह exact file curl के पढ़ते समय नियंत्रित करने वाला lower-privileged user अनुरोधित URL, local-file input, या output path को प्रभावित कर सकता है। Protected read या write का दावा करने से पहले job की effective identity, file और ancestor पर write rights, file को replace करने वाली किसी अन्य job का timing, और config options का fixed command-line options के साथ व्यवहार सत्यापित करें। Writable config path या दिखता हुआ `-K` flag अकेले यह साबित नहीं करते कि चुने गए options प्रभावी होंगे; passive enumeration के दौरान job चलाए बिना या URL fetch किए बिना schedule और metadata देखें।

यदि cron entry helper script invoke करती है, तो helper की working directory और archive command भी देखें। किसी दूसरे user के writable directory पर unquoted wildcard filenames को archiver options बना सकता है; GNU tar के checkpoint actions इसका एक उदाहरण हैं। Cross-user command path का दावा करने से पहले scheduled run-as identity, writable input directory, exact archiver और options, तथा option parsing को समाप्त करने वाले `--` की मौजूदगी सत्यापित करें। [wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md) देखें।

Backup-file disclosure का एक अलग path तब बन सकता है जब privileged helper यह जाँच किए बिना `cd INPUT_DIR; tar ... *` चलाती है कि `cd` सफल हुआ या नहीं। यदि lower-privileged user `INPUT_DIR` को हटा या replace कर सकता है, तो `cd` fail होने पर shell अपनी पिछली directory में रह सकती है, जिसे बाद की archive command पढ़ सकती है। Job की initial working directory, वास्तव में संभव failed-`cd` path, script exit करती है या `&&` का उपयोग करती है, exact archiver options, और output archive lower user के लिए readable है या नहीं—यह सत्यापित करें। Writable input directory या readable archive अकेले केवल संकेत हैं; live job बदले बिना helper और path permissions देखें।

Scheduled executable shell script को छिपा सकती है; इससे trust boundary खत्म नहीं होती: [SHc](https://github.com/neurobin/shc) encrypted script text को native binary में wrap करता है और runtime पर shell के ज़रिए चलाता है। `.sh.x` suffix या opaque ELF केवल review के संकेत हैं। Filename option injection का आकलन करने के लिए privileged scheduler identity, helper की वास्तविक working directory और command, वहाँ matching names बनाने की lower-user की क्षमता, तथा unquoted glob का option boundary के बिना `rsync` जैसी command तक पहुँचना स्थापित करें। [`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) तभी relevant है जब वही exact command path इस्तेमाल हो। Restricted `/proc` visibility या असफल static decryption से command अज्ञात रहती है; केवल उसे classify करने के लिए privileged helper न चलाएँ।

Process command-line text भी privileged helper के लिए एक और untrusted input है। Lower-privileged user ऐसा process title या `argv[0]` चुन सकता है जो `pgrep -f` से match करे; matching name executable या उसके owner को authenticate नहीं करता। यदि root-run script उस text को capture करके उसके किसी हिस्से को `apache2ctl`/`httpd` में बदलती है और fixed argument array के बिना नतीजे को execute करती है, तो attacker-chosen options अलग configuration directory या error log चुन सकते हैं। Apache configuration parsing modules load कर सकती है या configured helpers तक पहुँच सकती है, इसलिए enumeration के दौरान root के रूप में untrusted configuration validate न करें। Scheduler owner, exact helper, process identity, और data-to-argument flow देखें; जब तक shell metacharacter execution अलग से साबित न हो, यह option/configuration injection है।

Untrusted text को Bash arithmetic में देने वाला root-run parser उस text में substitutions execute कर सकता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) में worked example दिया गया है। हर arithmetic expression को exploitable मानने से पहले input source और parsing command की पुष्टि करें।

Application log parse करने वाली privileged job के लिए, पहले parse के बाद भी untrusted fields को trace करें। Lower-privileged account अपने मौजूदा process group के ज़रिए log में लिख सकता है या logged request fields को प्रभावित कर सकता है; कोई record फिर image चुन सकता है, जिसके metadata का उपयोग XML खोलने के लिए दूसरी pathname के रूप में हो सकता है। Job की effective identity, log पर वास्तविक write access, delimiter handling, canonical path containment, और चुनी गई XML attacker-controlled है या नहीं—जाँचें। यदि expanded result lower-privileged user के लिए readable output तक पहुँचता है, तो external-entity expansion उस दूसरी read को privileged file disclosure में बदल सकती है। [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) external DTD/entity access के controls बताती है; installed parser और उसकी effective settings देखें। Writable log या XML file अकेले केवल संकेत हैं। Enumeration के दौरान scheduled parser को input दिए बिना code और metadata की समीक्षा करें।

उन privileged jobs की भी जाँच करें जो दूसरे user की Git repository से files materialize करती हैं। कोई script `git checkout` के बजाय `git ls-tree` और `git cat-file` इस्तेमाल कर सकती है, फिर भी staging directory के साथ attacker-controlled tree paths जोड़ते समय उन पर भरोसा कर सकती है। यदि destination को लिखने से पहले normalize करके containment check न किया जाए, तो absolute paths और `..` components उस directory से बाहर जा सकते हैं। `git -c safe.directory=*` अलग ownership वाली repositories तक access की अनुमति देता है; यह अपने आप arbitrary-write condition नहीं बनाता।

Root-run database backup एक और ownership boundary बना सकता है। PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) source data directory में रखी अतिरिक्त regular files को copy करता है, और उसका default plain format `-D` में directory tree के रूप में files लिखता है। यदि lower-privileged account उन source files को बना या बदल सकता है, तो resulting destination की ownership और mode, उसका path traversable और executable है या नहीं, तथा mount पर `nosuid` लगा है या नहीं—जाँचें। Preserved set-ID permissions वाली root-owned copy खतरनाक हो सकती है; केवल tar backup, stripped permissions, या inaccessible destination से वही path साबित नहीं होता। Backup command को finding मानने से पहले scheduled wrapper और effective user trace करें।

## कम समय चलने वाले काम देखें

एक process snapshot ऐसी job को miss कर सकता है जो कुछ milliseconds तक चलती है। Timer/cron declarations की logs से तुलना करें और, जहाँ अधिकृत हो, `pspy` या audit जैसे process-event monitoring का उपयोग करें। Scheduled owner, exact command line, और task द्वारा पढ़ी या लिखी जाने वाली files का मिलान करें। Loopback scheduler web UI एक अलग interface है; [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc) देखें।
