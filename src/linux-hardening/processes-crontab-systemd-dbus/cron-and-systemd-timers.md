# Cron Jobs y timers de systemd

{{#include ../../banners/hacktricks-training.md}}

Las tareas programadas pueden ejecutarse con una identidad y un entorno distintos de los del shell actual. Enumera cron, `at`, anacron y los timers de systemd, y luego rastrea cada comando programado a través de sus scripts, imports, directorio de trabajo y entradas modificables.

## Enumerar las programaciones

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Las crontabs del sistema suelen incluir un campo de usuario; la crontab de un usuario no. Inspecciona el PATH efectivo y el entorno del scheduler real. `run-parts --test /etc/cron.daily` muestra qué nombres de archivo se seleccionarían en ese host. Los caracteres de control pueden ocultar una entrada a simple vista, así que usa `cat -A` o `sed -n l` cuando una programación parezca sospechosa.

## Rastrea la resolución de archivos y comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revisa las cadenas de scripts modificables, las rutas de `EnvironmentFile=`, los drop-ins, los symlinks, los comandos relativos, la expansión de comodines y los binarios que una tarea privilegiada copia o ejecuta. Un timer puede activar un servicio con otro nombre mediante su ajuste `Unit=`. Las páginas sobre [PATH](../linux-basics/linux-environment-variables.md#path), [comodines](../interesting-files-permissions/wildcards-spare-tricks.md) y [enlaces a archivos](../main-system-information/filesystem-links-and-file-descriptors.md) explican los principales componentes.

Para un script programado de `chkrootkit` que se ejecuta como root, inspecciona el código fuente instalado para detectar el antiguo [defecto de comillas en slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): un `file_port=$file_port $i` sin comillas después de comprobar una ruta temporal de `SLAPPER_FILES` puede ejecutar ese archivo. Verifica el script real o el parche del proveedor, la programación como root, el acceso de escritura de un usuario menos privilegiado a la ruta temporal exacta, si es ejecutable y la política de montaje. Una cadena de versión o la mera presencia de `chkrootkit` no demuestra que la ruta sea explotable; no crees ni ejecutes un archivo temporal durante una revisión pasiva.

Sigue un salto más entre unidades si el servicio root de un timer ejecuta `systemctl restart <other>.service`: la unidad reiniciada puede invocar un shell con un script modificable por un usuario menos privilegiado. Confirma los valores efectivos de `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, los argumentos exactos de `ExecStart=` y los permisos del script y de su ruta padre. Un script modificable solo es un candidato hasta que el timer y el servicio reiniciado estén activos en ese contexto de ejecución; inspecciona las propiedades de las unidades sin reiniciar ninguno de los servicios.

Si un trabajo con privilegios elevados obtiene un script mediante un hostname y pasa la respuesta a un shell, comprueba quién controla la resolución de ese hostname y también el script remoto. Un archivo `/etc/hosts` modificable, incluso mediante permisos de grupo o una ACL, puede redirigir un nombre que el trabajo resuelva localmente; una respuesta de `curl` solo se convierte en una ruta de ejecución entre usuarios cuando el comando programado realmente ejecuta esa respuesta y el trabajo utiliza la ruta de resolución afectada. Verifica la identidad de ejecución del trabajo, la URL exacta y la canalización del shell, el comportamiento efectivo del proxy/DNS y los permisos del archivo y del directorio padre. Un archivo hosts modificable por sí solo es una señal para revisar, no una prueba de que exista un consumidor privilegiado. Inspecciona la programación y los metadatos sin cambiar la asignación ni obtener el script durante la enumeración.

Una descarga programada de `wget` con privilegios es una frontera de escritura de archivos independiente, aunque el cuerpo descargado nunca se ejecute directamente. [GNU Wget 1.18 cambió el manejo predeterminado del nombre de archivo en redirecciones HTTP a FTP para corregir CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); las versiones afectadas anteriores podían usar el nombre de archivo de la redirección FTP, mientras que `--trust-server-names` solicita explícitamente ese comportamiento. Si una parte de menor confianza controla la respuesta HTTP y el recurso FTP, comprueba si el trabajo sigue esa redirección, la versión real de Wget o el backport del proveedor, las opciones de salida, la identidad de ejecución, el directorio de trabajo y si el nombre de destino puede convertirse en un archivo de inicio. [Wget carga `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), y [sus ajustes pueden seleccionar una fuente POST o una ruta de salida](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); una descarga privilegiada posterior es un requisito distinto para cualquier divulgación o escritura resultante. El acceso a un puerto bajo mediante `authbind` solo es relevante cuando el llamante puede servir la URL que solicita el trabajo. Revisa la configuración y los logs de forma pasiva, sin servir una redirección ni ejecutar el trabajo. El [acceso a dispositivos de bloques sin procesar mediante el grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) es independiente de esta ruta de descarga de red.

Sigue también los archivos de datos, no solo los scripts. Una herramienta programada de simulación u orquestación puede leer un archivo YAML que define los procesos que debe iniciar; si un usuario menos privilegiado puede editar ese archivo y el trabajo lo ejecuta con otra cuenta, los datos pueden convertirse en comandos ejecutados con la identidad del trabajo. Verifica el comando programado exacto, el usuario efectivo, la ruta del archivo, la semántica del parser y los permisos de escritura (incluidos los de los directorios padre) antes de considerar un YAML modificable como una ruta de ejecución. Para una clasificación pasiva basta con leer la programación y los metadatos del archivo; no ejecutes el trabajo ni modifiques su entrada durante la enumeración.

La configuración de un cliente SSH también es una entrada ejecutable cuando un trabajo con privilegios elevados ejecuta `ssh -F` con un archivo que un usuario menos privilegiado puede reemplazar. OpenSSH ejecuta [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) como un comando local mediante el shell del cliente, mientras que `Host`/`Match` y las opciones anteriores determinan si se aplica esa directiva. Correlaciona la invocación SSH programada exacta, la identidad de ejecución, la ruta de configuración seleccionada, los permisos de escritura del directorio y del archivo, y el orden efectivo de las opciones antes de clasificarlo como una ruta de ejecución entre usuarios. Revisa estos registros sin ejecutar el trabajo ni cargar la configuración no confiable como la cuenta privilegiada.

Una ejecución programada de `scp` seguida de `ssh` para ejecutar el script copiado requiere revisar una segunda frontera de confianza si un usuario menos privilegiado controla el servicio SSH de destino. Si ese servicio puede reenviar la conexión a otro host, el cliente privilegiado podría autenticarse en un endpoint no previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) debilita la protección ante cambios de clave de host, sujeto a las restricciones restantes de OpenSSH y a las opciones efectivas por host. Determina la identidad de ejecución del trabajo, el destino y el método de autenticación reales, la identidad efectiva del comando remoto y si la misma ruta de destino es modificable o ya existe en el host redirigido. Ejecutar un archivo antiguo o controlado por un atacante requiere además que la copia falle o no encuentre esa ruta **y** que el wrapper continúe con su comando SSH; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) y el manejo explícito del estado afectan ese flujo. Una configuración débil de la clave de host, un proceso `sshpass` visible o un directorio temporal modificable no demuestran por sí solos esta cadena. Inspecciona la programación, el script, la configuración SSH y los metadatos de los archivos sin redirigir el servicio ni activar el trabajo durante la enumeración.

Un scheduler de aplicaciones privilegiado puede obtener sus trabajos de filas de una base de datos, en vez de archivos modificables. Por ejemplo, una entrada de cron de root que invoque [`php artisan schedule:run` de Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) puede llegar a código de la aplicación que lee filas de tareas. Si una cuenta menos privilegiada puede escribir una fila que contenga una ruta local y el callback programado llama a [`file_get_contents` de PHP](https://www.php.net/manual/en/function.file-get-contents.php) como root y envía el cuerpo obtenido a un webhook indicado por la fila, se trata de una ruta privilegiada de divulgación de archivos. Verifica la identidad de cron, el callback real del scheduler y el flujo de datos de la fila a la ruta, la autorización de escritura en la base de datos, la validación posterior a la lectura de la fila y el destino de salida. Un `.env` de la aplicación legible solo es una pista sobre credenciales; la validación de un formulario web o una contraseña de base de datos por sí solas no demuestran que se pueda controlar la fila ni que haya divulgación. Inspecciona la programación, el código y los permisos del archivo de credenciales de forma pasiva, sin consultar la base de datos ni programar una tarea durante la enumeración.

Los trabajos basados en eventos de `incron` también merecen revisión: las [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) asocian una ruta vigilada y un evento con un comando que se ejecuta con la identidad del propietario de la tabla. Un usuario menos privilegiado puede influir indirectamente en un archivo vigilado si una aplicación sigue un enlace desde un directorio modificable y escribe texto controlado por el atacante en el destino vigilado. Verifica el propietario real de la tabla, el evento, los permisos del destino y sus directorios antecesores, el comportamiento de la aplicación al seguir enlaces y cómo ese texto se convierte en argumentos del comando. En particular, [`mail` de GNU Mailutils acepta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), y su [comando de escape al shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) puede ejecutar un programa; un campo no confiable pasado como opción independiente a esa implementación puede permitir la ejecución de comandos. Otras implementaciones de `mail` o un límite de argumentos fijo y entrecomillado pueden comportarse de otra manera. Inspecciona la programación, el código de la aplicación y los metadatos de los archivos sin modificar el archivo vigilado ni activar el trabajo durante la enumeración.

Un log vigilado también puede cruzar una frontera entre usuarios mediante un script auxiliar. Si una cuenta menos privilegiada puede escribir en el log y el propietario de `incron` lee un campo de este y lo inserta en una nueva cadena de comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), el shell analiza de nuevo ese campo con la identidad del propietario. Comprueba el evento vigilado exacto, los permisos del log y de su directorio padre, la ruta del helper, la transformación del campo del log y si se llega a ejecutar el comando resultante. Ver un log modificable y una entrada de `incron` no demuestra por sí solo el flujo de datos; no escribas una línea de activación ni ejecutes el helper durante la enumeración pasiva.

Los trabajos de renovación de certificados pueden cruzar la misma frontera. Un helper privilegiado puede leer el subject X.509 de un certificado en un directorio modificable por un usuario menos privilegiado e insertar su nombre común en una nueva cadena de comando `bash -c`. [OpenSSL puede mostrar el subject de un certificado y comprobar su caducidad](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analiza la cadena `-c` como entrada del shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), así que entrecomillar la variable en el script externo no protege el segundo análisis. Confirma la identidad programada, la ruta de entrada exacta y los permisos de escritura, la rama de renovación y el flujo de datos hasta `bash -c` antes de considerarlo una inyección de comandos. Inspecciona el script y los metadatos del certificado de forma pasiva; no actives la renovación durante la enumeración.

El mismo segundo análisis puede producirse cuando un trabajo privilegiado programado extrae un nombre del archivo de un usuario menos privilegiado y lo canaliza a `xargs -I` para insertarlo en una cadena de comando `sh -c`. [`xargs -I` de GNU reemplaza el marcador en los argumentos iniciales](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), y [`sh -c` interpreta su cadena de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Aunque el script externo entrecomille el nombre extraído, eso no hace segura una ejecución posterior de un programa de shell sustituido. Verifica la identidad de ejecución del trabajo, la ruta de entrada aceptada exacta y los permisos de escritura, la validación del archivo y las condiciones de la rama, y el flujo del nombre al shell. Un directorio de carga modificable o una invocación de `xargs` son solo indicios; inspecciona la programación, el script y los metadatos de las rutas sin enviar un paquete ni ejecutar el trabajo durante la enumeración.

Un importador programado de fuentes o imágenes también puede confiar en nombres *dentro* de un archivo suministrado por el usuario, aunque el nombre externo de la carga esté restringido. FontForge corrigió la inyección de comandos mediante nombres de miembros de archivos en su [cambio upstream para CVE-2024-25081 y CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirma que un trabajo con privilegios elevados realmente abra un archivo desde una ruta modificable por un usuario menos privilegiado, su identidad de ejecución, la versión exacta de FontForge o el backport del proveedor, y la ruta de manejo del archivo. Una cadena de versión o un sufijo de carga permitido no demuestran la ejecución. Inspecciona la programación, los permisos de la ruta y los metadatos de la compilación sin importar un archivo no confiable durante la enumeración.

Los scanners de red programados pueden cruzar una frontera diferente si un script personalizado trata el subject de un certificado TLS remoto como un nombre de archivo local. [Nmap NSE ejecuta los scripts seleccionados sin sandbox](https://nmap.org/book/nse-usage.html), así que inspecciona el script real y comprueba si une un campo subject no confiable con un directorio de datos sin verificar la contención. La divulgación de archivos requiere un destino que el scheduler vaya a escanear, una ruta que resuelva a un archivo legible por la identidad de ejecución del scanner, y un informe o log accesible para un usuario menos privilegiado. Un campo de certificado o la mera presencia de un scanner no demuestran esa cadena; revisa la programación, el script, la resolución de rutas y el destino del informe sin escanear un destino nuevo durante una enumeración pasiva.

Un comando de cron privilegiado que pasa un comodín del shell como `/path/to/tasks/*.yml` a un ejecutor de Ansible merece comprobar los permisos del directorio, aunque todos los playbooks existentes sean de solo lectura. Un usuario con permisos de escritura y búsqueda en el directorio al que se expande el comodín podría crear otro playbook coincidente. [Los playbooks de Ansible definen las tareas que ejecuta el runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), pero un wrapper personalizado puede filtrar rutas o usar otra identidad: verifica su comportamiento, el usuario real de cron, la expansión del shell, las ACL, el sticky bit y la política de montaje antes de considerar el directorio una ruta de ejecución. Inspecciona los metadatos y el wrapper de forma estática; no ejecutes el trabajo programado durante la enumeración.

Un wrapper de cron privilegiado puede pasar nombres de archivo de un directorio de carga a un helper de Perl después de expandir un comodín. El operador [`<>` de Perl usa `open` con dos argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), así que un nombre coincidente interpretado como un comando canalizado puede ejecutarse con la identidad del helper; [`<<>>` trata los argumentos como nombres de archivo literales](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirma la identidad del scheduler, el directorio de trabajo y el comodín del wrapper, el manejo real de `@ARGV` por el helper, las restricciones de nombres y si una identidad menos privilegiada puede crear un nombre coincidente mediante permisos del sistema de archivos o un servicio de carga autenticado. Una línea de cron, un script de Perl o un directorio FTP modificable no demuestran por sí solos la cadena completa. Inspecciona el código fuente y los metadatos sin enviar un nombre de archivo diseñado para ello ni ejecutar el trabajo durante la enumeración.

Un script de cron de solo lectura sigue siendo reemplazable si la cuenta programada lo ejecuta mediante una ruta y el usuario menos privilegiado puede escribir y atravesar su directorio padre no sticky. Comprueba la identidad de ejecución del trabajo, cada componente de la ruta, el sticky bit del directorio, las ACL y la política de montaje; revisa los metadatos sin mover el archivo ni ejecutar el trabajo.

Un wrapper de cron PHP privilegiado puede llegar a un helper que aún no existe. Si llama a [`exec()` de PHP](https://www.php.net/manual/en/function.exec.php) con una ruta absoluta fija al helper, un usuario menos privilegiado que pueda crear ese nombre en el directorio padre podría controlar lo que se ejecutará en una ejecución posterior. Confirma que la entrada de cron ejecuta realmente el wrapper con la identidad más privilegiada, la cadena de comando exacta y la política de ejecución de PHP, los permisos de escritura y búsqueda en el directorio del helper, el comportamiento de symlinks y sticky bit, y si la ruta del helper sigue vacante. Un directorio modificable o la ausencia de un helper son solo indicios; inspecciona la programación, el código fuente y los metadatos de la ruta sin crear el helper ni activar el trabajo.

Un trabajo programado también puede descubrir scripts de entrada con `find` y pasarlos a un intérprete. Por ejemplo, la función `system()` de [gnuplot invoca un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), así que un trabajo privilegiado que ejecute `gnuplot` con cada archivo `*.plt` de un directorio modificable por un usuario menos privilegiado puede ejecutar comandos con la identidad del trabajo. [El permiso de lectura del directorio controla su listado, mientras que los permisos de escritura y búsqueda (`x`) controlan la creación y el acceso a nombres conocidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); comprueba los permisos de escritura y búsqueda incluso cuando `ls` no puede listar el directorio. Correlaciona la identidad y el comando exactos del scheduler, el comportamiento del intérprete, el patrón de archivos seleccionados y los permisos del directorio; un directorio modificable o la presencia de un intérprete no demuestran por sí solos una escalada. Los schedules privados y los trabajos breves pueden requerir observación autorizada de eventos, ya que una sola captura de procesos puede no detectarlos.

Para un trabajo PHP privilegiado, inspecciona los `include`/`require` literales como parte de la cadena de scripts ejecutables. [PHP evalúa los archivos incluidos](https://www.php.net/manual/en/function.include.php), así que un archivo `.php` modificable por el grupo puede ejecutar código con la identidad del trabajo, aunque el script principal sea de solo lectura. Verifica la identidad programada, la resolución efectiva de `include_path`, los permisos de archivos y directorios, y si el trabajo realmente se ejecuta; una línea de cron de ejemplo en un comentario es solo un indicio. La misma revisión se aplica a un [servidor integrado de PHP](https://www.php.net/commandline.webserver) propiedad de root e iniciado con `-S` y `-t <document-root>`: un listener en loopback aún puede ejecutar PHP de la aplicación ante solicitudes locales. Inspecciona el proceso y el código fuente sin activar ninguno de los dos mecanismos durante la enumeración.

Un trabajo PHP privilegiado también puede cruzar la frontera a través de un **archivo de datos**: si un usuario menos privilegiado puede modificar el archivo exacto pasado a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP puede invocar el método `__wakeup()` o `__unserialize()` de una clase cargada al restaurar el objeto. Revisa la identidad efectiva del trabajo, los permisos del archivo y de sus directorios antecesores, las clases cargadas y los efectos reales del método, como escribir un archivo cuya ruta se selecciona mediante una propiedad. Un log modificable o una llamada a `unserialize()` por sí solos no demuestran una ruta viable. Inspecciona el código fuente y los metadatos sin escribir datos serializados ni ejecutar el trabajo durante la enumeración.

Una tarea de cron de root puede invocar el **ejecutor de páginas CLI** de una aplicación PHP en lugar del servidor web. Sigue la raíz de documentos y el URI seleccionados por el ejecutor hasta el punto de entrada PHP real; si la cuenta del servicio web puede modificar ese punto de entrada, la solicitud CLI programada puede ejecutar el código alterado como root, aunque el ejecutor y el wrapper de cron sean de solo lectura. Confirma la identidad del scheduler, la resolución exacta de URI a archivo, los permisos efectivos del archivo y de sus directorios antecesores, y si el propio punto de entrada está protegido por una comprobación de integridad. Inspecciona el código fuente y los metadatos sin invocar el ejecutor ni modificar la página durante la enumeración.

Un proceso `ipython` iniciado por un trabajo programado u otro usuario desde un directorio de trabajo compartido merece revisar los archivos de inicio. Las [notas de seguridad de IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explican que las versiones afectadas buscaban perfiles y configuración en el directorio actual, incluido el código de `profile_default/startup`, antes de la corrección de CVE-2022-21699. Correlaciona la versión instalada real o el parche del proveedor, el directorio de trabajo del comando, la identidad del proceso con privilegios elevados y la capacidad del usuario menos privilegiado para escribir y buscar en la ruta de inicio exacta. La presencia de `ipython`, un directorio modificable o una cadena de versión no demuestran por sí solos que otra identidad vaya a cargar un archivo desde allí. Inspecciona la programación y los metadatos de la ruta sin iniciar el intérprete privilegiado.

Para un servidor PHP privilegiado que llama a funciones de una extensión nativa personalizada, rastrea el SAPI de PHP del servicio, su `php.ini` efectivo y los archivos `.ini` escaneados antes de revisar la extensión. [PHP carga las bibliotecas de `extension` configuradas al iniciar](https://www.php.net/manual/en/ini.core.php), y [los SAPI CLI y web pueden usar archivos de configuración distintos](https://www.php.net/manual/en/configuration.file.php). Por tanto, un formulario de inicio de sesión accesible o un listener local pueden pasar cadenas controladas por el usuario a código compilado que se ejecuta con la identidad del servicio. Registra el `User=`, `ExecStart=`, directorio de trabajo, ruta real de la extensión y argumentos controlables por el llamante; la mera presencia de un `.so` o un socket en loopback no demuestra una vulnerabilidad de corrupción de memoria. Analiza por separado cualquier parser personalizado en lugar de enviar sondas durante la enumeración pasiva.

Cuando un wrapper privilegiado calcula el hash de un script usando una ruta y luego vuelve a abrir esa ruta para ejecutarlo, el digest solo autentica el objeto leído en la primera apertura. Si un usuario menos privilegiado puede reemplazar la entrada del directorio del script entre ambas aperturas, la ejecución posterior puede resolver un objeto distinto, aunque el archivo original sea propiedad de root. Un FIFO puede prolongar la fase de comprobación, pero la ruta depende de permisos reemplazables del directorio padre, de que realmente se produzcan aperturas separadas, de la identidad del scheduler, de las reglas del sticky bit y del montaje, y de la temporización. Inspecciona el wrapper y la salida de `namei -l` como indicio pasivo; un checksum correcto no demuestra que la ruta usada después esté protegida.

Un trabajo de backup privilegiado también puede **divulgar** datos sin ejecutar comandos proporcionados por un atacante. Averigua si un usuario menos privilegiado puede crear un archivo de control que el trabajo lea, si el trabajo abre después una fuente protegida como `/etc/shadow` y si un usuario controlado por el atacante recibe el resultado mediante una URL o una salida legible. Verifica los tres elementos antes de considerarlo una ruta de divulgación. Un comando de shell fijo en el mismo script no convierte por sí solo ese archivo de control en una entrada de inyección de shell. Inspecciona el script y los permisos de los archivos sin ejecutar el trabajo ni colocar un archivo de control durante la enumeración.

Si un trabajo privilegiado programado ejecuta `curl -K FILE` o `curl --config FILE`, [curl trata las opciones de ese archivo como argumentos de línea de comandos](https://curl.se/docs/manpage.html). Un usuario menos privilegiado que controle el archivo exacto cuando curl lo lea puede influir en la URL solicitada, la entrada de archivos locales o la ruta de salida. Confirma la identidad efectiva del trabajo, los permisos de escritura del archivo y de sus directorios antecesores, el momento en que cualquier otro trabajo reemplaza el archivo y cómo interactúan las opciones de configuración con las opciones fijas de la línea de comandos antes de afirmar que puede producirse una lectura o escritura protegida. Una ruta de configuración modificable o una opción `-K` visible no demuestran por sí solas que se apliquen las opciones elegidas; inspecciona la programación y los metadatos sin ejecutar el trabajo ni obtener una URL durante la enumeración pasiva.

Si una entrada de cron invoca un script helper, inspecciona también su directorio de trabajo y el comando de archivo. Un comodín sin comillas sobre un directorio modificable por otro usuario puede convertir nombres de archivo en opciones del archivador; las acciones checkpoint de GNU tar son un ejemplo. Confirma la identidad de ejecución programada, el directorio de entrada modificable, el archivador y las opciones exactos, y si `--` termina el análisis de opciones antes de afirmar que existe una ruta de comandos entre usuarios. Consulta el comportamiento de [comodines y tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Puede producirse una divulgación distinta de archivos de backup si un helper privilegiado ejecuta `cd INPUT_DIR; tar ... *` sin comprobar si `cd` tuvo éxito. Si un usuario menos privilegiado puede eliminar o reemplazar `INPUT_DIR`, un `cd` fallido puede dejar el shell en el directorio anterior, que el comando de archivado posterior podría leer. Verifica el directorio de trabajo inicial del trabajo, una ruta real en la que falle `cd`, si el script termina o usa `&&`, las opciones exactas del archivador y si el archivo resultante es legible por el usuario menos privilegiado. Un directorio de entrada modificable o un archivo legible por sí solos son solo indicios; inspecciona el helper y los permisos de las rutas sin alterar el trabajo activo.

Un ejecutable programado puede ocultar un script de shell en vez de eliminar la frontera de confianza: [SHc](https://github.com/neurobin/shc) envuelve texto de script cifrado en un binario nativo y lo ejecuta mediante un shell en tiempo de ejecución. Un sufijo `.sh.x` o un ELF opaco son solo indicios para revisar. Para evaluar la inyección de opciones mediante nombres de archivo, determina la identidad del scheduler privilegiado, el directorio de trabajo y el comando reales del helper, la capacidad del usuario menos privilegiado para crear allí nombres coincidentes y si un comodín sin comillas llega a un comando como `rsync` sin un límite de opciones. La [opción de shell remoto de `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) solo es relevante si se usa esa ruta de comando exacta. La visibilidad restringida de `/proc` o el fallo del descifrado estático dejan el comando sin determinar; no ejecutes el helper privilegiado solo para clasificarlo.

El texto de la línea de comandos de un proceso es otra entrada no confiable para un helper privilegiado. Un usuario menos privilegiado puede elegir el título de un proceso o su `argv[0]` para que coincida con `pgrep -f`; un nombre coincidente no autentica el ejecutable ni a su propietario. Si un script ejecutado como root captura ese texto, reescribe parte de él para convertirlo en `apache2ctl`/`httpd` y ejecuta el resultado sin una matriz fija de argumentos, las opciones elegidas por el atacante pueden seleccionar otro directorio de configuración o un log de errores. El análisis de la configuración de Apache puede cargar módulos o llegar a helpers configurados, así que no valides una configuración no confiable como root durante la enumeración. Inspecciona el propietario del scheduler, el helper exacto, la identidad del proceso y el flujo de datos a los argumentos; esto es una inyección de opciones/configuración, salvo que se demuestre por separado la ejecución de metacaracteres del shell.

Un parser ejecutado como root que introduce texto no confiable en la aritmética de Bash puede ejecutar sustituciones contenidas en ese texto. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) ofrece un ejemplo detallado. Confirma la fuente de entrada y el comando de análisis antes de considerar explotable toda expresión aritmética.

Para un trabajo privilegiado que analiza un log de una aplicación, sigue los campos no confiables más allá del primer análisis. Una cuenta menos privilegiada puede tener la capacidad de escribir en el log mediante su grupo de procesos actual o influir en los campos de solicitudes registrados; un registro puede seleccionar una imagen cuyos metadatos se convierten en una segunda ruta usada para abrir XML. Comprueba la identidad efectiva del trabajo, el acceso real de escritura al log, el manejo de delimitadores, la contención de rutas canónicas y si el XML seleccionado está bajo control del atacante. La expansión de entidades externas puede convertir esa segunda lectura en una divulgación privilegiada de archivos si el resultado expandido llega a una salida legible por un usuario menos privilegiado. La [guía de seguridad de procesamiento XML de Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para el acceso a DTD/entidades externas; inspecciona el parser instalado y sus ajustes efectivos. Un log modificable o un archivo XML por sí solos son solo indicios. Revisa el código y los metadatos sin proporcionar entradas al parser programado durante la enumeración.

Inspecciona también los trabajos privilegiados que materializan archivos desde el repositorio Git de otro usuario. Un script puede usar `git ls-tree` y `git cat-file` en vez de `git checkout` y, aun así, confiar en rutas de árbol controladas por un atacante al unirlas a un directorio de staging. Las rutas absolutas y los componentes `..` pueden escapar de ese directorio, salvo que se normalice el destino y se compruebe la contención antes de escribir. `git -c safe.directory=*` permite acceder a repositorios con distintos propietarios; por sí solo no crea la condición de escritura arbitraria.

Un backup de base de datos ejecutado como root puede crear otra frontera de propiedad. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia archivos regulares adicionales ubicados en el directorio de datos de origen, y su formato plain predeterminado escribe los archivos en `-D` como un árbol de directorios. Si una cuenta menos privilegiada puede crear o modificar esos archivos de origen, inspecciona la propiedad y los permisos del destino resultante, si se puede acceder y ejecutar desde su ruta, y si el montaje tiene `nosuid`. Una copia propiedad de root que conserve permisos set-ID puede ser peligrosa; un backup solo en formato tar, los permisos eliminados o un destino inaccesible no demuestran la misma ruta. Sigue el wrapper programado y el usuario efectivo antes de considerar el comando de backup un hallazgo.

## Observar trabajos de corta duración

Una sola captura de procesos puede pasar por alto un trabajo que se ejecuta durante milisegundos. Compara las declaraciones de timers/cron con los logs y, cuando esté autorizado, con la monitorización de eventos de procesos, como `pspy` o audit. Correlaciona el propietario programado, la línea de comando exacta y los archivos que la tarea lee o escribe. Una interfaz web del scheduler en loopback es una interfaz independiente; consulta el [ejemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
