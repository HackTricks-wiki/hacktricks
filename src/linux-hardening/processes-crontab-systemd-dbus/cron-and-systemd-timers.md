# Tarefas do Cron e timers do Systemd

{{#include ../../banners/hacktricks-training.md}}

Tarefas agendadas podem ser executadas com uma identidade e um ambiente diferentes dos do shell atual. Enumere cron, `at`, anacron e timers do systemd; em seguida, rastreie cada comando agendado por seus scripts, imports, diretório de trabalho e entradas graváveis.

## Enumerar agendamentos

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Os crontabs do sistema geralmente incluem um campo de usuário; o crontab de um usuário não. Inspecione o PATH efetivo e o ambiente do scheduler real. `run-parts --test /etc/cron.daily` mostra quais nomes de arquivo seriam selecionados nesse host. Caracteres de controle podem ocultar uma entrada em uma visualização casual, então use `cat -A` ou `sed -n l` quando um agendamento parecer suspeito.

## Rastrear a resolução de arquivos e comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revise cadeias de scripts graváveis, caminhos `EnvironmentFile=`, drop-ins, symlinks, comandos relativos, expansão de curingas e binários copiados ou executados por uma tarefa privilegiada. Um timer pode ativar um serviço com outro nome por meio da configuração `Unit=`. As páginas sobre [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explicam as principais primitivas.

Para um script `chkrootkit` agendado para ser executado como root, inspecione o código-fonte instalado em busca do antigo [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): um `file_port=$file_port $i` sem aspas, após uma verificação de um caminho temporário `SLAPPER_FILES`, pode executar esse arquivo. Confirme o script efetivo ou o patch do fornecedor, o agendamento como root, o acesso de escrita de um usuário menos privilegiado ao caminho temporário exato, se ele é executável e a política de montagem. Uma string de versão ou apenas a presença de `chkrootkit` não comprova esse caminho; não crie nem execute um arquivo temporário durante uma revisão passiva.

Investigue mais um salto de unidade quando o serviço root de um timer executa `systemctl restart <other>.service`: a unidade reiniciada pode invocar um shell com um script gravável por um usuário menos privilegiado. Confirme o `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, os argumentos exatos de `ExecStart=` e as permissões do script e do caminho até ele. Um script gravável é apenas um candidato até que o timer e o serviço reiniciado estejam ativos nesse contexto de execução; inspecione as propriedades das unidades sem reiniciar nenhum dos serviços.

Se uma tarefa com privilégios mais altos busca um script por hostname e passa a resposta para um shell, verifique quem controla a resolução desse hostname, além do script remoto. Um arquivo `/etc/hosts` gravável, inclusive por meio de permissões concedidas por grupo ou ACL, pode redirecionar um nome que a tarefa resolve localmente; uma resposta de `curl` só se torna um caminho de execução entre usuários quando o comando agendado realmente a executa e a tarefa usa o caminho de resolução afetado. Verifique a identidade de execução da tarefa, a URL exata e o pipeline para o shell, o comportamento efetivo de proxy/DNS e as permissões do arquivo e do diretório pai. Um arquivo hosts gravável, por si só, é um indício para revisão, não prova que exista um consumidor privilegiado. Inspecione o agendamento e os metadados sem alterar o mapeamento nem buscar o script durante a enumeração.

Uma busca agendada e privilegiada com `wget` é um limite distinto de gravação de arquivos, mesmo que o conteúdo baixado nunca seja executado diretamente. [O GNU Wget 1.18 alterou o tratamento padrão do nome de arquivo em redirecionamentos HTTP para FTP, corrigindo o CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); versões afetadas mais antigas podiam usar o nome de arquivo do FTP redirecionado, enquanto `--trust-server-names` solicita explicitamente esse comportamento. Se uma parte menos confiável controla a resposta HTTP e o recurso FTP, verifique se a tarefa segue esse redirecionamento, a versão efetiva do Wget ou o backport do fornecedor, as opções de saída, a identidade de execução, o diretório de trabalho e se o nome de destino pode se tornar um arquivo de inicialização. [O Wget carrega `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), e [suas configurações podem selecionar uma origem de POST ou um caminho de saída](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); uma busca privilegiada posterior é um pré-requisito distinto para qualquer divulgação ou gravação resultante. O acesso a uma porta baixa por meio de `authbind` só é relevante quando o chamador pode realmente servir a URL solicitada pela tarefa. Revise a configuração e os logs passivamente, sem servir um redirecionamento nem executar a tarefa. [O acesso bruto a dispositivos de bloco por meio do grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) é independente desse caminho de busca pela rede.

Investigue também arquivos de dados, não apenas scripts. Uma ferramenta agendada de simulação ou orquestração pode ler um arquivo YAML que define os processos a iniciar; se um usuário menos privilegiado puder editar esse arquivo e a tarefa o executar com outra conta, os dados podem se transformar em comandos executados com a identidade da tarefa. Verifique o comando agendado exato, o usuário efetivo, o caminho do arquivo, a semântica do parser e o acesso de escrita, inclusive aos diretórios pais, antes de tratar um YAML gravável como um caminho de execução. Para uma triagem passiva, basta ler o agendamento e os metadados do arquivo; não execute a tarefa nem modifique sua entrada durante a enumeração.

Uma configuração de cliente SSH também é uma entrada executável quando uma tarefa com privilégios mais altos executa `ssh -F` usando um arquivo que um usuário menos privilegiado pode substituir. O [`ProxyCommand` do OpenSSH](https://man.openbsd.org/ssh_config#ProxyCommand) executa um comando local por meio do shell do cliente, enquanto `Host`/`Match` e as opções anteriores determinam se essa diretiva se aplica. Correlacione a invocação SSH agendada exata, a identidade de execução, o caminho de configuração selecionado, as permissões de escrita do diretório e do arquivo e a ordem efetiva das opções antes de classificá-la como um caminho de execução entre usuários. Revise esses registros sem executar a tarefa nem carregar a configuração não confiável como a conta privilegiada.

Um `scp` agendado seguido por `ssh` para executar o script copiado exige uma segunda revisão do limite de confiança quando um usuário menos privilegiado controla o serviço SSH de destino. Se esse serviço puder encaminhar a conexão para outro host, o cliente privilegiado poderá se autenticar em um endpoint não pretendido; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) enfraquece a proteção contra alterações da chave do host, sujeito às restrições restantes do OpenSSH e às opções efetivas por host. Determine a identidade de execução da tarefa, o destino real e o método de autenticação, a identidade efetiva do comando remoto e se o mesmo caminho de destino é gravável ou já existe no host redirecionado. A execução de um arquivo antigo ou controlado por um atacante exige ainda que a cópia falhe ou não encontre esse caminho **e** que o wrapper prossiga para o comando SSH; [`errexit` do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e o tratamento explícito do status afetam esse fluxo. Uma configuração fraca de chave de host, um processo `sshpass` visível ou um diretório temporário gravável, isoladamente, não comprovam essa cadeia. Inspecione o agendamento, o script, a configuração SSH e os metadados dos arquivos sem redirecionar o serviço nem acionar a tarefa durante a enumeração.

Um scheduler de aplicação privilegiado pode obter suas tarefas de linhas do banco de dados, em vez de arquivos graváveis. Por exemplo, uma entrada cron de root que invoque o [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) do Laravel pode chegar a código da aplicação que lê linhas de tarefas. Se uma conta menos privilegiada puder gravar uma linha contendo um caminho local, e o callback agendado chamar o [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) do PHP como root e enviar o conteúdo retornado para um webhook selecionado pela linha, isso constitui um caminho privilegiado de divulgação de arquivos. Verifique a identidade do cron, o callback efetivo do scheduler e o fluxo de dados da linha ao caminho, as permissões de escrita no banco de dados, a validação após a leitura da linha e o destino de saída. Um `.env` da aplicação legível é apenas uma pista de credenciais; a validação de um formulário web ou uma senha de banco de dados, por si só, não prova controle da linha nem divulgação. Inspecione o agendamento, o código e as permissões do arquivo de credenciais passivamente, sem consultar o banco de dados nem agendar uma tarefa durante a enumeração.

Tarefas `incron` acionadas por eventos também merecem essa revisão: [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associam um caminho monitorado e um evento a um comando executado com a identidade do proprietário da tabela. Um usuário menos privilegiado pode influenciar indiretamente um arquivo monitorado quando uma aplicação segue um link de um diretório gravável e grava texto controlado por um atacante no destino monitorado. Verifique o proprietário efetivo da tabela, o evento, o destino e as permissões dos diretórios ancestrais, o comportamento da aplicação ao seguir links e como esse texto se transforma em argumentos de comando. Em particular, o [GNU Mailutils `mail` aceita `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), e seu [comando de escape para o shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) pode executar um programa; um campo não confiável passado como uma opção separada para essa implementação pode levar à execução de comandos. Outras implementações de `mail` ou um limite de argumentos fixo e devidamente entre aspas podem se comportar de outra forma. Inspecione o agendamento, o código da aplicação e os metadados dos arquivos sem modificar o arquivo monitorado nem acionar a tarefa durante a enumeração.

Um log monitorado também pode cruzar um limite entre usuários por meio de um script auxiliar. Se uma conta menos privilegiada puder gravar no log e o proprietário do `incron` ler um campo dele e incorporá-lo a uma nova string de comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), o shell analisará esse campo novamente com a identidade do proprietário. Verifique o evento monitorado exato, as permissões do log e dos diretórios pais, o caminho do auxiliar, a transformação do campo do log e se o comando resultante é alcançado. A existência de um log gravável e de uma entrada `incron`, por si só, não comprova o fluxo de dados; não escreva uma linha de acionamento nem execute o auxiliar durante uma enumeração passiva.

Tarefas de renovação de certificados podem cruzar o mesmo limite. Um auxiliar privilegiado pode ler um subject X.509 de um certificado em um diretório gravável por um usuário menos privilegiado e inserir o common name em uma nova string de comando `bash -c`. [O OpenSSL pode exibir o subject de um certificado e verificar sua validade](https://docs.openssl.org/3.3/man1/openssl-x509/); [o Bash analisa a string `-c` como entrada de shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), portanto, colocar a variável entre aspas no script externo não protege contra a segunda análise. Confirme a identidade agendada, o caminho de entrada exato e os direitos de escrita, o ramo de renovação e o fluxo de dados até `bash -c` antes de classificá-lo como command injection. Inspecione o script e os metadados do certificado passivamente; não acione a renovação durante a enumeração.

A mesma segunda análise pode ocorrer quando uma tarefa privilegiada extrai um nome do arquivo ou pacote de um usuário menos privilegiado e o envia a `xargs -I` para inseri-lo em uma string de comando `sh -c`. [`xargs -I` do GNU substitui o marcador nos argumentos iniciais](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), e [`sh -c` interpreta sua string de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Mesmo que o script externo coloque o nome extraído entre aspas, isso não torna seguro um programa de shell substituído posteriormente. Verifique a identidade de execução da tarefa, o caminho de entrada aceito exato e o acesso de escrita, a validação do arquivo e as condições do ramo, além do fluxo do nome até o shell. Um diretório de uploads gravável ou uma invocação de `xargs`, isoladamente, é apenas uma pista; inspecione o agendamento, o script e os metadados do caminho sem enviar um pacote nem executar a tarefa durante a enumeração.

Um importador agendado de fontes ou imagens também pode confiar em nomes *dentro* de um arquivo fornecido pelo chamador, mesmo quando o nome externo do upload é restrito. O FontForge corrigiu a command injection por nomes de membros do arquivo na [alteração upstream para CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirme que uma tarefa com privilégios mais altos realmente abre um arquivo de um caminho gravável por um usuário menos privilegiado, a identidade de execução, a versão exata do FontForge ou o backport do fornecedor e o caminho de código que trata o arquivo. Uma string de versão ou uma extensão de upload permitida, por si só, não prova execução. Inspecione o agendamento, as permissões do caminho e os metadados da versão sem importar um arquivo não confiável durante a enumeração.

Scanners de rede agendados podem cruzar outro limite quando um script personalizado trata o subject de um certificado TLS remoto como um nome de arquivo local. [O Nmap NSE executa os scripts selecionados sem sandbox](https://nmap.org/book/nse-usage.html); portanto, inspecione o script efetivo e verifique se ele combina um campo subject não confiável com um diretório de dados sem verificações de contenção. A divulgação de arquivos exige um alvo que o scheduler vá escanear, um caminho que resolva para um arquivo legível pela identidade de execução do scanner e um relatório ou log entregue a um leitor menos privilegiado. Um campo do certificado ou apenas a presença de um scanner instalado não comprova essa cadeia; revise o agendamento, o script, a resolução do caminho e o destino do relatório sem escanear um novo alvo durante uma enumeração passiva.

Um comando cron privilegiado que passa um glob de shell, como `/path/to/tasks/*.yml`, para um executor do Ansible merece uma verificação das permissões do diretório, mesmo quando todos os playbooks existentes são somente para leitura. Um usuário com acesso de escrita e busca ao diretório abrangido pelo glob pode conseguir criar outro playbook correspondente. [Playbooks do Ansible definem tarefas executadas pelo executor](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mas um wrapper personalizado pode filtrar caminhos ou usar outra identidade: verifique seu comportamento, o usuário efetivo do cron, a expansão do shell, as ACLs, o sticky bit e a política de montagem antes de tratar o diretório como um caminho de execução. Inspecione os metadados e o wrapper estaticamente; não execute a tarefa agendada durante a enumeração.

Um wrapper cron privilegiado pode passar nomes de arquivos de um diretório de uploads a um auxiliar Perl depois de expandir um glob. O operador [`<>` de diamante do Perl usa `open` com dois argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), então um nome de arquivo correspondente interpretado como um comando de pipe pode ser executado com a identidade do auxiliar; [`<<>>` trata os argumentos como nomes de arquivo literais](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirme a identidade do scheduler, o diretório de trabalho e o glob do wrapper, o tratamento efetivo de `@ARGV` pelo auxiliar, as restrições de nomes de arquivos e se uma identidade menos privilegiada pode inserir um nome correspondente por meio das permissões do sistema de arquivos ou de um serviço de upload autenticado. Uma linha cron, um script Perl ou um diretório FTP gravável, isoladamente, não comprovam a cadeia completa. Inspecione o código-fonte e os metadados sem enviar um nome de arquivo criado para esse fim nem executar a tarefa durante a enumeração.

Um script cron somente para leitura ainda pode ser substituído se a conta agendada o executar por caminho e um usuário menos privilegiado puder gravar e percorrer seu diretório pai, que não tenha sticky bit. Verifique a identidade de execução do agendamento, cada componente do caminho, o sticky bit do diretório, as ACLs e a política de montagem; revise os metadados sem mover o arquivo nem executar a tarefa.

Um wrapper cron PHP privilegiado pode chegar a um auxiliar que ainda não existe. Se ele chamar o [`exec()`](https://www.php.net/manual/en/function.exec.php) do PHP com o caminho absoluto fixo do auxiliar, um usuário menos privilegiado que possa criar esse nome no diretório pai poderá controlar o que uma execução posterior executa. Confirme que a entrada cron realmente executa o wrapper com a identidade mais privilegiada, a string de comando exata e a política de execução do PHP, os direitos de escrita e busca no diretório do auxiliar, o comportamento de symlinks e do sticky bit e se o caminho do auxiliar ainda está ausente. Um diretório gravável ou um auxiliar ausente, isoladamente, é apenas uma pista; inspecione o agendamento, o código-fonte e os metadados do caminho sem criar o auxiliar nem acionar a tarefa.

Uma tarefa agendada também pode localizar scripts de entrada com `find` e passá-los a um interpretador. Por exemplo, a função `system()` do [gnuplot invoca um shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), portanto, uma tarefa privilegiada que executa `gnuplot` em todos os arquivos `*.plt` de um diretório gravável por um usuário menos privilegiado pode executar comandos com a identidade da tarefa. [A permissão de leitura do diretório controla a listagem, enquanto a permissão de escrita e busca (`x`) controla a criação e o acesso a nomes conhecidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); verifique o acesso de escrita e busca mesmo quando `ls` não consegue listar o diretório. Correlacione a identidade e o comando exatos do scheduler, o comportamento do interpretador, o padrão de arquivos selecionado e as permissões do diretório; um diretório gravável ou a presença de um interpretador instalado, por si só, não comprova uma elevação de privilégios. Agendamentos privados e tarefas de curta duração podem exigir observação autorizada de eventos, pois um único snapshot de processos pode não capturá-los.

Para uma tarefa PHP privilegiada, inspecione instruções literais `include`/`require` como parte da cadeia de scripts executáveis. [O PHP avalia os arquivos incluídos](https://www.php.net/manual/en/function.include.php), portanto, um arquivo `.php` gravável por grupo que seja incluído pode executar código com a identidade da tarefa mesmo quando o script principal é somente para leitura. Verifique a identidade agendada, a resolução efetiva do include path, as permissões do arquivo e do diretório e se a tarefa realmente é executada; uma linha cron de exemplo em um comentário é apenas uma pista. A mesma revisão se aplica a um [servidor integrado do PHP](https://www.php.net/commandline.webserver) de propriedade do root iniciado com `-S` e `-t <document-root>`: um listener em loopback ainda pode executar PHP da aplicação para solicitações locais. Inspecione o processo e o código-fonte sem acionar nenhum dos gatilhos durante a enumeração.

Uma tarefa PHP privilegiada também pode cruzar o limite por meio de um **arquivo de dados**: se um usuário menos privilegiado puder alterar o arquivo exato passado para [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), o PHP poderá invocar o método `__wakeup()` ou `__unserialize()` de uma classe carregada durante a restauração do objeto. Revise a identidade efetiva da tarefa, as permissões do arquivo e dos diretórios ancestrais, as classes carregadas e os efeitos reais do método, como uma gravação em arquivo selecionada por uma propriedade. Um log gravável ou uma chamada a `unserialize()`, por si só, não prova que exista um caminho utilizável. Inspecione o código-fonte e os metadados sem gravar entrada serializada nem executar a tarefa durante a enumeração.

Uma tarefa cron de root pode invocar o **executor de páginas CLI** de uma aplicação PHP em vez do servidor web. Rastreie o document root e o URI selecionados pelo executor até o ponto de entrada PHP efetivo; se esse ponto de entrada for gravável pela conta do serviço web, a solicitação CLI agendada poderá executar o código alterado como root, mesmo que o executor e o wrapper cron sejam somente para leitura. Confirme a identidade do scheduler, a resolução exata de URI para arquivo, as permissões efetivas do arquivo e dos diretórios ancestrais e se uma verificação de integridade protege o próprio ponto de entrada. Inspecione o código-fonte e os metadados sem invocar o executor nem alterar a página durante a enumeração.

Um processo `ipython` iniciado por uma tarefa agendada ou por outro usuário em um diretório de trabalho compartilhado merece uma revisão dos arquivos de inicialização. [As notas de segurança do IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explicam que versões afetadas procuravam perfis e configurações no diretório atual, incluindo código em `profile_default/startup`, antes da correção do CVE-2022-21699. Correlacione a versão instalada efetiva ou o patch do fornecedor, o diretório de trabalho do comando, a identidade do processo com privilégios mais altos e a capacidade do usuário menos privilegiado de gravar e buscar o caminho exato de inicialização. A presença de `ipython`, um diretório gravável ou apenas uma string de versão não prova que outra identidade carregará um arquivo dali. Inspecione o agendamento e os metadados do caminho sem iniciar o interpretador com privilégios mais altos.

Para um servidor PHP privilegiado que chama funções de uma extensão nativa personalizada, rastreie o SAPI do PHP do serviço e seu `php.ini` efetivo, além dos arquivos `.ini` carregados, antes de revisar a extensão. [O PHP carrega as bibliotecas `extension` configuradas na inicialização](https://www.php.net/manual/en/ini.core.php), e [os SAPIs CLI e web podem usar arquivos de configuração diferentes](https://www.php.net/manual/en/configuration.file.php). Portanto, um formulário de login acessível ou um listener local pode passar strings controladas pelo usuário para código compilado executado com a identidade do serviço. Registre o `User=`, o `ExecStart=`, o diretório de trabalho, o caminho efetivo da extensão e os argumentos controlados pelo chamador; a mera presença de um `.so` ou de um socket em loopback não comprova uma falha de corrupção de memória. Analise qualquer parser personalizado separadamente, em vez de enviar probes durante a enumeração passiva.

Quando um wrapper privilegiado calcula o hash de um script por caminho e depois abre esse caminho novamente para executá-lo, o digest autentica apenas o objeto lido na primeira abertura. Se um usuário menos privilegiado puder substituir a entrada de diretório do script entre as duas aberturas, a execução posterior poderá resolver um objeto diferente, mesmo que o arquivo de script original pertença ao root. Um FIFO pode prolongar a fase de verificação, mas o caminho depende de direitos substituíveis no diretório pai, de aberturas realmente separadas, da identidade do scheduler, das regras de sticky bit e montagem e do tempo de execução. Inspecione o wrapper e a saída de `namei -l` como uma pista passiva; uma soma de verificação bem-sucedida não prova, por si só, que o caminho usado depois esteja protegido.

Uma tarefa de backup privilegiada também pode **divulgar** dados sem executar comandos fornecidos por um atacante. Investigue se um usuário menos privilegiado pode criar um arquivo de controle lido pela tarefa, se a tarefa abre em seguida uma origem protegida, como `/etc/shadow`, e se uma URL selecionada pelo atacante ou uma saída legível recebe o resultado. Verifique os três pontos antes de classificá-la como um caminho de divulgação. Um comando de shell fixo no mesmo script não transforma, por si só, esse arquivo de controle em uma entrada de shell injection. Inspecione o script e as permissões dos arquivos sem executar a tarefa nem inserir um arquivo de controle durante a enumeração.

Se uma tarefa agendada privilegiada executa `curl -K FILE` ou `curl --config FILE`, [o curl trata as opções desse arquivo como argumentos de linha de comando](https://curl.se/docs/manpage.html). Um usuário menos privilegiado que controle o arquivo exato quando o curl o lê pode influenciar a URL solicitada, a entrada de arquivos locais ou o caminho de saída. Confirme a identidade efetiva da tarefa, os direitos de escrita no arquivo e nos diretórios ancestrais, o momento de qualquer outra tarefa que substitua o arquivo e como as opções de configuração interagem com as opções fixas da linha de comando antes de alegar uma leitura ou gravação protegida. Um caminho de configuração gravável ou um sinalizador `-K` visível, por si só, não prova que as opções escolhidas surtirão efeito; inspecione o agendamento e os metadados sem executar a tarefa nem buscar uma URL durante a enumeração passiva.

Se uma entrada cron invoca um script auxiliar, inspecione também o diretório de trabalho do auxiliar e o comando de arquivamento. Um curinga sem aspas em um diretório gravável por outro usuário pode transformar nomes de arquivos em opções do arquivador; as ações de checkpoint do GNU tar são um exemplo. Confirme a identidade de execução agendada, o diretório de entrada gravável, o arquivador e as opções exatos e se `--` encerra a análise de opções antes de alegar um caminho de comandos entre usuários. Consulte o comportamento de [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Uma divulgação separada de arquivos de backup pode ocorrer quando um auxiliar privilegiado executa `cd INPUT_DIR; tar ... *` sem verificar se `cd` teve sucesso. Se um usuário menos privilegiado puder remover ou substituir `INPUT_DIR`, uma falha de `cd` poderá deixar o shell no diretório anterior, que o comando de arquivamento subsequente poderá ler. Verifique o diretório de trabalho inicial da tarefa, a existência de um caminho real de falha de `cd`, se o script encerra a execução ou usa `&&`, as opções exatas do arquivador e se o arquivo de saída é legível pelo usuário menos privilegiado. Um diretório de entrada gravável ou um arquivo legível, isoladamente, é apenas uma pista; inspecione o auxiliar e as permissões do caminho sem alterar a tarefa em execução.

Um executável agendado pode ocultar um script de shell em vez de eliminar seu limite de confiança: o [SHc](https://github.com/neurobin/shc) encapsula texto de script criptografado em um binário nativo e o executa por meio de um shell em tempo de execução. Um sufixo `.sh.x` ou um ELF opaco é apenas uma pista para revisão. Para avaliar a injeção de opções por nomes de arquivos, determine a identidade privilegiada do scheduler, o diretório de trabalho e o comando efetivos do auxiliar, a capacidade do usuário menos privilegiado de criar nomes correspondentes nesse diretório e se um glob sem aspas chega a um comando como `rsync` sem um limite de opções. A [opção de remote-shell do `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) só é relevante se esse caminho de comando exato for usado. Visibilidade restrita de `/proc` ou uma falha de descriptografia estática deixa o comando desconhecido; não execute o auxiliar privilegiado apenas para classificá-lo.

O texto da linha de comando de um processo é outra entrada não confiável para um auxiliar privilegiado. Um usuário menos privilegiado pode escolher um título de processo ou `argv[0]` que corresponda a `pgrep -f`; um nome correspondente não autentica o executável nem seu proprietário. Se um script executado como root captura esse texto, reescreve parte dele para formar `apache2ctl`/`httpd` e executa o resultado sem um array de argumentos fixo, opções escolhidas pelo atacante podem selecionar outro diretório de configuração ou log de erros. A análise de configuração do Apache pode carregar módulos ou alcançar auxiliares configurados; portanto, não valide uma configuração não confiável como root durante a enumeração. Inspecione o proprietário do agendamento, o auxiliar exato, a identidade do processo e o fluxo dos dados até os argumentos; isso é injeção de opções/configuração, a menos que a execução de metacaracteres do shell seja demonstrada separadamente.

Um parser executado como root que alimenta texto não confiável à aritmética do Bash pode executar substituições nesse texto. O [guia de elevação de privilégios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) apresenta um exemplo detalhado. Confirme a origem da entrada e o comando de análise antes de tratar toda expressão aritmética como explorável.

Para uma tarefa privilegiada que analisa um log da aplicação, rastreie os campos não confiáveis além da primeira análise. Uma conta menos privilegiada pode conseguir gravar no log por meio do grupo de processos atual ou influenciar campos de solicitações registrados; um registro pode então selecionar uma imagem, cujos metadados se tornam um segundo caminho usado para abrir XML. Verifique a identidade efetiva da tarefa, o acesso real de escrita no log, o tratamento de delimitadores, a contenção do caminho canônico e se o XML selecionado é controlado pelo atacante. A expansão de entidades externas pode transformar essa segunda leitura em divulgação privilegiada de arquivos se o resultado expandido chegar a uma saída legível por um usuário menos privilegiado. O [guia de segurança de processamento de XML em Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para acesso a DTDs/entidades externas; inspecione o parser instalado e suas configurações efetivas. Um log ou arquivo XML gravável, isoladamente, é apenas uma pista. Revise o código e os metadados sem alimentar o parser agendado durante a enumeração.

Inspecione também tarefas privilegiadas que materializam arquivos de outro repositório Git de um usuário. Um script pode usar `git ls-tree` e `git cat-file` em vez de `git checkout` e ainda assim confiar em caminhos de árvore controlados pelo atacante ao combiná-los com um diretório de preparação. Caminhos absolutos e componentes `..` podem escapar desse diretório, a menos que o destino seja normalizado e verificado para garantir a contenção antes da gravação. `git -c safe.directory=*` permite acessar repositórios com proprietários diferentes; por si só, não cria a condição de gravação arbitrária.

Um backup de banco de dados executado como root pode criar outro limite de propriedade. O [`pg_basebackup` do PostgreSQL](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia outros arquivos regulares colocados no diretório de dados de origem, e seu formato plain padrão grava arquivos em `-D` como uma árvore de diretórios. Se uma conta menos privilegiada puder criar ou modificar esses arquivos de origem, inspecione a propriedade e o modo dos arquivos de destino resultantes, se o caminho pode ser percorrido e executado e se a montagem tem `nosuid`. Uma cópia pertencente ao root que preserve permissões set-ID pode ser perigosa; um backup apenas em tar, permissões removidas ou um destino inacessível não estabelece o mesmo caminho. Rastreie o wrapper agendado e o usuário efetivo antes de tratar o comando de backup como um achado.

## Observe tarefas de curta duração

Um único snapshot de processos pode não capturar uma tarefa que executa por milissegundos. Compare as declarações de timer/cron com os logs e, quando autorizado, use monitoramento de eventos de processos, como `pspy` ou audit. Correlacione o proprietário agendado, a linha de comando exata e os arquivos lidos ou gravados pela tarefa. Uma interface web de scheduler em loopback é uma interface separada; consulte o [exemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
