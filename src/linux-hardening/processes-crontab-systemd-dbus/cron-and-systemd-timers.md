# Tareas cron y temporizadores de systemd

{{#include ../../banners/hacktricks-training.md}}

Las tareas programadas pueden ejecutarse con una identidad y un entorno distintos de los del shell actual. Enumera cron, `at`, anacron y los temporizadores de systemd; después, rastrea cada comando programado a través de sus scripts, importaciones, directorio de trabajo y entradas modificables.

## Enumerar tareas programadas

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Los crontabs del sistema suelen incluir un campo de usuario; el crontab de un usuario no. Inspecciona el PATH efectivo y el entorno del scheduler real. `run-parts --test /etc/cron.daily` muestra qué nombres de archivo se seleccionarían en ese host. Los caracteres de control pueden ocultar una entrada en una salida superficial, así que usa `cat -A` o `sed -n l` cuando un horario parezca sospechoso.

## Rastrea la resolución de archivos y comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revisa las cadenas de scripts con permisos de escritura, las rutas `EnvironmentFile=`, los drop-ins, los symlinks, los comandos relativos, la expansión de comodines y los binarios copiados o ejecutados por una tarea privilegiada. Un timer puede activar un servicio con otro nombre mediante su configuración `Unit=`. Las páginas sobre [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) y [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explican los principales elementos básicos.

Para un script de `chkrootkit` programado para ejecutarse como root, inspecciona el código fuente instalado en busca del antiguo [error de quoting de slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): una asignación sin comillas `file_port=$file_port $i` después de comprobar una ruta temporal de `SLAPPER_FILES` puede ejecutar ese archivo. Verifica el script real o el parche del proveedor, la programación con privilegios de root, el acceso de escritura de un usuario de menor privilegio a la ruta temporal exacta, si el archivo es ejecutable y la política de montaje. Una cadena de versión o la mera presencia de `chkrootkit` no demuestran que la ruta sea viable; no crees ni ejecutes un archivo temporal durante una revisión pasiva.

Sigue un salto más entre units si el servicio de root de un timer ejecuta `systemctl restart <other>.service`: la unit reiniciada podría invocar un shell con un script modificable por un usuario de menor privilegio. Confirma el `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, los argumentos exactos de `ExecStart=` y los permisos del script y de su ruta padre. Un script modificable es solo un candidato hasta que el timer y el servicio reiniciado estén activos en ese contexto de ejecución; inspecciona las propiedades de las units sin reiniciar ninguno de los dos servicios.

Si una tarea con privilegios elevados descarga un script mediante un hostname y pasa la respuesta a un shell, comprueba quién controla la resolución de ese hostname, además del script remoto. Un archivo `/etc/hosts` modificable, incluso con acceso concedido mediante un grupo o una ACL, puede redirigir un nombre que la tarea resuelve localmente; una respuesta de `curl` solo se convierte en una vía de ejecución entre usuarios cuando el comando programado realmente ejecuta esa respuesta y la tarea usa la ruta de resolución afectada. Verifica la identidad de ejecución de la tarea, la URL exacta y la pipeline del shell, el comportamiento efectivo de proxy/DNS y los permisos del archivo y del directorio padre. Un archivo de hosts modificable por sí solo es una señal para revisar, no una prueba de que exista un consumidor privilegiado. Inspecciona la programación y los metadatos sin cambiar la asignación ni descargar el script durante el reconocimiento.

Una descarga de `wget` programada con privilegios es un límite independiente de escritura en archivos, aunque el cuerpo descargado nunca se ejecute directamente. [GNU Wget 1.18 cambió el manejo predeterminado del nombre de archivo en redirecciones de HTTP a FTP para corregir CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); las versiones antiguas afectadas podían usar el nombre de archivo de la redirección FTP, mientras que `--trust-server-names` solicita explícitamente ese comportamiento. Si una parte de menor confianza controla la respuesta HTTP y el recurso FTP, comprueba si la tarea sigue esa redirección, la versión real de Wget o el parche del proveedor, las opciones de salida, la identidad de ejecución, el directorio de trabajo y si el nombre de archivo de destino puede convertirse en un archivo de inicio. [Wget carga `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), y [su configuración puede seleccionar una fuente POST o una ruta de salida](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); una descarga privilegiada posterior es un requisito distinto para cualquier divulgación o escritura resultante. El acceso a un puerto bajo mediante `authbind` solo es relevante si quien lo invoca realmente puede servir la URL que solicita la tarea. Revisa la configuración y los logs de forma pasiva, sin servir una redirección ni ejecutar la tarea. El [acceso raw a dispositivos de bloques mediante el grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) es independiente de esta vía de descarga de red.

Sigue también los archivos de datos, no solo los scripts. Una herramienta de simulación u orquestación programada puede leer un archivo YAML que define los procesos que se deben iniciar; si un usuario de menor privilegio puede editar ese archivo y la tarea lo ejecuta con otra cuenta, los datos pueden convertirse en comandos ejecutados con la identidad de la tarea. Verifica el comando programado exacto, el usuario efectivo, la ruta del archivo, la semántica del parser y el acceso de escritura (incluidos los directorios padre) antes de considerar que un YAML modificable es una vía de ejecución. Para una evaluación pasiva basta con leer la programación y los metadatos del archivo; no ejecutes la tarea ni modifiques su entrada durante el reconocimiento.

La configuración de un cliente SSH también es una entrada ejecutable si una tarea con privilegios elevados ejecuta `ssh -F` con un archivo que un usuario de menor privilegio puede reemplazar. OpenSSH ejecuta [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) como un comando local mediante el shell del cliente, mientras que `Host`/`Match` y las opciones anteriores determinan si se aplica esa directiva. Relaciona la invocación SSH programada exacta, la identidad de ejecución, la ruta de configuración seleccionada, los permisos de escritura del archivo y del directorio, y el orden efectivo de las opciones antes de considerarla una vía de ejecución entre usuarios. Revisa estos registros sin ejecutar la tarea ni cargar la configuración no confiable como la cuenta privilegiada.

Una tarea programada que ejecuta `scp` y luego `ssh` para ejecutar el script copiado requiere una segunda revisión de límites de confianza cuando un usuario de menor privilegio controla el servicio SSH de destino. Si ese servicio puede reenviar la conexión a otro host, el cliente privilegiado podría autenticarse en un endpoint no previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) debilita la protección frente a cambios de host key, con sujeción a las restricciones restantes de OpenSSH y a las opciones efectivas para cada host. Determina la identidad de ejecución de la tarea, el destino real y el método de autenticación, la identidad efectiva del comando remoto y si la misma ruta de destino es modificable o ya existe en el host redirigido. La ejecución de un archivo antiguo o controlado por un atacante requiere, además, que la copia falle o no encuentre esa ruta **y** que el wrapper continúe con el comando SSH; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) y el manejo explícito del estado afectan ese flujo. Una configuración débil de host key, un proceso `sshpass` visible o un directorio temporal modificable no demuestran por sí solos esta cadena. Inspecciona la programación, el script, la configuración SSH y los metadatos de los archivos sin redirigir el servicio ni activar la tarea durante el reconocimiento.

Un scheduler de aplicaciones privilegiado puede obtener sus tareas de filas de una base de datos en vez de archivos modificables. Por ejemplo, una entrada de cron de root que invoque [`php artisan schedule:run` de Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) puede llegar a código de la aplicación que lee filas de tareas. Si una cuenta de menor privilegio puede escribir una fila que contiene una ruta local, y el callback programado llama a [`file_get_contents` de PHP](https://www.php.net/manual/en/function.file-get-contents.php) como root y envía el cuerpo obtenido a un webhook seleccionado por la fila, existe una vía privilegiada de divulgación de archivos. Verifica la identidad de cron, el callback real del scheduler y el flujo de datos de la fila a la ruta, la autorización de escritura en la base de datos, la validación después de leer la fila y el destino de salida. Un archivo `.env` legible de la aplicación solo indica posibles credenciales; la validación de un formulario web o una contraseña de base de datos no demuestran por sí solas el control de la fila ni la divulgación. Inspecciona la programación, el código y los permisos de los archivos de credenciales de forma pasiva, sin consultar la base de datos ni programar una tarea durante el reconocimiento.

Las tareas de `incron` activadas por eventos requieren la misma revisión: las [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) asocian una ruta vigilada y un evento con un comando que se ejecuta con la identidad del propietario de la tabla. Un usuario de menor privilegio puede influir indirectamente en un archivo vigilado cuando una aplicación sigue un link desde un directorio modificable y escribe texto controlado por un atacante en el destino vigilado. Verifica el propietario real de la tabla, el evento, los permisos del destino y sus directorios ascendentes, el comportamiento de la aplicación al seguir links y cómo ese texto se convierte en argumentos del comando. En particular, [GNU Mailutils `mail` acepta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), y su [comando de escape al shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) puede ejecutar un programa; un campo no confiable que se pase como una opción independiente a esa implementación puede convertirse en ejecución de comandos. Otras implementaciones de `mail` o un límite de argumentos fijo y entrecomillado pueden comportarse de forma distinta. Inspecciona la programación, el código de la aplicación y los metadatos de los archivos sin modificar el archivo vigilado ni activar la tarea durante el reconocimiento.

Un log vigilado también puede cruzar un límite entre usuarios mediante un script auxiliar. Si una cuenta de menor privilegio puede escribir en el log y el propietario de `incron` lee un campo del log y lo incorpora a una nueva cadena de comandos [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), el shell vuelve a parsear ese campo con la identidad del propietario. Comprueba el evento vigilado exacto, los permisos del log y de sus directorios padre, la ruta del helper, la transformación del campo del log y si se llega a ejecutar el comando resultante. Ver un log modificable y una entrada de `incron` no demuestra por sí solo el flujo de datos; no escribas una línea de activación ni ejecutes el helper durante el reconocimiento pasivo.

Las tareas de renovación de certificados pueden cruzar el mismo límite. Un helper privilegiado puede leer el subject X.509 de un certificado situado en un directorio modificable por un usuario de menor privilegio e insertar su nombre común en una nueva cadena de comandos `bash -c`. [OpenSSL puede mostrar el subject de un certificado y comprobar su caducidad](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash interpreta la cadena `-c` como entrada de shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), por lo que entrecomillar la variable en el script externo no protege el segundo parseo. Confirma la identidad programada, la ruta de entrada exacta y los permisos de escritura, la rama de renovación y el flujo de datos hasta `bash -c` antes de considerarlo command injection. Inspecciona el script y los metadatos del certificado de forma pasiva; no actives la renovación durante el reconocimiento.

El mismo segundo parseo puede ocurrir cuando una tarea privilegiada extrae un nombre de un archivo o paquete de un usuario de menor privilegio y lo pasa mediante `xargs -I` para insertarlo en una cadena de comandos `sh -c`. [GNU `xargs -I` reemplaza el marcador en los argumentos iniciales](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), y [`sh -c` interpreta su cadena de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Aunque el script externo entrecomille el nombre extraído, eso no hace seguro un programa de shell sustituido posteriormente. Verifica la identidad de ejecución de la tarea, la ruta de entrada aceptada exacta y el acceso de escritura, la validación del archivo y las condiciones de la rama, y el flujo del nombre al shell. Un directorio de cargas modificable o una invocación de `xargs` son solo indicios; inspecciona la programación, el script y los metadatos de las rutas sin enviar un paquete ni ejecutar la tarea durante el reconocimiento.

Un importador programado de fuentes o imágenes también puede confiar en nombres *dentro* de un archivo proporcionado por quien lo invoca, aunque el nombre externo de la carga esté restringido. FontForge corrigió la command injection mediante nombres de miembros del archivo en su [cambio upstream para CVE-2024-25081 y CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirma que una tarea con privilegios elevados realmente abra un archivo desde una ruta modificable por un usuario de menor privilegio, su identidad de ejecución, la versión exacta de FontForge o el parche del proveedor y la ruta de manejo del archivo. Una cadena de versión o una extensión de carga permitida no prueban por sí solas que haya ejecución. Inspecciona la programación, los permisos de la ruta y los metadatos de la versión sin importar un archivo no confiable durante el reconocimiento.

Los network scanners programados pueden cruzar un límite distinto cuando un script personalizado trata el subject de un certificado TLS remoto como un nombre de archivo local. [Nmap NSE ejecuta los scripts seleccionados sin sandbox](https://nmap.org/book/nse-usage.html), así que inspecciona el script real y comprueba si une un campo subject no confiable a un directorio de datos sin verificar la contención. La divulgación de archivos requiere un destino que el scheduler vaya a analizar, una ruta que resuelva a un archivo legible por la identidad de ejecución del scanner y un informe o log que se entregue a un lector de menor privilegio. Un campo de certificado o la mera presencia de un scanner instalado no demuestran esa cadena; revisa la programación, el script, la resolución de rutas y el destino del informe sin analizar un destino nuevo durante el reconocimiento pasivo.

Un comando de cron privilegiado que pasa un glob del shell como `/path/to/tasks/*.yml` a un runner de Ansible requiere revisar los permisos del directorio, aunque todos los playbooks existentes sean de solo lectura. Un usuario con permisos de escritura y búsqueda en el directorio del glob podría crear otro playbook que coincida. [Los playbooks de Ansible definen tareas que ejecuta el runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), pero un wrapper personalizado puede filtrar rutas o usar otra identidad: verifica su comportamiento, el usuario real de cron, la expansión del shell, las ACL, el sticky bit y la política de montaje antes de tratar el directorio como una vía de ejecución. Inspecciona los metadatos y el wrapper de forma estática; no ejecutes la tarea programada durante el reconocimiento.

Un wrapper de cron privilegiado puede pasar nombres de archivo de un directorio de cargas a un helper de Perl después de expandir un glob. El operador [`<>` de diamante de Perl utiliza `open` con dos argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), por lo que un nombre coincidente interpretado como un comando de pipe puede ejecutarse con la identidad del helper; [`<<>>` trata los argumentos como nombres de archivo literales](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirma la identidad del scheduler, el directorio de trabajo y el glob del wrapper, el manejo real de `@ARGV` del helper, las restricciones de nombres de archivo y si una identidad de menor privilegio puede colocar un nombre coincidente mediante permisos del sistema de archivos o un servicio de carga autenticado. Una línea de cron, un script de Perl o un directorio FTP modificable no demuestran por sí solos la cadena completa. Inspecciona el código fuente y los metadatos sin enviar un nombre de archivo preparado ni ejecutar la tarea durante el reconocimiento.

Un script de cron de solo lectura sigue siendo reemplazable si la cuenta programada lo ejecuta por su ruta y un usuario de menor privilegio puede escribir y atravesar su directorio padre, que no tiene sticky bit. Comprueba la identidad de ejecución de la programación, cada componente de la ruta, el sticky bit del directorio, las ACL y la política de montaje; revisa los metadatos sin mover el archivo ni ejecutar la tarea.

Un wrapper de cron PHP privilegiado puede llegar a un helper que todavía no existe. Si llama a [`exec()` de PHP](https://www.php.net/manual/en/function.exec.php) con una ruta absoluta fija al helper, un usuario de menor privilegio que pueda crear ese nombre en el directorio padre podría controlar lo que ejecuta una ejecución posterior. Confirma que la entrada de cron realmente ejecuta el wrapper con la identidad elevada, la cadena de comandos exacta y la política de ejecución de PHP, los permisos de escritura y búsqueda del directorio del helper, el comportamiento de symlinks y sticky bit y si la ruta del helper sigue ausente. Un directorio modificable o un helper inexistente son solo indicios; inspecciona la programación, el código fuente y los metadatos de la ruta sin crear el helper ni activar la tarea.

Una tarea programada también puede descubrir scripts de entrada con `find` y pasar cada uno a un intérprete. Por ejemplo, la función `system()` de [gnuplot invoca un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), así que una tarea privilegiada que ejecute `gnuplot` con todos los archivos `*.plt` de un directorio modificable por un usuario de menor privilegio puede ejecutar comandos con la identidad de la tarea. [El permiso de lectura de un directorio controla su listado, mientras que escritura y búsqueda (`x`) controlan la creación y el acceso a nombres conocidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); comprueba el acceso de escritura y búsqueda aunque `ls` no pueda listar el directorio. Relaciona la identidad y el comando exactos del scheduler, el comportamiento del intérprete, el patrón de archivos seleccionado y los permisos del directorio; un directorio modificable o un intérprete instalado no demuestran por sí solos una escalada. Los schedules privados y las tareas breves pueden requerir observación autorizada de eventos, ya que una única instantánea de procesos podría no detectarlos.

Para una tarea PHP privilegiada, inspecciona las instrucciones literales `include`/`require` como parte de la cadena de scripts ejecutables. [PHP evalúa los archivos incluidos](https://www.php.net/manual/en/function.include.php), por lo que un archivo `.php` modificable por un grupo puede ejecutar código con la identidad de la tarea aunque el script principal sea de solo lectura. Verifica la identidad programada, la resolución efectiva de la ruta de inclusión, los permisos del archivo y del directorio y si la tarea realmente se ejecuta; una línea de cron de ejemplo en un comentario es solo una pista. La misma revisión se aplica a un [servidor integrado de PHP](https://www.php.net/commandline.webserver) propiedad de root e iniciado con `-S` y `-t <document-root>`: un listener de loopback puede seguir ejecutando PHP de la aplicación ante solicitudes locales. Inspecciona el proceso y el código fuente sin activar ninguno de los dos mecanismos durante el reconocimiento.

Una tarea PHP privilegiada también puede cruzar el límite mediante un **archivo de datos**: si un usuario de menor privilegio puede modificar el archivo exacto que se pasa a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP podría invocar el método `__wakeup()` o `__unserialize()` de una clase cargada al restaurar un objeto. Revisa la identidad efectiva de la tarea, los permisos del archivo y de los directorios ascendentes, las clases cargadas y los efectos secundarios reales de los métodos, como una escritura en un archivo seleccionada mediante una propiedad. Un log modificable o una llamada a `unserialize()` no demuestran por sí solos una ruta explotable. Inspecciona el código fuente y los metadatos sin escribir datos serializados ni ejecutar la tarea durante el reconocimiento.

Una tarea de cron de root puede invocar el **runner de páginas CLI** de una aplicación PHP en vez del servidor web. Sigue el document root y el URI seleccionados por el runner hasta el punto de entrada PHP real; si la cuenta del servicio web puede modificar ese punto de entrada, la solicitud CLI programada puede ejecutar como root el código modificado, aunque el runner y el wrapper de cron sean de solo lectura. Confirma la identidad del scheduler, la resolución exacta de URI a archivo, los permisos efectivos del archivo y de los directorios ascendentes, y si el propio punto de entrada está protegido por una comprobación de integridad. Inspecciona el código fuente y los metadatos sin invocar el runner ni cambiar la página durante el reconocimiento.

Un proceso de `ipython` iniciado por una tarea programada o por otro usuario desde un directorio de trabajo compartido merece revisar sus archivos de inicio. Las [notas de la versión de seguridad de IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explican que las versiones afectadas buscaban perfiles y configuración en el directorio actual, incluido código de `profile_default/startup`, antes de la corrección de CVE-2022-21699. Relaciona la versión instalada real o el parche del proveedor, el directorio de trabajo del comando, la identidad del proceso con privilegios elevados y la capacidad del usuario de menor privilegio para escribir y buscar en la ruta de inicio exacta. Un `ipython` instalado, un directorio modificable o una cadena de versión no demuestran por sí solos que otra identidad vaya a cargar un archivo allí. Inspecciona la programación y los metadatos de la ruta sin iniciar el intérprete con privilegios elevados.

Para un servidor PHP privilegiado que llama a funciones de una extensión nativa personalizada, rastrea el SAPI de PHP del servicio y sus archivos `php.ini` efectivos, además de los archivos `.ini` escaneados, antes de revisar la extensión. [PHP carga al inicio las bibliotecas `extension` configuradas](https://www.php.net/manual/en/ini.core.php), y [los SAPI CLI y web pueden usar archivos de configuración distintos](https://www.php.net/manual/en/configuration.file.php). Por tanto, un formulario de inicio de sesión accesible o un listener local podría pasar cadenas controladas por el usuario a código compilado que se ejecuta con la identidad del servicio. Registra el `User=`, `ExecStart=`, directorio de trabajo, ruta real de la extensión y argumentos controlables por quien llama; la mera presencia de un `.so` o un socket de loopback no demuestra que exista una vulnerabilidad de corrupción de memoria. Analiza por separado cualquier parser personalizado, en lugar de enviar probes durante el reconocimiento pasivo.

Cuando un wrapper privilegiado calcula el hash de un script por su ruta y luego vuelve a abrir esa ruta para ejecutarlo, el digest solo autentica el objeto leído en la primera apertura. Si un usuario de menor privilegio puede reemplazar la entrada del directorio del script entre ambas aperturas, la ejecución posterior puede resolver un objeto distinto aunque el archivo de script original sea propiedad de root. Un FIFO puede prolongar la fase de comprobación, pero la ruta depende de que se puedan reemplazar las entradas de directorios padre, de que realmente haya aperturas separadas, de la identidad del scheduler, de las reglas de sticky bit y montaje y del timing. Inspecciona el wrapper y la salida de `namei -l` como indicio pasivo; una suma de comprobación correcta no demuestra por sí sola que la ruta posterior esté protegida.

Una tarea de backup privilegiada también puede **divulgar** datos sin ejecutar comandos proporcionados por un atacante. Comprueba si un usuario de menor privilegio puede crear un archivo de control que la tarea lea, si después la tarea abre una fuente protegida como `/etc/shadow` y si una URL seleccionada por el atacante o un archivo de salida legible recibe el resultado. Verifica las tres partes antes de considerarlo una vía de divulgación. Un comando de shell fijo en el mismo script no convierte por sí solo ese archivo de control en una entrada de shell injection. Inspecciona el script y los permisos de los archivos sin ejecutar la tarea ni colocar un archivo de control durante el reconocimiento.

Si una tarea programada con privilegios ejecuta `curl -K FILE` o `curl --config FILE`, [curl trata las opciones de ese archivo como argumentos de línea de comandos](https://curl.se/docs/manpage.html). Un usuario de menor privilegio que controle el archivo exacto cuando curl lo lea podría influir en la URL solicitada, la entrada de archivo local o la ruta de salida. Confirma la identidad efectiva de la tarea, los permisos de escritura del archivo y de los directorios ascendentes, el timing de cualquier otra tarea que reemplace el archivo y cómo interactúan las opciones de configuración con las opciones fijas de la línea de comandos antes de afirmar que se puede leer o escribir un archivo protegido. Una ruta de configuración modificable o un flag `-K` visible no demuestran por sí solos que las opciones elegidas tengan efecto; inspecciona la programación y los metadatos sin ejecutar la tarea ni descargar una URL durante el reconocimiento pasivo.

Si una entrada de cron invoca un script helper, inspecciona también su directorio de trabajo y su comando de archivado. Un wildcard sin comillas sobre un directorio modificable por otro usuario puede convertir los nombres de archivo en opciones del archivador; las acciones de checkpoint de GNU tar son un ejemplo. Confirma la identidad de ejecución programada, el directorio de entrada modificable, el archivador y las opciones exactos, y si `--` termina el análisis de opciones antes de considerar que existe una vía de ejecución entre usuarios. Consulta el comportamiento de [wildcard y tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Puede producirse otra divulgación mediante archivos de backup si un helper privilegiado ejecuta `cd INPUT_DIR; tar ... *` sin comprobar si `cd` tuvo éxito. Si un usuario de menor privilegio puede eliminar o reemplazar `INPUT_DIR`, un `cd` fallido podría dejar el shell en su directorio anterior, que el comando de archivado posterior podría leer. Verifica el directorio de trabajo inicial de la tarea, que exista una ruta real de fallo de `cd`, si el script termina o usa `&&`, las opciones exactas del archivador y si el usuario de menor privilegio puede leer el archivo resultante. Un directorio de entrada modificable o un archivo legible son solo indicios; inspecciona el helper y los permisos de las rutas sin cambiar la tarea activa.

Un ejecutable programado puede ocultar un script de shell sin eliminar el límite de confianza: [SHc](https://github.com/neurobin/shc) envuelve texto de script cifrado en un binario nativo y lo ejecuta mediante un shell durante la ejecución. Un sufijo `.sh.x` o un ELF opaco son solo indicios para revisar. Para evaluar la inyección de opciones mediante nombres de archivo, determina la identidad del scheduler privilegiado, el directorio de trabajo y el comando reales del helper, si un usuario de menor privilegio puede crear allí nombres coincidentes y si un glob sin comillas llega a un comando como `rsync` sin un límite de opciones. La opción de shell remoto de [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) solo es relevante si se utiliza esa ruta de comando exacta. Una visibilidad restringida de `/proc` o el fallo del descifrado estático dejan desconocido el comando; no ejecutes el helper privilegiado solo para clasificarlo.

El texto de la línea de comandos de un proceso es otra entrada no confiable para un helper privilegiado. Un usuario de menor privilegio puede elegir un título de proceso o `argv[0]` que coincida con `pgrep -f`; un nombre coincidente no autentica el ejecutable ni a su propietario. Si un script ejecutado como root captura ese texto, reescribe parte para convertirlo en `apache2ctl`/`httpd` y ejecuta el resultado sin una matriz fija de argumentos, las opciones elegidas por el atacante pueden seleccionar otro directorio de configuración o log de errores. El parseo de configuración de Apache puede cargar módulos o llegar a helpers configurados, así que no valides una configuración no confiable como root durante el reconocimiento. Inspecciona el propietario del scheduler, el helper exacto, la identidad del proceso y el flujo de datos a los argumentos; esto es una inyección de opciones/configuración, salvo que se demuestre por separado la ejecución de metacaracteres del shell.

Un parser ejecutado como root que pasa texto no confiable a la aritmética de Bash puede ejecutar sustituciones contenidas en ese texto. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) ofrece un ejemplo desarrollado. Confirma la fuente de entrada y el comando de parseo antes de considerar explotable cualquier expresión aritmética.

Para una tarea privilegiada que parsea un log de aplicación, sigue los campos no confiables más allá del primer parseo. Una cuenta de menor privilegio podría escribir en el log mediante su grupo de procesos actual o influir en campos de solicitudes que se registran; un registro podría seleccionar una imagen cuyos metadatos se convierten en una segunda ruta para abrir un XML. Comprueba la identidad efectiva de la tarea, el acceso real de escritura al log, el manejo de delimitadores, la contención de rutas canónicas y si el XML seleccionado está controlado por el atacante. La expansión de entidades externas puede convertir esa segunda lectura en una divulgación privilegiada de archivos si el resultado expandido llega a una salida legible por un usuario de menor privilegio. La [guía de seguridad del procesamiento XML en Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para el acceso a DTD/entidades externas; inspecciona el parser instalado y su configuración efectiva. Un log o un archivo XML modificable son solo indicios. Revisa el código y los metadatos sin proporcionar datos al parser programado durante el reconocimiento.

Inspecciona también las tareas privilegiadas que materializan archivos desde el repositorio Git de otro usuario. Un script puede usar `git ls-tree` y `git cat-file` en vez de `git checkout`, pero aun así confiar en las rutas del árbol controladas por el atacante al unirlas a un directorio de staging. Las rutas absolutas y los componentes `..` pueden escapar de ese directorio, salvo que el destino se normalice y se compruebe que permanece dentro de sus límites antes de escribir. `git -c safe.directory=*` permite acceder a repositorios con distinto propietario; por sí solo no crea la condición de escritura arbitraria.

Un backup de base de datos ejecutado como root puede crear otro límite de propiedad. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia archivos regulares adicionales colocados en el directorio de datos de origen, y su formato plain predeterminado escribe los archivos en `-D` como un árbol de directorios. Si una cuenta de menor privilegio puede crear o modificar esos archivos de origen, inspecciona la propiedad y el modo del destino resultante, si se puede recorrer y ejecutar su ruta y si el montaje tiene `nosuid`. Una copia propiedad de root con permisos set-ID conservados puede ser peligrosa; un backup solo en formato tar, los permisos eliminados o un destino inaccesible no establecen la misma vía. Sigue el wrapper programado y el usuario efectivo antes de considerar el comando de backup un hallazgo.

## Observa las tareas de corta duración

Una sola instantánea de procesos podría no detectar una tarea que se ejecuta durante milisegundos. Compara las declaraciones de timer/cron con los logs y, cuando esté autorizado, con la monitorización de eventos de procesos, como `pspy` o audit. Relaciona el propietario programado, la línea de comandos exacta y los archivos que lee o escribe la tarea. Una interfaz web de scheduler en loopback es una interfaz independiente; consulta el [ejemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
