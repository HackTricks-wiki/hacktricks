# Cron Jobs और Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

शेड्यूल किए गए tasks मौजूदा shell से अलग identity और environment के साथ चल सकते हैं। cron, `at`, anacron और systemd timers की सूची बनाएँ, फिर हर शेड्यूल किए गए command को उसकी scripts, imports, working directory और writable inputs के माध्यम से trace करें।

## शेड्यूल की सूची बनाएँ

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontab में आमतौर पर user field होता है; user के crontab में नहीं। वास्तविक scheduler का प्रभावी PATH और environment जाँचें। `run-parts --test /etc/cron.daily` दिखाता है कि उस host पर कौन-से file names चुने जाएँगे। Control characters किसी entry को सामान्य output में छिपा सकते हैं, इसलिए schedule संदिग्ध लगे तो `cat -A` या `sed -n l` का उपयोग करें।

## Privileged फ़ाइल और command resolution का पता लगाएँ

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

लिखने योग्य script chains, `EnvironmentFile=` paths, drop-ins, symlinks, relative commands, wildcard expansion, और किसी privileged task द्वारा copy या execute की जाने वाली binaries की समीक्षा करें। कोई timer अपने `Unit=` setting के ज़रिए अलग नाम वाली service सक्रिय कर सकता है। मुख्य primitives की व्याख्या [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md), और [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) पेजों में है।

Root के रूप में चलने वाली scheduled `chkrootkit` script के लिए, पुराने [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) के लिए installed source जाँचें: `SLAPPER_FILES` के temporary path की जाँच के बाद unquoted `file_port=$file_port $i` उस file को execute कर सकता है। वास्तविक script या vendor patch, root scheduling, exact temporary path पर lower-user की write access, उसका executable status, और mount policy सत्यापित करें। केवल version string या `chkrootkit` की मौजूदगी से यह path साबित नहीं होता; passive review के दौरान temporary file न बनाएँ और न चलाएँ।

जब timer की root service `systemctl restart <other>.service` चलाती हो, तो unit की एक और hop trace करें: restarted unit, lower-privileged user द्वारा लिखी जा सकने वाली script के साथ shell चला सकती है। प्रभावी `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, exact `ExecStart=` arguments, और script तथा उसके parent path की permissions की पुष्टि करें। Writable script केवल एक candidate है, जब तक timer और restarted service उस execution context में सक्रिय न हों; किसी भी service को restart किए बिना unit properties जाँचें।

यदि कोई higher-privileged job hostname के ज़रिए script fetch करके response shell को देता है, तो remote script के साथ यह भी जाँचें कि उस hostname के resolution को कौन नियंत्रित करता है। Writable `/etc/hosts` file—जिसमें group या ACL से मिली access भी शामिल है—ऐसे नाम को redirect कर सकती है जिसे job स्थानीय रूप से resolve करता है; `curl` response cross-user execution path तभी बनता है जब वास्तविक scheduled command उस response को चलाए और job प्रभावित resolver path का उपयोग करे। Job की run-as identity, exact URL और shell pipeline, प्रभावी proxy/DNS behavior, तथा file और parent-directory permissions सत्यापित करें। Writable hosts file अपने आप में केवल review cue है, privileged consumer का प्रमाण नहीं। Enumeration के दौरान mapping बदले या script fetch किए बिना schedule और metadata देखें।

Privileged scheduled `wget` fetch, भले ही downloaded body सीधे कभी execute न हो, एक अलग file-write boundary है। [GNU Wget 1.18 ने CVE-2016-4971 ठीक करने के लिए HTTP-to-FTP redirect के default filename handling को बदला](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); पुराने प्रभावित builds redirect किए गए FTP filename का उपयोग कर सकते थे, जबकि `--trust-server-names` उस behavior को स्पष्ट रूप से माँगता है। यदि lower-trust party HTTP response और FTP resource नियंत्रित करती है, तो जाँचें कि job उस redirect का अनुसरण करती है या नहीं, उसका वास्तविक Wget build या vendor backport, output options, run-as identity, working directory, और क्या destination filename startup file बन सकता है। [Wget `WGETRC` या `$HOME/.wgetrc` लोड करता है](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), और [उसकी settings POST source या output path चुन सकती हैं](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); बाद का privileged fetch, उससे होने वाले किसी भी disclosure या write के लिए एक अलग prerequisite है। `authbind` के ज़रिए low port तक पहुँच तभी प्रासंगिक है जब caller वास्तव में वह URL serve कर सके जिसे job माँगती है। Redirect serve किए बिना या job चलाए बिना configuration और logs की passive समीक्षा करें। [ `disk` group के ज़रिए raw block-device access](../user-information/interesting-groups-linux-pe/README.md#disk-group) इस network-fetch path से स्वतंत्र है।

Scripts के साथ data files भी trace करें। कोई scheduled simulation या orchestration tool ऐसी YAML file पढ़ सकता है जो शुरू किए जाने वाले processes परिभाषित करती है; यदि lower-privileged user वह file संपादित कर सकता है और job उसे दूसरे account के तहत चलाती है, तो data job की identity के तहत commands बन सकता है। Writable YAML file को execution path मानने से पहले exact scheduled command, प्रभावी user, file path, parser semantics, और write access (parent directories सहित) सत्यापित करें। Passive triage के लिए schedule और file metadata पढ़ना पर्याप्त है; enumeration के दौरान job न चलाएँ और उसका input न बदलें।

जब कोई higher-privileged job `ssh -F` को ऐसी file के साथ चलाती है जिसे lower-privileged user बदल सकता है, तो SSH client configuration भी executable input होती है। OpenSSH का [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) client के shell के ज़रिए local command चलाता है, जबकि `Host`/`Match` और पहले के options तय करते हैं कि वह directive लागू होगी या नहीं। इसे cross-user execution path कहने से पहले exact scheduled SSH invocation, run-as identity, चुना हुआ config path, directory और file की write permissions, और प्रभावी option order का मिलान करें। Job चलाए या privileged account से untrusted config लोड किए बिना इन records की समीक्षा करें।

किसी scheduled `scp` के बाद copied script चलाने के लिए `ssh` का उपयोग हो, तो destination SSH service को lower-privileged user नियंत्रित करता हो तो trust-boundary की दूसरी समीक्षा आवश्यक है। यदि वह service connection को किसी दूसरे host पर forward कर सकती है, तो privileged client अनपेक्षित endpoint से authenticate कर सकता है; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) बदली हुई host key से सुरक्षा कमज़ोर करता है, जो OpenSSH की शेष restrictions और प्रभावी per-host options के अधीन है। Job की run-as identity, वास्तविक destination और authentication method, remote command की प्रभावी identity, और redirected host पर वही destination path writable है या पहले से मौजूद है—इनकी पुष्टि करें। किसी पुराने या attacker-controlled file का execution तभी संभव है जब copy fail हो या वह path न मिले **और** wrapper अपने SSH command तक जारी रहे; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) और explicit status handling इस flow को प्रभावित करते हैं। कमज़ोर host-key setting, दिखाई देने वाली `sshpass` process, या writable temporary directory अकेले इस chain को साबित नहीं करते। Enumeration के दौरान service redirect किए बिना या job trigger किए बिना schedule, script, SSH configuration, और file metadata देखें।

Privileged application scheduler अपनी jobs writable files के बजाय database rows से ले सकता है। उदाहरण के लिए, root cron entry जो Laravel का [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) चलाती है, ऐसे application code तक पहुँच सकती है जो task rows पढ़ता है। यदि lower-privileged account local pathname वाली row लिख सकता है, और scheduled callback root के रूप में PHP का [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) चलाकर लौटे हुए body को row-selected webhook पर भेजता है, तो यह privileged file-disclosure path है। Cron identity, वास्तविक scheduler callback और row-to-path data flow, database write authorization, row पढ़े जाने के बाद validation, और outbound destination सत्यापित करें। पढ़ी जा सकने वाली application `.env` केवल credential lead है; web-form validation या database password अकेले row control या disclosure साबित नहीं करते। Enumeration के दौरान database query किए या task schedule किए बिना schedule, code, और credential-file permissions की passive समीक्षा करें।

Event-driven `incron` jobs की भी इसी तरह समीक्षा करें: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) watched path और event को table owner की identity के तहत चलने वाले command से जोड़ती हैं। कोई lower-privileged user watched file को अप्रत्यक्ष रूप से प्रभावित कर सकता है, जब application writable directory से link follow करके attacker-controlled text watched target में लिखती है। वास्तविक table owner, event, target और ancestor permissions, application का link-following behavior, और उस text के command arguments बनने का तरीका सत्यापित करें। विशेष रूप से, [GNU Mailutils `mail`, `--exec` स्वीकार करता है](https://mailutils.org/manual/html_node/Invoking-Mail.html), और उसका [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) program चला सकता है; उस implementation में अलग option के रूप में दिया गया untrusted field command execution तक पहुँच सकता है। दूसरे `mail` implementations या quoted, fixed argument boundary का behavior अलग हो सकता है। Enumeration के दौरान schedule, application code, और file metadata देखें; watched file न बदलें और job trigger न करें।

Watched log भी helper script के ज़रिए user boundary पार कर सकता है। यदि lower-privileged account log लिख सकता है और `incron` owner उसमें से कोई field पढ़कर नई [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) में डालता है, तो shell उस field को owner की identity के तहत फिर से parse करती है। Exact watched event, log और parent permissions, helper path, log field का transformation, और resulting command तक पहुँचने की पुष्टि करें। केवल writable log और `incron` entry देखने से data flow साबित नहीं होता; passive enumeration के दौरान trigger line न लिखें और helper न चलाएँ।

Certificate-renewal jobs भी यही boundary पार कर सकती हैं। Privileged helper lower-privileged writable directory में certificate से X.509 subject पढ़कर उसका common name नई `bash -c` command string में डाल सकती है। [OpenSSL certificate का subject दिखा सकता है और उसकी expiry जाँच सकता है](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash `-c` string को shell input की तरह parse करता है](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), इसलिए outer script में variable को quote करने से दूसरा parse सुरक्षित नहीं होता। इसे command injection कहने से पहले scheduled identity, exact input path और write rights, renewal branch, तथा `bash -c` तक data flow की पुष्टि करें। Enumeration के दौरान renewal trigger किए बिना script और certificate metadata की passive समीक्षा करें।

यही दूसरा parse तब भी हो सकता है जब privileged scheduled job lower-privileged user के archive या package से नाम निकालकर `xargs -I` के ज़रिए `sh -c` command string में डालती है। [GNU `xargs -I` initial arguments में placeholder को replace करता है](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), और [`sh -c` अपनी command string की व्याख्या करता है](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)। भले ही outer script निकाले गए नाम को quote करे, इससे बाद में substitute किया गया shell program सुरक्षित नहीं हो जाता। Job की run-as identity, स्वीकार किए गए exact input path और write access, archive validation और branch conditions, तथा name-to-shell data flow सत्यापित करें। Writable upload directory या `xargs` invocation अकेले केवल lead हैं; Enumeration के दौरान package submit किए या job चलाए बिना schedule, script, और path metadata देखें।

Scheduled font या image importer भी caller-supplied archive के *अंदर* के नामों पर भरोसा कर सकता है, भले ही upload का बाहरी filename सीमित हो। FontForge ने [CVE-2024-25081 और CVE-2024-25082 के लिए upstream change](https://github.com/fontforge/fontforge/pull/5367) में archive member-name command injection ठीक किया। पुष्टि करें कि higher-privileged job वास्तव में lower-privileged writable path से archive खोलती है या नहीं, उसकी run-as identity, exact FontForge build या vendor backport, और archive-handling code path। Version string या अनुमत upload suffix अकेले execution का प्रमाण नहीं है। Enumeration के दौरान untrusted archive import किए बिना schedule, path permissions, और build metadata देखें।

Scheduled network scanners दूसरी boundary पार कर सकते हैं जब custom script remote TLS certificate subject को local filename मानती है। [Nmap NSE चुनी गई scripts को sandbox के बिना चलाता है](https://nmap.org/book/nse-usage.html), इसलिए वास्तविक script देखें और जाँचें कि वह untrusted subject field को containment checks के बिना data directory से जोड़ती है या नहीं। File disclosure के लिए scheduler द्वारा scan किया जाने वाला target, ऐसा path जो scanner की run-as identity के लिए readable file तक resolve हो, और lower-privileged reader तक पहुँचने वाली report या log आवश्यक हैं। Certificate field या installed scanner अकेले इस chain को साबित नहीं करते; passive enumeration के दौरान नया target scan किए बिना schedule, script, path resolution, और report destination की समीक्षा करें।

किसी privileged cron command द्वारा Ansible runner को `/path/to/tasks/*.yml` जैसा shell glob देना directory-permission जाँच की माँग करता है, भले ही हर मौजूदा playbook read-only हो। Globbed directory में write और search access वाला user एक और matching playbook बना सकता है। [Ansible playbooks वे tasks परिभाषित करती हैं जिन्हें runner execute करता है](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), लेकिन custom wrapper paths filter कर सकता है या अलग identity इस्तेमाल कर सकता है: directory को execution path मानने से पहले उसका behavior, वास्तविक cron user, shell expansion, ACLs, sticky bit, और mount policy सत्यापित करें। Enumeration के दौरान job चलाए बिना metadata और wrapper की static समीक्षा करें।

Privileged cron wrapper glob expand करने के बाद upload directory से filenames Perl helper को दे सकता है। Perl का [`<>` diamond operator two-argument `open` का उपयोग करता है](https://perldoc.perl.org/perlop#The-Null-Filehandle), इसलिए pipe command के रूप में interpreted matching filename helper की identity के तहत execute हो सकता है; [`<<>>` arguments को literal filenames की तरह मानता है](https://perldoc.perl.org/perlop#The-Null-Filehandle)। Scheduler identity, wrapper की working directory और glob, helper का वास्तविक `@ARGV` handling, filename restrictions, और यह सत्यापित करें कि lower-privileged identity filesystem rights या authenticated upload service के ज़रिए matching name रख सकती है या नहीं। Cron line, Perl script, या writable FTP directory अकेले पूरी chain साबित नहीं करते। Crafted filename submit किए या job चलाए बिना source और metadata देखें।

Read-only cron script भी replace की जा सकती है, यदि scheduled account उसे pathname से चलाता है और lower-privileged user उसकी non-sticky parent directory में write और traverse कर सकता है। Schedule की run-as identity, path के हर component, directory sticky bit, ACLs और mount policy जाँचें; file को move किए या job चलाए बिना metadata देखें।

Privileged PHP cron wrapper ऐसे helper तक पहुँच सकता है जो अभी मौजूद नहीं है। यदि वह PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) को fixed absolute helper path के साथ call करता है, तो उस parent directory में वह नाम बनाने में सक्षम lower-privileged user तय कर सकता है कि अगली run में क्या execute होगा। पुष्टि करें कि cron entry वास्तव में wrapper को higher identity के तहत चलाती है, exact command string और PHP execution policy, helper directory पर write और search rights, symlink तथा sticky-bit behavior, और helper path का अभी absent होना। Writable directory या missing helper अकेले केवल lead हैं; Enumeration के दौरान helper बनाए या job trigger किए बिना schedule, source, और path metadata देखें।

कोई scheduled job `find` से input scripts खोजकर हर एक को interpreter को दे सकती है। उदाहरण के लिए, [gnuplot का `system()` function shell चलाता है](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), इसलिए lower-privileged user की writable directory में हर `*.plt` file पर `gnuplot` चलाने वाली privileged job, job की identity के साथ commands execute कर सकती है। [Directory की read permission listing नियंत्रित करती है, जबकि write और search (`x`) किसी ज्ञात नाम को बनाने और access करने की अनुमति नियंत्रित करते हैं](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); directory को `ls` से list न कर पाने पर भी write और search access जाँचें। Exact scheduler identity और command, interpreter का behavior, चुना गया file pattern, और directory permissions का मिलान करें; writable directory या installed interpreter अकेले escalation साबित नहीं करते। Private schedules और कम समय चलने वाली jobs के लिए अधिकृत event observation आवश्यक हो सकता है, क्योंकि एक process snapshot उन्हें छोड़ सकता है।

Privileged PHP job के लिए executable script chain के हिस्से के रूप में literal `include`/`require` statements भी देखें। [PHP included files को evaluate करता है](https://www.php.net/manual/en/function.include.php), इसलिए group-writable included `.php` file job की identity के तहत code चला सकती है, भले ही main script read-only हो। Scheduled identity, प्रभावी include-path resolution, file और directory permissions, और job का वास्तव में चलना सत्यापित करें; comment में मौजूद sample cron line केवल एक clue है। यही समीक्षा root-owned [PHP built-in server](https://www.php.net/commandline.webserver) पर भी लागू होती है, जिसे `-S` और `-t <document-root>` के साथ शुरू किया गया हो: loopback listener भी local requests के लिए application PHP execute कर सकता है। Enumeration के दौरान trigger चलाए बिना process और source देखें।

Privileged PHP job **data file** के ज़रिए भी boundary पार कर सकती है: यदि lower-privileged user [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) को दी गई exact file बदल सकता है, तो PHP object restore करते समय loaded class का `__wakeup()` या `__unserialize()` method invoke कर सकता है। Job की प्रभावी identity, file और ancestor permissions, loaded classes, और वास्तविक method side effects—जैसे property-selected file write—की समीक्षा करें। Writable log या `unserialize()` call अकेले usable path साबित नहीं करते। Enumeration के दौरान serialized input लिखे या job चलाए बिना source और metadata देखें।

Root cron task web server के बजाय PHP application का **CLI page runner** चला सकता है। Runner के चुने हुए document root और URI को वास्तविक PHP entrypoint तक trace करें; यदि web-service account उस entrypoint को लिख सकता है, तो scheduled CLI request बदला हुआ code root के रूप में execute कर सकती है, भले ही runner और cron wrapper read-only हों। Scheduler identity, exact URI-to-file resolution, प्रभावी file और ancestor permissions, और entrypoint को integrity check से सुरक्षित किया गया है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान runner चलाए या page बदले बिना source और metadata देखें।

Shared working directory से scheduled job या किसी अन्य user द्वारा शुरू की गई `ipython` process की startup files की समीक्षा करें। [IPython के security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) बताते हैं कि CVE-2022-21699 के fix से पहले प्रभावित builds current directory में profiles और configuration, जिनमें `profile_default/startup` code भी शामिल है, खोजते थे। वास्तविक installed build या vendor patch, command working directory, higher-privileged process identity, और lower-privileged user की exact startup path पर write और search करने की क्षमता का मिलान करें। Installed `ipython`, writable directory, या version string अकेले यह साबित नहीं करते कि कोई दूसरी identity वहाँ file load करेगी। Higher-privileged interpreter launch किए बिना schedule और path metadata देखें।

Custom native extension के functions call करने वाले privileged PHP server के लिए extension की समीक्षा से पहले service का PHP SAPI और उसकी प्रभावी `php.ini` तथा scanned `.ini` files trace करें। [PHP startup पर configured `extension` libraries load करता है](https://www.php.net/manual/en/ini.core.php), और [CLI तथा web SAPIs अलग configuration files इस्तेमाल कर सकते हैं](https://www.php.net/manual/en/configuration.file.php)। इसलिए कोई reachable login form या local listener, user-controlled strings को service identity के तहत चल रहे compiled code तक पहुँचा सकता है। Unit का `User=`, `ExecStart=`, working directory, वास्तविक extension path, और caller-controlled arguments दर्ज करें; केवल `.so` की मौजूदगी या loopback socket memory-corruption flaw साबित नहीं करते। Passive enumeration के दौरान probes भेजने के बजाय किसी भी custom parser का अलग से विश्लेषण करें।

जब privileged wrapper script को pathname से hash करता है और बाद में execute करने के लिए उसी pathname को फिर खोलता है, तो digest केवल पहले open में पढ़े गए object को authenticate करता है। यदि lower-privileged user उन दोनों opens के बीच script की directory entry बदल सकता है, तो original script file root-owned होने पर भी बाद का execution अलग object resolve कर सकता है। FIFO check phase को लंबा कर सकता है, लेकिन path replaceable parent-directory rights, वास्तव में अलग-अलग opens, scheduler identity, sticky-bit और mount rules, तथा timing पर निर्भर है। Wrapper और `namei -l` output को passive lead की तरह देखें; सफल checksum इस बात का प्रमाण नहीं है कि बाद का pathname सुरक्षित है।

Privileged backup job attacker-supplied commands execute किए बिना भी data **disclose** कर सकती है। Trace करें कि lower-privileged user ऐसी control file बना सकता है या नहीं जिसे job पढ़ती है, क्या job उसके बाद `/etc/shadow` जैसे protected source को खोलती है, और क्या attacker-selected URL या readable output को परिणाम मिलता है। इसे disclosure path कहने से पहले तीनों हिस्सों की पुष्टि करें। उसी script में fixed shell command होने से control file अपने आप shell-injection input नहीं बनती। Enumeration के दौरान job चलाए या control file डाले बिना script और file permissions देखें।

यदि privileged scheduled job `curl -K FILE` या `curl --config FILE` चलाती है, तो [curl उस file के options को command-line arguments की तरह मानता है](https://curl.se/docs/manpage.html)। `curl` द्वारा पढ़े जाते समय exact file को नियंत्रित करने वाला lower-privileged user requested URL, local-file input, या output path को प्रभावित कर सकता है। Protected read या write का दावा करने से पहले job की प्रभावी identity, file और ancestor पर write rights, file को replace करने वाली किसी दूसरी job का timing, और config options का fixed command-line options के साथ interaction सत्यापित करें। Writable config path या दिखाई देने वाला `-K` flag अकेले यह साबित नहीं करते कि चुने गए options प्रभावी होंगे; Enumeration के दौरान job चलाए या URL fetch किए बिना schedule और metadata देखें।

यदि cron entry helper script चलाती है, तो helper की working directory और archive command भी देखें। किसी अन्य user द्वारा writable directory पर unquoted wildcard filenames को archiver options में बदल सकता है; GNU tar के checkpoint actions इसका एक उदाहरण हैं। Cross-user command path का दावा करने से पहले scheduled run-as identity, writable input directory, exact archiver और options, तथा `--` option parsing समाप्त करता है या नहीं—इनकी पुष्टि करें। [wildcard और tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md) देखें।

Backup-file disclosure का एक अलग path तब बन सकता है जब privileged helper `cd INPUT_DIR; tar ... *` चलाती है और यह नहीं जाँचती कि `cd` सफल हुआ या नहीं। यदि lower-privileged user `INPUT_DIR` को हटा या बदल सकता है, तो failed `cd` shell को उसकी पिछली directory में छोड़ सकता है, जिसे बाद की archive command पढ़ सकती है। Job की initial working directory, वास्तविक failed-`cd` path, script exit करती है या `&&` इस्तेमाल करती है, exact archiver options, और output archive lower user द्वारा readable है या नहीं—इनकी पुष्टि करें। Writable input directory या readable archive अकेले केवल lead हैं; live job बदले बिना helper और path permissions देखें।

Scheduled executable shell script को छिपा सकती है, लेकिन इससे trust boundary नहीं मिटती: [SHc](https://github.com/neurobin/shc) encrypted script text को native binary में wrap करता है और runtime पर shell के ज़रिए execute करता है। `.sh.x` suffix या अपारदर्शी ELF केवल review lead है। Filename option injection का आकलन करने के लिए privileged scheduler identity, helper की वास्तविक working directory और command, वहाँ matching names बनाने की lower-user की क्षमता, और क्या unquoted glob बिना option boundary के `rsync` जैसे command तक पहुँचता है—इनकी पुष्टि करें। [`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) तभी प्रासंगिक है जब वही exact command path इस्तेमाल हो। Restricted `/proc` visibility या विफल static decryption के कारण command अज्ञात रह सकता है; केवल वर्गीकरण करने के लिए privileged helper न चलाएँ।

Process command-line text भी privileged helper के लिए untrusted input है। Lower-privileged user ऐसा process title या `argv[0]` चुन सकता है जो `pgrep -f` से match करे; matching name executable या उसके owner को authenticate नहीं करता। यदि root-run script उस text को capture करके उसका कुछ हिस्सा `apache2ctl`/`httpd` में बदलती है और fixed argument array के बिना result execute करती है, तो attacker-chosen options अलग configuration directory या error log चुन सकते हैं। Apache configuration parsing modules load कर सकती है या configured helpers तक पहुँच सकती है, इसलिए enumeration के दौरान untrusted configuration को root के रूप में validate न करें। Scheduler owner, exact helper, process identity, और data-to-argument flow देखें; जब तक shell metacharacter execution अलग से प्रदर्शित न हो, यह option/configuration injection है।

Untrusted text को Bash arithmetic में देने वाला root-run parser उस text में मौजूद substitutions execute कर सकता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) में एक worked example है। हर arithmetic expression को exploitable मानने से पहले input source और parsing command की पुष्टि करें।

Application log parse करने वाली privileged job के लिए untrusted fields को पहले parse से आगे trace करें। Lower-privileged account अपनी current process group के ज़रिए log लिख सकता है या logged request fields को प्रभावित कर सकता है; कोई record image चुन सकती है, जिसका metadata XML खोलने के लिए दूसरा pathname बन जाए। Job की प्रभावी identity, वास्तविक log-write access, delimiter handling, canonical path containment, और चुनी गई XML attacker-controlled है या नहीं—इनकी जाँच करें। यदि expanded result lower-privileged-readable output तक पहुँचता है, तो external-entity expansion उस दूसरी read को privileged file disclosure में बदल सकती है। [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) external DTD/entity access के controls बताती है; installed parser और उसकी प्रभावी settings देखें। Writable log या XML file अकेले केवल lead हैं। Enumeration के दौरान scheduled parser को input दिए बिना code और metadata की समीक्षा करें।

किसी अन्य user के Git repository से files materialize करने वाली privileged jobs भी देखें। Script `git checkout` के बजाय `git ls-tree` और `git cat-file` इस्तेमाल कर सकती है, फिर भी staging directory से जोड़ते समय attacker-controlled tree paths पर भरोसा कर सकती है। Absolute paths और `..` components उस directory से बाहर जा सकते हैं, जब तक लिखने से पहले destination को normalize करके containment की जाँच न की जाए। `git -c safe.directory=*` अलग ownership वाली repositories तक पहुँच की अनुमति देता है; यह अपने आप arbitrary-write condition पैदा नहीं करता।

Root-run database backup एक और ownership boundary बना सकता है। PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) source data directory में रखी अतिरिक्त regular files को copy करता है, और इसका default plain format `-D` में directory tree के रूप में files लिखता है। यदि lower-privileged account वे source files बना या बदल सकता है, तो resulting destination ownership और mode, उसका path traversable और executable है या नहीं, और mount पर `nosuid` है या नहीं—इनकी समीक्षा करें। Preserved set-ID permissions वाली root-owned copy खतरनाक हो सकती है; केवल tar backup, stripped permissions, या inaccessible destination से वही path साबित नहीं होता। Backup command को finding मानने से पहले scheduled wrapper और प्रभावी user trace करें।

## Observe short-lived work

एक single process snapshot कुछ milliseconds चलने वाली job को छोड़ सकता है। Timer/cron declarations की logs से तुलना करें और अधिकृत होने पर `pspy` या audit जैसी process-event monitoring करें। Scheduled owner, exact command line, और task द्वारा पढ़ी या लिखी जाने वाली files का मिलान करें। Loopback scheduler web UI एक अलग interface है; [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc) देखें।
