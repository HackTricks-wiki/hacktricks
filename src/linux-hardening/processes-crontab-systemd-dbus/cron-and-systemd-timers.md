# Cron Jobs and Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

スケジュールされたタスクは、現在のシェルとは異なるユーザー権限や環境で実行されることがあります。cron、`at`、anacron、systemd timers を列挙し、各スケジュールコマンドをたどって、スクリプト、インポート、作業ディレクトリ、書き込み可能な入力を確認します。

## スケジュールを列挙する

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

システムの crontab には通常ユーザーフィールドがありますが、ユーザーの crontab にはありません。実際の scheduler の有効な PATH と環境変数を確認してください。`run-parts --test /etc/cron.daily` を実行すると、そのホストで選択されるファイル名が表示されます。制御文字によって通常の出力ではエントリが隠れることがあるため、スケジュールが怪しい場合は `cat -A` または `sed -n l` を使ってください。

## 特権ファイルとコマンドの解決を追跡する

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

高い権限で実行されるタスクが使用または実行する、書き込み可能なスクリプトチェーン、`EnvironmentFile=` のパス、drop-in、シンボリックリンク、相対コマンド、ワイルドカード展開、コピー対象のバイナリを確認します。タイマーは `Unit=` 設定を通じて、別名のサービスを起動する場合があります。[PATH](../linux-basics/linux-environment-variables.md#path)、[wildcard](../interesting-files-permissions/wildcards-spare-tricks.md)、[file-link](../main-system-information/filesystem-links-and-file-descriptors.md) の各ページで、主なプリミティブを解説しています。

root で実行される定期 `chkrootkit` スクリプトについては、インストール済みソースを調べ、古い [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) があるか確認します。`SLAPPER_FILES` の一時パスをチェックした後に、`file_port=$file_port $i` のように引用符で囲まず実行していると、そのファイルを実行できる可能性があります。実際のスクリプトまたはベンダーパッチ、root でのスケジュール実行、対象の正確な一時パスに対する低権限ユーザーの書き込み権限、実行可能属性、マウントポリシーを確認してください。バージョン文字列や `chkrootkit` の存在だけでは、このパスが成立する証拠になりません。受動的な調査では、一時ファイルを作成したり実行したりしないでください。

root のタイマーサービスが `systemctl restart <other>.service` を実行する場合は、さらに1段階先の unit も追跡します。再起動される unit が、低権限ユーザーの書き込み可能なスクリプトを使ってシェルを起動する可能性があります。有効な `User=`、`DynamicUser=`、`RootDirectory=`/`RootImage=`、正確な `ExecStart=` 引数、スクリプトと親パスの権限を確認してください。書き込み可能なスクリプトは候補にすぎず、その実行コンテキストでタイマーと再起動対象のサービスが有効でなければ、実行パスは成立しません。サービスを再起動せずに unit のプロパティを調べてください。

高い権限のジョブがホスト名でスクリプトを取得し、レスポンスをシェルに渡す場合、リモートスクリプトだけでなく、そのホスト名の名前解決を誰が制御できるかも確認します。グループや ACL によるアクセスも含め、書き込み可能な `/etc/hosts` は、ジョブがローカルで名前解決するホスト名を別の宛先に誘導できます。`curl` のレスポンスがユーザー間の実行パスになるのは、実際のスケジュールコマンドがそのレスポンスを実行し、ジョブが影響を受けるリゾルバー経路を使う場合に限られます。ジョブの実行ユーザー、正確な URL とシェルパイプライン、有効なプロキシ/DNS の動作、ファイルと親ディレクトリの権限を確認してください。hosts ファイルが書き込み可能というだけでは、高権限の利用者がいる証拠にはならず、確認の手がかりにすぎません。列挙中は、スケジュールとメタデータを調べるだけにとどめ、マッピングを変更したりスクリプトを取得したりしないでください。

高い権限でスケジュール実行される `wget` による取得は、ダウンロードした内容を直接実行しない場合でも、別個のファイル書き込み境界になります。[GNU Wget 1.18 changed the default HTTP-to-FTP redirect filename handling to fix CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html)。影響を受ける古いビルドでは、リダイレクト先 FTP のファイル名が使用される場合があり、`--trust-server-names` はその動作を明示的に要求します。信頼度の低いユーザーが HTTP レスポンスと FTP リソースを制御できる場合、ジョブがリダイレクトに従うか、実際の Wget ビルドまたはベンダーバックポート、出力オプション、実行ユーザー、作業ディレクトリ、保存先ファイル名が起動ファイルになり得るかを確認します。[Wget loads `WGETRC` or `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html)、また[設定で POST 元や出力先を指定できます](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html)。それによって情報漏えいや書き込みが発生するには、後続の高権限取得が別途必要です。`authbind` 経由で低位ポートを使えることが関係するのは、呼び出し元がジョブの要求する URL を実際に提供できる場合に限られます。リダイレクトを提供したりジョブを実行したりせず、設定とログを受動的に確認してください。[`disk` グループ経由の raw block-device access](../user-information/interesting-groups-linux-pe/README.md#disk-group) は、このネットワーク取得経路とは別の問題です。

スクリプトだけでなくデータファイルも追跡します。スケジュール実行されるシミュレーションやオーケストレーションツールが、起動するプロセスを定義した YAML ファイルを読む場合があります。低権限ユーザーがそのファイルを編集でき、ジョブが別のアカウントで実行するなら、そのデータがジョブの権限で実行されるコマンドになる可能性があります。書き込み可能な YAML ファイルを実行パスと判断する前に、正確なスケジュールコマンド、有効なユーザー、ファイルパス、パーサーの動作、書き込み権限（親ディレクトリを含む）を確認してください。受動的なトリアージでは、スケジュールとファイルメタデータを読むだけで十分です。列挙中にジョブを実行したり入力を変更したりしないでください。

高い権限のジョブが、低権限ユーザーが置き換え可能なファイルを `ssh -F` で指定して実行する場合、SSH クライアント設定も実行可能な入力です。OpenSSH の [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) は、クライアントのシェルを介してローカルコマンドを実行します。一方、`Host`/`Match` と先行するオプションによって、そのディレクティブが適用されるかが決まります。ユーザー間の実行パスと判断する前に、正確なスケジュール SSH 呼び出し、実行ユーザー、選択される設定ファイルのパス、ディレクトリとファイルの書き込み権限、有効なオプション順序を照合してください。ジョブを実行したり、高権限アカウントで信頼できない設定を読み込んだりせずに記録を確認します。

スケジュールされた `scp` の後に `ssh` でコピー済みスクリプトを実行する場合、低権限ユーザーが宛先の SSH サービスを制御できるなら、別途、信頼境界を確認する必要があります。そのサービスが接続を別のホストへ転送できると、高権限クライアントが意図しない接続先で認証する可能性があります。[`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) は、OpenSSH に残る制限と有効なホスト別オプションの範囲内で、ホスト鍵変更に対する保護を弱めます。ジョブの実行ユーザー、実際の宛先と認証方式、リモートコマンドの有効な実行ユーザー、転送先ホストの同じ宛先パスが書き込み可能か、またはすでに存在するかを確認します。古いファイルや攻撃者が制御するファイルが実行されるには、コピーが失敗するかそのパスを対象にしないことに**加え**、ラッパーが SSH コマンドまで処理を続ける必要があります。[Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) や明示的な終了ステータス処理が、その流れに影響します。ホスト鍵設定の弱さ、`sshpass` プロセスの表示、一時ディレクトリの書き込み権限だけでは、このチェーンは成立しません。列挙中にサービスを転送したりジョブを起動したりせず、スケジュール、スクリプト、SSH 設定、ファイルメタデータを確認してください。

高権限のアプリケーションスケジューラは、書き込み可能なファイルではなくデータベース行からジョブを取得する場合があります。たとえば、root の cron エントリが Laravel の [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) を実行し、タスク行を読むアプリケーションコードに到達することがあります。低権限アカウントがローカルのパス名を含む行を書き込めて、スケジュールされたコールバックが root で PHP の [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) を呼び出し、返された内容を行で指定された webhook に送るなら、これは高権限のファイル情報漏えい経路です。cron の実行ユーザー、実際のスケジューラコールバックと行からパスへのデータフロー、データベースの書き込み権限、行を読んだ後の検証、外部送信先を確認します。読み取り可能なアプリケーションの `.env` は認証情報の手がかりにすぎず、Web フォームの検証やデータベースパスワードだけでは、行の制御や情報漏えいの証拠になりません。列挙中にデータベースへ問い合わせたりタスクを登録したりせず、スケジュール、コード、認証情報ファイルの権限を受動的に調べてください。

イベント駆動の `incron` ジョブも同様に確認します。[incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) は、監視対象のパスとイベントを、テーブル所有者の権限で実行するコマンドに関連付けます。アプリケーションが書き込み可能なディレクトリ内のリンクをたどり、攻撃者が制御するテキストを監視対象へ書き込む場合、低権限ユーザーが間接的に監視ファイルへ影響を与える可能性があります。実際のテーブル所有者、イベント、対象と親ディレクトリの権限、アプリケーションのリンク追跡動作、そのテキストがコマンド引数になる方法を確認します。特に、[GNU Mailutils `mail` accepts `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html)。その[シェルエスケープコマンド](https://mailutils.org/manual/html_node/Shell-Escapes.html) はプログラムを実行できます。この実装で信頼できないフィールドが独立したオプションとして渡されると、コマンド実行に至る可能性があります。他の `mail` 実装や、引用符で保護された固定の引数境界では動作が異なることがあります。列挙中に監視対象ファイルを変更したりジョブを起動したりせず、スケジュール、アプリケーションコード、ファイルメタデータを確認してください。

監視対象のログも、ヘルパースクリプトを介してユーザー境界を越える場合があります。低権限アカウントがログへ書き込めて、`incron` の実行ユーザーがそこから取り出したフィールドを新しい [`sh -c` コマンド文字列](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) に組み込むなら、シェルはそのフィールドを実行ユーザーの権限で再解析します。対象イベント、ログと親ディレクトリの権限、ヘルパーのパス、ログフィールドの変換方法、最終的にそのコマンドが実行されるかを確認してください。書き込み可能なログと `incron` エントリがあるだけでは、データフローの証拠になりません。受動的な調査中にトリガー行を書き込んだり、ヘルパーを実行したりしないでください。

証明書更新ジョブも同じ境界を越える場合があります。高権限ヘルパーが、低権限ユーザーの書き込み可能なディレクトリにある証明書から X.509 subject を読み取り、その common name を新しい `bash -c` コマンド文字列に挿入する場合です。[OpenSSL can display a certificate's subject and check its expiry](https://docs.openssl.org/3.3/man1/openssl-x509/)。[Bash parses the `-c` string as shell input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html) ため、外側のスクリプトで変数を引用符で囲んでも、2回目の解析は保護されません。コマンドインジェクションと判断する前に、スケジュールされた実行ユーザー、正確な入力パスと書き込み権限、更新処理の分岐、その値が `bash -c` に渡る流れを確認します。列挙中はスクリプトと証明書のメタデータを受動的に調べ、更新をトリガーしないでください。

低権限ユーザーのアーカイブやパッケージから名前を取り出し、`xargs -I` で `sh -c` コマンド文字列に挿入する高権限のスケジュールジョブでも、同じ2回目の解析が起きる場合があります。[GNU `xargs -I` replaces the placeholder in initial arguments](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html)、そして[`sh -c` interprets its command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)。外側のスクリプトで取り出した名前を引用符で囲んでいても、後から置換されるシェルプログラムが安全になるわけではありません。ジョブの実行ユーザー、受け付ける入力パスと書き込み権限、アーカイブ検証と分岐条件、名前からシェルへのデータフローを確認してください。書き込み可能なアップロードディレクトリや `xargs` の呼び出しだけでは手がかりにすぎません。列挙中にパッケージを送信したりジョブを実行したりせず、スケジュール、スクリプト、パスのメタデータを調べてください。

スケジュールされたフォントまたは画像のインポーターは、アップロード時の外側のファイル名が制限されていても、ユーザー提供アーカイブ内の名前を信頼してしまうことがあります。FontForge は、アーカイブ内のメンバー名によるコマンドインジェクションを、[CVE-2024-25081 and CVE-2024-25082 に対する upstream change](https://github.com/fontforge/fontforge/pull/5367) で修正しました。高権限のジョブが低権限ユーザーの書き込み可能なパスから実際にアーカイブを開くか、実行ユーザー、正確な FontForge ビルドまたはベンダーバックポート、アーカイブ処理のコードパスを確認してください。バージョン文字列や許可されたアップロード拡張子だけでは実行の証拠になりません。列挙中に信頼できないアーカイブをインポートせず、スケジュール、パス権限、ビルドメタデータを調べてください。

スケジュールされたネットワークスキャナーは、カスタムスクリプトがリモート TLS 証明書の subject をローカルファイル名として扱う場合、別の境界を越えることがあります。[Nmap NSE runs selected scripts without a sandbox](https://nmap.org/book/nse-usage.html)。実際のスクリプトを確認し、信頼できない subject フィールドを、包含チェックなしにデータディレクトリへ連結していないか調べます。情報漏えいが成立するには、スケジューラがスキャンする対象、そのスキャナーの実行ユーザーが読み取り可能なファイルに解決されるパス、低権限ユーザーが読めるレポートまたはログが必要です。証明書フィールドやスキャナーがインストールされていることだけでは、そのチェーンの証拠になりません。受動的な列挙中に新しい対象をスキャンせず、スケジュール、スクリプト、パスの解決先、レポートの保存先を確認してください。

`/path/to/tasks/*.yml` のようなシェル glob を Ansible runner に渡す高権限 cron コマンドは、既存の playbook がすべて読み取り専用でも、ディレクトリ権限を確認する必要があります。glob 対象ディレクトリに書き込みと検索の権限があるユーザーは、新たに一致する playbook を作成できる可能性があります。[Ansible playbooks define tasks that the runner executes](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html)。ただし、カスタムラッパーがパスをフィルタリングしたり別の実行ユーザーを使ったりする場合があります。ディレクトリを実行パスと判断する前に、その動作、実際の cron ユーザー、シェル展開、ACL、sticky bit、マウントポリシーを確認してください。列挙中はメタデータとラッパーを静的に調べ、スケジュールジョブを実行しないでください。

高権限の cron ラッパーが、glob 展開後のアップロードディレクトリ内のファイル名を Perl ヘルパーに渡すことがあります。Perl の [`<>` diamond operator uses two-argument `open`](https://perldoc.perl.org/perlop#The-Null-Filehandle) は、一致するファイル名がパイプコマンドとして解釈されると、ヘルパーの権限で実行する可能性があります。一方、[`<<>>` treats arguments as literal filenames](https://perldoc.perl.org/perlop#The-Null-Filehandle)。スケジューラの実行ユーザー、ラッパーの作業ディレクトリと glob、ヘルパーの実際の `@ARGV` 処理、ファイル名制限、ファイルシステム権限または認証済みアップロードサービスを通じて低権限ユーザーが一致する名前を配置できるかを確認してください。cron 行、Perl スクリプト、書き込み可能な FTP ディレクトリだけではチェーン成立の証拠になりません。列挙中に細工したファイル名を送信したりジョブを実行したりせず、ソースとメタデータを調べてください。

読み取り専用の cron スクリプトでも、スケジュールされたアカウントがパス名で実行し、低権限ユーザーが sticky bit のない親ディレクトリに書き込み・検索できるなら、置き換え可能です。スケジュールの実行ユーザー、すべてのパス構成要素、ディレクトリの sticky bit、ACL、マウントポリシーを確認し、ファイルを移動したりジョブを実行したりせずにメタデータを調べてください。

高権限の PHP cron ラッパーは、まだ存在しないヘルパーを呼び出す場合もあります。固定の絶対ヘルパーパスを PHP の [`exec()`](https://www.php.net/manual/en/function.exec.php) に渡すなら、その親ディレクトリに低権限ユーザーが同名ファイルを作成できる場合、後続の実行で何が起動するかを制御できる可能性があります。cron エントリが実際に高権限でラッパーを実行するか、正確なコマンド文字列と PHP の実行ポリシー、ヘルパーディレクトリへの書き込み・検索権限、シンボリックリンクと sticky bit の動作、ヘルパーパスがまだ存在しないかを確認してください。書き込み可能なディレクトリや未作成のヘルパーだけでは手がかりにすぎません。列挙中にヘルパーを作成したりジョブをトリガーしたりせず、スケジュール、ソース、パスのメタデータを確認してください。

スケジュールジョブが `find` で入力スクリプトを見つけ、インタープリターに渡す場合もあります。たとえば、[gnuplot's `system()` function invokes a shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf)。低権限ユーザーの書き込み可能なディレクトリにあるすべての `*.plt` ファイルを高権限ジョブが `gnuplot` で実行すると、ジョブの権限でコマンドを実行できる可能性があります。[Directory read permission controls listing, while write and search (`x`) control creating and accessing known names](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html)。`ls` で一覧表示できなくても、書き込みと検索の権限を確認してください。スケジューラの正確な実行ユーザーとコマンド、インタープリターの動作、選択されるファイルパターン、ディレクトリ権限を照合します。書き込み可能なディレクトリやインタープリターのインストールだけでは、権限昇格の証拠になりません。非公開スケジュールや短時間のジョブは、プロセスの単一スナップショットでは見逃すことがあるため、必要に応じて許可を得た上でイベントを監視してください。

高権限の PHP ジョブでは、実行スクリプトチェーンの一部として、リテラルの `include`/`require` 文も確認してください。[PHP evaluates included files](https://www.php.net/manual/en/function.include.php)。そのため、メインスクリプトが読み取り専用でも、グループ書き込み可能な `.php` ファイルがジョブの権限でコードを実行する可能性があります。スケジュールされた実行ユーザー、有効な include-path の解決、ファイルとディレクトリの権限、ジョブが実際に動くかを確認してください。コメント内の cron 記述例は手がかりにすぎません。同じ確認は、`-S` と `-t <document-root>` で起動された root 所有の [PHP built-in server](https://www.php.net/commandline.webserver) にも当てはまります。ループバックリスナーでも、ローカルリクエストによってアプリケーションの PHP が実行される場合があります。列挙中にどちらのトリガーも呼び出さず、プロセスとソースを調べてください。

高権限の PHP ジョブは**データファイル**を通じても境界を越えることがあります。低権限ユーザーが [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) に渡される正確なファイルを変更できる場合、PHP はオブジェクト復元時にロード済みクラスの `__wakeup()` または `__unserialize()` メソッドを呼び出すことがあります。ジョブの有効な実行ユーザー、ファイルと親ディレクトリの権限、ロードされるクラス、プロパティで指定されたファイルへの書き込みなど、実際のメソッドの副作用を確認してください。書き込み可能なログや `unserialize()` の呼び出しだけでは、利用可能なパスの証拠になりません。列挙中にシリアライズ済み入力を書き込んだりジョブを実行したりせず、ソースとメタデータを調べてください。

root cron タスクは、Web サーバーではなく PHP アプリケーションの**CLI ページランナー**を呼び出す場合があります。ランナーが選択する document root と URI を実際の PHP エントリーポイントまで追跡します。そのエントリーポイントが Web サービスアカウントによって書き換え可能なら、ランナーや cron ラッパーが読み取り専用でも、スケジュールされた CLI リクエストは変更後のコードを root で実行できます。スケジューラの実行ユーザー、URI からファイルへの正確な解決、有効なファイルと親ディレクトリの権限、エントリーポイント自体を保護する整合性チェックの有無を確認してください。列挙中にランナーを呼び出したりページを変更したりせず、ソースとメタデータを調べてください。

スケジュールジョブなどによって共有作業ディレクトリから起動される `ipython` プロセスでは、起動ファイルを確認します。[IPython's security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) によると、CVE-2022-21699 の修正前の影響を受けるビルドは、カレントディレクトリのプロファイルや設定（`profile_default/startup` のコードなど）を検索していました。実際のインストール済みビルドまたはベンダーパッチ、コマンドの作業ディレクトリ、高権限プロセスの実行ユーザー、低権限ユーザーが正確な起動パスに対して書き込み・検索できるかを照合します。`ipython` のインストール、書き込み可能なディレクトリ、バージョン文字列だけでは、別の実行ユーザーがそこにあるファイルを読み込む証拠になりません。高権限のインタープリターを起動せず、スケジュールとパスのメタデータを調べてください。

カスタムネイティブ拡張の関数を呼び出す高権限 PHP サーバーでは、拡張機能を調べる前に、サービスの PHP SAPI と有効な `php.ini` および追加読み込みされる `.ini` ファイルを追跡します。[PHP loads configured `extension` libraries at startup](https://www.php.net/manual/en/ini.core.php)、また[CLI と Web の SAPI では異なる設定ファイルが使われる場合があります](https://www.php.net/manual/en/configuration.file.php)。そのため、アクセス可能なログインフォームやローカルリスナーを通じて、ユーザー制御の文字列がサービスの権限で動くコンパイル済みコードに渡る可能性があります。unit の `User=`、`ExecStart=`、作業ディレクトリ、実際の拡張機能パス、呼び出し元が制御できる引数を記録します。`.so` の存在やループバックソケットだけでは、メモリ破壊の脆弱性を示す証拠になりません。受動的な列挙中にプローブを送らず、カスタムパーサーは別途解析してください。

高権限ラッパーがパス名でスクリプトのハッシュを計算し、後から同じパスを開いて実行する場合、そのダイジェストが認証するのは最初のオープン時に読み取ったオブジェクトだけです。低権限ユーザーが2回のオープンの間にスクリプトのディレクトリエントリを置き換えられると、元のスクリプトが root 所有でも、後の実行では別のオブジェクトが解決される可能性があります。FIFO はチェック段階を長引かせることがありますが、このパスが成立するかは、置き換え可能な親ディレクトリの権限、実際に別々のオープンがあるか、スケジューラの実行ユーザー、sticky bit とマウントの規則、タイミングに依存します。ラッパーと `namei -l` の出力を受動的な手がかりとして調べてください。チェックサムが一致するだけでは、後続のパス名でのアクセスが保護されている証拠になりません。

高権限のバックアップジョブは、攻撃者のコマンドを実行せずにデータを**漏えい**することもあります。低権限ユーザーがジョブの読む制御ファイルを作成できるか、ジョブが `/etc/shadow` など保護対象のソースを開くか、攻撃者が選んだ URL または読み取り可能な出力先に結果を渡すかを追跡します。情報漏えい経路と判断する前に、3つすべてを確認してください。同じスクリプト内のシェルコマンドが固定されているからといって、制御ファイルがシェルインジェクション入力になるわけではありません。列挙中にジョブを実行したり制御ファイルを配置したりせず、スクリプトとファイル権限を調べてください。

高権限のスケジュールジョブが `curl -K FILE` または `curl --config FILE` を実行する場合、[curl treats options in that file as command-line arguments](https://curl.se/docs/manpage.html)。curl が読む時点で低権限ユーザーがそのファイルを制御できると、要求 URL、ローカルファイル入力、出力パスに影響を与える可能性があります。保護対象の読み取りや書き込みを主張する前に、ジョブの有効な実行ユーザー、ファイルと親ディレクトリへの書き込み権限、別のジョブがファイルを置き換えるタイミング、設定オプションと固定のコマンドラインオプションの相互作用を確認します。設定パスが書き込み可能、または `-K` フラグが見えるだけでは、選択したオプションが有効になる証拠になりません。列挙中にジョブを実行したり URL を取得したりせず、スケジュールとメタデータを調べてください。

cron エントリがヘルパースクリプトを呼び出す場合は、その作業ディレクトリとアーカイブコマンドも確認してください。他のユーザーが書き込み可能なディレクトリに対して引用符なしのワイルドカードを使うと、ファイル名をアーカイバーのオプションとして解釈させられる場合があります。GNU tar の checkpoint action はその一例です。ユーザー間のコマンド実行経路と判断する前に、スケジュールの実行ユーザー、書き込み可能な入力ディレクトリ、正確なアーカイバーとオプション、`--` でオプション解析を終了しているかを確認します。[wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md) を参照してください。

高権限ヘルパーが `cd INPUT_DIR; tar ... *` を実行し、`cd` の成否を確認しない場合、別のバックアップファイル情報漏えいが起きる可能性があります。低権限ユーザーが `INPUT_DIR` を削除または置き換えられると、`cd` の失敗後もシェルが元のディレクトリに残り、その後のアーカイブコマンドがそこを読み込むことがあります。ジョブの初期作業ディレクトリ、実際に `cd` が失敗する経路、スクリプトが終了するか `&&` を使うか、正確なアーカイバーオプション、出力アーカイブを低権限ユーザーが読めるかを確認してください。書き込み可能な入力ディレクトリや読み取り可能なアーカイブだけでは手がかりにすぎません。稼働中のジョブを変更せず、ヘルパーとパス権限を調べてください。

スケジュールされた実行ファイルがシェルスクリプトを隠している場合でも、信頼境界は変わりません。[SHc](https://github.com/neurobin/shc) は、暗号化されたスクリプトテキストをネイティブバイナリでラップし、実行時にシェルを介して実行します。`.sh.x` という拡張子や、内容が判然としない ELF は調査の手がかりにすぎません。ファイル名によるオプションインジェクションを評価するには、スケジューラの高権限実行ユーザー、ヘルパーの実際の作業ディレクトリとコマンド、低権限ユーザーがその場所に一致する名前を作成できるか、引用符なしの glob がオプション境界なしに `rsync` などのコマンドへ渡るかを確認します。[`rsync` の remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) が関係するのは、その正確なコマンドパスが使われている場合に限られます。`/proc` の可視性が制限されている、または静的な復号に失敗したことでコマンドが不明な場合、分類のためだけに高権限ヘルパーを実行しないでください。

プロセスのコマンドライン文字列も、高権限ヘルパーに渡される信頼できない入力です。低権限ユーザーは、`pgrep -f` に一致するプロセスタイトルや `argv[0]` を指定できます。一致した名前は、実行ファイルやその所有者を認証するものではありません。root で実行されるスクリプトがその文字列を取得し、一部を `apache2ctl`/`httpd` に書き換えて固定の引数配列を使わず実行すると、攻撃者が選んだオプションで別の設定ディレクトリやエラーログを指定できる可能性があります。Apache の設定解析はモジュールを読み込んだり、設定済みヘルパーに到達したりする場合があるため、列挙中に root で信頼できない設定を検証しないでください。スケジューラの所有者、正確なヘルパー、プロセスの識別情報、データから引数への流れを調べます。シェルのメタ文字による実行が別途示されない限り、これはオプション/設定インジェクションです。

高権限で実行されるパーサーが、信頼できないテキストを Bash の算術式に渡すと、そのテキスト内の置換が実行されることがあります。[privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) に具体例があります。あらゆる算術式を悪用可能と判断する前に、入力元と解析コマンドを確認してください。

アプリケーションログを解析する高権限ジョブでは、最初の解析以降の信頼できないフィールドも追跡します。低権限アカウントが現在のプロセスグループを通じてログに書き込めたり、ログに記録されるリクエストフィールドに影響を与えたりできる場合があります。ログレコードが画像を選び、そのメタデータが XML を開くための2つ目のパス名になることもあります。ジョブの有効な実行ユーザー、実際のログ書き込み権限、区切り文字の処理、正規化後のパスが所定の範囲内にあるか、選択された XML が攻撃者に制御されるかを確認してください。外部エンティティ展開によって、展開結果が低権限ユーザーの読み取り可能な出力へ渡るなら、高権限のファイル情報漏えいが起きる可能性があります。[Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) では、外部 DTD/エンティティアクセスの制御が説明されています。インストール済みのパーサーと有効な設定を調べてください。書き込み可能なログや XML ファイルだけでは手がかりにすぎません。列挙中にスケジュールされたパーサーへ入力を渡さず、コードとメタデータを調べてください。

他のユーザーの Git リポジトリからファイルを生成する高権限ジョブも確認してください。スクリプトが `git checkout` ではなく `git ls-tree` と `git cat-file` を使っていても、攻撃者が制御する tree path をステージングディレクトリに連結している場合は、そのパスを信頼していることになります。書き込み前に保存先を正規化して包含関係を検証しなければ、絶対パスや `..` を含む要素でそのディレクトリの外へ書き出せる可能性があります。`git -c safe.directory=*` は、所有者が異なるリポジトリへのアクセスを許可しますが、それ自体では任意ファイル書き込みにはなりません。

root で実行するデータベースバックアップが、別の所有権境界を作ることもあります。PostgreSQL の [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) は、ソースのデータディレクトリに追加された通常ファイルをコピーします。デフォルトの plain format では、`-D` にディレクトリツリーとしてファイルを書き込みます。低権限アカウントがこれらのソースファイルを作成または変更できる場合、コピー先の所有者とモード、パスをたどって実行できるか、マウントに `nosuid` が設定されているかを確認してください。set-ID 権限を保った root 所有のコピーは危険な場合があります。tar のみのバックアップ、権限の除去、アクセス不能な保存先では、同じパスが成立するとは限りません。バックアップコマンドを問題として扱う前に、スケジュールされたラッパーと有効な実行ユーザーを追跡してください。

## 短時間の処理を観察する

ミリ秒単位で実行されるジョブは、単一のプロセススナップショットでは見逃す場合があります。タイマー/cron の宣言とログを照合し、許可がある場合は `pspy` や audit などでプロセスイベントを監視します。スケジュールされた実行ユーザー、正確なコマンドライン、タスクが読み書きするファイルを照合してください。ループバックのスケジューラ Web UI は別のインターフェイスです。[Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc) を参照してください。
