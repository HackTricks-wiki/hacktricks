# Tâches cron et timers systemd

{{#include ../../banners/hacktricks-training.md}}

Les tâches planifiées peuvent s’exécuter avec une identité et un environnement différents de ceux du shell courant. Énumérez cron, `at`, anacron et les timers systemd, puis examinez chaque commande planifiée, ses scripts, ses imports, son répertoire de travail et ses entrées modifiables.

## Énumérer les planifications

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Les crontabs système incluent généralement un champ utilisateur ; celui d’un utilisateur n’en comporte pas. Vérifiez le PATH et l’environnement effectifs du scheduler réel. `run-parts --test /etc/cron.daily` indique quels noms de fichiers seraient sélectionnés sur cet hôte. Les caractères de contrôle peuvent masquer une entrée dans une sortie ordinaire ; utilisez donc `cat -A` ou `sed -n l` lorsqu’une planification semble suspecte.

## Tracer la résolution des fichiers et des commandes avec privilèges

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Examinez les chaînes de scripts modifiables, les chemins `EnvironmentFile=`, les drop-ins, les liens symboliques, les commandes relatives, l’expansion des wildcards et les binaires copiés ou exécutés par une tâche privilégiée. Un timer peut activer un service portant un autre nom via son paramètre `Unit=`. Les pages [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) et [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) expliquent les primitives principales.

Pour un script `chkrootkit` planifié et exécuté par root, examinez le code source installé afin de repérer l’ancien [défaut de guillemets dans slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) : après une vérification d’un chemin temporaire `SLAPPER_FILES`, une instruction non protégée par des guillemets `file_port=$file_port $i` peut exécuter ce fichier. Vérifiez le script réel ou le correctif du fournisseur, la planification par root, les droits d’écriture d’un utilisateur moins privilégié sur le chemin temporaire exact, son statut exécutable et la politique de montage. Une chaîne de version ou la simple présence de `chkrootkit` ne suffit pas à établir ce chemin ; ne créez ni n’exécutez de fichier temporaire lors d’un examen passif.

Suivez un saut d’unité supplémentaire lorsqu’un service root lancé par un timer exécute `systemctl restart <other>.service` : l’unité redémarrée peut invoquer un shell avec un script modifiable par un utilisateur moins privilégié. Vérifiez les paramètres effectifs `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, les arguments exacts de `ExecStart=` et les permissions du script et de son répertoire parent. Un script modifiable n’est qu’une piste tant que le timer et le service redémarré ne sont pas actifs dans ce contexte d’exécution ; examinez les propriétés des unités sans redémarrer l’un ou l’autre service.

Si une tâche exécutée avec des privilèges supérieurs récupère un script par nom d’hôte et transmet la réponse à un shell, vérifiez qui contrôle la résolution de ce nom d’hôte, ainsi que le script distant. Un fichier `/etc/hosts` modifiable, y compris via les droits accordés à un groupe ou une ACL, peut rediriger un nom que la tâche résout localement ; une réponse `curl` ne devient un chemin d’exécution inter-utilisateurs que si la commande planifiée l’exécute réellement et que la tâche utilise le chemin de résolution concerné. Vérifiez l’identité d’exécution de la tâche, l’URL exacte et le pipeline shell, le comportement effectif du proxy/DNS et les permissions du fichier et de son répertoire parent. Un fichier hosts modifiable est à lui seul un indice à examiner, pas la preuve qu’un consommateur privilégié existe. Examinez la planification et les métadonnées sans modifier la correspondance ni récupérer le script pendant l’énumération.

Un `wget` privilégié planifié représente une frontière d’écriture de fichier distincte, même si le contenu téléchargé n’est jamais exécuté directement. [GNU Wget 1.18 a modifié le comportement par défaut du nom de fichier lors d’une redirection HTTP vers FTP pour corriger CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html) ; les anciennes versions concernées pouvaient utiliser le nom de fichier de la redirection FTP, tandis que `--trust-server-names` demande explicitement ce comportement. Si une partie moins fiable contrôle la réponse HTTP et la ressource FTP, vérifiez si la tâche suit cette redirection, la version effective de Wget ou le correctif rétroporté du fournisseur, les options de sortie, l’identité d’exécution, le répertoire de travail et la possibilité que le nom de destination devienne un fichier de démarrage. [Wget charge `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), et [ses paramètres peuvent sélectionner une source POST ou un chemin de sortie](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html) ; une récupération privilégiée ultérieure est une condition préalable distincte à toute divulgation ou écriture qui en résulterait. L’accès à un port bas via `authbind` n’est pertinent que si l’appelant peut réellement servir l’URL demandée par la tâche. Examinez la configuration et les journaux passivement, sans servir de redirection ni lancer la tâche. [L’accès brut aux périphériques bloc via le groupe `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) est indépendant de ce chemin de récupération réseau.

Suivez aussi les fichiers de données, pas seulement les scripts. Un outil de simulation ou d’orchestration planifié peut lire un fichier YAML qui définit les processus à lancer ; si un utilisateur moins privilégié peut modifier ce fichier et que la tâche l’exécute sous un autre compte, les données peuvent devenir des commandes exécutées avec l’identité de la tâche. Vérifiez la commande planifiée exacte, l’utilisateur effectif, le chemin du fichier, la sémantique de l’analyseur et les droits d’écriture (y compris sur les répertoires parents) avant de considérer un fichier YAML modifiable comme un chemin d’exécution. La lecture de la planification et des métadonnées du fichier suffit au triage passif ; ne lancez pas la tâche et ne modifiez pas son entrée pendant l’énumération.

La configuration d’un client SSH constitue également une entrée exécutable lorsqu’une tâche exécutée avec des privilèges supérieurs lance `ssh -F` avec un fichier qu’un utilisateur moins privilégié peut remplacer. Le [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) d’OpenSSH exécute une commande locale via le shell du client, tandis que `Host`/`Match` et les options antérieures déterminent si cette directive s’applique. Avant de conclure à un chemin d’exécution inter-utilisateurs, établissez la commande SSH planifiée exacte, l’identité d’exécution, le chemin de configuration sélectionné, les droits d’écriture sur le fichier et son répertoire, ainsi que l’ordre effectif des options. Examinez ces éléments sans lancer la tâche ni charger la configuration non fiable sous l’identité privilégiée.

Une commande `scp` planifiée, suivie de `ssh` pour exécuter le script copié, nécessite un examen distinct de la frontière de confiance si un utilisateur moins privilégié contrôle le service SSH de destination. Si ce service peut rediriger la connexion vers un autre hôte, le client privilégié peut s’authentifier auprès d’un point de terminaison inattendu ; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) affaiblit la protection contre les clés d’hôte modifiées, sous réserve des autres restrictions d’OpenSSH et des options effectives par hôte. Établissez l’identité d’exécution de la tâche, la destination réelle et la méthode d’authentification, l’identité effective de la commande distante, ainsi que la présence ou l’accès en écriture au même chemin de destination sur l’hôte redirigé. L’exécution d’un ancien fichier ou d’un fichier contrôlé par un attaquant nécessite en outre que la copie échoue ou ne trouve pas ce chemin **et** que le wrapper poursuive avec sa commande SSH ; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) et la gestion explicite du statut influent sur ce flux. Un paramètre de clé d’hôte faible, un processus `sshpass` visible ou un répertoire temporaire modifiable ne suffit pas à établir cette chaîne. Examinez la planification, le script, la configuration SSH et les métadonnées des fichiers sans rediriger le service ni déclencher la tâche pendant l’énumération.

Un ordonnanceur d’application privilégié peut tirer ses tâches de lignes de base de données plutôt que de fichiers modifiables. Par exemple, une entrée cron root qui lance [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) de Laravel peut appeler du code applicatif qui lit des lignes de tâches. Si un compte moins privilégié peut écrire une ligne contenant un chemin local, et que le callback planifié appelle [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) de PHP sous root puis envoie le contenu récupéré à un webhook spécifié par la ligne, il s’agit d’un chemin de divulgation de fichiers privilégié. Vérifiez l’identité cron, le callback réel de l’ordonnanceur et le flux des données de la ligne vers le chemin, les autorisations d’écriture dans la base de données, la validation après lecture de la ligne et la destination sortante. Un fichier `.env` d’application lisible n’est qu’une piste concernant des identifiants ; la validation d’un formulaire web ou un mot de passe de base de données ne prouve pas à lui seul le contrôle des lignes ou une divulgation. Examinez passivement la planification, le code et les permissions des fichiers d’identifiants, sans interroger la base de données ni planifier une tâche pendant l’énumération.

Les tâches `incron` déclenchées par des événements méritent le même examen : les [entrées incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associent un chemin surveillé et un événement à une commande exécutée avec l’identité du propriétaire de la table. Un utilisateur moins privilégié peut influencer indirectement un fichier surveillé lorsqu’une application suit un lien depuis un répertoire modifiable et écrit du texte contrôlé par un attaquant dans la cible surveillée. Vérifiez le propriétaire réel de la table, l’événement, les permissions de la cible et de ses répertoires parents, le comportement de l’application vis-à-vis des liens et la façon dont ce texte devient des arguments de commande. En particulier, [GNU Mailutils `mail` accepte `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), et sa [commande d’échappement vers le shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) peut lancer un programme ; un champ non fiable transmis comme option séparée à cette implémentation peut aboutir à une exécution de commande. D’autres implémentations de `mail` ou une séparation des arguments fixe et protégée par des guillemets peuvent se comporter différemment. Examinez la planification, le code de l’application et les métadonnées des fichiers sans modifier le fichier surveillé ni déclencher la tâche pendant l’énumération.

Un journal surveillé peut également franchir la frontière entre utilisateurs via un script auxiliaire. Si un compte moins privilégié peut écrire dans le journal et que le propriétaire d’`incron` en lit un champ pour l’insérer dans une nouvelle chaîne de commande [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), le shell analyse à nouveau ce champ avec l’identité du propriétaire. Vérifiez l’événement surveillé exact, les permissions du journal et de ses répertoires parents, le chemin de l’auxiliaire, la transformation du champ du journal et si la commande résultante est exécutée. La présence d’un journal modifiable et d’une entrée `incron` ne suffit pas à établir le flux de données ; n’écrivez pas de ligne déclencheuse et ne lancez pas l’auxiliaire pendant un examen passif.

Les tâches de renouvellement de certificats peuvent franchir la même frontière. Un auxiliaire privilégié peut lire le sujet X.509 d’un certificat situé dans un répertoire modifiable par un utilisateur moins privilégié et insérer son nom commun dans une nouvelle chaîne de commande `bash -c`. [OpenSSL peut afficher le sujet d’un certificat et vérifier sa date d’expiration](https://docs.openssl.org/3.3/man1/openssl-x509/) ; [Bash analyse la chaîne `-c` comme une entrée shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), donc protéger la variable par des guillemets dans le script externe ne protège pas la seconde analyse. Confirmez l’identité planifiée, le chemin d’entrée exact et les droits d’écriture, la branche de renouvellement et le flux des données vers `bash -c` avant de conclure à une injection de commandes. Examinez le script et les métadonnées du certificat passivement ; ne déclenchez pas le renouvellement pendant l’énumération.

La même seconde analyse peut se produire lorsqu’une tâche privilégiée planifiée extrait un nom de l’archive ou du paquet d’un utilisateur moins privilégié et le transmet à `xargs -I` pour l’insérer dans une chaîne de commande `sh -c`. [GNU `xargs -I` remplace le paramètre fictif dans les arguments initiaux](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), et [`sh -c` interprète sa chaîne de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Même si le script externe protège le nom extrait par des guillemets, cela ne rend pas sûr un programme shell substitué ultérieurement. Vérifiez l’identité d’exécution de la tâche, le chemin d’entrée exact accepté et ses droits d’écriture, la validation de l’archive et les conditions de branchement, ainsi que le flux du nom vers le shell. Un répertoire de téléversement modifiable ou un appel à `xargs` n’est qu’une piste ; examinez la planification, le script et les métadonnées des chemins sans soumettre de paquet ni lancer la tâche pendant l’énumération.

Un importateur de polices ou d’images planifié peut également faire confiance aux noms *à l’intérieur* d’une archive fournie par un appelant, même si le nom de fichier externe du téléversement est restreint. FontForge a corrigé l’injection de commandes via les noms de membres d’archives dans sa [modification en amont pour CVE-2024-25081 et CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Vérifiez qu’une tâche exécutée avec des privilèges supérieurs ouvre réellement une archive depuis un chemin modifiable par un utilisateur moins privilégié, son identité d’exécution, la version exacte de FontForge ou le correctif rétroporté du fournisseur, ainsi que le chemin de traitement de l’archive. Une chaîne de version ou une extension de téléversement autorisée ne prouve pas à elle seule l’exécution. Examinez la planification, les permissions du chemin et les métadonnées de build sans importer d’archive non fiable pendant l’énumération.

Les scanners réseau planifiés peuvent franchir une autre frontière lorsqu’un script personnalisé traite le sujet d’un certificat TLS distant comme nom de fichier local. [Nmap NSE exécute les scripts sélectionnés sans sandbox](https://nmap.org/book/nse-usage.html) ; examinez donc le script réel et vérifiez s’il concatène un champ de sujet non fiable à un répertoire de données sans contrôle de confinement. La divulgation de fichiers exige une cible que l’ordonnanceur analysera, un chemin qui se résout en un fichier lisible par l’identité d’exécution du scanner et un rapport ou journal remis à un lecteur moins privilégié. Un champ de certificat ou la présence d’un scanner installé ne prouve pas cette chaîne ; examinez la planification, le script, la résolution du chemin et la destination du rapport sans analyser de nouvelle cible pendant un examen passif.

Une commande cron privilégiée qui transmet un glob shell tel que `/path/to/tasks/*.yml` à un exécuteur Ansible mérite une vérification des permissions du répertoire, même si tous les playbooks existants sont en lecture seule. Un utilisateur disposant des droits d’écriture et de recherche dans le répertoire visé par le glob peut éventuellement créer un autre playbook correspondant. [Les playbooks Ansible définissent les tâches exécutées par le runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mais un wrapper personnalisé peut filtrer les chemins ou utiliser une autre identité : vérifiez son comportement, l’utilisateur cron réel, l’expansion du shell, les ACL, le sticky bit et la politique de montage avant de considérer le répertoire comme un chemin d’exécution. Examinez les métadonnées et le wrapper de façon statique ; ne lancez pas la tâche planifiée pendant l’énumération.

Un wrapper cron privilégié peut transmettre à un auxiliaire Perl des noms de fichiers d’un répertoire de téléversement après expansion d’un glob. L’opérateur [`<>` de Perl utilise `open` à deux arguments](https://perldoc.perl.org/perlop#The-Null-Filehandle) ; un nom correspondant interprété comme commande de pipe peut donc s’exécuter avec l’identité de l’auxiliaire, tandis que [`<<>>` traite les arguments comme des noms de fichier littéraux](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirmez l’identité de l’ordonnanceur, le répertoire de travail et le glob du wrapper, la façon dont l’auxiliaire traite réellement `@ARGV`, les restrictions sur les noms de fichiers et la possibilité pour un utilisateur moins privilégié de placer un nom correspondant via les droits du système de fichiers ou un service de téléversement authentifié. Une ligne cron, un script Perl ou un répertoire FTP modifiable ne prouve pas à lui seul la chaîne complète. Examinez le code source et les métadonnées sans soumettre de nom de fichier conçu à cet effet ni lancer la tâche pendant l’énumération.

Un script cron en lecture seule peut tout de même être remplacé si le compte planificateur l’exécute par son chemin et si l’utilisateur moins privilégié peut écrire dans son répertoire parent non sticky et le traverser. Vérifiez l’identité d’exécution définie par la planification, chaque composant du chemin, le sticky bit du répertoire, les ACL et la politique de montage ; examinez les métadonnées sans déplacer le fichier ni lancer la tâche.

Un wrapper PHP cron privilégié peut atteindre un auxiliaire qui n’existe pas encore. S’il appelle [`exec()`](https://www.php.net/manual/en/function.exec.php) de PHP avec un chemin absolu fixe vers l’auxiliaire, un utilisateur moins privilégié qui peut créer ce nom dans le répertoire parent peut contrôler ce qu’exécutera une exécution ultérieure. Confirmez que l’entrée cron lance réellement le wrapper avec l’identité supérieure, la chaîne de commande exacte et la politique d’exécution de PHP, les droits d’écriture et de recherche sur le répertoire de l’auxiliaire, le comportement des liens symboliques et du sticky bit, ainsi que l’absence actuelle de l’auxiliaire. Un répertoire modifiable ou un auxiliaire manquant n’est qu’une piste ; examinez la planification, le code source et les métadonnées du chemin sans créer l’auxiliaire ni déclencher la tâche.

Une tâche planifiée peut aussi rechercher des scripts d’entrée avec `find` et les transmettre à un interpréteur. Par exemple, la fonction `system()` de [gnuplot invoque un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf) ; une tâche privilégiée qui exécute `gnuplot` sur chaque fichier `*.plt` d’un répertoire modifiable par un utilisateur moins privilégié peut donc exécuter des commandes avec l’identité de la tâche. [Le droit de lecture d’un répertoire contrôle son listage, tandis que les droits d’écriture et de recherche (`x`) contrôlent la création et l’accès aux noms connus](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html) ; vérifiez les droits d’écriture et de recherche même si `ls` ne peut pas lister le répertoire. Mettez en relation l’identité et la commande exactes de l’ordonnanceur, le comportement de l’interpréteur, le motif de fichier sélectionné et les permissions du répertoire ; un répertoire modifiable ou un interpréteur installé ne suffit pas à établir une élévation de privilèges. Les tâches planifiées privées et de courte durée peuvent nécessiter une observation autorisée des événements, car un instantané unique des processus peut les manquer.

Pour une tâche PHP privilégiée, examinez les instructions littérales `include`/`require` dans le cadre de la chaîne de scripts exécutables. [PHP évalue les fichiers inclus](https://www.php.net/manual/en/function.include.php) ; un fichier `.php` modifiable par un groupe peut donc exécuter du code avec l’identité de la tâche, même si le script principal est en lecture seule. Vérifiez l’identité planifiée, la résolution effective du chemin d’inclusion, les permissions du fichier et du répertoire, et si la tâche s’exécute réellement ; un exemple de ligne cron dans un commentaire n’est qu’un indice. Le même examen s’applique à un [serveur intégré PHP](https://www.php.net/commandline.webserver) appartenant à root et lancé avec `-S` et `-t <document-root>` : même une écoute en loopback peut exécuter le code PHP de l’application pour les requêtes locales. Examinez le processus et le code source sans déclencher l’un ou l’autre mécanisme pendant l’énumération.

Une tâche PHP privilégiée peut aussi franchir la frontière via un **fichier de données** : si un utilisateur moins privilégié peut modifier le fichier exact transmis à [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP peut invoquer la méthode `__wakeup()` ou `__unserialize()` d’une classe chargée lors de la restauration d’un objet. Examinez l’identité effective de la tâche, les permissions du fichier et de ses répertoires parents, les classes chargées et les effets secondaires réels des méthodes, par exemple l’écriture d’un fichier dont le chemin est choisi par une propriété. Un journal modifiable ou un appel à `unserialize()` ne prouve pas à lui seul l’existence d’un chemin exploitable. Examinez le code source et les métadonnées sans écrire d’entrée sérialisée ni lancer la tâche pendant l’énumération.

Une tâche cron root peut invoquer le **runner de pages CLI** d’une application PHP plutôt que le serveur web. Suivez le répertoire racine du document et l’URI sélectionnés par le runner jusqu’au véritable point d’entrée PHP ; si le compte du service web peut modifier ce point d’entrée, la requête CLI planifiée peut exécuter le code modifié en tant que root même si le runner et le wrapper cron sont en lecture seule. Confirmez l’identité de l’ordonnanceur, la résolution exacte URI-vers-fichier, les permissions effectives du fichier et de ses répertoires parents, ainsi que l’existence d’une vérification d’intégrité protégeant le point d’entrée lui-même. Examinez le code source et les métadonnées sans invoquer le runner ni modifier la page pendant l’énumération.

Un processus `ipython` lancé par une tâche planifiée ou un autre utilisateur depuis un répertoire de travail partagé mérite un examen des fichiers de démarrage. Les [notes de publication de sécurité d’IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) expliquent que les versions concernées recherchaient des profils et des fichiers de configuration dans le répertoire courant, y compris du code dans `profile_default/startup`, avant le correctif de CVE-2022-21699. Mettez en relation la version installée réelle ou le correctif du fournisseur, le répertoire de travail de la commande, l’identité du processus privilégié et la capacité de l’utilisateur moins privilégié à écrire dans le chemin de démarrage exact et à le parcourir. La présence d’`ipython`, d’un répertoire modifiable ou d’une chaîne de version ne prouve pas à elle seule qu’une autre identité chargera un fichier à cet emplacement. Examinez la planification et les métadonnées du chemin sans lancer l’interpréteur privilégié.

Pour un serveur PHP privilégié qui appelle des fonctions d’une extension native personnalisée, vérifiez le SAPI PHP du service, son `php.ini` effectif et les fichiers `.ini` analysés avant d’examiner l’extension. [PHP charge au démarrage les bibliothèques `extension` configurées](https://www.php.net/manual/en/ini.core.php), et [les SAPI CLI et web peuvent utiliser des fichiers de configuration différents](https://www.php.net/manual/en/configuration.file.php). Un formulaire de connexion accessible ou une écoute locale peut donc transmettre des chaînes contrôlées par l’utilisateur à du code compilé exécuté avec l’identité du service. Consignez `User=`, `ExecStart=`, le répertoire de travail, le chemin réel de l’extension et les arguments contrôlés par l’appelant ; la simple présence d’un `.so` ou d’un socket en loopback ne prouve pas l’existence d’une faille de corruption mémoire. Analysez séparément tout analyseur personnalisé, sans envoyer de sondes pendant l’énumération passive.

Lorsqu’un wrapper privilégié calcule le hash d’un script à partir de son chemin puis ouvre à nouveau ce chemin pour l’exécuter, le digest n’authentifie que l’objet lu lors de la première ouverture. Si un utilisateur moins privilégié peut remplacer l’entrée du répertoire du script entre ces deux ouvertures, la seconde exécution peut résoudre un autre objet, même si le fichier de script d’origine appartient à root. Un FIFO peut prolonger la phase de vérification, mais ce chemin dépend des droits modifiables sur les répertoires parents, des ouvertures réellement distinctes, de l’identité de l’ordonnanceur, des règles du sticky bit et du montage, ainsi que du timing. Examinez le wrapper et la sortie de `namei -l` comme piste passive ; un checksum réussi ne prouve pas à lui seul que le chemin ultérieur est protégé.

Une tâche de sauvegarde privilégiée peut également **divulguer** des données sans exécuter de commandes fournies par un attaquant. Vérifiez si un utilisateur moins privilégié peut créer un fichier de contrôle lu par la tâche, si celle-ci ouvre ensuite une source protégée telle que `/etc/shadow`, et si une URL choisie par l’attaquant ou une sortie lisible reçoit le résultat. Vérifiez ces trois éléments avant de conclure à un chemin de divulgation. Une commande shell fixe dans le même script ne transforme pas à elle seule ce fichier de contrôle en entrée d’injection shell. Examinez le script et les permissions des fichiers sans lancer la tâche ni déposer de fichier de contrôle pendant l’énumération.

Si une tâche privilégiée planifiée lance `curl -K FILE` ou `curl --config FILE`, [curl traite les options de ce fichier comme des arguments de ligne de commande](https://curl.se/docs/manpage.html). Un utilisateur moins privilégié qui contrôle le fichier exact au moment où curl le lit peut influencer l’URL demandée, l’entrée de fichier local ou le chemin de sortie. Confirmez l’identité effective de la tâche, les droits d’écriture sur le fichier et ses répertoires parents, le moment où une autre tâche remplace éventuellement le fichier et l’interaction entre les options de configuration et celles de la ligne de commande fixe avant d’affirmer qu’une lecture ou écriture protégée est possible. Un chemin de configuration modifiable ou un indicateur `-K` visible ne prouve pas à lui seul que les options choisies prennent effet ; examinez la planification et les métadonnées sans lancer la tâche ni récupérer d’URL pendant l’énumération passive.

Si une entrée cron invoque un script auxiliaire, examinez également son répertoire de travail et sa commande d’archivage. Un wildcard non protégé par des guillemets dans un répertoire modifiable par un autre utilisateur peut transformer les noms de fichiers en options d’archive ; les actions de point de contrôle de GNU tar en sont un exemple. Confirmez l’identité d’exécution planifiée, le répertoire d’entrée modifiable, l’archiveur et ses options exacts, ainsi que la présence de `--` pour terminer l’analyse des options avant de conclure à un chemin d’exécution inter-utilisateurs. Voir [comportement des wildcards et de tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Une divulgation distincte de fichiers de sauvegarde peut se produire lorsqu’un auxiliaire privilégié exécute `cd INPUT_DIR; tar ... *` sans vérifier si `cd` a réussi. Si un utilisateur moins privilégié peut supprimer ou remplacer `INPUT_DIR`, l’échec de `cd` peut laisser le shell dans son répertoire précédent, que la commande d’archivage suivante peut alors lire. Vérifiez le répertoire de travail initial de la tâche, l’existence d’un chemin d’échec réel de `cd`, la présence d’une sortie du script ou l’utilisation de `&&`, les options exactes de l’archiveur et la lisibilité de l’archive de sortie par l’utilisateur moins privilégié. Un répertoire d’entrée modifiable ou une archive lisible n’est qu’une piste ; examinez l’auxiliaire et les permissions du chemin sans modifier la tâche en cours.

Un exécutable planifié peut dissimuler un script shell sans supprimer sa frontière de confiance : [SHc](https://github.com/neurobin/shc) enveloppe le texte chiffré du script dans un binaire natif et l’exécute via un shell au moment de l’exécution. Un suffixe `.sh.x` ou un ELF opaque n’est qu’un indice à examiner. Pour évaluer une injection d’options via les noms de fichiers, établissez l’identité de l’ordonnanceur privilégié, le répertoire de travail et la commande réels de l’auxiliaire, la capacité de l’utilisateur moins privilégié à y créer des noms correspondants et le fait qu’un wildcard non protégé par des guillemets soit transmis à une commande telle que `rsync` sans délimiteur d’options. L’option remote-shell de [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) n’est pertinente que si ce chemin de commande précis est utilisé. Une visibilité restreinte de `/proc` ou l’échec du déchiffrement statique laisse la commande inconnue ; ne lancez pas l’auxiliaire privilégié uniquement pour l’identifier.

Le texte de la ligne de commande d’un processus constitue une autre entrée non fiable pour un auxiliaire privilégié. Un utilisateur moins privilégié peut choisir un titre de processus ou un `argv[0]` correspondant à `pgrep -f` ; un nom correspondant n’authentifie ni l’exécutable ni son propriétaire. Si un script exécuté par root capture ce texte, en remplace une partie par `apache2ctl`/`httpd` et exécute le résultat sans tableau d’arguments fixe, des options choisies par l’attaquant peuvent sélectionner un autre répertoire de configuration ou journal d’erreurs. L’analyse de la configuration Apache peut charger des modules ou atteindre des auxiliaires configurés ; ne validez donc pas une configuration non fiable en tant que root pendant l’énumération. Examinez le propriétaire de l’ordonnanceur, l’auxiliaire exact, l’identité du processus et le flux des données vers les arguments ; il s’agit d’une injection d’options/configuration, sauf si l’exécution de métacaractères shell est démontrée séparément.

Un analyseur exécuté par root qui transmet du texte non fiable à l’arithmétique Bash peut exécuter des substitutions présentes dans ce texte. Le [guide d’élévation de privilèges](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) donne un exemple détaillé. Vérifiez la source de l’entrée et la commande d’analyse avant de considérer toute expression arithmétique comme exploitable.

Pour une tâche privilégiée qui analyse un journal d’application, suivez les champs non fiables au-delà de la première analyse. Un compte moins privilégié peut pouvoir écrire dans le journal via son groupe de processus actuel ou influencer les champs de requête consignés ; un enregistrement peut alors sélectionner une image dont les métadonnées deviennent un second chemin utilisé pour ouvrir du XML. Vérifiez l’identité effective de la tâche, les droits réels d’écriture dans le journal, le traitement des délimiteurs, le confinement du chemin canonique et le caractère contrôlé ou non du XML sélectionné par l’attaquant. L’expansion d’entités externes peut entraîner la divulgation de fichiers privilégiés si le résultat de l’expansion est transmis à une sortie lisible par un utilisateur moins privilégié. Le [guide de sécurité du traitement XML Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) décrit les contrôles d’accès aux DTD/entités externes ; examinez l’analyseur installé et ses paramètres effectifs. Un journal ou un fichier XML modifiable n’est qu’une piste. Examinez le code et les métadonnées sans transmettre d’entrée à l’analyseur planifié pendant l’énumération.

Examinez également les tâches privilégiées qui matérialisent des fichiers à partir du dépôt Git d’un autre utilisateur. Un script peut utiliser `git ls-tree` et `git cat-file` plutôt que `git checkout`, tout en faisant confiance aux chemins d’arborescence contrôlés par l’attaquant lorsqu’il les concatène au répertoire de staging. Les chemins absolus et les composants `..` peuvent sortir de ce répertoire, sauf si la destination est normalisée et que son confinement est vérifié avant l’écriture. `git -c safe.directory=*` permet d’accéder à des dépôts dont le propriétaire est différent ; cela ne crée pas à lui seul une possibilité d’écriture arbitraire.

Une sauvegarde de base de données exécutée par root peut créer une autre frontière de propriété. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copie les fichiers ordinaires supplémentaires placés dans le répertoire de données source, et son format plain par défaut écrit les fichiers dans `-D` sous forme d’arborescence de répertoires. Si un utilisateur moins privilégié peut créer ou modifier ces fichiers source, examinez le propriétaire et le mode de la destination résultante, vérifiez si son chemin peut être parcouru et exécuté, et si le montage comporte `nosuid`. Une copie appartenant à root et conservant les permissions set-ID peut être dangereuse ; une sauvegarde uniquement en tar, des permissions supprimées ou une destination inaccessible n’établissent pas le même chemin. Suivez le wrapper planifié et l’utilisateur effectif avant de considérer la commande de sauvegarde comme un problème avéré.

## Observer les tâches de courte durée

Un instantané unique des processus peut manquer une tâche qui ne dure que quelques millisecondes. Comparez les déclarations des timers/cron aux journaux et, lorsque cela est autorisé, surveillez les événements de processus avec des outils tels que `pspy` ou audit. Mettez en relation le propriétaire de la tâche planifiée, la ligne de commande exacte et les fichiers lus ou écrits par la tâche. Une interface web d’ordonnanceur en loopback constitue une interface distincte ; voir l’[exemple de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
