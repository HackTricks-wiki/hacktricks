# Tarefas Cron e Timers do Systemd

{{#include ../../banners/hacktricks-training.md}}

Tarefas agendadas podem ser executadas com uma identidade e um ambiente diferentes dos do shell atual. Enumere cron, `at`, anacron e timers do systemd; em seguida, rastreie cada comando agendado passando por seus scripts, imports, diretório de trabalho e entradas graváveis.

## Enumerar agendamentos

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Os crontabs do sistema geralmente incluem um campo de usuário; o crontab de um usuário, não. Inspecione o PATH efetivo e o ambiente do scheduler real. `run-parts --test /etc/cron.daily` mostra quais nomes de arquivo seriam selecionados nesse host. Caracteres de controle podem ocultar uma entrada na saída casual; portanto, use `cat -A` ou `sed -n l` quando um agendamento parecer suspeito.

## Rastreie a resolução de arquivos e comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revise cadeias de scripts graváveis, caminhos `EnvironmentFile=`, drop-ins, symlinks, comandos relativos, expansão de curingas e binários copiados ou executados por uma tarefa privilegiada. Um timer pode ativar um serviço com outro nome por meio da configuração `Unit=`. As páginas sobre [PATH](../linux-basics/linux-environment-variables.md#path), [curingas](../interesting-files-permissions/wildcards-spare-tricks.md) e [links de arquivos](../main-system-information/filesystem-links-and-file-descriptors.md) explicam as principais primitivas.

Para um script `chkrootkit` agendado para execução como root, inspecione o código-fonte instalado em busca do antigo [defeito de aspas no loop slapper (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): uma atribuição sem aspas `file_port=$file_port $i`, após uma verificação de um caminho temporário `SLAPPER_FILES`, pode executar esse arquivo. Verifique o script real ou o patch do fornecedor, o agendamento como root, o acesso de escrita de um usuário com privilégios inferiores ao caminho temporário exato, se ele é executável e a política de montagem. Uma string de versão ou a mera presença de `chkrootkit` não comprova que o caminho existe; não crie nem execute um arquivo temporário durante uma revisão passiva.

Rastreie mais um salto entre unidades quando o serviço de um timer executado como root roda `systemctl restart <other>.service`: a unidade reiniciada pode invocar um shell com um script gravável por um usuário com menos privilégios. Confirme o `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, os argumentos exatos de `ExecStart=` e as permissões do script e do caminho até ele. Um script gravável é apenas um candidato até que o timer e o serviço reiniciado estejam ativos nesse contexto de execução; inspecione as propriedades das unidades sem reiniciar nenhum dos serviços.

Se uma tarefa com privilégios superiores busca um script por nome de host e envia a resposta a um shell, verifique quem controla a resolução desse nome, além do script remoto. Um arquivo `/etc/hosts` gravável, inclusive por permissões concedidas por grupo ou ACL, pode redirecionar um nome que a tarefa resolve localmente; uma resposta de `curl` só se torna um caminho de execução entre usuários quando o comando agendado realmente executa essa resposta e a tarefa usa o caminho de resolução afetado. Verifique a identidade de execução da tarefa, a URL e o pipeline de shell exatos, o comportamento efetivo de proxy/DNS e as permissões do arquivo e do diretório pai. Um arquivo hosts gravável, por si só, é um indício para revisão, não prova de que exista um consumidor privilegiado. Inspecione o agendamento e os metadados sem alterar o mapeamento nem buscar o script durante a enumeração.

Uma busca agendada com `wget` privilegiado é uma fronteira separada de escrita em arquivo, mesmo que o corpo baixado nunca seja executado diretamente. [O GNU Wget 1.18 alterou o tratamento padrão do nome de arquivo em redirecionamentos HTTP para FTP para corrigir o CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); versões afetadas mais antigas podiam usar o nome de arquivo do FTP de destino, enquanto `--trust-server-names` solicita esse comportamento explicitamente. Se uma parte com menos confiança controla a resposta HTTP e o recurso FTP, verifique se a tarefa segue esse redirecionamento, a versão real do Wget ou um backport do fornecedor, as opções de saída, a identidade de execução, o diretório de trabalho e se o nome de arquivo de destino pode se tornar um arquivo de inicialização. [O Wget carrega `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), e [suas configurações podem selecionar uma origem POST ou um caminho de saída](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); uma busca privilegiada posterior é um pré-requisito distinto para qualquer divulgação ou escrita resultante. O acesso a uma porta baixa por meio de `authbind` só é relevante quando quem chama pode realmente servir a URL solicitada pela tarefa. Revise a configuração e os logs passivamente, sem servir um redirecionamento nem executar a tarefa. O [acesso bruto a dispositivos de bloco pelo grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) é independente desse caminho de busca pela rede.

Rastreie arquivos de dados, assim como scripts. Uma ferramenta agendada de simulação ou orquestração pode ler um arquivo YAML que define processos a iniciar; se um usuário com menos privilégios puder editar esse arquivo e a tarefa executá-lo sob outra conta, os dados podem se tornar comandos executados com a identidade da tarefa. Verifique o comando agendado exato, o usuário efetivo, o caminho do arquivo, a semântica do parser e o acesso de escrita, inclusive nos diretórios pai, antes de tratar um arquivo YAML gravável como um caminho de execução. Para uma triagem passiva, basta ler o agendamento e os metadados do arquivo; não execute a tarefa nem modifique sua entrada durante a enumeração.

Uma configuração de cliente SSH também é uma entrada executável quando uma tarefa com privilégios superiores executa `ssh -F` com um arquivo que um usuário com menos privilégios pode substituir. O [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) do OpenSSH executa um comando local por meio do shell do cliente, enquanto `Host`/`Match` e as opções anteriores determinam se essa diretiva se aplica. Correlacione a invocação SSH agendada exata, a identidade de execução, o caminho de configuração selecionado, as permissões de escrita no diretório e no arquivo e a ordem efetiva das opções antes de classificá-la como um caminho de execução entre usuários. Revise esses registros sem executar a tarefa nem carregar a configuração não confiável como a conta privilegiada.

Uma tarefa agendada que executa `scp` e depois `ssh` para rodar o script copiado exige uma segunda revisão da fronteira de confiança quando um usuário com menos privilégios controla o serviço SSH de destino. Se esse serviço puder encaminhar a conexão para outro host, o cliente privilegiado poderá se autenticar em um endpoint não pretendido; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) enfraquece a proteção contra alterações na chave do host, sujeito às restrições restantes do OpenSSH e às opções efetivas por host. Determine a identidade de execução da tarefa, o destino real e o método de autenticação, a identidade efetiva do comando remoto e se o mesmo caminho de destino é gravável ou já existe no host para o qual a conexão foi redirecionada. Executar um arquivo antigo ou controlado por um atacante também exige que a cópia falhe ou não encontre esse caminho **e** que o wrapper continue até o comando SSH; o [`errexit` do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e o tratamento explícito de status afetam esse fluxo. Uma configuração de chave de host fraca, um processo `sshpass` visível ou um diretório temporário gravável, isoladamente, não comprovam essa cadeia. Inspecione o agendamento, o script, a configuração SSH e os metadados dos arquivos sem redirecionar o serviço nem disparar a tarefa durante a enumeração.

Um scheduler de aplicações privilegiado pode obter as tarefas de linhas no banco de dados em vez de arquivos graváveis. Por exemplo, uma entrada do cron como root que invoca o [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) do Laravel pode chegar a código da aplicação que lê linhas de tarefas. Se uma conta com menos privilégios puder gravar uma linha contendo um caminho local, e o callback agendado chamar o [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) do PHP como root e enviar o corpo retornado a um webhook selecionado pela linha, isso será um caminho privilegiado de divulgação de arquivos. Verifique a identidade do cron, o callback real do scheduler e o fluxo de dados da linha até o caminho, as permissões de escrita no banco de dados, a validação após a leitura da linha e o destino de saída. Um `.env` da aplicação legível é apenas uma pista de credenciais; validação de formulário web ou uma senha de banco de dados, por si só, não comprovam controle da linha nem divulgação. Inspecione passivamente o agendamento, o código e as permissões do arquivo de credenciais, sem consultar o banco de dados nem agendar uma tarefa durante a enumeração.

Tarefas orientadas a eventos do `incron` merecem a mesma revisão: [entradas do incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associam um caminho monitorado e um evento a um comando executado com a identidade do proprietário da tabela. Um usuário com menos privilégios pode influenciar indiretamente um arquivo monitorado quando uma aplicação segue um link a partir de um diretório gravável e grava texto controlado pelo atacante no destino monitorado. Verifique o proprietário real da tabela, o evento, o destino e as permissões dos diretórios ancestrais, o comportamento da aplicação ao seguir links e como esse texto se transforma em argumentos do comando. Em particular, o [`mail` do GNU Mailutils aceita `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), e seu [comando de escape para o shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) pode executar um programa; um campo não confiável passado como opção separada a essa implementação pode resultar em execução de comandos. Outras implementações de `mail` ou uma fronteira fixa de argumentos entre aspas podem se comportar de outra forma. Inspecione o agendamento, o código da aplicação e os metadados dos arquivos sem modificar o arquivo monitorado nem disparar a tarefa durante a enumeração.

Um log monitorado também pode cruzar a fronteira entre usuários por meio de um script auxiliar. Se uma conta com menos privilégios puder gravar no log e o proprietário do `incron` ler um campo dele para inseri-lo em uma nova [string de comando `sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), o shell analisará esse campo novamente com a identidade do proprietário. Verifique o evento monitorado exato, as permissões do log e dos diretórios pai, o caminho do auxiliar, a transformação do campo do log e se o comando resultante é alcançado. A existência de um log gravável e de uma entrada `incron`, por si só, não comprova o fluxo de dados; não escreva uma linha de acionamento nem execute o auxiliar durante a enumeração passiva.

Tarefas de renovação de certificados podem cruzar a mesma fronteira. Um auxiliar privilegiado pode ler um assunto X.509 de um certificado em um diretório gravável por um usuário com menos privilégios e inserir seu nome comum em uma nova string de comando `bash -c`. [O OpenSSL pode exibir o assunto de um certificado e verificar seu vencimento](https://docs.openssl.org/3.3/man1/openssl-x509/); [o Bash analisa a string `-c` como entrada de shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), portanto, colocar a variável entre aspas no script externo não protege a segunda análise. Confirme a identidade agendada, o caminho de entrada exato e os direitos de escrita, o ramo de renovação e o fluxo de dados até `bash -c` antes de classificar isso como injeção de comandos. Inspecione passivamente o script e os metadados do certificado; não acione a renovação durante a enumeração.

A mesma segunda análise pode ocorrer quando uma tarefa privilegiada agendada extrai um nome de um arquivo compactado ou pacote de um usuário com menos privilégios e o envia a `xargs -I` para inseri-lo em uma string de comando `sh -c`. O [`xargs -I` do GNU substitui o marcador de posição nos argumentos iniciais](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), e [`sh -c` interpreta sua string de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Mesmo que o script externo coloque o nome extraído entre aspas, isso não torna seguro um programa de shell substituído posteriormente. Verifique a identidade de execução da tarefa, o caminho de entrada aceito exato e o acesso de escrita, a validação do arquivo compactado e as condições do ramo, além do fluxo do nome até o shell. Um diretório de upload gravável ou uma invocação de `xargs`, isoladamente, é apenas uma pista; inspecione o agendamento, o script e os metadados do caminho sem enviar um pacote nem executar a tarefa durante a enumeração.

Um importador agendado de fontes ou imagens também pode confiar em nomes *dentro* de um arquivo compactado fornecido pelo usuário, mesmo quando o nome externo do arquivo enviado é restrito. O FontForge corrigiu a injeção de comandos por nomes de membros de arquivos compactados na [alteração upstream para CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirme que uma tarefa com privilégios superiores realmente abre um arquivo compactado em um caminho gravável por um usuário com menos privilégios, sua identidade de execução, a versão exata do FontForge ou um backport do fornecedor e o caminho de tratamento do arquivo compactado. Uma string de versão ou um sufixo de upload permitido não comprovam execução. Inspecione o agendamento, as permissões do caminho e os metadados da versão sem importar um arquivo compactado não confiável durante a enumeração.

Scanners de rede agendados podem cruzar outra fronteira quando um script personalizado trata o assunto de um certificado TLS remoto como um nome de arquivo local. [O Nmap NSE executa scripts selecionados sem sandbox](https://nmap.org/book/nse-usage.html); portanto, inspecione o script real e verifique se ele concatena um campo de assunto não confiável a um diretório de dados sem checagens de contenção. A divulgação de arquivos exige um alvo que o scheduler vá escanear, um caminho que resolva para um arquivo legível pela identidade de execução do scanner e um relatório ou log entregue a um leitor com menos privilégios. Um campo de certificado ou a mera instalação de um scanner não comprova essa cadeia; revise o agendamento, o script, a resolução do caminho e o destino do relatório sem escanear um novo alvo durante uma enumeração passiva.

Um comando de cron privilegiado que passa um curinga de shell, como `/path/to/tasks/*.yml`, a um executor do Ansible merece uma verificação das permissões do diretório, mesmo quando todos os playbooks existentes são somente de leitura. Um usuário com acesso de escrita e busca ao diretório abrangido pelo curinga pode conseguir criar outro playbook correspondente. [Playbooks do Ansible definem tarefas executadas pelo executor](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mas um wrapper personalizado pode filtrar caminhos ou usar outra identidade: verifique seu comportamento, o usuário real do cron, a expansão do shell, as ACLs, o sticky bit e a política de montagem antes de tratar o diretório como um caminho de execução. Inspecione os metadados e o wrapper estaticamente; não execute a tarefa agendada durante a enumeração.

Um wrapper de cron privilegiado pode passar nomes de arquivos de um diretório de upload a um auxiliar Perl após expandir um curinga. O operador diamante [`<>` do Perl usa `open` de dois argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), portanto, um nome de arquivo correspondente interpretado como comando de pipe pode ser executado com a identidade do auxiliar; [`<<>>` trata os argumentos como nomes de arquivos literais](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirme a identidade do scheduler, o diretório de trabalho e o curinga do wrapper, o tratamento real de `@ARGV` pelo auxiliar, as restrições de nomes de arquivo e se uma identidade com menos privilégios pode inserir um nome correspondente por meio de permissões do sistema de arquivos ou de um serviço de upload autenticado. Uma linha de cron, um script Perl ou um diretório FTP gravável, isoladamente, não comprova a cadeia completa. Inspecione o código-fonte e os metadados sem enviar um nome de arquivo preparado nem executar a tarefa durante a enumeração.

Um script de cron somente de leitura ainda pode ser substituído se a conta agendada o executar pelo caminho e um usuário com menos privilégios puder escrever e atravessar seu diretório pai não sticky. Verifique a identidade de execução do agendamento, cada componente do caminho, o sticky bit do diretório, as ACLs e a política de montagem; revise os metadados sem mover o arquivo nem executar a tarefa.

Um wrapper PHP de cron privilegiado pode alcançar um auxiliar que ainda não existe. Se ele chamar [`exec()`](https://www.php.net/manual/en/function.exec.php) do PHP com um caminho absoluto fixo para o auxiliar, um usuário com menos privilégios que possa criar esse nome no diretório pai poderá controlar o que uma execução posterior executará. Confirme se a entrada do cron realmente executa o wrapper com a identidade superior, a string de comando exata e a política de execução do PHP, os direitos de escrita e busca no diretório do auxiliar, o comportamento de symlinks e do sticky bit e se o caminho do auxiliar continua ausente. Um diretório gravável ou um auxiliar ausente, isoladamente, é apenas uma pista; inspecione o agendamento, o código-fonte e os metadados do caminho sem criar o auxiliar nem disparar a tarefa.

Uma tarefa agendada também pode localizar scripts de entrada com `find` e passá-los a um interpretador. Por exemplo, a função `system()` do [gnuplot invoca um shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf); assim, uma tarefa privilegiada que executa `gnuplot` em todos os arquivos `*.plt` no diretório gravável de um usuário com menos privilégios pode executar comandos com a identidade da tarefa. [A permissão de leitura do diretório controla a listagem, enquanto escrita e busca (`x`) controlam a criação e o acesso a nomes conhecidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); verifique o acesso de escrita e busca mesmo quando `ls` não consegue listar o diretório. Correlacione a identidade e o comando exatos do scheduler, o comportamento do interpretador, o padrão de arquivos selecionados e as permissões do diretório; um diretório gravável ou a instalação de um interpretador, isoladamente, não comprovam escalonamento de privilégios. Agendamentos privados e tarefas de curta duração podem exigir observação autorizada de eventos, pois uma única captura de processos pode não detectá-los.

Para uma tarefa PHP privilegiada, inspecione instruções literais `include`/`require` como parte da cadeia de scripts executáveis. [O PHP avalia os arquivos incluídos](https://www.php.net/manual/en/function.include.php); portanto, um arquivo `.php` gravável pelo grupo incluído pode executar código com a identidade da tarefa, mesmo que o script principal seja somente de leitura. Verifique a identidade agendada, a resolução efetiva do caminho de inclusão, as permissões do arquivo e do diretório e se a tarefa realmente é executada; uma linha de cron de exemplo em um comentário é apenas uma pista. A mesma revisão se aplica a um [servidor integrado do PHP](https://www.php.net/commandline.webserver) pertencente ao root, iniciado com `-S` e `-t <document-root>`: um listener de loopback ainda pode executar PHP da aplicação para requisições locais. Inspecione o processo e o código-fonte sem acionar nenhum dos gatilhos durante a enumeração.

Uma tarefa PHP privilegiada também pode cruzar a fronteira por meio de um **arquivo de dados**: se um usuário com menos privilégios puder alterar o arquivo exato passado a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), o PHP poderá invocar o método `__wakeup()` ou `__unserialize()` de uma classe carregada ao restaurar um objeto. Revise a identidade efetiva da tarefa, as permissões do arquivo e dos diretórios ancestrais, as classes carregadas e os efeitos reais do método, como uma gravação em arquivo selecionada por uma propriedade. Um log gravável ou uma chamada a `unserialize()`, isoladamente, não comprova a existência de um caminho utilizável. Inspecione o código-fonte e os metadados sem gravar entrada serializada nem executar a tarefa durante a enumeração.

Uma tarefa de cron como root pode invocar o **executor de páginas CLI** de uma aplicação PHP em vez do servidor web. Rastreie o document root e o URI selecionados pelo executor até o ponto de entrada PHP real; se esse ponto de entrada for gravável pela conta do serviço web, a requisição CLI agendada poderá executar seu código alterado como root, mesmo que o executor e o wrapper do cron sejam somente de leitura. Confirme a identidade do scheduler, a resolução exata de URI para arquivo, as permissões efetivas do arquivo e dos diretórios ancestrais e se uma verificação de integridade protege o próprio ponto de entrada. Inspecione o código-fonte e os metadados sem invocar o executor nem alterar a página durante a enumeração.

Um processo `ipython` iniciado por uma tarefa agendada ou por outro usuário a partir de um diretório compartilhado merece uma revisão dos arquivos de inicialização. As [notas de segurança do IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explicam que versões afetadas buscavam perfis e configurações no diretório atual, inclusive código em `profile_default/startup`, antes da correção do CVE-2022-21699. Correlacione a versão realmente instalada ou o patch do fornecedor, o diretório de trabalho do comando, a identidade do processo com privilégios superiores e a capacidade do usuário com menos privilégios de escrever e buscar no caminho exato de inicialização. A instalação do `ipython`, um diretório gravável ou uma string de versão, isoladamente, não comprovam que outra identidade carregará um arquivo dali. Inspecione o agendamento e os metadados do caminho sem iniciar o interpretador com privilégios superiores.

Para um servidor PHP privilegiado que chama funções de uma extensão nativa personalizada, rastreie o SAPI do PHP do serviço, o `php.ini` efetivo e os arquivos `.ini` incluídos antes de revisar a extensão. [O PHP carrega as bibliotecas `extension` configuradas na inicialização](https://www.php.net/manual/en/ini.core.php), e [os SAPIs CLI e web podem usar arquivos de configuração diferentes](https://www.php.net/manual/en/configuration.file.php). Portanto, um formulário de login acessível ou um listener local pode passar strings controladas pelo usuário a código compilado executado com a identidade do serviço. Registre o `User=`, `ExecStart=`, o diretório de trabalho da unidade, o caminho real da extensão e os argumentos controlados pelo chamador; a mera presença de um `.so` ou de um socket de loopback não comprova uma falha de corrupção de memória. Analise qualquer parser personalizado separadamente, em vez de enviar sondagens durante a enumeração passiva.

Quando um wrapper privilegiado calcula o hash de um script pelo caminho e depois abre novamente esse caminho para executá-lo, o digest autentica apenas o objeto lido na primeira abertura. Se um usuário com menos privilégios puder substituir a entrada do diretório do script entre essas duas aberturas, a execução posterior poderá resolver para outro objeto, mesmo que o arquivo original do script pertença ao root. Um FIFO pode prolongar a fase de verificação, mas o caminho depende de permissões substituíveis no diretório pai, de aberturas realmente separadas, da identidade do scheduler, das regras de sticky bit e de montagem e do timing. Inspecione o wrapper e a saída de `namei -l` como uma pista passiva; um checksum bem-sucedido, por si só, não prova que o caminho posterior esteja protegido.

Uma tarefa de backup privilegiada também pode **divulgar** dados sem executar comandos fornecidos pelo atacante. Rastreie se um usuário com menos privilégios pode criar um arquivo de controle lido pela tarefa, se a tarefa depois abre uma fonte protegida, como `/etc/shadow`, e se uma URL selecionada pelo atacante ou uma saída legível recebe o resultado. Verifique as três partes antes de classificar o caso como caminho de divulgação. Um comando de shell fixo no mesmo script não transforma, por si só, esse arquivo de controle em uma entrada de injeção de shell. Inspecione o script e as permissões dos arquivos sem executar a tarefa nem criar um arquivo de controle durante a enumeração.

Se uma tarefa privilegiada agendada executar `curl -K FILE` ou `curl --config FILE`, [o curl trata as opções desse arquivo como argumentos de linha de comando](https://curl.se/docs/manpage.html). Um usuário com menos privilégios que controle o arquivo exato quando o curl o ler poderá influenciar a URL solicitada, a entrada de arquivo local ou o caminho de saída. Confirme a identidade efetiva da tarefa, os direitos de escrita no arquivo e nos diretórios ancestrais, o momento em que outra tarefa substitui o arquivo e como as opções de configuração interagem com as opções fixas da linha de comando antes de afirmar que há leitura ou escrita de dados protegidos. Um caminho de configuração gravável ou uma flag `-K` visível, isoladamente, não comprovam que as opções escolhidas surtirão efeito; inspecione o agendamento e os metadados sem executar a tarefa nem buscar uma URL durante a enumeração passiva.

Se uma entrada de cron invocar um script auxiliar, inspecione também o diretório de trabalho do auxiliar e o comando de arquivamento. Um curinga sem aspas em um diretório gravável por outro usuário pode transformar nomes de arquivos em opções do arquivador; as ações de checkpoint do GNU tar são um exemplo. Confirme a identidade de execução agendada, o diretório de entrada gravável, o arquivador e as opções exatos e se `--` encerra a análise de opções antes de afirmar que há um caminho de execução entre usuários. Consulte o comportamento de [curingas e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Uma divulgação separada de arquivos de backup pode ocorrer quando um auxiliar privilegiado executa `cd INPUT_DIR; tar ... *` sem verificar se `cd` teve êxito. Se um usuário com menos privilégios puder remover ou substituir `INPUT_DIR`, uma falha de `cd` poderá deixar o shell no diretório anterior, que o comando de arquivamento subsequente poderá ler. Verifique o diretório de trabalho inicial da tarefa, um caminho real de falha de `cd`, se o script encerra ou usa `&&`, as opções exatas do arquivador e se o arquivo compactado de saída pode ser lido pelo usuário com menos privilégios. Um diretório de entrada gravável ou um arquivo compactado legível, isoladamente, é apenas uma pista; inspecione o auxiliar e as permissões do caminho sem alterar a tarefa em execução.

Um executável agendado pode ocultar um script de shell sem eliminar sua fronteira de confiança: o [SHc](https://github.com/neurobin/shc) encapsula texto de script criptografado em um binário nativo e o executa por meio de um shell em tempo de execução. Um sufixo `.sh.x` ou um ELF opaco é apenas uma pista para revisão. Para avaliar a injeção de opções por nomes de arquivo, determine a identidade do scheduler privilegiado, o diretório de trabalho e o comando reais do auxiliar, se um usuário com menos privilégios pode criar nomes correspondentes nesse diretório e se um curinga sem aspas alcança um comando como `rsync` sem uma separação de opções. A [opção de shell remoto do `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) só é relevante se esse caminho exato de comando for usado. Visibilidade restrita de `/proc` ou falha na descriptografia estática deixa o comando desconhecido; não execute o auxiliar privilegiado apenas para classificá-lo.

O texto da linha de comando de um processo é outra entrada não confiável para um auxiliar privilegiado. Um usuário com menos privilégios pode escolher um título de processo ou `argv[0]` que corresponda a `pgrep -f`; um nome correspondente não autentica o executável nem seu proprietário. Se um script executado como root capturar esse texto, reescrever parte dele como `apache2ctl`/`httpd` e executar o resultado sem um array fixo de argumentos, opções escolhidas pelo atacante poderão selecionar outro diretório de configuração ou log de erros. A análise de configuração do Apache pode carregar módulos ou alcançar auxiliares configurados; portanto, não valide uma configuração não confiável como root durante a enumeração. Inspecione o proprietário do scheduler, o auxiliar exato, a identidade do processo e o fluxo de dados até os argumentos; isso é injeção de opções/configuração, a menos que a execução de metacaracteres de shell seja demonstrada separadamente.

Um parser executado como root que alimenta texto não confiável à aritmética do Bash pode executar substituições nesse texto. O [guia de escalonamento de privilégios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) apresenta um exemplo explicado passo a passo. Confirme a origem da entrada e o comando de análise antes de tratar toda expressão aritmética como explorável.

Para uma tarefa privilegiada que analisa o log de uma aplicação, rastreie os campos não confiáveis além da primeira análise. Uma conta com menos privilégios pode conseguir gravar no log por meio do grupo de processos atual ou influenciar campos de requisições registrados; um registro pode então selecionar uma imagem, cujos metadados se tornam um segundo caminho usado para abrir XML. Verifique a identidade efetiva da tarefa, o acesso real de escrita no log, o tratamento de delimitadores, a contenção do caminho canônico e se o XML selecionado é controlado pelo atacante. A expansão de entidades externas pode transformar essa segunda leitura em divulgação privilegiada de arquivos se o resultado expandido chegar a uma saída legível por um usuário com menos privilégios. O [guia de segurança de processamento de XML em Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para acesso a DTDs/entidades externas; inspecione o parser instalado e suas configurações efetivas. Um log ou arquivo XML gravável, isoladamente, é apenas uma pista. Revise o código e os metadados sem alimentar o parser agendado durante a enumeração.

Inspecione também tarefas privilegiadas que materializam arquivos a partir do repositório Git de outro usuário. Um script pode usar `git ls-tree` e `git cat-file` em vez de `git checkout`, mas ainda confiar em caminhos de árvore controlados pelo atacante ao juntá-los a um diretório de staging. Caminhos absolutos e componentes `..` podem escapar desse diretório, a menos que o destino seja normalizado e verificado para garantir contenção antes da escrita. `git -c safe.directory=*` permite acesso a repositórios com outros proprietários; isso, por si só, não cria a condição de escrita arbitrária.

Um backup de banco de dados executado como root pode criar outra fronteira de propriedade. O PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia arquivos regulares adicionais colocados no diretório de dados de origem, e seu formato simples padrão grava arquivos em `-D` como uma árvore de diretórios. Se uma conta com menos privilégios puder criar ou modificar esses arquivos de origem, inspecione a propriedade e o modo do destino resultante, se o caminho pode ser percorrido e executado e se a montagem tem `nosuid`. Uma cópia pertencente ao root com permissões set-ID preservadas pode ser perigosa; um backup somente em tar, permissões removidas ou um destino inacessível não estabelece o mesmo caminho. Rastreie o wrapper agendado e o usuário efetivo antes de tratar o comando de backup como uma constatação.

## Observar tarefas de curta duração

Uma única captura de processos pode não detectar uma tarefa executada por milissegundos. Compare as declarações de timers/cron com os logs e, quando autorizado, use monitoramento de eventos de processo, como `pspy` ou audit. Correlacione o proprietário agendado, a linha de comando exata e os arquivos lidos ou gravados pela tarefa. Uma interface web de scheduler em loopback é uma interface separada; consulte o [exemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
