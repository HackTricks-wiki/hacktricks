# Job Cron e timer Systemd

{{#include ../../banners/hacktricks-training.md}}

Le attività pianificate possono essere eseguite con un'identità e un ambiente diversi da quelli della shell corrente. Esamina cron, `at`, anacron e i timer systemd, quindi analizza ogni comando pianificato seguendo i relativi script, import, directory di lavoro e input scrivibili.

## Esaminare le pianificazioni

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

I crontab di sistema di solito includono un campo utente; il crontab di un utente no. Esamina il PATH effettivo e l’ambiente dello scheduler reale. `run-parts --test /etc/cron.daily` mostra quali nomi di file verrebbero selezionati su quell’host. I caratteri di controllo possono nascondere una voce nell’output visualizzato normalmente: se una pianificazione sembra sospetta, usa `cat -A` o `sed -n l`.

## Traccia la risoluzione di file e comandi privilegiati

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Esamina le catene di script scrivibili, i percorsi `EnvironmentFile=`, i drop-in, i symlink, i comandi relativi, l'espansione dei wildcard e i binari copiati o eseguiti da un task privilegiato. Un timer può attivare un service con un nome diverso tramite l'impostazione `Unit=`. Le pagine [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) illustrano le primitive principali.

Per uno script `chkrootkit` pianificato ed eseguito come root, esamina il sorgente installato per verificare il vecchio [difetto di quoting slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): un'istruzione non quotata `file_port=$file_port $i` dopo un controllo di un percorso temporaneo `SLAPPER_FILES` può eseguire quel file. Verifica lo script effettivo o la patch del vendor, la pianificazione come root, l'accesso in scrittura dell'utente meno privilegiato al percorso temporaneo esatto, il suo stato eseguibile e le policy di mount. Una stringa di versione o la sola presenza di `chkrootkit` non dimostrano che il percorso sia percorribile; durante una verifica passiva, non creare né eseguire un file temporaneo.

Traccia un ulteriore passaggio tra unit quando il service root di un timer esegue `systemctl restart <other>.service`: l'unit riavviata potrebbe invocare una shell con uno script scrivibile da un utente meno privilegiato. Verifica `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, gli argomenti esatti di `ExecStart=` e i permessi dello script e del percorso della directory padre. Uno script scrivibile è solo un candidato finché il timer e il service riavviato non sono attivi in quel contesto di esecuzione; esamina le proprietà delle unit senza riavviare nessuno dei due service.

Se un job con privilegi più elevati scarica uno script tramite hostname e passa la risposta a una shell, verifica chi controlla la risoluzione di quell'hostname oltre allo script remoto. Un file `/etc/hosts` scrivibile, anche tramite permessi concessi a un gruppo o una ACL, può reindirizzare un nome che il job risolve localmente; una risposta di `curl` diventa un percorso di esecuzione tra utenti solo quando il comando pianificato effettivo esegue quella risposta e il job usa il percorso di risoluzione interessato. Verifica l'identità con cui viene eseguito il job, l'URL esatto e la pipeline verso la shell, il comportamento effettivo di proxy/DNS e i permessi del file e della directory padre. Un file hosts scrivibile da solo è un indizio da approfondire, non la prova che esista un consumer privilegiato. Durante l'enumerazione, esamina la pianificazione e i metadati senza modificare la mappatura né scaricare lo script.

Un download pianificato con `wget` privilegiato costituisce un confine di scrittura su file distinto, anche se il contenuto scaricato non viene mai eseguito direttamente. [GNU Wget 1.18 ha modificato la gestione predefinita del nome del file nei redirect HTTP-to-FTP per correggere CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); le versioni precedenti vulnerabili potevano usare il nome del file FTP di destinazione, mentre `--trust-server-names` richiede esplicitamente quel comportamento. Se una parte meno fidata controlla la risposta HTTP e la risorsa FTP, verifica se il job segue quel redirect, la versione effettiva di Wget o la patch del vendor, le opzioni di output, l'identità con cui viene eseguito, la directory di lavoro e se il nome del file di destinazione può diventare un file di avvio. [Wget carica `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), e [le sue impostazioni possono selezionare una sorgente POST o un percorso di output](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); un successivo download privilegiato è un prerequisito distinto per qualsiasi divulgazione o scrittura conseguente. L'accesso a una porta bassa tramite `authbind` è rilevante solo se il chiamante può effettivamente servire l'URL richiesto dal job. Esamina configurazione e log passivamente, senza servire un redirect né eseguire il job. [L'accesso raw ai block device tramite il gruppo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) è indipendente da questo percorso di download dalla rete.

Traccia anche i file di dati, non solo gli script. Un tool di simulazione o orchestrazione pianificato potrebbe leggere un file YAML che definisce i processi da avviare; se un utente meno privilegiato può modificare quel file e il job lo esegue con un altro account, i dati possono diventare comandi eseguiti con l'identità del job. Prima di considerare un file YAML scrivibile come un percorso di esecuzione, verifica il comando pianificato esatto, l'utente effettivo, il percorso del file, la semantica del parser e l'accesso in scrittura, incluse le directory padre. Per una verifica passiva è sufficiente leggere la pianificazione e i metadati del file; durante l'enumerazione, non eseguire il job né modificarne l'input.

Anche la configurazione di un client SSH è un input eseguibile quando un job con privilegi più elevati esegue `ssh -F` usando un file che un utente meno privilegiato può sostituire. `ProxyCommand` di OpenSSH [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) esegue un comando locale tramite la shell del client, mentre `Host`/`Match` e le opzioni precedenti determinano se quella direttiva si applica. Prima di considerarlo un percorso di esecuzione tra utenti, correla l'invocazione SSH pianificata esatta, l'identità con cui viene eseguita, il percorso della configurazione selezionata, i permessi di scrittura su directory e file e l'ordine effettivo delle opzioni. Esamina questi elementi senza eseguire il job né caricare la configurazione non fidata come account privilegiato.

Una sequenza pianificata di `scp` seguita da `ssh` per eseguire lo script copiato richiede un'ulteriore verifica del confine di fiducia se un utente meno privilegiato controlla il service SSH di destinazione. Se quel service può inoltrare la connessione a un altro host, il client privilegiato potrebbe autenticarsi a un endpoint imprevisto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) indebolisce la protezione contro la modifica della host key, nei limiti delle restrizioni restanti di OpenSSH e delle opzioni effettive per host. Determina l'identità con cui viene eseguito il job, la destinazione effettiva e il metodo di autenticazione, l'identità effettiva del comando remoto e se lo stesso percorso di destinazione è scrivibile o già esistente sull'host reindirizzato. L'esecuzione di un file precedente o controllato dall'attaccante richiede inoltre che la copia fallisca o non raggiunga quel percorso **e** che il wrapper prosegua con il comando SSH; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e la gestione esplicita dello stato di uscita influiscono su questo flusso. Un'impostazione debole per la host key, un processo `sshpass` visibile o una directory temporanea scrivibile non dimostrano da soli questa catena. Durante l'enumerazione, esamina la pianificazione, lo script, la configurazione SSH e i metadati dei file senza reindirizzare il service né attivare il job.

Uno scheduler applicativo privilegiato può ricavare i propri job da righe del database anziché da file scrivibili. Per esempio, una voce cron di root che invoca Laravel [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) può raggiungere codice applicativo che legge righe di task. Se un account meno privilegiato può scrivere una riga contenente un percorso locale e il callback pianificato invoca [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) di PHP come root e invia il contenuto restituito a un webhook selezionato dalla riga, si tratta di un percorso di divulgazione di file privilegiato. Verifica l'identità cron, il callback effettivo dello scheduler e il flusso di dati dalla riga al percorso, le autorizzazioni di scrittura sul database, la convalida eseguita dopo la lettura della riga e la destinazione in uscita. Un file `.env` applicativo leggibile è solo un indizio relativo alle credenziali; la convalida di un modulo web o una password del database, da soli, non dimostrano il controllo della riga né la divulgazione. Durante l'enumerazione, esamina passivamente la pianificazione, il codice e i permessi dei file delle credenziali senza interrogare il database né pianificare un task.

Anche i job `incron` basati su eventi richiedono la stessa verifica: le [voci incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associano un percorso monitorato e un evento a un comando eseguito con l'identità del proprietario della tabella. Un utente meno privilegiato potrebbe influenzare indirettamente un file monitorato se un'applicazione segue un link da una directory scrivibile e scrive testo controllato dall'attaccante nel file di destinazione monitorato. Verifica il proprietario effettivo della tabella, l'evento, i permessi del file di destinazione e delle directory antenate, il comportamento dell'applicazione rispetto ai link e il modo in cui quel testo diventa argomenti del comando. In particolare, [`mail` di GNU Mailutils accetta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html) e il suo [comando di escape verso la shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) può eseguire un programma; con quella specifica implementazione, un campo non fidato passato come opzione separata può portare all'esecuzione di comandi. Altre implementazioni di `mail` o un confine di argomenti fisso e quotato potrebbero comportarsi diversamente. Durante l'enumerazione, esamina la pianificazione, il codice applicativo e i metadati dei file senza modificare il file monitorato né attivare il job.

Un log monitorato può oltrepassare il confine tra utenti anche tramite uno script helper. Se un account meno privilegiato può scrivere nel log e il proprietario di `incron` legge un campo dal log e lo inserisce in una nuova stringa di comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), la shell analizza nuovamente quel campo con l'identità del proprietario. Verifica l'evento monitorato esatto, i permessi del log e delle directory padre, il percorso dell'helper, la trasformazione del campo del log e se il comando risultante viene effettivamente eseguito. La sola presenza di un log scrivibile e di una voce `incron` non dimostra il flusso di dati; durante un'enumerazione passiva, non scrivere una riga di trigger né eseguire l'helper.

Anche i job di rinnovo dei certificati possono oltrepassare lo stesso confine. Un helper privilegiato potrebbe leggere il subject X.509 da un certificato in una directory scrivibile da un utente meno privilegiato e inserire il common name in una nuova stringa di comando `bash -c`. [OpenSSL può visualizzare il subject di un certificato e verificarne la scadenza](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analizza la stringa `-c` come input della shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), quindi quotare la variabile nello script esterno non protegge dalla seconda analisi. Prima di considerarlo command injection, verifica l'identità pianificata, il percorso di input esatto e i relativi permessi di scrittura, il ramo di rinnovo e il flusso dei dati verso `bash -c`. Esamina lo script e i metadati del certificato passivamente; durante l'enumerazione, non attivare il rinnovo.

La stessa seconda analisi può verificarsi quando un job pianificato con privilegi estrae un nome dall'archivio o dal pacchetto di un utente meno privilegiato e lo passa a `xargs -I` affinché venga inserito in una stringa di comando `sh -c`. [GNU `xargs -I` sostituisce il segnaposto negli argomenti iniziali](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html) e [`sh -c` interpreta la stringa di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Anche se lo script esterno quota il nome estratto, ciò non rende sicuro un programma shell sostituito successivamente. Verifica l'identità con cui viene eseguito il job, il percorso di input esatto accettato e i relativi permessi di scrittura, la convalida dell'archivio e le condizioni dei rami, nonché il flusso dal nome alla shell. Una directory di upload scrivibile o la sola invocazione di `xargs` sono solo indizi; durante l'enumerazione, esamina la pianificazione, lo script e i metadati dei percorsi senza inviare un pacchetto né eseguire il job.

Anche un importatore pianificato di font o immagini può fidarsi dei nomi *contenuti* in un archivio fornito dal chiamante, anche se il nome esterno dell'upload è limitato. FontForge ha corretto la command injection tramite nomi dei membri dell'archivio nella sua [modifica upstream per CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Verifica che un job con privilegi più elevati apra effettivamente un archivio da un percorso scrivibile da un utente meno privilegiato, la sua identità di esecuzione, la versione esatta di FontForge o la patch del vendor e il percorso del codice che gestisce l'archivio. Una stringa di versione o una sola estensione di upload consentita non dimostrano l'esecuzione. Durante l'enumerazione, esamina la pianificazione, i permessi dei percorsi e i metadati della build senza importare un archivio non fidato.

Gli scanner di rete pianificati possono oltrepassare un confine diverso quando uno script personalizzato tratta il subject di un certificato TLS remoto come nome di file locale. [Nmap NSE esegue gli script selezionati senza sandbox](https://nmap.org/book/nse-usage.html), quindi esamina lo script effettivo e verifica se un campo subject non fidato viene unito a una directory dati senza controlli di contenimento. La divulgazione di file richiede un target che lo scheduler sottopone a scansione, un percorso che risolva in un file leggibile dall'identità con cui viene eseguito lo scanner e un report o log consegnato a un lettore meno privilegiato. Un campo del certificato o la sola presenza di uno scanner installato non dimostrano questa catena; durante un'enumerazione passiva, esamina la pianificazione, lo script, la risoluzione dei percorsi e la destinazione dei report senza sottoporre a scansione un nuovo target.

Un comando cron privilegiato che passa a un runner Ansible un glob shell come `/path/to/tasks/*.yml` richiede un controllo dei permessi della directory, anche se tutti i playbook esistenti sono di sola lettura. Un utente con permessi di scrittura e ricerca sulla directory interessata dal glob potrebbe creare un altro playbook corrispondente. [I playbook Ansible definiscono i task eseguiti dal runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), ma un wrapper personalizzato potrebbe filtrare i percorsi o usare un'identità diversa: prima di considerare la directory un percorso di esecuzione, verifica il suo comportamento, l'utente cron effettivo, l'espansione della shell, le ACL, lo sticky bit e la policy di mount. Esamina staticamente i metadati e il wrapper; durante l'enumerazione, non eseguire il job pianificato.

Un wrapper cron privilegiato può passare a un helper Perl i nomi di file di una directory di upload dopo aver espanso un glob. L'operatore [`<>` di Perl usa `open` con due argomenti](https://perldoc.perl.org/perlop#The-Null-Filehandle), quindi un nome corrispondente interpretato come comando tramite pipe può essere eseguito con l'identità dell'helper; [`<<>>` tratta gli argomenti come nomi di file letterali](https://perldoc.perl.org/perlop#The-Null-Filehandle). Verifica l'identità dello scheduler, la directory di lavoro del wrapper e il glob, la gestione effettiva di `@ARGV` da parte dell'helper, le restrizioni sui nomi dei file e se un'identità meno privilegiata può inserire un nome corrispondente tramite i permessi del filesystem o un servizio di upload autenticato. Una voce cron, uno script Perl o una directory FTP scrivibile, da soli, non dimostrano la catena completa. Durante l'enumerazione, esamina il sorgente e i metadati senza inviare un nome file appositamente creato né eseguire il job.

Uno script cron di sola lettura è comunque sostituibile se l'account pianificato lo esegue tramite pathname e l'utente meno privilegiato può scrivere nella directory padre non sticky e attraversarla. Verifica l'identità con cui viene eseguito il job, ogni componente del percorso, lo sticky bit della directory, le ACL e la policy di mount; esamina i metadati senza spostare il file né eseguire il job.

Un wrapper PHP cron privilegiato può raggiungere un helper che ancora non esiste. Se invoca [`exec()`](https://www.php.net/manual/en/function.exec.php) di PHP con il percorso assoluto fisso di un helper, un utente meno privilegiato che può creare quel nome nella directory padre può controllare ciò che verrà eseguito al successivo avvio. Verifica che la voce cron esegua effettivamente il wrapper con l'identità più privilegiata, la stringa di comando esatta e la policy di esecuzione PHP, i permessi di scrittura e ricerca sulla directory dell'helper, il comportamento di symlink e sticky bit e se il percorso dell'helper è ancora assente. Una directory scrivibile o un helper mancante, da soli, sono solo indizi; durante l'enumerazione, esamina la pianificazione, il sorgente e i metadati del percorso senza creare l'helper né attivare il job.

Un job pianificato potrebbe anche individuare script di input con `find` e passarli a un interprete. Per esempio, la funzione `system()` di [gnuplot invoca una shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), quindi un job privilegiato che esegue `gnuplot` su tutti i file `*.plt` in una directory scrivibile da un utente meno privilegiato può eseguire comandi con l'identità del job. [Il permesso di lettura della directory controlla l'elenco dei contenuti, mentre scrittura e ricerca (`x`) controllano la creazione e l'accesso a nomi noti](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); controlla i permessi di scrittura e ricerca anche quando `ls` non può elencare la directory. Metti in relazione l'identità effettiva dello scheduler e il comando esatto, il comportamento dell'interprete, il pattern di selezione dei file e i permessi della directory; una directory scrivibile o la presenza di un interprete installato, da sole, non dimostrano un'escalation. Pianificazioni private e job di breve durata potrebbero richiedere un'osservazione autorizzata degli eventi, poiché uno snapshot dei processi potrebbe non rilevarli.

Per un job PHP privilegiato, esamina le istruzioni letterali `include`/`require` come parte della catena di script eseguibili. [PHP valuta i file inclusi](https://www.php.net/manual/en/function.include.php), quindi un file `.php` scrivibile da un gruppo può eseguire codice con l'identità del job anche se lo script principale è di sola lettura. Verifica l'identità pianificata, la risoluzione effettiva dell'include path, i permessi di file e directory e se il job viene effettivamente eseguito; una riga cron d'esempio in un commento è solo un indizio. La stessa verifica si applica a un [server integrato PHP](https://www.php.net/commandline.webserver) di proprietà di root, avviato con `-S` e `-t <document-root>`: un listener loopback può comunque eseguire PHP applicativo per le richieste locali. Durante l'enumerazione, esamina il processo e il sorgente senza attivare nessuno dei due trigger.

Anche un job PHP privilegiato può oltrepassare il confine tramite un **file di dati**: se un utente meno privilegiato può modificare il file esatto passato a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), durante il ripristino dell'oggetto PHP potrebbe invocare il metodo `__wakeup()` o `__unserialize()` di una classe caricata. Esamina l'identità effettiva del job, i permessi del file e delle directory antenate, le classi caricate e gli effetti collaterali effettivi dei metodi, ad esempio una scrittura su file selezionata da una proprietà. Un log scrivibile o una chiamata a `unserialize()`, da soli, non dimostrano l'esistenza di un percorso utilizzabile. Durante l'enumerazione, esamina il sorgente e i metadati senza scrivere input serializzato né eseguire il job.

Un task cron di root potrebbe invocare un **runner di pagine CLI** di un'applicazione PHP anziché il server web. Traccia la document root e l'URI selezionati dal runner fino all'entrypoint PHP effettivo; se quell'entrypoint è scrivibile dall'account del web service, la richiesta CLI pianificata può eseguire come root il codice modificato, anche quando il runner e il wrapper cron sono di sola lettura. Verifica l'identità dello scheduler, la risoluzione esatta da URI a file, i permessi effettivi del file e delle directory antenate e se un controllo d'integrità protegge l'entrypoint stesso. Durante l'enumerazione, esamina il sorgente e i metadati senza invocare il runner né modificare la pagina.

Un processo `ipython` avviato da un job pianificato o da un altro utente da una directory di lavoro condivisa richiede di esaminare i file di avvio. Le [note di rilascio di sicurezza di IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) spiegano che le build interessate cercavano profili e configurazioni nella directory corrente, incluso codice in `profile_default/startup`, prima della correzione per CVE-2022-21699. Metti in relazione la build installata effettiva o la patch del vendor, la directory di lavoro del comando, l'identità del processo con privilegi più elevati e la possibilità per l'utente meno privilegiato di scrivere e cercare il percorso di avvio esatto. La presenza di `ipython`, una directory scrivibile o una stringa di versione, da sole, non dimostrano che un'altra identità caricherà un file da quel percorso. Durante l'enumerazione, esamina la pianificazione e i metadati del percorso senza avviare l'interprete con privilegi più elevati.

Per un server PHP privilegiato che chiama funzioni di un'estensione nativa personalizzata, prima di esaminare l'estensione, traccia il PHP SAPI del service, il suo `php.ini` effettivo e i file `.ini` scansionati. [PHP carica all'avvio le librerie `extension` configurate](https://www.php.net/manual/en/ini.core.php), e [CLI e i SAPI web possono usare file di configurazione diversi](https://www.php.net/manual/en/configuration.file.php). Un modulo di login raggiungibile o un listener locale può quindi passare stringhe controllate dall'utente a codice compilato eseguito con l'identità del service. Registra `User=`, `ExecStart=`, la directory di lavoro, il percorso effettivo dell'estensione e gli argomenti controllabili dal chiamante dell'unit; la semplice presenza di un `.so` o di un socket loopback non dimostra una vulnerabilità di memory corruption. Analizza separatamente qualsiasi parser personalizzato, invece di inviare probe durante un'enumerazione passiva.

Quando un wrapper privilegiato calcola l'hash di uno script tramite pathname e in seguito apre di nuovo quel pathname per eseguirlo, il digest autentica solo l'oggetto letto durante la prima apertura. Se un utente meno privilegiato può sostituire la voce della directory dello script tra le due aperture, l'esecuzione successiva potrebbe risolvere un oggetto diverso, anche quando il file originale è di proprietà di root. Una FIFO può allungare la fase di controllo, ma il percorso dipende dai permessi sostituibili della directory padre, dalle aperture separate effettive, dall'identità dello scheduler, dalle regole dello sticky bit e dei mount e dalla tempistica. Esamina il wrapper e l'output di `namei -l` come indizio passivo; un checksum valido non dimostra che il pathname usato in seguito sia protetto.

Un job di backup privilegiato può anche **divulgare** dati senza eseguire comandi forniti dall'attaccante. Traccia se un utente meno privilegiato può creare un file di controllo letto dal job, se il job apre poi una sorgente protetta come `/etc/shadow` e se un URL scelto dall'attaccante o un output leggibile riceve il risultato. Verifica tutti e tre gli elementi prima di considerarlo un percorso di divulgazione. Un comando shell fisso nello stesso script non trasforma di per sé quel file di controllo in un input di shell injection. Durante l'enumerazione, esamina lo script e i permessi dei file senza eseguire il job né introdurre un file di controllo.

Se un job pianificato con privilegi esegue `curl -K FILE` o `curl --config FILE`, [curl tratta le opzioni presenti in quel file come argomenti della riga di comando](https://curl.se/docs/manpage.html). Un utente meno privilegiato che controlla il file esatto quando curl lo legge potrebbe influenzare l'URL richiesto, l'input da un file locale o il percorso di output. Prima di affermare che è possibile leggere o scrivere dati protetti, verifica l'identità effettiva del job, i permessi di scrittura sul file e sulle directory antenate, la tempistica di eventuali altri job che sostituiscono il file e l'interazione tra le opzioni di configurazione e quelle fisse della riga di comando. Un percorso di configurazione scrivibile o un flag `-K` visibile, da soli, non dimostrano che le opzioni scelte abbiano effetto; durante un'enumerazione passiva, esamina la pianificazione e i metadati senza eseguire il job né scaricare un URL.

Se una voce cron invoca uno script helper, esamina anche la directory di lavoro dell'helper e il comando di archiviazione. Un wildcard non quotato su una directory scrivibile da un altro utente può trasformare i nomi dei file in opzioni dell'archiver; le azioni checkpoint di GNU tar ne sono un esempio. Prima di considerarlo un percorso di esecuzione tra utenti, verifica l'identità con cui viene eseguito il job, la directory di input scrivibile, l'archiver e le opzioni esatti e se `--` termina l'analisi delle opzioni. Vedi [comportamento di wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Una divulgazione distinta tramite file di backup può verificarsi quando un helper privilegiato esegue `cd INPUT_DIR; tar ... *` senza verificare se `cd` è riuscito. Se un utente meno privilegiato può rimuovere o sostituire `INPUT_DIR`, un `cd` fallito potrebbe lasciare la shell nella directory precedente, che il successivo comando di archiviazione potrebbe leggere. Verifica la directory di lavoro iniziale del job, l'esistenza di un percorso reale in cui `cd` fallisce, se lo script termina o usa `&&`, le opzioni esatte dell'archiver e se l'archivio di output è leggibile dall'utente meno privilegiato. Una directory di input scrivibile o un archivio leggibile, da soli, sono solo indizi; esamina l'helper e i permessi del percorso senza modificare il job attivo.

Un eseguibile pianificato potrebbe nascondere uno script shell anziché rimuovere il confine di fiducia: [SHc](https://github.com/neurobin/shc) racchiude testo di script cifrato in un binario nativo e lo esegue tramite una shell a runtime. Un suffisso `.sh.x` o un ELF opaco sono solo indizi da esaminare. Per valutare l'iniezione di opzioni tramite nomi di file, determina l'identità dello scheduler privilegiato, la directory di lavoro e il comando effettivi dell'helper, la possibilità per l'utente meno privilegiato di creare lì nomi corrispondenti e se un glob non quotato raggiunge un comando come `rsync` senza un separatore di opzioni. L'opzione remote-shell di [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) è rilevante solo se viene usato esattamente quel percorso di comando. Una visibilità limitata di `/proc` o una decifratura statica non riuscita lasciano ignoto il comando; non eseguire l'helper privilegiato solo per classificarlo.

Anche il testo della riga di comando di un processo è un input non fidato per un helper privilegiato. Un utente meno privilegiato può scegliere un titolo del processo o `argv[0]` che corrisponda a `pgrep -f`; un nome corrispondente non autentica l'eseguibile né il suo proprietario. Se uno script eseguito come root acquisisce quel testo, ne riscrive una parte in `apache2ctl`/`httpd` ed esegue il risultato senza un array di argomenti fisso, opzioni scelte dall'attaccante possono selezionare una directory di configurazione o un error log diversi. L'analisi della configurazione di Apache può caricare moduli o raggiungere helper configurati, quindi durante l'enumerazione non convalidare come root una configurazione non fidata. Esamina il proprietario dello scheduler, l'helper esatto, l'identità del processo e il flusso dai dati agli argomenti; si tratta di injection di opzioni/configurazione, a meno che non venga dimostrata separatamente l'esecuzione di metacaratteri shell.

Un parser eseguito come root che passa testo non fidato all'aritmetica di Bash può eseguire sostituzioni presenti in quel testo. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) presenta un esempio completo. Prima di considerare sfruttabile ogni espressione aritmetica, verifica la sorgente dell'input e il comando di parsing.

Per un job privilegiato che analizza un log applicativo, traccia i campi non fidati oltre la prima analisi. Un account meno privilegiato potrebbe riuscire a scrivere nel log tramite il proprio gruppo di processi corrente o influenzare i campi delle richieste registrate; un record può quindi selezionare un'immagine, i cui metadati diventano un secondo pathname usato per aprire XML. Verifica l'identità effettiva del job, l'effettivo accesso in scrittura al log, la gestione dei delimitatori, il contenimento del percorso canonico e se il file XML selezionato è controllabile dall'attaccante. L'espansione di entità esterne può trasformare questa seconda lettura in una divulgazione privilegiata di file se il risultato espanso raggiunge un output leggibile da un utente meno privilegiato. La [guida alla sicurezza dell'elaborazione XML Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta i controlli per l'accesso a DTD/entità esterne; esamina il parser installato e le sue impostazioni effettive. Un log o un file XML scrivibile, da soli, sono solo indizi. Durante l'enumerazione, esamina codice e metadati senza fornire input al parser pianificato.

Esamina anche i job privilegiati che materializzano file dal repository Git di un altro utente. Uno script potrebbe usare `git ls-tree` e `git cat-file` anziché `git checkout`, ma fidarsi comunque dei percorsi controllati dall'attaccante nell'albero quando li unisce a una directory di staging. I percorsi assoluti e i componenti `..` possono uscire da quella directory, a meno che la destinazione non venga normalizzata e verificata per accertarne il contenimento prima della scrittura. `git -c safe.directory=*` consente l'accesso a repository con proprietari diversi; da solo non crea la condizione di scrittura arbitraria.

Un backup di database eseguito come root può creare un ulteriore confine di proprietà. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia anche i file regolari aggiuntivi inseriti nella directory dei dati sorgente e, per impostazione predefinita, il formato plain scrive i file in `-D` come albero di directory. Se un account meno privilegiato può creare o modificare quei file sorgente, esamina la proprietà e la modalità della destinazione risultante, se il relativo percorso è attraversabile ed eseguibile e se il mount usa `nosuid`. Una copia di proprietà di root con permessi set-ID preservati può essere pericolosa; un backup solo tar, permessi rimossi o una destinazione inaccessibile non dimostrano lo stesso percorso. Prima di considerare il comando di backup un finding, traccia il wrapper pianificato e l'utente effettivo.

## Osservare i task di breve durata

Un singolo snapshot dei processi potrebbe non rilevare un job che viene eseguito per pochi millisecondi. Confronta le dichiarazioni di timer/cron con i log e, quando autorizzato, usa il monitoraggio degli eventi di processo, ad esempio `pspy` o audit. Metti in relazione il proprietario dello scheduler, la riga di comando esatta e i file letti o scritti dal task. Una web UI dello scheduler in ascolto su loopback è un'interfaccia distinta; vedi l'[esempio di Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
