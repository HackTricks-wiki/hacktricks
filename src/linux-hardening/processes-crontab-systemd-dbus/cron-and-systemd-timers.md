# Tarefas do Cron e Timers do systemd

{{#include ../../banners/hacktricks-training.md}}

Tarefas agendadas podem ser executadas com uma identidade e um ambiente diferentes dos do shell atual. Enumere cron, `at`, anacron e timers do systemd e, em seguida, rastreie cada comando agendado até seus scripts, imports, diretório de trabalho e entradas graváveis.

## Enumerar agendamentos

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Os crontabs do sistema geralmente incluem um campo de usuário; o crontab de um usuário não. Inspecione o PATH efetivo e o ambiente do scheduler real. `run-parts --test /etc/cron.daily` mostra quais nomes de arquivo seriam selecionados nesse host. Caracteres de controle podem ocultar uma entrada em uma saída casual, então use `cat -A` ou `sed -n l` quando uma programação parecer suspeita.

## Rastreie a resolução de arquivos e comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revise cadeias de scripts graváveis, caminhos `EnvironmentFile=`, drop-ins, symlinks, comandos relativos, expansão de curingas e binários copiados ou executados por uma tarefa privilegiada. Um timer pode ativar um serviço com outro nome por meio da configuração `Unit=`. As páginas [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explicam as principais primitivas.

Para um script agendado executado como root que roda `chkrootkit`, examine o código-fonte instalado para encontrar o antigo [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): um `file_port=$file_port $i` sem aspas após uma verificação de um caminho temporário `SLAPPER_FILES` pode executar esse arquivo. Verifique o script real ou o patch do fornecedor, o agendamento como root, o acesso de escrita de um usuário de menor privilégio ao caminho temporário exato, o status de execução do arquivo e a política de montagem. Uma string de versão ou a presença de `chkrootkit`, por si só, não comprova que o caminho existe; não crie nem execute um arquivo temporário durante uma revisão passiva.

Siga mais um salto entre units quando o serviço root de um timer executa `systemctl restart <other>.service`: a unit reiniciada pode invocar um shell com um script gravável por um usuário de menor privilégio. Confirme o `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, os argumentos exatos de `ExecStart=` e as permissões do script e do caminho pai. Um script gravável é apenas um candidato até que o timer e o serviço reiniciado estejam ativos nesse contexto de execução; inspecione as propriedades das units sem reiniciar nenhum dos serviços.

Se uma tarefa de maior privilégio obtiver um script por hostname e passar a resposta para um shell, verifique quem controla a resolução desse hostname, além do script remoto. Um arquivo `/etc/hosts` gravável, inclusive por acesso concedido via grupo ou ACL, pode redirecionar um nome que a tarefa resolve localmente; uma resposta de `curl` só se torna um caminho de execução entre usuários quando o comando agendado realmente executa essa resposta e a tarefa usa o caminho de resolução afetado. Verifique a identidade usada para executar a tarefa, a URL exata e o pipeline do shell, o comportamento efetivo de proxy/DNS e as permissões do arquivo e do diretório pai. Um arquivo hosts gravável, por si só, é um indício para revisão, não prova que existe um consumidor privilegiado. Inspecione o agendamento e os metadados sem alterar o mapeamento nem obter o script durante a enumeração.

Uma obtenção agendada de arquivos por `wget` privilegiado é um limite distinto de gravação de arquivo, mesmo que o corpo baixado nunca seja executado diretamente. [GNU Wget 1.18 alterou o tratamento padrão do nome de arquivo em redirecionamentos de HTTP para FTP, corrigindo CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); versões afetadas mais antigas podiam usar o nome do arquivo FTP de destino, enquanto `--trust-server-names` solicita esse comportamento explicitamente. Se uma parte de menor confiança controla a resposta HTTP e o recurso FTP, verifique se a tarefa segue esse redirecionamento, a versão real do Wget ou o backport do fornecedor, as opções de saída, a identidade usada para executar a tarefa, o diretório de trabalho e se o nome do arquivo de destino pode se tornar um arquivo de inicialização. [O Wget carrega `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), e [suas configurações podem selecionar uma origem POST ou um caminho de saída](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); uma obtenção privilegiada posterior é um requisito distinto para qualquer divulgação ou gravação resultante. O acesso a uma porta baixa por meio de `authbind` só é relevante quando o chamador pode realmente servir a URL solicitada pela tarefa. Revise a configuração e os logs passivamente, sem servir um redirecionamento nem executar a tarefa. [O acesso bruto a dispositivos de bloco pelo grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) é independente desse caminho de obtenção pela rede.

Rastreie arquivos de dados, assim como scripts. Uma ferramenta de simulação ou orquestração agendada pode ler um arquivo YAML que define os processos a iniciar; se um usuário de menor privilégio puder editar esse arquivo e a tarefa o executar sob outra conta, os dados podem se tornar comandos executados com a identidade da tarefa. Verifique o comando agendado exato, o usuário efetivo, o caminho do arquivo, a semântica do parser e o acesso de escrita (inclusive aos diretórios pais) antes de tratar um arquivo YAML gravável como um caminho de execução. Para uma triagem passiva, basta ler o agendamento e os metadados do arquivo; não execute a tarefa nem modifique sua entrada durante a enumeração.

A configuração de um cliente SSH também é uma entrada executável quando uma tarefa de maior privilégio executa `ssh -F` com um arquivo que um usuário de menor privilégio pode substituir. O [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) do OpenSSH executa um comando local por meio do shell do cliente, enquanto `Host`/`Match` e as opções anteriores determinam se essa diretiva se aplica. Correlacione a invocação SSH agendada exata, a identidade usada para executar a tarefa, o caminho de configuração selecionado, as permissões de escrita do diretório e do arquivo e a ordem efetiva das opções antes de classificá-la como um caminho de execução entre usuários. Revise esses registros sem executar a tarefa nem carregar a configuração não confiável como a conta privilegiada.

Um `scp` agendado seguido de `ssh` para executar o script copiado exige uma segunda revisão do limite de confiança quando um usuário de menor privilégio controla o serviço SSH de destino. Se esse serviço puder encaminhar a conexão a outro host, o cliente privilegiado poderá se autenticar em um endpoint não pretendido; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) enfraquece a proteção contra alterações da chave do host, sujeito às restrições restantes do OpenSSH e às opções efetivas por host. Determine a identidade usada para executar a tarefa, o destino real e o método de autenticação, a identidade efetiva do comando remoto e se o mesmo caminho de destino é gravável ou já existe no host para o qual a conexão foi redirecionada. A execução de um arquivo antigo ou controlado por um atacante também exige que a cópia falhe ou não encontre esse caminho **e** que o wrapper continue até o comando SSH; [`errexit` do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e o tratamento explícito do status afetam esse fluxo. Uma configuração fraca de chave de host, um processo `sshpass` visível ou um diretório temporário gravável, isoladamente, não comprovam essa cadeia. Inspecione o agendamento, o script, a configuração SSH e os metadados dos arquivos sem redirecionar o serviço nem acionar a tarefa durante a enumeração.

Um agendador de aplicações privilegiado pode obter suas tarefas de linhas de banco de dados, em vez de arquivos graváveis. Por exemplo, uma entrada do cron de root que invoca o [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) do Laravel pode alcançar código da aplicação que lê linhas de tarefas. Se uma conta de menor privilégio puder gravar uma linha contendo um caminho local, e o callback agendado chamar [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) do PHP como root e enviar o corpo retornado a um webhook escolhido pela linha, isso cria um caminho privilegiado de divulgação de arquivos. Verifique a identidade do cron, o callback real do agendador e o fluxo de dados da linha para o caminho, as permissões de gravação no banco de dados, a validação após a leitura da linha e o destino de saída. Um `.env` da aplicação legível é apenas uma pista sobre credenciais; a validação de um formulário web ou uma senha do banco de dados, por si só, não comprova o controle da linha nem a divulgação. Inspecione passivamente o agendamento, o código e as permissões do arquivo de credenciais, sem consultar o banco de dados nem agendar uma tarefa durante a enumeração.

Tarefas `incron` orientadas a eventos exigem a mesma revisão: [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associam um caminho monitorado e um evento a um comando executado com a identidade do proprietário da tabela. Um usuário de menor privilégio pode influenciar indiretamente um arquivo monitorado quando uma aplicação segue um link de um diretório gravável e grava texto controlado pelo atacante no destino monitorado. Verifique o proprietário real da tabela, o evento, as permissões do destino e dos diretórios ancestrais, o comportamento da aplicação ao seguir links e como esse texto se torna argumentos de comando. Em particular, o [`mail` do GNU Mailutils aceita `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), e seu [comando de escape para o shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) pode executar um programa; um campo não confiável passado como uma opção separada para essa implementação pode levar à execução de comandos. Outras implementações de `mail` ou um limite de argumentos fixo e entre aspas podem se comportar de forma diferente. Inspecione o agendamento, o código da aplicação e os metadados dos arquivos sem modificar o arquivo monitorado nem acionar a tarefa durante a enumeração.

Um log monitorado também pode atravessar um limite entre usuários por meio de um script auxiliar. Se uma conta de menor privilégio puder gravar no log e o proprietário do `incron` ler um campo dele e inseri-lo em uma nova string de comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), o shell analisará esse campo novamente com a identidade do proprietário. Verifique o evento monitorado exato, as permissões do log e do diretório pai, o caminho do auxiliar, a transformação do campo do log e se o comando resultante é alcançado. A existência de um log gravável e de uma entrada `incron`, por si só, não comprova o fluxo de dados; não escreva uma linha de acionamento nem execute o auxiliar durante uma enumeração passiva.

Tarefas de renovação de certificados podem atravessar o mesmo limite. Um auxiliar privilegiado pode ler um subject X.509 de um certificado em um diretório gravável por um usuário de menor privilégio e inserir seu common name em uma nova string de comando `bash -c`. [O OpenSSL pode exibir o subject de um certificado e verificar sua validade](https://docs.openssl.org/3.3/man1/openssl-x509/); [o Bash analisa a string `-c` como entrada do shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), portanto, colocar a variável entre aspas no script externo não protege contra a segunda análise. Confirme a identidade agendada, o caminho exato de entrada e as permissões de escrita, o ramo de renovação e o fluxo de dados até `bash -c` antes de classificá-lo como injeção de comandos. Inspecione o script e os metadados do certificado passivamente; não acione a renovação durante a enumeração.

A mesma segunda análise pode ocorrer quando uma tarefa privilegiada agendada extrai um nome de um arquivo compactado ou pacote de um usuário de menor privilégio e o envia a `xargs -I` para inseri-lo em uma string de comando `sh -c`. [O GNU `xargs -I` substitui o marcador nos argumentos iniciais](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), e [`sh -c` interpreta sua string de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Mesmo que o script externo coloque o nome extraído entre aspas, isso não torna seguro um programa de shell substituído posteriormente. Verifique a identidade usada para executar a tarefa, o caminho exato de entrada aceito e suas permissões de escrita, a validação do arquivo compactado e as condições do ramo, além do fluxo do nome até o shell. Um diretório de uploads gravável ou uma invocação de `xargs`, isoladamente, é apenas uma pista; inspecione o agendamento, o script e os metadados do caminho sem enviar um pacote nem executar a tarefa durante a enumeração.

Um importador agendado de fontes ou imagens também pode confiar em nomes *dentro* de um arquivo compactado fornecido por um chamador, mesmo quando o nome externo do upload é restrito. O FontForge corrigiu a injeção de comandos por nome de membro de arquivo compactado em sua [alteração upstream para CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirme que uma tarefa de maior privilégio realmente abre um arquivo compactado de um caminho gravável por um usuário de menor privilégio, a identidade usada para executar a tarefa, a versão exata do FontForge ou o backport do fornecedor e o caminho de código que trata o arquivo compactado. Uma string de versão ou uma extensão de upload permitida, por si só, não prova a execução. Inspecione o agendamento, as permissões do caminho e os metadados da versão sem importar um arquivo compactado não confiável durante a enumeração.

Scanners de rede agendados podem atravessar outro limite quando um script personalizado trata o subject de um certificado TLS remoto como um nome de arquivo local. [O Nmap NSE executa os scripts selecionados sem sandbox](https://nmap.org/book/nse-usage.html); portanto, inspecione o script real e verifique se ele junta um campo subject não confiável a um diretório de dados sem verificações de contenção. A divulgação de arquivos exige um alvo que o agendador vá escanear, um caminho que resolva para um arquivo legível pela identidade usada para executar o scanner e um relatório ou log entregue a um usuário de menor privilégio. Um campo de certificado ou um scanner instalado, por si só, não comprova essa cadeia; revise o agendamento, o script, a resolução do caminho e o destino do relatório sem escanear um novo alvo durante uma enumeração passiva.

Um comando privilegiado do cron que passa um glob do shell, como `/path/to/tasks/*.yml`, a um executor Ansible merece uma verificação das permissões do diretório, mesmo que todos os playbooks existentes sejam somente leitura. Um usuário com acesso de escrita e busca ao diretório abrangido pelo glob pode conseguir criar outro playbook correspondente. [Playbooks Ansible definem tarefas executadas pelo executor](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mas um wrapper personalizado pode filtrar caminhos ou usar outra identidade: verifique seu comportamento, o usuário real do cron, a expansão do shell, as ACLs, o sticky bit e a política de montagem antes de tratar o diretório como um caminho de execução. Inspecione estaticamente os metadados e o wrapper; não execute a tarefa agendada durante a enumeração.

Um wrapper privilegiado do cron pode passar nomes de arquivos de um diretório de uploads a um auxiliar Perl depois de expandir um glob. O operador diamante [`<>` do Perl usa `open` com dois argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), então um nome de arquivo correspondente interpretado como um comando em um pipe pode ser executado com a identidade do auxiliar; [`<<>>` trata os argumentos como nomes de arquivo literais](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirme a identidade do agendador, o diretório de trabalho do wrapper e o glob, o tratamento real de `@ARGV` pelo auxiliar, as restrições de nomes de arquivo e se uma identidade de menor privilégio pode inserir um nome correspondente por meio das permissões do sistema de arquivos ou de um serviço de upload autenticado. Uma linha do cron, um script Perl ou um diretório FTP gravável, isoladamente, não comprova a cadeia completa. Inspecione o código-fonte e os metadados sem enviar um nome de arquivo criado para esse fim nem executar a tarefa durante a enumeração.

Um script do cron somente leitura ainda pode ser substituído se a conta agendada o executar pelo caminho e o usuário de menor privilégio puder gravar no diretório pai não sticky e percorrê-lo. Verifique a identidade usada para executar a tarefa, cada componente do caminho, o sticky bit do diretório, as ACLs e a política de montagem; revise os metadados sem mover o arquivo nem executar a tarefa.

Um wrapper PHP privilegiado do cron pode chamar um auxiliar que ainda não existe. Se ele chamar [`exec()`](https://www.php.net/manual/en/function.exec.php) do PHP com um caminho absoluto fixo para o auxiliar, um usuário de menor privilégio que possa criar esse nome no diretório pai poderá controlar o que uma execução posterior executará. Confirme que a entrada do cron realmente executa o wrapper com a identidade de maior privilégio, a string de comando exata e a política de execução do PHP, as permissões de escrita e busca no diretório do auxiliar, o comportamento de symlinks e do sticky bit e se o caminho do auxiliar ainda está ausente. Um diretório gravável ou a ausência de um auxiliar, isoladamente, é apenas uma pista; inspecione o agendamento, o código-fonte e os metadados do caminho sem criar o auxiliar nem acionar a tarefa.

Uma tarefa agendada também pode localizar scripts de entrada com `find` e passá-los a um interpretador. Por exemplo, a função `system()` do [gnuplot invoca um shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf); portanto, uma tarefa privilegiada que executa `gnuplot` em cada arquivo `*.plt` de um diretório gravável por um usuário de menor privilégio pode executar comandos com a identidade da tarefa. [A permissão de leitura do diretório controla a listagem, enquanto a permissão de escrita e busca (`x`) controla a criação e o acesso a nomes conhecidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); verifique o acesso de escrita e busca mesmo quando `ls` não consegue listar o diretório. Correlacione a identidade e o comando exatos do agendador, o comportamento do interpretador, o padrão de arquivos selecionado e as permissões do diretório; um diretório gravável ou um interpretador instalado, por si só, não comprova elevação de privilégios. Agendamentos privados e tarefas de curta duração podem exigir observação autorizada de eventos, pois um único snapshot de processos pode não captá-los.

Para uma tarefa PHP privilegiada, inspecione as instruções literais `include`/`require` como parte da cadeia de scripts executáveis. [O PHP avalia os arquivos incluídos](https://www.php.net/manual/en/function.include.php); portanto, um arquivo `.php` gravável pelo grupo pode executar código com a identidade da tarefa, mesmo quando o script principal é somente leitura. Verifique a identidade agendada, a resolução efetiva do caminho de inclusão, as permissões do arquivo e do diretório e se a tarefa realmente é executada; uma linha de cron de exemplo em um comentário é apenas uma pista. A mesma revisão se aplica a um [servidor integrado do PHP](https://www.php.net/commandline.webserver) de propriedade do root iniciado com `-S` e `-t <document-root>`: mesmo um listener em loopback pode executar PHP da aplicação em solicitações locais. Inspecione o processo e o código-fonte sem acionar nenhum dos dois gatilhos durante a enumeração.

Uma tarefa PHP privilegiada também pode atravessar o limite por meio de um **arquivo de dados**: se um usuário de menor privilégio puder alterar o arquivo exato passado a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), o PHP poderá invocar o método `__wakeup()` ou `__unserialize()` de uma classe carregada ao restaurar um objeto. Revise a identidade efetiva da tarefa, as permissões do arquivo e dos diretórios ancestrais, as classes carregadas e os efeitos colaterais reais dos métodos, como uma gravação de arquivo selecionada por uma propriedade. Um log gravável ou uma chamada a `unserialize()`, por si só, não comprova a existência de um caminho utilizável. Inspecione o código-fonte e os metadados sem gravar dados serializados nem executar a tarefa durante a enumeração.

Uma tarefa root do cron pode invocar um **executor de páginas CLI** de uma aplicação PHP, em vez do servidor web. Rastreie a raiz de documentos e o URI selecionados pelo executor até o ponto de entrada PHP real; se esse ponto de entrada for gravável pela conta do serviço web, a solicitação CLI agendada poderá executar o código alterado como root, mesmo que o executor e o wrapper do cron sejam somente leitura. Confirme a identidade do agendador, a resolução exata do URI para o arquivo, as permissões efetivas do arquivo e dos diretórios ancestrais e se uma verificação de integridade protege o próprio ponto de entrada. Inspecione o código-fonte e os metadados sem invocar o executor nem alterar a página durante a enumeração.

Um processo `ipython` iniciado por uma tarefa agendada ou por outro usuário a partir de um diretório de trabalho compartilhado merece uma revisão dos arquivos de inicialização. As [notas de segurança do IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explicam que versões afetadas procuravam perfis e configurações no diretório atual, incluindo código em `profile_default/startup`, antes da correção de CVE-2022-21699. Correlacione a versão instalada real ou o patch do fornecedor, o diretório de trabalho do comando, a identidade do processo de maior privilégio e a capacidade do usuário de menor privilégio de gravar e buscar o caminho de inicialização exato. A presença do `ipython`, de um diretório gravável ou de uma string de versão, por si só, não prova que outra identidade carregará um arquivo ali. Inspecione o agendamento e os metadados do caminho sem iniciar o interpretador com privilégios elevados.

Para um servidor PHP privilegiado que chama funções de uma extensão nativa personalizada, rastreie o SAPI do PHP do serviço e o `php.ini` efetivo, além dos arquivos `.ini` carregados por ele, antes de revisar a extensão. [O PHP carrega as bibliotecas `extension` configuradas na inicialização](https://www.php.net/manual/en/ini.core.php), e [os SAPIs CLI e web podem usar arquivos de configuração diferentes](https://www.php.net/manual/en/configuration.file.php). Portanto, um formulário de login acessível ou um listener local pode passar strings controladas pelo usuário para código compilado executado com a identidade do serviço. Registre o `User=`, `ExecStart=`, diretório de trabalho, caminho real da extensão e argumentos controláveis pelo chamador na unit; a mera presença de um `.so` ou de um socket em loopback não comprova uma falha de corrupção de memória. Analise qualquer parser personalizado separadamente, em vez de enviar sondas durante uma enumeração passiva.

Quando um wrapper privilegiado calcula o hash de um script pelo caminho e depois abre novamente esse caminho para executá-lo, o digest autentica apenas o objeto lido na primeira abertura. Se um usuário de menor privilégio puder substituir a entrada do diretório do script entre as duas aberturas, a execução posterior poderá resolver para outro objeto, mesmo que o arquivo de script original pertença ao root. Um FIFO pode prolongar a fase de verificação, mas o caminho depende de permissões substituíveis nos diretórios pais, de aberturas realmente separadas, da identidade do agendador, das regras do sticky bit e da montagem, além do timing. Inspecione o wrapper e a saída de `namei -l` como uma pista passiva; um checksum bem-sucedido, por si só, não prova que o caminho usado posteriormente está protegido.

Uma tarefa de backup privilegiada também pode **divulgar** dados sem executar comandos fornecidos pelo atacante. Rastreie se um usuário de menor privilégio pode criar um arquivo de controle que a tarefa lê, se a tarefa então abre uma fonte protegida, como `/etc/shadow`, e se uma URL escolhida pelo atacante ou uma saída legível recebe o resultado. Verifique os três elementos antes de classificá-la como um caminho de divulgação. Um comando de shell fixo no mesmo script não transforma, por si só, esse arquivo de controle em uma entrada de injeção de shell. Inspecione o script e as permissões dos arquivos sem executar a tarefa nem colocar um arquivo de controle durante a enumeração.

Se uma tarefa privilegiada agendada executar `curl -K FILE` ou `curl --config FILE`, [o curl trata as opções desse arquivo como argumentos de linha de comando](https://curl.se/docs/manpage.html). Um usuário de menor privilégio que controle o arquivo exato quando o curl o lê pode influenciar a URL solicitada, a entrada de arquivo local ou o caminho de saída. Confirme a identidade efetiva da tarefa, as permissões de escrita do arquivo e dos diretórios ancestrais, o momento de qualquer outra tarefa que substitua o arquivo e como as opções de configuração interagem com as opções fixas da linha de comando antes de alegar leitura ou gravação de conteúdo protegido. Um caminho de configuração gravável ou uma flag `-K` visível, por si só, não prova que as opções escolhidas terão efeito; inspecione o agendamento e os metadados sem executar a tarefa nem obter uma URL durante a enumeração passiva.

Se uma entrada do cron invocar um script auxiliar, inspecione também o diretório de trabalho do auxiliar e o comando de arquivamento. Um curinga sem aspas em um diretório gravável por outro usuário pode transformar nomes de arquivos em opções do arquivador; as ações de checkpoint do GNU tar são um exemplo. Confirme a identidade usada para executar a tarefa, o diretório de entrada gravável, o arquivador e as opções exatos, e se `--` encerra a análise de opções antes de alegar a existência de um caminho de comando entre usuários. Consulte o comportamento de [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Uma divulgação separada de arquivos de backup pode ocorrer quando um auxiliar privilegiado executa `cd INPUT_DIR; tar ... *` sem verificar se `cd` teve sucesso. Se um usuário de menor privilégio puder remover ou substituir `INPUT_DIR`, um `cd` malsucedido pode deixar o shell no diretório anterior, que o comando de arquivamento seguinte poderá ler. Verifique o diretório de trabalho inicial da tarefa, a possibilidade real de falha de `cd`, se o script encerra ou usa `&&`, as opções exatas do arquivador e se o arquivo compactado de saída é legível pelo usuário de menor privilégio. Um diretório de entrada gravável ou um arquivo compactado legível, isoladamente, é apenas uma pista; inspecione o auxiliar e as permissões do caminho sem alterar a tarefa em execução.

Um executável agendado pode ocultar um script de shell em vez de eliminar seu limite de confiança: [SHc](https://github.com/neurobin/shc) envolve texto de script criptografado em um binário nativo e o executa por meio de um shell em tempo de execução. Um sufixo `.sh.x` ou um ELF opaco é apenas uma pista para revisão. Para avaliar a injeção de opções em nomes de arquivo, determine a identidade privilegiada do agendador, o diretório de trabalho e o comando reais do auxiliar, se um usuário de menor privilégio pode criar nomes correspondentes ali e se um glob sem aspas chega a um comando como `rsync` sem um limite de opções. A [`opção de remote-shell do `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) só é relevante se esse caminho de comando exato for usado. Visibilidade restrita de `/proc` ou falha na descriptografia estática deixa o comando desconhecido; não execute o auxiliar privilegiado só para classificá-lo.

O texto da linha de comando de um processo é outra entrada não confiável para um auxiliar privilegiado. Um usuário de menor privilégio pode escolher um título de processo ou `argv[0]` que corresponda a `pgrep -f`; um nome correspondente não autentica o executável nem seu proprietário. Se um script executado como root capturar esse texto, reescrever parte dele para `apache2ctl`/`httpd` e executar o resultado sem um array fixo de argumentos, opções escolhidas pelo atacante podem selecionar outro diretório de configuração ou log de erros. A análise da configuração do Apache pode carregar módulos ou alcançar auxiliares configurados; portanto, não valide uma configuração não confiável como root durante a enumeração. Inspecione o proprietário do agendamento, o auxiliar exato, a identidade do processo e o fluxo dos dados até os argumentos; isso é injeção de opções/configuração, a menos que a execução de metacaracteres do shell seja demonstrada separadamente.

Um parser executado como root que passa texto não confiável para a aritmética do Bash pode executar substituições nesse texto. O [guia de elevação de privilégios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) apresenta um exemplo detalhado. Confirme a origem da entrada e o comando de análise antes de considerar explorável toda expressão aritmética.

Para uma tarefa privilegiada que analisa um log de aplicação, rastreie os campos não confiáveis além da primeira análise. Uma conta de menor privilégio pode conseguir gravar no log por meio do grupo do processo atual ou influenciar campos de solicitações registrados; um registro pode então selecionar uma imagem, cujos metadados se tornam um segundo caminho usado para abrir XML. Verifique a identidade efetiva da tarefa, o acesso real de escrita ao log, o tratamento dos delimitadores, a contenção do caminho canônico e se o XML selecionado é controlado pelo atacante. A expansão de entidades externas pode transformar essa segunda leitura em divulgação privilegiada de arquivos se o resultado expandido chegar a uma saída legível por um usuário de menor privilégio. O [guia de segurança do processamento de XML em Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para o acesso a DTDs/entidades externas; inspecione o parser instalado e suas configurações efetivas. Um log ou arquivo XML gravável, por si só, é apenas uma pista. Revise o código e os metadados sem fornecer dados ao parser agendado durante a enumeração.

Inspecione também tarefas privilegiadas que materializam arquivos do repositório Git de outro usuário. Um script pode usar `git ls-tree` e `git cat-file` em vez de `git checkout` e, ainda assim, confiar nos caminhos de árvore controlados pelo atacante ao juntá-los a um diretório de staging. Caminhos absolutos e componentes `..` podem escapar desse diretório, a menos que o destino seja normalizado e verificado quanto à contenção antes da gravação. `git -c safe.directory=*` permite acessar repositórios com proprietários diferentes; isso, por si só, não cria a condição de gravação arbitrária.

Um backup de banco de dados executado como root pode criar outro limite de propriedade. O [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) do PostgreSQL copia arquivos regulares adicionais colocados no diretório de dados de origem, e seu formato padrão plain grava arquivos em `-D` como uma árvore de diretórios. Se uma conta de menor privilégio puder criar ou modificar esses arquivos de origem, inspecione a propriedade e as permissões do destino resultante, se seu caminho pode ser percorrido e executado e se a montagem tem `nosuid`. Uma cópia de propriedade do root que preserve permissões set-ID pode ser perigosa; um backup somente tar, permissões removidas ou um destino inacessível não comprovam o mesmo caminho. Rastreie o wrapper agendado e o usuário efetivo antes de tratar o comando de backup como uma constatação.

## Observe tarefas de curta duração

Um único snapshot de processos pode não capturar uma tarefa que executa por milissegundos. Compare as declarações de timer/cron com os logs e, quando autorizado, use monitoramento de eventos de processos, como `pspy` ou audit. Correlacione o proprietário do agendamento, a linha de comando exata e os arquivos que a tarefa lê ou grava. Uma interface web de agendador em loopback é uma interface separada; consulte o [exemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
