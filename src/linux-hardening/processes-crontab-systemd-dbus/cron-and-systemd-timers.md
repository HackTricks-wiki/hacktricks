# Cron Jobs and Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

スケジュールされたタスクは、現在の shell とは異なるユーザーIDや環境で実行されることがあります。cron、`at`、anacron、systemd timers を列挙し、各スケジュールコマンドをたどって、スクリプト、インポート、作業ディレクトリ、書き込み可能な入力を確認します。

## スケジュールを列挙する

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

システムのcrontabには通常ユーザーフィールドがありますが、ユーザーのcrontabにはありません。実際のスケジューラの有効なPATHと環境を確認してください。`run-parts --test /etc/cron.daily` を実行すると、そのホストで選択されるファイル名が表示されます。制御文字によって通常の出力ではエントリが隠れることがあるため、スケジュールが怪しい場合は `cat -A` または `sed -n l` を使用してください。

## 特権ファイルとコマンドの解決を追跡する

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

書き込み可能なスクリプトチェーン、`EnvironmentFile=` のパス、drop-in、シンボリックリンク、相対コマンド、ワイルドカード展開、特権タスクがコピーまたは実行するバイナリを確認します。タイマーは `Unit=` 設定を通じて、別名のサービスを起動する場合があります。主なプリミティブについては、[PATH](../linux-basics/linux-environment-variables.md#path)、[wildcard](../interesting-files-permissions/wildcards-spare-tricks.md)、[file-link](../main-system-information/filesystem-links-and-file-descriptors.md) の各ページを参照してください。

root で実行される `chkrootkit` の定期スクリプトを確認する場合は、インストール済みソースを調べ、古い [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) があるか確認します。`SLAPPER_FILES` の一時パスを確認した後に、引用符で囲まれていない `file_port=$file_port $i` があると、そのファイルを実行できる可能性があります。実際のスクリプトまたはベンダーパッチ、root でのスケジュール設定、一般ユーザーが正確な一時パスに書き込めるか、そのファイルが実行可能か、マウントポリシーを確認してください。バージョン文字列や `chkrootkit` の存在だけでは、この経路の成立は確認できません。受動的な確認では、一時ファイルを作成したり実行したりしないでください。

タイマーが root のサービスを起動し、そのサービスが `systemctl restart <other>.service` を実行する場合は、さらに1つ先の unit も追跡します。再起動された unit が、一般ユーザーの書き込み可能なスクリプトを使ってシェルを起動する場合があります。有効な `User=`、`DynamicUser=`、`RootDirectory=`/`RootImage=`、正確な `ExecStart=` 引数、スクリプトとその親パスの権限を確認してください。書き込み可能なスクリプトは候補にすぎません。タイマーと再起動対象のサービスが、その実行コンテキストで実際に有効である必要があります。どちらのサービスも再起動せず、unit のプロパティを確認してください。

高い権限のジョブがホスト名からスクリプトを取得し、そのレスポンスをシェルに渡す場合は、リモートスクリプトだけでなく、そのホスト名の名前解決を誰が制御できるかも確認します。グループや ACL によるアクセスも含め、書き込み可能な `/etc/hosts` は、ジョブがローカルで名前解決するホスト名を別の宛先に向けられる場合があります。ただし、`curl` のレスポンスがユーザー間の実行経路になるのは、実際の定期コマンドがそのレスポンスを実行し、かつ影響を受ける名前解決経路を使う場合だけです。ジョブの実行ユーザー、正確な URL とシェルパイプライン、有効な proxy/DNS の動作、ファイルおよび親ディレクトリの権限を確認してください。hosts ファイルが書き込み可能なだけでは、特権プロセスがそれを使う証明にはなりません。列挙中にマッピングを変更したりスクリプトを取得したりせず、スケジュールとメタデータを確認してください。

特権付きの定期 `wget` 取得は、ダウンロードした内容を直接実行しない場合でも、別個のファイル書き込み境界になります。[GNU Wget 1.18 changed the default HTTP-to-FTP redirect filename handling to fix CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html)。影響を受ける古いビルドでは、リダイレクト先の FTP ファイル名が使われる可能性があり、`--trust-server-names` はその動作を明示的に要求します。信頼度の低いユーザーが HTTP レスポンスと FTP リソースを制御できる場合は、ジョブがそのリダイレクトをたどるか、実際の Wget ビルドまたはベンダーバックポート、出力オプション、実行ユーザー、作業ディレクトリ、保存先のファイル名が起動ファイルになり得るかを確認します。[Wget loads `WGETRC` or `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html)。また、[its settings can select a POST source or output path](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html)。その後に特権で取得する処理がなければ、そこから情報漏えいや書き込みが生じる前提は成立しません。`authbind` 経由で低いポートを利用できても、呼び出し元がジョブの要求する URL を実際に提供できる場合に限り関係します。リダイレクトを提供したりジョブを実行したりせず、設定とログを受動的に確認してください。[Raw block-device access through the `disk` group](../user-information/interesting-groups-linux-pe/README.md#disk-group) は、このネットワーク取得経路とは別の問題です。

スクリプトだけでなくデータファイルも追跡します。定期実行されるシミュレーションまたはオーケストレーションツールが、起動するプロセスを定義した YAML ファイルを読み込む場合があります。一般ユーザーがそのファイルを編集でき、ジョブが別のアカウントで実行されるなら、そのデータがジョブの権限でコマンドとして扱われる可能性があります。書き込み可能な YAML ファイルを実行経路と判断する前に、正確な定期コマンド、有効な実行ユーザー、ファイルパス、パーサーの動作、書き込み権限（親ディレクトリを含む）を確認してください。受動的なトリアージでは、スケジュールとファイルのメタデータを読むだけで十分です。列挙中にジョブを実行したり入力を変更したりしないでください。

高い権限のジョブが一般ユーザーに置き換え可能なファイルを指定して `ssh -F` を実行する場合、SSH クライアント設定も実行可能な入力になります。OpenSSH の [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) は、クライアントのシェルを介してローカルコマンドを実行します。一方、`Host`/`Match` と先行するオプションによって、そのディレクティブが適用されるかが決まります。ユーザー間の実行経路と判断する前に、定期実行される SSH 呼び出しの正確な内容、実行ユーザー、選択される設定ファイルのパス、ディレクトリとファイルの書き込み権限、有効なオプション順序を照合します。特権アカウントでジョブを実行したり、信頼できない設定を読み込んだりせずに記録を確認してください。

定期実行の `scp` の後に `ssh` でコピーしたスクリプトを実行する場合、一般ユーザーが接続先の SSH サービスを制御できるなら、2つ目の信頼境界も確認します。そのサービスが接続を別ホストへ転送できると、特権クライアントが意図しない接続先で認証する可能性があります。[`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) は、OpenSSH に残る制約と有効なホスト別オプションの範囲内で、ホストキー変更の保護を弱めます。ジョブの実行ユーザー、実際の接続先と認証方式、リモートコマンドの有効な実行ユーザー、転送先ホストに同じパスが書き込み可能または既存かを確認します。古いファイルまたは攻撃者が制御するファイルが実行されるには、コピーが失敗するかそのパスに届かないことに**加えて**、ラッパーが SSH コマンドを続行する必要があります。[Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) と明示的なステータス処理は、その流れに影響します。弱いホストキー設定、プロセス一覧に見える `sshpass`、または書き込み可能な一時ディレクトリだけでは、このチェーンの成立は確認できません。列挙中にサービスの転送設定を変更したりジョブを起動したりせず、スケジュール、スクリプト、SSH 設定、ファイルのメタデータを調べてください。

特権アプリケーションのスケジューラは、書き込み可能なファイルではなく、データベースの行からジョブを取得する場合もあります。たとえば、root の cron エントリが Laravel の [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) を実行し、アプリケーションコードがタスク行を読み込む場合です。一般ユーザーがローカルパス名を含む行を書き込め、スケジュールされたコールバックが root で PHP の [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) を呼び出し、取得した内容を行で指定された webhook に送るなら、特権ファイルの情報漏えい経路になります。cron の実行ユーザー、実際のスケジューラコールバックと行からパスへのデータフロー、データベースへの書き込み権限、行を読み込んだ後の検証、送信先を確認してください。読み取り可能なアプリケーションの `.env` は認証情報を調べる手がかりにすぎません。Web フォームによる検証やデータベースのパスワードだけでは、行の制御や情報漏えいは証明できません。列挙中にデータベースへ問い合わせたりタスクを登録したりせず、スケジュール、コード、認証情報ファイルの権限を受動的に確認してください。

イベント駆動の `incron` ジョブも同様に確認します。[incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) は、監視対象のパスとイベントを、テーブル所有者の権限で実行されるコマンドに関連付けます。アプリケーションが書き込み可能なディレクトリ内のリンクをたどり、攻撃者が制御するテキストを監視対象へ書き込む場合、一般ユーザーが監視対象ファイルに間接的な影響を与える可能性があります。実際のテーブル所有者、イベント、対象とその祖先の権限、アプリケーションがリンクをたどる動作、そのテキストがコマンド引数になる仕組みを確認してください。特に、[GNU Mailutils `mail` accepts `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html)。その[shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) はプログラムを実行できます。この実装で信頼できないフィールドが別個のオプションとして渡されると、コマンド実行に至る可能性があります。他の `mail` 実装や、引用符で保護された固定引数の境界では、動作が異なる場合があります。列挙中に監視対象ファイルを変更したりジョブを起動したりせず、スケジュール、アプリケーションコード、ファイルのメタデータを確認してください。

監視対象のログも、ヘルパースクリプトを介してユーザー境界を越える場合があります。一般ユーザーがログに書き込め、`incron` の所有者がログからフィールドを読み取り、新しい [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) に入れる場合、シェルはそのフィールドを所有者の権限で再解析します。実際に監視されるイベント、ログと親ディレクトリの権限、ヘルパーのパス、ログフィールドの変換方法、生成されたコマンドまで処理が到達するかを確認してください。書き込み可能なログと `incron` エントリがあるだけでは、データフローの成立は確認できません。受動的な列挙では、トリガーとなる行を書き込んだりヘルパーを実行したりしないでください。

証明書の更新ジョブも同じ境界を越える可能性があります。特権ヘルパーが、一般ユーザーの書き込み可能なディレクトリにある証明書から X.509 subject を読み取り、その common name を新しい `bash -c` コマンド文字列に挿入する場合があります。[OpenSSL can display a certificate's subject and check its expiry](https://docs.openssl.org/3.3/man1/openssl-x509/)。[Bash parses the `-c` string as shell input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html) なので、外側のスクリプトで変数を引用符で囲んでも、2回目の解析からは保護されません。コマンドインジェクションと判断する前に、スケジュールの実行ユーザー、正確な入力パスと書き込み権限、更新処理の分岐、`bash -c` に至るデータフローを確認してください。列挙中に更新処理を起動せず、スクリプトと証明書のメタデータを受動的に確認します。

同じ2回目の解析は、特権ジョブが一般ユーザーのアーカイブまたはパッケージから名前を取り出し、`xargs -I` で `sh -c` のコマンド文字列に挿入する場合にも発生します。[GNU `xargs -I` replaces the placeholder in initial arguments](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html)、および[`sh -c` interprets its command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)。外側のスクリプトで抽出した名前を引用符で囲んでも、後から置換されるシェルプログラムが安全になるわけではありません。ジョブの実行ユーザー、受け入れる入力パスと書き込み権限、アーカイブの検証と分岐条件、名前からシェルに至るデータフローを確認してください。書き込み可能なアップロードディレクトリや `xargs` の呼び出しだけでは手がかりにすぎません。列挙中にパッケージを送信したりジョブを実行したりせず、スケジュール、スクリプト、パスのメタデータを調べてください。

定期実行のフォントまたは画像インポーターは、アップロード時の外側のファイル名が制限されていても、ユーザー提供のアーカイブ内の名前を信頼してしまう可能性があります。FontForge は、CVE-2024-25081 と CVE-2024-25082 に関する[upstream change](https://github.com/fontforge/fontforge/pull/5367)で、アーカイブのメンバー名によるコマンドインジェクションを修正しました。高い権限のジョブが一般ユーザーの書き込み可能なパスからアーカイブを実際に開くか、その実行ユーザー、正確な FontForge ビルドまたはベンダーバックポート、アーカイブ処理のコードパスを確認してください。バージョン文字列や許可されたアップロード拡張子だけでは、実行の証拠になりません。列挙中に信頼できないアーカイブをインポートせず、スケジュール、パス権限、ビルドのメタデータを確認してください。

定期実行されるネットワークスキャナーは、カスタムスクリプトがリモート TLS 証明書の subject をローカルファイル名として扱う場合、別の境界を越える可能性があります。[Nmap NSE runs selected scripts without a sandbox](https://nmap.org/book/nse-usage.html)。実際のスクリプトを調べ、信頼できない subject フィールドを、包含チェックなしでデータディレクトリに結合していないか確認します。ファイル開示が成立するには、スケジューラがスキャンする対象、スキャナーの実行ユーザーが読み取れるファイルに解決されるパス、一般ユーザーが読めるレポートまたはログへの出力が必要です。証明書フィールドやスキャナーのインストールだけでは、このチェーンの成立は証明できません。受動的な列挙中に新しい対象をスキャンせず、スケジュール、スクリプト、パス解決、レポートの送信先を確認してください。

Ansible runner に `/path/to/tasks/*.yml` のようなシェル glob を渡す特権 cron コマンドは、既存の playbook がすべて読み取り専用でも、ディレクトリの権限を確認する必要があります。glob の対象ディレクトリへの書き込み権限と検索権限があるユーザーは、条件に一致する別の playbook を作成できる場合があります。[Ansible playbooks define tasks that the runner executes](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html)。ただし、カスタムラッパーがパスをフィルタリングしたり、別の実行ユーザーを使ったりする場合があります。ディレクトリを実行経路と判断する前に、ラッパーの動作、実際の cron ユーザー、シェル展開、ACL、sticky bit、マウントポリシーを確認してください。列挙中は、メタデータとラッパーの静的な内容を調べるだけにし、定期ジョブを実行しないでください。

特権 cron ラッパーは、アップロードディレクトリ内のファイル名を glob 展開し、Perl ヘルパーに渡す場合があります。Perl の[`<>` diamond operator uses two-argument `open`](https://perldoc.perl.org/perlop#The-Null-Filehandle)は、パイプコマンドとして解釈される一致ファイル名をヘルパーの権限で実行する可能性があります。一方、[`<<>>` treats arguments as literal filenames](https://perldoc.perl.org/perlop#The-Null-Filehandle)。スケジューラの実行ユーザー、ラッパーの作業ディレクトリと glob、ヘルパーの実際の `@ARGV` 処理、ファイル名の制限、一般ユーザーがファイルシステム権限または認証済みアップロードサービス経由で一致する名前を配置できるかを確認してください。cron の行、Perl スクリプト、書き込み可能な FTP ディレクトリだけでは、チェーン全体の成立は証明できません。列挙中に細工したファイル名を送信したりジョブを実行したりせず、ソースとメタデータを確認してください。

読み取り専用の cron スクリプトでも、スケジュールされたアカウントがパス名で実行し、一般ユーザーが sticky bit のない親ディレクトリに書き込み、検索できるなら、置き換えられる可能性があります。スケジュールの実行ユーザー、各パス要素、ディレクトリの sticky bit、ACL、マウントポリシーを確認してください。ファイルを移動したりジョブを実行したりせずに、メタデータを調べます。

特権 PHP cron ラッパーは、まだ存在しないヘルパーを呼び出す場合もあります。PHP の [`exec()`](https://www.php.net/manual/en/function.exec.php) に固定の絶対パスを渡し、その親ディレクトリに一般ユーザーがその名前を作成できるなら、後の実行で使われる内容を制御できる可能性があります。cron エントリが実際に高い権限でラッパーを実行するか、正確なコマンド文字列と PHP の実行ポリシー、ヘルパーディレクトリへの書き込み・検索権限、シンボリックリンクと sticky bit の動作、ヘルパーがまだ存在しないかを確認します。書き込み可能なディレクトリやヘルパーの欠落だけでは手がかりにすぎません。列挙中にヘルパーを作成したりジョブを起動したりせず、スケジュール、ソース、パスのメタデータを調べてください。

定期ジョブが `find` で入力スクリプトを見つけ、インタープリターに渡す場合もあります。たとえば、[gnuplot's `system()` function invokes a shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf)。特権ジョブが一般ユーザーの書き込み可能なディレクトリ内にあるすべての `*.plt` ファイルに対して `gnuplot` を実行すると、ジョブの権限でコマンドを実行できる可能性があります。[Directory read permission controls listing, while write and search (`x`) control creating and accessing known names](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html)。`ls` で一覧を表示できなくても、書き込みと検索の権限を確認してください。スケジューラの正確な実行ユーザーとコマンド、インタープリターの動作、選択されるファイルパターン、ディレクトリ権限を照合します。書き込み可能なディレクトリやインタープリターのインストールだけでは、権限昇格は確認できません。非公開のスケジュールや短時間で終わるジョブの確認には、許可を得たうえでイベントを観測する必要がある場合があります。単一のプロセススナップショットでは見逃すことがあります。

特権 PHP ジョブでは、実行可能なスクリプトチェーンの一部として、リテラルな `include`/`require` 文も確認します。[PHP evaluates included files](https://www.php.net/manual/en/function.include.php)。そのため、メインスクリプトが読み取り専用でも、グループ書き込み可能な `.php` ファイルが読み込まれれば、ジョブの権限でコードが実行される可能性があります。スケジュールの実行ユーザー、有効な include-path の解決、ファイルとディレクトリの権限、ジョブが実際に実行されるかを確認してください。コメント内の cron 記述例は手がかりにすぎません。同様の確認は、`-S` と `-t <document-root>` を指定して起動される、root 所有の [PHP built-in server](https://www.php.net/commandline.webserver) にも当てはまります。loopback の待受けであっても、ローカルリクエストに対してアプリケーションの PHP を実行する場合があります。列挙中にいずれのトリガーも呼び出さず、プロセスとソースを調べてください。

特権 PHP ジョブは**データファイル**を介しても境界を越える可能性があります。一般ユーザーが [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) に渡される正確なファイルを変更できると、PHP がオブジェクトを復元する際、読み込まれているクラスの `__wakeup()` または `__unserialize()` メソッドを呼び出す可能性があります。ジョブの有効な実行ユーザー、ファイルと祖先の権限、読み込まれるクラス、プロパティで選択されるファイルへの書き込みなど、実際のメソッドの副作用を確認してください。書き込み可能なログや `unserialize()` の呼び出しだけでは、利用可能な経路の成立は証明できません。列挙中にシリアライズ済み入力を書き込んだりジョブを実行したりせず、ソースとメタデータを調べてください。

root cron タスクは、Web サーバーではなく PHP アプリケーションの**CLI ページランナー**を呼び出す場合があります。ランナーが選択する document root と URI から、実際の PHP エントリポイントまで追跡します。そのエントリポイントが Web サービスのアカウントで書き込み可能なら、ランナーと cron ラッパーが読み取り専用でも、定期実行の CLI リクエストによって変更後のコードが root で実行される可能性があります。スケジューラの実行ユーザー、URI からファイルへの正確な解決、有効なファイルと祖先の権限、整合性チェックがエントリポイント自体を保護するかを確認してください。列挙中にランナーを呼び出したりページを変更したりせず、ソースとメタデータを調べてください。

定期ジョブまたは別ユーザーによって共有作業ディレクトリから起動される `ipython` プロセスでは、startup file を確認します。[IPython's security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) によると、CVE-2022-21699 の修正前に影響を受けるビルドは、カレントディレクトリでプロファイルや設定を検索し、`profile_default/startup` のコードも読み込んでいました。実際にインストールされているビルドまたはベンダーパッチ、コマンドの作業ディレクトリ、高い権限のプロセスの実行ユーザー、一般ユーザーが正確な startup パスに書き込み・検索できるかを照合してください。`ipython` のインストール、書き込み可能なディレクトリ、バージョン文字列だけでは、別のユーザーがそこにあるファイルを読み込む証明にはなりません。高い権限のインタープリターを起動せずに、スケジュールとパスのメタデータを確認してください。

カスタムネイティブ拡張の関数を呼び出す特権 PHP サーバーでは、拡張を調べる前に、サービスの PHP SAPI と有効な `php.ini` および追加読み込みされる `.ini` ファイルを追跡します。[PHP loads configured `extension` libraries at startup](https://www.php.net/manual/en/ini.core.php)。また、[CLI and web SAPIs can use different configuration files](https://www.php.net/manual/en/configuration.file.php)。そのため、アクセス可能なログインフォームやローカルリスナーから、サービスの権限で動作するコンパイル済みコードへ、ユーザー制御の文字列が渡る場合があります。unit の `User=`、`ExecStart=`、作業ディレクトリ、実際の拡張パス、呼び出し元が制御できる引数を記録してください。`.so` の存在や loopback ソケットだけでは、メモリ破損の脆弱性は確認できません。受動的な列挙中にプローブを送信せず、カスタムパーサーは個別に分析してください。

特権ラッパーがスクリプトをパス名でハッシュし、後から同じパス名を再度開いて実行する場合、ダイジェストが検証するのは最初の open で読み込まれたオブジェクトだけです。一般ユーザーが2回の open の間にスクリプトのディレクトリエントリを置き換えられると、元のスクリプトが root 所有でも、後の実行時には別のオブジェクトに解決される可能性があります。FIFO は検証フェーズを長引かせることがありますが、この経路が成立するかは、置き換え可能な親ディレクトリの権限、実際に別々の open があること、スケジューラの実行ユーザー、sticky bit とマウントの規則、タイミングに依存します。ラッパーと `namei -l` の出力を受動的な手がかりとして確認してください。チェックサムに成功しただけでは、後から開くパスが保護されている証明にはなりません。

特権バックアップジョブは、攻撃者が用意したコマンドを実行せずにデータを**開示**する場合もあります。一般ユーザーがジョブの読み取る制御ファイルを作成できるか、ジョブがその後 `/etc/shadow` などの保護されたソースを開くか、攻撃者が選択した URL または読み取り可能な出力先に結果が送られるかを追跡します。情報漏えい経路と判断する前に、この3点すべてを確認してください。同じスクリプト内の固定シェルコマンドだけでは、その制御ファイルがシェルインジェクション入力であることの証明にはなりません。列挙中にジョブを実行したり制御ファイルを仕込んだりせず、スクリプトとファイルの権限を確認してください。

特権定期ジョブが `curl -K FILE` または `curl --config FILE` を実行する場合、[curl treats options in that file as command-line arguments](https://curl.se/docs/manpage.html)。curl が読み込む時点で一般ユーザーが正確なファイルを制御できると、要求 URL、ローカルファイル入力、出力パスに影響を与えられる可能性があります。保護されたファイルの読み取りまたは書き込みを主張する前に、ジョブの有効な実行ユーザー、ファイルと祖先への書き込み権限、別のジョブがファイルを置き換えるタイミング、設定オプションと固定のコマンドラインオプションの相互作用を確認してください。設定パスが書き込み可能であることや `-K` フラグが見えることだけでは、選択されたオプションが有効になる証明にはなりません。列挙中にジョブを実行したり URL を取得したりせず、スケジュールとメタデータを確認してください。

cron エントリがヘルパースクリプトを呼び出す場合は、その作業ディレクトリとアーカイブコマンドも確認します。他のユーザーが書き込み可能なディレクトリに対する引用符で囲まれていないワイルドカードは、ファイル名をアーカイバーのオプションとして解釈させる可能性があります。GNU tar の checkpoint action はその一例です。ユーザー間のコマンド実行経路と判断する前に、スケジュールされた実行ユーザー、書き込み可能な入力ディレクトリ、正確なアーカイバーとオプション、`--` によってオプション解析を終了しているかを確認してください。[wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md) を参照してください。

特権ヘルパーが `cd INPUT_DIR; tar ... *` を実行し、`cd` の成功を確認しない場合、別のバックアップファイル開示が発生する可能性があります。一般ユーザーが `INPUT_DIR` を削除または置換できると、`cd` が失敗してシェルが以前のディレクトリに残り、その後のアーカイブコマンドがそのディレクトリを読み込む場合があります。ジョブの初期作業ディレクトリ、実際に `cd` が失敗する経路、スクリプトが終了するか `&&` を使うか、正確なアーカイバーのオプション、出力アーカイブを一般ユーザーが読めるかを確認してください。入力ディレクトリが書き込み可能、またはアーカイブが読み取り可能というだけでは手がかりにすぎません。稼働中のジョブを変更せず、ヘルパーとパスの権限を調べてください。

定期実行ファイルがシェルスクリプトを隠している場合も、信頼境界はなくなりません。[SHc](https://github.com/neurobin/shc) は暗号化されたスクリプトテキストをネイティブバイナリで包み、実行時にシェル経由で実行します。`.sh.x` という拡張子や内容が不透明な ELF は確認の手がかりにすぎません。ファイル名によるオプションインジェクションを評価するには、特権スケジューラの実行ユーザー、ヘルパーの実際の作業ディレクトリとコマンド、一般ユーザーがそこで一致する名前を作成できるか、引用符で囲まれていない glob がオプションを区切らずに `rsync` などのコマンドへ渡るかを確認します。[`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) は、その正確なコマンド経路が使われる場合に限り関係します。`/proc` の表示が制限されている場合や、静的な復号に失敗してコマンドが不明な場合でも、分類のためだけに特権ヘルパーを実行しないでください。

プロセスのコマンドライン文字列も、特権ヘルパーに対する信頼できない入力です。一般ユーザーは `pgrep -f` に一致するプロセスタイトルまたは `argv[0]` を選べます。一致する名前は、実行ファイルやその所有者を証明しません。root で動作するスクリプトがその文字列を取り込み、一部を書き換えて `apache2ctl`/`httpd` にし、固定の引数配列を使わずに実行すると、攻撃者が選んだオプションによって別の設定ディレクトリや error log が指定される可能性があります。Apache の設定解析はモジュールを読み込んだり、設定済みのヘルパーに到達したりする場合があります。そのため、列挙中に信頼できない設定を root で検証しないでください。スケジューラの所有者、正確なヘルパー、プロセスの実行ユーザー、データから引数への流れを確認します。シェルのメタ文字による実行が別途確認されない限り、これはオプション／設定インジェクションです。

信頼できないテキストを Bash の算術式に渡す root 実行のパーサーは、そのテキスト内の置換を実行する可能性があります。[privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) に具体例があります。すべての算術式を悪用可能と判断する前に、入力元と解析コマンドを確認してください。

アプリケーションログを解析する特権ジョブでは、最初の解析後も信頼できないフィールドを追跡します。一般ユーザーは現在のプロセスグループを通じてログに書き込めたり、記録されるリクエストフィールドに影響を与えたりする場合があります。そのレコードが画像を選択し、そのメタデータが XML を開くための2つ目のパス名になることがあります。ジョブの有効な実行ユーザー、実際のログ書き込み権限、区切り文字の処理、正規化後のパスが指定ディレクトリ内にあるか、選択された XML が攻撃者に制御されているかを確認します。外部エンティティの展開によって2つ目のファイル読み取りが特権ファイルの漏えいに至るのは、展開結果が一般ユーザーの読める出力に渡される場合です。[Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) に、外部 DTD／エンティティへのアクセス制御が記載されています。インストール済みパーサーと有効な設定を確認してください。書き込み可能なログや XML ファイルだけでは手がかりにすぎません。列挙中にスケジュールされたパーサーへ入力を渡さず、コードとメタデータを調べてください。

別ユーザーの Git リポジトリからファイルを生成する特権ジョブも確認します。スクリプトは `git checkout` ではなく `git ls-tree` と `git cat-file` を使っていても、攻撃者が制御する tree path をステージングディレクトリに結合する際に、そのパスを信頼してしまう可能性があります。書き込み前に保存先を正規化し、その範囲内にあることを確認しなければ、絶対パスや `..` を含む要素がそのディレクトリの外へ出ることがあります。`git -c safe.directory=*` は、所有者の異なるリポジトリへのアクセスを許可しますが、それだけで任意ファイル書き込みが発生するわけではありません。

root で実行されるデータベースバックアップも、別の所有権境界を生むことがあります。PostgreSQL の [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) は、ソースデータディレクトリに追加された通常ファイルもコピーします。デフォルトの plain 形式では、`-D` にディレクトリツリーとしてファイルを書き込みます。一般ユーザーがこれらのソースファイルを作成または変更できる場合は、コピー先の所有者とモード、そのパスをたどれるか・実行可能か、マウントに `nosuid` が設定されているかを確認します。set-ID 権限が保持された root 所有のコピーは危険な場合があります。tar 形式のみのバックアップ、権限の除去、アクセスできない保存先では、同じ経路は成立しません。バックアップコマンドを問題として扱う前に、スケジュールされたラッパーと有効な実行ユーザーを追跡してください。

## Observe short-lived work

単一のプロセススナップショットでは、数ミリ秒で終わるジョブを見逃す場合があります。timer/cron の宣言をログと照合し、許可を得たうえで `pspy` や audit などのプロセスイベント監視を利用します。スケジュールされた実行ユーザー、正確なコマンドライン、タスクが読み書きするファイルを照合してください。loopback 上のスケジューラ Web UI は別のインターフェースです。[Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc) を参照してください。
