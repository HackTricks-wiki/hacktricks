# Cron-Jobs und Systemd-Timer

{{#include ../../banners/hacktricks-training.md}}

Geplante Aufgaben können mit einer anderen Identität und Umgebung als die aktuelle Shell ausgeführt werden. Durchsuche cron, `at`, anacron und systemd-Timer und verfolge jeden geplanten Befehl durch seine Skripte, Imports, sein Arbeitsverzeichnis und beschreibbare Eingaben.

## Zeitpläne auflisten

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System-Crontabs enthalten normalerweise ein Benutzerfeld; die Crontab eines Benutzers nicht. Prüfe den effektiven PATH und die Umgebung des tatsächlichen Schedulers. `run-parts --test /etc/cron.daily` zeigt, welche Dateinamen auf diesem Host ausgewählt würden. Steuerzeichen können einen Eintrag in einer flüchtigen Ausgabe verbergen. Verwende daher `cat -A` oder `sed -n l`, wenn ein Zeitplan verdächtig aussieht.

## Privilegierte Datei- und Befehlsauflösung nachverfolgen

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Prüfe beschreibbare Skriptketten, `EnvironmentFile=`-Pfade, Drop-ins, Symlinks, relative Befehle, Wildcard-Expansion sowie Binärdateien, die von einer privilegierten Aufgabe kopiert oder ausgeführt werden. Ein Timer kann über seine Einstellung `Unit=` einen Dienst mit einem anderen Namen aktivieren. Die Seiten [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) und [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) erklären die wichtigsten Grundlagen.

Untersuche bei einem geplanten, als root ausgeführten `chkrootkit`-Skript den installierten Quellcode auf den alten [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): Ein nicht in Anführungszeichen gesetztes `file_port=$file_port $i` nach einer Prüfung eines temporären `SLAPPER_FILES`-Pfads kann diese Datei ausführen. Überprüfe das tatsächliche Skript oder den Vendor-Patch, die Ausführung als root, den Schreibzugriff eines Benutzers mit geringeren Rechten auf den exakten temporären Pfad, dessen Ausführbarkeit und die Mount-Richtlinien. Eine Versionszeichenfolge oder allein das Vorhandensein von `chkrootkit` belegt diesen Pfad nicht; erstelle oder starte bei einer passiven Prüfung keine temporäre Datei.

Verfolge bei einem Timer, dessen Root-Dienst `systemctl restart <other>.service` ausführt, einen weiteren Unit-Schritt: Die neu gestartete Unit kann eine Shell mit einem Skript aufrufen, das ein Benutzer mit geringeren Rechten beschreiben kann. Bestätige die effektiven Werte von `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, die exakten Argumente von `ExecStart=` sowie die Berechtigungen des Skripts und seines übergeordneten Pfads. Ein beschreibbares Skript ist erst dann ein möglicher Angriffsvektor, wenn Timer und neu gestarteter Dienst in diesem Ausführungskontext aktiv sind. Prüfe die Unit-Eigenschaften, ohne einen der Dienste neu zu starten.

Wenn ein Job mit höheren Rechten ein Skript anhand eines Hostnamens abruft und die Antwort an eine Shell weitergibt, prüfe neben dem Remote-Skript auch, wer die Auflösung dieses Hostnamens kontrolliert. Eine beschreibbare Datei `/etc/hosts`, auch bei Zugriff über eine Gruppe oder ACL, kann einen Namen umleiten, den der Job lokal auflöst. Eine `curl`-Antwort wird jedoch nur dann zu einem benutzerübergreifenden Ausführungspfad, wenn der tatsächlich geplante Befehl diese Antwort ausführt und der Job den betroffenen Resolverpfad verwendet. Überprüfe die Identität, unter der der Job ausgeführt wird, die genaue URL und Shell-Pipeline, das effektive Proxy-/DNS-Verhalten sowie die Datei- und Verzeichnisberechtigungen. Eine beschreibbare Hosts-Datei ist für sich genommen nur ein Prüfhinweis, kein Beweis für einen privilegierten Verbraucher. Prüfe bei der Enumeration den Zeitplan und die Metadaten, ohne die Zuordnung zu ändern oder das Skript abzurufen.

Ein geplanter privilegierter `wget`-Abruf bildet eine separate Dateischreibgrenze, auch wenn der heruntergeladene Inhalt nicht direkt ausgeführt wird. [GNU Wget 1.18 änderte die Standardbehandlung von Dateinamen bei HTTP-zu-FTP-Weiterleitungen, um CVE-2016-4971 zu beheben](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); ältere betroffene Builds konnten den FTP-Dateinamen der Weiterleitung verwenden, während `--trust-server-names` dieses Verhalten explizit anfordert. Wenn eine Partei mit geringerem Vertrauensniveau die HTTP-Antwort und FTP-Ressource kontrolliert, prüfe, ob der Job dieser Weiterleitung folgt, den tatsächlichen Wget-Build oder Vendor-Backport, Ausgabeoptionen, die Ausführungsidentität, das Arbeitsverzeichnis und ob der Zieldateiname zu einer Startup-Datei werden kann. [Wget lädt `WGETRC` oder `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), und [seine Einstellungen können eine POST-Quelle oder einen Ausgabepfad festlegen](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); ein späterer privilegierter Abruf ist eine separate Voraussetzung für jede daraus folgende Offenlegung oder Schreiboperation. Zugriff auf einen niedrigen Port über `authbind` ist nur dann relevant, wenn der Aufrufer tatsächlich die URL bereitstellen kann, die der Job abruft. Prüfe Konfiguration und Logs passiv, ohne eine Weiterleitung bereitzustellen oder den Job auszuführen. [Unbeschränkter Zugriff auf Blockgeräte über die Gruppe `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) ist unabhängig von diesem Netzwerk-Abrufpfad.

Verfolge auch Datendateien, nicht nur Skripte. Ein geplantes Simulations- oder Orchestrierungstool kann eine YAML-Datei einlesen, in der zu startende Prozesse definiert sind. Kann ein Benutzer mit geringeren Rechten diese Datei bearbeiten und wird der Job unter einem anderen Konto ausgeführt, können die Daten zu Befehlen unter der Identität des Jobs werden. Überprüfe den exakten geplanten Befehl, den effektiven Benutzer, den Dateipfad, die Parser-Semantik und den Schreibzugriff (einschließlich übergeordneter Verzeichnisse), bevor du eine beschreibbare YAML-Datei als Ausführungspfad einstufst. Für eine passive Triage genügt es, den Zeitplan und die Dateimetadaten zu lesen; führe den Job nicht aus und ändere seine Eingabe während der Enumeration nicht.

Auch eine SSH-Clientkonfiguration ist ausführbarer Input, wenn ein Job mit höheren Rechten `ssh -F` mit einer Datei ausführt, die ein Benutzer mit geringeren Rechten ersetzen kann. OpenSSHs [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) führt über die Shell des Clients einen lokalen Befehl aus, während `Host`/`Match` und vorherige Optionen bestimmen, ob diese Direktive gilt. Gleiche den exakten geplanten SSH-Aufruf, die Ausführungsidentität, den ausgewählten Konfigurationspfad, Schreibberechtigungen für Verzeichnis und Datei sowie die effektive Optionsreihenfolge ab, bevor du von einem benutzerübergreifenden Ausführungspfad sprichst. Prüfe diese Einträge, ohne den Job auszuführen oder die nicht vertrauenswürdige Konfiguration als privilegiertes Konto zu laden.

Ein geplanter Aufruf von `scp` mit anschließendem `ssh`, um das kopierte Skript auszuführen, erfordert eine weitere Prüfung der Vertrauensgrenze, wenn ein Benutzer mit geringeren Rechten den Ziel-SSH-Dienst kontrolliert. Wenn dieser Dienst die Verbindung zu einem anderen Host weiterleiten kann, authentifiziert sich der privilegierte Client möglicherweise an einem unbeabsichtigten Endpunkt. [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) schwächt den Schutz vor geänderten Hostschlüsseln, vorbehaltlich der verbleibenden OpenSSH-Einschränkungen und der effektiven hostbezogenen Optionen. Ermittle die Ausführungsidentität des Jobs, das tatsächliche Ziel und die Authentifizierungsmethode, die effektive Identität des entfernten Befehls und ob derselbe Zielpfad auf dem umgeleiteten Host beschreibbar oder bereits vorhanden ist. Die Ausführung einer älteren oder vom Angreifer kontrollierten Datei setzt zusätzlich voraus, dass das Kopieren fehlschlägt oder diese Datei nicht trifft **und** der Wrapper mit seinem SSH-Befehl fortfährt; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) und eine explizite Statusbehandlung beeinflussen diesen Ablauf. Eine schwache Hostschlüsseleinstellung, ein sichtbarer `sshpass`-Prozess oder ein beschreibbares temporäres Verzeichnis allein belegen diese Kette nicht. Prüfe bei der Enumeration den Zeitplan, das Skript, die SSH-Konfiguration und die Dateimetadaten, ohne den Dienst umzuleiten oder den Job auszulösen.

Ein privilegierter Anwendungs-Scheduler kann seine Jobs aus Datenbankzeilen statt aus beschreibbaren Dateien beziehen. Beispielsweise kann ein Root-Cron-Eintrag, der Laravel-`schedule:run` mit [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) aufruft, Anwendungscode erreichen, der Task-Zeilen liest. Kann ein Konto mit geringeren Rechten eine Zeile mit einem lokalen Pfad schreiben und ruft der geplante Callback unter root PHPs [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) auf und sendet den zurückgegebenen Inhalt an einen in der Zeile festgelegten Webhook, entsteht ein privilegierter Dateioffenlegungspfad. Überprüfe die Cron-Identität, den tatsächlichen Scheduler-Callback und den Datenfluss von der Zeile zum Pfad, die Datenbank-Schreibberechtigung, die Validierung nach dem Lesen der Zeile und das ausgehende Ziel. Eine lesbare Anwendungsdatei `.env` ist lediglich ein Hinweis auf Zugangsdaten; eine Webformularvalidierung oder ein Datenbankpasswort allein beweist weder die Kontrolle über die Zeile noch eine Offenlegung. Prüfe bei der Enumeration den Zeitplan, den Code und die Berechtigungen der Zugangsdaten-Datei passiv, ohne die Datenbank abzufragen oder einen Task einzuplanen.

Auch ereignisgesteuerte `incron`-Jobs verdienen dieselbe Prüfung: [incrontab-Einträge](https://manpages.debian.org/testing/incron/incrontab.5.en.html) verknüpfen einen überwachten Pfad und ein Ereignis mit einem Befehl, der unter der Identität des Tabelleneigentümers ausgeführt wird. Ein Benutzer mit geringeren Rechten kann eine überwachte Datei indirekt beeinflussen, wenn eine Anwendung einem Link aus einem beschreibbaren Verzeichnis folgt und vom Angreifer kontrollierten Text in das überwachte Ziel schreibt. Überprüfe den tatsächlichen Tabelleneigentümer, das Ereignis, das Ziel und die Berechtigungen der übergeordneten Verzeichnisse, das Verhalten der Anwendung beim Folgen von Links und wie dieser Text zu Befehlsargumenten wird. Insbesondere akzeptiert [GNU Mailutils `mail` die Option `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), und sein [Shell-Escape-Befehl](https://mailutils.org/manual/html_node/Shell-Escapes.html) kann ein Programm ausführen. Ein nicht vertrauenswürdiges Feld, das als separates Argument an diese Implementierung übergeben wird, kann dadurch zur Befehlsausführung führen. Andere `mail`-Implementierungen oder eine Anführungszeichen-Begrenzung mit festen Argumenten können sich anders verhalten. Prüfe bei der Enumeration den Zeitplan, den Anwendungscode und die Dateimetadaten, ohne die überwachte Datei zu ändern oder den Job auszulösen.

Ein überwachtes Log kann über ein Hilfsskript ebenfalls eine Benutzergrenze überschreiten. Kann ein Benutzer mit geringeren Rechten das Log beschreiben und liest der `incron`-Eigentümer ein Feld daraus in eine neue [`sh -c`-Befehlszeichenfolge](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), parst die Shell dieses Feld unter der Identität des Eigentümers erneut. Prüfe das exakte überwachte Ereignis, die Berechtigungen des Logs und der übergeordneten Verzeichnisse, den Pfad des Hilfsskripts, die Verarbeitung des Log-Feldes und ob der resultierende Befehl tatsächlich ausgeführt wird. Ein beschreibbares Log und ein `incron`-Eintrag allein belegen den Datenfluss nicht. Schreibe bei einer passiven Enumeration keine Trigger-Zeile und führe das Hilfsskript nicht aus.

Jobs zur Zertifikatserneuerung können dieselbe Grenze überschreiten. Ein privilegiertes Hilfsprogramm kann den X.509-Subject eines Zertifikats in einem von einem Benutzer mit geringeren Rechten beschreibbaren Verzeichnis auslesen und dessen Common Name in eine neue `bash -c`-Befehlszeichenfolge einsetzen. [OpenSSL kann den Subject eines Zertifikats anzeigen und dessen Ablauf prüfen](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash parst die Zeichenfolge von `-c` als Shell-Input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), daher schützt das Quoten der Variablen im äußeren Skript nicht vor dem zweiten Parse. Bestätige die geplante Identität, den exakten Eingabepfad und dessen Schreibberechtigungen, den Erneuerungszweig und den Datenfluss zu `bash -c`, bevor du von Command Injection sprichst. Prüfe Skript und Zertifikatsmetadaten passiv; löse bei der Enumeration keine Erneuerung aus.

Ein zweiter Parse kann auch auftreten, wenn ein privilegierter geplanter Job einen Namen aus dem Archiv oder Paket eines Benutzers mit geringeren Rechten extrahiert und ihn zur Einfügung in eine `sh -c`-Befehlszeichenfolge an `xargs -I` weitergibt. [GNU `xargs -I` ersetzt den Platzhalter in den ursprünglichen Argumenten](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), und [`sh -c` interpretiert seine Befehlszeichenfolge](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Selbst wenn das äußere Skript den extrahierten Namen in Anführungszeichen setzt, macht das ein später eingesetztes Shell-Programm nicht sicher. Überprüfe die Ausführungsidentität des Jobs, den exakten akzeptierten Eingabepfad und dessen Schreibberechtigungen, die Archivvalidierung und Verzweigungsbedingungen sowie den Datenfluss vom Namen zur Shell. Ein beschreibbares Upload-Verzeichnis oder ein `xargs`-Aufruf allein ist nur ein Hinweis. Prüfe bei der Enumeration den Zeitplan, das Skript und die Pfadmetadaten, ohne ein Paket einzureichen oder den Job auszuführen.

Ein geplanter Font- oder Bildimporter kann ebenso Namen *im Inneren* eines vom Aufrufer bereitgestellten Archivs vertrauen, auch wenn der äußere Upload-Dateiname eingeschränkt ist. FontForge behob die Command Injection über Archiv-Eintragsnamen in der [Upstream-Änderung für CVE-2024-25081 und CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Bestätige, dass ein Job mit höheren Rechten tatsächlich ein Archiv aus einem von einem Benutzer mit geringeren Rechten beschreibbaren Pfad öffnet, die Ausführungsidentität, den exakten FontForge-Build oder Vendor-Backport und den Codepfad zur Archivverarbeitung. Eine Versionszeichenfolge oder ein zulässiges Upload-Suffix allein beweist keine Ausführung. Prüfe bei der Enumeration Zeitplan, Pfadberechtigungen und Build-Metadaten, ohne ein nicht vertrauenswürdiges Archiv zu importieren.

Geplante Netzwerk-Scanner können eine andere Grenze überschreiten, wenn ein benutzerdefiniertes Skript den Subject eines Remote-TLS-Zertifikats als lokalen Dateinamen behandelt. [Nmap NSE führt ausgewählte Skripte ohne Sandbox aus](https://nmap.org/book/nse-usage.html). Prüfe daher das tatsächliche Skript und ob es ein nicht vertrauenswürdiges Subject-Feld ohne Containment-Prüfungen an ein Datenverzeichnis anhängt. Für eine Offenlegung von Dateien braucht es ein Ziel, das der Scheduler scannt, einen Pfad, der auf eine Datei aufgelöst wird, die für die Ausführungsidentität des Scanners lesbar ist, sowie einen Bericht oder ein Log, das ein Benutzer mit geringeren Rechten lesen kann. Ein Zertifikatsfeld oder ein installierter Scanner allein belegt diese Kette nicht. Prüfe bei einer passiven Enumeration den Zeitplan, das Skript, die Pfadauflösung und das Berichtsziel, ohne ein neues Ziel zu scannen.

Ein privilegierter Cron-Befehl, der einen Shell-Glob wie `/path/to/tasks/*.yml` an einen Ansible-Runner übergibt, verdient eine Prüfung der Verzeichnisberechtigungen, selbst wenn alle vorhandenen Playbooks nur lesend arbeiten. Ein Benutzer mit Schreib- und Suchzugriff auf das vom Glob erfasste Verzeichnis kann möglicherweise ein weiteres passendes Playbook erstellen. [Ansible-Playbooks definieren Tasks, die der Runner ausführt](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), aber ein benutzerdefinierter Wrapper kann Pfade filtern oder eine andere Identität verwenden. Überprüfe dessen Verhalten, den tatsächlichen Cron-Benutzer, die Shell-Expansion, ACLs, das Sticky Bit und die Mount-Richtlinien, bevor du das Verzeichnis als Ausführungspfad einstufst. Prüfe Metadaten und Wrapper statisch; führe den geplanten Job bei der Enumeration nicht aus.

Ein privilegierter Cron-Wrapper kann Dateinamen aus einem Upload-Verzeichnis nach der Expansion eines Glob an einen Perl-Helfer übergeben. Perl verwendet beim [`<>`-Diamond-Operator ein `open` mit zwei Argumenten](https://perldoc.perl.org/perlop#The-Null-Filehandle); ein passender Dateiname, der als Pipe-Befehl interpretiert wird, kann daher unter der Identität des Helfers ausgeführt werden. [`<<>>` behandelt Argumente als literale Dateinamen](https://perldoc.perl.org/perlop#The-Null-Filehandle). Bestätige die Scheduler-Identität, das Arbeitsverzeichnis und den Glob des Wrappers, die tatsächliche `@ARGV`-Verarbeitung des Helfers, die Namensbeschränkungen und ob eine Identität mit geringeren Rechten über Dateisystemrechte oder einen authentifizierten Upload-Dienst einen passenden Namen anlegen kann. Eine Cron-Zeile, ein Perl-Skript oder ein beschreibbares FTP-Verzeichnis allein belegen nicht die gesamte Kette. Prüfe bei der Enumeration Quellcode und Metadaten, ohne einen präparierten Dateinamen einzureichen oder den Job auszuführen.

Ein schreibgeschütztes Cron-Skript lässt sich dennoch ersetzen, wenn das geplante Konto es anhand seines Pfads ausführt und ein Benutzer mit geringeren Rechten das nicht mit Sticky Bit geschützte übergeordnete Verzeichnis beschreiben und durchqueren kann. Prüfe die Ausführungsidentität des Zeitplans, alle Pfadkomponenten, das Sticky Bit des Verzeichnisses, ACLs und Mount-Richtlinien. Prüfe die Metadaten, ohne die Datei zu verschieben oder den Job auszuführen.

Ein privilegierter PHP-Cron-Wrapper kann einen Helfer aufrufen, der noch nicht existiert. Ruft er PHPs [`exec()`](https://www.php.net/manual/en/function.exec.php) mit einem festgelegten absoluten Helferpfad auf, kann ein Benutzer mit geringeren Rechten, der diesen Namen im übergeordneten Verzeichnis erstellen kann, kontrollieren, was bei einem späteren Lauf ausgeführt wird. Bestätige, dass der Cron-Eintrag den Wrapper tatsächlich unter der höheren Identität ausführt, den exakten Befehlsstring und die PHP-Ausführungsrichtlinie, Schreib- und Suchrechte für das Helferverzeichnis, das Verhalten von Symlinks und Sticky Bit sowie, ob der Helferpfad noch nicht existiert. Ein beschreibbares Verzeichnis oder ein fehlender Helfer allein ist nur ein Hinweis. Prüfe bei der Enumeration den Zeitplan, den Quellcode und die Pfadmetadaten, ohne den Helfer zu erstellen oder den Job auszulösen.

Ein geplanter Job kann Eingabe-Skripte auch mit `find` ermitteln und jedes davon an einen Interpreter übergeben. Beispielsweise ruft [gnuplots `system()`-Funktion eine Shell auf](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf). Ein privilegierter Job, der `gnuplot` für jede `*.plt`-Datei in einem von einem Benutzer mit geringeren Rechten beschreibbaren Verzeichnis ausführt, kann daher Befehle mit der Identität des Jobs ausführen. [Leseberechtigung für ein Verzeichnis kontrolliert die Auflistung, Schreib- und Suchberechtigung (`x`) kontrollieren das Erstellen und den Zugriff auf bekannte Namen](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html). Prüfe Schreib- und Suchzugriff auch dann, wenn `ls` das Verzeichnis nicht auflisten kann. Gleiche die exakte Scheduler-Identität und den Befehl, das Verhalten des Interpreters, das ausgewählte Dateimuster und die Verzeichnisberechtigungen ab. Ein beschreibbares Verzeichnis oder ein installierter Interpreter allein belegt keine Rechteausweitung. Private Zeitpläne und kurzlebige Jobs können eine autorisierte Ereignisbeobachtung erfordern, weil eine einzelne Prozessaufnahme sie möglicherweise verpasst.

Prüfe bei einem privilegierten PHP-Job auch literale `include`-/`require`-Anweisungen als Teil der ausführbaren Skriptkette. [PHP wertet eingebundene Dateien aus](https://www.php.net/manual/en/function.include.php); daher kann eine gruppenbeschreibbare eingebundene `.php`-Datei Code mit der Identität des Jobs ausführen, selbst wenn das Hauptskript schreibgeschützt ist. Überprüfe die geplante Identität, die effektive Auflösung des Include-Pfads, Datei- und Verzeichnisberechtigungen sowie, ob der Job tatsächlich ausgeführt wird. Eine beispielhafte Cron-Zeile in einem Kommentar ist nur ein Hinweis. Dieselbe Prüfung gilt für einen root-eigenen [PHP-Built-in-Server](https://www.php.net/commandline.webserver), der mit `-S` und `-t <document-root>` gestartet wird: Auch ein Loopback-Listener kann bei lokalen Anfragen Anwendungs-PHP ausführen. Prüfe bei der Enumeration Prozess und Quellcode, ohne einen der beiden Trigger aufzurufen.

Ein privilegierter PHP-Job kann die Grenze auch über eine **Datendatei** überschreiten: Kann ein Benutzer mit geringeren Rechten genau die Datei ändern, die an [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) übergeben wird, kann PHP beim Wiederherstellen eines Objekts die Methode `__wakeup()` oder `__unserialize()` einer geladenen Klasse aufrufen. Prüfe die effektive Identität des Jobs, die Berechtigungen der Datei und ihrer übergeordneten Verzeichnisse, die geladenen Klassen und die tatsächlichen Nebenwirkungen der Methoden, etwa einen durch eine Eigenschaft ausgewählten Dateischreibvorgang. Ein beschreibbares Log oder ein Aufruf von `unserialize()` allein belegt keinen nutzbaren Pfad. Prüfe bei der Enumeration Quellcode und Metadaten, ohne serialisierten Input zu schreiben oder den Job auszuführen.

Ein Root-Cron-Task kann statt des Webservers einen PHP-Anwendungs-**CLI-Seiten-Runner** aufrufen. Verfolge das vom Runner ausgewählte Dokumentenverzeichnis und den URI bis zum tatsächlichen PHP-Einstiegspunkt. Ist dieser Einstiegspunkt für das Konto des Webdienstes beschreibbar, kann die geplante CLI-Anfrage den geänderten Code als root ausführen, selbst wenn Runner und Cron-Wrapper schreibgeschützt sind. Bestätige die Scheduler-Identität, die exakte Auflösung von URI zu Datei, die effektiven Berechtigungen der Datei und ihrer übergeordneten Verzeichnisse sowie, ob eine Integritätsprüfung den Einstiegspunkt selbst schützt. Prüfe bei der Enumeration Quellcode und Metadaten, ohne den Runner aufzurufen oder die Seite zu ändern.

Ein `ipython`-Prozess, der von einem geplanten Job oder einem anderen Benutzer aus einem gemeinsam genutzten Arbeitsverzeichnis gestartet wird, verdient eine Prüfung der Startup-Dateien. [IPythons Security-Release-Hinweise](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) erläutern, dass betroffene Builds vor der Behebung von CVE-2022-21699 im aktuellen Verzeichnis nach Profilen und Konfigurationen, einschließlich Code unter `profile_default/startup`, suchten. Gleiche den tatsächlich installierten Build oder Vendor-Patch, das Arbeitsverzeichnis des Befehls, die Identität des privilegierten Prozesses und die Möglichkeit des Benutzers mit geringeren Rechten ab, den exakten Startup-Pfad zu beschreiben und zu durchsuchen. Ein installiertes `ipython`, ein beschreibbares Verzeichnis oder eine Versionszeichenfolge allein beweist nicht, dass eine andere Identität dort eine Datei lädt. Prüfe bei der Enumeration den Zeitplan und die Pfadmetadaten, ohne den privilegierten Interpreter zu starten.

Wenn ein privilegierter PHP-Server Funktionen aus einer benutzerdefinierten nativen Erweiterung aufruft, verfolge vor der Prüfung der Erweiterung das PHP-SAPI des Dienstes und dessen effektive `php.ini` sowie eingelesene `.ini`-Dateien. [PHP lädt beim Start konfigurierte `extension`-Bibliotheken](https://www.php.net/manual/en/ini.core.php), und [CLI- und Web-SAPIs können unterschiedliche Konfigurationsdateien verwenden](https://www.php.net/manual/en/configuration.file.php). Ein erreichbares Anmeldeformular oder ein lokaler Listener kann daher vom Benutzer kontrollierte Zeichenfolgen an kompilierten Code übergeben, der mit der Identität des Dienstes läuft. Halte `User=`, `ExecStart=`, das Arbeitsverzeichnis, den tatsächlichen Erweiterungspfad und die vom Aufrufer kontrollierbaren Argumente der Unit fest. Das bloße Vorhandensein einer `.so`-Datei oder eines Loopback-Sockets belegt keinen Memory-Corruption-Fehler. Analysiere einen benutzerdefinierten Parser separat, statt bei einer passiven Enumeration Probes zu senden.

Wenn ein privilegierter Wrapper ein Skript anhand seines Pfads hasht und denselben Pfad später erneut zur Ausführung öffnet, authentifiziert der Digest nur das Objekt, das beim ersten Öffnen gelesen wurde. Kann ein Benutzer mit geringeren Rechten den Verzeichniseintrag des Skripts zwischen diesen Öffnungen ersetzen, kann die spätere Ausführung ein anderes Objekt auflösen, selbst wenn die ursprüngliche Skriptdatei root gehört. Eine FIFO kann die Prüfphase verlängern, aber der Pfad hängt von ersetzbaren Berechtigungen der übergeordneten Verzeichnisse, tatsächlich separaten Öffnungen, der Scheduler-Identität, Sticky-Bit- und Mount-Regeln sowie dem Timing ab. Prüfe den Wrapper und die Ausgabe von `namei -l` als passiven Hinweis. Ein erfolgreicher Checksum allein beweist nicht, dass der spätere Pfad geschützt ist.

Ein privilegierter Backup-Job kann Daten auch **offenlegen**, ohne vom Angreifer bereitgestellte Befehle auszuführen. Verfolge, ob ein Benutzer mit geringeren Rechten eine Steuerdatei erstellen kann, die der Job einliest, ob der Job anschließend eine geschützte Quelle wie `/etc/shadow` öffnet und ob ein vom Angreifer ausgewählter URL oder eine lesbare Ausgabe das Ergebnis erhält. Überprüfe alle drei Teile, bevor du von einem Offenlegungspfad sprichst. Ein fester Shell-Befehl im selben Skript macht diese Steuerdatei nicht automatisch zu einem Shell-Injection-Input. Prüfe bei der Enumeration Skript und Dateiberechtigungen, ohne den Job auszuführen oder eine Steuerdatei anzulegen.

Wenn ein privilegierter geplanter Job `curl -K FILE` oder `curl --config FILE` ausführt, [behandelt curl Optionen in dieser Datei wie Kommandozeilenargumente](https://curl.se/docs/manpage.html). Ein Benutzer mit geringeren Rechten, der genau die Datei kontrolliert, wenn curl sie einliest, kann die angeforderte URL, lokale Datei-Eingaben oder den Ausgabepfad beeinflussen. Bestätige die effektive Identität des Jobs, Schreibrechte für die Datei und ihre übergeordneten Verzeichnisse, den Zeitpunkt eines anderen Jobs, der die Datei ersetzt, sowie die Auswirkungen der Konfigurationsoptionen im Zusammenspiel mit festen Kommandozeilenoptionen, bevor du einen geschützten Lese- oder Schreibzugriff behauptest. Ein beschreibbarer Konfigurationspfad oder ein sichtbares `-K`-Flag allein belegt nicht, dass die gewählten Optionen greifen. Prüfe bei einer passiven Enumeration den Zeitplan und die Metadaten, ohne den Job auszuführen oder eine URL abzurufen.

Wenn ein Cron-Eintrag ein Hilfsskript aufruft, prüfe auch das Arbeitsverzeichnis und den Archivbefehl des Helfers. Ein nicht in Anführungszeichen gesetzter Wildcard über ein Verzeichnis, das ein anderer Benutzer beschreiben kann, kann Dateinamen in Archiver-Optionen verwandeln; Checkpoint-Aktionen von GNU tar sind ein Beispiel. Bestätige die geplante Ausführungsidentität, das beschreibbare Eingabeverzeichnis, den genauen Archiver und seine Optionen sowie, ob `--` die Optionsauswertung beendet, bevor du einen benutzerübergreifenden Befehlsausführungspfad behauptest. Siehe [wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md).

Eine separate Offenlegung über Backup-Dateien kann entstehen, wenn ein privilegierter Helfer `cd INPUT_DIR; tar ... *` ausführt, ohne zu prüfen, ob `cd` erfolgreich war. Kann ein Benutzer mit geringeren Rechten `INPUT_DIR` entfernen oder ersetzen, kann ein fehlgeschlagenes `cd` die Shell im vorherigen Verzeichnis belassen, aus dem der spätere Archivbefehl dann Dateien lesen kann. Überprüfe das anfängliche Arbeitsverzeichnis des Jobs, einen tatsächlich möglichen fehlgeschlagenen `cd`-Pfad, ob das Skript beendet wird oder `&&` verwendet, die genauen Archiver-Optionen und ob der Benutzer mit geringeren Rechten das Ausgabe-Archiv lesen kann. Ein beschreibbares Eingabeverzeichnis oder ein lesbares Archiv allein ist nur ein Hinweis. Prüfe den Helfer und die Pfadberechtigungen, ohne den laufenden Job zu ändern.

Eine geplante ausführbare Datei kann ein Shell-Skript verbergen, statt dessen Vertrauensgrenze zu beseitigen: [SHc](https://github.com/neurobin/shc) verpackt verschlüsselten Skripttext in eine native Binärdatei und führt ihn zur Laufzeit über eine Shell aus. Ein Suffix wie `.sh.x` oder ein undurchsichtiges ELF ist nur ein Prüfhinweis. Um eine Option Injection über Dateinamen zu beurteilen, ermittle die privilegierte Scheduler-Identität, das tatsächliche Arbeitsverzeichnis und den Befehl des Helfers, die Möglichkeit eines Benutzers mit geringeren Rechten, dort passende Namen anzulegen, und ob ein nicht gequoteter Glob ohne Optionsbegrenzung einen Befehl wie `rsync` erreicht. Die [`rsync`-Remote-Shell-Option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) ist nur relevant, wenn genau dieser Befehlspfad verwendet wird. Eingeschränkte Sichtbarkeit von `/proc` oder eine fehlgeschlagene statische Entschlüsselung lassen den Befehl unbekannt; führe den privilegierten Helfer nicht allein aus, um ihn einzuordnen.

Text in der Prozesskommandozeile ist eine weitere nicht vertrauenswürdige Eingabe für einen privilegierten Helfer. Ein Benutzer mit geringeren Rechten kann einen Prozesstitel oder `argv[0]` wählen, der auf `pgrep -f` passt; ein passender Name authentifiziert weder die ausführbare Datei noch ihren Eigentümer. Wenn ein als root laufendes Skript diesen Text erfasst, Teile davon in `apache2ctl`/`httpd` umschreibt und das Ergebnis ohne festes Argument-Array ausführt, können vom Angreifer gewählte Optionen ein anderes Konfigurationsverzeichnis oder Fehlerlog auswählen. Der Apache-Konfigurationsparser kann Module laden oder konfigurierte Helfer erreichen. Prüfe daher bei der Enumeration keine nicht vertrauenswürdige Konfiguration als root. Prüfe den Eigentümer des Schedulers, den exakten Helfer, die Prozessidentität und den Datenfluss zu den Argumenten. Das ist Option-/Konfigurations-Injection, sofern Shell-Metazeichen-Ausführung nicht separat nachgewiesen wird.

Ein als root laufender Parser, der nicht vertrauenswürdigen Text in Bash-Arithmetik einspeist, kann Substitutionen in diesem Text ausführen. Der [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) enthält ein ausgearbeitetes Beispiel. Bestätige die Eingabequelle und den Parsing-Befehl, bevor du jeden arithmetischen Ausdruck als ausnutzbar einstufst.

Verfolge bei einem privilegierten Job, der ein Anwendungslog parst, nicht vertrauenswürdige Felder über den ersten Parse hinaus. Ein Benutzer mit geringeren Rechten kann möglicherweise über seine aktuelle Prozessgruppe in das Log schreiben oder protokollierte Request-Felder beeinflussen. Ein Eintrag kann dann ein Bild auswählen, dessen Metadaten zu einem zweiten Pfad werden, über den eine XML-Datei geöffnet wird. Prüfe die effektive Identität des Jobs, den tatsächlichen Schreibzugriff auf das Log, die Behandlung von Trennzeichen, die kanonische Pfadbegrenzung und ob das ausgewählte XML vom Angreifer kontrolliert wird. Die Auflösung externer Entitäten kann zur Offenlegung privilegierter Dateien führen, wenn das erweiterte Ergebnis in einer für einen Benutzer mit geringeren Rechten lesbaren Ausgabe landet. Der [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) dokumentiert Kontrollen für den Zugriff auf externe DTDs/Entitäten. Prüfe den installierten Parser und seine effektiven Einstellungen. Ein beschreibbares Log oder eine XML-Datei allein ist nur ein Hinweis. Prüfe Code und Metadaten, ohne den geplanten Parser bei der Enumeration mit Eingaben zu versorgen.

Prüfe außerdem privilegierte Jobs, die Dateien aus dem Git-Repository eines anderen Benutzers erstellen. Ein Skript kann `git ls-tree` und `git cat-file` statt `git checkout` verwenden und dennoch vom Angreifer kontrollierten Tree-Pfaden vertrauen, wenn es sie mit einem Staging-Verzeichnis verknüpft. Absolute Pfade und `..`-Komponenten können dieses Verzeichnis verlassen, sofern das Ziel vor dem Schreiben nicht normalisiert und auf Containment geprüft wird. `git -c safe.directory=*` erlaubt den Zugriff auf Repositories mit anderen Eigentümern; dadurch entsteht für sich genommen keine beliebige Schreibmöglichkeit.

Ein als root ausgeführtes Datenbank-Backup kann eine weitere Eigentumsgrenze schaffen. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) kopiert zusätzliche reguläre Dateien im Quelldatenverzeichnis. Das Standardformat `plain` schreibt Dateien aus `-D` als Verzeichnisbaum. Kann ein Benutzer mit geringeren Rechten diese Quelldateien erstellen oder ändern, prüfe den Eigentümer und Modus der resultierenden Dateien im Ziel, ob der Pfad durchquert und ausgeführt werden kann und ob der Mount `nosuid` verwendet. Eine root-eigene Kopie mit beibehaltenen set-ID-Berechtigungen kann gefährlich sein; ein reines Tar-Backup, entfernte Berechtigungen oder ein unzugängliches Ziel belegen nicht denselben Pfad. Verfolge den geplanten Wrapper und den effektiven Benutzer, bevor du den Backup-Befehl als Finding einstufst.

## Kurzlebige Arbeit beobachten

Eine einzelne Prozessaufnahme kann einen Job verpassen, der nur Millisekunden läuft. Vergleiche Timer-/Cron-Deklarationen mit Logs und, sofern autorisiert, mit der Prozessereignisüberwachung wie `pspy` oder Audit. Gleiche den geplanten Eigentümer, die exakte Kommandozeile und die Dateien ab, die der Task liest oder schreibt. Eine Loopback-Web-UI für den Scheduler ist eine separate Schnittstelle; siehe das [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
