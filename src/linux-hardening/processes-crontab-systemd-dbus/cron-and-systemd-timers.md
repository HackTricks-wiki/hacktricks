# Cron Jobs e Timers do Systemd

{{#include ../../banners/hacktricks-training.md}}

Tarefas agendadas podem ser executadas com uma identidade e um ambiente diferentes dos do shell atual. Enumere cron, `at`, anacron e timers do systemd; em seguida, rastreie cada comando agendado por seus scripts, imports, diretório de trabalho e entradas graváveis.

## Enumerar agendamentos

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

As crontabs do sistema geralmente incluem um campo de usuário; a crontab de um usuário não. Inspecione o PATH efetivo e o ambiente do scheduler real. `run-parts --test /etc/cron.daily` mostra quais nomes de arquivos seriam selecionados nesse host. Caracteres de controle podem ocultar uma entrada na saída casual; portanto, use `cat -A` ou `sed -n l` quando uma programação parecer suspeita.

## Rastrear a resolução de arquivos e comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revise cadeias de scripts graváveis, caminhos `EnvironmentFile=`, drop-ins, symlinks, comandos relativos, expansão de curingas e binários copiados ou executados por uma tarefa privilegiada. Um timer pode ativar um serviço com outro nome por meio da configuração `Unit=`. As páginas [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explicam os principais primitivos.

Para um script `chkrootkit` agendado para executar como root, inspecione o código-fonte instalado em busca do antigo [defeito de aspas no slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): um `file_port=$file_port $i` sem aspas, após uma verificação de um caminho temporário `SLAPPER_FILES`, pode executar esse arquivo. Verifique o script real ou o patch do fornecedor, o agendamento como root, o acesso de escrita de um usuário menos privilegiado ao caminho temporário exato, se ele é executável e a política de montagem. Uma versão ou apenas a presença do `chkrootkit` não comprova esse caminho; não crie nem execute um arquivo temporário durante uma revisão passiva.

Siga mais um salto de unidade quando o serviço root de um timer executa `systemctl restart <other>.service`: a unidade reiniciada pode invocar um shell com um script gravável por um usuário menos privilegiado. Confirme `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, os argumentos exatos de `ExecStart=` e as permissões do script e do caminho até ele. Um script gravável só é um candidato até que o timer e o serviço reiniciado estejam ativos nesse contexto de execução; inspecione as propriedades da unidade sem reiniciar nenhum dos serviços.

Se uma tarefa de privilégio mais alto busca um script por nome de host e passa a resposta a um shell, verifique quem controla a resolução desse nome, além do script remoto. Um arquivo `/etc/hosts` gravável, inclusive por permissões concedidas via grupo ou ACL, pode redirecionar um nome que a tarefa resolve localmente; uma resposta de `curl` só se torna um caminho de execução entre usuários quando o comando agendado realmente a executa e a tarefa usa o caminho de resolução afetado. Verifique a identidade de execução da tarefa, a URL exata e o pipeline do shell, o comportamento efetivo de proxy/DNS e as permissões do arquivo e do diretório pai. Um arquivo hosts gravável, por si só, é um indício para revisão, não prova que exista um consumidor privilegiado. Inspecione o agendamento e os metadados sem alterar o mapeamento nem buscar o script durante a enumeração.

Uma busca privilegiada agendada com `wget` constitui um limite separado de gravação de arquivos, mesmo que o conteúdo baixado nunca seja executado diretamente. [GNU Wget 1.18 alterou o tratamento padrão do nome de arquivo em redirecionamentos HTTP para FTP, corrigindo CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); versões antigas afetadas podiam usar o nome de arquivo do FTP redirecionado, enquanto `--trust-server-names` solicita explicitamente esse comportamento. Se uma parte de menor confiança controla a resposta HTTP e o recurso FTP, verifique se a tarefa segue esse redirecionamento, a versão real do Wget ou o backport do fornecedor, as opções de saída, a identidade de execução, o diretório de trabalho e se o nome de destino pode se tornar um arquivo de inicialização. [Wget carrega `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), e [suas configurações podem selecionar uma origem POST ou um caminho de saída](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); uma busca privilegiada posterior é um requisito distinto para qualquer divulgação ou gravação resultante. O acesso a uma porta baixa por meio de `authbind` só é relevante quando o chamador pode realmente servir a URL solicitada pela tarefa. Revise a configuração e os logs passivamente, sem servir um redirecionamento nem executar a tarefa. [O acesso bruto a dispositivos de bloco pelo grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) é independente desse caminho de busca pela rede.

Siga também os arquivos de dados, não apenas os scripts. Uma ferramenta de simulação ou orquestração agendada pode ler um arquivo YAML que define processos a iniciar; se um usuário menos privilegiado puder editar esse arquivo e a tarefa o executar sob outra conta, os dados podem se tornar comandos executados com a identidade da tarefa. Verifique o comando agendado exato, o usuário efetivo, o caminho do arquivo, a semântica do parser e o acesso de escrita (inclusive aos diretórios pais) antes de considerar um YAML gravável um caminho de execução. Ler o agendamento e os metadados do arquivo é suficiente para uma triagem passiva; não execute a tarefa nem modifique sua entrada durante a enumeração.

A configuração de um cliente SSH também é uma entrada executável quando uma tarefa de privilégio mais alto executa `ssh -F` com um arquivo que um usuário menos privilegiado pode substituir. O [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) do OpenSSH executa um comando local por meio do shell do cliente, enquanto `Host`/`Match` e as opções anteriores determinam se essa diretiva se aplica. Correlacione a invocação SSH agendada exata, a identidade de execução, o caminho de configuração selecionado, as permissões de escrita no arquivo e no diretório e a ordem efetiva das opções antes de classificar isso como um caminho de execução entre usuários. Revise esses registros sem executar a tarefa nem carregar a configuração não confiável como a conta privilegiada.

Um `scp` agendado seguido de `ssh` para executar o script copiado exige uma segunda revisão do limite de confiança quando um usuário menos privilegiado controla o serviço SSH de destino. Se esse serviço puder encaminhar a conexão para outro host, o cliente privilegiado pode se autenticar em um endpoint não pretendido; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) enfraquece a proteção contra alterações na chave do host, sujeito às restrições restantes do OpenSSH e às opções efetivas por host. Determine a identidade de execução da tarefa, o destino real e o método de autenticação, a identidade efetiva do comando remoto e se o mesmo caminho de destino é gravável ou já existe no host redirecionado. A execução de um arquivo antigo ou controlado por um invasor também exige que a cópia falhe ou não encontre esse caminho **e** que o wrapper prossiga para o comando SSH; [`errexit` do Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e o tratamento explícito do status afetam esse fluxo. Uma configuração fraca da chave do host, um processo `sshpass` visível ou um diretório temporário gravável, por si só, não comprovam essa cadeia. Inspecione o agendamento, o script, a configuração SSH e os metadados dos arquivos sem redirecionar o serviço nem disparar a tarefa durante a enumeração.

Um scheduler de aplicações privilegiado pode obter suas tarefas de linhas de banco de dados em vez de arquivos graváveis. Por exemplo, uma entrada cron de root que invoca [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) do Laravel pode chegar a código da aplicação que lê linhas de tarefas. Se uma conta menos privilegiada puder gravar uma linha contendo um caminho local e o callback agendado chamar o [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) do PHP como root e enviar o corpo retornado a um webhook escolhido pela linha, isso constitui um caminho privilegiado de divulgação de arquivos. Verifique a identidade do cron, o callback real do scheduler e o fluxo de dados da linha ao caminho, a autorização de escrita no banco de dados, a validação após a leitura da linha e o destino de saída. Um `.env` da aplicação legível é apenas uma pista de credenciais; validação por formulário web ou uma senha de banco de dados, por si só, não comprovam controle da linha nem divulgação. Inspecione passivamente o agendamento, o código e as permissões dos arquivos de credenciais, sem consultar o banco de dados nem agendar uma tarefa durante a enumeração.

Tarefas orientadas a eventos do `incron` merecem a mesma revisão: [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associam um caminho monitorado e um evento a um comando executado com a identidade do proprietário da tabela. Um usuário menos privilegiado pode influenciar indiretamente um arquivo monitorado quando uma aplicação segue um link de um diretório gravável e grava texto controlado pelo invasor no destino monitorado. Verifique o proprietário real da tabela, o evento, o destino e as permissões dos diretórios ancestrais, o comportamento da aplicação ao seguir links e como esse texto se torna argumentos de comando. Em particular, o [`mail` do GNU Mailutils aceita `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), e seu [comando de escape para o shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) pode executar um programa; um campo não confiável passado como opção separada para essa implementação pode chegar à execução de comandos. Outras implementações de `mail` ou um limite de argumentos fixo e entre aspas podem se comportar de outra forma. Inspecione o agendamento, o código da aplicação e os metadados dos arquivos sem modificar o arquivo monitorado nem disparar a tarefa durante a enumeração.

Um log monitorado também pode cruzar um limite entre usuários por meio de um script auxiliar. Se uma conta menos privilegiada puder gravar no log e o proprietário do `incron` ler um campo dele para inseri-lo em uma nova string de comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), o shell analisará esse campo novamente com a identidade do proprietário. Verifique o evento monitorado exato, as permissões do log e dos diretórios pais, o caminho do auxiliar, a transformação do campo do log e se o comando resultante é alcançado. A existência de um log gravável e de uma entrada `incron`, por si só, não comprova o fluxo de dados; não escreva uma linha de disparo nem execute o auxiliar durante uma enumeração passiva.

Tarefas de renovação de certificados podem cruzar o mesmo limite. Um auxiliar privilegiado pode ler um subject X.509 de um certificado em um diretório gravável por um usuário menos privilegiado e inserir o common name em uma nova string de comando `bash -c`. [O OpenSSL pode exibir o subject de um certificado e verificar sua expiração](https://docs.openssl.org/3.3/man1/openssl-x509/); [o Bash analisa a string `-c` como entrada do shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), portanto, colocar a variável entre aspas no script externo não protege a segunda análise. Confirme a identidade agendada, o caminho exato de entrada e os direitos de escrita, o ramo de renovação e o fluxo de dados até `bash -c` antes de classificar isso como injeção de comandos. Inspecione passivamente o script e os metadados do certificado; não dispare a renovação durante a enumeração.

A mesma segunda análise pode ocorrer quando uma tarefa privilegiada agendada extrai um nome de um arquivo ou pacote de um usuário menos privilegiado e o envia a `xargs -I` para inserção em uma string de comando `sh -c`. [`xargs -I` do GNU substitui o marcador nos argumentos iniciais](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), e [`sh -c` interpreta sua string de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Mesmo que o script externo coloque o nome extraído entre aspas, isso não torna seguro um programa de shell substituído posteriormente. Verifique a identidade de execução da tarefa, o caminho exato de entrada aceito e o acesso de escrita, a validação do arquivo e as condições do ramo, além do fluxo do nome até o shell. Um diretório de upload gravável ou uma invocação de `xargs`, por si só, é apenas uma pista; inspecione o agendamento, o script e os metadados do caminho sem enviar um pacote nem executar a tarefa durante a enumeração.

Um importador agendado de fontes ou imagens também pode confiar nos nomes *dentro* de um arquivo fornecido pelo chamador, mesmo quando o nome externo do upload é restrito. O FontForge corrigiu a injeção de comandos por nomes de membros de arquivo na [alteração upstream para CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirme que uma tarefa de privilégio mais alto realmente abre um arquivo de um caminho gravável por um usuário menos privilegiado, a identidade de execução, a versão exata do FontForge ou o backport do fornecedor e o caminho do código que trata o arquivo. Uma versão ou apenas uma extensão de upload permitida não comprova execução. Inspecione o agendamento, as permissões do caminho e os metadados da versão sem importar um arquivo não confiável durante a enumeração.

Scanners de rede agendados podem cruzar outro limite quando um script personalizado trata o subject de um certificado TLS remoto como nome de arquivo local. [O Nmap NSE executa scripts selecionados sem sandbox](https://nmap.org/book/nse-usage.html), portanto, inspecione o script real e verifique se ele combina um campo subject não confiável com um diretório de dados sem verificações de contenção. A divulgação de arquivos exige um destino que o scheduler vá examinar, um caminho que corresponda a um arquivo legível pela identidade de execução do scanner e um relatório ou log entregue a um leitor menos privilegiado. Um campo de certificado ou apenas um scanner instalado não comprovam essa cadeia; revise o agendamento, o script, a resolução do caminho e o destino do relatório sem examinar um novo destino durante uma enumeração passiva.

Um comando cron privilegiado que passa um glob de shell como `/path/to/tasks/*.yml` a um runner do Ansible merece uma verificação das permissões do diretório, mesmo quando todos os playbooks existentes são somente para leitura. Um usuário com acesso de escrita e busca ao diretório abrangido pelo glob pode conseguir criar outro playbook correspondente. [Playbooks do Ansible definem tarefas que o runner executa](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mas um wrapper personalizado pode filtrar caminhos ou usar outra identidade: verifique seu comportamento, o usuário real do cron, a expansão do shell, as ACLs, o sticky bit e a política de montagem antes de considerar o diretório um caminho de execução. Inspecione estaticamente os metadados e o wrapper; não execute a tarefa agendada durante a enumeração.

Um wrapper cron privilegiado pode passar nomes de arquivos de um diretório de upload a um auxiliar Perl após expandir um glob. O operador [`<>` diamond do Perl usa `open` com dois argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), portanto, um nome correspondente interpretado como comando de pipe pode ser executado com a identidade do auxiliar; [`<<>>` trata os argumentos como nomes de arquivo literais](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirme a identidade do scheduler, o diretório de trabalho e o glob do wrapper, o tratamento real de `@ARGV` pelo auxiliar, as restrições de nomes de arquivos e se uma identidade menos privilegiada pode inserir um nome correspondente por meio das permissões do sistema de arquivos ou de um serviço de upload autenticado. Uma linha cron, um script Perl ou um diretório FTP gravável, por si só, não comprovam a cadeia completa. Inspecione o código-fonte e os metadados sem enviar um nome de arquivo especialmente criado nem executar a tarefa durante a enumeração.

Um script cron somente para leitura ainda pode ser substituído se a conta agendada o executar por caminho e o usuário menos privilegiado puder escrever e atravessar seu diretório pai sem sticky bit. Verifique a identidade de execução do agendamento, cada componente do caminho, o sticky bit do diretório, as ACLs e a política de montagem; revise os metadados sem mover o arquivo nem executar a tarefa.

Um wrapper cron PHP privilegiado pode chegar a um auxiliar que ainda não existe. Se ele chamar o PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) com um caminho absoluto fixo para o auxiliar, um usuário menos privilegiado que possa criar esse nome no diretório pai pode controlar o que uma execução posterior executará. Confirme que a entrada cron realmente executa o wrapper com a identidade de privilégio mais alto, a string de comando exata e a política de execução do PHP, os direitos de escrita e busca no diretório do auxiliar, o comportamento de symlinks e sticky bit e se o caminho do auxiliar ainda está ausente. Um diretório gravável ou um auxiliar ausente, por si só, é apenas uma pista; inspecione o agendamento, o código-fonte e os metadados do caminho sem criar o auxiliar nem disparar a tarefa.

Uma tarefa agendada também pode localizar scripts de entrada com `find` e passar cada um a um interpretador. Por exemplo, a função `system()` do [gnuplot invoca um shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), portanto, uma tarefa privilegiada que executa `gnuplot` em todos os arquivos `*.plt` de um diretório gravável por um usuário menos privilegiado pode executar comandos com a identidade da tarefa. [A permissão de leitura de diretório controla a listagem, enquanto escrita e busca (`x`) controlam a criação e o acesso a nomes conhecidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); verifique o acesso de escrita e busca mesmo quando `ls` não consegue listar o diretório. Correlacione a identidade e o comando exatos do scheduler, o comportamento do interpretador, o padrão de arquivos selecionado e as permissões do diretório; um diretório gravável ou um interpretador instalado, por si só, não comprovam escalonamento de privilégios. Agendamentos privados e tarefas de curta duração podem exigir observação autorizada de eventos, pois uma única captura de processos pode não detectá-los.

Para uma tarefa PHP privilegiada, inspecione as instruções literais `include`/`require` como parte da cadeia de scripts executáveis. [O PHP avalia os arquivos incluídos](https://www.php.net/manual/en/function.include.php), portanto, um arquivo `.php` gravável por grupo pode executar código com a identidade da tarefa mesmo quando o script principal é somente para leitura. Verifique a identidade agendada, a resolução efetiva do include-path, as permissões do arquivo e dos diretórios e se a tarefa realmente é executada; uma linha cron de exemplo em um comentário é apenas uma pista. A mesma revisão se aplica a um [servidor integrado do PHP](https://www.php.net/commandline.webserver) pertencente a root e iniciado com `-S` e `-t <document-root>`: um listener em loopback ainda pode executar PHP da aplicação para requisições locais. Inspecione o processo e o código-fonte sem acionar nenhum dos dois gatilhos durante a enumeração.

Uma tarefa PHP privilegiada também pode cruzar o limite por meio de um **arquivo de dados**: se um usuário menos privilegiado puder alterar o arquivo exato passado a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), o PHP poderá invocar o método `__wakeup()` ou `__unserialize()` de uma classe carregada ao restaurar um objeto. Revise a identidade efetiva da tarefa, as permissões do arquivo e dos diretórios ancestrais, as classes carregadas e os efeitos colaterais reais dos métodos, como a gravação de um arquivo selecionado por uma propriedade. Um log gravável ou uma chamada a `unserialize()`, por si só, não comprova um caminho utilizável. Inspecione o código-fonte e os metadados sem gravar entrada serializada nem executar a tarefa durante a enumeração.

Uma tarefa cron de root pode invocar um **executor de páginas CLI** de uma aplicação PHP em vez do servidor web. Siga o document root e o URI selecionados pelo executor até o ponto de entrada PHP real; se a conta do serviço web puder gravar nesse ponto de entrada, a requisição CLI agendada poderá executar o código alterado como root, mesmo que o executor e o wrapper cron sejam somente para leitura. Confirme a identidade do scheduler, a resolução exata do URI para o arquivo, as permissões efetivas do arquivo e dos diretórios ancestrais e se uma verificação de integridade protege o ponto de entrada. Inspecione o código-fonte e os metadados sem invocar o executor nem alterar a página durante a enumeração.

Um processo `ipython` iniciado por uma tarefa agendada ou por outro usuário a partir de um diretório de trabalho compartilhado merece uma revisão dos arquivos de inicialização. As [notas de segurança do IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explicam que as versões afetadas procuravam perfis e configurações no diretório atual, incluindo código em `profile_default/startup`, antes da correção de CVE-2022-21699. Correlacione a versão instalada real ou o patch do fornecedor, o diretório de trabalho do comando, a identidade do processo de privilégio mais alto e a capacidade do usuário menos privilegiado de gravar e buscar o caminho exato de inicialização. A presença do `ipython`, de um diretório gravável ou apenas de uma versão não prova que outra identidade carregará um arquivo dali. Inspecione o agendamento e os metadados do caminho sem iniciar o interpretador de privilégio mais alto.

Para um servidor PHP privilegiado que chama funções de uma extensão nativa personalizada, rastreie o SAPI PHP do serviço e o `php.ini` efetivo, além dos arquivos `.ini` carregados, antes de revisar a extensão. [O PHP carrega as bibliotecas `extension` configuradas na inicialização](https://www.php.net/manual/en/ini.core.php), e [SAPI CLI e web podem usar arquivos de configuração diferentes](https://www.php.net/manual/en/configuration.file.php). Assim, um formulário de login acessível ou um listener local pode passar strings controladas pelo usuário a código compilado executado com a identidade do serviço. Registre `User=`, `ExecStart=`, o diretório de trabalho da unidade, o caminho real da extensão e os argumentos controlados pelo chamador; a mera presença de um `.so` ou de um socket em loopback não comprova uma falha de corrupção de memória. Analise qualquer parser personalizado separadamente, em vez de enviar sondas durante uma enumeração passiva.

Quando um wrapper privilegiado calcula o hash de um script por caminho e depois abre esse caminho novamente para executá-lo, o digest autentica apenas o objeto lido na primeira abertura. Se um usuário menos privilegiado puder substituir a entrada do diretório do script entre essas aberturas, a execução posterior poderá resolver para outro objeto, mesmo que o arquivo de script original pertença a root. Um FIFO pode prolongar a fase de verificação, mas o caminho depende de direitos de diretórios pais que permitam substituições, de aberturas separadas reais, da identidade do scheduler, das regras de sticky bit e montagem e do timing. Inspecione o wrapper e a saída de `namei -l` como pistas passivas; um checksum válido, por si só, não prova que o caminho posterior esteja protegido.

Uma tarefa de backup privilegiada também pode **divulgar** dados sem executar comandos fornecidos pelo invasor. Rastreie se um usuário menos privilegiado pode criar um arquivo de controle que a tarefa lê, se a tarefa então abre uma origem protegida, como `/etc/shadow`, e se o resultado chega a uma URL escolhida pelo invasor ou a uma saída legível. Verifique as três partes antes de classificar isso como um caminho de divulgação. Um comando shell fixo no mesmo script não transforma, por si só, esse arquivo de controle em uma entrada de injeção de shell. Inspecione o script e as permissões dos arquivos sem executar a tarefa nem plantar um arquivo de controle durante a enumeração.

Se uma tarefa privilegiada agendada executar `curl -K FILE` ou `curl --config FILE`, [o curl trata as opções desse arquivo como argumentos de linha de comando](https://curl.se/docs/manpage.html). Um usuário menos privilegiado que controle o arquivo exato quando o curl o lê pode influenciar a URL solicitada, a entrada de arquivo local ou o caminho de saída. Confirme a identidade efetiva da tarefa, os direitos de escrita no arquivo e nos diretórios ancestrais, o momento de qualquer outra tarefa que substitua o arquivo e como as opções de configuração interagem com as opções fixas da linha de comando antes de alegar uma leitura ou gravação protegida. Um caminho de configuração gravável ou uma flag `-K` visível, por si só, não prova que as opções escolhidas surtirão efeito; inspecione o agendamento e os metadados sem executar a tarefa nem buscar uma URL durante a enumeração passiva.

Se uma entrada cron invoca um script auxiliar, inspecione também o diretório de trabalho do auxiliar e o comando de arquivamento. Um curinga sem aspas sobre um diretório gravável por outro usuário pode transformar nomes de arquivos em opções do arquivador; as ações de checkpoint do GNU tar são um exemplo. Confirme a identidade de execução agendada, o diretório de entrada gravável, o arquivador e as opções exatos e se `--` encerra a análise de opções antes de alegar um caminho de comandos entre usuários. Consulte o comportamento de [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Uma divulgação separada de arquivos de backup pode ocorrer quando um auxiliar privilegiado executa `cd INPUT_DIR; tar ... *` sem verificar se `cd` teve sucesso. Se um usuário menos privilegiado puder remover ou substituir `INPUT_DIR`, um `cd` malsucedido pode deixar o shell no diretório anterior, que o comando de arquivamento seguinte poderá ler. Verifique o diretório de trabalho inicial da tarefa, um caminho real de falha do `cd`, se o script sai ou usa `&&`, as opções exatas do arquivador e se o usuário menos privilegiado consegue ler o arquivo resultante. Um diretório de entrada gravável ou um arquivo legível, por si só, é apenas uma pista; inspecione o auxiliar e as permissões do caminho sem alterar a tarefa ativa.

Um executável agendado pode ocultar um script de shell, em vez de eliminar seu limite de confiança: o [SHc](https://github.com/neurobin/shc) empacota o texto criptografado do script em um binário nativo e o executa por meio de um shell durante a execução. Um sufixo `.sh.x` ou um ELF opaco é apenas uma pista para revisão. Para avaliar a injeção de opções por nome de arquivo, estabeleça a identidade do scheduler privilegiado, o diretório de trabalho e o comando reais do auxiliar, a capacidade do usuário menos privilegiado de criar nomes correspondentes nesse local e se um glob sem aspas chega a um comando como `rsync` sem um limite de opções. A [opção de remote-shell do `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) só é relevante se esse caminho exato de comando for usado. Visibilidade restrita de `/proc` ou falha na descriptografia estática deixa o comando desconhecido; não execute o auxiliar privilegiado apenas para classificá-lo.

O texto da linha de comando de um processo é outra entrada não confiável para um auxiliar privilegiado. Um usuário menos privilegiado pode escolher um título de processo ou `argv[0]` correspondente a `pgrep -f`; um nome correspondente não autentica o executável nem seu proprietário. Se um script executado como root capturar esse texto, reescrever parte dele como `apache2ctl`/`httpd` e executar o resultado sem um array fixo de argumentos, as opções escolhidas pelo invasor podem selecionar outro diretório de configuração ou log de erros. A análise da configuração do Apache pode carregar módulos ou alcançar auxiliares configurados, portanto, não valide uma configuração não confiável como root durante a enumeração. Inspecione o proprietário do scheduler, o auxiliar exato, a identidade do processo e o fluxo de dados até os argumentos; isso é injeção de opções/configuração, a menos que a execução de metacaracteres de shell seja demonstrada separadamente.

Um parser executado como root que alimenta texto não confiável à aritmética do Bash pode executar substituições nesse texto. O [guia de escalonamento de privilégios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) apresenta um exemplo detalhado. Confirme a origem da entrada e o comando de parsing antes de tratar toda expressão aritmética como explorável.

Para uma tarefa privilegiada que analisa um log da aplicação, rastreie os campos não confiáveis além da primeira análise. Uma conta menos privilegiada pode conseguir gravar no log por meio do grupo atual do processo ou influenciar campos de requisição registrados; um registro pode então selecionar uma imagem, cujos metadados se tornam um segundo caminho usado para abrir XML. Verifique a identidade efetiva da tarefa, o acesso real de escrita no log, o tratamento dos delimitadores, a contenção do caminho canônico e se o XML selecionado é controlado pelo invasor. A expansão de entidades externas pode transformar essa segunda leitura em divulgação privilegiada de arquivos se o resultado expandido chegar a uma saída legível por um usuário menos privilegiado. O [guia de segurança do processamento de XML em Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para o acesso a DTDs/entidades externas; inspecione o parser instalado e suas configurações efetivas. Um log ou arquivo XML gravável, por si só, é apenas uma pista. Revise o código e os metadados sem alimentar o parser agendado durante a enumeração.

Inspecione também tarefas privilegiadas que materializam arquivos de um repositório Git de outro usuário. Um script pode usar `git ls-tree` e `git cat-file` em vez de `git checkout` e ainda assim confiar em caminhos de árvore controlados pelo invasor ao combiná-los com um diretório de staging. Caminhos absolutos e componentes `..` podem escapar desse diretório, a menos que o destino seja normalizado e verificado quanto à contenção antes da gravação. `git -c safe.directory=*` permite acesso a repositórios com proprietários diferentes; por si só, não cria a condição de gravação arbitrária.

Um backup de banco de dados executado como root pode criar outro limite de propriedade. O PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia arquivos regulares adicionais colocados no diretório de dados de origem, e seu formato plain padrão grava arquivos em `-D` como uma árvore de diretórios. Se uma conta menos privilegiada puder criar ou modificar esses arquivos de origem, inspecione a propriedade e o modo do destino resultante, se o caminho permite travessia e execução e se a montagem tem `nosuid`. Uma cópia pertencente a root com permissões set-ID preservadas pode ser perigosa; um backup somente em tar, permissões removidas ou um destino inacessível não comprova o mesmo caminho. Rastreie o wrapper agendado e o usuário efetivo antes de considerar o comando de backup uma descoberta.

## Observe tarefas de curta duração

Uma única captura de processos pode não detectar uma tarefa executada por milissegundos. Compare as declarações de timer/cron com os logs e, quando autorizado, use monitoramento de eventos de processos, como `pspy` ou audit. Correlacione o proprietário agendado, a linha de comando exata e os arquivos que a tarefa lê ou grava. Uma interface web de scheduler em loopback é uma interface separada; consulte o [exemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
