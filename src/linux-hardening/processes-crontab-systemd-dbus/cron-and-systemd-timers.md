# Attività cron e timer systemd

{{#include ../../banners/hacktricks-training.md}}

Le attività pianificate possono essere eseguite con un'identità e un ambiente diversi da quelli della shell corrente. Elenca cron, `at`, anacron e i timer systemd, quindi esamina ogni comando pianificato attraverso i relativi script, importazioni, directory di lavoro e input scrivibili.

## Elencare le pianificazioni

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Le crontab di sistema di solito includono un campo utente; il crontab di un utente no. Esamina il PATH effettivo e l'ambiente dello scheduler in uso. `run-parts --test /etc/cron.daily` mostra quali nomi di file verrebbero selezionati su quell'host. I caratteri di controllo possono nascondere una voce nell'output visualizzato normalmente: se una pianificazione sembra sospetta, usa `cat -A` o `sed -n l`.

## Tracciare la risoluzione di file e comandi privilegiati

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Esamina le catene di script scrivibili, i percorsi `EnvironmentFile=`, i drop-in, i symlink, i comandi relativi, l'espansione dei wildcard e i binari copiati o eseguiti da un task privilegiato. Un timer può attivare un service con un nome diverso tramite l'impostazione `Unit=`. Le pagine [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) spiegano i principali elementi di base.

Per uno script `chkrootkit` pianificato ed eseguito da root, esamina il sorgente installato per verificare il vecchio [difetto di quoting slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): un `file_port=$file_port $i` senza virgolette, dopo un controllo di un percorso temporaneo `SLAPPER_FILES`, può eseguire quel file. Verifica lo script effettivo o la patch del vendor, la pianificazione come root, l'accesso in scrittura dell'utente meno privilegiato al percorso temporaneo esatto, il suo stato eseguibile e le policy di mount. La sola stringa della versione o la presenza di `chkrootkit` non dimostrano che il percorso sia sfruttabile; durante una verifica passiva non creare né eseguire un file temporaneo.

Traccia un altro passaggio tra unità quando il service root di un timer esegue `systemctl restart <other>.service`: l'unità riavviata può invocare una shell con uno script scrivibile da un utente meno privilegiato. Verifica `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, gli argomenti esatti di `ExecStart=` e i permessi dello script e del percorso parent. Uno script scrivibile è solo un candidato finché il timer e il service riavviato non sono attivi in quel contesto di esecuzione; esamina le proprietà delle unità senza riavviare nessuno dei due service.

Se un job con privilegi più elevati scarica uno script tramite hostname e passa la risposta a una shell, verifica chi controlla la risoluzione di quell'hostname oltre allo script remoto. Un file `/etc/hosts` scrivibile, anche se l'accesso è concesso tramite un gruppo o una ACL, può reindirizzare un nome che il job risolve localmente; una risposta di `curl` diventa un percorso di esecuzione tra utenti solo quando il comando pianificato la esegue davvero e il job usa il percorso di risoluzione interessato. Verifica l'identità con cui viene eseguito il job, l'URL esatto e la pipeline della shell, il comportamento effettivo di proxy/DNS e i permessi del file e della directory parent. Un file hosts scrivibile è un indizio da approfondire, non la prova dell'esistenza di un consumer privilegiato. Esamina la pianificazione e i metadati senza modificare la mappatura né scaricare lo script durante l'enumerazione.

Un `wget` privilegiato pianificato costituisce un confine di scrittura dei file distinto, anche se il contenuto scaricato non viene eseguito direttamente. [GNU Wget 1.18 ha modificato la gestione predefinita del nome del file nei redirect HTTP-to-FTP per correggere CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); le build precedenti interessate potevano usare il nome del file del redirect FTP, mentre `--trust-server-names` richiede esplicitamente quel comportamento. Se una parte meno fidata controlla la risposta HTTP e la risorsa FTP, verifica se il job segue il redirect, la build effettiva di Wget o il backport del vendor, le opzioni di output, l'identità con cui viene eseguito, la directory di lavoro e se il nome del file di destinazione può diventare un file di startup. [Wget carica `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html) e [le sue impostazioni possono selezionare una sorgente POST o un percorso di output](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); uno scaricamento privilegiato successivo è un prerequisito distinto per qualsiasi disclosure o scrittura risultante. L'accesso a una porta bassa tramite `authbind` è rilevante solo se il chiamante può effettivamente servire l'URL richiesto dal job. Esamina configurazione e log in modo passivo, senza servire un redirect né eseguire il job. [L'accesso grezzo ai block device tramite il gruppo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) è indipendente da questo percorso di download via rete.

Traccia anche i file di dati, non solo gli script. Un tool di simulazione o orchestrazione pianificato può leggere un file YAML che definisce i processi da avviare; se un utente meno privilegiato può modificare quel file e il job lo esegue con un altro account, i dati possono diventare comandi eseguiti con l'identità del job. Verifica il comando pianificato esatto, l'utente effettivo, il percorso del file, la semantica del parser e l'accesso in scrittura (incluse le directory parent) prima di considerare un file YAML scrivibile un percorso di esecuzione. Per un triage passivo basta leggere la pianificazione e i metadati del file; durante l'enumerazione non eseguire il job né modificarne l'input.

Anche la configurazione di un client SSH è input eseguibile quando un job con privilegi più elevati esegue `ssh -F` su un file sostituibile da un utente meno privilegiato. In OpenSSH, [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) esegue un comando locale tramite la shell del client, mentre `Host`/`Match` e le opzioni precedenti determinano se quella direttiva si applica. Prima di considerarlo un percorso di esecuzione tra utenti, correla l'invocazione SSH pianificata esatta, l'identità con cui viene eseguita, il percorso di configurazione selezionato, i permessi di scrittura su directory e file e l'ordine effettivo delle opzioni. Esamina questi elementi senza eseguire il job né caricare la configurazione non fidata come account privilegiato.

Un `scp` pianificato seguito da `ssh` per eseguire lo script copiato richiede un secondo controllo del confine di fiducia se un utente meno privilegiato controlla il service SSH di destinazione. Se quel service può inoltrare la connessione a un altro host, il client privilegiato potrebbe autenticarsi a un endpoint non previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) indebolisce la protezione contro la modifica della chiave host, nei limiti delle restanti restrizioni di OpenSSH e delle opzioni effettive per host. Determina l'identità con cui viene eseguito il job, la destinazione effettiva e il metodo di autenticazione, l'identità effettiva del comando remoto e se lo stesso percorso di destinazione è scrivibile o già esistente sull'host reindirizzato. L'esecuzione di un file vecchio o controllato da un attaccante richiede inoltre che la copia fallisca o non trovi quel percorso **e** che il wrapper continui con il comando SSH; [`errexit` di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e la gestione esplicita dello stato influenzano questo flusso. Una configurazione host-key debole, un processo `sshpass` visibile o una directory temporanea scrivibile, da soli, non dimostrano questa catena. Esamina la pianificazione, lo script, la configurazione SSH e i metadati dei file senza reindirizzare il service né attivare il job durante l'enumerazione.

Uno scheduler applicativo privilegiato può ricavare i job da righe del database invece che da file scrivibili. Per esempio, una voce cron di root che invoca Laravel con [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) può raggiungere codice applicativo che legge righe di task. Se un account meno privilegiato può scrivere una riga contenente un percorso locale e il callback pianificato chiama [`file_get_contents` di PHP](https://www.php.net/manual/en/function.file-get-contents.php) come root, inviando poi il contenuto restituito a un webhook selezionato dalla riga, si tratta di un percorso di disclosure di file privilegiato. Verifica l'identità cron, il callback effettivo dello scheduler e il flusso dei dati dalla riga al percorso, le autorizzazioni di scrittura sul database, la validazione dopo la lettura della riga e la destinazione in uscita. Un file `.env` dell'applicazione leggibile è solo un indizio relativo alle credenziali; la validazione di un form web o una password del database, da sole, non dimostrano il controllo della riga o la disclosure. Esamina la pianificazione, il codice e i permessi dei file di credenziali in modo passivo, senza interrogare il database né pianificare un task durante l'enumerazione.

Anche i job event-driven `incron` meritano la stessa verifica: le [voci incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associano un percorso monitorato e un evento a un comando eseguito con l'identità del proprietario della tabella. Un utente meno privilegiato può influenzare indirettamente un file monitorato quando un'applicazione segue un link da una directory scrivibile e scrive testo controllato dall'attaccante nel target monitorato. Verifica il proprietario effettivo della tabella, l'evento, i permessi del target e delle directory ancestor, il comportamento dell'applicazione nel seguire i link e il modo in cui il testo diventa argomenti del comando. In particolare, [`mail` di GNU Mailutils accetta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html) e il suo [comando di shell escape](https://mailutils.org/manual/html_node/Shell-Escapes.html) può eseguire un programma; un campo non fidato passato come opzione separata a quell'implementazione può portare all'esecuzione di comandi. Altre implementazioni di `mail` o un confine di argomenti fisso e quotato possono comportarsi diversamente. Esamina la pianificazione, il codice dell'applicazione e i metadati dei file senza modificare il file monitorato né attivare il job durante l'enumerazione.

Un log monitorato può inoltre attraversare il confine tra utenti tramite uno script helper. Se un account meno privilegiato può scrivere il log e il proprietario di `incron` legge un campo del log inserendolo in una nuova stringa di comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), la shell analizza nuovamente quel campo con l'identità del proprietario. Verifica l'evento monitorato esatto, i permessi del log e delle directory parent, il percorso dell'helper, la trasformazione del campo del log e se il comando risultante viene effettivamente eseguito. Vedere un log scrivibile e una voce `incron`, da soli, non dimostra il flusso dei dati; durante un'enumerazione passiva non scrivere una riga di trigger né eseguire l'helper.

Anche i job di rinnovo dei certificati possono attraversare lo stesso confine. Un helper privilegiato può leggere il subject X.509 da un certificato in una directory scrivibile da un utente meno privilegiato e inserire il common name in una nuova stringa di comando `bash -c`. [OpenSSL può mostrare il subject di un certificato e verificarne la scadenza](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analizza la stringa `-c` come input della shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), quindi quotare la variabile nello script esterno non protegge dalla seconda analisi. Prima di considerarlo command injection, verifica l'identità pianificata, il percorso di input esatto e i permessi di scrittura, il ramo di rinnovo e il flusso dei dati verso `bash -c`. Esamina lo script e i metadati del certificato in modo passivo; durante l'enumerazione non attivare il rinnovo.

La stessa seconda analisi può verificarsi quando un job privilegiato estrae un nome da un archivio o pacchetto di un utente meno privilegiato e lo passa a `xargs -I` per inserirlo in una stringa di comando `sh -c`. [`xargs -I` di GNU sostituisce il placeholder negli argomenti iniziali](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html) e [`sh -c` interpreta la stringa di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Anche se lo script esterno quota il nome estratto, ciò non rende sicuro un programma shell sostituito successivamente. Verifica l'identità con cui viene eseguito il job, il percorso di input accettato esatto e i permessi di scrittura, la validazione dell'archivio e le condizioni del ramo, nonché il flusso dal nome alla shell. Una directory di upload scrivibile o un'invocazione di `xargs`, da sole, sono solo indizi; durante l'enumerazione esamina la pianificazione, lo script e i metadati dei percorsi senza inviare un pacchetto né eseguire il job.

Anche un importatore pianificato di font o immagini può fidarsi dei nomi *contenuti* in un archivio fornito dal chiamante, anche quando il nome esterno dell'upload è soggetto a restrizioni. FontForge ha corretto la command injection tramite nomi dei membri dell'archivio nella [modifica upstream per CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Verifica che un job con privilegi più elevati apra davvero un archivio da un percorso scrivibile da un utente meno privilegiato, l'identità con cui viene eseguito, la build esatta di FontForge o il backport del vendor e il percorso di gestione dell'archivio. Una stringa della versione o un suffisso di upload consentito, da soli, non dimostrano l'esecuzione. Durante l'enumerazione esamina la pianificazione, i permessi dei percorsi e i metadati della build senza importare un archivio non fidato.

Gli scanner di rete pianificati possono attraversare un confine diverso quando uno script personalizzato tratta il subject di un certificato TLS remoto come un nome di file locale. [Nmap NSE esegue gli script selezionati senza sandbox](https://nmap.org/book/nse-usage.html), quindi esamina lo script effettivo e verifica se concatena un campo subject non fidato a una directory di dati senza controlli di contenimento. La disclosure di un file richiede un target che lo scheduler analizzerà, un percorso che risolva in un file leggibile dall'identità con cui viene eseguito lo scanner e un report o log consegnato a un lettore meno privilegiato. Un campo di un certificato o la sola presenza di uno scanner installato non dimostrano la catena; durante un'enumerazione passiva esamina la pianificazione, lo script, la risoluzione del percorso e la destinazione del report senza analizzare un nuovo target.

Un comando cron privilegiato che passa a un runner Ansible un wildcard shell come `/path/to/tasks/*.yml` richiede una verifica dei permessi della directory, anche quando tutti i playbook esistenti sono di sola lettura. Un utente con accesso in scrittura e ricerca alla directory inclusa nel wildcard potrebbe creare un altro playbook corrispondente. [I playbook Ansible definiscono i task eseguiti dal runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), ma un wrapper personalizzato potrebbe filtrare i percorsi o usare un'identità diversa: verifica il suo comportamento, l'utente cron effettivo, l'espansione della shell, le ACL, lo sticky bit e le policy di mount prima di considerare la directory un percorso di esecuzione. Esamina staticamente i metadati e il wrapper; durante l'enumerazione non eseguire il job pianificato.

Un wrapper cron privilegiato può passare nomi di file da una directory di upload a un helper Perl dopo aver espanso un wildcard. L'operatore [`<>` diamond di Perl usa `open` a due argomenti](https://perldoc.perl.org/perlop#The-Null-Filehandle), quindi un nome corrispondente interpretato come comando pipe può essere eseguito con l'identità dell'helper; [`<<>>` tratta gli argomenti come nomi di file letterali](https://perldoc.perl.org/perlop#The-Null-Filehandle). Verifica l'identità dello scheduler, la directory di lavoro e il wildcard del wrapper, la gestione effettiva di `@ARGV` nell'helper, le restrizioni sui nomi dei file e se un'identità meno privilegiata può inserire un nome corrispondente tramite i permessi del filesystem o un servizio di upload autenticato. Una riga cron, uno script Perl o una directory FTP scrivibile, da soli, non dimostrano l'intera catena. Esamina il codice sorgente e i metadati senza inviare un nome di file creato ad hoc né eseguire il job durante l'enumerazione.

Uno script cron di sola lettura è comunque sostituibile se l'account pianificato lo esegue tramite pathname e l'utente meno privilegiato può scrivere e attraversare la sua directory parent non sticky. Verifica l'identità con cui viene eseguita la pianificazione, ogni componente del percorso, lo sticky bit della directory, le ACL e le policy di mount; esamina i metadati senza spostare il file né eseguire il job.

Un wrapper PHP cron privilegiato può raggiungere un helper che ancora non esiste. Se chiama [`exec()` di PHP](https://www.php.net/manual/en/function.exec.php) con un percorso assoluto fisso dell'helper, un utente meno privilegiato che può creare quel nome nella directory parent potrebbe controllare ciò che verrà eseguito al run successivo. Verifica che la voce cron esegua davvero il wrapper con l'identità più privilegiata, la stringa di comando esatta e la policy di esecuzione PHP, i permessi di scrittura e ricerca sulla directory dell'helper, il comportamento di symlink e sticky bit e che il percorso dell'helper sia ancora assente. Una directory scrivibile o un helper mancante, da soli, sono solo indizi; durante l'enumerazione esamina la pianificazione, il sorgente e i metadati dei percorsi senza creare l'helper né attivare il job.

Un job pianificato può anche individuare script di input con `find` e passarli a un interprete. Per esempio, la funzione `system()` di [gnuplot invoca una shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), quindi un job privilegiato che esegue `gnuplot` su ogni file `*.plt` in una directory scrivibile da un utente meno privilegiato può eseguire comandi con l'identità del job. [Il permesso di lettura della directory controlla l'elenco dei nomi, mentre scrittura e ricerca (`x`) controllano la creazione e l'accesso ai nomi noti](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); verifica l'accesso in scrittura e ricerca anche quando `ls` non riesce a elencare la directory. Correlaziona l'identità e il comando esatti dello scheduler, il comportamento dell'interprete, il pattern dei file selezionati e i permessi della directory; una directory scrivibile o un interprete installato, da soli, non dimostrano un'escalation. Le pianificazioni private e i job di breve durata possono richiedere un'osservazione autorizzata degli eventi, perché un singolo snapshot dei processi può non rilevarli.

Per un job PHP privilegiato, esamina le istruzioni letterali `include`/`require` come parte della catena di script eseguibili. [PHP valuta i file inclusi](https://www.php.net/manual/en/function.include.php), quindi un file `.php` scrivibile dal gruppo può eseguire codice con l'identità del job anche quando lo script principale è di sola lettura. Verifica l'identità pianificata, la risoluzione effettiva dell'include path, i permessi di file e directory e se il job viene davvero eseguito; un esempio di riga cron in un commento è solo un indizio. La stessa verifica vale per un [server integrato PHP](https://www.php.net/commandline.webserver) di proprietà di root avviato con `-S` e `-t <document-root>`: un listener loopback può comunque eseguire PHP dell'applicazione per richieste locali. Durante l'enumerazione esamina il processo e il sorgente senza attivare nessuno dei due trigger.

Un job PHP privilegiato può anche attraversare il confine tramite un **file di dati**: se un utente meno privilegiato può modificare il file esatto passato a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP può invocare il metodo `__wakeup()` o `__unserialize()` di una classe caricata durante il ripristino dell'oggetto. Esamina l'identità effettiva del job, i permessi del file e delle directory ancestor, le classi caricate e gli effetti collaterali effettivi dei metodi, come una scrittura su file selezionata da una proprietà. Un log scrivibile o una chiamata a `unserialize()`, da soli, non dimostrano l'esistenza di un percorso utilizzabile. Durante l'enumerazione esamina il sorgente e i metadati senza scrivere input serializzato né eseguire il job.

Un task cron di root può invocare il **CLI page runner** di un'applicazione PHP anziché il server web. Traccia la document root e l'URI selezionati dal runner fino all'entrypoint PHP effettivo; se l'account del web service può scrivere quell'entrypoint, la richiesta CLI pianificata può eseguire come root il codice modificato, anche quando il runner e il wrapper cron sono di sola lettura. Verifica l'identità dello scheduler, la risoluzione esatta dell'URI al file, i permessi effettivi del file e delle directory ancestor e se un controllo d'integrità protegge l'entrypoint stesso. Durante l'enumerazione esamina il sorgente e i metadati senza invocare il runner né modificare la pagina.

Un processo `ipython` avviato da un job pianificato o da un altro utente da una directory di lavoro condivisa merita una verifica dei file di startup. Le [note di rilascio di sicurezza di IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) spiegano che le build interessate cercavano profili e configurazioni nella directory corrente, incluso il codice in `profile_default/startup`, prima della correzione di CVE-2022-21699. Correlaziona la build installata effettiva o la patch del vendor, la directory di lavoro del comando, l'identità del processo con privilegi più elevati e la possibilità per l'utente meno privilegiato di scrivere e cercare il percorso di startup esatto. La presenza di `ipython`, una directory scrivibile o una stringa della versione, da sole, non dimostrano che un'altra identità caricherà un file da lì. Durante l'enumerazione esamina la pianificazione e i metadati dei percorsi senza avviare l'interprete con privilegi più elevati.

Per un server PHP privilegiato che chiama funzioni di un'estensione nativa personalizzata, prima di esaminare l'estensione traccia la SAPI PHP del service, il suo `php.ini` effettivo e i file `.ini` scansionati. [PHP carica all'avvio le librerie `extension` configurate](https://www.php.net/manual/en/ini.core.php) e [le SAPI CLI e web possono usare file di configurazione diversi](https://www.php.net/manual/en/configuration.file.php). Un form di login raggiungibile o un listener locale possono quindi passare stringhe controllate dall'utente a codice compilato eseguito con l'identità del service. Registra `User=`, `ExecStart=`, la directory di lavoro, il percorso effettivo dell'estensione e gli argomenti controllati dal chiamante nell'unità; la sola presenza di un `.so` o di un socket loopback non dimostra un difetto di memory corruption. Analizza separatamente qualsiasi parser personalizzato invece di inviare probe durante un'enumerazione passiva.

Quando un wrapper privilegiato calcola l'hash di uno script tramite pathname e poi riapre lo stesso pathname per eseguirlo, il digest autentica solo l'oggetto letto durante la prima apertura. Se un utente meno privilegiato può sostituire la voce della directory dello script tra le due aperture, l'esecuzione successiva può risolvere un oggetto diverso anche se il file originale appartiene a root. Una FIFO può allungare la fase di controllo, ma il percorso dipende dai permessi sostituibili della directory parent, da aperture effettivamente separate, dall'identità dello scheduler, dalle regole di sticky bit e mount e dalla tempistica. Esamina il wrapper e l'output di `namei -l` come indizio passivo; un checksum valido, da solo, non dimostra che il pathname sia protetto per l'apertura successiva.

Un job di backup privilegiato può anche **divulgare** dati senza eseguire comandi forniti dall'attaccante. Traccia se un utente meno privilegiato può creare un file di controllo letto dal job, se il job apre poi una sorgente protetta come `/etc/shadow` e se un URL scelto dall'attaccante o un output leggibile riceve il risultato. Verifica tutte e tre le parti prima di considerarlo un percorso di disclosure. Un comando shell fisso nello stesso script non rende di per sé quel file di controllo un input di shell injection. Esamina lo script e i permessi dei file senza eseguire il job né inserire un file di controllo durante l'enumerazione.

Se un job privilegiato pianificato esegue `curl -K FILE` o `curl --config FILE`, [curl tratta le opzioni contenute nel file come argomenti della riga di comando](https://curl.se/docs/manpage.html). Un utente meno privilegiato che controlla il file esatto al momento in cui curl lo legge può influenzare l'URL richiesto, l'input da file locale o il percorso di output. Prima di sostenere che sia possibile una lettura o scrittura protetta, verifica l'identità effettiva del job, i permessi di scrittura sul file e sulle directory ancestor, la tempistica di eventuali altri job che sostituiscono il file e l'interazione tra le opzioni di configurazione e quelle fisse della riga di comando. Un percorso di configurazione scrivibile o un flag `-K` visibile, da soli, non dimostrano che le opzioni scelte abbiano effetto; durante un'enumerazione passiva esamina la pianificazione e i metadati senza eseguire il job né scaricare un URL.

Se una voce cron invoca uno script helper, esamina anche la sua directory di lavoro e il comando di archiviazione. Un wildcard non quotato su una directory scrivibile da un altro utente può trasformare i nomi dei file in opzioni dell'archiver; le azioni checkpoint di GNU tar sono un esempio. Prima di sostenere che esista un percorso di esecuzione tra utenti, verifica l'identità con cui viene eseguito il job, la directory di input scrivibile, l'archiver e le opzioni esatte e se `--` termina l'analisi delle opzioni. Vedi il comportamento di [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Una disclosure di file di backup distinta può verificarsi quando un helper privilegiato esegue `cd INPUT_DIR; tar ... *` senza verificare che `cd` sia riuscito. Se un utente meno privilegiato può rimuovere o sostituire `INPUT_DIR`, un `cd` fallito può lasciare la shell nella directory precedente, che il successivo comando di archiviazione potrebbe leggere. Verifica la directory di lavoro iniziale del job, un percorso reale di fallimento di `cd`, se lo script termina o usa `&&`, le opzioni esatte dell'archiver e se l'archivio di output è leggibile dall'utente meno privilegiato. Una directory di input scrivibile o un archivio leggibile, da soli, sono solo indizi; esamina l'helper e i permessi dei percorsi senza modificare il job attivo.

Un eseguibile pianificato può nascondere uno script shell anziché eliminare il relativo confine di fiducia: [SHc](https://github.com/neurobin/shc) racchiude testo di script cifrato in un binario nativo e lo esegue tramite una shell a runtime. Un suffisso `.sh.x` o un ELF opaco sono solo indizi da approfondire. Per valutare l'injection di opzioni tramite i nomi dei file, accerta l'identità privilegiata dello scheduler, la directory di lavoro e il comando effettivi dell'helper, la possibilità per un utente meno privilegiato di creare nomi corrispondenti in quella directory e se un wildcard non quotato raggiunge un comando come `rsync` senza un confine tra opzioni e argomenti. L'opzione [`rsync` remote-shell](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) è rilevante solo se viene usato quel percorso di comando esatto. La visibilità limitata di `/proc` o la decrittazione statica non riuscita lasciano il comando sconosciuto; non eseguire l'helper privilegiato solo per classificarlo.

Anche il testo della command line di un processo può essere un input non fidato per un helper privilegiato. Un utente meno privilegiato può scegliere un titolo di processo o `argv[0]` che corrisponda a `pgrep -f`; un nome corrispondente non autentica l'eseguibile né il suo proprietario. Se uno script eseguito da root acquisisce quel testo, ne riscrive una parte in `apache2ctl`/`httpd` ed esegue il risultato senza un array di argomenti fisso, le opzioni scelte dall'attaccante possono selezionare un'altra directory di configurazione o un altro error log. L'analisi della configurazione Apache può caricare moduli o raggiungere helper configurati, quindi durante l'enumerazione non convalidare una configurazione non fidata come root. Esamina il proprietario dello scheduler, l'helper esatto, l'identità del processo e il flusso dai dati agli argomenti; si tratta di option/configuration injection, a meno che non venga dimostrata separatamente l'esecuzione di metacaratteri della shell.

Un parser eseguito da root che inserisce testo non fidato nell'aritmetica Bash può eseguire sostituzioni contenute in quel testo. La [guida alla privilege escalation](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) presenta un esempio completo. Verifica la sorgente dell'input e il comando di parsing prima di considerare sfruttabile ogni espressione aritmetica.

Per un job privilegiato che analizza un log applicativo, traccia i campi non fidati oltre la prima analisi. Un account meno privilegiato potrebbe poter scrivere nel log tramite il proprio gruppo di processi attuale o influenzare i campi delle richieste registrate; un record può quindi selezionare un'immagine, i cui metadati diventano un secondo pathname usato per aprire XML. Verifica l'identità effettiva del job, l'accesso effettivo in scrittura al log, la gestione dei delimitatori, il contenimento del percorso canonico e se l'XML selezionato è controllato dall'attaccante. L'espansione di external entity può trasformare questa seconda lettura in una disclosure di file privilegiata se il risultato espanso raggiunge un output leggibile da un utente meno privilegiato. La [guida alla sicurezza dell'elaborazione XML Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta i controlli per l'accesso a DTD/entity esterni; esamina il parser installato e le sue impostazioni effettive. Un log scrivibile o un file XML, da soli, sono solo indizi. Durante l'enumerazione esamina il codice e i metadati senza passare input al parser pianificato.

Esamina anche i job privilegiati che materializzano file da un repository Git di un altro utente. Uno script può usare `git ls-tree` e `git cat-file` invece di `git checkout`, ma fidarsi comunque dei percorsi nell'albero controllati dall'attaccante quando li concatena a una directory di staging. Percorsi assoluti e componenti `..` possono uscire da quella directory, a meno che la destinazione non venga normalizzata e verificata per il contenimento prima della scrittura. `git -c safe.directory=*` consente l'accesso a repository con proprietari diversi; da solo non crea la condizione di scrittura arbitraria.

Un backup di database eseguito da root può creare un altro confine di ownership. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia i file regolari aggiuntivi presenti nella directory dati sorgente e il formato plain predefinito scrive i file in `-D` come struttura di directory. Se un account meno privilegiato può creare o modificare quei file sorgente, esamina la proprietà e i permessi della destinazione risultante, se il percorso è attraversabile ed eseguibile e se il mount ha `nosuid`. Una copia di proprietà di root con permessi set-ID conservati può essere pericolosa; un backup solo tar, permessi rimossi o una destinazione inaccessibile non dimostrano lo stesso percorso. Traccia il wrapper pianificato e l'utente effettivo prima di considerare il comando di backup una finding.

## Osservare i job di breve durata

Un singolo snapshot dei processi può non rilevare un job che dura pochi millisecondi. Confronta le dichiarazioni di timer/cron con i log e, quando autorizzato, con il monitoraggio degli eventi di processo, ad esempio `pspy` o audit. Correlaziona il proprietario pianificato, la command line esatta e i file letti o scritti dal task. Una UI web dello scheduler in ascolto su loopback è un'interfaccia distinta; vedi l'[esempio Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
