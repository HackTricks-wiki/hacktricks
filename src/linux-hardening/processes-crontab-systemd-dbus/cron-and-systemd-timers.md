# Job Cron e timer systemd

{{#include ../../banners/hacktricks-training.md}}

Le attività pianificate possono essere eseguite con un'identità e un ambiente diversi da quelli della shell corrente. Elenca cron, `at`, anacron e i timer systemd, quindi segui ogni comando pianificato attraverso i relativi script, import, directory di lavoro e input scrivibili.

## Elencare le pianificazioni

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

I crontab di sistema di solito includono un campo utente; il crontab di un utente no. Esamina il PATH effettivo e l’ambiente dello scheduler. `run-parts --test /etc/cron.daily` mostra quali nomi di file verrebbero selezionati su quell’host. I caratteri di controllo possono nascondere una voce nell’output visualizzato normalmente, quindi usa `cat -A` o `sed -n l` quando una pianificazione sembra sospetta.

## Traccia la risoluzione dei file e dei comandi con privilegi elevati

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Esamina le catene di script scrivibili, i percorsi `EnvironmentFile=`, i drop-in, i symlink, i comandi relativi, l’espansione dei wildcard e i binari copiati o eseguiti da un task privilegiato. Un timer può attivare un servizio con un nome diverso tramite l’impostazione `Unit=`. Le pagine su [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) illustrano le primitive principali.

Per uno script `chkrootkit` pianificato ed eseguito come root, esamina il sorgente installato per verificare il vecchio [difetto di quoting slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): un’istruzione non quotata `file_port=$file_port $i`, eseguita dopo un controllo di un percorso temporaneo `SLAPPER_FILES`, può eseguire quel file. Verifica lo script effettivo o la patch del vendor, la pianificazione come root, l’accesso in scrittura dell’utente meno privilegiato al percorso temporaneo esatto, il suo stato eseguibile e le policy di mount. Una stringa di versione o la sola presenza di `chkrootkit` non dimostrano che il percorso sia sfruttabile; durante una revisione passiva, non creare né eseguire un file temporaneo.

Segui un ulteriore passaggio tra unità quando il servizio root di un timer esegue `systemctl restart <other>.service`: l’unità riavviata può invocare una shell con uno script scrivibile da un utente meno privilegiato. Verifica `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, gli argomenti esatti di `ExecStart=` e i permessi dello script e del percorso che lo contiene. Uno script scrivibile è solo un possibile candidato finché il timer e il servizio riavviato non sono attivi in quel contesto di esecuzione; esamina le proprietà delle unità senza riavviare nessuno dei due servizi.

Se un job con privilegi maggiori scarica uno script tramite hostname e passa la risposta a una shell, verifica chi controlla la risoluzione di quell’hostname oltre allo script remoto. Un file `/etc/hosts` scrivibile, anche tramite permessi concessi a un gruppo o ACL, può reindirizzare un nome risolto localmente dal job; una risposta di `curl` diventa un percorso di esecuzione tra utenti solo se il comando pianificato esegue effettivamente quella risposta e il job usa il percorso di risoluzione interessato. Verifica l’identità usata per eseguire il job, l’URL esatto e la pipeline della shell, il comportamento effettivo di proxy/DNS e i permessi del file e della directory che lo contiene. Un file hosts scrivibile è di per sé un indizio da approfondire, non la prova dell’esistenza di un consumer privilegiato. Durante l’enumerazione, esamina la pianificazione e i metadati senza modificare la mappatura né scaricare lo script.

Un `wget` privilegiato pianificato costituisce un confine di scrittura distinto, anche se il contenuto scaricato non viene mai eseguito direttamente. [GNU Wget 1.18 ha modificato il comportamento predefinito nella gestione del nome del file dei redirect da HTTP a FTP per correggere CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); le versioni precedenti interessate potevano usare il nome del file del redirect FTP, mentre `--trust-server-names` richiede esplicitamente quel comportamento. Se una parte meno attendibile controlla la risposta HTTP e la risorsa FTP, verifica se il job segue quel redirect, la versione effettiva di Wget o la patch del vendor, le opzioni di output, l’identità usata per eseguire il job, la directory di lavoro e se il nome del file di destinazione può diventare un file di avvio. [Wget carica `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html) e [le sue impostazioni possono selezionare una sorgente POST o un percorso di output](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); un successivo download privilegiato è un prerequisito distinto per qualsiasi divulgazione o scrittura conseguente. L’accesso a una porta bassa tramite `authbind` è rilevante solo se il chiamante può effettivamente fornire l’URL richiesto dal job. Esamina la configurazione e i log passivamente, senza servire un redirect né eseguire il job. [L’accesso grezzo ai dispositivi a blocchi tramite il gruppo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) è indipendente da questo percorso di download di rete.

Traccia anche i file di dati, non solo gli script. Uno strumento di simulazione o orchestrazione pianificato può leggere un file YAML che definisce i processi da avviare; se un utente meno privilegiato può modificare quel file e il job lo esegue con un altro account, i dati possono diventare comandi eseguiti con l’identità del job. Verifica il comando pianificato esatto, l’utente effettivo, il percorso del file, la semantica del parser e l’accesso in scrittura, incluse le directory che lo contengono, prima di considerare un file YAML scrivibile un percorso di esecuzione. Per una prima valutazione passiva basta leggere la pianificazione e i metadati del file; durante l’enumerazione non eseguire il job né modificare il suo input.

Anche una configurazione del client SSH è un input eseguibile quando un job con privilegi maggiori esegue `ssh -F` usando un file sostituibile da un utente meno privilegiato. [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) di OpenSSH esegue un comando locale tramite la shell del client, mentre `Host`/`Match` e le opzioni precedenti determinano se tale direttiva viene applicata. Prima di considerarlo un percorso di esecuzione tra utenti, correla l’invocazione SSH pianificata esatta, l’identità usata per eseguire il job, il percorso della configurazione selezionata, i permessi di scrittura del file e della directory e l’ordine effettivo delle opzioni. Esamina questi elementi senza eseguire il job né caricare la configurazione non attendibile come account privilegiato.

Un `scp` pianificato seguito da `ssh` per eseguire lo script copiato richiede una seconda verifica dei confini di fiducia quando un utente meno privilegiato controlla il servizio SSH di destinazione. Se quel servizio può inoltrare la connessione a un altro host, il client privilegiato potrebbe autenticarsi a un endpoint inatteso; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) indebolisce la protezione contro la modifica della host key, fatte salve le restrizioni rimanenti di OpenSSH e le opzioni effettive per host. Determina l’identità usata dal job, la destinazione effettiva e il metodo di autenticazione, l’identità effettiva del comando remoto e se lo stesso percorso di destinazione è scrivibile o già esistente sull’host reindirizzato. L’esecuzione di un file precedente o controllato da un attaccante richiede inoltre che la copia fallisca o non raggiunga quel percorso **e** che il wrapper prosegua con il comando SSH; [`errexit` di Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e la gestione esplicita dello stato di uscita influiscono su questo flusso. Una configurazione debole della host key, un processo `sshpass` visibile o una directory temporanea scrivibile, da soli, non dimostrano questa catena. Durante l’enumerazione, esamina la pianificazione, lo script, la configurazione SSH e i metadati dei file senza reindirizzare il servizio né attivare il job.

Uno scheduler applicativo privilegiato può ricavare i job da righe di database invece che da file scrivibili. Per esempio, una voce cron di root che invoca [`php artisan schedule:run` di Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) può raggiungere codice applicativo che legge righe di task. Se un account meno privilegiato può scrivere una riga contenente un percorso locale e il callback pianificato chiama [`file_get_contents` di PHP](https://www.php.net/manual/en/function.file-get-contents.php) come root e invia il contenuto restituito a un webhook selezionato dalla riga, si tratta di un percorso di divulgazione di file privilegiato. Verifica l’identità cron, il callback effettivo dello scheduler e il flusso dei dati dalla riga al percorso, le autorizzazioni di scrittura nel database, la convalida dopo la lettura della riga e la destinazione in uscita. Un file `.env` applicativo leggibile è solo un indizio relativo alle credenziali; la convalida di un modulo web o una password del database, da soli, non dimostrano il controllo della riga o la divulgazione. Durante l’enumerazione, esamina passivamente la pianificazione, il codice e i permessi dei file delle credenziali, senza interrogare il database né pianificare un task.

Anche i job event-driven `incron` richiedono la stessa verifica: le [voci incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associano un percorso monitorato e un evento a un comando eseguito con l’identità del proprietario della tabella. Un utente meno privilegiato può influenzare indirettamente un file monitorato quando un’applicazione segue un link da una directory scrivibile e scrive nel file di destinazione del testo controllato dall’attaccante. Verifica il proprietario effettivo della tabella, l’evento, i permessi del file di destinazione e delle directory antenate, il comportamento dell’applicazione rispetto ai link e il modo in cui il testo diventa argomenti del comando. In particolare, [GNU Mailutils `mail` accetta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html) e il suo [comando shell-escape](https://mailutils.org/manual/html_node/Shell-Escapes.html) può eseguire un programma; un campo non attendibile passato come opzione separata a questa implementazione può portare all’esecuzione di comandi. Altre implementazioni di `mail` o un confine di argomenti fisso e quotato possono comportarsi diversamente. Durante l’enumerazione, esamina la pianificazione, il codice dell’applicazione e i metadati dei file senza modificare il file monitorato né attivare il job.

Anche un log monitorato può attraversare il confine tra utenti tramite uno script helper. Se un account meno privilegiato può scrivere nel log e il proprietario di `incron` legge un campo e lo inserisce in una nuova stringa di comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), la shell analizza nuovamente quel campo con l’identità del proprietario. Controlla l’evento monitorato esatto, i permessi del log e delle directory che lo contengono, il percorso dell’helper, la trasformazione del campo del log e se il comando risultante viene effettivamente raggiunto. La sola presenza di un log scrivibile e di una voce `incron` non dimostra il flusso dei dati; durante l’enumerazione passiva, non scrivere una riga trigger né eseguire l’helper.

I job di rinnovo dei certificati possono attraversare lo stesso confine. Un helper privilegiato può leggere il subject X.509 da un certificato in una directory scrivibile da un utente meno privilegiato e inserire il common name in una nuova stringa di comando `bash -c`. [OpenSSL può visualizzare il subject di un certificato e verificarne la scadenza](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analizza la stringa `-c` come input della shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), quindi quotare la variabile nello script esterno non protegge dalla seconda analisi. Prima di considerarlo command injection, verifica l’identità pianificata, il percorso di input esatto e i relativi permessi di scrittura, il ramo di rinnovo e il flusso dei dati verso `bash -c`. Esamina passivamente lo script e i metadati del certificato; durante l’enumerazione non attivare il rinnovo.

La stessa seconda analisi può verificarsi quando un job privilegiato pianificato estrae un nome dall’archivio o dal pacchetto di un utente meno privilegiato e lo passa a `xargs -I` affinché venga inserito in una stringa di comando `sh -c`. [GNU `xargs -I` sostituisce il segnaposto negli argomenti iniziali](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html) e [`sh -c` interpreta la stringa di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Anche se lo script esterno quota il nome estratto, ciò non rende sicuro un programma shell sostituito successivamente. Verifica l’identità usata dal job, il percorso di input accettato esatto e i permessi di scrittura, la convalida dell’archivio e le condizioni del ramo, nonché il flusso dal nome alla shell. Una directory di upload scrivibile o la sola invocazione di `xargs` sono soltanto indizi; durante l’enumerazione, esamina la pianificazione, lo script e i metadati dei percorsi senza inviare un pacchetto né eseguire il job.

Anche un importer pianificato di font o immagini può fidarsi dei nomi *interni* a un archivio fornito da un chiamante, anche quando il nome esterno del file caricato è soggetto a restrizioni. FontForge ha corretto la command injection nei nomi dei membri degli archivi con la [modifica upstream per CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Verifica che un job con privilegi maggiori apra effettivamente un archivio da un percorso scrivibile da un utente meno privilegiato, la sua identità di esecuzione, la versione esatta di FontForge o la patch del vendor e il percorso di gestione dell’archivio. Una stringa di versione o una suffisso di upload consentito, da soli, non provano l’esecuzione. Durante l’enumerazione, esamina la pianificazione, i permessi dei percorsi e i metadati della build senza importare un archivio non attendibile.

Gli scanner di rete pianificati possono attraversare un confine diverso quando uno script personalizzato tratta il subject di un certificato TLS remoto come un nome di file locale. [Nmap NSE esegue gli script selezionati senza sandbox](https://nmap.org/book/nse-usage.html), quindi esamina lo script effettivo e verifica se un campo subject non attendibile viene unito a una directory di dati senza controlli di contenimento. La divulgazione di file richiede una destinazione che lo scheduler analizzi, un percorso che corrisponda a un file leggibile dall’identità usata dallo scanner e un report o log accessibile a un utente meno privilegiato. Un campo di certificato o la sola presenza di uno scanner installato non dimostrano questa catena; durante l’enumerazione passiva, esamina la pianificazione, lo script, la risoluzione del percorso e la destinazione del report senza analizzare una nuova destinazione.

Un comando cron privilegiato che passa un glob shell come `/path/to/tasks/*.yml` a un runner Ansible merita un controllo dei permessi della directory, anche quando tutti i playbook esistenti sono in sola lettura. Un utente con accesso in scrittura e ricerca alla directory interessata dal glob potrebbe creare un altro playbook corrispondente. [I playbook Ansible definiscono i task eseguiti dal runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), ma un wrapper personalizzato può filtrare i percorsi o usare un’identità diversa: prima di considerare la directory un percorso di esecuzione, verifica il suo comportamento, l’utente cron effettivo, l’espansione della shell, le ACL, lo sticky bit e le policy di mount. Durante l’enumerazione, esamina staticamente i metadati e il wrapper; non eseguire il job pianificato.

Un wrapper cron privilegiato può passare i nomi dei file di una directory di upload a un helper Perl dopo aver espanso un glob. L’operatore diamond di Perl [`<>` usa `open` a due argomenti](https://perldoc.perl.org/perlop#The-Null-Filehandle), quindi un nome corrispondente interpretato come comando pipe può essere eseguito con l’identità dell’helper; [`<<>>` tratta gli argomenti come nomi di file letterali](https://perldoc.perl.org/perlop#The-Null-Filehandle). Verifica l’identità dello scheduler, la directory di lavoro del wrapper e il glob, la gestione effettiva di `@ARGV` nell’helper, le restrizioni sui nomi dei file e se un’identità meno privilegiata può inserire un nome corrispondente tramite i permessi del filesystem o un servizio di upload autenticato. Una voce cron, uno script Perl o una directory FTP scrivibile, da soli, non dimostrano la catena completa. Durante l’enumerazione, esamina il codice sorgente e i metadati senza inviare un nome file appositamente creato né eseguire il job.

Uno script cron in sola lettura è comunque sostituibile se l’account pianificato lo esegue tramite pathname e l’utente meno privilegiato può scrivere nella directory che lo contiene e attraversarla, quando non ha lo sticky bit. Controlla l’identità usata dal job, ogni componente del percorso, lo sticky bit della directory, le ACL e le policy di mount; esamina i metadati senza spostare il file né eseguire il job.

Un wrapper cron PHP privilegiato può raggiungere un helper che ancora non esiste. Se invoca PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) con il percorso assoluto fisso di un helper, un utente meno privilegiato che può creare quel nome nella directory che lo contiene può controllare ciò che un’esecuzione successiva avvierà. Verifica che la voce cron esegua effettivamente il wrapper con l’identità privilegiata, la stringa di comando esatta e le policy di esecuzione PHP, i permessi di scrittura e ricerca sulla directory dell’helper, il comportamento di symlink e sticky bit e se il percorso dell’helper è ancora assente. Una directory scrivibile o un helper mancante, da soli, sono soltanto indizi; durante l’enumerazione, esamina la pianificazione, il sorgente e i metadati del percorso senza creare l’helper né attivare il job.

Un job pianificato può anche individuare script di input con `find` e passarli a un interpreter. Per esempio, la funzione `system()` di [gnuplot invoca una shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), quindi un job privilegiato che esegue `gnuplot` su ogni file `*.plt` in una directory scrivibile da un utente meno privilegiato può eseguire comandi con l’identità del job. [Il permesso di lettura della directory controlla l’elenco dei contenuti, mentre scrittura e ricerca (`x`) controllano la creazione e l’accesso ai nomi conosciuti](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); controlla i permessi di scrittura e ricerca anche quando `ls` non può elencare la directory. Correlaziona l’identità e il comando esatti dello scheduler, il comportamento dell’interpreter, il pattern selezionato per i file e i permessi della directory; una directory scrivibile o la sola presenza di un interpreter installato non dimostrano l’escalation. Le pianificazioni private e i job di breve durata possono richiedere un’osservazione autorizzata degli eventi, poiché uno snapshot dei processi può non rilevarli.

Per un job PHP privilegiato, esamina le istruzioni letterali `include`/`require` come parte della catena di script eseguibili. [PHP valuta i file inclusi](https://www.php.net/manual/en/function.include.php), quindi un file `.php` scrivibile dal gruppo può eseguire codice con l’identità del job anche quando lo script principale è in sola lettura. Verifica l’identità pianificata, la risoluzione effettiva dell’include path, i permessi del file e delle directory e se il job viene effettivamente eseguito; una riga cron di esempio in un commento è solo un indizio. La stessa verifica si applica a un [server integrato PHP](https://www.php.net/commandline.webserver) di proprietà di root, avviato con `-S` e `-t <document-root>`: anche un listener loopback può eseguire PHP dell’applicazione per richieste locali. Durante l’enumerazione, esamina il processo e il sorgente senza attivare nessuno dei due trigger.

Un job PHP privilegiato può anche attraversare il confine tramite un **file di dati**: se un utente meno privilegiato può modificare il file esatto passato a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP può invocare il metodo `__wakeup()` o `__unserialize()` di una classe caricata durante il ripristino dell’oggetto. Esamina l’identità effettiva del job, i permessi del file e delle directory antenate, le classi caricate e gli effetti collaterali reali dei metodi, come una scrittura su file selezionata da una proprietà. Un log scrivibile o la sola chiamata a `unserialize()` non dimostrano un percorso utilizzabile. Durante l’enumerazione, esamina il sorgente e i metadati senza scrivere input serializzato né eseguire il job.

Un task cron di root può invocare il **CLI page runner** di un’applicazione PHP invece del server web. Segui la document root e l’URI selezionati dal runner fino all’entrypoint PHP effettivo; se l’account del servizio web può scrivere in quell’entrypoint, la richiesta CLI pianificata può eseguire come root il codice modificato, anche quando il runner e il wrapper cron sono in sola lettura. Verifica l’identità dello scheduler, la risoluzione URI-file esatta, i permessi effettivi del file e delle directory antenate e se un controllo di integrità protegge l’entrypoint stesso. Durante l’enumerazione, esamina il sorgente e i metadati senza invocare il runner né modificare la pagina.

Un processo `ipython` avviato da un job pianificato o da un altro utente da una directory di lavoro condivisa merita una verifica dei file di avvio. Le [note di rilascio di sicurezza di IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) spiegano che le build interessate cercavano profili e configurazioni nella directory corrente, incluso il codice in `profile_default/startup`, prima della correzione per CVE-2022-21699. Correlaziona la build installata effettiva o la patch del vendor, la directory di lavoro del comando, l’identità del processo con privilegi maggiori e la possibilità per l’utente meno privilegiato di scrivere e attraversare il percorso di avvio esatto. La sola presenza di `ipython`, di una directory scrivibile o di una stringa di versione non dimostra che un’altra identità caricherà un file da quel percorso. Durante l’enumerazione, esamina la pianificazione e i metadati del percorso senza avviare l’interpreter con privilegi maggiori.

Per un server PHP privilegiato che chiama funzioni di un’estensione nativa personalizzata, prima di esaminare l’estensione, ricostruisci la SAPI PHP del servizio e il suo `php.ini` effettivo, oltre ai file `.ini` scansionati. [PHP carica all’avvio le librerie `extension` configurate](https://www.php.net/manual/en/ini.core.php) e [le SAPI CLI e web possono usare file di configurazione diversi](https://www.php.net/manual/en/configuration.file.php). Un modulo di login raggiungibile o un listener locale può quindi passare stringhe controllate dall’utente a codice compilato eseguito con l’identità del servizio. Registra `User=`, `ExecStart=`, la directory di lavoro, il percorso effettivo dell’estensione e gli argomenti controllabili dal chiamante dell’unità; la sola presenza di un `.so` o di un socket loopback non dimostra una vulnerabilità di memory corruption. Analizza separatamente gli eventuali parser personalizzati, senza inviare probe durante l’enumerazione passiva.

Quando un wrapper privilegiato calcola l’hash di uno script tramite pathname e in seguito apre di nuovo quel pathname per eseguirlo, il digest autentica solo l’oggetto letto durante la prima apertura. Se un utente meno privilegiato può sostituire la voce di directory dello script tra le due aperture, la successiva esecuzione può risolvere un oggetto diverso anche se il file originale appartiene a root. Una FIFO può prolungare la fase di controllo, ma il percorso dipende dai permessi sostituibili delle directory antenate, da aperture effettivamente separate, dall’identità dello scheduler, dalle regole su sticky bit e mount e dalla tempistica. Esamina il wrapper e l’output di `namei -l` come indizio passivo; un checksum corretto non dimostra che il pathname successivo sia protetto.

Un job di backup privilegiato può anche **divulgare** dati senza eseguire comandi forniti dall’attaccante. Verifica se un utente meno privilegiato può creare un file di controllo letto dal job, se il job apre poi una sorgente protetta come `/etc/shadow` e se un URL selezionato dall’attaccante o un output leggibile riceve il risultato. Verifica tutti e tre gli elementi prima di definirlo un percorso di divulgazione. Un comando shell fisso nello stesso script non trasforma di per sé quel file di controllo in un input di shell injection. Durante l’enumerazione, esamina lo script e i permessi dei file senza eseguire il job né inserire un file di controllo.

Se un job privilegiato pianificato esegue `curl -K FILE` o `curl --config FILE`, [curl tratta le opzioni contenute in quel file come argomenti della riga di comando](https://curl.se/docs/manpage.html). Un utente meno privilegiato che controlla il file esatto al momento in cui curl lo legge può influenzare l’URL richiesto, l’input da file locale o il percorso di output. Prima di ipotizzare una lettura o scrittura protetta, verifica l’identità effettiva del job, i permessi di scrittura del file e delle directory antenate, la tempistica di eventuali altri job che sostituiscono il file e il modo in cui le opzioni di configurazione interagiscono con quelle fisse della riga di comando. Un percorso di configurazione scrivibile o la presenza visibile del flag `-K`, da soli, non dimostrano che le opzioni scelte abbiano effetto; durante l’enumerazione passiva, esamina la pianificazione e i metadati senza eseguire il job né scaricare un URL.

Se una voce cron invoca uno script helper, esamina anche la directory di lavoro dell’helper e il comando per l’archivio. Un wildcard non quotato in una directory scrivibile da un altro utente può trasformare i nomi dei file in opzioni dell’archiver; le azioni checkpoint di GNU tar sono un esempio. Prima di ipotizzare un percorso di comando tra utenti, verifica l’identità usata dal job, la directory di input scrivibile, l’archiver e le opzioni esatte e se `--` termina l’analisi delle opzioni. Vedi il comportamento di [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Una divulgazione distinta tramite file di backup può verificarsi quando un helper privilegiato esegue `cd INPUT_DIR; tar ... *` senza verificare che `cd` sia riuscito. Se un utente meno privilegiato può rimuovere o sostituire `INPUT_DIR`, un `cd` fallito può lasciare la shell nella directory precedente, che il successivo comando di archiviazione potrebbe leggere. Verifica la directory di lavoro iniziale del job, un percorso reale che provochi il fallimento di `cd`, se lo script termina o usa `&&`, le opzioni esatte dell’archiver e se l’archivio risultante è leggibile dall’utente meno privilegiato. Una directory di input scrivibile o un archivio leggibile sono soltanto indizi; esamina l’helper e i permessi del percorso senza modificare il job attivo.

Un eseguibile pianificato può nascondere uno script shell invece di eliminare il relativo confine di fiducia: [SHc](https://github.com/neurobin/shc) racchiude il testo cifrato dello script in un binario nativo e lo esegue tramite una shell a runtime. Un suffisso `.sh.x` o un ELF opaco sono solo indizi da approfondire. Per valutare l’injection di opzioni tramite nomi di file, accerta l’identità dello scheduler privilegiato, la directory di lavoro e il comando effettivi dell’helper, la possibilità per un utente meno privilegiato di creare nomi corrispondenti in quella directory e se un glob non quotato raggiunge un comando come `rsync` senza un confine tra opzioni e argomenti. L’opzione remote-shell di [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) è rilevante solo se viene usato esattamente quel percorso di comando. Una visibilità limitata di `/proc` o una decifratura statica non riuscita lasciano il comando sconosciuto; non eseguire l’helper privilegiato solo per classificarlo.

Anche il testo della riga di comando di un processo può essere un input non attendibile per un helper privilegiato. Un utente meno privilegiato può scegliere un titolo del processo o `argv[0]` che corrisponde a `pgrep -f`; un nome corrispondente non autentica l’eseguibile né il suo proprietario. Se uno script eseguito come root acquisisce quel testo, ne riscrive una parte in `apache2ctl`/`httpd` ed esegue il risultato senza un array di argomenti fisso, le opzioni scelte dall’attaccante possono selezionare una directory di configurazione o un error log diversi. L’analisi della configurazione Apache può caricare moduli o raggiungere helper configurati: durante l’enumerazione non convalidare come root una configurazione non attendibile. Esamina il proprietario dello scheduler, l’helper esatto, l’identità del processo e il flusso dai dati agli argomenti; si tratta di injection di opzioni/configurazione, salvo che venga dimostrata separatamente l’esecuzione tramite metacaratteri shell.

Un parser eseguito come root che passa testo non attendibile all’aritmetica di Bash può eseguire sostituzioni contenute in quel testo. La [guida all’escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) fornisce un esempio dettagliato. Prima di considerare sfruttabile ogni espressione aritmetica, verifica la sorgente dell’input e il comando di parsing.

Per un job privilegiato che analizza un log applicativo, segui i campi non attendibili oltre la prima analisi. Un account meno privilegiato può riuscire a scrivere nel log tramite il gruppo di processi corrente o influenzando i campi delle richieste registrate; un record può quindi selezionare un’immagine, i cui metadati diventano un secondo pathname usato per aprire un file XML. Verifica l’identità effettiva del job, l’effettivo accesso in scrittura al log, la gestione dei delimitatori, il contenimento canonico del percorso e se il file XML selezionato è controllato dall’attaccante. L’espansione di external entity può trasformare questa seconda lettura in una divulgazione privilegiata di file se il risultato espanso raggiunge un output leggibile da un utente meno privilegiato. La [guida alla sicurezza dell’elaborazione XML in Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta i controlli per l’accesso a DTD/entity esterni; esamina il parser installato e le sue impostazioni effettive. Un log o un file XML scrivibile, da solo, è soltanto un indizio. Durante l’enumerazione, esamina il codice e i metadati senza fornire input al parser pianificato.

Esamina anche i job privilegiati che materializzano file dal repository Git di un altro utente. Uno script può usare `git ls-tree` e `git cat-file` invece di `git checkout`, ma fidarsi comunque dei percorsi dell’albero controllati dall’attaccante quando li unisce a una directory di staging. I percorsi assoluti e i componenti `..` possono uscire da quella directory, a meno che la destinazione non venga normalizzata e verificata per il contenimento prima della scrittura. `git -c safe.directory=*` consente l’accesso a repository con proprietari diversi; da solo, non crea la condizione di scrittura arbitraria.

Un backup del database eseguito come root può creare un altro confine di proprietà. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia gli ulteriori file regolari presenti nella directory dati sorgente e il formato plain predefinito scrive i file in `-D` come albero di directory. Se un account meno privilegiato può creare o modificare quei file sorgente, esamina la proprietà e i permessi della destinazione risultante, se il percorso è attraversabile ed eseguibile e se il mount ha `nosuid`. Una copia di proprietà di root che conserva i permessi set-ID può essere pericolosa; un backup solo tar, permessi rimossi o una destinazione inaccessibile non dimostrano lo stesso percorso. Segui il wrapper pianificato e l’utente effettivo prima di considerare il comando di backup un finding.

## Osservare i job di breve durata

Un singolo snapshot dei processi può non rilevare un job che viene eseguito per pochi millisecondi. Confronta le dichiarazioni di timer/cron con i log e, quando autorizzato, con il monitoraggio degli eventi di processo, ad esempio `pspy` o audit. Correlaziona il proprietario del job pianificato, la riga di comando esatta e i file letti o scritti dal task. Una UI web dello scheduler in ascolto su loopback è un’interfaccia separata; vedi l’[esempio Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
