# Cron Jobs और Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

Scheduled tasks मौजूदा shell से अलग identity और environment के साथ चल सकते हैं। cron, `at`, anacron और systemd timers की सूची बनाएँ, फिर हर scheduled command को उसकी scripts, imports, working directory और writable inputs के ज़रिए trace करें।

## Schedules की सूची बनाएँ

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontab में आमतौर पर user field होता है; user के crontab में नहीं। वास्तविक scheduler के प्रभावी PATH और environment की जाँच करें। `run-parts --test /etc/cron.daily` दिखाता है कि उस host पर कौन-से file names चुने जाएँगे। Control characters किसी entry को सामान्य output में छिपा सकते हैं, इसलिए जब कोई schedule संदिग्ध लगे, तो `cat -A` या `sed -n l` का उपयोग करें।

## Privileged file और command resolution का पता लगाएँ

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

लिखने योग्य script chains, `EnvironmentFile=` paths, drop-ins, symlinks, relative commands, wildcard expansion, और privileged task द्वारा copy या execute की गई binaries की जाँच करें। Timer अपनी `Unit=` setting के ज़रिए अलग नाम वाली service activate कर सकता है। मुख्य primitives की जानकारी [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md), और [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) pages में है।

Root द्वारा चलाए जाने वाले scheduled `chkrootkit` script के लिए, पुराने [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) के लिए installed source देखें: `SLAPPER_FILES` temporary path की जाँच के बाद बिना quotes वाला `file_port=$file_port $i` उस file को execute कर सकता है। वास्तविक script या vendor patch, root scheduling, निचले privilege वाले user की exact temporary path पर write access, उसका executable status, और mount policy सत्यापित करें। केवल version string या `chkrootkit` की मौजूदगी से यह path साबित नहीं होता; passive review के दौरान temporary file न बनाएँ और न चलाएँ।

जब timer की root service `systemctl restart <other>.service` चलाती है, तो एक और unit hop trace करें: restarted unit ऐसा shell चला सकती है जिसमें script निचले privilege वाले user के लिए writable हो। प्रभावी `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, exact `ExecStart=` arguments, और script तथा उसके parent path की permissions की पुष्टि करें। Writable script केवल एक candidate है, जब तक timer और restarted service उसी execution context में active न हों; किसी भी service को restart किए बिना unit properties देखें।

अगर कोई higher-privileged job hostname से script fetch करती है और response shell को देती है, तो remote script के साथ यह भी जाँचें कि hostname resolution को कौन नियंत्रित करता है। Writable `/etc/hosts` file—जिसमें किसी group या ACL से मिला access भी शामिल है—ऐसे name को redirect कर सकती है जिसे job स्थानीय रूप से resolve करती है। `curl` response cross-user execution path तभी बनता है, जब वास्तविक scheduled command उस response को चलाए और job प्रभावित resolver path का उपयोग करे। Job की run-as identity, exact URL और shell pipeline, प्रभावी proxy/DNS behavior, तथा file और parent-directory permissions सत्यापित करें। Writable hosts file अपने आप में केवल review का संकेत है, privileged consumer का प्रमाण नहीं। Enumeration के दौरान mapping बदले या script fetch किए बिना schedule और metadata देखें।

Privileged scheduled `wget` fetch, file-write की एक अलग सीमा है—भले ही downloaded body सीधे execute न की जाए। [GNU Wget 1.18 ने CVE-2016-4971 ठीक करने के लिए default HTTP-to-FTP redirect filename handling बदली](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); पुराने प्रभावित builds redirected FTP filename का उपयोग कर सकते थे, जबकि `--trust-server-names` उस behavior का स्पष्ट अनुरोध करता है। अगर lower-trust पक्ष HTTP response और FTP resource नियंत्रित करता है, तो देखें कि job redirect follow करती है या नहीं, उसका वास्तविक Wget build या vendor backport क्या है, output options, run-as identity, working directory क्या हैं, और destination filename startup file बन सकती है या नहीं। [Wget `WGETRC` या `$HOME/.wgetrc` load करता है](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), और [उसकी settings POST source या output path चुन सकती हैं](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); बाद में होने वाला privileged fetch, उससे संभावित disclosure या write के लिए एक अलग prerequisite है। `authbind` के ज़रिए low port तक access तभी प्रासंगिक है, जब caller वास्तव में वह URL serve कर सके जिसे job request करती है। Redirect serve किए या job चलाए बिना configuration और logs को passive रूप से देखें। [`disk` group के ज़रिए raw block-device access](../user-information/interesting-groups-linux-pe/README.md#disk-group) इस network-fetch path से स्वतंत्र है।

Scripts के साथ data files भी trace करें। कोई scheduled simulation या orchestration tool ऐसी YAML file पढ़ सकती है जो शुरू किए जाने वाले processes परिभाषित करती है; अगर lower-privileged user वह file edit कर सकता है और job उसे किसी दूसरे account के तहत चलाती है, तो data job की identity के तहत commands बन सकता है। Writable YAML file को execution path मानने से पहले exact scheduled command, effective user, file path, parser semantics, और write access—parent directories सहित—सत्यापित करें। Passive triage के लिए schedule और file metadata पढ़ना पर्याप्त है; enumeration के दौरान job न चलाएँ और उसका input न बदलें।

जब higher-privileged job `ssh -F` चलाकर ऐसी file इस्तेमाल करती है जिसे lower-privileged user replace कर सकता है, तो SSH client configuration भी executable input है। OpenSSH का [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) client के shell के ज़रिए local command चलाता है, जबकि `Host`/`Match` और पहले के options तय करते हैं कि वह directive लागू होगी या नहीं। इसे cross-user execution path कहने से पहले exact scheduled SSH invocation, run-as identity, चुना गया config path, directory और file की write permissions, तथा प्रभावी option order का मिलान करें। ये records देखें; job न चलाएँ और privileged account के रूप में untrusted config load न करें।

अगर scheduled `scp` के बाद copied script चलाने के लिए `ssh` किया जाता है, और lower-privileged user destination SSH service नियंत्रित करता है, तो एक और trust-boundary review ज़रूरी है। अगर वह service connection को दूसरे host पर forward कर सकती है, तो privileged client अनपेक्षित endpoint से authenticate कर सकता है; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) बदली हुई host key से सुरक्षा कमज़ोर करता है, हालाँकि OpenSSH की बाकी पाबंदियाँ और प्रभावी per-host options लागू रहते हैं। Job की run-as identity, वास्तविक destination और authentication method, remote command की प्रभावी identity, तथा redirected host पर वही destination path writable है या पहले से मौजूद है—इनकी पुष्टि करें। पुराने या attacker-controlled file का execution तभी संभव है, जब copy विफल हो या उस path को छोड़ दे **और** wrapper अपने SSH command तक जारी रहे; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) और explicit status handling इस flow को प्रभावित करते हैं। कमज़ोर host-key setting, दिखता हुआ `sshpass` process, या writable temporary directory अकेले इस chain को साबित नहीं करते। Enumeration के दौरान service redirect किए या job trigger किए बिना schedule, script, SSH configuration, और file metadata देखें।

Privileged application scheduler अपनी jobs writable files के बजाय database rows से भी ले सकता है। उदाहरण के लिए, root cron entry जो Laravel का [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) चलाती है, ऐसे application code तक पहुँच सकती है जो task rows पढ़ता है। अगर lower-privileged account local pathname वाली row लिख सकता है, और scheduled callback root के तहत PHP [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) call करके लौटाए गए body को row द्वारा चुने webhook पर भेजता है, तो यह privileged file-disclosure path है। Cron identity, वास्तविक scheduler callback और row-to-path data flow, database write authorization, row पढ़ने के बाद होने वाला validation, तथा outbound destination सत्यापित करें। पढ़ी जा सकने वाली application `.env` केवल credentials का सुराग है; web-form validation या database password अकेले row control या disclosure साबित नहीं करते। Enumeration के दौरान database query किए या task schedule किए बिना schedule, code, और credential-file permissions को passive रूप से देखें।

Event-driven `incron` jobs की भी ऐसी ही जाँच करें: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) watched path और event को table के owner की identity के तहत चलने वाले command से जोड़ती हैं। जब कोई application writable directory के link को follow करके attacker-controlled text watched target में लिखती है, तो lower-privileged user उस watched file को अप्रत्यक्ष रूप से प्रभावित कर सकता है। वास्तविक table owner, event, target और ancestor permissions, application का link-following behavior, तथा वह text command arguments में कैसे बदलता है—सत्यापित करें। खास तौर पर, [GNU Mailutils `mail` `--exec` स्वीकार करता है](https://mailutils.org/manual/html_node/Invoking-Mail.html), और उसका [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) program चला सकता है; उस implementation में अलग option के रूप में दिया गया untrusted field command execution तक पहुँच सकता है। दूसरे `mail` implementations या quoted, fixed argument boundary का behavior अलग हो सकता है। Enumeration के दौरान watched file बदले या job trigger किए बिना schedule, application code, और file metadata देखें।

Watched log भी helper script के ज़रिए user boundary पार कर सकता है। अगर lower-privileged account log लिख सकता है और `incron` owner उसमें से कोई field पढ़कर नई [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) में डालता है, तो shell उस field को owner की identity के तहत फिर से parse करती है। Exact watched event, log और parent permissions, helper path, log field का transformation, और resulting command तक पहुँचने की पुष्टि करें। Writable log और `incron` entry दिखना अकेले data flow साबित नहीं करता; passive enumeration के दौरान trigger line न लिखें और helper न चलाएँ।

Certificate-renewal jobs भी यही boundary पार कर सकती हैं। कोई privileged helper lower-privileged writable directory में मौजूद certificate से X.509 subject पढ़कर उसका common name नई `bash -c` command string में डाल सकता है। [OpenSSL certificate का subject दिखा सकता है और उसकी expiry जाँच सकता है](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash `-c` string को shell input की तरह parse करता है](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), इसलिए outer script में variable को quote करना दूसरे parse को सुरक्षित नहीं बनाता। इसे command injection कहने से पहले scheduled identity, exact input path और write rights, renewal branch, तथा `bash -c` तक data flow की पुष्टि करें। Enumeration के दौरान renewal trigger किए बिना script और certificate metadata को passive रूप से देखें।

जब privileged scheduled job lower-privileged user के archive या package से name निकालकर उसे `xargs -I` के ज़रिए `sh -c` command string में डालती है, तब भी वही दूसरा parse हो सकता है। [GNU `xargs -I` शुरुआती arguments में placeholder को replace करता है](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), और [`sh -c` अपनी command string को interpret करता है](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)। भले outer script निकाले गए name को quote करे, बाद में substituted shell program इससे सुरक्षित नहीं हो जाता। Job की run-as identity, exact accepted input path और write access, archive validation और branch conditions, तथा name-to-shell data flow सत्यापित करें। Writable upload directory या `xargs` invocation अकेले केवल सुराग हैं; enumeration के दौरान package submit किए या job चलाए बिना schedule, script, और path metadata देखें।

Scheduled font या image importer भी caller-supplied archive के *अंदर* मौजूद names पर भरोसा कर सकता है, भले upload का बाहरी filename restricted हो। FontForge ने [CVE-2024-25081 और CVE-2024-25082 के लिए upstream change](https://github.com/fontforge/fontforge/pull/5367) में archive member-name command injection ठीक किया। पुष्टि करें कि higher-privileged job वास्तव में lower-privileged writable path से archive खोलती है, उसकी run-as identity क्या है, exact FontForge build या vendor backport कौन-सा है, और archive-handling code path लागू होता है या नहीं। Version string या permitted upload suffix अकेले execution का प्रमाण नहीं है। Enumeration के दौरान untrusted archive import किए बिना schedule, path permissions, और build metadata देखें।

Scheduled network scanners एक अलग boundary पार कर सकते हैं, जब custom script remote TLS certificate subject को local filename की तरह इस्तेमाल करती है। [Nmap NSE चुनी गई scripts sandbox के बिना चलाता है](https://nmap.org/book/nse-usage.html), इसलिए वास्तविक script देखें और जाँचें कि वह containment checks के बिना untrusted subject field को data directory के साथ जोड़ती है या नहीं। File disclosure के लिए scheduler द्वारा scan किया जाने वाला target, scanner की run-as identity द्वारा पढ़ी जा सकने वाली file तक resolve होने वाला path, और lower-privileged reader तक पहुँचने वाली report या log—तीनों ज़रूरी हैं। Certificate field या installed scanner अकेले इस chain को साबित नहीं करते; passive enumeration के दौरान नया target scan किए बिना schedule, script, path resolution, और report destination देखें।

Privileged cron command, जो `/path/to/tasks/*.yml` जैसे shell glob को Ansible runner को देती है, directory permissions की जाँच की माँग करती है—भले हर मौजूदा playbook केवल read-only हो। Globbed directory में write और search access वाला user एक और matching playbook बना सकता है। [Ansible playbooks वे tasks परिभाषित करती हैं जिन्हें runner चलाता है](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), लेकिन custom wrapper paths filter कर सकती है या दूसरी identity इस्तेमाल कर सकती है: directory को execution path मानने से पहले उसका behavior, वास्तविक cron user, shell expansion, ACLs, sticky bit, और mount policy सत्यापित करें। Enumeration के दौरान scheduled job चलाए बिना metadata और wrapper को static रूप से देखें।

Privileged cron wrapper glob expand करने के बाद upload directory के filenames Perl helper को दे सकती है। Perl का [`<>` diamond operator two-argument `open` का उपयोग करता है](https://perldoc.perl.org/perlop#The-Null-Filehandle), इसलिए command pipe की तरह interpret हुआ matching filename helper की identity के तहत execute हो सकता है; [`<<>>` arguments को literal filenames मानता है](https://perldoc.perl.org/perlop#The-Null-Filehandle)। Scheduler identity, wrapper working directory और glob, helper का वास्तविक `@ARGV` handling, filename restrictions, तथा filesystem rights या authenticated upload service के ज़रिए lower-privileged identity matching name रख सकती है या नहीं—इनकी पुष्टि करें। Cron line, Perl script, या writable FTP directory अकेले पूरी chain साबित नहीं करते। Enumeration के दौरान crafted filename submit किए या job चलाए बिना source और metadata देखें।

Read-only cron script भी replace की जा सकती है, अगर scheduled account उसे pathname से चलाता है और lower-privileged user उसकी non-sticky parent directory में लिख तथा traverse कर सकता है। Schedule की run-as identity, path का हर component, directory sticky bit, ACLs, और mount policy जाँचें; file को move किए या job चलाए बिना metadata देखें।

Privileged PHP cron wrapper ऐसे helper तक पहुँच सकती है जो अभी मौजूद नहीं है। अगर वह PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) को fixed absolute helper path के साथ call करती है, तो उसके parent directory में वह name बना सकने वाला lower-privileged user बाद के run द्वारा execute की जाने वाली चीज़ नियंत्रित कर सकता है। पुष्टि करें कि cron entry वास्तव में wrapper को higher identity के तहत चलाती है, exact command string और PHP execution policy क्या हैं, helper directory पर write और search rights क्या हैं, symlink तथा sticky-bit behavior क्या है, और helper path अभी भी अनुपस्थित है या नहीं। Writable directory या missing helper अकेले केवल सुराग हैं; enumeration के दौरान helper बनाए या job trigger किए बिना schedule, source, और path metadata देखें।

Scheduled job `find` से input scripts खोजकर हर script interpreter को दे सकती है। उदाहरण के लिए, [gnuplot का `system()` function shell invoke करता है](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), इसलिए lower-privileged user की writable directory में हर `*.plt` file पर `gnuplot` चलाने वाली privileged job अपने identity के तहत commands execute कर सकती है। [Directory की read permission listing नियंत्रित करती है, जबकि write और search (`x`) permissions से known names बनाए और access किए जा सकते हैं](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); अगर `ls` directory list नहीं कर सकता, तब भी write और search access जाँचें। Exact scheduler identity और command, interpreter का behavior, चुना गया file pattern, और directory permissions का मिलान करें; writable directory या installed interpreter अकेले escalation साबित नहीं करते। Private schedules और थोड़े समय चलने वाली jobs के लिए अधिकृत event observation ज़रूरी हो सकता है, क्योंकि एक process snapshot उन्हें छोड़ सकता है।

Privileged PHP job के लिए executable script chain के हिस्से के रूप में literal `include`/`require` statements भी देखें। [PHP included files को evaluate करता है](https://www.php.net/manual/en/function.include.php), इसलिए group-writable included `.php` file job की identity के तहत code चला सकती है, भले मुख्य script read-only हो। Scheduled identity, प्रभावी include-path resolution, file और directory permissions, तथा job वास्तव में चलती है या नहीं—इनकी पुष्टि करें; comment में sample cron line केवल एक संकेत है। यही समीक्षा root-owned [PHP built-in server](https://www.php.net/commandline.webserver) पर भी लागू होती है, जिसे `-S` और `-t <document-root>` के साथ शुरू किया गया हो: loopback listener भी local requests के लिए application PHP execute कर सकता है। Enumeration के दौरान किसी भी trigger को invoke किए बिना process और source देखें।

Privileged PHP job **data file** के ज़रिए भी boundary पार कर सकती है: अगर lower-privileged user [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) को दी गई exact file बदल सकता है, तो PHP object restore करते समय loaded class का `__wakeup()` या `__unserialize()` method invoke कर सकता है। Job की effective identity, file और ancestor permissions, loaded classes, तथा method के वास्तविक side effects—जैसे property से चुनी गई file write—देखें। Writable log या `unserialize()` call अकेले usable path साबित नहीं करते। Enumeration के दौरान serialized input लिखे या job चलाए बिना source और metadata देखें।

Root cron task web server के बजाय PHP application का **CLI page runner** चला सकती है। Runner के चुने हुए document root और URI को वास्तविक PHP entrypoint तक trace करें; अगर वह entrypoint web-service account के लिए writable है, तो runner और cron wrapper read-only होने पर भी scheduled CLI request उसका बदला हुआ code root के रूप में execute कर सकती है। Scheduler identity, exact URI-to-file resolution, प्रभावी file और ancestor permissions, तथा entrypoint integrity check से सुरक्षित है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान runner invoke किए या page बदले बिना source और metadata देखें।

Shared working directory से scheduled job या किसी अन्य user द्वारा शुरू किए गए `ipython` process के startup files की जाँच करें। [IPython के security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) बताते हैं कि CVE-2022-21699 के fix से पहले प्रभावित builds current directory में profiles और configuration खोजते थे, जिनमें `profile_default/startup` code भी शामिल था। वास्तविक installed build या vendor patch, command working directory, higher-privileged process identity, तथा exact startup path में write और search करने की lower-privileged user की क्षमता का मिलान करें। Installed `ipython`, writable directory, या version string अकेले यह साबित नहीं करते कि कोई दूसरी identity वहाँ की file load करेगी। Higher-privileged interpreter launch किए बिना schedule और path metadata देखें।

Custom native extension के functions call करने वाले privileged PHP server के लिए extension की जाँच से पहले service का PHP SAPI और उसकी प्रभावी `php.ini` तथा scanned `.ini` files trace करें। [PHP startup पर configured `extension` libraries load करता है](https://www.php.net/manual/en/ini.core.php), और [CLI तथा web SAPIs अलग-अलग configuration files इस्तेमाल कर सकते हैं](https://www.php.net/manual/en/configuration.file.php)। इसलिए reachable login form या local listener user-controlled strings को service identity के तहत चल रहे compiled code तक पहुँचा सकता है। Unit का `User=`, `ExecStart=`, working directory, वास्तविक extension path, और caller-controlled arguments दर्ज करें; केवल `.so` की मौजूदगी या loopback socket से memory-corruption flaw साबित नहीं होता। Passive enumeration के दौरान probes भेजने के बजाय किसी custom parser का अलग से विश्लेषण करें।

जब privileged wrapper किसी script को pathname से hash करती है और बाद में execute करने के लिए उसी pathname को फिर खोलती है, तो digest केवल पहले open में पढ़े गए object को authenticate करता है। अगर lower-privileged user उन दोनों opens के बीच script की directory entry replace कर सकता है, तो बाद का execution किसी दूसरे object तक resolve हो सकता है, भले original script file root-owned हो। FIFO check phase को लंबा कर सकती है, लेकिन यह path बदल सकने वाली parent-directory permissions, वास्तव में अलग-अलग opens होने, scheduler identity, sticky-bit और mount rules, तथा timing पर निर्भर है। Wrapper और `namei -l` output को passive lead की तरह देखें; सफल checksum यह साबित नहीं करता कि बाद वाला pathname सुरक्षित है।

Privileged backup job attacker-supplied commands execute किए बिना भी data **disclose** कर सकती है। Trace करें कि lower-privileged user ऐसी control file बना सकता है या नहीं जिसे job पढ़ती है, फिर job `/etc/shadow` जैसे protected source को खोलती है या नहीं, और attacker द्वारा चुने गए URL या पढ़े जा सकने वाले output तक उसका परिणाम पहुँचता है या नहीं। इसे disclosure path कहने से पहले तीनों हिस्सों की पुष्टि करें। उसी script में fixed shell command होने से control file अपने आप shell-injection input नहीं बनती। Enumeration के दौरान job चलाए या control file रखे बिना script और file permissions देखें।

अगर privileged scheduled job `curl -K FILE` या `curl --config FILE` चलाती है, तो [curl उस file के options को command-line arguments की तरह मानता है](https://curl.se/docs/manpage.html)। जब curl file पढ़ता है, उस समय उसे नियंत्रित करने वाला lower-privileged user requested URL, local-file input, या output path प्रभावित कर सकता है। Protected read या write का दावा करने से पहले job की effective identity, file और ancestor पर write rights, file बदलने वाले किसी दूसरे job का timing, तथा config options और fixed command-line options के आपसी प्रभाव की पुष्टि करें। Writable config path या दिखता हुआ `-K` flag अकेले यह साबित नहीं करता कि चुने गए options प्रभावी होंगे; passive enumeration के दौरान job चलाए या URL fetch किए बिना schedule और metadata देखें।

अगर cron entry helper script invoke करती है, तो helper की working directory और archive command भी देखें। किसी दूसरे user की writable directory पर unquoted wildcard filenames को archiver options में बदल सकता है; GNU tar के checkpoint actions इसका एक उदाहरण हैं। Cross-user command path का दावा करने से पहले scheduled run-as identity, writable input directory, exact archiver और options, तथा `--` option parsing रोकता है या नहीं—इनकी पुष्टि करें। देखें [wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md)।

Backup-file का एक अलग disclosure तब हो सकता है जब privileged helper `cd INPUT_DIR; tar ... *` चलाती है और यह जाँच नहीं करती कि `cd` सफल हुआ या नहीं। अगर lower-privileged user `INPUT_DIR` हटा या replace कर सकता है, तो `cd` विफल होने पर shell पिछली directory में रह सकती है, जिसे बाद की archive command पढ़ सकती है। Job की शुरुआती working directory, `cd` विफल होने का वास्तविक path, script exit करती है या `&&` इस्तेमाल करती है, exact archiver options, और output archive lower user पढ़ सकता है या नहीं—इनकी पुष्टि करें। Writable input directory या readable archive अकेले केवल सुराग हैं; live job बदले बिना helper और path permissions देखें।

Scheduled executable shell script को छिपा सकती है, लेकिन इससे trust boundary खत्म नहीं होती: [SHc](https://github.com/neurobin/shc) encrypted script text को native binary में wrap करता है और runtime पर shell के ज़रिए execute करता है। `.sh.x` suffix या opaque ELF केवल review का संकेत है। Filename option injection का आकलन करने के लिए privileged scheduler identity, helper की वास्तविक working directory और command, वहाँ matching names बनाने की lower-user की क्षमता, तथा unquoted glob `rsync` जैसी command तक बिना option boundary के पहुँचता है या नहीं—इनकी पुष्टि करें। [`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) तभी प्रासंगिक है, जब वही exact command path इस्तेमाल हो। Restricted `/proc` visibility या विफल static decryption के कारण command अज्ञात रहने पर, केवल classification के लिए privileged helper न चलाएँ।

Process command-line text भी privileged helper के लिए untrusted input है। Lower-privileged user ऐसा process title या `argv[0]` चुन सकता है जो `pgrep -f` से match करे; matching name executable या उसके owner को authenticate नहीं करता। अगर root-run script वह text capture करके उसका कुछ हिस्सा `apache2ctl`/`httpd` में rewrite करती है और fixed argument array के बिना result execute करती है, तो attacker-chosen options अलग configuration directory या error log चुन सकते हैं। Apache configuration parsing modules load कर सकती है या configured helpers तक पहुँच सकती है, इसलिए enumeration के दौरान root के रूप में untrusted configuration validate न करें। Scheduler owner, exact helper, process identity, और data-to-argument flow देखें; यह option/configuration injection है, जब तक shell metacharacter execution अलग से साबित न हो।

जो root-run parser untrusted text को Bash arithmetic में डालता है, वह उस text में मौजूद substitutions execute कर सकता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) में worked example दिया गया है। हर arithmetic expression को exploitable मानने से पहले input source और parsing command की पुष्टि करें।

Privileged job द्वारा application log parse किए जाने पर, पहले parse के बाद भी untrusted fields trace करें। Lower-privileged account अपनी वर्तमान process group के ज़रिए log लिख सकता है या logged request fields प्रभावित कर सकता है; कोई record फिर image चुन सकता है, जिसका metadata XML खोलने के लिए दूसरी pathname बन जाता है। Job की effective identity, वास्तविक log-write access, delimiter handling, canonical path containment, और चुनी गई XML attacker-controlled है या नहीं—इनकी जाँच करें। अगर expanded result lower-privileged user द्वारा पढ़े जा सकने वाले output तक पहुँचता है, तो external-entity expansion इस दूसरे read को privileged file disclosure में बदल सकती है। [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) external DTD/entity access के controls बताती है; installed parser और उसकी प्रभावी settings देखें। Writable log या XML file अकेले केवल सुराग हैं। Enumeration के दौरान scheduled parser को input दिए बिना code और metadata देखें।

ऐसे privileged jobs भी देखें जो किसी दूसरे user के Git repository से files बनाती हैं। कोई script `git checkout` के बजाय `git ls-tree` और `git cat-file` इस्तेमाल कर सकती है, फिर भी staging directory के साथ attacker-controlled tree paths जोड़ते समय उन पर भरोसा कर सकती है। Absolute paths और `..` components उस directory से बाहर जा सकते हैं, जब तक लिखने से पहले destination को normalize करके containment जाँचा न जाए। `git -c safe.directory=*` अलग ownership वाले repositories तक access की अनुमति देता है; इससे अपने आप arbitrary-write condition नहीं बनती।

Root-run database backup एक और ownership boundary बना सकता है। PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) source data directory में रखी अतिरिक्त regular files की copy करता है, और उसका default plain format `-D` में directory tree के रूप में files लिखता है। अगर lower-privileged account वे source files बना या बदल सकता है, तो resulting destination का ownership और mode, उसका path traversable और executable है या नहीं, तथा mount पर `nosuid` है या नहीं—इनकी जाँच करें। Preserved set-ID permissions वाली root-owned copy ख़तरनाक हो सकती है; tar-only backup, stripped permissions, या inaccessible destination से वैसा path साबित नहीं होता। Backup command को finding मानने से पहले scheduled wrapper और effective user trace करें।

## थोड़े समय चलने वाले कामों को देखें

एक process snapshot milliseconds तक चलने वाली job को छोड़ सकता है। Timer/cron declarations की logs से तुलना करें और, अधिकृत होने पर, `pspy` या audit जैसे process-event monitoring का उपयोग करें। Scheduled owner, exact command line, और task द्वारा पढ़ी या लिखी जाने वाली files का मिलान करें। Loopback scheduler web UI एक अलग interface है; देखें [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc)।
