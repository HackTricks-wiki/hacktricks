# Tâches cron et timers systemd

{{#include ../../banners/hacktricks-training.md}}

Les tâches planifiées peuvent s’exécuter avec une identité et un environnement différents de ceux du shell actuel. Énumérez cron, `at`, anacron et les timers systemd, puis suivez chaque commande planifiée à travers ses scripts, ses imports, son répertoire de travail et ses entrées modifiables.

## Énumérer les tâches planifiées

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Les crontabs système incluent généralement un champ utilisateur, contrairement aux crontabs d’un utilisateur. Examinez le PATH effectif et l’environnement du scheduler réel. `run-parts --test /etc/cron.daily` indique les noms de fichiers qui seraient sélectionnés sur cet hôte. Les caractères de contrôle peuvent masquer une entrée dans un affichage ordinaire ; utilisez donc `cat -A` ou `sed -n l` si une planification semble suspecte.

## Tracer la résolution des fichiers et commandes privilégiés

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Examinez les chaînes de scripts modifiables, les chemins `EnvironmentFile=`, les drop-ins, les liens symboliques, les commandes relatives, l’expansion des jokers et les binaires copiés ou exécutés par une tâche privilégiée. Un timer peut activer un service portant un autre nom via son paramètre `Unit=`. Les pages [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) et [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) présentent les principaux mécanismes.

Pour un script `chkrootkit` planifié et exécuté en tant que root, examinez le code source installé afin de repérer l’ancien [défaut de guillemets dans slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) : après la vérification d’un chemin temporaire `SLAPPER_FILES`, l’affectation non protégée `file_port=$file_port $i` peut exécuter ce fichier. Vérifiez le script réel ou le correctif du fournisseur, l’exécution planifiée en tant que root, les droits d’écriture d’un utilisateur de moindre privilège sur le chemin temporaire exact, son statut exécutable et la politique de montage. La chaîne de version ou la seule présence de `chkrootkit` ne suffit pas à établir ce chemin ; ne créez ni n’exécutez de fichier temporaire lors d’un examen passif.

Suivez un saut d’unité supplémentaire lorsqu’un service root lancé par un timer exécute `systemctl restart <other>.service` : l’unité redémarrée peut appeler un shell avec un script modifiable par un utilisateur de moindre privilège. Confirmez les valeurs effectives de `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, les arguments exacts de `ExecStart=` et les permissions du script et de son répertoire parent. Un script modifiable n’est qu’une piste tant que le timer et le service redémarré ne sont pas actifs dans ce contexte d’exécution ; inspectez les propriétés des unités sans redémarrer aucun des deux services.

Si une tâche de privilèges supérieurs récupère un script via un nom d’hôte et transmet la réponse à un shell, vérifiez qui contrôle la résolution de ce nom d’hôte, ainsi que le script distant. Un fichier `/etc/hosts` modifiable, y compris par les droits accordés à un groupe ou par une ACL, peut rediriger un nom que la tâche résout localement ; une réponse `curl` ne constitue un chemin d’exécution entre utilisateurs que si la commande planifiée exécute réellement cette réponse et si la tâche utilise le chemin de résolution concerné. Vérifiez l’identité d’exécution de la tâche, l’URL exacte et le pipeline shell, le comportement effectif du proxy/DNS, ainsi que les permissions du fichier et de son répertoire parent. Un fichier hosts modifiable est un indice à examiner, pas la preuve de l’existence d’un consommateur privilégié. Examinez la planification et les métadonnées sans modifier la correspondance ni récupérer le script pendant l’inventaire.

Un `wget` privilégié planifié constitue une frontière distincte d’écriture de fichier, même si le contenu téléchargé n’est jamais exécuté directement. [GNU Wget 1.18 a modifié le comportement par défaut concernant le nom de fichier des redirections HTTP vers FTP pour corriger CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html) ; les anciennes versions concernées pouvaient utiliser le nom de fichier de la redirection FTP, tandis que `--trust-server-names` demande explicitement ce comportement. Si une partie moins fiable contrôle la réponse HTTP et la ressource FTP, vérifiez si la tâche suit cette redirection, la version réelle de Wget ou le correctif rétroporté du fournisseur, les options de sortie, l’identité d’exécution, le répertoire de travail et la possibilité que le nom de destination devienne un fichier de démarrage. [Wget charge `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), et [ses paramètres peuvent sélectionner une source POST ou un chemin de sortie](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html) ; une récupération ultérieure privilégiée est un prérequis distinct pour toute divulgation ou écriture qui en résulterait. L’accès à un port bas via `authbind` n’est pertinent que si l’appelant peut effectivement servir l’URL demandée par la tâche. Examinez la configuration et les journaux passivement, sans servir de redirection ni exécuter la tâche. [L’accès brut aux périphériques bloc via le groupe `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) est indépendant de ce chemin de récupération réseau.

Suivez aussi les fichiers de données, pas uniquement les scripts. Un outil de simulation ou d’orchestration planifié peut lire un fichier YAML qui définit les processus à démarrer ; si un utilisateur de moindre privilège peut modifier ce fichier et que la tâche l’exécute sous un autre compte, les données peuvent devenir des commandes exécutées avec l’identité de la tâche. Vérifiez la commande planifiée exacte, l’utilisateur effectif, le chemin du fichier, la sémantique de l’analyseur et les droits d’écriture, y compris sur les répertoires parents, avant de considérer un fichier YAML modifiable comme un chemin d’exécution. La lecture de la planification et des métadonnées du fichier suffit pour un triage passif ; n’exécutez pas la tâche et ne modifiez pas son entrée pendant l’inventaire.

La configuration d’un client SSH constitue également une entrée exécutable lorsqu’une tâche de privilèges supérieurs lance `ssh -F` avec un fichier qu’un utilisateur de moindre privilège peut remplacer. Le [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) d’OpenSSH exécute une commande locale via le shell du client, tandis que `Host`/`Match` et les options précédentes déterminent si cette directive s’applique. Recoupez l’invocation SSH planifiée exacte, l’identité d’exécution, le chemin de configuration sélectionné, les droits d’écriture sur le fichier et le répertoire, ainsi que l’ordre effectif des options, avant de conclure à un chemin d’exécution entre utilisateurs. Examinez ces éléments sans exécuter la tâche ni charger la configuration non fiable en tant que compte privilégié.

Un `scp` planifié suivi d’un `ssh` qui exécute le script copié exige un examen supplémentaire de la frontière de confiance lorsque le service SSH de destination est contrôlé par un utilisateur de moindre privilège. Si ce service peut transférer la connexion vers un autre hôte, le client privilégié peut s’authentifier auprès d’un point de terminaison inattendu ; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) affaiblit la protection contre les clés d’hôte modifiées, sous réserve des autres restrictions d’OpenSSH et des options effectives par hôte. Déterminez l’identité d’exécution de la tâche, la destination réelle et la méthode d’authentification, l’identité effective de la commande distante, et si le même chemin de destination est modifiable ou préexistant sur l’hôte redirigé. L’exécution d’un ancien fichier ou d’un fichier contrôlé par un attaquant exige aussi que la copie échoue ou ne trouve pas ce chemin **et** que le wrapper poursuive avec sa commande SSH ; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) et la gestion explicite des codes de retour influent sur ce déroulement. Un paramètre de clé d’hôte faible, un processus `sshpass` visible ou un répertoire temporaire modifiable ne suffisent pas à établir cette chaîne. Examinez la planification, le script, la configuration SSH et les métadonnées des fichiers sans rediriger le service ni déclencher la tâche pendant l’inventaire.

Un ordonnanceur d’application privilégié peut obtenir ses tâches depuis des lignes de base de données plutôt que depuis des fichiers modifiables. Par exemple, une entrée cron root qui lance [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) de Laravel peut atteindre du code d’application qui lit des lignes de tâche. Si un compte de moindre privilège peut écrire une ligne contenant un chemin local et que le callback planifié appelle [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) de PHP en tant que root, puis transmet le corps renvoyé à un webhook choisi dans une ligne, il s’agit d’un chemin de divulgation de fichiers privilégié. Vérifiez l’identité cron, le callback réel de l’ordonnanceur et le flux des données de la ligne vers le chemin, les droits d’écriture dans la base de données, la validation après lecture de la ligne et la destination sortante. Un `.env` d’application lisible n’est qu’une piste de credential ; la validation d’un formulaire Web ou un mot de passe de base de données ne prouve ni le contrôle de la ligne ni la divulgation. Examinez passivement la planification, le code et les permissions du fichier de credentials, sans interroger la base de données ni planifier une tâche pendant l’inventaire.

Les tâches `incron` déclenchées par des événements méritent le même examen : les [entrées incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associent un chemin surveillé et un événement à une commande exécutée avec l’identité du propriétaire de la table. Un utilisateur de moindre privilège peut influencer indirectement un fichier surveillé lorsqu’une application suit un lien depuis un répertoire modifiable et écrit du texte contrôlé par un attaquant dans la cible surveillée. Vérifiez le propriétaire réel de la table, l’événement, la cible et les permissions de ses répertoires parents, le comportement de l’application concernant le suivi des liens et la façon dont ce texte devient des arguments de commande. En particulier, [GNU Mailutils `mail` accepte `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), et sa [commande d’échappement vers le shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) peut lancer un programme ; un champ non fiable passé comme option distincte à cette implémentation peut mener à l’exécution de commandes. D’autres implémentations de `mail`, ou une frontière d’arguments fixe et correctement citée, peuvent se comporter différemment. Examinez la planification, le code de l’application et les métadonnées des fichiers sans modifier le fichier surveillé ni déclencher la tâche pendant l’inventaire.

Un journal surveillé peut également franchir une frontière entre utilisateurs via un script auxiliaire. Si un compte de moindre privilège peut écrire dans le journal et que le propriétaire d’`incron` lit un champ de ce journal pour le placer dans une nouvelle chaîne de commande [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), le shell analyse de nouveau ce champ avec l’identité du propriétaire. Vérifiez l’événement surveillé exact, les permissions du journal et de ses répertoires parents, le chemin du script auxiliaire, la transformation du champ du journal et si la commande obtenue est effectivement exécutée. La présence d’un journal modifiable et d’une entrée `incron` ne suffit pas à établir le flux de données ; n’écrivez pas de ligne de déclenchement et n’exécutez pas le script auxiliaire lors d’un inventaire passif.

Les tâches de renouvellement de certificats peuvent franchir la même frontière. Un outil privilégié peut lire le sujet X.509 d’un certificat situé dans un répertoire modifiable par un utilisateur de moindre privilège et insérer son nom commun dans une nouvelle chaîne de commande `bash -c`. [OpenSSL peut afficher le sujet d’un certificat et vérifier sa date d’expiration](https://docs.openssl.org/3.3/man1/openssl-x509/) ; [Bash analyse la chaîne `-c` comme une entrée shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), donc citer la variable dans le script externe ne protège pas contre la seconde analyse. Confirmez l’identité planifiée, le chemin d’entrée exact et les droits d’écriture, la branche de renouvellement et le flux de données vers `bash -c` avant de conclure à une injection de commandes. Examinez le script et les métadonnées du certificat passivement ; ne déclenchez pas le renouvellement pendant l’inventaire.

La même seconde analyse peut se produire lorsqu’une tâche privilégiée extrait un nom de l’archive ou du paquet d’un utilisateur de moindre privilège et le transmet à `xargs -I` pour l’insérer dans une chaîne de commande `sh -c`. [GNU `xargs -I` remplace le marqueur dans les arguments initiaux](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), et [`sh -c` interprète sa chaîne de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Même si le script externe cite le nom extrait, cela ne sécurise pas un programme shell substitué ultérieurement. Vérifiez l’identité d’exécution de la tâche, le chemin d’entrée exact accepté et ses droits d’écriture, la validation de l’archive et les conditions de branchement, ainsi que le flux du nom vers le shell. Un répertoire de téléversement modifiable ou une invocation de `xargs` ne sont que des pistes ; examinez la planification, le script et les métadonnées du chemin sans soumettre de paquet ni exécuter la tâche pendant l’inventaire.

Un importateur de polices ou d’images planifié peut également faire confiance aux noms *à l’intérieur* d’une archive fournie par l’appelant, même si le nom de fichier externe du téléversement est restreint. FontForge a corrigé l’injection de commandes via le nom des membres d’archive dans sa [modification en amont pour CVE-2024-25081 et CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirmez qu’une tâche de privilèges supérieurs ouvre effectivement une archive depuis un chemin modifiable par un utilisateur de moindre privilège, son identité d’exécution, la version exacte de FontForge ou le correctif rétroporté du fournisseur, ainsi que le chemin de traitement de l’archive. Une chaîne de version ou un suffixe de téléversement autorisé ne prouve pas à lui seul qu’il y a exécution. Examinez la planification, les permissions du chemin et les métadonnées de la version sans importer d’archive non fiable pendant l’inventaire.

Les scanners réseau planifiés peuvent franchir une autre frontière lorsqu’un script personnalisé traite le sujet d’un certificat TLS distant comme un nom de fichier local. [Nmap NSE exécute les scripts sélectionnés sans bac à sable](https://nmap.org/book/nse-usage.html) ; examinez donc le script réel et vérifiez s’il joint un champ de sujet non fiable à un répertoire de données sans contrôle de confinement. La divulgation de fichiers nécessite une cible que l’ordonnanceur va scanner, un chemin qui pointe vers un fichier lisible avec l’identité d’exécution du scanner, ainsi qu’un rapport ou journal accessible à un utilisateur de moindre privilège. Un champ de certificat ou la seule présence d’un scanner ne prouve pas cette chaîne ; examinez la planification, le script, la résolution du chemin et la destination du rapport sans scanner de nouvelle cible lors d’un inventaire passif.

Une commande cron privilégiée qui transmet un glob shell comme `/path/to/tasks/*.yml` à un exécuteur Ansible mérite de vérifier les permissions du répertoire, même si tous les playbooks existants sont en lecture seule. Un utilisateur disposant des droits d’écriture et de recherche dans le répertoire visé par le glob peut éventuellement y créer un autre playbook correspondant. [Les playbooks Ansible définissent les tâches exécutées par l’exécuteur](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mais un wrapper personnalisé peut filtrer les chemins ou utiliser une autre identité : vérifiez son comportement, l’utilisateur cron réel, l’expansion shell, les ACL, le sticky bit et la politique de montage avant de considérer le répertoire comme un chemin d’exécution. Examinez passivement les métadonnées et le wrapper ; n’exécutez pas la tâche planifiée pendant l’inventaire.

Un wrapper cron privilégié peut transmettre des noms de fichiers provenant d’un répertoire de téléversement à un auxiliaire Perl après l’expansion d’un glob. L’opérateur [`<>` de Perl utilise `open` à deux arguments](https://perldoc.perl.org/perlop#The-Null-Filehandle) ; un nom correspondant interprété comme une commande de pipe peut donc s’exécuter avec l’identité de l’auxiliaire. [`<<>>` traite les arguments comme des noms de fichiers littéraux](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirmez l’identité de l’ordonnanceur, le répertoire de travail et le glob du wrapper, le traitement réel de `@ARGV` par l’auxiliaire, les restrictions de noms de fichiers et la possibilité pour un utilisateur de moindre privilège de placer un nom correspondant via les droits du système de fichiers ou un service de téléversement authentifié. Une ligne cron, un script Perl ou un répertoire FTP modifiable ne prouve pas à lui seul la chaîne complète. Examinez le code source et les métadonnées sans soumettre de nom de fichier spécialement conçu ni exécuter la tâche pendant l’inventaire.

Un script cron en lecture seule peut quand même être remplacé si le compte planifié l’exécute par son chemin et si un utilisateur de moindre privilège peut écrire dans son répertoire parent non sticky et le traverser. Vérifiez l’identité d’exécution de la tâche, chaque composant du chemin, le sticky bit du répertoire, les ACL et la politique de montage ; examinez les métadonnées sans déplacer le fichier ni exécuter la tâche.

Un wrapper cron PHP privilégié peut atteindre un auxiliaire qui n’existe pas encore. S’il appelle [`exec()`](https://www.php.net/manual/en/function.exec.php) de PHP avec un chemin absolu fixe vers l’auxiliaire, un utilisateur de moindre privilège pouvant créer ce nom dans son répertoire parent peut contrôler ce qui sera exécuté lors d’une exécution ultérieure. Confirmez que l’entrée cron exécute réellement le wrapper avec l’identité supérieure, la chaîne de commande exacte et la politique d’exécution PHP, les droits d’écriture et de recherche sur le répertoire de l’auxiliaire, le comportement des liens symboliques et du sticky bit, et si le chemin de l’auxiliaire est toujours absent. Un répertoire modifiable ou un auxiliaire manquant ne sont que des pistes ; examinez la planification, le code source et les métadonnées du chemin sans créer l’auxiliaire ni déclencher la tâche.

Une tâche planifiée peut aussi découvrir des scripts d’entrée avec `find` et les transmettre à un interpréteur. Par exemple, la fonction `system()` de [gnuplot invoque un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf) ; une tâche privilégiée qui lance `gnuplot` sur chaque fichier `*.plt` d’un répertoire modifiable par un utilisateur de moindre privilège peut donc exécuter des commandes avec l’identité de la tâche. [Le droit de lecture d’un répertoire contrôle son affichage, tandis que les droits d’écriture et de recherche (`x`) contrôlent la création et l’accès aux noms connus](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html) ; vérifiez les droits d’écriture et de recherche même si `ls` ne peut pas lister le répertoire. Recoupez l’identité et la commande exactes de l’ordonnanceur, le comportement de l’interpréteur, le motif de fichier sélectionné et les permissions du répertoire ; un répertoire modifiable ou un interpréteur installé ne suffit pas à établir une élévation. Les tâches privées et de courte durée peuvent nécessiter une observation autorisée des événements, car un instantané des processus peut les manquer.

Pour une tâche PHP privilégiée, examinez les instructions littérales `include`/`require` dans la chaîne de scripts exécutables. [PHP évalue les fichiers inclus](https://www.php.net/manual/en/function.include.php) ; un fichier `.php` modifiable par le groupe peut donc exécuter du code avec l’identité de la tâche, même si le script principal est en lecture seule. Vérifiez l’identité planifiée, la résolution effective du chemin d’inclusion, les permissions du fichier et du répertoire, ainsi que l’exécution réelle de la tâche ; un exemple de ligne cron en commentaire n’est qu’un indice. Le même examen s’applique à un [serveur intégré PHP](https://www.php.net/commandline.webserver) appartenant à root et lancé avec `-S` et `-t <document-root>` : même en écoute sur l’interface loopback, il peut exécuter le PHP de l’application pour les requêtes locales. Examinez le processus et le code source sans déclencher l’un ou l’autre pendant l’inventaire.

Une tâche PHP privilégiée peut aussi franchir la frontière via un **fichier de données** : si un utilisateur de moindre privilège peut modifier le fichier exact transmis à [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP peut appeler la méthode `__wakeup()` ou `__unserialize()` d’une classe chargée lors de la restauration d’un objet. Examinez l’identité effective de la tâche, les permissions du fichier et de ses répertoires parents, les classes chargées et les effets réels de la méthode, par exemple une écriture de fichier dont la cible est choisie via une propriété. Un journal modifiable ou un appel à `unserialize()` ne suffit pas à prouver l’existence d’un chemin exploitable. Examinez le code source et les métadonnées sans écrire de données sérialisées ni exécuter la tâche pendant l’inventaire.

Une tâche cron root peut lancer le **gestionnaire de pages CLI** d’une application PHP plutôt que le serveur Web. Suivez le répertoire racine de documents et l’URI sélectionnés par le gestionnaire jusqu’au véritable point d’entrée PHP ; si le compte du service Web peut modifier ce point d’entrée, la requête CLI planifiée peut exécuter le code modifié en tant que root, même si le gestionnaire et le wrapper cron sont en lecture seule. Confirmez l’identité de l’ordonnanceur, la résolution exacte de l’URI vers le fichier, les permissions effectives du fichier et de ses répertoires parents, ainsi que l’existence d’un contrôle d’intégrité du point d’entrée lui-même. Examinez le code source et les métadonnées sans invoquer le gestionnaire ni modifier la page pendant l’inventaire.

Un processus `ipython` lancé par une tâche planifiée ou un autre utilisateur depuis un répertoire de travail partagé mérite un examen de ses fichiers de démarrage. Les [notes de version de sécurité d’IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) expliquent que les versions concernées recherchaient des profils et fichiers de configuration dans le répertoire courant, notamment du code dans `profile_default/startup`, avant la correction de CVE-2022-21699. Recoupez la version réellement installée ou le correctif du fournisseur, le répertoire de travail de la commande, l’identité du processus privilégié et la capacité de l’utilisateur de moindre privilège à écrire dans le chemin de démarrage exact et à le parcourir. La présence d’`ipython`, d’un répertoire modifiable ou d’une chaîne de version ne prouve pas à elle seule qu’une autre identité y chargera un fichier. Examinez la planification et les métadonnées du chemin sans lancer l’interpréteur privilégié.

Pour un serveur PHP privilégié qui appelle des fonctions d’une extension native personnalisée, déterminez le SAPI PHP du service, son `php.ini` effectif et les fichiers `.ini` analysés avant d’examiner l’extension. [PHP charge au démarrage les bibliothèques d’extension configurées](https://www.php.net/manual/en/ini.core.php), et [les SAPI CLI et Web peuvent utiliser des fichiers de configuration différents](https://www.php.net/manual/en/configuration.file.php). Un formulaire de connexion accessible ou un listener local peut donc transmettre des chaînes contrôlées par l’utilisateur à du code compilé exécuté avec l’identité du service. Consignez le `User=`, l’`ExecStart=`, le répertoire de travail, le chemin réel de l’extension et les arguments contrôlés par l’appelant ; la seule présence d’un `.so` ou d’un socket loopback ne prouve pas un défaut de corruption mémoire. Analysez séparément tout parseur personnalisé au lieu d’envoyer des probes pendant un inventaire passif.

Lorsqu’un wrapper privilégié calcule le hash d’un script par son chemin puis ouvre de nouveau ce chemin pour l’exécuter, le digest n’authentifie que l’objet lu lors de la première ouverture. Si un utilisateur de moindre privilège peut remplacer l’entrée de répertoire du script entre les deux ouvertures, la seconde exécution peut résoudre un autre objet, même si le fichier d’origine appartient à root. Un FIFO peut prolonger la phase de vérification, mais le chemin dépend des droits de remplacement des répertoires parents, des ouvertures réellement distinctes, de l’identité de l’ordonnanceur, des règles du sticky bit et du montage, ainsi que du timing. Examinez le wrapper et la sortie de `namei -l` comme pistes passives ; un checksum réussi ne prouve pas à lui seul que le chemin ultérieurement utilisé est protégé.

Une tâche de sauvegarde privilégiée peut également **divulguer** des données sans exécuter de commandes fournies par un attaquant. Déterminez si un utilisateur de moindre privilège peut créer un fichier de contrôle lu par la tâche, si celle-ci ouvre ensuite une source protégée telle que `/etc/shadow`, et si une URL choisie par l’attaquant ou une sortie lisible reçoit le résultat. Vérifiez ces trois éléments avant de conclure à un chemin de divulgation. La présence d’une commande shell fixe dans le même script ne suffit pas à faire de ce fichier de contrôle une entrée d’injection shell. Examinez le script et les permissions des fichiers sans exécuter la tâche ni déposer de fichier de contrôle pendant l’inventaire.

Si une tâche privilégiée planifiée exécute `curl -K FILE` ou `curl --config FILE`, [curl traite les options de ce fichier comme des arguments de ligne de commande](https://curl.se/docs/manpage.html). Un utilisateur de moindre privilège qui contrôle le fichier exact au moment où curl le lit peut influencer l’URL demandée, l’entrée d’un fichier local ou le chemin de sortie. Confirmez l’identité effective de la tâche, les droits d’écriture sur le fichier et ses répertoires parents, le moment où une autre tâche peut remplacer le fichier et l’interaction des options de configuration avec les options fixes de la ligne de commande avant de conclure à une lecture ou écriture protégée. Un chemin de configuration modifiable ou un indicateur `-K` visible ne prouvent pas à eux seuls que les options choisies prennent effet ; examinez la planification et les métadonnées sans exécuter la tâche ni récupérer d’URL lors d’un inventaire passif.

Si une entrée cron invoque un script auxiliaire, examinez également son répertoire de travail et sa commande d’archivage. Un joker non protégé par des guillemets dans un répertoire modifiable par un autre utilisateur peut transformer les noms de fichiers en options d’archive ; les actions de checkpoint de GNU tar en sont un exemple. Confirmez l’identité d’exécution planifiée, le répertoire d’entrée modifiable, l’archiveur et les options exacts, ainsi que la présence éventuelle de `--` pour terminer l’analyse des options avant de conclure à un chemin de commande entre utilisateurs. Voir [le comportement des wildcards et de tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Une divulgation distincte via un fichier de sauvegarde peut se produire lorsqu’un auxiliaire privilégié exécute `cd INPUT_DIR; tar ... *` sans vérifier si `cd` a réussi. Si un utilisateur de moindre privilège peut supprimer ou remplacer `INPUT_DIR`, un échec de `cd` peut laisser le shell dans son répertoire précédent, que la commande d’archivage suivante peut alors lire. Vérifiez le répertoire de travail initial de la tâche, l’existence d’un chemin où `cd` échoue réellement, la présence d’une sortie anticipée ou l’utilisation de `&&`, les options exactes de l’archiveur et la lisibilité de l’archive de sortie par l’utilisateur de moindre privilège. Un répertoire d’entrée modifiable ou une archive lisible ne sont que des pistes ; examinez l’auxiliaire et les permissions du chemin sans modifier la tâche active.

Un exécutable planifié peut masquer un script shell au lieu de supprimer sa frontière de confiance : [SHc](https://github.com/neurobin/shc) encapsule du texte de script chiffré dans un binaire natif et l’exécute via un shell à l’exécution. Un suffixe `.sh.x` ou un ELF opaque n’est qu’un indice à examiner. Pour évaluer l’injection d’options via les noms de fichiers, établissez l’identité de l’ordonnanceur privilégié, le répertoire de travail et la commande réels de l’auxiliaire, la capacité d’un utilisateur de moindre privilège à y créer des noms correspondants et la possibilité qu’un glob non protégé par des guillemets atteigne une commande comme `rsync` sans frontière d’options. L’option [`rsync` remote-shell](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) n’est pertinente que si ce chemin de commande exact est utilisé. Une visibilité restreinte de `/proc` ou l’échec du déchiffrement statique laisse la commande inconnue ; ne lancez pas l’auxiliaire privilégié simplement pour le classifier.

Le texte de la ligne de commande d’un processus est une autre entrée non fiable pour un auxiliaire privilégié. Un utilisateur de moindre privilège peut choisir un titre de processus ou un `argv[0]` correspondant à `pgrep -f` ; un nom correspondant n’authentifie ni l’exécutable ni son propriétaire. Si un script exécuté en tant que root capture ce texte, en réécrit une partie en `apache2ctl`/`httpd` et exécute le résultat sans tableau d’arguments fixe, des options choisies par l’attaquant peuvent sélectionner un autre répertoire de configuration ou journal d’erreurs. L’analyse de la configuration Apache peut charger des modules ou atteindre des auxiliaires configurés ; ne validez donc pas une configuration non fiable en tant que root pendant l’inventaire. Examinez le propriétaire de la tâche planifiée, l’auxiliaire exact, l’identité du processus et le flux des données vers les arguments ; il s’agit d’une injection d’options/configuration, sauf si l’exécution de métacaractères shell est démontrée séparément.

Un parseur exécuté en tant que root qui transmet du texte non fiable à l’arithmétique de Bash peut exécuter des substitutions présentes dans ce texte. Le [guide d’élévation de privilèges](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) présente un exemple détaillé. Confirmez la source de l’entrée et la commande d’analyse avant de considérer toute expression arithmétique comme exploitable.

Pour une tâche privilégiée qui analyse un journal d’application, suivez les champs non fiables au-delà de la première analyse. Un compte de moindre privilège peut parfois écrire dans le journal via son groupe de processus actuel ou influencer les champs de requête consignés ; un enregistrement peut alors sélectionner une image dont les métadonnées deviennent un second chemin utilisé pour ouvrir du XML. Vérifiez l’identité effective de la tâche, les droits réels d’écriture dans le journal, le traitement des délimiteurs, le confinement des chemins canoniques et le caractère contrôlable ou non du XML sélectionné par un attaquant. L’expansion d’entités externes peut transformer cette seconde lecture en divulgation de fichiers privilégiés si le résultat développé est transmis à une sortie lisible par un utilisateur de moindre privilège. Le [guide de sécurité du traitement XML Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documente les contrôles d’accès aux DTD/entités externes ; examinez l’analyseur installé et ses paramètres effectifs. Un journal ou un fichier XML modifiable ne sont que des pistes. Examinez le code et les métadonnées sans fournir d’entrée au parseur planifié pendant l’inventaire.

Examinez également les tâches privilégiées qui matérialisent des fichiers depuis le dépôt Git d’un autre utilisateur. Un script peut utiliser `git ls-tree` et `git cat-file` au lieu de `git checkout`, tout en faisant confiance aux chemins d’arborescence contrôlés par un attaquant lorsqu’il les joint à un répertoire de staging. Les chemins absolus et les composants `..` peuvent sortir de ce répertoire, à moins que la destination soit normalisée et vérifiée pour en garantir le confinement avant l’écriture. `git -c safe.directory=*` permet d’accéder aux dépôts dont le propriétaire est différent ; cela ne crée pas, à lui seul, une condition d’écriture arbitraire.

Une sauvegarde de base de données exécutée en tant que root peut créer une autre frontière de propriété. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copie les fichiers ordinaires supplémentaires placés dans le répertoire de données source, et son format plain par défaut écrit les fichiers dans `-D` sous forme d’arborescence. Si un utilisateur de moindre privilège peut créer ou modifier ces fichiers source, examinez la propriété et le mode des fichiers de destination, la possibilité de parcourir et d’exécuter le chemin, ainsi que la présence de l’option `nosuid` sur le montage. Une copie appartenant à root et conservant les permissions set-ID peut être dangereuse ; une sauvegarde au format tar uniquement, des permissions supprimées ou une destination inaccessible ne créent pas le même chemin. Suivez le wrapper planifié et l’utilisateur effectif avant de considérer la commande de sauvegarde comme un finding.

## Observer les tâches de courte durée

Un instantané unique des processus peut manquer une tâche qui ne s’exécute que pendant quelques millisecondes. Comparez les déclarations de timer/cron aux journaux et, lorsque cela est autorisé, à une surveillance des événements de processus telle que `pspy` ou audit. Recoupez le propriétaire de la tâche planifiée, la ligne de commande exacte et les fichiers lus ou écrits par la tâche. Une interface Web d’ordonnanceur accessible sur loopback constitue une interface distincte ; voir [l’exemple Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
