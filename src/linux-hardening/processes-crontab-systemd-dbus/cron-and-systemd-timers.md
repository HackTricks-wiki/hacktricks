# Cronjobs und Systemd-Timer

{{#include ../../banners/hacktricks-training.md}}

Geplante Aufgaben können mit einer anderen Identität und Umgebung als die aktuelle Shell ausgeführt werden. Ermittle cron-, `at`-, anacron- und systemd-Timer-Aufgaben und verfolge dann jeden geplanten Befehl durch seine Skripte, Importe, das Arbeitsverzeichnis und beschreibbare Eingaben.

## Zeitpläne ermitteln

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System-Crontabs enthalten normalerweise ein Benutzerfeld; die Crontab eines Benutzers nicht. Prüfe den effektiven PATH und die Umgebung des tatsächlichen Schedulers. `run-parts --test /etc/cron.daily` zeigt, welche Dateinamen auf diesem Host ausgewählt würden. Steuerzeichen können einen Eintrag in einer oberflächlichen Ausgabe verbergen. Verwende daher `cat -A` oder `sed -n l`, wenn ein Zeitplan verdächtig aussieht.

## Nachverfolgen der Auflösung privilegierter Dateien und Befehle

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Prüfe beschreibbare Skriptketten, `EnvironmentFile=`-Pfade, Drop-ins, Symlinks, relative Befehle, Wildcard-Expansion sowie Binärdateien, die von einer privilegierten Aufgabe kopiert oder ausgeführt werden. Ein Timer kann über seine `Unit=`-Einstellung einen Dienst mit einem anderen Namen aktivieren. Die Seiten [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) und [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) erklären die wichtigsten Grundlagen.

Prüfe bei einem geplanten, als root laufenden `chkrootkit`-Skript den installierten Quellcode auf den alten [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): Ein nicht in Anführungszeichen gesetztes `file_port=$file_port $i` nach einer Prüfung eines temporären `SLAPPER_FILES`-Pfads kann diese Datei ausführen. Verifiziere das tatsächliche Skript oder den Vendor-Patch, die Ausführung als root, Schreibzugriff eines niedrig privilegierten Benutzers auf den exakten temporären Pfad, dessen Ausführbarkeit und die Mount-Richtlinie. Eine Versionszeichenfolge oder das bloße Vorhandensein von `chkrootkit` belegt den Angriffsweg nicht; erstelle oder starte bei einer passiven Prüfung keine temporäre Datei.

Verfolge einen weiteren Unit-Schritt, wenn der Root-Dienst eines Timers `systemctl restart <other>.service` ausführt: Die neu gestartete Unit kann eine Shell mit einem Skript aufrufen, das für einen niedrig privilegierten Benutzer beschreibbar ist. Prüfe den effektiven Wert von `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, die exakten Argumente von `ExecStart=` sowie die Berechtigungen des Skripts und seines übergeordneten Pfads. Ein beschreibbares Skript ist nur ein möglicher Ansatzpunkt, solange Timer und neu gestarteter Dienst nicht in diesem Ausführungskontext aktiv sind. Prüfe die Unit-Eigenschaften, ohne einen der Dienste neu zu starten.

Wenn ein Job mit höheren Privilegien ein Skript über einen Hostnamen abruft und die Antwort an eine Shell weitergibt, prüfe neben dem Remote-Skript auch, wer die Auflösung dieses Hostnamens kontrolliert. Eine beschreibbare Datei `/etc/hosts`, einschließlich Schreibzugriff über eine Gruppe oder ACL, kann einen Namen umleiten, den der Job lokal auflöst. Eine `curl`-Antwort wird nur dann zu einem Ausführungspfad zwischen Benutzern, wenn der tatsächlich geplante Befehl diese Antwort ausführt und der Job den betroffenen Resolver-Pfad verwendet. Verifiziere die Identität, unter der der Job läuft, die exakte URL und Shell-Pipeline, das effektive Proxy-/DNS-Verhalten sowie die Berechtigungen der Datei und ihres übergeordneten Verzeichnisses. Eine beschreibbare hosts-Datei allein ist ein Prüfhinweis, kein Beweis für einen privilegierten Verbraucher. Prüfe Zeitplan und Metadaten, ohne die Zuordnung zu ändern oder das Skript während der Auflistung abzurufen.

Ein geplanter, privilegierter `wget`-Abruf bildet eine separate Dateischreibgrenze, selbst wenn der heruntergeladene Inhalt nie direkt ausgeführt wird. [GNU Wget 1.18 änderte die standardmäßige Behandlung von Dateinamen bei HTTP-zu-FTP-Weiterleitungen, um CVE-2016-4971 zu beheben](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); ältere betroffene Builds konnten den FTP-Zieldateinamen verwenden, während `--trust-server-names` dieses Verhalten ausdrücklich anfordert. Wenn eine Partei mit geringerem Vertrauensniveau die HTTP-Antwort und die FTP-Ressource kontrolliert, prüfe, ob der Job dieser Weiterleitung folgt, den tatsächlichen Wget-Build oder Vendor-Backport, Ausgabeoptionen, Ausführungsidentität, Arbeitsverzeichnis und ob der Zieldateiname zu einer Startdatei werden kann. [Wget lädt `WGETRC` oder `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), und [seine Einstellungen können eine POST-Quelle oder einen Ausgabepfad festlegen](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); ein späterer privilegierter Abruf ist eine separate Voraussetzung für jede daraus entstehende Offenlegung oder Schreiboperation. Zugriff auf einen niedrigen Port über `authbind` ist nur relevant, wenn der aufrufende Benutzer tatsächlich die URL bereitstellen kann, die der Job anfordert. Prüfe Konfiguration und Protokolle passiv, ohne eine Weiterleitung bereitzustellen oder den Job auszuführen. [Raw block-device access through the `disk` group](../user-information/interesting-groups-linux-pe/README.md#disk-group) ist unabhängig von diesem Netzwerkabruf.

Verfolge auch Datendateien, nicht nur Skripte. Ein geplanter Simulations- oder Orchestrierungstask kann eine YAML-Datei mit Definitionen der zu startenden Prozesse lesen. Kann ein niedrig privilegierter Benutzer diese Datei bearbeiten und läuft der Job unter einem anderen Konto, können die Daten zu Befehlen werden, die unter der Identität des Jobs ausgeführt werden. Prüfe den exakten geplanten Befehl, den effektiven Benutzer, den Dateipfad, die Parser-Semantik und den Schreibzugriff (einschließlich übergeordneter Verzeichnisse), bevor du eine beschreibbare YAML-Datei als Ausführungspfad einstufst. Für eine passive Triage genügen die Prüfung des Zeitplans und der Dateimetadaten; führe den Job nicht aus und ändere seine Eingabe nicht während der Auflistung.

Auch eine SSH-Client-Konfiguration ist ausführbarer Input, wenn ein Job mit höheren Privilegien `ssh -F` mit einer Datei ausführt, die ein niedrig privilegierter Benutzer ersetzen kann. OpenSSHs [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) führt über die Shell des Clients einen lokalen Befehl aus, während `Host`/`Match` und frühere Optionen bestimmen, ob diese Direktive gilt. Gleiche den exakten geplanten SSH-Aufruf, die Ausführungsidentität, den ausgewählten Konfigurationspfad, Schreibberechtigungen für Verzeichnis und Datei sowie die effektive Optionsreihenfolge ab, bevor du den Pfad als Ausführung zwischen Benutzern einstufst. Prüfe diese Einträge, ohne den Job auszuführen oder die nicht vertrauenswürdige Konfiguration als privilegierter Benutzer zu laden.

Ein geplantes `scp` mit anschließendem `ssh`, das das kopierte Skript ausführt, erfordert eine zusätzliche Prüfung der Vertrauensgrenze, wenn ein niedrig privilegierter Benutzer den Ziel-SSH-Dienst kontrolliert. Kann dieser Dienst die Verbindung zu einem anderen Host weiterleiten, authentifiziert sich der privilegierte Client möglicherweise an einem unerwünschten Endpunkt. [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) schwächt den Schutz gegen geänderte Host-Keys, vorbehaltlich der verbleibenden OpenSSH-Beschränkungen und der effektiven Host-spezifischen Optionen. Ermittle die Ausführungsidentität des Jobs, das tatsächliche Ziel und die Authentifizierungsmethode, die effektive Identität des Remote-Befehls sowie, ob derselbe Zielpfad auf dem umgeleiteten Host beschreibbar oder bereits vorhanden ist. Die Ausführung einer älteren oder vom Angreifer kontrollierten Datei erfordert zusätzlich, dass das Kopieren fehlschlägt oder diesen Pfad verfehlt **und** der Wrapper mit seinem SSH-Befehl fortfährt; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) und eine explizite Statusbehandlung beeinflussen diesen Ablauf. Eine schwache Host-Key-Einstellung, ein sichtbarer `sshpass`-Prozess oder ein beschreibbares temporäres Verzeichnis allein belegt diese Kette nicht. Prüfe Zeitplan, Skript, SSH-Konfiguration und Dateimetadaten, ohne den Dienst umzuleiten oder den Job während der Auflistung auszulösen.

Ein privilegierter Anwendungs-Scheduler kann seine Jobs aus Datenbankzeilen statt aus beschreibbaren Dateien beziehen. Beispielsweise kann ein Root-Cron-Eintrag, der Laravels [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) aufruft, Anwendungscode erreichen, der Task-Zeilen liest. Kann ein niedrig privilegiertes Konto eine Zeile mit einem lokalen Pfad schreiben und ruft der geplante Callback PHPs [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) als root auf und sendet den zurückgegebenen Inhalt an einen über die Zeile festgelegten Webhook, liegt ein privilegierter Pfad zur Dateioffenlegung vor. Prüfe die Cron-Identität, den tatsächlichen Scheduler-Callback und den Datenfluss von der Zeile zum Pfad, die Datenbank-Schreibberechtigung, die Validierung nach dem Lesen der Zeile sowie das ausgehende Ziel. Eine lesbare `.env`-Datei der Anwendung ist nur ein Hinweis auf Zugangsdaten; eine Webformular-Validierung oder ein Datenbankpasswort allein beweist weder die Kontrolle über die Zeile noch eine Offenlegung. Prüfe Zeitplan, Code und Berechtigungen der Zugangsdaten-Datei passiv, ohne während der Auflistung die Datenbank abzufragen oder einen Task zu planen.

Auch ereignisgesteuerte `incron`-Jobs verdienen dieselbe Prüfung: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) ordnen einem überwachten Pfad und Ereignis einen Befehl zu, der unter der Identität des Tabelleneigentümers läuft. Ein niedrig privilegierter Benutzer kann eine überwachte Datei indirekt beeinflussen, wenn eine Anwendung einem Link aus einem beschreibbaren Verzeichnis folgt und vom Angreifer kontrollierten Text in das überwachte Ziel schreibt. Prüfe den tatsächlichen Tabelleneigentümer, das Ereignis, Berechtigungen des Ziels und seiner übergeordneten Pfade, das Verhalten der Anwendung beim Folgen von Links und wie dieser Text zu Befehlsargumenten wird. Insbesondere akzeptiert [GNU Mailutils `mail` die Option `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), und sein [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) kann ein Programm ausführen; ein nicht vertrauenswürdiges Feld, das als separate Option an diese Implementierung übergeben wird, kann zur Befehlsausführung führen. Andere `mail`-Implementierungen oder eine in Anführungszeichen gesetzte, feste Argumentgrenze können sich anders verhalten. Prüfe Zeitplan, Anwendungscode und Dateimetadaten, ohne die überwachte Datei zu ändern oder den Job während der Auflistung auszulösen.

Ein überwachtes Protokoll kann über ein Hilfsskript ebenfalls eine Benutzergrenze überschreiten. Kann ein niedrig privilegiertes Konto in das Protokoll schreiben und liest der `incron`-Eigentümer daraus ein Feld in eine neue [`sh -c`-Befehlszeichenfolge](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), parst die Shell dieses Feld erneut unter der Identität des Eigentümers. Prüfe das genaue überwachte Ereignis, die Berechtigungen des Protokolls und seiner übergeordneten Pfade, den Hilfsskriptpfad, die Umwandlung des Protokollfelds und ob der resultierende Befehl tatsächlich erreicht wird. Ein beschreibbares Protokoll und ein `incron`-Eintrag allein belegen den Datenfluss nicht. Schreibe während der passiven Auflistung keine Trigger-Zeile und führe das Hilfsskript nicht aus.

Auch Zertifikat-Erneuerungsjobs können dieselbe Grenze überschreiten. Ein privilegiertes Hilfsprogramm kann den X.509-Subject eines Zertifikats in einem beschreibbaren Verzeichnis eines niedrig privilegierten Benutzers lesen und dessen Common Name in eine neue `bash -c`-Befehlszeichenfolge einsetzen. [OpenSSL kann den Subject eines Zertifikats anzeigen und dessen Ablauf prüfen](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash parst die `-c`-Zeichenfolge als Shell-Input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), daher schützt das Setzen der Variablen in Anführungszeichen im äußeren Skript nicht vor dem zweiten Parse. Prüfe die geplante Identität, den exakten Eingabepfad und dessen Schreibrechte, den Erneuerungszweig sowie den Datenfluss zu `bash -c`, bevor du den Fall als Command Injection einstufst. Prüfe Skript und Zertifikatsmetadaten passiv; löse während der Auflistung keine Erneuerung aus.

Ein solcher zweiter Parse kann auch stattfinden, wenn ein privilegierter geplanter Job einen Namen aus dem Archiv oder Paket eines niedrig privilegierten Benutzers extrahiert und ihn über `xargs -I` in eine `sh -c`-Befehlszeichenfolge einsetzt. [GNU `xargs -I` ersetzt den Platzhalter in den anfänglichen Argumenten](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), und [`sh -c` interpretiert seine Befehlszeichenfolge](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Selbst wenn das äußere Skript den extrahierten Namen in Anführungszeichen setzt, macht das ein später eingefügtes Shell-Programm nicht sicher. Prüfe die Ausführungsidentität des Jobs, den exakt akzeptierten Eingabepfad und dessen Schreibrechte, Archivvalidierung und Zweigbedingungen sowie den Datenfluss vom Namen zur Shell. Ein beschreibbares Upload-Verzeichnis oder ein `xargs`-Aufruf allein ist nur ein Hinweis. Prüfe Zeitplan, Skript und Pfadmetadaten, ohne während der Auflistung ein Paket einzureichen oder den Job auszuführen.

Ein geplanter Font- oder Bildimporter kann ebenso Namen *innerhalb* eines vom Benutzer bereitgestellten Archivs vertrauen, selbst wenn der äußere Upload-Dateiname eingeschränkt ist. FontForge behob die Command Injection über Archivmitgliedsnamen in der [upstream change for CVE-2024-25081 and CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Bestätige, dass ein Job mit höheren Privilegien tatsächlich ein Archiv aus einem für niedrig privilegierte Benutzer beschreibbaren Pfad öffnet, prüfe die Ausführungsidentität, den genauen FontForge-Build oder Vendor-Backport sowie den Codepfad zur Archivverarbeitung. Eine Versionszeichenfolge oder eine erlaubte Upload-Endung allein beweist keine Ausführung. Prüfe Zeitplan, Pfadberechtigungen und Build-Metadaten, ohne während der Auflistung ein nicht vertrauenswürdiges Archiv zu importieren.

Geplante Netzwerk-Scanner können eine andere Grenze überschreiten, wenn ein benutzerdefiniertes Skript den Subject eines Remote-TLS-Zertifikats als lokalen Dateinamen behandelt. [Nmap NSE führt ausgewählte Skripte ohne Sandbox aus](https://nmap.org/book/nse-usage.html); prüfe daher das tatsächliche Skript und ob es ein nicht vertrauenswürdiges Subject-Feld ohne Containment-Prüfungen an ein Datenverzeichnis anhängt. Eine Offenlegung von Dateien erfordert ein Ziel, das der Scheduler scannt, einen Pfad, der auf eine für die Ausführungsidentität des Scanners lesbare Datei aufgelöst wird, und einen Bericht oder ein Protokoll, das für einen niedrig privilegierten Leser zugänglich ist. Ein Zertifikatsfeld oder ein installierter Scanner allein belegt diese Kette nicht. Prüfe Zeitplan, Skript, Pfadauflösung und Berichtsziel, ohne während der passiven Auflistung ein neues Ziel zu scannen.

Ein privilegierter Cron-Befehl, der einen Shell-Glob wie `/path/to/tasks/*.yml` an einen Ansible-Runner übergibt, erfordert eine Prüfung der Verzeichnisberechtigungen, selbst wenn alle vorhandenen Playbooks schreibgeschützt sind. Ein Benutzer mit Schreib- und Suchzugriff auf das vom Glob erfasste Verzeichnis kann möglicherweise ein weiteres passendes Playbook erstellen. [Ansible-Playbooks definieren Tasks, die der Runner ausführt](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), aber ein benutzerdefinierter Wrapper kann Pfade filtern oder eine andere Identität verwenden. Prüfe dessen Verhalten, den tatsächlichen Cron-Benutzer, die Shell-Expansion, ACLs, das Sticky Bit und die Mount-Richtlinie, bevor du das Verzeichnis als Ausführungspfad einstufst. Prüfe Metadaten und Wrapper statisch; führe den geplanten Job während der Auflistung nicht aus.

Ein privilegierter Cron-Wrapper kann Dateinamen aus einem Upload-Verzeichnis nach Expansion eines Globs an ein Perl-Hilfsprogramm übergeben. Perl verwendet beim [`<>`-Diamond-Operator ein zweiparametriges `open`](https://perldoc.perl.org/perlop#The-Null-Filehandle), sodass ein passender Dateiname, der als Pipe-Befehl interpretiert wird, unter der Identität des Hilfsprogramms ausgeführt werden kann; [`<<>>` behandelt Argumente als wörtliche Dateinamen](https://perldoc.perl.org/perlop#The-Null-Filehandle). Bestätige die Scheduler-Identität, das Arbeitsverzeichnis des Wrappers und den Glob, die tatsächliche Verarbeitung von `@ARGV` durch das Hilfsprogramm, Dateinamensbeschränkungen sowie, ob eine niedrig privilegierte Identität über Dateisystemrechte oder einen authentifizierten Upload-Dienst einen passenden Namen ablegen kann. Eine Cron-Zeile, ein Perl-Skript oder ein beschreibbares FTP-Verzeichnis allein beweist nicht die vollständige Kette. Prüfe Quellcode und Metadaten, ohne einen präparierten Dateinamen einzureichen oder den Job während der Auflistung auszuführen.

Ein schreibgeschütztes Cron-Skript ist trotzdem ersetzbar, wenn das geplante Konto es über seinen Pfad ausführt und ein niedrig privilegierter Benutzer in sein übergeordnetes Verzeichnis schreiben und es durchsuchen kann, sofern dieses Verzeichnis kein Sticky Bit hat. Prüfe die Ausführungsidentität des Zeitplans, jede Pfadkomponente, das Sticky Bit des Verzeichnisses, ACLs und die Mount-Richtlinie. Prüfe die Metadaten, ohne die Datei zu verschieben oder den Job auszuführen.

Ein privilegierter PHP-Cron-Wrapper kann ein Hilfsprogramm aufrufen, das noch nicht existiert. Ruft er PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) mit einem festen absoluten Hilfsprogrammpfad auf, kann ein niedrig privilegierter Benutzer, der diesen Namen im übergeordneten Verzeichnis erstellen darf, kontrollieren, was bei einem späteren Lauf ausgeführt wird. Bestätige, dass der Cron-Eintrag den Wrapper tatsächlich mit der höheren Identität ausführt, prüfe die exakte Befehlszeichenfolge und PHP-Ausführungsrichtlinie, Schreib- und Suchrechte für das Hilfsprogramm-Verzeichnis, Symlink- und Sticky-Bit-Verhalten sowie, ob der Hilfsprogrammpfad noch fehlt. Ein beschreibbares Verzeichnis oder ein fehlendes Hilfsprogramm allein ist nur ein Hinweis. Prüfe Zeitplan, Quellcode und Pfadmetadaten, ohne das Hilfsprogramm zu erstellen oder den Job auszulösen.

Ein geplanter Job kann Eingabe-Skripte auch mit `find` suchen und jedes davon an einen Interpreter übergeben. Beispielsweise ruft [gnuplots `system()`-Funktion eine Shell auf](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf); ein privilegierter Job, der `gnuplot` für jede `*.plt`-Datei in einem für einen niedrig privilegierten Benutzer beschreibbaren Verzeichnis ausführt, kann daher Befehle mit der Identität des Jobs ausführen. [Leserechte für ein Verzeichnis steuern die Auflistung, während Schreib- und Suchrechte (`x`) das Erstellen und den Zugriff auf bekannte Namen steuern](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html). Prüfe daher Schreib- und Suchzugriff, auch wenn `ls` das Verzeichnis nicht auflisten kann. Gleiche die genaue Scheduler-Identität und den Befehl, das Verhalten des Interpreters, das ausgewählte Dateimuster und die Verzeichnisberechtigungen ab. Ein beschreibbares Verzeichnis oder ein installierter Interpreter allein belegt keine Rechteausweitung. Private Zeitpläne und kurzlebige Jobs können eine autorisierte Ereignisbeobachtung erfordern, da eine einzelne Prozessaufnahme sie möglicherweise verpasst.

Prüfe bei einem privilegierten PHP-Job auch wörtliche `include`-/`require`-Anweisungen als Teil der ausführbaren Skriptkette. [PHP wertet eingebundene Dateien aus](https://www.php.net/manual/en/function.include.php); eine gruppenbeschreibbare eingebundene `.php`-Datei kann daher Code mit der Identität des Jobs ausführen, selbst wenn das Hauptskript schreibgeschützt ist. Prüfe die geplante Identität, die effektive Auflösung über den Include-Pfad, Datei- und Verzeichnisberechtigungen sowie, ob der Job tatsächlich läuft. Eine beispielhafte Cron-Zeile in einem Kommentar ist nur ein Hinweis. Dieselbe Prüfung gilt für einen root-eigenen [PHP built-in server](https://www.php.net/commandline.webserver), der mit `-S` und `-t <document-root>` gestartet wird: Auch ein Loopback-Listener kann bei lokalen Anfragen PHP-Anwendungscode ausführen. Prüfe Prozess und Quellcode, ohne während der Auflistung einen der Auslöser aufzurufen.

Ein privilegierter PHP-Job kann die Grenze auch über eine **Datendatei** überschreiten: Kann ein niedrig privilegierter Benutzer die exakte Datei ändern, die an [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) übergeben wird, kann PHP beim Wiederherstellen eines Objekts die Methode `__wakeup()` oder `__unserialize()` einer geladenen Klasse aufrufen. Prüfe die effektive Identität des Jobs, Datei- und übergeordnete Berechtigungen, die geladenen Klassen sowie die tatsächlichen Auswirkungen der Methoden, etwa einen durch eine Eigenschaft ausgewählten Dateischreibzugriff. Ein beschreibbares Protokoll oder ein Aufruf von `unserialize()` allein belegt keinen nutzbaren Pfad. Prüfe Quellcode und Metadaten, ohne während der Auflistung serialisierte Eingaben zu schreiben oder den Job auszuführen.

Ein Root-Cron-Task kann statt des Webservers den **CLI-Seiten-Runner** einer PHP-Anwendung aufrufen. Verfolge das ausgewählte Document Root und den URI des Runners bis zum tatsächlichen PHP-Einstiegspunkt. Ist dieser Einstiegspunkt für das Webservice-Konto beschreibbar, kann die geplante CLI-Anfrage den geänderten Code als root ausführen, selbst wenn Runner und Cron-Wrapper schreibgeschützt sind. Bestätige die Scheduler-Identität, die exakte Auflösung vom URI zur Datei, die effektiven Berechtigungen der Datei und ihrer übergeordneten Pfade sowie, ob eine Integritätsprüfung den Einstiegspunkt selbst schützt. Prüfe Quellcode und Metadaten, ohne den Runner aufzurufen oder die Seite während der Auflistung zu ändern.

Ein `ipython`-Prozess, der von einem geplanten Job oder einem anderen Benutzer aus einem gemeinsam genutzten Arbeitsverzeichnis gestartet wird, sollte auf Startdateien geprüft werden. [IPythons Security Release Notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) erklären, dass betroffene Builds vor der Behebung von CVE-2022-21699 im aktuellen Verzeichnis nach Profilen und Konfiguration suchten, einschließlich Code unter `profile_default/startup`. Gleiche den tatsächlich installierten Build oder Vendor-Patch, das Arbeitsverzeichnis des Befehls, die Identität des höher privilegierten Prozesses und die Möglichkeit des niedrig privilegierten Benutzers ab, in den exakten Startpfad zu schreiben und ihn zu durchsuchen. Ein installiertes `ipython`, ein beschreibbares Verzeichnis oder eine Versionszeichenfolge allein belegt nicht, dass eine andere Identität dort eine Datei lädt. Prüfe Zeitplan und Pfadmetadaten, ohne den höher privilegierten Interpreter zu starten.

Bei einem privilegierten PHP-Server, der Funktionen einer benutzerdefinierten nativen Erweiterung aufruft, ermittle vor der Prüfung der Erweiterung das PHP-SAPI des Dienstes, dessen effektive `php.ini` und die zusätzlich eingelesenen `.ini`-Dateien. [PHP lädt beim Start konfigurierte `extension`-Bibliotheken](https://www.php.net/manual/en/ini.core.php), und [CLI- und Web-SAPIs können unterschiedliche Konfigurationsdateien verwenden](https://www.php.net/manual/en/configuration.file.php). Ein erreichbares Login-Formular oder ein lokaler Listener kann daher benutzergesteuerte Zeichenfolgen an kompilierten Code übergeben, der mit der Dienstidentität läuft. Erfasse `User=`, `ExecStart=`, das Arbeitsverzeichnis, den tatsächlichen Erweiterungspfad und vom Aufrufer kontrollierte Argumente der Unit. Das bloße Vorhandensein einer `.so`-Datei oder eines Loopback-Sockets belegt keinen Memory-Corruption-Fehler. Analysiere jeden benutzerdefinierten Parser separat, statt während der passiven Auflistung Probes zu senden.

Wenn ein privilegierter Wrapper ein Skript über seinen Pfad hasht und denselben Pfad später erneut zur Ausführung öffnet, authentifiziert der Hash nur das Objekt, das beim ersten Öffnen gelesen wurde. Kann ein niedrig privilegierter Benutzer den Verzeichniseintrag des Skripts zwischen den beiden Öffnungen ersetzen, kann die spätere Ausführung ein anderes Objekt auflösen, selbst wenn die ursprüngliche Skriptdatei root-eigen ist. Eine FIFO kann die Prüfphase verlängern, aber der Pfad hängt von ersetzbaren Berechtigungen des übergeordneten Verzeichnisses, tatsächlich getrennten Öffnungen, der Scheduler-Identität, Sticky-Bit- und Mount-Regeln sowie dem Timing ab. Prüfe den Wrapper und die Ausgabe von `namei -l` als passiven Hinweis; ein erfolgreicher Checksum-Nachweis belegt nicht, dass der spätere Pfad geschützt ist.

Ein privilegierter Backup-Job kann Daten auch **offenlegen**, ohne vom Angreifer bereitgestellte Befehle auszuführen. Verfolge, ob ein niedrig privilegierter Benutzer eine vom Job gelesene Steuerdatei erstellen kann, ob der Job anschließend eine geschützte Quelle wie `/etc/shadow` öffnet und ob eine vom Angreifer gewählte URL oder eine lesbare Ausgabedatei das Ergebnis erhält. Prüfe alle drei Punkte, bevor du von einem Offenlegungspfad sprichst. Ein fester Shell-Befehl im selben Skript macht diese Steuerdatei nicht automatisch zu einer Shell-Injection-Eingabe. Prüfe Skript und Dateiberechtigungen, ohne den Job auszuführen oder während der Auflistung eine Steuerdatei anzulegen.

Wenn ein privilegierter geplanter Job `curl -K FILE` oder `curl --config FILE` ausführt, [behandelt curl Optionen in dieser Datei wie Befehlszeilenargumente](https://curl.se/docs/manpage.html). Ein niedrig privilegierter Benutzer, der die exakte Datei beim Einlesen durch curl kontrolliert, kann die angeforderte URL, lokale Datei-Eingabe oder den Ausgabepfad beeinflussen. Bestätige die effektive Identität des Jobs, Schreibrechte für Datei und übergeordnete Pfade, den Zeitpunkt eines anderen Jobs, der die Datei ersetzt, sowie die Wechselwirkung der Konfigurationsoptionen mit festen Befehlszeilenoptionen, bevor du einen geschützten Lese- oder Schreibzugriff behauptest. Ein beschreibbarer Konfigurationspfad oder ein sichtbares `-K`-Flag allein belegt nicht, dass die gewählten Optionen wirksam werden. Prüfe Zeitplan und Metadaten, ohne den Job auszuführen oder während der passiven Auflistung eine URL abzurufen.

Wenn ein Cron-Eintrag ein Hilfsskript aufruft, prüfe auch dessen Arbeitsverzeichnis und Archivierungsbefehl. Ein nicht in Anführungszeichen gesetzter Wildcard-Ausdruck über ein Verzeichnis, das ein anderer Benutzer beschreiben kann, kann Dateinamen in Optionen für das Archivierungsprogramm verwandeln; GNU-tar-Checkpoint-Aktionen sind ein Beispiel. Bestätige die geplante Ausführungsidentität, das beschreibbare Eingabeverzeichnis, das genaue Archivierungsprogramm und dessen Optionen sowie, ob `--` die Optionsverarbeitung beendet, bevor du einen Befehlsausführungspfad zwischen Benutzern annimmst. Siehe [wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md).

Eine separate Offenlegung aus einer Backup-Datei kann entstehen, wenn ein privilegiertes Hilfsprogramm `cd INPUT_DIR; tar ... *` ausführt, ohne zu prüfen, ob `cd` erfolgreich war. Kann ein niedrig privilegierter Benutzer `INPUT_DIR` entfernen oder ersetzen, kann ein fehlgeschlagenes `cd` die Shell im vorherigen Verzeichnis belassen, das der spätere Archivierungsbefehl dann möglicherweise liest. Prüfe das anfängliche Arbeitsverzeichnis des Jobs, einen tatsächlich möglichen fehlgeschlagenen `cd`-Pfad, ob das Skript beendet wird oder `&&` verwendet, die genauen Archivierungsoptionen und ob das Ausgabe-Archiv für den niedrig privilegierten Benutzer lesbar ist. Ein beschreibbares Eingabeverzeichnis oder ein lesbares Archiv allein ist nur ein Hinweis. Prüfe das Hilfsprogramm und die Pfadberechtigungen, ohne den laufenden Job zu ändern.

Ein geplanter Executable kann ein Shell-Skript verbergen, statt die Vertrauensgrenze zu beseitigen: [SHc](https://github.com/neurobin/shc) verpackt verschlüsselten Skripttext in eine native Binärdatei und führt ihn zur Laufzeit über eine Shell aus. Die Endung `.sh.x` oder ein undurchsichtiges ELF ist nur ein Prüfhinweis. Um eine Dateinamen-Option-Injection zu bewerten, ermittle die privilegierte Scheduler-Identität, das tatsächliche Arbeitsverzeichnis und den Befehl des Hilfsprogramms, ob ein niedrig privilegierter Benutzer dort passende Namen erstellen kann und ob ein nicht in Anführungszeichen gesetzter Glob ohne Optionsgrenze einen Befehl wie `rsync` erreicht. Die [`rsync`-Remote-Shell-Option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) ist nur relevant, wenn genau dieser Befehlspfad verwendet wird. Eingeschränkte Sichtbarkeit in `/proc` oder fehlgeschlagene statische Entschlüsselung lassen den Befehl unbekannt; starte das privilegierte Hilfsprogramm nicht nur, um es einzuordnen.

Text in der Prozessbefehlszeile ist eine weitere nicht vertrauenswürdige Eingabe für ein privilegiertes Hilfsprogramm. Ein niedrig privilegierter Benutzer kann einen Prozesstitel oder `argv[0]` wählen, der zu `pgrep -f` passt; ein passender Name authentifiziert weder die ausführbare Datei noch deren Eigentümer. Wenn ein als root laufendes Skript diesen Text erfasst, Teile davon in `apache2ctl`/`httpd` umschreibt und das Ergebnis ohne festes Argument-Array ausführt, können vom Angreifer gewählte Optionen ein anderes Konfigurationsverzeichnis oder Fehlerprotokoll auswählen. Beim Parsen der Apache-Konfiguration können Module geladen oder konfigurierte Hilfsprogramme erreicht werden. Validiere während der Auflistung keine nicht vertrauenswürdige Konfiguration als root. Prüfe Scheduler-Eigentümer, genaues Hilfsprogramm, Prozessidentität und Datenfluss zu den Argumenten. Es handelt sich um Options-/Konfigurations-Injection, sofern Shell-Metazeichen-Ausführung nicht separat nachgewiesen wird.

Ein als root laufender Parser, der nicht vertrauenswürdigen Text in Bash-Arithmetik einsetzt, kann darin enthaltene Substitutionen ausführen. Der [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) enthält ein ausführliches Beispiel. Bestätige die Eingabequelle und den Parse-Befehl, bevor du jeden arithmetischen Ausdruck als ausnutzbar einstufst.

Verfolge bei einem privilegierten Job, der ein Anwendungsprotokoll parst, nicht vertrauenswürdige Felder über den ersten Parse hinaus. Ein niedrig privilegiertes Konto kann möglicherweise über seine aktuelle Prozessgruppe in das Protokoll schreiben oder protokollierte Request-Felder beeinflussen. Ein Eintrag kann dann ein Bild auswählen, dessen Metadaten als zweiter Pfad zum Öffnen einer XML-Datei verwendet werden. Prüfe die effektive Identität des Jobs, den tatsächlichen Schreibzugriff auf das Protokoll, die Behandlung von Trennzeichen, die kanonische Pfadbegrenzung und ob die ausgewählte XML-Datei vom Angreifer kontrolliert wird. Die Expansion externer Entitäten kann zu einer privilegierten Dateioffenlegung führen, wenn das expandierte Ergebnis in einer für niedrig privilegierte Benutzer lesbaren Ausgabe landet. Der [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) dokumentiert Kontrollen für den Zugriff auf externe DTDs und Entitäten; prüfe den installierten Parser und seine effektiven Einstellungen. Ein beschreibbares Protokoll oder eine XML-Datei allein ist nur ein Hinweis. Prüfe Code und Metadaten, ohne den geplanten Parser während der Auflistung mit Eingaben zu versorgen.

Prüfe auch privilegierte Jobs, die Dateien aus dem Git-Repository eines anderen Benutzers materialisieren. Ein Skript kann `git ls-tree` und `git cat-file` statt `git checkout` verwenden und dennoch vom Angreifer kontrollierten Tree-Pfaden vertrauen, wenn es sie an ein Staging-Verzeichnis anhängt. Absolute Pfade und `..`-Komponenten können aus diesem Verzeichnis herausführen, sofern das Ziel vor dem Schreiben nicht normalisiert und auf Pfadbegrenzung geprüft wird. `git -c safe.directory=*` erlaubt den Zugriff auf Repositories mit anderen Eigentümern; allein dadurch entsteht keine beliebige Schreibmöglichkeit.

Ein als root laufendes Datenbank-Backup kann eine weitere Eigentumsgrenze schaffen. PostgreSQL-[`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) kopiert zusätzliche reguläre Dateien im Quelldatenverzeichnis, und das standardmäßige Plain-Format schreibt Dateien unter `-D` als Verzeichnisbaum. Kann ein niedrig privilegiertes Konto diese Quelldateien erstellen oder ändern, prüfe Eigentümer und Modus der resultierenden Zieldateien, ob ihr Pfad durchsuchbar und ausführbar ist sowie, ob der Mount mit `nosuid` eingebunden ist. Eine root-eigene Kopie mit erhaltenen Set-ID-Berechtigungen kann gefährlich sein; ein reines Tar-Backup, entfernte Berechtigungen oder ein unzugängliches Ziel belegen nicht denselben Pfad. Verfolge den geplanten Wrapper und den effektiven Benutzer, bevor du den Backup-Befehl als Finding einstufst.

## Kurzlebige Aufgaben beobachten

Eine einzelne Prozessaufnahme kann einen Job verpassen, der nur Millisekunden läuft. Vergleiche Timer-/Cron-Einträge mit Protokollen und nutze, sofern autorisiert, Prozessereignisüberwachung wie `pspy` oder Audit. Gleiche den geplanten Eigentümer, die exakte Befehlszeile und die Dateien ab, die der Task liest oder schreibt. Eine Loopback-Weboberfläche für den Scheduler ist eine separate Schnittstelle; siehe das [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
