# Job Cron e timer Systemd

{{#include ../../banners/hacktricks-training.md}}

Le attività pianificate possono essere eseguite con un'identità e un ambiente diversi da quelli della shell corrente. Elenca cron, `at`, anacron e i timer systemd, quindi segui ogni comando pianificato attraverso i relativi script, importazioni, directory di lavoro e input scrivibili.

## Elencare le pianificazioni

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

I crontab di sistema di solito includono un campo utente; il crontab di un utente no. Esamina il PATH effettivo e l'ambiente dello scheduler reale. `run-parts --test /etc/cron.daily` mostra quali nomi di file verrebbero selezionati su quell'host. I caratteri di controllo possono nascondere una voce nell'output ordinario: se una pianificazione sembra sospetta, usa `cat -A` o `sed -n l`.

## Traccia la risoluzione di file e comandi privilegiati

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Esamina le catene di script scrivibili, i percorsi `EnvironmentFile=`, i drop-in, i symlink, i comandi relativi, l'espansione dei wildcard e i binari copiati o eseguiti da un task privilegiato. Un timer può attivare un servizio con un nome diverso tramite l'impostazione `Unit=`. Le pagine [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) e [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) spiegano le primitive principali.

Per uno script `chkrootkit` pianificato ed eseguito come root, esamina il sorgente installato per verificare il vecchio [difetto di quoting nello slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): dopo aver controllato un percorso temporaneo `SLAPPER_FILES`, un'istruzione non quotata `file_port=$file_port $i` può eseguire quel file. Verifica lo script effettivo o la patch del vendor, la pianificazione come root, l'accesso in scrittura dell'utente con privilegi inferiori al percorso temporaneo esatto, il suo stato eseguibile e le policy di mount. Una stringa di versione o la sola presenza di `chkrootkit` non dimostrano che il percorso sia sfruttabile; durante una verifica passiva, non creare né eseguire un file temporaneo.

Segui un ulteriore passaggio tra unità quando il servizio root di un timer esegue `systemctl restart <other>.service`: l'unità riavviata potrebbe invocare una shell con uno script scrivibile da un utente con privilegi inferiori. Verifica l'effettivo `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, gli argomenti esatti di `ExecStart=` e i permessi dello script e del percorso della directory che lo contiene. Uno script scrivibile è solo un possibile indizio, finché il timer e il servizio riavviato non sono attivi in quel contesto di esecuzione; esamina le proprietà delle unità senza riavviare nessuno dei due servizi.

Se un job con privilegi superiori scarica uno script usando un hostname e passa la risposta a una shell, verifica chi controlla la risoluzione di quel nome oltre allo script remoto. Un file `/etc/hosts` scrivibile, anche tramite permessi concessi a un gruppo o una ACL, può reindirizzare un nome che il job risolve localmente; una risposta di `curl` diventa un percorso di esecuzione tra utenti diversi solo se il comando pianificato effettivo esegue quella risposta e il job usa il percorso di risoluzione interessato. Verifica l'identità con cui viene eseguito il job, l'URL esatto e la pipeline della shell, il comportamento effettivo di proxy/DNS e i permessi del file e della directory che lo contiene. Un file hosts scrivibile, da solo, è un elemento da esaminare, non la prova che esista un consumer privilegiato. Durante l'enumerazione, esamina la pianificazione e i metadati senza modificare la mappatura né scaricare lo script.

Un download pianificato con `wget` privilegiato costituisce un confine di scrittura su file distinto, anche se il contenuto scaricato non viene mai eseguito direttamente. [GNU Wget 1.18 ha modificato la gestione predefinita del nome del file nei reindirizzamenti da HTTP a FTP per correggere CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); le vecchie build interessate potevano usare il nome del file FTP di destinazione, mentre `--trust-server-names` richiede esplicitamente tale comportamento. Se una parte meno fidata controlla la risposta HTTP e la risorsa FTP, verifica se il job segue il reindirizzamento, la build effettiva di Wget o la patch del vendor, le opzioni di output, l'identità con cui viene eseguito, la directory di lavoro e se il nome del file di destinazione può corrispondere a un file di avvio. [Wget carica `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html) e [le sue impostazioni possono selezionare una sorgente POST o un percorso di output](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); un successivo download privilegiato è un prerequisito distinto per qualsiasi divulgazione o scrittura conseguente. L'accesso a una porta non privilegiata tramite `authbind` è rilevante solo se il chiamante può effettivamente servire l'URL richiesto dal job. Esamina configurazione e log passivamente, senza servire un reindirizzamento né eseguire il job. [L'accesso grezzo ai dispositivi a blocchi tramite il gruppo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) è indipendente da questo percorso di download dalla rete.

Traccia anche i file di dati, non solo gli script. Uno strumento di simulazione o orchestrazione pianificato potrebbe leggere un file YAML che definisce i processi da avviare; se un utente con privilegi inferiori può modificare quel file e il job lo esegue sotto un altro account, i dati possono diventare comandi eseguiti con l'identità del job. Prima di considerare un file YAML scrivibile un percorso di esecuzione, verifica il comando pianificato esatto, l'utente effettivo, il percorso del file, la semantica del parser e l'accesso in scrittura, comprese le directory che lo contengono. Per un triage passivo basta leggere la pianificazione e i metadati del file; durante l'enumerazione, non eseguire il job né modificarne l'input.

Anche una configurazione del client SSH è un input eseguibile quando un job con privilegi superiori esegue `ssh -F` con un file che un utente meno privilegiato può sostituire. `ProxyCommand` di OpenSSH esegue un comando locale tramite la shell del client, mentre `Host`/`Match` e le opzioni precedenti determinano se quella direttiva si applica. Prima di considerarlo un percorso di esecuzione tra utenti diversi, confronta l'invocazione SSH pianificata esatta, l'identità con cui viene eseguito il job, il percorso della configurazione selezionata, i permessi di scrittura del file e della directory e l'ordine effettivo delle opzioni. Esamina questi elementi senza eseguire il job né caricare la configurazione non fidata con l'account privilegiato.

Un `scp` pianificato seguito da `ssh` per eseguire lo script copiato richiede un'ulteriore verifica del confine di fiducia quando un utente con privilegi inferiori controlla il servizio SSH di destinazione. Se quel servizio può inoltrare la connessione a un altro host, il client privilegiato potrebbe autenticarsi presso un endpoint non previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) indebolisce la protezione contro la modifica della chiave host, fatte salve le restrizioni rimanenti di OpenSSH e le opzioni effettive per host. Verifica l'identità con cui viene eseguito il job, la destinazione effettiva e il metodo di autenticazione, l'identità effettiva del comando remoto e se lo stesso percorso di destinazione è scrivibile o già esistente sull'host reindirizzato. L'esecuzione di un file precedente o controllato da un attaccante richiede inoltre che la copia fallisca o non raggiunga quel percorso **e** che il wrapper prosegua comunque con il comando SSH; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) e la gestione esplicita dello stato di uscita influiscono su questo flusso. Un'impostazione debole per la chiave host, un processo `sshpass` visibile o una directory temporanea scrivibile, da soli, non dimostrano questa catena. Durante l'enumerazione, esamina la pianificazione, lo script, la configurazione SSH e i metadati dei file senza reindirizzare il servizio né attivare il job.

Uno scheduler applicativo privilegiato potrebbe prendere i job da righe del database invece che da file scrivibili. Per esempio, una voce cron di root che invoca [`php artisan schedule:run` di Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) può raggiungere codice applicativo che legge righe di task. Se un account con privilegi inferiori può scrivere una riga contenente un percorso locale, e il callback pianificato chiama [`file_get_contents` di PHP](https://www.php.net/manual/en/function.file-get-contents.php) come root e invia il contenuto ottenuto a un webhook indicato nella riga, si tratta di un percorso di divulgazione di file privilegiato. Verifica l'identità della voce cron, il callback effettivo dello scheduler e il flusso dei dati dalla riga al percorso, l'autorizzazione alla scrittura nel database, la validazione eseguita dopo la lettura della riga e la destinazione in uscita. Un file `.env` applicativo leggibile è solo un indizio relativo alle credenziali; la validazione di un form web o una password del database, da soli, non dimostrano il controllo della riga né la divulgazione. Durante l'enumerazione, esamina passivamente la pianificazione, il codice e i permessi dei file delle credenziali, senza interrogare il database né pianificare un task.

Anche i job `incron` attivati da eventi richiedono la stessa verifica: le [voci incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associano un percorso monitorato e un evento a un comando eseguito con l'identità del proprietario della tabella. Un utente con privilegi inferiori potrebbe influenzare indirettamente un file monitorato quando un'applicazione segue un link da una directory scrivibile e scrive testo controllato dall'attaccante nel file di destinazione monitorato. Verifica il proprietario effettivo della tabella, l'evento, i permessi del file di destinazione e delle directory antenate, il comportamento dell'applicazione nel seguire i link e il modo in cui quel testo diventa argomenti del comando. In particolare, [GNU Mailutils `mail` accetta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html) e il suo [comando di escape della shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) può eseguire un programma; un campo non fidato passato come opzione separata a quell'implementazione può consentire l'esecuzione di comandi. Altre implementazioni di `mail` o un confine di argomenti quotato e fisso possono comportarsi diversamente. Durante l'enumerazione, esamina la pianificazione, il codice dell'applicazione e i metadati dei file senza modificare il file monitorato né attivare il job.

Anche un log monitorato può attraversare il confine tra utenti tramite uno script helper. Se un account con privilegi inferiori può scrivere nel log e il proprietario di `incron` legge un campo dal log e lo inserisce in una nuova stringa di comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), la shell analizza di nuovo quel campo con l'identità del proprietario. Verifica l'evento monitorato esatto, i permessi del log e delle directory che lo contengono, il percorso dell'helper, la trasformazione del campo del log e se il comando risultante viene effettivamente eseguito. La sola presenza di un log scrivibile e di una voce `incron` non dimostra il flusso dei dati; durante l'enumerazione passiva, non scrivere una riga di trigger né eseguire l'helper.

Anche i job di rinnovo dei certificati possono attraversare lo stesso confine. Un helper privilegiato potrebbe leggere il subject X.509 da un certificato in una directory scrivibile da un utente con privilegi inferiori e inserire il common name in una nuova stringa di comando `bash -c`. [OpenSSL può mostrare il subject di un certificato e verificarne la scadenza](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analizza la stringa `-c` come input della shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), quindi quotare la variabile nello script esterno non protegge la seconda analisi. Prima di parlare di command injection, verifica l'identità pianificata, il percorso di input esatto e i relativi permessi di scrittura, il ramo di rinnovo e il flusso dei dati verso `bash -c`. Esamina passivamente lo script e i metadati del certificato; durante l'enumerazione, non attivare il rinnovo.

La stessa seconda analisi può verificarsi quando un job privilegiato pianificato estrae un nome dall'archivio o dal pacchetto di un utente con privilegi inferiori e lo passa a `xargs -I` per inserirlo in una stringa di comando `sh -c`. [GNU `xargs -I` sostituisce il segnaposto negli argomenti iniziali](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html) e [`sh -c` interpreta la propria stringa di comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Anche se lo script esterno quota il nome estratto, ciò non rende sicuro un programma shell sostituito in un secondo momento. Verifica l'identità con cui viene eseguito il job, il percorso di input accettato esatto e i relativi permessi di scrittura, la validazione dell'archivio e le condizioni dei rami, nonché il flusso dal nome alla shell. Una directory di upload scrivibile o la presenza di `xargs`, da sole, sono solo indizi; durante l'enumerazione, esamina la pianificazione, lo script e i metadati del percorso senza inviare un pacchetto né eseguire il job.

Anche un job pianificato di importazione di font o immagini potrebbe fidarsi dei nomi *contenuti* in un archivio fornito dal chiamante, anche quando il nome esterno del file caricato è limitato. FontForge ha corretto la command injection tramite i nomi dei membri dell'archivio nella sua [modifica upstream per CVE-2024-25081 e CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Verifica che un job con privilegi superiori apra effettivamente un archivio da un percorso scrivibile da un utente con privilegi inferiori, l'identità con cui viene eseguito, la build esatta di FontForge o la patch del vendor e il percorso di gestione dell'archivio. Una stringa di versione o la sola presenza di un'estensione consentita per l'upload non dimostrano l'esecuzione. Durante l'enumerazione, esamina la pianificazione, i permessi del percorso e i metadati della build senza importare un archivio non fidato.

Gli scanner di rete pianificati possono attraversare un confine diverso quando uno script personalizzato tratta il subject di un certificato TLS remoto come nome di un file locale. [Nmap NSE esegue gli script selezionati senza sandbox](https://nmap.org/book/nse-usage.html), quindi esamina lo script effettivo e verifica se concatena un campo subject non fidato a una directory di dati senza controlli di contenimento. Per divulgare file serve una destinazione che lo scheduler sottoporrà a scansione, un percorso che risolva in un file leggibile dall'identità con cui viene eseguito lo scanner e un report o log consegnato a un utente con privilegi inferiori. Un campo di un certificato o la sola presenza di uno scanner installato non dimostrano questa catena; durante una verifica passiva, esamina la pianificazione, lo script, la risoluzione del percorso e la destinazione del report senza sottoporre a scansione una nuova destinazione.

Un comando cron privilegiato che passa a un runner Ansible un glob di shell come `/path/to/tasks/*.yml` richiede un controllo dei permessi della directory, anche quando tutti i playbook esistenti sono in sola lettura. Un utente con accesso in scrittura e ricerca alla directory interessata dal glob potrebbe creare un altro playbook corrispondente. [I playbook Ansible definiscono i task eseguiti dal runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), ma un wrapper personalizzato potrebbe filtrare i percorsi o usare un'identità diversa: prima di considerare la directory un percorso di esecuzione, verifica il suo comportamento, l'utente cron effettivo, l'espansione della shell, le ACL, lo sticky bit e le policy di mount. Esamina staticamente i metadati e il wrapper; durante l'enumerazione, non eseguire il job pianificato.

Un wrapper cron privilegiato può passare a un helper Perl i nomi dei file di una directory di upload dopo aver espanso un glob. L'operatore a diamante [`<>` di Perl usa `open` a due argomenti](https://perldoc.perl.org/perlop#The-Null-Filehandle), quindi un nome di file corrispondente interpretato come comando con pipe può essere eseguito con l'identità dell'helper; [`<<>>` tratta gli argomenti come nomi di file letterali](https://perldoc.perl.org/perlop#The-Null-Filehandle). Verifica l'identità dello scheduler, la directory di lavoro del wrapper e il glob, l'effettiva gestione di `@ARGV` nell'helper, le restrizioni sui nomi dei file e se un utente con privilegi inferiori può inserire un nome corrispondente tramite i permessi del filesystem o un servizio di upload autenticato. Una voce cron, uno script Perl o una directory FTP scrivibile, da soli, non dimostrano la catena completa. Durante l'enumerazione, esamina sorgente e metadati senza inviare un nome costruito ad hoc né eseguire il job.

Uno script cron in sola lettura è comunque sostituibile se l'account pianificato lo esegue tramite percorso e l'utente con privilegi inferiori può scrivere e attraversare la directory non-sticky che lo contiene. Controlla l'identità con cui viene eseguita la pianificazione, ogni componente del percorso, lo sticky bit della directory, le ACL e le policy di mount; esamina i metadati senza spostare il file né eseguire il job.

Un wrapper cron PHP privilegiato può raggiungere un helper che ancora non esiste. Se chiama [`exec()` di PHP](https://www.php.net/manual/en/function.exec.php) con un percorso assoluto e fisso per l'helper, un utente con privilegi inferiori che può creare quel nome nella directory che lo contiene potrebbe controllare cosa verrà eseguito in un'esecuzione successiva. Verifica che la voce cron esegua effettivamente il wrapper con l'identità superiore, la stringa di comando esatta e le policy di esecuzione di PHP, i permessi di scrittura e ricerca sulla directory dell'helper, il comportamento di symlink e sticky bit e se il percorso dell'helper è ancora assente. Una directory scrivibile o un helper mancante, da soli, sono solo indizi; durante l'enumerazione, esamina la pianificazione, il sorgente e i metadati del percorso senza creare l'helper né attivare il job.

Un job pianificato potrebbe anche individuare script di input con `find` e passarli a un interprete. Per esempio, la funzione `system()` di [gnuplot invoca una shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), quindi un job privilegiato che esegue `gnuplot` su ogni file `*.plt` in una directory scrivibile da un utente con privilegi inferiori può eseguire comandi con l'identità del job. [Il permesso di lettura della directory controlla l'elenco dei file, mentre i permessi di scrittura e ricerca (`x`) controllano la creazione e l'accesso ai nomi noti](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); controlla i permessi di scrittura e ricerca anche quando `ls` non può elencare la directory. Verifica l'identità esatta dello scheduler e il comando, il comportamento dell'interprete, il pattern dei file selezionati e i permessi della directory; una directory scrivibile o la sola presenza di un interprete installato non dimostrano un'escalation. Le pianificazioni private e i job di breve durata potrebbero richiedere l'osservazione autorizzata degli eventi, poiché uno snapshot dei processi può non rilevarli.

Per un job PHP privilegiato, esamina le istruzioni letterali `include`/`require` come parte della catena di script eseguibili. [PHP valuta i file inclusi](https://www.php.net/manual/en/function.include.php), quindi un file `.php` scrivibile dal gruppo può eseguire codice con l'identità del job anche quando lo script principale è in sola lettura. Verifica l'identità pianificata, la risoluzione effettiva dell'include path, i permessi dei file e delle directory e se il job viene davvero eseguito; una voce cron di esempio in un commento è solo un indizio. La stessa verifica si applica a un [server integrato PHP](https://www.php.net/commandline.webserver) di proprietà di root avviato con `-S` e `-t <document-root>`: anche un listener loopback può eseguire codice PHP dell'applicazione per richieste locali. Durante l'enumerazione, esamina il processo e il sorgente senza attivare nessuno dei due percorsi.

Un job PHP privilegiato può anche attraversare il confine tramite un **file di dati**: se un utente con privilegi inferiori può modificare il file esatto passato a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP potrebbe invocare il metodo `__wakeup()` o `__unserialize()` di una classe caricata durante il ripristino dell'oggetto. Esamina l'identità effettiva del job, i permessi del file e delle directory antenate, le classi caricate e gli effetti collaterali effettivi del metodo, per esempio la scrittura di un file selezionato da una proprietà. Un log scrivibile o una chiamata a `unserialize()`, da soli, non dimostrano l'esistenza di un percorso utilizzabile. Durante l'enumerazione, esamina sorgente e metadati senza scrivere input serializzato né eseguire il job.

Un task cron di root potrebbe invocare il **runner di pagine CLI** di un'applicazione PHP anziché il server web. Traccia la document root e l'URI selezionati dal runner fino all'entrypoint PHP effettivo; se quell'entrypoint è scrivibile dall'account del servizio web, la richiesta CLI pianificata può eseguire come root il codice modificato anche quando il runner e il wrapper cron sono in sola lettura. Verifica l'identità dello scheduler, la risoluzione esatta da URI a file, i permessi effettivi del file e delle directory antenate e se l'entrypoint è protetto da un controllo di integrità. Durante l'enumerazione, esamina sorgente e metadati senza invocare il runner né modificare la pagina.

Un processo `ipython` avviato da un job pianificato o da un altro utente in una directory di lavoro condivisa richiede una verifica dei file di avvio. Le [note di rilascio di sicurezza di IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) spiegano che le build interessate cercavano profili e configurazioni nella directory corrente, incluso il codice in `profile_default/startup`, prima della correzione di CVE-2022-21699. Verifica la build installata effettiva o la patch del vendor, la directory di lavoro del comando, l'identità del processo con privilegi superiori e la possibilità per l'utente con privilegi inferiori di scrivere e attraversare il percorso di avvio esatto. La sola presenza di `ipython`, una directory scrivibile o una stringa di versione non dimostrano che un'altra identità vi caricherà un file. Durante l'enumerazione, esamina la pianificazione e i metadati del percorso senza avviare l'interprete con privilegi superiori.

Per un server PHP privilegiato che chiama funzioni di un'estensione nativa personalizzata, prima di esaminare l'estensione, ricostruisci la SAPI PHP del servizio e i file `php.ini` effettivi, più i file `.ini` scansionati. [PHP carica all'avvio le librerie `extension` configurate](https://www.php.net/manual/en/ini.core.php) e [le SAPI CLI e web possono usare file di configurazione diversi](https://www.php.net/manual/en/configuration.file.php). Un form di login raggiungibile o un listener locale possono quindi passare stringhe controllate dall'utente a codice compilato eseguito con l'identità del servizio. Registra `User=`, `ExecStart=`, la directory di lavoro, il percorso effettivo dell'estensione e gli argomenti controllabili dal chiamante; la sola presenza di un `.so` o di un socket loopback non dimostra un difetto di memory corruption. Analizza separatamente qualsiasi parser personalizzato, senza inviare probe durante l'enumerazione passiva.

Quando un wrapper privilegiato calcola l'hash di uno script usando il percorso e poi riapre lo stesso percorso per eseguirlo, il digest autentica solo l'oggetto letto durante la prima apertura. Se un utente con privilegi inferiori può sostituire l'elemento della directory dello script tra le due aperture, l'esecuzione successiva potrebbe risolvere un oggetto diverso anche se il file di script originale è di proprietà di root. Una FIFO può prolungare la fase di controllo, ma il percorso dipende dai permessi modificabili delle directory antenate, da aperture separate effettive, dall'identità dello scheduler, dalle regole di sticky bit e mount e dalla temporizzazione. Esamina il wrapper e l'output di `namei -l` come indizio passivo; un checksum valido, da solo, non dimostra che il percorso usato successivamente sia protetto.

Un job di backup privilegiato può anche **divulgare** dati senza eseguire comandi forniti dall'attaccante. Verifica se un utente con privilegi inferiori può creare un file di controllo letto dal job, se il job apre poi una sorgente protetta come `/etc/shadow` e se l'URL scelto dall'attaccante o un output leggibile ricevono il risultato. Verifica tutti e tre gli elementi prima di considerarlo un percorso di divulgazione. Un comando shell fisso nello stesso script non fa, da solo, di quel file di controllo un input per shell injection. Durante l'enumerazione, esamina lo script e i permessi dei file senza eseguire il job né inserire un file di controllo.

Se un job pianificato privilegiato esegue `curl -K FILE` o `curl --config FILE`, [curl tratta le opzioni contenute in quel file come argomenti della riga di comando](https://curl.se/docs/manpage.html). Un utente con privilegi inferiori che controlla il file esatto al momento in cui curl lo legge può influenzare l'URL richiesto, l'input da file locale o il percorso di output. Prima di affermare che è possibile leggere o scrivere file protetti, verifica l'identità effettiva del job, i permessi di scrittura del file e delle directory antenate, la tempistica di qualsiasi altro job che sostituisca il file e il modo in cui le opzioni di configurazione interagiscono con quelle fisse della riga di comando. Un percorso di configurazione scrivibile o la presenza di `-K`, da soli, non dimostrano che le opzioni scelte abbiano effetto; durante l'enumerazione passiva, esamina pianificazione e metadati senza eseguire il job né scaricare un URL.

Se una voce cron invoca uno script helper, esamina anche la directory di lavoro dell'helper e il comando per gli archivi. Un wildcard non quotato in una directory scrivibile da un altro utente può trasformare i nomi dei file in opzioni dell'archiviatore; le azioni checkpoint di GNU tar ne sono un esempio. Prima di affermare che esiste un percorso di esecuzione tra utenti diversi, verifica l'identità con cui viene eseguito il job, la directory di input scrivibile, l'archiviatore e le opzioni esatti e se `--` interrompe l'analisi delle opzioni. Vedi il comportamento di [wildcard e tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Un caso distinto di divulgazione tramite file di backup può verificarsi quando un helper privilegiato esegue `cd INPUT_DIR; tar ... *` senza verificare se `cd` è riuscito. Se un utente con privilegi inferiori può rimuovere o sostituire `INPUT_DIR`, un `cd` fallito potrebbe lasciare la shell nella directory precedente, che il comando di archiviazione successivo potrebbe leggere. Verifica la directory di lavoro iniziale del job, l'esistenza di un percorso in cui `cd` fallisce, se lo script termina o usa `&&`, le opzioni esatte dell'archiviatore e se l'archivio di output è leggibile dall'utente con privilegi inferiori. Una directory di input scrivibile o un archivio leggibile, da soli, sono solo indizi; durante l'enumerazione, esamina l'helper e i permessi del percorso senza modificare il job attivo.

Un eseguibile pianificato può nascondere uno script shell invece di eliminare il relativo confine di fiducia: [SHc](https://github.com/neurobin/shc) incapsula il testo cifrato dello script in un binario nativo e lo esegue tramite una shell a runtime. Un suffisso `.sh.x` o un ELF opaco sono solo elementi da esaminare. Per valutare l'iniezione di opzioni tramite nomi di file, verifica l'identità privilegiata dello scheduler, la directory di lavoro e il comando effettivi dell'helper, la possibilità per un utente con privilegi inferiori di creare nomi corrispondenti e se un glob non quotato raggiunge un comando come `rsync` senza un separatore delle opzioni. L'opzione [`rsync` per la shell remota](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) è rilevante solo se viene usato esattamente quel percorso di comando. Una visibilità limitata di `/proc` o un tentativo di decrittazione statica fallito non chiariscono il comando; non eseguire l'helper privilegiato solo per classificarlo.

Anche il testo della riga di comando di un processo può essere un input non fidato per un helper privilegiato. Un utente con privilegi inferiori può scegliere un titolo del processo o `argv[0]` che corrisponda a `pgrep -f`; un nome corrispondente non autentica né l'eseguibile né il suo proprietario. Se uno script eseguito come root acquisisce quel testo, ne riscrive una parte in `apache2ctl`/`httpd` ed esegue il risultato senza un array di argomenti fisso, le opzioni scelte dall'attaccante possono selezionare un'altra directory di configurazione o un altro error log. L'analisi della configurazione di Apache può caricare moduli o raggiungere helper configurati, quindi durante l'enumerazione non validare come root una configurazione non fidata. Esamina il proprietario dello scheduler, l'helper esatto, l'identità del processo e il flusso dai dati agli argomenti; si tratta di injection di opzioni/configurazione, a meno che non venga dimostrata separatamente l'esecuzione di metacaratteri della shell.

Un parser eseguito come root che passa testo non fidato all'aritmetica di Bash può eseguire sostituzioni contenute in quel testo. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) presenta un esempio dettagliato. Prima di considerare sfruttabile ogni espressione aritmetica, verifica la sorgente dell'input e il comando di parsing.

Per un job privilegiato che analizza un log applicativo, traccia i campi non fidati oltre la prima analisi. Un account con privilegi inferiori potrebbe essere in grado di scrivere nel log tramite il gruppo di processi corrente o di influenzare i campi di richiesta registrati; un record può quindi selezionare un'immagine, i cui metadati diventano un secondo percorso usato per aprire un file XML. Verifica l'identità effettiva del job, l'effettivo accesso in scrittura al log, la gestione dei delimitatori, il contenimento del percorso canonico e se il file XML selezionato è controllato dall'attaccante. L'espansione di entità esterne può trasformare quella seconda lettura in una divulgazione di file privilegiati se il risultato espanso raggiunge un output leggibile da un utente con privilegi inferiori. La [guida alla sicurezza per l'elaborazione XML in Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta i controlli per l'accesso a DTD/entità esterne; esamina il parser installato e le sue impostazioni effettive. Un log o un file XML scrivibile, da soli, sono solo indizi. Durante l'enumerazione, esamina il codice e i metadati senza fornire input al parser pianificato.

Esamina anche i job privilegiati che materializzano file dal repository Git di un altro utente. Uno script potrebbe usare `git ls-tree` e `git cat-file` invece di `git checkout`, ma fidarsi comunque dei percorsi del tree controllati dall'attaccante quando li concatena a una directory di staging. I percorsi assoluti e i componenti `..` possono uscire da quella directory, a meno che la destinazione non venga normalizzata e controllata per verificarne il contenimento prima della scrittura. `git -c safe.directory=*` consente l'accesso a repository con proprietari diversi; da solo, non crea la condizione di scrittura arbitraria.

Un backup di un database eseguito come root può creare un ulteriore confine di proprietà. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia gli ulteriori file regolari presenti nella directory dei dati sorgente e, nel formato plain predefinito, scrive i file in `-D` come albero di directory. Se un account con privilegi inferiori può creare o modificare quei file sorgente, esamina la proprietà e i permessi della destinazione risultante, verifica se il percorso è attraversabile ed eseguibile e se il mount ha l'opzione `nosuid`. Una copia di proprietà di root con permessi set-ID preservati può essere pericolosa; un backup solo tar, permessi rimossi o una destinazione inaccessibile non dimostrano lo stesso percorso. Ricostruisci il wrapper pianificato e l'utente effettivo prima di considerare il comando di backup una vulnerabilità.

## Osservare i job di breve durata

Un singolo snapshot dei processi potrebbe non rilevare un job che dura pochi millisecondi. Confronta le dichiarazioni di timer/cron con i log e, quando autorizzato, con il monitoraggio degli eventi di processo, come `pspy` o audit. Metti in correlazione il proprietario pianificato, la riga di comando esatta e i file letti o scritti dal task. Un'interfaccia web dello scheduler in loopback è un'interfaccia distinta; vedi l'[esempio di Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
