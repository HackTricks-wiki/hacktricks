# Cron Jobs và Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

Các tác vụ được lên lịch có thể chạy với danh tính và môi trường khác với shell hiện tại. Liệt kê cron, `at`, anacron và systemd timers, sau đó lần theo từng lệnh được lên lịch qua các script, mục nhập, thư mục làm việc và đầu vào có thể ghi.

## Liệt kê lịch chạy

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontab thường có trường user; crontab của người dùng thì không. Kiểm tra PATH và môi trường hiệu lực của scheduler thực tế. `run-parts --test /etc/cron.daily` hiển thị những tên file sẽ được chọn trên host đó. Ký tự điều khiển có thể che giấu một mục trong đầu ra thông thường, vì vậy hãy dùng `cat -A` hoặc `sed -n l` khi lịch chạy có vẻ đáng ngờ.

## Truy vết cách phân giải file và lệnh có đặc quyền

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Rà soát các chuỗi script có thể ghi, đường dẫn `EnvironmentFile=`, drop-in, symlink, lệnh tương đối, mở rộng wildcard và binary được tác vụ có đặc quyền sao chép hoặc thực thi. Timer có thể kích hoạt một service tên khác thông qua thiết lập `Unit=`. Các trang [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) và [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) giải thích các primitive chính.

Với script `chkrootkit` chạy định kỳ bằng root, kiểm tra source đã cài để tìm lỗi trích dẫn cũ [slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): dòng `file_port=$file_port $i` không được đặt trong dấu nháy sau khi kiểm tra đường dẫn tạm `SLAPPER_FILES` có thể thực thi file đó. Xác minh script thực tế hoặc bản vá của nhà cung cấp, lịch chạy bằng root, quyền ghi của user thấp hơn vào đúng đường dẫn tạm, trạng thái thực thi của file và chính sách mount. Chỉ riêng chuỗi phiên bản hoặc sự hiện diện của `chkrootkit` không xác nhận được đường khai thác; không tạo hay chạy file tạm trong quá trình rà soát thụ động.

Theo dõi thêm một bước chuyển giữa các unit khi service chạy bằng root của timer thực hiện `systemctl restart <other>.service`: unit được khởi động lại có thể gọi shell bằng một script mà user ít đặc quyền hơn có thể ghi. Xác nhận `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, các đối số `ExecStart=` thực tế và quyền trên script cùng đường dẫn cha. Script có thể ghi chỉ là một ứng viên cho đến khi timer và service được khởi động lại hoạt động trong ngữ cảnh thực thi đó; kiểm tra thuộc tính unit mà không khởi động lại service nào.

Nếu một tác vụ có đặc quyền cao hơn tải script bằng hostname rồi chuyển phản hồi cho shell, hãy kiểm tra ai kiểm soát việc phân giải hostname đó cũng như script từ xa. File `/etc/hosts` có thể ghi, kể cả khi quyền truy cập được cấp qua group hoặc ACL, có thể chuyển hướng tên mà tác vụ phân giải cục bộ; phản hồi `curl` chỉ trở thành đường thực thi chéo user khi lệnh đã lên lịch thực sự chạy phản hồi đó và tác vụ sử dụng đường phân giải bị ảnh hưởng. Xác minh danh tính chạy tác vụ, URL và pipeline shell chính xác, hành vi proxy/DNS hiệu lực, cùng quyền trên file và thư mục cha. Bản thân file hosts có thể ghi chỉ là dấu hiệu cần rà soát, không chứng minh có consumer đặc quyền. Kiểm tra lịch và metadata mà không thay đổi ánh xạ hay tải script trong quá trình rà soát.

Một lần tải bằng `wget` được lên lịch với đặc quyền là ranh giới ghi file riêng biệt, kể cả khi nội dung tải về không được thực thi trực tiếp. [GNU Wget 1.18 thay đổi cách xử lý tên file mặc định khi chuyển hướng HTTP sang FTP để sửa CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); các bản cũ bị ảnh hưởng có thể dùng tên file từ FTP được chuyển hướng đến, còn `--trust-server-names` yêu cầu rõ hành vi đó. Nếu một bên có mức độ tin cậy thấp hơn kiểm soát phản hồi HTTP và tài nguyên FTP, hãy kiểm tra tác vụ có theo chuyển hướng hay không, bản Wget thực tế hoặc bản vá ngược của nhà cung cấp, tùy chọn output, danh tính chạy tác vụ, thư mục làm việc và khả năng tên file đích trở thành file khởi động. [Wget tải `WGETRC` hoặc `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), và [các thiết lập của nó có thể chọn nguồn POST hoặc đường dẫn output](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); một lần tải đặc quyền về sau là điều kiện tiên quyết riêng để xảy ra bất kỳ việc lộ dữ liệu hay ghi file nào. Quyền truy cập cổng thấp qua `authbind` chỉ liên quan khi caller thực sự có thể phục vụ URL mà tác vụ yêu cầu. Rà soát cấu hình và log theo cách thụ động, không phục vụ chuyển hướng hay chạy tác vụ. [Quyền truy cập thiết bị block thô thông qua group `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) không phụ thuộc vào đường tải qua mạng này.

Theo dõi cả file dữ liệu, không chỉ script. Một công cụ mô phỏng hoặc điều phối được lên lịch có thể đọc file YAML định nghĩa các process cần khởi chạy; nếu user ít đặc quyền hơn có thể sửa file đó và tác vụ chạy file dưới một account khác, dữ liệu có thể trở thành lệnh chạy với danh tính của tác vụ. Xác minh lệnh được lên lịch chính xác, user hiệu lực, đường dẫn file, ngữ nghĩa của parser và quyền ghi (bao gồm cả thư mục cha) trước khi xem file YAML có thể ghi là một đường thực thi. Đọc lịch và metadata file là đủ để phân loại thụ động; không chạy tác vụ hoặc sửa input của nó trong quá trình rà soát.

Cấu hình SSH client cũng là input có thể thực thi khi tác vụ có đặc quyền cao hơn chạy `ssh -F` với file mà user ít đặc quyền hơn có thể thay thế. OpenSSH [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) chạy lệnh cục bộ thông qua shell của client, còn `Host`/`Match` và các tùy chọn xuất hiện trước đó quyết định directive đó có được áp dụng hay không. Đối chiếu lệnh SSH được gọi chính xác theo lịch, danh tính chạy tác vụ, đường dẫn config được chọn, quyền ghi trên thư mục và file, cùng thứ tự tùy chọn hiệu lực trước khi kết luận đây là đường thực thi chéo user. Rà soát các bản ghi này mà không chạy tác vụ hoặc nạp config không đáng tin cậy dưới account có đặc quyền.

Một lệnh `scp` được lên lịch rồi dùng `ssh` để chạy script đã sao chép cần được rà soát thêm ranh giới tin cậy nếu user ít đặc quyền hơn kiểm soát dịch vụ SSH đích. Nếu dịch vụ đó có thể chuyển tiếp kết nối sang host khác, client có đặc quyền có thể xác thực với một endpoint ngoài dự kiến; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) làm yếu cơ chế bảo vệ khi host key thay đổi, tùy thuộc vào các hạn chế còn lại của OpenSSH và tùy chọn hiệu lực theo từng host. Xác định danh tính chạy tác vụ, đích thực tế và phương thức xác thực, danh tính hiệu lực của lệnh từ xa, và liệu đường dẫn đích tương tự có thể ghi được hoặc đã tồn tại trên host được chuyển hướng hay không. Việc thực thi file cũ hoặc do attacker kiểm soát còn đòi hỏi thao tác sao chép thất bại hoặc bỏ qua đường dẫn đó **và** wrapper vẫn tiếp tục chạy lệnh SSH; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) và cách xử lý trạng thái thoát tường minh ảnh hưởng đến luồng này. Một thiết lập host key yếu, process `sshpass` hiển thị hoặc thư mục tạm có thể ghi tự nó không chứng minh được chuỗi tấn công này. Kiểm tra lịch, script, cấu hình SSH và metadata file mà không chuyển hướng dịch vụ hay kích hoạt tác vụ trong quá trình rà soát.

Scheduler ứng dụng có đặc quyền có thể lấy các tác vụ từ bản ghi cơ sở dữ liệu thay vì file có thể ghi. Ví dụ, một mục cron chạy bằng root gọi Laravel [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) có thể đi đến code ứng dụng đọc các dòng task. Nếu account ít đặc quyền hơn có thể ghi một dòng chứa pathname cục bộ, và callback được lên lịch gọi PHP [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) dưới quyền root rồi gửi nội dung trả về đến webhook được chọn trong dòng đó, đây là đường lộ file có đặc quyền. Xác minh danh tính chạy cron, callback scheduler thực tế và luồng dữ liệu từ dòng đến pathname, quyền ghi cơ sở dữ liệu, bước xác thực sau khi đọc dòng và đích gửi đi. File `.env` của ứng dụng có thể đọc chỉ là manh mối về credential; validation ở web form hoặc mật khẩu cơ sở dữ liệu tự nó không chứng minh quyền kiểm soát dòng hay việc lộ dữ liệu. Kiểm tra lịch, code và quyền trên file credential theo cách thụ động, không truy vấn cơ sở dữ liệu hay lên lịch tác vụ trong quá trình rà soát.

Các tác vụ `incron` chạy theo sự kiện cũng cần được rà soát tương tự: [các mục incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) liên kết đường dẫn được theo dõi và sự kiện với lệnh chạy dưới danh tính chủ sở hữu bảng. User ít đặc quyền hơn có thể tác động gián tiếp đến file được theo dõi khi ứng dụng đi theo link từ một thư mục có thể ghi và ghi nội dung do attacker kiểm soát vào đích được theo dõi. Xác minh chủ sở hữu bảng thực tế, sự kiện, quyền trên đích và các thư mục cha, hành vi đi theo link của ứng dụng, và cách văn bản đó trở thành đối số lệnh. Cụ thể, [GNU Mailutils `mail` chấp nhận `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), và [lệnh thoát sang shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) của nó có thể chạy chương trình; một trường không đáng tin cậy được truyền thành tùy chọn riêng cho bản triển khai đó có thể dẫn đến thực thi lệnh. Các bản triển khai `mail` khác hoặc ranh giới đối số cố định, được trích dẫn đúng cách có thể hoạt động khác. Kiểm tra lịch, code ứng dụng và metadata file mà không sửa file được theo dõi hay kích hoạt tác vụ trong quá trình rà soát.

Log được theo dõi cũng có thể vượt qua ranh giới user thông qua script trợ giúp. Nếu account ít đặc quyền hơn có thể ghi log và chủ sở hữu `incron` đọc một trường từ đó rồi đưa vào chuỗi lệnh [`sh -c` mới](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), shell sẽ phân tích lại trường đó dưới danh tính của chủ sở hữu. Kiểm tra sự kiện được theo dõi chính xác, quyền trên log và thư mục cha, đường dẫn helper, cách chuyển đổi trường log và liệu luồng có đi đến lệnh thực thi hay không. Chỉ thấy log có thể ghi và một mục `incron` không chứng minh được luồng dữ liệu; không ghi dòng kích hoạt hay chạy helper trong quá trình rà soát thụ động.

Tác vụ gia hạn certificate cũng có thể vượt qua ranh giới tương tự. Một helper có đặc quyền có thể đọc subject X.509 từ certificate trong thư mục mà user ít đặc quyền hơn có thể ghi, rồi chèn common name vào chuỗi lệnh `bash -c` mới. [OpenSSL có thể hiển thị subject của certificate và kiểm tra thời hạn](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash phân tích chuỗi `-c` như input shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), vì vậy trích dẫn biến trong script bên ngoài không bảo vệ được lần phân tích thứ hai. Xác nhận danh tính được lên lịch, đường dẫn input chính xác và quyền ghi, nhánh gia hạn, cùng luồng dữ liệu đi vào `bash -c` trước khi gọi đây là command injection. Kiểm tra script và metadata certificate theo cách thụ động; không kích hoạt gia hạn trong quá trình rà soát.

Lần phân tích thứ hai tương tự có thể xảy ra khi tác vụ đặc quyền được lên lịch trích xuất tên từ archive hoặc package của user ít đặc quyền hơn rồi đưa tên đó qua `xargs -I` để chèn vào chuỗi lệnh `sh -c`. [GNU `xargs -I` thay placeholder trong các đối số ban đầu](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), còn [`sh -c` diễn giải chuỗi lệnh của nó](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Dù script bên ngoài đặt tên trích xuất trong dấu nháy, điều đó không làm cho chương trình shell được chèn về sau trở nên an toàn. Xác minh danh tính chạy tác vụ, đường dẫn input được chấp nhận chính xác và quyền ghi, việc kiểm tra archive cùng các điều kiện nhánh, và luồng dữ liệu từ tên đến shell. Thư mục upload có thể ghi hoặc lệnh `xargs` tự nó chỉ là manh mối; kiểm tra lịch, script và metadata đường dẫn mà không gửi package hay chạy tác vụ trong quá trình rà soát.

Một tác vụ nhập font hoặc image được lên lịch cũng có thể tin vào tên *bên trong* archive do caller cung cấp, kể cả khi tên file upload bên ngoài bị giới hạn. FontForge đã sửa command injection qua tên thành viên archive trong [thay đổi upstream cho CVE-2024-25081 và CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Xác nhận tác vụ có đặc quyền cao hơn thực sự mở archive từ đường dẫn mà user ít đặc quyền hơn có thể ghi hay không, danh tính chạy tác vụ, bản FontForge chính xác hoặc bản vá ngược của nhà cung cấp, và code xử lý archive có được gọi hay không. Chuỗi phiên bản hoặc phần mở rộng upload được phép tự nó không chứng minh việc thực thi. Kiểm tra lịch, quyền đường dẫn và metadata bản build mà không nhập archive không đáng tin cậy trong quá trình rà soát.

Network scanner được lên lịch có thể vượt qua ranh giới khác nếu script tùy chỉnh dùng subject certificate TLS từ xa làm tên file cục bộ. [Nmap NSE chạy các script được chọn mà không có sandbox](https://nmap.org/book/nse-usage.html), vì vậy hãy kiểm tra script thực tế và xem nó có ghép trường subject không đáng tin cậy vào thư mục dữ liệu mà thiếu kiểm tra containment hay không. Để lộ file đòi hỏi có target mà scheduler sẽ quét, đường dẫn được phân giải thành file mà danh tính chạy scanner có thể đọc, và báo cáo hoặc log được gửi đến nơi user ít đặc quyền hơn có thể đọc. Một trường certificate hoặc scanner đã cài không tự chứng minh được chuỗi này; rà soát lịch, script, cách phân giải đường dẫn và đích báo cáo mà không quét target mới trong quá trình rà soát thụ động.

Lệnh cron có đặc quyền truyền glob shell như `/path/to/tasks/*.yml` cho trình chạy Ansible cần được kiểm tra quyền thư mục, ngay cả khi mọi playbook hiện có đều chỉ đọc. User có quyền ghi và tìm kiếm trong thư mục được glob có thể tạo thêm playbook khớp mẫu. [Ansible playbook định nghĩa các task mà trình chạy thực thi](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), nhưng wrapper tùy chỉnh có thể lọc đường dẫn hoặc dùng danh tính khác: xác minh hành vi của wrapper, user cron thực tế, việc mở rộng shell, ACL, sticky bit và chính sách mount trước khi xem thư mục là đường thực thi. Kiểm tra metadata và wrapper theo cách tĩnh; không chạy tác vụ đã lên lịch trong quá trình rà soát.

Wrapper cron có đặc quyền có thể mở rộng glob rồi truyền tên file từ thư mục upload cho helper Perl. Toán tử [`<>` của Perl dùng `open` hai đối số](https://perldoc.perl.org/perlop#The-Null-Filehandle), vì vậy tên file khớp mẫu nếu bị diễn giải thành lệnh qua pipe có thể thực thi dưới danh tính của helper; [`<<>>` xem đối số là tên file theo nghĩa đen](https://perldoc.perl.org/perlop#The-Null-Filehandle). Xác nhận danh tính scheduler, thư mục làm việc và glob của wrapper, cách helper xử lý `@ARGV` thực tế, hạn chế tên file, và liệu danh tính ít đặc quyền hơn có thể đặt tên khớp mẫu thông qua quyền filesystem hoặc dịch vụ upload đã xác thực hay không. Dòng cron, script Perl hoặc thư mục FTP có thể ghi tự nó không chứng minh được toàn bộ chuỗi. Kiểm tra source và metadata mà không gửi tên file được tạo có chủ đích hay chạy tác vụ trong quá trình rà soát.

Script cron chỉ đọc vẫn có thể bị thay thế nếu account chạy tác vụ gọi script bằng pathname và user ít đặc quyền hơn có thể ghi cũng như truy cập qua thư mục cha không có sticky bit. Kiểm tra danh tính chạy tác vụ trong lịch, mọi thành phần của đường dẫn, sticky bit của thư mục, ACL và chính sách mount; rà soát metadata mà không di chuyển file hay chạy tác vụ.

Wrapper PHP chạy bằng cron có đặc quyền có thể gọi helper chưa tồn tại. Nếu wrapper gọi PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) với đường dẫn helper tuyệt đối cố định, user ít đặc quyền hơn có thể kiểm soát lần chạy sau bằng cách tạo tên đó trong thư mục cha nếu họ có quyền ghi tại đó. Xác nhận mục cron thực sự chạy wrapper dưới danh tính có đặc quyền cao hơn, chuỗi lệnh chính xác và chính sách thực thi của PHP, quyền ghi và tìm kiếm trên thư mục helper, hành vi symlink và sticky bit, cũng như helper vẫn chưa tồn tại. Thư mục có thể ghi hoặc helper bị thiếu tự nó chỉ là manh mối; kiểm tra lịch, source và metadata đường dẫn mà không tạo helper hay kích hoạt tác vụ.

Tác vụ được lên lịch cũng có thể dùng `find` để tìm script input rồi chuyển từng script cho một trình thông dịch. Ví dụ, hàm `system()` của [gnuplot gọi shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), vì vậy tác vụ có đặc quyền chạy `gnuplot` trên mọi file `*.plt` trong thư mục mà user ít đặc quyền hơn có thể ghi có thể thực thi lệnh dưới danh tính của tác vụ. [Quyền đọc thư mục kiểm soát việc liệt kê, còn quyền ghi và tìm kiếm (`x`) kiểm soát việc tạo và truy cập tên đã biết](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); hãy kiểm tra quyền ghi và tìm kiếm ngay cả khi `ls` không thể liệt kê thư mục. Đối chiếu danh tính scheduler và lệnh chính xác, hành vi của trình thông dịch, mẫu file được chọn và quyền thư mục; thư mục có thể ghi hoặc trình thông dịch đã cài tự nó không chứng minh được khả năng leo thang. Lịch riêng tư và tác vụ chạy trong thời gian ngắn có thể cần quan sát sự kiện được cho phép vì một snapshot process có thể bỏ lỡ chúng.

Với tác vụ PHP có đặc quyền, hãy kiểm tra các câu lệnh `include`/`require` cố định như một phần của chuỗi script thực thi. [PHP thực thi các file được include](https://www.php.net/manual/en/function.include.php), vì vậy file `.php` có thể ghi bởi group được include có thể chạy code dưới danh tính của tác vụ dù script chính chỉ đọc. Xác minh danh tính được lên lịch, cách phân giải include-path hiệu lực, quyền trên file và thư mục, và tác vụ có thực sự chạy hay không; một dòng cron mẫu trong comment chỉ là manh mối. Cách rà soát tương tự áp dụng cho [PHP built-in server](https://www.php.net/commandline.webserver) thuộc sở hữu root, được khởi chạy với `-S` và `-t <document-root>`: listener loopback vẫn có thể thực thi PHP của ứng dụng khi nhận yêu cầu cục bộ. Kiểm tra process và source mà không kích hoạt bất kỳ cơ chế nào trong quá trình rà soát.

Tác vụ PHP có đặc quyền cũng có thể vượt ranh giới qua một **file dữ liệu**: nếu user ít đặc quyền hơn có thể thay đổi đúng file được truyền cho [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP có thể gọi phương thức `__wakeup()` hoặc `__unserialize()` của class đã nạp khi khôi phục object. Rà soát danh tính hiệu lực của tác vụ, quyền trên file và các thư mục cha, các class đã nạp và tác động thực tế của phương thức, chẳng hạn ghi file được chọn qua thuộc tính. Log có thể ghi hoặc lời gọi `unserialize()` tự nó không chứng minh được một đường khai thác khả dụng. Kiểm tra source và metadata mà không ghi input đã serialize hay chạy tác vụ trong quá trình rà soát.

Tác vụ cron chạy bằng root có thể gọi **CLI page runner** của ứng dụng PHP thay vì web server. Theo dõi document root và URI được runner chọn đến entrypoint PHP thực tế; nếu account dịch vụ web có thể ghi entrypoint đó, yêu cầu CLI được lên lịch có thể thực thi code đã bị sửa dưới quyền root dù runner và wrapper cron chỉ đọc. Xác nhận danh tính scheduler, cách ánh xạ URI sang file chính xác, quyền hiệu lực trên file và các thư mục cha, và liệu integrity check có bảo vệ chính entrypoint hay không. Kiểm tra source và metadata mà không gọi runner hoặc sửa trang trong quá trình rà soát.

Một process `ipython` được khởi chạy bởi tác vụ đã lên lịch hoặc user khác từ thư mục làm việc dùng chung cần được rà soát file khởi động. [Ghi chú phát hành bảo mật của IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) giải thích rằng các bản bị ảnh hưởng tìm profile và cấu hình trong thư mục hiện tại, bao gồm code trong `profile_default/startup`, trước khi sửa CVE-2022-21699. Đối chiếu bản đã cài thực tế hoặc bản vá của nhà cung cấp, thư mục làm việc của lệnh, danh tính process có đặc quyền cao hơn và khả năng user ít đặc quyền hơn ghi cũng như tìm kiếm đúng đường dẫn khởi động đó. `ipython` đã cài, thư mục có thể ghi hoặc chuỗi phiên bản tự nó không chứng minh rằng một danh tính khác sẽ nạp file tại đó. Kiểm tra lịch và metadata đường dẫn mà không khởi chạy trình thông dịch có đặc quyền cao hơn.

Với server PHP có đặc quyền gọi các hàm từ extension native tùy chỉnh, hãy xác định PHP SAPI của service cùng `php.ini` hiệu lực và các file `.ini` được quét trước khi rà soát extension. [PHP nạp các thư viện `extension` được cấu hình khi khởi động](https://www.php.net/manual/en/ini.core.php), và [CLI cùng web SAPI có thể dùng các file cấu hình khác nhau](https://www.php.net/manual/en/configuration.file.php). Vì vậy, form đăng nhập có thể truy cập hoặc listener cục bộ có thể truyền chuỗi do user kiểm soát vào code đã biên dịch chạy dưới danh tính service. Ghi lại `User=`, `ExecStart=`, thư mục làm việc, đường dẫn extension thực tế và các đối số do caller kiểm soát của unit; chỉ có `.so` hoặc socket loopback không chứng minh được lỗi memory corruption. Phân tích riêng parser tùy chỉnh, thay vì gửi probe trong quá trình rà soát thụ động.

Khi wrapper có đặc quyền băm script theo pathname rồi mở lại pathname đó để thực thi, digest chỉ xác thực object được đọc trong lần mở đầu tiên. Nếu user ít đặc quyền hơn có thể thay entry của script trong thư mục giữa hai lần mở, lần thực thi sau có thể phân giải thành object khác, ngay cả khi file script ban đầu thuộc sở hữu root. FIFO có thể kéo dài giai đoạn kiểm tra, nhưng khả năng khai thác phụ thuộc vào quyền trên thư mục cha có thể thay đổi, việc thực sự mở riêng biệt hai lần, danh tính scheduler, quy tắc sticky bit và mount, cùng thời điểm. Kiểm tra wrapper và kết quả `namei -l` như manh mối thụ động; checksum thành công tự nó không chứng minh pathname được bảo vệ ở lần mở sau.

Tác vụ backup có đặc quyền cũng có thể **làm lộ** dữ liệu mà không thực thi lệnh do attacker cung cấp. Theo dõi liệu user ít đặc quyền hơn có thể tạo file điều khiển mà tác vụ đọc hay không, liệu sau đó tác vụ có mở nguồn được bảo vệ như `/etc/shadow` hay không, và liệu URL do attacker chọn hoặc output có thể đọc được có nhận kết quả hay không. Xác minh đủ cả ba phần trước khi gọi đây là đường lộ dữ liệu. Lệnh shell cố định trong cùng script không tự biến file điều khiển đó thành input shell injection. Kiểm tra script và quyền file mà không chạy tác vụ hay tạo file điều khiển trong quá trình rà soát.

Nếu tác vụ được lên lịch với đặc quyền chạy `curl -K FILE` hoặc `curl --config FILE`, [curl coi các tùy chọn trong file đó như đối số dòng lệnh](https://curl.se/docs/manpage.html). User ít đặc quyền hơn kiểm soát đúng file tại thời điểm curl đọc có thể ảnh hưởng đến URL được yêu cầu, input file cục bộ hoặc đường dẫn output. Xác nhận danh tính hiệu lực của tác vụ, quyền ghi trên file và các thư mục cha, thời điểm của bất kỳ tác vụ nào khác thay thế file, và cách tùy chọn config tương tác với tùy chọn dòng lệnh cố định trước khi kết luận có thể đọc hoặc ghi dữ liệu được bảo vệ. Đường dẫn config có thể ghi hoặc cờ `-K` hiển thị tự nó không chứng minh rằng tùy chọn được chọn có hiệu lực; kiểm tra lịch và metadata mà không chạy tác vụ hay tải URL trong quá trình rà soát thụ động.

Nếu mục cron gọi script helper, hãy kiểm tra cả thư mục làm việc của helper và lệnh archive. Wildcard không được trích dẫn trong thư mục user khác có thể ghi có thể biến tên file thành tùy chọn của archiver; các thao tác checkpoint của GNU tar là một ví dụ. Xác nhận danh tính chạy tác vụ, thư mục input có thể ghi, archiver và tùy chọn chính xác, và `--` có chấm dứt việc phân tích tùy chọn hay không trước khi kết luận có đường thực thi lệnh chéo user. Xem [hành vi wildcard và tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Một trường hợp lộ file backup riêng biệt có thể xảy ra khi helper có đặc quyền chạy `cd INPUT_DIR; tar ... *` mà không kiểm tra `cd` có thành công hay không. Nếu user ít đặc quyền hơn có thể xóa hoặc thay thế `INPUT_DIR`, `cd` thất bại có thể khiến shell vẫn ở thư mục trước đó, nơi lệnh archive tiếp theo có thể đọc. Xác minh thư mục làm việc ban đầu của tác vụ, đường dẫn `cd` thất bại thực tế, script có thoát hay dùng `&&` hay không, tùy chọn archiver chính xác và archive output có thể được user ít đặc quyền đọc hay không. Thư mục input có thể ghi hoặc archive có thể đọc tự nó chỉ là manh mối; kiểm tra helper và quyền đường dẫn mà không thay đổi tác vụ đang chạy.

Executable được lên lịch có thể che giấu một shell script thay vì loại bỏ ranh giới tin cậy của nó: [SHc](https://github.com/neurobin/shc) bọc nội dung script đã mã hóa trong binary native rồi thực thi bằng shell lúc chạy. Đuôi `.sh.x` hoặc ELF không rõ nội dung chỉ là manh mối cần rà soát. Để đánh giá việc chèn tùy chọn qua tên file, hãy xác định danh tính scheduler có đặc quyền, thư mục làm việc và lệnh thực tế của helper, khả năng user thấp hơn tạo tên khớp mẫu tại đó, và liệu wildcard không được trích dẫn có đến được lệnh như `rsync` mà không có ranh giới tùy chọn hay không. Tùy chọn remote-shell của [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) chỉ liên quan nếu chính đường lệnh đó được dùng. Hạn chế về khả năng quan sát `/proc` hoặc việc giải mã tĩnh thất bại khiến lệnh chưa rõ; không chạy helper có đặc quyền chỉ để phân loại nó.

Văn bản dòng lệnh của process cũng là input không đáng tin cậy đối với helper có đặc quyền. User ít đặc quyền hơn có thể chọn process title hoặc `argv[0]` khớp với `pgrep -f`; tên khớp không xác thực executable hay chủ sở hữu của nó. Nếu script chạy bằng root thu thập văn bản đó, sửa một phần thành `apache2ctl`/`httpd` rồi thực thi kết quả mà không dùng mảng đối số cố định, tùy chọn do attacker chọn có thể trỏ đến thư mục cấu hình hoặc error log khác. Việc phân tích cấu hình Apache có thể nạp module hoặc gọi helper đã cấu hình, vì vậy không xác thực cấu hình không đáng tin cậy bằng root trong quá trình rà soát. Kiểm tra chủ sở hữu scheduler, helper chính xác, danh tính process và luồng dữ liệu vào đối số; đây là injection tùy chọn/cấu hình, trừ khi việc thực thi ký tự đặc biệt của shell được chứng minh riêng.

Parser chạy bằng root đưa văn bản không đáng tin cậy vào phép tính số học của Bash có thể thực thi các phép thay thế trong văn bản đó. [Hướng dẫn leo thang đặc quyền](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) có ví dụ minh họa. Xác nhận nguồn input và lệnh phân tích trước khi xem mọi biểu thức số học là có thể khai thác.

Với tác vụ có đặc quyền phân tích log ứng dụng, hãy theo dõi các trường không đáng tin cậy vượt qua lần phân tích đầu tiên. Account ít đặc quyền hơn có thể ghi log thông qua process group hiện tại hoặc ảnh hưởng đến các trường request được ghi log; một bản ghi sau đó có thể chọn image, metadata của image trở thành pathname thứ hai dùng để mở XML. Kiểm tra danh tính hiệu lực của tác vụ, quyền ghi log thực tế, cách xử lý delimiter, containment của đường dẫn canonical và XML được chọn có do attacker kiểm soát hay không. Mở rộng external entity có thể biến lần đọc thứ hai thành việc lộ file có đặc quyền nếu kết quả mở rộng được đưa đến output mà user ít đặc quyền hơn có thể đọc. [Hướng dẫn bảo mật xử lý XML của Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) mô tả các biện pháp kiểm soát quyền truy cập DTD/entity bên ngoài; hãy kiểm tra parser đã cài và các thiết lập hiệu lực của nó. Log có thể ghi hoặc file XML đơn lẻ chỉ là manh mối. Rà soát code và metadata mà không đưa dữ liệu vào parser đã lên lịch trong quá trình rà soát.

Cũng kiểm tra các tác vụ có đặc quyền tạo file từ repository Git của user khác. Script có thể dùng `git ls-tree` và `git cat-file` thay vì `git checkout`, nhưng vẫn tin vào đường dẫn trong tree do attacker kiểm soát khi ghép chúng với thư mục staging. Đường dẫn tuyệt đối và thành phần `..` có thể thoát khỏi thư mục đó trừ khi đích được chuẩn hóa và kiểm tra containment trước khi ghi. `git -c safe.directory=*` cho phép truy cập repository thuộc sở hữu khác; tự nó không tạo ra khả năng ghi tùy ý.

Backup cơ sở dữ liệu chạy bằng root có thể tạo thêm ranh giới quyền sở hữu. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) sao chép các file thông thường bổ sung được đặt trong thư mục dữ liệu nguồn, và định dạng plain mặc định ghi file vào `-D` dưới dạng cây thư mục. Nếu account ít đặc quyền hơn có thể tạo hoặc sửa các file nguồn đó, hãy kiểm tra quyền sở hữu và mode của đích sau khi sao chép, đường dẫn có thể truy cập và thực thi hay không, và mount có `nosuid` hay không. Bản sao thuộc root giữ nguyên quyền set-ID có thể nguy hiểm; backup chỉ tạo tar, quyền bị loại bỏ hoặc đích không thể truy cập không tạo ra cùng đường khai thác. Theo dõi wrapper được lên lịch và user hiệu lực trước khi xem lệnh backup là một phát hiện.

## Quan sát tác vụ chạy trong thời gian ngắn

Một snapshot process duy nhất có thể bỏ lỡ tác vụ chạy trong vài mili giây. Đối chiếu khai báo timer/cron với log và, khi được cho phép, công cụ giám sát sự kiện process như `pspy` hoặc audit. Đối chiếu chủ sở hữu tác vụ được lên lịch, command line chính xác và các file mà tác vụ đọc hoặc ghi. Web UI scheduler trên loopback là một giao diện riêng; xem [ví dụ Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
