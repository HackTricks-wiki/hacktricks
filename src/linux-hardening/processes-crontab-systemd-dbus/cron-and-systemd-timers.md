# Cron Jobs और Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

Scheduled tasks, मौजूदा shell से अलग identity और environment के साथ चल सकते हैं। cron, `at`, anacron और systemd timers enumerate करें, फिर हर scheduled command को उसकी scripts, imports, working directory और writable inputs के ज़रिए trace करें।

## Schedules enumerate करें

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontab में आमतौर पर user field होता है; किसी user के crontab में नहीं। वास्तविक scheduler का प्रभावी PATH और environment जाँचें। `run-parts --test /etc/cron.daily` दिखाता है कि उस host पर कौन-से file names चुने जाएँगे। Control characters किसी entry को सामान्य output में छिपा सकते हैं, इसलिए जब कोई schedule संदिग्ध लगे, तो `cat -A` या `sed -n l` का उपयोग करें।

## विशेषाधिकार प्राप्त फ़ाइल और कमांड resolution का पता लगाएँ

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

लिखने योग्य script chains, `EnvironmentFile=` paths, drop-ins, symlinks, relative commands, wildcard expansion, और privileged task द्वारा copy या execute की जाने वाली binaries की समीक्षा करें। Timer अपनी `Unit=` setting के ज़रिए किसी अलग नाम वाली service activate कर सकता है। मुख्य primitives की व्याख्या [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md), और [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) pages में है।

Scheduled root-run `chkrootkit` script के लिए, पुराने [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) के लिए installed source की जाँच करें: `SLAPPER_FILES` temporary path की जाँच के बाद unquoted `file_port=$file_port $i` उस file को execute कर सकता है। असली script या vendor patch, root scheduling, ठीक उसी temporary path पर lower-user की write access, उसका executable status, और mount policy verify करें। केवल version string या `chkrootkit` की मौजूदगी से यह path सिद्ध नहीं होता; passive review के दौरान temporary file न बनाएँ और न चलाएँ।

अगर timer की root service `systemctl restart <other>.service` चलाती है, तो एक unit hop और trace करें: restarted unit किसी lower-privileged user की लिखी script के साथ shell चला सकती है। प्रभावी `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, सटीक `ExecStart=` arguments, और script तथा उसके parent path की permissions की पुष्टि करें। Writable script केवल एक candidate है, जब तक timer और restarted service उस execution context में active न हों; किसी भी service को restart किए बिना unit properties जाँचें।

अगर higher-privileged job hostname से script fetch करके response को shell में देता है, तो remote script के साथ यह भी जाँचें कि उस hostname का resolution किसके नियंत्रण में है। Writable `/etc/hosts` file—जिसमें group या ACL से मिली access भी शामिल है—ऐसा नाम redirect कर सकती है जिसे job locally resolve करता है। `curl` response cross-user execution path तभी बनता है जब scheduled command वास्तव में उस response को चलाता हो और job प्रभावित resolver path का उपयोग करता हो। Job की run-as identity, सटीक URL और shell pipeline, प्रभावी proxy/DNS व्यवहार, तथा file और parent-directory permissions verify करें। Writable hosts file अपने-आप में review cue है, privileged consumer का प्रमाण नहीं। Enumeration के दौरान mapping बदले या script fetch किए बिना schedule और metadata जाँचें।

Privileged scheduled `wget` fetch एक अलग file-write boundary है, भले ही downloaded body सीधे execute न हो। [GNU Wget 1.18 ने CVE-2016-4971 ठीक करने के लिए HTTP-to-FTP redirect filename की default handling बदली](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); पुराने प्रभावित builds redirect में FTP filename इस्तेमाल कर सकते थे, जबकि `--trust-server-names` उस व्यवहार को स्पष्ट रूप से माँगता है। अगर lower-trust party HTTP response और FTP resource नियंत्रित करती है, तो जाँचें कि job उस redirect को follow करता है या नहीं, उसका असली Wget build या vendor backport क्या है, output options, run-as identity, working directory, और क्या destination filename startup file बन सकता है। [Wget `WGETRC` या `$HOME/.wgetrc` लोड करता है](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), और [उसकी settings POST source या output path चुन सकती हैं](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); इससे होने वाले disclosure या write के लिए बाद में एक अलग privileged fetch आवश्यक है। `authbind` के ज़रिए low port तक access तभी relevant है जब caller वास्तव में वही URL serve कर सके जिसकी job को ज़रूरत है। Redirect serve किए या job चलाए बिना configuration और logs की passive समीक्षा करें। [ `disk` group के ज़रिए raw block-device access](../user-information/interesting-groups-linux-pe/README.md#disk-group) इस network-fetch path से स्वतंत्र है।

Scripts के साथ data files भी trace करें। Scheduled simulation या orchestration tool ऐसी YAML file पढ़ सकता है जो शुरू किए जाने वाले processes परिभाषित करती है; अगर lower-privileged user उस file को edit कर सके और job उसे दूसरे account के तहत चलाए, तो data job की identity के तहत commands बन सकता है। Writable YAML file को execution path मानने से पहले सटीक scheduled command, प्रभावी user, file path, parser semantics, और write access (parent directories सहित) verify करें। Passive triage के लिए schedule और file metadata पढ़ना पर्याप्त है; enumeration के दौरान job न चलाएँ और उसका input न बदलें।

जब higher-privileged job, lower-privileged user द्वारा बदली जा सकने वाली file पर `ssh -F` चलाता है, तब SSH client configuration भी executable input बन जाती है। OpenSSH का [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) client के shell के ज़रिए local command चलाता है, जबकि `Host`/`Match` और पहले के options तय करते हैं कि वह directive लागू होता है या नहीं। इसे cross-user execution path कहने से पहले सटीक scheduled SSH invocation, run-as identity, चुना हुआ config path, directory और file write permissions, तथा प्रभावी option order का मिलान करें। Privileged account के रूप में job चलाए या untrusted config load किए बिना इन records की समीक्षा करें।

Scheduled `scp` के बाद copied script चलाने वाला `ssh` तब दूसरी trust-boundary review माँगता है जब lower-privileged user destination SSH service को नियंत्रित करता हो। अगर वह service connection को किसी दूसरे host पर forward कर सकती है, तो privileged client अनपेक्षित endpoint पर authenticate कर सकता है; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) बदली हुई host-key protection को कमज़ोर करता है, OpenSSH की शेष restrictions और प्रभावी per-host options के अधीन। Job की run-as identity, असली destination और authentication method, remote command की प्रभावी identity, और redirected host पर वही destination path writable या पहले से मौजूद है या नहीं—यह तय करें। पुरानी या attacker-controlled file का execution तभी संभव है जब copy fail हो या उस path को न छुए **और** wrapper SSH command तक आगे बढ़े; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) और explicit status handling इस flow को प्रभावित करते हैं। कमज़ोर host-key setting, दिखता हुआ `sshpass` process, या writable temporary directory अकेले इस chain को सिद्ध नहीं करते। Enumeration के दौरान service redirect या job trigger किए बिना schedule, script, SSH configuration, और file metadata जाँचें।

Privileged application scheduler अपनी jobs writable files के बजाय database rows से ले सकता है। उदाहरण के लिए, root cron entry जो Laravel का [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) चलाती है, ऐसे application code तक पहुँच सकती है जो task rows पढ़ता है। अगर lower-privileged account local pathname वाली row लिख सके और scheduled callback root के तहत PHP [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) से उसे पढ़कर body को row द्वारा चुने webhook पर भेजे, तो यह privileged file-disclosure path है। Cron identity, असली scheduler callback और row-to-path data flow, database write authorization, row पढ़ने के बाद validation, और outbound destination verify करें। Readable application `.env` केवल credentials का सुराग है; web-form validation या database password अकेले row control या disclosure सिद्ध नहीं करते। Enumeration के दौरान database query या task schedule किए बिना schedule, code, और credential-file permissions की passive समीक्षा करें।

Event-driven `incron` jobs की भी इसी तरह समीक्षा करें: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) watched path और event को table owner की identity के तहत चलने वाले command से जोड़ती हैं। अगर application writable directory से link follow करके attacker-controlled text watched target में लिखती है, तो lower-privileged user watched file को अप्रत्यक्ष रूप से प्रभावित कर सकता है। असली table owner, event, target और ancestor permissions, application का link-following behavior, और वह text command arguments कैसे बनता है—यह verify करें। विशेष रूप से, [GNU Mailutils `mail` में `--exec` स्वीकार होता है](https://mailutils.org/manual/html_node/Invoking-Mail.html), और उसका [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) program चला सकता है; उस implementation में अलग option के रूप में दिया गया untrusted field command execution तक पहुँच सकता है। दूसरे `mail` implementations या quoted, fixed argument boundary का व्यवहार अलग हो सकता है। Enumeration के दौरान watched file बदले या job trigger किए बिना schedule, application code, और file metadata जाँचें।

Watched log भी helper script के ज़रिए user boundary पार कर सकता है। अगर lower-privileged account log में लिख सके और `incron` owner उससे field पढ़कर नए [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) में डालता है, तो shell उस field को owner की identity के तहत दोबारा parse करता है। सटीक watched event, log और parent permissions, helper path, log field का transformation, और resulting command तक पहुँच होती है या नहीं—यह जाँचें। Writable log और `incron` entry दिखना अकेले data flow सिद्ध नहीं करता; passive enumeration के दौरान trigger line न लिखें और helper न चलाएँ।

Certificate-renewal jobs भी यही boundary पार कर सकती हैं। Privileged helper lower-privileged writable directory में certificate से X.509 subject पढ़कर उसका common name नए `bash -c` command string में डाल सकता है। [OpenSSL certificate का subject दिखा सकता है और उसकी expiry जाँच सकता है](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash `-c` string को shell input की तरह parse करता है](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), इसलिए outer script में variable को quote करना दूसरी parse को सुरक्षित नहीं करता। Command injection कहने से पहले scheduled identity, सटीक input path और write rights, renewal branch, तथा `bash -c` तक data flow की पुष्टि करें। Enumeration के दौरान renewal trigger किए बिना script और certificate metadata की passive समीक्षा करें।

यही दूसरी parse तब भी हो सकती है जब privileged scheduled job lower-privileged user के archive या package से name निकालकर उसे `xargs -I` के ज़रिए `sh -c` command string में डालता है। [GNU `xargs -I` initial arguments में placeholder को बदलता है](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), और [`sh -c` अपने command string को interpret करता है](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)। भले outer script निकाले गए name को quote करे, बाद में substitute किया गया shell program सुरक्षित नहीं हो जाता। Job की run-as identity, सटीक स्वीकार्य input path और write access, archive validation और branch conditions, तथा name-to-shell data flow verify करें। Writable upload directory या `xargs` invocation अकेले केवल एक सुराग है; enumeration के दौरान package submit किए या job चलाए बिना schedule, script, और path metadata जाँचें।

Scheduled font या image importer भी caller-supplied archive के *अंदर* मौजूद names पर भरोसा कर सकता है, भले upload का बाहरी filename प्रतिबंधित हो। FontForge ने अपने [CVE-2024-25081 और CVE-2024-25082 के upstream change](https://github.com/fontforge/fontforge/pull/5367) में archive member-name command injection ठीक किया। पुष्टि करें कि higher-privileged job वास्तव में lower-privileged writable path से archive खोलता है, उसकी run-as identity, सटीक FontForge build या vendor backport, और archive-handling code path क्या है। Version string या अनुमत upload suffix अकेले execution का प्रमाण नहीं है। Enumeration के दौरान untrusted archive import किए बिना schedule, path permissions, और build metadata जाँचें।

Scheduled network scanners एक अलग boundary पार कर सकते हैं जब custom script remote TLS certificate subject को local filename की तरह इस्तेमाल करती है। [Nmap NSE चुनी गई scripts बिना sandbox के चलाता है](https://nmap.org/book/nse-usage.html), इसलिए असली script की समीक्षा करें और जाँचें कि वह containment checks के बिना untrusted subject field को data directory के path से जोड़ती है या नहीं। File disclosure के लिए scheduler द्वारा scan किए जाने वाला target, scanner की run-as identity के लिए readable file तक पहुँचने वाला path, और lower-privileged reader को दी जाने वाली report या log—तीनों ज़रूरी हैं। Certificate field या installed scanner अकेले इस chain को सिद्ध नहीं करते; passive enumeration के दौरान नया target scan किए बिना schedule, script, path resolution, और report destination की समीक्षा करें।

Privileged cron command जो shell glob जैसे `/path/to/tasks/*.yml` को Ansible runner को देती है, उसमें directory permissions जाँचें—भले हर मौजूदा playbook केवल read-only हो। Globbed directory में write और search access वाला user एक और matching playbook बना सकता है। [Ansible playbooks वे tasks परिभाषित करते हैं जिन्हें runner execute करता है](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), लेकिन custom wrapper paths filter कर सकता है या अलग identity इस्तेमाल कर सकता है: directory को execution path मानने से पहले उसका behavior, असली cron user, shell expansion, ACLs, sticky bit, और mount policy verify करें। Enumeration के दौरान scheduled job चलाए बिना metadata और wrapper की static जाँच करें।

Privileged cron wrapper glob expand करने के बाद upload directory के filenames Perl helper को दे सकता है। Perl का [`<>` diamond operator two-argument `open` इस्तेमाल करता है](https://perldoc.perl.org/perlop#The-Null-Filehandle), इसलिए matching filename को pipe command की तरह interpret करके helper की identity के तहत execute किया जा सकता है; [`<<>>` arguments को literal filenames मानता है](https://perldoc.perl.org/perlop#The-Null-Filehandle)। Scheduler identity, wrapper working directory और glob, helper का असली `@ARGV` handling, filename restrictions, और lower-privileged identity filesystem rights या authenticated upload service के ज़रिए matching name रख सकती है या नहीं—यह पुष्टि करें। Cron line, Perl script, या writable FTP directory अकेले पूरी chain सिद्ध नहीं करते। Crafted filename submit किए या job चलाए बिना source और metadata जाँचें।

Read-only cron script भी बदली जा सकती है, अगर scheduled account उसे pathname से चलाता हो और lower-privileged user उसके non-sticky parent directory में write और traverse कर सके। Schedule की run-as identity, path के हर component, directory sticky bit, ACLs, और mount policy जाँचें; file को हटाए-बदले या job चलाए बिना metadata की समीक्षा करें।

Privileged PHP cron wrapper ऐसे helper तक पहुँच सकता है जो अभी मौजूद ही न हो। अगर वह PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) को fixed absolute helper path के साथ call करता है, तो उसके parent directory में वह name बनाने वाला lower-privileged user बाद की run में execute होने वाली चीज़ नियंत्रित कर सकता है। पुष्टि करें कि cron entry wrapper को वास्तव में higher identity के तहत चलाती है, सटीक command string और PHP execution policy, helper directory पर write और search rights, symlink और sticky-bit behavior, तथा helper path अभी भी absent है या नहीं। Writable directory या missing helper अकेले केवल एक सुराग है; helper बनाए या job trigger किए बिना schedule, source, और path metadata जाँचें।

Scheduled job `find` से input scripts खोजकर हर script interpreter को दे सकता है। उदाहरण के लिए, [gnuplot का `system()` function shell invoke करता है](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), इसलिए lower-privileged user की writable directory में हर `*.plt` file पर `gnuplot` चलाने वाली privileged job, job की identity के तहत commands execute कर सकती है। [Directory पर read permission listing नियंत्रित करती है, जबकि write और search (`x`) से नाम बनाना और ज्ञात नामों तक पहुँचना नियंत्रित होता है](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); `ls` directory list न कर सके तब भी write और search access जाँचें। सटीक scheduler identity और command, interpreter behavior, चुना हुआ file pattern, और directory permissions का मिलान करें; writable directory या installed interpreter अकेले escalation सिद्ध नहीं करते। Private schedules और थोड़ी देर चलने वाली jobs के लिए authorized event observation की ज़रूरत हो सकती है, क्योंकि एक process snapshot उन्हें miss कर सकता है।

Privileged PHP job के लिए executable script chain के हिस्से के रूप में literal `include`/`require` statements की जाँच करें। [PHP included files को evaluate करता है](https://www.php.net/manual/en/function.include.php), इसलिए group-writable included `.php` file job की identity के तहत code चला सकती है, भले main script read-only हो। Scheduled identity, प्रभावी include-path resolution, file और directory permissions, और job वास्तव में चलता है या नहीं—verify करें; comment में दिया sample cron line केवल एक सुराग है। यही समीक्षा root-owned [PHP built-in server](https://www.php.net/commandline.webserver) पर भी लागू होती है जिसे `-S` और `-t <document-root>` के साथ शुरू किया गया हो: loopback listener भी local requests के लिए application PHP execute कर सकता है। Enumeration के दौरान कोई trigger invoke किए बिना process और source जाँचें।

Privileged PHP job **data file** के ज़रिए भी boundary पार कर सकती है: अगर lower-privileged user [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) को दी जाने वाली सटीक file बदल सके, तो PHP object restore करते समय loaded class के `__wakeup()` या `__unserialize()` method को invoke कर सकता है। Job की प्रभावी identity, file और ancestor permissions, loaded classes, और property से चुनी गई file write जैसे वास्तविक method side effects की समीक्षा करें। Writable log या `unserialize()` call अकेले उपयोगी path सिद्ध नहीं करते। Enumeration के दौरान serialized input लिखे या job चलाए बिना source और metadata जाँचें।

Root cron task web server के बजाय PHP application का **CLI page runner** चला सकती है। Runner के चुने हुए document root और URI को असली PHP entrypoint तक trace करें; अगर web-service account उस entrypoint को लिख सके, तो scheduled CLI request बदला हुआ code root के रूप में execute कर सकती है, भले runner और cron wrapper read-only हों। Scheduler identity, सटीक URI-to-file resolution, प्रभावी file और ancestor permissions, तथा entrypoint को integrity check सुरक्षित करता है या नहीं—पुष्टि करें। Enumeration के दौरान runner invoke किए या page बदले बिना source और metadata जाँचें।

Scheduled job या किसी दूसरे user द्वारा shared working directory से शुरू किया गया `ipython` process startup-file review माँगता है। [IPython की security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) के अनुसार, CVE-2022-21699 के fix से पहले प्रभावित builds current directory में profiles और configuration—जिसमें `profile_default/startup` code भी शामिल है—खोजते थे। असली installed build या vendor patch, command working directory, higher-privileged process identity, और lower-privileged user की सटीक startup path पर write और search करने की क्षमता का मिलान करें। Installed `ipython`, writable directory, या version string अकेले यह सिद्ध नहीं करते कि कोई दूसरा identity वहाँ की file load करेगा। Higher-privileged interpreter launch किए बिना schedule और path metadata जाँचें।

Custom native extension के functions call करने वाले privileged PHP server के लिए extension की समीक्षा से पहले service का PHP SAPI और उसकी प्रभावी `php.ini` तथा scanned `.ini` files trace करें। [PHP startup पर configured `extension` libraries load करता है](https://www.php.net/manual/en/ini.core.php), और [CLI तथा web SAPIs अलग configuration files इस्तेमाल कर सकते हैं](https://www.php.net/manual/en/configuration.file.php)। इसलिए reachable login form या local listener user-controlled strings को service identity के तहत चल रहे compiled code तक पहुँचा सकता है। Unit का `User=`, `ExecStart=`, working directory, असली extension path, और caller-controlled arguments दर्ज करें; केवल `.so` या loopback socket की मौजूदगी memory-corruption flaw सिद्ध नहीं करती। Passive enumeration के दौरान probes भेजने के बजाय किसी custom parser का अलग से विश्लेषण करें।

जब privileged wrapper किसी script को pathname से hash करके बाद में उसी pathname को फिर से खोलकर execute करता है, तो digest केवल पहली बार खोले गए object को authenticate करता है। अगर lower-privileged user उन दोनों opens के बीच script की directory entry बदल सके, तो original script file root-owned होने पर भी बाद का execution किसी दूसरे object को resolve कर सकता है। FIFO check phase को लंबा कर सकती है, लेकिन path replaceable parent-directory rights, अलग-अलग opens, scheduler identity, sticky-bit और mount rules, तथा timing पर निर्भर है। Wrapper और `namei -l` output को passive सुराग के रूप में जाँचें; सफल checksum अकेले यह सिद्ध नहीं करता कि बाद वाला pathname सुरक्षित है।

Privileged backup job attacker-supplied commands execute किए बिना भी data **disclose** कर सकती है। Trace करें कि lower-privileged user ऐसा control file बना सकता है या नहीं जिसे job पढ़े, फिर job `/etc/shadow` जैसे protected source को खोले या नहीं, और attacker-selected URL या readable output को result मिलता है या नहीं। Disclosure path कहने से पहले इन तीनों हिस्सों की पुष्टि करें। उसी script में fixed shell command होना अपने-आप उस control file को shell-injection input नहीं बनाता। Enumeration के दौरान job चलाए या control file रखे बिना script और file permissions जाँचें।

अगर privileged scheduled job `curl -K FILE` या `curl --config FILE` चलाती है, तो [curl उस file के options को command-line arguments की तरह मानता है](https://curl.se/docs/manpage.html)। ठीक उस file को curl के पढ़ने के समय नियंत्रित करने वाला lower-privileged user requested URL, local-file input, या output path प्रभावित कर सकता है। Protected read या write का दावा करने से पहले job की प्रभावी identity, file और ancestor write rights, file बदलने वाली किसी अन्य job का timing, और config options का fixed command-line options से interaction verify करें। Writable config path या दिखता हुआ `-K` flag अकेले यह सिद्ध नहीं करता कि चुने गए options प्रभावी होंगे; passive enumeration के दौरान job चलाए या URL fetch किए बिना schedule और metadata जाँचें।

अगर cron entry helper script invoke करती है, तो helper की working directory और archive command भी जाँचें। किसी दूसरे user की writable directory पर unquoted wildcard filenames को archiver options में बदल सकता है; GNU tar के checkpoint actions इसका एक उदाहरण हैं। Cross-user command path का दावा करने से पहले scheduled run-as identity, writable input directory, सटीक archiver और options, तथा option parsing रोकने के लिए `--` मौजूद है या नहीं—पुष्टि करें। [wildcard और tar behavior देखें](../interesting-files-permissions/wildcards-spare-tricks.md)।

Backup-file disclosure का एक अलग मामला तब हो सकता है जब privileged helper `cd INPUT_DIR; tar ... *` चलाए और यह न जाँचे कि `cd` सफल हुआ या नहीं। अगर lower-privileged user `INPUT_DIR` हटाए या बदल सके, तो `cd` fail होने पर shell पिछली directory में रह सकती है, जहाँ से बाद की archive command files पढ़ ले। Job की शुरुआती working directory, वास्तविक failed-`cd` path, script exit करता है या `&&` इस्तेमाल करता है, सटीक archiver options, और output archive lower user के लिए readable है या नहीं—verify करें। Writable input directory या readable archive अकेले केवल सुराग हैं; live job बदले बिना helper और path permissions जाँचें।

Scheduled executable shell script को हटाने के बजाय छिपा सकता है: [SHc](https://github.com/neurobin/shc) encrypted script text को native binary में wrap करता है और runtime पर shell के ज़रिए execute करता है। `.sh.x` suffix या opaque ELF केवल review का सुराग है। Filename option injection जाँचने के लिए privileged scheduler identity, helper की असली working directory और command, वहाँ matching names बनाने की lower-user की क्षमता, और unquoted glob किसी `rsync` जैसे command तक option boundary के बिना पहुँचता है या नहीं—स्थापित करें। [`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) तभी relevant है जब ठीक वही command path इस्तेमाल हो। Restricted `/proc` visibility या static decryption का fail होना command को अज्ञात छोड़ता है; केवल classify करने के लिए privileged helper न चलाएँ।

Process command-line text भी privileged helper को दिया जाने वाला untrusted input है। Lower-privileged user ऐसा process title या `argv[0]` चुन सकता है जो `pgrep -f` से match हो; matching name executable या उसके owner को authenticate नहीं करता। अगर root-run script वह text capture करे, उसका कुछ हिस्सा `apache2ctl`/`httpd` में rewrite करे, और fixed argument array के बिना resulting command execute करे, तो attacker-chosen options अलग configuration directory या error log चुन सकते हैं। Apache configuration parsing modules load कर सकती है या configured helpers तक पहुँच सकती है, इसलिए enumeration के दौरान root के रूप में untrusted configuration validate न करें। Scheduler owner, सटीक helper, process identity, और data-to-argument flow की समीक्षा करें; जब तक shell metacharacter execution अलग से साबित न हो, यह option/configuration injection है।

Untrusted text को Bash arithmetic में देने वाला root-run parser उस text में substitutions execute कर सकता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) में worked example दिया गया है। हर arithmetic expression को exploitable मानने से पहले input source और parsing command की पुष्टि करें।

Application log parse करने वाली privileged job के लिए, पहले parse के बाद भी untrusted fields को trace करें। Lower-privileged account अपने current process group के ज़रिए log लिख सकता है या logged request fields को प्रभावित कर सकता है; कोई record image चुन सकता है, जिसका metadata XML खोलने के लिए दूसरा pathname बन जाए। Job की प्रभावी identity, log पर असली write access, delimiter handling, canonical path containment, और चुनी गई XML attacker-controlled है या नहीं—जाँचें। अगर expanded result lower-privileged user के लिए readable output तक पहुँचता है, तो external-entity expansion इस दूसरी read को privileged file disclosure में बदल सकती है। [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) external DTD/entity access के controls बताती है; installed parser और उसकी प्रभावी settings जाँचें। Writable log या XML file अकेले केवल सुराग है। Enumeration के दौरान scheduled parser को input दिए बिना code और metadata की समीक्षा करें।

ऐसी privileged jobs की भी जाँच करें जो किसी दूसरे user के Git repository से files बनाती हैं। Script `git checkout` के बजाय `git ls-tree` और `git cat-file` इस्तेमाल कर सकती है, फिर भी staging directory से जोड़ते समय attacker-controlled tree paths पर भरोसा कर सकती है। Absolute paths और `..` components उस directory से बाहर निकल सकते हैं, जब तक लिखने से पहले destination normalize करके containment की जाँच न हो। `git -c safe.directory=*` अलग ownership वाले repositories तक access देता है; अपने-आप arbitrary-write condition नहीं बनाता।

Root-run database backup ownership की एक और boundary बना सकता है। PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) source data directory में रखी अतिरिक्त regular files को copy करता है, और इसका default plain format `-D` में directory tree के रूप में files लिखता है। अगर lower-privileged account source files बना या बदल सकता है, तो resulting destination का ownership और mode, उसका path traversable और executable है या नहीं, तथा mount पर `nosuid` है या नहीं—जाँचें। Preserved set-ID permissions वाली root-owned copy खतरनाक हो सकती है; केवल tar backup, stripped permissions, या inaccessible destination से वही path सिद्ध नहीं होता। Backup command को finding मानने से पहले scheduled wrapper और प्रभावी user trace करें।

## अल्पकालिक काम देखें

एक process snapshot उस job को miss कर सकता है जो milliseconds में चलती है। Timer/cron declarations की तुलना logs से करें और, जहाँ authorized हो, `pspy` या audit जैसे process-event monitoring का उपयोग करें। Scheduled owner, सटीक command line, और task द्वारा पढ़ी या लिखी जाने वाली files का मिलान करें। Loopback scheduler web UI एक अलग interface है; [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc) देखें।
