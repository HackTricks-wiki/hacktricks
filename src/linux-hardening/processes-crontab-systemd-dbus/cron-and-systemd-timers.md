# Cron Jobs and Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

Scheduled tasks can run with a different identity and environment from the current shell. Enumerate cron, `at`, anacron, and systemd timers, then trace each scheduled command through its scripts, imports, working directory, and writable inputs.

## Enumerate schedules

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontabs usually include a user field; a user's crontab does not. Inspect the effective PATH and environment of the actual scheduler. `run-parts --test /etc/cron.daily` shows which file names would be selected on that host. Control characters can hide an entry in casual output, so use `cat -A` or `sed -n l` when a schedule looks suspicious.

## Trace privileged file and command resolution

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Review writable script chains, `EnvironmentFile=` paths, drop-ins, symlinks, relative commands, wildcard expansion, and binaries copied or executed by a privileged task. A timer may activate a service with a different name through its `Unit=` setting. The [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md), and [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) pages explain the main primitives.

For a scheduled root-run `chkrootkit` script, inspect the installed source for the old [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): an unquoted `file_port=$file_port $i` after a check of a `SLAPPER_FILES` temporary path can execute that file. Verify the actual script or vendor patch, root scheduling, lower-user write access to the exact temporary path, its executable status, and mount policy. A version string or the presence of `chkrootkit` alone does not establish the path; do not create or run a temporary file during passive review.

Trace one more unit hop when a timer's root service runs `systemctl restart <other>.service`: the restarted unit can invoke a shell with a script writable by a lower-privileged user. Confirm the effective `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, exact `ExecStart=` arguments, and permissions on the script and its parent path. A writable script is only a candidate until the timer and restarted service are active in that execution context; inspect the unit properties without restarting either service.

If a higher-privileged job fetches a script by hostname and passes the response to a shell, check who controls that hostname's resolution as well as the remote script. A writable `/etc/hosts` file, including access granted by a group or ACL, can redirect a name that the job resolves locally; a `curl` response only becomes a cross-user execution path when the actual scheduled command runs that response and the job uses the affected resolver path. Verify the job's run-as identity, exact URL and shell pipeline, effective proxy/DNS behavior, and file and parent-directory permissions. A writable hosts file by itself is a review cue, not proof that a privileged consumer exists. Inspect the schedule and metadata without changing the mapping or fetching the script during enumeration.

A privileged scheduled `wget` fetch is a separate file-write boundary even if the downloaded body is never executed directly. [GNU Wget 1.18 changed the default HTTP-to-FTP redirect filename handling to fix CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); older affected builds could use the redirected FTP filename, while `--trust-server-names` requests that behavior explicitly. If a lower-trust party controls the HTTP response and FTP resource, inspect whether the job follows that redirect, its actual Wget build or vendor backport, output options, run-as identity, working directory, and whether the destination filename can become a startup file. [Wget loads `WGETRC` or `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), and [its settings can select a POST source or output path](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); a later privileged fetch is a distinct prerequisite for any resulting disclosure or write. Access to a low port through `authbind` is relevant only when the caller can actually serve the URL the job requests. Review configuration and logs passively, without serving a redirect or running the job. [Raw block-device access through the `disk` group](../user-information/interesting-groups-linux-pe/README.md#disk-group) is independent of this network-fetch path.

Trace data files as well as scripts. A scheduled simulation or orchestration tool may read a YAML file that defines processes to start; if a lower-privileged user can edit that file and the job runs it under another account, the data can become commands under the job's identity. Verify the exact scheduled command, effective user, file path, parser semantics, and write access (including parent directories) before treating a writable YAML file as an execution path. Reading the schedule and file metadata is enough for passive triage; do not run the job or modify its input during enumeration.

An SSH client configuration is also executable input when a higher-privileged job runs `ssh -F` against a file a lower-privileged user can replace. OpenSSH's [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) runs a local command through the client's shell, while `Host`/`Match` and earlier options determine whether that directive applies. Correlate the exact scheduled SSH invocation, run-as identity, selected config path, directory and file write permissions, and effective option order before calling it a cross-user execution path. Review these records without running the job or loading the untrusted config as the privileged account.

A scheduled `scp` followed by `ssh` to run the copied script needs a second trust-boundary review when a lower-privileged user controls the destination SSH service. If that service can forward the connection to another host, the privileged client may authenticate to an unintended endpoint; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) weakens changed-host-key protection, subject to OpenSSH's remaining restrictions and effective per-host options. Establish the job's run-as identity, actual destination and authentication method, the remote command's effective identity, and whether the same destination path is writable or pre-existing on the redirected host. Execution of an older or attacker-controlled file additionally requires the copy to fail or miss that path **and** the wrapper to continue to its SSH command; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) and explicit status handling affect that flow. A weak host-key setting, visible `sshpass` process, or writable temporary directory alone does not establish this chain. Inspect the schedule, script, SSH configuration, and file metadata without redirecting the service or triggering the job during enumeration.

A privileged application scheduler may take its jobs from database rows instead of writable files. For example, a root cron entry invoking Laravel's [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) can reach application code that reads task rows. If a lower-privileged account can write a row containing a local pathname, and the scheduled callback calls PHP's [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) under root and sends the returned body to a row-selected webhook, that is a privileged file-disclosure path. Verify the cron identity, actual scheduler callback and row-to-path data flow, database write authorization, validation after the row is read, and outbound destination. A readable application `.env` is only a credential lead; web-form validation or a database password alone does not prove row control or disclosure. Inspect the schedule, code, and credential-file permissions passively without querying the database or scheduling a task during enumeration.

Event-driven `incron` jobs deserve the same review: [incrontab entries](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associate a watched path and event with a command run under the table owner's identity. A lower-privileged user may influence a watched file indirectly when an application follows a link from a writable directory and writes attacker-controlled text into the watched target. Verify the actual table owner, event, target and ancestor permissions, application link-following behavior, and how that text becomes command arguments. In particular, [GNU Mailutils `mail` accepts `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), and its [shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) can run a program; an untrusted field passed as a separate option to that implementation can cross into command execution. Other `mail` implementations or a quoted, fixed argument boundary may behave differently. Inspect the schedule, application code, and file metadata without modifying the watched file or triggering the job during enumeration.

A watched log can also cross a user boundary through a helper script. If a lower-privileged account can write the log and the `incron` owner reads a field from it into a new [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), the shell parses that field again under the owner's identity. Check the exact watched event, log and parent permissions, helper path, transformation of the log field, and whether the resulting command is reached. Seeing a writable log and an `incron` entry alone does not establish the data flow; do not write a trigger line or run the helper during passive enumeration.

Certificate-renewal jobs can cross the same boundary. A privileged helper may read an X.509 subject from a certificate in a lower-privileged writable directory and insert its common name into a new `bash -c` command string. [OpenSSL can display a certificate's subject and check its expiry](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash parses the `-c` string as shell input](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), so quoting the variable in the outer script does not protect the second parse. Confirm the scheduled identity, exact input path and write rights, the renewal branch, and the data flow into `bash -c` before calling it command injection. Inspect the script and certificate metadata passively; do not trigger renewal during enumeration.

The same second parse can occur when a privileged scheduled job extracts a name from a lower-privileged user's archive or package and pipes it to `xargs -I` for insertion into a `sh -c` command string. [GNU `xargs -I` replaces the placeholder in initial arguments](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), and [`sh -c` interprets its command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Even if the outer script quotes the extracted name, that does not make a later substituted shell program safe. Verify the job's run-as identity, the exact accepted input path and write access, archive validation and branch conditions, and the name-to-shell data flow. A writable upload directory or `xargs` invocation alone is only a lead; inspect the schedule, script, and path metadata without submitting a package or running the job during enumeration.

A scheduled font or image importer can likewise trust names *inside* a caller-supplied archive even when the upload's outer filename is restricted. FontForge fixed archive member-name command injection in its [upstream change for CVE-2024-25081 and CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirm that a higher-privileged job actually opens an archive from a lower-privileged writable path, its run-as identity, the exact FontForge build or vendor backport, and the archive-handling code path. A version string or a permitted upload suffix alone is not proof of execution. Inspect schedule, path permissions, and build metadata without importing an untrusted archive during enumeration.

Scheduled network scanners can cross a different boundary when a custom script treats a remote TLS certificate subject as a local filename. [Nmap NSE runs selected scripts without a sandbox](https://nmap.org/book/nse-usage.html), so inspect the actual script and whether it joins an untrusted subject field to a data directory without containment checks. File disclosure requires a target the scheduler will scan, a path that resolves to a file readable by the scanner's run-as identity, and a report or log delivered to a lower-privileged reader. A certificate field or an installed scanner alone does not prove that chain; review the schedule, script, path resolution, and report destination without scanning a new target during passive enumeration.

A privileged cron command that passes a shell glob such as `/path/to/tasks/*.yml` to an Ansible runner deserves a directory-permission check, even when every existing playbook is read-only. A user with write and search access to the globbed directory may be able to create another matching playbook. [Ansible playbooks define tasks that the runner executes](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), but a custom wrapper may filter paths or use a different identity: verify its behavior, the actual cron user, shell expansion, ACLs, sticky bit, and mount policy before treating the directory as an execution path. Inspect metadata and the wrapper statically; do not run the scheduled job during enumeration.

A privileged cron wrapper can pass filenames from an upload directory to a Perl helper after expanding a glob. Perl's [`<>` diamond operator uses two-argument `open`](https://perldoc.perl.org/perlop#The-Null-Filehandle), so a matching filename interpreted as a pipe command can execute under the helper's identity; [`<<>>` treats arguments as literal filenames](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirm the scheduler identity, wrapper working directory and glob, the helper's actual `@ARGV` handling, filename restrictions, and whether a lower-privileged identity can place a matching name through filesystem rights or an authenticated upload service. A cron line, Perl script, or writable FTP directory alone does not prove the full chain. Inspect source and metadata without submitting a crafted filename or running the job during enumeration.

A read-only cron script is still replaceable if the scheduled account runs it by pathname and the lower-privileged user can write and traverse its non-sticky parent directory. Check the schedule's run-as identity, every path component, directory sticky bit, ACLs and mount policy; review metadata without moving the file or running the job.

A privileged PHP cron wrapper can reach a helper that does not yet exist. If it calls PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) with a fixed absolute helper path, a lower-privileged user who can create that name in its parent directory may control what a later run executes. Confirm the cron entry actually runs the wrapper under the higher identity, the exact command string and PHP execution policy, write and search rights on the helper directory, symlink and sticky-bit behavior, and whether the helper path is still absent. A writable directory or a missing helper alone is only a lead; inspect the schedule, source, and path metadata without creating the helper or triggering the job.

A scheduled job may also discover input scripts with `find` and pass each one to an interpreter. For example, [gnuplot's `system()` function invokes a shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), so a privileged job that runs `gnuplot` on every `*.plt` file in a lower-privileged user's writable directory can execute commands with the job's identity. [Directory read permission controls listing, while write and search (`x`) control creating and accessing known names](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); check write and search access even when `ls` cannot list the directory. Correlate the exact scheduler identity and command, the interpreter's behavior, the selected file pattern, and directory permissions; a writable directory or an installed interpreter alone does not establish escalation. Private schedules and short-lived jobs may require authorized event observation because one process snapshot can miss them.

For a privileged PHP job, inspect literal `include`/`require` statements as part of the executable script chain. [PHP evaluates included files](https://www.php.net/manual/en/function.include.php), so a group-writable included `.php` file can run code with the job's identity even when the main script is read-only. Verify the scheduled identity, effective include-path resolution, file and directory permissions, and whether the job actually runs; a sample cron line in a comment is only a clue. The same review applies to a root-owned [PHP built-in server](https://www.php.net/commandline.webserver) started with `-S` and `-t <document-root>`: a loopback listener may still execute application PHP for local requests. Inspect the process and source without invoking either trigger during enumeration.

A privileged PHP job can also cross the boundary through a **data file**: if a lower-privileged user can change the exact file passed to [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP may invoke a loaded class's `__wakeup()` or `__unserialize()` method while restoring an object. Review the job's effective identity, the file and ancestor permissions, the loaded classes, and the actual method side effects, such as a property-selected file write. A writable log or a call to `unserialize()` alone does not prove a usable path. Inspect source and metadata without writing serialized input or running the job during enumeration.

A root cron task may invoke a PHP application's **CLI page runner** rather than the web server. Trace the runner's selected document root and URI to the actual PHP entrypoint; if that entrypoint is writable by the web-service account, the scheduled CLI request can execute its changed code as root even when the runner and cron wrapper are read-only. Confirm the scheduler identity, exact URI-to-file resolution, effective file and ancestor permissions, and whether an integrity check protects the entrypoint itself. Inspect source and metadata without invoking the runner or changing the page during enumeration.

An `ipython` process started by a scheduled job or another user from a shared working directory deserves a startup-file review. [IPython's security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explain that affected builds searched the current directory for profiles and configuration, including `profile_default/startup` code, before the fix for CVE-2022-21699. Correlate the actual installed build or vendor patch, command working directory, higher-privileged process identity, and the lower-privileged user's ability to write and search the exact startup path. An installed `ipython`, a writable directory, or a version string alone does not prove that another identity will load a file there. Inspect the schedule and path metadata without launching the higher-privileged interpreter.

For a privileged PHP server that calls functions from a custom native extension, trace the service's PHP SAPI and its effective `php.ini` plus scanned `.ini` files before reviewing the extension. [PHP loads configured `extension` libraries at startup](https://www.php.net/manual/en/ini.core.php), and [CLI and web SAPIs can use different configuration files](https://www.php.net/manual/en/configuration.file.php). A reachable login form or local listener can therefore pass user-controlled strings into compiled code running with the service identity. Record the unit's `User=`, `ExecStart=`, working directory, actual extension path, and caller-controlled arguments; the mere presence of a `.so` or a loopback socket does not establish a memory-corruption flaw. Analyze any custom parser separately rather than sending probes during passive enumeration.

When a privileged wrapper hashes a script by pathname and later opens that pathname again to execute it, the digest authenticates only the object read during the first open. If a lower-privileged user can replace the script's directory entry between those opens, the later execution may resolve a different object even when the original script file is root-owned. A FIFO can lengthen the check phase, but the path depends on replaceable parent-directory rights, actual separate opens, scheduler identity, sticky-bit and mount rules, and timing. Inspect the wrapper and `namei -l` output as a passive lead; a successful checksum alone is not proof that the later pathname is protected.

A privileged backup job can also **disclose** data without executing attacker-supplied commands. Trace whether a lower-privileged user can create a control file that the job reads, whether the job then opens a protected source such as `/etc/shadow`, and whether an attacker-selected URL or readable output receives the result. Verify all three parts before calling it a disclosure path. A fixed shell command in the same script does not by itself make that control file a shell-injection input. Inspect the script and file permissions without running the job or planting a control file during enumeration.

If a privileged scheduled job runs `curl -K FILE` or `curl --config FILE`, [curl treats options in that file as command-line arguments](https://curl.se/docs/manpage.html). A lower-privileged user who controls the exact file when curl reads it may influence the requested URL, local-file input, or output path. Confirm the job's effective identity, file and ancestor write rights, timing of any other job that replaces the file, and how config options interact with fixed command-line options before claiming a protected read or write. A writable config path or visible `-K` flag alone does not prove that the chosen options take effect; inspect the schedule and metadata without running the job or fetching a URL during passive enumeration.

If a cron entry invokes a helper script, inspect the helper's working directory and archive command too. An unquoted wildcard over a directory writable by another user can turn filenames into archiver options; GNU tar's checkpoint actions are one example. Confirm the scheduled run-as identity, writable input directory, exact archiver and options, and whether `--` terminates option parsing before claiming a cross-user command path. See [wildcard and tar behavior](../interesting-files-permissions/wildcards-spare-tricks.md).

A separate backup-file disclosure can arise when a privileged helper runs `cd INPUT_DIR; tar ... *` without checking whether `cd` succeeded. If a lower-privileged user can remove or replace `INPUT_DIR`, a failed `cd` may leave the shell in its previous directory, which the later archive command may read. Verify the job's initial working directory, a real failed-`cd` path, whether the script exits or uses `&&`, the exact archiver options, and whether the output archive is readable by the lower user. A writable input directory or a readable archive alone is only a lead; inspect the helper and path permissions without changing the live job.

A scheduled executable may conceal a shell script rather than remove its trust boundary: [SHc](https://github.com/neurobin/shc) wraps encrypted script text in a native binary and executes it through a shell at runtime. A `.sh.x` suffix or an opaque ELF is only a review lead. To assess filename option injection, establish the privileged scheduler identity, the helper's actual working directory and command, lower-user ability to create matching names there, and whether an unquoted glob reaches a command such as `rsync` without an option boundary. The [`rsync` remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) is relevant only if that exact command path is used. Restricted `/proc` visibility or failed static decryption leaves the command unknown; do not run the privileged helper merely to classify it.

Process command-line text is another untrusted input to a privileged helper. A lower-privileged user can choose a process title or `argv[0]` that matches `pgrep -f`; a matching name does not authenticate the executable or its owner. If a root-run script captures that text, rewrites part of it into `apache2ctl`/`httpd`, and executes the result without a fixed argument array, attacker-chosen options can select a different configuration directory or error log. Apache configuration parsing can load modules or reach configured helpers, so do not validate an untrusted configuration as root during enumeration. Inspect the scheduler owner, exact helper, process identity, and data-to-argument flow; this is option/configuration injection unless shell metacharacter execution is separately demonstrated.

A root-run parser that feeds untrusted text into Bash arithmetic can execute substitutions in that text. The [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) gives a worked example. Confirm the input source and parsing command before treating every arithmetic expression as exploitable.

For a privileged job that parses an application log, trace untrusted fields beyond the first parse. A lower-privileged account may be able to write the log through its current process group or influence logged request fields; a record can then select an image, whose metadata becomes a second pathname used to open XML. Check the job's effective identity, actual log-write access, delimiter handling, canonical path containment, and whether the selected XML is attacker-controlled. External-entity expansion can turn that second read into privileged file disclosure if the expanded result reaches a lower-privileged-readable output. The [Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documents controls for external DTD/entity access; inspect the installed parser and its effective settings. A writable log or XML file alone is only a lead. Review code and metadata without feeding the scheduled parser during enumeration.

Also inspect privileged jobs that materialize files from another user's Git repository. A script may use `git ls-tree` and `git cat-file` rather than `git checkout`, yet still trust attacker-controlled tree paths when it joins them to a staging directory. Absolute paths and `..` components can escape that directory unless the destination is normalized and checked for containment before writing. `git -c safe.directory=*` permits access to repositories with different ownership; it does not by itself create the arbitrary-write condition.

A root-run database backup can create another ownership boundary. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copies additional regular files placed in the source data directory, and its default plain format writes files into `-D` as a directory tree. If a lower-privileged account can create or modify those source files, inspect the resulting destination ownership and mode, whether its path is traversable and executable, and whether the mount has `nosuid`. A root-owned copy with preserved set-ID permissions can be dangerous; a tar-only backup, stripped permissions, or an inaccessible destination does not establish the same path. Trace the scheduled wrapper and effective user before treating the backup command as a finding.

## Observe short-lived work

A single process snapshot may miss a job that runs for milliseconds. Compare timer/cron declarations with logs and, when authorized, process-event monitoring such as `pspy` or audit. Correlate the scheduled owner, exact command line, and files that the task reads or writes. A loopback scheduler web UI is a separate interface; see the [Crontab UI example](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
