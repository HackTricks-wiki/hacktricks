# Cron JobとSystemd Timer

{{#include ../../banners/hacktricks-training.md}}

スケジュールされたタスクは、現在のシェルとは異なるユーザーIDや環境で実行されることがあります。cron、`at`、anacron、systemd timerを列挙し、各スケジュールコマンドのスクリプト、インポート、作業ディレクトリ、書き込み可能な入力をたどって確認しましょう。

## スケジュールの列挙

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

System crontabには通常ユーザーフィールドがありますが、ユーザーのcrontabにはありません。実際のschedulerの有効なPATHと環境変数を確認してください。`run-parts --test /etc/cron.daily`を実行すると、そのホストで選択されるファイル名が表示されます。制御文字によって通常の出力ではエントリが隠れることがあるため、スケジュールが怪しい場合は`cat -A`または`sed -n l`を使ってください。

## 特権ファイルとコマンドの解決を追跡する

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

書き込み可能なスクリプトチェーン、`EnvironmentFile=` のパス、drop-in、シンボリックリンク、相対コマンド、ワイルドカード展開、特権タスクがコピーまたは実行するバイナリを確認してください。タイマーは `Unit=` 設定を通じて、別名のサービスを起動することがあります。[PATH](../linux-basics/linux-environment-variables.md#path)、[ワイルドカード](../interesting-files-permissions/wildcards-spare-tricks.md)、[ファイルリンク](../main-system-information/filesystem-links-and-file-descriptors.md)の各ページで、主要な基本要素を説明しています。

root で実行される定期 `chkrootkit` スクリプトについては、インストール済みソースを確認し、古い [slapper-loop の引用符の欠陥（CVE-2014-0476）](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476)がないか調べてください。`SLAPPER_FILES` の一時パスを確認した後に、`file_port=$file_port $i` を引用符で囲まずに実行すると、そのファイルを実行できる場合があります。実際のスクリプトまたはベンダーパッチ、root でのスケジュール実行、該当する正確な一時パスへの低権限ユーザーの書き込み権限、そのパスの実行可否、マウントポリシーを確認してください。バージョン文字列や `chkrootkit` の存在だけでは、この経路があるとは判断できません。受動的な確認中に一時ファイルを作成したり実行したりしないでください。

タイマーが root サービスを起動し、そのサービスが `systemctl restart <other>.service` を実行する場合は、さらに1つ先の unit まで追跡してください。再起動される unit が、低権限ユーザーに書き込み可能なスクリプトを使ってシェルを起動することがあります。有効な `User=`、`DynamicUser=`、`RootDirectory=`/`RootImage=`、正確な `ExecStart=` 引数、スクリプトとその親パスの権限を確認してください。書き込み可能なスクリプトは、タイマーと再起動されるサービスがその実行コンテキストで有効になるまでは、候補にすぎません。どちらのサービスも再起動せずに unit のプロパティを確認してください。

高権限ジョブがホスト名からスクリプトを取得し、その応答をシェルに渡す場合は、リモートスクリプトだけでなく、そのホスト名の名前解決を誰が制御できるかも確認してください。グループや ACL によるアクセス権を含め、書き込み可能な `/etc/hosts` ファイルを使えば、ジョブがローカルで名前解決するホスト名を別の宛先に向けられる場合があります。`curl` の応答がクロスユーザー実行経路になるのは、実際のスケジュール済みコマンドがその応答を実行し、ジョブが影響を受ける resolver 経路を使う場合に限られます。ジョブの実行ユーザー、正確な URL とシェルパイプライン、有効な proxy/DNS の挙動、ファイルと親ディレクトリの権限を確認してください。書き込み可能な hosts ファイルだけなら、確認の手がかりにすぎず、特権コンシューマーの存在を証明するものではありません。列挙中はマッピングを変更したりスクリプトを取得したりせず、スケジュールとメタデータを確認してください。

特権スケジュール済み `wget` による取得は、ダウンロードした本文を直接実行しない場合でも、別個のファイル書き込み境界です。[GNU Wget 1.18 では、CVE-2016-4971 を修正するため HTTP から FTP へのリダイレクト時のファイル名処理のデフォルトが変更されました](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html)。影響を受ける古いビルドではリダイレクト先の FTP ファイル名が使われる場合があり、`--trust-server-names` はその挙動を明示的に要求します。信頼度の低い当事者が HTTP 応答と FTP リソースを制御できる場合、ジョブがそのリダイレクトをたどるか、実際の Wget ビルドまたはベンダーバックポート、出力オプション、実行ユーザー、作業ディレクトリ、保存先ファイル名が起動ファイルになり得るかを確認してください。[Wget は `WGETRC` または `$HOME/.wgetrc` を読み込みます](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html)。また、[その設定で POST 元や出力先を指定できます](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html)。その結果として情報漏えいや書き込みが起きるには、後続の特権取得が別途必要です。低番ポートへの `authbind` 経由のアクセスが関係するのは、呼び出し元がジョブの要求する URL を実際に提供できる場合に限られます。リダイレクトを提供したりジョブを実行したりせず、設定とログを受動的に確認してください。[`disk` グループ経由の raw ブロックデバイスアクセス](../user-information/interesting-groups-linux-pe/README.md#disk-group)は、このネットワーク取得経路とは別の問題です。

スクリプトだけでなくデータファイルも追跡してください。スケジュール済みのシミュレーションツールやオーケストレーションツールが、起動するプロセスを定義した YAML ファイルを読み込むことがあります。低権限ユーザーがそのファイルを編集でき、ジョブが別アカウントで実行されるなら、そのデータがジョブの権限で実行されるコマンドになる可能性があります。書き込み可能な YAML ファイルを実行経路と見なす前に、正確なスケジュール済みコマンド、有効な実行ユーザー、ファイルパス、parser のセマンティクス、（親ディレクトリを含む）書き込み権限を確認してください。受動的なトリアージにはスケジュールとファイルメタデータの確認で十分です。列挙中にジョブを実行したり、入力を変更したりしないでください。

高権限ジョブが、低権限ユーザーに置き換え可能なファイルを `ssh -F` に渡す場合、SSH クライアント設定も実行可能な入力です。OpenSSH の [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) は、クライアントのシェルを通じてローカルコマンドを実行します。また、`Host`/`Match` と先行するオプションによって、そのディレクティブが適用されるかどうかが決まります。これをクロスユーザー実行経路と判断する前に、正確なスケジュール済み SSH 呼び出し、実行ユーザー、選択される設定ファイルのパス、ディレクトリとファイルの書き込み権限、有効なオプションの順序を照合してください。ジョブを実行したり、特権アカウントで信頼できない設定を読み込んだりせずに、これらの記録を確認してください。

スケジュール済みの `scp` の後に SSH で接続してコピーしたスクリプトを実行する場合、低権限ユーザーが宛先 SSH サービスを制御できるなら、2つ目の信頼境界を確認する必要があります。そのサービスが接続を別のホストに転送できる場合、特権クライアントが意図しないエンドポイントに認証する可能性があります。[`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) は、OpenSSH に残る制約と有効なホスト別オプションの範囲内で、ホスト鍵変更に対する保護を弱めます。ジョブの実行ユーザー、実際の宛先と認証方式、リモートコマンドの有効な実行ユーザー、リダイレクト先ホストに同じ宛先パスが書き込み可能な状態で存在するかを確認してください。古いファイルまたは攻撃者が制御するファイルが実行されるには、コピーが失敗するかそのパスを取りこぼす**ことに加えて**、ラッパーが SSH コマンドまで処理を続ける必要があります。[Bash の `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) と明示的な終了ステータス処理が、このフローに影響します。ホスト鍵設定が弱い、`sshpass` プロセスが見える、一時ディレクトリが書き込み可能というだけでは、このチェーンは成立しません。列挙中はサービスをリダイレクトしたりジョブを起動したりせず、スケジュール、スクリプト、SSH 設定、ファイルメタデータを確認してください。

特権アプリケーションの scheduler が、書き込み可能なファイルではなくデータベースの行からジョブを取得することもあります。たとえば、root cron エントリが Laravel の [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) を呼び出し、行に格納されたタスクを読むアプリケーションコードに到達する場合があります。低権限アカウントがローカルパス名を含む行を書き込めて、スケジュール済み callback が root で PHP の [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) を呼び出し、取得した本文をその行が指定した webhook に送るなら、これは特権ファイル漏えい経路です。cron の実行ユーザー、実際の scheduler callback と行からパスへのデータフロー、データベースの書き込み認可、行の読み込み後の検証、外部送信先を確認してください。読み取り可能なアプリケーション `.env` は認証情報の手がかりにすぎません。Web フォームの検証やデータベースパスワードだけでは、行の制御や情報漏えいは証明されません。列挙中にデータベースへ問い合わせたりタスクを登録したりせず、スケジュール、コード、認証情報ファイルの権限を受動的に確認してください。

イベント駆動の `incron` ジョブも同様に確認してください。[incrontab エントリ](https://manpages.debian.org/testing/incron/incrontab.5.en.html)は、監視対象のパスとイベントを、そのテーブル所有者の権限で実行するコマンドに関連付けます。アプリケーションが書き込み可能なディレクトリ内のリンクをたどり、攻撃者が制御するテキストを監視対象に書き込む場合、低権限ユーザーが間接的に監視対象ファイルへ影響を与える可能性があります。実際のテーブル所有者、イベント、対象と祖先の権限、アプリケーションのリンク追従動作、そのテキストがコマンド引数になる過程を確認してください。特に、[GNU Mailutils の `mail` は `--exec` を受け付けます](https://mailutils.org/manual/html_node/Invoking-Mail.html)。また、その[シェルエスケープコマンド](https://mailutils.org/manual/html_node/Shell-Escapes.html)はプログラムを実行できます。この実装で信頼できないフィールドが個別のオプションとして渡されると、コマンド実行に至る可能性があります。他の `mail` 実装や、引用符で囲まれた固定引数境界では、挙動が異なる場合があります。列挙中に監視対象ファイルを変更したりジョブを起動したりせず、スケジュール、アプリケーションコード、ファイルメタデータを確認してください。

監視対象のログも、ヘルパースクリプトを介してユーザー境界を越えることがあります。低権限アカウントがログを書き込めて、`incron` の所有者がそこからフィールドを読み取って新しい [`sh -c` コマンド文字列](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)に組み込む場合、シェルはそのフィールドを所有者の権限で再度解析します。正確な監視イベント、ログと親の権限、ヘルパーパス、ログフィールドの変換処理、その結果のコマンドに到達するかを確認してください。書き込み可能なログと `incron` エントリが見つかっただけではデータフローは証明されません。受動的な列挙中にトリガーとなる行を書き込んだりヘルパーを実行したりしないでください。

証明書の更新ジョブも、同じ境界を越えることがあります。特権ヘルパーが、低権限ユーザーの書き込み可能なディレクトリにある証明書から X.509 subject を読み取り、その common name を新しい `bash -c` コマンド文字列に挿入する場合があります。[OpenSSL は証明書の subject の表示と有効期限の確認ができます](https://docs.openssl.org/3.3/man1/openssl-x509/)。[Bash は `-c` 文字列をシェル入力として解析します](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html)。そのため、外側のスクリプトで変数を引用符で囲んでも、2回目の解析は防げません。コマンドインジェクションと判断する前に、スケジュールされた実行ユーザー、正確な入力パスと書き込み権限、更新処理の分岐、`bash -c` へのデータフローを確認してください。列挙中はスクリプトと証明書メタデータを受動的に確認し、更新処理を起動しないでください。

同じ2回目の解析は、特権スケジュール済みジョブが低権限ユーザーのアーカイブまたはパッケージから名前を抽出し、その名前を `xargs -I` で `sh -c` コマンド文字列に挿入する場合にも発生します。[GNU `xargs -I` は初期引数内のプレースホルダーを置換します](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html)。また、[`sh -c` はそのコマンド文字列を解釈します](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)。外側のスクリプトで抽出した名前を引用符で囲んでも、後から置換されるシェルプログラムが安全になるわけではありません。ジョブの実行ユーザー、受け付ける正確な入力パスと書き込み権限、アーカイブの検証と分岐条件、名前からシェルへのデータフローを確認してください。書き込み可能なアップロードディレクトリや `xargs` の呼び出しだけなら、手がかりにすぎません。列挙中にパッケージを送信したりジョブを実行したりせず、スケジュール、スクリプト、パスメタデータを確認してください。

スケジュール済みのフォントまたは画像のインポーターも、アップロード時の外側のファイル名が制限されていても、呼び出し元が提供したアーカイブ内の名前を信頼することがあります。FontForge は、[CVE-2024-25081 および CVE-2024-25082 に関する upstream の変更](https://github.com/fontforge/fontforge/pull/5367)で、アーカイブ内のメンバー名を利用したコマンドインジェクションを修正しました。高権限ジョブが低権限ユーザーの書き込み可能なパスから実際にアーカイブを開くか、その実行ユーザー、正確な FontForge ビルドまたはベンダーバックポート、アーカイブ処理のコードパスを確認してください。バージョン文字列や許可されたアップロード拡張子だけでは、実行の証明になりません。列挙中に信頼できないアーカイブをインポートせず、スケジュール、パス権限、ビルドメタデータを確認してください。

スケジュール済みネットワークスキャナーは、カスタムスクリプトがリモート TLS 証明書の subject をローカルファイル名として扱う場合、別の境界を越えることがあります。[Nmap NSE は選択されたスクリプトを sandbox なしで実行します](https://nmap.org/book/nse-usage.html)。そのため、実際のスクリプトを確認し、信頼できない subject フィールドを containment check なしでデータディレクトリに結合していないか調べてください。ファイル漏えいには、scheduler がスキャンする対象、スキャナーの実行ユーザーが読み取り可能なファイルに解決されるパス、低権限ユーザーが読める宛先に配信されるレポートまたはログが必要です。証明書フィールドやスキャナーのインストールだけでは、このチェーンは証明されません。受動的な列挙中に新しい対象をスキャンせず、スケジュール、スクリプト、パス解決、レポートの宛先を確認してください。

既存の playbook がすべて読み取り専用であっても、シェル glob のような `/path/to/tasks/*.yml` を Ansible runner に渡す特権 cron コマンドでは、ディレクトリの権限を確認してください。glob の対象ディレクトリに書き込みと search の権限があるユーザーは、一致する playbook を追加できる場合があります。[Ansible playbook は runner が実行するタスクを定義します](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html)。ただし、カスタムラッパーがパスをフィルターする場合や、別の実行ユーザーを使う場合があります。ディレクトリを実行経路と判断する前に、その挙動、実際の cron ユーザー、シェル展開、ACL、sticky bit、マウントポリシーを確認してください。列挙中にスケジュール済みジョブを実行せず、メタデータとラッパーを静的に確認してください。

特権 cron ラッパーが、glob 展開後にアップロードディレクトリ内のファイル名を Perl ヘルパーに渡すことがあります。Perl の [`<>` diamond operator は2引数形式の `open` を使います](https://perldoc.perl.org/perlop#The-Null-Filehandle)。そのため、一致するファイル名がパイプコマンドとして解釈されると、ヘルパーの実行ユーザーでコマンドが実行される可能性があります。[`<<>>` は引数をリテラルのファイル名として扱います](https://perldoc.perl.org/perlop#The-Null-Filehandle)。scheduler の実行ユーザー、ラッパーの作業ディレクトリと glob、ヘルパーの実際の `@ARGV` 処理、ファイル名の制限、低権限ユーザーがファイルシステム権限または認証済みアップロードサービスを通じて一致する名前を配置できるかを確認してください。cron エントリ、Perl スクリプト、書き込み可能な FTP ディレクトリだけでは、チェーン全体は証明されません。列挙中に細工したファイル名を送信したりジョブを実行したりせず、ソースとメタデータを確認してください。

スケジュール済みアカウントがパス名で実行するスクリプトは、低権限ユーザーが sticky bit のない親ディレクトリに書き込みと traverse の権限を持つ場合、スクリプト自体が読み取り専用でも置き換え可能です。スケジュールの実行ユーザー、すべてのパス要素、ディレクトリの sticky bit、ACL、マウントポリシーを確認してください。ファイルを移動したりジョブを実行したりせず、メタデータを確認してください。

特権 PHP cron ラッパーは、まだ存在しないヘルパーを呼び出すことがあります。固定の絶対ヘルパーパスを指定して PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) を呼び出す場合、その親ディレクトリに低権限ユーザーがその名前のファイルを作成できると、後の実行で何が実行されるかを制御できる可能性があります。cron エントリが実際にラッパーを高権限で実行するか、正確なコマンド文字列と PHP の実行ポリシー、ヘルパーディレクトリへの書き込みと search の権限、シンボリックリンクと sticky bit の挙動、ヘルパーパスがまだ存在しないかを確認してください。書き込み可能なディレクトリや存在しないヘルパーだけなら、手がかりにすぎません。列挙中にヘルパーを作成したりジョブを起動したりせず、スケジュール、ソース、パスメタデータを確認してください。

スケジュール済みジョブが `find` で入力スクリプトを見つけ、各ファイルを interpreter に渡すこともあります。たとえば、[gnuplot の `system()` 関数はシェルを起動します](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf)。そのため、低権限ユーザーの書き込み可能なディレクトリ内のすべての `*.plt` ファイルに対して `gnuplot` を実行する特権ジョブは、ジョブの実行ユーザーの権限でコマンドを実行する可能性があります。[ディレクトリの読み取り権限は一覧表示を制御し、書き込み権限と search（`x`）権限は名前の作成と既知の名前へのアクセスを制御します](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html)。`ls` で一覧表示できない場合でも、書き込みと search のアクセス権を確認してください。スケジュールの正確な実行ユーザーとコマンド、interpreter の挙動、選択されるファイルパターン、ディレクトリの権限を照合してください。書き込み可能なディレクトリや interpreter のインストールだけでは、権限昇格は証明されません。private なスケジュールや短時間で終了するジョブは、認可されたイベント監視が必要になる場合があります。単一のプロセススナップショットでは見逃す可能性があります。

特権 PHP ジョブでは、実行されるスクリプトチェーンの一部として、リテラルの `include`/`require` 文も確認してください。[PHP は include されたファイルを評価します](https://www.php.net/manual/en/function.include.php)。そのため、メインスクリプトが読み取り専用でも、グループ書き込み可能な `.php` ファイルが include されれば、ジョブの実行ユーザーでコードが実行される可能性があります。スケジュールの実行ユーザー、有効な include path の解決、ファイルとディレクトリの権限、ジョブが実際に実行されるかを確認してください。コメント中の cron の例は手がかりにすぎません。同じ確認は、`-S` と `-t <document-root>` を指定して起動した root 所有の [PHP built-in server](https://www.php.net/commandline.webserver) にも当てはまります。loopback listener でも、ローカルリクエストに対してアプリケーション PHP を実行することがあります。列挙中はどちらのトリガーも呼び出さず、プロセスとソースを確認してください。

特権 PHP ジョブは**データファイル**を介しても境界を越えることがあります。低権限ユーザーが [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) に渡される正確なファイルを変更できる場合、オブジェクトの復元中に、読み込まれたクラスの `__wakeup()` または `__unserialize()` メソッドが呼び出される可能性があります。ジョブの有効な実行ユーザー、ファイルと祖先の権限、読み込まれるクラス、プロパティで指定されたファイルへの書き込みなど、実際のメソッドの副作用を確認してください。書き込み可能なログや `unserialize()` の呼び出しだけでは、利用可能な経路の証明になりません。列挙中にシリアライズ入力を書き込んだりジョブを実行したりせず、ソースとメタデータを確認してください。

root cron タスクは、Web サーバーではなく PHP アプリケーションの**CLI page runner**を呼び出すことがあります。runner が選択する document root と URI を、実際の PHP entrypoint まで追跡してください。その entrypoint が Web サービスアカウントに書き込み可能なら、runner と cron ラッパーが読み取り専用でも、スケジュール済み CLI リクエストが変更されたコードを root で実行する可能性があります。scheduler の実行ユーザー、正確な URI からファイルへの解決、有効なファイルと祖先の権限、entrypoint 自体が整合性チェックで保護されているかを確認してください。列挙中に runner を呼び出したりページを変更したりせず、ソースとメタデータを確認してください。

共有作業ディレクトリで、スケジュール済みジョブまたは別ユーザーが `ipython` プロセスを起動する場合は、startup file を確認してください。[IPython のセキュリティリリースノート](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699)によると、影響を受けるビルドは CVE-2022-21699 の修正前、現在のディレクトリから profile と設定を検索しており、`profile_default/startup` のコードも対象でした。実際のインストール済みビルドまたはベンダーパッチ、コマンドの作業ディレクトリ、高権限プロセスの実行ユーザー、低権限ユーザーが正確な startup path に書き込みと search の権限を持つかを照合してください。`ipython` のインストール、書き込み可能なディレクトリ、バージョン文字列だけでは、別の実行ユーザーがそこにあるファイルを読み込むとは証明できません。列挙中は高権限 interpreter を起動せず、スケジュールとパスメタデータを確認してください。

カスタム native extension の関数を呼び出す特権 PHP server では、extension を確認する前に、サービスの PHP SAPI、有効な `php.ini`、スキャン対象の `.ini` ファイルを追跡してください。[PHP は起動時に設定された `extension` ライブラリを読み込みます](https://www.php.net/manual/en/ini.core.php)。また、[CLI と Web の SAPI では異なる設定ファイルが使われる場合があります](https://www.php.net/manual/en/configuration.file.php)。そのため、到達可能なログインフォームやローカル listener から、サービスの実行ユーザーで動くコンパイル済みコードに、ユーザー制御の文字列が渡る可能性があります。unit の `User=`、`ExecStart=`、作業ディレクトリ、実際の extension path、呼び出し元が制御する引数を記録してください。`.so` の存在や loopback socket だけでは、メモリ破損の脆弱性は証明されません。受動的な列挙中に probe を送信するのではなく、カスタム parser は個別に解析してください。

特権ラッパーがパス名でスクリプトの hash を計算し、後で同じパス名を再度開いて実行する場合、digest が認証するのは最初の open で読み込まれたオブジェクトだけです。低権限ユーザーがその2回の open の間にスクリプトのディレクトリエントリを置き換えられると、元のスクリプトファイルが root 所有でも、後の実行時に別のオブジェクトがそのパスから解決される可能性があります。FIFO はチェックのフェーズを長引かせることがありますが、この経路の成否は、置き換え可能な親ディレクトリの権限、実際に別々の open があるか、scheduler の実行ユーザー、sticky bit とマウントのルール、タイミングに依存します。ラッパーと `namei -l` の出力を受動的な手がかりとして確認してください。チェックサムが一致しただけでは、後のパス名による実行が保護されている証明にはなりません。

特権バックアップジョブは、攻撃者が提供するコマンドを実行しなくても、データを**漏えい**させることがあります。低権限ユーザーがジョブの読み込む制御ファイルを作成できるか、ジョブが続いて `/etc/shadow` などの保護されたソースを開くか、攻撃者が選択した URL または読み取り可能な出力先に結果を送るかを追跡してください。漏えい経路と判断する前に、3つすべてを確認してください。同じスクリプト内に固定シェルコマンドがあっても、それだけで制御ファイルがシェルインジェクション入力になるわけではありません。列挙中にジョブを実行したり制御ファイルを配置したりせず、スクリプトとファイル権限を確認してください。

特権スケジュール済みジョブが `curl -K FILE` または `curl --config FILE` を実行する場合は、[curl がそのファイル内のオプションをコマンドライン引数として扱う](https://curl.se/docs/manpage.html)ことを考慮してください。curl がそのファイルを読み込む時点で低権限ユーザーが正確なファイルを制御できると、要求 URL、ローカルファイル入力、出力先に影響を与える可能性があります。保護された読み取りや書き込みを主張する前に、ジョブの有効な実行ユーザー、ファイルと祖先の書き込み権限、別のジョブがファイルを置き換えるタイミング、設定オプションと固定コマンドラインオプションの相互作用を確認してください。書き込み可能な設定パスや見える `-K` フラグだけでは、指定したオプションが有効になるとは証明できません。列挙中にジョブを実行したり URL を取得したりせず、スケジュールとメタデータを確認してください。

cron エントリがヘルパースクリプトを呼び出す場合は、ヘルパーの作業ディレクトリとアーカイブコマンドも確認してください。他のユーザーが書き込み可能なディレクトリに対して、引用符で囲まないワイルドカードを使うと、ファイル名が archiver のオプションとして扱われる可能性があります。GNU tar の checkpoint action はその一例です。クロスユーザーのコマンド実行経路と判断する前に、スケジュールの実行ユーザー、書き込み可能な入力ディレクトリ、正確な archiver とオプション、`--` でオプション解析を終了しているかを確認してください。[ワイルドカードと tar の挙動](../interesting-files-permissions/wildcards-spare-tricks.md)を参照してください。

特権ヘルパーが `cd INPUT_DIR; tar ... *` を実行する際、`cd` の成功を確認しない場合は、バックアップファイルを介した別の情報漏えいが起こる可能性があります。低権限ユーザーが `INPUT_DIR` を削除または置き換えられると、`cd` が失敗してもシェルが以前のディレクトリにとどまり、後続の archive コマンドがそのディレクトリを読み込む可能性があります。ジョブの初期作業ディレクトリ、実際に `cd` が失敗する経路、スクリプトが終了するか `&&` を使うか、正確な archiver オプション、出力 archive が低権限ユーザーに読み取り可能かを確認してください。書き込み可能な入力ディレクトリや読み取り可能な archive だけなら、手がかりにすぎません。実行中のジョブを変更せず、ヘルパーとパス権限を確認してください。

スケジュール済み実行ファイルはシェルスクリプトを隠していることがありますが、信頼境界がなくなるわけではありません。[SHc](https://github.com/neurobin/shc) は暗号化されたスクリプトテキストを native binary に埋め込み、実行時にシェルを通じて実行します。`.sh.x` という拡張子や内容が不透明な ELF は、確認の手がかりにすぎません。ファイル名によるオプションインジェクションを評価するには、特権 scheduler の実行ユーザー、ヘルパーの実際の作業ディレクトリとコマンド、低権限ユーザーがその場所に一致する名前を作成できるか、引用符で囲まない glob がオプション境界なしに `rsync` などのコマンドへ渡るかを確認してください。[`rsync` の remote-shell オプション](../interesting-files-permissions/wildcards-spare-tricks.md#rsync)が関係するのは、その正確なコマンド経路が使われる場合に限られます。`/proc` の可視性が制限されていたり、静的な復号に失敗したりしても、コマンドは不明のままです。分類だけを目的に特権ヘルパーを実行しないでください。

プロセスのコマンドライン文字列も、特権ヘルパーに渡される信頼できない入力です。低権限ユーザーは、`pgrep -f` に一致するプロセスタイトルや `argv[0]` を選べます。一致する名前は、実行ファイルやその所有者を認証するものではありません。root で動くスクリプトがその文字列を取得し、一部を書き換えて `apache2ctl`/`httpd` に渡し、固定の引数配列を使わずに実行する場合、攻撃者が選んだオプションで別の設定ディレクトリや error log を指定できる可能性があります。Apache の設定解析は module を読み込んだり、設定された helper に到達したりする場合があるため、列挙中に信頼できない設定を root で検証しないでください。scheduler の所有者、正確なヘルパー、プロセスの実行ユーザー、データから引数へのフローを確認してください。これは、シェルメタ文字による実行が別途示されない限り、オプション/設定インジェクションです。

root で動く parser が、信頼できないテキストを Bash の算術式に渡すと、そのテキスト内の substitution が実行される可能性があります。[権限昇格ガイド](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers)に具体例があります。すべての算術式が悪用可能と判断する前に、入力元と解析コマンドを確認してください。

アプリケーションログを解析する特権ジョブでは、最初の解析より先にある処理も追跡してください。低権限アカウントが現在のプロセスグループを通じてログを書き込めたり、記録されるリクエストフィールドに影響を与えたりする場合があります。そのレコードが画像を選択し、画像の metadata が XML を開くための2つ目のパス名になることがあります。ジョブの有効な実行ユーザー、実際のログ書き込み権限、区切り文字の処理、正規化されたパスによる containment、選択された XML が攻撃者に制御可能かを確認してください。外部 entity の展開結果が低権限ユーザーに読み取り可能な出力に到達すると、その2つ目の読み取りによって特権ファイルが漏えいする可能性があります。[Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html)では、外部 DTD/entity アクセスの制御について説明しています。インストール済み parser と有効な設定を確認してください。書き込み可能なログや XML ファイルだけなら、手がかりにすぎません。列挙中にスケジュール済み parser に入力を与えず、コードとメタデータを確認してください。

別ユーザーの Git repository からファイルを生成する特権ジョブも確認してください。スクリプトが `git checkout` の代わりに `git ls-tree` と `git cat-file` を使っていても、tree に含まれる攻撃者制御のパスを staging directory に結合する際に信頼していることがあります。書き込み前に宛先を正規化して containment を確認しなければ、絶対パスや `..` 要素によってそのディレクトリの外に書き込めます。`git -c safe.directory=*` は、所有者が異なる repository へのアクセスを許可しますが、それだけで任意ファイル書き込みが成立するわけではありません。

root で動くデータベースバックアップは、別の所有権境界を作ることがあります。PostgreSQL の [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) は、ソースのデータディレクトリに置かれた追加の通常ファイルもコピーします。また、デフォルトの plain format では、`-D` にディレクトリツリーとしてファイルを書き込みます。低権限アカウントがそのソースファイルを作成または変更できる場合は、出力先の所有者と mode、そのパスが traverse および実行可能か、マウントに `nosuid` が指定されているかを確認してください。set-ID 権限を保持した root 所有のコピーは危険な場合があります。tar のみのバックアップ、権限の除去、アクセス不能な出力先では、同じ経路は成立しません。バックアップコマンドを問題と判断する前に、スケジュール済みラッパーと有効な実行ユーザーを追跡してください。

## 短時間で終了する処理を観察する

単一のプロセススナップショットでは、数ミリ秒で実行されるジョブを見逃す可能性があります。timer/cron の宣言をログと照合し、認可されている場合は `pspy` や audit などでプロセスイベントを監視してください。スケジュールの所有者、正確なコマンドライン、タスクが読み書きするファイルを照合します。loopback の scheduler Web UI は別のインターフェースです。[Crontab UI の例](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc)を参照してください。
