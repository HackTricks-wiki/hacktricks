# Tareas cron y temporizadores de systemd

{{#include ../../banners/hacktricks-training.md}}

Las tareas programadas pueden ejecutarse con una identidad y un entorno distintos de los del shell actual. Enumera cron, `at`, anacron y los temporizadores de systemd; después, rastrea cada comando programado a través de sus scripts, imports, directorio de trabajo y entradas modificables.

## Enumerar tareas programadas

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Los crontabs del sistema suelen incluir un campo de usuario; el crontab de un usuario, no. Inspecciona el PATH y el entorno efectivos del scheduler real. `run-parts --test /etc/cron.daily` muestra qué nombres de archivo se seleccionarían en ese host. Los caracteres de control pueden ocultar una entrada en una salida casual, así que usa `cat -A` o `sed -n l` cuando un horario parezca sospechoso.

## Rastrea la resolución de archivos y comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revisa las cadenas de scripts con permisos de escritura, las rutas de `EnvironmentFile=`, los drop-ins, los symlinks, los comandos relativos, la expansión de comodines y los binarios copiados o ejecutados por una tarea privilegiada. Un timer puede activar un servicio con otro nombre mediante su ajuste `Unit=`. Las páginas sobre [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) y [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explican los principales mecanismos.

Para un script programado de `chkrootkit` ejecutado como root, inspecciona el código fuente instalado para buscar el antiguo [fallo de comillas en slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): una asignación sin comillas `file_port=$file_port $i` después de comprobar una ruta temporal de `SLAPPER_FILES` puede ejecutar ese archivo. Verifica el script real o el parche del proveedor, la programación como root, el acceso de escritura de un usuario con menos privilegios a la ruta temporal exacta, si el archivo es ejecutable y la política de montaje. Una cadena de versión o la mera presencia de `chkrootkit` no demuestra que la ruta exista; no crees ni ejecutes un archivo temporal durante una revisión pasiva.

Si un servicio de root activado por un timer ejecuta `systemctl restart <other>.service`, sigue un salto más entre units: la unit reiniciada puede invocar un shell con un script modificable por un usuario con menos privilegios. Confirma el `User=` efectivo, `DynamicUser=`, `RootDirectory=`/`RootImage=`, los argumentos exactos de `ExecStart=` y los permisos del script y de su ruta padre. Un script modificable solo es un posible vector hasta que el timer y el servicio reiniciado están activos en ese contexto de ejecución; inspecciona las propiedades de las units sin reiniciar ninguno de los servicios.

Si un trabajo con más privilegios descarga un script por hostname y pasa la respuesta a un shell, comprueba quién controla la resolución de ese hostname, además del script remoto. Un archivo `/etc/hosts` modificable, incluso mediante permisos de grupo o ACL, puede redirigir un nombre que el trabajo resuelve localmente; una respuesta de `curl` solo se convierte en una ruta de ejecución entre usuarios cuando el comando programado realmente ejecuta esa respuesta y el trabajo usa la ruta de resolución afectada. Verifica la identidad con la que se ejecuta el trabajo, la URL y la canalización de shell exactas, el comportamiento efectivo de proxy/DNS y los permisos del archivo y de su directorio padre. Un archivo hosts modificable por sí solo es una señal para revisar, no una prueba de que exista un consumidor privilegiado. Inspecciona la programación y los metadatos sin cambiar la asignación ni descargar el script durante el reconocimiento.

Una descarga de `wget` privilegiada y programada es un límite independiente de escritura de archivos, aunque el cuerpo descargado nunca se ejecute directamente. [GNU Wget 1.18 cambió el comportamiento predeterminado del nombre de archivo en redirecciones HTTP a FTP para corregir CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); las versiones antiguas afectadas podían usar el nombre de archivo de la redirección FTP, mientras que `--trust-server-names` solicita ese comportamiento explícitamente. Si una parte de menor confianza controla la respuesta HTTP y el recurso FTP, inspecciona si el trabajo sigue esa redirección, la versión real de Wget o el backport del proveedor, las opciones de salida, la identidad de ejecución, el directorio de trabajo y si el nombre de destino puede convertirse en un archivo de inicio. [Wget carga `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), y [sus ajustes pueden seleccionar una fuente POST o una ruta de salida](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); una descarga privilegiada posterior es un requisito independiente para cualquier divulgación o escritura resultante. El acceso a un puerto bajo mediante `authbind` solo es relevante si quien lo invoca puede servir la URL que solicita el trabajo. Revisa la configuración y los logs de forma pasiva, sin servir una redirección ni ejecutar el trabajo. El [acceso a dispositivos de bloque sin procesar mediante el grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) es independiente de esta ruta de descarga de red.

Sigue también los archivos de datos, no solo los scripts. Una herramienta de simulación u orquestación programada puede leer un archivo YAML que define procesos que iniciar; si un usuario con menos privilegios puede editar ese archivo y el trabajo lo ejecuta con otra cuenta, los datos pueden convertirse en comandos ejecutados con la identidad del trabajo. Verifica el comando programado exacto, el usuario efectivo, la ruta del archivo, la semántica del parser y los permisos de escritura (incluidos los de los directorios padre) antes de considerar un YAML modificable como una ruta de ejecución. Para el triage pasivo basta con leer la programación y los metadatos del archivo; no ejecutes el trabajo ni modifiques su entrada durante el reconocimiento.

La configuración de un cliente SSH también es una entrada ejecutable cuando un trabajo con más privilegios ejecuta `ssh -F` con un archivo que un usuario con menos privilegios puede reemplazar. OpenSSH ejecuta [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) mediante el shell local del cliente, mientras que `Host`/`Match` y las opciones anteriores determinan si se aplica esa directiva. Correlaciona la invocación SSH programada exacta, la identidad de ejecución, la ruta de configuración seleccionada, los permisos de escritura del directorio y del archivo, y el orden efectivo de las opciones antes de considerarlo una ruta de ejecución entre usuarios. Revisa estos registros sin ejecutar el trabajo ni cargar la configuración no confiable como la cuenta privilegiada.

Un `scp` programado seguido de `ssh` para ejecutar el script copiado requiere revisar un segundo límite de confianza cuando un usuario con menos privilegios controla el servicio SSH de destino. Si ese servicio puede reenviar la conexión a otro host, el cliente privilegiado podría autenticarse en un endpoint no previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) debilita la protección frente a cambios de clave de host, sujeto a las restricciones restantes de OpenSSH y a las opciones efectivas para cada host. Determina la identidad de ejecución del trabajo, el destino y el método de autenticación reales, la identidad efectiva del comando remoto y si la misma ruta de destino existe previamente o admite escritura en el host redirigido. La ejecución de un archivo antiguo o controlado por un atacante también requiere que la copia falle o no encuentre esa ruta **y** que el wrapper continúe con el comando SSH; [Bash `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) y el manejo explícito del estado de salida afectan ese flujo. Una configuración débil de la clave de host, un proceso `sshpass` visible o un directorio temporal modificable no demuestran por sí solos esta cadena. Inspecciona la programación, el script, la configuración SSH y los metadatos de los archivos sin redirigir el servicio ni activar el trabajo durante el reconocimiento.

Un programador de aplicaciones privilegiado puede obtener sus trabajos de filas de una base de datos en lugar de archivos modificables. Por ejemplo, una entrada de cron de root que invoque [`php artisan schedule:run` de Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) puede llegar a código de la aplicación que lee filas de tareas. Si una cuenta con menos privilegios puede escribir una fila que contenga una ruta local, y la callback programada llama a [`file_get_contents` de PHP](https://www.php.net/manual/en/function.file-get-contents.php) como root y envía el cuerpo devuelto a un webhook indicado por la fila, existe una ruta de divulgación de archivos privilegiada. Verifica la identidad de cron, la callback real del scheduler y el flujo de datos de la fila a la ruta, los permisos de escritura en la base de datos, la validación posterior a la lectura de la fila y el destino de salida. Un `.env` de la aplicación legible solo da una pista sobre credenciales; la validación de un formulario web o una contraseña de base de datos no demuestra por sí sola que se puedan controlar las filas ni divulgar datos. Inspecciona la programación, el código y los permisos de los archivos de credenciales de forma pasiva, sin consultar la base de datos ni programar una tarea durante el reconocimiento.

Los trabajos de `incron` activados por eventos requieren la misma revisión: las [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) asocian una ruta observada y un evento con un comando ejecutado con la identidad del propietario de la tabla. Un usuario con menos privilegios puede influir indirectamente en un archivo observado si una aplicación sigue un enlace desde un directorio modificable y escribe texto controlado por un atacante en el destino observado. Verifica el propietario real de la tabla, el evento, los permisos del destino y de sus directorios antecesores, el comportamiento de la aplicación al seguir enlaces y cómo ese texto se convierte en argumentos de comando. En concreto, [`mail` de GNU Mailutils acepta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), y su [comando de escape al shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) puede ejecutar un programa; un campo no confiable pasado como opción independiente a esa implementación puede llegar a la ejecución de comandos. Otras implementaciones de `mail` o un límite de argumentos entre comillas y fijo pueden comportarse de forma distinta. Inspecciona la programación, el código de la aplicación y los metadatos de los archivos sin modificar el archivo observado ni activar el trabajo durante el reconocimiento.

Un log observado también puede cruzar el límite entre usuarios mediante un script auxiliar. Si una cuenta con menos privilegios puede escribir en el log y el propietario de `incron` lee un campo y lo inserta en una nueva cadena de comando [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), el shell vuelve a analizar ese campo con la identidad del propietario. Comprueba el evento observado exacto, los permisos del log y de sus directorios padre, la ruta del helper, la transformación del campo del log y si se llega a ejecutar el comando resultante. Ver un log modificable y una entrada de `incron` no demuestra por sí solo el flujo de datos; no escribas una línea de activación ni ejecutes el helper durante el reconocimiento pasivo.

Los trabajos de renovación de certificados pueden cruzar el mismo límite. Un helper privilegiado puede leer el subject X.509 de un certificado ubicado en un directorio modificable por un usuario con menos privilegios e insertar su common name en una nueva cadena de comando `bash -c`. [OpenSSL puede mostrar el subject de un certificado y comprobar su caducidad](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analiza la cadena `-c` como entrada de shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), por lo que entrecomillar la variable en el script externo no protege del segundo análisis. Confirma la identidad programada, la ruta exacta de entrada y sus permisos de escritura, la rama de renovación y el flujo de datos hacia `bash -c` antes de considerarlo una inyección de comandos. Inspecciona el script y los metadatos del certificado de forma pasiva; no actives la renovación durante el reconocimiento.

El mismo segundo análisis puede ocurrir cuando un trabajo privilegiado programado extrae un nombre de un archivo o paquete de un usuario con menos privilegios y lo pasa a `xargs -I` para insertarlo en una cadena de comando `sh -c`. [`xargs -I` de GNU reemplaza el marcador en los argumentos iniciales](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), y [`sh -c` interpreta su cadena de comando](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Aunque el script externo entrecomille el nombre extraído, eso no vuelve seguro un programa de shell sustituido posteriormente. Verifica la identidad de ejecución del trabajo, la ruta de entrada aceptada y sus permisos de escritura, la validación del archivo y las condiciones de la rama, y el flujo del nombre al shell. Un directorio de carga modificable o una invocación de `xargs` son solo pistas; inspecciona la programación, el script y los metadatos de la ruta sin enviar un paquete ni ejecutar el trabajo durante el reconocimiento.

Un importador programado de fuentes o imágenes también puede confiar en los nombres *dentro* de un archivo proporcionado por quien lo sube, aunque se restrinja el nombre externo del archivo. FontForge corrigió la inyección de comandos mediante nombres de miembros del archivo en su [cambio upstream para CVE-2024-25081 y CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirma que un trabajo con más privilegios realmente abre un archivo desde una ruta modificable por un usuario con menos privilegios, su identidad de ejecución, la versión exacta de FontForge o el backport del proveedor y la ruta de manejo del archivo. Una cadena de versión o una extensión de carga permitida no prueban por sí solas que se ejecute el archivo. Inspecciona la programación, los permisos de la ruta y los metadatos de la versión sin importar un archivo no confiable durante el reconocimiento.

Los scanners de red programados pueden cruzar otro límite cuando un script personalizado trata el subject de un certificado TLS remoto como un nombre de archivo local. [Nmap NSE ejecuta los scripts seleccionados sin sandbox](https://nmap.org/book/nse-usage.html), así que inspecciona el script real y comprueba si concatena un campo subject no confiable a un directorio de datos sin verificar que la ruta permanezca dentro de él. Para divulgar un archivo, el scheduler debe escanear un objetivo, la ruta debe resolverse a un archivo legible por la identidad de ejecución del scanner y el informe o log debe llegar a un lector con menos privilegios. Un campo de certificado o la presencia de un scanner no prueban por sí solos esa cadena; revisa la programación, el script, la resolución de la ruta y el destino del informe sin escanear un objetivo nuevo durante el reconocimiento pasivo.

Un comando de cron privilegiado que pasa un glob de shell como `/path/to/tasks/*.yml` a un runner de Ansible requiere revisar los permisos del directorio, aunque todos los playbooks existentes sean de solo lectura. Un usuario con permisos de escritura y búsqueda en el directorio al que se aplica el glob puede crear otro playbook coincidente. [Los playbooks de Ansible definen tareas que ejecuta el runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), pero un wrapper personalizado puede filtrar rutas o usar otra identidad: verifica su comportamiento, el usuario real de cron, la expansión del shell, las ACL, el sticky bit y la política de montaje antes de considerar el directorio una ruta de ejecución. Inspecciona los metadatos y el wrapper de forma estática; no ejecutes el trabajo programado durante el reconocimiento.

Un wrapper de cron privilegiado puede pasar nombres de archivo de un directorio de carga a un helper de Perl después de expandir un glob. El operador [`<>` de Perl usa `open` con dos argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), por lo que un nombre coincidente interpretado como un comando de tubería puede ejecutarse con la identidad del helper; [`<<>>` trata los argumentos como nombres de archivo literales](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirma la identidad del scheduler, el directorio de trabajo y el glob del wrapper, cómo maneja realmente `@ARGV` el helper, las restricciones de nombres de archivo y si una identidad con menos privilegios puede colocar un nombre coincidente mediante permisos del sistema de archivos o un servicio de carga autenticado. Una línea de cron, un script de Perl o un directorio FTP modificable no demuestran por sí solos toda la cadena. Inspecciona el código fuente y los metadatos sin enviar un nombre de archivo preparado ni ejecutar el trabajo durante el reconocimiento.

Un script de cron de solo lectura aún puede reemplazarse si la cuenta programada lo ejecuta por ruta y un usuario con menos privilegios puede escribir y atravesar su directorio padre sin sticky bit. Comprueba la identidad de ejecución de la programación, cada componente de la ruta, el sticky bit del directorio, las ACL y la política de montaje; revisa los metadatos sin mover el archivo ni ejecutar el trabajo.

Un wrapper de cron privilegiado en PHP puede llegar a un helper que aún no existe. Si llama a [`exec()` de PHP](https://www.php.net/manual/en/function.exec.php) con una ruta absoluta fija al helper, un usuario con menos privilegios que pueda crear ese nombre en el directorio padre puede controlar lo que ejecutará una ejecución posterior. Confirma que la entrada de cron realmente ejecuta el wrapper con la identidad de más privilegios, la cadena de comando exacta y la política de ejecución de PHP, los permisos de escritura y búsqueda del directorio del helper, el comportamiento de symlinks y sticky bit, y si la ruta del helper sigue ausente. Un directorio modificable o un helper inexistente son solo pistas; inspecciona la programación, el código fuente y los metadatos de la ruta sin crear el helper ni activar el trabajo.

Un trabajo programado también puede descubrir scripts de entrada con `find` y pasarlos a un intérprete. Por ejemplo, la función `system()` de [gnuplot invoca un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), así que un trabajo privilegiado que ejecute `gnuplot` con todos los archivos `*.plt` de un directorio modificable por un usuario con menos privilegios puede ejecutar comandos con la identidad del trabajo. [El permiso de lectura del directorio controla su listado, mientras que los permisos de escritura y búsqueda (`x`) controlan la creación y el acceso a nombres conocidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); comprueba el acceso de escritura y búsqueda aunque `ls` no pueda listar el directorio. Correlaciona la identidad y el comando exactos del scheduler, el comportamiento del intérprete, el patrón de archivos seleccionado y los permisos del directorio; un directorio modificable o la presencia de un intérprete no demuestran por sí solos una escalada. Las programaciones privadas y los trabajos de corta duración pueden requerir observación autorizada de eventos, ya que una única instantánea de procesos puede no detectarlos.

Para un trabajo PHP privilegiado, inspecciona las instrucciones literales `include`/`require` como parte de la cadena de scripts ejecutables. [PHP evalúa los archivos incluidos](https://www.php.net/manual/en/function.include.php), por lo que un archivo `.php` modificable por el grupo puede ejecutar código con la identidad del trabajo aunque el script principal sea de solo lectura. Verifica la identidad programada, la resolución efectiva de la ruta de inclusión, los permisos del archivo y del directorio, y si el trabajo realmente se ejecuta; una línea de cron de ejemplo en un comentario es solo una pista. La misma revisión se aplica a un [servidor integrado de PHP](https://www.php.net/commandline.webserver) propiedad de root, iniciado con `-S` y `-t <document-root>`: un listener de loopback aún puede ejecutar PHP de la aplicación para solicitudes locales. Inspecciona el proceso y el código fuente sin activar ninguno de los dos mecanismos durante el reconocimiento.

Un trabajo PHP privilegiado también puede cruzar el límite mediante un **archivo de datos**: si un usuario con menos privilegios puede cambiar el archivo exacto pasado a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP podría invocar el método `__wakeup()` o `__unserialize()` de una clase cargada al restaurar un objeto. Revisa la identidad efectiva del trabajo, los permisos del archivo y de sus directorios antecesores, las clases cargadas y los efectos secundarios reales del método, como una escritura de archivo seleccionada por una propiedad. Un log modificable o una llamada a `unserialize()` no demuestran por sí solos que exista una ruta viable. Inspecciona el código fuente y los metadatos sin escribir datos serializados ni ejecutar el trabajo durante el reconocimiento.

Una tarea de cron de root puede invocar el **runner de páginas CLI** de una aplicación PHP en lugar del servidor web. Sigue el document root y el URI seleccionados por el runner hasta el punto de entrada PHP real; si la cuenta del servicio web puede modificar ese punto de entrada, la solicitud CLI programada puede ejecutar el código modificado como root aunque el runner y el wrapper de cron sean de solo lectura. Confirma la identidad del scheduler, la resolución exacta del URI al archivo, los permisos efectivos del archivo y de sus directorios antecesores, y si un control de integridad protege el punto de entrada. Inspecciona el código fuente y los metadatos sin invocar el runner ni cambiar la página durante el reconocimiento.

Un proceso `ipython` iniciado por un trabajo programado o por otro usuario desde un directorio de trabajo compartido requiere revisar sus archivos de inicio. Las [notas de seguridad de IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explican que las versiones afectadas buscaban perfiles y configuración en el directorio actual, incluido el código de `profile_default/startup`, antes de la corrección de CVE-2022-21699. Correlaciona la versión instalada real o el parche del proveedor, el directorio de trabajo del comando, la identidad del proceso con más privilegios y la capacidad del usuario con menos privilegios para escribir y buscar en la ruta de inicio exacta. La presencia de `ipython`, un directorio modificable o una cadena de versión no demuestran por sí solos que otra identidad vaya a cargar un archivo desde allí. Inspecciona la programación y los metadatos de la ruta sin iniciar el intérprete con más privilegios.

Para un servidor PHP privilegiado que llama funciones de una extensión nativa personalizada, identifica el SAPI de PHP del servicio y su `php.ini` efectivo, además de los archivos `.ini` explorados, antes de revisar la extensión. [PHP carga las bibliotecas `extension` configuradas al inicio](https://www.php.net/manual/en/ini.core.php), y [los SAPI CLI y web pueden usar archivos de configuración distintos](https://www.php.net/manual/en/configuration.file.php). Por tanto, un formulario de inicio de sesión accesible o un listener local puede pasar cadenas controladas por el usuario a código compilado que se ejecuta con la identidad del servicio. Registra `User=`, `ExecStart=`, el directorio de trabajo, la ruta real de la extensión y los argumentos controlables por quien realiza la solicitud; la mera presencia de un `.so` o un socket de loopback no demuestra una vulnerabilidad de corrupción de memoria. Analiza cualquier parser personalizado por separado, sin enviar pruebas durante el reconocimiento pasivo.

Cuando un wrapper privilegiado calcula el hash de un script mediante su ruta y luego vuelve a abrir esa ruta para ejecutarlo, el digest solo autentica el objeto leído en la primera apertura. Si un usuario con menos privilegios puede reemplazar la entrada del directorio del script entre ambas aperturas, la ejecución posterior puede resolver un objeto distinto aunque el archivo original pertenezca a root. Una FIFO puede alargar la fase de comprobación, pero la ruta depende de que se puedan reemplazar las entradas de los directorios padre, de que realmente se hagan aperturas separadas, de la identidad del scheduler, de las reglas del sticky bit y del montaje, y de la temporización. Inspecciona el wrapper y la salida de `namei -l` como una pista pasiva; que la suma de comprobación sea correcta no demuestra que la ruta posterior esté protegida.

Un trabajo de copia de seguridad privilegiado también puede **divulgar** datos sin ejecutar comandos proporcionados por un atacante. Averigua si un usuario con menos privilegios puede crear un archivo de control que el trabajo lea, si después el trabajo abre una fuente protegida como `/etc/shadow` y si un URL seleccionado por el atacante o una salida legible recibe el resultado. Verifica los tres elementos antes de considerarlo una ruta de divulgación. Un comando de shell fijo en el mismo script no convierte por sí solo ese archivo de control en una entrada de inyección de shell. Inspecciona el script y los permisos de los archivos sin ejecutar el trabajo ni colocar un archivo de control durante el reconocimiento.

Si un trabajo privilegiado programado ejecuta `curl -K FILE` o `curl --config FILE`, [curl trata las opciones de ese archivo como argumentos de línea de comandos](https://curl.se/docs/manpage.html). Un usuario con menos privilegios que controle el archivo exacto cuando curl lo lea puede influir en la URL solicitada, la entrada de archivos locales o la ruta de salida. Confirma la identidad efectiva del trabajo, los permisos de escritura del archivo y de sus directorios antecesores, el momento en que cualquier otro trabajo reemplaza el archivo y cómo interactúan las opciones de configuración con las opciones fijas de la línea de comandos antes de afirmar que puede producirse una lectura o escritura protegida. Una ruta de configuración modificable o una opción `-K` visible no demuestran por sí solas que las opciones elegidas surtan efecto; inspecciona la programación y los metadatos sin ejecutar el trabajo ni descargar una URL durante el reconocimiento pasivo.

Si una entrada de cron invoca un script helper, inspecciona también su directorio de trabajo y el comando de archivo. Un comodín sin comillas sobre un directorio modificable por otro usuario puede convertir los nombres de archivo en opciones del archivador; las acciones de checkpoint de GNU tar son un ejemplo. Confirma la identidad de ejecución programada, el directorio de entrada modificable, el archivador y las opciones exactos, y si `--` detiene el análisis de opciones antes de afirmar que existe una ruta de comandos entre usuarios. Consulta [el comportamiento de wildcard y tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Puede producirse una divulgación distinta de archivos de copia de seguridad cuando un helper privilegiado ejecuta `cd INPUT_DIR; tar ... *` sin comprobar si `cd` tuvo éxito. Si un usuario con menos privilegios puede eliminar o reemplazar `INPUT_DIR`, un `cd` fallido puede dejar el shell en el directorio anterior, que el comando de archivo posterior podría leer. Verifica el directorio de trabajo inicial del trabajo, una ruta real de `cd` fallido, si el script termina o usa `&&`, las opciones exactas del archivador y si el usuario con menos privilegios puede leer el archivo de salida. Un directorio de entrada modificable o un archivo de salida legible son solo pistas; inspecciona el helper y los permisos de la ruta sin cambiar el trabajo activo.

Un ejecutable programado puede ocultar un script de shell en lugar de eliminar su límite de confianza: [SHc](https://github.com/neurobin/shc) incluye texto de script cifrado en un binario nativo y lo ejecuta mediante un shell en tiempo de ejecución. El sufijo `.sh.x` o un ELF opaco son solo pistas para revisar. Para evaluar una inyección de opciones mediante nombres de archivo, determina la identidad del scheduler privilegiado, el directorio de trabajo y el comando reales del helper, si un usuario con menos privilegios puede crear allí nombres coincidentes y si un glob sin comillas llega a un comando como `rsync` sin un límite de opciones. La [`opción de shell remoto de `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) solo es relevante si se usa esa ruta de comando exacta. La visibilidad restringida de `/proc` o el fallo al descifrar estáticamente dejan el comando en desconocido; no ejecutes el helper privilegiado solo para clasificarlo.

El texto de la línea de comandos de un proceso es otra entrada no confiable para un helper privilegiado. Un usuario con menos privilegios puede elegir un título de proceso o `argv[0]` que coincida con `pgrep -f`; un nombre coincidente no autentica el ejecutable ni a su propietario. Si un script ejecutado como root captura ese texto, reescribe parte de él como `apache2ctl`/`httpd` y ejecuta el resultado sin una matriz de argumentos fija, las opciones elegidas por el atacante pueden seleccionar otro directorio de configuración o log de errores. El análisis de configuración de Apache puede cargar módulos o acceder a helpers configurados, así que no valides una configuración no confiable como root durante el reconocimiento. Inspecciona el propietario del scheduler, el helper exacto, la identidad del proceso y el flujo de datos a los argumentos; esto es una inyección de opciones/configuración, salvo que se demuestre por separado la ejecución de metacaracteres del shell.

Un parser ejecutado como root que introduce texto no confiable en aritmética de Bash puede ejecutar sustituciones presentes en ese texto. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) ofrece un ejemplo detallado. Confirma la fuente de entrada y el comando de análisis antes de considerar explotable cualquier expresión aritmética.

Para un trabajo privilegiado que analiza un log de aplicación, sigue los campos no confiables más allá del primer análisis. Una cuenta con menos privilegios puede tener la capacidad de escribir en el log mediante su grupo de proceso actual o influir en los campos de solicitudes registrados; un registro puede seleccionar una imagen cuyos metadatos se convierten en una segunda ruta usada para abrir XML. Comprueba la identidad efectiva del trabajo, el acceso real de escritura al log, el manejo de delimitadores, la contención de rutas canónicas y si el XML seleccionado está bajo control del atacante. La expansión de entidades externas puede convertir esa segunda lectura en una divulgación privilegiada de archivos si el resultado expandido llega a una salida legible por un usuario con menos privilegios. La [guía de seguridad de procesamiento XML de Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para el acceso a DTD/entidades externas; inspecciona el parser instalado y sus ajustes efectivos. Un log o archivo XML modificable por sí solo es solo una pista. Revisa el código y los metadatos sin proporcionar datos al parser programado durante el reconocimiento.

Inspecciona también los trabajos privilegiados que materializan archivos desde el repositorio Git de otro usuario. Un script puede usar `git ls-tree` y `git cat-file` en lugar de `git checkout`, pero aun así confiar en rutas del árbol controladas por un atacante al concatenarlas con un directorio de preparación. Las rutas absolutas y los componentes `..` pueden escapar de ese directorio, salvo que se normalice el destino y se compruebe que sigue dentro del directorio antes de escribir. `git -c safe.directory=*` permite acceder a repositorios con propietarios distintos; no crea por sí solo la posibilidad de escritura arbitraria.

Una copia de seguridad de una base de datos ejecutada como root puede crear otro límite de propiedad. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia archivos regulares adicionales ubicados en el directorio de datos de origen, y su formato plano predeterminado escribe los archivos en `-D` como un árbol de directorios. Si una cuenta con menos privilegios puede crear o modificar esos archivos de origen, inspecciona la propiedad y el modo del destino resultante, si se puede atravesar y ejecutar desde su ruta y si el montaje tiene `nosuid`. Una copia propiedad de root con permisos set-ID preservados puede ser peligrosa; una copia solo en formato tar, permisos eliminados o un destino inaccesible no establece la misma ruta. Sigue el wrapper programado y el usuario efectivo antes de tratar el comando de copia de seguridad como un hallazgo.

## Observar trabajos de corta duración

Una sola instantánea de procesos puede pasar por alto un trabajo que solo se ejecuta durante milisegundos. Compara las declaraciones de timer/cron con los logs y, cuando esté autorizado, con la monitorización de eventos de procesos, como `pspy` o audit. Correlaciona el propietario programado, la línea de comandos exacta y los archivos que la tarea lee o escribe. Una interfaz web de scheduler disponible en loopback es una interfaz aparte; consulta el [ejemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
