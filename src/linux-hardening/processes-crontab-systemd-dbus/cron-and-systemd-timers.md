# Tâches cron et timers systemd

{{#include ../../banners/hacktricks-training.md}}

Les tâches planifiées peuvent s’exécuter avec une identité et un environnement différents de ceux du shell actuel. Énumérez les tâches cron, `at`, anacron et les timers systemd, puis remontez chaque commande planifiée jusqu’à ses scripts, ses imports, son répertoire de travail et ses entrées modifiables.

## Énumérer les tâches planifiées

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Les crontabs système incluent généralement un champ utilisateur ; ceux des utilisateurs n’en ont pas. Inspectez le PATH et l’environnement effectifs de l’ordonnanceur réel. `run-parts --test /etc/cron.daily` indique quels noms de fichiers seraient sélectionnés sur cet hôte. Les caractères de contrôle peuvent masquer une entrée dans une sortie ordinaire : utilisez `cat -A` ou `sed -n l` si une planification semble suspecte.

## Suivre la résolution des fichiers et des commandes privilégiés

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Examinez les chaînes de scripts modifiables, les chemins `EnvironmentFile=`, les drop-ins, les liens symboliques, les commandes relatives, l'expansion des jokers et les binaires copiés ou exécutés par une tâche privilégiée. Un timer peut activer un service portant un autre nom via son paramètre `Unit=`. Les pages [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) et [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) expliquent les primitives principales.

Pour un script `chkrootkit` exécuté par root de façon planifiée, examinez le code source installé pour détecter l'ancien [défaut de guillemets dans slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) : un `file_port=$file_port $i` sans guillemets après la vérification d'un chemin temporaire `SLAPPER_FILES` peut exécuter ce fichier. Vérifiez le script réel ou le correctif du fournisseur, la planification par root, les droits d'écriture d'un utilisateur moins privilégié sur le chemin temporaire exact, son statut exécutable et la politique de montage. Une chaîne de version ou la seule présence de `chkrootkit` ne suffit pas à établir l'existence de cette voie ; ne créez et n'exécutez pas de fichier temporaire lors d'une revue passive.

Suivez encore un saut d'unité lorsqu'un service root déclenché par un timer exécute `systemctl restart <other>.service` : l'unité redémarrée peut appeler un shell avec un script modifiable par un utilisateur moins privilégié. Confirmez le `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, les arguments exacts de `ExecStart=` et les permissions du script et de son répertoire parent. Un script modifiable n'est qu'un candidat tant que le timer et le service redémarré ne sont pas actifs dans ce contexte d'exécution ; inspectez les propriétés des unités sans redémarrer aucun des deux services.

Si une tâche exécutée avec des privilèges supérieurs récupère un script par son nom d'hôte et transmet la réponse à un shell, vérifiez qui contrôle la résolution de ce nom d'hôte, ainsi que le script distant. Un fichier `/etc/hosts` modifiable, y compris via les droits d'un groupe ou une ACL, peut rediriger un nom que la tâche résout localement ; une réponse `curl` ne devient une voie d'exécution entre utilisateurs que si la commande planifiée exécute réellement cette réponse et que la tâche utilise le chemin de résolution concerné. Vérifiez l'identité d'exécution de la tâche, l'URL exacte et le pipeline shell, le comportement effectif du proxy/DNS, ainsi que les permissions du fichier et de son répertoire parent. Un fichier hosts modifiable est à examiner, mais ne prouve pas à lui seul l'existence d'un consommateur privilégié. Inspectez la planification et les métadonnées sans modifier la correspondance ni récupérer le script pendant l'énumération.

Un téléchargement `wget` planifié avec des privilèges élevés constitue une frontière d'écriture distincte, même si le corps téléchargé n'est jamais exécuté directement. [GNU Wget 1.18 a modifié la gestion par défaut du nom de fichier lors des redirections HTTP vers FTP afin de corriger CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html) ; les anciennes versions concernées pouvaient utiliser le nom de fichier de la redirection FTP, tandis que `--trust-server-names` demande explicitement ce comportement. Si une partie moins fiable contrôle la réponse HTTP et la ressource FTP, vérifiez si la tâche suit cette redirection, la version réelle de Wget ou le rétroportage du fournisseur, les options de sortie, l'identité d'exécution, le répertoire de travail et si le nom de fichier de destination peut devenir un fichier de démarrage. [Wget charge `WGETRC` ou `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), et [ses paramètres peuvent choisir une source POST ou un chemin de sortie](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html) ; un téléchargement ultérieur avec des privilèges élevés est une condition préalable distincte à toute divulgation ou écriture qui en résulterait. L'accès à un port bas via `authbind` n'est pertinent que si l'appelant peut réellement servir l'URL demandée par la tâche. Examinez la configuration et les journaux passivement, sans servir de redirection ni exécuter la tâche. [L'accès brut aux périphériques bloc via le groupe `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) est indépendant de cette voie de téléchargement réseau.

Suivez aussi les fichiers de données, pas seulement les scripts. Un outil de simulation ou d'orchestration planifié peut lire un fichier YAML qui définit les processus à démarrer ; si un utilisateur moins privilégié peut modifier ce fichier et que la tâche l'exécute sous un autre compte, ces données peuvent devenir des commandes exécutées avec l'identité de la tâche. Vérifiez la commande planifiée exacte, l'utilisateur effectif, le chemin du fichier, la sémantique de l'analyseur et les droits d'écriture, y compris sur les répertoires parents, avant de considérer un fichier YAML modifiable comme une voie d'exécution. La lecture de la planification et des métadonnées du fichier suffit au triage passif ; n'exécutez pas la tâche et ne modifiez pas son entrée pendant l'énumération.

La configuration d'un client SSH est également une entrée exécutable lorsqu'une tâche avec des privilèges supérieurs lance `ssh -F` avec un fichier qu'un utilisateur moins privilégié peut remplacer. Le [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) d'OpenSSH exécute une commande locale via le shell du client, tandis que `Host`/`Match` et les options précédentes déterminent si cette directive s'applique. Recoupez l'invocation SSH planifiée exacte, l'identité d'exécution, le chemin de configuration sélectionné, les droits d'écriture sur le répertoire et le fichier, ainsi que l'ordre effectif des options avant de conclure à une voie d'exécution entre utilisateurs. Examinez ces éléments sans lancer la tâche ni charger la configuration non fiable avec le compte privilégié.

Un `scp` planifié suivi d'un `ssh` qui exécute le script copié nécessite une seconde vérification de la frontière de confiance si un utilisateur moins privilégié contrôle le service SSH de destination. Si ce service peut rediriger la connexion vers un autre hôte, le client privilégié peut s'authentifier auprès d'un point de terminaison imprévu ; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) affaiblit la protection contre les changements de clé d'hôte, sous réserve des autres restrictions d'OpenSSH et des options effectives par hôte. Établissez l'identité d'exécution de la tâche, la destination réelle et la méthode d'authentification, l'identité effective de la commande distante, et si le même chemin de destination est modifiable ou préexistant sur l'hôte redirigé. L'exécution d'un ancien fichier ou d'un fichier contrôlé par un attaquant exige en outre que la copie échoue ou ne trouve pas ce chemin **et** que le wrapper poursuive avec sa commande SSH ; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) et la gestion explicite du statut influent sur ce déroulement. Un paramètre de clé d'hôte faible, un processus `sshpass` visible ou un répertoire temporaire modifiable ne suffisent pas, à eux seuls, à établir cette chaîne. Examinez la planification, le script, la configuration SSH et les métadonnées des fichiers sans rediriger le service ni déclencher la tâche pendant l'énumération.

Un ordonnanceur d'applications privilégié peut tirer ses tâches de lignes de base de données plutôt que de fichiers modifiables. Par exemple, une entrée cron root qui invoque [`php artisan schedule:run` de Laravel](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) peut atteindre du code applicatif qui lit des lignes de tâches. Si un compte moins privilégié peut écrire une ligne contenant un chemin local et que le callback planifié appelle [`file_get_contents` de PHP](https://www.php.net/manual/en/function.file-get-contents.php) sous root, puis envoie le contenu récupéré à un webhook choisi dans la ligne, il s'agit d'une voie de divulgation de fichiers privilégiée. Vérifiez l'identité cron, le callback réel de l'ordonnanceur et le flux de données entre la ligne et le chemin, les droits d'écriture dans la base de données, la validation effectuée après lecture de la ligne et la destination sortante. Un fichier `.env` applicatif lisible n'est qu'un indice de présence d'identifiants ; la validation d'un formulaire Web ou un mot de passe de base de données ne prouve pas à lui seul le contrôle d'une ligne ni une divulgation. Inspectez passivement la planification, le code et les permissions du fichier contenant les identifiants, sans interroger la base de données ni planifier une tâche pendant l'énumération.

Les tâches `incron` déclenchées par événement méritent le même examen : les [entrées incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) associent un chemin surveillé et un événement à une commande exécutée avec l'identité du propriétaire de la table. Un utilisateur moins privilégié peut influencer indirectement un fichier surveillé lorsqu'une application suit un lien depuis un répertoire modifiable et écrit du texte contrôlé par l'attaquant dans la cible surveillée. Vérifiez le propriétaire réel de la table, l'événement, les permissions de la cible et de ses répertoires parents, le comportement de l'application concernant le suivi des liens et la façon dont ce texte devient des arguments de commande. En particulier, [`mail` de GNU Mailutils accepte `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), et sa [commande d'échappement vers le shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) peut exécuter un programme ; un champ non fiable transmis comme option distincte à cette implémentation peut mener à l'exécution de commandes. D'autres implémentations de `mail` ou une séparation des arguments correctement citée et fixe peuvent se comporter différemment. Examinez la planification, le code applicatif et les métadonnées des fichiers sans modifier le fichier surveillé ni déclencher la tâche pendant l'énumération.

Un journal surveillé peut également franchir une frontière entre utilisateurs via un script auxiliaire. Si un compte moins privilégié peut écrire dans le journal et que le propriétaire d'`incron` en lit un champ pour le placer dans une nouvelle chaîne de commande [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), le shell analyse de nouveau ce champ avec l'identité du propriétaire. Vérifiez l'événement surveillé exact, les permissions du journal et de son répertoire parent, le chemin de l'auxiliaire, la transformation du champ du journal et si la commande résultante est bien atteinte. La seule présence d'un journal modifiable et d'une entrée `incron` ne prouve pas le flux de données ; n'écrivez pas de ligne déclencheuse et n'exécutez pas l'auxiliaire lors d'une énumération passive.

Les tâches de renouvellement de certificats peuvent franchir la même frontière. Un auxiliaire privilégié peut lire le sujet X.509 d'un certificat situé dans un répertoire modifiable par un utilisateur moins privilégié et insérer son nom commun dans une nouvelle chaîne de commande `bash -c`. [OpenSSL peut afficher le sujet d'un certificat et vérifier sa date d'expiration](https://docs.openssl.org/3.3/man1/openssl-x509/) ; [Bash analyse la chaîne `-c` comme une entrée shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), donc citer la variable dans le script externe ne protège pas contre la seconde analyse. Confirmez l'identité de la tâche planifiée, le chemin d'entrée exact et les droits d'écriture, la branche de renouvellement et le flux de données vers `bash -c` avant de conclure à une injection de commande. Inspectez passivement le script et les métadonnées du certificat ; ne déclenchez pas le renouvellement pendant l'énumération.

La même seconde analyse peut se produire lorsqu'une tâche planifiée privilégiée extrait un nom de l'archive ou du paquet d'un utilisateur moins privilégié et le transmet à `xargs -I` pour l'insérer dans une chaîne de commande `sh -c`. [GNU `xargs -I` remplace le marqueur dans les arguments initiaux](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), et [`sh -c` interprète sa chaîne de commande](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Même si le script externe cite le nom extrait, cela ne rend pas sûr un programme shell substitué ultérieurement. Vérifiez l'identité d'exécution de la tâche, le chemin d'entrée accepté et ses droits d'écriture, la validation de l'archive et les conditions de branchement, ainsi que le flux du nom vers le shell. Un répertoire de téléversement modifiable ou un appel à `xargs` ne sont que des indices ; inspectez la planification, le script et les métadonnées du chemin sans soumettre de paquet ni exécuter la tâche pendant l'énumération.

Un importateur planifié de polices ou d'images peut également faire confiance aux noms *à l'intérieur* d'une archive fournie par l'appelant, même si le nom externe du fichier téléversé est soumis à des restrictions. FontForge a corrigé l'injection de commande via les noms de membres d'archive dans sa [modification en amont pour CVE-2024-25081 et CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirmez qu'une tâche exécutée avec des privilèges supérieurs ouvre réellement une archive provenant d'un chemin modifiable par un utilisateur moins privilégié, son identité d'exécution, la version exacte de FontForge ou le rétroportage du fournisseur, ainsi que le chemin de traitement de l'archive. Une chaîne de version ou une extension de téléversement autorisée ne prouve pas à elle seule l'exécution. Inspectez la planification, les permissions du chemin et les métadonnées de version sans importer d'archive non fiable pendant l'énumération.

Les scanners réseau planifiés peuvent franchir une autre frontière lorsqu'un script personnalisé traite le sujet d'un certificat TLS distant comme un nom de fichier local. [Nmap NSE exécute les scripts sélectionnés sans sandbox](https://nmap.org/book/nse-usage.html) ; examinez donc le script réel et vérifiez s'il joint un champ de sujet non fiable à un répertoire de données sans contrôle de confinement. La divulgation d'un fichier exige une cible que l'ordonnanceur analysera, un chemin qui résout vers un fichier lisible par l'identité d'exécution du scanner et un rapport ou journal remis à un lecteur moins privilégié. Un champ de certificat ou la seule présence d'un scanner installé ne prouve pas cette chaîne ; examinez la planification, le script, la résolution du chemin et la destination du rapport sans analyser une nouvelle cible pendant une énumération passive.

Une commande cron privilégiée qui transmet un motif shell tel que `/path/to/tasks/*.yml` à un exécuteur Ansible mérite une vérification des permissions du répertoire, même si tous les playbooks existants sont en lecture seule. Un utilisateur disposant des droits d'écriture et de recherche sur le répertoire visé par le motif peut éventuellement créer un autre playbook correspondant. [Les playbooks Ansible définissent les tâches exécutées par l'exécuteur](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), mais un wrapper personnalisé peut filtrer les chemins ou utiliser une autre identité : vérifiez son comportement, l'utilisateur cron réel, l'expansion shell, les ACL, le sticky bit et la politique de montage avant de considérer le répertoire comme une voie d'exécution. Inspectez les métadonnées et le wrapper statiquement ; n'exécutez pas la tâche planifiée pendant l'énumération.

Un wrapper cron privilégié peut transmettre à un auxiliaire Perl les noms de fichiers d'un répertoire de téléversement après expansion d'un motif. L'opérateur [`<>` en diamant de Perl utilise `open` à deux arguments](https://perldoc.perl.org/perlop#The-Null-Filehandle) : un nom correspondant interprété comme une commande via un pipe peut donc être exécuté avec l'identité de l'auxiliaire ; [`<<>>` traite les arguments comme des noms de fichiers littéraux](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirmez l'identité de l'ordonnanceur, le répertoire de travail du wrapper et son motif, le traitement réel de `@ARGV` par l'auxiliaire, les restrictions sur les noms de fichiers et la possibilité pour une identité moins privilégiée de placer un nom correspondant via les droits du système de fichiers ou un service de téléversement authentifié. Une ligne cron, un script Perl ou un répertoire FTP modifiable ne prouve pas à lui seul la chaîne complète. Inspectez le code source et les métadonnées sans soumettre de nom de fichier conçu à cet effet ni exécuter la tâche pendant l'énumération.

Un script cron en lecture seule reste remplaçable si le compte planifié l'exécute par chemin et qu'un utilisateur moins privilégié peut écrire dans son répertoire parent non sticky et le parcourir. Vérifiez l'identité d'exécution de la planification, chaque composant du chemin, le sticky bit du répertoire, les ACL et la politique de montage ; examinez les métadonnées sans déplacer le fichier ni exécuter la tâche.

Un wrapper cron PHP privilégié peut faire appel à un auxiliaire qui n'existe pas encore. S'il appelle [`exec()` de PHP](https://www.php.net/manual/en/function.exec.php) avec le chemin absolu fixe d'un auxiliaire, un utilisateur moins privilégié qui peut créer ce nom dans le répertoire parent peut contrôler ce qu'une exécution ultérieure lancera. Confirmez que l'entrée cron exécute réellement le wrapper avec l'identité supérieure, la chaîne de commande exacte et la politique d'exécution de PHP, les droits d'écriture et de recherche sur le répertoire de l'auxiliaire, le comportement des liens symboliques et du sticky bit, et si le chemin de l'auxiliaire est toujours absent. Un répertoire modifiable ou un auxiliaire manquant ne sont que des indices ; inspectez la planification, le code source et les métadonnées du chemin sans créer l'auxiliaire ni déclencher la tâche.

Une tâche planifiée peut aussi détecter des scripts d'entrée avec `find` et transmettre chacun d'eux à un interpréteur. Par exemple, la fonction `system()` de [gnuplot invoque un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf) ; une tâche privilégiée qui exécute `gnuplot` sur chaque fichier `*.plt` d'un répertoire modifiable par un utilisateur moins privilégié peut donc exécuter des commandes avec l'identité de la tâche. [Le droit de lecture d'un répertoire contrôle son listage, tandis que les droits d'écriture et de recherche (`x`) contrôlent la création et l'accès aux noms connus](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html) ; vérifiez les droits d'écriture et de recherche même si `ls` ne peut pas lister le répertoire. Recoupez l'identité et la commande exactes de l'ordonnanceur, le comportement de l'interpréteur, le motif de fichiers sélectionnés et les permissions du répertoire ; un répertoire modifiable ou un interpréteur installé ne suffit pas à établir une escalade. Les planifications privées et les tâches de courte durée peuvent nécessiter une observation autorisée des événements, car un instantané de processus peut les manquer.

Pour une tâche PHP privilégiée, examinez les instructions littérales `include`/`require` dans le cadre de la chaîne de scripts exécutables. [PHP évalue les fichiers inclus](https://www.php.net/manual/en/function.include.php) ; un fichier `.php` modifiable par un groupe peut donc exécuter du code avec l'identité de la tâche même si le script principal est en lecture seule. Vérifiez l'identité planifiée, la résolution effective de l'include-path, les permissions du fichier et du répertoire, ainsi que l'exécution réelle de la tâche ; un exemple de ligne cron dans un commentaire n'est qu'un indice. Le même examen s'applique à un [serveur intégré PHP](https://www.php.net/commandline.webserver) appartenant à root et lancé avec `-S` et `-t <document-root>` : un écouteur local peut tout de même exécuter le code PHP de l'application à la suite de requêtes locales. Inspectez le processus et le code source sans déclencher l'un ou l'autre de ces mécanismes pendant l'énumération.

Une tâche PHP privilégiée peut aussi franchir la frontière par un **fichier de données** : si un utilisateur moins privilégié peut modifier le fichier exact transmis à [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP peut appeler les méthodes `__wakeup()` ou `__unserialize()` d'une classe chargée lors de la restauration de l'objet. Examinez l'identité effective de la tâche, les permissions du fichier et de ses répertoires parents, les classes chargées et les effets réels des méthodes, par exemple une écriture de fichier déterminée par une propriété. Un journal modifiable ou un appel à `unserialize()` ne suffit pas à prouver qu'une voie exploitable existe. Inspectez le code source et les métadonnées sans écrire de données sérialisées ni exécuter la tâche pendant l'énumération.

Une tâche cron root peut invoquer l'**exécuteur de pages CLI** d'une application PHP plutôt que le serveur Web. Suivez le document root et l'URI sélectionnés par l'exécuteur jusqu'au véritable point d'entrée PHP ; si ce point d'entrée est modifiable par le compte du service Web, la requête CLI planifiée peut exécuter le code modifié en tant que root même si l'exécuteur et le wrapper cron sont en lecture seule. Confirmez l'identité de l'ordonnanceur, la résolution exacte de l'URI vers le fichier, les permissions effectives du fichier et de ses répertoires parents, ainsi que l'existence d'un contrôle d'intégrité protégeant le point d'entrée lui-même. Inspectez le code source et les métadonnées sans invoquer l'exécuteur ni modifier la page pendant l'énumération.

Un processus `ipython` lancé par une tâche planifiée ou un autre utilisateur depuis un répertoire de travail partagé mérite un examen des fichiers de démarrage. Les [notes de sécurité d'IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) expliquent que les versions concernées recherchaient des profils et des fichiers de configuration dans le répertoire courant, y compris du code dans `profile_default/startup`, avant le correctif de CVE-2022-21699. Recoupez la version réellement installée ou le correctif du fournisseur, le répertoire de travail de la commande, l'identité du processus privilégié et la possibilité pour l'utilisateur moins privilégié d'écrire dans le chemin de démarrage exact et de le parcourir. La présence d'`ipython`, d'un répertoire modifiable ou d'une chaîne de version ne prouve pas à elle seule qu'une autre identité y chargera un fichier. Inspectez la planification et les métadonnées du chemin sans lancer l'interpréteur avec des privilèges supérieurs.

Pour un serveur PHP privilégié qui appelle des fonctions d'une extension native personnalisée, déterminez le SAPI PHP du service et son `php.ini` effectif ainsi que les fichiers `.ini` analysés avant d'examiner l'extension. [PHP charge au démarrage les bibliothèques `extension` configurées](https://www.php.net/manual/en/ini.core.php), et [les SAPI CLI et Web peuvent utiliser des fichiers de configuration différents](https://www.php.net/manual/en/configuration.file.php). Un formulaire de connexion accessible ou un écouteur local peut donc transmettre des chaînes contrôlées par l'utilisateur à du code compilé exécuté avec l'identité du service. Relevez le `User=` de l'unité, `ExecStart=`, le répertoire de travail, le chemin réel de l'extension et les arguments contrôlables par l'appelant ; la simple présence d'un fichier `.so` ou d'un socket local ne prouve pas l'existence d'un défaut de corruption mémoire. Analysez séparément tout analyseur personnalisé au lieu d'envoyer des sondes pendant l'énumération passive.

Lorsqu'un wrapper privilégié calcule le hash d'un script par chemin puis ouvre à nouveau ce chemin pour l'exécuter, le condensat authentifie uniquement l'objet lu lors de la première ouverture. Si un utilisateur moins privilégié peut remplacer l'entrée de répertoire du script entre ces deux ouvertures, l'exécution ultérieure peut résoudre vers un autre objet même si le fichier de script d'origine appartient à root. Un FIFO peut prolonger la phase de vérification, mais cette voie dépend des droits modifiables sur les répertoires parents, de l'existence d'ouvertures réellement distinctes, de l'identité de l'ordonnanceur, des règles sur le sticky bit et les montages, ainsi que du minutage. Examinez le wrapper et la sortie de `namei -l` comme indices passifs ; un contrôle d'intégrité réussi ne prouve pas à lui seul que le chemin utilisé ensuite est protégé.

Une tâche de sauvegarde privilégiée peut aussi **divulguer** des données sans exécuter de commandes fournies par un attaquant. Vérifiez si un utilisateur moins privilégié peut créer un fichier de contrôle que la tâche lit, si la tâche ouvre ensuite une source protégée comme `/etc/shadow` et si un attaquant peut recevoir le résultat via une URL qu'il choisit ou une sortie lisible. Vérifiez ces trois éléments avant de conclure à une voie de divulgation. Une commande shell fixe dans le même script ne fait pas à elle seule de ce fichier de contrôle une entrée d'injection shell. Inspectez le script et les permissions des fichiers sans exécuter la tâche ni placer de fichier de contrôle pendant l'énumération.

Si une tâche planifiée privilégiée exécute `curl -K FILE` ou `curl --config FILE`, [curl traite les options de ce fichier comme des arguments de ligne de commande](https://curl.se/docs/manpage.html). Un utilisateur moins privilégié qui contrôle le fichier exact au moment où curl le lit peut influencer l'URL demandée, l'entrée provenant d'un fichier local ou le chemin de sortie. Confirmez l'identité effective de la tâche, les droits d'écriture sur le fichier et ses répertoires parents, le moment où une autre tâche peut remplacer le fichier, ainsi que l'interaction entre les options de configuration et les options fixes de la ligne de commande avant d'affirmer qu'une lecture ou une écriture protégée est possible. Un chemin de configuration modifiable ou un indicateur `-K` visible ne prouve pas à lui seul que les options choisies prennent effet ; inspectez la planification et les métadonnées sans exécuter la tâche ni récupérer d'URL pendant l'énumération passive.

Si une entrée cron invoque un script auxiliaire, examinez aussi son répertoire de travail et sa commande d'archivage. Un joker sans guillemets portant sur un répertoire modifiable par un autre utilisateur peut transformer les noms de fichiers en options pour l'archiveur ; les actions de points de contrôle de GNU tar en sont un exemple. Confirmez l'identité d'exécution planifiée, le répertoire d'entrée modifiable, l'archiveur et les options exacts, ainsi que la présence éventuelle de `--` pour terminer l'analyse des options avant de conclure à une voie d'exécution entre utilisateurs. Voir [le comportement des jokers et de tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Une divulgation distincte de fichiers de sauvegarde peut se produire si un auxiliaire privilégié exécute `cd INPUT_DIR; tar ... *` sans vérifier si `cd` a réussi. Si un utilisateur moins privilégié peut supprimer ou remplacer `INPUT_DIR`, l'échec de `cd` peut laisser le shell dans son répertoire précédent, que la commande d'archivage suivante risque alors de lire. Vérifiez le répertoire de travail initial de la tâche, l'existence d'un scénario réel d'échec de `cd`, si le script s'arrête ou utilise `&&`, les options exactes de l'archiveur et si l'utilisateur moins privilégié peut lire l'archive de sortie. Un répertoire d'entrée modifiable ou une archive lisible ne sont que des indices ; inspectez l'auxiliaire et les permissions du chemin sans modifier la tâche en cours.

Un exécutable planifié peut dissimuler un script shell sans supprimer sa frontière de confiance : [SHc](https://github.com/neurobin/shc) encapsule du texte de script chiffré dans un binaire natif et l'exécute via un shell au moment de l'exécution. Un suffixe `.sh.x` ou un ELF opaque n'est qu'un indice à examiner. Pour évaluer l'injection d'options via les noms de fichiers, établissez l'identité de l'ordonnanceur privilégié, le répertoire de travail et la commande réels de l'auxiliaire, la capacité d'un utilisateur moins privilégié à y créer des noms correspondants et la possibilité qu'un joker sans guillemets atteigne une commande telle que `rsync` sans délimitation des options. L'option de shell distant de [`rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) n'est pertinente que si ce chemin de commande exact est utilisé. Une visibilité limitée de `/proc` ou l'échec d'un déchiffrement statique ne permet pas de connaître la commande ; n'exécutez pas l'auxiliaire privilégié dans le seul but de le classifier.

Le texte de la ligne de commande d'un processus constitue une autre entrée non fiable pour un auxiliaire privilégié. Un utilisateur moins privilégié peut choisir un titre de processus ou un `argv[0]` correspondant à `pgrep -f` ; un nom correspondant n'authentifie ni l'exécutable ni son propriétaire. Si un script exécuté par root capture ce texte, en réécrit une partie en `apache2ctl`/`httpd` et exécute le résultat sans tableau d'arguments fixe, des options choisies par l'attaquant peuvent sélectionner un autre répertoire de configuration ou journal d'erreurs. L'analyse de configuration Apache peut charger des modules ou atteindre des auxiliaires configurés ; ne validez donc pas une configuration non fiable en tant que root pendant l'énumération. Examinez le propriétaire de l'ordonnanceur, l'auxiliaire exact, l'identité du processus et le flux des données vers les arguments ; il s'agit d'une injection d'options/de configuration, sauf si l'exécution de métacaractères shell est démontrée séparément.

Un analyseur exécuté par root qui transmet du texte non fiable à l'arithmétique de Bash peut exécuter des substitutions contenues dans ce texte. Le [guide d'escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) présente un exemple détaillé. Confirmez la source d'entrée et la commande d'analyse avant de considérer toute expression arithmétique comme exploitable.

Pour une tâche privilégiée qui analyse un journal applicatif, suivez les champs non fiables au-delà de la première analyse. Un compte moins privilégié peut être en mesure d'écrire dans le journal via son groupe de processus actuel ou d'influencer des champs de requête consignés ; un enregistrement peut alors sélectionner une image dont les métadonnées deviennent un second chemin utilisé pour ouvrir du XML. Vérifiez l'identité effective de la tâche, les véritables droits d'écriture sur le journal, le traitement des délimiteurs, le confinement du chemin canonique et le caractère contrôlable par un attaquant du fichier XML sélectionné. L'expansion d'entités externes peut entraîner la divulgation de fichiers privilégiés si le résultat développé parvient à une sortie lisible par un utilisateur moins privilégié. Le [guide de sécurité du traitement XML en Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documente les contrôles d'accès aux DTD et entités externes ; examinez l'analyseur installé et ses paramètres effectifs. Un journal ou un fichier XML modifiable ne sont que des indices. Examinez le code et les métadonnées sans alimenter l'analyseur planifié pendant l'énumération.

Examinez aussi les tâches privilégiées qui matérialisent des fichiers depuis le dépôt Git d'un autre utilisateur. Un script peut utiliser `git ls-tree` et `git cat-file` plutôt que `git checkout`, tout en faisant confiance aux chemins d'arborescence contrôlés par l'attaquant lorsqu'il les joint à un répertoire intermédiaire. Les chemins absolus et les composants `..` peuvent sortir de ce répertoire si la destination n'est pas normalisée et contrôlée pour en vérifier le confinement avant l'écriture. `git -c safe.directory=*` autorise l'accès aux dépôts appartenant à d'autres utilisateurs ; cela ne crée pas, à lui seul, une possibilité d'écriture arbitraire.

Une sauvegarde de base de données exécutée par root peut créer une autre frontière de propriété. [`pg_basebackup` de PostgreSQL](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copie les fichiers ordinaires supplémentaires placés dans le répertoire de données source, et son format plain par défaut écrit les fichiers dans `-D` sous forme d'arborescence. Si un utilisateur moins privilégié peut créer ou modifier ces fichiers source, examinez le propriétaire et le mode des fichiers de destination, l'accessibilité du chemin et son caractère exécutable, ainsi que l'option de montage `nosuid`. Une copie appartenant à root avec des permissions set-ID préservées peut être dangereuse ; une sauvegarde au format tar uniquement, des permissions supprimées ou une destination inaccessible n'établissent pas la même voie. Suivez le wrapper planifié et l'utilisateur effectif avant de considérer la commande de sauvegarde comme une vulnérabilité.

## Observer les tâches de courte durée

Un instantané unique des processus peut manquer une tâche qui ne s'exécute que pendant quelques millisecondes. Comparez les déclarations des timers et de cron aux journaux et, lorsque cela est autorisé, à la surveillance des événements de processus avec des outils tels que `pspy` ou audit. Recoupez le propriétaire de la tâche planifiée, la ligne de commande exacte et les fichiers lus ou écrits par la tâche. Une interface Web d'ordonnanceur sur loopback constitue une interface distincte ; voir [l'exemple Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
