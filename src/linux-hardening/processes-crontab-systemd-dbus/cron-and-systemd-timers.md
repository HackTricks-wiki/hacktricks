# Cron Jobs and Systemd Timers

{{#include ../../banners/hacktricks-training.md}}

スケジュールされたタスクは、現在のシェルとは異なるユーザー ID や環境で実行される場合があります。cron、`at`、anacron、systemd timers を列挙し、各スケジュール済みコマンドについて、スクリプト、インポート、作業ディレクトリ、書き込み可能な入力をたどって確認します。

## スケジュールを列挙する

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

システムの crontab には通常ユーザーフィールドがありますが、ユーザーの crontab にはありません。実際のスケジューラの有効な PATH と環境変数を調べます。`run-parts --test /etc/cron.daily` を実行すると、そのホストで選択されるファイル名が表示されます。制御文字によって通常の出力ではエントリが隠れることがあるため、スケジュールに不審な点がある場合は `cat -A` または `sed -n l` を使います。

## 特権ファイルとコマンドの解決を追跡する

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

書き込み可能なスクリプトチェーン、`EnvironmentFile=` のパス、drop-in、symlink、相対コマンド、wildcard 展開、特権タスクがコピーまたは実行するバイナリを確認します。timer は `Unit=` 設定を通じて、異なる名前の service を起動することがあります。[PATH](../linux-basics/linux-environment-variables.md#path)、[wildcard](../interesting-files-permissions/wildcards-spare-tricks.md)、[file-link](../main-system-information/filesystem-links-and-file-descriptors.md) の各ページでは、主なプリミティブを解説しています。

root で実行されるスケジュール済み `chkrootkit` script を調べる場合、インストール済みソースに古い [slapper-loop quoting defect (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476) があるか確認します。`SLAPPER_FILES` の一時パスを確認した後に、`file_port=$file_port $i` が引用符なしで記述されていると、そのファイルを実行できます。実際の script または vendor patch、root によるスケジュール、該当する正確な一時パスへの低権限ユーザーの書き込み権限、そのファイルの実行可能性、mount policy を確認してください。version string や `chkrootkit` の存在だけでは、このパスがあるとは判断できません。passive review 中に一時ファイルを作成したり実行したりしないでください。

timer の root service が `systemctl restart <other>.service` を実行する場合は、さらに unit を1つたどります。再起動される unit が、低権限ユーザーの書き込み可能な script を指定して shell を起動することがあります。有効な `User=`、`DynamicUser=`、`RootDirectory=`/`RootImage=`、正確な `ExecStart=` 引数、script と親パスの権限を確認してください。書き込み可能な script は、timer と再起動対象の service がその実行コンテキストで有効になるまでは候補にすぎません。service を再起動せずに unit のプロパティを調べてください。

高権限の job が hostname から script を取得し、その応答を shell に渡す場合は、リモート script に加えて、その hostname の名前解決を誰が制御できるかも確認してください。group または ACL によってアクセス権が付与されている場合を含め、書き込み可能な `/etc/hosts` によって、job がローカルで名前解決する宛先を変更できることがあります。`curl` の応答がクロスユーザー実行パスになるのは、実際のスケジュール済みコマンドがその応答を実行し、job が影響を受ける resolver 経路を使う場合に限られます。job の実行ユーザー、正確な URL と shell pipeline、有効な proxy/DNS の挙動、ファイルと親ディレクトリの権限を確認してください。hosts file が書き込み可能というだけでは、特権 consumer が存在する証拠にはなりません。列挙中は、schedule と metadata を調べるにとどめ、mapping の変更や script の取得を行わないでください。

特権スケジュール済み `wget` による取得は、ダウンロードした内容が直接実行されなくても、別個のファイル書き込み境界になります。[GNU Wget 1.18 は CVE-2016-4971 の修正として、HTTP から FTP への redirect 時のデフォルトのファイル名処理を変更しました](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html)。古い影響を受ける build では、redirect 先の FTP filename が使われることがあり、`--trust-server-names` はその挙動を明示的に要求します。低信頼の主体が HTTP response と FTP resource の両方を制御できる場合、job がその redirect に従うか、実際の Wget build または vendor backport、出力オプション、実行ユーザー、作業ディレクトリ、保存先のファイル名が startup file になり得るかを調べてください。[Wget は `WGETRC` または `$HOME/.wgetrc` を読み込みます](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html)。また、[その設定では POST source や出力先を指定できます](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html)。その結果として情報漏えいや書き込みが発生するには、後続の特権 fetch が別途必要です。`authbind` による低い port へのアクセスが関係するのは、呼び出し側が job の要求する URL を実際に提供できる場合に限られます。redirect を提供したり job を実行したりせずに、設定と log を受動的に確認してください。[`disk` group による raw block-device access](../user-information/interesting-groups-linux-pe/README.md#disk-group) は、この network-fetch 経路とは独立しています。

script だけでなく data file もたどってください。スケジュール済みの simulation または orchestration tool が、起動する process を定義した YAML file を読み込むことがあります。低権限ユーザーがその file を編集でき、job が別のアカウントで実行する場合、そのデータは job の実行ユーザー権限で実行される command になり得ます。書き込み可能な YAML file を実行パスとみなす前に、正確なスケジュール済みコマンド、有効な実行ユーザー、ファイルパス、parser の意味、親ディレクトリを含む書き込み権限を確認してください。passive triage では schedule とファイル metadata の確認で十分です。列挙中に job を実行したり、入力を変更したりしないでください。

高権限の job が、低権限ユーザーが置き換え可能なファイルを `ssh -F` で指定する場合、SSH client configuration も実行可能な入力になります。OpenSSH の [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) は client の shell を通じてローカルコマンドを実行します。一方、`Host`/`Match` と先行する option によって、その directive が適用されるかが決まります。これをクロスユーザー実行パスと判断する前に、正確なスケジュール済み SSH invocation、実行ユーザー、選択された config path、ディレクトリとファイルの書き込み権限、有効な option の順序を照合してください。job を実行したり、特権アカウントで信頼できない config を読み込んだりせずに、これらの記録を調べてください。

スケジュール済み `scp` の後に `ssh` でコピーした script を実行する場合、低権限ユーザーが接続先 SSH service を制御できるなら、別の trust boundary も確認する必要があります。その service が接続を別の host に転送できる場合、特権 client が意図しない endpoint に認証する可能性があります。[`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) は変更された host key に対する保護を弱めますが、OpenSSH に残る制限と有効な host ごとの option が適用されます。job の実行ユーザー、実際の接続先と認証方法、リモートコマンドの有効な実行ユーザー、転送先 host の同じ宛先パスが書き込み可能か、または既存かを確認してください。古いファイルや攻撃者が制御するファイルを実行するには、copy が失敗するかそのパスを見落とすことに**加えて**、wrapper が SSH command まで処理を続ける必要があります。[Bash の `errexit`](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) と明示的な status 処理が、その流れに影響します。弱い host-key 設定、見えている `sshpass` process、書き込み可能な一時ディレクトリだけでは、この chain が成立するとは判断できません。列挙中は service を転送したり job を実行したりせずに、schedule、script、SSH configuration、ファイル metadata を調べてください。

特権アプリケーションの scheduler は、書き込み可能な file ではなく database row から job を取得することがあります。たとえば、root cron entry が Laravel の [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) を実行し、task row を読むアプリケーションコードに到達する場合があります。低権限アカウントがローカルパスを含む row を書き込め、スケジュール済み callback が root で PHP の [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) を呼び出し、返された本文を row で選択された webhook に送信するなら、特権ファイル漏えいの経路になります。cron の実行ユーザー、実際の scheduler callback と row から path への data flow、database の書き込み権限、row 読み込み後の validation、送信先を確認してください。読み取り可能なアプリケーション `.env` は credential の手がかりにすぎません。web form の validation や database password だけでは、row の制御や情報漏えいの証明にはなりません。列挙中は database に query したり task をスケジュールしたりせず、schedule、コード、credential file の権限を受動的に調べてください。

イベント駆動の `incron` job も同様に確認してください。[incrontab entry](https://manpages.debian.org/testing/incron/incrontab.5.en.html) では、監視対象の path と event に、table の所有者の権限で実行する command を紐付けます。アプリケーションが書き込み可能なディレクトリ内の link をたどり、攻撃者が制御するテキストを監視対象の宛先に書き込む場合、低権限ユーザーが監視対象 file に間接的な影響を及ぼすことがあります。実際の table 所有者、event、対象と親ディレクトリの権限、アプリケーションの link-following 挙動、そのテキストが command 引数になる仕組みを確認してください。特に、[GNU Mailutils の `mail` は `--exec` を受け付けます](https://mailutils.org/manual/html_node/Invoking-Mail.html)。また、その[shell-escape command](https://mailutils.org/manual/html_node/Shell-Escapes.html) では program を実行できます。この実装に対して、信頼できない field が別個の option として渡されると、command execution につながる場合があります。他の `mail` 実装や、引用符で保護された固定の引数境界では、挙動が異なることがあります。列挙中は、監視対象 file を変更したり job を起動したりせずに、schedule、アプリケーションコード、ファイル metadata を調べてください。

監視対象の log も helper script を介してユーザー境界を越えることがあります。低権限アカウントが log に書き込め、`incron` の所有者が log から field を読み取って、新しい [`sh -c` command string](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) に挿入する場合、shell はその field を所有者の権限で再度解析します。実際に監視する event、log と親ディレクトリの権限、helper path、log field の変換方法、生成された command が実行されるかを確認してください。書き込み可能な log と `incron` entry があるだけでは、data flow の証明にはなりません。passive enumeration 中に trigger 用の行を書き込んだり helper を実行したりしないでください。

証明書更新 job でも同じ境界を越えることがあります。特権 helper が、低権限ユーザーの書き込み可能なディレクトリにある証明書から X.509 subject を読み取り、その common name を新しい `bash -c` command string に挿入することがあります。[OpenSSL では証明書の subject 表示と有効期限の確認ができます](https://docs.openssl.org/3.3/man1/openssl-x509/)。[Bash は `-c` string を shell input として解析します](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html)。そのため、外側の script で変数を引用符で囲んでも、2回目の解析は保護されません。command injection と判断する前に、スケジュールの実行ユーザー、正確な入力パスと書き込み権限、更新処理の分岐、`bash -c` への data flow を確認してください。列挙中は script と証明書 metadata を受動的に調べ、renewal を起動しないでください。

同じ2回目の解析は、特権スケジュール済み job が低権限ユーザーの archive または package から name を取り出し、`xargs -I` に渡して `sh -c` command string に挿入する場合にも起こり得ます。[GNU `xargs -I` は初期引数内の placeholder を置換します](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html)。また、[`sh -c` は command string を解釈します](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)。外側の script で抽出した name を引用符で囲んでも、後から置換される shell program が安全になるわけではありません。job の実行ユーザー、受け付ける正確な入力パスと書き込み権限、archive validation と分岐条件、name から shell への data flow を確認してください。書き込み可能な upload directory や `xargs` の使用だけでは手がかりにすぎません。列挙中は package を送信したり job を実行したりせず、schedule、script、path metadata を調べてください。

スケジュール済みの font または image importer も、upload の外側の filename が制限されていても、caller が渡した archive 内の name を信頼してしまうことがあります。FontForge は、[CVE-2024-25081 と CVE-2024-25082 に関する upstream の変更](https://github.com/fontforge/fontforge/pull/5367)で、archive member name による command injection を修正しました。高権限の job が低権限ユーザーの書き込み可能な path から archive を実際に開くか、その実行ユーザー、正確な FontForge build または vendor backport、archive 処理のコードパスを確認してください。version string や許可された upload suffix だけでは、実行の証明になりません。列挙中に信頼できない archive を import せず、schedule、path 権限、build metadata を調べてください。

スケジュール済み network scanner が、リモート TLS certificate の subject をローカルの filename として扱う場合、別の境界を越える可能性があります。[Nmap NSE は選択した script を sandbox なしで実行します](https://nmap.org/book/nse-usage.html)。実際の script を調べ、信頼できない subject field を containment check なしで data directory に連結していないか確認してください。ファイル漏えいには、scheduler が scan する対象、scanner の実行ユーザーが読み取れる file に解決される path、その結果を低権限の読者に渡す report または log が必要です。certificate field や scanner のインストールだけでは chain の証明になりません。列挙中に新たな対象を scan せず、schedule、script、path 解決、report の送信先を確認してください。

特権 cron command が `/path/to/tasks/*.yml` のような shell glob を Ansible runner に渡す場合、既存の playbook がすべて読み取り専用でも、directory の権限を確認してください。glob 対象の directory に書き込みと search の権限を持つユーザーは、パターンに一致する playbook を追加できることがあります。[Ansible playbook は runner が実行する task を定義します](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html)。ただし、custom wrapper が path を filter したり別の実行ユーザーを使ったりすることがあります。directory を実行パスとみなす前に、wrapper の挙動、実際の cron ユーザー、shell expansion、ACL、sticky bit、mount policy を確認してください。metadata と wrapper を静的に調べ、列挙中にスケジュール済み job を実行しないでください。

特権 cron wrapper が glob を展開した後、upload directory 内の filename を Perl helper に渡す場合があります。Perl の [`<>` diamond operator は2引数の `open` を使います](https://perldoc.perl.org/perlop#The-Null-Filehandle)。そのため、pipe command として解釈される一致 filename は helper の実行ユーザー権限で実行される可能性があります。[`<<>>` は引数をリテラル filename として扱います](https://perldoc.perl.org/perlop#The-Null-Filehandle)。scheduler の実行ユーザー、wrapper の作業ディレクトリと glob、helper が実際に `@ARGV` を処理する方法、filename の制限、低権限ユーザーがファイルシステム権限または認証済み upload service を通じて一致する name を配置できるかを確認してください。cron line、Perl script、書き込み可能な FTP directory だけでは chain 全体の証明になりません。列挙中に細工した filename を送信したり job を実行したりせず、ソースと metadata を調べてください。

スケジュールされたアカウントが pathname で実行する read-only cron script も、低権限ユーザーがその非 sticky 親ディレクトリに書き込みと traverse の権限を持つ場合は置き換え可能です。schedule の実行ユーザー、すべての path component、directory の sticky bit、ACL、mount policy を確認してください。file を移動したり job を実行したりせず、metadata を調べてください。

特権 PHP cron wrapper は、まだ存在しない helper に到達することがあります。絶対パスで固定された helper path を PHP [`exec()`](https://www.php.net/manual/en/function.exec.php) に渡す場合、親ディレクトリ内にその name を作成できる低権限ユーザーが、後の実行で何が起動するかを制御できることがあります。cron entry が実際に高権限で wrapper を実行するか、正確な command string と PHP の実行 policy、helper directory への書き込みと search の権限、symlink と sticky bit の挙動、helper path がまだ存在しないかを確認してください。書き込み可能な directory や helper がないことだけでは手がかりにすぎません。列挙中は helper を作成したり job を起動したりせず、schedule、ソース、path metadata を調べてください。

スケジュール済み job が `find` で入力 script を見つけ、interpreter に渡すこともあります。たとえば、[gnuplot の `system()` function は shell を起動します](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf)。そのため、低権限ユーザーの書き込み可能な directory にあるすべての `*.plt` file を特権 job が `gnuplot` で実行する場合、job の実行ユーザー権限で command を実行できます。[directory の read permission は一覧表示を制御し、write と search (`x`) は名前を作成して既知の名前にアクセスすることを制御します](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html)。`ls` で一覧表示できない場合でも、write と search の権限を確認してください。実行パスを確認するには、scheduler の正確な実行ユーザーと command、interpreter の挙動、選択される file pattern、directory の権限を照合してください。書き込み可能な directory や interpreter のインストールだけでは、権限昇格の証明になりません。private schedule や短時間の job は、単一の process snapshot では見逃すことがあるため、許可を得た event observation が必要になる場合があります。

特権 PHP job では、実行可能な script chain の一部として、literal な `include`/`require` statement も確認してください。[PHP は include した file を評価します](https://www.php.net/manual/en/function.include.php)。そのため、main script が read-only でも、group が書き込み可能な `.php` file が job の実行ユーザー権限で code を実行できます。スケジュールの実行ユーザー、有効な include-path 解決、ファイルとディレクトリの権限、job が実際に実行されるかを確認してください。comment 内の cron line の例は手がかりにすぎません。同じ確認は、`-S` と `-t <document-root>` で起動された root 所有の [PHP built-in server](https://www.php.net/commandline.webserver) にも当てはまります。loopback listener でも、ローカル request に対してアプリケーションの PHP を実行することがあります。列挙中は、どちらの trigger も呼び出さずに process とソースを調べてください。

特権 PHP job は、**data file** を通じても境界を越えることがあります。低権限ユーザーが [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php) に渡される正確な file を変更できると、PHP は object の復元時に読み込み済み class の `__wakeup()` または `__unserialize()` method を呼び出す可能性があります。job の有効な実行ユーザー、file と親ディレクトリの権限、読み込み済み class、property で選択した file への書き込みなどの実際の method の副作用を確認してください。書き込み可能な log や `unserialize()` の呼び出しだけでは、利用可能な経路の証明になりません。列挙中は serialized input を書き込んだり job を実行したりせず、ソースと metadata を調べてください。

root cron task が Web server ではなく PHP application の **CLI page runner** を呼び出す場合があります。runner が選択する document root と URI を、実際の PHP entrypoint までたどってください。その entrypoint が web-service account から書き込み可能なら、runner と cron wrapper が read-only でも、スケジュール済み CLI request が変更済み code を root 権限で実行できます。scheduler の実行ユーザー、正確な URI から file への解決、有効な file と親ディレクトリの権限、entrypoint 自体を保護する integrity check があるかを確認してください。列挙中は runner を呼び出したり page を変更したりせず、ソースと metadata を調べてください。

スケジュール済み job や別のユーザーによって共有作業ディレクトリから起動される `ipython` process では、startup file を確認してください。[IPython の security release notes](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) によると、CVE-2022-21699 の修正前の影響を受ける build では、`profile_default/startup` code などの profile と configuration を current directory から検索していました。実際にインストールされている build または vendor patch、command の作業ディレクトリ、高権限 process の実行ユーザー、低権限ユーザーが正確な startup path に対して持つ write と search の権限を照合してください。`ipython` のインストール、書き込み可能な directory、version string だけでは、別のユーザーがその場所の file を読み込む証拠になりません。高権限の interpreter を起動せずに、schedule と path metadata を調べてください。

custom native extension の function を呼び出す特権 PHP server では、extension を調べる前に、service の PHP SAPI、有効な `php.ini`、scan 対象の `.ini` file をたどってください。[PHP は起動時に設定された `extension` library を読み込みます](https://www.php.net/manual/en/ini.core.php)。また、[CLI と web SAPI では異なる configuration file が使われる場合があります](https://www.php.net/manual/en/configuration.file.php)。そのため、到達可能な login form やローカル listener から、service の実行ユーザー権限で動作する compiled code にユーザー制御の文字列が渡される可能性があります。unit の `User=`、`ExecStart=`、作業ディレクトリ、実際の extension path、caller が制御できる引数を記録してください。`.so` の存在や loopback socket だけでは、memory-corruption flaw の証明になりません。passive enumeration 中に probe を送信せず、custom parser は別途解析してください。

特権 wrapper が script を pathname で hash 化した後、実行のために同じ pathname を再度開く場合、digest が認証するのは最初に開いたときに読み込まれた object だけです。低権限ユーザーが2回の open の間に script の directory entry を置き換えられると、元の script file が root 所有でも、後の実行で別の object が解決される可能性があります。FIFO で check 段階を長引かせられる場合もありますが、この経路の成立には、置き換え可能な親ディレクトリの権限、実際に別々の open が行われること、scheduler の実行ユーザー、sticky bit と mount の規則、タイミングが関係します。wrapper と `namei -l` の出力を受動的な手がかりとして調べてください。checksum が成功しても、後の pathname が保護されている証明にはなりません。

特権 backup job は、攻撃者が指定した command を実行せずにデータを**漏えい**させることもあります。低権限ユーザーが job の読み込む control file を作成できるか、その後 job が `/etc/shadow` などの保護対象 source を開くか、攻撃者が指定した URL または読み取り可能な出力先に結果が届くかをたどってください。情報漏えい経路と判断する前に、この3点すべてを確認してください。同じ script に固定 shell command があっても、その control file が shell-injection 入力になるとは限りません。列挙中は job を実行したり control file を配置したりせず、script とファイル権限を調べてください。

特権スケジュール済み job が `curl -K FILE` または `curl --config FILE` を実行する場合、[curl はその file 内の option を command-line 引数として扱います](https://curl.se/docs/manpage.html)。curl が読み込む時点でその正確な file を制御できる低権限ユーザーは、要求する URL、ローカル file の入力、出力先に影響を与えられる可能性があります。保護対象の読み取りや書き込みを主張する前に、job の有効な実行ユーザー、file と親ディレクトリへの書き込み権限、file を置き換える別 job の実行タイミング、config option と固定 command-line option の相互作用を確認してください。書き込み可能な config path や `-K` flag が見えるだけでは、指定した option が有効になる証拠になりません。passive enumeration 中は job を実行したり URL を取得したりせず、schedule と metadata を調べてください。

cron entry が helper script を呼び出す場合は、helper の作業ディレクトリと archive command も確認してください。別のユーザーが書き込み可能な directory に対する引用符なしの wildcard は、filename を archiver option として解釈させることがあります。GNU tar の checkpoint action はその一例です。クロスユーザー command 経路と判断する前に、スケジュールの実行ユーザー、書き込み可能な入力ディレクトリ、正確な archiver と option、`--` で option の解析を終了しているかを確認してください。[wildcard と tar の挙動](../interesting-files-permissions/wildcards-spare-tricks.md)を参照してください。

特権 helper が `cd INPUT_DIR; tar ... *` を実行し、`cd` の成功を確認しない場合、backup file の情報漏えいが別途発生することがあります。低権限ユーザーが `INPUT_DIR` を削除または置き換えられると、`cd` の失敗後も shell は以前のディレクトリに残り、後続の archive command がそこでファイルを読み込む可能性があります。job の初期作業ディレクトリ、実際に `cd` が失敗する経路、script が終了するか `&&` を使うか、正確な archiver option、出力 archive が低権限ユーザーから読み取り可能かを確認してください。書き込み可能な入力ディレクトリや読み取り可能な archive だけでは手がかりにすぎません。実行中の job を変更せず、helper と path の権限を調べてください。

スケジュール済み executable が shell script を隠している場合も、trust boundary は残ります。[SHc](https://github.com/neurobin/shc) は暗号化された script text を native binary に包み、実行時に shell 経由で実行します。`.sh.x` suffix や内容が不透明な ELF は、確認を始める手がかりにすぎません。filename option injection を評価するには、特権 scheduler の実行ユーザー、helper の実際の作業ディレクトリと command、低権限ユーザーがそこで一致する name を作成できるか、引用符なしの glob が option の境界なしに `rsync` などの command に渡されるかを確認してください。[`rsync` の remote-shell option](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) が関係するのは、正確にその command path が使われる場合に限られます。`/proc` の可視性が制限されている場合や静的復号に失敗した場合は command が不明のままです。分類だけを目的に特権 helper を実行しないでください。

process の command-line text も特権 helper に対する信頼できない入力です。低権限ユーザーは、`pgrep -f` に一致する process title または `argv[0]` を選べます。一致する name は executable や所有者を認証しません。root で実行される script がその text を取得し、一部を書き換えて `apache2ctl`/`httpd` にし、固定の argument array を使わずに実行すると、攻撃者が指定した option によって、別の configuration directory や error log が選択されることがあります。Apache の configuration 解析では module を読み込んだり、設定済み helper に到達したりする可能性があるため、列挙中に root で信頼できない configuration を検証しないでください。scheduler の所有者、正確な helper、process identity、data から argument への流れを調べてください。shell metacharacter による実行が別途示されない限り、これは option/configuration injection です。

信頼できない text を Bash arithmetic に渡す root 実行の parser は、その text 内の substitution を実行する可能性があります。[privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) に実例があります。すべての arithmetic expression を exploitable と判断する前に、入力元と解析 command を確認してください。

アプリケーション log を解析する特権 job では、最初の解析の後も信頼できない field をたどってください。低権限アカウントは、現在の process group を通じて log に書き込めたり、log に記録される request field に影響を与えたりすることがあります。その record が image を選び、その metadata が XML を開くための2つ目の pathname になる場合があります。job の有効な実行ユーザー、実際の log 書き込み権限、delimiter の処理、canonical path の containment、選択される XML が攻撃者の制御下にあるかを確認してください。外部 entity expansion の結果が低権限ユーザーにも読める出力に届く場合、2つ目の読み取りを特権ファイル漏えいに利用できます。[Java XML processing security guide](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) では、外部 DTD/entity access の制御方法が説明されています。インストール済み parser と有効な設定を調べてください。書き込み可能な log や XML file だけでは手がかりにすぎません。列挙中にスケジュール済み parser に入力を渡さず、code と metadata を確認してください。

別ユーザーの Git repository から file を生成する特権 job も調べてください。script が `git checkout` ではなく `git ls-tree` と `git cat-file` を使っていても、staging directory に連結する attacker-controlled tree path を信頼することがあります。書き込む前に宛先を正規化し、containment を確認しなければ、absolute path や `..` component によってその directory の外に出られる可能性があります。`git -c safe.directory=*` は、所有者が異なる repository へのアクセスを許可しますが、それだけで任意の書き込みが可能になるわけではありません。

root で実行される database backup によって、別の所有権境界が生じることもあります。PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) は、source data directory 内に置かれた追加の regular file をコピーします。また、デフォルトの plain format では `-D` に directory tree として file を書き込みます。低権限アカウントがこれらの source file を作成または変更できる場合、生成先の所有者と mode、その path に traverse と execute が可能か、mount に `nosuid` が設定されているかを調べてください。set-ID permission が保持された root 所有の copy は危険な場合があります。tar のみの backup、permission の削除、またはアクセス不能な生成先では、同じ経路は成立しません。backup command を問題と判断する前に、スケジュール済み wrapper と有効な実行ユーザーをたどってください。

## 短時間の処理を観察する

数ミリ秒で実行される job は、1回の process snapshot では見逃すことがあります。timer/cron の宣言を log と照合し、許可を得た場合は `pspy` や audit などで process event を監視してください。スケジュールの所有者、正確な command line、task が読み書きする file を照合します。loopback の scheduler web UI は別の interface です。[Crontab UI の例](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc)を参照してください。
