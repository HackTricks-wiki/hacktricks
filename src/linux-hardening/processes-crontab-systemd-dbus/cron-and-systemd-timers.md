# Tareas cron y timers de systemd

{{#include ../../banners/hacktricks-training.md}}

Las tareas programadas pueden ejecutarse con una identidad y un entorno distintos de los del shell actual. Enumera cron, `at`, anacron y los timers de systemd; luego rastrea cada comando programado a través de sus scripts, imports, directorio de trabajo y entradas modificables.

## Enumerar programaciones

```bash
crontab -l 2>/dev/null
ls -la /etc/crontab /etc/cron.* /var/spool/cron* 2>/dev/null
atq 2>/dev/null
systemctl list-timers --all 2>/dev/null
```

Los crontabs del sistema suelen incluir un campo de usuario; el crontab de un usuario, no. Inspecciona el PATH efectivo y el entorno del planificador real. `run-parts --test /etc/cron.daily` muestra qué nombres de archivo se seleccionarían en ese host. Los caracteres de control pueden ocultar una entrada en una salida superficial, así que usa `cat -A` o `sed -n l` cuando un horario parezca sospechoso.

## Rastrea la resolución de archivos y comandos privilegiados

```bash
systemctl cat <name>.timer <name>.service
systemctl show <name>.service -p User -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/to/scheduled/script
```

Revisa las cadenas de scripts con permisos de escritura, las rutas de `EnvironmentFile=`, los drop-ins, los symlinks, los comandos relativos, la expansión de comodines y los binarios que una tarea privilegiada copia o ejecuta. Un timer puede activar un servicio con otro nombre mediante su ajuste `Unit=`. Las páginas de [PATH](../linux-basics/linux-environment-variables.md#path), [wildcard](../interesting-files-permissions/wildcards-spare-tricks.md) y [file-link](../main-system-information/filesystem-links-and-file-descriptors.md) explican los principales elementos básicos.

Para un script programado de `chkrootkit` que se ejecuta como root, inspecciona el código fuente instalado para detectar el antiguo [defecto de comillas en slapper-loop (CVE-2014-0476)](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2014-0476): un `file_port=$file_port $i` sin comillas, después de comprobar una ruta temporal de `SLAPPER_FILES`, puede ejecutar ese archivo. Verifica el script real o el parche del proveedor, la programación con root, el acceso de escritura de un usuario de menor privilegio a la ruta temporal exacta, si el archivo es ejecutable y la política de montaje. Una cadena de versión o la mera presencia de `chkrootkit` no demuestra que la ruta sea explotable; no crees ni ejecutes un archivo temporal durante una revisión pasiva.

Sigue un salto más entre unidades cuando el servicio root de un timer ejecuta `systemctl restart <other>.service`: la unidad reiniciada puede invocar un shell con un script en el que un usuario de menor privilegio puede escribir. Confirma el `User=`, `DynamicUser=`, `RootDirectory=`/`RootImage=`, los argumentos exactos de `ExecStart=` y los permisos del script y de su ruta padre. Un script con permisos de escritura es solo un candidato hasta que el timer y el servicio reiniciado estén activos en ese contexto de ejecución; inspecciona las propiedades de las unidades sin reiniciar ninguno de los servicios.

Si un trabajo con privilegios más altos obtiene un script mediante un hostname y pasa la respuesta a un shell, comprueba quién controla la resolución de ese hostname, además del script remoto. Un archivo `/etc/hosts` con permisos de escritura, incluso si el acceso se concede mediante un grupo o una ACL, puede redirigir un nombre que el trabajo resuelve localmente; una respuesta de `curl` solo se convierte en una ruta de ejecución entre usuarios cuando el comando programado realmente ejecuta esa respuesta y el trabajo usa la ruta de resolución afectada. Verifica la identidad de ejecución del trabajo, la URL exacta y el pipeline del shell, el comportamiento efectivo del proxy/DNS y los permisos del archivo y de su directorio padre. Un archivo hosts con permisos de escritura por sí solo es una señal para revisar, no una prueba de que exista un consumidor privilegiado. Inspecciona la programación y los metadatos sin cambiar la asignación ni obtener el script durante el reconocimiento.

Una descarga privilegiada programada con `wget` es un límite de escritura de archivos independiente, aunque el cuerpo descargado nunca se ejecute directamente. [GNU Wget 1.18 cambió el manejo predeterminado del nombre de archivo en redirecciones HTTP a FTP para corregir CVE-2016-4971](https://lists.gnu.org/archive/html/info-gnu/2016-06/msg00004.html); las versiones antiguas afectadas podían usar el nombre de archivo de la redirección FTP, mientras que `--trust-server-names` solicita explícitamente ese comportamiento. Si una parte con menor nivel de confianza controla la respuesta HTTP y el recurso FTP, comprueba si el trabajo sigue esa redirección, la versión real de Wget o el backport del proveedor, las opciones de salida, la identidad de ejecución, el directorio de trabajo y si el nombre de destino puede convertirse en un archivo de inicio. [Wget carga `WGETRC` o `$HOME/.wgetrc`](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Location.html), y [sus ajustes pueden seleccionar una fuente POST o una ruta de salida](https://www.gnu.org/software/wget/manual/html_node/Wgetrc-Commands.html); una descarga privilegiada posterior es un requisito distinto para cualquier divulgación o escritura resultante. El acceso a un puerto bajo mediante `authbind` solo es relevante cuando quien lo invoca realmente puede servir la URL que solicita el trabajo. Revisa la configuración y los logs de forma pasiva, sin servir una redirección ni ejecutar el trabajo. El [acceso a dispositivos de bloques sin procesar mediante el grupo `disk`](../user-information/interesting-groups-linux-pe/README.md#disk-group) es independiente de esta ruta de descarga de red.

Sigue también los archivos de datos, no solo los scripts. Una herramienta de simulación u orquestación programada puede leer un archivo YAML que define los procesos que debe iniciar; si un usuario de menor privilegio puede editar ese archivo y el trabajo lo ejecuta bajo otra cuenta, los datos pueden convertirse en comandos ejecutados con la identidad del trabajo. Verifica el comando programado exacto, el usuario efectivo, la ruta del archivo, la semántica del parser y el acceso de escritura (incluidos los directorios padre) antes de considerar un archivo YAML modificable como una ruta de ejecución. Para un triaje pasivo basta con leer la programación y los metadatos del archivo; no ejecutes el trabajo ni modifiques su entrada durante el reconocimiento.

La configuración de un cliente SSH también es una entrada ejecutable cuando un trabajo con privilegios más altos ejecuta `ssh -F` con un archivo que puede reemplazar un usuario de menor privilegio. [`ProxyCommand`](https://man.openbsd.org/ssh_config#ProxyCommand) de OpenSSH ejecuta un comando local mediante el shell del cliente, mientras que `Host`/`Match` y las opciones anteriores determinan si se aplica esa directiva. Antes de considerarlo una ruta de ejecución entre usuarios, correlaciona la invocación SSH programada exacta, la identidad de ejecución, la ruta de configuración seleccionada, los permisos de escritura del directorio y del archivo, y el orden efectivo de las opciones. Revisa estos registros sin ejecutar el trabajo ni cargar la configuración no confiable como la cuenta privilegiada.

Un `scp` programado seguido de `ssh` para ejecutar el script copiado requiere una segunda revisión del límite de confianza cuando un usuario de menor privilegio controla el servicio SSH de destino. Si ese servicio puede reenviar la conexión a otro host, el cliente privilegiado podría autenticarse en un endpoint no previsto; [`StrictHostKeyChecking no`](https://man.openbsd.org/ssh_config#StrictHostKeyChecking) debilita la protección contra cambios en la host key, sujeto a las restricciones restantes de OpenSSH y a las opciones efectivas por host. Determina la identidad de ejecución del trabajo, el destino real y el método de autenticación, la identidad efectiva del comando remoto y si la misma ruta de destino se puede escribir o ya existe en el host redirigido. La ejecución de un archivo antiguo o controlado por un atacante requiere, además, que la copia falle o no llegue a esa ruta **y** que el wrapper continúe con su comando SSH; [`errexit` de Bash](https://www.gnu.org/software/bash/manual/html_node/The-Set-Builtin.html) y el manejo explícito del estado afectan ese flujo. Un ajuste débil de host key, un proceso `sshpass` visible o un directorio temporal con permisos de escritura no demuestran por sí solos esta cadena. Inspecciona la programación, el script, la configuración SSH y los metadatos de los archivos sin redirigir el servicio ni activar el trabajo durante el reconocimiento.

Un scheduler de aplicaciones privilegiado puede obtener sus trabajos de filas de base de datos en lugar de archivos modificables. Por ejemplo, una entrada de cron de root que invoque [`php artisan schedule:run`](https://laravel.com/docs/9.x/scheduling#running-the-scheduler) de Laravel puede llegar a código de aplicación que lee filas de tareas. Si una cuenta de menor privilegio puede escribir una fila que contiene una ruta local, y el callback programado llama a [`file_get_contents`](https://www.php.net/manual/en/function.file-get-contents.php) de PHP bajo root y envía el cuerpo obtenido a un webhook especificado en la fila, eso constituye una ruta privilegiada de divulgación de archivos. Verifica la identidad de cron, el callback real del scheduler y el flujo de datos desde la fila hasta la ruta, los permisos de escritura en la base de datos, la validación que se realiza después de leer la fila y el destino de salida. Un `.env` de aplicación legible solo es una pista sobre credenciales; la validación de un formulario web o una contraseña de base de datos no demuestran por sí solas el control de la fila ni la divulgación. Inspecciona la programación, el código y los permisos del archivo de credenciales de forma pasiva, sin consultar la base de datos ni programar una tarea durante el reconocimiento.

Los trabajos de `incron` activados por eventos requieren la misma revisión: las [entradas de incrontab](https://manpages.debian.org/testing/incron/incrontab.5.en.html) asocian una ruta observada y un evento con un comando que se ejecuta con la identidad del propietario de la tabla. Un usuario de menor privilegio puede influir indirectamente en un archivo observado cuando una aplicación sigue un link desde un directorio modificable y escribe texto controlado por un atacante en el destino observado. Verifica el propietario real de la tabla, el evento, los permisos del destino y sus directorios padre, cómo sigue la aplicación los links y cómo ese texto se convierte en argumentos del comando. En particular, [GNU Mailutils `mail` acepta `--exec`](https://mailutils.org/manual/html_node/Invoking-Mail.html), y su [comando de escape al shell](https://mailutils.org/manual/html_node/Shell-Escapes.html) puede ejecutar un programa; un campo no confiable pasado como una opción independiente a esa implementación puede permitir la ejecución de comandos. Otras implementaciones de `mail` o un límite fijo y entrecomillado para los argumentos pueden comportarse de otra manera. Inspecciona la programación, el código de la aplicación y los metadatos de los archivos sin modificar el archivo observado ni activar el trabajo durante el reconocimiento.

Un log observado también puede cruzar un límite entre usuarios mediante un script auxiliar. Si una cuenta de menor privilegio puede escribir el log y el propietario de `incron` lee un campo y lo incluye en una nueva cadena de comandos [`sh -c`](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html), el shell vuelve a analizar ese campo con la identidad del propietario. Comprueba el evento observado exacto, los permisos del log y de su directorio padre, la ruta del auxiliar, la transformación del campo del log y si se llega a ejecutar el comando resultante. Ver un log modificable y una entrada de `incron` no demuestra por sí solo el flujo de datos; no escribas una línea de activación ni ejecutes el auxiliar durante el reconocimiento pasivo.

Los trabajos de renovación de certificados pueden cruzar el mismo límite. Un auxiliar privilegiado puede leer el subject X.509 de un certificado en un directorio modificable por un usuario de menor privilegio e insertar su common name en una nueva cadena de comandos `bash -c`. [OpenSSL puede mostrar el subject de un certificado y comprobar su vencimiento](https://docs.openssl.org/3.3/man1/openssl-x509/); [Bash analiza la cadena de `-c` como entrada del shell](https://www.gnu.org/software/bash/manual/html_node/Invoking-Bash.html), por lo que entrecomillar la variable en el script externo no protege del segundo análisis. Confirma la identidad programada, la ruta de entrada exacta y los permisos de escritura, la rama de renovación y el flujo de datos hacia `bash -c` antes de considerarlo una inyección de comandos. Inspecciona el script y los metadatos del certificado de forma pasiva; no actives la renovación durante el reconocimiento.

El mismo segundo análisis puede ocurrir cuando un trabajo privilegiado programado extrae un nombre del archivo de un usuario de menor privilegio y lo pasa a `xargs -I` para insertarlo en una cadena de comandos `sh -c`. [`xargs -I` de GNU reemplaza el marcador de posición en los argumentos iniciales](https://www.gnu.org/software/findutils/manual/html_node/find_html/xargs-options.html), y [`sh -c` interpreta su cadena de comandos](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html). Aunque el script externo entrecomille el nombre extraído, eso no hace seguro un programa de shell sustituido posteriormente. Verifica la identidad de ejecución del trabajo, la ruta de entrada aceptada exacta y los permisos de escritura, la validación del archivo y las condiciones de la rama, y el flujo de datos del nombre al shell. Un directorio de subida modificable o una invocación de `xargs` por sí solos son solo pistas; inspecciona la programación, el script y los metadatos de la ruta sin enviar un paquete ni ejecutar el trabajo durante el reconocimiento.

Un importador programado de fuentes o imágenes también puede confiar en nombres *dentro* de un archivo proporcionado por quien lo llama, incluso si el nombre externo de la subida está restringido. FontForge corrigió la inyección de comandos mediante nombres de miembros del archivo en su [cambio upstream para CVE-2024-25081 y CVE-2024-25082](https://github.com/fontforge/fontforge/pull/5367). Confirma que un trabajo con privilegios más altos realmente abre un archivo desde una ruta modificable por un usuario de menor privilegio, su identidad de ejecución, la versión exacta de FontForge o el backport del proveedor y la ruta de código que maneja el archivo. Una cadena de versión o una extensión de subida permitida no demuestra que vaya a ejecutarse. Inspecciona la programación, los permisos de la ruta y los metadatos de la versión sin importar un archivo no confiable durante el reconocimiento.

Los scanners de red programados pueden cruzar un límite distinto cuando un script personalizado trata el subject de un certificado TLS remoto como un nombre de archivo local. [Nmap NSE ejecuta los scripts seleccionados sin sandbox](https://nmap.org/book/nse-usage.html), así que inspecciona el script real y comprueba si une un campo subject no confiable a un directorio de datos sin verificar que la ruta permanezca dentro de él. La divulgación de archivos requiere un destino que el scheduler vaya a escanear, una ruta que se resuelva a un archivo legible por la identidad de ejecución del scanner y un informe o log que se entregue a un usuario de menor privilegio. Un campo de certificado o la mera presencia de un scanner instalado no demuestra esa cadena; revisa la programación, el script, la resolución de la ruta y el destino del informe sin escanear un destino nuevo durante el reconocimiento pasivo.

Un comando de cron privilegiado que pasa un glob de shell como `/path/to/tasks/*.yml` a un ejecutor de Ansible requiere revisar los permisos del directorio, aunque todos los playbooks existentes sean de solo lectura. Un usuario con permisos de escritura y búsqueda en el directorio al que apunta el glob podría crear otro playbook que coincida. [Los playbooks de Ansible definen las tareas que ejecuta el runner](https://docs.ansible.com/projects/ansible/latest/cli/ansible-playbook.html), pero un wrapper personalizado puede filtrar las rutas o usar otra identidad: verifica su comportamiento, el usuario real de cron, la expansión del shell, las ACL, el sticky bit y la política de montaje antes de considerar el directorio una ruta de ejecución. Inspecciona los metadatos y el wrapper estáticamente; no ejecutes el trabajo programado durante el reconocimiento.

Un wrapper privilegiado de cron puede pasar nombres de archivo de un directorio de subida a un auxiliar de Perl después de expandir un glob. El operador [`<>` de Perl usa `open` de dos argumentos](https://perldoc.perl.org/perlop#The-Null-Filehandle), así que un nombre coincidente interpretado como un comando de pipe puede ejecutarse con la identidad del auxiliar; [`<<>>` trata los argumentos como nombres de archivo literales](https://perldoc.perl.org/perlop#The-Null-Filehandle). Confirma la identidad del scheduler, el directorio de trabajo y el glob del wrapper, cómo maneja realmente `@ARGV` el auxiliar, las restricciones sobre nombres de archivo y si una identidad de menor privilegio puede colocar un nombre coincidente mediante permisos del sistema de archivos o un servicio de subida autenticado. Una línea de cron, un script de Perl o un directorio FTP modificable no demuestran por sí solos la cadena completa. Inspecciona el código fuente y los metadatos sin enviar un nombre de archivo manipulado ni ejecutar el trabajo durante el reconocimiento.

Un script de cron de solo lectura se puede reemplazar si la cuenta programada lo ejecuta mediante su ruta y un usuario de menor privilegio puede escribir en su directorio padre, que no tiene sticky bit, y atravesarlo. Comprueba la identidad de ejecución de la programación, todos los componentes de la ruta, el sticky bit del directorio, las ACL y la política de montaje; revisa los metadatos sin mover el archivo ni ejecutar el trabajo.

Un wrapper privilegiado de cron en PHP puede llegar a un auxiliar que todavía no existe. Si llama a [`exec()`](https://www.php.net/manual/en/function.exec.php) de PHP con una ruta absoluta fija al auxiliar, un usuario de menor privilegio que pueda crear ese nombre en el directorio padre puede controlar lo que ejecutará una ejecución posterior. Confirma que la entrada de cron realmente ejecuta el wrapper con la identidad de mayor privilegio, la cadena de comandos exacta y la política de ejecución de PHP, los permisos de escritura y búsqueda en el directorio del auxiliar, el comportamiento de los symlinks y del sticky bit, y si la ruta del auxiliar sigue sin existir. Un directorio modificable o un auxiliar inexistente por sí solos son solo pistas; inspecciona la programación, el código fuente y los metadatos de la ruta sin crear el auxiliar ni activar el trabajo.

Un trabajo programado también puede descubrir scripts de entrada con `find` y pasar cada uno a un intérprete. Por ejemplo, la función `system()` de [gnuplot invoca un shell](https://gnuplot.sourceforge.net/docs_6.0/gnuplot.pdf), así que un trabajo privilegiado que ejecuta `gnuplot` con cada archivo `*.plt` de un directorio modificable por un usuario de menor privilegio puede ejecutar comandos con la identidad del trabajo. [El permiso de lectura del directorio controla su listado, mientras que los permisos de escritura y búsqueda (`x`) controlan la creación y el acceso a nombres conocidos](https://www.gnu.org/software/coreutils/manual/html_node/Mode-Structure.html); comprueba los permisos de escritura y búsqueda aunque `ls` no pueda listar el directorio. Correlaciona la identidad y el comando exactos del scheduler, el comportamiento del intérprete, el patrón de archivos seleccionado y los permisos del directorio; un directorio modificable o un intérprete instalado no demuestran por sí solos una escalada. Los schedules privados y los trabajos de corta duración pueden requerir observación autorizada de eventos, ya que una sola captura de procesos puede no detectarlos.

En un trabajo privilegiado de PHP, inspecciona las instrucciones literales `include`/`require` como parte de la cadena de scripts ejecutables. [PHP evalúa los archivos incluidos](https://www.php.net/manual/en/function.include.php), así que un archivo `.php` modificable por el grupo puede ejecutar código con la identidad del trabajo aunque el script principal sea de solo lectura. Verifica la identidad programada, la resolución efectiva de include-path, los permisos del archivo y del directorio, y si el trabajo realmente se ejecuta; una línea de cron de ejemplo en un comentario es solo una pista. La misma revisión se aplica a un [servidor integrado de PHP](https://www.php.net/commandline.webserver) propiedad de root, iniciado con `-S` y `-t <document-root>`: un listener de loopback aún puede ejecutar PHP de la aplicación ante solicitudes locales. Inspecciona el proceso y el código fuente sin activar ninguno de los dos mecanismos durante el reconocimiento.

Un trabajo privilegiado de PHP también puede cruzar el límite mediante un **archivo de datos**: si un usuario de menor privilegio puede cambiar el archivo exacto que se pasa a [`unserialize()`](https://www.php.net/manual/en/function.unserialize.php), PHP puede invocar el método `__wakeup()` o `__unserialize()` de una clase cargada al restaurar un objeto. Revisa la identidad efectiva del trabajo, los permisos del archivo y de sus directorios padre, las clases cargadas y los efectos secundarios reales de esos métodos, como una escritura de archivo determinada por una propiedad. Un log modificable o una llamada a `unserialize()` por sí solos no demuestran que exista una ruta utilizable. Inspecciona el código fuente y los metadatos sin escribir una entrada serializada ni ejecutar el trabajo durante el reconocimiento.

Una tarea de cron de root puede invocar el **CLI page runner** de una aplicación PHP en vez del servidor web. Sigue la raíz de documentos y el URI seleccionados por el runner hasta el punto de entrada PHP real; si la cuenta del servicio web puede modificar ese punto de entrada, la solicitud CLI programada puede ejecutar el código modificado como root aunque el runner y el wrapper de cron sean de solo lectura. Confirma la identidad del scheduler, la resolución exacta del URI al archivo, los permisos efectivos del archivo y sus directorios padre, y si un control de integridad protege el propio punto de entrada. Inspecciona el código fuente y los metadatos sin invocar el runner ni modificar la página durante el reconocimiento.

Un proceso `ipython` iniciado por un trabajo programado o por otro usuario desde un directorio de trabajo compartido requiere revisar sus archivos de inicio. Las [notas de seguridad de IPython](https://ipython.readthedocs.io/en/8.25.0/whatsnew/version8.html#ipython-8-0-1-cve-2022-21699) explican que las versiones afectadas buscaban perfiles y configuración en el directorio actual, incluido el código de `profile_default/startup`, antes de la corrección de CVE-2022-21699. Correlaciona la versión instalada real o el parche del proveedor, el directorio de trabajo del comando, la identidad del proceso con privilegios más altos y la posibilidad de que un usuario de menor privilegio escriba y busque en la ruta exacta de inicio. Tener `ipython` instalado, un directorio modificable o una cadena de versión no demuestra por sí solo que otra identidad vaya a cargar un archivo de ahí. Inspecciona la programación y los metadatos de la ruta sin iniciar el intérprete con privilegios más altos.

Para un servidor PHP privilegiado que llama a funciones de una extensión nativa personalizada, sigue el SAPI de PHP del servicio y su `php.ini` efectivo, además de los archivos `.ini` explorados, antes de revisar la extensión. [PHP carga las bibliotecas `extension` configuradas al iniciarse](https://www.php.net/manual/en/ini.core.php), y [los SAPI de CLI y web pueden usar archivos de configuración distintos](https://www.php.net/manual/en/configuration.file.php). Por lo tanto, un formulario de inicio de sesión accesible o un listener local puede pasar cadenas controladas por el usuario a código compilado que se ejecuta con la identidad del servicio. Registra el `User=`, `ExecStart=`, directorio de trabajo, ruta real de la extensión y argumentos controlables por quien llama de la unidad; la mera presencia de un `.so` o un socket de loopback no demuestra una vulnerabilidad de corrupción de memoria. Analiza por separado cualquier parser personalizado en lugar de enviar probes durante el reconocimiento pasivo.

Cuando un wrapper privilegiado calcula el hash de un script por su ruta y luego vuelve a abrir esa ruta para ejecutarlo, el digest solo autentica el objeto leído durante la primera apertura. Si un usuario de menor privilegio puede reemplazar la entrada del directorio del script entre esas aperturas, la ejecución posterior puede resolver un objeto distinto aunque el archivo de script original sea propiedad de root. Un FIFO puede alargar la fase de comprobación, pero la ruta depende de permisos reemplazables en los directorios padre, de que realmente haya dos aperturas separadas, de la identidad del scheduler, de las reglas del sticky bit y del montaje, y del momento de la operación. Inspecciona el wrapper y la salida de `namei -l` como pista pasiva; una suma de comprobación correcta no demuestra que la ruta posterior esté protegida.

Un trabajo de backup privilegiado también puede **divulgar** datos sin ejecutar comandos proporcionados por un atacante. Investiga si un usuario de menor privilegio puede crear un archivo de control que lea el trabajo, si luego el trabajo abre una fuente protegida como `/etc/shadow` y si una URL seleccionada por el atacante o una salida legible recibe el resultado. Verifica las tres partes antes de considerarlo una ruta de divulgación. Un comando de shell fijo en el mismo script no convierte por sí solo ese archivo de control en una entrada de inyección de shell. Inspecciona el script y los permisos de los archivos sin ejecutar el trabajo ni colocar un archivo de control durante el reconocimiento.

Si un trabajo privilegiado programado ejecuta `curl -K FILE` o `curl --config FILE`, [curl trata las opciones de ese archivo como argumentos de línea de comandos](https://curl.se/docs/manpage.html). Un usuario de menor privilegio que controle el archivo exacto cuando curl lo lea puede influir en la URL solicitada, la entrada de un archivo local o la ruta de salida. Confirma la identidad efectiva del trabajo, los permisos de escritura del archivo y de sus directorios padre, el momento de cualquier otro trabajo que reemplace el archivo y cómo interactúan las opciones de configuración con las opciones fijas de la línea de comandos antes de afirmar que se puede leer o escribir un archivo protegido. Una ruta de configuración modificable o un indicador `-K` visible no demuestran por sí solos que las opciones elegidas surtan efecto; inspecciona la programación y los metadatos sin ejecutar el trabajo ni obtener una URL durante el reconocimiento pasivo.

Si una entrada de cron invoca un script auxiliar, inspecciona también el directorio de trabajo del auxiliar y el comando de archivado. Un comodín sin comillas sobre un directorio modificable por otro usuario puede convertir los nombres de archivo en opciones del archivador; las acciones de checkpoint de GNU tar son un ejemplo. Confirma la identidad de ejecución programada, el directorio de entrada modificable, el archivador y las opciones exactos, y si `--` termina el análisis de opciones antes de afirmar que existe una ruta de comandos entre usuarios. Consulta el comportamiento de [wildcard y tar](../interesting-files-permissions/wildcards-spare-tricks.md).

Puede producirse una divulgación independiente de archivos de backup cuando un auxiliar privilegiado ejecuta `cd INPUT_DIR; tar ... *` sin comprobar si `cd` tuvo éxito. Si un usuario de menor privilegio puede eliminar o reemplazar `INPUT_DIR`, un `cd` fallido puede dejar el shell en el directorio anterior, que el comando de archivado posterior podría leer. Verifica el directorio de trabajo inicial del trabajo, una ruta real de fallo de `cd`, si el script termina o usa `&&`, las opciones exactas del archivador y si el archivo de salida es legible por el usuario de menor privilegio. Un directorio de entrada modificable o un archivo de backup legible por sí solos son solo pistas; inspecciona el auxiliar y los permisos de la ruta sin cambiar el trabajo activo.

Un ejecutable programado puede ocultar un script de shell sin eliminar su límite de confianza: [SHc](https://github.com/neurobin/shc) envuelve texto de script cifrado en un binario nativo y lo ejecuta mediante un shell en tiempo de ejecución. Un sufijo `.sh.x` o un ELF opaco solo son pistas para revisar. Para evaluar la inyección de opciones mediante nombres de archivo, determina la identidad privilegiada del scheduler, el directorio de trabajo y el comando reales del auxiliar, si un usuario de menor privilegio puede crear nombres coincidentes allí y si un glob sin comillas llega a un comando como `rsync` sin un límite de opciones. La [opción remote-shell de `rsync`](../interesting-files-permissions/wildcards-spare-tricks.md#rsync) solo es relevante si se usa esa ruta exacta del comando. La visibilidad restringida de `/proc` o el fallo del descifrado estático dejan el comando sin determinar; no ejecutes el auxiliar privilegiado solo para clasificarlo.

El texto de la línea de comandos de un proceso es otra entrada no confiable para un auxiliar privilegiado. Un usuario de menor privilegio puede elegir un título de proceso o un `argv[0]` que coincida con `pgrep -f`; un nombre coincidente no autentica el ejecutable ni a su propietario. Si un script ejecutado como root captura ese texto, lo transforma parcialmente en `apache2ctl`/`httpd` y ejecuta el resultado sin un array fijo de argumentos, las opciones elegidas por el atacante pueden seleccionar otro directorio de configuración o un log de errores. El análisis de configuración de Apache puede cargar módulos o llegar a auxiliares configurados, así que no valides una configuración no confiable como root durante el reconocimiento. Inspecciona el propietario del scheduler, el auxiliar exacto, la identidad del proceso y el flujo de datos a los argumentos; se trata de una inyección de opciones/configuración, salvo que se demuestre por separado la ejecución de metacaracteres del shell.

Un parser ejecutado como root que introduce texto no confiable en la aritmética de Bash puede ejecutar sustituciones contenidas en ese texto. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#bash-arithmetic-expansion-injection-in-cron-log-parsers) ofrece un ejemplo desarrollado. Confirma el origen de la entrada y el comando de análisis antes de considerar explotable cualquier expresión aritmética.

En un trabajo privilegiado que analiza un log de aplicación, sigue los campos no confiables más allá del primer análisis. Una cuenta de menor privilegio podría escribir en el log a través de su grupo de procesos actual o influir en los campos de solicitud registrados; después, un registro podría seleccionar una imagen cuyos metadatos se conviertan en una segunda ruta para abrir XML. Comprueba la identidad efectiva del trabajo, el acceso real de escritura al log, el manejo de delimitadores, la contención de la ruta canónica y si el XML seleccionado está bajo control del atacante. La expansión de entidades externas puede convertir esa segunda lectura en una divulgación privilegiada de archivos si el resultado expandido llega a una salida legible por un usuario de menor privilegio. La [guía de seguridad del procesamiento XML de Java](https://docs.oracle.com/en/java/javase/17/security/java-api-xml-processing-jaxp-security-guide.html) documenta controles para el acceso a DTD/entidades externas; inspecciona el parser instalado y sus ajustes efectivos. Un log modificable o un archivo XML por sí solo son solo pistas. Revisa el código y los metadatos sin proporcionar datos al parser programado durante el reconocimiento.

Inspecciona también los trabajos privilegiados que materializan archivos desde el repositorio Git de otro usuario. Un script puede usar `git ls-tree` y `git cat-file` en vez de `git checkout`, pero aun así confiar en rutas de árbol controladas por el atacante al unirlas con un directorio de staging. Las rutas absolutas y los componentes `..` pueden escapar de ese directorio, a menos que el destino se normalice y se compruebe que permanece dentro de él antes de escribir. `git -c safe.directory=*` permite acceder a repositorios con distintos propietarios; no crea por sí solo la condición de escritura arbitraria.

Un backup de base de datos ejecutado como root puede crear otro límite de propiedad. PostgreSQL [`pg_basebackup`](https://www.postgresql.org/docs/14/app-pgbasebackup.html) copia los archivos regulares adicionales que haya en el directorio de datos de origen, y su formato plain predeterminado escribe los archivos en `-D` como un árbol de directorios. Si una cuenta de menor privilegio puede crear o modificar esos archivos de origen, inspecciona la propiedad y el modo del destino resultante, si se puede recorrer y ejecutar su ruta y si el montaje tiene `nosuid`. Una copia propiedad de root que preserve permisos set-ID puede ser peligrosa; un backup solo en formato tar, permisos eliminados o un destino inaccesible no demuestra la misma ruta. Sigue el wrapper programado y el usuario efectivo antes de considerar que el comando de backup constituye un hallazgo.

## Observar trabajos de corta duración

Una sola captura de procesos puede pasar por alto un trabajo que se ejecuta durante milisegundos. Compara las declaraciones de timer/cron con los logs y, cuando esté autorizado, con la monitorización de eventos de procesos, por ejemplo `pspy` o audit. Correlaciona el propietario programado, la línea de comandos exacta y los archivos que lee o escribe la tarea. Una interfaz web de scheduler en loopback es una interfaz aparte; consulta el [ejemplo de Crontab UI](../linux-basics/linux-privilege-escalation/README.md#crontab-ui-alseambusher-running-as-root--web-based-scheduler-privesc).
