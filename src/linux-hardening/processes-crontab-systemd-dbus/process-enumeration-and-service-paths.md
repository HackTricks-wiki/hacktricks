# Enumerazione dei processi e percorsi dei servizi

{{#include ../../banners/hacktricks-training.md}}

La domanda utile è quale processo privilegiato utilizza dati o codice che un utente con privilegi inferiori può influenzare. Esamina l’albero dei processi, l’ambiente attivo, i file aperti e l’unità o lo script che ha avviato ciascun processo candidato.

## Mappare i processi e la proprietà

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Una relazione padre-figlio tra utenti diversi può essere normale, ma una transizione inattesa richiede di esaminare il comando del processo padre, gli argomenti, l'eseguibile, la directory di lavoro e i file a cui fa riferimento. Usa [users and sessions](../user-information/user-and-session-triage.md) per interpretare il proprietario e il contesto di login.

### Console di macchine virtuali locali

Esamina le opzioni `-spice` di un processo QEMU insieme all'indirizzo su cui è in ascolto. La [documentazione di QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) specifica che `disable-ticketing` consente ai client SPICE di connettersi senza autenticazione. Un listener associato all'indirizzo loopback può comunque essere raggiungibile da altri utenti locali dell'host. Verifica il listener attivo, le opzioni di autenticazione e l'accesso locale prima di considerare la riga di comando una console esposta. Il controllo della console riguarda il **guest**; ottenere un account guest o modificarne lo stato di avvio richiede condizioni distinte lato guest e non conferisce root sull'host di virtualizzazione. Durante l'enumerazione passiva, leggi gli argomenti del processo e i metadati dei socket senza connetterti al guest né riavviarlo.

Un'interfaccia web raggiungibile localmente può eseguire codice con l'account del servizio anche quando la shell iniziale non può accedere ai suoi file. Per esempio, CVE-2023-0297 riguardava la gestione di `/flash/addcrypted2` in pyLoad, quando JavaScript non attendibile veniva passato a Js2Py con le importazioni Python abilitate; la [correzione upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) ha disabilitato `pyimport`. Prima di considerare un processo pyLoad una via di escalation, incrocia le informazioni sul proprietario del processo in esecuzione, l'indirizzo di ascolto, l'esposizione dell'endpoint e la patch installata o il backport del vendor. Il nome di un processo, una porta aperta o la sola versione di un pacchetto non dimostrano l'esposizione; l'enumerazione passiva non deve inviare un payload di esecuzione.

### Shell di login privilegiate che condividono un terminale

Una shell interattiva privilegiata che esegue `su --login <user>` senza uno pseudo-terminale indipendente può lasciare il terminale condiviso con la shell di login dell'utente meno privilegiato. Se il file di avvio di quell'utente è controllabile e il codice al suo interno può usare `TIOCSTI` per iniettare input nel terminale, l'input potrebbe raggiungere la shell privilegiata quando riprende l'esecuzione. Il [manuale di util-linux `su`](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) descrive il rischio legato alla condivisione del terminale e raccomanda `su --pty`/`-P` per l'uso interattivo; `su -c` avvia una sessione separata senza un terminale di controllo. Il rischio dipende dalla shell padre effettiva, dalla relazione tra i terminali, dal file di avvio dell'utente di destinazione e dai criteri del kernel. Il solo nome di un processo o l'argomento `su -l` costituiscono soltanto un'indicazione da approfondire.

Esamina l'albero dei processi osservato e le colonne TTY, quindi il launcher leggibile e la proprietà/i permessi del file di avvio. Su Linux, `/proc/sys/dev/tty/legacy_tiocsti`, se presente, può aiutare a interpretare i criteri; la sua assenza non dimostra che il sistema sia sicuro. Il [manuale Linux `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) segnala che, da Linux 6.2, l'operazione può richiedere `CAP_SYS_ADMIN` quando questo sysctl è impostato su false. Non invocare l'ioctl al solo scopo di enumerare l'host.

In alcuni casi, un account database può modificare il file di avvio dell'utente di destinazione senza accesso diretto in scrittura al filesystem. Il comando PostgreSQL lato server `COPY ... TO 'filename'` scrive come account OS del server database, ma [PostgreSQL limita](https://www.postgresql.org/docs/current/sql-copy.html) questa forma a superuser del database o a ruoli come `pg_write_server_files`. Verifica sia il ruolo database sia i permessi sui file dell'OS del server; una stringa di connessione dell'applicazione, da sola, non concede l'autorizzazione a scrivere file. Nel valutare la catena, considera separatamente il launcher privilegiato e le capacità dell'account database.

## Esaminare gli artefatti runtime

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Gli eseguibili eliminati e i file eliminati ma ancora aperti rimangono referenziati finché non viene chiuso il loro ultimo descrittore. Possono conservare prove o segreti accessibili. Gli ambienti e la memoria dei processi possono contenere credenziali, ma la lettura di un altro processo è soggetta a restrizioni basate sulla proprietà, sulle opzioni di mount di `/proc`, sui criteri Yama per ptrace e su altri controlli di sicurezza. Consulta [file descriptors](../main-system-information/filesystem-links-and-file-descriptors.md) e [post-exploitation credential hunting](../post-exploitation/README.md) per tecniche correlate.

Le tracce syscall salvate costituiscono un altro limite basato sui permessi dei file. [`strace` registra gli argomenti delle syscall in un file di output](https://man7.org/linux/man-pages/man1/strace.1.html), quindi una traccia leggibile di argomenti [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) potrebbe esporre una password passata da un job privilegiato nella riga di comando. Per prima cosa, verifica che l’utente corrente possa leggere la traccia specifica e che l’argomento contenga effettivamente una credenziale; per dimostrare che la credenziale è accettata in una successiva transizione a un altro account Unix occorrono verifiche separate. I metadati dei file sono un utile indizio passivo, senza dover esaminare tutte le tracce o stamparne il contenuto durante l’enumerazione ordinaria.

## Socket privilegiati per l’automazione di office

LibreOffice e OpenOffice possono esporre la propria API UNO tramite un argomento `--accept=socket,host=<host>,port=<port>;urp;`. Un processo office di proprietà di root con un endpoint raggiungibile potrebbe consentire a un utente locale con privilegi inferiori di invocare servizi API nel contesto di sicurezza del processo. Il servizio `SystemShellExecute` include un’operazione per avviare un comando di sistema. Il binding all’indirizzo loopback limita la raggiungibilità remota, ma il socket rimane raggiungibile dagli utenti locali, a meno che un altro controllo non impedisca l’accesso.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Correla il proprietario del processo, l’argomento esatto `--accept` e l’indirizzo e la porta attualmente in ascolto. Un acceptor configurato che non è riuscito a eseguire il bind è solo un indizio; durante l’enumerazione passiva, non connetterti all’API né invocarla. Evita di avviare un’istanza di office con privilegi elevati solo per verificare questa condizione.

## Memoria condivisa System V utilizzata da processi con privilegi

Un helper di proprietà di root può creare un segmento di memoria condivisa System V su cui un altro utente può scrivere. Se in seguito l’helper si fida dei dati contenuti in quel segmento per eseguire un comando shell o un’altra operazione sensibile, il segmento attraversa un confine di privilegi anche se l’eseguibile e i relativi file sono protetti. `shmget()` ricava i permessi di accesso dai nove bit meno significativi dei flag; la modalità `0666` consente agli altri utenti di scrivere, mentre il flag `IPC_CREAT` non restringe tali permessi. Esamina passivamente i segmenti attivi con `ipcs -m` e metti in relazione il proprietario, la modalità e la durata con il processo privilegiato e la gestione del suo input. Un segmento scrivibile da chiunque, da solo, non dimostra l’esecuzione di comandi.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

I segmenti System V sono distinti dai file di memoria condivisa POSIX in `/dev/shm`. Un segmento creato solo per un istante potrebbe non comparire in una singola istantanea di `ipcs`, quindi un output vuoto non esclude un helper che usa la memoria condivisa. Esamina il suo codice sorgente o il comportamento del binario e qualsiasi regola `sudo` che lo avvii; non eseguire l’helper con privilegi elevati solo per far comparire un segmento durante l’enumerazione. La [guida ai namespace IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) spiega come i namespace influiscono sulla visibilità.<sup>[[2]](#references)[[3]](#references)</sup>

## Controlli script dell’agent Consul

Consul può eseguire controlli di integrità tramite script con l’identità del sistema operativo del suo agent. Se un agent viene eseguito come root, abilita `enable_script_checks` e consente a un utente con privilegi inferiori di registrare un servizio con un controllo script tramite l’API HTTP locale, tale utente potrebbe causare l’esecuzione di comandi come root. Associare l’API solo a `127.0.0.1` consente comunque agli utenti locali di raggiungerla. L’impostazione `enable_local_script_checks` è più restrittiva: esclude i controlli script inviati tramite registrazioni all’API HTTP. Quando gli ACL di Consul sono abilitati, la registrazione di un servizio richiede `service:write`; una riga `acl.default_policy=allow`, da sola, non dimostra che un chiamante anonimo possa registrarsi. Esamina insieme l’identità effettiva dell’agent, le impostazioni caricate, l’indirizzo a cui è associata l’API e le autorizzazioni.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Segui gli argomenti `-config-dir` e `-config-file` dell'agent in esecuzione fino alla configurazione pertinente e controlla solo i nomi e le impostazioni dei campi relativi ai controlli degli script e agli ACL. I file di configurazione possono contenere anche chiavi o token gossip: evita di incollarli nei log condivisi. Non registrare un servizio né eseguire un health check solo per individuare questa condizione.

Esiste un percorso separato tramite file locale se un utente con privilegi inferiori può **scrivere e cercare** nella directory indicata da `-config-dir` di un agent eseguito da root: da quella directory potrebbe essere caricato un nuovo servizio definito in un file `.hcl` o `.json`. I permessi di ricerca e scrittura sulla directory possono consentire di aggiungere un file anche quando è vietato elencarne il contenuto. Per confermare l'esecuzione di comandi come root, verifica che l'agent carichi effettivamente quella directory, che l'impostazione *effettiva* dei controlli degli script consenta definizioni locali, che la definizione venga caricata e che l'agent mantenga i privilegi di root. [La documentazione di Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) specifica quali impostazioni e definizioni di health check possono essere ricaricate; per abilitare i controlli degli script potrebbe essere necessario un riavvio, quindi verifica il comportamento della versione installata. Se gli ACL proteggono l'agent, [`consul reload` richiede `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); il solo permesso di scrittura su KV non lo concede. Considera i metadati di una directory scrivibile come un elemento da verificare, non come prova di un reload, riavvio o esecuzione di comandi autorizzati. Esamina percorsi, permessi e policy senza scrivere configurazioni né chiamare l'API.

## Segui la catena di esecuzione del servizio

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Controlla l'unit, i drop-in, `EnvironmentFile=`, gli script helper, i comandi relativi, le directory scrivibili e l'attivazione dei socket. Un'unit di proprietà di root può comunque essere insicura se legge una configurazione o uno script scrivibile dall'utente. La pagina sull'[arbitrary file write](../interesting-files-permissions/write-to-root.md) illustra i comuni percorsi di abuso di servizi e unit. Monitora i job di breve durata con [pspy](https://github.com/DominicBreuker/pspy) o con telemetria di audit/processo quando una singola esecuzione di `ps` non li rileva.

Per un servizio **xinetd** personalizzato, correla le direttive `server`, `user` e i controlli di accesso dello stanza abilitato con il listener attivo e l'eseguibile esatto. L'impostazione [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) sceglie l'identità del processo avviato, mentre un bit set-user-ID sull'eseguibile può modificarne separatamente l'identità effettiva, se [`execve` consente tale transizione](https://man7.org/linux/man-pages/man2/execve.2.html). Un binario privilegiato raggiungibile che accetta input non attendibile merita un'analisi offline del sorgente o del disassemblato per individuare bug di memory safety, come una conversione di stringa [`scanf` senza limiti](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) in un buffer di dimensione fissa. La mappatura del servizio e i metadati set-user-ID sono indizi, non prove della presenza di un bug di questo tipo; non inviare input che provochino crash e non eseguire il debug del servizio privilegiato attivo durante l'enumerazione passiva.

Per un listener privilegiato personalizzato di cui è disponibile il sorgente in lettura, esamina ogni lunghezza controllata dal chiamante usata da un'operazione di copia come [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Controllare solo che l'indice di scrittura corrente rientri in un buffer di dimensione fissa non dimostra che la **lunghezza della copia** rientri nello spazio restante; verifica `copy_length <= capacity - index` dopo aver confermato che l'indice sia entro i limiti, e controlla signedness e overflow aritmetici. È un'indicazione utile per la revisione solo se l'input raggiunge quell'operazione, il listener è accessibile all'utente con privilegi inferiori e il processo mantiene un'identità effettiva superiore. Esamina offline il sorgente e i metadati del processo; non inviare input che provochino crash al servizio attivo durante l'enumerazione.

Nei sistemi che usano **Upstart**, le definizioni dei job di sistema possono trovarsi in `/etc/init/*.conf`. Un file di job scrivibile dall'utente corrente è rilevante se il demone init attivo carica proprio quel job, la direttiva `script` o `exec` viene eseguita con un'identità più privilegiata e l'utente può avviarlo tramite un comando `initctl` consentito o un altro trigger reale. Un'autorizzazione sudo per `initctl`, da sola, non dimostra che un file di job sia scrivibile né che un job modificato verrà eseguito. Durante l'enumerazione, controlla i permessi del file di job esatto, l'impostazione effettiva dell'utente di esecuzione, il demone attivo e il trigger, senza modificare né avviare il job. Consulta i manuali di [configurazione dei job Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) e di [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un file di password per l'autologin leggibile, come `/etc/autologin/passwd` nei sistemi in cui il [job di avvio legge proprio quel percorso](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), è un indizio di esposizione di credenziali. Conferma che il job di avvio sia installato e utilizzi il file, quindi verifica separatamente se la password è valida per un altro account locale o servizio. Il solo nome del file non dimostra il riutilizzo della password; registra percorso e metadati di accesso senza inserire la password nell'output condiviso dell'enumerazione.

La direttiva `ExecStart=` di un'unit o un comando pianificato può rivelare il percorso esatto di uno script contenuto in una directory di cui non è possibile elencare i file. Il [permesso di ricerca della directory](https://man7.org/linux/man-pages/man7/path_resolution.7.html) può comunque consentire all'identità corrente di attraversare quel percorso noto; verifica il permesso di ricerca su ogni directory genitore e il permesso di lettura sul file, invece di presumere che un elenco della directory non riuscito lo protegga. Uno script leggibile può contenere una credenziale per il trasferimento, ma per passare a un altro account è necessario che la credenziale sia ancora valida e accettata indipendentemente da quell'account. Registra il percorso e le evidenze sui permessi senza stampare valori segreti nei log condivisi.

Per uno script CommonJS Node.js pianificato, esamina gli import bare come `require('package')`, anche se lo script stesso è di sola lettura. [Node cerca `node_modules` accanto al file che effettua l'import e poi nelle directory antenate](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), prima di ricorrere ai percorsi globali configurati. Un utente con privilegi inferiori che può **scrivere e cercare** in una di queste directory antenate potrebbe riuscire a creare un package che venga trovato prima. Conferma che l'import esatto venga raggiunto, che il package selezionato non sia un modulo integrato, che il percorso pertinente possa essere creato o modificato, che il modulo venga risolto lì nel runtime installato e che un job con privilegi superiori lo caricherà alla prossima esecuzione. I metadati di una directory genitore scrivibile sono solo un'indicazione per la revisione; esamina passivamente lo script e lo scheduler, senza inserire un modulo né attivare il job.

Un indice di package Python privato è un altro confine di fiducia quando un job automatizzato installa package con un'identità OS diversa. Correlati il job esatto e l'account di esecuzione con l'indice configurato, i nomi dei package selezionati e la possibilità che un utente con privilegi inferiori pubblichi o sostituisca un package che il job installerà effettivamente. La creazione di una source distribution può eseguire il backend di build o il `setup.py` legacy con l'identità dell'installer; l'importazione del package installato è un percorso di esecuzione distinto. Un listener sull'indice, un hash leggibile della password di upload o il solo nome di un package non dimostrano questa catena. Esamina il job, le autorizzazioni dell'indice e la provenienza del package, senza caricare né installare nulla durante l'enumerazione. Consulta le indicazioni di [pip sull'interfaccia del build system](https://pip.pypa.io/en/stable/reference/build-system/) e sulle [installazioni sicure](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agent privilegiato potrebbe interrogare una task queue gestita da un servizio web o container separato. Se un'identità con un livello di fiducia inferiore può scrivere nel database delle task del servizio, determina se quelle righe vengono effettivamente servite a quell'agent e se una command task viene eseguita con l'identità OS dell'agent. Verifica separatamente l'accesso in scrittura al database, la sessione di destinazione o la routing key, l'interrogazione attiva, l'autorizzazione delle task e l'utente effettivo dell'agent. Essere root all'interno di un container non implica di per sé l'accesso come root sull'host; il confine viene superato solo se un consumer con privilegi host esegue dati di task controllati dall'attaccante. Esamina i metadati del processo, del file di database e del servizio senza modificare la queue né inviare una task durante l'enumerazione.

Un job ricorrente potrebbe invece leggere un comando da una riga di configurazione di un database applicativo. Conferma che il ruolo database con privilegi inferiori possa modificare proprio quella riga, che il job attivo la legga dopo la modifica e che il valore raggiunga una shell o un esecutore di comandi equivalente con un'identità OS più privilegiata. L'accesso in scrittura al database o un valore che sembra un comando non dimostrano da soli l'esecuzione; esamina il job e i permessi senza modificare la riga durante l'enumerazione passiva.

Un messaggio in coda può contenere anche un URL anziché codice. Se un consumer privilegiato recupera quell'URL e carica la risposta come plugin Lua o di altro tipo eseguibile, verifica i permessi del publisher sull'exchange e sulla routing key esatti, il binding alla queue consumata, il percorso di recupero e caricamento del plugin e l'identità effettiva del worker. [RabbitMQ instrada i messaggi pubblicati tramite gli exchange](https://www.rabbitmq.com/docs/exchanges); un listener del broker o un login valido, da soli, non dimostrano la consegna a questo worker. Le credenziali del broker in chiaro catturate sono un indizio separato che richiede un accesso effettivo alla cattura dei pacchetti e traffico leggibile; non dimostrano l'autorizzazione alla pubblicazione. Un plugin Lua può invocare comandi shell tramite [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) solo se quell'API è disponibile nel runtime. Esamina configurazione e codice senza catturare traffico, pubblicare messaggi o recuperare un plugin durante l'enumerazione passiva.

Quando un servizio Python privilegiato espone un endpoint HTTP o socket locale, uno script leggibile può rivelare un percorso dall'input al codice anche se i suoi permessi impediscono di modificarlo. Correlati il processo attivo e l'identità dell'unit con lo script esatto, il listener, l'autorizzazione delle route e i campi controllati dal chiamante. Segui quindi quei campi attraverso parsing e validazione fino a un sink dinamico `eval()` o `exec()`. In particolare, costruire un nuovo f-string a partire dal testo della richiesta e valutarlo può interpretare i campi di sostituzione forniti dall'attaccante come espressioni Python (avvertenza Python su [`eval`](https://docs.python.org/3/library/functions.html#eval); [semantica degli f-string](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). La semplice presenza di `eval` o un binding su loopback non dimostrano che un chiamante non attendibile raggiunga il sink; esamina il flusso effettivo dei dati e i controlli di accesso senza inviare un payload di test durante l'enumerazione.

Anche il controllo delle richieste firmate su quella route richiede una revisione specifica. Se il sorgente leggibile deriva la chiave di firma da uno spazio di output dimostrabilmente piccolo o prevedibile e il servizio espone un esempio firmato valido, la firma potrebbe non proteggere più un sink `eval()` privilegiato. Verifica l'esatta derivazione della chiave e il verificatore, l'identità del servizio attivo e l'accesso dei chiamanti locali, nonché se il campo firmato raggiunga il sink; importare il modulo Python [`random`](https://docs.python.org/3/library/random.html) o disporre di una firma di esempio non dimostra nessuna di queste condizioni. Python avverte inoltre che limitare `__builtins__` [non costituisce un confine di sicurezza per input non attendibili a `eval()`](https://docs.python.org/3/library/functions.html#eval). Analizza le chiavi offline e non inviare richieste contraffatte durante l'enumerazione passiva.

Una directory `/etc/systemd/system/<unit>.service.d` vuota ma scrivibile è rilevante anche quando il file dell'unit e tutti i drop-in esistenti sono protetti: l'utente può creare un nuovo override `.conf`. Verifica che l'identità corrente possa scrivere e cercare nella directory, che l'unit sia caricata e venga eseguita come root, e se seguiranno un reload del daemon e un restart. Un'autorizzazione al reload o al restart, un timer o un successivo avvio possono rendere effettiva la modifica; l'accesso in scrittura alla directory, da solo, non la esegue immediatamente.

Per i servizi in esecuzione, segui i percorsi letterali di `EnvironmentFile=` dalla sezione `[Service]` dell'unit, compresi i file il cui nome non inizia con `.env`. Se un utente con privilegi inferiori può leggerne uno, elenca i nomi delle chiavi che sembrano credenziali, come `API_TOKEN` o `APP_SECRET_KEY`, senza stampare i valori nei log condivisi. Quando valuti l'unit effettiva, controlla gli override dei drop-in e i prefissi `-` opzionali. La leggibilità indica una possibile esposizione di credenziali; perché ciò porti a un'escalation, il valore deve comunque essere valido per un'azione privilegiata.

### Elaborazione privilegiata di upload non attendibili

Un file watcher eseguito da root può passare file provenienti da una directory di upload scrivibile dall'utente a un parser o estrattore di breve durata. Segui lo script genitore o il servizio del watcher in esecuzione e conferma la directory esatta, chi può inserirvi file, il comando figlio e i relativi argomenti, nonché l'identità con cui viene eseguito il figlio. Uno snapshot dei processi può mostrare il watcher senza rilevare l'estrattore tra un upload e l'altro. Non inserire un payload di test né attivare il watcher durante l'enumerazione passiva.

Un esempio concreto è la modalità di estrazione (`-e`) di Binwalk che elabora dati PFS controllati dall'attaccante. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) consentiva all'estrattore PFS di scrivere al di fuori della directory prevista, incluso in un percorso di plugin che Binwalk avrebbe potuto caricare in seguito. Il progetto upstream ha incluso la correzione nella versione [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), ma i backport delle distribuzioni possono mantenere una versione visualizzata precedente; prima di valutarne l'applicabilità, controlla lo stato di sicurezza del package installato, ad esempio nel [tracker Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510). La sola versione di Binwalk installata non dimostra un percorso di escalation dei privilegi: l'estrazione deve essere effettivamente avviata da un processo con privilegi superiori su input controllabile dall'utente con privilegi inferiori.

### Build pianificate con dipendenze locali

Un `cargo run` pianificato ricompila il sorgente con l'utente di esecuzione del job. Esamina le dipendenze locali `{ path = "..." }` del manifest e i permessi del sorgente e delle directory genitore di ogni dipendenza, non solo del crate principale. Se un utente con privilegi inferiori può modificare una dipendenza che Cargo compila e il job pianificato esegue il risultato, il codice compilato può essere eseguito con l'identità di esecuzione del job. Conferma il comando effettivo dello scheduler, la directory di lavoro, la risoluzione delle dipendenze e se avverrà una ricompilazione; un file sorgente Rust scrivibile altrove è solo un indizio. Per una verifica passiva iniziale bastano la lettura del manifest e i metadati dei percorsi. Consulta la [documentazione Cargo sulle dipendenze path](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## File framebuffer di Xvfb

`Xvfb -fbdir <directory>` usa file mappati in memoria denominati `Xvfb_screen<n>` per i suoi schermi virtuali. Se il processo Xvfb in esecuzione di un altro utente indica una directory i cui file di schermo sono leggibili dall'utente corrente, il framebuffer può esporre i contenuti del desktop di quell'utente. Conferma insieme il processo, la proprietà dei file e i relativi permessi; il solo fatto che un file sia leggibile non dimostra che sullo schermo siano presenti contenuti utili. Esamina prima i percorsi e i metadati, senza copiare i dati delle immagini nell'output condiviso dell'enumerazione. Il [manuale di Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) documenta il comportamento di `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
