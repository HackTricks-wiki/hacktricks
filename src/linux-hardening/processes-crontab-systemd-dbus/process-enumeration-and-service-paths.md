# Перелік процесів і шляхи служб

{{#include ../../banners/hacktricks-training.md}}

Корисно з’ясувати, який привілейований процес використовує дані або код, на які може впливати користувач із нижчим рівнем привілеїв. Перевірте дерево процесів, поточне середовище, відкриті файли, а також юніт або скрипт, який запустив кожен потенційно вразливий процес.

## Перегляд процесів і власників

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Зв’язок «батьківський процес — дочірній процес» між різними користувачами може бути нормальним, але несподіваний перехід варто перевірити: дослідіть команду батьківського процесу, аргументи, виконуваний файл, робочий каталог і файли, на які він посилається. Скористайтеся розділом [користувачі та сеанси](../user-information/user-and-session-triage.md), щоб інтерпретувати власника та контекст входу.

### Локальні консолі віртуальних машин

Перевірте параметри `-spice` процесу QEMU разом з адресою, на якій він прослуховує з’єднання. У [документації QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) зазначено, що `disable-ticketing` дає змогу SPICE-клієнтам підключатися без автентифікації. Слухач, прив’язаний до loopback-адреси, усе ще може бути доступним іншим локальним користувачам хоста. Перш ніж вважати консоль доступною без обмежень, перевірте активний слухач, параметри автентифікації та локальний доступ. Керування консоллю впливає на **гостьову систему**; отримання облікового запису в гостьовій системі або зміна стану її завантаження потребує окремих умов на стороні гостьової системи й не надає root-доступу до хоста віртуалізації. Під час пасивного переліку переглядайте аргументи процесу й метадані сокетів, не підключаючись до гостьової системи та не перезавантажуючи її.

Локально доступний вебінтерфейс може виконувати код із правами свого облікового запису служби, навіть якщо перша оболонка не має доступу до файлів цього облікового запису. Наприклад, CVE-2023-0297 стосувалася обробки `/flash/addcrypted2` у pyLoad, коли недовірений JavaScript потрапляв до Js2Py з увімкненим імпортом Python; [виправлення в upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) вимкнуло `pyimport`. Перш ніж вважати процес pyLoad шляхом підвищення привілеїв, зіставте власника запущеного процесу, адресу прослуховування, доступність кінцевої точки та встановлене виправлення або backport від постачальника. Самі лише назва процесу, відкритий порт або версія пакета не доводять наявності вразливості; під час пасивного переліку не надсилайте payload для виконання коду.

### Привілейовані оболонки входу зі спільним терміналом

Привілейована інтерактивна оболонка, яка запускає `su --login <user>` без окремого псевдотермінала, може залишити термінал спільним з оболонкою входу менш привілейованого користувача. Якщо цей користувач може керувати своїм файлом запуску, а код у ньому може використовувати `TIOCSTI` для ін’єкції введення в термінал, це введення може надійти до привілейованої оболонки, коли вона відновить роботу. У [посібнику util-linux для `su`](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) описано ризик спільного термінала та рекомендовано використовувати `su --pty`/`-P` для інтерактивної роботи; `su -c` запускає окремий сеанс без керувального термінала. Ризик залежить від фактичної батьківської оболонки, зв’язку з терміналом, цільового файлу запуску та політики ядра. Сама назва процесу або аргумент `su -l` — лише привід для перевірки.

Перегляньте спостережене дерево процесів і стовпці TTY, а потім доступний для читання файл запуску, його власника та дозволи. У Linux файл `/proc/sys/dev/tty/legacy_tiocsti`, якщо він існує, може допомогти з’ясувати політику; його відсутність не доводить безпечність. У [посібнику Linux для `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) зазначено, що починаючи з Linux 6.2 для цієї операції може вимагатися `CAP_SYS_ADMIN`, якщо цей sysctl має значення false. Не викликайте ioctl лише для переліку даних про хост.

Обліковий запис бази даних іноді може змінити файл запуску цільового користувача без прямого доступу на запис до файлової системи. Серверна команда PostgreSQL `COPY ... TO 'filename'` записує файл від імені облікового запису ОС сервера бази даних, але, згідно з [обмеженнями PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html), така форма доступна лише суперкористувачам бази даних або ролям на кшталт `pg_write_server_files`. Перевірте і роль бази даних, і дозволи ОС-сервера на файл; сам рядок підключення застосунку не надає права запису у файл. Оцінюючи ланцюжок, розглядайте можливості привілейованого засобу запуску й облікового запису бази даних окремо.

## Перевірка артефактів середовища виконання

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Видалені виконувані файли та видалені, але відкриті файли залишаються доступними за посиланням, доки не буде закрито останній дескриптор. Вони можуть зберігати докази або доступні секрети. Середовища процесів і пам’ять можуть містити облікові дані, але читання даних іншого процесу обмежується власником, параметрами монтування `/proc`, політикою Yama ptrace та іншими засобами безпеки. Пов’язані техніки див. у розділах [дескриптори файлів](../main-system-information/filesystem-links-and-file-descriptors.md) і [пошук облікових даних після експлуатації](../post-exploitation/README.md).

Збережені трасування системних викликів — це ще одна межа дозволів файлів. [`strace` записує аргументи системних викликів у вихідний файл](https://man7.org/linux/man-pages/man1/strace.1.html), тож доступне для читання трасування аргументів [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) може розкрити пароль, переданий привілейованим завданням у командному рядку. Спочатку переконайтеся, що поточний користувач може прочитати саме це трасування і що аргумент справді містить облікові дані; для переходу до іншого облікового запису Unix потрібне окреме підтвердження, що ці облікові дані там приймаються. Метадані файлів — це корисна пасивна зачіпка, яка дає змогу не сканувати всі трасування та не виводити їхній вміст під час звичайного переліку.

## Сокети офісної автоматизації з привілеями

LibreOffice та OpenOffice можуть надавати доступ до свого UNO API через аргумент `--accept=socket,host=<host>,port=<port>;urp;`. Процес офісного застосунку, що належить root і має доступну кінцеву точку, може дозволити локальному користувачеві з нижчими привілеями викликати API-сервіси в контексті безпеки цього процесу. Сервіс `SystemShellExecute` містить операцію для запуску системної команди. Прив’язка до loopback обмежує віддалений доступ, але сокет усе одно залишається доступним локальним користувачам, якщо доступ не блокує інший засіб контролю.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Зіставте власника процесу, точний аргумент `--accept`, а також поточну адресу й порт, на яких він прослуховує з’єднання. Налаштований acceptor, якому не вдалося прив’язатися до адреси, — лише зачіпка; під час пасивного переліку не підключайтеся до API й не викликайте його. Не запускайте привілейований екземпляр офісного застосунку лише для перевірки цієї умови.

## System V shared memory, яку використовують привілейовані процеси

Допоміжна програма, що належить root, може створити сегмент спільної пам’яті System V, у який може записувати інший користувач. Якщо згодом допоміжна програма довіряє даним із цього сегмента під час виконання shell-команди чи іншої чутливої операції, сегмент перетинає межу привілеїв, навіть якщо виконуваний файл і пов’язані з ним файли захищені. `shmget()` бере права доступу з молодших дев’яти бітів своїх прапорців; режим `0666` дає іншим користувачам право на запис, тоді як прапорець `IPC_CREAT` не обмежує ці права. Пасивно перевіряйте активні сегменти за допомогою `ipcs -m` і зіставляйте їхнього власника, режим і час існування з привілейованим процесом та обробкою його вхідних даних. Сам по собі сегмент із правом на запис для всіх не свідчить про можливість виконання команд.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Сегменти System V відрізняються від файлів спільної пам’яті POSIX у `/dev/shm`. Сегмент, створений лише на мить, може бути відсутнім у знімку `ipcs`, тож порожній вивід не виключає наявності помічника, який використовує спільну пам’ять. Перевірте його вихідний код або поведінку бінарного файлу, а також будь-яке правило `sudo`, яке його запускає; не запускайте привілейований помічник лише для того, щоб під час переліку з’явився сегмент. У [посібнику з просторів імен IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) пояснюється, як простори імен впливають на видимість.<sup>[[2]](#references)[[3]](#references)</sup>

## Перевірки скриптів агента Consul

Consul може виконувати скриптові перевірки працездатності з ідентифікатором користувача операційної системи, під яким працює агент. Якщо агент працює від root, у ньому ввімкнено `enable_script_checks`, а користувач із нижчими привілеями може зареєструвати сервіс зі скриптовою перевіркою через локальний HTTP API, цей користувач може спричинити виконання команд від root. Прив’язка API лише до `127.0.0.1` усе одно дає локальним користувачам змогу звертатися до нього. Налаштування `enable_local_script_checks` має вужчу дію: воно не дозволяє скриптові перевірки, передані через реєстрацію в HTTP API. Коли ACL Consul увімкнено, для реєстрації сервісу потрібен `service:write`; сам рядок `acl.default_policy=allow` не доводить, що анонімний користувач може виконати реєстрацію. Перевіряйте фактичний ідентифікатор агента, завантажені налаштування, прив’язку API та авторизацію разом.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Скористайтеся аргументами `-config-dir` і `-config-file` запущеного agent, щоб знайти відповідну конфігурацію, і перевірте лише назви та значення полів script-check і ACL. Файли конфігурації можуть також містити gossip keys або tokens; не вставляйте їх у спільні журнали. Не реєструйте службу й не запускайте перевірку працездатності лише для переліку цієї умови.

Окремий шлях через локальний файл існує, якщо користувач із нижчими привілеями може **записувати в каталог, названий у `-config-dir` agent, запущеного від root, і шукати в ньому**: з цього каталогу може бути завантажено нове визначення служби `.hcl` або `.json`. Пошук у каталозі та право запису можуть дозволити додати файл, навіть якщо перегляд вмісту каталогу заборонено. Для виконання команд від root підтвердьте, що agent справді завантажує цей каталог, його **ефективне** налаштування script-check дозволяє локальні визначення, визначення завантажено, а agent зберігає привілеї root. [У документації Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) описано, які налаштування й визначення health-check можна перезавантажити; для ввімкнення script-check може знадобитися перезапуск, тому перевірте поведінку встановленої версії. Якщо agent захищено ACL, команда [`consul reload` потребує `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); самого дозволу на запис у KV недостатньо. Сприймайте можливість змінювати метадані каталогу як сигнал для перевірки, а не доказ наявності дозволу на перезавантаження, перезапуск чи виконання команд. Перевіряйте шляхи, дозволи й політики, не записуючи конфігурацію та не викликаючи API.

## Простежте ланцюжок виконання служби

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Перевірте unit, drop-ins, `EnvironmentFile=`, helper scripts, відносні команди, writable directories і socket activation. Навіть unit, власником якого є root, може бути небезпечним, якщо він читає конфігурацію або скрипт, доступні для запису користувачу. На сторінці [arbitrary file write](../interesting-files-permissions/write-to-root.md) описані типові способи зловживання сервісами й unit. Відстежуйте короткочасні завдання за допомогою [pspy](https://github.com/DominicBreuker/pspy) або телеметрії аудиту/процесів, якщо одноразовий список `ps` їх не показує.

Для custom-сервісу **xinetd** зіставте `server`, `user` і контролі доступу в увімкненому stanza з активним listener і точним executable. Налаштування [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) визначає identity запущеного процесу, тоді як set-user-ID bit на executable може окремо змінити його effective identity, якщо [`execve` дозволяє такий перехід](https://man7.org/linux/man-pages/man2/execve.2.html). Доступний привілейований binary, який приймає недовірені дані, варто перевірити офлайн за вихідним кодом або дизасемблюванням на наявність помилок memory safety, наприклад необмеженого перетворення рядка в [`scanf`](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) у буфер фіксованого розміру. Відповідність сервісу та метадані set-user-ID — це зачіпки, а не доказ наявності такої помилки; не надсилайте дані, що спричиняють аварійне завершення, і не налагоджуйте активний привілейований сервіс під час пасивного переліку.

Для custom-привілейованого listener із доступним для читання вихідним кодом перевірте довжини, контрольовані викликачем, які використовуються в операціях копіювання, наприклад [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Перевірка лише того, що поточний індекс запису перебуває в межах буфера фіксованого розміру, не доводить, що **довжина копіювання** вміщується в доступний залишок; переконайтеся, що `copy_length <= capacity - index` після перевірки діапазону індексу, а також перевірте знаковість і переповнення арифметики. Це лише зачіпка для перевірки за умови, що дані доходять до цієї операції, listener доступний користувачу з нижчими привілеями, а процес зберігає вищу effective identity. Переглядайте вихідний код і метадані процесу офлайн; під час переліку не надсилайте дані, що спричиняють аварійне завершення активного сервісу.

У системах, що використовують **Upstart**, визначення system jobs можуть міститися в `/etc/init/*.conf`. Файл job, доступний для запису поточному користувачу, має значення, якщо активний init daemon завантажує саме цей job, його stanza `script` або `exec` виконується з вищою identity, а користувач може запустити його за допомогою дозволеної команди `initctl` або іншого реального trigger. Сам по собі дозвіл sudo на `initctl` не доводить, що якийсь файл job доступний для запису або що змінений job запуститься. Перевірте дозволи точного файла job, ефективне налаштування run-as, активний daemon і trigger, не редагуючи та не запускаючи job під час переліку. Дивіться посібники [Upstart job configuration](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) і [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Доступний для читання файл пароля autologin, наприклад `/etc/autologin/passwd` у системах, де [boot job читає саме цей шлях](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), є зачіпкою щодо витоку облікових даних. Переконайтеся, що boot job встановлений і використовує цей файл, а потім окремо перевірте, чи дійсний пароль для іншого локального облікового запису або сервісу. Саме ім’я файла не доводить повторне використання пароля; зафіксуйте шлях і метадані доступу, не додаючи пароль до спільного виводу переліку.

`ExecStart=` у unit або запланована команда можуть вказувати точний шлях до скрипта в каталозі, вміст якого не можна переглянути списком. [Дозвіл пошуку в каталозі](https://man7.org/linux/man-pages/man7/path_resolution.7.html) усе ще може дозволяти поточній identity пройти за цим відомим шляхом; перевірте дозвіл пошуку в кожному батьківському каталозі та дозвіл читання самого файла, а не припускайте, що невдалий перегляд вмісту каталогу захищає його. Доступний для читання скрипт може містити облікові дані для передачі, але перехід до іншого облікового запису можливий лише тоді, коли ці облікові дані залишаються дійсними й окремо приймаються там. Зафіксуйте шлях і докази дозволів, не виводячи секрети у спільні журнали.

Для запланованого скрипта CommonJS Node.js перевіряйте bare imports на кшталт `require('package')`, навіть якщо сам скрипт доступний лише для читання. [Node шукає `node_modules` поруч із файлом, що виконує імпорт, а потім у його батьківських каталогах](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), перш ніж перейти до налаштованих глобальних шляхів. Користувач із нижчим рівнем привілеїв, який може **записувати й шукати** в одному з цих батьківських каталогів, може створити пакет, що відповідатиме раніше за інші. Переконайтеся, що точний імпорт виконується, вибраний пакет не є вбудованим модулем, відповідний шлях можна створити або змінити, модуль розв’язується за цим шляхом у встановленому runtime, а привілейованіший job завантажить його під час майбутнього запуску. Writable parent metadata — лише підказка для перевірки; пасивно перегляньте скрипт і scheduler, не розміщуючи модуль і не запускаючи job.

Приватний індекс Python-пакетів — ще одна межа довіри, якщо автоматизований job встановлює пакети під іншою OS identity. Зіставте точний job і обліковий запис run-as із налаштованим індексом та вибраними іменами пакетів, а також з’ясуйте, чи може користувач із нижчими привілеями опублікувати або замінити пакет, який job справді встановить. Створення source distribution може запустити його build backend або застарілий `setup.py` з identity інсталятора; імпорт встановленого пакета — окремий шлях виконання. Самі по собі listener індексу, доступний для читання hash пароля завантаження або ім’я файла пакета не доводять наявність такого ланцюжка. Перевірте job, авторизацію індексу та походження пакета, нічого не завантажуючи й не встановлюючи під час переліку. Дивіться [інтерфейс build-system у pip](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Привілейований agent може опитувати чергу завдань, якою керує окремий web service або container. Якщо identity з нижчим рівнем довіри може записувати в базу даних завдань сервісу, з’ясуйте, чи передаються ці записи цьому agent і чи виконується command task з OS identity agent. Окремо перевірте доступ на запис до бази даних, цільову сесію або routing key, активне опитування, авторизацію завдань і effective user agent. Root усередині container сам по собі не означає доступ до host-root; межа перетинається лише тоді, коли споживач із привілеями на host виконує контрольовані зловмисником дані завдання. Перевірте метадані процесів, файла бази даних і сервісу, не змінюючи чергу й не надсилаючи завдання під час переліку.

Натомість періодичний job може читати команду з рядка конфігурації в базі даних застосунку. Переконайтеся, що роль бази даних із нижчим рівнем привілеїв може змінити саме цей рядок, що активний job читає його після зміни, а значення потрапляє в shell або еквівалентний виконавець команд із вищою OS identity. Самі по собі доступ на запис до бази даних або значення, схоже на команду, не доводять виконання; перегляньте job і дозволи, не змінюючи рядок під час пасивного переліку.

Повідомлення в черзі може також містити URL, а не код. Якщо привілейований consumer отримує дані за цим URL і завантажує відповідь як Lua або інший executable plugin, перевірте дозвіл publisher на точні exchange і routing key, прив’язку до черги, яку споживають, шлях отримання даних і завантаження plugin та effective identity worker. [RabbitMQ маршрутизує опубліковані повідомлення через exchanges](https://www.rabbitmq.com/docs/exchanges); listener брокера або дійсний логін самі по собі не доводять доставку цьому worker. Перехоплені облікові дані брокера у відкритому тексті — окрема зачіпка, для якої потрібні реальний доступ до захоплення пакетів і доступний для читання трафік; вони не доводять наявність дозволу на публікацію. Lua plugin може викликати shell-команди через [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute), лише якщо цей API доступний у його runtime. Перегляньте конфігурацію та код, не захоплюючи трафік, не публікуючи повідомлень і не отримуючи plugin під час пасивного переліку.

Якщо привілейований Python service надає локальний HTTP- або socket endpoint, доступний для читання скрипт може виявити шлях від введених даних до коду, навіть якщо дозволи файла не дають змоги його змінити. Зіставте активний процес та identity unit із точним скриптом, listener, авторизацією маршруту й полями, контрольованими викликачем. Потім простежте ці поля через парсинг і валідацію до динамічного sink `eval()` або `exec()`. Зокрема, створення нового f-string із тексту запиту та його оцінювання може інтерпретувати контрольовані зловмисником поля підстановки як вирази Python ([застереження щодо Python `eval`](https://docs.python.org/3/library/functions.html#eval); [семантика f-string](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Сам по собі збіг `eval` або прив’язка до loopback не доводять, що недовірений викликач може дістатися до sink; перегляньте фактичний потік даних і контролі доступу, не надсилаючи тестові дані під час переліку.

Окремо перевірте gate підписаних запитів на цьому маршруті. Якщо доступний для читання код виводить ключ підпису з явно малого або передбачуваного простору значень, а сервіс надає зразок із дійсним підписом, підпис може більше не захищати привілейований sink `eval()`. Перевірте точний спосіб отримання ключа й verifier, identity активного сервісу та локальний доступ викликачів, а також чи потрапляє підписане поле до sink; самі по собі імпорт Python-модуля [`random`](https://docs.python.org/3/library/random.html) або зразок підпису не доводять жодної з цих умов. Python також попереджає, що обмеження `__builtins__` [не є межею безпеки для недовірених даних `eval()`](https://docs.python.org/3/library/functions.html#eval). Аналізуйте ключ офлайн і не надсилайте підроблені запити під час пасивного переліку.

Порожній каталог `/etc/systemd/system/<unit>.service.d`, доступний для запису, має значення, навіть якщо файл unit і всі наявні drop-in захищені: користувач може створити новий override `.conf`. Перевірте, чи каталог доступний для запису й пошуку поточній identity, чи завантажено unit і чи працює він від root, а також чи відбудеться перезавантаження daemon із подальшим перезапуском. Дозвіл на перезавантаження або перезапуск, timer чи наступне завантаження системи можуть активувати зміну; сам доступ до каталогу на запис не запускає її негайно.

Для запущених сервісів перевіряйте буквальні шляхи `EnvironmentFile=` із секції `[Service]` unit, зокрема файли, чиї імена не починаються з `.env`. Якщо користувач із низькими привілеями може прочитати такий файл, перелічіть імена ключів, схожі на облікові дані, наприклад `API_TOKEN` або `APP_SECRET_KEY`, не виводячи значення у спільні журнали. Перевірте drop-in overrides і необов’язкові префікси `-`, визначаючи ефективну конфігурацію unit. Доступність для читання — це зачіпка щодо витоку облікових даних; для ескалації значення все одно має бути дійсним для привілейованої дії.

### Привілейована обробка недовірених завантажень

File watcher, що працює від root, може передавати файли з каталогу завантажень, доступного користувачам для запису, короткочасному parser або extractor. Перевірте батьківський скрипт або сервіс запущеного watcher і з’ясуйте точний каталог, хто може поміщати туди файли, команду дочірнього процесу та її аргументи, а також identity, від якої працює дочірній процес. Знімок процесів може показати watcher, але пропустити extractor між завантаженнями. Не розміщуйте тестовий payload і не запускайте watcher під час пасивного переліку.

Один конкретний приклад — режим видобування Binwalk (`-e`), що обробляє контрольовані зловмисником дані PFS. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) дозволяла PFS extractor записувати файли за межами призначеного каталогу, зокрема за шляхом до plugin, який Binwalk міг згодом завантажити. Виправлення додали в upstream у версії [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), але backport виправлень у дистрибутивах може залишити старішу версію, що відображається; перш ніж оцінювати застосовність, перевірте стан безпеки встановленого пакета, наприклад у [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2022-4510). Сама лише встановлена версія Binwalk не доводить наявність шляху ескалації привілеїв: видобування має фактично запускатися привілейованішим процесом на даних, які може контролювати користувач із нижчими привілеями.

### Заплановані збірки з локальними залежностями

Запланований `cargo run` компілює вихідний код заново від імені користувача run-as job. Перевірте локальні залежності `{ path = "..." }` у маніфесті, вихідний код і дозволи батьківських каталогів кожної залежності, а не лише основного crate. Якщо користувач із нижчими привілеями може змінити залежність, яку компілює Cargo, а запланований job запускає результат, скомпільований код може виконатися від імені цього користувача run-as. Переконайтеся в ефективній команді scheduler, робочому каталозі, розв’язанні залежностей і тому, чи відбудеться повторна збірка; доступний для запису файл вихідного коду Rust деінде — лише зачіпка. Для пасивного первинного аналізу достатньо прочитати маніфест і метадані шляхів. Дивіться [документацію Cargo щодо path-залежностей](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Файли framebuffer Xvfb

`Xvfb -fbdir <directory>` використовує memory-mapped файли з назвами `Xvfb_screen<n>` для своїх віртуальних екранів. Якщо в запущеному процесі Xvfb іншого користувача вказано каталог, файли екрана в якому доступні поточному користувачу для читання, framebuffer може розкривати вміст робочого столу цього користувача. Перевірте процес, власника файлів і дозволи разом; сам по собі доступний для читання файл не доводить, що на екрані є корисний вміст. Спочатку перевірте шляхи й метадані, не копіюючи дані зображення у спільний вивід переліку. Поведінку `-fbdir` описано в [посібнику Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html).

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
