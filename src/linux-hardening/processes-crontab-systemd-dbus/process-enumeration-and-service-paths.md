# Перелік процесів і шляхи служб

{{#include ../../banners/hacktricks-training.md}}

Корисно з’ясувати, який привілейований процес використовує дані або код, на які може впливати користувач із нижчим рівнем привілеїв. Перевірте дерево процесів, поточне середовище, відкриті файли, а також unit або скрипт, що запустив кожен із кандидатів.

## Визначення процесів і власників

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Міжкористувацький зв’язок «батьківський процес — дочірній процес» може бути нормальним, але неочікуваний перехід потребує перевірки батьківської команди, аргументів, виконуваного файла, робочого каталогу та згаданих файлів. Скористайтеся розділом про [користувачів і сеанси](../user-information/user-and-session-triage.md), щоб визначити власника та контекст входу.

### Локальні консолі віртуальних машин

Перевіряйте параметри `-spice` процесу QEMU разом із його адресою прослуховування. [Документація QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) зазначає, що `disable-ticketing` дає змогу SPICE-клієнтам підключатися без автентифікації. Навіть якщо прослуховувач прив’язаний до loopback, інші локальні користувачі хоста все одно можуть мати до нього доступ. Перш ніж вважати консоль відкритою, перевірте активний прослуховувач, параметри автентифікації та локальний доступ. Керування консоллю впливає на **гостьову систему**; отримання облікового запису гостя або зміна стану його завантаження потребує окремих умов на гостьовій системі й не надає root-доступу до хоста віртуалізації. Під час пасивного переліку переглядайте аргументи процесу й метадані сокета, не підключаючись до гостьової системи та не перезавантажуючи її.

Локально доступний вебінтерфейс може виконувати код із правами свого сервісного облікового запису, навіть якщо перша оболонка не має доступу до файлів цього облікового запису. Наприклад, CVE-2023-0297 стосувалася обробки `/flash/addcrypted2` у pyLoad, коли недовірений JavaScript потрапляв до Js2Py з увімкненими імпортами Python; [виправлення в upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) вимкнуло `pyimport`. Перш ніж вважати процес pyLoad шляхом підвищення привілеїв, зіставте власника запущеного процесу, адресу прослуховування, доступність endpoint і встановлений патч або backport від постачальника. Сама назва процесу, відкритий порт чи версія пакета не доводять наявність вразливості; під час пасивного переліку не надсилайте payload для виконання коду.

### Привілейовані оболонки входу, що спільно використовують термінал

Якщо привілейована інтерактивна оболонка запускає `su --login <user>` без окремого псевдотермінала, її термінал може залишитися спільним із менш привілейованою оболонкою входу. Якщо файл запуску цього користувача можна змінити, а код у ньому може використовувати `TIOCSTI` для введення даних у термінал, ці дані можуть надійти до привілейованої оболонки, коли вона відновить роботу. [Посібник util-linux для `su`](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) описує ризик спільного термінала й рекомендує для інтерактивного використання `su --pty`/`-P`; `su -c` запускає окремий сеанс без керувального термінала. Для оцінки ризику потрібно перевірити фактичну батьківську оболонку, зв’язок із терміналом, цільовий файл запуску та політику ядра. Одна лише назва процесу чи аргумент `su -l` — це тільки підстава для перевірки.

Перевірте дерево запущених процесів і стовпці TTY, а потім доступний для читання файл запуску та власника й дозволи файла запуску оболонки. У Linux `/proc/sys/dev/tty/legacy_tiocsti`, якщо він наявний, може допомогти з’ясувати політику; його відсутність не є доказом безпеки. [Посібник Linux для `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) зазначає, що починаючи з Linux 6.2 ця операція може вимагати `CAP_SYS_ADMIN`, якщо цей sysctl має значення false. Не викликайте ioctl лише для переліку даних хоста.

Іноді обліковий запис бази даних може змінити файл запуску цільового користувача, не маючи прямого доступу на запис до файлової системи. Серверна команда PostgreSQL `COPY ... TO 'filename'` записує файл від імені облікового запису ОС сервера бази даних, але [обмеження PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) дозволяють цей варіант лише суперкористувачам бази даних або ролям на кшталт `pg_write_server_files`. Перевірте і роль у базі даних, і дозволи ОС сервера на файл; сам рядок підключення застосунку не надає права записувати файли. Оцінюючи ланцюжок, розглядайте можливості привілейованого процесу запуску й облікового запису бази даних окремо.

## Перевірка артефактів середовища виконання

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Видалені виконувані файли та видалені, але відкриті файли залишаються доступними за посиланнями, доки не закриється останній дескриптор. Вони можуть зберігати докази або доступні секрети. Середовища процесів і пам’ять можуть містити облікові дані, але читання іншого процесу обмежене правами власника, параметрами монтування `/proc`, політикою Yama ptrace та іншими засобами безпеки. Докладніше про пов’язані техніки див. у розділах [файлові дескриптори](../main-system-information/filesystem-links-and-file-descriptors.md) та [пошук облікових даних після експлуатації](../post-exploitation/README.md).

Збережені трасування системних викликів — це ще одна межа дозволів на файли. [`strace` записує аргументи системних викликів у вихідний файл](https://man7.org/linux/man-pages/man1/strace.1.html), тож доступне для читання трасування аргументів [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) може розкрити пароль, який привілейоване завдання передало в командному рядку. Спочатку переконайтеся, що поточний користувач може читати конкретне трасування та що аргумент справді містить облікові дані; для подальшого переходу на Unix-обліковий запис потрібен окремий доказ, що ці облікові дані там приймаються. Метадані файлів — це корисна пасивна зачіпка, яка не потребує сканування всіх трасувань або виведення їхнього вмісту під час звичайного переліку.

## Сокети привілейованої офісної автоматизації

LibreOffice та OpenOffice можуть надавати доступ до свого UNO API через аргумент `--accept=socket,host=<host>,port=<port>;urp;`. Офісний процес, що належить root і має доступну кінцеву точку, може дозволити локальному користувачеві з нижчими привілеями викликати API-сервіси в контексті безпеки цього процесу. Сервіс `SystemShellExecute` містить операцію для запуску системної команди. Прив’язування до loopback обмежує віддалений доступ, але сокет усе одно залишається доступним локальним користувачам, якщо інший засіб контролю не перешкоджає цьому.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Зіставте власника процесу, точний аргумент `--accept`, а також поточну адресу й порт, на яких він прослуховує з’єднання. Налаштований acceptor, якому не вдалося прив’язатися, — лише зачіпка; під час пасивного переліку не підключайтеся до API й не викликайте його. Не запускайте привілейований екземпляр office лише для перевірки цієї умови.

## System V shared memory, яку використовують привілейовані процеси

Допоміжна програма, що належить root, може створити сегмент System V shared memory, доступний для запису іншому користувачеві. Якщо згодом програма довіряє даним із цього сегмента під час виконання shell-команди чи іншої чутливої операції, сегмент перетинає межу привілеїв, навіть якщо виконуваний файл і його файли захищені. `shmget()` бере дозволи доступу з молодших дев’яти бітів своїх прапорців; режим `0666` дозволяє іншим користувачам записувати дані, тоді як прапорець `IPC_CREAT` не обмежує ці дозволи. Пасивно перевіряйте активні сегменти за допомогою `ipcs -m` і зіставляйте їхнього власника, режим і час існування з привілейованим процесом та способом обробки його вхідних даних. Сам по собі сегмент із правами на запис для всіх не доводить можливість виконання команд.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Сегменти System V відрізняються від файлів спільної пам’яті POSIX у `/dev/shm`. Сегмент, створений лише на мить, може бути відсутнім у конкретному знімку `ipcs`, тож порожній вивід не виключає наявності допоміжної програми, яка використовує спільну пам’ять. Перевірте її вихідний код або поведінку бінарного файла, а також будь-яке правило `sudo`, яке її запускає; не запускайте привілейовану допоміжну програму лише для того, щоб сегмент з’явився під час переліку. У [посібнику з просторів імен IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) пояснюється, як простори імен впливають на видимість.<sup>[[2]](#references)[[3]](#references)</sup>

## Перевірки скриптів агента Consul

Consul може виконувати скриптові перевірки стану з ідентичністю операційної системи свого агента. Якщо агент працює від імені root, має ввімкнене `enable_script_checks` і дозволяє користувачеві з нижчими привілеями реєструвати службу зі скриптовою перевіркою через локальний HTTP API, цей користувач може спричинити виконання команд від імені root. Прив’язка API лише до `127.0.0.1` усе одно дає локальним користувачам змогу звертатися до нього. Налаштування `enable_local_script_checks` має вужчу дію: воно виключає скриптові перевірки, надіслані через реєстрацію HTTP API. Коли ACL Consul увімкнені, для реєстрації служби потрібен дозвіл `service:write`; сам рядок `acl.default_policy=allow` не доводить, що анонімний користувач може виконати реєстрацію. Перевіряйте ідентичність самого агента, завантажені налаштування, прив’язку API та авторизацію разом.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Дотримуйтеся аргументів `-config-dir` і `-config-file` запущеного агента, щоб знайти відповідну конфігурацію, і перевіряйте лише назви та значення полів script-check і ACL. Файли конфігурації також можуть містити ключі або токени gossip; не вставляйте їх у спільні журнали. Не реєструйте сервіс і не запускайте перевірку працездатності лише для того, щоб виявити цю умову.

Окремий шлях через локальний файл існує, якщо користувач із нижчими привілеями може **записувати до каталогу, названого в аргументі `-config-dir` агента, запущеного від root, і шукати в ньому**: із цього каталогу може бути завантажене нове визначення сервісу `.hcl` або `.json`. Права на пошук і запис у каталог можуть дозволити додати файл, навіть якщо перегляд вмісту каталогу заборонений. Для виконання команд від root переконайтеся, що агент справді завантажує конфігурацію з цього каталогу, його **ефективне** налаштування script-check дозволяє локальні визначення, визначення завантажене, а агент зберігає привілеї root. [У документації Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) описано, які налаштування та визначення перевірок працездатності можна перезавантажувати; для ввімкнення script checks може знадобитися перезапуск, тому перевірте, як це працює в установленій версії. Якщо доступом до агента керують ACL, для [`consul reload` потрібен дозвіл `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); одного лише дозволу на запис у KV недостатньо. Вважайте можливість запису в метадані каталогу приводом для перевірки, а не доказом дозволеного перезавантаження, перезапуску чи виконання команд. Перевіряйте шляхи, дозволи та політики, не записуючи конфігурацію й не викликаючи API.

## Простежте ланцюжок виконання сервісу

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Перевірте unit, drop-ins, `EnvironmentFile=`, допоміжні скрипти, відносні команди, каталоги з правом запису та socket activation. Навіть unit, власником якого є root, може бути небезпечним, якщо він читає конфігураційний файл або скрипт, доступний для запису користувачу. На сторінці [arbitrary file write](../interesting-files-permissions/write-to-root.md) описано поширені способи зловживання сервісами та unit-файлами. Відстежуйте короткочасні задачі за допомогою [pspy](https://github.com/DominicBreuker/pspy) або засобів аудиту/телеметрії процесів, якщо одноразовий перегляд через `ps` їх пропускає.

Для власного сервісу **xinetd** зіставте ввімкнений stanza `server`, `user` і правила доступу з активним listener та точним виконуваним файлом. Параметр [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) визначає identity запущеного процесу, тоді як біт set-user-ID на виконуваному файлі може окремо змінити його effective identity, якщо [`execve` дозволяє такий перехід](https://man7.org/linux/man-pages/man2/execve.2.html). Доступний привілейований бінарний файл, який приймає недовірені дані, варто перевірити за вихідним кодом або дизасемблюванням офлайн на наявність помилок memory-safety, наприклад необмеженого перетворення рядка [`scanf`](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) у буфер фіксованого розміру. Відповідність сервісу та метадані set-user-ID — це підказки, а не доказ наявності такої помилки; не надсилайте дані, що спричиняють збій, і не налагоджуйте активний привілейований сервіс під час пасивного переліку.

Якщо власний привілейований listener має доступний для читання вихідний код, перевірте кожну довжину, яку контролює викликач і яка використовується операцією копіювання на кшталт [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Перевірка лише того, що поточний індекс запису не виходить за межі фіксованого буфера, не доводить, що **довжина копіювання** вміщується в залишок вільного місця; переконайтеся, що `copy_length <= capacity - index`, попередньо перевіривши, що індекс у межах буфера, а також перевірте знаковість і переповнення арифметики. Це лише підказка для перевірки, якщо дані доходять до цієї операції, listener доступний користувачу з нижчими привілеями, а процес зберігає вищу effective identity. Перевіряйте вихідний код і метадані процесу офлайн; не надсилайте дані, що спричиняють збій, активному сервісу під час переліку.

У системах, що використовують **Upstart**, визначення системних задач можуть міститися в `/etc/init/*.conf`. Файл задачі, доступний поточному користувачу для запису, має значення, якщо активний init daemon завантажує саме цю задачу, її stanza `script` або `exec` виконується з вищими привілеями, а користувач може запустити її дозволеною командою `initctl` або іншим реальним тригером. Сам факт надання sudo-доступу до `initctl` не доводить, що якийсь файл задачі доступний для запису або що змінена задача запуститься. Перевірте дозволи саме цього файла задачі, effective run-as, активний daemon і тригер, не редагуючи та не запускаючи задачу під час переліку. Див. посібники [конфігурації задач Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) і [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Доступний для читання файл пароля автологіну, наприклад `/etc/autologin/passwd` у системах, де [завантажувальна задача читає саме цей шлях](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), вказує на можливе розкриття облікових даних. Переконайтеся, що завантажувальну задачу встановлено і вона використовує цей файл, а потім окремо перевірте, чи пароль дійсний для іншого локального облікового запису або сервісу. Саме ім’я файла не доводить повторне використання пароля; зафіксуйте шлях і метадані доступу, не додаючи пароль до спільного виводу переліку.

`ExecStart=` у unit-файлі або запланована команда можуть розкрити точний шлях до скрипту в каталозі, вміст якого неможливо переглянути списком. [Право пошуку в каталозі](https://man7.org/linux/man-pages/man7/path_resolution.7.html) усе ще може дозволити поточному користувачу пройти за відомим шляхом; перевірте право пошуку в кожному батьківському каталозі та право читання файла, а не припускайте, що невдала спроба переглянути список каталогу захищає його вміст. Доступний для читання скрипт може містити облікові дані для передачі, але доступ до іншого облікового запису можливий лише якщо ці облікові дані залишаються дійсними й окремо приймаються там. Зафіксуйте шлях і підтвердження дозволів, не виводячи секрети у спільні журнали.

Для запланованого скрипту CommonJS Node.js перевіряйте bare imports на кшталт `require('package')`, навіть якщо сам скрипт доступний лише для читання. [Node шукає `node_modules` поруч із файлом-імпортером, а потім у його батьківських каталогах](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), перш ніж переходити до налаштованих глобальних шляхів. Користувач із нижчим рівнем привілеїв, який може **записувати в один із цих батьківських каталогів і шукати в ньому**, може створити пакет, що матиме пріоритет під час пошуку. Переконайтеся, що саме цей імпорт виконується, вибраний пакет не є вбудованим модулем, відповідний шлях можна створити або змінити, модуль буде знайдено там у встановленому runtime, а привілейована задача завантажить його під час наступного запуску. Метадані доступного для запису батьківського каталогу — лише підказка для перевірки; оглядайте скрипт і планувальник пасивно, не розміщуючи модуль і не запускаючи задачу.

Приватний індекс пакетів Python — ще одна межа довіри, якщо автоматизована задача встановлює пакети з-під іншої OS identity. Зіставте точну задачу та обліковий запис run-as із налаштованим індексом, вибраними назвами пакетів і можливістю користувача з нижчим рівнем привілеїв опублікувати або замінити пакет, який задача справді встановить. Збірка source distribution може виконати build backend або застарілий `setup.py` з-під identity інсталятора; імпорт установленого пакета — окремий шлях виконання. Listener індексу, доступний для читання hash пароля завантаження або лише ім’я файла пакета не доводять наявність такого ланцюжка. Перевіряйте задачу, права доступу до індексу та походження пакета, нічого не завантажуючи й не встановлюючи під час переліку. Див. [інтерфейс build system pip](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Привілейований агент може опитувати чергу задач, якою керує окремий вебсервіс або контейнер. Якщо identity з нижчим рівнем довіри може записувати в базу даних задач сервісу, з’ясуйте, чи справді ці записи обслуговуються цим агентом і чи виконується command task з-під OS identity агента. Окремо перевірте доступ на запис до бази даних, цільову сесію або routing key, активне опитування, авторизацію задач і effective user агента. Root усередині контейнера сам по собі не означає доступу до host-root; межа перетинається лише якщо споживач із привілеями на хості виконує контрольовані атакувальником дані задачі. Перевіряйте метадані процесу, файла бази даних і сервісу, не змінюючи чергу та не надсилаючи задачу під час переліку.

Натомість повторювана задача може читати команду з рядка конфігурації в базі даних застосунку. Переконайтеся, що роль бази даних із нижчим рівнем привілеїв може змінити саме цей рядок, що активна задача читає його після зміни, а значення передається до shell або еквівалентного засобу запуску команд з-під вищої OS identity. Доступ на запис до бази даних або значення, схоже на команду, самі по собі не доводять виконання; перевіряйте задачу й дозволи, не змінюючи рядок під час пасивного переліку.

Повідомлення в черзі також може містити URL, а не код. Якщо привілейований споживач отримує дані за цим URL і завантажує відповідь як Lua або інший виконуваний plugin, перевірте права видавця на точний exchange і routing key, прив’язку до черги, яку споживають, шлях отримання та завантаження plugin і effective identity worker-процесу. [RabbitMQ спрямовує опубліковані повідомлення через exchanges](https://www.rabbitmq.com/docs/exchanges); самі по собі listener брокера або дійсний логін не доводять доставлення повідомлення цьому worker-процесу. Перехоплені облікові дані брокера у відкритому тексті — окрема підказка, для підтвердження якої потрібні реальний доступ до захоплення пакетів і незашифрований трафік; вони не доводять право публікувати повідомлення. Lua plugin може запускати shell-команди через [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute), лише якщо цей API доступний у його runtime. Перевіряйте конфігурацію та код, не перехоплюючи трафік, не публікуючи повідомлення й не отримуючи plugin під час пасивного переліку.

Якщо привілейований Python-сервіс надає локальний HTTP- або socket endpoint, скрипт, доступний для читання, може розкрити шлях від введених даних до виконання коду, навіть якщо його дозволи не дають змоги змінити файл. Зіставте активний процес і identity unit із точним скриптом, listener, авторизацією маршруту та полями, контрольованими викликачем. Потім простежте ці поля крізь парсинг і валідацію до динамічного sink `eval()` або `exec()`. Зокрема, створення нового f-string із тексту запиту та його обчислення може інтерпретувати передані атакувальником поля підстановки як вирази Python ([попередження щодо Python `eval`](https://docs.python.org/3/library/functions.html#eval); [семантика f-string](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Сам факт збігу `eval` або прив’язки до loopback не доводить, що недовірений викликач може дістатися до sink; перевіряйте реальний потік даних і контроль доступу, не надсилаючи тестове навантаження під час переліку.

Окремо перевірте gate підписаних запитів для цього маршруту. Якщо доступний для читання вихідний код показує, що ключ підпису отримується з явно малого або передбачуваного простору можливих значень, а сервіс надає приклад дійсного підпису, підпис може більше не захищати привілейований sink `eval()`. Перевірте точний алгоритм отримання ключа та верифікатор, identity активного сервісу й локальний доступ викликачів, а також те, чи доходить підписане поле до sink; сам імпорт модуля Python [`random`](https://docs.python.org/3/library/random.html) або приклад підпису не доводять жодної з цих умов. Python також попереджає, що обмеження `__builtins__` [не є межею безпеки для недовірених даних `eval()`](https://docs.python.org/3/library/functions.html#eval). Аналізуйте ключ офлайн і не надсилайте підроблені запити під час пасивного переліку.

Порожній каталог `/etc/systemd/system/<unit>.service.d`, доступний для запису, має значення, навіть якщо сам unit-файл і всі наявні drop-in захищені: користувач може створити новий override `.conf`. Перевірте, чи поточна identity має право запису й пошуку в каталозі, чи завантажено unit і чи запускається він від root, а також чи відбудеться reload daemon із подальшим restart. Дозвіл на reload або restart, таймер чи наступне завантаження системи можуть активувати зміну; сам доступ до каталогу на запис не виконує її негайно.

Для запущених сервісів перевіряйте буквальні шляхи `EnvironmentFile=` із секції `[Service]` unit-файла, зокрема файли, назви яких не починаються з `.env`. Якщо користувач із низькими привілеями може прочитати такий файл, перелічіть назви ключів, схожі на облікові дані, наприклад `API_TOKEN` або `APP_SECRET_KEY`, не виводячи значення у спільні журнали. Перевіряючи фактичний unit, враховуйте drop-in overrides і необов’язковий префікс `-`. Можливість читання вказує на потенційне розкриття облікових даних; для підвищення привілеїв значення все одно має бути дійсним для привілейованої дії.

### Обробка недовірених завантажень із привілеями

Файловий watcher, запущений від root, може передавати файли з каталогу завантажень, доступного користувачам для запису, короткочасному parser або extractor. Відстежте батьківський скрипт чи сервіс активного watcher і перевірте точний каталог, хто може розміщувати там файли, дочірню команду та її аргументи, а також identity, з-під якої запускається дочірній процес. Знімок процесів може показати watcher, але пропустити extractor між завантаженнями. Не розміщуйте тестове навантаження й не запускайте watcher під час пасивного переліку.

Конкретний приклад — режим розпакування Binwalk (`-e`), який обробляє контрольовані атакувальником дані PFS. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) дозволяла PFS extractor записувати файли за межами призначеного каталогу, зокрема за шляхом plugin, який Binwalk міг завантажити пізніше. Виправлення було включено в [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), але дистрибутивні backport-патчі можуть залишати старішу версію у виводі; перш ніж оцінювати застосовність, перевірте стан безпеки встановленого пакета, наприклад у [трекері Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510). Сама встановлена версія Binwalk не доводить наявності шляху до підвищення привілеїв: привілейований процес має справді запускати розпакування над даними, які може контролювати користувач із нижчими привілеями.

### Заплановані збірки з локальними залежностями

Запланований `cargo run` повторно компілює вихідний код як користувач run-as цієї задачі. Перевірте локальні залежності `{ path = "..." }` у manifest, а також дозволи на вихідний код і батьківські каталоги кожної залежності, а не лише основного crate. Якщо користувач із нижчими привілеями може змінити залежність, яку компілює Cargo, а запланована задача запускає результат, скомпільований код може виконуватися з-під користувача run-as. Переконайтеся в ефективній команді планувальника, робочому каталозі, розв’язанні залежностей і тому, чи відбудеться повторна збірка; доступний для запису файл вихідного коду Rust деінде — лише підказка. Для пасивного аналізу достатньо прочитати manifest і метадані шляхів. Див. [документацію Cargo щодо залежностей за шляхом](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Файли framebuffer Xvfb

`Xvfb -fbdir <directory>` використовує файли memory-mapped з назвами `Xvfb_screen<n>` для своїх віртуальних екранів. Якщо активний процес Xvfb іншого користувача вказує на каталог, файли екрана в якому доступні поточному користувачу для читання, framebuffer може розкривати вміст робочого столу цього користувача. Перевірте процес, власника файла й дозволи разом; сам факт доступності файла для читання не доводить, що на екрані є корисний вміст. Спочатку перегляньте шляхи й метадані, не копіюючи зображення до спільного виводу переліку. Поведінку параметра `-fbdir` описано в [посібнику Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html).

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
