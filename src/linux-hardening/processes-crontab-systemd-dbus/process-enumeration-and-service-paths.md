# Enumeración de procesos y rutas de servicios

{{#include ../../banners/hacktricks-training.md}}

La pregunta útil es qué proceso privilegiado consume datos o código que puede controlar un usuario con menos privilegios. Inspecciona el árbol de procesos, el entorno activo, los archivos abiertos y la unidad o el script que inició cada candidato.

## Mapear procesos y propietarios

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Una relación padre-hijo entre usuarios puede ser normal, pero una transición inesperada justifica revisar el comando del proceso padre, sus argumentos, el ejecutable, el directorio de trabajo y los archivos a los que hace referencia. Usa [usuarios y sesiones](../user-information/user-and-session-triage.md) para interpretar el propietario y el contexto de inicio de sesión.

### Consolas locales de máquinas virtuales

Revisa las opciones `-spice` de un proceso QEMU junto con su dirección de escucha. [La documentación de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) indica que `disable-ticketing` permite que los clientes SPICE se conecten sin autenticación. Aunque un listener esté enlazado a la interfaz de loopback, otros usuarios locales del host podrían tener acceso. Confirma el listener activo, las opciones de autenticación y el acceso local antes de considerar que la línea de comandos expone una consola. El control de la consola afecta al **guest**; obtener una cuenta en el guest o cambiar su estado de arranque requiere condiciones independientes dentro del guest y no otorga root en el host de virtualización. Durante la enumeración pasiva, lee los argumentos del proceso y los metadatos del socket sin conectarte al guest ni reiniciarlo.

Una interfaz web accesible localmente puede ejecutar código con la cuenta de servicio, aunque el primer shell no pueda acceder a los archivos de esa cuenta. Por ejemplo, CVE-2023-0297 afectaba el manejo de `/flash/addcrypted2` de pyLoad cuando JavaScript no confiable llegaba a Js2Py con las importaciones de Python habilitadas; la [corrección upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deshabilitó `pyimport`. Correlaciona el propietario del proceso en ejecución, la dirección de escucha, la exposición del endpoint y el parche instalado o backport del proveedor antes de considerar un proceso pyLoad como una vía de escalada. El nombre de un proceso, un puerto abierto o la versión de un paquete, por sí solos, no prueban que exista exposición; la enumeración pasiva no debe enviar un payload de ejecución.

### Shells de inicio de sesión privilegiados que comparten un terminal

Un shell interactivo privilegiado que ejecuta `su --login <user>` sin un pseudoterminal independiente puede dejar su terminal compartido con el shell de inicio de sesión con menos privilegios. Si el archivo de inicio de ese usuario es controlable y el código que contiene puede usar `TIOCSTI` para inyectar entrada en el terminal, esa entrada podría llegar al shell privilegiado cuando este reanude la ejecución. [El manual de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) describe el riesgo de compartir el terminal y recomienda `su --pty`/`-P` para uso interactivo; `su -c` inicia una sesión independiente sin terminal de control. El riesgo depende del shell padre real, la relación entre terminales, el archivo de inicio de sesión objetivo y la política del kernel. Un nombre de proceso o un argumento `su -l` por sí solos solo justifican revisar el caso.

Inspecciona el árbol de procesos observado y las columnas TTY; después, revisa el lanzador legible y la propiedad/permisos del archivo de inicio. En Linux, `/proc/sys/dev/tty/legacy_tiocsti` puede ayudar a interpretar la política, si está presente; su ausencia no demuestra que el sistema sea seguro. [El manual de Linux de `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) señala que, desde Linux 6.2, la operación puede requerir `CAP_SYS_ADMIN` cuando este sysctl es falso. No invoques el ioctl solo para enumerar el host.

En algunos casos, una cuenta de base de datos puede modificar el archivo de inicio del usuario objetivo sin tener acceso de escritura directo al sistema de archivos. `COPY ... TO 'filename'` del lado del servidor de PostgreSQL escribe con la cuenta de sistema operativo del servidor de base de datos, pero [PostgreSQL limita](https://www.postgresql.org/docs/current/sql-copy.html) esta forma de archivo a superusuarios de la base de datos o a roles como `pg_write_server_files`. Confirma tanto el rol de la base de datos como los permisos del archivo para la cuenta del sistema operativo del servidor; una cadena de conexión de aplicación por sí sola no otorga permisos de escritura en archivos. Al evaluar la cadena, analiza por separado las capacidades del lanzador privilegiado y las de la cuenta de base de datos.

## Inspeccionar artefactos de ejecución-vesm

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Los ejecutables eliminados y los archivos eliminados pero abiertos siguen referenciados hasta que se cierra su último descriptor. Pueden conservar pruebas o secretos accesibles. Los entornos y la memoria de los procesos pueden contener credenciales, pero leer otro proceso está sujeto a restricciones de propiedad, opciones de montaje de `/proc`, la política ptrace de Yama y otros controles de seguridad. Consulta [descriptores de archivo](../main-system-information/filesystem-links-and-file-descriptors.md) y [búsqueda de credenciales en post-exploitation](../post-exploitation/README.md) para ver técnicas relacionadas.

Las trazas de syscall guardadas constituyen otro límite de permisos de archivo. [`strace` registra los argumentos de syscall en un archivo de salida](https://man7.org/linux/man-pages/man1/strace.1.html), por lo que una traza legible de los [argumentos de `execve`](https://man7.org/linux/man-pages/man2/execve.2.html) podría revelar una contraseña que un job privilegiado pasó en su línea de comandos. Primero comprueba que el usuario actual puede leer esa traza concreta y que el argumento realmente contiene una credencial; demostrar después que la credencial es aceptada al cambiar a una cuenta Unix requiere pruebas por separado. Los metadatos del archivo son una pista pasiva útil, sin tener que escanear todas las trazas ni mostrar su contenido durante el reconocimiento rutinario.

## Sockets de automatización de oficina privilegiados

LibreOffice y OpenOffice pueden exponer su API UNO mediante un argumento `--accept=socket,host=<host>,port=<port>;urp;`. Un proceso de oficina propiedad de root con un endpoint accesible podría permitir que un usuario local con menos privilegios invoque servicios de la API en el contexto de seguridad de ese proceso. El servicio `SystemShellExecute` incluye una operación para ejecutar un comando del sistema. Enlazarlo a loopback limita la accesibilidad remota, pero el socket sigue siendo accesible para los usuarios locales, salvo que otro control lo impida.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Correlaciona el propietario del proceso, el argumento `--accept` exacto y la dirección y el puerto en escucha actuales. Un acceptor configurado que no pudo enlazarse es solo una pista; no te conectes a la API ni la invoques durante la enumeración pasiva. Evita iniciar una instancia de office con privilegios solo para probar esta condición.

## Memoria compartida System V consumida por procesos con privilegios

Un helper propiedad de root puede crear un segmento de memoria compartida System V en el que otro usuario pueda escribir. Si después el helper confía en los datos de ese segmento en un comando de shell u otra operación sensible, el segmento cruza un límite de privilegios, aunque el ejecutable y sus archivos estén protegidos. `shmget()` toma los permisos de acceso de los nueve bits inferiores de sus flags; el modo `0666` permite que otros usuarios escriban, mientras que un flag `IPC_CREAT` no reduce esos permisos. Inspecciona los segmentos activos de forma pasiva con `ipcs -m` y correlaciona su propietario, modo y duración con el proceso con privilegios y el manejo de sus entradas. Un segmento con permisos de escritura para todos no demuestra por sí solo la ejecución de comandos.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Los segmentos de System V son distintos de los archivos de memoria compartida POSIX en `/dev/shm`. Un segmento creado solo por un instante puede no aparecer en una única captura de `ipcs`, por lo que una salida vacía no descarta que un helper use memoria compartida. Revisa su código fuente o el comportamiento del binario, así como cualquier regla de `sudo` que lo ejecute; no invoques el helper con privilegios solo para hacer que aparezca un segmento durante la enumeración. La [guía de IPC namespaces](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explica cómo los namespaces afectan la visibilidad.<sup>[[2]](#references)[[3]](#references)</sup>

## Consul agent script checks

Consul puede ejecutar comprobaciones de estado mediante scripts con la identidad del sistema operativo de su agent. Si un agent se ejecuta como root, habilita `enable_script_checks` y permite que un usuario con menos privilegios registre un servicio con una comprobación mediante script a través de la API HTTP local, ese usuario podría provocar la ejecución de comandos como root. Vincular la API solo a `127.0.0.1` sigue permitiendo que los usuarios locales accedan a ella. El ajuste `enable_local_script_checks` es más restrictivo: excluye las comprobaciones mediante script enviadas a través de registros de la API HTTP. Cuando las ACL de Consul están habilitadas, el registro de servicios requiere `service:write`; una línea `acl.default_policy=allow` por sí sola no demuestra que un usuario anónimo pueda registrar servicios. Revisa conjuntamente la identidad real del agent, los ajustes cargados, el enlace de la API y la autorización.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Sigue los argumentos `-config-dir` y `-config-file` del agent en ejecución hasta la configuración correspondiente, e inspecciona solo los nombres y valores de los campos de comprobación de scripts y ACL. Los archivos de configuración también pueden contener claves o tokens de gossip; evita pegarlos en registros compartidos. No registres un servicio ni ejecutes una comprobación de estado solo para enumerar esta condición.

Existe una ruta independiente mediante archivos locales cuando un usuario con menos privilegios puede **escribir y buscar** en el directorio indicado por `-config-dir` de un agent ejecutado como root: podría cargarse desde ese directorio una nueva definición de servicio `.hcl` o `.json`. Los permisos de búsqueda y escritura en el directorio pueden permitir agregar un archivo incluso cuando se deniega listar su contenido. Para ejecutar comandos como root, confirma que el agent realmente carga ese directorio, que su configuración **efectiva** de comprobación de scripts permite definiciones locales, que se carga la definición y que el agent conserva los privilegios de root. [La documentación de Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) indica qué configuraciones y definiciones de comprobación de estado se pueden recargar; habilitar las comprobaciones de scripts podría requerir un reinicio, así que verifica el comportamiento de la versión instalada. Cuando las ACL protegen el agent, [`consul reload` requiere `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); el permiso de escritura en KV no lo proporciona. Considera los metadatos de directorios con permisos de escritura como una señal para revisar, no como prueba de una recarga, un reinicio o una ejecución de comandos autorizados. Inspecciona las rutas, los permisos y las políticas sin escribir en la configuración ni llamar a la API.

## Sigue la cadena de ejecución del servicio

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Comprueba la unidad, los drop-ins, `EnvironmentFile=`, los scripts auxiliares, los comandos relativos, los directorios con permisos de escritura y la activación por socket. Una unidad propiedad de root aún puede ser insegura si lee un archivo de configuración o un script modificable por un usuario. La página sobre [escritura arbitraria de archivos](../interesting-files-permissions/write-to-root.md) cubre vías habituales de abuso de servicios y unidades. Supervisa los trabajos de corta duración con [pspy](https://github.com/DominicBreuker/pspy) o telemetría de auditoría y procesos cuando una única consulta a `ps` no los detecte.

Para un servicio **xinetd** personalizado, correlaciona la sección habilitada (`server`, `user` y los controles de acceso) con el listener activo y el ejecutable exacto. El [ajuste `user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) elige la identidad del proceso generado, mientras que el bit set-user-ID del ejecutable puede cambiar por separado su identidad efectiva si [`execve` permite esa transición](https://man7.org/linux/man-pages/man2/execve.2.html). Un binario privilegiado accesible que acepte entradas no confiables merece una revisión offline del código fuente o del desensamblado para buscar errores de seguridad de memoria, como una [conversión de cadena de `scanf` sin límites](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) hacia un búfer de tamaño fijo. La asociación del servicio y los metadatos de set-user-ID son indicios, no pruebas de que exista ese error; no envíes entradas que provoquen fallos ni depures el servicio privilegiado activo durante la enumeración pasiva.

Si hay código fuente legible para un listener privilegiado personalizado, revisa cada longitud controlada por quien llama que se use en una operación de copia como [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Comprobar solo que el índice de escritura actual está dentro de un búfer fijo no demuestra que la **longitud de copia** quepa en el espacio restante; verifica `copy_length <= capacity - index` después de confirmar que el índice está dentro de los límites, y comprueba el signo y el desbordamiento aritmético. Esto es solo una pista para la revisión si la entrada llega a esa operación, el listener es accesible para el usuario con menos privilegios y el proceso conserva una identidad efectiva superior. Inspecciona offline el código fuente y los metadatos del proceso; no envíes entradas que provoquen fallos al servicio activo durante la enumeración.

En sistemas que usan **Upstart**, las definiciones de trabajos del sistema pueden estar en `/etc/init/*.conf`. Un archivo de trabajo modificable por el usuario actual es relevante cuando el daemon init activo carga ese archivo concreto, su sección `script` o `exec` se ejecuta con una identidad de mayores privilegios y el usuario puede iniciarlo mediante un comando `initctl` permitido u otro desencadenante real. Un permiso de `sudo initctl` por sí solo no demuestra que haya archivos de trabajo modificables ni que se vaya a ejecutar un trabajo modificado. Comprueba los permisos del archivo de trabajo exacto, la identidad efectiva de ejecución, el daemon activo y el desencadenante, sin editar ni iniciar el trabajo durante la enumeración. Consulta los manuales de [configuración de trabajos de Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) y [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un archivo de contraseñas de autologin legible, como `/etc/autologin/passwd` en sistemas cuyo [trabajo de arranque lee esa ruta exacta](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), es un indicio de exposición de credenciales. Confirma que el trabajo de arranque está instalado y usa el archivo; después, verifica por separado si la contraseña es válida para otra cuenta o servicio local. El nombre del archivo por sí solo no demuestra la reutilización de la contraseña; registra la ruta y los metadatos de acceso sin incluir la contraseña en resultados de enumeración compartidos.

`ExecStart=` de una unidad o un comando programado pueden revelar la ruta exacta de un script dentro de un directorio cuyo contenido no se puede listar. El [permiso de búsqueda de directorios](https://man7.org/linux/man-pages/man7/path_resolution.7.html) aún puede permitir que la identidad actual recorra esa ruta conocida; confirma el permiso de búsqueda en cada directorio padre y el permiso de lectura del archivo, en lugar de asumir que no poder listar el directorio lo protege. Un script legible puede contener una credencial para transferencias, pero acceder a otra cuenta requiere que esa credencial siga siendo válida y que esa cuenta la acepte de forma independiente. Registra la ruta y las pruebas de permisos sin mostrar secretos en registros compartidos.

En un script CommonJS de Node.js programado, revisa las importaciones sin ruta explícita, como `require('package')`, aunque el script sea de solo lectura. [Node busca `node_modules` junto al archivo que importa y luego en sus directorios ancestros](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), antes de recurrir a las rutas globales configuradas. Un usuario con menos privilegios que pueda **escribir y buscar** en uno de esos directorios ancestros podría crear un paquete que coincida antes. Confirma que se alcanza la importación exacta, que el paquete seleccionado no es un módulo integrado, que se puede crear o modificar la ruta pertinente, que el módulo se resuelve allí en el runtime instalado y que un trabajo con mayores privilegios lo cargará en una ejecución futura. Los metadatos de directorios padres modificables son solo una pista para la revisión; inspecciona pasivamente el script y el programador, sin instalar un módulo ni activar el trabajo.

Un índice privado de paquetes de Python es otra frontera de confianza cuando un trabajo automatizado instala paquetes con una identidad de SO diferente. Correlaciona el trabajo exacto y la cuenta de ejecución con el índice configurado, los nombres de los paquetes seleccionados y la posibilidad de que un usuario con menos privilegios publique o sustituya un paquete que el trabajo vaya a instalar realmente. La compilación de una distribución de código fuente puede ejecutar su backend de compilación o el `setup.py` heredado con la identidad del instalador; importar el paquete instalado es una vía de ejecución distinta. Un listener de índice, un hash de contraseña de carga legible o el nombre de un archivo de paquete no demuestran por sí solos esa cadena. Revisa el trabajo, la autorización del índice y la procedencia del paquete sin cargar ni instalar nada durante la enumeración. Consulta la [interfaz de sistemas de compilación de pip](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones para instalaciones seguras](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agente privilegiado puede consultar periódicamente una cola de tareas administrada por otro servicio web o contenedor. Si una identidad con menos confianza puede escribir en la base de datos de tareas del servicio, determina si esas filas se sirven realmente al agente y si una tarea de comandos se ejecuta con la identidad de SO del agente. Confirma por separado el acceso de escritura a la base de datos, la sesión de destino o la clave de enrutamiento, la consulta activa, la autorización de tareas y el usuario efectivo del agente. Ser root dentro de un contenedor no implica por sí mismo acceso como root en el host; la frontera solo se cruza si un consumidor con privilegios en el host ejecuta datos de tareas controlados por un atacante. Inspecciona los metadatos de procesos, archivos de base de datos y servicios sin modificar la cola ni enviar una tarea durante la enumeración.

En cambio, un trabajo recurrente puede leer un comando de una fila de configuración de una base de datos de la aplicación. Confirma que el rol de base de datos con menos privilegios puede modificar esa fila concreta, que el trabajo activo la lee después del cambio y que el valor llega a un shell o ejecutor de comandos equivalente bajo una identidad de SO con mayores privilegios. El acceso de escritura a la base de datos o un valor que parezca un comando no demuestran por sí solos que vaya a ejecutarse; inspecciona el trabajo y los permisos sin modificar la fila durante la enumeración pasiva.

Un mensaje en cola también puede contener una URL en vez de código. Si un consumidor privilegiado obtiene esa URL y carga la respuesta como un plugin ejecutable de Lua u otro tipo, verifica los permisos del publicador sobre el exchange y la clave de enrutamiento exactos, la vinculación con la cola consumida, la ruta de obtención y carga del plugin, y la identidad efectiva del worker. [RabbitMQ enruta los mensajes publicados a través de exchanges](https://www.rabbitmq.com/docs/exchanges); un listener del broker o unas credenciales válidas no demuestran por sí solos la entrega a este worker. Las credenciales del broker capturadas en texto claro son un indicio independiente que requiere acceso real a una captura de paquetes y tráfico legible; no demuestran autorización para publicar. Un plugin de Lua puede invocar comandos de shell mediante [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) solo si esa API está disponible en su runtime. Revisa la configuración y el código sin capturar tráfico, publicar mensajes ni obtener un plugin durante la enumeración pasiva.

Cuando un servicio privilegiado de Python expone un endpoint HTTP o socket local, un script legible puede revelar una ruta desde la entrada hasta la ejecución de código, aunque sus permisos impidan modificarlo. Correlaciona el proceso activo y la identidad de la unidad con el script exacto, el listener, la autorización de la ruta y los campos controlables por quien llama. Después, sigue esos campos durante el análisis y la validación hasta llegar a un punto de ejecución dinámica `eval()` o `exec()`. En particular, construir un f-string nuevo a partir del texto de una solicitud y evaluarlo puede interpretar los campos de sustitución proporcionados por un atacante como expresiones de Python ([advertencia de Python sobre `eval`](https://docs.python.org/3/library/functions.html#eval); [semántica de f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Encontrar `eval` o una vinculación a loopback no demuestra que una entrada no confiable llegue al punto de ejecución; revisa el flujo de datos y los controles de acceso reales sin enviar una carga de prueba durante la enumeración.

Un control de solicitudes firmadas en esa ruta requiere su propia revisión. Si el código fuente legible deriva la clave de firma a partir de un espacio de resultados demostrablemente pequeño o predecible, y el servicio expone una muestra firmada válida, la firma quizá ya no proteja un punto de ejecución privilegiado `eval()`. Verifica la derivación exacta de la clave y el verificador, la identidad del servicio activo y el acceso de clientes locales, y si el campo firmado llega al punto de ejecución; importar el módulo [`random` de Python](https://docs.python.org/3/library/random.html) o disponer de una firma de muestra no demuestra ninguna de esas condiciones. Python también advierte que restringir `__builtins__` [no es una frontera de seguridad para entradas no confiables de `eval()`](https://docs.python.org/3/library/functions.html#eval). Analiza las claves offline y no envíes solicitudes falsificadas durante la enumeración pasiva.

Un directorio `/etc/systemd/system/<unit>.service.d` vacío pero modificable es relevante aunque el archivo de unidad y todos los drop-ins existentes estén protegidos: el usuario podría crear un nuevo override `.conf`. Comprueba que la identidad actual puede escribir y buscar en el directorio, que la unidad está cargada y se ejecuta como root, y si se producirá una recarga del daemon seguida de un reinicio. Un permiso de recarga o reinicio, un timer o un arranque posterior pueden hacer efectivo el cambio; el acceso de escritura al directorio por sí solo no lo ejecuta de inmediato.

En servicios en ejecución, sigue las rutas literales de `EnvironmentFile=` en la sección `[Service]` de la unidad, incluidos los archivos cuyos nombres no empiezan por `.env`. Si un usuario con pocos privilegios puede leer alguno, enumera nombres de claves que parezcan credenciales, como `API_TOKEN` o `APP_SECRET_KEY`, sin mostrar sus valores en registros compartidos. Al evaluar la unidad efectiva, comprueba los overrides de drop-ins y los prefijos opcionales `-`. La legibilidad es un indicio de exposición de credenciales; para que permita escalar privilegios, el valor aún debe ser válido para una acción privilegiada.

### Procesamiento privilegiado de cargas no confiables

Un supervisor de archivos ejecutado como root puede entregar archivos de un directorio de cargas modificable por usuarios a un analizador o extractor de corta duración. Sigue el script padre o el servicio del supervisor activo y confirma el directorio exacto, quién puede depositar archivos allí, el comando hijo y sus argumentos, y la identidad con la que se ejecuta el proceso hijo. Una instantánea de procesos puede mostrar el supervisor y pasar por alto el extractor entre cargas. No coloques una carga de prueba ni actives el supervisor durante la enumeración pasiva.

Un ejemplo concreto es el modo de extracción de Binwalk (`-e`) al procesar datos PFS controlados por un atacante. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permitía que el extractor PFS escribiera fuera del directorio previsto, incluida una ruta de plugins que Binwalk podía cargar posteriormente. La versión upstream incluyó la corrección en [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), pero los backports de las distribuciones pueden conservar una versión mostrada más antigua; comprueba el estado de seguridad del paquete instalado, por ejemplo en el [tracker de Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), antes de determinar si es aplicable. Tener Binwalk instalado, por sí solo, no demuestra una vía de escalada de privilegios: un proceso con mayores privilegios debe invocar realmente la extracción con una entrada que el usuario con menos privilegios pueda controlar.

### Compilaciones programadas con dependencias locales

Un `cargo run` programado vuelve a compilar el código fuente con la identidad de ejecución del trabajo. Inspecciona las dependencias locales `{ path = "..." }` del manifiesto, así como los permisos del código fuente y los directorios padres de cada dependencia, no solo los de la crate principal. Si un usuario con menos privilegios puede modificar una dependencia que Cargo compila y el trabajo programado ejecuta el resultado, el código compilado puede ejecutarse con la identidad de ejecución del trabajo. Confirma el comando efectivo del programador, el directorio de trabajo, la resolución de dependencias y si se producirá una recompilación; un archivo de código fuente de Rust modificable en otra ubicación es solo un indicio. Para una evaluación pasiva basta con leer el manifiesto y los metadatos de las rutas. Consulta la [documentación de Cargo sobre dependencias por ruta](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Archivos de framebuffer de Xvfb

`Xvfb -fbdir <directory>` utiliza archivos mapeados en memoria llamados `Xvfb_screen<n>` para sus pantallas virtuales. Si un proceso Xvfb activo de otro usuario indica un directorio cuyos archivos de pantalla puede leer el usuario actual, el framebuffer podría exponer el contenido del escritorio de ese usuario. Confirma conjuntamente el proceso, la propiedad de los archivos y sus permisos; que un archivo sea legible no demuestra por sí solo que contenga información útil en pantalla. Primero inspecciona las rutas y los metadatos, sin copiar datos de imagen a resultados de enumeración compartidos. El [manual de Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) documenta el comportamiento de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
