# Enumeración de procesos y rutas de servicios

{{#include ../../banners/hacktricks-training.md}}

La pregunta útil es qué proceso privilegiado consume datos o código que un usuario con menos privilegios puede influir. Inspecciona el árbol de procesos, el entorno activo, los archivos abiertos y la unidad o el script que inició cada candidato.

## Mapear procesos y propietarios

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Una relación padre-hijo entre usuarios distintos puede ser normal, pero una transición inesperada justifica revisar el comando del proceso padre, sus argumentos, el ejecutable, el directorio de trabajo y los archivos referenciados. Usa [usuarios y sesiones](../user-information/user-and-session-triage.md) para interpretar el propietario y el contexto de inicio de sesión.

### Consolas de máquinas virtuales locales

Revisa las opciones `-spice` de un proceso QEMU junto con su dirección de escucha. La [documentación de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) indica que `disable-ticketing` permite que los clientes SPICE se conecten sin autenticación. Aunque un listener esté asociado a loopback, otros usuarios locales del host podrían alcanzarlo. Confirma el listener activo, las opciones de autenticación y el acceso local antes de considerar que la línea de comandos expone una consola. El control de la consola afecta al **guest**; obtener una cuenta en el guest o cambiar su estado de arranque requiere condiciones adicionales en el guest y no otorga root en el host de virtualización. Durante la enumeración pasiva, lee los argumentos del proceso y los metadatos del socket sin conectarte al guest ni reiniciarlo.

Una interfaz web accesible localmente puede ejecutar código con la cuenta del servicio, aunque el primer shell no pueda acceder a los archivos de esa cuenta. Por ejemplo, CVE-2023-0297 afectaba el manejo de `/flash/addcrypted2` de pyLoad cuando JavaScript no confiable llegaba a Js2Py con las importaciones de Python habilitadas; la [corrección upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deshabilitó `pyimport`. Antes de considerar un proceso pyLoad como una vía de escalada, correlaciona el propietario del proceso activo, la dirección de escucha, la exposición del endpoint y el parche instalado o el backport del proveedor. El nombre de un proceso, un puerto abierto o la versión de un paquete por sí solos no demuestran exposición; la enumeración pasiva no debe enviar un payload de ejecución.

### Shells de inicio de sesión privilegiados que comparten un terminal

Un shell interactivo privilegiado que ejecuta `su --login <user>` sin un pseudo-terminal independiente puede dejar su terminal compartido con el shell de inicio de sesión con menos privilegios. Si el archivo de inicio de ese usuario se puede controlar y el código que contiene puede usar `TIOCSTI` para inyectar entrada en el terminal, esa entrada podría llegar al shell privilegiado cuando se reanude. El [manual de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) describe el riesgo de compartir el terminal y recomienda `su --pty`/`-P` para el uso interactivo; `su -c` inicia una sesión separada sin terminal de control. El riesgo depende del shell padre real, la relación entre terminales, el archivo de inicio de destino y la política del kernel. El nombre de un proceso o el argumento `su -l` por sí solos son solo un indicio que conviene revisar.

Inspecciona el árbol de procesos observado y las columnas TTY; después, revisa el lanzador legible y la propiedad y los permisos del archivo de inicio. En Linux, `/proc/sys/dev/tty/legacy_tiocsti` puede ayudar a interpretar la política cuando está presente; su ausencia no demuestra que el sistema sea seguro. El [manual de `TIOCSTI` de Linux](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) señala que, desde Linux 6.2, la operación puede requerir `CAP_SYS_ADMIN` cuando este sysctl es falso. No invoques el ioctl para limitarte a enumerar el host.

En ocasiones, una cuenta de base de datos puede modificar el archivo de inicio del usuario de destino sin acceso directo de escritura al sistema de archivos. En PostgreSQL, `COPY ... TO 'filename'` en el servidor escribe con la cuenta del sistema operativo del servidor, pero [PostgreSQL limita](https://www.postgresql.org/docs/current/sql-copy.html) esta forma de archivo a superusuarios de la base de datos o roles como `pg_write_server_files`. Confirma tanto el rol de la base de datos como los permisos de archivos del sistema operativo del servidor; una cadena de conexión de una aplicación no otorga por sí sola autorización para escribir archivos. Al evaluar la cadena, considera por separado las capacidades del lanzador privilegiado y las de la cuenta de base de datos.

## Inspeccionar artefactos de ejecución

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Los ejecutables eliminados y los archivos eliminados pero aún abiertos siguen referenciados hasta que se cierra su último descriptor. Pueden conservar evidencia o secretos accesibles. Los entornos y la memoria de los procesos pueden contener credenciales, pero leer otro proceso está sujeto a restricciones de propiedad, opciones de montaje de `/proc`, la política ptrace de Yama y otros controles de seguridad. Consulta [descriptores de archivo](../main-system-information/filesystem-links-and-file-descriptors.md) y [búsqueda de credenciales durante el post-exploitation](../post-exploitation/README.md) para conocer técnicas relacionadas.

Los rastros de syscall guardados están sujetos a otras restricciones de permisos de archivo. [`strace` registra los argumentos de syscall en un archivo](https://man7.org/linux/man-pages/man1/strace.1.html), por lo que un rastro legible de los argumentos de [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) puede revelar una contraseña que un trabajo privilegiado pasó en su línea de comandos. Primero confirma que el usuario actual puede leer el rastro concreto y que el argumento realmente contiene una credencial; cualquier transición posterior a una cuenta Unix requiere pruebas independientes de que la credencial es aceptada allí. Los metadatos del archivo son una pista pasiva útil, sin necesidad de escanear todos los rastros ni mostrar su contenido durante la enumeración rutinaria.

## Sockets de automatización de oficina privilegiados

LibreOffice y OpenOffice pueden exponer su API UNO mediante un argumento `--accept=socket,host=<host>,port=<port>;urp;`. Un proceso de oficina propiedad de root con un endpoint accesible puede permitir que un usuario local con menos privilegios invoque servicios de la API en el contexto de seguridad de ese proceso. El servicio `SystemShellExecute` incluye una operación para ejecutar un comando del sistema. Enlazar el socket a loopback limita la accesibilidad remota, pero sigue dejando el socket accesible a los usuarios locales, salvo que otro control impida el acceso.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Correlaciona el propietario del proceso, el argumento exacto `--accept` y la dirección y el puerto en los que está escuchando actualmente. Un acceptor configurado que no haya podido enlazarse es solo una pista; no te conectes a la API ni la invoques durante la enumeración pasiva. Evita iniciar una instancia de office con privilegios únicamente para probar esta condición.

## Memoria compartida de System V consumida por procesos con privilegios

Un helper propiedad de root puede crear un segmento de memoria compartida de System V en el que otro usuario pueda escribir. Si luego el helper confía en los datos de ese segmento para ejecutar un comando de shell u otra operación sensible, el segmento cruza un límite de privilegios, aunque el ejecutable y sus archivos estén protegidos. `shmget()` toma los permisos de acceso de los nueve bits inferiores de sus flags; el modo `0666` permite que otros usuarios escriban, mientras que un flag `IPC_CREAT` no restringe esos permisos. Inspecciona pasivamente los segmentos activos con `ipcs -m` y correlaciona su propietario, modo y duración con el proceso con privilegios y su manejo de la entrada. Un segmento con permisos de escritura para todos no demuestra por sí solo que pueda ejecutarse un comando.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Los segmentos System V son distintos de los archivos de memoria compartida POSIX en `/dev/shm`. Un segmento creado solo por un instante puede no aparecer en una única instantánea de `ipcs`, así que una salida vacía no descarta que un helper use memoria compartida. Revisa su código fuente o el comportamiento del binario y cualquier regla de `sudo` que lo ejecute; no invoques el helper con privilegios solo para hacer aparecer un segmento durante el inventario. La [guía de IPC namespace](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explica cómo los namespaces afectan a la visibilidad.<sup>[[2]](#references)[[3]](#references)</sup>

## Comprobaciones de scripts del agente de Consul

Consul puede ejecutar comprobaciones de estado de scripts con la identidad del sistema operativo de su agente. Si un agente se ejecuta como root, habilita `enable_script_checks` y permite que un usuario con menos privilegios registre un servicio con una comprobación de script a través de la API HTTP local, ese usuario puede hacer que se ejecuten comandos como root. Vincular la API solo a `127.0.0.1` sigue permitiendo que los usuarios locales accedan a ella. El ajuste `enable_local_script_checks` es más restrictivo: excluye las comprobaciones de scripts enviadas mediante registros a través de la API HTTP. Cuando las ACL de Consul están habilitadas, el registro de servicios requiere `service:write`; una línea `acl.default_policy=allow` por sí sola no demuestra que un llamador anónimo pueda registrar servicios. Revisa conjuntamente la identidad real del agente, los ajustes cargados, la vinculación de la API y la autorización.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Sigue los argumentos `-config-dir` y `-config-file` del agente en ejecución hasta llegar a la configuración pertinente, e inspecciona únicamente los nombres y valores de los campos de script-check y ACL. Los archivos de configuración también pueden contener claves o tokens de gossip; evita pegarlos en registros compartidos. No registres un servicio ni ejecutes un health check solo para enumerar esta condición.

Existe una ruta independiente mediante archivos locales cuando un usuario con menos privilegios puede **escribir y buscar** en el directorio indicado por `-config-dir` de un agente ejecutado como root: es posible que se cargue desde ese directorio una nueva definición de servicio `.hcl` o `.json`. Los permisos de búsqueda y escritura del directorio pueden permitir agregar un archivo aunque se deniegue listar su contenido. Para confirmar la ejecución de comandos como root, comprueba que el agente realmente carga ese directorio, que su configuración **efectiva** de script-check permite definiciones locales, que la definición se carga y que el agente conserva los privilegios de root. [Consul documents](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) qué configuraciones y definiciones de health check se pueden recargar; habilitar los script checks puede requerir un reinicio, así que verifica el comportamiento de la versión instalada. Cuando las ACL protegen al agente, [`consul reload` requires `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); el permiso de escritura de KV por sí solo no lo concede. Considera los metadatos de directorios con permisos de escritura como una señal para revisar, no como prueba de una recarga, un reinicio o una ejecución de comandos autorizados. Inspecciona las rutas, los permisos y las políticas sin escribir configuraciones ni llamar a la API.

## Sigue la cadena de ejecución del servicio

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Comprueba la unidad, los drop-ins, `EnvironmentFile=`, los scripts auxiliares, los comandos relativos, los directorios con permisos de escritura y la activación de sockets. Una unidad propiedad de root puede seguir siendo insegura si lee un archivo de configuración o un script que un usuario puede modificar. La página sobre [escritura arbitraria de archivos](../interesting-files-permissions/write-to-root.md) cubre rutas habituales de abuso de servicios y unidades. Supervisa los jobs de corta duración con [pspy](https://github.com/DominicBreuker/pspy) o con telemetría de auditoría/procesos cuando una consulta puntual de `ps` no los detecte.

Para un servicio **xinetd** personalizado, correlaciona las opciones `server`, `user` y los controles de acceso de la stanza habilitada con el listener activo y el ejecutable exacto. La opción [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) determina la identidad del proceso iniciado, mientras que el bit set-user-ID del ejecutable puede cambiar por separado su identidad efectiva si [`execve` permite esa transición](https://man7.org/linux/man-pages/man2/execve.2.html). Un binario privilegiado accesible que acepta datos no confiables merece una revisión offline del código fuente o del desensamblado para detectar errores de seguridad de memoria, como una conversión de cadena [`scanf` sin límites](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) a un buffer de tamaño fijo. El mapeo del servicio y los metadatos set-user-ID son indicios, no pruebas de que exista ese tipo de error; no envíes entradas que provoquen fallos ni depures el servicio privilegiado en ejecución durante la enumeración pasiva.

Para un listener privilegiado personalizado con código fuente legible, revisa cada longitud controlada por el caller que se use en una operación de copia, como [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Comprobar únicamente que el índice de escritura actual está dentro de un buffer fijo no demuestra que la **longitud de copia** quepa en el espacio restante; verifica `copy_length <= capacity - index` después de confirmar que el índice está dentro de los límites, y comprueba los tipos con signo y el desbordamiento aritmético. Esto es solo un indicio para la revisión si la entrada llega a esa operación, el listener es accesible para el usuario con menos privilegios y el proceso conserva una identidad efectiva superior. Inspecciona offline el código fuente y los metadatos del proceso; no envíes entradas que provoquen fallos al servicio en ejecución durante la enumeración.

En sistemas que usan **Upstart**, las definiciones de jobs del sistema pueden estar en `/etc/init/*.conf`. Un archivo de job que el usuario actual puede modificar es relevante si el daemon init activo carga ese archivo concreto, su stanza `script` o `exec` se ejecuta con una identidad más privilegiada y el usuario puede iniciarlo mediante un comando `initctl` permitido u otro desencadenante real. Un permiso sudo para `initctl`, por sí solo, no demuestra que se pueda modificar ningún archivo de job ni que vaya a ejecutarse un job modificado. Comprueba los permisos del archivo de job exacto, la configuración efectiva de run-as, el daemon activo y el desencadenante, sin editar ni iniciar el job durante la enumeración. Consulta los manuales de [configuración de jobs de Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) y [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un archivo de contraseñas de autologin legible, como `/etc/autologin/passwd` en sistemas cuyo [job de arranque lee esa ruta exacta](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), es un indicio de exposición de credenciales. Confirma que el job de arranque está instalado y usa el archivo; luego verifica por separado si la contraseña es válida para otra cuenta o servicio local. El nombre del archivo, por sí solo, no demuestra que se reutilice la contraseña; registra la ruta y los metadatos de acceso sin incluir la contraseña en la salida compartida de enumeración.

El `ExecStart=` de una unidad o un comando programado puede revelar la ruta exacta de un script dentro de un directorio cuyo contenido no se puede listar. El [permiso de búsqueda del directorio](https://man7.org/linux/man-pages/man7/path_resolution.7.html) aún puede permitir que la identidad actual recorra esa ruta conocida; confirma el permiso de búsqueda en cada directorio padre y el permiso de lectura del archivo, en lugar de asumir que un listado fallido del directorio lo protege. Un script legible puede contener una credencial para transferencias, pero el acceso a otra cuenta requiere que esa credencial siga siendo válida y que se acepte allí de forma independiente. Registra la ruta y las pruebas de permisos sin imprimir valores secretos en logs compartidos.

En un script CommonJS de Node.js programado, revisa las importaciones sin ruta explícita, como `require('package')`, aunque el script sea de solo lectura. [Node busca `node_modules` junto al archivo que importa y luego en sus directorios ancestros](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), antes de recurrir a las rutas globales configuradas. Un usuario con menos privilegios que pueda **escribir y buscar** en uno de esos directorios ancestros podría crear un paquete que coincida antes en la búsqueda. Confirma que se alcanza la importación exacta, que el paquete seleccionado no es un módulo integrado, que se puede crear o modificar la ruta correspondiente, que el módulo se resuelve allí en el runtime instalado y que un job más privilegiado lo cargará en una ejecución futura. Los metadatos de un directorio padre con permisos de escritura son solo una pista para la revisión; inspecciona el script y el scheduler de forma pasiva, sin instalar un módulo ni activar el job.

Un índice privado de paquetes de Python es otro límite de confianza cuando un job automatizado instala paquetes con otra identidad del SO. Correlaciona el job exacto y la cuenta run-as con el índice configurado, los nombres de los paquetes seleccionados y la posibilidad de que un usuario con menos privilegios publique o reemplace un paquete que el job vaya a instalar realmente. Crear una distribución de código fuente puede ejecutar su backend de compilación o el `setup.py` heredado con la identidad del instalador; importar el paquete instalado es una ruta de ejecución distinta. Un listener de índice, un hash de contraseña de subida legible o el nombre de un paquete no demuestran por sí solos esa cadena. Revisa el job, la autorización del índice y la procedencia del paquete, sin subir ni instalar nada durante la enumeración. Consulta la [interfaz de sistemas de compilación de pip](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones para instalaciones seguras](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agente privilegiado puede consultar periódicamente una cola de tareas gestionada por un servicio web o contenedor independiente. Si una identidad de menor confianza puede escribir en la base de datos de tareas del servicio, determina si esas filas se sirven realmente al agente y si una tarea de comandos se ejecuta con la identidad del SO del agente. Confirma por separado el acceso de escritura a la base de datos, la sesión de destino o clave de enrutamiento, la consulta periódica activa, la autorización de tareas y el usuario efectivo del agente. Ser root dentro de un contenedor no implica por sí solo acceso como root al host; el límite solo se cruza si un consumidor con privilegios en el host ejecuta datos de tareas controlados por un atacante. Inspecciona los metadatos del proceso, el archivo de base de datos y el servicio sin modificar la cola ni enviar una tarea durante la enumeración.

Un job recurrente también puede leer un comando de una fila de configuración de una base de datos de aplicaciones. Confirma que el rol de base de datos con menos privilegios puede modificar esa fila exacta, que el job activo la lee después del cambio y que el valor llega a un shell o a un ejecutor de comandos equivalente bajo una identidad de SO más privilegiada. El acceso de escritura a la base de datos o un valor que parece un comando no demuestran por sí solos que vaya a ejecutarse; inspecciona el job y los permisos sin modificar la fila durante la enumeración pasiva.

Un mensaje en cola también puede contener una URL en lugar de código. Si un consumidor privilegiado obtiene esa URL y carga la respuesta como plugin ejecutable de Lua u otro lenguaje, verifica los permisos del publicador sobre el exchange y la clave de enrutamiento exactos, el binding con la cola consumida, la ruta de obtención y carga del plugin, y la identidad efectiva del worker. [RabbitMQ enruta los mensajes publicados a través de exchanges](https://www.rabbitmq.com/docs/exchanges); un listener del broker o un login válido no demuestran por sí solos que el mensaje llegue a este worker. Las credenciales del broker capturadas en texto claro son un indicio aparte que requiere acceso real a la captura de paquetes y tráfico legible; no demuestran autorización para publicar. Un plugin de Lua puede ejecutar comandos del shell mediante [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) solo si esa API está disponible en su runtime. Revisa la configuración y el código sin capturar tráfico, publicar mensajes ni obtener un plugin durante la enumeración pasiva.

Cuando un servicio privilegiado de Python expone un endpoint HTTP local o un socket, un script legible puede revelar una ruta desde la entrada hasta el código aunque sus permisos impidan modificarlo. Correlaciona el proceso activo y la identidad de la unidad con el script exacto, el listener, la autorización de la ruta y los campos controlados por el caller. Luego sigue esos campos a través del parseo y la validación hasta un punto de ejecución dinámica `eval()` o `exec()`. En particular, construir un f-string nuevo a partir del texto de una solicitud y evaluarlo puede interpretar los campos de reemplazo proporcionados por un atacante como expresiones de Python (advertencia de [Python `eval`](https://docs.python.org/3/library/functions.html#eval); [semántica de f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Encontrar `eval` o una vinculación a loopback no demuestra que un caller no confiable llegue al punto de ejecución; revisa el flujo de datos real y los controles de acceso sin enviar un payload de prueba durante la enumeración.

Un control de solicitudes firmadas en esa ruta requiere una revisión propia. Si el código fuente legible deriva la clave de firma de un espacio de salida demostrablemente pequeño o predecible, y el servicio expone una muestra firmada válida, la firma podría dejar de proteger un punto de ejecución `eval()` privilegiado. Verifica la derivación exacta de la clave y el verificador, la identidad del servicio activo y el acceso de callers locales, y si el campo firmado llega al punto de ejecución; importar el módulo [`random` de Python](https://docs.python.org/3/library/random.html) o tener una firma de muestra no demuestra ninguna de esas condiciones. Python también advierte que restringir `__builtins__` [no es un límite de seguridad para entradas no confiables de `eval()`](https://docs.python.org/3/library/functions.html#eval). Analiza las claves offline y no envíes solicitudes falsificadas durante la enumeración pasiva.

Un directorio `/etc/systemd/system/<unit>.service.d` vacío pero con permisos de escritura es relevante incluso cuando el archivo de unidad y todos los drop-ins existentes están protegidos: el usuario puede crear un nuevo override `.conf`. Comprueba que la identidad actual puede escribir y buscar en el directorio, que la unidad está cargada y se ejecuta como root, y si se llevará a cabo una recarga del daemon seguida de un reinicio. Una recarga o un reinicio permitidos, un timer o un arranque posterior pueden hacer efectivo el cambio; el acceso de escritura al directorio no lo ejecuta de inmediato.

En servicios en ejecución, sigue las rutas literales de `EnvironmentFile=` de la sección `[Service]` de la unidad, incluidos los archivos cuyos nombres no empiezan por `.env`. Si un usuario con pocos privilegios puede leer alguno, enumera nombres de claves que parezcan credenciales, como `API_TOKEN` o `APP_SECRET_KEY`, sin imprimir sus valores en logs compartidos. Comprueba los overrides de drop-ins y los prefijos opcionales `-` al determinar la configuración efectiva de la unidad. La legibilidad es un indicio de exposición de credenciales; para que derive en escalada, el valor aún debe ser válido para una acción privilegiada.

### Procesamiento privilegiado de cargas no confiables

Un watcher de archivos ejecutado como root puede entregar archivos de un directorio de carga modificable por usuarios a un parser o extractor de corta duración. Sigue el script padre o el servicio del watcher en ejecución y confirma el directorio exacto, quién puede colocar archivos allí, el comando hijo y sus argumentos, y la identidad con la que se ejecuta el hijo. Una instantánea de procesos puede mostrar el watcher y no detectar el extractor entre cargas. No coloques un payload de prueba ni actives el watcher durante la enumeración pasiva.

Un ejemplo concreto es el modo de extracción de Binwalk (`-e`) al procesar datos PFS controlados por un atacante. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permitía que el extractor PFS escribiera fuera del directorio previsto, incluida una ruta de plugins que Binwalk podía cargar posteriormente. El upstream incluyó la corrección en [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), pero los backports de las distribuciones pueden conservar una versión mostrada más antigua; comprueba el estado de seguridad del paquete instalado, por ejemplo en el [tracker de Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), antes de determinar si aplica. La versión instalada de Binwalk, por sí sola, no demuestra una ruta de escalada de privilegios: un proceso con más privilegios debe invocar realmente la extracción con una entrada controlable por el usuario con menos privilegios.

### Builds programados con dependencias locales

Un `cargo run` programado recompila el código fuente con el usuario run-as del job. Inspecciona las dependencias locales `{ path = "..." }` del manifiesto y los permisos del código fuente y de los directorios padre de cada dependencia, no solo los del crate principal. Si un usuario con menos privilegios puede modificar una dependencia que Cargo compila y el job programado ejecuta el resultado, el código compilado puede ejecutarse con la identidad run-as. Confirma el comando efectivo del scheduler, el directorio de trabajo, la resolución de dependencias y si se realizará una recompilación; un archivo de código fuente Rust modificable en otra ubicación es solo un indicio. Leer el manifiesto y los metadatos de las rutas basta para un análisis pasivo. Consulta la [documentación de Cargo sobre dependencias por ruta](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Archivos del framebuffer de Xvfb

`Xvfb -fbdir <directory>` usa archivos mapeados en memoria llamados `Xvfb_screen<n>` para sus pantallas virtuales. Si el proceso Xvfb en ejecución de otro usuario especifica un directorio cuyos archivos de pantalla puede leer el usuario actual, el framebuffer podría exponer el contenido del escritorio de ese usuario. Confirma conjuntamente el proceso, la propiedad de los archivos y sus permisos; que un archivo sea legible no demuestra por sí solo que la pantalla contenga información útil. Primero inspecciona las rutas y los metadatos, sin copiar datos de imagen a la salida compartida de enumeración. El [manual de Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) documenta el comportamiento de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
