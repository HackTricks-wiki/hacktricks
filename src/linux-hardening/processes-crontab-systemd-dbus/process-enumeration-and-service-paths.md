# Enumeración de procesos y rutas de servicios

{{#include ../../banners/hacktricks-training.md}}

La pregunta útil es qué proceso privilegiado consume datos o código que puede controlar un usuario con menos privilegios. Inspecciona el árbol de procesos, el entorno en ejecución, los archivos abiertos y la unidad o el script que inició cada candidato.

## Mapear procesos y propietarios

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Una relación padre-hijo entre usuarios puede ser normal, pero una transición inesperada justifica revisar el comando del proceso padre, sus argumentos, el ejecutable, el directorio de trabajo y los archivos referenciados. Usa [usuarios y sesiones](../user-information/user-and-session-triage.md) para interpretar el propietario y el contexto de inicio de sesión.

### Consolas de máquinas virtuales locales

Revisa las opciones `-spice` de un proceso QEMU junto con su dirección de escucha. [La documentación de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) indica que `disable-ticketing` permite que los clientes SPICE se conecten sin autenticación. Incluso si un listener está vinculado a loopback, otros usuarios locales del host podrían acceder a él. Confirma el listener activo, las opciones de autenticación y el acceso local antes de considerar la línea de comandos una consola expuesta. El control de la consola afecta al **guest**; obtener una cuenta de guest o cambiar su estado de arranque requiere condiciones independientes en el guest y no otorga root en el host de virtualización. Lee los argumentos del proceso y los metadatos del socket sin conectarte al guest ni reiniciarlo durante la enumeración pasiva.

Una interfaz web accesible localmente puede ejecutar código con la cuenta de servicio, aunque el primer shell no pueda acceder a los archivos de esa cuenta. Por ejemplo, CVE-2023-0297 afectaba al manejo de `/flash/addcrypted2` de pyLoad cuando JavaScript no confiable llegaba a Js2Py con las importaciones de Python habilitadas; la [corrección upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deshabilitó `pyimport`. Correlaciona el propietario del proceso en ejecución, la dirección de escucha, la exposición del endpoint y el parche instalado o backport del proveedor antes de considerar un proceso pyLoad una vía de escalada. El nombre de un proceso, un puerto abierto o la versión de un paquete por sí solos no demuestran que haya exposición; la enumeración pasiva no debe enviar un payload de ejecución.

### Shells de inicio de sesión privilegiados que comparten un terminal

Un shell interactivo privilegiado que ejecuta `su --login <user>` sin un pseudo-terminal independiente puede dejar su terminal compartido con el shell de inicio de sesión del usuario con menos privilegios. Si el archivo de inicio de ese usuario es modificable y el código que contiene puede usar `TIOCSTI` para inyectar entrada en el terminal, la entrada podría llegar al shell privilegiado cuando este reanude la ejecución. [El manual de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) describe el riesgo de compartir un terminal y recomienda `su --pty`/`-P` para uso interactivo; `su -c` inicia una sesión independiente sin un terminal de control. El riesgo depende del shell padre real, la relación entre terminales, el archivo de inicio del usuario objetivo y la política del kernel. El nombre de un proceso o el argumento `su -l` por sí solos solo justifican una revisión.

Inspecciona el árbol de procesos observado y las columnas de TTY; después, revisa el launcher legible y la propiedad/permisos del archivo de inicio. En Linux, `/proc/sys/dev/tty/legacy_tiocsti` puede ayudar a interpretar la política cuando está presente; su ausencia no demuestra que el sistema sea seguro. [El manual de Linux de `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) señala que, desde Linux 6.2, la operación puede requerir `CAP_SYS_ADMIN` cuando este sysctl es false. No invoques el ioctl solo para enumerar el host.

En ocasiones, una cuenta de base de datos puede modificar el archivo de inicio del usuario objetivo sin acceso directo de escritura al sistema de archivos. `COPY ... TO 'filename'` del lado del servidor PostgreSQL escribe con la cuenta de sistema operativo del servidor de base de datos, pero [PostgreSQL limita](https://www.postgresql.org/docs/current/sql-copy.html) esta forma de archivo a superusuarios de la base de datos o a roles como `pg_write_server_files`. Confirma tanto el rol de la base de datos como los permisos de archivos del sistema operativo del servidor; una cadena de conexión de la aplicación no otorga por sí sola permisos de escritura en archivos. Al evaluar la cadena, considera por separado las capacidades del launcher privilegiado y las de la cuenta de la base de datos.

## Inspeccionar artefactos de ejecución

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Los ejecutables eliminados y los archivos eliminados pero aún abiertos siguen referenciados hasta que se cierra su último descriptor. Pueden conservar evidencia o secretos accesibles. Los entornos de procesos y la memoria pueden contener credenciales, pero leer otro proceso está sujeto a restricciones de propiedad, opciones de montaje de `/proc`, la política ptrace de Yama y otros controles de seguridad. Consulta [descriptores de archivos](../main-system-information/filesystem-links-and-file-descriptors.md) y [búsqueda de credenciales durante la post-explotación](../post-exploitation/README.md) para ver técnicas relacionadas.

Los rastros de syscall guardados constituyen otra frontera de permisos de archivos. [`strace` registra los argumentos de las syscall en un archivo de salida](https://man7.org/linux/man-pages/man1/strace.1.html), así que un rastro legible de los [argumentos de `execve`](https://man7.org/linux/man-pages/man2/execve.2.html) podría revelar una contraseña que un trabajo privilegiado pasó en su línea de comandos. Primero comprueba que el usuario actual pueda leer el rastro concreto y que el argumento realmente contenga una credencial; demostrar que la credencial es aceptada al cambiar a otra cuenta Unix requiere pruebas independientes. Los metadatos del archivo son una pista pasiva útil, sin tener que escanear todos los rastros ni mostrar su contenido durante el reconocimiento rutinario.

## Sockets de automatización ofimática privilegiados

LibreOffice y OpenOffice pueden exponer su API UNO mediante un argumento `--accept=socket,host=<host>,port=<port>;urp;`. Un proceso ofimático propiedad de root con un endpoint accesible podría permitir que un usuario local con menos privilegios invoque servicios de la API en el contexto de seguridad de ese proceso. El servicio `SystemShellExecute` incluye una operación para ejecutar un comando del sistema. Vincularlo a loopback limita la accesibilidad remota, pero el socket sigue siendo accesible para usuarios locales, salvo que otro control impida el acceso.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Correlaciona el propietario del proceso, el argumento exacto `--accept` y la dirección y el puerto en los que escucha actualmente. Un acceptor configurado que no pudo enlazarse es solo una pista; no te conectes a la API ni la invoques durante la enumeración pasiva. Evita iniciar una instancia de office con privilegios solo para probar esta condición.

## Memoria compartida System V consumida por procesos con privilegios

Un helper propiedad de root puede crear un segmento de memoria compartida System V en el que otro usuario pueda escribir. Si después el helper confía en los datos de ese segmento para ejecutar un comando de shell u otra operación sensible, el segmento cruza un límite de privilegios, aunque el ejecutable y sus archivos estén protegidos. `shmget()` toma los permisos de acceso de los nueve bits inferiores de sus flags; el modo `0666` permite que otros usuarios escriban, mientras que un flag `IPC_CREAT` no restringe esos permisos. Inspecciona los segmentos activos de forma pasiva con `ipcs -m` y correlaciona su propietario, modo y duración con el proceso con privilegios y el manejo de sus entradas. Un segmento con permisos de escritura para todos, por sí solo, no demuestra la ejecución de comandos.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Los segmentos System V son distintos de los archivos de memoria compartida POSIX en `/dev/shm`. Un segmento creado solo por un momento puede no aparecer en una única instantánea de `ipcs`, así que una salida vacía no descarta que un helper use memoria compartida. Revisa su código fuente o el comportamiento del binario, así como cualquier regla de `sudo` que lo ejecute; no invoques el helper privilegiado solo para que aparezca un segmento durante la enumeración. La [guía de namespaces de IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explica cómo los namespaces afectan la visibilidad.<sup>[[2]](#references)[[3]](#references)</sup>

## Comprobaciones de scripts del agente Consul

Consul puede ejecutar comprobaciones de estado de scripts con la identidad del sistema operativo de su agente. Si un agente se ejecuta como root, habilita `enable_script_checks` y permite que un usuario con menos privilegios registre un servicio con una comprobación de script a través de la API HTTP local, ese usuario podría ejecutar comandos como root. Vincular la API únicamente a `127.0.0.1` sigue permitiendo que los usuarios locales accedan a ella. La opción `enable_local_script_checks` es más restrictiva: excluye las comprobaciones de scripts enviadas mediante registros de la API HTTP. Cuando las ACL de Consul están habilitadas, el registro de servicios requiere `service:write`; una línea `acl.default_policy=allow` por sí sola no demuestra que un usuario anónimo pueda registrar servicios. Revisa conjuntamente la identidad real del agente, la configuración cargada, la vinculación de la API y la autorización.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Sigue los argumentos `-config-dir` y `-config-file` del agent en ejecución hasta la configuración correspondiente e inspecciona únicamente los nombres y valores de los campos de script-check y ACL. Los archivos de configuración también pueden contener claves o tokens de gossip; evita pegarlos en registros compartidos. No registres un servicio ni ejecutes un health check solo para enumerar esta condición.

Existe una ruta independiente a través de archivos locales cuando un usuario con menos privilegios puede **escribir y buscar** en el directorio indicado por `-config-dir` de un agent ejecutado como root: desde ese directorio se puede cargar una nueva definición de servicio `.hcl` o `.json`. El permiso de búsqueda y escritura en un directorio puede permitir agregar un archivo aunque esté denegado el listado del directorio. Para ejecutar comandos como root, confirma que el agent realmente carga ese directorio, que su configuración **efectiva** de script-check permite definiciones locales, que la definición se carga y que el agent conserva los privilegios de root. [Consul documents](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) qué configuraciones y definiciones de health check se pueden recargar; habilitar los script checks puede requerir un reinicio, así que verifica el comportamiento de la versión instalada. Cuando los ACL protegen el agent, [`consul reload` requires `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); el permiso de escritura en KV no lo concede. Considera los metadatos de directorios con permisos de escritura como una señal para revisar, no como prueba de que haya una recarga autorizada, un reinicio o una ejecución de comandos. Inspecciona las rutas, los permisos y la política sin escribir configuración ni llamar a la API.

## Sigue la cadena de ejecución del servicio

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Comprueba la unidad, los drop-ins, `EnvironmentFile=`, los scripts auxiliares, los comandos relativos, los directorios con permisos de escritura y la activación por socket. Una unidad propiedad de root puede seguir siendo insegura si lee una configuración o un script modificable por un usuario. La página sobre [escritura arbitraria de archivos](../interesting-files-permissions/write-to-root.md) cubre rutas comunes de abuso de servicios y unidades. Monitoriza los jobs de corta duración con [pspy](https://github.com/DominicBreuker/pspy) o telemetría de auditoría/procesos cuando una consulta puntual a `ps` no los detecte.

Para un servicio **xinetd** personalizado, correlaciona las directivas `server`, `user` y los controles de acceso del bloque habilitado con el listener activo y el ejecutable exacto. El [ajuste `user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) selecciona la identidad del proceso iniciado, mientras que un bit set-user-ID en el ejecutable puede cambiar por separado su identidad efectiva si [`execve` permite esa transición](https://man7.org/linux/man-pages/man2/execve.2.html). Un binario privilegiado accesible que acepte entradas no confiables merece una revisión offline del código fuente o del desensamblado para detectar bugs de seguridad de memoria, como una conversión de cadena [`scanf` sin límites](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) a un búfer de tamaño fijo. La asociación con el servicio y los metadatos set-user-ID son indicios, no pruebas de que exista un bug; no envíes entradas que provoquen fallos ni depures el servicio privilegiado en ejecución durante la enumeración pasiva.

Para un listener privilegiado personalizado con código fuente legible, revisa cada longitud controlada por el llamador que se use en una operación de copia como [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Comprobar solo que el índice de escritura actual esté dentro de un búfer fijo no demuestra que la **longitud de copia** quepa en el espacio restante; verifica `copy_length <= capacity - index` después de confirmar que el índice está dentro del rango, y comprueba el signo y el desbordamiento aritmético. Esto es solo un indicio de revisión si la entrada llega a esa operación, el usuario con menos privilegios puede acceder al listener y el proceso conserva una identidad efectiva superior. Inspecciona offline el código fuente y los metadatos del proceso; no envíes entradas que provoquen fallos al servicio en ejecución durante la enumeración.

En sistemas que usan **Upstart**, las definiciones de jobs del sistema pueden estar en `/etc/init/*.conf`. Un archivo de job modificable por el usuario actual es relevante cuando el daemon de init activo carga ese archivo exacto, su directiva `script` o `exec` se ejecuta con una identidad más privilegiada y el usuario puede iniciarlo mediante un comando `initctl` permitido u otro trigger real. Un permiso sudo para `initctl` por sí solo no demuestra que algún archivo de job sea modificable ni que se ejecute un job modificado. Comprueba los permisos del archivo de job exacto, la configuración efectiva de la identidad de ejecución, el daemon activo y el trigger, sin modificar ni iniciar el job durante la enumeración. Consulta los manuales de [configuración de jobs de Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) e [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un archivo de contraseña de autologin legible, como `/etc/autologin/passwd` en sistemas cuyo [job de arranque lee esa ruta exacta](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), es un indicio de exposición de credenciales. Confirma que el job de arranque está instalado y usa el archivo; luego verifica por separado si la contraseña es válida para otra cuenta local o servicio. El nombre del archivo por sí solo no demuestra la reutilización de la contraseña; registra la ruta y los metadatos de acceso sin incluir la contraseña en la salida de enumeración compartida.

Un `ExecStart=` de una unidad o un comando programado puede revelar la ruta exacta de un script dentro de un directorio cuyo contenido no se puede listar. El [permiso de búsqueda en directorios](https://man7.org/linux/man-pages/man7/path_resolution.7.html) aún puede permitir que la identidad actual recorra esa ruta conocida; confirma el permiso de búsqueda en cada directorio padre y el permiso de lectura del archivo, en vez de asumir que no poder listar un directorio lo protege. Un script legible puede contener una credencial para transferencias, pero acceder a otra cuenta requiere que esa credencial siga siendo válida y que la otra cuenta la acepte de forma independiente. Registra la ruta y las pruebas de permisos sin imprimir valores secretos en logs compartidos.

Para un script CommonJS de Node.js programado, revisa los imports sin ruta explícita, como `require('package')`, aunque el script en sí sea de solo lectura. [Node busca `node_modules` junto al archivo que importa el módulo y luego en sus directorios ascendientes](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), antes de recurrir a las rutas globales configuradas. Un usuario con menos privilegios que pueda **escribir y buscar** en uno de esos directorios ascendientes podría crear un paquete que coincida antes en la búsqueda. Confirma que se alcanza el import exacto, que el paquete seleccionado no es un módulo integrado, que se puede crear o modificar la ruta pertinente, que el módulo se resuelve allí en el runtime instalado y que un job con más privilegios lo cargará en una ejecución futura. Los metadatos de un directorio padre modificable son solo una señal para revisar; inspecciona el script y el scheduler de forma pasiva, sin instalar un módulo ni activar el job.

Un índice privado de paquetes Python es otro límite de confianza cuando un job automatizado instala paquetes con una identidad de OS diferente. Correlaciona el job exacto y la cuenta de ejecución con el índice configurado, los nombres de los paquetes seleccionados y la posibilidad de que un usuario con menos privilegios publique o sustituya un paquete que el job vaya a instalar realmente. Crear una distribución de código fuente puede ejecutar su backend de compilación o el `setup.py` heredado con la identidad del instalador; importar el paquete instalado es una vía de ejecución aparte. Un listener de índice, un hash de contraseña de subida legible o el nombre de un paquete por sí solos no demuestran esa cadena. Revisa el job, la autorización del índice y la procedencia del paquete sin subir ni instalar nada durante la enumeración. Consulta la [interfaz de sistemas de compilación de pip](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones para instalaciones seguras](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agente privilegiado puede consultar una cola de tareas gestionada por un servicio web o contenedor independiente. Si una identidad de menor confianza puede escribir en la base de datos de tareas del servicio, determina si esas filas realmente se sirven al agente y si una tarea de comandos se ejecuta con la identidad de OS del agente. Confirma por separado el acceso de escritura a la base de datos, la sesión objetivo o la clave de enrutamiento, la consulta activa, la autorización de tareas y el usuario efectivo del agente. Ser root dentro de un contenedor no implica por sí solo acceso como root en el host; el límite solo se cruza si un consumidor con privilegios en el host ejecuta datos de tareas controlados por un atacante. Inspecciona los metadatos de procesos, archivos de base de datos y servicios sin modificar la cola ni enviar una tarea durante la enumeración.

En cambio, un job recurrente puede leer un comando de una fila de configuración de una base de datos de la aplicación. Confirma que el rol de base de datos con menos privilegios pueda modificar esa fila exacta, que el job activo la lea después del cambio y que el valor llegue a un shell o a un ejecutor de comandos equivalente bajo una identidad de OS superior. El acceso de escritura a la base de datos o un valor que parezca un comando no demuestran por sí solos que vaya a ejecutarse; inspecciona el job y los permisos sin modificar la fila durante la enumeración pasiva.

Un mensaje en cola también puede contener una URL en lugar de código. Si un consumidor privilegiado obtiene esa URL y carga la respuesta como un plugin ejecutable de Lua u otro lenguaje, verifica los permisos del publicador en el exchange y la clave de enrutamiento exactos, el binding con la cola consumida, la ruta de obtención y carga del plugin, y la identidad efectiva del worker. [RabbitMQ enruta los mensajes publicados a través de exchanges](https://www.rabbitmq.com/docs/exchanges); un listener del broker o un login válido no demuestran por sí solos que el mensaje llegue a este worker. Las credenciales del broker capturadas en texto claro son un indicio aparte que requiere acceso real a la captura de paquetes y tráfico legible; no demuestran autorización para publicar. Un plugin Lua puede ejecutar comandos de shell mediante [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) solo si esa API está disponible en su runtime. Revisa la configuración y el código sin capturar tráfico, publicar mensajes ni obtener un plugin durante la enumeración pasiva.

Cuando un servicio Python privilegiado expone un endpoint HTTP o socket local, un script legible puede revelar una ruta desde la entrada hasta el código, aunque sus permisos impidan modificarlo. Correlaciona la identidad del proceso y la unidad activos con el script exacto, el listener, la autorización de rutas y los campos controlados por el llamador. Después, sigue esos campos a través del análisis y la validación hasta un punto de ejecución dinámica `eval()` o `exec()`. En particular, construir un f-string nuevo a partir del texto de una solicitud y evaluarlo puede interpretar los campos de sustitución proporcionados por un atacante como expresiones Python (advertencia de [Python `eval`](https://docs.python.org/3/library/functions.html#eval); [semántica de f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Una coincidencia con `eval` sin más o un binding a loopback no demuestra que un llamador no confiable llegue al punto de ejecución; revisa el flujo de datos y los controles de acceso reales sin enviar una carga de prueba durante la enumeración.

Un control de solicitudes firmadas en esa ruta requiere su propia revisión. Si el código fuente legible deriva la clave de firma mediante un espacio de salida demostrablemente pequeño o predecible, y el servicio expone una muestra válida firmada, es posible que la firma ya no proteja un punto de ejecución privilegiado `eval()`. Verifica la derivación exacta de la clave y el verificador, la identidad del servicio activo y el acceso de los llamadores locales, y si el campo firmado llega al punto de ejecución; importar el módulo [`random` de Python](https://docs.python.org/3/library/random.html) o disponer de una firma de muestra no demuestra ninguna de esas condiciones. Python también advierte que restringir `__builtins__` [no constituye un límite de seguridad para entradas no confiables de `eval()`](https://docs.python.org/3/library/functions.html#eval). Analiza la clave offline y no envíes solicitudes falsificadas durante la enumeración pasiva.

Un directorio `/etc/systemd/system/<unit>.service.d` vacío pero modificable es relevante incluso si el archivo de unidad y todos los drop-ins existentes están protegidos: el usuario puede crear un nuevo override `.conf`. Comprueba que la identidad actual tenga permisos de escritura y búsqueda en el directorio, que la unidad esté cargada y se ejecute como root, y si se producirá una recarga del daemon seguida de un reinicio. Un permiso para recargar o reiniciar, un timer o un arranque posterior puede hacer efectivo el cambio; el permiso de escritura en el directorio no lo ejecuta de inmediato.

En los servicios en ejecución, sigue las rutas literales de `EnvironmentFile=` de la sección `[Service]` de la unidad, incluidos los archivos cuyos nombres no empiezan por `.env`. Si un usuario con pocos privilegios puede leer alguno, enumera nombres de claves que parezcan credenciales, como `API_TOKEN` o `APP_SECRET_KEY`, sin imprimir sus valores en logs compartidos. Comprueba los overrides de drop-ins y los prefijos opcionales `-` al determinar la unidad efectiva. Que el archivo sea legible es un indicio de exposición de credenciales; el valor aún debe ser válido para que una acción privilegiada permita escalar privilegios.

### Procesamiento privilegiado de cargas no confiables

Un file watcher ejecutado como root puede entregar archivos de un directorio de cargas modificable por usuarios a un parser o extractor de corta duración. Sigue el script padre o el servicio del watcher en ejecución y confirma el directorio exacto, quién puede colocar archivos allí, el comando hijo y sus argumentos, y la identidad con la que se ejecuta el hijo. Una instantánea de procesos puede mostrar el watcher y pasar por alto el extractor entre cargas. No coloques una carga de prueba ni actives el watcher durante la enumeración pasiva.

Un ejemplo concreto es el modo de extracción de Binwalk (`-e`) al procesar datos PFS controlados por un atacante. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permitía que el extractor PFS escribiera fuera del directorio previsto, incluida una ruta de plugins que Binwalk podía cargar más adelante. El proyecto upstream incluyó la corrección en [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), pero los backports de las distribuciones pueden conservar una versión mostrada anterior; comprueba el estado de seguridad del paquete instalado, por ejemplo en el [tracker de Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), antes de determinar si es aplicable. La versión de Binwalk instalada por sí sola no demuestra una ruta de escalada de privilegios: un proceso con más privilegios debe invocar realmente la extracción con una entrada controlable por el usuario con menos privilegios.

### Compilaciones programadas con dependencias locales

Un `cargo run` programado vuelve a compilar el código fuente con la identidad de ejecución del job. Inspecciona las dependencias locales `{ path = "..." }` del manifiesto y los permisos del código fuente y los directorios padre de cada dependencia, no solo los del crate principal. Si un usuario con menos privilegios puede modificar una dependencia que Cargo compila y el job programado ejecuta su resultado, el código compilado puede ejecutarse con la identidad de ejecución de ese job. Confirma el comando efectivo del scheduler, el directorio de trabajo, la resolución de dependencias y si se producirá una recompilación; un archivo de código fuente Rust modificable en otra ubicación es solo un indicio. Leer el manifiesto y los metadatos de las rutas basta para un análisis pasivo inicial. Consulta la [documentación de dependencias por ruta de Cargo](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Archivos de framebuffer de Xvfb

`Xvfb -fbdir <directory>` usa archivos memory-mapped llamados `Xvfb_screen<n>` para sus pantallas virtuales. Si el proceso Xvfb en ejecución de otro usuario indica un directorio cuyos archivos de pantalla puede leer el usuario actual, el framebuffer podría exponer el contenido del escritorio de ese usuario. Confirma conjuntamente el proceso, la propiedad de los archivos y sus permisos; que un archivo sea legible no demuestra por sí solo que haya contenido útil en pantalla. Inspecciona primero las rutas y los metadatos, sin copiar datos de imagen a la salida de enumeración compartida. El [manual de Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) documenta el comportamiento de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
