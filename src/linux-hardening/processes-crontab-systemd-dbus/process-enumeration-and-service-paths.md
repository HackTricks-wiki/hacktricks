# Enumeración de procesos y rutas de servicios

{{#include ../../banners/hacktricks-training.md}}

La pregunta útil es qué proceso privilegiado consume datos o código que puede controlar un usuario con menos privilegios. Inspecciona el árbol de procesos, el entorno en ejecución, los archivos abiertos y la unidad o el script que inició cada candidato.

## Mapear procesos y propietarios

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Una relación padre-hijo entre usuarios distintos puede ser normal, pero una transición inesperada justifica revisar el comando del proceso padre, sus argumentos, el ejecutable, el directorio de trabajo y los archivos a los que hace referencia. Usa [usuarios y sesiones](../user-information/user-and-session-triage.md) para interpretar el propietario y el contexto de inicio de sesión.

### Consolas de máquinas virtuales locales

Revisa las opciones `-spice` de un proceso QEMU junto con su dirección de escucha. [La documentación de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) indica que `disable-ticketing` permite que los clientes SPICE se conecten sin autenticación. Incluso si un listener está enlazado a la interfaz de loopback, otros usuarios locales del host podrían acceder a él. Confirma el listener activo, las opciones de autenticación y el acceso local antes de considerar que la línea de comandos expone una consola. El control de la consola afecta al **guest**; obtener una cuenta en el guest o cambiar su estado de arranque requiere condiciones independientes del lado del guest y no otorga root en el host de virtualización. Lee los argumentos del proceso y los metadatos del socket sin conectarte al guest ni reiniciarlo durante la enumeración pasiva.

Una interfaz web accesible localmente puede ejecutar código con la cuenta del servicio incluso cuando el primer shell no puede acceder a los archivos de esa cuenta. Por ejemplo, CVE-2023-0297 afectaba al manejo de `/flash/addcrypted2` de pyLoad cuando JavaScript no confiable llegaba a Js2Py con las importaciones de Python habilitadas; la [corrección upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deshabilitó `pyimport`. Correlaciona el propietario del proceso en ejecución, la dirección de escucha, la exposición del endpoint y el parche instalado o backport del proveedor antes de considerar un proceso pyLoad como una vía de escalada. El nombre de un proceso, un puerto abierto o la versión de un paquete, por sí solos, no demuestran que haya exposición; la enumeración pasiva no debe enviar un payload de ejecución.

### Shells de inicio de sesión privilegiados que comparten una terminal

Un shell interactivo privilegiado que ejecuta `su --login <user>` sin una pseudo-terminal independiente puede dejar su terminal compartida con el shell de inicio de sesión con menos privilegios. Si el archivo de inicio de ese usuario es controlable y el código que contiene puede usar `TIOCSTI` para inyectar entrada en la terminal, esta entrada podría llegar al shell privilegiado cuando se reanude. [El manual de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) describe el riesgo de compartir una terminal y recomienda `su --pty`/`-P` para el uso interactivo; `su -c` inicia una sesión independiente sin una terminal de control. El riesgo depende del shell padre real, la relación con la terminal, el archivo de inicio del usuario de destino y la política del kernel. El nombre de un proceso o el argumento `su -l`, por sí solos, solo justifican una revisión.

Inspecciona el árbol de procesos observado y las columnas TTY; luego, el lanzador legible y la propiedad y los permisos del archivo de inicio. En Linux, `/proc/sys/dev/tty/legacy_tiocsti` puede ayudar a interpretar la política cuando está presente; su ausencia no demuestra que sea seguro. [El manual de Linux de `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) señala que, desde Linux 6.2, la operación puede requerir `CAP_SYS_ADMIN` cuando este sysctl es falso. No invoques el ioctl solo para enumerar el host.

En algunos casos, una cuenta de base de datos puede modificar el archivo de inicio del usuario de destino sin acceso directo de escritura al sistema de archivos. `COPY ... TO 'filename'` del lado del servidor PostgreSQL escribe con la cuenta del sistema operativo del servidor de base de datos, pero [las restricciones de PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) limitan esta forma de archivo a superusuarios de la base de datos o a roles como `pg_write_server_files`. Confirma tanto el rol de la base de datos como los permisos de archivos del sistema operativo del servidor; una cadena de conexión de la aplicación no otorga por sí sola autoridad para escribir archivos. Al evaluar la cadena, considera por separado el lanzador privilegiado y las capacidades de la cuenta de la base de datos.

## Inspeccionar artefactos de ejecución

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Los ejecutables eliminados y los archivos eliminados pero aún abiertos siguen referenciados hasta que se cierra su último descriptor. Pueden conservar pruebas o secretos accesibles. Los entornos y la memoria de los procesos pueden contener credenciales, pero leer otro proceso está sujeto a restricciones de propiedad, opciones de montaje de `/proc`, políticas `ptrace` de Yama y otros controles de seguridad. Consulta [file descriptors](../main-system-information/filesystem-links-and-file-descriptors.md) y [post-exploitation credential hunting](../post-exploitation/README.md) para ver técnicas relacionadas.

Los rastros de syscall guardados también están sujetos a permisos de archivo. [`strace` registra los argumentos de las syscall en un archivo de salida](https://man7.org/linux/man-pages/man1/strace.1.html), por lo que un rastro legible de los [argumentos de `execve`](https://man7.org/linux/man-pages/man2/execve.2.html) puede revelar una contraseña que un trabajo privilegiado pasó en su línea de comandos. Primero, confirma que el usuario actual puede leer ese rastro en particular y que el argumento realmente contiene una credencial; después, se necesita una prueba independiente de que la credencial es válida para realizar una transición a otra cuenta Unix. Los metadatos del archivo son una pista pasiva útil, sin tener que escanear todos los rastros ni mostrar su contenido durante la enumeración rutinaria.

## Sockets de automatización ofimática privilegiados

LibreOffice y OpenOffice pueden exponer su API UNO mediante un argumento `--accept=socket,host=<host>,port=<port>;urp;`. Un proceso ofimático propiedad de root con un endpoint accesible puede permitir que un usuario local con menos privilegios invoque servicios de la API en el contexto de seguridad de ese proceso. El servicio `SystemShellExecute` incluye una operación para ejecutar un comando del sistema. Vincularlo a loopback limita el acceso remoto, pero el socket sigue siendo accesible para los usuarios locales, a menos que otro control lo impida.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Correlaciona el propietario del proceso, el argumento exacto `--accept` y la dirección y el puerto en los que escucha actualmente. Un acceptor configurado que no pudo enlazarse es solo una pista; no te conectes a la API ni la invoques durante la enumeración pasiva. Evita iniciar una instancia de office con privilegios solo para probar esta condición.

## Memoria compartida System V utilizada por procesos privilegiados

Un helper propiedad de root puede crear un segmento de memoria compartida System V en el que otro usuario pueda escribir. Si después el helper confía en los datos de ese segmento para ejecutar un comando de shell u otra operación sensible, el segmento cruza un límite de privilegios aunque el ejecutable y sus archivos estén protegidos. `shmget()` toma los permisos de acceso de los nueve bits inferiores de sus flags; el modo `0666` permite que otros usuarios escriban, mientras que un flag `IPC_CREAT` no restringe esos permisos. Inspecciona pasivamente los segmentos activos con `ipcs -m` y correlaciona su propietario, modo y duración con el proceso privilegiado y el tratamiento que da a sus entradas. Un segmento con permisos de escritura para todos no demuestra por sí solo que se puedan ejecutar comandos.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Los segmentos System V son distintos de los archivos de memoria compartida POSIX en `/dev/shm`. Un segmento creado solo por un instante puede no aparecer en una única instantánea de `ipcs`, por lo que una salida vacía no descarta la existencia de un helper que use memoria compartida. Revisa su código fuente o el comportamiento del binario, así como cualquier regla de `sudo` que lo ejecute; no invoques el helper con privilegios solo para hacer aparecer un segmento durante la enumeración. La [guía de espacios de nombres IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explica cómo afectan los espacios de nombres a la visibilidad.<sup>[[2]](#references)[[3]](#references)</sup>

## Comprobaciones de scripts del agente de Consul

Consul puede ejecutar comprobaciones de estado mediante scripts con la identidad del sistema operativo de su agente. Si un agente se ejecuta como root, habilita `enable_script_checks` y permite que un usuario con menos privilegios registre un servicio con una comprobación mediante script a través de la API HTTP local, ese usuario podría hacer que se ejecuten comandos como root. Aunque la API esté enlazada solo a `127.0.0.1`, los usuarios locales aún pueden acceder a ella. El ajuste `enable_local_script_checks` es más restrictivo: excluye las comprobaciones mediante script enviadas a través de registros de la API HTTP. Cuando las ACL de Consul están habilitadas, el registro de servicios requiere `service:write`; una línea `acl.default_policy=allow` por sí sola no demuestra que un usuario anónimo pueda registrar servicios. Revisa conjuntamente la identidad real del agente, los ajustes cargados, el enlace de la API y la autorización.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Sigue los argumentos `-config-dir` y `-config-file` del agent en ejecución hasta la configuración correspondiente e inspecciona únicamente los nombres y ajustes de los campos de script-check y ACL. Los archivos de configuración también pueden contener claves o tokens de gossip; evita pegarlos en logs compartidos. No registres un servicio ni ejecutes una comprobación de estado solo para enumerar esta condición.

Existe una ruta independiente mediante archivos locales cuando un usuario con menos privilegios puede **escribir y buscar** en el directorio indicado por `-config-dir` de un agent ejecutado como root: podría cargarse desde ese directorio una nueva definición de servicio `.hcl` o `.json`. Los permisos de búsqueda y escritura en el directorio pueden permitir añadir un archivo aunque no se permita listar su contenido. Para ejecutar comandos como root, confirma que el agent realmente carga ese directorio, que el ajuste **efectivo** de script-check permite definiciones locales, que se carga la definición y que el agent conserva los privilegios de root. [Consul documenta](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) qué ajustes y definiciones de comprobaciones de estado se pueden recargar; puede que habilitar script checks requiera reiniciar el agent, así que verifica el comportamiento de la versión instalada. Cuando las ACL protegen el agent, [`consul reload` requiere `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); el permiso para escribir en KV no lo concede. Considera los metadatos de directorios con permisos de escritura como una señal para revisarlos, no como prueba de que se haya autorizado una recarga, un reinicio o la ejecución de comandos. Inspecciona las rutas, los permisos y la política sin escribir configuraciones ni llamar a la API.

## Sigue la cadena de ejecución del servicio

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Comprueba la unidad, los drop-ins, `EnvironmentFile=`, los scripts auxiliares, los comandos relativos, los directorios con permisos de escritura y la activación de sockets. Una unidad propiedad de root aún puede ser insegura si lee una configuración o un script en los que un usuario puede escribir. La página sobre [escritura arbitraria de archivos](../interesting-files-permissions/write-to-root.md) cubre las vías comunes de abuso de servicios y unidades. Supervisa los trabajos de corta duración con [pspy](https://github.com/DominicBreuker/pspy) o con telemetría de auditoría/procesos cuando una única consulta a `ps` no los detecte.

Para un servicio **xinetd** personalizado, relaciona las directivas `server`, `user` y los controles de acceso del bloque habilitado con el listener activo y el ejecutable exacto. La [configuración `user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) elige la identidad del proceso generado, mientras que un bit set-user-ID en el ejecutable puede cambiar por separado su identidad efectiva si [`execve` permite esa transición](https://man7.org/linux/man-pages/man2/execve.2.html). Un binario privilegiado accesible que acepta entradas no confiables justifica revisar su código fuente o desensamblado sin conexión para detectar errores de seguridad de memoria, como una conversión de cadena [`scanf` sin límites](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) en un búfer de tamaño fijo. La asignación del servicio y los metadatos set-user-ID son indicios, no pruebas de que exista tal error; no envíes entradas que provoquen fallos ni depures el servicio privilegiado activo durante la enumeración pasiva.

Para un listener privilegiado personalizado cuyo código fuente sea legible, revisa cada longitud controlada por el llamante que se use en una operación de copia como [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Comprobar únicamente que el índice de escritura actual esté dentro de un búfer fijo no demuestra que la **longitud de copia** quepa en el espacio restante; verifica `copy_length <= capacity - index` después de confirmar que el índice está dentro del rango, y comprueba el signo y el desbordamiento aritmético. Esto es solo un indicio para la revisión si la entrada llega a esa operación, el usuario de menor privilegio puede acceder al listener y el proceso conserva una identidad efectiva superior. Inspecciona el código fuente y los metadatos del proceso sin conexión; no envíes entradas que provoquen fallos al servicio activo durante la enumeración.

En sistemas que usan **Upstart**, las definiciones de trabajos del sistema pueden estar en `/etc/init/*.conf`. Un archivo de trabajo en el que el usuario actual puede escribir es relevante cuando el daemon init activo carga ese archivo específico, su bloque `script` o `exec` se ejecuta con una identidad de mayor privilegio y el usuario puede iniciarlo mediante un comando `initctl` permitido u otro desencadenante real. Un permiso de sudo para `initctl`, por sí solo, no demuestra que se pueda escribir en ningún archivo de trabajo ni que se vaya a ejecutar un trabajo modificado. Comprueba los permisos del archivo de trabajo exacto, la configuración efectiva de ejecución como usuario, el daemon activo y el desencadenante sin editar ni iniciar el trabajo durante la enumeración. Consulta los manuales de [configuración de trabajos de Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) y [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un archivo de contraseñas de autologin legible, como `/etc/autologin/passwd` en sistemas cuyo [trabajo de arranque lee esa ruta exacta](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), es un indicio de exposición de credenciales. Confirma que el trabajo de arranque está instalado y usa el archivo; luego verifica por separado si la contraseña es válida para otra cuenta o servicio local. El nombre del archivo por sí solo no demuestra que se reutilice la contraseña; registra la ruta y los metadatos de acceso sin incluir la contraseña en los resultados compartidos de enumeración.

El `ExecStart=` de una unidad o un comando programado puede revelar la ruta exacta de un script dentro de un directorio cuyo contenido no se puede listar. [El permiso de búsqueda de directorio](https://man7.org/linux/man-pages/man7/path_resolution.7.html) aún puede permitir que la identidad actual recorra esa ruta conocida; confirma el permiso de búsqueda en cada directorio padre y el permiso de lectura del archivo, en vez de suponer que un fallo al listar el directorio lo protege. Un script legible puede contener una credencial de transferencia, pero para acceder a otra cuenta, esa credencial debe seguir siendo válida y ser aceptada allí de forma independiente. Registra la ruta y las pruebas de permisos sin mostrar valores secretos en registros compartidos.

Para un script CommonJS de Node.js programado, revisa las importaciones sin ruta, como `require('package')`, incluso si el propio script es de solo lectura. [Node busca `node_modules` junto al archivo que importa y luego en sus directorios antecesores](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), antes de recurrir a las rutas globales configuradas. Un usuario de menor privilegio que pueda **escribir y buscar** en uno de esos directorios antecesores quizá pueda crear un paquete que coincida antes. Confirma que se alcanza la importación exacta, que el paquete seleccionado no es un módulo integrado, que se puede crear o modificar la ruta pertinente, que el módulo se resuelve allí en el runtime instalado y que un trabajo de mayor privilegio lo cargará en una ejecución futura. Los metadatos de un directorio padre con permisos de escritura son solo una pista para la revisión; inspecciona el script y el programador de forma pasiva, sin instalar un módulo ni activar el trabajo.

Un índice privado de paquetes de Python es otro límite de confianza cuando un trabajo automatizado instala paquetes con una identidad distinta del sistema operativo. Relaciona el trabajo exacto y la cuenta de ejecución con el índice configurado, los nombres de los paquetes seleccionados y la posibilidad de que un usuario de menor privilegio publique o reemplace un paquete que el trabajo realmente vaya a instalar. Crear una distribución de código fuente puede ejecutar su backend de compilación o el `setup.py` heredado con la identidad del instalador; importar el paquete instalado es una ruta de ejecución distinta. Un listener del índice, un hash de contraseña de carga legible o el nombre de un paquete, por sí solos, no demuestran esa cadena. Revisa el trabajo, la autorización del índice y la procedencia del paquete sin cargar ni instalar nada durante la enumeración. Consulta la [interfaz de sistemas de compilación de pip](https://pip.pypa.io/en/stable/reference/build-system/) y las [directrices para instalaciones seguras](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agente privilegiado puede consultar periódicamente una cola de tareas administrada por un servicio web o contenedor independiente. Si una identidad de menor confianza puede escribir en la base de datos de tareas del servicio, determina si esas filas realmente se sirven a ese agente y si una tarea de comando se ejecuta con la identidad de sistema operativo del agente. Confirma por separado el acceso de escritura a la base de datos, la sesión de destino o clave de enrutamiento, la consulta activa, la autorización de tareas y el usuario efectivo del agente. Ser root dentro de un contenedor no implica por sí solo acceso como root al host; el límite solo se cruza si un consumidor con privilegios en el host ejecuta datos de tareas controlados por un atacante. Inspecciona los metadatos de procesos, archivos de base de datos y servicios sin modificar la cola ni enviar una tarea durante la enumeración.

En cambio, un trabajo recurrente puede leer un comando de una fila de configuración de una base de datos de aplicación. Confirma que el rol de base de datos de menor privilegio puede modificar esa fila exacta, que el trabajo activo la lee después del cambio y que el valor llega a un shell o ejecutor de comandos equivalente bajo una identidad de sistema operativo superior. El acceso de escritura a la base de datos o un valor con aspecto de comando, por sí solos, no demuestran que se ejecute; inspecciona el trabajo y los permisos sin modificar la fila durante la enumeración pasiva.

Un mensaje en cola también puede contener una URL en lugar de código. Si un consumidor privilegiado obtiene esa URL y carga la respuesta como un plugin Lua u otro plugin ejecutable, verifica los permisos del publicador sobre el exchange y la clave de enrutamiento exactos, el binding con la cola consumida, la ruta de obtención y carga del plugin, y la identidad efectiva del worker. [RabbitMQ enruta los mensajes publicados a través de exchanges](https://www.rabbitmq.com/docs/exchanges); un listener del broker o un inicio de sesión válido, por sí solos, no demuestran que el mensaje llegue a este worker. Las credenciales del broker en texto claro capturadas son un indicio aparte que requiere acceso real a la captura de paquetes y tráfico legible; no demuestran autorización para publicar. Un plugin Lua puede ejecutar comandos de shell mediante [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) solo si esa API está disponible en su runtime. Revisa la configuración y el código sin capturar tráfico, publicar mensajes ni obtener un plugin durante la enumeración pasiva.

Cuando un servicio privilegiado de Python expone un endpoint HTTP o socket local, un script legible puede revelar una ruta desde la entrada hasta la ejecución de código incluso si sus permisos impiden modificarlo. Relaciona la identidad del proceso y de la unidad activos con el script exacto, el listener, la autorización de rutas y los campos controlados por el llamante. Luego sigue esos campos a través del análisis y la validación hasta un punto de ejecución dinámica `eval()` o `exec()`. En particular, construir un f-string nuevo a partir del texto de una solicitud y evaluarlo puede interpretar los campos de reemplazo proporcionados por el atacante como expresiones de Python ([advertencia sobre `eval` de Python](https://docs.python.org/3/library/functions.html#eval); [semántica de f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Encontrar `eval` sin contexto o una vinculación a loopback no demuestra que un llamante no confiable llegue al punto de ejecución; revisa el flujo de datos y los controles de acceso reales sin enviar una carga de prueba durante la enumeración.

Un control de solicitudes firmadas en esa ruta requiere su propia revisión. Si el código fuente legible obtiene la clave de firma a partir de un espacio de salida que se puede demostrar pequeño o predecible, y el servicio expone una muestra firmada válida, es posible que la firma ya no proteja un punto de ejecución privilegiado `eval()`. Verifica la derivación exacta de la clave y el verificador, la identidad del servicio activo y el acceso de llamantes locales, y si el campo firmado llega al punto de ejecución; una importación del módulo [`random` de Python](https://docs.python.org/3/library/random.html) o una firma de muestra no demuestra ninguna de esas condiciones. Python también advierte que restringir `__builtins__` [no constituye un límite de seguridad para entradas no confiables de `eval()`](https://docs.python.org/3/library/functions.html#eval). Analiza las claves sin conexión y no envíes solicitudes falsificadas durante la enumeración pasiva.

Un directorio `/etc/systemd/system/<unit>.service.d` vacío en el que se puede escribir es relevante incluso si el archivo de unidad y todos los drop-ins existentes están protegidos: el usuario podría crear un nuevo override `.conf`. Comprueba si la identidad actual puede escribir y buscar en el directorio, si la unidad está cargada y se ejecuta como root, y si se realizará una recarga del daemon seguida de un reinicio. Un permiso de recarga o reinicio, un timer o un arranque posterior pueden hacer efectivo el cambio; el acceso de escritura al directorio no lo ejecuta de inmediato.

En los servicios en ejecución, sigue las rutas literales de `EnvironmentFile=` desde la sección `[Service]` de la unidad, incluidos los archivos cuyos nombres no empiezan por `.env`. Si un usuario con pocos privilegios puede leer alguno, enumera nombres de claves que parezcan credenciales, como `API_TOKEN` o `APP_SECRET_KEY`, sin mostrar sus valores en registros compartidos. Al evaluar la unidad efectiva, comprueba los overrides de drop-ins y los prefijos opcionales `-`. La legibilidad es un indicio de exposición de credenciales; el valor aún debe ser válido para que una acción privilegiada permita la escalada.

### Procesamiento privilegiado de cargas no confiables

Un watcher de archivos que se ejecuta como root puede entregar archivos de un directorio de cargas en el que los usuarios pueden escribir a un parser o extractor de corta duración. Sigue el script padre o servicio del watcher en ejecución y confirma el directorio exacto, quién puede colocar archivos allí, el comando hijo y sus argumentos, y la identidad con la que se ejecuta el hijo. Una instantánea de procesos puede mostrar el watcher y no detectar el extractor entre cargas. No coloques una carga de prueba ni actives el watcher durante la enumeración pasiva.

Un ejemplo concreto es el modo de extracción de Binwalk (`-e`) al procesar datos PFS controlados por un atacante. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permitía que el extractor PFS escribiera fuera de su directorio previsto, incluida una ruta de plugin que Binwalk podía cargar posteriormente. El proyecto upstream incluyó la corrección en [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), pero los backports de las distribuciones pueden conservar una versión mostrada más antigua; comprueba el estado de seguridad del paquete instalado, como en el [tracker de Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), antes de determinar si es aplicable. La versión de Binwalk instalada, por sí sola, no demuestra una vía de escalada de privilegios: un proceso con más privilegios debe invocar realmente la extracción sobre una entrada que el usuario de menor privilegio pueda controlar.

### Compilaciones programadas con dependencias locales

Un `cargo run` programado vuelve a compilar el código fuente con el usuario de ejecución del trabajo. Inspecciona las dependencias locales `{ path = "..." }` del manifiesto, así como los permisos del código fuente y los directorios padres de cada dependencia, no solo los del crate principal. Si un usuario de menor privilegio puede modificar una dependencia que Cargo compila y el trabajo programado ejecuta el resultado, el código compilado puede ejecutarse como ese usuario de ejecución. Confirma el comando efectivo del programador, el directorio de trabajo, la resolución de dependencias y si se realizará una nueva compilación; un archivo de código fuente Rust modificable en otra ubicación es solo un indicio. Para el triaje pasivo basta con leer el manifiesto y los metadatos de las rutas. Consulta la [documentación de Cargo sobre dependencias de ruta](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Archivos del framebuffer de Xvfb

`Xvfb -fbdir <directory>` utiliza archivos mapeados en memoria llamados `Xvfb_screen<n>` para sus pantallas virtuales. Si el proceso Xvfb en ejecución de otro usuario especifica un directorio cuyos archivos de pantalla puede leer el usuario actual, el framebuffer podría revelar el contenido del escritorio de ese usuario. Confirma conjuntamente el proceso, la propiedad de los archivos y sus permisos; que un archivo sea legible no demuestra por sí solo que haya contenido útil en pantalla. Inspecciona primero las rutas y los metadatos, sin copiar datos de imagen en resultados compartidos de enumeración. El [manual de Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) documenta el comportamiento de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
