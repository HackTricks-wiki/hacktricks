# Перелік процесів і шляхи служб

{{#include ../../banners/hacktricks-training.md}}

Корисно з’ясувати, який привілейований процес використовує дані або код, на які може впливати користувач із нижчими привілеями. Перевірте дерево процесів, поточне середовище, відкриті файли, а також unit або скрипт, який запустив кожен кандидат.

## Визначення процесів і власників

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Зв’язок «батьківський процес — дочірній процес» між різними користувачами може бути нормальним, але неочікуваний перехід потребує перевірки команди батьківського процесу, аргументів, виконуваного файла, робочого каталогу та файлів, на які є посилання. Скористайтеся розділом про [користувачів і сеанси](../user-information/user-and-session-triage.md), щоб визначити власника та контекст входу.

### Локальні консолі віртуальних машин

Перевірте параметри `-spice` процесу QEMU разом із адресою, на якій він прослуховує з’єднання. [Документація QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) зазначає, що `disable-ticketing` дає змогу SPICE-клієнтам підключатися без автентифікації. Навіть якщо прослуховувач прив’язаний до loopback, він усе одно може бути доступним іншим локальним користувачам хоста. Перш ніж вважати командний рядок ознакою відкритої консолі, перевірте активний прослуховувач, параметри автентифікації та локальний доступ. Керування консоллю впливає на **гостьову систему**; отримання облікового запису гостя чи зміна стану його завантаження потребує окремих умов на гостьовій системі й не надає root-доступу до хоста віртуалізації. Під час пасивного переліку зчитуйте аргументи процесу та метадані сокета, не підключаючись до гостьової системи й не перезавантажуючи її.

Локально доступний вебінтерфейс може виконувати код із правами свого облікового запису служби, навіть якщо початкова оболонка не має доступу до файлів цього облікового запису. Наприклад, CVE-2023-0297 стосувалася обробки `/flash/addcrypted2` у pyLoad, коли недовірений JavaScript передавався до Js2Py з увімкненими імпортами Python; [виправлення в upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) вимкнуло `pyimport`. Перш ніж вважати процес pyLoad шляхом до підвищення привілеїв, зіставте власника запущеного процесу, адресу прослуховування, доступність endpoint і встановлене виправлення чи backport від постачальника. Самі лише назва процесу, відкритий порт або версія пакета не доводять наявність вразливості; під час пасивного переліку не надсилайте payload для виконання коду.

### Привілейовані оболонки входу зі спільним терміналом

Привілейована інтерактивна оболонка, яка запускає `su --login <user>` без окремого псевдотермінала, може залишити термінал спільним з оболонкою входу користувача з нижчими привілеями. Якщо файл запуску цього користувача можна змінити, а код у ньому може використовувати `TIOCSTI` для ін’єкції введення в термінал, це введення може потрапити до привілейованої оболонки після її відновлення. [Посібник util-linux `su`](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) описує ризик спільного термінала й рекомендує `su --pty`/`-P` для інтерактивного використання; `su -c` запускає окремий сеанс без керівного термінала. Для оцінки ризику потрібно перевірити фактичну батьківську оболонку, зв’язок із терміналом, цільовий файл запуску та політику ядра. Сама лише назва процесу чи аргумент `su -l` — це лише привід для перевірки.

Перегляньте спостережене дерево процесів і стовпці TTY, а потім — читабельний файл запуску та власника й дозволи файла запуску оболонки. У Linux файл `/proc/sys/dev/tty/legacy_tiocsti`, якщо він існує, може допомогти визначити політику; його відсутність не доводить безпечність. [Посібник Linux `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) зазначає, що починаючи з Linux 6.2 для цієї операції може вимагатися `CAP_SYS_ADMIN`, якщо значення цього sysctl — false. Не викликайте ioctl лише для переліку даних хоста.

Іноді обліковий запис бази даних може змінити файл запуску цільового користувача без прямого доступу на запис до файлової системи. Команда PostgreSQL на стороні сервера `COPY ... TO 'filename'` записує файл від імені облікового запису ОС сервера бази даних, але [обмеження PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) дозволяють таку форму лише суперкористувачам бази даних або ролям на кшталт `pg_write_server_files`. Перевірте і роль бази даних, і дозволи ОС сервера на файл; сам лише рядок підключення застосунку не надає права запису до файла. Оцінюючи цей ланцюжок, розглядайте привілейований засіб запуску та можливості облікового запису бази даних окремо.

## Перевірте артефакти часу виконання

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Видалені виконувані файли та видалені, але відкриті файли залишаються доступними, доки не буде закрито останній дескриптор. Вони можуть зберігати докази або доступні секрети. Середовища процесів і пам’ять можуть містити облікові дані, але читання даних іншого процесу обмежується власником, параметрами монтування `/proc`, політикою Yama ptrace та іншими засобами безпеки. Див. [дескриптори файлів](../main-system-information/filesystem-links-and-file-descriptors.md) і [пошук облікових даних під час post-exploitation](../post-exploitation/README.md), щоб ознайомитися з пов’язаними методами.

Збережені трасування системних викликів — ще одна межа дозволів на файли. [`strace` записує аргументи системних викликів у вихідний файл](https://man7.org/linux/man-pages/man1/strace.1.html), тож доступне для читання трасування аргументів [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) може розкрити пароль, переданий привілейованому завданню в командному рядку. Спершу переконайтеся, що поточний користувач може прочитати конкретне трасування і що аргумент справді містить облікові дані; для подальшого переходу до облікового запису Unix потрібен окремий доказ того, що ці облікові дані приймаються. Метадані файлу — корисна пасивна зачіпка, що дає змогу не сканувати всі трасування та не виводити їхній вміст під час звичайного переліку.

## Сокети офісної автоматизації з привілеями

LibreOffice та OpenOffice можуть надавати доступ до свого UNO API через аргумент `--accept=socket,host=<host>,port=<port>;urp;`. Процес офісного пакета, запущений від root і доступний через мережеву кінцеву точку, може дозволити локальному користувачу з нижчими привілеями викликати служби API в контексті безпеки цього процесу. Служба `SystemShellExecute` має операцію для запуску системної команди. Прив’язка до loopback обмежує віддалений доступ, але сокет усе одно доступний локальним користувачам, якщо доступ не заблоковано іншим засобом контролю.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Зіставте власника процесу, точний аргумент `--accept`, а також поточну адресу й порт, на яких він прослуховує з’єднання. Налаштований приймач, якому не вдалося прив’язати адресу, — лише зачіпка; під час пасивного переліку не підключайтеся до API й не викликайте його. Не запускайте привілейований екземпляр office лише для перевірки цієї умови.

## System V shared memory, що використовується привілейованими процесами

Допоміжна програма, що належить root, може створити сегмент спільної пам’яті System V, доступний для запису іншому користувачеві. Якщо згодом ця програма використовує дані із сегмента в команді оболонки чи під час іншої чутливої операції, сегмент перетинає межу привілеїв, навіть якщо виконуваний файл і його файли захищені. `shmget()` бере дозволи на доступ із молодших дев’яти бітів своїх прапорців; режим `0666` дозволяє іншим користувачам записувати дані, тоді як прапорець `IPC_CREAT` не звужує ці дозволи. Пасивно перевіряйте активні сегменти за допомогою `ipcs -m` і зіставляйте їхнього власника, режим і час існування з привілейованим процесом та його обробкою вхідних даних. Сам по собі сегмент, доступний для запису всім, не є доказом виконання команд.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Сегменти System V відрізняються від файлів спільної пам’яті POSIX у `/dev/shm`. Сегмент, створений лише на мить, може бути відсутнім в одному знімку `ipcs`, тому порожній результат не виключає наявності helper, який використовує спільну пам’ять. Перевірте його вихідний код або поведінку бінарного файла, а також будь-яке правило `sudo`, яке його запускає; не запускайте привілейований helper лише для того, щоб сегмент з’явився під час переліку. У [посібнику з IPC namespace](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) пояснюється, як namespace впливають на видимість.<sup>[[2]](#references)[[3]](#references)</sup>

## Перевірки Consul agent за допомогою скриптів

Consul може виконувати скриптові перевірки працездатності з ідентифікатором ОС свого agent. Якщо agent працює від root, увімкнено `enable_script_checks` і користувач із нижчими привілеями може зареєструвати сервіс зі скриптовою перевіркою через локальний HTTP API, цей користувач може спричинити виконання команд від root. Прив’язка API лише до `127.0.0.1` усе одно дає змогу локальним користувачам звертатися до нього. Налаштування `enable_local_script_checks` має вужчу дію: воно виключає скриптові перевірки, надіслані через реєстрацію в HTTP API. Якщо ввімкнено ACL Consul, для реєстрації сервісу потрібен `service:write`; сам рядок `acl.default_policy=allow` не доводить, що анонімний користувач може зареєструвати сервіс. Перевірте разом фактичну identity agent, завантажені налаштування, прив’язку API та авторизацію.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Спрямуйте перевірку за аргументами `-config-dir` і `-config-file` запущеного агента до відповідної конфігурації та перевірте лише назви й значення полів перевірки скриптів і ACL. Конфігураційні файли також можуть містити ключі або токени gossip; не вставляйте їх у спільні журнали. Не реєструйте сервіс і не запускайте перевірку працездатності лише для переліку таких умов.

Окремий шлях через локальні файли існує, якщо користувач із нижчими привілеями може **записувати до каталогу, названого в аргументі `-config-dir` агента, запущеного від root, і шукати в ньому**: із цього каталогу може завантажуватися нове визначення сервісу `.hcl` або `.json`. Можливість пошуку в каталозі та запису до нього може дозволити додати файл, навіть якщо перегляд вмісту каталогу заборонений. Щоб підтвердити можливість виконання команд від root, переконайтеся, що агент справді завантажує конфігурацію з цього каталогу, його **ефективне** налаштування перевірки скриптів дозволяє локальні визначення, визначення завантажується, а агент зберігає привілеї root. [Документація Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) описує, які налаштування та визначення перевірок працездатності можна перезавантажити; для ввімкнення самих перевірок скриптів може знадобитися перезапуск, тож перевірте поведінку встановленої версії. Якщо агента захищено ACL, для [`consul reload` потрібен дозвіл `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); самого дозволу на запис до KV недостатньо. Розглядайте можливість змінювати метадані каталогу як сигнал для перевірки, а не як доказ дозволеного перезавантаження, перезапуску чи виконання команд. Перевіряйте шляхи, дозволи та політики, не записуючи конфігурацію й не викликаючи API.

## Простежте ланцюжок виконання сервісу

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Перевірте unit, drop-ins, `EnvironmentFile=`, helper scripts, relative commands, writable directories і socket activation. Навіть unit, що належить root, може бути небезпечним, якщо читає конфігурацію або скрипт, доступні для запису користувачу. На сторінці про [arbitrary file write](../interesting-files-permissions/write-to-root.md) описано типові способи зловживання сервісами й units. Відстежуйте короткочасні jobs за допомогою [pspy](https://github.com/DominicBreuker/pspy) або засобів аудиту/телеметрії процесів, якщо одноразовий список `ps` їх не показує.

Для власного сервісу **xinetd** зіставте параметри `server`, `user` і контролю доступу в увімкненій секції з активним listener і точним виконуваним файлом. Параметр [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) визначає ідентичність породженого процесу, тоді як set-user-ID bit на виконуваному файлі може окремо змінити його ефективну ідентичність, якщо [`execve` дозволяє такий перехід](https://man7.org/linux/man-pages/man2/execve.2.html). Доступний привілейований binary, що приймає недовірені дані, варто перевірити офлайн за вихідним кодом або дизасемблюванням на наявність memory-safety bugs, наприклад необмеженого перетворення рядка [`scanf`](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) у фіксований buffer. Відповідність сервісу та метадані set-user-ID — це підказки, а не доказ наявності такого бага; не надсилайте дані, що спричиняють збій, і не налагоджуйте активний привілейований сервіс під час пасивного переліку.

Для власного привілейованого listener із доступним для читання вихідним кодом перевірте кожну довжину, контрольовану caller, яка використовується в операції копіювання, наприклад [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Перевірка лише того, що поточний індекс запису перебуває в межах фіксованого buffer, не доводить, що **довжина копіювання** вміщується у вільний простір; після підтвердження, що індекс у межах, перевірте умову `copy_length <= capacity - index`, а також signedness і переповнення арифметики. Це лише підказка для перевірки за умови, що вхідні дані доходять до цієї операції, listener доступний користувачу з нижчими привілеями, а процес зберігає вищу ефективну ідентичність. Перевіряйте вихідний код і метадані процесу офлайн; не надсилайте дані, що спричиняють збій, активному сервісу під час переліку.

У системах, що використовують **Upstart**, визначення system jobs можуть міститися в `/etc/init/*.conf`. Файл job, доступний для запису поточному користувачу, має значення, якщо активний init daemon завантажує саме цей job, його секція `script` або `exec` виконується з вищими привілеями, а користувач може запустити його дозволеною командою `initctl` або іншим реальним тригером. Саме по собі надання sudo-доступу до `initctl` не доводить, що якийсь файл job доступний для запису або що змінений job запуститься. Перевірте права доступу до точного файла job, ефективний параметр run-as, активний daemon і тригер, не редагуючи й не запускаючи job під час переліку. Див. посібники з [конфігурації job в Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) і [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Доступний для читання файл пароля автологіну, наприклад `/etc/autologin/passwd` у системах, де [boot job читає саме цей шлях](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), вказує на можливе розкриття облікових даних. Переконайтеся, що boot job встановлений і використовує цей файл, а потім окремо перевірте, чи пароль дійсний для іншого локального облікового запису або сервісу. Саме ім’я файла не доводить повторне використання пароля; зафіксуйте шлях і метадані доступу, не додаючи пароль до спільного виводу переліку.

`ExecStart=` у unit або запланована команда можуть розкрити точний шлях до скрипту в каталозі, вміст якого не можна перелічити. [Дозвіл на пошук у каталозі](https://man7.org/linux/man-pages/man7/path_resolution.7.html) усе ще може дозволяти поточній ідентичності пройти за цим відомим шляхом; перевірте доступ на пошук для кожного батьківського каталогу та дозвіл на читання файла, а не припускайте, що невдалий перегляд каталогу захищає файл. Скрипт, доступний для читання, може містити облікові дані для передавання даних, але перехід до іншого облікового запису можливий лише за умови, що ці облікові дані залишаються дійсними й окремо приймаються там. Зафіксуйте шлях і дані про права доступу, не виводячи секретні значення у спільні журнали.

Для запланованого скрипту CommonJS Node.js перевіряйте bare imports на кшталт `require('package')`, навіть якщо сам скрипт доступний лише для читання. [Node шукає `node_modules` поруч із файлом, що виконує імпорт, а потім у батьківських каталогах](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), перш ніж переходити до налаштованих глобальних шляхів. Користувач із нижчим рівнем привілеїв, який може **записувати й виконувати пошук** в одному з цих батьківських каталогів, може створити пакет, що відповідатиме раніше за інші. Переконайтеся, що до точного імпорту доходить виконання, вибраний пакет не є вбудованим модулем, відповідний шлях можна створити або змінити, модуль резолвиться там у встановленому runtime, а job із вищими привілеями завантажить його під час наступного запуску. Метадані доступу до батьківського каталогу — лише підказка для перевірки; пасивно перевіряйте скрипт і scheduler, не розміщуючи модуль і не запускаючи job.

Приватний індекс Python-пакетів — ще одна межа довіри, коли автоматизований job встановлює пакети від імені іншої OS-ідентичності. Зіставте точний job і обліковий запис run-as із налаштованим індексом, вибраними назвами пакетів і можливістю користувача з нижчим рівнем привілеїв опублікувати чи замінити пакет, який job справді встановить. Створення source distribution може запустити build backend або застарілий `setup.py` з ідентичністю інсталятора; імпорт встановленого пакета — окремий шлях виконання. Наявність listener індексу, доступного для читання хешу пароля для завантаження або самого імені файла пакета не доводить існування такого ланцюжка. Перевірте job, авторизацію в індексі та походження пакета, нічого не завантажуючи й не встановлюючи під час переліку. Див. [інтерфейс build system у pip](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Привілейований agent може опитувати чергу завдань, якою керує окремий web service або container. Якщо ідентичність із нижчим рівнем довіри може записувати в базу даних завдань сервісу, з’ясуйте, чи надходять ці записи саме цьому agent і чи виконується command task від імені OS-ідентичності agent. Окремо перевірте доступ на запис до бази даних, цільову session або routing key, активне опитування, авторизацію завдань та ефективного користувача agent. root усередині container сам по собі не означає доступу root до host; межа перетинається лише тоді, коли споживач із привілеями на host виконує контрольовані зловмисником дані завдання. Перевіряйте метадані процесу, файла бази даних і сервісу, не змінюючи чергу й не надсилаючи завдання під час переліку.

Натомість recurring job може читати команду з рядка конфігурації application database. Переконайтеся, що роль бази даних із нижчим рівнем привілеїв може змінити саме цей рядок, що активний job читає його після зміни, а значення передається shell або еквівалентному засобу запуску команд із вищою OS-ідентичністю. Доступ на запис до бази даних або саме лише значення, схоже на команду, не доводять виконання; пасивно перевіряйте job і дозволи, не змінюючи рядок.

Повідомлення в черзі також може містити URL, а не код. Якщо привілейований споживач завантажує цей URL і завантажує відповідь як Lua або інший executable plugin, перевірте дозвіл відправника на точний exchange і routing key, прив’язку до черги, з якої читають повідомлення, шлях завантаження й підключення plugin та ефективну ідентичність worker. [RabbitMQ маршрутизує опубліковані повідомлення через exchanges](https://www.rabbitmq.com/docs/exchanges); самі лише listener брокера або дійсні облікові дані не доводять доставку повідомлення цьому worker. Перехоплені незашифровані облікові дані брокера — окрема підказка, для перевірки якої потрібні фактичний доступ до захоплення пакетів і трафік, доступний для читання; вони не доводять наявність дозволу на публікацію. Lua plugin може запускати shell-команди через [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute), лише якщо цей API доступний у його runtime. Перевіряйте конфігурацію та код, не перехоплюючи трафік, не публікуючи повідомлення й не завантажуючи plugin під час пасивного переліку.

Коли привілейований Python service відкриває локальну HTTP- або socket-точку доступу, скрипт, доступний для читання, може розкрити шлях від вхідних даних до виконання коду, навіть якщо права файла не дозволяють його змінювати. Зіставте активний процес та ідентичність unit із точним скриптом, listener, авторизацією маршруту й полями, контрольованими caller. Потім простежте ці поля через розбір і валідацію до динамічного виклику `eval()` або `exec()`. Зокрема, створення нового f-string із тексту запиту та його обчислення може інтерпретувати поля підстановки, надані зловмисником, як вирази Python ([попередження Python щодо `eval`](https://docs.python.org/3/library/functions.html#eval); [семантика f-string](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Сам по собі збіг `eval` або прив’язка до loopback не доводить, що недовірений caller досягає цього місця; перевірте фактичний рух даних і контролі доступу, не надсилаючи тестове навантаження під час переліку.

Окремо перевірте gate підписаних запитів на цьому маршруті. Якщо доступний для читання вихідний код показує, що signing key походить із простору можливих значень, який явно малий або передбачуваний, а сервіс надає дійсний підписаний приклад, підпис може більше не захищати привілейований виклик `eval()`. Перевірте точний спосіб отримання ключа та verifier, ідентичність активного сервісу й доступ локальних caller, а також чи потрапляє підписане поле до цього місця; імпорт Python-модуля [`random`](https://docs.python.org/3/library/random.html) або сам підписаний приклад нічого з цього не доводять. Python також попереджає, що обмеження `__builtins__` [не є межею безпеки для недовірених вхідних даних `eval()`](https://docs.python.org/3/library/functions.html#eval). Аналізуйте ключ офлайн і не надсилайте підроблені запити під час пасивного переліку.

Порожній каталог `/etc/systemd/system/<unit>.service.d`, доступний для запису, має значення, навіть якщо файл unit і всі наявні drop-ins захищені: користувач може створити нове перевизначення `.conf`. Перевірте, чи поточна ідентичність має доступ на запис і пошук у каталозі, чи завантажений unit і чи виконується він від root, а також чи відбудеться daemon reload із подальшим перезапуском. Дозвіл на reload або restart, timer чи наступне завантаження системи можуть активувати зміни; одного доступу на запис до каталогу недостатньо для негайного виконання.

Для активних сервісів перевіряйте буквальні шляхи `EnvironmentFile=` із секції `[Service]` unit, зокрема файли, назви яких не починаються з `.env`. Якщо користувач із низькими привілеями може прочитати такий файл, перелічіть назви ключів, схожі на облікові дані, наприклад `API_TOKEN` або `APP_SECRET_KEY`, не виводячи значення у спільні журнали. Перевіряйте drop-in overrides і необов’язковий префікс `-`, визначаючи ефективну конфігурацію unit. Доступність для читання вказує на можливе розкриття облікових даних; для підвищення привілеїв це значення ще має бути дійсним для привілейованої дії.

### Привілейована обробка недовірених завантажень

Файловий watcher, запущений від root, може передавати файли з доступного користувачам для запису каталогу завантажень короткочасному parser або extractor. Простежте батьківський скрипт або сервіс активного watcher і перевірте точний каталог, хто може поміщати туди файли, дочірню команду та її аргументи, а також ідентичність, від імені якої запускається дочірній процес. Знімок процесів може показати watcher, але не extractor, який працює між завантаженнями. Не розміщуйте тестове навантаження й не запускайте watcher під час пасивного переліку.

Конкретний приклад — режим розпакування Binwalk (`-e`), який обробляє контрольовані зловмисником дані PFS. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) дозволяла extractor для PFS записувати файли за межі передбаченого каталогу, зокрема за шляхом plugin, який Binwalk міг завантажити пізніше. Upstream включив виправлення у [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), але distribution backports можуть зберігати старішу версію, що відображається; перш ніж визначати, чи стосується це системи, перевірте стан безпеки встановленого пакета, наприклад у [трекері Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510). Сама лише встановлена версія Binwalk не доводить наявність шляху до підвищення привілеїв: розпакування має фактично запускатися привілейованішим процесом на даних, які може контролювати користувач із нижчими привілеями.

### Заплановані збірки з локальними залежностями

Запланована команда `cargo run` компілює вихідний код від імені користувача run-as цього job. Перевірте локальні залежності `{ path = "..." }` у manifest, а також права доступу до вихідного коду й батьківських каталогів кожної залежності, а не лише основного crate. Якщо користувач із нижчим рівнем привілеїв може змінити залежність, яку Cargo компілює, а запланований job запускає результат, скомпільований код може виконуватися від імені цього користувача run-as. Переконайтеся, яка команда scheduler фактично виконується, який робочий каталог використовується, як розв’язуються залежності та чи відбудеться повторна збірка; доступний для запису файл вихідного коду Rust деінде — лише підказка. Для пасивного аналізу достатньо прочитати manifest і метадані шляху. Див. [документацію Cargo про залежності за шляхом](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Файли framebuffer Xvfb

`Xvfb -fbdir <directory>` використовує файли, зіставлені з пам’яттю, з назвами `Xvfb_screen<n>` для своїх віртуальних екранів. Якщо активний процес Xvfb іншого користувача вказує каталог, файли екранів у якому доступні для читання поточному користувачу, framebuffer може розкрити вміст робочого столу цього користувача. Перевірте разом процес, власника файлів і дозволи; сам по собі доступний для читання файл не доводить, що на екрані є корисний вміст. Спочатку перевірте шляхи й метадані, не копіюючи дані зображення у спільний вивід переліку. Поведінку `-fbdir` описано в [посібнику Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html).

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
