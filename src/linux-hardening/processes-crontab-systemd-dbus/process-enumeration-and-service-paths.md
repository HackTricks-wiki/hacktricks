# Prozessauflistung und Dienstpfade

{{#include ../../banners/hacktricks-training.md}}

Die entscheidende Frage ist, welcher privilegierte Prozess Daten oder Code verarbeitet, die ein Benutzer mit geringeren Berechtigungen beeinflussen kann. Untersuche den Prozessbaum, die aktuelle Umgebung, offene Dateien sowie die Unit oder das Skript, mit dem jeder infrage kommende Prozess gestartet wurde.

## Prozesse und Eigentümer ermitteln

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Eine Parent-Child-Beziehung zwischen verschiedenen Benutzern kann normal sein, aber ein unerwarteter Übergang sollte Anlass sein, den Parent-Befehl, die Argumente, die ausführbare Datei, das Arbeitsverzeichnis und referenzierte Dateien zu überprüfen. Nutze [users and sessions](../user-information/user-and-session-triage.md), um den Eigentümer und den Login-Kontext einzuordnen.

### Lokale Konsolen virtueller Maschinen

Überprüfe die `-spice`-Optionen eines QEMU-Prozesses zusammen mit seiner Listening-Adresse. [QEMU dokumentiert](https://www.qemu.org/docs/master/system/qemu-manpage.html), dass `disable-ticketing` SPICE-Clients eine Verbindung ohne Authentifizierung ermöglicht. Ein an loopback gebundener Listener kann dennoch für andere lokale Host-Benutzer erreichbar sein. Bestätige den aktiven Listener, die Authentifizierungsoptionen und den lokalen Zugriff, bevor du die Befehlszeile als exponierte Konsole einstufst. Die Konsolensteuerung wirkt sich auf den **Guest** aus; ein Guest-Konto zu erhalten oder dessen Boot-Zustand zu ändern, erfordert separate Bedingungen innerhalb des Guests und verschafft keinen root-Zugriff auf den Virtualisierungshost. Lies Prozessargumente und Socket-Metadaten, ohne dich während der passiven Enumeration mit dem Guest zu verbinden oder ihn neu zu starten.

Eine lokal erreichbare Weboberfläche kann Code mit dem Service-Konto ausführen, selbst wenn die erste Shell nicht auf dessen Dateien zugreifen kann. CVE-2023-0297 betraf beispielsweise pyLoads Verarbeitung von `/flash/addcrypted2`, wenn nicht vertrauenswürdiges JavaScript mit aktivierten Python-Imports an Js2Py übergeben wurde; der [upstream fix](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deaktivierte `pyimport`. Setze den Eigentümer des laufenden Prozesses, die Listening-Adresse, die Erreichbarkeit des Endpoints und den installierten Patch oder Backport des Anbieters in Beziehung, bevor du einen pyLoad-Prozess als möglichen Eskalationspfad einstufst. Ein Prozessname, ein offener Port oder eine Paketversion allein beweist keine Exponierung; bei der passiven Enumeration sollte kein Execution-Payload gesendet werden.

### Privilegierte Login-Shells mit gemeinsamem Terminal

Eine privilegierte interaktive Shell, die `su --login <user>` ohne unabhängiges Pseudo-Terminal ausführt, kann dazu führen, dass ihr Terminal weiterhin mit der Login-Shell des weniger privilegierten Benutzers geteilt wird. Wenn die Startdatei dieses Benutzers kontrollierbar ist und darin ausgeführter Code `TIOCSTI` verwenden kann, um Terminaleingaben einzuschleusen, können diese Eingaben die privilegierte Shell erreichen, sobald sie wieder aktiv wird. Das [Handbuch zu `su` aus util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) beschreibt das Risiko gemeinsam genutzter Terminals und empfiehlt für die interaktive Verwendung `su --pty`/`-P`; `su -c` startet eine separate Sitzung ohne steuerndes Terminal. Das Risiko hängt von der tatsächlichen Parent-Shell, der Terminalbeziehung, der Startdatei des Zielbenutzers und der Kernel-Richtlinie ab. Ein Prozessname oder ein `su -l`-Argument allein ist lediglich ein Hinweis zur Überprüfung.

Untersuche den beobachteten Prozessbaum und die TTY-Spalten sowie anschließend den lesbaren Launcher und die Eigentums- und Berechtigungseinstellungen der Startdatei. Unter Linux kann `/proc/sys/dev/tty/legacy_tiocsti`, sofern vorhanden, bei der Einordnung der Richtlinie helfen; sein Fehlen ist kein Sicherheitsbeweis. Das [Linux-Handbuch zu `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) weist darauf hin, dass die Operation seit Linux 6.2 möglicherweise `CAP_SYS_ADMIN` erfordert, wenn dieser sysctl-Wert false ist. Rufe das ioctl nicht auf, nur um den Host zu enumerieren.

Ein Datenbankkonto kann manchmal die Startdatei des Zielbenutzers ändern, ohne direkten Schreibzugriff auf das Dateisystem zu haben. PostgreSQLs serverseitiges `COPY ... TO 'filename'` schreibt unter dem OS-Konto des Datenbankservers, aber [PostgreSQL schränkt dies ein](https://www.postgresql.org/docs/current/sql-copy.html): Diese Dateiform ist Datenbank-Superusern oder Rollen wie `pg_write_server_files` vorbehalten. Bestätige sowohl die Datenbankrolle als auch die Dateiberechtigungen des Server-OS; eine Connection-String der Anwendung gewährt allein keine Schreibberechtigung für Dateien. Berücksichtige bei der Bewertung der Angriffskette den privilegierten Launcher und die Fähigkeiten des Datenbankkontos getrennt voneinander.

## Laufzeit-Artefakte untersuchen

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Gelöschte Executables und gelöschte, aber noch geöffnete Dateien bleiben referenziert, bis ihr letzter Dateideskriptor geschlossen wird. Sie können Beweise oder zugängliche Secrets bewahren. Prozessumgebungen und Speicher können Zugangsdaten enthalten, doch das Auslesen eines anderen Prozesses wird durch den Besitz, `/proc`-Mount-Optionen, die Yama-`ptrace`-Richtlinie und weitere Sicherheitskontrollen eingeschränkt. Weitere Techniken finden Sie unter [file descriptors](../main-system-information/filesystem-links-and-file-descriptors.md) und [post-exploitation credential hunting](../post-exploitation/README.md).

Gespeicherte syscall-Traces unterliegen ebenfalls Dateiberechtigungen. [`strace` zeichnet syscall-Argumente in eine Ausgabedatei auf](https://man7.org/linux/man-pages/man1/strace.1.html), daher kann ein lesbarer Trace von [`execve`-Argumenten](https://man7.org/linux/man-pages/man2/execve.2.html) ein Passwort offenlegen, das ein privilegierter Job in seiner Befehlszeile übergeben hat. Stellen Sie zunächst fest, dass der aktuelle Benutzer den jeweiligen Trace lesen kann und das Argument tatsächlich Zugangsdaten enthält; für einen späteren Wechsel des Unix-Kontos muss separat nachgewiesen werden, dass die Zugangsdaten dort akzeptiert werden. Dateimetadaten sind ein nützlicher passiver Hinweis, ohne jeden Trace zu durchsuchen oder bei der routinemäßigen Enumeration seinen Inhalt auszugeben.

## Privilegierte Office-Automatisierungs-Sockets

LibreOffice und OpenOffice können ihre UNO-API über ein Argument der Form `--accept=socket,host=<host>,port=<port>;urp;` bereitstellen. Ein root-eigener Office-Prozess mit einem erreichbaren Endpunkt kann es einem lokal niedriger privilegierten Benutzer ermöglichen, API-Dienste im Sicherheitskontext dieses Prozesses aufzurufen. Der Dienst `SystemShellExecute` enthält eine Operation zum Starten eines Systembefehls. Eine Bindung an Loopback schränkt die Erreichbarkeit aus der Ferne ein, lässt den Socket jedoch weiterhin für lokale Benutzer erreichbar, sofern keine andere Kontrolle den Zugriff verhindert.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Korreliere den Prozesseigentümer, das genaue Argument `--accept` sowie die aktuelle Listening-Adresse und den Port. Ein konfigurierter Acceptor, der nicht an eine Adresse binden konnte, ist lediglich ein Ansatzpunkt; stelle bei der passiven Enumeration keine Verbindung zur API her und rufe sie nicht auf. Starte nicht eigens zum Testen dieser Bedingung eine privilegierte Office-Instanz.

## Von privilegierten Prozessen verwendeter System-V-Shared-Memory

Ein root-eigener Helper kann ein System-V-Shared-Memory-Segment erstellen, in das ein anderer Benutzer schreiben kann. Wenn der Helper später den Daten aus diesem Segment in einem Shell-Befehl oder bei einem anderen sensiblen Vorgang vertraut, überschreitet das Segment eine Privilegiengrenze, auch wenn die ausführbare Datei und ihre Dateien geschützt sind. `shmget()` übernimmt die Zugriffsberechtigungen aus den unteren neun Bits seiner Flags; der Modus `0666` erlaubt anderen Benutzern das Schreiben, während ein `IPC_CREAT`-Flag diese Berechtigungen nicht einschränkt. Untersuche aktive Segmente passiv mit `ipcs -m` und gleiche deren Eigentümer, Modus und Lebensdauer mit dem privilegierten Prozess und dessen Eingabeverarbeitung ab. Ein für alle Benutzer beschreibbares Segment allein belegt keine Befehlsausführung.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

System-V-Segmente unterscheiden sich von POSIX-Dateien für gemeinsam genutzten Speicher unter `/dev/shm`. Ein nur kurzzeitig erstelltes Segment kann in einer einzelnen `ipcs`-Momentaufnahme fehlen. Eine leere Ausgabe schließt daher einen Helper, der gemeinsam genutzten Speicher verwendet, nicht aus. Prüfe sein Quellcode oder das Verhalten der Binärdatei sowie alle `sudo`-Regeln, die es starten; rufe den privilegierten Helper nicht nur auf, damit während der Enumeration ein Segment erscheint. Der [IPC-Namespace-Leitfaden](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) erklärt, wie Namespaces die Sichtbarkeit beeinflussen.<sup>[[2]](#references)[[3]](#references)</sup>

## Consul-Agent-Script-Checks

Consul kann Script-Health-Checks mit der Betriebssystemidentität seines Agents ausführen. Wenn ein Agent als root läuft, `enable_script_checks` aktiviert und einem Benutzer mit niedrigeren Berechtigungen erlaubt, über die lokale HTTP-API einen Service mit einem Script-Check zu registrieren, kann dieser Benutzer dadurch Befehle mit root-Rechten ausführen lassen. Auch wenn die API nur an `127.0.0.1` gebunden ist, können lokale Benutzer darauf zugreifen. Die Einstellung `enable_local_script_checks` ist enger gefasst: Sie schließt Script-Checks aus, die über HTTP-API-Registrierungen übermittelt werden. Wenn Consul-ACLs aktiviert sind, erfordert die Service-Registrierung `service:write`; eine Zeile mit `acl.default_policy=allow` allein beweist nicht, dass ein anonymer Aufrufer Services registrieren kann. Prüfe gemeinsam die tatsächliche Agent-Identität, die geladenen Einstellungen, die API-Bindung und die Autorisierung.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Folgen Sie den Argumenten `-config-dir` und `-config-file` des laufenden Agents zur entsprechenden Konfiguration und prüfen Sie ausschließlich die Namen und Einstellungen der Felder für Script-Checks und ACLs. Konfigurationsdateien können auch Gossip-Schlüssel oder Tokens enthalten; vermeiden Sie es, diese in gemeinsam genutzte Logs einzufügen. Registrieren Sie keinen Service und führen Sie keinen Health-Check aus, nur um diesen Sachverhalt zu ermitteln.

Ein separater lokaler Datei-Pfad besteht, wenn ein Benutzer mit geringeren Berechtigungen in das Verzeichnis schreiben und darin suchen kann, das mit `-config-dir` für einen als Root ausgeführten Agent angegeben ist: Eine neue `.hcl`- oder `.json`-Service-Definition kann aus diesem Verzeichnis geladen werden. Such- und Schreibberechtigungen für ein Verzeichnis können das Hinzufügen einer Datei ermöglichen, selbst wenn das Auflisten des Verzeichnisses verweigert wird. Damit Befehle als Root ausgeführt werden, müssen Sie bestätigen, dass der Agent dieses Verzeichnis tatsächlich lädt, die **effektive** Script-Check-Einstellung lokale Definitionen zulässt, die Definition geladen wird und der Agent Root-Berechtigungen behält. [Consul dokumentiert](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations), welche Einstellungen und Health-Check-Definitionen neu geladen werden können; zum Aktivieren von Script-Checks kann selbst ein Neustart erforderlich sein. Prüfen Sie daher das Verhalten der installierten Version. Wenn ACLs den Agent schützen, erfordert [`consul reload` die Berechtigung `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); die KV-Schreibberechtigung allein reicht dafür nicht aus. Betrachten Sie beschreibbare Verzeichnismetadaten als Anlass zur Prüfung, nicht als Beleg für einen autorisierten Reload, Neustart oder die Ausführung von Befehlen. Prüfen Sie Pfade, Berechtigungen und Richtlinien, ohne Konfigurationen zu schreiben oder die API aufzurufen.

## Folgen Sie der Service-Ausführungskette

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Prüfen Sie die Unit, Drop-ins, `EnvironmentFile=`, Hilfsskripte, relative Befehle, beschreibbare Verzeichnisse und Socket-Aktivierung. Eine root-eigene Unit kann trotzdem unsicher sein, wenn sie eine benutzerbeschreibbare Konfiguration oder ein solches Skript einliest. Die Seite zu [arbitrary file write](../interesting-files-permissions/write-to-root.md) behandelt häufige Missbrauchswege über Services und Units. Überwachen Sie kurzlebige Jobs mit [pspy](https://github.com/DominicBreuker/pspy) oder Audit-/Prozess-Telemetrie, wenn ein einmaliges `ps`-Listing sie nicht erfasst.

Bei einem benutzerdefinierten **xinetd**-Service gleichen Sie die aktivierte Konfiguration mit `server`, `user` und Zugriffskontrollen mit dem aktiven Listener und der genauen ausführbaren Datei ab. Die [`user`-Einstellung](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) bestimmt die Identität des gestarteten Prozesses, während ein Set-user-ID-Bit auf der ausführbaren Datei dessen effektive Identität separat ändern kann, wenn [`execve` diesen Übergang zulässt](https://man7.org/linux/man-pages/man2/execve.2.html). Eine erreichbare privilegierte Binärdatei, die nicht vertrauenswürdige Eingaben akzeptiert, sollte offline anhand des Quellcodes oder Disassemblats auf Memory-Safety-Fehler geprüft werden, etwa auf eine unbegrenzte [`scanf`-Stringkonvertierung](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) in einen festen Buffer. Das Service-Mapping und die Set-user-ID-Metadaten sind Hinweise, aber kein Beweis für einen solchen Fehler; senden Sie während der passiven Enumeration keine Crash-Eingaben und debuggen Sie den laufenden privilegierten Service nicht.

Bei einem benutzerdefinierten privilegierten Listener mit lesbarem Quellcode prüfen Sie jede vom Aufrufer kontrollierte Länge, die bei einer Kopieroperation wie [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html) verwendet wird. Nur zu prüfen, ob der aktuelle Schreibindex innerhalb eines festen Buffers liegt, belegt nicht, dass die **Kopierlänge** in den verbleibenden Platz passt; verifizieren Sie `copy_length <= capacity - index`, nachdem Sie bestätigt haben, dass der Index im gültigen Bereich liegt, und prüfen Sie Vorzeichen sowie arithmetischen Überlauf. Dieser Hinweis ist nur relevant, wenn die Eingabe diese Operation erreicht, der Listener für den weniger privilegierten Benutzer zugänglich ist und der Prozess eine höhere effektive Identität behält. Prüfen Sie Quellcode und Prozessmetadaten offline; senden Sie während der Enumeration keine Crash-Eingaben an den laufenden Service.

Auf Systemen mit **Upstart** können System-Jobdefinitionen unter `/etc/init/*.conf` liegen. Eine für den aktuellen Benutzer beschreibbare Jobdatei ist relevant, wenn der aktive Init-Daemon genau diesen Job lädt, dessen `script`- oder `exec`-Abschnitt mit einer höher privilegierten Identität ausgeführt wird und der Benutzer ihn über einen zulässigen `initctl`-Befehl oder einen anderen tatsächlichen Trigger starten kann. Eine sudo-Freigabe für `initctl` allein beweist weder, dass eine Jobdatei beschreibbar ist, noch, dass ein geänderter Job ausgeführt wird. Prüfen Sie die Berechtigungen der konkreten Jobdatei, die effektive Ausführungsidentität, den aktiven Daemon und den Trigger, ohne den Job während der Enumeration zu bearbeiten oder zu starten. Siehe die Handbücher zur [Upstart-Jobkonfiguration](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) und zu [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Eine lesbare Autologin-Passwortdatei, etwa `/etc/autologin/passwd` auf Systemen, deren [Boot-Job genau diesen Pfad einliest](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), ist ein Hinweis auf offengelegte Zugangsdaten. Bestätigen Sie, dass der Boot-Job installiert ist und die Datei verwendet, und prüfen Sie dann separat, ob das Passwort für ein anderes lokales Konto oder einen Service gültig ist. Der Dateiname allein belegt keine Wiederverwendung des Passworts; dokumentieren Sie Pfad und Zugriffsmetadaten, ohne das Passwort in gemeinsam genutzte Enumeration-Ausgaben aufzunehmen.

`ExecStart=` einer Unit oder ein geplanter Befehl kann den genauen Pfad eines Skripts in einem nicht auflistbaren Verzeichnis offenlegen. Die [Verzeichnissuchberechtigung](https://man7.org/linux/man-pages/man7/path_resolution.7.html) kann der aktuellen Identität weiterhin erlauben, diesen bekannten Pfad zu durchlaufen; bestätigen Sie die Suchberechtigung für jedes übergeordnete Verzeichnis und die Leseberechtigung für die Datei, statt anzunehmen, dass ein fehlgeschlagenes Verzeichnis-Listing sie schützt. Ein lesbares Skript kann Zugangsdaten für einen Transfer enthalten, aber der Zugriff auf ein anderes Konto setzt voraus, dass diese Zugangsdaten weiterhin gültig sind und dort unabhängig akzeptiert werden. Dokumentieren Sie Pfad und Berechtigungsnachweise, ohne Geheimnisse in gemeinsam genutzte Logs auszugeben.

Prüfen Sie bei einem geplanten CommonJS-Node.js-Skript auch unqualifizierte Imports wie `require('package')`, selbst wenn das Skript selbst schreibgeschützt ist. [Node sucht `node_modules` neben der importierenden Datei und anschließend in deren übergeordneten Verzeichnissen](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), bevor es auf konfigurierte globale Pfade zurückgreift. Ein weniger privilegierter Benutzer, der eines dieser übergeordneten Verzeichnisse **beschreiben und durchsuchen** kann, kann möglicherweise ein früher gefundenes Package erstellen. Bestätigen Sie, dass der konkrete Import erreicht wird, das ausgewählte Package kein integriertes Modul ist, der relevante Pfad erstellt oder geändert werden kann, das Modul dort in der installierten Runtime aufgelöst wird und ein höher privilegierter Job es bei einem künftigen Aufruf lädt. Beschreibbare Metadaten eines übergeordneten Verzeichnisses sind lediglich ein Prüfhinnweis; untersuchen Sie das Skript und den Scheduler passiv, ohne ein Modul abzulegen oder den Job auszulösen.

Ein privater Python-Package-Index ist eine weitere Vertrauensgrenze, wenn ein automatisierter Job Packages unter einer anderen OS-Identität installiert. Gleichen Sie den konkreten Job und das Run-as-Konto mit dem konfigurierten Index, den ausgewählten Package-Namen und der Frage ab, ob ein weniger privilegierter Benutzer ein Package veröffentlichen oder ersetzen kann, das der Job tatsächlich installieren wird. Beim Erstellen einer Source Distribution können deren Build-Backend oder das veraltete `setup.py` unter der Identität des Installers ausgeführt werden; das Importieren des installierten Packages ist ein separater Ausführungspfad. Ein Index-Listener, ein lesbarer Passwort-Hash für Uploads oder ein Package-Dateiname allein belegt diese Angriffskette nicht. Prüfen Sie Job, Index-Autorisierung und Package-Provenienz, ohne während der Enumeration etwas hochzuladen oder zu installieren. Siehe [pips Build-System-Schnittstelle](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Ein privilegierter Agent kann eine von einem separaten Webservice oder Container verwaltete Task-Queue abfragen. Wenn eine weniger vertrauenswürdige Identität in die Task-Datenbank des Service schreiben kann, stellen Sie fest, ob diese Einträge tatsächlich an den Agenten ausgeliefert werden und ob ein Command-Task mit der OS-Identität des Agenten ausgeführt wird. Prüfen Sie Datenbank-Schreibzugriff, Ziel-Session oder Routing-Key, aktives Polling, Task-Autorisierung und effektiven Benutzer des Agenten jeweils separat. Root innerhalb eines Containers bedeutet nicht automatisch Host-Root-Zugriff; die Grenze wird nur überschritten, wenn ein hostprivilegierter Consumer angreiferkontrollierte Task-Daten ausführt. Prüfen Sie Prozess-, Datenbankdatei- und Service-Metadaten, ohne während der Enumeration die Queue zu ändern oder einen Task zu senden.

Ein wiederkehrender Job kann stattdessen einen Befehl aus einer Konfigurationszeile in einer Anwendungsdatenbank lesen. Bestätigen Sie, dass die weniger privilegierte Datenbankrolle genau diese Zeile ändern kann, dass der aktive Job sie nach der Änderung einliest und dass der Wert unter einer höheren OS-Identität an eine Shell oder einen gleichwertigen Command Runner übergeben wird. Datenbank-Schreibzugriff oder ein befehlsähnlicher Wert allein belegt keine Ausführung; prüfen Sie Job und Berechtigungen, ohne die Zeile während der passiven Enumeration zu ändern.

Eine Nachricht in einer Queue kann statt Code auch eine URL enthalten. Wenn ein privilegierter Consumer diese URL abruft und die Antwort als Lua- oder anderes ausführbares Plugin lädt, verifizieren Sie die Veröffentlichungsberechtigung für den konkreten Exchange und Routing-Key, die Bindung an die konsumierte Queue, den Abruf- und Plugin-Ladepfad sowie die effektive Identität des Workers. [RabbitMQ leitet veröffentlichte Nachrichten über Exchanges weiter](https://www.rabbitmq.com/docs/exchanges); ein Broker-Listener oder ein gültiger Login allein belegt nicht, dass die Nachricht an diesen Worker zugestellt wird. Abgefangene unverschlüsselte Broker-Zugangsdaten sind ein separater Hinweis, für den tatsächlicher Zugriff auf einen Packet Capture und lesbarer Traffic erforderlich sind; sie belegen keine Veröffentlichungsberechtigung. Ein Lua-Plugin kann über [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) Shell-Befehle ausführen, aber nur, wenn diese API in seiner Runtime verfügbar ist. Prüfen Sie Konfiguration und Code, ohne während der passiven Enumeration Traffic mitzuschneiden, Nachrichten zu veröffentlichen oder ein Plugin abzurufen.

Wenn ein privilegierter Python-Service einen lokalen HTTP- oder Socket-Endpunkt bereitstellt, kann ein lesbares Skript einen Pfad von Eingaben zu ausführbarem Code offenlegen, selbst wenn seine Dateiberechtigungen Änderungen verhindern. Gleichen Sie den aktiven Prozess und die Unit-Identität mit dem konkreten Skript, Listener, der Routenautorisierung und den vom Aufrufer kontrollierten Feldern ab. Verfolgen Sie diese Felder anschließend durch Parsing und Validierung bis zu einem dynamischen `eval()`- oder `exec()`-Sink. Insbesondere kann das Erstellen eines neuen f-Strings aus Request-Text und dessen Auswertung vom Angreifer gelieferte Replacement-Felder als Python-Ausdrücke interpretieren ([Python-Warnung zu `eval`](https://docs.python.org/3/library/functions.html#eval); [Semantik von f-Strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Ein bloßer Treffer für `eval` oder eine Loopback-Bindung beweist nicht, dass ein nicht vertrauenswürdiger Aufrufer den Sink erreicht; prüfen Sie den tatsächlichen Datenfluss und die Zugriffskontrollen, ohne während der Enumeration eine Test-Payload zu senden.

Ein Gate für signierte Requests auf dieser Route muss separat geprüft werden. Wenn der lesbare Quellcode den Signaturschlüssel nachweislich aus einem sehr kleinen oder vorhersagbaren Ausgaberaum ableitet und der Service ein gültiges signiertes Beispiel bereitstellt, schützt die Signatur einen privilegierten `eval()`-Sink möglicherweise nicht mehr. Verifizieren Sie die konkrete Schlüsselableitung und den Verifier, die Identität des laufenden Service und den lokalen Zugriff des Aufrufers sowie, ob das signierte Feld den Sink erreicht; ein Import von Pythons [`random`-Modul](https://docs.python.org/3/library/random.html) oder eine Beispielsignatur allein beweist keine dieser Bedingungen. Python warnt außerdem, dass eine Einschränkung von `__builtins__` [keine Sicherheitsgrenze für nicht vertrauenswürdige `eval()`-Eingaben darstellt](https://docs.python.org/3/library/functions.html#eval). Analysieren Sie Schlüssel offline und senden Sie während der passiven Enumeration keine gefälschten Requests.

Ein leeres, aber beschreibbares Verzeichnis `/etc/systemd/system/<unit>.service.d` ist relevant, selbst wenn die Unit-Datei und alle vorhandenen Drop-ins geschützt sind: Der Benutzer kann einen neuen `.conf`-Override erstellen. Prüfen Sie, ob das Verzeichnis für die aktuelle Identität beschreibbar und durchsuchbar ist, ob die Unit geladen ist und als root ausgeführt wird und ob ein Daemon-Reload mit anschließendem Neustart stattfindet. Eine Reload- oder Neustartberechtigung, ein Timer oder ein späterer Boot kann die Änderung wirksam machen; Schreibzugriff auf das Verzeichnis allein führt sie nicht sofort aus.

Verfolgen Sie bei laufenden Services die wörtlichen `EnvironmentFile=`-Pfade aus dem `[Service]`-Abschnitt der Unit, auch wenn die Dateinamen nicht mit `.env` beginnen. Wenn ein Benutzer mit geringen Berechtigungen eine solche Datei lesen kann, listen Sie namenähnliche Schlüssel für Zugangsdaten wie `API_TOKEN` oder `APP_SECRET_KEY` auf, ohne die Werte in gemeinsam genutzte Logs auszugeben. Prüfen Sie beim Bewerten der effektiven Unit auch Drop-in-Overrides und optionale `-`-Präfixe. Lesbarkeit ist ein Hinweis auf offengelegte Zugangsdaten; der Wert muss weiterhin für eine privilegierte Aktion gültig sein, damit daraus eine Rechteausweitung entsteht.

### Privilegierte Verarbeitung nicht vertrauenswürdiger Uploads

Ein als root laufender File-Watcher kann Dateien aus einem benutzerbeschreibbaren Upload-Verzeichnis an einen kurzlebigen Parser oder Extractor übergeben. Verfolgen Sie das übergeordnete Skript oder den Service des laufenden Watchers und bestätigen Sie das konkrete Verzeichnis, wer dort Dateien ablegen kann, den Child-Befehl und seine Argumente sowie die Identität, unter der der Child-Prozess ausgeführt wird. Ein Prozess-Snapshot kann den Watcher zeigen, aber den Extractor zwischen Uploads verpassen. Legen Sie während der passiven Enumeration keine Test-Payload ab und lösen Sie den Watcher nicht aus.

Ein konkretes Beispiel ist der Extraktionsmodus (`-e`) von Binwalk, der angreiferkontrollierte PFS-Daten verarbeitet. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) ermöglichte es dem PFS-Extractor, außerhalb seines vorgesehenen Verzeichnisses zu schreiben, unter anderem in einen Plugin-Pfad, den Binwalk später laden konnte. Upstream nahm die Korrektur in [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4) auf, aber Distributionen können Fixes zurückportieren, obwohl eine ältere Version angezeigt wird; prüfen Sie vor der Bewertung der Anwendbarkeit den Sicherheitsstatus des installierten Packages, etwa im [Debian-Tracker](https://security-tracker.debian.org/tracker/CVE-2022-4510). Eine installierte Binwalk-Version allein belegt keinen Rechteausweitungspfad: Die Extraktion muss tatsächlich von einem privilegierteren Prozess mit Eingaben aufgerufen werden, die der weniger privilegierte Benutzer kontrollieren kann.

### Geplante Builds mit lokalen Abhängigkeiten

Ein geplanter `cargo run` kompiliert den Quellcode als Benutzer, unter dem der Job ausgeführt wird, erneut. Prüfen Sie die lokalen `{ path = "..." }`-Abhängigkeiten im Manifest sowie Quellcode- und Verzeichnisberechtigungen jeder Abhängigkeit, nicht nur die des Haupt-Crates. Wenn ein weniger privilegierter Benutzer eine Abhängigkeit ändern kann, die Cargo kompiliert, und der geplante Job das Ergebnis ausführt, kann der kompilierte Code als dieser Run-as-Benutzer ausgeführt werden. Bestätigen Sie den effektiven Scheduler-Befehl, das Arbeitsverzeichnis, die Auflösung der Abhängigkeiten und ob ein erneuter Build stattfindet; eine an anderer Stelle beschreibbare Rust-Quelldatei ist lediglich ein Hinweis. Für eine passive Ersteinschätzung reichen das Lesen des Manifests und der Pfadmetadaten aus. Siehe die [Cargo-Dokumentation zu Pfadabhängigkeiten](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Xvfb-Framebuffer-Dateien

`Xvfb -fbdir <directory>` verwendet Memory-Mapped-Dateien mit den Namen `Xvfb_screen<n>` für seine virtuellen Bildschirme. Wenn ein laufender Xvfb-Prozess eines anderen Benutzers ein Verzeichnis angibt, dessen Bildschirmdateien für den aktuellen Benutzer lesbar sind, kann der Framebuffer Inhalte vom Desktop dieses Benutzers offenlegen. Bestätigen Sie Prozess-, Dateieigentümer- und Berechtigungsinformationen gemeinsam; eine lesbare Datei allein beweist nicht, dass der Bildschirm nützliche Inhalte enthält. Prüfen Sie zunächst Pfade und Metadaten, ohne Bilddaten in gemeinsam genutzte Enumeration-Ausgaben zu kopieren. Das [Xvfb-Handbuch](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) dokumentiert das Verhalten von `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
