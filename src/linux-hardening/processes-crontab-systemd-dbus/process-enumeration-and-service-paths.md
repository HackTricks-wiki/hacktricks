# Prozessaufzählung und Dienstpfade

{{#include ../../banners/hacktricks-training.md}}

Die entscheidende Frage ist, welcher privilegierte Prozess Daten oder Code verarbeitet, die ein Benutzer mit geringeren Privilegien beeinflussen kann. Untersuche den Prozessbaum, die aktuelle Umgebung, geöffnete Dateien sowie die Unit oder das Skript, mit dem jeder infrage kommende Prozess gestartet wurde.

## Prozesse und Eigentümer ermitteln

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Eine benutzerübergreifende Eltern-Kind-Beziehung kann normal sein, aber ein unerwarteter Übergang sollte Anlass sein, den Elternbefehl, die Argumente, die ausführbare Datei, das Arbeitsverzeichnis und referenzierte Dateien zu überprüfen. Nutze [Benutzer und Sitzungen](../user-information/user-and-session-triage.md), um den Eigentümer und den Anmeldekontext einzuordnen.

### Konsolen lokaler virtueller Maschinen

Überprüfe die `-spice`-Optionen eines QEMU-Prozesses zusammen mit seiner Listening-Adresse. Die [QEMU-Dokumentation](https://www.qemu.org/docs/master/system/qemu-manpage.html) besagt, dass `disable-ticketing` SPICE-Clients erlaubt, sich ohne Authentifizierung zu verbinden. Auch ein an Loopback gebundener Listener kann für andere lokale Host-Benutzer erreichbar sein. Prüfe den aktiven Listener, die Authentifizierungsoptionen und den lokalen Zugriff, bevor du die Befehlszeile als offengelegte Konsole einstufst. Die Konsolensteuerung betrifft den **Gast**; um ein Gastkonto zu erhalten oder dessen Bootstatus zu ändern, sind separate Bedingungen innerhalb des Gasts erforderlich. Dadurch erhält man keinen Root-Zugriff auf dem Virtualisierungshost. Lies Prozessargumente und Socket-Metadaten, ohne während der passiven Aufzählung eine Verbindung zum Gast herzustellen oder ihn neu zu starten.

Eine lokal erreichbare Weboberfläche kann Code mit dem Dienstkonto ausführen, auch wenn die erste Shell nicht auf die Dateien dieses Kontos zugreifen kann. CVE-2023-0297 betraf beispielsweise pyLoads Verarbeitung von `/flash/addcrypted2`, wenn nicht vertrauenswürdiges JavaScript mit aktivierten Python-Imports zu Js2Py gelangte; der [Upstream-Fix](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deaktivierte `pyimport`. Gleiche den Eigentümer des laufenden Prozesses, die Listening-Adresse, die Erreichbarkeit des Endpunkts und den installierten Patch oder Backport des Anbieters ab, bevor du einen pyLoad-Prozess als möglichen Eskalationspfad einstufst. Ein Prozessname, ein offener Port oder eine Paketversion allein beweist keine Verwundbarkeit; bei der passiven Aufzählung sollte kein Payload zur Codeausführung gesendet werden.

### Privilegierte Login-Shells mit gemeinsamem Terminal

Eine privilegierte interaktive Shell, die `su --login <user>` ohne unabhängiges Pseudo-Terminal ausführt, kann ihr Terminal mit der Login-Shell des weniger privilegierten Benutzers teilen. Wenn die Startdatei dieses Benutzers kontrollierbar ist und darin ausgeführter Code `TIOCSTI` zum Einschleusen von Terminaleingaben verwenden kann, können die Eingaben die privilegierte Shell erreichen, sobald diese fortgesetzt wird. Das [Handbuch zu `su` aus util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) beschreibt das Risiko gemeinsam genutzter Terminals und empfiehlt für interaktive Nutzung `su --pty`/`-P`; `su -c` startet eine separate Sitzung ohne steuerndes Terminal. Das Risiko hängt von der tatsächlichen Eltern-Shell, der Terminalbeziehung, der Startdatei des Zielbenutzers und den Kernel-Richtlinien ab. Ein Prozessname oder das Argument `su -l` allein ist lediglich ein Ansatzpunkt für weitere Prüfungen.

Untersuche den beobachteten Prozessbaum und die TTY-Spalten, dann den lesbaren Starter sowie Eigentümer und Berechtigungen der Startdatei. Unter Linux kann `/proc/sys/dev/tty/legacy_tiocsti`, sofern vorhanden, bei der Einordnung der Richtlinie helfen; das Fehlen dieser Datei ist kein Sicherheitsnachweis. Das [Linux-Handbuch zu `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) weist darauf hin, dass die Operation seit Linux 6.2 möglicherweise `CAP_SYS_ADMIN` erfordert, wenn dieser Sysctl auf „false“ gesetzt ist. Rufe das ioctl nicht auf, nur um den Host aufzuzählen.

Ein Datenbankkonto kann die Startdatei des Zielbenutzers manchmal ändern, ohne direkten Schreibzugriff auf das Dateisystem zu haben. PostgreSQL-seitiges `COPY ... TO 'filename'` schreibt als das Betriebssystemkonto des Datenbankservers. [PostgreSQL beschränkt](https://www.postgresql.org/docs/current/sql-copy.html) diese Dateivariante jedoch auf Datenbank-Superuser oder Rollen wie `pg_write_server_files`. Prüfe sowohl die Datenbankrolle als auch die Dateiberechtigungen des Serverbetriebssystems; eine Verbindungszeichenfolge der Anwendung gewährt allein keine Schreibberechtigung für Dateien. Berücksichtige beim Bewerten der Angriffskette die Fähigkeiten des privilegierten Starters und des Datenbankkontos getrennt.

## Laufzeit-Artefakte untersuchen

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Gelöschte ausführbare Dateien und gelöschte, aber noch geöffnete Dateien bleiben referenziert, bis ihr letzter Deskriptor geschlossen wird. Sie können Beweismaterial oder zugängliche Geheimnisse bewahren. Prozessumgebungen und Arbeitsspeicher können Zugangsdaten enthalten, doch das Auslesen eines anderen Prozesses wird durch Eigentumsverhältnisse, `/proc`-Einhängeoptionen, die Yama-`ptrace`-Richtlinie und weitere Sicherheitskontrollen eingeschränkt. Weitere verwandte Techniken finden Sie unter [Dateideskriptoren](../main-system-information/filesystem-links-and-file-descriptors.md) und [Suche nach Zugangsdaten nach der Ausnutzung](../post-exploitation/README.md).

Gespeicherte `syscall`-Traces bilden eine weitere Grenze für Dateiberechtigungen. [`strace` zeichnet `syscall`-Argumente in eine Ausgabedatei auf](https://man7.org/linux/man-pages/man1/strace.1.html), daher kann ein lesbarer Trace von [`execve`-Argumenten](https://man7.org/linux/man-pages/man2/execve.2.html) ein Passwort offenlegen, das ein privilegierter Job in seiner Befehlszeile übergeben hat. Stellen Sie zunächst fest, ob der aktuelle Benutzer den konkreten Trace lesen kann und ob das Argument tatsächlich Zugangsdaten enthält; ein späterer Wechsel zu einem Unix-Konto erfordert einen separaten Nachweis, dass die Zugangsdaten dort akzeptiert werden. Dateimetadaten sind ein nützlicher passiver Hinweis, ohne bei der routinemäßigen Enumeration jeden Trace zu durchsuchen oder dessen Inhalt auszugeben.

## Privilegierte Office-Automatisierungs-Sockets

LibreOffice und OpenOffice können ihre UNO-API über ein Argument der Form `--accept=socket,host=<host>,port=<port>;urp;` bereitstellen. Ein Office-Prozess im Besitz von root mit einem erreichbaren Endpunkt kann es einem lokalen Benutzer mit geringeren Privilegien ermöglichen, API-Dienste im Sicherheitskontext dieses Prozesses aufzurufen. Der Dienst `SystemShellExecute` bietet eine Funktion zum Starten eines Systembefehls. Eine Bindung an die Loopback-Schnittstelle beschränkt zwar die Erreichbarkeit aus der Ferne, lässt den Socket aber weiterhin für lokale Benutzer erreichbar, sofern keine andere Kontrolle den Zugriff verhindert.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Ordne den Prozesseigentümer, das exakte Argument `--accept` sowie die aktuelle Listening-Adresse und den Port einander zu. Ein konfigurierter Acceptor, der nicht an eine Adresse gebunden werden konnte, ist lediglich ein Hinweis; stelle während der passiven Enumeration keine Verbindung zur API her und rufe sie nicht auf. Starte nicht eigens eine privilegierte Office-Instanz, um diesen Zustand zu testen.

## Von privilegierten Prozessen verwendeter System-V-Shared-Memory

Ein Hilfsprogramm mit Root-Rechten kann ein System-V-Shared-Memory-Segment erstellen, in das ein anderer Benutzer schreiben kann. Wenn das Hilfsprogramm später Daten aus diesem Segment in einem Shell-Befehl oder einem anderen sensiblen Vorgang verwendet, überschreitet das Segment eine Privilegiengrenze, selbst wenn die ausführbare Datei und ihre Dateien geschützt sind. `shmget()` übernimmt die Zugriffsberechtigungen aus den unteren neun Bits seiner Flags; der Modus `0666` erlaubt anderen Benutzern das Schreiben, während ein `IPC_CREAT`-Flag diese Berechtigungen nicht einschränkt. Untersuche aktive Segmente passiv mit `ipcs -m` und vergleiche deren Eigentümer, Modus und Lebensdauer mit dem privilegierten Prozess und dessen Eingabeverarbeitung. Ein weltweit beschreibbares Segment allein belegt keine Befehlsausführung.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

System-V-Segmente unterscheiden sich von POSIX-Dateien für Shared Memory unter `/dev/shm`. Ein nur kurzzeitig erstelltes Segment ist möglicherweise in einer einzelnen `ipcs`-Momentaufnahme nicht vorhanden. Eine leere Ausgabe schließt daher nicht aus, dass ein Hilfsprogramm Shared Memory verwendet. Überprüfe den Quellcode oder das Verhalten der Binärdatei sowie alle `sudo`-Regeln, die sie starten. Rufe das privilegierte Hilfsprogramm nicht nur deshalb auf, damit bei der Auflistung ein Segment erscheint. Der [IPC-Namespace-Leitfaden](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) erklärt, wie Namespaces die Sichtbarkeit beeinflussen.<sup>[[2]](#references)[[3]](#references)</sup>

## Consul agent script checks

Consul kann Script-Health-Checks mit der Betriebssystemidentität seines Agents ausführen. Wenn ein Agent als root läuft, `enable_script_checks` aktiviert ist und ein Benutzer mit geringeren Privilegien über die lokale HTTP-API einen Service mit einem Script-Check registrieren darf, kann dieser Benutzer möglicherweise Befehle mit root-Rechten ausführen lassen. Die Bindung der API ausschließlich an `127.0.0.1` verhindert nicht, dass lokale Benutzer darauf zugreifen. Die Einstellung `enable_local_script_checks` ist restriktiver: Sie schließt Script-Checks aus, die über HTTP-API-Registrierungen übermittelt werden. Wenn Consul-ACLs aktiviert sind, erfordert die Service-Registrierung `service:write`; eine Zeile mit `acl.default_policy=allow` allein beweist nicht, dass ein anonymer Aufrufer einen Service registrieren kann. Überprüfe gemeinsam die tatsächliche Agent-Identität, die geladenen Einstellungen, die API-Bindung und die Autorisierung.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Folgen Sie den Argumenten `-config-dir` und `-config-file` des laufenden Agents bis zur relevanten Konfiguration und prüfen Sie nur die Feldnamen und Einstellungen für Script-Checks und ACLs. Konfigurationsdateien können auch Gossip-Schlüssel oder Tokens enthalten; vermeiden Sie es, diese in gemeinsam genutzte Logs einzufügen. Registrieren Sie keinen Service und führen Sie keinen Health-Check aus, nur um diesen Sachverhalt zu ermitteln.

Ein separater lokaler Dateipfad besteht, wenn ein Benutzer mit geringeren Rechten **Schreib- und Suchrechte** für das Verzeichnis hat, das durch `-config-dir` eines als root laufenden Agents angegeben wird: Eine neue `.hcl`- oder `.json`-Servicedefinition kann aus diesem Verzeichnis geladen werden. Such- und Schreibrechte für ein Verzeichnis können das Hinzufügen einer Datei ermöglichen, selbst wenn das Auflisten des Verzeichnisses untersagt ist. Um die Ausführung von Befehlen als root zu bestätigen, prüfen Sie, ob der Agent dieses Verzeichnis tatsächlich lädt, ob die **effektive** Script-Check-Einstellung lokale Definitionen zulässt, ob die Definition geladen wird und ob der Agent seine root-Rechte behält. [Consul documents](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) welche Einstellungen und Health-Check-Definitionen neu geladen werden können; das Aktivieren von Script-Checks erfordert möglicherweise einen Neustart. Prüfen Sie daher das Verhalten der installierten Version. Wenn ACLs den Agent schützen, [`consul reload` requires `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); eine KV-Schreibberechtigung allein reicht dafür nicht aus. Betrachten Sie beschreibbare Verzeichnismetadaten als Anlass zur Überprüfung, nicht als Beleg für einen autorisierten Reload, Neustart oder eine Befehlsausführung. Prüfen Sie Pfade, Berechtigungen und Richtlinien, ohne Konfiguration zu schreiben oder die API aufzurufen.

## Der Service-Ausführungskette folgen

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Prüfe die Unit, Drop-ins, `EnvironmentFile=`, Hilfsskripte, relative Befehle, beschreibbare Verzeichnisse und Socket-Aktivierung. Auch eine root-eigene Unit kann unsicher sein, wenn sie eine benutzerbeschreibbare Konfiguration oder ein solches Skript einliest. Die Seite zu [arbitrary file write](../interesting-files-permissions/write-to-root.md) behandelt gängige Missbrauchswege bei Diensten und Units. Überwache kurzlebige Jobs mit [pspy](https://github.com/DominicBreuker/pspy) oder Audit-/Prozess-Telemetrie, wenn eine einmalige `ps`-Auflistung sie nicht erfasst.

Bei einem benutzerdefinierten **xinetd**-Dienst solltest du den aktivierten Abschnitt `server`, `user` und die Zugriffskontrollen mit dem aktiven Listener und der genauen ausführbaren Datei abgleichen. Die Einstellung [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) legt die Identität des gestarteten Prozesses fest, während ein set-user-ID-Bit auf der ausführbaren Datei dessen effektive Identität separat ändern kann, sofern [`execve` diesen Übergang erlaubt](https://man7.org/linux/man-pages/man2/execve.2.html). Eine erreichbare privilegierte Binärdatei, die nicht vertrauenswürdige Eingaben akzeptiert, sollte offline anhand des Quellcodes oder Disassemblats auf Speicherfehler geprüft werden, etwa eine unbegrenzte [`scanf`-String-Konvertierung](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) in einen festen Puffer. Dienstzuordnung und set-user-ID-Metadaten sind Hinweise, kein Beweis für einen solchen Fehler. Sende bei der passiven Enumeration keine Eingaben, die Abstürze auslösen, und debugge den aktiven privilegierten Dienst nicht.

Bei einem benutzerdefinierten privilegierten Listener mit lesbarem Quellcode solltest du jede vom Aufrufer kontrollierte Länge prüfen, die bei einer Kopieroperation wie [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html) verwendet wird. Nur zu prüfen, ob der aktuelle Schreibindex innerhalb eines festen Puffers liegt, belegt nicht, dass die **Kopierlänge** in den verbleibenden Platz passt. Verifiziere `copy_length <= capacity - index`, nachdem du bestätigt hast, dass der Index im gültigen Bereich liegt, und prüfe Vorzeichen sowie arithmetischen Überlauf. Dies ist nur dann ein Prüfhinweis, wenn die Eingabe diese Operation erreicht, der Listener für den weniger privilegierten Benutzer zugänglich ist und der Prozess eine höhere effektive Identität behält. Untersuche Quellcode und Prozessmetadaten offline; sende während der Enumeration keine Eingaben, die den aktiven Dienst zum Absturz bringen.

Auf Systemen mit **Upstart** können System-Jobdefinitionen unter `/etc/init/*.conf` liegen. Eine für den aktuellen Benutzer beschreibbare Jobdatei ist relevant, wenn der aktive Init-Daemon genau diesen Job lädt, dessen `script`- oder `exec`-Abschnitt mit einer höher privilegierten Identität ausgeführt wird und der Benutzer ihn über einen erlaubten `initctl`-Befehl oder einen anderen tatsächlichen Auslöser starten kann. Eine sudo-Freigabe für `initctl` allein beweist weder, dass eine Jobdatei beschreibbar ist, noch, dass ein geänderter Job ausgeführt wird. Prüfe die Berechtigungen der genauen Jobdatei, die effektive Ausführungsidentität, den aktiven Daemon und den Auslöser, ohne den Job während der Enumeration zu bearbeiten oder zu starten. Siehe die Handbücher zur [Upstart-Jobkonfiguration](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) und zu [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Eine lesbare Autologin-Passwortdatei, etwa `/etc/autologin/passwd` auf Systemen, deren [Boot-Job genau diesen Pfad einliest](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), ist ein Hinweis auf mögliche Offenlegung von Zugangsdaten. Bestätige, dass der Boot-Job installiert ist und die Datei verwendet, und prüfe anschließend separat, ob das Passwort für ein anderes lokales Konto oder einen Dienst gültig ist. Der Dateiname allein belegt keine Wiederverwendung des Passworts. Dokumentiere Pfad und Zugriffsmetadaten, ohne das Passwort in gemeinsam genutzte Enumerationsausgaben aufzunehmen.

`ExecStart=` einer Unit oder ein geplanter Befehl kann den genauen Pfad eines Skripts in einem nicht auflistbaren Verzeichnis offenlegen. Die [Suchberechtigung für Verzeichnisse](https://man7.org/linux/man-pages/man7/path_resolution.7.html) kann der aktuellen Identität weiterhin erlauben, diesen bekannten Pfad zu durchlaufen. Prüfe den Suchzugriff auf jedem übergeordneten Verzeichnis und die Leseberechtigung für die Datei, statt anzunehmen, dass ein fehlgeschlagenes Auflisten des Verzeichnisses sie schützt. Ein lesbares Skript kann Zugangsdaten für eine Übertragung enthalten; ein Wechsel zu einem anderen Konto setzt jedoch voraus, dass diese Zugangsdaten weiterhin gültig sind und dort unabhängig akzeptiert werden. Dokumentiere den Pfad und die Berechtigungsnachweise, ohne Geheimnisse in gemeinsam genutzte Logs auszugeben.

Prüfe bei einem geplanten CommonJS-Node.js-Skript auch Bare Imports wie `require('package')`, selbst wenn das Skript selbst schreibgeschützt ist. [Node sucht `node_modules` neben der importierenden Datei und anschließend in deren übergeordneten Verzeichnissen](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), bevor es auf konfigurierte globale Pfade zurückgreift. Ein weniger privilegierter Benutzer, der eines dieser übergeordneten Verzeichnisse **beschreiben und durchsuchen** kann, kann möglicherweise ein Paket anlegen, das früher in der Suche gefunden wird. Bestätige, dass der genaue Import erreicht wird, das ausgewählte Paket kein eingebautes Modul ist, der relevante Pfad angelegt oder geändert werden kann, das Modul dort in der installierten Laufzeit aufgelöst wird und ein höher privilegierter Job es bei einem zukünftigen Aufruf laden wird. Beschreibbare Metadaten eines übergeordneten Verzeichnisses sind lediglich ein Prüfhinweis. Untersuche Skript und Scheduler passiv, ohne ein Modul abzulegen oder den Job auszulösen.

Ein privater Python-Paketindex ist eine weitere Vertrauensgrenze, wenn ein automatisierter Job Pakete unter einer anderen Betriebssystemidentität installiert. Gleiche den genauen Job und das Ausführungskonto mit dem konfigurierten Index, den ausgewählten Paketnamen und der Frage ab, ob ein weniger privilegierter Benutzer ein Paket veröffentlichen oder ersetzen kann, das der Job tatsächlich installieren wird. Beim Erstellen einer Source Distribution können deren Build-Backend oder das veraltete `setup.py` unter der Identität des Installierenden ausgeführt werden; der Import des installierten Pakets ist ein separater Ausführungspfad. Ein Index-Listener, ein lesbarer Hash eines Upload-Passworts oder ein Paketdateiname allein belegt diese Kette nicht. Prüfe Job, Indexberechtigungen und Paketprovenienz, ohne während der Enumeration etwas hochzuladen oder zu installieren. Siehe die [Build-System-Schnittstelle von pip](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Ein privilegierter Agent kann eine von einem separaten Webdienst oder Container verwaltete Aufgabenwarteschlange abfragen. Wenn eine Identität mit geringerem Vertrauensniveau in die Aufgabendatenbank des Dienstes schreiben kann, stelle fest, ob diese Einträge dem Agenten tatsächlich bereitgestellt werden und ob eine Befehlsaufgabe mit der Betriebssystemidentität des Agenten ausgeführt wird. Bestätige Datenbank-Schreibzugriff, Zielsitzung oder Routing-Schlüssel, aktives Polling, Aufgabenautorisierung und effektiven Benutzer des Agenten jeweils separat. Root innerhalb eines Containers bedeutet nicht automatisch Host-Root-Zugriff. Die Grenze wird nur überschritten, wenn ein auf dem Host privilegierter Verbraucher angreiferkontrollierte Aufgabendaten ausführt. Untersuche Prozess-, Datenbankdatei- und Dienstmetadaten, ohne die Warteschlange zu ändern oder während der Enumeration eine Aufgabe zu senden.

Ein wiederkehrender Job kann stattdessen einen Befehl aus einer Konfigurationszeile in einer Anwendungsdatenbank einlesen. Bestätige, dass die Datenbankrolle mit geringeren Rechten genau diese Zeile ändern kann, dass der aktive Job sie nach der Änderung einliest und dass der Wert unter einer höher privilegierten Betriebssystemidentität an eine Shell oder einen entsprechenden Befehlsausführer gelangt. Datenbank-Schreibzugriff oder ein wie ein Befehl aussehender Wert belegen allein keine Ausführung. Untersuche den Job und die Berechtigungen, ohne die Zeile während der passiven Enumeration zu ändern.

Eine Nachricht in einer Warteschlange kann statt Code auch eine URL enthalten. Wenn ein privilegierter Verbraucher diese URL abruft und die Antwort als Lua- oder anderes ausführbares Plugin lädt, überprüfe die Veröffentlichungsberechtigung für den genauen Exchange und Routing-Key, die Bindung an die konsumierte Warteschlange, den Abruf- und Plugin-Ladepfad sowie die effektive Identität des Workers. [RabbitMQ leitet veröffentlichte Nachrichten über Exchanges weiter](https://www.rabbitmq.com/docs/exchanges). Ein Broker-Listener oder gültiger Login allein belegt nicht, dass die Nachricht diesen Worker erreicht. Abgefangene Klartext-Zugangsdaten für den Broker sind ein separater Hinweis, der tatsächlichen Zugriff auf eine Paketaufzeichnung und lesbaren Datenverkehr voraussetzt; sie belegen keine Veröffentlichungsberechtigung. Ein Lua-Plugin kann Shell-Befehle über [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) ausführen, aber nur, wenn diese API in seiner Laufzeit verfügbar ist. Untersuche Konfiguration und Code, ohne während der passiven Enumeration Datenverkehr aufzuzeichnen, Nachrichten zu veröffentlichen oder ein Plugin abzurufen.

Wenn ein privilegierter Python-Dienst einen lokalen HTTP- oder Socket-Endpunkt bereitstellt, kann ein lesbares Skript einen Pfad von Eingaben zu ausführbarem Code offenlegen, auch wenn seine Dateiberechtigungen Änderungen verhindern. Gleiche den aktiven Prozess und die Unit-Identität mit dem genauen Skript, Listener, der Routenautorisierung und den vom Aufrufer kontrollierten Feldern ab. Verfolge diese Felder anschließend durch Parsing und Validierung bis zu einem dynamischen `eval()`- oder `exec()`-Sink. Insbesondere kann das Erstellen eines neuen f-Strings aus Request-Text und dessen Auswertung vom Angreifer gelieferte Ersetzungsfelder als Python-Ausdrücke interpretieren (Warnung zu [Python `eval`](https://docs.python.org/3/library/functions.html#eval); [f-String-Semantik](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Ein bloßer Treffer auf `eval` oder eine Bindung an Loopback beweist nicht, dass ein nicht vertrauenswürdiger Aufrufer den Sink erreicht. Untersuche den tatsächlichen Datenfluss und die Zugriffskontrollen, ohne während der Enumeration eine Test-Payload zu senden.

Eine Schranke für signierte Requests auf dieser Route sollte separat geprüft werden. Wenn lesbarer Quellcode den Signaturschlüssel nachweislich aus einem sehr kleinen oder vorhersagbaren Ausgaberaum ableitet und der Dienst ein gültiges signiertes Beispiel bereitstellt, schützt die Signatur einen privilegierten `eval()`-Sink möglicherweise nicht mehr. Verifiziere die genaue Schlüsselableitung und den Prüfer, die Identität des aktiven Dienstes und den Zugriff lokaler Aufrufer sowie, ob das signierte Feld den Sink erreicht. Ein Import von Pythons [`random`-Modul](https://docs.python.org/3/library/random.html) oder eine Beispielsignatur allein belegt keine dieser Bedingungen. Python warnt außerdem, dass das Einschränken von `__builtins__` [keine Sicherheitsgrenze für nicht vertrauenswürdige `eval()`-Eingaben darstellt](https://docs.python.org/3/library/functions.html#eval). Analysiere Schlüssel offline und übermittle bei der passiven Enumeration keine gefälschten Requests.

Ein leeres, aber beschreibbares Verzeichnis `/etc/systemd/system/<unit>.service.d` ist relevant, auch wenn die Unit-Datei und alle vorhandenen Drop-ins geschützt sind: Der Benutzer kann möglicherweise eine neue `.conf`-Override-Datei erstellen. Prüfe, ob das Verzeichnis für die aktuelle Identität beschreibbar und durchsuchbar ist, ob die Unit geladen ist und als root läuft und ob ein Daemon-Reload mit anschließendem Neustart stattfinden wird. Eine Reload- oder Neustartberechtigung, ein Timer oder ein späterer Systemstart kann die Änderung wirksam machen; alleiniger Schreibzugriff auf das Verzeichnis führt sie nicht sofort aus.

Verfolge bei laufenden Diensten die wörtlichen Pfade von `EnvironmentFile=` aus dem Abschnitt `[Service]` der Unit, auch wenn die Dateinamen nicht mit `.env` beginnen. Wenn ein Benutzer mit geringen Rechten eine Datei lesen kann, liste schlüsselartige Namen wie `API_TOKEN` oder `APP_SECRET_KEY` auf, ohne die Werte in gemeinsam genutzte Logs auszugeben. Berücksichtige bei der Beurteilung der effektiven Unit Drop-in-Overrides und optionale `-`-Präfixe. Lesbarkeit ist ein Hinweis auf mögliche Offenlegung von Zugangsdaten; für eine Privilegienausweitung muss der Wert bei einer privilegierten Aktion weiterhin gültig sein.

### Privilegierte Verarbeitung nicht vertrauenswürdiger Uploads

Ein als root laufender Datei-Watcher kann Dateien aus einem benutzerbeschreibbaren Upload-Verzeichnis an einen kurzlebigen Parser oder Entpacker übergeben. Verfolge das übergeordnete Skript oder den Dienst des laufenden Watchers und bestätige das genaue Verzeichnis, wer dort Dateien ablegen kann, den untergeordneten Befehl samt Argumenten und die Identität, unter der der Unterprozess läuft. Eine Prozessaufnahme kann den Watcher zeigen, aber den Entpacker zwischen Uploads verpassen. Lege während der passiven Enumeration keine Test-Payload ab und löse den Watcher nicht aus.

Ein konkretes Beispiel ist der Extraktionsmodus von Binwalk (`-e`), der angreiferkontrollierte PFS-Daten verarbeitet. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) ermöglichte es dem PFS-Extractor, außerhalb des vorgesehenen Verzeichnisses zu schreiben, unter anderem in einen Plugin-Pfad, den Binwalk später laden konnte. Upstream wurde die Korrektur in [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4) aufgenommen; Distributionen können jedoch Backports enthalten, sodass eine ältere Version angezeigt wird. Prüfe daher vor der Bewertung der Anwendbarkeit den Sicherheitsstatus des installierten Pakets, etwa im [Debian-Tracker](https://security-tracker.debian.org/tracker/CVE-2022-4510). Eine installierte Binwalk-Version allein belegt keinen Pfad zur Privilegienausweitung: Die Extraktion muss tatsächlich von einem privilegierteren Prozess für Eingaben aufgerufen werden, die der weniger privilegierte Benutzer kontrollieren kann.

### Geplante Builds mit lokalen Abhängigkeiten

Ein geplantes `cargo run` kompiliert den Quellcode erneut als Benutzer, unter dem der Job ausgeführt wird. Prüfe die lokalen `{ path = "..." }`-Abhängigkeiten im Manifest sowie Quellcode- und Verzeichnisberechtigungen jeder Abhängigkeit, nicht nur die des Haupt-Crates. Wenn ein weniger privilegierter Benutzer eine Abhängigkeit ändern kann, die Cargo kompiliert, und der geplante Job das Ergebnis ausführt, kann der kompilierte Code als dieser Ausführungsbenutzer laufen. Bestätige den effektiven Scheduler-Befehl, das Arbeitsverzeichnis, die Auflösung der Abhängigkeiten und ob ein Neubuild stattfindet. Eine beschreibbare Rust-Quelldatei an anderer Stelle ist lediglich ein Hinweis. Für eine passive Erstprüfung genügen das Lesen des Manifests und der Pfadmetadaten. Siehe die [Cargo-Dokumentation zu Pfadabhängigkeiten](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Xvfb-Framebuffer-Dateien

`Xvfb -fbdir <directory>` verwendet Memory-Mapped-Dateien mit dem Namen `Xvfb_screen<n>` für seine virtuellen Bildschirme. Wenn ein laufender Xvfb-Prozess eines anderen Benutzers ein Verzeichnis angibt, dessen Bildschirmdateien für den aktuellen Benutzer lesbar sind, kann der Framebuffer Desktop-Inhalte dieses Benutzers offenlegen. Bestätige Prozess, Dateieigentümer und Berechtigungen gemeinsam. Eine lesbare Datei allein beweist nicht, dass sich nützliche Inhalte auf dem Bildschirm befinden. Prüfe zunächst Pfade und Metadaten, ohne Bilddaten in gemeinsam genutzte Enumerationsausgaben zu kopieren. Das [Xvfb-Handbuch](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) dokumentiert das Verhalten von `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
