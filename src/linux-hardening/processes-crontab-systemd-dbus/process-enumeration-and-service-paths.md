# Énumération des processus et chemins des services

{{#include ../../banners/hacktricks-training.md}}

La question utile est de savoir quel processus privilégié consomme des données ou du code qu’un utilisateur moins privilégié peut influencer. Inspectez l’arborescence des processus, l’environnement en cours, les fichiers ouverts, ainsi que l’unité ou le script qui a lancé chaque candidat.

## Cartographier les processus et leur propriétaire

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Une relation parent-enfant entre utilisateurs différents peut être normale, mais une transition inattendue justifie d’examiner la commande parente, ses arguments, l’exécutable, le répertoire de travail et les fichiers référencés. Utilisez [users and sessions](../user-information/user-and-session-triage.md) pour interpréter le propriétaire et le contexte de connexion.

### Consoles de machines virtuelles locales

Examinez les options `-spice` d’un processus QEMU ainsi que son adresse d’écoute. [La documentation de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) indique que `disable-ticketing` permet aux clients SPICE de se connecter sans authentification. Même lié à l’interface loopback, un écouteur peut être accessible aux autres utilisateurs de l’hôte local. Vérifiez l’écouteur actif, les options d’authentification et les accès locaux avant de considérer la ligne de commande comme une console exposée. Le contrôle de la console agit sur le **guest** ; obtenir un compte sur le guest ou modifier son état de démarrage nécessite des conditions distinctes côté guest et ne confère pas les droits root sur l’hôte de virtualisation. Lors d’une énumération passive, lisez les arguments du processus et les métadonnées du socket sans vous connecter au guest ni le redémarrer.

Une interface web accessible localement peut exécuter du code avec le compte de service, même si le premier shell ne peut pas accéder aux fichiers de ce compte. Par exemple, CVE-2023-0297 concernait le traitement de `/flash/addcrypted2` par pyLoad lorsque du JavaScript non fiable était transmis à Js2Py avec les imports Python activés ; le [correctif en amont](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) a désactivé `pyimport`. Recoupez le propriétaire du processus actif, l’adresse d’écoute, l’exposition du point de terminaison et le correctif installé ou rétroporté par le fournisseur avant de considérer un processus pyLoad comme une voie d’escalade. Un nom de processus, un port ouvert ou une version de paquet ne suffisent pas, à eux seuls, à prouver une exposition ; une énumération passive ne doit pas envoyer de payload d’exécution.

### Shells de connexion privilégiés partageant un terminal

Un shell interactif privilégié qui exécute `su --login <user>` sans pseudo-terminal indépendant peut laisser son terminal partagé avec le shell de connexion moins privilégié. Si le fichier de démarrage de cet utilisateur est modifiable et que le code qu’il contient peut utiliser `TIOCSTI` pour injecter des entrées dans le terminal, celles-ci peuvent atteindre le shell privilégié lorsque celui-ci reprend. [Le manuel de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) décrit le risque lié au terminal partagé et recommande `su --pty`/`-P` pour une utilisation interactive ; `su -c` démarre une session distincte sans terminal de contrôle. Ce risque dépend du shell parent réel, de la relation entre les terminaux, du fichier de démarrage cible et de la politique du noyau. Le seul nom d’un processus ou l’argument `su -l` ne constitue qu’un indice à examiner.

Examinez l’arborescence des processus observée et les colonnes TTY, puis le lanceur lisible et le propriétaire/les permissions du fichier de démarrage. Sous Linux, `/proc/sys/dev/tty/legacy_tiocsti` peut aider à interpréter la politique lorsqu’il est présent ; son absence ne prouve pas que le système est sûr. [Le manuel Linux de `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) indique que depuis Linux 6.2, l’opération peut nécessiter `CAP_SYS_ADMIN` lorsque ce sysctl est à false. N’invoquez pas l’ioctl dans le seul but d’énumérer l’hôte.

Un compte de base de données peut parfois modifier le fichier de démarrage de l’utilisateur cible sans accès direct en écriture au système de fichiers. La commande PostgreSQL côté serveur `COPY ... TO 'filename'` écrit en tant que compte OS du serveur de base de données, mais [les restrictions de PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) limitent cette forme à des superutilisateurs de la base de données ou à des rôles tels que `pg_write_server_files`. Vérifiez à la fois le rôle de la base de données et les permissions de fichiers du serveur OS ; une chaîne de connexion d’application ne confère pas, à elle seule, le droit d’écrire des fichiers. Lors de l’évaluation de la chaîne, distinguez les capacités du lanceur privilégié de celles du compte de base de données.

## Examiner les artefacts d’exécution

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Les exécutables supprimés et les fichiers supprimés mais encore ouverts restent référencés jusqu’à la fermeture de leur dernier descripteur. Ils peuvent préserver des preuves ou des secrets accessibles. Les environnements et la mémoire des processus peuvent contenir des identifiants, mais la lecture d’un autre processus est soumise à des restrictions liées au propriétaire, aux options de montage de `/proc`, à la politique Yama ptrace et à d’autres contrôles de sécurité. Consultez les [descripteurs de fichiers](../main-system-information/filesystem-links-and-file-descriptors.md) et la [recherche d’identifiants après exploitation](../post-exploitation/README.md) pour des techniques connexes.

Les traces de syscall enregistrées constituent une autre limite liée aux permissions des fichiers. [`strace` enregistre les arguments des syscall dans un fichier de sortie](https://man7.org/linux/man-pages/man1/strace.1.html), de sorte qu’une trace lisible de [`execve` arguments](https://man7.org/linux/man-pages/man2/execve.2.html) peut révéler un mot de passe transmis sur la ligne de commande par une tâche privilégiée. Vérifiez d’abord que l’utilisateur actuel peut lire la trace concernée et que l’argument contient réellement un identifiant ; une transition ultérieure vers un autre compte Unix nécessite une preuve distincte que l’identifiant y est accepté. Les métadonnées des fichiers constituent une piste passive utile, sans qu’il soit nécessaire de parcourir chaque trace ni d’en afficher le contenu lors d’une énumération de routine.

## Sockets d’automatisation bureautique privilégiés

LibreOffice et OpenOffice peuvent exposer leur API UNO via un argument `--accept=socket,host=<host>,port=<port>;urp;`. Un processus bureautique appartenant à root doté d’un point de terminaison accessible peut permettre à un utilisateur local moins privilégié d’invoquer des services API dans le contexte de sécurité de ce processus. Le service `SystemShellExecute` inclut une opération permettant de lancer une commande système. Une liaison à l’interface loopback limite l’accessibilité à distance, mais laisse le socket accessible aux utilisateurs locaux, sauf si un autre contrôle en empêche l’accès.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Corrélez le propriétaire du processus, l’argument exact `--accept` et l’adresse et le port actuellement en écoute. Un acceptor configuré qui n’a pas réussi à se lier à une adresse est seulement une piste ; ne vous connectez pas à l’API et ne l’invoquez pas pendant l’énumération passive. Évitez de démarrer une instance bureautique privilégiée uniquement pour tester cette condition.

## Mémoire partagée System V utilisée par des processus privilégiés

Un helper appartenant à root peut créer un segment de mémoire partagée System V dans lequel un autre utilisateur peut écrire. Si le helper fait ensuite confiance aux données de ce segment dans une commande shell ou lors d’une autre opération sensible, le segment franchit une frontière de privilèges, même si l’exécutable et ses fichiers sont protégés. `shmget()` récupère les permissions d’accès depuis les neuf bits de poids faible de ses flags ; le mode `0666` permet aux autres utilisateurs d’écrire, tandis qu’un flag `IPC_CREAT` ne restreint pas ces permissions. Inspectez passivement les segments actifs avec `ipcs -m` et corrélez leur propriétaire, leur mode et leur durée de vie avec le processus privilégié et le traitement de ses entrées. Un segment accessible en écriture à tous ne suffit pas, à lui seul, à établir une exécution de commandes.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Les segments System V sont distincts des fichiers de mémoire partagée POSIX sous `/dev/shm`. Un segment créé pendant un très court instant peut être absent d’un instantané `ipcs` unique ; une sortie vide ne suffit donc pas à écarter l’hypothèse d’un helper qui utilise la mémoire partagée. Examinez son code source ou son comportement binaire, ainsi que toute règle `sudo` qui le lance ; n’exécutez pas le helper privilégié juste pour faire apparaître un segment lors de l’énumération. Le [guide des espaces de noms IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explique comment les espaces de noms affectent la visibilité.<sup>[[2]](#references)[[3]](#references)</sup>

## Vérifications de script de l’agent Consul

Consul peut exécuter des vérifications d’intégrité par script avec l’identité système de son agent. Si un agent s’exécute en tant que root, active `enable_script_checks` et autorise un utilisateur moins privilégié à enregistrer un service avec une vérification par script via l’API HTTP locale, cet utilisateur peut provoquer l’exécution de commandes par root. Le fait de lier l’API uniquement à `127.0.0.1` permet toujours aux utilisateurs locaux d’y accéder. Le paramètre `enable_local_script_checks` est plus restrictif : il exclut les vérifications par script soumises via des enregistrements de l’API HTTP. Lorsque les ACL Consul sont activées, l’enregistrement d’un service nécessite `service:write` ; une ligne `acl.default_policy=allow` ne prouve pas à elle seule qu’un appelant anonyme peut effectuer un enregistrement. Examinez conjointement l’identité réelle de l’agent, les paramètres chargés, la liaison de l’API et les autorisations.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Suivez les arguments `-config-dir` et `-config-file` de l’agent en cours d’exécution jusqu’aux fichiers de configuration concernés, puis examinez uniquement les noms et paramètres des champs relatifs aux script-checks et aux ACL. Les fichiers de configuration peuvent également contenir des clés ou des tokens gossip ; évitez de les coller dans des journaux partagés. N’enregistrez pas de service et ne lancez pas de health check uniquement pour énumérer cette situation.

Il existe aussi un chemin d’accès par fichier local lorsqu’un utilisateur disposant de privilèges inférieurs peut **écrire dans le répertoire** indiqué par l’argument `-config-dir` d’un agent exécuté en tant que root et **le parcourir** : une nouvelle définition de service `.hcl` ou `.json` peut être chargée depuis ce répertoire. Les droits de parcours et d’écriture sur le répertoire peuvent permettre d’y ajouter un fichier même si son contenu ne peut pas être listé. Pour exécuter des commandes en tant que root, confirmez que l’agent charge effectivement ce répertoire, que son paramètre effectif de script-check autorise les définitions locales, que la définition est chargée et que l’agent conserve ses privilèges root. [Consul documents](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) quels paramètres et définitions de health check peuvent être rechargés ; l’activation des script-checks peut elle-même nécessiter un redémarrage, vérifiez donc le comportement de la version installée. Lorsque des ACL protègent l’agent, [`consul reload` requires `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent) ; un droit d’écriture KV ne suffit pas. Considérez les métadonnées d’un répertoire accessible en écriture comme un indice à examiner, et non comme une preuve qu’un rechargement autorisé, un redémarrage ou une exécution de commande est possible. Examinez les chemins, les permissions et les politiques sans écrire de configuration ni appeler l’API.

## Suivre la chaîne d’exécution du service

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Vérifiez l'unité, les drop-ins, `EnvironmentFile=`, les scripts auxiliaires, les commandes relatives, les répertoires inscriptibles et l'activation par socket. Une unité appartenant à root peut tout de même être dangereuse si elle lit un fichier de configuration ou un script modifiable par un utilisateur. La page sur l'[écriture arbitraire de fichiers](../interesting-files-permissions/write-to-root.md) couvre les vecteurs d'abus courants liés aux services et aux unités. Surveillez les tâches de courte durée avec [pspy](https://github.com/DominicBreuker/pspy) ou avec la télémétrie d'audit/des processus lorsqu'une seule liste `ps` ne suffit pas à les repérer.

Pour un service **xinetd** personnalisé, mettez en corrélation les directives `server`, `user` et les contrôles d'accès du bloc activé avec le listener actif et l'exécutable exact. Le [paramètre `user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) définit l'identité du processus lancé, tandis qu'un bit set-user-ID sur l'exécutable peut modifier séparément son identité effective si [`execve` autorise cette transition](https://man7.org/linux/man-pages/man2/execve.2.html). Un binaire privilégié accessible qui accepte des entrées non fiables mérite une analyse hors ligne du code source ou du désassemblage afin de rechercher des bugs de sécurité mémoire, comme une conversion de chaîne [`scanf` non bornée](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) vers un tampon de taille fixe. La correspondance avec le service et les métadonnées set-user-ID sont des pistes, pas la preuve d'un tel bug ; n'envoyez pas d'entrées provoquant un crash et ne déboguez pas le service privilégié en cours d'exécution lors d'une énumération passive.

Pour un listener privilégié personnalisé dont le code source est lisible, examinez chaque longueur contrôlée par l'appelant utilisée par une opération de copie telle que [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Vérifier uniquement que l'index d'écriture courant se trouve dans les limites d'un tampon fixe ne prouve pas que la **longueur de copie** tient dans l'espace restant ; vérifiez `copy_length <= capacity - index` après avoir confirmé que l'index est dans les limites, et vérifiez les signes et les débordements arithmétiques. Cette piste d'analyse n'est pertinente que si l'entrée atteint cette opération, si le listener est accessible à l'utilisateur moins privilégié et si le processus conserve une identité effective supérieure. Examinez le code source et les métadonnées du processus hors ligne ; n'envoyez pas d'entrées provoquant un crash au service actif pendant l'énumération.

Sur les systèmes utilisant **Upstart**, les définitions des jobs système peuvent se trouver sous `/etc/init/*.conf`. Un fichier de job modifiable par l'utilisateur courant est pertinent lorsque le démon init actif charge ce fichier précis, que son bloc `script` ou `exec` s'exécute sous une identité plus privilégiée et que l'utilisateur peut le démarrer via une commande `initctl` autorisée ou un autre déclencheur réel. Une autorisation sudo pour `initctl` ne prouve pas à elle seule qu'un fichier de job est modifiable ni qu'un job modifié sera exécuté. Vérifiez les permissions du fichier de job exact, le paramètre d'exécution effectif, le démon actif et le déclencheur, sans modifier ni démarrer le job pendant l'énumération. Consultez les manuels de [configuration des jobs Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) et d'[ `initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un fichier de mot de passe d'autologin lisible, tel que `/etc/autologin/passwd` sur les systèmes dont le [job de démarrage lit précisément ce chemin](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), constitue une piste d'exposition d'identifiants. Confirmez que le job de démarrage est installé et utilise le fichier, puis vérifiez séparément si le mot de passe est valide pour un autre compte ou service local. Le nom du fichier ne prouve pas à lui seul la réutilisation du mot de passe ; consignez le chemin et les métadonnées d'accès sans inscrire le mot de passe dans les résultats d'énumération partagés.

Le `ExecStart=` d'une unité ou une commande planifiée peut révéler le chemin exact d'un script situé dans un répertoire non listable. Le [droit de recherche dans un répertoire](https://man7.org/linux/man-pages/man7/path_resolution.7.html) peut tout de même permettre à l'identité courante de parcourir ce chemin connu ; vérifiez le droit de recherche sur chaque répertoire parent et le droit de lecture sur le fichier, au lieu de supposer qu'un échec de listage du répertoire le protège. Un script lisible peut contenir un identifiant de transfert, mais l'accès à un autre compte exige que cet identifiant soit toujours valide et accepté indépendamment par ce compte. Consignez le chemin et les preuves liées aux permissions sans afficher de valeurs secrètes dans les journaux partagés.

Pour un script CommonJS Node.js planifié, examinez les imports nus tels que `require('package')`, même si le script lui-même est en lecture seule. [Node recherche `node_modules` à côté du fichier qui importe le module, puis dans ses répertoires parents](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), avant de se rabattre sur les chemins globaux configurés. Un utilisateur moins privilégié qui peut **écrire dans l'un de ces répertoires parents et y effectuer une recherche** peut être en mesure d'y créer un package prioritaire. Confirmez que l'import exact est atteint, que le package sélectionné n'est pas un module intégré, que le chemin concerné peut être créé ou modifié, que le module s'y résout dans l'environnement d'exécution installé et qu'un job plus privilégié le chargera lors d'une prochaine exécution. Les métadonnées d'un répertoire parent inscriptible ne sont qu'un indice à examiner ; inspectez le script et le planificateur passivement, sans déposer de module ni déclencher le job.

Un index privé de packages Python constitue une autre frontière de confiance lorsqu'un job automatisé installe des packages sous une identité OS différente. Mettez en corrélation le job exact et le compte d'exécution avec l'index configuré, les noms des packages sélectionnés et la possibilité pour un utilisateur moins privilégié de publier ou remplacer un package que le job installera effectivement. La création d'une distribution source peut exécuter son backend de build ou son ancien `setup.py` sous l'identité de l'installateur ; l'importation du package installé est un chemin d'exécution distinct. Un listener d'index, un hash de mot de passe de téléversement lisible ou un nom de fichier de package ne suffit pas à établir cette chaîne. Examinez le job, les autorisations de l'index et la provenance du package sans téléverser ni installer quoi que ce soit pendant l'énumération. Consultez [l'interface de build-system de pip](https://pip.pypa.io/en/stable/reference/build-system/) et les [recommandations d'installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agent privilégié peut interroger une file de tâches gérée par un service web ou un conteneur distinct. Si une identité de confiance inférieure peut écrire dans la base de données des tâches du service, déterminez si ces lignes sont effectivement transmises à cet agent et si une tâche de commande s'exécute avec l'identité OS de l'agent. Vérifiez séparément l'accès en écriture à la base de données, la session cible ou la clé de routage, l'interrogation active, l'autorisation des tâches et l'utilisateur effectif de l'agent. Être root dans un conteneur n'implique pas à lui seul un accès root à l'hôte ; la frontière n'est franchie que si un consommateur privilégié sur l'hôte exécute des données de tâche contrôlées par un attaquant. Examinez les métadonnées du processus, du fichier de base de données et du service sans modifier la file ni envoyer de tâche pendant l'énumération.

Un job récurrent peut plutôt lire une commande depuis une ligne de configuration d'une base de données applicative. Confirmez que le rôle de base de données moins privilégié peut modifier cette ligne précise, que le job actif la lit après la modification et que la valeur parvient à un shell ou à un exécuteur de commandes équivalent sous une identité OS supérieure. L'accès en écriture à la base de données ou une valeur ressemblant à une commande ne prouve pas à lui seul qu'elle sera exécutée ; examinez le job et les permissions sans modifier la ligne pendant l'énumération passive.

Un message mis en file d'attente peut également contenir une URL plutôt que du code. Si un consommateur privilégié récupère cette URL et charge la réponse comme plugin Lua ou autre plugin exécutable, vérifiez les droits de publication sur l'exchange et la clé de routage exacts, le binding vers la file consommée, le chemin de récupération et de chargement du plugin, ainsi que l'identité effective du worker. [RabbitMQ achemine les messages publiés via des exchanges](https://www.rabbitmq.com/docs/exchanges) ; un listener du broker ou un identifiant de connexion valide ne prouve pas à lui seul que le message sera livré à ce worker. Des identifiants de broker en clair capturés constituent une piste distincte qui exige un véritable accès à la capture de paquets et à du trafic lisible ; ils ne prouvent pas l'autorisation de publication. Un plugin Lua ne peut invoquer des commandes shell via [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) que si cette API est disponible dans son environnement d'exécution. Examinez la configuration et le code sans capturer de trafic, publier de messages ni récupérer de plugin pendant l'énumération passive.

Lorsqu'un service Python privilégié expose un endpoint HTTP ou socket local, un script lisible peut révéler un chemin entre une entrée et du code, même si ses permissions empêchent sa modification. Mettez en corrélation le processus actif et l'identité de l'unité avec le script exact, le listener, l'autorisation de la route et les champs contrôlés par l'appelant. Suivez ensuite ces champs à travers l'analyse et la validation jusqu'à un point d'exécution dynamique `eval()` ou `exec()`. En particulier, construire une nouvelle f-string à partir du texte d'une requête et l'évaluer peut interpréter les champs de remplacement fournis par un attaquant comme des expressions Python ([avertissement de Python concernant `eval`](https://docs.python.org/3/library/functions.html#eval) ; [sémantique des f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). La simple présence de `eval` ou une liaison à loopback ne prouve pas qu'un appelant non fiable atteint le point d'exécution ; examinez le flux réel des données et les contrôles d'accès sans envoyer de charge de test pendant l'énumération.

Un mécanisme de vérification de requête signée sur cette route mérite une analyse distincte. Si le code source lisible montre que la clé de signature est dérivée d'un espace de sortie manifestement restreint ou prévisible et que le service expose un exemple signé valide, la signature peut ne plus protéger un point d'exécution privilégié `eval()`. Vérifiez la dérivation exacte de la clé et le vérificateur, l'identité du service actif et l'accès des appelants locaux, ainsi que le fait que le champ signé atteint le point d'exécution ; la présence d'un import du module Python [`random`](https://docs.python.org/3/library/random.html) ou d'une signature d'exemple ne prouve aucune de ces conditions. Python avertit également que restreindre `__builtins__` [ne constitue pas une frontière de sécurité pour une entrée `eval()` non fiable](https://docs.python.org/3/library/functions.html#eval). Analysez la clé hors ligne et ne soumettez pas de requêtes falsifiées pendant l'énumération passive.

Un répertoire `/etc/systemd/system/<unit>.service.d` vide mais inscriptible est important même si le fichier d'unité et tous les drop-ins existants sont protégés : l'utilisateur peut créer un nouveau fichier de surcharge `.conf`. Vérifiez que le répertoire est inscriptible et accessible en recherche par l'identité courante, que l'unité est chargée et s'exécute en tant que root, et qu'un rechargement du démon suivi d'un redémarrage aura lieu. Une autorisation de rechargement ou de redémarrage, un timer ou un démarrage ultérieur peut rendre la modification effective ; le seul droit d'écriture dans le répertoire ne l'exécute pas immédiatement.

Pour les services en cours d'exécution, suivez les chemins littéraux `EnvironmentFile=` de la section `[Service]` de l'unité, y compris les fichiers dont le nom ne commence pas par `.env`. Si un utilisateur peu privilégié peut en lire un, relevez les noms de clés ressemblant à des identifiants, tels que `API_TOKEN` ou `APP_SECRET_KEY`, sans afficher leurs valeurs dans les journaux partagés. Vérifiez les surcharges drop-in et les préfixes `-` facultatifs lors de l'évaluation de l'unité effective. Le fait qu'un fichier soit lisible constitue une piste d'exposition d'identifiants ; la valeur doit toujours être valide pour une action privilégiée afin de permettre une élévation de privilèges.

### Traitement privilégié des fichiers téléversés non fiables

Un observateur de fichiers exécuté en tant que root peut transmettre des fichiers d'un répertoire de téléversement inscriptible par un utilisateur à un analyseur ou extracteur de courte durée. Suivez le script parent ou le service de l'observateur en cours d'exécution et confirmez le répertoire exact, les personnes autorisées à y déposer des fichiers, la commande enfant et ses arguments, ainsi que l'identité sous laquelle l'enfant s'exécute. Un instantané des processus peut montrer l'observateur sans repérer l'extracteur entre deux téléversements. Ne déposez pas de charge de test et ne déclenchez pas l'observateur pendant l'énumération passive.

Un exemple concret est le mode d'extraction de Binwalk (`-e`) qui traite des données PFS contrôlées par un attaquant. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permettait à l'extracteur PFS d'écrire hors du répertoire prévu, notamment dans un chemin de plugin que Binwalk pouvait charger ultérieurement. Le correctif a été intégré en amont dans [la version 2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), mais des rétroportages par les distributions peuvent conserver une version affichée plus ancienne ; vérifiez le statut de sécurité du package installé, par exemple dans le [tracker Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), avant de juger si le problème s'applique. La seule présence d'une version de Binwalk installée ne prouve pas l'existence d'un chemin d'élévation de privilèges : l'extraction doit effectivement être invoquée par un processus plus privilégié sur une entrée contrôlable par l'utilisateur moins privilégié.

### Builds planifiés avec des dépendances locales

Un `cargo run` planifié recompile le code source en tant qu'utilisateur d'exécution du job. Examinez les dépendances locales `{ path = "..." }` du manifeste ainsi que les permissions du code source et des répertoires parents de chaque dépendance, et pas seulement celles du crate principal. Si un utilisateur moins privilégié peut modifier une dépendance compilée par Cargo et que le job planifié exécute le résultat, le code compilé peut s'exécuter en tant que cet utilisateur d'exécution. Confirmez la commande effective du planificateur, le répertoire de travail, la résolution des dépendances et si une recompilation aura lieu ; un fichier source Rust inscriptible ailleurs n'est qu'une piste. La lecture du manifeste et des métadonnées des chemins suffit pour un triage passif. Consultez la [documentation Cargo sur les dépendances par chemin](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Fichiers framebuffer Xvfb

`Xvfb -fbdir <directory>` utilise des fichiers mappés en mémoire nommés `Xvfb_screen<n>` pour ses écrans virtuels. Si le processus Xvfb actif d'un autre utilisateur indique un répertoire dont les fichiers d'écran sont lisibles par l'utilisateur courant, le framebuffer peut exposer le contenu du bureau de cet utilisateur. Confirmez ensemble le processus, le propriétaire des fichiers et leurs permissions ; un fichier lisible ne prouve pas à lui seul que son écran contient des informations utiles. Commencez par examiner les chemins et les métadonnées, sans copier de données d'image dans les résultats d'énumération partagés. Le [manuel de Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) décrit le fonctionnement de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
