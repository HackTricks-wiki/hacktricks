# Énumération des processus et chemins des services

{{#include ../../banners/hacktricks-training.md}}

La question utile est de savoir quel processus privilégié consomme des données ou du code qu’un utilisateur moins privilégié peut influencer. Examinez l’arbre des processus, l’environnement en direct, les fichiers ouverts, ainsi que l’unité ou le script qui a lancé chaque candidat.

## Cartographier les processus et leur propriétaire

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Une relation parent-enfant entre utilisateurs différents peut être normale, mais une transition inattendue justifie d'examiner la commande parente, ses arguments, l'exécutable, le répertoire de travail et les fichiers référencés. Consultez [users and sessions](../user-information/user-and-session-triage.md) pour interpréter le propriétaire et le contexte de connexion.

### Consoles de machines virtuelles locales

Examinez les options `-spice` d'un processus QEMU en parallèle de son adresse d'écoute. [La documentation de QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) précise que `disable-ticketing` permet aux clients SPICE de se connecter sans authentification. Un listener lié à l'interface loopback peut tout de même être accessible à d'autres utilisateurs locaux de l'hôte. Vérifiez le listener actif, les options d'authentification et l'accès local avant de considérer la ligne de commande comme une console exposée. Le contrôle de la console affecte le **guest** ; obtenir un compte guest ou modifier son état de démarrage nécessite des conditions distinctes côté guest et ne confère pas les privilèges root sur l'hôte de virtualisation. Lors de l'énumération passive, lisez les arguments du processus et les métadonnées des sockets sans vous connecter au guest ni le redémarrer.

Une interface web accessible localement peut exécuter du code avec le compte de son service, même si le shell initial ne peut pas accéder aux fichiers de ce compte. Par exemple, CVE-2023-0297 affectait le traitement de `/flash/addcrypted2` par pyLoad lorsque du JavaScript non fiable était transmis à Js2Py avec les imports Python activés ; le [correctif upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) a désactivé `pyimport`. Recoupez le propriétaire du processus en cours, l'adresse d'écoute, l'exposition de l'endpoint et le correctif installé ou rétroporté par le fournisseur avant de considérer un processus pyLoad comme une voie d'escalade. Un nom de processus, un port ouvert ou une version de paquet ne suffit pas à prouver l'exposition ; l'énumération passive ne doit pas envoyer de payload d'exécution.

### Shells de connexion privilégiés partageant un terminal

Un shell interactif privilégié qui exécute `su --login <user>` sans pseudo-terminal indépendant peut laisser son terminal partagé avec le shell de connexion moins privilégié. Si le fichier de démarrage de cet utilisateur est modifiable et que le code qu'il contient peut utiliser `TIOCSTI` pour injecter des entrées dans le terminal, celles-ci peuvent atteindre le shell privilégié lorsque celui-ci reprend son exécution. [Le manuel de `su` de util-linux](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) décrit le risque lié au terminal partagé et recommande `su --pty`/`-P` pour une utilisation interactive ; `su -c` démarre une session distincte sans terminal de contrôle. Le risque dépend du shell parent réel, de la relation entre les terminaux, du fichier de démarrage ciblé et de la politique du noyau. Un nom de processus ou un argument `su -l` ne constitue qu'un indice à examiner.

Examinez l'arborescence des processus observée et les colonnes TTY, puis le lanceur lisible ainsi que le propriétaire et les permissions du fichier de démarrage. Sous Linux, `/proc/sys/dev/tty/legacy_tiocsti` peut aider à interpréter la politique lorsqu'il est présent ; son absence ne prouve pas que la configuration est sûre. [Le manuel Linux de `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) indique que depuis Linux 6.2, cette opération peut nécessiter `CAP_SYS_ADMIN` lorsque ce sysctl est désactivé. N'invoquez pas cet ioctl dans le seul but d'énumérer l'hôte.

Un compte de base de données peut parfois modifier le fichier de démarrage de l'utilisateur ciblé sans disposer d'un accès direct en écriture au système de fichiers. La commande côté serveur PostgreSQL `COPY ... TO 'filename'` écrit en tant que compte OS du serveur de base de données, mais [les restrictions de PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) réservent cette forme de fichier aux superutilisateurs de la base de données ou aux rôles tels que `pg_write_server_files`. Vérifiez à la fois le rôle de la base de données et les permissions sur les fichiers du système d'exploitation du serveur ; une chaîne de connexion d'application ne confère pas à elle seule le droit d'écrire des fichiers. Évaluez séparément les capacités du lanceur privilégié et celles du compte de base de données lors de l'analyse de la chaîne.

## Inspecter les artefacts d'exécution

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Les exécutables supprimés et les fichiers supprimés mais toujours ouverts restent référencés jusqu’à la fermeture de leur dernier descripteur. Ils peuvent préserver des preuves ou des secrets accessibles. Les environnements et la mémoire des processus peuvent contenir des identifiants, mais la lecture d’un autre processus est limitée par la propriété, les options de montage de `/proc`, la politique ptrace de Yama et d’autres contrôles de sécurité. Consultez [file descriptors](../main-system-information/filesystem-links-and-file-descriptors.md) et [post-exploitation credential hunting](../post-exploitation/README.md) pour découvrir des techniques connexes.

Les traces de syscall enregistrées constituent une autre limite liée aux permissions des fichiers. [`strace` enregistre les arguments des syscall dans un fichier de sortie](https://man7.org/linux/man-pages/man1/strace.1.html), donc une trace lisible de [`execve` arguments](https://man7.org/linux/man-pages/man2/execve.2.html) peut révéler un mot de passe transmis en ligne de commande par un job privilégié. Vérifiez d’abord que l’utilisateur actuel peut lire la trace concernée et que l’argument contient bien un identifiant ; il faut des preuves distinctes pour établir ensuite que cet identifiant est accepté lors d’une transition vers un autre compte Unix. Les métadonnées des fichiers constituent une piste passive utile, sans qu’il soit nécessaire de parcourir toutes les traces ni d’en afficher le contenu lors d’une énumération de routine.

## Sockets d’automatisation bureautique privilégiés

LibreOffice et OpenOffice peuvent exposer leur API UNO via un argument `--accept=socket,host=<host>,port=<port>;urp;`. Un processus bureautique appartenant à root et doté d’un endpoint accessible peut permettre à un utilisateur local moins privilégié d’invoquer des services API dans le contexte de sécurité de ce processus. Le service `SystemShellExecute` inclut une opération permettant de lancer une commande système. Une liaison à l’interface loopback limite l’accessibilité à distance, mais le socket reste accessible aux utilisateurs locaux, sauf si un autre contrôle en empêche l’accès.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Corrélez le propriétaire du processus, l’argument exact `--accept` et l’adresse et le port actuellement en écoute. Un accepteur configuré qui n’a pas réussi à se lier à une adresse n’est qu’une piste ; ne vous connectez pas à l’API et ne l’invoquez pas pendant l’énumération passive. Évitez de démarrer une instance bureautique privilégiée dans le seul but de tester cette condition.

## Mémoire partagée System V utilisée par des processus privilégiés

Un utilitaire appartenant à root peut créer un segment de mémoire partagée System V dans lequel un autre utilisateur peut écrire. Si l’utilitaire fait ensuite confiance aux données de ce segment dans une commande shell ou une autre opération sensible, le segment franchit une frontière de privilèges, même si l’exécutable et ses fichiers sont protégés. `shmget()` tire les permissions d’accès des neuf bits de poids faible de ses indicateurs ; le mode `0666` permet aux autres utilisateurs d’écrire, tandis qu’un indicateur `IPC_CREAT` ne restreint pas ces permissions. Examinez passivement les segments actifs avec `ipcs -m` et corrélez leur propriétaire, leur mode et leur durée de vie avec le processus privilégié et la manière dont il traite ses entrées. Un segment accessible en écriture à tous ne suffit pas à établir qu’une exécution de commandes est possible.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Les segments System V sont distincts des fichiers de mémoire partagée POSIX dans `/dev/shm`. Un segment créé pendant un bref instant peut être absent d’un instantané unique de `ipcs` ; une sortie vide n’exclut donc pas la présence d’un utilitaire qui utilise la mémoire partagée. Examinez son code source ou le comportement de son binaire, ainsi que toute règle `sudo` qui le lance ; n’exécutez pas l’utilitaire privilégié simplement pour faire apparaître un segment pendant l’énumération. Le [guide des espaces de noms IPC](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) explique comment les espaces de noms affectent la visibilité.<sup>[[2]](#references)[[3]](#references)</sup>

## Vérifications de santé par script de l’agent Consul

Consul peut exécuter des vérifications de santé par script avec l’identité système de son agent. Si un agent s’exécute en tant que root, active `enable_script_checks` et autorise un utilisateur aux privilèges moindres à enregistrer un service avec une vérification par script via l’API HTTP locale, cet utilisateur peut déclencher des commandes exécutées en tant que root. Limiter l’écoute de l’API à `127.0.0.1` permet toujours aux utilisateurs locaux d’y accéder. Le paramètre `enable_local_script_checks` est plus restrictif : il exclut les vérifications par script soumises via les enregistrements de l’API HTTP. Lorsque les ACL Consul sont activées, l’enregistrement d’un service requiert `service:write` ; une ligne `acl.default_policy=allow` ne prouve pas à elle seule qu’un appelant anonyme peut effectuer un enregistrement. Examinez conjointement l’identité réelle de l’agent, les paramètres chargés, l’adresse d’écoute de l’API et les autorisations.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Suivez les arguments `-config-dir` et `-config-file` de l’agent en cours d’exécution jusqu’à la configuration concernée, puis examinez uniquement les noms et paramètres des champs de script-check et d’ACL. Les fichiers de configuration peuvent également contenir des clés ou des tokens gossip ; évitez de les copier dans des journaux partagés. N’enregistrez pas de service et ne lancez pas de contrôle de santé dans le seul but d’énumérer cette situation.

Il existe un chemin distinct passant par un fichier local lorsqu’un utilisateur aux privilèges inférieurs peut **écrire dans le répertoire** indiqué par `-config-dir` d’un agent exécuté en tant que root et y **rechercher** des fichiers : une nouvelle définition de service `.hcl` ou `.json` peut être chargée depuis ce répertoire. Les droits de recherche et d’écriture sur le répertoire peuvent permettre d’y ajouter un fichier même si l’affichage de son contenu est interdit. Pour une exécution de commandes en tant que root, confirmez que l’agent charge effectivement ce répertoire, que son paramètre effectif de script-check autorise les définitions locales, que la définition est chargée et que l’agent conserve ses privilèges root. [Consul documente](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) les paramètres et définitions de contrôle de santé qui peuvent être rechargés ; l’activation des script checks peut elle-même nécessiter un redémarrage. Vérifiez donc le comportement de la version installée. Lorsque des ACL protègent l’agent, [`consul reload` nécessite `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent) ; une autorisation d’écriture KV ne l’accorde pas. Considérez les métadonnées d’un répertoire accessible en écriture comme un indice à examiner, et non comme la preuve d’un rechargement, d’un redémarrage ou d’une exécution de commande autorisés. Examinez les chemins, les permissions et la politique sans écrire de configuration ni appeler l’API.

## Suivre la chaîne d’exécution du service

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Vérifiez l’unité, les drop-ins, `EnvironmentFile=`, les scripts auxiliaires, les commandes relatives, les répertoires inscriptibles et l’activation par socket. Une unité appartenant à root peut quand même être dangereuse si elle lit un fichier de configuration ou un script modifiable par un utilisateur. La page [arbitrary file write](../interesting-files-permissions/write-to-root.md) couvre les voies courantes d’abus des services et des unités. Surveillez les tâches de courte durée avec [pspy](https://github.com/DominicBreuker/pspy) ou la télémétrie d’audit et de processus lorsqu’une seule liste `ps` ne suffit pas à les repérer.

Pour un service **xinetd** personnalisé, mettez en corrélation les paramètres `server`, `user` et les contrôles d’accès de la stanza activée avec le listener actif et l’exécutable exact. Le [paramètre `user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) définit l’identité du processus lancé, tandis qu’un bit set-user-ID sur l’exécutable peut modifier séparément son identité effective si [`execve` autorise cette transition](https://man7.org/linux/man-pages/man2/execve.2.html). Un binaire privilégié accessible qui accepte des entrées non fiables mérite une analyse hors ligne du code source ou du désassemblage pour repérer des bugs de sécurité mémoire, comme une [conversion de chaîne `scanf` non bornée](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) dans un tampon de taille fixe. La configuration du service et les métadonnées set-user-ID sont des pistes, pas une preuve de bug ; n’envoyez pas d’entrées provoquant un crash et ne déboguez pas le service privilégié actif pendant l’énumération passive.

Pour un listener privilégié personnalisé dont le code source est lisible, examinez chaque longueur contrôlée par l’appelant utilisée par une opération de copie telle que [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Vérifier uniquement que l’index d’écriture actuel se trouve dans les limites d’un tampon fixe ne prouve pas que la **longueur de copie** tient dans l’espace restant ; vérifiez `copy_length <= capacity - index` après avoir confirmé que l’index est dans les limites, et vérifiez le signe et les débordements arithmétiques. Cette piste d’analyse n’est pertinente que si l’entrée atteint cette opération, si le listener est accessible à l’utilisateur moins privilégié et si le processus conserve une identité effective supérieure. Examinez le code source et les métadonnées du processus hors ligne ; n’envoyez pas d’entrées provoquant un crash au service actif pendant l’énumération.

Sur les systèmes utilisant **Upstart**, les définitions des tâches système peuvent se trouver sous `/etc/init/*.conf`. Un fichier de tâche modifiable par l’utilisateur actuel est important lorsque le démon init actif charge précisément cette tâche, que sa stanza `script` ou `exec` s’exécute avec une identité plus privilégiée et que l’utilisateur peut la lancer via une commande `initctl` autorisée ou un autre déclencheur réel. Une autorisation sudo pour `initctl` ne prouve pas à elle seule qu’un fichier de tâche est modifiable ni qu’une tâche modifiée sera exécutée. Vérifiez les permissions du fichier de tâche exact, le paramètre d’exécution effectif, le démon actif et le déclencheur sans modifier ni lancer la tâche pendant l’énumération. Consultez les manuels de [configuration des tâches Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) et d’[`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Un fichier de mot de passe d’autologin lisible, tel que `/etc/autologin/passwd` sur les systèmes dont la [tâche de démarrage lit précisément ce chemin](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), constitue une piste d’exposition d’identifiants. Confirmez que la tâche de démarrage est installée et utilise ce fichier, puis vérifiez séparément si le mot de passe est valide pour un autre compte ou service local. Le nom du fichier ne prouve pas à lui seul la réutilisation du mot de passe ; consignez le chemin et les métadonnées d’accès sans inclure le mot de passe dans les sorties d’énumération partagées.

Le `ExecStart=` d’une unité ou une commande planifiée peut révéler le chemin exact d’un script situé dans un répertoire dont le contenu ne peut pas être listé. L’[autorisation de recherche dans un répertoire](https://man7.org/linux/man-pages/man7/path_resolution.7.html) peut quand même permettre à l’identité actuelle de parcourir ce chemin connu ; vérifiez l’autorisation de recherche sur chaque répertoire parent et l’autorisation de lecture sur le fichier au lieu de supposer qu’un échec de listage du répertoire le protège. Un script lisible peut contenir un identifiant de transfert, mais l’accès à un autre compte nécessite que cet identifiant soit encore valide et accepté indépendamment par ce compte. Consignez le chemin et les éléments attestant les permissions sans afficher de valeurs secrètes dans les journaux partagés.

Pour un script Node.js CommonJS planifié, examinez les imports nus comme `require('package')`, même si le script lui-même est en lecture seule. [Node recherche `node_modules` à côté du fichier qui effectue l’import, puis dans ses répertoires parents](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), avant de se rabattre sur les chemins globaux configurés. Un utilisateur moins privilégié pouvant **écrire dans l’un de ces répertoires parents et le parcourir** pourrait créer un package correspondant en priorité. Confirmez que l’import exact est atteint, que le package sélectionné n’est pas un module intégré, que le chemin concerné peut être créé ou modifié, que le module s’y résout dans l’environnement d’exécution installé et qu’une tâche plus privilégiée le chargera lors d’une prochaine exécution. Les métadonnées d’un répertoire parent modifiable ne sont qu’un indice à examiner ; inspectez le script et le planificateur passivement, sans déposer de module ni déclencher la tâche.

Un index de packages Python privé constitue une autre frontière de confiance lorsqu’une tâche automatisée installe des packages sous une identité OS différente. Mettez en corrélation la tâche exacte et son compte d’exécution avec l’index configuré, les noms des packages sélectionnés et la possibilité pour un utilisateur moins privilégié de publier ou de remplacer un package que la tâche installera effectivement. La création d’une distribution source peut exécuter son backend de build ou son ancien `setup.py` sous l’identité de l’installateur ; l’importation du package installé est une voie d’exécution distincte. Un listener d’index, un hash de mot de passe de téléversement lisible ou un nom de fichier de package ne suffisent pas à établir cette chaîne. Examinez la tâche, les autorisations de l’index et la provenance du package sans rien téléverser ni installer pendant l’énumération. Consultez les pages [interface de build de pip](https://pip.pypa.io/en/stable/reference/build-system/) et [recommandations d’installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Un agent privilégié peut interroger une file de tâches gérée par un service web ou un conteneur distinct. Si une identité moins fiable peut écrire dans la base de données des tâches du service, déterminez si ces lignes sont effectivement servies à cet agent et si une tâche de commande s’exécute avec l’identité OS de l’agent. Confirmez séparément l’accès en écriture à la base de données, la session cible ou la clé de routage, l’interrogation active, l’autorisation des tâches et l’utilisateur effectif de l’agent. Être root dans un conteneur n’implique pas en soi un accès root à l’hôte ; la frontière n’est franchie que si un consommateur privilégié sur l’hôte exécute des données de tâche contrôlées par un attaquant. Examinez les métadonnées des processus, du fichier de base de données et du service sans modifier la file ni y envoyer de tâche pendant l’énumération.

Une tâche récurrente peut plutôt lire une commande depuis une ligne de configuration d’une base de données applicative. Confirmez que le rôle de base de données moins privilégié peut modifier cette ligne précise, que la tâche active la lit après la modification et que la valeur parvient à un shell ou à un exécuteur de commandes équivalent sous une identité OS plus privilégiée. L’accès en écriture à la base de données ou une valeur ressemblant à une commande ne prouve pas à lui seul qu’il y aura exécution ; examinez la tâche et les permissions sans modifier la ligne pendant l’énumération passive.

Un message en file d’attente peut également contenir une URL plutôt que du code. Si un consommateur privilégié récupère cette URL et charge la réponse comme plugin Lua ou autre plugin exécutable, vérifiez les autorisations de publication sur l’échange et la clé de routage exacts, la liaison avec la file consommée, le chemin de récupération et de chargement du plugin, ainsi que l’identité effective du worker. [RabbitMQ achemine les messages publiés par l’intermédiaire des échanges](https://www.rabbitmq.com/docs/exchanges) ; un listener du broker ou un identifiant de connexion valide ne suffit pas à établir que le message sera livré à ce worker. Des identifiants broker en clair capturés constituent une piste distincte qui nécessite un accès réel à la capture de paquets et à du trafic lisible ; ils ne prouvent pas l’autorisation de publication. Un plugin Lua ne peut invoquer des commandes shell via [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) que si cette API est disponible dans son environnement d’exécution. Examinez la configuration et le code sans capturer de trafic, publier de messages ni récupérer de plugin pendant l’énumération passive.

Lorsqu’un service Python privilégié expose un endpoint HTTP local ou un socket, un script lisible peut révéler un chemin d’une entrée vers du code, même si ses permissions empêchent toute modification. Mettez en corrélation le processus actif et l’identité de l’unité avec le script exact, le listener, l’autorisation de la route et les champs contrôlés par l’appelant. Suivez ensuite ces champs à travers l’analyse et la validation jusqu’à un point d’exécution dynamique `eval()` ou `exec()`. En particulier, construire une nouvelle f-string à partir du texte de la requête puis l’évaluer peut interpréter les champs de substitution fournis par un attaquant comme des expressions Python ([avertissement de Python sur `eval`](https://docs.python.org/3/library/functions.html#eval) ; [sémantique des f-strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). La présence d’une correspondance `eval` ou une liaison à loopback ne prouve pas qu’un appelant non fiable atteint ce point d’exécution ; examinez le flux de données réel et les contrôles d’accès sans envoyer de charge de test pendant l’énumération.

Un mécanisme de validation des requêtes signées sur cette route nécessite une analyse distincte. Si le code source lisible dérive la clé de signature à partir d’un espace de sortie dont la taille est manifestement petite ou prévisible, et que le service expose un exemple signé valide, la signature peut ne plus protéger un point d’exécution privilégié `eval()`. Vérifiez la dérivation exacte de la clé et le vérificateur, l’identité du service actif et l’accès des appelants locaux, ainsi que la présence du champ signé à l’entrée du point d’exécution ; un import du module Python [`random`](https://docs.python.org/3/library/random.html) ou un exemple de signature ne prouve aucune de ces conditions. Python avertit également que restreindre `__builtins__` ne constitue [pas une frontière de sécurité pour une entrée non fiable passée à `eval()`](https://docs.python.org/3/library/functions.html#eval). Analysez la clé hors ligne et n’envoyez pas de requêtes falsifiées pendant l’énumération passive.

Un répertoire `/etc/systemd/system/<unit>.service.d` vide mais modifiable est important même si le fichier de l’unité et tous les drop-ins existants sont protégés : l’utilisateur peut créer un nouveau fichier de surcharge `.conf`. Vérifiez que le répertoire est modifiable et parcourable par l’identité actuelle, que l’unité est chargée et s’exécute en tant que root, et si un rechargement du démon suivi d’un redémarrage aura lieu. Une autorisation de rechargement ou de redémarrage, un timer ou un démarrage ultérieur peut rendre la modification effective ; l’accès en écriture au répertoire ne l’exécute pas immédiatement.

Pour les services en cours d’exécution, suivez les chemins littéraux `EnvironmentFile=` de la section `[Service]` de l’unité, y compris les fichiers dont le nom ne commence pas par `.env`. Si un utilisateur peu privilégié peut en lire un, relevez les noms de clés ressemblant à des identifiants, tels que `API_TOKEN` ou `APP_SECRET_KEY`, sans afficher leurs valeurs dans les journaux partagés. Vérifiez les overrides des drop-ins et les préfixes `-` facultatifs lors de l’évaluation de l’unité effective. La lisibilité constitue une piste d’exposition d’identifiants ; la valeur doit encore être valide pour permettre une action privilégiée menant à une élévation.

### Traitement privilégié de fichiers téléversés non fiables

Un watcher de fichiers exécuté en tant que root peut transmettre des fichiers provenant d’un répertoire de téléversement modifiable par un utilisateur à un parseur ou extracteur de courte durée. Suivez le script parent ou le service du watcher actif et confirmez le répertoire exact, qui peut y déposer des fichiers, la commande enfant et ses arguments, ainsi que l’identité sous laquelle l’enfant s’exécute. Un instantané des processus peut montrer le watcher sans voir l’extracteur entre deux téléversements. Ne déposez pas de charge de test et ne déclenchez pas le watcher pendant l’énumération passive.

Un exemple concret est le mode d’extraction de Binwalk (`-e`) appliqué à des données PFS contrôlées par un attaquant. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) permettait à l’extracteur PFS d’écrire en dehors du répertoire prévu, notamment dans un chemin de plugin que Binwalk pouvait ensuite charger. Le correctif a été intégré en amont dans [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), mais les rétroportages des distributions peuvent conserver une ancienne version affichée ; vérifiez l’état de sécurité du package installé, par exemple dans le [suivi Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510), avant d’en évaluer l’applicabilité. La seule présence d’une version de Binwalk installée ne suffit pas à établir une voie d’élévation de privilèges : l’extraction doit réellement être lancée par un processus plus privilégié sur une entrée contrôlable par l’utilisateur moins privilégié.

### Builds planifiés avec des dépendances locales

Un `cargo run` planifié recompile les sources en tant qu’utilisateur d’exécution de la tâche. Examinez les dépendances locales `{ path = "..." }` du manifeste, ainsi que les permissions des sources et des répertoires parents de chaque dépendance, et pas seulement celles du crate principal. Si un utilisateur moins privilégié peut modifier une dépendance que Cargo compile et que la tâche planifiée exécute le résultat, le code compilé peut s’exécuter en tant que cet utilisateur d’exécution. Confirmez la commande effective du planificateur, le répertoire de travail, la résolution des dépendances et si une recompilation aura lieu ; un fichier source Rust modifiable ailleurs n’est qu’une piste. La lecture du manifeste et des métadonnées des chemins suffit pour un triage passif. Consultez la [documentation Cargo sur les dépendances par chemin](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Fichiers framebuffer Xvfb

`Xvfb -fbdir <directory>` utilise des fichiers mappés en mémoire nommés `Xvfb_screen<n>` pour ses écrans virtuels. Si le processus Xvfb actif d’un autre utilisateur indique un répertoire dont les fichiers d’écran sont lisibles par l’utilisateur actuel, le framebuffer peut exposer le contenu du bureau de cet utilisateur. Confirmez conjointement le processus, la propriété des fichiers et leurs permissions ; le fait qu’un fichier soit lisible ne prouve pas à lui seul que son écran contient des données utiles. Examinez d’abord les chemins et les métadonnées, sans copier les données d’image dans les sorties d’énumération partagées. Le [manuel Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) décrit le fonctionnement de `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
