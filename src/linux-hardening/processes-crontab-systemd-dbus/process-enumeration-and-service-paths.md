# Prozessaufzählung und Dienstpfade

{{#include ../../banners/hacktricks-training.md}}

Die entscheidende Frage ist, welcher privilegierte Prozess Daten oder Code verarbeitet, die ein Benutzer mit geringeren Rechten beeinflussen kann. Untersuche den Prozessbaum, die Laufzeitumgebung, offene Dateien und die Unit oder das Skript, mit der bzw. dem jeder infrage kommende Prozess gestartet wurde.

## Prozesse und Eigentümer ermitteln

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Eine benutzerübergreifende Eltern-Kind-Beziehung kann normal sein, ein unerwarteter Übergang sollte jedoch Anlass sein, den Elternprozess, die Argumente, die ausführbare Datei, das Arbeitsverzeichnis und referenzierte Dateien zu überprüfen. Verwenden Sie [Benutzer und Sitzungen](../user-information/user-and-session-triage.md), um den Eigentümer und den Login-Kontext einzuordnen.

### Lokale Konsolen virtueller Maschinen

Überprüfen Sie die `-spice`-Optionen eines QEMU-Prozesses zusammen mit seiner Listening-Adresse. [Die QEMU-Dokumentation](https://www.qemu.org/docs/master/system/qemu-manpage.html) besagt, dass `disable-ticketing` SPICE-Clients die Verbindung ohne Authentifizierung ermöglicht. Ein an Loopback gebundener Listener kann dennoch für andere lokale Host-Benutzer erreichbar sein. Prüfen Sie den aktiven Listener, die Authentifizierungsoptionen und den lokalen Zugriff, bevor Sie die Befehlszeile als offengelegte Konsole einstufen. Die Konsolensteuerung betrifft den **Gast**; der Erhalt eines Gastkontos oder eine Änderung seines Boot-Status erfordert separate Bedingungen innerhalb des Gasts und verschafft keinen Root-Zugriff auf den Virtualisierungshost. Lesen Sie Prozessargumente und Socket-Metadaten, ohne während der passiven Enumeration eine Verbindung zum Gast herzustellen oder ihn neu zu starten.

Eine lokal erreichbare Weboberfläche kann Code mit dem Dienstkonto ausführen, selbst wenn die erste Shell nicht auf die Dateien dieses Kontos zugreifen kann. So betraf CVE-2023-0297 die Verarbeitung von `/flash/addcrypted2` in pyLoad, wenn nicht vertrauenswürdiges JavaScript Js2Py mit aktivierten Python-Imports erreichte; der [Upstream-Fix](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deaktivierte `pyimport`. Setzen Sie den Eigentümer des laufenden Prozesses, die Listening-Adresse, die Erreichbarkeit des Endpunkts und den installierten Patch oder Vendor-Backport zueinander in Beziehung, bevor Sie einen pyLoad-Prozess als Eskalationspfad einstufen. Ein Prozessname, ein offener Port oder eine Paketversion allein belegt keine Gefährdung; bei der passiven Enumeration sollte kein Ausführungspayload gesendet werden.

### Privilegierte Login-Shells mit gemeinsamem Terminal

Eine privilegierte interaktive Shell, die `su --login <user>` ohne ein unabhängiges Pseudo-Terminal ausführt, kann dazu führen, dass ihr Terminal gemeinsam mit der niedriger privilegierten Login-Shell verwendet wird. Wenn die Startdatei dieses Benutzers manipulierbar ist und darin ausgeführter Code `TIOCSTI` zur Eingabe von Terminalbefehlen verwenden kann, kann diese Eingabe die privilegierte Shell erreichen, sobald sie wieder aktiv wird. [Das util-linux-`su`-Handbuch](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) beschreibt das Risiko gemeinsam genutzter Terminals und empfiehlt für die interaktive Nutzung `su --pty`/`-P`; `su -c` startet eine separate Sitzung ohne steuerndes Terminal. Das Risiko setzt die tatsächliche Eltern-Shell, die Terminalbeziehung, die Startdatei des Zielbenutzers und die Kernelrichtlinie voraus. Ein Prozessname oder ein `su -l`-Argument allein ist lediglich ein Hinweis zur Überprüfung.

Prüfen Sie den beobachteten Prozessbaum und die TTY-Spalten sowie anschließend den lesbaren Launcher und die Eigentums- und Berechtigungseinstellungen der Startdatei. Unter Linux kann `/proc/sys/dev/tty/legacy_tiocsti`, sofern vorhanden, bei der Beurteilung der Richtlinie helfen; sein Fehlen ist kein Sicherheitsnachweis. [Das Linux-`TIOCSTI`-Handbuch](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) weist darauf hin, dass der Vorgang seit Linux 6.2 möglicherweise `CAP_SYS_ADMIN` erfordert, wenn dieser Sysctl-Wert auf false gesetzt ist. Rufen Sie das ioctl nicht allein zur Enumeration des Hosts auf.

Ein Datenbankkonto kann manchmal die Startdatei des Zielbenutzers ändern, ohne direkten Schreibzugriff auf das Dateisystem zu haben. `COPY ... TO 'filename'` auf der PostgreSQL-Serverseite schreibt als Betriebssystemkonto des Datenbankservers, aber [PostgreSQL schränkt dies ein](https://www.postgresql.org/docs/current/sql-copy.html): Diese Dateiform ist Datenbank-Superusern oder Rollen wie `pg_write_server_files` vorbehalten. Prüfen Sie sowohl die Datenbankrolle als auch die Dateiberechtigungen des Serverbetriebssystems; eine Verbindungszeichenfolge der Anwendung allein gewährt keine Berechtigung zum Schreiben von Dateien. Berücksichtigen Sie bei der Bewertung der Angriffskette den privilegierten Launcher und die Fähigkeiten des Datenbankkontos getrennt voneinander.

## Laufzeit-Artefakte untersuchen

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Gelöschte Executables und gelöschte, aber noch geöffnete Dateien bleiben referenziert, bis ihr letzter Descriptor geschlossen wird. Sie können Beweise oder zugängliche Secrets bewahren. Prozessumgebungen und Speicher können Zugangsdaten enthalten, aber das Auslesen eines anderen Prozesses wird durch Eigentümerschaft, `/proc`-Mount-Optionen, die Yama-`ptrace`-Richtlinie und weitere Sicherheitskontrollen eingeschränkt. Siehe [Dateideskriptoren](../main-system-information/filesystem-links-and-file-descriptors.md) und [Suche nach Zugangsdaten nach der Kompromittierung](../post-exploitation/README.md) für verwandte Techniken.

Gespeicherte Syscall-Traces unterliegen ebenfalls Dateiberechtigungen. [`strace` zeichnet Syscall-Argumente in eine Ausgabedatei auf](https://man7.org/linux/man-pages/man1/strace.1.html), sodass ein lesbarer Trace von [`execve`-Argumenten](https://man7.org/linux/man-pages/man2/execve.2.html) möglicherweise ein Passwort offenlegt, das ein privilegierter Job auf seiner Kommandozeile übergeben hat. Stelle zunächst fest, ob der aktuelle Benutzer den jeweiligen Trace lesen kann und ob das Argument tatsächlich eine Zugangsinformation enthält; ein späterer Wechsel zu einem Unix-Konto erfordert einen separaten Nachweis, dass die Zugangsinformation dort akzeptiert wird. Dateimetadaten sind ein nützlicher passiver Anhaltspunkt, ohne bei der routinemäßigen Enumeration jeden Trace zu durchsuchen oder dessen Inhalt auszugeben.

## Privilegierte Office-Automatisierungs-Sockets

LibreOffice und OpenOffice können ihre UNO API über ein Argument der Form `--accept=socket,host=<host>,port=<port>;urp;` bereitstellen. Ein root-eigener Office-Prozess mit einem erreichbaren Endpunkt kann einem lokal niedriger privilegierten Benutzer ermöglichen, API-Dienste im Sicherheitskontext dieses Prozesses aufzurufen. Der Dienst `SystemShellExecute` umfasst eine Operation zum Starten eines Systembefehls. Eine Bindung an Loopback schränkt die Erreichbarkeit aus der Ferne ein, lässt den Socket für lokale Benutzer aber weiterhin erreichbar, sofern keine andere Kontrolle den Zugriff verhindert.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Ordne den Prozessbesitzer, das exakte Argument `--accept` sowie die aktuelle Listening-Adresse und den Port einander zu. Ein konfigurierter Acceptor, der nicht an eine Adresse binden konnte, ist lediglich ein Hinweis; stelle während der passiven Enumeration keine Verbindung zur API her und rufe sie nicht auf. Starte keine privilegierte Office-Instanz nur, um diesen Zustand zu testen.

## Von privilegierten Prozessen verwendeter System-V-Speicher

Ein root-eigener Helfer kann ein System-V-Speichersegment erstellen, in das ein anderer Benutzer schreiben kann. Vertraut der Helfer später Daten aus diesem Segment in einem Shell-Befehl oder bei einem anderen sensiblen Vorgang, überschreitet das Segment eine Privilegiengrenze, selbst wenn die ausführbare Datei und ihre Dateien geschützt sind. `shmget()` übernimmt die Zugriffsrechte aus den unteren neun Bits seiner Flags; der Modus `0666` erlaubt anderen Benutzern Schreibzugriff, während ein `IPC_CREAT`-Flag diese Rechte nicht einschränkt. Untersuche aktive Segmente passiv mit `ipcs -m` und ordne ihren Besitzer, Modus und ihre Lebensdauer dem privilegierten Prozess und dessen Eingabeverarbeitung zu. Ein weltweit beschreibbares Segment allein belegt keine Befehlsausführung.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

System-V-Segmente unterscheiden sich von POSIX-Dateien für gemeinsamen Speicher unter `/dev/shm`. Ein nur kurzzeitig erstelltes Segment kann in einem einzelnen `ipcs`-Snapshot fehlen. Eine leere Ausgabe schließt daher nicht aus, dass ein Hilfsprogramm gemeinsamen Speicher verwendet. Prüfe das Verhalten des Quelltexts oder der Binärdatei sowie alle `sudo`-Regeln, die das Programm starten. Rufe das privilegierte Hilfsprogramm nicht nur deshalb auf, um bei der Aufzählung ein Segment sichtbar zu machen. Der [Leitfaden zu IPC-Namespaces](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) erklärt, wie Namespaces die Sichtbarkeit beeinflussen.<sup>[[2]](#references)[[3]](#references)</sup>

## Consul-Agent-Script-Checks

Consul kann Script-Health-Checks mit der Betriebssystemidentität seines Agents ausführen. Wenn ein Agent als root läuft, `enable_script_checks` aktiviert ist und ein Benutzer mit geringeren Privilegien über die lokale HTTP-API einen Service mit einem Script-Check registrieren darf, kann dieser Benutzer möglicherweise Befehle als root ausführen lassen. Auch wenn die API nur an `127.0.0.1` gebunden ist, können lokale Benutzer darauf zugreifen. Die Einstellung `enable_local_script_checks` ist restriktiver: Sie schließt Script-Checks aus, die über HTTP-API-Registrierungen übermittelt werden. Wenn Consul-ACLs aktiviert sind, erfordert die Service-Registrierung `service:write`; eine `acl.default_policy=allow`-Zeile allein beweist nicht, dass ein anonymer Aufrufer Services registrieren kann. Prüfe gemeinsam die tatsächliche Agent-Identität, die geladenen Einstellungen, die API-Bindung und die Autorisierung.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Folge den Argumenten `-config-dir` und `-config-file` des laufenden Agents zur relevanten Konfiguration und prüfe nur die Feldnamen und Einstellungen für Script-Checks und ACLs. Konfigurationsdateien können auch Gossip-Schlüssel oder Tokens enthalten; vermeide es, diese in gemeinsam genutzte Logs einzufügen. Registriere keinen Service und führe keinen Health Check aus, nur um diesen Zustand zu ermitteln.

Ein separater Pfad über lokale Dateien besteht, wenn ein Benutzer mit geringeren Berechtigungen **Schreib- und Suchzugriff** auf das Verzeichnis hat, das mit `-config-dir` für einen als root laufenden Agent angegeben wurde: Eine neue `.hcl`- oder `.json`-Servicedefinition kann aus diesem Verzeichnis geladen werden. Such- und Schreibzugriff auf ein Verzeichnis können das Hinzufügen einer Datei ermöglichen, selbst wenn das Auflisten des Verzeichnisses verweigert wird. Um die Ausführung von Befehlen als root zu bestätigen, überprüfe, ob der Agent dieses Verzeichnis tatsächlich lädt, seine **effektive** Einstellung für Script-Checks lokale Definitionen zulässt, die Definition geladen wird und der Agent weiterhin root-Berechtigungen hat. [Consul dokumentiert](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations), welche Einstellungen und Health-Check-Definitionen neu geladen werden können; das Aktivieren von Script-Checks kann selbst einen Neustart erfordern, prüfe daher das Verhalten der installierten Version. Wenn ACLs den Agent schützen, erfordert [`consul reload` die Berechtigung `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); eine Schreibberechtigung für KV reicht dafür nicht aus. Betrachte beschreibbare Verzeichnismetadaten als Hinweis für eine Überprüfung, nicht als Beweis für einen autorisierten Reload, Neustart oder eine Befehlsausführung. Prüfe Pfade, Berechtigungen und Richtlinien, ohne Konfiguration zu schreiben oder die API aufzurufen.

## Folge der Service-Ausführungskette

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Prüfe die Unit, Drop-ins, `EnvironmentFile=`, Hilfsskripte, relative Befehle, beschreibbare Verzeichnisse und Socket-Aktivierung. Eine root-eigene Unit kann dennoch unsicher sein, wenn sie eine benutzerbeschreibbare Konfigurationsdatei oder ein benutzerbeschreibbares Skript einliest. Die Seite zu [beliebigem Schreiben in Dateien](../interesting-files-permissions/write-to-root.md) behandelt gängige Missbrauchswege bei Services und Units. Überwache kurzlebige Jobs mit [pspy](https://github.com/DominicBreuker/pspy) oder Audit-/Prozess-Telemetrie, wenn eine einmalige `ps`-Auflistung sie nicht erfasst.

Ordne bei einem benutzerdefinierten **xinetd**-Service die aktivierte Stanza mit `server`, `user` und den Zugriffskontrollen dem aktiven Listener und der exakten ausführbaren Datei zu. Die Einstellung [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) legt die Identität des gestarteten Prozesses fest. Ein Set-User-ID-Bit auf der ausführbaren Datei kann dessen effektive Identität separat ändern, sofern [`execve` diesen Übergang zulässt](https://man7.org/linux/man-pages/man2/execve.2.html). Eine erreichbare privilegierte Binärdatei, die nicht vertrauenswürdige Eingaben annimmt, sollte offline anhand des Quellcodes oder Disassemblats auf Speicherfehler untersucht werden, etwa auf eine unbegrenzte [`scanf`-Stringkonvertierung](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) in einen festen Puffer. Das Service-Mapping und die Set-User-ID-Metadaten sind Hinweise, aber kein Nachweis für einen solchen Fehler. Sende während der passiven Enumeration keine Eingaben aus, die Abstürze verursachen, und debugge den aktiven privilegierten Service nicht.

Prüfe bei einem benutzerdefinierten privilegierten Listener mit lesbarem Quellcode jede vom Aufrufer kontrollierte Länge, die bei einer Kopieroperation wie [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html) verwendet wird. Nur zu prüfen, ob der aktuelle Schreibindex innerhalb eines festen Puffers liegt, belegt nicht, dass die **Kopierlänge** in den verbleibenden Platz passt. Verifiziere `copy_length <= capacity - index`, nachdem du bestätigt hast, dass der Index im gültigen Bereich liegt, und prüfe Vorzeichenbehandlung sowie arithmetischen Überlauf. Dies ist nur dann ein Prüfhinweis, wenn die Eingabe diese Operation erreicht, der Listener für den weniger privilegierten Benutzer zugänglich ist und der Prozess eine höhere effektive Identität behält. Untersuche Quellcode und Prozessmetadaten offline. Sende während der Enumeration keine Eingaben an den aktiven Service, die Abstürze verursachen.

Auf Systemen mit **Upstart** können System-Jobdefinitionen unter `/etc/init/*.conf` liegen. Eine für den aktuellen Benutzer beschreibbare Jobdatei ist relevant, wenn der aktive Init-Daemon genau diesen Job lädt, dessen `script`- oder `exec`-Stanza mit einer höher privilegierten Identität ausgeführt wird und der Benutzer ihn über einen erlaubten `initctl`-Befehl oder einen anderen tatsächlichen Auslöser starten kann. Eine sudo-Berechtigung für `initctl` allein beweist weder, dass eine Jobdatei beschreibbar ist, noch, dass ein geänderter Job ausgeführt wird. Prüfe die Berechtigungen der exakten Jobdatei, die effektive Run-as-Einstellung, den aktiven Daemon und den Auslöser, ohne den Job während der Enumeration zu bearbeiten oder zu starten. Siehe die Handbücher zur [Upstart-Jobkonfiguration](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) und zu [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Eine lesbare Autologin-Passwortdatei, etwa `/etc/autologin/passwd` auf Systemen, deren [Boot-Job genau diesen Pfad einliest](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), ist ein Hinweis auf mögliche Offenlegung von Zugangsdaten. Bestätige, dass der Boot-Job installiert ist und die Datei verwendet, und prüfe anschließend separat, ob das Passwort für ein anderes lokales Konto oder einen Service gültig ist. Der Dateiname allein belegt keine Wiederverwendung des Passworts. Erfasse Pfad- und Zugriffsmetadaten, ohne das Passwort in gemeinsam genutzte Enumeration-Ausgaben aufzunehmen.

`ExecStart=` einer Unit oder ein geplanter Befehl kann den exakten Pfad eines Skripts in einem nicht auflistbaren Verzeichnis offenlegen. [Suchberechtigung für Verzeichnisse](https://man7.org/linux/man-pages/man7/path_resolution.7.html) kann der aktuellen Identität dennoch erlauben, diesen bekannten Pfad zu durchlaufen. Bestätige den Suchzugriff auf jedem übergeordneten Verzeichnis und die Leseberechtigung für die Datei, statt anzunehmen, dass eine fehlgeschlagene Verzeichnisauflistung sie schützt. Ein lesbares Skript kann Zugangsdaten für eine Übertragung enthalten. Der Zugriff auf ein anderes Konto setzt jedoch voraus, dass diese Zugangsdaten weiterhin gültig sind und dort unabhängig akzeptiert werden. Erfasse Pfad und Berechtigungsnachweise, ohne Geheimnisse in gemeinsam genutzte Logs auszugeben.

Prüfe bei einem geplanten CommonJS-Node.js-Skript einfache Imports wie `require('package')`, auch wenn das Skript selbst schreibgeschützt ist. [Node sucht `node_modules` neben der importierenden Datei und anschließend in deren übergeordneten Verzeichnissen](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), bevor es auf konfigurierte globale Pfade zurückgreift. Ein weniger privilegierter Benutzer, der eines dieser übergeordneten Verzeichnisse **beschreiben und durchsuchen** kann, kann möglicherweise ein Paket anlegen, das früher gefunden wird. Bestätige, dass der exakte Import erreicht wird, es sich bei dem ausgewählten Paket nicht um ein integriertes Modul handelt, der betreffende Pfad erstellt oder geändert werden kann, das Modul dort in der installierten Laufzeitumgebung aufgelöst wird und ein höher privilegierter Job es bei einem künftigen Aufruf laden wird. Beschreibbare Metadaten übergeordneter Verzeichnisse sind nur ein Prüfhinweis. Untersuche Skript und Scheduler passiv, ohne ein Modul abzulegen oder den Job auszulösen.

Ein privater Python-Paketindex ist eine weitere Vertrauensgrenze, wenn ein automatisierter Job Pakete unter einer anderen OS-Identität installiert. Ordne dem exakten Job und Run-as-Konto den konfigurierten Index, die ausgewählten Paketnamen und die Frage zu, ob ein weniger privilegierter Benutzer ein Paket veröffentlichen oder ersetzen kann, das der Job tatsächlich installieren wird. Beim Erstellen einer Source Distribution können deren Build-Backend oder das veraltete `setup.py` unter der Identität des Installationsprozesses ausgeführt werden. Das Importieren des installierten Pakets ist ein separater Ausführungspfad. Ein Index-Listener, ein lesbarer Hash eines Upload-Passworts oder ein Paketdateiname allein belegt diese Angriffskette nicht. Prüfe Job, Indexautorisierung und Paketherkunft, ohne während der Enumeration etwas hochzuladen oder zu installieren. Siehe [pips Schnittstelle für das Build-System](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Ein privilegierter Agent fragt möglicherweise eine Task-Queue ab, die von einem separaten Webservice oder Container verwaltet wird. Wenn eine Identität mit geringerem Vertrauensniveau die Task-Datenbank des Services beschreiben kann, stelle fest, ob diese Zeilen tatsächlich an den Agenten ausgeliefert werden und ob ein Command-Task mit der OS-Identität des Agenten ausgeführt wird. Prüfe Datenbank-Schreibzugriff, Ziel-Session oder Routing-Key, aktives Polling, Task-Autorisierung und den effektiven Benutzer des Agenten jeweils separat. Root innerhalb eines Containers bedeutet nicht automatisch Zugriff als Host-Root. Die Grenze wird nur überschritten, wenn ein privilegierter Host-Prozess vom Angreifer kontrollierte Task-Daten ausführt. Untersuche Prozess-, Datenbankdatei- und Service-Metadaten, ohne während der Enumeration die Queue zu ändern oder einen Task zu senden.

Ein wiederkehrender Job liest möglicherweise stattdessen einen Befehl aus einer Konfigurationszeile in einer Anwendungsdatenbank. Bestätige, dass die Datenbankrolle mit geringeren Berechtigungen genau diese Zeile ändern kann, dass der aktive Job sie nach der Änderung einliest und dass der Wert unter einer höheren OS-Identität an eine Shell oder einen gleichwertigen Befehlsausführer übergeben wird. Datenbank-Schreibzugriff oder ein wie ein Befehl aussehender Wert belegen allein keine Ausführung. Untersuche Job und Berechtigungen, ohne die Zeile während der passiven Enumeration zu ändern.

Eine Nachricht in einer Queue kann auch eine URL statt Code enthalten. Wenn ein privilegierter Consumer diese URL abruft und die Antwort als Lua- oder anderes ausführbares Plugin lädt, prüfe die Veröffentlichungsberechtigung für den exakten Exchange und Routing-Key, die Bindung an die konsumierte Queue, den Abruf- und Plugin-Ladepfad sowie die effektive Identität des Workers. [RabbitMQ leitet veröffentlichte Nachrichten über Exchanges weiter](https://www.rabbitmq.com/docs/exchanges). Ein Broker-Listener oder gültiger Login allein belegt nicht, dass die Nachricht diesem Worker zugestellt wird. Abgefangene Klartext-Zugangsdaten für den Broker sind ein separater Hinweis, der tatsächlichen Zugriff auf eine Paketerfassung und lesbaren Traffic voraussetzt. Sie belegen keine Veröffentlichungsberechtigung. Ein Lua-Plugin kann Shell-Befehle über [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) ausführen, aber nur, wenn diese API in seiner Laufzeitumgebung verfügbar ist. Untersuche Konfiguration und Code, ohne während der passiven Enumeration Traffic abzufangen, Nachrichten zu veröffentlichen oder ein Plugin abzurufen.

Wenn ein privilegierter Python-Service einen lokalen HTTP- oder Socket-Endpunkt bereitstellt, kann ein lesbares Skript einen Pfad von Eingaben zu Code offenlegen, selbst wenn seine Dateiberechtigungen Änderungen verhindern. Ordne den aktiven Prozess und die Identität der Unit dem exakten Skript, Listener, der Routenautorisierung und den vom Aufrufer kontrollierten Feldern zu. Verfolge diese Felder anschließend durch Parsing und Validierung bis zu einem dynamischen `eval()`- oder `exec()`-Sink. Insbesondere kann das Erzeugen eines neuen f-Strings aus Request-Text und dessen Auswertung vom Angreifer gelieferte Ersetzungsfelder als Python-Ausdrücke interpretieren ([Python-Warnung zu `eval`](https://docs.python.org/3/library/functions.html#eval); [Semantik von f-Strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Ein bloßer Treffer für `eval` oder eine Loopback-Bindung belegt nicht, dass ein nicht vertrauenswürdiger Aufrufer den Sink erreicht. Untersuche den tatsächlichen Datenfluss und die Zugriffskontrollen, ohne während der Enumeration eine Test-Payload zu senden.

Ein Gate für signierte Requests auf dieser Route muss separat geprüft werden. Wenn lesbarer Quellcode den Signaturschlüssel nachweislich aus einem sehr kleinen oder vorhersehbaren Ausgaberaum ableitet und der Service ein gültiges signiertes Beispiel bereitstellt, schützt die Signatur einen privilegierten `eval()`-Sink möglicherweise nicht mehr. Prüfe die genaue Schlüsselableitung und Verifikation, die Identität des aktiven Services und den lokalen Zugriff durch Aufrufer sowie, ob das signierte Feld den Sink erreicht. Ein Import von Pythons [`random`-Modul](https://docs.python.org/3/library/random.html) oder eine Beispielsignatur belegt keine dieser Bedingungen. Python warnt außerdem, dass das Einschränken von `__builtins__` [keine Sicherheitsgrenze für nicht vertrauenswürdige `eval()`-Eingaben darstellt](https://docs.python.org/3/library/functions.html#eval). Analysiere Schlüssel offline und übermittle während der passiven Enumeration keine gefälschten Requests.

Ein leeres, aber beschreibbares Verzeichnis `/etc/systemd/system/<unit>.service.d` ist auch dann relevant, wenn die Unit-Datei und alle vorhandenen Drop-ins geschützt sind: Der Benutzer kann möglicherweise eine neue `.conf`-Override-Datei anlegen. Prüfe, ob das Verzeichnis für die aktuelle Identität beschreibbar und durchsuchbar ist, ob die Unit geladen ist und als root läuft und ob ein Daemon-Reload mit anschließendem Neustart stattfinden wird. Eine Berechtigung zum Neuladen oder Neustarten, ein Timer oder ein späterer Systemstart kann die Änderung wirksam machen. Schreibzugriff auf das Verzeichnis allein führt sie nicht sofort aus.

Verfolge bei laufenden Services die wörtlichen `EnvironmentFile=`-Pfade aus dem Abschnitt `[Service]` der Unit, auch wenn die Dateinamen nicht mit `.env` beginnen. Wenn ein Benutzer mit geringen Berechtigungen eine Datei lesen kann, liste schlüsselähnliche Namen wie `API_TOKEN` oder `APP_SECRET_KEY` auf, ohne die Werte in gemeinsam genutzte Logs auszugeben. Berücksichtige bei der Beurteilung der effektiven Unit Drop-in-Overrides und optionale `-`-Präfixe. Lesbarkeit ist ein Hinweis auf mögliche Offenlegung von Zugangsdaten. Damit sich daraus eine Rechteausweitung ergibt, muss der Wert noch für eine privilegierte Aktion gültig sein.

### Privilegierte Verarbeitung nicht vertrauenswürdiger Uploads

Ein als root ausgeführter File-Watcher kann Dateien aus einem benutzerbeschreibbaren Upload-Verzeichnis an einen kurzlebigen Parser oder Extraktor übergeben. Verfolge das übergeordnete Skript oder den Service des laufenden Watchers und bestätige das exakte Verzeichnis, wer dort Dateien ablegen kann, den Child-Befehl samt Argumenten und die Identität, unter der der Child-Prozess läuft. Ein Prozess-Snapshot kann den Watcher zeigen, während er den Extraktor zwischen Uploads verpasst. Lege während der passiven Enumeration keine Test-Payload ab und löse den Watcher nicht aus.

Ein konkretes Beispiel ist der Extraktionsmodus (`-e`) von Binwalk, der angreifergesteuerte PFS-Daten verarbeitet. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) erlaubte es dem PFS-Extraktor, außerhalb des vorgesehenen Verzeichnisses zu schreiben, unter anderem in einen Plugin-Pfad, den Binwalk später laden konnte. Upstream wurde die Korrektur in [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4) aufgenommen. Distributionen können jedoch Backports enthalten, sodass eine ältere Version angezeigt wird. Prüfe daher vor der Beurteilung der Anwendbarkeit den Sicherheitsstatus des installierten Pakets, etwa im [Debian-Tracker](https://security-tracker.debian.org/tracker/CVE-2022-4510). Eine installierte Binwalk-Version allein belegt keinen Pfad zur Rechteausweitung: Die Extraktion muss tatsächlich von einem privilegierteren Prozess für Eingaben gestartet werden, die der weniger privilegierte Benutzer kontrollieren kann.

### Geplante Builds mit lokalen Abhängigkeiten

Ein geplantes `cargo run` kompiliert den Quellcode erneut unter dem Run-as-Benutzer des Jobs. Untersuche die lokalen `{ path = "..." }`-Abhängigkeiten im Manifest sowie die Berechtigungen für Quellcode und übergeordnete Verzeichnisse jeder Abhängigkeit, nicht nur die der Haupt-Crate. Wenn ein weniger privilegierter Benutzer eine Abhängigkeit ändern kann, die Cargo kompiliert, und der geplante Job das Ergebnis ausführt, kann der kompilierte Code als Run-as-Benutzer ausgeführt werden. Bestätige den effektiven Scheduler-Befehl, das Arbeitsverzeichnis, die Auflösung der Abhängigkeiten und ob eine Neukompilierung stattfindet. Eine beschreibbare Rust-Quelldatei an anderer Stelle ist nur ein Hinweis. Für eine passive Triage genügen das Lesen des Manifests und die Prüfung der Pfadmetadaten. Siehe die [Cargo-Dokumentation zu Pfad-Abhängigkeiten](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Xvfb-Framebuffer-Dateien

`Xvfb -fbdir <directory>` verwendet speicherabgebildete Dateien namens `Xvfb_screen<n>` für seine virtuellen Bildschirme. Wenn der Xvfb-Prozess eines anderen Benutzers ein Verzeichnis angibt, dessen Bildschirmdateien für den aktuellen Benutzer lesbar sind, kann der Framebuffer Inhalte des Desktops dieses Benutzers offenlegen. Bestätige Prozess, Dateieigentümer und Berechtigungen gemeinsam. Eine lesbare Datei allein beweist nicht, dass sich darin nützliche Bildschirminhalte befinden. Prüfe zuerst Pfade und Metadaten, ohne Bilddaten in gemeinsam genutzte Enumeration-Ausgaben zu kopieren. Das [Xvfb-Handbuch](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) dokumentiert das Verhalten von `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
