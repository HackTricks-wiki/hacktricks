# Prozesserfassung und Servicepfade

{{#include ../../banners/hacktricks-training.md}}

Die entscheidende Frage ist, welcher privilegierte Prozess Daten oder Code verarbeitet, die ein Benutzer mit niedrigeren Berechtigungen beeinflussen kann. Untersuche den Prozessbaum, die aktuelle Umgebung, geöffnete Dateien sowie die Unit oder das Skript, mit der bzw. dem jeder infrage kommende Prozess gestartet wurde.

## Prozesse und Besitzverhältnisse erfassen

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Eine Parent-Child-Beziehung zwischen unterschiedlichen Benutzern kann normal sein, aber ein unerwarteter Übergang sollte Anlass sein, den Parent-Befehl, die Argumente, die ausführbare Datei, das Arbeitsverzeichnis und referenzierte Dateien zu überprüfen. Verwenden Sie [Benutzer und Sitzungen](../user-information/user-and-session-triage.md), um den Eigentümer und den Login-Kontext einzuordnen.

### Lokale Konsolen virtueller Maschinen

Überprüfen Sie die `-spice`-Optionen eines QEMU-Prozesses zusammen mit seiner Listening-Adresse. [Die QEMU-Dokumentation](https://www.qemu.org/docs/master/system/qemu-manpage.html) besagt, dass `disable-ticketing` SPICE-Clients erlaubt, sich ohne Authentifizierung zu verbinden. Ein an Loopback gebundener Listener kann dennoch für andere Benutzer des lokalen Hosts erreichbar sein. Prüfen Sie den aktiven Listener, die Authentifizierungsoptionen und den lokalen Zugriff, bevor Sie die Befehlszeile als exponierte Konsole einstufen. Die Steuerung der Konsole betrifft den **Gast**; um ein Gastkonto zu erhalten oder dessen Boot-Zustand zu ändern, sind separate Bedingungen auf Gastseite erforderlich, und dies verschafft keinen Root-Zugriff auf dem Virtualisierungshost. Lesen Sie bei der passiven Enumeration Prozessargumente und Socket-Metadaten, ohne sich mit dem Gast zu verbinden oder ihn neu zu starten.

Eine lokal erreichbare Weboberfläche kann Code mit dem Dienstkonto ausführen, selbst wenn die erste Shell nicht auf dessen Dateien zugreifen kann. Zum Beispiel betraf CVE-2023-0297 die Verarbeitung von `/flash/addcrypted2` durch pyLoad, wenn nicht vertrauenswürdiges JavaScript mit aktivierten Python-Imports Js2Py erreichte; der [Upstream-Fix](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) deaktivierte `pyimport`. Gleichen Sie den Prozessbesitzer, die Listening-Adresse, die Erreichbarkeit des Endpunkts und installierte Patches oder Vendor-Backports ab, bevor Sie einen pyLoad-Prozess als Privilegienausweitungspfad einstufen. Ein Prozessname, ein offener Port oder eine Paketversion allein beweist keine Exponierung; bei der passiven Enumeration sollte kein Ausführungspayload gesendet werden.

### Privilegierte Login-Shells mit gemeinsamem Terminal

Eine privilegierte interaktive Shell, die `su --login <user>` ohne ein unabhängiges Pseudo-Terminal ausführt, kann dazu führen, dass ihr Terminal weiterhin mit der Login-Shell des weniger privilegierten Benutzers gemeinsam genutzt wird. Wenn die Startdatei dieses Benutzers kontrollierbar ist und darin ausgeführter Code `TIOCSTI` zum Einschleusen von Terminaleingaben verwenden kann, erreichen diese Eingaben möglicherweise die privilegierte Shell, wenn sie wieder aktiv wird. [Das util-linux-`su`-Handbuch](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) beschreibt das Risiko gemeinsam genutzter Terminals und empfiehlt `su --pty`/`-P` für die interaktive Nutzung; `su -c` startet eine separate Sitzung ohne steuerndes Terminal. Das Risiko setzt voraus, dass die tatsächliche Parent-Shell, die Terminalbeziehung, die Startdatei des Zielbenutzers und die Kernel-Richtlinie dies ermöglichen. Ein Prozessname oder das Argument `su -l` allein ist lediglich ein Ansatzpunkt zur Überprüfung.

Untersuchen Sie den beobachteten Prozessbaum und die TTY-Spalten sowie anschließend den lesbaren Launcher und die Eigentums- und Berechtigungseinstellungen der Startdatei. Unter Linux kann `/proc/sys/dev/tty/legacy_tiocsti`, sofern vorhanden, bei der Einordnung der Richtlinie helfen; das Fehlen dieser Datei ist kein Sicherheitsnachweis. [Das Linux-`TIOCSTI`-Handbuch](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) weist darauf hin, dass die Operation seit Linux 6.2 möglicherweise `CAP_SYS_ADMIN` erfordert, wenn dieser Sysctl-Wert false ist. Rufen Sie das ioctl nicht allein zur Enumeration des Hosts auf.

Ein Datenbankkonto kann manchmal die Startdatei des Zielbenutzers ändern, ohne direkten Schreibzugriff auf das Dateisystem zu haben. PostgreSQL-seitiges `COPY ... TO 'filename'` schreibt als Betriebssystemkonto des Datenbankservers, aber [PostgreSQL schränkt](https://www.postgresql.org/docs/current/sql-copy.html) diese Dateiform auf Datenbank-Superuser oder Rollen wie `pg_write_server_files` ein. Prüfen Sie sowohl die Datenbankrolle als auch die Dateiberechtigungen des Server-Betriebssystems; eine Verbindungszeichenfolge der Anwendung verleiht allein keine Schreibberechtigung für Dateien. Berücksichtigen Sie den privilegierten Launcher und die Fähigkeiten des Datenbankkontos bei der Bewertung der Angriffskette getrennt voneinander.

## Laufzeit-Artefakte untersuchen

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Gelöschte ausführbare Dateien und gelöschte, aber noch geöffnete Dateien bleiben referenziert, bis ihr letzter Dateideskriptor geschlossen wird. Sie können Beweise oder zugängliche Geheimnisse bewahren. Prozessumgebungen und Speicher können Zugangsdaten enthalten, aber das Auslesen eines anderen Prozesses wird durch Eigentümerschaft, `/proc`-Mount-Optionen, die Yama- ptrace-Richtlinie und andere Sicherheitskontrollen eingeschränkt. Verwandte Techniken finden Sie unter [Dateideskriptoren](../main-system-information/filesystem-links-and-file-descriptors.md) und [Suche nach Zugangsdaten nach der Kompromittierung](../post-exploitation/README.md).

Gespeicherte syscall-Traces bilden eine weitere Grenze für Dateiberechtigungen. [`strace` zeichnet syscall-Argumente in einer Ausgabedatei auf](https://man7.org/linux/man-pages/man1/strace.1.html), daher kann ein lesbarer Trace von [`execve`-Argumenten](https://man7.org/linux/man-pages/man2/execve.2.html) ein Passwort offenlegen, das ein privilegierter Job über seine Befehlszeile übergeben hat. Stellen Sie zunächst fest, dass der aktuelle Benutzer den konkreten Trace lesen kann und dass das Argument tatsächlich ein Zugangsdaten enthält; für einen späteren Wechsel des Unix-Kontos muss separat nachgewiesen werden, dass die Zugangsdaten dort akzeptiert werden. Dateimetadaten sind ein nützlicher passiver Hinweis, ohne alle Traces zu durchsuchen oder ihre Inhalte bei der routinemäßigen Auflistung auszugeben.

## Sockets für privilegierte Office-Automatisierung

LibreOffice und OpenOffice können ihre UNO API über ein `--accept=socket,host=<host>,port=<port>;urp;`-Argument bereitstellen. Ein root-eigener Office-Prozess mit einem erreichbaren Endpunkt kann es einem lokalen Benutzer mit geringeren Berechtigungen ermöglichen, API-Dienste im Sicherheitskontext dieses Prozesses aufzurufen. Der `SystemShellExecute`-Dienst umfasst eine Funktion zum Starten eines Systembefehls. Eine Bindung an Loopback beschränkt die Erreichbarkeit aus der Ferne, lässt den Socket aber weiterhin für lokale Benutzer erreichbar, sofern keine andere Kontrolle den Zugriff verhindert.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Korrelieren Sie den Prozesseigentümer, das genaue Argument `--accept` sowie die aktuelle Listening-Adresse und den Port. Ein konfigurierter Acceptor, der nicht an eine Adresse binden konnte, ist lediglich ein Hinweis; stellen Sie bei der passiven Enumeration keine Verbindung zur API her und rufen Sie sie nicht auf. Starten Sie nicht eigens zum Testen dieser Bedingung eine privilegierte Office-Instanz.

## System-V-Shared-Memory, das von privilegierten Prozessen verwendet wird

Ein root-eigener Helper kann ein System-V-Shared-Memory-Segment erstellen, in das ein anderer Benutzer schreiben kann. Wenn der Helper später Daten aus diesem Segment in einem Shell-Befehl oder einer anderen sensiblen Operation verwendet, überschreitet das Segment eine Privilegiengrenze, selbst wenn die ausführbare Datei und ihre Dateien geschützt sind. `shmget()` übernimmt die Zugriffsberechtigungen aus den neun niederwertigen Bits seiner Flags; der Modus `0666` erlaubt anderen Benutzern das Schreiben, während ein `IPC_CREAT`-Flag diese Berechtigungen nicht einschränkt. Untersuchen Sie aktive Segmente passiv mit `ipcs -m` und korrelieren Sie deren Eigentümer, Modus und Lebensdauer mit dem privilegierten Prozess und dessen Eingabeverarbeitung. Ein für alle Benutzer beschreibbares Segment allein belegt keine Befehlsausführung.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

System-V-Segmente unterscheiden sich von POSIX-Shared-Memory-Dateien unter `/dev/shm`. Ein nur für kurze Zeit erstelltes Segment ist möglicherweise in einem einzelnen `ipcs`-Snapshot nicht vorhanden. Eine leere Ausgabe schließt daher nicht aus, dass ein Helper Shared Memory verwendet. Prüfen Sie dessen Quellcode oder Binärverhalten sowie jede `sudo`-Regel, die ihn startet. Rufen Sie den privilegierten Helper nicht allein deshalb auf, um während der Enumeration ein Segment erscheinen zu lassen. Die [IPC namespace guide](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) erklärt, wie Namespaces die Sichtbarkeit beeinflussen.<sup>[[2]](#references)[[3]](#references)</sup>

## Consul-Agent-Skriptprüfungen

Consul kann Skript-Health-Checks mit der Betriebssystemidentität seines Agents ausführen. Wenn ein Agent als root läuft, `enable_script_checks` aktiviert ist und ein Benutzer mit geringeren Rechten über die lokale HTTP-API einen Service mit einem Skript-Check registrieren darf, kann dieser Benutzer möglicherweise Befehle mit root-Rechten ausführen lassen. Auch wenn die API nur an `127.0.0.1` gebunden ist, können lokale Benutzer darauf zugreifen. Die Einstellung `enable_local_script_checks` ist restriktiver: Sie schließt Skript-Checks aus, die über HTTP-API-Registrierungen eingereicht werden. Wenn Consul-ACLs aktiviert sind, erfordert die Registrierung eines Services `service:write`; eine Zeile mit `acl.default_policy=allow` allein beweist nicht, dass ein anonymer Aufrufer Services registrieren kann. Prüfen Sie gemeinsam die tatsächliche Agent-Identität, die geladenen Einstellungen, die API-Bindung und die Autorisierung.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Folgen Sie den Argumenten `-config-dir` und `-config-file` des laufenden Agents zur relevanten Konfiguration und prüfen Sie ausschließlich die Feldnamen und Einstellungen für Script-Checks und ACLs. Konfigurationsdateien können auch Gossip-Schlüssel oder Tokens enthalten; vermeiden Sie es, diese in gemeinsam genutzte Logs einzufügen. Registrieren Sie keinen Service und führen Sie keinen Health-Check aus, nur um diesen Zustand aufzuzählen.

Ein separater Pfad über lokale Dateien besteht, wenn ein Benutzer mit geringeren Berechtigungen **Schreib- und Suchzugriff** auf das Verzeichnis hat, das mit `-config-dir` für einen als root laufenden Agent angegeben wurde: Eine neue Service-Definition im Format `.hcl` oder `.json` kann aus diesem Verzeichnis geladen werden. Mit Such- und Schreibzugriff auf ein Verzeichnis kann eine Datei hinzugefügt werden, selbst wenn das Auflisten des Verzeichnisses verweigert wird. Um eine Ausführung von Befehlen als root zu bestätigen, prüfen Sie, ob der Agent dieses Verzeichnis tatsächlich lädt, ob die **effektive** Einstellung für Script-Checks lokale Definitionen zulässt, ob die Definition geladen wird und ob der Agent seine root-Berechtigungen beibehält. In der [Consul-Dokumentation](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) wird beschrieben, welche Einstellungen und Health-Check-Definitionen neu geladen werden können; das Aktivieren von Script-Checks kann selbst einen Neustart erfordern. Prüfen Sie daher das Verhalten der installierten Version. Wenn ACLs den Agent schützen, erfordert [`consul reload` die Berechtigung `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); eine KV-Schreibberechtigung allein gewährt diese nicht. Betrachten Sie beschreibbare Verzeichnismetadaten als Anlass zur Prüfung, nicht als Beweis für einen autorisierten Reload, Neustart oder eine Befehlsausführung. Prüfen Sie Pfade, Berechtigungen und Richtlinien, ohne Konfiguration zu schreiben oder die API aufzurufen.

## Folgen Sie der Ausführungskette des Service

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Prüfe die Unit, Drop-ins, `EnvironmentFile=`, Hilfsskripte, relative Befehle, beschreibbare Verzeichnisse und Socket-Aktivierung. Eine root-eigene Unit kann trotzdem unsicher sein, wenn sie eine benutzerbeschreibbare Konfiguration oder ein entsprechendes Skript einliest. Die Seite [arbitrary file write](../interesting-files-permissions/write-to-root.md) behandelt gängige Missbrauchswege für Services und Units. Überwache kurzlebige Jobs mit [pspy](https://github.com/DominicBreuker/pspy) oder Audit-/Prozess-Telemetrie, wenn eine einmalige `ps`-Auflistung sie nicht erfasst.

Ordne bei einem benutzerdefinierten **xinetd**-Service die aktivierte Stanza mit den Angaben `server`, `user` und den Zugriffskontrollen dem aktiven Listener und der genauen ausführbaren Datei zu. Die [`user`-Einstellung](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) bestimmt die Identität des gestarteten Prozesses, während ein set-user-ID-Bit auf der ausführbaren Datei die effektive Identität separat ändern kann, wenn [`execve` diesen Übergang erlaubt](https://man7.org/linux/man-pages/man2/execve.2.html). Eine erreichbare privilegierte Binärdatei, die nicht vertrauenswürdige Eingaben akzeptiert, sollte Anlass für eine Offline-Prüfung des Quellcodes oder Disassemblats auf Memory-Safety-Fehler sein, etwa eine unbegrenzte [`scanf`-String-Konvertierung](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) in einen fest dimensionierten Puffer. Das Service-Mapping und die set-user-ID-Metadaten sind Hinweise, aber kein Beweis für einen solchen Fehler. Sende während der passiven Enumeration keine Crash-Eingaben und debugge den aktiven privilegierten Service nicht.

Prüfe bei einem benutzerdefinierten privilegierten Listener mit lesbarem Quellcode jede vom Aufrufer kontrollierte Länge, die bei einer Kopieroperation wie [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html) verwendet wird. Die Prüfung, ob der aktuelle Schreibindex innerhalb eines fest dimensionierten Puffers liegt, belegt nicht, dass die **Kopierlänge** in den verbleibenden Platz passt. Verifiziere `copy_length <= capacity - index`, nachdem du bestätigt hast, dass der Index im gültigen Bereich liegt, und prüfe Vorzeichen sowie arithmetischen Überlauf. Dieser Prüfhinweis gilt nur, wenn die Eingabe diese Operation erreicht, der Listener für den Benutzer mit niedrigeren Privilegien erreichbar ist und der Prozess eine höhere effektive Identität behält. Untersuche Quellcode und Prozessmetadaten offline; sende während der Enumeration keine Crash-Eingaben an den aktiven Service.

Auf Systemen mit **Upstart** können System-Jobdefinitionen unter `/etc/init/*.conf` liegen. Eine für den aktuellen Benutzer beschreibbare Jobdatei ist relevant, wenn der aktive Init-Daemon genau diesen Job lädt, dessen `script`- oder `exec`-Stanza mit einer höher privilegierten Identität ausgeführt wird und der Benutzer ihn über einen erlaubten `initctl`-Befehl oder einen anderen tatsächlichen Trigger starten kann. Eine sudo-Freigabe für `initctl` allein beweist weder, dass eine Jobdatei beschreibbar ist, noch dass ein geänderter Job ausgeführt wird. Prüfe die Berechtigungen der genauen Jobdatei, die effektive Run-as-Einstellung, den aktiven Daemon und den Trigger, ohne den Job während der Enumeration zu bearbeiten oder zu starten. Siehe die Handbücher zur [Upstart-Jobkonfiguration](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) und zu [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Eine lesbare Autologin-Passwortdatei, etwa `/etc/autologin/passwd` auf Systemen, deren [Boot-Job genau diesen Pfad einliest](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), ist ein Hinweis auf offengelegte Zugangsdaten. Bestätige, dass der Boot-Job installiert ist und die Datei verwendet, und prüfe anschließend separat, ob das Passwort für ein anderes lokales Konto oder einen Service gültig ist. Der Dateiname allein belegt keine Wiederverwendung des Passworts. Dokumentiere Pfad und Zugriffsmetadaten, ohne das Passwort in gemeinsam genutzte Enumeration-Ausgaben aufzunehmen.

`ExecStart=` einer Unit oder ein geplanter Befehl kann den genauen Pfad eines Skripts in einem nicht auflistbaren Verzeichnis offenlegen. Die [Suchberechtigung für Verzeichnisse](https://man7.org/linux/man-pages/man7/path_resolution.7.html) kann der aktuellen Identität dennoch erlauben, den bekannten Pfad zu durchlaufen. Prüfe die Suchberechtigung für jedes übergeordnete Verzeichnis und die Leseberechtigung für die Datei, statt anzunehmen, dass eine fehlgeschlagene Verzeichnisauflistung sie schützt. Ein lesbares Skript kann Zugangsdaten für eine Übertragung enthalten, aber ein Wechsel zu einem anderen Konto setzt voraus, dass diese Zugangsdaten noch gültig sind und dort unabhängig akzeptiert werden. Dokumentiere den Pfad und die Berechtigungsnachweise, ohne Geheimnisse in gemeinsam genutzte Logs auszugeben.

Prüfe bei einem geplanten CommonJS-Node.js-Skript auch einfache Imports wie `require('package')`, selbst wenn das Skript selbst schreibgeschützt ist. [Node sucht nach `node_modules` neben der importierenden Datei und anschließend in deren übergeordneten Verzeichnissen](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), bevor es auf konfigurierte globale Pfade zurückgreift. Ein Benutzer mit niedrigeren Privilegien, der eines dieser übergeordneten Verzeichnisse **beschreiben und durchsuchen** kann, kann möglicherweise ein Paket erstellen, das früher gefunden wird. Bestätige, dass der genaue Import erreicht wird, das ausgewählte Paket kein Built-in-Modul ist, der relevante Pfad erstellt oder geändert werden kann, das Modul dort in der installierten Runtime aufgelöst wird und ein höher privilegierter Job es bei einem künftigen Aufruf lädt. Beschreibbare Metadaten eines übergeordneten Verzeichnisses sind lediglich ein Prüfhinweis. Untersuche das Skript und den Scheduler passiv, ohne ein Modul abzulegen oder den Job auszulösen.

Ein privater Python-Paketindex ist eine weitere Vertrauensgrenze, wenn ein automatisierter Job Pakete unter einer anderen OS-Identität installiert. Ordne den genauen Job und das Run-as-Konto dem konfigurierten Index, den ausgewählten Paketnamen und der Frage zu, ob ein Benutzer mit niedrigeren Privilegien ein Paket veröffentlichen oder ersetzen kann, das der Job tatsächlich installieren wird. Beim Erstellen einer Source Distribution können deren Build-Backend oder das veraltete `setup.py` unter der Identität des Installationsprozesses ausgeführt werden; das Importieren des installierten Pakets ist ein separater Ausführungspfad. Ein Index-Listener, ein lesbarer Hash für ein Upload-Passwort oder ein Paketdateiname allein belegt diese Angriffskette nicht. Prüfe den Job, die Autorisierung des Index und die Herkunft des Pakets, ohne während der Enumeration etwas hochzuladen oder zu installieren. Siehe die [Build-System-Schnittstelle von pip](https://pip.pypa.io/en/stable/reference/build-system/) und die [Anleitung zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Ein privilegierter Agent kann eine von einem separaten Web-Service oder Container verwaltete Aufgabenwarteschlange abfragen. Wenn eine Identität mit geringerem Vertrauen die Aufgaben-Datenbank des Services beschreiben kann, ermittle, ob diese Zeilen dem Agent tatsächlich bereitgestellt werden und ob eine Command-Task mit der OS-Identität des Agents ausgeführt wird. Bestätige separat den Schreibzugriff auf die Datenbank, die Zielsitzung oder den Routing-Schlüssel, das aktive Polling, die Aufgabenautorisierung und den effektiven Benutzer des Agents. Root innerhalb eines Containers bedeutet nicht automatisch Host-Root-Zugriff. Die Grenze wird nur überschritten, wenn ein hostprivilegierter Consumer vom Angreifer kontrollierte Aufgabendaten ausführt. Prüfe Prozess-, Datenbankdatei- und Service-Metadaten, ohne die Warteschlange zu ändern oder während der Enumeration eine Aufgabe zu senden.

Ein wiederkehrender Job kann stattdessen einen Befehl aus einer Konfigurationszeile in einer Anwendungsdatenbank einlesen. Bestätige, dass die Datenbankrolle mit niedrigeren Privilegien genau diese Zeile ändern kann, dass der aktive Job sie nach der Änderung einliest und dass der Wert unter einer höheren OS-Identität an eine Shell oder einen entsprechenden Befehls-Runner übergeben wird. Schreibzugriff auf die Datenbank oder ein wie ein Befehl aussehender Wert belegt allein keine Ausführung. Untersuche den Job und die Berechtigungen, ohne die Zeile während der passiven Enumeration zu ändern.

Eine Warteschlangennachricht kann auch eine URL statt Code enthalten. Wenn ein privilegierter Consumer diese URL abruft und die Antwort als Lua- oder anderes ausführbares Plugin lädt, überprüfe die Veröffentlichungsberechtigung für den genauen Exchange und Routing Key, die Bindung an die konsumierte Queue, den Abruf- und Plugin-Ladepfad sowie die effektive Identität des Workers. [RabbitMQ leitet veröffentlichte Nachrichten über Exchanges weiter](https://www.rabbitmq.com/docs/exchanges). Ein Broker-Listener oder ein gültiger Login allein belegt nicht, dass die Nachricht diesem Worker zugestellt wird. Mitgeschnittene Klartext-Zugangsdaten für den Broker sind ein separater Hinweis, der tatsächlichen Zugriff auf Paketmitschnitte und lesbaren Traffic voraussetzt; sie belegen keine Veröffentlichungsberechtigung. Ein Lua-Plugin kann Shell-Befehle über [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute) aufrufen, aber nur, wenn diese API in seiner Runtime verfügbar ist. Prüfe Konfiguration und Code, ohne während der passiven Enumeration Traffic mitzuschneiden, Nachrichten zu veröffentlichen oder ein Plugin abzurufen.

Wenn ein privilegierter Python-Service einen lokalen HTTP- oder Socket-Endpunkt bereitstellt, kann ein lesbares Skript einen Pfad von Eingaben zu Code offenlegen, selbst wenn die Dateiberechtigungen eine Änderung verhindern. Ordne den aktiven Prozess und die Identität der Unit dem genauen Skript, Listener, der Routenautorisierung und den vom Aufrufer kontrollierten Feldern zu. Verfolge anschließend diese Felder durch Parsing und Validierung bis zu einem dynamischen `eval()`- oder `exec()`-Sink. Insbesondere kann das Erstellen eines neuen f-Strings aus Request-Text und dessen Auswertung vom Angreifer bereitgestellte Ersetzungsfelder als Python-Ausdrücke interpretieren ([Python-Warnung zu `eval`](https://docs.python.org/3/library/functions.html#eval); [Semantik von f-Strings](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Ein einfacher `eval`-Treffer oder eine Loopback-Bindung beweist nicht, dass eine nicht vertrauenswürdige Person den Sink erreicht. Prüfe den tatsächlichen Datenfluss und die Zugriffskontrollen, ohne während der Enumeration eine Test-Payload zu senden.

Ein Gate für signierte Requests auf dieser Route muss separat geprüft werden. Wenn lesbarer Quellcode den Signierschlüssel nachweislich aus einem sehr kleinen oder vorhersagbaren Ausgaberaum ableitet und der Service ein gültig signiertes Beispiel offenlegt, schützt die Signatur einen privilegierten `eval()`-Sink möglicherweise nicht mehr. Verifiziere die genaue Schlüsselableitung und den Verifier, die Identität des aktiven Services und den lokalen Zugriff des Aufrufers sowie, ob das signierte Feld den Sink erreicht. Ein Import von Pythons [`random`-Modul](https://docs.python.org/3/library/random.html) oder eine Beispielsignatur belegt keine dieser Bedingungen. Python warnt außerdem, dass die Einschränkung von `__builtins__` [keine Sicherheitsgrenze für nicht vertrauenswürdige `eval()`-Eingaben ist](https://docs.python.org/3/library/functions.html#eval). Analysiere Schlüssel offline und übermittle während der passiven Enumeration keine gefälschten Requests.

Ein leeres, aber beschreibbares Verzeichnis `/etc/systemd/system/<unit>.service.d` ist relevant, selbst wenn die Unit-Datei und alle vorhandenen Drop-ins geschützt sind: Der Benutzer kann möglicherweise eine neue `.conf`-Override-Datei erstellen. Prüfe, ob das Verzeichnis für die aktuelle Identität beschreibbar und durchsuchbar ist, ob die Unit geladen ist und als root ausgeführt wird und ob ein Daemon-Reload mit anschließendem Neustart stattfindet. Eine Reload- oder Neustartberechtigung, ein Timer oder ein späterer Systemstart kann die Änderung wirksam machen. Schreibzugriff auf das Verzeichnis allein führt sie nicht sofort aus.

Verfolge bei laufenden Services die literalen `EnvironmentFile=`-Pfade aus dem Abschnitt `[Service]` der Unit, auch wenn die Dateinamen nicht mit `.env` beginnen. Wenn ein Benutzer mit niedrigen Privilegien eine Datei lesen kann, liste schlüsselähnliche Namen wie `API_TOKEN` oder `APP_SECRET_KEY` auf, ohne die Werte in gemeinsam genutzte Logs auszugeben. Berücksichtige bei der Beurteilung der effektiven Unit Drop-in-Overrides und optionale `-`-Präfixe. Lesbarkeit ist ein Hinweis auf offengelegte Zugangsdaten. Der Wert muss jedoch weiterhin für eine privilegierte Aktion gültig sein, damit er eine Rechteausweitung ermöglicht.

### Privilegierte Verarbeitung nicht vertrauenswürdiger Uploads

Ein als root laufender File-Watcher kann Dateien aus einem benutzerbeschreibbaren Upload-Verzeichnis an einen kurzlebigen Parser oder Extractor übergeben. Verfolge das übergeordnete Skript oder den Service des laufenden Watchers und bestätige das genaue Verzeichnis, wer dort Dateien ablegen kann, den Child-Befehl samt Argumenten und die Identität, unter der der Child-Prozess läuft. Ein Prozess-Snapshot kann den Watcher zeigen, aber den Extractor zwischen Uploads verpassen. Lege während der passiven Enumeration keine Test-Payload ab und löse den Watcher nicht aus.

Ein konkretes Beispiel ist der Extraktionsmodus (`-e`) von Binwalk, der vom Angreifer kontrollierte PFS-Daten verarbeitet. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) ermöglichte es dem PFS-Extractor, außerhalb des vorgesehenen Verzeichnisses zu schreiben, auch in einen Plugin-Pfad, den Binwalk später laden konnte. Upstream nahm die Korrektur in [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4) auf, aber Backports von Distributionen können eine ältere angezeigte Version beibehalten. Prüfe daher vor der Bewertung der Anwendbarkeit den Sicherheitsstatus des installierten Pakets, beispielsweise im [Debian-Tracker](https://security-tracker.debian.org/tracker/CVE-2022-4510). Eine installierte Binwalk-Version allein belegt keinen Pfad zur Rechteausweitung: Die Extraktion muss tatsächlich von einem privilegierteren Prozess für Eingaben ausgeführt werden, die der Benutzer mit niedrigeren Privilegien kontrollieren kann.

### Geplante Builds mit lokalen Dependencies

Ein geplantes `cargo run` kompiliert den Quellcode erneut unter dem Run-as-Benutzer des Jobs. Prüfe die lokalen `{ path = "..." }`-Dependencies im Manifest sowie Quellcode- und Verzeichnisberechtigungen jeder Dependency, nicht nur die des Haupt-Crates. Wenn ein Benutzer mit niedrigeren Privilegien eine Dependency ändern kann, die Cargo kompiliert, und der geplante Job das Ergebnis ausführt, kann der kompilierte Code als dieser Run-as-Benutzer laufen. Bestätige den effektiven Scheduler-Befehl, das Arbeitsverzeichnis, die Dependency-Auflösung und ob eine Neukompilierung erfolgt. Eine beschreibbare Rust-Quelldatei an anderer Stelle ist lediglich ein Hinweis. Das Lesen des Manifests und der Pfadmetadaten reicht für eine passive Triage aus. Siehe die [Cargo-Dokumentation zu Path-Dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Xvfb-Framebuffer-Dateien

`Xvfb -fbdir <directory>` verwendet Memory-Mapped-Dateien mit den Namen `Xvfb_screen<n>` für seine virtuellen Bildschirme. Wenn der laufende Xvfb-Prozess eines anderen Benutzers ein Verzeichnis angibt, dessen Bildschirmdateien für den aktuellen Benutzer lesbar sind, kann der Framebuffer Desktop-Inhalte dieses Benutzers offenlegen. Bestätige Prozess, Dateieigentümer und Berechtigungen gemeinsam. Eine lesbare Datei allein beweist nicht, dass nützliche Inhalte auf dem Bildschirm angezeigt werden. Prüfe zunächst Pfade und Metadaten, ohne Bilddaten in gemeinsam genutzte Enumeration-Ausgaben zu kopieren. Das [Xvfb-Handbuch](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html) dokumentiert das Verhalten von `-fbdir`.

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
