# Перелік процесів і шляхи служб

{{#include ../../banners/hacktricks-training.md}}

Корисно з’ясувати, який привілейований процес використовує дані або код, на які може впливати користувач із нижчими привілеями. Перевірте дерево процесів, активне середовище, відкриті файли, а також unit або скрипт, який запустив кожен із процесів-кандидатів.

## Визначення процесів і власників

```bash
ps -eo user,pid,ppid,tty,comm,args --sort=ppid
pstree -alp 2>/dev/null
systemctl list-units --type=service --state=running 2>/dev/null
ss -lntup
```

Міжкористувацький зв'язок батьківського та дочірнього процесів може бути нормальним, але неочікуваний перехід потребує перевірки команди батьківського процесу, аргументів, виконуваного файла, робочого каталогу та згаданих файлів. Щоб визначити власника та контекст входу, скористайтеся розділом [користувачі та сеанси](../user-information/user-and-session-triage.md).

### Локальні консолі віртуальних машин

Перевірте параметри `-spice` процесу QEMU разом з адресою, на якій він прослуховує з'єднання. [Документація QEMU](https://www.qemu.org/docs/master/system/qemu-manpage.html) зазначає, що `disable-ticketing` дає змогу клієнтам SPICE підключатися без автентифікації. Навіть якщо слухач прив'язаний до loopback, інші локальні користувачі хоста потенційно можуть до нього звернутися. Перш ніж вважати командний рядок ознакою доступної консолі, перевірте активний слухач, параметри автентифікації та локальний доступ. Керування консоллю впливає на **гостьову систему**; отримання облікового запису гостя або зміна стану її завантаження потребує окремих умов на гостьовій системі й не надає root-доступу до хоста віртуалізації. Під час пасивного переліку переглядайте аргументи процесу та метадані сокета, не підключаючись до гостьової системи й не перезавантажуючи її.

Локально доступний вебінтерфейс може виконувати код з обліковим записом служби, навіть якщо початкова оболонка не має доступу до файлів цього облікового запису. Наприклад, CVE-2023-0297 стосувалася обробки `/flash/addcrypted2` у pyLoad: недовірений JavaScript потрапляв до Js2Py, де імпорт Python був увімкнений; [виправлення в upstream](https://github.com/pyload/pyload/commit/7d73ba7919e594d783b3411d7ddb87885aea782d) вимкнуло `pyimport`. Перш ніж вважати процес pyLoad шляхом ескалації привілеїв, зіставте власника запущеного процесу, адресу прослуховування, доступність кінцевої точки та встановлене виправлення або бекпорт від постачальника. Самі по собі назва процесу, відкритий порт або версія пакета не доводять наявності вразливості; під час пасивного переліку не надсилайте payload для виконання коду.

### Привілейовані оболонки входу зі спільним терміналом

Привілейована інтерактивна оболонка, яка запускає `su --login <user>` без окремого псевдотермінала, може залишити термінал спільним з оболонкою входу користувача з нижчими привілеями. Якщо файл запуску цього користувача можна змінити, а код у ньому може використовувати `TIOCSTI` для введення даних у термінал, ці дані можуть потрапити до привілейованої оболонки після її відновлення. [Посібник util-linux для `su`](https://man7.org/linux/man-pages/man1/su.1.html#SECURITY_NOTES) описує ризик спільного термінала й рекомендує використовувати `su --pty`/`-P` для інтерактивної роботи; `su -c` запускає окремий сеанс без керівного термінала. Ризик залежить від фактичної батьківської оболонки, зв'язку з терміналом, цільового файла запуску та політики ядра. Одна лише назва процесу чи аргумент `su -l` — лише привід для перевірки.

Перегляньте спостережуване дерево процесів і стовпці TTY, а потім доступний для читання launcher і власника/дозволи файла запуску. У Linux `/proc/sys/dev/tty/legacy_tiocsti`, якщо він є, допоможе визначити політику; його відсутність не доводить безпечність. [Посібник Linux для `TIOCSTI`](https://man7.org/linux/man-pages/man2/TIOCSTI.2const.html) зазначає, що починаючи з Linux 6.2 для цієї операції може вимагатися `CAP_SYS_ADMIN`, якщо цей sysctl має значення false. Не викликайте ioctl лише для переліку даних про хост.

Іноді обліковий запис бази даних може змінити файл запуску цільового користувача без прямого доступу на запис до файлової системи. Серверна команда PostgreSQL `COPY ... TO 'filename'` записує файл від імені облікового запису ОС сервера бази даних, але [обмеження PostgreSQL](https://www.postgresql.org/docs/current/sql-copy.html) дозволяють такий варіант лише суперкористувачам бази даних або ролям на кшталт `pg_write_server_files`. Перевірте і роль бази даних, і дозволи ОС сервера на файл; сам рядок підключення застосунку не надає права запису у файл. Під час оцінювання цього ланцюжка розглядайте можливості привілейованого launcher і облікового запису бази даних окремо.

## Перевірте артефакти виконання

```bash
readlink /proc/<PID>/exe
tr '\0' ' ' </proc/<PID>/cmdline; echo
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Видалені виконувані файли та видалені, але відкриті файли залишаються доступними за посиланнями, доки не буде закрито останній дескриптор. Вони можуть зберігати докази або доступні секрети. Середовища процесів і пам’ять можуть містити облікові дані, але читання даних іншого процесу обмежують власник, параметри монтування `/proc`, політика Yama ptrace та інші засоби безпеки. Пов’язані методи описано в розділах [дескриптори файлів](../main-system-information/filesystem-links-and-file-descriptors.md) і [пошук облікових даних після експлуатації](../post-exploitation/README.md).

Збережені трасування системних викликів також підпадають під обмеження дозволів файлів. [`strace` записує аргументи системних викликів у вихідний файл](https://man7.org/linux/man-pages/man1/strace.1.html), тому доступне для читання трасування аргументів [`execve`](https://man7.org/linux/man-pages/man2/execve.2.html) може розкрити пароль, переданий привілейованим завданням у командному рядку. Спершу з’ясуйте, чи може поточний користувач прочитати конкретне трасування та чи справді аргумент містить облікові дані; окремо потрібно довести, що облікові дані приймаються під час подальшого переходу до іншого облікового запису Unix. Метадані файлів — корисна пасивна зачіпка, яка дає змогу не сканувати кожне трасування й не виводити його вміст під час звичайного переліку.

## Сокети привілейованої автоматизації офісних програм

LibreOffice і OpenOffice можуть надавати доступ до свого UNO API через аргумент `--accept=socket,host=<host>,port=<port>;urp;`. Процес офісної програми, запущений від root і доступний через кінцеву точку, може дозволити локальному користувачеві з нижчими привілеями викликати служби API в контексті безпеки цього процесу. Служба `SystemShellExecute` має операцію для запуску системної команди. Прив’язка до loopback обмежує віддалений доступ, але сокет і далі доступний локальним користувачам, якщо цьому не перешкоджають інші засоби контролю.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
ps -eo user,args | grep -E '[s]office|[l]ibreoffice|[o]penoffice'
ss -ltn 2>/dev/null
```

Зіставте власника процесу, точний аргумент `--accept`, а також поточну адресу й порт, на яких він прослуховує з’єднання. Налаштований acceptor, якому не вдалося прив’язатися до адреси, — це лише зачіпка; під час пасивного переліку не підключайтеся до API й не викликайте його. Не запускайте привілейований екземпляр офісного застосунку лише для перевірки цієї умови.

## System V shared memory, яку використовують привілейовані процеси

Допоміжна програма, що належить root, може створити сегмент System V shared memory, у який може записувати інший користувач. Якщо згодом допоміжна програма довіряє даним із цього сегмента під час виконання shell-команди чи іншої чутливої операції, сегмент перетинає межу привілеїв, навіть якщо виконуваний файл і його файли захищені. `shmget()` бере дозволи доступу з молодших дев’яти бітів своїх прапорців; режим `0666` дозволяє іншим користувачам записувати дані, тоді як прапорець `IPC_CREAT` не звужує ці дозволи. Пасивно перевірте активні сегменти командою `ipcs -m` і зіставте їхнього власника, режим і час життя з привілейованим процесом та його обробкою вхідних даних. Сам по собі сегмент із правом запису для всіх не свідчить про можливість виконання команд.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
ipcs -m
```

Сегменти System V відрізняються від файлів спільної пам’яті POSIX у `/dev/shm`. Сегмент, створений лише на мить, може бути відсутнім в окремому знімку `ipcs`, тому порожній вивід не виключає, що допоміжна програма використовує спільну пам’ять. Перевірте її вихідний код або поведінку бінарного файла, а також будь-яке правило `sudo`, яке її запускає; не запускайте привілейовану допоміжну програму лише для того, щоб сегмент з’явився під час переліку. У [посібнику з IPC namespace](../containers-namespaces/container-security/protections/namespaces/ipc-namespace.md) пояснюється, як namespaces впливають на видимість.<sup>[[2]](#references)[[3]](#references)</sup>

## Перевірки Consul agent за допомогою скриптів

Consul може запускати скрипти перевірки стану з ідентичністю операційної системи свого agent. Якщо agent працює від root, увімкнено `enable_script_checks`, а користувач із нижчим рівнем привілеїв може зареєструвати сервіс зі скриптовою перевіркою через локальний HTTP API, цей користувач може спричинити виконання команд від root. Прив’язка API лише до `127.0.0.1` усе одно дає змогу локальним користувачам звертатися до нього. Налаштування `enable_local_script_checks` має вужчу дію: воно не допускає скриптові перевірки, передані через реєстрацію в HTTP API. Коли ввімкнено Consul ACLs, для реєстрації сервісу потрібен `service:write`; сам рядок `acl.default_policy=allow` не доводить, що анонімний клієнт може зареєструвати сервіс. Перевіряйте фактичну ідентичність agent, завантажені налаштування, прив’язку API та авторизацію в сукупності.<sup>[[4]](#references)[[5]](#references)[[6]](#references)</sup>

```bash
ps -eo user,args | grep '[c]onsul agent'
ls -l /etc/consul.d 2>/dev/null
```

Перейдіть за аргументами `-config-dir` і `-config-file` запущеного agent до відповідної конфігурації та перевірте лише назви й налаштування полів script-check і ACL. Файли конфігурації також можуть містити ключі чи токени gossip; не вставляйте їх у спільні журнали. Не реєструйте сервіс і не запускайте health check лише для виявлення цієї умови.

Окремий шлях через локальний файл можливий, якщо користувач із нижчими привілеями може **записувати в каталог** і **шукати в ньому**, а цей каталог указано в `-config-dir` agent, запущеного від root: звідти може завантажитися нове визначення сервісу `.hcl` або `.json`. Право шукати в каталозі й записувати до нього може дозволити додати файл, навіть якщо переглядати вміст каталогу заборонено. Щоб підтвердити можливість виконання команд від root, перевірте, що agent справді завантажує цей каталог, його **ефективне** налаштування script-check дозволяє локальні визначення, визначення завантажено, а agent зберігає привілеї root. У [документації Consul](https://developer.hashicorp.com/consul/docs/fundamentals/agent#reloadable-configurations) зазначено, які налаштування й визначення health check можна перезавантажити; для ввімкнення script checks може знадобитися перезапуск, тож перевірте поведінку встановленої версії. Якщо agent захищено ACL, [`consul reload` потребує `agent:write`](https://developer.hashicorp.com/consul/api-docs/agent#reload-agent); самого дозволу на запис у KV недостатньо. Розглядайте можливість змінювати метадані каталогу лише як привід для перевірки, а не як доказ того, що дозволено перезавантаження, перезапуск або виконання команд. Перевірте шляхи, дозволи й політику, не записуючи конфігурацію й не викликаючи API.

## Простежте ланцюжок виконання сервісу

```bash
systemctl cat <unit>.service
systemctl show <unit>.service -p User -p Group -p ExecStart -p EnvironmentFiles -p WorkingDirectory
namei -l /path/from/ExecStart
```

Перевірте unit, drop-ins, `EnvironmentFile=`, допоміжні скрипти, відносні команди, каталоги з правом запису та socket activation. Навіть unit, власником якого є root, може бути небезпечним, якщо він читає конфігурацію чи скрипт, доступні користувачу для запису. На сторінці про [arbitrary file write](../interesting-files-permissions/write-to-root.md) описані поширені шляхи зловживання сервісами та unit-файлами. Відстежуйте короткочасні завдання за допомогою [pspy](https://github.com/DominicBreuker/pspy) або телеметрії аудиту/процесів, якщо одноразовий список `ps` їх не виявляє.

Для власного сервісу **xinetd** зіставте активний stanza `server`, `user` і правила контролю доступу з активним listener та точним виконуваним файлом. Налаштування [`user`](https://manpages.debian.org/testing/xinetd/xinetd.conf.5.en.html) визначає ідентичність запущеного процесу, тоді як set-user-ID bit на виконуваному файлі може окремо змінити його ефективну ідентичність, якщо [`execve` дозволяє такий перехід](https://man7.org/linux/man-pages/man2/execve.2.html). Доступний привілейований binary, що приймає недовірені дані, варто перевірити офлайн за вихідним кодом або дизасемблюванням на помилки безпеки пам’яті, наприклад необмежене перетворення рядка [`scanf`](https://www.gnu.org/software/libc/manual/html_node/String-Input-Conversions.html) у буфер фіксованого розміру. Відповідність сервісу та метадані set-user-ID — це підказки для перевірки, а не доказ наявності такої помилки; не надсилайте дані, що спричиняють збій, і не налагоджуйте активний привілейований сервіс під час пасивного переліку.

Для власного привілейованого listener із доступним для читання вихідним кодом перевірте кожну довжину, контрольовану викликачем, яка використовується операцією копіювання на кшталт [`memcpy`](https://man7.org/linux/man-pages/man3/memcpy.3.html). Перевірка лише того, що поточний індекс запису перебуває в межах буфера фіксованого розміру, не гарантує, що **довжина копіювання** вміщується в доступний залишок; переконайтеся, що `copy_length <= capacity - index`, після перевірки індексу на вихід за межі, а також перевірте знаковість і арифметичне переповнення. Це лише підказка для аналізу, якщо дані доходять до цієї операції, listener доступний користувачу з нижчими привілеями, а процес зберігає вищу ефективну ідентичність. Перевіряйте вихідний код і метадані процесу офлайн; не надсилайте дані, що спричиняють збій, активному сервісу під час переліку.

У системах, що використовують **Upstart**, визначення системних завдань можуть міститися в `/etc/init/*.conf`. Файл завдання, доступний поточному користувачу для запису, має значення, якщо активний демон init завантажує саме це завдання, його stanza `script` або `exec` запускається з вищими привілеями, а користувач може запустити його за допомогою дозволеної команди `initctl` або іншого реального тригера. Сам дозвіл `sudo initctl` не доводить, що якийсь файл завдання доступний для запису або що змінене завдання запуститься. Перевірте права саме на цей файл завдання, ефективне налаштування run-as, активний демон і тригер, не змінюючи та не запускаючи завдання під час переліку. Див. посібники з [налаштування завдань Upstart](https://manpages.ubuntu.com/manpages/trusty/man5/init.5.html) і [`initctl`](https://manpages.ubuntu.com/manpages/xenial/man8/initctl.8.html).

Доступний для читання файл пароля autologin, наприклад `/etc/autologin/passwd` у системах, де [завантажувальне завдання читає саме цей шлях](https://chromium.googlesource.com/chromiumos/overlays/chromiumos-overlay/+/master/chromeos-base/autologin/files/init/autologin.conf), вказує на можливе розкриття облікових даних. Переконайтеся, що завантажувальне завдання встановлене й використовує цей файл, а потім окремо перевірте, чи дійсний пароль для іншого локального облікового запису або сервісу. Саме ім’я файлу не доводить повторне використання пароля; зафіксуйте шлях і метадані доступу, не вносячи пароль у спільні результати переліку.

`ExecStart=` unit-файлу або запланована команда можуть розкрити точний шлях до скрипту в каталозі, вміст якого не можна переглянути списком. [Право пошуку в каталозі](https://man7.org/linux/man-pages/man7/path_resolution.7.html) усе ще може дозволити поточній ідентичності пройти за відомим шляхом; перевірте доступ на пошук у кожному батьківському каталозі й право читання файлу, а не припускайте, що невдалий перегляд списку каталогу захищає його. Скрипт, доступний для читання, може містити облікові дані для передавання, але перехід до іншого облікового запису можливий лише за умови, що ці облікові дані залишаються дійсними та приймаються там окремо. Зафіксуйте шлях і докази наявності прав, не виводячи секретні значення у спільні журнали.

Для запланованого скрипту CommonJS Node.js перевірте імпорти без шляху, як-от `require('package')`, навіть якщо сам скрипт доступний лише для читання. [Node шукає `node_modules` поруч із файлом, що виконує імпорт, а потім у батьківських каталогах](https://nodejs.org/api/modules.html#loading-from-node_modules-folders), перш ніж переходити до налаштованих глобальних шляхів. Користувач із нижчим рівнем привілеїв, який може **записувати й шукати** в одному з таких батьківських каталогів, може створити пакет, що відповідатиме раніше за інші. Переконайтеся, що конкретний імпорт виконується, вибраний пакет не є вбудованим модулем, відповідний шлях можна створити або змінити, модуль у встановленому runtime розв’язується за цим шляхом, а завдання з вищими привілеями завантажить його під час наступного запуску. Метадані про права запису в батьківському каталозі — лише підказка для перевірки; досліджуйте скрипт і планувальник пасивно, не розміщуючи модуль і не запускаючи завдання.

Приватний індекс пакетів Python — ще одна межа довіри, якщо автоматизоване завдання встановлює пакети під іншою ідентичністю ОС. Зіставте конкретне завдання й обліковий запис run-as із налаштованим індексом, вибраними іменами пакетів і можливістю користувача з нижчим рівнем привілеїв опублікувати або підмінити пакет, який завдання справді встановить. Створення source distribution може запускати build backend або застарілий `setup.py` з ідентичністю інсталятора; імпорт установленого пакета — окремий шлях виконання. Listener індексу, доступний для читання хеш пароля завантаження або саме ім’я файлу пакета не доводять наявність такого ланцюжка. Перевіряйте завдання, авторизацію індексу та походження пакета, нічого не завантажуючи й не встановлюючи під час переліку. Див. [інтерфейс системи збирання pip](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Привілейований agent може опитувати чергу завдань, якою керує окремий вебсервіс або container. Якщо менш довірена ідентичність може записувати в базу даних завдань сервісу, з’ясуйте, чи справді ці рядки доступні цьому agent і чи виконується command task з ідентичністю ОС agent. Окремо перевірте право запису в базу даних, цільову сесію або routing key, активне опитування, авторизацію завдання та ефективного користувача agent. Root усередині container сам по собі не означає доступу як root на host; межа перетинається лише тоді, коли споживач із привілеями host виконує контрольовані зловмисником дані завдання. Перевіряйте метадані процесів, файлу бази даних і сервісу, не змінюючи чергу й не надсилаючи завдання під час переліку.

Натомість періодичне завдання може читати команду з рядка конфігурації бази даних застосунку. Переконайтеся, що роль бази даних із нижчим рівнем привілеїв може змінити саме цей рядок, активне завдання читає його після зміни, а значення передається до shell або еквівалентного виконавця команд з ідентичністю ОС із вищими привілеями. Сам доступ на запис у базу даних або значення, схоже на команду, не доводять виконання; досліджуйте завдання й дозволи, не змінюючи рядок під час пасивного переліку.

Повідомлення в черзі може містити URL, а не код. Якщо привілейований споживач отримує дані за цим URL і завантажує відповідь як Lua або інший виконуваний plugin, перевірте права видавця на конкретний exchange і routing key, прив’язку до черги, яку споживають, шлях отримання й завантаження plugin та ефективну ідентичність worker. [RabbitMQ маршрутизує опубліковані повідомлення через exchanges](https://www.rabbitmq.com/docs/exchanges); сам listener брокера або дійсний логін не доводять доставку цьому worker. Перехоплені облікові дані брокера у відкритому вигляді — окрема підказка, що потребує фактичного доступу до захоплення пакетів і трафіку, доступного для читання; вони не доводять права публікації. Lua plugin може викликати shell-команди через [`os.execute`](https://www.lua.org/manual/5.4/manual.html#pdf-os.execute), лише якщо цей API доступний у його runtime. Перевіряйте конфігурацію й код, не захоплюючи трафік, не публікуючи повідомлень і не отримуючи plugin під час пасивного переліку.

Якщо привілейований сервіс Python надає локальну HTTP- або socket-точку доступу, скрипт, доступний для читання, може розкрити шлях від вхідних даних до виконання коду, навіть якщо права на файл не дозволяють його змінити. Зіставте активний процес та ідентичність unit із конкретним скриптом, listener, авторизацією маршрутів і полями, контрольованими викликачем. Потім простежте ці поля через парсинг і перевірку до динамічного sink `eval()` або `exec()`. Зокрема, створення нового f-string із тексту запиту та його обчислення може інтерпретувати контрольовані зловмисником поля підстановки як вирази Python ([попередження Python щодо `eval`](https://docs.python.org/3/library/functions.html#eval); [семантика f-string](https://docs.python.org/3/reference/lexical_analysis.html#f-strings)). Сам збіг `eval` або прив’язка до loopback не доводять, що недовірений викликач може дійти до sink; перевірте фактичний потік даних і контролі доступу, не надсилаючи тестове навантаження під час переліку.

Окремо перевірте gate підписаних запитів на цьому маршруті. Якщо доступний для читання вихідний код показує, що ключ підпису отримується з очевидно малого або передбачуваного простору значень, а сервіс надає коректний підписаний приклад, підпис може більше не захищати привілейований sink `eval()`. Перевірте точний спосіб отримання ключа й verifier, ідентичність активного сервісу та доступ локальних викликачів, а також те, чи потрапляє підписане поле до sink; сам імпорт модуля Python [`random`](https://docs.python.org/3/library/random.html) або приклад підпису не доводить жодної з цих умов. Python також попереджає, що обмеження `__builtins__` [не є межею безпеки для недовірених даних `eval()`](https://docs.python.org/3/library/functions.html#eval). Аналізуйте ключ офлайн і не надсилайте підроблені запити під час пасивного переліку.

Порожній каталог `/etc/systemd/system/<unit>.service.d` із правом запису має значення, навіть якщо файл unit і всі наявні drop-in захищені: користувач може створити нове перевизначення `.conf`. Перевірте, чи має поточна ідентичність право запису й пошуку в каталозі, чи завантажений unit і чи запускається він як root, а також чи відбудеться перезавантаження демона з подальшим перезапуском. Дозвіл на перезавантаження або перезапуск, timer чи наступне завантаження системи можуть активувати зміну; самого права запису в каталог недостатньо для негайного виконання.

Для запущених сервісів перевіряйте буквальні шляхи `EnvironmentFile=` із секції `[Service]` unit-файлу, зокрема файли, чиї імена не починаються з `.env`. Якщо користувач із низькими привілеями може прочитати такий файл, перелічіть схожі на облікові дані назви ключів, наприклад `API_TOKEN` або `APP_SECRET_KEY`, не виводячи значення у спільні журнали. Перевіряючи ефективний unit, враховуйте drop-in-перевизначення й необов’язкові префікси `-`. Можливість читання вказує на потенційне розкриття облікових даних; для ескалації потрібна також дійсність значення для привілейованої дії.

### Привілейована обробка недовірених завантажень

Запущений від root file watcher може передавати файли з каталогу завантажень, доступного користувачам для запису, короткочасному parser або extractor. Перевірте батьківський скрипт або сервіс запущеного watcher і з’ясуйте точний каталог, хто може розміщувати там файли, дочірню команду та її аргументи, а також ідентичність, з якою запускається дочірній процес. Знімок процесів може показати watcher, але не extractor, запущений між завантаженнями. Не розміщуйте тестове навантаження й не запускайте watcher під час пасивного переліку.

Конкретний приклад — режим розпакування Binwalk (`-e`), що обробляє контрольовані зловмисником дані PFS. [CVE-2022-4510](https://github.com/ReFirmLabs/binwalk/pull/617) дозволяла PFS extractor записувати дані поза призначеним каталогом, зокрема за шляхом plugin, який Binwalk міг пізніше завантажити. Upstream включив виправлення у версію [2.3.4](https://github.com/ReFirmLabs/binwalk/releases/tag/v2.3.4), але дистрибутивні backport можуть зберігати старішу відображувану версію; перш ніж оцінювати застосовність, перевірте статус безпеки встановленого пакета, наприклад у [трекері Debian](https://security-tracker.debian.org/tracker/CVE-2022-4510). Сам факт встановлення певної версії Binwalk не доводить наявність шляху ескалації привілеїв: розпакування має справді запускатися процесом із вищими привілеями на даних, контрольованих користувачем із нижчими привілеями.

### Заплановані збирання з локальними залежностями

Запланована команда `cargo run` повторно компілює вихідний код з ідентичністю користувача, під якою запускається завдання. Перевірте локальні залежності `{ path = "..." }` у manifest, а також права на вихідний код і батьківські каталоги кожної залежності, а не лише основного crate. Якщо користувач із нижчим рівнем привілеїв може змінити залежність, яку Cargo компілює, і заплановане завдання запускає результат, скомпільований код може виконуватися з ідентичністю run-as. Перевірте ефективну команду планувальника, робочий каталог, розв’язання залежностей і те, чи відбудеться повторне збирання; файл вихідного коду Rust, доступний для запису в іншому місці, — лише підказка. Для пасивної первинної перевірки достатньо прочитати manifest і метадані шляхів. Див. [документацію Cargo щодо залежностей за шляхом](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-path-dependencies).

## Файли framebuffer Xvfb

`Xvfb -fbdir <directory>` використовує файли, зіставлені в пам’ять і названі `Xvfb_screen<n>`, для своїх віртуальних екранів. Якщо запущений процес Xvfb іншого користувача вказує на каталог, файли екрана в якому доступні поточному користувачу для читання, framebuffer може розкрити вміст робочого столу цього користувача. Перевірте процес, власника файлу та права доступу разом; сам факт можливості прочитати файл не доводить, що на екрані є корисний вміст. Спочатку перевірте шляхи й метадані, не копіюючи дані зображення у спільні результати переліку. Поведінку `-fbdir` описано в [посібнику Xvfb](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man1/Xvfb.1.html).

```bash
pgrep -a -x Xvfb
ls -l /path/from/-fbdir/Xvfb_screen*
```
