# Container Runtimes, Engines, Builders, And Sandboxes

{{#include ../../../banners/hacktricks-training.md}}

Μία από τις μεγαλύτερες πηγές σύγχυσης στην ασφάλεια των containers είναι ότι αρκετά εντελώς διαφορετικά στοιχεία συχνά συγχωνεύονται κάτω από τον ίδιο όρο. Το «Docker» μπορεί να αναφέρεται σε format image, CLI, daemon, build system, runtime stack ή απλώς στη γενική έννοια των containers. Στις εργασίες ασφάλειας, αυτή η ασάφεια αποτελεί πρόβλημα, επειδή διαφορετικά επίπεδα είναι υπεύθυνα για διαφορετικές προστασίες. Ένα breakout που οφείλεται σε κακό bind mount δεν είναι το ίδιο με ένα breakout που οφείλεται σε bug χαμηλού επιπέδου στο runtime, και κανένα από τα δύο δεν είναι το ίδιο με ένα λάθος στην πολιτική cluster του Kubernetes.

Αυτή η σελίδα διαχωρίζει το οικοσύστημα ανά ρόλο, ώστε η υπόλοιπη ενότητα να μπορεί να αναφέρεται με ακρίβεια στο επίπεδο όπου βρίσκεται κάθε προστασία ή αδυναμία.

## OCI As The Common Language

Τα σύγχρονα Linux container stacks συχνά συνεργάζονται επειδή χρησιμοποιούν ένα σύνολο προδιαγραφών OCI. Το **OCI Image Specification** περιγράφει τον τρόπο αναπαράστασης των images και των layers. Το **OCI Runtime Specification** περιγράφει πώς πρέπει το runtime να εκκινεί τη διεργασία, συμπεριλαμβανομένων των namespaces, των mounts, των cgroups και των ρυθμίσεων ασφάλειας. Το **OCI Distribution Specification** τυποποιεί τον τρόπο με τον οποίο τα registries διαθέτουν περιεχόμενο.

Αυτό έχει σημασία επειδή εξηγεί γιατί ένα container image που δημιουργήθηκε με ένα εργαλείο μπορεί συχνά να εκτελεστεί με κάποιο άλλο, καθώς και γιατί πολλά engines μπορούν να χρησιμοποιούν το ίδιο runtime χαμηλού επιπέδου. Εξηγεί επίσης γιατί η συμπεριφορά ασφάλειας μπορεί να φαίνεται παρόμοια σε διαφορετικά προϊόντα: πολλά από αυτά δημιουργούν την ίδια διαμόρφωση OCI runtime και τη μεταβιβάζουν στο ίδιο μικρό σύνολο runtimes.

## Low-Level OCI Runtimes

Το runtime χαμηλού επιπέδου είναι το στοιχείο που βρίσκεται πιο κοντά στο όριο του kernel. Είναι το μέρος που δημιουργεί τα namespaces, γράφει τις ρυθμίσεις των cgroups, εφαρμόζει capabilities και φίλτρα seccomp και, τέλος, εκτελεί την container διεργασία με `execve()`. Όταν γίνεται λόγος για «container isolation» σε μηχανικό επίπεδο, συνήθως εννοείται αυτό το επίπεδο, ακόμη κι αν δεν αναφέρεται ρητά.

### `runc`

Το `runc` είναι το reference OCI runtime και παραμένει η πιο γνωστή υλοποίηση. Χρησιμοποιείται ευρέως από τα Docker, containerd και πολλές εγκαταστάσεις Kubernetes. Πολλή δημόσια έρευνα και υλικό για exploitation στοχεύουν περιβάλλοντα τύπου `runc`, απλώς επειδή είναι διαδεδομένα και επειδή το `runc` ορίζει τη βασική υλοποίηση που έχουν κατά νου πολλοί όταν σκέφτονται ένα Linux container. Επομένως, η κατανόηση του `runc` προσφέρει στον αναγνώστη ένα ισχυρό νοητικό μοντέλο για το κλασικό container isolation.

### `crun`

Το `crun` είναι ένα ακόμη OCI runtime, γραμμένο σε C και ευρέως χρησιμοποιούμενο σε σύγχρονα περιβάλλοντα Podman. Συχνά επαινείται για την καλή υποστήριξη cgroup v2, την ευκολία χρήσης σε rootless περιβάλλοντα και το μικρότερο overhead. Από την πλευρά της ασφάλειας, το σημαντικό δεν είναι ότι είναι γραμμένο σε διαφορετική γλώσσα, αλλά ότι εξακολουθεί να έχει τον ίδιο ρόλο: μετατρέπει τη διαμόρφωση OCI σε ένα εκτελούμενο process tree υπό τον kernel. Μια rootless ροή εργασίας με Podman συχνά μοιάζει ασφαλέστερη όχι επειδή το `crun` διορθώνει μαγικά τα πάντα, αλλά επειδή το συνολικό stack συνήθως βασίζεται περισσότερο στα user namespaces και στην αρχή του ελάχιστου προνομίου.

### `runsc` From gVisor

Το `runsc` είναι το runtime που χρησιμοποιεί το gVisor. Εδώ, το όριο αλλάζει ουσιαστικά. Αντί να περνά τις περισσότερες syscalls απευθείας στον host kernel με τον συνηθισμένο τρόπο, το gVisor παρεμβάλλει ένα userspace kernel layer που εξομοιώνει ή ελέγχει μεγάλα τμήματα του Linux interface. Το αποτέλεσμα δεν είναι ένα κανονικό container `runc` με λίγα επιπλέον flags· πρόκειται για διαφορετικό σχεδιασμό sandbox, με σκοπό τη μείωση της επιφάνειας επίθεσης του host kernel. Οι συμβιβασμοί ως προς τη συμβατότητα και την απόδοση αποτελούν μέρος αυτού του σχεδιασμού, επομένως τα περιβάλλοντα που χρησιμοποιούν `runsc` πρέπει να τεκμηριώνονται διαφορετικά από τα συνηθισμένα περιβάλλοντα OCI runtime.

### `kata-runtime`

Το Kata Containers προχωρά ακόμη περισσότερο, εκκινώντας το workload μέσα σε μια lightweight virtual machine. Από διαχειριστική άποψη, αυτό μπορεί να μοιάζει με ανάπτυξη container, και τα επίπεδα orchestration μπορεί να το αντιμετωπίζουν ως τέτοια, αλλά το υποκείμενο όριο απομόνωσης είναι πιο κοντά στο virtualization παρά σε ένα κλασικό container που μοιράζεται τον host kernel. Αυτό καθιστά το Kata χρήσιμο όταν επιδιώκεται ισχυρότερη απομόνωση μεταξύ tenants, χωρίς να εγκαταλείπονται οι ροές εργασίας που βασίζονται σε containers.

## Engines And Container Managers

Αν το runtime χαμηλού επιπέδου είναι το στοιχείο που επικοινωνεί απευθείας με τον kernel, το engine ή ο manager είναι το στοιχείο με το οποίο συνήθως αλληλεπιδρούν οι χρήστες και οι operators. Διαχειρίζεται image pulls, metadata, logs, networks, volumes, λειτουργίες lifecycle και έκθεση API. Αυτό το επίπεδο έχει τεράστια σημασία, επειδή πολλά πραγματικά περιστατικά παραβίασης συμβαίνουν εδώ: η πρόσβαση σε ένα runtime socket ή σε ένα daemon API μπορεί να ισοδυναμεί με παραβίαση του host, ακόμη κι αν το ίδιο το runtime χαμηλού επιπέδου λειτουργεί άψογα.

### Docker Engine

Το Docker Engine είναι η πιο αναγνωρίσιμη container πλατφόρμα για developers και ένας από τους λόγους που η ορολογία των containers διαμορφώθηκε γύρω από το Docker. Η συνηθισμένη ακολουθία είναι `docker` CLI προς `dockerd`, το οποίο συντονίζει στοιχεία χαμηλότερου επιπέδου, όπως το `containerd` και ένα OCI runtime. Ιστορικά, οι εγκαταστάσεις Docker ήταν συχνά **rootful**, και επομένως η πρόσβαση στο Docker socket αποτελούσε ένα πολύ ισχυρό primitive. Γι’ αυτό τόσο πολύ πρακτικό υλικό για privilege escalation εστιάζει στο `docker.sock`: αν μια διεργασία μπορεί να ζητήσει από το `dockerd` να δημιουργήσει ένα privileged container, να κάνει mount paths του host ή να συνδεθεί στα host namespaces, μπορεί να μη χρειάζεται καθόλου kernel exploit.

Συγκρίνετε τους αριθμούς εκδόσεων ανά major, minor και patch στοιχεία, αντί να αφαιρείτε τις τελείες: το `18.09.1` είναι παλαιότερο τόσο από το `18.09.2` όσο και από το `18.09.4`, παρότι το minor στοιχείο του έχει μηδενικό padding. Τα [18.09 release notes του Docker](https://docs.docker.com/engine/release-notes/18.09/) καταγράφουν τη διόρθωση του `runc` για το CVE-2019-5736 στην έκδοση 18.09.2 και τη διόρθωση build-reference για το CVE-2019-13139 στην έκδοση 18.09.4. Αυτές οι εκδόσεις αποτελούν ενδείξεις για περαιτέρω έλεγχο, όχι απόδειξη ότι ένα exploit είναι προσβάσιμο. Τα ίδια release notes προειδοποιούν ότι ο daemon, ο client και το runtime διατίθενται σε ξεχωριστά πακέτα, επομένως ελέγξτε το εγκατεστημένο runtime και τα backports του vendor παράλληλα με την έκδοση του daemon· ένα build-reference ζήτημα απαιτεί επίσης πρόσβαση στη σχετική ροή build και είσοδο που ελέγχεται από attacker.

### Podman

Το Podman σχεδιάστηκε γύρω από ένα πιο daemonless μοντέλο. Σε λειτουργικό επίπεδο, αυτό ενισχύει την ιδέα ότι τα containers είναι απλώς διεργασίες που διαχειρίζονται μέσω τυπικών Linux μηχανισμών, αντί μέσω ενός μοναδικού, μακρόβιου privileged daemon. Το Podman προσφέρει επίσης πολύ ισχυρότερη υποστήριξη **rootless** από τις κλασικές εγκαταστάσεις Docker με τις οποίες εξοικειώθηκαν αρχικά πολλοί. Αυτό δεν καθιστά αυτομάτως το Podman ασφαλές, αλλά αλλάζει σημαντικά το προεπιλεγμένο προφίλ κινδύνου, ειδικά σε συνδυασμό με user namespaces, SELinux και `crun`.

### containerd

Το containerd είναι βασικό στοιχείο διαχείρισης runtime σε πολλά σύγχρονα stacks. Χρησιμοποιείται από το Docker και αποτελεί επίσης ένα από τα κυρίαρχα runtime backends του Kubernetes. Παρέχει ισχυρά APIs, διαχειρίζεται images και snapshots και αναθέτει την τελική δημιουργία διεργασιών σε ένα runtime χαμηλού επιπέδου. Οι συζητήσεις ασφάλειας γύρω από το containerd πρέπει να τονίζουν ότι η πρόσβαση στο socket του containerd ή στη λειτουργικότητα των `ctr`/`nerdctl` μπορεί να είναι εξίσου επικίνδυνη με την πρόσβαση στο API του Docker, ακόμη κι αν το interface και η ροή εργασίας φαίνονται λιγότερο «φιλικά προς τους developers».

### CRI-O

Το CRI-O έχει πιο εξειδικευμένο σκοπό από το Docker Engine. Αντί να είναι μια πλατφόρμα γενικής χρήσης για developers, έχει σχεδιαστεί για να υλοποιεί με καθαρό τρόπο το Kubernetes Container Runtime Interface. Γι’ αυτό είναι ιδιαίτερα συνηθισμένο σε διανομές Kubernetes και σε οικοσυστήματα με έντονη χρήση SELinux, όπως το OpenShift. Από την πλευρά της ασφάλειας, αυτό το πιο περιορισμένο πεδίο είναι χρήσιμο, επειδή μειώνει την εννοιολογική πολυπλοκότητα: το CRI-O ανήκει σαφώς στο επίπεδο «εκτέλεσης containers για το Kubernetes» και όχι σε μια πλατφόρμα για τα πάντα.

Όταν ένας κόμβος Kubernetes χρησιμοποιεί CRI-O, ελέγξτε την **ενεργή έκδοση CRI-O του κόμβου** και αν η τρέχουσα ταυτότητα μπορεί να δημιουργήσει Pods σε ένα namespace που προγραμματίζει workloads σε αυτόν τον κόμβο. Το [CVE-2022-0811](https://github.com/cri-o/cri-o/security/advisories/GHSA-6x2m-w449-qwx7) επέτρεπε σε ειδικά διαμορφωμένες τιμές sysctl ενός Pod να αλλάξουν μια παράμετρο του host kernel και να οδηγήσουν σε εκτέλεση με δικαιώματα host-root στις επηρεαζόμενες εκδόσεις. Η upstream συμβουλευτική ανακοίνωση παραθέτει τις διορθωμένες εκδόσεις και τα workarounds. Μια τοπική εκτέλεση του `crio --version` μπορεί να μην εντοπίσει ένα runtime που είναι ενσωματωμένο σε Minikube ή σε άλλο node container· ένα αναγνώσιμο log εκκίνησης του Minikube μπορεί να δώσει ένδειξη για την έκδοση, αλλά αποτελεί ιστορικό στοιχείο και όχι απόδειξη για το ενεργό runtime ή την κατάσταση των patches του. Επιβεβαιώστε το πραγματικό runtime του κόμβου, τα δικαιώματα δημιουργίας Pod, τους κανόνες admission και τα σχετικά όρια seccomp και user namespace προτού θεωρήσετε ότι πρόκειται για προσβάσιμο privilege escalation.

Υπάρχει επίσης μια άμεση τοπική διαδρομή ελέγχου του `pinns`: οι [ερευνητές σημειώνουν ότι δεν απαιτείται Kubernetes για την εκτέλεση του προβληματικού helper](https://www.crowdstrike.com/en-us/blog/cr8escape-new-vulnerability-discovered-in-cri-o-container-engine-cve-2022-0811/). Ελέγξτε αν ο τρέχων λογαριασμός μπορεί να εκτελέσει ένα setuid `pinns` που ανήκει στον root, αν το NoNewPrivs ή ένα `nosuid` mount εμποδίζει αυτή τη μετάβαση και αν το εγκατεστημένο **build του helper** δεν περιλαμβάνει τη διόρθωση. Η [upstream συμβουλευτική ανακοίνωση](https://github.com/cri-o/cri-o/security/advisories/GHSA-6x2m-w449-qwx7) παραθέτει τις διορθωμένες εκδόσεις, αλλά η έκδοση που εμφανίζει ένας daemon από μόνη της δεν αποδεικνύει ποιο helper binary είναι εγκατεστημένο, ενώ τα backports των διανομέων μπορούν να αλλάξουν την έκθεση. Ένα setuid αρχείο είναι μόνο υποψήφιο εύρημα· επαληθεύστε την προέλευση του helper, τη διαμόρφωση και τη συμπεριφορά των host sysctl χωρίς να το εκτελέσετε κατά τη συνήθη απαρίθμηση.

### Incus, LXD, And LXC

Τα συστήματα Incus/LXD/LXC αξίζει να διαχωρίζονται από τα application containers τύπου Docker, επειδή συχνά χρησιμοποιούνται ως **system containers**. Ένα system container αναμένεται συνήθως να μοιάζει περισσότερο με ένα ελαφρύ μηχάνημα, με πληρέστερο userspace, υπηρεσίες μεγάλης διάρκειας, ευρύτερη έκθεση συσκευών και εκτενέστερη ενσωμάτωση με τον host. Οι μηχανισμοί απομόνωσης εξακολουθούν να βασίζονται σε primitives του kernel, αλλά οι λειτουργικές προσδοκίες είναι διαφορετικές. Ως αποτέλεσμα, οι λανθασμένες ρυθμίσεις εδώ μοιάζουν συχνά λιγότερο με «κακές προεπιλεγμένες ρυθμίσεις app-container» και περισσότερο με λάθη σε lightweight virtualization ή στην ανάθεση δικαιωμάτων του host.

### systemd-nspawn

Το systemd-nspawn κατέχει μια ενδιαφέρουσα θέση, επειδή είναι εγγενές στο systemd και πολύ χρήσιμο για testing, debugging και εκτέλεση περιβαλλόντων που μοιάζουν με λειτουργικά συστήματα. Δεν είναι το κυρίαρχο runtime παραγωγής σε cloud-native περιβάλλοντα, αλλά εμφανίζεται αρκετά συχνά σε labs και περιβάλλοντα προσανατολισμένα στις διανομές ώστε να αξίζει να αναφερθεί. Για την ανάλυση ασφάλειας, αποτελεί ακόμη μια υπενθύμιση ότι η έννοια «container» καλύπτει πολλά οικοσυστήματα και λειτουργικά μοντέλα.

### Apptainer / Singularity

Το Apptainer (πρώην Singularity) είναι συνηθισμένο σε περιβάλλοντα έρευνας και HPC. Οι παραδοχές εμπιστοσύνης, η ροή εργασίας των χρηστών και το μοντέλο εκτέλεσής του διαφέρουν σημαντικά από τα stacks που βασίζονται σε Docker/Kubernetes. Ειδικότερα, αυτά τα περιβάλλοντα συχνά δίνουν μεγάλη σημασία στη δυνατότητα των χρηστών να εκτελούν packaged workloads χωρίς να τους παρέχονται ευρεία privileged δικαιώματα διαχείρισης containers. Αν ένας reviewer υποθέσει ότι κάθε περιβάλλον container είναι ουσιαστικά «Docker σε server», θα παρανοήσει σοβαρά αυτές τις εγκαταστάσεις.

## Build-Time Tooling

Πολλές συζητήσεις ασφάλειας αφορούν μόνο το run time, αλλά σημασία έχει και το tooling κατά το build, καθώς καθορίζει το περιεχόμενο των images, την έκθεση των build secrets και το πόσο έμπιστο context ενσωματώνεται στο τελικό artifact.

Τα **BuildKit** και `docker buildx` είναι σύγχρονα build backends που υποστηρίζουν λειτουργίες όπως caching, secret mounting, SSH forwarding και multi-platform builds. Αυτές είναι χρήσιμες λειτουργίες, αλλά από την πλευρά της ασφάλειας δημιουργούν επίσης σημεία όπου secrets μπορούν να διαρρεύσουν σε image layers ή όπου ένα υπερβολικά ευρύ build context μπορεί να εκθέσει αρχεία που δεν έπρεπε ποτέ να συμπεριληφθούν. Το **Buildah** επιτελεί παρόμοιο ρόλο σε οικοσυστήματα εγγενή στο OCI, ειδικά γύρω από το Podman, ενώ το **Kaniko** χρησιμοποιείται συχνά σε CI περιβάλλοντα που δεν θέλουν να παραχωρήσουν privileged Docker daemon στο build pipeline.

Το βασικό συμπέρασμα είναι ότι η δημιουργία ενός image και η εκτέλεσή του είναι διαφορετικές φάσεις, αλλά ένα αδύναμο build pipeline μπορεί να δημιουργήσει αδύναμη στάση ασφάλειας πολύ πριν ξεκινήσει το container.

## Orchestration Is Another Layer, Not The Runtime

Το Kubernetes δεν πρέπει να ταυτίζεται νοητικά με το ίδιο το runtime. Το Kubernetes είναι ο orchestrator. Προγραμματίζει Pods, αποθηκεύει την επιθυμητή κατάσταση και εκφράζει πολιτικές ασφάλειας μέσω της διαμόρφωσης των workloads. Στη συνέχεια, το kubelet επικοινωνεί με μια υλοποίηση CRI, όπως το containerd ή το CRI-O, η οποία με τη σειρά της καλεί ένα runtime χαμηλού επιπέδου, όπως τα `runc`, `crun`, `runsc` ή `kata-runtime`.

Αυτός ο διαχωρισμός έχει σημασία, επειδή πολλοί αποδίδουν λανθασμένα μια προστασία στο «Kubernetes», ενώ στην πραγματικότητα επιβάλλεται από το runtime του κόμβου, ή κατηγορούν τις «προεπιλεγμένες ρυθμίσεις του containerd» για συμπεριφορά που προήλθε από ένα Pod spec. Στην πράξη, η τελική στάση ασφάλειας είναι συνδυασμός: ο orchestrator ζητά κάτι, το runtime stack το μεταφράζει και ο kernel το επιβάλλει τελικά.

## Why Runtime Identification Matters During Assessment

Αν εντοπίσετε νωρίς το engine και το runtime, πολλές μεταγενέστερες παρατηρήσεις γίνονται ευκολότερες στην ερμηνεία. Ένα rootless Podman container υποδηλώνει ότι πιθανότατα συμμετέχουν user namespaces. Ένα Docker socket mounted μέσα σε workload υποδηλώνει ότι το privilege escalation μέσω API είναι ρεαλιστική διαδρομή. Ένας κόμβος CRI-O/OpenShift πρέπει αμέσως να σας κάνει να σκεφτείτε τις ετικέτες SELinux και την πολιτική περιορισμού των workloads. Ένα περιβάλλον gVisor ή Kata πρέπει να σας κάνει πιο επιφυλακτικούς ως προς την υπόθεση ότι ένα κλασικό PoC για breakout από `runc` θα συμπεριφερθεί με τον ίδιο τρόπο.

Γι’ αυτό ένα από τα πρώτα βήματα σε μια αξιολόγηση container πρέπει πάντα να είναι να απαντήσετε σε δύο απλές ερωτήσεις: **ποιο στοιχείο διαχειρίζεται το container** και **ποιο runtime εκκίνησε πράγματι τη διεργασία**. Μόλις γίνουν σαφείς οι απαντήσεις, το υπόλοιπο περιβάλλον συνήθως γίνεται πολύ ευκολότερο στην ανάλυση.

## Runtime Vulnerabilities

Δεν οφείλεται κάθε container escape σε λανθασμένη ρύθμιση από operator. Μερικές φορές, το ίδιο το runtime είναι το ευάλωτο στοιχείο. Αυτό έχει σημασία, επειδή ένα workload μπορεί να εκτελείται με μια φαινομενικά προσεκτική διαμόρφωση και παρ’ όλα αυτά να είναι εκτεθειμένο μέσω ενός bug σε runtime χαμηλού επιπέδου.

Το κλασικό παράδειγμα είναι το **CVE-2019-5736** στο `runc`, όπου ένα κακόβουλο container μπορούσε να αντικαταστήσει το binary `runc` του host και στη συνέχεια να περιμένει μια μεταγενέστερη κλήση `docker exec` ή παρόμοια κλήση runtime, ώστε να εκτελεστεί κώδικας ελεγχόμενος από τον attacker. Η διαδρομή του exploit διαφέρει σημαντικά από ένα απλό λάθος σε bind mount ή capability, επειδή καταχράται τον τρόπο με τον οποίο το runtime επιστρέφει στον χώρο διεργασιών του container κατά τη διαχείριση του exec.<sup>[[1]](#references)</sup>

Μια ελάχιστη ροή αναπαραγωγής από την οπτική ενός red team είναι:

```bash
go build main.go
./main
```

Έπειτα, από τον host:

```bash
docker exec -it <container-name> /bin/sh
```

Το βασικό δίδαγμα δεν αφορά την ακριβή υλοποίηση του ιστορικού exploit, αλλά τις επιπτώσεις για την αξιολόγηση: αν η έκδοση του runtime είναι ευάλωτη, η συνηθισμένη εκτέλεση κώδικα μέσα στο container μπορεί να αρκεί για να παραβιαστεί το host, ακόμη κι αν η ορατή διαμόρφωση του container δεν φαίνεται προφανώς αδύναμη.

Πρόσφατα CVE σε runtime, όπως το `CVE-2024-21626` στο `runc`, τα race conditions στα mounts του BuildKit και τα σφάλματα ανάλυσης του containerd, ενισχύουν το ίδιο συμπέρασμα. Η έκδοση του runtime και το επίπεδο ενημερώσεων κώδικα αποτελούν μέρος του ορίου ασφαλείας και δεν είναι απλώς ασήμαντες λεπτομέρειες συντήρησης.
