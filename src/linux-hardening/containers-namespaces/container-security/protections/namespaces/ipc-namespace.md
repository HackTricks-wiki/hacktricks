# Простір імен IPC

{{#include ../../../../../banners/hacktricks-training.md}}

## Огляд

Простір імен IPC ізолює **об'єкти System V IPC** і **черги повідомлень POSIX**. Сюди належать сегменти спільної пам'яті, семафори та черги повідомлень, які інакше були б видимими для інших, не пов'язаних між собою процесів на хості. На практиці це не дає контейнеру довільно підключатися до IPC-об'єктів, що належать іншим робочим навантаженням або хосту.

Порівняно з просторами імен mount, PID або user, простір імен IPC обговорюють рідше, але це не означає, що він не має значення. Спільна пам'ять та пов'язані з нею IPC-механізми можуть містити дуже корисний стан. Якщо простір імен IPC хоста відкритий, робоче навантаження може отримати доступ до об'єктів або даних міжпроцесної координації, які ніколи не призначалися для виходу за межі контейнера.

## Робота

Коли runtime створює новий простір імен IPC, процес отримує власний ізольований набір ідентифікаторів IPC. Це означає, що такі команди, як `ipcs`, показують лише об'єкти, доступні в цьому просторі імен. Якщо натомість контейнер приєднується до простору імен IPC хоста, ці об'єкти стають частиною спільного глобального представлення.

Це особливо важливо в середовищах, де застосунки або сервіси активно використовують спільну пам'ять. Навіть якщо контейнер не може безпосередньо виконати breakout лише через IPC, простір імен може leak інформацію або забезпечити міжпроцесне втручання, яке суттєво допоможе під час подальшої атаки.

## Лабораторна робота

Ви можете створити приватний простір імен IPC за допомогою:
```bash
sudo unshare --ipc --fork bash
ipcs
```
І порівняйте поведінку під час виконання з:
```bash
docker run --rm debian:stable-slim ipcs
docker run --rm --ipc=host debian:stable-slim ipcs
```
## Використання під час виконання

Docker і Podman за замовчуванням ізолюють IPC. Kubernetes зазвичай надає Pod власний IPC namespace, спільний для контейнерів у тому самому Pod, але не спільний із хостом за замовчуванням. Спільне використання IPC із хостом можливе, але його слід розглядати як суттєве зниження рівня ізоляції, а не як незначну опцію runtime.

## Неправильні налаштування

Очевидною помилкою є `--ipc=host` або `hostIPC: true`. Це може робитися для сумісності зі legacy software або заради зручності, але суттєво змінює модель довіри. Інша поширена проблема — просто не враховувати IPC, оскільки він здається менш критичним, ніж host PID або host networking. Насправді, якщо workload працює з браузерами, базами даних, науковими workload або іншим software, що активно використовує shared memory, поверхня IPC може бути дуже важливою.

## Зловживання

Якщо host IPC є спільним, attacker може переглядати або втручатися в об’єкти shared memory, отримувати додаткові відомості про поведінку хоста чи сусідніх workload або поєднувати отриману там інформацію з visibility процесів і capabilities у стилі ptrace. Спільне використання IPC часто є допоміжною слабкістю, а не повним шляхом до breakout, але допоміжні слабкості мають значення, оскільки скорочують і стабілізують реальні attack chain.

Перший корисний крок — перелічити, які IPC-об’єкти взагалі видимі:
```bash
readlink /proc/self/ns/ipc
ipcs -a
ls -la /dev/shm 2>/dev/null | head -n 50
```
Якщо IPC namespace хоста є спільним, великі сегменти shared memory або цікаві власники об’єктів можуть одразу розкрити поведінку застосунку:
```bash
ipcs -m -p
ipcs -q -p
```
У деяких середовищах сам вміст `/dev/shm` може leak-ити імена файлів, артефакти або токени, які варто перевірити:
```bash
find /dev/shm -maxdepth 2 -type f 2>/dev/null -ls | head -n 50
strings /dev/shm/* 2>/dev/null | head -n 50
```
Спільне використання IPC рідко саме по собі миттєво надає root на хості, але може відкрити доступ до каналів даних і координації, що значно спрощує подальші атаки на процеси.

### Повний приклад: відновлення секретів із `/dev/shm`

Найреалістичніший повний сценарій зловживання — це крадіжка даних, а не прямий escape. Якщо IPC хоста або широке розташування shared memory відкриті, конфіденційні артефакти іноді можна безпосередньо відновити:
```bash
find /dev/shm -maxdepth 2 -type f 2>/dev/null -print
strings /dev/shm/* 2>/dev/null | grep -Ei 'token|secret|password|jwt|key'
```
Вплив:

- вилучення секретів або матеріалів сесій, залишених у спільній пам’яті
- отримання інформації про застосунки, активні на host
- ефективніше націлювання подальших атак через PID-namespace або на основі ptrace

Тому спільний IPC краще розглядати як **підсилювач атаки**, а не як самостійний примітив втечі з host.

## Перевірки

Ці команди допоможуть визначити, чи має workload приватне представлення IPC, чи видимі значущі об’єкти спільної пам’яті або повідомлень, а також чи відкриває сам `/dev/shm` корисні артефакти.
```bash
readlink /proc/self/ns/ipc   # Namespace identifier for IPC
ipcs -a                      # Visible SysV IPC objects
mount | grep shm             # Shared-memory mounts, especially /dev/shm
```
Що тут цікаво:

- Якщо `ipcs -a` показує об’єкти, власниками яких є неочікувані користувачі або сервіси, namespace може бути ізольований не так, як очікувалося.
- Великі або незвичні сегменти shared memory часто варто дослідити додатково.
- Широке монтування `/dev/shm` не є автоматично помилкою, але в деяких середовищах воно leak filenames, артефакти та тимчасові секрети.

IPC рідко отримує стільки ж уваги, як важливіші типи namespace, але в середовищах, де він активно використовується, спільне використання з host є повноцінним security-рішенням.
