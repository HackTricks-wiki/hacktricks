# Простори імен

{{#include ../../../../../banners/hacktricks-training.md}}

Простори імен — це функція ядра, завдяки якій контейнер сприймається як «власна машина», хоча насправді він є лише деревом процесів хоста. Вони не створюють нове ядро і не віртуалізують усе, але дають змогу ядру представляти різні уявлення про вибрані ресурси для різних груп процесів. Це основа ілюзії контейнера: workload бачить файлову систему, таблицю процесів, мережевий стек, ім'я хоста, ресурси IPC і модель ідентифікації користувачів/груп, які здаються локальними, хоча базова система є спільною.

Саме тому простори імен — перша концепція, з якою стикається більшість людей, вивчаючи принцип роботи контейнерів. Водночас це одна з найбільш неправильно зрозумілих концепцій, оскільки читачі часто припускають, що «наявність просторів імен» означає «безпечну ізоляцію». Насправді простір імен ізолює лише конкретний клас ресурсів, для якого його створено. Процес може мати приватний PID namespace і водночас бути небезпечним, якщо він має доступний для запису bind mount хоста. Він може мати приватний network namespace і водночас бути небезпечним, якщо зберігає `CAP_SYS_ADMIN` та працює без seccomp. Простори імен є фундаментальними, але вони становлять лише один рівень підсумкової межі.

## Типи просторів імен

Контейнери Linux зазвичай одночасно використовують кілька типів просторів імен. **Mount namespace** надає процесу окрему таблицю монтувань і, відповідно, контрольоване уявлення про файлову систему. **PID namespace** змінює видимість і нумерацію процесів, завдяки чому workload бачить власне дерево процесів. **Network namespace** ізолює інтерфейси, маршрути, сокети та стан firewall. **IPC namespace** ізолює SysV IPC і черги повідомлень POSIX. **UTS namespace** ізолює ім'я хоста та доменне ім'я NIS. **User namespace** перепризначає ідентифікатори користувачів і груп, тому root усередині контейнера не обов'язково означає root на хості. **Cgroup namespace** віртуалізує видиму ієрархію cgroup, а **time namespace** у новіших ядрах віртуалізує вибрані годинники.

Кожен із цих просторів імен вирішує окрему проблему. Саме тому практичний аналіз безпеки контейнерів часто зводиться до перевірки того, **які простори імен ізольовані**, а **які навмисно спільно використовуються з хостом**.

## Спільне використання просторів імен хоста

Багато container breakouts починаються не з уразливості ядра. Вони починаються з того, що оператор навмисно послаблює модель ізоляції. Приклади `--pid=host`, `--network=host` і `--userns=host` — це **прапорці CLI у стилі Docker/Podman**, використані тут як конкретні приклади спільного використання просторів імен хоста. Інші runtimes виражають ту саму ідею інакше. У Kubernetes відповідники зазвичай представлені налаштуваннями Pod, такими як `hostPID: true`, `hostNetwork: true` або `hostIPC: true`. У низькорівневих runtime-стеках, таких як containerd або CRI-O, тієї самої поведінки часто досягають через згенеровану конфігурацію OCI runtime, а не через користувацький прапорець із такою самою назвою. У всіх цих випадках результат подібний: workload більше не отримує стандартне ізольоване уявлення про простори імен.

Саме тому перевірка просторів імен ніколи не повинна зупинятися на твердженні «процес перебуває в якомусь просторі імен». Важливе питання полягає в тому, чи є простір імен приватним для контейнера, спільним із сусідніми контейнерами або безпосередньо приєднаним до хоста. У Kubernetes та сама ідея реалізується за допомогою прапорців на кшталт `hostPID`, `hostNetwork` і `hostIPC`. Назви відрізняються між платформами, але risk pattern той самий: спільний простір імен хоста робить решту привілеїв контейнера та доступний стан хоста набагато важливішими.

## Перевірка

Найпростіший огляд такий:
```bash
ls -l /proc/self/ns
```
Кожен запис є символічним посиланням з ідентифікатором, подібним до inode. Якщо два процеси вказують на один ідентифікатор namespace, вони перебувають в одному namespace цього типу. Це робить `/proc` дуже корисним місцем для порівняння поточного процесу з іншими цікавими процесами на машині.

Цих швидких команд часто достатньо для початку:
```bash
readlink /proc/self/ns/mnt
readlink /proc/self/ns/pid
readlink /proc/self/ns/net
readlink /proc/1/ns/mnt
```
Звідти наступним кроком є порівняння процесу контейнера з процесами хоста або сусідніх процесів і визначення того, чи є namespace справді приватним.

### Перерахування екземплярів namespace з хоста

Якщо у вас уже є доступ до хоста й ви хочете зрозуміти, скільки окремих namespace певного типу існує, `/proc` надає швидкий перелік:
```bash
sudo find /proc -maxdepth 3 -type l -name mnt    -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name pid    -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name net    -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name ipc    -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name uts    -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name user   -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name cgroup -exec readlink {} \; 2>/dev/null | sort -u
sudo find /proc -maxdepth 3 -type l -name time   -exec readlink {} \; 2>/dev/null | sort -u
```
Якщо потрібно визначити, які процеси належать певному ідентифікатору простору імен, замініть `readlink` на `ls -l` і виконайте grep для пошуку номера цільового простору імен:
```bash
sudo find /proc -maxdepth 3 -type l -name mnt -exec ls -l {} \; 2>/dev/null | grep <ns-number>
```
Ці команди корисні, оскільки дають змогу визначити, чи працює на хості одне ізольоване робоче навантаження, багато ізольованих робочих навантажень або поєднання спільних і приватних екземплярів просторів імен.

### Вхід до цільового простору імен

Коли викликач має достатні привілеї, `nsenter` є стандартним способом приєднатися до простору імен іншого процесу:
```bash
nsenter -m TARGET_PID --pid /bin/bash   # mount
nsenter -t TARGET_PID --pid /bin/bash   # pid
nsenter -n TARGET_PID --pid /bin/bash   # network
nsenter -i TARGET_PID --pid /bin/bash   # ipc
nsenter -u TARGET_PID --pid /bin/bash   # uts
nsenter -U TARGET_PID --pid /bin/bash   # user
nsenter -C TARGET_PID --pid /bin/bash   # cgroup
nsenter -T TARGET_PID --pid /bin/bash   # time
```
Сенс наведення цих форм разом полягає не в тому, що кожна оцінка потребує їх усіх, а в тому, що специфічний для namespace post-exploitation часто стає значно простішим, коли оператор знає точний синтаксис входу, а не пам'ятає лише форму для всіх namespace.

## Типові налаштування runtime

| Runtime / платформа | Типова конфігурація namespace | Поширене ручне послаблення |
| --- | --- | --- |
| Docker Engine | За замовчуванням створюються нові mount, PID, network, IPC і UTS namespaces; user namespaces доступні, але за замовчуванням не ввімкнені у стандартних rootful налаштуваннях | `--pid=host`, `--network=host`, `--ipc=host`, `--uts=host`, `--userns=host`, `--cgroupns=host`, `--privileged` |
| Podman | За замовчуванням створюються нові namespaces; rootless Podman автоматично використовує user namespace; значення cgroup namespace за замовчуванням залежать від версії cgroup | `--pid=host`, `--network=host`, `--ipc=host`, `--uts=host`, `--userns=host`, `--cgroupns=host`, `--privileged` |
| Kubernetes | Pods **не** використовують спільні host PID, network або IPC за замовчуванням; Pod networking є приватною для Pod, а не для кожного окремого контейнера; user namespaces вмикаються окремо через `spec.hostUsers: false` у кластерах із відповідною підтримкою | `hostPID: true`, `hostNetwork: true`, `hostIPC: true`, `spec.hostUsers: true` / відсутність opt-in для user namespace, налаштування privileged workload |
| containerd / CRI-O під Kubernetes | Зазвичай дотримуються типових налаштувань Kubernetes Pod | те саме, що й у рядку Kubernetes; прямі CRI/OCI specs також можуть запитувати приєднання до host namespaces |

Головне правило переносимості просте: **концепція** спільного використання host namespace є спільною для різних runtime, але **синтаксис** залежить від конкретного runtime.
