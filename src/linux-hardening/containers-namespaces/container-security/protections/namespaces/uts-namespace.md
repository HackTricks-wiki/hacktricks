# Простір імен UTS

{{#include ../../../../../banners/hacktricks-training.md}}

## Огляд

Простір імен UTS ізолює **hostname** та **доменне ім'я NIS**, які бачить процес. На перший погляд це може здаватися дрібницею порівняно з просторами імен mount, PID або user, але саме це є частиною механізму, завдяки якому контейнер виглядає як окремий хост. Усередині простору імен workload може бачити й іноді змінювати hostname, локальний для цього простору імен, а не глобальний для машини.

Сам по собі цей механізм зазвичай не є центральним елементом breakout story. Однак якщо простір імен UTS хоста спільно використовується, достатньо привілейований процес може впливати на налаштування, пов'язані з ідентичністю хоста, що може мати операційне, а іноді й security-значення.

## Лабораторія

Ви можете створити простір імен UTS за допомогою:
```bash
sudo unshare --uts --fork bash
hostname
hostname lab-container
hostname
```
Зміна hostname залишається локальною для цього namespace і не змінює глобальний hostname хоста. Це проста, але ефективна демонстрація властивості ізоляції.

## Використання під час виконання

Звичайні контейнери отримують ізольований UTS namespace. Docker і Podman можуть приєднатися до UTS namespace хоста через `--uts=host`, а подібні шаблони спільного використання хоста можуть застосовуватися в інших runtime та системах оркестрації. Однак здебільшого приватна ізоляція UTS є просто частиною стандартного налаштування контейнера й майже не потребує уваги оператора.

## Вплив на безпеку

Хоча UTS namespace зазвичай не є найбільш небезпечним для спільного використання, він усе одно підтримує цілісність межі контейнера. Якщо UTS namespace хоста відкритий, а процес має необхідні привілеї, він може отримати можливість змінювати пов’язану з hostname інформацію хоста. Це може вплинути на моніторинг, журналювання, операційні припущення або скрипти, які ухвалюють рішення щодо довіри на основі даних про ідентичність хоста.

## Зловживання

Якщо UTS namespace хоста є спільним, практичне питання полягає в тому, чи може процес змінювати налаштування ідентичності хоста, а не лише читати їх:
```bash
readlink /proc/self/ns/uts
hostname
cat /proc/sys/kernel/hostname
```
Якщо контейнер також має необхідні привілеї, перевірте, чи можна змінити ім’я хоста:
```bash
hostname hacked-host 2>/dev/null && echo "hostname change worked"
hostname
```
Це насамперед проблема цілісності та операційного впливу, а не повний escape, але вона все одно показує, що container може безпосередньо впливати на глобальну для host властивість.

Вплив:

- підроблення ідентичності host
- плутанина в логах, моніторингу або автоматизації, які довіряють hostname
- зазвичай не є повним escape сам по собі, якщо не поєднується з іншими вразливостями

У середовищах на кшталт Docker корисний шаблон виявлення на стороні host має такий вигляд:
```bash
docker ps -aq | xargs -r docker inspect --format '{{.Id}} UTSMode={{.HostConfig.UTSMode}}'
```
Контейнери, у яких указано `UTSMode=host`, спільно використовують UTS namespace хоста, тому їх слід ретельніше перевірити, якщо вони також мають capabilities, що дозволяють викликати `sethostname()` або `setdomainname()`.

## Перевірки

Цих команд достатньо, щоб визначити, чи має workload власне представлення hostname, чи спільно використовує UTS namespace хоста.
```bash
readlink /proc/self/ns/uts   # UTS namespace identifier
hostname                     # Hostname as seen by the current process
cat /proc/sys/kernel/hostname   # Kernel hostname value in this namespace
```
Що тут цікавого:

- Збіг ідентифікаторів namespace з host process може вказувати на спільне використання UTS з host.
- Якщо зміна hostname впливає не лише на сам container, workload має більший вплив на ідентичність host, ніж повинен.
- Зазвичай це знахідка з нижчим пріоритетом, ніж проблеми з PID, mount або user namespace, але вона все одно підтверджує, наскільки насправді ізольований процес.

У більшості середовищ UTS namespace найкраще розглядати як допоміжний рівень ізоляції. Він рідко є першим, що перевіряють під час breakout, але все одно є частиною загальної узгодженості та безпеки представлення container.
