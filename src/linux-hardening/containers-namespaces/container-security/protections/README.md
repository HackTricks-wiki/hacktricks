# Огляд захисту контейнерів

{{#include ../../../../banners/hacktricks-training.md}}

Найважливіша ідея hardening контейнерів полягає в тому, що не існує єдиного механізму під назвою "container security". Те, що називають ізоляцією контейнерів, насправді є результатом спільної роботи кількох механізмів безпеки та керування ресурсами Linux. Якщо документація описує лише один із них, читачі схильні переоцінювати його стійкість. Якщо документація перелічує їх усі, але не пояснює, як вони взаємодіють, читачі отримують каталог назв, але не реальну модель. Цей розділ намагається уникнути обох помилок.

У центрі цієї моделі перебувають **namespaces**, які ізолюють те, що може бачити workload. Вони надають процесу приватне або частково приватне представлення монтувань файлової системи, PID, мережі, об'єктів IPC, імен хостів, зіставлень користувачів/груп, шляхів cgroup і деяких годинників. Але самі namespaces не визначають, що процесу дозволено робити. Саме тут з'являються наступні рівні.

**cgroups** керують використанням ресурсів. Вони не є передусім межею ізоляції в тому самому сенсі, що mount або PID namespaces, але мають критичне операційне значення, оскільки обмежують пам'ять, CPU, PID, I/O і доступ до пристроїв. Вони також важливі для безпеки, оскільки історичні техніки breakout зловживали функціями cgroup, доступними для запису, особливо в середовищах cgroup v1.

**Capabilities** розділяють стару модель всемогутнього root на менші одиниці привілеїв. Це фундаментально важливо для контейнерів, оскільки багато workload досі працюють як UID 0 усередині контейнера. Тому питання полягає не лише в тому, "чи є процес root?", а радше в тому, "які capabilities збереглися, у яких namespaces, і за яких обмежень seccomp та MAC?" Саме тому root-процес в одному контейнері може бути відносно обмеженим, тоді як root-процес в іншому контейнері на практиці може бути майже невідрізнимим від root на хості.

**seccomp** фільтрує syscalls і зменшує attack surface ядра, відкриту для workload. Це часто механізм, який блокує очевидно небезпечні виклики, такі як `unshare`, `mount`, `keyctl`, або інші syscalls, що використовуються в ланцюжках breakout. Навіть якщо процес має capability, яка за інших умов дозволила б виконати операцію, seccomp все одно може заблокувати шлях syscall ще до того, як ядро повністю його обробить.

**AppArmor** і **SELinux** додають Mandatory Access Control поверх звичайних перевірок файлової системи та привілеїв. Це особливо важливо, оскільки вони продовжують мати значення навіть тоді, коли контейнер має більше capabilities, ніж повинен. Workload може мати теоретичний привілей для спроби виконати дію, але все одно не зможе її здійснити, оскільки його label або profile забороняє доступ до відповідного шляху, об'єкта чи операції.

Нарешті, існують додаткові рівні hardening, яким приділяють менше уваги, але які регулярно мають значення в реальних атаках: `no_new_privs`, masked procfs paths, read-only system paths, read-only root filesystems і ретельно налаштовані runtime defaults. Ці механізми часто зупиняють "останню милю" компрометації, особливо коли attacker намагається перетворити виконання коду на ширше підвищення привілеїв.

Решта цієї папки детальніше пояснює кожен із цих механізмів, зокрема те, що насправді робить примітив ядра, як спостерігати за ним локально, як його використовують поширені runtimes і як оператори випадково послаблюють його.
