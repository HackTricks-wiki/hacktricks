# Επισκόπηση Προστασιών Container

{{#include ../../../../banners/hacktricks-training.md}}

Η σημαντικότερη ιδέα στο hardening των container είναι ότι δεν υπάρχει ένας μεμονωμένος έλεγχος που ονομάζεται "container security". Αυτό που αποκαλούν container isolation είναι στην πραγματικότητα το αποτέλεσμα της συνεργασίας αρκετών μηχανισμών ασφάλειας και διαχείρισης πόρων του Linux. Αν η τεκμηρίωση περιγράφει μόνο έναν από αυτούς, οι αναγνώστες τείνουν να υπερεκτιμούν την ισχύ του. Αν η τεκμηρίωση παραθέτει όλους τους μηχανισμούς χωρίς να εξηγεί πώς αλληλεπιδρούν, οι αναγνώστες αποκτούν έναν κατάλογο ονομάτων αλλά όχι ένα πραγματικό μοντέλο. Αυτή η ενότητα προσπαθεί να αποφύγει και τα δύο λάθη.

Στο κέντρο του μοντέλου βρίσκονται τα **namespaces**, τα οποία απομονώνουν όσα μπορεί να δει το workload. Παρέχουν στη διεργασία μια ιδιωτική ή μερικώς ιδιωτική άποψη των filesystem mounts, των PIDs, της δικτύωσης, των αντικειμένων IPC, των hostnames, των αντιστοιχίσεων χρηστών/ομάδων, των διαδρομών cgroup και ορισμένων clocks. Ωστόσο, τα namespaces από μόνα τους δεν αποφασίζουν τι επιτρέπεται να κάνει μια διεργασία. Εκεί εισέρχονται τα επόμενα layers.

Τα **cgroups** διέπουν τη χρήση πόρων. Δεν αποτελούν πρωτίστως boundary απομόνωσης με την ίδια έννοια όπως τα mount ή PID namespaces, αλλά είναι κρίσιμα σε επιχειρησιακό επίπεδο, επειδή περιορίζουν τη μνήμη, το CPU, τα PIDs, το I/O και την πρόσβαση σε συσκευές. Έχουν επίσης σημασία για την ασφάλεια, επειδή ιστορικές τεχνικές breakout έκαναν abuse σε writable χαρακτηριστικά των cgroup, ιδιαίτερα σε περιβάλλοντα cgroup v1.

Τα **Capabilities** χωρίζουν το παλιό, πανίσχυρο μοντέλο του root σε μικρότερες μονάδες προνομίων. Αυτό είναι θεμελιώδες για τα container, επειδή πολλά workloads εξακολουθούν να εκτελούνται ως UID 0 μέσα στο container. Επομένως, το ερώτημα δεν είναι απλώς "είναι η διεργασία root;", αλλά μάλλον "ποιες capabilities διατηρήθηκαν, μέσα σε ποια namespaces, υπό ποιους περιορισμούς seccomp και MAC;" Γι' αυτό μια root διεργασία σε ένα container μπορεί να είναι σχετικά περιορισμένη, ενώ μια root διεργασία σε άλλο container μπορεί στην πράξη να είναι σχεδόν δυσδιάκριτη από το host root.

Το **seccomp** φιλτράρει τα syscalls και μειώνει το kernel attack surface που εκτίθεται στο workload. Συχνά είναι ο μηχανισμός που αποκλείει προφανώς επικίνδυνες κλήσεις, όπως `unshare`, `mount`, `keyctl` ή άλλα syscalls που χρησιμοποιούνται σε αλυσίδες breakout. Ακόμη και αν μια διεργασία διαθέτει μια capability που διαφορετικά θα επέτρεπε μια ενέργεια, το seccomp μπορεί και πάλι να αποκλείσει τη διαδρομή του syscall πριν ο kernel την επεξεργαστεί πλήρως.

Τα **AppArmor** και **SELinux** προσθέτουν Mandatory Access Control πάνω από τους κανονικούς ελέγχους filesystem και προνομίων. Είναι ιδιαίτερα σημαντικά, επειδή εξακολουθούν να έχουν σημασία ακόμη και όταν ένα container διαθέτει περισσότερες capabilities από όσες θα έπρεπε. Ένα workload μπορεί να έχει το θεωρητικό προνόμιο να επιχειρήσει μια ενέργεια, αλλά και πάλι να εμποδίζεται από την ολοκλήρωσή της, επειδή το label ή το profile του απαγορεύει την πρόσβαση στη σχετική διαδρομή, στο αντικείμενο ή στη λειτουργία.

Τέλος, υπάρχουν επιπλέον layers hardening που λαμβάνουν λιγότερη προσοχή αλλά έχουν τακτικά σημασία σε πραγματικές επιθέσεις: `no_new_privs`, masked procfs paths, read-only system paths, read-only root filesystems και προσεκτικά runtime defaults. Αυτοί οι μηχανισμοί συχνά σταματούν το "τελευταίο βήμα" ενός compromise, ιδιαίτερα όταν ένας attacker προσπαθεί να μετατρέψει την εκτέλεση κώδικα σε ευρύτερη απόκτηση προνομίων.

Ο υπόλοιπος φάκελος εξηγεί καθέναν από αυτούς τους μηχανισμούς με περισσότερες λεπτομέρειες, συμπεριλαμβανομένου του τι κάνει πραγματικά το kernel primitive, πώς μπορείτε να τον παρατηρήσετε τοπικά, πώς τον χρησιμοποιούν τα συνηθισμένα runtimes και πώς οι operators τον αποδυναμώνουν κατά λάθος.
