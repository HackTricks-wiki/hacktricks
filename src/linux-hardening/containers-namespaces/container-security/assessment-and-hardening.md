# Оцінювання та посилення безпеки

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

Якісне оцінювання контейнера має дати відповіді на два паралельні запитання. По-перше, що може зробити зловмисник із поточного workload? По-друге, які рішення оператора це уможливили? Інструменти переліку допомагають відповісти на перше запитання, а рекомендації з посилення безпеки — на друге. Якщо розмістити обидві теми на одній сторінці, вона буде кориснішим довідником для практичної роботи, а не просто каталогом способів втечі.

Важливо враховувати, що в багатьох старіших описах контейнерів мовчки припускаються **rootful runtime**, **відсутність ізоляції user namespace** і часто **cgroup v1**. Тепер ці припущення не можна вважати безпечними. Перш ніж витрачати час на старі примітиви втечі, з'ясуйте, чи є workload rootless або userns-remapped, чи використовує хост cgroup v2, а також чи застосовують Kubernetes або runtime стандартні профілі seccomp та AppArmor. Ці деталі часто визначають, чи досі працює відомий спосіб прориву.

## Інструменти переліку

Кілька інструментів і надалі корисні для швидкого аналізу середовища контейнера:

- `linpeas` виявляє багато ознак контейнера, змонтовані сокети, набори capabilities, небезпечні файлові системи та підказки щодо можливих способів прориву.
- `CDK` спеціалізується на середовищах контейнерів і містить засоби переліку, а також деякі автоматизовані перевірки на втечу.
- `amicontained` — легкий інструмент, корисний для виявлення обмежень контейнера, capabilities, доступу до namespace та ймовірних класів прориву.
- `deepce` — ще один інструмент переліку, орієнтований на контейнери, з перевірками способів прориву.
- `grype` стане в пригоді, якщо оцінювання охоплює пошук вразливостей у пакетах образу, а не лише аналіз втечі під час виконання.
- `Tracee` корисний, коли потрібні **дані про виконання**, а не лише статичний аналіз стану безпеки, особливо для виявлення підозрілого запуску процесів, доступу до файлів і збору подій з урахуванням контейнерів.
- `Inspektor Gadget` корисний під час розслідувань у Kubernetes та на Linux-хостах, коли потрібна видимість на основі eBPF з прив'язкою до pod, контейнерів, namespace та інших високорівневих сутностей.

Цінність цих інструментів — у швидкості та охопленні, а не в безпомилковості. Вони допомагають швидко оцінити загальний рівень захищеності, але цікаві результати все одно потрібно вручну інтерпретувати з урахуванням фактичної моделі runtime, namespace, capabilities та монтувань.

## Пріоритети посилення безпеки

Найважливіші принципи посилення безпеки концептуально прості, хоча їх реалізація залежить від платформи. Уникайте привілейованих контейнерів. Не монтуйте сокети runtime. Не надавайте контейнерам доступ на запис до шляхів хоста, якщо для цього немає конкретної причини. За можливості використовуйте user namespace або rootless-виконання. Відкидайте всі capabilities і додавайте лише ті, які справді потрібні workload. Не вимикайте seccomp, AppArmor та SELinux для усунення проблем сумісності застосунку. Обмежуйте ресурси, щоб скомпрометований контейнер не міг легко порушити роботу хоста.

Не менш важливі належна робота з образами та гігієна збірки. Використовуйте мінімальні образи, регулярно перезбирайте їх, скануйте, де це практично можливо, вимагайте підтвердження походження та не зберігайте секрети в шарах. Контейнер, що працює від непривілейованого користувача, має невеликий образ і обмежений набір системних викликів та capabilities, захистити набагато простіше, ніж великий універсальний образ, який запускається від root з привілеями, еквівалентними привілеям хоста, і має попередньо встановлені засоби налагодження.

Для Kubernetes сучасні базові вимоги до безпеки суворіші, ніж досі вважають багато операторів. Вбудовані **Pod Security Standards** визначають `restricted` як профіль «сучасної найкращої практики»: `allowPrivilegeEscalation` має дорівнювати `false`, workload має запускатися від непривілейованого користувача, seccomp має бути явно встановлений у `RuntimeDefault` або `Localhost`, а набори capabilities потрібно максимально скоротити. Під час оцінювання це важливо, оскільки кластер, у якому використовуються лише мітки `warn` або `audit`, може здаватися захищеним на папері, але на практиці й далі дозволяти ризиковані pod.<sup>[[1]](#references)</sup>

Якщо в Pod змонтовано токен service account, оцінюйте його дозволи **окремо для кожного цільового namespace**. Правило, що дозволяє переглядати список Pod в одному namespace, не означає, що такий дозвіл є в іншому; токен, змонтований в іншому Pod, може мати інші права. Використовуйте `kubectl auth can-i list pods -n <target-namespace>` та `kubectl auth can-i list secrets -n <target-namespace>` з ідентичністю, яку перевіряєте. Дозвіл на перегляд списку Secret — серйозна зачіпка, оскільки відповідь може містити вміст Secret, але це не доводить наявність привілейованого токена. Для доступу до хоста також потрібні право створювати workload, яке можна використати, допуск запропонованого монтування `hostPath` та контекст безпеки вузла/Pod, що дозволяє потрібну файлову операцію. Див. [перевірки авторизації](https://kubernetes.io/docs/reference/access-authn-authz/authorization/) та [рекомендації RBAC щодо ескалації привілеїв](https://kubernetes.io/docs/concepts/security/rbac-good-practices/) Kubernetes.

## Запитання для сучасного первинного аналізу

Перш ніж переходити до окремих сторінок про втечу, дайте відповіді на ці короткі запитання:

1. Workload працює як **rootful**, **rootless** чи **userns-remapped**?
2. На вузлі використовується **cgroup v1** чи **cgroup v2**?
3. **seccomp** та **AppArmor/SELinux** налаштовано явно чи вони лише успадковуються, якщо доступні?
4. У Kubernetes namespace справді **застосовує** `baseline` або `restricted`, чи лише видає попередження/проводить аудит?

Корисні перевірки:

```bash
id
cat /proc/self/uid_map 2>/dev/null
cat /proc/self/gid_map 2>/dev/null
stat -fc %T /sys/fs/cgroup 2>/dev/null
cat /sys/fs/cgroup/cgroup.controllers 2>/dev/null
grep -E 'Seccomp|NoNewPrivs' /proc/self/status
cat /proc/1/attr/current 2>/dev/null
find /var/run/secrets -maxdepth 3 -type f 2>/dev/null | head
NS=$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace 2>/dev/null)
kubectl get ns "$NS" -o jsonpath='{.metadata.labels}' 2>/dev/null
kubectl get pod "$HOSTNAME" -n "$NS" -o jsonpath='{.spec.securityContext.supplementalGroupsPolicy}{"\n"}' 2>/dev/null
kubectl get pod "$HOSTNAME" -n "$NS" -o jsonpath='{.spec.securityContext.seccompProfile.type}{"\n"}{.spec.containers[*].securityContext.allowPrivilegeEscalation}{"\n"}{.spec.containers[*].securityContext.capabilities.drop}{"\n"}' 2>/dev/null
```

Що тут цікаво:

- Якщо `/proc/self/uid_map` показує, що root у контейнері зіставлено з **високим діапазоном UID хоста**, багато старих матеріалів про запис із правами root на хості стають менш релевантними, оскільки root у контейнері вже не еквівалентний root на хості.
- Якщо `/sys/fs/cgroup` має тип файлової системи `cgroup2fs`, старі матеріали, специфічні для **cgroup v1**, як-от зловживання `release_agent`, більше не мають бути першою версією, яку ви перевіряєте.
- Якщо seccomp і AppArmor лише неявно успадковуються, їхня переносимість може бути нижчою, ніж очікують захисники. У Kubernetes явне встановлення `RuntimeDefault` часто надійніше, ніж непомітна залежність від типових налаштувань вузла.
- Якщо для `supplementalGroupsPolicy` встановлено `Strict`, pod не має непомітно успадковувати додаткове членство в групах із `/etc/group` усередині образу, завдяки чому поведінка доступу до томів і файлів на основі груп стає передбачуванішою.
- Варто безпосередньо перевіряти мітки просторів імен, як-от `pod-security.kubernetes.io/enforce=restricted`. `warn` і `audit` корисні, але вони не заважають створенню ризикованого pod.

## Первинне сортування базового рівня середовища виконання

Перевірка базового рівня середовища виконання — це швидкий огляд, який допомагає визначити, чи схожий контейнер на звичайне ізольоване робоче навантаження, чи на точку опори в площині керування, що впливає на хост. Вона має зібрати достатньо фактів, щоб визначити, яку тему перевіряти наступною: зловживання сокетом середовища виконання, монтування хоста, простори імен, cgroups, capabilities або перевірку секретів в образі.

Корисні перевірки зсередини робочого навантаження:

```bash
id
hostname
cat /proc/1/cgroup 2>/dev/null
cat /proc/self/uid_map 2>/dev/null
grep -E 'CapEff|Seccomp|NoNewPrivs' /proc/self/status
stat -fc %T /sys/fs/cgroup 2>/dev/null
cat /sys/fs/cgroup/memory.max 2>/dev/null
cat /sys/fs/cgroup/pids.max 2>/dev/null
readlink /proc/self/ns/{pid,mnt,net,ipc,cgroup,user} 2>/dev/null
mount
find /run /var/run -maxdepth 3 \( -name docker.sock -o -name containerd.sock -o -name crio.sock -o -name podman.sock \) 2>/dev/null
```

Інтерпретація:

- Відсутні або необмежені `memory.max` / `pids.max` свідчать про слабкий контроль радіуса ураження, навіть без повноцінного виходу з контейнера.
- Root shell із `NoNewPrivs: 0`, широкими capabilities і permissive seccomp значно цікавіший за вузько налаштоване навантаження без прав root.
- Runtime sockets і доступні для запису монтування хоста зазвичай важливіші за kernel exploits, адже вони вже відкривають шлях до керування системою або файловою системою.
- Спільні простори імен PID, мережі, IPC або cgroup самі по собі не завжди дають змогу повністю вийти з контейнера, але полегшують пошук наступного кроку.

## Приклади вичерпання ресурсів

Обмеження ресурсів не надто ефектні, але вони є частиною безпеки контейнерів, оскільки обмежують радіус ураження в разі компрометації. Без обмежень пам’яті, CPU або PID простого shell може бути достатньо, щоб погіршити роботу хоста чи сусідніх навантажень.

Приклади тестів, що впливають на хост:

```bash
stress-ng --vm 1 --vm-bytes 1G --verify -t 5m
docker run -d --name malicious-container -c 512 busybox sh -c 'while true; do :; done'
nc -lvp 4444 >/dev/null & while true; do cat /dev/urandom | nc <target_ip> 4444; done
```

Ці приклади корисні, оскільки показують, що не кожен небезпечний наслідок роботи контейнера є повноцінним «escape». Слабкі обмеження cgroup все одно можуть перетворити code execution на реальний операційний вплив.

У середовищах на базі Kubernetes також перевіряйте, чи існують взагалі обмеження ресурсів, перш ніж вважати DoS суто теоретичною загрозою:

```bash
kubectl get pod "$HOSTNAME" -n "$NS" -o jsonpath='{range .spec.containers[*]}{.name}{" cpu="}{.resources.limits.cpu}{" mem="}{.resources.limits.memory}{"\n"}{end}' 2>/dev/null
cat /sys/fs/cgroup/pids.max 2>/dev/null
cat /sys/fs/cgroup/memory.max 2>/dev/null
cat /sys/fs/cgroup/cpu.max 2>/dev/null
```

## Інструменти для посилення безпеки

Для середовищ, орієнтованих на Docker, `docker-bench-security` залишається корисним базовим інструментом аудиту на стороні хоста, оскільки перевіряє поширені проблеми конфігурації відповідно до загальновизнаних рекомендацій бенчмарків. Рекомендації щодо runtime слід розглядати окремо, оскільки бенчмарк конфігурації не може визначити, чи вразливе встановлене середовище виконання до нещодавно розкритої вразливості. <sup>[[2]](#references)</sup>

```bash
git clone https://github.com/docker/docker-bench-security.git
cd docker-bench-security
sudo sh docker-bench-security.sh
```

Інструмент не замінює моделювання загроз, але він усе ще корисний для виявлення недбалих налаштувань daemon, монтування, мережі та runtime, які накопичуються з часом.

Для Kubernetes і середовищ із інтенсивним використанням runtime поєднуйте статичні перевірки з видимістю під час роботи:

- `Tracee` корисний для виявлення загроз під час роботи з урахуванням контейнерів і швидкої криміналістики, коли потрібно підтвердити, до чого саме отримало доступ скомпрометоване робоче навантаження.
- `Inspektor Gadget` корисний, коли під час оцінювання потрібна телеметрія на рівні ядра, пов’язана з подами, контейнерами, активністю DNS, виконанням файлів або мережевою поведінкою.

## Перевірки

Використовуйте ці команди для швидкої первинної перевірки під час оцінювання:

```bash
id
capsh --print 2>/dev/null
grep -E 'Seccomp|NoNewPrivs' /proc/self/status
cat /proc/self/uid_map 2>/dev/null
stat -fc %T /sys/fs/cgroup 2>/dev/null
mount
find / -maxdepth 3 \( -name docker.sock -o -name containerd.sock -o -name crio.sock -o -name podman.sock \) 2>/dev/null
```

Що тут цікаво:

- Процес root із широкими capabilities і `Seccomp: 0` потребує негайної уваги.
- Процес root, який також має **мапу UID 1:1**, набагато цікавіший за «root» усередині належно ізольованого user namespace.
- `cgroup2fs` зазвичай означає, що багато старих ланцюжків escape для **cgroup v1** — не найкраща відправна точка, тоді як відсутність `memory.max` або `pids.max` усе ще свідчить про слабкі засоби обмеження радіуса ураження.
- Підозрілі монтування та runtime-сокети часто дають швидший шлях до впливу, ніж будь-який kernel exploit.
- Поєднання слабких налаштувань runtime та слабких обмежень ресурсів зазвичай свідчить про загалом надто permissive середовище контейнерів, а не про одну окрему помилку.
