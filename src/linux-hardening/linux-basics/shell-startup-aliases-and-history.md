# Запуск оболонки, псевдоніми та історія

{{#include ../../banners/hacktricks-training.md}}

Команда оболонки може поводитися інакше, ніж виконуваний файл із такою самою назвою, якщо псевдонім, функція, файл запуску або змінна середовища змінює її роботу. Перевірте їх, перш ніж довіряти виводу команди або вважати, що скрипт використовує той самий PATH, що й інтерактивний сеанс.

## Перевірте поточну оболонку

```bash
printf '%s\n' "$SHELL" "$PATH"
type -a ls sudo curl 2>/dev/null
alias
command -V python3
history | tail -50
```

`type` і `command -V` показують, чи ім’я відповідає alias, function, builtin або файлу. `command -v` і `which` можуть по-різному показувати alias і function. Історія команд оболонки може розкрити команди або облікові дані, але вона може бути неповною, вимкненою або зберігатися в пам’яті до завершення сеансу.

Змінений `.bashrc` може визначити alias `sudo`, який імітує запит пароля, записує введену відповідь і передає її справжній команді. Це дає змогу перехоплювати облікові дані непомітно, не змінюючи виконуваний файл `sudo` або `PATH`.<sup>[[5]](#references)</sup> Оболонка має прочитати змінений файл запуску й розгорнути alias.<sup>[[7]](#references)</sup> За замовчуванням Bash у неінтерактивному режимі не розгортає alias, якщо не ввімкнено `expand_aliases`.<sup>[[6]](#references)</sup>

## Перевірте файли запуску й історії

```bash
ls -la ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zprofile ~/.bash_history ~/.zsh_history 2>/dev/null
ls -ld /etc/profile /etc/profile.d /etc/bash.bashrc 2>/dev/null
printenv HISTFILE HISTSIZE HISTCONTROL BASH_ENV ENV 2>/dev/null
```

Файл автозапуску, доступний для запису користувачу, може виконувати команди під час наступного запуску оболонки. Загальносистемний файл автозапуску або файл автозапуску привілейованого користувача є чутливішим, якщо обліковий запис із нижчими привілеями може його змінити. Неінтерактивний Bash також може читати файл, заданий у `BASH_ENV`; на сторінці [змінних середовища](linux-environment-variables.md#bash_env--env) описано цю поведінку та інші хуки інтерпретатора. Перш ніж стверджувати, що це шлях для закріплення, перевірте, які файли фактична оболонка читає під час входу в систему, в інтерактивних і неінтерактивних сеансах.

Також перевірте файли, які підключає загальносистемний файл автозапуску. Наприклад, літерал `source /opt/app/venv/bin/activate` у `/etc/bash.bashrc` виконує файл активації як shell-код, коли оболонка справді читає цей файл автозапуску. Перевірте файл активації, права доступу до symlink і батьківських каталогів, а також ACL; користувач із нижчими привілеями може впливати на привілейовану оболонку лише тоді, коли ця оболонка або привілейоване завдання згодом підключає цей файл. Якщо доступ на запис залежить від `sudoedit`, спочатку перевірте точне правило sudoers і встановлений пакет sudo із виправленнями постачальника; сам рядок версії upstream не підтверджує наявність [вразливості sudoedit до ін’єкції аргументів](../main-system-information/linux-privilege-escalation-checklist.md#sudo-and-suid-commands).

Перевірте історію команд, dotfiles і резервні копії на наявність секретів, як описано в розділі [користувачі та сеанси](../user-information/user-and-session-triage.md). Якщо привілейований скрипт шукає команди за назвою, поєднайте цю перевірку з [рекомендаціями щодо перехоплення PATH](linux-environment-variables.md#path).

## Перенаправлення запуску Zsh і скомпільовані файли

За типових налаштувань `RCS` zsh читає `$ZDOTDIR/.zshenv` перед звичайними запусками, зокрема під час виконання `zsh -c` і скриптів; якщо `ZDOTDIR` не задано, використовується `$HOME`. Якщо засіб запуску команд приймає карту середовища, перевірте, чи передає він будь-яку з цих змінних привілейованому процесу zsh. Тоді доступний для запису `.zshenv` може виконатися **до** тіла команди, яке засіб запуску перевіряє або вносить до списку дозволених. Для цього привілейований процес має успадкувати перенаправлений каталог; `zsh -f` пропускає користувацькі файли автозапуску, але не глобальний `zshenv` (зазвичай `/etc/zshenv`, хоча шляхи дистрибутивів відрізняються). На [сторінці про ін’єкцію zsh у macOS](../../macos-hardening/macos-security-and-privilege-escalation/macos-proces-abuse/macos-bash-applications-injection.md#zsh-zdotdir) наведено мінімальний приклад із `ZDOTDIR`.<sup>[[1]](#references)[[2]](#references)</sup>

Новіший і коректний `.zshenv.zwc` або `.zshrc.zwc` виконується замість відповідного текстового файла автозапуску. Якщо ви можете записувати у каталог автозапуску, скомпілюйте змінений файл, а потім відновіть текстовий файл, що виглядає нешкідливо: виконуваний код може залишитися у скомпільованій копії. Це приховування, а не шифрування. Наведений нижче тест у тимчасовому середовищі демонструє, чому недостатньо перевірити лише текстовий файл; він не змінює справжній домашній каталог.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
lab=$(mktemp -d)
printf '%s\n' 'print -r -- compiled > "$ZDOTDIR/result"' > "$lab/.zshenv"
zsh -f -c 'zcompile -R "$1"' _ "$lab/.zshenv"
printf '%s\n' 'print -r -- plaintext > "$ZDOTDIR/result"' > "$lab/.zshenv"
touch -d '2 minutes ago' "$lab/.zshenv"  # ensure the .zwc is newer
ZDOTDIR="$lab" zsh -c :
cat "$lab/result"  # compiled
zsh -f -c 'zcompile -t "$1"' _ "$lab/.zshenv.zwc"
```

Для реальної цілі визначте її ефективні значення `ZDOTDIR`/`HOME`, перевірте і текстові файли, і файли `.zwc`, а також перевірте часові мітки, власника та каталоги-батьки на можливість запису. Щоб файл `.zwc` мав пріоритет, він має відповідати файлу-джерелу й бути новішим за нього.<sup>[[1]](#references)[[3]](#references)</sup>
