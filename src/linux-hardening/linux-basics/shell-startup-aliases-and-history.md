# Запуск shell, псевдоніми та історія

{{#include ../../banners/hacktricks-training.md}}

Команда в shell може поводитися інакше, ніж виконуваний файл із такою самою назвою, якщо псевдонім, функція, файл запуску або змінна середовища змінює спосіб її виконання. Перевірте це, перш ніж довіряти виводу команди або припускати, що скрипт використовує той самий PATH, що й інтерактивний сеанс.

## Перевірка поточного shell

```bash
printf '%s\n' "$SHELL" "$PATH"
type -a ls sudo curl 2>/dev/null
alias
command -V python3
history | tail -50
```

`type` і `command -V` показують, чи відповідає ім’я псевдоніму, функції, вбудованій команді або файлу. `command -v` і `which` можуть по-різному визначати псевдоніми та функції. Історія команд оболонки може розкривати команди або облікові дані, але вона може бути неповною, вимкненою або зберігатися в пам’яті до завершення сеансу.

## Перевірте файли запуску та історії команд

```bash
ls -la ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zprofile ~/.bash_history ~/.zsh_history 2>/dev/null
ls -ld /etc/profile /etc/profile.d /etc/bash.bashrc 2>/dev/null
printenv HISTFILE HISTSIZE HISTCONTROL BASH_ENV ENV 2>/dev/null
```

Файл запуску, доступний для запису користувачу, може виконувати команди під час майбутнього запуску shell. Загальносистемний файл запуску або файл запуску привілейованого користувача є чутливішим, якщо його може змінювати обліковий запис із нижчими привілеями. Неінтерактивний Bash також може читати файл, указаний у `BASH_ENV`; на сторінці про [змінні середовища](linux-environment-variables.md#bash_env--env) пояснено цю поведінку та інші хуки інтерпретаторів. Перш ніж заявляти про можливість закріплення, перевірте, які саме файли читає фактична оболонка під час входу в систему, в інтерактивних і неінтерактивних сеансах.

Також перевірте файли, які підключає загальносистемний файл запуску. Наприклад, буквальний `source /opt/app/venv/bin/activate` у `/etc/bash.bashrc` виконує файл активації як код shell, коли оболонка справді читає цей файл запуску. Перевірте файл активації, права доступу до символічного посилання й батьківських каталогів, а також ACL; користувач із нижчими привілеями може вплинути на привілейовану оболонку, лише якщо ця оболонка або привілейоване завдання згодом підключить файл. Якщо доступ на запис залежить від `sudoedit`, спершу перевірте точне правило sudoers і встановлений пакет sudo з виправленнями постачальника; сама лише версія з upstream не підтверджує [вразливість sudoedit до ін’єкції аргументів](../main-system-information/linux-privilege-escalation-checklist.md#sudo-and-suid-commands).

Перевірте історію команд, dotfiles і резервні копії на наявність секретів, як описано в розділі [користувачі та сеанси](../user-information/user-and-session-triage.md). Якщо привілейований скрипт шукає команди за назвою, поєднайте цю перевірку з [рекомендаціями щодо перехоплення PATH](linux-environment-variables.md#path).
