# Запуск shell, aliases та історія

{{#include ../../banners/hacktricks-training.md}}

Команда shell може поводитися інакше, ніж виконуваний файл із такою самою назвою, якщо alias, функція, файл запуску або змінна середовища змінює спосіб її виконання. Перевірте їх, перш ніж довіряти виводу команди або вважати, що скрипт використовує той самий PATH, що й інтерактивний сеанс.

## Перевірка поточного shell

```bash
printf '%s\n' "$SHELL" "$PATH"
type -a ls sudo curl 2>/dev/null
alias
command -V python3
history | tail -50
```

`type` і `command -V` показують, чи відповідає ім’я alias, функції, вбудованій команді або файлу. `command -v` і `which` можуть по-різному показувати alias і функції. Історія команд shell може розкрити команди або облікові дані, але вона може бути неповною, вимкненою або зберігатися в пам’яті до завершення сеансу.

## Перевірка файлів запуску та історії

```bash
ls -la ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zprofile ~/.bash_history ~/.zsh_history 2>/dev/null
ls -ld /etc/profile /etc/profile.d /etc/bash.bashrc 2>/dev/null
printenv HISTFILE HISTSIZE HISTCONTROL BASH_ENV ENV 2>/dev/null
```

Файл автозапуску, доступний для запису користувачу, може виконувати команди під час майбутнього запуску оболонки. Загальносистемний файл автозапуску або файл автозапуску привілейованого користувача є чутливішим, якщо обліковий запис із нижчими привілеями може його змінювати. Неінтерактивний Bash також може читати файл, указаний у `BASH_ENV`; на сторінці [змінних середовища](linux-environment-variables.md#bash_env--env) описано цю поведінку й інші хуки інтерпретатора. Перш ніж заявляти про можливість закріплення через автозапуск, перевірте, які саме файли фактично читає оболонка під час запуску сеансів із входом у систему, інтерактивних і неінтерактивних сеансів.

Також перевірте файли, які підключає загальносистемний файл автозапуску. Наприклад, буквальна команда `source /opt/app/venv/bin/activate` у `/etc/bash.bashrc` виконає файл активації як shell-код, якщо оболонка справді читає цей файл автозапуску. Перевірте файл активації, дозволи на символічне посилання та батьківські каталоги, а також ACL; користувач із нижчими привілеями може вплинути на привілейовану оболонку лише за умови, що ця оболонка або привілейоване завдання згодом підключить цей файл. Якщо доступ на запис залежить від `sudoedit`, спершу перевірте точне правило sudoers і встановлений пакет sudo із виправленнями постачальника; самого рядка версії upstream недостатньо, щоб підтвердити [вразливість sudoedit до ін’єкції аргументів](../main-system-information/linux-privilege-escalation-checklist.md#sudo-and-suid-commands).

Перевірте історію команд, dotfiles і резервні копії на наявність секретів, як описано в розділі [користувачі та сеанси](../user-information/user-and-session-triage.md). Якщо привілейований скрипт знаходить команди за назвою, поєднайте цю перевірку з [рекомендаціями щодо перехоплення PATH](linux-environment-variables.md#path).
