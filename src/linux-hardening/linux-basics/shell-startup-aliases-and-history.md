# Запуск shell, псевдоніми та історія команд

{{#include ../../banners/hacktricks-training.md}}

Команда shell може поводитися інакше, ніж виконуваний файл з такою самою назвою, якщо alias, функція, файл запуску або змінна середовища змінює спосіб її виконання. Перевірте їх, перш ніж довіряти виводу команди або припускати, що скрипт використовує той самий PATH, що й інтерактивний сеанс.

## Перевірка поточного shell

```bash
printf '%s\n' "$SHELL" "$PATH"
type -a ls sudo curl 2>/dev/null
alias
command -V python3
history | tail -50
```

`type` і `command -V` показують, чи ім’я відповідає alias, функції, вбудованій команді або файлу. `command -v` і `which` можуть по-різному показувати alias і функції. Історія shell може розкривати команди або облікові дані, але вона може бути неповною, вимкненою або зберігатися в пам’яті до завершення сеансу.

## Перевірте файли запуску та історії

```bash
ls -la ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zprofile ~/.bash_history ~/.zsh_history 2>/dev/null
ls -ld /etc/profile /etc/profile.d /etc/bash.bashrc 2>/dev/null
printenv HISTFILE HISTSIZE HISTCONTROL BASH_ENV ENV 2>/dev/null
```

Файл запуску, доступний для запису користувачу, може виконувати команди під час майбутнього запуску shell. Загальносистемний файл запуску або файл запуску привілейованого користувача є чутливішим, якщо обліковий запис із нижчими привілеями може його змінювати. Неінтерактивний Bash також може читати файл, указаний у `BASH_ENV`; на сторінці [змінних середовища](linux-environment-variables.md#bash_env--env) пояснюється така поведінка та інші гачки інтерпретатора. Перш ніж стверджувати, що існує шлях до persistence, перевірте, які саме файли читає shell під час входу в систему, в інтерактивних і неінтерактивних сеансах.

Також перевірте файли, які підключає загальносистемний файл запуску. Наприклад, буквальний рядок `source /opt/app/venv/bin/activate` у `/etc/bash.bashrc` виконує файл активації як shell-код, коли shell справді читає цей файл запуску. Перевірте файл активації, дозволи на symlink і батьківські каталоги, а також ACL; користувач із нижчими привілеями може впливати на привілейований shell лише тоді, коли цей shell або привілейоване завдання згодом підключає цей файл. Якщо доступ на запис залежить від `sudoedit`, спершу перевірте точне правило sudoers і встановлений пакет sudo із виправленнями постачальника; самого рядка версії upstream недостатньо, щоб підтвердити [вразливість sudoedit до ін’єкції аргументів](../main-system-information/linux-privilege-escalation-checklist.md#sudo-and-suid-commands).

Перевірте історію команд, dotfiles і резервні копії на наявність секретів, як описано в розділі [користувачів і сеансів](../user-information/user-and-session-triage.md). Якщо привілейований скрипт знаходить команди за назвою, поєднайте цю перевірку з [рекомендаціями щодо перехоплення PATH](linux-environment-variables.md#path).
