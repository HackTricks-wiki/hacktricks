# Запуск shell, псевдоніми та історія команд

{{#include ../../banners/hacktricks-training.md}}

Команда shell може поводитися інакше, ніж виконуваний файл із такою самою назвою, якщо псевдонім, функція, файл запуску або змінна середовища змінює спосіб її виконання. Перевірте це, перш ніж довіряти виводу команди або припускати, що скрипт використовує той самий PATH, що й інтерактивний сеанс.

## Перевірка поточної оболонки

```bash
printf '%s\n' "$SHELL" "$PATH"
type -a ls sudo curl 2>/dev/null
alias
command -V python3
history | tail -50
```

`type` і `command -V` показують, чи відповідає ім’я псевдоніму, функції, вбудованій команді або файлу. `command -v` і `which` можуть по-різному визначати псевдоніми та функції. Історія команд оболонки може розкрити команди чи облікові дані, але вона може бути неповною, вимкненою або зберігатися в пам’яті до завершення сеансу.

## Перегляд файлів запуску та історії команд

```bash
ls -la ~/.bashrc ~/.bash_profile ~/.profile ~/.zshrc ~/.zprofile ~/.bash_history ~/.zsh_history 2>/dev/null
ls -ld /etc/profile /etc/profile.d /etc/bash.bashrc 2>/dev/null
printenv HISTFILE HISTSIZE HISTCONTROL BASH_ENV ENV 2>/dev/null
```

Файл запуску, доступний для запису користувачу, може виконувати команди під час наступного запуску shell. Загальносистемний файл запуску або файл запуску привілейованого користувача становить більший ризик, якщо його може змінювати обліковий запис із нижчими привілеями. Неінтерактивний Bash також може читати файл, указаний у `BASH_ENV`; на сторінці про [змінні середовища](linux-environment-variables.md#bash_env--env) пояснено цю поведінку та інші механізми підключення інтерпретаторів. Перш ніж стверджувати, що це шлях для persistence, перевірте, які саме файли читає shell для сеансів входу, інтерактивних і неінтерактивних сеансів.

Також перевірте файли, які підключає загальносистемний файл запуску. Наприклад, буквальний `source /opt/app/venv/bin/activate` у `/etc/bash.bashrc` виконає файл активації як shell-код, коли shell справді прочитає цей файл запуску. Перевірте файл активації, права symlink і батьківських каталогів, а також ACL; користувач із нижчими привілеями може впливати на привілейований shell лише якщо цей shell або привілейоване завдання згодом підключить цей файл. Якщо доступ на запис залежить від `sudoedit`, спершу перевірте точне правило sudoers і встановлений пакет sudo із виправленнями постачальника; самої версії upstream недостатньо, щоб підтвердити [вразливість sudoedit до ін'єкції аргументів](../main-system-information/linux-privilege-escalation-checklist.md#sudo-and-suid-commands).

Перевірте історію команд, dotfiles і резервні копії на наявність секретів, як описано в розділі [користувачі та сеанси](../user-information/user-and-session-triage.md). Якщо привілейований скрипт шукає команди за іменем, поєднайте цю перевірку з [рекомендаціями щодо перехоплення PATH](linux-environment-variables.md#path).

## Перенаправлення запуску Zsh і скомпільовані файли

За стандартних налаштувань `RCS` zsh читає `$ZDOTDIR/.zshenv` перед звичайними запусками, зокрема перед `zsh -c` і скриптами; якщо `ZDOTDIR` не задано, використовується `$HOME`. Якщо засіб запуску команд приймає карту змінних середовища, перевірте, чи передає він будь-яку з цих змінних привілейованому процесу zsh. Тоді доступний для запису `.zshenv` може виконатися **до** тіла команди, яке засіб запуску перевіряє або дозволяє за списком. Для цього привілейований процес має успадкувати перенаправлений каталог; `zsh -f` пропускає файли запуску користувача, але не глобальний `zshenv` (часто `/etc/zshenv`, але шляхи залежать від дистрибутива). На сторінці про [ін'єкцію zsh у macOS](../../macos-hardening/macos-security-and-privilege-escalation/macos-proces-abuse/macos-bash-applications-injection.md#zsh-zdotdir) наведено мінімальний приклад із `ZDOTDIR`.<sup>[[1]](#references)[[2]](#references)</sup>

Новіший і коректний `.zshenv.zwc` або `.zshrc.zwc` виконується замість відповідного текстового файла запуску. Якщо ви можете записувати у каталог запуску, скомпілювавши змінений файл, а потім відновивши текстовий файл, що має нешкідливий вигляд, можна залишити виконуваний код у скомпільованій копії. Це маскування, а не шифрування. Наведений нижче тест у тимчасовому середовищі показує, чому недостатньо перевіряти лише текстовий файл; він не змінює справжній домашній каталог.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
lab=$(mktemp -d)
printf '%s\n' 'print -r -- compiled > "$ZDOTDIR/result"' > "$lab/.zshenv"
zsh -f -c 'zcompile -R "$1"' _ "$lab/.zshenv"
printf '%s\n' 'print -r -- plaintext > "$ZDOTDIR/result"' > "$lab/.zshenv"
touch -d '2 minutes ago' "$lab/.zshenv"  # ensure the .zwc is newer
ZDOTDIR="$lab" zsh -c :
cat "$lab/result"  # compiled
zsh -f -c 'zcompile -t "$1"' _ "$lab/.zshenv.zwc"
```

Для реальної цілі визначте фактичні значення `ZDOTDIR`/`HOME`, перевірте текстові файли та файли `.zwc`, а також дати зміни, власника й батьківські каталоги, доступні для запису. Файл `.zwc` має відповідати вихідному файлу й бути новішим, щоб мати пріоритет.<sup>[[1]](#references)[[3]](#references)</sup>
