# DDexec / EverythingExec

## Контекст

У Linux, щоб запустити програму, вона має існувати як файл і бути певним чином доступною через ієрархію файлової системи (саме так працює `execve()`). Цей файл може розташовуватися на диску або в RAM (tmpfs, memfd), але вам потрібен шлях до файлу. Це значно спрощує контроль того, що запускається в Linux-системі, виявлення загроз і інструментів атакувальника або повне запобігання спробам їх виконання (_наприклад_, заборона непривілейованим користувачам розміщувати виконувані файли будь-де).

Але ця техніка покликана все це змінити. Якщо ви не можете запустити потрібний процес... **тоді ви перехоплюєте вже наявний**.

Ця техніка дає змогу **обійти поширені методи захисту, такі як read-only, noexec, file-name whitelisting і hash whitelisting**.<sup>[[1]](#references)</sup>

## Залежності

Для роботи фінальний скрипт залежить від наведених нижче інструментів. Вони мають бути доступні в системі, яку ви атакуєте (типово всі вони є всюди):
```
dd
bash | zsh | ash (busybox)
head
tail
cut
grep
od
readlink
wc
tr
base64
```
## The technique

Якщо ви можете довільно змінювати пам'ять процесу, то можете заволодіти ним. Це можна використати для перехоплення вже наявного процесу та його заміни іншою програмою. Цього можна досягти або за допомогою syscall `ptrace()` (що вимагає можливості виконувати syscalls або наявності `gdb` у системі), або, що цікавіше, шляхом запису до `/proc/$pid/mem`.<sup>[[1]](#references)</sup>

Файл `/proc/$pid/mem` є однозначним відображенням усього адресного простору процесу (_напр._ від `0x0000000000000000` до `0x7ffffffffffff000` в x86-64). Це означає, що читання з цього файлу або запис до нього за зміщенням `x` еквівалентні читанню або зміні вмісту за віртуальною адресою `x`.

Тепер маємо чотири основні проблеми:

- Загалом змінювати файл можуть лише root і власник програми.
- ASLR.
- Якщо спробувати прочитати адресу, яка не відображена в адресному просторі програми, або записати за нею, ми отримаємо помилку I/O.

Ці проблеми мають рішення, які, хоча й не є ідеальними, цілком придатні:

- Більшість shell-інтерпретаторів дозволяють створювати file descriptors, які потім успадковуються дочірніми процесами. Ми можемо створити fd, що вказує на файл `mem` shell з дозволами на запис... тоді дочірні процеси, які використовують цей fd, зможуть змінювати пам'ять shell.
- ASLR взагалі не є проблемою: ми можемо перевірити файл `maps` shell або будь-який інший файл із procfs, щоб отримати інформацію про адресний простір процесу.
- Отже, нам потрібно виконати `lseek()` над файлом. Із shell це неможливо зробити без використання сумнозвісної `dd`.

### Детальніше

Ці кроки відносно прості, і для їх розуміння не потрібні спеціальні знання:<sup>[[1]](#references)</sup>

- Проаналізувати binary, яку ми хочемо запустити, і loader, щоб визначити, які mappings їм потрібні. Потім створити "shell"code, який загалом виконуватиме ті самі кроки, що й kernel під час кожного виклику `execve()`:
- Створити зазначені mappings.
- Прочитати binaries у них.
- Налаштувати permissions.
- Нарешті, ініціалізувати stack аргументами програми та розмістити auxiliary vector (потрібний loader).
- Перейти до loader і дозволити йому виконати решту (завантажити libraries, потрібні програмі).
- Отримати з файлу `syscall` адресу, на яку процес повернеться після syscall, який він виконує.
- Перезаписати це місце, яке буде executable, нашим shellcode (через `mem` можна змінювати unwritable pages).
- Передати програму, яку ми хочемо запустити, у stdin процесу (його прочитає `read()` цей "shell"code).
- На цьому етапі loader має завантажити необхідні libraries для нашої програми та перейти до неї.

**Перегляньте tool у** [**https://github.com/arget13/DDexec**](https://github.com/arget13/DDexec).<sup>[[1]](#references)</sup>

## EverythingExec

Існує кілька альтернатив `dd`, однією з яких є `tail`, що наразі є програмою за замовчуванням для виконання `lseek()` через файл `mem` (це була єдина причина використання `dd`). Такими альтернативами є:<sup>[[1]](#references)</sup>
```bash
tail
hexdump
cmp
xxd
```
Встановивши змінну `SEEKER`, можна змінити використовуваний механізм пошуку, _наприклад_:
```bash
SEEKER=cmp bash ddexec.sh ls -l <<< $(base64 -w0 /bin/ls)
```
Якщо ви знайдете інший дійсний seeker, не реалізований у скрипті, ви все одно можете його використати, задавши змінну `SEEKER_ARGS`:
```bash
SEEKER=xxd SEEKER_ARGS='-s $offset' zsh ddexec.sh ls -l <<< $(base64 -w0 /bin/ls)
```
Заблокуйте це, EDR.
