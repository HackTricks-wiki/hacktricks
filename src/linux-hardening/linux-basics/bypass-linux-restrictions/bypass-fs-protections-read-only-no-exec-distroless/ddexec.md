# DDexec / EverythingExec

{{#include ../../../../banners/hacktricks-training.md}}

## Контекст

Linux зазвичай запускає програми з виконуваних файлів, що зберігаються на диску або в пам’яті. Він може визначити виконуваний файл за шляхом або файловим дескриптором, тож звичайний шлях у файловій системі потрібен не завжди.<sup>[[2]](#references)</sup>

DDexec / EverythingExec використовує пам’ять **вже запущеного процесу**. На сторінці [Fileless Execution у Linux](../../../post-exploitation/linux-fileless-execution.md) розглянуто виконання з анонімних файлів, а також пов’язані з ним виявлення та збір криміналістичних даних; в [огляді обходів захисту пам’яті](index.html#memory-bypasses) також наведено посилання на MemExec і Memdlopen.<sup>[[1]](#references)</sup>

Ця техніка дає змогу **обходити поширені механізми захисту, як-от режими лише для читання, noexec, списки дозволених імен файлів та списки дозволених хешів**.<sup>[[1]](#references)</sup>

## Залежності

Для роботи кінцевого скрипту потрібні наведені нижче інструменти. Вони мають бути доступні в системі, яку ви атакуєте (за замовчуванням усі вони є майже всюди):

```
dd
bash | zsh | ash (busybox)
head
tail
cut
grep
od
readlink
wc
tr
base64
```

## Техніка

Якщо ви можете довільно змінювати пам’ять процесу, то можете захопити його. Це можна використати, щоб перехопити вже наявний процес і замінити його іншою програмою. Цього можна досягти або за допомогою syscall `ptrace()` (для цього потрібна можливість виконувати syscalls або наявність gdb у системі), або, що цікавіше, записуючи до `/proc/$pid/mem`.<sup>[[1]](#references)</sup>

Файл `/proc/$pid/mem` є відображенням усього адресного простору процесу один до одного (_наприклад_, від `0x0000000000000000` до `0x7ffffffffffff000` в x86-64). Це означає, що читання з цього файлу або запис до нього за зсувом `x` — це те саме, що читання віртуальної адреси `x` або зміна вмісту за нею.

Тепер маємо розв’язати чотири основні проблеми:

- Загалом змінювати файл можуть лише root і власник програми.
- ASLR.
- Якщо спробувати прочитати або записати адресу, не відображену в адресному просторі програми, отримаємо помилку вводу-виводу.

Для цих проблем є рішення, які, хоч і не ідеальні, але цілком придатні:

- Більшість shell-інтерпретаторів дозволяють створювати файлові дескриптори, які потім успадковують дочірні процеси. Ми можемо створити fd, що вказує на файл `mem` shell із правами на запис... тож дочірні процеси, які використовують цей fd, зможуть змінювати пам’ять shell.
- ASLR навіть не є проблемою: ми можемо перевірити файл `maps` shell або будь-який інший файл у procfs, щоб отримати інформацію про адресний простір процесу.
- Тож нам потрібно виконати `lseek()` для файлу. Із shell цього не можна зробити, хіба що за допомогою сумнозвісного `dd`.

### Детальніше

Кроки відносно прості й не потребують спеціальних знань для розуміння:<sup>[[1]](#references)</sup>

- Розібрати бінарний файл, який ми хочемо запустити, і loader, щоб визначити, які мапінги їм потрібні. Потім створити «shell»code, який, загалом кажучи, виконає ті самі кроки, що й ядро під час кожного виклику `execve()`:
  - Створити ці мапінги.
  - Зчитати до них бінарні файли.
  - Налаштувати права доступу.
  - Нарешті ініціалізувати стек аргументами для програми й розмістити допоміжний вектор (потрібний loader).
  - Перейти до loader і дозволити йому виконати решту (завантажити потрібні програмі бібліотеки).
- Отримати з файлу `syscall` адресу, на яку повернеться процес після виконання syscall.
- Перезаписати цю ділянку, яка буде виконуваною, нашим shellcode (через `mem` можна змінювати сторінки, доступні лише для читання).
- Передати програму, яку ми хочемо запустити, у stdin процесу (її зчитає `read()` із цього «shell»code).
- На цьому етапі loader має завантажити необхідні для нашої програми бібліотеки й перейти до неї.

**Ознайомтеся з інструментом:** [**https://github.com/arget13/DDexec**](https://github.com/arget13/DDexec).<sup>[[1]](#references)</sup>

## EverythingExec

Існує кілька альтернатив `dd`. Одна з них — `tail`, яка зараз є програмою за замовчуванням для виконання `lseek()` у файлі `mem` (це була єдина причина використовувати `dd`). Ці альтернативи:<sup>[[1]](#references)</sup>

```bash
tail
hexdump
cmp
xxd
```

Задавши змінну `SEEKER`, можна змінити використовуваний пошуковий механізм, _наприклад_:

```bash
SEEKER=cmp bash ddexec.sh ls -l <<< $(base64 -w0 /bin/ls)
```

Якщо ви знайдете інший дійсний seeker, який не реалізовано у скрипті, ви все одно можете скористатися ним, задавши змінну `SEEKER_ARGS`:

```bash
SEEKER=xxd SEEKER_ARGS='-s $offset' zsh ddexec.sh ls -l <<< $(base64 -w0 /bin/ls)
```

Блокуйте це, EDRs.
