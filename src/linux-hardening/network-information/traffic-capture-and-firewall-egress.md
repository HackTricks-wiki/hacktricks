# Аналіз перехоплення трафіку, firewall і вихідних з’єднань

{{#include ../../banners/hacktricks-training.md}}

Знайшовши [локальні прослуховувачі та Unix-сокети](local-network-and-socket-triage.md), перевірте, які інтерфейси передають їхній трафік і які правила firewall або проксі впливають на доступність. Служба, доступна лише через loopback, може передавати конфіденційні HTTP-заголовки, навіть якщо до неї не можна під’єднатися з іншого хоста.

## Перевірте дозволи на перехоплення та виберіть інтерфейс

```bash
ip -br addr
ip route
getcap "$(command -v dumpcap)" 2>/dev/null
tcpdump -D 2>/dev/null
```

`dumpcap` може мати можливість захоплювати пакети, навіть якщо поточний користувач не має доступу до sudo. Перевірте фактичні capabilities виконуваного файла та дозволи групи. Захоплюйте трафік лише з найменшої корисної кількості інтерфейсів, протягом найкоротшого часу та з відповідним фільтром; захоплені дані можуть містити облікові дані або персональну інформацію.

```bash
sudo tcpdump -i lo -s 0 -w /tmp/loopback.pcap 'tcp port 8080'
tshark -r /tmp/loopback.pcap -Y 'http.request' -T fields -e ip.src -e http.host -e http.request.uri
tcpflow -r /tmp/loopback.pcap 2>/dev/null
```

`tcpflow` відновлює відкриті текстові потоки TCP; `tshark` може фільтрувати трафік і витягувати поля з capture. Для TLS-трафіку розшифрування потребує ключів кінцевих вузлів або підтримуваного клієнта, налаштованого на `SSLKEYLOGFILE` до встановлення з’єднання. На [сторінці з первинного аналізу локальної мережі](local-network-and-socket-triage.md#tls-key-logging) описано цей процес. Не вважайте зашифрований capture читабельним відкритим текстом.

Збережені артефакти інциденту можуть змінити цю оцінку. [Core dump Linux — це образ пам’яті процесу](https://man7.org/linux/man-pages/man5/core.5.html), у якому може зберегтися ключ сеансу; якщо читабельний дамп і capture пакетів отримано від того самого процесу й сеансу, аналітик може мати змогу розшифрувати цей трафік. Спершу складіть перелік шляхів до артефактів і дозволів до них, а потім окремо перевірте ідентичність процесу, час capture, протокол і формат ключа. Розшифрований трафік або відновлений архів — це зачіпка щодо розголошення даних, а не доказ доступу до іншого облікового запису: будь-які часткові дані ключа SSH потрібно відновити, зіставити з відповідним відкритим ключем і перевірити, чи приймає його політика SSH цього облікового запису. Не виводьте вміст core dump або payload capture у результати широкого переліку.

## Визначте рівні firewall

```bash
sudo nft list ruleset 2>/dev/null
sudo iptables-save 2>/dev/null
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null
```

`nftables` і `iptables` можуть бути доступні через обгортки дистрибутива, як-от UFW або firewalld. Перегляньте активні правила та збережену конфігурацію обгортки: правило, видиме в одному представленні, могло бути створене іншим інструментом. Перш ніж пов’язувати блокування служби з певним правилом, перевірте інтерфейс, напрямок, джерело, призначення, протокол, порт і стан з’єднання. Цілеспрямований приклад див. у розділі [перевірка правил nftables](local-network-and-socket-triage.md#nftables-review-and-authorized-rule-changes).

## Перевірка вихідного трафіку та поведінки proxy

```bash
ip route get 1.1.1.1
getent hosts example.com
curl -I --connect-timeout 3 https://example.com/
printenv http_proxy https_proxy all_proxy no_proxy 2>/dev/null
```

Відрізняйте збій DNS від збоїв TCP, TLS або проксі. Перевіряйте конкретне призначення та протокол, актуальні для оцінювання: доступність через ICMP не означає, що дозволено TCP або UDP. Якщо налаштовано проксі, порівняйте запит через проксі з тим самим запитом до тієї самої цілі з урахуванням відповідних правил `no_proxy`. Локальне перенаправлення порту також може зробити сервіс loopback доступним в іншому місці, тож перевірте активні слухачі та SSH-тунелі, якщо дані брандмауера не збігаються зі спостережуваною доступністю.
