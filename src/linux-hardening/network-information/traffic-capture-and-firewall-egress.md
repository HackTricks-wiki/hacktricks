# Аналіз перехоплення трафіку, firewall та вихідних з’єднань

{{#include ../../banners/hacktricks-training.md}}

Після виявлення [локальних слухачів і Unix-сокетів](local-network-and-socket-triage.md) перевірте, через які інтерфейси проходить їхній трафік і які правила firewall або проксі впливають на доступність. Служба, доступна лише через loopback, може передавати чутливі HTTP-заголовки, навіть якщо до неї неможливо підключитися з іншого хоста.

## Перевірте дозволи на перехоплення та виберіть інтерфейс

```bash
ip -br addr
ip route
getcap "$(command -v dumpcap)" 2>/dev/null
tcpdump -D 2>/dev/null
```

`dumpcap` може мати можливості захоплення пакетів, навіть якщо поточний користувач не має доступу до sudo. Перевірте фактичні capabilities виконуваного файла та дозволи груп. Захоплюйте трафік лише з найменшої корисної кількості інтерфейсів, протягом найкоротшого потрібного часу та з відповідним фільтром; захоплені дані можуть містити облікові дані або персональну інформацію.

```bash
sudo tcpdump -i lo -s 0 -w /tmp/loopback.pcap 'tcp port 8080'
tshark -r /tmp/loopback.pcap -Y 'http.request' -T fields -e ip.src -e http.host -e http.request.uri
tcpflow -r /tmp/loopback.pcap 2>/dev/null
```

`tcpflow` реконструює відкриті TCP-потоки; `tshark` може фільтрувати дані захоплення й витягувати з них поля. Для трафіку TLS розшифрування потребує ключів кінцевих вузлів або підтримуваного клієнта, налаштованого на використання `SSLKEYLOGFILE` до встановлення з’єднання. [Сторінка з первинного аналізу локальної мережі](local-network-and-socket-triage.md#tls-key-logging) описує цей процес. Не вважайте зашифроване захоплення даних читабельним відкритим текстом.

Збережені артефакти інциденту можуть змінити цю оцінку. [Дамп ядра Linux — це образ пам’яті процесу](https://man7.org/linux/man-pages/man5/core.5.html), у якому може зберегтися ключ сеансу; якщо читабельний дамп і захоплення пакетів отримані від того самого процесу й сеансу, аналітик може мати змогу розшифрувати цей трафік. Спершу складіть перелік шляхів до артефактів і прав доступу, а потім окремо перевірте ідентичність процесу, час захоплення, протокол і формат ключа. Розшифрований трафік або відновлений архів — це зачіпка щодо витоку даних, а не доказ доступу до іншого облікового запису: будь-який частковий матеріал ключа SSH потрібно реконструювати, зіставити з відповідним відкритим ключем і перевірити, чи відповідає він політиці SSH цього облікового запису. Не виводьте вміст дампів пам’яті або корисне навантаження захоплених пакетів у результати широкого переліку даних.

## Визначення рівнів брандмауера

```bash
sudo nft list ruleset 2>/dev/null
sudo iptables-save 2>/dev/null
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null
```

`nftables` і `iptables` можуть бути доступні через обгортки дистрибутива, як-от UFW або firewalld. Перегляньте активні правила та збережену конфігурацію обгортки: правило, видиме в одному представленні, могло бути створене іншим інструментом. Перш ніж пов’язувати блокування служби з певним правилом, перевірте інтерфейс, напрямок, джерело, призначення, протокол, порт і стан з’єднання. Див. [огляд правил nftables](local-network-and-socket-triage.md#nftables-review-and-authorized-rule-changes) — приклад із конкретним розбором.

## Перевірка вихідного трафіку та роботи проксі

```bash
ip route get 1.1.1.1
getent hosts example.com
curl -I --connect-timeout 3 https://example.com/
printenv http_proxy https_proxy all_proxy no_proxy 2>/dev/null
```

Відрізняйте збій DNS від збоїв TCP, TLS або proxy. Перевіряйте саме адресу призначення та протокол, що стосуються оцінювання; доступність через ICMP не означає, що TCP або UDP дозволено. Якщо налаштовано proxy, порівняйте запит через proxy з тим самим запитом до тієї самої цілі з урахуванням відповідних правил `no_proxy`. Локальне перенаправлення порту також може зробити loopback-сервіс доступним з іншого місця, тож перевірте активні слухачі та SSH-тунелі, якщо дані firewall не відповідають фактичній доступності.
