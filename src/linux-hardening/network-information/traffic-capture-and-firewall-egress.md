# Аналіз захоплення трафіку, firewall та вихідного трафіку

{{#include ../../banners/hacktricks-training.md}}

Після пошуку [локальних слухачів і Unix-сокетів](local-network-and-socket-triage.md) перевірте, які інтерфейси передають їхній трафік і які правила firewall або проксі впливають на доступність. Служба, доступна лише через loopback, може передавати конфіденційні HTTP-заголовки, навіть якщо до неї неможливо підключитися з іншого хоста.

## Перевірте дозволи на захоплення трафіку та виберіть інтерфейс

```bash
ip -br addr
ip route
getcap "$(command -v dumpcap)" 2>/dev/null
tcpdump -D 2>/dev/null
```

`dumpcap` може мати можливість захоплювати пакети, навіть якщо поточний користувач не має sudo-доступу. Перевірте фактичні capabilities виконуваного файла та дозволи групи. Захоплюйте трафік лише на найменшому корисному інтерфейсі, протягом найкоротшого часу та з найточнішим фільтром; захоплення може містити облікові дані або персональні дані.

```bash
sudo tcpdump -i lo -s 0 -w /tmp/loopback.pcap 'tcp port 8080'
tshark -r /tmp/loopback.pcap -Y 'http.request' -T fields -e ip.src -e http.host -e http.request.uri
tcpflow -r /tmp/loopback.pcap 2>/dev/null
```

`tcpflow` відновлює відкриті TCP-потоки; `tshark` може фільтрувати дані захоплення та витягувати з них поля. Для розшифрування TLS-трафіку потрібні ключі кінцевих вузлів або підтримуваний клієнт, налаштований на `SSLKEYLOGFILE` до встановлення з’єднання. На [сторінці з первинного аналізу локальної мережі](local-network-and-socket-triage.md#tls-key-logging) показано цей процес. Не вважайте зашифровані дані захоплення читабельним відкритим текстом.

Збережені артефакти інциденту можуть змінити цю оцінку. [Дамп пам’яті Linux — це образ пам’яті процесу](https://man7.org/linux/man-pages/man5/core.5.html), у якому може зберегтися ключ сеансу; якщо читабельний дамп і дані захоплення пакетів отримано від того самого процесу й сеансу, аналітик може мати змогу розшифрувати цей трафік. Спершу складіть перелік шляхів до артефактів і перевірте дозволи, а потім окремо перевірте ідентичність процесу, час захоплення, протокол і формат ключа. Розшифрований трафік або відновлений архів — це підказка щодо можливого розголошення, а не доказ доступу до чужого облікового запису: будь-які часткові дані SSH-ключа потрібно відновити, зіставити з відповідним відкритим ключем, а сам ключ має бути прийнятий політикою SSH цього облікового запису. Не виводьте вміст дампів пам’яті чи корисне навантаження захоплених пакетів у загальнодоступні результати розвідки.

## Визначення рівнів брандмауера

```bash
sudo nft list ruleset 2>/dev/null
sudo iptables-save 2>/dev/null
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null
```

`nftables` і `iptables` можуть бути доступні через оболонки дистрибутива, як-от UFW або firewalld. Перегляньте активні правила та збережену конфігурацію оболонки: правило, видиме в одному представленні, могло бути створене іншим інструментом. Перш ніж пов’язувати блокування служби з певним правилом, перевірте інтерфейс, напрямок, джерело, призначення, протокол, порт і стан з’єднання. Див. [перевірку правил nftables](local-network-and-socket-triage.md#nftables-review-and-authorized-rule-changes), де наведено конкретний приклад.

## Перевірка вихідного трафіку та поведінки проксі

```bash
ip route get 1.1.1.1
getent hosts example.com
curl -I --connect-timeout 3 https://example.com/
printenv http_proxy https_proxy all_proxy no_proxy 2>/dev/null
```

Відрізняйте збій DNS від збою TCP, TLS або proxy. Перевіряйте конкретне призначення та протокол, що стосуються оцінювання; доступність через ICMP не означає, що дозволено TCP або UDP. Якщо налаштовано proxy, порівняйте запит через proxy, який ви плануєте виконати, із запитом до тієї самої цілі з урахуванням відповідних правил `no_proxy`. Локальне перенаправлення порту також може зробити сервіс loopback доступним в іншому місці, тому перевірте активні порти, що прослуховуються, та SSH-тунелі, якщо дані брандмауера не збігаються зі спостережуваною доступністю.
