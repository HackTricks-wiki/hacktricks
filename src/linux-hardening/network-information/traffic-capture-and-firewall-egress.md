# Захоплення трафіку, брандмауер і аналіз вихідного трафіку

{{#include ../../banners/hacktricks-training.md}}

Після виявлення [локальних слухачів і сокетів Unix](local-network-and-socket-triage.md) перевірте, через які інтерфейси проходить їхній трафік і які правила брандмауера або проксі впливають на доступність. Служба, доступна лише через loopback, може передавати конфіденційні HTTP-заголовки, навіть якщо до неї неможливо підключитися з іншого хоста.

## Перевірте дозволи на захоплення трафіку й виберіть інтерфейс

```bash
ip -br addr
ip route
getcap "$(command -v dumpcap)" 2>/dev/null
tcpdump -D 2>/dev/null
```

`dumpcap` може мати можливість захоплювати пакети, навіть якщо поточний користувач не має доступу до sudo. Перевірте фактичні можливості виконуваного файла та дозволи групи. Захоплюйте трафік на найменшому корисному інтерфейсі, протягом найкоротшого часу та з найвужчим фільтром; захоплений трафік може містити облікові дані або персональні дані.

```bash
sudo tcpdump -i lo -s 0 -w /tmp/loopback.pcap 'tcp port 8080'
tshark -r /tmp/loopback.pcap -Y 'http.request' -T fields -e ip.src -e http.host -e http.request.uri
tcpflow -r /tmp/loopback.pcap 2>/dev/null
```

`tcpflow` відновлює відкриті TCP-потоки; `tshark` може фільтрувати захоплений трафік і витягувати з нього поля. Для розшифрування TLS-трафіку потрібні ключі кінцевої точки або сумісний клієнт, налаштований на використання `SSLKEYLOGFILE` до встановлення з’єднання. На [сторінці з первинного аналізу локальної мережі](local-network-and-socket-triage.md#tls-key-logging) показано цей процес. Не вважайте зашифроване захоплення читабельним відкритим текстом.

Збережені артефакти інциденту можуть змінити цю оцінку. [Дамп пам’яті Linux — це образ пам’яті процесу](https://man7.org/linux/man-pages/man5/core.5.html), у якому може зберегтися ключ сеансу; якщо читабельний дамп і захоплення пакетів отримано з того самого процесу та сеансу, аналітик може мати змогу розшифрувати цей трафік. Спочатку проінвентаризуйте шляхи до артефактів і дозволи доступу, а потім окремо перевірте ідентичність процесу, час захоплення, протокол і формат ключа. Розшифрований трафік або відновлений архів — це зачіпка щодо розголошення, а не доказ доступу до облікового запису іншого користувача: будь-які часткові дані SSH-ключа потрібно відновити, зіставити з відповідним відкритим ключем і перевірити на відповідність політикам SSH цього облікового запису. Не виводьте вміст дампів пам’яті чи дані пакетів у загальні результати переліку.

## Визначення рівнів firewall

```bash
sudo nft list ruleset 2>/dev/null
sudo iptables-save 2>/dev/null
sudo ufw status verbose 2>/dev/null
sudo firewall-cmd --list-all 2>/dev/null
```

`nftables` і `iptables` можуть бути доступні через оболонки дистрибутива, як-от UFW або firewalld. Перегляньте активні правила й збережену конфігурацію оболонки: правило, видиме в одному представленні, могло бути створене іншим інструментом. Перш ніж пов’язувати блокування служби з певним правилом, перевірте інтерфейс, напрямок, джерело, призначення, протокол, порт і стан з’єднання. Див. [огляд правил nftables](local-network-and-socket-triage.md#nftables-review-and-authorized-rule-changes), де наведено конкретний приклад.

## Перевірка вихідного трафіку та поведінки проксі-сервера

```bash
ip route get 1.1.1.1
getent hosts example.com
curl -I --connect-timeout 3 https://example.com/
printenv http_proxy https_proxy all_proxy no_proxy 2>/dev/null
```

Розрізняйте помилки DNS від помилок TCP, TLS або проксі. Перевіряйте конкретне призначення та протокол, що стосуються оцінювання; доступність через ICMP не означає, що TCP або UDP дозволені. Якщо налаштовано проксі, порівняйте запит через проксі з таким самим запитом до тієї самої цілі з урахуванням відповідних правил `no_proxy`. Локальне перенаправлення порту також може зробити сервіс на loopback доступним з інших місць, тому перевірте активні прослуховувачі та SSH-тунелі, якщо дані брандмауера не збігаються з фактичною доступністю.
