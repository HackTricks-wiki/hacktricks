# Користувачі, сеанси та артефакти облікових даних

{{#include ../../banners/hacktricks-training.md}}

Почніть з ідентифікатора користувача, якому належить поточна оболонка, а потім перелікуйте інших користувачів, групи, активні сеанси та сховища облікових даних. На сторінці про [реальний, ефективний і збережений ідентифікатор користувача](euid-ruid-suid.md) пояснюється, чому ефективні привілеї процесу можуть відрізнятися від привілеїв його облікового запису для входу.

## Перелік ідентифікаторів і доступу на основі груп членства

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

`getent` включає облікові записи з каталогів, які можуть бути відсутні у звичайному вмісті `/etc/passwd`. Перевірте облікові записи з UID 0, оболонки входу, домашні каталоги, додаткові групи та облікові записи, конфігурація яких несподівано дозволяє інтерактивний вхід. На сторінці [цікаві групи](interesting-groups-linux-pe/README.md) описано делегований доступ, зокрема через `sudo`, `docker`, `disk` і `shadow`. Перш ніж вважати назву групи ознакою привілеїв, перевірте фактичні ACL файлової системи та локальну політику.

Якщо [NSS спрямовує пошук `passwd`, `group` або `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) до бази даних, перед оцінюванням облікових записів із цієї бази перевірте активне джерело та шлях до його конфігурації. Для розгортань PostgreSQL NSS файли `/etc/nss-pgsql.conf` і `/etc/nss-pgsql-root.conf` є лише підказками щодо шляхів, оскільки параметри підключення можуть містити облікові дані. Роль у базі даних має значення лише тоді, коли вона може змінювати записи, які фактично повертає активне джерело NSS, і обліковий запис може пройти автентифікацію з їх використанням. Основний GID 0 означає членство в групі root, а не UID 0; зіставлення з групою sudo вимагає чинного [правила групи sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) і, за потреби, автентифікації. Зіставлення з UID 0 — це інша межа ідентичності. Під час пасивного переліку не виводьте рядки підключення й не змінюйте записи облікових записів.

Також порівняйте числові UID локальних облікових записів. Два імені в [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) можуть відповідати одній і тій самій ідентичності Unix-файлів, тоді як їхні записи автентифікації для входу можуть відрізнятися. Тому щойно доданий псевдонім зі спільним ненульовим UID після успішної автентифікації може надати доступ до файлів або процесів іншого користувача; він не надає root, якщо цей UID або окремий шлях підвищення привілеїв цього не забезпечує. Спільне використання UID може бути навмисним. Перевірте джерело облікового запису (`/etc/passwd` чи NSS), історію створення, оболонку й домашній каталог, фактичну політику автентифікації та наявність дозволу на спільне використання ідентичності цими обліковими записами. Перевірка дублікатів лише в локальних облікових записах не виключає псевдонім із каталогу.

## Знайти активні та нещодавні сеанси

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

`screen` або `tmux` socket може надати доступ до наявної оболонки, якщо його дозволи дають поточному користувачеві змогу під’єднатися. Перш ніж намагатися отримати доступ, перевірте власника та режим socket; сесія іншого користувача не стає доступною автоматично. Також можуть мати значення активна мітка часу sudo або socket SSH agent, але їх повторне використання залежить від ідентичності користувача, дозволів і політики. Щоб дізнатися про зловживання пересиланням agent, див. [SSH forwarding agent exploitation](ssh-forward-agent-exploitation.md).

[OpenSSH multiplex control socket](https://man.openbsd.org/ssh_config#ControlMaster) відокремлений від `SSH_AUTH_SOCK`: `ControlMaster` і `ControlPath` дають змогу подальшим SSH-клієнтам спільно використовувати наявне автентифіковане з’єднання, а `ControlPersist` може залишити master доступним після завершення першої сесії. Перевірте `.ssh/config` поточного користувача та socket-шляхи без заглиблення в підкаталоги `.ssh`, зокрема власника й дозволи. Сама назва socket-файлу не доводить, що master активний, що поточний користувач може під’єднатися або який віддалений обліковий запис він використовує.

## Перевірка артефактів користувача

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Історія командної оболонки, файли запуску, ключі SSH, конфігурації застосунків, сховища ключів GPG і кеші Kerberos можуть розкрити облікові дані або точки для закріплення, доступні для запису. Варто перевірити файл `authorized_keys` або файл запуску командної оболонки, доступний для запису обліковому запису з вищими привілеями. На [сторінці post-exploitation](../post-exploitation/README.md) описано переміщення каталогу GPG та пошук облікових даних; у матеріалі [Linux Active Directory](linux-active-directory.md) розглянуто повторне використання кешу Kerberos і keytab. На [сторінці PAM](../software-information/pam-pluggable-authentication-modules.md) пояснено ризики політик автентифікації.
