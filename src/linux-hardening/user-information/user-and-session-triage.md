# Користувачі, сеанси та артефакти облікових даних

{{#include ../../banners/hacktricks-training.md}}

Почніть з ідентифікатора користувача, якому належить поточна оболонка, а потім перелічіть інших користувачів, групи, активні сеанси та сховища облікових даних. На сторінці про [реальний, ефективний і збережений ідентифікатори користувача](euid-ruid-suid.md) пояснюється, чому ефективні привілеї процесу можуть відрізнятися від привілеїв його облікового запису для входу.

## Перелік ідентифікаторів користувачів і доступу на основі груп

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

`getent` включає облікові записи з каталогів, які можуть бути відсутні під час звичайного читання `/etc/passwd`. Перевірте облікові записи з UID 0, оболонки входу, домашні каталоги, додаткові групи й облікові записи, конфігурація яких неочікувано дозволяє інтерактивний вхід. На сторінці [цікавих груп](interesting-groups-linux-pe/README.md) описано делегований доступ, зокрема через `sudo`, `docker`, `disk` і `shadow`. Перш ніж вважати членство в групі привілеєм, перевірте фактичні ACL файлової системи та локальну політику.

Якщо [NSS спрямовує запити `passwd`, `group` або `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) до бази даних, перш ніж оцінювати ідентифікаційні дані з бази даних, перевірте активний провайдер і шлях до його конфігурації. Для розгортань PostgreSQL NSS файли `/etc/nss-pgsql.conf` і `/etc/nss-pgsql-root.conf` є лише підказками щодо шляхів, оскільки параметри підключення можуть містити облікові дані. Роль у базі даних має значення лише тоді, коли вона може змінювати записи, які фактично повертає активний провайдер NSS, і обліковий запис може автентифікуватися за їх допомогою. Основний GID 0 означає членство в групі root, а не UID 0; відповідність групі sudo вимагає чинного [правила групи sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) і, за потреби, автентифікації. Відповідність UID 0 означає іншу межу ідентичності. Не виводьте рядки підключення й не змінюйте записи облікових записів під час пасивного переліку.

Також порівняйте числові UID між локальними іменами облікових записів. Два імені в [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) можуть відповідати тій самій ідентичності Unix у файловій системі, хоча записи автентифікації для входу в них можуть відрізнятися. Тому щойно доданий псевдонім зі спільним ненульовим UID після успішної автентифікації може надати доступ до файлів або процесів іншого користувача; він не надає root, якщо цей UID або окремий шлях підвищення привілеїв не дає таких прав. Спільне використання UID може бути навмисним. Перевірте джерело облікового запису (`/etc/passwd` чи NSS), історію створення, оболонку й домашній каталог, фактичну політику автентифікації, а також те, чи мають ці облікові записи право спільно використовувати цю ідентичність. Перевірка лише локальних облікових записів на дублікати не виключає наявності псевдоніма з каталогу.

## Знайти активні й нещодавні сеанси

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

Сокет `screen` або `tmux` може надати доступ до наявної оболонки, якщо його дозволи дають поточному користувачеві змогу під’єднатися. Перш ніж намагатися отримати доступ, перевірте власника та режим сокета: сеанс іншого користувача не стає автоматично доступним для під’єднання. Також можуть мати значення активна мітка часу sudo або сокет SSH-агента, але можливість їх повторного використання залежить від ідентичності користувача, дозволів і політики. Про зловживання пересиланням агента див. [SSH forwarding agent exploitation](ssh-forward-agent-exploitation.md).

Керівний сокет мультиплексування [OpenSSH](https://man.openbsd.org/ssh_config#ControlMaster) відрізняється від `SSH_AUTH_SOCK`: `ControlMaster` і `ControlPath` дають змогу наступним SSH-клієнтам використовувати наявне автентифіковане з’єднання, а `ControlPersist` може залишати головний процес доступним після завершення першого сеансу. Перевірте `.ssh/config` поточного користувача та неглибокі шляхи сокетів у `.ssh`, зокрема власника й дозволи. Саме ім’я файла сокета не доводить, що головний процес працює, що поточний користувач може під’єднатися або який віддалений обліковий запис він використовує.

## Огляд артефактів користувача

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Історія shell, файли запуску, SSH-ключі, конфігурація застосунків, сховища ключів GPG і кеші Kerberos можуть розкрити облікові дані або місця для закріплення, доступні для запису. Варто перевірити `authorized_keys` або файл запуску shell облікового запису з вищими привілеями, якщо вони доступні для запису. На [сторінці post-exploitation](../post-exploitation/README.md) описано перенесення домашнього каталогу GPG і пошук облікових даних; у матеріалі [Linux Active Directory](linux-active-directory.md) розглянуто повторне використання кешу Kerberos і keytab. На [сторінці PAM](../software-information/pam-pluggable-authentication-modules.md) пояснено ризики політик автентифікації.
