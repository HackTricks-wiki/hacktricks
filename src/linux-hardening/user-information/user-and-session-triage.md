# Користувачі, сеанси та артефакти облікових даних

{{#include ../../banners/hacktricks-training.md}}

Почніть з визначення користувача, якому належить поточна оболонка, а потім перелічіть інших користувачів, групи, активні сеанси та сховища облікових даних. На сторінці про [реальний, ефективний і збережений ідентифікатори користувача](euid-ruid-suid.md) пояснюється, чому ефективні привілеї процесу можуть відрізнятися від привілеїв його облікового запису для входу.

## Перелік ідентифікаторів і доступу на основі групેણ

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

`getent` включає облікові записи з каталогів, які можуть бути відсутні під час звичайного читання `/etc/passwd`. Перевірте облікові записи з UID 0, оболонки входу, домашні каталоги, додаткові групи та облікові записи, конфігурація яких неочікувано дозволяє інтерактивний вхід. На сторінці [цікаві групи](interesting-groups-linux-pe/README.md) описано делегований доступ, зокрема через `sudo`, `docker`, `disk` і `shadow`. Перш ніж вважати назву групи ознакою привілеїв, перевірте фактичні ACL файлової системи та локальну політику.

Якщо [NSS спрямовує запити до `passwd`, `group` або `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) до бази даних, перш ніж оцінювати ідентичності з бази даних, перевірте активний провайдер і шлях до його конфігурації. Для розгортань PostgreSQL NSS файли `/etc/nss-pgsql.conf` і `/etc/nss-pgsql-root.conf` є лише підказками щодо шляхів, оскільки параметри підключення можуть містити облікові дані. Роль у базі даних має значення лише тоді, коли вона може змінювати записи, які фактично повертає активний провайдер NSS, і обліковий запис може автентифікуватися з їх використанням. Основний GID 0 надає членство в групі root, але не UID 0; відповідність групі sudo вимагає чинного [правила групи в sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) і будь-якої потрібної автентифікації. Відповідність UID 0 означає іншу межу ідентичності. Під час пасивного переліку не виводьте рядки підключення й не змінюйте записи облікових записів.

Також порівняйте числові UID для локальних імен облікових записів. Два імені в [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) можуть відповідати тій самій Unix-ідентичності файлів, хоча записи автентифікації для входу можуть відрізнятися. Тому щойно доданий псевдонім зі спільним ненульовим UID після успішної автентифікації може надати доступ до файлів або процесів іншого користувача; він не надає root, якщо це не забезпечує сам UID або окремий шлях підвищення привілеїв. Спільні UID можуть бути навмисними. Перевірте джерело облікового запису (`/etc/passwd` чи NSS), історію створення, оболонку й домашній каталог, фактичну політику автентифікації та наявність дозволу на спільне використання ідентичності. Перевірка лише локальних дублікатів не виключає псевдоніма з каталогу.

## Знайти активні й нещодавні сеанси

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

Сокет `screen` або `tmux` може надати доступ до наявної оболонки, якщо його дозволи дають поточному користувачеві змогу під’єднатися. Перш ніж намагатися отримати доступ, перевірте власника та режим сокета: сеанс іншого користувача не можна автоматично приєднати. Також можуть мати значення активна мітка часу sudo або сокет SSH agent, але можливість їх повторного використання залежить від ідентичності користувача, дозволів і політики. Щоб дізнатися про зловживання переадресацією agent, див. [SSH forwarding agent exploitation](ssh-forward-agent-exploitation.md).

[Керівний сокет мультиплексування OpenSSH](https://man.openbsd.org/ssh_config#ControlMaster) відрізняється від `SSH_AUTH_SOCK`: `ControlMaster` і `ControlPath` дають змогу наступним SSH-клієнтам використовувати наявне автентифіковане з’єднання, а `ControlPersist` може залишити master доступним після завершення першого сеансу. Перегляньте `.ssh/config` поточного користувача та неглибокі шляхи до сокетів у `.ssh`, зокрема власника й дозволи. Саме ім’я файла сокета не доводить, що master активний, що поточний користувач може під’єднатися або який віддалений обліковий запис він використовує.

## Перегляд артефактів користувача

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Історія командної оболонки, файли запуску, ключі SSH, конфігурації застосунків, сховища ключів GPG і кеші Kerberos можуть розкрити облікові дані або точки для збереження доступу, доступні для запису. Варто перевірити `authorized_keys` або файл запуску оболонки, доступні для запису для облікового запису з вищими привілеями. На [сторінці про post-exploitation](../post-exploitation/README.md) описано перенесення домашнього каталогу GPG і пошук облікових даних; у розділі [Linux Active Directory](linux-active-directory.md) описано повторне використання кешу Kerberos і keytab. На [сторінці про PAM](../software-information/pam-pluggable-authentication-modules.md) пояснено ризики політик автентифікації.
