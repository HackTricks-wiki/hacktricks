# Χρήστες, συνεδρίες και τεχνουργήματα διαπιστευτηρίων

{{#include ../../banners/hacktricks-training.md}}

Ξεκινήστε από την ταυτότητα στην οποία ανήκει το τρέχον shell και, στη συνέχεια, απαριθμήστε τους άλλους χρήστες, τις ομάδες, τις ενεργές συνεδρίες και τα αποθετήρια διαπιστευτηρίων. Η σελίδα [πραγματικό, αποτελεσματικό και αποθηκευμένο αναγνωριστικό χρήστη](euid-ruid-suid.md) εξηγεί γιατί τα αποτελεσματικά δικαιώματα μιας διεργασίας ενδέχεται να διαφέρουν από τον λογαριασμό σύνδεσής της.

## Απαρίθμηση ταυτοτήτων και πρόσβασης βάσει ομάδων

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

`getent` περιλαμβάνει λογαριασμούς που προέρχονται από καταλόγους και μπορεί να μην εμφανίζονται σε μια απλή ανάγνωση του `/etc/passwd`. Ελέγξτε τους λογαριασμούς με UID 0, τα κελύφη σύνδεσης, τους αρχικούς καταλόγους, τις συμπληρωματικές ομάδες και τους λογαριασμούς των οποίων οι ρυθμίσεις επιτρέπουν απροσδόκητα διαδραστική σύνδεση. Η σελίδα [interesting groups](interesting-groups-linux-pe/README.md) καλύπτει την εκχωρημένη πρόσβαση, όπως `sudo`, `docker`, `disk` και `shadow`. Ελέγξτε τα πραγματικά ACL του συστήματος αρχείων και την τοπική πολιτική, προτού θεωρήσετε ένα όνομα ομάδας ένδειξη προνομίων.

Αν το [NSS αντιστοιχίζει αναζητήσεις `passwd`, `group` ή `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) σε βάση δεδομένων, ελέγξτε τον ενεργό πάροχο και τη διαδρομή των ρυθμίσεών του προτού αξιολογήσετε ταυτότητες που προέρχονται από βάση δεδομένων. Σε εγκαταστάσεις PostgreSQL NSS, τα `/etc/nss-pgsql.conf` και `/etc/nss-pgsql-root.conf` αποτελούν μόνο ενδείξεις διαδρομής, καθώς οι ρυθμίσεις σύνδεσης ενδέχεται να περιέχουν διαπιστευτήρια. Ένας ρόλος βάσης δεδομένων έχει σημασία μόνο αν μπορεί να αλλάξει εγγραφές που επιστρέφει πράγματι ο ενεργός πάροχος NSS και αν ένας λογαριασμός μπορεί να πιστοποιηθεί χρησιμοποιώντας αυτές. Ένα κύριο GID 0 παρέχει συμμετοχή στην ομάδα root, όχι UID 0· η αντιστοίχιση στην ομάδα sudo απαιτεί έναν ενεργό [κανόνα ομάδας sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) και τυχόν απαιτούμενη πιστοποίηση. Η αντιστοίχιση UID 0 αφορά διαφορετικό όριο ταυτότητας. Μην εμφανίζετε συμβολοσειρές σύνδεσης ούτε να αλλάζετε εγγραφές λογαριασμών κατά την παθητική απαρίθμηση.

Επίσης, συγκρίνετε τα αριθμητικά UID μεταξύ των τοπικών ονομάτων λογαριασμών. Δύο ονόματα στο [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) μπορεί να αναφέρονται στην ίδια ταυτότητα αρχείου Unix, ενώ οι εγγραφές πιστοποίησης σύνδεσής τους ενδέχεται να διαφέρουν. Επομένως, ένα alias που προστέθηκε πρόσφατα και έχει κοινό μη μηδενικό UID μπορεί, μετά από επιτυχή πιστοποίηση, να οδηγήσει στα αρχεία ή τις διεργασίες άλλου χρήστη· δεν παρέχει root, εκτός αν το συγκεκριμένο UID ή κάποια ξεχωριστή διαδρομή προνομίων το επιτρέπει. Τα κοινόχρηστα UID μπορεί να είναι σκόπιμα. Επαληθεύστε την πηγή του λογαριασμού (`/etc/passwd` έναντι NSS), το ιστορικό δημιουργίας, το κέλυφος και τον αρχικό κατάλογο, την πραγματική πολιτική πιστοποίησης και το αν οι λογαριασμοί επιτρέπεται να χρησιμοποιούν την ίδια ταυτότητα. Ένας έλεγχος μόνο των τοπικών λογαριασμών δεν μπορεί να αποκλείσει ένα alias που προέρχεται από κατάλογο.

## Εύρεση ενεργών και πρόσφατων συνόδων

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

Ένα socket `screen` ή `tmux` μπορεί να εκθέσει ένα υπάρχον shell, αν τα δικαιώματά του επιτρέπουν στον τρέχοντα χρήστη να συνδεθεί. Ελέγξτε τον κάτοχο και τα δικαιώματα του socket πριν επιχειρήσετε πρόσβαση· η συνεδρία άλλου χρήστη δεν είναι αυτομάτως προσβάσιμη. Μπορεί επίσης να έχουν σημασία ένα ενεργό sudo timestamp ή ένα socket SSH agent, αλλά η επαναχρησιμοποίησή τους εξαρτάται από την ταυτότητα χρήστη, τα δικαιώματα και την πολιτική. Για κατάχρηση agent forwarding, δείτε [SSH forwarding agent exploitation](ssh-forward-agent-exploitation.md).

Ένα [OpenSSH multiplex control socket](https://man.openbsd.org/ssh_config#ControlMaster) είναι ξεχωριστό από το `SSH_AUTH_SOCK`: τα `ControlMaster` και `ControlPath` επιτρέπουν σε μεταγενέστερους SSH clients να μοιράζονται μια υπάρχουσα, πιστοποιημένη σύνδεση, ενώ το `ControlPersist` μπορεί να διατηρήσει διαθέσιμο το master μετά το τέλος της πρώτης συνεδρίας. Ελέγξτε το `.ssh/config` του τρέχοντος χρήστη και τις διαδρομές socket σε μικρό βάθος μέσα στο `.ssh`, μαζί με τον κάτοχο και τα δικαιώματα. Το όνομα ενός socket από μόνο του δεν αποδεικνύει ότι το master είναι ενεργό, ότι ο τρέχων χρήστης μπορεί να συνδεθεί ή ποιον απομακρυσμένο λογαριασμό χρησιμοποιεί.

## Έλεγχος τεχνουργημάτων χρήστη

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Το ιστορικό του shell, τα αρχεία εκκίνησης, τα SSH keys, οι ρυθμίσεις εφαρμογών, τα keyrings του GPG και οι caches του Kerberos μπορούν να αποκαλύψουν διαπιστευτήρια ή σημεία persistence με δυνατότητα εγγραφής. Ένα `authorized_keys` ή αρχείο εκκίνησης του shell με δυνατότητα εγγραφής για λογαριασμό με περισσότερα προνόμια αξίζει να ελεγχθεί. Η [σελίδα post-exploitation](../post-exploitation/README.md) καλύπτει τη μεταφορά του GPG homedir και την αναζήτηση διαπιστευτηρίων· η [Linux Active Directory](linux-active-directory.md) καλύπτει την επαναχρησιμοποίηση cache και keytab του Kerberos. Η [σελίδα PAM](../software-information/pam-pluggable-authentication-modules.md) εξηγεί τους κινδύνους των πολιτικών ελέγχου ταυτότητας.
