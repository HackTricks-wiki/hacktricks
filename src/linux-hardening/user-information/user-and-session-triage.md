# Χρήστες, συνεδρίες και τεχνουργήματα διαπιστευτηρίων

{{#include ../../banners/hacktricks-training.md}}

Ξεκινήστε με την ταυτότητα που ανήκει στο τρέχον shell και, στη συνέχεια, απαριθμήστε τους άλλους χρήστες, τις ομάδες, τις ενεργές συνεδρίες και τα αποθετήρια διαπιστευτηρίων. Η σελίδα για το [πραγματικό, ενεργό και αποθηκευμένο αναγνωριστικό χρήστη](euid-ruid-suid.md) εξηγεί γιατί τα ενεργά προνόμια μιας διεργασίας μπορεί να διαφέρουν από τον λογαριασμό με τον οποίο συνδέθηκε ο χρήστης.

## Απαρίθμηση ταυτοτήτων και πρόσβασης βάσει ομάδων

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

Το `getent` περιλαμβάνει λογαριασμούς από καταλόγους, τους οποίους μπορεί να μην εμφανίζει μια απλή ανάγνωση του `/etc/passwd`. Ελέγξτε τους λογαριασμούς με UID 0, τα login shells, τους home directories, τις συμπληρωματικές ομάδες και τους λογαριασμούς των οποίων οι ρυθμίσεις επιτρέπουν απροσδόκητα διαδραστικό login. Η σελίδα [interesting groups](interesting-groups-linux-pe/README.md) καλύπτει εκχωρημένη πρόσβαση, όπως `sudo`, `docker`, `disk` και `shadow`. Ελέγξτε τα πραγματικά filesystem ACLs και την τοπική πολιτική προτού θεωρήσετε ότι ένα όνομα ομάδας συνεπάγεται προνόμια.

Αν το [NSS αντιστοιχίζει τις αναζητήσεις `passwd`, `group` ή `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) σε βάση δεδομένων, ελέγξτε τον ενεργό provider και τη διαδρομή των ρυθμίσεών του προτού αξιολογήσετε ταυτότητες που υποστηρίζονται από βάση δεδομένων. Σε εγκαταστάσεις PostgreSQL NSS, τα `/etc/nss-pgsql.conf` και `/etc/nss-pgsql-root.conf` είναι απλώς ενδείξεις διαδρομών, επειδή οι ρυθμίσεις σύνδεσης ενδέχεται να περιέχουν διαπιστευτήρια. Ένας ρόλος βάσης δεδομένων έχει σημασία μόνο αν μπορεί να αλλάξει εγγραφές που επιστρέφει πράγματι ο ενεργός NSS provider και αν ένας λογαριασμός μπορεί να πραγματοποιήσει authentication χρησιμοποιώντας αυτές. Ένα primary GID ίσο με 0 παρέχει συμμετοχή στην ομάδα root, όχι UID 0· η αντιστοίχιση σε ομάδα sudo απαιτεί έναν ενεργό [κανόνα ομάδας sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) και οποιοδήποτε απαιτούμενο authentication. Η αντιστοίχιση σε UID 0 αποτελεί διαφορετικό όριο ταυτότητας. Μην εμφανίζετε connection strings και μην αλλάζετε εγγραφές λογαριασμών κατά την παθητική απαρίθμηση.

Επίσης, συγκρίνετε τα αριθμητικά UID μεταξύ των τοπικών ονομάτων λογαριασμών. Δύο ονόματα στο [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) μπορεί να αντιστοιχούν στην ίδια ταυτότητα αρχείων Unix, ενώ οι εγγραφές authentication για το login τους μπορεί να διαφέρουν. Επομένως, ένα νεοδημιουργημένο alias με κοινό, μη μηδενικό UID μπορεί, μετά από επιτυχημένο authentication, να δώσει πρόσβαση στα αρχεία ή τις διεργασίες άλλου χρήστη· δεν παρέχει root, εκτός αν το συγκεκριμένο UID ή μια ξεχωριστή διαδρομή προνομίων το επιτρέπει. Τα κοινόχρηστα UID μπορεί να είναι σκόπιμα. Επαληθεύστε την πηγή του λογαριασμού (`/etc/passwd` έναντι NSS), το ιστορικό δημιουργίας, το shell και το home, την πραγματική πολιτική authentication και το αν οι λογαριασμοί έχουν εξουσιοδοτηθεί να μοιράζονται την ίδια ταυτότητα. Ένας έλεγχος μόνο για τοπικούς διπλότυπους λογαριασμούς δεν μπορεί να αποκλείσει ένα alias από κατάλογο.

## Εντοπισμός ενεργών και πρόσφατων sessions

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

Ένα socket `screen` ή `tmux` μπορεί να εκθέσει ένα υπάρχον shell, αν τα δικαιώματά του επιτρέπουν στον τρέχοντα χρήστη να συνδεθεί. Ελέγξτε τον κάτοχο και τα δικαιώματα του socket πριν επιχειρήσετε πρόσβαση· η συνεδρία άλλου χρήστη δεν είναι αυτόματα προσβάσιμη. Μπορεί επίσης να έχει σημασία ένα ενεργό sudo timestamp ή ένα socket SSH agent, αλλά η επαναχρησιμοποίησή τους εξαρτάται από την ταυτότητα του χρήστη, τα δικαιώματα και την πολιτική. Για κατάχρηση προώθησης agent, δείτε [SSH forwarding agent exploitation](ssh-forward-agent-exploitation.md).

Ένα [socket ελέγχου πολυπλεξίας OpenSSH](https://man.openbsd.org/ssh_config#ControlMaster) είναι ξεχωριστό από το `SSH_AUTH_SOCK`: τα `ControlMaster` και `ControlPath` επιτρέπουν σε μεταγενέστερους SSH clients να χρησιμοποιούν μια υπάρχουσα, πιστοποιημένη σύνδεση, ενώ το `ControlPersist` μπορεί να διατηρήσει διαθέσιμο το master μετά τη λήξη της πρώτης συνεδρίας. Ελέγξτε το `.ssh/config` του τρέχοντος χρήστη και τις διαδρομές socket μέσα στο `.ssh` σε μικρό βάθος, συμπεριλαμβανομένου του κατόχου και των δικαιωμάτων. Το όνομα ενός socket από μόνο του δεν αποδεικνύει ότι το master λειτουργεί, ότι ο τρέχων χρήστης μπορεί να συνδεθεί ή ποιον απομακρυσμένο λογαριασμό χρησιμοποιεί.

## Επισκόπηση τεχνουργημάτων χρήστη

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Το ιστορικό του shell, τα αρχεία εκκίνησης, τα SSH keys, οι ρυθμίσεις εφαρμογών, τα keyrings του GPG και οι caches του Kerberos μπορεί να αποκαλύψουν διαπιστευτήρια ή σημεία persistence με δυνατότητα εγγραφής. Ένα `authorized_keys` ή αρχείο εκκίνησης shell με δυνατότητα εγγραφής για λογαριασμό με περισσότερα προνόμια αξίζει να ελεγχθεί. Η [σελίδα post-exploitation](../post-exploitation/README.md) καλύπτει τη μεταφορά του GPG homedir και την αναζήτηση διαπιστευτηρίων· η [σελίδα Linux Active Directory](linux-active-directory.md) καλύπτει την επαναχρησιμοποίηση cache Kerberos και keytab. Η [σελίδα PAM](../software-information/pam-pluggable-authentication-modules.md) εξηγεί τους κινδύνους των πολιτικών ελέγχου ταυτότητας.
