# Користувачі, сеанси та артефакти облікових даних

{{#include ../../banners/hacktricks-training.md}}

Почніть з ідентичності, якій належить поточна оболонка, а потім перелічіть інших користувачів, групи, активні сеанси та сховища облікових даних. На сторінці [реальний, ефективний і збережений ідентифікатор користувача](euid-ruid-suid.md) пояснюється, чому ефективні привілеї процесу можуть відрізнятися від привілеїв його облікового запису.

## Перелік ідентичностей і доступу на основі груп

```bash
id
getent passwd
getent group
whoami
stat -c '%A %U:%G %n' /etc/passwd /etc/shadow /etc/group
```

`getent` включає облікові записи з каталогів, які звичайне читання `/etc/passwd` може не виявити. Перевірте облікові записи з UID 0, оболонки входу, домашні каталоги, додаткові групи та облікові записи, конфігурація яких несподівано дозволяє інтерактивний вхід. На сторінці [цікавих груп](interesting-groups-linux-pe/README.md) описано делегований доступ, зокрема через `sudo`, `docker`, `disk` і `shadow`. Перш ніж вважати назву групи ознакою привілеїв, перевірте фактичні ACL файлової системи та локальну політику.

Якщо [NSS спрямовує пошук у `passwd`, `group` або `shadow`](https://man7.org/linux/man-pages/man5/nsswitch.conf.5.html) до бази даних, перед оцінюванням ідентичностей із бази перевірте активного провайдера та шлях до його конфігурації. Для розгортань PostgreSQL NSS файли `/etc/nss-pgsql.conf` і `/etc/nss-pgsql-root.conf` — лише шляхи для подальшої перевірки, оскільки параметри підключення можуть містити облікові дані. Роль у базі даних має значення лише тоді, коли вона може змінювати записи, які активний провайдер NSS фактично повертає, і обліковий запис може автентифікуватися за допомогою цих записів. Основний GID 0 надає членство в групі root, але не UID 0; відповідність групі sudo вимагає чинного [правила групи в sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html) і, за потреби, автентифікації. Відповідність UID 0 — це інша межа ідентичності. Під час пасивного переліку не виводьте рядки підключення та не змінюйте записи облікових записів.

Також порівняйте числові UID різних локальних імен облікових записів. Два імені в [`/etc/passwd`](https://man7.org/linux/man-pages/man5/passwd.5.html) можуть відповідати тій самій ідентичності файлів Unix, хоча записи автентифікації для входу можуть відрізнятися. Тому щойно доданий псевдонім зі спільним ненульовим UID після успішної автентифікації може надати доступ до файлів або процесів іншого користувача; він не надає root, якщо цей UID або окремий шлях підвищення привілеїв цього не забезпечує. Спільне використання UID може бути навмисним. Перевірте джерело облікового запису (`/etc/passwd` чи NSS), історію створення, оболонку та домашній каталог, фактичну політику автентифікації, а також чи дозволено цим обліковим записам спільно використовувати ідентичність. Перевірка дублікатів лише в локальних облікових записах не виключає псевдонім із каталогу.

## Пошук активних і нещодавніх сеансів

```bash
who -a
w
last -a | head
loginctl list-sessions 2>/dev/null
ps -eo user,pid,ppid,tty,cmd --sort=user | head -80
screen -ls 2>/dev/null
tmux ls 2>/dev/null
```

Сокет `screen` або `tmux` може надати доступ до наявної оболонки, якщо його дозволи дають змогу поточному користувачу приєднатися до неї. Перед спробою доступу перевірте власника та режим сокета: сесія іншого користувача не стає доступною автоматично. Також можуть мати значення активна мітка часу `sudo` або сокет SSH agent, але можливість їх повторного використання залежить від ідентичності користувача, дозволів і політик. Про зловживання пересиланням agent див. [експлуатація пересилання SSH agent](ssh-forward-agent-exploitation.md).

[Керівний сокет мультиплексування OpenSSH](https://man.openbsd.org/ssh_config#ControlMaster) відрізняється від `SSH_AUTH_SOCK`: `ControlMaster` і `ControlPath` дають змогу наступним SSH-клієнтам використовувати спільне наявне автентифіковане з’єднання, а `ControlPersist` може залишати master доступним після завершення першої сесії. Перевірте `.ssh/config` поточного користувача та неглибоко вкладені шляхи до сокетів у `.ssh`, зокрема власника й дозволи. Саме ім’я файлу сокета не доводить, що master активний, що поточний користувач може під’єднатися або який віддалений обліковий запис він використовує.

## Перевірка артефактів користувача

```bash
find /home -maxdepth 3 -type f \( -name 'authorized_keys' -o -name 'id_*' -o -name '*history' -o -name '.netrc' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home -maxdepth 3 -type f \( -name '.bashrc' -o -name '.profile' -o -name '.zshrc' \) -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Історія командної оболонки, файли запуску, SSH-ключі, конфігурація застосунків, сховища ключів GPG і кеші Kerberos можуть розкрити облікові дані або доступні для запису точки закріплення. Файл `authorized_keys` або файл запуску командної оболонки для привілейованішого облікового запису, доступний для запису, потребує перевірки. На [сторінці про post-exploitation](../post-exploitation/README.md) описано перенесення домашнього каталогу GPG і пошук облікових даних; у матеріалі [Linux Active Directory](linux-active-directory.md) розглянуто повторне використання кешу Kerberos і keytab. На [сторінці про PAM](../software-information/pam-pluggable-authentication-modules.md) пояснюються ризики політик автентифікації.
