# Βάσεις δεδομένων και απόρρητα δεδομένα σε Linux hosts

{{#include ../../banners/hacktricks-training.md}}

Τα διαπιστευτήρια βάσεων δεδομένων και εφαρμογών βρίσκονται συχνά δίπλα στην υπηρεσία που υποστηρίζουν. Καταγράψτε τη διεργασία, το τοπικό socket ή port, τη ρύθμιση και το αρχείο διαπιστευτηρίων πριν ελέγξετε αν ένας λογαριασμός μπορεί να διαβάσει δεδομένα ή να εκτελέσει μια προνομιούχα ενέργεια.

## Εντοπισμός τοπικών υπηρεσιών δεδομένων και διαπιστευτηρίων

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Ελέγξτε τα αναγνώσιμα αρχεία ρυθμίσεων εφαρμογών, αρχεία deployment, αρχεία περιβάλλοντος υπηρεσιών και αντίγραφα ασφαλείας για συμβολοσειρές σύνδεσης ή κλειδιά. Το Unix socket μιας διεργασίας DB μπορεί να έχει διαφορετικούς κανόνες πρόσβασης από τον TCP listener της. Τα δικαιώματα DB διαφέρουν από τα δικαιώματα του OS: ένας ανακτημένος κωδικός πρόσβασης DB παρέχει μόνο τους ρόλους που έχουν εκχωρηθεί σε αυτόν τον λογαριασμό DB, εκτός αν τεκμηριωθεί άλλη διαδρομή. Στο PostgreSQL, οι πολιτικές row-level security μπορούν να αποκρύπτουν εγγραφές από έναν ρόλο, ενώ ένας ρόλος με δικαιώματα διαχείρισης πολιτικών μπορεί να αλλάξει αυτή την προβολή· διακρίνετε την πρόσβαση σε δεδομένα από τη διαχείριση πολιτικών. Χρησιμοποιήστε τους ειδικούς για κάθε υπηρεσία οδηγούς για [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) και [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Ένα αναγνώσιμο script αυτοματοποίησης στον home directory άλλου λογαριασμού μπορεί να ενσωματώνει ένα διαπιστευτήριο, ακόμη κι αν το όνομα του αρχείου δεν αναφέρει κωδικούς πρόσβασης. Για παράδειγμα, ένα Python script μπορεί να εκκινεί το `su` και να στέλνει μια κυριολεκτική τιμή στην προτροπή κωδικού πρόσβασης μέσω του [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html)· το [`su`](https://man7.org/linux/man-pages/man1/su.1.html) εξακολουθεί να εφαρμόζει την πολιτική αυθεντικοποίησής του. Επιβεβαιώστε ότι ο τρέχων χρήστης μπορεί να διασχίσει τον κατάλογο και να διαβάσει το συγκεκριμένο script, ότι η κυριολεκτική τιμή προορίζεται ως κωδικός πρόσβασης του λογαριασμού-στόχου και ότι το διαπιστευτήριο εξακολουθεί να ισχύει, προτού το θεωρήσετε μετάβαση σε άλλον λογαριασμό. Το script δεν χρειάζεται να εκτελεστεί επιτυχώς για να αποκαλύψει ένα μυστικό μέσω του κειμένου του. Η παθητική έξοδος πρέπει να εμφανίζει τη διαδρομή και τα δικαιώματα χωρίς να εκτυπώνει την τιμή ή να επιχειρεί σύνδεση.

Μια αναγνώσιμη βάση δεδομένων εφαρμογής SQLite μπορεί να περιέχει ονόματα χρηστών και password hashes χωρίς να υπάρχει κάποια υπηρεσία βάσης δεδομένων σε κατάσταση ακρόασης. Επιθεωρήστε το schema και τα δικαιώματα του αρχείου προτού θεωρήσετε ένα hash αφορμή για offline έλεγχο. Ένας ανακτημένος κωδικός πρόσβασης εφαρμογής παρέχει πρόσβαση σε λογαριασμό OS ή σε τοπικό admin panel μόνο αν επιβεβαιωθεί ξεχωριστά η επαναχρησιμοποίησή του· η μορφή του hash ή το όνομα χρήστη που ταιριάζει δεν αποδεικνύει επαναχρησιμοποίηση.

Το Apache OFBiz μπορεί να χρησιμοποιεί ενσωματωμένη βάση δεδομένων Derby στη διαδρομή `runtime/data/derby/<database>/`. Το αρχείο `service.properties` του Derby προσδιορίζει τον κατάλογο της βάσης δεδομένων· ο γειτονικός κατάλογος `seg0` περιέχει τα αρχεία των πινάκων. Ελέγξτε τα δικαιώματα σε ολόκληρο τον κατάλογο της βάσης δεδομένων προτού εξετάσετε εγγραφές εφαρμογής όπως το `USER_LOGIN`. Ένας αναγνώσιμος δείκτης δεν αποδεικνύει ότι οι πίνακες είναι αναγνώσιμοι, ότι μπορεί να ανακτηθεί κωδικός πρόσβασης ή ότι ένα διαπιστευτήριο εφαρμογής λειτουργεί για λογαριασμό Unix. Μην εμφανίζετε το περιεχόμενο της βάσης δεδομένων και τα password hashes στη συνήθη έξοδο απαρίθμησης. Δείτε την [τεκμηρίωση καταλόγου βάσης δεδομένων Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) και το [API σύνδεσης του OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

Το TeamCity αποθηκεύει τα δεδομένα του server σε έναν διαμορφώσιμο κατάλογο δεδομένων (συχνά `.BuildServer`). Ελέγξτε τα δικαιώματα στα `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` όταν χρησιμοποιείται το ενσωματωμένο HSQLDB, καθώς και στα `backup/TeamCity_Backup_*.zip`. Τα SSH keys που έχουν μεταφορτωθεί και άλλες ασφαλείς ρυθμίσεις μπορεί να είναι κρυπτογραφημένα, επομένως μια αναγνώσιμη διαδρομή από μόνη της δεν αποδεικνύει ότι υπάρχει αξιοποιήσιμο ιδιωτικό κλειδί. Η βάση δεδομένων ή το αντίγραφο ασφαλείας μπορεί να περιέχει χρήστες εφαρμογής και password hashes· η χρήση τους για λογαριασμό Unix απαιτεί ξεχωριστά στοιχεία που να επιβεβαιώνουν την επαναχρησιμοποίηση κωδικού πρόσβασης. Κατά την απαρίθμηση, καταγράψτε διαδρομές και δικαιώματα πρόσβασης αντί να εκτυπώνετε κλειδιά, hashes ή γραμμές της βάσης δεδομένων. Δείτε την τεκμηρίωση του TeamCity για τον [κατάλογο δεδομένων](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), τα [SSH keys](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) και τα [αντίγραφα ασφαλείας](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Ο backup server Duplicati αποθηκεύει τις ρυθμίσεις του στο `Duplicati-server.sqlite`. Ο κατάλογος δεδομένων του μπορεί να βρίσκεται στον home directory του λογαριασμού της υπηρεσίας, στο `/var/lib/Duplicati` ή σε ένα container volume, ενώ τα `--server-datafolder` ή `DUPLICATI_HOME` μπορούν να αλλάξουν τη θέση του. Μια αναγνώσιμη βάση δεδομένων είναι σημαντικό εύρημα, καθώς μπορεί να περιέχει διαπιστευτήρια σύνδεσης και υλικό υπογραφής του server, αλλά οι νεότερες εγκαταστάσεις μπορεί να κρυπτογραφούν ευαίσθητα πεδία και να περιορίζουν την πρόσβαση στον κατάλογο. Συσχετίστε τα δικαιώματά του με τον πραγματικό λογαριασμό server και με οποιαδήποτε αυθεντικοποιημένη πρόσβαση στο UI ή στο ServerUtil. Αν ο server εκτελείται ως root με προσαρτημένο το host `/` στο container του, οι εξουσιοδοτημένες λειτουργίες επαναφοράς backup και τα job hooks μπορούν να διασχίσουν το όριο του filesystem του host· ένας listener σε loopback ή ένα όνομα αρχείου βάσης δεδομένων από μόνο του δεν αποδεικνύει έλεγχο. Η συμπεριφορά σύνδεσης με nonce παλαιότερων εκδόσεων δεν πρέπει να θεωρείται δεδομένη στις τρέχουσες εκδόσεις, οι οποίες χρησιμοποιούν διαφορετικό [μοντέλο αυθεντικοποίησης](https://docs.duplicati.com/technical-details/server-authentication-model). Για λεπτομέρειες ανά έκδοση, δείτε την τεκμηρίωση του Duplicati για τη [βάση δεδομένων του server](https://docs.duplicati.com/database-and-storage/the-server-database) και το [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil).

Για το PostgreSQL, επιθεωρήστε τα `pg_policies` και `pg_class.relrowsecurity` για να διακρίνετε ένα φιλτραρισμένο query από εγγραφές που λείπουν. Η αλλαγή ή απενεργοποίηση μιας πολιτικής απαιτεί τα κατάλληλα δικαιώματα ιδιοκτησίας πίνακα ή διαχειριστή. Ένας ξεχωριστά leaked λογαριασμός συντήρησης μπορεί να έχει αυτά τα δικαιώματα, ακόμη κι όταν δεν τα έχει ο λογαριασμός της εφαρμογής. Ένας Redis listener χωρίς αυθεντικοποίηση αποτελεί διαφορετικό εύρημα: επαληθεύστε αν κάνει bind μόνο σε loopback και αν το protected mode ή τα ACL περιορίζουν την τρέχουσα σύνδεση, προτού τον θεωρήσετε πηγή μυστικών.

## Ελέγξτε τα αποθετήρια κλειδιών και token

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Ένα SSH private key, ένα agent socket, ένα Kerberos cache, ένα GPG keyring ή ένα PKCS#12 bundle είναι χρήσιμο μόνο αν ο τρέχων χρήστης μπορεί να έχει πρόσβαση σε αυτό και τυχόν απαιτούμενη passphrase ή policy επιτρέπει τη χρήση του. Ελέγξτε πρώτα τον ιδιοκτήτη και τα permissions. Οι σελίδες [χρήστες και sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) και [post-exploitation](../post-exploitation/README.md) περιγράφουν τις αντίστοιχες διαδρομές πρόσβασης. Το Git history, τα παλιά backups και το shell history μπορεί επίσης να διατηρούν secrets αφού έχει καθαριστεί ένα ενεργό config. Ένας αναγνώσιμος κατάλογος `.git` μπορεί να διατηρεί διαγραμμένο source code και παλαιότερα committed credentials, ακόμη κι όταν το working tree είναι κενό· ελέγξτε την πρόσβαση και εξετάστε το history χειροκίνητα, αντί να το απορρίπτετε κατά την αυτοματοποιημένη απαρίθμηση.

Μια αναγνώσιμη boot image στο `/boot` είναι ένα ακόμη πιθανό αρχείο. Τα [Initramfs boot scripts και τα αντιγραμμένα helpers](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) μπορεί να περιλαμβάνουν custom logic που παρέχει ένα key στο [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Ελέγξτε τα permissions πρόσβασης της image και εξετάστε μόνο το σχετικό boot script και helper σε εξουσιοδοτημένο offline αντίγραφο. Μια ενσωματωμένη ή παραγόμενη passphrase ξεκλειδώματος δίσκου δεν είναι αυτομάτως password λογαριασμού Unix: επιβεβαιώστε τα inputs του helper, την πραγματική διαδρομή εκκίνησης και τυχόν ξεχωριστή επαναχρησιμοποίηση credentials πριν τη θεωρήσετε μετάβαση σε λογαριασμό. Η συνήθης απαρίθμηση δεν πρέπει να αποσυμπιέζει την image, να εκτελεί τα helpers της ή να εμφανίζει πιθανά keys.

Το Vault CLI [συνήθως αποθηκεύει προσωρινά το authentication token στο `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), αν και ένα custom token helper μπορεί να το αποθηκεύει αλλού. Μια αναγνώσιμη διαδρομή αποτελεί μόνο ένδειξη πιθανού credential: επαληθεύστε την εγκυρότητα του token και την policy πριν συμπεράνετε ότι υπάρχει πρόσβαση σε κάποιο secret engine. Για τα [Vault SSH one-time passwords](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), το token πρέπει να είναι εξουσιοδοτημένο να εκδίδει credentials για έναν ρόλο του οποίου ο χρήστης και το CIDR περιλαμβάνουν τον επιδιωκόμενο λογαριασμό και host· ο host πρέπει επίσης να έχει ρυθμισμένο το SSH verification helper και να αποδέχεται τη σύνδεση. Ένας ρόλος με όνομα `root` ή ένα αρχείο token από μόνο του δεν αποδεικνύει πρόσβαση root. Η παθητική απαρίθμηση πρέπει να αναφέρει τη διαδρομή του αρχείου, χωρίς να διαβάζει το token ή να ζητά OTP.

[Το KeePass 1.x χρησιμοποιεί `.kdb`, ενώ το KeePass 2.x χρησιμοποιεί `.kdbx`](https://keepass.info/help/v2/version.html). Αντιμετωπίστε ένα αρχείο με αντίστοιχο όνομα ως πιθανό κρυπτογραφημένο vault, καθώς και άλλα προϊόντα μπορεί να χρησιμοποιούν την κατάληξη `.kdb`. Ένα αναγνώσιμο vault δεν αποκαλύπτει τις καταχωρίσεις του χωρίς το απαιτούμενο master password ή key file· ένα SSH key αποθηκευμένο ως συνημμένο αποτελεί ξεχωριστή ένδειξη, της οποίας η πρόσβαση σε host πρέπει να επικυρωθεί. [Το KeePass δέχεται αυθαίρετα αρχεία, συμπεριλαμβανομένων εικόνων, ως key files](https://keepass.info/help/base/keys.html), αλλά ένα κοντινό αρχείο είναι απλώς υποψήφιο μέχρι να επιβεβαιωθούν ανεξάρτητα ο ρόλος του, όλα τα απαιτούμενα στοιχεία του master key και τυχόν σύνδεση σε λογαριασμό με υψηλότερα προνόμια.

Ένα support archive μπορεί να περιέχει τόσο ένα KeePass vault όσο και ένα process memory dump. Για το [KeePass 2.x πριν από την έκδοση 2.54, το CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) καθιστά πιθανή την ανάκτηση του master password από ένα αντίστοιχο dump· ένα κρυπτογραφημένο vault ή ένα άσχετο dump από μόνο του δεν αρκεί. Εξετάστε χειροκίνητα τα περιεχόμενα του archive και τα δικαιώματα πρόσβασης, χωρίς μαζική εξαγωγή ή εμφάνιση secrets κατά τη συνήθη απαρίθμηση. Τα private keys του PuTTY μπορεί να εμφανίζονται ως αρχεία `.ppk` ή ως κείμενο `PuTTY-User-Key-File` σε καταχώριση vault· επιβεβαιώστε ξεχωριστά τον λογαριασμό για τον οποίο προορίζεται το key, την κρυπτογράφησή του και τον host που το αποδέχεται.

Ένα αναγνώσιμο HTTP archive `.har` μπορεί να διατηρεί browser requests και responses, συμπεριλαμβανομένων authentication headers, cookies και πεδίων φορμών. Μπορεί να έχει αποθηκευτεί απευθείας ή μέσα σε συνημμένο υποστήριξης. Ελέγξτε πρώτα τον ιδιοκτήτη και την πρόσβαση και, στη συνέχεια, εξετάστε μόνο τις σχετικές καταχωρίσεις· το όνομα ενός αρχείου από μόνο του δεν αποδεικνύει ότι περιέχει επαναχρησιμοποιήσιμο credential. Η αυτοματοποιημένη απαρίθμηση πρέπει να καταγράφει τη διαδρομή του archive χωρίς να εμφανίζει τις τιμές που έχουν καταγραφεί. Η [τεκμηρίωση του Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) εξηγεί την επιλογή εξαγωγής ευαίσθητων δεδομένων.

Για κρυπτογραφημένα database backups, συσχετίστε το αναγνώσιμο archive, το προσβάσιμο υλικό private key και τυχόν απαίτηση passphrase πριν καταλήξετε σε συμπέρασμα. Όπου υπάρχει εξουσιοδότηση, η ανάκτηση της passphrase ενός προστατευμένου key και η εξέταση των αποκρυπτογραφημένων δεδομένων backup είναι ξεχωριστά χειροκίνητα βήματα. Ένα database credential για `root` δεν είναι Unix credential για `root`· η επαναχρησιμοποίηση password μεταξύ αυτών των λογαριασμών απαιτεί ξεχωριστή, εξουσιοδοτημένη επικύρωση. Τα όρια εμπιστοσύνης του filesystem σε web applications μπορούν επίσης να αποκαλύψουν τον λογαριασμό που κατέχει αυτά τα υλικά· δείτε την [εξέταση του Django file-cache](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Το container root και το host root είναι ξεχωριστές ταυτότητες. Ένα private SSH key που είναι αναγνώσιμο μόνο αφού αποκτήσετε root μέσα σε ένα container μπορεί να χρησιμοποιηθεί για σύνδεση σε λογαριασμό του host, αν ο host το αποδέχεται, αλλά το όνομα του key file ή το σχόλιο του public key δεν αποδεικνύει αυτή την πρόσβαση. Παρομοίως, ένας custom password generator δίπλα σε μια χρονοσημασμένη εγγραφή αλλαγής password αποτελεί μόνο ένδειξη για χειροκίνητη ανάλυση: ένας μη κρυπτογραφικός generator με seed από την ώρα μπορεί να έχει μικρό εύρος πιθανών seeds, αλλά η ζώνη ώρας, η ακρίβεια του ρολογιού, η συμπεριφορά της βιβλιοθήκης και οι μεταγενέστερες αλλαγές password επηρεάζουν την ανακατασκευή. Επικυρώστε πιθανά credentials μόνο όταν υπάρχει εξουσιοδότηση· μην θεωρείτε τα παραγόμενα υποψήφια passwords επιβεβαιωμένα.

Ένας service account μέσα σε container μπορεί να έχει τη δυνατότητα να διαβάσει ένα παλιό provisioning script σε έναν φαινομενικά προνομιούχο home directory, αν ο κατάλογος επιτρέπει διέλευση και τα permissions του αρχείου το επιτρέπουν. Ένα ενσωματωμένο application-admin password αποτελεί ένδειξη έκθεσης credential, όχι πρόσβαση host-root: ελέγξτε αν το script και το credential ήταν ενεργά, σε ποιον λογαριασμό ανήκει η τιμή και αν κάποιος ξεχωριστός λογαριασμός του host εξακολουθεί να δέχεται το ίδιο password. Κατά την παθητική απαρίθμηση, καταγράψτε τη διαδρομή του αρχείου και τα δικαιώματα πρόσβασης χωρίς να εμφανίσετε το secret ή να επιχειρήσετε authentication στον host.

Αν ένα αναγνώσιμο bundle `.p12` ή `.pfx` έχει password εκτεθειμένο στο application configuration, εξετάστε το με `openssl pkcs12 -info -in bundle.p12 -noout`. Αν το bundle περιέχει private key που μπορεί να εξαχθεί, η εντολή `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` γράφει το key χωρίς κρυπτογράφηση. Προστατέψτε το αρχείο εξόδου και διαγράψτε το μετά την ανάλυση· χρησιμοποιήστε το ανακτημένο key μόνο για την υπηρεσία ή το ciphertext με το οποίο πράγματι αντιστοιχεί. Ένα bundle από μόνο του δεν συνεπάγεται ότι το private key του είναι χρήσιμο για διαφορετική εφαρμογή.
