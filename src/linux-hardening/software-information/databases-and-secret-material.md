# Bancos de dados e material secreto em hosts Linux

{{#include ../../banners/hacktricks-training.md}}

As credenciais de bancos de dados e aplicações costumam ficar próximas ao serviço que atendem. Mapeie o processo, o socket ou a porta local, a configuração e o arquivo de credenciais antes de testar se uma conta pode ler dados ou executar uma operação privilegiada.

## Localizar serviços de dados locais e credenciais

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Inspecione configurações de aplicativos legíveis, arquivos de implantação, arquivos de ambiente de serviços e backups em busca de strings de conexão ou chaves. Um socket Unix de um processo de banco de dados pode ter regras de acesso diferentes das do listener TCP. As permissões do banco de dados diferem das permissões do sistema operacional: uma senha de banco de dados recuperada concede apenas as funções atribuídas àquela conta do banco de dados, a menos que outro caminho seja demonstrado. No PostgreSQL, políticas de segurança em nível de linha podem ocultar registros de uma função, enquanto uma função com direitos de gerenciamento de políticas pode alterar essa visualização; diferencie o acesso aos dados da administração de políticas. Use os guias específicos de cada serviço para [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) e [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Um script de automação legível no diretório home de outra conta pode conter uma credencial, mesmo que o nome do arquivo não mencione senhas. Por exemplo, um script Python pode iniciar `su` e enviar um valor literal ao prompt de senha com [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html); [`su`](https://man7.org/linux/man-pages/man1/su.1.html) ainda aplica sua política de autenticação. Confirme se o usuário atual pode percorrer o diretório e ler o script específico, se o valor literal é a senha da conta de destino e se a credencial ainda é válida antes de considerar isso uma transição de conta. O script não precisa ser executado com sucesso para que seu conteúdo revele um segredo. A saída passiva deve mostrar o caminho e as permissões sem exibir o valor nem tentar fazer login.

Um banco de dados SQLite legível de um aplicativo pode conter nomes de usuário e hashes de senha sem que haja um serviço de banco de dados em escuta. Inspecione o esquema e as permissões do arquivo antes de tratar um hash como uma pista para auditoria offline. Uma senha de aplicativo recuperada concede acesso a uma conta do sistema operacional ou a um painel de administração local somente se a reutilização for confirmada separadamente; o formato do hash ou um nome de usuário correspondente não comprovam reutilização.

O Apache OFBiz pode usar um banco de dados Derby incorporado em `runtime/data/derby/<database>/`. O arquivo `service.properties` do Derby identifica o diretório do banco de dados; seu diretório irmão `seg0` contém os arquivos das tabelas. Verifique as permissões de todo o diretório do banco de dados antes de analisar registros do aplicativo, como `USER_LOGIN`. Um marcador legível não prova que as tabelas sejam legíveis, que uma senha possa ser recuperada ou que uma credencial do aplicativo funcione para uma conta Unix. Não inclua o conteúdo do banco de dados nem hashes de senha na saída de enumeração rotineira. Consulte a [documentação do diretório de banco de dados do Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) e a [API de login do OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

O TeamCity mantém os dados do servidor em um diretório configurável (geralmente `.BuildServer`). Verifique as permissões de `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` quando o HSQLDB incorporado estiver em uso e `backup/TeamCity_Backup_*.zip`. Chaves SSH carregadas e outras configurações seguras podem estar criptografadas; portanto, um caminho legível, por si só, não comprova que uma chave privada seja utilizável. O banco de dados ou o backup podem conter usuários do aplicativo e hashes de senha; usá-los para uma conta Unix exige evidências separadas de reutilização da senha. Durante a enumeração, registre os caminhos e direitos de acesso em vez de exibir chaves, hashes ou linhas do banco de dados. Consulte a documentação do TeamCity sobre [diretório de dados](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [chaves SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) e [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

O servidor de backup Duplicati mantém a configuração em `Duplicati-server.sqlite`. Seu diretório de dados pode estar no diretório home da conta de serviço, em `/var/lib/Duplicati` ou em um volume de contêiner; `--server-datafolder` ou `DUPLICATI_HOME` podem alterá-lo. Um banco de dados legível é uma pista valiosa, pois pode conter credenciais de conexão e material de assinatura do servidor, mas instalações mais recentes podem criptografar campos confidenciais e restringir o acesso ao diretório. Correlacione suas permissões com a conta real do servidor e com qualquer acesso autenticado à interface ou ao ServerUtil. Se esse servidor for executado como root com o `/` do host montado em seu contêiner, a restauração autorizada de backups e os hooks de tarefas podem atravessar o limite do sistema de arquivos do host; um listener de loopback ou apenas o nome de um arquivo de banco de dados não comprovam controle. Não presuma que o comportamento de login baseado em nonce de versões antigas se aplica às versões atuais, que usam um [modelo de autenticação](https://docs.duplicati.com/technical-details/server-authentication-model) diferente. Consulte a documentação do Duplicati sobre o [banco de dados do servidor](https://docs.duplicati.com/database-and-storage/the-server-database) e o [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) para obter detalhes específicos da versão.

No PostgreSQL, inspecione `pg_policies` e `pg_class.relrowsecurity` para diferenciar uma consulta filtrada de registros ausentes. Alterar ou desativar uma política exige a propriedade apropriada da tabela ou privilégios administrativos. Uma conta de manutenção obtida por leak separadamente pode ter esses privilégios mesmo quando a conta do aplicativo não os tem. Um listener Redis sem autenticação é outra descoberta distinta: verifique se ele está vinculado apenas ao loopback e se o modo protegido ou as ACLs restringem a conexão atual antes de tratá-lo como fonte de segredos.

## Revise os armazenamentos de chaves e tokens

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Uma chave privada SSH, um socket do agent, um cache Kerberos, um keyring GPG ou um pacote PKCS#12 só são úteis se o usuário atual puder acessá-los e qualquer frase-senha ou política exigida permitir seu uso. Primeiro, inspecione a propriedade e as permissões. As páginas [usuários e sessões](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) e [post-exploitation](../post-exploitation/README.md) explicam os caminhos de acesso correspondentes. O histórico do Git, backups antigos e o histórico do shell também podem reter segredos depois que uma configuração ativa é limpa. Um diretório `.git` legível pode preservar código-fonte excluído e credenciais de commits anteriores, mesmo quando a árvore de trabalho está vazia; verifique o acesso e revise o histórico manualmente, em vez de despejá-lo durante a enumeração automatizada.

Uma imagem de boot legível em `/boot` é outra possível fonte de arquivos arquivados. [Scripts de boot do initramfs e auxiliares copiados](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) podem incluir lógica personalizada que fornece uma chave para [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Verifique as permissões de acesso da imagem e revise apenas o script de boot e o auxiliar relevantes em uma cópia offline autorizada. Uma frase-senha de desbloqueio de disco incorporada ou derivada não é automaticamente a senha de uma conta Unix: confirme as entradas do auxiliar, o caminho de boot real e se há reutilização independente de credenciais antes de tratá-la como uma transição entre contas. A enumeração de rotina não deve desempacotar a imagem, executar seus auxiliares nem exibir possíveis chaves.

A CLI do Vault [normalmente armazena em cache seu token de autenticação em `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), embora um token helper personalizado possa armazená-lo em outro local. Um caminho legível é apenas uma pista de credencial: verifique a validade do token e a política antes de inferir acesso a qualquer secret engine. Para [senhas de uso único SSH do Vault](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), o token deve estar autorizado a emitir credenciais para uma role cujo usuário e CIDR incluam a conta e o host pretendidos; esse host também deve ter o helper de verificação SSH configurado e aceitar o login. Uma role com o nome `root` ou um arquivo de token, por si só, não comprova acesso root. A enumeração passiva deve informar o caminho do arquivo sem ler o token ou solicitar uma OTP.

[O KeePass 1.x usa `.kdb`, enquanto o KeePass 2.x usa `.kdbx`](https://keepass.info/help/v2/version.html). Trate um nome de arquivo correspondente como um possível cofre criptografado, pois outros produtos podem usar o sufixo `.kdb`. Um cofre legível não revela suas entradas sem a senha mestra ou o arquivo de chave exigidos; uma chave SSH armazenada como anexo é uma pista separada cujo acesso ao host precisa ser validado. [O KeePass aceita arquivos arbitrários, incluindo imagens, como arquivos de chave](https://keepass.info/help/base/keys.html), mas um arquivo próximo é apenas um candidato até que sua função, todos os componentes da chave mestra exigidos e qualquer login em uma conta com privilégios mais elevados sejam confirmados de forma independente.

Um arquivo de suporte pode conter tanto um cofre KeePass quanto um dump da memória de um processo. Para [KeePass 2.x anterior à versão 2.54, o CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) torna potencialmente recuperável a senha mestra a partir de um dump correspondente; um cofre criptografado ou um dump não relacionado, por si só, não é suficiente. Inspecione manualmente as entradas do arquivo e os direitos de acesso, sem extração em massa nem exibição de segredos durante a enumeração de rotina. Chaves privadas PuTTY podem aparecer como arquivos `.ppk` ou como texto `PuTTY-User-Key-File` em uma entrada do cofre; confirme separadamente a conta pretendida para a chave, sua criptografia e se o host a aceita.

Um arquivo de tráfego HTTP `.har` legível pode preservar solicitações e respostas do navegador, incluindo cabeçalhos de autenticação, cookies e campos de formulários. Ele pode ser salvo diretamente ou dentro de um anexo de suporte. Primeiro, verifique a propriedade e o acesso; depois, inspecione apenas as entradas relevantes. Um nome de arquivo, por si só, não comprova que há uma credencial reutilizável. A enumeração automatizada deve listar o caminho do arquivo sem exibir os valores capturados. A [documentação do Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) explica a opção de exportação de dados confidenciais.

Para backups de banco de dados criptografados, correlacione o arquivo legível, o material de chave privada acessível e qualquer requisito de frase-senha antes de tirar conclusões. Quando autorizado, recuperar a frase-senha de uma chave protegida e inspecionar os dados do backup descriptografado são etapas manuais distintas. Uma credencial `root` de banco de dados não é uma credencial `root` do Unix; a reutilização de senha entre essas contas exige validação autorizada independente. Limites de confiança do sistema de arquivos em aplicações web também podem expor a conta proprietária desses materiais; consulte a [análise do cache de arquivos do Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

O root do container e o root do host são identidades distintas. Uma chave privada SSH legível somente após obter root dentro de um container pode autenticar em uma conta do host, caso o host a aceite, mas o nome do arquivo ou o comentário da chave pública não comprovam esse acesso. Da mesma forma, um gerador de senhas personalizado encontrado ao lado de um registro datado de alteração de senha é apenas uma pista para análise manual: um gerador não criptográfico baseado em tempo pode ter uma pequena janela de seeds candidatas, mas o fuso horário, a precisão do relógio, o comportamento da biblioteca e alterações posteriores de senha afetam a reconstrução. Valide credenciais candidatas somente quando autorizado; não trate as candidatas geradas como senhas confirmadas.

Uma conta de serviço dentro de um container pode conseguir ler um script antigo de provisionamento em um diretório home nominalmente privilegiado, se for possível atravessar o diretório e as permissões do arquivo permitirem. Uma senha de administrador da aplicação incorporada no script é uma pista de exposição de credencial, não de acesso root ao host: verifique se o script e a credencial estavam ativos, a qual conta o valor pertence e se uma conta separada do host ainda aceita a mesma senha. Durante a enumeração passiva, registre o caminho do arquivo e as permissões de acesso sem exibir o segredo nem tentar autenticação no host.

Se um pacote `.p12` ou `.pfx` legível tiver uma senha exposta na configuração da aplicação, inspecione-o com `openssl pkcs12 -info -in bundle.p12 -noout`. Quando o pacote contiver uma chave privada exportável, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` grava essa chave sem criptografia. Proteja o arquivo de saída e remova-o após a análise; use a chave recuperada apenas para o serviço ou texto cifrado com o qual ela realmente corresponde. Um pacote, por si só, não implica que sua chave privada seja útil para outra aplicação.
