# Βάσεις δεδομένων και μυστικό υλικό σε Linux Hosts

{{#include ../../banners/hacktricks-training.md}}

Τα διαπιστευτήρια βάσεων δεδομένων και εφαρμογών βρίσκονται συχνά δίπλα στην υπηρεσία που εξυπηρετούν. Χαρτογραφήστε τη διεργασία, το τοπικό socket ή port, τη διαμόρφωση και το αρχείο διαπιστευτηρίων πριν ελέγξετε αν ένας λογαριασμός μπορεί να διαβάσει δεδομένα ή να εκτελέσει μια προνομιακή ενέργεια.

## Εντοπισμός τοπικών υπηρεσιών δεδομένων και διαπιστευτηρίων

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Επιθεωρήστε τις αναγνώσιμες ρυθμίσεις εφαρμογών, τα αρχεία deployment, τα αρχεία περιβάλλοντος υπηρεσιών και τα αντίγραφα ασφαλείας για connection strings ή κλειδιά. Ένα Unix socket διεργασίας DB μπορεί να έχει διαφορετικούς κανόνες πρόσβασης από τον TCP listener της. Τα δικαιώματα βάσεων δεδομένων διαφέρουν από τα δικαιώματα του OS: ένας ανακτημένος κωδικός πρόσβασης DB παρέχει μόνο τους ρόλους που έχουν εκχωρηθεί σε αυτόν τον λογαριασμό DB, εκτός αν τεκμηριωθεί κάποια άλλη διαδρομή. Στο PostgreSQL, οι πολιτικές row-level security μπορούν να αποκρύπτουν εγγραφές από έναν ρόλο, ενώ ένας ρόλος με δικαιώματα διαχείρισης πολιτικών μπορεί να αλλάξει αυτή την προβολή· διακρίνετε την πρόσβαση σε δεδομένα από τη διαχείριση πολιτικών. Χρησιμοποιήστε τους οδηγούς για τις συγκεκριμένες υπηρεσίες [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) και [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Ένα αναγνώσιμο script αυτοματοποίησης στον home directory άλλου λογαριασμού μπορεί να περιέχει ενσωματωμένο credential, ακόμη κι αν το όνομά του δεν αναφέρει κωδικούς πρόσβασης. Για παράδειγμα, ένα Python script μπορεί να εκκινεί το `su` και να περνά μια κυριολεκτική τιμή στο prompt κωδικού πρόσβασης μέσω του [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html)· το [`su`](https://man7.org/linux/man-pages/man1/su.1.html) εξακολουθεί να εφαρμόζει την πολιτική αυθεντικοποίησής του. Επιβεβαιώστε ότι ο τρέχων χρήστης μπορεί να διασχίσει τον κατάλογο και να διαβάσει το συγκεκριμένο script, ότι η κυριολεκτική τιμή προορίζεται ως κωδικός πρόσβασης του λογαριασμού-στόχου και ότι το credential εξακολουθεί να ισχύει, προτού το θεωρήσετε μετάβαση σε άλλον λογαριασμό. Δεν χρειάζεται το script να εκτελείται επιτυχώς για να αποκαλύψει ένα μυστικό μέσω του περιεχομένου του. Η παθητική έξοδος πρέπει να εμφανίζει τη διαδρομή και τα δικαιώματα, χωρίς να εκτυπώνει την τιμή ή να δοκιμάζει σύνδεση.

Μια αναγνώσιμη βάση δεδομένων εφαρμογής SQLite μπορεί να περιέχει ονόματα χρηστών και hashes κωδικών πρόσβασης, χωρίς να υπάρχει κάποια υπηρεσία βάσης δεδομένων σε κατάσταση ακρόασης. Εξετάστε το schema και τα δικαιώματα του αρχείου προτού θεωρήσετε ένα hash αφορμή για offline έλεγχο. Ένας ανακτημένος κωδικός πρόσβασης εφαρμογής παρέχει πρόσβαση σε λογαριασμό OS ή σε τοπικό admin panel μόνο αν επιβεβαιωθεί ξεχωριστά η επαναχρησιμοποίησή του· η μορφή του hash ή το αντίστοιχο όνομα χρήστη δεν αποδεικνύουν επαναχρησιμοποίηση.

Το Apache OFBiz μπορεί να χρησιμοποιεί ενσωματωμένη βάση δεδομένων Derby στον κατάλογο `runtime/data/derby/<database>/`. Το αρχείο `service.properties` του Derby υποδεικνύει τον κατάλογο της βάσης δεδομένων· ο γειτονικός κατάλογος `seg0` περιέχει αρχεία πινάκων. Ελέγξτε τα δικαιώματα ολόκληρου του καταλόγου της βάσης δεδομένων προτού εξετάσετε εγγραφές εφαρμογής, όπως το `USER_LOGIN`. Ένα αναγνώσιμο αρχείο-δείκτης δεν αποδεικνύει ότι οι πίνακες είναι αναγνώσιμοι, ότι μπορεί να ανακτηθεί κωδικός πρόσβασης ή ότι ένα credential εφαρμογής λειτουργεί για λογαριασμό Unix. Μην συμπεριλαμβάνετε τα περιεχόμενα της βάσης δεδομένων και τα hashes κωδικών πρόσβασης στη συνήθη έξοδο enumeration. Δείτε την [Derby database-directory documentation](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) και το [OFBiz login API](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

Το TeamCity διατηρεί τα δεδομένα του server σε έναν διαμορφώσιμο κατάλογο δεδομένων (συχνά `.BuildServer`). Ελέγξτε τα δικαιώματα των `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` όταν χρησιμοποιείται το ενσωματωμένο HSQLDB, και `backup/TeamCity_Backup_*.zip`. Τα μεταφορτωμένα SSH keys και άλλες ασφαλείς ρυθμίσεις ενδέχεται να είναι κρυπτογραφημένα, επομένως μια αναγνώσιμη διαδρομή από μόνη της δεν αποδεικνύει ότι το ιδιωτικό κλειδί μπορεί να χρησιμοποιηθεί. Η βάση δεδομένων ή το αντίγραφο ασφαλείας μπορεί να περιέχει χρήστες εφαρμογής και hashes κωδικών πρόσβασης· η χρήση τους για λογαριασμό Unix απαιτεί ξεχωριστά στοιχεία που να αποδεικνύουν επαναχρησιμοποίηση κωδικού πρόσβασης. Κατά το enumeration, καταγράψτε διαδρομές και δικαιώματα πρόσβασης αντί να εκτυπώνετε κλειδιά, hashes ή γραμμές βάσης δεδομένων. Δείτε την τεκμηρίωση του TeamCity για τον [data-directory](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), τα [SSH-key](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) και τα [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Ο backup server Duplicati διατηρεί τις ρυθμίσεις του στο `Duplicati-server.sqlite`. Ο κατάλογος δεδομένων του μπορεί να βρίσκεται στον home directory του λογαριασμού υπηρεσίας, στο `/var/lib/Duplicati` ή σε ένα container volume, ενώ τα `--server-datafolder` ή `DUPLICATI_HOME` μπορούν να αλλάξουν τη θέση του. Μια αναγνώσιμη βάση δεδομένων αποτελεί σημαντικό στοιχείο, επειδή μπορεί να περιέχει credentials σύνδεσης και υλικό υπογραφής του server, αλλά σε νεότερες εγκαταστάσεις τα ευαίσθητα πεδία ενδέχεται να είναι κρυπτογραφημένα και η πρόσβαση στον κατάλογο περιορισμένη. Συσχετίστε τα δικαιώματά της με τον πραγματικό λογαριασμό του server και με οποιαδήποτε αυθεντικοποιημένη πρόσβαση μέσω UI ή ServerUtil. Αν ο server εκτελείται ως root με προσαρτημένο το host `/` μέσα στο container του, οι εξουσιοδοτημένες λειτουργίες επαναφοράς backup και τα hooks εργασιών μπορούν να παρακάμψουν τα όρια του filesystem του host· ένας listener loopback ή ένα όνομα αρχείου βάσης δεδομένων από μόνο του δεν αποδεικνύει έλεγχο. Δεν πρέπει να θεωρείται δεδομένη για τις τρέχουσες εκδόσεις η συμπεριφορά σύνδεσης παλαιότερων εκδόσεων που βασιζόταν σε nonce· οι τρέχουσες εκδόσεις χρησιμοποιούν διαφορετικό [authentication model](https://docs.duplicati.com/technical-details/server-authentication-model). Για λεπτομέρειες ανά έκδοση, δείτε την τεκμηρίωση του Duplicati για τη [server database](https://docs.duplicati.com/database-and-storage/the-server-database) και το [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil).

Για το PostgreSQL, εξετάστε τα `pg_policies` και `pg_class.relrowsecurity` για να διακρίνετε ένα φιλτραρισμένο query από εγγραφές που λείπουν. Η αλλαγή ή απενεργοποίηση μιας πολιτικής απαιτεί τα κατάλληλα δικαιώματα ιδιοκτησίας πίνακα ή διαχειριστή. Ένας ξεχωριστός λογαριασμός συντήρησης με leak μπορεί να διαθέτει αυτά τα δικαιώματα, ακόμη κι αν ο λογαριασμός της εφαρμογής δεν τα έχει. Ένας listener Redis χωρίς αυθεντικοποίηση αποτελεί διαφορετικό εύρημα: επαληθεύστε αν είναι δεσμευμένος μόνο στο loopback και αν το protected mode ή τα ACL περιορίζουν την τρέχουσα σύνδεση, προτού τον θεωρήσετε πηγή μυστικών.

## Εξέταση αποθηκευμένων κλειδιών και token

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Ένα SSH private key, agent socket, Kerberos cache, GPG keyring ή PKCS#12 bundle είναι χρήσιμο μόνο αν ο τρέχων χρήστης έχει πρόσβαση σε αυτό και αν η χρήση του επιτρέπεται από τυχόν απαιτούμενο passphrase ή πολιτική. Ελέγξτε πρώτα τον κάτοχο και τα δικαιώματα. Οι σελίδες [χρήστες και συνεδρίες](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) και [post-exploitation](../post-exploitation/README.md) εξηγούν τις αντίστοιχες διαδρομές πρόσβασης. Το ιστορικό του Git, τα παλιά αντίγραφα ασφαλείας και το ιστορικό του shell μπορούν επίσης να διατηρούν μυστικά ακόμη και αφού καθαριστεί μια ενεργή ρύθμιση. Ένας αναγνώσιμος κατάλογος `.git` μπορεί να διατηρεί διαγραμμένο πηγαίο κώδικα και παλαιότερα διαπιστευτήρια που είχαν γίνει commit, ακόμη κι όταν το working tree είναι κενό· ελέγξτε την πρόσβαση και εξετάστε το ιστορικό χειροκίνητα αντί να το εξάγετε κατά την αυτοματοποιημένη απαρίθμηση.

Μια αναγνώσιμη εικόνα εκκίνησης στο `/boot` είναι ένα ακόμη πιθανό αρχείο. Τα [initramfs boot scripts και τα αντιγραμμένα βοηθητικά προγράμματα](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) μπορεί να περιλαμβάνουν προσαρμοσμένη λογική που παρέχει ένα κλειδί στο [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Ελέγξτε τα δικαιώματα πρόσβασης της εικόνας και εξετάστε μόνο το σχετικό boot script και το βοηθητικό πρόγραμμα σε εξουσιοδοτημένο offline αντίγραφο. Ένα ενσωματωμένο ή παράγωγο passphrase ξεκλειδώματος δίσκου δεν είναι αυτομάτως κωδικός πρόσβασης λογαριασμού Unix: επιβεβαιώστε τις εισόδους του βοηθητικού προγράμματος, την πραγματική διαδρομή εκκίνησης και τυχόν επαναχρησιμοποίηση διαπιστευτηρίων ξεχωριστά, προτού το θεωρήσετε μετάβαση σε λογαριασμό. Η συνηθισμένη απαρίθμηση δεν πρέπει να αποσυσκευάζει την εικόνα, να εκτελεί τα βοηθητικά προγράμματα ή να εμφανίζει πιθανά κλειδιά.

Το Vault CLI [συνήθως αποθηκεύει προσωρινά το authentication token στο `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), αν και ένα προσαρμοσμένο token helper μπορεί να το αποθηκεύει αλλού. Μια αναγνώσιμη διαδρομή αποτελεί μόνο ένδειξη για πιθανό διαπιστευτήριο: επαληθεύστε την εγκυρότητα του token και την πολιτική του προτού συμπεράνετε ότι υπάρχει πρόσβαση σε οποιοδήποτε secret engine. Για [one-time passwords του Vault SSH](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), το token πρέπει να είναι εξουσιοδοτημένο να εκδίδει διαπιστευτήρια για έναν ρόλο του οποίου ο χρήστης και το CIDR περιλαμβάνουν τον προοριζόμενο λογαριασμό και host· ο host πρέπει επίσης να έχει ρυθμισμένο το SSH verification helper και να αποδέχεται τη σύνδεση. Ένας ρόλος με όνομα `root` ή ένα αρχείο token από μόνο του δεν αποδεικνύει πρόσβαση root. Η παθητική απαρίθμηση πρέπει να αναφέρει τη διαδρομή του αρχείου χωρίς να διαβάζει το token ή να ζητά OTP.

[Το KeePass 1.x χρησιμοποιεί `.kdb`, ενώ το KeePass 2.x χρησιμοποιεί `.kdbx`](https://keepass.info/help/v2/version.html). Αντιμετωπίστε ένα αρχείο με αντίστοιχο όνομα ως πιθανό κρυπτογραφημένο vault, καθώς και άλλα προϊόντα μπορεί να χρησιμοποιούν την κατάληξη `.kdb`. Ένα αναγνώσιμο vault δεν αποκαλύπτει τις καταχωρίσεις του χωρίς το απαιτούμενο master password ή key file· ένα SSH key αποθηκευμένο ως συνημμένο είναι ξεχωριστή ένδειξη, της οποίας η πρόσβαση σε host πρέπει να επαληθευτεί. [Το KeePass δέχεται αυθαίρετα αρχεία, συμπεριλαμβανομένων εικόνων, ως key files](https://keepass.info/help/base/keys.html), αλλά ένα κοντινό αρχείο είναι απλώς υποψήφιο μέχρι να επιβεβαιωθούν ανεξάρτητα ο ρόλος του, όλα τα απαιτούμενα συστατικά του master key και τυχόν σύνδεση σε λογαριασμό με υψηλότερα δικαιώματα.

Ένα αρχείο υποστήριξης μπορεί να περιέχει τόσο ένα KeePass vault όσο και ένα dump μνήμης διεργασίας. Για [το KeePass 2.x πριν από την έκδοση 2.54, το CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) καθιστά πιθανώς ανακτήσιμο το master password από το αντίστοιχο dump· ένα κρυπτογραφημένο vault ή ένα άσχετο dump από μόνο του δεν αρκεί. Εξετάστε χειροκίνητα τις καταχωρίσεις του αρχείου και τα δικαιώματα πρόσβασης, χωρίς μαζική εξαγωγή ή εμφάνιση μυστικών κατά τη συνηθισμένη απαρίθμηση. Τα private keys του PuTTY μπορεί να εμφανίζονται ως αρχεία `.ppk` ή ως κείμενο `PuTTY-User-Key-File` σε καταχώριση vault· επιβεβαιώστε ξεχωριστά τον προβλεπόμενο λογαριασμό του κλειδιού, την κρυπτογράφησή του και τον host που το αποδέχεται.

Ένα αναγνώσιμο HTTP archive `.har` μπορεί να διατηρεί αιτήματα και αποκρίσεις του browser, συμπεριλαμβανομένων των authentication headers, cookies και πεδίων φορμών. Μπορεί να είναι αποθηκευμένο απευθείας ή μέσα σε συνημμένο υποστήριξης. Ελέγξτε πρώτα τον κάτοχο και την πρόσβαση και, στη συνέχεια, εξετάστε μόνο τις σχετικές καταχωρίσεις· ένα όνομα αρχείου από μόνο του δεν αποδεικνύει ότι περιέχει επαναχρησιμοποιήσιμο διαπιστευτήριο. Η αυτοματοποιημένη απαρίθμηση πρέπει να καταγράφει τη διαδρομή του αρχείου χωρίς να εμφανίζει τις καταγεγραμμένες τιμές. Η [τεκμηρίωση του Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) εξηγεί την επιλογή εξαγωγής ευαίσθητων δεδομένων.

Για κρυπτογραφημένα αντίγραφα ασφαλείας βάσεων δεδομένων, συσχετίστε το αναγνώσιμο αρχείο, το προσβάσιμο υλικό private key και τυχόν απαίτηση passphrase προτού καταλήξετε σε συμπέρασμα. Όπου υπάρχει εξουσιοδότηση, η ανάκτηση του passphrase ενός προστατευμένου κλειδιού και η εξέταση των αποκρυπτογραφημένων δεδομένων αντιγράφου ασφαλείας είναι ξεχωριστά χειροκίνητα βήματα. Ένα διαπιστευτήριο `root` βάσης δεδομένων δεν είναι διαπιστευτήριο `root` του Unix· η επαναχρησιμοποίηση κωδικού πρόσβασης μεταξύ αυτών των λογαριασμών απαιτεί ξεχωριστή, εξουσιοδοτημένη επαλήθευση. Τα όρια εμπιστοσύνης του filesystem σε web εφαρμογές μπορούν επίσης να αποκαλύψουν τον λογαριασμό στον οποίο ανήκει αυτό το υλικό· δείτε την [εξέταση του file cache στο Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Το root του container και το root του host είναι ξεχωριστές ταυτότητες. Ένα private SSH key που είναι αναγνώσιμο μόνο αφού αποκτήσετε root μέσα σε ένα container μπορεί να επιτρέψει authentication σε λογαριασμό του host, αν ο host το αποδέχεται, αλλά το όνομα του αρχείου ή το σχόλιο του public key δεν αποδεικνύει αυτή την πρόσβαση. Παρομοίως, ένας προσαρμοσμένος password generator που βρίσκεται δίπλα σε ένα χρονοσημασμένο αρχείο καταγραφής αλλαγής κωδικού πρόσβασης αποτελεί μόνο ένδειξη για χειροκίνητη ανάλυση: ένας μη κρυπτογραφικός generator με seed τον χρόνο μπορεί να έχει μικρό εύρος πιθανών seed, αλλά η ζώνη ώρας, η ακρίβεια του ρολογιού, η συμπεριφορά της βιβλιοθήκης και τυχόν μεταγενέστερες αλλαγές κωδικού επηρεάζουν την ανακατασκευή. Επαληθεύστε πιθανά διαπιστευτήρια μόνο εφόσον έχετε εξουσιοδότηση· μην αντιμετωπίζετε τους παραγόμενους υποψήφιους κωδικούς ως επιβεβαιωμένους.

Ένας λογαριασμός υπηρεσίας μέσα σε container μπορεί να έχει δυνατότητα ανάγνωσης ενός παλιού script προετοιμασίας σε έναν φαινομενικά προνομιούχο προσωπικό κατάλογο, αν ο κατάλογος επιτρέπει τη διέλευση και τα δικαιώματα του αρχείου το επιτρέπουν. Ένας ενσωματωμένος κωδικός πρόσβασης διαχειριστή εφαρμογής αποτελεί ένδειξη έκθεσης διαπιστευτηρίου, όχι πρόσβαση root στον host: ελέγξτε αν το script και το διαπιστευτήριο ήταν ενεργά, σε ποιον λογαριασμό αντιστοιχεί η τιμή και αν κάποιος ξεχωριστός λογαριασμός του host εξακολουθεί να αποδέχεται τον ίδιο κωδικό πρόσβασης. Κατά την παθητική απαρίθμηση, καταγράψτε τη διαδρομή του αρχείου και τα δικαιώματα πρόσβασης χωρίς να εμφανίσετε το μυστικό ή να επιχειρήσετε authentication στον host.

Αν ένα αναγνώσιμο bundle `.p12` ή `.pfx` έχει κωδικό πρόσβασης εκτεθειμένο στη ρύθμιση παραμέτρων της εφαρμογής, εξετάστε το με `openssl pkcs12 -info -in bundle.p12 -noout`. Αν το bundle περιέχει εξαγώγιμο private key, η εντολή `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` γράφει αυτό το κλειδί χωρίς κρυπτογράφηση. Προστατέψτε το αρχείο εξόδου και διαγράψτε το μετά την ανάλυση· χρησιμοποιήστε το κλειδί που ανακτήθηκε μόνο για την υπηρεσία ή το ciphertext με το οποίο αντιστοιχεί πράγματι. Ένα bundle από μόνο του δεν συνεπάγεται ότι το private key του είναι χρήσιμο για διαφορετική εφαρμογή.
