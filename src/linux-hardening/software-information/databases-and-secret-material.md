# Βάσεις δεδομένων και μυστικό υλικό σε Linux Hosts

{{#include ../../banners/hacktricks-training.md}}

Τα διαπιστευτήρια βάσεων δεδομένων και εφαρμογών βρίσκονται συχνά δίπλα στην υπηρεσία που υποστηρίζουν. Χαρτογραφήστε τη διεργασία, το τοπικό socket ή port, τη διαμόρφωση και το αρχείο διαπιστευτηρίων, προτού ελέγξετε αν ένας λογαριασμός μπορεί να διαβάσει δεδομένα ή να εκτελέσει μια προνομιακή λειτουργία.

## Εντοπισμός τοπικών υπηρεσιών δεδομένων και διαπιστευτηρίων

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Ελέγξτε αναγνώσιμα application configs, αρχεία deployment, αρχεία περιβάλλοντος υπηρεσιών και αντίγραφα ασφαλείας για connection strings ή keys. Ένα Unix socket μιας διεργασίας DB μπορεί να έχει διαφορετικούς κανόνες πρόσβασης από τον TCP listener της. Τα δικαιώματα της βάσης δεδομένων διαφέρουν από τα δικαιώματα του OS: ένας ανακτημένος κωδικός πρόσβασης DB παρέχει μόνο τους ρόλους που έχουν εκχωρηθεί σε αυτόν τον λογαριασμό DB, εκτός αν αποδειχθεί άλλη οδός. Στο PostgreSQL, οι πολιτικές row-level security μπορεί να αποκρύπτουν εγγραφές από έναν ρόλο, ενώ ένας ρόλος με δικαιώματα διαχείρισης πολιτικών μπορεί να αλλάξει αυτήν την προβολή· διακρίνετε την πρόσβαση στα δεδομένα από τη διαχείριση πολιτικών. Χρησιμοποιήστε τους ειδικούς οδηγούς για [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) και [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Ένα αναγνώσιμο automation script στον home directory άλλου λογαριασμού μπορεί να περιέχει ενσωματωμένο credential, ακόμη κι αν το όνομα του αρχείου δεν αναφέρει κωδικούς πρόσβασης. Για παράδειγμα, ένα Python script μπορεί να εκκινήσει το `su` και να στείλει μια κυριολεκτική τιμή στο prompt κωδικού πρόσβασης μέσω του [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html)· το [`su`](https://man7.org/linux/man-pages/man1/su.1.html) εξακολουθεί να εφαρμόζει την πολιτική αυθεντικοποίησής του. Επιβεβαιώστε ότι ο τρέχων χρήστης μπορεί να διασχίσει τον κατάλογο και να διαβάσει το συγκεκριμένο script, ότι η κυριολεκτική τιμή προορίζεται για κωδικό πρόσβασης του λογαριασμού-στόχου και ότι το credential παραμένει έγκυρο, προτού το θεωρήσετε μετάβαση σε άλλον λογαριασμό. Το script δεν χρειάζεται να εκτελείται επιτυχώς για να αποκαλύψει ένα secret στο κείμενό του. Η παθητική έξοδος πρέπει να εμφανίζει τη διαδρομή και τα δικαιώματα χωρίς να εκτυπώνει την τιμή ή να επιχειρεί σύνδεση.

Μια αναγνώσιμη SQLite database εφαρμογής μπορεί να περιέχει ονόματα χρηστών και password hashes χωρίς να υπάρχει υπηρεσία βάσης δεδομένων που ακούει. Εξετάστε το schema και τα δικαιώματα του αρχείου προτού θεωρήσετε ένα hash στοιχείο για offline έλεγχο. Ένας ανακτημένος κωδικός πρόσβασης εφαρμογής παρέχει πρόσβαση σε OS account ή τοπικό admin panel μόνο αν επιβεβαιωθεί ξεχωριστά η επαναχρησιμοποίησή του· η μορφή του hash ή το αντίστοιχο όνομα χρήστη δεν αποδεικνύουν επαναχρησιμοποίηση.

Το Apache OFBiz μπορεί να χρησιμοποιεί ενσωματωμένη Derby database στο `runtime/data/derby/<database>/`. Το αρχείο `service.properties` της Derby υποδεικνύει τον κατάλογο της βάσης δεδομένων· ο γειτονικός κατάλογος `seg0` περιέχει αρχεία πινάκων. Ελέγξτε τα δικαιώματα ολόκληρου του καταλόγου της βάσης δεδομένων προτού εξετάσετε εγγραφές εφαρμογής, όπως το `USER_LOGIN`. Ένας αναγνώσιμος δείκτης δεν αποδεικνύει ότι οι πίνακες είναι αναγνώσιμοι, ότι μπορεί να ανακτηθεί κωδικός πρόσβασης ή ότι ένα credential εφαρμογής λειτουργεί για λογαριασμό Unix. Μην συμπεριλαμβάνετε τα περιεχόμενα βάσεων δεδομένων και τα password hashes στη συνήθη έξοδο enumeration. Δείτε την [τεκμηρίωση καταλόγου βάσης δεδομένων Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) και το [login API του OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

Το TeamCity διατηρεί τα δεδομένα του server σε έναν παραμετροποιήσιμο κατάλογο δεδομένων (συχνά `.BuildServer`). Ελέγξτε τα δικαιώματα στα `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` όταν χρησιμοποιείται η ενσωματωμένη HSQLDB, καθώς και στο `backup/TeamCity_Backup_*.zip`. Τα SSH keys που έχουν μεταφορτωθεί και άλλες ασφαλείς ρυθμίσεις μπορεί να είναι κρυπτογραφημένα, επομένως μια αναγνώσιμη διαδρομή από μόνη της δεν αποδεικνύει ότι υπάρχει αξιοποιήσιμο private key. Η βάση δεδομένων ή το backup μπορεί να περιέχει χρήστες εφαρμογής και password hashes· η χρήση τους για λογαριασμό Unix απαιτεί ξεχωριστά στοιχεία που να αποδεικνύουν επαναχρησιμοποίηση κωδικού πρόσβασης. Κατά το enumeration, καταγράψτε τις διαδρομές και τα δικαιώματα πρόσβασης αντί να εκτυπώνετε keys, hashes ή γραμμές βάσεων δεδομένων. Δείτε την τεκμηρίωση του TeamCity για τον [κατάλογο δεδομένων](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), τη [διαχείριση SSH keys](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) και τα [backups](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Ο backup server του Duplicati διατηρεί τις ρυθμίσεις του στο `Duplicati-server.sqlite`. Ο κατάλογος δεδομένων του μπορεί να βρίσκεται στον home directory του service account, στο `/var/lib/Duplicati` ή σε ένα container volume, ενώ τα `--server-datafolder` ή `DUPLICATI_HOME` μπορούν να τον αλλάξουν. Μια αναγνώσιμη βάση δεδομένων αποτελεί σημαντικό στοιχείο, επειδή μπορεί να περιέχει connection credentials και υλικό υπογραφής του server, αλλά οι νεότερες εγκαταστάσεις ενδέχεται να κρυπτογραφούν ευαίσθητα πεδία και να περιορίζουν την πρόσβαση στον κατάλογο. Συσχετίστε τα δικαιώματά της με τον πραγματικό λογαριασμό του server και με τυχόν αυθεντικοποιημένη πρόσβαση μέσω UI ή ServerUtil. Αν αυτός ο server εκτελείται ως root με προσαρτημένο το host `/` στο container του, οι εξουσιοδοτημένες λειτουργίες επαναφοράς backup και τα job hooks μπορούν να διασχίσουν το όριο του filesystem του host· ένας loopback listener ή ένα όνομα αρχείου βάσης δεδομένων από μόνο του δεν αποδεικνύει έλεγχο. Δεν πρέπει να θεωρείται δεδομένη για τις τρέχουσες εκδόσεις η συμπεριφορά σύνδεσης παλαιότερων εκδόσεων που βασιζόταν σε nonce· χρησιμοποιούν διαφορετικό [μοντέλο αυθεντικοποίησης](https://docs.duplicati.com/technical-details/server-authentication-model). Δείτε την τεκμηρίωση του Duplicati για τη [βάση δεδομένων του server](https://docs.duplicati.com/database-and-storage/the-server-database) και το [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) για λεπτομέρειες ανά έκδοση.

Για το PostgreSQL, εξετάστε τα `pg_policies` και `pg_class.relrowsecurity` για να διακρίνετε ένα φιλτραρισμένο query από εγγραφές που λείπουν. Η αλλαγή ή απενεργοποίηση μιας πολιτικής απαιτεί τα κατάλληλα δικαιώματα ιδιοκτησίας πίνακα ή διαχειριστή. Ένας λογαριασμός συντήρησης που έχει διαρρεύσει ξεχωριστά μπορεί να έχει αυτά τα δικαιώματα, ακόμη κι αν ο λογαριασμός της εφαρμογής δεν τα έχει. Ένας μη αυθεντικοποιημένος Redis listener είναι επίσης ξεχωριστό εύρημα: επαληθεύστε αν κάνει bind μόνο στη loopback διεύθυνση και αν το protected mode ή τα ACL περιορίζουν την τρέχουσα σύνδεση προτού τον θεωρήσετε πηγή secret.

## Ελέγξτε τα stores κλειδιών και token

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Ένα SSH private key, agent socket, Kerberos cache, GPG keyring ή PKCS#12 bundle είναι χρήσιμο μόνο αν ο τρέχων χρήστης έχει πρόσβαση σε αυτό και αν η απαιτούμενη passphrase ή policy επιτρέπει τη χρήση του. Ελέγξτε πρώτα τον ιδιοκτήτη και τα δικαιώματα. Οι σελίδες [χρήστες και συνεδρίες](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) και [post-exploitation](../post-exploitation/README.md) εξηγούν τις αντίστοιχες διαδρομές πρόσβασης. Το Git history, τα παλιά backups και το shell history μπορούν επίσης να διατηρούν secrets, ακόμη και μετά τον καθαρισμό μιας ενεργής διαμόρφωσης. Ένας αναγνώσιμος κατάλογος `.git` μπορεί να διατηρεί διαγραμμένο πηγαίο κώδικα και παλαιότερα διαπιστευτήρια που είχαν γίνει commit, ακόμη κι αν το working tree είναι κενό· ελέγξτε την πρόσβαση και εξετάστε το history χειροκίνητα, αντί να το εξάγετε κατά την αυτοματοποιημένη απαρίθμηση.

Μια αναγνώσιμη boot image στο `/boot` είναι ένα ακόμη πιθανό αρχειακό στοιχείο. Τα [boot scripts του initramfs και τα αντιγραμμένα βοηθητικά προγράμματα](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) μπορεί να περιλαμβάνουν προσαρμοσμένη λογική που παρέχει ένα key στο [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Ελέγξτε τα δικαιώματα πρόσβασης της image και εξετάστε μόνο το σχετικό boot script και το helper σε εξουσιοδοτημένο offline αντίγραφο. Μια ενσωματωμένη ή παραγόμενη passphrase ξεκλειδώματος δίσκου δεν είναι αυτομάτως κωδικός πρόσβασης λογαριασμού Unix: επιβεβαιώστε τα inputs του helper, την πραγματική διαδρομή εκκίνησης και την ξεχωριστή επαναχρησιμοποίηση διαπιστευτηρίων πριν τη θεωρήσετε μετάβαση σε λογαριασμό. Η συνήθης απαρίθμηση δεν πρέπει να αποσυσκευάζει την image, να εκτελεί τα helpers της ή να εμφανίζει πιθανά keys.

Το Vault CLI [συνήθως αποθηκεύει προσωρινά το authentication token στο `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), αν και ένα προσαρμοσμένο token helper μπορεί να το αποθηκεύει αλλού. Μια αναγνώσιμη διαδρομή είναι απλώς ένδειξη πιθανού διαπιστευτηρίου: επαληθεύστε την ισχύ του token και την policy πριν συμπεράνετε ότι υπάρχει πρόσβαση σε οποιοδήποτε secret engine. Για [one-time passwords του Vault SSH](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), το token πρέπει να έχει εξουσιοδότηση να εκδίδει διαπιστευτήρια για έναν ρόλο του οποίου ο χρήστης και το CIDR περιλαμβάνουν τον προβλεπόμενο λογαριασμό και host· ο host πρέπει επίσης να έχει ρυθμισμένο το SSH verification helper και να δέχεται τη σύνδεση. Ένας ρόλος με όνομα `root` ή ένα αρχείο token από μόνο του δεν αποδεικνύει πρόσβαση root. Η παθητική απαρίθμηση πρέπει να αναφέρει τη διαδρομή του αρχείου χωρίς να διαβάζει το token ή να ζητά OTP.

Το [KeePass 1.x χρησιμοποιεί `.kdb`, ενώ το KeePass 2.x χρησιμοποιεί `.kdbx`](https://keepass.info/help/v2/version.html). Αντιμετωπίστε ένα αρχείο με αντίστοιχο όνομα ως πιθανό κρυπτογραφημένο vault, καθώς και άλλα προϊόντα μπορεί να χρησιμοποιούν την κατάληξη `.kdb`. Ένα αναγνώσιμο vault δεν αποκαλύπτει τις εγγραφές του χωρίς τον απαιτούμενο master password ή key file· ένα SSH key αποθηκευμένο ως attachment είναι ξεχωριστή ένδειξη, της οποίας η πρόσβαση σε host πρέπει να επαληθευτεί. Το [KeePass δέχεται αυθαίρετα αρχεία, συμπεριλαμβανομένων εικόνων, ως key files](https://keepass.info/help/base/keys.html), αλλά ένα κοντινό αρχείο είναι απλώς υποψήφιο μέχρι να επιβεβαιωθούν ανεξάρτητα ο ρόλος του, όλα τα απαιτούμενα στοιχεία του master key και οποιαδήποτε σύνδεση σε λογαριασμό με υψηλότερα προνόμια.

Ένα support archive μπορεί να περιέχει τόσο ένα KeePass vault όσο και ένα dump μνήμης διεργασίας. Για το [KeePass 2.x πριν από την έκδοση 2.54, το CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) καθιστά πιθανή την ανάκτηση του master password από αντίστοιχο dump· ένα κρυπτογραφημένο vault ή ένα άσχετο dump από μόνο του δεν αρκεί. Εξετάστε χειροκίνητα τις εγγραφές του archive και τα δικαιώματα πρόσβασης, χωρίς μαζική εξαγωγή ή εμφάνιση secrets κατά τη συνήθη απαρίθμηση. Τα PuTTY private keys μπορεί να εμφανίζονται ως αρχεία `.ppk` ή ως κείμενο `PuTTY-User-Key-File` σε εγγραφή vault· επιβεβαιώστε ξεχωριστά τον προβλεπόμενο λογαριασμό του key, την κρυπτογράφησή του και τον host που το αποδέχεται.

Ένα αναγνώσιμο HTTP archive `.har` μπορεί να διατηρεί αιτήματα και αποκρίσεις του browser, συμπεριλαμβανομένων authentication headers, cookies και πεδίων φορμών. Μπορεί να είναι αποθηκευμένο απευθείας ή μέσα σε ένα support attachment. Ελέγξτε πρώτα τον ιδιοκτήτη και τα δικαιώματα πρόσβασης και, έπειτα, εξετάστε μόνο τις σχετικές εγγραφές· το όνομα αρχείου από μόνο του δεν αποδεικνύει ότι περιέχει επαναχρησιμοποιήσιμο διαπιστευτήριο. Η αυτοματοποιημένη απαρίθμηση πρέπει να εμφανίζει τη διαδρομή του archive χωρίς να εκτυπώνει τις καταγεγραμμένες τιμές. Η [τεκμηρίωση του Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) εξηγεί την επιλογή εξαγωγής ευαίσθητων δεδομένων.

Για κρυπτογραφημένα database backups, συσχετίστε το αναγνώσιμο archive, το προσβάσιμο υλικό private key και τυχόν απαίτηση passphrase πριν καταλήξετε σε συμπέρασμα. Όπου υπάρχει εξουσιοδότηση, η ανάκτηση της passphrase ενός προστατευμένου key και η εξέταση των αποκρυπτογραφημένων δεδομένων backup είναι ξεχωριστά χειροκίνητα βήματα. Ένα διαπιστευτήριο `root` βάσης δεδομένων δεν είναι διαπιστευτήριο `root` Unix· η επαναχρησιμοποίηση κωδικού πρόσβασης μεταξύ αυτών των λογαριασμών απαιτεί ξεχωριστή, εξουσιοδοτημένη επαλήθευση. Τα όρια εμπιστοσύνης του filesystem σε web applications μπορούν επίσης να αποκαλύψουν τον λογαριασμό που κατέχει αυτά τα υλικά· δείτε την [εξέταση της file cache του Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Το root ενός container και το root του host είναι ξεχωριστές ταυτότητες. Ένα private SSH key, αναγνώσιμο μόνο αφού αποκτήσετε root μέσα σε container, μπορεί να χρησιμοποιηθεί για authentication σε λογαριασμό του host αν ο host το αποδέχεται, αλλά το όνομα αρχείου ή το σχόλιο public key δεν αποδεικνύει αυτή την πρόσβαση. Ομοίως, ένα προσαρμοσμένο password generator που βρίσκεται δίπλα σε μια χρονοσημασμένη εγγραφή αλλαγής κωδικού πρόσβασης είναι απλώς ένδειξη για χειροκίνητη ανάλυση: ένας μη κρυπτογραφικός generator με seed από τον χρόνο μπορεί να έχει μικρό εύρος πιθανών seed, αλλά η ζώνη ώρας, η ακρίβεια του ρολογιού, η συμπεριφορά της βιβλιοθήκης και μεταγενέστερες αλλαγές κωδικού επηρεάζουν την ανακατασκευή. Επαληθεύστε πιθανά διαπιστευτήρια μόνο όταν έχετε εξουσιοδότηση· μην αντιμετωπίζετε τους παραγόμενους υποψήφιους κωδικούς ως επιβεβαιωμένους.

Ένας service account μέσα σε container μπορεί να έχει τη δυνατότητα να διαβάσει ένα παλιό provisioning script σε έναν κατά τα άλλα προνομιούχο κατάλογο home, αν ο κατάλογος επιτρέπει τη διέλευση και τα δικαιώματα του αρχείου το επιτρέπουν. Ένας ενσωματωμένος κωδικός πρόσβασης application-admin αποτελεί ένδειξη έκθεσης διαπιστευτηρίου, όχι πρόσβασης host-root: ελέγξτε αν το script και το διαπιστευτήριο ήταν ενεργά, σε ποιον λογαριασμό ανήκει η τιμή και αν κάποιος ξεχωριστός λογαριασμός host εξακολουθεί να δέχεται τον ίδιο κωδικό πρόσβασης. Κατά την παθητική απαρίθμηση, καταγράψτε τη διαδρομή του αρχείου και τα δικαιώματα πρόσβασης χωρίς να εμφανίσετε το secret ή να επιχειρήσετε authentication στον host.

Αν ένα αναγνώσιμο bundle `.p12` ή `.pfx` έχει κωδικό πρόσβασης εκτεθειμένο στη διαμόρφωση της εφαρμογής, εξετάστε το με `openssl pkcs12 -info -in bundle.p12 -noout`. Αν το bundle περιέχει private key που μπορεί να εξαχθεί, η εντολή `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` γράφει το key χωρίς κρυπτογράφηση. Προστατεύστε το αρχείο εξόδου και διαγράψτε το μετά την ανάλυση· χρησιμοποιήστε το ανακτημένο key μόνο για την υπηρεσία ή το ciphertext με το οποίο πράγματι αντιστοιχεί. Ένα bundle από μόνο του δεν υποδηλώνει ότι το private key του είναι χρήσιμο για διαφορετική εφαρμογή.
