# Linux Hosts पर Databases और Secret Material

{{#include ../../banners/hacktricks-training.md}}

Database और application credentials अक्सर उसी service के पास रखे होते हैं जिसे वे support करते हैं। यह जाँचने से पहले कि कोई account data पढ़ सकता है या privileged operation execute कर सकता है, process, local socket या port, configuration और credential file का पता लगाएँ।

## Local data services और credentials का पता लगाएँ

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

पठनीय application configs, deployment files, service environment files और backups में connection strings या keys देखें। DB process के Unix socket पर access rules, उसके TCP listener से अलग हो सकते हैं। Database permissions, OS permissions से अलग होते हैं: बरामद DB password से केवल वही roles मिलते हैं जो उस DB account को दिए गए हैं, जब तक कि किसी दूसरे रास्ते का प्रमाण न हो। PostgreSQL में row-level security policies किसी role से records छिपा सकती हैं, जबकि policy-management rights वाला role उस view को बदल सकता है; data access और policy administration में अंतर करें। [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) और [Redis](../../network-services-pentesting/6379-pentesting-redis.md) के लिए service-specific guides देखें।

किसी दूसरे account के home में मौजूद पठनीय automation script में credential हो सकता है, भले ही उसके filename में password का उल्लेख न हो। उदाहरण के लिए, Python script [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html) के ज़रिए `su` चला सकती है और उसके password prompt में literal value भेज सकती है; [`su`](https://man7.org/linux/man-pages/man1/su.1.html) फिर भी अपनी authentication policy लागू करता है। इसे account transition मानने से पहले पुष्टि करें कि मौजूदा user directory में जा सकता है और ठीक वही script पढ़ सकता है, literal value लक्षित account के password के रूप में इस्तेमाल होनी है, और credential अब भी मान्य है। किसी secret का खुलासा करने के लिए script का सफलतापूर्वक चलना ज़रूरी नहीं है। Passive output में path और permissions दिखने चाहिए, value प्रिंट नहीं होनी चाहिए और login की कोशिश नहीं करनी चाहिए।

पठनीय SQLite application database में user names और password hashes हो सकते हैं, भले ही कोई database service listen न कर रही हो। Hash को offline audit lead मानने से पहले उसका schema और file permissions देखें। बरामद application password से OS-account या local-admin-panel access तभी मिलता है, जब password reuse की अलग से पुष्टि हो; hash format या मेल खाता user name, reuse का प्रमाण नहीं है।

Apache OFBiz `runtime/data/derby/<database>/` के अंदर embedded Derby database इस्तेमाल कर सकता है। Derby की `service.properties` file database directory को चिह्नित करती है; उसकी sibling `seg0` directory में table files होती हैं। `USER_LOGIN` जैसे application records देखने से पहले पूरी database directory की permissions जाँचें। पठनीय marker से यह साबित नहीं होता कि tables भी पठनीय हैं, password बरामद किया जा सकता है, या application credential किसी Unix account के लिए काम करता है। नियमित enumeration output में database contents और password hashes शामिल न करें। [Derby database-directory documentation](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) और [OFBiz login API](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html) देखें।

TeamCity अपना server data configurable data directory में रखता है (अक्सर `.BuildServer`)। `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, embedded HSQLDB इस्तेमाल होने पर `system/buildserver.*`, और `backup/TeamCity_Backup_*.zip` की permissions देखें। Uploaded SSH keys और अन्य secure settings encrypted हो सकती हैं, इसलिए केवल path का पठनीय होना usable private key का प्रमाण नहीं है। Database या backup में application users और password hashes हो सकते हैं; उन्हें Unix account के लिए इस्तेमाल करने हेतु password reuse का अलग प्रमाण चाहिए। Enumeration के दौरान paths और access rights दर्ज करें; keys, hashes या database rows प्रिंट न करें। TeamCity के [data-directory](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [SSH-key](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) और [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html) documentation देखें।

Duplicati backup server अपना configuration `Duplicati-server.sqlite` में रखता है। इसकी data directory service account के home, `/var/lib/Duplicati` या container volume में हो सकती है; `--server-datafolder` या `DUPLICATI_HOME` इसे बदल सकते हैं। पठनीय database एक high-value lead है, क्योंकि इसमें connection credentials और server signing material हो सकता है, लेकिन नए installations sensitive fields को encrypt कर सकते हैं और directory access सीमित कर सकते हैं। इसकी permissions का मिलान वास्तविक server account और किसी authenticated UI या ServerUtil access से करें। यदि वह server root के रूप में चलता है और उसके container में host `/` mounted है, तो authorized backup restore और job hooks host filesystem boundary पार कर सकते हैं; loopback listener या database filename अकेले control का प्रमाण नहीं हैं। पुराने releases के nonce-based login behavior को मौजूदा versions के लिए न मानें, क्योंकि वे अलग [authentication model](https://docs.duplicati.com/technical-details/server-authentication-model) इस्तेमाल करते हैं। Version-specific जानकारी के लिए Duplicati की [server database](https://docs.duplicati.com/database-and-storage/the-server-database) और [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) documentation देखें।

PostgreSQL में `pg_policies` और `pg_class.relrowsecurity` देखें, ताकि filtered query और missing records में अंतर किया जा सके। किसी policy को बदलने या disable करने के लिए उचित table ownership या administrative privileges चाहिए। अलग से leak हुआ maintenance account ये privileges रख सकता है, भले ही application account के पास न हों। Unauthenticated Redis listener एक अलग finding है: इसे secret source मानने से पहले सत्यापित करें कि वह केवल loopback से bind है या नहीं, और protected mode या ACLs मौजूदा connection को सीमित करते हैं या नहीं।

## Key और token stores की समीक्षा करें

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

एक SSH private key, agent socket, Kerberos cache, GPG keyring या PKCS#12 bundle तभी उपयोगी है, जब मौजूदा user उसे access कर सके और आवश्यक passphrase या policy उसके उपयोग की अनुमति दे। पहले ownership और permissions की जाँच करें। [users and sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) और [post-exploitation](../post-exploitation/README.md) पेज संबंधित access paths समझाते हैं। Git history, पुराने backups और shell history में live config साफ़ किए जाने के बाद भी secrets मौजूद रह सकते हैं। Readable `.git` directory में deleted source और पहले commit किए गए credentials सुरक्षित रह सकते हैं, भले ही working tree खाली हो; automated enumeration के दौरान history dump करने के बजाय access जाँचें और उसका manually review करें।

`/boot` में readable boot image भी archive की जाँच के लिए एक सुराग है। [Initramfs boot scripts and copied helpers](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) में custom logic हो सकता है, जो [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html) को key देता है। Image की access permissions जाँचें और अधिकृत offline copy में केवल संबंधित boot script और helper का review करें। Embedded या derived disk-unlock passphrase अपने-आप में Unix account password नहीं होता: इसे account transition मानने से पहले helper के inputs, वास्तविक boot path और credential reuse की अलग से पुष्टि करें। Routine enumeration के दौरान image को unpack न करें, इसके helpers execute न करें और संभावित keys प्रिंट न करें।

Vault CLI [आमतौर पर अपना authentication token `~/.vault-token` में cache करता है](https://developer.hashicorp.com/vault/docs/commands/token-helper), हालाँकि custom token helper उसे कहीं और store कर सकता है। किसी path का readable होना केवल credential का सुराग है: किसी भी secret engine तक access का अनुमान लगाने से पहले token की validity और policy की पुष्टि करें। [Vault SSH one-time passwords](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords) के लिए, token को ऐसे role के लिए credentials जारी करने की अनुमति होनी चाहिए जिसका user और CIDR इच्छित account और host को शामिल करता हो; उस host पर SSH verification helper भी configured होना चाहिए और उसे login स्वीकार करना चाहिए। `root` नाम वाला role या केवल token file, root access साबित नहीं करता। Passive enumeration में token पढ़े या OTP माँगे बिना file path की जानकारी दें।

[KeePass 1.x `.kdb` का उपयोग करता है, जबकि KeePass 2.x `.kdbx` का](https://keepass.info/help/v2/version.html)। किसी मेल खाते filename को संभावित encrypted vault मानें, क्योंकि अन्य products भी `.kdb` suffix का उपयोग कर सकते हैं। आवश्यक master password या key file के बिना readable vault की entries नहीं दिखेंगी; attachment के रूप में stored SSH key एक अलग सुराग है, जिसके host access की पुष्टि करनी होगी। [KeePass किसी भी file, images सहित, को key file के रूप में स्वीकार करता है](https://keepass.info/help/base/keys.html), लेकिन पास की कोई file तब तक केवल एक candidate है, जब तक उसकी भूमिका, सभी आवश्यक master-key components और अधिक privileged account login की स्वतंत्र रूप से पुष्टि न हो जाए।

एक support archive में KeePass vault और process memory dump, दोनों हो सकते हैं। [KeePass 2.x में 2.54 से पहले, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) के कारण संबंधित dump से master password संभावित रूप से recover किया जा सकता है; केवल encrypted vault या असंबंधित dump पर्याप्त नहीं है। Routine enumeration के दौरान bulk extraction या secrets प्रिंट किए बिना archive entries और access rights को manually inspect करें। PuTTY private keys `.ppk` files के रूप में या vault entry में `PuTTY-User-Key-File` text के रूप में मिल सकती हैं; key का intended account, encryption और स्वीकार करने वाले host की अलग से पुष्टि करें।

Readable `.har` HTTP archive में authentication headers, cookies और form fields सहित browser requests और responses सुरक्षित रह सकते हैं। इसे सीधे या support attachment के भीतर save किया गया हो सकता है। पहले ownership और access जाँचें, फिर केवल संबंधित entries inspect करें; केवल filename से reusable credential साबित नहीं होता। Automated enumeration में captured values प्रिंट किए बिना archive path की जानकारी दें। [Microsoft Edge documentation](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) में sensitive-data export option की जानकारी है।

Encrypted database backups के लिए निष्कर्ष निकालने से पहले readable archive, accessible private-key material और किसी भी passphrase की आवश्यकता का आपस में मिलान करें। जहाँ अधिकृत हो, protected key का passphrase recover करना और decrypted backup data inspect करना अलग-अलग manual steps हैं। Database का `root` credential, Unix का `root` credential नहीं है; उन accounts के बीच password reuse की अलग से, अधिकृत पुष्टि आवश्यक है। Web applications में filesystem trust boundaries उन accounts को भी expose कर सकती हैं जिनके पास ये materials हैं; [Django file-cache review](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce) देखें।

Container root और host root अलग identities हैं। Container के अंदर root बनने के बाद ही readable होने वाली private SSH key किसी host account से authenticate कर सकती है, यदि host उसे स्वीकार करता हो; लेकिन key filename या public-key comment उस access को साबित नहीं करता। इसी तरह, timestamped password-change record के पास मिला custom password generator केवल manual analysis का सुराग है: time-seeded non-cryptographic generator के संभावित seed की छोटी window हो सकती है, लेकिन timezone, clock precision, library behavior और बाद में हुए password changes reconstruction को प्रभावित करते हैं। Candidate credentials की पुष्टि केवल अधिकृत होने पर करें; generated candidates को confirmed passwords न मानें।

Container के अंदर किसी service account को nominally privileged home directory में पुरानी provisioning script पढ़ने की अनुमति हो सकती है, यदि directory traversable हो और file permissions इसकी अनुमति दें। उसमें मौजूद application-admin password credential exposure का सुराग है, host-root access नहीं: जाँचें कि script और credential सक्रिय थे या नहीं, value किस account की है और क्या कोई अलग host account अब भी वही password स्वीकार करता है। Passive enumeration के दौरान secret प्रिंट किए या host authentication का प्रयास किए बिना file path और access rights दर्ज करें।

यदि readable `.p12` या `.pfx` bundle का password application configuration में exposed है, तो इसे `openssl pkcs12 -info -in bundle.p12 -noout` से inspect करें। जहाँ bundle में exportable private key हो, वहाँ `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` उस key को बिना encryption के लिखता है। Output file को सुरक्षित रखें और analysis के बाद हटा दें; recovered key का उपयोग केवल उसी service या ciphertext के लिए करें जिससे उसका वास्तव में मेल हो। केवल bundle मौजूद होने से यह सिद्ध नहीं होता कि उसकी private key किसी दूसरे application के लिए उपयोगी है।
