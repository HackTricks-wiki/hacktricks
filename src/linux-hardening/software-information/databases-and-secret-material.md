# Linux होस्ट पर डेटाबेस और सीक्रेट सामग्री

{{#include ../../banners/hacktricks-training.md}}

डेटाबेस और एप्लिकेशन के क्रेडेंशियल अक्सर उसी सर्विस के पास रखे होते हैं, जिसका वे समर्थन करते हैं। यह जाँचने से पहले कि कोई अकाउंट डेटा पढ़ सकता है या प्रिविलेज्ड ऑपरेशन कर सकता है, प्रोसेस, लोकल सॉकेट या पोर्ट, कॉन्फ़िगरेशन और क्रेडेंशियल फ़ाइल का पता लगाएँ।

## लोकल डेटा सर्विस और क्रेडेंशियल खोजें

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

पढ़ने योग्य application configs, deployment files, service environment files और backups में connection strings या keys देखें। DB process के Unix socket पर TCP listener से अलग access rules लागू हो सकते हैं। Database permissions और OS permissions अलग होती हैं: मिला हुआ DB password केवल उस DB account को दिए गए roles तक access देता है, जब तक कोई दूसरा रास्ता साबित न हो। PostgreSQL में row-level security policies एक role से records छिपा सकती हैं, जबकि policy-management rights वाला role उस view को बदल सकता है; data access और policy administration में फर्क करें। [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md), और [Redis](../../network-services-pentesting/6379-pentesting-redis.md) के लिए service-specific guides देखें।

किसी दूसरे account के home में पढ़ने योग्य automation script में credential हो सकता है, भले ही उसके filename में passwords का ज़िक्र न हो। उदाहरण के लिए, Python script `su` चला सकती है और [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html) के ज़रिए उसके password prompt पर literal value भेज सकती है; [`su`](https://man7.org/linux/man-pages/man1/su.1.html) फिर भी अपनी authentication policy लागू करता है। इसे account transition मानने से पहले पुष्टि करें कि मौजूदा user directory में traverse कर सकता है और ठीक उस script को पढ़ सकता है, literal value target account के password के तौर पर ही है, और credential अब भी valid है। Secret उजागर करने के लिए script का सफलतापूर्वक चलना ज़रूरी नहीं है। Passive output में value दिखाए बिना path और permissions दिखने चाहिए; login करने की कोशिश भी न करें।

पढ़ने योग्य SQLite application database में user names और password hashes हो सकते हैं, जबकि कोई database service listen न कर रही हो। Hash को offline audit के lead के तौर पर लेने से पहले उसका schema और file permissions जाँचें। मिला हुआ application password OS-account या local-admin-panel access तभी देता है, जब password reuse की अलग से पुष्टि हो; hash format या मिलता-जुलता user name reuse का सबूत नहीं है।

Apache OFBiz `runtime/data/derby/<database>/` में embedded Derby database का इस्तेमाल कर सकता है। Derby की `service.properties` file database directory बताती है; उसकी sibling `seg0` directory में table files होते हैं। `USER_LOGIN` जैसे application records देखने से पहले पूरी database directory की permissions जाँचें। Marker का पढ़ने योग्य होना यह साबित नहीं करता कि tables भी पढ़ी जा सकती हैं, password recover किया जा सकता है, या application credential किसी Unix account के लिए काम करता है। सामान्य enumeration output में database contents और password hashes न दिखाएँ। [Derby database-directory documentation](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) और [OFBiz login API](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html) देखें।

TeamCity अपना server data configurable data directory में रखता है (अक्सर `.BuildServer`)। `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, embedded HSQLDB के इस्तेमाल पर `system/buildserver.*`, और `backup/TeamCity_Backup_*.zip` की permissions जाँचें। Uploaded SSH keys और अन्य secure settings encrypted हो सकती हैं, इसलिए केवल path का पढ़ने योग्य होना किसी usable private key का सबूत नहीं है। Database या backup में application users और password hashes हो सकते हैं; Unix account के लिए उनका इस्तेमाल करने के लिए password reuse का अलग सबूत चाहिए। Enumeration के दौरान keys, hashes या database rows दिखाने के बजाय paths और access rights दर्ज करें। TeamCity की [data-directory](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [SSH-key](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html), और [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html) documentation देखें।

Duplicati backup server configuration को `Duplicati-server.sqlite` में रखता है। इसका data directory service account के home, `/var/lib/Duplicati`, या container volume में हो सकता है; `--server-datafolder` या `DUPLICATI_HOME` इसे बदल सकते हैं। पढ़ने योग्य database एक high-value lead है, क्योंकि इसमें connection credentials और server signing material हो सकते हैं; लेकिन नए installations में sensitive fields encrypted हो सकते हैं और directory access प्रतिबंधित हो सकता है। इसकी permissions का मिलान असल server account और किसी authenticated UI या ServerUtil access से करें। अगर वह server root के रूप में चलता है और उसके container में host का `/` mounted है, तो authorized backup restore और job hooks host filesystem boundary पार कर सकते हैं; केवल loopback listener या database filename control का सबूत नहीं है। पुराने releases के nonce-based login व्यवहार को मौजूदा versions पर लागू न मानें; वे अलग [authentication model](https://docs.duplicati.com/technical-details/server-authentication-model) इस्तेमाल करते हैं। Version-specific जानकारी के लिए Duplicati की [server database](https://docs.duplicati.com/database-and-storage/the-server-database) और [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) documentation देखें।

PostgreSQL में `pg_policies` और `pg_class.relrowsecurity` जाँचें, ताकि filtered query और missing records में फर्क किया जा सके। Policy बदलने या disable करने के लिए उचित table ownership या administrative privileges चाहिए। अलग से leak हुआ maintenance account ये privileges रख सकता है, जबकि application account के पास न हों। Unauthenticated Redis listener एक अलग finding है: इसे secret source मानने से पहले जाँचें कि वह केवल loopback पर bind है या नहीं, और protected mode या ACLs मौजूदा connection को प्रतिबंधित करते हैं या नहीं।

## Key और token stores की समीक्षा करें

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

एक SSH private key, agent socket, Kerberos cache, GPG keyring, या PKCS#12 bundle तभी उपयोगी है जब मौजूदा user उसे access कर सके और आवश्यक passphrase या policy उसके उपयोग की अनुमति दे। पहले ownership और permissions की जाँच करें। [users and sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md), और [post-exploitation](../post-exploitation/README.md) पेज संबंधित access paths समझाते हैं। Live config को साफ़ करने के बाद भी Git history, पुराने backups, और shell history में secrets रह सकते हैं। Readable `.git` directory में हटाया गया source और पहले commit किए गए credentials सुरक्षित रह सकते हैं, भले ही working tree खाली हो; automated enumeration के दौरान उन्हें dump करने के बजाय access जाँचें और history की manually समीक्षा करें।

`/boot` में मौजूद readable boot image, archives की जाँच के लिए एक और सुराग है। [Initramfs boot scripts and copied helpers](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) में ऐसा custom logic हो सकता है जो [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html) को key देता हो। Image की access permissions जाँचें और केवल संबंधित boot script तथा helper की authorized offline copy में समीक्षा करें। Embedded या derived disk-unlock passphrase अपने-आप में Unix account password नहीं होता: इसे account transition मानने से पहले helper के inputs, वास्तविक boot path, और credential reuse की अलग से पुष्टि करें। Routine enumeration में image को unpack न करें, उसके helpers execute न करें, और संभावित keys print न करें।

Vault CLI [आमतौर पर अपना authentication token `~/.vault-token` में cache करता है](https://developer.hashicorp.com/vault/docs/commands/token-helper), हालांकि custom token helper उसे कहीं और store कर सकता है। Readable path केवल credential का सुराग है: किसी भी secret engine तक access मानने से पहले token की validity और policy की पुष्टि करें। [Vault SSH one-time passwords](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords) के लिए, token को ऐसी role के credentials issue करने की अनुमति होनी चाहिए जिसके user और CIDR में लक्षित account और host शामिल हों; उस host पर SSH verification helper भी configured होना चाहिए और login स्वीकार होना चाहिए। `root` नाम वाली role या केवल token file, root access साबित नहीं करती। Passive enumeration में token पढ़े या OTP माँगे बिना file path दर्ज करें।

[KeePass 1.x `.kdb` का उपयोग करता है, जबकि KeePass 2.x `.kdbx` का](https://keepass.info/help/v2/version.html)। मिलते-जुलते filename को संभावित encrypted vault मानें, क्योंकि अन्य products भी `.kdb` suffix का उपयोग कर सकते हैं। आवश्यक master password या key file के बिना readable vault की entries नहीं दिखेंगी; attachment के रूप में store की गई SSH key एक अलग सुराग है, जिसके host access की पुष्टि करनी होगी। [KeePass images सहित कोई भी file key file के रूप में स्वीकार करता है](https://keepass.info/help/base/keys.html), लेकिन पास की कोई file केवल संभावित key file है—उसकी भूमिका, आवश्यक सभी master-key components, और अधिक privileges वाले account से login की स्वतंत्र रूप से पुष्टि होने तक।

Support archive में KeePass vault और process memory dump दोनों हो सकते हैं। [KeePass 2.x में 2.54 से पहले के versions के लिए, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) के कारण संबंधित dump से master password संभावित रूप से recover किया जा सकता है; केवल encrypted vault या असंबंधित dump पर्याप्त नहीं है। Routine enumeration के दौरान bulk extraction या secrets print किए बिना archive entries और access rights की manually जाँच करें। PuTTY private keys `.ppk` files के रूप में या vault entry में `PuTTY-User-Key-File` text के रूप में मिल सकती हैं; key का intended account, encryption, और accepted host अलग से verify करें।

Readable `.har` HTTP archive में browser requests और responses सुरक्षित रह सकते हैं, जिनमें authentication headers, cookies, और form fields शामिल हैं। इसे सीधे या support attachment के अंदर save किया गया हो सकता है। पहले ownership और access जाँचें, फिर केवल संबंधित entries की जाँच करें; केवल filename से reusable credential साबित नहीं होता। Automated enumeration में captured values print करने के बजाय archive path सूचीबद्ध करें। [Microsoft Edge documentation](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) में sensitive-data export option का विवरण है।

Encrypted database backups के लिए निष्कर्ष निकालने से पहले readable archive, accessible private-key material, और किसी भी passphrase requirement का मिलान करें। जहाँ authorized हो, protected key का passphrase recover करना और decrypted backup data की जाँच करना अलग-अलग manual steps हैं। Database का `root` credential, Unix का `root` credential नहीं है; इन accounts के बीच password reuse की अलग से authorized पुष्टि आवश्यक है। Web applications में filesystem trust boundaries उस account को भी उजागर कर सकती हैं जिसके पास ये materials हैं; [Django file-cache review](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce) देखें।

Container root और host root अलग identities हैं। Container के अंदर root बनने के बाद ही readable होने वाली private SSH key किसी host account से authenticate कर सकती है, यदि host उसे स्वीकार करे; लेकिन key filename या public-key comment से access साबित नहीं होता। इसी तरह, timestamp वाले password-change record के पास मिला custom password generator केवल manual analysis का सुराग है: time-seeded non-cryptographic generator में संभावित seed की छोटी window हो सकती है, लेकिन timezone, clock precision, library behavior, और बाद के password changes reconstruction को प्रभावित करते हैं। Candidate credentials को केवल authorized होने पर validate करें; generated candidates को confirmed passwords न मानें।

Container के अंदर service account nominally privileged home directory में पुरानी provisioning script पढ़ सकता है, यदि directory traversable हो और file permissions इसकी अनुमति दें। Script में मौजूद application-admin password, credential exposure का सुराग है—host-root access का नहीं: जाँचें कि script और credential सक्रिय थे या नहीं, value किस account की है, और क्या कोई अलग host account अब भी वही password स्वीकार करता है। Passive enumeration के दौरान secret print किए या host authentication का प्रयास किए बिना file path और access rights दर्ज करें।

यदि readable `.p12` या `.pfx` bundle का password application configuration में exposed हो, तो इसकी जाँच `openssl pkcs12 -info -in bundle.p12 -noout` से करें। यदि bundle में exportable private key हो, तो `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` उस key को बिना encryption के लिखता है। Output file को सुरक्षित रखें और analysis के बाद हटा दें; recovered key का उपयोग केवल उसी service या ciphertext के लिए करें जिससे वह वास्तव में मेल खाती है। केवल bundle होने से यह नहीं माना जा सकता कि उसकी private key किसी दूसरी application के लिए उपयोगी है।
