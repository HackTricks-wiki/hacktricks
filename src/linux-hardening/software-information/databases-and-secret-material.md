# Бази даних і секретні дані на Linux-хостах

{{#include ../../banners/hacktricks-training.md}}

Облікові дані баз даних і застосунків часто зберігаються поруч із сервісом, якому вони потрібні. Перш ніж перевіряти, чи може обліковий запис читати дані або виконувати привілейовану операцію, визначте процес, локальний сокет або порт, конфігурацію та файл з обліковими даними.

## Пошук локальних сервісів даних і облікових даних

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Перевіряйте доступні для читання конфігурації застосунків, файли розгортання, файли середовища служб і резервні копії на наявність рядків підключення або ключів. Unix-сокет процесу БД може мати інші правила доступу, ніж його TCP-слухач. Дозволи бази даних відрізняються від дозволів ОС: відновлений пароль БД надає лише ролі, призначені цьому обліковому запису БД, якщо не продемонстровано інший шлях. У PostgreSQL політики row-level security можуть приховувати записи від однієї ролі, тоді як роль із правами керування політиками може змінити цей доступ; розрізняйте доступ до даних і адміністрування політик. Скористайтеся посібниками для конкретних служб: [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) і [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Доступний для читання скрипт автоматизації в домашньому каталозі іншого облікового запису може містити облікові дані, навіть якщо назва файлу не згадує паролі. Наприклад, скрипт Python може запустити `su` і передати рядок пароля у відповідь на запит пароля за допомогою [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html); [`su`](https://man7.org/linux/man-pages/man1/su.1.html) усе одно застосовує власну політику автентифікації. Переконайтеся, що поточний користувач може пройти через каталог і прочитати саме цей скрипт, що цей рядок призначений як пароль цільового облікового запису, а облікові дані досі чинні, перш ніж вважати це переходом до іншого облікового запису. Скрипту не обов’язково успішно запускатися, щоб його текст розкрив секрет. Пасивний вивід має показувати шлях і дозволи, не виводячи значення та не намагаючись увійти.

Доступна для читання база даних SQLite застосунку може містити імена користувачів і хеші паролів, навіть якщо жодна служба бази даних не слухає з’єднання. Перш ніж розглядати хеш як підставу для офлайн-аудиту, перевірте схему й дозволи на файл. Відновлений пароль застосунку надає доступ до облікового запису ОС або локальної адмін-панелі лише за умови окремого підтвердження повторного використання пароля; формат хешу або збіг імені користувача цього не доводять.

Apache OFBiz може використовувати вбудовану базу даних Derby у `runtime/data/derby/<database>/`. Файл `service.properties` позначає каталог бази даних; у сусідньому каталозі `seg0` зберігаються файли таблиць. Перш ніж переглядати записи застосунку, як-от `USER_LOGIN`, перевірте дозволи для всього каталогу бази даних. Доступний для читання файл-маркер не доводить, що таблиці доступні для читання, що пароль можна відновити або що облікові дані застосунку працюють для облікового запису Unix. Не додавайте вміст баз даних і хеші паролів до звичайного виводу під час переліку. Див. [документацію Derby про каталоги баз даних](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) та [API входу OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

TeamCity зберігає дані сервера в каталозі даних, який можна налаштувати (часто `.BuildServer`). Перевірте дозволи для `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*`, якщо використовується вбудована HSQLDB, і `backup/TeamCity_Backup_*.zip`. Завантажені SSH-ключі та інші захищені налаштування можуть бути зашифровані, тож сам факт доступності шляху для читання не доводить, що приватний ключ придатний до використання. База даних або резервна копія можуть містити облікові записи користувачів застосунку та хеші паролів; їх використання для облікового запису Unix потребує окремих доказів повторного використання пароля. Під час переліку фіксуйте шляхи й права доступу, а не виводьте ключі, хеші чи рядки бази даних. Див. документацію TeamCity про [каталог даних](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [SSH-ключі](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) і [резервне копіювання](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Сервер резервного копіювання Duplicati зберігає конфігурацію у `Duplicati-server.sqlite`. Його каталог даних може бути в домашньому каталозі облікового запису служби, у `/var/lib/Duplicati` або у томі контейнера; параметр `--server-datafolder` чи змінна `DUPLICATI_HOME` можуть змінити його розташування. Доступна для читання база даних є цінною зачіпкою, оскільки може містити облікові дані підключення та матеріали для підписування сервера, але новіші інсталяції можуть шифрувати конфіденційні поля й обмежувати доступ до каталогу. Зіставте дозволи з фактичним обліковим записом сервера та доступом до автентифікованого інтерфейсу чи ServerUtil. Якщо сервер запущений від root, а до його контейнера змонтовано хостовий `/`, авторизоване відновлення резервної копії та хуки завдань можуть перетинати межу файлової системи хоста; сам по собі слухач loopback або назва файлу бази даних не доводять наявності контролю. Не слід припускати, що поведінка входу на основі nonce зі старих випусків характерна для поточних версій, які використовують іншу [модель автентифікації](https://docs.duplicati.com/technical-details/server-authentication-model). Докладніше про особливості конкретних версій див. документацію Duplicati щодо [бази даних сервера](https://docs.duplicati.com/database-and-storage/the-server-database) і [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil).

У PostgreSQL перевірте `pg_policies` і `pg_class.relrowsecurity`, щоб відрізнити відфільтрований запит від відсутніх записів. Змінювати або вимикати політику можна лише за наявності відповідних прав власника таблиці чи адміністративних привілеїв. Окремий злитий обліковий запис обслуговування може мати такі привілеї, навіть якщо обліковий запис застосунку їх не має. Неавтентифікований слухач Redis — це окрема знахідка: перш ніж вважати його джерелом секретів, перевірте, чи прив’язаний він лише до loopback і чи обмежують поточне з’єднання захищений режим або ACL.

## Перевірка сховищ ключів і токенів

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Приватний SSH-ключ, сокет агента, кеш Kerberos, сховище ключів GPG або пакет PKCS#12 корисні лише тоді, коли поточний користувач має до них доступ, а потрібна парольна фраза чи політика дозволяє їх використовувати. Спочатку перевірте власника та дозволи. На сторінках [users and sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) і [post-exploitation](../post-exploitation/README.md) описано відповідні шляхи доступу. Історія Git, старі резервні копії та історія командної оболонки також можуть зберігати секрети після очищення поточної конфігурації. Каталог `.git`, доступний для читання, може зберігати видалений вихідний код і раніше закомічені облікові дані, навіть якщо робоче дерево порожнє; перевірте доступ і перегляньте історію вручну, а не вивантажуйте її під час автоматизованого збору даних.

Доступний для читання образ завантаження в `/boot` — ще одна можлива архівна знахідка. [Сценарії завантаження initramfs і скопійовані допоміжні програми](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) можуть містити спеціальну логіку, яка передає ключ до [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Перевірте дозволи доступу до образу та перегляньте лише відповідний сценарій завантаження й допоміжну програму в авторизованій офлайн-копії. Вбудована або похідна парольна фраза для розблокування диска не є автоматично паролем облікового запису Unix: перш ніж вважати це переходом до облікового запису, перевірте вхідні дані допоміжної програми, фактичний шлях завантаження та повторне використання інших облікових даних. Під час звичайного збору даних не слід розпаковувати образ, виконувати його допоміжні програми або виводити потенційні ключі.

CLI Vault [зазвичай кешує токен автентифікації у `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), хоча спеціальна програма-помічник для токенів може зберігати його в іншому місці. Доступний для читання шлях — лише можлива знахідка облікових даних: перш ніж робити висновки про доступ до будь-якого механізму секретів, перевірте чинність токена та його політику. Для [одноразових паролів Vault SSH](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords) токен має бути авторизований на випуск облікових даних для ролі, в якій користувач і CIDR охоплюють потрібний обліковий запис і хост; на цьому хості також має бути налаштований допоміжний засіб перевірки SSH і дозволений вхід. Назва ролі `root` або сам файл токена не доводять наявність доступу root. Під час пасивного збору даних слід указувати шлях до файлу, не читаючи токен і не запитуючи OTP.

[У KeePass 1.x використовується `.kdb`, а в KeePass 2.x — `.kdbx`](https://keepass.info/help/v2/version.html). Розглядайте файл із відповідною назвою як можливе зашифроване сховище, оскільки інші продукти також можуть використовувати суфікс `.kdb`. Доступне для читання сховище не розкриває своїх записів без потрібного майстер-пароля або ключового файлу; SSH-ключ, збережений як вкладення, є окремою зачіпкою, доступ до хоста через яку потрібно перевірити. [KeePass приймає довільні файли, зокрема зображення, як ключові файли](https://keepass.info/help/base/keys.html), але файл поблизу — лише кандидат, доки незалежно не підтверджено його роль, наявність усіх необхідних компонентів майстер-ключа та вхід до облікового запису з вищими привілеями.

Архів підтримки може містити і сховище KeePass, і дамп пам’яті процесу. Для [KeePass 2.x до версії 2.54 включно, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) означає, що майстер-пароль потенційно можна відновити з відповідного дампа; самого зашифрованого сховища або не пов’язаного з ним дампа недостатньо. Під час звичайного збору даних вручну перевіряйте вміст архіву та права доступу, не виконуючи масового розпакування й не виводячи секрети. Приватні ключі PuTTY можуть бути файлами `.ppk` або текстом `PuTTY-User-Key-File` у записі сховища; окремо перевірте призначений обліковий запис для ключа, його шифрування та хости, які його приймають.

Доступний для читання HTTP-архів `.har` може зберігати запити й відповіді браузера, зокрема заголовки автентифікації, cookie та поля форм. Він може бути збережений безпосередньо або у вкладенні до звернення в службу підтримки. Спочатку перевірте власника та доступ, а потім перегляньте лише відповідні записи; сама назва файлу не доводить наявність придатних для повторного використання облікових даних. Під час автоматизованого збору даних слід указувати шлях до архіву, не виводячи перехоплені значення. У [документації Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) описано параметр експорту конфіденційних даних.

Для зашифрованих резервних копій баз даних перед висновками зіставте доступний для читання архів, доступні приватні ключі та вимоги до парольної фрази. Якщо це авторизовано, відновлення парольної фрази захищеного ключа та перегляд розшифрованих даних резервної копії — це окремі ручні дії. Облікові дані `root` бази даних не є обліковими даними Unix `root`; повторне використання пароля між цими обліковими записами потрібно окремо й авторизовано перевірити. Межі довіри файлової системи у вебзастосунках також можуть відкрити доступ до облікового запису, якому належать ці матеріали; див. [перевірку файлового кешу Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

root контейнера й root хоста — це різні ідентичності. Приватний SSH-ключ, доступний для читання лише після отримання root усередині контейнера, може автентифікуватися на обліковий запис хоста, якщо хост його приймає, але назва файла чи коментар у відкритому ключі цього не доводять. Так само спеціальна програма генерації паролів, знайдена поруч із записом про зміну пароля з часовою міткою, є лише зачіпкою для ручного аналізу: не криптографічний генератор із початковим значенням, похідним від часу, може мати невелике вікно потенційних початкових значень, але на відновлення впливають часовий пояс, точність годинника, поведінка бібліотеки та подальші зміни пароля. Перевіряйте потенційні облікові дані лише за наявності авторизації; не вважайте згенеровані варіанти підтвердженими паролями.

Обліковий запис служби всередині контейнера може читати старий сценарій ініціалізації в номінально привілейованому домашньому каталозі, якщо каталог доступний для проходу, а дозволи файла це допускають. Вбудований пароль адміністратора застосунку вказує на витік облікових даних, а не на доступ root до хоста: перевірте, чи були сценарій і облікові дані чинними, якому обліковому запису відповідає це значення та чи досі приймає окремий обліковий запис хоста той самий пароль. Під час пасивного збору даних фіксуйте шлях до файла та права доступу, не виводячи секрет і не намагаючись автентифікуватися на хості.

Якщо доступний для читання пакет `.p12` або `.pfx` має пароль, указаний у конфігурації застосунку, перегляньте його за допомогою `openssl pkcs12 -info -in bundle.p12 -noout`. Якщо пакет містить експортований приватний ключ, команда `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` записує цей ключ без шифрування. Захистіть вихідний файл і видаліть його після аналізу; використовуйте отриманий ключ лише для служби або шифротексту, з якими він справді пов’язаний. Сам факт наявності пакета не означає, що його приватний ключ буде корисним для іншого застосунку.
