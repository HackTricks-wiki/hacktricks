# Linux Hosts पर डेटाबेस और सीक्रेट सामग्री

{{#include ../../banners/hacktricks-training.md}}

डेटाबेस और एप्लिकेशन क्रेडेंशियल्स अक्सर उसी सर्विस के पास रखे होते हैं जिसका वे समर्थन करते हैं। यह जाँचने से पहले कि कोई अकाउंट डेटा पढ़ सकता है या विशेषाधिकार-युक्त ऑपरेशन कर सकता है, प्रोसेस, लोकल सॉकेट या पोर्ट, कॉन्फ़िगरेशन और क्रेडेंशियल फ़ाइल का पता लगाएँ।

## लोकल डेटा सर्विस और क्रेडेंशियल्स का पता लगाएँ

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Readable application configs, deployment files, service environment files और backups में connection strings या keys देखें। DB process के Unix socket के access rules उसके TCP listener से अलग हो सकते हैं। Database permissions, OS permissions से अलग होती हैं: recovered DB password केवल उन्हीं roles तक access देता है जो उस DB account को assigned हैं, जब तक कि कोई दूसरा रास्ता साबित न हो। PostgreSQL में row-level security policies किसी role से records छिपा सकती हैं, जबकि policy-management rights वाला role उस view को बदल सकता है; data access और policy administration में अंतर करें। [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md), और [Redis](../../network-services-pentesting/6379-pentesting-redis.md) के लिए service-specific guides देखें।

किसी दूसरे account के home में readable automation script में credential हो सकता है, भले ही उसके filename में password का ज़िक्र न हो। उदाहरण के लिए, Python script `su` चला सकती है और [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html) के ज़रिए उसके password prompt में literal value भेज सकती है; [`su`](https://man7.org/linux/man-pages/man1/su.1.html) फिर भी अपनी authentication policy लागू करता है। इसे account transition मानने से पहले पुष्टि करें कि current user उस directory तक पहुँच सकता है और exact script पढ़ सकता है, literal target account के password के रूप में intended है, और credential अब भी valid है। Secret उजागर करने के लिए script का सफलतापूर्वक चलना ज़रूरी नहीं है। Passive output में value दिखाए बिना या login आज़माए बिना path और permissions दिखने चाहिए।

किसी readable SQLite application database में user names और password hashes हो सकते हैं, भले ही कोई database service listen न कर रही हो। किसी hash को offline audit lead मानने से पहले उसका schema और file permissions जाँचें। Recovered application password से OS-account या local-admin-panel access तभी मिलता है, जब password reuse की अलग से पुष्टि हो; hash format या matching user name, reuse का प्रमाण नहीं है।

Apache OFBiz, `runtime/data/derby/<database>/` के अंतर्गत embedded Derby database इस्तेमाल कर सकता है। Derby की `service.properties` file database directory की पहचान करती है; उसके साथ वाली `seg0` directory में table files होती हैं। `USER_LOGIN` जैसे application records देखने से पहले पूरे database directory की permissions जाँचें। Readable marker से यह साबित नहीं होता कि tables भी readable हैं, password recover किया जा सकता है, या application credential किसी Unix account के लिए काम करता है। Routine enumeration output में database contents और password hashes शामिल न करें। [Derby database-directory documentation](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) और [OFBiz login API](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html) देखें।

TeamCity अपना server data configurable data directory में रखता है (अक्सर `.BuildServer`)। `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, embedded HSQLDB इस्तेमाल होने पर `system/buildserver.*`, और `backup/TeamCity_Backup_*.zip` की permissions जाँचें। Uploaded SSH keys और अन्य secure settings encrypted हो सकती हैं, इसलिए केवल path का readable होना usable private key होने का प्रमाण नहीं है। Database या backup में application users और password hashes हो सकते हैं; उन्हें Unix account के लिए इस्तेमाल करने हेतु password reuse का अलग प्रमाण चाहिए। Enumeration के दौरान keys, hashes या database rows दिखाने के बजाय paths और access rights दर्ज करें। TeamCity की [data-directory](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [SSH-key](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html), और [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html) documentation देखें।

Duplicati backup server अपनी configuration `Duplicati-server.sqlite` में रखता है। इसका data directory service account के home, `/var/lib/Duplicati`, या container volume में हो सकता है; `--server-datafolder` या `DUPLICATI_HOME` इसे बदल सकते हैं। Readable database एक high-value lead है, क्योंकि इसमें connection credentials और server signing material हो सकते हैं, लेकिन नए installations में sensitive fields encrypted हो सकते हैं और directory access restricted हो सकता है। इसकी permissions का मिलान actual server account और किसी authenticated UI या ServerUtil access से करें। अगर वह server root के रूप में चलता है और उसके container में host `/` mounted है, तो authorized backup restore और job hooks host filesystem boundary पार कर सकते हैं; केवल loopback listener या database filename से control साबित नहीं होता। पुराने releases का nonce-based login behavior current versions के लिए नहीं मानना चाहिए, क्योंकि वे अलग [authentication model](https://docs.duplicati.com/technical-details/server-authentication-model) इस्तेमाल करते हैं। Version-specific विवरण के लिए Duplicati की [server database](https://docs.duplicati.com/database-and-storage/the-server-database) और [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) documentation देखें।

PostgreSQL में `pg_policies` और `pg_class.relrowsecurity` देखें, ताकि filtered query और missing records में अंतर किया जा सके। किसी policy को बदलने या disable करने के लिए उपयुक्त table ownership या administrative privileges चाहिए। अलग से leak हुआ maintenance account ये privileges रख सकता है, भले ही application account के पास न हों। Unauthenticated Redis listener एक अलग finding है: इसे secret source मानने से पहले जाँचें कि वह केवल loopback पर bind है या नहीं, और protected mode या ACLs current connection को restrict करते हैं या नहीं।

## Review key and token stores

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

एक SSH private key, agent socket, Kerberos cache, GPG keyring या PKCS#12 bundle तभी उपयोगी है, जब मौजूदा user उसे access कर सके और कोई भी आवश्यक passphrase या policy उसके उपयोग की अनुमति दे। पहले ownership और permissions जाँचें। [users and sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) और [post-exploitation](../post-exploitation/README.md) पेज संबंधित access paths समझाते हैं। Live config साफ़ किए जाने के बाद भी Git history, पुराने backups और shell history में secrets रह सकते हैं। Readable `.git` directory में deleted source और पहले commit किए गए credentials मौजूद रह सकते हैं, भले ही working tree खाली हो; automated enumeration के दौरान उसे dump करने के बजाय access जाँचें और history की manually समीक्षा करें।

`/boot` में readable boot image भी archive का एक संभावित स्रोत है। [Initramfs boot scripts और copied helpers](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) में custom logic हो सकता है, जो [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html) को key देता है। Image की access permissions जाँचें और authorized offline copy में केवल संबंधित boot script और helper की समीक्षा करें। Embedded या derived disk-unlock passphrase अपने-आप Unix account password नहीं होता: इसे account transition मानने से पहले helper के inputs, वास्तविक boot path और अलग से credential reuse की पुष्टि करें। Routine enumeration में image को unpack न करें, उसके helpers execute न करें और संभावित keys print न करें।

Vault CLI [आमतौर पर अपना authentication token `~/.vault-token` में cache करता है](https://developer.hashicorp.com/vault/docs/commands/token-helper), हालाँकि custom token helper उसे कहीं और store कर सकता है। Readable path केवल credential का एक संभावित संकेत है: किसी भी secret engine तक access का अनुमान लगाने से पहले token की validity और policy verify करें। [Vault SSH one-time passwords](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords) के लिए token को ऐसी role के credentials जारी करने की अनुमति होनी चाहिए, जिसके user और CIDR में लक्षित account और host शामिल हों; उस host पर SSH verification helper भी configured होना चाहिए और login स्वीकार होना चाहिए। `root` नाम वाली role या केवल token file, root access साबित नहीं करती। Passive enumeration में token पढ़े या OTP माँगे बिना file path report करें।

[KeePass 1.x में `.kdb` और KeePass 2.x में `.kdbx` का उपयोग होता है](https://keepass.info/help/v2/version.html)। मिलते-जुलते filename को संभावित encrypted vault मानें, क्योंकि अन्य products भी `.kdb` suffix का उपयोग कर सकते हैं। आवश्यक master password या key file के बिना readable vault की entries नहीं देखी जा सकतीं; attachment के रूप में stored SSH key एक अलग संकेत है, जिसकी host access की पुष्टि करनी होगी। [KeePass images समेत मनमानी files को key files के रूप में स्वीकार करता है](https://keepass.info/help/base/keys.html), लेकिन पास की कोई file तब तक केवल एक candidate है, जब तक उसकी भूमिका, सभी आवश्यक master-key components और किसी अधिक privileged account का login स्वतंत्र रूप से confirm न हो जाए।

किसी support archive में KeePass vault और process memory dump, दोनों हो सकते हैं। [KeePass 2.x में 2.54 से पहले, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) के कारण संबंधित dump से master password संभावित रूप से recover किया जा सकता है; केवल encrypted vault या असंबंधित dump पर्याप्त नहीं है। Routine enumeration के दौरान bulk extraction या secrets print किए बिना archive entries और access rights की manually जाँच करें। PuTTY private keys `.ppk` files के रूप में या vault entry में `PuTTY-User-Key-File` text के रूप में मिल सकती हैं; key के intended account, encryption और स्वीकार करने वाले host की अलग-अलग पुष्टि करें।

Readable `.har` HTTP archive में browser requests और responses, जिनमें authentication headers, cookies और form fields शामिल हैं, सुरक्षित रह सकते हैं। इसे सीधे या support attachment के अंदर save किया गया हो सकता है। पहले ownership और access जाँचें, फिर केवल संबंधित entries देखें; केवल filename से reusable credential साबित नहीं होता। Automated enumeration में captured values print करने के बजाय archive path list करें। [Microsoft Edge documentation](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) में sensitive-data export option समझाया गया है।

Encrypted database backups के लिए निष्कर्ष निकालने से पहले readable archive, accessible private-key material और किसी भी passphrase की आवश्यकता का आपस में मिलान करें। जहाँ authorized हो, protected key का passphrase recover करना और decrypted backup data की जाँच करना अलग-अलग manual steps हैं। Database का `root` credential, Unix का `root` credential नहीं है; इन accounts में password reuse को अलग से और authorized तरीके से validate करना होगा। Web applications में filesystem trust boundaries से उस account का पता भी चल सकता है जिसके पास ये materials हैं; [Django file-cache review](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce) देखें।

Container root और host root अलग identities हैं। Container के अंदर root बनने के बाद ही readable होने वाली private SSH key, host account से authenticate कर सकती है—यदि host उसे स्वीकार करता हो—लेकिन key filename या public-key comment उस access को साबित नहीं करता। इसी तरह, timestamp वाले password-change record के पास मिला custom password generator केवल manual analysis का एक संकेत है: time-seeded non-cryptographic generator में संभावित seed का दायरा छोटा हो सकता है, लेकिन timezone, clock precision, library behavior और बाद में हुए password changes पुनर्निर्माण को प्रभावित करते हैं। Candidate credentials को केवल authorized होने पर validate करें; generated candidates को confirmed passwords न मानें।

Container के अंदर कोई service account पुराने provisioning script को पढ़ने में सक्षम हो सकता है, भले ही script nominally privileged home directory में हो—यदि directory traversable हो और file permissions इसकी अनुमति दें। Embedded application-admin password, credential exposure का संकेत है, host-root access का नहीं: जाँचें कि script और credential active थे या नहीं, value किस account की है और क्या कोई अलग host account अब भी वही password स्वीकार करता है। Passive enumeration के दौरान secret print किए या host authentication का प्रयास किए बिना file path और access rights दर्ज करें।

यदि किसी readable `.p12` या `.pfx` bundle का password application configuration में exposed हो, तो `openssl pkcs12 -info -in bundle.p12 -noout` से उसकी जाँच करें। यदि bundle में exportable private key हो, तो `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` उस key को बिना encryption के लिखता है। Output file को सुरक्षित रखें और analysis के बाद हटा दें; recovered key का उपयोग केवल उसी service या ciphertext के लिए करें जिससे वह वास्तव में मेल खाती हो। केवल bundle होने से यह साबित नहीं होता कि उसकी private key किसी अलग application के लिए उपयोगी है।
