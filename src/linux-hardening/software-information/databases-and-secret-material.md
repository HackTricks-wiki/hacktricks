# Bases de données et secrets sur les hôtes Linux

{{#include ../../banners/hacktricks-training.md}}

Les identifiants des bases de données et des applications se trouvent souvent à proximité du service qu’ils prennent en charge. Repérez le processus, le socket ou le port local, la configuration et le fichier d’identifiants avant de vérifier si un compte peut lire des données ou exécuter une opération privilégiée.

## Localiser les services de données locaux et les identifiants

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Inspectez les configurations d’application lisibles, les fichiers de déploiement, les fichiers d’environnement des services et les sauvegardes à la recherche de chaînes de connexion ou de clés. Un socket Unix de processus DB peut avoir des règles d’accès différentes de celles de son écouteur TCP. Les permissions de base de données diffèrent des permissions du système d’exploitation : un mot de passe DB récupéré ne donne accès qu’aux rôles attribués à ce compte DB, sauf si une autre voie est démontrée. Dans PostgreSQL, les politiques de sécurité au niveau des lignes peuvent masquer des enregistrements à un rôle, tandis qu’un rôle ayant des droits de gestion des politiques peut modifier cette visibilité ; distinguez l’accès aux données de l’administration des politiques. Consultez les guides spécifiques aux services [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) et [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Un script d’automatisation lisible dans le répertoire personnel d’un autre compte peut intégrer un identifiant, même si son nom de fichier ne mentionne pas les mots de passe. Par exemple, un script Python peut lancer `su` et transmettre une valeur littérale à son invite de mot de passe avec [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html) ; [`su`](https://man7.org/linux/man-pages/man1/su.1.html) applique toujours sa politique d’authentification. Vérifiez que l’utilisateur courant peut traverser le répertoire et lire le script concerné, que la valeur littérale est bien censée être le mot de passe du compte cible et que l’identifiant est toujours valide avant de considérer cela comme un changement de compte. Le script n’a pas besoin de s’exécuter correctement pour que son texte révèle un secret. La sortie passive doit indiquer le chemin et les permissions sans afficher la valeur ni tenter de connexion.

Une base de données applicative SQLite lisible peut contenir des noms d’utilisateur et des hachages de mots de passe sans qu’aucun service de base de données n’écoute. Examinez son schéma et les permissions du fichier avant de considérer un hachage comme une piste d’audit hors ligne. Un mot de passe applicatif récupéré ne donne accès à un compte du système d’exploitation ou à un panneau d’administration local que si sa réutilisation est confirmée séparément ; le format du hachage ou la correspondance du nom d’utilisateur ne prouve pas cette réutilisation.

Apache OFBiz peut utiliser une base de données Derby intégrée dans `runtime/data/derby/<database>/`. Le fichier `service.properties` de Derby indique le répertoire de la base de données ; son répertoire frère `seg0` contient les fichiers des tables. Vérifiez les permissions de tout le répertoire de la base de données avant d’examiner des enregistrements applicatifs tels que `USER_LOGIN`. Un marqueur lisible ne prouve ni que les tables sont lisibles, ni qu’un mot de passe peut être récupéré, ni qu’un identifiant applicatif fonctionne pour un compte Unix. N’incluez pas le contenu des bases de données ni les hachages de mots de passe dans les sorties d’énumération habituelles. Consultez la [documentation Derby sur les répertoires de bases de données](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) et l’[API de connexion OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

TeamCity stocke les données de son serveur dans un répertoire configurable (souvent `.BuildServer`). Vérifiez les permissions de `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` lorsque HSQLDB intégrée est utilisée, et `backup/TeamCity_Backup_*.zip`. Les clés SSH téléversées et d’autres paramètres sécurisés peuvent être chiffrés ; un chemin lisible ne prouve donc pas à lui seul qu’une clé privée est utilisable. La base de données ou la sauvegarde peut contenir des utilisateurs applicatifs et des hachages de mots de passe ; leur utilisation pour un compte Unix nécessite des preuves distinctes de réutilisation du mot de passe. Pendant l’énumération, consignez les chemins et les droits d’accès au lieu d’afficher les clés, les hachages ou les lignes de la base de données. Consultez la documentation TeamCity sur le [répertoire de données](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), les [clés SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) et les [sauvegardes](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Le serveur de sauvegarde Duplicati stocke sa configuration dans `Duplicati-server.sqlite`. Son répertoire de données peut se trouver dans le répertoire personnel du compte de service, dans `/var/lib/Duplicati` ou dans un volume de conteneur ; `--server-datafolder` ou `DUPLICATI_HOME` peut le modifier. Une base de données lisible constitue une piste de grande valeur, car elle peut contenir des identifiants de connexion et du matériel de signature du serveur, mais les installations récentes peuvent chiffrer les champs sensibles et restreindre l’accès au répertoire. Mettez ses permissions en corrélation avec le compte réel du serveur et tout accès authentifié à l’interface utilisateur ou à ServerUtil. Si ce serveur s’exécute en tant que root avec `/` de l’hôte monté dans son conteneur, les restaurations de sauvegarde autorisées et les hooks de tâche peuvent franchir la limite du système de fichiers de l’hôte ; un écouteur sur loopback ou un nom de fichier de base de données ne prouve pas à lui seul un contrôle. Il ne faut pas supposer que le comportement de connexion basé sur un nonce des anciennes versions s’applique aux versions actuelles, qui utilisent un [modèle d’authentification](https://docs.duplicati.com/technical-details/server-authentication-model) différent. Consultez la documentation Duplicati sur la [base de données du serveur](https://docs.duplicati.com/database-and-storage/the-server-database) et [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) pour les détails propres à chaque version.

Pour PostgreSQL, examinez `pg_policies` et `pg_class.relrowsecurity` afin de distinguer une requête filtrée d’enregistrements manquants. La modification ou la désactivation d’une politique nécessite les privilèges appropriés de propriétaire de table ou d’administration. Un compte de maintenance divulgué séparément peut disposer de ces privilèges même si ce n’est pas le cas du compte applicatif. Un écouteur Redis sans authentification constitue un autre constat distinct : vérifiez s’il est lié uniquement à loopback et si le mode protégé ou les ACL restreignent la connexion actuelle avant de le considérer comme une source de secrets.

## Examiner les magasins de clés et de jetons

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Une clé privée SSH, un socket d’agent, un cache Kerberos, un trousseau GPG ou un bundle PKCS#12 ne sont utiles que si l’utilisateur actuel peut y accéder et si toute phrase secrète ou règle requise autorise leur utilisation. Commencez par vérifier la propriété et les permissions. Les pages sur les [utilisateurs et les sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) et la [post-exploitation](../post-exploitation/README.md) expliquent les voies d’accès correspondantes. L’historique Git, les anciennes sauvegardes et l’historique du shell peuvent également conserver des secrets après le nettoyage d’une configuration active. Un répertoire `.git` lisible peut contenir des sources supprimées et d’anciens identifiants validés, même si l’arbre de travail est vide ; vérifiez les accès et examinez l’historique manuellement plutôt que de le vider lors d’une énumération automatisée.

Une image d’amorçage lisible dans `/boot` est une autre piste d’archive. Les [scripts d’amorçage initramfs et les helpers copiés](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) peuvent inclure une logique personnalisée qui fournit une clé à [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Vérifiez les permissions d’accès à l’image et examinez uniquement le script d’amorçage et le helper pertinents dans une copie hors ligne autorisée. Une phrase secrète de déverrouillage de disque intégrée ou dérivée n’est pas automatiquement le mot de passe d’un compte Unix : confirmez les entrées du helper, le chemin d’amorçage réellement utilisé et la réutilisation distincte des identifiants avant d’y voir une transition de compte. L’énumération courante ne doit ni décompresser l’image, ni exécuter ses helpers, ni afficher des clés potentielles.

La CLI Vault [met normalement en cache son jeton d’authentification dans `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), bien qu’un helper de jeton personnalisé puisse le stocker ailleurs. Un chemin lisible n’est qu’une piste d’identifiant : vérifiez la validité du jeton et sa policy avant d’en déduire un accès à un moteur de secrets. Pour les [mots de passe à usage unique Vault SSH](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), le jeton doit être autorisé à émettre des identifiants pour un rôle dont l’utilisateur et le CIDR incluent le compte et l’hôte visés ; cet hôte doit également avoir le helper de vérification SSH configuré et accepter la connexion. Un rôle nommé `root` ou la présence d’un fichier de jeton ne prouvent pas un accès root. L’énumération passive doit indiquer le chemin du fichier sans lire le jeton ni demander d’OTP.

[KeePass 1.x utilise `.kdb`, tandis que KeePass 2.x utilise `.kdbx`](https://keepass.info/help/v2/version.html). Considérez un nom de fichier correspondant comme un coffre potentiellement chiffré, car d’autres produits peuvent utiliser le suffixe `.kdb`. Un coffre lisible ne révèle pas ses entrées sans le mot de passe principal ou le fichier de clé requis ; une clé SSH stockée en pièce jointe constitue une piste distincte dont l’accès à l’hôte doit être validé. [KeePass accepte des fichiers arbitraires, y compris des images, comme fichiers de clé](https://keepass.info/help/base/keys.html), mais un fichier à proximité n’est qu’un candidat tant que son rôle, tous les composants requis de la clé principale et toute connexion à un compte de privilèges supérieurs ne sont pas confirmés indépendamment.

Une archive de support peut contenir à la fois un coffre KeePass et un dump de mémoire de processus. Pour [KeePass 2.x antérieur à la version 2.54, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) rend le mot de passe principal potentiellement récupérable à partir d’un dump correspondant ; un coffre chiffré ou un dump sans lien ne suffit pas. Examinez manuellement le contenu de l’archive et les droits d’accès, sans extraction en masse ni affichage de secrets lors de l’énumération courante. Les clés privées PuTTY peuvent apparaître sous forme de fichiers `.ppk` ou de texte `PuTTY-User-Key-File` dans une entrée de coffre ; vérifiez séparément le compte visé par la clé, son chiffrement et les hôtes qui l’acceptent.

Une archive HTTP `.har` lisible peut conserver les requêtes et réponses du navigateur, notamment les en-têtes d’authentification, les cookies et les champs de formulaire. Elle peut être enregistrée directement ou dans une pièce jointe de support. Vérifiez d’abord la propriété et les accès, puis examinez uniquement les entrées pertinentes ; le nom du fichier ne prouve pas à lui seul qu’il contient un identifiant réutilisable. L’énumération automatisée doit lister le chemin de l’archive sans afficher les valeurs capturées. La [documentation de Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) explique l’option d’exportation des données sensibles.

Pour les sauvegardes de bases de données chiffrées, recoupez l’archive lisible, le matériel de clé privée accessible et toute exigence de phrase secrète avant de tirer une conclusion. Lorsque cela est autorisé, la récupération de la phrase secrète d’une clé protégée et l’examen des données de sauvegarde déchiffrées sont deux étapes manuelles distinctes. Un identifiant `root` de base de données n’est pas un identifiant `root` Unix ; toute réutilisation de mot de passe entre ces comptes nécessite une validation distincte et autorisée. Les limites de confiance du système de fichiers dans les applications web peuvent également exposer le compte propriétaire de ces éléments ; consultez l’[examen du cache de fichiers Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Le root d’un conteneur et le root de l’hôte sont deux identités distinctes. Une clé privée lisible uniquement après être devenu root dans un conteneur peut permettre de s’authentifier auprès d’un compte hôte si celui-ci l’accepte, mais le nom du fichier ou le commentaire de la clé publique ne prouve pas cet accès. De même, un générateur de mots de passe personnalisé trouvé à côté d’un enregistrement horodaté de changement de mot de passe n’est qu’une piste d’analyse manuelle : un générateur non cryptographique initialisé à partir de l’heure peut avoir une petite fenêtre de seeds candidates, mais le fuseau horaire, la précision de l’horloge, le comportement de la bibliothèque et les changements de mot de passe ultérieurs influent sur la reconstitution. Ne validez des identifiants candidats que si cela est autorisé ; ne considérez pas les candidats générés comme des mots de passe confirmés.

Un compte de service dans un conteneur peut être en mesure de lire un ancien script de provisionnement situé dans un répertoire personnel apparemment privilégié, si le répertoire est traversable et que les permissions du fichier le permettent. Un mot de passe d’administrateur d’application intégré est une piste d’exposition d’identifiant, pas un accès root à l’hôte : vérifiez si le script et l’identifiant étaient actifs, à quel compte la valeur appartient et si un compte hôte distinct accepte toujours le même mot de passe. Lors de l’énumération passive, consignez le chemin du fichier et les droits d’accès sans afficher le secret ni tenter de vous authentifier auprès de l’hôte.

Si un bundle `.p12` ou `.pfx` lisible a un mot de passe exposé dans la configuration de l’application, examinez-le avec `openssl pkcs12 -info -in bundle.p12 -noout`. Si le bundle contient une clé privée exportable, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` écrit cette clé sans chiffrement. Protégez le fichier de sortie et supprimez-le après l’analyse ; n’utilisez la clé récupérée que pour le service ou le texte chiffré auquel elle correspond réellement. Un bundle seul n’implique pas que sa clé privée soit utile pour une autre application.
