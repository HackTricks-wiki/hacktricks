# Bases de données et éléments secrets sur les hôtes Linux

{{#include ../../banners/hacktricks-training.md}}

Les identifiants des bases de données et des applications se trouvent souvent à proximité du service qu’ils prennent en charge. Repérez le processus, le socket ou le port local, la configuration et le fichier d’identifiants avant de vérifier si un compte peut lire des données ou exécuter une opération privilégiée.

## Repérer les services de données locaux et les identifiants

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Inspectez les fichiers de configuration lisibles des applications, les fichiers de déploiement, les fichiers d’environnement des services et les sauvegardes à la recherche de chaînes de connexion ou de clés. Le socket Unix d’un processus DB peut avoir des règles d’accès différentes de celles de son écouteur TCP. Les permissions de la base de données diffèrent des permissions du système d’exploitation : un mot de passe DB récupéré ne donne accès qu’aux rôles attribués à ce compte DB, sauf si une autre voie est démontrée. Dans PostgreSQL, les politiques de sécurité au niveau des lignes peuvent masquer des enregistrements à un rôle, tandis qu’un rôle disposant des droits de gestion des politiques peut modifier cette visibilité ; distinguez l’accès aux données de l’administration des politiques. Consultez les guides propres à chaque service pour [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) et [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Un script d’automatisation lisible dans le répertoire personnel d’un autre compte peut intégrer un identifiant, même si son nom de fichier ne mentionne pas les mots de passe. Par exemple, un script Python peut lancer `su` et transmettre une valeur littérale à son invite de mot de passe avec [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html) ; [`su`](https://man7.org/linux/man-pages/man1/su.1.html) applique toujours sa politique d’authentification. Vérifiez que l’utilisateur actuel peut parcourir le répertoire et lire le script concerné, que la valeur littérale est bien censée être le mot de passe du compte cible et que l’identifiant est toujours valide avant de considérer cela comme un changement de compte. Le script n’a pas besoin de s’exécuter correctement pour que son contenu révèle un secret. La sortie passive doit indiquer le chemin et les permissions sans afficher la valeur ni tenter une connexion.

Une base de données SQLite d’application lisible peut contenir des noms d’utilisateur et des hachages de mots de passe sans qu’aucun service de base de données n’écoute. Examinez son schéma et les permissions du fichier avant de considérer un hachage comme une piste d’audit hors ligne. Un mot de passe d’application récupéré ne donne accès à un compte du système d’exploitation ou à un panneau d’administration local que si sa réutilisation est confirmée séparément ; le format du hachage ou la correspondance du nom d’utilisateur ne prouvent pas cette réutilisation.

Apache OFBiz peut utiliser une base de données Derby intégrée sous `runtime/data/derby/<database>/`. Le fichier `service.properties` de Derby indique le répertoire de la base de données ; son répertoire frère `seg0` contient les fichiers des tables. Vérifiez les permissions de l’ensemble du répertoire de la base de données avant d’examiner les enregistrements de l’application, tels que `USER_LOGIN`. Un marqueur lisible ne prouve ni que les tables sont lisibles, ni qu’un mot de passe peut être récupéré, ni qu’un identifiant d’application fonctionne pour un compte Unix. N’incluez pas le contenu des bases de données ni les hachages de mots de passe dans les sorties d’énumération courantes. Consultez la [documentation sur les répertoires de base de données Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) et l’[API de connexion OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

TeamCity stocke les données de son serveur dans un répertoire configurable (souvent `.BuildServer`). Vérifiez les permissions de `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` lorsque HSQLDB intégrée est utilisée, et `backup/TeamCity_Backup_*.zip`. Les clés SSH importées et d’autres paramètres sécurisés peuvent être chiffrés ; un chemin lisible ne prouve donc pas qu’une clé privée est utilisable. La base de données ou la sauvegarde peut contenir des utilisateurs de l’application et des hachages de mots de passe ; leur utilisation pour un compte Unix nécessite des preuves distinctes de réutilisation du mot de passe. Lors de l’énumération, consignez les chemins et les droits d’accès au lieu d’afficher les clés, les hachages ou les lignes de la base de données. Consultez la documentation de TeamCity sur le [répertoire de données](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), les [clés SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) et les [sauvegardes](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Le serveur de sauvegarde Duplicati stocke sa configuration dans `Duplicati-server.sqlite`. Son répertoire de données peut se trouver dans le répertoire personnel du compte de service, sous `/var/lib/Duplicati` ou dans un volume de conteneur ; `--server-datafolder` ou `DUPLICATI_HOME` peut en modifier l’emplacement. Une base de données lisible constitue une piste importante, car elle peut contenir des identifiants de connexion et du matériel de signature du serveur, mais les versions récentes peuvent chiffrer les champs sensibles et restreindre l’accès au répertoire. Mettez ses permissions en regard du compte réel du serveur et de tout accès authentifié à l’interface ou à ServerUtil. Si ce serveur s’exécute en tant que root avec `/` de l’hôte monté dans son conteneur, les opérations de restauration de sauvegarde et les hooks de tâche autorisés peuvent franchir la frontière du système de fichiers de l’hôte ; un écouteur sur loopback ou le seul nom du fichier de base de données ne prouve pas qu’un contrôle est possible. Ne présumez pas que le comportement de connexion basé sur un nonce des anciennes versions s’applique aux versions actuelles, qui utilisent un [modèle d’authentification](https://docs.duplicati.com/technical-details/server-authentication-model) différent. Consultez la documentation de Duplicati sur la [base de données du serveur](https://docs.duplicati.com/database-and-storage/the-server-database) et [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) pour les détails propres à chaque version.

Pour PostgreSQL, examinez `pg_policies` et `pg_class.relrowsecurity` afin de distinguer une requête filtrée de l’absence d’enregistrements. La modification ou la désactivation d’une politique nécessite les privilèges appropriés de propriétaire de table ou d’administration. Un compte de maintenance divulgué séparément peut disposer de ces privilèges même si le compte de l’application ne les possède pas. Un écouteur Redis sans authentification constitue une autre constatation distincte : vérifiez s’il est lié uniquement à loopback et si le mode protégé ou les ACL restreignent la connexion actuelle avant de le considérer comme une source de secrets.

## Examiner les magasins de clés et de jetons

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Une clé privée SSH, un socket d’agent, un cache Kerberos, un trousseau de clés GPG ou un bundle PKCS#12 n’est utile que si l’utilisateur courant peut y accéder et si toute phrase de passe ou politique requise en autorise l’utilisation. Vérifiez d’abord le propriétaire et les permissions. Les pages [utilisateurs et sessions](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) et [post-exploitation](../post-exploitation/README.md) expliquent les voies d’accès correspondantes. L’historique Git, les anciennes sauvegardes et l’historique du shell peuvent également conserver des secrets même après le nettoyage d’une configuration active. Un répertoire `.git` lisible peut préserver du code source supprimé et d’anciens identifiants commités, même si l’arborescence de travail est vide ; vérifiez les accès et examinez l’historique manuellement au lieu de le vider lors d’une énumération automatisée.

Une image de démarrage lisible dans `/boot` est une autre piste d’archive. Les [scripts de démarrage initramfs et les utilitaires copiés](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) peuvent inclure une logique personnalisée qui fournit une clé à [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Vérifiez les permissions d’accès à l’image et examinez uniquement le script de démarrage et l’utilitaire pertinents dans une copie hors ligne autorisée. Une phrase de passe de déverrouillage de disque intégrée ou dérivée n’est pas automatiquement le mot de passe d’un compte Unix : confirmez les entrées de l’utilitaire, le chemin de démarrage réel et la réutilisation distincte des identifiants avant de considérer cela comme un accès à un compte. Une énumération de routine ne doit ni décompresser l’image, ni exécuter ses utilitaires, ni afficher des clés candidates.

Le CLI de Vault [met normalement en cache son token d’authentification dans `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), bien qu’un token helper personnalisé puisse le stocker ailleurs. Un chemin lisible n’est qu’une piste d’identifiant : vérifiez la validité du token et sa politique avant de déduire un accès à un moteur de secrets. Pour les [mots de passe à usage unique SSH de Vault](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), le token doit être autorisé à émettre des identifiants pour un rôle dont l’utilisateur et le CIDR incluent le compte et l’hôte visés ; cet hôte doit également avoir configuré le helper de vérification SSH et accepter la connexion. Un rôle nommant `root` ou un simple fichier de token ne prouve pas un accès root. L’énumération passive doit signaler le chemin du fichier sans lire le token ni demander de OTP.

[KeePass 1.x utilise `.kdb`, tandis que KeePass 2.x utilise `.kdbx`](https://keepass.info/help/v2/version.html). Considérez un nom de fichier correspondant comme un coffre chiffré potentiel, car d’autres produits peuvent utiliser le suffixe `.kdb`. Un coffre lisible ne révèle pas ses entrées sans le mot de passe maître ou le fichier de clé requis ; une clé SSH stockée en pièce jointe constitue une piste distincte dont l’accès à l’hôte doit être validé. [KeePass accepte des fichiers arbitraires, y compris des images, comme fichiers de clé](https://keepass.info/help/base/keys.html), mais un fichier à proximité n’est qu’un candidat tant que son rôle, tous les composants requis de la clé maîtresse et toute connexion à un compte aux privilèges supérieurs ne sont pas confirmés indépendamment.

Une archive de support peut contenir à la fois un coffre KeePass et un dump de mémoire de processus. Pour [KeePass 2.x antérieur à la version 2.54, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) rend potentiellement récupérable le mot de passe maître à partir d’un dump correspondant ; un coffre chiffré ou un dump sans rapport ne suffit pas à lui seul. Examinez manuellement le contenu de l’archive et les droits d’accès, sans extraction massive ni affichage de secrets lors d’une énumération de routine. Les clés privées PuTTY peuvent apparaître sous forme de fichiers `.ppk` ou de texte `PuTTY-User-Key-File` dans une entrée de coffre ; confirmez séparément le compte visé par la clé, son chiffrement et l’hôte qui l’accepte.

Une archive HTTP `.har` lisible peut conserver les requêtes et réponses du navigateur, y compris les en-têtes d’authentification, les cookies et les champs de formulaire. Elle peut être enregistrée directement ou dans une pièce jointe de support. Vérifiez d’abord le propriétaire et les accès, puis examinez uniquement les entrées pertinentes ; le nom du fichier ne prouve pas à lui seul qu’un identifiant est réutilisable. L’énumération automatisée doit lister le chemin de l’archive sans afficher les valeurs capturées. La [documentation Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) explique l’option d’exportation des données sensibles.

Pour les sauvegardes de bases de données chiffrées, recoupez l’archive lisible, le matériel de clé privée accessible et toute exigence de phrase de passe avant de tirer une conclusion. Lorsque cela est autorisé, la récupération de la phrase de passe d’une clé protégée et l’examen des données de sauvegarde déchiffrées sont deux étapes manuelles distinctes. Un identifiant `root` de base de données n’est pas un identifiant `root` Unix ; la réutilisation du mot de passe entre ces comptes doit être validée séparément et avec autorisation. Les limites de confiance du système de fichiers dans les applications web peuvent également exposer le compte propriétaire de ces ressources ; consultez la [revue du cache de fichiers Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

root dans un conteneur et root sur l’hôte sont des identités distinctes. Une clé SSH privée lisible uniquement après être devenu root dans un conteneur peut authentifier un compte de l’hôte si celui-ci l’accepte, mais le nom du fichier de clé ou le commentaire de la clé publique ne prouve pas cet accès. De même, un générateur de mots de passe personnalisé trouvé à côté d’un enregistrement horodaté de changement de mot de passe n’est qu’une piste d’analyse manuelle : un générateur non cryptographique initialisé à partir de l’heure peut avoir une fenêtre réduite de graines candidates, mais le fuseau horaire, la précision de l’horloge, le comportement de la bibliothèque et les changements ultérieurs de mot de passe influent sur la reconstruction. Ne validez des identifiants candidats qu’avec autorisation ; ne considérez pas les candidats générés comme des mots de passe confirmés.

Un compte de service dans un conteneur peut être en mesure de lire un ancien script de provisionnement situé dans un répertoire personnel nominalement privilégié, si le répertoire est traversable et si les permissions du fichier le permettent. Un mot de passe d’administrateur d’application intégré est une piste d’exposition d’identifiants, pas un accès root à l’hôte : vérifiez si le script et l’identifiant étaient actifs, à quel compte correspond cette valeur et si un compte distinct de l’hôte accepte toujours le même mot de passe. Lors d’une énumération passive, consignez le chemin du fichier et les droits d’accès sans afficher le secret ni tenter une authentification auprès de l’hôte.

Si un bundle `.p12` ou `.pfx` lisible a un mot de passe exposé dans la configuration de l’application, examinez-le avec `openssl pkcs12 -info -in bundle.p12 -noout`. Si le bundle contient une clé privée exportable, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` écrit cette clé sans chiffrement. Protégez le fichier de sortie et supprimez-le après l’analyse ; n’utilisez la clé récupérée que pour le service ou le texte chiffré auquel elle correspond réellement. Un bundle ne signifie pas à lui seul que sa clé privée est utile pour une autre application.
