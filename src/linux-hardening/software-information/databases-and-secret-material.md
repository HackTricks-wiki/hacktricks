# Bancos de dados e material secreto em hosts Linux

{{#include ../../banners/hacktricks-training.md}}

As credenciais de bancos de dados e aplicativos geralmente ficam ao lado do serviço que elas atendem. Mapeie o processo, o socket ou a porta local, a configuração e o arquivo de credenciais antes de testar se uma conta pode ler dados ou executar uma operação privilegiada.

## Localizar serviços de dados locais e credenciais

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Inspecione configurações legíveis de aplicações, arquivos de implantação, arquivos de ambiente de serviços e backups em busca de strings de conexão ou chaves. O socket Unix de um processo de DB pode ter regras de acesso diferentes das do listener TCP. As permissões do banco de dados diferem das permissões do SO: uma senha de DB recuperada concede apenas as funções atribuídas a essa conta de DB, a menos que outro caminho seja demonstrado. No PostgreSQL, políticas de segurança em nível de linha podem ocultar registros de uma função, enquanto uma função com direitos de gerenciamento de políticas pode alterar essa visualização; diferencie acesso aos dados de administração de políticas. Consulte os guias específicos de cada serviço para [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) e [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Um script de automação legível no diretório home de outra conta pode conter uma credencial, mesmo que o nome do arquivo não mencione senhas. Por exemplo, um script Python pode iniciar `su` e enviar um valor literal ao prompt de senha usando [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html); [`su`](https://man7.org/linux/man-pages/man1/su.1.html) ainda aplica sua política de autenticação. Confirme que o usuário atual pode percorrer o diretório e ler o script específico, que o valor literal se destina a ser a senha da conta de destino e que a credencial continua válida antes de considerar isso uma transição entre contas. O script não precisa ser executado com sucesso para que seu texto revele um segredo. A saída passiva deve mostrar o caminho e as permissões sem exibir o valor nem tentar fazer login.

Um banco de dados SQLite legível de uma aplicação pode conter nomes de usuário e hashes de senha sem nenhum serviço de banco de dados em escuta. Inspecione o esquema e as permissões do arquivo antes de considerar um hash como uma pista para auditoria offline. Uma senha de aplicação recuperada só concede acesso a uma conta do SO ou a um painel de administração local se a reutilização for confirmada separadamente; o formato do hash ou um nome de usuário correspondente não comprovam reutilização.

O Apache OFBiz pode usar um banco de dados Derby incorporado em `runtime/data/derby/<database>/`. O arquivo `service.properties` do Derby identifica o diretório do banco de dados; o diretório irmão `seg0` contém os arquivos das tabelas. Verifique as permissões de todo o diretório do banco de dados antes de examinar registros da aplicação, como `USER_LOGIN`. Um marcador legível não prova que as tabelas podem ser lidas, que uma senha pode ser recuperada ou que uma credencial da aplicação funciona para uma conta Unix. Mantenha o conteúdo do banco de dados e os hashes de senha fora da saída de enumeração de rotina. Consulte a [documentação sobre diretórios de bancos de dados do Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) e a [API de login do OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

O TeamCity mantém os dados do servidor em um diretório de dados configurável (geralmente `.BuildServer`). Revise as permissões de `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` quando o HSQLDB incorporado estiver em uso e `backup/TeamCity_Backup_*.zip`. Chaves SSH enviadas e outras configurações seguras podem estar criptografadas; portanto, um caminho legível, por si só, não comprova que uma chave privada pode ser usada. O banco de dados ou o backup podem conter usuários da aplicação e hashes de senha; usá-los para uma conta Unix exige evidências separadas de reutilização de senha. Durante a enumeração, registre caminhos e direitos de acesso em vez de exibir chaves, hashes ou linhas do banco de dados. Consulte a documentação do TeamCity sobre [diretório de dados](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), [chaves SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) e [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

O servidor de backup Duplicati mantém a configuração em `Duplicati-server.sqlite`. Seu diretório de dados pode estar no diretório home da conta de serviço, em `/var/lib/Duplicati` ou em um volume de contêiner, e `--server-datafolder` ou `DUPLICATI_HOME` podem alterá-lo. Um banco de dados legível é uma pista valiosa, pois pode conter credenciais de conexão e material de assinatura do servidor, mas instalações mais recentes podem criptografar campos sensíveis e restringir o acesso ao diretório. Compare suas permissões com a conta real do servidor e com qualquer acesso autenticado à interface ou ao ServerUtil. Se esse servidor for executado como root com o `/` do host montado em seu contêiner, hooks de restauração de backup e de tarefas autorizados podem atravessar os limites do sistema de arquivos do host; um listener de loopback ou o nome de um banco de dados, por si só, não comprova controle. Não presuma que o comportamento de login baseado em nonce das versões mais antigas se aplica às versões atuais, que usam um [modelo de autenticação](https://docs.duplicati.com/technical-details/server-authentication-model) diferente. Consulte a documentação do Duplicati sobre o [banco de dados do servidor](https://docs.duplicati.com/database-and-storage/the-server-database) e o [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) para obter detalhes específicos de cada versão.

No PostgreSQL, inspecione `pg_policies` e `pg_class.relrowsecurity` para diferenciar uma consulta filtrada de registros ausentes. Alterar ou desabilitar uma política exige os privilégios apropriados de propriedade da tabela ou de administração. Uma conta de manutenção cujo leak tenha ocorrido separadamente pode ter esses privilégios, mesmo quando a conta da aplicação não os tem. Um listener Redis sem autenticação é uma descoberta distinta: verifique se ele está vinculado apenas ao loopback e se o modo protegido ou as ACLs restringem a conexão atual antes de considerá-lo uma fonte de segredos.

## Revise os armazenamentos de chaves e tokens

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Uma chave privada SSH, um socket de agent, um cache Kerberos, um keyring GPG ou um bundle PKCS#12 só é útil se o usuário atual puder acessá-lo e qualquer passphrase ou política exigida permitir seu uso. Primeiro, inspecione a propriedade e as permissões. As páginas sobre [usuários e sessões](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) e [post-exploitation](../post-exploitation/README.md) explicam os caminhos de acesso correspondentes. O histórico do Git, backups antigos e o histórico do shell também podem reter secrets depois que uma configuração ativa foi limpa. Um diretório `.git` legível pode preservar código-fonte excluído e credenciais de commits anteriores, mesmo quando a working tree está vazia; verifique o acesso e revise o histórico manualmente, em vez de despejá-lo durante a enumeração automatizada.

Uma imagem de boot legível em `/boot` é outra possível fonte de arquivos. [Scripts de boot do initramfs e helpers copiados](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) podem incluir lógica personalizada que fornece uma chave para [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Verifique as permissões de acesso da imagem e revise apenas o script de boot e o helper relevantes em uma cópia offline autorizada. Uma passphrase de desbloqueio de disco incorporada ou derivada não é automaticamente a senha de uma conta Unix: confirme as entradas do helper, o caminho de boot real e o uso separado da mesma credencial antes de tratá-la como uma transição entre contas. A enumeração rotineira não deve desempacotar a imagem, executar seus helpers nem exibir possíveis chaves.

A CLI do Vault [normalmente armazena em cache seu token de autenticação em `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), embora um token helper personalizado possa armazená-lo em outro lugar. Um caminho legível é apenas uma pista de credencial: verifique a validade do token e a política antes de inferir acesso a qualquer secret engine. Para [senhas de uso único de SSH do Vault](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), o token precisa estar autorizado a emitir credenciais para uma role cujo usuário e CIDR incluam a conta e o host pretendidos; esse host também precisa ter o helper de verificação de SSH configurado e aceitar o login. Uma role chamada `root` ou um arquivo de token, por si só, não comprova acesso root. A enumeração passiva deve informar o caminho do arquivo sem ler o token nem solicitar uma OTP.

[KeePass 1.x usa `.kdb`, enquanto KeePass 2.x usa `.kdbx`](https://keepass.info/help/v2/version.html). Trate um nome de arquivo correspondente como um possível cofre criptografado, pois outros produtos também podem usar o sufixo `.kdb`. Um cofre legível não revela suas entradas sem a senha mestra ou o arquivo de chave exigido; uma chave SSH armazenada como anexo é uma pista separada cujo acesso ao host precisa ser validado. [KeePass aceita arquivos arbitrários, incluindo imagens, como arquivos de chave](https://keepass.info/help/base/keys.html), mas um arquivo próximo é apenas uma possibilidade até que sua função, todos os componentes obrigatórios da chave mestra e qualquer login de conta com privilégios mais altos sejam confirmados de forma independente.

Um arquivo de suporte pode conter tanto um cofre KeePass quanto um dump de memória de processo. No caso do [KeePass 2.x anterior à versão 2.54, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) pode tornar a senha mestra recuperável a partir de um dump correspondente; um cofre criptografado ou um dump não relacionado, por si só, não basta. Inspecione manualmente as entradas do arquivo e os direitos de acesso, sem extração em massa nem exibição de secrets durante a enumeração rotineira. Chaves privadas PuTTY podem aparecer como arquivos `.ppk` ou como texto `PuTTY-User-Key-File` em uma entrada do cofre; confirme separadamente a conta pretendida para a chave, sua criptografia e o host que a aceita.

Um arquivo `.har` legível pode preservar solicitações e respostas do navegador, incluindo cabeçalhos de autenticação, cookies e campos de formulário. Ele pode ser salvo diretamente ou dentro de um anexo de suporte. Primeiro, verifique a propriedade e o acesso; depois, inspecione apenas as entradas relevantes. O nome do arquivo, por si só, não comprova a existência de uma credencial reutilizável. A enumeração automatizada deve listar o caminho do arquivo sem exibir os valores capturados. A [documentação do Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) explica a opção de exportação de dados confidenciais.

Para backups de banco de dados criptografados, correlacione o arquivo legível, o material de chave privada acessível e qualquer exigência de passphrase antes de chegar a uma conclusão. Quando autorizado, recuperar a passphrase de uma chave protegida e inspecionar os dados do backup descriptografado são etapas manuais separadas. Uma credencial `root` de banco de dados não é uma credencial `root` do Unix; o uso da mesma senha nessas contas exige validação separada e autorizada. Os limites de confiança do sistema de arquivos em aplicações web também podem expor a conta proprietária desses materiais; consulte a [análise do cache de arquivos do Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Root de um container e root do host são identidades separadas. Uma chave privada SSH legível somente após obter root dentro de um container pode autenticar em uma conta do host se o host a aceitar, mas o nome do arquivo ou o comentário da chave pública não comprova esse acesso. Da mesma forma, um gerador de senhas personalizado encontrado ao lado de um registro de alteração de senha com timestamp é apenas uma pista para análise manual: um gerador não criptográfico baseado em tempo pode ter uma pequena janela de seeds candidatas, mas o fuso horário, a precisão do relógio, o comportamento da biblioteca e alterações posteriores de senha afetam a reconstrução. Valide credenciais candidatas somente quando autorizado; não trate senhas geradas como confirmadas.

Uma conta de serviço dentro de um container pode conseguir ler um script de provisionamento antigo em um diretório home nominalmente privilegiado, se o diretório permitir travessia e as permissões do arquivo permitirem o acesso. Uma senha de administrador de aplicação embutida é uma pista de exposição de credencial, não acesso root ao host: verifique se o script e a credencial estavam ativos, a qual conta o valor pertence e se uma conta separada do host ainda aceita a mesma senha. Durante a enumeração passiva, registre o caminho do arquivo e os direitos de acesso sem exibir o secret nem tentar autenticação no host.

Se um bundle `.p12` ou `.pfx` legível tiver uma senha exposta na configuração da aplicação, inspecione-o com `openssl pkcs12 -info -in bundle.p12 -noout`. Se o bundle contiver uma chave privada exportável, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` grava essa chave sem criptografia. Proteja o arquivo de saída e remova-o após a análise; use a chave recuperada apenas para o serviço ou ciphertext ao qual ela realmente corresponde. Um bundle, por si só, não implica que sua chave privada seja útil para outra aplicação.
