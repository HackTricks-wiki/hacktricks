# Database e materiale segreto sugli host Linux

{{#include ../../banners/hacktricks-training.md}}

Le credenziali di database e applicazioni si trovano spesso accanto al servizio a cui appartengono. Mappa il processo, il socket o la porta locale, la configurazione e il file delle credenziali prima di verificare se un account può leggere dati o eseguire un'operazione privilegiata.

## Individuare i servizi dati locali e le credenziali

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Esamina le configurazioni applicative leggibili, i file di deployment, i file di ambiente dei servizi e i backup alla ricerca di stringhe di connessione o chiavi. Il socket Unix di un processo DB può avere regole di accesso diverse da quelle del listener TCP. Le autorizzazioni del database differiscono da quelle del sistema operativo: una password DB recuperata concede solo i ruoli assegnati a quell’account DB, a meno che non venga dimostrato un altro percorso. In PostgreSQL, le policy di row-level security possono nascondere record a un ruolo, mentre un ruolo con diritti di gestione delle policy può modificare ciò che quel ruolo vede; distingui l’accesso ai dati dall’amministrazione delle policy. Consulta le guide specifiche per [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) e [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Uno script di automazione leggibile nella home di un altro account può contenere credenziali anche se il nome del file non menziona le password. Per esempio, uno script Python può avviare `su` e passare un valore letterale al prompt della password con [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html); [`su`](https://man7.org/linux/man-pages/man1/su.1.html) applica comunque la propria policy di autenticazione. Verifica che l’utente corrente possa attraversare la directory e leggere lo script specifico, che il valore letterale sia destinato a essere la password dell’account di destinazione e che la credenziale sia ancora valida prima di considerarla un passaggio a un altro account. Non è necessario che lo script venga eseguito correttamente perché il suo testo riveli un segreto. L’output passivo dovrebbe mostrare il percorso e le autorizzazioni senza stampare il valore né tentare un login.

Un database applicativo SQLite leggibile può contenere nomi utente e hash delle password senza che sia in ascolto alcun servizio database. Esamina lo schema e le autorizzazioni del file prima di considerare un hash una pista per un’analisi offline. Una password applicativa recuperata consente l’accesso a un account OS o a un pannello di amministrazione locale solo se il suo riutilizzo viene verificato separatamente; il formato dell’hash o la corrispondenza del nome utente non dimostrano che sia stata riutilizzata.

Apache OFBiz può usare un database Derby integrato in `runtime/data/derby/<database>/`. Il file `service.properties` di Derby identifica la directory del database; la directory adiacente `seg0` contiene i file delle tabelle. Verifica le autorizzazioni sull’intera directory del database prima di esaminare record applicativi come `USER_LOGIN`. Un file marcatore leggibile non dimostra che le tabelle siano leggibili, che si possa recuperare una password o che una credenziale applicativa funzioni per un account Unix. Non includere i contenuti dei database e gli hash delle password nell’output delle normali attività di enumerazione. Consulta la [documentazione di Derby sulle directory dei database](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) e l’[API di login di OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

TeamCity conserva i dati del server in una directory configurabile (spesso `.BuildServer`). Controlla le autorizzazioni di `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` quando viene usato l’HSQLDB integrato e `backup/TeamCity_Backup_*.zip`. Le chiavi SSH caricate e altre impostazioni sensibili potrebbero essere cifrate, quindi il solo fatto che un percorso sia leggibile non dimostra che una chiave privata sia utilizzabile. Il database o il backup possono contenere utenti applicativi e hash delle password; usarli per un account Unix richiede prove separate del riutilizzo della password. Durante l’enumerazione, registra i percorsi e i diritti di accesso invece di stampare chiavi, hash o righe del database. Consulta la documentazione di TeamCity relativa alla [directory dei dati](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), alle [chiavi SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) e ai [backup](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

Il server di backup Duplicati conserva la configurazione in `Duplicati-server.sqlite`. La directory dei dati può trovarsi nella home dell’account del servizio, in `/var/lib/Duplicati` o in un volume del container; `--server-datafolder` o `DUPLICATI_HOME` possono modificarla. Un database leggibile è una pista di grande valore perché può contenere credenziali di connessione e materiale di firma del server, ma le installazioni più recenti potrebbero cifrare i campi sensibili e limitare l’accesso alla directory. Metti in relazione le sue autorizzazioni con l’account effettivo del server e con eventuali accessi autenticati all’interfaccia utente o a ServerUtil. Se il server viene eseguito come root e il filesystem host `/` è montato nel suo container, le operazioni autorizzate di ripristino dei backup e gli hook dei job possono oltrepassare il confine del filesystem host; un listener loopback o il solo nome del file del database non dimostrano il controllo. Non presumere che il comportamento di login basato su nonce delle versioni precedenti sia valido per quelle attuali, che usano un diverso [modello di autenticazione](https://docs.duplicati.com/technical-details/server-authentication-model). Per i dettagli specifici delle versioni, consulta la documentazione di Duplicati sul [database del server](https://docs.duplicati.com/database-and-storage/the-server-database) e su [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil).

Per PostgreSQL, esamina `pg_policies` e `pg_class.relrowsecurity` per distinguere una query filtrata da record mancanti. Per modificare o disabilitare una policy servono i privilegi appropriati di proprietà della tabella o di amministrazione. Un account di manutenzione ottenuto tramite un leak distinto potrebbe avere tali privilegi anche quando l’account applicativo non li ha. Un listener Redis senza autenticazione è un altro rilievo distinto: verifica se è associato solo all’interfaccia loopback e se la modalità protetta o le ACL limitano la connessione corrente prima di considerarlo una fonte di segreti.

## Esamina gli archivi di chiavi e token

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Una chiave privata SSH, un socket dell’agent, una cache Kerberos, un keyring GPG o un bundle PKCS#12 è utile solo se l’utente corrente può accedervi e se l’eventuale passphrase o policy ne consente l’uso. Controlla prima proprietario e permessi. Le pagine [utenti e sessioni](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) e [post-exploitation](../post-exploitation/README.md) descrivono i relativi percorsi di accesso. Anche la cronologia Git, i vecchi backup e la cronologia della shell possono conservare segreti dopo la pulizia di una configurazione attiva. Una directory `.git` leggibile può conservare codice sorgente eliminato e credenziali precedentemente sottoposte a commit anche quando l’albero di lavoro è vuoto; controlla i permessi e rivedi la cronologia manualmente, invece di riversarne il contenuto durante l’enumerazione automatizzata.

Un’immagine di boot leggibile in `/boot` è un altro possibile archivio. Gli [script di boot e gli helper copiati di initramfs](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) possono includere logica personalizzata che fornisce una chiave a [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Controlla i permessi di accesso all’immagine ed esamina solo lo script di boot e l’helper pertinenti in una copia offline autorizzata. Una passphrase incorporata o derivata per sbloccare il disco non è automaticamente la password di un account Unix: verifica gli input dell’helper, il percorso di boot effettivo e l’eventuale riutilizzo separato delle credenziali prima di considerarla un passaggio a un account. L’enumerazione ordinaria non dovrebbe decomprimere l’immagine, eseguire i suoi helper o stampare possibili chiavi.

La CLI di Vault [memorizza normalmente il token di autenticazione in `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), anche se un token helper personalizzato può salvarlo altrove. Un percorso leggibile è solo un possibile indizio di credenziali: verifica la validità del token e la policy prima di dedurre l’accesso a qualsiasi secret engine. Per le [password monouso SSH di Vault](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), il token deve essere autorizzato a emettere credenziali per un ruolo il cui utente e CIDR includano l’account e l’host previsti; inoltre, quell’host deve avere configurato l’helper di verifica SSH e accettare il login. Un ruolo che indica `root` o un file di token, da soli, non dimostrano l’accesso root. L’enumerazione passiva dovrebbe riportare il percorso del file senza leggere il token né richiedere un OTP.

[KeePass 1.x usa `.kdb`, mentre KeePass 2.x usa `.kdbx`](https://keepass.info/help/v2/version.html). Considera un nome di file corrispondente come un possibile vault cifrato, poiché anche altri prodotti potrebbero usare il suffisso `.kdb`. Un vault leggibile non ne rivela le voci senza la password principale o il file chiave richiesti; una chiave SSH memorizzata come allegato è un indizio distinto, il cui accesso all’host deve essere verificato. [KeePass accetta file arbitrari, incluse immagini, come file chiave](https://keepass.info/help/base/keys.html), ma un file nelle vicinanze è solo un candidato finché non vengono confermati in modo indipendente il suo ruolo, tutti i componenti richiesti della chiave principale e l’eventuale login a un account con privilegi superiori.

Un archivio di supporto può contenere sia un vault KeePass sia un dump della memoria di un processo. Per [KeePass 2.x precedente alla versione 2.54, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) rende potenzialmente recuperabile la password principale da un dump corrispondente; un vault cifrato o un dump non correlato, da soli, non sono sufficienti. Esamina manualmente le voci dell’archivio e i permessi di accesso, senza estrarre in blocco o stampare segreti durante l’enumerazione ordinaria. Le chiavi private PuTTY possono comparire come file `.ppk` o come testo `PuTTY-User-Key-File` in una voce del vault; verifica separatamente l’account previsto per la chiave, la cifratura e l’host che la accetta.

Un archivio HTTP `.har` leggibile può conservare richieste e risposte del browser, incluse intestazioni di autenticazione, cookie e campi dei moduli. Può essere salvato direttamente o all’interno di un allegato di supporto. Controlla prima proprietario e permessi di accesso, poi esamina solo le voci pertinenti; il solo nome del file non dimostra che contenga credenziali riutilizzabili. L’enumerazione automatizzata dovrebbe elencare il percorso dell’archivio senza stampare i valori acquisiti. La [documentazione di Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) descrive l’opzione di esportazione dei dati sensibili.

Per i backup cifrati di database, correla l’archivio leggibile, il materiale accessibile della chiave privata e l’eventuale passphrase richiesta prima di trarre conclusioni. Se autorizzati, il recupero della passphrase di una chiave protetta e l’esame dei dati del backup decifrato sono passaggi manuali distinti. Una credenziale `root` del database non è una credenziale `root` Unix; il riutilizzo della password tra questi account richiede una verifica separata e autorizzata. Anche i confini di fiducia del filesystem nelle applicazioni web possono esporre l’account proprietario di questi materiali; consulta la [revisione della cache dei file di Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

Il root di un container e il root dell’host sono identità distinte. Una chiave privata SSH leggibile solo dopo essere diventati root all’interno di un container può autenticare a un account dell’host, se l’host la accetta, ma il nome del file o il commento della chiave pubblica non dimostrano tale accesso. Analogamente, un generatore di password personalizzato trovato accanto a una registrazione con timestamp di un cambio password è solo un indizio da analizzare manualmente: un generatore non crittografico con seed basato sull’ora può avere una finestra ristretta di seed candidati, ma il fuso orario, la precisione dell’orologio, il comportamento della libreria e i cambi di password successivi influiscono sulla ricostruzione. Verifica le credenziali candidate solo se autorizzato; non considerare le password generate come confermate.

Un account di servizio all’interno di un container potrebbe essere in grado di leggere un vecchio script di provisioning in una directory home nominalmente privilegiata, se la directory è attraversabile e i permessi del file lo consentono. Una password di amministratore dell’applicazione incorporata è un indizio di esposizione di credenziali, non di accesso root all’host: verifica se lo script e la credenziale erano attivi, a quale account appartiene il valore e se un account separato dell’host accetta ancora la stessa password. Durante l’enumerazione passiva, registra il percorso del file e i permessi di accesso senza stampare il segreto né tentare l’autenticazione sull’host.

Se un bundle `.p12` o `.pfx` leggibile ha una password esposta nella configurazione dell’applicazione, esaminalo con `openssl pkcs12 -info -in bundle.p12 -noout`. Se il bundle contiene una chiave privata esportabile, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` scrive la chiave senza cifrarla. Proteggi il file di output e rimuovilo dopo l’analisi; usa la chiave recuperata solo per il servizio o il testo cifrato a cui corrisponde effettivamente. Un bundle, da solo, non implica che la sua chiave privata sia utile per un’applicazione diversa.
