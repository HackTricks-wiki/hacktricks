# Bases de datos y material secreto en hosts Linux

{{#include ../../banners/hacktricks-training.md}}

Las credenciales de bases de datos y aplicaciones suelen estar junto al servicio al que dan soporte. Identifica el proceso, el socket o puerto local, la configuración y el archivo de credenciales antes de comprobar si una cuenta puede leer datos o ejecutar una operación privilegiada.

## Localizar servicios de datos locales y credenciales

```bash
ss -lntup
ss -lnx
ps -eo user,pid,args | grep -E '[m]ysqld|[m]ariadbd|[p]ostgres|[r]edis-server|[m]ongod'
find /etc /opt /var/www /home -type f \( -name '*.env' -o -name '*config*' -o -name '.my.cnf' -o -name '.pgpass' \) -ls 2>/dev/null | head -100
```

Inspecciona las configuraciones legibles de aplicaciones, los archivos de despliegue, los archivos de entorno de servicios y las copias de seguridad en busca de cadenas de conexión o claves. Un socket Unix de un proceso de DB puede tener reglas de acceso distintas de las de su listener TCP. Los permisos de la base de datos son distintos de los permisos del sistema operativo: una contraseña de DB recuperada solo concede los roles asignados a esa cuenta de DB, a menos que se demuestre otra vía. En PostgreSQL, las políticas de seguridad a nivel de fila pueden ocultar registros a un rol, mientras que un rol con derechos para administrar políticas puede cambiar esa vista; distingue el acceso a los datos de la administración de políticas. Usa las guías específicas de cada servicio para [MySQL/MariaDB](../../network-services-pentesting/pentesting-mysql.md), [PostgreSQL](../../network-services-pentesting/pentesting-postgresql.md) y [Redis](../../network-services-pentesting/6379-pentesting-redis.md).

Un script de automatización legible en el directorio personal de otra cuenta puede incluir una credencial aunque su nombre de archivo no mencione contraseñas. Por ejemplo, un script de Python puede iniciar `su` y pasar un valor literal a su prompt de contraseña con [`pexpect.sendline`](https://pexpect.readthedocs.io/en/latest/api/pexpect.html); [`su`](https://man7.org/linux/man-pages/man1/su.1.html) sigue aplicando su política de autenticación. Confirma que el usuario actual puede recorrer el directorio y leer el script específico, que el valor literal está pensado como contraseña de la cuenta de destino y que la credencial sigue siendo válida antes de considerarlo un cambio de cuenta. No es necesario que el script se ejecute correctamente para que su texto revele un secreto. La salida pasiva debe mostrar la ruta y los permisos sin imprimir el valor ni intentar iniciar sesión.

Una base de datos SQLite legible de una aplicación puede contener nombres de usuario y hashes de contraseñas sin que haya ningún servicio de base de datos escuchando. Inspecciona su esquema y los permisos del archivo antes de tratar un hash como pista para una auditoría offline. Una contraseña de aplicación recuperada solo concede acceso a una cuenta del sistema operativo o a un panel de administración local si se confirma por separado que se reutiliza; el formato del hash o la coincidencia del nombre de usuario no prueban que se reutilice.

Apache OFBiz puede usar una base de datos Derby integrada en `runtime/data/derby/<database>/`. El archivo `service.properties` de Derby identifica el directorio de la base de datos; su directorio hermano `seg0` contiene los archivos de las tablas. Comprueba los permisos de todo el directorio de la base de datos antes de revisar registros de la aplicación, como `USER_LOGIN`. Que el archivo indicador sea legible no demuestra que las tablas se puedan leer, que se pueda recuperar una contraseña ni que una credencial de la aplicación funcione para una cuenta Unix. Mantén el contenido de la base de datos y los hashes de contraseñas fuera de la salida habitual de enumeración. Consulta la [documentación del directorio de bases de datos de Derby](https://db.apache.org/derby/docs/10.4/devguide/cdevdvlp40724.html) y la [API de inicio de sesión de OFBiz](https://nightlies.apache.org/ofbiz/stable/javadoc/org/apache/ofbiz/common/login/LoginServices.html).

TeamCity almacena los datos del servidor en un directorio de datos configurable (a menudo `.BuildServer`). Revisa los permisos de `config/projects/<project>/pluginData/ssh_keys`, `config/database.properties`, `system/buildserver.*` cuando se use la HSQLDB integrada y `backup/TeamCity_Backup_*.zip`. Las claves SSH cargadas y otras configuraciones seguras pueden estar cifradas, por lo que una ruta legible por sí sola no demuestra que haya una clave privada utilizable. La base de datos o la copia de seguridad pueden contener usuarios de la aplicación y hashes de contraseñas; para usar estos datos con una cuenta Unix hace falta evidencia independiente de que la contraseña se reutiliza. Durante la enumeración, registra las rutas y los permisos de acceso en lugar de imprimir claves, hashes o filas de la base de datos. Consulta la documentación de TeamCity sobre el [directorio de datos](https://www.jetbrains.com/help/teamcity/teamcity-data-directory.html), la [administración de claves SSH](https://www.jetbrains.com/help/teamcity/ssh-keys-management.html) y las [copias de seguridad](https://www.jetbrains.com/help/teamcity/manual-backup-and-restore.html).

El servidor de copias de seguridad Duplicati guarda la configuración en `Duplicati-server.sqlite`. Su directorio de datos puede estar en el directorio personal de la cuenta del servicio, en `/var/lib/Duplicati` o en un volumen de contenedor; `--server-datafolder` o `DUPLICATI_HOME` pueden cambiarlo. Una base de datos legible es una pista de gran valor porque puede contener credenciales de conexión y material de firma del servidor, pero las instalaciones más recientes pueden cifrar los campos sensibles y restringir el acceso al directorio. Correlaciona sus permisos con la cuenta real del servidor y con cualquier acceso autenticado a la interfaz de usuario o a ServerUtil. Si ese servidor se ejecuta como root con `/` del host montado en su contenedor, las funciones autorizadas de restauración de copias de seguridad y los hooks de tareas pueden cruzar el límite del sistema de archivos del host; un listener de loopback o el nombre de un archivo de base de datos no prueban por sí solos que se tenga control. No se debe asumir que el comportamiento de inicio de sesión basado en nonce de versiones antiguas se aplica a las versiones actuales, que usan un [modelo de autenticación](https://docs.duplicati.com/technical-details/server-authentication-model) distinto. Consulta la documentación de Duplicati sobre la [base de datos del servidor](https://docs.duplicati.com/database-and-storage/the-server-database) y [ServerUtil](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli-1/serverutil) para obtener detalles específicos de cada versión.

En PostgreSQL, inspecciona `pg_policies` y `pg_class.relrowsecurity` para distinguir una consulta filtrada de registros ausentes. Cambiar o desactivar una política requiere los privilegios adecuados de propietario de la tabla o de administrador. Una cuenta de mantenimiento filtrada por separado puede tener esos privilegios aunque la cuenta de la aplicación no los tenga. Un listener de Redis sin autenticación es otro hallazgo distinto: verifica si solo está enlazado a loopback y si el modo protegido o las ACL restringen la conexión actual antes de considerarlo una fuente de secretos.

## Revisa los almacenes de claves y tokens

```bash
find /home /root -maxdepth 4 -type f \( -name 'id_*' -o -name '*.ppk' -o -name '*.p12' -o -name '*.pfx' -o -name '*.kdb' -o -name '*.kdbx' -o -name '*.gpg' -o -name '.git-credentials' \) -ls 2>/dev/null
find /home /root -maxdepth 4 -type d -name '.gnupg' -ls 2>/dev/null
printenv SSH_AUTH_SOCK KRB5CCNAME GNUPGHOME 2>/dev/null
```

Una clave privada SSH, un socket de agente, una caché de Kerberos, un keyring de GPG o un paquete PKCS#12 solo son útiles si el usuario actual puede acceder a ellos y la passphrase o política requerida permite usarlos. Comprueba primero la propiedad y los permisos. Las páginas sobre [usuarios y sesiones](../user-information/user-and-session-triage.md), [Linux AD](../user-information/linux-active-directory.md) y [post-exploitation](../post-exploitation/README.md) explican las rutas de acceso correspondientes. El historial de Git, las copias de seguridad antiguas y el historial del shell también pueden conservar secretos después de limpiar una configuración activa. Un directorio `.git` legible puede conservar código fuente eliminado y credenciales confirmadas anteriormente, aunque el árbol de trabajo esté vacío; comprueba el acceso y revisa el historial manualmente en lugar de volcarlo durante la enumeración automatizada.

Una imagen de arranque legible en `/boot` es otra posible fuente de archivos. Los [scripts de arranque de initramfs y los helpers copiados](https://manpages.debian.org/testing/initramfs-tools-core/initramfs-tools.7.en.html) pueden incluir lógica personalizada que proporciona una clave a [`cryptsetup --key-file=-`](https://manpages.debian.org/testing/cryptsetup-bin/cryptsetup.8.en.html). Comprueba los permisos de acceso de la imagen y revisa solo el script de arranque y el helper pertinentes en una copia offline autorizada. Una passphrase de desbloqueo de disco incrustada o derivada no es automáticamente una contraseña de cuenta Unix: confirma las entradas del helper, la ruta de arranque real y la reutilización independiente de credenciales antes de considerarla una transición de cuenta. La enumeración rutinaria no debería desempaquetar la imagen, ejecutar sus helpers ni mostrar posibles claves.

La CLI de Vault [normalmente almacena en caché su token de autenticación en `~/.vault-token`](https://developer.hashicorp.com/vault/docs/commands/token-helper), aunque un token helper personalizado puede guardarlo en otro lugar. Una ruta legible solo indica una posible credencial: verifica la validez del token y la política antes de inferir acceso a cualquier secret engine. Para las [contraseñas de un solo uso de Vault SSH](https://developer.hashicorp.com/vault/docs/secrets/ssh/one-time-ssh-passwords), el token debe estar autorizado para emitir credenciales para un rol cuyo usuario y CIDR incluyan la cuenta y el host previstos; además, ese host debe tener configurado el helper de verificación SSH y aceptar el inicio de sesión. Que un rol se llame `root` o que exista un archivo de token no demuestra que haya acceso root. La enumeración pasiva debería informar la ruta del archivo sin leer el token ni solicitar un OTP.

[KeePass 1.x usa `.kdb`, mientras que KeePass 2.x usa `.kdbx`](https://keepass.info/help/v2/version.html). Considera un nombre de archivo coincidente como posible vault cifrado, ya que otros productos también pueden usar el sufijo `.kdb`. Un vault legible no revela sus entradas sin la contraseña maestra o el archivo de clave requeridos; una clave SSH almacenada como adjunto es una pista independiente cuyo acceso al host debe validarse. [KeePass acepta archivos arbitrarios, incluidas imágenes, como archivos de clave](https://keepass.info/help/base/keys.html), pero un archivo cercano solo es un candidato hasta confirmar de forma independiente su función, todos los componentes necesarios de la clave maestra y cualquier inicio de sesión con una cuenta con más privilegios.

Un archivo de soporte puede contener tanto un vault de KeePass como un volcado de memoria de procesos. Para [KeePass 2.x anterior a 2.54, CVE-2023-32784](https://nvd.nist.gov/vuln/detail/CVE-2023-32784) puede hacer que la contraseña maestra sea potencialmente recuperable a partir de un volcado correspondiente; un vault cifrado o un volcado no relacionado no bastan por sí solos. Inspecciona manualmente las entradas del archivo y los permisos de acceso, sin extraer todo ni mostrar secretos durante la enumeración rutinaria. Las claves privadas de PuTTY pueden aparecer como archivos `.ppk` o como texto `PuTTY-User-Key-File` en una entrada del vault; confirma por separado la cuenta prevista para la clave, su cifrado y el host que la acepta.

Un archivo HTTP `.har` legible puede conservar solicitudes y respuestas del navegador, incluidos encabezados de autenticación, cookies y campos de formulario. Puede guardarse directamente o dentro de un adjunto de soporte. Comprueba primero la propiedad y el acceso, y luego inspecciona solo las entradas pertinentes; el nombre del archivo por sí solo no demuestra que contenga una credencial reutilizable. La enumeración automatizada debería indicar la ruta del archivo sin mostrar los valores capturados. La [documentación de Microsoft Edge](https://learn.microsoft.com/en-us/microsoft-edge/devtools/network/reference#save-all-network-requests-to-a-har-file) explica la opción de exportación de datos confidenciales.

En el caso de copias de seguridad de bases de datos cifradas, correlaciona el archivo legible, el material de clave privada accesible y cualquier requisito de passphrase antes de llegar a una conclusión. Cuando esté autorizado, recuperar la passphrase de una clave protegida e inspeccionar los datos descifrados de la copia de seguridad son pasos manuales independientes. Una credencial `root` de base de datos no es una credencial `root` de Unix; la reutilización de contraseñas entre esas cuentas requiere una validación independiente y autorizada. Los límites de confianza del sistema de archivos en aplicaciones web también pueden exponer la cuenta propietaria de estos materiales; consulta la [revisión de la caché de archivos de Django](../../network-services-pentesting/pentesting-web/django.md#cache-manipulation-to-rce).

El usuario root del contenedor y el usuario root del host son identidades distintas. Una clave privada SSH legible solo después de convertirse en root dentro de un contenedor podría autenticar en una cuenta del host si este la acepta, pero el nombre del archivo o el comentario de la clave pública no demuestra que se tenga acceso. Asimismo, un generador de contraseñas personalizado encontrado junto a un registro fechado de cambio de contraseña solo es una pista para el análisis manual: un generador no criptográfico cuya semilla depende del tiempo puede tener una ventana pequeña de semillas candidatas, pero la zona horaria, la precisión del reloj, el comportamiento de la biblioteca y los cambios posteriores de contraseña afectan la reconstrucción. Valida las credenciales candidatas solo cuando esté autorizado; no consideres las contraseñas generadas como confirmadas.

Una cuenta de servicio dentro de un contenedor puede tener permiso para leer un script de aprovisionamiento antiguo en un directorio de inicio nominalmente privilegiado si se puede recorrer el directorio y los permisos del archivo lo permiten. Una contraseña de administrador de aplicación incrustada es una pista de exposición de credenciales, no de acceso root al host: comprueba si el script y la credencial estaban activos, a qué cuenta pertenece el valor y si otra cuenta del host sigue aceptando la misma contraseña. Durante la enumeración pasiva, registra la ruta del archivo y los permisos de acceso sin mostrar el secreto ni intentar autenticarse en el host.

Si un paquete `.p12` o `.pfx` legible tiene una contraseña expuesta en la configuración de la aplicación, inspecciónalo con `openssl pkcs12 -info -in bundle.p12 -noout`. Si el paquete contiene una clave privada exportable, `openssl pkcs12 -in bundle.p12 -nocerts -nodes -out extracted.key` escribe esa clave sin cifrar. Protege el archivo de salida y elimínalo después del análisis; usa la clave recuperada solo para el servicio o el texto cifrado con el que realmente coincida. La existencia de un paquete no implica que su clave privada sea útil para otra aplicación.
