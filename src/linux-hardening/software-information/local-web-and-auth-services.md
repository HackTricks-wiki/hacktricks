# स्थानीय Web और Authentication Services

{{#include ../../banners/hacktricks-training.md}}

Linux shell से Web और Authentication Services का host-side view मिलता है: process arguments, listeners, unit files, configuration, logs और केवल स्थानीय interfaces। इस view का उपयोग करके किसी reachable service को उन accounts और files से जोड़ें जिनका वह वास्तव में उपयोग करती है।

## स्थानीय Web stack का नक्शा बनाएँ

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

वर्चुअल-होस्ट नाम, document root, proxy routes, upload directories, PHP execution settings और credentials वाली config files की जाँच करें। Loopback listener किसी proxy या SSH tunnel के ज़रिए पहुँच योग्य हो सकता है। Local listener के विरुद्ध किसी नामित virtual host की जाँच करने के लिए, इच्छित `Host` header भेजें या सही address और port के साथ `curl --resolve` का उपयोग करें। Virtual-host enumeration से ऐसे नाम भी सामने आ सकते हैं जो default response में मौजूद नहीं होते। किसी writable upload directory को code execution मानने से पहले जाँचें कि Apache `.htaccess` overrides की अनुमति देता है या नहीं और upload paths में PHP execute हो सकता है या नहीं। Deployed JavaScript source map से source paths या client-side secrets उजागर हो सकते हैं; मिले हुए values को clues मानें और उनके वास्तविक privileges की पुष्टि करें। Web-विशिष्ट जाँचों के लिए [Apache](../../network-services-pentesting/pentesting-web/apache.md) और [Nginx](../../network-services-pentesting/pentesting-web/nginx.md) देखें।

Apache के साथ [mpm-itk](https://mpm-itk.sesse.net/) में, सक्रिय `AssignUserID` किसी virtual host को अलग user और group के अंतर्गत चला सकता है। यदि कम-privileged account उस host के `DocumentRoot` में script लिख सकता है, तो जाँचें कि कोई पहुँच योग्य route उसे वास्तव में assigned identity के अंतर्गत execute करता है या नहीं। पुष्टि करें कि module loaded है, virtual-host configuration प्रभावी है (इसमें expression-based identity overrides भी शामिल हैं), directory पर write और search permissions हैं, script handler सही है और listener तक पहुँच है। केवल किसी directive का highlighted होना या directory का writable होना cross-user execution का प्रमाण नहीं है।

Web server के ज़रिए प्रकाशित home directory में SSH identity files के backup archives हो सकते हैं, भले ही live `.ssh` directory private हो। उदाहरण के लिए, [Nostromo की `homedirs_public` setting](https://www.nazgul.ch/dev/nostromo_man.html) user homes से serve होने वाली subdirectory चुनती है। केवल path में archive मिलने का संकेत एक lead है: server की effective mapping, local readability या HTTP authorization, archive contents, private-key passphrase और संबंधित account द्वारा उस key को स्वीकार किए जाने की पुष्टि करें। नियमित host enumeration के दौरान archives extract न करें और key material print न करें।

किसी अधिक-privileged local web app के readable backup से authentication और file-read logic उजागर हो सकता है, भले ही उसका live source पहुँच योग्य न हो। उस पर भरोसा करने से पहले backup की deployed service से तुलना करें। खास तौर पर, caller-controlled text के बाद secret और role flag को encrypt करके cookie बनाने वाले code की समीक्षा करें, यदि app deterministic ECB blocks का उपयोग करती है, चुने गए text के लिए नए cookies लौटाती है और बाद में decrypted value को unescaped delimiter पर split करती है। [NIST बताता है कि ECB में blocks की mapping स्वतंत्र और दोहराने योग्य होती है](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); यह गुण chosen-input comparison में मदद कर सकता है, लेकिन अपने आप कोई higher role नहीं देता। Live route, session prerequisites, सटीक parser/data flow, service identity और किसी अलग privileged action या file-read path की पुष्टि करें। Passive inventory में archive contents पढ़े बिना या authentication probes भेजे बिना backup metadata और listener ownership की रिपोर्ट दें।

Source-review का यही तरीका किसी privileged **non-HTTP** loopback service, जैसे custom SSH-backed interface, पर भी लागू होता है। यदि accessible source backup में ऐसा command दिखता है जो caller द्वारा चुना गया file path स्वीकार करता है, तो उसका authentication gate, path resolve करने का तरीका और file खोलने से पहले यह साबित करने की जाँच करें कि resolved file इच्छित directory के भीतर ही रहता है। Go में [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) path को clean करता है, लेकिन उसके directory के भीतर रहने की गारंटी नहीं देता। पुष्टि करें कि backup running build से मेल खाता है, listener पहुँच योग्य है, कम-privileged account उस command का उपयोग कर सकता है और process target को पढ़ सकता है; readable SSH key का होना login-policy से जुड़ा एक अलग प्रश्न है। Archive contents या keys को automated output में extract किए बिना source archive paths और service ownership की रिपोर्ट दें।

TCP loopback पर सुनने वाले PHP-FPM pool तक कोई दूसरा local account पहुँच सकता है, भले ही उसकी website पर authentication हो। [PHP चेतावनी देता है कि FastCGI से connect कर सकने वाला client request settings, जिनमें `auto_prepend_file` भी शामिल है, नियंत्रित कर सकता है](https://www.php.net/manual/en/install.fpm.php)। Pool की `listen` और `listen.allowed_clients` settings के साथ live listener, worker UID, किसी मौजूदा script path और `security.limit_extensions` या `php_admin_value` जैसी पाबंदियों की समीक्षा करें। Pool configuration files में `env[...]` directives के तहत credentials हो सकते हैं, इसलिए automated inventory में contents के बजाय उनके paths की रिपोर्ट दें। केवल config file या port cross-user execution route का प्रमाण नहीं है; protocol के विवरण के लिए [FastCGI guide](../../network-services-pentesting/9000-pentesting-fastcgi.md) देखें।

किसी privileged local API के लिए, code execution के साथ authorization की भी जाँच करें। ऐसा database role जिसे कम-privileged account बदल सकता है, कोई API route unlock कर सकता है, लेकिन अगली boundary उस route के implementation पर निर्भर करती है। उदाहरण के लिए, request JSON को JavaScript object में merge करके फिर [`child_process.exec`](https://nodejs.org/api/child_process.html) call करना, [prototype-pollution-to-execution dataflow](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md) की समीक्षा करने का कारण है। इस्तेमाल हो रही merge library/version, input validation, पहुँच योग्य route, process identity और child-process options की पुष्टि करें; केवल root-owned Node listener या vulnerable dependency का नाम एक lead है।

File-backed CMS stores में administrator password verifiers, सामान्य `.php` configuration files के बाहर रखे जा सकते हैं। उदाहरणों में site की `data/database.js` या `data/settings/pass.php` शामिल हैं। Manual review से पहले file ownership और readability जाँचें और hashes को automated shared output में शामिल न करें। Recover किया जा सकने वाला application password, Unix account से जुड़ी एक अलग privilege boundary है: password reuse के किसी दावे की पुष्टि संबंधित account और अनुमत authentication method के लिए करें।

किसी application के authentication controller में configuration file के बजाय source code में literal login password भी हो सकता है। यदि कम-privileged user deployed controller पढ़ सकता है, तो उसकी authentication comparison की locally समीक्षा करें और किसी भी value को shared enumeration output से बाहर रखें। दावा करने से पहले पुष्टि करें कि code path सक्रिय है, password application के लिए valid है और कोई अलग higher-privileged Unix account वही password स्वीकार करता है। केवल controller filename एक review lead है।

Dolibarr database connection settings, जिनमें `dolibarr_main_db_pass` भी शामिल है, `htdocs/conf/conf.php` में रखता है ([configuration reference](https://wiki.dolibarr.org/index.php/Configuration_file))। Readable file credentials का एक lead है; केवल अलग से सत्यापित account-password reuse या कोई अन्य database permission ही इसे local privilege escalation बना सकती है। पहले permissions जाँचें और automated output में value print न करें।

GitLab की Linux package configuration आम तौर पर `/etc/gitlab/gitlab.rb` होती है, जबकि deployments में इसकी readable copies कहीं और भी हो सकती हैं। [GitLab के दस्तावेज़](https://docs.gitlab.com/omnibus/settings/smtp/) बताते हैं कि इस file में `gitlab_rails['smtp_password']` हो सकता है, हालांकि encrypted SMTP settings में password plaintext file के बाहर रखा जा सकता है। Readable configuration को credentials का lead मानें: higher-privileged account द्वारा password reuse का दावा करने से पहले पुष्टि करें कि configuration सक्रिय है, credential अभी valid है और कोई विशिष्ट higher-privileged account उसे स्वीकार करता है। अलग से, [GitLab `gitlab.rb` को root के अंतर्गत Ruby code के रूप में चलाता है, जब `gitlab-ctl reconfigure` execute होता है](https://docs.gitlab.com/omnibus/settings/configuration/); किसी writable active file या शामिल `from_file` को execution finding मानने के लिए वास्तविक privileged reconfigure path होना ज़रूरी है। Config preview से credential values उजागर हो सकती हैं, इसलिए उसके output को sensitive मानें और इसके बजाय paths तथा permissions साझा करें।

Self-hosted Mattermost installation में `SqlSettings.DataSource`, `/opt/mattermost/config/config.json` में हो सकता है; [Mattermost के दस्तावेज़](https://docs.mattermost.com/deployment-guide/server/troubleshooting) इस सामान्य path के साथ उन deployments का भी उल्लेख करते हैं जहाँ active configuration database में रखी जाती है। Readable file से application database credential उजागर हो सकता है, लेकिन इससे database access या Unix root access साबित नहीं होता। Enumeration के दौरान connection string print किए बिना या database query किए बिना, active configuration source, database role के वास्तविक अधिकार, अलग से recover किए गए किसी application password और उस password को किसी विशिष्ट higher-privileged Unix account द्वारा स्वीकार किए जाने की पुष्टि करें। Password-hash format Mattermost versions के साथ बदल सकता है; config path और access metadata दर्ज करें।

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

डिफ़ॉल्ट response size या किसी अन्य स्थिर baseline के आधार पर virtual-host परिणामों को फ़िल्टर करें, ताकि अनुमानित हर नाम valid न दिखे। Source map तभी उपयोगी है जब वह वास्तव में deployed हो या किसी अन्य तरीके से पढ़ा जा सके।

Reverse proxies यह बदल सकते हैं कि application किन client headers पर भरोसा करता है। यह मानने से पहले कि `X-Forwarded-For`, `X-Forwarded-Host` या ऐसे ही headers caller की पहचान स्थापित करते हैं, direct और proxied requests की तुलना करें। Proxy और application configuration की एक साथ समीक्षा करें।

यदि PHP `$_SERVER['HTTP_X_FORWARDED_FOR']` को [`system()`](https://www.php.net/manual/en/function.system.php) में पास की गई string में कॉपी करता है, तो जाँचें कि क्या पहुँच योग्य request path में caller द्वारा दिया गया header स्वीकार होता है और shell metacharacters उस string तक बिना बदले पहुँचते हैं। शुरुआत में शामिल `sudo iptables` जैसा command बाद के shell-separated commands को root के रूप में नहीं चलाता; वे web worker के रूप में चलते हैं, जब तक कि कोई अलग प्रभावी sudo rule privilege escalation की अनुमति न दे। Root path का दावा करने से पहले worker की identity, सटीक `sudo -l` grant और authentication की आवश्यकता, तथा command की argument boundary की पुष्टि करें। सामान्य host enumeration के दौरान injection probe भेजे बिना source और policy का निरीक्षण करें।

## Access logs में login credentials

यदि कोई application `GET` के साथ login form submit करती है, तो username और password request URI में query parameters बन सकते हैं। `POST` request में भी query string हो सकती है; `POST` का उपयोग करने से URI में गलती से रखी गई secret छिपती नहीं है—इसमें किसी असंबंधित form field में दर्ज password भी शामिल है। [Apache का सामान्य access-log request line](https://httpd.apache.org/docs/2.4/logs.html), जब configured format में `%r` का उपयोग होता है, तो query string समेत method और URI रिकॉर्ड करता है। इसलिए, कुछ Linux systems में `adm` group के ज़रिए, उन logs को पढ़ने की अनुमति वाला account credential का सुराग पा सकता है। वास्तविक log format और permissions जाँचें, फिर पुष्टि करें कि value secret है, account उसे स्वीकार करता है, और वह privilege boundary पार करती है। यह न मानें कि request body log हुई थी और संभावित values को shared output में कॉपी न करें।

केवल पढ़े जा सकने वाले access logs का निरीक्षण करें और credential values को shared command output से बाहर रखें। लंबी request lines में referrer और user agent भी हो सकते हैं, इसलिए short-line filter से वही request छूट सकती है जिसमें आपकी रुचि है। Apache, httpd और Nginx access logs के सामान्य स्थान `/var/log/apache2/access.log`, `/var/log/httpd/access_log` और `/var/log/nginx/access.log` हैं। Rotated logs में पुराने credentials हो सकते हैं। [LFI के ज़रिए log-file access](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay), उसी data तक पहुँचने का एक संबंधित रास्ता है।

Application authentication logs में failed login के दौरान **username** field में गलती से दर्ज किया गया password भी सामने आ सकता है। पहले पुष्टि करें कि log पढ़ा जा सकता है और उसका format submitted username रिकॉर्ड करता है; स्थानीय रूप से केवल एक छोटा, प्रासंगिक हिस्सा देखें और संभावित credentials को shared output में कॉपी न करें। Password जैसा दिखने वाला username एक सुराग है, valid password या अधिक privilege का प्रमाण नहीं। किसी transition का दावा करने से पहले इच्छित account और उस विशिष्ट service या Unix account में password reuse की पुष्टि करें।

जब किसी अन्य identity के अंतर्गत scheduled client उस endpoint पर credentials submit करता हो, तो writable web login handler की अलग से समीक्षा करें। **Active** handler पर write access, client का वास्तविक schedule और request path, वह किसके credentials भेजता है, और क्या वह application password स्वतंत्र रूप से अधिक privileged operating-system account के लिए valid है—इन सबकी पुष्टि करें। केवल writable page या recurring process से ऐसा transition स्थापित नहीं होता। Passive inventory में handler बदले या passwords इकट्ठा किए बिना path permissions और job metadata दर्ज करें।

FTP event logging सक्षम होने पर Suricata के EVE JSON logs, FTP `USER` और `PASS` commands को उनके `command_data` सहित रिकॉर्ड कर सकते हैं। स्थानीय रूप से छोटा, प्रासंगिक हिस्सा देखने से पहले rotated या compressed files समेत `/var/log/suricata/eve*.json*` की readability जाँचें। पढ़ी जा सकने वाली EVE file केवल एक सुराग है: पुष्टि करें कि FTP events log किए गए थे, data में उपयोगी credential शामिल है, और वह privilege boundary पार करता है। Shared enumeration output में `command_data` प्रिंट करने से बचें। Suricata [FTP event fields](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) और [EVE rotation तथा filename variants](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html) का दस्तावेज़ देता है।

## Generated Apache configuration और piped logs

[remco](https://github.com/HeavyHorst/remco) key/value backend पर नज़र रख सकता है, template को Apache configuration file में render कर सकता है और reload command चला सकता है। चल रहे remco process की identity, उसके configured template source और destination, निगरानी किए जा रहे key prefixes, और यह जाँचें कि backend value सीधे `ServerName` जैसे Apache directive में डाली जाती है या नहीं। केवल local backend listener से यह साबित नहीं होता कि मौजूदा user किसी watched key को लिख सकता है; escalation का दावा करने से पहले backend authentication और permissions की पुष्टि करें।

Writable backend value में unescaped newline, एक इच्छित directive value को अतिरिक्त Apache directives में बदल सकती है। [Apache piped logs](https://httpd.apache.org/docs/2.4/logs.html#piped) विशेष रूप से संवेदनशील हैं: `|` command वाला `CustomLog` या `ErrorLog`, parent httpd identity—अक्सर root—के अंतर्गत helper शुरू करता है; `|$` Apache को shell इस्तेमाल करने के लिए कहता है। Enumeration के दौरान backend data बदले या service restart किए बिना generated configuration और उसके reload path की समीक्षा करें। पूरा piped command निजी रखें, क्योंकि उसके arguments में secrets हो सकते हैं।

## Authentication और service identities

Monit की control file आम तौर पर `~/.monitrc` या `/etc/monitrc` होती है, लेकिन `monit -c` से कोई दूसरा path चुना जा सकता है। पढ़ी जा सकने वाली file में उसके web interface के लिए `set httpd` और `allow user:password` entries हो सकती हैं, जो अक्सर local port 2812 पर उपलब्ध होता है। File की समीक्षा से पहले उसके owner और permissions जाँचें, और password values को shared enumeration output से बाहर रखें। Web credentials केवल configured Monit role देते हैं; read-only users control actions नहीं चला सकते। अलग Unix-account escalation के लिए password reuse की पुष्टि, या ऐसा privileged Monit action ज़रूरी है जिसे authenticated role वास्तव में चला सके। [Monit control-file और authentication documentation](https://www.mmonit.com/monit/documentation/monit.html) देखें।

Webmin के लिए `/etc/webmin/miniserv.conf` server settings बताती है और `/etc/webmin/webmin.acl` दर्ज करती है कि users किन modules तक पहुँच सकते हैं; [Webmin module-grant boundary का दस्तावेज़ देता है](https://webmin.com/docs/development/creating-modules/). Unix password या पढ़ी जा सकने वाली ACL file अपने-आप Webmin session नहीं देती। वास्तविक authentication mapping, पहुँच योग्य listener, authenticated account, प्रभावी Package Updates module permission, installed code या vendor fix, और Webmin process identity की पुष्टि करें। प्रभावित builds में 1.910 तक, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) ने उस module permission वाले account को उसके update handler के ज़रिए commands चलाने की अनुमति दी। Passive enumeration के दौरान credentials प्रिंट किए या update आज़माए बिना configuration paths और permissions दर्ज करें।

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) service-specific authentication को नियंत्रित करता है; writable policy या module paths login behavior बदल सकते हैं।
- LDAP/SSSD configuration directory endpoints, bind identities और access rules उजागर कर सकती है। बरामद bind password से मौजूदा OS account से आगे LDAP queries की जा सकती हैं; सटीक bind identity और directory ACLs जाँचें। Secrets देखने से पहले file permissions की समीक्षा करें; [Linux Active Directory](../user-information/linux-active-directory.md) और [FreeIPA](freeipa-pentesting.md) में ticket और directory use शामिल हैं।
- Postfix aliases प्राप्त mail को local commands तक pipe कर सकते हैं। यदि कम privilege वाला user संदर्भित script बदल सकता है, तो mail delivery उस user का code delivery identity के तहत trigger कर सकती है। इस path का दावा करने से पहले alias maps और script ownership की समीक्षा करें; [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md) देखें।
- Jenkins और अन्य CI services jobs को किसी शक्तिशाली local account के तहत चला सकती हैं। Pipeline या plugin की जाँच से पहले service user, writable job/workspace paths और local administration interface देखें। साथ ही **job के लिए उपलब्ध credentials** और वह account भी जाँचें जिसके रूप में वे authenticate कर सकते हैं: [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) का उपयोग करने वाला Pipeline, host को SSH credential के user के रूप में access कर सकता है, भले ही Jenkins स्वयं कम privilege वाले Unix account के तहत चलता हो। Host privilege escalation का दावा करने से पहले पुष्टि करें कि मौजूदा Jenkins identity के पास Pipeline बदलने के लिए `Job/Create`, `Job/Configure` या कोई अन्य प्रभावी रास्ता है, credential उस job के scope में है, और target SSH account key स्वीकार करता है। केवल credential का display name या ID इनमें से किसी भी शर्त को साबित नहीं करता। Jenkins चेतावनी देता है कि job creators और अक्सर job configurators अपने scope में उपलब्ध credentials का मनमाने ढंग से उपयोग कर सकते हैं; इसलिए service UID जितना ही [credential scope](https://www.jenkins.io/doc/book/security/credentials/) और [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) भी महत्वपूर्ण हैं। Shared enumeration output में credential values और private keys शामिल न करें।

## Gogs repository file writes

Local Gogs service के लिए `gogs web` process owner का मिलान executable version और `custom/conf/app.ini` से करें। Configuration service identity, repository root, listener address और registration disabled है या नहीं—यह उजागर कर सकती है। केवल loopback पर सुनने वाला listener भी local users के लिए reachable होता है। 0.13.3 तक के Gogs versions में authenticated `PutContents` symlink file-write issue है ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): repository writer एक symlink commit करके API write को उसके ज़रिए निर्देशित कर सकता है। परिणामी file access को Gogs process के privileges मिलते हैं, इसलिए root-owned instance पर तुरंत ध्यान देना चाहिए। Usable path का दावा करने से पहले deployed fix और authentication requirements की पुष्टि करें; API error यह साबित नहीं करता कि file write विफल हुआ।

## Gitea repository-description XSS and privileged viewers

Gitea 1.22.0 में repository description में stored JavaScript की अनुमति थी ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); 1.22.1 में इसे ठीक किया गया। Description edit कर सकने वाला user, अधिक privileged browser session को प्रभावित कर सकता है, यदि वह user repository देखे और malicious link सक्रिय करे। फिर उस browser identity से private repository content या अन्य application data उजागर हो सकता है। अलग से local escalation के लिए उस content के ज़रिए उपलब्ध credential या permission चाहिए, जैसे दोबारा इस्तेमाल किया गया administrator password; केवल Gitea process owner होना root impact साबित नहीं करता। इस chain का दावा करने से पहले deployed version, description-edit access, viewer workflow और वास्तविक browser interaction जाँचें।

## Cobbler provisioning API

Cobbler की management service XML-RPC API उजागर करती है, आमतौर पर port `25151` पर। Impact का आकलन करने से पहले listener और `cobblerd` process owner जाँचें; केवल loopback पर उपलब्ध API को भी host का user access कर सकता है। `/etc/cobbler/modules.conf` में authentication और authorization modules, `/etc/cobbler/settings` या `/etc/cobbler/settings.yaml` में service settings, और `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` तथा `/var/lib/cobbler/web.ss` की permissions की समीक्षा करें। Digest और shared-secret files में credential material होता है, इसलिए default रूप से उनकी सामग्री दिखाए बिना उनकी readability दर्ज करें।

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** Cobbler 3.0.0 से 3.2.2 और 3.3.0 से 3.3.6 में XML-RPC authentication bypass है। Shared-secret पढ़ने में त्रुटि होने पर अनुमानित मान `-1` लौटाया जाता था, जिसे API password के रूप में स्वीकार करता था। इसके सुधार 3.2.3 और 3.3.7 में हैं। Package version केवल शुरुआती संकेत है; जोखिम की रिपोर्ट करने से पहले deployed code और backported fix की पुष्टि करें।

जब `cobblerd` root के रूप में चलता है, तो authenticated API session एक privileged execution path बन सकता है। प्रभावित implementations में, `background_import` user-controlled `rsync_flags` को shell command में भेजता है, और user-controlled Cheetah autoinstall template को render करने पर Python evaluate हो सकता है। इनमें से किसी भी path को test करने से पहले API permissions और installed version जाँचें। Management API तक पहुँच सीमित करें, authentication bypass को patch करें, और configuration तथा credential files को केवल service administrators के लिए readable रखें।

## Motion और motionEye configuration

`/etc/motioneye/motioneye.conf` में `conf_path` देखें, फिर उस directory में `motion.conf` और कुछ `camera-*.conf` files जाँचें। रिपोर्ट करें कि readable `# @admin_password` hash मौजूद है या नहीं, लेकिन उसे प्रिंट न करें। [पुराने motionEye releases इन files को व्यापक read permissions के साथ लिखते थे](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); इसका fix 0.44.0 में है। Motion की `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method`, और `webcontrol_localhost` settings को साथ में जाँचें: authentication बंद होने पर advanced control (`2` या `3`) किसी local user को शक्तिशाली operations करने दे सकता है, loopback listener पर भी। [Motion में values और defaults के बारे में जानकारी दी गई है](https://motion-project.github.io/motion_config.html)।

0.43.1b5 से पुराने motionEye में, Motion द्वारा camera filename setting को process करने पर admin session उसे command execution में बदल सकता था ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx))। Escalation का दावा करने से पहले running version, service identity, usable authentication path, और camera configured है या नहीं, इसकी पुष्टि करें। केवल configuration से यह साबित नहीं होता कि service चल रही है या privileged है।

Service name या installed package केवल शुरुआती संकेत है। Privilege boundary, reachable input, process identity, writable configuration, और अंततः उसके नियंत्रण में आने वाली command या file के मेल से तय होती है।

## Local AWS emulators और stored credentials

Host user, container में चल रहे AWS-compatible emulator तक उसके published loopback endpoint के ज़रिये पहुँच सकता है। [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) या [KMS](https://docs.localstack.cloud/aws/services/kms/) तक पहुँच का आकलन करने से पहले, live listener, client द्वारा चुने गए endpoint और account, तथा emulator की installed authorization settings का मिलान करें। LocalStack में, [IAM policy enforcement एक अलग setting है](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); केवल credential file, IAM policy, या listener के आधार पर प्रभावी API permissions का अनुमान न लगाएँ। Installed release और configuration का व्यवहार सत्यापित करें।

Stored secret, local escalation के लिए तभी उपयोगी है जब मौजूदा API identity उसे retrieve कर सके और कोई अलग higher-privileged account प्राप्त credential स्वीकार करे। Encrypted local blob के लिए file read access, उससे मेल खाती usable KMS key और algorithm, तथा प्रभावी decrypt access भी आवश्यक हैं। [Asymmetric KMS key](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) के लिए, decrypt request में blob को encrypt करने के लिए इस्तेमाल किया गया algorithm निर्दिष्ट करना होगा। Routine enumeration के दौरान automatic host inventory को process, listener, configuration-path, और file-permission evidence तक सीमित रखें; secret values या decrypted plaintext न माँगें और न प्रिंट करें।
