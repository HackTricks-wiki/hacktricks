# Servizi Web locali e di autenticazione

{{#include ../../banners/hacktricks-training.md}}

Una shell Linux offre una visuale sull'host dei servizi Web e di autenticazione: argomenti dei processi, listener, file delle unità, configurazione, log e interfacce accessibili solo localmente. Usa questa visuale per collegare un servizio raggiungibile all'account e ai file che usa effettivamente.

## Mappare lo stack Web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Esamina i nomi dei virtual host, le root dei documenti, le route proxy, le directory di upload, le impostazioni di esecuzione PHP e i file di configurazione contenenti credenziali. Un listener loopback potrebbe essere raggiungibile tramite un proxy o un tunnel SSH. Per testare un virtual host nominato contro un listener locale, invia l’header `Host` previsto oppure usa `curl --resolve` con l’indirizzo e la porta corretti. L’enumerazione dei virtual host può inoltre rivelare nomi assenti dalla risposta predefinita. Verifica se Apache consente gli override tramite `.htaccess` e se i percorsi di upload possono eseguire PHP, prima di considerare una directory di upload scrivibile come esecuzione di codice. Una source map JavaScript distribuita potrebbe esporre percorsi dei sorgenti o segreti lato client; considera i valori recuperati come indizi e verifica i privilegi effettivi. Per controlli specifici sul web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Con Apache e [mpm-itk](https://mpm-itk.sesse.net/), una direttiva `AssignUserID` attiva può eseguire un virtual host con un utente e un gruppo diversi. Se un account con privilegi inferiori può scrivere uno script nel `DocumentRoot` di quel virtual host, verifica se una route raggiungibile lo esegue effettivamente con l’identità assegnata. Conferma che il modulo sia caricato, la configurazione effettiva del virtual host (compresi gli override dell’identità basati su espressioni), i permessi di scrittura e attraversamento delle directory, l’handler dello script e l’accessibilità del listener. Una direttiva evidenziata o una directory scrivibile, da sole, non dimostrano l’esecuzione tra utenti diversi.

Una directory home pubblicata tramite un web server può esporre archivi di backup di file di identità SSH, anche quando la directory `.ssh` attiva è privata. Per esempio, l’impostazione [`homedirs_public` di Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleziona una sottodirectory da servire dalle directory home degli utenti. Trovare un archivio basandosi solo sul percorso è un indizio: verifica la mappatura effettiva del server, la leggibilità locale o l’autorizzazione HTTP, il contenuto dell’archivio, la passphrase della chiave privata e se l’account corrispondente accetta davvero la chiave. Durante la normale enumerazione dell’host, non estrarre archivi né stampare il contenuto delle chiavi.

Un backup leggibile di un’applicazione web locale con privilegi superiori può rivelare la logica di autenticazione e lettura dei file anche quando il sorgente attivo è inaccessibile. Confronta il backup con il servizio distribuito prima di farvi affidamento. In particolare, merita attenzione un cookie creato cifrando testo controllato dal chiamante seguito da un segreto e da un flag di ruolo, se l’app usa blocchi ECB deterministici, restituisce cookie nuovi per testo scelto e in seguito divide il valore decifrato usando un delimitatore non sottoposto a escape. [NIST spiega la mappatura indipendente e ripetibile dei blocchi ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); questa proprietà può consentire un confronto con input scelto, ma non concede da sola un ruolo superiore. Conferma la route attiva, i prerequisiti della sessione, il parser e il flusso dei dati esatti, l’identità del servizio e un’azione privilegiata o un percorso di lettura dei file separati. L’inventario passivo dovrebbe riportare i metadati dei backup e la titolarità del listener senza leggere il contenuto degli archivi né inviare probe di autenticazione.

Lo stesso approccio di analisi del sorgente si applica a un servizio locale privilegiato **non HTTP**, per esempio un’interfaccia personalizzata basata su SSH. Se un backup accessibile del sorgente mostra un comando che accetta un percorso di file scelto dal chiamante, controlla il gate di autenticazione, il modo in cui risolve il percorso e se verifica che il file risolto rimanga all’interno della directory prevista prima di aprirlo. In Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normalizza un percorso, ma non ne impone il contenimento. Conferma che il backup corrisponda alla build in esecuzione, che il listener sia raggiungibile, che il comando sia utilizzabile dall’account con privilegi inferiori e che il processo possa leggere il file di destinazione; il possesso di una chiave SSH leggibile è una questione distinta, legata alle regole di accesso. Riporta i percorsi degli archivi sorgente e la titolarità del servizio senza estrarre il contenuto degli archivi o le chiavi nell’output automatizzato.

Un pool PHP-FPM in ascolto su TCP loopback può essere raggiunto da un altro account locale anche quando il sito web richiede autenticazione. [PHP avverte che un client in grado di connettersi a FastCGI può controllare le impostazioni delle richieste, incluso `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Esamina le impostazioni `listen` e `listen.allowed_clients` del pool insieme al listener attivo, all’UID dei worker, a un percorso di script esistente e a eventuali restrizioni `security.limit_extensions` o `php_admin_value`. I file di configurazione dei pool possono contenere credenziali nelle direttive `env[...]`, quindi l’inventario automatizzato dovrebbe riportarne i percorsi, non il contenuto. Un file di configurazione o una porta, da soli, non dimostrano un percorso di esecuzione tra utenti diversi; per i dettagli sul protocollo, consulta la [guida FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md).

Per un’API locale privilegiata, analizza sia l’autorizzazione sia l’esecuzione del codice. Un ruolo del database modificabile dall’account con privilegi inferiori può sbloccare una route API, ma il confine successivo dipende dall’implementazione della route. Per esempio, unire il JSON della richiesta a un oggetto JavaScript e poi chiamare [`child_process.exec`](https://nodejs.org/api/child_process.html) merita un’analisi del [flusso di dati da prototype pollution a esecuzione](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la libreria/versione effettivamente usata per l’unione, la validazione dell’input, la route raggiungibile, l’identità del processo e le opzioni del processo figlio; un listener Node di proprietà di root o il nome di una dipendenza vulnerabile sono soltanto indizi.

Gli archivi CMS basati su file possono contenere verificatori di password di amministratori al di fuori dei consueti file di configurazione `.php`. Tra gli esempi ci sono `data/database.js` o `data/settings/pass.php` di un sito. Prima di esaminarli manualmente, controlla la proprietà e la leggibilità dei file e non includere gli hash nell’output automatizzato condiviso. Una password applicativa recuperabile rappresenta un confine di privilegi distinto da quello di un account Unix: verifica ogni eventuale riutilizzo dichiarato rispetto all’account specifico e al metodo di autenticazione consentito.

Il controller di autenticazione di un’applicazione può anche contenere una password di accesso letterale nel codice sorgente anziché in un file di configurazione. Se un utente con privilegi inferiori può leggere il controller distribuito, esamina localmente il confronto usato per l’autenticazione e non includere eventuali valori nell’output di enumerazione condiviso. Prima di dichiarare un’escalation locale, conferma che il percorso di codice sia attivo, che la password sia valida per l’applicazione e che un account Unix specifico con privilegi superiori accetti davvero la stessa password. Il solo nome del file del controller è un semplice indizio da approfondire.

Dolibarr archivia le impostazioni di connessione al database, incluso `dolibarr_main_db_pass`, in `htdocs/conf/conf.php` ([riferimento alla configurazione](https://wiki.dolibarr.org/index.php/Configuration_file)). Un file leggibile è un indizio relativo alle credenziali; solo un riutilizzo verificato della password di un account separato o un altro permesso del database lo trasformerebbe in un’escalation dei privilegi locali. Prima controlla i permessi ed evita di stampare il valore nell’output automatizzato.

Il file di configurazione del pacchetto Linux di GitLab è normalmente `/etc/gitlab/gitlab.rb`, ma le distribuzioni possono conservarne copie leggibili altrove. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) che questo file può contenere `gitlab_rails['smtp_password']`, anche se le impostazioni SMTP cifrate potrebbero conservare la password al di fuori del file in testo in chiaro. Considera una configurazione leggibile un indizio relativo alle credenziali: verifica che sia attiva, che la credenziale sia aggiornata e che un account specifico con privilegi superiori la accetti prima di dichiarare un riutilizzo della password. Separatamente, [GitLab esegue `gitlab.rb` come codice Ruby con privilegi root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un file attivo scrivibile o un `from_file` incluso richiede un effettivo percorso di riconfigurazione privilegiato prima di poter essere considerato un risultato di esecuzione. L’anteprima di una configurazione può esporre valori di credenziali: considera sensibile il suo output e condividi invece percorsi e permessi.

Un’installazione Mattermost self-hosted può conservare `SqlSettings.DataSource` in `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) sia questo percorso abituale sia le distribuzioni che archiviano invece la configurazione attiva in un database. Un file leggibile può esporre una credenziale del database dell’applicazione, ma non dimostra l’accesso al database né l’accesso Unix root. Verifica la fonte della configurazione attiva, i permessi effettivi del ruolo del database, eventuali password applicative recuperate separatamente e se una password del genere funziona per un account Unix specifico con privilegi superiori. Il formato degli hash delle password può cambiare tra versioni di Mattermost; durante l’enumerazione, registra il percorso del file di configurazione e i metadati di accesso senza stampare la stringa di connessione né interrogare il database.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra i risultati dei virtual host confrontandoli con la dimensione della risposta predefinita o con un'altra baseline stabile, così che ogni nome indovinato non sembri valido. Una source map è utile solo se è effettivamente distribuita o comunque leggibile.

I reverse proxy possono modificare quali header del client un'applicazione considera attendibili. Confronta le richieste dirette e quelle inoltrate dal proxy prima di presumere che `X-Forwarded-For`, `X-Forwarded-Host` o header simili identifichino chi effettua la richiesta. Esamina insieme la configurazione del proxy e quella dell'applicazione.

Se PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` in una stringa passata a [`system()`](https://www.php.net/manual/en/function.system.php), verifica se il percorso della richiesta raggiungibile consente a chi la invia di fornire un header e se i metacaratteri della shell arrivano inalterati a quella stringa. Un comando come `sudo iptables` inserito all'inizio **non** fa sì che i comandi successivi separati dalla shell vengano eseguiti come root: questi vengono eseguiti con l'identità del web worker, a meno che una regola sudo effettiva separata non consenta l'escalation. Verifica l'identità del worker, l'autorizzazione esatta mostrata da `sudo -l` e i requisiti di autenticazione, nonché i limiti degli argomenti del comando, prima di affermare che esiste un percorso verso root. Esamina il codice sorgente e le policy senza inviare probe di injection durante la normale enumerazione dell'host.

## Credenziali di login nei log di accesso

Se un'applicazione invia un modulo di login con `GET`, il nome utente e la password possono diventare parametri della query nell'URI della richiesta. Anche una richiesta `POST` può contenere una query string: usare `POST` non nasconde un segreto inserito per errore nell'URI, inclusa una password digitata in un campo di un modulo non pertinente. La [riga di richiesta del log di accesso comune di Apache](https://httpd.apache.org/docs/2.4/logs.html) registra il metodo e l'URI, inclusa la query string, quando il formato configurato usa `%r`. Un account autorizzato a leggere tali log, ad esempio tramite il gruppo `adm` su alcuni sistemi Linux, potrebbe quindi trovare un indizio su una credenziale. Controlla il formato effettivo del log e i permessi, quindi verifica che il valore sia un segreto, che l'account lo accetti e che consenta di attraversare un confine di privilegi. Non presumere che il corpo della richiesta sia stato registrato e non copiare i valori candidati in output condivisi.

Esamina solo i log di accesso leggibili e non includere i valori delle credenziali nell'output condiviso dei comandi. Le righe di richiesta lunghe possono contenere anche un referrer e uno user agent, quindi un filtro per righe brevi può nascondere proprio la richiesta d'interesse. I percorsi comuni dei log di accesso di Apache, httpd e Nginx sono `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. I log ruotati possono contenere credenziali meno recenti. [Accesso ai file di log tramite LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) è un percorso correlato per accedere agli stessi dati.

Anche i log di autenticazione delle applicazioni possono esporre per errore una password digitata nel campo **username** durante un tentativo di login non riuscito. Per prima cosa, accerta che il log sia leggibile e che il suo formato registri il nome utente inviato; esamina localmente solo una piccola porzione pertinente e non copiare le credenziali candidate in output condivisi. Un nome utente che sembra una password è un indizio, non la prova che la password sia valida o che abbia privilegi maggiori. Prima di affermare che è possibile un passaggio di privilegi, verifica l'account previsto e l'eventuale riutilizzo della password per lo specifico servizio o account Unix.

Un handler di login web scrivibile richiede un'analisi separata quando un client pianificato, eseguito con un'altra identità, invia credenziali a quell'endpoint. Verifica l'accesso in scrittura all'handler **attivo**, la pianificazione effettiva del client e il percorso della richiesta, di chi siano le credenziali inviate e se quella password dell'applicazione sia valida anche per un account del sistema operativo con privilegi superiori. Una pagina scrivibile o un processo ricorrente, da soli, non dimostrano che il passaggio sia possibile. Durante l'inventario passivo, riporta i permessi del percorso e i metadati del job senza modificare l'handler né raccogliere password.

I log JSON EVE di Suricata possono registrare anche i comandi FTP `USER` e `PASS` con il relativo `command_data`, se la registrazione degli eventi FTP è abilitata. Verifica la leggibilità di `/var/log/suricata/eve*.json*`, inclusi i file ruotati o compressi, prima di esaminarne localmente una piccola porzione pertinente. Un file EVE leggibile è solo un indizio: conferma che gli eventi FTP siano stati registrati, che i dati includano credenziali utilizzabili e che consentano di attraversare un confine di privilegi. Evita di stampare `command_data` nell'output condiviso dell'enumerazione. Suricata documenta i [campi degli eventi FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e le [varianti di rotazione e dei nomi dei file EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configurazione Apache generata e log con pipe

[remco](https://github.com/HeavyHorst/remco) può monitorare un backend chiave/valore, generare un file di configurazione Apache da un template ed eseguire un comando di reload. Esamina l'identità del processo remco in esecuzione, la sorgente e la destinazione del template configurato, i prefissi delle chiavi monitorati e se un valore del backend viene inserito direttamente in una direttiva Apache come `ServerName`. La sola presenza di un listener del backend locale non dimostra che l'utente corrente possa scrivere una chiave monitorata; verifica l'autenticazione e i permessi del backend prima di affermare che sia possibile un'escalation.

Un newline non sottoposto a escaping in un valore scrivibile del backend può trasformare un valore previsto per una singola direttiva in direttive Apache aggiuntive. I [log con pipe di Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) sono particolarmente sensibili: `CustomLog` o `ErrorLog` con un comando preceduto da `|` avvia un helper con l'identità del processo httpd padre, spesso root; `|$` chiede ad Apache di usare una shell. Esamina la configurazione generata e il relativo percorso di reload senza modificare i dati del backend né riavviare il servizio durante l'enumerazione. Mantieni privato il comando completo della pipe, perché i suoi argomenti potrebbero contenere segreti.

## Autenticazione e identità dei servizi

Il file di controllo di Monit si trova di solito in `~/.monitrc` o `/etc/monitrc`, ma `monit -c` può selezionare un altro percorso. Un file leggibile può contenere voci `set httpd` e `allow user:password` per la sua interfaccia web, spesso sulla porta locale 2812. Controlla il proprietario e i permessi del file prima di esaminarlo e non includere i valori delle password nell'output condiviso dell'enumerazione. Le credenziali web concedono solo il ruolo Monit configurato; gli utenti di sola lettura non possono eseguire azioni di controllo. Per un'escalation tramite un account Unix distinto, occorre verificare il riutilizzo della password oppure un'azione Monit privilegiata che il ruolo autenticato possa effettivamente avviare. Consulta la [documentazione di Monit sul file di controllo e sull'autenticazione](https://www.mmonit.com/monit/documentation/monit.html).

Per Webmin, `/etc/webmin/miniserv.conf` identifica le impostazioni del server e `/etc/webmin/webmin.acl` registra i moduli a cui gli utenti possono accedere; [Webmin documenta i limiti delle autorizzazioni sui moduli](https://webmin.com/docs/development/creating-modules/). Una password Unix o un file ACL leggibile non concedono di per sé una sessione Webmin. Verifica la mappatura effettiva dell'autenticazione, il listener raggiungibile, l'account autenticato, i permessi effettivi del modulo Package Updates, il codice installato o la correzione del vendor e l'identità del processo Webmin. Nelle build vulnerabili fino alla 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) consentiva a un account con i permessi di quel modulo di eseguire comandi tramite il suo handler di aggiornamento. Durante l'enumerazione passiva, riporta i percorsi e i permessi di configurazione senza stampare credenziali né tentare un aggiornamento.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) gestisce l'autenticazione specifica dei servizi; policy o percorsi dei moduli scrivibili possono modificare il comportamento del login.
- La configurazione di LDAP/SSSD può rivelare endpoint di directory, identità di bind e regole di accesso. Una password di bind recuperata può consentire query LDAP oltre quelle permesse dall'account OS corrente; verifica l'identità di bind esatta e le ACL della directory. Controlla i permessi dei file prima di esaminare i segreti; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) trattano l'uso di ticket e directory.
- Gli alias di Postfix possono inoltrare le email ricevute a comandi locali. Se un utente con privilegi inferiori può modificare lo script a cui fanno riferimento, la consegna delle email può eseguire il suo codice con l'identità di consegna. Controlla le mappe degli alias e la proprietà degli script prima di affermare che il percorso sia sfruttabile; vedi [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e altri servizi CI possono eseguire job con un account locale privilegiato. Esamina l'utente del servizio, i percorsi scrivibili dei job/workspace e l'interfaccia di amministrazione locale prima di testare una pipeline o un plugin. Esamina anche le **credenziali disponibili a un job** e l'account con cui possono autenticarsi: una Pipeline che usa il [passaggio SSH Agent](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) può accedere a un host come utente della credenziale SSH, anche quando Jenkins stesso viene eseguito con un account Unix meno privilegiato. Prima di affermare che vi sia una privilege escalation sull'host, verifica che l'identità Jenkins corrente disponga di `Job/Create`, `Job/Configure` o di un altro modo effettivo per modificare la Pipeline, che la credenziale sia disponibile per quel job e che l'account SSH di destinazione accetti la chiave. Il solo nome visualizzato o ID di una credenziale non dimostra nessuna di queste condizioni. Jenkins avverte che chi crea un job e, spesso, chi lo configura può usare arbitrariamente le credenziali disponibili nel suo ambito; perciò [l'ambito delle credenziali](https://www.jenkins.io/doc/book/security/credentials/) e [l'affidabilità delle Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) sono importanti quanto l'UID del servizio. Non includere valori delle credenziali e chiavi private nell'output di enumerazione condiviso.

## Scrittura di file nei repository Gogs

Per un servizio Gogs locale, confronta il proprietario del processo `gogs web` con la versione dell'eseguibile e `custom/conf/app.ini`. La configurazione può rivelare l'identità del servizio, la root del repository, l'indirizzo di ascolto e se la registrazione è disabilitata. Anche un listener limitato al loopback è raggiungibile dagli utenti locali. Le versioni di Gogs fino alla 0.13.3 incluse presentano un problema di scrittura di file tramite symlink in `PutContents` autenticato ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): chi può scrivere nel repository può eseguire il commit di un symlink e poi indirizzare tramite esso la scrittura dell'API. L'accesso al file risultante avviene con i privilegi del processo Gogs, quindi un'istanza eseguita da root richiede attenzione immediata. Verifica la correzione installata e i requisiti di autenticazione prima di affermare che il percorso sia utilizzabile; un errore API non dimostra che la scrittura del file sia fallita.

## XSS nella descrizione dei repository Gitea e visualizzatori privilegiati

Gitea 1.22.0 consentiva l'inserimento di JavaScript persistente nella descrizione di un repository ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versione 1.22.1 ha corretto il problema. Un utente che può modificare una descrizione può influire su una sessione browser più privilegiata se l'utente visualizza il repository e attiva il link malevolo. Tale identità del browser può quindi esporre contenuti di repository privati o altri dati dell'applicazione. Per una privilege escalation locale distinta è necessaria una credenziale o un permesso raggiungibile tramite quei contenuti, per esempio una password di amministratore riutilizzata; il solo proprietario del processo Gitea non dimostra un impatto su root. Verifica la versione installata, i permessi di modifica della descrizione, il flusso di visualizzazione e l'effettiva interazione con il browser prima di affermare che la catena sia sfruttabile.

## API di provisioning Cobbler

Il servizio di gestione di Cobbler espone un'API XML-RPC, comunemente sulla porta `25151`. Controlla il listener e il proprietario del processo `cobblerd` prima di valutarne l'impatto; un'API limitata al loopback può comunque essere raggiunta da un utente dell'host. Esamina i moduli di autenticazione e autorizzazione in `/etc/cobbler/modules.conf`, le impostazioni del servizio in `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml` e i permessi su `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. I file digest e quelli contenenti segreti condivisi contengono materiale relativo alle credenziali, quindi annota se sono leggibili senza stamparne i contenuti per impostazione predefinita.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** è un bypass dell'autenticazione XML-RPC in Cobbler dalla versione 3.0.0 alla 3.2.2 e dalla 3.3.0 alla 3.3.6. Un errore di lettura del segreto condiviso restituiva il valore prevedibile `-1`, che l'API accettava come password. Le versioni che risolvono il problema sono la 3.2.3 e la 3.3.7. La versione del pacchetto è solo un indizio: prima di segnalare un'esposizione, verifica il codice distribuito e l'eventuale backport della correzione.

Una sessione API autenticata può consentire l'esecuzione di codice con privilegi se `cobblerd` viene eseguito come root. Nelle implementazioni vulnerabili, `background_import` passa `rsync_flags` controllato dall'utente a un comando shell, mentre il rendering di un template di autoinstall Cheetah controllato dall'utente può eseguire Python. Prima di testare uno dei due percorsi, verifica i permessi dell'API e la versione installata. Limita l'accesso all'API di gestione, applica la patch per il bypass dell'autenticazione e consenti la lettura dei file di configurazione e delle credenziali solo agli amministratori del servizio.

## Configurazione di Motion e motionEye

Esamina `/etc/motioneye/motioneye.conf` per individuare `conf_path`, quindi controlla `motion.conf` e un piccolo numero di file `camera-*.conf` in quella directory. Segnala se è presente un hash `# @admin_password` leggibile, senza stamparlo. [Le versioni precedenti di motionEye creavano questi file con permessi di lettura ampi](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la correzione è inclusa nella versione 0.44.0. Controlla insieme le impostazioni Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost`: il controllo avanzato (`2` o `3`) con l'autenticazione disabilitata può esporre operazioni potenti a un utente locale, anche se il listener è in loopback. [Motion documenta i valori e le impostazioni predefinite](https://motion-project.github.io/motion_config.html).

Una sessione admin su motionEye precedente alla versione 0.43.1b5 poteva trasformare un'impostazione del nome file di una camera in esecuzione di comandi quando Motion la elaborava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Prima di affermare che è possibile un'escalation, verifica la versione in esecuzione, l'identità del servizio, un percorso di autenticazione utilizzabile e se è configurata una camera. La sola configurazione non dimostra che il servizio sia in esecuzione o disponga di privilegi elevati.

Il nome di un servizio o un pacchetto installato sono solo indizi. Il confine dei privilegi dipende dalla combinazione di input raggiungibile, identità del processo, configurazione scrivibile e comando o file che controlla in ultima istanza.

## Emulatori AWS locali e credenziali memorizzate

Un utente host potrebbe raggiungere un emulatore compatibile con AWS in esecuzione in un container tramite il suo endpoint loopback pubblicato. Prima di valutare l'accesso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), correla il listener attivo, l'endpoint e l'account selezionati dal client e le impostazioni di autorizzazione installate nell'emulatore. In LocalStack, [l'applicazione delle policy IAM è un'impostazione separata](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/): non dedurre i permessi API effettivi basandoti solo su un file di credenziali, una policy IAM o un listener. Verifica il comportamento della versione e della configurazione installate.

Un segreto memorizzato è utile per un'escalation locale solo se l'identità API corrente può recuperarlo e un account separato con privilegi superiori accetta la credenziale ottenuta. Per decifrare un blob locale occorrono anche l'accesso in lettura al file, la chiave KMS corrispondente e utilizzabile, l'algoritmo corretto e l'effettivo permesso di decifrazione. Per una [chiave KMS asimmetrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la richiesta di decifrazione deve specificare l'algoritmo usato per cifrare il blob. Nell'inventario automatico degli host, limita le verifiche a processi, listener, percorsi di configurazione e permessi dei file; durante l'enumerazione ordinaria non richiedere né stampare valori segreti o testo in chiaro decifrato.
