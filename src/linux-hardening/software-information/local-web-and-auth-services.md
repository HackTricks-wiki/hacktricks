# Serviços Web e de Autenticação Locais

{{#include ../../banners/hacktricks-training.md}}

Um shell Linux oferece uma visão do host dos serviços web e de autenticação: argumentos de processos, listeners, arquivos de unidade, configurações, logs e interfaces acessíveis apenas localmente. Use essa visão para relacionar um serviço acessível à conta e aos arquivos que ele realmente usa.

## Mapear a pilha web local

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecione nomes de virtual hosts, document roots, rotas de proxy, diretórios de upload, configurações de execução do PHP e arquivos de configuração que contenham credenciais. Um listener de loopback pode ser acessível por meio de um proxy ou túnel SSH. Para testar um virtual host nomeado contra um listener local, envie o cabeçalho `Host` pretendido ou use `curl --resolve` com o endereço e a porta corretos. A enumeração de virtual hosts também pode revelar nomes ausentes da resposta padrão. Verifique se o Apache permite sobrescritas por `.htaccess` e se os caminhos de upload podem executar PHP antes de tratar um diretório de upload gravável como execução de código. Um source map de JavaScript implantado pode expor caminhos de origem ou secrets do lado do cliente; trate os valores recuperados como pistas e verifique os privilégios que eles realmente concedem. Para verificações específicas de web, consulte [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

No Apache com [mpm-itk](https://mpm-itk.sesse.net/), um `AssignUserID` ativo pode executar um virtual host com outro usuário e grupo. Se uma conta com menos privilégios puder gravar um script no `DocumentRoot` desse host, verifique se uma rota acessível realmente o executa com a identidade atribuída. Confirme se o módulo está carregado, a configuração efetiva do virtual host (incluindo substituições de identidade baseadas em expressões), as permissões de gravação e busca no diretório, o handler do script e o acesso ao listener. Uma diretiva destacada ou um diretório gravável, por si só, não comprovam execução entre usuários.

Um diretório home publicado por um servidor web pode expor arquivos de backup de identidades SSH, mesmo quando o diretório `.ssh` ativo é privado. Por exemplo, a configuração [`homedirs_public` do Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleciona um subdiretório servido a partir dos diretórios home dos usuários. Encontrar apenas o caminho de um arquivo compactado é uma pista: verifique o mapeamento efetivo do servidor, a leitura local ou a autorização HTTP, o conteúdo do arquivo compactado, a frase-senha da chave privada e se a conta correspondente realmente aceita a chave. Não extraia arquivos compactados nem imprima material de chave durante a enumeração rotineira do host.

Um backup legível de um aplicativo web local com privilégios elevados pode revelar a lógica de autenticação e leitura de arquivos, mesmo quando o código-fonte ativo não está acessível. Compare o backup com o serviço implantado antes de confiar nele. Em particular, um cookie criado criptografando texto controlado pelo solicitante seguido de um secret e um sinalizador de função merece análise se o aplicativo usar blocos ECB determinísticos, retornar cookies novos para textos escolhidos e depois dividir o valor descriptografado por um delimitador sem escape. [A NIST explica o mapeamento independente e repetível de blocos do ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); essa propriedade pode permitir uma comparação com entrada escolhida, mas, por si só, não concede uma função de maior privilégio. Confirme a rota ativa, os pré-requisitos da sessão, o parser e o fluxo de dados exatos, a identidade do serviço e uma ação privilegiada separada ou um caminho de leitura de arquivos. O inventário passivo deve informar os metadados do backup e a propriedade do listener sem ler o conteúdo do arquivo compactado nem enviar sondas de autenticação.

A mesma abordagem de revisão de código-fonte se aplica a um serviço local privilegiado **não HTTP**, como uma interface personalizada apoiada por SSH. Se um backup acessível do código-fonte mostrar um comando que aceita um caminho de arquivo escolhido pelo solicitante, verifique o controle de autenticação, como o caminho é resolvido e se o código garante que o arquivo resolvido permaneça dentro de um diretório previsto antes de abri-lo. Em Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normaliza um caminho, mas não garante que ele permaneça dentro desse diretório. Confirme se o backup corresponde à build em execução, se o listener está acessível, se a conta com menos privilégios pode usar o comando e se o processo pode ler o alvo; possuir uma chave SSH legível é uma questão separada das políticas de login. Informe os caminhos dos arquivos compactados com o código-fonte e a propriedade do serviço sem extrair o conteúdo desses arquivos ou chaves para a saída automatizada.

Um pool PHP-FPM que escuta em TCP de loopback pode ser acessado por outra conta local, mesmo quando o site exige autenticação. [O PHP alerta que um cliente capaz de se conectar ao FastCGI pode controlar as configurações da requisição, incluindo `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Analise as configurações `listen` e `listen.allowed_clients` do pool junto com o listener ativo, o UID do worker, um caminho de script existente e quaisquer restrições `security.limit_extensions` ou `php_admin_value`. Arquivos de configuração do pool podem conter credenciais em diretivas `env[...]`, portanto o inventário automatizado deve informar seus caminhos, não seu conteúdo. Um arquivo de configuração ou uma porta, por si só, não comprova um caminho de execução entre usuários; consulte o [guia do FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para detalhes do protocolo.

Para uma API local privilegiada, rastreie a autorização além da execução de código. Uma função de banco de dados que a conta com menos privilégios pode alterar pode desbloquear uma rota da API, mas o próximo limite depende da implementação dessa rota. Por exemplo, mesclar JSON da requisição em um objeto JavaScript e depois chamar [`child_process.exec`](https://nodejs.org/api/child_process.html) justifica investigar um [fluxo de dados de prototype pollution até execução](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifique a biblioteca e a versão de mesclagem reais, a validação de entrada, a rota acessível, a identidade do processo e as opções do processo filho; um listener Node de propriedade do root ou o nome de uma dependência vulnerável, por si só, é apenas uma pista.

Armazenamentos de CMS baseados em arquivos podem guardar verificadores de senha de administrador fora dos arquivos de configuração `.php` convencionais. Alguns exemplos são `data/database.js` ou `data/settings/pass.php` de um site. Verifique a propriedade e a legibilidade dos arquivos antes de analisá-los manualmente e não inclua hashes na saída compartilhada automatizada. Uma senha de aplicativo recuperável representa um limite de privilégio separado de uma conta Unix: verifique qualquer alegação de reutilização para a conta específica e o método de autenticação permitido.

O controller de autenticação de um aplicativo também pode conter uma senha de login literal no código-fonte, em vez de em um arquivo de configuração. Se um usuário com menos privilégios puder ler o controller implantado, analise localmente a comparação de autenticação e não inclua nenhum valor na saída compartilhada de enumeração. Confirme se o caminho de código está ativo, se a senha é válida para o aplicativo e se uma conta Unix separada com privilégios mais elevados realmente aceita essa mesma senha antes de alegar elevação de privilégios local. O nome de um arquivo de controller, por si só, é apenas uma pista para análise.

O Dolibarr armazena configurações de conexão com o banco de dados, incluindo `dolibarr_main_db_pass`, em `htdocs/conf/conf.php` ([referência de configuração](https://wiki.dolibarr.org/index.php/Configuration_file)). Um arquivo legível é uma pista de credencial; apenas a reutilização de senha de uma conta separada e verificada ou outra permissão de banco de dados poderia transformá-la em uma elevação de privilégios local. Primeiro, verifique as permissões e evite imprimir o valor na saída automatizada.

A configuração do pacote Linux do GitLab normalmente fica em `/etc/gitlab/gitlab.rb`, embora as implantações possam manter cópias legíveis em outros locais. [O GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que esse arquivo pode conter `gitlab_rails['smtp_password']`, embora as configurações SMTP criptografadas possam manter a senha fora do arquivo em texto simples. Trate uma configuração legível como uma pista de credencial: verifique se está ativa, se a credencial ainda é válida e se uma conta específica com privilégios mais elevados a aceita antes de alegar reutilização de senha. Separadamente, [o GitLab executa `gitlab.rb` como código Ruby sob o root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); um arquivo ativo gravável ou um `from_file` incluído exige um caminho real de reconfiguração privilegiada para constituir uma descoberta de execução. Uma prévia da configuração pode expor valores de credenciais; trate sua saída como sensível e compartilhe apenas os caminhos e as permissões.

Uma instalação self-hosted do Mattermost pode armazenar `SqlSettings.DataSource` em `/opt/mattermost/config/config.json`; [o Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esse caminho habitual quanto implantações que armazenam a configuração ativa em um banco de dados. Um arquivo legível pode expor uma credencial do banco de dados do aplicativo, mas não comprova acesso ao banco de dados nem acesso root no Unix. Verifique a origem da configuração ativa, as permissões reais da função do banco de dados, qualquer senha de aplicativo recuperada separadamente e se essa senha funciona para uma conta Unix específica com privilégios mais elevados. O formato do hash de senha pode variar entre versões do Mattermost; durante a enumeração, registre o caminho da configuração e os metadados de acesso sem imprimir a string de conexão nem consultar o banco de dados.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtre os resultados de virtual hosts em relação ao tamanho da resposta padrão ou a outra referência estável para que cada nome adivinhado não pareça válido. Um source map só é útil se estiver realmente implantado ou puder ser lido de outra forma.

Proxies reversos podem alterar quais cabeçalhos do cliente uma aplicação considera confiáveis. Compare as requisições diretas e as encaminhadas por proxy antes de presumir que `X-Forwarded-For`, `X-Forwarded-Host` ou cabeçalhos semelhantes estabelecem a identidade de quem faz a chamada. Revise em conjunto as configurações do proxy e da aplicação.

Se o PHP copiar `$_SERVER['HTTP_X_FORWARDED_FOR']` para uma string passada a [`system()`](https://www.php.net/manual/en/function.system.php), verifique se o caminho de requisição acessível permite que quem faz a chamada forneça um cabeçalho e se os metacaracteres do shell chegam inalterados a essa string. Um comando como `sudo iptables` inserido no início **não** faz com que comandos posteriores separados por shell sejam executados como root; eles são executados com a identidade do worker web, a menos que uma regra efetiva separada do sudo permita a elevação. Confirme a identidade do worker, a concessão exata em `sudo -l` e os requisitos de autenticação, além dos limites dos argumentos do comando, antes de afirmar que há um caminho para root. Inspecione o código-fonte e as políticas sem enviar uma tentativa de injeção durante a enumeração rotineira do host.

## APIs privilegiadas de loopback após obter acesso à web

Um shell do processo web pode chamar serviços HTTP locais mesmo quando os listeners estão vinculados a `127.0.0.1`. Na versão vulnerável relatada do Control Web Panel, o painel da conta é executado como o usuário de hospedagem, mas a API de usuário em `https://127.0.0.1:2302` é executada como root. A rota POST `/v1/restoredatabase/` não verifica o token de acesso e passa o campo `file` para `shell_exec('mysql ... < ' . $file)`. Portanto, a partir de um ponto de apoio como usuário de hospedagem, separadores de shell em `file` são executados como root. Confirme tanto a proteção da rota quanto a identidade efetiva do processo da API; o vínculo a loopback, por si só, não é autenticação. Consulte [Execução de PHP após redirecionamento](../../pentesting-web/login-bypass/#php-execution-after-redirect) para uma forma de obter esse ponto de apoio. As falhas relatadas foram totalmente corrigidas no CWP 1.29.<sup>[[1]](#references)</sup>

```bash
curl -sk 'https://127.0.0.1:2302/v1/restoredatabase/' \
  --data-urlencode 'file=/dev/null ; id > /tmp/root-proof ; echo'
```

A mesma API também tem uma falha distinta no mecanismo de autenticação: `access_token()` interpola o token fornecido em `WHERE authorization_code='$access_token' AND client_id='$user'`. Uma linha `UNION` com as colunas esperadas e uma data de expiração futura pode satisfazer a verificação do token e comentar a condição original de `client_id`. Isso libera rotas protegidas, como `/v1/newpass/`, onde o valor bruto de `user` é anexado a um comando `passwd` executado pelo shell com privilégios de root. A injeção do token contorna o mecanismo de autenticação; a execução de comandos ainda depende desse segundo ponto vulnerável. Consulte [SQL injection authentication bypass](../../pentesting-web/login-bypass/#sql-injection-authentication-bypass).<sup>[[1]](#references)</sup>

No mecanismo de autenticação divulgado, composto por seis colunas, o token injetado pode fornecer uma data de expiração futura e suprimir o restante da condição; a estrutura das colunas é específica dessa compilação.<sup>[[1]](#references)</sup>

```sql
' UNION SELECT 'a','x','c','d','2099-01-01 00:00:00','f' -- -
```

Uma rota separada sem token, `/v1/user_panel_dashboard/`, interpola `user` em uma consulta a `oauth_clients`. Esta é uma leitura cega do banco de dados com a conexão da API como root do MySQL, **não** execução como root no sistema operacional: o servidor MySQL é executado como o usuário `mysql` do sistema operacional. Quando a tabela consultada está vazia, uma [sonda de tempo com tabela derivada constante](../../pentesting-web/sql-injection/#exploiting-time-based-sqli) evita perder o atraso devido à ausência de linhas.<sup>[[1]](#references)</sup>

## Credenciais de login nos logs de acesso

Se uma aplicação envia um formulário de login com `GET`, o nome de usuário e a senha podem se tornar parâmetros de consulta no URI da requisição. Uma requisição `POST` também pode conter uma query string; usar `POST` não oculta um segredo colocado acidentalmente no URI, incluindo uma senha inserida em um campo de formulário sem relação com ela. A [linha de requisição do log de acesso comum do Apache](https://httpd.apache.org/docs/2.4/logs.html) registra o método e o URI, incluindo sua query string, quando o formato configurado usa `%r`. Portanto, uma conta com permissão para ler esses logs, por exemplo, por meio do grupo `adm` em alguns sistemas Linux, pode encontrar uma pista sobre credenciais. Verifique o formato e as permissões reais do log e, em seguida, confirme que o valor é um segredo, que a conta o aceita e que ele atravessa uma fronteira de privilégios. Não presuma que o corpo da requisição foi registrado nem copie valores candidatos para uma saída compartilhada.

Inspecione somente logs de acesso que possam ser lidos e mantenha os valores de credenciais fora da saída compartilhada de comandos. Linhas de requisição longas também podem conter um referrer e um user agent; portanto, um filtro para linhas curtas pode ocultar justamente a requisição de interesse. Os locais comuns dos logs de acesso do Apache, httpd e Nginx são `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. Logs rotacionados podem conter credenciais antigas. O [acesso a arquivos de log por LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) é uma rota relacionada aos mesmos dados.

Os logs de autenticação da aplicação também podem expor uma senha inserida acidentalmente no campo de **nome de usuário** de uma tentativa de login malsucedida. Primeiro, confirme que o log pode ser lido e que seu formato registra o nome de usuário enviado; inspecione localmente apenas um pequeno trecho relevante e não copie credenciais candidatas para uma saída compartilhada. Um nome de usuário com aparência de senha é uma pista, não uma prova de que seja uma senha válida ou de que tenha privilégios maiores. Antes de afirmar que houve uma transição, confirme a conta pretendida e qualquer reutilização nas contas específicas do serviço ou do Unix.

Um manipulador de login web com permissão de escrita merece uma análise separada quando um cliente agendado, executado sob outra identidade, envia credenciais a esse endpoint. Confirme o acesso de escrita ao manipulador **ativo**, a agenda real do cliente e o caminho da requisição, de quem é a credencial enviada e se essa senha da aplicação também é válida para uma conta do sistema operacional com mais privilégios. Uma página com permissão de escrita ou um processo recorrente, por si só, não comprova essa transição. O inventário passivo deve informar as permissões do caminho e os metadados do job sem alterar o manipulador nem coletar senhas.

Os logs JSON EVE do Suricata também podem registrar os comandos FTP `USER` e `PASS` com seus dados em `command_data` quando o registro de eventos FTP está habilitado. Verifique se `/var/log/suricata/eve*.json*` pode ser lido, incluindo arquivos rotacionados ou compactados, antes de revisar localmente um pequeno trecho relevante. Um arquivo EVE legível é apenas uma pista: confirme que os eventos FTP foram registrados, que os dados incluem uma credencial utilizável e que ela atravessa uma fronteira de privilégios. Evite exibir `command_data` na saída compartilhada de enumeração. O Suricata documenta os [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e as [variações de rotação e nomes de arquivos EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuração gerada do Apache e logs canalizados

O [remco](https://github.com/HeavyHorst/remco) pode monitorar um backend de chave/valor, renderizar um template em um arquivo de configuração do Apache e executar um comando de reload. Inspecione a identidade do processo remco em execução, a origem e o destino configurados do template, os prefixos de chaves monitorados e se um valor do backend é inserido diretamente em uma diretiva do Apache, como `ServerName`. A existência de um listener local do backend, por si só, não comprova que o usuário atual pode gravar uma chave monitorada; verifique a autenticação e as permissões do backend antes de afirmar que há uma escalação de privilégios.

Uma nova linha sem escape em um valor gravável do backend pode transformar um valor destinado a uma única diretiva em diretivas adicionais do Apache. Os [logs canalizados do Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) são especialmente sensíveis: `CustomLog` ou `ErrorLog` com um comando `|` inicia um helper sob a identidade do processo httpd pai, geralmente root; `|$` solicita ao Apache que use um shell. Analise a configuração gerada e seu caminho de reload sem alterar os dados do backend nem reiniciar o serviço durante a enumeração. Mantenha o comando canalizado completo em sigilo, pois seus argumentos podem conter segredos.

## Identidades de autenticação e de serviços

O arquivo de controle do Monit costuma ser `~/.monitrc` ou `/etc/monitrc`, mas `monit -c` pode selecionar outro caminho. Um arquivo legível pode conter entradas `set httpd` e `allow user:password` para a interface web, geralmente na porta local 2812. Verifique o proprietário e as permissões do arquivo antes de analisá-lo e mantenha os valores das senhas fora da saída compartilhada de enumeração. As credenciais web concedem apenas a função Monit configurada; usuários somente leitura não podem invocar ações de controle. Uma escalação separada para uma conta Unix exige reutilização de senha confirmada ou uma ação privilegiada do Monit que a função autenticada possa realmente executar. Consulte a [documentação de autenticação e do arquivo de controle do Monit](https://www.mmonit.com/monit/documentation/monit.html).

No Webmin, `/etc/webmin/miniserv.conf` identifica as configurações do servidor e `/etc/webmin/webmin.acl` registra quais módulos os usuários podem acessar; o [Webmin documenta os limites de concessão de módulos](https://webmin.com/docs/development/creating-modules/). Uma senha Unix ou um arquivo ACL legível não concede, por si só, uma sessão do Webmin. Confirme o mapeamento real de autenticação, o listener acessível, a conta autenticada, a permissão efetiva do módulo Package Updates, o código instalado ou a correção do fornecedor e a identidade do processo Webmin. Em versões afetadas até a 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitia que uma conta com essa permissão de módulo executasse comandos por meio de seu manipulador de atualização. Durante a enumeração passiva, informe os caminhos e as permissões de configuração sem exibir credenciais nem tentar uma atualização.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) controla a autenticação específica de cada serviço; caminhos graváveis de políticas ou módulos podem alterar o comportamento de login.
- As configurações de LDAP/SSSD podem revelar endpoints de diretório, identidades de bind e regras de acesso. Uma senha de bind recuperada pode permitir consultas LDAP além da conta atual do SO; teste a identidade de bind exata e as ACLs do diretório. Revise as permissões dos arquivos antes de inspecionar segredos; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) abordam o uso de tickets e diretórios.
- Os aliases do Postfix podem encaminhar e-mails recebidos para comandos locais. Se um usuário com menos privilégios puder alterar o script referenciado, a entrega de e-mail poderá executar seu código sob a identidade de entrega. Revise os mapas de aliases e a propriedade do script antes de afirmar que esse caminho é viável; consulte [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e outros serviços de CI podem executar jobs sob uma conta local poderosa. Inspecione o usuário do serviço, os caminhos graváveis de jobs/workspaces e a interface de administração local antes de testar um pipeline ou plugin. Revise também as **credenciais disponíveis para um job** e a conta com a qual podem se autenticar: um Pipeline que usa a [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) pode acessar um host como o usuário da credencial SSH, mesmo quando o próprio Jenkins é executado sob uma conta Unix com menos privilégios. Confirme que a identidade atual do Jenkins tem `Job/Create`, `Job/Configure` ou outra forma efetiva de alterar o Pipeline, que a credencial está no escopo desse job e que a conta SSH de destino aceita a chave antes de afirmar que houve escalada de privilégios no host. O nome de exibição ou o ID de uma credencial, por si só, não comprova nenhuma dessas condições. O Jenkins alerta que criadores de jobs e, muitas vezes, configuradores de jobs podem usar arbitrariamente as credenciais disponíveis no escopo deles; por isso, o [escopo das credenciais](https://www.jenkins.io/doc/book/security/credentials/) e a [confiança do Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) são tão importantes quanto o UID do serviço. Não inclua valores de credenciais nem chaves privadas em saídas de enumeração compartilhadas.

## Gravação de arquivos em repositórios Gogs

Em um serviço Gogs local, correlacione o proprietário do processo `gogs web` com a versão do executável e `custom/conf/app.ini`. A configuração pode revelar a identidade do serviço, a raiz do repositório, o endereço do listener e se o registro está desabilitado. Um listener restrito ao loopback ainda pode ser acessado por usuários locais. As versões do Gogs até 0.13.3 têm uma falha de gravação de arquivos por symlink em `PutContents` autenticado ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): um usuário com permissão de escrita no repositório pode fazer commit de um symlink e, em seguida, direcionar a gravação da API por meio dele. O acesso resultante aos arquivos tem os privilégios do processo Gogs, portanto uma instância executada como root exige atenção imediata. Valide a correção implantada e os requisitos de autenticação antes de afirmar que há um caminho utilizável; um erro da API não comprova que a gravação do arquivo falhou.

## XSS em descrição de repositório Gitea e visualizadores privilegiados

O Gitea 1.22.0 permitia JavaScript armazenado na descrição de um repositório ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); a versão 1.22.1 corrigiu o problema. Um usuário que pode editar uma descrição pode afetar uma sessão de navegador com mais privilégios se esse usuário visualizar o repositório e ativar o link malicioso. Essa identidade do navegador pode então expor conteúdo de repositórios privados ou outros dados da aplicação. Uma escalada local separada exige uma credencial ou permissão acessível por meio desse conteúdo, como uma senha de administrador reutilizada; o proprietário do processo Gitea, por si só, não comprova impacto de root. Verifique a versão implantada, o acesso para editar descrições, o fluxo de trabalho do visualizador e a interação real com o navegador antes de afirmar que a cadeia é viável.

## API de provisionamento do Cobbler

O serviço de gerenciamento do Cobbler expõe uma API XML-RPC, geralmente na porta `25151`. Verifique o listener e o proprietário do processo `cobblerd` antes de avaliar o impacto; uma API restrita ao loopback ainda pode ser acessada por um usuário no host. Revise os módulos de autenticação e autorização em `/etc/cobbler/modules.conf`, as configurações do serviço em `/etc/cobbler/settings` ou `/etc/cobbler/settings.yaml` e as permissões de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. Os arquivos de digest e de segredo compartilhado contêm material de credenciais; por padrão, registre se podem ser lidos sem exibir seu conteúdo.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** é um bypass de autenticação XML-RPC no Cobbler 3.0.0 até 3.2.2 e 3.3.0 até 3.3.6. Um erro de leitura do segredo compartilhado retornava o valor previsível `-1`, que a API aceitava como senha. As correções correspondentes estão nas versões 3.2.3 e 3.3.7. A versão de um pacote é apenas uma pista; verifique o código implantado e qualquer correção retroportada antes de reportar exposição.

Uma sessão de API autenticada pode ser um caminho de execução privilegiada quando `cobblerd` é executado como root. Nas implementações afetadas, `background_import` passa `rsync_flags` controlado pelo usuário para um comando de shell, e a renderização de um template de instalação automática Cheetah controlado pelo usuário pode avaliar Python. Verifique as permissões da API e a versão instalada antes de testar qualquer um desses caminhos. Restrinja o acesso à API de gerenciamento, aplique o patch para o bypass de autenticação e permita que apenas os administradores do serviço leiam os arquivos de configuração e credenciais.

## Configuração do Motion e do motionEye

Inspecione `/etc/motioneye/motioneye.conf` para encontrar `conf_path` e, em seguida, examine `motion.conf` e um pequeno número de arquivos `camera-*.conf` nesse diretório. Informe se existe um hash `# @admin_password` legível, sem imprimi-lo. [Versões antigas do motionEye gravavam esses arquivos com permissões de leitura amplas](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); a correção está na versão 0.44.0. Verifique em conjunto as configurações `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost` do Motion: o controle avançado (`2` ou `3`) com autenticação desativada pode expor operações poderosas a um usuário local, inclusive em um listener de loopback. [A documentação do Motion descreve os valores e padrões](https://motion-project.github.io/motion_config.html).

Uma sessão de administrador no motionEye anterior à versão 0.43.1b5 podia transformar uma configuração de nome de arquivo da câmera em execução de comandos quando o Motion a processava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Confirme a versão em execução, a identidade do serviço, um caminho de autenticação utilizável e se há uma câmera configurada antes de alegar uma escalada. A configuração, por si só, não comprova que o serviço está em execução ou tem privilégios.

O nome de um serviço ou um pacote instalado é apenas uma pista. O limite de privilégio é determinado pela combinação entre a entrada acessível, a identidade do processo, a configuração gravável e o comando ou arquivo que ele controla no fim.

## Emuladores locais de AWS e credenciais armazenadas

Um usuário do host pode acessar um emulador compatível com AWS em execução em um contêiner por meio do endpoint de loopback publicado. Correlacione o listener ativo, o endpoint e a conta selecionados pelo cliente e as configurações de autorização instaladas no emulador antes de avaliar o acesso ao [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) ou ao [KMS](https://docs.localstack.cloud/aws/services/kms/). No LocalStack, [a aplicação de políticas do IAM é uma configuração separada](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); não deduza as permissões efetivas da API com base apenas em um arquivo de credenciais, uma política do IAM ou um listener. Confirme o comportamento da versão e da configuração instaladas.

Um segredo armazenado só é útil para escalada local se a identidade atual da API puder recuperá-lo e uma conta separada com privilégios superiores aceitar a credencial obtida. Um blob local criptografado também exige acesso de leitura ao arquivo, a chave KMS correspondente e utilizável, o algoritmo correspondente e acesso efetivo para descriptografar. Para uma [chave KMS assimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), a solicitação de descriptografia deve especificar o algoritmo usado para criptografar o blob. Limite o inventário automático do host a evidências sobre processos, listeners, caminhos de configuração e permissões de arquivos; não solicite nem imprima valores de segredos ou texto simples descriptografado durante a enumeração de rotina.
