# Web local y servicios de autenticación

{{#include ../../banners/hacktricks-training.md}}

Un shell de Linux ofrece una vista desde el host de los servicios web y de autenticación: argumentos de procesos, sockets en escucha, archivos de unidades, configuración, registros e interfaces solo locales. Usa esa vista para relacionar un servicio accesible con la cuenta y los archivos que realmente utiliza.

## Mapear la pila web local

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecciona los nombres de virtual hosts, los document roots, las rutas del proxy, los directorios de upload, la configuración de ejecución de PHP y los archivos de configuración que contengan credenciales. Un listener de loopback puede ser accesible a través de un proxy o un túnel SSH. Para probar un virtual host con nombre contra un listener local, envía el encabezado `Host` previsto o usa `curl --resolve` con la dirección y el puerto correctos. La enumeración de virtual hosts también puede revelar nombres ausentes de la respuesta predeterminada. Comprueba si Apache permite overrides de `.htaccess` y si las rutas de upload pueden ejecutar PHP antes de considerar que un directorio de upload con permisos de escritura permite ejecutar código. Un source map de JavaScript desplegado puede revelar rutas de código fuente o secretos del cliente; trata los valores recuperados como pistas y verifica sus privilegios reales. Para comprobaciones específicas de web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) y [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

En Apache con [mpm-itk](https://mpm-itk.sesse.net/), un `AssignUserID` activo puede ejecutar un virtual host con otro usuario y grupo. Si una cuenta con menos privilegios puede escribir un script en el `DocumentRoot` de ese host, revisa si una ruta accesible realmente lo ejecuta con la identidad asignada. Confirma que el módulo esté cargado, la configuración efectiva del virtual host (incluidos los overrides de identidad basados en expresiones), los permisos de escritura y búsqueda del directorio, el handler del script y el acceso al listener. Una directiva destacada o un directorio con permisos de escritura no demuestran por sí solos que se pueda ejecutar código con otro usuario.

Un directorio home publicado a través de un servidor web puede exponer archivos de backup con archivos de identidad SSH, incluso si el directorio `.ssh` activo es privado. Por ejemplo, la configuración [`homedirs_public` de Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) selecciona un subdirectorio que se sirve desde los directorios home de los usuarios. Encontrar una ruta de archivo es solo una pista: verifica el mapeo efectivo del servidor, la lectura local o la autorización HTTP, el contenido del archivo, la passphrase de la clave privada y si la cuenta correspondiente realmente acepta la clave. No extraigas archivos ni imprimas material de claves durante la enumeración rutinaria del host.

Un backup legible de una aplicación web local con más privilegios puede revelar la lógica de autenticación y lectura de archivos, aunque no se pueda acceder al código fuente activo. Compara el backup con el servicio desplegado antes de basarte en él. En particular, conviene revisar una cookie creada cifrando texto controlado por quien realiza la petición, seguido de un secreto y una marca de rol, si la aplicación usa bloques ECB deterministas, devuelve cookies nuevas para texto elegido y luego divide el valor descifrado por un delimitador sin escape. [NIST explica el mapeo independiente y repetible de bloques de ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); esa propiedad puede facilitar una comparación con entrada elegida, pero no otorga por sí sola un rol superior. Confirma la ruta activa, los requisitos de sesión, el parser y el flujo de datos exactos, la identidad del servicio y una acción privilegiada independiente o una ruta de lectura de archivos. El inventario pasivo debe informar los metadatos del backup y la propiedad del listener, sin leer el contenido del archivo ni enviar probes de autenticación.

El mismo enfoque de revisión del código fuente se aplica a un servicio local privilegiado **que no use HTTP**, como una interfaz personalizada respaldada por SSH. Si un backup de código fuente accesible muestra un comando que acepta una ruta de archivo elegida por quien realiza la petición, comprueba su mecanismo de autenticación, cómo resuelve la ruta y si verifica que el archivo resuelto siga estando dentro de un directorio previsto antes de abrirlo. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) limpia una ruta, pero no garantiza que permanezca dentro de ese directorio. Confirma que el backup corresponda a la build en ejecución, que se pueda acceder al listener, que la cuenta con menos privilegios pueda usar el comando y que el proceso pueda leer el objetivo; tener una clave SSH legible plantea una cuestión aparte sobre la política de inicio de sesión. Informa las rutas de los archivos de código fuente y la propiedad del servicio sin extraer el contenido de los archivos ni las claves en la salida automatizada.

Se puede acceder a un pool de PHP-FPM que escucha en el loopback TCP desde otra cuenta local, aunque su sitio web requiera autenticación. [PHP advierte que un cliente capaz de conectarse a FastCGI puede controlar la configuración de las peticiones, incluido `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revisa la configuración `listen` y `listen.allowed_clients` del pool junto con el listener activo, el UID del worker, una ruta de script existente y cualquier restricción `security.limit_extensions` o `php_admin_value`. Los archivos de configuración del pool pueden contener credenciales en directivas `env[...]`, por lo que el inventario automatizado debe informar sus rutas, no su contenido. Un archivo de configuración o un puerto por sí solos no demuestran que exista una vía de ejecución entre usuarios; consulta la [guía de FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para conocer los detalles del protocolo.

En una API local privilegiada, rastrea la autorización además de la ejecución de código. Un rol de base de datos que la cuenta con menos privilegios pueda cambiar podría habilitar una ruta de la API, pero el siguiente límite depende de la implementación de esa ruta. Por ejemplo, merece la pena revisar si combinar JSON de la petición en un objeto JavaScript y luego llamar a [`child_process.exec`](https://nodejs.org/api/child_process.html) crea un [flujo de datos de prototype pollution a ejecución](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la biblioteca/versión real de combinación, la validación de entradas, la ruta accesible, la identidad del proceso y las opciones del proceso hijo; un listener de Node propiedad de root o el nombre de una dependencia vulnerable son solo pistas.

Los CMS que almacenan datos en archivos pueden guardar verificadores de contraseñas de administrador fuera de los archivos de configuración `.php` convencionales. Algunos ejemplos son `data/database.js` del sitio o `data/settings/pass.php`. Comprueba la propiedad y los permisos de lectura del archivo antes de revisarlo manualmente, y no incluyas hashes en salidas automatizadas compartidas. Una contraseña recuperable de una aplicación plantea un límite de privilegios distinto al de una cuenta Unix: verifica cualquier posible reutilización para la cuenta específica y el método de autenticación permitido.

El controlador de autenticación de una aplicación también puede contener una contraseña de inicio de sesión literal en el código fuente, en vez de en un archivo de configuración. Si un usuario con menos privilegios puede leer el controlador desplegado, revisa localmente su comparación de autenticación y no incluyas ningún valor en salidas de enumeración compartidas. Confirma que la ruta de código esté activa, que la contraseña sea válida para la aplicación y que una cuenta Unix específica con más privilegios acepte esa misma contraseña antes de afirmar que permite una escalada local. El nombre de un archivo de controlador es solo una pista para revisarlo.

Dolibarr almacena la configuración de conexión a la base de datos, incluido `dolibarr_main_db_pass`, en `htdocs/conf/conf.php` ([referencia de configuración](https://wiki.dolibarr.org/index.php/Configuration_file)). Un archivo legible es una pista sobre posibles credenciales; solo la reutilización verificada de la contraseña de otra cuenta o algún otro permiso de base de datos permitiría una escalada local de privilegios. Comprueba primero los permisos y evita imprimir el valor en la salida automatizada.

La configuración del paquete Linux de GitLab suele estar en `/etc/gitlab/gitlab.rb`, aunque los despliegues pueden conservar copias legibles en otros lugares. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que este archivo puede contener `gitlab_rails['smtp_password']`, aunque la configuración SMTP cifrada puede guardar la contraseña fuera del archivo de texto sin cifrar. Trata una configuración legible como una pista sobre posibles credenciales: verifica que esté activa, que las credenciales sigan vigentes y que una cuenta específica con más privilegios las acepte antes de afirmar que hay reutilización de contraseña. Por otra parte, [GitLab ejecuta `gitlab.rb` como código Ruby con privilegios de root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un archivo activo con permisos de escritura o un archivo `from_file` incluido requiere una ruta real de reconfiguración privilegiada para considerarse un hallazgo de ejecución. Una vista previa de la configuración puede exponer valores de credenciales, así que trata su salida como información sensible y comparte las rutas y los permisos.

Una instalación autohospedada de Mattermost puede guardar `SqlSettings.DataSource` en `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esa ruta habitual como los despliegues que almacenan la configuración activa en una base de datos. Un archivo legible puede exponer una credencial de la base de datos de la aplicación, pero no demuestra que se pueda acceder a la base de datos ni a root de Unix. Verifica la fuente de configuración activa, los permisos reales del rol de la base de datos, cualquier contraseña de aplicación recuperada por separado y si esa contraseña funciona para una cuenta Unix específica con más privilegios. El formato de los hashes de contraseñas puede variar entre versiones de Mattermost; durante la enumeración, registra la ruta de configuración y los metadatos de acceso sin imprimir la cadena de conexión ni consultar la base de datos.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra los resultados de virtual hosts comparándolos con el tamaño de la respuesta predeterminada u otra referencia estable para que no todos los nombres probados parezcan válidos. Un source map solo es útil si realmente está desplegado o se puede leer de otro modo.

Los reverse proxies pueden cambiar qué encabezados del cliente confía una aplicación. Compara las solicitudes directas y las que pasan por proxy antes de asumir que `X-Forwarded-For`, `X-Forwarded-Host` u otros encabezados similares establecen la identidad de quien realiza la solicitud. Revisa conjuntamente la configuración del proxy y de la aplicación.

Si PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` en una cadena que se pasa a [`system()`](https://www.php.net/manual/en/function.system.php), revisa si la ruta de solicitud accesible permite que quien realiza la solicitud proporcione un encabezado y si los metacaracteres del shell llegan intactos a esa cadena. Incluir un comando como `sudo iptables` al principio **no** hace que los comandos posteriores separados por el shell se ejecuten como root; estos se ejecutan como el proceso worker web, salvo que una regla `sudo` efectiva independiente permita la escalada. Confirma la identidad del worker, la concesión exacta de `sudo -l` y sus requisitos de autenticación, y los límites de argumentos del comando antes de afirmar que existe una ruta a root. Inspecciona el código fuente y las políticas sin enviar una prueba de inyección durante el inventario rutinario del host.

## Credenciales de inicio de sesión en los logs de acceso

Si una aplicación envía un formulario de inicio de sesión con `GET`, el nombre de usuario y la contraseña pueden convertirse en parámetros de consulta en el URI de la solicitud. Una solicitud `POST` también puede contener una cadena de consulta; usar `POST` no oculta un secreto colocado accidentalmente en el URI, incluida una contraseña introducida en un campo de formulario que no corresponde. La [línea de solicitud del log de acceso común de Apache](https://httpd.apache.org/docs/2.4/logs.html) registra el método y el URI, incluida su cadena de consulta, cuando el formato configurado usa `%r`. Por lo tanto, una cuenta con permiso para leer esos logs —por ejemplo, mediante el grupo `adm` en algunos sistemas Linux— puede encontrar una posible credencial. Comprueba el formato y los permisos reales del log; luego verifica que el valor sea un secreto, que la cuenta lo acepte y que permita cruzar un límite de privilegios. No des por hecho que se registró el cuerpo de la solicitud ni copies posibles valores a la salida compartida.

Inspecciona solo los logs de acceso que puedas leer y evita incluir valores de credenciales en la salida compartida de comandos. Las líneas de solicitud largas también pueden contener un referrer y un user agent, por lo que un filtro de líneas cortas puede ocultar precisamente la solicitud que interesa. Las ubicaciones habituales de los logs de acceso de Apache, httpd y Nginx son `/var/log/apache2/access.log`, `/var/log/httpd/access_log` y `/var/log/nginx/access.log`. Los logs rotados pueden contener credenciales antiguas. [El acceso a archivos de log mediante LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) es una ruta relacionada para acceder a los mismos datos.

Los logs de autenticación de una aplicación también pueden exponer una contraseña introducida accidentalmente en el campo de **nombre de usuario** durante un inicio de sesión fallido. Primero confirma que el log se pueda leer y que su formato registre el nombre de usuario enviado; inspecciona localmente solo un fragmento pequeño y pertinente, y no copies posibles credenciales a la salida compartida. Un nombre de usuario con aspecto de contraseña es una pista, no una prueba de que sea una contraseña válida ni de que otorgue más privilegios. Verifica la cuenta prevista y cualquier reutilización en el servicio o la cuenta Unix específicos antes de afirmar que permite una transición.

Un controlador de inicio de sesión web con permisos de escritura merece una revisión aparte cuando un cliente programado con otra identidad envía credenciales a ese endpoint. Confirma que se pueda escribir en el controlador **activo**, la programación y la ruta de solicitud reales del cliente, de quién son las credenciales que envía y si esa contraseña de la aplicación también es válida para una cuenta del sistema operativo con más privilegios. Una página modificable o un proceso recurrente, por sí solos, no demuestran que esa transición sea posible. El inventario pasivo debe informar de los permisos de la ruta y los metadatos del trabajo sin modificar el controlador ni recopilar contraseñas.

Los logs JSON EVE de Suricata también pueden registrar los comandos FTP `USER` y `PASS` junto con `command_data` cuando está habilitado el registro de eventos FTP. Comprueba que se pueda leer `/var/log/suricata/eve*.json*`, incluidos los archivos rotados o comprimidos, antes de revisar localmente un fragmento pequeño y pertinente. Un archivo EVE legible es solo una pista: confirma que se registraron eventos FTP, que los datos incluyen una credencial utilizable y que esta permite cruzar un límite de privilegios. Evita mostrar `command_data` en la salida compartida del inventario. Suricata documenta los [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) y las [variantes de rotación y nombres de archivo de EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuración de Apache generada y logs canalizados

[remco](https://github.com/HeavyHorst/remco) puede vigilar un backend de clave/valor, renderizar una plantilla en un archivo de configuración de Apache y ejecutar un comando de recarga. Inspecciona la identidad del proceso remco en ejecución, el origen y el destino de la plantilla configurada, los prefijos de claves vigilados y si un valor del backend se inserta directamente en una directiva de Apache como `ServerName`. Que haya un listener de backend local no demuestra, por sí solo, que el usuario actual pueda escribir en una clave vigilada; verifica la autenticación y los permisos del backend antes de afirmar que existe una escalada.

Un salto de línea sin escapar en un valor del backend modificable puede convertir el valor previsto de una directiva en directivas adicionales de Apache. Los [logs canalizados de Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) son especialmente sensibles: `CustomLog` o `ErrorLog` con un comando `|` inicia un proceso auxiliar con la identidad del proceso httpd padre, a menudo root; `|$` indica a Apache que use un shell. Revisa la configuración generada y su ruta de recarga sin cambiar los datos del backend ni reiniciar el servicio durante el inventario. Mantén privado el comando canalizado completo, ya que sus argumentos pueden contener secretos.

## Autenticación e identidades de servicio

El archivo de control de Monit suele ser `~/.monitrc` o `/etc/monitrc`, pero `monit -c` puede seleccionar otra ruta. Un archivo legible puede contener entradas `set httpd` y `allow user:password` para su interfaz web, a menudo en el puerto local 2812. Comprueba el propietario y los permisos del archivo antes de revisarlo, y evita incluir los valores de contraseña en la salida compartida del inventario. Las credenciales web solo otorgan el rol de Monit configurado; los usuarios de solo lectura no pueden ejecutar acciones de control. Para escalar mediante una cuenta Unix independiente, es necesario confirmar que se reutilice la contraseña o que el rol autenticado pueda activar una acción privilegiada de Monit. Consulta la [documentación del archivo de control y la autenticación de Monit](https://www.mmonit.com/monit/documentation/monit.html).

En Webmin, `/etc/webmin/miniserv.conf` identifica la configuración del servidor y `/etc/webmin/webmin.acl` registra a qué módulos pueden acceder los usuarios; [Webmin documenta los límites de las concesiones de módulos](https://webmin.com/docs/development/creating-modules/). Una contraseña Unix o un archivo ACL legible no otorgan, por sí solos, una sesión de Webmin. Confirma la asignación de autenticación real, el listener accesible, la cuenta autenticada, los permisos efectivos del módulo Package Updates, el código instalado o la corrección del proveedor, y la identidad del proceso de Webmin. En las versiones afectadas hasta la 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitía que una cuenta con permiso para ese módulo ejecutara comandos mediante su controlador de actualizaciones. Durante el inventario pasivo, informa de las rutas y los permisos de configuración sin mostrar credenciales ni intentar una actualización.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) rige la autenticación específica de cada servicio; las rutas modificables de políticas o módulos pueden cambiar el comportamiento del inicio de sesión.
- La configuración de LDAP/SSSD puede revelar endpoints de directorio, identidades de enlace y reglas de acceso. Una contraseña de enlace recuperada puede permitir consultas LDAP que van más allá de la cuenta actual del sistema operativo; prueba la identidad de enlace exacta y las ACL del directorio. Revisa los permisos de los archivos antes de inspeccionar secretos; [Linux Active Directory](../user-information/linux-active-directory.md) y [FreeIPA](freeipa-pentesting.md) cubren el uso de tickets y directorios.
- Los alias de Postfix pueden canalizar el correo recibido a comandos locales. Si un usuario con menos privilegios puede cambiar el script referenciado, la entrega de correo puede ejecutar su código con la identidad de entrega. Revisa los mapas de alias y la propiedad del script antes de afirmar que esa vía es viable; consulta [pruebas de servicios SMTP y correo](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins y otros servicios de CI pueden ejecutar tareas con una cuenta local con muchos privilegios. Inspecciona el usuario del servicio, las rutas modificables de tareas/espacios de trabajo y la interfaz de administración local antes de probar una pipeline o un plugin. Revisa también las **credenciales disponibles para una tarea** y la cuenta con la que pueden autenticarse: una Pipeline que usa el [paso SSH Agent](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) puede acceder a un host como el usuario de la credencial SSH, incluso si Jenkins se ejecuta con una cuenta Unix con menos privilegios. Confirma que la identidad actual de Jenkins tenga `Job/Create`, `Job/Configure` u otra vía efectiva para modificar la Pipeline, que la credencial esté disponible para esa tarea y que la cuenta SSH de destino acepte la clave antes de afirmar que se trata de una escalada de privilegios en el host. El nombre o ID visible de una credencial, por sí solo, no demuestra ninguna de estas condiciones. Jenkins advierte que quienes crean tareas y, a menudo, quienes las configuran pueden usar arbitrariamente las credenciales disponibles dentro de su ámbito; por eso, el [ámbito de las credenciales](https://www.jenkins.io/doc/book/security/credentials/) y la [confianza de Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) importan tanto como el UID del servicio. No incluyas valores de credenciales ni claves privadas en resultados de enumeración compartidos.

## Escrituras de archivos de repositorio en Gogs

En un servicio Gogs local, correlaciona el propietario del proceso `gogs web` con la versión del ejecutable y `custom/conf/app.ini`. La configuración puede revelar la identidad del servicio, la raíz del repositorio, la dirección de escucha y si el registro está deshabilitado. Incluso los usuarios locales pueden acceder a un listener que solo escucha en loopback. Las versiones de Gogs hasta la 0.13.3 inclusive tienen un problema autenticado de escritura de archivos mediante enlace simbólico en `PutContents` ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): quien puede escribir en un repositorio puede hacer commit de un enlace simbólico y luego dirigir a través de él la escritura de la API. El acceso resultante a los archivos tiene los privilegios del proceso Gogs, por lo que una instancia ejecutada como root requiere atención inmediata. Valida la corrección desplegada y los requisitos de autenticación antes de afirmar que existe una vía utilizable; un error de la API no demuestra que la escritura del archivo haya fallado.

## XSS en la descripción de repositorios de Gitea y usuarios privilegiados

Gitea 1.22.0 permitía JavaScript almacenado en la descripción de un repositorio ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versión 1.22.1 lo corrigió. Un usuario que puede editar una descripción puede afectar una sesión de navegador con más privilegios si ese usuario visita el repositorio y activa el enlace malicioso. Esa identidad del navegador puede entonces exponer contenido de repositorios privados u otros datos de la aplicación. Una escalada local aparte requiere una credencial o un permiso accesible a través de ese contenido, como una contraseña reutilizada de administrador; el propietario del proceso Gitea, por sí solo, no demuestra un impacto de root. Comprueba la versión desplegada, el acceso para editar descripciones, el flujo de trabajo de los usuarios que las visitan y la interacción real con el navegador antes de afirmar que la cadena es viable.

## API de aprovisionamiento de Cobbler

El servicio de gestión de Cobbler expone una API XML-RPC, comúnmente en el puerto `25151`. Comprueba el listener y el propietario del proceso `cobblerd` antes de evaluar su impacto; un usuario del host puede acceder incluso a una API que solo escucha en loopback. Revisa los módulos de autenticación y autorización en `/etc/cobbler/modules.conf`, la configuración del servicio en `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml`, y los permisos de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` y `/var/lib/cobbler/web.ss`. Los archivos de digest y de secreto compartido contienen material de credenciales, así que registra si se pueden leer sin imprimir su contenido de forma predeterminada.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** es un bypass de autenticación XML-RPC en Cobbler 3.0.0 a 3.2.2 y 3.3.0 a 3.3.6. Un error de lectura del secreto compartido devolvía el valor predecible `-1`, que la API aceptaba como contraseña. Las versiones que corrigen el problema son la 3.2.3 y la 3.3.7. La versión del paquete es solo una pista; verifica el código implementado y cualquier corrección retroportada antes de informar sobre la exposición.

Una sesión autenticada de la API puede permitir la ejecución de código con privilegios cuando `cobblerd` se ejecuta como root. En las implementaciones afectadas, `background_import` pasa `rsync_flags`, controlado por el usuario, a un comando de shell, y al renderizar una plantilla de autoinstall de Cheetah controlada por el usuario se puede evaluar Python. Comprueba los permisos de la API y la versión instalada antes de probar cualquiera de estas vías. Restringe el acceso a la API de administración, aplica el parche para el bypass de autenticación y permite que solo los administradores del servicio lean los archivos de configuración y credenciales.

## Configuración de Motion y motionEye

Inspecciona `/etc/motioneye/motioneye.conf` para encontrar `conf_path`; luego revisa `motion.conf` y una pequeña cantidad de archivos `camera-*.conf` de ese directorio. Informa si existe un hash legible de `# @admin_password`, pero no lo muestres. [Las versiones antiguas de motionEye escribían estos archivos con permisos de lectura demasiado amplios](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la corrección está en la versión 0.44.0. Comprueba conjuntamente los ajustes `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` y `webcontrol_localhost` de Motion: el control avanzado (`2` o `3`) con la autenticación deshabilitada puede exponer operaciones potentes a un usuario local, incluso en un listener de loopback. [Motion documenta los valores y los ajustes predeterminados](https://motion-project.github.io/motion_config.html).

Una sesión de administrador en motionEye anterior a la versión 0.43.1b5 podía convertir un ajuste del nombre de archivo de una cámara en ejecución de comandos cuando Motion lo procesaba ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Confirma la versión en ejecución, la identidad del servicio, la existencia de una vía de autenticación utilizable y si hay una cámara configurada antes de afirmar que es posible una escalada. La configuración, por sí sola, no demuestra que el servicio esté en ejecución o tenga privilegios.

El nombre de un servicio o un paquete instalado es solo una pista. El límite de privilegios depende de la combinación de la entrada accesible, la identidad del proceso, la configuración modificable y el comando o archivo que este controla en última instancia.

## Emuladores locales de AWS y credenciales almacenadas

Un usuario del host puede acceder a un emulador compatible con AWS que se ejecuta en un contenedor a través de su endpoint de loopback publicado. Correlaciona el listener activo, el endpoint y la cuenta seleccionados por el cliente, y los ajustes de autorización instalados en el emulador antes de evaluar el acceso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/). En LocalStack, [la aplicación de políticas de IAM es un ajuste independiente](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); no deduzcas los permisos efectivos de la API basándote únicamente en un archivo de credenciales, una política de IAM o un listener. Confirma el comportamiento de la versión y la configuración instaladas.

Un secreto almacenado solo sirve para una escalada local si la identidad actual de la API puede recuperarlo y una cuenta independiente con más privilegios acepta la credencial obtenida. Un blob local cifrado también requiere acceso de lectura al archivo, la clave de KMS correspondiente y utilizable, el algoritmo adecuado y permisos efectivos de descifrado. Para una [clave asimétrica de KMS](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la solicitud de descifrado debe especificar el algoritmo utilizado para cifrar el blob. Limita el inventario automático del host a evidencias de procesos, listeners, rutas de configuración y permisos de archivos; durante el reconocimiento habitual, no solicites ni muestres valores secretos ni texto plano descifrado.
