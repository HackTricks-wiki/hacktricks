# स्थानीय वेब और प्रमाणीकरण सेवाएँ

{{#include ../../banners/hacktricks-training.md}}

Linux shell वेब और प्रमाणीकरण सेवाओं का होस्ट-साइड दृश्य देता है: प्रोसेस आर्ग्युमेंट, लिसनर, यूनिट फ़ाइलें, कॉन्फ़िगरेशन, लॉग और केवल-स्थानीय इंटरफ़ेस। इस दृश्य का उपयोग करके पता लगाएँ कि किसी पहुँच योग्य सेवा में वास्तव में कौन-सा अकाउंट और कौन-सी फ़ाइलें इस्तेमाल हो रही हैं।

## स्थानीय वेब स्टैक का मानचित्र बनाएँ

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

वर्चुअल-होस्ट नाम, document roots, proxy routes, upload directories, PHP execution settings और credentials वाली config files की जाँच करें। Loopback listener किसी proxy या SSH tunnel के ज़रिए पहुँच योग्य हो सकता है। किसी local listener पर named virtual host जाँचने के लिए इच्छित `Host` header भेजें या सही address और port के साथ `curl --resolve` का उपयोग करें। Virtual-host enumeration से ऐसे नाम भी सामने आ सकते हैं जो default response में मौजूद नहीं होते। Writable upload directory को code execution मानने से पहले जाँचें कि Apache `.htaccess` overrides की अनुमति देता है या नहीं, और upload paths में PHP execute हो सकता है या नहीं। Deployed JavaScript source map से source paths या client-side secrets उजागर हो सकते हैं; मिली हुई values को सुराग मानें और उनके वास्तविक privileges की पुष्टि करें। Web-specific checks के लिए [Apache](../../network-services-pentesting/pentesting-web/apache.md) और [Nginx](../../network-services-pentesting/pentesting-web/nginx.md) देखें।

Apache में [mpm-itk](https://mpm-itk.sesse.net/) के साथ, सक्रिय `AssignUserID` किसी virtual host को अलग user और group के तहत चला सकता है। यदि कम privilege वाला account उस host के `DocumentRoot` में script लिख सकता है, तो जाँचें कि कोई पहुँच योग्य route वास्तव में उसे assigned identity के तहत execute करता है या नहीं। पुष्टि करें कि module loaded है, virtual-host की प्रभावी configuration (जिसमें expression-आधारित identity overrides भी शामिल हैं), directory में write और search permissions, script handler और listener तक पहुँच क्या है। केवल highlighted directive या writable directory से cross-user execution सिद्ध नहीं होता।

Web server के ज़रिए प्रकाशित home directory में SSH identity files के backup archives हो सकते हैं, भले ही live `.ssh` directory private हो। उदाहरण के लिए, [Nostromo की `homedirs_public` setting](https://www.nazgul.ch/dev/nostromo_man.html) तय करती है कि user homes की कौन-सी subdirectory serve होगी। केवल path से archive मिलने पर उसे सुराग मानें: server की प्रभावी mapping, local readability या HTTP authorization, archive contents, private-key passphrase और संबंधित account उस key को स्वीकार करता है या नहीं—इनकी पुष्टि करें। नियमित host enumeration के दौरान archives extract न करें और key material print न करें।

किसी higher-privileged local web app का readable backup authentication और file-read logic उजागर कर सकता है, भले ही उसका live source उपलब्ध न हो। उस पर भरोसा करने से पहले backup की deployed service से तुलना करें। विशेष रूप से, ऐसा cookie जो caller-controlled text के बाद secret और role flag को encrypt करके बनाया जाता हो, जाँचने योग्य है—अगर app deterministic ECB blocks का उपयोग करता है, चुने गए text के लिए नए cookies लौटाता है और बाद में decrypted value को unescaped delimiter पर split करता है। [NIST बताता है कि ECB में blocks की mapping स्वतंत्र और दोहराई जा सकने वाली होती है](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); यह गुण चुने गए input की तुलना में मदद कर सकता है, लेकिन अपने-आप higher role नहीं देता। Live route, session prerequisites, सटीक parser/data flow, service identity और अलग privileged action या file-read path की पुष्टि करें। Passive inventory में archive contents पढ़े या authentication probes भेजे बिना backup metadata और listener ownership दर्ज करें।

Source-review का यही तरीका किसी privileged **non-HTTP** loopback service, जैसे custom SSH-backed interface, पर भी लागू होता है। यदि उपलब्ध source backup में ऐसा command दिखता है जो caller द्वारा चुना गया file path स्वीकार करता है, तो उसका authentication gate, path resolve करने का तरीका और file खोलने से पहले यह सुनिश्चित करना कि resolved file इच्छित directory के भीतर ही रहे—इनकी जाँच करें। Go में [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) path को साफ करता है, लेकिन यह containment लागू नहीं करता। पुष्टि करें कि backup running build से मेल खाता है, listener पहुँच योग्य है, command का उपयोग कम privilege वाला account कर सकता है और process target को पढ़ सकता है; readable SSH key होना एक अलग login-policy का प्रश्न है। Archive contents या keys extract किए बिना source archive paths और service ownership रिपोर्ट करें।

TCP loopback पर listening PHP-FPM pool तक कोई दूसरा local account पहुँच सकता है, भले ही उसकी website में authentication हो। [PHP चेतावनी देता है कि FastCGI से connect कर सकने वाला client `auto_prepend_file` समेत request settings नियंत्रित कर सकता है](https://www.php.net/manual/en/install.fpm.php)। Pool की `listen` और `listen.allowed_clients` settings के साथ live listener, worker UID, मौजूदा script path और `security.limit_extensions` या `php_admin_value` restrictions की जाँच करें। Pool configuration files में `env[...]` directives के तहत credentials हो सकते हैं, इसलिए automated inventory में उनकी contents के बजाय paths रिपोर्ट करें। केवल config file या port से cross-user execution path सिद्ध नहीं होता; protocol की जानकारी के लिए [FastCGI guide](../../network-services-pentesting/9000-pentesting-fastcgi.md) देखें।

किसी privileged local API के लिए code execution के साथ authorization का भी पता लगाएँ। ऐसा database role जिसे कम privilege वाला account बदल सकता है, API route तक पहुँच दे सकता है, लेकिन अगली boundary उस route के implementation पर निर्भर करती है। उदाहरण के लिए, request JSON को JavaScript object में merge करने और फिर [`child_process.exec`](https://nodejs.org/api/child_process.html) call करने पर [prototype-pollution-to-execution dataflow](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md) की जाँच करना उचित है। इस्तेमाल की गई merge library/version, input validation, पहुँच योग्य route, process identity और child-process options की पुष्टि करें; केवल root-owned Node listener या vulnerable dependency का नाम एक सुराग भर है।

File-backed CMS stores में administrator password verifiers, पारंपरिक `.php` configuration files के बाहर भी हो सकते हैं। उदाहरणों में किसी site का `data/database.js` या `data/settings/pass.php` शामिल हैं। Manual review से पहले file ownership और readability जाँचें, और hashes को automated shared output में शामिल न करें। Recover किया जा सकने वाला application password, Unix account से अलग privilege boundary है: password reuse के किसी भी दावे की संबंधित account और अनुमत authentication method के साथ पुष्टि करें।

किसी application के authentication controller में configuration file के बजाय source code में literal login password भी हो सकता है। यदि कम privilege वाला user deployed controller पढ़ सकता है, तो authentication comparison की स्थानीय रूप से जाँच करें और किसी भी value को shared enumeration output से बाहर रखें। Local escalation का दावा करने से पहले पुष्टि करें कि code path सक्रिय है, password application के लिए valid है और कोई अलग higher-privileged Unix account वास्तव में वही password स्वीकार करता है। Controller का filename अकेले केवल जाँच का सुराग है।

Dolibarr database connection settings, जिनमें `dolibarr_main_db_pass` भी शामिल है, `htdocs/conf/conf.php` में रखता है ([configuration reference](https://wiki.dolibarr.org/index.php/Configuration_file))। Readable file credentials का सुराग है; केवल अलग से सत्यापित account-password reuse या कोई अन्य database permission ही इसे local privilege escalation बना सकती है। पहले permissions देखें और automated output में value print करने से बचें।

GitLab की Linux package configuration सामान्यतः `/etc/gitlab/gitlab.rb` होती है, जबकि deployments इसकी readable copies कहीं और भी रख सकते हैं। [GitLab के दस्तावेज़](https://docs.gitlab.com/omnibus/settings/smtp/) बताते हैं कि इस file में `gitlab_rails['smtp_password']` हो सकता है, हालाँकि encrypted SMTP settings में password plaintext file के बाहर रखा जा सकता है। Readable configuration को credentials का सुराग मानें: दावा करने से पहले पुष्टि करें कि यह सक्रिय है, credential अभी valid है और कोई specific higher-privileged account उसे स्वीकार करता है। अलग से, [GitLab `gitlab-ctl reconfigure` के दौरान root के तहत `gitlab.rb` को Ruby code की तरह चलाता है](https://docs.gitlab.com/omnibus/settings/configuration/); writable active file या included `from_file` को execution finding मानने से पहले वास्तविक privileged reconfigure path होना आवश्यक है। Config preview में credential values उजागर हो सकती हैं, इसलिए उसके output को sensitive मानें और इसके बजाय paths और permissions साझा करें।

Self-hosted Mattermost installation में `SqlSettings.DataSource` `/opt/mattermost/config/config.json` में हो सकता है; [Mattermost के दस्तावेज़](https://docs.mattermost.com/deployment-guide/server/troubleshooting) इस सामान्य path और ऐसे deployments—जिनमें active configuration किसी database में रखी जाती है—दोनों का उल्लेख करते हैं। Readable file से application database credential उजागर हो सकता है, लेकिन इससे database access या Unix root access सिद्ध नहीं होता। Enumeration के दौरान connection string print किए या database query किए बिना active configuration source, database role के वास्तविक अधिकार, अलग से recovered application password और उस password के किसी specific higher-privileged Unix account पर काम करने की पुष्टि करें। Mattermost versions के बीच password-hash format बदल सकता है; config path और access metadata दर्ज करें।

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

डिफ़ॉल्ट response size या किसी अन्य स्थिर baseline के आधार पर virtual-host results को फ़िल्टर करें, ताकि हर अनुमानित नाम valid न लगे। Source map तभी उपयोगी है, जब वह वास्तव में deploy किया गया हो या किसी अन्य तरीके से पढ़ा जा सकता हो।

Reverse proxies इस बात को बदल सकते हैं कि application किन client headers पर भरोसा करता है। यह मानने से पहले कि `X-Forwarded-For`, `X-Forwarded-Host` या ऐसे ही headers caller की पहचान स्थापित करते हैं, direct और proxied requests की तुलना करें। Proxy और application configuration को साथ में देखें।

यदि PHP `$_SERVER['HTTP_X_FORWARDED_FOR']` को [`system()`](https://www.php.net/manual/en/function.system.php) में पास की गई string में कॉपी करता है, तो जाँचें कि उपलब्ध request path caller-supplied header की अनुमति देता है या नहीं, और shell metacharacters उस string तक बिना बदलाव पहुँचते हैं या नहीं। शुरुआत में `sudo iptables` जैसा command होना **यह सुनिश्चित नहीं करता** कि shell से अलग किए गए बाद के commands root के रूप में चलेंगे; वे web worker के रूप में चलेंगे, जब तक कि अलग से कोई प्रभावी sudo rule privilege escalation की अनुमति न दे। Root path का दावा करने से पहले worker की identity, सटीक `sudo -l` grant और authentication requirement, तथा command की argument boundary की पुष्टि करें। Routine host enumeration के दौरान injection probe भेजे बिना source और policy की जाँच करें।

## Access logs में login credentials

यदि कोई application login form को `GET` के साथ submit करती है, तो username और password request URI में query parameters बन सकते हैं। `POST` request में भी query string हो सकती है; `POST` का उपयोग करने से URI में गलती से रखी गई secret जानकारी छिपती नहीं है—इसमें किसी असंबंधित form field में दर्ज password भी शामिल है। यदि configured format में `%r` का उपयोग हो, तो [Apache की सामान्य access-log request line](https://httpd.apache.org/docs/2.4/logs.html) method और URI, query string सहित, दर्ज करती है। इसलिए जिन accounts को इन logs को पढ़ने की अनुमति है—उदाहरण के लिए, कुछ Linux systems पर `adm` group के ज़रिए—उन्हें credential का सुराग मिल सकता है। वास्तविक log format और permissions जाँचें, फिर पुष्टि करें कि value एक secret है, account उसे स्वीकार करता है, और उससे privilege boundary पार होती है। यह न मानें कि request body log की गई थी, और संभावित values को shared output में कॉपी न करें।

केवल पढ़े जा सकने वाले access logs देखें और credential values को shared command output से बाहर रखें। लंबी request lines में referrer और user agent भी हो सकते हैं, इसलिए short-line filter उस request को छिपा सकता है जिसमें आपकी रुचि है। Apache, httpd और Nginx के सामान्य access-log locations हैं: `/var/log/apache2/access.log`, `/var/log/httpd/access_log` और `/var/log/nginx/access.log`। Rotated logs में पुराने credentials हो सकते हैं। [LFI के ज़रिए log-file access](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) उसी data तक पहुँचने का एक संबंधित तरीका है।

Application authentication logs में failed login के दौरान **username** field में गलती से दर्ज किया गया password भी उजागर हो सकता है। पहले पुष्टि करें कि log पढ़ा जा सकता है और उसका format submitted username दर्ज करता है; फिर स्थानीय रूप से केवल छोटा, संबंधित हिस्सा देखें और संभावित credentials को shared output में कॉपी न करें। Password जैसा दिखने वाला username एक सुराग है, valid password या उच्च privilege का प्रमाण नहीं। किसी transition का दावा करने से पहले इच्छित account और उस विशिष्ट service या Unix account में किसी भी password reuse की पुष्टि करें।

जब किसी अन्य identity के तहत scheduled client उस endpoint पर credentials submit करता हो, तो writable web login handler की अलग से जाँच करें। पुष्टि करें कि **active** handler पर write access है, client का वास्तविक schedule और request path क्या है, वह किसके credentials भेजता है, और क्या वह application password किसी अधिक-privileged operating-system account के लिए स्वतंत्र रूप से valid है। केवल writable page या recurring process से ऐसा transition साबित नहीं होता। Passive inventory में handler को बदले या passwords इकट्ठा किए बिना path permissions और job metadata दर्ज करें।

FTP event logging सक्षम होने पर Suricata के EVE JSON logs FTP `USER` और `PASS` commands को उनके `command_data` सहित दर्ज कर सकते हैं। स्थानीय रूप से छोटा, संबंधित हिस्सा देखने से पहले `/var/log/suricata/eve*.json*` को पढ़ने की अनुमति जाँचें; इसमें rotated या compressed files भी शामिल हैं। पढ़ी जा सकने वाली EVE file केवल एक सुराग है: पुष्टि करें कि FTP events log किए गए थे, data में उपयोगी credential शामिल है, और उससे privilege boundary पार होती है। Shared enumeration output में `command_data` दिखाने से बचें। Suricata [FTP event fields](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) और [EVE rotation तथा filename variants](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html) का दस्तावेज़ देता है।

## Generated Apache configuration और piped logs

[remco](https://github.com/HeavyHorst/remco) key/value backend को watch कर सकता है, template को Apache configuration file में render कर सकता है, और reload command चला सकता है। चल रहे remco process की identity, उसका configured template source और destination, watch किए गए key prefixes, और यह जाँचें कि backend value सीधे `ServerName` जैसे Apache directive में डाली जाती है या नहीं। केवल local backend listener होने से यह साबित नहीं होता कि मौजूदा user watched key लिख सकता है; escalation का दावा करने से पहले backend authentication और permissions की पुष्टि करें।

Writable backend value में unescaped newline होने से एक intended directive value अतिरिक्त Apache directives में बदल सकती है। [Apache piped logs](https://httpd.apache.org/docs/2.4/logs.html#piped) विशेष रूप से संवेदनशील हैं: `|` command वाला `CustomLog` या `ErrorLog` parent httpd identity के तहत helper शुरू करता है, जो अक्सर root होता है; `|$` Apache को shell इस्तेमाल करने के लिए कहता है। Enumeration के दौरान backend data बदले या service restart किए बिना generated configuration और उसके reload path की जाँच करें। पूरे piped command को निजी रखें, क्योंकि उसके arguments में secrets हो सकते हैं।

## Authentication और service identities

Monit की control file आमतौर पर `~/.monitrc` या `/etc/monitrc` होती है, लेकिन `monit -c` किसी दूसरे path को चुन सकता है। पढ़ी जा सकने वाली file में उसके web interface के लिए `set httpd` और `allow user:password` entries हो सकती हैं, जो अक्सर local port 2812 पर उपलब्ध होता है। File देखने से पहले उसके owner और permissions जाँचें, और password values को shared enumeration output से बाहर रखें। Web credentials केवल configured Monit role देते हैं; read-only users control actions नहीं चला सकते। अलग Unix-account escalation के लिए password reuse की पुष्टि या ऐसा privileged Monit action आवश्यक है जिसे authenticated role वास्तव में trigger कर सके। [Monit control-file और authentication documentation](https://www.mmonit.com/monit/documentation/monit.html) देखें।

Webmin के लिए, `/etc/webmin/miniserv.conf` में server settings होती हैं और `/etc/webmin/webmin.acl` में दर्ज होता है कि users किन modules तक पहुँच सकते हैं; [Webmin module-grant boundary का दस्तावेज़ देता है](https://webmin.com/docs/development/creating-modules/). Unix password या पढ़ी जा सकने वाली ACL file से अपने-आप Webmin session नहीं मिलता। वास्तविक authentication mapping, reachable listener, authenticated account, प्रभावी Package Updates module permission, installed code या vendor fix, और Webmin process identity की पुष्टि करें। 1.910 तक के प्रभावित builds में, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) के कारण उस module permission वाला account अपने update handler के ज़रिए commands चला सकता था। Passive enumeration के दौरान credentials दिखाए या update करने की कोशिश किए बिना configuration paths और permissions की रिपोर्ट करें।

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) service-specific authentication को नियंत्रित करता है; writable policy या module paths login behavior बदल सकते हैं।
- LDAP/SSSD configuration से directory endpoints, bind identities और access rules का पता चल सकता है। प्राप्त bind password से मौजूदा OS account से आगे की LDAP queries संभव हो सकती हैं; सटीक bind identity और directory ACLs की जाँच करें। Secrets देखने से पहले file permissions जाँचें; [Linux Active Directory](../user-information/linux-active-directory.md) और [FreeIPA](freeipa-pentesting.md) में ticket और directory के उपयोग की जानकारी है।
- Postfix aliases प्राप्त mail को local commands तक pipe कर सकते हैं। यदि कम privileges वाला user संदर्भित script बदल सकता है, तो mail delivery उसके code को delivery identity के अंतर्गत चला सकती है। इस path का दावा करने से पहले alias maps और script ownership जाँचें; [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md) देखें।
- Jenkins और अन्य CI services jobs को किसी शक्तिशाली local account के अंतर्गत चला सकती हैं। Pipeline या plugin की जाँच करने से पहले service user, writable job/workspace paths और local administration interface देखें। किसी job के लिए उपलब्ध **credentials** और वह account भी जाँचें जिसके रूप में वे authenticate कर सकते हैं: [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) का उपयोग करने वाला Pipeline, SSH credential के user के रूप में host तक पहुँच सकता है, भले ही Jenkins स्वयं कम privileges वाले Unix account के अंतर्गत चलता हो। Host privilege escalation का दावा करने से पहले पुष्टि करें कि मौजूदा Jenkins identity के पास Pipeline बदलने के लिए `Job/Create`, `Job/Configure` या कोई अन्य प्रभावी तरीका है, credential उस job के scope में है, और target SSH account उस key को स्वीकार करता है। Credential का display name या ID अकेले इनमें से किसी भी शर्त को साबित नहीं करता। Jenkins चेतावनी देता है कि job creators और अक्सर job configurators, अपने scope में उपलब्ध credentials का मनमाने ढंग से उपयोग कर सकते हैं; इसलिए [credential scope](https://www.jenkins.io/doc/book/security/credentials/) और [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) service UID जितने ही महत्वपूर्ण हैं। Shared enumeration output में credential values और private keys न रखें।

## Gogs repository file writes

Local Gogs service के लिए `gogs web` process owner का मिलान executable version और `custom/conf/app.ini` से करें। Configuration से service identity, repository root, listener address और registration disabled है या नहीं, इसका पता चल सकता है। केवल loopback पर सुनने वाला listener भी local users के लिए reachable होता है। 0.13.3 तक के Gogs versions में authenticated `PutContents` symlink file-write issue ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)) है: repository writer symlink commit कर सकता है और फिर API write को उसके माध्यम से निर्देशित कर सकता है। इस तरह होने वाली file access, Gogs process के privileges के अंतर्गत होती है, इसलिए root-owned instance पर तुरंत ध्यान देना चाहिए। Usable path का दावा करने से पहले deployed fix और authentication requirements की पुष्टि करें; API error यह साबित नहीं करता कि file write विफल हुआ।

## Gitea repository-description XSS and privileged viewers

Gitea 1.22.0 में repository description के भीतर stored JavaScript की अनुमति थी ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); 1.22.1 में इसे ठीक किया गया। Description edit कर सकने वाला user, अधिक privileges वाले browser session को प्रभावित कर सकता है, यदि वह user repository देखे और malicious link को सक्रिय करे। फिर उस browser identity से private repository content या अन्य application data उजागर हो सकता है। इससे अलग local escalation के लिए उस content के माध्यम से reachable credential या permission आवश्यक है, जैसे दोबारा इस्तेमाल किया गया administrator password; केवल Gitea process owner से root impact साबित नहीं होता। इस chain का दावा करने से पहले deployed version, description-edit access, viewer workflow और वास्तविक browser interaction जाँचें।

## Cobbler provisioning API

Cobbler की management service XML-RPC API उपलब्ध कराती है, जो आम तौर पर port `25151` पर होती है। Impact का आकलन करने से पहले listener और `cobblerd` process owner जाँचें; केवल loopback पर उपलब्ध API तक भी host पर मौजूद user पहुँच सकता है। `/etc/cobbler/modules.conf` में authentication और authorization modules, `/etc/cobbler/settings` या `/etc/cobbler/settings.yaml` में service settings, और `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` तथा `/var/lib/cobbler/web.ss` पर permissions जाँचें। Digest और shared-secret files में credential material होता है, इसलिए सामान्यतः उनकी contents दिखाए बिना उनकी readability दर्ज करें।

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** Cobbler 3.0.0 से 3.2.2 और 3.3.0 से 3.3.6 में XML-RPC authentication bypass है। Shared-secret पढ़ने में हुई त्रुटि से अनुमान लगाने योग्य `-1` मान वापस आया, जिसे API ने password के रूप में स्वीकार कर लिया। इसके संबंधित fixes 3.2.3 और 3.3.7 में हैं। Package version केवल शुरुआती संकेत है; exposure की रिपोर्ट करने से पहले deployed code और backported fix की पुष्टि करें।

जब `cobblerd` root के रूप में चलता है, तो authenticated API session से privileged execution path मिल सकता है। प्रभावित implementations में, `background_import` user-controlled `rsync_flags` को shell command में भेजता है, और user-controlled Cheetah autoinstall template को render करने पर Python evaluate हो सकता है। इनमें से किसी भी path को test करने से पहले API permissions और installed version जाँचें। Management API तक पहुँच सीमित करें, authentication bypass को patch करें, और configuration तथा credential files को केवल service administrators के लिए readable रखें।

## Motion और motionEye configuration

`/etc/motioneye/motioneye.conf` में `conf_path` देखें, फिर उस directory में `motion.conf` और कुछ `camera-*.conf` files की जाँच करें। बताएँ कि readable `# @admin_password` hash मौजूद है या नहीं—इसे प्रिंट न करें। [MotionEye के पुराने releases ने इन files को व्यापक read permissions के साथ लिखा था](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); इसका fix 0.44.0 में है। Motion की `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method`, और `webcontrol_localhost` settings को एक साथ जाँचें: authentication disabled होने पर advanced control (`2` या `3`) किसी local user को शक्तिशाली operations तक पहुँच दे सकता है, loopback listener पर भी। [Motion इन values और defaults का दस्तावेज़ देता है](https://motion-project.github.io/motion_config.html).

0.43.1b5 से पुराने motionEye में, Motion द्वारा camera filename setting को process करने पर admin session उसे command execution में बदल सकता था ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx))। Escalation का दावा करने से पहले running version, service identity, इस्तेमाल किया जा सकने वाला authentication path, और camera configured है या नहीं, इसकी पुष्टि करें। केवल configuration से यह साबित नहीं होता कि service चल रही है या privileged है।

Service name या installed package केवल शुरुआती संकेत है। Privilege boundary, reachable input, process identity, writable configuration, और उसके नियंत्रण में आने वाले command या file—इन सबका मेल है।

## Local AWS emulators और stored credentials

Host user published loopback endpoint के ज़रिए container में चल रहे AWS-compatible emulator तक पहुँच सकता है। [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) या [KMS](https://docs.localstack.cloud/aws/services/kms/) तक पहुँच का आकलन करने से पहले live listener, client द्वारा चुने गए endpoint और account, तथा emulator की installed authorization settings का मिलान करें। LocalStack में, [IAM policy enforcement एक अलग setting है](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); केवल credential file, IAM policy या listener के आधार पर प्रभावी API permissions का अनुमान न लगाएँ। Installed release और configuration के व्यवहार की पुष्टि करें।

Stored secret से local escalation तभी संभव है जब मौजूदा API identity उसे retrieve कर सके और कोई अलग, higher-privileged account प्राप्त credential स्वीकार करे। Encrypted local blob के लिए file read access, उससे मेल खाती usable KMS key और algorithm, तथा प्रभावी decrypt access भी आवश्यक हैं। [Asymmetric KMS key](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) के लिए, decrypt request में blob encrypt करने के लिए इस्तेमाल किया गया algorithm निर्दिष्ट होना चाहिए। Automatic host inventory को process, listener, configuration-path और file-permission के प्रमाण तक सीमित रखें; routine enumeration के दौरान secret values या decrypted plaintext न माँगें और न प्रिंट करें।
