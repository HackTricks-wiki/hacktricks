# Servicios web locales y de autenticación

{{#include ../../banners/hacktricks-training.md}}

Una shell de Linux ofrece una vista desde el host de los servicios web y de autenticación: argumentos de procesos, listeners, archivos de unidad, configuración, logs e interfaces accesibles solo localmente. Usa esa vista para relacionar un servicio accesible con la cuenta y los archivos que realmente utiliza.

## Mapear la pila web local

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecciona los nombres de virtual-host, las raíces de documentos, las rutas de proxy, los directorios de carga, la configuración de ejecución de PHP y los archivos de configuración que contengan credenciales. Es posible acceder a un listener de loopback a través de un proxy o un túnel SSH. Para probar un virtual host con nombre contra un listener local, envía el encabezado `Host` previsto o usa `curl --resolve` con la dirección y el puerto correctos. La enumeración de virtual hosts también puede revelar nombres ausentes de la respuesta predeterminada. Comprueba si Apache permite sobrescrituras mediante `.htaccess` y si las rutas de carga pueden ejecutar PHP antes de considerar que un directorio de carga con permisos de escritura permite la ejecución de código. Un source map de JavaScript desplegado puede revelar rutas de origen o secretos del lado del cliente; trata los valores recuperados como pistas y verifica sus privilegios reales. Para comprobaciones específicas de web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) y [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

En Apache con [mpm-itk](https://mpm-itk.sesse.net/), una directiva `AssignUserID` activa puede ejecutar un virtual host con un usuario y grupo diferentes. Si una cuenta con menos privilegios puede escribir un script en el `DocumentRoot` de ese host, revisa si una ruta accesible realmente lo ejecuta con la identidad asignada. Confirma que el módulo esté cargado, la configuración efectiva del virtual host (incluidas las sobrescrituras de identidad basadas en expresiones), los permisos de escritura y búsqueda del directorio, el handler del script y el acceso al listener. Una directiva destacada o un directorio con permisos de escritura no demuestran por sí solos la ejecución con la identidad de otro usuario.

Un directorio personal publicado mediante un servidor web puede exponer archivos de respaldo con archivos de identidad SSH, aunque el directorio `.ssh` activo sea privado. Por ejemplo, el ajuste `homedirs_public` de [Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) selecciona un subdirectorio servido desde los directorios personales de los usuarios. Encontrar únicamente la ruta del archivo es una pista: verifica la asignación efectiva del servidor, la legibilidad local o la autorización HTTP, el contenido del archivo de respaldo, la frase de contraseña de la clave privada y si la cuenta correspondiente realmente acepta la clave. No extraigas archivos de respaldo ni imprimas material de claves durante la enumeración rutinaria del host.

Un archivo de respaldo legible de una aplicación web local con más privilegios puede revelar la lógica de autenticación y lectura de archivos, aunque no se pueda acceder al código fuente activo. Compara el archivo de respaldo con el servicio desplegado antes de confiar en él. En particular, conviene revisar una cookie construida cifrando texto controlado por quien realiza la solicitud seguido de un secreto y una marca de rol si la aplicación usa bloques ECB deterministas, devuelve cookies nuevas para texto elegido y luego divide el valor descifrado usando un delimitador sin escapar. [NIST explica el mapeo de bloques independiente y repetible de ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); esa propiedad puede permitir una comparación con entradas elegidas, pero no otorga por sí misma un rol superior. Confirma la ruta activa, los requisitos previos de sesión, el flujo exacto del parser y los datos, la identidad del servicio y una acción privilegiada independiente o una ruta de lectura de archivos. El inventario pasivo debe informar los metadatos del archivo de respaldo y la propiedad del listener sin leer su contenido ni enviar pruebas de autenticación.

El mismo enfoque de revisión de código fuente se aplica a un servicio local privilegiado **que no sea HTTP**, como una interfaz personalizada basada en SSH. Si una copia de respaldo accesible del código fuente muestra un comando que acepta una ruta de archivo elegida por quien realiza la solicitud, comprueba su control de autenticación, cómo resuelve la ruta y si verifica que el archivo resuelto permanezca dentro de un directorio previsto antes de abrirlo. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normaliza una ruta, pero no garantiza que permanezca dentro de ese directorio. Confirma que el archivo de respaldo coincida con la compilación en ejecución, que el listener sea accesible, que la cuenta con menos privilegios pueda usar el comando y que el proceso pueda leer el objetivo; disponer de una clave SSH legible es una cuestión aparte de la política de inicio de sesión. Informa las rutas de los archivos de respaldo del código fuente y la propiedad del servicio sin extraer su contenido ni claves en la salida automatizada.

Un pool de PHP-FPM que escucha en el loopback TCP puede ser accesible desde otra cuenta local aunque el sitio web requiera autenticación. [PHP advierte que un cliente capaz de conectarse a FastCGI puede controlar los ajustes de la solicitud, incluido `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revisa los ajustes `listen` y `listen.allowed_clients` del pool junto con el listener activo, el UID del worker, una ruta de script existente y las restricciones `security.limit_extensions` o `php_admin_value`. Los archivos de configuración del pool pueden contener credenciales en directivas `env[...]`, por lo que el inventario automatizado debe informar sus rutas, no su contenido. Un archivo de configuración o un puerto por sí solos no demuestran que exista una vía de ejecución entre usuarios; consulta la [guía de FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para conocer los detalles del protocolo.

En una API local privilegiada, sigue el flujo de autorización además del de ejecución de código. Un rol de base de datos que la cuenta con menos privilegios pueda cambiar podría habilitar una ruta de la API, pero el siguiente límite depende de la implementación de esa ruta. Por ejemplo, combinar JSON de una solicitud en un objeto JavaScript y luego llamar a [`child_process.exec`](https://nodejs.org/api/child_process.html) requiere revisar el [flujo de datos de prototype pollution a ejecución](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la biblioteca y versión de combinación reales, la validación de entradas, la ruta accesible, la identidad del proceso y las opciones del proceso hijo; un listener de Node propiedad de root o el nombre de una dependencia vulnerable son solo pistas.

Los CMS que almacenan datos en archivos pueden guardar verificadores de contraseñas de administrador fuera de los archivos de configuración `.php` convencionales. Algunos ejemplos son `data/database.js` o `data/settings/pass.php` de un sitio. Comprueba la propiedad y legibilidad del archivo antes de revisarlo manualmente, y no incluyas hashes en la salida automatizada compartida. Una contraseña de aplicación recuperable constituye un límite de privilegios distinto al de una cuenta Unix: verifica cualquier reutilización alegada para la cuenta específica y el método de autenticación permitido.

El controlador de autenticación de una aplicación también puede contener una contraseña de inicio de sesión literal en el código fuente, en lugar de un archivo de configuración. Si un usuario con menos privilegios puede leer el controlador desplegado, revisa localmente su comparación de autenticación y no incluyas ningún valor en la salida compartida de enumeración. Confirma que la ruta de código esté activa, que la contraseña sea válida para la aplicación y que una cuenta Unix independiente con más privilegios acepte realmente esa misma contraseña antes de afirmar que permite escalar privilegios localmente. El nombre de un controlador es solo una pista para revisar.

Dolibarr almacena los ajustes de conexión a la base de datos, incluido `dolibarr_main_db_pass`, en `htdocs/conf/conf.php` ([referencia de configuración](https://wiki.dolibarr.org/index.php/Configuration_file)). Un archivo legible es una pista de que puede contener credenciales; solo una reutilización de contraseña de cuenta verificada por separado u otro permiso de base de datos permitiría escalar privilegios localmente. Inspecciona primero los permisos y evita imprimir el valor en la salida automatizada.

La configuración del paquete Linux de GitLab suele estar en `/etc/gitlab/gitlab.rb`, aunque las instalaciones pueden conservar copias legibles en otros lugares. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que este archivo puede contener `gitlab_rails['smtp_password']`, aunque los ajustes SMTP cifrados pueden guardar la contraseña fuera del archivo de texto sin formato. Trata una configuración legible como una pista de credenciales: verifica que esté activa, que la credencial siga vigente y que una cuenta específica con más privilegios la acepte antes de afirmar que se reutiliza la contraseña. Por otra parte, [GitLab ejecuta `gitlab.rb` como código Ruby con privilegios de root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); para que un archivo activo con permisos de escritura o un archivo incluido mediante `from_file` constituya un hallazgo de ejecución, debe existir una ruta real de reconfiguración privilegiada. Una vista previa de la configuración puede exponer valores de credenciales, así que trata su salida como información confidencial y comparte únicamente las rutas y los permisos.

Una instalación autohospedada de Mattermost puede guardar `SqlSettings.DataSource` en `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esa ruta habitual como instalaciones que almacenan la configuración activa en una base de datos. Un archivo legible puede exponer una credencial de base de datos de la aplicación, pero no demuestra que se pueda acceder a la base de datos ni obtener acceso Unix a root. Verifica el origen de la configuración activa, los permisos reales del rol de base de datos, cualquier contraseña de aplicación recuperada por separado y si esa contraseña funciona para una cuenta Unix específica con más privilegios. El formato del hash de contraseña puede cambiar entre versiones de Mattermost; durante la enumeración, registra la ruta de configuración y los metadatos de acceso sin imprimir la cadena de conexión ni consultar la base de datos.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra los resultados de virtual hosts comparándolos con el tamaño de la respuesta predeterminada u otra referencia estable, para que cada nombre probado no parezca válido. Un source map solo es útil si realmente está desplegado o se puede leer de otro modo.

Los proxies inversos pueden cambiar qué encabezados del cliente considera confiables una aplicación. Compara las solicitudes directas y las enviadas a través del proxy antes de asumir que `X-Forwarded-For`, `X-Forwarded-Host` o encabezados similares establecen la identidad de quien realiza la solicitud. Revisa conjuntamente la configuración del proxy y de la aplicación.

Si PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` en una cadena que se pasa a [`system()`](https://www.php.net/manual/en/function.system.php), revisa si la ruta de solicitud accesible permite que quien realiza la solicitud proporcione un encabezado y si los metacaracteres del shell llegan intactos a esa cadena. Un comando como `sudo iptables` al principio **no** hace que los comandos posteriores separados por el shell se ejecuten como root; esos se ejecutan como el worker web, salvo que una regla sudo efectiva independiente permita la escalada. Confirma la identidad del worker, la autorización exacta de `sudo -l` y sus requisitos de autenticación, y los límites de los argumentos del comando antes de afirmar que existe una ruta a root. Inspecciona el código fuente y las políticas sin enviar una prueba de inyección durante el reconocimiento rutinario del host.

## Credenciales de inicio de sesión en los logs de acceso

Si una aplicación envía un formulario de inicio de sesión con `GET`, el nombre de usuario y la contraseña pueden convertirse en parámetros de consulta en el URI de la solicitud. Una solicitud `POST` también puede contener una cadena de consulta; usar `POST` no oculta un secreto colocado accidentalmente en el URI, incluida una contraseña introducida en un campo de formulario no relacionado. [La línea de solicitud del log de acceso común de Apache](https://httpd.apache.org/docs/2.4/logs.html) registra el método y el URI, incluida su cadena de consulta, cuando el formato configurado usa `%r`. Por lo tanto, una cuenta con permiso para leer esos logs, por ejemplo, mediante el grupo `adm` en algunos sistemas Linux, podría encontrar una pista sobre credenciales. Comprueba el formato real del log y los permisos; luego verifica que el valor sea un secreto, que la cuenta lo acepte y que permita cruzar un límite de privilegios. No supongas que se registró el cuerpo de la solicitud ni copies valores candidatos en una salida compartida.

Inspecciona solo los logs de acceso que puedas leer y mantén los valores de credenciales fuera de la salida compartida de comandos. Las líneas de solicitud largas también pueden contener un referer y un user agent, por lo que un filtro para líneas cortas puede ocultar justo la solicitud que interesa. Las ubicaciones habituales de los logs de acceso de Apache, httpd y Nginx son `/var/log/apache2/access.log`, `/var/log/httpd/access_log` y `/var/log/nginx/access.log`. Los logs rotados pueden contener credenciales antiguas. [El acceso a archivos de log mediante LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) es una ruta relacionada hacia los mismos datos.

Los logs de autenticación de las aplicaciones también pueden exponer una contraseña introducida accidentalmente en el campo de **nombre de usuario** durante un inicio de sesión fallido. Primero comprueba que el log se pueda leer y que su formato registre el nombre de usuario enviado; inspecciona localmente solo una pequeña sección pertinente y no copies credenciales candidatas en una salida compartida. Un nombre de usuario con aspecto de contraseña es una pista, no una prueba de que sea una contraseña válida ni de que otorgue más privilegios. Verifica la cuenta prevista y cualquier reutilización de contraseña en el servicio concreto o la cuenta Unix antes de afirmar que hay una transición.

Un handler de inicio de sesión web con permisos de escritura requiere una revisión aparte cuando un cliente programado con otra identidad envía credenciales a ese endpoint. Confirma el permiso de escritura sobre el handler **activo**, el horario y la ruta de solicitud reales del cliente, a quién pertenecen las credenciales que envía y si esa contraseña de la aplicación es válida de forma independiente para una cuenta del sistema operativo con más privilegios. Una página con permisos de escritura o un proceso recurrente, por sí solos, no demuestran esa transición. El inventario pasivo debe informar sobre los permisos de las rutas y los metadatos de las tareas sin modificar el handler ni recopilar contraseñas.

Los logs EVE JSON de Suricata también pueden registrar los comandos FTP `USER` y `PASS` con su `command_data` cuando está habilitado el registro de eventos FTP. Comprueba que se puedan leer `/var/log/suricata/eve*.json*`, incluidos los archivos rotados o comprimidos, antes de revisar localmente una pequeña sección pertinente. Un archivo EVE legible es solo una pista: confirma que se registraron eventos FTP, que los datos incluyen credenciales utilizables y que permiten cruzar un límite de privilegios. Evita mostrar `command_data` en la salida compartida del reconocimiento. Suricata documenta los [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) y [las variantes de rotación y nombres de archivo de EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuración de Apache generada y logs enviados a comandos

[remco](https://github.com/HeavyHorst/remco) puede observar un backend de clave/valor, renderizar una plantilla en un archivo de configuración de Apache y ejecutar un comando de recarga. Inspecciona la identidad del proceso remco en ejecución, la fuente y el destino de la plantilla configurada, los prefijos de claves observados y si un valor del backend se inserta directamente en una directiva de Apache como `ServerName`. Que haya un listener local del backend no demuestra por sí solo que el usuario actual pueda escribir una clave observada; verifica la autenticación y los permisos del backend antes de afirmar que existe una escalada.

Un salto de línea sin escapar en un valor modificable del backend puede convertir el valor previsto de una directiva en directivas adicionales de Apache. Los [logs de Apache enviados a comandos](https://httpd.apache.org/docs/2.4/logs.html#piped) son especialmente sensibles: `CustomLog` o `ErrorLog` con un comando `|` inicia un helper con la identidad del proceso httpd padre, a menudo root; `|$` le indica a Apache que use un shell. Revisa la configuración generada y su ruta de recarga sin cambiar los datos del backend ni reiniciar el servicio durante el reconocimiento. Mantén privado el comando completo enviado a través de una tubería, ya que sus argumentos pueden contener secretos.

## Autenticación e identidades de servicio

El archivo de control de Monit suele ser `~/.monitrc` o `/etc/monitrc`, pero `monit -c` puede seleccionar otra ruta. Un archivo legible puede contener entradas `set httpd` y `allow user:password` para su interfaz web, a menudo en el puerto local 2812. Comprueba el propietario y los permisos del archivo antes de revisarlo, y mantén los valores de las contraseñas fuera de la salida compartida del reconocimiento. Las credenciales web solo otorgan el rol de Monit configurado; los usuarios de solo lectura no pueden ejecutar acciones de control. Para escalar a una cuenta Unix se requiere confirmar la reutilización de la contraseña o que el rol autenticado pueda activar una acción privilegiada de Monit. Consulta la [documentación de Monit sobre el archivo de control y la autenticación](https://www.mmonit.com/monit/documentation/monit.html).

En Webmin, `/etc/webmin/miniserv.conf` identifica la configuración del servidor y `/etc/webmin/webmin.acl` registra a qué módulos pueden acceder los usuarios; [Webmin documenta los límites de las autorizaciones de módulos](https://webmin.com/docs/development/creating-modules/). Una contraseña Unix o un archivo ACL legible no otorgan por sí solos una sesión de Webmin. Confirma la correspondencia de autenticación real, el listener accesible, la cuenta autenticada, el permiso efectivo del módulo Package Updates, el código instalado o la corrección del proveedor y la identidad del proceso Webmin. En las versiones afectadas hasta la 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitía que una cuenta con ese permiso de módulo ejecutara comandos mediante su handler de actualización. Durante el reconocimiento pasivo, informa de las rutas de configuración y los permisos sin mostrar credenciales ni intentar una actualización.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) rige la autenticación específica de cada servicio; las rutas de políticas o módulos con permisos de escritura pueden cambiar el comportamiento del inicio de sesión.
- La configuración de LDAP/SSSD puede revelar endpoints del directorio, identidades de enlace y reglas de acceso. Una contraseña de enlace recuperada puede permitir consultas LDAP que excedan las del usuario actual del sistema operativo; prueba la identidad de enlace exacta y las ACL del directorio. Revisa los permisos de los archivos antes de inspeccionar secretos; [Linux Active Directory](../user-information/linux-active-directory.md) y [FreeIPA](freeipa-pentesting.md) cubren el uso de tickets y directorios.
- Los alias de Postfix pueden canalizar el correo recibido a comandos locales. Si un usuario con menos privilegios puede modificar el script referenciado, la entrega del correo puede ejecutar su código con la identidad de entrega. Revisa los mapas de alias y la propiedad de los scripts antes de afirmar que existe esa vía; consulta [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins y otros servicios de CI pueden ejecutar trabajos con una cuenta local privilegiada. Inspecciona el usuario del servicio, las rutas de trabajos o espacios de trabajo con permisos de escritura y la interfaz de administración local antes de probar un pipeline o plugin. Revisa también las **credenciales disponibles para un trabajo** y la cuenta con la que pueden autenticarse: un Pipeline que use el [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) puede acceder a un host como el usuario de la credencial SSH, aunque Jenkins se ejecute con una cuenta Unix con menos privilegios. Confirma que la identidad actual de Jenkins tenga `Job/Create`, `Job/Configure` u otra vía efectiva para modificar el Pipeline, que la credencial esté dentro del ámbito de ese trabajo y que la cuenta SSH de destino acepte la clave antes de afirmar que existe una escalada de privilegios en el host. El nombre visible o el ID de una credencial, por sí solos, no confirman ninguna de estas condiciones. Jenkins advierte que quienes crean trabajos y, a menudo, quienes los configuran pueden usar arbitrariamente las credenciales disponibles dentro de su ámbito; por tanto, el [ámbito de las credenciales](https://www.jenkins.io/doc/book/security/credentials/) y la [confianza de Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) importan tanto como el UID del servicio. No incluyas valores de credenciales ni claves privadas en resultados de enumeración compartidos.

## Escrituras en archivos de repositorios de Gogs

Para un servicio local de Gogs, correlaciona el propietario del proceso `gogs web` con la versión del ejecutable y `custom/conf/app.ini`. La configuración puede revelar la identidad del servicio, la raíz del repositorio, la dirección de escucha y si el registro está deshabilitado. Incluso los usuarios locales pueden acceder a un listener que solo escucha en loopback. Las versiones de Gogs hasta la 0.13.3 inclusive tienen un problema de escritura de archivos mediante enlaces simbólicos en `PutContents` que requiere autenticación ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): quien pueda escribir en un repositorio puede confirmar un enlace simbólico y luego dirigir a través de él una escritura de la API. El acceso resultante a los archivos tiene los privilegios del proceso de Gogs, por lo que una instancia que se ejecute como root requiere atención inmediata. Valida la corrección implementada y los requisitos de autenticación antes de afirmar que existe una vía utilizable; un error de la API no demuestra que la escritura del archivo haya fallado.

## XSS en la descripción de repositorios de Gitea y usuarios con privilegios que la ven

Gitea 1.22.0 permitía JavaScript almacenado en la descripción de un repositorio ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versión 1.22.1 lo corrigió. Un usuario que pueda editar una descripción puede afectar una sesión de navegador con más privilegios si ese usuario visita el repositorio y activa el enlace malicioso. La identidad de ese navegador puede entonces exponer contenido de repositorios privados u otros datos de la aplicación. Una escalada local independiente requiere una credencial o permiso accesible mediante ese contenido, como una contraseña de administrador reutilizada; el propietario del proceso de Gitea, por sí solo, no demuestra un impacto de root. Comprueba la versión implementada, los permisos para editar descripciones, el flujo de visualización y la interacción real con el navegador antes de afirmar que la cadena es viable.

## API de aprovisionamiento de Cobbler

El servicio de administración de Cobbler expone una API XML-RPC, normalmente en el puerto `25151`. Comprueba el listener y el propietario del proceso `cobblerd` antes de evaluar su impacto; incluso un usuario del host puede acceder a una API que solo escucha en loopback. Revisa los módulos de autenticación y autorización en `/etc/cobbler/modules.conf`, la configuración del servicio en `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml`, y los permisos de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` y `/var/lib/cobbler/web.ss`. Los archivos de resumen criptográfico y de secreto compartido contienen material de credenciales, así que registra si se pueden leer sin mostrar su contenido de forma predeterminada.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** es un bypass de autenticación XML-RPC en Cobbler 3.0.0 a 3.2.2 y 3.3.0 a 3.3.6. Un error al leer el secreto compartido devolvía el valor predecible `-1`, que la API aceptaba como contraseña. Las correcciones correspondientes están en las versiones 3.2.3 y 3.3.7. La versión de un paquete es solo una pista; verifica el código desplegado y cualquier corrección retroportada antes de informar que el sistema está expuesto.

Una sesión autenticada de la API puede permitir una ejecución privilegiada si `cobblerd` se ejecuta como root. En las implementaciones afectadas, `background_import` pasa `rsync_flags` controlado por el usuario a un comando de shell, y al renderizar una plantilla de autoinstalación Cheetah controlada por el usuario se puede ejecutar Python. Antes de probar cualquiera de estas vías, comprueba los permisos de la API y la versión instalada. Restringe el acceso a la API de administración, aplica el parche para el bypass de autenticación y limita la lectura de los archivos de configuración y credenciales a los administradores del servicio.

## Configuración de Motion y motionEye

Inspecciona `/etc/motioneye/motioneye.conf` para localizar `conf_path`; después, revisa `motion.conf` y una pequeña cantidad de archivos `camera-*.conf` en ese directorio. Informa si existe un hash `# @admin_password` legible, sin imprimirlo. [Las versiones anteriores de motionEye guardaban estos archivos con permisos de lectura amplios](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la corrección está en la versión 0.44.0. Comprueba conjuntamente los ajustes de Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` y `webcontrol_localhost`: el control avanzado (`2` o `3`) con la autenticación deshabilitada puede exponer operaciones potentes a un usuario local, incluso si el listener está en loopback. [Motion documenta los valores y los valores predeterminados](https://motion-project.github.io/motion_config.html).

Una sesión de administrador en motionEye anterior a la versión 0.43.1b5 podía convertir un ajuste de nombre de archivo de cámara en ejecución de comandos cuando Motion lo procesaba ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Antes de afirmar que hay una escalada, confirma la versión en ejecución, la identidad del servicio, si existe una vía de autenticación utilizable y si hay una cámara configurada. La configuración por sí sola no demuestra que el servicio esté en ejecución ni que tenga privilegios.

El nombre de un servicio o un paquete instalado es solo una pista. El límite de privilegios depende de la combinación de la entrada accesible, la identidad del proceso, la configuración con permisos de escritura y el comando o archivo que controla en última instancia.

## Emuladores locales de AWS y credenciales almacenadas

Un usuario del host puede acceder a un emulador compatible con AWS que se ejecuta en un contenedor a través de su endpoint de loopback publicado. Antes de evaluar el acceso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), correlaciona el listener activo, el endpoint y la cuenta seleccionados por el cliente, y los ajustes de autorización instalados en el emulador. En LocalStack, [la aplicación de políticas de IAM es un ajuste independiente](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); no deduzcas los permisos efectivos de la API a partir únicamente de un archivo de credenciales, una política de IAM o un listener. Confirma el comportamiento de la versión y la configuración instaladas.

Un secreto almacenado solo sirve para una escalada local si la identidad actual de la API puede recuperarlo y una cuenta independiente con privilegios superiores acepta la credencial recuperada. Un blob local cifrado también requiere acceso de lectura al archivo, la clave KMS correspondiente y utilizable, el algoritmo correcto y permisos de descifrado efectivos. Para una [clave KMS asimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la solicitud de descifrado debe especificar el algoritmo utilizado para cifrar el blob. Limita el inventario automático del host a evidencias sobre procesos, listeners, rutas de configuración y permisos de archivos; durante la enumeración rutinaria, no solicites ni imprimas valores secretos ni texto en claro descifrado.
