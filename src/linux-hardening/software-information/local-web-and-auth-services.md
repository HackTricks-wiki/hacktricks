# Serviços locais de Web e autenticação

{{#include ../../banners/hacktricks-training.md}}

Um shell Linux oferece uma visão do host dos serviços de Web e autenticação: argumentos de processos, listeners, arquivos de unit, configurações, logs e interfaces acessíveis apenas localmente. Use essa visão para associar um serviço acessível à conta e aos arquivos que ele realmente utiliza.

## Mapear a stack local de Web

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecione nomes de virtual hosts, document roots, rotas de proxy, diretórios de upload, configurações de execução do PHP e arquivos de configuração que contenham credenciais. Um listener de loopback pode ser acessível por meio de um proxy ou túnel SSH. Para testar um virtual host nomeado contra um listener local, envie o cabeçalho `Host` pretendido ou use `curl --resolve` com o endereço e a porta corretos. A enumeração de virtual hosts também pode revelar nomes ausentes na resposta padrão. Verifique se o Apache permite substituições por `.htaccess` e se os caminhos de upload podem executar PHP antes de tratar um diretório de upload gravável como execução de código. Um source map de JavaScript implantado pode expor caminhos do código-fonte ou segredos do lado do cliente; trate os valores recuperados como pistas e verifique suas permissões efetivas. Para verificações específicas de web, consulte [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

No Apache com [mpm-itk](https://mpm-itk.sesse.net/), um `AssignUserID` ativo pode executar um virtual host com um usuário e grupo diferentes. Se uma conta com menos privilégios puder gravar um script no `DocumentRoot` desse host, verifique se uma rota acessível realmente o executa com a identidade atribuída. Confirme se o módulo está carregado, a configuração efetiva do virtual host (incluindo substituições de identidade baseadas em expressões), as permissões de gravação e busca no diretório, o handler do script e o acesso ao listener. Uma diretiva destacada ou um diretório gravável, por si só, não comprova execução entre usuários.

Um diretório home publicado por um servidor web pode expor arquivos de backup de identidades SSH mesmo quando o diretório `.ssh` ativo é privado. Por exemplo, a configuração [`homedirs_public` do Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleciona um subdiretório servido a partir dos diretórios home dos usuários. Encontrar apenas o caminho de um arquivo é uma pista: verifique o mapeamento efetivo do servidor, a legibilidade local ou a autorização HTTP, o conteúdo do arquivo, a passphrase da chave privada e se a conta correspondente realmente aceita a chave. Não extraia arquivos nem exiba material de chave durante a enumeração rotineira do host.

Um backup legível de um aplicativo web local com mais privilégios pode revelar a lógica de autenticação e leitura de arquivos, mesmo quando seu código-fonte ativo está inacessível. Compare o backup com o serviço implantado antes de confiar nele. Em particular, vale revisar um cookie criado ao criptografar texto controlado pelo chamador seguido de um segredo e uma flag de função, caso o app use blocos ECB determinísticos, retorne cookies novos para textos escolhidos e depois divida o valor descriptografado por um delimitador sem escape. [A NIST explica o mapeamento independente e repetível de blocos do ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); essa propriedade pode permitir uma comparação com entrada escolhida, mas, por si só, não concede uma função mais privilegiada. Confirme a rota ativa, os pré-requisitos da sessão, o parser e o fluxo de dados exatos, a identidade do serviço e uma ação privilegiada ou caminho de leitura de arquivos separado. O inventário passivo deve informar os metadados do backup e a propriedade do listener sem ler o conteúdo do arquivo nem enviar sondas de autenticação.

A mesma abordagem de análise de código-fonte se aplica a um serviço local privilegiado **que não seja HTTP**, como uma interface personalizada baseada em SSH. Se um backup de código-fonte acessível mostrar um comando que aceita um caminho de arquivo escolhido pelo chamador, verifique a barreira de autenticação, como o caminho é resolvido e se o código garante que o arquivo resolvido permaneça dentro de um diretório pretendido antes de abri-lo. Em Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normaliza um caminho, mas não impõe esse confinamento. Confirme se o backup corresponde à versão em execução, se o listener é acessível, se a conta com menos privilégios pode usar o comando e se o processo pode ler o alvo; possuir uma chave SSH legível é uma questão separada, relacionada à política de login. Informe os caminhos dos arquivos de código-fonte e a propriedade do serviço sem extrair o conteúdo dos arquivos ou as chaves para a saída automatizada.

Um pool PHP-FPM que escuta no loopback TCP pode ser acessado por outra conta local, mesmo que o site exija autenticação. [O PHP alerta que um cliente capaz de se conectar ao FastCGI pode controlar configurações da requisição, incluindo `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revise as configurações `listen` e `listen.allowed_clients` do pool junto com o listener ativo, o UID do worker, um caminho de script existente e quaisquer restrições `security.limit_extensions` ou `php_admin_value`. Arquivos de configuração do pool podem conter credenciais em diretivas `env[...]`; portanto, o inventário automatizado deve informar seus caminhos, não seu conteúdo. Um arquivo de configuração ou uma porta, por si só, não comprova um caminho de execução entre usuários; consulte o [guia de FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para obter detalhes do protocolo.

Para uma API local privilegiada, analise a autorização além da execução de código. Uma função de banco de dados que a conta com menos privilégios pode alterar pode liberar uma rota da API, mas o limite seguinte depende da implementação da rota. Por exemplo, mesclar JSON da requisição em um objeto JavaScript e depois chamar [`child_process.exec`](https://nodejs.org/api/child_process.html) justifica a análise do [fluxo de dados de prototype pollution até execução](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifique a biblioteca e a versão reais usadas na mesclagem, a validação da entrada, a rota acessível, a identidade do processo e as opções do processo filho; um listener Node pertencente ao root ou o nome de uma dependência vulnerável, por si só, é apenas uma pista.

Armazenamentos de CMS baseados em arquivos podem manter verificadores de senha de administrador fora dos arquivos de configuração `.php` convencionais. Exemplos incluem `data/database.js` ou `data/settings/pass.php` de um site. Verifique a propriedade e a legibilidade dos arquivos antes da análise manual e não inclua hashes na saída automatizada compartilhada. Uma senha recuperável do aplicativo representa um limite de privilégio diferente de uma conta Unix: verifique qualquer reutilização alegada com a conta específica e o método de autenticação permitido.

O controller de autenticação de um aplicativo também pode conter uma senha de login literal no código-fonte, em vez de em um arquivo de configuração. Se um usuário com menos privilégios puder ler o controller implantado, analise localmente a comparação de autenticação e não inclua nenhum valor na saída de enumeração compartilhada. Confirme que o caminho de código está ativo, que a senha é válida no aplicativo e que uma conta Unix separada, com mais privilégios, realmente aceita a mesma senha antes de alegar escalada local. O nome de um arquivo de controller, por si só, é apenas uma pista para análise.

O Dolibarr armazena configurações de conexão com o banco de dados, incluindo `dolibarr_main_db_pass`, em `htdocs/conf/conf.php` ([referência de configuração](https://wiki.dolibarr.org/index.php/Configuration_file)). Um arquivo legível é uma pista de credencial; somente uma reutilização de senha de conta verificada separadamente ou outra permissão no banco de dados permitiria escalada de privilégios local. Verifique as permissões primeiro e evite exibir o valor na saída automatizada.

A configuração do pacote Linux do GitLab normalmente fica em `/etc/gitlab/gitlab.rb`, embora implantações possam manter cópias legíveis em outros locais. [A documentação do GitLab](https://docs.gitlab.com/omnibus/settings/smtp/) informa que esse arquivo pode conter `gitlab_rails['smtp_password']`, embora configurações SMTP criptografadas possam manter a senha fora do arquivo em texto simples. Trate uma configuração legível como uma pista de credencial: verifique se está ativa, se a credencial ainda é válida e se uma conta específica com mais privilégios a aceita antes de alegar reutilização de senha. Separadamente, [o GitLab executa `gitlab.rb` como código Ruby sob o root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); para que um arquivo ativo gravável ou um `from_file` incluído represente uma descoberta de execução, é necessário que haja um caminho real para executar a reconfiguração com privilégios. Uma prévia da configuração pode expor valores de credenciais; trate sua saída como sensível e compartilhe apenas os caminhos e as permissões.

Uma instalação self-hosted do Mattermost pode manter `SqlSettings.DataSource` em `/opt/mattermost/config/config.json`; [a documentação do Mattermost](https://docs.mattermost.com/deployment-guide/server/troubleshooting) descreve tanto esse caminho usual quanto implantações que armazenam a configuração ativa em um banco de dados. Um arquivo legível pode expor uma credencial do banco de dados do aplicativo, mas não comprova acesso ao banco nem acesso ao root do Unix. Verifique a fonte de configuração ativa, as permissões reais da função do banco de dados, qualquer senha do aplicativo recuperada separadamente e se essa senha funciona para uma conta Unix específica com mais privilégios. O formato do hash de senha pode mudar entre versões do Mattermost; durante a enumeração, registre o caminho da configuração e os metadados de acesso sem exibir a string de conexão nem consultar o banco de dados.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtre os resultados de virtual-host pelo tamanho da resposta padrão ou por outra referência estável, para que cada nome testado não pareça válido. Um source map só é útil se estiver realmente implantado ou puder ser lido por outro meio.

Reverse proxies podem alterar quais cabeçalhos do cliente uma aplicação considera confiáveis. Compare solicitações diretas e via proxy antes de presumir que `X-Forwarded-For`, `X-Forwarded-Host` ou cabeçalhos semelhantes estabeleçam a identidade de quem fez a chamada. Analise em conjunto as configurações do proxy e da aplicação.

Se o PHP copiar `$_SERVER['HTTP_X_FORWARDED_FOR']` para uma string passada a [`system()`](https://www.php.net/manual/en/function.system.php), verifique se o caminho de solicitação acessível permite um cabeçalho fornecido por quem fez a chamada e se os metacaracteres do shell chegam inalterados a essa string. Um comando como `sudo iptables` no início **não** faz com que comandos posteriores separados pelo shell sejam executados como root; eles são executados como o worker web, a menos que uma regra sudo efetiva separada permita a escalada. Confirme a identidade do worker, a concessão exata de `sudo -l` e o requisito de autenticação, além do limite dos argumentos do comando, antes de afirmar que existe um caminho para root. Inspecione o código-fonte e a política sem enviar uma tentativa de injection durante a enumeração rotineira do host.

## Credenciais de login nos logs de acesso

Se uma aplicação enviar um formulário de login com `GET`, o nome de usuário e a senha podem se tornar parâmetros de consulta na URI da solicitação. Uma solicitação `POST` também pode conter uma query string; usar `POST` não oculta um segredo colocado acidentalmente na URI, incluindo uma senha inserida em um campo de formulário não relacionado. A [linha de solicitação do log de acesso comum do Apache](https://httpd.apache.org/docs/2.4/logs.html) registra o método e a URI, incluindo a query string, quando o formato configurado usa `%r`. Portanto, uma conta com permissão para ler esses logs, por exemplo, por meio do grupo `adm` em alguns sistemas Linux, pode encontrar uma pista de credencial. Verifique o formato e as permissões reais do log e, em seguida, confirme que o valor é um segredo, que a conta o aceita e que ele atravessa uma fronteira de privilégios. Não presuma que o corpo da solicitação foi registrado nem copie valores candidatos para uma saída compartilhada.

Inspecione apenas logs de acesso que possam ser lidos e mantenha os valores das credenciais fora da saída compartilhada de comandos. Linhas longas de solicitação também podem conter um referrer e um user agent; por isso, um filtro de linhas curtas pode ocultar justamente a solicitação relevante. Os locais comuns dos logs de acesso do Apache, httpd e Nginx são `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. Logs rotacionados podem conter credenciais antigas. O [acesso a arquivos de log por meio de LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) é uma rota relacionada aos mesmos dados.

Os logs de autenticação da aplicação também podem expor uma senha inserida acidentalmente no campo de **nome de usuário** de uma tentativa de login malsucedida. Primeiro, confirme que o log pode ser lido e que seu formato registra o nome de usuário enviado; inspecione apenas um pequeno trecho relevante localmente e não copie credenciais candidatas para uma saída compartilhada. Um nome de usuário com aparência de senha é uma pista, não prova de que seja uma senha válida ou de que ofereça privilégios maiores. Verifique a conta pretendida e qualquer reutilização na conta Unix ou no serviço específico antes de afirmar que há uma transição.

Um handler de login web com permissão de escrita requer uma análise separada quando um cliente agendado, executado sob outra identidade, envia credenciais a esse endpoint. Confirme o acesso de escrita ao handler **ativo**, o agendamento real do cliente e o caminho da solicitação, de quem são as credenciais enviadas e se a senha da aplicação é válida, de forma independente, para uma conta do sistema operacional com privilégios maiores. Uma página gravável ou um processo recorrente, por si só, não comprova essa transição. O inventário passivo deve registrar as permissões dos caminhos e os metadados das tarefas sem modificar o handler nem coletar senhas.

Os logs EVE JSON do Suricata também podem registrar os comandos FTP `USER` e `PASS` com seus dados em `command_data` quando o registro de eventos FTP está habilitado. Verifique se `/var/log/suricata/eve*.json*` pode ser lido, incluindo arquivos rotacionados ou compactados, antes de analisar localmente um pequeno trecho relevante. Um arquivo EVE legível é apenas uma pista: confirme que os eventos FTP foram registrados, que os dados incluem uma credencial utilizável e que ela atravessa uma fronteira de privilégios. Evite exibir `command_data` na saída compartilhada da enumeração. A documentação do Suricata descreve os [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e as [variações de rotação e nome de arquivo do EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuração gerada do Apache e logs redirecionados

O [remco](https://github.com/HeavyHorst/remco) pode monitorar um backend de chave/valor, renderizar um template em um arquivo de configuração do Apache e executar um comando de recarga. Inspecione a identidade do processo remco em execução, a origem e o destino do template configurado, os prefixos de chaves monitorados e se um valor do backend é inserido diretamente em uma diretiva do Apache, como `ServerName`. Um listener de backend local, por si só, não comprova que o usuário atual possa gravar uma chave monitorada; verifique a autenticação e as permissões do backend antes de afirmar que há uma escalada.

Uma quebra de linha não escapada em um valor gravável do backend pode transformar o valor de uma diretiva pretendida em diretivas adicionais do Apache. Os [logs redirecionados do Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) são particularmente sensíveis: `CustomLog` ou `ErrorLog` com um comando precedido por `|` inicia um helper sob a identidade do processo httpd pai, geralmente root; `|$` pede ao Apache que use um shell. Analise a configuração gerada e o caminho de recarga sem alterar os dados do backend nem reiniciar o serviço durante a enumeração. Mantenha privado o comando completo redirecionado, pois seus argumentos podem conter segredos.

## Autenticação e identidades de serviço

O arquivo de controle do Monit geralmente fica em `~/.monitrc` ou `/etc/monitrc`, mas `monit -c` pode selecionar outro caminho. Um arquivo legível pode conter entradas `set httpd` e `allow user:password` para a interface web, muitas vezes na porta local 2812. Verifique o proprietário e as permissões do arquivo antes de analisá-lo e mantenha os valores das senhas fora da saída compartilhada da enumeração. As credenciais web concedem apenas a função Monit configurada; usuários somente de leitura não podem executar ações de controle. Uma escalada para uma conta Unix exige reutilização de senha confirmada ou uma ação privilegiada do Monit que a função autenticada possa realmente acionar. Consulte a [documentação do arquivo de controle e da autenticação do Monit](https://www.mmonit.com/monit/documentation/monit.html).

No Webmin, `/etc/webmin/miniserv.conf` identifica as configurações do servidor e `/etc/webmin/webmin.acl` registra os módulos que os usuários podem acessar; o [Webmin documenta os limites das concessões de módulos](https://webmin.com/docs/development/creating-modules/). Uma senha Unix ou um arquivo ACL legível não concede, por si só, uma sessão do Webmin. Confirme o mapeamento de autenticação real, o listener acessível, a conta autenticada, a permissão efetiva para o módulo Package Updates, o código instalado ou a correção do fornecedor e a identidade do processo Webmin. Em versões afetadas até a 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitia que uma conta com essa permissão de módulo executasse comandos por meio do handler de atualização. Durante a enumeração passiva, informe os caminhos e as permissões de configuração sem exibir credenciais nem tentar uma atualização.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) controla a autenticação específica de cada serviço; caminhos de políticas ou módulos com permissão de escrita podem alterar o comportamento do login.
- A configuração de LDAP/SSSD pode revelar endpoints de diretório, identidades de bind e regras de acesso. Uma senha de bind recuperada pode permitir consultas LDAP além da conta atual do SO; teste a identidade de bind exata e as ACLs do diretório. Revise as permissões dos arquivos antes de inspecionar segredos; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) abordam o uso de tickets e diretórios.
- Aliases do Postfix podem encaminhar e-mails recebidos para comandos locais. Se um usuário com menos privilégios puder alterar o script referenciado, a entrega de e-mails poderá executar o código desse usuário sob a identidade usada na entrega. Revise os mapas de aliases e a propriedade do script antes de afirmar que esse caminho é viável; consulte [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e outros serviços de CI podem executar jobs usando uma conta local com privilégios elevados. Inspecione o usuário do serviço, os caminhos de job/workspace com permissão de escrita e a interface de administração local antes de testar um pipeline ou plugin. Revise também as **credenciais disponíveis para um job** e a conta com a qual podem autenticar: um Pipeline que use o [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) pode acessar um host como o usuário da credencial SSH, mesmo quando o próprio Jenkins é executado sob uma conta Unix com menos privilégios. Confirme que a identidade atual do Jenkins tem `Job/Create`, `Job/Configure` ou outra forma efetiva de alterar o Pipeline, que a credencial está disponível para esse job e que a conta SSH de destino aceita a chave antes de afirmar que houve elevação de privilégios no host. O nome de exibição ou o ID de uma credencial, por si só, não comprova nenhuma dessas condições. O Jenkins alerta que criadores de jobs e, muitas vezes, seus configuradores podem usar arbitrariamente as credenciais disponíveis em seu escopo; portanto, o [escopo das credenciais](https://www.jenkins.io/doc/book/security/credentials/) e a [confiabilidade do Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) são tão importantes quanto o UID do serviço. Não inclua valores de credenciais nem chaves privadas em saídas de enumeração compartilhadas.

## Escrita de arquivos em repositórios Gogs

Para um serviço Gogs local, relacione o proprietário do processo `gogs web` à versão do executável e ao arquivo `custom/conf/app.ini`. A configuração pode revelar a identidade do serviço, a raiz dos repositórios, o endereço de escuta e se o registro está desativado. Mesmo um listener limitado ao loopback pode ser acessado por usuários locais. As versões do Gogs até a 0.13.3 têm um problema de escrita de arquivos por symlink em `PutContents` que exige autenticação ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): um usuário com permissão para gravar no repositório pode enviar um symlink e, em seguida, direcionar a escrita da API por meio dele. O acesso resultante aos arquivos usa os privilégios do processo Gogs, portanto, uma instância executada como root exige atenção imediata. Valide a correção implantada e os requisitos de autenticação antes de afirmar que há um caminho viável; um erro da API não prova que a escrita do arquivo falhou.

## XSS na descrição de repositórios Gitea e visualizadores privilegiados

O Gitea 1.22.0 permitia JavaScript armazenado na descrição de um repositório ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); a versão 1.22.1 corrigiu o problema. Um usuário que possa editar uma descrição pode afetar uma sessão de navegador com mais privilégios se esse usuário visualizar o repositório e ativar o link malicioso. Essa identidade do navegador pode então expor conteúdo de repositórios privados ou outros dados da aplicação. Uma elevação local separada exige uma credencial ou permissão acessível por meio desse conteúdo, como uma senha de administrador reutilizada; o proprietário do processo Gitea, por si só, não comprova impacto de root. Verifique a versão implantada, o acesso para editar descrições, o fluxo de trabalho dos visualizadores e a interação real com o navegador antes de afirmar que a cadeia é viável.

## API de provisionamento Cobbler

O serviço de gerenciamento do Cobbler expõe uma API XML-RPC, geralmente na porta `25151`. Verifique o listener e o proprietário do processo `cobblerd` antes de avaliar seu impacto; uma API limitada ao loopback ainda pode ser acessada por um usuário no host. Revise os módulos de autenticação e autorização em `/etc/cobbler/modules.conf`, as configurações do serviço em `/etc/cobbler/settings` ou `/etc/cobbler/settings.yaml` e as permissões de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. Os arquivos de digest e de segredo compartilhado contêm material de credenciais; por padrão, registre se podem ser lidos sem imprimir seu conteúdo.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** é um bypass de autenticação XML-RPC no Cobbler 3.0.0 até 3.2.2 e 3.3.0 até 3.3.6. Um erro ao ler o segredo compartilhado retornava o valor previsível `-1`, que a API aceitava como senha. As correções correspondentes estão nas versões 3.2.3 e 3.3.7. A versão de um pacote é apenas uma pista; antes de reportar exposição, verifique o código implantado e se há uma correção retroportada.

Uma sessão autenticada da API pode ser um caminho para execução privilegiada quando `cobblerd` é executado como root. Nas implementações afetadas, `background_import` passa `rsync_flags` controlado pelo usuário para um comando shell, e a renderização de um template Cheetah de autoinstall controlado pelo usuário pode avaliar Python. Verifique as permissões da API e a versão instalada antes de testar qualquer um desses caminhos. Restrinja o acesso à API de gerenciamento, aplique a correção do bypass de autenticação e permita que apenas os administradores do serviço leiam os arquivos de configuração e credenciais.

## Configuração do Motion e do motionEye

Inspecione `/etc/motioneye/motioneye.conf` para localizar `conf_path` e, em seguida, examine `motion.conf` e um pequeno número de arquivos `camera-*.conf` nesse diretório. Informe se existe um hash legível de `# @admin_password` sem exibi-lo. [Versões antigas do motionEye criavam esses arquivos com permissões de leitura amplas](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); a correção está na versão 0.44.0. Verifique em conjunto as configurações `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost` do Motion: o controle avançado (`2` ou `3`) com autenticação desativada pode expor operações poderosas a um usuário local, inclusive em um listener de loopback. [A documentação do Motion descreve os valores e padrões](https://motion-project.github.io/motion_config.html).

Uma sessão de admin no motionEye anterior à versão 0.43.1b5 podia transformar uma configuração de nome de arquivo de câmera em execução de comandos quando o Motion a processava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Antes de alegar uma escalada, confirme a versão em execução, a identidade do serviço, se há um caminho de autenticação utilizável e se uma câmera está configurada. A configuração, por si só, não prova que o serviço está em execução ou tem privilégios.

Um nome de serviço ou pacote instalado é apenas uma pista. O limite de privilégio depende da combinação entre entrada acessível, identidade do processo, configuração gravável e o comando ou arquivo que ela controla.

## Emuladores AWS locais e credenciais armazenadas

Um usuário do host pode acessar um emulador compatível com AWS executado em um container por meio do endpoint de loopback publicado. Antes de avaliar o acesso ao [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) ou ao [KMS](https://docs.localstack.cloud/aws/services/kms/), correlacione o listener ativo, o endpoint e a conta selecionados pelo cliente e as configurações de autorização instaladas no emulador. No LocalStack, [a aplicação de políticas IAM é uma configuração separada](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); não deduza as permissões efetivas da API com base apenas em um arquivo de credenciais, uma política IAM ou um listener. Confirme o comportamento da versão e da configuração instaladas.

Um segredo armazenado só é útil para escalada local se a identidade atual da API puder recuperá-lo e uma conta separada com privilégios superiores aceitar a credencial recuperada. Um blob local criptografado também exige acesso de leitura ao arquivo, a chave KMS correspondente utilizável e o algoritmo correspondente, além de acesso efetivo para descriptografar. Para uma [chave KMS assimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), a solicitação de descriptografia deve especificar o algoritmo usado para criptografar o blob. Em inventários automáticos do host, limite-se a evidências sobre processos, listeners, caminhos de configuração e permissões de arquivos; não solicite nem exiba valores de segredos ou texto simples descriptografado durante a enumeração rotineira.
