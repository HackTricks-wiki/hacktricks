# Services Web et d'authentification locaux

{{#include ../../banners/hacktricks-training.md}}

Un shell Linux donne une vue côté hôte des services Web et d'authentification : arguments des processus, sockets en écoute, fichiers d'unité, configuration, journaux et interfaces accessibles uniquement en local. Utilisez cette vue pour relier un service accessible au compte et aux fichiers qu'il utilise réellement.

## Cartographier la pile Web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspectez les noms de virtual hosts, les racines des documents, les routes de proxy, les répertoires d’envoi, les paramètres d’exécution PHP et les fichiers de configuration contenant des identifiants. Un listener sur l’interface de loopback peut être accessible via un proxy ou un tunnel SSH. Pour tester un virtual host nommé contre un listener local, envoyez l’en-tête `Host` prévu ou utilisez `curl --resolve` avec l’adresse et le port appropriés. L’énumération des virtual hosts peut également révéler des noms absents de la réponse par défaut. Vérifiez si Apache autorise les surcharges `.htaccess` et si les chemins d’envoi peuvent exécuter du PHP avant de considérer qu’un répertoire d’envoi inscriptible permet l’exécution de code. Une source map JavaScript déployée peut révéler des chemins source ou des secrets côté client ; traitez les valeurs récupérées comme des indices et vérifiez les privilèges qu’elles confèrent réellement. Pour les vérifications spécifiques au web, consultez [Apache](../../network-services-pentesting/pentesting-web/apache.md) et [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Avec Apache et [mpm-itk](https://mpm-itk.sesse.net/), une directive `AssignUserID` active peut exécuter un virtual host sous un autre utilisateur et groupe. Si un compte moins privilégié peut écrire un script dans le `DocumentRoot` de cet hôte, vérifiez si une route accessible l’exécute effectivement avec l’identité assignée. Confirmez que le module est chargé, vérifiez la configuration effective du virtual host (y compris les surcharges d’identité basées sur des expressions), les permissions d’écriture et de recherche sur le répertoire, le gestionnaire de scripts et l’accès au listener. Une directive mise en évidence ou un répertoire inscriptible ne prouve pas à lui seul une exécution avec les privilèges d’un autre utilisateur.

Un répertoire personnel publié par un serveur web peut exposer des archives de sauvegarde de fichiers d’identité SSH, même si le répertoire `.ssh` actif est privé. Par exemple, le paramètre [`homedirs_public` de Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) sélectionne un sous-répertoire des répertoires personnels des utilisateurs à servir. La découverte d’une archive à partir de son seul chemin est un indice : vérifiez le mappage effectif du serveur, la lisibilité locale ou l’autorisation HTTP, le contenu de l’archive, la phrase secrète de la clé privée et si le compte correspondant accepte réellement la clé. N’extrayez pas les archives et n’affichez pas le contenu des clés lors de l’énumération courante des hôtes.

Une sauvegarde lisible d’une application web locale plus privilégiée peut révéler la logique d’authentification et de lecture de fichiers, même si son code source actif est inaccessible. Comparez la sauvegarde au service déployé avant de vous y fier. En particulier, un cookie construit en chiffrant un texte contrôlé par l’appelant, suivi d’un secret et d’un indicateur de rôle, mérite un examen si l’application utilise des blocs ECB déterministes, renvoie de nouveaux cookies pour un texte choisi et découpe ensuite la valeur déchiffrée sur un délimiteur non échappé. [NIST explique le mappage indépendant et répétable des blocs en mode ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a) ; cette propriété peut permettre une comparaison avec une entrée choisie, mais ne confère pas à elle seule un rôle plus élevé. Confirmez la route active, les prérequis de session, l’analyse exacte et le flux de données, l’identité du service et l’existence d’une action privilégiée distincte ou d’un chemin de lecture de fichiers. L’inventaire passif doit signaler les métadonnées des sauvegardes et la propriété du listener, sans lire le contenu des archives ni envoyer de sondes d’authentification.

La même méthode d’examen du code source s’applique à un service local privilégié **non HTTP**, tel qu’une interface personnalisée reposant sur SSH. Si une sauvegarde source accessible montre une commande qui accepte un chemin de fichier choisi par l’appelant, vérifiez son mécanisme d’authentification, la résolution du chemin et si elle garantit que le fichier résolu reste dans un répertoire prévu avant de l’ouvrir. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) nettoie un chemin, mais n’impose pas ce confinement. Confirmez que la sauvegarde correspond au binaire en cours d’exécution, que le listener est accessible, que le compte moins privilégié peut utiliser la commande et que le processus peut lire la cible ; la possession d’une clé SSH lisible relève d’une question distincte, celle de la politique de connexion. Signalez les chemins des archives sources et la propriété du service, sans extraire le contenu des archives ni les clés dans la sortie automatisée.

Un pool PHP-FPM à l’écoute sur le TCP de loopback peut être accessible à un autre compte local, même si son site web exige une authentification. [PHP avertit qu’un client capable de se connecter à FastCGI peut contrôler les paramètres de requête, notamment `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Examinez les paramètres `listen` et `listen.allowed_clients` du pool, ainsi que le listener actif, l’UID du worker, un chemin de script existant et toute restriction `security.limit_extensions` ou `php_admin_value`. Les fichiers de configuration du pool peuvent contenir des identifiants dans des directives `env[...]` ; l’inventaire automatisé doit donc signaler leurs chemins plutôt que leur contenu. Un fichier de configuration ou un port ne prouve pas à lui seul l’existence d’un chemin d’exécution entre utilisateurs ; consultez le [guide FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) pour les détails du protocole.

Pour une API locale privilégiée, examinez l’autorisation autant que l’exécution de code. Un rôle de base de données que le compte moins privilégié peut modifier peut débloquer une route d’API, mais la frontière suivante dépend de l’implémentation de cette route. Par exemple, la fusion du JSON de requête dans un objet JavaScript, suivie d’un appel à [`child_process.exec`](https://nodejs.org/api/child_process.html), justifie d’examiner un [flux de données allant de la pollution de prototypes à l’exécution](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Vérifiez la bibliothèque/version de fusion réellement utilisée, la validation des entrées, la route accessible, l’identité du processus et les options du processus enfant ; un listener Node appartenant à root ou le nom d’une dépendance vulnérable ne constitue à lui seul qu’un indice.

Les CMS stockés dans des fichiers peuvent conserver les vérificateurs de mots de passe administrateur en dehors des fichiers de configuration `.php` habituels. Parmi les exemples figurent `data/database.js` ou `data/settings/pass.php` d’un site. Vérifiez la propriété et la lisibilité des fichiers avant tout examen manuel, et excluez les hachages des sorties automatisées partagées. Un mot de passe d’application récupérable représente une frontière de privilèges distincte de celle d’un compte Unix : vérifiez toute réutilisation présumée pour le compte concerné et la méthode d’authentification autorisée.

Le contrôleur d’authentification d’une application peut également contenir un mot de passe de connexion en clair dans le code source plutôt que dans un fichier de configuration. Si un utilisateur moins privilégié peut lire le contrôleur déployé, examinez localement sa comparaison d’authentification et excluez toute valeur des sorties d’énumération partagées. Confirmez que le chemin de code est actif, que le mot de passe est valide pour l’application et qu’un compte Unix distinct plus privilégié accepte réellement ce même mot de passe avant de conclure à une élévation de privilèges locale. Le nom du fichier du contrôleur n’est qu’un indice à examiner.

Dolibarr stocke les paramètres de connexion à la base de données, notamment `dolibarr_main_db_pass`, dans `htdocs/conf/conf.php` ([référence de configuration](https://wiki.dolibarr.org/index.php/Configuration_file)). Un fichier lisible est un indice d’identifiant ; seule une réutilisation distincte et vérifiée du mot de passe d’un compte, ou une autre permission sur la base de données, permettrait d’en faire une élévation de privilèges locale. Vérifiez d’abord les permissions et évitez d’afficher la valeur dans les sorties automatisées.

Le fichier de configuration du paquet Linux de GitLab est normalement `/etc/gitlab/gitlab.rb`, mais les déploiements peuvent conserver ailleurs des copies lisibles. [GitLab indique](https://docs.gitlab.com/omnibus/settings/smtp/) que ce fichier peut contenir `gitlab_rails['smtp_password']`, même si les paramètres SMTP chiffrés peuvent conserver le mot de passe hors du fichier en clair. Traitez une configuration lisible comme un indice d’identifiant : vérifiez qu’elle est active, que l’identifiant est toujours valide et qu’un compte précis plus privilégié l’accepte avant de conclure à une réutilisation de mot de passe. Par ailleurs, [GitLab exécute `gitlab.rb` comme du code Ruby sous root lors de `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/) ; un fichier actif inscriptible ou un fichier inclus par `from_file` nécessite un chemin de reconfiguration réellement privilégié pour constituer un constat d’exécution. Un aperçu de la configuration peut exposer des identifiants ; traitez sa sortie comme sensible et partagez plutôt les chemins et les permissions.

Une installation Mattermost auto-hébergée peut conserver `SqlSettings.DataSource` dans `/opt/mattermost/config/config.json` ; [Mattermost documente](https://docs.mattermost.com/deployment-guide/server/troubleshooting) à la fois ce chemin habituel et les déploiements qui stockent plutôt la configuration active dans une base de données. Un fichier lisible peut exposer un identifiant de base de données de l’application, mais ne prouve ni l’accès à la base de données ni l’accès à root sous Unix. Vérifiez la source de configuration active, les droits réels du rôle de base de données, tout mot de passe d’application récupéré séparément et si ce mot de passe fonctionne pour un compte Unix précis plus privilégié. Le format des hachages de mots de passe peut varier selon les versions de Mattermost ; lors de l’énumération, consignez le chemin du fichier de configuration et les métadonnées d’accès sans afficher la chaîne de connexion ni interroger la base de données.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtrez les résultats des virtual hosts en les comparant à la taille de la réponse par défaut ou à une autre référence stable, afin que chaque nom deviné ne semble pas valide. Une source map n'est utile que si elle est effectivement déployée ou accessible d'une autre manière.

Les reverse proxies peuvent modifier les en-têtes client auxquels une application fait confiance. Comparez les requêtes directes et celles passant par le proxy avant de supposer que `X-Forwarded-For`, `X-Forwarded-Host` ou des en-têtes similaires établissent l'identité d'un appelant. Examinez ensemble la configuration du proxy et celle de l'application.

Si PHP copie `$_SERVER['HTTP_X_FORWARDED_FOR']` dans une chaîne transmise à [`system()`](https://www.php.net/manual/en/function.system.php), vérifiez si le chemin de requête accessible permet à un appelant de fournir cet en-tête et si les métacaractères shell parviennent à cette chaîne sans modification. Une commande telle que `sudo iptables` placée au début ne fait **pas** exécuter en root les commandes suivantes séparées par le shell ; celles-ci s'exécutent avec l'identité du worker web, sauf si une règle sudo effective distincte autorise l'escalade. Confirmez l'identité du worker, l'autorisation exacte dans `sudo -l` et ses exigences d'authentification, ainsi que les limites des arguments de la commande avant de conclure à un chemin vers root. Examinez le code source et la politique sans envoyer de sonde d'injection lors d'un inventaire courant de l'hôte.

## Identifiants de connexion dans les journaux d'accès

Si une application envoie un formulaire de connexion avec `GET`, le nom d'utilisateur et le mot de passe peuvent apparaître comme paramètres de requête dans l'URI de la requête. Une requête `POST` peut également contenir une chaîne de requête ; utiliser `POST` ne masque pas un secret placé par inadvertance dans l'URI, y compris un mot de passe saisi dans un champ sans rapport du formulaire. La [ligne de requête des journaux d'accès Apache courants](https://httpd.apache.org/docs/2.4/logs.html) enregistre la méthode et l'URI, chaîne de requête comprise, lorsque le format configuré utilise `%r`. Un compte autorisé à lire ces journaux, par exemple via le groupe `adm` sur certains systèmes Linux, peut donc y trouver une piste concernant des identifiants. Vérifiez le format réel du journal et les permissions, puis confirmez que la valeur est un secret, que le compte l'accepte et qu'elle franchit une frontière de privilèges. Ne supposez pas que le corps de la requête a été journalisé et ne copiez pas les valeurs candidates dans des sorties partagées.

Examinez uniquement les journaux d'accès lisibles et gardez les identifiants hors des sorties de commandes partagées. Les longues lignes de requête peuvent également contenir un référent et un user-agent ; un filtre qui ne conserve que les lignes courtes peut donc masquer précisément la requête recherchée. Les emplacements courants des journaux d'accès Apache, httpd et Nginx sont `/var/log/apache2/access.log`, `/var/log/httpd/access_log` et `/var/log/nginx/access.log`. Les journaux rotatifs peuvent contenir d'anciens identifiants. [L'accès aux fichiers journaux via LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) est une autre voie menant aux mêmes données.

Les journaux d'authentification des applications peuvent aussi révéler un mot de passe saisi par inadvertance dans le champ **nom d'utilisateur** d'une tentative de connexion échouée. Vérifiez d'abord que le journal est lisible et que son format enregistre le nom d'utilisateur soumis ; examinez localement uniquement un petit extrait pertinent et ne copiez pas les identifiants candidats dans des sorties partagées. Un nom d'utilisateur qui ressemble à un mot de passe est une piste, pas la preuve d'un mot de passe valide ou d'un privilège supérieur. Vérifiez le compte visé et toute réutilisation sur le service ou le compte Unix concerné avant de conclure à une élévation de privilèges.

Un gestionnaire de connexion web accessible en écriture mérite un examen distinct lorsqu'un client planifié, exécuté sous une autre identité, envoie des identifiants à ce point de terminaison. Confirmez l'accès en écriture au gestionnaire **actif**, la planification réelle du client et son chemin de requête, l'identité dont il envoie les identifiants, et si ce mot de passe d'application est également valide pour un compte du système d'exploitation doté de privilèges supérieurs. Une page accessible en écriture ou un processus récurrent ne suffit pas à établir cette élévation. Un inventaire passif doit indiquer les permissions des chemins et les métadonnées des tâches sans modifier le gestionnaire ni recueillir de mots de passe.

Les journaux EVE JSON de Suricata peuvent également enregistrer les commandes FTP `USER` et `PASS` avec leur `command_data` lorsque la journalisation des événements FTP est activée. Vérifiez que `/var/log/suricata/eve*.json*` est lisible, y compris les fichiers rotatifs ou compressés, avant d'en examiner localement un petit extrait pertinent. Un fichier EVE lisible n'est qu'une piste : confirmez que les événements FTP ont été journalisés, que les données contiennent des identifiants utilisables et qu'ils franchissent une frontière de privilèges. Évitez d'afficher `command_data` dans les sorties d'inventaire partagées. Suricata documente les [champs des événements FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) et la [rotation EVE et les variantes de noms de fichiers](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuration Apache générée et journaux redirigés vers des commandes

[remco](https://github.com/HeavyHorst/remco) peut surveiller un backend clé/valeur, générer un fichier de configuration Apache à partir d'un template et exécuter une commande de rechargement. Examinez l'identité du processus remco en cours d'exécution, la source et la destination de son template configuré, les préfixes de clés surveillés et si une valeur du backend est insérée directement dans une directive Apache telle que `ServerName`. Un listener local du backend ne prouve pas à lui seul que l'utilisateur actuel peut écrire une clé surveillée ; vérifiez l'authentification et les permissions du backend avant de conclure à une élévation de privilèges.

Un saut de ligne non échappé dans une valeur de backend modifiable peut transformer la valeur d'une directive prévue en directives Apache supplémentaires. Les [journaux Apache redirigés vers des commandes](https://httpd.apache.org/docs/2.4/logs.html#piped) sont particulièrement sensibles : `CustomLog` ou `ErrorLog` suivi d'une commande avec `|` lance un processus auxiliaire sous l'identité du processus httpd parent, souvent root ; `|$` demande à Apache d'utiliser un shell. Examinez la configuration générée et son chemin de rechargement sans modifier les données du backend ni redémarrer le service pendant l'inventaire. Gardez la commande complète redirigée vers un processus privé, car ses arguments peuvent contenir des secrets.

## Authentification et identités de service

Le fichier de contrôle de Monit est généralement `~/.monitrc` ou `/etc/monitrc`, mais `monit -c` peut en sélectionner un autre. Un fichier lisible peut contenir des entrées `set httpd` et `allow user:password` pour son interface web, souvent sur le port local 2812. Vérifiez le propriétaire et les permissions du fichier avant de l'examiner, et gardez les mots de passe hors des sorties d'inventaire partagées. Les identifiants web donnent uniquement accès au rôle Monit configuré ; les utilisateurs en lecture seule ne peuvent pas déclencher d'actions de contrôle. Une élévation distincte vers un compte Unix nécessite une réutilisation de mot de passe confirmée ou une action Monit privilégiée que le rôle authentifié peut réellement déclencher. Consultez la [documentation de Monit sur le fichier de contrôle et l'authentification](https://www.mmonit.com/monit/documentation/monit.html).

Pour Webmin, `/etc/webmin/miniserv.conf` définit les paramètres du serveur et `/etc/webmin/webmin.acl` indique les modules auxquels les utilisateurs peuvent accéder ; [Webmin documente les limites des autorisations de modules](https://webmin.com/docs/development/creating-modules/). Un mot de passe Unix ou un fichier ACL lisible ne donne pas à lui seul accès à une session Webmin. Confirmez la correspondance réelle des méthodes d'authentification, le listener accessible, le compte authentifié, les autorisations effectives du module Package Updates, le code installé ou le correctif du fournisseur, ainsi que l'identité du processus Webmin. Dans les versions concernées jusqu'à la 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permettait à un compte disposant de cette autorisation de module d'exécuter des commandes via son gestionnaire de mises à jour. Lors d'un inventaire passif, indiquez les chemins de configuration et les permissions sans afficher d'identifiants ni tenter de mise à jour.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) régit l'authentification propre à chaque service ; des chemins de stratégie ou de module modifiables peuvent changer le comportement de connexion.
- La configuration LDAP/SSSD peut révéler les points de terminaison de l'annuaire, les identités de liaison et les règles d'accès. Un mot de passe de liaison récupéré peut permettre des requêtes LDAP au-delà des droits du compte OS actuel ; testez l'identité de liaison exacte et les ACL de l'annuaire. Vérifiez les permissions des fichiers avant d'inspecter les secrets ; [Linux Active Directory](../user-information/linux-active-directory.md) et [FreeIPA](freeipa-pentesting.md) traitent de l'utilisation des tickets et de l'annuaire.
- Les alias Postfix peuvent acheminer les e-mails reçus vers des commandes locales. Si un utilisateur moins privilégié peut modifier le script référencé, la livraison d'e-mails peut déclencher son code sous l'identité de livraison. Examinez les tables d'alias et le propriétaire du script avant d'affirmer que cette voie est exploitable ; voir [Tests des services SMTP et de messagerie](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins et d'autres services CI peuvent exécuter des tâches sous un compte local puissant. Examinez l'utilisateur du service, les chemins de tâche/espace de travail modifiables et l'interface d'administration locale avant de tester un pipeline ou un plugin. Examinez également les **identifiants accessibles à une tâche** et le compte auquel ils permettent de s'authentifier : un Pipeline utilisant l'étape [SSH Agent](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) peut accéder à un hôte en tant qu'utilisateur de l'identifiant SSH, même si Jenkins s'exécute sous un compte Unix moins privilégié. Vérifiez que l'identité Jenkins actuelle dispose de `Job/Create`, `Job/Configure` ou d'une autre possibilité effective de modifier le Pipeline, que l'identifiant est accessible à cette tâche et que le compte SSH cible accepte la clé avant d'affirmer qu'il s'agit d'une élévation de privilèges sur l'hôte. Le nom d'affichage ou l'ID d'un identifiant ne suffit pas, à lui seul, à établir ces conditions. Jenkins avertit que les créateurs de tâches et, souvent, les personnes qui les configurent peuvent utiliser arbitrairement les identifiants accessibles dans leur périmètre ; la [portée des identifiants](https://www.jenkins.io/doc/book/security/credentials/) et la [fiabilité du Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) sont donc aussi importantes que l'UID du service. Ne faites pas apparaître les valeurs des identifiants ni les clés privées dans les sorties d'énumération partagées.

## Écriture de fichiers dans les dépôts Gogs

Pour un service Gogs local, mettez en corrélation le propriétaire du processus `gogs web`, la version de l'exécutable et `custom/conf/app.ini`. La configuration peut révéler l'identité du service, la racine des dépôts, l'adresse d'écoute et si l'inscription est désactivée. Un service qui n'écoute que sur loopback reste accessible aux utilisateurs locaux. Les versions de Gogs jusqu'à 0.13.3 inclus présentent un problème d'écriture de fichier via symlink dans PutContents, qui nécessite une authentification ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)) : un utilisateur pouvant écrire dans un dépôt peut valider un symlink, puis rediriger l'écriture de l'API à travers celui-ci. L'accès au fichier qui en résulte bénéficie des privilèges du processus Gogs ; une instance exécutée en tant que root nécessite donc une attention rapide. Vérifiez le correctif déployé et les exigences d'authentification avant d'affirmer qu'une voie est exploitable ; une erreur d'API ne prouve pas que l'écriture du fichier a échoué.

## XSS dans la description d'un dépôt Gitea et visiteurs privilégiés

Gitea 1.22.0 autorisait l'injection persistante de JavaScript dans la description d'un dépôt ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)) ; la version 1.22.1 a corrigé le problème. Un utilisateur pouvant modifier une description peut affecter une session de navigateur plus privilégiée si cet utilisateur consulte le dépôt et active le lien malveillant. Cette identité de navigateur peut alors exposer le contenu privé du dépôt ou d'autres données de l'application. Une élévation locale distincte nécessite un identifiant ou une permission accessible via ce contenu, comme un mot de passe d'administrateur réutilisé ; le propriétaire du processus Gitea ne suffit pas, à lui seul, à établir un impact root. Vérifiez la version déployée, les droits de modification de description, le parcours du visiteur et l'interaction réelle avec le navigateur avant d'affirmer que cette chaîne est exploitable.

## API de provisionnement Cobbler

Le service de gestion de Cobbler expose une API XML-RPC, généralement sur le port `25151`. Vérifiez le processus à l'écoute et le propriétaire du processus `cobblerd` avant d'évaluer son impact ; une API qui n'écoute que sur loopback reste accessible à un utilisateur de l'hôte. Examinez les modules d'authentification et d'autorisation dans `/etc/cobbler/modules.conf`, les paramètres du service dans `/etc/cobbler/settings` ou `/etc/cobbler/settings.yaml`, ainsi que les permissions de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` et `/var/lib/cobbler/web.ss`. Les fichiers de condensats et de secrets partagés contiennent des identifiants ; consignez leur lisibilité sans afficher leur contenu par défaut.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** est un contournement de l’authentification XML-RPC dans Cobbler 3.0.0 à 3.2.2 et 3.3.0 à 3.3.6. Une erreur de lecture du secret partagé renvoyait la valeur prévisible `-1`, que l’API acceptait comme mot de passe. Les correctifs correspondants sont les versions 3.2.3 et 3.3.7. La version d’un paquet constitue un indice ; vérifiez le code déployé et la présence d’un éventuel correctif rétroporté avant de signaler une exposition.

Une session API authentifiée peut permettre une exécution privilégiée si `cobblerd` s’exécute en tant que root. Dans les implémentations concernées, `background_import` transmet la valeur contrôlée par l’utilisateur `rsync_flags` à une commande shell, et le rendu d’un modèle d’installation automatisée Cheetah contrôlé par l’utilisateur peut exécuter du Python. Vérifiez les permissions de l’API et la version installée avant de tester l’une ou l’autre de ces voies. Limitez l’accès à l’API de gestion, corrigez le contournement de l’authentification et veillez à ce que seuls les administrateurs du service puissent lire les fichiers de configuration et d’identifiants.

## Configuration de Motion et motionEye

Inspectez `/etc/motioneye/motioneye.conf` pour trouver `conf_path`, puis examinez `motion.conf` et quelques fichiers `camera-*.conf` dans ce répertoire. Indiquez si un hash `# @admin_password` lisible est présent, sans l’afficher. [Les anciennes versions de motionEye créaient ces fichiers avec des permissions de lecture trop larges](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67) ; le correctif est inclus dans la version 0.44.0. Vérifiez ensemble les paramètres Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` et `webcontrol_localhost` : un contrôle avancé (`2` ou `3`) sans authentification peut exposer des opérations puissantes à un utilisateur local, y compris sur un écouteur en boucle locale. [Motion documente les valeurs et les paramètres par défaut](https://motion-project.github.io/motion_config.html).

Avant la version 0.43.1b5 de motionEye, une session d’administration pouvait transformer un paramètre de nom de fichier de caméra en exécution de commande lorsque Motion le traitait ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Vérifiez la version en cours d’exécution, l’identité du service, la possibilité d’utiliser un chemin d’authentification et la présence d’une caméra configurée avant de conclure à une élévation de privilèges. La configuration seule ne prouve pas que le service est en cours d’exécution ou qu’il dispose de privilèges.

Un nom de service ou un paquet installé n’est qu’un indice. La frontière de privilèges dépend de la combinaison entre l’entrée accessible, l’identité du processus, les permissions d’écriture sur la configuration et la commande ou le fichier finalement contrôlé.

## Émulateurs AWS locaux et identifiants stockés

Un utilisateur de l’hôte peut accéder à un émulateur compatible avec AWS exécuté dans un conteneur via son endpoint de boucle locale publié. Avant d’évaluer l’accès à [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) ou à [KMS](https://docs.localstack.cloud/aws/services/kms/), corrélez l’écouteur actif, l’endpoint et le compte sélectionnés par le client, ainsi que les paramètres d’autorisation installés de l’émulateur. Dans LocalStack, [l’application des politiques IAM est un paramètre distinct](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/) ; ne déduisez pas les permissions API effectives à partir d’un fichier d’identifiants, d’une politique IAM ou d’un écouteur seul. Vérifiez le comportement de la version et de la configuration installées.

Un secret stocké n’est utile pour une élévation de privilèges locale que si l’identité API actuelle peut le récupérer et si un compte distinct disposant de privilèges supérieurs accepte l’identifiant récupéré. Un blob local chiffré nécessite également un accès en lecture au fichier, la clé KMS correspondante utilisable et l’algorithme approprié, ainsi qu’un accès effectif au déchiffrement. Pour une [clé KMS asymétrique](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la requête de déchiffrement doit spécifier l’algorithme utilisé pour chiffrer le blob. Pour l’inventaire automatique de l’hôte, limitez-vous aux éléments de preuve concernant les processus, les écouteurs, les chemins de configuration et les permissions des fichiers ; ne demandez pas et n’affichez pas les valeurs des secrets ni leur texte en clair déchiffré lors d’une énumération de routine.
