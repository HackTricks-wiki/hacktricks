# Servizi web e di autenticazione locali

{{#include ../../banners/hacktricks-training.md}}

Una shell Linux offre una vista dei servizi web e di autenticazione dal lato host: argomenti dei processi, listener, file unit, configurazione, log e interfacce accessibili solo localmente. Usa questa vista per collegare un servizio raggiungibile all’account e ai file che usa effettivamente.

## Mappare lo stack web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Esamina i nomi dei virtual host, le directory root dei documenti, le route proxy, le directory di upload, le impostazioni di esecuzione PHP e i file di configurazione che contengono credenziali. Un listener loopback potrebbe essere raggiungibile tramite un proxy o un tunnel SSH. Per testare un virtual host nominato rispetto a un listener locale, invia l'header `Host` previsto oppure usa `curl --resolve` con indirizzo e porta corretti. L'enumerazione dei virtual host può anche rivelare nomi assenti dalla risposta predefinita. Verifica se Apache consente override tramite `.htaccess` e se i percorsi di upload possono eseguire PHP prima di considerare una directory di upload scrivibile come un vettore di code execution. Una source map JavaScript distribuita può esporre percorsi dei sorgenti o segreti lato client; considera i valori recuperati come indizi e verifica i privilegi effettivi che concedono. Per i controlli specifici del web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Per Apache con [mpm-itk](https://mpm-itk.sesse.net/), una direttiva `AssignUserID` attiva può eseguire un virtual host con un utente e un gruppo diversi. Se un account con privilegi inferiori può scrivere uno script nel `DocumentRoot` di quell'host, verifica se una route raggiungibile lo esegue effettivamente con l'identità assegnata. Conferma che il modulo sia caricato, controlla la configurazione effettiva del virtual host (incluse eventuali sovrascritture dell'identità basate su espressioni), i permessi di scrittura e ricerca delle directory, l'handler dello script e l'accesso al listener. Una direttiva evidenziata o una directory scrivibile, da sole, non dimostrano l'esecuzione tra utenti.

Una home directory pubblicata tramite un web server può esporre archivi di backup di file di identità SSH anche quando la directory `.ssh` attiva è privata. Per esempio, l'impostazione `homedirs_public` di [Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleziona una sottodirectory delle home degli utenti da esporre. Trovare un archivio basandosi solo sul percorso è un indizio: verifica la mappatura effettiva del server, la leggibilità locale o l'autorizzazione HTTP, il contenuto dell'archivio, la passphrase della chiave privata e se l'account corrispondente accetta davvero la chiave. Non estrarre archivi né stampare materiale delle chiavi durante la normale enumerazione dell'host.

Un backup leggibile di un'app web locale con privilegi elevati può rivelare la logica di autenticazione e lettura dei file anche quando il sorgente attivo non è accessibile. Confronta il backup con il servizio distribuito prima di farvi affidamento. In particolare, merita attenzione un cookie creato cifrando testo controllato dal chiamante seguito da un segreto e da un flag di ruolo, se l'app usa blocchi ECB deterministici, restituisce cookie nuovi per testo scelto e in seguito divide il valore decifrato usando un delimitatore non escapato. [NIST spiega la mappatura indipendente e ripetibile dei blocchi ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); questa proprietà può supportare un confronto con input scelto, ma da sola non concede un ruolo superiore. Conferma la route attiva, i prerequisiti di sessione, il parser esatto e il flusso dei dati, l'identità del servizio e un'azione privilegiata separata o un percorso di lettura dei file. L'inventario passivo dovrebbe riportare i metadati dei backup e la proprietà dei listener senza leggere il contenuto degli archivi né inviare probe di autenticazione.

Lo stesso approccio di revisione del sorgente si applica a un servizio loopback locale privilegiato **non HTTP**, come un'interfaccia personalizzata basata su SSH. Se un backup del sorgente accessibile mostra un comando che accetta un percorso di file scelto dal chiamante, verifica il controllo di autenticazione, come risolve il percorso e se dimostra che il file risolto rimane all'interno di una directory prevista prima di aprirlo. In Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normalizza un percorso, ma non ne impone il contenimento. Conferma che il backup corrisponda alla build in esecuzione, che il listener sia raggiungibile, che l'account con privilegi inferiori possa usare il comando e che il processo possa leggere il file bersaglio; il possesso di una chiave SSH leggibile è una questione distinta, legata alle policy di login. Riporta i percorsi degli archivi sorgente e la proprietà del servizio senza estrarre il contenuto degli archivi o le chiavi nell'output automatizzato.

Un pool PHP-FPM in ascolto su TCP loopback può essere raggiunto da un altro account locale anche se il relativo sito web richiede autenticazione. [PHP avverte che un client in grado di connettersi a FastCGI può controllare le impostazioni delle richieste, incluso `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Esamina le impostazioni `listen` e `listen.allowed_clients` del pool insieme al listener attivo, all'UID dei worker, al percorso di uno script esistente e a eventuali restrizioni `security.limit_extensions` o `php_admin_value`. I file di configurazione dei pool possono contenere credenziali nelle direttive `env[...]`, quindi l'inventario automatizzato dovrebbe riportarne i percorsi, non il contenuto. Un file di configurazione o una porta, da soli, non dimostrano un percorso di esecuzione tra utenti; per i dettagli del protocollo, consulta la [guida FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md).

Per un'API locale privilegiata, ricostruisci il flusso di autorizzazione oltre a quello di code execution. Un ruolo del database modificabile dall'account con privilegi inferiori potrebbe sbloccare una route API, ma il confine successivo dipende dall'implementazione della route. Per esempio, unire il JSON della richiesta a un oggetto JavaScript e poi chiamare [`child_process.exec`](https://nodejs.org/api/child_process.html) merita una verifica del [flusso di dati da prototype pollution a esecuzione](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la libreria/versione effettiva usata per l'unione, la validazione dell'input, la route raggiungibile, l'identità del processo e le opzioni del processo figlio; un listener Node di proprietà di root o il nome di una dipendenza vulnerabile sono solo indizi.

Gli archivi CMS basati su file possono contenere verificatori di password degli amministratori al di fuori dei tradizionali file di configurazione `.php`. Tra gli esempi ci sono `data/database.js` o `data/settings/pass.php` di un sito. Prima di esaminarli manualmente, controlla la proprietà e la leggibilità dei file e non includere hash nell'output automatizzato condiviso. Una password recuperabile dell'applicazione costituisce un confine di privilegio distinto da un account Unix: verifica ogni eventuale riutilizzo dichiarato rispetto all'account specifico e al metodo di autenticazione consentito.

Il controller di autenticazione di un'applicazione può contenere una password di login letterale nel codice sorgente, anziché in un file di configurazione. Se un utente con privilegi inferiori può leggere il controller distribuito, esamina localmente il confronto di autenticazione e non includere valori nell'output condiviso dell'enumerazione. Prima di dichiarare un'escalation locale, verifica che il percorso di codice sia attivo, che la password sia valida per l'applicazione e che un account Unix distinto con privilegi superiori accetti effettivamente la stessa password. Il solo nome di un file controller è un semplice indizio da esaminare.

Dolibarr memorizza le impostazioni di connessione al database, incluso `dolibarr_main_db_pass`, in `htdocs/conf/conf.php` ([riferimento alla configurazione](https://wiki.dolibarr.org/index.php/Configuration_file)). Un file leggibile è un indizio relativo a credenziali; solo un riutilizzo verificato della password per un altro account o un diverso privilegio sul database potrebbe trasformarlo in un'escalation di privilegi locale. Controlla prima i permessi ed evita di stampare il valore nell'output automatizzato.

Il file di configurazione del pacchetto Linux di GitLab è normalmente `/etc/gitlab/gitlab.rb`, ma le installazioni potrebbero conservarne copie leggibili altrove. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) che questo file può contenere `gitlab_rails['smtp_password']`, anche se le impostazioni SMTP cifrate possono mantenere la password al di fuori del file in testo semplice. Considera una configurazione leggibile come un indizio relativo a credenziali: verifica che sia attiva, che la credenziale sia ancora valida e che un account specifico con privilegi superiori la accetti, prima di dichiarare un riutilizzo della password. Separatamente, [GitLab esegue `gitlab.rb` come codice Ruby con privilegi di root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un file attivo scrivibile o un file incluso tramite `from_file` richiede un effettivo percorso di riconfigurazione privilegiata prima di poter essere considerato un finding di esecuzione. L'anteprima di una configurazione può esporre valori delle credenziali: considera sensibile il relativo output e condividi invece percorsi e permessi.

Un'installazione Mattermost self-hosted può conservare `SqlSettings.DataSource` in `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) sia questo percorso abituale, sia le installazioni che archiviano invece la configurazione attiva in un database. Un file leggibile può esporre una credenziale del database dell'applicazione, ma non dimostra l'accesso al database né l'accesso a Unix root. Verifica la fonte di configurazione attiva, i privilegi effettivi del ruolo del database, eventuali password dell'applicazione recuperate separatamente e se tale password funziona per uno specifico account Unix con privilegi superiori. Il formato degli hash delle password può variare tra le versioni di Mattermost; durante l'enumerazione registra il percorso della configurazione e i metadati di accesso senza stampare la stringa di connessione né interrogare il database.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra i risultati dei virtual host rispetto alla dimensione della risposta predefinita o a un'altra baseline stabile, così che ogni nome ipotizzato non sembri valido. Una source map è utile solo se è effettivamente distribuita o altrimenti leggibile.

I reverse proxy possono modificare quali header del client considera attendibili un'applicazione. Confronta le richieste dirette e quelle instradate tramite proxy prima di presumere che `X-Forwarded-For`, `X-Forwarded-Host` o header simili stabiliscano l'identità del chiamante. Esamina insieme la configurazione del proxy e quella dell'applicazione.

Se PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` in una stringa passata a [`system()`](https://www.php.net/manual/en/function.system.php), verifica se il percorso della richiesta raggiungibile consente un header fornito dal chiamante e se i metacaratteri della shell arrivano invariati a quella stringa. Un comando come `sudo iptables` inserito all'inizio **non** fa sì che i successivi comandi separati dalla shell vengano eseguiti come root; questi vengono eseguiti con l'identità del worker web, a meno che una regola sudo effettiva separata non consenta l'escalation. Verifica l'identità del worker, l'autorizzazione esatta di `sudo -l` e i relativi requisiti di autenticazione, oltre ai limiti degli argomenti del comando, prima di affermare che esiste un percorso verso root. Durante la normale enumerazione dell'host, esamina codice sorgente e policy senza inviare probe di injection.

## Credenziali di accesso nei log

Se un'applicazione invia un modulo di login con `GET`, il nome utente e la password possono diventare parametri della query nell'URI della richiesta. Anche una richiesta `POST` può contenere una query string; usare `POST` non nasconde un segreto inserito per errore nell'URI, compresa una password digitata in un campo di un modulo non correlato. La [riga di richiesta nei log di accesso comuni di Apache](https://httpd.apache.org/docs/2.4/logs.html) registra il metodo e l'URI, inclusa la query string, quando il formato configurato usa `%r`. Un account autorizzato a leggere quei log, ad esempio tramite il gruppo `adm` su alcuni sistemi Linux, potrebbe quindi trovare un indizio relativo a una credenziale. Verifica il formato effettivo dei log e i permessi, poi accertati che il valore sia un segreto, che l'account lo accetti e che consenta di attraversare un confine di privilegio. Non presumere che sia stato registrato il corpo della richiesta e non copiare i valori candidati nell'output condiviso.

Esamina solo i log di accesso leggibili e non inserire i valori delle credenziali nell'output condiviso dei comandi. Le righe di richiesta lunghe possono contenere anche un referrer e uno user agent, quindi un filtro per righe brevi può nascondere proprio la richiesta di interesse. I percorsi comuni dei log di accesso di Apache, httpd e Nginx sono `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. I log ruotati possono contenere credenziali meno recenti. [Accesso ai file di log tramite LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) è un percorso correlato agli stessi dati.

I log di autenticazione delle applicazioni possono esporre anche una password inserita per errore nel campo **username** di un tentativo di login non riuscito. Per prima cosa, verifica che il log sia leggibile e che il suo formato registri il nome utente inviato; esamina localmente solo una piccola parte pertinente e non copiare le credenziali candidate nell'output condiviso. Un nome utente che somiglia a una password è un indizio, non la prova che si tratti di una password valida o di un account con privilegi superiori. Verifica l'account a cui era destinata e l'eventuale riutilizzo della password per lo specifico servizio o account Unix prima di affermare che è possibile una transizione.

Un handler di login web scrivibile merita un esame distinto quando un client pianificato, eseguito con un'altra identità, invia credenziali a quell'endpoint. Verifica i permessi di scrittura sull'handler **attivo**, la pianificazione effettiva del client e il percorso della richiesta, di chi siano le credenziali inviate e se quella password dell'applicazione sia valida anche per un account del sistema operativo con privilegi superiori. Una pagina scrivibile o un processo ricorrente, da soli, non dimostrano che tale transizione sia possibile. L'inventario passivo dovrebbe riportare i permessi del percorso e i metadati del job senza modificare l'handler né raccogliere password.

I log EVE JSON di Suricata possono registrare anche i comandi FTP `USER` e `PASS` con il relativo `command_data`, se la registrazione degli eventi FTP è abilitata. Prima di esaminare localmente una piccola parte pertinente, verifica che `/var/log/suricata/eve*.json*` sia leggibile, inclusi i file ruotati o compressi. Un file EVE leggibile è solo un indizio: conferma che gli eventi FTP siano stati registrati, che i dati includano credenziali utilizzabili e che queste consentano di attraversare un confine di privilegio. Evita di stampare `command_data` nell'output condiviso dell'enumerazione. Suricata documenta i [campi degli eventi FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e la [rotazione EVE e le varianti dei nomi dei file](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configurazione Apache generata e log rediretti a comandi

[remco](https://github.com/HeavyHorst/remco) può monitorare un backend key/value, renderizzare un template in un file di configurazione Apache ed eseguire un comando di reload. Esamina l'identità del processo remco in esecuzione, la sorgente e la destinazione del template configurato, i prefissi delle chiavi monitorati e verifica se un valore del backend viene inserito direttamente in una direttiva Apache, come `ServerName`. La sola presenza di un listener del backend locale non dimostra che l'utente corrente possa scrivere una chiave monitorata; verifica l'autenticazione e i permessi del backend prima di affermare che è possibile un'escalation.

Un carattere di nuova riga non sottoposto a escaping in un valore scrivibile del backend può trasformare il valore di una singola direttiva prevista in direttive Apache aggiuntive. I [log Apache rediretti a comandi](https://httpd.apache.org/docs/2.4/logs.html#piped) sono particolarmente sensibili: `CustomLog` o `ErrorLog` con un comando preceduto da `|` avvia un helper con l'identità del processo padre di httpd, spesso root; `|$` chiede ad Apache di usare una shell. Esamina la configurazione generata e il relativo percorso di reload senza modificare i dati del backend né riavviare il servizio durante l'enumerazione. Mantieni riservato il comando completo rediretto, perché i suoi argomenti potrebbero contenere segreti.

## Autenticazione e identità dei servizi

Il file di controllo di Monit si trova solitamente in `~/.monitrc` o `/etc/monitrc`, ma `monit -c` può selezionare un altro percorso. Un file leggibile può contenere voci `set httpd` e `allow user:password` per la sua interfaccia web, spesso sulla porta locale 2812. Prima di esaminarlo, controlla il proprietario e i permessi del file e non inserire i valori delle password nell'output condiviso dell'enumerazione. Le credenziali web concedono solo il ruolo Monit configurato; gli utenti in sola lettura non possono eseguire azioni di controllo. Un'escalation separata verso un account Unix richiede una conferma del riutilizzo della password o un'azione Monit privilegiata che il ruolo autenticato possa effettivamente attivare. Consulta la [documentazione di Monit sui file di controllo e sull'autenticazione](https://www.mmonit.com/monit/documentation/monit.html).

Per Webmin, `/etc/webmin/miniserv.conf` identifica le impostazioni del server e `/etc/webmin/webmin.acl` registra i moduli a cui gli utenti possono accedere; [Webmin documenta i limiti delle autorizzazioni dei moduli](https://webmin.com/docs/development/creating-modules/). Una password Unix o un file ACL leggibile non concede di per sé una sessione Webmin. Verifica la mappatura di autenticazione effettiva, il listener raggiungibile, l'account autenticato, i permessi effettivi del modulo Package Updates, il codice installato o la correzione del vendor e l'identità del processo Webmin. Nelle build interessate fino alla 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) consentiva a un account con i permessi di quel modulo di eseguire comandi tramite il relativo handler di aggiornamento. Durante l'enumerazione passiva, riporta i percorsi di configurazione e i permessi senza stampare credenziali né tentare un aggiornamento.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) gestisce l'autenticazione specifica dei servizi; policy o percorsi dei moduli scrivibili possono modificare il comportamento di login.
- La configurazione di LDAP/SSSD può rivelare endpoint della directory, identità di bind e regole di accesso. Una password di bind recuperata può consentire query LDAP che vanno oltre l'account OS corrente; verifica l'identità di bind esatta e le ACL della directory. Controlla i permessi dei file prima di esaminare i segreti; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) trattano l'uso di ticket e directory.
- Gli alias di Postfix possono inoltrare la posta ricevuta a comandi locali. Se un utente con privilegi inferiori può modificare lo script a cui fanno riferimento, la consegna della posta può eseguire il suo codice con l'identità usata per la consegna. Esamina le mappe degli alias e la proprietà degli script prima di dichiarare percorribile questa strada; vedi [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e altri servizi CI possono eseguire job con un account locale potente. Esamina l'utente del servizio, i percorsi di job/workspace scrivibili e l'interfaccia di amministrazione locale prima di testare una pipeline o un plugin. Esamina anche le **credenziali disponibili per un job** e gli account con cui possono autenticarsi: una Pipeline che usa lo [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) può accedere a un host come utente della credenziale SSH, anche quando Jenkins viene eseguito con un account Unix meno privilegiato. Verifica che l'identità Jenkins corrente disponga di `Job/Create`, `Job/Configure` o di un altro mezzo effettivo per modificare la Pipeline, che la credenziale sia disponibile per quel job e che l'account SSH di destinazione accetti la chiave prima di dichiarare un'escalation dei privilegi sull'host. Il solo nome visualizzato o ID di una credenziale non dimostra nessuna di queste condizioni. Jenkins avverte che chi crea i job e, spesso, chi li configura può usare arbitrariamente le credenziali disponibili nel proprio ambito; perciò [l'ambito delle credenziali](https://www.jenkins.io/doc/book/security/credentials/) e [l'affidabilità delle Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) sono importanti quanto l'UID del servizio. Non includere i valori delle credenziali né le chiavi private nell'output di enumerazione condiviso.

## Scrittura di file nei repository Gogs

Per un servizio Gogs locale, metti in relazione il proprietario del processo `gogs web` con la versione dell'eseguibile e `custom/conf/app.ini`. La configurazione può rivelare l'identità del servizio, la directory radice dei repository, l'indirizzo di ascolto e se la registrazione è disabilitata. Anche un listener limitato al loopback è raggiungibile dagli utenti locali. Le versioni di Gogs fino alla 0.13.3 inclusa presentano un problema di scrittura di file tramite symlink in `PutContents`, autenticato ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): chi può scrivere nel repository può eseguire il commit di un symlink e poi indirizzare tramite esso la scrittura dell'API. L'accesso risultante ai file avviene con i privilegi del processo Gogs, quindi un'istanza eseguita da root richiede attenzione immediata. Verifica la correzione distribuita e i requisiti di autenticazione prima di dichiarare percorribile questa strada; un errore dell'API non dimostra che la scrittura del file sia fallita.

## XSS nella descrizione dei repository Gitea e utenti con privilegi elevati

Gitea 1.22.0 consentiva JavaScript memorizzato nella descrizione di un repository ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versione 1.22.1 ha corretto il problema. Un utente che può modificare una descrizione può influire su una sessione del browser con privilegi maggiori, se quell'utente visualizza il repository e attiva il link malevolo. L'identità del browser può quindi esporre contenuti di repository privati o altri dati dell'applicazione. Per una distinta escalation locale è necessaria una credenziale o un permesso raggiungibile tramite tali contenuti, ad esempio una password di amministratore riutilizzata; il solo proprietario del processo Gitea non dimostra un impatto su root. Verifica la versione distribuita, l'accesso alla modifica delle descrizioni, il flusso di lavoro di chi visualizza il repository e l'effettiva interazione con il browser prima di dichiarare percorribile la catena.

## API di provisioning Cobbler

Il servizio di gestione di Cobbler espone un'API XML-RPC, comunemente sulla porta `25151`. Controlla il listener e il proprietario del processo `cobblerd` prima di valutarne l'impatto; un'API limitata al loopback può comunque essere raggiunta da un utente sull'host. Esamina i moduli di autenticazione e autorizzazione in `/etc/cobbler/modules.conf`, le impostazioni del servizio in `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml` e i permessi su `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. I file digest e del segreto condiviso contengono materiale di autenticazione: annota se sono leggibili senza stamparne il contenuto per impostazione predefinita.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** è un bypass dell'autenticazione XML-RPC in Cobbler dalla versione 3.0.0 alla 3.2.2 e dalla 3.3.0 alla 3.3.6. Un errore di lettura del shared secret restituiva il valore prevedibile `-1`, che l'API accettava come password. Le versioni che correggono il problema sono 3.2.3 e 3.3.7. La versione di un pacchetto è solo un indizio: prima di segnalare un'esposizione, verifica il codice effettivamente distribuito e l'eventuale backport della correzione.

Una sessione API autenticata può consentire l'esecuzione di comandi con privilegi se `cobblerd` viene eseguito come root. Nelle implementazioni vulnerabili, `background_import` passa `rsync_flags` controllati dall'utente a un comando shell, mentre il rendering di un template Cheetah per l'installazione automatica, controllato dall'utente, può eseguire Python. Prima di testare uno dei due percorsi, verifica le autorizzazioni dell'API e la versione installata. Limita l'accesso all'API di gestione, applica la patch per il bypass dell'autenticazione e consenti la lettura dei file di configurazione e delle credenziali solo agli amministratori del servizio.

## Configurazione di Motion e motionEye

Esamina `/etc/motioneye/motioneye.conf` per individuare `conf_path`, quindi controlla `motion.conf` e un numero ridotto di file `camera-*.conf` in quella directory. Segnala se è presente un hash leggibile `# @admin_password`, senza stamparlo. [Le versioni precedenti di motionEye creavano questi file con permessi di lettura troppo ampi](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la correzione è stata introdotta nella versione 0.44.0. Controlla insieme le impostazioni Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost`: il controllo avanzato (`2` o `3`) senza autenticazione può esporre operazioni potenti a un utente locale, anche quando il listener è associato all'interfaccia loopback. [Motion documenta i valori e le impostazioni predefinite](https://motion-project.github.io/motion_config.html).

Prima della versione 0.43.1b5, una sessione amministratore su motionEye poteva trasformare un'impostazione del nome file della telecamera in esecuzione di comandi quando Motion la elaborava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Prima di dichiarare un'escalation, verifica la versione in esecuzione, l'identità del servizio, la disponibilità di un percorso di autenticazione utilizzabile e che sia configurata una telecamera. La sola configurazione non dimostra che il servizio sia in esecuzione o disponga di privilegi.

Il nome di un servizio o un pacchetto installato sono solo indizi. Il confine dei privilegi dipende dall'input raggiungibile, dall'identità del processo, dalla configurazione modificabile e dal comando o file che controlla in ultima istanza.

## Emulatori AWS locali e credenziali archiviate

Un utente dell'host potrebbe raggiungere un emulatore compatibile con AWS in esecuzione in un container tramite il suo endpoint loopback pubblicato. Prima di valutare l'accesso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), correlaziona il listener attivo, l'endpoint e l'account selezionati dal client, nonché le impostazioni di autorizzazione dell'emulatore installato. In LocalStack, [l'applicazione delle policy IAM è un'impostazione separata](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/): non dedurre i permessi effettivi dell'API da un file di credenziali, da una policy IAM o dal solo listener. Verifica il comportamento della versione e della configurazione installate.

Un secret archiviato è utile per un'escalation locale solo se l'identità API corrente può recuperarlo e un account separato con privilegi superiori accetta la credenziale ottenuta. Per accedere a un blob locale cifrato servono inoltre i permessi di lettura sul file, la chiave KMS corrispondente e utilizzabile, l'algoritmo corretto e i permessi effettivi di decrittazione. Per una [chiave KMS asimmetrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la richiesta di decrittazione deve specificare l'algoritmo usato per cifrare il blob. Durante l'enumerazione ordinaria, limita l'inventario automatico dell'host alle prove relative a processi, listener, percorsi di configurazione e permessi dei file; non richiedere né stampare valori secret o testo in chiaro decrittato.
