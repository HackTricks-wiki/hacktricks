# Serviços locais de Web e autenticação

{{#include ../../banners/hacktricks-training.md}}

Um shell Linux oferece uma visão do host dos serviços de Web e autenticação: argumentos dos processos, listeners, arquivos de unidades, configuração, logs e interfaces disponíveis apenas localmente. Use essa visão para relacionar um serviço acessível à conta e aos arquivos que ele realmente usa.

## Mapear a stack local de Web

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecione nomes de virtual hosts, document roots, rotas de proxy, diretórios de upload, configurações de execução do PHP e arquivos de configuração que contenham credenciais. Um listener loopback pode ser acessível por meio de um proxy ou túnel SSH. Para testar um virtual host nomeado contra um listener local, envie o cabeçalho `Host` pretendido ou use `curl --resolve` com o endereço e a porta corretos. A enumeração de virtual hosts também pode revelar nomes ausentes da resposta padrão. Verifique se o Apache permite overrides via `.htaccess` e se os caminhos de upload podem executar PHP antes de tratar um diretório de upload gravável como execução de código. Um source map JavaScript implantado pode expor caminhos do código-fonte ou segredos do lado do cliente; trate os valores recuperados como pistas e verifique os privilégios que eles realmente concedem. Para verificações específicas de web, consulte [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

No Apache com [mpm-itk](https://mpm-itk.sesse.net/), um `AssignUserID` ativo pode executar um virtual host com outro usuário e grupo. Se uma conta com menos privilégios puder gravar um script no `DocumentRoot` desse host, verifique se uma rota acessível realmente o executa com a identidade atribuída. Confirme se o módulo está carregado, a configuração efetiva do virtual host (incluindo overrides de identidade baseados em expressões), as permissões de gravação e busca no diretório, o handler do script e o acesso ao listener. Uma diretiva destacada ou um diretório gravável, por si só, não comprova execução entre usuários.

Um diretório home publicado por um servidor web pode expor arquivos de backup de arquivos de identidade SSH mesmo quando o diretório `.ssh` ativo é privado. Por exemplo, a configuração [`homedirs_public` do Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleciona um subdiretório servido a partir dos diretórios home dos usuários. Um resultado de arquivo baseado apenas no caminho é uma pista: verifique o mapeamento efetivo do servidor, a legibilidade local ou a autorização HTTP, o conteúdo do arquivo, a senha da chave privada e se a conta correspondente realmente aceita a chave. Não extraia arquivos de backup nem imprima material de chaves durante a enumeração rotineira de hosts.

Um backup legível de um aplicativo web local com privilégios mais altos pode revelar a lógica de autenticação e leitura de arquivos, mesmo quando o código-fonte ativo está inacessível. Compare o backup com o serviço implantado antes de confiar nele. Em particular, vale revisar um cookie criado criptografando texto controlado pelo usuário, seguido de um segredo e de uma flag de função, se o aplicativo usar blocos ECB determinísticos, retornar cookies novos para texto escolhido e depois dividir o valor descriptografado por um delimitador sem escape. [A NIST explica o mapeamento de blocos independente e repetível do ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); essa propriedade pode viabilizar uma comparação com entrada escolhida, mas não concede, por si só, uma função mais privilegiada. Confirme a rota ativa, os pré-requisitos da sessão, o parser e o fluxo de dados exatos, a identidade do serviço e uma ação privilegiada separada ou um caminho de leitura de arquivos. O inventário passivo deve informar os metadados do backup e a propriedade do listener, sem ler o conteúdo do arquivo nem enviar sondagens de autenticação.

A mesma abordagem de revisão de código-fonte se aplica a um serviço local privilegiado **não HTTP**, como uma interface personalizada baseada em SSH. Se um backup de código-fonte acessível mostrar um comando que aceita um caminho de arquivo escolhido pelo usuário, verifique a autenticação, como o caminho é resolvido e se o código comprova que o arquivo resolvido permanece dentro de um diretório pretendido antes de abri-lo. Em Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normaliza um caminho, mas não garante que ele permaneça dentro desse diretório. Confirme que o backup corresponde à build em execução, que o listener é acessível, que a conta com menos privilégios pode usar o comando e que o processo pode ler o destino; possuir uma chave SSH legível é uma questão separada da política de login. Informe os caminhos dos arquivos de código-fonte e a propriedade do serviço sem extrair o conteúdo de arquivos ou chaves para a saída automatizada.

Um pool PHP-FPM escutando em TCP loopback pode ser acessado por outra conta local mesmo quando o site exige autenticação. [O PHP alerta que um cliente capaz de se conectar ao FastCGI pode controlar as configurações da requisição, incluindo `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revise as configurações `listen` e `listen.allowed_clients` do pool junto com o listener ativo, o UID dos workers, o caminho de um script existente e quaisquer restrições `security.limit_extensions` ou `php_admin_value`. Arquivos de configuração de pools podem conter credenciais em diretivas `env[...]`, portanto o inventário automatizado deve informar seus caminhos, não seu conteúdo. Um arquivo de configuração ou uma porta, por si só, não comprova um caminho de execução entre usuários; consulte o [guia FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para detalhes do protocolo.

Para uma API local privilegiada, rastreie também a autorização, além da execução de código. Uma função de banco de dados que a conta com menos privilégios pode alterar pode liberar uma rota de API, mas o próximo limite depende da implementação dessa rota. Por exemplo, mesclar o JSON da requisição em um objeto JavaScript e depois chamar [`child_process.exec`](https://nodejs.org/api/child_process.html) merece uma revisão do [fluxo de dados de prototype pollution até a execução](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifique a biblioteca/versão de mesclagem real, a validação da entrada, a rota acessível, a identidade do processo e as opções do processo filho; um listener Node de propriedade do root ou o nome de uma dependência vulnerável é apenas uma pista.

Armazenamentos de CMS baseados em arquivos podem conter verificadores de senha de administrador fora dos arquivos de configuração `.php` convencionais. Exemplos incluem `data/database.js` ou `data/settings/pass.php` de um site. Verifique a propriedade e a legibilidade dos arquivos antes de revisá-los manualmente, e não inclua hashes na saída automatizada compartilhada. Uma senha recuperável do aplicativo é um limite de privilégio separado de uma conta Unix: verifique qualquer alegação de reutilização para a conta específica e o método de autenticação permitido.

O controlador de autenticação de um aplicativo também pode conter uma senha de login literal no código-fonte, em vez de em um arquivo de configuração. Se um usuário com menos privilégios puder ler o controlador implantado, revise localmente a comparação de autenticação e não inclua nenhum valor na saída de enumeração compartilhada. Confirme que o caminho de código está ativo, que a senha é válida para o aplicativo e que uma conta Unix separada com privilégios mais altos realmente aceita essa mesma senha antes de alegar escalonamento de privilégios local. O nome de um arquivo controlador é apenas uma pista para revisão.

O Dolibarr armazena configurações de conexão ao banco de dados, incluindo `dolibarr_main_db_pass`, em `htdocs/conf/conf.php` ([referência de configuração](https://wiki.dolibarr.org/index.php/Configuration_file)). Um arquivo legível é uma pista de credencial; somente a reutilização de senha de uma conta verificada separadamente ou outra permissão no banco de dados poderia transformá-la em escalonamento de privilégios local. Inspecione as permissões primeiro e evite imprimir o valor na saída automatizada.

A configuração do pacote Linux do GitLab normalmente fica em `/etc/gitlab/gitlab.rb`, embora implantações possam manter cópias legíveis em outros locais. [O GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que esse arquivo pode conter `gitlab_rails['smtp_password']`, embora configurações SMTP criptografadas possam manter a senha fora do arquivo em texto simples. Trate uma configuração legível como uma pista de credencial: verifique se está ativa, se a credencial ainda é válida e se uma conta específica com privilégios mais altos a aceita antes de alegar reutilização de senha. Separadamente, [o GitLab executa `gitlab.rb` como código Ruby sob o root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); um arquivo ativo gravável ou um `from_file` incluído precisa de um caminho real para reconfiguração privilegiada antes de ser considerado uma descoberta de execução. Uma prévia da configuração pode expor valores de credenciais; trate sua saída como sensível e compartilhe apenas caminhos e permissões.

Uma instalação self-hosted do Mattermost pode manter `SqlSettings.DataSource` em `/opt/mattermost/config/config.json`; [o Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esse caminho usual quanto implantações que armazenam a configuração ativa em um banco de dados. Um arquivo legível pode expor uma credencial do banco de dados do aplicativo, mas não comprova acesso ao banco de dados nem acesso ao root Unix. Verifique a origem da configuração ativa, as permissões reais da função do banco de dados, qualquer senha do aplicativo recuperada separadamente e se essa senha funciona para uma conta Unix específica com privilégios mais altos. O formato dos hashes de senha pode mudar entre versões do Mattermost; durante a enumeração, registre o caminho da configuração e os metadados de acesso sem imprimir a string de conexão nem consultar o banco de dados.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtre os resultados de virtual hosts comparando-os com o tamanho da resposta padrão ou outra referência estável, para que todos os nomes adivinhados não pareçam válidos. Um source map só é útil se estiver realmente implantado ou puder ser lido de outra forma.

Proxies reversos podem alterar quais cabeçalhos do cliente uma aplicação considera confiáveis. Compare solicitações diretas e via proxy antes de presumir que `X-Forwarded-For`, `X-Forwarded-Host` ou cabeçalhos semelhantes estabelecem a identidade de quem fez a solicitação. Revise em conjunto a configuração do proxy e da aplicação.

Se o PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` para uma string passada a [`system()`](https://www.php.net/manual/en/function.system.php), verifique se o caminho de solicitação acessível permite que quem faz a solicitação forneça um cabeçalho e se os metacaracteres do shell chegam inalterados a essa string. Um comando como `sudo iptables` inserido no início **não** faz com que comandos posteriores separados pelo shell sejam executados como root; eles são executados como o worker web, a menos que uma regra sudo efetiva separada permita a escalada. Confirme a identidade do worker, a concessão exata de `sudo -l` e o requisito de autenticação, além dos limites dos argumentos do comando, antes de afirmar que há um caminho para root. Inspecione o código-fonte e a política sem enviar uma tentativa de injeção durante a enumeração rotineira do host.

## Credenciais de login em logs de acesso

Se uma aplicação envia um formulário de login com `GET`, o nome de usuário e a senha podem se tornar parâmetros de consulta na URI da solicitação. Uma solicitação `POST` também pode conter uma query string; usar `POST` não oculta um segredo colocado acidentalmente na URI, incluindo uma senha inserida em um campo não relacionado do formulário. A [linha de solicitação do log de acesso comum do Apache](https://httpd.apache.org/docs/2.4/logs.html) registra o método e a URI, incluindo sua query string, quando o formato configurado usa `%r`. Portanto, uma conta com permissão para ler esses logs, por exemplo, por pertencer ao grupo `adm` em alguns sistemas Linux, pode encontrar uma possível credencial. Verifique o formato e as permissões reais do log; em seguida, confirme que o valor é um segredo, que a conta o aceita e que ele atravessa um limite de privilégios. Não presuma que o corpo da solicitação foi registrado nem copie possíveis valores para uma saída compartilhada.

Inspecione apenas logs de acesso legíveis e não inclua valores de credenciais na saída compartilhada de comandos. Linhas longas de solicitação também podem conter um referenciador e um user agent, então um filtro para linhas curtas pode ocultar justamente a solicitação de interesse. Os locais comuns dos logs de acesso do Apache, httpd e Nginx são `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. Logs rotacionados podem conter credenciais antigas. [O acesso a arquivos de log por LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) é um caminho relacionado para acessar os mesmos dados.

Os logs de autenticação da aplicação também podem expor uma senha inserida acidentalmente no campo **username** de um login malsucedido. Primeiro, confirme que o log pode ser lido e que seu formato registra o nome de usuário enviado; inspecione localmente apenas um pequeno trecho relevante e não copie possíveis credenciais para uma saída compartilhada. Um nome de usuário com formato de senha é uma pista, não uma prova de que seja uma senha válida ou de que ofereça privilégios mais elevados. Verifique a conta pretendida e qualquer reutilização da senha no serviço específico ou em uma conta Unix antes de afirmar que há uma transição.

Um manipulador de login web gravável exige uma análise separada quando um cliente agendado, executado com outra identidade, envia credenciais a esse endpoint. Confirme o acesso de gravação ao manipulador **ativo**, o agendamento real do cliente e o caminho da solicitação, de quem é a credencial enviada e se essa senha da aplicação também é válida para uma conta do sistema operacional com privilégios mais elevados. Uma página gravável ou um processo recorrente, por si só, não comprova essa transição. O inventário passivo deve registrar as permissões do caminho e os metadados da tarefa sem alterar o manipulador nem coletar senhas.

Os logs JSON EVE do Suricata também podem registrar comandos FTP `USER` e `PASS` com seus dados `command_data` quando o registro de eventos FTP está habilitado. Verifique se `/var/log/suricata/eve*.json*` pode ser lido, incluindo arquivos rotacionados ou compactados, antes de revisar localmente um pequeno trecho relevante. Um arquivo EVE legível é apenas uma pista: confirme que os eventos FTP foram registrados, que os dados incluem uma credencial utilizável e que ela atravessa um limite de privilégios. Evite exibir `command_data` na saída compartilhada da enumeração. O Suricata documenta os [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e as [variantes de rotação e nomes de arquivos EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuração do Apache gerada e logs encaminhados por pipe

O [remco](https://github.com/HeavyHorst/remco) pode monitorar um backend de chave/valor, renderizar um template em um arquivo de configuração do Apache e executar um comando de recarga. Inspecione a identidade do processo remco em execução, a origem e o destino do template configurado, os prefixos de chave monitorados e se um valor do backend é inserido diretamente em uma diretiva do Apache, como `ServerName`. Um listener local do backend, por si só, não comprova que o usuário atual pode gravar uma chave monitorada; verifique a autenticação e as permissões do backend antes de afirmar que há uma escalada.

Uma quebra de linha não escapada em um valor gravável do backend pode transformar o valor de uma diretiva pretendida em diretivas adicionais do Apache. Os [logs encaminhados por pipe do Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) são especialmente sensíveis: `CustomLog` ou `ErrorLog` com um comando `|` inicia um processo auxiliar sob a identidade do processo httpd pai, geralmente root; `|$` solicita que o Apache use um shell. Revise a configuração gerada e seu caminho de recarga sem alterar os dados do backend nem reiniciar o serviço durante a enumeração. Mantenha privado o comando completo do pipe, pois seus argumentos podem conter segredos.

## Identidades de autenticação e de serviço

O arquivo de controle do Monit costuma ser `~/.monitrc` ou `/etc/monitrc`, mas `monit -c` pode selecionar outro caminho. Um arquivo legível pode conter entradas `set httpd` e `allow user:password` para sua interface web, geralmente na porta local 2812. Verifique o proprietário e as permissões do arquivo antes de analisá-lo e não inclua valores de senha na saída compartilhada da enumeração. As credenciais web concedem apenas a função Monit configurada; usuários somente de leitura não podem executar ações de controle. Uma escalada separada para uma conta Unix exige a confirmação da reutilização da senha ou de uma ação privilegiada do Monit que a função autenticada possa realmente acionar. Consulte a [documentação de autenticação e do arquivo de controle do Monit](https://www.mmonit.com/monit/documentation/monit.html).

No Webmin, `/etc/webmin/miniserv.conf` identifica as configurações do servidor e `/etc/webmin/webmin.acl` registra quais módulos os usuários podem acessar; o [Webmin documenta o limite de concessão de módulos](https://webmin.com/docs/development/creating-modules/). Uma senha Unix ou um arquivo ACL legível não concede, por si só, uma sessão Webmin. Confirme o mapeamento de autenticação real, o listener acessível, a conta autenticada, a permissão efetiva do módulo Package Updates, o código instalado ou a correção do fornecedor e a identidade do processo Webmin. Em versões afetadas até a 1.910, a [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitia que uma conta com essa permissão de módulo executasse comandos por meio do manipulador de atualização. Durante a enumeração passiva, informe os caminhos e as permissões da configuração sem exibir credenciais nem tentar uma atualização.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) rege a autenticação específica de cada serviço; caminhos de políticas ou módulos com permissão de escrita podem alterar o comportamento do login.
- A configuração de LDAP/SSSD pode revelar endpoints de diretório, identidades de bind e regras de acesso. Uma senha de bind recuperada pode permitir consultas LDAP além da conta atual do SO; teste a identidade de bind exata e as ACLs do diretório. Revise as permissões dos arquivos antes de inspecionar segredos; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) abordam o uso de tickets e diretórios.
- Aliases do Postfix podem encaminhar emails recebidos para comandos locais. Se um usuário com menos privilégios puder alterar o script referenciado, a entrega de email poderá executar o código desse usuário sob a identidade usada na entrega. Revise os mapas de aliases e a propriedade do script antes de afirmar que esse caminho é viável; consulte [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e outros serviços de CI podem executar jobs sob uma conta local privilegiada. Inspecione o usuário do serviço, os caminhos de jobs/workspaces com permissão de escrita e a interface de administração local antes de testar um pipeline ou plugin. Revise também as **credenciais disponíveis para um job** e a conta com a qual podem autenticar: um Pipeline que usa o [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) pode acessar um host como o usuário da credencial SSH, mesmo quando o próprio Jenkins é executado sob uma conta Unix com menos privilégios. Confirme que a identidade atual do Jenkins tem `Job/Create`, `Job/Configure` ou outra forma efetiva de alterar o Pipeline, que a credencial está disponível para esse job e que a conta SSH de destino aceita a chave antes de afirmar que houve uma escalada de privilégios no host. O nome de exibição ou ID de uma credencial, por si só, não comprova nenhuma dessas condições. O Jenkins alerta que criadores de jobs e, muitas vezes, seus configuradores podem usar arbitrariamente as credenciais disponíveis no escopo deles; portanto, o [credential scope](https://www.jenkins.io/doc/book/security/credentials/) e o [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) são tão importantes quanto o UID do serviço. Não inclua valores de credenciais nem chaves privadas na saída de enumeração compartilhada.

## Escrita de arquivos em repositórios do Gogs

Em um serviço Gogs local, correlacione o proprietário do processo `gogs web` com a versão do executável e `custom/conf/app.ini`. A configuração pode revelar a identidade do serviço, a raiz do repositório, o endereço de escuta e se o registro está desativado. Mesmo um listener limitado ao loopback continua acessível a usuários locais. Versões do Gogs até a 0.13.3 têm um problema de escrita de arquivos via symlink em `PutContents` que exige autenticação ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): um usuário com permissão para escrever no repositório pode fazer commit de um symlink e, em seguida, direcionar a escrita da API por ele. O acesso resultante aos arquivos usa os privilégios do processo Gogs, portanto, uma instância executada como root exige atenção imediata. Valide a correção implantada e os requisitos de autenticação antes de afirmar que o caminho é viável; um erro da API não comprova que a escrita do arquivo falhou.

## XSS na descrição de repositórios do Gitea e visualizadores privilegiados

O Gitea 1.22.0 permitia JavaScript armazenado na descrição de um repositório ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); a versão 1.22.1 corrigiu o problema. Um usuário que possa editar uma descrição pode afetar uma sessão de navegador mais privilegiada se esse usuário visualizar o repositório e ativar o link malicioso. Essa identidade do navegador pode então expor conteúdo de repositórios privados ou outros dados da aplicação. Uma escalada local separada exige uma credencial ou permissão acessível por meio desse conteúdo, como uma senha de administrador reutilizada; o fato de o processo Gitea pertencer a determinado usuário não comprova impacto de root. Verifique a versão implantada, o acesso para editar descrições, o fluxo de trabalho do visualizador e a interação real com o navegador antes de afirmar que a cadeia é viável.

## API de provisionamento do Cobbler

O serviço de gerenciamento do Cobbler expõe uma API XML-RPC, normalmente na porta `25151`. Verifique o listener e o proprietário do processo `cobblerd` antes de avaliar o impacto; uma API limitada ao loopback ainda pode ser acessada por um usuário no host. Revise os módulos de autenticação e autorização em `/etc/cobbler/modules.conf`, as configurações do serviço em `/etc/cobbler/settings` ou `/etc/cobbler/settings.yaml` e as permissões de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. Os arquivos de digest e de segredo compartilhado contêm material de credenciais; por padrão, registre se podem ser lidos sem imprimir seu conteúdo.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** é um bypass de autenticação XML-RPC no Cobbler 3.0.0 a 3.2.2 e 3.3.0 a 3.3.6. Um erro de leitura do segredo compartilhado retornava o valor previsível `-1`, que a API aceitava como senha. As correções correspondentes estão nas versões 3.2.3 e 3.3.7. A versão de um pacote é apenas uma pista; verifique o código implantado e qualquer correção retroportada antes de relatar a exposição.

Uma sessão autenticada da API pode oferecer um caminho para execução privilegiada quando `cobblerd` é executado como root. Nas implementações afetadas, `background_import` passa `rsync_flags` controlado pelo usuário para um comando de shell, e a renderização de um template de autoinstall Cheetah controlado pelo usuário pode avaliar Python. Verifique as permissões da API e a versão instalada antes de testar qualquer um desses caminhos. Restrinja o acesso à API de gerenciamento, corrija o bypass de autenticação e permita que apenas os administradores do serviço leiam os arquivos de configuração e credenciais.

## Configuração do Motion e do motionEye

Inspecione `/etc/motioneye/motioneye.conf` para encontrar `conf_path` e, em seguida, examine `motion.conf` e uma pequena quantidade de arquivos `camera-*.conf` nesse diretório. Informe se existe um hash legível de `# @admin_password`, sem exibi-lo. [Versões antigas do motionEye gravavam esses arquivos com permissões de leitura amplas](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); a correção está na versão 0.44.0. Verifique em conjunto as configurações do Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost`: o controle avançado (`2` ou `3`) com autenticação desativada pode expor operações poderosas a um usuário local, inclusive em um listener loopback. [A documentação do Motion descreve os valores e padrões](https://motion-project.github.io/motion_config.html).

Uma sessão de admin no motionEye anterior à versão 0.43.1b5 podia transformar uma configuração de nome de arquivo de câmera em execução de comandos quando o Motion a processava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Confirme a versão em execução, a identidade do serviço, um caminho de autenticação utilizável e se há uma câmera configurada antes de afirmar que há escalada. A configuração, por si só, não prova que o serviço está em execução ou é privilegiado.

O nome de um serviço ou um pacote instalado é apenas uma pista. O limite de privilégio é determinado pela combinação de entrada acessível, identidade do processo, configuração gravável e o comando ou arquivo que ela controla por fim.

## Emuladores locais de AWS e credenciais armazenadas

Um usuário do host pode alcançar um emulador compatível com AWS em execução em um container por meio do endpoint loopback publicado. Correlacione o listener ativo, o endpoint e a conta selecionados pelo cliente e as configurações de autorização instaladas no emulador antes de avaliar o acesso ao [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) ou ao [KMS](https://docs.localstack.cloud/aws/services/kms/). No LocalStack, [a aplicação de políticas do IAM é uma configuração separada](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); não deduza as permissões efetivas da API com base apenas em um arquivo de credenciais, uma política do IAM ou um listener. Confirme o comportamento da versão e da configuração instaladas.

Um segredo armazenado só é útil para escalada local se a identidade atual da API puder recuperá-lo e se uma conta separada com privilégios superiores aceitar a credencial recuperada. Um blob local criptografado também exige acesso de leitura ao arquivo, a chave KMS correspondente e utilizável e acesso efetivo para descriptografar. Para uma [chave KMS assimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), a solicitação de descriptografia deve especificar o algoritmo usado para criptografar o blob. Limite o inventário automático do host a evidências de processos, listeners, caminhos de configuração e permissões de arquivos; durante a enumeração de rotina, não solicite nem exiba valores de segredos ou texto simples descriptografado.
