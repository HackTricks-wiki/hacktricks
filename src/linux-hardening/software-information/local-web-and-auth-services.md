# Web local y servicios de autenticación

{{#include ../../banners/hacktricks-training.md}}

Una shell de Linux proporciona una vista desde el host de los servicios web y de autenticación: argumentos de procesos, sockets en escucha, archivos de unidades, configuración, registros e interfaces solo locales. Usa esa vista para relacionar un servicio accesible con la cuenta y los archivos que realmente utiliza.

## Mapear la pila web local

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecciona los nombres de virtual hosts, las raíces de documentos, las rutas del proxy, los directorios de subida, la configuración de ejecución de PHP y los archivos de configuración que contengan credenciales. Un listener de loopback puede ser accesible a través de un proxy o un túnel SSH. Para probar un virtual host con nombre contra un listener local, envía el encabezado `Host` previsto o usa `curl --resolve` con la dirección y el puerto correctos. La enumeración de virtual hosts también puede revelar nombres ausentes en la respuesta predeterminada. Comprueba si Apache permite overrides de `.htaccess` y si las rutas de subida pueden ejecutar PHP antes de considerar que un directorio de subida con permisos de escritura permite ejecutar código. Un mapa de código fuente de JavaScript desplegado puede revelar rutas de origen o secretos del lado del cliente; trata los valores recuperados como pistas y verifica sus privilegios reales. Para comprobaciones específicas de web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) y [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

En Apache con [mpm-itk](https://mpm-itk.sesse.net/), un `AssignUserID` activo puede ejecutar un virtual host con un usuario y grupo diferentes. Si una cuenta con menos privilegios puede escribir un script en el `DocumentRoot` de ese host, comprueba si una ruta accesible realmente lo ejecuta con la identidad asignada. Confirma que el módulo está cargado, la configuración efectiva del virtual host (incluidos los overrides de identidad basados en expresiones), los permisos de escritura y búsqueda del directorio, el handler del script y el acceso al listener. Una directiva resaltada o un directorio con permisos de escritura no demuestran por sí solos la ejecución entre usuarios.

Un directorio personal publicado a través de un servidor web puede exponer copias de seguridad de archivos de identidad SSH, aunque el directorio `.ssh` activo sea privado. Por ejemplo, la configuración `homedirs_public` de [Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) selecciona un subdirectorio servido desde los directorios personales de los usuarios. Encontrar una ruta en un archivo de archivo es solo una pista: verifica la asignación efectiva del servidor, la legibilidad local o la autorización HTTP, el contenido del archivo de archivo, la frase de contraseña de la clave privada y si la cuenta correspondiente realmente acepta la clave. No extraigas archivos de archivo ni muestres material de claves durante la enumeración rutinaria del host.

Una copia de seguridad legible de una aplicación web local con más privilegios puede revelar la lógica de autenticación y lectura de archivos, aunque no se pueda acceder al código fuente activo. Compara la copia de seguridad con el servicio desplegado antes de confiar en ella. En particular, conviene revisar una cookie creada cifrando texto controlado por quien llama, seguido de un secreto y un indicador de rol, si la aplicación usa bloques ECB deterministas, devuelve cookies nuevas para texto elegido y luego divide el valor descifrado usando un delimitador sin escapar. [NIST explica el mapeo independiente y repetible de bloques de ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); esa propiedad puede permitir una comparación con entrada elegida, pero no concede por sí sola un rol superior. Confirma la ruta activa, los requisitos de sesión, el flujo exacto del parser y de los datos, la identidad del servicio y una acción privilegiada independiente o una ruta de lectura de archivos. El inventario pasivo debe informar los metadatos de la copia de seguridad y quién es el propietario del listener, sin leer el contenido del archivo de archivo ni enviar pruebas de autenticación.

El mismo enfoque de revisión de código fuente se aplica a un servicio local privilegiado **no HTTP**, como una interfaz personalizada respaldada por SSH. Si una copia de seguridad accesible del código fuente muestra un comando que acepta una ruta de archivo elegida por quien llama, comprueba su mecanismo de autenticación, cómo resuelve la ruta y si verifica que el archivo resuelto permanezca dentro de un directorio previsto antes de abrirlo. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) limpia una ruta, pero no garantiza que permanezca dentro de ese directorio. Confirma que la copia de seguridad coincide con la compilación en ejecución, que se puede acceder al listener, que la cuenta con menos privilegios puede usar el comando y que el proceso puede leer el objetivo; disponer de una clave SSH legible es una cuestión independiente de la política de inicio de sesión. Informa las rutas de los archivos de archivo de código fuente y quién es el propietario del servicio, sin extraer el contenido de los archivos de archivo ni las claves en la salida automatizada.

Se puede acceder a un pool de PHP-FPM que escucha en el loopback TCP desde otra cuenta local, aunque su sitio web requiera autenticación. [PHP advierte que un cliente capaz de conectarse a FastCGI puede controlar la configuración de las solicitudes, incluido `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revisa los ajustes `listen` y `listen.allowed_clients` del pool junto con el listener activo, el UID de los workers, una ruta de script existente y cualquier restricción `security.limit_extensions` o `php_admin_value`. Los archivos de configuración del pool pueden contener credenciales en directivas `env[...]`, por lo que el inventario automatizado debe informar sus rutas, no su contenido. Un archivo de configuración o un puerto por sí solos no demuestran una ruta de ejecución entre usuarios; consulta la [guía de FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para conocer los detalles del protocolo.

En el caso de una API local privilegiada, sigue también la autorización, además de la ejecución de código. Un rol de base de datos que la cuenta con menos privilegios pueda cambiar podría desbloquear una ruta de API, pero el siguiente límite depende de la implementación de esa ruta. Por ejemplo, merece la pena revisar si combinar el JSON de una solicitud con un objeto JavaScript y luego llamar a [`child_process.exec`](https://nodejs.org/api/child_process.html) crea un [flujo de datos de prototype pollution a ejecución](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la biblioteca y versión reales usadas para combinar los datos, la validación de entradas, la ruta accesible, la identidad del proceso y las opciones del proceso hijo; un listener de Node propiedad de root o el nombre de una dependencia vulnerable son solo pistas.

Los CMS que almacenan datos en archivos pueden guardar verificadores de contraseñas de administrador fuera de los archivos de configuración `.php` convencionales. Algunos ejemplos son `data/database.js` o `data/settings/pass.php` de un sitio. Comprueba la propiedad y la legibilidad de los archivos antes de revisarlos manualmente, y no incluyas hashes en la salida automatizada compartida. Una contraseña recuperable de una aplicación es un límite de privilegios distinto al de una cuenta Unix: verifica cualquier reutilización alegada con la cuenta específica y el método de autenticación permitido.

El controlador de autenticación de una aplicación también puede contener una contraseña literal de inicio de sesión en el código fuente, en lugar de en un archivo de configuración. Si un usuario con menos privilegios puede leer el controlador desplegado, revisa localmente su comparación de autenticación y no incluyas ningún valor en la salida de enumeración compartida. Confirma que la ruta de código está activa, que la contraseña es válida para la aplicación y que una cuenta Unix independiente con más privilegios acepta realmente esa misma contraseña antes de afirmar que permite una escalada local de privilegios. El nombre de un archivo de controlador es solo una pista para revisarlo.

Dolibarr almacena la configuración de conexión a la base de datos, incluido `dolibarr_main_db_pass`, en `htdocs/conf/conf.php` ([referencia de configuración](https://wiki.dolibarr.org/index.php/Configuration_file)). Un archivo legible es una pista de que puede haber credenciales; solo la reutilización verificada de la contraseña de una cuenta independiente u otro permiso de base de datos permitiría una escalada local de privilegios. Comprueba primero los permisos y evita mostrar el valor en la salida automatizada.

La configuración del paquete de GitLab para Linux suele estar en `/etc/gitlab/gitlab.rb`, aunque las instalaciones pueden conservar copias legibles en otros lugares. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que este archivo puede contener `gitlab_rails['smtp_password']`, aunque la configuración SMTP cifrada puede guardar la contraseña fuera del archivo de texto sin cifrar. Trata un archivo de configuración legible como una pista de que puede haber credenciales: verifica que esté activo, que la credencial siga vigente y que una cuenta específica con más privilegios la acepte antes de afirmar que hay reutilización de contraseña. Por separado, [GitLab ejecuta `gitlab.rb` como código Ruby con privilegios de root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un archivo activo con permisos de escritura o un `from_file` incluido requiere una ruta real de reconfiguración privilegiada para constituir un hallazgo de ejecución. La vista previa de una configuración puede exponer valores de credenciales, así que trata su salida como información sensible y comparte las rutas y los permisos.

Una instalación de Mattermost autohospedada puede guardar `SqlSettings.DataSource` en `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esa ruta habitual como las instalaciones que guardan la configuración activa en una base de datos. Un archivo legible puede exponer una credencial de base de datos de la aplicación, pero no demuestra que se pueda acceder a la base de datos ni a la cuenta Unix root. Verifica la fuente de configuración activa, los permisos reales del rol de la base de datos, cualquier contraseña de aplicación recuperada por separado y si esa contraseña funciona para una cuenta Unix específica con más privilegios. El formato de los hashes de contraseñas puede cambiar entre versiones de Mattermost; durante la enumeración, registra la ruta de configuración y los metadatos de acceso sin mostrar la cadena de conexión ni consultar la base de datos.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra los resultados de virtual hosts comparándolos con el tamaño de la respuesta predeterminada u otra referencia estable para que no parezca válido cada nombre probado. Un source map solo es útil si realmente está desplegado o se puede leer de otro modo.

Los reverse proxies pueden cambiar qué headers del cliente considera fiables una aplicación. Compara las solicitudes directas y las que pasan por el proxy antes de asumir que `X-Forwarded-For`, `X-Forwarded-Host` o headers similares establecen la identidad de quien realiza la solicitud. Revisa conjuntamente la configuración del proxy y la aplicación.

Si PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` en una cadena que se pasa a [`system()`](https://www.php.net/manual/en/function.system.php), revisa si la ruta de solicitud accesible permite que el cliente proporcione un header y si los metacaracteres del shell llegan intactos a esa cadena. Que al inicio se incluya un comando como `sudo iptables` **no** hace que los comandos posteriores separados por el shell se ejecuten como root; se ejecutan como el proceso worker web, salvo que otra regla efectiva de sudo permita la escalada. Confirma la identidad del worker, la concesión exacta de `sudo -l` y el requisito de autenticación, así como el límite de los argumentos del comando, antes de afirmar que hay una ruta a root. Inspecciona el código fuente y la política sin enviar una prueba de inyección durante el inventario rutinario del host.

## Credenciales de inicio de sesión en los logs de acceso

Si una aplicación envía un formulario de inicio de sesión mediante `GET`, el nombre de usuario y la contraseña pueden convertirse en parámetros de consulta en el URI de la solicitud. Una solicitud `POST` también puede incluir una cadena de consulta; usar `POST` no oculta un secreto que se haya colocado accidentalmente en el URI, incluida una contraseña introducida en un campo de formulario no relacionado. [La línea de solicitud del log de acceso común de Apache](https://httpd.apache.org/docs/2.4/logs.html) registra el método y el URI, incluida su cadena de consulta, cuando el formato configurado usa `%r`. Por lo tanto, una cuenta con permiso para leer esos logs, por ejemplo, a través del grupo `adm` en algunos sistemas Linux, podría encontrar indicios de credenciales. Comprueba el formato y los permisos reales del log; luego verifica que el valor sea un secreto, que la cuenta lo acepte y que permita cruzar un límite de privilegios. No des por hecho que se registró el cuerpo de la solicitud ni copies valores candidatos en la salida compartida.

Inspecciona solo los logs de acceso que puedas leer y no incluyas valores de credenciales en la salida compartida de comandos. Las líneas de solicitud largas también pueden contener un referrer y un user agent, por lo que un filtro de líneas cortas puede ocultar precisamente la solicitud que interesa. Las ubicaciones habituales de los logs de acceso de Apache, httpd y Nginx son `/var/log/apache2/access.log`, `/var/log/httpd/access_log` y `/var/log/nginx/access.log`. Los logs rotados pueden contener credenciales antiguas. [El acceso a archivos de log mediante LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) es una ruta relacionada para acceder a los mismos datos.

Los logs de autenticación de aplicaciones también pueden exponer una contraseña que se haya introducido accidentalmente en el campo de **nombre de usuario** al fallar un inicio de sesión. Primero confirma que puedes leer el log y que su formato registra el nombre de usuario enviado; inspecciona localmente solo un fragmento pequeño y relevante, y no copies credenciales candidatas en la salida compartida. Un nombre de usuario con aspecto de contraseña es un indicio, no una prueba de que sea una contraseña válida ni de que otorgue mayores privilegios. Verifica la cuenta prevista y cualquier reutilización en el servicio o la cuenta Unix específicos antes de afirmar que permite una transición.

Un handler de inicio de sesión web con permisos de escritura merece una revisión aparte cuando un cliente programado, bajo otra identidad, envía credenciales a ese endpoint. Confirma que se pueda escribir en el handler **activo**, cuál es la programación real del cliente y la ruta de la solicitud, de quién son las credenciales que envía y si esa contraseña de la aplicación es válida por separado para una cuenta del sistema operativo con mayores privilegios. Una página con permisos de escritura o un proceso recurrente, por sí solos, no demuestran que se pueda realizar esa transición. El inventario pasivo debe informar sobre los permisos de la ruta y los metadatos del job sin modificar el handler ni recopilar contraseñas.

Los logs JSON EVE de Suricata también pueden registrar los comandos FTP `USER` y `PASS` con su `command_data` si está habilitado el registro de eventos FTP. Comprueba si se pueden leer los archivos `/var/log/suricata/eve*.json*`, incluidos los rotados o comprimidos, antes de revisar localmente un fragmento pequeño y relevante. Un archivo EVE legible es solo un indicio: confirma que se registraron eventos FTP, que los datos incluyen una credencial utilizable y que esta permite cruzar un límite de privilegios. Evita mostrar `command_data` en la salida compartida del inventario. Suricata documenta los [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) y [la rotación y las variantes de nombres de archivo de EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuración generada de Apache y logs canalizados

[remco](https://github.com/HeavyHorst/remco) puede supervisar un backend de clave/valor, renderizar una plantilla en un archivo de configuración de Apache y ejecutar un comando de recarga. Inspecciona la identidad del proceso remco en ejecución, el origen y el destino de la plantilla configurada, los prefijos de claves supervisados y si un valor del backend se inserta directamente en una directiva de Apache como `ServerName`. Que haya un listener local del backend no demuestra que el usuario actual pueda escribir en una clave supervisada; verifica la autenticación y los permisos del backend antes de afirmar que permite una escalada.

Un salto de línea sin escapar en un valor del backend con permisos de escritura puede convertir el valor previsto para una directiva en directivas de Apache adicionales. Los [logs canalizados de Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) son especialmente sensibles: `CustomLog` o `ErrorLog` con un comando `|` inicia un helper con la identidad del proceso padre httpd, a menudo root; `|$` indica a Apache que use un shell. Revisa la configuración generada y su ruta de recarga sin cambiar los datos del backend ni reiniciar el servicio durante el inventario. Mantén privado el comando canalizado completo, porque sus argumentos pueden contener secretos.

## Autenticación e identidades de servicio

El archivo de control de Monit suele ser `~/.monitrc` o `/etc/monitrc`, pero `monit -c` puede seleccionar otra ruta. Un archivo legible puede contener entradas `set httpd` y `allow user:password` para su interfaz web, a menudo en el puerto local 2812. Comprueba el propietario y los permisos del archivo antes de revisarlo, y no incluyas valores de contraseña en la salida compartida del inventario. Las credenciales web solo otorgan el rol de Monit configurado; los usuarios de solo lectura no pueden ejecutar acciones de control. Para escalar mediante una cuenta Unix, se necesita confirmar la reutilización de la contraseña o una acción privilegiada de Monit que el rol autenticado pueda ejecutar. Consulta la [documentación del archivo de control y la autenticación de Monit](https://www.mmonit.com/monit/documentation/monit.html).

En Webmin, `/etc/webmin/miniserv.conf` identifica la configuración del servidor y `/etc/webmin/webmin.acl` registra a qué módulos pueden acceder los usuarios; [Webmin documenta el límite de permisos de los módulos](https://webmin.com/docs/development/creating-modules/). Una contraseña Unix o un archivo ACL legible no otorgan por sí solos una sesión de Webmin. Confirma la asignación real de autenticación, el listener accesible, la cuenta autenticada, los permisos efectivos del módulo Package Updates, el código instalado o la corrección del proveedor y la identidad del proceso Webmin. En las versiones afectadas hasta la 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitía que una cuenta con permisos para ese módulo ejecutara comandos mediante su handler de actualización. Durante el inventario pasivo, informa de las rutas de configuración y sus permisos sin mostrar credenciales ni intentar una actualización.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) rige la autenticación específica de cada servicio; las rutas de políticas o módulos con permisos de escritura pueden cambiar el comportamiento del inicio de sesión.
- La configuración de LDAP/SSSD puede revelar endpoints del directorio, identidades de enlace y reglas de acceso. Una contraseña de enlace recuperada puede permitir consultas LDAP que van más allá de la cuenta actual del sistema operativo; prueba la identidad de enlace exacta y las ACL del directorio. Revisa los permisos de los archivos antes de inspeccionar secretos; [Linux Active Directory](../user-information/linux-active-directory.md) y [FreeIPA](freeipa-pentesting.md) tratan el uso de tickets y directorios.
- Los alias de Postfix pueden canalizar el correo recibido a comandos locales. Si un usuario con menos privilegios puede modificar el script referenciado, la entrega de correo podría ejecutar su código con la identidad de entrega. Revisa los mapas de alias y la propiedad del script antes de afirmar que esa ruta es viable; consulta [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins y otros servicios de CI pueden ejecutar jobs con una cuenta local con muchos privilegios. Inspecciona el usuario del servicio, las rutas de jobs/workspace con permisos de escritura y la interfaz de administración local antes de probar un pipeline o plugin. Revisa también las **credenciales disponibles para un job** y la cuenta con la que pueden autenticarse: un Pipeline que use el [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) puede acceder a un host como el usuario de la credencial SSH, incluso si Jenkins se ejecuta con una cuenta Unix con menos privilegios. Confirma que la identidad actual de Jenkins tiene `Job/Create`, `Job/Configure` u otra forma efectiva de modificar el Pipeline, que la credencial está dentro del alcance de ese job y que la cuenta SSH de destino acepta la clave antes de afirmar que hay una escalada de privilegios en el host. El nombre visible o el ID de una credencial, por sí solos, no demuestran ninguna de estas condiciones. Jenkins advierte que quienes crean jobs y, a menudo, quienes los configuran pueden usar arbitrariamente las credenciales disponibles en su ámbito; por lo tanto, [credential scope](https://www.jenkins.io/doc/book/security/credentials/) y [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) importan tanto como el UID del servicio. No incluyas valores de credenciales ni claves privadas en resultados de enumeración compartidos.

## Escritura de archivos en repositorios de Gogs

En un servicio local de Gogs, relaciona el propietario del proceso `gogs web` con la versión del ejecutable y `custom/conf/app.ini`. La configuración puede revelar la identidad del servicio, la raíz del repositorio, la dirección de escucha y si el registro está deshabilitado. Incluso un listener limitado a loopback es accesible para usuarios locales. Las versiones de Gogs hasta la 0.13.3 tienen un problema de escritura de archivos mediante symlink en `PutContents` que requiere autenticación ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): un usuario con permisos de escritura en el repositorio puede subir un symlink y luego dirigir a través de él una escritura mediante la API. El acceso resultante a los archivos tiene los privilegios del proceso de Gogs, por lo que una instancia ejecutada como root requiere atención inmediata. Valida que la corrección esté implementada y los requisitos de autenticación antes de afirmar que la ruta es viable; un error de la API no demuestra que la escritura del archivo haya fallado.

## XSS en la descripción de repositorios de Gitea y usuarios con privilegios que la ven

Gitea 1.22.0 permitía JavaScript almacenado en la descripción de un repositorio ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versión 1.22.1 lo corrigió. Un usuario que pueda editar una descripción puede afectar una sesión de navegador con más privilegios si ese usuario ve el repositorio y activa el enlace malicioso. Esa identidad del navegador puede entonces exponer contenido de repositorios privados u otros datos de la aplicación. Para una escalada local independiente se necesita una credencial o permiso accesible a través de ese contenido, como una contraseña de administrador reutilizada; que el proceso de Gitea se ejecute con determinado usuario no demuestra por sí solo un impacto en root. Comprueba la versión implementada, los permisos para editar descripciones, el flujo de trabajo de quien ve el contenido y la interacción real con el navegador antes de afirmar que la cadena es viable.

## API de aprovisionamiento de Cobbler

El servicio de administración de Cobbler expone una API XML-RPC, normalmente en el puerto `25151`. Comprueba el listener y el propietario del proceso `cobblerd` antes de evaluar su impacto; incluso un API limitado a loopback puede ser accesible para un usuario del host. Revisa los módulos de autenticación y autorización en `/etc/cobbler/modules.conf`, la configuración del servicio en `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml`, y los permisos de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` y `/var/lib/cobbler/web.ss`. Los archivos de digest y de secretos compartidos contienen material de credenciales, así que registra si se pueden leer sin imprimir su contenido de forma predeterminada.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** es un bypass de autenticación XML-RPC en Cobbler 3.0.0 a 3.2.2 y 3.3.0 a 3.3.6. Un error al leer el secreto compartido devolvía el valor predecible `-1`, que la API aceptaba como contraseña. Las versiones que corrigen el problema son 3.2.3 y 3.3.7. La versión de un paquete es solo una pista; verifica el código desplegado y cualquier corrección retroportada antes de informar de una exposición.

Una sesión autenticada de la API puede ser una vía de ejecución con privilegios si `cobblerd` se ejecuta como root. En las implementaciones afectadas, `background_import` pasa `rsync_flags` controlados por el usuario a un comando de shell, y al renderizar una plantilla Cheetah de autoinstalación controlada por el usuario se puede evaluar Python. Comprueba los permisos de la API y la versión instalada antes de probar cualquiera de estas vías. Restringe el acceso a la API de gestión, aplica el parche del bypass de autenticación y permite que solo los administradores del servicio lean los archivos de configuración y credenciales.

## Configuración de Motion y motionEye

Inspecciona `/etc/motioneye/motioneye.conf` para encontrar `conf_path` y, después, revisa `motion.conf` y una pequeña cantidad de archivos `camera-*.conf` en ese directorio. Informa si existe un hash `# @admin_password` legible, sin imprimirlo. [Las versiones anteriores de motionEye escribían estos archivos con permisos de lectura amplios](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la corrección está en la versión 0.44.0. Comprueba en conjunto los ajustes `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` y `webcontrol_localhost` de Motion: el control avanzado (`2` o `3`) con la autenticación deshabilitada puede exponer operaciones potentes a un usuario local, incluso si el listener está en loopback. [Motion documenta los valores y los valores predeterminados](https://motion-project.github.io/motion_config.html).

Una sesión de administrador en motionEye anterior a la versión 0.43.1b5 podía convertir un ajuste del nombre de archivo de la cámara en ejecución de comandos cuando Motion lo procesaba ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Confirma la versión en ejecución, la identidad del servicio, una vía de autenticación utilizable y si hay una cámara configurada antes de afirmar que se puede escalar privilegios. La configuración por sí sola no demuestra que el servicio se esté ejecutando o tenga privilegios.

El nombre de un servicio o un paquete instalado es solo una pista. El límite de privilegios depende de la combinación de una entrada accesible, la identidad del proceso, la configuración con permisos de escritura y el comando o archivo que controla en última instancia.

## Emuladores locales de AWS y credenciales almacenadas

Un usuario del host puede acceder a un emulador compatible con AWS que se ejecute en un contenedor a través de su endpoint de loopback publicado. Antes de evaluar el acceso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), correlaciona el listener activo, el endpoint y la cuenta que selecciona el cliente, y los ajustes de autorización instalados en el emulador. En LocalStack, [la aplicación de políticas de IAM es un ajuste independiente](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); no deduzcas los permisos efectivos de la API a partir de un archivo de credenciales, una política de IAM o un listener por sí solos. Confirma el comportamiento de la versión y la configuración instaladas.

Un secreto almacenado solo sirve para escalar privilegios localmente si la identidad actual de la API puede recuperarlo y una cuenta independiente con más privilegios acepta la credencial obtenida. Un blob local cifrado también requiere acceso de lectura al archivo, la clave KMS correspondiente utilizable y el algoritmo adecuado, y permisos efectivos de descifrado. Para una [clave KMS asimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la solicitud de descifrado debe especificar el algoritmo utilizado para cifrar el blob. Limita el inventario automático del host a pruebas del proceso, el listener, la ruta de configuración y los permisos de los archivos; durante la enumeración rutinaria, no solicites ni imprimas valores de secretos ni texto en claro descifrado.
