# Servizi web locali e di autenticazione

{{#include ../../banners/hacktricks-training.md}}

Una shell Linux offre una visione dei servizi web e di autenticazione dal punto di vista dell’host: argomenti dei processi, listener, file delle unità, configurazione, log e interfacce accessibili solo localmente. Usa questa prospettiva per collegare un servizio raggiungibile all’account e ai file che utilizza effettivamente.

## Mappare lo stack web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Esamina i nomi dei virtual host, le root dei documenti, le route proxy, le directory di upload, le impostazioni di esecuzione PHP e i file di configurazione che contengono credenziali. Un listener loopback potrebbe essere raggiungibile tramite un proxy o un tunnel SSH. Per testare un virtual host nominato rispetto a un listener locale, invia l'header `Host` previsto oppure usa `curl --resolve` con l'indirizzo e la porta corretti. L'enumerazione dei virtual host può anche rivelare nomi assenti dalla risposta predefinita. Verifica se Apache consente gli override tramite `.htaccess` e se i percorsi di upload possono eseguire PHP prima di considerare una directory di upload scrivibile come un'esecuzione di codice. Una source map JavaScript distribuita può esporre percorsi sorgente o segreti lato client; considera i valori recuperati come indizi e verifica i loro privilegi effettivi. Per i controlli specifici del web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Con Apache e [mpm-itk](https://mpm-itk.sesse.net/), un `AssignUserID` attivo può eseguire un virtual host con un utente e un gruppo diversi. Se un account con privilegi inferiori può scrivere uno script nella `DocumentRoot` di quell'host, verifica se una route raggiungibile lo esegue effettivamente con l'identità assegnata. Conferma che il modulo sia caricato, verifica la configurazione effettiva del virtual host (compresi gli override dell'identità basati su espressioni), i permessi di scrittura e attraversamento delle directory, l'handler dello script e l'accesso al listener. Una direttiva evidenziata o una directory scrivibile, da sole, non dimostrano l'esecuzione con l'identità di un altro utente.

Una directory home pubblicata tramite un web server può esporre archivi di backup di file di identità SSH anche quando la directory `.ssh` attiva è privata. Per esempio, l'impostazione `homedirs_public` di [Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleziona una sottodirectory servita dalle directory home degli utenti. Un riscontro di un archivio basato solo sul percorso è un indizio: verifica la mappatura effettiva del server, la leggibilità locale o l'autorizzazione HTTP, il contenuto dell'archivio, la passphrase della chiave privata e se l'account corrispondente accetta davvero la chiave. Nelle normali attività di enumerazione dell'host, non estrarre archivi né stampare il contenuto delle chiavi.

Un backup leggibile di un'applicazione web locale con privilegi più elevati può rivelare la logica di autenticazione e lettura dei file anche quando il codice sorgente attivo non è accessibile. Confronta il backup con il servizio distribuito prima di farci affidamento. In particolare, è opportuno esaminare un cookie creato cifrando testo controllato dal chiamante seguito da un segreto e da un flag di ruolo, se l'app usa blocchi ECB deterministici, restituisce cookie nuovi per testo scelto e in seguito suddivide il valore decifrato usando un delimitatore non sottoposto a escape. [NIST spiega la mappatura indipendente e ripetibile dei blocchi ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); questa proprietà può supportare un confronto con input scelti, ma non concede di per sé un ruolo più elevato. Conferma la route attiva, i prerequisiti della sessione, il parser e il flusso dei dati esatti, l'identità del servizio e un'azione privilegiata o un percorso di lettura dei file indipendente. L'inventario passivo dovrebbe riportare i metadati dei backup e la proprietà dei listener senza leggerne il contenuto né inviare richieste di autenticazione.

Lo stesso approccio di revisione del codice sorgente si applica a un servizio locale privilegiato **non HTTP**, come un'interfaccia personalizzata basata su SSH. Se un backup accessibile del codice sorgente mostra un comando che accetta un percorso di file scelto dal chiamante, verifica il controllo di autenticazione, il modo in cui risolve il percorso e se dimostra che il file risolto rimane all'interno di una directory prevista prima di aprirlo. In Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normalizza un percorso, ma non ne impone il confinamento. Conferma che il backup corrisponda alla build in esecuzione, che il listener sia raggiungibile, che l'account con privilegi inferiori possa usare il comando e che il processo possa leggere il file di destinazione; il possesso di una chiave SSH leggibile è una questione distinta dalle policy di accesso. Riporta i percorsi degli archivi sorgente e la proprietà del servizio senza estrarre il contenuto degli archivi o le chiavi nell'output automatizzato.

Un pool PHP-FPM in ascolto su TCP loopback può essere raggiunto da un altro account locale anche quando il sito web richiede l'autenticazione. [PHP avverte che un client in grado di connettersi a FastCGI può controllare le impostazioni delle richieste, tra cui `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Esamina le impostazioni `listen` e `listen.allowed_clients` del pool insieme al listener attivo, all'UID dei worker, al percorso di uno script esistente e a eventuali restrizioni `security.limit_extensions` o `php_admin_value`. I file di configurazione dei pool possono contenere credenziali nelle direttive `env[...]`, quindi l'inventario automatizzato dovrebbe riportarne i percorsi, non il contenuto. Un file di configurazione o una porta, da soli, non dimostrano un percorso di esecuzione tra utenti; per i dettagli del protocollo, consulta la [guida FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md).

Per un'API locale privilegiata, analizza l'autorizzazione oltre all'esecuzione del codice. Un ruolo del database modificabile dall'account con privilegi inferiori potrebbe sbloccare una route API, ma il confine successivo dipende dall'implementazione della route. Per esempio, unire il JSON della richiesta a un oggetto JavaScript e poi chiamare [`child_process.exec`](https://nodejs.org/api/child_process.html) richiede una verifica del [flusso dei dati da prototype pollution a esecuzione](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la libreria/versione effettiva usata per l'unione, la validazione dell'input, la route raggiungibile, l'identità del processo e le opzioni del processo figlio; un listener Node di proprietà di root o il solo nome di una dipendenza vulnerabile sono soltanto indizi.

Gli archivi CMS basati su file possono contenere verificatori delle password degli amministratori al di fuori dei tradizionali file di configurazione `.php`. Alcuni esempi sono `data/database.js` o `data/settings/pass.php` di un sito. Verifica la proprietà e la leggibilità dei file prima di esaminarli manualmente e non includere gli hash nell'output automatizzato condiviso. Una password dell'applicazione recuperabile costituisce un confine di privilegio distinto da un account Unix: verifica ogni presunto riutilizzo sull'account specifico e con il metodo di autenticazione consentito.

Il controller di autenticazione di un'applicazione può contenere anche una password di accesso in chiaro nel codice sorgente invece che in un file di configurazione. Se un utente con privilegi inferiori può leggere il controller distribuito, esamina localmente il confronto usato per l'autenticazione e non includere alcun valore nell'output condiviso dell'enumerazione. Conferma che il percorso del codice sia attivo, che la password sia valida per l'applicazione e che un account Unix distinto con privilegi più elevati accetti davvero la stessa password prima di dichiarare un'escalation locale dei privilegi. Il solo nome di un file controller è soltanto un indizio da verificare.

Dolibarr memorizza le impostazioni di connessione al database, tra cui `dolibarr_main_db_pass`, in `htdocs/conf/conf.php` ([riferimento alla configurazione](https://wiki.dolibarr.org/index.php/Configuration_file)). Un file leggibile è un indizio relativo a credenziali; solo un riutilizzo verificato della password di un account distinto o un altro permesso del database può trasformarlo in un'escalation locale dei privilegi. Controlla prima i permessi ed evita di stampare il valore nell'output automatizzato.

Il file di configurazione del pacchetto Linux di GitLab è normalmente `/etc/gitlab/gitlab.rb`, anche se le installazioni potrebbero conservare altrove copie leggibili. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) che questo file può contenere `gitlab_rails['smtp_password']`, sebbene le impostazioni SMTP cifrate possano mantenere la password al di fuori del file in chiaro. Considera una configurazione leggibile come un indizio relativo a credenziali: verifica che sia attiva, che la credenziale sia valida e che un account specifico con privilegi più elevati la accetti prima di dichiarare il riutilizzo della password. Separatamente, [GitLab esegue `gitlab.rb` come codice Ruby con privilegi di root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un file attivo scrivibile o un `from_file` incluso richiede un effettivo percorso di riconfigurazione privilegiata prima di poter essere considerato un riscontro di esecuzione. L'anteprima di una configurazione può esporre i valori delle credenziali: considera sensibile il relativo output e condividi invece i percorsi e i permessi.

Un'installazione self-hosted di Mattermost può memorizzare `SqlSettings.DataSource` in `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) sia questo percorso abituale sia le installazioni che memorizzano invece la configurazione attiva in un database. Un file leggibile può esporre una credenziale del database dell'applicazione, ma non dimostra né l'accesso al database né l'accesso a root in Unix. Verifica la fonte di configurazione attiva, i permessi effettivi del ruolo del database, le eventuali password dell'applicazione recuperate separatamente e se tale password funziona per uno specifico account Unix con privilegi più elevati. Il formato dell'hash delle password può variare tra le versioni di Mattermost; durante l'enumerazione registra il percorso del file di configurazione e i metadati di accesso senza stampare la stringa di connessione né interrogare il database.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra i risultati dei virtual host confrontandoli con la dimensione della risposta predefinita o con un’altra baseline stabile, così da evitare che ogni nome indovinato sembri valido. Una source map è utile solo se è effettivamente distribuita o comunque leggibile.

I reverse proxy possono modificare quali header del client vengono considerati attendibili da un’applicazione. Confronta le richieste dirette e quelle inoltrate dal proxy prima di presumere che `X-Forwarded-For`, `X-Forwarded-Host` o header simili identifichino il chiamante. Esamina insieme la configurazione del proxy e quella dell’applicazione.

Se PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` in una stringa passata a [`system()`](https://www.php.net/manual/en/function.system.php), verifica se il percorso della richiesta accessibile consente di impostare un header controllato dal chiamante e se i metacaratteri della shell arrivano invariati a quella stringa. Un comando come `sudo iptables` inserito all’inizio **non** fa sì che i comandi successivi separati dalla shell vengano eseguiti come root; questi vengono eseguiti con l’identità del web worker, a meno che una regola sudo effettiva separata non consenta l’escalation. Prima di affermare che esiste un percorso verso root, verifica l’identità del worker, l’esatta autorizzazione `sudo -l`, l’eventuale requisito di autenticazione e i limiti degli argomenti del comando. Durante la normale enumerazione degli host, esamina il codice sorgente e le policy senza inviare probe di injection.

## API loopback privilegiate dopo un foothold web

Una shell ottenuta tramite un processo web può chiamare servizi HTTP locali anche quando i relativi listener sono associati a `127.0.0.1`. Nella versione vulnerabile di Control Web Panel segnalata, la dashboard dell’account viene eseguita come utente di hosting, ma l’API utente su `https://127.0.0.1:2302` viene eseguita come root. La sua route POST `/v1/restoredatabase/` omette il controllo dell’access-token e passa il campo `file` a `shell_exec('mysql ... < ' . $file)`. Pertanto, da un foothold con un utente di hosting, i separatori della shell nel campo `file` vengono eseguiti come root. Verifica sia il controllo della route sia l’identità effettiva del processo API; il binding su loopback, da solo, non equivale ad autenticazione. Vedi [PHP execution after redirect](../../pentesting-web/login-bypass/#php-execution-after-redirect) per un metodo per ottenere quel foothold. Le vulnerabilità segnalate sono state corrette completamente entro CWP 1.29.<sup>[[1]](#references)</sup>

```bash
curl -sk 'https://127.0.0.1:2302/v1/restoredatabase/' \
  --data-urlencode 'file=/dev/null ; id > /tmp/root-proof ; echo'
```

La stessa API presenta anche una vulnerabilità distinta nel controllo di autenticazione: `access_token()` inserisce il token fornito nella query `WHERE authorization_code='$access_token' AND client_id='$user'`. Una riga `UNION` con le colonne attese e una scadenza futura può soddisfare il controllo del token, commentando la condizione originale relativa all’ID client. Questo sblocca route protette come `/v1/newpass/`, dove `user` non sanitizzato viene aggiunto a un comando shell `passwd` di proprietà di root. L’injection del token aggira il controllo; l’esecuzione di comandi dipende comunque da quel secondo sink. Vedi [SQL injection authentication bypass](../../pentesting-web/login-bypass/#sql-injection-authentication-bypass).<sup>[[1]](#references)</sup>

Nel controllo a sei colonne descritto, il token iniettato può fornire una scadenza futura e ignorare il predicato rimanente; la struttura delle colonne è specifica di quella build.<sup>[[1]](#references)</sup>

```sql
' UNION SELECT 'a','x','c','d','2099-01-01 00:00:00','f' -- -
```

Una route separata senza token, `/v1/user_panel_dashboard/`, inserisce `user` in una query a `oauth_clients`. Si tratta di una lettura blind del database con la connessione MySQL-root dell'API, **non** di esecuzione come root del sistema operativo: il server MySQL gira con l'utente OS `mysql`. Se la tabella interrogata è vuota, una [sonda temporale con derived table costante](../../pentesting-web/sql-injection/#exploiting-time-based-sqli) evita di perdere il ritardo a causa delle righe mancanti.<sup>[[1]](#references)</sup>

## Credenziali di login nei log di accesso

Se un'applicazione invia un modulo di login con `GET`, nome utente e password possono diventare parametri di query nell'URI della richiesta. Anche una richiesta `POST` può contenere una query string: usare `POST` non nasconde un segreto inserito per errore nell'URI, inclusa una password digitata in un campo non correlato del modulo. La [riga di richiesta comune del log di accesso Apache](https://httpd.apache.org/docs/2.4/logs.html) registra il metodo e l'URI, inclusa la query string, quando il formato configurato usa `%r`. Un account autorizzato a leggere quei log, per esempio tramite il gruppo `adm` su alcuni sistemi Linux, potrebbe quindi trovare una credenziale da verificare. Controlla il formato effettivo del log e i permessi, poi verifica che il valore sia un segreto, che l'account lo accetti e che consenta di oltrepassare un confine di privilegi. Non presumere che sia stato registrato il corpo della richiesta e non copiare valori candidati in output condivisi.

Esamina solo i log di accesso leggibili e non includere i valori delle credenziali nell'output dei comandi condiviso. Le righe di richiesta lunghe possono contenere anche un referrer e uno user agent, quindi un filtro per righe brevi può nascondere proprio la richiesta che interessa. I percorsi comuni dei log di accesso Apache, httpd e Nginx sono `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. I log ruotati possono contenere credenziali meno recenti. [L'accesso ai file di log tramite LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) è un percorso correlato per ottenere gli stessi dati.

Anche i log di autenticazione dell'applicazione possono esporre una password inserita per errore nel campo **username** durante un login non riuscito. Prima accertati che il log sia leggibile e che il suo formato registri lo username inviato; esamina localmente solo una piccola sezione pertinente e non copiare credenziali candidate nell'output condiviso. Uno username che somiglia a una password è un indizio, non la prova che si tratti di una password valida o di privilegi superiori. Prima di dichiarare un passaggio di privilegi, verifica l'account previsto e l'eventuale riutilizzo della password nello specifico servizio o account Unix.

Un handler di login web scrivibile merita una verifica separata se un client pianificato, con un'altra identità, invia credenziali a quell'endpoint. Conferma l'accesso in scrittura all'handler **attivo**, la pianificazione effettiva del client e il percorso della richiesta, a chi appartengono le credenziali che invia e se quella password dell'applicazione è valida anche per un account del sistema operativo con privilegi superiori. Una pagina scrivibile o un processo ricorrente, da soli, non dimostrano quel passaggio. L'inventario passivo dovrebbe riportare i permessi del percorso e i metadati del job senza modificare l'handler né raccogliere password.

I log JSON EVE di Suricata possono registrare anche i comandi FTP `USER` e `PASS` con il relativo `command_data`, se è attiva la registrazione degli eventi FTP. Verifica che `/var/log/suricata/eve*.json*` sia leggibile, inclusi i file ruotati o compressi, prima di esaminarne localmente una piccola sezione pertinente. Un file EVE leggibile è solo un indizio: conferma che siano stati registrati gli eventi FTP, che i dati includano credenziali utilizzabili e che consentano di oltrepassare un confine di privilegi. Evita di stampare `command_data` nell'output di enumerazione condiviso. Suricata documenta i [campi degli eventi FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e le [varianti di rotazione e nome file EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configurazione Apache generata e log con pipe

[remco](https://github.com/HeavyHorst/remco) può monitorare un backend key/value, generare un file di configurazione Apache da un template ed eseguire un comando di reload. Esamina l'identità del processo remco in esecuzione, la sorgente e la destinazione del template configurato, i prefissi delle chiavi monitorati e se un valore del backend viene inserito direttamente in una direttiva Apache come `ServerName`. La sola presenza di un listener locale del backend non dimostra che l'utente corrente possa scrivere una chiave monitorata; verifica autenticazione e permessi del backend prima di dichiarare un'escalation.

Un newline non escapato in un valore scrivibile del backend può trasformare il valore previsto di una direttiva in ulteriori direttive Apache. I [log con pipe di Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) sono particolarmente sensibili: `CustomLog` o `ErrorLog` con un comando `|` avvia un helper con l'identità del processo httpd padre, spesso root; `|$` chiede ad Apache di usare una shell. Esamina la configurazione generata e il relativo percorso di reload senza modificare i dati del backend né riavviare il servizio durante l'enumerazione. Mantieni privato il comando completo della pipe, perché i suoi argomenti potrebbero contenere segreti.

## Identità di autenticazione e dei servizi

Il file di controllo di Monit è solitamente `~/.monitrc` o `/etc/monitrc`, ma `monit -c` può selezionare un altro percorso. Un file leggibile può contenere voci `set httpd` e `allow user:password` per la sua interfaccia web, spesso sulla porta locale 2812. Controlla proprietario e permessi del file prima di esaminarlo e non includere i valori delle password nell'output di enumerazione condiviso. Le credenziali web concedono solo il ruolo Monit configurato; gli utenti in sola lettura non possono eseguire azioni di controllo. Un'escalation separata verso un account Unix richiede il riutilizzo della password confermato o un'azione Monit privilegiata che il ruolo autenticato possa effettivamente avviare. Consulta la [documentazione di Monit sui file di controllo e sull'autenticazione](https://www.mmonit.com/monit/documentation/monit.html).

Per Webmin, `/etc/webmin/miniserv.conf` identifica le impostazioni del server e `/etc/webmin/webmin.acl` registra i moduli a cui gli utenti possono accedere; [Webmin documenta i limiti delle autorizzazioni sui moduli](https://webmin.com/docs/development/creating-modules/). Una password Unix o un file ACL leggibile non concedono di per sé una sessione Webmin. Verifica la mappatura di autenticazione effettiva, il listener raggiungibile, l'account autenticato, i permessi effettivi del modulo Package Updates, il codice installato o la correzione del vendor e l'identità del processo Webmin. Nelle build interessate fino alla 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) consentiva a un account con quell'autorizzazione sul modulo di eseguire comandi tramite il relativo handler di aggiornamento. Durante l'enumerazione passiva, riporta i percorsi di configurazione e i permessi senza stampare credenziali né tentare un aggiornamento.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) gestisce l’autenticazione specifica dei servizi; modificare policy o percorsi dei moduli scrivibili può cambiare il comportamento dell’accesso.
- La configurazione LDAP/SSSD può rivelare endpoint di directory, identità di bind e regole di accesso. Una password di bind recuperata può consentire query LDAP oltre quelle permesse dall’account OS corrente; verifica l’identità di bind esatta e le ACL della directory. Controlla i permessi dei file prima di esaminare i segreti; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) trattano l’uso di ticket e directory.
- Gli alias di Postfix possono inoltrare le email ricevute a comandi locali. Se un utente con privilegi inferiori può modificare lo script indicato, la consegna delle email può eseguire il suo codice con l’identità usata per la consegna. Esamina le mappe degli alias e la proprietà degli script prima di affermare che questo percorso sia utilizzabile; vedi [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e altri servizi CI possono eseguire job con un potente account locale. Esamina l’utente del servizio, i percorsi di job/workspace scrivibili e l’interfaccia di amministrazione locale prima di testare una pipeline o un plugin. Esamina anche le **credenziali disponibili per un job** e l’account con cui possono autenticarsi: una Pipeline che usa lo [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) può accedere a un host come utente della credenziale SSH, anche se Jenkins stesso viene eseguito con un account Unix meno privilegiato. Prima di affermare che ci sia un’escalation dei privilegi sull’host, verifica che l’identità Jenkins corrente disponga di `Job/Create`, `Job/Configure` o di un altro percorso effettivo per modificare la Pipeline, che la credenziale rientri nell’ambito di quel job e che l’account SSH di destinazione accetti la chiave. Il solo nome visualizzato o ID di una credenziale non dimostra nessuna di queste condizioni. Jenkins avverte che chi crea i job e, spesso, chi li configura può usare arbitrariamente le credenziali disponibili nel proprio ambito; perciò [credential scope](https://www.jenkins.io/doc/book/security/credentials/) e [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) contano tanto quanto l’UID del servizio. Non includere i valori delle credenziali e le chiavi private nell’output di enumerazione condiviso.

## Gogs repository file writes

Per un servizio Gogs locale, correla il proprietario del processo `gogs web` con la versione dell’eseguibile e `custom/conf/app.ini`. La configurazione può rivelare l’identità del servizio, la root dei repository, l’indirizzo su cui è in ascolto e se la registrazione è disabilitata. Un listener raggiungibile solo tramite loopback è comunque accessibile agli utenti locali. Le versioni di Gogs fino alla 0.13.3 inclusa presentano un problema di scrittura di file tramite symlink autenticato in `PutContents` ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): chi può scrivere in un repository può eseguire il commit di un symlink e poi indirizzare la scrittura dell’API attraverso di esso. L’accesso ai file risultante ha i privilegi del processo Gogs, quindi un’istanza eseguita da root richiede attenzione immediata. Verifica la correzione installata e i requisiti di autenticazione prima di affermare che il percorso sia utilizzabile; un errore API non dimostra che la scrittura del file non sia riuscita.

## Gitea repository-description XSS and privileged viewers

Gitea 1.22.0 permetteva JavaScript memorizzato nella descrizione di un repository ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versione 1.22.1 ha corretto il problema. Un utente che può modificare una descrizione può influire su una sessione browser con privilegi maggiori se quell’utente visualizza il repository e attiva il link malevolo. L’identità del browser può quindi esporre contenuti di repository privati o altri dati dell’applicazione. Un’escalation locale separata richiede credenziali o autorizzazioni raggiungibili attraverso quei contenuti, come una password amministratore riutilizzata; il solo proprietario del processo Gitea non dimostra un impatto su root. Prima di affermare che la catena sia sfruttabile, controlla la versione installata, i permessi di modifica della descrizione, il flusso di visualizzazione e l’effettiva interazione con il browser.

## Cobbler provisioning API

Il servizio di gestione di Cobbler espone un’API XML-RPC, comunemente sulla porta `25151`. Prima di valutarne l’impatto, controlla il listener e il proprietario del processo `cobblerd`; un’API raggiungibile solo tramite loopback può comunque essere raggiunta da un utente sull’host. Esamina i moduli di autenticazione e autorizzazione in `/etc/cobbler/modules.conf`, le impostazioni del servizio in `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml` e i permessi su `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. I file digest e delle chiavi segrete condivise contengono materiale di autenticazione: annota se sono leggibili senza stamparne il contenuto per impostazione predefinita.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** è un bypass dell'autenticazione XML-RPC in Cobbler dalla versione 3.0.0 alla 3.2.2 e dalla 3.3.0 alla 3.3.6. Un errore durante la lettura del shared secret restituiva il valore prevedibile `-1`, che l'API accettava come password. Le versioni con le correzioni sono la 3.2.3 e la 3.3.7. La versione di un pacchetto è solo un indizio: prima di segnalare un'esposizione, verifica il codice effettivamente installato e l'eventuale presenza di una correzione backportata.

Una sessione API autenticata può costituire un percorso di esecuzione privilegiata se `cobblerd` viene eseguito come root. Nelle implementazioni vulnerabili, `background_import` passa `rsync_flags`, controllato dall'utente, a un comando shell, mentre il rendering di un template Cheetah autoinstall controllato dall'utente può eseguire codice Python. Prima di testare uno dei due percorsi, verifica le autorizzazioni API e la versione installata. Limita l'accesso all'API di gestione, applica la patch per il bypass dell'autenticazione e consenti la lettura dei file di configurazione e delle credenziali solo agli amministratori del servizio.

## Configurazione di Motion e motionEye

Esamina `/etc/motioneye/motioneye.conf` per trovare `conf_path`, quindi controlla `motion.conf` e alcuni file `camera-*.conf` in quella directory. Segnala se è presente un hash leggibile `# @admin_password`, senza stamparlo. [Le versioni precedenti di motionEye scrivevano questi file con permessi di lettura troppo ampi](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la correzione è inclusa nella versione 0.44.0. Controlla insieme le impostazioni Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost`: il controllo avanzato (`2` o `3`) con autenticazione disabilitata può esporre operazioni potenti a un utente locale, anche su un listener loopback. [Motion documenta i valori e le impostazioni predefinite](https://motion-project.github.io/motion_config.html).

Una sessione admin su motionEye prima della versione 0.43.1b5 poteva trasformare un'impostazione del nome file della videocamera in esecuzione di comandi, quando Motion la elaborava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Prima di dichiarare un'escalation, verifica la versione in esecuzione, l'identità del servizio, la possibilità di autenticarsi e la presenza di una videocamera configurata. La sola configurazione non dimostra che il servizio sia in esecuzione o disponga di privilegi.

Il nome di un servizio o un pacchetto installato sono solo indizi. Il confine dei privilegi dipende dalla combinazione di input raggiungibile, identità del processo, configurazione scrivibile e comando o file controllato in ultima istanza.

## Emulatori AWS locali e credenziali memorizzate

Un utente host potrebbe raggiungere un emulatore compatibile con AWS eseguito in un container tramite il suo endpoint loopback pubblicato. Prima di valutare l'accesso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), verifica il listener attivo, l'endpoint e l'account selezionati dal client, nonché le impostazioni di autorizzazione installate nell'emulatore. In LocalStack, [l'applicazione delle policy IAM è un'impostazione separata](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/): non dedurre i permessi API effettivi da un file di credenziali, da una policy IAM o dal solo listener. Verifica il comportamento della versione e della configurazione installate.

Un secret memorizzato è utile per l'escalation locale solo se l'identità API corrente può recuperarlo e un account separato con privilegi superiori accetta la credenziale ottenuta. Per accedere a un blob locale cifrato servono anche l'accesso in lettura al file, la chiave KMS corrispondente utilizzabile e l'algoritmo corretto, oltre all'autorizzazione effettiva per la decifratura. Per una [chiave KMS asimmetrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la richiesta di decifratura deve specificare l'algoritmo usato per cifrare il blob. Limita l'inventario automatico dell'host alle evidenze relative a processi, listener, percorsi di configurazione e permessi dei file; durante la normale enumerazione, non richiedere né stampare valori dei secret o testo in chiaro decifrato.
