# स्थानीय Web और Authentication Services

{{#include ../../banners/hacktricks-training.md}}

Linux shell, web और authentication services का host-side view देता है: process arguments, listeners, unit files, configuration, logs और केवल स्थानीय interfaces। इस view का उपयोग करके किसी reachable service को उस account और files से जोड़ें जिनका वह वास्तव में उपयोग करती है।

## स्थानीय web stack का मानचित्र बनाएँ

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Virtual-host names, document roots, proxy routes, upload directories, PHP execution settings और credentials वाली config files की जाँच करें। Loopback listener किसी proxy या SSH tunnel के ज़रिए पहुँच योग्य हो सकता है। किसी local listener पर named virtual host जाँचने के लिए, इच्छित `Host` header भेजें या सही address और port के साथ `curl --resolve` का उपयोग करें। Virtual-host enumeration से ऐसे नाम भी सामने आ सकते हैं जो default response में मौजूद नहीं होते। Writable upload directory को code execution मानने से पहले जाँचें कि Apache `.htaccess` overrides की अनुमति देता है या नहीं और upload paths में PHP execute हो सकता है या नहीं। Deployed JavaScript source map से source paths या client-side secrets उजागर हो सकते हैं; मिले हुए values को सुराग मानें और उनके वास्तविक privileges verify करें। Web-specific जाँचों के लिए [Apache](../../network-services-pentesting/pentesting-web/apache.md) और [Nginx](../../network-services-pentesting/pentesting-web/nginx.md) देखें।

`[mpm-itk](https://mpm-itk.sesse.net/)` वाले Apache में, सक्रिय `AssignUserID` किसी virtual host को अलग user और group के तहत चला सकता है। अगर कम privileged account उस host के `DocumentRoot` में script लिख सकता है, तो जाँचें कि कोई पहुँच योग्य route वास्तव में उसे assigned identity के तहत execute करता है या नहीं। Confirm करें कि module loaded है, प्रभावी virtual-host configuration (expression-based identity overrides सहित), directory की write और search permissions, script handler और listener access सही हैं। केवल highlighted directive या writable directory से cross-user execution साबित नहीं होता।

Web server के ज़रिए प्रकाशित home directory, SSH identity files के backup archives उजागर कर सकती है, भले ही live `.ssh` directory private हो। उदाहरण के लिए, [Nostromo की `homedirs_public` setting](https://www.nazgul.ch/dev/nostromo_man.html) यह चुनती है कि user homes से कौन-सी subdirectory serve होगी। केवल path वाला archive hit एक सुराग है: server की प्रभावी mapping, local readability या HTTP authorization, archive contents, private-key passphrase और यह verify करें कि संबंधित account उस key को स्वीकार करता है या नहीं। Routine host enumeration के दौरान archives extract न करें और key material print न करें।

किसी अधिक privileged local web app का readable backup authentication और file-read logic उजागर कर सकता है, भले ही उसका live source inaccessible हो। इस पर निर्भर होने से पहले backup की तुलना deployed service से करें। खास तौर पर, अगर app deterministic ECB blocks का उपयोग करती है, चुने गए text के लिए fresh cookies लौटाती है और बाद में decrypted value को unescaped delimiter पर split करती है, तो caller-controlled text के बाद secret और role flag encrypt करके बनाई गई cookie की जाँच होनी चाहिए। [NIST ECB की independent, repeatable block mapping की व्याख्या करता है](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); यह गुण chosen-input comparison में मदद कर सकता है, लेकिन अपने आप में higher role नहीं देता। Live route, session prerequisites, exact parser/data flow, service identity और अलग privileged action या file-read path की पुष्टि करें। Passive inventory में archive contents पढ़े या authentication probes भेजे बिना backup metadata और listener ownership report करें।

Source-review का यही तरीका किसी privileged **non-HTTP** loopback service, जैसे custom SSH-backed interface, पर भी लागू होता है। अगर accessible source backup में ऐसा command दिखे जो caller द्वारा चुना गया file path स्वीकार करता है, तो उसका authentication gate, path resolve करने का तरीका और file खोलने से पहले यह साबित करने की जाँच करें कि resolved file इच्छित directory के भीतर ही रहता है। Go में, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) path को साफ करता है, लेकिन containment लागू नहीं करता। Confirm करें कि backup running build से मेल खाता है, listener पहुँच योग्य है, कम privileged account command का उपयोग कर सकता है और process target को पढ़ सकता है; readable SSH key होना अलग login-policy का प्रश्न है। Archive contents या keys extract किए बिना, source archive paths और service ownership report करें।

TCP loopback पर सुनने वाले PHP-FPM pool तक कोई दूसरा local account पहुँच सकता है, भले ही उसकी website पर authentication हो। [PHP चेतावनी देता है कि FastCGI से जुड़ सकने वाला client `auto_prepend_file` सहित request settings नियंत्रित कर सकता है](https://www.php.net/manual/en/install.fpm.php)। Pool की `listen` और `listen.allowed_clients` settings को live listener, worker UID, किसी मौजूदा script path और `security.limit_extensions` या `php_admin_value` restrictions के साथ जाँचें। Pool configuration files में `env[...]` directives के तहत credentials हो सकते हैं, इसलिए automated inventory में contents के बजाय उनके paths report करें। केवल config file या port से cross-user execution route साबित नहीं होता; protocol details के लिए [FastCGI guide](../../network-services-pentesting/9000-pentesting-fastcgi.md) देखें।

किसी privileged local API के लिए, code execution के साथ authorization भी trace करें। कम privileged account जिस database role को बदल सकता है, वह API route खोल सकता है, लेकिन अगली boundary route के implementation पर निर्भर करती है। उदाहरण के लिए, request JSON को JavaScript object में merge करके [`child_process.exec`](https://nodejs.org/api/child_process.html) call करना, [prototype-pollution-to-execution dataflow](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md) की जाँच का कारण है। वास्तविक merge library/version, input validation, पहुँच योग्य route, process identity और child-process options verify करें; root-owned Node listener या किसी vulnerable dependency का नाम अपने आप में केवल एक सुराग है।

File-backed CMS stores में administrator password verifiers, सामान्य `.php` configuration files के बाहर भी हो सकते हैं। उदाहरणों में site की `data/database.js` या `data/settings/pass.php` शामिल हैं। Manual review से पहले file ownership और readability जाँचें, और hashes को automated shared output में न रखें। Recover किया जा सकने वाला application password, Unix account से अलग privilege boundary है: password reuse के किसी भी दावे को उस specific account और अनुमत authentication method के विरुद्ध verify करें।

किसी application के authentication controller में configuration file के बजाय source code में literal login password भी हो सकता है। अगर कम privileged user deployed controller पढ़ सकता है, तो उसकी authentication comparison स्थानीय रूप से जाँचें और किसी भी value को shared enumeration output में न रखें। यह दावा करने से पहले confirm करें कि code path सक्रिय है, password application के लिए valid है और कोई अलग higher-privileged Unix account वास्तव में वही password स्वीकार करता है। केवल controller filename जाँच का सुराग है।

Dolibarr database connection settings, जिनमें `dolibarr_main_db_pass` भी शामिल है, `htdocs/conf/conf.php` में रखता है ([configuration reference](https://wiki.dolibarr.org/index.php/Configuration_file))। Readable file credentials का सुराग है; केवल अलग से verified account-password reuse या कोई अन्य database permission ही इसे local privilege escalation बना सकती है। पहले permissions जाँचें और automated output में value print करने से बचें।

GitLab की Linux package configuration आम तौर पर `/etc/gitlab/gitlab.rb` होती है, जबकि deployments में इसकी readable copies अन्य जगह भी हो सकती हैं। [GitLab के documentation के अनुसार](https://docs.gitlab.com/omnibus/settings/smtp/), इस file में `gitlab_rails['smtp_password']` हो सकता है, हालाँकि encrypted SMTP settings में password plaintext file के बाहर रखा जा सकता है। Readable configuration को credentials का सुराग मानें: password reuse का दावा करने से पहले verify करें कि यह सक्रिय है, credential मौजूदा है और कोई specific higher-privileged account इसे स्वीकार करता है। अलग से, [GitLab `gitlab-ctl reconfigure` के दौरान root के तहत `gitlab.rb` को Ruby code के रूप में चलाता है](https://docs.gitlab.com/omnibus/settings/configuration/); writable active file या included `from_file` को execution finding मानने से पहले वास्तविक privileged reconfigure path होना चाहिए। Config preview credential values उजागर कर सकता है, इसलिए उसके output को sensitive मानें और इसके बजाय paths और permissions साझा करें।

Self-hosted Mattermost installation में `SqlSettings.DataSource` `/opt/mattermost/config/config.json` में हो सकता है; [Mattermost के documentation में](https://docs.mattermost.com/deployment-guide/server/troubleshooting) यह usual path और वे deployments, दोनों बताए गए हैं जिनमें active configuration database में रखी जाती है। Readable file application database credential उजागर कर सकती है, लेकिन इससे database access या Unix root access साबित नहीं होता। Active configuration source, database role के वास्तविक rights, अलग से recover किए गए किसी application password और यह verify करें कि वह password किसी specific higher-privileged Unix account के लिए काम करता है या नहीं। Mattermost versions के अनुसार password-hash format बदल सकता है; enumeration के दौरान connection string print किए या database query किए बिना config path और access metadata दर्ज करें।

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

वर्चुअल-होस्ट परिणामों को डिफ़ॉल्ट response size या किसी अन्य स्थिर baseline से मिलाकर फ़िल्टर करें, ताकि हर अनुमानित नाम वैध न दिखे। Source map तभी उपयोगी है, जब वह वास्तव में deployed हो या किसी अन्य तरीके से पढ़ने योग्य हो।

Reverse proxy यह बदल सकते हैं कि application किन client headers पर भरोसा करता है। यह मानने से पहले कि `X-Forwarded-For`, `X-Forwarded-Host` या इसी तरह के headers caller की पहचान तय करते हैं, direct और proxied requests की तुलना करें। Proxy और application configuration की एक साथ समीक्षा करें।

यदि PHP `$_SERVER['HTTP_X_FORWARDED_FOR']` को [`system()`](https://www.php.net/manual/en/function.system.php) को दी गई string में कॉपी करता है, तो जाँचें कि reachable request path caller को header देने देता है या नहीं और shell metacharacters उस string तक बिना बदलाव के पहुँचते हैं या नहीं। शुरुआत में एम्बेड किया गया `sudo iptables` जैसा command बाद में shell से अलग किए गए commands को root के रूप में नहीं चलाता; अलग से प्रभावी sudo rule द्वारा escalation की अनुमति न हो, तो वे web worker के रूप में चलते हैं। Root path का दावा करने से पहले worker की पहचान, सटीक `sudo -l` grant और authentication की ज़रूरत, तथा command की argument boundary की पुष्टि करें। नियमित host enumeration के दौरान injection probe भेजे बिना source और policy की जाँच करें।

## Access logs में login credentials

यदि application `GET` के साथ login form submit करता है, तो username और password request URI में query parameters बन सकते हैं। `POST` request में भी query string हो सकती है; `POST` इस्तेमाल करने से URI में गलती से रखी गई secret छिपती नहीं है—इसमें किसी असंबंधित form field में दर्ज password भी शामिल है। [Apache की सामान्य access-log request line](https://httpd.apache.org/docs/2.4/logs.html), configured format में `%r` होने पर, method और query string सहित URI रिकॉर्ड करती है। इसलिए, कुछ Linux systems पर `adm` group के ज़रिए, उन logs को पढ़ने की अनुमति वाला account credential से जुड़ा सुराग पा सकता है। वास्तविक log format और permissions जाँचें, फिर पुष्टि करें कि value secret है, account उसे स्वीकार करता है और उससे privilege boundary पार होती है। यह न मानें कि request body log की गई थी और संभावित values को shared output में कॉपी न करें।

केवल पढ़ने योग्य access logs की जाँच करें और credential values को shared command output से बाहर रखें। लंबी request lines में referrer और user agent भी हो सकते हैं, इसलिए short-line filter से वही request छूट सकती है जिसमें आपकी दिलचस्पी है। Apache, httpd और Nginx access logs के सामान्य स्थान `/var/log/apache2/access.log`, `/var/log/httpd/access_log` और `/var/log/nginx/access.log` हैं। Rotated logs में पुराने credentials हो सकते हैं। [LFI के ज़रिए log-file access](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) इसी data तक पहुँचने का एक संबंधित रास्ता है।

Application authentication logs में कभी-कभी असफल login के दौरान **username** field में गलती से दर्ज किया गया password भी सामने आ सकता है। पहले पुष्टि करें कि log पढ़ने योग्य है और उसका format submitted username रिकॉर्ड करता है; स्थानीय रूप से केवल छोटा, प्रासंगिक हिस्सा देखें और संभावित credentials को shared output में कॉपी न करें। Password जैसा दिखने वाला username एक सुराग है, वैध password या अधिक privilege का प्रमाण नहीं। किसी बदलाव का दावा करने से पहले इच्छित account और उसी service या Unix account पर password reuse की पुष्टि करें।

जब किसी अन्य identity के अंतर्गत scheduled client उस endpoint पर credentials submit करता हो, तो writable web login handler की अलग से समीक्षा करें। **Active** handler पर write access, client का वास्तविक schedule और request path, वह किसके credentials भेजता है, और क्या वह application password किसी अधिक privileged operating-system account के लिए स्वतंत्र रूप से वैध है—इन सबकी पुष्टि करें। केवल writable page या बार-बार चलने वाला process उस बदलाव को साबित नहीं करता। Passive inventory में handler बदले या passwords एकत्र किए बिना path permissions और job metadata दर्ज करें।

FTP event logging सक्षम होने पर Suricata के EVE JSON logs, `command_data` सहित FTP `USER` और `PASS` commands भी रिकॉर्ड कर सकते हैं। छोटा प्रासंगिक हिस्सा स्थानीय रूप से देखने से पहले `/var/log/suricata/eve*.json*` की readability जाँचें; इसमें rotated या compressed files भी शामिल हैं। पढ़ने योग्य EVE file केवल एक सुराग है: पुष्टि करें कि FTP events log किए गए थे, data में उपयोगी credential है और उससे privilege boundary पार होती है। Shared enumeration output में `command_data` दिखाने से बचें। Suricata [FTP event fields](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) और [EVE rotation तथा filename variants](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html) का दस्तावेज़ देता है।

## Generated Apache configuration और piped logs

[remco](https://github.com/HeavyHorst/remco) key/value backend को watch कर सकता है, template को Apache configuration file में render कर सकता है और reload command चला सकता है। चल रहे remco process की identity, configured template source और destination, watch किए गए key prefixes, और यह जाँचें कि backend value सीधे `ServerName` जैसे Apache directive में डाली जाती है या नहीं। केवल local backend listener होने से यह साबित नहीं होता कि मौजूदा user किसी watched key में लिख सकता है; escalation का दावा करने से पहले backend authentication और permissions की पुष्टि करें।

Writable backend value में unescaped newline से एक intended directive value कई अतिरिक्त Apache directives में बदल सकती है। [Apache piped logs](https://httpd.apache.org/docs/2.4/logs.html#piped) विशेष रूप से संवेदनशील हैं: `|` command वाला `CustomLog` या `ErrorLog`, parent httpd identity के तहत—अक्सर root के रूप में—एक helper शुरू करता है; `|$` होने पर Apache shell का उपयोग करता है। Enumeration के दौरान backend data बदले या service restart किए बिना generated configuration और उसके reload path की समीक्षा करें। Piped command को निजी रखें, क्योंकि उसके arguments में secrets हो सकते हैं।

## Authentication और service identities

Monit की control file आमतौर पर `~/.monitrc` या `/etc/monitrc` होती है, लेकिन `monit -c` किसी अन्य path को चुन सकता है। पढ़ने योग्य file में उसके web interface के लिए `set httpd` और `allow user:password` entries हो सकती हैं, जो अक्सर local port 2812 पर उपलब्ध होता है। इसकी समीक्षा करने से पहले file के owner और permissions जाँचें, और password values को shared enumeration output से बाहर रखें। Web credentials केवल configured Monit role देते हैं; read-only users control actions नहीं चला सकते। अलग Unix-account escalation के लिए password reuse की पुष्टि या ऐसा privileged Monit action ज़रूरी है जिसे authenticated role वास्तव में चला सके। [Monit control-file और authentication documentation](https://www.mmonit.com/monit/documentation/monit.html) देखें।

Webmin के लिए `/etc/webmin/miniserv.conf` में server settings होती हैं और `/etc/webmin/webmin.acl` में दर्ज होता है कि users किन modules तक पहुँच सकते हैं; [Webmin module-grant boundary का दस्तावेज़ देता है](https://webmin.com/docs/development/creating-modules/)। Unix password या पढ़ने योग्य ACL file अपने-आप Webmin session नहीं देता। वास्तविक authentication mapping, reachable listener, authenticated account, प्रभावी Package Updates module permission, installed code या vendor fix, और Webmin process identity की पुष्टि करें। प्रभावित builds में 1.910 तक, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) के कारण उस module permission वाला account अपने update handler के ज़रिए commands चला सकता था। Passive enumeration के दौरान credentials दिखाए या update आज़माए बिना configuration paths और permissions दर्ज करें।

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) service-specific authentication को नियंत्रित करता है; writable policy या module paths login behavior बदल सकते हैं।
- LDAP/SSSD configuration से directory endpoints, bind identities और access rules का पता चल सकता है। मिला हुआ bind password मौजूदा OS account से आगे LDAP queries की अनुमति दे सकता है; सटीक bind identity और directory ACLs जाँचें। Secrets की जाँच से पहले file permissions देखें; [Linux Active Directory](../user-information/linux-active-directory.md) और [FreeIPA](freeipa-pentesting.md) में ticket और directory के उपयोग का विवरण है।
- Postfix aliases प्राप्त mail को local commands तक pipe कर सकते हैं। यदि कम-विशेषाधिकार वाला user संदर्भित script बदल सकता है, तो mail delivery उसके code को delivery identity के तहत चला सकती है। इस path का दावा करने से पहले alias maps और script ownership जाँचें; देखें [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md)।
- Jenkins और अन्य CI services jobs को किसी शक्तिशाली local account के तहत चला सकती हैं। Pipeline या plugin की जाँच से पहले service user, writable job/workspace paths और local administration interface देखें। **किसी job के लिए उपलब्ध credentials** और वह account भी जाँचें जिसके रूप में वे authenticate कर सकते हैं: [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) का उपयोग करने वाला Pipeline किसी host तक SSH credential के user के रूप में पहुँच सकता है, भले ही Jenkins खुद कम विशेषाधिकार वाले Unix account के तहत चलता हो। Host privilege escalation का दावा करने से पहले पुष्टि करें कि मौजूदा Jenkins identity के पास Pipeline बदलने के लिए `Job/Create`, `Job/Configure` या कोई अन्य प्रभावी रास्ता है, credential उस job के scope में है, और target SSH account key स्वीकार करता है। केवल credential का display name या ID इनमें से किसी भी शर्त को साबित नहीं करता। Jenkins चेतावनी देता है कि job बनाने वाले और अक्सर job configure करने वाले, अपने scope में उपलब्ध credentials का मनमाने ढंग से उपयोग कर सकते हैं; इसलिए [credential scope](https://www.jenkins.io/doc/book/security/credentials/) और [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) service UID जितने ही महत्वपूर्ण हैं। Shared enumeration output में credential values और private keys शामिल न करें।

## Gogs repository file writes

Local Gogs service के लिए, `gogs web` process के owner का executable version और `custom/conf/app.ini` से मिलान करें। Configuration से service identity, repository root, listener address और registration बंद है या नहीं—यह पता चल सकता है। केवल loopback पर सुनने वाला listener भी local users के लिए reachable होता है। 0.13.3 तक के Gogs versions में authenticated `PutContents` symlink file-write issue ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)) मौजूद है: repository writer एक symlink commit कर सकता है और फिर API write को उसके माध्यम से निर्देशित कर सकता है। परिणामी file access को Gogs process के privileges मिलते हैं, इसलिए root-owned instance पर तुरंत ध्यान देना ज़रूरी है। उपयोगी path का दावा करने से पहले deployed fix और authentication requirements की पुष्टि करें; API error यह साबित नहीं करता कि file write विफल हुआ।

## Gitea repository-description XSS and privileged viewers

Gitea 1.22.0 में repository description में stored JavaScript की अनुमति थी ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); 1.22.1 में इसे ठीक किया गया। Description संपादित कर सकने वाला user किसी अधिक विशेषाधिकार वाले browser session को प्रभावित कर सकता है, यदि वह user repository देखता है और malicious link सक्रिय करता है। इसके बाद वह browser identity निजी repository content या अन्य application data उजागर कर सकती है। एक अलग local escalation के लिए उस content के माध्यम से उपलब्ध credential या permission आवश्यक है, जैसे दोबारा इस्तेमाल किया गया administrator password; केवल Gitea process owner होना root impact साबित नहीं करता। इस chain का दावा करने से पहले deployed version, description-edit access, viewer workflow और वास्तविक browser interaction जाँचें।

## Cobbler provisioning API

Cobbler की management service XML-RPC API उपलब्ध कराती है, जो आम तौर पर port `25151` पर होती है। इसके impact का आकलन करने से पहले listener और `cobblerd` process owner जाँचें; केवल loopback पर उपलब्ध API तक भी host का user पहुँच सकता है। `/etc/cobbler/modules.conf` में authentication और authorization modules, `/etc/cobbler/settings` या `/etc/cobbler/settings.yaml` में service settings, और `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` तथा `/var/lib/cobbler/web.ss` की permissions देखें। Digest और shared-secret files में credential material होता है, इसलिए default रूप से उनकी सामग्री दिखाए बिना केवल उनकी readability दर्ज करें।

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** Cobbler 3.0.0 से 3.2.2 और 3.3.0 से 3.3.6 तक के संस्करणों में XML-RPC authentication bypass है। Shared-secret read error से अनुमान लगाया जा सकने वाला मान `-1` लौटता था, जिसे API ने password के रूप में स्वीकार कर लिया। इसके fixes 3.2.3 और 3.3.7 में हैं। Package version केवल एक सुराग है; exposure की रिपोर्ट करने से पहले deployed code और backported fix की पुष्टि करें।

जब `cobblerd` root के रूप में चलता है, तब authenticated API session से privileged execution path मिल सकता है। प्रभावित implementations में, `background_import` user-controlled `rsync_flags` को shell command में पास करता है, और user-controlled Cheetah autoinstall template को render करने पर Python evaluate हो सकता है। इनमें से किसी भी path को test करने से पहले API permissions और installed version जांचें। Management API तक पहुंच सीमित करें, authentication bypass को patch करें, और configuration तथा credential files को केवल service administrators के लिए readable रखें।

## Motion और motionEye configuration

`conf_path` के लिए `/etc/motioneye/motioneye.conf` देखें, फिर उस directory में `motion.conf` और कुछ `camera-*.conf` files की जांच करें। यह बताए बिना रिपोर्ट करें कि readable `# @admin_password` hash मौजूद है या नहीं; hash को प्रिंट न करें। [motionEye के पुराने releases में ये files व्यापक read permissions के साथ लिखी जाती थीं](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); इसका fix 0.44.0 में है। Motion की `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method`, और `webcontrol_localhost` settings को एक साथ जांचें: authentication disabled होने पर advanced control (`2` या `3`) किसी local user को शक्तिशाली operations करने दे सकता है, loopback listener पर भी। [Motion में values और defaults दर्ज हैं](https://motion-project.github.io/motion_config.html)।

0.43.1b5 से पुराने motionEye पर admin session से camera filename setting को command execution में बदला जा सकता था, जब Motion उसे process करता था ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx))। Escalation का दावा करने से पहले running version, service identity, उपलब्ध authentication path, और camera configured है या नहीं, इसकी पुष्टि करें। केवल configuration से यह साबित नहीं होता कि service चल रही है या privileged है।

Service name या installed package केवल एक सुराग है। Privilege boundary, reachable input, process identity, writable configuration, और अंततः उसके नियंत्रण में आने वाले command या file के संयोजन से तय होती है।

## Local AWS emulators और stored credentials

Host user, container में चल रहे AWS-compatible emulator तक उसके published loopback endpoint से पहुंच सकता है। [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) या [KMS](https://docs.localstack.cloud/aws/services/kms/) तक पहुंच का आकलन करने से पहले live listener, client द्वारा चुने गए endpoint और account, तथा emulator की installed authorization settings का मिलान करें। LocalStack में, [IAM policy enforcement एक अलग setting है](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); केवल credential file, IAM policy, या listener के आधार पर प्रभावी API permissions का अनुमान न लगाएं। Installed release और configuration का व्यवहार सत्यापित करें।

Stored secret, local escalation के लिए तभी उपयोगी है जब मौजूदा API identity उसे retrieve कर सकती हो और कोई अलग, अधिक privileged account प्राप्त credential को स्वीकार करता हो। Encrypted local blob के लिए file read access, matching और usable KMS key तथा algorithm, और प्रभावी decrypt access भी चाहिए। [Asymmetric KMS key](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) के लिए, decrypt request में blob को encrypt करने के लिए इस्तेमाल किया गया algorithm निर्दिष्ट होना चाहिए। Host की automatic inventory को process, listener, configuration-path, और file-permission के साक्ष्य तक सीमित रखें; routine enumeration के दौरान secret values या decrypted plaintext न मांगें और न प्रिंट करें।
