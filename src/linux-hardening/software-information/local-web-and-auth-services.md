# स्थानीय Web और Authentication Services

{{#include ../../banners/hacktricks-training.md}}

Linux shell, web और authentication services का host-side view देता है: process arguments, listeners, unit files, configuration, logs और केवल स्थानीय interfaces। इस view का उपयोग किसी reachable service को उस account और files से जोड़ने के लिए करें जिनका वह वास्तव में उपयोग करती है।

## स्थानीय Web stack का मानचित्र बनाएँ

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Virtual-host names, document roots, proxy routes, upload directories, PHP execution settings और credentials वाली config files की जाँच करें। Loopback listener किसी proxy या SSH tunnel के माध्यम से पहुँच योग्य हो सकता है। किसी named virtual host को local listener के विरुद्ध जाँचने के लिए इच्छित `Host` header भेजें या सही address और port के साथ `curl --resolve` का उपयोग करें। Virtual-host enumeration से ऐसे names भी सामने आ सकते हैं जो default response में मौजूद नहीं होते। यह जाँचें कि Apache `.htaccess` overrides की अनुमति देता है या नहीं, और writable upload directory को code execution मानने से पहले सुनिश्चित करें कि upload paths में PHP execute हो सकता है या नहीं। Deployed JavaScript source map से source paths या client-side secrets उजागर हो सकते हैं; प्राप्त values को सुराग मानें और उनके वास्तविक privileges सत्यापित करें। Web-विशिष्ट जाँचों के लिए [Apache](../../network-services-pentesting/pentesting-web/apache.md) और [Nginx](../../network-services-pentesting/pentesting-web/nginx.md) देखें।

[mpm-itk](https://mpm-itk.sesse.net/) वाले Apache में, सक्रिय `AssignUserID` किसी virtual host को अलग user और group के अंतर्गत चला सकता है। यदि कम-privileged account उस host के `DocumentRoot` में script लिख सकता है, तो जाँचें कि कोई पहुँच योग्य route वास्तव में उसे assigned identity के अंतर्गत execute करता है या नहीं। पुष्टि करें कि module loaded है, प्रभावी virtual-host configuration (expression-आधारित identity overrides सहित) क्या है, directory में write और search permissions हैं या नहीं, script handler क्या है, और listener तक पहुँच संभव है या नहीं। केवल highlighted directive या writable directory, cross-user execution का प्रमाण नहीं है।

Web server के माध्यम से प्रकाशित home directory में SSH identity files के backup archives उजागर हो सकते हैं, भले ही live `.ssh` directory private हो। उदाहरण के लिए, [Nostromo की `homedirs_public` setting](https://www.nazgul.ch/dev/nostromo_man.html) user homes से serve की जाने वाली subdirectory चुनती है। केवल path के आधार पर archive मिलने को सुराग मानें: server की प्रभावी mapping, local readability या HTTP authorization, archive contents, private-key passphrase, और संबंधित account वास्तव में उस key को स्वीकार करता है या नहीं—इनकी पुष्टि करें। Routine host enumeration के दौरान archives extract न करें और key material print न करें।

अधिक-privileged local web app का readable backup, authentication और file-read logic उजागर कर सकता है, भले ही उसका live source inaccessible हो। इस पर निर्भर होने से पहले backup की deployed service से तुलना करें। विशेष रूप से, caller-controlled text के बाद secret और role flag जोड़कर cookie encrypt करना जाँच के योग्य है, यदि app deterministic ECB blocks का उपयोग करता है, चुने गए text के लिए नए cookies लौटाता है, और बाद में decrypted value को unescaped delimiter पर split करता है। [NIST बताता है कि ECB में blocks की mapping स्वतंत्र और दोहराने योग्य होती है](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); यह गुण चुने गए input की तुलना में सहायक हो सकता है, लेकिन अपने आप में अधिक ऊँचा role नहीं देता। Live route, session prerequisites, सटीक parser/data flow, service identity, और अलग privileged action या file-read path की पुष्टि करें। Passive inventory में archive contents पढ़े बिना या authentication probes भेजे बिना backup metadata और listener ownership की जानकारी दें।

Source review का यही तरीका किसी privileged **non-HTTP** loopback service पर भी लागू होता है, जैसे custom SSH-backed interface। यदि उपलब्ध source backup में ऐसा command दिखता है जो caller द्वारा चुना गया file path स्वीकार करता है, तो उसका authentication gate, path resolve करने का तरीका, और file खोलने से पहले यह सुनिश्चित करने का तरीका जाँचें कि resolved file इच्छित directory के भीतर ही रहे। Go में, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) path को साफ़ करता है, लेकिन उसके directory के भीतर रहने की सीमा लागू नहीं करता। पुष्टि करें कि backup running build से मेल खाता है, listener पहुँच योग्य है, कम-privileged account command का उपयोग कर सकता है, और process target को पढ़ सकता है; readable SSH key का होना अलग login-policy प्रश्न है। Automated output में archive contents या keys extract किए बिना source archive paths और service ownership की जानकारी दें।

TCP loopback पर सुनने वाले PHP-FPM pool तक कोई दूसरा local account पहुँच सकता है, भले ही उसकी website में authentication हो। [PHP चेतावनी देता है कि FastCGI से connect कर सकने वाला client `auto_prepend_file` सहित request settings को नियंत्रित कर सकता है](https://www.php.net/manual/en/install.fpm.php)। Pool की `listen` और `listen.allowed_clients` settings की जाँच live listener, worker UID, मौजूदा script path, और किसी भी `security.limit_extensions` या `php_admin_value` restrictions के साथ करें। Pool configuration files में `env[...]` directives के तहत credentials हो सकते हैं, इसलिए automated inventory में contents के बजाय उनके paths की जानकारी दें। केवल config file या port, cross-user execution route का प्रमाण नहीं है; protocol की जानकारी के लिए [FastCGI guide](../../network-services-pentesting/9000-pentesting-fastcgi.md) देखें।

किसी privileged local API के लिए code execution के साथ authorization की भी पड़ताल करें। यदि कम-privileged account database role बदल सकता है, तो इससे API route खुल सकता है, लेकिन अगली सीमा उस route के implementation पर निर्भर करती है। उदाहरण के लिए, request JSON को JavaScript object में merge करने और फिर [`child_process.exec`](https://nodejs.org/api/child_process.html) call करने की स्थिति में [prototype-pollution-to-execution dataflow](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md) की जाँच आवश्यक है। वास्तविक merge library/version, input validation, पहुँच योग्य route, process identity, और child-process options सत्यापित करें; केवल root-owned Node listener या vulnerable dependency का नाम एक सुराग है।

File-backed CMS stores में administrator password verifiers, सामान्य `.php` configuration files के बाहर भी हो सकते हैं। उदाहरणों में site का `data/database.js` या `data/settings/pass.php` शामिल हैं। Manual review से पहले file ownership और readability जाँचें, और hashes को automated shared output में न रखें। Recover किया जा सकने वाला application password, Unix account से अलग privilege boundary है: password reuse के किसी भी दावे को संबंधित account और अनुमत authentication method के विरुद्ध सत्यापित करें।

किसी application के authentication controller में configuration file के बजाय source code में literal login password भी हो सकता है। यदि कम-privileged user deployed controller पढ़ सकता है, तो उसके authentication comparison की स्थानीय रूप से समीक्षा करें और किसी भी value को shared enumeration output से बाहर रखें। दावा करने से पहले पुष्टि करें कि code path सक्रिय है, password application के लिए मान्य है, और कोई अलग अधिक-privileged Unix account वही password स्वीकार करता है। केवल controller filename, समीक्षा का एक सुराग है।

Dolibarr database connection settings, जिनमें `dolibarr_main_db_pass` भी शामिल है, `htdocs/conf/conf.php` में रखता है ([configuration reference](https://wiki.dolibarr.org/index.php/Configuration_file))। Readable file में credential का सुराग हो सकता है; केवल अलग से सत्यापित account-password reuse या कोई अन्य database permission ही इसे local privilege escalation में बदल सकती है। पहले permissions जाँचें और automated output में value print करने से बचें।

GitLab Linux package की configuration सामान्यतः `/etc/gitlab/gitlab.rb` होती है, जबकि deployments में इसकी readable copies कहीं और भी हो सकती हैं। [GitLab के दस्तावेज़](https://docs.gitlab.com/omnibus/settings/smtp/) बताते हैं कि इस file में `gitlab_rails['smtp_password']` हो सकता है, हालाँकि encrypted SMTP settings में password plaintext file के बाहर रखा जा सकता है। Readable configuration को credential का सुराग मानें: password reuse का दावा करने से पहले सत्यापित करें कि यह सक्रिय है, credential वर्तमान है, और कोई विशिष्ट अधिक-privileged account इसे स्वीकार करता है। इसके अलावा, [GitLab `gitlab-ctl reconfigure` के दौरान root के अंतर्गत `gitlab.rb` को Ruby code के रूप में चलाता है](https://docs.gitlab.com/omnibus/settings/configuration/); writable active file या शामिल `from_file` तभी execution finding है, जब वास्तव में privileged reconfigure path मौजूद हो। Config preview से credential values उजागर हो सकती हैं, इसलिए इसके output को sensitive मानें और इसके बजाय paths और permissions साझा करें।

Self-hosted Mattermost installation में `SqlSettings.DataSource` `/opt/mattermost/config/config.json` में हो सकता है; [Mattermost इस सामान्य path और उन deployments, दोनों का दस्तावेज़ देता है](https://docs.mattermost.com/deployment-guide/server/troubleshooting), जिनमें सक्रिय configuration किसी database में रखी जाती है। Readable file से application database credential उजागर हो सकता है, लेकिन इससे database access या Unix root access सिद्ध नहीं होता। सक्रिय configuration source, database role के वास्तविक rights, अलग से प्राप्त किसी application password, और उस password को किसी विशिष्ट अधिक-privileged Unix account पर काम करने की पुष्टि करें। Mattermost versions के बीच password-hash format बदल सकता है; enumeration के दौरान connection string या database query print किए बिना config path और access metadata दर्ज करें।

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

वर्चुअल-होस्ट के परिणामों को डिफ़ॉल्ट response size या किसी अन्य स्थिर baseline से मिलाकर फ़िल्टर करें, ताकि हर अनुमानित नाम वैध न लगे। Source map तभी उपयोगी है, जब वह वास्तव में deployed हो या किसी अन्य तरीके से पढ़ा जा सके।

Reverse proxy यह बदल सकते हैं कि application किन client headers पर भरोसा करती है। यह मानने से पहले कि `X-Forwarded-For`, `X-Forwarded-Host` या ऐसे ही headers caller की पहचान स्थापित करते हैं, direct और proxied requests की तुलना करें। Proxy और application configuration की एक साथ समीक्षा करें।

यदि PHP `$_SERVER['HTTP_X_FORWARDED_FOR']` को [`system()`](https://www.php.net/manual/en/function.system.php) में पास की गई string में कॉपी करता है, तो जाँचें कि reachable request path caller-supplied header की अनुमति देता है या नहीं और shell metacharacters उस string तक बिना बदलाव के पहुँचते हैं या नहीं। शुरुआत में `sudo iptables` जैसी command embedded होने से बाद की shell-separated commands root के रूप में नहीं चलतीं; वे web worker के रूप में चलती हैं, जब तक कि कोई अलग प्रभावी sudo rule privilege escalation की अनुमति न दे। Root path का दावा करने से पहले worker की identity, सटीक `sudo -l` grant और authentication की आवश्यकता, और command की argument boundary की पुष्टि करें। Routine host enumeration के दौरान injection probe भेजे बिना source और policy की जाँच करें।

## वेब foothold के बाद privileged loopback APIs

Web-process shell स्थानीय HTTP services को call कर सकता है, भले ही उनके listeners `127.0.0.1` पर bound हों। रिपोर्ट किए गए vulnerable Control Web Panel build में, account dashboard hosting user के रूप में चलता है, लेकिन `https://127.0.0.1:2302` पर user API root के रूप में चलती है। इसका `/v1/restoredatabase/` POST route access-token check छोड़ देता है और `file` field को `shell_exec('mysql ... < ' . $file)` में पास करता है। इसलिए, hosting-user foothold से, `file` में shell separators root के रूप में execute होते हैं। Route के gate और API process की प्रभावी identity—दोनों की पुष्टि करें; केवल loopback binding authentication नहीं है। यह foothold हासिल करने के एक तरीके के लिए [redirect के बाद PHP execution](../../pentesting-web/login-bypass/#php-execution-after-redirect) देखें। रिपोर्ट की गई खामियाँ CWP 1.29 तक पूरी तरह ठीक कर दी गई थीं।<sup>[[1]](#references)</sup>

```bash
curl -sk 'https://127.0.0.1:2302/v1/restoredatabase/' \
  --data-urlencode 'file=/dev/null ; id > /tmp/root-proof ; echo'
```

उसी API में authentication-gate की एक अलग खामी भी है: `access_token()` दिए गए token को `WHERE authorization_code='$access_token' AND client_id='$user'` में interpolate करता है। अपेक्षित columns और future expiry वाली `UNION` row token check को संतुष्ट कर सकती है और original client-ID condition को comment out कर सकती है। इससे `/v1/newpass/` जैसे protected routes खुल जाते हैं, जहाँ raw `user` को root-owned `passwd` shell command में append किया जाता है। Token injection gate को bypass करता है; command execution फिर भी दूसरे sink पर निर्भर करती है। देखें [SQL injection authentication bypass](../../pentesting-web/login-bypass/#sql-injection-authentication-bypass).<sup>[[1]](#references)</sup>

बताए गए six-column gate के लिए, injected token future expiry दे सकता है और बाकी predicate को दबा सकता है; columns का यह आकार उसी build के लिए विशिष्ट है।<sup>[[1]](#references)</sup>

```sql
' UNION SELECT 'a','x','c','d','2099-01-01 00:00:00','f' -- -
```

एक अलग tokenless `/v1/user_panel_dashboard/` route, `user` को `oauth_clients` lookup में interpolate करता है। यह API के MySQL-root connection के ज़रिए blind database read है, **root OS execution नहीं**: MySQL server `mysql` OS user के रूप में चलता है। जब queried table खाली हो, तो [constant derived-table timing probe](../../pentesting-web/sql-injection/#exploiting-time-based-sqli) missing rows के कारण delay खोने से बचाता है।<sup>[[1]](#references)</sup>

## Access logs में login credentials

अगर कोई application `GET` के साथ login form submit करती है, तो username और password request URI में query parameters बन सकते हैं। `POST` request में भी query string हो सकती है; `POST` का इस्तेमाल करने से URI में गलती से रखा गया secret छिपता नहीं है, जिसमें किसी असंबंधित form field में दर्ज किया गया password भी शामिल है। [Apache की सामान्य access-log request line](https://httpd.apache.org/docs/2.4/logs.html) configured format में `%r` होने पर method और URI, जिसमें query string भी शामिल है, रिकॉर्ड करती है। इसलिए जिन accounts को वे logs पढ़ने की अनुमति है, उदाहरण के लिए कुछ Linux systems में `adm` group के ज़रिए, उन्हें credentials से जुड़ा कोई सुराग मिल सकता है। असल log format और permissions जाँचें, फिर सत्यापित करें कि value secret है, account उसे स्वीकार करता है और उससे privilege boundary पार होती है। यह न मानें कि request body log हुई थी और candidate values को shared output में कॉपी न करें।

केवल पढ़े जा सकने वाले access logs देखें और credential values को shared command output से बाहर रखें। लंबी request lines में referrer और user agent भी हो सकते हैं, इसलिए short-line filter से रुचि वाली request छूट सकती है। सामान्य Apache, httpd और Nginx access-log paths हैं: `/var/log/apache2/access.log`, `/var/log/httpd/access_log` और `/var/log/nginx/access.log`। Rotated logs में पुराने credentials हो सकते हैं। [LFI के ज़रिए log-file access](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) उसी data तक पहुँचने का एक संबंधित तरीका है।

Application authentication logs में failed login के दौरान **username** field में गलती से दर्ज किया गया password भी सामने आ सकता है। पहले पता करें कि log पढ़ा जा सकता है और उसका format submit किया गया username रिकॉर्ड करता है; केवल स्थानीय तौर पर छोटा, प्रासंगिक हिस्सा देखें और candidate credentials को shared output में कॉपी न करें। Password जैसा दिखने वाला username एक सुराग है, valid password या higher privilege का प्रमाण नहीं। किसी transition का दावा करने से पहले intended account और संबंधित service या Unix account में password reuse की पुष्टि करें।

जब किसी दूसरे identity के अंतर्गत चलने वाला scheduled client उस endpoint पर credentials submit करता हो, तो writable web login handler की अलग से समीक्षा करें। Active handler पर write access, client का वास्तविक schedule और request path, वह किसका credential भेजता है, और क्या application password किसी higher-privileged operating-system account के लिए स्वतंत्र रूप से valid है—इन सबकी पुष्टि करें। केवल writable page या recurring process से ऐसा transition सिद्ध नहीं होता। Passive inventory में handler बदले या passwords इकट्ठा किए बिना path permissions और job metadata दर्ज करें।

FTP event logging enabled होने पर Suricata के EVE JSON logs FTP `USER` और `PASS` commands को उनके `command_data` के साथ भी रिकॉर्ड कर सकते हैं। स्थानीय तौर पर छोटा, प्रासंगिक हिस्सा देखने से पहले `/var/log/suricata/eve*.json*` की readability जाँचें, जिसमें rotated या compressed files भी शामिल हैं। पढ़ी जा सकने वाली EVE file केवल एक सुराग है: पुष्टि करें कि FTP events log हुए थे, data में इस्तेमाल करने योग्य credential है और उससे privilege boundary पार होती है। Shared enumeration output में `command_data` छापने से बचें। Suricata [FTP event fields](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) और [EVE rotation तथा filename variants](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html) का दस्तावेज़ देता है।

## Generated Apache configuration और piped logs

[remco](https://github.com/HeavyHorst/remco) key/value backend को watch कर सकता है, template को Apache configuration file में render कर सकता है और reload command चला सकता है। चल रहे remco process की identity, उसके configured template source और destination, watched key prefixes, और क्या backend value को सीधे किसी Apache directive जैसे `ServerName` में डाला जाता है—इनकी जाँच करें। केवल local backend listener होने से यह सिद्ध नहीं होता कि current user watched key लिख सकता है; escalation का दावा करने से पहले backend authentication और permissions सत्यापित करें।

Writable backend value में unescaped newline, एक intended directive value को कई अतिरिक्त Apache directives में बदल सकता है। [Apache piped logs](https://httpd.apache.org/docs/2.4/logs.html#piped) खास तौर पर संवेदनशील हैं: `|` command वाला `CustomLog` या `ErrorLog`, parent httpd identity—जो अक्सर root होती है—के अंतर्गत helper शुरू करता है; `|$` Apache को shell इस्तेमाल करने के लिए कहता है। Enumeration के दौरान backend data बदले या service restart किए बिना generated configuration और उसके reload path की समीक्षा करें। पूरा piped command निजी रखें, क्योंकि उसके arguments में secrets हो सकते हैं।

## Authentication और service identities

Monit की control file आमतौर पर `~/.monitrc` या `/etc/monitrc` होती है, लेकिन `monit -c` से कोई दूसरा path चुना जा सकता है। पढ़ी जा सकने वाली file में उसके web interface के लिए `set httpd` और `allow user:password` entries हो सकती हैं, जो अक्सर local port 2812 पर होता है। File की समीक्षा से पहले उसका owner और permissions जाँचें, और password values को shared enumeration output से बाहर रखें। Web credentials केवल configured Monit role देते हैं; read-only users control actions नहीं चला सकते। अलग Unix-account escalation के लिए password reuse की पुष्टि या ऐसा privileged Monit action ज़रूरी है जिसे authenticated role वास्तव में trigger कर सके। [Monit control-file और authentication documentation](https://www.mmonit.com/monit/documentation/monit.html) देखें।

Webmin के लिए `/etc/webmin/miniserv.conf` में server settings होती हैं और `/etc/webmin/webmin.acl` में दर्ज होता है कि users किन modules तक पहुँच सकते हैं; [Webmin module-grant boundary का दस्तावेज़ देता है](https://webmin.com/docs/development/creating-modules/)। Unix password या पढ़ी जा सकने वाली ACL file से अपने-आप Webmin session नहीं मिलता। वास्तविक authentication mapping, reachable listener, authenticated account, प्रभावी Package Updates module permission, installed code या vendor fix, और Webmin process identity की पुष्टि करें। 1.910 तक के प्रभावित builds में, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) ने उस module permission वाले account को उसके update handler के ज़रिए commands चलाने की अनुमति दी। Passive enumeration के दौरान credentials छापे या update आज़माए बिना configuration paths और permissions दर्ज करें।

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) service-specific authentication को नियंत्रित करता है; writable policy या module paths login behavior बदल सकते हैं।
- LDAP/SSSD configuration से directory endpoints, bind identities और access rules का पता चल सकता है। मिला हुआ bind password, मौजूदा OS account से आगे की LDAP queries की अनुमति दे सकता है; सटीक bind identity और directory ACLs जाँचें। Secrets देखने से पहले file permissions की समीक्षा करें; [Linux Active Directory](../user-information/linux-active-directory.md) और [FreeIPA](freeipa-pentesting.md) में ticket और directory के उपयोग की जानकारी है।
- Postfix aliases प्राप्त mail को local commands तक pipe कर सकते हैं। यदि कम privileged user संदर्भित script बदल सकता है, तो mail delivery उस user का code delivery identity के अंतर्गत चला सकती है। इस path का दावा करने से पहले alias maps और script ownership की समीक्षा करें; [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md) देखें।
- Jenkins और अन्य CI services jobs को किसी शक्तिशाली local account के अंतर्गत चला सकती हैं। Pipeline या plugin की जाँच से पहले service user, writable job/workspace paths और local administration interface देखें। साथ ही, **किसी job को उपलब्ध credentials** और वे किस account के रूप में authenticate कर सकते हैं, इसकी भी समीक्षा करें: [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) का उपयोग करने वाला Pipeline किसी host पर SSH credential के user के रूप में access कर सकता है, भले ही Jenkins किसी कम privileged Unix account के अंतर्गत चलता हो। Host privilege escalation का दावा करने से पहले पुष्टि करें कि मौजूदा Jenkins identity के पास `Job/Create`, `Job/Configure` या Pipeline बदलने का कोई अन्य प्रभावी रास्ता है, credential उस job के scope में है, और target SSH account उस key को स्वीकार करता है। Credential का display name या ID अकेले इनमें से किसी भी शर्त को साबित नहीं करता। Jenkins चेतावनी देता है कि job बनाने वाले और अक्सर job configure करने वाले लोग, अपने scope में उपलब्ध credentials का मनमाने ढंग से उपयोग कर सकते हैं; इसलिए [credential scope](https://www.jenkins.io/doc/book/security/credentials/) और [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) भी service UID जितने ही महत्वपूर्ण हैं। Credentials की values और private keys को साझा enumeration output में शामिल न करें।

## Gogs repository files में write करना

Local Gogs service के लिए `gogs web` process owner का मिलान executable version और `custom/conf/app.ini` से करें। Configuration से service identity, repository root, listener address और registration disabled है या नहीं, इसका पता चल सकता है। केवल loopback पर सुनने वाला listener भी local users के लिए reachable होता है। 0.13.3 तक के Gogs versions में authenticated `PutContents` symlink file-write issue ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)) है: repository writer symlink commit करके फिर API write को उसके माध्यम से निर्देशित कर सकता है। परिणामी file access, Gogs process के privileges के अंतर्गत होता है, इसलिए root-owned instance पर तुरंत ध्यान देना चाहिए। Usable path का दावा करने से पहले deployed fix और authentication requirements की पुष्टि करें; API error यह साबित नहीं करता कि file write विफल हुआ।

## Gitea repository-description XSS और privileged viewers

Gitea 1.22.0 में repository description में stored JavaScript की अनुमति थी ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); 1.22.1 में इसे ठीक किया गया। Description edit कर सकने वाला user, किसी अधिक privileged browser session को प्रभावित कर सकता है, यदि वह user repository देखे और malicious link activate करे। फिर वह browser identity private repository content या अन्य application data उजागर कर सकती है। अलग से local escalation के लिए उस content के माध्यम से reachable credential या permission की आवश्यकता होती है, जैसे दोबारा इस्तेमाल किया गया administrator password; केवल Gitea process owner होना root impact साबित नहीं करता। इस chain का दावा करने से पहले deployed version, description-edit access, viewer workflow और वास्तविक browser interaction जाँचें।

## Cobbler provisioning API

Cobbler की management service एक XML-RPC API उपलब्ध कराती है, आम तौर पर port `25151` पर। Impact का आकलन करने से पहले listener और `cobblerd` process owner जाँचें; केवल loopback पर उपलब्ध API को भी host पर मौजूद user access कर सकता है। `/etc/cobbler/modules.conf` में authentication और authorization modules, `/etc/cobbler/settings` या `/etc/cobbler/settings.yaml` में service settings, और `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` तथा `/var/lib/cobbler/web.ss` की permissions देखें। Digest और shared-secret files में credential material होता है, इसलिए उनकी readability दर्ज करें, लेकिन default रूप से उनकी contents न छापें।

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** Cobbler 3.0.0 से 3.2.2 और 3.3.0 से 3.3.6 में XML-RPC authentication bypass है। Shared-secret पढ़ने में त्रुटि होने पर अनुमान लगाया जा सकने वाला मान `-1` लौटता था, जिसे API password के रूप में स्वीकार करता था। इसके लिए fixes 3.2.3 और 3.3.7 में उपलब्ध हैं। Package version एक सुराग है; exposure की रिपोर्ट करने से पहले deployed code और backport किए गए किसी भी fix की पुष्टि करें।

अगर `cobblerd` root के रूप में चलता है, तो authenticated API session से privileged execution path मिल सकता है। प्रभावित implementations में, `background_import` user-controlled `rsync_flags` को shell command में भेजता है, और user-controlled Cheetah autoinstall template को render करने पर Python evaluate हो सकता है। इनमें से किसी भी path की जाँच करने से पहले API permissions और installed version जाँचें। Management API तक पहुँच सीमित करें, authentication bypass को patch करें, और configuration तथा credential files को केवल service administrators के लिए readable रखें।

## Motion और motionEye configuration

`conf_path` जानने के लिए `/etc/motioneye/motioneye.conf` देखें, फिर उस directory में `motion.conf` और कुछ `camera-*.conf` files की समीक्षा करें। यह रिपोर्ट करें कि readable `# @admin_password` hash मौजूद है या नहीं—उसे प्रिंट न करें। [MotionEye के पुराने releases में ये files व्यापक read permissions के साथ लिखी जाती थीं](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); इसका fix 0.44.0 में है। Motion की `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method`, और `webcontrol_localhost` settings को साथ में जाँचें: authentication disabled होने पर advanced control (`2` या `3`) किसी local user को शक्तिशाली operations करने दे सकता है, loopback listener पर भी। [Motion में values और defaults की जानकारी दी गई है](https://motion-project.github.io/motion_config.html).

0.43.1b5 से पुराने motionEye के विरुद्ध admin session से camera filename setting को command execution में बदला जा सकता था, जब Motion उसे process करता था ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Escalation का दावा करने से पहले running version, service identity, उपयोग योग्य authentication path, और camera configured है या नहीं—इनकी पुष्टि करें। केवल configuration से यह साबित नहीं होता कि service चल रही है या privileged है।

Service name या installed package केवल एक सुराग है। Privilege boundary, reachable input, process identity, writable configuration, और अंततः उसके नियंत्रण में आने वाले command या file के मेल से तय होती है।

## Local AWS emulators और stored credentials

Host user container में चल रहे AWS-compatible emulator तक उसके published loopback endpoint के ज़रिए पहुँच सकता है। [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) या [KMS](https://docs.localstack.cloud/aws/services/kms/) तक पहुँच का आकलन करने से पहले live listener, client द्वारा चुने गए endpoint और account, तथा emulator की installed authorization settings का मिलान करें। LocalStack में, [IAM policy enforcement एक अलग setting है](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); केवल credential file, IAM policy, या listener के आधार पर प्रभावी API permissions का अनुमान न लगाएँ। Installed release और configuration के व्यवहार की पुष्टि करें।

Stored secret तभी local escalation में उपयोगी है, जब मौजूदा API identity उसे retrieve कर सके और कोई अलग, अधिक privileged account मिले हुए credential को स्वीकार करे। Encrypted local blob के लिए भी file read access, उससे मेल खाती उपयोग योग्य KMS key और algorithm, तथा प्रभावी decrypt access आवश्यक हैं। [Asymmetric KMS key](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) के लिए, decrypt request में blob को encrypt करने के लिए इस्तेमाल किया गया algorithm निर्दिष्ट होना चाहिए। Host की routine inventory को process, listener, configuration-path, और file-permission के साक्ष्य तक सीमित रखें; routine enumeration के दौरान secret values या decrypted plaintext की माँग या उन्हें प्रिंट न करें।
