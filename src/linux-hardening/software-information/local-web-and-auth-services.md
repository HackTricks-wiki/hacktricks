# Servicios web locales y de autenticación

{{#include ../../banners/hacktricks-training.md}}

Una shell de Linux ofrece una vista desde el host de los servicios web y de autenticación: argumentos de procesos, listeners, archivos de unidades, configuración, logs e interfaces de acceso local. Usa esa vista para relacionar un servicio accesible con la cuenta y los archivos que realmente utiliza.

## Mapear la pila web local

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspecciona los nombres de virtual hosts, los document roots, las rutas de proxy, los directorios de subida, la configuración de ejecución de PHP y los archivos de configuración que contengan credenciales. Un listener de loopback podría ser accesible a través de un proxy o un túnel SSH. Para probar un virtual host con nombre contra un listener local, envía el encabezado `Host` previsto o usa `curl --resolve` con la dirección y el puerto correctos. La enumeración de virtual hosts también puede revelar nombres que no aparecen en la respuesta predeterminada. Comprueba si Apache permite sobrescrituras mediante `.htaccess` y si las rutas de subida pueden ejecutar PHP antes de considerar que un directorio de subida con permisos de escritura permite ejecutar código. Un source map de JavaScript desplegado puede revelar rutas de código fuente o secretos del lado del cliente; trata los valores recuperados como indicios y verifica sus privilegios reales. Para comprobaciones específicas de web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) y [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

En Apache con [mpm-itk](https://mpm-itk.sesse.net/), un `AssignUserID` activo puede ejecutar un virtual host con un usuario y grupo diferentes. Si una cuenta con menos privilegios puede escribir un script en el `DocumentRoot` de ese host, revisa si una ruta accesible lo ejecuta realmente con la identidad asignada. Confirma que el módulo esté cargado, la configuración efectiva del virtual host (incluidas las sobrescrituras de identidad basadas en expresiones), los permisos de escritura y búsqueda del directorio, el handler del script y el acceso al listener. Una directiva resaltada o un directorio con permisos de escritura, por sí solos, no demuestran ejecución entre usuarios.

Un directorio personal publicado a través de un servidor web puede exponer archivos de respaldo de claves de identidad SSH aunque el directorio `.ssh` activo sea privado. Por ejemplo, la configuración `homedirs_public` de [Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) selecciona un subdirectorio servido desde los directorios personales de los usuarios. Encontrar un archivo comprimido solo por su ruta es un indicio: verifica la asignación efectiva del servidor, la legibilidad local o la autorización HTTP, el contenido del archivo, la frase de contraseña de la clave privada y si la cuenta correspondiente realmente acepta la clave. No extraigas archivos ni muestres material de claves durante la enumeración rutinaria del host.

Un respaldo legible de una aplicación web local con más privilegios puede revelar la lógica de autenticación y lectura de archivos aunque no se pueda acceder al código fuente activo. Compara el respaldo con el servicio desplegado antes de confiar en él. En particular, conviene revisar una cookie creada cifrando texto controlado por quien la solicita, seguido de un secreto y un indicador de rol, si la aplicación usa bloques ECB deterministas, devuelve cookies nuevas para texto elegido y luego divide el valor descifrado mediante un delimitador sin escapar. [NIST explica la asignación independiente y repetible de bloques de ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); esa propiedad puede permitir una comparación con entrada elegida, pero por sí sola no otorga un rol superior. Confirma la ruta activa, los requisitos previos de sesión, el flujo exacto del parser y los datos, la identidad del servicio y una acción privilegiada o ruta de lectura de archivos independiente. El inventario pasivo debe informar los metadatos del respaldo y la propiedad del listener sin leer el contenido del archivo ni enviar pruebas de autenticación.

El mismo enfoque de revisión del código fuente se aplica a un servicio local privilegiado **que no sea HTTP**, como una interfaz personalizada respaldada por SSH. Si un respaldo de código fuente accesible muestra un comando que acepta una ruta de archivo elegida por quien lo invoca, comprueba su control de autenticación, cómo resuelve la ruta y si verifica que el archivo resuelto permanezca dentro de un directorio previsto antes de abrirlo. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) limpia una ruta, pero no garantiza que permanezca dentro de ese directorio. Confirma que el respaldo corresponda a la compilación en ejecución, que el listener sea accesible, que la cuenta con menos privilegios pueda usar el comando y que el proceso pueda leer el objetivo; disponer de una clave SSH legible plantea una cuestión independiente sobre la política de inicio de sesión. Informa las rutas de los archivos de código fuente y la propiedad del servicio sin extraer el contenido de los archivos ni las claves a la salida automatizada.

Un pool de PHP-FPM que escucha en TCP loopback puede ser accesible desde otra cuenta local incluso si el sitio web requiere autenticación. [PHP advierte que un cliente capaz de conectarse a FastCGI puede controlar la configuración de la solicitud, incluido `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Revisa la configuración `listen` y `listen.allowed_clients` del pool junto con el listener activo, el UID de los workers, una ruta de script existente y cualquier restricción `security.limit_extensions` o `php_admin_value`. Los archivos de configuración del pool pueden contener credenciales en directivas `env[...]`, por lo que el inventario automatizado debe informar sus rutas, no su contenido. Un archivo de configuración o un puerto, por sí solos, no demuestran una ruta de ejecución entre usuarios; consulta la [guía de FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) para obtener detalles del protocolo.

En una API local privilegiada, rastrea la autorización además de la ejecución de código. Un rol de base de datos que la cuenta con menos privilegios pueda cambiar podría habilitar una ruta de API, pero el siguiente límite depende de cómo esté implementada esa ruta. Por ejemplo, combinar el JSON de una solicitud con un objeto JavaScript y luego llamar a [`child_process.exec`](https://nodejs.org/api/child_process.html) justifica revisar el [flujo de datos desde la contaminación de prototipos hasta la ejecución](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la biblioteca y versión de combinación reales, la validación de entrada, la ruta accesible, la identidad del proceso y las opciones del proceso hijo; un listener de Node propiedad de root o el nombre de una dependencia vulnerable, por sí solos, son solo indicios.

Los almacenes de CMS basados en archivos pueden guardar verificadores de contraseñas de administrador fuera de los archivos de configuración `.php` convencionales. Algunos ejemplos son `data/database.js` o `data/settings/pass.php` del sitio. Comprueba la propiedad y la legibilidad de los archivos antes de revisarlos manualmente, y no incluyas hashes en la salida compartida automatizada. Una contraseña de aplicación recuperable constituye un límite de privilegios distinto al de una cuenta Unix: verifica cualquier reutilización alegada con la cuenta específica y el método de autenticación permitido.

El controlador de autenticación de una aplicación también puede contener una contraseña de inicio de sesión literal en el código fuente, en lugar de un archivo de configuración. Si un usuario con menos privilegios puede leer el controlador desplegado, revisa localmente la comparación de autenticación y no incluyas ningún valor en la salida de enumeración compartida. Confirma que la ruta de código esté activa, que la contraseña sea válida para la aplicación y que una cuenta Unix distinta con más privilegios acepte realmente esa misma contraseña antes de afirmar que permite una escalada local de privilegios. El nombre de un archivo de controlador solo es un indicio para revisar.

Dolibarr almacena la configuración de conexión a la base de datos, incluido `dolibarr_main_db_pass`, en `htdocs/conf/conf.php` ([referencia de configuración](https://wiki.dolibarr.org/index.php/Configuration_file)). Un archivo legible es un indicio de credenciales; solo una reutilización de contraseña de cuenta verificada por separado u otro permiso de base de datos permitiría una escalada local de privilegios. Primero inspecciona los permisos y evita mostrar el valor en la salida automatizada.

La configuración del paquete de GitLab para Linux suele estar en `/etc/gitlab/gitlab.rb`, aunque los despliegues pueden conservar copias legibles en otros lugares. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) que este archivo puede contener `gitlab_rails['smtp_password']`, aunque la configuración SMTP cifrada puede guardar la contraseña fuera del archivo en texto plano. Trata una configuración legible como un indicio de credenciales: verifica que esté activa, que la credencial siga vigente y que una cuenta específica con más privilegios la acepte antes de afirmar que se reutiliza la contraseña. Por separado, [GitLab ejecuta `gitlab.rb` como código Ruby bajo root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un archivo activo con permisos de escritura o un `from_file` incluido necesita una ruta real de reconfiguración privilegiada para constituir un hallazgo de ejecución. La vista previa de una configuración puede exponer valores de credenciales; trata su salida como sensible y comparte en su lugar las rutas y los permisos.

Una instalación autogestionada de Mattermost puede guardar `SqlSettings.DataSource` en `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) tanto esa ruta habitual como los despliegues que almacenan la configuración activa en una base de datos. Un archivo legible puede exponer una credencial de la base de datos de la aplicación, pero no demuestra que se pueda acceder a la base de datos ni obtener acceso root en Unix. Verifica la fuente de configuración activa, los permisos reales del rol de base de datos, cualquier contraseña de aplicación recuperada por separado y si esa contraseña funciona para una cuenta Unix específica con más privilegios. El formato del hash de contraseña puede variar según la versión de Mattermost; durante la enumeración, registra la ruta de configuración y los metadatos de acceso sin mostrar la cadena de conexión ni consultar la base de datos.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra los resultados de virtual hosts comparándolos con el tamaño de la respuesta predeterminada u otra referencia estable, para que cada nombre adivinado no parezca válido. Un source map solo es útil si está realmente desplegado o se puede leer de otro modo.

Los reverse proxies pueden cambiar qué encabezados del cliente considera fiables una aplicación. Compara las solicitudes directas y las enviadas a través del proxy antes de asumir que `X-Forwarded-For`, `X-Forwarded-Host` u otros encabezados similares establecen la identidad de quien realiza la solicitud. Revisa conjuntamente la configuración del proxy y de la aplicación.

Si PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` en una cadena pasada a [`system()`](https://www.php.net/manual/en/function.system.php), revisa si la ruta de solicitud accesible permite que quien realiza la solicitud proporcione el encabezado y si los metacaracteres de shell llegan intactos a esa cadena. Incluir al principio un comando como `sudo iptables` **no** hace que los comandos posteriores separados por shell se ejecuten como root; estos se ejecutan con la identidad del worker web, salvo que una regla de sudo efectiva independiente permita la escalada. Confirma la identidad del worker, la concesión exacta de `sudo -l` y sus requisitos de autenticación, así como los límites de los argumentos del comando, antes de afirmar que existe una ruta a root. Inspecciona el código fuente y la política sin enviar una prueba de inyección durante la enumeración rutinaria del host.

## Credenciales de inicio de sesión en los logs de acceso

Si una aplicación envía un formulario de inicio de sesión mediante `GET`, el nombre de usuario y la contraseña pueden convertirse en parámetros de consulta en el URI de la solicitud. Una solicitud `POST` también puede incluir una cadena de consulta; usar `POST` no oculta un secreto colocado accidentalmente en el URI, incluida una contraseña introducida en un campo no relacionado del formulario. [La línea de solicitud de los logs de acceso habituales de Apache](https://httpd.apache.org/docs/2.4/logs.html) registra el método y el URI, incluida su cadena de consulta, cuando el formato configurado usa `%r`. Por tanto, una cuenta con permiso para leer esos logs, por ejemplo, a través del grupo `adm` en algunos sistemas Linux, podría encontrar una pista sobre credenciales. Comprueba el formato y los permisos reales del log, y luego verifica que el valor sea un secreto, que la cuenta lo acepte y que cruce un límite de privilegios. No des por sentado que se registró el cuerpo de la solicitud ni copies posibles valores en resultados compartidos.

Inspecciona solo los logs de acceso que puedas leer y evita incluir valores de credenciales en la salida compartida de comandos. Las líneas largas de solicitud también pueden contener un referrer y un user agent, por lo que un filtro de líneas cortas podría ocultar precisamente la solicitud que interesa. Las ubicaciones habituales de los logs de acceso de Apache, httpd y Nginx son `/var/log/apache2/access.log`, `/var/log/httpd/access_log` y `/var/log/nginx/access.log`. Los logs rotados pueden contener credenciales antiguas. [El acceso a archivos de log mediante LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) es una ruta relacionada a los mismos datos.

Los logs de autenticación de aplicaciones también pueden exponer una contraseña introducida accidentalmente en el campo de **nombre de usuario** de un inicio de sesión fallido. Primero, confirma que el log se puede leer y que su formato registra el nombre de usuario enviado; inspecciona localmente solo un fragmento pequeño y pertinente, y no copies posibles credenciales en resultados compartidos. Un nombre de usuario con aspecto de contraseña es una pista, no una prueba de que sea una contraseña válida ni de que otorgue mayores privilegios. Verifica la cuenta prevista y cualquier reutilización de contraseña en el servicio específico o la cuenta Unix antes de afirmar que existe una transición.

Un handler de inicio de sesión web modificable requiere una revisión aparte cuando un cliente programado que se ejecuta con otra identidad envía credenciales a ese endpoint. Confirma el acceso de escritura al handler **activo**, la programación y la ruta de solicitud reales del cliente, de quién son las credenciales que envía y si esa contraseña de aplicación también es válida para una cuenta del sistema operativo con más privilegios. Una página modificable o un proceso recurrente, por sí solos, no demuestran que exista esa transición. El inventario pasivo debe informar sobre los permisos de la ruta y los metadatos del trabajo sin modificar el handler ni recopilar contraseñas.

Los logs JSON EVE de Suricata también pueden registrar los comandos FTP `USER` y `PASS` con su `command_data` cuando está habilitado el registro de eventos FTP. Comprueba si se puede leer `/var/log/suricata/eve*.json*`, incluidos los archivos rotados o comprimidos, antes de revisar localmente un fragmento pequeño y pertinente. Un archivo EVE legible es solo una pista: confirma que se registraron eventos FTP, que los datos incluyen credenciales utilizables y que estas cruzan un límite de privilegios. Evita imprimir `command_data` en la salida compartida de enumeración. Suricata documenta los [campos de eventos FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) y [la rotación de EVE y las variantes de nombres de archivo](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuración de Apache generada y logs canalizados

[remco](https://github.com/HeavyHorst/remco) puede supervisar un backend de clave/valor, renderizar una plantilla en un archivo de configuración de Apache y ejecutar un comando de recarga. Inspecciona la identidad del proceso remco en ejecución, el origen y el destino configurados de la plantilla, los prefijos de claves supervisados y si un valor del backend se inserta directamente en una directiva de Apache como `ServerName`. Que haya un listener local del backend no demuestra por sí solo que el usuario actual pueda escribir una clave supervisada; verifica la autenticación y los permisos del backend antes de afirmar que existe una escalada.

Un salto de línea sin escapar en un valor modificable del backend puede convertir el valor previsto para una directiva en directivas adicionales de Apache. Los [logs canalizados de Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) son especialmente sensibles: `CustomLog` o `ErrorLog` con un comando precedido por `|` inicia un proceso auxiliar con la identidad del proceso httpd padre, a menudo root; `|$` pide a Apache que use un shell. Revisa la configuración generada y la ruta de recarga sin modificar los datos del backend ni reiniciar el servicio durante la enumeración. Mantén privado el comando canalizado completo, ya que sus argumentos pueden contener secretos.

## Identidades de autenticación y servicio

El archivo de control de Monit suele ser `~/.monitrc` o `/etc/monitrc`, pero `monit -c` puede seleccionar otra ruta. Un archivo legible puede contener entradas `set httpd` y `allow user:password` para su interfaz web, a menudo en el puerto local 2812. Comprueba el propietario y los permisos del archivo antes de revisarlo, y evita incluir valores de contraseña en la salida compartida de enumeración. Las credenciales web solo otorgan el rol de Monit configurado; los usuarios de solo lectura no pueden invocar acciones de control. Para escalar mediante una cuenta Unix hace falta confirmar la reutilización de la contraseña o que el rol autenticado pueda activar una acción privilegiada de Monit. Consulta la [documentación de Monit sobre el archivo de control y la autenticación](https://www.mmonit.com/monit/documentation/monit.html).

En Webmin, `/etc/webmin/miniserv.conf` identifica la configuración del servidor y `/etc/webmin/webmin.acl` registra a qué módulos pueden acceder los usuarios; [Webmin documenta el límite de concesión de módulos](https://webmin.com/docs/development/creating-modules/). Una contraseña Unix o un archivo ACL legible no otorgan por sí solos una sesión de Webmin. Confirma la asignación de autenticación efectiva, el listener accesible, la cuenta autenticada, el permiso efectivo para el módulo Package Updates, el código instalado o la corrección del proveedor y la identidad del proceso Webmin. En versiones afectadas hasta la 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permitía que una cuenta con permiso para ese módulo ejecutara comandos mediante su handler de actualizaciones. Durante la enumeración pasiva, informa sobre las rutas de configuración y sus permisos sin imprimir credenciales ni intentar una actualización.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) rige la autenticación específica de cada servicio; las rutas de políticas o módulos con permisos de escritura pueden cambiar el comportamiento del inicio de sesión.
- La configuración de LDAP/SSSD puede revelar endpoints de directorio, identidades de bind y reglas de acceso. Una contraseña de bind recuperada puede permitir consultas LDAP que excedan las del usuario actual del sistema operativo; prueba la identidad de bind exacta y las ACL del directorio. Revisa los permisos de los archivos antes de inspeccionar secretos; [Linux Active Directory](../user-information/linux-active-directory.md) y [FreeIPA](freeipa-pentesting.md) cubren el uso de tickets y directorios.
- Los alias de Postfix pueden canalizar el correo recibido a comandos locales. Si un usuario con menos privilegios puede modificar el script referenciado, la entrega de correo puede ejecutar su código con la identidad de entrega. Revisa los mapas de alias y la propiedad de los scripts antes de afirmar que esa vía es viable; consulta [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins y otros servicios de CI pueden ejecutar trabajos con una cuenta local privilegiada. Inspecciona el usuario del servicio, las rutas de trabajos/workspace con permisos de escritura y la interfaz de administración local antes de probar un pipeline o plugin. Revisa también las **credenciales disponibles para un trabajo** y la cuenta con la que pueden autenticarse: un Pipeline que use el [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) puede acceder a un host como el usuario de la credencial SSH, aunque Jenkins se ejecute con una cuenta Unix menos privilegiada. Confirma que la identidad actual de Jenkins tiene `Job/Create`, `Job/Configure` u otra vía efectiva para modificar el Pipeline, que la credencial está dentro del alcance de ese trabajo y que la cuenta SSH de destino acepta la clave antes de afirmar que hay una escalada de privilegios en el host. El nombre visible o el ID de una credencial, por sí solos, no confirman ninguna de estas condiciones. Jenkins advierte que quienes crean trabajos y, a menudo, quienes los configuran pueden usar arbitrariamente las credenciales disponibles en su alcance; por tanto, [credential scope](https://www.jenkins.io/doc/book/security/credentials/) y [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) importan tanto como el UID del servicio. No incluyas valores de credenciales ni claves privadas en resultados de enumeración compartidos.

## Escrituras de archivos en repositorios de Gogs

En un servicio Gogs local, relaciona el propietario del proceso `gogs web` con la versión del ejecutable y `custom/conf/app.ini`. La configuración puede revelar la identidad del servicio, la raíz del repositorio, la dirección de escucha y si el registro está deshabilitado. Incluso los listeners limitados a loopback son accesibles para los usuarios locales. Las versiones de Gogs hasta la 0.13.3 tienen un problema de escritura de archivos mediante symlink en `PutContents` autenticado ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): un usuario con permisos de escritura en el repositorio puede guardar un symlink y luego dirigir a través de él una escritura de la API. El acceso resultante a los archivos tiene los privilegios del proceso Gogs, por lo que una instancia ejecutada como root requiere atención inmediata. Valida que la corrección esté implementada y verifica los requisitos de autenticación antes de afirmar que la vía es utilizable; un error de la API no demuestra que la escritura del archivo haya fallado.

## XSS en la descripción de repositorios de Gitea y usuarios con privilegios

Gitea 1.22.0 permitía JavaScript almacenado en la descripción de un repositorio ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versión 1.22.1 lo corrigió. Un usuario que pueda editar una descripción puede afectar una sesión de navegador con más privilegios si ese usuario visita el repositorio y activa el enlace malicioso. Esa identidad del navegador puede entonces exponer contenido de repositorios privados u otros datos de la aplicación. Una escalada local independiente requiere una credencial o permiso accesible a través de ese contenido, como una contraseña reutilizada de administrador; el propietario del proceso Gitea, por sí solo, no demuestra un impacto en root. Comprueba la versión implementada, el acceso para editar descripciones, el flujo de trabajo del usuario y la interacción real con el navegador antes de afirmar que la cadena es viable.

## API de aprovisionamiento de Cobbler

El servicio de administración de Cobbler expone una API XML-RPC, habitualmente en el puerto `25151`. Comprueba el listener y el propietario del proceso `cobblerd` antes de evaluar su impacto; incluso una API limitada a loopback puede ser accesible para un usuario del host. Revisa los módulos de autenticación y autorización en `/etc/cobbler/modules.conf`, la configuración del servicio en `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml`, y los permisos de `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` y `/var/lib/cobbler/web.ss`. Los archivos de digest y secreto compartido contienen material de credenciales, así que registra si se pueden leer sin imprimir su contenido de forma predeterminada.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** es una omisión de autenticación de XML-RPC en Cobbler 3.0.0 a 3.2.2 y 3.3.0 a 3.3.6. Un error al leer el secreto compartido devolvía el valor predecible `-1`, que la API aceptaba como contraseña. Las correcciones correspondientes están en las versiones 3.2.3 y 3.3.7. La versión de un paquete es solo una pista; verifica el código desplegado y cualquier corrección retroportada antes de informar de una exposición.

Una sesión de API autenticada puede ser una vía de ejecución privilegiada si `cobblerd` se ejecuta como root. En las implementaciones afectadas, `background_import` pasa `rsync_flags` controlados por el usuario a un comando de shell, y al renderizar una plantilla de autoinstalación Cheetah controlada por el usuario se puede evaluar Python. Comprueba los permisos de la API y la versión instalada antes de probar cualquiera de estas vías. Restringe el acceso a la API de administración, aplica el parche para la omisión de autenticación y permite que solo los administradores del servicio lean los archivos de configuración y credenciales.

## Configuración de Motion y motionEye

Inspecciona `/etc/motioneye/motioneye.conf` para encontrar `conf_path` y luego revisa `motion.conf` y un pequeño número de archivos `camera-*.conf` en ese directorio. Informa si existe un hash legible de `# @admin_password`, sin imprimirlo. [Las versiones antiguas de motionEye escribían estos archivos con permisos de lectura demasiado amplios](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la corrección está en la versión 0.44.0. Comprueba conjuntamente los ajustes `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` y `webcontrol_localhost` de Motion: el control avanzado (`2` o `3`) sin autenticación habilitada puede exponer operaciones potentes a un usuario local, incluso en un listener loopback. [Motion documenta los valores y valores predeterminados](https://motion-project.github.io/motion_config.html).

Una sesión de admin en motionEye anterior a la versión 0.43.1b5 podía convertir un ajuste del nombre de archivo de una cámara en ejecución de comandos cuando Motion lo procesaba ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Confirma la versión en ejecución, la identidad del servicio, una vía de autenticación utilizable y si hay una cámara configurada antes de afirmar que existe una escalada. La configuración por sí sola no demuestra que el servicio esté en ejecución ni que tenga privilegios.

El nombre de un servicio o un paquete instalado es solo una pista. El límite de privilegios depende de la combinación de una entrada accesible, la identidad del proceso, la configuración modificable y el comando o archivo que controla en última instancia.

## Emuladores locales de AWS y credenciales almacenadas

Un usuario del host puede acceder a un emulador compatible con AWS que se ejecuta en un contenedor mediante su endpoint loopback publicado. Antes de evaluar el acceso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), correlaciona el listener activo, el endpoint y la cuenta seleccionados por el cliente, y los ajustes de autorización instalados del emulador. En LocalStack, [la aplicación de políticas de IAM es un ajuste independiente](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); no infieras los permisos efectivos de la API a partir únicamente de un archivo de credenciales, una política de IAM o un listener. Confirma el comportamiento de la versión y la configuración instaladas.

Un secreto almacenado solo sirve para una escalada local si la identidad actual de la API puede recuperarlo y una cuenta distinta con más privilegios acepta la credencial obtenida. Un blob local cifrado también requiere acceso de lectura al archivo, la clave KMS correspondiente utilizable y el algoritmo adecuado, y acceso efectivo para descifrar. Para una [clave KMS asimétrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la solicitud de descifrado debe especificar el algoritmo usado para cifrar el blob. Limita el inventario automático del host a evidencias sobre procesos, listeners, rutas de configuración y permisos de archivos; durante la enumeración rutinaria, no solicites ni imprimas valores secretos ni texto sin cifrar descifrado.
