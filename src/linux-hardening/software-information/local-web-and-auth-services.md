# Servizi web locali e di autenticazione

{{#include ../../banners/hacktricks-training.md}}

Una shell Linux offre una visuale lato host dei servizi web e di autenticazione: argomenti dei processi, listener, file delle unità, configurazione, log e interfacce accessibili solo localmente. Usa questa visuale per collegare un servizio raggiungibile all’account e ai file che usa effettivamente.

## Mappare lo stack web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Esamina i nomi dei virtual host, le root dei documenti, le route proxy, le directory di upload, le impostazioni di esecuzione PHP e i file di configurazione che contengono credenziali. Un listener loopback potrebbe essere raggiungibile tramite un proxy o un tunnel SSH. Per testare un virtual host nominato rispetto a un listener locale, invia l'header `Host` previsto oppure usa `curl --resolve` con l'indirizzo e la porta corretti. L'enumerazione dei virtual host può anche rivelare nomi assenti dalla risposta predefinita. Verifica se Apache consente gli override tramite `.htaccess` e se i percorsi di upload possono eseguire PHP prima di considerare una directory di upload scrivibile come un'esecuzione di codice. Una source map JavaScript distribuita può esporre percorsi del sorgente o segreti lato client; considera i valori recuperati come indizi e verifica i privilegi effettivi. Per i controlli specifici del web, consulta [Apache](../../network-services-pentesting/pentesting-web/apache.md) e [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Per Apache con [mpm-itk](https://mpm-itk.sesse.net/), una direttiva `AssignUserID` attiva può eseguire un virtual host con un utente e un gruppo diversi. Se un account con privilegi inferiori può scrivere uno script nella `DocumentRoot` di quell'host, verifica se una route raggiungibile lo esegue effettivamente con l'identità assegnata. Conferma che il modulo sia caricato, la configurazione effettiva del virtual host (inclusi gli override dell'identità basati su espressioni), i permessi di scrittura e attraversamento della directory, l'handler dello script e l'accesso al listener. Una direttiva evidenziata o una directory scrivibile, da sole, non dimostrano un'esecuzione tra utenti diversi.

Una home directory pubblicata tramite un web server può esporre archivi di backup contenenti file di identità SSH anche quando la directory `.ssh` attiva è privata. Per esempio, l'impostazione [`homedirs_public` di Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) seleziona una sottodirectory delle home directory degli utenti da servire. Trovare un archivio tramite il solo percorso è un indizio: verifica la mappatura effettiva del server, la leggibilità locale o l'autorizzazione HTTP, il contenuto dell'archivio, la passphrase della chiave privata e se l'account corrispondente accetta davvero la chiave. Durante la normale enumerazione dell'host, non estrarre archivi né stampare il contenuto delle chiavi.

Un backup leggibile di un'app web locale con privilegi superiori può rivelare la logica di autenticazione e lettura dei file anche quando il sorgente attivo non è accessibile. Confronta il backup con il servizio distribuito prima di farvi affidamento. In particolare, merita un esame un cookie creato cifrando testo controllato dal chiamante, seguito da un segreto e da un flag di ruolo, se l'app usa blocchi ECB deterministici, restituisce cookie nuovi per testo scelto e in seguito separa il valore decifrato in corrispondenza di un delimitatore non sottoposto a escape. [NIST spiega la mappatura indipendente e ripetibile dei blocchi ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); questa proprietà può consentire un confronto con input scelti, ma da sola non concede un ruolo superiore. Conferma la route attiva, i prerequisiti della sessione, il parser esatto e il flusso dei dati, l'identità del servizio e l'esistenza di un'azione privilegiata o di un percorso separato per la lettura dei file. L'inventario passivo dovrebbe riportare i metadati del backup e chi possiede il listener, senza leggere il contenuto dell'archivio né inviare probe di autenticazione.

Lo stesso approccio di revisione del sorgente si applica a un servizio locale privilegiato **non-HTTP**, come un'interfaccia personalizzata basata su SSH. Se un backup accessibile del sorgente mostra un comando che accetta un percorso di file scelto dal chiamante, controlla il suo meccanismo di autenticazione, come risolve il percorso e se verifica che il file risolto rimanga all'interno di una directory prevista prima di aprirlo. In Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) normalizza un percorso, ma non ne impone il contenimento. Conferma che il backup corrisponda alla build in esecuzione, che il listener sia raggiungibile, che l'account con privilegi inferiori possa usare il comando e che il processo possa leggere il file di destinazione; il possesso di una chiave SSH leggibile è una questione distinta, legata alle policy di accesso. Riporta i percorsi degli archivi sorgente e la proprietà del servizio senza estrarre il contenuto degli archivi o le chiavi nell'output automatizzato.

Un pool PHP-FPM in ascolto su TCP loopback può essere raggiunto da un altro account locale anche se il sito web richiede l'autenticazione. [PHP avverte che un client in grado di connettersi a FastCGI può controllare le impostazioni delle richieste, incluso `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Esamina le impostazioni `listen` e `listen.allowed_clients` del pool insieme al listener attivo, all'UID dei worker, al percorso di uno script esistente e a eventuali restrizioni `security.limit_extensions` o `php_admin_value`. I file di configurazione del pool possono contenere credenziali nelle direttive `env[...]`, quindi l'inventario automatizzato dovrebbe riportarne i percorsi, non il contenuto. Un file di configurazione o una porta, da soli, non dimostrano un percorso di esecuzione tra utenti diversi; consulta la [guida FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) per i dettagli del protocollo.

Per un'API locale privilegiata, analizza l'autorizzazione oltre all'esecuzione del codice. Un ruolo del database modificabile dall'account con privilegi inferiori può sbloccare una route API, ma il confine successivo dipende dall'implementazione della route. Per esempio, unire il JSON della richiesta a un oggetto JavaScript e poi chiamare [`child_process.exec`](https://nodejs.org/api/child_process.html) merita una verifica del [flusso dei dati da prototype pollution a esecuzione](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Verifica la libreria/versione effettiva usata per l'unione, la validazione dell'input, la route raggiungibile, l'identità del processo e le opzioni del processo figlio; un listener Node di proprietà di root o il nome di una dipendenza vulnerabile sono soltanto indizi.

Gli archivi CMS basati su file possono contenere verificatori di password amministrative al di fuori dei convenzionali file di configurazione `.php`. Tra gli esempi ci sono `data/database.js` o `data/settings/pass.php` di un sito. Verifica la proprietà e la leggibilità dei file prima di esaminarli manualmente, e non includere gli hash nell'output automatizzato condiviso. Una password applicativa recuperabile è un confine di privilegio distinto da un account Unix: verifica ogni presunto riutilizzo per lo specifico account e il metodo di autenticazione consentito.

Il controller di autenticazione di un'applicazione può contenere anche una password di accesso letterale nel codice sorgente, anziché in un file di configurazione. Se un utente con privilegi inferiori può leggere il controller distribuito, esamina localmente il confronto usato per l'autenticazione e non includere eventuali valori nell'output di enumerazione condiviso. Conferma che il percorso del codice sia attivo, che la password sia valida per l'applicazione e che uno specifico account Unix con privilegi superiori accetti davvero la stessa password prima di dichiarare un'escalation dei privilegi locali. Il solo nome del file del controller è soltanto un indizio da verificare.

Dolibarr memorizza le impostazioni di connessione al database, incluso `dolibarr_main_db_pass`, in `htdocs/conf/conf.php` ([riferimento della configurazione](https://wiki.dolibarr.org/index.php/Configuration_file)). Un file leggibile è un indizio relativo alle credenziali; solo un riutilizzo verificato separatamente della password di un account o un altro permesso sul database potrebbe trasformarlo in un'escalation dei privilegi locali. Prima controlla i permessi ed evita di stampare il valore nell'output automatizzato.

La configurazione del pacchetto Linux di GitLab si trova normalmente in `/etc/gitlab/gitlab.rb`, anche se le installazioni potrebbero conservare copie leggibili altrove. [GitLab documenta](https://docs.gitlab.com/omnibus/settings/smtp/) che questo file può contenere `gitlab_rails['smtp_password']`, sebbene le impostazioni SMTP cifrate possano mantenere la password al di fuori del file in testo chiaro. Considera una configurazione leggibile un indizio relativo alle credenziali: verifica che sia attiva, che la credenziale sia valida e che uno specifico account con privilegi superiori la accetti prima di dichiarare il riutilizzo della password. Separatamente, [GitLab esegue `gitlab.rb` come codice Ruby con privilegi root durante `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); un file attivo scrivibile o un `from_file` incluso richiede un percorso effettivo di riconfigurazione privilegiata prima di poter essere considerato una vulnerabilità di esecuzione. Un'anteprima della configurazione potrebbe esporre i valori delle credenziali, quindi considera sensibile il suo output e condividi invece percorsi e permessi.

Un'installazione Mattermost self-hosted può conservare `SqlSettings.DataSource` in `/opt/mattermost/config/config.json`; [Mattermost documenta](https://docs.mattermost.com/deployment-guide/server/troubleshooting) sia il percorso abituale sia le installazioni in cui la configurazione attiva è invece memorizzata in un database. Un file leggibile può esporre una credenziale del database dell'applicazione, ma non dimostra né l'accesso al database né l'accesso root a Unix. Verifica la fonte della configurazione attiva, i permessi effettivi del ruolo del database, eventuali password applicative recuperate separatamente e se tale password funziona per uno specifico account Unix con privilegi superiori. Il formato degli hash delle password può cambiare tra le versioni di Mattermost; durante l'enumerazione registra il percorso della configurazione e i metadati di accesso senza stampare la stringa di connessione né interrogare il database.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtra i risultati dei virtual host confrontandoli con la dimensione della risposta predefinita o con un'altra baseline stabile, così che ogni nome ipotizzato non sembri valido. Una source map è utile solo se è effettivamente distribuita o altrimenti leggibile.

I reverse proxy possono modificare quali header del client vengono considerati attendibili da un'applicazione. Confronta le richieste dirette e quelle inoltrate da proxy prima di presumere che `X-Forwarded-For`, `X-Forwarded-Host` o header simili stabiliscano l'identità del chiamante. Esamina insieme la configurazione del proxy e quella dell'applicazione.

Se PHP copia `$_SERVER['HTTP_X_FORWARDED_FOR']` in una stringa passata a [`system()`](https://www.php.net/manual/en/function.system.php), verifica se il percorso della richiesta raggiungibile consente di impostare l'header e se i metacaratteri della shell arrivano inalterati a quella stringa. Un comando come `sudo iptables` inserito all'inizio **non** fa sì che i comandi successivi separati dalla shell vengano eseguiti come root: vengono eseguiti con l'identità del worker web, a meno che una regola sudo effettiva separata non consenta l'escalation. Prima di affermare che esista un percorso verso root, verifica l'identità del worker, la regola esatta concessa da `sudo -l` e i requisiti di autenticazione, nonché il confine degli argomenti del comando. Durante la normale enumerazione dell'host, esamina il codice sorgente e le policy senza inviare probe di injection.

## Credenziali di login nei log di accesso

Se un'applicazione invia un modulo di login con `GET`, il nome utente e la password possono diventare parametri di query nell'URI della richiesta. Anche una richiesta `POST` può contenere una query string: usare `POST` non nasconde un segreto inserito per errore nell'URI, inclusa una password digitata in un campo non correlato del modulo. La [riga di richiesta nei log di accesso comuni di Apache](https://httpd.apache.org/docs/2.4/logs.html) registra il metodo e l'URI, inclusa la query string, quando il formato configurato usa `%r`. Un account autorizzato a leggere quei log, per esempio tramite il gruppo `adm` su alcuni sistemi Linux, potrebbe quindi trovare una credenziale da verificare. Controlla il formato effettivo dei log e i permessi, poi verifica che il valore sia un segreto, che l'account lo accetti e che consenta di oltrepassare un confine di privilegi. Non presumere che il corpo della richiesta sia stato registrato e non copiare valori potenzialmente validi in output condivisi.

Esamina solo i log di accesso leggibili e non includere i valori delle credenziali nell'output condiviso dei comandi. Le righe di richiesta lunghe possono contenere anche un referrer e uno user agent, quindi un filtro per righe brevi può nascondere proprio la richiesta di interesse. I percorsi comuni dei log di accesso di Apache, httpd e Nginx sono `/var/log/apache2/access.log`, `/var/log/httpd/access_log` e `/var/log/nginx/access.log`. I log ruotati possono contenere credenziali più vecchie. [L'accesso ai file di log tramite LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) è un percorso correlato agli stessi dati.

Anche i log di autenticazione delle applicazioni possono esporre una password inserita per errore nel campo **username** di un login non riuscito. Per prima cosa, verifica che il log sia leggibile e che il suo formato registri il nome utente inviato; esamina localmente solo una piccola porzione pertinente e non copiare credenziali potenzialmente valide in output condivisi. Un nome utente che sembra una password è un indizio, non la prova di una password valida o di privilegi più elevati. Prima di affermare che ci sia una transizione, verifica l'account previsto e l'eventuale riutilizzo della password per lo specifico servizio o account Unix.

Un gestore di login web scrivibile merita un esame separato quando un client pianificato, eseguito con un'altra identità, invia credenziali a quell'endpoint. Verifica l'accesso in scrittura al gestore **attivo**, la pianificazione effettiva del client e il percorso della richiesta, a chi appartengano le credenziali inviate e se la password dell'applicazione sia valida autonomamente per un account del sistema operativo con privilegi più elevati. Una pagina scrivibile o un processo ricorrente, da soli, non dimostrano questa transizione. L'inventario passivo dovrebbe riportare i permessi dei percorsi e i metadati dei job senza modificare il gestore né raccogliere password.

I log JSON EVE di Suricata possono registrare anche i comandi FTP `USER` e `PASS` con i relativi `command_data` quando la registrazione degli eventi FTP è attiva. Prima di esaminare localmente una piccola porzione pertinente, verifica la leggibilità di `/var/log/suricata/eve*.json*`, compresi i file ruotati o compressi. Un file EVE leggibile è solo un indizio: verifica che siano stati registrati eventi FTP, che i dati contengano credenziali utilizzabili e che consentano di oltrepassare un confine di privilegi. Evita di stampare `command_data` nell'output condiviso dell'enumerazione. Suricata documenta i [campi degli eventi FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) e le [varianti di rotazione e dei nomi dei file EVE](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configurazione Apache generata e log inoltrati tramite pipe

[remco](https://github.com/HeavyHorst/remco) può monitorare un backend key/value, renderizzare un template in un file di configurazione Apache ed eseguire un comando di reload. Esamina l'identità del processo remco in esecuzione, la sorgente e la destinazione del template configurato, i prefissi delle chiavi monitorate e se un valore del backend viene inserito direttamente in una direttiva Apache come `ServerName`. La sola presenza di un listener del backend locale non dimostra che l'utente corrente possa scrivere una chiave monitorata; verifica l'autenticazione e i permessi del backend prima di affermare che sia possibile un'escalation.

Un newline non escaped in un valore scrivibile del backend può trasformare il valore previsto per una direttiva in direttive Apache aggiuntive. I [log Apache inoltrati tramite pipe](https://httpd.apache.org/docs/2.4/logs.html#piped) sono particolarmente sensibili: `CustomLog` o `ErrorLog` con un comando preceduto da `|` avvia un helper con l'identità del processo httpd padre, spesso root; `|$` chiede ad Apache di usare una shell. Esamina la configurazione generata e il percorso di reload senza modificare i dati del backend né riavviare il servizio durante l'enumerazione. Non condividere il comando completo della pipe, perché i suoi argomenti potrebbero contenere segreti.

## Autenticazione e identità dei servizi

Il file di controllo di Monit è solitamente `~/.monitrc` o `/etc/monitrc`, ma `monit -c` può selezionare un percorso diverso. Un file leggibile può contenere voci `set httpd` e `allow user:password` per la sua interfaccia web, spesso sulla porta locale 2812. Prima di esaminarlo, controllane proprietario e permessi e non includere i valori delle password nell'output condiviso dell'enumerazione. Le credenziali web concedono solo il ruolo Monit configurato; gli utenti di sola lettura non possono eseguire azioni di controllo. Per un'escalation tramite account Unix servono la conferma del riutilizzo della password oppure un'azione Monit privilegiata effettivamente eseguibile dal ruolo autenticato. Consulta la [documentazione di Monit sui file di controllo e sull'autenticazione](https://www.mmonit.com/monit/documentation/monit.html).

Per Webmin, `/etc/webmin/miniserv.conf` contiene le impostazioni del server e `/etc/webmin/webmin.acl` registra i moduli accessibili agli utenti; [Webmin documenta i limiti delle autorizzazioni sui moduli](https://webmin.com/docs/development/creating-modules/). Una password Unix o un file ACL leggibile non concedono di per sé una sessione Webmin. Verifica la mappatura effettiva dell'autenticazione, il listener raggiungibile, l'account autenticato, l'autorizzazione effettiva al modulo Package Updates, il codice installato o la correzione del fornitore e l'identità del processo Webmin. Nelle versioni vulnerabili fino alla 1.910, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) consentiva a un account con quell'autorizzazione al modulo di eseguire comandi tramite il gestore degli aggiornamenti. Durante l'enumerazione passiva, riporta i percorsi di configurazione e i permessi senza stampare credenziali né tentare un aggiornamento.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) gestisce l'autenticazione specifica dei servizi; percorsi delle policy o dei moduli scrivibili possono modificare il comportamento di login.
- La configurazione LDAP/SSSD può rivelare endpoint di directory, identità di bind e regole di accesso. Una password di bind recuperata può consentire query LDAP che vanno oltre l'account OS corrente; verifica l'identità di bind esatta e le ACL della directory. Controlla i permessi dei file prima di esaminare i segreti; [Linux Active Directory](../user-information/linux-active-directory.md) e [FreeIPA](freeipa-pentesting.md) trattano l'uso di ticket e directory.
- Gli alias di Postfix possono inoltrare le email ricevute a comandi locali. Se un utente con privilegi inferiori può modificare lo script indicato, la consegna delle email può eseguire il suo codice con l'identità usata per la consegna. Controlla le mappe degli alias e la proprietà degli script prima di affermare che il percorso è sfruttabile; vedi [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins e altri servizi CI possono eseguire job con un account locale dotato di privilegi elevati. Esamina l'utente del servizio, i percorsi di job/workspace scrivibili e l'interfaccia di amministrazione locale prima di testare una pipeline o un plugin. Esamina anche le **credenziali disponibili per un job** e l'account con cui possono autenticarsi: una Pipeline che usa lo [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) può accedere a un host come utente della credenziale SSH, anche quando Jenkins stesso è eseguito con un account Unix meno privilegiato. Verifica che l'identità Jenkins corrente disponga di `Job/Create`, `Job/Configure` o di un altro modo effettivo per modificare la Pipeline, che la credenziale sia disponibile per quel job e che l'account SSH di destinazione accetti la chiave, prima di affermare che si tratta di un'escalation di privilegi sull'host. Il nome visualizzato o l'ID di una credenziale, da solo, non dimostra nessuna di queste condizioni. Jenkins avverte che chi crea i job e, spesso, chi li configura può usare arbitrariamente le credenziali disponibili nel proprio ambito; perciò [credential scope](https://www.jenkins.io/doc/book/security/credentials/) e [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) sono importanti quanto l'UID del servizio. Non includere i valori delle credenziali né le chiavi private nell'output di enumerazione condiviso.

## Scrittura di file nei repository Gogs

Per un servizio Gogs locale, confronta il proprietario del processo `gogs web` con la versione dell'eseguibile e `custom/conf/app.ini`. La configurazione può rivelare l'identità del servizio, la root dei repository, l'indirizzo di ascolto e se la registrazione è disabilitata. Un listener accessibile solo tramite loopback è comunque raggiungibile dagli utenti locali. Le versioni di Gogs fino alla 0.13.3 presentano un problema di scrittura di file tramite symlink in `PutContents`, autenticato ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): chi può scrivere nel repository può inviare un symlink e poi indirizzare la scrittura dell'API attraverso di esso. L'accesso al file risultante avviene con i privilegi del processo Gogs, quindi un'istanza eseguita da root richiede attenzione immediata. Verifica la correzione installata e i requisiti di autenticazione prima di affermare che il percorso è sfruttabile; un errore dell'API non dimostra che la scrittura del file sia fallita.

## XSS nella descrizione dei repository Gitea e visualizzatori con privilegi elevati

Gitea 1.22.0 consentiva l'esecuzione di JavaScript memorizzato nella descrizione di un repository ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); la versione 1.22.1 ha corretto il problema. Un utente che può modificare una descrizione può influire su una sessione del browser con privilegi più elevati, se quell'utente visualizza il repository e attiva il link malevolo. L'identità del browser può quindi esporre contenuti di repository privati o altri dati dell'applicazione. Un'escalation locale separata richiede una credenziale o un permesso accessibile tramite tali contenuti, per esempio una password di amministratore riutilizzata; il solo proprietario del processo Gitea non dimostra un impatto root. Controlla la versione installata, i permessi di modifica della descrizione, il flusso di lavoro del visualizzatore e l'interazione effettiva con il browser prima di affermare che la catena è sfruttabile.

## API di provisioning Cobbler

Il servizio di gestione di Cobbler espone un'API XML-RPC, comunemente sulla porta `25151`. Controlla il listener e il proprietario del processo `cobblerd` prima di valutarne l'impatto; un'API accessibile solo tramite loopback può comunque essere raggiunta da un utente sull'host. Esamina i moduli di autenticazione e autorizzazione in `/etc/cobbler/modules.conf`, le impostazioni del servizio in `/etc/cobbler/settings` o `/etc/cobbler/settings.yaml` e i permessi di `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` e `/var/lib/cobbler/web.ss`. I file digest e delle chiavi segrete condivise contengono materiale relativo alle credenziali: annota se sono leggibili senza stamparne il contenuto per impostazione predefinita.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** è un bypass dell'autenticazione XML-RPC in Cobbler dalla versione 3.0.0 alla 3.2.2 e dalla 3.3.0 alla 3.3.6. Un errore di lettura del secret condiviso restituiva il valore prevedibile `-1`, che l'API accettava come password. Le correzioni corrispondenti sono le versioni 3.2.3 e 3.3.7. La versione di un pacchetto è un indizio: prima di segnalare un'esposizione, verifica il codice distribuito e l'eventuale applicazione di una correzione retroportata.

Una sessione API autenticata può consentire l'esecuzione di operazioni privilegiate se `cobblerd` viene eseguito come root. Nelle implementazioni vulnerabili, `background_import` passa `rsync_flags` controllato dall'utente a un comando shell e il rendering di un template Cheetah di installazione automatica controllato dall'utente può eseguire codice Python. Prima di testare uno dei due percorsi, controlla le autorizzazioni API e la versione installata. Limita l'accesso all'API di gestione, applica la correzione al bypass di autenticazione e consenti la lettura dei file di configurazione e delle credenziali solo agli amministratori del servizio.

## Configurazione di Motion e motionEye

Esamina `/etc/motioneye/motioneye.conf` per trovare `conf_path`, quindi controlla `motion.conf` e un numero limitato di file `camera-*.conf` in quella directory. Segnala se è presente un hash `# @admin_password` leggibile, senza stamparlo. [Le versioni precedenti di motionEye creavano questi file con permessi di lettura troppo ampi](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); la correzione è inclusa nella versione 0.44.0. Controlla insieme le impostazioni Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` e `webcontrol_localhost`: il controllo avanzato (`2` o `3`) senza autenticazione può esporre operazioni potenti a un utente locale, anche con un listener in loopback. [Motion documenta i valori e le impostazioni predefinite](https://motion-project.github.io/motion_config.html).

Prima della versione 0.43.1b5, una sessione admin su motionEye poteva trasformare un'impostazione del nome file della videocamera in esecuzione di comandi quando Motion la elaborava ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Prima di segnalare un'escalation, verifica la versione in esecuzione, l'identità del servizio, la disponibilità di un percorso di autenticazione utilizzabile e la configurazione di una videocamera. La sola configurazione non dimostra che il servizio sia in esecuzione o disponga di privilegi.

Il nome di un servizio o un pacchetto installato sono solo indizi. Il confine dei privilegi dipende dalla combinazione di input raggiungibili, identità del processo, configurazione scrivibile e comando o file che controlla in ultima istanza.

## Emulatori AWS locali e credenziali archiviate

Un utente host potrebbe raggiungere un emulatore compatibile con AWS in esecuzione in un container tramite il suo endpoint loopback pubblicato. Prima di valutare l'accesso a [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) o [KMS](https://docs.localstack.cloud/aws/services/kms/), verifica il listener attivo, l'endpoint e l'account selezionati dal client e le impostazioni di autorizzazione installate nell'emulatore. In LocalStack, [l'applicazione delle policy IAM è un'impostazione separata](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); non dedurre i permessi API effettivi basandoti solo su un file di credenziali, una policy IAM o un listener. Verifica il comportamento della versione e della configurazione installate.

Un secret archiviato è utile per un'escalation locale solo se l'identità API corrente può recuperarlo e un account separato con privilegi superiori accetta la credenziale ottenuta. Un blob locale cifrato richiede anche l'accesso in lettura al file, la chiave KMS corrispondente e utilizzabile e l'autorizzazione effettiva alla decifratura. Per una [chiave KMS asimmetrica](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la richiesta di decifratura deve specificare l'algoritmo usato per cifrare il blob. Per l'inventario automatico degli host, limitati alle evidenze relative a processi, listener, percorsi di configurazione e permessi dei file; durante la normale enumerazione, non richiedere né stampare i valori dei secret o il testo in chiaro decifrato.
