# Services Web locaux et d’authentification

{{#include ../../banners/hacktricks-training.md}}

Un shell Linux donne une vue côté hôte des services Web et d’authentification : arguments des processus, sockets en écoute, fichiers d’unités, configuration, journaux et interfaces accessibles uniquement en local. Utilisez cette vue pour relier un service accessible au compte et aux fichiers qu’il utilise réellement.

## Cartographier la pile Web locale

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Inspectez les noms de virtual hosts, les racines des documents, les routes de proxy, les répertoires d’upload, les paramètres d’exécution de PHP et les fichiers de configuration contenant des identifiants. Un listener sur l’interface loopback peut être accessible via un proxy ou un tunnel SSH. Pour tester un virtual host nommé sur un listener local, envoyez l’en-tête `Host` attendu ou utilisez `curl --resolve` avec l’adresse et le port corrects. L’énumération des virtual hosts peut également révéler des noms absents de la réponse par défaut. Vérifiez si Apache autorise les overrides `.htaccess` et si les chemins d’upload peuvent exécuter du PHP avant de considérer un répertoire d’upload accessible en écriture comme un vecteur d’exécution de code. Une source map JavaScript déployée peut révéler des chemins de sources ou des secrets côté client ; considérez les valeurs récupérées comme des indices et vérifiez les privilèges réels qui leur sont associés. Pour les vérifications spécifiques au web, consultez [Apache](../../network-services-pentesting/pentesting-web/apache.md) et [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Avec Apache et [mpm-itk](https://mpm-itk.sesse.net/), un `AssignUserID` actif peut exécuter un virtual host sous un autre utilisateur et groupe. Si un compte moins privilégié peut écrire un script dans le `DocumentRoot` de cet hôte, vérifiez si une route accessible l’exécute réellement avec l’identité attribuée. Confirmez que le module est chargé, vérifiez la configuration effective du virtual host (y compris les overrides d’identité basés sur des expressions), les permissions d’écriture et de recherche dans le répertoire, le gestionnaire de scripts et l’accès au listener. Une directive mise en évidence ou un répertoire accessible en écriture ne prouve pas à lui seul une exécution entre utilisateurs.

Un répertoire personnel publié par un serveur web peut exposer des archives de sauvegarde de fichiers d’identité SSH, même si le répertoire `.ssh` actif est privé. Par exemple, le paramètre [`homedirs_public` de Nostromo](https://www.nazgul.ch/dev/nostromo_man.html) sélectionne un sous-répertoire servi depuis les répertoires personnels des utilisateurs. La découverte d’une archive via son seul chemin constitue un indice : vérifiez le mapping effectif du serveur, la possibilité de la lire localement ou l’autorisation HTTP, le contenu de l’archive, la passphrase de la clé privée et si le compte correspondant accepte effectivement cette clé. N’extrayez pas les archives et n’affichez pas le contenu des clés lors de l’énumération de routine d’un hôte.

Une sauvegarde lisible d’une application web locale plus privilégiée peut révéler la logique d’authentification et de lecture de fichiers, même si son code source actif est inaccessible. Comparez la sauvegarde au service déployé avant de vous y fier. En particulier, un cookie construit en chiffrant du texte contrôlé par l’appelant, suivi d’un secret et d’un indicateur de rôle, mérite d’être examiné si l’application utilise des blocs ECB déterministes, renvoie de nouveaux cookies pour du texte choisi et découpe ensuite la valeur déchiffrée sur un délimiteur non échappé. [NIST explique le mapping indépendant et répétable des blocs en mode ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a) ; cette propriété peut permettre une comparaison avec une entrée choisie, mais elle n’accorde pas à elle seule un rôle supérieur. Confirmez la route active, les prérequis de session, le parser exact et le flux de données, l’identité du service ainsi qu’une action privilégiée distincte ou un chemin de lecture de fichiers. L’inventaire passif doit signaler les métadonnées des sauvegardes et le propriétaire du listener, sans lire le contenu des archives ni envoyer de sondes d’authentification.

La même approche d’examen du code source s’applique à un service local privilégié **non HTTP**, comme une interface personnalisée reposant sur SSH. Si une sauvegarde accessible du code source montre une commande qui accepte un chemin de fichier choisi par l’appelant, vérifiez son mécanisme d’authentification, la façon dont elle résout le chemin et si elle prouve que le fichier résolu se trouve toujours sous un répertoire prévu avant de l’ouvrir. En Go, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) nettoie un chemin, mais n’en garantit pas le confinement. Confirmez que la sauvegarde correspond à la version en cours d’exécution, que le listener est accessible, que le compte moins privilégié peut utiliser la commande et que le processus peut lire la cible ; posséder une clé SSH lisible est une question distincte des règles d’authentification. Signalez les chemins des archives sources et le propriétaire du service sans extraire le contenu des archives ni les clés dans la sortie automatisée.

Un pool PHP-FPM en écoute sur l’interface loopback TCP peut être accessible à un autre compte local, même si le site web est protégé par authentification. [PHP avertit qu’un client capable de se connecter à FastCGI peut contrôler les paramètres de requête, notamment `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Examinez les paramètres `listen` et `listen.allowed_clients` du pool, ainsi que le listener actif, l’UID des workers, un chemin de script existant et toute restriction `security.limit_extensions` ou `php_admin_value`. Les fichiers de configuration des pools peuvent contenir des identifiants dans des directives `env[...]` ; l’inventaire automatisé doit donc signaler leurs chemins plutôt que leur contenu. Un fichier de configuration ou un port ne prouve pas à lui seul l’existence d’un chemin d’exécution entre utilisateurs ; consultez le [guide FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md) pour les détails du protocole.

Pour une API locale privilégiée, suivez aussi bien l’autorisation que l’exécution de code. Un rôle de base de données que le compte moins privilégié peut modifier peut débloquer une route d’API, mais la frontière suivante dépend de l’implémentation de cette route. Par exemple, fusionner le JSON d’une requête dans un objet JavaScript puis appeler [`child_process.exec`](https://nodejs.org/api/child_process.html) justifie d’examiner le [flux de données entre la pollution de prototype et l’exécution](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Vérifiez la bibliothèque/version de fusion réellement utilisée, la validation des entrées, la route accessible, l’identité du processus et les options du processus enfant ; un listener Node appartenant à root ou le nom d’une dépendance vulnérable ne constitue qu’un indice.

Les CMS reposant sur des fichiers peuvent stocker les vérificateurs de mot de passe administrateur en dehors des fichiers de configuration `.php` classiques. On peut notamment trouver `data/database.js` ou `data/settings/pass.php` dans le site. Vérifiez le propriétaire et les permissions de lecture des fichiers avant de les examiner manuellement, et ne faites pas apparaître les hashes dans une sortie automatisée partagée. Un mot de passe d’application récupérable constitue une frontière de privilèges distincte d’un compte Unix : vérifiez toute réutilisation supposée pour le compte concerné et la méthode d’authentification autorisée.

Le contrôleur d’authentification d’une application peut également contenir un mot de passe de connexion littéral dans son code source plutôt que dans un fichier de configuration. Si un utilisateur moins privilégié peut lire le contrôleur déployé, examinez localement sa vérification d’authentification et ne faites pas apparaître de valeur dans la sortie d’énumération partagée. Confirmez que le chemin de code est actif, que le mot de passe est valide pour l’application et qu’un compte Unix distinct et plus privilégié accepte effectivement ce même mot de passe avant de conclure à une élévation locale de privilèges. Le nom d’un fichier de contrôleur n’est qu’un indice justifiant un examen.

Dolibarr stocke les paramètres de connexion à la base de données, notamment `dolibarr_main_db_pass`, dans `htdocs/conf/conf.php` ([référence de configuration](https://wiki.dolibarr.org/index.php/Configuration_file)). Un fichier lisible constitue un indice de la présence d’identifiants ; seule une réutilisation de mot de passe vérifiée pour un autre compte ou une autre permission de base de données permettrait d’en faire un vecteur d’élévation locale de privilèges. Vérifiez d’abord les permissions et évitez d’afficher la valeur dans la sortie automatisée.

Le fichier de configuration du paquet Linux de GitLab est généralement `/etc/gitlab/gitlab.rb`, mais des déploiements peuvent en conserver des copies lisibles ailleurs. [GitLab indique](https://docs.gitlab.com/omnibus/settings/smtp/) que ce fichier peut contenir `gitlab_rails['smtp_password']`, bien que les paramètres SMTP chiffrés puissent stocker le mot de passe ailleurs que dans le fichier en texte clair. Considérez une configuration lisible comme un indice de la présence d’identifiants : vérifiez qu’elle est active, que l’identifiant est toujours valide et qu’un compte spécifique plus privilégié l’accepte avant de conclure à une réutilisation de mot de passe. Par ailleurs, [GitLab exécute `gitlab.rb` comme du code Ruby avec les privilèges de root lors de `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/) ; pour qu’un fichier actif accessible en écriture ou un fichier `from_file` inclus constitue un constat d’exécution, il faut qu’une véritable voie de reconfiguration privilégiée existe. Un aperçu de configuration peut exposer des identifiants ; traitez sa sortie comme sensible et partagez plutôt les chemins et les permissions.

Une installation Mattermost auto-hébergée peut conserver `SqlSettings.DataSource` dans `/opt/mattermost/config/config.json` ; [Mattermost documente](https://docs.mattermost.com/deployment-guide/server/troubleshooting) à la fois ce chemin habituel et les déploiements où la configuration active est stockée dans une base de données. Un fichier lisible peut exposer un identifiant de base de données de l’application, mais ne prouve ni l’accès à la base de données ni l’accès à root sous Unix. Vérifiez la source de configuration active, les droits réels du rôle de base de données, tout mot de passe d’application récupéré séparément et si ce mot de passe fonctionne pour un compte Unix spécifique et plus privilégié. Le format des hashes de mots de passe peut varier selon les versions de Mattermost ; lors de l’énumération, consignez le chemin de configuration et les métadonnées d’accès sans afficher la chaîne de connexion ni interroger la base de données.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Filtrez les résultats de virtual-host par rapport à la taille de la réponse par défaut ou à une autre référence stable afin que chaque nom deviné ne semble pas valide. Une source map n'est utile que si elle est effectivement déployée ou lisible d'une autre manière.

Les reverse proxies peuvent modifier les en-têtes client auxquels une application fait confiance. Comparez les requêtes directes et celles passant par un proxy avant de supposer que `X-Forwarded-For`, `X-Forwarded-Host` ou des en-têtes similaires établissent l'identité de l'appelant. Examinez ensemble la configuration du proxy et celle de l'application.

Si PHP copie `$_SERVER['HTTP_X_FORWARDED_FOR']` dans une chaîne passée à [`system()`](https://www.php.net/manual/en/function.system.php), vérifiez si le chemin de requête accessible permet à l'appelant de fournir un en-tête et si les métacaractères shell parviennent inchangés dans cette chaîne. Une commande telle que `sudo iptables` intégrée au début ne fait **pas** exécuter comme root les commandes suivantes séparées par le shell ; celles-ci s'exécutent avec l'identité du worker web, sauf si une règle sudo effective distincte autorise une élévation de privilèges. Confirmez l'identité du worker, l'autorisation exacte de `sudo -l` et ses exigences d'authentification, ainsi que les limites des arguments de la commande avant d'affirmer qu'il existe un chemin vers root. Examinez le code source et la politique sans envoyer de tentative d'injection lors de l'énumération habituelle de l'hôte.

## APIs loopback privilégiées après un foothold web

Un shell obtenu dans un processus web peut appeler des services HTTP locaux, même lorsque leurs listeners sont liés à `127.0.0.1`. Dans la version vulnérable de Control Web Panel signalée, le tableau de bord du compte s'exécute en tant qu'utilisateur d'hébergement, mais l'API utilisateur sur `https://127.0.0.1:2302` s'exécute en tant que root. Sa route POST `/v1/restoredatabase/` omet la vérification du jeton d'accès et transmet le champ `file` à `shell_exec('mysql ... < ' . $file)`. Depuis un foothold avec un compte d'hébergement, les séparateurs shell dans `file` s'exécutent donc en tant que root. Confirmez à la fois le contrôle d'accès de la route et l'identité effective du processus API ; une liaison loopback seule n'est pas une authentification. Voir [PHP execution after redirect](../../pentesting-web/login-bypass/#php-execution-after-redirect) pour une façon d'obtenir ce foothold. Les failles signalées ont été entièrement corrigées dans CWP 1.29.<sup>[[1]](#references)</sup>

```bash
curl -sk 'https://127.0.0.1:2302/v1/restoredatabase/' \
  --data-urlencode 'file=/dev/null ; id > /tmp/root-proof ; echo'
```

La même API présente également une faille distincte au niveau du contrôle d’authentification : `access_token()` insère le token fourni dans `WHERE authorization_code='$access_token' AND client_id='$user'`. Une ligne `UNION` comportant les colonnes attendues et une date d’expiration future peut satisfaire la vérification du token tout en neutralisant la condition d’origine sur l’ID client. Cela déverrouille des routes protégées telles que `/v1/newpass/`, où la valeur brute de `user` est ajoutée à une commande shell `passwd` exécutée par root. L’injection du token contourne le contrôle d’accès ; l’exécution de commandes dépend toujours de ce second point d’injection. Voir [contournement de l’authentification par injection SQL](../../pentesting-web/login-bypass/#sql-injection-authentication-bypass).<sup>[[1]](#references)</sup>

Pour le contrôle d’accès à six colonnes divulgué, le token injecté peut fournir une date d’expiration future et neutraliser le prédicat restant ; la structure des colonnes est propre à cette version.<sup>[[1]](#references)</sup>

```sql
' UNION SELECT 'a','x','c','d','2099-01-01 00:00:00','f' -- -
```

Une route distincte `/v1/user_panel_dashboard/`, sans token, insère `user` dans une requête de recherche dans `oauth_clients`. Il s'agit d'une lecture aveugle de la base de données avec la connexion MySQL-root de l'API, **et non** d'une exécution en tant que root du système d'exploitation : le serveur MySQL s'exécute sous l'utilisateur OS `mysql`. Lorsque la table interrogée est vide, une [sonde de temporisation à table dérivée constante](../../pentesting-web/sql-injection/#exploiting-time-based-sqli) permet d'éviter de perdre le délai à cause de l'absence de lignes.<sup>[[1]](#references)</sup>

## Identifiants de connexion dans les journaux d'accès

Si une application soumet un formulaire de connexion avec `GET`, le nom d'utilisateur et le mot de passe peuvent devenir des paramètres de requête dans l'URI de la requête. Une requête `POST` peut également contenir une chaîne de requête ; utiliser `POST` ne masque pas un secret placé par inadvertance dans l'URI, y compris un mot de passe saisi dans un champ sans rapport du formulaire. La [ligne de requête des journaux d'accès courants d'Apache](https://httpd.apache.org/docs/2.4/logs.html) enregistre la méthode et l'URI, y compris sa chaîne de requête, lorsque le format configuré utilise `%r`. Un compte autorisé à lire ces journaux, par exemple via le groupe `adm` sur certains systèmes Linux, peut donc y trouver une piste d'identifiant. Vérifiez le format réel du journal et les permissions, puis confirmez que la valeur est un secret, que le compte l'accepte et qu'elle permet de franchir une frontière de privilèges. Ne supposez pas que le corps de la requête a été journalisé et ne copiez pas les valeurs candidates dans une sortie partagée.

N'inspectez que les journaux d'accès lisibles et évitez d'inclure les valeurs d'identifiants dans les sorties de commandes partagées. Les longues lignes de requête peuvent également contenir un référent et un agent utilisateur ; un filtre limité aux lignes courtes risque donc de masquer la requête recherchée. Les emplacements courants des journaux d'accès Apache, httpd et Nginx sont `/var/log/apache2/access.log`, `/var/log/httpd/access_log` et `/var/log/nginx/access.log`. Les journaux archivés peuvent contenir d'anciens identifiants. [L'accès aux fichiers journaux via LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) est un autre moyen d'accéder aux mêmes données.

Les journaux d'authentification des applications peuvent également exposer un mot de passe saisi par erreur dans le champ **nom d'utilisateur** lors d'une tentative de connexion échouée. Commencez par vérifier que le journal est lisible et que son format consigne le nom d'utilisateur soumis ; examinez uniquement une petite portion pertinente en local et ne copiez pas les identifiants candidats dans une sortie partagée. Un nom d'utilisateur qui ressemble à un mot de passe constitue une piste, pas la preuve d'un mot de passe valide ni de privilèges supérieurs. Vérifiez le compte visé et toute réutilisation du mot de passe sur le service ou le compte Unix concerné avant de conclure à une élévation de privilèges.

Un gestionnaire de connexion web modifiable mérite un examen distinct lorsqu'un client planifié, exécuté sous une autre identité, soumet des identifiants à ce point de terminaison. Confirmez que le gestionnaire **actif** est modifiable, ainsi que le calendrier réel du client et son chemin de requête, l'identité à laquelle appartiennent ses identifiants et la validité indépendante de ce mot de passe d'application pour un compte du système d'exploitation doté de privilèges supérieurs. Une page modifiable ou un processus récurrent ne suffit pas à établir cette élévation. Un inventaire passif doit signaler les permissions des chemins et les métadonnées des tâches sans modifier le gestionnaire ni collecter de mots de passe.

Les journaux JSON EVE de Suricata peuvent également consigner les commandes FTP `USER` et `PASS`, avec leur champ `command_data`, lorsque la journalisation des événements FTP est activée. Vérifiez la lisibilité de `/var/log/suricata/eve*.json*`, y compris des fichiers archivés ou compressés, avant d'examiner en local une petite portion pertinente. Un fichier EVE lisible n'est qu'une piste : confirmez que les événements FTP ont été journalisés, que les données comprennent un identifiant utilisable et qu'il permet de franchir une frontière de privilèges. Évitez d'afficher `command_data` dans les sorties d'énumération partagées. Suricata documente les [champs des événements FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) et la [rotation EVE et ses variantes de noms de fichiers](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Configuration Apache générée et journaux redirigés vers des commandes

[remco](https://github.com/HeavyHorst/remco) peut surveiller un backend clé/valeur, générer un fichier de configuration Apache à partir d'un modèle et exécuter une commande de rechargement. Examinez l'identité du processus remco en cours d'exécution, la source et la destination configurées du modèle, les préfixes de clés surveillés et vérifiez si une valeur du backend est insérée directement dans une directive Apache telle que `ServerName`. La présence d'un écouteur de backend local ne prouve pas à elle seule que l'utilisateur actuel peut écrire une clé surveillée ; vérifiez l'authentification et les permissions du backend avant de conclure à une élévation de privilèges.

Un saut de ligne non échappé dans une valeur de backend modifiable peut transformer la valeur d'une directive prévue en directives Apache supplémentaires. Les [journaux Apache redirigés vers des commandes](https://httpd.apache.org/docs/2.4/logs.html#piped) sont particulièrement sensibles : `CustomLog` ou `ErrorLog` avec une commande précédée de `|` démarre un processus auxiliaire sous l'identité du processus parent httpd, souvent root ; `|$` demande à Apache d'utiliser un shell. Examinez la configuration générée et son processus de rechargement sans modifier les données du backend ni redémarrer le service pendant l'énumération. Gardez privée la commande complète redirigée, car ses arguments peuvent contenir des secrets.

## Identités d'authentification et de service

Le fichier de contrôle de Monit se trouve généralement dans `~/.monitrc` ou `/etc/monitrc`, mais `monit -c` peut désigner un autre chemin. Un fichier lisible peut contenir des entrées `set httpd` et `allow user:password` pour son interface web, souvent sur le port local 2812. Vérifiez le propriétaire et les permissions du fichier avant de l'examiner, et évitez d'inclure les mots de passe dans les sorties d'énumération partagées. Les identifiants web ne confèrent que le rôle Monit configuré ; les utilisateurs en lecture seule ne peuvent pas déclencher d'actions de contrôle. Une élévation via un compte Unix distinct nécessite une réutilisation de mot de passe confirmée ou une action Monit privilégiée que le rôle authentifié peut réellement déclencher. Consultez la [documentation de Monit sur le fichier de contrôle et l'authentification](https://www.mmonit.com/monit/documentation/monit.html).

Pour Webmin, `/etc/webmin/miniserv.conf` indique les paramètres du serveur et `/etc/webmin/webmin.acl` consigne les modules auxquels les utilisateurs peuvent accéder ; [Webmin documente les limites liées à l'attribution des modules](https://webmin.com/docs/development/creating-modules/). Un mot de passe Unix ou un fichier ACL lisible ne donne pas à lui seul accès à une session Webmin. Confirmez la configuration réelle de l'authentification, l'accessibilité de l'écouteur, le compte authentifié, les permissions effectives sur le module Package Updates, la version du code installé ou le correctif du fournisseur, ainsi que l'identité du processus Webmin. Dans les versions vulnérables jusqu'à la 1.910 incluse, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) permettait à un compte disposant de cette permission de module d'exécuter des commandes via son gestionnaire de mises à jour. Lors d'une énumération passive, indiquez les chemins de configuration et les permissions sans afficher d'identifiants ni tenter d'effectuer une mise à jour.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) régit l’authentification propre à chaque service ; des chemins de politiques ou de modules accessibles en écriture peuvent modifier le comportement de connexion.
- La configuration LDAP/SSSD peut révéler les points de terminaison d’annuaire, les identités de liaison et les règles d’accès. Un mot de passe de liaison récupéré peut permettre d’effectuer des requêtes LDAP au-delà du compte OS actuel ; testez l’identité de liaison exacte et les ACL de l’annuaire. Vérifiez les permissions des fichiers avant d’inspecter les secrets ; [Linux Active Directory](../user-information/linux-active-directory.md) et [FreeIPA](freeipa-pentesting.md) traitent de l’utilisation des tickets et des annuaires.
- Les alias Postfix peuvent acheminer les courriels reçus vers des commandes locales. Si un utilisateur moins privilégié peut modifier le script référencé, la distribution du courrier peut déclencher son code sous l’identité de distribution. Vérifiez les tables d’alias et le propriétaire du script avant d’affirmer que cette voie est exploitable ; voir [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins et d’autres services CI peuvent exécuter des tâches sous un compte local puissant. Inspectez l’utilisateur du service, les chemins de tâches ou d’espaces de travail accessibles en écriture et l’interface d’administration locale avant de tester un pipeline ou un plugin. Examinez également les **identifiants accessibles à une tâche** et le compte auquel ils permettent de s’authentifier : un Pipeline utilisant l’étape [SSH Agent](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) peut accéder à un hôte en tant qu’utilisateur associé à l’identifiant SSH, même si Jenkins s’exécute sous un compte Unix moins privilégié. Vérifiez que l’identité Jenkins actuelle dispose de `Job/Create`, `Job/Configure` ou d’un autre moyen effectif de modifier le Pipeline, que l’identifiant est accessible à cette tâche et que le compte SSH cible accepte la clé avant d’affirmer qu’il y a élévation de privilèges sur l’hôte. Le nom d’affichage ou l’ID d’un identifiant ne suffit pas à établir ces conditions. Jenkins avertit que les créateurs de tâches et, souvent, les personnes pouvant les configurer peuvent utiliser arbitrairement les identifiants accessibles dans leur périmètre ; la [portée des identifiants](https://www.jenkins.io/doc/book/security/credentials/) et la [confiance accordée aux Pipelines](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) comptent donc autant que l’UID du service. Ne divulguez pas les valeurs des identifiants ni les clés privées dans les résultats d’énumération partagés.

## Écriture de fichiers dans les dépôts Gogs

Pour un service Gogs local, mettez en corrélation le propriétaire du processus `gogs web`, la version de l’exécutable et `custom/conf/app.ini`. La configuration peut révéler l’identité du service, la racine des dépôts, l’adresse d’écoute et si l’inscription est désactivée. Même une adresse d’écoute limitée à la boucle locale reste accessible aux utilisateurs locaux. Les versions de Gogs jusqu’à la version 0.13.3 incluse présentent un problème d’écriture de fichiers par lien symbolique dans `PutContents`, nécessitant une authentification ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)) : une personne pouvant écrire dans un dépôt peut y enregistrer un lien symbolique, puis faire passer l’écriture de l’API par ce lien. L’accès au fichier obtenu correspond aux privilèges du processus Gogs ; une instance exécutée en tant que root nécessite donc une attention rapide. Vérifiez le correctif déployé et les exigences d’authentification avant d’affirmer qu’une voie est exploitable ; une erreur de l’API ne prouve pas que l’écriture du fichier a échoué.

## XSS dans la description d’un dépôt Gitea et utilisateurs privilégiés qui la consultent

Gitea 1.22.0 permettait d’inclure du JavaScript persistant dans la description d’un dépôt ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)) ; la version 1.22.1 corrigeait le problème. Un utilisateur pouvant modifier une description peut affecter une session de navigateur plus privilégiée si cet utilisateur consulte le dépôt et active le lien malveillant. L’identité de ce navigateur peut alors exposer le contenu de dépôts privés ou d’autres données de l’application. Une élévation de privilèges locale distincte nécessite un identifiant ou une permission accessible par ce contenu, comme un mot de passe administrateur réutilisé ; le propriétaire du processus Gitea ne suffit pas, à lui seul, à établir un impact sur root. Vérifiez la version déployée, les droits de modification des descriptions, le parcours de consultation et l’interaction réelle avec le navigateur avant d’affirmer que cette chaîne est exploitable.

## API de provisionnement Cobbler

Le service de gestion de Cobbler expose une API XML-RPC, généralement sur le port `25151`. Vérifiez l’écoute et le propriétaire du processus `cobblerd` avant d’évaluer son impact ; une API limitée à la boucle locale reste accessible aux utilisateurs de l’hôte. Examinez les modules d’authentification et d’autorisation dans `/etc/cobbler/modules.conf`, les paramètres du service dans `/etc/cobbler/settings` ou `/etc/cobbler/settings.yaml`, ainsi que les permissions sur `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` et `/var/lib/cobbler/web.ss`. Les fichiers de digest et de secret partagé contiennent des identifiants ; consignez s’ils sont lisibles sans en afficher le contenu par défaut.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** est un contournement de l’authentification XML-RPC dans Cobbler 3.0.0 à 3.2.2 et 3.3.0 à 3.3.6. Une erreur de lecture du secret partagé renvoyait la valeur prévisible `-1`, que l’API acceptait comme mot de passe. Les versions correctives sont 3.2.3 et 3.3.7. La version d’un package est une piste ; vérifiez le code déployé et toute correction rétroportée avant de signaler une exposition.

Une session API authentifiée peut offrir un chemin d’exécution privilégié lorsque `cobblerd` s’exécute en tant que root. Dans les implémentations concernées, `background_import` transmet `rsync_flags`, contrôlé par l’utilisateur, à une commande shell, et le rendu d’un modèle Cheetah d’installation automatique contrôlé par l’utilisateur peut évaluer du Python. Vérifiez les permissions de l’API et la version installée avant de tester l’un ou l’autre de ces chemins. Restreignez l’accès à l’API de gestion, corrigez le contournement de l’authentification et veillez à ce que seuls les administrateurs du service puissent lire les fichiers de configuration et d’identifiants.

## Configuration de Motion et motionEye

Examinez `/etc/motioneye/motioneye.conf` pour trouver `conf_path`, puis consultez `motion.conf` et un petit nombre de fichiers `camera-*.conf` dans ce répertoire. Signalez si un hash `# @admin_password` lisible est présent, sans l’afficher. [Les anciennes versions de motionEye créaient ces fichiers avec des permissions de lecture trop larges](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67) ; le correctif est inclus dans la version 0.44.0. Vérifiez conjointement les paramètres Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` et `webcontrol_localhost` : un contrôle avancé (`2` ou `3`) avec l’authentification désactivée peut exposer des opérations puissantes à un utilisateur local, y compris sur un écouteur loopback. [Motion documente les valeurs et les valeurs par défaut](https://motion-project.github.io/motion_config.html).

Avant la version 0.43.1b5, une session administrateur sur motionEye pouvait transformer un paramètre de nom de fichier de caméra en exécution de commande lorsque Motion le traitait ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Vérifiez la version en cours d’exécution, l’identité du service, l’existence d’un chemin d’authentification utilisable et la configuration d’une caméra avant de signaler une élévation de privilèges. La configuration seule ne prouve ni que le service est en cours d’exécution, ni qu’il est privilégié.

Un nom de service ou un package installé n’est qu’une piste. La frontière des privilèges dépend de la combinaison entre les entrées accessibles, l’identité du processus, les fichiers de configuration modifiables et la commande ou le fichier qu’il contrôle en fin de compte.

## Émulateurs AWS locaux et identifiants stockés

Un utilisateur de l’hôte peut accéder à un émulateur compatible avec AWS exécuté dans un conteneur par son point de terminaison loopback publié. Pour évaluer l’accès à [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) ou à [KMS](https://docs.localstack.cloud/aws/services/kms/), recoupez l’écouteur actif, le point de terminaison et le compte sélectionnés par le client, ainsi que les paramètres d’autorisation de l’émulateur installé. Dans LocalStack, [l’application des politiques IAM est un paramètre distinct](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/) ; ne déduisez pas les permissions API effectives d’un fichier d’identifiants, d’une politique IAM ou d’un écouteur pris isolément. Vérifiez le comportement de la version et de la configuration installées.

Un secret stocké n’est utile pour une élévation de privilèges locale que si l’identité API actuelle peut le récupérer et qu’un compte distinct disposant de privilèges plus élevés accepte l’identifiant obtenu. Un blob local chiffré nécessite également un accès en lecture au fichier, la clé KMS correspondante et utilisable, l’algorithme adéquat et les droits de déchiffrement effectifs. Pour une [clé KMS asymétrique](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html), la requête de déchiffrement doit spécifier l’algorithme utilisé pour chiffrer le blob. Limitez l’inventaire automatique de l’hôte aux preuves concernant les processus, les écouteurs, les chemins de configuration et les permissions des fichiers ; ne demandez pas et n’affichez pas de valeurs secrètes ni de texte en clair déchiffré lors d’une énumération courante.
