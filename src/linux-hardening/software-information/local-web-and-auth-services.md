# Local Web और Authentication Services

{{#include ../../banners/hacktricks-training.md}}

Linux shell, web और authentication services का host-side view देता है: process arguments, listeners, unit files, configuration, logs और केवल local interfaces। इस view का इस्तेमाल करके किसी reachable service को उस account और files से जोड़ें जिनका वह वास्तव में इस्तेमाल करती है।

## Local web stack का नक्शा बनाएँ

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Virtual-host names, document roots, proxy routes, upload directories, PHP execution settings और credentials वाली config files की जाँच करें। Loopback listener किसी proxy या SSH tunnel के ज़रिए पहुँच योग्य हो सकता है। Local listener के विरुद्ध किसी नामित virtual host को जाँचने के लिए अपेक्षित `Host` header भेजें या सही address और port के साथ `curl --resolve` का उपयोग करें। Virtual-host enumeration से ऐसे नाम भी सामने आ सकते हैं जो default response में नहीं हैं। Writable upload directory को code execution मानने से पहले जाँचें कि Apache `.htaccess` overrides की अनुमति देता है या नहीं और क्या upload paths में PHP execute हो सकता है। Deployed JavaScript source map से source paths या client-side secrets उजागर हो सकते हैं; मिले हुए values को सुराग मानें और उनके वास्तविक privileges की पुष्टि करें। Web-specific checks के लिए [Apache](../../network-services-pentesting/pentesting-web/apache.md) और [Nginx](../../network-services-pentesting/pentesting-web/nginx.md) देखें।

Apache में [mpm-itk](https://mpm-itk.sesse.net/) के लिए, सक्रिय `AssignUserID` किसी virtual host को अलग user और group के अंतर्गत चला सकता है। यदि कम-privileged account उस host के `DocumentRoot` में script लिख सकता है, तो जाँचें कि कोई पहुँच योग्य route उसे वास्तव में assigned identity के तहत execute करता है या नहीं। पुष्टि करें कि module loaded है, virtual-host configuration प्रभावी है (इसमें expression-based identity overrides भी शामिल हैं), directory में write और search permissions हैं, script handler सही है और listener तक पहुँच है। केवल highlight किया हुआ directive या writable directory cross-user execution साबित नहीं करता।

Web server के ज़रिए प्रकाशित home directory में SSH identity files के backup archives उजागर हो सकते हैं, भले ही live `.ssh` directory private हो। उदाहरण के लिए, [Nostromo की `homedirs_public` setting](https://www.nazgul.ch/dev/nostromo_man.html) user homes से serve की जाने वाली subdirectory चुनती है। केवल path मिलने से वह जाँच का सुराग है: server की प्रभावी mapping, local readability या HTTP authorization, archive contents, private-key passphrase और यह सत्यापित करें कि संबंधित account उस key को स्वीकार करता है या नहीं। Routine host enumeration के दौरान archives extract न करें और key material प्रिंट न करें।

किसी higher-privileged local web app का readable backup authentication और file-read logic उजागर कर सकता है, भले ही उसका live source inaccessible हो। इस पर भरोसा करने से पहले backup की deployed service से तुलना करें। खास तौर पर, caller-controlled text के बाद secret और role flag को encrypt करके बनाया गया cookie जाँच के योग्य है, यदि app deterministic ECB blocks का उपयोग करता है, चुने हुए text के लिए नए cookies लौटाता है और बाद में decrypted value को unescaped delimiter पर split करता है। [NIST, ECB की independent और repeatable block mapping समझाता है](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); यह गुण चुने हुए input की तुलना में मदद कर सकता है, लेकिन अपने आप higher role नहीं देता। Live route, session prerequisites, सटीक parser/data flow, service identity और कोई अलग privileged action या file-read path सत्यापित करें। Passive inventory में backup metadata और listener ownership की जानकारी दें, archive contents पढ़े बिना या authentication probes भेजे बिना।

Source-review का यही तरीका किसी privileged **non-HTTP** loopback service, जैसे custom SSH-backed interface, पर भी लागू होता है। यदि उपलब्ध source backup में ऐसा command दिखता है जो caller द्वारा चुना गया file path स्वीकार करता है, तो उसका authentication gate, path resolve करने का तरीका और file खोलने से पहले यह सुनिश्चित करने की प्रक्रिया जाँचें कि resolved file इच्छित directory के भीतर ही रहे। Go में, [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) path को साफ करता है, लेकिन यह containment लागू नहीं करता। पुष्टि करें कि backup running build से मेल खाता है, listener तक पहुँचा जा सकता है, कम-privileged account command का उपयोग कर सकता है और process target को पढ़ सकता है; readable SSH key होना एक अलग login-policy का प्रश्न है। Source archive paths और service ownership की जानकारी दें, archive contents या keys को automated output में extract किए बिना।

TCP loopback पर सुनने वाले PHP-FPM pool तक कोई दूसरा local account पहुँच सकता है, भले ही उसकी website पर authentication हो। [PHP चेतावनी देता है कि FastCGI से connect कर सकने वाला client request settings नियंत्रित कर सकता है, जिनमें `auto_prepend_file` भी शामिल है](https://www.php.net/manual/en/install.fpm.php)। Pool की `listen` और `listen.allowed_clients` settings को live listener, worker UID, किसी मौजूदा script path और `security.limit_extensions` या `php_admin_value` restrictions के साथ जाँचें। Pool configuration files में `env[...]` directives के तहत credentials हो सकते हैं, इसलिए automated inventory में उनके contents के बजाय paths दें। केवल config file या port cross-user execution route साबित नहीं करता; protocol details के लिए [FastCGI guide](../../network-services-pentesting/9000-pentesting-fastcgi.md) देखें।

किसी privileged local API के लिए code execution के साथ authorization flow भी trace करें। Lower-privileged account जिस database role को बदल सकता है, वह API route खोल सकता है, लेकिन अगली security boundary उस route के implementation पर निर्भर करती है। उदाहरण के लिए, request JSON को JavaScript object में merge करना और फिर [`child_process.exec`](https://nodejs.org/api/child_process.html) call करना, [prototype-pollution-to-execution dataflow](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md) की जाँच का कारण है। वास्तविक merge library/version, input validation, पहुँच योग्य route, process identity और child-process options सत्यापित करें; केवल root-owned Node listener या vulnerable dependency का नाम एक सुराग है।

File-backed CMS stores में administrator password verifiers सामान्य `.php` configuration files के बाहर भी हो सकते हैं। उदाहरणों में किसी site का `data/database.js` या `data/settings/pass.php` शामिल है। Manual review से पहले file ownership और readability जाँचें, और hashes को automated shared output में न रखें। Recover किया जा सकने वाला application password, Unix account से अलग privilege boundary है: password reuse के किसी दावे को संबंधित account और अनुमत authentication method के लिए सत्यापित करें।

किसी application का authentication controller configuration file के बजाय source code में literal login password भी रख सकता है। यदि lower-privileged user deployed controller पढ़ सकता है, तो authentication comparison की स्थानीय स्तर पर जाँच करें और किसी भी value को shared enumeration output में न रखें। Local escalation का दावा करने से पहले पुष्टि करें कि code path सक्रिय है, password application के लिए valid है और कोई अलग higher-privileged Unix account वही password स्वीकार करता है। केवल controller filename जाँच का एक सुराग है।

Dolibarr database connection settings, जिनमें `dolibarr_main_db_pass` शामिल है, `htdocs/conf/conf.php` में रखता है ([configuration reference](https://wiki.dolibarr.org/index.php/Configuration_file))। Readable file credentials का सुराग है; केवल अलग से सत्यापित account-password reuse या कोई अन्य database permission ही इसे local privilege escalation बना सकती है। पहले permissions जाँचें और automated output में value प्रिंट न करें।

GitLab Linux package की configuration सामान्यतः `/etc/gitlab/gitlab.rb` होती है, जबकि deployments इसकी readable copies कहीं और रख सकते हैं। [GitLab के दस्तावेज़](https://docs.gitlab.com/omnibus/settings/smtp/) बताते हैं कि इस file में `gitlab_rails['smtp_password']` हो सकता है, हालाँकि encrypted SMTP settings password को plaintext file के बाहर रख सकती हैं। Readable configuration को credentials का सुराग मानें: password reuse का दावा करने से पहले सत्यापित करें कि यह सक्रिय है, credential अभी भी valid है और कोई विशिष्ट higher-privileged account इसे स्वीकार करता है। अलग से, [GitLab `gitlab-ctl reconfigure` के दौरान root के अंतर्गत `gitlab.rb` को Ruby code की तरह चलाता है](https://docs.gitlab.com/omnibus/settings/configuration/); execution finding के लिए writable active file या included `from_file` के साथ वास्तविक privileged reconfigure path होना ज़रूरी है। Config preview में credential values उजागर हो सकते हैं, इसलिए उसके output को संवेदनशील मानें और इसके बजाय paths और permissions साझा करें।

Self-hosted Mattermost installation में `SqlSettings.DataSource`, `/opt/mattermost/config/config.json` में हो सकता है; [Mattermost दस्तावेज़](https://docs.mattermost.com/deployment-guide/server/troubleshooting) इस सामान्य path और उन deployments, दोनों के बारे में बताते हैं जो active configuration को database में रखते हैं। Readable file से application database credential उजागर हो सकता है, लेकिन इससे database access या Unix root access साबित नहीं होता। Enumeration के दौरान connection string या database query किए बिना active configuration source, database role के वास्तविक अधिकार, अलग से recover किए गए किसी application password और यह कि password किसी विशिष्ट higher-privileged Unix account के लिए काम करता है या नहीं, सत्यापित करें। Mattermost versions के बीच password-hash format बदल सकता है; config path और access metadata दर्ज करें, लेकिन connection string प्रिंट न करें।

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

वर्चुअल-होस्ट के नतीजों को डिफ़ॉल्ट रिस्पॉन्स साइज़ या किसी अन्य स्थिर आधार से फ़िल्टर करें, ताकि हर अनुमानित नाम वैध न लगे। Source map तभी उपयोगी है, जब वह वास्तव में डिप्लॉय किया गया हो या किसी अन्य तरीके से पढ़ा जा सकता हो।

Reverse proxy यह बदल सकते हैं कि एप्लिकेशन किन client headers पर भरोसा करता है। यह मानने से पहले कि `X-Forwarded-For`, `X-Forwarded-Host` या ऐसे ही headers कॉलर की पहचान स्थापित करते हैं, direct और proxied requests की तुलना करें। Proxy और application configuration को साथ में देखें।

अगर PHP `$_SERVER['HTTP_X_FORWARDED_FOR']` को `[`system()`](https://www.php.net/manual/en/function.system.php)` को दिए जाने वाले string में कॉपी करता है, तो देखें कि क्या अनुरोध का पहुँच योग्य रास्ता कॉलर द्वारा दिया गया header स्वीकार करता है और क्या shell metacharacters उस string तक बिना बदले पहुँचते हैं। शुरुआत में एम्बेड किया गया `sudo iptables` जैसा command बाद के shell-separated commands को root के रूप में नहीं चलाता; वे web worker के रूप में चलते हैं, जब तक कि कोई अलग प्रभावी sudo rule privilege escalation की अनुमति न देता हो। Root तक पहुँच का दावा करने से पहले worker की identity, `sudo -l` का सटीक grant और authentication की आवश्यकता, तथा command की argument boundary की पुष्टि करें। सामान्य host enumeration के दौरान injection probe भेजे बिना source और policy देखें।

## Access logs में login credentials

अगर कोई एप्लिकेशन `GET` से login form सबमिट करता है, तो username और password request URI में query parameters बन सकते हैं। `POST` request में भी query string हो सकती है; `POST` का उपयोग URI में गलती से रखे गए secret को छिपाता नहीं है, इसमें किसी असंबंधित form field में दर्ज किया गया password भी शामिल है। [Apache की सामान्य access-log request line](https://httpd.apache.org/docs/2.4/logs.html) में method और URI, query string सहित, दर्ज होते हैं—जब configured format में `%r का उपयोग हो। इसलिए उन logs को पढ़ने की अनुमति वाला account, उदाहरण के लिए कुछ Linux systems पर `adm` group के ज़रिए, credentials से जुड़ा कोई सुराग पा सकता है। वास्तविक log format और permissions जाँचें, फिर पुष्टि करें कि value एक secret है, account उसे स्वीकार करता है और वह privilege boundary पार करता है। यह न मानें कि request body log की गई थी और संभावित values को shared output में कॉपी न करें।

केवल पढ़े जा सकने वाले access logs देखें और credential values को shared command output से बाहर रखें। लंबी request lines में referrer और user agent भी हो सकते हैं, इसलिए short-line filter उस request को छिपा सकता है जिसमें आपकी रुचि है। Apache, httpd और Nginx के सामान्य access-log paths हैं: `/var/log/apache2/access.log`, `/var/log/httpd/access_log` और `/var/log/nginx/access.log`। Rotated logs में पुराने credentials हो सकते हैं। [LFI के ज़रिए log-file access](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) उसी data तक पहुँचने का एक संबंधित रास्ता है।

Application authentication logs में असफल login के दौरान **username** field में गलती से दर्ज किया गया password भी सामने आ सकता है। पहले पुष्टि करें कि log पढ़ा जा सकता है और उसका format सबमिट किया गया username दर्ज करता है; locally केवल छोटा, प्रासंगिक हिस्सा देखें और संभावित credentials को shared output में कॉपी न करें। Password जैसा दिखने वाला username एक सुराग है, वैध password या अधिक privilege का प्रमाण नहीं। किसी transition का दावा करने से पहले इच्छित account और संबंधित service या Unix account में password reuse की पुष्टि करें।

किसी writable web login handler की अलग से जाँच करना उचित है, जब किसी अन्य identity के अंतर्गत चलने वाला scheduled client उस endpoint पर credentials सबमिट करता हो। **Active** handler पर write access, client का वास्तविक schedule और request path, वह किसके credentials भेजता है, और क्या application password किसी अधिक privileged operating-system account के लिए अलग से मान्य है—इन सबकी पुष्टि करें। केवल writable page या बार-बार चलने वाली process उस transition को साबित नहीं करती। Passive inventory में handler बदले या passwords इकट्ठा किए बिना path permissions और job metadata दर्ज करें।

FTP event logging सक्षम होने पर Suricata के EVE JSON logs FTP `USER` और `PASS` commands को उनके `command_data` सहित दर्ज कर सकते हैं। locally केवल छोटा प्रासंगिक हिस्सा देखने से पहले `/var/log/suricata/eve*.json*` की readability जाँचें, जिसमें rotated या compressed files भी शामिल हों। पढ़ी जा सकने वाली EVE file केवल एक सुराग है: पुष्टि करें कि FTP events log किए गए थे, data में उपयोगी credential है और वह privilege boundary पार करता है। Shared enumeration output में `command_data` प्रिंट न करें। Suricata [FTP event fields](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) और [EVE rotation तथा filename variants](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html) का दस्तावेज़ देता है।

## Generated Apache configuration और piped logs

[remco](https://github.com/HeavyHorst/remco) key/value backend को watch कर सकता है, template को Apache configuration file में render कर सकता है और reload command चला सकता है। चल रहे remco process की identity, उसके configured template source और destination, watch किए जाने वाले key prefixes, और यह जाँचें कि क्या backend value सीधे `ServerName` जैसे Apache directive में डाली जाती है। केवल local backend listener से यह साबित नहीं होता कि मौजूदा user watched key लिख सकता है; escalation का दावा करने से पहले backend authentication और permissions की पुष्टि करें।

किसी writable backend value में unescaped newline एक अपेक्षित directive value को अतिरिक्त Apache directives में बदल सकती है। [Apache piped logs](https://httpd.apache.org/docs/2.4/logs.html#piped) विशेष रूप से संवेदनशील हैं: `|` command वाला `CustomLog` या `ErrorLog` parent httpd identity के तहत helper शुरू करता है, जो अक्सर root होती है; `|$` Apache को shell इस्तेमाल करने के लिए कहता है। Enumeration के दौरान backend data बदले या service restart किए बिना generated configuration और उसके reload path की जाँच करें। पूरा piped command निजी रखें, क्योंकि उसके arguments में secrets हो सकते हैं।

## Authentication और service identities

Monit की control file आम तौर पर `~/.monitrc` या `/etc/monitrc` होती है, लेकिन `monit -c` से कोई दूसरा path चुना जा सकता है। पढ़ी जा सकने वाली file में उसके web interface के लिए `set httpd` और `allow user:password` entries हो सकती हैं, जो अक्सर local port 2812 पर उपलब्ध होता है। File देखने से पहले उसके owner और permissions जाँचें, और password values को shared enumeration output से बाहर रखें। Web credentials केवल configured Monit role की अनुमति देते हैं; read-only users control actions नहीं चला सकते। अलग Unix-account escalation के लिए password reuse या ऐसा privileged Monit action पुष्ट होना ज़रूरी है, जिसे authenticated role वास्तव में चला सके। [Monit control-file और authentication दस्तावेज़](https://www.mmonit.com/monit/documentation/monit.html) देखें।

Webmin के लिए `/etc/webmin/miniserv.conf` में server settings होती हैं और `/etc/webmin/webmin.acl` में दर्ज होता है कि users किन modules तक पहुँच सकते हैं; [Webmin module-grant boundary का दस्तावेज़ देता है](https://webmin.com/docs/development/creating-modules/)। Unix password या पढ़ी जा सकने वाली ACL file अपने आप Webmin session की अनुमति नहीं देती। वास्तविक authentication mapping, पहुँच योग्य listener, authenticated account, प्रभावी Package Updates module permission, installed code या vendor fix, और Webmin process की identity की पुष्टि करें। 1.910 तक के प्रभावित builds में, [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) ने उस module permission वाले account को अपने update handler के ज़रिए commands चलाने की अनुमति दी। Passive enumeration के दौरान credentials प्रिंट किए या update आज़माए बिना configuration paths और permissions दर्ज करें।

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) service-विशिष्ट authentication को नियंत्रित करता है; writable policy या module paths login व्यवहार बदल सकते हैं।
- LDAP/SSSD configuration से directory endpoints, bind identities और access rules का पता चल सकता है। मिला हुआ bind password मौजूदा OS account से आगे की LDAP queries की अनुमति दे सकता है; सटीक bind identity और directory ACLs जाँचें। Secrets देखने से पहले file permissions की समीक्षा करें; [Linux Active Directory](../user-information/linux-active-directory.md) और [FreeIPA](freeipa-pentesting.md) में ticket और directory के उपयोग को शामिल किया गया है।
- Postfix aliases प्राप्त mail को local commands तक pipe कर सकते हैं। अगर कम विशेषाधिकार वाला user संदर्भित script बदल सकता है, तो mail delivery उसके code को delivery identity के अंतर्गत चला सकती है। इस path का दावा करने से पहले alias maps और script ownership की समीक्षा करें; [SMTP and mail service testing](../../network-services-pentesting/pentesting-smtp/README.md) देखें।
- Jenkins और अन्य CI services jobs को किसी शक्तिशाली local account के अंतर्गत चला सकती हैं। Pipeline या plugin की जाँच से पहले service user, writable job/workspace paths और local administration interface देखें। साथ ही **किसी job के लिए उपलब्ध credentials** और उस account की समीक्षा करें, जिसके रूप में वे authenticate कर सकते हैं: [SSH Agent step](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/) का उपयोग करने वाला Pipeline किसी host पर SSH credential के user के रूप में पहुँच सकता है, भले ही Jenkins स्वयं कम विशेषाधिकार वाले Unix account के अंतर्गत चलता हो। Host privilege escalation का दावा करने से पहले पुष्टि करें कि मौजूदा Jenkins identity के पास Pipeline बदलने के लिए `Job/Create`, `Job/Configure` या कोई अन्य प्रभावी तरीका है, credential उस job के scope में है, और target SSH account उस key को स्वीकार करता है। केवल credential का display name या ID इनमें से किसी भी शर्त को सिद्ध नहीं करता। Jenkins चेतावनी देता है कि job बनाने वाले लोग और अक्सर job configure करने वाले लोग, अपने scope में उपलब्ध credentials का मनमाने ढंग से उपयोग कर सकते हैं; इसलिए [credential scope](https://www.jenkins.io/doc/book/security/credentials/) और [Pipeline trust](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) भी service UID जितने ही महत्वपूर्ण हैं। Shared enumeration output में credential values और private keys न रखें।

## Gogs repository में फ़ाइल लेखन

किसी local Gogs service के लिए `gogs web` process के owner का मिलान executable version और `custom/conf/app.ini` से करें। Configuration से service identity, repository root, listener address और registration disabled है या नहीं, इसका पता चल सकता है। केवल loopback पर सुनने वाला listener भी local users के लिए पहुँच योग्य होता है। 0.13.3 तक के Gogs versions में authenticated `PutContents` symlink file-write समस्या है ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): repository writer symlink commit करके फिर API write को उसके ज़रिए निर्देशित कर सकता है। परिणामी file access के पास Gogs process के privileges होते हैं, इसलिए root-owned instance पर तुरंत ध्यान देना चाहिए। उपयोग योग्य path का दावा करने से पहले deployed fix और authentication requirements की पुष्टि करें; API error यह साबित नहीं करता कि file write विफल हुआ।

## Gitea repository description XSS और privileged viewers

Gitea 1.22.0 में repository description में stored JavaScript की अनुमति थी ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); 1.22.1 में इसे ठीक किया गया। Description संपादित कर सकने वाला user किसी अधिक privileged browser session को प्रभावित कर सकता है, यदि वह user repository देखे और malicious link सक्रिय करे। इसके बाद वह browser identity private repository content या अन्य application data उजागर कर सकती है। अलग से local escalation के लिए उस content के ज़रिए उपलब्ध credential या permission चाहिए, जैसे दोबारा उपयोग किया गया administrator password; केवल Gitea process owner होने से root impact सिद्ध नहीं होता। इस chain का दावा करने से पहले deployed version, description-edit access, viewer workflow और वास्तविक browser interaction जाँचें।

## Cobbler provisioning API

Cobbler की management service XML-RPC API उपलब्ध कराती है, जो आम तौर पर port `25151` पर होती है। Impact का आकलन करने से पहले listener और `cobblerd` process owner जाँचें; केवल loopback पर उपलब्ध API तक भी host का user पहुँच सकता है। `/etc/cobbler/modules.conf` में authentication और authorization modules, `/etc/cobbler/settings` या `/etc/cobbler/settings.yaml` में service settings, और `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` तथा `/var/lib/cobbler/web.ss` की permissions की समीक्षा करें। Digest और shared-secret files में credential material होता है, इसलिए default रूप से उनकी सामग्री प्रिंट किए बिना उनकी readability दर्ज करें।

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** Cobbler 3.0.0 से 3.2.2 तक और 3.3.0 से 3.3.6 तक में XML-RPC authentication bypass है। Shared-secret पढ़ने में त्रुटि होने पर अनुमानित मान `-1` लौटता था, जिसे API पासवर्ड के रूप में स्वीकार करती थी। संबंधित fixes 3.2.3 और 3.3.7 में हैं। Package version एक सुराग है; exposure की रिपोर्ट करने से पहले deployed code और backported fix की पुष्टि करें।

जब `cobblerd` root के रूप में चलता है, तो authenticated API session एक privileged execution path बन सकता है। प्रभावित implementations में, `background_import` user-controlled `rsync_flags` को shell command में पास करता है, और user-controlled Cheetah autoinstall template render करने पर Python evaluate हो सकता है। इनमें से किसी भी path की जाँच करने से पहले API permissions और installed version की पुष्टि करें। Management API तक पहुँच सीमित करें, authentication bypass को patch करें, और configuration तथा credential files को केवल service administrators के लिए readable रखें।

## Motion और motionEye configuration

`/etc/motioneye/motioneye.conf` में `conf_path` देखें, फिर उस directory में `motion.conf` और कुछ `camera-*.conf` files की जाँच करें। रिपोर्ट करें कि readable `# @admin_password` hash मौजूद है या नहीं, लेकिन उसे प्रिंट न करें। [पुराने motionEye releases इन files को व्यापक read permissions के साथ लिखते थे](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); इसका fix 0.44.0 में है। Motion की `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method`, और `webcontrol_localhost` settings को साथ में जाँचें: authentication disabled होने पर advanced control (`2` या `3`) किसी local user को शक्तिशाली operations तक पहुँच दे सकता है, loopback listener पर भी। [Motion इन values और defaults का दस्तावेज़ देता है](https://motion-project.github.io/motion_config.html).

0.43.1b5 से पहले motionEye के विरुद्ध admin session, Motion द्वारा process किए जाने पर camera filename setting को command execution में बदल सकता था ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Escalation का दावा करने से पहले running version, service identity, उपयोग योग्य authentication path, और camera configured है या नहीं, इसकी पुष्टि करें। केवल configuration से यह साबित नहीं होता कि service चल रही है या privileged है।

Service name या installed package केवल एक सुराग है। Privilege boundary, reachable input, process identity, writable configuration, और अंततः उसके नियंत्रण में आने वाले command या file के संयोजन से तय होती है।

## Local AWS emulators और stored credentials

किसी host user को container में चल रहे AWS-compatible emulator तक उसके published loopback endpoint के ज़रिए पहुँच मिल सकती है। [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) या [KMS](https://docs.localstack.cloud/aws/services/kms/) तक पहुँच का आकलन करने से पहले live listener, client द्वारा चुने गए endpoint और account, तथा emulator की installed authorization settings का मिलान करें। LocalStack में, [IAM policy enforcement एक अलग setting है](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); केवल credential file, IAM policy, या listener के आधार पर प्रभावी API permissions का अनुमान न लगाएँ। Installed release और configuration का व्यवहार सत्यापित करें।

Stored secret, local escalation के लिए तभी उपयोगी है जब मौजूदा API identity उसे retrieve कर सके और कोई अलग, अधिक privileged account प्राप्त credential को स्वीकार करे। Encrypted local blob के लिए file पढ़ने की अनुमति, उससे मेल खाती उपयोग योग्य KMS key और algorithm, तथा प्रभावी decrypt access भी आवश्यक हैं। [Asymmetric KMS key](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) के लिए, decrypt request में blob को encrypt करने के लिए इस्तेमाल किया गया algorithm निर्दिष्ट होना चाहिए। Host की automatic inventory को process, listener, configuration-path, और file-permission evidence तक सीमित रखें; नियमित enumeration के दौरान secret values या decrypted plaintext न माँगें और न प्रिंट करें।
