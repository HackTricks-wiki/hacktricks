# Локальні вебслужби та служби автентифікації

{{#include ../../banners/hacktricks-training.md}}

Linux shell дає змогу переглянути вебслужби та служби автентифікації з боку хоста: аргументи процесів, прослуховувані порти, файли unit, конфігурацію, журнали та інтерфейси, доступні лише локально. Скористайтеся цим оглядом, щоб з’ясувати, з яким обліковим записом і файлами фактично працює доступна служба.

## Складіть карту локального вебстека

```bash
ss -lntup
ps -eo user,pid,args | grep -E '[a]pache|[n]ginx|[p]hp-fpm|[j]enkins'
systemctl list-units --type=service --state=running 2>/dev/null
find /etc/apache2 /etc/httpd /etc/nginx -maxdepth 3 -type f 2>/dev/null | head -80
```

Перевірте імена virtual host, корені документів, маршрути проксі, каталоги завантажень, налаштування виконання PHP і конфігураційні файли з обліковими даними. Loopback-слухач може бути доступним через проксі або SSH-тунель. Щоб перевірити іменований virtual host через локальний слухач, надішліть відповідний заголовок `Host` або використайте `curl --resolve` із правильною адресою та портом. Перебирання virtual host також може виявити імена, яких немає у відповіді за замовчуванням. Перевірте, чи дозволяє Apache перевизначення через `.htaccess` і чи можуть шляхи завантаження виконувати PHP, перш ніж вважати каталог завантажень із правом запису шляхом до виконання коду. Розгорнута source map JavaScript може розкрити шляхи до вихідного коду або секрети на стороні клієнта; сприймайте знайдені значення як зачіпки й перевіряйте їхні фактичні привілеї. Перевірки, специфічні для вебсерверів, див. у розділах [Apache](../../network-services-pentesting/pentesting-web/apache.md) і [Nginx](../../network-services-pentesting/pentesting-web/nginx.md).

Для Apache з [mpm-itk](https://mpm-itk.sesse.net/) активна директива `AssignUserID` може запускати virtual host від імені іншого користувача й групи. Якщо обліковий запис із нижчими привілеями може записати скрипт у `DocumentRoot` цього хоста, перевірте, чи виконує доступний маршрут цей скрипт під призначеною ідентичністю. Переконайтеся, що модуль завантажено, перевірте ефективну конфігурацію virtual host (включно з перевизначеннями ідентичності на основі виразів), дозволи на запис і пошук у каталогах, обробник скриптів і доступність слухача. Виділена директива або каталог із правом запису самі по собі не доводять можливість виконання від імені іншого користувача.

Домашній каталог, опублікований через вебсервер, може розкривати резервні архіви SSH-файлів ідентифікації, навіть якщо активний каталог `.ssh` приватний. Наприклад, налаштування [Nostromo `homedirs_public`](https://www.nazgul.ch/dev/nostromo_man.html) визначає підкаталог, який надається з домашніх каталогів користувачів. Збіг лише за шляхом до архіву — це зачіпка: перевірте фактичне відображення на сервері, доступність файлу для локального читання або HTTP-авторизацію, вміст архіву, парольну фразу приватного ключа та чи приймає відповідний обліковий запис цей ключ. Під час звичайного переліку хоста не розпаковуйте архіви й не виводьте матеріали ключів.

Доступна для читання резервна копія локальної вебпрограми з вищими привілеями може розкрити логіку автентифікації та читання файлів, навіть якщо активний вихідний код недоступний. Порівняйте резервну копію з розгорнутим сервісом, перш ніж покладатися на неї. Зокрема, варто перевірити cookie, створену шифруванням контрольованого користувачем тексту з наступним додаванням секрету й прапорця ролі, якщо програма використовує детерміновані блоки ECB, повертає нові cookie для вибраного тексту, а згодом розбиває розшифроване значення за неекранованим роздільником. [NIST пояснює незалежне й повторюване відображення блоків у ECB](https://csrc.nist.gov/news/2022/proposal-to-revise-sp-800-38a); ця властивість може підтримати порівняння з вибраним введенням, але сама по собі не надає вищу роль. Перевірте активний маршрут, передумови сесії, точний парсер і потік даних, ідентичність сервісу та окрему привілейовану дію або шлях читання файлів. Пасивний інвентар має повідомляти метадані резервних копій і власника слухача, не читаючи вміст архіву й не надсилаючи запити автентифікації.

Такий самий підхід до аналізу вихідного коду застосовується до привілейованого локального сервісу `non-HTTP`, наприклад власного інтерфейсу на базі SSH. Якщо доступна резервна копія вихідного коду містить команду, що приймає шлях до файлу, заданий користувачем, перевірте її автентифікаційний бар’єр, спосіб розв’язання шляху та чи гарантує вона, що розв’язаний файл залишається всередині призначеного каталогу перед відкриттям. У Go [`filepath.Join`](https://pkg.go.dev/path/filepath#Join) нормалізує шлях, але не гарантує такого обмеження. Переконайтеся, що резервна копія відповідає запущеній збірці, слухач доступний, команда доступна обліковому запису з нижчими привілеями, а процес може прочитати цільовий файл; наявність доступного для читання SSH-ключа — це окреме питання політики входу. Повідомляйте шляхи до архівів вихідного коду й власника сервісу, не розпаковуючи вміст архівів і не додаючи ключі до автоматизованого виводу.

PHP-FPM-пул, що слухає TCP loopback, може бути доступний іншому локальному обліковому запису, навіть якщо вебсайт вимагає автентифікації. [PHP попереджає, що клієнт, здатний під’єднатися до FastCGI, може контролювати параметри запиту, зокрема `auto_prepend_file`](https://www.php.net/manual/en/install.fpm.php). Перевірте налаштування `listen` і `listen.allowed_clients` у пулі разом з активним слухачем, UID воркера, наявним шляхом до скрипту та будь-якими обмеженнями `security.limit_extensions` або `php_admin_value`. Конфігураційні файли пулу можуть містити облікові дані в директивах `env[...]`, тому автоматизований інвентар має повідомляти їхні шляхи, а не вміст. Сам конфігураційний файл або порт не доводять наявність шляху до виконання коду від імені іншого користувача; подробиці протоколу див. у [посібнику з FastCGI](../../network-services-pentesting/9000-pentesting-fastcgi.md).

Для привілейованого локального API відстежуйте авторизацію так само, як і виконання коду. Роль бази даних, яку може змінити обліковий запис із нижчими привілеями, може відкрити маршрут API, але наступна межа залежить від реалізації цього маршруту. Наприклад, об’єднання JSON запиту з об’єктом JavaScript із подальшим викликом [`child_process.exec`](https://nodejs.org/api/child_process.html) потребує перевірки на наявність [потоку даних від prototype pollution до виконання коду](../../pentesting-web/deserialization/nodejs-proto-prototype-pollution/prototype-pollution-to-rce.md). Перевірте фактичну бібліотеку й версію для об’єднання, валідацію введення, доступний маршрут, ідентичність процесу та параметри дочірнього процесу; слухач Node, яким володіє root, або сама назва вразливої залежності — лише зачіпки.

CMS зі зберіганням даних у файлах може тримати верифікатори паролів адміністратора поза звичними конфігураційними файлами `.php`. Приклади: `data/database.js` сайту або `data/settings/pass.php`. Перш ніж перевіряти вручну, з’ясуйте власника файлу й можливість його читання; не додавайте хеші до спільного автоматизованого виводу. Відновлюваний пароль програми перетинає окрему межу привілеїв відносно Unix-облікового запису: перевірте будь-яке заявлене повторне використання пароля для конкретного облікового запису й дозволеного методу автентифікації.

Контролер автентифікації програми також може містити буквальний пароль для входу у вихідному коді, а не в конфігураційному файлі. Якщо користувач із нижчими привілеями може читати розгорнутий контролер, локально перевірте порівняння під час автентифікації та не додавайте жодних значень до спільного виводу інвентаризації. Переконайтеся, що шлях виконання коду активний, пароль дійсний для програми, а окремий Unix-обліковий запис із вищими привілеями справді приймає той самий пароль, перш ніж заявляти про локальне підвищення привілеїв. Саме ім’я файлу контролера — лише зачіпка для перевірки.

Dolibarr зберігає налаштування підключення до бази даних, зокрема `dolibarr_main_db_pass`, у `htdocs/conf/conf.php` ([довідка з конфігурації](https://wiki.dolibarr.org/index.php/Configuration_file)). Доступний для читання файл — це зачіпка щодо облікових даних; лише окремо перевірене повторне використання пароля облікового запису або інший дозвіл бази даних можуть перетворити його на локальне підвищення привілеїв. Спершу перевірте дозволи й не виводьте значення в автоматизований вивід.

Зазвичай конфігураційний файл Linux-пакета GitLab розташований за шляхом `/etc/gitlab/gitlab.rb`, хоча в розгортаннях можуть зберігатися його доступні для читання копії в інших місцях. [GitLab документує](https://docs.gitlab.com/omnibus/settings/smtp/), що цей файл може містити `gitlab_rails['smtp_password']`, хоча зашифровані налаштування SMTP можуть зберігати пароль поза відкритим текстом файлу. Вважайте доступну для читання конфігурацію зачіпкою щодо облікових даних: перевірте, чи вона активна, чи актуальні облікові дані та чи приймає їх конкретний обліковий запис із вищими привілеями, перш ніж заявляти про повторне використання пароля. Окремо, [GitLab виконує `gitlab.rb` як код Ruby від імені root під час `gitlab-ctl reconfigure`](https://docs.gitlab.com/omnibus/settings/configuration/); щоб вважати активний файл або підключений через `from_file` файл знахідкою щодо виконання коду, потрібен фактичний шлях до привілейованого переналаштування. Попередній перегляд конфігурації може розкрити значення облікових даних, тож вважайте його вивід чутливим і натомість поширюйте шляхи й дозволи.

Власна інсталяція Mattermost може зберігати `SqlSettings.DataSource` у `/opt/mattermost/config/config.json`; [Mattermost документує](https://docs.mattermost.com/deployment-guide/server/troubleshooting) і цей типовий шлях, і розгортання, у яких активна конфігурація зберігається в базі даних. Доступний для читання файл може розкрити облікові дані бази даних програми, але сам по собі не підтверджує доступ до бази даних або доступ до Unix root. Перевірте активне джерело конфігурації, фактичні права ролі бази даних, будь-який окремо відновлений пароль програми й те, чи працює цей пароль для конкретного Unix-облікового запису з вищими привілеями. Формат хешів паролів може змінюватися між версіями Mattermost; під час інвентаризації фіксуйте шлях до конфігурації та метадані доступу, не виводячи рядок підключення й не надсилаючи запитів до бази даних.

```bash
curl -i -H 'Host: admin.example.local' http://127.0.0.1:8080/
ffuf -w wordlist.txt -u http://127.0.0.1:8080/ -H 'Host: FUZZ.example.local' -fs 1234 # replace 1234 with the default response size
grep -R 'sourceMappingURL' /var/www /opt 2>/dev/null | head
```

Відфільтруйте результати віртуальних хостів за розміром відповіді за замовчуванням або іншою стабільною базовою відповіддю, щоб кожне вгадане ім’я не виглядало дійсним. Карта джерел корисна лише тоді, коли її справді розгорнуто або вона доступна іншим способом.

Reverse proxy можуть змінювати те, яким заголовкам клієнта довіряє застосунок. Порівняйте прямі запити й запити через proxy, перш ніж припускати, що `X-Forwarded-For`, `X-Forwarded-Host` або подібні заголовки ідентифікують викликувача. Перевірте конфігурації proxy та застосунку разом.

Якщо PHP копіює `$_SERVER['HTTP_X_FORWARDED_FOR']` у рядок, переданий до [`system()`](https://www.php.net/manual/en/function.system.php), перевірте, чи дозволяє доступний шлях запиту передати власний заголовок і чи потрапляють shell-метасимволи в цей рядок без змін. Команда на кшталт `sudo iptables` на початку **не** змушує наступні команди, відокремлені shell-операторами, виконуватися від root; вони виконуються від імені вебворкера, якщо окреме ефективне правило sudo не дозволяє підвищення привілеїв. Перш ніж заявляти про можливість отримати root, з’ясуйте, від імені якого користувача працює воркер, які саме дозволи надає `sudo -l`, чи потрібна автентифікація та де проходить межа аргументів команди. Під час звичайного переліку вузла перевіряйте вихідний код і політику, не надсилаючи тестовий запит на ін’єкцію.

## Привілейовані loopback API після отримання web foothold

Shell вебпроцесу може викликати локальні HTTP-сервіси, навіть якщо їхні слухачі прив’язані до `127.0.0.1`. У вразливій збірці Control Web Panel, про яку повідомлялося, панель керування обліковим записом працює від імені користувача хостингу, але user API на `https://127.0.0.1:2302` працює від root. Його маршрут POST `/v1/restoredatabase/` не перевіряє токен доступу та передає поле `file` до `shell_exec('mysql ... < ' . $file)`. Тому, отримавши foothold від імені користувача хостингу, можна виконати команди від root, додавши shell-роздільники до `file`. Перевірте як обмеження доступу до маршруту, так і фактичні права процесу API: прив’язка до loopback сама по собі не є автентифікацією. Див. [PHP execution after redirect](../../pentesting-web/login-bypass/#php-execution-after-redirect), де описано один зі способів отримати такий foothold. Про повідомлені вразливості було повністю усунуто у CWP 1.29.<sup>[[1]](#references)</sup>

```bash
curl -sk 'https://127.0.0.1:2302/v1/restoredatabase/' \
  --data-urlencode 'file=/dev/null ; id > /tmp/root-proof ; echo'
```

У того самого API є окрема вада в механізмі автентифікації: `access_token()` підставляє переданий токен у `WHERE authorization_code='$access_token' AND client_id='$user'`. Рядок `UNION` з очікуваними стовпцями та майбутнім терміном дії може пройти перевірку токена, закоментувавши початкову умову `client_id`. Це відкриває доступ до захищених маршрутів, як-от `/v1/newpass/`, де необроблене значення `user` додається до shell-команди `passwd`, що належить root. Ін'єкція токена обходить перевірку доступу; виконання команди все ще залежить від цієї другої вразливої точки. Див. [обхід автентифікації через SQL injection](../../pentesting-web/login-bypass/#sql-injection-authentication-bypass).<sup>[[1]](#references)</sup>

Для описаної перевірки з шістьма стовпцями ін'єктований токен може вказати майбутній термін дії та приховати решту умови; структура стовпців залежить від конкретної збірки.<sup>[[1]](#references)</sup>

```sql
' UNION SELECT 'a','x','c','d','2099-01-01 00:00:00','f' -- -
```

Окремий tokenless маршрут `/v1/user_panel_dashboard/` підставляє `user` у запит до `oauth_clients`. Це blind database read із використанням API-підключення MySQL-root, **а не виконання команд від імені root в OS**: сервер MySQL працює від імені OS-користувача `mysql`. Коли таблиця запиту порожня, [constant derived-table timing probe](../../pentesting-web/sql-injection/#exploiting-time-based-sqli) дає змогу не втратити затримку через відсутність рядків.<sup>[[1]](#references)</sup>

## Облікові дані для входу в access logs

Якщо застосунок надсилає форму входу методом `GET`, ім’я користувача та пароль можуть стати query-параметрами в URI запиту. Запит `POST` також може містити query string; використання `POST` не приховує секрет, випадково розміщений в URI, зокрема пароль, введений у поле іншої форми. [Типовий рядок запиту в access log Apache](https://httpd.apache.org/docs/2.4/logs.html) фіксує метод і URI, включно з query string, якщо у налаштованому форматі використовується `%r`. Тому обліковий запис, якому дозволено читати ці журнали, наприклад через групу `adm` у деяких системах Linux, може знайти зачіпку для пошуку облікових даних. Перевірте фактичний формат журналу та дозволи, а потім переконайтеся, що значення є секретом, обліковий запис його приймає і це дає змогу перетнути межу привілеїв. Не припускайте, що тіло запиту записувалося в журнал, і не копіюйте можливі значення в спільний вивід.

Переглядайте лише доступні для читання access logs і не виводьте значення облікових даних у спільний вивід команд. Довгі рядки запитів також можуть містити referrer і user agent, тому фільтр коротких рядків може приховати саме той запит, який вас цікавить. Типові розташування access logs Apache, httpd і Nginx: `/var/log/apache2/access.log`, `/var/log/httpd/access_log` і `/var/log/nginx/access.log`. У ротованих журналах можуть бути старі облікові дані. [Доступ до файлів журналів через LFI](../../pentesting-web/file-inclusion/README.md#read-access-logs-to-harvest-get-based-auth-tokens-token-replay) — споріднений шлях до тих самих даних.

Журнали автентифікації застосунку також можуть випадково розкрити пароль, введений у поле **імені користувача** під час невдалої спроби входу. Спершу з’ясуйте, чи доступний журнал для читання і чи записує його формат надіслане ім’я користувача; локально перегляньте лише невеликий релевантний фрагмент і не копіюйте можливі облікові дані в спільний вивід. Ім’я користувача, схоже на пароль, — це зачіпка, а не доказ дійсності пароля чи наявності вищих привілеїв. Перш ніж стверджувати про перехід, перевірте цільовий обліковий запис і можливе повторне використання пароля саме в цьому сервісі або Unix-обліковому записі.

Якщо обробник вебформи входу доступний для запису, його варто окремо перевірити, коли запланований клієнт під іншою ідентичністю надсилає облікові дані на цей endpoint. Переконайтеся, що активний обробник доступний для запису, з’ясуйте фактичний розклад клієнта й шлях запиту, чий пароль він надсилає та чи є пароль застосунку незалежно дійсним для привілейованішого облікового запису операційної системи. Самі по собі сторінка, доступна для запису, або процес, що запускається регулярно, не доводять наявність такого переходу. Пасивна інвентаризація має фіксувати дозволи шляхів і метадані завдань, не змінюючи обробник і не збираючи паролі.

Журнали Suricata у форматі EVE JSON також можуть записувати команди FTP `USER` і `PASS` разом із `command_data`, якщо ввімкнено журналювання подій FTP. Перш ніж переглядати локально невеликий релевантний фрагмент, перевірте, чи доступні для читання `/var/log/suricata/eve*.json*`, зокрема ротовані або стиснуті файли. Доступний для читання файл EVE — лише зачіпка: підтвердьте, що події FTP записувалися, дані містять придатні облікові дані й це дає змогу перетнути межу привілеїв. Не виводьте `command_data` у спільний результат інвентаризації. Suricata документує [поля подій FTP](https://docs.suricata.io/en/suricata-8.0.2/output/eve/eve-json-format.html) і [ротацію EVE та варіанти назв файлів](https://docs.suricata.io/en/suricata-7.0.15/output/eve/eve-json-output.html).

## Згенерована конфігурація Apache та piped logs

[remco](https://github.com/HeavyHorst/remco) може стежити за key/value backend, генерувати файл конфігурації Apache з шаблону та виконувати команду перезавантаження. Перевірте ідентичність процесу remco, що працює, налаштовані джерело й призначення шаблону, префікси ключів, за якими ведеться спостереження, і чи вставляється значення backend безпосередньо в директиву Apache, наприклад `ServerName`. Сам факт наявності локального backend listener не доводить, що поточний користувач може записувати ключ, за яким ведеться спостереження; перш ніж стверджувати про підвищення привілеїв, перевірте автентифікацію та дозволи backend.

Неекранований символ нового рядка у значенні backend, доступному для запису, може перетворити одне заплановане значення директиви на додаткові директиви Apache. [Piped logs Apache](https://httpd.apache.org/docs/2.4/logs.html#piped) особливо чутливі: `CustomLog` або `ErrorLog` із командою, що починається з `|`, запускає допоміжний процес від імені батьківського процесу httpd, часто root; `|$` вказує Apache використовувати shell. Під час інвентаризації переглядайте згенеровану конфігурацію та шлях її перезавантаження, не змінюючи дані backend і не перезапускаючи службу. Не розголошуйте повну команду piped, оскільки її аргументи можуть містити секрети.

## Автентифікація та ідентичності служб

Файл керування Monit зазвичай розташований у `~/.monitrc` або `/etc/monitrc`, але `monit -c` може вказати інший шлях. У доступному для читання файлі можуть міститися записи `set httpd` і `allow user:password` для вебінтерфейсу, часто на локальному порту 2812. Перш ніж переглядати файл, перевірте його власника та дозволи й не виводьте паролі у спільний результат інвентаризації. Вебоблікові дані надають лише роль Monit, налаштовану для цього облікового запису; користувачі лише для читання не можуть виконувати керувальні дії. Окреме підвищення привілеїв Unix-облікового запису потребує підтвердженого повторного використання пароля або привілейованої дії Monit, яку справді може виконати автентифікована роль. Див. [документацію Monit щодо файла керування та автентифікації](https://www.mmonit.com/monit/documentation/monit.html).

Для Webmin файл `/etc/webmin/miniserv.conf` містить налаштування сервера, а `/etc/webmin/webmin.acl` — перелік модулів, доступних користувачам; [у документації Webmin описано межі надання доступу до модулів](https://webmin.com/docs/development/creating-modules/). Пароль Unix або доступний для читання файл ACL самі по собі не надають сеанс Webmin. Перевірте фактичне зіставлення автентифікації, доступність listener, автентифікований обліковий запис, ефективні дозволи модуля Package Updates, встановлений код або виправлення від постачальника й ідентичність процесу Webmin. У вразливих збірках до версії 1.910 включно [CVE-2019-12840](https://nvd.nist.gov/vuln/detail/CVE-2019-12840) дозволяла обліковому запису з дозволом на цей модуль виконувати команди через обробник оновлень. Під час пасивної інвентаризації повідомляйте шляхи конфігурації та дозволи, не виводячи облікові дані й не намагаючись виконати оновлення.

```bash
find /etc/pam.d /etc/sssd /etc/postfix -maxdepth 2 -type f -ls 2>/dev/null
systemctl cat sssd postfix jenkins 2>/dev/null
getent passwd
```

- [PAM](pam-pluggable-authentication-modules.md) керує автентифікацією для окремих служб; доступні для запису файли політик або модулів можуть змінити поведінку під час входу.
- Конфігурація LDAP/SSSD може розкрити адреси каталогів, ідентифікатори для прив’язки та правила доступу. Отриманий пароль для прив’язки може дозволити виконувати LDAP-запити, недоступні поточному обліковому запису ОС; перевірте саме цей ідентифікатор для прив’язки та ACL каталогу. Перш ніж переглядати секрети, перевірте дозволи на файли; у розділах [Linux Active Directory](../user-information/linux-active-directory.md) і [FreeIPA](freeipa-pentesting.md) розглянуто використання квитків і каталогів.
- Псевдоніми Postfix можуть перенаправляти отриману пошту до локальних команд. Якщо користувач із нижчими привілеями може змінити вказаний скрипт, доставка пошти може запустити його код від імені облікового запису доставки. Перш ніж стверджувати, що такий шлях існує, перевірте таблиці псевдонімів і власника скрипту; див. [Тестування SMTP і поштових служб](../../network-services-pentesting/pentesting-smtp/README.md).
- Jenkins та інші CI-служби можуть виконувати завдання від імені потужного локального облікового запису. Перш ніж тестувати Pipeline або плагін, перевірте обліковий запис служби, доступні для запису шляхи завдань/робочих просторів і локальний інтерфейс адміністрування. Також перевірте **облікові дані, доступні завданню**, і обліковий запис, від імені якого вони можуть проходити автентифікацію: Pipeline, що використовує крок [SSH Agent](https://www.jenkins.io/doc/pipeline/steps/ssh-agent/), може отримати доступ до хоста від імені користувача, якому належать облікові дані SSH, навіть якщо сам Jenkins працює від імені облікового запису Unix із нижчими привілеями. Перш ніж стверджувати про підвищення привілеїв на хості, підтвердьте, що поточна ідентичність Jenkins має `Job/Create`, `Job/Configure` або інший дієвий спосіб змінити Pipeline, що облікові дані доступні для цього завдання та що цільовий обліковий запис SSH приймає ключ. Самі лише відображуване ім’я чи ID облікових даних не підтверджують жодної з цих умов. Jenkins попереджає, що автори завдань і часто їхні конфігуратори можуть довільно використовувати облікові дані, доступні в їхній області видимості; тому [область видимості облікових даних](https://www.jenkins.io/doc/book/security/credentials/) і [довіра до Pipeline](https://www.jenkins.io/doc/book/security/securing-org-folders-and-multibranch-pipelines/) важливі не менше, ніж UID служби. Не додавайте значення облікових даних і приватні ключі до спільного виводу під час переліку.

## Запис файлів репозиторію Gogs

Для локальної служби Gogs зіставте власника процесу `gogs web` із версією виконуваного файла та `custom/conf/app.ini`. Конфігурація може розкрити ідентичність служби, кореневий каталог репозиторіїв, адресу прослуховування та чи вимкнено реєстрацію. Навіть інтерфейс, що прослуховує лише loopback, доступний локальним користувачам. У версіях Gogs до 0.13.3 включно є автентифікована вразливість запису файлів через символічне посилання в `PutContents` ([CVE-2025-8110](https://github.com/advisories/GHSA-mq8m-42gh-wq7r)): користувач із правом запису до репозиторію може зафіксувати символічне посилання, а потім спрямувати через нього запис API. Доступ до файлів у результаті здійснюється з привілеями процесу Gogs, тож екземпляр, що працює від імені root, потребує невідкладної уваги. Перш ніж стверджувати, що шлях придатний до використання, перевірте встановлене виправлення та вимоги до автентифікації; помилка API не доводить, що запис файлу не вдався.

## XSS в описі репозиторію Gitea та привілейовані користувачі

У Gitea 1.22.0 дозволялося зберігати JavaScript в описі репозиторію ([CVE-2024-6886](https://github.com/advisories/GHSA-4h4p-553m-46qh)); у версії 1.22.1 цю проблему виправлено. Користувач, який може редагувати опис, може вплинути на сеанс браузера користувача з вищими привілеями, якщо той перегляне репозиторій і активує шкідливе посилання. Це може надати доступ до приватного вмісту репозиторію або інших даних застосунку від імені цього користувача браузера. Для окремого локального підвищення привілеїв потрібні облікові дані або дозволи, доступні через цей вміст, наприклад повторно використаний пароль адміністратора; сам факт, що власником процесу є Gitea, не доводить впливу на root. Перш ніж стверджувати, що цей ланцюжок можливий, перевірте встановлену версію, доступ до редагування опису, сценарій перегляду та фактичну взаємодію з браузером.

## API підготовки системи Cobbler

Служба керування Cobbler надає API XML-RPC, зазвичай на порту `25151`. Перш ніж оцінювати її вплив, перевірте інтерфейс прослуховування та власника процесу `cobblerd`; навіть API, доступний лише через loopback, можна викликати від імені користувача на цьому хості. Перегляньте модулі автентифікації й авторизації у `/etc/cobbler/modules.conf`, параметри служби в `/etc/cobbler/settings` або `/etc/cobbler/settings.yaml`, а також дозволи на `/etc/cobbler/users.conf`, `/etc/cobbler/users.digest` і `/var/lib/cobbler/web.ss`. Файли digest і спільного секрету містять облікові дані, тому за замовчуванням фіксуйте лише доступність для читання, не виводячи їхній вміст.

```bash
ps -eo user,pid,args | grep '[c]obblerd'
ss -ltn 2>/dev/null | grep ':25151'
for file in /etc/cobbler/modules.conf /etc/cobbler/settings /etc/cobbler/settings.yaml \
            /etc/cobbler/users.conf /etc/cobbler/users.digest /var/lib/cobbler/web.ss; do
    [ -e "$file" ] && ls -l "$file"
done
```

**CVE-2024-47533** — це обхід автентифікації XML-RPC у Cobbler версій від 3.0.0 до 3.2.2 і від 3.3.0 до 3.3.6. Помилка читання спільного секрету повертала передбачуване значення `-1`, яке API приймав як пароль. Виправлення доступні у версіях 3.2.3 і 3.3.7. Версія пакета — лише підказка; перш ніж повідомляти про вразливість, перевірте розгорнутий код і наявність зворотно перенесеного виправлення.

Автентифікована сесія API може стати шляхом до привілейованого виконання, якщо `cobblerd` працює від імені root. У вразливих реалізаціях `background_import` передає контрольований користувачем `rsync_flags` до shell-команди, а під час обробки контрольованого користувачем шаблону автоналаштування Cheetah може виконуватися Python-код. Перш ніж тестувати будь-який із цих шляхів, перевірте дозволи API та встановлену версію. Обмежте доступ до API керування, виправте обхід автентифікації та надайте доступ на читання до файлів конфігурації й облікових даних лише адміністраторам служби.

## Конфігурація Motion і motionEye

Перевірте `/etc/motioneye/motioneye.conf`, щоб знайти `conf_path`, а потім перегляньте `motion.conf` і кілька файлів `camera-*.conf` у цій директорії. Повідомте, чи є там доступний для читання хеш `# @admin_password`, але не виводьте його. [У старіших версіях motionEye ці файли створювалися з надто широкими дозволами на читання](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-rhgp-6wq6-9j67); виправлення доступне у версії 0.44.0. Перевіряйте разом параметри Motion `webcontrol_port`, `webcontrol_parms`, `webcontrol_auth_method` і `webcontrol_localhost`: розширене керування (`2` або `3`) з вимкненою автентифікацією може надати локальному користувачеві доступ до потужних операцій, зокрема через loopback-слухач. [У документації Motion наведено значення та типові параметри](https://motion-project.github.io/motion_config.html).

Адміністраторська сесія в motionEye до версії 0.43.1b5 могла перетворити параметр імені файла камери на виконання команд під час його обробки Motion ([CVE-2025-60787](https://github.com/motioneye-project/motioneye/security/advisories/GHSA-j945-qm58-4gjx)). Перш ніж заявляти про підвищення привілеїв, перевірте запущену версію, обліковий запис служби, доступний шлях автентифікації та наявність налаштованої камери. Одна лише конфігурація не доводить, що служба запущена або має привілеї.

Назва служби або встановлений пакет — лише підказка. Межа привілеїв визначається сукупністю доступного вхідного інтерфейсу, облікового запису процесу, доступності конфігурації для запису та команди або файла, якими він зрештою керує.

## Локальні емулятори AWS і збережені облікові дані

Користувач хоста може отримати доступ до сумісного з AWS емулятора, запущеного в контейнері, через опубліковану loopback-кінцеву точку. Перш ніж оцінювати доступ до [Secrets Manager](https://docs.localstack.cloud/aws/services/secretsmanager/) або [KMS](https://docs.localstack.cloud/aws/services/kms/), зіставте активний слухач, кінцеву точку й обліковий запис, вибрані клієнтом, а також налаштування авторизації встановленого емулятора. У LocalStack [застосування IAM-політик є окремим параметром](https://docs.localstack.cloud/aws/developer-tools/security-testing/iam-policy-enforcement/); не робіть висновків про фактичні дозволи API лише на підставі файла облікових даних, IAM-політики чи слухача. Перевірте поведінку встановленого випуску та його конфігурацію.

Збережений секрет корисний для локального підвищення привілеїв лише тоді, коли поточна ідентичність API може його отримати, а інший обліковий запис із вищими привілеями приймає отримані облікові дані. Для розшифрування локального зашифрованого файла також потрібні доступ на читання до файла, відповідний придатний до використання ключ KMS і алгоритм, а також фактичний дозвіл на розшифрування. Для [асиметричного ключа KMS](https://docs.aws.amazon.com/cli/latest/reference/kms/decrypt.html) у запиті на розшифрування потрібно вказати алгоритм, яким було зашифровано файл. Під час автоматичної інвентаризації хоста збирайте лише дані про процеси, слухачі, шляхи конфігурації та дозволи файлів; не запитуйте й не виводьте значення секретів або розшифрований відкритий текст під час звичайного переліку.
