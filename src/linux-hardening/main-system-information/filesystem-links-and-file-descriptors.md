# Link simbolici, hard link e descrittori di file

{{#include ../../banners/hacktricks-training.md}}

Un percorso identifica un oggetto nel momento in cui viene risolto; un descrittore di file aperto mantiene un riferimento all’oggetto anche dopo che il nome del percorso cambia. Questa differenza spiega le race condition sui link simbolici, gli hard link nascosti, il recupero di file eliminati e le fughe di descrittori ereditati. Consulta [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) per informazioni di base su inode e mount.

## Esaminare i link e la proprietà dei percorsi

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink reindirizza la risoluzione dei percorsi; un hardlink è un altro nome per lo stesso inode sullo stesso filesystem. Se un’attività con privilegi legge o scrive in un percorso prevedibile all’interno di una directory scrivibile dall’utente, quest’ultimo potrebbe riuscire a reindirizzare quel percorso verso una destinazione sensibile. Verifica la proprietà e i permessi di ogni directory genitore, non solo quelli del file finale. `fs.protected_symlinks` e `fs.protected_hardlinks` riducono i comuni attacchi tra utenti, ma non rendono sicuri tutti i percorsi scrivibili.

Per un job con privilegi che modifica i permessi usando un glob della shell, distingui i link espansi in **operandi della riga di comando** da quelli individuati successivamente durante la traversata ricorsiva. [GNU `chmod` agisce sul referent di un symlink specificato nella riga di comando](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mentre normalmente ignora i symlink incontrati durante la ricorsione; `-R` da solo non rende equivalenti i due casi. Verifica l’identità effettiva e il comando pianificati, se un utente non fidato può creare una voce corrispondente al glob, il comportamento e le opzioni della versione di `chmod` installata, e i permessi risultanti sulla destinazione proposta. Una directory scrivibile o un symlink, da soli, non dimostrano che si verificherà una modifica dei permessi con privilegi. Esamina lo script e i metadati del percorso senza creare un link né avviare il job durante l’enumerazione passiva.

Un writer pianificato con privilegi può usare un percorso di output prevedibile anche quando il nome del file contiene un hash dall’aspetto casuale: [`rand()` in C ripete la sequenza per lo stesso seed di `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), anche se il seed deriva da un orario di esecuzione noto. Se il job legge anche righe di database scrivibili dal chiamante per costruire quel nome, verifica l’esatto algoritmo di conversione da riga a nome, il seed e il comportamento di libc, la pianificazione, i permessi del chiamante per modificare le righe e creare directory, e se è possibile collocare un symlink preesistente prima dell’apertura con privilegi. [`fopen(..., "w")` crea o tronca il file risolto](https://man7.org/linux/man-pages/man3/fopen.3.html); verifica nell’implementazione effettiva l’uso di flag di apertura sicuri rispetto ai link o della sostituzione atomica, l’identità effettiva usata per la scrittura, i permessi della destinazione e la policy sui symlink nelle directory sticky. Un nome prevedibile o una riga scrivibile, da soli, sono soltanto spunti da approfondire. Esamina il codice, la pianificazione e i metadati senza inserire righe né avviare il job durante l’enumerazione passiva.

Per un servizio di conversione file eseguito come un altro utente, verifica se il chiamante può scegliere un percorso di output o un’estensione e se il convertitore segue un symlink di output preesistente. Alcuni convertitori scelgono il formato di output in base all’estensione del percorso; un link con un’estensione accettata può comunque puntare a una destinazione sensibile senza estensione. Perché una scrittura tra utenti vada a buon fine, il servizio deve essere raggiungibile, il chiamante deve poter controllare il percorso e il link, il convertitore deve aprire il link in scrittura e l’identità del servizio deve avere i permessi di scrittura. Su Linux, `fs.protected_symlinks=1` limita il dereferenziamento di un link appartenente a un altro utente in una **directory sticky scrivibile da tutti**; non offre la stessa protezione per un link in una normale directory di proprietà dell’utente. Esamina il percorso risolto e la proprietà delle directory genitrici prima di trarre conclusioni. Vedi il [comportamento di calibre per i file di output](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) e la [policy di Linux sui symlink](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Anche per un wrapper di download autorizzato da sudo occorre verificare il percorso di output, se scarica dati scelti dal chiamante mantenendo una directory di lavoro controllata da quest’ultimo. Esamina il downloader effettivo e verifica se il nome base scelto, la gestione delle collisioni o un symlink preesistente possono reindirizzare una scrittura con privilegi; la scelta dell’URL o un symlink, da soli, non bastano. [Axel documenta un file `~/.axelrc` per utente](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt) e il suo [file di configurazione di esempio include `default_filename` e `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), quindi un wrapper che usa Axel potrebbe ereditare anche da quel file la scelta del nome di output. Verifica il valore effettivo di `HOME`: [sudo può reimpostarlo o mantenerlo in base alla policy](https://man7.org/linux/man-pages/man8/sudo.8.html), e il `.axelrc` dell’utente è rilevante solo se il downloader con privilegi lo legge davvero. Esamina la regola, il wrapper, il percorso e i permessi della configurazione, il nome finale dell’output e lo stato del file di destinazione, senza avviare un download durante l’enumerazione passiva.

Per un wrapper ACL autorizzato da sudo, verifica come convalida un file scelto dal chiamante prima di invocare `setfacl`. Un controllo lessicale del prefisso e il rifiuto di `..` non impediscono a un symlink all’interno della directory consentita di risolversi al di fuori di essa; anche `test -f` segue il link. Verifica che il wrapper raggiunga l’operazione ACL con privilegi sufficienti, che il chiamante controlli il link e che l’ACL risultante conceda l’accesso necessario al target **e alle directory genitrici**. Alcuni programmi rifiutano file con ACL scrivibili o permessi troppo permissivi, quindi una modifica ACL, da sola, non dimostra l’esistenza di un percorso di escalation funzionante.

## Esaminare le scritture con privilegi nei filesystem FUSE montati dall’utente

Una riga `user_allow_other` attiva e autonoma in `/etc/fuse.conf` consente a un utente non root di richiedere `allow_other` o `allow_root` su un mount FUSE. Queste opzioni di mount possono permettere a un processo root di accedere a un filesystem implementato dall’utente che ha effettuato il mount. Se un helper autorizzato da sudo scrive un log contenente segreti o altri dati di output in un percorso relativo alla directory di lavoro controllata dal chiamante, verifica se tale directory può essere un filesystem FUSE montato dall’utente. L’implementazione FUSE può osservare le scritture anche quando il file risultante sembra appartenere a root o avere permessi `0600` su un filesystem ordinario.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Questa è una **candidata**, non una prova di divulgazione. Verifica l'identità effettiva di sudo/run-as e gli argomenti, il percorso di output dell'helper e i contenuti sensibili, l'accesso a `/dev/fuse`, il successo del mount con `allow_other` o `allow_root` e la possibilità per il processo privilegiato di accedere al mount. Non eseguire l'helper privilegiato né montare un filesystem durante la normale enumerazione. Consulta la [libfuse policy description](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) e le [libfuse access FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Cerca race condition sui percorsi

Lo schema pericoloso è un programma privilegiato che controlla un pathname e in seguito apre lo stesso pathname senza mantenere un riferimento sicuro all'oggetto controllato. Un attaccante che controlla una directory padre può sostituire un file o un symlink tra le due operazioni. Lo stesso problema si presenta nei file temporanei, negli script eseguiti da timer, nell'estrazione di archivi e nei flussi di lavoro di backup. Prima di dichiarare un impatto, verifica l'effettiva operazione di lettura/scrittura e i permessi del target.

Anche la **creazione** di archivi può divulgare file tra identità diverse. Info-ZIP `zip -r` normalmente segue un symlink inserito nell'albero sorgente e archivia i contenuti del target; `-y`/`--symlinks` archivia invece il link stesso. Se un utente con privilegi inferiori può aggiungere un link in una directory di cui viene eseguito il backup, verifica l'archiver e le opzioni esatti, l'identità di lettura del job di backup e se l'utente può leggere l'archivio risultante. Una directory sorgente scrivibile o un symlink, da soli, non dimostrano una divulgazione. Esamina i metadati di link e archivi senza attivare il backup né estrarre contenuti segreti durante l'enumerazione. Consulta la [Info-ZIP option documentation](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` ha un comportamento predefinito diverso: normalmente archivia un symlink come link, mentre [`-h` / `--dereference` segue il link durante la creazione dell'archivio](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Per un backup pianificato con privilegi elevati, esamina l'invocazione esatta di `tar`, verifica se un utente con privilegi inferiori può sostituire un pathname di input prima che `tar` lo legga e se tale utente può accedere all'archivio risultante. Un checksum temporaneo o un altro file di supporto in una directory di staging scrivibile può diventare un input di questo tipo se viene specificato esplicitamente in un successivo comando `tar -h`. Occorre verificare la finestra della race condition, l'identità del job, la policy sui symlink, la leggibilità del target con tale identità e l'ACL dell'archivio. Durante i controlli passivi, non sostituire file, eseguire il job o estrarre archivi sensibili.

L'**estrazione** di un archivio supera un diverso confine di fiducia quando un job privilegiato legge un archivio che un utente con privilegi inferiori può sostituire. [GNU tar normalmente ripristina la proprietà archiviata quando viene eseguito dal superuser](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html) e le sue [opzioni di ripristino dei permessi](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) influiscono sui bit di modalità degli elementi estratti. Esamina l'estrattore e i flag esatti, la finestra di sostituzione dell'archivio, i metadati numerici di proprietario e modalità, i permessi della directory di estrazione e se la pulizia lascia il risultato accessibile. Un elemento SUID di proprietà di root è un problema solo se la modalità sopravvive all'estrazione e la policy del mount e del processo di destinazione consente il cambio di identità; un archivio non attendibile o un percorso di staging scrivibile, da soli, non lo dimostrano. Durante l'enumerazione passiva, ispeziona il job e i metadati senza sostituire o estrarre archivi.

Un symlink estratto può anche divulgare un file protetto tramite un successivo confronto privilegiato. [GNU `diff` normalmente segue i symlink quando confronta directory](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), quindi un `diff -r` eseguito come root su un albero estratto non attendibile potrebbe leggere il target di un link e includere nel proprio output il contenuto diverso. Verifica che l'archivio possa essere sostituito, che il link punti a un percorso effettivamente visitato dal confronto, che il job possa leggere il target e che l'output del confronto o il log degli errori siano accessibili all'utente con privilegi inferiori. Il link o l'archivio, da soli, non dimostrano una divulgazione; esamina il job, i metadati dei percorsi e i permessi dei log senza eseguire il confronto né leggere contenuti protetti durante l'enumerazione.

Un trasferimento ripetuto lato host può trasformare un elemento di archivio non attendibile in un successivo percorso di output. Se un job con privilegi superiori copia un archivio da un container meno attendibile, estrae un symlink il cui nome coincide con il basename della destinazione del trasferimento successivo e in seguito scrive sullo stesso pathname, la scrittura successiva potrebbe raggiungere il target del link. Verifica il nome e il target dell'elemento nell'archivio, i flag e la directory di estrazione, se l'estrattore lascia effettivamente quel link al suo posto, il comportamento dell'implementazione di trasferimento in presenza di un link già esistente nella destinazione e l'identità effettiva con cui il job host scrive. [GNU tar documents how extraction handles existing files and symlinks](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp uses SFTP by default in modern releases](https://man.openbsd.org/scp.1), quindi verifica il comportamento dell'implementazione di trasferimento installata, invece di presumere che tutte le versioni di `scp` scrivano attraverso un link. Un processo `scp` visibile nel container o un archivio scrivibile, da soli, non dimostrano cosa avvenga durante l'estrazione sull'host e la successiva scrittura. Esamina il job e i metadati dei percorsi senza trasferire né estrarre un archivio creato ad hoc durante l'enumerazione.

Il modulo Ansible [`synchronize`](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) usa rsync; `copy_links: true` copia il referente di un symlink invece del link stesso. Per un backup pianificato, verifica se un utente con privilegi inferiori può creare un link nell'esatto albero sorgente, se l'identità usata per la sincronizzazione può leggere il target e se tale utente può leggere la copia o l'archivio risultante. Il playbook, la posizione del link, l'identità run-as e i permessi dell'output devono essere tutti coerenti; una directory di upload scrivibile o l'impostazione `copy_links`, da sole, sono soltanto spunti per una verifica. Esamina i metadati e il playbook senza creare link né attivare il job.

## Esamina i descrittori aperti

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un processo può mantenere l'accesso a un file anche dopo che è stato eliminato o rinominato. Un processo privilegiato può anche passare un descrittore tramite un socket Unix oppure lasciarlo aperto involontariamente durante `execve()` se manca close-on-exec. Esamina i target di `/proc/<PID>/fd` alla ricerca di file sensibili, file eliminati, percorsi host visibili all'interno di un container e socket inattesi. Dereferenziare i descrittori di un altro processo è soggetto ai controlli di accesso del kernel; un symlink visibile non garantisce che il suo contenuto sia leggibile.

Un helper SUID personalizzato può aprire un percorso protetto, abbassare il proprio UID effettivo e lasciare aperto il descrittore. Se poi si rende dumpable, la proprietà e l'accessibilità di `/proc/<PID>/fd` possono cambiare; verifica l'esatta transizione delle credenziali, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), le policy di procfs/ptrace e i permessi del file di destinazione. Riaprire un percorso di descrittore può aggirare una **directory padre** inaccessibile, ma può comunque fallire se il chiamante non ha i permessi di lettura sul file. Un target di descrittore visibile o il solo bit SUID non dimostrano che vi sia stata una divulgazione.

Gli artefatti di crash sono una pista distinta: un core dump può contenere la memoria del processo, inclusi dati letti in precedenza con un'identità più privilegiata. Su Ubuntu, [Apport normalmente salva i report in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); altri sistemi possono usare un handler `core_pattern` diverso o l'archiviazione di systemd. Durante l'enumerazione di routine, controlla solo i percorsi dei report, il proprietario, i permessi e la leggibilità. Un report leggibile è rilevante solo se il processo in questione era dumpable, l'handler di crash ha conservato i byte sensibili e l'utente corrente può accedere al report. Non causare il crash di un helper né estrarre un dump durante l'enumerazione passiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) per le condizioni relative a SUID e alla generazione dei dump.

Quando un servizio usa un descrittore ereditato, esamina la catena di avvio e i numeri dei descrittori prima di provare il reindirizzamento della shell o `/proc/self/fd/<N>`. Se un file è stato eliminato ma è ancora aperto, il [recupero di file eliminati](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) può preservare le prove o consentire di recuperarne il contenuto. Per il triage a livello di processo, continua con [l'enumerazione dei processi e i percorsi dei servizi](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
