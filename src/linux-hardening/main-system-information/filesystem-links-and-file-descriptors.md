# Symlinks, Hardlinks और फ़ाइल डिस्क्रिप्टर

{{#include ../../banners/hacktricks-training.md}}

किसी पाथ का नाम उस ऑब्जेक्ट को दर्शाता है जिसे वह resolve किए जाने के समय इंगित करता है; खुला हुआ फ़ाइल डिस्क्रिप्टर, pathname बदलने के बाद भी उस ऑब्जेक्ट का संदर्भ बनाए रखता है। यह अंतर symlink races, छिपे हुए hardlinks, हटाई गई फ़ाइलों की recovery और inherited descriptor leaks को समझाता है। inode और mount की पृष्ठभूमि के लिए [फ़ाइल सिस्टम, inodes और recovery](filesystem-inodes-and-recovery.md) देखें।

## Links और path ownership की जाँच करें

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

एक symlink pathname resolution को redirect करता है; hardlink उसी filesystem पर उसी inode का दूसरा नाम होता है। यदि कोई privileged task user-writable directory के अंदर किसी अनुमानित path को पढ़ता या लिखता है, तो user उस path को किसी संवेदनशील target की ओर redirect कर सकता है। केवल अंतिम file ही नहीं, हर parent directory के ownership और permissions की जाँच करें। `fs.protected_symlinks` और `fs.protected_hardlinks` आम cross-user attacks को कम करते हैं, लेकिन मनमाने writable paths को सुरक्षित नहीं बनाते।

ऐसे privileged job के लिए जो shell glob से permissions बदलता है, command-line operands के रूप में expand हुए links और बाद में recursive traversal के दौरान मिले links में अंतर करें। [GNU `chmod` acts on the referent of a symlink named on its command line](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), जबकि recursion के दौरान मिले symlinks को यह आम तौर पर अनदेखा करता है; केवल `-R` देने से ये दोनों मामले समान नहीं हो जाते। वास्तविक scheduled identity और command, यह जाँचें कि क्या कोई untrusted user glob से match होने वाली entry बना सकता है, installed `chmod` का व्यवहार और options, तथा प्रस्तावित target को मिलने वाली access जाँचें। केवल writable directory या symlink होना privileged mode change का प्रमाण नहीं है। Passive enumeration के दौरान link बनाए या job चलाए बिना script और path metadata की जाँच करें।

कोई scheduled privileged writer अपने output path को अनुमानित बना सकता है, भले ही filename में random-जैसा hash हो: [C `rand()` repeats its sequence for the same `srand()` seed](https://man7.org/linux/man-pages/man3/rand.3.html), जिसमें ज्ञात execution time से निकला seed भी शामिल है। यदि job उस नाम को बनाने के लिए caller-writable database rows भी पढ़ता है, तो सटीक row-to-name algorithm, seed और libc behavior, schedule, caller के row-write और directory-create अधिकार, तथा यह जाँचें कि privileged open से पहले कोई pre-existing symlink रखा जा सकता है या नहीं। [`fopen(..., "w")` creates or truncates the resolved file](https://man7.org/linux/man-pages/man3/fopen.3.html); link-safe open flags या atomic replacement, effective write identity, target permissions और sticky-directory symlink policy के लिए वास्तविक implementation की जाँच करें। अनुमानित नाम या writable row अकेले केवल जाँच का संकेत हैं। Passive enumeration के दौरान rows डाले या job चलाए बिना code, schedule और metadata की जाँच करें।

किसी अन्य user के रूप में चलने वाली file-conversion service के लिए जाँचें कि क्या caller output path या extension चुन सकता है और converter किसी pre-existing output symlink को follow करता है। कुछ converters output format को pathname extension से चुनते हैं; स्वीकार्य extension वाले नाम का link फिर भी किसी संवेदनशील, extension-रहित target की ओर इशारा कर सकता है। सफल cross-user write के लिए service तक पहुँच, path और link पर caller का नियंत्रण, converter द्वारा link को output के लिए खोलना, और service identity के पास write permission होना आवश्यक है। Linux का `fs.protected_symlinks=1` किसी अन्य user के link को **sticky world-writable directory** में follow करने पर रोक लगाता है; सामान्य user-owned directory में मौजूद link के लिए यह समान सुरक्षा नहीं देता। निष्कर्ष निकालने से पहले resolved path और parent ownership की जाँच करें। देखें [calibre's output-file behavior](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) और [Linux symlink policy](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks)।

यदि sudo-allowed download wrapper caller-controlled working directory बनाए रखते हुए caller द्वारा चुना गया data fetch करता है, तो उसके output path की भी इसी तरह जाँच करें। वास्तविक downloader की जाँच करें और देखें कि क्या उसका चुना हुआ basename, collision handling या pre-existing symlink privileged write को redirect कर सकता है; केवल URL चुनना या symlink होना पर्याप्त नहीं है। [Axel documents a per-user `~/.axelrc`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), और इसके [example configuration includes `default_filename` and `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), इसलिए Axel इस्तेमाल करने वाला wrapper उस file से output-name का विकल्प भी ले सकता है। प्रभावी `HOME` की पुष्टि करें: [sudo can reset or preserve it according to policy](https://man7.org/linux/man-pages/man8/sudo.8.html), और user की `.axelrc` तभी प्रासंगिक है जब privileged downloader वास्तव में उसे पढ़ता हो। Passive enumeration के दौरान download शुरू किए बिना rule, wrapper, config path और permissions, अंतिम output name तथा target-file state की जाँच करें।

sudo-allowed ACL wrapper के लिए जाँचें कि `setfacl` call करने से पहले वह caller द्वारा चुनी गई file को कैसे validate करता है। केवल lexical prefix check और `..` को अस्वीकार करने से allowed directory के भीतर मौजूद symlink को उसके बाहर resolve होने से नहीं रोका जा सकता; `test -f` भी link को follow करता है। पुष्टि करें कि wrapper पर्याप्त privilege के साथ ACL operation तक पहुँचता है, caller link को नियंत्रित करता है, और resulting ACL target **और उसकी parent directories** पर आवश्यक access देता है। कुछ consumers writable ACLs या ढीले modes वाली files को अस्वीकार करते हैं, इसलिए केवल ACL change से सफल escalation path सिद्ध नहीं होता।

## User-mounted FUSE filesystems पर privileged writes की समीक्षा करें

`/etc/fuse.conf` में सक्रिय standalone `user_allow_other` line किसी non-root user को FUSE mount पर `allow_other` या `allow_root` का अनुरोध करने देती है। ये mount options root process को mounting user द्वारा implemented filesystem तक पहुँचने दे सकते हैं। यदि sudo-allowed helper caller-controlled working directory के सापेक्ष secret-bearing log या अन्य output लिखता है, तो जाँचें कि क्या वह directory user-mounted FUSE filesystem हो सकती है। FUSE implementation writes को देख सकता है, भले ही resulting file सामान्य filesystem पर root-owned या mode `0600` दिखाई दे।

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

यह **candidate** है, disclosure का प्रमाण नहीं। वास्तविक sudo/run-as identity और arguments, helper का output path और sensitive content, `/dev/fuse` तक पहुँच, `allow_other` या `allow_root` के साथ सफल mounting, और privileged process के mount में प्रवेश कर सकने की पुष्टि करें। Routine enumeration के दौरान privileged helper न चलाएँ और filesystem mount न करें। [libfuse policy description](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) और [libfuse access FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem) देखें।

## Path races देखें

खतरनाक pattern तब होता है जब कोई privileged program एक pathname की जाँच करता है और बाद में जाँची गई object का सुरक्षित reference रखे बिना उसी pathname को खोलता है। Parent directory पर नियंत्रण रखने वाला attacker इन दोनों operations के बीच file या symlink बदल सकता है। यही समस्या temporary files, timer-driven scripts, archive extraction और backup workflows में भी आती है। Impact का दावा करने से पहले वास्तविक read/write operation और target की permissions की पुष्टि करें।

Archive **creation** से identities के बीच files का disclosure भी हो सकता है। Info-ZIP `zip -r` आम तौर पर source tree के अंदर रखे symlink को follow करता है और target का content store करता है; `-y`/`--symlinks` इसके बजाय link को ही store करता है। अगर lower-privileged user backed-up directory में link जोड़ सकता है, तो सटीक archiver/options, backup job की read identity और यह जाँचें कि बना हुआ archive उस user के लिए readable है या नहीं। Writable source directory या symlink अकेले disclosure साबित नहीं करते। Backup trigger किए बिना या enumeration के दौरान secret content extract किए बिना link और archive metadata की समीक्षा करें। [Info-ZIP option documentation](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638) देखें।

GNU `tar` का default अलग है: यह आम तौर पर symlink को link के रूप में store करता है, जबकि [`-h` / `--dereference` archive creation के दौरान उसे follow करता है](https://www.gnu.org/software/tar/manual/html_node/dereference.html)। Privileged scheduled backup के लिए, सटीक `tar` invocation, `tar` द्वारा input पढ़ने से पहले lower-privileged user के input pathname को बदल सकने की संभावना, और बने हुए archive तक उस user की पहुँच की जाँच करें। Writable staging directory में मौजूद temporary checksum या अन्य sidecar, बाद के `tar -h` command में स्पष्ट रूप से नामित किए जाने पर ऐसा input बन सकता है। Race window, job identity, symlink policy, उस identity के तहत target की readability और archive ACL—इन सभी की पुष्टि ज़रूरी है। Passive checks के दौरान files न बदलें, job न चलाएँ और sensitive archives unpack न करें।

Archive **extraction** एक अलग boundary पार करता है, जब कोई privileged job ऐसा archive पढ़ता है जिसे lower-privileged user बदल सकता है। [GNU tar आम तौर पर superuser के रूप में चलने पर archived ownership restore करता है](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), और इसके [permission-restoration options](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) extracted mode bits को प्रभावित करते हैं। सटीक extractor और flags, archive replacement window, numeric owner और mode metadata, extraction directory permissions, और cleanup के बाद result की पहुँच की समीक्षा करें। Root-owned SUID member तभी चिंता का विषय है जब extraction के बाद उसका mode बना रहे और target mount तथा process policy identity change की अनुमति दें; untrusted archive या writable staging path अकेले इसे साबित नहीं करते। Passive enumeration के दौरान archive बदले या extract किए बिना job और metadata का निरीक्षण करें।

Extract किया गया symlink बाद की privileged comparison के ज़रिए protected file का disclosure भी कर सकता है। [GNU `diff` आम तौर पर directories की तुलना करते समय symlinks follow करता है](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), इसलिए untrusted extracted tree पर root के रूप में चलाया गया `diff -r` किसी link target को पढ़ सकता है और अपने output में अलग-अलग content शामिल कर सकता है। पुष्टि करें कि archive बदला जा सकता है, link ऐसी path पर जाता है जहाँ comparison वास्तव में पहुँचता है, job के लिए target readable है, और comparison output या error log lower-privileged user के लिए readable है। Link या archive अकेले disclosure साबित नहीं करते; enumeration के दौरान comparison चलाए या protected content पढ़े बिना job, path metadata और log permissions की समीक्षा करें।

बार-बार होने वाला host-side transfer किसी untrusted archive member को बाद का output path बना सकता है। यदि higher-privileged job lower-trust container से archive copy करता है, ऐसा symlink extract करता है जिसका नाम अगले transfer के destination basename से मेल खाता है, और बाद में उसी pathname पर लिखता है, तो बाद का write link target तक पहुँच सकता है। Archive member का नाम और target, extraction flags और directory, extractor द्वारा उस link को वहीं छोड़े जाने की पुष्टि, मौजूदा destination link के साथ transfer implementation का व्यवहार, और host job की प्रभावी write identity जाँचें। [GNU tar बताता है कि extraction मौजूदा files और symlinks को कैसे handle करता है](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp आधुनिक releases में default रूप से SFTP का उपयोग करता है](https://man.openbsd.org/scp.1), इसलिए यह मानने के बजाय कि सभी `scp` versions link के ज़रिए लिखते हैं, installed transfer behavior की पुष्टि करें। Container में दिखने वाला `scp` process या writable archive अकेले host पर extraction और बाद के write को साबित नहीं करते। Enumeration के दौरान crafted archive transfer या extract किए बिना job और path metadata का निरीक्षण करें।

Ansible का [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) rsync को wrap करता है; `copy_links: true` symlink के बजाय उसके referent को copy करता है। Scheduled backup के लिए जाँचें कि lower-privileged user सटीक source tree के अंदर link बना सकता है या नहीं, synchronization identity उसका target पढ़ सकती है या नहीं, और बनी हुई copy या archive उस user के लिए readable है या नहीं। Playbook, link placement, run-as identity और output permissions—सभी का एक साथ मेल खाना ज़रूरी है; writable upload directory या `copy_links` setting अकेले केवल जाँच का संकेत है। Link बनाए या job trigger किए बिना metadata और playbook का निरीक्षण करें।

## Open descriptors का निरीक्षण करें

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

कोई process किसी file को delete या rename किए जाने के बाद भी उस तक पहुंच बनाए रख सकता है। कोई privileged process Unix socket के माध्यम से descriptor भी भेज सकता है, या close-on-exec न होने पर अनजाने में उसे `execve()` के दौरान खुला छोड़ सकता है। संवेदनशील files, deleted files, container के अंदर दिखने वाले host paths और अनपेक्षित sockets के लिए `/proc/<PID>/fd` targets की जांच करें। किसी दूसरे process के descriptors को dereference करना kernel access checks के अधीन है; दिखाई देने वाली symlink से यह सुनिश्चित नहीं होता कि उसकी सामग्री पढ़ी जा सकती है।

कोई custom SUID helper सुरक्षित pathname खोल सकता है, अपना effective UID drop कर सकता है और descriptor को खुला छोड़ सकता है। यदि वह इसके बाद खुद को dumpable बनाता है, तो `/proc/<PID>/fd` का ownership और access बदल सकता है; credentials के सटीक बदलाव, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), procfs/ptrace policy और target file mode की समीक्षा करें। Descriptor path को फिर से खोलने से किसी inaccessible **parent directory** को bypass किया जा सकता है, लेकिन यदि caller file पढ़ नहीं सकता तो यह फिर भी विफल होगा। दिखाई देने वाला descriptor target या SUID bit अकेले disclosure साबित नहीं करता।

Crash artifacts जांच का एक अलग रास्ता हैं: core dump में process memory हो सकती है, जिसमें पहले किसी higher identity के तहत पढ़ा गया data भी शामिल है। Ubuntu पर, [Apport normally places reports in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); अन्य systems में कोई अलग `core_pattern` handler या systemd storage इस्तेमाल हो सकता है। नियमित enumeration के दौरान केवल report paths, owner, mode और readability जांचें। कोई report तभी उपयोगी है जब संबंधित process dumpable था, crash handler ने संवेदनशील bytes सुरक्षित रखे, और मौजूदा user उस report तक पहुंच सकता हो। Passive enumeration के दौरान किसी helper को crash न करें और न ही dump unpack करें। SUID और dump-generation की शर्तों के लिए [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) देखें।

जब कोई service inherited descriptor इस्तेमाल करती है, तो shell redirection या `/proc/self/fd/<N>` आज़माने से पहले उसकी launch chain और descriptor numbers की समीक्षा करें। यदि कोई file delete हो गई है लेकिन अब भी खुली है, तो [deleted-file recovery](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) से evidence सुरक्षित रह सकता है या content recover हो सकता है। Process-level triage के लिए, [process enumeration and service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md) जारी रखें।
