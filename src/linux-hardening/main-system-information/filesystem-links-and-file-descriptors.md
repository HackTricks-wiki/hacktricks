# Symlinks, Hardlinks, और File Descriptors

{{#include ../../banners/hacktricks-training.md}}

किसी path का नाम उस object को दर्शाता है, जब उसे resolve किया जाता है; open file descriptor, pathname बदलने के बाद भी उस object का reference बनाए रखता है। यही अंतर symlink races, छिपे हुए hardlinks, deleted-file recovery और inherited descriptor leaks को समझाता है। inode और mount की पृष्ठभूमि के लिए [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) देखें।

## Links और path ownership का निरीक्षण करें

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Symlink pathname resolution को redirect करता है; hardlink उसी filesystem पर उसी inode का दूसरा नाम होता है। अगर कोई privileged task user-writable directory के अंदर किसी अनुमानित path को पढ़ता या लिखता है, तो user उस path को किसी sensitive target की ओर redirect कर सकता है। सिर्फ़ अंतिम file नहीं, हर parent directory के ownership और permissions जाँचें। `fs.protected_symlinks` और `fs.protected_hardlinks` आम cross-user attacks को सीमित करते हैं, लेकिन हर writable path को सुरक्षित नहीं बनाते।

ऐसे privileged job के लिए जो shell glob से permissions बदलता है, उन links में फ़र्क करें जो **command-line operands** के रूप में expand होते हैं और उन links में जो बाद में recursive traversal के दौरान मिलते हैं। [GNU `chmod` command line पर दिए गए symlink के referent पर काम करता है](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), जबकि recursion के दौरान मिले symlinks को यह आम तौर पर अनदेखा करता है; सिर्फ़ `-R` देने से ये दोनों मामले एक जैसे नहीं हो जाते। असल में scheduled identity और command, यह कि कोई untrusted user glob से match होने वाली entry बना सकता है या नहीं, install किए गए `chmod` का व्यवहार और options, तथा प्रस्तावित target की परिणामी access जाँचें। Writable directory या symlink अकेले privileged mode change साबित नहीं करते। Passive enumeration के दौरान symlink रखे या job trigger किए बिना script और path metadata जाँचें।

कोई scheduled privileged writer अपने output path को अनुमानित बना सकता है, भले filename में देखने में random hash हो: [C `rand()` एक ही `srand()` seed के लिए अपना sequence दोहराता है](https://man7.org/linux/man-pages/man3/rand.3.html), जिसमें ज्ञात execution time से निकाला गया seed भी शामिल है। अगर job वह नाम बनाते समय caller-writable database rows भी पढ़ता है, तो सटीक row-to-name algorithm, seed और libc का व्यवहार, schedule, caller के row लिखने और directory बनाने के अधिकार, तथा यह जाँचें कि privileged open से पहले कोई मौजूदा symlink रखा जा सकता है या नहीं। [`fopen(..., "w")` resolved file बनाता या truncate करता है](https://man7.org/linux/man-pages/man3/fopen.3.html); link-safe open flags या atomic replacement, effective write identity, target permissions और sticky-directory symlink policy के लिए असल implementation जाँचें। अनुमानित नाम या writable row अकेले सिर्फ़ जाँच का संकेत हैं। Passive enumeration के दौरान rows जोड़े या job चलाए बिना code, schedule और metadata जाँचें।

किसी दूसरे user के रूप में चलने वाली file-conversion service के लिए जाँचें कि caller output path या extension चुन सकता है या नहीं, और converter पहले से मौजूद output symlink को follow करता है या नहीं। कुछ converters output format, pathname extension से चुनते हैं; accepted extension वाले नाम का link किसी sensitive extensionless target की ओर फिर भी इशारा कर सकता है। Cross-user write के सफल होने के लिए service तक पहुँच, path और link पर caller का नियंत्रण, output के लिए link को खोलने वाला converter, और service identity के पास write permission होना ज़रूरी है। Linux में `fs.protected_symlinks=1` **sticky world-writable directory** में किसी दूसरे user के link को follow करने पर पाबंदी लगाता है; सामान्य user-owned directory के link को यह वही सुरक्षा नहीं देता। कोई निष्कर्ष निकालने से पहले resolved path और parent के ownership की जाँचें। [calibre का output-file व्यवहार](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) और [Linux symlink policy](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks) देखें।

अगर sudo से चलने वाला download wrapper caller के चुने हुए data को fetch करते समय caller-controlled working directory बनाए रखता है, तो उसके output path की भी इसी तरह जाँच करें। असल downloader और यह जाँचें कि उसका चुना हुआ basename, collision handling या पहले से मौजूद symlink privileged write को redirect कर सकता है या नहीं; सिर्फ़ URL चुन पाना या symlink होना काफ़ी नहीं है। [Axel प्रति-user `~/.axelrc` को दस्तावेज़ित करता है](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), और उसकी [उदाहरण configuration में `default_filename` और `no_clobber` शामिल हैं](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), इसलिए Axel इस्तेमाल करने वाला wrapper उस file से output-name का विकल्प भी ले सकता है। Effective `HOME` की पुष्टि करें: [sudo policy के अनुसार इसे reset या preserve कर सकता है](https://man7.org/linux/man-pages/man8/sudo.8.html), और user की `.axelrc` तभी प्रासंगिक है जब privileged downloader वास्तव में उसे पढ़ता हो। Passive enumeration के दौरान download शुरू किए बिना rule, wrapper, config path और permissions, अंतिम output name, तथा target-file की स्थिति जाँचें।

sudo से चलने वाले ACL wrapper के लिए, `setfacl` call करने से पहले caller द्वारा चुनी गई file को यह कैसे validate करता है, इसकी जाँच करें। केवल lexical prefix check और `..` को अस्वीकार करना, allowed directory के अंदर के symlink को बाहर resolve होने से नहीं रोकता; `test -f` भी link को follow करता है। पुष्टि करें कि wrapper पर्याप्त privilege के साथ ACL operation तक पहुँचता है, caller link को नियंत्रित करता है, और परिणामी ACL target **और उसकी parent directories** पर आवश्यक access देता है। कुछ consumers writable ACL या ढीले modes वाली files को अस्वीकार करते हैं, इसलिए सिर्फ़ ACL बदलना किसी काम करने वाले escalation path को साबित नहीं करता।

## User-mounted FUSE filesystems पर privileged writes की समीक्षा

`/etc/fuse.conf` में सक्रिय, standalone `user_allow_other` line किसी non-root user को FUSE mount पर `allow_other` या `allow_root` का अनुरोध करने देती है। ये mount options root process को उस filesystem तक पहुँच दे सकते हैं जिसे mount करने वाले user ने implement किया है। अगर sudo से चलने वाला helper caller-controlled working directory के relative path पर secret-bearing log या कोई अन्य output लिखता है, तो जाँचें कि क्या वह directory user-mounted FUSE filesystem हो सकती है। FUSE implementation writes को देख सकता है, भले ही सामान्य filesystem पर परिणामी file root-owned या mode `0600` की दिखे।

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

यह **संभावित मामला** है, disclosure का प्रमाण नहीं। वास्तविक sudo/run-as identity और arguments, helper का output path और संवेदनशील सामग्री, `/dev/fuse` तक पहुँच, `allow_other` या `allow_root` के साथ सफल mounting, और यह कि privileged process mount में प्रवेश कर सकता है या नहीं—इनकी पुष्टि करें। नियमित enumeration के दौरान privileged helper न चलाएँ और न ही filesystem mount करें। [libfuse policy description](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) और [libfuse access FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem) देखें।

## Path races खोजें

खतरनाक pattern तब होता है जब कोई privileged program एक pathname की जाँच करता है और बाद में जाँची गई object का सुरक्षित reference रखे बिना उसी pathname को खोलता है। किसी parent directory को नियंत्रित करने वाला attacker इन दोनों operations के बीच किसी file या symlink को बदल सकता है। यही समस्या temporary files, timer-driven scripts, archive extraction और backup workflows में भी दिखाई देती है। प्रभाव का दावा करने से पहले वास्तविक read/write operation और target की permissions की पुष्टि करें।

Archive **बनाने** से भी अलग-अलग identities के बीच files का disclosure हो सकता है। Info-ZIP `zip -r` आम तौर पर source tree के अंदर रखे symlink को follow करता है और target की सामग्री को store करता है; `-y`/`--symlinks` इसके बजाय link को ही store करता है। अगर कम-privileged user backed-up directory में link जोड़ सकता है, तो इस्तेमाल किए गए archiver/options, backup job की read identity, और यह जाँचें कि बना हुआ archive उस user के लिए readable है या नहीं। Writable source directory या अकेला symlink disclosure साबित नहीं करता। Backup को trigger किए बिना या enumeration के दौरान secret content extract किए बिना link और archive metadata की जाँच करें। [Info-ZIP option documentation](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638) देखें।

GNU `tar` का default अलग है: यह आम तौर पर symlink को link के रूप में store करता है, जबकि [`-h` / `--dereference` archive बनाते समय उसे follow करता है](https://www.gnu.org/software/tar/manual/html_node/dereference.html)। किसी privileged scheduled backup के लिए, इस्तेमाल किए गए सटीक `tar` invocation की जाँच करें; यह भी देखें कि क्या कम-privileged user `tar` द्वारा input pathname पढ़े जाने से पहले उसे बदल सकता है, और क्या बना हुआ archive उस user के लिए accessible है। Writable staging directory में रखा temporary checksum या कोई अन्य sidecar, बाद के `tar -h` command में उसका नाम स्पष्ट रूप से दिए जाने पर, ऐसा input बन सकता है। Race window, job identity, symlink policy, उस identity के तहत target की readability और archive ACL—इन सभी की पुष्टि ज़रूरी है। Passive checks के दौरान files न बदलें, job न चलाएँ और sensitive archives unpack न करें।

Archive **extract करने** पर एक अलग boundary पार होती है, जब कोई privileged job ऐसा archive पढ़ता है जिसे कम-privileged user बदल सकता है। [GNU tar आम तौर पर superuser के रूप में चलाए जाने पर archived ownership बहाल करता है](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), और इसके [permission-restoration options](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) extracted mode bits को प्रभावित करते हैं। इस्तेमाल किए गए सटीक extractor और flags, archive बदलने की window, numeric owner और mode metadata, extraction directory की permissions, और यह जाँचें कि cleanup के बाद परिणाम accessible रहता है या नहीं। Root-owned SUID member तभी चिंता का विषय है जब extraction के बाद उसका mode बना रहे और target mount तथा process policy identity बदलने की अनुमति दें; केवल untrusted archive या writable staging path इससे साबित नहीं होता। Passive enumeration के दौरान archive बदले या extract किए बिना job और metadata की जाँच करें।

Extract किया गया symlink बाद में होने वाली privileged comparison के ज़रिए protected file का disclosure भी कर सकता है। [GNU `diff` directories की तुलना करते समय आम तौर पर symlinks follow करता है](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), इसलिए untrusted extracted tree पर root के रूप में चलाया गया `diff -r` किसी link target को पढ़ सकता है और अपने output में अलग content शामिल कर सकता है। पुष्टि करें कि archive बदला जा सकता है, link ऐसे path पर पहुँचता है जहाँ comparison वास्तव में जाती है, target job के लिए readable है, और comparison output या error log कम-privileged user के लिए readable है। Link या archive अकेले disclosure साबित नहीं करते; enumeration के दौरान comparison चलाए या protected content पढ़े बिना job, path metadata और log permissions की जाँच करें।

Host-side transfer को दोहराने से untrusted archive member बाद के output path में बदल सकता है। अगर higher-privileged job lower-trust container से archive copy करता है, ऐसा symlink extract करता है जिसका नाम अगले transfer के destination basename के बराबर है, और बाद में उसी pathname पर लिखता है, तो बाद का write link target तक पहुँच सकता है। Archive member का नाम और target, extraction flags और directory, क्या extractor वास्तव में उस link को वहीं छोड़ता है, मौजूदा destination link के साथ transfer implementation का व्यवहार, और host job की effective write identity जाँचें। [GNU tar बताता है कि extraction मौजूदा files और symlinks को कैसे संभालता है](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [आधुनिक releases में OpenSSH scp default रूप से SFTP इस्तेमाल करता है](https://man.openbsd.org/scp.1), इसलिए यह मानने के बजाय कि सभी `scp` versions link के ज़रिए लिखते हैं, installed transfer behavior की पुष्टि करें। Container में दिखाई देने वाली `scp` process या writable archive अकेले host extraction और बाद के write को साबित नहीं करते। Enumeration के दौरान crafted archive transfer या extract किए बिना job और path metadata की जाँच करें।

Ansible का [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) rsync को wrap करता है; `copy_links: true` symlink के बजाय उसके referent को copy करता है। Scheduled backup के लिए जाँचें कि क्या कम-privileged user exact source tree के अंदर link बना सकता है, synchronization identity उसका target पढ़ सकती है या नहीं, और बनी हुई copy या archive उस user के लिए readable है या नहीं। Playbook, link placement, run-as identity और output permissions—इन सबका एक साथ मेल होना ज़रूरी है; writable upload directory या `copy_links` setting अकेले केवल जाँच का संकेत है। Link बनाए या job trigger किए बिना metadata और playbook की जाँच करें।

## Open descriptors की जाँच करें

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

कोई process, फ़ाइल को delete या rename किए जाने के बाद भी उस तक पहुँच बनाए रख सकता है। कोई privileged process Unix socket के ज़रिए descriptor भी भेज सकता है, या close-on-exec मौजूद न होने पर अनजाने में `execve()` के दौरान उसे खुला छोड़ सकता है। संवेदनशील फ़ाइलों, deleted फ़ाइलों, container के अंदर दिखाई देने वाले host paths और अप्रत्याशित sockets के लिए `/proc/<PID>/fd` के targets की जाँच करें। किसी दूसरे process के descriptors को dereference करना kernel access checks के अधीन है; दिखाई देने वाली symlink इस बात की गारंटी नहीं देती कि उसकी सामग्री पढ़ी जा सकती है।

कोई custom SUID helper, protected pathname को खोलकर अपना effective UID drop कर सकता है और descriptor को खुला छोड़ सकता है। अगर वह इसके बाद खुद को dumpable बनाता है, तो `/proc/<PID>/fd` का ownership और access बदल सकता है; credential transition, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), procfs/ptrace policy और target file mode की ठीक-ठीक जाँच करें। Descriptor path को दोबारा खोलने से कोई inaccessible **parent directory** bypass हो सकती है, लेकिन फिर भी ऐसी फ़ाइल खोलना विफल हो सकता है जिसे caller पढ़ नहीं सकता। केवल दिखाई देने वाला descriptor target या SUID bit, disclosure का प्रमाण नहीं है।

Crash artifacts एक अलग सुराग हैं: core dump में process memory हो सकती है, जिसमें पहले higher identity के तहत पढ़ा गया data भी शामिल है। Ubuntu पर, [Apport आमतौर पर reports को `/var/crash` में रखता है](https://documentation.ubuntu.com/project/contributors/debugging/apport/); दूसरे systems में अलग `core_pattern` handler या systemd storage इस्तेमाल हो सकता है। सामान्य enumeration के दौरान केवल report paths, owner, mode और readability की जाँच करें। कोई report तभी उपयोगी है, जब संबंधित process dumpable था, crash handler ने sensitive bytes सुरक्षित रखे हों और मौजूदा user उस report को access कर सके। Passive enumeration के हिस्से के तौर पर किसी helper को crash न करें और न ही dump को unpack करें। SUID और dump generation की शर्तों के लिए [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) देखें।

जब कोई service inherited descriptor का इस्तेमाल करती है, तो shell redirection या `/proc/self/fd/<N>` आज़माने से पहले उसकी launch chain और descriptor numbers की जाँच करें। अगर कोई फ़ाइल delete हो गई है लेकिन अब भी खुली है, तो [खुले FDs के ज़रिए deleted फ़ाइल की recovery](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) से evidence सुरक्षित रह सकता है या content recover हो सकता है। Process-level triage के लिए, [process enumeration और service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md) जारी रखें।
