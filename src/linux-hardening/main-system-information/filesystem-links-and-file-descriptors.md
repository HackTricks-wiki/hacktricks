# Symlink, hardlink e file descriptor

{{#include ../../banners/hacktricks-training.md}}

Un percorso indica un oggetto nel momento in cui viene risolto; un file descriptor aperto mantiene un riferimento all’oggetto anche dopo che il nome del percorso cambia. Questa differenza spiega le race condition con i symlink, gli hardlink nascosti, il recupero di file eliminati e le fughe di descriptor ereditati. Vedi [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) per informazioni di base su inode e mount.

## Esaminare i link e la proprietà dei percorsi

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink reindirizza la risoluzione dei pathname; un hardlink è un altro nome per lo stesso inode sullo stesso filesystem. Se un task privilegiato legge o scrive in un path prevedibile all'interno di una directory scrivibile dall'utente, quest'ultimo potrebbe riuscire a reindirizzare quel path verso un target sensibile. Controlla la proprietà e i permessi di ogni directory parent, non solo del file finale. `fs.protected_symlinks` e `fs.protected_hardlinks` riducono i comuni attacchi tra utenti, ma non rendono sicuri tutti i path scrivibili.

Per un job privilegiato che modifica i permessi usando uno shell glob, distingui i link espansi in **operandi della riga di comando** dai link trovati successivamente durante la traversata ricorsiva. [GNU `chmod` agisce sul referent di un symlink indicato nella riga di comando](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mentre normalmente ignora i symlink incontrati durante la ricorsione; `-R` da solo non rende equivalenti i due casi. Verifica l'identità e il comando effettivamente pianificati, se un utente non attendibile può creare una voce corrispondente al glob, il comportamento e le opzioni di `chmod` installato e i permessi che il target proposto otterrebbe. Una directory scrivibile o un symlink, da soli, non dimostrano che si verificherà una modifica privilegiata dei permessi. Esamina lo script e i metadati del path senza creare un link né attivare il job durante l'enumerazione passiva.

Un writer privilegiato pianificato può usare un path di output prevedibile anche quando il nome del file contiene un hash dall'aspetto casuale: [C `rand()` ripete la stessa sequenza con lo stesso seed di `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), anche quando il seed deriva da un orario di esecuzione noto. Se il job legge anche righe di database scrivibili dal chiamante per costruire quel nome, verifica l'esatto algoritmo che converte le righe in nomi, il seed e il comportamento di libc, la pianificazione, i permessi del chiamante per scrivere righe e creare directory e se è possibile posizionare un symlink preesistente prima dell'apertura privilegiata. [`fopen(..., "w")` crea o tronca il file risolto](https://man7.org/linux/man-pages/man3/fopen.3.html); controlla l'implementazione effettiva per verificare la presenza di flag di apertura sicuri rispetto ai link o di una sostituzione atomica, l'identità effettiva usata per la scrittura, i permessi del target e la policy sui symlink nelle directory sticky. Un nome prevedibile o una riga scrivibile, da soli, sono soltanto un punto di partenza per la verifica. Esamina il codice, la pianificazione e i metadati senza inserire righe né eseguire il job durante l'enumerazione passiva.

Per un servizio di conversione file in esecuzione con un altro utente, verifica se il chiamante può scegliere un path o un'estensione di output e se il convertitore segue un symlink di output preesistente. Alcuni convertitori scelgono il formato di output in base all'estensione del pathname; un link con un'estensione accettata può comunque puntare a un target sensibile senza estensione. Per riuscire a scrivere tra utenti servono un servizio raggiungibile, il controllo da parte del chiamante del path e del link, l'apertura del link in scrittura da parte del convertitore e i permessi di scrittura per l'identità del servizio. Linux `fs.protected_symlinks=1` limita il follow di un link appartenente a un altro utente in una **directory sticky scrivibile da tutti**; non offre la stessa protezione per un link in una normale directory di proprietà dell'utente. Esamina il path risolto e la proprietà della directory parent prima di trarre conclusioni. Vedi [il comportamento dei file di output di calibre](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) e la [policy Linux sui symlink](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Un wrapper di download consentito da sudo richiede la stessa verifica del path di output se scarica dati scelti dal chiamante mantenendo una directory di lavoro controllata da quest'ultimo. Esamina il downloader effettivo e verifica se il basename selezionato, la gestione delle collisioni o un symlink preesistente possono reindirizzare una scrittura privilegiata; la scelta dell'URL o un symlink, da soli, non bastano. [Axel documenta un file `~/.axelrc` per utente](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt) e il suo [file di configurazione di esempio include `default_filename` e `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), quindi un wrapper che usa Axel potrebbe anche ereditare da quel file la scelta del nome di output. Verifica il valore effettivo di `HOME`: [sudo può reimpostarlo o mantenerlo in base alla policy](https://man7.org/linux/man-pages/man8/sudo.8.html), e il file `.axelrc` di un utente è rilevante solo se il downloader privilegiato lo legge effettivamente. Controlla la regola, il wrapper, il path e i permessi della configurazione, il nome finale dell'output e lo stato del file target, senza avviare un download durante l'enumerazione passiva.

Per un wrapper ACL consentito da sudo, esamina come convalida un file scelto dal chiamante prima di chiamare `setfacl`. Un controllo del prefisso lessicale e il rifiuto di `..` non impediscono a un symlink all'interno della directory consentita di risolversi al di fuori di essa; anche `test -f` segue il link. Verifica che il wrapper raggiunga l'operazione ACL con privilegi sufficienti, che il chiamante controlli il link e che l'ACL risultante conceda l'accesso necessario sul target **e sulle relative directory parent**. Alcuni programmi che usano questi file rifiutano quelli con ACL scrivibili o permessi troppo permissivi, quindi una modifica dell'ACL da sola non dimostra che esista un percorso di escalation funzionante.

## Verifica le scritture privilegiate nei filesystem FUSE montati dagli utenti

Una riga attiva e standalone `user_allow_other` in `/etc/fuse.conf` consente a un utente non root di richiedere `allow_other` o `allow_root` su un mount FUSE. Queste opzioni di mount possono permettere a un processo root di accedere a un filesystem implementato dall'utente che lo ha montato. Se un helper consentito da sudo scrive un log contenente segreti o un altro output relativamente a una directory di lavoro controllata dal chiamante, verifica se tale directory può essere un filesystem FUSE montato dall'utente. L'implementazione FUSE può osservare le scritture anche quando il file risultante appare di proprietà di root o con modalità `0600` su un filesystem ordinario.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Questo è un **possibile caso**, non una prova di disclosure. Verifica l'identità e gli argomenti effettivi di sudo/run-as, il percorso di output dell'helper e i contenuti sensibili, l'accesso a `/dev/fuse`, il successo del mount con `allow_other` o `allow_root` e se il processo privilegiato può accedere al mount. Non eseguire l'helper privilegiato né montare un filesystem durante la normale enumerazione. Consulta la [descrizione delle policy di libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) e le [FAQ sull'accesso di libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Cerca le race condition sui path

Lo schema pericoloso si verifica quando un programma privilegiato controlla un pathname e in seguito lo apre senza mantenere un riferimento sicuro all'oggetto verificato. Un attaccante che controlla una directory padre può sostituire un file o un symlink tra le due operazioni. Lo stesso problema si presenta con i file temporanei, gli script eseguiti da timer, l'estrazione di archivi e i flussi di lavoro di backup. Prima di dichiarare un impatto, verifica l'effettiva operazione di lettura/scrittura e i permessi del target.

Anche la **creazione** di archivi può esporre file tra identità diverse. Di norma, Info-ZIP `zip -r` segue un symlink inserito nell'albero sorgente e archivia i contenuti del target; `-y`/`--symlinks` archivia invece il link stesso. Se un utente con privilegi inferiori può aggiungere un link a una directory inclusa nel backup, verifica l'archiviatore e le opzioni effettivi, l'identità di lettura del processo di backup e se l'archivio risultante è leggibile da quell'utente. Una directory sorgente scrivibile o un symlink, da soli, non dimostrano una disclosure. Esamina i metadati di link e archivi senza attivare il backup né estrarre contenuti segreti durante l'enumerazione. Consulta la [documentazione delle opzioni di Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` ha un comportamento predefinito diverso: normalmente archivia un symlink come link, mentre [`-h` / `--dereference` lo segue durante la creazione dell'archivio](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Per un backup pianificato con privilegi elevati, esamina l'invocazione esatta di `tar`, verifica se un utente con privilegi inferiori può sostituire un pathname di input prima che `tar` lo legga e se l'archivio risultante è accessibile a quell'utente. Un checksum temporaneo o un altro file sidecar in una directory di staging scrivibile può diventare un input di questo tipo se viene specificato esplicitamente in un successivo comando `tar -h`. Occorre verificare la finestra temporale della race, l'identità del job, la policy sui symlink, la leggibilità del target con tale identità e le ACL dell'archivio. Durante i controlli passivi, non sostituire file, eseguire il job o estrarre archivi sensibili.

L'**estrazione** di archivi oltrepassa un confine diverso quando un job privilegiato legge un archivio che un utente con privilegi inferiori può sostituire. [GNU tar normalmente ripristina la proprietà archiviata quando viene eseguito dal superuser](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html) e le sue [opzioni per il ripristino dei permessi](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) influiscono sui bit di modalità dei file estratti. Esamina l'estrattore e i flag effettivi, la finestra temporale in cui l'archivio può essere sostituito, i metadati numerici di proprietario e modalità, i permessi della directory di estrazione e se la pulizia lascia il risultato accessibile. Un membro SUID di proprietà di root è preoccupante solo se la sua modalità sopravvive all'estrazione e le policy del mount e del processo consentono il cambio d'identità; un archivio non attendibile o un percorso di staging scrivibile, da soli, non lo dimostrano. Durante l'enumerazione passiva, esamina il job e i metadati senza sostituire o estrarre archivi.

Un symlink estratto può anche esporre un file protetto tramite un successivo confronto privilegiato. [GNU `diff` normalmente segue i symlink quando confronta directory](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), quindi un `diff -r` eseguito da root su un albero estratto non attendibile può leggere il target di un link e includere nel proprio output i contenuti diversi. Verifica che l'archivio possa essere sostituito, che il link punti a un percorso effettivamente esaminato dal confronto, che il job possa leggere il target e che l'output del confronto o il log degli errori siano leggibili dall'utente con privilegi inferiori. Il link o l'archivio, da soli, non dimostrano una disclosure; durante l'enumerazione, esamina il job, i metadati dei path e i permessi dei log senza eseguire il confronto né leggere contenuti protetti.

Un trasferimento ripetuto lato host può trasformare un membro di archivio non attendibile in un successivo percorso di output. Se un job con privilegi superiori copia un archivio da un container con un livello di fiducia inferiore, estrae un symlink il cui nome corrisponde al basename della destinazione del trasferimento successivo e poi scrive sullo stesso pathname, la scrittura successiva potrebbe raggiungere il target del link. Verifica il nome del membro dell'archivio e il target, i flag e la directory di estrazione, se l'estrattore lascia effettivamente quel link al suo posto, come l'implementazione del trasferimento gestisce un link di destinazione già esistente e l'identità effettiva con cui il job host scrive. [GNU tar documenta come l'estrazione gestisce file e symlink già esistenti](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [nelle versioni moderne, OpenSSH scp usa SFTP per impostazione predefinita](https://man.openbsd.org/scp.1), quindi verifica il comportamento dello strumento di trasferimento installato invece di presumere che tutte le versioni di `scp` scrivano attraverso un link. Un processo `scp` visibile dal container o un archivio scrivibile, da soli, non dimostrano che l'host esegua l'estrazione e la scrittura successive. Durante l'enumerazione, esamina il job e i metadati dei path senza trasferire o estrarre un archivio creato appositamente.

Il [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) di Ansible si basa su rsync; `copy_links: true` copia il contenuto referenziato da un symlink invece del link stesso. Per un backup pianificato, verifica se un utente con privilegi inferiori può creare un link all'interno dell'esatto albero sorgente, se l'identità usata per la sincronizzazione può leggere il target e se la copia o l'archivio risultante è leggibile da quell'utente. Playbook, posizione del link, identità run-as e permessi dell'output devono essere tutti compatibili; una directory di upload scrivibile o l'impostazione `copy_links`, da sole, sono soltanto elementi da approfondire. Esamina i metadati e il playbook senza creare link né attivare il job.

## Esamina i file descriptor aperti

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un processo può mantenere l'accesso a un file dopo che è stato eliminato o rinominato. Un processo con privilegi può anche passare un descrittore tramite un socket Unix oppure lasciarlo involontariamente aperto durante `execve()` se manca close-on-exec. Esamina i target di `/proc/<PID>/fd` alla ricerca di file sensibili, file eliminati, percorsi dell'host visibili all'interno di un container e socket inattesi. Il dereferenziamento dei descrittori di un altro processo è soggetto ai controlli di accesso del kernel; un symlink visibile non garantisce che il suo contenuto sia leggibile.

Un helper SUID personalizzato può aprire un percorso protetto, abbassare il proprio UID effettivo e lasciare aperto il descrittore. Se poi imposta se stesso come dumpable, proprietà e accesso a `/proc/<PID>/fd` possono cambiare; verifica l'esatta transizione delle credenziali, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), le policy di procfs/ptrace e i permessi del file target. Riaprire il percorso di un descrittore può aggirare una **directory padre** inaccessibile, ma fallire comunque se il chiamante non può leggere il file. Un target del descrittore visibile o il solo bit SUID non dimostrano che i dati siano divulgati.

Gli artefatti di crash sono una pista separata: un core dump può contenere la memoria del processo, inclusi dati letti in precedenza con un'identità più privilegiata. Su Ubuntu, [Apport colloca normalmente i report in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); altri sistemi possono usare un handler `core_pattern` diverso o l'archiviazione di systemd. Durante l'enumerazione di routine, controlla solo i percorsi dei report, il proprietario, i permessi e la leggibilità. Un report leggibile è rilevante solo se il processo interessato era dumpable, l'handler di crash ha conservato i byte sensibili e l'utente corrente può accedere al report. Non mandare in crash un helper né estrarre un dump durante l'enumerazione passiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) per le condizioni relative a SUID e alla generazione dei dump.

Quando un servizio usa un descrittore ereditato, verifica la catena di avvio e i numeri dei descrittori prima di provare il reindirizzamento della shell o `/proc/self/fd/<N>`. Se un file è stato eliminato ma è ancora aperto, il [recupero dei file eliminati](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) può preservare le prove o recuperare il contenuto. Per il triage a livello di processo, continua con [l'enumerazione dei processi e i percorsi dei servizi](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
