# シンボリックリンク、ハードリンク、ファイルディスクリプター

{{#include ../../banners/hacktricks-training.md}}

パスは解決された時点のオブジェクトを指します。一方、open file descriptor は、パス名が変更された後もオブジェクトへの参照を保持します。この違いによって、シンボリックリンクの競合状態、隠れたハードリンク、削除済みファイルの復元、継承されたディスクリプターの leak を説明できます。inode とマウントの背景については、[filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) を参照してください。

## リンクとパスの所有権を調べる

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

シンボリックリンクはパス名の解決先を変更します。ハードリンクは、同じファイルシステム上の同じ inode に対する別名です。特権タスクがユーザー書き込み可能なディレクトリ内の予測可能なパスを読み書きする場合、ユーザーがそのパスを機密性の高い対象へリダイレクトできる可能性があります。最終ファイルだけでなく、すべての親ディレクトリの所有者と権限を確認してください。`fs.protected_symlinks` と `fs.protected_hardlinks` は、一般的なユーザー間攻撃を軽減しますが、任意の書き込み可能なパスを安全にするものではありません。

シェルの glob を使って権限を変更する特権ジョブでは、**コマンドライン引数**として展開されたリンクと、再帰的な走査中に後から見つかるリンクを区別してください。[GNU `chmod` は、コマンドラインで指定されたシンボリックリンクの参照先に作用します](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html)。一方、再帰処理中に遭遇したシンボリックリンクは通常無視します。`-R` を指定するだけで、この2つのケースが同じ動作になるわけではありません。実際の実行 ID とコマンド、信頼されていないユーザーが glob に一致するエントリを作成できるか、インストール済み `chmod` の動作とオプション、対象に適用された場合のアクセス権を確認してください。書き込み可能なディレクトリやシンボリックリンクがあるだけでは、特権によるモード変更が起きるとは限りません。受動的な列挙中は、リンクを作成したりジョブを実行したりせずに、スクリプトとパスのメタデータを調べてください。

特権スケジュールジョブが、ファイル名にランダムに見えるハッシュを含めていても、出力先のパスが予測可能な場合があります。[C の `rand()` は、同じ `srand()` シードでシーケンスを繰り返します](https://man7.org/linux/man-pages/man3/rand.3.html)。既知の実行時刻からシードが導出される場合も同様です。さらに、ジョブがその名前の生成時に呼び出し元が書き込み可能なデータベース行を読み取る場合は、行から名前への正確な変換アルゴリズム、シードと libc の動作、スケジュール、呼び出し元が持つ行の書き込み権限とディレクトリ作成権限、特権プロセスがファイルを開く前に既存のシンボリックリンクを配置できるかを確認してください。[`fopen(..., "w")` は解決後のファイルを作成または切り詰めます](https://man7.org/linux/man-pages/man3/fopen.3.html)。リンク対策の open フラグやアトミックな置換の有無、実効的な書き込み ID、対象ファイルの権限、sticky ディレクトリでのシンボリックリンクポリシーも、実際の実装で確認してください。予測可能な名前や書き込み可能な行があるだけなら、あくまで調査の手掛かりです。受動的な列挙中は、行を挿入したりジョブを実行したりせずに、コード、スケジュール、メタデータを調べてください。

別のユーザーとして動作するファイル変換サービスでは、呼び出し元が出力パスや拡張子を選択できるか、変換ツールが既存の出力シンボリックリンクをたどるかを確認してください。変換ツールによっては、パス名の拡張子から出力形式を選択します。受け付けられる拡張子を持つリンクでも、拡張子のない機密性の高い対象を指すことがあります。ユーザー間の書き込みを成立させるには、サービスにアクセス可能であること、呼び出し元がパスとリンクを制御できること、変換ツールがリンクを出力用に開くこと、サービスの実行 ID に書き込み権限があることが必要です。Linux の `fs.protected_symlinks=1` は、**sticky 属性付きの全ユーザー書き込み可能ディレクトリ**内で別ユーザーのリンクをたどる動作を制限します。通常のユーザー所有ディレクトリ内のリンクには、同じ保護を提供しません。結論を出す前に、解決後のパスと親ディレクトリの所有者を確認してください。[calibre の出力ファイルの動作](https://manual.calibre-ebook.com/generated/en/ebook-convert.html)と[Linux のシンボリックリンクポリシー](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks)を参照してください。

sudo で実行を許可されたダウンロードラッパーについても、呼び出し元が制御する作業ディレクトリを維持したまま、呼び出し元が選んだデータを取得する場合は、同じ出力パスの確認が必要です。実際のダウンローダーと、選択されるベース名、ファイル名の衝突処理、既存のシンボリックリンクが特権による書き込みをリダイレクトできるかを調べてください。URL の選択やシンボリックリンクだけでは不十分です。[Axel はユーザーごとの `~/.axelrc` を説明しています](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt)。また、[設定例には `default_filename` と `no_clobber` が含まれています](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example)。そのため Axel を使うラッパーは、このファイルから出力名の指定を引き継ぐ可能性もあります。実効的な `HOME` を確認してください。[sudo はポリシーに応じて `HOME` をリセットまたは維持できます](https://man7.org/linux/man-pages/man8/sudo.8.html)。ユーザーの `.axelrc` が関係するのは、特権ダウンローダーが実際にそのファイルを読み込む場合に限られます。受動的な列挙中は、ダウンロードを開始せずに、ルール、ラッパー、設定ファイルのパスと権限、最終的な出力名、対象ファイルの状態を確認してください。

sudo で実行を許可された ACL ラッパーについては、`setfacl` を呼び出す前に、呼び出し元が選択したファイルをどのように検証するかを調べてください。字句的なプレフィックス確認や `..` の拒否では、許可されたディレクトリ内のシンボリックリンクが外部へ解決されることを防げません。また、`test -f` もリンクをたどります。ラッパーが十分な権限で ACL 操作に到達すること、呼び出し元がリンクを制御できること、適用後の ACL が対象**およびその親ディレクトリ**に必要なアクセス権を与えることを確認してください。書き込み可能な ACL や緩いモードのファイルを拒否する利用側プログラムもあるため、ACL の変更だけでは権限昇格につながるとは限りません。

## ユーザーがマウントした FUSE ファイルシステムへの特権書き込みの確認

`/etc/fuse.conf` に有効な単独行 `user_allow_other` があると、root 以外のユーザーは FUSE マウントに `allow_other` または `allow_root` を指定できます。これらのマウントオプションにより、root プロセスがマウントしたユーザーの実装するファイルシステムにアクセスできる場合があります。sudo で実行を許可されたヘルパーが、呼び出し元の制御する作業ディレクトリを基準に、秘密情報を含むログやその他の出力を書き込む場合、そのディレクトリがユーザーのマウントした FUSE ファイルシステムであり得るかを確認してください。通常のファイルシステム上では最終的なファイルが root 所有またはモード `0600` に見えても、FUSE の実装側は書き込みを観察できます。

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

これは**候補**であり、情報開示の証拠ではありません。実際の sudo/run-as identity と引数、helper の出力パスと機密情報の内容、`/dev/fuse` へのアクセス、`allow_other` または `allow_root` を指定したマウントの成功、そして特権プロセスがマウント内に入れるかを確認してください。通常の列挙中に特権 helper を実行したり、ファイルシステムをマウントしたりしないでください。[libfuse のポリシー説明](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf)と[libfuse のアクセスに関する FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem)を参照してください。

## パス競合を探す

危険なパターンは、特権プログラムがあるパス名を検査した後、検査対象への安全な参照を保持せずに同じパス名を開くことです。親ディレクトリを制御できる攻撃者は、2つの操作の間にファイルやシンボリックリンクを置き換えられます。同じ問題は、一時ファイル、タイマーで起動されるスクリプト、アーカイブの展開、バックアップのワークフローにも生じます。影響を主張する前に、実際の読み書き操作と対象の権限を確認してください。

アーカイブの**作成**によっても、異なる identity 間でファイルが開示されることがあります。Info-ZIP の `zip -r` は通常、ソースツリー内に置かれたシンボリックリンクをたどり、リンク先の内容を保存します。一方、`-y`/`--symlinks` はリンク自体を保存します。低権限ユーザーがバックアップ対象ディレクトリにリンクを追加できる場合は、実際の archiver/options、バックアップジョブの読み取り identity、生成されたアーカイブをそのユーザーが読めるかを確認してください。書き込み可能なソースディレクトリやシンボリックリンクがあるだけでは、情報開示の証明にはなりません。バックアップを実行したり、列挙中に機密情報を展開したりせず、リンクとアーカイブのメタデータを確認してください。[Info-ZIP のオプションに関するドキュメント](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638)を参照してください。

GNU `tar` のデフォルト動作は異なります。通常はシンボリックリンクをリンクとして保存し、アーカイブ作成時に[`-h` / `--dereference` を指定するとリンクをたどります](https://www.gnu.org/software/tar/manual/html_node/dereference.html)。特権で定期実行されるバックアップでは、実際の `tar` 呼び出し、`tar` が読み取る前に低権限ユーザーが入力パス名を置き換えられるか、生成されたアーカイブをそのユーザーが利用できるかを確認してください。書き込み可能なステージングディレクトリにある一時的な checksum などの sidecar ファイルも、後続の `tar -h` コマンドで明示的に指定されれば、そのような入力になり得ます。競合の発生時間帯、ジョブの identity、シンボリックリンクのポリシー、その identity でのリンク先の読み取り可否、アーカイブの ACL をすべて検証する必要があります。受動的なチェック中にファイルを置き換えたり、ジョブを実行したり、機密アーカイブを展開したりしないでください。

特権ジョブが低権限ユーザーによって置き換え可能なアーカイブを読む場合、アーカイブの**展開**では別の境界を越えることになります。[GNU tar はスーパーユーザーとして実行されると、通常はアーカイブ内の所有権を復元します](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html)。また、[権限復元オプション](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html)は、展開されるファイルの mode bits に影響します。実際の extractor と flags、アーカイブを置き換えられる時間帯、数値の owner と mode のメタデータ、展開先ディレクトリの権限、クリーンアップ後も結果を利用できるかを確認してください。root 所有の SUID メンバーが問題となるのは、展開後もその mode が維持され、対象の mount とプロセスのポリシーが identity の変更を許す場合に限られます。信頼できないアーカイブや書き込み可能なステージングパスがあるだけでは、これが起きる証明にはなりません。受動的な列挙中にアーカイブを置き換えたり展開したりせず、ジョブとメタデータを確認してください。

展開されたシンボリックリンクが、後続の特権比較処理を通じて保護されたファイルを開示することもあります。[GNU `diff` は通常、ディレクトリを比較する際にシンボリックリンクをたどります](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html)。そのため、信頼できない展開済みツリーに対する root 実行の `diff -r` は、リンク先を読み取り、異なる内容を出力に含める可能性があります。アーカイブを置き換えられること、比較処理が実際にたどるパスにリンクが作成されること、ジョブがリンク先を読めること、比較結果またはエラーログを低権限ユーザーが読めることを確認してください。リンクやアーカイブがあるだけでは、情報開示の証明にはなりません。列挙中に比較処理を実行したり、保護された内容を読んだりせず、ジョブ、パスのメタデータ、ログの権限を確認してください。

ホスト側で転送が繰り返されると、信頼できないアーカイブメンバーが後続の出力パスになることがあります。より高い権限のジョブが、信頼度の低いコンテナからアーカイブをコピーし、次の転送先のベース名と同じ名前のシンボリックリンクを展開し、その後同じパス名に書き込む場合、後続の書き込みがリンク先に到達する可能性があります。アーカイブメンバーの名前とリンク先、展開時の flags とディレクトリ、extractor が実際にそのリンクを残すか、既存の宛先リンクを転送実装がどう扱うか、ホストジョブの実効書き込み identity を確認してください。[GNU tar は展開時に既存ファイルやシンボリックリンクをどう扱うかを説明しています](https://www.gnu.org/software/tar/manual/html_section/extract-options.html)。また、[最近のリリースでは OpenSSH scp はデフォルトで SFTP を使用します](https://man.openbsd.org/scp.1)。すべての `scp` バージョンがリンクをたどって書き込むと想定せず、インストール済みの転送動作を確認してください。コンテナから見える `scp` プロセスや書き込み可能なアーカイブだけでは、ホストでの展開や後続の書き込みが起きる証明にはなりません。列挙中に細工したアーカイブを転送または展開せず、ジョブとパスのメタデータを確認してください。

Ansible の[`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html)は rsync をラップします。`copy_links: true` はシンボリックリンク自体ではなく、リンク先をコピーします。定期実行されるバックアップでは、低権限ユーザーが正確なソースツリー内にリンクを作成できるか、同期 identity がリンク先を読めるか、生成されたコピーまたはアーカイブをそのユーザーが読めるかを確認してください。playbook、リンクの配置、run-as identity、出力の権限がすべて揃う必要があります。書き込み可能なアップロードディレクトリや `copy_links` の設定だけなら、調査の手がかりにすぎません。リンクを作成したりジョブを実行したりせずに、メタデータと playbook を確認してください。

## オープン中の descriptor を調べる

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

プロセスは、ファイルが削除または名前変更された後も、そのファイルへのアクセスを保持できます。特権プロセスが Unix socket 経由でファイルディスクリプタを渡す場合や、close-on-exec が設定されていないために `execve()` 後も意図せずファイルディスクリプタを開いたままにする場合もあります。`/proc/<PID>/fd` のリンク先を調べ、機密ファイル、削除済みファイル、コンテナ内から見えるホストのパス、予期しない socket がないか確認してください。別プロセスのファイルディスクリプタを参照する際は、カーネルのアクセスチェックが適用されます。symlink が見えていても、その内容を読み取れるとは限りません。

カスタム SUID helper が保護されたパスを開き、実効 UID を下げた後もファイルディスクリプタを開いたままにする場合があります。その後、自身を dumpable に設定すると、`/proc/<PID>/fd` の所有権とアクセス権が変化することがあります。実際の credential の遷移、[`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html)、procfs/ptrace のポリシー、対象ファイルの mode を確認してください。ファイルディスクリプタのパスを再度開くと、アクセスできない **親ディレクトリ** を迂回できることがありますが、呼び出し元が読み取れないファイルは引き続き開けません。ファイルディスクリプタのリンク先が見えることや SUID bit が設定されていることだけでは、情報漏えいの証拠になりません。

クラッシュアーティファクトも別の手掛かりになります。core dump には、より高い権限で以前読み込まれたデータを含め、プロセスメモリが含まれる場合があります。Ubuntu では、[Apport は通常、レポートを `/var/crash` に保存します](https://documentation.ubuntu.com/project/contributors/debugging/apport/)。ほかのシステムでは、異なる `core_pattern` handler や systemd のストレージが使われることがあります。通常の列挙では、レポートのパス、所有者、mode、読み取り可否だけを確認してください。読み取り可能なレポートが問題となるのは、対象プロセスが dumpable であり、クラッシュ handler が機密データを保持し、現在のユーザーがそのレポートにアクセスできる場合に限られます。受動的な列挙の一環として helper をクラッシュさせたり、dump を展開したりしないでください。SUID と dump 生成の条件については、[`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) を参照してください。

サービスが継承したファイルディスクリプタを使用する場合、shell のリダイレクトや `/proc/self/fd/<N>` を試す前に、起動チェーンとファイルディスクリプタ番号を確認してください。ファイルが削除済みでも開かれたままなら、[開いているファイルディスクリプタを使った削除済みファイルの復旧](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds)によって、証拠を保持したり内容を復旧したりできる場合があります。プロセス単位のトリアージを続けるには、[プロセスの列挙とサービスのパス](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md)を参照してください。
