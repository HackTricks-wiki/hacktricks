# Link simbolici, hard link e descrittori di file

{{#include ../../banners/hacktricks-training.md}}

Un percorso identifica un oggetto nel momento in cui viene risolto; un descrittore di file aperto mantiene un riferimento all’oggetto anche dopo che il nome del percorso è cambiato. Questa differenza spiega le race condition sui link simbolici, gli hard link nascosti, il recupero di file eliminati e le fughe di descrittori ereditati. Consulta [filesystem, inode e recupero](filesystem-inodes-and-recovery.md) per informazioni di base su inode e mount.

## Esaminare i link e la proprietà dei percorsi

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink reindirizza la risoluzione del pathname; un hardlink è un altro nome per lo stesso inode sullo stesso filesystem. Se un'attività con privilegi legge o scrive in un percorso prevedibile all'interno di una directory scrivibile dall'utente, quest'ultimo potrebbe riuscire a reindirizzare quel percorso verso una destinazione sensibile. Controlla proprietà e permessi di ogni directory padre, non solo del file finale. `fs.protected_symlinks` e `fs.protected_hardlinks` riducono i comuni attacchi tra utenti, ma non rendono sicuri i percorsi scrivibili arbitrari.

Per un'attività con privilegi che modifica i permessi usando una shell glob, distingui i link espansi in **argomenti della riga di comando** dai link trovati successivamente durante la traversata ricorsiva. [GNU `chmod` agisce sul referente di un symlink indicato nella riga di comando](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mentre normalmente ignora i symlink incontrati durante la ricorsione; `-R` da solo non rende equivalenti i due casi. Esamina l'identità e il comando effettivamente pianificati, se un utente non attendibile può creare una voce corrispondente alla glob, il comportamento e le opzioni di `chmod` installato e l'accesso risultante sulla destinazione proposta. Una directory scrivibile o un symlink, da soli, non dimostrano che si verificherà una modifica dei permessi privilegiata. Esamina lo script e i metadati dei percorsi senza inserire un link né attivare l'attività durante l'enumerazione passiva.

Un processo pianificato con privilegi può rendere prevedibile il percorso di output anche quando il nome del file contiene un hash dall'aspetto casuale: [`rand()` in C ripete la sequenza per lo stesso seed di `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), anche quando il seed deriva da un orario di esecuzione noto. Se inoltre l'attività legge righe di database scrivibili dal chiamante per costruire quel nome, verifica l'esatto algoritmo di conversione da riga a nome, il seed e il comportamento di libc, la pianificazione, i diritti del chiamante per modificare le righe e creare directory e la possibilità di collocare un symlink preesistente prima dell'apertura con privilegi. [`fopen(..., "w")` crea o tronca il file risolto](https://man7.org/linux/man-pages/man3/fopen.3.html); controlla l'implementazione effettiva per verificare la presenza di flag di apertura sicura rispetto ai link o della sostituzione atomica, l'identità effettiva con cui si scrive, i permessi della destinazione e la policy sui symlink nelle directory sticky. Un nome prevedibile o una riga scrivibile, da soli, sono soltanto elementi da approfondire. Esamina codice, pianificazione e metadati senza inserire righe né eseguire l'attività durante l'enumerazione passiva.

Per un servizio di conversione file eseguito come un altro utente, verifica se il chiamante può scegliere un percorso o un'estensione di output e se il convertitore segue un symlink di output preesistente. Alcuni convertitori selezionano il formato di output dall'estensione del pathname; un link con un'estensione accettata può comunque puntare a una destinazione sensibile senza estensione. Perché una scrittura tra utenti riesca, servono un servizio raggiungibile, il controllo del percorso e del link da parte del chiamante, l'apertura del link in scrittura da parte del convertitore e i permessi di scrittura per l'identità del servizio. Linux `fs.protected_symlinks=1` limita il seguire il link di un altro utente in una **directory sticky scrivibile da tutti**; non offre la stessa protezione per un link in una normale directory di proprietà di un utente. Esamina il percorso risolto e la proprietà delle directory padre prima di trarre conclusioni. Vedi [il comportamento di calibre per i file di output](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) e la [policy di Linux sui symlink](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Anche per un wrapper di download consentito da sudo occorre esaminare il percorso di output, se scarica dati scelti dal chiamante mantenendo una directory di lavoro controllata da quest'ultimo. Esamina il downloader effettivo e verifica se il basename selezionato, la gestione delle collisioni o un symlink preesistente possono reindirizzare una scrittura privilegiata; la scelta dell'URL o un symlink, da soli, non bastano. [Axel documenta un `~/.axelrc` per utente](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt) e il suo [file di configurazione di esempio include `default_filename` e `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), quindi un wrapper che usa Axel potrebbe anche ereditare da quel file la scelta del nome di output. Verifica l'effettivo `HOME`: [sudo può reimpostarlo o mantenerlo in base alla policy](https://man7.org/linux/man-pages/man8/sudo.8.html) e il `.axelrc` dell'utente è pertinente solo se il downloader con privilegi lo legge davvero. Controlla la regola, il wrapper, il percorso e i permessi della configurazione, il nome di output finale e lo stato del file di destinazione, senza avviare un download durante l'enumerazione passiva.

Per un wrapper ACL consentito da sudo, verifica come convalida un file scelto dal chiamante prima di invocare `setfacl`. Un controllo del prefisso lessicale e il rifiuto di `..` non impediscono a un symlink all'interno della directory consentita di risolversi al di fuori di essa; anche `test -f` segue il link. Verifica che il wrapper possa eseguire l'operazione ACL con privilegi sufficienti, che il chiamante controlli il link e che l'ACL risultante conceda l'accesso necessario sulla destinazione **e sulle relative directory padre**. Alcuni programmi che utilizzano i file rifiutano quelli con ACL scrivibili o permessi troppo permissivi, quindi una modifica ACL, da sola, non dimostra l'esistenza di un percorso di escalation funzionante.

## Esaminare le scritture privilegiate nei filesystem FUSE montati dagli utenti

Una riga attiva e autonoma `user_allow_other` in `/etc/fuse.conf` consente a un utente non root di richiedere `allow_other` o `allow_root` su un mount FUSE. Queste opzioni di mount possono permettere a un processo root di accedere a un filesystem implementato dall'utente che lo ha montato. Se un helper consentito da sudo scrive un log contenente segreti o altri output relativi a una directory di lavoro controllata dal chiamante, verifica se quella directory può essere un filesystem FUSE montato dall'utente. L'implementazione FUSE può osservare le scritture anche quando il file risultante appare di proprietà di root o con permessi `0600` su un filesystem ordinario.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Questo è un **possibile indizio**, non una prova di divulgazione. Verifica l'identità e gli argomenti effettivi di sudo/run-as, il percorso di output dell'helper e i contenuti sensibili, l'accesso a `/dev/fuse`, il corretto montaggio con `allow_other` o `allow_root` e se il processo privilegiato può accedere al mount. Non eseguire l'helper privilegiato né montare un filesystem durante la normale enumerazione. Consulta la [descrizione delle policy di libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) e le [FAQ sull'accesso di libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Cerca race condition nei percorsi

Lo schema pericoloso è un programma privilegiato che verifica un percorso e in seguito apre lo stesso percorso senza mantenere un riferimento sicuro all'oggetto verificato. Un attaccante che controlla una directory padre può sostituire un file o un symlink tra le due operazioni. Lo stesso problema si presenta con i file temporanei, gli script eseguiti da timer, l'estrazione di archivi e i flussi di lavoro di backup. Prima di dichiarare un impatto, verifica l'effettiva operazione di lettura/scrittura e i permessi della destinazione.

Anche la **creazione** di archivi può divulgare file tra identità diverse. Info-ZIP `zip -r` normalmente segue un symlink inserito nell'albero sorgente e archivia i contenuti della destinazione; `-y`/`--symlinks`, invece, archivia il link stesso. Se un utente con privilegi inferiori può aggiungere un link in una directory sottoposta a backup, verifica l'archiver e le opzioni esatti, l'identità con cui il job di backup legge i file e se l'utente può leggere l'archivio risultante. Una directory sorgente scrivibile o un symlink, da soli, non dimostrano una divulgazione. Durante l'enumerazione, esamina i metadati dei link e dell'archivio senza attivare il backup né estrarre contenuti segreti. Consulta la [documentazione delle opzioni di Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` ha un comportamento predefinito diverso: normalmente archivia un symlink come link, mentre [`-h` / `--dereference` lo segue durante la creazione dell'archivio](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Per un backup pianificato con privilegi elevati, esamina l'invocazione esatta di `tar`, verifica se un utente con privilegi inferiori può sostituire un percorso di input prima che `tar` lo legga e se tale utente può accedere all'archivio risultante. Un checksum temporaneo o un altro file accessorio in una directory di staging scrivibile può diventare un input di questo tipo se viene indicato esplicitamente in un successivo comando `tar -h`. Occorre verificare la finestra di race condition, l'identità del job, la policy sui symlink, la leggibilità della destinazione con quell'identità e gli ACL dell'archivio. Durante i controlli passivi, non sostituire file, eseguire il job né estrarre archivi sensibili.

L'**estrazione** di un archivio oltrepassa un confine diverso quando un job privilegiato legge un archivio che un utente con privilegi inferiori può sostituire. [GNU tar normalmente ripristina la proprietà archiviata quando viene eseguito dal superuser](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html) e le sue [opzioni per il ripristino dei permessi](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) influiscono sui bit di modalità dei file estratti. Esamina l'estrattore e i flag esatti, la finestra temporale in cui l'archivio può essere sostituito, i metadati numerici di proprietario e modalità, i permessi della directory di estrazione e se la pulizia lascia i file risultanti accessibili. Un membro SUID di proprietà di root è un rischio solo se la sua modalità viene preservata durante l'estrazione e le policy del mount e del processo di destinazione consentono il cambio di identità; un archivio non attendibile o un percorso di staging scrivibile, da soli, non lo dimostrano. Durante l'enumerazione passiva, esamina il job e i metadati senza sostituire né estrarre un archivio.

Un symlink estratto può anche divulgare un file protetto tramite un successivo confronto eseguito con privilegi elevati. [GNU `diff` normalmente segue i symlink quando confronta directory](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), quindi un `diff -r` eseguito da root su un albero estratto non attendibile può leggere la destinazione del link e includere contenuti diversi nell'output. Verifica che l'archivio possa essere sostituito, che il link punti a un percorso effettivamente visitato dal confronto, che il job possa leggere la destinazione e che l'output del confronto o il log degli errori sia leggibile dall'utente con privilegi inferiori. Il link o l'archivio, da soli, non dimostrano una divulgazione; durante l'enumerazione, esamina il job, i metadati dei percorsi e i permessi dei log senza eseguire il confronto né leggere contenuti protetti.

Un trasferimento ripetuto lato host può trasformare un membro non attendibile di un archivio in un successivo percorso di output. Se un job con privilegi superiori copia un archivio da un container meno attendibile, estrae un symlink il cui nome corrisponde al basename della destinazione del trasferimento successivo e poi scrive sullo stesso percorso, la scrittura successiva potrebbe raggiungere la destinazione del link. Verifica il nome e la destinazione del membro nell'archivio, i flag e la directory di estrazione, se l'estrattore lascia effettivamente il link al suo posto, come l'implementazione del trasferimento gestisce un link di destinazione già esistente e l'identità effettiva con cui il job host scrive. [GNU tar documenta la gestione dei file e dei symlink già esistenti durante l'estrazione](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [nelle versioni moderne OpenSSH scp usa SFTP per impostazione predefinita](https://man.openbsd.org/scp.1), quindi verifica il comportamento del trasferimento installato invece di presumere che tutte le versioni di `scp` scrivano seguendo un link. Un processo `scp` visibile dal container o un archivio scrivibile, da soli, non dimostrano che l'host eseguirà l'estrazione e la successiva scrittura. Durante l'enumerazione, esamina il job e i metadati dei percorsi senza trasferire né estrarre un archivio appositamente creato.

Il [modulo `synchronize` di Ansible](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) si basa su rsync; `copy_links: true` copia la destinazione di un symlink anziché il link stesso. Per un backup pianificato, verifica se un utente con privilegi inferiori può creare un link nell'esatto albero sorgente, se l'identità usata per la sincronizzazione può leggere la destinazione e se tale utente può leggere la copia o l'archivio risultante. Il playbook, la posizione del link, l'identità run-as e i permessi dell'output devono essere tutti compatibili; una directory di upload scrivibile o l'impostazione `copy_links`, da sole, sono soltanto elementi da approfondire. Esamina i metadati e il playbook senza creare link né attivare il job.

## Esamina i descrittori aperti

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un processo può mantenere l'accesso a un file anche dopo che è stato eliminato o rinominato. Un processo privilegiato può anche passare un descrittore tramite un socket Unix o lasciarlo aperto involontariamente durante `execve()` se manca close-on-exec. Esamina i target in `/proc/<PID>/fd` per individuare file sensibili, file eliminati, percorsi host visibili all'interno di un container e socket inattesi. Il dereferenziamento dei descrittori di un altro processo è soggetto ai controlli di accesso del kernel; la presenza di un symlink visibile non garantisce che sia possibile leggerne il contenuto.

Un helper SUID personalizzato può aprire un percorso protetto, abbassare il proprio UID effettivo e lasciare aperto il descrittore. Se poi si rende dumpable, la proprietà e l'accesso a `/proc/<PID>/fd` possono cambiare; verifica l'esatta transizione delle credenziali, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), le policy di procfs/ptrace e i permessi del file di destinazione. Riaprire un percorso del descrittore può aggirare una **directory padre** inaccessibile, ma fallire comunque se il chiamante non può leggere il file. La visibilità del target di un descrittore o del bit SUID, da soli, non provano che vi sia stata una divulgazione.

Gli artefatti di crash sono un indizio distinto: un core dump può contenere la memoria del processo, compresi dati letti in precedenza con un'identità più privilegiata. Su Ubuntu, [Apport colloca normalmente i report in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); altri sistemi possono usare un gestore `core_pattern` diverso o l'archiviazione di systemd. Durante la normale enumerazione, controlla solo i percorsi dei report, il proprietario, i permessi e la leggibilità. Un report leggibile è rilevante solo se il processo in questione era dumpable, il gestore di crash ha conservato i byte sensibili e l'utente corrente può accedere al report. Non mandare in crash un helper né estrarre un dump durante l'enumerazione passiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) per le condizioni relative a SUID e alla generazione dei dump.

Quando un servizio usa un descrittore ereditato, esamina la catena di avvio e i numeri dei descrittori prima di provare il reindirizzamento della shell o `/proc/self/fd/<N>`. Se un file è stato eliminato ma è ancora aperto, il [recupero di file eliminati](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) può preservare le prove o consentire di recuperare il contenuto. Per il triage a livello di processo, prosegui con [enumerazione dei processi e percorsi dei servizi](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
