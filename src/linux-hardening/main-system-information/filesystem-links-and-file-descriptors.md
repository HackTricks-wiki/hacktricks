# Символічні посилання, жорсткі посилання та файлові дескриптори

{{#include ../../banners/hacktricks-training.md}}

Шлях називає об’єкт у момент його розв’язання; відкритий файловий дескриптор зберігає посилання на об’єкт після зміни імені шляху. Ця відмінність пояснює гонки символічних посилань, приховані жорсткі посилання, відновлення видалених файлів і витоки успадкованих дескрипторів. Див. [файлова система, inode та відновлення](filesystem-inodes-and-recovery.md), щоб дізнатися про inode і монтування.

## Перевірка посилань і власників шляхів

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Symlink перенаправляє розв’язання pathname; hardlink — це інше ім’я того самого inode у тій самій файловій системі. Якщо привілейоване завдання читає або записує передбачуваний шлях у каталозі, доступному для запису користувачам, користувач може перенаправити цей шлях на ціль із конфіденційними даними. Перевіряйте власника та дозволи кожного батьківського каталогу, а не лише кінцевого файла. `fs.protected_symlinks` і `fs.protected_hardlinks` зменшують поширені атаки між користувачами, але не роблять безпечними довільні шляхи, доступні для запису.

Для привілейованого завдання, яке змінює дозволи за допомогою shell glob, розрізняйте посилання, розгорнуті в **аргументи командного рядка**, та посилання, знайдені пізніше під час рекурсивного обходу. [GNU `chmod` діє на ціль symlink, зазначеного в командному рядку](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), тоді як під час рекурсивного обходу зазвичай ігнорує знайдені symlink; сам параметр `-R` не робить ці випадки еквівалентними. Перевірте фактичний обліковий запис і команду за розкладом, чи може недовірений користувач створити запис, що відповідатиме glob, поведінку та параметри встановленого `chmod`, а також доступ, який отримає запропонована ціль. Каталог, доступний для запису, або сам symlink ще не доводить, що привілейовані дозволи буде змінено. Під час пасивного переліку перевіряйте скрипт і метадані шляхів, не створюючи посилань і не запускаючи завдання.

Привілейоване завдання за розкладом може створювати передбачуваний шлях виводу, навіть якщо ім’я файла містить хеш, схожий на випадковий: [`C rand()` повторює послідовність за однакового початкового значення `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), зокрема й тоді, коли початкове значення отримано з відомого часу виконання. Якщо під час формування цього імені завдання також читає рядки бази даних, доступні для запису користувачеві, перевірте точний алгоритм перетворення рядка на ім’я, початкове значення й поведінку libc, розклад, права користувача на зміну рядків і створення каталогів, а також чи можна розмістити наявний symlink до привілейованого відкриття файла. [`fopen(..., "w")` створює або обрізає файл, на який указує розв’язаний шлях](https://man7.org/linux/man-pages/man3/fopen.3.html); перевірте, чи використовує фактична реалізація безпечні для symlink прапорці відкриття або атомарну заміну, ідентичність ефективного користувача для запису, дозволи цільового файла та політику symlink для каталогів зі sticky bit. Передбачуване ім’я або доступний для запису рядок — лише привід для перевірки. Під час пасивного переліку перевіряйте код, розклад і метадані, не додаючи рядків і не запускаючи завдання.

Для служби перетворення файлів, що працює від імені іншого користувача, перевірте, чи може клієнт вибирати шлях виводу або розширення та чи переходить конвертер за наявним symlink виводу. Деякі конвертери визначають формат виводу за розширенням шляху; посилання з допустимим розширенням усе одно може вказувати на ціль із конфіденційними даними, що не має розширення. Для успішного запису між користувачами потрібні доступна служба, контроль клієнта над шляхом і посиланням, відкриття конвертером посилання для запису та дозвіл на запис для ідентичності служби. У Linux `fs.protected_symlinks=1` обмежує перехід за посиланням іншого користувача в **каталозі зі sticky bit, доступному для запису всім користувачам**; для посилання у звичайному каталозі, що належить користувачу, такий самий захист не надається. Перш ніж робити висновки, перевірте розв’язаний шлях і власників батьківських каталогів. Див. [поведінку calibre щодо вихідних файлів](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) і [політику symlink у Linux](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Для дозволеної через sudo обгортки завантаження так само перевірте шлях виводу, якщо вона отримує вибрані клієнтом дані, зберігаючи контроль клієнта над робочим каталогом. Перевірте фактичну програму завантаження та з’ясуйте, чи може вибране нею базове ім’я, обробка конфліктів або наявний symlink перенаправити привілейований запис; сам вибір URL або symlink для цього недостатній. [Axel документує файл `~/.axelrc` для кожного користувача](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), а його [приклад конфігурації містить `default_filename` і `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), тож обгортка, що використовує Axel, може також успадкувати вибір імені виводу з цього файла. Перевірте ефективне значення `HOME`: [sudo може скидати або зберігати його відповідно до політики](https://man7.org/linux/man-pages/man8/sudo.8.html), а файл `.axelrc` користувача має значення лише тоді, коли привілейована програма завантаження справді його читає. Під час пасивного переліку перевірте правило, обгортку, шлях до конфігурації та дозволи, остаточне ім’я виводу й стан цільового файла, не починаючи завантаження.

Для дозволеної через sudo обгортки ACL перевірте, як вона перевіряє вибраний клієнтом файл перед викликом `setfacl`. Перевірка лексичного префікса й відхилення `..` не завадять symlink усередині дозволеного каталогу вести за його межі; `test -f` також переходить за посиланням. Переконайтеся, що обгортка має достатньо привілеїв для виконання операції ACL, що клієнт контролює посилання, а отриманий ACL надає потрібний доступ до цілі **та її батьківських каталогів**. Деякі програми відмовляються працювати з файлами, що мають ACL із дозволом на запис або надто широкі звичайні дозволи, тож сама зміна ACL не доводить наявності робочого шляху до підвищення привілеїв.

## Перевірка привілейованого запису у файлові системи FUSE, змонтовані користувачами

Активний окремий рядок `user_allow_other` у `/etc/fuse.conf` дозволяє користувачу без прав root запитувати параметри монтування FUSE `allow_other` або `allow_root`. Ці параметри монтування можуть дозволити процесу root звертатися до файлової системи, реалізованої користувачем, який її змонтував. Якщо дозволена через sudo допоміжна програма записує журнал із конфіденційними даними чи інший вивід відносно робочого каталогу, контрольованого клієнтом, перевірте, чи може цей каталог бути файловою системою FUSE, змонтованою користувачем. Реалізація FUSE може спостерігати за записами, навіть якщо створений файл у звичайній файловій системі виглядає як файл root із режимом `0600`.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Це **кандидат**, а не доказ розкриття. Перевірте фактичну особу sudo/run-as і аргументи, шлях виводу допоміжної програми та наявність у ньому чутливих даних, доступ до `/dev/fuse`, успішність монтування з `allow_other` або `allow_root`, а також те, чи може привілейований процес увійти до точки монтування. Не запускайте привілейовану допоміжну програму й не монтуйте файлову систему під час звичайного переліку. Див. [опис політики libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) і [FAQ щодо доступу libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Шукайте гонки шляхів

Небезпечна схема — це коли привілейована програма перевіряє один шлях, а згодом відкриває той самий шлях, не зберігши безпечне посилання на перевірений об’єкт. Зловмисник, який контролює батьківський каталог, може замінити файл або symlink між цими двома операціями. Та сама проблема виникає з тимчасовими файлами, скриптами, що запускаються таймером, розпакуванням архівів і процедурами резервного копіювання. Перш ніж заявляти про вплив, підтвердьте фактичну операцію читання/запису та права доступу до цілі.

Створення архіву також може розкривати файли між обліковими записами. Info-ZIP `zip -r` зазвичай переходить за symlink, розміщеним у вихідному дереві, і зберігає вміст цілі; натомість `-y`/`--symlinks` зберігає саме посилання. Якщо користувач із нижчими привілеями може додати посилання до каталогу, який резервно копіюється, перевірте конкретний архіватор і параметри, обліковий запис, від імені якого завдання резервного копіювання читає файли, а також чи може цей користувач читати створений архів. Доступний для запису вихідний каталог або сам symlink не доводять факту розкриття. Перегляньте метадані посилань і архіву, не запускаючи резервне копіювання й не розпаковуючи секретний вміст під час переліку. Див. [документацію параметрів Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` за замовчуванням поводиться інакше: зазвичай він зберігає symlink як посилання, а [`-h` / `--dereference` переходить за ним під час створення архіву](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Для привілейованого запланованого резервного копіювання перевірте точний виклик `tar`, чи може користувач із нижчими привілеями замінити вхідний шлях до того, як `tar` його прочитає, а також чи має цей користувач доступ до створеного архіву. Тимчасова контрольна сума або інший допоміжний файл у доступному для запису проміжному каталозі може стати таким входом, якщо його явно вказано в пізнішій команді `tar -h`. Потрібно перевірити вікно гонки, обліковий запис завдання, політику щодо symlink, читабельність цілі для цього облікового запису та ACL архіву. Під час пасивних перевірок не замінюйте файли, не запускайте завдання й не розпаковуйте чутливі архіви.

Розпакування архіву перетинає іншу межу довіри, якщо привілейоване завдання читає архів, який може замінити користувач із нижчими привілеями. [GNU tar зазвичай відновлює власника файлів з архіву, якщо запущений суперкористувачем](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), а його [параметри відновлення дозволів](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) впливають на біти режиму розпакованих файлів. Перевірте точний розпаковувач і прапорці, вікно можливості заміни архіву, метадані числових власника й режиму, права доступу до каталогу розпакування, а також чи залишає очищення результат доступним. Елемент із SUID, власником root, викликає занепокоєння лише якщо його режим зберігається під час розпакування, а політика цільового монтування та процесу дозволяє зміну облікової особи; самі по собі недовірений архів або доступний для запису проміжний шлях цього не доводять. Перевірте завдання й метадані, не замінюючи та не розпаковуючи архів під час пасивного переліку.

Розпакований symlink також може розкрити захищений файл під час подальшого привілейованого порівняння. [GNU `diff` зазвичай переходить за symlink під час порівняння каталогів](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), тому запущений від root `diff -r` для недовіреного розпакованого дерева може прочитати ціль посилання та включити відмінний вміст у вивід. Перевірте, чи можна замінити архів, чи вказує посилання на шлях, який порівняння фактично відвідує, чи має завдання доступ до цілі та чи може користувач із нижчими привілеями читати вивід порівняння або журнал помилок. Самі по собі посилання чи архів не доводять факту розкриття; перевірте завдання, метадані шляхів і права доступу до журналів, не запускаючи порівняння й не читаючи захищений вміст під час переліку.

Повторюване передавання файлів на хості може перетворити елемент недовіреного архіву на шлях майбутнього виводу. Якщо завдання з вищими привілеями копіює архів із контейнера з нижчим рівнем довіри, розпаковує symlink, ім’я якого збігається з базовим ім’ям цільового файла наступного передавання, а потім записує дані за тим самим шляхом, подальший запис може потрапити у ціль посилання. Перевірте ім’я елемента архіву та ціль, параметри розпакування й каталог, чи залишає розпаковувач це посилання на місці, як механізм передавання обробляє вже наявне посилання призначення, а також фактичну особу хоста, від імені якої виконується запис. [GNU tar описує обробку наявних файлів і symlink під час розпакування](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp за замовчуванням використовує SFTP у сучасних випусках](https://man.openbsd.org/scp.1), тож перевірте поведінку встановленої версії передавання, а не припускайте, що всі версії `scp` записують за посиланням. Сам по собі процес `scp`, видимий у контейнері, або доступний для запису архів не доводять, що відбулося розпакування на хості та подальший запис. Перевірте завдання й метадані шляхів, не передаючи й не розпаковуючи спеціально створений архів під час переліку.

Модуль Ansible [`synchronize`](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) використовує rsync; `copy_links: true` копіює ціль symlink, а не саме посилання. Для запланованого резервного копіювання перевірте, чи може користувач із нижчими привілеями створити посилання в точному вихідному дереві, чи може обліковий запис синхронізації прочитати його ціль і чи має цей користувач доступ до створеної копії або архіву. Файл playbook, розташування посилання, обліковий запис запуску та права доступу до результату мають відповідати одне одному; доступний для запису каталог завантаження або параметр `copy_links` самі по собі є лише приводом для перевірки. Перегляньте метадані й playbook, не створюючи посилань і не запускаючи завдання.

## Перевірте відкриті файлові дескриптори

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Процес може зберігати доступ до файлу після його видалення або перейменування. Привілейований процес також може передати дескриптор через Unix-сокет або ненавмисно залишити його відкритим під час `execve()`, якщо не встановлено прапорець close-on-exec. Перевірте цілі в `/proc/<PID>/fd` на наявність конфіденційних файлів, видалених файлів, шляхів хоста, видимих усередині контейнера, та неочікуваних сокетів. Доступ до дескрипторів іншого процесу підпадає під перевірки доступу ядра; видиме символічне посилання не гарантує, що його вміст можна прочитати.

Власний допоміжний SUID-файл може відкрити захищений шлях, скинути свій ефективний UID і залишити дескриптор відкритим. Якщо потім він встановить для себе режим dumpable, власник і доступ до `/proc/<PID>/fd` можуть змінитися; перевірте точний перехід облікових даних, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), політику procfs/ptrace та режим цільового файлу. Повторне відкриття шляху дескриптора може обійти недоступний **батьківський каталог**, але все одно завершитися помилкою, якщо викликач не має права читати файл. Видима ціль дескриптора або сам біт SUID не доводять, що дані розкрито.

Артефакти аварійного завершення — це окремий напрямок перевірки: core dump може містити пам’ять процесу, зокрема дані, раніше прочитані з вищими привілеями. В Ubuntu [Apport зазвичай розміщує звіти в `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); в інших системах може використовуватися інший обробник `core_pattern` або сховище systemd. Під час звичайного переліку перевіряйте лише шляхи до звітів, їхнього власника, режим доступу та можливість читання. Звіт має значення лише тоді, коли відповідний процес був у режимі dumpable, обробник аварійного завершення зберіг конфіденційні байти, а поточний користувач має доступ до цього звіту. Не аварійно завершуйте допоміжний процес і не розпаковуйте дамп під час пасивного переліку. Умови створення дампів і правила для SUID описано в [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html).

Якщо служба використовує успадкований дескриптор, перевірте ланцюжок її запуску та номери дескрипторів, перш ніж випробовувати перенаправлення оболонки або `/proc/self/fd/<N>`. Якщо файл видалено, але він усе ще відкритий, [відновлення видалених файлів](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) може зберегти докази або відновити вміст. Для тріажу на рівні процесів перейдіть до [переліку процесів і шляхів служб](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
