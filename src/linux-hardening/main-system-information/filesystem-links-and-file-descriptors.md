# Символічні посилання, жорсткі посилання та файлові дескриптори

{{#include ../../banners/hacktricks-training.md}}

Шлях іменує об’єкт на момент його визначення; відкритий файловий дескриптор зберігає посилання на об’єкт навіть після зміни шляху. Ця відмінність пояснює гонки символічних посилань, приховані жорсткі посилання, відновлення видалених файлів і витоки успадкованих дескрипторів. Див. [файлова система, inode та відновлення](filesystem-inodes-and-recovery.md), щоб дізнатися про inode та монтування.

## Перевірка посилань і власності на шляхи

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Symlink перенаправляє розв’язання шляху; hardlink — це інше ім’я того самого inode у тій самій файловій системі. Якщо привілейоване завдання читає або записує передбачуваний шлях у каталозі, доступному для запису користувачам, користувач може перенаправити цей шлях на чутливий файл. Перевіряйте власника та права доступу для кожного батьківського каталогу, а не лише для кінцевого файлу. `fs.protected_symlinks` і `fs.protected_hardlinks` зменшують ризик поширених атак між користувачами, але не роблять довільні шляхи, доступні для запису, безпечними.

Для привілейованого завдання, яке змінює права за допомогою shell glob, розрізняйте посилання, розгорнуті в **аргументи командного рядка**, і посилання, виявлені пізніше під час рекурсивного обходу. [GNU `chmod` застосовує зміни до цільового файлу symlink, указаного в командному рядку](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), тоді як зазвичай ігнорує symlink, знайдені під час рекурсивного обходу; сама опція `-R` не робить ці два випадки еквівалентними. Перевірте фактичного користувача, від імені якого заплановано виконання, і команду, можливість для недовіреного користувача створити запис, який відповідає glob, поведінку та параметри встановленого `chmod`, а також рівень доступу, який отримає запропонована ціль. Каталог, доступний для запису, або symlink самі по собі не доводять, що відбудеться привілейована зміна прав. Під час пасивного переліку перевірте скрипт і метадані шляхів, не створюючи посилань і не запускаючи завдання.

Заплановане привілейоване завдання запису може використовувати передбачуваний шлях виводу, навіть якщо ім’я файлу містить хеш, який виглядає випадковим: [C `rand()` повторює послідовність за того самого seed для `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), зокрема якщо seed обчислюється з відомого часу виконання. Якщо завдання також читає рядки бази даних, доступні для запису викликачеві, щоб сформувати це ім’я, перевірте точний алгоритм перетворення рядка на ім’я, seed і поведінку libc, розклад запуску, права викликачa на зміну рядків і створення каталогів, а також можливість розмістити symlink до привілейованого відкриття файлу. [`fopen(..., "w")` створює або обрізає файл, на який указує розв’язаний шлях](https://man7.org/linux/man-pages/man3/fopen.3.html); перевірте фактичну реалізацію на наявність безпечних щодо symlink прапорців відкриття або атомарної заміни, ефективні права запису, права доступу до цільового файлу та політику symlink для каталогів із sticky bit. Передбачуване ім’я або рядок, доступний для запису, самі по собі є лише приводом для перевірки. Під час пасивного переліку перевірте код, розклад запуску й метадані, не додаючи рядків і не запускаючи завдання.

Для служби перетворення файлів, що працює від імені іншого користувача, перевірте, чи може викликач вибрати вихідний шлях або розширення, а також чи переходить конвертер за наявним symlink для вихідного файлу. Деякі конвертери визначають формат виводу за розширенням шляху; посилання з допустимим розширенням усе одно може вказувати на чутливий файл без розширення. Для успішного запису між користувачами потрібні доступна служба, контроль викликачем шляху й посилання, відкриття конвертером посилання для запису та права на запис від імені користувача служби. У Linux `fs.protected_symlinks=1` обмежує перехід за посиланням іншого користувача в **каталозі з sticky bit, доступному для запису всім**; такий самий захист не поширюється на посилання у звичайному каталозі, яким володіє користувач. Перш ніж робити висновки, перевірте розв’язаний шлях і власника батьківського каталогу. Див. [поведінку calibre щодо вихідного файлу](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) та [політику Linux щодо symlink](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Якщо обгортка завантаження, дозволена через sudo, отримує дані, вибрані викликачем, зберігаючи при цьому контрольований ним робочий каталог, потрібно так само перевірити шлях виводу. Перевірте фактичну програму-завантажувач і з’ясуйте, чи можуть вибране нею базове ім’я, обробка конфліктів або наявний symlink перенаправити привілейований запис; вибір URL або symlink сам по собі недостатній. [Axel документує файл `~/.axelrc` для кожного користувача](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), а його [приклад конфігурації містить `default_filename` і `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), тож обгортка, яка використовує Axel, може також успадкувати вибір імені виводу з цього файлу. Перевірте ефективне значення `HOME`: [sudo може скидати його або зберігати відповідно до політики](https://man7.org/linux/man-pages/man8/sudo.8.html), а `.axelrc` користувача важливий, лише якщо привілейована програма-завантажувач справді читає цей файл. Під час пасивного переліку перевірте правило, обгортку, шлях до конфігурації та права доступу, кінцеве ім’я вихідного файлу й стан цільового файлу, не починаючи завантаження.

Для обгортки ACL, дозволеної через sudo, перевірте, як вона валідує вибраний викликачем файл перед викликом `setfacl`. Перевірка лексичного префікса та відхилення `..` не завадять symlink усередині дозволеного каталогу вказувати за його межі; `test -f` також переходить за посиланням. Переконайтеся, що обгортка має достатні привілеї для виконання операції ACL, викликач контролює посилання, а результівний ACL надає потрібний доступ до цільового файлу **та його батьківських каталогів**. Деякі програми відмовляються працювати з файлами, що мають ACL, доступний для запису, або надто широкі права; сама зміна ACL не доводить, що шлях підвищення привілеїв спрацює.

## Перевірка привілейованого запису у файлові системи FUSE, підключені користувачами

Активний окремий рядок `user_allow_other` у `/etc/fuse.conf` дає користувачу без прав root змогу запитувати `allow_other` або `allow_root` для підключення FUSE. Ці параметри підключення можуть дозволити процесу root звертатися до файлової системи, реалізованої користувачем, який її підключив. Якщо помічник, дозволений через sudo, записує журнал із секретами чи інші дані відносно робочого каталогу, контрольованого викликачем, перевірте, чи може цей каталог бути файловою системою FUSE, підключеною користувачем. Реалізація FUSE може спостерігати за записами, навіть якщо на звичайній файловій системі створений файл має власника root або режим `0600`.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Це **кандидат**, а не доказ розголошення даних. Перевірте фактичну ідентичність `sudo`/`run-as` і аргументи, шлях виводу та конфіденційний вміст допоміжної програми, доступ до `/dev/fuse`, можливість успішного монтування з `allow_other` або `allow_root`, а також те, чи може привілейований процес увійти до точки монтування. Не запускайте привілейовану допоміжну програму й не монтуйте файлову систему під час звичайного збору даних. Див. [опис політики libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) і [FAQ щодо доступу libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Шукайте гонки шляхів

Небезпечний шаблон — це коли привілейована програма перевіряє шлях, а згодом відкриває той самий шлях, не зберігаючи безпечне посилання на перевірений об’єкт. Зловмисник, який контролює батьківський каталог, може підмінити файл або символічне посилання між цими операціями. Та сама проблема трапляється з тимчасовими файлами, скриптами, що запускаються за таймером, розпакуванням архівів і процесами резервного копіювання. Перш ніж заявляти про вплив, перевірте фактичну операцію читання/запису та права доступу до цільового об’єкта.

**Створення** архіву також може розголошувати файли між різними ідентичностями. Info-ZIP `zip -r` зазвичай переходить за символічним посиланням, розміщеним у вихідному дереві, і зберігає вміст його цілі; параметр `-y`/`--symlinks` натомість зберігає саме посилання. Якщо користувач із нижчими привілеями може додати посилання до каталогу, для якого створюється резервна копія, перевірте конкретний архіватор і його параметри, ідентичність, від імені якої завдання резервного копіювання читає дані, і чи може цей користувач читати створений архів. Сам по собі доступ на запис до вихідного каталогу або символічне посилання не доводять розголошення. Перегляньте метадані посилань і архіву, не запускаючи резервне копіювання та не розпаковуючи секретний вміст під час збору даних. Див. [документацію щодо параметрів Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

У GNU `tar` інша поведінка за замовчуванням: зазвичай він зберігає символічне посилання як посилання, тоді як [`-h` / `--dereference` переходить за ним під час створення архіву](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Для привілейованого запланованого резервного копіювання перевірте точний виклик `tar`, чи може користувач із нижчими привілеями підмінити шлях до вхідного файла до того, як `tar` прочитає його, і чи має цей користувач доступ до створеного архіву. Тимчасова контрольна сума або інший допоміжний файл у доступному для запису проміжному каталозі може стати таким вхідним файлом, якщо його явно вказано в подальшій команді `tar -h`. Необхідно перевірити вікно гонки, ідентичність завдання, політику щодо символічних посилань, доступність цілі для читання від імені цієї ідентичності та ACL архіву. Під час пасивних перевірок не підмінюйте файли, не запускайте завдання й не розпаковуйте конфіденційні архіви.

**Розпакування** архіву перетинає іншу межу довіри, коли привілейоване завдання читає архів, який може підмінити користувач із нижчими привілеями. [GNU tar зазвичай відновлює власників з архіву під час запуску суперкористувачем](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), а його [параметри відновлення прав доступу](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) впливають на біти режиму доступу розпакованих файлів. Перевірте конкретний засіб розпакування та його параметри, вікно для підміни архіву, числові метадані власника й режиму доступу, права на каталог розпакування та чи залишає очищення результат доступним. Файл із SUID-бітом і власником root становить загрозу лише тоді, коли його режим зберігається під час розпакування, а політика цільового монтування та процесу дозволяє змінити ідентичність; сам по собі ненадійний архів або доступний для запису проміжний шлях цього не доводить. Перегляньте завдання й метадані, не підмінюючи та не розпаковуючи архів під час пасивного збору даних.

Розпаковане символічне посилання також може розголосити захищений файл під час подальшого привілейованого порівняння. [GNU `diff` зазвичай переходить за символічними посиланнями під час порівняння каталогів](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), тому запущений від root `diff -r` для ненадійного розпакованого дерева може прочитати ціль посилання та включити відмінний вміст у вивід. Переконайтеся, що архів можна підмінити, посилання веде до шляху, який порівняння фактично переглядає, завдання має доступ до цілі для читання, а користувач із нижчими привілеями може читати вивід порівняння або журнал помилок. Саме посилання чи архів не доводять розголошення; перегляньте завдання, метадані шляхів і права доступу до журналів, не запускаючи порівняння та не читаючи захищений вміст під час збору даних.

Повторне передавання даних на хост може перетворити файл із ненадійного архіву на шлях для подальшого запису. Якщо завдання з вищими привілеями копіює архів із контейнера з нижчим рівнем довіри, розпаковує символічне посилання з ім’ям, що збігається з базовим ім’ям цільового файла наступного передавання, а згодом записує дані за тим самим шляхом, пізніший запис може перейти за посиланням і потрапити до його цілі. Перевірте ім’я та ціль файла в архіві, параметри розпакування й каталог, чи залишає засіб розпакування це посилання на місці, як реалізація передавання обробляє наявне посилання на призначення, а також ефективну ідентичність для запису завдання на хості. [У документації GNU tar описано обробку наявних файлів і символічних посилань під час розпакування](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp у сучасних версіях за замовчуванням використовує SFTP](https://man.openbsd.org/scp.1), тому перевірте поведінку встановленої версії засобу передавання, а не припускайте, що всі версії `scp` записують через посилання. Сам факт наявності процесу `scp`, видимого з контейнера, або доступного для запису архіву не доводить, що на хості відбудеться розпакування й подальший запис. Перегляньте завдання та метадані шляхів, не передаючи й не розпаковуючи спеціально створений архів під час збору даних.

Модуль Ansible [`synchronize`](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) використовує rsync; `copy_links: true` копіює ціль символічного посилання, а не саме посилання. Для запланованого резервного копіювання перевірте, чи може користувач із нижчими привілеями створити посилання в точному вихідному дереві, чи має ідентичність синхронізації доступ до цілі для читання і чи може цей користувач читати отриману копію або архів. Плейбук, розташування посилання, ідентичність `run-as` і права доступу до результату мають збігатися; сам по собі каталог завантаження з доступом на запис або параметр `copy_links` лише вказують, що варто провести перевірку. Перегляньте метадані й плейбук, не створюючи посилань і не запускаючи завдання.

## Перевірте відкриті файлові дескриптори

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Процес може зберегти доступ до файлу після його видалення або перейменування. Привілейований процес також може передати дескриптор через Unix-сокет або ненавмисно залишити його відкритим після `execve()`, якщо не встановлено прапорець close-on-exec. Перевіряйте цілі посилань у `/proc/<PID>/fd` на наявність конфіденційних файлів, видалених файлів, шляхів хоста, видимих усередині контейнера, та неочікуваних сокетів. Доступ до дескрипторів іншого процесу залежить від перевірок доступу ядра; видиме символічне посилання не гарантує, що його вміст можна прочитати.

Спеціально створена допоміжна програма з SUID може відкрити захищений шлях, скинути свій ефективний UID і залишити дескриптор відкритим. Якщо після цього вона зробить себе dumpable, власник і доступ до `/proc/<PID>/fd` можуть змінитися; перевірте точний перехід між обліковими даними, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), політику procfs/ptrace та права доступу до цільового файлу. Повторне відкриття шляху до дескриптора може обійти недоступний **батьківський каталог**, але все одно не спрацювати, якщо користувач не має права читати сам файл. Саме по собі видиме призначення дескриптора або наявність біта SUID не доводить, що дані розкрито.

Артефакти збоїв — це окрема зачіпка: дамп пам’яті може містити пам’ять процесу, зокрема дані, раніше прочитані з вищими привілеями. В Ubuntu [Apport зазвичай зберігає звіти в `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); в інших системах може використовуватися інший обробник `core_pattern` або сховище systemd. Під час звичайного переліку перевіряйте лише шляхи до звітів, власника, права доступу та можливість читання. Звіт має значення лише тоді, коли відповідний процес допускав створення дампу, обробник аварійного завершення зберіг конфіденційні байти, а поточний користувач має доступ до цього звіту. Не спричиняйте аварійне завершення допоміжної програми й не розпаковуйте дамп під час пасивного переліку. Умови створення дампів для SUID і генерування дампів описано в [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html).

Якщо служба використовує успадкований дескриптор, перевірте ланцюжок її запуску та номери дескрипторів, перш ніж пробувати перенаправлення оболонки або `/proc/self/fd/<N>`. Якщо файл видалено, але він досі відкритий, [відновлення видалених файлів](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) може зберегти докази або відновити вміст. Для первинної перевірки на рівні процесів перейдіть до [переліку процесів і шляхів служб](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
