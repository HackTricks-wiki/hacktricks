# Enlaces simbólicos, enlaces duros y descriptores de archivo

{{#include ../../banners/hacktricks-training.md}}

Una ruta nombra un objeto en el momento en que se resuelve; un descriptor de archivo abierto mantiene una referencia al objeto aunque cambie el nombre de la ruta. Esta diferencia explica las carreras de symlinks, los hardlinks ocultos, la recuperación de archivos eliminados y las fugas de descriptores heredados. Consulta [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) para obtener información sobre inodes y mounts.

## Inspeccionar los enlaces y la propiedad de las rutas

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink redirige la resolución de nombres de ruta; un hardlink es otro nombre para el mismo inode en el mismo sistema de archivos. Si una tarea con privilegios lee o escribe en una ruta predecible dentro de un directorio donde un usuario puede escribir, este podría redirigir esa ruta a un destino sensible. Comprueba la propiedad y los permisos de cada directorio padre, no solo del archivo final. `fs.protected_symlinks` y `fs.protected_hardlinks` reducen los ataques habituales entre usuarios, pero no hacen seguros los paths arbitrarios donde se puede escribir.

Para una tarea con privilegios que cambia permisos mediante un glob del shell, distingue los enlaces expandidos como **operandos de la línea de comandos** de los enlaces encontrados después durante el recorrido recursivo. [GNU `chmod` actúa sobre el referente de un symlink indicado en la línea de comandos](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mientras que normalmente ignora los symlinks encontrados durante el recorrido recursivo; `-R` por sí solo no hace equivalentes ambos casos. Revisa la identidad programada y el comando reales, si un usuario no confiable puede crear una entrada que coincida con el glob, el comportamiento y las opciones de `chmod` instalado, y el acceso que obtendría el destino propuesto. Un directorio donde se puede escribir o un symlink por sí solo no demuestra que se produzca un cambio de modo con privilegios. Inspecciona el script y los metadatos de la ruta sin crear un enlace ni activar la tarea durante la enumeración pasiva.

Un proceso programado con privilegios puede usar una ruta de salida predecible incluso si el nombre de archivo contiene un hash que parece aleatorio: [C `rand()` repite su secuencia con la misma semilla de `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), incluso si la semilla se deriva de una hora de ejecución conocida. Si el trabajo también lee filas de una base de datos donde el solicitante puede escribir para construir ese nombre, verifica el algoritmo exacto de conversión de fila a nombre, la semilla y el comportamiento de libc, la programación, los permisos del solicitante para modificar filas y crear directorios, y si se puede colocar un symlink preexistente antes de la apertura con privilegios. [`fopen(..., "w")` crea o trunca el archivo resuelto](https://man7.org/linux/man-pages/man3/fopen.3.html); comprueba la implementación real para ver si usa flags de apertura seguros frente a enlaces o reemplazo atómico, la identidad efectiva de escritura, los permisos del destino y la política de symlinks en directorios sticky. Un nombre predecible o una fila donde se puede escribir son solo indicios para revisar. Inspecciona el código, la programación y los metadatos sin insertar filas ni ejecutar el trabajo durante la enumeración pasiva.

En un servicio de conversión de archivos que se ejecuta como otro usuario, revisa si el solicitante puede elegir una ruta o extensión de salida y si el conversor sigue un symlink preexistente en la ruta de salida. Algunos conversores seleccionan el formato de salida a partir de la extensión de la ruta; un enlace con un nombre que tenga una extensión aceptada puede apuntar igualmente a un destino sensible sin extensión. Para que se produzca una escritura entre usuarios, el servicio debe ser accesible, el solicitante debe controlar la ruta y el enlace, el conversor debe abrir el enlace para escribir y la identidad del servicio debe tener permiso de escritura. En Linux, `fs.protected_symlinks=1` restringe el seguimiento de un enlace de otro usuario en un **directorio sticky donde todos los usuarios pueden escribir**; no ofrece la misma protección para un enlace en un directorio ordinario propiedad de un usuario. Inspecciona la ruta resuelta y la propiedad de los directorios padre antes de sacar conclusiones. Consulta el [comportamiento de calibre con los archivos de salida](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) y la [política de symlinks de Linux](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Un wrapper de descarga permitido por sudo requiere la misma revisión de la ruta de salida si descarga datos elegidos por el solicitante y conserva un directorio de trabajo controlado por este. Inspecciona el downloader real y comprueba si el nombre base elegido, el tratamiento de colisiones o un symlink preexistente pueden redirigir una escritura con privilegios; elegir una URL o crear un symlink no basta. [Axel documenta un archivo `~/.axelrc` por usuario](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), y su [configuración de ejemplo incluye `default_filename` y `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), por lo que un wrapper que use Axel también puede heredar de ese archivo la elección del nombre de salida. Confirma el valor efectivo de `HOME`: [sudo puede restablecerlo o conservarlo según la política](https://man7.org/linux/man-pages/man8/sudo.8.html), y el archivo `.axelrc` de un usuario solo es relevante si el downloader con privilegios realmente lo lee. Comprueba la regla, el wrapper, la ruta y los permisos del archivo de configuración, el nombre de salida final y el estado del archivo de destino sin iniciar una descarga durante la enumeración pasiva.

En un wrapper de ACL permitido por sudo, inspecciona cómo valida un archivo elegido por el solicitante antes de llamar a `setfacl`. Una comprobación de prefijo léxico y el rechazo de `..` no impiden que un symlink dentro del directorio permitido resuelva a una ruta externa; `test -f` también sigue el enlace. Confirma que el wrapper llega a la operación de ACL con privilegios suficientes, que el solicitante controla el enlace y que la ACL resultante concede el acceso necesario al destino **y a sus directorios padre**. Algunos consumidores rechazan archivos con ACL que permiten escritura o con permisos demasiado abiertos, por lo que un cambio de ACL por sí solo no demuestra que haya una ruta de escalada funcional.

## Revisar escrituras con privilegios en sistemas de archivos FUSE montados por usuarios

Una línea activa independiente `user_allow_other` en `/etc/fuse.conf` permite que un usuario que no sea root solicite `allow_other` o `allow_root` en un montaje FUSE. Esas opciones de montaje pueden permitir que un proceso root acceda a un sistema de archivos implementado por el usuario que lo montó. Si un helper permitido por sudo escribe un registro que contiene secretos u otro archivo de salida en una ruta relativa al directorio de trabajo controlado por el solicitante, revisa si ese directorio puede ser un sistema de archivos FUSE montado por un usuario. La implementación de FUSE puede observar las escrituras incluso cuando el archivo resultante parece pertenecer a root o tener modo `0600` en un sistema de archivos ordinario.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Esto es un **indicio**, no una prueba de divulgación. Confirma la identidad y los argumentos reales de sudo/run-as, la ruta de salida del helper y su contenido sensible, el acceso a `/dev/fuse`, si el montaje se realiza correctamente con `allow_other` o `allow_root` y si el proceso privilegiado puede acceder al montaje. No ejecutes el helper privilegiado ni montes un sistema de archivos durante la enumeración rutinaria. Consulta la [descripción de la política de libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) y las [preguntas frecuentes sobre el acceso de libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Busca condiciones de carrera en las rutas

El patrón peligroso se da cuando un programa privilegiado comprueba una ruta y, más tarde, la abre sin conservar una referencia segura al objeto comprobado. Un atacante que controle un directorio padre puede sustituir un archivo o un enlace simbólico entre ambas operaciones. El mismo problema aparece con archivos temporales, scripts activados por temporizadores, la extracción de archivos y los procesos de copia de seguridad. Confirma la operación real de lectura/escritura y los permisos del destino antes de afirmar que hay impacto.

La **creación** de archivos comprimidos también puede divulgar archivos entre identidades. Normalmente, Info-ZIP `zip -r` sigue un enlace simbólico ubicado dentro del árbol de origen y almacena el contenido del destino; en cambio, `-y`/`--symlinks` almacena el propio enlace. Si un usuario con menos privilegios puede añadir un enlace a un directorio del que se hacen copias de seguridad, comprueba el archivador y las opciones exactas, la identidad con la que el trabajo de copia de seguridad lee los archivos y si ese usuario puede leer el archivo resultante. Un directorio de origen con permisos de escritura o un enlace simbólico por sí solos no demuestran que haya divulgación. Revisa los metadatos de enlaces y archivos comprimidos sin activar el trabajo de copia de seguridad ni extraer contenido secreto durante la enumeración. Consulta la [documentación de opciones de Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` tiene un comportamiento predeterminado distinto: normalmente almacena un enlace simbólico como enlace, mientras que [`-h` / `--dereference` sigue el enlace durante la creación del archivo](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Si se trata de una copia de seguridad programada con privilegios, inspecciona la invocación exacta de `tar`, si un usuario con menos privilegios puede sustituir una ruta de entrada antes de que `tar` la lea y si ese usuario puede acceder al archivo resultante. Un checksum temporal u otro archivo auxiliar en un directorio de preparación con permisos de escritura puede convertirse en una entrada de este tipo si se especifica explícitamente en un comando `tar -h` posterior. Es necesario verificar la ventana de carrera, la identidad del trabajo, la política de enlaces simbólicos, la legibilidad del destino con esa identidad y las ACL del archivo. No sustituyas archivos, ejecutes el trabajo ni descomprimas archivos sensibles durante las comprobaciones pasivas.

La **extracción** de archivos cruza un límite distinto cuando un trabajo privilegiado lee un archivo que un usuario con menos privilegios puede sustituir. [GNU tar normalmente restaura la propiedad archivada cuando lo ejecuta el superusuario](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), y sus [opciones de restauración de permisos](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) afectan los bits de modo de los archivos extraídos. Revisa el extractor y las opciones exactas, la ventana de sustitución del archivo, los metadatos numéricos de propietario y modo, los permisos del directorio de extracción y si la limpieza deja el resultado accesible. Un miembro SUID propiedad de root solo es preocupante si su modo se conserva durante la extracción y la política del proceso y del montaje de destino permiten el cambio de identidad; un archivo no confiable o una ruta de preparación con permisos de escritura por sí solos no lo demuestran. Inspecciona el trabajo y los metadatos sin sustituir ni extraer un archivo durante la enumeración pasiva.

Un enlace simbólico extraído también puede divulgar un archivo protegido mediante una comparación privilegiada posterior. [GNU `diff` normalmente sigue los enlaces simbólicos al comparar directorios](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), por lo que un `diff -r` ejecutado como root sobre un árbol extraído no confiable puede leer el destino del enlace e incluir contenido distinto en su salida. Confirma que se pueda sustituir el archivo, que el enlace apunte a una ruta que la comparación realmente recorra, que el trabajo pueda leer el destino y que el usuario con menos privilegios pueda leer la salida de la comparación o el registro de errores. El enlace o el archivo por sí solos no demuestran que haya divulgación; revisa el trabajo, los metadatos de las rutas y los permisos de los registros sin ejecutar la comparación ni leer contenido protegido durante la enumeración.

Una transferencia repetida desde el host puede convertir un miembro no confiable del archivo en una ruta de salida posterior. Si un trabajo con más privilegios copia un archivo desde un contenedor menos confiable, extrae un enlace simbólico cuyo nombre coincide con el nombre base del destino de la siguiente transferencia y luego escribe en esa misma ruta, la escritura posterior podría llegar al destino del enlace. Comprueba el nombre y el destino del miembro del archivo, las opciones y el directorio de extracción, si el extractor realmente deja ese enlace en su lugar, cómo trata la implementación de transferencia un enlace existente en el destino y la identidad efectiva con permisos de escritura del trabajo en el host. [GNU tar documenta cómo se gestionan los archivos y enlaces simbólicos existentes durante la extracción](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp usa SFTP de forma predeterminada en las versiones modernas](https://man.openbsd.org/scp.1), así que verifica el comportamiento de transferencia instalado en lugar de asumir que todas las versiones de `scp` escriben a través de un enlace. Que un proceso `scp` sea visible desde el contenedor o que un archivo tenga permisos de escritura no demuestra por sí solo que se produzcan la extracción en el host y la escritura posterior. Inspecciona el trabajo y los metadatos de las rutas sin transferir ni extraer un archivo preparado durante la enumeración.

El módulo [`synchronize` de Ansible](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) ejecuta rsync; `copy_links: true` copia el destino de un enlace simbólico en lugar del enlace. Para una copia de seguridad programada, comprueba si un usuario con menos privilegios puede crear un enlace dentro del árbol de origen exacto, si la identidad de sincronización puede leer su destino y si ese usuario puede leer la copia o el archivo resultante. El playbook, la ubicación del enlace, la identidad de ejecución y los permisos de salida deben coincidir; un directorio de carga con permisos de escritura o la opción `copy_links` por sí solos son únicamente pistas para revisar. Inspecciona los metadatos y el playbook sin crear enlaces ni activar el trabajo.

## Inspecciona los descriptores abiertos

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un proceso puede conservar el acceso a un archivo después de que este se elimine o se cambie de nombre. Un proceso privilegiado también puede pasar un descriptor a través de un socket Unix o dejarlo abierto sin querer durante `execve()` si falta close-on-exec. Inspecciona los destinos de `/proc/<PID>/fd` en busca de archivos sensibles, archivos eliminados, rutas del host visibles dentro de un contenedor y sockets inesperados. El kernel aplica controles de acceso al desreferenciar los descriptores de otro proceso; que un enlace simbólico sea visible no garantiza que se pueda leer su contenido.

Un helper SUID personalizado puede abrir una ruta protegida, descartar su UID efectivo y dejar el descriptor abierto. Si luego se marca como dumpable, la propiedad y el acceso a `/proc/<PID>/fd` pueden cambiar; revisa la transición exacta de credenciales, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), la política de procfs/ptrace y los permisos del archivo de destino. Volver a abrir la ruta de un descriptor puede evitar un **directorio padre** inaccesible, pero aun así fallar si quien llama no puede leer el archivo. Que el destino de un descriptor sea visible o que tenga el bit SUID no demuestra por sí solo que haya una divulgación.

Los artefactos de fallos son una pista aparte: un volcado de memoria puede contener memoria del proceso, incluidos datos leídos anteriormente con una identidad de mayor privilegio. En Ubuntu, [Apport normalmente guarda los informes en `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); otros sistemas pueden usar un gestor `core_pattern` distinto o el almacenamiento de systemd. Durante una enumeración rutinaria, comprueba únicamente las rutas de los informes, su propietario, sus permisos y si se pueden leer. Un informe legible solo es relevante si el proceso correspondiente era dumpable, el gestor de fallos conservó los bytes sensibles y el usuario actual puede acceder al informe. No provoques el fallo de un helper ni desempaquetes un volcado como parte de una enumeración pasiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) para conocer las condiciones de SUID y generación de volcados.

Cuando un servicio usa un descriptor heredado, revisa su cadena de lanzamiento y los números de los descriptores antes de probar la redirección del shell o `/proc/self/fd/<N>`. Si se elimina un archivo mientras sigue abierto, la [recuperación de archivos eliminados](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) puede conservar evidencia o recuperar contenido. Para el análisis inicial de procesos, continúa con la [enumeración de procesos y rutas de servicios](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
