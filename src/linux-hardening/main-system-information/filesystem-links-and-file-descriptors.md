# Symlinks, Hardlinks, और File Descriptors

{{#include ../../banners/hacktricks-training.md}}

किसी path का नाम उस समय किसी object को संदर्भित करता है जब उसे resolve किया जाता है; खुला हुआ file descriptor, pathname बदलने के बाद भी उस object का संदर्भ बनाए रखता है। यह अंतर symlink races, छिपे हुए hardlinks, deleted files की recovery, और inherited descriptor leaks को समझाता है। inode और mount की पृष्ठभूमि के लिए [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) देखें।

## Links और path ownership का निरीक्षण करें

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

एक symlink pathname resolution को दूसरी ओर भेजता है; hardlink उसी filesystem पर उसी inode का एक और नाम है। अगर कोई privileged task user-writable directory के भीतर किसी अनुमानित path को पढ़ता या लिखता है, तो user उस path को किसी संवेदनशील target की ओर भेज सकता है। केवल अंतिम file ही नहीं, हर parent directory के ownership और permissions भी जाँचें। `fs.protected_symlinks` और `fs.protected_hardlinks` आम cross-user attacks को कम करते हैं, लेकिन मनमाने writable paths को सुरक्षित नहीं बनाते।

ऐसे privileged job के लिए जो shell glob से permissions बदलता है, उन links में फर्क करें जो **command-line operands** के रूप में expand होते हैं और उन links में जो बाद में recursive traversal के दौरान मिलते हैं। [GNU `chmod` command line पर दिए गए symlink के referent पर काम करता है](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), जबकि recursion के दौरान मिले symlinks को यह आम तौर पर अनदेखा करता है; केवल `-R` होने से ये दोनों स्थितियाँ एक जैसी नहीं हो जातीं। वास्तविक scheduled identity और command, यह कि untrusted user glob से मेल खाने वाली entry बना सकता है या नहीं, इंस्टॉल किए गए `chmod` का व्यवहार और options, और प्रस्तावित target को मिलने वाली access की जाँच करें। केवल writable directory या symlink होने से privileged mode change साबित नहीं होता। Passive enumeration के दौरान link बनाए या job चलाए बिना script और path metadata की जाँच करें।

कोई scheduled privileged writer अपने output path को अनुमानित बना सकता है, भले ही filename में देखने में random hash हो: [C `rand()` एक ही `srand()` seed के लिए अपना sequence दोहराता है](https://man7.org/linux/man-pages/man3/rand.3.html), जिसमें ज्ञात execution time से निकला seed भी शामिल है। अगर job उस नाम को बनाते समय caller-writable database rows भी पढ़ता है, तो row से name बनाने का सटीक algorithm, seed और libc का व्यवहार, schedule, caller के row लिखने और directory बनाने के अधिकार, और privileged open से पहले pre-existing symlink रखने की संभावना की पुष्टि करें। [`fopen(..., "w")` resolved file बनाता है या उसे truncate करता है](https://man7.org/linux/man-pages/man3/fopen.3.html); link-safe open flags या atomic replacement, effective write identity, target permissions और sticky-directory symlink policy के लिए वास्तविक implementation जाँचें। अनुमानित नाम या writable row अकेले केवल आगे जाँचने का संकेत है। Passive enumeration के दौरान rows डाले या job चलाए बिना code, schedule और metadata की जाँच करें।

किसी अन्य user के रूप में चलने वाली file-conversion service के लिए जाँचें कि caller output path या extension चुन सकता है या नहीं, और converter pre-existing output symlink को follow करता है या नहीं। कुछ converters output format को pathname extension से चुनते हैं; स्वीकार्य extension वाले नाम का link फिर भी किसी संवेदनशील, extension-रहित target की ओर जा सकता है। Cross-user write सफल होने के लिए service तक पहुँचना संभव होना, caller का path और link नियंत्रित करना, converter का link को output के लिए खोलना, और service identity के पास write permission होना ज़रूरी है। Linux का `fs.protected_symlinks=1` **sticky world-writable directory** में किसी दूसरे user के link को follow करने पर रोक लगाता है; यह सामान्य user-owned directory में मौजूद link को वैसी सुरक्षा नहीं देता। निष्कर्ष निकालने से पहले resolved path और parent ownership जाँचें। [calibre के output-file व्यवहार](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) और [Linux symlink policy](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks) देखें।

अगर sudo-allowed download wrapper caller द्वारा चुना गया data fetch करते समय caller-controlled working directory बनाए रखता है, तो उसके output path की भी इसी तरह जाँच करें। वास्तविक downloader की जाँच करें: क्या उसका चुना हुआ basename, collision handling या pre-existing symlink privileged write को दूसरी ओर भेज सकता है? केवल URL का चुनाव या symlink होना पर्याप्त नहीं है। [Axel प्रति-user `~/.axelrc` का दस्तावेज़ देता है](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), और इसके [example configuration में `default_filename` और `no_clobber` शामिल हैं](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), इसलिए Axel इस्तेमाल करने वाला wrapper उस file से output-name का चुनाव भी ले सकता है। प्रभावी `HOME` की पुष्टि करें: [sudo policy के अनुसार इसे reset या preserve कर सकता है](https://man7.org/linux/man-pages/man8/sudo.8.html), और user की `.axelrc` तभी प्रासंगिक है जब privileged downloader वास्तव में उसे पढ़ता हो। Passive enumeration के दौरान download शुरू किए बिना rule, wrapper, config path और permissions, अंतिम output name और target-file की स्थिति जाँचें।

sudo-allowed ACL wrapper के लिए, जाँचें कि `setfacl` को call करने से पहले यह caller द्वारा चुनी गई file को कैसे validate करता है। केवल lexical prefix check और `..` को अस्वीकार करने से allowed directory के भीतर का symlink बाहर resolve होने से नहीं रुकता; `test -f` भी link को follow करता है। पुष्टि करें कि wrapper पर्याप्त privilege के साथ ACL operation तक पहुँचता है, caller link को नियंत्रित करता है, और resulting ACL target **और उसके parent directories** पर ज़रूरी access देता है। कुछ consumers writable ACL या ढीले modes वाली files को अस्वीकार करते हैं, इसलिए केवल ACL change से escalation path के काम करने की पुष्टि नहीं होती।

## User-mounted FUSE filesystems में privileged writes की समीक्षा करें

`/etc/fuse.conf` में सक्रिय standalone `user_allow_other` line किसी non-root user को FUSE mount पर `allow_other` या `allow_root` का अनुरोध करने देती है। ये mount options किसी root process को mounting user द्वारा लागू किए गए filesystem तक पहुँचने दे सकते हैं। अगर sudo-allowed helper caller-controlled working directory के सापेक्ष secret रखने वाला log या अन्य output लिखता है, तो जाँचें कि क्या वह directory user-mounted FUSE filesystem हो सकती है। FUSE implementation writes को देख सकती है, भले ही resulting file सामान्य filesystem पर root-owned या mode `0600` वाली दिखे।

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

यह **संभावित मामला** है, disclosure का प्रमाण नहीं। वास्तविक sudo/run-as identity और arguments, helper का output path और संवेदनशील content, `/dev/fuse` तक पहुंच, `allow_other` या `allow_root` के साथ सफल mounting, और privileged process के mount में प्रवेश कर पाने की पुष्टि करें। नियमित enumeration के दौरान privileged helper न चलाएं और न ही filesystem mount करें। [libfuse की policy description](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) और [libfuse access FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem) देखें।

## Path races खोजें

खतरनाक pattern यह है कि कोई privileged program एक pathname की जांच करे और बाद में जांचे गए object का सुरक्षित reference रखे बिना उसी pathname को खोले। Parent directory पर नियंत्रण रखने वाला attacker इन दोनों operations के बीच file या symlink बदल सकता है। यही समस्या temporary files, timer-driven scripts, archive extraction और backup workflows में भी दिखती है। Impact का दावा करने से पहले वास्तविक read/write operation और target की permissions की पुष्टि करें।

Archive **बनाने** से भी अलग-अलग identities के बीच files disclose हो सकती हैं। Info-ZIP `zip -r` आम तौर पर source tree के अंदर रखे symlink को follow करता है और target का content store करता है; `-y`/`--symlinks` इसके बजाय link को ही store करता है। अगर lower-privileged user किसी backed-up directory में link जोड़ सकता है, तो इस्तेमाल किए गए archiver/options, backup job की read identity और यह जांचें कि resulting archive उस user के लिए readable है या नहीं। Writable source directory या अकेला symlink disclosure साबित नहीं करता। Backup trigger किए बिना या enumeration के दौरान secret content extract किए बिना link और archive metadata की समीक्षा करें। [Info-ZIP के option documentation](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638) देखें।

GNU `tar` का default अलग है: यह आम तौर पर symlink को link के रूप में store करता है, जबकि [`-h` / `--dereference` archive बनाते समय उसे follow करता है](https://www.gnu.org/software/tar/manual/html_node/dereference.html)। Privileged scheduled backup के लिए, इस्तेमाल किए गए सटीक `tar` invocation की जांच करें; यह भी देखें कि `tar` द्वारा पढ़े जाने से पहले lower-privileged user किसी input pathname को बदल सकता है या नहीं, और resulting archive उस user के लिए accessible है या नहीं। Writable staging directory में temporary checksum या कोई अन्य sidecar, बाद के `tar -h` command में स्पष्ट रूप से नामित होने पर ऐसा input बन सकता है। Race window, job identity, symlink policy, उस identity के तहत target की readability और archive ACL—इन सभी की पुष्टि जरूरी है। Passive checks के दौरान files न बदलें, job न चलाएं और sensitive archives unpack न करें।

Archive **extract करने** पर एक अलग boundary पार होती है, जब कोई privileged job ऐसा archive पढ़ता है जिसे lower-privileged user बदल सकता है। [GNU tar आम तौर पर superuser के रूप में चलने पर archived ownership restore करता है](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), और इसके [permission-restoration options](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) extracted mode bits को प्रभावित करते हैं। इस्तेमाल किए गए सटीक extractor और flags, archive बदलने की window, numeric owner और mode metadata, extraction directory permissions, और cleanup के बाद result accessible रह जाता है या नहीं—इनकी समीक्षा करें। Root-owned SUID member तभी चिंता का विषय है, जब उसका mode extraction के बाद बना रहे और target mount व process policy identity बदलने की अनुमति दें; केवल untrusted archive या writable staging path इसका प्रमाण नहीं है। Passive enumeration के दौरान archive बदले या extract किए बिना job और metadata की जांच करें।

Extract किया गया symlink बाद में होने वाली privileged comparison के जरिए protected file disclose कर सकता है। [GNU `diff` directories की तुलना करते समय आम तौर पर symlinks follow करता है](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), इसलिए untrusted extracted tree पर root-run `diff -r` किसी link target को पढ़ सकता है और अलग content को अपने output में शामिल कर सकता है। पुष्टि करें कि archive बदला जा सकता है, link ऐसे path पर पहुंचता है जहां comparison वास्तव में जाती है, target job के लिए readable है, और comparison output या error log lower-privileged user के लिए readable है। अकेला link या archive disclosure साबित नहीं करता; enumeration के दौरान comparison चलाए या protected content पढ़े बिना job, path metadata और log permissions की समीक्षा करें।

बार-बार होने वाला host-side transfer untrusted archive member को बाद के output path में बदल सकता है। यदि कोई higher-privileged job lower-trust container से archive copy करता है, ऐसे symlink को extract करता है जिसका नाम अगले transfer के destination basename से मेल खाता है, और बाद में उसी pathname पर लिखता है, तो अगला write link target तक पहुंच सकता है। Archive member का नाम और target, extraction flags और directory, extractor वास्तव में उस link को वहीं छोड़ता है या नहीं, मौजूदा destination link के साथ transfer implementation का व्यवहार, और host job की effective write identity जांचें। [GNU tar बताता है कि extraction के दौरान मौजूदा files और symlinks को कैसे संभाला जाता है](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [आधुनिक releases में OpenSSH scp default रूप से SFTP इस्तेमाल करता है](https://man.openbsd.org/scp.1), इसलिए यह मानने के बजाय कि हर `scp` version link के जरिए लिखता है, installed transfer behavior की पुष्टि करें। Container में दिखने वाला `scp` process या writable archive अकेले host पर extraction और बाद के write को साबित नहीं करता। Enumeration के दौरान crafted archive transfer या extract किए बिना job और path metadata की जांच करें।

Ansible का [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) rsync को wrap करता है; `copy_links: true` symlink के बजाय उसके referent को copy करता है। Scheduled backup के लिए जांचें कि lower-privileged user सटीक source tree के अंदर link बना सकता है या नहीं, synchronization identity उसका target पढ़ सकती है या नहीं, और resulting copy या archive उस user के लिए readable है या नहीं। Playbook, link placement, run-as identity और output permissions—सभी का मेल होना चाहिए; केवल writable upload directory या `copy_links` setting जांच के लिए संकेत मात्र है। Link बनाए या job trigger किए बिना metadata और playbook की जांच करें।

## Open descriptors की जांच करें

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

कोई process किसी file को delete या rename किए जाने के बाद भी उस तक पहुँच बनाए रख सकता है। कोई privileged process Unix socket के ज़रिए descriptor भी पास कर सकता है, या close-on-exec सेट न होने पर `execve()` के दौरान अनजाने में उसे खुला छोड़ सकता है। संवेदनशील files, deleted files, container के अंदर दिखाई देने वाले host paths और अनपेक्षित sockets के लिए `/proc/<PID>/fd` के targets देखें। किसी दूसरे process के descriptors को dereference करना kernel access checks के अधीन है; दिखाई देने वाली symlink से यह सुनिश्चित नहीं होता कि उसकी सामग्री पढ़ी जा सकती है।

कोई custom SUID helper संरक्षित pathname को खोल सकता है, अपना effective UID छोड़ सकता है और descriptor खुला छोड़ सकता है। अगर वह बाद में खुद को dumpable बनाता है, तो `/proc/<PID>/fd` का ownership और access बदल सकता है; credential transition, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), procfs/ptrace policy और target file mode की बारीकी से समीक्षा करें। Descriptor path को दोबारा खोलने से किसी inaccessible **parent directory** को bypass किया जा सकता है, लेकिन फिर भी उस file को खोलना विफल हो सकता है जिसे caller पढ़ नहीं सकता। केवल दिखाई देने वाला descriptor target या SUID bit disclosure साबित नहीं करता।

Crash artifacts एक अलग सुराग हैं: core dump में process memory हो सकती है, जिसमें पहले किसी higher identity के तहत पढ़ा गया data भी शामिल है। Ubuntu पर [Apport आम तौर पर reports को `/var/crash` में रखता है](https://documentation.ubuntu.com/project/contributors/debugging/apport/); अन्य systems में अलग `core_pattern` handler या systemd storage इस्तेमाल हो सकता है। Routine enumeration के दौरान केवल report paths, owner, mode और readability जाँचें। कोई readable report तभी मायने रखती है जब संबंधित process dumpable था, crash handler ने संवेदनशील bytes को बनाए रखा हो और मौजूदा user उस report को access कर सकता हो। Passive enumeration के हिस्से के रूप में किसी helper को crash न करें और न ही dump को unpack करें। SUID और dump-generation conditions के लिए [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) देखें।

जब कोई service inherited descriptor इस्तेमाल करती है, तो shell redirection या `/proc/self/fd/<N>` आज़माने से पहले उसकी launch chain और descriptor numbers की समीक्षा करें। अगर कोई file delete हो गई है लेकिन अब भी खुली है, तो [deleted-file recovery](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) से evidence बचाया जा सकता है या content recover किया जा सकता है। Process-level triage के लिए [process enumeration and service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md) जारी रखें।
