# Symlinks, Hardlinks y descriptores de archivo

{{#include ../../banners/hacktricks-training.md}}

Una ruta identifica un objeto en el momento en que se resuelve; un descriptor de archivo abierto mantiene una referencia al objeto aunque cambie el nombre de la ruta. Esta diferencia explica las carreras con symlinks, los hardlinks ocultos, la recuperación de archivos eliminados y los leaks de descriptores heredados. Consulta [sistema de archivos, inodos y recuperación](filesystem-inodes-and-recovery.md) para obtener información sobre inodos y montajes.

## Inspeccionar enlaces y la propiedad de las rutas

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink redirige la resolución de nombres de ruta; un hardlink es otro nombre para el mismo inode en el mismo sistema de archivos. Si una tarea privilegiada lee o escribe en una ruta predecible dentro de un directorio donde un usuario puede escribir, ese usuario podría redirigir la ruta a un objetivo sensible. Comprueba la propiedad y los permisos de todos los directorios padre, no solo del archivo final. `fs.protected_symlinks` y `fs.protected_hardlinks` reducen los ataques habituales entre usuarios, pero no hacen que cualquier ruta escribible sea segura.

En una tarea privilegiada que cambia permisos mediante un comodín de shell, distingue entre los symlinks expandidos como **operandos de la línea de comandos** y los encontrados después durante el recorrido recursivo. [GNU `chmod` actúa sobre el destino de un symlink indicado en la línea de comandos](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mientras que normalmente ignora los symlinks encontrados durante la recursión; `-R` por sí solo no hace que ambos casos sean equivalentes. Revisa la identidad y el comando programados reales, si un usuario no confiable puede crear una entrada que coincida con el comodín, el comportamiento y las opciones de `chmod` instalado, y el acceso resultante al objetivo propuesto. Un directorio escribible o un symlink, por sí solos, no demuestran que se produzca un cambio de permisos privilegiado. Inspecciona el script y los metadatos de las rutas sin crear un symlink ni activar la tarea durante la enumeración pasiva.

Un proceso privilegiado programado puede usar una ruta de salida predecible incluso si el nombre del archivo contiene un hash que parece aleatorio: [`rand()` de C repite su secuencia con la misma semilla de `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), incluso si la semilla se deriva de una hora de ejecución conocida. Si el proceso también lee filas de una base de datos donde quien lo invoca puede escribir para construir ese nombre, verifica el algoritmo exacto que convierte las filas en nombres, la semilla y el comportamiento de libc, la programación, los permisos de quien lo invoca para modificar filas y crear directorios, y si se puede colocar un symlink preexistente antes de la apertura privilegiada. [`fopen(..., "w")` crea o trunca el archivo resuelto](https://man7.org/linux/man-pages/man3/fopen.3.html); comprueba si la implementación real usa indicadores de apertura que protejan contra symlinks o un reemplazo atómico, la identidad efectiva de escritura, los permisos del objetivo y la política de symlinks en directorios sticky. Un nombre predecible o una fila escribible, por sí solos, solo justifican una revisión. Inspecciona el código, la programación y los metadatos sin insertar filas ni ejecutar el proceso durante la enumeración pasiva.

En un servicio de conversión de archivos que se ejecuta como otro usuario, revisa si quien lo invoca puede elegir una ruta o extensión de salida y si el conversor sigue un symlink de salida preexistente. Algunos conversores seleccionan el formato de salida según la extensión de la ruta; un link con un nombre que tenga una extensión aceptada aún puede apuntar a un objetivo sensible sin extensión. Para que se produzca una escritura entre usuarios, el servicio debe ser accesible, quien lo invoca debe controlar la ruta y el link, el conversor debe abrir el link para escribir y la identidad del servicio debe tener permiso de escritura. Linux `fs.protected_symlinks=1` restringe el seguimiento del link de otro usuario en un **directorio sticky con permisos de escritura para todos**; no ofrece la misma protección para un link en un directorio ordinario propiedad de un usuario. Inspecciona la ruta resuelta y la propiedad de los directorios padre antes de llegar a una conclusión. Consulta el [comportamiento de calibre con los archivos de salida](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) y la [política de symlinks de Linux](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Un wrapper de descarga permitido por sudo requiere la misma revisión de la ruta de salida si obtiene datos elegidos por quien lo invoca y conserva un directorio de trabajo controlado por esa persona. Inspecciona el descargador real y comprueba si el nombre base seleccionado, el manejo de colisiones o un symlink preexistente pueden redirigir una escritura privilegiada; elegir una URL o usar un symlink, por sí solos, no es suficiente. [Axel documenta un archivo `~/.axelrc` por usuario](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), y su [configuración de ejemplo incluye `default_filename` y `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), por lo que un wrapper que use Axel también podría heredar de ese archivo la elección del nombre de salida. Confirma el valor efectivo de `HOME`: [sudo puede restablecerlo o conservarlo según la política](https://man7.org/linux/man-pages/man8/sudo.8.html), y el archivo `.axelrc` de un usuario solo es relevante si el descargador privilegiado realmente lo lee. Comprueba la regla, el wrapper, la ruta y los permisos de la configuración, el nombre final de salida y el estado del archivo objetivo sin iniciar una descarga durante la enumeración pasiva.

En un wrapper de ACL permitido por sudo, inspecciona cómo valida un archivo elegido por quien lo invoca antes de llamar a `setfacl`. Una comprobación de prefijo léxico y el rechazo de `..` no impiden que un symlink dentro del directorio permitido se resuelva fuera de él; `test -f` también sigue el link. Confirma que el wrapper llega a la operación de ACL con privilegios suficientes, que quien lo invoca controla el link y que la ACL resultante concede el acceso necesario al objetivo **y a sus directorios padre**. Algunos consumidores rechazan archivos con ACL escribibles o permisos demasiado laxos, por lo que un cambio de ACL, por sí solo, no demuestra que exista una vía de escalada funcional.

## Revisar escrituras privilegiadas en sistemas de archivos FUSE montados por usuarios

Una línea activa e independiente `user_allow_other` en `/etc/fuse.conf` permite que un usuario no root solicite `allow_other` o `allow_root` en un montaje FUSE. Esas opciones de montaje pueden permitir que un proceso root acceda a un sistema de archivos implementado por el usuario que lo montó. Si un helper permitido por sudo escribe un registro con secretos u otra salida relativa a un directorio de trabajo controlado por quien lo invoca, revisa si ese directorio puede ser un sistema de archivos FUSE montado por un usuario. La implementación de FUSE puede observar las escrituras incluso cuando el archivo resultante parece pertenecer a root o tener modo `0600` en un sistema de archivos ordinario.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

This is a **candidato**, no una prueba de divulgación. Confirma la identidad y los argumentos reales de sudo/run-as, la ruta de salida y el contenido sensible del helper, el acceso a `/dev/fuse`, si el montaje se realiza correctamente con `allow_other` o `allow_root`, y si el proceso privilegiado puede acceder al punto de montaje. No ejecutes el helper privilegiado ni montes un sistema de archivos durante la enumeración rutinaria. Consulta la [descripción de la política de libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) y las [preguntas frecuentes sobre acceso de libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Busca condiciones de carrera en rutas

El patrón peligroso ocurre cuando un programa privilegiado comprueba una ruta y luego la abre sin conservar una referencia segura al objeto comprobado. Un atacante que controle un directorio padre puede reemplazar un archivo o symlink entre ambas operaciones. El mismo problema aparece con archivos temporales, scripts ejecutados por temporizador, extracción de archivos comprimidos y flujos de trabajo de copias de seguridad. Confirma la operación real de lectura/escritura y los permisos del objetivo antes de afirmar que existe un impacto.

La **creación** de archivos comprimidos también puede divulgar archivos entre identidades. Info-ZIP `zip -r` normalmente sigue un symlink ubicado dentro del árbol de origen y guarda el contenido del objetivo; `-y`/`--symlinks`, en cambio, guarda el propio enlace. Si un usuario con menos privilegios puede añadir un enlace en un directorio del que se hace una copia de seguridad, comprueba el compresor y las opciones exactos, la identidad con la que el trabajo de copia de seguridad lee los archivos y si ese usuario puede leer el archivo comprimido resultante. Un directorio de origen escribible o un symlink por sí solos no demuestran que haya divulgación. Revisa los metadatos del enlace y del archivo comprimido sin activar la copia de seguridad ni extraer contenido secreto durante la enumeración. Consulta la [documentación de opciones de Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` tiene un comportamiento predeterminado distinto: normalmente guarda un symlink como enlace, mientras que [`-h` / `--dereference` lo sigue al crear el archivo comprimido](https://www.gnu.org/software/tar/manual/html_node/dereference.html). En una copia de seguridad programada con privilegios, inspecciona la invocación exacta de `tar`, si un usuario con menos privilegios puede reemplazar una ruta de entrada antes de que `tar` la lea y si dicho usuario puede acceder al archivo comprimido resultante. Una suma de comprobación temporal u otro archivo auxiliar en un directorio de preparación escribible puede convertirse en una entrada de este tipo si se indica explícitamente en un comando posterior `tar -h`. Es necesario verificar la ventana de carrera, la identidad del trabajo, la política sobre symlinks, si el objetivo es legible con esa identidad y las ACL del archivo comprimido. No reemplaces archivos, ejecutes el trabajo ni descomprimas archivos sensibles durante las comprobaciones pasivas.

La **extracción** de archivos comprimidos cruza un límite distinto cuando un trabajo privilegiado lee un archivo comprimido que un usuario con menos privilegios puede reemplazar. [GNU tar normalmente restaura la propiedad archivada cuando lo ejecuta el superusuario](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), y sus [opciones de restauración de permisos](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) afectan los bits de modo de los archivos extraídos. Revisa el extractor y las opciones exactos, la ventana para reemplazar el archivo comprimido, los metadatos numéricos de propietario y modo, los permisos del directorio de extracción y si la limpieza deja el resultado accesible. Un miembro SUID propiedad de root solo es preocupante si su modo se conserva durante la extracción y la política del proceso y del punto de montaje permite el cambio de identidad; un archivo comprimido no confiable o una ruta de preparación escribible, por sí solos, no lo demuestran. Inspecciona el trabajo y los metadatos sin reemplazar ni extraer archivos comprimidos durante la enumeración pasiva.

Un symlink extraído también puede divulgar un archivo protegido mediante una comparación privilegiada posterior. [GNU `diff` normalmente sigue los symlinks al comparar directorios](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), por lo que un `diff -r` ejecutado como root sobre un árbol extraído no confiable podría leer el objetivo del enlace e incluir contenido distinto en su salida. Confirma que se puede reemplazar el archivo comprimido, que el enlace apunta a una ruta que la comparación realmente visita, que el trabajo puede leer el objetivo y que el usuario con menos privilegios puede leer la salida de la comparación o el registro de errores. El enlace o el archivo comprimido por sí solos no demuestran que haya divulgación; revisa el trabajo, los metadatos de las rutas y los permisos de los registros sin ejecutar la comparación ni leer contenido protegido durante la enumeración.

Una transferencia repetida desde el host puede convertir un miembro no confiable de un archivo comprimido en una ruta de salida posterior. Si un trabajo con más privilegios copia un archivo comprimido desde un contenedor con menor nivel de confianza, extrae un symlink cuyo nombre coincide con el nombre base del destino de la siguiente transferencia y luego escribe en esa misma ruta, la escritura posterior podría alcanzar el objetivo del enlace. Comprueba el nombre y el objetivo del miembro del archivo comprimido, las opciones de extracción y el directorio, si el extractor realmente deja el enlace en su lugar, cómo trata la implementación de transferencia un enlace existente en el destino y la identidad efectiva con la que escribe el trabajo del host. [GNU tar documenta cómo la extracción trata los archivos y symlinks existentes](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [OpenSSH scp usa SFTP de forma predeterminada en las versiones modernas](https://man.openbsd.org/scp.1), así que verifica el comportamiento de transferencia instalado en lugar de asumir que todas las versiones de `scp` escriben a través de un enlace. Un proceso `scp` visible desde el contenedor o un archivo comprimido escribible no bastan para demostrar lo que ocurre durante la extracción en el host y la escritura posterior. Inspecciona el trabajo y los metadatos de las rutas sin transferir ni extraer un archivo comprimido manipulado durante la enumeración.

El [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) de Ansible utiliza rsync; `copy_links: true` copia el referente de un symlink en vez del enlace. En una copia de seguridad programada, comprueba si un usuario con menos privilegios puede crear un enlace dentro del árbol de origen exacto, si la identidad de sincronización puede leer su objetivo y si ese usuario puede leer la copia o el archivo comprimido resultante. El playbook, la ubicación del enlace, la identidad de ejecución y los permisos de salida deben coincidir; un directorio de carga escribible o la opción `copy_links`, por sí solos, solo justifican revisar el caso. Inspecciona los metadatos y el playbook sin crear enlaces ni activar el trabajo.

## Inspecciona los descriptores abiertos

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un proceso puede conservar el acceso a un archivo después de que se elimine o se cambie su nombre. Un proceso privilegiado también puede pasar un descriptor a través de un socket Unix o dejarlo abierto involuntariamente durante `execve()` si falta close-on-exec. Inspecciona los destinos de `/proc/<PID>/fd` en busca de archivos sensibles, archivos eliminados, rutas del host visibles dentro de un contenedor y sockets inesperados. El acceso a los descriptores de otro proceso está sujeto a las comprobaciones de acceso del kernel; que un enlace simbólico sea visible no garantiza que su contenido se pueda leer.

Un helper SUID personalizado puede abrir una ruta protegida, reducir su UID efectivo y dejar el descriptor abierto. Si luego se marca como dumpable, la propiedad y el acceso a `/proc/<PID>/fd` pueden cambiar; revisa la transición exacta de credenciales, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), la política de procfs/ptrace y los permisos del archivo de destino. Reabrir la ruta de un descriptor puede eludir un **directorio padre** inaccesible, pero aun así fallar si quien llama no puede leer el archivo. Un destino de descriptor visible o el bit SUID, por sí solos, no demuestran que haya divulgación.

Los artefactos de fallos son una pista distinta: un volcado de núcleo puede contener memoria del proceso, incluidos datos leídos anteriormente con una identidad de nivel superior. En Ubuntu, [Apport normally places reports in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); otros sistemas pueden usar un gestor `core_pattern` distinto o almacenamiento de systemd. Durante la enumeración rutinaria, comprueba únicamente las rutas de los informes, su propietario, sus permisos y si se pueden leer. Un informe legible solo es relevante si el proceso en cuestión era dumpable, el gestor de fallos conservó los datos sensibles y el usuario actual puede acceder al informe. No provoques el fallo de un helper ni desempaquetes un volcado como parte de una enumeración pasiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) para conocer las condiciones de SUID y generación de volcados.

Cuando un servicio usa un descriptor heredado, revisa la cadena de lanzamiento y los números de descriptor antes de probar la redirección del shell o `/proc/self/fd/<N>`. Si un archivo se elimina pero sigue abierto, [deleted-file recovery](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) puede conservar pruebas o recuperar contenido. Para el análisis inicial a nivel de proceso, continúa con [process enumeration and service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
