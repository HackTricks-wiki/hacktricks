# Link simbolici, hard link e descrittori di file

{{#include ../../banners/hacktricks-training.md}}

Un percorso identifica un oggetto nel momento in cui viene risolto; un descrittore di file aperto mantiene un riferimento all’oggetto anche dopo che il nome del percorso cambia. Questa differenza spiega le race condition con i link simbolici, gli hard link nascosti, il recupero dei file eliminati e i leak dei descrittori ereditati. Consulta [filesystem, inode e recupero](filesystem-inodes-and-recovery.md) per informazioni su inode e mount.

## Ispezionare i link e la proprietà dei percorsi

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

Un symlink reindirizza la risoluzione del pathname; un hardlink è un altro nome per lo stesso inode sullo stesso filesystem. Se un task con privilegi legge o scrive in un percorso prevedibile all'interno di una directory scrivibile dall'utente, quest'ultimo potrebbe riuscire a reindirizzare quel percorso verso una destinazione sensibile. Controlla proprietà e permessi di ogni directory genitore, non solo quelli del file finale. `fs.protected_symlinks` e `fs.protected_hardlinks` riducono i comuni attacchi tra utenti, ma non rendono sicuri percorsi arbitrari scrivibili.

Per un job con privilegi che modifica i permessi usando un glob della shell, distingui i link espansi come **operandi della riga di comando** da quelli incontrati in seguito durante la ricorsione. [GNU `chmod` opera sul referente di un symlink specificato nella riga di comando](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), mentre normalmente ignora i symlink incontrati durante la ricorsione; `-R` da solo non rende equivalenti i due casi. Esamina l'identità e il comando effettivamente usati per l'esecuzione pianificata, se un utente non fidato può creare un elemento corrispondente al glob, il comportamento e le opzioni della versione di `chmod` installata e gli accessi risultanti per la destinazione proposta. Una directory scrivibile o un symlink, da soli, non dimostrano che ci sarà una modifica dei permessi con privilegi. Esamina lo script e i metadati del percorso senza creare un link né avviare il job durante la ricognizione passiva.

Un writer pianificato con privilegi può usare un percorso di output prevedibile anche se il nome del file contiene un hash dall'aspetto casuale: [la sequenza di `rand()` in C si ripete con lo stesso seed di `srand()`](https://man7.org/linux/man-pages/man3/rand.3.html), anche quando il seed deriva da un orario di esecuzione noto. Se per costruire quel nome il job legge anche righe di database scrivibili dal chiamante, verifica l'esatto algoritmo di conversione da riga a nome, il seed e il comportamento di libc, la pianificazione, i diritti del chiamante di modificare le righe e creare directory e la possibilità di collocare un symlink preesistente prima dell'apertura con privilegi. [`fopen(..., "w")` crea o tronca il file risolto](https://man7.org/linux/man-pages/man3/fopen.3.html); controlla nell'implementazione effettiva l'uso di flag di apertura sicuri rispetto ai link o della sostituzione atomica, l'identità effettiva con cui avviene la scrittura, i permessi della destinazione e la policy sui symlink nelle directory sticky. Un nome prevedibile o una riga scrivibile, da soli, sono soltanto spunti da approfondire. Esamina codice, pianificazione e metadati senza inserire righe né eseguire il job durante la ricognizione passiva.

Per un servizio di conversione file eseguito come un altro utente, verifica se il chiamante può scegliere un percorso o un'estensione di output e se il convertitore segue un symlink di output preesistente. Alcuni convertitori selezionano il formato di output in base all'estensione del pathname; un link con un'estensione accettata può comunque puntare a una destinazione sensibile senza estensione. Perché una scrittura tra utenti vada a buon fine, il servizio deve essere raggiungibile, il chiamante deve poter controllare il percorso e il link, il convertitore deve aprire il link in scrittura e l'identità del servizio deve avere i permessi di scrittura. In Linux, `fs.protected_symlinks=1` limita il follow di un link appartenente a un altro utente in una **directory sticky scrivibile da tutti**; non offre la stessa protezione per un link in una normale directory di proprietà dell'utente. Esamina il percorso risolto e la proprietà delle directory genitrici prima di trarre conclusioni. Vedi il [comportamento di calibre per i file di output](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) e la [policy Linux sui symlink](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks).

Anche un wrapper di download consentito da sudo richiede la stessa verifica del percorso di output se scarica dati scelti dal chiamante mantenendo una directory di lavoro controllata da quest'ultimo. Esamina il downloader effettivo e verifica se il basename selezionato, la gestione delle collisioni o un symlink preesistente possono reindirizzare una scrittura con privilegi; la scelta dell'URL o la sola presenza di un symlink non sono sufficienti. [Axel documenta un `~/.axelrc` per utente](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt) e il suo [file di configurazione di esempio include `default_filename` e `no_clobber`](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), quindi un wrapper che usa Axel potrebbe ereditare da quel file anche la scelta del nome di output. Verifica il valore effettivo di `HOME`: [sudo può reimpostarlo o mantenerlo in base alla policy](https://man7.org/linux/man-pages/man8/sudo.8.html) e il `.axelrc` dell'utente è rilevante solo se il downloader con privilegi lo legge davvero. Controlla la regola, il wrapper, il percorso e i permessi della configurazione, il nome finale dell'output e lo stato del file di destinazione senza avviare un download durante la ricognizione passiva.

Per un wrapper ACL consentito da sudo, verifica come convalida un file scelto dal chiamante prima di chiamare `setfacl`. Un controllo lessicale del prefisso e il rifiuto di `..` non impediscono a un symlink all'interno della directory consentita di risolversi al di fuori di essa; anche `test -f` segue il link. Verifica che il wrapper arrivi all'operazione ACL con privilegi sufficienti, che il chiamante controlli il link e che l'ACL risultante conceda l'accesso necessario alla destinazione **e alle relative directory genitrici**. Alcuni programmi che usano i file rifiutano quelli con ACL scrivibili o permessi troppo permissivi, quindi una modifica ACL, da sola, non dimostra l'esistenza di un percorso di escalation funzionante.

## Esamina le scritture con privilegi nei filesystem FUSE montati dall'utente

Una riga attiva standalone `user_allow_other` in `/etc/fuse.conf` consente a un utente non root di richiedere `allow_other` o `allow_root` su un mount FUSE. Queste opzioni di mount possono consentire a un processo root di accedere a un filesystem implementato dall'utente che lo ha montato. Se un helper consentito da sudo scrive un log contenente segreti o un altro output in un percorso relativo alla directory di lavoro controllata dal chiamante, verifica se tale directory può essere un filesystem FUSE montato dall'utente. L'implementazione FUSE può osservare le scritture anche se, su un filesystem ordinario, il file risultante sembra appartenere a root o avere modalità `0600`.

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

Questo è un **possibile indizio**, non una prova di divulgazione. Verifica l’identità effettiva usata da sudo/run-as e gli argomenti, il percorso di output dell’helper e i contenuti sensibili, l’accesso a `/dev/fuse`, l’esito positivo del mount con `allow_other` o `allow_root` e la possibilità per il processo privilegiato di accedere al mount. Non eseguire l’helper privilegiato né montare un filesystem durante la normale enumerazione. Consulta la [descrizione delle policy di libfuse](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) e le [FAQ sull’accesso di libfuse](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem).

## Cerca race sulle path

Lo schema pericoloso è un programma privilegiato che controlla un pathname e in seguito apre lo stesso pathname senza mantenere un riferimento sicuro all’oggetto verificato. Un attaccante che controlla una directory padre può sostituire un file o un symlink tra le due operazioni. Lo stesso problema si presenta nei file temporanei, negli script eseguiti da timer, nell’estrazione di archivi e nei workflow di backup. Prima di dichiarare un impatto, verifica l’effettiva operazione di lettura/scrittura e i permessi del target.

Anche la **creazione** di archivi può divulgare file tra identità diverse. Info-ZIP `zip -r` normalmente segue un symlink inserito nell’albero sorgente e salva il contenuto del target; `-y`/`--symlinks` salva invece il link stesso. Se un utente con privilegi inferiori può aggiungere un link a una directory di cui viene eseguito il backup, verifica l’archiver e le opzioni esatti, l’identità con cui il job di backup legge i dati e se l’utente può leggere l’archivio risultante. Una directory sorgente scrivibile o un symlink, da soli, non dimostrano una divulgazione. Esamina i metadati di link e archivi senza attivare il backup né estrarre contenuti segreti durante l’enumerazione. Consulta la [documentazione delle opzioni di Info-ZIP](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638).

GNU `tar` ha un comportamento predefinito diverso: normalmente salva un symlink come link, mentre [`-h` / `--dereference` lo segue durante la creazione dell’archivio](https://www.gnu.org/software/tar/manual/html_node/dereference.html). Per un backup pianificato eseguito con privilegi elevati, esamina l’invocazione esatta di `tar`, verifica se un utente con privilegi inferiori può sostituire un pathname di input prima che `tar` lo legga e se tale utente può accedere all’archivio risultante. Un checksum temporaneo o un altro file sidecar in una directory di staging scrivibile può diventare un input di questo tipo se viene nominato esplicitamente in un successivo comando `tar -h`. È necessario verificare la finestra di race, l’identità del job, la policy sui symlink, la leggibilità del target con tale identità e gli ACL dell’archivio. Durante i controlli passivi, non sostituire file, eseguire il job né estrarre archivi sensibili.

L’**estrazione** di archivi oltrepassa un confine diverso quando un job privilegiato legge un archivio che un utente con privilegi inferiori può sostituire. [GNU tar normalmente ripristina la proprietà archiviata quando viene eseguito dal superuser](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), e le sue [opzioni per il ripristino dei permessi](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) influiscono sui bit di modalità dei file estratti. Esamina l’estrattore e i flag esatti, la finestra temporale in cui l’archivio può essere sostituito, i metadati numerici di proprietario e modalità, i permessi della directory di estrazione e se la pulizia lascia i risultati accessibili. Un membro SUID di proprietà di root è un problema solo se la sua modalità sopravvive all’estrazione e le policy del mount e del processo target consentono il cambio di identità; un archivio non attendibile o un percorso di staging scrivibile, da soli, non lo dimostrano. Esamina il job e i metadati senza sostituire o estrarre archivi durante l’enumerazione passiva.

Un symlink estratto può anche divulgare un file protetto tramite un successivo confronto privilegiato. [GNU `diff` normalmente segue i symlink quando confronta directory](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), quindi un `diff -r` eseguito da root su un albero estratto non attendibile può leggere il target di un link e includere nel proprio output il contenuto diverso. Verifica che l’archivio possa essere sostituito, che il link punti a un percorso effettivamente esaminato dal confronto, che il job possa leggere il target e che l’utente con privilegi inferiori possa leggere l’output del confronto o il log degli errori. Il link o l’archivio, da soli, non dimostrano una divulgazione; esamina il job, i metadati del percorso e i permessi dei log senza eseguire il confronto né leggere contenuti protetti durante l’enumerazione.

Un trasferimento ripetuto lato host può trasformare un membro di archivio non attendibile in un successivo percorso di output. Se un job con privilegi superiori copia un archivio da un container con un livello di fiducia inferiore, estrae un symlink il cui nome coincide con il basename della destinazione del trasferimento successivo e in seguito scrive sullo stesso pathname, la scrittura successiva potrebbe raggiungere il target del link. Controlla il nome e il target del membro dell’archivio, i flag e la directory di estrazione, se l’estrattore lascia effettivamente quel link al suo posto, come l’implementazione del trasferimento gestisce un link di destinazione già esistente e l’identità effettiva con cui scrive il job host. [GNU tar documenta come l’estrazione gestisce file e symlink esistenti](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [nelle versioni moderne OpenSSH scp usa SFTP per impostazione predefinita](https://man.openbsd.org/scp.1), quindi verifica il comportamento del trasferimento installato invece di presumere che tutte le versioni di `scp` scrivano attraverso un link. Un processo `scp` visibile dal container o un archivio scrivibile, da soli, non dimostrano cosa accadrà durante l’estrazione sull’host né nella scrittura successiva. Esamina il job e i metadati del percorso senza trasferire o estrarre archivi appositamente creati durante l’enumerazione.

Il modulo [`synchronize` di Ansible](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) usa rsync; `copy_links: true` copia il target del symlink invece del link. Per un backup pianificato, verifica se un utente con privilegi inferiori può creare un link all’interno dell’albero sorgente esatto, se l’identità usata per la sincronizzazione può leggere il target e se tale utente può leggere la copia o l’archivio risultante. Playbook, posizione del link, identità run-as e permessi dell’output devono essere tutti coerenti; una directory di upload scrivibile o l’opzione `copy_links`, da sole, sono soltanto spunti per un’analisi. Esamina i metadati e il playbook senza creare link né attivare il job.

## Esamina i file descriptor aperti

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

Un processo può mantenere l'accesso a un file anche dopo che questo è stato eliminato o rinominato. Un processo con privilegi può anche passare un descrittore tramite un socket Unix oppure lasciarlo aperto involontariamente durante `execve()` se manca close-on-exec. Esamina i target in `/proc/<PID>/fd` alla ricerca di file sensibili, file eliminati, percorsi dell'host visibili all'interno di un container e socket inattesi. Il dereferenziamento dei descrittori di un altro processo è soggetto ai controlli di accesso del kernel; la visibilità di un link simbolico non garantisce che sia possibile leggerne il contenuto.

Un helper SUID personalizzato può aprire un percorso protetto, abbassare il proprio UID effettivo e lasciare aperto il descrittore. Se poi si rende dumpable, la proprietà e l'accessibilità di `/proc/<PID>/fd` possono cambiare; verifica l'esatta transizione delle credenziali, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), le policy di procfs/ptrace e i permessi del file target. Riaprire un percorso di un descrittore può aggirare una **directory padre** inaccessibile, ma può comunque fallire se il chiamante non può leggere il file. La visibilità del target di un descrittore o del bit SUID, da sola, non dimostra che i dati siano divulgati.

Gli artefatti di crash sono un indizio distinto: un core dump può contenere la memoria del processo, compresi i dati letti in precedenza con un'identità più privilegiata. Su Ubuntu, [Apport normalmente colloca i report in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/); altri sistemi possono usare un handler `core_pattern` diverso o l'archiviazione di systemd. Durante la normale enumerazione, controlla solo i percorsi dei report, il proprietario, i permessi e la leggibilità. Un report leggibile è rilevante solo se il processo interessato era dumpable, l'handler di crash ha conservato i byte sensibili e l'utente corrente può accedere al report. Non mandare in crash un helper né decomprimere un dump durante l'enumerazione passiva. Consulta [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) per le condizioni relative a SUID e alla generazione dei dump.

Quando un servizio usa un descrittore ereditato, esamina la catena di avvio e i numeri dei descrittori prima di provare il reindirizzamento della shell o `/proc/self/fd/<N>`. Se un file è stato eliminato ma è ancora aperto, il [recupero di file eliminati](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) può preservare le prove o consentire di recuperarne il contenuto. Per il triage a livello di processo, continua con [l'enumerazione dei processi e i percorsi dei servizi](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md).
