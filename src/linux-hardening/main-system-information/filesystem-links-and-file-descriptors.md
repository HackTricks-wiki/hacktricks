# Symlinks, Hardlinks, और File Descriptors

{{#include ../../banners/hacktricks-training.md}}

किसी path का नाम उस object को दर्शाता है जिसे resolve किए जाने के समय वह नाम दिया गया हो; open file descriptor, pathname बदलने के बाद भी उस object का reference बनाए रखता है। यही अंतर symlink races, छिपे हुए hardlinks, deleted files की recovery और inherited descriptor leaks को समझाता है। inode और mount की पृष्ठभूमि के लिए [filesystem, inodes and recovery](filesystem-inodes-and-recovery.md) देखें।

## Links और path ownership की जाँच करें

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

एक symlink pathname resolution को redirect करता है; hardlink उसी filesystem पर उसी inode का दूसरा नाम होता है। अगर कोई privileged task किसी user-writable directory के अंदर अनुमानित path को पढ़ता या लिखता है, तो user उस path को किसी संवेदनशील target पर redirect कर सकता है। सिर्फ़ अंतिम file की नहीं, हर parent directory की ownership और permissions जाँचें। `fs.protected_symlinks` और `fs.protected_hardlinks` आम cross-user attacks को कम करते हैं, लेकिन मनमाने writable paths को सुरक्षित नहीं बनाते।

किसी privileged job के लिए, जो shell glob के साथ permissions बदलता है, उन links में अंतर करें जो **command-line operands** के रूप में expand होते हैं और उन links में जो बाद में recursive traversal के दौरान मिलते हैं। [GNU `chmod` command line पर दिए गए symlink के referent पर काम करता है](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html), जबकि recursion के दौरान मिले symlinks को आम तौर पर अनदेखा करता है; सिर्फ़ `-R` जोड़ने से ये दोनों मामले एक जैसे नहीं हो जाते। वास्तविक scheduled identity और command, यह कि कोई untrusted user glob से match होने वाली entry बना सकता है या नहीं, install किए गए `chmod` का व्यवहार और options, और प्रस्तावित target को मिलने वाली access की जाँच करें। सिर्फ़ writable directory या symlink से privileged mode change साबित नहीं होता। Passive enumeration के दौरान link रखे या job चलाए बिना script और path metadata देखें।

कोई scheduled privileged writer, output path को अनुमानित बना सकता है—भले ही filename में random-जैसा दिखने वाला hash हो: [C `rand()` एक ही `srand()` seed पर अपना sequence दोहराता है](https://man7.org/linux/man-pages/man3/rand.3.html), इसमें known execution time से निकला seed भी शामिल है। अगर job उस नाम को बनाते समय caller-writable database rows भी पढ़ता है, तो सटीक row-to-name algorithm, seed और libc behavior, schedule, caller के row-write और directory-create अधिकार, और यह जाँचें कि privileged open से पहले पहले से मौजूद symlink रखा जा सकता है या नहीं। [`fopen(..., "w")` resolved file को बनाता या truncate करता है](https://man7.org/linux/man-pages/man3/fopen.3.html); link-safe open flags या atomic replacement, effective write identity, target permissions और sticky-directory symlink policy के लिए वास्तविक implementation जाँचें। अनुमानित नाम या writable row अपने-आप में सिर्फ़ समीक्षा का संकेत है। Passive enumeration के दौरान rows जोड़े या job चलाए बिना code, schedule और metadata देखें।

किसी दूसरे user के रूप में चलने वाली file-conversion service के लिए, जाँचें कि caller output path या extension चुन सकता है या नहीं, और क्या converter पहले से मौजूद output symlink को follow करता है। कुछ converters pathname extension से output format चुनते हैं; स्वीकार्य extension वाले नाम का link फिर भी बिना extension वाले संवेदनशील target पर जा सकता है। Cross-user write सफल होने के लिए service तक पहुँच, path और link पर caller का नियंत्रण, converter द्वारा link को output के लिए खोलना, और service identity के पास write permission—ये सभी ज़रूरी हैं। Linux का `fs.protected_symlinks=1` **sticky world-writable directory** में किसी दूसरे user के link को follow करने पर रोक लगाता है; सामान्य user-owned directory में मौजूद link को यह वही सुरक्षा नहीं देता। निष्कर्ष निकालने से पहले resolved path और parent की ownership जाँचें। [calibre का output-file behavior](https://manual.calibre-ebook.com/generated/en/ebook-convert.html) और [Linux symlink policy](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks) देखें।

अगर sudo की अनुमति वाला download wrapper, caller के नियंत्रण वाले working directory को बनाए रखते हुए caller द्वारा चुना गया data fetch करता है, तो उसके output path की भी ऐसी ही जाँच ज़रूरी है। वास्तविक downloader और यह जाँचें कि उसका चुना हुआ basename, collision handling या पहले से मौजूद symlink किसी privileged write को redirect कर सकता है या नहीं; सिर्फ़ URL का चुनाव या symlink पर्याप्त नहीं है। [Axel प्रति-user `~/.axelrc` का दस्तावेज़ देता है](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt), और उसके [उदाहरण configuration में `default_filename` और `no_clobber` शामिल हैं](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example), इसलिए Axel इस्तेमाल करने वाला wrapper उस file से output-name का चुनाव भी inherit कर सकता है। Effective `HOME` की पुष्टि करें: [sudo policy के अनुसार इसे reset या preserve कर सकता है](https://man7.org/linux/man-pages/man8/sudo.8.html), और user की `.axelrc` तभी प्रासंगिक है जब privileged downloader वास्तव में उसे पढ़ता हो। Passive enumeration के दौरान download शुरू किए बिना rule, wrapper, config path और permissions, अंतिम output name और target-file state जाँचें।

अगर sudo की अनुमति वाला ACL wrapper है, तो जाँचें कि `setfacl` को call करने से पहले वह caller द्वारा चुनी गई file को कैसे validate करता है। केवल lexical prefix check और `..` को अस्वीकार करना, allowed directory के अंदर मौजूद symlink को उसके बाहर resolve होने से नहीं रोकता; `test -f` भी link को follow करता है। पुष्टि करें कि wrapper पर्याप्त privilege के साथ ACL operation तक पहुँचता है, caller का link पर नियंत्रण है, और resulting ACL target **और उसकी parent directories** पर ज़रूरी access देता है। कुछ consumers writable ACL या ढीले modes वाली files को अस्वीकार करते हैं, इसलिए केवल ACL बदलने से काम करने वाला escalation path साबित नहीं होता।

## User-mounted FUSE filesystems पर privileged writes की समीक्षा

`/etc/fuse.conf` में मौजूद सक्रिय, standalone `user_allow_other` line किसी non-root user को FUSE mount पर `allow_other` या `allow_root` का अनुरोध करने देती है। ये mount options root process को उस filesystem तक पहुँचने दे सकते हैं जिसे mount करने वाले user ने implement किया है। अगर sudo की अनुमति वाला helper caller के नियंत्रण वाले working directory के सापेक्ष secret-bearing log या कोई अन्य output लिखता है, तो जाँचें कि वह directory user-mounted FUSE filesystem हो सकती है या नहीं। FUSE implementation writes देख सकता है, भले ही परिणामी file किसी सामान्य filesystem पर root-owned या mode `0600` दिखे।

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

यह **संभावित संकेत** है, disclosure का प्रमाण नहीं। वास्तविक sudo/run-as identity और arguments, helper का output path और संवेदनशील content, `/dev/fuse` तक पहुँच, `allow_other` या `allow_root` के साथ सफल mounting, और यह सत्यापित करें कि privileged process mount में प्रवेश कर सकता है या नहीं। नियमित enumeration के दौरान privileged helper न चलाएँ और filesystem mount न करें। [libfuse की policy का विवरण](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf) और [libfuse का access FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem) देखें।

## Path race की जाँच करें

खतरनाक स्थिति तब बनती है जब कोई privileged program किसी pathname की जाँच करता है और बाद में जाँचे गए object का सुरक्षित reference रखे बिना उसी pathname को खोलता है। Parent directory को नियंत्रित करने वाला attacker इन दोनों कार्रवाइयों के बीच file या symlink बदल सकता है। यही समस्या temporary files, timer-driven scripts, archive extraction और backup workflows में भी आती है। Impact का दावा करने से पहले वास्तविक read/write operation और target की permissions की पुष्टि करें।

Archive **बनाने** से भी अलग-अलग identities के बीच files disclose हो सकती हैं। Info-ZIP `zip -r` सामान्यतः source tree में रखे symlink को follow करके target का content store करता है; `-y`/`--symlinks` इसके बजाय link को ही store करता है। अगर कम privileges वाला user backed-up directory में link जोड़ सकता है, तो इस्तेमाल किए गए archiver/options, backup job की read identity और यह जाँचें कि बना हुआ archive उस user द्वारा पढ़ा जा सकता है या नहीं। Writable source directory या अकेला symlink disclosure साबित नहीं करता। Backup trigger किए बिना या enumeration के दौरान secret content extract किए बिना link और archive metadata देखें। [Info-ZIP के option दस्तावेज़](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638) देखें।

GNU `tar` का default अलग है: यह सामान्यतः symlink को link के रूप में store करता है, जबकि [`-h` / `--dereference` archive बनाते समय symlink को follow करता है](https://www.gnu.org/software/tar/manual/html_node/dereference.html)। Privileged scheduled backup के लिए, सटीक `tar` invocation देखें; जाँचें कि क्या कम privileges वाला user `tar` द्वारा input pathname पढ़े जाने से पहले उसे बदल सकता है, और क्या बना हुआ archive उस user के लिए accessible है। Writable staging directory में रखा temporary checksum या कोई अन्य sidecar ऐसी input बन सकता है, अगर बाद की `tar -h` command में उसे स्पष्ट रूप से नाम दिया गया हो। Race window, job identity, symlink policy, उस identity के तहत target की readability और archive ACL—इन सभी की पुष्टि ज़रूरी है। Passive checks के दौरान files न बदलें, job न चलाएँ और संवेदनशील archives unpack न करें।

Archive **extract करने** पर एक अलग boundary पार होती है, जब privileged job ऐसा archive पढ़ता है जिसे कम privileges वाला user बदल सकता है। [GNU tar सामान्यतः superuser के रूप में चलने पर archived ownership बहाल करता है](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html), और इसके [permission-restoration options](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html) extracted mode bits को प्रभावित करते हैं। सटीक extractor और flags, archive बदलने की window, numeric owner और mode metadata, extraction directory permissions, तथा cleanup के बाद परिणाम accessible रहता है या नहीं—इनकी जाँच करें। Root-owned SUID member तभी चिंता का विषय है जब extraction के बाद उसका mode बना रहे और target mount तथा process policy identity change की अनुमति दें; केवल untrusted archive या writable staging path इसका प्रमाण नहीं है। Passive enumeration के दौरान archive बदले या extract किए बिना job और metadata देखें।

Extract किया गया symlink बाद में privileged comparison के ज़रिए protected file disclose कर सकता है। [Directories की तुलना करते समय GNU `diff` सामान्यतः symlinks को follow करता है](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html), इसलिए untrusted extracted tree पर root के रूप में चलाया गया `diff -r` किसी link target को पढ़ सकता है और अपने output में अलग content शामिल कर सकता है। पुष्टि करें कि archive बदला जा सकता है, link ऐसे path पर पहुँचता है जिसे comparison वास्तव में देखता है, target job के लिए readable है, और comparison output या error log कम privileges वाले user द्वारा पढ़ा जा सकता है। केवल link या archive disclosure साबित नहीं करता; enumeration के दौरान comparison चलाए या protected content पढ़े बिना job, path metadata और log permissions देखें।

Host-side बार-बार होने वाला transfer untrusted archive member को बाद का output path बना सकता है। अगर higher-privileged job lower-trust container से archive copy करता है, ऐसे symlink को extract करता है जिसका नाम अगले transfer के destination basename से मेल खाता है, और बाद में उसी pathname पर लिखता है, तो बाद का write link target तक पहुँच सकता है। Archive member का नाम और target, extraction flags और directory, extractor वास्तव में उस link को वहीं छोड़ता है या नहीं, मौजूदा destination link के साथ transfer implementation का व्यवहार, और host job की effective write identity जाँचें। [GNU tar बताता है कि extraction के दौरान मौजूदा files और symlinks कैसे संभाले जाते हैं](https://www.gnu.org/software/tar/manual/html_section/extract-options.html); [आधुनिक releases में OpenSSH scp default रूप से SFTP इस्तेमाल करता है](https://man.openbsd.org/scp.1), इसलिए यह मानने के बजाय कि सभी `scp` versions link के रास्ते write करते हैं, installed transfer behavior की पुष्टि करें। Container में दिखने वाला `scp` process या writable archive अकेले host extraction और बाद के write को साबित नहीं करता। Enumeration के दौरान crafted archive transfer या extract किए बिना job और path metadata देखें।

Ansible का [`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html) rsync का उपयोग करता है; `copy_links: true` symlink के बजाय उसके referent को copy करता है। Scheduled backup के लिए जाँचें कि क्या कम privileges वाला user सटीक source tree में link बना सकता है, synchronization identity उसका target पढ़ सकती है या नहीं, और बनी हुई copy या archive उस user के लिए readable है या नहीं। Playbook, link की जगह, run-as identity और output permissions—सभी का एक साथ मेल होना ज़रूरी है; केवल writable upload directory या `copy_links` setting जाँच का संकेत है। Link बनाए या job trigger किए बिना metadata और playbook देखें।

## खुले descriptors की जाँच करें

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

कोई process फ़ाइल को delete या rename किए जाने के बाद भी उस तक पहुँच बनाए रख सकता है। कोई privileged process Unix socket के ज़रिए descriptor भी भेज सकता है, या `execve()` के दौरान close-on-exec न होने पर अनजाने में उसे खुला छोड़ सकता है। संवेदनशील फ़ाइलों, deleted फ़ाइलों, container के अंदर दिखाई देने वाले host paths और अनपेक्षित sockets के लिए `/proc/<PID>/fd` के targets की जाँच करें। किसी दूसरे process के descriptors को dereference करने पर kernel access checks लागू होते हैं; दिखाई देने वाली symlink से यह सुनिश्चित नहीं होता कि उसकी सामग्री पढ़ी जा सकती है।

कोई custom SUID helper संरक्षित pathname खोल सकता है, अपना effective UID छोड़ सकता है और descriptor खुला छोड़ सकता है। अगर वह इसके बाद खुद को dumpable बना ले, तो `/proc/<PID>/fd` का ownership और access बदल सकता है; credentials में हुए सटीक बदलाव, [`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html), procfs/ptrace policy और target file mode की समीक्षा करें। Descriptor path को दोबारा खोलने से किसी अप्राप्य **parent directory** को दरकिनार किया जा सकता है, लेकिन अगर caller फ़ाइल पढ़ नहीं सकता, तो यह फिर भी विफल होगा। दिखाई देने वाला descriptor target या SUID bit अकेले disclosure साबित नहीं करता।

Crash artifacts जाँच का एक अलग सुराग हैं: core dump में process memory हो सकती है, जिसमें किसी उच्चतर identity के तहत पहले पढ़ा गया डेटा भी शामिल है। Ubuntu पर, [Apport आमतौर पर reports को `/var/crash` में रखता है](https://documentation.ubuntu.com/project/contributors/debugging/apport/); अन्य systems में अलग `core_pattern` handler या systemd storage हो सकता है। नियमित enumeration के दौरान सिर्फ report paths, owner, mode और readability की जाँच करें। कोई report तभी मायने रखती है, जब संबंधित process dumpable रहा हो, crash handler ने संवेदनशील bytes रखे हों और मौजूदा user उस report तक पहुँच सकता हो। Passive enumeration के दौरान किसी helper को crash न करें और न ही कोई dump unpack करें। SUID और dump generation की शर्तों के लिए [`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) देखें।

जब कोई service inherited descriptor का उपयोग करती है, तो shell redirection या `/proc/self/fd/<N>` आज़माने से पहले उसकी launch chain और descriptor numbers की समीक्षा करें। अगर कोई फ़ाइल deleted है, लेकिन अभी भी खुली है, तो [deleted फ़ाइल की रिकवरी](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) से सबूत सुरक्षित रह सकते हैं या सामग्री recover हो सकती है। Process-level triage के लिए, [process enumeration और service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md) पर जाएँ।
