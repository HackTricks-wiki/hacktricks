# シンボリックリンク、ハードリンク、ファイルディスクリプター

{{#include ../../banners/hacktricks-training.md}}

パス名は解決時点のオブジェクトを指します。一方、開いたファイルディスクリプターは、パス名が変更された後もオブジェクトへの参照を保持します。この違いが、シンボリックリンクの競合状態、隠れたハードリンク、削除済みファイルの復旧、継承されたディスクリプターの漏えいを説明します。inode とマウントの背景については、[filesystem、inode、復旧](filesystem-inodes-and-recovery.md)を参照してください。

## リンクとパスの所有権を調べる

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

symlinkはパス名解決をリダイレクトします。hardlinkは、同じファイルシステム上の同じinodeに対する別の名前です。特権タスクがユーザー書き込み可能なディレクトリ内の予測可能なパスを読み書きする場合、ユーザーがそのパスを機密性の高い対象へリダイレクトできる可能性があります。最終ファイルだけでなく、すべての親ディレクトリの所有者と権限を確認してください。`fs.protected_symlinks`と`fs.protected_hardlinks`は、よくあるユーザー間攻撃のリスクを下げますが、任意の書き込み可能パスを安全にするものではありません。

シェルのglobを使って権限を変更する特権ジョブについては、glob展開時に**コマンドライン引数**になったリンクと、再帰的な探索中に後から見つかったリンクを区別してください。[GNU `chmod`は、コマンドライン上で指定されたsymlinkの参照先に対して動作します](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html)。一方、再帰処理中に見つかったsymlinkは通常無視します。`-R`を指定するだけでは、これらのケースは同じになりません。実際に実行されるIDとコマンド、信頼できないユーザーがglobに一致するエントリを作成できるか、インストール済みの`chmod`の動作とオプション、対象のアクセス権が変更後にどうなるかを確認してください。書き込み可能なディレクトリやsymlinkがあるだけでは、特権によるモード変更が起きるとは限りません。受動的な列挙中は、リンクを作成したりジョブを実行したりせずに、スクリプトとパスのメタデータを調べてください。

特権ユーザーで実行される定期ジョブでは、ファイル名にランダムに見えるハッシュが含まれていても、出力パスを予測できる場合があります。[Cの`rand()`は同じ`srand()`シードで同じ系列を繰り返します](https://man7.org/linux/man-pages/man3/rand.3.html)。既知の実行時刻から導出されたシードも同様です。さらに、そのジョブが名前の生成時に呼び出し元が書き込み可能なデータベース行を読み取る場合は、行から名前を生成する正確なアルゴリズム、シードとlibcの動作、スケジュール、呼び出し元が持つ行の書き込み権限とディレクトリ作成権限、特権プロセスがファイルを開く前に既存のsymlinkを配置できるかを確認してください。[`fopen(..., "w")`は解決後のファイルを作成または切り詰めます](https://man7.org/linux/man-pages/man3/fopen.3.html)。リンクに対して安全なopenフラグやアトミックな置き換えの有無、実効書き込みID、対象の権限、stickyディレクトリにおけるsymlinkポリシーを実装で確認してください。名前が予測可能であることや、行が書き込み可能であることだけでは、調査の手掛かりにすぎません。受動的な列挙中は、行を挿入したりジョブを実行したりせずに、コード、スケジュール、メタデータを調べてください。

別ユーザーとして実行されるファイル変換サービスでは、呼び出し元が出力パスや拡張子を選べるか、変換ツールが既存の出力symlinkをたどるかを確認してください。変換ツールによっては、パス名の拡張子から出力形式を選択します。受け入れられる拡張子の名前を持つリンクでも、機密性の高い拡張子なしの対象を指すことがあります。ユーザー間の書き込みを成立させるには、サービスに到達できること、呼び出し元がパスとリンクを制御できること、変換ツールがそのリンクを出力先として開くこと、サービスの実行IDに書き込み権限があることが必要です。Linuxの`fs.protected_symlinks=1`は、**sticky属性付きの全ユーザー書き込み可能ディレクトリ**内にある別ユーザーのリンクをたどる動作を制限しますが、通常のユーザー所有ディレクトリ内のリンクには同じ保護を提供しません。結論を出す前に、解決後のパスと親ディレクトリの所有者を確認してください。[calibreの出力ファイルの動作](https://manual.calibre-ebook.com/generated/en/ebook-convert.html)と[Linuxのsymlinkポリシー](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks)を参照してください。

sudoで許可されたダウンロード用ラッパーでも、呼び出し元が制御する作業ディレクトリを使ったまま、呼び出し元が選んだデータを取得する場合は、同じ出力パスの確認が必要です。実際のダウンローダーを調べ、選択されるベース名、同名ファイルがある場合の処理、既存のsymlinkによって特権書き込みがリダイレクトされる可能性を確認してください。URLの選択やsymlinkがあるだけでは不十分です。[Axelはユーザーごとの`~/.axelrc`を文書化しています](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt)。また、[設定例には`default_filename`と`no_clobber`が含まれます](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example)。そのため、Axelを使うラッパーは、このファイルに指定された出力名を引き継ぐ可能性もあります。実効`HOME`を確認してください。[sudoはポリシーに応じて`HOME`をリセットまたは保持できます](https://man7.org/linux/man-pages/man8/sudo.8.html)。ユーザーの`.axelrc`が関係するのは、特権ダウンローダーが実際にそのファイルを読み込む場合だけです。受動的な列挙中はダウンロードを開始せずに、ルール、ラッパー、設定ファイルのパスと権限、最終的な出力名、対象ファイルの状態を確認してください。

sudoで許可されたACL用ラッパーでは、`setfacl`を呼び出す前に、呼び出し元が選んだファイルをどのように検証しているかを調べてください。字句的なプレフィックスのチェックや`..`の拒否だけでは、許可されたディレクトリ内のsymlinkが外部を指すのを防げません。`test -f`もリンクをたどります。ラッパーが十分な権限でACL操作を実行すること、呼び出し元がリンクを制御できること、変更後のACLによって対象**およびその親ディレクトリ**に必要なアクセス権が付与されることを確認してください。書き込み可能なACLや緩いモードのファイルを拒否する利用側もあります。そのため、ACLの変更だけでは、実際に成立する権限昇格経路があるとは言えません。

## ユーザーがマウントしたFUSEファイルシステムへの特権書き込みを調査する

`/etc/fuse.conf`に有効な`user_allow_other`の単独行があると、root以外のユーザーがFUSEマウントで`allow_other`または`allow_root`を要求できます。これらのマウントオプションにより、rootプロセスがマウントしたユーザーによって実装されたファイルシステムにアクセスできる場合があります。sudoで許可されたヘルパーが、呼び出し元が制御する作業ディレクトリを基準に、秘密を含むログなどの出力を書き込む場合、そのディレクトリをユーザーがマウントしたFUSEファイルシステムにできるか確認してください。通常のファイルシステム上ではroot所有またはモード`0600`に見えるファイルであっても、FUSEの実装は書き込みを観察できる場合があります。

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

これは**候補**であり、情報開示の証明ではありません。実際の sudo/run-as の identity と引数、helper の出力先と機密情報の内容、`/dev/fuse` へのアクセス、`allow_other` または `allow_root` を指定したマウントの成功、そして特権プロセスがそのマウントに入れるかを確認してください。通常の列挙中に特権 helper を実行したり、ファイルシステムをマウントしたりしないでください。[libfuse のポリシー説明](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf)と[libfuse のアクセス FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem)を参照してください。

## パス競合を探す

危険なパターンは、特権プログラムがあるパス名を確認した後、確認済みのオブジェクトへの安全な参照を保持せず、後から同じパス名を開くことです。親ディレクトリを制御できる攻撃者は、2つの操作の間にファイルや symlink を置き換えられます。同様の問題は、一時ファイル、タイマー起動スクリプト、アーカイブの展開、バックアップ処理でも発生します。影響を主張する前に、実際の読み書き操作と対象の権限を確認してください。

アーカイブの**作成**によっても、異なる identity 間でファイルが開示されることがあります。Info-ZIP の `zip -r` は通常、ソースツリー内の symlink をたどってリンク先の内容を保存します。一方、`-y`/`--symlinks` はリンク自体を保存します。権限の低いユーザーがバックアップ対象ディレクトリにリンクを追加できる場合は、使用される archiver とオプション、バックアップジョブの読み取り identity、生成されたアーカイブをそのユーザーが読めるかを確認してください。ソースディレクトリへの書き込み権限や symlink の存在だけでは、情報開示の証明になりません。バックアップを起動したり、列挙中に機密情報を展開したりせずに、リンクとアーカイブのメタデータを確認してください。[Info-ZIP のオプションドキュメント](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638)を参照してください。

GNU `tar` のデフォルト動作は異なります。通常、symlink はリンクとして保存されますが、[アーカイブ作成時に `-h` / `--dereference` を指定するとリンク先をたどります](https://www.gnu.org/software/tar/manual/html_node/dereference.html)。特権スケジュールバックアップについては、実際の `tar` 呼び出し、`tar` が入力パスを読み取る前に権限の低いユーザーがそのパスを置き換えられるか、生成されたアーカイブをそのユーザーが読めるかを確認してください。書き込み可能なステージングディレクトリにある一時チェックサムなどのサイドカーファイルも、後続の `tar -h` コマンドで明示的に指定されると、そのような入力になり得ます。競合が起きる時間枠、ジョブの identity、symlink のポリシー、その identity でのリンク先の読み取り可否、アーカイブの ACL をすべて検証する必要があります。受動的な確認中にファイルを置き換えたり、ジョブを実行したり、機密アーカイブを展開したりしないでください。

権限の低いユーザーが置き換え可能なアーカイブを特権ジョブが読み取る場合、アーカイブの**展開**は別の境界を越える可能性があります。[GNU tar は通常、superuser として実行されると、アーカイブ内の所有者情報を復元します](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html)。また、[権限復元オプション](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html)は、展開される mode bit に影響します。実際の extractor とフラグ、アーカイブの置き換え可能な時間枠、数値の所有者情報と mode メタデータ、展開先ディレクトリの権限、クリーンアップ後も結果を読み取れるかを確認してください。root 所有の SUID メンバーが問題となるのは、展開後もその mode が維持され、対象の mount とプロセスポリシーが identity の変更を許可する場合に限られます。信頼できないアーカイブや書き込み可能なステージングパスだけでは、これを証明できません。受動的な列挙中にアーカイブを置き換えたり展開したりせず、ジョブとメタデータを確認してください。

展開された symlink が、後続の特権比較処理を通じて保護対象ファイルを開示することもあります。[GNU `diff` は通常、ディレクトリを比較する際に symlink をたどります](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html)。そのため、信頼できない展開済みツリーに対して root で実行される `diff -r` は、リンク先を読み取り、差分の内容を出力に含める可能性があります。アーカイブを置き換えられること、リンク先が比較処理の実際にたどるパスにあること、ジョブがリンク先を読めること、比較結果やエラーログを権限の低いユーザーが読めることを確認してください。リンクやアーカイブだけでは情報開示の証明になりません。列挙中に比較処理を実行したり保護対象の内容を読んだりせず、ジョブ、パスメタデータ、ログの権限を確認してください。

ホスト側の転送が繰り返されると、信頼できないアーカイブメンバーが後続の出力パスになる可能性があります。より高い権限のジョブが信頼度の低いコンテナからアーカイブをコピーし、次回の転送先 basename と同じ名前の symlink を展開した後、同じパス名に書き込む場合、後続の書き込みがリンク先に到達する可能性があります。アーカイブメンバーの名前とリンク先、展開フラグとディレクトリ、extractor が実際にそのリンクを残すか、転送実装が既存の転送先 symlink をどう扱うか、ホストジョブの実効書き込み identity を確認してください。[GNU tar は、既存ファイルや symlink を展開時にどう扱うかを説明しています](https://www.gnu.org/software/tar/manual/html_section/extract-options.html)。[最近の OpenSSH では、scp はデフォルトで SFTP を使用します](https://man.openbsd.org/scp.1)。すべての `scp` バージョンが symlink を経由して書き込むと決めつけず、インストール済みの転送動作を確認してください。コンテナ内から見える `scp` プロセスや書き込み可能なアーカイブだけでは、ホスト側での展開や後続の書き込みを証明できません。列挙中に細工したアーカイブを転送または展開せず、ジョブとパスメタデータを確認してください。

Ansible の[`synchronize` module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html)は rsync をラップします。`copy_links: true` を指定すると、symlink ではなくリンク先がコピーされます。スケジュールバックアップについては、権限の低いユーザーが正確なソースツリー内にリンクを作成できるか、同期の identity がリンク先を読めるか、生成されたコピーやアーカイブをそのユーザーが読めるかを確認してください。playbook、リンクの配置、run-as identity、出力の権限がすべてそろう必要があります。アップロードディレクトリへの書き込み権限や `copy_links` の設定だけでは、調査の手掛かりにすぎません。リンクを作成したりジョブを起動したりせず、メタデータと playbook を確認してください。

## 開いているファイルディスクリプターを調べる

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

プロセスは、ファイルが削除または名前変更された後も、そのファイルへのアクセスを保持することがあります。特権プロセスがUnixソケット経由でファイルディスクリプターを渡す場合や、close-on-execが設定されていないために`execve()`後も意図せず開いたままにする場合もあります。`/proc/<PID>/fd`のリンク先を調べ、機密ファイル、削除済みファイル、コンテナ内から見えるホストパス、予期しないソケットがないか確認してください。他のプロセスのファイルディスクリプターをたどる際には、カーネルのアクセスチェックが適用されます。シンボリックリンクが見えていても、その内容を読み取れるとは限りません。

カスタムSUIDヘルパーは、保護されたパスを開いて実効UIDを落とした後も、ファイルディスクリプターを開いたままにすることがあります。その後、自身をダンプ可能にすると、`/proc/<PID>/fd`の所有権やアクセス権が変わる可能性があります。認証情報の変更手順、[`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html)、procfs/ptraceのポリシー、対象ファイルのモードを正確に確認してください。ファイルディスクリプターのパスを開き直すと、アクセスできない**親ディレクトリ**を迂回できる場合がありますが、呼び出し元に読み取り権限のないファイルは引き続き開けません。ファイルディスクリプターのリンク先が見えることや、SUIDビットがあることだけでは、情報開示の証明にはなりません。

クラッシュ生成物も別途調査する価値があります。コアダンプには、より高い権限で以前に読み込まれたデータを含むプロセスメモリが記録されることがあります。Ubuntuでは、[Apportは通常、レポートを`/var/crash`に保存します](https://documentation.ubuntu.com/project/contributors/debugging/apport/)。他のシステムでは、別の`core_pattern`ハンドラーやsystemdストレージが使われることがあります。通常の列挙では、レポートのパス、所有者、モード、読み取り可否だけを確認してください。読み取り可能なレポートが問題となるのは、対象プロセスがダンプ可能で、クラッシュハンドラーが機密データを保持し、現在のユーザーがそのレポートにアクセスできる場合に限られます。受動的な列挙の一環として、ヘルパーをクラッシュさせたり、ダンプを展開したりしないでください。SUIDとダンプ生成の条件については、[`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html)を参照してください。

サービスが継承したファイルディスクリプターを使う場合は、シェルのリダイレクトや`/proc/self/fd/<N>`を試す前に、起動チェーンとファイルディスクリプター番号を確認してください。ファイルが削除されても開いたままの場合、[削除済みファイルの復元](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds)によって証拠を保全したり、内容を復元したりできる可能性があります。プロセスレベルのトリアージを続けるには、[プロセスの列挙とサービスパス](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md)を参照してください。
