# シンボリックリンク、ハードリンク、ファイルディスクリプタ

{{#include ../../banners/hacktricks-training.md}}

パスは解決された時点でオブジェクトを指します。一方、オープン中のファイルディスクリプタは、パス名が変更された後もそのオブジェクトへの参照を保持します。この違いによって、シンボリックリンクの競合、隠れたハードリンク、削除済みファイルの復元、継承されたファイルディスクリプタのleakを説明できます。inodeとマウントの背景については、[ファイルシステム、inode、復元](filesystem-inodes-and-recovery.md)を参照してください。

## リンクとパスの所有権を調べる

```bash
namei -l /path/to/privileged/input
stat -c '%D %i %h %U:%G %a %n' /path/to/file
readlink -f /path/to/link
find /path/to/tree -type l -ls 2>/dev/null
find /path/to/tree -type f -links +1 -ls 2>/dev/null
```

シンボリックリンクはパス名の解決先を変更し、ハードリンクは同じファイルシステム上の同じ inode に対する別名です。特権タスクがユーザー書き込み可能なディレクトリ内の予測可能なパスを読み書きする場合、ユーザーがそのパスを機密性の高い対象へリダイレクトできる可能性があります。最終ファイルだけでなく、すべての親ディレクトリの所有者と権限を確認してください。`fs.protected_symlinks` と `fs.protected_hardlinks` は一般的なユーザー間攻撃を軽減しますが、任意の書き込み可能なパスを安全にするものではありません。

シェルの glob を使って権限を変更する特権ジョブについては、**コマンドライン引数**として展開されたリンクと、再帰的な走査中に見つかるリンクを区別してください。[GNU `chmod` は、コマンドラインで指定されたシンボリックリンクの参照先に対して動作します](https://www.gnu.org/software/coreutils/manual/html_node/chmod-invocation.html)。一方、再帰処理中に遭遇したシンボリックリンクは通常無視します。`-R` を付けただけでは、この2つのケースが同じになるわけではありません。実際のスケジュール実行ユーザーとコマンド、信頼できないユーザーが glob に一致するエントリを作成できるか、インストール済み `chmod` の動作とオプション、提案された対象に最終的にどのアクセス権が設定されるかを確認してください。書き込み可能なディレクトリやシンボリックリンクがあるだけでは、特権によるモード変更が起きるとは言えません。受動的な列挙では、リンクを配置したりジョブを実行したりせずに、スクリプトとパスのメタデータを確認してください。

特権スケジュールジョブの書き込み先は、ファイル名にランダムに見えるハッシュが含まれていても予測できる場合があります。[C の `rand()` は同じ `srand()` seed に対して同じ系列を繰り返します](https://man7.org/linux/man-pages/man3/rand.3.html)。既知の実行時刻から導出された seed も同様です。さらに、ジョブが名前の生成時に呼び出し元の書き込み可能なデータベース行を読み取る場合は、行から名前への正確なアルゴリズム、seed と libc の動作、スケジュール、呼び出し元が持つ行の書き込み権限とディレクトリ作成権限、特権プロセスがファイルを開く前に既存のシンボリックリンクを配置できるかを確認してください。[`fopen(..., "w")` は解決後のファイルを作成または切り詰めます](https://man7.org/linux/man-pages/man3/fopen.3.html)。リンク攻撃に安全な open フラグやアトミックな置換が使われているか、実際の実装、実効書き込みユーザー、対象の権限、スティッキーディレクトリのシンボリックリンクポリシーを確認してください。予測可能な名前や書き込み可能な行があるだけでは、調査の手掛かりにとどまります。受動的な列挙では、行を挿入したりジョブを実行したりせずに、コード、スケジュール、メタデータを確認してください。

別ユーザーとして動作するファイル変換サービスについては、呼び出し元が出力パスや拡張子を指定できるか、変換プログラムが既存の出力先シンボリックリンクをたどるかを確認してください。変換プログラムによっては、パス名の拡張子から出力形式を選択します。許可された拡張子を持つ名前のリンクであっても、拡張子のない機密性の高い対象を指している場合があります。ユーザー間の書き込みを成功させるには、サービスに到達できること、呼び出し元がパスとリンクを制御できること、変換プログラムがリンクを出力先として開くこと、サービス実行ユーザーに書き込み権限があることが必要です。Linux の `fs.protected_symlinks=1` は、**スティッキー属性が設定された全ユーザー書き込み可能ディレクトリ**内にある他ユーザーのリンクをたどる動作を制限します。通常のユーザー所有ディレクトリ内のリンクには、同じ保護は適用されません。結論を出す前に、解決後のパスと親ディレクトリの所有者を確認してください。[calibre の出力ファイルの動作](https://manual.calibre-ebook.com/generated/en/ebook-convert.html)および[Linux のシンボリックリンクポリシー](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/fs.html#protected-symlinks)を参照してください。

sudo で許可されたダウンロードラッパーが、呼び出し元が制御する作業ディレクトリを保持したまま、呼び出し元が選択したデータを取得する場合も、同様に出力パスを確認する必要があります。実際のダウンローダーと、選択されるベース名、名前の衝突処理、既存のシンボリックリンクによって特権書き込み先がリダイレクトされる可能性を確認してください。URL の選択やシンボリックリンクがあるだけでは不十分です。[Axel はユーザーごとの `~/.axelrc` を説明しています](https://github.com/axel-download-accelerator/axel/blob/master/doc/axel.txt)。また、[設定例には `default_filename` と `no_clobber` が含まれています](https://github.com/axel-download-accelerator/axel/blob/master/doc/axelrc.example)。そのため、Axel を使うラッパーは、このファイルから出力名の指定を引き継ぐ場合もあります。実効 `HOME` を確認してください。[sudo はポリシーに応じて `HOME` をリセットまたは保持できます](https://man7.org/linux/man-pages/man8/sudo.8.html)。ユーザーの `.axelrc` が関係するのは、特権ダウンローダーが実際にそのファイルを読み込む場合だけです。受動的な列挙では、ダウンロードを開始せずに、ルール、ラッパー、設定ファイルのパスと権限、最終的な出力名、対象ファイルの状態を確認してください。

sudo で許可された ACL ラッパーについては、`setfacl` の呼び出し前に、呼び出し元が選択したファイルをどのように検証するかを調べてください。字句的なプレフィックスチェックや `..` の拒否だけでは、許可ディレクトリ内のシンボリックリンクが外部を指すのを防げません。また、`test -f` もリンクをたどります。ラッパーが十分な権限で ACL 操作を実行できること、呼び出し元がリンクを制御できること、結果の ACL が対象ファイル**および親ディレクトリ**に必要なアクセス権を付与することを確認してください。ACL が書き込み可能なファイルや緩いモードのファイルを拒否する利用側もあるため、ACL の変更だけでは、実際に権限昇格につながる経路が成立するとは言えません。

## ユーザーがマウントした FUSE ファイルシステムへの特権書き込みを確認する

`/etc/fuse.conf` に有効な単独行 `user_allow_other` があると、root 以外のユーザーが FUSE マウントに `allow_other` または `allow_root` を指定できます。これらのマウントオプションにより、root プロセスがマウントしたユーザーによって実装されたファイルシステムにアクセスできる場合があります。sudo で許可されたヘルパーが、呼び出し元の制御する作業ディレクトリを基準に、秘密情報を含むログやその他の出力を書き込む場合、そのディレクトリがユーザーのマウントした FUSE ファイルシステムである可能性を確認してください。通常のファイルシステム上では root 所有やモード `0600` に見えるファイルであっても、FUSE の実装側は書き込みを監視できます。

```bash
grep -n '^[[:space:]]*user_allow_other[[:space:]]*$' /etc/fuse.conf 2>/dev/null
sudo -l
```

これは**候補**であり、情報漏えいの証明ではありません。実際の sudo/run-as identity と引数、helper の出力先と機密情報の内容、`/dev/fuse` へのアクセス、`allow_other` または `allow_root` を指定したマウントの成功、そして特権プロセスがマウント内に入れるかを確認してください。通常の列挙中に、特権 helper を実行したりファイルシステムをマウントしたりしないでください。[libfuse のポリシー説明](https://github.com/libfuse/libfuse/blob/master/util/fuse.conf)と[libfuse のアクセスに関する FAQ](https://github.com/libfuse/libfuse/wiki/FAQ#why-dont-other-users-have-access-to-the-mounted-filesystem)を参照してください。

## パスの競合を探す

危険なパターンは、特権プログラムがあるパス名を確認した後、安全な参照を保持せずに同じパス名を開くことです。親ディレクトリを制御できる攻撃者は、2つの操作の間にファイルや symlink を置き換えられます。同じ問題は、一時ファイル、タイマー駆動のスクリプト、アーカイブの展開、バックアップのワークフローでも発生します。影響を主張する前に、実際の読み書き操作と対象の権限を確認してください。

アーカイブの**作成**によって、異なる identity 間でファイルが漏えいすることもあります。Info-ZIP の `zip -r` は通常、ソースツリー内に置かれた symlink をたどり、リンク先の内容を保存します。`-y`/`--symlinks` を指定すると、代わりにリンク自体を保存します。バックアップ対象のディレクトリに下位権限のユーザーがリンクを追加できる場合は、実際の archiver とオプション、バックアップジョブの読み取り identity、生成されたアーカイブをそのユーザーが読めるかを確認してください。ソースディレクトリが書き込み可能、あるいは symlink があるだけでは、情報漏えいは立証されません。列挙中にバックアップを実行したり機密情報を展開したりせず、リンクとアーカイブのメタデータを確認してください。[Info-ZIP のオプションドキュメント](https://sources.debian.org/src/zip/3.0-3/man/zip.1/#L1638)を参照してください。

GNU `tar` のデフォルト動作は異なります。通常、symlink をリンクとして保存し、アーカイブ作成時にリンクをたどるのは[`-h` / `--dereference`](https://www.gnu.org/software/tar/manual/html_node/dereference.html)を指定した場合です。特権で実行される定期バックアップでは、正確な `tar` 呼び出し、`tar` が読み取る前に下位権限のユーザーが入力パス名を置き換えられるか、生成されたアーカイブをそのユーザーが読めるかを確認してください。書き込み可能なステージングディレクトリ内の一時チェックサムなどのサイドカーファイルは、後続の `tar -h` コマンドで明示的に指定されると、入力になり得ます。競合が起きる時間枠、ジョブの identity、symlink の扱い、その identity でのリンク先の読み取り可否、アーカイブの ACL をすべて検証する必要があります。受動的な確認中にファイルを置き換えたり、ジョブを実行したり、機密アーカイブを展開したりしないでください。

下位権限のユーザーが置き換えられるアーカイブを特権ジョブが読み取る場合、アーカイブの**展開**では別の境界を越えることになります。[GNU tar は、superuser として実行すると通常、アーカイブに記録された所有権を復元します](https://www.gnu.org/software/tar/manual/html_node/Option-Summary.html)。また、[権限復元オプション](https://www.gnu.org/software/tar/manual/html_node/Setting-Access-Permissions.html)は、展開されるファイルの mode bits に影響します。実際の extractor とフラグ、アーカイブを置き換えられる時間枠、数値で記録された owner と mode のメタデータ、展開先ディレクトリの権限、クリーンアップ後も展開結果にアクセスできるかを確認してください。root 所有の SUID ファイルが問題となるのは、展開後もその mode が保持され、対象のマウントとプロセスのポリシーで identity の変更が許可される場合に限られます。信頼できないアーカイブや書き込み可能なステージングパスがあるだけでは、これらは証明されません。受動的な列挙中にアーカイブを置き換えたり展開したりせず、ジョブとメタデータを確認してください。

展開された symlink は、後続の特権付き比較を通じて保護されたファイルを漏えいさせることもあります。[GNU `diff` は通常、ディレクトリ比較時に symlink をたどります](https://www.gnu.org/software/diffutils/manual/html_node/Special-Files.html)。そのため、信頼できない展開済みツリーに対する root 実行の `diff -r` は、リンク先を読み取り、異なる内容を出力に含める可能性があります。アーカイブを置き換えられるか、比較が実際に参照するパスにリンクが作られるか、ジョブがリンク先を読み取れるか、比較の出力やエラーログを下位権限のユーザーが読めるかを確認してください。リンクやアーカイブがあるだけでは、情報漏えいは立証されません。列挙中に比較を実行したり保護された内容を読んだりせず、ジョブ、パスのメタデータ、ログの権限を確認してください。

ホスト側で繰り返される転送によって、信頼できないアーカイブメンバーが後続の出力パスになることがあります。より高い権限のジョブが、信頼度の低いコンテナからアーカイブをコピーし、次回転送の宛先 basename と同じ名前の symlink を展開して、その後同じパス名に書き込む場合、後続の書き込みがリンク先に到達する可能性があります。アーカイブのメンバー名とリンク先、展開フラグとディレクトリ、展開後も extractor がそのリンクを残すか、既存の宛先リンクを転送処理がどう扱うか、ホストジョブの実効書き込み identity を確認してください。[GNU tar は、既存のファイルや symlink を展開時にどう扱うかを説明しています](https://www.gnu.org/software/tar/manual/html_section/extract-options.html)。[OpenSSH scp は最近のリリースではデフォルトで SFTP を使用します](https://man.openbsd.org/scp.1)。すべての `scp` バージョンがリンクをたどって書き込むと決めつけず、インストール済みの転送動作を確認してください。コンテナ内から見える `scp` プロセスや書き込み可能なアーカイブだけでは、ホスト側での展開と後続の書き込みは立証できません。列挙中に細工したアーカイブを転送・展開せず、ジョブとパスのメタデータを確認してください。

Ansible の[`synchronize` モジュール](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/synchronize_module.html)は rsync をラップします。`copy_links: true` は symlink ではなく、その参照先をコピーします。定期バックアップでは、下位権限のユーザーが対象のソースツリー内にリンクを作成できるか、同期を実行する identity がリンク先を読み取れるか、生成されたコピーやアーカイブをそのユーザーが読めるかを確認してください。playbook、リンクの配置、run-as identity、出力の権限がすべて揃う必要があります。書き込み可能なアップロードディレクトリや `copy_links` の設定があるだけでは、調査の手がかりにすぎません。リンクを作成したりジョブを実行したりせず、メタデータと playbook を確認してください。

## オープン中の file descriptor を調べる

```bash
ls -l /proc/<PID>/fd 2>/dev/null
lsof -p <PID> 2>/dev/null
lsof +L1 2>/dev/null
```

プロセスは、ファイルが削除または名前変更された後も、そのファイルへのアクセスを保持できる場合があります。特権プロセスは、Unix socket 経由で file descriptor を渡すことも、close-on-exec が設定されていない場合、意図せず `execve()` 後も descriptor を開いたままにすることがあります。`/proc/<PID>/fd` のリンク先を調べ、機密ファイル、削除済みファイル、コンテナ内から見えるホストパス、予期しない socket がないか確認してください。他のプロセスの descriptor を参照する際は、kernel のアクセスチェックが適用されます。symlink が見えていても、その内容を読み取れるとは限りません。

独自の SUID helper が保護されたパスを開き、effective UID を下げた後も descriptor を開いたままにする場合があります。その後、自身を dumpable にすると、`/proc/<PID>/fd` の所有者とアクセス可否が変わることがあります。credential の正確な遷移、[`PR_SET_DUMPABLE`](https://man7.org/linux/man-pages/man2/PR_SET_DUMPABLE.2const.html)、procfs/ptrace のポリシー、および対象ファイルの mode を確認してください。descriptor のパスを再度開くことで、アクセスできない**親ディレクトリ**を迂回できる場合がありますが、呼び出し元に読み取り権限のないファイルは引き続き開けません。descriptor のリンク先が見えることや SUID bit があることだけでは、情報漏えいの証拠にはなりません。

crash artifact も別の手掛かりになります。core dump には、より高い権限で以前に読み取られたデータを含め、プロセスのメモリが含まれることがあります。Ubuntu では、[Apport normally places reports in `/var/crash`](https://documentation.ubuntu.com/project/contributors/debugging/apport/)。その他のシステムでは、別の `core_pattern` handler や systemd storage が使われる場合があります。通常の列挙では、report のパス、所有者、mode、読み取り可否のみを確認してください。report が読めることに意味があるのは、該当プロセスが dumpable であり、crash handler が機密データを保持していて、現在のユーザーがその report にアクセスできる場合に限られます。受動的な列挙の一環として helper を crash させたり、dump を展開したりしないでください。SUID と dump 生成の条件については、[`core(5)`](https://man7.org/linux/man-pages/man5/core.5.html) を参照してください。

サービスが継承した descriptor を使用する場合は、shell redirection や `/proc/self/fd/<N>` を試す前に、起動チェーンと descriptor 番号を確認してください。ファイルが削除済みでも開かれたままなら、[deleted-file recovery](filesystem-inodes-and-recovery.md#deleted-file-recovery-through-open-fds) により証拠を保持したり、内容を復元したりできる場合があります。プロセスレベルのトリアージを続けるには、[process enumeration and service paths](../processes-crontab-systemd-dbus/process-enumeration-and-service-paths.md) を参照してください。
