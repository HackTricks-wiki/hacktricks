# Очищення маркера forwarded skb у Open vSwitch для запису ESP у кеш сторінок

{{#include ../../../banners/hacktricks-training.md}}

Корисний шаблон експлуатації ядра Linux — **очистити метадані власності skb, не видаляючи його чужі фрагменти**, а потім спрямувати цей skb до споживача, який виконує запис на місці. У випадку Open vSwitch (OVS) невдалий userspace upcall очищує `SKBFL_SHARED_FRAG` у все ще активному skb `MSG_ZEROCOPY`; згодом ESP розшифровує дані безпосередньо поверх folio кешу сторінок файла, доступного лише для читання. Це дає змогу детерміновано записувати в локальний кеш сторінок; проблему відстежували під номерами CVE-2026-90049, CVE-2026-89487 і CVE-2026-80977.<sup>[[1]](#references)[[2]](#references)</sup>

Це проблема класу Copy Fail/Dirty Frag, а не класичне пошкодження пам’яті: не потрібні ані race condition, ані розкриття адреси; файл має бути лише доступним для читання, а змінені байти з’являються в кеші сторінок, а не на диску.<sup>[[2]](#references)[[3]](#references)</sup>

## Інваріант безпеки: чужі фрагменти мають залишатися позначеними

`SKBFL_SHARED_FRAG` повідомляє споживачам, які записують на місці, що фрагмент skb може посилатися на сховище, яким вони не володіють приватно. Швидкий шлях ESP у `esp_input()` може розшифровувати нелінійний, неклонований skb на місці лише тоді, коли `skb_has_shared_frag()` повертає false; інакше `skb_cow_data()` спершу створює приватне сховище. Цю перевірку на стороні споживача додали після Dirty Frag.<sup>[[5]](#references)</sup>

Отже, інваріант має дві незалежні частини:<sup>[[2]](#references)[[4]](#references)[[5]](#references)</sup>

1. Записувачі на місці мають перевіряти `SKBFL_SHARED_FRAG` і копіювати спільні дані перед зміною.
2. Кожен шлях клонування, об’єднання, передавання або переспрямування має зберігати маркер, доки чужа сторінка залишається приєднаною.

Fragnesia порушила друге правило під час переміщення дескрипторів фрагментів у `skb_try_coalesce()`. Шлях OVS дещо відрізняється: він узагалі не передає фрагмент, а очищує маркер **безпосередньо в оригінальному skb і продовжує його переспрямування**.<sup>[[2]](#references)[[4]](#references)</sup>

## Доступність OVS без привілеїв

Ядерним datapath OVS керують через сімейства generic-netlink, зокрема `ovs_datapath`, `ovs_vport`, `ovs_flow` і `ovs_packet`. Для операцій, що змінюють стан, використовують `GENL_UNS_ADMIN_PERM` з урахуванням просторів імен, тож процес, запущений через `unshare -Urn`, отримує `CAP_NET_ADMIN`, необхідний для створення datapath, під’єднання veth і встановлення дій flow у власному мережевому просторі імен. Під час визначення сімейства OVS також може автоматично завантажитися `openvswitch.ko`; для цієї поверхні атаки не потрібні `CAP_SYS_MODULE` на хості, `ovs-vsctl` чи `ovs-vswitchd`.<sup>[[2]](#references)[[7]](#references)</sup>

Важливо розрізняти два типи upcall:<sup>[[2]](#references)[[7]](#references)</sup>

- **Промах flow** надсилає пакет до `ovs-vswitchd`; якщо upcall завершується невдало, пакет зазвичай відкидається.
- Явна дія `OVS_ACTION_ATTR_USERSPACE` надсилає позичену копію до вибраного ID порту, а потім виконує наступні дії над оригінальним skb.

Тому зловмисник може встановити flow такого вигляду:<sup>[[1]](#references)[[2]](#references)</sup>

```text
in_port(1),ipv4 -> USERSPACE(pid=<unbound-portid>), OUTPUT(0)
```

Жоден listener не володіє вибраним ID порту, тож дія userspace очікувано завершується помилкою, а наступна дія `OUTPUT` залишає початковий пакет живим.<sup>[[1]](#references)[[2]](#references)</sup>

## Першопричина: `skb_tx_error()` для пакета, який залишається живим

У вразливому шляху обробки помилок upcall в OVS викликається `skb_tx_error(skb)`. Цей helper призначений для невдалої передачі, після якої skb звільняється; він завершує облік zerocopy через `skb_zcopy_clear()`, маска прапорців якого історично також видаляла `SKBFL_SHARED_FRAG`. OVS ігнорував помилку дії userspace і продовжував виконання списку дій, порушуючи контракт часу життя helper-функції.<sup>[[1]](#references)[[2]](#references)</sup>

Вразливий перехід стану:<sup>[[2]](#references)</sup>

```text
before failed upcall: flags=0xb, nr_frags=1, page-cache folio attached
skb_tx_error():       zerocopy flags, including SHARED_FRAG, are cleared
after failed upcall:  flags=0x0, nr_frags=1, same folio still attached
OUTPUT:               unmarked skb continues to local ESP input
```

Це працює лише тоді, коли `skb_zcopy()` знаходить стан zerocopy. Фрагмента, що містить лише `SKBFL_SHARED_FRAG`, недостатньо; `MSG_ZEROCOPY` корисний, оскільки створює `SKBFL_ZEROCOPY_ENABLE | SKBFL_SHARED_FRAG` і також встановлює `SKBFL_DONT_ORPHAN`. Останній прапорець змушує `skb_orphan_frags()` пропускати заміну чужих сторінок під час копіювання OVS у userspace.<sup>[[2]](#references)[[3]](#references)</sup>

## Побудова примітиву запису

Наскрізний тригер має такі компоненти.<sup>[[2]](#references)[[3]](#references)</sup>

1. Увійдіть у приватні user і network namespaces за допомогою `unshare -Urn`.
2. Зіставте файл-ціль для читання за допомогою `PROT_READ | MAP_SHARED`.
3. Використовуйте окремий sender netns і пару veth; локальний loopback копіював би запозичені сторінки й руйнував примітив.
4. Створіть datapath OVS і потік, що спричиняє збій, із послідовністю `USERSPACE`-потім-`OUTPUT`.
5. Встановіть стан XFRM у режимі transport-mode ESP-in-UDP, використовуючи `rfc4106(gcm(aes))` і UDP-порт 4500.
6. Надішліть одну дейтаграму `MSG_ZEROCOPY` з iovec такої структури: `[ESP header | mapped file bytes | invalid ICV]`.

Для стану XFRM використовується 20 байтів ключового матеріалу AES-128-GCM: 16 байтів ключа AES, за якими йде чотирибайтовий salt RFC 4106. Для вибраного восьмибайтового явного IV конфіденційність корисного навантаження починається з блока лічильника `salt || IV || be32(2)`; натомість значення лічильника 1 маскує результат автентифікації.<sup>[[2]](#references)[[6]](#references)</sup>

```bash
ip xfrm state add src 10.99.99.1 dst 10.99.99.2 proto esp \
  spi 0x42434445 mode transport \
  aead 'rfc4106(gcm(aes))' \
  0x000102030405060708090a0b0c0d0e0f11223344 128 \
  encap espinudp 4500 4500 0.0.0.0
```

Після того як OVS видаляє marker, ESP переходить шляхом без копіювання та виконує `plaintext = ciphertext XOR keystream` над фрагментом, що спирається на файл. Автентифікація перевіряється **після** цього перетворення, тож пакет із недійсним ICV, що складається лише з нулів, завершується помилкою `-EBADMSG` лише після того, як байти page cache уже змінилися.<sup>[[2]](#references)</sup>

### Перетворення GCM на вибрані байти

Для поточного байта `C` і бажаного байта `P` перший байт потоку ключа payload має бути `C XOR P`. Коли AES key і salt зафіксовані, переберіть 16-бітний суфікс явного IV і заздалегідь обчисліть по одному суфіксу для кожного можливого першого байта потоку ключа:<sup>[[2]](#references)[[3]](#references)[[6]](#references)</sup>

```text
for n in 0..0xffff:
    iv = 0xcccccccc || 0x0000 || be16(n)
    k0 = AES_K(salt || iv || be32(2))[0]
    first_suffix_for[k0] ??= n
```

Публічна реалізація обмежує шифротекст 32 байтами та зсуває фрагмент файла на один байт для кожного пакета. Вибраний перший байт перезаписує перший побічний байт попереднього пакета; `pread()` оновлює `C` перед кожним пакетом, однакові байти пропускаються, а останній пакет скорочується, щоб запис не виходив за межі запитаного діапазону. Таким чином таблиця пошуку на 256 елементів перетворює цей примітив на запис у page cache із точністю до байта та заданим вмістом — приблизно один пакет на кожен байт, що відрізняється.<sup>[[2]](#references)[[3]](#references)</sup>

## Запис у page cache для отримання root

Практична ціль — наявний виконуваний файл із setuid-root. PoC замінює перші 160 байтів повним статичним ELF-файлом з одним `PT_LOAD` із фіксованою адресою та правами читання/виконання, без `PT_INTERP` і з кодом, який викликає `setuid(0)` перед `execve("/bin/sh", ...)`. Це дає змогу не покладатися на адресу точки входу оригінального бінарного файла, компонування PIE, динамічний завантажувач чи релокації.<sup>[[2]](#references)[[3]](#references)</sup>

Модифікація видима в усіх просторах імен користувачів, оскільки page cache не ізольований за просторами імен. Змінене фоліо не позначається як брудне, тож зміни не записуються назад на диск; виконайте ціль, поки вона перебуває в кеші, а потім відкиньте тимчасове пошкодження за допомогою `posix_fadvise(..., POSIX_FADV_DONTNEED)`, щоб під час подальших читань завантажувався оригінальний вміст із диска.<sup>[[2]](#references)[[3]](#references)</sup>

## Перевірка вразливості та усунення

Спершу перевірте фактичне ядро постачальника. Важливі умови вразливості: непривілейовані простори імен користувачів, доступність або наявність OVS у системі та доступна реалізація ESP.<sup>[[1]](#references)[[2]](#references)</sup>

```bash
unshare -Urn true 2>/dev/null && echo 'user+net namespaces available'
sysctl user.max_user_namespaces kernel.unprivileged_userns_clone \
  kernel.apparmor_restrict_unprivileged_userns 2>/dev/null
lsmod | grep openvswitch
modprobe -n -v openvswitch esp4 esp6 2>/dev/null
modinfo esp4 esp6 2>/dev/null | grep -E '^(name|alias):'
```

Оновіть ядро до версії з повним набором виправлень: остаточне виправлення охоплює шлях повторної циркуляції та не змінює спільний стан `skb_shinfo()`, а також усуває пов’язане очищення в `skb_zerocopy()`.<sup>[[1]](#references)[[2]](#references)</sup>

Якщо OVS не використовується, забороніть завантаження і за псевдонімом, і за назвою за допомогою правила `install` для modprobe, а не покладайтеся лише на `blacklist`. Якщо хост не завершує IPsec, а ESP завантажується як модуль, той самий засіб контролю дасть змогу прибрати й точку приймання розшифрованих даних.<sup>[[2]](#references)</sup>

```conf
# /etc/modprobe.d/disable-unused-network-surfaces.conf
install openvswitch /bin/false
install esp4 /bin/false
install esp6 /bin/false
```

Ці правила не допомагають, якщо модуль уже завантажено або функцію вбудовано в ядро. Вимкнення непривілейованих просторів імен користувачів також усуває джерело можливостей просторів імен, але може порушити роботу браузерів, Flatpak, Podman та інших ізольованих середовищ/контейнерних навантажень.<sup>[[2]](#references)</sup>

## Уроки аудиту

Під час аудиту zero-copy networking не обмежуйте пошук допоміжними функціями, які копіюють або переміщують фрагменти. Також визначайте функції обробки помилок/завершення, які очищають згруповані прапорці, а потім перевіряйте, чи кожен викликач дотримується задокументованого контракту життєвого циклу skb. Біт володіння сторінкою, згрупований із бітами життєвого циклу zerocopy, має значення для безпеки, навіть якщо код очищення безпосередньо не звертається до жодного фрагмента.<sup>[[1]](#references)[[2]](#references)</sup>

Надійне виправлення має охоплювати всі шляхи, якими skb може зберегтися, зокрема продовження дії та повторну циркуляцію, а також враховувати клони, що спільно використовують `skb_shinfo()`. На боці споживача помилка автентифікації не скасовує запис plaintext, який уже виконало AEAD-перетворення на місці, тому перевірки стороннього сховища потрібно виконувати до початку дешифрування.<sup>[[1]](#references)[[2]](#references)</sup>
