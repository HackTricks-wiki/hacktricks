## Interpretadores permitidos pelo sudo

Se `sudo -l` permitir que um usuário execute um interpretador como root, trate isso como execução direta de código. Os interpretadores foram projetados para executar código arbitrário; portanto, uma regra que permita `python3`, `perl`, `ruby`, `lua`, `node` ou binários semelhantes geralmente equivale à execução de comandos como root, a menos que os argumentos sejam rigorosamente restringidos e validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Fluxo de análise comum: primeiro, liste os privilégios do usuário; depois, execute uma instrução Python com a opção `-c` do interpretador.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Outros exemplos de interpretadores são mostrados abaixo; os interpretadores listados documentam a execução de código inline ou APIs de processos-filho.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

O caminho exato importa. Se a regra do sudo permitir `/usr/bin/python3`, use esse caminho exato durante a validação.<sup>[[2]](#references)</sup>

Um glob de executáveis do sudo, como `/usr/bin/python*`, também pode permitir Python 2 para um script escrito para Python 3. Se o script chegar a `input()` com texto controlado pelo chamador, [Python 2 avalia esse texto como uma expressão](https://docs.python.org/2/library/functions.html#input); uma invocação explícita do interpretador substitui o shebang do script. Verifique os binários correspondentes instalados, a política efetiva de RunAs e de argumentos, as negações e se a entrada pode ser alcançada antes de considerar isso um caminho de execução.

Um caminho de script fixo em uma regra do sudo com capacidade de execução como root não restringe o que o script executa. Para um wrapper Bash legível, verifique se o primeiro comando executável usa um parâmetro posicional sem aspas, como `$1`, como **palavra de comando**, enquanto o sudo permite que o chamador escolha os argumentos. Confirme a identidade efetiva de RunAs, a política de senha e de argumentos, as negações posteriores e o ramo real do script; `NOEXEC`, uma lista fixa de argumentos seguros ou um wrapper que valida o comando podem alterar o resultado. Durante a enumeração, inspecione estaticamente o script curto em vez de invocá-lo com um comando de teste.

Uma regra irrestrita do sudo para `dotnet` com capacidade de execução como root também merece uma análise do interpretador. Com um .NET SDK instalado, [`dotnet fsi` executa código F# interativamente ou a partir de um script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), e [`dotnet run` executa um projeto a partir do código-fonte](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Primeiro, confirme a identidade efetiva de RunAs e a política exata de argumentos: uma regra limitada a um subcomando seguro específico ou a um aplicativo confiável é uma concessão diferente, e uma instalação apenas do runtime pode não incluir os comandos do SDK. O nome do executável é apenas um indício para análise, não uma prova de execução de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editores permitidos pelo sudo

Se `sudo -l` permitir que um usuário execute um editor interativo como root, trate isso como uma superfície de execução de comandos, não como uma permissão inofensiva para editar arquivos. Os editores geralmente podem executar comandos do shell, ler arquivos arbitrários, gravar arquivos arbitrários ou invocar helpers externos de dentro do editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Fluxo comum de análise: liste os privilégios do usuário e, em seguida, invoque cada editor ou pager permitido usando sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Execução de comandos do Nano

Quando `nano` é permitido via sudo, a execução de comandos pode ser acessada pela interface do editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Em seguida, forneça um comando como `id` ou `/bin/sh` no prompt de comando do nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se um shell interativo não tiver fluxos de terminal utilizáveis, esta forma de redirecionamento mapeia a saída padrão e o erro para o descritor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

A sequência exata de teclas pode variar conforme a versão do nano e as opções de compilação, mas o problema de segurança é o mesmo: o editor está sendo executado como root e pode invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Outras formas comuns de escapar de editores

Editores no estilo Vim geralmente permitem executar comandos por meio de `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Paginadores como `less` também podem permitir a execução de comandos no shell.<sup>[[14]](#references)</sup>

Uma regra do sudo que permite executar `apport-cli` como root merece a mesma análise do paginador. Versões afetadas do Apport podiam abrir um relatório de falha no `less` com um tamanho de terminal ajustável pelo atacante; nessas condições, o paginador podia fornecer um shell root se os requisitos especiais do sudo e do paginador fossem atendidos. Verifique a regra efetiva do sudo, a configuração do paginador e a correção do pacote da distribuição antes de considerar a versão vulnerável por si só. Durante a enumeração passiva, consulte os metadados do pacote e da política sem gerar uma falha nem abrir o relatório privilegiado. [O registro CVE do Ubuntu](https://ubuntu.com/security/CVE-2023-1326) lista as versões corrigidas dos pacotes específicas de cada versão, incluindo correções retroportadas.

```text
!/bin/sh
```

## Outros riscos em regras sudo e doas

Comece com `sudo -l`, `sudo -V` e qualquer política `doas` aplicável. Leia em conjunto o comando permitido, o usuário de execução, os argumentos, o ambiente e os padrões. A permissão para executar como uma conta de serviço que não seja root ainda pode expor os arquivos dessa conta ou uma rota para root.

Um script Python fixo permitido pelo sudo ainda pode executar um comando de shell sob a identidade RunAs se a entrada interativa controlada pelo chamador for concatenada em [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Uma denylist de pontuação de shell não basta para garantir segurança: o [shell também reconhece a substituição de comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirme que os argumentos permitidos chegam ao ramo de entrada, que a entrada chega ao comando de shell sem validação segura e que a política sudo efetiva permite o usuário RunAs pretendido. O caminho do script ou uma chamada a `os.system()` são apenas indícios para análise; inspecione o código-fonte sem executar o script privilegiado.

Uma concessão sudo efetiva para root em `chattr` pode remover o atributo imutável (`i`) de um arquivo, mas isso, por si só, não concede permissão de escrita nem uma nova identidade. [O manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) informa que o atributo bloqueia modificações e que somente root ou um processo com `CAP_LINUX_IMMUTABLE` pode alterá-lo. Verifique a política exata de argumentos do sudo e o suporte do sistema de arquivos; depois, confirme separadamente que o chamador pode escrever no arquivo após a remoção do atributo e que um consumidor de identidade superior o utiliza. A substituição de um shell de login, por exemplo, também exige credenciais aceitas pela conta-alvo e um login efetivo por meio desse shell. Analise a política, os atributos dos arquivos e as permissões sem alterá-los durante a enumeração.

Se o sudo solicitar uma senha e um código de uso único, trate esses requisitos separadamente da concessão do comando. Um arquivo `.google_authenticator` legível contém material de seed sensível, enquanto um hash antigo de senha de aplicativo ou banco de dados é apenas uma possível senha atual da conta; nenhum deles comprova que o outro fator é aceito pela configuração PAM efetiva. Após obter autorização, analise o RunAs e os argumentos exatos: uma concessão irrestrita para root de `gem` do RubyGems pode expor seu comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mas uma concessão restrita ou uma autenticação malsucedida não. A enumeração passiva deve informar caminhos e políticas sem imprimir o seed, recuperar uma senha, gerar um código ou invocar o comando privilegiado.

Uma concessão sudo irrestrita com capacidade de root para `knife` do Chef merece análise no nível do interpretador: [o Chef documenta que `knife exec -E` avalia localmente uma string Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifique se a regra sudo efetiva permite o subcomando `exec` e o argumento `-E` fornecido pelo chamador, a identidade RunAs pretendida e quaisquer negações de comando ou argumentos fixos correspondentes. O binário instalado ou uma regra restrita a outros subcomandos é apenas um indício. A enumeração passiva deve informar a regra sem invocar `knife`.

Uma concessão sudo exata com capacidade de root para um `msfconsole` interativo também é sensível: [GTFOBins documenta seu console `irb`](https://gtfobins.org/gtfobins/msfconsole/), que pode herdar a identidade do sudo. Confirme o usuário RunAs efetivo, a lista de argumentos permitidos, as negações de comando, `NOEXEC` ou outras restrições, o comportamento do console instalado e se o chamador pode fornecer entrada interativa. Um destaque de caminho, por si só, é apenas um indício para análise; a enumeração passiva não deve iniciar o console.

No FreeBSD, até mesmo uma regra sudo limitada a `pkg update` e `pkg install *` como root merece uma análise da confiança nos repositórios. Verifique se `/etc/hosts` pode ser escrito pelo chamador e se a configuração efetiva dos repositórios habilitados usa um hostname HTTP com `signature_type: none`. [O manual de `pkg.conf` do FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) informa que `none` desabilita as verificações de assinatura; `pkg+http`, por si só, não comprova isso. [Um pacote pode conter scripts de instalação](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), portanto, um chamador que realmente controle o endpoint do repositório e possa selecionar um pacote pode cruzar a fronteira de root. Verifique substituições de repositório, resolução de SRV/espelhos, argumentos sudo efetivos, seleção do pacote e execução dos scripts antes de chegar a essa conclusão. Inspecione a política e os pequenos arquivos de configuração locais sem redirecionar nomes nem executar `pkg` durante a enumeração.

Uma regra sudo com capacidade de root para `apt-get update` e `apt-get upgrade` também exige análise da confiança nos repositórios quando o sudo preserva um `http_proxy` controlado pelo chamador. Verifique se a configuração APT efetiva realmente usa essa variável e quais solicitações aos repositórios habilitados ela pode afetar; um proxy, por si só, não pode substituir pacotes de um arquivo autenticado por uma chave de assinatura confiável. [O manual do transporte HTTP do APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta a precedência dos proxies, e [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta verificações de assinatura, substituições para repositórios inseguros e confirmações para pacotes não autenticados. Confirme o RunAs e os argumentos exatos do sudo, a política de autenticação do repositório, qualquer confirmação interativa exigida e se a atualização selecionada executa scripts de pacote como root. Inspecione a política e a configuração local passivamente; não redirecione o tráfego de pacotes nem execute uma atualização durante a enumeração.

Uma regra sudo com capacidade de root para `snap install` pode criar uma fronteira entre pacote e código se os argumentos permitirem ao chamador selecionar um snap local e um modo de instalação permissivo. [A documentação do Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) informa que `--dangerous` ignora as verificações de assertion de snaps locais e que `--devmode` relaxa o confinement; [um hook de instalação pode ser executado na instalação inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Verifique a política exata de argumentos/RunAs do sudo, quem controla o arquivo snap, se esses modos são aceitos pelo snapd instalado e a identidade efetiva e o confinement do hook antes de alegar acesso a arquivos protegidos do host. Um binário `snap` ou uma regra aparentemente com curinga não comprova essa cadeia. A enumeração passiva não deve instalar um pacote nem executar seu hook.

Para uma concessão sudo exata a um binário personalizado que lê credenciais e executa como uma conta **não root**, primeiro inspecione o binário concedido e suas permissões sem executá-lo. Uma verificação de senha embutida pode ser visível apenas como caracteres wide; [a documentação do GNU `strings` descreve a extração little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Uma string visível não prova que essa seja a senha aceita nem que o ramo de sucesso exponha uma credencial atual. Confirme separadamente o comportamento do binário, o acesso da conta-alvo aos dados protegidos, a validade da credencial e qualquer transição posterior de conta ou grupo. Se essa conta pertencer ao grupo `docker`, verifique o acesso ao socket e a identidade rootful ou rootless do daemon antes de inferir acesso a root no host; [a documentação do Docker explica as implicações de nível root do grupo](https://docs.docker.com/engine/install/linux-postinstall/). A enumeração rotineira deve informar a regra sudo e a associação ao grupo sem executar o binário nem despejar suas strings.

Uma regra sudo com curinga para scripts de manutenção de um aplicativo exige análise além do caminho do script. Verifique se o script permitido aceita argumentos irrestritos ou lê configurações que uma conta de aplicativo com menos privilégios pode gravar; depois, rastreie esses valores até comandos de shell ou o ambiente de um subprocesso. Por exemplo, o [`zmupdate.pl` do ZoneMinder monta um comando `mysqldump` e o executa por meio de `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), enquanto o [`zmdc.pl` copia a configuração `ZM_LD_PRELOAD` para `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Uma regra sudo que permita qualquer um dos scripts como root pode cruzar uma fronteira de confiança se a entrada correspondente for controlável e chegar a esse código na versão instalada. Inspecione a regra sudo efetiva, as permissões da configuração do aplicativo e o código-fonte do script; o curinga ou a configuração, por si só, são indícios para análise, não prova de execução.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` podem transformar um comando aparentemente restrito em um hijack de importação, biblioteca ou PATH. Consulte o [guia de variáveis de ambiente](../linux-basics/linux-environment-variables.md) e [abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Uma concessão `SETENV` exata, com capacidade de root, para um wrapper de shell também merece uma análise de um salto se o wrapper iniciar um script Python fixo com uma importação literal. `secure_path` restringe a busca de comandos do shell, não a [busca de módulos `PYTHONPATH` do Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fazem o Python ignorar essa variável de ambiente. Confirme as tags e negações sudo efetivas, o ramo do wrapper, as opções do interpretador, a resolução da importação e a existência de um diretório de busca gravável pelo chamador antes de considerar isso execução de código. Inspecione scripts curtos estaticamente; não invoque o wrapper privilegiado.

Uma concessão sudo exata para root de `neofetch ""` ainda pode carregar uma configuração de shell quando os padrões sudo aplicáveis preservam `XDG_CONFIG_HOME` controlado pelo chamador. [O carregador de configuração do Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carrega `neofetch/config.conf` ou `neofetch/config` abaixo desse diretório; a lista de argumentos vazia não impede essa busca. Confirme o carregador instalado, a política efetiva de RunAs e argumentos, quaisquer negações de comando, se o sudo realmente preserva a variável selecionada para esse comando e se o chamador controla um caminho de configuração legível. Uma variável preservada ou o Neofetch instalado são apenas indícios para análise. Inspecione a política e os metadados dos arquivos sem invocar o comando privilegiado nem imprimir o conteúdo da configuração; consulte [o tratamento do ambiente pelo sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Uma regra sudo irrestrita com capacidade de root para `facter` merece uma análise separada de custom facts. [A documentação do Puppet](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) informa que `--custom-dir` carrega arquivos Ruby de facts de um diretório selecionado. Verifique se a regra sudo exata permite essa opção, se o Facter instalado a aceita e se o chamador controla o diretório. Uma concessão com argumentos fixos, uma negação explícita do comando ou custom facts desabilitados podem alterar o resultado. A enumeração passiva deve informar o possível caso de política sem invocar Facter nem ler o conteúdo dos facts.

Para uma concessão sudo exata de um script com capacidade de root e `SETENV`, analise nomes de comandos sem caminho absoluto, como `find`, e o `PATH` efetivo após a política sudo e a inicialização do script. Um arquivo Bash carregado por `source` também pode executar `enable -n [`: [o Bash então pesquisa o `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) em busca de um `[` externo quando o script usa esse comando posteriormente. Confirme as regras aplicáveis de [ambiente sudoers e `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), eventuais entradas `NOSETENV`/`NOEXEC` ou negações, o fluxo do script e dos arquivos carregados e a existência de um diretório de busca executável controlado pelo chamador. Um script legível que contenha um comando sem caminho absoluto é apenas um indício para análise, não prova de execução privilegiada; inspecione-o sem invocar a regra sudo.

- Um script privilegiado que busca uma URL fixa com `curl` ainda pode aceitar uma resposta escolhida pelo chamador se uma regra sudo aplicável preservar `http_proxy` e a solicitação passar por esse proxy. Se o script passar a resposta a um parser XML que resolve entidades externas, uma resposta maliciosa pode revelar arquivos legíveis pelo processo privilegiado. Verifique a política exata de ambiente do sudo, as exclusões `no_proxy`, a URL solicitada, a configuração do parser e o destino da saída; uma variável de proxy ou um parser XML, por si só, não constitui vulnerabilidade. A [documentação das variáveis de ambiente de proxy do curl](https://everything.curl.dev/usingcurl/proxies/env.html) descreve o comportamento dessas variáveis. Não faça solicitações de rede nem analise XML malicioso durante a enumeração passiva.
- Um script sudo com capacidade de root que monta um arquivo PostScript com dados influenciados pelo chamador e depois executa `ps2pdf -dNOSAFER` merece uma análise separada do fluxo de entrada. O Ghostscript documenta que essa flag desabilita o SAFER até `.setsafe`, permitindo operações de arquivo PostScript dentro das permissões do sistema operacional do processo. Uma consulta SQL montada a partir de um argumento do chamador pode fornecer linhas controladas por um atacante ao modelo PostScript, mas uma string de consulta ou invocação de `ps2pdf`, por si só, não prova que os dados cheguem à sintaxe PostScript executável. Confirme a regra sudo efetiva, o caminho exato da entrada ao modelo, qualquer escaping, o comportamento do Ghostscript instalado e se o SAFER é reabilitado antes de o documento ser interpretado. Não invoque a conversão privilegiada durante a enumeração passiva. Consulte a [documentação do `-dNOSAFER` do Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para uma regra sudo que executa um script de shell, compare as variáveis preservadas com o próprio script. Uma construção como `if $CHECK_CONTENT; then` executa o valor expandido como comando; portanto, preservar `CHECK_CONTENT` pode permitir execução de comandos mesmo quando o caminho e os argumentos do script são fixos. É preciso verificar, para a regra específica, se o ramo pode ser alcançado e se o ambiente é realmente preservado.<sup>[[2]](#references)[[22]](#references)</sup>
- Um script Python permitido pelo sudo pode importar código de um diretório gravável ou de um arquivo `.pyc` em cache. O [guia de escalonamento de privilégios](../linux-basics/linux-privilege-escalation/README.md) detalha o caso do cache.
- Um script Python fixo permitido pelo sudo para execução como root ainda pode expor um debugger interativo. Chamadas como `pdb.set_trace()` ou `pdb.post_mortem()` permitem instruções Python no contexto do processo depurado quando o chamador consegue alcançar o breakpoint ou o handler de exceção **e controlar o fluxo de entrada do debugger**. Verifique a regra exata de RunAs do sudo, a autenticação e as condições do ramo, a possibilidade de alcançar a exceção, o controle do terminal/entrada e se o debugger é executado nesse mesmo processo privilegiado. Uma solicitação de socket que provoque uma exceção não concede, por si só, acesso a um debugger conectado a outro terminal. [A documentação do Python descreve a avaliação de instruções pelo debugger e o modo post-mortem](https://docs.python.org/3/library/pdb.html); inspecione o script estaticamente em vez de acionar o handler privilegiado durante a enumeração.
- Um script Python fixo permitido pelo sudo também pode ler um campo de perfil de um banco de dados ou socket Unix e acrescentá-lo a uma string que depois se torna a **string de formato** de `str.format()`. [Campos de substituição podem acessar atributos e chaves de mapeamento](https://docs.python.org/3/library/string.html#format-string-syntax), portanto, um campo controlado por um atacante pode inspecionar objetos passados a `format()` e expor dados acessíveis por meio deles se o resultado for impresso ou armazenado em um local legível pelo chamador. Verifique a identidade efetiva de RunAs do sudo, o acesso de escrita ao registro específico, o fluxo dos dados até a string de formato, quais objetos são fornecidos e a visibilidade da saída. Isso não é execução automática de código, e uma string de formato literal e confiável com *valores* controlados por um atacante é um caso diferente. Um segredo revelado só permite uma transição para uma conta do sistema operacional se essa conta o aceitar. Analise o script e as permissões do socket sem invocar a operação privilegiada.
- Um wrapper Python com capacidade de root pode passar uma URL escolhida pelo chamador para `Repo.clone_from` do GitPython. Se o wrapper também habilitar `protocol.ext.allow=always` do Git, um remoto `ext::` pode invocar um helper externo. Verifique os argumentos exatos do sudo, a origem da URL, a versão do pacote GitPython e o status de patches do fornecedor, e se o wrapper opta explicitamente por protocolos inseguros. O GitPython adicionou uma [proteção padrão contra protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) na versão 3.1.30; a versão do executável `git` é um dado separado. A análise passiva deve ler apenas a regra e uma parte limitada do código-fonte, sem invocar o clone.
- Uma concessão sudo entre usuários para uma CLI que clona repositórios pode expor um caminho separado de injeção em string de shell. Rastreie se o argumento do repositório escolhido pelo chamador chega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) do Node.js ou a outro construtor de comandos de shell sem separação segura de argumentos; o `exec` do Node passa sua string de comando a um shell. Confirme o usuário RunAs exato, os subcomandos e argumentos permitidos, o código do wrapper instalado e a validação da entrada. O nome de uma ferramenta de repositório ou uma regra sudo irrestrita, por si só, não comprova injeção de comandos. Inspecione o wrapper sem invocar um clone privilegiado durante a enumeração.
- Um wrapper personalizado pertencente a root pode parecer seguro porque seus binários e scripts não são graváveis, mas a decisão de executar uma ação privilegiada pode depender de uma flag, valor de API local ou estado de serviço que um usuário sem privilégios pode alterar. Rastreie cada condição até sua entrada e suas verificações de autorização. Durante a enumeração, inspecione a configuração e as permissões sem alterar o estado operacional; uma chamada `systemd-run` dentro do wrapper só é relevante se a condição puder ser influenciada.
- Um cliente de backup permitido pelo sudo como root pode aceitar um arquivo de configuração escolhido pelo chamador (por exemplo, `npbackup-cli -c`). Verifique o usuário de execução e os argumentos permitidos exatos, depois confirme se o chamador controla o caminho da configuração, os caminhos de origem do backup e as opções de repositório ou leitura/restauração. Um segredo de repositório criptografado em uma configuração legível ainda pode ser utilizável pelo cliente, mas a regra, por si só, não comprova acesso ao repositório nem divulgação de arquivos root. Valide a autorização sem executar um backup nem despejar seu conteúdo.
- O [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) oferece suporte a `--password-command`, que chama um programa para obter a senha de um repositório. Se uma regra sudo permitir que um usuário com menos privilégios execute o Restic como root com um comando de senha escolhido pelo chamador e um subcomando que precise da senha, esse helper poderá ser executado como root. Analise os argumentos e as exclusões exatos do sudo; não invoque o helper nem um comando de backup apenas para enumerar essa condição.
- Uma concessão privilegiada de `restic backup` também pode cruzar uma fronteira de leitura de arquivos se o padrão de argumentos do sudo permitir ao chamador escolher tanto a origem quanto um repositório que ele possa ler e descriptografar depois. [Curingas de argumentos do sudoers podem corresponder a espaços em branco e barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), portanto, inspecione curingas finais em vez de presumir que um prefixo fixo de repositório confina a origem. [O Restic pode fazer backup para repositórios locais e remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mas um repositório local pode conter objetos recém-gravados que só root pode ler; confirme a política sudo efetiva, o acesso ao backend, a senha do repositório e as permissões dos objetos resultantes antes de considerar isso uma divulgação. Uma chave SSH incluída no backup só concede acesso se a conta de destino a aceitar. Não execute um backup para testar isso durante uma análise passiva.
- Um comando personalizado irrestrito de manutenção ou backup pode aceitar um caminho de saída ou oferecer seu próprio agendador de tarefas. Para um caminho de escrita de arquivo, verifique a regra sudo exata e o usuário de execução; depois, confirme se o chamador controla tanto os dados quanto o destino. Para um caminho de comando agendado, verifique a identidade de execução do agendador, a entrada do comando e qualquer requisito adicional de senha ou autorização. O nome do comando ou `NOPASSWD`, por si só, não comprova nenhuma dessas rotas. Consulte [escrita em arquivos pertencentes a root](../interesting-files-permissions/write-to-root.md) e [cron e timers do systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Um comando sudo fixo ainda pode carregar um arquivo de configuração previsível de um diretório compartilhado gravável. Rastreie se o chamador pode substituir esse arquivo e se os campos de origem e destino controlam um fetch ou cópia privilegiados. Uma URL de arquivo local pode expor dados legíveis apenas pela conta RunAs do sudo; uma origem controlada pelo chamador combinada com um destino protegido pode criar um caminho de escrita. Confirme o tratamento de URLs pelo programa instalado, as verificações do caminho de destino, a regra sudo efetiva e a acessibilidade da saída. Um caminho de configuração gravável em `/tmp`, por si só, é apenas um indício para análise; inspecione o binário e os metadados do arquivo sem invocar a transferência privilegiada.
- Uma regra sudo para `git apply` pode permitir que a conta RunAs escreva arquivos selecionados por um patch controlado pelo chamador. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitia que um patch criado para isso produzisse um symlink e depois escrevesse além da árvore de trabalho, mesmo quando o comando não aceitava `--unsafe-paths`. Verifique a regra efetiva de argumentos do sudo, a origem do patch, o acesso da conta RunAs ao diretório de trabalho e a correção do Git instalado ou o backport do fornecedor. Uma regra irrestrita que permita `--unsafe-paths` representa um risco separado dessa opção explícita; nem uma versão do Git nem a permissão para executar `git apply`, por si sós, provam que um arquivo protegido pode ser alterado. Não aplique um patch não confiável durante a enumeração passiva.
- Uma regra sudo com capacidade de root para `clamscan --debug` pode cruzar uma fronteira de leitura se um usuário com menos privilégios puder fornecer uma imagem DMG e o parser instalado for afetado pela [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que poderia revelar conteúdo de arquivos pela saída de debug. Confirme os argumentos permitidos e o caminho de verificação exatos, o controle da entrada, a conta RunAs efetiva, a correção/backport do mecanismo e se a saída é visível ao chamador. Se uma regra mais ampla permitir `--file-list`/`-f`, analise separadamente o comportamento dessa lista; uma política fixada em `--debug <scan-path>` não permite essa opção. Inspecione a política e os metadados do pacote sem verificar um arquivo criado para isso nem imprimir saída protegida durante a enumeração.
- Uma regra sudo com capacidade de root que abre uma imagem de disco criptografada escolhida pelo chamador, combinada com uma segunda regra que monta o mapper resultante, pode importar arquivos controlados pelo chamador para o namespace de montagem do host. Confirme ambas as regras efetivas e seus argumentos, o controle da imagem e do nome do mapper, o destino real da montagem e o proprietário e modo dos arquivos resultantes. Uma transição de set-user-ID também exige um executável acessível, opções de montagem que o respeitem (`nosuid` o bloqueia) e políticas de processo ou MAC aplicáveis; abrir ou montar uma imagem, por si só, é apenas um indício para análise. Uma rota separada por meio de um backup existente exige a chave correspondente e um segredo útil e legível em seu interior. Inspecione a política e os caminhos sem abrir nem montar uma imagem durante a enumeração passiva. Consulte o [manual do cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e as [opções de montagem](https://man7.org/linux/man-pages/man8/mount.8.html).
- Uma regra sudo com capacidade de root para um script de shell ou Python merece uma análise do diretório de trabalho se o script invocar `./helper` sem antes mudar para um diretório fixo. Uma lista Python como `['./helper']` passada a `subprocess.run` pode ter o mesmo comportamento: o diretório de trabalho é escolhido pelo chamador. O chamador pode conseguir escolher um diretório gravável e colocar nele um executável com esse nome relativo; um caminho absoluto em outra parte do script não protege essa chamada. Confirme a regra efetiva, `runchdir` ou outra política que altere o diretório, o fluxo do script e a possibilidade de alcançar o ramo, um diretório gravável e executável e as restrições de montagem/`NOEXEC` antes de considerar isso execução de código. Se o script não puder ser lido, o comportamento permanece desconhecido até que seu código-fonte seja analisado por um caminho autorizado. Analise os scripts estaticamente em vez de executar o helper. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta a política de diretório de trabalho.
- Um validador Python fixo com capacidade de root ainda pode avaliar um arquivo de dados escolhido pelo chamador. [A documentação do `eval()` do Python alerta contra entradas não confiáveis](https://docs.python.org/3/library/functions.html#eval): uma verificação de sufixo, um prefixo aritmético ou um ramo de validação não constituem sandbox se a expressão restante chegar a `eval`. Confirme a regra sudo efetiva, se o chamador pode selecionar e controlar o arquivo exato, as condições do ramo do parser e a construção da expressão, e a identidade do processo privilegiado antes de considerar isso um caminho de execução. A presença de `eval` em um script legível é apenas uma indicação para análise; inspecione o código-fonte e as permissões do arquivo sem executar o validador nem enviar uma expressão de teste durante a enumeração.
- Um wrapper Ruby sudo com capacidade de root que lê um nome de arquivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, pode obter a entrada do diretório de trabalho do chamador, a menos que o wrapper ou a política sudo fixe esse diretório. Verifique os argumentos permitidos exatos, as permissões do diretório e do arquivo e o comportamento da versão instalada do Psych: implementações mais antigas de `YAML.load` podiam desserializar objetos Ruby arbitrários, enquanto versões mais recentes restringem as classes por padrão. Um ponto de chamada estático é apenas um indício; confirme que o arquivo realmente vem de um diretório gravável pelo chamador e que o carregador instalado aceita classes perigosas. Prefira `safe_load` com uma lista explícita e mínima de classes permitidas para entradas não confiáveis. Consulte a [documentação do Psych para Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e a [documentação do Psych para Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Uma concessão sudo exata para root de `sudo go run /absolute/file.go` merece uma análise do diretório de trabalho quando o código Go lê um arquivo WASM relativo e pode executar um script de shell relativo após inspecionar seu resultado. Confirme o RunAs efetivo, os argumentos e as negações do comando, um diretório de trabalho atual gravável pelo chamador, o fluxo de dados do WASM até o ramo e se esse ramo invoca o helper. Um `runchdir` fixo do sudo, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pode alterar o local da busca. A ocorrência conjunta estática é apenas um caso candidato; inspecione o código-fonte sem executar Go, WASM ou o helper.
- `sudoedit` e curingas em argumentos exigem verificações exatas da versão e da regra; a [lista de verificação](linux-privilege-escalation-checklist.md) inclui o problema de edição de arquivos pelo sudoedit. Para uma concessão `sudoedit` entre usuários com um caminho curinga, inspecione a configuração efetiva de `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, o destino resolvido e quem pode substituir cada entrada de diretório pai. A primeira pode permitir seguir um symlink, enquanto desabilitar a segunda remove as verificações de diretórios graváveis; nenhuma dessas configurações, por si só, comprova escrita no arquivo de outro usuário. Confirme a política sudo instalada e os argumentos correspondentes exatos antes de chegar a essa conclusão. Consulte as [definições de opções do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Em uma regra de comando sudoers, um curinga de argumento pode corresponder a espaços em branco, além de caracteres de caminho. Uma regra para um comando capaz de ler com um argumento como `/restricted/*` pode, portanto, permitir um argumento de arquivo adicional após um prefixo correspondente. Analise o usuário run-as, o caminho do comando, o padrão de argumentos e as negações posteriores exatos; uma leitura de arquivo demonstrada não implica execução de comandos. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) diferencia curingas de argumentos de curingas no caminho do comando.
- Um curinga de argumento que parece restringir caminhos também pode corresponder a `../`. Por exemplo, uma regra com capacidade de root para `node /opt/scripts/*.js` pode permitir que o chamador controle um arquivo JavaScript fora de `/opt/scripts` se o nome de caminho fornecido ainda começar com `/opt/scripts/` e resolver por segmentos de diretório pai. Trata-se de um curinga de **argumento**; as regras de correspondência de barras para o curinga do caminho do executável Node são diferentes. Verifique a regra efetiva, as negações posteriores, a resolução do caminho, o controle do arquivo de destino e quaisquer restrições de expressão regular ou digest do sudoers antes de concluir que há execução de código. Consulte as [regras de curingas do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e a [documentação de linha de comando do Node](https://nodejs.org/api/cli.html).
- Arquivadores e outros utilitários podem ter hooks de execução. Compare os argumentos exatos permitidos com [GTFOBins](https://gtfobins.github.io/) em vez de presumir que somente shells ou interpretadores executam comandos.
- Uma regra irrestrita de `qpdf` com capacidade de root pode expor um arquivo privilegiado por meio de anexos PDF: qpdf 10.2 e versões posteriores oferecem suporte a `--empty` e `--add-attachment file ... --` com um PDF de saída. Se o processo privilegiado puder ler a origem selecionada e gravar o PDF em um caminho acessível ao chamador, esse arquivo de saída poderá conter os bytes da origem. Analise os argumentos e as exclusões efetivos do sudo, a versão do qpdf, o acesso à origem e o caminho de saída antes de concluir que a divulgação de arquivos é possível. Ler uma chave SSH de root só é útil para login se a chave for válida e a autenticação SSH de root for permitida. Consulte as [opções de anexos do qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- O reaproveitamento de timestamps do sudo depende da política de cache, do usuário proprietário, do terminal/sessão e das permissões. O [guia de escalonamento de privilégios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) aborda essas verificações.
- O `doas` tem suas próprias regras e configuração. Verifique os comandos permitidos e os caminhos de configuração graváveis conforme descrito na [seção doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Ferramentas de build e pacotes executadas pelo sudo

Uma concessão sudo irrestrita para `forge` do Foundry pode ser relevante mesmo quando a identidade RunAs é outro usuário que não seja root. Opções do compilador como `--use` podem selecionar um executável local, e `forge flatten -o` seleciona um arquivo de saída. Verifique a versão instalada do Forge, os argumentos exatos do sudo, os caminhos acessíveis do projeto e do compilador, as permissões da saída e o ambiente efetivo antes de considerar a concessão explorável. Um executável helper relativo encontrado por meio de `PATH` é uma rota dependente da versão e do ambiente, não uma característica que se deva presumir em todas as compilações do Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Uma concessão irrestrita com capacidade de root para `pacman` permite mais do que consultas de pacote: `-U` aceita um pacote local, pacotes podem conter scripts de instalação e `--hookdir` seleciona outro diretório de hooks. Analise a regra sudo efetiva, as restrições de argumentos e as exclusões antes de testar; a enumeração passiva não precisa instalar um pacote nem executar um hook.<sup>[[25]](#references)[[26]](#references)</sup>

Um wrapper fixo de shell pelo sudo também pode instalar uma dependência npm nomeada e depois iniciar um aplicativo Node. Analise a regra exata de RunAs, se o pacote já está instalado, o `HOME` e o `userconfig` efetivos do npm, as substituições da configuração do projeto ou da linha de comando e se um usuário com menos privilégios controla o registry ou o pacote retornado para esse nome. [A documentação do npm descreve a busca por `.npmrc` por usuário e por projeto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); o comportamento de `HOME` do sudo depende da política e da distribuição instaladas, portanto, o `.npmrc` gravável de um usuário pode ou não ser lido pelo processo npm privilegiado. Se o aplicativo privilegiado importar o pacote recém-instalado, o código do módulo poderá ser executado sob a identidade desse aplicativo. Scripts executados durante a instalação constituem uma rota separada, dependente da versão e da configuração; [a documentação do npm descreve seu ciclo de vida e o tratamento de usuários](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Um caminho `.npmrc` ou uma linha `npm install`, por si só, é apenas um indício para análise. Inspecione a regra, o wrapper curto, os caminhos de configuração e a procedência do pacote sem instalar nem iniciar o aplicativo durante a enumeração passiva.

Uma concessão para `pip` ou `pip3 download` com capacidade de root também é um indício para análise de build de pacotes quando os argumentos permitem ao chamador selecionar uma distribuição de origem não confiável, mesmo que o padrão da URL a restrinja a um serviço local e ao sufixo `.tar.gz`. `pip download` aceita URLs de arquivos e resolve metadados; preparar uma sdist pode invocar seu backend de build ou código legado de `setup.py` antes de o arquivo ser simplesmente salvo. Confirme o RunAs do sudo e a regra de argumentos exatos, se o chamador pode publicar ou substituir o arquivo selecionado e se essa versão do pip realmente prepara os metadados. Um arquivo fixo e confiável ou um wheel não estabelece essa rota. Não busque nem compile um pacote não confiável durante a enumeração passiva. Consulte o [comando download do pip](https://pip.pypa.io/en/stable/cli/pip_download/), a [interface do sistema de build](https://pip.pypa.io/en/stable/reference/build-system/) e as [orientações de instalação segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Uma regra sudo que permita `pip install` com um caminho de projeto local escolhido pelo chamador cria uma fronteira de build mais direta. [O pip aceita diretórios de projeto locais](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca seu sistema de build; o [backend de build executa hooks de build controlados pelo projeto](https://pip.pypa.io/en/stable/reference/build-system/). Confirme a identidade efetiva de RunAs, as restrições e negações exatas de argumentos, o controle do projeto selecionado e o comportamento do pip/backend instalado antes de considerar a regra execução de código privilegiada. Um projeto fixo e confiável ou uma regra que exclua caminhos escolhidos pelo chamador não estabelece essa rota. Analise a regra e os metadados do projeto sem instalar um pacote durante a enumeração passiva.

Uma concessão irrestrita com capacidade de root para `easy_install` é um indício relacionado de build de pacotes legado. [A documentação do Setuptools](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) informa que Easy Install aceita um diretório de projeto local e compila distribuições de origem; um projeto controlado pelo chamador pode executar seu `setup.py` durante esse build sob a identidade do sudo. Confirme a conta RunAs efetiva, as restrições exatas do comando e dos argumentos (incluindo negações posteriores), o controle do projeto selecionado e o comportamento da ferramenta instalada. Um projeto fixo e confiável ou uma política que não permita uma origem escolhida pelo chamador não estabelece essa rota. Inspecione a regra e os metadados do projeto sem instalar um pacote durante a enumeração.

Um wrapper Python permitido pelo sudo que usa `setuptools.package_index.PackageIndex.download` com uma URL escolhida pelo chamador é um caso de análise diferente de `pip download`: [GHSA-5rjg-fvgr-3xxf do setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descreve um nome de arquivo derivado da URL que escapa do diretório de download pretendido e grava com as permissões do processo nas versões afetadas anteriores à 78.1.1. Confirme o RunAs efetivo e a regra de argumentos do sudo, se o wrapper passa a URL do chamador a essa API exata, o build instalado ou o backport do fornecedor e o destino resolvido do caminho resultante. Uma string de versão ou um diretório de download gravável, por si só, não comprova escrita arbitrária. Analise o wrapper curto e os metadados do pacote sem buscar a URL nem gravar um arquivo durante a enumeração.

Um wrapper de build permitido pelo sudo que passa um arquivo `.spec` escolhido pelo chamador ao PyInstaller exige a mesma análise da fronteira de confiança. Um arquivo spec do PyInstaller é Python executável avaliado durante o **build**, e suas entradas `datas` podem incluir em um artefato arquivos legíveis pela identidade de build. Confirme o usuário RunAs exato, as regras de argumentos e negações do sudo, o tratamento de caminhos e ramos pelo wrapper, o controle do arquivo spec escolhido e o acesso ao artefato resultante. Permitir apenas uma entrada `.py` ou encontrar o PyInstaller instalado não comprova controle do arquivo spec nem execução privilegiada. A análise passiva deve ler apenas um arquivo limitado do wrapper e seus metadados; não deve executar um build. Consulte a [documentação dos arquivos spec do PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Carregadores de presets e plugins executados pelo sudo

Ferramentas Python que aceitam um preset ou diretório de plugins escolhido pelo chamador podem importar código com os privilégios concedidos pelo sudo. Por exemplo, o BBOT aceita um preset com `-p`, e sua [documentação de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descreve entradas `module_dirs` que selecionam diretórios adicionais de módulos Python. Se a regra sudo efetiva permitir um preset escolhido pelo chamador e este controlar um módulo no diretório selecionado, a importação poderá executar código como o usuário privilegiado, potencialmente antes de a ferramenta rejeitar um módulo inválido. Verifique a versão instalada, a política exata de RunAs e argumentos do sudo e a propriedade dos caminhos do preset e do módulo sem carregar o módulo durante a enumeração.

### Ferramenta de linha de comando Backdrop executada pelo sudo

[Bee](https://github.com/backdrop-contrib/bee) é uma ferramenta de linha de comando PHP para Backdrop CMS. Seus comandos `eval` (`php-eval`) e `php-script` podem executar PHP fornecido pelo chamador. Portanto, uma regra sudo que permita o executável Bee como root com argumentos irrestritos pode expor execução de código como root quando Bee consegue inicializar uma instalação Backdrop. Execute-a a partir do diretório do site ou selecione um site usando a opção global `--root=<directory>`; encontrar Bee ou um arquivo `settings.php` do Backdrop não comprova a permissão sudo, a existência de um site utilizável nem uma inicialização bem-sucedida. Analise a regra sudo efetiva, quaisquer exclusões de comando, a identidade do executável e o acesso ao site antes de testar. Durante a enumeração passiva, inspecione a regra e os caminhos dos arquivos sem invocar Bee. Consulte o [changelog dos comandos do Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver a inclusão dos comandos PHP.

### Servidores de terminal executados pelo sudo

`mosh-server` inicia um servidor de terminal interativo como o usuário que o invoca. Ele escolhe uma porta UDP alta e uma chave de sessão, informa ambos ao chamador e normalmente inicia o shell de login desse usuário quando um cliente se conecta. Portanto, uma concessão sudo irrestrita para root de `mosh-server` é um candidato à análise de shell, embora o próprio comando do servidor se desconecte. Verifique a identidade efetiva de RunAs, os argumentos permitidos e as exclusões, o binário instalado, o shell, a disponibilidade de um cliente e o acesso UDP. A enumeração passiva deve inspecionar a regra sudo sem iniciar um servidor nem imprimir uma chave de sessão ativa. Consulte o [manual do servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e as [notas de projeto upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de backup privilegiados que reescrevem o arquivo de tarefas do chamador

Um wrapper de shell executado como root pode aceitar um arquivo de tarefas escolhido pelo chamador, remover `../` dos caminhos de origem, verificar se cada resultado começa com um diretório permitido, reescrever o arquivo de tarefas e depois passar seu *nome de caminho* a um programa de backup. Analise o caminho transformado após a resolução canônica completa: uma única passagem de substituição de strings pode expor uma nova sequência de travessia que uma verificação lexical de prefixo aceita. Verifique também se o programa de backup lê os dados transformados em memória ou abre o arquivo novamente. Se ele abrir o arquivo novamente, uma reescrita malsucedida pode deixar a entrada original no lugar.

No Linux, `fs.protected_regular` pode negar uma escrita com `O_CREAT` em um arquivo regular de outro usuário dentro de um diretório sticky gravável por todos. Essa negação é protetiva, mas um wrapper de shell que ignora o erro de escrita ainda pode continuar usando o arquivo de tarefas original. Confirme a configuração, o proprietário do arquivo e do diretório e se o wrapper interrompe a execução quando ocorre uma falha. O caminho só é candidato a divulgação de arquivos se a regra sudo efetiva permitir executar o wrapper como usuário privilegiado, o chamador controlar a entrada de tarefas e um destino de backup legível, e o utilitário de backup realmente incluir origens protegidas. Inspecione essas condições sem executar o backup durante a enumeração.

### Curingas de argumentos em ferramentas de pacotes privilegiadas

Em uma regra sudo para `tcpdump`, um `*` no **padrão do argumento** pode corresponder a espaços em branco e barras; portanto, uma restrição que parece limitar um caminho ainda pode permitir texto adicional de opção. Isso difere de um curinga no caminho do executável do comando; inspecione a regra completa de RunAs e quaisquer negações posteriores. Se for possível injetar opções, a invocação permitida e a [semântica das opções do `tcpdump` instalado](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinam se `-F`, `-V`, `-r`, `-w` ou `-Z` fornece uma primitiva útil de leitura/escrita. `-V` lê uma lista de nomes de arquivos de captura, não despeja arquivos arbitrários de uso geral. AppArmor ou outra política MAC pode bloquear o acesso a arquivos mesmo quando o sudo permite o comando; um arquivo de perfil no disco não comprova que ele esteja carregado ou em modo enforcing. Analise a autorização e a política passivamente antes de chegar a uma conclusão. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descreve a diferença entre curingas.

Uma regra sudo com capacidade de root que liste apenas o executável `tcpdump`, sem restrição de argumentos, também merece análise. O [manual do tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como um comando pós-rotação quando `-C` ou `-G` rotaciona uma captura salva; `-Z` ou um padrão definido durante a compilação pode remover privilégios antes da execução desse comando. Verifique a regra sudo efetiva, o build instalado, o comportamento de remoção de privilégios e se a rotação pode ocorrer antes de considerar a regra uma rota de escalonamento. Uma regra destacada é um caso candidato, não prova de execução de comandos como root.

### Wrappers do Nmap executados pelo sudo

Quando um caminho `nmap` permitido pelo sudo é um wrapper de shell, inspecione o caminho permitido exato e todas as opções que ele encaminha. Bloquear a grafia conhecida `--script` não bloqueia necessariamente o carregamento de código NSE: [`--datadir` do Nmap](https://nmap.org/book/man-misc-options.html) seleciona arquivos de dados, e o NSE [carrega `nse_main.lua`](https://nmap.org/book/nse-implementation.html) do diretório de dados selecionado quando o scripting está habilitado. Alguns builds instalados também aceitam grafias longas alternativas de opções; portanto, compare as restrições com o parser efetivo desse binário. [`--excludefile`](https://nmap.org/book/man-target-specification.html) é outra superfície de leitura de arquivos; erros do parser podem revelar texto. Verifique a regra sudo efetiva, a lógica do wrapper, a versão do Nmap, o controle do diretório e a política MAC sem executar scans durante a enumeração.

### Hooks de pull do Mercurial executados pelo sudo

Uma origem fixa em `sudo hg pull /fixed/source` ainda deixa o repositório **receptor** ser selecionado pelo diretório de trabalho atual, a menos que o comando o fixe com `-R`. Um repositório receptor controlado pelo chamador pode definir hooks em `.hg/hgrc`, e um hook pode ser executado como o usuário RunAs do sudo. [O Mercurial ignora configurações de repositórios pertencentes a um usuário ou grupo não confiável](https://mercurial-scm.org/help/topics/config); portanto, inspecione os usuários/grupos confiáveis da conta RunAs e o diretório de trabalho exato antes de considerar isso execução de código. Ler a política e a configuração basta para uma análise passiva; não execute `pull` nem invoque um hook para enumerá-lo.

### Hooks de pull do Git executados pelo sudo

Para uma concessão sudo exata com capacidade de root de `sudo git pull`, verifique também o repositório **receptor** selecionado pelo diretório de trabalho. Um repositório pertencente ao chamador pode ter um hook `post-merge` executável que roda com a identidade do processo Git quando um pull realmente realiza uma merge bem-sucedida; [o Git documenta esse hook](https://git-scm.com/docs/githooks) e o [comportamento de merge versus rebase do pull](https://git-scm.com/docs/git-pull). Verifique a regra sudo efetiva e o CWD, o caminho ativo do hook e suas permissões, e se é possível realizar um merge com novos commits. Um pull malsucedido, sem alterações ou que apenas faça rebase não comprova essa rota de hook. Inspecione a política e os metadados do repositório sem executar o pull privilegiado.

### Cópias de arquivos por rsync executadas pelo sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, um `*` no **padrão de argumentos do sudoers** pode corresponder a espaços e permitir uma opção adicional entre a origem e o destino. Isso é diferente da expansão de nomes de arquivo pelo shell. Se o chamador puder preencher a origem e o destino puder ser escrito pelo processo rsync privilegiado, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) poderá solicitar a propriedade privilegiada, enquanto o modo de arquivamento preserva os bits de permissão, potencialmente criando um arquivo SetUID de propriedade privilegiada. Verifique a semântica exata dos [curingas do sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), a versão do rsync, as negações posteriores, `nosuid` do sistema de arquivos e a política MAC. Uma regra correspondente é um caso candidato para análise, não prova de escalonamento de privilégios bem-sucedido.

### Exportação de regras de filtros de pacotes executada pelo sudo

Uma concessão irrestrita com capacidade de root para `iptables` e `iptables-save` (ou o par correspondente `ip6tables`) merece uma análise de escrita em arquivo. A correspondência `comment` aceita texto de regra escolhido pelo chamador, enquanto `iptables-save -f` grava o conjunto de regras serializado em um caminho selecionado.<sup>[[20]](#references)[[21]](#references)</sup> Um payload útil depende de como o backend instalado serializa comentários e se o arquivo de destino aceita outras linhas na exportação; `iptables-save`, por si só, não fornece conteúdo arbitrário escolhido pelo chamador. Verifique a identidade RunAs, os argumentos e as exclusões exatos do sudo, a extensão de correspondência disponível, o backend e as permissões do destino. Durante a enumeração, inspecione a concessão sem alterar as regras de firewall nem gravar um arquivo.

### Diretório de logs privilegiado do Below

A [CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afetou versões do Below anteriores à 0.9.0 que criavam um diretório `/var/log/below` gravável por todos. Se um serviço ou comando sudo permitido executar como root um build afetado, um usuário que possa gravar e atravessar um diretório de logs sem sticky bit talvez consiga substituir uma entrada de log por um symlink antes de o processo privilegiado abri-la. Analise o status dos patches do pacote instalado, o caminho exato de execução privilegiada, o acesso efetivo ao diretório, o sticky bit e as ACLs, e os metadados de `/var/log/below/error_root.log`. Um caminho gravável por todos ou uma regra sudo, por si só, não comprova a cadeia completa. Um diretório sticky ou um backport do fornecedor altera a avaliação. A enumeração passiva deve inspecionar apenas metadados; não é necessário criar um link nem executar o programa privilegiado.

### Coleta privilegiada de bundles de suporte a partir de entradas graváveis

Um script de perfil de suporte permitido pelo `sudo` pode ler caminhos fixos de logs como root e copiar seu conteúdo para um arquivo de perfil. Analise o script real em busca de leituras de arquivos; depois, verifique se o chamador pode substituir um caminho de origem ou qualquer entrada de diretório pai por um symlink. Se a leitura privilegiada seguir esse link e o arquivo de perfil resultante puder ser lido pelo chamador, um arquivo protegido poderá ser divulgado. A concessão sudo, o caminho de origem gravável, a leitura privilegiada e a saída legível precisam estar todos presentes; um log gravável ou nome de arquivo de perfil, por si só, não basta. Inspecione as permissões efetivas e os metadados dos links sem substituir arquivos nem gerar um perfil durante a enumeração. As [orientações de suporte do Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentam seu script de perfil executado como root e o arquivo de saída, ilustrando por que esses bundles exigem entradas e acesso à saída restritos.

### Scripts Python de restauração de arquivos executados como root

Mesmo uma regra sudo rigorosamente limitada para um script Python de restauração exige analisar a entrada do arquivo compactado. Se o chamador puder selecionar ou substituir o arquivo e o script extraí-lo como root com `tarfile.extractall(filter="data")`, verifique as atualizações de segurança do interpretador antes de confiar no filtro. O CPython corrigiu vários bypasses de filtro envolvendo symlinks e hard links, incluindo a CVE-2025-4517, nas versões 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. Backports de distribuições podem corrigir versões anteriores; portanto, a versão exibida do interpretador, por si só, não comprova exposição.<sup>[[16]](#references)[[17]](#references)</sup>

Para uma análise passiva, leia o comando e o script exatos do sudo, rastreie qual argumento seleciona o arquivo e verifique se o usuário atual pode gravar nele ou no diretório que o contém. Confirme separadamente o patch do fornecedor instalado e o destino da extração; `filter="data"` não torna seguro todo arquivo compactado não confiável.<sup>[[16]](#references)[[17]](#references)</sup>

### Carregadores de modelos de machine learning executados pelo sudo

Uma regra sudo que permite um arquivo `.pt`, `.pth` ou `.ckpt` escolhido pelo chamador merece análise quando um script privilegiado passa esse arquivo para [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou outro carregador baseado em pickle. Verifique a regra efetiva de RunAs, se o chamador pode criar ou substituir o modelo selecionado e o fluxo real dos argumentos por qualquer wrapper de shell até o helper Python. A extensão `.pth` também é usada por arquivos de configuração de site Python sem relação com modelos; portanto, a extensão, por si só, não comprova carregamento de modelo. Uma análise do arquivo compactado ou um scan estático de pickle não comprova que o carregamento posterior seja seguro; inspecione o comportamento de `weights_only`, que depende da [versão](https://docs.pytorch.org/docs/stable/notes/serialization.html), e qualquer allowlist. Consulte as [notas sobre pickle em ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). A enumeração passiva nunca deve carregar nem descompactar o modelo.

### Análise de expressões de entradas armazenadas executada pelo sudo

Um script Python fixo executado como root pelo sudo ainda pode avaliar texto que um usuário com menos privilégios consiga armazenar em um banco de dados de aplicativo. No TensorFlow, uma chamada a `preprocess_input_exprs_arg_string(value, safe=False)` seleciona um caminho com `eval`; o [aviso do TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descreve o parser inseguro e uma correção para seu chamador de linha de comando. Uma chamada explícita do aplicativo com `safe=False` exige análise separada, mesmo quando esse chamador de linha de comando está corrigido. Verifique a regra sudo efetiva, quem pode modificar a linha exata de entrada, se a filtragem ou pontuação permite que essa linha chegue à chamada e o comportamento da função instalada. Uma versão do TensorFlow, uma concessão sudo ou um arquivo de modelo fixo, por si sós, não comprovam a cadeia. Inspecione o script e o fluxo de dados passivamente; não execute o helper privilegiado nem envie expressões de teste durante a enumeração.

### Configuração de needrestart permitida pelo sudo

`needrestart -c` carrega e avalia o conteúdo de um arquivo de configuração Perl escolhido pelo chamador. Se `sudo -l` permitir `needrestart` como root com argumentos que permitam `-c`, e o chamador puder escolher um arquivo de configuração legível em um local gravável, essa permissão poderá levar à execução de código como root. Verifique a regra exata de RunAs e argumentos do sudo; uma regra que permita apenas uma lista fixa de argumentos pode bloquear essa rota. Isso é separado das vulnerabilidades de varredura de interpretadores do needrestart: atualizar o pacote ou desabilitar `interpscan` não torna segura uma concessão irrestrita de `-c` como root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importações Python executadas pelo sudo sob outra conta

Um ponto de entrada Python fixo ainda pode importar um módulo que o chamador consiga editar ou substituir, inclusive quando o sudo executa o script como um usuário de serviço **não root**. Para um `from utils import status` literal, analise `utils/__init__.py` e `utils/status.py` locais, bem como as permissões do diretório do pacote. Confirme o caminho de importação do script, os argumentos exatos permitidos pelo sudo e se a ação relevante alcança essa importação antes de considerar o arquivo gravável um caminho de execução. Inspecione arquivos e permissões sem importar nem executar o script durante a enumeração.<sup>[[2]](#references)[[3]](#references)</sup>

Uma regra sudo exata para `python3 /absolute/script.py` precisa apenas que o script seja legível; o arquivo não precisa ser executável nem ter shebang. Analise também módulos locais **ausentes**: se o script importar um módulo cujo nome de arquivo possa ser criado em um diretório de script gravável pelo chamador, o Python poderá carregar esse arquivo sob a identidade RunAs. Confirme a regra sudo efetiva, o [caminho de busca de módulos](https://docs.python.org/3/library/sys_path_init.html) real do interpretador, se o módulo é built-in ou frozen e se a importação é alcançada. Uma regra sudo direta para o script tem requisitos diferentes de bit de execução e shebang. Um wrapper separado que acrescenta tokens fornecidos pelo chamador depois de `sudo -u account` também exige análise do fluxo de argumentos: outro `-u` nesses tokens só importa se a política sudo invocada permitir a identidade resultante. Strings estáticas, por si só, não comprovam nenhuma das rotas.

### Apache executado pelo sudo com configuração controlada pelo chamador

Se uma regra sudo permitir uma invocação privilegiada de `apachectl`, `apache2ctl` ou `httpd` com um arquivo de configuração `-f` controlado pelo chamador, analise as permissões desse arquivo e de seu diretório pai. A diretiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) do Apache recebe o nome do módulo seguido pelo **nome do arquivo do módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) também carrega um arquivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) podem estender a configuração ou expor conteúdo de arquivos por meio de erros. Um wrapper personalizado pode validar esses caminhos, remover privilégios ou restringir argumentos; portanto, uma configuração gravável é um caso candidato para análise, não prova de execução de código. Verifique a canonicalização de caminhos, os symlinks e a análise das diretivas antes de chegar a uma conclusão.

### nginx executado pelo sudo com configuração controlada pelo chamador

Uma regra irrestrita com capacidade de root para `nginx` pode permitir que [`-c` selecione outra configuração](https://nginx.org/en/docs/switches.html). Analise os argumentos e as exclusões exatos do sudo, se o chamador pode fornecer a configuração e se os processos master ou workers resultantes mantêm acesso a caminhos protegidos. Uma combinação de `root` escolhido e `autoindex` pode expor arquivos por meio de um novo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) pode oferecer um caminho de escrita de arquivos privilegiado, mas o módulo DAV não é incluído por padrão e é preciso verificar sua presença, a acessibilidade do listener, as permissões dos arquivos e o comportamento de arquivos temporários. A diretiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) também pode apontar para um arquivo escolhido; gravar logs em um arquivo de configuração sensível, como `/etc/ld.so.preload`, exige um gravador privilegiado efetivo e um registro de log controlável antes de se tornar uma rota de escalonamento. O destaque do executável em `sudo -l` é um indício para análise, não prova de que qualquer uma dessas rotas funcione. A enumeração passiva não deve iniciar nem reconfigurar o nginx.

### Comparação de padrões em prompts Bash privilegiados

Quando um script Bash permitido pelo sudo lê um valor do chamador e o compara com `[[ "$expected" == $entered ]]`, o Bash interpreta o operando direito sem aspas como um padrão. Portanto, um curinga pode satisfazer a comparação sem que o valor esperado seja conhecido. Colocar o operando entre aspas (`[[ "$expected" == "$entered" ]]`) o transforma em uma comparação literal de strings. Analise a regra sudo exata, se o prompt pode ser alcançado e o que o script faz após a comparação; a sintaxe, por si só, não comprova um caminho explorável. Evite imprimir o valor esperado durante a enumeração. Consulte a [referência das construções condicionais do Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers executados pelo sudo que baixam e executam um arquivo

Uma concessão irrestrita com capacidade de root para um helper personalizado merece uma análise de fluxo de dados se ele aceitar uma URL escolhida pelo chamador, gravar a resposta em disco e depois invocar esse arquivo com um interpretador ou shell. [O sudoers permite argumentos arbitrários quando a entrada de comando não lista nenhum](https://man7.org/linux/man-pages/man5/sudoers.5.html); um caminho de executável fixo não restringe o que os argumentos podem selecionar. Confirme a validação real da URL, o caminho de saída, o ramo de sucesso e a execução posterior no helper instalado. Uma importação de libcurl correspondente ou uma string imprimível, por si só, não comprova essa cadeia.

Mesmo um nome de saída fixo pode ser substituído entre a escrita e a execução quando o helper usa um **caminho relativo em um diretório de trabalho controlado pelo chamador**. A renomeação ou substituição de um arquivo pertencente a root depende do acesso de escrita e busca ao diretório e de eventuais restrições de sticky bit, não apenas do modo do arquivo; consulte [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifique se o helper abre o caminho novamente ou usa o descritor já aberto, e se muda para um diretório confiável antes de gravar. Inspecione passivamente a política sudo, o helper e os metadados do diretório; não invoque o download privilegiado nem faça uma corrida durante a enumeração.

Um helper de download executado como root pelo sudo também pode expor uma injeção de **argumentos** quando monta uma string de comando Bash como `curl <caller input> -o <fixed output>`. Um filtro que rejeite espaços em branco ainda permite a [expansão de chaves do Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementos separados por vírgulas e sem aspas podem se transformar em argumentos separados para o curl. Se a entrada chegar ao curl antes do `-o` fixo, uma opção de saída fornecida pelo chamador poderá selecionar o destino para a primeira URL, sob a identidade do helper; [o curl associa opções de saída às URLs na ordem](https://curl.se/docs/manpage.html#-o). Confirme o shell exato, o quoting, a validação da entrada, a regra sudo efetiva, a ordem dos argumentos do curl e os esquemas de URL aceitos, e se o chamador controla os bytes baixados ou pode ler o resultado. Um executável empacotado com PyInstaller pode conter lógica de aplicativo Python, mas o marcador de empacotamento ou uma string `curl`, por si só, não comprova esse fluxo de dados. Analise uma cópia offline limitada quando autorizado; a enumeração rotineira não deve executar o helper nem buscar dados escolhidos por um atacante.

Um script de shell executado como root pelo sudo que chama [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) apenas escolhe um nome ainda não utilizado; ele **não** cria o arquivo. Se o script depois criar esse nome em um diretório que outro usuário possa afetar, reabri-lo e anexar seu conteúdo a um destino protegido, como o `authorized_keys` de root, analise a possibilidade de uma corrida com arquivo temporário. Confirme a regra sudo exata, a propriedade do diretório e do arquivo, a sequência de criação e reabertura, as proteções do kernel e se a escrita privilegiada realmente usa bytes controlados por um atacante. Uma string `mktemp -u` ou um `/tmp` gravável, por si só, não comprova a corrida. Inspecione o script e os metadados do caminho sem executá-lo nem disputar seu arquivo temporário durante a enumeração.

## Notas defensivas

- Evite conceder acesso a interpretadores ou editores interativos pelo sudo.<sup>[[1]](#references)</sup>
- Prefira wrappers fixos, pertencentes a root e que executem uma única ação administrativa restrita.<sup>[[1]](#references)[[2]](#references)</sup>
- Se um interpretador for inevitável, restrinja o caminho exato do script e impeça argumentos controlados pelo usuário, importações graváveis, `PYTHONPATH` e a preservação de ambiente inseguro.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se for necessário editar arquivos, restrinja o caminho exato do arquivo e considere `sudoedit` com versões corrigidas do sudo e tratamento rigoroso do ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Analise `SETENV`, `env_keep`, diretórios de trabalho graváveis, caminhos de módulos/importação graváveis, `NOEXEC`, `use_pty` e logging, mas não os trate como uma sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
