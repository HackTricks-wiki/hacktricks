# Missbrauch von Sudo-Befehlen

## Mit Sudo erlaubte Interpreter

Wenn `sudo -l` einem Benutzer erlaubt, einen Interpreter als Root auszuführen, sollte dies als direkte Codeausführung behandelt werden. Interpreter sind dafür ausgelegt, beliebigen Code auszuführen. Eine Regel, die `python3`, `perl`, `ruby`, `lua`, `node` oder ähnliche Binärdateien erlaubt, entspricht daher meist der Ausführung von Befehlen als Root, sofern die Argumente nicht strikt eingeschränkt und validiert werden.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Üblicher Prüfungsablauf: Zuerst die Berechtigungen des Benutzers auflisten und dann mit der Option `-c` des Interpreters eine Python-Anweisung ausführen.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Weitere Interpreter-Beispiele sind unten aufgeführt; die genannten Interpreter dokumentieren die Ausführung von Inline-Code oder APIs für Kindprozesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Der genaue Pfad ist wichtig. Wenn die sudo-Regel `/usr/bin/python3` erlaubt, verwende bei der Validierung genau diesen Pfad.<sup>[[2]](#references)</sup>

Ein sudo-Executable-Glob wie `/usr/bin/python*` kann auch Python 2 für ein Skript zulassen, das für Python 3 geschrieben wurde. Wenn das Skript `input()` mit vom Aufrufer kontrolliertem Text erreicht, [wertet Python 2 diesen Text als Ausdruck aus](https://docs.python.org/2/library/functions.html#input); ein expliziter Interpreter-Aufruf setzt den Shebang des Skripts außer Kraft. Überprüfe die installierten passenden Binaries, die effektive RunAs- und Argumentrichtlinie, Ablehnungen und erreichbare Eingaben, bevor du dies als Ausführungspfad einstufst.

Ein festgelegter Skriptpfad in einer sudo-Regel mit Root-Rechten schränkt nicht ein, was das Skript ausführt. Prüfe bei einem lesbaren Bash-Wrapper, ob dessen erster ausführbarer Befehl einen nicht in Anführungszeichen gesetzten Positionsparameter wie `$1` als **Befehlswort** verwendet, während sudo vom Aufrufer gewählte Argumente zulässt. Bestätige die effektive RunAs-Identität, die Passwort- und Argumentrichtlinie, spätere Ablehnungen und den tatsächlich ausgeführten Skriptzweig; `NOEXEC`, eine feste sichere Argumentliste oder ein Wrapper, der seinen Befehl validiert, können das Ergebnis ändern. Untersuche das kurze Skript bei der Enumeration statisch, statt es mit einem Testbefehl aufzurufen.

Eine uneingeschränkte sudo-Regel mit Root-Rechten für `dotnet` verdient ebenfalls eine Prüfung des Interpreters. Wenn ein .NET SDK installiert ist, führt [`dotnet fsi` F#-Code interaktiv oder aus einem Skript aus](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), und [`dotnet run` führt ein Projekt aus dem Quellcode aus](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bestätige zuerst die effektive RunAs-Identität und die genaue Argumentrichtlinie: Eine Regel, die auf einen bestimmten sicheren Unterbefehl oder eine vertrauenswürdige Anwendung beschränkt ist, ist eine andere Berechtigung, und bei einer Installation, die nur die Runtime enthält, können SDK-Befehle fehlen. Der Name der ausführbaren Datei allein ist ein Anlass zur Prüfung, kein Beweis für die Ausführung von Code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo-erlaubtes `tee`: beliebiges Schreiben in privilegierte Dateien

GNU `tee` kopiert die Standardeingabe in jeden Pfad, der als Dateioperand angegeben wird. Daher gewährt eine sudo-Regel, die die Ausführung von `/usr/bin/tee` als root mit vom Aufrufer kontrollierten Argumenten erlaubt, die Möglichkeit, beliebige Dateien als root anzulegen oder zu überschreiben. Mit `-a` wird stattdessen angehängt. Ein `PASSWD:`-Tag betrifft die sudo-Authentifizierung; für sich genommen schränkt es weder das Ziel noch die aus der Standardeingabe gelesenen Bytes ein.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Prüfe zuerst die genaue Regel. Validiere die Funktion auf einem autorisierten Testsystem nur mit einem entbehrlichen Ziel, dessen Erstellung unbedenklich ist. Das abschließende `>/dev/null` unterdrückt lediglich die Ausgabe von `tee` auf der Standardausgabe.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Wenn `sudo` vor dem Producer steht, wird eine spätere Shell-Umleitung nicht mit erhöhten Rechten ausgeführt, da die Shell des Aufrufers das Ziel öffnet. Der privilegierte Prozess muss der Schreiber sein, wie in der obigen Pipeline.<sup>[[1]](#references)[[15]](#references)</sup>

Nachdem der Schreibzugriff bestätigt wurde, wähle einen geeigneten Sink für Root-Codeausführung aus [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Bei einer beobachteten Angriffskette wurde mit Root-Rechten `tee` verwendet, um eine kurzlebige Datei unter `/etc/cron.d/` anzulegen, über ein benutzergesteuertes Skript eine Backdoor zu starten und die Cron-Datei nach der Ausführung zu löschen. Durch das Entfernen der Cron-Datei wurde verhindert, dass sie zu einem dauerhaften Persistence-Eintrag wurde, obwohl Systemprotokolle weiterhin Belege für die Aktivität enthielten.<sup>[[27]](#references)</sup>

## Mit sudo erlaubte Editoren

Wenn `sudo -l` einem Benutzer erlaubt, einen interaktiven Editor als Root auszuführen, betrachte dies als Angriffsfläche zur Befehlsausführung und nicht als harmlose Berechtigung zum Bearbeiten von Dateien. Editoren können häufig Shell-Befehle ausführen, beliebige Dateien lesen oder schreiben oder externe Hilfsprogramme aus dem Editor heraus aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Üblicher Prüfablauf: Liste die Berechtigungen des Benutzers auf und starte dann jeden erlaubten Editor oder Pager mit sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Befehlsausführung mit Nano

Wenn `nano` über sudo erlaubt ist, kann die Befehlsausführung über die Editoroberfläche möglich sein.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Geben Sie dann an der nano-Eingabeaufforderung einen Befehl wie `id` oder `/bin/sh` ein.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Wenn eine interaktive Shell keine nutzbaren Terminal-Streams hat, leitet diese Umleitungsform ihre Standardausgabe und Standardfehler auf Deskriptor 0 um.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die genaue Tastenfolge kann je nach nano-Version und Build-Optionen variieren, aber das Sicherheitsproblem ist dasselbe: Der Editor läuft als root und kann externe Befehle ausführen.<sup>[[1]](#references)[[12]](#references)</sup>

### Andere gängige Editor-Ausbrüche

Vim-ähnliche Editoren ermöglichen häufig die Ausführung von Befehlen über `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pager wie `less` können ebenfalls die Ausführung einer Shell ermöglichen.<sup>[[14]](#references)</sup>

Eine sudo-Regel, die `apport-cli` als root erlaubt, sollte ebenfalls auf Pager geprüft werden. Betroffene Apport-Versionen konnten einen Crash-Report in `less` mit einer vom Angreifer anpassbaren Terminalgröße öffnen; unter bestimmten sudo- und Pager-Bedingungen konnte der Pager dann eine root-Shell bereitstellen. Prüfe die effektive sudo-Regel, die Pager-Konfiguration und den Paket-Fix der Distribution, bevor du allein aufgrund der Version von einer Verwundbarkeit ausgehst. Lies bei der passiven Enumeration die Paket- und Policy-Metadaten, ohne einen Crash auszulösen oder den privilegierten Report zu öffnen. [Ubuntus CVE-Eintrag](https://ubuntu.com/security/CVE-2023-1326) führt release-spezifische Versionen mit Fixes auf, einschließlich zurückportierter Fixes.

```text
!/bin/sh
```

## Weitere Gefahren durch sudo- und doas-Regeln

Beginne mit `sudo -l`, `sudo -V` und allen anwendbaren `doas`-Richtlinien. Lies den erlaubten Befehl, den RunAs-Benutzer, die Argumente, die Umgebung und die Defaults zusammen. Die Berechtigung, als Nicht-root-Dienstkonto auszuführen, kann weiterhin Dateien dieses Kontos offenlegen oder einen Weg zu root eröffnen.

Ein festes, durch sudo erlaubtes Python-Skript kann dennoch einen Shell-Befehl unter seiner RunAs-Identität ausführen, wenn interaktive, vom Aufrufer kontrollierte Eingaben an [`os.system()`](https://docs.python.org/3/library/os.html#os.system) angehängt werden. Eine Denylist für Shell-Sonderzeichen reicht nicht aus, um Sicherheit festzustellen: [Die Shell erkennt auch die Befehlssubstitution `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Bestätige, dass die erlaubten Argumente den Eingabezweig erreichen, dass die Eingabe ohne sichere Validierung in den Shell-Befehl gelangt und dass die wirksame sudo-Richtlinie den beabsichtigten RunAs-Benutzer zulässt. Der Skriptpfad oder ein Aufruf von `os.system()` allein ist lediglich ein Prüfhinweis; untersuche den Quellcode, ohne das privilegierte Skript aufzurufen.

Ein wirksamer sudo-Eintrag, der `chattr` als root erlaubt, kann ein unveränderliches (`i`) Dateiattribut entfernen, gewährt dadurch allein aber weder Schreibzugriff noch eine neue Identität. Laut [Handbuch zu `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) verhindert das Attribut Änderungen; nur root oder ein Prozess mit `CAP_LINUX_IMMUTABLE` kann es ändern. Prüfe die genauen sudo-Argumentregeln und die Unterstützung durch das Dateisystem. Verifiziere anschließend separat, ob der Aufrufer nach dem Entfernen des Attributs in die Datei schreiben kann und ob ein Prozess mit höherer Identität sie verwendet. Ein Ersatz der Login-Shell erfordert beispielsweise auch gültige Anmeldedaten für das Zielkonto und eine tatsächliche Anmeldung über diese Shell. Prüfe Richtlinien, Dateiattribute und Berechtigungen, ohne sie bei der Bestandsaufnahme zu ändern.

Wenn sudo sowohl nach einem Passwort als auch nach einem Einmalcode fragt, behandle diese Voraussetzungen getrennt von der Befehlsfreigabe. Eine lesbare `.google_authenticator`-Datei enthält sensibles Seed-Material; ein alter Anwendungs- oder Datenbankpasswort-Hash ist dagegen lediglich ein Kandidat für das aktuelle Kontopasswort. Keines von beidem beweist, dass der jeweils andere Faktor von der wirksamen PAM-Konfiguration akzeptiert wird. Prüfe nach erfolgter Autorisierung den genauen RunAs-Benutzer und die Argumente: Ein uneingeschränkter root-Eintrag für RubyGems `gem` kann dessen Editorbefehl offenlegen ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ein eingeschränkter Eintrag oder eine fehlgeschlagene Authentifizierung hingegen nicht. Bei einer passiven Bestandsaufnahme sollten Pfade und Richtlinien gemeldet werden, ohne das Seed auszugeben, ein Passwort wiederherzustellen, einen Code zu erzeugen oder den privilegierten Befehl aufzurufen.

Ein uneingeschränkter, root-fähiger sudo-Eintrag für Chefs `knife` verdient eine Prüfung auf Interpreterebene: [Chef dokumentiert, dass `knife exec -E` lokal einen Ruby-String auswertet](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifiziere, dass die wirksame sudo-Regel das Unterkommando `exec` und das vom Aufrufer angegebene Argument `-E` erlaubt, die vorgesehene RunAs-Identität gilt und keine passenden Befehlsverbote oder festen Argumente greifen. Die installierte Binärdatei oder eine Regel, die andere Unterkommandos beschränkt, ist lediglich ein Hinweis. Bei einer passiven Bestandsaufnahme sollte die Regel gemeldet werden, ohne `knife` aufzurufen.

Ein exakter, root-fähiger sudo-Eintrag für eine interaktive `msfconsole` ist ähnlich sensibel: [GTFOBins dokumentiert deren `irb`-Konsole](https://gtfobins.org/gtfobins/msfconsole/), die die sudo-Identität übernehmen kann. Bestätige den wirksamen RunAs-Benutzer, die erlaubte Argumentliste, Befehlsverbote, `NOEXEC` oder andere Einschränkungen, das Verhalten der installierten Konsole und ob der Aufrufer interaktive Eingaben liefern kann. Eine hervorgehobene Pfadangabe allein ist nur ein Prüfhinweis; bei einer passiven Bestandsaufnahme sollte die Konsole nicht gestartet werden.

Auf FreeBSD verdient selbst eine auf `pkg update` und `pkg install *` als root beschränkte sudo-Regel eine Prüfung des Repository-Vertrauens. Prüfe, ob `/etc/hosts` für den Aufrufer beschreibbar ist und ob die *wirksame* aktivierte Repository-Konfiguration einen HTTP-Hostnamen mit `signature_type: none` verwendet. Laut [Handbuch zu FreeBSDs `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) deaktiviert `none` die Signaturprüfungen; `pkg+http` allein belegt das nicht. Ein Paket kann Installationsskripte enthalten ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)); wer den Repository-Endpunkt tatsächlich kontrolliert und ein Paket auswählen kann, kann dadurch die root-Grenze überschreiten. Prüfe Repository-Überschreibungen, SRV-/Mirror-Auflösung, wirksame sudo-Argumente, Paketauswahl und Skriptausführung, bevor du zu diesem Schluss kommst. Untersuche Richtlinien und kleine lokale Konfigurationsdateien, ohne Namen umzuleiten oder `pkg` bei der Bestandsaufnahme auszuführen.

Ein root-fähiger sudo-Eintrag für `apt-get update` und `apt-get upgrade` erfordert ebenfalls eine Prüfung des Repository-Vertrauens, wenn sudo ein vom Aufrufer kontrolliertes `http_proxy` beibehält. Prüfe, ob die wirksame APT-Proxy-Konfiguration diese Variable tatsächlich verwendet und welche aktivierten Repository-Anfragen davon betroffen sein können; ein Proxy allein kann keine Pakete aus einem Archiv ersetzen, das mit einem vertrauenswürdigen Signaturschlüssel authentifiziert wird. [APT-Handbuch zum HTTP-Transport](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) beschreibt die Proxy-Priorität, und [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) beschreibt Signaturprüfungen, Überschreibungen für unsichere Repositories und die Bestätigung für nicht authentifizierte Pakete. Bestätige den genauen sudo-RunAs-Benutzer und die Argumente, die Repository-Authentifizierungsrichtlinie, erforderliche interaktive Bestätigungen und ob das ausgewählte Upgrade Paket-Skripte als root ausführt. Prüfe Richtlinien und lokale Konfiguration passiv; leite bei der Bestandsaufnahme keinen Paketverkehr um und führe kein Upgrade aus.

Eine root-fähige sudo-Regel für `snap install` kann eine Grenze zwischen Paket und Code darstellen, wenn ihre Argumente dem Aufrufer erlauben, einen lokalen Snap und einen permissiven Installationsmodus auszuwählen. [Snap dokumentiert](https://snapcraft.io/docs/explanation/snap-development/install-modes/), dass `--dangerous` die Assertionsprüfungen lokaler Snaps überspringt und `--devmode` die Confinement-Einschränkungen lockert; [ein Installations-Hook kann bei der ersten Installation ausgeführt werden](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prüfe die genauen sudo-Argument- und RunAs-Regeln, wer die Snap-Datei kontrolliert, ob die installierte snapd-Version diese Modi akzeptiert und welche Identität und Confinement-Einstellungen für den Hook gelten, bevor du den Zugriff auf geschützte Host-Dateien annimmst. Eine `snap`-Binärdatei oder eine scheinbare Wildcard-Regel allein belegt diese Kette nicht. Bei einer passiven Bestandsaufnahme sollte kein Paket installiert und kein Hook ausgeführt werden.

Bei einem exakten sudo-Eintrag für ein benutzerdefiniertes Programm zum Auslesen von Zugangsdaten unter einem **Nicht-root-Konto** solltest du zuerst die freigegebene Binärdatei und ihre Dateiberechtigungen prüfen, ohne sie auszuführen. Ein eingebettetes Passwort kann nur als Wide Characters sichtbar sein; [GNU `strings` dokumentiert die Extraktion von 16-Bit-Little-Endian-Strings](https://sourceware.org/binutils/docs/binutils/strings.html). Ein sichtbarer String beweist weder, dass es sich um das akzeptierte Passwort handelt, noch, dass der Erfolgszweig aktuelle Zugangsdaten offenlegt. Bestätige das Verhalten der Binärdatei, den Zugriff des Zielkontos auf die geschützten Daten, die Gültigkeit der Zugangsdaten und einen möglichen späteren Wechsel von Konto oder Gruppe separat. Gehört dieses Konto zu `docker`, überprüfe den Socket-Zugriff und ob der Daemon rootful oder rootless läuft, bevor du auf Host-root-Zugriff schließt; [Docker dokumentiert die Auswirkungen der Gruppenmitgliedschaft auf root-Ebene](https://docs.docker.com/engine/install/linux-postinstall/). Eine routinemäßige Bestandsaufnahme sollte die sudo-Regel und die Gruppenmitgliedschaft melden, ohne die Binärdatei auszuführen oder ihre Strings auszugeben.

Eine Wildcard-sudo-Regel für Wartungsskripte einer Anwendung sollte nicht nur anhand des Skriptpfads geprüft werden. Prüfe, ob das erlaubte Skript uneingeschränkte Argumente akzeptiert oder Einstellungen ausliest, die ein weniger privilegiertes Anwendungskonto ändern kann, und verfolge diese Werte bis zu Shell-Befehlen oder einer Subprozess-Umgebung. Beispielsweise setzt ZoneMinders [`zmupdate.pl` einen `mysqldump`-Befehl zusammen und führt ihn über `qx` aus](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), während [`zmdc.pl` die Einstellung `ZM_LD_PRELOAD` in `LD_PRELOAD` übernimmt](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in), bevor Daemons gestartet werden. Eine sudo-Regel, die eines dieser Skripte als root erlaubt, kann eine Vertrauensgrenze überschreiten, wenn die entsprechende Eingabe kontrollierbar ist und im installierten Skript diese Stelle erreicht. Prüfe die wirksame sudo-Regel, die Schreibrechte für die Anwendungskonfiguration und den Skriptquellcode. Die Wildcard oder Einstellung allein ist ein Prüfhinweis, kein Nachweis der Ausführung.

- `SETENV`, `env_keep`, `secure_path` und `LD_PRELOAD` können aus einem ansonsten eng begrenzten Befehl einen Hijack von Imports, Bibliotheken oder PATH machen. Siehe den [Leitfaden zu Umgebungsvariablen](../linux-basics/linux-environment-variables.md) und [SUID-/Linker-Missbrauch](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Auch ein exakter, root-fähiger `SETENV`-Eintrag für einen Shell-Wrapper verdient eine Prüfung über einen Hop, wenn der Wrapper ein festes Python-Skript mit einem literalen Import startet. `secure_path` beschränkt die Shell-Befehlsauflösung, nicht die Python-Modulsuche über [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` und `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) sorgen dafür, dass Python diese Umgebungsvariable ignoriert. Bestätige die wirksamen sudo-Tags und Verbote, den Wrapper-Zweig, die Interpreteroptionen, die Importauflösung und ein vom Aufrufer beschreibbares Suchverzeichnis, bevor du dies als Codeausführung einstufst. Untersuche kurze Skripte statisch; rufe den privilegierten Wrapper nicht auf.

Ein exakter, root-fähiger sudo-Eintrag für `neofetch ""` kann dennoch eine Shell-Konfiguration laden, wenn die anwendbaren sudo-Defaults ein vom Aufrufer kontrolliertes `XDG_CONFIG_HOME` beibehalten. [Neofetchs Konfigurationslader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) lädt `neofetch/config.conf` oder `neofetch/config` aus diesem Verzeichnis; die leere Argumentliste verhindert diese Suche nicht. Bestätige den installierten Loader, die wirksame RunAs- und Argumentrichtlinie, etwaige Befehlsverbote, ob sudo die ausgewählte Variable für diesen Befehl tatsächlich beibehält und ob der Aufrufer einen lesbaren Konfigurationspfad kontrolliert. Eine beibehaltene Variable oder ein installiertes Neofetch ist jeweils nur ein Prüfhinweis. Untersuche Richtlinien und Dateimetadaten, ohne den privilegierten Befehl aufzurufen oder Konfigurationsinhalte auszugeben; siehe [Umgebungsbehandlung in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Ein uneingeschränkter, root-fähiger sudo-Eintrag für `facter` verdient eine separate Prüfung auf benutzerdefinierte Facts. [Puppet dokumentiert](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), dass `--custom-dir` Ruby-Fact-Dateien aus einem ausgewählten Verzeichnis lädt. Prüfe, ob die genaue sudo-Regel diese Option erlaubt, ob der installierte Facter sie akzeptiert und ob der Aufrufer das Verzeichnis kontrolliert. Ein Eintrag mit festen Argumenten, ein ausdrückliches Befehlsverbot oder deaktivierte benutzerdefinierte Facts können das Ergebnis ändern. Bei einer passiven Bestandsaufnahme sollte der mögliche Richtlinieneintrag gemeldet werden, ohne Facter aufzurufen oder Fact-Inhalte zu lesen.

Bei einem exakten, root-fähigen sudo-Skripteintrag mit `SETENV` solltest du einfache Befehlsnamen wie `find` und den wirksamen `PATH` nach Anwendung der sudo-Richtlinie und Skriptinitialisierung prüfen. Eine eingebundene Bash-Datei kann außerdem `enable -n [` ausführen: [Bash sucht dann über `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) nach einem externen `[` für spätere Aufrufe dieses Befehls im Skript. Bestätige die anwendbaren [sudoers-Regeln für Umgebung und `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), etwaige `NOSETENV`-/`NOEXEC`- oder Verbotsregeln, den Ablauf des Skripts und eingebundener Dateien sowie ein ausführbares, vom Aufrufer kontrolliertes Suchverzeichnis. Ein lesbares Skript mit einem einfachen Befehlsnamen ist nur ein Prüfhinweis, kein Nachweis privilegierter Ausführung; untersuche es, ohne die sudo-Regel aufzurufen.
- Ein privilegiertes Skript, das eine feste URL mit `curl` abruft, kann dennoch eine vom Aufrufer ausgewählte Antwort akzeptieren, wenn eine anwendbare sudo-Regel `http_proxy` beibehält und die Anfrage über diesen Proxy gesendet wird. Übergibt das Skript die Antwort anschließend an einen XML-Parser, der externe Entities auflöst, kann eine manipulierte Antwort Dateien offenlegen, die der privilegierte Prozess lesen kann. Prüfe die genaue sudo-Umgebungsrichtlinie, `no_proxy`-Ausnahmen, die angeforderte URL, die Parserkonfiguration und das Ausgabeziel; eine Proxy-Variable oder ein XML-Parser allein ist keine Schwachstelle. Die [Dokumentation zur Proxy-Umgebung von curl](https://everything.curl.dev/usingcurl/proxies/env.html) beschreibt das Verhalten der Variablen. Führe bei einer passiven Bestandsaufnahme keine Netzwerkanfragen aus und parse kein manipuliertes XML.
- Ein root-fähiges sudo-Skript, das aus vom Aufrufer beeinflussten Daten eine PostScript-Datei erstellt und anschließend `ps2pdf -dNOSAFER` ausführt, verdient eine separate Prüfung des Eingabeflusses. Laut Ghostscript deaktiviert dieses Flag SAFER bis zu `.setsafe` und erlaubt PostScript-Dateioperationen innerhalb der Betriebssystemberechtigungen des Prozesses. Eine aus einem Aufruferargument zusammengesetzte SQL-Abfrage kann vom Angreifer kontrollierte Zeilen in die PostScript-Vorlage einspeisen; ein Abfrage-String oder ein Aufruf von `ps2pdf` allein beweist jedoch nicht, dass die Daten ausführbare PostScript-Syntax erreichen. Bestätige die wirksame sudo-Regel, den genauen Weg von der Eingabe zur Vorlage, eine etwaige Maskierung, das Verhalten der installierten Ghostscript-Version und ob SAFER vor der Interpretation des Dokuments wieder aktiviert wird. Rufe bei einer passiven Bestandsaufnahme die privilegierte Konvertierung nicht auf. Siehe die [Ghostscript-Dokumentation zu `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Bei einer sudo-Regel für ein Shell-Skript solltest du beibehaltene Variablen mit dem Skript selbst vergleichen. Ein Ausdruck wie `if $CHECK_CONTENT; then` führt den expandierten Wert als Befehl aus. Wenn `CHECK_CONTENT` beibehalten wird, kann das Befehlsausführung ermöglichen, selbst wenn Skriptpfad und Argumente feststehen. Ob der Zweig erreichbar ist und die Umgebung tatsächlich beibehalten wird, muss für die jeweilige Regel geprüft werden.<sup>[[2]](#references)[[22]](#references)</sup>
- Ein durch sudo erlaubtes Python-Skript kann Code aus einem beschreibbaren Verzeichnis oder einer zwischengespeicherten `.pyc`-Datei importieren. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md) erläutert den Cache-Fall.
- Ein festes, durch sudo erlaubtes Python-Skript kann einen interaktiven Debugger offenlegen. Aufrufe wie `pdb.set_trace()` oder `pdb.post_mortem()` erlauben Python-Anweisungen im Kontext des debuggten Prozesses, wenn der Aufrufer den Breakpoint oder Exception-Handler erreichen **und den Eingabestrom des Debuggers kontrollieren kann**. Prüfe die genaue sudo-RunAs-Regel, Authentifizierung und Zweigbedingungen, die Erreichbarkeit der Exception, die Kontrolle über Terminal/Eingabe und ob der Debugger im selben privilegierten Prozess läuft. Eine Socket-Anfrage, die eine Exception auslöst, gewährt nicht automatisch Zugriff auf einen Debugger, der an ein anderes Terminal gebunden ist. [Python dokumentiert die Auswertung von Anweisungen im Debugger und den Post-mortem-Modus](https://docs.python.org/3/library/pdb.html); untersuche das Skript statisch, statt den privilegierten Handler bei der Bestandsaufnahme auszulösen.
- Ein festes, durch sudo erlaubtes Python-Skript kann auch ein Profilfeld aus einer Datenbank oder einem Unix-Socket lesen und an einen String anhängen, der später als **Format-String** für `str.format()` dient. [Ersetzungsfelder können Attributen und Mapping-Schlüsseln folgen](https://docs.python.org/3/library/string.html#format-string-syntax). Ein vom Angreifer kontrolliertes Feld kann daher Objekte untersuchen, die an `format()` übergeben werden, und daraus erreichbare Daten offenlegen, wenn das Ergebnis ausgegeben oder an einem für den Aufrufer lesbaren Ort gespeichert wird. Prüfe die wirksame sudo-RunAs-Identität, Schreibzugriff auf den konkreten Datensatz, den Datenfluss in den Format-String, die übergebenen Objekte und die Sichtbarkeit der Ausgabe. Dies ist keine automatische Codeausführung; ein literaler, vertrauenswürdiger Format-String mit vom Angreifer kontrollierten *Werten* ist ein anderer Fall. Ein offengelegtes Geheimnis führt nur dann zu einem OS-Kontowechsel, wenn das Konto es akzeptiert. Prüfe Skript und Socket-Berechtigungen, ohne den privilegierten Vorgang aufzurufen.
- Ein root-fähiger Python-Wrapper kann eine vom Aufrufer ausgewählte URL an GitPythons `Repo.clone_from` übergeben. Aktiviert der Wrapper außerdem Git mit `protocol.ext.allow=always`, kann ein `ext::`-Remote einen externen Helfer aufrufen. Prüfe die genauen sudo-Argumente, die Herkunft der URL, die GitPython-Paketversion und mögliche Hersteller-Patches sowie, ob der Wrapper unsichere Protokolle ausdrücklich zulässt. GitPython ergänzte in Version 3.1.30 eine [standardmäßige Sperre für unsichere Protokolle](https://github.com/gitpython-developers/GitPython/commit/2625ed9); die Version der ausführbaren `git`-Datei ist davon unabhängig. Eine passive Prüfung sollte nur die Regel und einen begrenzten Quellcodeausschnitt lesen, ohne den Klon aufzurufen.
- Eine sudo-Freigabe für ein Klon-CLI unter einem anderen Benutzer kann einen separaten Pfad für Shell-String-Injection eröffnen. Verfolge, ob das vom Aufrufer ausgewählte Repository-Argument ohne sichere Trennung der Argumente an Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) oder einen anderen Shell-Befehlsaufbau gelangt; Node führt den Befehls-String von `exec` über eine Shell aus. Bestätige den genauen RunAs-Benutzer, erlaubte Unterkommandos und Argumente, den installierten Wrapper-Code und die Eingabevalidierung. Der Name eines Repository-Tools oder eine uneingeschränkte sudo-Regel allein beweist keine Befehlsinjektion. Untersuche den Wrapper, ohne bei der Bestandsaufnahme einen privilegierten Klon auszuführen.
- Ein benutzerdefinierter, root-eigener Wrapper kann sicher erscheinen, weil seine Binärdateien und Skripte nicht beschreibbar sind. Die Entscheidung, eine privilegierte Aktion auszuführen, kann jedoch von einem Flag, einem lokalen API-Wert oder einem Dienststatus abhängen, den ein unprivilegierter Benutzer ändern kann. Verfolge jede Bedingung bis zu ihrer Eingabe und den zugehörigen Autorisierungsprüfungen zurück. Untersuche bei der Bestandsaufnahme Konfiguration und Berechtigungen, ohne den Betriebszustand zu ändern; ein `systemd-run`-Aufruf im Wrapper ist nur relevant, wenn die Bedingung beeinflusst werden kann.
- Ein Backup-Client, der über sudo als root erlaubt ist, kann eine vom Aufrufer ausgewählte Konfigurationsdatei akzeptieren (zum Beispiel `npbackup-cli -c`). Prüfe den genauen RunAs-Benutzer und die erlaubten Argumente sowie, ob der Aufrufer den Konfigurationspfad, Quellpfade des Backups und Repository- oder Lese-/Wiederherstellungsoptionen kontrolliert. Ein verschlüsseltes Repository-Geheimnis in einer lesbaren Konfiguration kann für den Client dennoch nutzbar sein; die Regel allein beweist aber weder Repository-Zugriff noch die Offenlegung von root-Dateien. Prüfe die Autorisierung, ohne ein Backup auszuführen oder dessen Inhalte auszugeben.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) unterstützt `--password-command`, das ein Programm zum Abrufen des Repository-Passworts aufruft. Erlaubt eine sudo-Regel einem weniger privilegierten Benutzer, Restic als root mit einem vom Aufrufer ausgewählten Passwortbefehl und einem passwortpflichtigen Unterkommando auszuführen, kann dieser Helfer als root laufen. Prüfe die genauen sudo-Argumente und Ausschlüsse; rufe den Helfer oder einen Backup-Befehl nicht allein zur Bestandsaufnahme auf.
- Eine privilegierte Freigabe von `restic backup` kann auch eine Grenze für Dateizugriffe überschreiten, wenn das sudo-Argumentmuster dem Aufrufer erlaubt, sowohl die Quelle als auch ein Repository auszuwählen, das er später lesen und entschlüsseln kann. [Argument-Wildcards in sudoers können Whitespace und Schrägstriche enthalten](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf); prüfe daher nachgestellte Wildcards, statt anzunehmen, dass ein festes Repository-Präfix die Quelle einschränkt. [Restic kann in lokale und entfernte Repositories sichern](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), aber ein lokales Repository kann neu geschriebene, nur für root zugängliche Objekte enthalten. Bestätige die wirksame sudo-Richtlinie, Backend-Zugriff, Repository-Passwort und Berechtigungen der resultierenden Objekte, bevor du dies als Offenlegung einstufst. Ein gesicherter SSH-Schlüssel gewährt nur dann Zugriff, wenn das Zielkonto ihn akzeptiert. Führe bei einer passiven Prüfung kein Backup zu Testzwecken aus.
- Ein uneingeschränkter benutzerdefinierter Wartungs- oder Backup-Befehl kann einen Ausgabepfad akzeptieren oder einen eigenen Job-Scheduler anbieten. Prüfe bei einem Dateischreibpfad die genaue sudo-Regel und den RunAs-Benutzer sowie, ob der Aufrufer sowohl Daten als auch Ziel kontrolliert. Prüfe bei einem geplanten Befehl die Ausführungsidentität des Schedulers, die Befehlseingabe und eine mögliche zusätzliche Passwort- oder Autorisierungsschranke. Der Befehlsname oder `NOPASSWD` allein beweist keinen der beiden Wege. Siehe [Schreiben in root-eigene Dateien](../interesting-files-permissions/write-to-root.md) und [cron und systemd-Timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Ein fester sudo-Befehl kann weiterhin eine vorhersehbare Konfigurationsdatei aus einem gemeinsam beschreibbaren Verzeichnis laden. Verfolge, ob der Aufrufer diese Datei ersetzen kann und ob ihre Quell- und Zielfelder einen privilegierten Abruf oder Kopiervorgang steuern. Eine URL zu einer lokalen Datei kann Daten offenlegen, die nur das sudo-RunAs-Konto lesen kann; eine vom Aufrufer kontrollierte Quelle in Verbindung mit einem geschützten Ziel kann einen Schreibpfad schaffen. Bestätige das URL-Verhalten des installierten Programms, Zielpfadprüfungen, die wirksame sudo-Regel und die Zugänglichkeit der Ausgabe. Ein beschreibbarer Konfigurationspfad unter `/tmp` allein ist nur ein Prüfhinweis; untersuche Binärdatei und Dateimetadaten, ohne den privilegierten Transfer aufzurufen.
- Eine sudo-Regel für `git apply` kann das RunAs-Konto Dateien schreiben lassen, die ein vom Aufrufer kontrollierter Patch auswählt. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) ermöglichte es einem präparierten Patch, einen Symlink zu erstellen und anschließend außerhalb des Arbeitsbaums zu schreiben, selbst wenn der Befehl `--unsafe-paths` nicht akzeptierte. Prüfe die wirksame sudo-Argumentregel, die Patch-Quelle, den Zugriff des RunAs-Kontos auf das Arbeitsverzeichnis und die installierte Git-Korrektur oder einen Hersteller-Backport. Eine uneingeschränkte Regel, die `--unsafe-paths` zulässt, stellt ein separates explizites Optionsrisiko dar; weder eine Git-Version noch die Berechtigung für `git apply` allein beweist, dass eine geschützte Datei geändert werden kann. Wende bei einer passiven Bestandsaufnahme keinen nicht vertrauenswürdigen Patch an.
- Eine root-fähige sudo-Regel für `clamscan --debug` kann eine Grenze für Dateizugriffe überschreiten, wenn ein weniger privilegierter Benutzer ein DMG-Image bereitstellen kann und der installierte Parser von [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) betroffen ist, wodurch Dateiinhalte über die Debug-Ausgabe offengelegt werden konnten. Bestätige die genau erlaubten Argumente und den Scan-Pfad, die Kontrolle über die Eingabe, das wirksame RunAs-Konto, die Korrektur oder den Backport der Engine und ob die Ausgabe für den Aufrufer sichtbar ist. Erlaubt eine umfassendere Regel `--file-list`/`-f`, prüfe dieses Verhalten separat; eine auf `--debug <scan-path>` beschränkte Richtlinie lässt es nicht zu. Untersuche Richtlinie und Paketmetadaten, ohne bei der Bestandsaufnahme eine präparierte Datei zu scannen oder geschützte Ausgaben anzuzeigen.
- Eine root-fähige sudo-Regel, die ein vom Aufrufer ausgewähltes verschlüsseltes Disk-Image öffnet, und eine zweite Regel, die das daraus resultierende Mapper-Gerät einbindet, können vom Aufrufer kontrollierte Dateien in den Mount-Namespace des Hosts importieren. Bestätige beide wirksamen Regeln und ihre Argumente, die Kontrolle über Image und Mapper-Namen, das tatsächliche Einbindungsziel sowie Eigentümer und Modus der resultierenden Dateien. Ein Set-User-ID-Übergang erfordert zusätzlich eine zugängliche ausführbare Datei, Mount-Optionen, die das berücksichtigen (`nosuid` verhindert es), sowie anwendbare Prozess- oder MAC-Richtlinien; das Öffnen oder Einbinden eines Images allein ist nur ein Prüfhinweis. Ein separater Weg über ein vorhandenes Backup erfordert den tatsächlichen Schlüssel und ein brauchbares, lesbares Geheimnis darin. Untersuche Richtlinie und Pfade, ohne bei der passiven Prüfung ein Image zu öffnen oder einzubinden. Siehe das [cryptsetup-Handbuch](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) und die [Mount-Optionen](https://man7.org/linux/man-pages/man8/mount.8.html).
- Eine root-fähige sudo-Regel für ein Shell- oder Python-Skript verdient eine Prüfung des Arbeitsverzeichnisses, wenn das Skript `./helper` aufruft, ohne vorher in ein festes Verzeichnis zu wechseln. Eine Python-Liste wie `['./helper']`, die an `subprocess.run` übergeben wird, kann dasselbe Verhalten mit dem vom Aufrufer ausgewählten Arbeitsverzeichnis haben. Der Aufrufer kann möglicherweise ein beschreibbares Verzeichnis auswählen und dort eine ausführbare Datei mit diesem relativen Namen ablegen; ein absoluter Pfad an anderer Stelle im Skript schützt diesen Aufruf nicht. Bestätige die wirksame Regel, `runchdir` oder eine andere Richtlinie zum Verzeichniswechsel, den Skriptablauf und die Erreichbarkeit des Zweigs, ein beschreibbares und ausführbares Verzeichnis sowie Mount- und `NOEXEC`-Einschränkungen, bevor du dies als Codeausführung einstufst. Ist das Skript nicht lesbar, bleibt das Verhalten unbekannt, bis der Quellcode über einen autorisierten Weg geprüft wurde. Prüfe Skripte statisch, statt den Helfer auszuführen. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) dokumentiert die Richtlinie für Arbeitsverzeichnisse.
- Ein fester, root-fähiger Python-Validator kann weiterhin eine vom Aufrufer ausgewählte Datendatei auswerten. [Pythons Dokumentation zu `eval()` warnt vor nicht vertrauenswürdiger Eingabe](https://docs.python.org/3/library/functions.html#eval): Eine Suffixprüfung der Eingabe, ein arithmetischer Präfix oder ein Validierungszweig ist keine Sandbox, wenn der verbleibende Ausdruck `eval` erreicht. Bestätige die wirksame sudo-Regel, ob der Aufrufer die konkrete Datei auswählen und kontrollieren kann, die Zweigbedingungen des Parsers und den Ausdrucksaufbau sowie die Identität des privilegierten Prozesses, bevor du dies als Ausführungspfad einstufst. Das Vorkommen von `eval` in einem lesbaren Skript allein ist nur ein Prüfhinweis; untersuche Quellcode und Dateiberechtigungen, ohne den Validator auszuführen oder bei der Bestandsaufnahme einen Testausdruck einzureichen.
- Ein root-fähiger sudo-Ruby-Wrapper, der einen relativen YAML-Dateinamen wie `YAML.load(File.read("dependencies.yml"))` liest, kann Eingaben aus dem Arbeitsverzeichnis des Aufrufers beziehen, sofern der Wrapper oder die sudo-Richtlinie dieses Verzeichnis nicht festlegt. Prüfe die genau erlaubten Argumente, Verzeichnis- und Dateiberechtigungen sowie das Verhalten der installierten Psych-Version: Ältere Implementierungen von `YAML.load` konnten beliebige Ruby-Objekte deserialisieren, während neuere Versionen Klassen standardmäßig einschränken. Ein statischer Aufruf ist nur ein Prüfhinweis; bestätige, dass die Datei tatsächlich aus einem vom Aufrufer beschreibbaren Verzeichnis stammt und der installierte Loader gefährliche Klassen akzeptiert. Für nicht vertrauenswürdige Eingaben solltest du `safe_load` mit einer ausdrücklich festgelegten, minimalen Klassen-Allowlist bevorzugen. Siehe die [Ruby-3.0-Psych-Dokumentation](https://docs.ruby-lang.org/en/3.0/Psych.html) und die [Ruby-3.1-Psych-Dokumentation](https://ruby-doc.org/core-3.1.2/Psych.html).

- Ein exakter, root-fähiger Eintrag für `sudo go run /absolute/file.go` verdient eine Prüfung des Arbeitsverzeichnisses, wenn der Go-Quellcode eine relative WASM-Datei liest und nach Prüfung ihres Ergebnisses möglicherweise ein relatives Shell-Skript ausführt. Bestätige den wirksamen RunAs-Benutzer, Befehlsargumente und Verbote, ein vom Aufrufer beschreibbares aktuelles Verzeichnis, den Datenfluss von WASM zum Zweig und ob dieser Zweig den Helfer aufruft. Ein festes sudo-`runchdir`, `os.Chdir` oder [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) kann das Suchverzeichnis ändern. Ein statisches gemeinsames Auftreten ist lediglich ein möglicher Kandidat; untersuche den Quellcode, ohne Go, WASM oder den Helfer auszuführen.
- `sudoedit` und Argument-Wildcards erfordern eine genaue Prüfung der Version und Regel; die [Checkliste](linux-privilege-escalation-checklist.md) behandelt das Problem der Dateibearbeitung mit sudoedit. Bei einer `sudoedit`-Freigabe für einen anderen Benutzer mit einem Wildcard-Pfad solltest du die wirksame Einstellung `sudoedit_follow` oder `FOLLOW`, `sudoedit_checkdir`, das aufgelöste Ziel und prüfen, wer jeden übergeordneten Verzeichniseintrag ersetzen kann. Erstere kann das Folgen eines Symlinks erlauben; durch Deaktivieren der Letzteren entfallen Prüfungen beschreibbarer Verzeichnisse. Keine der beiden Einstellungen allein belegt einen Schreibzugriff auf die Datei eines anderen Benutzers. Bestätige die installierte sudo-Richtlinie und die genau passenden Argumente, bevor du zu diesem Schluss kommst. Siehe die [sudoers-Optionsdefinitionen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In einer sudoers-Befehlsregel kann eine Argument-Wildcard Whitespace ebenso wie Pfadzeichen erfassen. Eine Regel für einen lesefähigen Befehl mit einem Argument wie `/restricted/*` kann daher nach einem passenden Präfix ein zusätzliches Dateiargument zulassen. Prüfe den genauen RunAs-Benutzer, den Befehlspfad, das Argumentmuster und spätere Verbote; ein nachgewiesener Dateizugriff bedeutet nicht automatisch Befehlsausführung. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unterscheidet Argument-Globs von Befehlsweg-Globs.
- Ein pfadähnliches Argument-Glob kann auch `../` erfassen. Beispielsweise kann eine root-fähige Regel `node /opt/scripts/*.js` eine vom Aufrufer kontrollierte JavaScript-Datei außerhalb von `/opt/scripts` erlauben, wenn der angegebene Pfad weiterhin mit `/opt/scripts/` beginnt und über übergeordnete Verzeichnisse aufgelöst wird. Dies ist ein **Argument**-Glob; für den Befehlsweg-Glob der Node-Binärdatei gelten andere Regeln zur Übereinstimmung mit Schrägstrichen. Prüfe die wirksame Regel, spätere Verbote, die Pfadauflösung, die Kontrolle über die Zieldatei und etwaige sudoers-Regex- oder Digest-Einschränkungen, bevor du auf Codeausführung schließt. Siehe die [sudoers-Wildcard-Regeln](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) und die [Node-Befehlszeilendokumentation](https://nodejs.org/api/cli.html).
- Archivierungsprogramme und andere Dienstprogramme können Ausführungshooks bieten. Vergleiche die genau erlaubten Argumente mit [GTFOBins](https://gtfobins.github.io/), statt anzunehmen, nur Shells oder Interpreter könnten Befehle ausführen.
- Eine uneingeschränkte, root-fähige `qpdf`-Regel kann über PDF-Anhänge eine privilegierte Datei offenlegen: qpdf 10.2 und neuere Versionen unterstützen `--empty` und `--add-attachment file ... --` zusammen mit einer Ausgabe-PDF. Wenn der privilegierte Prozess die ausgewählte Quelle lesen und die PDF an einen für den Aufrufer zugänglichen Pfad schreiben kann, kann diese Ausgabe die Quelldaten enthalten. Prüfe die wirksamen sudo-Argumente und Ausschlüsse, die qpdf-Version, den Zugriff auf die Quelle und den Ausgabepfad, bevor du auf eine mögliche Dateioffenlegung schließt. Das Lesen eines root-SSH-Schlüssels ist für eine Anmeldung nur dann nützlich, wenn der Schlüssel gültig ist und SSH-Authentifizierung für root erlaubt ist. Siehe die [qpdf-Optionen für Anhänge](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Die Wiederverwendung von sudo-Zeitstempeln hängt von der Cache-Richtlinie, dem besitzenden Benutzer, Terminal/Sitzung und den Berechtigungen ab. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) beschreibt die Prüfungen.
- `doas` hat eigene Regeln und Konfiguration. Prüfe erlaubte Befehle und beschreibbare Konfigurationspfade wie im [doas-Abschnitt](../linux-basics/linux-privilege-escalation/README.md#doas) beschrieben.

### Mit sudo ausgeführte Build- und Paketwerkzeuge

Eine uneingeschränkte sudo-Freigabe für Foundrys `forge` kann relevant sein, selbst wenn die RunAs-Identität ein anderer Nicht-root-Benutzer ist. Compileroptionen wie `--use` können eine lokale ausführbare Datei auswählen, und `forge flatten -o` wählt eine Ausgabedatei. Prüfe die installierte Forge-Version, die genauen sudo-Argumente, zugängliche Projekt- und Compilerpfade, Ausgabeberechtigungen und die wirksame Umgebung, bevor du die Freigabe als ausnutzbar einstufst. Eine relative Hilfsdatei, die über `PATH` gefunden wird, ist ein von Version und Umgebung abhängiger Pfad und keine Eigenschaft, die für jeden Forge-Build angenommen werden sollte.<sup>[[23]](#references)[[24]](#references)</sup>

Eine uneingeschränkte, root-fähige `pacman`-Freigabe erlaubt mehr als Paketabfragen: `-U` akzeptiert ein lokales Paket, Pakete können Installationsskripte enthalten und `--hookdir` wählt ein anderes Hook-Verzeichnis. Prüfe die wirksame sudo-Regel sowie Argumentbeschränkungen und Ausschlüsse, bevor du testest; eine passive Bestandsaufnahme erfordert weder eine Paketinstallation noch die Ausführung eines Hooks.<sup>[[25]](#references)[[26]](#references)</sup>

Ein festes sudo-Shell-Wrapper-Skript kann auch eine benannte npm-Abhängigkeit installieren und anschließend eine Node-Anwendung starten. Prüfe die genaue RunAs-Regel, ob das Paket bereits installiert ist, das wirksame `HOME` und `userconfig` von npm, Projektkonfiguration oder Befehlszeilenüberschreibungen sowie, ob ein weniger privilegierter Benutzer die Registry oder das für diesen Namen gelieferte Paket kontrolliert. [npm dokumentiert die Suche nach `.npmrc` pro Benutzer und Projekt](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); das `HOME`-Verhalten von sudo hängt von der installierten Richtlinie und Distribution ab. Eine beschreibbare `.npmrc` eines Benutzers wird daher möglicherweise vom privilegierten npm-Prozess gelesen, möglicherweise aber auch nicht. Wird das neu installierte Paket von der privilegierten Anwendung importiert, kann dessen Modulcode unter der Identität der Anwendung ausgeführt werden. Installationsskripte sind ein separater, versions- und konfigurationsabhängiger Pfad; [npm dokumentiert deren Lebenszyklus und Benutzerbehandlung](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ein `.npmrc`-Pfad oder eine Zeile mit `npm install` allein ist nur ein Prüfhinweis. Untersuche die Regel, das kurze Wrapper-Skript, Konfigurationspfade und die Herkunft des Pakets, ohne bei einer passiven Bestandsaufnahme etwas zu installieren oder die Anwendung zu starten.

Eine root-fähige Freigabe für `pip` oder `pip3 download` ist ebenfalls ein Hinweis für eine Paket-Build-Prüfung, wenn die Argumente dem Aufrufer erlauben, eine nicht vertrauenswürdige Source Distribution auszuwählen – selbst wenn das URL-Muster auf einen lokalen Dienst und ein Suffix `.tar.gz` beschränkt ist. `pip download` akzeptiert Archiv-URLs und löst Paketmetadaten auf; das Vorbereiten einer sdist kann deren Build-Backend oder älteren `setup.py`-Code aufrufen, bevor das Archiv lediglich gespeichert wird. Bestätige den genauen sudo-RunAs-Benutzer und die Argumentregel, ob der Aufrufer das ausgewählte Archiv veröffentlichen oder ersetzen kann und ob diese pip-Version die Metadaten tatsächlich vorbereitet. Ein festes, vertrauenswürdiges Archiv oder Wheel belegt diesen Pfad nicht. Lade oder baue bei einer passiven Bestandsaufnahme kein nicht vertrauenswürdiges Paket. Siehe pips [download-Befehl](https://pip.pypa.io/en/stable/cli/pip_download/), die [Build-System-Schnittstelle](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Eine sudo-Regel, die `pip install` mit einem vom Aufrufer ausgewählten lokalen Projektpfad erlaubt, schafft eine direktere Build-Grenze. [pip akzeptiert lokale Projektverzeichnisse](https://pip.pypa.io/en/stable/topics/local-project-installs/) und ruft deren Build-System auf; das [Build-Backend führt vom Projekt kontrollierte Build-Hooks aus](https://pip.pypa.io/en/stable/reference/build-system/). Bestätige die wirksame RunAs-Identität, genaue Argumentbeschränkungen und Verbote, die Kontrolle über das ausgewählte Projekt sowie das Verhalten der installierten pip-/Backend-Version, bevor du die Regel als privilegierte Codeausführung einstufst. Ein festes, vertrauenswürdiges Projekt oder eine Regel, die vom Aufrufer ausgewählte Pfade ausschließt, belegt diesen Pfad nicht. Prüfe Regel und Projektmetadaten, ohne bei einer passiven Bestandsaufnahme ein Paket zu installieren.

Eine uneingeschränkte, root-fähige Freigabe für `easy_install` ist ein ähnlicher Hinweis auf einen älteren Paket-Build-Pfad. [Setuptools dokumentiert](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), dass Easy Install ein lokales Projektverzeichnis akzeptiert und Source Distributions baut; bei einem vom Aufrufer kontrollierten Projekt kann während dieses Builds `setup.py` unter der sudo-Identität ausgeführt werden. Bestätige das wirksame RunAs-Konto, die genauen Befehls- und Argumentbeschränkungen (einschließlich späterer Verbote), die Kontrolle über das ausgewählte Projekt und das Verhalten des installierten Werkzeugs. Ein festes, vertrauenswürdiges Projekt oder eine Richtlinie, die keine vom Aufrufer ausgewählte Quelle erlaubt, belegt diesen Pfad nicht. Untersuche Regel und Projektmetadaten, ohne bei der Bestandsaufnahme ein Paket zu installieren.

Ein durch sudo erlaubtes Python-Wrapper-Skript, das `setuptools.package_index.PackageIndex.download` mit einer vom Aufrufer ausgewählten URL verwendet, ist ein anderer Prüfungsfall als `pip download`: [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) beschreibt, dass in betroffenen Versionen vor 78.1.1 ein aus der URL abgeleiteter Dateiname aus dem vorgesehenen Download-Verzeichnis ausbrechen und mit den Berechtigungen des Prozesses schreiben konnte. Bestätige die wirksame sudo-RunAs- und Argumentregel, dass das Wrapper-Skript die URL des Aufrufers an genau diese API übergibt, den installierten Build oder einen Hersteller-Backport und wohin der resultierende Pfad aufgelöst wird. Eine Versionsangabe oder ein beschreibbares Download-Verzeichnis allein belegt keinen beliebigen Schreibzugriff. Prüfe das kurze Wrapper-Skript und Paketmetadaten, ohne die URL abzurufen oder bei der Bestandsaufnahme eine Datei zu schreiben.

Ein durch sudo erlaubtes Build-Wrapper-Skript, das eine vom Aufrufer ausgewählte `.spec`-Datei an PyInstaller übergibt, erfordert dieselbe Prüfung der Vertrauensgrenze. Eine PyInstaller-Spec-Datei ist während des **Builds** ausführbarer Python-Code, und ihre `datas`-Einträge können Dateien, die für die Build-Identität lesbar sind, in ein Artefakt aufnehmen. Bestätige den genauen RunAs-Benutzer, sudo-Argument- und Verbotsregeln, Pfad- und Zweigbehandlung des Wrapper-Skripts, die Kontrolle über die ausgewählte Spec-Datei und den Zugriff auf das resultierende Artefakt. Das bloße Erlauben einer `.py`-Eingabe oder die Feststellung, dass PyInstaller installiert ist, belegt weder die Kontrolle über die Spec-Datei noch eine privilegierte Ausführung. Bei einer passiven Prüfung sollten nur eine begrenzte Wrapper-Datei und Metadaten gelesen werden; ein Build sollte nicht ausgeführt werden. Siehe die [PyInstaller-Dokumentation zu Spec-Dateien](https://pyinstaller.org/en/stable/spec-files.html).

### Mit sudo ausgeführte Preset- und Plugin-Loader

Python-Werkzeuge, die ein vom Aufrufer ausgewähltes Preset- oder Plugin-Verzeichnis akzeptieren, können Code mit den durch sudo gewährten Berechtigungen importieren. BBOT akzeptiert beispielsweise ein Preset mit `-p`; die [Dokumentation zu benutzerdefinierten Modulen](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) beschreibt `module_dirs`-Einträge, mit denen zusätzliche Python-Modulverzeichnisse ausgewählt werden. Erlaubt die wirksame sudo-Regel ein vom Aufrufer ausgewähltes Preset und kontrolliert der Aufrufer ein Modul im ausgewählten Verzeichnis, kann der Import Code als privilegierter Benutzer ausführen – möglicherweise sogar, bevor das Werkzeug ein ungültiges Modul zurückweist. Prüfe die installierte Version, den genauen sudo-RunAs- und Argumentregeln sowie die Eigentümerschaft der Preset- und Modulpfade, ohne das Modul bei der Bestandsaufnahme zu laden.

### Mit sudo ausgeführtes Backdrop-Kommandozeilenwerkzeug

[Bee](https://github.com/backdrop-contrib/bee) ist ein PHP-Kommandozeilenwerkzeug für Backdrop CMS. Seine Befehle `eval` (`php-eval`) und `php-script` können vom Aufrufer bereitgestelltes PHP ausführen. Eine sudo-Regel, die die Bee-Datei als root mit uneingeschränkten Argumenten erlaubt, kann daher root-Codeausführung ermöglichen, wenn Bee eine Backdrop-Installation initialisieren kann. Führe es aus dem Website-Verzeichnis aus oder wähle eine Website über die globale Option `--root=<directory>` aus; Bee oder eine Backdrop-`settings.php`-Datei zu finden, beweist weder die sudo-Berechtigung noch eine nutzbare Website oder eine erfolgreiche Initialisierung. Prüfe die wirksame sudo-Regel, etwaige Befehlsausschlüsse, die Identität der ausführbaren Datei und den Zugriff auf die Website, bevor du testest. Untersuche bei einer passiven Bestandsaufnahme die Regel und Dateipfade, ohne Bee aufzurufen. Siehe das [Bee-Befehls-Changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) für die PHP-Befehle.

### Mit sudo ausgeführte Terminalserver

`mosh-server` startet einen interaktiven Terminalserver als aufrufender Benutzer. Er wählt einen hohen UDP-Port und einen Sitzungsschlüssel, meldet beides dem Aufrufer und startet normalerweise die Login-Shell dieses Benutzers, wenn ein Client eine Verbindung herstellt. Eine uneingeschränkte, root-fähige sudo-Freigabe für `mosh-server` ist daher ein Kandidat für eine Shell-Prüfung, auch wenn sich der Serverbefehl selbst abkoppelt. Prüfe die wirksame RunAs-Identität, erlaubte Argumente und Ausschlüsse, die installierte Binärdatei, die Shell, die Verfügbarkeit eines Clients und den UDP-Zugriff. Bei einer passiven Bestandsaufnahme sollte die sudo-Regel geprüft werden, ohne einen Server zu starten oder einen aktiven Sitzungsschlüssel auszugeben. Siehe das [Mosh-Server-Handbuch](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) und die [Designhinweise des Upstream-Projekts](https://github.com/mobile-shell/mosh#how-it-works).

### Privilegierte Backup-Wrapper, die die Task-Datei eines Aufrufers umschreiben

Ein als root ausgeführter Shell-Wrapper kann eine vom Aufrufer ausgewählte Task-Datei akzeptieren, `../` aus Quellpfaden entfernen, prüfen, ob jedes Ergebnis mit einem zulässigen Verzeichnis beginnt, die Task-Datei umschreiben und anschließend deren *Pfadnamen* an ein Backup-Programm übergeben. Prüfe den transformierten Pfad nach vollständiger kanonischer Auflösung: Bei einem einzigen String-Ersetzungsschritt kann eine neue Traversalsequenz entstehen, die eine lexikalische Präfixprüfung akzeptiert. Prüfe außerdem, ob das Backup-Programm die transformierten Daten aus dem Speicher liest oder die Datei erneut öffnet. Öffnet es die Datei erneut, kann eine fehlgeschlagene Umschreibung die Originaleingabe zurücklassen.

Unter Linux kann `fs.protected_regular` einen Schreibzugriff mit `O_CREAT` auf die reguläre Datei eines anderen Benutzers in einem Sticky-Verzeichnis mit weltweiten Schreibrechten verweigern. Diese Verweigerung ist ein Schutz. Ein Shell-Wrapper, der den Schreibfehler ignoriert, kann dennoch mit der ursprünglichen Task-Datei fortfahren. Bestätige die Einstellung, den Eigentümer der Datei und des Verzeichnisses sowie, ob der Wrapper bei einem Fehler abbricht. Der Pfad ist nur dann ein Kandidat für eine Dateioffenlegung, wenn die wirksame sudo-Regel den Wrapper als privilegierten Benutzer erlaubt, der Aufrufer die Task-Eingabe und ein lesbares Backup-Ziel kontrolliert und das Backup-Werkzeug geschützte Quellen tatsächlich aufnimmt. Untersuche diese Bedingungen, ohne bei der Bestandsaufnahme das Backup auszuführen.

### Argument-Wildcards bei privilegierten Paketwerkzeugen

In einer sudo-Regel für `tcpdump` kann ein `*` im **Argumentmuster** Whitespace und Schrägstriche erfassen, sodass eine pfadähnliche Einschränkung weiterhin zusätzlichen Optionstext zulassen kann. Das unterscheidet sich von einer Wildcard im ausführbaren Befehlspfad; prüfe die vollständige RunAs-Regel und etwaige spätere Verbote. Können Optionen eingeschleust werden, bestimmen der erlaubte Aufruf und die installierte [`tcpdump`-Optionssemantik](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), ob `-F`, `-V`, `-r`, `-w` oder `-Z` eine nützliche Lese- oder Schreibfunktion bietet. `-V` liest eine Liste von Capture-Dateinamen, nicht eine beliebige Datei als allgemeine Dateiausgabe. AppArmor oder eine andere MAC-Richtlinie kann den Dateizugriff verhindern, selbst wenn sudo den Befehl erlaubt; eine Profildatei auf der Festplatte beweist nicht, dass sie geladen ist oder durchgesetzt wird. Prüfe Autorisierung und Richtlinien passiv, bevor du zu einem Schluss kommst. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) beschreibt den Unterschied zwischen den Wildcards.

Eine root-fähige sudo-Regel, die nur die ausführbare Datei `tcpdump` auflistet und keine Argumentbeschränkung enthält, verdient ebenfalls eine Prüfung. Das [tcpdump-Handbuch](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) beschreibt `-z` als einen nach einer Rotation ausgeführten Befehl, wenn `-C` oder `-G` eine gespeicherte Aufzeichnung rotiert; `-Z` oder eine Build-Standardvorgabe kann Berechtigungen ablegen, bevor dieser Befehl läuft. Verifiziere die wirksame sudo-Regel, den installierten Build, das Verhalten beim Ablegen der Berechtigungen und ob eine Rotation stattfinden kann, bevor du die Regel als Pfad zur Rechteausweitung einstufst. Eine hervorgehobene Regel ist ein Kandidat, kein Nachweis für die Ausführung eines root-Befehls.

### Mit sudo ausgeführte Nmap-Wrapper

Wenn ein durch sudo erlaubter `nmap`-Pfad ein Shell-Wrapper ist, untersuche den genauen erlaubten Pfad und jede weitergereichte Option. Das Blockieren der bekannten Schreibweise `--script` blockiert das Laden von NSE-Code nicht notwendigerweise: Nmaps [`--datadir`](https://nmap.org/book/man-misc-options.html) wählt Datendateien aus, und NSE [lädt `nse_main.lua`](https://nmap.org/book/nse-implementation.html) aus dem ausgewählten Datenverzeichnis, wenn Scripting aktiviert ist. Einige installierte Builds akzeptieren außerdem alternative Langoption-Schreibweisen. Vergleiche daher die Einschränkungen mit dem tatsächlichen Parser dieser Binärdatei. [`--excludefile`](https://nmap.org/book/target-specification.html) bietet eine separate Fläche für Dateizugriffe; Parserfehler können Text offenlegen. Prüfe die wirksame sudo-Regel, die Wrapper-Logik, die Nmap-Version, die Kontrolle über Verzeichnisse und die MAC-Richtlinie, ohne bei der Bestandsaufnahme Scans auszuführen.

### Mit sudo ausgeführte Mercurial-Pull-Hooks

Eine feste Quelle in `sudo hg pull /fixed/source` lässt weiterhin das **Empfänger-Repository** durch das aktuelle Arbeitsverzeichnis auswählen, sofern der Befehl es nicht mit `-R` festlegt. Ein vom Aufrufer kontrolliertes Empfänger-Repository kann Hooks in `.hg/hgrc` definieren, und ein Hook kann als sudo-RunAs-Benutzer ausgeführt werden. [Mercurial ignoriert Repository-Konfigurationen, deren Eigentümer ein nicht vertrauenswürdiger Benutzer oder eine nicht vertrauenswürdige Gruppe ist](https://mercurial-scm.org/help/topics/config). Prüfe daher die vertrauenswürdigen Benutzer und Gruppen des RunAs-Kontos sowie das genaue Arbeitsverzeichnis, bevor du dies als Codeausführung einstufst. Für eine passive Prüfung genügt es, Richtlinie und Konfiguration zu lesen; führe kein Pull aus und rufe keinen Hook auf.

### Mit sudo ausgeführte Git-Pull-Hooks

Bei einer exakten, root-fähigen Freigabe für `sudo git pull` solltest du auch das durch das Arbeitsverzeichnis ausgewählte **Empfänger-Repository** prüfen. Ein Repository im Eigentum des Aufrufers kann einen ausführbaren `post-merge`-Hook enthalten, der mit der Identität des Git-Prozesses läuft, wenn ein Pull tatsächlich einen erfolgreichen Merge ausführt; [Git dokumentiert diesen Hook](https://git-scm.com/docs/githooks) und [das Merge- oder Rebase-Verhalten von pull](https://git-scm.com/docs/git-pull). Verifiziere die wirksame sudo-Regel und das aktuelle Arbeitsverzeichnis, den aktiven Hook-Pfad und dessen Berechtigungen sowie, ob ein Merge mit neuen Commits möglich ist. Ein fehlgeschlagener oder wirkungsloser Pull und ein Pull, der nur rebased, belegen diesen Hook-Pfad nicht. Prüfe Richtlinie und Repository-Metadaten, ohne den privilegierten Pull auszuführen.

### Mit sudo ausgeführte rsync-Archivkopien

Bei `sudo rsync -a ... /writable/source/* /fixed/destination/` kann ein `*` im **Argumentmuster von sudoers** Whitespace erfassen und zwischen Quelle und Ziel eine zusätzliche Option zulassen. Das ist nicht dasselbe wie die Shell-Erweiterung von Dateinamen. Wenn der Aufrufer die Quelle befüllen kann und das Ziel für den privilegierten rsync-Prozess beschreibbar ist, kann [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privilegierte Eigentümerschaft anfordern, während der Archivmodus Berechtigungsbits beibehält, was möglicherweise eine SetUID-Datei mit passendem Eigentümer erzeugt. Prüfe die genauen [sudoers-Wildcard-Semantiken](https://man7.org/linux/man-pages/man5/sudoers.5.html), die rsync-Version, spätere Verbote, das Dateisystem-Flag `nosuid` und die MAC-Richtlinie. Eine passende Regel ist ein Prüfhinweis, kein Nachweis einer erfolgreichen Rechteausweitung.

### Mit sudo ausgeführter Export von Paketfilterregeln

Eine uneingeschränkte, root-fähige Freigabe sowohl für `iptables` als auch `iptables-save` (oder das entsprechende `ip6tables`-Paar) verdient eine Prüfung auf Dateischreibzugriffe. Der `comment`-Match akzeptiert vom Aufrufer gewählten Regeltext, während `iptables-save -f` das serialisierte Regelwerk in einen ausgewählten Pfad schreibt.<sup>[[20]](#references)[[21]](#references)</sup> Ob eine nutzbare Nutzlast entsteht, hängt davon ab, wie das installierte Backend Kommentare serialisiert und ob die Zieldatei weitere Zeilen im Export akzeptiert; `iptables-save` allein ermöglicht keine beliebig wählbaren Inhalte. Prüfe die genaue sudo-RunAs-Identität, Argumente und Ausschlüsse, verfügbare Match-Erweiterungen, das Backend und die Zielberechtigungen. Untersuche bei der Bestandsaufnahme die Freigabe, ohne Firewall-Regeln zu ändern oder eine Datei zu schreiben.

### Privilegiertes Below-Protokollverzeichnis

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) betraf Below-Versionen vor 0.9.0, die ein Verzeichnis `/var/log/below` mit weltweiten Schreibrechten anlegten. Führt ein Dienst oder ein erlaubter sudo-Befehl einen betroffenen Build als root aus, kann ein Benutzer mit Schreib- und Suchrechten in einem Log-Verzeichnis ohne Sticky-Bit möglicherweise einen Logeintrag durch einen Symlink ersetzen, bevor der privilegierte Prozess ihn öffnet. Prüfe den Patch-Status des installierten Pakets, den genauen privilegierten Ausführungspfad, effektiven Verzeichniszugriff, Sticky-Bit und ACLs sowie die Metadaten von `/var/log/below/error_root.log`. Ein Pfad mit weltweiten Schreibrechten oder eine sudo-Regel allein belegt nicht die vollständige Kette. Ein Sticky-Verzeichnis oder Hersteller-Backport ändert die Bewertung. Bei einer passiven Bestandsaufnahme sollten nur Metadaten geprüft werden; ein Link muss weder erstellt noch das privilegierte Programm ausgeführt werden.

### Privilegierte Erfassung von Support-Bundles aus beschreibbaren Eingaben

Ein durch sudo erlaubtes Support-Profilskript kann feste Logpfade als root lesen und ihre Inhalte in ein Profilarchiv kopieren. Prüfe das tatsächliche Skript auf Dateizugriffe und anschließend, ob der Aufrufer einen Quellpfad oder einen übergeordneten Verzeichniseintrag durch einen Symlink ersetzen kann. Folgt der privilegierte Lesezugriff diesem Link und ist das resultierende Archiv für den Aufrufer lesbar, kann eine geschützte Datei offengelegt werden. Die sudo-Freigabe, ein beschreibbarer Quellpfad, der privilegierte Lesezugriff und eine lesbare Ausgabe müssen alle vorliegen; ein beschreibbares Log oder ein Profil-Dateiname allein reicht nicht aus. Untersuche die wirksamen Berechtigungen und Link-Metadaten, ohne bei der Bestandsaufnahme Dateien zu ersetzen oder ein Profil zu erstellen. Die [Support-Hinweise von Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) dokumentieren dessen als root ausgeführtes Profilskript und Ausgabe-Archiv und zeigen, warum Eingaben und Ausgabezugriff solcher Bundles eingeschränkt werden müssen.

### Als root ausgeführte Python-Archivwiederherstellungsskripte

Auch eine eng begrenzte sudo-Regel für ein Python-Wiederherstellungsskript erfordert eine Prüfung seiner Archiv-Eingabe. Kann der Aufrufer das Archiv auswählen oder ersetzen und extrahiert das Skript es als root mit `tarfile.extractall(filter="data")`, prüfe die Sicherheitsupdates des Interpreters, bevor du dem Filter vertraust. CPython behob mehrere Umgehungen des Symlink- und Hardlink-Filters, darunter CVE-2025-4517, in den Versionen 3.9.23, 3.10.18, 3.11.13, 3.12.11 und 3.13.4. Distributions-Backports können eine ältere Version korrigieren; die angezeigte Interpreterversion allein belegt daher keine Anfälligkeit.<sup>[[16]](#references)[[17]](#references)</sup>

Lies bei einer passiven Prüfung den genauen sudo-Befehl und das Skript, verfolge, welches Argument das Archiv auswählt, und prüfe, ob der aktuelle Benutzer das Archiv oder dessen übergeordnetes Verzeichnis beschreiben kann. Bestätige den installierten Hersteller-Patch und das Extraktionsziel separat; `filter="data"` macht nicht jedes nicht vertrauenswürdige Archiv sicher.<sup>[[16]](#references)[[17]](#references)</sup>

### Mit sudo ausgeführte Machine-Learning-Modell-Loader

Eine sudo-Regel, die eine vom Aufrufer ausgewählte `.pt`-, `.pth`- oder `.ckpt`-Datei zulässt, verdient eine Prüfung, wenn ein privilegiertes Skript diese Datei an [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` oder einen anderen Pickle-basierten Loader übergibt. Prüfe die wirksame RunAs-Regel, ob der Aufrufer das ausgewählte Modell erstellen oder ersetzen kann und wie das Argument durch einen Shell-Wrapper zum Python-Helfer gelangt. Die Erweiterung `.pth` bezeichnet auch unabhängige Konfigurationsdateien für Python-Site-Packages; die Erweiterung allein ist daher kein Beleg für das Laden eines Modells. Ein Archiv-Scan oder statischer Pickle-Scan belegt nicht, dass das spätere Laden sicher ist. Prüfe das [versionsabhängige Verhalten von `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) und etwaige Allowlists des Loaders. Siehe die [Hinweise zu ML-Pickle und Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). Bei einer passiven Bestandsaufnahme sollte das Modell niemals geladen oder entpackt werden.

### Mit sudo ausgeführtes Parsen gespeicherter Eingaben als Ausdruck

Ein festes, über sudo als root ausgeführtes Python-Skript kann weiterhin Text auswerten, den ein weniger privilegierter Benutzer in einer Anwendungsdatenbank speichern kann. In TensorFlow wählt ein Aufruf von `preprocess_input_exprs_arg_string(value, safe=False)` einen `eval`-Pfad; die [TensorFlow-Sicherheitsempfehlung](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) beschreibt den unsicheren Parser und eine Korrektur im Kommandozeilenaufrufer. Ein ausdrücklicher `safe=False`-Aufruf einer Anwendung muss separat geprüft werden, selbst wenn dieser Kommandozeilenaufrufer korrigiert wurde. Prüfe die wirksame sudo-Regel, wer die konkrete Eingabezeile ändern kann, ob Filterung oder Bewertung zulässt, dass diese Zeile den Aufruf erreicht, und wie sich die installierte Funktion verhält. Eine TensorFlow-Version, eine sudo-Freigabe oder eine fest codierte Modelldatei allein belegt die Kette nicht. Untersuche Skript und Datenfluss passiv; führe den privilegierten Helfer nicht aus und übermittle bei der Bestandsaufnahme keine Testausdrücke.

### Durch sudo erlaubte needrestart-Konfiguration

`needrestart -c` lädt eine vom Aufrufer ausgewählte Perl-Konfigurationsdatei und wertet deren Inhalt aus. Erlaubt `sudo -l` `needrestart` als root mit Argumenten, die `-c` zulassen, und kann der Aufrufer eine lesbare Konfigurationsdatei an einem beschreibbaren Ort auswählen, kann diese Berechtigung zu root-Codeausführung führen. Prüfe die genaue sudo-RunAs- und Argumentregel; eine Regel, die nur eine feste Argumentliste erlaubt, kann diesen Pfad blockieren. Dies ist unabhängig von den Interpreter-Scan-Schwachstellen in needrestart: Ein Paketupdate oder das Deaktivieren von `interpscan` macht eine uneingeschränkte root-Freigabe für `-c` nicht sicher.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Mit sudo ausgeführte Python-Imports unter einem anderen Konto

Ein fester Python-Einstiegspunkt kann weiterhin ein Modul importieren, das der Aufrufer bearbeiten oder ersetzen kann, auch wenn sudo das Skript als **Nicht-root-Dienstbenutzer** ausführt. Bei einem literalen `from utils import status` solltest du sowohl `utils/__init__.py` und `utils/status.py` als auch die Berechtigungen des Paketverzeichnisses prüfen. Bestätige den Importpfad des Skripts, die genau erlaubten sudo-Argumente und ob die relevante Aktion diesen Import erreicht, bevor du die beschreibbare Datei als Ausführungspfad einstufst. Untersuche Dateien und Berechtigungen, ohne das Skript bei der Bestandsaufnahme zu importieren oder auszuführen.<sup>[[2]](#references)[[3]](#references)</sup>

Eine exakte sudo-Regel für `python3 /absolute/script.py` benötigt lediglich ein lesbares Skript; die Datei muss weder ausführbar sein noch einen Shebang enthalten. Prüfe auch **fehlende** lokale Module: Importiert das Skript ein Modul, dessen Dateiname in einem vom Aufrufer beschreibbaren Skriptverzeichnis erstellt werden kann, lädt Python diese Datei möglicherweise unter der RunAs-Identität. Bestätige die wirksame sudo-Regel, den tatsächlichen [Modulsuchpfad](https://docs.python.org/3/library/sys_path_init.html) des Interpreters, ob das Modul eingebaut oder eingefroren ist und ob der Import erreicht wird. Eine direkte sudo-Regel für das Skript hat andere Anforderungen an Execute-Bit und Shebang. Auch ein separater Wrapper, der vom Aufrufer bereitgestellte Tokens hinter `sudo -u account` anhängt, erfordert eine Prüfung des Argumentflusses: Ein weiteres `-u` in diesen Tokens ist nur relevant, wenn die aufgerufene sudo-Richtlinie die resultierende Identität zulässt. Statische Strings allein beweisen keinen der beiden Pfade.

### Mit sudo ausgeführtes Apache mit vom Aufrufer kontrollierter Konfiguration

Erlaubt eine sudo-Regel einen privilegierten Aufruf von `apachectl`, `apache2ctl` oder `httpd` mit einer vom Aufrufer kontrollierten Konfigurationsdatei über `-f`, prüfe die Berechtigungen dieser Datei und ihrer übergeordneten Verzeichnisse. Apaches [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)-Direktive akzeptiert einen Modulnamen gefolgt vom **Dateinamen des Moduls**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) lädt ebenfalls eine Datei. [`Include` und `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) können die Konfiguration erweitern oder Dateiinhalte über Fehler offenlegen. Ein benutzerdefinierter Wrapper kann diese Pfade validieren, Berechtigungen ablegen oder Argumente einschränken. Eine beschreibbare Konfiguration ist daher ein Prüfhinweis, kein Nachweis für Codeausführung. Prüfe Pfadkanonisierung, Symlinks und das Parsen der Direktiven, bevor du zu einem Schluss kommst.

### Mit sudo ausgeführtes nginx mit vom Aufrufer kontrollierter Konfiguration

Eine uneingeschränkte, root-fähige `nginx`-Regel kann erlauben, mit [`-c` eine andere Konfiguration auszuwählen](https://nginx.org/en/docs/switches.html). Prüfe die genauen sudo-Argumente und Ausschlüsse, ob der Aufrufer die Konfiguration bereitstellen kann und ob der resultierende Master oder die Worker weiterhin auf geschützte Pfade zugreifen können. Ein ausgewähltes `root`-Verzeichnis mit `autoindex` kann Dateien über einen neuen Listener offenlegen; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kann einen privilegierten Dateischreibpfad bieten. Das DAV-Modul ist jedoch standardmäßig nicht eingebaut; seine Verfügbarkeit, Erreichbarkeit des Listeners, Dateiberechtigungen und das Verhalten temporärer Dateien müssen geprüft werden. Auch die [`error_log`-Direktive](https://nginx.org/en/docs/ngx_core_module.html#error_log) kann auf eine ausgewählte Datei zeigen. Das Schreiben von Logs in eine sensible Konfigurationsdatei wie `/etc/ld.so.preload` erfordert einen tatsächlich privilegierten Schreibzugriff und einen kontrollierbaren Logeintrag, bevor daraus ein Pfad zur Rechteausweitung wird. Die Hervorhebung der ausführbaren Datei in `sudo -l` ist ein Prüfhinweis, kein Beleg dafür, dass einer dieser Pfade funktioniert. Starte nginx bei einer passiven Bestandsaufnahme nicht und ändere seine Konfiguration nicht.

### Mustervergleich in privilegierten Bash-Eingabeaufforderungen

Liest ein durch sudo erlaubtes Bash-Skript einen Wert vom Aufrufer und prüft ihn mit `[[ "$expected" == $entered ]]`, interpretiert Bash den unquotierten rechten Operanden als Muster. Ein Wildcard-Zeichen kann daher den Vergleich erfüllen, ohne den erwarteten Wert zu kennen. Durch Anführungszeichen um den Operanden (`[[ "$expected" == "$entered" ]]`) wird der Vergleich zu einem literalen Stringvergleich. Prüfe die genaue sudo-Regel, ob die Eingabeaufforderung erreichbar ist und was das Skript nach dem Vergleich ausführt; die Syntax allein belegt keinen ausnutzbaren Pfad. Gib den erwarteten Wert bei der Bestandsaufnahme nicht aus. Siehe die [Referenz zu Bash-Bedingungskonstrukten](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Mit sudo ausgeführte Helfer, die eine Datei herunterladen und ausführen

Eine uneingeschränkte, root-fähige sudo-Freigabe für einen benutzerdefinierten Helfer verdient eine Datenflussprüfung, wenn er eine vom Aufrufer ausgewählte URL akzeptiert, die Antwort auf der Festplatte speichert und die Datei später mit einem Interpreter oder einer Shell aufruft. [Sudoers erlaubt beliebige Argumente, wenn ein Befehlseintrag keine auflistet](https://man7.org/linux/man-pages/man5/sudoers.5.html); ein fester Pfad zur ausführbaren Datei schränkt nicht ein, was sich mit den Argumenten auswählen lässt. Bestätige die tatsächliche URL-Validierung, den Ausgabepfad, den Erfolgszweig und die anschließende Ausführung im installierten Helfer. Ein passender libcurl-Import oder ein auslesbarer String allein belegt diese Kette nicht.

Selbst ein fest vorgegebener Ausgabedateiname kann zwischen Schreiben und Ausführung ersetzt werden, wenn der Helfer einen **relativen Pfad in einem vom Aufrufer kontrollierten Arbeitsverzeichnis** verwendet. Das Umbenennen oder Ersetzen einer root-eigenen Datei hängt von Schreib- und Suchrechten im Verzeichnis sowie etwaigen Sticky-Bit-Einschränkungen ab, nicht nur vom Dateimodus; siehe [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Prüfe, ob der Helfer den Pfad später erneut öffnet oder den bereits geöffneten Deskriptor verwendet und ob er vor dem Schreiben in ein vertrauenswürdiges Verzeichnis wechselt. Untersuche sudo-Richtlinie, Helfer und Verzeichnismetadaten passiv; rufe bei der Bestandsaufnahme weder den privilegierten Download auf noch führe einen Race durch.

Ein root-sudo-Download-Helfer kann auch eine **Argument**-Injection ermöglichen, wenn er einen Bash-Befehls-String wie `curl <caller input> -o <fixed output>` zusammensetzt. Ein Filter, der Whitespace zurückweist, lässt weiterhin [Bash-Klammererweiterung](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) zu: Unquotierte, durch Kommas getrennte Elemente können zu separaten curl-Argumenten werden. Erreicht die Eingabe `curl` vor dem festen `-o`, kann eine vom Aufrufer angegebene Ausgabedatei das Ziel der ersten URL unter der Identität des Helfers auswählen; [curl ordnet Ausgabeoptionen den URLs der Reihe nach zu](https://curl.se/docs/manpage.html#-o). Bestätige die genaue Shell, Quotierung, Eingabevalidierung, wirksame sudo-Regel, Argumentreihenfolge von curl und unterstützte URL-Schemata sowie, ob der Aufrufer die abgerufenen Bytes kontrolliert oder das Ergebnis lesen kann. Eine mit PyInstaller gepackte ausführbare Datei kann Python-Anwendungslogik enthalten; ihr Verpackungsmarker oder ein `curl`-String allein belegt diesen Datenfluss jedoch nicht. Prüfe, sofern autorisiert, eine begrenzte Offline-Kopie; bei einer routinemäßigen Bestandsaufnahme sollte der Helfer weder ausgeführt noch vom Angreifer ausgewählte Daten abgerufen werden.

Ein root-sudo-Shellskript, das [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aufruft, wählt lediglich einen ungenutzten Namen aus; es **erstellt die Datei nicht**. Erstellt das Skript diesen Namen später in einem Verzeichnis, das ein anderer Benutzer beeinflussen kann, öffnet ihn erneut und hängt seinen Inhalt an ein geschütztes Ziel wie die `authorized_keys`-Datei von root an, sollte ein möglicher Race mit einer temporären Datei geprüft werden. Bestätige die genaue sudo-Regel, Verzeichnis- und Dateieigentümer, Reihenfolge von Erstellung und erneutem Öffnen, Kernel-Schutzmechanismen und ob der privilegierte Schreibvorgang tatsächlich angreiferkontrollierte Bytes verwendet. Ein `mktemp -u`-String oder ein beschreibbares `/tmp` allein belegt den Race nicht. Untersuche Skript und Pfadmetadaten, ohne es auszuführen oder bei der Bestandsaufnahme einen Race mit der temporären Datei durchzuführen.

## Defensive Hinweise

- Vermeide es, Interpreter oder interaktive Editoren über sudo freizugeben.<sup>[[1]](#references)</sup>
- Erlaube keine generischen Dateischreiber wie `tee` mit uneingeschränkten Operanden. Verwende einen root-eigenen Wrapper, der ein festes Ziel auswählt und vom Aufrufer kontrollierte Pfade zurückweist.<sup>[[2]](#references)</sup>
- Bevorzuge feste, root-eigene Wrapper, die eine einzelne, eng begrenzte Verwaltungsaktion ausführen.<sup>[[1]](#references)[[2]](#references)</sup>
- Ist ein Interpreter unvermeidbar, beschränke den exakten Skriptpfad und verhindere vom Benutzer kontrollierte Argumente, beschreibbare Imports, `PYTHONPATH` und unsicheres Beibehalten von Umgebungsvariablen.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Wenn Dateibearbeitung erforderlich ist, beschränke den genauen Dateipfad und erwäge `sudoedit` mit gepatchten sudo-Versionen und strikter Behandlung der Umgebung.<sup>[[1]](#references)[[2]](#references)</sup>
- Prüfe `SETENV`, `env_keep`, beschreibbare Arbeitsverzeichnisse, beschreibbare Modul-/Importpfade, `NOEXEC`, `use_pty` und Protokollierung; behandle sie jedoch nicht als vollständige Sandbox.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
