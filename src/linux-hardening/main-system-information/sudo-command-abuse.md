## Sudo-अनुमत interpreters

अगर `sudo -l` किसी user को root के रूप में interpreter चलाने की अनुमति देता है, तो इसे सीधे code execution के रूप में देखें। Interpreters मनमाना code चलाने के लिए बनाए गए हैं, इसलिए `python3`, `perl`, `ruby`, `lua`, `node` या ऐसे ही binaries चलाने की अनुमति देने वाला नियम आमतौर पर root command execution के बराबर होता है, जब तक कि arguments पर कड़ी पाबंदी न हो और उन्हें validate न किया जाए।<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

समीक्षा का सामान्य क्रम: पहले user के privileges की सूची देखें, फिर interpreter के `-c` option से Python statement चलाएँ।<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

अन्य interpreter के उदाहरण नीचे दिखाए गए हैं; सूचीबद्ध interpreter inline-code execution या child-process APIs का दस्तावेज़ीकरण करते हैं।<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

सटीक path मायने रखता है। यदि sudo rule `/usr/bin/python3` की अनुमति देता है, तो validation के दौरान उसी सटीक path का उपयोग करें।<sup>[[2]](#references)</sup>

`/usr/bin/python*` जैसा sudo executable glob, Python 3 के लिए लिखी गई script के लिए Python 2 को भी अनुमति दे सकता है। यदि script caller-controlled text के साथ `input()` तक पहुँचती है, तो [Python 2 उस text का expression के रूप में मूल्यांकन करता है](https://docs.python.org/2/library/functions.html#input); interpreter को स्पष्ट रूप से invoke करने पर script का shebang निष्प्रभावी हो जाता है। इसे execution path मानने से पहले, मेल खाने वाले installed binaries, effective RunAs और argument policy, denials, और input तक पहुँच की पुष्टि करें।

root-capable sudo rule में तय script path इस बात को सीमित नहीं करता कि script क्या execute करती है। पढ़ी जा सकने वाली Bash wrapper के लिए जाँचें कि क्या उसका पहला executable command, unquoted positional parameter जैसे `$1` को **command word** के रूप में इस्तेमाल करता है, जबकि sudo caller द्वारा चुने गए arguments की अनुमति देता है। Effective RunAs identity, password और argument policy, बाद में लागू होने वाले denials, और script के वास्तविक branch की पुष्टि करें; `NOEXEC`, एक तय safe argument list, या ऐसी wrapper जो अपने command को validate करती है, नतीजे को बदल सकती है। Enumeration के दौरान छोटी script को test command के साथ invoke करने के बजाय statically inspect करें।

`dotnet` के लिए unrestricted root-capable sudo rule की interpreter के लिहाज़ से भी समीक्षा करें। .NET SDK installed होने पर, [`dotnet fsi` F# code को interactively या script से चलाता है](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), और [`dotnet run` source से project execute करता है](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)। पहले effective RunAs identity और सटीक argument policy की पुष्टि करें: किसी खास safe subcommand या trusted application तक सीमित rule एक अलग grant है, और केवल runtime वाली installation में SDK commands उपलब्ध न भी हों। Executable का नाम केवल review का संकेत है, code execution का प्रमाण नहीं।

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo द्वारा अनुमत `tee`: मनमानी privileged फ़ाइल लिखना

GNU `tee` standard input को file operand के रूप में दिए गए हर path पर कॉपी करता है। इसलिए, ऐसा sudo rule जो caller-controlled arguments के साथ `/usr/bin/tee` को root के रूप में चलाने की अनुमति देता है, मनमानी root फ़ाइल बनाने या overwrite करने की क्षमता देता है। `-a` जोड़ने से यह क्षमता append करने की हो जाती है। `PASSWD:` tag sudo authentication से संबंधित है; अपने आप में, यह destination या standard input से पढ़े जाने वाले bytes को सीमित नहीं करता।<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

पहले सटीक rule की जाँच करें। अधिकृत test system पर, इस क्षमता को केवल ऐसे अस्थायी destination से validate करें जिसे सुरक्षित रूप से बनाया जा सकता हो। अंत में दिया गया `>/dev/null` केवल `tee` द्वारा standard output पर की जाने वाली कॉपी को दबाता है।<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

`sudo` को producer से पहले लगाने से बाद का shell redirection elevated नहीं होता, क्योंकि destination को caller का shell खोलता है। ऊपर दी गई pipeline की तरह, privileged process को ही writer होना चाहिए।<sup>[[1]](#references)[[15]](#references)</sup>

Write की पुष्टि करने के बाद, [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md) से root code execution के लिए उपयुक्त sink चुनें। एक देखी गई chain में root `tee` का इस्तेमाल करके `/etc/cron.d/` के अंदर थोड़े समय के लिए रहने वाली file बनाई गई, user-controlled script के ज़रिए backdoor launch किया गया, और execution के बाद cron file हटा दी गई। cron file हटाने से वह long-term persistence entry नहीं बन पाई, हालांकि system logs में गतिविधि के सबूत अब भी मौजूद थे।<sup>[[27]](#references)</sup>

## sudo-अनुमत editors

अगर `sudo -l` किसी user को root के रूप में interactive editor चलाने की अनुमति देता है, तो इसे harmless file-editing permission नहीं, बल्कि command-execution surface मानें। Editors अक्सर shell commands चला सकते हैं, मनमानी files पढ़ या लिख सकते हैं, या editor के अंदर से external helpers चला सकते हैं।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

सामान्य समीक्षा प्रक्रिया: पहले user के privileges की सूची देखें, फिर sudo के तहत हर अनुमत editor या pager चलाएँ।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano command execution

जब `nano` को sudo के ज़रिए चलाने की अनुमति हो, तो editor interface से command execution संभव हो सकता है।<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

इसके बाद nano command prompt पर `id` या `/bin/sh` जैसा कोई command दें।<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

यदि interactive shell में उपयोग करने योग्य terminal streams न हों, तो redirection का यह रूप उसके standard output और error को descriptor 0 पर मैप करता है।<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

nano के version और build options के अनुसार सटीक key sequence अलग हो सकता है, लेकिन security issue वही है: editor root के रूप में चल रहा है और external commands चला सकता है।<sup>[[1]](#references)[[12]](#references)</sup>

### अन्य सामान्य editor escapes

Vim-style editors आमतौर पर `:!` के ज़रिए command execution की सुविधा देते हैं।<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` जैसे pagers shell execution भी उजागर कर सकते हैं।<sup>[[14]](#references)</sup>

`apport-cli` को root के रूप में चलाने की अनुमति देने वाले sudo नियम की भी इसी तरह pager समीक्षा करें। Apport के प्रभावित versions crash report को attacker द्वारा समायोजित किए जा सकने वाले terminal size के साथ `less` में खोल सकते थे; यदि sudo और pager की विशेष शर्तें पूरी होतीं, तो pager root shell दे सकता था। केवल version के आधार पर इसे vulnerable मानने से पहले प्रभावी sudo नियम, pager configuration और distribution package fix की जाँच करें। Passive enumeration के दौरान crash पैदा किए बिना या privileged report खोले बिना package और policy metadata पढ़ें। [Ubuntu का CVE रिकॉर्ड](https://ubuntu.com/security/CVE-2023-1326) backported fixes समेत, release के अनुसार fixed package versions सूचीबद्ध करता है।

```text
!/bin/sh
```

## अन्य sudo और doas नियमों के खतरे

`sudo -l`, `sudo -V`, और लागू होने वाली किसी भी `doas` policy से शुरुआत करें। अनुमत command, RunAs user, arguments, environment और defaults को एक साथ पढ़ें। गैर-root service account के रूप में चलाने की अनुमति से भी उस account की files तक पहुंच या root तक पहुंचने का रास्ता मिल सकता है।

एक तय sudo-अनुमत Python script भी अपने RunAs identity के अंतर्गत shell command चला सकती है, यदि interactive, caller-controlled input को [`os.system()`](https://docs.python.org/3/library/os.html#os.system) में जोड़ा जाता हो। Shell punctuation की denylist सुरक्षा साबित करने के लिए पर्याप्त नहीं है: [shell `$(...)` command substitution को भी पहचानता है](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)। पुष्टि करें कि अनुमत arguments input branch तक पहुंचते हैं, input बिना सुरक्षित validation के shell command तक जाता है, और प्रभावी sudo policy इच्छित RunAs user की अनुमति देती है। केवल script path या `os.system()` का call समीक्षा का संकेत है; privileged script चलाए बिना उसके source का निरीक्षण करें।

`chattr` के लिए प्रभावी root sudo grant immutable (`i`) file attribute हटा सकता है, लेकिन इससे अपने-आप write access या नई identity नहीं मिलती। [`chattr` manual](https://man7.org/linux/man-pages/man1/chattr.1.html) के अनुसार, यह attribute बदलाव रोकता है और इसे केवल root या `CAP_LINUX_IMMUTABLE` वाला process बदल सकता है। sudo argument policy और filesystem support जांचें; फिर अलग से सत्यापित करें कि attribute हटने के बाद caller file लिख सकता है और कोई higher-identity consumer उसका उपयोग करता है। उदाहरण के लिए, login shell बदलने के लिए target account के स्वीकार्य credentials और उस shell के जरिए वास्तविक login भी जरूरी हैं। Enumeration के दौरान policy, file attributes और permissions देखें, लेकिन उनमें बदलाव न करें।

यदि sudo password और one-time code, दोनों मांगता है, तो इन prerequisites को command grant से अलग रखें। पढ़ी जा सकने वाली `.google_authenticator` file में संवेदनशील seed material होता है, जबकि पुराना application या database password hash केवल मौजूदा account password का संभावित उम्मीदवार है; इनमें से कोई भी साबित नहीं करता कि प्रभावी PAM configuration दूसरा factor स्वीकार करती है। अधिकृत होने के बाद, सटीक RunAs और arguments की समीक्षा करें: RubyGems `gem` के लिए unrestricted root grant उसका editor command उजागर कर सकता है ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), लेकिन restricted grant या विफल authentication ऐसा नहीं करता। Passive enumeration में seed दिखाए, password recover करे, code बनाए या privileged command चलाए बिना paths और policy रिपोर्ट करें।

Chef के `knife` के लिए unrestricted root-capable sudo grant की interpreter स्तर पर समीक्षा जरूरी है: [Chef के अनुसार `knife exec -E` स्थानीय रूप से Ruby string evaluate करता है](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). सत्यापित करें कि प्रभावी sudo rule `exec` subcommand और caller द्वारा दिया गया `-E` argument, इच्छित RunAs identity, तथा लागू command denials या fixed arguments की अनुमति देता है। Installed binary या अन्य subcommands तक सीमित rule केवल जांच का संकेत है। Passive enumeration में `knife` चलाए बिना rule रिपोर्ट करें।

Interactive `msfconsole` के लिए सटीक root-capable sudo grant भी इसी तरह संवेदनशील है: [GTFOBins इसके `irb` console का उल्लेख करता है](https://gtfobins.org/gtfobins/msfconsole/), जो sudo identity विरासत में ले सकता है। प्रभावी RunAs user, अनुमत argument list, command denials, `NOEXEC` या अन्य restrictions, installed console का व्यवहार, और caller द्वारा interactive input देने की क्षमता की पुष्टि करें। केवल path highlight समीक्षा का संकेत है; passive enumeration में console न चलाएं।

FreeBSD पर, root के लिए केवल `pkg update` और `pkg install *` तक सीमित sudo rule में भी repository trust की समीक्षा जरूरी है। जांचें कि caller `/etc/hosts` लिख सकता है या नहीं और क्या *प्रभावी* enabled repository configuration `signature_type: none` वाले HTTP hostname का उपयोग करती है। [FreeBSD के `pkg.conf` manual](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) के अनुसार, `none` signature checks बंद करता है; केवल `pkg+http` होना इसका प्रमाण नहीं है। Package में install scripts हो सकती हैं ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), इसलिए यदि caller वास्तव में repository endpoint नियंत्रित कर सकता है और package चुन सकता है, तो root boundary पार हो सकती है। यह निष्कर्ष निकालने से पहले repository overrides, SRV/mirror resolution, प्रभावी sudo arguments, package selection और script execution सत्यापित करें। Enumeration के दौरान names redirect किए या `pkg` चलाए बिना policy और छोटी local configuration files देखें।

`apt-get update` और `apt-get upgrade` के लिए root-capable sudo grant में repository trust की समीक्षा जरूरी है, यदि sudo caller-controlled `http_proxy` बनाए रखता हो। जांचें कि प्रभावी APT proxy configuration वास्तव में उस variable का उपयोग करती है या नहीं और यह किन enabled repository requests को प्रभावित कर सकता है; proxy अकेले trusted signing key से authenticated archive के packages नहीं बदल सकता। [APT के HTTP transport manual](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) में proxy precedence, और [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) में signature checks, insecure-repository overrides तथा unauthenticated packages की पुष्टि का वर्णन है। सटीक sudo RunAs और arguments, repository authentication policy, आवश्यक interactive acceptance, और चुना गया upgrade root के रूप में package scripts चलाता है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान policy और local configuration का निरीक्षण करें; package traffic redirect न करें और upgrade न चलाएं।

`snap install` के लिए root-capable sudo rule package से code तक की boundary बन सकता है, यदि उसके arguments caller को local snap और permissive install mode चुनने दें। [Snap के दस्तावेज़](https://snapcraft.io/docs/explanation/snap-development/install-modes/) के अनुसार, `--dangerous` local-snap assertion checks छोड़ता है और `--devmode` confinement ढीला करता है; [install hook शुरुआती installation के समय चल सकता है](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Protected host files तक पहुंच का दावा करने से पहले सटीक sudo argument/RunAs policy, snap file पर किसका नियंत्रण है, installed snapd इन modes को स्वीकार करता है या नहीं, और hook की प्रभावी identity तथा confinement जांचें। केवल `snap` binary या wildcard-जैसा rule इस chain को साबित नहीं करता। Passive enumeration में package install न करें और उसका hook न चलाएं।

किसी **non-root** account के custom credential-reading binary के लिए सटीक sudo grant हो, तो पहले binary और उसकी file permissions का निरीक्षण करें; उसे चलाएं नहीं। Embedded password gate केवल wide characters में दिख सकता है; [GNU `strings` में 16-bit little-endian extraction का वर्णन है](https://sourceware.org/binutils/docs/binutils/strings.html)। दिखने वाली string यह साबित नहीं करती कि वही स्वीकार्य password है या success branch मौजूदा credential उजागर करती है। Binary का व्यवहार, protected data तक target account की पहुंच, credential की वैधता, और बाद में account या group transition—इनकी अलग-अलग पुष्टि करें। यदि वह account `docker` group में है, तो host-root access का निष्कर्ष निकालने से पहले socket access और daemon की rootful या rootless identity जांचें; [Docker इस group के root-level प्रभावों का वर्णन करता है](https://docs.docker.com/engine/install/linux-postinstall/). Routine enumeration में binary चलाए या उसके strings dump किए बिना sudo rule और group membership रिपोर्ट करें।

Application के maintenance scripts के लिए wildcard sudo rule की समीक्षा केवल script path तक सीमित नहीं होनी चाहिए। जांचें कि अनुमत script unrestricted arguments स्वीकार करती है या ऐसे settings पढ़ती है जिन्हें lower-privileged application account लिख सकता है; फिर उन values को shell commands या subprocess environment तक trace करें। उदाहरण के लिए, ZoneMinder की [`zmupdate.pl` एक `mysqldump` command बनाकर उसे `qx` के जरिए चलाती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), जबकि [`zmdc.pl` daemons शुरू करने से पहले `ZM_LD_PRELOAD` setting को `LD_PRELOAD` में copy करती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)। यदि संबंधित input controllable हो और installed version में उस code तक पहुंचे, तो इनमें से किसी script को root के रूप में चलाने की अनुमति trust boundary पार कर सकती है। प्रभावी sudo rule, application configuration permissions और script source देखें; wildcard या setting अकेले execution का प्रमाण नहीं है।

- `SETENV`, `env_keep`, `secure_path`, और `LD_PRELOAD` अन्यथा सीमित command को import, library या PATH hijack में बदल सकते हैं। [environment-variable guide](../linux-basics/linux-environment-variables.md) और [SUID/linker abuse](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md) देखें।

Shell wrapper को `SETENV` के साथ दिया गया सटीक root-capable grant हो, तो एक-hop समीक्षा करें—खासकर यदि wrapper तय Python script को literal import के साथ चलाता है। `secure_path` shell command lookup को सीमित करता है, Python की [`PYTHONPATH` module search](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) को नहीं; [`-E` और `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) Python को उस environment variable को अनदेखा कराते हैं। इसे code execution मानने से पहले प्रभावी sudo tags और denials, wrapper branch, interpreter options, import resolution और caller-writable search directory की पुष्टि करें। छोटी scripts का static निरीक्षण करें; privileged wrapper न चलाएं।

सटीक root-capable `neofetch ""` sudo grant भी shell configuration load कर सकता है, यदि लागू sudo defaults caller-controlled `XDG_CONFIG_HOME` को बनाए रखते हों। [Neofetch का configuration loader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) उस directory के नीचे `neofetch/config.conf` या `neofetch/config` source करता है; खाली argument list इस lookup को नहीं रोकती। Installed loader, प्रभावी RunAs और argument policy, command denials, sudo इस command के लिए चुने गए variable को वास्तव में बनाए रखता है या नहीं, और caller किसी readable configuration path को नियंत्रित करता है या नहीं—इनकी पुष्टि करें। केवल preserved variable या installed Neofetch समीक्षा का संकेत है। Privileged command चलाए या configuration contents दिखाए बिना policy और file metadata देखें; [sudoers environment handling](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।

`facter` के लिए unrestricted root-capable sudo rule में custom-fact की अलग समीक्षा जरूरी है। [Puppet के दस्तावेज़](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) के अनुसार, `--custom-dir` चुनी गई directory से Ruby fact files load करता है। जांचें कि सटीक sudo rule उस option की अनुमति देता है या नहीं, installed Facter उसे स्वीकार करता है या नहीं, और caller directory नियंत्रित करता है या नहीं। Fixed-argument grant, explicit command denial या disabled custom facts परिणाम बदल सकते हैं। Passive enumeration में Facter चलाए या fact contents पढ़े बिना policy candidate रिपोर्ट करें।

`SETENV` वाले सटीक root-capable sudo script grant के लिए, `find` जैसे bare command names और sudo policy तथा script initialization के बाद प्रभावी `PATH` की समीक्षा करें। Source की गई Bash file `enable -n [` भी चला सकती है: [इसके बाद Bash `PATH` में external `[` खोजता है](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), यदि script आगे उस command का उपयोग करे। इसे privileged execution मानने से पहले लागू [sudoers environment और `secure_path` rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), `NOSETENV`/`NOEXEC` या denial entries, script और sourced-file flow, तथा caller-controlled executable search directory की पुष्टि करें। Bare command वाली readable script समीक्षा का संकेत है, privileged execution का प्रमाण नहीं; sudo rule चलाए बिना उसका निरीक्षण करें।
- तय URL को `curl` से fetch करने वाली privileged script भी caller द्वारा चुना गया response स्वीकार कर सकती है, यदि लागू sudo rule `http_proxy` बनाए रखता हो और request उसी proxy से भेजी जाती हो। यदि script फिर response को ऐसे XML parser को देती है जो external entities resolve करता है, तो hostile response privileged process द्वारा पढ़ी जा सकने वाली files उजागर कर सकता है। सटीक sudo environment policy, `no_proxy` exclusions, requested URL, parser configuration और output destination जांचें; proxy variable या XML parser अकेले vulnerability नहीं है। [curl proxy environment documentation](https://everything.curl.dev/usingcurl/proxies/env.html) में variable का व्यवहार बताया गया है। Passive enumeration में network requests न करें और hostile XML parse न करें।
- Caller-influenced data से PostScript file बनाने और फिर `ps2pdf -dNOSAFER` चलाने वाली root-capable sudo script में input flow की अलग समीक्षा करें। Ghostscript के अनुसार, यह flag `.setsafe` आने तक SAFER बंद करता है, जिससे process अपनी OS permissions के भीतर PostScript file operations कर सकता है। Caller argument से बनाई गई SQL query attacker-controlled rows को PostScript template तक पहुंचा सकती है, लेकिन query string या `ps2pdf` invocation अकेले यह साबित नहीं करते कि data executable PostScript syntax तक पहुंचता है। प्रभावी sudo rule, input से template तक का सटीक path, escaping, installed Ghostscript का व्यवहार, और document interpret होने से पहले SAFER फिर चालू होता है या नहीं—इनकी पुष्टि करें। Passive enumeration में privileged conversion न चलाएं। [Ghostscript के `-dNOSAFER` documentation](https://ghostscript.readthedocs.io/en/master/Use.html) देखें।
- Shell script चलाने वाले sudo rule के लिए preserved variables की तुलना script से करें। `if $CHECK_CONTENT; then` जैसा construct expanded value को command की तरह चलाता है, इसलिए `CHECK_CONTENT` को preserve करना command execution की अनुमति दे सकता है, भले ही script path और arguments fixed हों। इस branch तक पहुंचा जा सकता है या नहीं और environment वास्तव में बना रहता है या नहीं, यह उस विशेष rule के लिए जांचना होगा।<sup>[[2]](#references)[[22]](#references)</sup>
- Sudo-अनुमत Python script writable directory या cached `.pyc` file से code import कर सकती है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md) में cache वाले मामले का विवरण है।
- Root के रूप में चलाने की अनुमति वाली fixed Python script interactive debugger भी उजागर कर सकती है। `pdb.set_trace()` या `pdb.post_mortem()` जैसे calls debug किए जा रहे process के context में Python statements चलाने देते हैं, यदि caller breakpoint या exception handler तक पहुंच सकता हो **और debugger के input stream को नियंत्रित करता हो**। सटीक sudo RunAs rule, authentication और branch conditions, exception तक पहुंच, terminal/input ownership, तथा debugger उसी privileged process में चलता है या नहीं—इनकी जांच करें। किसी exception को trigger करने वाली socket request अपने-आप दूसरे terminal से जुड़े debugger तक पहुंच नहीं देती। [Python debugger की statement evaluation और post-mortem mode का दस्तावेज़ देता है](https://docs.python.org/3/library/pdb.html); enumeration के दौरान privileged handler trigger करने के बजाय script का static निरीक्षण करें।
- Sudo-अनुमत fixed Python script database या Unix socket से profile field पढ़कर उसे ऐसी string में जोड़ सकती है जो बाद में `str.format()` की **format string** बनती है। [Replacement fields attributes और mapping keys का अनुसरण कर सकते हैं](https://docs.python.org/3/library/string.html#format-string-syntax), इसलिए attacker-controlled field `format()` को दिए गए objects की जांच कर सकता है और उनसे पहुंच योग्य data उजागर कर सकता है—यदि परिणाम print हो या ऐसी जगह store हो जहां caller उसे पढ़ सके। प्रभावी sudo RunAs identity, उस specific record पर write access, format string तक data flow, दिए गए objects और output visibility जांचें। इससे अपने-आप code execution नहीं होता; attacker-controlled *values* वाली literal trusted format string अलग मामला है। Privileged operation चलाए बिना script और socket permissions की समीक्षा करें।
- Root-capable Python wrapper caller द्वारा चुना गया URL GitPython के `Repo.clone_from` को दे सकता है। यदि wrapper Git का `protocol.ext.allow=always` भी चालू करता है, तो `ext::` remote external helper चला सकता है। सटीक sudo arguments, URL कहां से आता है, GitPython package version और vendor patch status, तथा wrapper unsafe protocols को स्पष्ट रूप से अनुमति देता है या नहीं—इनकी जांच करें। GitPython ने 3.1.30 में [default unsafe-protocol guard](https://github.com/gitpython-developers/GitPython/commit/2625ed9) जोड़ा; `git` executable का version अलग जानकारी है। Passive review में केवल rule और सीमित source पढ़ें; clone न चलाएं।
- Repository-cloning CLI के लिए cross-user sudo grant से shell-string injection का अलग रास्ता खुल सकता है। जांचें कि caller द्वारा चुना repository argument Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) या किसी अन्य shell-command builder तक बिना सुरक्षित argument separation के पहुंचता है या नहीं; Node का `exec` अपनी command string shell को देता है। सटीक RunAs user, अनुमत subcommands और arguments, installed wrapper code, तथा input validation की पुष्टि करें। Repository tool का नाम या unrestricted sudo rule अकेले command injection साबित नहीं करता। Enumeration में privileged clone चलाए बिना wrapper का निरीक्षण करें।
- Custom root-owned wrapper सुरक्षित दिख सकता है, क्योंकि उसकी binaries और scripts writable नहीं हैं, फिर भी privileged action चलाने का उसका निर्णय ऐसे flag, local API value या service state पर निर्भर हो सकता है जिसे unprivileged user बदल सकता है। हर gate को उसके input और authorization checks तक trace करें। Enumeration के दौरान operational state बदले बिना configuration और permissions देखें; wrapper में `systemd-run` call तभी प्रासंगिक है जब gate को प्रभावित किया जा सके।
- Root के रूप में sudo से चलाया जा सकने वाला backup client caller द्वारा चुनी गई configuration file स्वीकार कर सकता है, जैसे `npbackup-cli -c`। सटीक RunAs user और अनुमत arguments जांचें; फिर देखें कि caller configuration path, backup source paths, और repository या read/restore options नियंत्रित करता है या नहीं। Readable config में encrypted repository secret client द्वारा फिर भी उपयोग किया जा सकता है, लेकिन rule अकेले repository access या root-file disclosure साबित नहीं करता। Backup चलाए या उसके contents dump किए बिना authorization की जांच करें।
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) `--password-command` समर्थित करता है, जो repository password पाने के लिए program चलाता है। यदि sudo rule lower-privileged user को caller-chosen password command और password मांगने वाले subcommand के साथ root के रूप में restic चलाने देता है, तो वह helper root के रूप में चल सकता है। सटीक sudo arguments और exclusions की समीक्षा करें; इस स्थिति की enumeration के लिए helper या backup command न चलाएं।
- Privileged `restic backup` grant file-read boundary भी पार कर सकता है, यदि sudo argument pattern caller को source और ऐसा repository, दोनों चुनने दे जिसे वह बाद में पढ़ और decrypt कर सके। [Sudoers argument wildcards whitespace और slashes से match कर सकते हैं](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), इसलिए trailing wildcards देखें; यह न मानें कि fixed repository prefix source को सीमित करता है। [Restic local और remote repositories में backup कर सकता है](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), लेकिन local repository में नए, केवल root को पढ़े जा सकने वाले objects हो सकते हैं; इसे disclosure मानने से पहले प्रभावी sudo policy, backend access, repository password और परिणामी object permissions की पुष्टि करें। Backup की गई SSH key तभी login देती है जब destination account उसे स्वीकार करता हो। Passive review में जांचने के लिए backup न चलाएं।
- Unrestricted custom maintenance या backup command output path स्वीकार कर सकती है या अपना job scheduler दे सकती है। File-write path के लिए सटीक sudo rule और RunAs user सत्यापित करें, फिर जांचें कि caller data और destination, दोनों नियंत्रित करता है या नहीं। Scheduled-command path के लिए scheduler की execution identity, command input और किसी अतिरिक्त password या authorization gate की पुष्टि करें। Command का नाम या केवल `NOPASSWD` इनमें से कोई रास्ता साबित नहीं करता। [root-owned files में लिखना](../interesting-files-permissions/write-to-root.md) और [cron तथा systemd timers](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md) देखें।
- Fixed sudo command shared writable directory से अनुमानित configuration file load कर सकती है। जांचें कि caller उस file को बदल सकता है या नहीं और क्या उसके source तथा destination fields privileged fetch या copy को नियंत्रित करते हैं। Local-file URL से केवल sudo RunAs account द्वारा पढ़ा जा सकने वाला data उजागर हो सकता है; protected destination के साथ caller-controlled source write path बना सकता है। Installed program की URL handling, destination path checks, प्रभावी sudo rule और output की पहुंच की पुष्टि करें। Writable `/tmp` configuration path अकेले समीक्षा का संकेत है; privileged transfer चलाए बिना binary और file metadata देखें।
- `git apply` का sudo rule RunAs account को caller-controlled patch से चुनी गई files लिखने दे सकता है। [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) में crafted patch symlink बना सकता था और फिर working tree के बाहर लिख सकता था, भले command `--unsafe-paths` स्वीकार न करती हो। प्रभावी sudo argument rule, patch source, RunAs account की working-directory access, तथा installed Git fix या vendor backport जांचें। `--unsafe-paths` की अनुमति देने वाला unrestricted rule अलग explicit option risk है; Git version या `git apply` permission अकेले यह साबित नहीं करते कि protected file बदली जा सकती है। Passive enumeration में untrusted patch लागू न करें।
- Root-capable `clamscan --debug` rule read boundary पार कर सकता है, यदि lower-privileged user DMG image दे सकता हो और installed parser [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) से प्रभावित हो, जिसमें debug output के जरिए file contents उजागर हो सकते थे। सटीक अनुमत arguments और scan path, input पर नियंत्रण, प्रभावी RunAs account, engine patch/backport, तथा output caller को दिखता है या नहीं—इनकी पुष्टि करें। यदि व्यापक rule `--file-list`/`-f` की अनुमति देता है, तो उसके व्यवहार की अलग समीक्षा करें; `--debug <scan-path>` तक सीमित policy इसकी अनुमति नहीं देती। Enumeration में crafted file scan किए या protected output दिखाए बिना policy और package metadata देखें।
- Caller द्वारा चुनी encrypted disk image खोलने वाला root-capable sudo rule और resulting mapper को mount करने वाला दूसरा rule, caller-controlled files को host के mount namespace में ला सकता है। दोनों प्रभावी rules और arguments, image और mapper name पर नियंत्रण, वास्तविक mount target, तथा परिणामी file owner और mode की पुष्टि करें। Set-user-ID transition के लिए accessible executable, इसे अनुमति देने वाले mount options (`nosuid` इसे रोकता है), और लागू process या MAC policy भी जरूरी हैं; image खोलना या mount करना अकेले समीक्षा का संकेत है। मौजूदा backup के जरिए अलग रास्ते के लिए उसकी वास्तविक key और उपयोगी readable secret जरूरी है। Passive enumeration में image खोले या mount किए बिना policy और paths देखें। [cryptsetup manual](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) और [mount options](https://man7.org/linux/man-pages/man8/mount.8.html) देखें।
- Shell या Python script के लिए root-capable sudo rule हो, तो working directory की समीक्षा करें—खासकर यदि script fixed directory में जाने से पहले `./helper` चलाती है। `subprocess.run` को दी गई `['./helper']` जैसी Python list में भी caller द्वारा चुनी गई working directory का यही व्यवहार हो सकता है। Caller writable directory चुनकर वहां उस relative name का executable रख सकता है; script में कहीं और दिया absolute path इस call को सुरक्षित नहीं करता। इसे code execution मानने से पहले प्रभावी rule, `runchdir` या अन्य directory-changing policy, script flow और branch तक पहुंच, writable और executable directory, तथा mount/`NOEXEC` restrictions की पुष्टि करें। Unreadable script का व्यवहार तब तक अज्ञात है जब तक authorized path से उसका source न देखा जाए। Helper चलाने के बजाय scripts का static निरीक्षण करें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) में working-directory policy का वर्णन है।
- Root-capable fixed Python validator caller द्वारा चुनी data file फिर भी evaluate कर सकता है। [Python का `eval()` documentation untrusted input के विरुद्ध चेतावनी देता है](https://docs.python.org/3/library/functions.html#eval): यदि शेष expression `eval` तक पहुंचता है, तो input suffix check, arithmetic prefix या validation branch sandbox नहीं है। इसे execution path कहने से पहले प्रभावी sudo rule, caller सटीक file चुन और नियंत्रित कर सकता है या नहीं, parser की branch conditions और expression construction, तथा privileged process identity की पुष्टि करें। Readable script में `eval` का होना केवल समीक्षा का संकेत है; enumeration के दौरान validator चलाए या test expression दिए बिना source और file permissions देखें।
- Relative YAML filename, जैसे `YAML.load(File.read("dependencies.yml"))`, पढ़ने वाला root-capable sudo Ruby wrapper caller की working directory से input ले सकता है—जब तक wrapper या sudo policy उस directory को तय न करे। सटीक अनुमत arguments, directory और file permissions, तथा installed Psych behavior जांचें: पुराने `YAML.load` implementations मनमाने Ruby objects deserialize कर सकते थे, जबकि नए releases default रूप से classes सीमित करते हैं। Static call site केवल समीक्षा का संकेत है; पुष्टि करें कि file वास्तव में caller-writable directory से आती है और installed loader खतरनाक classes स्वीकार करता है। Untrusted input के लिए स्पष्ट न्यूनतम class allowlist के साथ `safe_load` बेहतर है। [Ruby 3.0 Psych documentation](https://docs.ruby-lang.org/en/3.0/Psych.html) और [Ruby 3.1 Psych documentation](https://ruby-doc.org/core-3.1.2/Psych.html) देखें।

- `sudo go run /absolute/file.go` का सटीक root-capable grant हो, तो working directory की समीक्षा करें—खासकर यदि Go source relative WASM file पढ़ता है और उसका परिणाम देखने के बाद relative shell script चला सकता है। प्रभावी RunAs, command arguments और denials, caller-writable current directory, WASM से branch तक data flow, और वह branch helper चलाती है या नहीं—इनकी पुष्टि करें। Fixed sudo `runchdir`, `os.Chdir`, या [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) lookup location बदल सकता है। केवल static co-occurrence समीक्षा का उम्मीदवार है; Go, WASM या helper चलाए बिना source देखें।
- `sudoedit` और argument wildcards के लिए सटीक version और rule checks जरूरी हैं; [checklist](linux-privilege-escalation-checklist.md) में sudoedit file-edit issue शामिल है। Wildcard path पर cross-user `sudoedit` grant हो, तो प्रभावी `sudoedit_follow` या `FOLLOW` setting, `sudoedit_checkdir`, resolved target, और हर parent entry को कौन बदल सकता है—यह जांचें। पहला symlink follow करने की अनुमति दे सकता है, जबकि दूसरे को disable करने से writable-directory checks हट जाते हैं; इनमें से कोई भी setting अकेले दूसरे user की file में write साबित नहीं करती। यह निष्कर्ष निकालने से पहले installed sudo policy और सटीक matched arguments की पुष्टि करें। [sudoers option definitions](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।
- Sudoers command rule में argument wildcard whitespace के साथ-साथ path characters से भी match कर सकता है। Read-capable command के लिए `/restricted/*` जैसा argument इसलिए matching prefix के बाद अतिरिक्त file argument की अनुमति दे सकता है। सटीक RunAs user, command path, argument pattern और बाद के denials की समीक्षा करें; file पढ़ पाने का प्रदर्शन command execution का अर्थ नहीं है। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) argument globs और command-path globs में अंतर बताता है।
- Path-जैसा दिखने वाला argument glob `../` से भी match कर सकता है। उदाहरण के लिए, root-capable `node /opt/scripts/*.js` rule caller-controlled JavaScript file को `/opt/scripts` के बाहर भी अनुमति दे सकता है, यदि दिया गया pathname `/opt/scripts/` से शुरू होता हो और parent-directory segments के जरिए resolve होता हो। यह **argument** glob है; Node executable के command-path glob में slash matching के अलग नियम हैं। Code execution का निष्कर्ष निकालने से पहले प्रभावी rule, बाद के denials, pathname resolution, target file पर नियंत्रण, और sudoers regular-expression या digest restrictions जांचें। [sudoers wildcard rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) और [Node command-line documentation](https://nodejs.org/api/cli.html) देखें।
- Archivers और अन्य utility programs में execution hooks हो सकते हैं। यह मानने के बजाय कि केवल shells या interpreters commands चलाते हैं, सटीक अनुमत arguments को [GTFOBins](https://gtfobins.github.io/) से जांचें।
- Unrestricted root-capable `qpdf` rule PDF attachments के जरिए privileged file उजागर कर सकता है: qpdf 10.2 और बाद के versions output PDF के साथ `--empty` और `--add-attachment file ... --` समर्थित करते हैं। यदि privileged process चुने गए source को पढ़ और PDF को caller-accessible path पर लिख सकता है, तो output में source bytes हो सकते हैं। File disclosure संभव है, यह निष्कर्ष निकालने से पहले प्रभावी sudo arguments और exclusions, qpdf version, source access और output path की समीक्षा करें। Root SSH key पढ़ना तभी login के काम आता है जब key valid हो और root SSH authentication अनुमत हो। [qpdf attachment options](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments) देखें।
- Sudo timestamp reuse cache policy, owning user, terminal/session और permissions पर निर्भर करता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) में checks दिए गए हैं।
- `doas` के अपने rules और configuration हैं। [doas section](../linux-basics/linux-privilege-escalation/README.md#doas) में बताए अनुसार अनुमत commands और writable configuration paths जांचें।

### Sudo के तहत चलने वाले build और package tools

Foundry के `forge` के लिए unrestricted sudo grant तब भी महत्वपूर्ण हो सकता है जब RunAs identity कोई दूसरा non-root user हो। `--use` जैसे compiler options local executable चुन सकते हैं और `forge flatten -o` output file चुनता है। इस grant को exploitable मानने से पहले installed Forge version, सटीक sudo arguments, accessible project और compiler paths, output permissions, तथा प्रभावी environment जांचें। `PATH` के जरिए मिलने वाला relative helper executable version और environment पर निर्भर रास्ता है; इसे हर Forge build का गुण न मानें।<sup>[[23]](#references)[[24]](#references)</sup>

Unrestricted root-capable `pacman` grant package queries से आगे की अनुमति देता है: `-U` local package स्वीकार करता है, packages में install scripts हो सकती हैं और `--hookdir` दूसरी hook directory चुनता है। जांचने से पहले प्रभावी sudo rule, argument restrictions और exclusions की समीक्षा करें; passive enumeration में package install करने या hook चलाने की जरूरत नहीं है।<sup>[[25]](#references)[[26]](#references)</sup>

Fixed sudo shell wrapper नामित npm dependency install करके Node application भी शुरू कर सकता है। उसके सटीक RunAs rule, package पहले से installed है या नहीं, प्रभावी `HOME` और npm `userconfig`, project configuration या command-line overrides, तथा lower-privileged user उस नाम के लिए registry या लौटाया गया package नियंत्रित करता है या नहीं—इनकी समीक्षा करें। [npm के दस्तावेज़ में per-user और per-project `.npmrc` lookup का उल्लेख है](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo का `HOME` व्यवहार installed policy और distribution पर निर्भर है, इसलिए privileged npm process writable user `.npmrc` पढ़ भी सकता है और नहीं भी। यदि privileged application newly installed package import करती है, तो उसका module code उस application की identity के अंतर्गत चल सकता है। Install-time scripts अलग, version और configuration पर निर्भर रास्ता हैं; [npm इनके lifecycle और user handling का वर्णन करता है](https://docs.npmjs.com/cli/v6/using-npm/scripts/). `.npmrc` path या `npm install` line अकेले समीक्षा का संकेत है। Passive enumeration में application install या start किए बिना rule, छोटी wrapper, configuration paths और package provenance जांचें।

Root-capable `pip` या `pip3 download` grant में भी package-build की समीक्षा जरूरी है, यदि arguments caller को untrusted source distribution चुनने दें—भले URL pattern इसे local service और `.tar.gz` suffix तक सीमित करे। `pip download` archive URLs स्वीकार करता है और package metadata resolve करता है; sdist तैयार करते समय archive केवल save होने से पहले ही उसका build backend या legacy `setup.py` code चल सकता है। सटीक sudo RunAs और argument rule, caller चुने गए archive को publish या replace कर सकता है या नहीं, और वह pip version metadata तैयार करता है या नहीं—इनकी पुष्टि करें। Fixed trusted archive या wheel इस रास्ते को साबित नहीं करता। Passive enumeration में untrusted package fetch या build न करें। pip का [download command](https://pip.pypa.io/en/stable/cli/pip_download/), [build-system interface](https://pip.pypa.io/en/stable/reference/build-system/), और [secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/) देखें।

Caller द्वारा चुने local project path के साथ `pip install` की अनुमति देने वाला sudo rule build boundary को अधिक सीधे खोलता है। [pip local project directories स्वीकार करता है](https://pip.pypa.io/en/stable/topics/local-project-installs/) और उनका build system चलाता है; [build backend project-controlled build hooks चलाता है](https://pip.pypa.io/en/stable/reference/build-system/). Rule को privileged code execution मानने से पहले प्रभावी RunAs identity, सटीक argument restrictions और denials, चुने project पर नियंत्रण, तथा installed pip/backend behavior की पुष्टि करें। Fixed trusted project या caller-selected paths को रोकने वाला rule यह रास्ता स्थापित नहीं करता। Passive enumeration में package install किए बिना rule और project metadata देखें।

Unrestricted root-capable `easy_install` grant भी legacy package-build का संबंधित संकेत है। [Setuptools के दस्तावेज़](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) के अनुसार, Easy Install local project directory स्वीकार करता है और source distributions बनाता है; caller-controlled project sudo identity के अंतर्गत उस build के दौरान `setup.py` चला सकता है। प्रभावी RunAs account, सटीक command और argument restrictions—बाद के denials सहित—चुने project पर नियंत्रण, तथा installed tool का व्यवहार जांचें। Fixed trusted project या caller-selected source की अनुमति न देने वाली policy इस रास्ते को स्थापित नहीं करती। Enumeration में package install किए बिना rule और project metadata देखें।

Caller द्वारा चुने URL के साथ `setuptools.package_index.PackageIndex.download` इस्तेमाल करने वाला sudo-अनुमत Python wrapper, `pip download` से अलग समीक्षा का मामला है: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) के अनुसार, 78.1.1 से पहले के प्रभावित releases में URL से निकला filename intended download directory से बाहर जा सकता था और process की permissions के साथ लिख सकता था। प्रभावी sudo RunAs और argument rule, wrapper caller का URL इसी API को देता है या नहीं, installed build या vendor backport, और परिणामी path कहां resolve होता है—इनकी पुष्टि करें। Version string या writable download directory अकेले arbitrary write साबित नहीं करते। Enumeration में URL fetch या file write किए बिना छोटी wrapper और package metadata की समीक्षा करें।

Caller द्वारा चुनी `.spec` file PyInstaller को देने वाली sudo-अनुमत build wrapper में भी trust boundary की समीक्षा जरूरी है। PyInstaller spec build के दौरान evaluate होने वाला executable Python है, और उसकी `datas` entries build identity द्वारा पढ़ी जा सकने वाली files को artifact में bundle कर सकती हैं। सटीक RunAs user, sudo argument और denial rules, wrapper का path और branch handling, चुनी spec file पर नियंत्रण, तथा परिणामी artifact तक पहुंच—इनकी पुष्टि करें। केवल `.py` input की अनुमति या PyInstaller installed होना spec file पर नियंत्रण या privileged execution साबित नहीं करता। Passive review में केवल सीमित wrapper file और metadata पढ़ें; build न चलाएं। [PyInstaller spec-file documentation](https://pyinstaller.org/en/stable/spec-files.html) देखें।

### Sudo के तहत चलने वाले preset और plugin loaders

Caller द्वारा चुना preset या plugin directory स्वीकार करने वाले Python tools, sudo से मिली privileges के साथ code import कर सकते हैं। उदाहरण के लिए, BBOT `-p` के साथ preset स्वीकार करता है, और उसके [custom-module documentation](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) में `module_dirs` entries द्वारा अतिरिक्त Python module directories चुनने का वर्णन है। यदि प्रभावी sudo rule caller द्वारा चुने preset की अनुमति देता है और caller चुनी directory के module को नियंत्रित करता है, तो tool द्वारा invalid module अस्वीकार किए जाने से पहले भी import privileged user के रूप में code चला सकता है। Enumeration में module load किए बिना installed version, सटीक sudo run-as और argument policy, तथा preset और module paths का ownership जांचें।

### Sudo के तहत चलने वाला Backdrop command line tool

[Bee](https://github.com/backdrop-contrib/bee) Backdrop CMS के लिए PHP command line tool है। इसके `eval` (`php-eval`) और `php-script` commands caller द्वारा दिया गया PHP चला सकते हैं। इसलिए root के रूप में unrestricted arguments के साथ Bee executable की अनुमति देने वाला sudo rule root code execution खोल सकता है, यदि Bee Backdrop installation bootstrap कर सके। Site directory से चलाएं या global `--root=<directory>` option से site चुनें; केवल Bee या Backdrop `settings.php` file मिलने से sudo permission, usable site या सफल bootstrap साबित नहीं होता। जांचने से पहले प्रभावी sudo rule, किसी भी command exclusion, executable की identity और site तक पहुंच की समीक्षा करें। Passive enumeration में Bee चलाए बिना rule और file paths देखें। PHP commands जोड़े जाने के बारे में [Bee command changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) देखें।

### Sudo के तहत चलने वाले terminal servers

`mosh-server` invoking user के रूप में interactive terminal server शुरू करता है। यह high UDP port और session key चुनता है, दोनों caller को बताता है और सामान्यतः client connect होने पर उस user का login shell चलाता है। इसलिए `mosh-server` के लिए unrestricted root-capable sudo grant shell-समीक्षा का उम्मीदवार है, भले server command स्वयं detach हो जाती हो। प्रभावी RunAs identity, अनुमत arguments और exclusions, installed binary, shell, client availability और UDP access जांचें। Passive enumeration में server शुरू किए या live session key दिखाए बिना sudo rule देखें। [Mosh server manual](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) और [upstream design notes](https://github.com/mobile-shell/mosh#how-it-works) देखें।

### Caller की task file को दोबारा लिखने वाले privileged backup wrappers

Root के रूप में चलने वाली shell wrapper caller द्वारा चुनी task file स्वीकार कर सकती है, source paths से `../` हटा सकती है, जांच सकती है कि हर परिणाम अनुमत directory से शुरू होता है, task file दोबारा लिख सकती है, और फिर उसका *pathname* backup program को दे सकती है। पूरा canonical resolution करने के बाद transformed path की समीक्षा करें: string replacement का एक pass नया traversal sequence बना सकता है, जिसे lexical prefix check स्वीकार कर ले। यह भी जांचें कि backup program transformed in-memory data पढ़ता है या file फिर खोलता है। यदि वह file फिर खोलता है, तो विफल rewrite के बाद मूल input बची रह सकती है।

Linux पर `fs.protected_regular` world-writable sticky directory में किसी दूसरे user की regular file पर `O_CREAT` write रोक सकता है। यह रोक सुरक्षात्मक है, लेकिन यदि shell wrapper write error को अनदेखा करती है, तो वह मूल task file के साथ आगे बढ़ सकती है। Setting, file का owner और directory, तथा विफलता पर wrapper रुकती है या नहीं—इनकी पुष्टि करें। यह path file-disclosure का उम्मीदवार तभी है जब प्रभावी sudo rule wrapper को privileged user के रूप में चलाने दे, caller task input और readable backup destination नियंत्रित करे, और backup utility वास्तव में protected sources शामिल करे। Enumeration के दौरान backup चलाए बिना इन शर्तों का निरीक्षण करें।

### Privileged packet tools पर argument wildcards

`tcpdump` के sudo rule में **argument pattern** का `*` whitespace और slashes से match कर सकता है, इसलिए pathname-जैसी restriction अतिरिक्त option text की अनुमति दे सकती है। यह command के executable path में wildcard से अलग है; पूरा RunAs rule और बाद के denials देखें। यदि options inject किए जा सकते हैं, तो अनुमत invocation और installed [`tcpdump` option semantics](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) तय करते हैं कि `-F`, `-V`, `-r`, `-w`, या `-Z` उपयोगी read/write primitive देता है या नहीं। `-V` capture filenames की list पढ़ता है, मनमानी files का सामान्य dump नहीं। Sudo command की अनुमति देने पर भी AppArmor या दूसरी MAC policy file access रोक सकती है; disk पर profile file होना यह साबित नहीं करता कि वह loaded है या enforcing। निष्कर्ष निकालने से पहले authorization और policy की passive समीक्षा करें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) wildcard के इस अंतर का वर्णन करता है।

Root-capable sudo rule में केवल `tcpdump` executable सूचीबद्ध हो और कोई argument restriction न हो, तो उसकी भी समीक्षा करें। [tcpdump manual](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) के अनुसार, जब `-C` या `-G` saved capture rotate करता है, तब `-z` post-rotation command है; `-Z` या compile-time default उस command के चलने से पहले privileges गिरा सकता है। इस rule को escalation path मानने से पहले प्रभावी sudo rule, installed build, privilege-drop behavior और rotation हो सकती है या नहीं—इनकी पुष्टि करें। Highlighted rule उम्मीदवार है, root command execution का प्रमाण नहीं।

### Sudo के तहत चलने वाली Nmap wrappers

जब sudo-अनुमत `nmap` path shell wrapper हो, तो सटीक अनुमत path और आगे भेजे गए हर option की समीक्षा करें। परिचित `--script` spelling को रोकना हमेशा NSE code loading नहीं रोकता: Nmap का [`--datadir`](https://nmap.org/book/man-misc-options.html) data files चुनता है और NSE scripting enabled होने पर चुनी data directory से [`nse_main.lua` load करता है](https://nmap.org/book/nse-implementation.html)। कुछ installed builds alternate long-option spellings भी स्वीकार करते हैं, इसलिए restrictions की तुलना उस binary के वास्तविक parser से करें। [`--excludefile`](https://nmap.org/book/man-target-specification.html) file-read का अलग surface है; parser errors text उजागर कर सकते हैं। Enumeration में scan चलाए बिना प्रभावी sudo rule, wrapper logic, Nmap version, directory control और MAC policy जांचें।

### Sudo के तहत चलने वाले Mercurial pull hooks

`sudo hg pull /fixed/source` में fixed source होने पर भी **receiving** repository current working directory से चुनी जाती है, जब तक command `-R` से उसे तय न करे। Caller-controlled receiving repo `.hg/hgrc` में hooks परिभाषित कर सकती है और hook sudo RunAs user के रूप में चल सकता है। [Mercurial untrusted user या group के स्वामित्व वाली repository configuration को अनदेखा करता है](https://mercurial-scm.org/help/topics/config), इसलिए इसे code execution मानने से पहले RunAs account के trusted users/groups और सटीक working directory की समीक्षा करें। Passive review के लिए policy और config पढ़ना पर्याप्त है; enumeration के लिए pull या hook न चलाएं।

### Sudo के तहत चलने वाले Git pull hooks

Root-capable `sudo git pull` के सटीक grant के लिए, working directory से चुनी **receiving** repository भी जांचें। Caller-owned repository में executable `post-merge` hook हो सकता है, जो pull में सफल merge होने पर Git process की identity के साथ चलता है; [Git इस hook](https://git-scm.com/docs/githooks) और [pull के merge-versus-rebase व्यवहार](https://git-scm.com/docs/git-pull) का दस्तावेज़ देता है। प्रभावी sudo rule और CWD, active hook path और उसकी permissions, तथा नए commits के साथ merge संभव है या नहीं—इनकी पुष्टि करें। Failed, no-op या केवल rebase वाला pull इस hook path को साबित नहीं करता। Privileged pull चलाए बिना policy और repository metadata देखें।

### Sudo के तहत चलने वाली rsync archive copies

`sudo rsync -a ... /writable/source/* /fixed/destination/` के लिए **sudoers argument pattern** में `*` whitespace से match कर सकता है और source तथा destination के बीच अतिरिक्त option की अनुमति दे सकता है। यह filenames के shell expansion से अलग है। यदि caller source में files रख सकता है और privileged rsync process destination लिख सकता है, तो [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privileged ownership का अनुरोध कर सकता है, जबकि archive mode permission bits बनाए रखता है; इससे संभवतः owned SetUID file बन सकती है। सटीक [sudoers wildcard semantics](https://man7.org/linux/man-pages/man5/sudoers.5.html), rsync version, बाद के denials, filesystem `nosuid` और MAC policy जांचें। Matching rule समीक्षा का उम्मीदवार है, सफल privilege escalation का प्रमाण नहीं।

### Sudo के तहत packet-filter rule export

`iptables` और `iptables-save`—या matching `ip6tables` pair—दोनों के लिए unrestricted root-capable grant में file-write की समीक्षा जरूरी है। `comment` match caller द्वारा चुना rule text स्वीकार करता है, जबकि `iptables-save -f` serialized ruleset को चुने pathname पर लिखता है।<sup>[[20]](#references)[[21]](#references)</sup> उपयोगी payload इस पर निर्भर करता है कि installed backend comments को कैसे serialize करता है और destination file export में अन्य lines स्वीकार करती है या नहीं; `iptables-save` अकेले मनमाना चुना content नहीं देता। सटीक sudo RunAs identity, arguments और exclusions, उपलब्ध match extension, backend और destination permissions जांचें। Enumeration में firewall rules बदले या file लिखे बिना grant देखें।

### Privileged Below logging directory

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ने 0.9.0 से पहले के Below releases को प्रभावित किया, जो world-writable `/var/log/below` directory बनाते थे। यदि service या अनुमत sudo command प्रभावित build को root के रूप में चलाती है, तो non-sticky log directory लिख और traverse कर सकने वाला user privileged process द्वारा log खोलने से पहले किसी log entry को symlink से बदल सकता है। Installed package का patch status, सटीक privileged execution path, प्रभावी directory access, sticky bit और ACLs, तथा `/var/log/below/error_root.log` का metadata देखें। World-writable path या sudo rule अकेले पूरी chain साबित नहीं करते। Sticky directory या vendor backport आकलन बदल सकते हैं। Passive enumeration में केवल metadata देखें; link बनाने या privileged program चलाने की जरूरत नहीं है।

### Writable inputs से privileged support-bundle collection

`sudo` द्वारा अनुमत support-profile script root के रूप में तय log paths पढ़कर उनकी contents profile archive में copy कर सकती है। File reads के लिए वास्तविक script देखें, फिर जांचें कि caller source path या किसी parent directory entry को symlink से बदल सकता है या नहीं। यदि privileged read उस link को follow करे और परिणामी archive caller पढ़ सके, तो protected file उजागर हो सकती है। Sudo grant, writable source path, privileged read और readable output—सभी मौजूद होने चाहिए; केवल writable log या profile filename पर्याप्त नहीं। Enumeration में files बदले या profile बनाए बिना प्रभावी permissions और link metadata देखें। [Nagios XI support guidance](https://support.nagios.com/forum/viewtopic.php?t=62758) इसकी root-run profile script और output archive का उल्लेख करती है, जो दिखाता है कि ऐसे bundles के inputs और output तक पहुंच सीमित क्यों होनी चाहिए।

### Root के रूप में चलने वाली Python archive restore scripts

Python restore script के लिए कड़ा sudo rule हो, तब भी उसके archive input की समीक्षा जरूरी है। यदि caller archive चुन या बदल सकता है और script उसे root के रूप में `tarfile.extractall(filter="data")` से extract करती है, तो filter पर भरोसा करने से पहले interpreter के security updates जांचें। CPython ने CVE-2025-4517 सहित कई symlink और hard-link filter bypass को 3.9.23, 3.10.18, 3.11.13, 3.12.11 और 3.13.4 में ठीक किया। Distribution backports पुराने version में भी fix ला सकते हैं, इसलिए दिखाई गई interpreter version अकेले exposure साबित नहीं करती।<sup>[[16]](#references)[[17]](#references)</sup>

Passive review के लिए सटीक sudo command और script पढ़ें, trace करें कि कौन सा argument archive चुनता है, और जांचें कि current user archive या उसकी containing directory लिख सकता है या नहीं। Installed vendor patch और extraction destination की अलग से पुष्टि करें; `filter="data"` हर untrusted archive को सुरक्षित नहीं बनाता।<sup>[[16]](#references)[[17]](#references)</sup>

### Sudo के तहत चलने वाले machine-learning model loaders

Caller द्वारा चुनी `.pt`, `.pth` या `.ckpt` file की अनुमति देने वाले sudo rule की समीक्षा जरूरी है, यदि privileged script वह file [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` या किसी अन्य pickle-based loader को देती हो। प्रभावी RunAs rule, caller चुने model को बना या बदल सकता है या नहीं, और किसी shell wrapper से Python helper तक वास्तविक argument flow जांचें। `.pth` extension असंबंधित Python site configuration files के लिए भी इस्तेमाल होती है, इसलिए केवल extension model loading का प्रमाण नहीं है। Archive scan या static pickle scan यह साबित नहीं करते कि बाद का load सुरक्षित है; loader का [version-dependent `weights_only` behavior](https://docs.pytorch.org/docs/stable/notes/serialization.html) और किसी allowlisting का निरीक्षण करें। [ML pickle और Fickling notes](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md) देखें। Passive enumeration में model को कभी load या unpack न करें।

### Stored input का sudo के तहत expression parsing

Sudo के जरिए root के रूप में चलने वाली fixed Python script ऐसा text evaluate कर सकती है जिसे lower-privileged user application database में store कर सकता है। TensorFlow में `preprocess_input_exprs_arg_string(value, safe=False)` call `eval` path चुनता है; [TensorFlow advisory](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) unsafe parser और उसके command-line caller के fix का वर्णन करती है। Application का स्पष्ट `safe=False` call अलग समीक्षा मांगता है, भले command-line caller patch किया गया हो। प्रभावी sudo rule, सटीक input row कौन बदल सकता है, filtering या scoring उस row को call तक पहुंचने देती है या नहीं, और installed function का व्यवहार जांचें। TensorFlow version, sudo grant या hardcoded model file अकेले chain साबित नहीं करते। Passive तरीके से script और data flow देखें; enumeration में privileged helper न चलाएं और test expressions न भेजें।

### Sudo-अनुमत needrestart configuration

`needrestart -c` caller द्वारा चुनी Perl configuration file load करके उसकी contents evaluate करता है। यदि `sudo -l` root के रूप में `needrestart` को `-c` की अनुमति देने वाले arguments के साथ चलाता है और caller writable location में readable configuration file चुन सकता है, तो इससे root code execution हो सकता है। सटीक sudo run-as और argument rule जांचें; केवल fixed argument list की अनुमति देने वाला rule इस रास्ते को रोक सकता है। यह needrestart की interpreter-scanning vulnerabilities से अलग है: package update करना या `interpscan` बंद करना unrestricted root `-c` grant को सुरक्षित नहीं बनाता।<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Sudo के तहत दूसरे account के रूप में Python imports

Fixed Python entry point caller द्वारा edit या replace किया जा सकने वाला module import कर सकता है—तब भी जब sudo script को **non-root** service user के रूप में चलाता हो। Literal `from utils import status` के लिए local `utils/__init__.py` और `utils/status.py`, साथ ही package directory permissions भी देखें। Writable file को execution path मानने से पहले script का import path, सटीक अनुमत sudo arguments, और संबंधित action उस import तक पहुंचता है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान files import या script run किए बिना files और permissions जांचें।<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` का सटीक sudo rule केवल readable script मांगता है; file का executable होना या shebang होना जरूरी नहीं। **Missing** local modules भी देखें: यदि script ऐसा module import करती है जिसका filename caller-writable script directory में बनाया जा सकता है, तो Python उसे RunAs identity के अंतर्गत load कर सकता है। प्रभावी sudo rule, interpreter का वास्तविक [module search path](https://docs.python.org/3/library/sys_path_init.html), module built-in या frozen है या नहीं, और import तक पहुंचा जाता है या नहीं—इनकी पुष्टि करें। Script के लिए direct sudo rule में execute-bit और shebang की शर्तें अलग हैं। `sudo -u account` के बाद caller द्वारा दिए tokens जोड़ने वाली अलग wrapper के लिए भी argument-flow review जरूरी है: उन tokens में दूसरा `-u` तभी मायने रखता है जब invoked sudo policy परिणामी identity की अनुमति देती हो। Static strings अकेले इनमें से कोई रास्ता साबित नहीं करतीं।

### Caller-controlled configuration के साथ sudo के तहत चलने वाला Apache

यदि sudo rule caller-controlled `-f` configuration file के साथ privileged `apachectl`, `apache2ctl` या `httpd` invocation की अनुमति देता है, तो उस file और parent directory permissions की समीक्षा करें। Apache का [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) directive module name के बाद **module filename** लेता है; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) भी file load करता है। [`Include` और `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) configuration बढ़ा सकते हैं या errors के जरिए file contents उजागर कर सकते हैं। Custom wrapper इन paths की validation, privileges drop या arguments सीमित कर सकती है, इसलिए writable config code execution का प्रमाण नहीं, केवल समीक्षा का उम्मीदवार है। निष्कर्ष निकालने से पहले path canonicalization, symlinks और directive parsing जांचें।

### Caller-controlled configuration के साथ sudo के तहत चलने वाला nginx

Unrestricted root-capable `nginx` rule [`-c` से दूसरी configuration चुनने की अनुमति दे सकता है](https://nginx.org/en/docs/switches.html)। सटीक sudo arguments और exclusions, caller configuration दे सकता है या नहीं, और परिणामी master या workers की protected paths तक पहुंच बनी रहती है या नहीं—इनकी समीक्षा करें। चुना `root` और `autoindex` नए listener के जरिए files उजागर कर सकते हैं; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) privileged file-write path दे सकता है, लेकिन DAV module default रूप से built नहीं होता। इसका मौजूद होना, listener तक पहुंच, file permissions और temporary-file behavior जांचना जरूरी है। [`error_log` directive](https://nginx.org/en/docs/ngx_core_module.html#error_log) भी चुनी file पर लिख सकती है; `/etc/ld.so.preload` जैसी संवेदनशील configuration file में logs लिखना escalation path तभी बनता है जब प्रभावी privileged writer और नियंत्रित log record मौजूद हों। `sudo -l` में executable highlight समीक्षा का संकेत है, यह प्रमाण नहीं कि इनमें से कोई रास्ता काम करता है। Passive enumeration में nginx शुरू या reconfigure न करें।

### Privileged Bash prompts में pattern comparison

जब sudo-अनुमत Bash script caller से value पढ़कर `[[ "$expected" == $entered ]]` से जांचती है, तो Bash unquoted right-hand operand को pattern की तरह समझता है। इसलिए wildcard, expected value जाने बिना भी comparison को संतुष्ट कर सकता है। Operand को quote करने (`[[ "$expected" == "$entered" ]]`) से literal string comparison होता है। सटीक sudo rule, prompt तक पहुंच और comparison के बाद script क्या करती है—इनकी समीक्षा करें; syntax अकेले exploitable path साबित नहीं करता। Enumeration में expected value न दिखाएं। [Bash conditional constructs reference](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html) देखें।

### Sudo के तहत चलने वाले helpers जो file download और execute करते हैं

Caller द्वारा चुना URL स्वीकार करने, response को disk पर लिखने और बाद में उस file को interpreter या shell से चलाने वाली custom helper के लिए unrestricted root-capable sudo grant हो, तो dataflow की समीक्षा करें। [Sudoers में command entry के साथ arguments न दिए हों तो कोई भी argument दिया जा सकता है](https://man7.org/linux/man-pages/man5/sudoers.5.html); fixed executable path यह सीमित नहीं करता कि arguments क्या चुन सकते हैं। Installed helper में वास्तविक URL validation, output path, success branch और उसके बाद होने वाले execution की पुष्टि करें। Matching libcurl import या printable string अकेले इस chain को साबित नहीं करते।

Relative path का उपयोग करने वाली caller-controlled working directory में **relative path** के साथ helper file लिखे और बाद में execute करे, तो fixed output basename भी उस बीच बदली जा सकती है। Root-owned file का rename या replacement directory write/search access और sticky-bit restrictions से नियंत्रित होता है, केवल file mode से नहीं; [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) देखें। जांचें कि helper बाद में path फिर खोलती है या पहले से खुले descriptor का उपयोग करती है, और लिखने से पहले trusted directory में जाती है या नहीं। Enumeration में sudo policy, helper और directory metadata का passive निरीक्षण करें; privileged download या race न चलाएं।

Root-sudo download helper Bash command string, जैसे `curl <caller input> -o <fixed output>`, बनाती हो तो **argument** injection भी संभव है। Whitespace रोकने वाला filter फिर भी [Bash brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) को नहीं रोकता: unquoted comma-separated elements अलग curl arguments बन सकते हैं। यदि input fixed `-o` से पहले curl तक पहुंचे, तो caller द्वारा दिया output option helper की identity के अंतर्गत पहली URL का destination चुन सकता है; [curl output options को URL के क्रम से जोड़ता है](https://curl.se/docs/manpage.html#-o)। सटीक shell, quoting, input validation, प्रभावी sudo rule, curl argument order और समर्थित URL schemes, तथा caller fetch किए गए bytes नियंत्रित करता है या परिणाम पढ़ सकता है या नहीं—इनकी पुष्टि करें। PyInstaller-packaged executable में Python application logic हो सकती है, लेकिन केवल उसका packaging marker या `curl` string यह data flow साबित नहीं करता। अधिकृत होने पर सीमित offline copy की समीक्षा करें; routine enumeration में helper न चलाएं और attacker-selected data fetch न करें।

Root-sudo shell script अगर [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) call करती है, तो वह केवल unused name चुनती है; file **बनाती नहीं**। यदि script बाद में उस नाम को ऐसी directory में बनाती है जिसे दूसरा user प्रभावित कर सकता है, फिर उसे दोबारा खोलती है और उसकी contents root के `authorized_keys` जैसे protected destination में जोड़ती है, तो temporary-file race की समीक्षा करें। सटीक sudo rule, directory और file ownership, creation तथा reopen का क्रम, kernel protections, और privileged write वास्तव में attacker-controlled bytes का उपयोग करती है या नहीं—इनकी पुष्टि करें। `mktemp -u` string या writable `/tmp` अकेले race साबित नहीं करते। Enumeration में script और path metadata देखें; उसे चलाएं नहीं और temporary file पर race न करें।

## रक्षात्मक नोट्स

- sudo के जरिए interpreters या interactive editors देने से बचें।<sup>[[1]](#references)</sup>
- `tee` जैसे generic file writers को unrestricted operands के साथ अनुमति न दें। ऐसा root-owned wrapper उपयोग करें जो fixed destination चुने और caller-controlled paths अस्वीकार करे।<sup>[[2]](#references)</sup>
- Fixed, root-owned wrappers को प्राथमिकता दें जो एक सीमित administrative action करें।<sup>[[1]](#references)[[2]](#references)</sup>
- यदि interpreter अनिवार्य हो, तो सटीक script path सीमित करें और user-controlled arguments, writable imports, `PYTHONPATH`, तथा असुरक्षित environment preservation रोकें।<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- यदि file editing जरूरी हो, तो सटीक file path सीमित करें और patched sudo versions तथा सख्त environment handling के साथ `sudoedit` पर विचार करें।<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`, `env_keep`, writable working directories, writable module/import paths, `NOEXEC`, `use_pty` और logging की समीक्षा करें, लेकिन इन्हें पूर्ण sandbox न मानें।<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
