## Interpretery dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interpreter jako root, traktuj to jako bezpośrednie wykonanie kodu. Interpretery są przeznaczone do wykonywania dowolnego kodu, dlatego reguła zezwalająca na użycie `python3`, `perl`, `ruby`, `lua`, `node` lub podobnych plików binarnych jest zwykle równoważna wykonywaniu poleceń z uprawnieniami root, chyba że argumenty są ściśle ograniczone i walidowane.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Typowy przebieg analizy: najpierw wyświetl uprawnienia użytkownika, a następnie wykonaj instrukcję Pythona za pomocą opcji `-c` interpretera.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Poniżej przedstawiono inne przykłady interpreterów; wymienione interpretery dokumentują wykonywanie kodu inline lub korzystanie z API procesów potomnych.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Dokładna ścieżka ma znaczenie. Jeśli reguła sudo zezwala na `/usr/bin/python3`, podczas weryfikacji użyj dokładnie tej ścieżki.<sup>[[2]](#references)</sup>

Glob dla pliku wykonywalnego sudo, taki jak `/usr/bin/python*`, może również dopuścić Python 2 w przypadku skryptu napisanego dla Python 3. Jeśli skrypt wywołuje `input()` z tekstem kontrolowanym przez wywołującego, [Python 2 interpretuje ten tekst jako wyrażenie](https://docs.python.org/2/library/functions.html#input); jawne wywołanie interpretera nadpisuje shebang skryptu. Zanim uznasz to za ścieżkę do wykonania kodu, sprawdź zainstalowane pasujące pliki binarne, efektywną tożsamość RunAs i politykę argumentów, odmowy oraz dostępne dane wejściowe.

Stała ścieżka skryptu w regule sudo pozwalającej na działanie z uprawnieniami roota nie ogranicza tego, co skrypt wykonuje. W przypadku czytelnego wrappera Bash sprawdź, czy jego pierwsze polecenie wykonywalne używa nieujętego w cudzysłowy parametru pozycyjnego, takiego jak `$1`, jako **słowa polecenia**, gdy sudo zezwala na argumenty wybrane przez wywołującego. Potwierdź efektywną tożsamość RunAs, politykę haseł i argumentów, późniejsze odmowy oraz faktycznie wykonywaną gałąź skryptu; `NOEXEC`, stała bezpieczna lista argumentów lub wrapper weryfikujący polecenie mogą zmienić wynik. Podczas enumeracji przeanalizuj krótki skrypt statycznie, zamiast uruchamiać go z testowym poleceniem.

Nieograniczona reguła sudo dla `dotnet`, pozwalająca na działanie z uprawnieniami roota, również wymaga sprawdzenia interpretera. Jeśli zainstalowany jest .NET SDK, [`dotnet fsi` uruchamia kod F# interaktywnie lub ze skryptu](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), a [`dotnet run` wykonuje projekt ze źródeł](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Najpierw potwierdź efektywną tożsamość RunAs i dokładną politykę argumentów: reguła ograniczona do konkretnego bezpiecznego podpolecenia lub zaufanej aplikacji stanowi inne uprawnienie, a instalacja zawierająca wyłącznie środowisko uruchomieniowe może nie mieć poleceń SDK. Sama nazwa pliku wykonywalnego jest wskazówką do weryfikacji, a nie dowodem możliwości wykonania kodu.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` dozwolone przez sudo: dowolny uprzywilejowany zapis do pliku

GNU `tee` kopiuje standardowe wejście do każdej ścieżki podanej jako operand plikowy. Dlatego reguła sudo zezwalająca na uruchomienie `/usr/bin/tee` jako root z argumentami kontrolowanymi przez użytkownika daje możliwość tworzenia lub nadpisywania dowolnych plików z uprawnieniami roota. Dodanie `-a` zmienia tę możliwość na dopisywanie. Tag `PASSWD:` dotyczy uwierzytelniania sudo; sam w sobie nie ogranicza miejsca docelowego ani bajtów odczytywanych ze standardowego wejścia.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Najpierw sprawdź dokładną regułę. W autoryzowanym systemie testowym zweryfikuj tę możliwość wyłącznie przy użyciu tymczasowego miejsca docelowego, które można bezpiecznie utworzyć. Końcowe `>/dev/null` jedynie ukrywa kopię wysyłaną przez `tee` na standardowe wyjście.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Umieszczenie `sudo` przed procesem zapisującym dane nie podnosi uprawnień późniejszego przekierowania powłoki, ponieważ to powłoka wywołującego otwiera plik docelowy. Zapis musi wykonywać proces z podwyższonymi uprawnieniami, jak w powyższym potoku.<sup>[[1]](#references)[[15]](#references)</sup>

Po potwierdzeniu możliwości zapisu wybierz odpowiedni punkt wejścia do wykonania kodu jako root z sekcji [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). W jednym zaobserwowanym łańcuchu root użył `tee`, by utworzyć krótkotrwały plik w katalogu `/etc/cron.d/`, uruchomić backdoor za pośrednictwem skryptu kontrolowanego przez użytkownika, a następnie usunąć plik cron po wykonaniu. Usunięcie pliku cron zapobiegło utworzeniu długotrwałego wpisu persistence, choć logi systemowe nadal zawierały ślady tej aktywności.<sup>[[27]](#references)</sup>

## Edytory dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interaktywny edytor jako root, potraktuj to jako powierzchnię umożliwiającą wykonanie poleceń, a nie jako nieszkodliwe uprawnienie do edycji plików. Edytory często potrafią wykonywać polecenia powłoki, odczytywać dowolne pliki, zapisywać dowolne pliki lub uruchamiać zewnętrzne narzędzia z poziomu edytora.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Typowy przebieg sprawdzania: wyświetl uprawnienia użytkownika, a następnie uruchom przez sudo każdy dozwolony edytor lub pager.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Wykonywanie poleceń w nano

Gdy `nano` jest dozwolone przez sudo, wykonywanie poleceń może być dostępne z poziomu interfejsu edytora.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Następnie wpisz polecenie, takie jak `id` lub `/bin/sh`, w wierszu poleceń nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Jeśli interaktywna powłoka nie ma użytecznych strumieni terminala, ta forma przekierowania mapuje jej standardowe wyjście i standardowe wyjście błędów na deskryptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Dokładna sekwencja klawiszy może się różnić w zależności od wersji nano i opcji kompilacji, ale problem z bezpieczeństwem pozostaje ten sam: edytor działa jako root i może uruchamiać zewnętrzne polecenia.<sup>[[1]](#references)[[12]](#references)</sup>

### Inne typowe sposoby ucieczki z edytora

Edytory w stylu Vim często umożliwiają wykonywanie poleceń za pomocą `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Programy pager, takie jak `less`, mogą również umożliwiać uruchomienie powłoki.<sup>[[14]](#references)</sup>

Regułę sudo zezwalającą na uruchomienie `apport-cli` jako root warto sprawdzić pod kątem działania pagera. W podatnych wersjach Apport raport o awarii mógł być otwierany w `less` z rozmiarem terminala ustawianym przez atakującego; pager mógł wówczas zapewnić powłokę root, jeśli spełnione były szczególne warunki dotyczące sudo i pagera. Zanim uznasz daną wersję za podatną, sprawdź efektywną regułę sudo, konfigurację pagera oraz poprawkę w pakiecie dystrybucji. Podczas pasywnego rozpoznania odczytaj metadane pakietu i polityki, nie wywołując awarii ani nie otwierając uprzywilejowanego raportu. [Wpis CVE w Ubuntu](https://ubuntu.com/security/CVE-2023-1326) zawiera informacje o poprawionych wersjach pakietów dla poszczególnych wydań, w tym poprawkach backportowanych.

```text
!/bin/sh
```

## Inne zagrożenia związane z regułami sudo i doas

Zacznij od `sudo -l`, `sudo -V` i wszelkich mających zastosowanie zasad `doas`. Odczytuj dozwolone polecenie, użytkownika, na którego można się przełączyć, argumenty, środowisko i ustawienia domyślne łącznie. Uprawnienie do uruchamiania poleceń jako nie-rootowe konto usługi nadal może ujawnić pliki tego konta lub zapewnić drogę do roota.

Skrypt Python dozwolony przez sudo może nadal uruchamiać polecenie powłoki z tożsamością określoną przez RunAs, jeśli dane wejściowe pod kontrolą wywołującego są interaktywnie pobierane i konkatenowane w [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Czarna lista znaków interpunkcyjnych powłoki nie wystarcza, by uznać to za bezpieczne: [powłoka rozpoznaje również podstawianie poleceń `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Potwierdź, że dozwolone argumenty prowadzą do gałęzi pobierającej dane wejściowe, że dane te trafiają do polecenia powłoki bez bezpiecznej walidacji, a efektywna polityka sudo zezwala na zamierzonego użytkownika RunAs. Sama ścieżka skryptu lub wywołanie `os.system()` to jedynie wskazówka do dalszej analizy; sprawdź kod źródłowy bez uruchamiania uprzywilejowanego skryptu.

Efektywne uprawnienie sudo roota do `chattr` może usunąć atrybut niezmienności (`i`) pliku, ale samo w sobie nie daje możliwości zapisu ani nowej tożsamości. [Podręcznik `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) informuje, że atrybut blokuje modyfikacje i że może go zmienić tylko root lub proces z `CAP_LINUX_IMMUTABLE`. Sprawdź dokładną politykę argumentów sudo i obsługę systemu plików, a następnie osobno zweryfikuj, czy wywołujący może zapisywać plik po usunięciu atrybutu oraz czy korzysta z niego odbiorca o wyższej tożsamości. Na przykład podmiana powłoki logowania wymaga również poświadczeń akceptowanych przez konto docelowe i faktycznego logowania przez tę powłokę. Podczas enumeracji analizuj politykę, atrybuty plików i uprawnienia, ale ich nie zmieniaj.

Jeśli sudo wymaga zarówno hasła, jak i jednorazowego kodu, traktuj te wymagania niezależnie od uprawnień do uruchomienia polecenia. Czytelny plik `.google_authenticator` zawiera poufny materiał seed, a stary hash hasła aplikacji lub bazy danych jest jedynie możliwym hasłem bieżącego konta; żaden z nich nie dowodzi, że drugi czynnik jest akceptowany przez efektywną konfigurację PAM. Po uzyskaniu upoważnienia sprawdź dokładny RunAs i argumenty: nieograniczone uprawnienie roota do RubyGems `gem` może udostępnić jego polecenie edytora ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ale ograniczone uprawnienie lub nieudane uwierzytelnienie — nie. Pasywna enumeracja powinna wykazywać ścieżki i politykę, nie ujawniając seeda, nie odzyskując hasła, nie generując kodu ani nie uruchamiając uprzywilejowanego polecenia.

Nieograniczone uprawnienie sudo do `knife` z możliwością działania jako root wymaga analizy na poziomie interpretera: [Chef dokumentuje, że `knife exec -E` lokalnie interpretuje ciąg Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Zweryfikuj, czy efektywna reguła sudo zezwala na podpolecenie `exec` i dostarczony przez wywołującego argument `-E`, zamierzoną tożsamość RunAs oraz wszelkie pasujące odmowy poleceń lub ustalone argumenty. Zainstalowany plik binarny lub reguła ograniczona do innych podpoleceń to jedynie wskazówka. Pasywna enumeracja powinna wykazać regułę bez uruchamiania `knife`.

Dokładne uprawnienie sudo do interaktywnego `msfconsole` z możliwością działania jako root jest równie wrażliwe: [GTFOBins opisuje jego konsolę `irb`](https://gtfobins.org/gtfobins/msfconsole/), która może odziedziczyć tożsamość sudo. Potwierdź efektywnego użytkownika RunAs, dozwoloną listę argumentów, odmowy poleceń, ograniczenia `NOEXEC` lub inne ograniczenia, zachowanie zainstalowanej konsoli oraz możliwość podania przez wywołującego danych wejściowych w trybie interaktywnym. Samo wyróżnienie ścieżki to jedynie wskazówka do analizy; podczas pasywnej enumeracji nie uruchamiaj konsoli.

We FreeBSD nawet reguła sudo ograniczona do `pkg update` jako root i `pkg install *` wymaga sprawdzenia zaufania do repozytorium. Ustal, czy wywołujący może zapisywać do `/etc/hosts` i czy *efektywna* konfiguracja włączonego repozytorium używa hosta HTTP z `signature_type: none`. [Podręcznik FreeBSD `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) informuje, że `none` wyłącza sprawdzanie podpisów; samo `pkg+http` tego nie dowodzi. Pakiet może zawierać skrypty instalacyjne ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), więc wywołujący, który faktycznie kontroluje punkt końcowy repozytorium i może wybrać pakiet, może przekroczyć granicę roota. Przed takim wnioskiem zweryfikuj nadpisania repozytoriów, rozwiązywanie SRV/luster, efektywne argumenty sudo, wybór pakietu i wykonywanie skryptów. Podczas enumeracji przeglądaj politykę i małe lokalne pliki konfiguracyjne, nie przekierowując nazw ani nie uruchamiając `pkg`.

Uprawnienie sudo do `apt-get update` i `apt-get upgrade` z możliwością działania jako root również wymaga sprawdzenia zaufania do repozytoriów, gdy sudo zachowuje zmienną `http_proxy` kontrolowaną przez wywołującego. Ustal, czy efektywna konfiguracja APT faktycznie korzysta z tej zmiennej i na które żądania do włączonych repozytoriów może ona wpływać; sam proxy nie może zastąpić pakietów z archiwum uwierzytelnionego zaufanym kluczem podpisującym. [Podręcznik transportu HTTP APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) opisuje priorytety proxy, a [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — sprawdzanie podpisów, nadpisania dla niezaufanych repozytoriów i potwierdzanie instalacji nieuwierzytelnionych pakietów. Potwierdź dokładne RunAs i argumenty sudo, politykę uwierzytelniania repozytorium, wymagane interaktywne potwierdzenia oraz to, czy wybrane uaktualnienie uruchamia skrypty pakietu jako root. Podczas pasywnej enumeracji przeglądaj politykę i lokalną konfigurację; nie przekierowuj ruchu pakietów ani nie uruchamiaj uaktualnienia.

Reguła sudo umożliwiająca `snap install` jako root może stanowić granicę między pakietem a kodem, jeśli argumenty pozwalają wywołującemu wybrać lokalny snap i liberalny tryb instalacji. [Dokumentacja Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) informuje, że `--dangerous` pomija sprawdzanie asercji lokalnego snapa, a `--devmode` łagodzi ograniczenia; [hook instalacyjny może zostać uruchomiony podczas pierwszej instalacji](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Zanim stwierdzisz, że możliwy jest dostęp do chronionych plików hosta, sprawdź dokładną politykę argumentów/RunAs sudo, kto kontroluje plik snapa, czy zainstalowany snapd akceptuje te tryby oraz tożsamość i ograniczenia hooka. Sam plik binarny `snap` lub reguła wyglądająca na wieloznaczną nie dowodzą istnienia takiego łańcucha. Pasywna enumeracja nie powinna instalować pakietu ani uruchamiać jego hooka.

W przypadku dokładnego uprawnienia sudo do nirootowego pliku binarnego, który odczytuje poświadczenia, najpierw sprawdź przyznany plik i jego uprawnienia bez uruchamiania go. Osadzone sprawdzanie hasła może być widoczne wyłącznie jako szerokie znaki; [GNU `strings` opisuje ekstrakcję 16-bit little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Widoczny ciąg nie dowodzi, że jest akceptowanym hasłem ani że gałąź sukcesu ujawnia aktualne poświadczenie. Osobno potwierdź zachowanie pliku binarnego, dostęp konta docelowego do chronionych danych, ważność poświadczeń oraz wszelkie późniejsze przejście na inne konto lub grupę. Jeśli to konto należy do `docker`, zweryfikuj dostęp do gniazda i tożsamość demona — rootful lub rootless — zanim wywnioskujesz dostęp roota hosta; [Docker opisuje konsekwencje przynależności do tej grupy na poziomie roota](https://docs.docker.com/engine/install/linux-postinstall/). Rutynowa enumeracja powinna wykazać regułę sudo i członkostwo w grupie bez uruchamiania pliku binarnego ani zrzucania jego ciągów.

Wieloznaczna reguła sudo dla skryptów konserwacyjnych aplikacji wymaga sprawdzenia czegoś więcej niż samej ścieżki skryptu. Sprawdź, czy dozwolony skrypt przyjmuje nieograniczone argumenty lub odczytuje ustawienia, które może modyfikować konto aplikacji o niższych uprawnieniach, a następnie prześledź te wartości aż do poleceń powłoki lub środowiska podprocesu. Na przykład ZoneMinder: [`zmupdate.pl` składa polecenie `mysqldump` i wykonuje je przez `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), a [`zmdc.pl` kopiuje ustawienie `ZM_LD_PRELOAD` do `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) przed uruchomieniem demonów. Reguła sudo pozwalająca uruchomić dowolny z tych skryptów jako root może przekroczyć granicę zaufania, jeśli odpowiednie dane wejściowe są pod kontrolą użytkownika i trafiają do tego kodu w zainstalowanej wersji. Sprawdź efektywną regułę sudo, uprawnienia do konfiguracji aplikacji i kod źródłowy skryptu; sama reguła wieloznaczna lub ustawienie to wskazówka do analizy, a nie dowód wykonania.

- `SETENV`, `env_keep`, `secure_path` i `LD_PRELOAD` mogą zmienić wąskie polecenie w wektor hijackingu importu, biblioteki lub `PATH`. Zobacz [przewodnik po zmiennych środowiskowych](../linux-basics/linux-environment-variables.md) oraz [nadużycia SUID/linkera](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Dokładne uprawnienie sudo z `SETENV` do wrappera powłoki, który uruchamia ustalony skrypt Python z dosłownym importem, również wymaga sprawdzenia jednego etapu. `secure_path` ogranicza wyszukiwanie poleceń przez powłokę, ale nie wyszukiwanie modułów Python przez [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); opcje [`-E` i `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) powodują, że Python ignoruje tę zmienną środowiskową. Zanim uznasz to za wykonanie kodu, potwierdź efektywne tagi i odmowy sudo, gałąź wrappera, opcje interpretera, rozwiązywanie importu oraz katalog wyszukiwania zapisywalny przez wywołującego. Krótkie skrypty sprawdzaj statycznie; nie uruchamiaj uprzywilejowanego wrappera.

Dokładne uprawnienie sudo do `neofetch ""` z możliwością działania jako root może nadal ładować konfigurację powłoki, gdy obowiązujące domyślne ustawienia sudo zachowują zmienną `XDG_CONFIG_HOME` kontrolowaną przez wywołującego. [Loader konfiguracji Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) wczytuje `neofetch/config.conf` lub `neofetch/config` z tego katalogu; pusta lista argumentów nie zapobiega temu wyszukiwaniu. Zachowana zmienna lub samo zainstalowanie Neofetch to jedynie wskazówka do analizy. Sprawdź politykę i metadane plików bez uruchamiania uprzywilejowanego polecenia ani wyświetlania zawartości konfiguracji; zobacz [obsługę środowiska w sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Sprawdź, czy dokładna reguła sudo zezwala na tę opcję, czy zainstalowany Facter ją obsługuje i czy wywołujący kontroluje katalog. Reguła z ustalonymi argumentami, jawna odmowa polecenia lub wyłączone custom facts mogą zmienić wynik. Pasywna enumeracja powinna wykazać potencjalne uprawnienie bez uruchamiania Facter ani odczytywania zawartości plików faktów.

W przypadku dokładnego uprawnienia sudo do skryptu z możliwością działania jako root i tagiem `SETENV` sprawdź niekwalifikowane nazwy poleceń, takie jak `find`, oraz efektywną wartość `PATH` po zastosowaniu polityki sudo i inicjalizacji skryptu. Potwierdź obowiązujące [zasady środowiska sudoers i `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), ewentualne wpisy `NOSETENV`/`NOEXEC` lub odmowy, przepływ wykonania w skrypcie i plikach wczytywanych przez `source`, a także katalog wyszukiwania, w którym wywołujący może umieścić plik wykonywalny. Czytelny skrypt zawierający niekwalifikowane polecenie to wskazówka do analizy, a nie dowód uprzywilejowanego wykonania; sprawdź go bez uruchamiania reguły sudo.

Potwierdź efektywne RunAs, argumenty polecenia i odmowy, bieżący katalog zapisywalny przez wywołującego, przepływ danych WASM do gałęzi oraz to, czy ta gałąź wywołuje helper. Ustalona reguła sudo `runchdir`, `os.Chdir` lub [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) może zmienić lokalizację wyszukiwania. Sama współobecność tych elementów w kodzie to jedynie potencjalny przypadek; sprawdź kod źródłowy bez uruchamiania Go, WASM ani helpera.
- `sudoedit` i symbole wieloznaczne argumentów wymagają dokładnego sprawdzenia wersji i reguły; [lista kontrolna](linux-privilege-escalation-checklist.md) obejmuje problem edycji plików przez sudoedit. W przypadku międzyużytkowego uprawnienia `sudoedit` do ścieżki z symbolem wieloznacznym sprawdź efektywne ustawienie `sudoedit_follow` lub `FOLLOW`, `sudoedit_checkdir`, rozwiązaną ścieżkę docelową oraz to, kto może podmienić każdy wpis katalogu nadrzędnego. Pierwsze ustawienie może pozwolić na podążanie za symlinkiem, a wyłączenie drugiego usuwa kontrole katalogów zapisywalnych; żadne z nich samo w sobie nie dowodzi możliwości zapisu do pliku innego użytkownika. Przed wyciągnięciem takiego wniosku potwierdź zainstalowaną politykę sudo i dokładnie dopasowane argumenty. Zobacz [definicje opcji sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- W regule polecenia sudoers symbol wieloznaczny argumentu może dopasowywać białe znaki, a nie tylko znaki ścieżki. Reguła dla polecenia umożliwiającego odczyt z argumentem takim jak `/restricted/*` może zatem dopuszczać dodatkowy argument pliku po pasującym prefiksie. Sprawdź dokładnego użytkownika RunAs, ścieżkę polecenia, wzorzec argumentów i późniejsze odmowy; wykazany odczyt pliku nie oznacza wykonania polecenia. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) rozróżnia wzorce argumentów od wzorców ścieżek poleceń.
- Wzorzec argumentu wyglądający jak ścieżka może też dopasować `../`. Na przykład reguła `node /opt/scripts/*.js` z możliwością działania jako root może pozwalać wywołującemu wskazać kontrolowany plik JavaScript spoza `/opt/scripts`, jeśli podana nazwa ścieżki nadal zaczyna się od `/opt/scripts/` i po segmentach katalogu nadrzędnego rozwiązuje się do tego pliku. To wzorzec **argumentu**; wzorzec ścieżki polecenia dla pliku wykonywalnego Node ma inne zasady dopasowywania ukośników. Przed uznaniem tego za wykonanie kodu sprawdź efektywną regułę, późniejsze odmowy, rozwiązywanie ścieżki, kontrolę nad docelowym plikiem oraz ewentualne ograniczenia wyrażeń regularnych lub digestów sudoers. Zobacz [zasady symboli wieloznacznych w sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) i [dokumentację wiersza poleceń Node](https://nodejs.org/api/cli.html).
- Archiwizatory i inne programy narzędziowe mogą mieć hooki wykonawcze. Sprawdź dokładne dozwolone argumenty w [GTFOBins](https://gtfobins.github.io/), zamiast zakładać, że polecenia uruchamiają tylko powłoki lub interpretery.
- Nieograniczona reguła sudo do `qpdf` z możliwością działania jako root może ujawnić uprzywilejowany plik przez załączniki PDF: qpdf 10.2 i nowsze obsługują `--empty` oraz `--add-attachment file ... --` wraz z wyjściowym plikiem PDF. Jeśli uprzywilejowany proces może odczytać wybrane źródło i zapisać PDF w miejscu dostępnym dla wywołującego, plik wyjściowy może zawierać bajty źródła. Zanim stwierdzisz, że możliwe jest ujawnienie pliku, sprawdź efektywne argumenty i wykluczenia sudo, wersję qpdf, dostęp do źródła i ścieżkę wyjściową. Odczyt klucza SSH roota jest przydatny do logowania tylko wtedy, gdy klucz jest prawidłowy, a logowanie roota przez SSH jest dozwolone. Zobacz [opcje załączników qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Ponowne użycie znacznika czasu sudo zależy od polityki cache, właściciela, terminala/sesji i uprawnień. Kontrole opisuje [przewodnik po eskalacji uprawnień](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens).
- `doas` ma własne reguły i konfigurację. Sprawdź dozwolone polecenia i zapisywalne ścieżki konfiguracji zgodnie z opisem w [sekcji doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Narzędzia budowania i pakietowania uruchamiane przez sudo

Nieograniczone uprawnienie sudo do Foundry `forge` może mieć znaczenie nawet wtedy, gdy tożsamość RunAs oznacza innego użytkownika niebędącego rootem. Opcje kompilatora, takie jak `--use`, mogą wskazać lokalny plik wykonywalny, a `forge flatten -o` wybiera plik wyjściowy. Zanim uznasz to uprawnienie za możliwe do wykorzystania, sprawdź wersję zainstalowanego Forge, dokładne argumenty sudo, dostęp do projektu i ścieżek kompilatora, uprawnienia do pliku wyjściowego oraz efektywne środowisko. Względny plik wykonywalny helpera wyszukiwany przez `PATH` to ścieżka zależna od wersji i środowiska, a nie właściwość, którą należy zakładać dla każdej kompilacji Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Nieograniczone uprawnienie do `pacman` z możliwością działania jako root pozwala na więcej niż zapytania o pakiety: `-U` przyjmuje lokalny pakiet, pakiety mogą zawierać skrypty instalacyjne, a `--hookdir` wybiera inny katalog hooków. Przed testowaniem sprawdź efektywną regułę sudo, ograniczenia argumentów i wykluczenia; pasywna enumeracja nie wymaga instalowania pakietu ani uruchamiania hooka.<sup>[[25]](#references)[[26]](#references)</sup>

Ustalony wrapper powłoki sudo może również instalować określoną zależność npm, a następnie uruchamiać aplikację Node. Sprawdź dokładną regułę RunAs, czy pakiet jest już zainstalowany, efektywne `HOME` i `userconfig` npm, konfigurację projektu lub nadpisania w wierszu polecenia oraz to, czy użytkownik o niższych uprawnieniach kontroluje rejestr lub pakiet zwracany dla tej nazwy. [Dokumentacja npm opisuje wyszukiwanie pliku `.npmrc` dla użytkownika i projektu](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); zachowanie `HOME` przez sudo zależy od zainstalowanej polityki i dystrybucji, więc plik `.npmrc` zapisywalny przez użytkownika może być odczytywany przez uprzywilejowany proces npm albo nie. Jeśli nowo zainstalowany pakiet zostanie zaimportowany przez uprzywilejowaną aplikację, jego kod modułu może działać z tożsamością tej aplikacji. Skrypty uruchamiane podczas instalacji to osobna ścieżka zależna od wersji i konfiguracji; [dokumentacja npm opisuje ich cykl życia i obsługę użytkownika](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Sama ścieżka `.npmrc` lub linia `npm install` to jedynie wskazówka do analizy. Podczas pasywnej enumeracji sprawdź regułę, krótki wrapper, ścieżki konfiguracji i pochodzenie pakietu, nie instalując pakietu ani nie uruchamiając aplikacji.

Uprawnienie sudo do `pip` lub `pip3 download` z możliwością działania jako root również wymaga sprawdzenia procesu budowania pakietu, gdy argumenty pozwalają wywołującemu wskazać niezaufaną dystrybucję źródłową — nawet jeśli wzorzec URL-a ogranicza go do lokalnej usługi i sufiksu `.tar.gz`. `pip download` akceptuje URL-e archiwów i rozwiązuje metadane pakietu; przygotowanie sdist może uruchomić backend budowania lub kod legacy `setup.py`, zanim archiwum zostanie jedynie zapisane. Potwierdź dokładnego użytkownika RunAs i regułę argumentów sudo, możliwość publikowania lub zastępowania wybranego archiwum przez wywołującego oraz to, czy dana wersja pip rzeczywiście przygotowuje metadane. Ustalony, zaufany plik archiwum lub wheel nie dowodzi istnienia tej ścieżki. Podczas pasywnej enumeracji nie pobieraj ani nie buduj niezaufanego pakietu. Zobacz [polecenie download w pip](https://pip.pypa.io/en/stable/cli/pip_download/), [interfejs build-system](https://pip.pypa.io/en/stable/reference/build-system/) oraz [wskazówki dotyczące bezpiecznej instalacji](https://pip.pypa.io/en/stable/topics/secure-installs/).

Reguła sudo zezwalająca na `pip install` z lokalną ścieżką projektu wybraną przez wywołującego tworzy bardziej bezpośrednią granicę procesu budowania. [pip akceptuje lokalne katalogi projektów](https://pip.pypa.io/en/stable/topics/local-project-installs/) i wywołuje ich system budowania; [backend budowania uruchamia hooki kontrolowane przez projekt](https://pip.pypa.io/en/stable/reference/build-system/). Zanim uznasz regułę za uprzywilejowane wykonanie kodu, potwierdź efektywną tożsamość RunAs, dokładne ograniczenia i odmowy argumentów, kontrolę nad wybranym projektem oraz zachowanie zainstalowanego pip/backendu. Ustalony zaufany projekt lub reguła wykluczająca ścieżki wybrane przez wywołującego nie dowodzą istnienia tej ścieżki. Podczas pasywnej enumeracji sprawdź regułę i metadane projektu bez instalowania pakietu.

Nieograniczone uprawnienie do `easy_install` z możliwością działania jako root to powiązany, dotyczący przestarzałego narzędzia sygnał do sprawdzenia budowania pakietów. [Dokumentacja Setuptools](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) informuje, że Easy Install przyjmuje lokalny katalog projektu i buduje dystrybucje źródłowe; podczas tego procesu projekt kontrolowany przez wywołującego może uruchomić `setup.py` z tożsamością sudo. Potwierdź efektywne konto RunAs, dokładne ograniczenia polecenia i argumentów (w tym późniejsze odmowy), kontrolę nad wybranym projektem oraz zachowanie zainstalowanego narzędzia. Ustalony zaufany projekt lub polityka niedopuszczająca źródła wybranego przez wywołującego nie dowodzą istnienia tej ścieżki. Podczas enumeracji sprawdź regułę i metadane projektu bez instalowania pakietu.

Wrapper Python dozwolony przez sudo, który używa `setuptools.package_index.PackageIndex.download` z URL-em wybranym przez wywołującego, wymaga innego rodzaju analizy niż `pip download`: [GHSA-5rjg-fvgr-3xxf w setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) opisuje wyprowadzaną z URL-a nazwę pliku, która w podatnych wydaniach sprzed 78.1.1 wychodziła poza zamierzony katalog pobierania i zapisywała z uprawnieniami procesu. Potwierdź efektywnego użytkownika RunAs i regułę argumentów sudo, czy wrapper przekazuje URL wywołującego do dokładnie tego API, zainstalowaną kompilację lub backport dostawcy oraz miejsce rozwiązania wynikowej ścieżki. Sam numer wersji lub zapisywalny katalog pobierania nie dowodzą możliwości dowolnego zapisu. Podczas enumeracji sprawdź krótki wrapper i metadane pakietu bez pobierania z URL-a ani zapisywania pliku.

Wrapper budowania dozwolony przez sudo, który przekazuje wybrany przez wywołującego plik `.spec` do PyInstaller, wymaga podobnego sprawdzenia granicy zaufania. Plik spec PyInstaller to wykonywalny kod Python interpretowany podczas **budowania**, a jego wpisy `datas` mogą dołączyć do artefaktu pliki czytelne dla tożsamości procesu budującego. Potwierdź dokładnego użytkownika RunAs, reguły argumentów i odmów sudo, obsługę ścieżek i gałęzi przez wrapper, kontrolę nad wybranym plikiem spec oraz dostęp do wynikowego artefaktu. Samo zezwolenie na dane wejściowe `.py` lub stwierdzenie, że PyInstaller jest zainstalowany, nie dowodzi kontroli nad plikiem spec ani uprzywilejowanego wykonania. Pasywna analiza powinna ograniczać się do odczytu krótkiego wrappera i metadanych; nie uruchamiaj budowania. Zobacz [dokumentację plików spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loadery presetów i pluginów uruchamiane przez sudo

Narzędzia Python przyjmujące preset lub katalog pluginów wybrane przez wywołującego mogą importować kod z uprawnieniami przyznanymi przez sudo. Na przykład BBOT akceptuje preset za pomocą `-p`, a jego [dokumentacja custom modules](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) opisuje wpisy `module_dirs`, które wskazują dodatkowe katalogi modułów Python. Jeśli efektywna reguła sudo pozwala wybrać preset, a wywołujący kontroluje moduł w wybranym katalogu, import może wykonać kod jako uprzywilejowany użytkownik, potencjalnie zanim narzędzie odrzuci nieprawidłowy moduł. Podczas enumeracji sprawdź zainstalowaną wersję, dokładną politykę RunAs i argumentów sudo oraz właścicieli presetu i ścieżek modułów, nie ładując modułu.

### Narzędzie wiersza poleceń Backdrop uruchamiane przez sudo

[Bee](https://github.com/backdrop-contrib/bee) to narzędzie wiersza poleceń PHP dla Backdrop CMS. Jego polecenia `eval` (`php-eval`) i `php-script` mogą uruchamiać kod PHP dostarczony przez wywołującego. Reguła sudo zezwalająca na uruchomienie Bee jako root z nieograniczonymi argumentami może więc umożliwić wykonanie kodu jako root, jeśli Bee może zainicjować instalację Backdrop. Uruchom je z katalogu witryny lub wskaż witrynę globalną opcją `--root=<directory>`; samo znalezienie Bee lub pliku Backdrop `settings.php` nie dowodzi uprawnień sudo, działającej witryny ani pomyślnej inicjalizacji. Przed testowaniem sprawdź efektywną regułę sudo, ewentualne wykluczenia poleceń, tożsamość pliku wykonywalnego i dostęp do witryny. Podczas pasywnej enumeracji sprawdź regułę i ścieżki plików bez uruchamiania Bee. Zobacz [dziennik zmian poleceń Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md), który opisuje dodanie poleceń PHP.

### Serwery terminalowe uruchamiane przez sudo

`mosh-server` uruchamia interaktywny serwer terminalowy jako użytkownik wywołujący. Wybiera wysoki port UDP i klucz sesji, zwraca oba wywołującemu, a po połączeniu klienta zwykle uruchamia powłokę logowania tego użytkownika. Nieograniczone uprawnienie sudo do `mosh-server` z możliwością działania jako root jest zatem kandydatem do analizy powłoki, mimo że samo polecenie serwera odłącza się od terminala. Sprawdź efektywną tożsamość RunAs, dozwolone argumenty i wykluczenia, zainstalowany plik binarny, powłokę, dostępność klienta oraz dostęp UDP. Pasywna enumeracja powinna sprawdzać regułę sudo bez uruchamiania serwera i wyświetlania aktywnego klucza sesji. Zobacz [podręcznik serwera Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) i [notatki projektowe upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Uprzywilejowane wrappery kopii zapasowej, które przepisują plik zadań wywołującego

Wrapper powłoki uruchamiany jako root może przyjmować plik zadań wybrany przez wywołującego, usuwać `../` ze ścieżek źródłowych, sprawdzać, czy każdy wynik zaczyna się od dozwolonego katalogu, przepisywać plik zadań, a następnie przekazywać jego *ścieżkę* do programu kopii zapasowej. Sprawdź przekształconą ścieżkę po pełnym kanonicznym rozwiązaniu: pojedyncza operacja zastępowania ciągu może utworzyć nową sekwencję przejścia do katalogu nadrzędnego, którą akceptuje leksykalne sprawdzenie prefiksu. Sprawdź też, czy program kopii zapasowej odczytuje przekształcone dane w pamięci, czy ponownie otwiera plik. Jeśli ponownie go otwiera, nieudana modyfikacja może pozostawić oryginalne dane wejściowe.

W Linuksie `fs.protected_regular` może zablokować zapis `O_CREAT` do zwykłego pliku innego użytkownika w katalogu z bitem sticky, zapisywalnym dla wszystkich. To zabezpieczenie ochronne, ale wrapper powłoki ignorujący błąd zapisu może nadal kontynuować i użyć oryginalnego pliku zadań. Potwierdź to ustawienie, właściciela pliku i katalogu oraz to, czy wrapper przerywa działanie po błędzie. Taka ścieżka jest kandydatem do ujawnienia plików tylko wtedy, gdy efektywna reguła sudo pozwala uruchomić wrapper jako użytkownik uprzywilejowany, wywołujący kontroluje dane zadania i czytelne miejsce docelowe kopii zapasowej, a narzędzie kopii faktycznie uwzględnia chronione źródła. Podczas enumeracji sprawdź te warunki bez uruchamiania kopii zapasowej.

### Symbole wieloznaczne argumentów w uprzywilejowanych narzędziach sieciowych

W regule sudo dla `tcpdump` symbol `*` we **wzorcu argumentów** może dopasowywać białe znaki i ukośniki, więc ograniczenie wyglądające na ścieżkę może nadal dopuszczać dodatkowy tekst opcji. Różni się to od symbolu wieloznacznego w ścieżce pliku wykonywalnego polecenia; sprawdź pełną regułę RunAs i wszelkie późniejsze odmowy. Jeśli można wstrzykiwać opcje, przydatną funkcję odczytu/zapisu określają dozwolone wywołanie i semantyka opcji zainstalowanego [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in): `-F`, `-V`, `-r`, `-w` lub `-Z`. `-V` odczytuje listę nazw plików przechwyconych pakietów, a nie dowolny plik w celu jego zrzucenia. AppArmor lub inna polityka MAC może blokować dostęp do plików, nawet jeśli sudo zezwala na polecenie; sam plik profilu na dysku nie dowodzi, że profil jest załadowany i wymuszany. Zanim wyciągniesz wniosek, pasywnie sprawdź autoryzację i politykę. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) opisuje różnicę między tymi symbolami wieloznacznymi.

Reguła sudo z możliwością działania jako root, która wymienia wyłącznie plik wykonywalny `tcpdump` i nie ogranicza argumentów, również wymaga analizy. [Podręcznik tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) opisuje `-z` jako polecenie uruchamiane po rotacji, gdy opcja `-C` lub `-G` rotuje zapisywany plik przechwycenia; `-Z` lub domyślne ustawienie kompilacji może obniżyć uprawnienia przed uruchomieniem tego polecenia. Zanim uznasz regułę za ścieżkę eskalacji, zweryfikuj efektywną regułę sudo, zainstalowaną kompilację, zachowanie dotyczące obniżania uprawnień oraz to, czy może dojść do rotacji. Wyróżniona reguła to potencjalny przypadek, a nie dowód wykonania polecenia jako root.

### Wrappery Nmap uruchamiane przez sudo

Jeśli ścieżka `nmap` dozwolona przez sudo jest wrapperem powłoki, sprawdź dokładnie dozwoloną ścieżkę i każdą przekazywaną opcję. Blokowanie dobrze znanej pisowni `--script` nie musi blokować ładowania kodu NSE: opcja Nmap [`--datadir`](https://nmap.org/book/man-misc-options.html) wybiera pliki danych, a NSE [ładuje `nse_main.lua`](https://nmap.org/book/nse-implementation.html) z wybranego katalogu danych, gdy włączone jest skryptowanie. Niektóre zainstalowane kompilacje akceptują też alternatywną pisownię długich opcji, dlatego porównaj ograniczenia z rzeczywistym parserem danego pliku binarnego. [`--excludefile`](https://nmap.org/book/man-target-specification.html) tworzy osobną powierzchnię odczytu plików; błędy parsera mogą ujawniać tekst. Podczas enumeracji sprawdź efektywną regułę sudo, logikę wrappera, wersję Nmap, kontrolę nad katalogiem i politykę MAC bez uruchamiania skanów.

### Hooki pull Mercurial uruchamiane przez sudo

Ustalony parametr źródła w `sudo hg pull /fixed/source` nadal pozostawia **repozytorium odbierające** wybrane przez bieżący katalog roboczy, chyba że polecenie ustala je za pomocą `-R`. Repozytorium odbierające kontrolowane przez wywołującego może definiować hooki w `.hg/hgrc`, a hook może uruchomić się z tożsamością użytkownika RunAs sudo. [Mercurial ignoruje konfigurację repozytorium należącą do niezaufanego użytkownika lub grupy](https://mercurial-scm.org/help/topics/config), dlatego przed uznaniem tego za wykonanie kodu sprawdź zaufanych użytkowników/grupy konta RunAs i dokładny katalog roboczy. Do pasywnej analizy wystarczy odczyt polityki i konfiguracji; nie wykonuj `pull` ani hooka.

### Hooki pull Git uruchamiane przez sudo

W przypadku dokładnego uprawnienia `sudo git pull` z możliwością działania jako root sprawdź również **repozytorium odbierające**, wybierane na podstawie katalogu roboczego. Repozytorium należące do wywołującego może mieć wykonywalny hook `post-merge`, który uruchamia się z tożsamością procesu Git, gdy pull faktycznie pomyślnie scala zmiany; [Git opisuje ten hook](https://git-scm.com/docs/githooks) oraz [zachowanie pull: merge lub rebase](https://git-scm.com/docs/git-pull). Zweryfikuj efektywną regułę sudo i katalog roboczy, aktywną ścieżkę hooka i jego uprawnienia oraz możliwość wykonania merge’a z nowymi commitami. Nieudany pull, operacja bez zmian lub pull wykonujący wyłącznie rebase nie dowodzi istnienia tej ścieżki. Sprawdź politykę i metadane repozytorium bez uruchamiania uprzywilejowanego `pull`.

### Kopiowanie archiwów przez rsync uruchamiane przez sudo

W przypadku `sudo rsync -a ... /writable/source/* /fixed/destination/` symbol `*` we **wzorcu argumentów sudoers** może dopasowywać białe znaki i dopuścić dodatkową opcję między źródłem a miejscem docelowym. To coś innego niż rozwijanie nazw plików przez powłokę. Jeśli wywołujący może umieszczać pliki w źródle, a proces rsync o podwyższonych uprawnieniach może zapisywać do miejsca docelowego, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) może zażądać uprzywilejowanej zmiany właściciela, podczas gdy tryb archiwizacji zachowuje bity uprawnień, potencjalnie tworząc plik SetUID należący do wybranego właściciela. Sprawdź dokładną [semantykę symboli wieloznacznych sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), wersję rsync, późniejsze odmowy, opcję systemu plików `nosuid` i politykę MAC. Dopasowana reguła to kandydat do analizy, a nie dowód udanej eskalacji uprawnień.

### Eksport reguł filtrowania pakietów uruchamiany przez sudo

Nieograniczone uprawnienie do `iptables` i `iptables-save` z możliwością działania jako root (lub odpowiadającej pary `ip6tables`) wymaga sprawdzenia możliwości zapisu pliku. Dopasowanie `comment` akceptuje tekst reguły wybrany przez wywołującego, a `iptables-save -f` zapisuje serializowany zestaw reguł do wybranej ścieżki.<sup>[[20]](#references)[[21]](#references)</sup> Użyteczny payload zależy od tego, jak zainstalowany backend serializuje komentarze oraz czy docelowy plik akceptuje inne wiersze eksportu; samo `iptables-save` nie umożliwia umieszczenia dowolnie wybranej treści. Sprawdź dokładną tożsamość sudo RunAs, argumenty i wykluczenia, dostępne rozszerzenie match, backend i uprawnienia do miejsca docelowego. Podczas enumeracji sprawdź przyznane uprawnienie bez zmieniania reguł firewalla ani zapisywania pliku.

### Uprzywilejowany katalog logów Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) dotyczyła wersji Below sprzed 0.9.0, które tworzyły katalog `/var/log/below` z prawem zapisu dla wszystkich. Jeśli usługa lub dozwolone polecenie sudo uruchamia jako root podatną kompilację, użytkownik mogący zapisywać do katalogu logów i przechodzić przez niego — o ile nie ma bitu sticky — może zastąpić wpis logu symlinkiem przed otwarciem go przez uprzywilejowany proces. Sprawdź status poprawki zainstalowanego pakietu, dokładną ścieżkę uprzywilejowanego wykonania, efektywny dostęp do katalogu, bit sticky i ACL oraz metadane `/var/log/below/error_root.log`. Sam katalog zapisywalny dla wszystkich lub reguła sudo nie dowodzą istnienia całego łańcucha. Katalog z bitem sticky lub backport dostawcy zmienia ocenę. Pasywna enumeracja powinna ograniczać się do sprawdzania metadanych; nie ma potrzeby tworzenia symlinka ani uruchamiania uprzywilejowanego programu.

### Uprzywilejowane zbieranie pakietu pomocy z danych wejściowych zapisywalnych przez użytkownika

Skrypt profilu pomocy dozwolony przez `sudo` może odczytywać ustalone ścieżki logów jako root i kopiować ich zawartość do archiwum profilu. Sprawdź, czy skrypt rzeczywiście odczytuje pliki, a następnie ustal, czy wywołujący może zastąpić ścieżkę źródłową lub którykolwiek wpis katalogu nadrzędnego symlinkiem. Jeśli uprzywilejowany odczyt podąża za takim linkiem, a archiwum wynikowe jest czytelne dla wywołującego, chroniony plik może zostać ujawniony. Muszą występować wszystkie elementy: uprawnienie sudo, zapisywalna ścieżka źródłowa, uprzywilejowany odczyt i czytelne wyjście; samo zapisywalne logowanie lub nazwa profilu nie wystarczą. Podczas enumeracji sprawdź efektywne uprawnienia i metadane linków bez zastępowania plików ani generowania profilu. [Wskazówki dotyczące pomocy Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) opisują uruchamiany jako root skrypt profilu i archiwum wyjściowe, pokazując, dlaczego takie pakiety powinny mieć ograniczone dane wejściowe i dostęp do wyjścia.

### Skrypty Python przywracające archiwa uruchamiane jako root

Nawet ściśle ograniczona reguła sudo dla skryptu Python przywracającego dane wymaga sprawdzenia wejściowego archiwum. Jeśli wywołujący może wybrać lub zastąpić archiwum, a skrypt rozpakowuje je jako root za pomocą `tarfile.extractall(filter="data")`, przed zaufaniem temu filtrowi sprawdź aktualizacje bezpieczeństwa interpretera. CPython naprawił kilka przypadków obejścia filtra z użyciem symlinków i hardlinków, w tym CVE-2025-4517, w wersjach 3.9.23, 3.10.18, 3.11.13, 3.12.11 i 3.13.4. Backporty dystrybucji mogą naprawiać problem w starszej wersji, więc sam wyświetlany numer wersji interpretera nie dowodzi podatności.<sup>[[16]](#references)[[17]](#references)</sup>

Podczas pasywnej analizy odczytaj dokładne polecenie sudo i skrypt, prześledź, który argument wybiera archiwum, i sprawdź, czy bieżący użytkownik może zapisywać do archiwum lub jego katalogu. Osobno potwierdź poprawkę dostawcy i katalog docelowy rozpakowywania; `filter="data"` nie czyni każdego niezaufanego archiwum bezpiecznym.<sup>[[16]](#references)[[17]](#references)</sup>

### Loadery modeli uczenia maszynowego uruchamiane przez sudo

Reguła sudo zezwalająca na plik `.pt`, `.pth` lub `.ckpt` wybrany przez wywołującego wymaga sprawdzenia, gdy uprzywilejowany skrypt przekazuje go do [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` lub innego loadera opartego na pickle. Sprawdź efektywną regułę RunAs, możliwość utworzenia lub zastąpienia wybranego modelu przez wywołującego oraz rzeczywisty przepływ argumentów przez wrapper powłoki do helpera Python. Rozszerzenie `.pth` oznacza też niezwiązane z tym pliki konfiguracji witryny Python, więc samo rozszerzenie nie jest dowodem ładowania modelu. Skan archiwum lub statyczna analiza pickle nie dowodzą, że późniejsze ładowanie jest bezpieczne; sprawdź [zależne od wersji zachowanie `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) i wszelkie listy dozwolonych typów. Zobacz [notatki o pickle w ML i Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Pasywna enumeracja nigdy nie powinna ładować ani rozpakowywać modelu.

### Parsowanie wyrażeń z zapisanych danych wejściowych przez sudo

Ustalony skrypt Python uruchamiany jako root przez sudo może nadal ewaluować tekst zapisany przez użytkownika o niższych uprawnieniach w bazie danych aplikacji. W TensorFlow wywołanie `preprocess_input_exprs_arg_string(value, safe=False)` wybiera ścieżkę `eval`; [ostrzeżenie TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) opisuje niebezpieczny parser i poprawkę w jego wywołującym z wiersza poleceń. Wywołanie `safe=False` przez aplikację wymaga osobnej analizy, nawet gdy wywołujący z wiersza poleceń jest już poprawiony. Sprawdź efektywną regułę sudo, kto może modyfikować dokładny rekord wejściowy, czy filtrowanie lub ocena pozwala temu rekordowi dotrzeć do wywołania oraz zachowanie zainstalowanej funkcji. Sama wersja TensorFlow, uprawnienie sudo lub ustalony plik modelu nie dowodzą istnienia całego łańcucha. Podczas pasywnej analizy sprawdź skrypt i przepływ danych; podczas enumeracji nie uruchamiaj uprzywilejowanego helpera ani nie wysyłaj testowych wyrażeń.

### Konfiguracja needrestart dozwolona przez sudo

`needrestart -c` wczytuje wybrany przez wywołującego plik konfiguracyjny Perl i interpretuje jego zawartość. Jeśli `sudo -l` pozwala uruchomić `needrestart` jako root z argumentami dopuszczającymi `-c`, a wywołujący może wybrać czytelny plik konfiguracyjny w zapisywalnej lokalizacji, uprawnienie to może prowadzić do wykonania kodu jako root. Sprawdź dokładną regułę sudo RunAs i argumentów; reguła zezwalająca tylko na ustaloną listę argumentów może blokować tę ścieżkę. Jest to niezależne od podatności skanowania interpreterów w needrestart: aktualizacja pakietu lub wyłączenie `interpscan` nie sprawia, że nieograniczone uprawnienie roota do `-c` staje się bezpieczne.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importy Python uruchamiane przez sudo jako inne konto

Ustalony punkt wejścia Python może nadal importować moduł, który wywołujący może edytować lub zastąpić, także wtedy, gdy sudo uruchamia skrypt jako **nirootowe** konto usługi. W przypadku dosłownego `from utils import status` sprawdź zarówno lokalne `utils/__init__.py` i `utils/status.py`, jak i uprawnienia katalogu pakietu. Zanim uznasz zapisywalny plik za ścieżkę wykonania, potwierdź ścieżkę importu skryptu, dokładne dozwolone argumenty sudo oraz to, czy dane działanie dociera do tego importu. Podczas enumeracji sprawdzaj pliki i uprawnienia bez importowania modułu ani uruchamiania skryptu.<sup>[[2]](#references)[[3]](#references)</sup>

Dokładna reguła sudo dla `python3 /absolute/script.py` wymaga jedynie, aby skrypt był czytelny; plik nie musi być wykonywalny ani mieć shebanga. Sprawdź również **brakujące** moduły lokalne: jeśli skrypt importuje moduł, którego nazwę pliku można utworzyć w katalogu skryptu zapisywalnym przez wywołującego, Python może załadować ten plik z tożsamością RunAs. Potwierdź efektywną regułę sudo, rzeczywistą [ścieżkę wyszukiwania modułów interpretera](https://docs.python.org/3/library/sys_path_init.html), to, czy moduł jest wbudowany lub zamrożony, oraz czy import jest osiągalny. Bezpośrednia reguła sudo dla skryptu ma inne wymagania dotyczące bitu wykonania i shebanga. Oddzielny wrapper dopisujący tokeny podane przez wywołującego po `sudo -u account` również wymaga analizy przepływu argumentów: dodatkowe `-u` w tych tokenach ma znaczenie tylko wtedy, gdy wywołane sudo zezwala na wynikową tożsamość. Same ciągi w kodzie nie dowodzą żadnej z tych ścieżek.

### Apache uruchamiany przez sudo z konfiguracją kontrolowaną przez wywołującego

Jeśli reguła sudo zezwala na uprzywilejowane wywołanie `apachectl`, `apache2ctl` lub `httpd` z plikiem konfiguracyjnym `-f` kontrolowanym przez wywołującego, sprawdź uprawnienia do tego pliku i jego katalogu nadrzędnego. Dyrektywa Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) przyjmuje nazwę modułu, a następnie **nazwę pliku modułu**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) również wczytuje plik. [`Include` i `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) mogą rozszerzyć konfigurację lub ujawnić zawartość plików w błędach. Własny wrapper może walidować te ścieżki, obniżać uprawnienia lub ograniczać argumenty, więc sama zapisywalna konfiguracja to kandydat do analizy, a nie dowód wykonania kodu. Przed wyciągnięciem wniosku sprawdź kanonikalizację ścieżek, symlinki i parsowanie dyrektyw.

### nginx uruchamiany przez sudo z konfiguracją kontrolowaną przez wywołującego

Nieograniczona reguła nginx z możliwością działania jako root może pozwalać użyć [`-c` do wskazania innego pliku konfiguracji](https://nginx.org/en/docs/switches.html). Sprawdź dokładne argumenty i wykluczenia sudo, możliwość dostarczenia konfiguracji przez wywołującego oraz to, czy wynikowy proces master lub workery zachowują dostęp do chronionych ścieżek. Wybrana kombinacja `root` i `autoindex` może udostępnić pliki przez nowy nasłuchujący serwer; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) może umożliwić uprzywilejowany zapis pliku, ale moduł DAV nie jest domyślnie kompilowany i trzeba sprawdzić jego obecność, dostępność nasłuchującego serwera, uprawnienia plików oraz zachowanie plików tymczasowych. Dyrektywa [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) może również wskazywać wybrany plik; zapisywanie logów do wrażliwego pliku konfiguracyjnego, takiego jak `/etc/ld.so.preload`, staje się ścieżką eskalacji dopiero wtedy, gdy istnieje efektywny uprzywilejowany zapisujący i kontrolowany przez wywołującego rekord logu. Wyróżnienie pliku wykonywalnego przez `sudo -l` to wskazówka do analizy, a nie dowód, że którakolwiek z tych ścieżek działa. Pasywna enumeracja nie powinna uruchamiać ani rekonfigurować nginx.

### Porównywanie wzorców w uprzywilejowanych promptach Bash

Gdy skrypt Bash dozwolony przez sudo odczytuje wartość od wywołującego i sprawdza ją za pomocą `[[ "$expected" == $entered ]]`, Bash interpretuje nieujęty w cudzysłowy prawy operand jako wzorzec. Symbol wieloznaczny może więc spełnić warunek bez znajomości oczekiwanej wartości. Ujęcie operandu w cudzysłowy (`[[ "$expected" == "$entered" ]]`) wymusza porównanie dosłownych ciągów. Sprawdź dokładną regułę sudo, osiągalność promptu i działanie skryptu po porównaniu; sama składnia nie dowodzi istnienia możliwej do wykorzystania ścieżki. Podczas enumeracji unikaj wyświetlania oczekiwanej wartości. Zobacz [opis konstrukcji warunkowych Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpery uruchamiane przez sudo, które pobierają plik i go wykonują

Nieograniczone uprawnienie sudo do własnego helpera z możliwością działania jako root wymaga analizy przepływu danych, jeśli helper przyjmuje URL wybrany przez wywołującego, zapisuje odpowiedź na dysku, a następnie uruchamia plik przez interpreter lub powłokę. [sudoers zezwala na dowolne argumenty, gdy wpis polecenia ich nie określa](https://man7.org/linux/man-pages/man5/sudoers.5.html); ustalona ścieżka pliku wykonywalnego nie ogranicza tego, co mogą wybrać argumenty. Potwierdź walidację URL-a, ścieżkę wyjściową, gałąź sukcesu i późniejsze wykonanie w zainstalowanym helperze. Pasujący import libcurl lub drukowalny ciąg sam w sobie nie dowodzi istnienia tego łańcucha.

Nawet ustalona nazwa pliku wyjściowego może zostać podmieniona między zapisem a wykonaniem, gdy helper używa **ścieżki względnej w katalogu roboczym kontrolowanym przez wywołującego**. Zmiana nazwy lub zastąpienie pliku należącego do roota zależy od prawa zapisu i przeszukiwania katalogu oraz ewentualnych ograniczeń bitu sticky, a nie tylko od trybu pliku; zobacz [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Sprawdź, czy helper później ponownie otwiera ścieżkę, czy używa już otwartego deskryptora, oraz czy przed zapisem przechodzi do zaufanego katalogu. Pasywnie sprawdź politykę sudo, helper i metadane katalogu; podczas enumeracji nie uruchamiaj uprzywilejowanego pobierania ani wyścigu.

Helper pobierający dane przez sudo jako root może również umożliwiać wstrzyknięcie **argumentu**, jeśli buduje ciąg polecenia Bash, np. `curl <caller input> -o <fixed output>`. Filtr odrzucający białe znaki nadal pozostawia [rozwijanie nawiasów klamrowych w Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): nieujęte w cudzysłowy elementy oddzielone przecinkami mogą stać się osobnymi argumentami curl. Jeśli dane wejściowe trafiają do curl przed ustaloną opcją `-o`, opcja wyjściowa podana przez wywołującego może wybrać miejsce docelowe dla pierwszego URL-a z tożsamością helpera; [curl przypisuje opcje wyjściowe do URL-i w kolejności](https://curl.se/docs/manpage.html#-o). Potwierdź dokładną powłokę, cudzysłowy, walidację danych wejściowych, efektywną regułę sudo, kolejność argumentów curl i obsługiwane schematy URL oraz to, czy wywołujący kontroluje pobierane bajty lub może odczytać wynik. Plik wykonywalny spakowany przez PyInstaller może zawierać logikę aplikacji Python, ale sam znacznik pakowania lub ciąg `curl` nie dowodzą przepływu danych. Jeśli masz upoważnienie, przeanalizuj ograniczoną kopię offline; rutynowa enumeracja nie powinna uruchamiać helpera ani pobierać danych wybranych przez atakującego.

Skrypt powłoki uruchamiany jako root przez sudo, który wywołuje [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), wybiera tylko nieużywaną nazwę — **nie** tworzy pliku. Jeśli skrypt później tworzy plik o tej nazwie w katalogu, na który może wpływać inny użytkownik, ponownie go otwiera i dopisuje jego zawartość do chronionego miejsca docelowego, takiego jak `authorized_keys` roota, należy sprawdzić możliwość wyścigu pliku tymczasowego. Potwierdź dokładną regułę sudo, właściciela katalogu i pliku, kolejność tworzenia i ponownego otwarcia, zabezpieczenia jądra oraz to, czy uprzywilejowany zapis faktycznie używa bajtów kontrolowanych przez atakującego. Sam ciąg `mktemp -u` lub zapisywalny `/tmp` nie dowodzą istnienia wyścigu. Podczas enumeracji sprawdź skrypt i metadane ścieżki bez uruchamiania go ani wywoływania wyścigu pliku tymczasowego.

## Uwagi dotyczące obrony

- Unikaj udzielania przez sudo uprawnień do interpreterów i interaktywnych edytorów.<sup>[[1]](#references)</sup>
- Nie udzielaj nieograniczonych uprawnień do ogólnych narzędzi zapisu plików, takich jak `tee`. Używaj wrappera należącego do roota, który wybiera ustalone miejsce docelowe i odrzuca ścieżki kontrolowane przez wywołującego.<sup>[[2]](#references)</sup>
- Preferuj ustalone wrappery należące do roota, które wykonują jedną, wąsko określoną czynność administracyjną.<sup>[[1]](#references)[[2]](#references)</sup>
- Jeśli interpreter jest niezbędny, ogranicz dokładną ścieżkę skryptu i zablokuj argumenty kontrolowane przez użytkownika, zapisywalne importy, `PYTHONPATH` oraz niebezpieczne zachowywanie środowiska.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Jeśli konieczna jest edycja pliku, ogranicz dokładną ścieżkę pliku i rozważ `sudoedit` z poprawionymi wersjami sudo oraz rygorystyczną obsługą środowiska.<sup>[[1]](#references)[[2]](#references)</sup>
- Sprawdź `SETENV`, `env_keep`, zapisywalne katalogi robocze, zapisywalne ścieżki modułów/importów, `NOEXEC`, `use_pty` i logowanie, ale nie traktuj ich jako kompletnego sandboxa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
