## Intérpretes permitidos por sudo

Si `sudo -l` permite a un usuario ejecutar un intérprete como root, considéralo ejecución directa de código. Los intérpretes están diseñados para ejecutar código arbitrario, así que una regla que permita usar `python3`, `perl`, `ruby`, `lua`, `node` o binarios similares suele equivaler a ejecutar comandos como root, a menos que los argumentos estén estrictamente restringidos y validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flujo de revisión habitual: primero enumera los privilegios del usuario y, después, ejecuta una instrucción de Python con la opción `-c` del intérprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

A continuación se muestran otros ejemplos de intérpretes; los intérpretes enumerados documentan la ejecución de código en línea o las API de procesos secundarios.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

La ruta exacta importa. Si la regla de sudo permite `/usr/bin/python3`, usa esa ruta exacta durante la validación.<sup>[[2]](#references)</sup>

Un patrón glob de ejecutables de sudo como `/usr/bin/python*` también puede permitir Python 2 para un script escrito para Python 3. Si el script llega a `input()` con texto controlado por quien lo invoca, [Python 2 evalúa ese texto como una expresión](https://docs.python.org/2/library/functions.html#input); una invocación explícita del intérprete prevalece sobre el shebang del script. Verifica los binarios coincidentes instalados, la política efectiva de RunAs y de argumentos, las denegaciones y si la entrada es alcanzable antes de considerar que esto permite ejecutar código.

Una ruta de script fija en una regla de sudo con capacidad de ejecutar como root no limita lo que ejecuta el script. Si se trata de un wrapper de Bash legible, comprueba si su primer comando ejecutable usa un parámetro posicional sin comillas, como `$1`, como **palabra de comando**, mientras sudo permite que quien lo invoca elija los argumentos. Confirma la identidad efectiva de RunAs, la política de contraseña y argumentos, las denegaciones posteriores y la rama que realmente sigue el script; `NOEXEC`, una lista fija de argumentos seguros o un wrapper que valide el comando pueden cambiar el resultado. Durante la enumeración, inspecciona estáticamente el script breve en lugar de invocarlo con un comando de prueba.

Una regla de sudo sin restricciones para `dotnet` con capacidad de ejecutar como root también merece una revisión del intérprete. Con un SDK de .NET instalado, [`dotnet fsi` ejecuta código F# de forma interactiva o desde un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), y [`dotnet run` ejecuta un proyecto desde el código fuente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Primero confirma la identidad efectiva de RunAs y la política exacta de argumentos: una regla limitada a un subcomando seguro específico o a una aplicación de confianza es un permiso distinto, y una instalación que solo incluya el runtime puede carecer de los comandos del SDK. El nombre del ejecutable por sí solo es una señal para revisarlo, no una prueba de ejecución de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` permitido por sudo: escritura arbitraria de archivos privilegiada

GNU `tee` copia la entrada estándar en todas las rutas proporcionadas como operandos de archivo. Por lo tanto, una regla de sudo que permita ejecutar `/usr/bin/tee` como root con argumentos controlados por quien lo ejecuta otorga una primitiva para crear o sobrescribir cualquier archivo como root. Añadir `-a` cambia la primitiva para que agregue contenido. Una etiqueta `PASSWD:` se refiere a la autenticación de sudo; por sí sola, no limita el destino ni los bytes leídos desde la entrada estándar.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Primero inspecciona la regla exacta. En un sistema de prueba autorizado, valida la primitiva solo con un destino desechable que sea seguro crear. El `>/dev/null` final solo suprime la copia de `tee` a la salida estándar.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Poner `sudo` antes del productor no eleva una redirección posterior del shell, porque el shell del usuario que invoca el comando abre el destino. El proceso privilegiado debe ser quien escriba, como en la canalización anterior.<sup>[[1]](#references)[[15]](#references)</sup>

Tras confirmar que se puede escribir, elige un vector adecuado de ejecución de código como root de [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Una cadena observada usó `tee` como root para crear un archivo de corta duración en `/etc/cron.d/`, iniciar un backdoor mediante un script controlado por el usuario y eliminar el archivo cron después de la ejecución. Eliminar el archivo cron evitó que se convirtiera en una entrada de persistencia a largo plazo, aunque los registros del sistema conservaron pruebas de la actividad.<sup>[[27]](#references)</sup>

## Editores permitidos por Sudo

Si `sudo -l` permite que un usuario ejecute un editor interactivo como root, considéralo una superficie de ejecución de comandos, no un permiso inofensivo para editar archivos. A menudo, los editores pueden ejecutar comandos del shell, leer archivos arbitrarios, escribir archivos arbitrarios o invocar ayudantes externos desde el propio editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flujo de revisión habitual: enumera los privilegios del usuario y luego ejecuta con sudo cada editor o pager permitido.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Ejecución de comandos con Nano

Cuando `nano` está permitido mediante sudo, es posible ejecutar comandos desde la interfaz del editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Luego proporciona un comando como `id` o `/bin/sh` en el prompt de comandos de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactivo no tiene flujos de terminal utilizables, esta forma de redirección asigna su salida estándar y error al descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La secuencia exacta de teclas puede variar según la versión de nano y las opciones de compilación, pero el problema de seguridad es el mismo: el editor se ejecuta como root y puede invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Otras formas comunes de escapar de editores

Los editores de estilo Vim suelen permitir ejecutar comandos mediante `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Los paginadores como `less` también pueden permitir ejecutar comandos de shell.<sup>[[14]](#references)</sup>

Una regla de sudo que permita ejecutar `apport-cli` como root merece la misma revisión del paginador. Algunas versiones afectadas de Apport podían abrir un informe de fallo en `less` con un tamaño de terminal ajustable por un atacante; el paginador podía entonces proporcionar una shell de root si se cumplían las condiciones especiales de sudo y del paginador. Comprueba la regla de sudo efectiva, la configuración del paginador y la corrección del paquete de la distribución antes de considerar vulnerable una versión basándote únicamente en su número. Durante la enumeración pasiva, consulta los metadatos del paquete y de las políticas sin generar un fallo ni abrir el informe privilegiado. [El registro de CVE de Ubuntu](https://ubuntu.com/security/CVE-2023-1326) enumera las versiones corregidas de los paquetes para cada versión de la distribución, incluidas las correcciones retroportadas.

```text
!/bin/sh
```

## Otros riesgos de las reglas de sudo y doas

Empieza con `sudo -l`, `sudo -V` y cualquier política aplicable de `doas`. Lee en conjunto el comando permitido, el usuario de ejecución, los argumentos, el entorno y los valores predeterminados. El permiso para ejecutarse como una cuenta de servicio que no sea root aún puede exponer los archivos de esa cuenta o una vía hacia root.

Un script de Python fijo permitido por sudo aún puede ejecutar un comando de shell bajo la identidad RunAs si concatena entrada interactiva controlada por quien lo invoca en [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una lista de denegación de signos de puntuación del shell no basta para establecer que sea seguro: [el shell también reconoce la sustitución de comandos `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirma que los argumentos permitidos lleguen a la rama de entrada, que la entrada llegue al comando de shell sin una validación segura y que la política efectiva de sudo permita el usuario RunAs previsto. La ruta del script o una llamada a `os.system()` por sí solas solo son indicios para revisar; inspecciona el código fuente sin invocar el script privilegiado.

Un permiso efectivo de sudo como root para `chattr` puede eliminar el atributo inmutable (`i`) de un archivo, pero esto por sí solo no concede permisos de escritura ni una nueva identidad. [El manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indica que el atributo bloquea las modificaciones y que solo root o un proceso con `CAP_LINUX_IMMUTABLE` puede cambiarlo. Comprueba la política exacta de argumentos de sudo y la compatibilidad del sistema de archivos; luego verifica por separado que quien invoca el comando pueda escribir en el archivo una vez eliminado el atributo y que un consumidor con una identidad superior lo utilice. Por ejemplo, reemplazar un shell de inicio de sesión también requiere credenciales aceptadas por la cuenta objetivo y un inicio de sesión real a través de ese shell. Revisa la política, los atributos del archivo y los permisos sin modificarlos durante la enumeración.

Si sudo solicita una contraseña y un código de un solo uso, trata esos requisitos previos por separado del permiso para ejecutar el comando. Un archivo `.google_authenticator` legible contiene material sensible para generar semillas, mientras que un hash antiguo de contraseña de aplicación o base de datos solo es una contraseña candidata para la cuenta actual; ninguno demuestra que la otra forma de autenticación sea aceptada por la configuración efectiva de PAM. Una vez autorizado, revisa el RunAs y los argumentos exactos: un permiso irrestricto como root para RubyGems `gem` puede exponer su comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), pero un permiso restringido o una autenticación fallida no. La enumeración pasiva debe informar de las rutas y la política sin mostrar la semilla, recuperar una contraseña, generar un código ni invocar el comando privilegiado.

Un permiso irrestricto de sudo con capacidad de ejecutarse como root para `knife` de Chef merece una revisión a nivel de intérprete: [Chef documenta que `knife exec -E` evalúa localmente una cadena de Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica que la regla efectiva de sudo permita el subcomando `exec` y el argumento `-E` proporcionado por quien invoca el comando, la identidad RunAs prevista y cualquier denegación de comandos o argumento fijo coincidente. El binario instalado o una regla limitada a otros subcomandos solo son indicios. La enumeración pasiva debe informar de la regla sin invocar `knife`.

Un permiso exacto de sudo con capacidad de ejecutarse como root para un `msfconsole` interactivo también es delicado: [GTFOBins documenta su consola `irb`](https://gtfobins.org/gtfobins/msfconsole/), que puede heredar la identidad de sudo. Confirma el usuario RunAs efectivo, la lista de argumentos permitidos, las denegaciones de comandos, `NOEXEC` u otras restricciones, el comportamiento de la consola instalada y si quien invoca el comando puede proporcionar entrada interactiva. Que la ruta aparezca resaltada solo es un indicio; la enumeración pasiva no debe iniciar la consola.

En FreeBSD, incluso una regla de sudo limitada a `pkg update` y `pkg install *` como root merece una revisión de la confianza en los repositorios. Comprueba si quien invoca el comando puede escribir en `/etc/hosts` y si la configuración efectiva de repositorios habilitados usa un nombre de host HTTP con `signature_type: none`. [El manual de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indica que `none` desactiva las comprobaciones de firma; `pkg+http` por sí solo no demuestra que así sea. Un paquete puede incluir scripts de instalación ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), por lo que quien realmente controle el endpoint del repositorio y pueda seleccionar un paquete podría cruzar el límite de root. Verifica las anulaciones de repositorio, la resolución de SRV/espejos, los argumentos efectivos de sudo, la selección del paquete y la ejecución de scripts antes de llegar a esa conclusión. Inspecciona la política y los archivos de configuración locales pequeños sin redirigir nombres ni ejecutar `pkg` durante la enumeración.

Un permiso de sudo con capacidad de ejecutarse como root para `apt-get update` y `apt-get upgrade` también requiere revisar la confianza en los repositorios cuando sudo conserva un `http_proxy` controlado por quien invoca el comando. Comprueba si la configuración efectiva de proxy de APT usa realmente esa variable y qué solicitudes a repositorios habilitados puede afectar; un proxy por sí solo no puede sustituir paquetes de un archivo autenticado con una clave de firma de confianza. [El manual del transporte HTTP de APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedencia de los proxies, y [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta las comprobaciones de firma, las anulaciones de repositorios no seguros y la confirmación para paquetes no autenticados. Confirma el RunAs y los argumentos exactos de sudo, la política de autenticación del repositorio, cualquier aceptación interactiva requerida y si la actualización seleccionada ejecuta scripts de paquetes como root. Inspecciona la política y la configuración local de forma pasiva; no redirijas el tráfico de paquetes ni ejecutes una actualización durante la enumeración.

Una regla de sudo con capacidad de ejecutarse como root para `snap install` puede crear un límite entre paquete y código si sus argumentos permiten a quien invoca el comando seleccionar un snap local y un modo de instalación permisivo. [Snap documenta](https://snapcraft.io/docs/explanation/snap-development/install-modes/) que `--dangerous` omite las comprobaciones de aserciones de snaps locales y que `--devmode` relaja el confinamiento; [un hook de instalación puede ejecutarse en la instalación inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Comprueba la política exacta de argumentos/RunAs de sudo, quién controla el archivo snap, si snapd instalado acepta esos modos y la identidad efectiva y el confinamiento del hook antes de afirmar que puede acceder a archivos protegidos del host. Un binario `snap` o una regla que parece usar comodines no demuestran por sí solos esta cadena. La enumeración pasiva no debe instalar un paquete ni ejecutar su hook.

Para un permiso exacto de sudo para un binario personalizado que lee credenciales como una cuenta que **no es root**, primero inspecciona el binario permitido y sus permisos de archivo sin ejecutarlo. Una barrera de contraseña integrada podría ser visible solo como caracteres anchos; [GNU `strings` documenta la extracción de 16 bits little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Una cadena visible no demuestra que sea la contraseña aceptada ni que la rama de éxito exponga una credencial vigente. Confirma por separado el comportamiento del binario, el acceso de la cuenta objetivo a los datos protegidos, la validez de la credencial y cualquier transición posterior de cuenta o grupo. Si esa cuenta pertenece a `docker`, verifica el acceso al socket y la identidad rootful o rootless del daemon antes de inferir acceso a root del host; [Docker documenta las implicaciones de su grupo a nivel de root](https://docs.docker.com/engine/install/linux-postinstall/). La enumeración habitual debe informar de la regla de sudo y la pertenencia a grupos sin ejecutar el binario ni volcar sus cadenas.

Una regla de sudo con comodines para los scripts de mantenimiento de una aplicación requiere revisar algo más que la ruta del script. Comprueba si el script permitido acepta argumentos sin restricciones o lee ajustes que una cuenta de aplicación con menos privilegios puede modificar; luego rastrea esos valores hasta los comandos de shell o el entorno de un subproceso. Por ejemplo, [`zmupdate.pl` de ZoneMinder construye un comando `mysqldump` y lo ejecuta mediante `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mientras que [`zmdc.pl` copia el ajuste `ZM_LD_PRELOAD` a `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Una regla de sudo que permita ejecutar cualquiera de los dos scripts como root puede cruzar un límite de confianza si la entrada correspondiente es controlable y llega a ese código en la versión instalada. Inspecciona la regla efectiva de sudo, los permisos de configuración de la aplicación y el código fuente del script; el comodín o el ajuste por sí solos son indicios para revisar, no una prueba de ejecución.

- `SETENV`, `env_keep`, `secure_path` y `LD_PRELOAD` pueden convertir un comando que, de otro modo, sería limitado en un secuestro de importación, biblioteca o `PATH`. Consulta la [guía de variables de entorno](../linux-basics/linux-environment-variables.md) y el [abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Un permiso exacto de `SETENV` de sudo con capacidad de ejecutarse como root para un wrapper de shell también merece revisar el siguiente salto si el wrapper inicia un script fijo de Python con un import literal. `secure_path` limita la búsqueda de comandos del shell, no la búsqueda de módulos de Python mediante [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` y `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hacen que Python ignore esa variable de entorno. Confirma las etiquetas y denegaciones efectivas de sudo, la rama del wrapper, las opciones del intérprete, la resolución del import y la existencia de un directorio de búsqueda modificable por quien invoca el comando antes de considerarlo ejecución de código. Inspecciona los scripts cortos de forma estática; no invoques el wrapper privilegiado.

Un permiso exacto de sudo para `neofetch ""` con capacidad de ejecutarse como root aún puede cargar una configuración de shell cuando los valores predeterminados aplicables de sudo conservan un `XDG_CONFIG_HOME` controlado por quien invoca el comando. [El cargador de configuración de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carga `neofetch/config.conf` o `neofetch/config` desde ese directorio; la lista vacía de argumentos no impide esta búsqueda. Confirma el cargador instalado, la política efectiva de RunAs y argumentos, cualquier denegación de comandos, si sudo conserva realmente la variable elegida para este comando y si quien lo invoca controla una ruta de configuración legible. Una variable conservada o Neofetch instalado por sí solos solo son indicios. Inspecciona la política y los metadatos de archivos sin invocar el comando privilegiado ni mostrar el contenido de la configuración; consulta [el manejo del entorno en sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regla irrestricta de sudo para `facter` con capacidad de ejecutarse como root merece revisar por separado los custom facts. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` carga archivos de facts de Ruby desde un directorio seleccionado. Comprueba si la regla exacta de sudo permite esa opción, si Facter instalado la acepta y si quien invoca el comando controla el directorio. Un permiso con argumentos fijos, una denegación explícita del comando o los custom facts deshabilitados pueden cambiar el resultado. La enumeración pasiva debe informar de la posibilidad indicada por la política sin invocar Facter ni leer el contenido de los facts.

Para un permiso exacto de sudo para un script como root con `SETENV`, inspecciona nombres de comandos sin ruta, como `find`, y el `PATH` efectivo después de aplicar la política de sudo y la inicialización del script. Un archivo Bash cargado también puede ejecutar `enable -n [`: [Bash busca entonces en `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un `[` externo cuando el script usa ese comando más adelante. Confirma las reglas aplicables de [entorno de sudoers y `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), cualquier entrada `NOSETENV`/`NOEXEC` o de denegación, el flujo del script y de los archivos cargados, y un directorio de búsqueda ejecutable controlado por quien invoca el comando. Un script legible que contiene un comando sin ruta es un indicio para revisar, no una prueba de ejecución privilegiada; inspecciónalo sin invocar la regla de sudo.
- Un script privilegiado que descarga una URL fija con `curl` aún puede aceptar una respuesta elegida por quien invoca el comando si una regla aplicable de sudo conserva `http_proxy` y la solicitud se envía a través de ese proxy. Si luego el script pasa la respuesta a un analizador XML que resuelve entidades externas, una respuesta maliciosa puede revelar archivos legibles por el proceso privilegiado. Comprueba la política exacta de entorno de sudo, las exclusiones `no_proxy`, la URL solicitada, la configuración del analizador y el destino de salida; una variable proxy o un analizador XML por sí solos no constituyen una vulnerabilidad. La [documentación de variables de entorno de proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) describe el comportamiento de esas variables. No realices solicitudes de red ni analices XML malicioso durante la enumeración pasiva.
- Un script de sudo con capacidad de ejecutarse como root que construye un archivo PostScript a partir de datos influenciados por quien lo invoca y luego ejecuta `ps2pdf -dNOSAFER` merece revisar por separado el flujo de entrada. Ghostscript documenta que esta opción desactiva SAFER hasta `.setsafe`, lo que permite operaciones de archivos PostScript dentro de los permisos del sistema operativo del proceso. Una consulta SQL construida con un argumento de quien invoca el comando puede alimentar filas controladas por un atacante a la plantilla PostScript, pero una cadena de consulta o una invocación de `ps2pdf` por sí solas no demuestran que los datos lleguen a sintaxis PostScript ejecutable. Confirma la regla efectiva de sudo, la ruta exacta desde la entrada hasta la plantilla, cualquier escape, el comportamiento de Ghostscript instalado y si se vuelve a habilitar SAFER antes de interpretar el documento. No invoques la conversión privilegiada durante la enumeración pasiva. Consulta la [documentación de `-dNOSAFER` de Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para una regla de sudo que ejecuta un script de shell, compara las variables conservadas con el propio script. Una construcción como `if $CHECK_CONTENT; then` ejecuta el valor expandido como comando, por lo que conservar `CHECK_CONTENT` puede permitir ejecutar comandos aunque la ruta y los argumentos del script sean fijos. Hay que comprobar si la rama puede alcanzarse y si el entorno se conserva realmente para la regla específica.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script de Python permitido por sudo puede importar código desde un directorio modificable o un archivo `.pyc` en caché. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md) detalla el caso de la caché.
- Un script fijo de Python permitido por sudo como root aún puede exponer un depurador interactivo. Llamadas como `pdb.set_trace()` o `pdb.post_mortem()` permiten ejecutar sentencias de Python en el contexto del proceso depurado cuando quien invoca el comando puede alcanzar el punto de interrupción o el manejador de excepciones **y controlar la entrada del depurador**. Comprueba la regla exacta de sudo y RunAs, la autenticación y las condiciones de la rama, si se puede alcanzar la excepción, quién controla el terminal/la entrada y si el depurador se ejecuta en ese mismo proceso privilegiado. Una solicitud de socket que desencadena una excepción no concede por sí sola acceso a un depurador conectado a otro terminal. [Python documenta la evaluación de sentencias del depurador y el modo post mortem](https://docs.python.org/3/library/pdb.html); inspecciona el script de forma estática en lugar de activar el manejador privilegiado durante la enumeración.
- Un script fijo de Python permitido por sudo también puede leer un campo de perfil de una base de datos o un socket Unix y añadirlo a una cadena que luego se convierte en la **cadena de formato** de `str.format()`. [Los campos de reemplazo pueden seguir atributos y claves de mapas](https://docs.python.org/3/library/string.html#format-string-syntax), por lo que un campo controlado por un atacante puede inspeccionar objetos pasados a `format()` y exponer datos accesibles desde ellos si el resultado se imprime o se guarda donde quien invoca el comando pueda leerlo. Comprueba la identidad RunAs efectiva de sudo, el acceso de escritura al registro específico, el flujo de datos hacia la cadena de formato, qué objetos se proporcionan y la visibilidad de la salida. Esto no es ejecución automática de código, y una cadena de formato literal de confianza con *valores* controlados por un atacante es un caso distinto. Un secreto revelado solo se convierte en una transición de cuenta del sistema operativo si esa cuenta lo acepta. Revisa el script y los permisos del socket sin invocar la operación privilegiada.
- Un wrapper de Python con capacidad de ejecutarse como root puede pasar una URL seleccionada por quien lo invoca a `Repo.clone_from` de GitPython. Si el wrapper también habilita `protocol.ext.allow=always` de Git, un remoto `ext::` puede invocar un helper externo. Comprueba los argumentos exactos de sudo, el origen de la URL, la versión del paquete GitPython y el estado de los parches del proveedor, y si el wrapper habilita explícitamente protocolos inseguros. GitPython añadió una [protección predeterminada contra protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) en la versión 3.1.30; la versión del ejecutable `git` es un dato independiente. Una revisión pasiva debe limitarse a leer la regla y una parte acotada del código fuente, sin invocar la clonación.
- Un permiso de sudo entre usuarios para una CLI que clona repositorios puede exponer una vía independiente de inyección en cadenas de shell. Rastrea si el argumento del repositorio seleccionado por quien invoca el comando llega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js o a otro generador de comandos de shell sin separar los argumentos de forma segura; `exec` de Node pasa su cadena de comando a un shell. Confirma el usuario RunAs exacto, los subcomandos y argumentos permitidos, el código del wrapper instalado y la validación de entrada. El nombre de una herramienta de repositorios o una regla irrestricta de sudo por sí solos no demuestran inyección de comandos. Inspecciona el wrapper sin invocar una clonación privilegiada durante la enumeración.
- Un wrapper personalizado propiedad de root puede parecer seguro porque sus binarios y scripts no son modificables, aunque su decisión de realizar una acción privilegiada dependa de una bandera, un valor de una API local o el estado de un servicio que un usuario sin privilegios pueda cambiar. Rastrea cada condición hasta su entrada y sus comprobaciones de autorización. Durante la enumeración, inspecciona la configuración y los permisos sin cambiar el estado operativo; una llamada a `systemd-run` dentro del wrapper solo es pertinente si se puede influir en la condición.
- Un cliente de copias de seguridad permitido a través de sudo como root puede aceptar un archivo de configuración seleccionado por quien lo invoca (por ejemplo, `npbackup-cli -c`). Comprueba el usuario exacto de ejecución y los argumentos permitidos, y luego si quien invoca el comando controla la ruta de configuración, las rutas de origen de las copias y las opciones de repositorio o de lectura/restauración. Un secreto de repositorio cifrado en una configuración legible aún puede ser utilizable por el cliente, pero la regla por sí sola no demuestra acceso al repositorio ni divulgación de archivos de root. Valida la autorización sin ejecutar una copia de seguridad ni volcar su contenido.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) admite `--password-command`, que llama a un programa para obtener la contraseña de un repositorio. Si una regla de sudo permite a un usuario con menos privilegios ejecutar restic como root con un comando de contraseña elegido por quien lo invoca y un subcomando que necesita la contraseña, el helper podría ejecutarse como root. Revisa los argumentos exactos de sudo y las exclusiones; no invoques el helper ni un comando de copia de seguridad solo para comprobar esta condición durante la enumeración.
- Un permiso privilegiado para `restic backup` también puede cruzar un límite de lectura de archivos si el patrón de argumentos de sudo permite a quien invoca el comando elegir tanto el origen como un repositorio que luego pueda leer y descifrar. [Los comodines de argumentos de sudoers pueden coincidir con espacios en blanco y barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), así que inspecciona los comodines finales en lugar de asumir que un prefijo fijo de repositorio limita el origen. [Restic puede guardar copias en repositorios locales y remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), pero un repositorio local puede contener objetos recién escritos que solo root puede leer; confirma la política efectiva de sudo, el acceso al backend, la contraseña del repositorio y los permisos de los objetos resultantes antes de considerarlo una divulgación. Una clave SSH de la que se hizo una copia solo concede acceso si la cuenta de destino la acepta. No ejecutes una copia de seguridad para probarlo durante una revisión pasiva.
- Un comando personalizado irrestricto de mantenimiento o copias de seguridad puede aceptar una ruta de salida o proporcionar su propio planificador de tareas. Para una vía de escritura de archivos, verifica la regla exacta de sudo y el usuario de ejecución, y luego si quien invoca el comando controla tanto los datos como el destino. Para una vía de comandos programados, verifica la identidad de ejecución del planificador, la entrada de comandos y cualquier requisito adicional de contraseña o autorización. El nombre del comando o `NOPASSWD` por sí solos no demuestran ninguna de las dos vías. Consulta [escritura en archivos propiedad de root](../interesting-files-permissions/write-to-root.md) y [temporizadores de cron y systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando fijo de sudo puede cargar un archivo de configuración predecible desde un directorio compartido modificable. Rastrea si quien invoca el comando puede reemplazar ese archivo y si sus campos de origen y destino controlan una descarga o copia privilegiada. Una URL de archivo local puede exponer datos legibles solo por la cuenta RunAs de sudo; un origen controlado por quien invoca el comando junto con un destino protegido puede crear una vía de escritura. Confirma cómo maneja las URL el programa instalado, las comprobaciones de la ruta de destino, la regla efectiva de sudo y la accesibilidad de la salida. Una ruta de configuración modificable en `/tmp` por sí sola es solo un indicio; inspecciona el binario y los metadatos de archivos sin invocar la transferencia privilegiada.
- Una regla de sudo para `git apply` puede hacer que la cuenta RunAs escriba archivos seleccionados por un parche controlado por quien invoca el comando. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitía que un parche manipulado creara un enlace simbólico y luego escribiera fuera del árbol de trabajo, incluso cuando el comando no aceptaba `--unsafe-paths`. Comprueba la regla efectiva de argumentos de sudo, el origen del parche, el acceso de la cuenta RunAs al directorio de trabajo y la corrección de Git instalado o del parche retroportado por el proveedor. Una regla irrestricta que admita `--unsafe-paths` representa un riesgo distinto y explícito; ni una versión de Git ni un permiso para `git apply` por sí solos demuestran que se pueda modificar un archivo protegido. No apliques un parche no confiable durante la enumeración pasiva.
- Una regla de sudo con capacidad de ejecutarse como root para `clamscan --debug` puede cruzar un límite de lectura si un usuario con menos privilegios puede proporcionar una imagen DMG y el analizador instalado está afectado por [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que podía revelar el contenido de archivos en la salida de depuración. Confirma los argumentos permitidos exactos y la ruta de análisis, el control de la entrada, la cuenta RunAs efectiva, el parche o retroportación del motor y si quien invoca el comando puede ver la salida. Si una regla más amplia permite `--file-list`/`-f`, revisa por separado el comportamiento de esa lista; una política fija a `--debug <scan-path>` no lo admite. Inspecciona la política y los metadatos del paquete sin analizar un archivo manipulado ni mostrar salida protegida durante la enumeración.
- Una regla de sudo con capacidad de ejecutarse como root que abre una imagen de disco cifrada elegida por quien invoca el comando y una segunda regla que monta el mapper resultante pueden importar archivos controlados por quien invoca el comando al espacio de nombres de montaje del host. Confirma ambas reglas efectivas y sus argumentos, el control de la imagen y del nombre del mapper, el destino real del montaje y el propietario y modo de los archivos resultantes. Una transición a set-user-ID requiere además un ejecutable accesible, opciones de montaje que lo admitan (`nosuid` lo impide) y una política MAC o de procesos aplicable; abrir o montar una imagen por sí solo es solo un indicio. Una vía distinta mediante una copia de seguridad existente requiere su clave real y un secreto útil y legible dentro de ella. Inspecciona la política y las rutas sin abrir ni montar una imagen durante la enumeración pasiva. Consulta el [manual de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) y las [opciones de montaje](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regla de sudo con capacidad de ejecutarse como root para un script de shell o Python merece revisar el directorio de trabajo si el script invoca `./helper` sin cambiar antes a un directorio fijo. Una lista de Python como `['./helper']` pasada a `subprocess.run` puede tener el mismo comportamiento, con un directorio de trabajo elegido por quien invoca el comando. Esa persona podría elegir un directorio modificable y colocar ahí un ejecutable con ese nombre relativo; una ruta absoluta en otra parte del script no protege esta llamada. Confirma la regla efectiva, `runchdir` u otra política de cambio de directorio, el flujo y la alcanzabilidad de la rama del script, un directorio modificable y ejecutable, y las restricciones de montaje/`NOEXEC` antes de considerarlo ejecución de código. Si el script no es legible, el comportamiento seguirá siendo desconocido hasta que su código se revise por una vía autorizada. Revisa los scripts de forma estática en lugar de ejecutar el helper. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la política de directorio de trabajo.
- Un validador fijo de Python con capacidad de ejecutarse como root aún puede evaluar un archivo de datos elegido por quien lo invoca. [La documentación de `eval()` de Python advierte contra la entrada no confiable](https://docs.python.org/3/library/functions.html#eval): una comprobación del sufijo de entrada, un prefijo aritmético o una rama de validación no constituyen una zona segura si la expresión restante llega a `eval`. Confirma la regla efectiva de sudo, si quien invoca el comando puede seleccionar y controlar el archivo exacto, las condiciones de las ramas del analizador y la construcción de la expresión, y la identidad del proceso privilegiado antes de considerarlo una vía de ejecución. La presencia de `eval` en un script legible solo es una señal para revisar; inspecciona el código fuente y los permisos de los archivos sin ejecutar el validador ni enviar una expresión de prueba durante la enumeración.
- Un wrapper de Ruby con capacidad de ejecutarse como root mediante sudo que lee un nombre de archivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, puede tomar la entrada del directorio de trabajo de quien lo invoca, a menos que el wrapper o la política de sudo fijen ese directorio. Comprueba los argumentos permitidos exactos, los permisos del directorio y del archivo, y el comportamiento de Psych instalado: las implementaciones antiguas de `YAML.load` podían deserializar objetos Ruby arbitrarios, mientras que las versiones recientes restringen las clases de forma predeterminada. Una llamada estática solo es un indicio; confirma que el archivo proceda realmente de un directorio modificable por quien invoca el comando y que el cargador instalado acepte clases peligrosas. Para entradas no confiables, prefiere `safe_load` con una lista explícita y mínima de clases permitidas. Consulta la [documentación de Psych de Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) y la [documentación de Psych de Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Un permiso exacto de `sudo go run /absolute/file.go` con capacidad de ejecutarse como root merece revisar el directorio de trabajo cuando el código Go lee un archivo WASM relativo y puede ejecutar un script de shell relativo tras inspeccionar su resultado. Confirma el RunAs efectivo, los argumentos y las denegaciones del comando, la existencia de un directorio de trabajo modificable por quien invoca el comando, el flujo de datos desde WASM hasta la rama y si esta invoca el helper. Un `runchdir` fijo de sudo, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pueden cambiar la ubicación de búsqueda. La coincidencia estática de estas operaciones solo es un indicio; inspecciona el código fuente sin ejecutar Go, WASM ni el helper.
- `sudoedit` y los comodines en argumentos requieren comprobar la versión y la regla exactas; la [lista de comprobación](linux-privilege-escalation-checklist.md) incluye el problema de edición de archivos con sudoedit. Para un permiso de `sudoedit` entre usuarios sobre una ruta con comodines, inspecciona los ajustes efectivos `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, el destino resuelto y quién puede reemplazar cada entrada del directorio padre. El primero puede permitir seguir un enlace simbólico, mientras que desactivar el segundo elimina las comprobaciones de directorios modificables; ninguno de los dos ajustes demuestra por sí solo que se pueda escribir en el archivo de otro usuario. Confirma la política de sudo instalada y los argumentos exactos que coinciden antes de llegar a esa conclusión. Consulta las [definiciones de opciones de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- En una regla de comandos de sudoers, un comodín en los argumentos puede coincidir con espacios en blanco y caracteres de ruta. Por lo tanto, una regla para un comando capaz de leer archivos con un argumento como `/restricted/*` podría admitir un argumento de archivo adicional después de un prefijo coincidente. Revisa el usuario de ejecución exacto, la ruta del comando, el patrón de argumentos y las denegaciones posteriores; demostrar que se puede leer un archivo no implica que se puedan ejecutar comandos. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue entre los comodines de argumentos y los de rutas de comandos.
- Un comodín de argumentos con aspecto de ruta también puede coincidir con `../`. Por ejemplo, una regla de `node /opt/scripts/*.js` con capacidad de ejecutarse como root podría permitir un archivo JavaScript controlado por quien invoca el comando fuera de `/opt/scripts` si la ruta proporcionada sigue empezando por `/opt/scripts/` y se resuelve a través de segmentos de directorio padre. Este es un comodín de **argumento**; los comodines de la ruta del comando para el ejecutable de Node tienen reglas distintas para las barras. Comprueba la regla efectiva, las denegaciones posteriores, la resolución de la ruta, el control del archivo de destino y cualquier restricción de expresiones regulares o digest de sudoers antes de concluir que hay ejecución de código. Consulta las [reglas de comodines de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) y la [documentación de línea de comandos de Node](https://nodejs.org/api/cli.html).
- Los archivadores y otros programas de utilidad pueden tener hooks de ejecución. Comprueba los argumentos permitidos exactos con [GTFOBins](https://gtfobins.github.io/) en lugar de asumir que solo los shells o intérpretes ejecutan comandos.
- Una regla irrestricta de `qpdf` con capacidad de ejecutarse como root puede exponer un archivo privilegiado mediante adjuntos PDF: qpdf 10.2 y posteriores admiten `--empty` y `--add-attachment file ... --` con un PDF de salida. Si el proceso privilegiado puede leer el origen seleccionado y escribir el PDF en una ruta accesible para quien invoca el comando, la salida puede contener los bytes del origen. Revisa los argumentos y las exclusiones efectivas de sudo, la versión de qpdf, el acceso al origen y la ruta de salida antes de concluir que es posible divulgar el archivo. Leer una clave SSH de root solo es útil para iniciar sesión si la clave es válida y se permite la autenticación SSH de root. Consulta las [opciones de adjuntos de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La reutilización de marcas de tiempo de sudo depende de la política de caché, el usuario propietario, el terminal/la sesión y los permisos. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) cubre las comprobaciones.
- `doas` tiene sus propias reglas y configuración. Comprueba los comandos permitidos y las rutas de configuración modificables, tal como se describe en la [sección de doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Herramientas de compilación y paquetes ejecutadas mediante sudo

Un permiso irrestricto de sudo para `forge` de Foundry puede ser relevante aunque la identidad RunAs sea otro usuario sin privilegios de root. Las opciones del compilador, como `--use`, pueden seleccionar un ejecutable local, y `forge flatten -o` selecciona un archivo de salida. Comprueba la versión instalada de Forge, los argumentos exactos de sudo, las rutas accesibles del proyecto y del compilador, los permisos de salida y el entorno efectivo antes de considerar que el permiso es explotable. Un ejecutable helper relativo encontrado mediante `PATH` es una vía que depende de la versión y el entorno, no una propiedad que deba asumirse para todas las compilaciones de Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Un permiso irrestricto de `pacman` con capacidad de ejecutarse como root permite más que consultas de paquetes: `-U` acepta un paquete local, los paquetes pueden incluir scripts de instalación y `--hookdir` selecciona otro directorio de hooks. Revisa la regla efectiva de sudo, las restricciones y exclusiones de argumentos antes de probar; la enumeración pasiva no requiere instalar un paquete ni ejecutar un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper fijo de shell ejecutado mediante sudo también puede instalar una dependencia npm con nombre y luego iniciar una aplicación Node. Revisa la regla exacta de RunAs, si el paquete ya está instalado, los valores efectivos de `HOME` y `userconfig` de npm, la configuración del proyecto o las anulaciones de línea de comandos, y si un usuario con menos privilegios controla el registro o el paquete que se obtiene con ese nombre. [npm documenta la búsqueda de `.npmrc` por usuario y por proyecto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); el comportamiento de `HOME` de sudo depende de la política y la distribución instaladas, por lo que es posible que el proceso npm privilegiado lea o no el archivo `.npmrc` de un usuario modificable. Si la aplicación privilegiada importa el paquete recién instalado, su código de módulo puede ejecutarse bajo la identidad de esa aplicación. Los scripts durante la instalación son una vía distinta, dependiente de la versión y la configuración; [npm documenta su ciclo de vida y el manejo del usuario](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Una ruta `.npmrc` o una línea `npm install` por sí solas solo son indicios. Inspecciona la regla, el wrapper corto, las rutas de configuración y la procedencia del paquete sin instalarlo ni iniciar la aplicación durante la enumeración pasiva.

Un permiso de `pip` o `pip3 download` con capacidad de ejecutarse como root también es un indicio para revisar la compilación de paquetes si sus argumentos permiten seleccionar una distribución de origen no confiable, aunque el patrón de URL la limite a un servicio local y al sufijo `.tar.gz`. `pip download` acepta URL de archivos y resuelve metadatos del paquete; preparar los metadatos de una distribución de origen puede invocar su backend de compilación o código `setup.py` heredado antes de guardar el archivo. Confirma la regla exacta de RunAs y argumentos de sudo, si quien invoca el comando puede publicar o reemplazar el archivo seleccionado y si esa versión de pip realmente prepara sus metadatos. Un archivo fijo de confianza o una wheel no demuestran esta vía. No descargues ni compiles un paquete no confiable durante la enumeración pasiva. Consulta el [comando download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), la [interfaz del sistema de compilación](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones de instalación segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regla de sudo que permite `pip install` con una ruta de proyecto local seleccionada por quien invoca el comando crea un límite de compilación más directo. [pip acepta directorios de proyectos locales](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca su sistema de compilación; el [backend de compilación ejecuta hooks controlados por el proyecto](https://pip.pypa.io/en/stable/reference/build-system/). Confirma la identidad RunAs efectiva, las restricciones exactas de argumentos y las denegaciones, el control del proyecto seleccionado y el comportamiento del pip/backend instalado antes de considerar la regla como ejecución privilegiada de código. Un proyecto fijo de confianza o una regla que excluya rutas elegidas por quien invoca el comando no demuestra esta vía. Revisa la regla y los metadatos del proyecto sin instalar un paquete durante la enumeración pasiva.

Un permiso irrestricto de `easy_install` con capacidad de ejecutarse como root es un indicio relacionado de compilación de paquetes heredada. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install acepta un directorio de proyecto local y compila distribuciones de origen; un proyecto controlado por quien invoca el comando podría ejecutar su `setup.py` durante esa compilación bajo la identidad de sudo. Confirma la cuenta RunAs efectiva, las restricciones exactas de comando y argumentos (incluidas las denegaciones posteriores), el control del proyecto seleccionado y el comportamiento de la herramienta instalada. Un proyecto fijo de confianza o una política que no permita seleccionar un origen controlado por quien invoca el comando no demuestra esta vía. Inspecciona la regla y los metadatos del proyecto sin instalar un paquete durante la enumeración.

Un wrapper de Python permitido por sudo que use `setuptools.package_index.PackageIndex.download` con una URL seleccionada por quien lo invoca representa un caso distinto al de `pip download`: [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) describe cómo, en versiones afectadas anteriores a la 78.1.1, un nombre de archivo derivado de la URL podía escapar del directorio de descarga previsto y escribirse con los permisos del proceso. Confirma la regla efectiva de RunAs y argumentos de sudo, que el wrapper pase la URL de quien lo invoca a esta API concreta, la compilación instalada o el parche retroportado por el proveedor y dónde se resuelve la ruta resultante. Una cadena de versión o un directorio de descarga modificable por sí solos no demuestran que se pueda escribir en cualquier ruta. Revisa el wrapper breve y los metadatos del paquete sin obtener la URL ni escribir un archivo durante la enumeración.

Un wrapper de compilación permitido por sudo que pasa un archivo `.spec` seleccionado por quien lo invoca a PyInstaller requiere la misma revisión del límite de confianza. Un archivo spec de PyInstaller es Python ejecutable evaluado durante la **compilación**, y sus entradas `datas` pueden incluir en un artefacto archivos legibles por la identidad de compilación. Confirma el usuario RunAs exacto, las reglas de argumentos y denegaciones de sudo, el manejo de rutas y ramas del wrapper, el control del archivo spec seleccionado y el acceso al artefacto resultante. Permitir simplemente una entrada `.py` o encontrar PyInstaller instalado no demuestra control del archivo spec ni ejecución privilegiada. La revisión pasiva debe limitarse a leer un archivo wrapper acotado y sus metadatos; no debe ejecutar una compilación. Consulta la [documentación de archivos spec de PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Cargadores de presets y plugins ejecutados mediante sudo

Las herramientas Python que aceptan un preset o directorio de plugins seleccionado por quien las invoca pueden importar código con los privilegios concedidos por sudo. Por ejemplo, BBOT acepta un preset con `-p`, y su [documentación de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) describe entradas `module_dirs` que seleccionan directorios adicionales de módulos Python. Si la regla efectiva de sudo permite un preset seleccionado por quien invoca el comando y esa persona controla un módulo del directorio seleccionado, la importación puede ejecutar código como el usuario privilegiado, potencialmente antes de que la herramienta rechace un módulo no válido. Comprueba la versión instalada, la política exacta de RunAs y argumentos de sudo, y la propiedad de las rutas del preset y del módulo sin cargar el módulo durante la enumeración.

### Herramienta de línea de comandos Backdrop ejecutada mediante sudo

[Bee](https://github.com/backdrop-contrib/bee) es una herramienta PHP de línea de comandos para Backdrop CMS. Sus comandos `eval` (`php-eval`) y `php-script` pueden ejecutar PHP proporcionado por quien los invoca. Por lo tanto, una regla de sudo que permita ejecutar Bee como root con argumentos irrestrictos puede exponer la ejecución de código como root cuando Bee pueda iniciar una instalación de Backdrop. Ejecútalo desde el directorio del sitio o selecciona un sitio con la opción global `--root=<directory>`; encontrar Bee o un archivo `settings.php` de Backdrop no demuestra que exista el permiso de sudo, que haya un sitio utilizable ni que el inicio se complete correctamente. Revisa la regla efectiva de sudo, las exclusiones de comandos, la identidad del ejecutable y el acceso al sitio antes de probar. Durante la enumeración pasiva, inspecciona la regla y las rutas de archivos sin invocar Bee. Consulta el [registro de cambios de comandos de Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver la incorporación de los comandos PHP.

### Servidores de terminal ejecutados mediante sudo

`mosh-server` inicia un servidor de terminal interactivo como el usuario que lo invoca. Elige un puerto UDP alto y una clave de sesión, informa de ambos a quien lo invoca y normalmente inicia el shell de inicio de sesión de ese usuario cuando un cliente se conecta. Por lo tanto, un permiso irrestricto de sudo para `mosh-server` con capacidad de ejecutarse como root es un candidato para revisar como shell, aunque el propio comando del servidor se desacople. Comprueba la identidad RunAs efectiva, los argumentos y exclusiones permitidos, el binario instalado, el shell, la disponibilidad del cliente y el acceso UDP. La enumeración pasiva debe inspeccionar la regla de sudo sin iniciar un servidor ni mostrar ninguna clave de sesión activa. Consulta el [manual del servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) y las [notas de diseño del proyecto](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers privilegiados de copias de seguridad que reescriben el archivo de tareas de quien los invoca

Un wrapper de shell ejecutado como root puede aceptar un archivo de tareas seleccionado por quien lo invoca, eliminar `../` de las rutas de origen, comprobar que cada resultado empiece por un directorio permitido, reescribir el archivo de tareas y luego pasar su *nombre de ruta* a un programa de copias de seguridad. Revisa la ruta transformada después de resolverla de forma canónica completa: una única pasada de reemplazo de cadenas puede revelar una nueva secuencia de recorrido que una comprobación léxica de prefijo acepte. Comprueba también si el programa de copias de seguridad lee los datos transformados en memoria o vuelve a abrir el archivo. Si vuelve a abrirlo, una reescritura fallida puede dejar intacta la entrada original.

En Linux, `fs.protected_regular` puede denegar una escritura `O_CREAT` en un archivo normal de otro usuario dentro de un directorio sticky modificable por todos. Esa denegación es protectora, pero un wrapper de shell que ignore el error de escritura aún podría continuar con el archivo de tareas original. Confirma el ajuste, el propietario del archivo y el directorio, y si el wrapper se detiene cuando falla. La ruta solo es candidata a divulgación de archivos si la regla efectiva de sudo permite ejecutar el wrapper como un usuario privilegiado, quien lo invoca controla la entrada de tareas y un destino de copias de seguridad legible, y la utilidad de copias incluye realmente los orígenes protegidos. Inspecciona estas condiciones sin ejecutar la copia de seguridad durante la enumeración.

### Comodines de argumentos en herramientas de red privilegiadas

En una regla de sudo para `tcpdump`, un `*` en el **patrón de argumentos** puede coincidir con espacios en blanco y barras, por lo que una restricción que parece limitar una ruta aún podría permitir texto de opciones adicional. Esto es distinto de un comodín en la ruta del ejecutable del comando; inspecciona toda la regla de RunAs y cualquier denegación posterior. Si se pueden inyectar opciones, la invocación permitida y la [semántica de opciones de `tcpdump` instalado](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinan si `-F`, `-V`, `-r`, `-w` o `-Z` proporcionan una primitiva útil de lectura/escritura. `-V` lee una lista de nombres de archivos de captura, no vuelca arbitrariamente cualquier archivo. AppArmor u otra política MAC puede bloquear el acceso a archivos aunque sudo permita el comando; la existencia de un archivo de perfil en el disco no demuestra que esté cargado o aplicándose. Revisa la autorización y la política de forma pasiva antes de llegar a una conclusión. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) describe la diferencia entre comodines.

Una regla de sudo con capacidad de ejecutarse como root que solo enumera el ejecutable `tcpdump`, sin restricción de argumentos, también merece revisión. El [manual de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como un comando posterior a la rotación cuando `-C` o `-G` rota una captura guardada; `-Z` o un valor predeterminado de compilación pueden reducir los privilegios antes de ejecutar ese comando. Verifica la regla efectiva de sudo, la compilación instalada, el comportamiento de reducción de privilegios y si puede producirse una rotación antes de tratar la regla como una vía de escalada. Una regla resaltada es una candidata, no una prueba de ejecución de comandos como root.

### Wrappers de Nmap ejecutados mediante sudo

Cuando una ruta de `nmap` permitida por sudo sea un wrapper de shell, inspecciona la ruta permitida exacta y cada opción que reenvía. Bloquear la forma habitual `--script` no necesariamente bloquea la carga de código NSE: [`--datadir` de Nmap](https://nmap.org/book/man-misc-options.html) selecciona archivos de datos, y NSE [carga `nse_main.lua`](https://nmap.org/book/nse-implementation.html) desde el directorio de datos seleccionado cuando se habilitan los scripts. Algunas compilaciones instaladas también aceptan formas alternativas de opciones largas, así que compara las restricciones con el analizador real de ese binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) es una superficie distinta de lectura de archivos; los errores del analizador pueden revelar texto. Comprueba la regla efectiva de sudo, la lógica del wrapper, la versión de Nmap, el control del directorio y la política MAC sin ejecutar análisis durante la enumeración.

### Hooks de pull de Mercurial ejecutados mediante sudo

Una fuente fija en `sudo hg pull /fixed/source` sigue dejando que el **repositorio receptor** dependa del directorio de trabajo actual, a menos que el comando lo fije con `-R`. Un repositorio receptor controlado por quien invoca el comando puede definir hooks en `.hg/hgrc`, que quizá se ejecuten como el usuario RunAs de sudo. [Mercurial ignora la configuración de repositorios propiedad de un usuario o grupo no confiable](https://mercurial-scm.org/help/topics/config), así que inspecciona los usuarios/grupos de confianza de la cuenta RunAs y el directorio de trabajo exacto antes de considerarlo ejecución de código. Leer la política y la configuración basta para una revisión pasiva; no ejecutes un pull ni invoques un hook para enumerarlo.

### Hooks de pull de Git ejecutados mediante sudo

Para un permiso exacto de `sudo git pull` con capacidad de ejecutarse como root, comprueba también el repositorio **receptor** seleccionado por el directorio de trabajo. Un repositorio propiedad de quien invoca el comando puede tener un hook ejecutable `post-merge` que se ejecute con la identidad del proceso Git cuando un pull realiza realmente una fusión exitosa; [Git documenta este hook](https://git-scm.com/docs/githooks) y [el comportamiento de pull en cuanto a fusión o rebase](https://git-scm.com/docs/git-pull). Verifica la regla efectiva de sudo y el CWD, la ruta activa del hook y sus permisos, y si es posible realizar una fusión con nuevos commits. Un pull fallido, sin cambios o que solo haga rebase no demuestra esta vía de hook. Inspecciona la política y los metadatos del repositorio sin ejecutar el pull privilegiado.

### Copias de archivado de rsync ejecutadas mediante sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` en el **patrón de argumentos de sudoers** puede coincidir con espacios y admitir una opción adicional entre el origen y el destino. Esto es distinto de la expansión del shell de los nombres de archivo. Si quien invoca el comando puede llenar el origen y el proceso rsync privilegiado puede escribir en el destino, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) puede solicitar la propiedad privilegiada mientras el modo de archivado conserva los bits de permisos, con lo que podría crear un archivo SetUID de su propiedad. Comprueba la [semántica exacta de los comodines de sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versión de rsync, las denegaciones posteriores, `nosuid` del sistema de archivos y la política MAC. Una regla coincidente es una candidata para revisar, no una prueba de escalada de privilegios exitosa.

### Exportación de reglas de filtros de paquetes ejecutada mediante sudo

Un permiso irrestricto de sudo con capacidad de ejecutarse como root para `iptables` e `iptables-save` (o el par equivalente `ip6tables`) merece revisar la escritura de archivos. La coincidencia `comment` acepta texto de regla elegido por quien invoca el comando, mientras que `iptables-save -f` escribe el conjunto de reglas serializado en una ruta seleccionada.<sup>[[20]](#references)[[21]](#references)</sup> La utilidad de una carga depende de cómo el backend instalado serialice los comentarios y de si el archivo de destino acepta otras líneas de la exportación; `iptables-save` por sí solo no permite elegir contenido arbitrario. Comprueba la identidad RunAs exacta de sudo, los argumentos y las exclusiones, la extensión de coincidencia disponible, el backend y los permisos del destino. Durante la enumeración, inspecciona el permiso sin cambiar las reglas del firewall ni escribir un archivo.

### Directorio de registro privilegiado de Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afectaba a las versiones de Below anteriores a la 0.9.0, que creaban un directorio `/var/log/below` modificable por todos. Si un servicio o un comando permitido por sudo ejecuta como root una compilación afectada, un usuario que pueda escribir y recorrer un directorio de registros sin sticky podría sustituir una entrada de registro por un enlace simbólico antes de que el proceso privilegiado la abra. Revisa el estado del parche del paquete instalado, la ruta exacta de ejecución privilegiada, el acceso efectivo al directorio, el sticky bit y las ACL, y los metadatos de `/var/log/below/error_root.log`. Una ruta modificable por todos o una regla de sudo por sí solas no demuestran toda la cadena. Un directorio sticky o un parche retroportado por el proveedor cambian la evaluación. La enumeración pasiva solo debe inspeccionar metadatos; no es necesario crear un enlace ni ejecutar el programa privilegiado.

### Recopilación privilegiada de paquetes de soporte desde entradas modificables

Un script de perfiles de soporte permitido por `sudo` puede leer como root rutas fijas de registros y copiar su contenido a un archivo del perfil. Revisa el script real para identificar las lecturas de archivos y luego comprueba si quien lo invoca puede sustituir una ruta de origen o cualquier entrada de directorio padre por un enlace simbólico. Si la lectura privilegiada sigue ese enlace y el archivo resultante es legible por quien invoca el comando, se puede divulgar un archivo protegido. Deben darse todos los elementos: el permiso de sudo, la ruta de origen modificable, la lectura privilegiada y la salida legible; un registro o nombre de perfil modificable por sí solo no basta. Inspecciona los permisos efectivos y los metadatos de los enlaces sin reemplazar archivos ni generar un perfil durante la enumeración. La [guía de soporte de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documenta su script de perfiles ejecutado como root y el archivo de salida, lo que ilustra por qué esos paquetes deben tener entradas y acceso de salida restringidos.

### Scripts de restauración de archivos Python ejecutados como root

Una regla de sudo de alcance limitado para un script de restauración Python aún requiere revisar su entrada de archivo comprimido. Si quien invoca el comando puede seleccionar o reemplazar el archivo y el script lo extrae como root con `tarfile.extractall(filter="data")`, comprueba las actualizaciones de seguridad del intérprete antes de confiar en el filtro. CPython corrigió varias omisiones de filtros para enlaces simbólicos y duros, incluidas las de CVE-2025-4517, en las versiones 3.9.23, 3.10.18, 3.11.13, 3.12.11 y 3.13.4. Los parches retroportados por la distribución pueden corregir versiones anteriores, por lo que el número de versión mostrado por sí solo no demuestra que exista exposición.<sup>[[16]](#references)[[17]](#references)</sup>

Para una revisión pasiva, lee el comando exacto de sudo y el script, rastrea qué argumento selecciona el archivo comprimido y comprueba si el usuario actual puede escribir en él o en el directorio que lo contiene. Confirma por separado el parche del proveedor instalado y el destino de extracción; `filter="data"` no hace que todos los archivos comprimidos no confiables sean seguros.<sup>[[16]](#references)[[17]](#references)</sup>

### Cargadores de modelos de aprendizaje automático ejecutados mediante sudo

Una regla de sudo que permite seleccionar un archivo `.pt`, `.pth` o `.ckpt` merece revisión cuando un script privilegiado pasa ese archivo a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` u otro cargador basado en pickle. Comprueba la regla efectiva de RunAs, si quien invoca el comando puede crear o reemplazar el modelo seleccionado y el flujo real de argumentos a través de cualquier wrapper de shell hacia el helper Python. La extensión `.pth` también identifica archivos de configuración de Python site no relacionados, por lo que la extensión por sí sola no demuestra que se cargue un modelo. Un análisis del archivo comprimido o un análisis estático de pickle no demuestra que la carga posterior sea segura; inspecciona el comportamiento de [`weights_only`, que depende de la versión](https://docs.pytorch.org/docs/stable/notes/serialization.html), y cualquier lista de permitidos. Consulta las [notas sobre pickle de ML y Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). La enumeración pasiva nunca debe cargar ni descomprimir el modelo.

### Análisis de expresiones ejecutado mediante sudo sobre entradas almacenadas

Un script fijo de Python ejecutado como root mediante sudo aún puede evaluar texto que un usuario con menos privilegios almacene en una base de datos de la aplicación. En TensorFlow, una llamada a `preprocess_input_exprs_arg_string(value, safe=False)` selecciona una vía que usa `eval`; [el aviso de TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) describe el analizador inseguro y una corrección en su invocador de línea de comandos. Una llamada explícita de una aplicación a `safe=False` requiere una revisión aparte, aunque se haya corregido ese invocador de línea de comandos. Comprueba la regla efectiva de sudo, quién puede modificar la fila de entrada exacta, si los filtros o la puntuación permiten que esa fila llegue a la llamada y el comportamiento de la función instalada. Una versión de TensorFlow, un permiso de sudo o un archivo de modelo codificado directamente no demuestran por sí solos toda la cadena. Inspecciona el script y el flujo de datos de forma pasiva; no ejecutes el helper privilegiado ni envíes expresiones de prueba durante la enumeración.

### Configuración de needrestart permitida por sudo

`needrestart -c` carga un archivo de configuración Perl seleccionado por quien invoca el comando y evalúa su contenido. Si `sudo -l` permite ejecutar `needrestart` como root con argumentos que permiten `-c`, y quien invoca el comando puede elegir un archivo de configuración legible en una ubicación modificable, ese permiso puede llevar a ejecutar código como root. Comprueba la regla exacta de RunAs y argumentos de sudo; una regla que permita solo una lista fija de argumentos puede bloquear esta vía. Esto es distinto de las vulnerabilidades de análisis de intérpretes de needrestart: actualizar el paquete o desactivar `interpscan` no hace que un permiso irrestricto de `-c` como root sea seguro.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports de Python ejecutados mediante sudo con otra cuenta

Un punto de entrada fijo de Python aún puede importar un módulo que quien lo invoca pueda editar o reemplazar, incluso cuando sudo ejecuta el script como un usuario de servicio **que no es root**. Para un `from utils import status` literal, revisa `utils/__init__.py` y `utils/status.py` locales, además de los permisos del directorio del paquete. Confirma la ruta de importación del script, los argumentos exactos de sudo permitidos y si la acción pertinente llega a ese import antes de considerar el archivo modificable como una vía de ejecución. Inspecciona los archivos y permisos sin importar el módulo ni ejecutar el script durante la enumeración.<sup>[[2]](#references)[[3]](#references)</sup>

Una regla exacta de sudo para `python3 /absolute/script.py` solo requiere que el script sea legible; no es necesario que el archivo sea ejecutable ni que tenga un shebang. Revisa también los módulos locales **ausentes**: si el script importa un módulo cuyo nombre de archivo puede crearse en un directorio de scripts modificable por quien invoca el comando, Python podría cargarlo bajo la identidad RunAs. Confirma la regla efectiva de sudo, la [ruta de búsqueda de módulos](https://docs.python.org/3/library/sys_path_init.html) real del intérprete, si el módulo es integrado o está congelado y si se alcanza el import. Una regla directa de sudo para el script tiene requisitos distintos respecto al bit de ejecución y al shebang. Un wrapper aparte que añada tokens proporcionados por quien lo invoca después de `sudo -u account` también requiere revisar el flujo de argumentos: otro `-u` en esos tokens solo importa si la política de sudo invocada permite la identidad resultante. Las cadenas estáticas por sí solas no demuestran ninguna de las dos vías.

### Apache ejecutado mediante sudo con configuración controlada por quien lo invoca

Si una regla de sudo permite ejecutar como usuario privilegiado `apachectl`, `apache2ctl` o `httpd` con un archivo de configuración `-f` controlado por quien lo invoca, revisa los permisos de ese archivo y de su directorio padre. La directiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) de Apache recibe un nombre de módulo seguido del **nombre de archivo del módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) también carga archivos. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) pueden ampliar la configuración o revelar el contenido de archivos mediante errores. Un wrapper personalizado podría validar estas rutas, eliminar privilegios o restringir argumentos, por lo que una configuración modificable es una candidata para revisar, no una prueba de ejecución de código. Comprueba la canonicalización de rutas, los enlaces simbólicos y el análisis de directivas antes de llegar a una conclusión.

### nginx ejecutado mediante sudo con configuración controlada por quien lo invoca

Una regla irrestricta de `nginx` con capacidad de ejecutarse como root puede permitir que [`-c` seleccione otra configuración](https://nginx.org/en/docs/switches.html). Revisa los argumentos y exclusiones exactos de sudo, si quien invoca el comando puede proporcionar la configuración y si el master o los workers resultantes conservan acceso a rutas protegidas. Un `root` elegido junto con `autoindex` puede exponer archivos mediante un nuevo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) puede ofrecer una vía privilegiada de escritura de archivos, pero el módulo DAV no está compilado de forma predeterminada y hay que comprobar su presencia, la accesibilidad del listener, los permisos de archivos y el comportamiento de los archivos temporales. La directiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) también puede apuntar a un archivo elegido; escribir registros en un archivo de configuración sensible, como `/etc/ld.so.preload`, requiere un escritor privilegiado efectivo y un registro controlable antes de convertirse en una vía de escalada. Que el ejecutable aparezca resaltado en `sudo -l` es una señal para revisar, no una prueba de que alguna de estas vías funcione. La enumeración pasiva no debe iniciar ni reconfigurar nginx.

### Comparación de patrones en avisos Bash privilegiados

Cuando un script Bash permitido por sudo lee un valor de quien lo invoca y lo comprueba con `[[ "$expected" == $entered ]]`, Bash interpreta como patrón el operando derecho sin comillas. Por lo tanto, un comodín puede satisfacer la comparación sin conocer el valor esperado. Entrecomillar el operando (`[[ "$expected" == "$entered" ]]`) lo convierte en una comparación de cadenas literales. Revisa la regla exacta de sudo, si se puede llegar a la solicitud y qué hace el script después de la comparación; la sintaxis por sí sola no demuestra una vía explotable. Evita mostrar el valor esperado durante la enumeración. Consulta la [referencia de construcciones condicionales de Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers ejecutados mediante sudo que descargan y ejecutan un archivo

Un permiso irrestricto de sudo para un helper personalizado con capacidad de ejecutarse como root merece revisar el flujo de datos si acepta una URL seleccionada por quien lo invoca, escribe la respuesta en disco y luego invoca ese archivo con un intérprete o shell. [Sudoers permite argumentos arbitrarios si la entrada del comando no especifica ninguno](https://man7.org/linux/man-pages/man5/sudoers.5.html); una ruta de ejecutable fija no limita lo que pueden seleccionar sus argumentos. Confirma la validación real de la URL, la ruta de salida, la rama de éxito y la ejecución posterior en el helper instalado. Un import de libcurl coincidente o una cadena imprimible por sí solos no demuestran esta cadena.

Incluso un nombre fijo de archivo de salida puede sustituirse entre la escritura y la ejecución cuando el helper usa una **ruta relativa en un directorio de trabajo controlado por quien lo invoca**. Renombrar o sustituir un archivo propiedad de root depende del acceso de escritura y búsqueda al directorio y de cualquier restricción de sticky bit, no solo del modo del archivo; consulta [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Comprueba si el helper vuelve a abrir la ruta o usa el descriptor ya abierto y si cambia a un directorio de confianza antes de escribir. Inspecciona pasivamente la política de sudo, el helper y los metadatos del directorio; no invoques la descarga privilegiada ni intentes una carrera durante la enumeración.

Un helper de descarga ejecutado mediante sudo como root también puede exponer una inyección de **argumentos** cuando construye una cadena de comando Bash como `curl <caller input> -o <fixed output>`. Un filtro que rechaza los espacios en blanco aún deja disponible la [expansión de llaves de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): los elementos separados por comas y sin comillas pueden convertirse en argumentos independientes de curl. Si la entrada llega a curl antes del `-o` fijo, una opción de salida proporcionada por quien invoca el comando podría seleccionar el destino de la primera URL bajo la identidad del helper; [curl asocia las opciones de salida con las URL en orden](https://curl.se/docs/manpage.html#-o). Confirma el shell exacto, el uso de comillas, la validación de entrada, la regla efectiva de sudo, el orden de argumentos de curl y los esquemas de URL admitidos, y si quien invoca el comando controla los bytes obtenidos o puede leer el resultado. Un ejecutable empaquetado con PyInstaller puede contener lógica de aplicación Python, pero la marca del empaquetado o una cadena `curl` por sí solas no demuestran este flujo de datos. Revisa una copia local acotada y sin conexión cuando esté autorizado; la enumeración habitual no debe ejecutar el helper ni obtener datos seleccionados por un atacante.

Un script de shell ejecutado mediante sudo como root que llama a [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) solo elige un nombre libre; **no** crea el archivo. Si el script crea luego ese nombre en un directorio que otro usuario puede afectar, vuelve a abrirlo y añade su contenido a un destino protegido, como `authorized_keys` de root, revisa una posible carrera con el archivo temporal. Confirma la regla exacta de sudo, el propietario del directorio y del archivo, la secuencia de creación y reapertura, las protecciones del kernel y si la escritura privilegiada usa realmente bytes controlados por un atacante. Una cadena `mktemp -u` o un `/tmp` modificable por sí solos no demuestran que exista la carrera. Inspecciona el script y los metadatos de rutas sin ejecutarlo ni competir por su archivo temporal durante la enumeración.

## Notas defensivas

- Evita conceder intérpretes o editores interactivos mediante sudo.<sup>[[1]](#references)</sup>
- No concedas permisos genéricos de escritura de archivos, como `tee`, con operandos irrestrictos. Usa un wrapper propiedad de root que seleccione un destino fijo y rechace rutas controladas por quien lo invoca.<sup>[[2]](#references)</sup>
- Prefiere wrappers fijos propiedad de root que realicen una única acción administrativa de alcance limitado.<sup>[[1]](#references)[[2]](#references)</sup>
- Si un intérprete es inevitable, restringe la ruta exacta del script y evita los argumentos controlados por usuarios, los imports modificables, `PYTHONPATH` y la conservación insegura del entorno.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si se requiere editar archivos, restringe la ruta exacta del archivo y considera `sudoedit` con versiones de sudo corregidas y un manejo estricto del entorno.<sup>[[1]](#references)[[2]](#references)</sup>
- Revisa `SETENV`, `env_keep`, los directorios de trabajo modificables, las rutas de módulos/imports modificables, `NOEXEC`, `use_pty` y el registro, pero no los consideres una zona segura completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
