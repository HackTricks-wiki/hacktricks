## Interpretadores permitidos pelo sudo

Se `sudo -l` permitir que um usuário execute um interpretador como root, trate isso como execução direta de código. Interpretadores são projetados para executar código arbitrário, portanto, uma regra que permita `python3`, `perl`, `ruby`, `lua`, `node` ou binários semelhantes geralmente equivale à execução de comandos como root, a menos que os argumentos sejam rigorosamente restritos e validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Fluxo comum de análise: primeiro liste os privilégios do usuário e, em seguida, execute uma instrução Python com a opção `-c` do interpretador.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Outros exemplos de interpretadores são mostrados abaixo; os interpretadores listados documentam a execução de código em linha ou APIs de processos filhos.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

O caminho exato importa. Se a regra do sudo permitir `/usr/bin/python3`, use esse caminho exato durante a validação.<sup>[[2]](#references)</sup>

Um glob de executável do sudo, como `/usr/bin/python*`, também pode permitir Python 2 para um script escrito para Python 3. Se o script chegar a `input()` com texto controlado pelo chamador, [Python 2 avalia esse texto como uma expressão](https://docs.python.org/2/library/functions.html#input); uma invocação explícita do interpretador substitui o shebang do script. Verifique os binários correspondentes instalados, a identidade RunAs efetiva e a política de argumentos, as negações e se a entrada é alcançável antes de tratar isso como um caminho de execução.

Um caminho de script fixo em uma regra do sudo com capacidade de root não restringe o que o script executa. Para um wrapper Bash legível, verifique se o primeiro comando executável usa um parâmetro posicional sem aspas, como `$1`, como a **palavra de comando**, enquanto o sudo permite argumentos escolhidos pelo chamador. Confirme a identidade RunAs efetiva, a política de senha e de argumentos, as negações posteriores e o ramo real do script; `NOEXEC`, uma lista fixa de argumentos seguros ou um wrapper que valida o comando podem alterar o resultado. Durante a enumeração, inspecione estaticamente o script curto, em vez de invocá-lo com um comando de teste.

Uma regra irrestrita do sudo com capacidade de root para `dotnet` também merece uma análise do interpretador. Com um .NET SDK instalado, [`dotnet fsi` executa código F# interativamente ou a partir de um script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), e [`dotnet run` executa um projeto a partir do código-fonte](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Primeiro, confirme a identidade RunAs efetiva e a política exata de argumentos: uma regra restrita a um subcomando seguro específico ou a um aplicativo confiável concede algo diferente, e uma instalação somente do runtime pode não incluir comandos do SDK. O nome do executável, por si só, é um indício para análise, não uma prova de execução de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editores permitidos pelo sudo

Se `sudo -l` permitir que um usuário execute um editor interativo como root, trate isso como uma superfície de execução de comandos, não como uma permissão inofensiva para editar arquivos. Editores muitas vezes podem executar comandos de shell, ler arquivos arbitrários, gravar arquivos arbitrários ou invocar helpers externos de dentro do editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Fluxo comum de análise: liste os privilégios do usuário e, em seguida, invoque cada editor ou pager permitido usando sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Execução de comandos com o Nano

Quando o `nano` pode ser executado via sudo, a execução de comandos pode ser acessada pela interface do editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Em seguida, forneça um comando como `id` ou `/bin/sh` no prompt de comando do nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se um shell interativo não tiver fluxos de terminal utilizáveis, esta forma de redirecionamento mapeia sua saída padrão e seu erro para o descritor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

A sequência exata de teclas pode variar conforme a versão do nano e as opções de compilação, mas o problema de segurança é o mesmo: o editor está sendo executado como root e pode invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Outras formas comuns de escapar de editores

Editores no estilo do Vim geralmente permitem executar comandos por meio de `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers como `less` também podem permitir a execução de comandos do shell.<sup>[[14]](#references)</sup>

Uma regra do sudo que permita executar `apport-cli` como root merece a mesma verificação do pager. Versões afetadas do Apport podiam abrir um relatório de falha no `less` com um tamanho de terminal ajustável pelo invasor; o pager poderia então fornecer um shell root se as condições especiais do sudo e do pager fossem atendidas. Verifique a regra efetiva do sudo, a configuração do pager e a correção do pacote da distribuição antes de considerar a versão, por si só, vulnerável. Leia os metadados do pacote e da política sem gerar uma falha nem abrir o relatório privilegiado durante a enumeração passiva. [O registro de CVE da Ubuntu](https://ubuntu.com/security/CVE-2023-1326) lista as versões corrigidas dos pacotes específicas de cada release, incluindo correções retroportadas.

```text
!/bin/sh
```

## Outros riscos em regras de sudo e doas

Comece com `sudo -l`, `sudo -V` e qualquer política `doas` aplicável. Leia em conjunto o comando permitido, o usuário RunAs, os argumentos, o ambiente e os defaults. A permissão para executar como uma conta de serviço que não seja root ainda pode expor os arquivos dessa conta ou uma rota para root.

Um script Python fixo permitido pelo sudo ainda pode executar um comando de shell sob a identidade RunAs se uma entrada interativa controlada pelo chamador for concatenada em [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Uma denylist de pontuação de shell não é suficiente para garantir segurança: [o shell também reconhece substituição de comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirme que os argumentos permitidos chegam ao ramo de entrada, que a entrada chega ao comando de shell sem validação segura e que a política sudo efetiva permite o usuário RunAs pretendido. O caminho do script ou uma chamada a `os.system()` são apenas pistas para revisão; inspecione o código-fonte sem executar o script privilegiado.

Uma concessão sudo efetiva como root para `chattr` pode remover o atributo de arquivo imutável (`i`), mas isso, por si só, não concede permissão de escrita nem uma nova identidade. [O manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) informa que o atributo bloqueia modificações e que apenas root ou um processo com `CAP_LINUX_IMMUTABLE` pode alterá-lo. Verifique a política exata de argumentos do sudo e o suporte do sistema de arquivos; depois, confirme separadamente que o chamador pode escrever no arquivo após limpar o atributo e que um consumidor com identidade superior o utiliza. Uma substituição de shell de login, por exemplo, também exige credenciais aceitas pela conta de destino e um login real por meio desse shell. Revise a política, os atributos do arquivo e as permissões sem alterá-los durante a enumeração.

Se o sudo solicitar uma senha e um código de uso único, mantenha esses requisitos separados da concessão do comando. Um arquivo `.google_authenticator` legível contém material de seed sensível, enquanto um hash antigo de senha de aplicativo ou banco de dados é apenas uma candidata à senha atual da conta; nenhum dos dois prova que o outro fator é aceito pela configuração PAM efetiva. Após obter autorização, revise o RunAs e os argumentos exatos: uma concessão irrestrita como root para o `gem` do RubyGems pode expor seu comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mas uma concessão restrita ou uma autenticação malsucedida não o faz. A enumeração passiva deve informar caminhos e políticas sem exibir o seed, recuperar uma senha, gerar um código ou executar o comando privilegiado.

Uma concessão sudo efetiva que permita root para o `knife` do Chef merece uma revisão no nível do interpretador: [a documentação do Chef informa que `knife exec -E` avalia uma string Ruby localmente](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifique se a regra sudo efetiva permite o subcomando `exec` e o argumento `-E` fornecido pelo chamador, a identidade RunAs pretendida e quaisquer negações de comando ou argumentos fixos correspondentes. O binário instalado ou uma regra restrita a outros subcomandos são apenas pistas. A enumeração passiva deve informar a regra sem executar `knife`.

Uma concessão sudo exata para um `msfconsole` interativo capaz de executar como root é igualmente sensível: [GTFOBins documenta seu console `irb`](https://gtfobins.org/gtfobins/msfconsole/), que pode herdar a identidade do sudo. Confirme o usuário RunAs efetivo, a lista de argumentos permitidos, as negações de comando, `NOEXEC` ou outras restrições, o comportamento do console instalado e se o chamador pode fornecer entrada interativa. Apenas encontrar o caminho destacado é uma pista; a enumeração passiva não deve iniciar o console.

No FreeBSD, até uma regra sudo limitada a `pkg update` e `pkg install *` como root exige revisar a confiança nos repositórios. Verifique se `/etc/hosts` pode ser escrito pelo chamador e se a configuração efetiva de repositórios habilitados usa um hostname HTTP com `signature_type: none`. [O manual de `pkg.conf` do FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) informa que `none` desativa a verificação de assinaturas; `pkg+http` por si só não comprova isso. Um pacote pode conter scripts de instalação ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), portanto, um chamador que realmente controle o endpoint do repositório e possa selecionar um pacote pode cruzar a fronteira de root. Verifique sobrescritas de repositório, resolução de SRV/espelhos, argumentos sudo efetivos, seleção do pacote e execução do script antes de chegar a essa conclusão. Inspecione a política e arquivos pequenos de configuração local sem redirecionar nomes nem executar `pkg` durante a enumeração.

Uma regra sudo capaz de executar como root para `apt-get update` e `apt-get upgrade` também exige revisar a confiança nos repositórios quando o sudo preserva um `http_proxy` controlado pelo chamador. Verifique se a configuração efetiva do APT realmente usa essa variável e quais solicitações aos repositórios habilitados ela pode afetar; um proxy, por si só, não pode substituir pacotes de um arquivo autenticado por uma chave de assinatura confiável. [O manual do transporte HTTP do APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta a precedência dos proxies, e [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta verificações de assinatura, sobrescritas para repositórios inseguros e confirmação para pacotes não autenticados. Confirme o RunAs e os argumentos exatos do sudo, a política de autenticação do repositório, qualquer confirmação interativa necessária e se a atualização selecionada executa scripts de pacote como root. Inspecione a política e a configuração local passivamente; não redirecione o tráfego de pacotes nem execute uma atualização durante a enumeração.

Uma regra sudo capaz de executar `snap install` como root pode criar uma fronteira entre pacote e código se os argumentos permitirem ao chamador selecionar um snap local e um modo de instalação permissivo. [A documentação do Snap informa](https://snapcraft.io/docs/explanation/snap-development/install-modes/) que `--dangerous` ignora as verificações de asserção de snaps locais e `--devmode` relaxa o confinamento; [um hook de instalação pode ser executado na instalação inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Verifique a política exata de argumentos/RunAs do sudo, quem controla o arquivo snap, se esses modos são aceitos pelo snapd instalado e a identidade efetiva e o confinamento do hook antes de alegar acesso a arquivos protegidos do host. A presença do binário `snap` ou uma regra que parece usar curinga não comprova essa cadeia. A enumeração passiva não deve instalar um pacote nem executar seu hook.

Para uma concessão sudo exata a um binário personalizado que lê credenciais como uma conta **que não seja root**, primeiro inspecione o binário concedido e as permissões dos arquivos sem executá-lo. Um controle de senha embutido pode ser visível apenas como caracteres largos; [a documentação do GNU `strings` descreve a extração little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Uma string visível não prova que ela seja a senha aceita nem que o ramo de sucesso exponha uma credencial atual. Confirme separadamente o comportamento do binário, o acesso da conta de destino aos dados protegidos, a validade da credencial e qualquer transição posterior de conta ou grupo. Se essa conta pertencer a `docker`, verifique o acesso ao socket e a identidade rootful ou rootless do daemon antes de inferir acesso a root no host; [a documentação do Docker descreve as implicações de nível root desse grupo](https://docs.docker.com/engine/install/linux-postinstall/). A enumeração rotineira deve informar a regra sudo e a associação ao grupo sem executar o binário nem despejar suas strings.

Uma regra sudo com curinga para scripts de manutenção de um aplicativo exige revisar mais do que o caminho do script. Verifique se o script permitido aceita argumentos irrestritos ou lê configurações que uma conta de aplicativo com menos privilégios pode alterar; depois, rastreie esses valores até comandos de shell ou até o ambiente de um subprocesso. Por exemplo, o [`zmupdate.pl` do ZoneMinder monta um comando `mysqldump` e o executa por meio de `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), enquanto o [`zmdc.pl` copia a configuração `ZM_LD_PRELOAD` para `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Uma regra sudo que permita qualquer um desses scripts como root pode cruzar uma fronteira de confiança se a entrada correspondente for controlável e chegar a esse código na versão instalada. Inspecione a regra sudo efetiva, as permissões das configurações do aplicativo e o código-fonte do script; o curinga ou a configuração isoladamente são apenas pistas, não prova de execução.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` podem transformar um comando que, de outra forma, seria restrito em um sequestro de importação, biblioteca ou PATH. Consulte o [guia de variáveis de ambiente](../linux-basics/linux-environment-variables.md) e [abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Uma concessão exata `SETENV` capaz de executar como root para um wrapper de shell também merece uma revisão de um salto se o wrapper iniciar um script Python fixo com um import literal. `secure_path` restringe a busca de comandos pelo shell, não a busca de módulos [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) do Python; [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fazem o Python ignorar essa variável de ambiente. Confirme as tags e negações sudo efetivas, o ramo do wrapper, as opções do interpretador, a resolução do import e a existência de um diretório de busca gravável pelo chamador antes de considerar isso execução de código. Inspecione scripts curtos estaticamente; não invoque o wrapper privilegiado.

Uma concessão sudo exata `neofetch ""` capaz de executar como root ainda pode carregar uma configuração de shell quando os defaults sudo aplicáveis preservam um `XDG_CONFIG_HOME` controlado pelo chamador. [O carregador de configuração do Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carrega `neofetch/config.conf` ou `neofetch/config` sob esse diretório; a lista de argumentos vazia não impede essa busca. Confirme o carregador instalado, a política efetiva de RunAs e argumentos, quaisquer negações de comando, se o sudo realmente mantém a variável selecionada para esse comando e se o chamador controla um caminho de configuração legível. Uma variável preservada ou o Neofetch instalado são apenas pistas. Inspecione a política e os metadados dos arquivos sem executar o comando privilegiado nem exibir o conteúdo da configuração; consulte [tratamento de ambiente do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Uma regra sudo irrestrita para `facter` capaz de executar como root merece uma revisão separada de custom facts. [A documentação do Puppet informa](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` carrega arquivos Ruby de fact de um diretório selecionado. Verifique se a regra sudo exata permite essa opção, se o Facter instalado a aceita e se o chamador controla o diretório. Uma concessão com argumentos fixos, uma negação explícita do comando ou custom facts desativados podem alterar o resultado. A enumeração passiva deve informar a regra candidata sem executar o Facter nem ler o conteúdo dos facts.

Para uma concessão sudo exata de script capaz de executar como root com `SETENV`, inspecione nomes de comando não qualificados, como `find`, e o `PATH` efetivo após a política sudo e a inicialização do script. Um arquivo Bash carregado com `source` também pode executar `enable -n [`: [o Bash então procura um `[` externo no `PATH](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) quando o script usa esse comando mais tarde. Confirme as [regras de ambiente e `secure_path` do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) aplicáveis, quaisquer entradas `NOSETENV`/`NOEXEC` ou de negação, o fluxo do script e dos arquivos carregados e a existência de um diretório executável controlado pelo chamador. Um script legível que contenha um comando não qualificado é uma pista para revisão, não prova de execução privilegiada; inspecione-o sem invocar a regra sudo.
- Um script privilegiado que busca uma URL fixa com `curl` ainda pode aceitar uma resposta escolhida pelo chamador se uma regra sudo aplicável preservar `http_proxy` e a solicitação passar por esse proxy. Se o script então passar a resposta a um analisador XML que resolva entidades externas, uma resposta maliciosa pode revelar arquivos legíveis pelo processo privilegiado. Verifique a política de ambiente sudo exata, as exclusões `no_proxy`, a URL solicitada, a configuração do analisador e o destino da saída; uma variável de proxy ou um analisador XML isoladamente não constitui uma vulnerabilidade. A [documentação das variáveis de ambiente de proxy do curl](https://everything.curl.dev/usingcurl/proxies/env.html) descreve o comportamento dessas variáveis. Não faça solicitações de rede nem analise XML malicioso durante a enumeração passiva.
- Um script sudo capaz de executar como root que cria um arquivo PostScript com dados influenciados pelo chamador e depois executa `ps2pdf -dNOSAFER` merece uma revisão separada do fluxo de entrada. O Ghostscript documenta que essa flag desativa SAFER até `.setsafe`, permitindo operações de arquivo PostScript dentro das permissões do processo no sistema operacional. Uma consulta SQL montada a partir de um argumento do chamador pode fornecer linhas controladas pelo atacante ao modelo PostScript, mas uma string de consulta ou uma invocação de `ps2pdf` isoladamente não prova que os dados cheguem a sintaxe PostScript executável. Confirme a regra sudo efetiva, o caminho exato da entrada até o modelo, qualquer escaping, o comportamento do Ghostscript instalado e se SAFER é reativado antes da interpretação do documento. Não invoque a conversão privilegiada durante a enumeração passiva. Consulte a [documentação de `-dNOSAFER` do Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para uma regra sudo que executa um script de shell, compare as variáveis preservadas com o próprio script. Uma construção como `if $CHECK_CONTENT; then` executa o valor expandido como um comando; portanto, preservar `CHECK_CONTENT` pode permitir execução de comandos mesmo quando o caminho e os argumentos do script são fixos. É preciso verificar se o ramo pode ser alcançado e se o ambiente é realmente mantido para a regra específica.<sup>[[2]](#references)[[22]](#references)</sup>
- Um script Python permitido pelo sudo pode importar código de um diretório gravável ou de um arquivo `.pyc` em cache. O [guia de escalada de privilégios](../linux-basics/linux-privilege-escalation/README.md) detalha o caso do cache.
- Um script Python fixo permitido para execução como root ainda pode expor um depurador interativo. Chamadas como `pdb.set_trace()` ou `pdb.post_mortem()` permitem executar instruções Python no contexto do processo depurado quando o chamador consegue alcançar o breakpoint ou o tratador de exceções **e controlar o fluxo de entrada do depurador**. Verifique a regra sudo exata de RunAs, a autenticação e as condições do ramo, se a exceção pode ser alcançada, quem controla o terminal/entrada e se o depurador é executado nesse mesmo processo privilegiado. Uma solicitação de socket que provoca uma exceção não concede, por si só, acesso a um depurador ligado a outro terminal. [A documentação do Python descreve a avaliação de instruções do depurador e o modo post-mortem](https://docs.python.org/3/library/pdb.html); inspecione o script estaticamente em vez de acionar o tratador privilegiado durante a enumeração.
- Um script Python fixo permitido pelo sudo também pode ler um campo de perfil de um banco de dados ou socket Unix e anexá-lo a uma string que depois se torna a **string de formato** de `str.format()`. [Campos de substituição podem percorrer atributos e chaves de mapeamento](https://docs.python.org/3/library/string.html#format-string-syntax), portanto, um campo controlado por um atacante pode inspecionar objetos passados a `format()` e expor dados acessíveis por eles se o resultado for impresso ou armazenado em um local que o chamador possa ler. Verifique a identidade efetiva de RunAs do sudo, o acesso de escrita ao registro específico, o fluxo dos dados até a string de formato, quais objetos são fornecidos e a visibilidade da saída. Isso não é execução automática de código; uma string de formato literal confiável com *valores* controlados pelo atacante é outro caso. Um segredo revelado só permite uma transição para uma conta do sistema operacional se essa conta o aceitar. Revise o script e as permissões do socket sem invocar a operação privilegiada.
- Um wrapper Python capaz de executar como root pode passar uma URL escolhida pelo chamador para `Repo.clone_from` do GitPython. Se o wrapper também habilitar `protocol.ext.allow=always` do Git, um remoto `ext::` pode invocar um helper externo. Verifique os argumentos exatos do sudo, a origem da URL, a versão do pacote GitPython e o estado de correções do fornecedor, e se o wrapper opta explicitamente por protocolos inseguros. O GitPython adicionou uma [proteção padrão contra protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) na versão 3.1.30; a versão do executável `git` é um fato separado. A revisão passiva deve ler apenas a regra e uma parte delimitada do código-fonte, sem invocar o clone.
- Uma concessão sudo entre usuários para uma CLI que clona repositórios pode expor um caminho separado de injeção em string de shell. Rastreie se o argumento de repositório escolhido pelo chamador chega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) do Node.js ou a outro construtor de comandos de shell sem separação segura de argumentos; o `exec` do Node passa sua string de comando a um shell. Confirme o usuário RunAs exato, os subcomandos e argumentos permitidos, o código do wrapper instalado e a validação da entrada. O nome de uma ferramenta de repositório ou uma regra sudo irrestrita isoladamente não prova injeção de comandos. Inspecione o wrapper sem invocar um clone privilegiado durante a enumeração.
- Um wrapper personalizado de propriedade do root pode parecer seguro porque seus binários e scripts não são graváveis, mas a decisão de executar uma ação privilegiada pode depender de uma flag, valor de API local ou estado de serviço que um usuário sem privilégios pode alterar. Rastreie cada condição até sua entrada e suas verificações de autorização. Durante a enumeração, inspecione configurações e permissões sem alterar o estado operacional; uma chamada a `systemd-run` dentro do wrapper só é relevante se a condição puder ser influenciada.
- Um cliente de backup permitido pelo sudo como root pode aceitar um arquivo de configuração escolhido pelo chamador (por exemplo, `npbackup-cli -c`). Verifique o usuário RunAs e os argumentos permitidos exatos; depois, confirme se o chamador controla o caminho da configuração, os caminhos de origem do backup e o repositório ou as opções de leitura/restauração. Um segredo de repositório criptografado em uma configuração legível ainda pode ser utilizável pelo cliente, mas a regra, por si só, não comprova acesso ao repositório nem divulgação de arquivos root. Valide a autorização sem executar um backup nem despejar seu conteúdo.
- O [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) oferece suporte a `--password-command`, que chama um programa para obter a senha de um repositório. Se uma regra sudo permitir que um usuário com menos privilégios execute o Restic como root com um comando de senha escolhido pelo chamador e um subcomando que exija a senha, esse helper poderá ser executado como root. Revise os argumentos e as exclusões exatas do sudo; não invoque o helper nem um comando de backup apenas para enumerar a condição.
- Uma concessão privilegiada `restic backup` também pode cruzar uma fronteira de leitura de arquivos se o padrão de argumentos do sudo permitir ao chamador escolher tanto a origem quanto um repositório que ele possa ler e descriptografar depois. [Curingas de argumentos do sudoers podem corresponder a espaços em branco e barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf); inspecione curingas finais em vez de presumir que um prefixo fixo do repositório restringe a origem. [O Restic pode fazer backup para repositórios locais e remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mas um repositório local pode conter objetos root-only recém-gravados; confirme a política sudo efetiva, o acesso ao backend, a senha do repositório e as permissões dos objetos resultantes antes de considerar isso divulgação. Uma chave SSH armazenada no backup só dá acesso se a conta de destino a aceitar. Não execute um backup para testar isso durante a revisão passiva.
- Um comando irrestrito de manutenção ou backup personalizado pode aceitar um caminho de saída ou oferecer seu próprio agendador de tarefas. Para um caminho de gravação de arquivo, verifique a regra sudo exata e o usuário RunAs; depois, confirme se o chamador controla tanto os dados quanto o destino. Para um caminho de comando agendado, verifique a identidade de execução do agendador, a entrada do comando e qualquer senha ou autorização adicional. O nome do comando ou `NOPASSWD`, por si só, não comprova nenhuma das rotas. Consulte [gravação em arquivos de propriedade do root](../interesting-files-permissions/write-to-root.md) e [cron e temporizadores systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Um comando sudo fixo ainda pode carregar um arquivo de configuração previsível de um diretório gravável compartilhado. Rastreie se o chamador pode substituir esse arquivo e se os campos de origem e destino controlam uma busca ou cópia privilegiada. Uma URL de arquivo local pode expor dados legíveis apenas pela conta RunAs do sudo; uma origem controlada pelo chamador combinada com um destino protegido pode criar um caminho de escrita. Confirme o tratamento de URLs pelo programa instalado, as verificações do caminho de destino, a regra sudo efetiva e a acessibilidade da saída. Um caminho de configuração gravável em `/tmp`, por si só, é apenas uma pista; inspecione o binário e os metadados do arquivo sem invocar a transferência privilegiada.
- Uma regra sudo para `git apply` pode permitir que a conta RunAs grave arquivos selecionados por um patch controlado pelo chamador. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitia que um patch criado para esse fim criasse um symlink e depois gravasse fora da árvore de trabalho, mesmo quando o comando não aceitava `--unsafe-paths`. Verifique a regra efetiva de argumentos do sudo, a origem do patch, o acesso da conta RunAs ao diretório de trabalho e a correção do Git instalado ou o backport do fornecedor. Uma regra irrestrita que permita `--unsafe-paths` representa um risco separado dessa opção explícita; nem a versão do Git nem a permissão para `git apply`, isoladamente, comprovam que um arquivo protegido possa ser alterado. Não aplique um patch não confiável durante a enumeração passiva.
- Uma regra root-capable do sudo para `clamscan --debug` pode cruzar uma fronteira de leitura se um usuário com menos privilégios puder fornecer uma imagem DMG e o analisador instalado for afetado pela [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que podia divulgar o conteúdo de arquivos pela saída de debug. Confirme os argumentos permitidos e o caminho de verificação exatos, o controle da entrada, a conta RunAs efetiva, a correção/backport do mecanismo e se o chamador consegue ver a saída. Se uma regra mais ampla permitir `--file-list`/`-f`, revise separadamente o comportamento dessa lista; uma política fixa a `--debug <caminho-de-verificação>` não permite essa opção. Inspecione a política e os metadados dos pacotes sem verificar um arquivo criado para explorar a falha nem exibir saída protegida durante a enumeração.
- Uma regra sudo capaz de executar como root que abre uma imagem de disco criptografada escolhida pelo chamador e uma segunda regra que monta o mapper resultante pode importar arquivos controlados pelo chamador para o namespace de montagem do host. Confirme ambas as regras efetivas e seus argumentos, o controle da imagem e do nome do mapper, o destino real da montagem e o proprietário e modo dos arquivos resultantes. Uma transição set-user-ID exige também um executável acessível, opções de montagem que a respeitem (`nosuid` a bloqueia) e políticas de processo ou MAC aplicáveis; abrir ou montar uma imagem, por si só, é apenas uma pista. Uma rota separada por meio de um backup existente exige sua chave real e um segredo útil e legível dentro dele. Inspecione a política e os caminhos sem abrir nem montar uma imagem durante a enumeração passiva. Consulte o [manual de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e as [opções de montagem](https://man7.org/linux/man-pages/man8/mount.8.html).
- Uma regra sudo capaz de executar como root para um script de shell ou Python merece revisar o diretório de trabalho se o script invocar `./helper` sem antes mudar para um diretório fixo. Uma lista Python como `['./helper']` passada a `subprocess.run` pode ter o mesmo comportamento de diretório de trabalho escolhido pelo chamador. O chamador pode conseguir selecionar um diretório gravável e colocar nele um executável com esse nome relativo; um caminho absoluto em outra parte do script não protege essa chamada. Confirme a regra efetiva, `runchdir` ou outra política de mudança de diretório, o fluxo e a possibilidade de alcançar o ramo do script, um diretório gravável e executável e as restrições de montagem/`NOEXEC` antes de considerar isso execução de código. Se o script não puder ser lido, o comportamento é desconhecido até que seu código seja revisado por um meio autorizado. Revise os scripts estaticamente em vez de executar o helper. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta a política de diretório de trabalho.
- Um validador Python fixo capaz de executar como root ainda pode avaliar um arquivo de dados escolhido pelo chamador. [A documentação de `eval()` do Python alerta contra entradas não confiáveis](https://docs.python.org/3/library/functions.html#eval): uma verificação de sufixo, um prefixo aritmético ou um ramo de validação não cria um sandbox se a expressão restante chegar a `eval`. Confirme a regra sudo efetiva, se o chamador pode selecionar e controlar o arquivo exato, as condições do ramo do analisador e a construção da expressão, e a identidade do processo privilegiado antes de considerar isso um caminho de execução. A presença de `eval` em um script legível é apenas uma pista para revisão; inspecione o código-fonte e as permissões dos arquivos sem executar o validador nem enviar uma expressão de teste durante a enumeração.
- Um wrapper Ruby do sudo capaz de executar como root que lê um nome de arquivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, pode receber entrada do diretório de trabalho do chamador, a menos que o wrapper ou a política sudo fixe esse diretório. Verifique os argumentos permitidos exatos, as permissões do diretório e do arquivo e o comportamento do Psych instalado: implementações antigas de `YAML.load` podiam desserializar objetos Ruby arbitrários, enquanto versões mais novas restringem as classes por padrão. Uma chamada estática é apenas uma pista; confirme que o arquivo realmente vem de um diretório gravável pelo chamador e que o carregador instalado aceita classes perigosas. Prefira `safe_load` com uma allowlist mínima e explícita de classes para entradas não confiáveis. Consulte a [documentação do Psych do Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e a [documentação do Psych do Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Uma concessão sudo exata `sudo go run /absolute/file.go` capaz de executar como root merece revisar o diretório de trabalho quando o código Go lê um arquivo WASM relativo e pode executar um script de shell relativo após inspecionar seu resultado. Confirme o RunAs efetivo, os argumentos e as negações do comando, um diretório atual gravável pelo chamador, o fluxo dos dados do WASM até o ramo e se esse ramo invoca o helper. Um `runchdir` fixo do sudo, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) podem alterar o local da busca. A ocorrência conjunta estática é apenas uma candidata; inspecione o código-fonte sem executar Go, WASM ou o helper.
- `sudoedit` e curingas de argumentos exigem verificar a versão e a regra exatas; a [checklist](linux-privilege-escalation-checklist.md) inclui o problema de edição de arquivo do sudoedit. Para uma concessão sudoedit entre usuários em um caminho com curinga, inspecione a configuração efetiva `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, o destino resolvido e quem pode substituir cada entrada de diretório pai. A primeira pode permitir seguir um symlink, enquanto desativar a segunda remove as verificações de diretório gravável; nenhuma das configurações, isoladamente, comprova que seja possível gravar no arquivo de outro usuário. Confirme a política sudo instalada e os argumentos correspondentes exatos antes de chegar a essa conclusão. Consulte as [definições das opções do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Em uma regra de comando do sudoers, um curinga de argumento pode corresponder a espaços em branco, além de caracteres de caminho. Uma regra para um comando capaz de ler arquivos com um argumento como `/restricted/*` pode, portanto, aceitar um argumento de arquivo extra após um prefixo correspondente. Revise o usuário RunAs exato, o caminho do comando, o padrão de argumentos e as negações posteriores; comprovar a leitura de arquivo não implica execução de comandos. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue curingas de argumentos de curingas de caminhos de comando.
- Um padrão de argumento que parece restringir um caminho também pode corresponder a `../`. Por exemplo, uma regra root-capable `node /opt/scripts/*.js` pode permitir um arquivo JavaScript controlado pelo chamador fora de `/opt/scripts` se o caminho fornecido ainda começar com `/opt/scripts/` e resolver por segmentos de diretório pai. Esse é um curinga de **argumento**; o curinga no caminho do comando para o executável Node tem regras diferentes para barras. Verifique a regra efetiva, as negações posteriores, a resolução do caminho, o controle do arquivo de destino e quaisquer restrições de expressão regular ou digest do sudoers antes de concluir que há execução de código. Consulte as [regras de curinga do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e a [documentação de linha de comando do Node](https://nodejs.org/api/cli.html).
- Arquivadores e outros utilitários podem ter hooks de execução. Teste os argumentos exatos permitidos contra o [GTFOBins](https://gtfobins.github.io/) em vez de presumir que apenas shells ou interpretadores executam comandos.
- Uma regra irrestrita root-capable para `qpdf` pode expor um arquivo privilegiado por meio de anexos PDF: o qpdf 10.2 e versões posteriores oferecem suporte a `--empty` e `--add-attachment file ... --` com um PDF de saída. Se o processo privilegiado puder ler a origem selecionada e gravar o PDF em um caminho acessível pelo chamador, essa saída poderá conter os bytes da origem. Revise os argumentos e as exclusões sudo efetivos, a versão do qpdf, o acesso à origem e o caminho de saída antes de concluir que a divulgação de arquivos é possível. Ler uma chave SSH do root só é útil para login se a chave for válida e a autenticação SSH do root estiver permitida. Consulte as [opções de anexos do qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- O reaproveitamento de timestamps do sudo depende da política de cache, do usuário proprietário, do terminal/sessão e das permissões. O [guia de escalada de privilégios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) aborda as verificações.
- `doas` tem suas próprias regras e configurações. Verifique os comandos permitidos e os caminhos de configuração graváveis conforme descrito na [seção do doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Ferramentas de build e pacotes executadas pelo sudo

Uma concessão sudo irrestrita para `forge` do Foundry pode ser relevante mesmo quando a identidade RunAs é outro usuário sem privilégios de root. Opções do compilador como `--use` podem selecionar um executável local, e `forge flatten -o` seleciona um arquivo de saída. Verifique a versão instalada do Forge, os argumentos sudo exatos, os caminhos acessíveis do projeto e do compilador, as permissões da saída e o ambiente efetivo antes de considerar a concessão explorável. Um executável helper relativo encontrado por meio de `PATH` é uma rota dependente da versão e do ambiente, não algo que se deva presumir em qualquer build do Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Uma concessão irrestrita root-capable para `pacman` permite mais do que consultas a pacotes: `-U` aceita um pacote local, pacotes podem conter scripts de instalação e `--hookdir` seleciona outro diretório de hooks. Revise a regra sudo efetiva, as restrições de argumentos e as exclusões antes de testar; a enumeração passiva não precisa instalar um pacote nem executar um hook.<sup>[[25]](#references)[[26]](#references)</sup>

Um wrapper de shell fixo do sudo também pode instalar uma dependência npm nomeada e depois iniciar um aplicativo Node. Revise sua regra RunAs exata, se o pacote já está instalado, o `HOME` efetivo e o `userconfig` do npm, as configurações do projeto ou sobrescritas de linha de comando, e se um usuário com menos privilégios controla o registry ou o pacote retornado para esse nome. [A documentação do npm descreve a busca por `.npmrc` por usuário e por projeto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); o comportamento de `HOME` do sudo depende da política instalada e da distribuição, portanto, o processo npm privilegiado pode ou não ler o `.npmrc` de um usuário gravável. Se o aplicativo privilegiado importar o pacote recém-instalado, o código do módulo poderá ser executado sob a identidade desse aplicativo. Scripts executados durante a instalação são um caminho separado, dependente da versão e da configuração; [a documentação do npm descreve seu ciclo de vida e o tratamento de usuários](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Um caminho `.npmrc` ou uma linha `npm install`, isoladamente, é apenas uma pista. Inspecione a regra, o wrapper curto, os caminhos de configuração e a procedência do pacote sem instalar o pacote nem iniciar o aplicativo durante a enumeração passiva.

Uma concessão root-capable para `pip` ou `pip3 download` também é uma pista para revisar o build de pacotes quando os argumentos permitem ao chamador selecionar uma distribuição fonte não confiável, mesmo que o padrão da URL a restrinja a um serviço local e a um sufixo `.tar.gz`. `pip download` aceita URLs de arquivos compactados e resolve metadados de pacotes; a preparação de uma sdist pode invocar seu backend de build ou código legado `setup.py` antes que o arquivo seja apenas salvo. Confirme o RunAs e a regra de argumentos exatos do sudo, se o chamador pode publicar ou substituir o arquivo selecionado e se essa versão do pip realmente prepara seus metadados. Um arquivo compactado ou wheel confiável e fixo não comprova esse caminho. Não busque nem compile um pacote não confiável durante a enumeração passiva. Consulte o [comando download do pip](https://pip.pypa.io/en/stable/cli/pip_download/), a [interface do sistema de build](https://pip.pypa.io/en/stable/reference/build-system/) e as [orientações de instalação segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Uma regra sudo que permite `pip install` com um caminho de projeto local escolhido pelo chamador cria uma fronteira de build mais direta. [O pip aceita diretórios de projeto locais](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca seu sistema de build; o [backend de build executa hooks controlados pelo projeto](https://pip.pypa.io/en/stable/reference/build-system/). Confirme a identidade RunAs efetiva, as restrições e negações exatas dos argumentos, o controle do projeto selecionado e o comportamento do pip/backend instalado antes de considerar a regra execução de código privilegiada. Um projeto confiável fixo ou uma regra que exclua caminhos escolhidos pelo chamador não comprova essa rota. Revise a regra e os metadados do projeto sem instalar um pacote durante a enumeração passiva.

Uma concessão irrestrita root-capable para `easy_install` é uma pista relacionada a builds de pacotes legados. [A documentação do Setuptools informa](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que o Easy Install aceita um diretório de projeto local e compila distribuições fonte; um projeto controlado pelo chamador pode executar seu `setup.py` durante esse build sob a identidade do sudo. Confirme a conta RunAs efetiva, o comando e as restrições exatas de argumentos (incluindo negações posteriores), o controle do projeto selecionado e o comportamento da ferramenta instalada. Um projeto confiável fixo ou uma política que não permita uma origem escolhida pelo chamador não comprova esse caminho. Inspecione a regra e os metadados do projeto sem instalar um pacote durante a enumeração.

Um wrapper Python permitido pelo sudo que usa `setuptools.package_index.PackageIndex.download` com uma URL escolhida pelo chamador é um caso de revisão diferente de `pip download`: [GHSA-5rjg-fvgr-3xxf do setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descreve como, em versões afetadas anteriores à 78.1.1, um nome de arquivo derivado da URL podia escapar do diretório de download pretendido e gravar com as permissões do processo. Confirme o RunAs efetivo e a regra de argumentos do sudo, se o wrapper passa a URL do chamador para essa API exata, o build instalado ou o backport do fornecedor e onde o caminho resultante é resolvido. Uma string de versão ou um diretório de download gravável, por si só, não comprova escrita arbitrária. Revise o wrapper curto e os metadados do pacote sem buscar a URL nem gravar um arquivo durante a enumeração.

Um wrapper de build permitido pelo sudo que passa um arquivo `.spec` escolhido pelo chamador ao PyInstaller exige a mesma revisão de fronteira de confiança. Um spec do PyInstaller é Python executável avaliado durante o **build**, e suas entradas `datas` podem incluir em um artefato arquivos legíveis pela identidade de build. Confirme o usuário RunAs exato, as regras sudo de argumentos e negações, o tratamento de caminhos e ramos do wrapper, o controle do arquivo spec selecionado e o acesso ao artefato resultante. Permitir apenas uma entrada `.py` ou encontrar o PyInstaller instalado não comprova controle do arquivo spec nem execução privilegiada. A revisão passiva deve ler apenas um arquivo wrapper e metadados delimitados; não deve executar um build. Consulte a [documentação de arquivos spec do PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Carregadores de presets e plugins executados pelo sudo

Ferramentas Python que aceitam um preset ou diretório de plugins escolhido pelo chamador podem importar código com os privilégios concedidos pelo sudo. Por exemplo, o BBOT aceita um preset com `-p`, e sua [documentação de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descreve entradas `module_dirs` que selecionam diretórios adicionais de módulos Python. Se a regra sudo efetiva permitir um preset escolhido pelo chamador e este controlar um módulo no diretório selecionado, a importação poderá executar código como o usuário privilegiado, potencialmente antes de a ferramenta rejeitar um módulo inválido. Verifique a versão instalada, a política exata de RunAs e argumentos do sudo e a propriedade dos caminhos do preset e do módulo sem carregar o módulo durante a enumeração.

### Ferramenta de linha de comando Backdrop executada pelo sudo

[Bee](https://github.com/backdrop-contrib/bee) é uma ferramenta de linha de comando PHP para Backdrop CMS. Seus comandos `eval` (`php-eval`) e `php-script` podem executar PHP fornecido pelo chamador. Portanto, uma regra sudo que permita o executável Bee como root com argumentos irrestritos pode expor execução de código como root quando Bee consegue inicializar uma instalação do Backdrop. Execute-o no diretório do site ou selecione um site usando a opção global `--root=<directory>`; simplesmente encontrar Bee ou um arquivo `settings.php` do Backdrop não comprova a permissão sudo, a existência de um site utilizável nem uma inicialização bem-sucedida. Revise a regra sudo efetiva, quaisquer exclusões de comando, a identidade do executável e o acesso ao site antes de testar. Durante a enumeração passiva, inspecione a regra e os caminhos dos arquivos sem invocar Bee. Consulte o [changelog dos comandos do Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver a inclusão dos comandos PHP.

### Servidores de terminal executados pelo sudo

`mosh-server` inicia um servidor de terminal interativo como o usuário que o invoca. Ele escolhe uma porta UDP alta e uma chave de sessão, informa ambos ao chamador e normalmente inicia o shell de login desse usuário quando um cliente se conecta. Portanto, uma concessão sudo irrestrita root-capable para `mosh-server` é candidata a revisão de shell, embora o próprio comando do servidor se desacople. Verifique a identidade RunAs efetiva, os argumentos e as exclusões permitidos, o binário instalado, o shell, a disponibilidade do cliente e o acesso UDP. A enumeração passiva deve inspecionar a regra sudo sem iniciar um servidor nem exibir uma chave de sessão ativa. Consulte o [manual do servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e as [notas de design upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers privilegiados de backup que reescrevem o arquivo de tarefas do chamador

Um wrapper de shell executado como root pode aceitar um arquivo de tarefas selecionado pelo chamador, remover `../` dos caminhos de origem, verificar se cada resultado começa com um diretório permitido, reescrever o arquivo de tarefas e depois passar seu *caminho* a um programa de backup. Revise o caminho transformado após a resolução canônica completa: uma única passagem de substituição de string pode revelar uma nova sequência de traversal aceita por uma verificação de prefixo lexical. Verifique também se o programa de backup lê os dados transformados em memória ou abre o arquivo novamente. Se ele reabrir o arquivo, uma reescrita malsucedida pode deixar a entrada original intacta.

No Linux, `fs.protected_regular` pode negar uma gravação `O_CREAT` em um arquivo regular de outro usuário dentro de um diretório sticky gravável por todos. Essa negação é uma proteção, mas um wrapper de shell que ignora o erro de gravação ainda pode continuar usando o arquivo de tarefas original. Confirme a configuração, o proprietário do arquivo e do diretório e se o wrapper interrompe a execução em caso de falha. O caminho só é candidato a divulgação de arquivos quando a regra sudo efetiva permite executar o wrapper como um usuário privilegiado, o chamador controla a entrada de tarefas e um destino de backup legível, e o utilitário de backup realmente inclui origens protegidas. Inspecione essas condições sem executar o backup durante a enumeração.

### Curingas de argumentos em ferramentas de rede privilegiadas

Em uma regra sudo para `tcpdump`, um `*` no **padrão de argumento** pode corresponder a espaços em branco e barras; portanto, uma restrição que parece limitar um caminho ainda pode permitir texto de opção adicional. Isso é diferente de um curinga no caminho do executável do comando; inspecione a regra RunAs completa e quaisquer negações posteriores. Se opções puderem ser injetadas, a invocação permitida e a [semântica das opções de `tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) na versão instalada determinam se `-F`, `-V`, `-r`, `-w` ou `-Z` oferece uma primitiva útil de leitura/escrita. `-V` lê uma lista de nomes de arquivos de captura, não um despejo genérico de arquivos arbitrários. AppArmor ou outra política MAC pode bloquear o acesso a arquivos mesmo quando o sudo permite o comando; a existência de um arquivo de perfil no disco não comprova que ele esteja carregado ou em modo de imposição. Revise a autorização e a política passivamente antes de chegar a uma conclusão. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descreve a distinção entre curingas.

Uma regra sudo root-capable que liste apenas o executável `tcpdump`, sem restrição de argumentos, também merece revisão. O [manual do tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como um comando executado após a rotação quando `-C` ou `-G` rotaciona uma captura salva; `-Z` ou um padrão definido durante a compilação pode remover privilégios antes que esse comando seja executado. Verifique a regra sudo efetiva, o build instalado, o comportamento de remoção de privilégios e se uma rotação pode ocorrer antes de considerar a regra um caminho de escalada. Uma regra destacada é uma candidata, não prova de execução de comandos como root.

### Wrappers do Nmap executados pelo sudo

Quando um caminho `nmap` permitido pelo sudo é um wrapper de shell, inspecione o caminho exato permitido e todas as opções que ele repassa. Bloquear a forma conhecida `--script` não necessariamente bloqueia o carregamento de código NSE: a opção [`--datadir`](https://nmap.org/book/man-misc-options.html) do Nmap seleciona arquivos de dados, e o NSE [carrega `nse_main.lua`](https://nmap.org/book/nse-implementation.html) do diretório de dados selecionado quando o scripting está habilitado. Alguns builds instalados também aceitam formas alternativas de opções longas; compare as restrições com o parser real desse binário. [`--excludefile`](https://nmap.org/book/man-target-specification.html) é outra superfície de leitura de arquivos; erros do parser podem revelar texto. Verifique a regra sudo efetiva, a lógica do wrapper, a versão do Nmap, o controle do diretório e a política MAC sem executar varreduras durante a enumeração.

### Hooks de pull do Mercurial executados pelo sudo

Uma origem fixa em `sudo hg pull /fixed/source` ainda deixa o repositório **de recebimento** selecionado pelo diretório de trabalho atual, a menos que o comando o fixe com `-R`. Um repositório de recebimento controlado pelo chamador pode definir hooks em `.hg/hgrc`, e um hook pode ser executado como o usuário RunAs do sudo. [O Mercurial ignora configurações de repositório pertencentes a um usuário ou grupo não confiável](https://mercurial-scm.org/help/topics/config); portanto, inspecione os usuários/grupos confiáveis da conta RunAs e o diretório de trabalho exato antes de considerar isso execução de código. Ler a política e a configuração basta para uma revisão passiva; não execute pull nem invoque um hook durante a enumeração.

### Hooks de pull do Git executados pelo sudo

Para uma concessão sudo exata e root-capable de `sudo git pull`, verifique também o repositório **de recebimento** selecionado pelo diretório de trabalho. Um repositório pertencente ao chamador pode ter um hook executável `post-merge`, executado com a identidade do processo Git quando um pull realmente realiza um merge bem-sucedido; [o Git documenta esse hook](https://git-scm.com/docs/githooks) e o [comportamento de merge versus rebase do pull](https://git-scm.com/docs/git-pull). Verifique a regra sudo e o CWD efetivos, o caminho e as permissões do hook ativo e se é possível alcançar um merge com novos commits. Um pull que falha, não faz alterações ou só executa rebase não comprova esse caminho de hook. Inspecione a política e os metadados do repositório sem executar o pull privilegiado.

### Cópias de arquivos com rsync executado pelo sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, um `*` no **padrão de argumentos do sudoers** pode corresponder a espaços e permitir uma opção extra entre a origem e o destino. Isso é distinto da expansão do shell de nomes de arquivos. Se o chamador puder preencher a origem e o destino puder ser gravado pelo processo rsync privilegiado, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) pode solicitar propriedade privilegiada enquanto o modo de arquivamento preserva bits de permissão, podendo criar um arquivo owned SetUID. Verifique a semântica exata de [curingas do sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), a versão do rsync, as negações posteriores, `nosuid` no sistema de arquivos e a política MAC. Uma regra correspondente é uma candidata à revisão, não prova de escalada de privilégios bem-sucedida.

### Exportação de regras de filtro de pacotes executada pelo sudo

Uma concessão root-capable irrestrita para `iptables` e `iptables-save` (ou o par correspondente `ip6tables`) merece uma revisão de gravação de arquivo. O match `comment` aceita texto de regra escolhido pelo chamador, enquanto `iptables-save -f` grava o ruleset serializado em um caminho selecionado.<sup>[[20]](#references)[[21]](#references)</sup> Um payload útil depende de como o backend instalado serializa comentários e se o arquivo de destino aceita outras linhas na exportação; `iptables-save`, por si só, não fornece conteúdo arbitrário escolhido pelo chamador. Verifique a identidade RunAs, os argumentos e as exclusões exatos do sudo, a extensão de match disponível, o backend e as permissões do destino. Durante a enumeração, inspecione a concessão sem alterar regras de firewall nem gravar um arquivo.

### Diretório de logs do Below acessível de forma privilegiada

A [CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afetou versões do Below anteriores à 0.9.0 que criavam o diretório `/var/log/below` gravável por todos. Se um serviço ou comando sudo permitido executar um build afetado como root, um usuário que possa gravar e percorrer um diretório de logs sem sticky bit pode conseguir substituir uma entrada de log por um symlink antes que o processo privilegiado a abra. Revise o estado de correção do pacote instalado, o caminho exato de execução privilegiada, o acesso efetivo ao diretório, o sticky bit e as ACLs, além dos metadados de `/var/log/below/error_root.log`. Um caminho gravável por todos ou uma regra sudo, isoladamente, não comprova a cadeia completa. Um diretório sticky ou um backport do fornecedor altera a avaliação. A enumeração passiva deve inspecionar apenas metadados; não é necessário criar um link nem executar o programa privilegiado.

### Coleta privilegiada de pacotes de suporte a partir de entradas graváveis

Um script de perfil de suporte permitido pelo `sudo` pode ler caminhos fixos de logs como root e copiar seu conteúdo para um arquivo de perfil. Revise o script real para identificar leituras de arquivos; depois, verifique se o chamador pode substituir um caminho de origem ou qualquer entrada de diretório pai por um symlink. Se a leitura privilegiada seguir esse link e o arquivo resultante puder ser lido pelo chamador, um arquivo protegido poderá ser divulgado. A concessão sudo, o caminho de origem gravável, a leitura privilegiada e a saída legível precisam estar presentes; um log ou nome de perfil gravável, isoladamente, não basta. Inspecione as permissões efetivas e os metadados dos links sem substituir arquivos nem gerar um perfil durante a enumeração. As [orientações de suporte do Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentam seu script de perfil executado como root e o arquivo de saída, ilustrando por que esses pacotes precisam de entradas restritas e acesso de saída limitado.

### Scripts Python de restauração de arquivos executados como root

Uma regra sudo estritamente delimitada para um script Python de restauração ainda exige revisar sua entrada de arquivo compactado. Se o chamador puder selecionar ou substituir o arquivo e o script o extrair como root usando `tarfile.extractall(filter="data")`, verifique as atualizações de segurança do interpretador antes de confiar no filtro. O CPython corrigiu várias formas de contornar o filtro com symlinks e hard links, incluindo a CVE-2025-4517, nas versões 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. Backports das distribuições podem corrigir uma versão anterior; portanto, a versão exibida do interpretador, por si só, não comprova exposição.<sup>[[16]](#references)[[17]](#references)</sup>

Para uma revisão passiva, leia o comando sudo e o script exatos, rastreie qual argumento escolhe o arquivo compactado e verifique se o usuário atual pode gravar nele ou em seu diretório pai. Confirme separadamente o patch do fornecedor instalado e o destino da extração; `filter="data"` não torna seguro todo arquivo compactado não confiável.<sup>[[16]](#references)[[17]](#references)</sup>

### Carregadores de modelos de machine learning executados pelo sudo

Uma regra sudo que permite ao chamador selecionar um arquivo `.pt`, `.pth` ou `.ckpt` merece revisão quando um script privilegiado passa esse arquivo para [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou outro carregador baseado em pickle. Verifique a regra efetiva de RunAs, se o chamador pode criar ou substituir o modelo selecionado e o fluxo real do argumento por qualquer wrapper de shell até o helper Python. A extensão `.pth` também nomeia arquivos de configuração Python site sem relação com modelos; portanto, a extensão, por si só, não comprova carregamento de modelo. Uma varredura de arquivo compactado ou análise estática de pickle não comprova que o carregamento posterior seja seguro; inspecione o comportamento de `weights_only`, que [depende da versão](https://docs.pytorch.org/docs/stable/notes/serialization.html), e qualquer allowlist. Consulte as [notas sobre pickle em ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). A enumeração passiva nunca deve carregar nem descompactar o modelo.

### Análise de expressões executada pelo sudo sobre entrada armazenada

Um script Python fixo executado como root pelo sudo ainda pode avaliar texto que um usuário com menos privilégios pode armazenar em um banco de dados de aplicativo. No TensorFlow, uma chamada a `preprocess_input_exprs_arg_string(value, safe=False)` seleciona um caminho `eval`; o [aviso do TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descreve o parser inseguro e uma correção no chamador de linha de comando. Uma chamada explícita `safe=False` de um aplicativo exige revisão separada, mesmo quando esse chamador de linha de comando está corrigido. Verifique a regra sudo efetiva, quem pode modificar a linha de entrada exata, se filtragem ou pontuação permite que essa linha chegue à chamada e o comportamento da função instalada. Uma versão do TensorFlow, uma concessão sudo ou um arquivo de modelo fixo, isoladamente, não comprovam a cadeia. Inspecione o script e o fluxo de dados passivamente; não execute o helper privilegiado nem envie expressões de teste durante a enumeração.

### Configuração do needrestart permitida pelo sudo

`needrestart -c` carrega um arquivo de configuração Perl escolhido pelo chamador e avalia seu conteúdo. Se `sudo -l` permitir executar `needrestart` como root com argumentos que permitam `-c`, e o chamador puder selecionar um arquivo de configuração legível em um local gravável, essa permissão pode levar à execução de código como root. Verifique a regra exata de RunAs e argumentos do sudo; uma regra que permita apenas uma lista fixa de argumentos pode bloquear esse caminho. Isso é separado das vulnerabilidades de varredura de interpretadores do needrestart: atualizar o pacote ou desativar `interpscan` não torna segura uma concessão irrestrita root `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python executados pelo sudo sob outra conta

Um ponto de entrada Python fixo ainda pode importar um módulo que o chamador consiga editar ou substituir, inclusive quando o sudo executa o script como um usuário de serviço **que não seja root**. Para um `from utils import status` literal, revise `utils/__init__.py` e `utils/status.py` locais, além das permissões do diretório do pacote. Confirme o caminho de importação do script, os argumentos exatos permitidos pelo sudo e se a ação relevante chega a esse import antes de considerar o arquivo gravável um caminho de execução. Inspecione arquivos e permissões sem importar nem executar o script durante a enumeração.<sup>[[2]](#references)[[3]](#references)</sup>

Uma regra sudo exata para `python3 /absolute/script.py` só precisa que o script seja legível; o arquivo não precisa ser executável nem ter shebang. Revise também os módulos locais **ausentes**: se o script importar um módulo cujo nome de arquivo possa ser criado em um diretório de script gravável pelo chamador, o Python poderá carregar esse arquivo sob a identidade RunAs. Confirme a regra sudo efetiva, o [caminho de busca de módulos](https://docs.python.org/3/library/sys_path_init.html) real do interpretador, se o módulo é integrado ou congelado e se o import é alcançado. Uma regra sudo direta para o script tem requisitos diferentes de bit de execução e shebang. Um wrapper separado que acrescenta tokens fornecidos pelo chamador após `sudo -u account` também exige revisar o fluxo de argumentos: outro `-u` nesses tokens só importa se a política sudo invocada permitir a identidade resultante. Strings estáticas, por si só, não comprovam nenhum dos caminhos.

### Apache executado pelo sudo com configuração controlada pelo chamador

Se uma regra sudo permitir uma invocação privilegiada de `apachectl`, `apache2ctl` ou `httpd` com um arquivo de configuração `-f` controlado pelo chamador, revise as permissões desse arquivo e do diretório pai. A diretiva Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) recebe um nome de módulo seguido pelo **nome do arquivo do módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) também carrega um arquivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) podem estender a configuração ou expor conteúdo de arquivos por meio de erros. Um wrapper personalizado pode validar esses caminhos, remover privilégios ou restringir argumentos; portanto, uma configuração gravável é candidata à revisão, não prova de execução de código. Verifique a canonicalização de caminhos, os symlinks e a análise das diretivas antes de chegar a uma conclusão.

### nginx executado pelo sudo com configuração controlada pelo chamador

Uma regra nginx irrestrita root-capable pode permitir que [`-c selecione outra configuração`](https://nginx.org/en/docs/switches.html). Revise os argumentos e as exclusões exatos do sudo, se o chamador pode fornecer a configuração e se o master ou os workers resultantes mantêm acesso a caminhos protegidos. Uma combinação de `root` escolhido e `autoindex` pode expor arquivos por meio de um novo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) pode oferecer um caminho privilegiado de gravação de arquivos, mas o módulo DAV não é compilado por padrão e é necessário verificar sua presença, a acessibilidade do listener, as permissões dos arquivos e o comportamento dos arquivos temporários. A diretiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) também pode apontar para um arquivo escolhido; gravar logs em um arquivo de configuração sensível, como `/etc/ld.so.preload`, exige um gravador privilegiado efetivo e um registro de log controlável antes de se tornar uma rota de escalada. O executável destacado em `sudo -l` é uma pista, não prova de que algum desses caminhos funcione. A enumeração passiva não deve iniciar nem reconfigurar o nginx.

### Comparação de padrões em prompts Bash privilegiados

Quando um script Bash permitido pelo sudo lê um valor do chamador e o verifica com `[[ "$expected" == $entered ]]`, o Bash interpreta o operando direito sem aspas como um padrão. Portanto, um curinga pode satisfazer a comparação sem que o valor esperado seja conhecido. Colocar o operando entre aspas (`[[ "$expected" == "$entered" ]]`) faz uma comparação literal de strings. Revise a regra sudo exata, se o prompt pode ser alcançado e o que o script faz após a comparação; a sintaxe, por si só, não comprova um caminho explorável. Evite exibir o valor esperado durante a enumeração. Consulte a [referência de construções condicionais do Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers executados pelo sudo que baixam e executam um arquivo

Uma concessão sudo irrestrita root-capable para um helper personalizado merece revisar o fluxo de dados se ele aceitar uma URL escolhida pelo chamador, gravar a resposta em disco e depois invocar esse arquivo com um interpretador ou shell. [O sudoers permite argumentos arbitrários quando uma entrada de comando não lista nenhum](https://man7.org/linux/man-pages/man5/sudoers.5.html); um caminho fixo de executável não restringe o que os argumentos podem selecionar. Confirme a validação real da URL, o caminho de saída, o ramo de sucesso e a execução posterior no helper instalado. Um import correspondente de libcurl ou uma string imprimível, isoladamente, não comprova essa cadeia.

Mesmo um nome base de saída fixo pode ser substituído entre a gravação e a execução quando o helper usa um **caminho relativo em um diretório de trabalho controlado pelo chamador**. Renomear ou substituir um arquivo pertencente ao root depende do acesso de escrita e busca ao diretório e de quaisquer restrições do sticky bit, não apenas do modo do arquivo; consulte [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifique se o helper reabre o caminho mais tarde ou usa o descritor já aberto, e se muda para um diretório confiável antes de gravar. Inspecione passivamente a política sudo, o helper e os metadados do diretório; não invoque o download privilegiado nem tente uma corrida durante a enumeração.

Um helper de download executado pelo sudo como root também pode expor uma injeção de **argumentos** quando monta uma string de comando Bash como `curl <entrada do chamador> -o <saída fixa>`. Um filtro que rejeite espaços em branco ainda permite a [expansão de chaves do Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementos separados por vírgula e sem aspas podem virar argumentos curl distintos. Se a entrada chegar ao curl antes do `-o` fixo, uma opção de saída fornecida pelo chamador poderá selecionar o destino para a primeira URL sob a identidade do helper; [o curl associa as opções de saída às URLs em ordem](https://curl.se/docs/manpage.html#-o). Confirme o shell exato, o quoting, a validação da entrada, a regra sudo efetiva, a ordem dos argumentos do curl e os esquemas de URL aceitos, além de verificar se o chamador controla os bytes baixados ou consegue ler o resultado. Um executável empacotado com PyInstaller pode conter lógica de aplicativo Python, mas a indicação de empacotamento ou uma string `curl`, isoladamente, não comprova esse fluxo de dados. Quando autorizado, revise uma cópia offline delimitada; a enumeração rotineira não deve executar o helper nem buscar dados escolhidos por um atacante.

Um script de shell executado como root pelo sudo que chama [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) apenas escolhe um nome não utilizado; ele **não** cria o arquivo. Se o script criar esse nome depois em um diretório que outro usuário possa afetar, reabri-lo e acrescentar seu conteúdo a um destino protegido, como `authorized_keys` do root, revise uma possível corrida de arquivo temporário. Confirme a regra sudo exata, o proprietário do diretório e do arquivo, a sequência de criação e reabertura, as proteções do kernel e se a gravação privilegiada realmente usa bytes controlados pelo atacante. Uma string `mktemp -u` ou um `/tmp` gravável, isoladamente, não comprova a corrida. Inspecione o script e os metadados do caminho sem executá-lo nem disputar o arquivo temporário durante a enumeração.

## Notas defensivas

- Evite conceder interpretadores ou editores interativos pelo sudo.<sup>[[1]](#references)</sup>
- Prefira wrappers fixos, pertencentes ao root, que executem uma única ação administrativa restrita.<sup>[[1]](#references)[[2]](#references)</sup>
- Se um interpretador for inevitável, restrinja o caminho exato do script e impeça argumentos controlados pelo usuário, imports graváveis, `PYTHONPATH` e a preservação insegura do ambiente.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se for necessário editar arquivos, restrinja o caminho exato do arquivo e considere `sudoedit` com versões corrigidas do sudo e tratamento estrito do ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Revise `SETENV`, `env_keep`, diretórios de trabalho graváveis, caminhos de módulos/imports graváveis, `NOEXEC`, `use_pty` e logging, mas não os considere um sandbox completo.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
