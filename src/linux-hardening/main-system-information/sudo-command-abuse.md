## Interpreti consentiti da sudo

Se `sudo -l` consente a un utente di eseguire un interprete come root, consideralo un caso di direct code execution. Gli interpreti sono progettati per eseguire codice arbitrario, quindi una regola che consente `python3`, `perl`, `ruby`, `lua`, `node` o binari simili equivale di solito all'esecuzione di comandi come root, a meno che gli argomenti non siano sottoposti a restrizioni e convalidati in modo rigoroso.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flusso di revisione comune: prima elenca i privilegi dell'utente, poi esegui un'istruzione Python con l'opzione `-c` dell'interprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Di seguito sono riportati altri esempi di interpreti; quelli elencati documentano l'esecuzione di codice inline o le API per la creazione di processi figlio.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Il percorso esatto è importante. Se la regola sudo consente `/usr/bin/python3`, usa quel percorso esatto durante la verifica.<sup>[[2]](#references)</sup>

Un glob per gli eseguibili sudo come `/usr/bin/python*` può consentire anche Python 2 per uno script scritto per Python 3. Se lo script raggiunge `input()` con testo controllato da chi lo invoca, [Python 2 valuta quel testo come un'espressione](https://docs.python.org/2/library/functions.html#input); l'invocazione esplicita dell'interprete prevale sullo shebang dello script. Verifica i binari corrispondenti installati, l'identità RunAs effettiva e la policy sugli argomenti, i dinieghi e la possibilità di raggiungere l'input prima di considerare questo un percorso di esecuzione.

Un percorso di script fisso in una regola sudo con privilegi root non limita ciò che lo script esegue. Per un wrapper Bash leggibile, controlla se il suo primo comando eseguibile usa un parametro posizionale non racchiuso tra virgolette, come `$1`, come **parola di comando**, mentre sudo consente ad argomenti scelti da chi lo invoca. Verifica l'identità RunAs effettiva, la policy relativa alla password e agli argomenti, i dinieghi successivi e il ramo effettivamente seguito dallo script; `NOEXEC`, un elenco fisso di argomenti sicuri o un wrapper che convalida il comando possono cambiare il risultato. Durante l'enumerazione, esamina staticamente lo script breve invece di invocarlo con un comando di test.

Anche una regola sudo senza restrizioni per `dotnet` con privilegi root merita una verifica dell'interprete. Se è installato un .NET SDK, [`dotnet fsi` esegue codice F# in modo interattivo o da uno script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/) e [`dotnet run` esegue un progetto dal codice sorgente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Prima verifica l'identità RunAs effettiva e la policy esatta sugli argomenti: una regola limitata a uno specifico sottocomando sicuro o a un'applicazione attendibile concede autorizzazioni diverse, e un'installazione che include solo il runtime potrebbe non disporre dei comandi dell'SDK. Il solo nome dell'eseguibile è un'indicazione da approfondire, non una prova di esecuzione di codice.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` consentito da sudo: scrittura arbitraria di file con privilegi elevati

GNU `tee` copia lo standard input in ogni percorso fornito come operando file. Pertanto, una regola sudo che consente di eseguire `/usr/bin/tee` come root con argomenti controllati dal chiamante concede la possibilità di creare o sovrascrivere file arbitrari come root. Aggiungendo `-a`, la possibilità diventa quella di aggiungere contenuto. Un tag `PASSWD:` riguarda l'autenticazione sudo; da solo, non limita la destinazione né i byte letti dallo standard input.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Per prima cosa, esamina la regola esatta. Su un sistema di test autorizzato, verifica questa possibilità solo usando una destinazione usa e getta che sia sicuro creare. Il `>/dev/null` finale sopprime soltanto la copia di `tee` sullo standard output.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Mettere `sudo` prima del producer non eleva i privilegi di una redirezione shell successiva, perché è la shell del chiamante ad aprire la destinazione. Il processo privilegiato deve essere quello che scrive, come nella pipeline qui sopra.<sup>[[1]](#references)[[15]](#references)</sup>

Dopo aver verificato la scrittura, scegli un sink appropriato per l'esecuzione di codice come root da [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Una catena osservata ha usato `tee` con privilegi root per creare un file temporaneo in `/etc/cron.d/`, avviare una backdoor tramite uno script controllato dall'utente ed eliminare il file cron dopo l'esecuzione. La rimozione del file cron ha impedito che diventasse un meccanismo di persistenza a lungo termine, anche se i log di sistema conservavano ancora tracce dell'attività.<sup>[[27]](#references)</sup>

## Editor consentiti da sudo

Se `sudo -l` consente a un utente di eseguire un editor interattivo come root, consideralo una superficie di command execution, non un innocuo permesso di modifica dei file. Gli editor spesso possono eseguire comandi shell, leggere file arbitrari, scrivere file arbitrari o richiamare helper esterni dall'interno dell'editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flusso di verifica comune: elenca i privilegi dell'utente, quindi avvia con sudo ogni editor o pager consentito.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Esecuzione di comandi con Nano

Quando `nano` è consentito tramite sudo, è possibile eseguire comandi dall'interfaccia dell'editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Quindi fornire un comando come `id` o `/bin/sh` al prompt dei comandi di nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se una shell interattiva non dispone di flussi di terminale utilizzabili, questa forma di redirezione reindirizza lo standard output e l'errore al descrittore 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La sequenza esatta di tasti può variare in base alla versione di nano e alle opzioni di compilazione, ma il problema di sicurezza è lo stesso: l'editor viene eseguito come root e può avviare comandi esterni.<sup>[[1]](#references)[[12]](#references)</sup>

### Altri modi comuni per uscire dagli editor

Gli editor in stile Vim consentono comunemente di eseguire comandi tramite `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Anche i pager come `less` possono esporre l'esecuzione di shell.<sup>[[14]](#references)</sup>

Una regola sudo che consente di eseguire `apport-cli` come root merita lo stesso controllo del pager. Alcune versioni di Apport potevano aprire un report di crash in `less` con una dimensione del terminale modificabile dall'attaccante; il pager poteva quindi fornire una shell root se erano soddisfatte le specifiche condizioni relative a sudo e al pager. Prima di considerare vulnerabile una versione basandosi solo sul numero, verifica la regola sudo effettiva, la configurazione del pager e la correzione del pacchetto della distribuzione. Durante l'enumerazione passiva, leggi i metadati del pacchetto e delle policy senza generare un crash né aprire il report privilegiato. [Il record CVE di Ubuntu](https://ubuntu.com/security/CVE-2023-1326) elenca le versioni dei pacchetti corrette per le diverse release, incluse le correzioni retroportate.

```text
!/bin/sh
```

## Altri rischi nelle regole di sudo e doas

Inizia con `sudo -l`, `sudo -V` e con le eventuali policy di `doas`. Esamina insieme il comando consentito, l'utente RunAs, gli argomenti, l'ambiente e le impostazioni predefinite. Il permesso di eseguire comandi come un account di servizio non root può comunque esporre i file di quell'account o offrire un percorso verso root.

Uno script Python specifico consentito da sudo può comunque eseguire un comando shell con l'identità RunAs se concatena input interattivo controllabile dall'utente in [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist della punteggiatura della shell non basta a dimostrare che sia sicuro: [la shell riconosce anche la sostituzione di comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Verifica che gli argomenti consentiti raggiungano il ramo che acquisisce l'input, che l'input arrivi al comando shell senza una convalida sicura e che la policy sudo effettiva consenta l'utente RunAs previsto. Il percorso dello script o una chiamata a `os.system()` sono solo spunti per la revisione; esamina il sorgente senza eseguire lo script privilegiato.

Una concessione sudo effettiva per eseguire `chattr` come root può rimuovere l'attributo immutabile (`i`) di un file, ma questo da solo non concede il permesso di scrittura né una nuova identità. [Il manuale di `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) specifica che l'attributo impedisce le modifiche e che solo root o un processo con `CAP_LINUX_IMMUTABLE` può cambiarlo. Controlla la policy esatta sugli argomenti sudo e il supporto del filesystem, poi verifica separatamente che l'utente possa scrivere il file dopo aver rimosso l'attributo e che un componente con identità superiore lo utilizzi. Per esempio, sostituire una shell di login richiede anche credenziali accettate dall'account di destinazione e un login effettivo tramite quella shell. Durante l'enumerazione, esamina policy, attributi dei file e permessi senza modificarli.

Se sudo richiede sia una password sia un codice monouso, considera questi prerequisiti separatamente dalla concessione del comando. Un file `.google_authenticator` leggibile contiene materiale seed sensibile, mentre un hash obsoleto della password di un'applicazione o di un database è solo una possibile password per l'account corrente; nessuno dei due dimostra che l'altro fattore sia accettato dalla configurazione PAM effettiva. Una volta autorizzato, esamina RunAs e argomenti esatti: una concessione root senza restrizioni per RubyGems `gem` può esporre il relativo comando editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ma una concessione limitata o un'autenticazione non riuscita non lo fa. L'enumerazione passiva dovrebbe riportare percorsi e policy senza stampare il seed, recuperare una password, generare un codice o invocare il comando privilegiato.

Una concessione sudo senza restrizioni, eseguibile come root, per `knife` di Chef merita una revisione a livello di interprete: [Chef documenta che `knife exec -E` valuta localmente una stringa Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica che la regola sudo effettiva consenta il sottocomando `exec` e l'argomento `-E` fornito dall'utente, l'identità RunAs prevista e gli eventuali divieti di comando o argomenti fissi corrispondenti. Il binario installato o una regola limitata ad altri sottocomandi sono solo indizi. L'enumerazione passiva dovrebbe riportare la regola senza invocare `knife`.

Una concessione sudo esatta per `msfconsole`, eseguibile come root, è altrettanto sensibile: [GTFOBins documenta la sua console `irb`](https://gtfobins.org/gtfobins/msfconsole/), che può ereditare l'identità sudo. Verifica l'utente RunAs effettivo, l'elenco degli argomenti consentiti, i divieti di comando, `NOEXEC` o altre restrizioni, il comportamento della console installata e la possibilità per l'utente di fornire input interattivo. La sola evidenziazione del percorso è uno spunto per la revisione; l'enumerazione passiva non dovrebbe avviare la console.

Su FreeBSD, anche una regola sudo limitata a `pkg update` e `pkg install *` come root merita una revisione dell'affidabilità dei repository. Controlla se l'utente può scrivere `/etc/hosts` e se la configurazione *effettiva* dei repository abilitati usa un hostname HTTP con `signature_type: none`. [Il manuale di `pkg.conf` di FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) specifica che `none` disabilita i controlli delle firme; il solo `pkg+http` non è sufficiente a dimostrarlo. Un pacchetto può contenere script di installazione ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), quindi un utente che controlla davvero l'endpoint del repository e può selezionare un pacchetto potrebbe oltrepassare il confine di root. Prima di giungere a tale conclusione, verifica gli override dei repository, la risoluzione SRV/mirror, gli argomenti sudo effettivi, la selezione del pacchetto e l'esecuzione degli script. Durante l'enumerazione, esamina la policy e i piccoli file di configurazione locali senza reindirizzare i nomi né eseguire `pkg`.

Una regola sudo eseguibile come root per `apt-get update` e `apt-get upgrade` richiede anch'essa una revisione dell'affidabilità dei repository se sudo preserva un `http_proxy` controllabile dall'utente. Controlla se la configurazione APT effettiva usa davvero quella variabile e quali richieste ai repository abilitati può influenzare; un proxy da solo non può sostituire pacchetti provenienti da un archivio autenticato con una chiave di firma attendibile. [Il manuale del trasporto HTTP di APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedenza dei proxy, mentre [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta i controlli delle firme, gli override per i repository non sicuri e la conferma richiesta per i pacchetti non autenticati. Verifica RunAs e argomenti sudo esatti, la policy di autenticazione dei repository, l'eventuale conferma interattiva necessaria e se l'aggiornamento selezionato esegue script di pacchetto come root. Esamina passivamente policy e configurazione locale; durante l'enumerazione non reindirizzare il traffico dei pacchetti né eseguire un aggiornamento.

Una regola sudo eseguibile come root per `snap install` può creare un confine tra pacchetto e codice se gli argomenti consentono all'utente di selezionare uno snap locale e una modalità d'installazione permissiva. [Snap documenta](https://snapcraft.io/docs/explanation/snap-development/install-modes/) che `--dangerous` salta i controlli delle asserzioni sugli snap locali e che `--devmode` allenta il confinamento; [un hook di installazione può essere eseguito durante l'installazione iniziale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prima di affermare che consenta l'accesso a file protetti dell'host, verifica la policy sudo esatta su argomenti/RunAs, chi controlla il file snap, se le modalità sono accettate dalla versione installata di snapd e l'identità effettiva e il confinamento dell'hook. La presenza del binario `snap` o una regola apparentemente con wildcard non dimostrano da sole questa catena. L'enumerazione passiva non dovrebbe installare pacchetti né eseguire i relativi hook.

Per una concessione sudo esatta al binario personalizzato di un account **non root** che legge credenziali, esamina anzitutto il binario autorizzato e i permessi dei file senza eseguirlo. Una password incorporata può essere visibile solo come caratteri wide; [GNU `strings` documenta l'estrazione little-endian a 16 bit](https://sourceware.org/binutils/docs/binutils/strings.html). Una stringa visibile non dimostra che sia la password accettata né che il ramo di successo esponga una credenziale corrente. Verifica separatamente il comportamento del binario, l'accesso dell'account di destinazione ai dati protetti, la validità delle credenziali e ogni successivo passaggio a un altro account o gruppo. Se l'account appartiene a `docker`, verifica l'accesso al socket e se il daemon opera come root o rootless prima di dedurre l'accesso a root dell'host; [Docker documenta le implicazioni del suo gruppo a livello root](https://docs.docker.com/engine/install/linux-postinstall/). L'enumerazione ordinaria dovrebbe riportare la regola sudo e l'appartenenza ai gruppi senza eseguire il binario né scaricarne le stringhe.

Una regola sudo con wildcard per gli script di manutenzione di un'applicazione va esaminata oltre il semplice percorso dello script. Controlla se lo script consentito accetta argomenti senza restrizioni o legge impostazioni scrivibili da un account dell'applicazione con privilegi inferiori, poi segui quei valori fino ai comandi shell o all'ambiente di un sottoprocesso. Per esempio, [`zmupdate.pl` di ZoneMinder assembla un comando `mysqldump` e lo esegue tramite `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mentre [`zmdc.pl` copia l'impostazione `ZM_LD_PRELOAD` in `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) prima di avviare i daemon. Una regola sudo che consenta di eseguire uno dei due script come root può oltrepassare un confine di fiducia se l'input corrispondente è controllabile e raggiunge quel codice nella versione installata. Esamina la regola sudo effettiva, i permessi sulla configurazione dell'applicazione e il sorgente dello script: la wildcard o l'impostazione, da sole, sono solo spunti per la revisione, non prove di esecuzione.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` possono trasformare un comando altrimenti limitato in un dirottamento di import, librerie o `PATH`. Consulta la [guida alle variabili d'ambiente](../linux-basics/linux-environment-variables.md) e [l'abuso di SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Una concessione `SETENV` esatta per sudo, eseguibile come root, a un wrapper shell merita anche una revisione limitata al passaggio diretto se il wrapper avvia uno script Python specifico con un import letterale. `secure_path` limita la ricerca dei comandi della shell, non la ricerca dei moduli Python tramite [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fanno sì che Python ignori quella variabile d'ambiente. Prima di considerarlo esecuzione di codice, verifica i tag e i divieti sudo effettivi, il ramo del wrapper, le opzioni dell'interprete, la risoluzione dell'import e la presenza di una directory di ricerca scrivibile dall'utente. Esamina staticamente gli script brevi; non invocare il wrapper privilegiato.

Una concessione sudo esatta per `neofetch ""`, eseguibile come root, può comunque caricare una configurazione shell se le impostazioni predefinite sudo applicabili preservano un `XDG_CONFIG_HOME` controllabile dall'utente. [Il loader di configurazione di Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carica `neofetch/config.conf` o `neofetch/config` da quella directory; l'elenco di argomenti vuoto non impedisce questa ricerca. Verifica il loader installato, RunAs e la policy effettivi sugli argomenti, gli eventuali divieti di comando, se sudo conserva davvero la variabile selezionata per questo comando e se l'utente controlla un percorso di configurazione leggibile. Una variabile preservata o la presenza di Neofetch sono solo spunti per la revisione. Esamina policy e metadati dei file senza invocare il comando privilegiato né stampare il contenuto della configurazione; consulta [la gestione dell'ambiente di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regola sudo senza restrizioni per `facter`, eseguibile come root, merita una revisione separata dei custom fact. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) che `--custom-dir` carica file Ruby contenenti fact da una directory selezionata. Controlla se la regola sudo esatta consente tale opzione, se Facter installato la accetta e se l'utente controlla la directory. Una concessione con argomenti fissi, un divieto di comando esplicito o i custom fact disabilitati possono cambiare l'esito. L'enumerazione passiva dovrebbe riportare la regola candidata senza invocare Facter né leggere il contenuto dei fact.

Per una concessione sudo esatta a uno script eseguibile come root con `SETENV`, esamina i nomi di comando non qualificati come `find` e il `PATH` effettivo dopo l'applicazione della policy sudo e l'inizializzazione dello script. Un file Bash importato può anche eseguire `enable -n [`: [a quel punto Bash cerca in `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un eseguibile esterno `[` quando lo script userà in seguito quel comando. Verifica le regole applicabili di [sudoers sull'ambiente e `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), le eventuali voci `NOSETENV`/`NOEXEC` o di diniego, il flusso dello script e dei file importati e la presenza di una directory di ricerca eseguibile controllabile dall'utente. Uno script leggibile contenente un comando non qualificato è uno spunto per la revisione, non una prova di esecuzione privilegiata; esaminalo senza invocare la regola sudo.

- Uno script privilegiato che scarica un URL fisso con `curl` può comunque accettare una risposta scelta dall'utente se una regola sudo applicabile preserva `http_proxy` e la richiesta passa attraverso quel proxy. Se poi lo script passa la risposta a un parser XML che risolve entità esterne, una risposta ostile può rivelare file leggibili dal processo privilegiato. Controlla la policy sudo esatta sull'ambiente, le esclusioni `no_proxy`, l'URL richiesto, la configurazione del parser e la destinazione dell'output; una variabile proxy o un parser XML, da soli, non sono una vulnerabilità. La [documentazione di curl sulle variabili d'ambiente dei proxy](https://everything.curl.dev/usingcurl/proxies/env.html) descrive il comportamento di queste variabili. Durante l'enumerazione passiva non effettuare richieste di rete né analizzare XML ostile.
- Uno script sudo eseguibile come root che crea un file PostScript usando dati influenzati dall'utente e poi esegue `ps2pdf -dNOSAFER` merita una revisione separata del flusso degli input. Ghostscript documenta che questo flag disabilita SAFER fino a `.setsafe`, consentendo operazioni sui file nei limiti dei permessi del processo sul sistema operativo. Una query SQL assemblata da un argomento dell'utente può fornire righe controllate dall'attaccante al template PostScript, ma una stringa di query o la chiamata a `ps2pdf`, da sole, non dimostrano che i dati raggiungano sintassi PostScript eseguibile. Verifica la regola sudo effettiva, il percorso esatto dall'input al template, eventuali escape, il comportamento della versione installata di Ghostscript e se SAFER viene riattivato prima di interpretare il documento. Durante l'enumerazione passiva non eseguire la conversione privilegiata. Consulta la [documentazione di Ghostscript su `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Per una regola sudo che esegue uno script shell, confronta le variabili preservate con il contenuto dello script. Un costrutto come `if $CHECK_CONTENT; then` esegue il valore espanso come comando, quindi preservare `CHECK_CONTENT` può consentire l'esecuzione di comandi anche se percorso e argomenti dello script sono fissi. Per la regola specifica, verifica se il ramo è raggiungibile e se l'ambiente viene davvero conservato.<sup>[[2]](#references)[[22]](#references)</sup>
- Uno script Python consentito da sudo può importare codice da una directory scrivibile o da un file `.pyc` memorizzato nella cache. La [guida alla privilege escalation](../linux-basics/linux-privilege-escalation/README.md) descrive il caso della cache.
- Uno script Python specifico consentito da sudo ed eseguibile come root può comunque esporre un debugger interattivo. Chiamate come `pdb.set_trace()` o `pdb.post_mortem()` consentono di eseguire istruzioni Python nel contesto del processo sottoposto a debug quando l'utente può raggiungere il breakpoint o il gestore di eccezioni **e controllare lo stream di input del debugger**. Controlla la regola sudo esatta su RunAs, le condizioni di autenticazione e del ramo, la raggiungibilità dell'eccezione, la proprietà del terminale/input e se il debugger viene eseguito nello stesso processo privilegiato. Una richiesta socket che provoca un'eccezione non concede da sola l'accesso a un debugger collegato a un altro terminale. [Python documenta la valutazione delle istruzioni nel debugger e la modalità post-mortem](https://docs.python.org/3/library/pdb.html); esamina staticamente lo script anziché attivare il gestore privilegiato durante l'enumerazione.
- Uno script Python specifico consentito da sudo può anche leggere un campo di profilo da un database o da un socket Unix e aggiungerlo a una stringa che diventa in seguito la **stringa di formato** di `str.format()`. [I campi di sostituzione possono accedere ad attributi e chiavi di mapping](https://docs.python.org/3/library/string.html#format-string-syntax), quindi un campo controllato dall'attaccante può ispezionare gli oggetti passati a `format()` ed esporre dati a cui questi danno accesso, se il risultato viene stampato o salvato in un luogo leggibile dall'utente. Controlla l'identità RunAs effettiva, l'accesso in scrittura al record specifico, il flusso dei dati fino alla stringa di formato, gli oggetti forniti e la visibilità dell'output. Questo non comporta automaticamente l'esecuzione di codice; una stringa di formato letterale attendibile con *valori* controllati dall'utente è un caso diverso. Un segreto divulgato consente il passaggio a un account del sistema operativo solo se quell'account lo accetta. Esamina lo script e i permessi del socket senza invocare l'operazione privilegiata.
- Un wrapper Python eseguibile come root può passare a `Repo.clone_from` di GitPython un URL scelto dall'utente. Se il wrapper abilita anche `protocol.ext.allow=always` di Git, un remote `ext::` può invocare un helper esterno. Controlla gli argomenti sudo esatti, la provenienza dell'URL, la versione del pacchetto GitPython e l'eventuale presenza di patch del vendor, nonché l'eventuale opt-in esplicito del wrapper ai protocolli non sicuri. GitPython ha aggiunto una [protezione predefinita per i protocolli non sicuri](https://github.com/gitpython-developers/GitPython/commit/2625ed9) nella versione 3.1.30; la versione dell'eseguibile `git` è un dato distinto. La revisione passiva dovrebbe limitarsi a leggere la regola e una porzione contenuta del sorgente, senza avviare la clonazione.
- Una concessione sudo tra utenti per un'interfaccia CLI di clonazione di repository può esporre un percorso distinto di injection di stringhe shell. Verifica se l'argomento repository scelto dall'utente raggiunge Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) o un altro costruttore di comandi shell senza una separazione sicura degli argomenti; Node `exec` passa la stringa di comando a una shell. Verifica l'utente RunAs esatto, i sottocomandi e gli argomenti consentiti, il codice del wrapper installato e la convalida degli input. Il nome di uno strumento per repository o una regola sudo senza restrizioni non dimostrano, da soli, l'iniezione di comandi. Esamina il wrapper senza eseguire una clonazione privilegiata durante l'enumerazione.
- Un wrapper personalizzato di proprietà di root può sembrare sicuro perché binari e script non sono scrivibili, ma la decisione di eseguire un'azione privilegiata potrebbe dipendere da un flag, da un valore API locale o dallo stato di un servizio che un utente non privilegiato può modificare. Segui ogni condizione fino al relativo input e ai controlli di autorizzazione. Durante l'enumerazione, esamina configurazione e permessi senza modificare lo stato operativo; una chiamata a `systemd-run` nel wrapper è rilevante solo se la condizione può essere influenzata.
- Un client di backup consentito tramite sudo come root può accettare un file di configurazione scelto dall'utente, per esempio tramite `npbackup-cli -c`. Verifica l'utente RunAs esatto e gli argomenti consentiti, poi controlla se l'utente controlla il percorso di configurazione, i percorsi sorgente del backup e il repository o le opzioni di lettura/ripristino. Un segreto per un repository cifrato in una configurazione leggibile può comunque essere utilizzabile dal client, ma la sola regola non dimostra l'accesso al repository o la divulgazione di file root. Verifica l'autorizzazione senza eseguire un backup né scaricarne il contenuto.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) supporta `--password-command`, che esegue un programma per ottenere la password del repository. Se una regola sudo consente a un utente con privilegi inferiori di eseguire restic come root con un comando password scelto dall'utente e un sottocomando che richiede la password, l'helper può essere eseguito come root. Esamina argomenti sudo esatti ed esclusioni; non invocare l'helper né un comando di backup solo per verificare la condizione durante l'enumerazione.
- Una concessione privilegiata per `restic backup` può oltrepassare anche un confine di lettura dei file se il modello degli argomenti sudo consente all'utente di scegliere sia la sorgente sia un repository che in seguito potrà leggere e decifrare. [Le wildcard negli argomenti sudoers possono corrispondere a spazi e slash](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), quindi esamina le wildcard finali invece di presumere che un prefisso fisso del repository limiti la sorgente. [Restic può eseguire backup su repository locali e remoti](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), ma un repository locale può contenere nuovi oggetti scritti solo da root; prima di considerarlo una divulgazione, verifica la policy sudo effettiva, l'accesso al backend, la password del repository e i permessi degli oggetti risultanti. Una chiave SSH salvata concede accesso solo se l'account di destinazione la accetta. Durante la revisione passiva non eseguire un backup per verificarlo.
- Un comando personalizzato di manutenzione o backup senza restrizioni può accettare un percorso di output o disporre di un proprio scheduler di job. Per un percorso di scrittura su file, verifica la regola sudo esatta e l'utente RunAs, poi controlla se l'utente controlla sia i dati sia la destinazione. Per un percorso basato su comandi pianificati, verifica l'identità con cui li esegue lo scheduler, l'input del comando e gli eventuali ulteriori controlli di password o autorizzazione. Il nome del comando o `NOPASSWD`, da soli, non dimostrano nessuno dei due percorsi. Consulta [la scrittura di file di proprietà di root](../interesting-files-permissions/write-to-root.md) e [cron e i timer systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando sudo fisso può comunque caricare un file di configurazione prevedibile da una directory condivisa e scrivibile. Verifica se l'utente può sostituire quel file e se i campi di origine e destinazione controllano un fetch o una copia privilegiati. Un URL a un file locale può esporre dati leggibili solo dall'account RunAs di sudo; una sorgente controllata dall'utente associata a una destinazione protetta può creare un percorso di scrittura. Verifica la gestione degli URL da parte del programma installato, i controlli sul percorso di destinazione, la regola sudo effettiva e l'accessibilità dell'output. Un percorso di configurazione scrivibile in `/tmp`, da solo, è solo uno spunto per la revisione; esamina il binario e i metadati dei file senza invocare il trasferimento privilegiato.
- Una regola sudo per `git apply` può consentire all'utente RunAs di scrivere file selezionati da una patch controllata dall'utente. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) consentiva a una patch appositamente creata di generare un symlink e poi scrivere al di fuori dell'albero di lavoro, anche se il comando non accettava `--unsafe-paths`. Controlla la regola sudo effettiva sugli argomenti, la provenienza della patch, l'accesso dell'utente RunAs alla directory di lavoro e la correzione Git installata o il backport del vendor. Una regola senza restrizioni che ammette `--unsafe-paths` comporta un rischio distinto dovuto all'opzione esplicita; né una versione di Git né il permesso di eseguire `git apply`, da soli, dimostrano che un file protetto possa essere modificato. Durante l'enumerazione passiva non applicare patch non attendibili.
- Una regola sudo eseguibile come root per `clamscan --debug` può oltrepassare un confine di lettura se un utente con privilegi inferiori può fornire un'immagine DMG e il parser installato è affetto da [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), che poteva divulgare contenuti di file tramite l'output di debug. Verifica gli argomenti consentiti esatti e il percorso di scansione, il controllo dell'input, l'account RunAs effettivo, la correzione/backport del motore e la visibilità dell'output per l'utente. Se una regola più ampia consente `--file-list`/`-f`, esamina separatamente il comportamento dell'elenco; una policy fissa a `--debug <scan-path>` non lo ammette. Durante l'enumerazione, esamina policy e metadati dei pacchetti senza scansionare file creati appositamente né stampare output protetto.
- Una regola sudo eseguibile come root che apre un'immagine disco cifrata scelta dall'utente e una seconda regola che monta il mapper risultante possono importare file controllati dall'utente nel namespace di mount dell'host. Verifica entrambe le regole effettive e i rispettivi argomenti, il controllo dell'immagine e del nome mapper, la destinazione effettiva del mount e il proprietario e i permessi dei file risultanti. Un passaggio a un programma SetUID richiede inoltre un eseguibile accessibile, opzioni di mount che lo consentano (`nosuid` lo impedisce) e policy di processo o MAC applicabili; aprire o montare un'immagine, da solo, è soltanto uno spunto per la revisione. Un percorso separato tramite un backup esistente richiede la chiave effettiva e un segreto utile e leggibile al suo interno. Durante la revisione passiva, esamina policy e percorsi senza aprire né montare immagini. Consulta il [manuale di cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e le [opzioni di mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regola sudo eseguibile come root per uno script shell o Python merita una revisione della directory di lavoro se lo script invoca `./helper` senza prima spostarsi in una directory fissa. Anche una lista Python come `['./helper']` passata a `subprocess.run` può dipendere dalla directory di lavoro scelta dall'utente. L'utente potrebbe scegliere una directory scrivibile e inserirvi un eseguibile con quel nome relativo; un percorso assoluto in un'altra parte dello script non protegge questa chiamata. Prima di considerarlo esecuzione di codice, verifica la regola effettiva, `runchdir` o altre policy che cambiano directory, il flusso dello script e la raggiungibilità del ramo, la presenza di una directory scrivibile ed eseguibile e le restrizioni di mount/`NOEXEC`. Se lo script non è leggibile, il comportamento resta sconosciuto finché il sorgente non viene esaminato tramite un percorso autorizzato. Esamina gli script staticamente invece di eseguire l'helper. Il [manuale sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta le policy sulla directory di lavoro.
- Un validator Python fisso ed eseguibile come root può comunque valutare un file di dati scelto dall'utente. [La documentazione di `eval()` di Python mette in guardia dagli input non attendibili](https://docs.python.org/3/library/functions.html#eval): un controllo del suffisso dell'input, un prefisso aritmetico o un ramo di convalida non costituiscono una sandbox se l'espressione restante raggiunge `eval`. Prima di definirlo un percorso di esecuzione, verifica la regola sudo effettiva, se l'utente può scegliere e controllare il file esatto, le condizioni del ramo del parser e la costruzione dell'espressione, nonché l'identità del processo privilegiato. La sola presenza di `eval` in uno script leggibile è uno spunto per la revisione; durante l'enumerazione esamina sorgente e permessi dei file senza eseguire il validator né inviargli un'espressione di prova.
- Un wrapper Ruby sudo eseguibile come root che legge un file YAML tramite un percorso relativo, come `YAML.load(File.read("dependencies.yml"))`, può leggere dalla directory di lavoro dell'utente se il wrapper o la policy sudo non la fissano. Controlla gli argomenti consentiti esatti, i permessi della directory e del file e il comportamento della versione di Psych installata: le vecchie implementazioni di `YAML.load` potevano deserializzare oggetti Ruby arbitrari, mentre le versioni più recenti limitano le classi per impostazione predefinita. Una chiamata statica è solo uno spunto per la revisione; verifica che il file provenga davvero da una directory scrivibile dall'utente e che il loader installato accetti classi pericolose. Per input non attendibili, preferisci `safe_load` con una allowlist minima ed esplicita di classi. Consulta la [documentazione di Ruby 3.0 per Psych](https://docs.ruby-lang.org/en/3.0/Psych.html) e la [documentazione di Ruby 3.1 per Psych](https://ruby-doc.org/core-3.1.2/Psych.html).

- Una concessione sudo esatta per `sudo go run /absolute/file.go`, eseguibile come root, merita una revisione della directory di lavoro se il sorgente Go legge un file WASM relativo e potrebbe eseguire uno script shell relativo dopo averne esaminato il risultato. Verifica RunAs effettivo, argomenti e divieti del comando, la presenza di una directory corrente scrivibile dall'utente, il flusso dei dati dal WASM al ramo e se quel ramo invoca l'helper. Un `runchdir` sudo fisso, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) possono cambiare la directory di ricerca. La sola co-occorrenza statica è un caso candidato; esamina il sorgente senza eseguire Go, WASM o l'helper.
- `sudoedit` e le wildcard negli argomenti richiedono controlli precisi su versione e regola; la [checklist](linux-privilege-escalation-checklist.md) include il problema di modifica file di sudoedit. Per una concessione `sudoedit` tra utenti su un percorso con wildcard, esamina l'impostazione effettiva `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, il target risolto e chi può sostituire ciascuna voce delle directory genitrici. La prima può consentire di seguire un symlink, mentre disabilitare la seconda rimuove i controlli sulle directory scrivibili; nessuna delle due, da sola, dimostra la possibilità di scrivere nel file di un altro utente. Prima di giungere a tale conclusione, verifica la policy sudo installata e gli argomenti esatti che corrispondono alla regola. Consulta le [definizioni delle opzioni sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In una regola di comando sudoers, una wildcard negli argomenti può corrispondere sia agli spazi sia ai caratteri dei percorsi. Una regola per un comando capace di leggere con un argomento come `/restricted/*` può quindi ammettere un ulteriore argomento file dopo un prefisso corrispondente. Esamina l'utente RunAs esatto, il percorso del comando, il modello degli argomenti e gli eventuali divieti successivi; dimostrare la lettura di un file non implica l'esecuzione di comandi. Il [manuale sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue le glob degli argomenti da quelle del percorso del comando.
- Anche una glob di argomenti che sembra limitata a un percorso può corrispondere a `../`. Per esempio, una regola root per `node /opt/scripts/*.js` può consentire all'utente di specificare un file JavaScript al di fuori di `/opt/scripts` se il percorso fornito inizia comunque con `/opt/scripts/` e si risolve attraverso segmenti di directory parent. Questa è una glob negli **argomenti**; le regole che determinano la corrispondenza degli slash nella glob del percorso dell'eseguibile Node sono diverse. Prima di concludere che consenta l'esecuzione di codice, verifica la regola effettiva, gli eventuali divieti successivi, la risoluzione del percorso, il controllo del file di destinazione e le restrizioni sudoers basate su espressioni regolari o digest. Consulta le [regole delle wildcard sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e la [documentazione della riga di comando di Node](https://nodejs.org/api/cli.html).
- Archiviatori e altri programmi di utilità possono avere hook di esecuzione. Verifica gli argomenti esatti consentiti con [GTFOBins](https://gtfobins.github.io/) invece di presumere che solo le shell o gli interpreti possano eseguire comandi.
- Una regola `qpdf` senza restrizioni, eseguibile come root, può esporre un file privilegiato tramite allegati PDF: qpdf 10.2 e versioni successive supportano `--empty` e `--add-attachment file ... --` con un PDF di output. Se il processo privilegiato può leggere la sorgente selezionata e scrivere il PDF in un percorso accessibile all'utente, l'output può contenere i byte della sorgente. Prima di concludere che sia possibile divulgare il file, esamina gli argomenti sudo effettivi e le esclusioni, la versione di qpdf, l'accesso alla sorgente e il percorso di output. Leggere una chiave SSH di root è utile per il login solo se la chiave è valida e l'autenticazione SSH di root è consentita. Consulta le [opzioni qpdf per gli allegati](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Il riutilizzo dei timestamp sudo dipende dalla policy della cache, dall'utente proprietario, dal terminale/sessione e dai permessi. La [guida alla privilege escalation](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) illustra i controlli.
- `doas` ha regole e configurazione proprie. Controlla i comandi consentiti e i percorsi di configurazione scrivibili come descritto nella [sezione doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Strumenti di build e pacchetti eseguiti tramite sudo

Una concessione sudo senza restrizioni per `forge` di Foundry può essere rilevante anche quando l'identità RunAs è un altro utente non root. Opzioni del compilatore come `--use` possono selezionare un eseguibile locale, mentre `forge flatten -o` seleziona un file di output. Prima di considerare sfruttabile la concessione, controlla la versione di Forge installata, gli argomenti sudo esatti, i percorsi accessibili del progetto e del compilatore, i permessi dell'output e l'ambiente effettivo. Un eseguibile helper relativo individuato tramite `PATH` è un percorso che dipende dalla versione e dall'ambiente, non una caratteristica da presumere in ogni build Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Una concessione `pacman` senza restrizioni, eseguibile come root, consente più delle sole interrogazioni sui pacchetti: `-U` accetta un pacchetto locale, i pacchetti possono contenere script d'installazione e `--hookdir` seleziona un'altra directory di hook. Prima di effettuare verifiche, esamina la regola sudo effettiva, le restrizioni sugli argomenti e le esclusioni; l'enumerazione passiva non richiede di installare un pacchetto né di eseguire un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fisso eseguito tramite sudo può anche installare una dipendenza npm specifica e poi avviare un'applicazione Node. Esamina la regola RunAs esatta, se il pacchetto è già installato, `HOME` e `userconfig` npm effettivi, la configurazione del progetto o gli override da riga di comando e se un utente con privilegi inferiori controlla il registry o il pacchetto restituito per quel nome. [npm documenta la ricerca di `.npmrc` per utente e progetto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); il comportamento di `HOME` con sudo dipende dalla policy e dalla distribuzione installate, quindi il processo npm privilegiato potrebbe leggere o meno il file `.npmrc` di un utente scrivibile. Se il pacchetto appena installato viene importato dall'applicazione privilegiata, il suo codice può essere eseguito con l'identità dell'applicazione. Gli script d'installazione costituiscono un percorso separato, dipendente dalla versione e dalla configurazione; [npm ne documenta il ciclo di vita e la gestione degli utenti](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un percorso `.npmrc` o una riga `npm install`, da soli, sono solo spunti per la revisione. Durante l'enumerazione passiva, esamina la regola, il wrapper breve, i percorsi di configurazione e la provenienza del pacchetto senza installarlo né avviare l'applicazione.

Una concessione root per `pip` o `pip3 download` è anche un indizio da esaminare come build di pacchetti se gli argomenti consentono all'utente di selezionare una distribuzione sorgente non attendibile, anche quando il modello dell'URL la limita a un servizio locale e a un suffisso `.tar.gz`. `pip download` accetta URL di archivi e risolve i metadati dei pacchetti; preparare una sdist può invocare il backend di build o il codice legacy `setup.py` prima che l'archivio venga semplicemente salvato. Verifica RunAs e la regola sugli argomenti sudo esatti, se l'utente può pubblicare o sostituire l'archivio selezionato e se quella versione di pip prepara effettivamente i metadati. Un archivio fisso e attendibile o un wheel non dimostrano questo percorso. Durante l'enumerazione passiva non scaricare né compilare pacchetti non attendibili. Consulta il [comando download di pip](https://pip.pypa.io/en/stable/cli/pip_download/), l'[interfaccia del sistema di build](https://pip.pypa.io/en/stable/reference/build-system/) e le [indicazioni per installazioni sicure](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regola sudo che consente `pip install` con un percorso a un progetto locale scelto dall'utente costituisce un confine di build più diretto. [pip accetta directory di progetti locali](https://pip.pypa.io/en/stable/topics/local-project-installs/) e ne invoca il sistema di build; il [backend di build esegue hook del progetto controllati dall'utente](https://pip.pypa.io/en/stable/reference/build-system/). Prima di considerare la regola un'esecuzione di codice privilegiata, verifica l'identità RunAs effettiva, le restrizioni esatte sugli argomenti e i divieti, il controllo del progetto selezionato e il comportamento di pip/backend installati. Un progetto fisso e attendibile o una regola che esclude i percorsi scelti dall'utente non dimostrano questo percorso. Durante l'enumerazione passiva, esamina la regola e i metadati del progetto senza installare pacchetti.

Una concessione `easy_install` senza restrizioni, eseguibile come root, è un indizio analogo relativo alle build di pacchetti legacy. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) che Easy Install accetta una directory di progetto locale e compila distribuzioni sorgente; un progetto controllato dall'utente può eseguire il proprio `setup.py` durante la build con l'identità sudo. Verifica l'account RunAs effettivo, il comando esatto e le restrizioni sugli argomenti (compresi eventuali divieti successivi), il controllo del progetto selezionato e il comportamento dello strumento installato. Un progetto fisso e attendibile o una policy che non consente di selezionare una sorgente dall'utente non dimostrano questo percorso. Durante l'enumerazione, esamina la regola e i metadati del progetto senza installare pacchetti.

Un wrapper Python consentito da sudo che usa `setuptools.package_index.PackageIndex.download` con un URL scelto dall'utente è un caso di revisione diverso da `pip download`: [GHSA-5rjg-fvgr-3xxf di setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descrive come, nelle versioni vulnerabili precedenti alla 78.1.1, un nome file derivato dall'URL potesse uscire dalla directory di download prevista e scrivere con i permessi del processo. Verifica RunAs e la regola sugli argomenti sudo effettivi, che il wrapper passi l'URL dell'utente proprio a questa API, la build installata o un backport del vendor e dove si risolva il percorso risultante. Una stringa di versione o una directory di download scrivibile, da sole, non dimostrano la possibilità di scrivere in percorsi arbitrari. Durante l'enumerazione, esamina il wrapper breve e i metadati del pacchetto senza scaricare l'URL né scrivere file.

Un wrapper di build consentito da sudo che passa a PyInstaller un file `.spec` scelto dall'utente richiede una revisione analoga del confine di fiducia. Un file spec PyInstaller è codice Python eseguibile valutato **durante la build**, e le sue voci `datas` possono includere in un artefatto file leggibili dall'identità di build. Verifica l'utente RunAs esatto, la regola sudo sugli argomenti e i relativi divieti, la gestione di percorsi e rami nel wrapper, il controllo del file spec selezionato e l'accesso all'artefatto risultante. Consentire semplicemente un input `.py` o trovare PyInstaller installato non dimostra il controllo del file spec né l'esecuzione privilegiata. La revisione passiva dovrebbe leggere solo un file wrapper di dimensioni contenute e i relativi metadati; non dovrebbe eseguire build. Consulta la [documentazione dei file spec di PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loader di preset e plugin eseguiti tramite sudo

Gli strumenti Python che accettano un preset scelto dall'utente o una directory di plugin possono importare codice con i privilegi concessi da sudo. Per esempio, BBOT accetta un preset con `-p` e la sua [documentazione sui moduli personalizzati](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descrive le voci `module_dirs` che selezionano ulteriori directory di moduli Python. Se la regola sudo effettiva consente un preset scelto dall'utente e questi controlla un modulo nella directory selezionata, l'import può eseguire codice come utente privilegiato, potenzialmente prima che lo strumento rifiuti un modulo non valido. Controlla la versione installata, la policy sudo esatta su RunAs e argomenti e la proprietà delle directory del preset e del modulo, senza caricare il modulo durante l'enumerazione.

### Strumento a riga di comando Backdrop eseguito tramite sudo

[Bee](https://github.com/backdrop-contrib/bee) è uno strumento PHP a riga di comando per Backdrop CMS. I comandi `eval` (`php-eval`) e `php-script` possono eseguire PHP fornito dall'utente. Una regola sudo che consente di eseguire Bee come root con argomenti senza restrizioni può quindi esporre l'esecuzione di codice come root quando Bee riesce ad avviare un'installazione Backdrop. Eseguilo dalla directory del sito oppure seleziona un sito con l'opzione globale `--root=<directory>`; trovare Bee o un file Backdrop `settings.php` non dimostra di per sé il permesso sudo, la presenza di un sito utilizzabile o il corretto bootstrap. Prima di effettuare verifiche, esamina la regola sudo effettiva, le eventuali esclusioni di comando, l'identità dell'eseguibile e l'accesso al sito. Durante l'enumerazione passiva, esamina la regola e i percorsi dei file senza invocare Bee. Consulta il [changelog dei comandi di Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) per l'aggiunta dei comandi PHP.

### Server terminali eseguiti tramite sudo

`mosh-server` avvia un server terminale interattivo come utente invocante. Sceglie una porta UDP alta e una chiave di sessione, comunica entrambe all'utente e, quando un client si connette, avvia normalmente la shell di login di quell'utente. Una concessione sudo senza restrizioni per `mosh-server`, eseguibile come root, è quindi candidata a una revisione della shell, anche se il comando server si distacca. Controlla l'identità RunAs effettiva, gli argomenti consentiti e le esclusioni, il binario installato, la shell, la disponibilità del client e l'accesso UDP. L'enumerazione passiva dovrebbe esaminare la regola sudo senza avviare un server né stampare una chiave di sessione attiva. Consulta il [manuale di Mosh server](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e le [note di progettazione upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrapper di backup privilegiati che riscrivono il file di task dell'utente

Un wrapper shell eseguito come root può accettare un file di task selezionato dall'utente, rimuovere `../` dai percorsi sorgente, verificare che ogni risultato inizi con una directory consentita, riscrivere il file di task e poi passare al programma di backup il suo *percorso*. Esamina il percorso trasformato dopo la risoluzione canonica completa: una singola sostituzione di stringa può creare una nuova sequenza di traversal che supera un controllo lessicale del prefisso. Verifica anche se il programma di backup legge i dati trasformati dalla memoria o riapre il file. Se lo riapre, una riscrittura non riuscita può lasciare intatto l'input originale.

Su Linux, `fs.protected_regular` può negare una scrittura `O_CREAT` sul file regolare di un altro utente all'interno di una directory sticky scrivibile da tutti. È una protezione, ma un wrapper shell che ignora l'errore di scrittura potrebbe comunque proseguire usando il file di task originale. Verifica l'impostazione, il proprietario del file e della directory e se il wrapper si arresta in caso di errore. Il percorso è solo un candidato per la divulgazione di file se la regola sudo effettiva consente di eseguire il wrapper come utente privilegiato, l'utente controlla l'input del task e una destinazione di backup leggibile e l'utility di backup include davvero sorgenti protette. Durante l'enumerazione, verifica queste condizioni senza eseguire il backup.

### Wildcard negli argomenti degli strumenti di rete privilegiati

In una regola sudo per `tcpdump`, una `*` nel **modello degli argomenti** può corrispondere a spazi e slash, quindi una restrizione che sembra riferirsi a un percorso potrebbe comunque consentire testo di opzioni aggiuntivo. Questo è diverso da una wildcard nel percorso dell'eseguibile del comando; esamina l'intera regola RunAs e gli eventuali divieti successivi. Se è possibile iniettare opzioni, la chiamata consentita e la semantica delle opzioni della versione installata di [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinano se `-F`, `-V`, `-r`, `-w` o `-Z` offrono una primitiva utile di lettura/scrittura. `-V` legge un elenco di nomi di file di cattura, non esegue un dump generico di file arbitrari. AppArmor o un'altra policy MAC può bloccare l'accesso ai file anche quando sudo consente il comando; la presenza di un file di profilo su disco non dimostra che sia caricato o in modalità enforcement. Prima di giungere a una conclusione, esamina passivamente autorizzazioni e policy. Il [manuale sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descrive la distinzione tra wildcard.

Anche una regola sudo eseguibile come root che elenca solo l'eseguibile `tcpdump`, senza limitazioni sugli argomenti, merita una revisione. Il [manuale di tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` come comando post-rotazione quando `-C` o `-G` ruotano una cattura salvata; `-Z` o un valore predefinito in fase di compilazione potrebbero rimuovere i privilegi prima dell'esecuzione di quel comando. Prima di considerare la regola un percorso di escalation, verifica la regola sudo effettiva, la build installata, il comportamento di riduzione dei privilegi e la possibilità che avvenga una rotazione. Una regola evidenziata è un caso candidato, non la prova dell'esecuzione di comandi come root.

### Wrapper Nmap eseguiti tramite sudo

Quando il percorso `nmap` consentito da sudo è un wrapper shell, esamina il percorso esatto consentito e tutte le opzioni che inoltra. Bloccare la familiare opzione `--script` non necessariamente impedisce il caricamento di codice NSE: [`--datadir` di Nmap](https://nmap.org/book/man-misc-options.html) seleziona i file di dati e NSE [carica `nse_main.lua`](https://nmap.org/book/nse-implementation.html) dalla directory dati selezionata quando lo scripting è abilitato. Alcune build installate accettano anche forme alternative delle opzioni lunghe, quindi confronta le restrizioni con il parser effettivo del binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) è una superficie separata di lettura dei file; gli errori del parser possono rivelare testo. Durante l'enumerazione, verifica la regola sudo effettiva, la logica del wrapper, la versione di Nmap, il controllo della directory e la policy MAC senza eseguire scansioni.

### Hook di pull Mercurial eseguiti tramite sudo

Anche con una sorgente fissa in `sudo hg pull /fixed/source`, il repository **ricevente** dipende dalla directory di lavoro corrente, a meno che il comando non lo fissi con `-R`. Un repository ricevente controllato dall'utente può definire hook in `.hg/hgrc`, che potrebbero essere eseguiti come utente RunAs di sudo. [Mercurial ignora la configurazione dei repository di proprietà di un utente o gruppo non attendibile](https://mercurial-scm.org/help/topics/config), quindi prima di considerarlo esecuzione di codice esamina gli utenti/gruppi attendibili dell'account RunAs e la directory di lavoro esatta. Per una revisione passiva è sufficiente leggere la policy e la configurazione; non eseguire `pull` né invocare hook durante l'enumerazione.

### Hook di pull Git eseguiti tramite sudo

Per una concessione sudo esatta per `sudo git pull`, esamina anche il repository **ricevente** selezionato dalla directory di lavoro. Un repository di proprietà dell'utente può avere un hook `post-merge` eseguibile che viene eseguito con l'identità del processo Git quando un pull completa correttamente un merge; [Git documenta questo hook](https://git-scm.com/docs/githooks) e [il comportamento di pull tra merge e rebase](https://git-scm.com/docs/git-pull). Verifica la regola sudo effettiva e la directory corrente, il percorso dell'hook attivo e i relativi permessi, nonché la possibilità di eseguire un merge con nuovi commit. Un pull fallito, che non produce modifiche o che esegue solo un rebase non dimostra questo percorso tramite hook. Esamina policy e metadati del repository senza eseguire il pull privilegiato.

### Copie archiviate con rsync tramite sudo

Per `sudo rsync -a ... /writable/source/* /fixed/destination/`, una `*` nel **modello degli argomenti sudoers** può corrispondere a spazi e consentire un'opzione aggiuntiva tra sorgente e destinazione. Questo è diverso dall'espansione dei nomi dei file da parte della shell. Se l'utente può popolare la sorgente e la destinazione è scrivibile da rsync privilegiato, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) può richiedere una proprietà privilegiata mentre la modalità archivio conserva i bit di permesso, creando potenzialmente un file di proprietà privilegiata con SetUID. Controlla la semantica esatta delle [wildcard sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versione di rsync, gli eventuali divieti successivi, l'opzione filesystem `nosuid` e la policy MAC. Una regola corrispondente è un caso da esaminare, non la prova di un'escalation riuscita.

### Esportazione delle regole del filtro pacchetti tramite sudo

Una concessione sudo senza restrizioni per `iptables` e `iptables-save` (o per la coppia corrispondente `ip6tables`) ed eseguibile come root merita una revisione della scrittura su file. Il match `comment` accetta testo di regole scelto dall'utente, mentre `iptables-save -f` scrive il ruleset serializzato in un percorso selezionato.<sup>[[20]](#references)[[21]](#references)</sup> L'utilità del payload dipende da come il backend installato serializza i commenti e dal fatto che il file di destinazione accetti altre righe nell'esportazione; `iptables-save`, da solo, non consente di scegliere contenuti arbitrari. Controlla l'identità RunAs sudo esatta, gli argomenti e le esclusioni, l'estensione di match disponibile, il backend e i permessi della destinazione. Durante l'enumerazione, esamina la concessione senza modificare le regole del firewall né scrivere file.

### Directory di log Below privilegiata

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) riguardava le versioni di Below precedenti alla 0.9.0, che creavano una directory `/var/log/below` scrivibile da tutti. Se un servizio o un comando sudo consentito esegue come root una build affetta, un utente che può scrivere e attraversare una directory di log non sticky potrebbe sostituire una voce di log con un symlink prima che il processo privilegiato la apra. Esamina lo stato delle patch del pacchetto installato, il percorso esatto di esecuzione privilegiata, l'accesso effettivo alla directory, il bit sticky e gli ACL, nonché i metadati di `/var/log/below/error_root.log`. Un percorso scrivibile da tutti o una regola sudo, da soli, non dimostrano l'intera catena. Una directory sticky o un backport del vendor cambiano la valutazione. L'enumerazione passiva dovrebbe esaminare solo i metadati; non è necessario creare un link né eseguire il programma privilegiato.

### Raccolta privilegiata di support bundle da input scrivibili

Uno script di profilo di supporto consentito da `sudo` può leggere percorsi di log fissi come root e copiarne il contenuto in un archivio di profilo. Esamina lo script effettivo per individuare le letture di file, poi verifica se l'utente può sostituire un percorso sorgente o una voce della directory genitrice con un symlink. Se la lettura privilegiata segue quel link e l'archivio risultante è leggibile dall'utente, un file protetto può essere divulgato. Devono essere presenti tutti gli elementi: concessione sudo, percorso sorgente scrivibile, lettura privilegiata e output leggibile; un log o nome di profilo scrivibile, da solo, non basta. Durante l'enumerazione, esamina i permessi effettivi e i metadati dei link senza sostituire file né generare un profilo. Le [indicazioni di supporto di Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentano lo script di profilo eseguito come root e il relativo archivio di output, illustrando perché questi bundle necessitano di input e accessi all'output limitati.

### Script Python di ripristino archivi eseguiti come root

Anche una regola sudo strettamente limitata per uno script Python di ripristino richiede una revisione dell'input archivio. Se l'utente può selezionare o sostituire l'archivio e lo script lo estrae come root con `tarfile.extractall(filter="data")`, verifica gli aggiornamenti di sicurezza dell'interprete prima di fidarti del filtro. CPython ha corretto diverse bypass del filtro con symlink e hard link, tra cui CVE-2025-4517, nelle versioni 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. I backport delle distribuzioni possono correggere versioni precedenti, quindi la versione mostrata dell'interprete non dimostra da sola l'esposizione.<sup>[[16]](#references)[[17]](#references)</sup>

Per una revisione passiva, leggi il comando sudo e lo script esatti, segui l'argomento che seleziona l'archivio e verifica se l'utente corrente può scrivere l'archivio o la directory che lo contiene. Controlla separatamente la patch del vendor installata e la destinazione dell'estrazione; `filter="data"` non rende sicuro ogni archivio non attendibile.<sup>[[16]](#references)[[17]](#references)</sup>

### Loader di modelli di machine learning eseguiti tramite sudo

Una regola sudo che consente di selezionare un file `.pt`, `.pth` o `.ckpt` merita una revisione quando uno script privilegiato lo passa a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` o a un altro loader basato su pickle. Controlla la regola RunAs effettiva, se l'utente può creare o sostituire il modello selezionato e il flusso effettivo dell'argomento attraverso un eventuale wrapper shell fino all'helper Python. L'estensione `.pth` indica anche file di configurazione Python di site non correlati, quindi da sola non dimostra il caricamento di un modello. L'analisi di un archivio o di un pickle in modo statico non dimostra che il caricamento successivo sia sicuro; esamina il comportamento di `weights_only` in funzione della [versione](https://docs.pytorch.org/docs/stable/notes/serialization.html) e le eventuali allowlist. Consulta le [note su pickle ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). L'enumerazione passiva non dovrebbe mai caricare né estrarre il modello.

### Parsing di espressioni su input memorizzati eseguito tramite sudo

Uno script Python fisso eseguito come root tramite sudo può comunque valutare testo che un utente con privilegi inferiori può salvare in un database applicativo. In TensorFlow, una chiamata a `preprocess_input_exprs_arg_string(value, safe=False)` seleziona un percorso `eval`; [l'avviso di TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descrive il parser non sicuro e una correzione nel relativo chiamante da riga di comando. Una chiamata esplicita `safe=False` dell'applicazione richiede una revisione a sé anche quando quel chiamante è stato corretto. Verifica la regola sudo effettiva, chi può modificare la riga di input specifica, se il filtraggio o lo scoring consente a quella riga di raggiungere la chiamata e il comportamento della funzione installata. Una versione di TensorFlow, una concessione sudo o un file modello fisso non dimostrano da soli l'intera catena. Esamina passivamente script e flusso dei dati; durante l'enumerazione non eseguire l'helper privilegiato né inviare espressioni di prova.

### Configurazione di needrestart consentita da sudo

`needrestart -c` carica e valuta il contenuto di un file di configurazione Perl scelto dall'utente. Se `sudo -l` consente di eseguire `needrestart` come root con argomenti che ammettono `-c` e l'utente può scegliere un file di configurazione leggibile in una posizione scrivibile, tale permesso può portare all'esecuzione di codice come root. Controlla la regola sudo esatta su RunAs e argomenti; una regola che consente solo un elenco fisso di argomenti può bloccare questo percorso. È un problema distinto dalle vulnerabilità di needrestart nella scansione degli interpreti: aggiornare il pacchetto o disabilitare `interpscan` non rende sicura una concessione root senza restrizioni con `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Import Python eseguiti tramite sudo con un altro account

Un entry point Python fisso può comunque importare un modulo che l'utente può modificare o sostituire, anche se sudo esegue lo script come un account di servizio **non root**. Per un import letterale come `from utils import status`, esamina `utils/__init__.py` e `utils/status.py` locali, oltre ai permessi della directory del pacchetto. Prima di considerare il file scrivibile un percorso di esecuzione, verifica il percorso di import dello script, gli argomenti sudo esatti consentiti e se l'azione pertinente raggiunge quell'import. Durante l'enumerazione, esamina file e permessi senza importare né eseguire lo script.<sup>[[2]](#references)[[3]](#references)</sup>

Una regola sudo esatta per `python3 /absolute/script.py` richiede solo uno script leggibile; il file non deve essere eseguibile né avere uno shebang. Esamina anche i moduli locali **mancanti**: se lo script importa un modulo il cui nome file può essere creato in una directory dello script scrivibile dall'utente, Python può caricare quel file con l'identità RunAs. Verifica la regola sudo effettiva, il [percorso di ricerca dei moduli](https://docs.python.org/3/library/sys_path_init.html) realmente usato dall'interprete, se il modulo è incorporato o congelato e se l'import viene raggiunto. Una regola sudo diretta per lo script ha requisiti diversi riguardo al bit eseguibile e allo shebang. Un wrapper separato che aggiunge token forniti dall'utente dopo `sudo -u account` richiede anche un'analisi del flusso degli argomenti: un altro `-u` tra quei token è rilevante solo se la policy sudo invocata consente l'identità risultante. Le sole stringhe statiche non dimostrano nessuno dei due percorsi.

### Apache eseguito tramite sudo con configurazione controllata dall'utente

Se una regola sudo consente di eseguire `apachectl`, `apache2ctl` o `httpd` con privilegi elevati e un file di configurazione `-f` controllato dall'utente, esamina i permessi del file e della relativa directory genitrice. La direttiva Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) accetta un nome di modulo seguito dal **nome del file del modulo**; anche [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) carica un file. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) possono estendere la configurazione o esporre contenuti di file tramite errori. Un wrapper personalizzato può convalidare questi percorsi, ridurre i privilegi o limitare gli argomenti; una configurazione scrivibile è quindi un caso da esaminare, non la prova di esecuzione di codice. Prima di giungere a una conclusione, controlla la canonicalizzazione dei percorsi, i symlink e l'analisi delle direttive.

### nginx eseguito tramite sudo con configurazione controllata dall'utente

Una regola `nginx` senza restrizioni, eseguibile come root, può consentire a [`-c` di selezionare un'altra configurazione](https://nginx.org/en/docs/switches.html). Esamina gli argomenti sudo esatti e le esclusioni, se l'utente può fornire la configurazione e se i processi master o worker risultanti mantengono accesso a percorsi protetti. Un `root` scelto dall'utente insieme a `autoindex` può esporre file attraverso un nuovo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) può offrire un percorso di scrittura file privilegiato, ma il modulo DAV non viene compilato per impostazione predefinita e vanno verificati la sua presenza, la raggiungibilità del listener, i permessi dei file e il comportamento dei file temporanei. Anche la direttiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) può puntare a un file scelto; scrivere log in un file di configurazione sensibile, come `/etc/ld.so.preload`, diventa un percorso di escalation solo se esiste un writer privilegiato effettivo e un record di log controllabile. L'evidenziazione dell'eseguibile in `sudo -l` è uno spunto per la revisione, non la prova che uno di questi percorsi funzioni. Durante l'enumerazione passiva non avviare né riconfigurare nginx.

### Confronto di pattern nei prompt Bash privilegiati

Quando uno script Bash consentito da sudo legge un valore dall'utente e lo verifica con `[[ "$expected" == $entered ]]`, Bash interpreta l'operando destro non quotato come un pattern. Un wildcard può quindi soddisfare il confronto senza conoscere il valore atteso. Quotare l'operando (`[[ "$expected" == "$entered" ]]`) lo trasforma in un confronto letterale tra stringhe. Esamina la regola sudo esatta, se il prompt è raggiungibile e cosa fa lo script dopo il confronto; la sola sintassi non dimostra un percorso sfruttabile. Durante l'enumerazione, evita di stampare il valore atteso. Consulta il [riferimento alle espressioni condizionali Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper eseguiti tramite sudo che scaricano ed eseguono un file

Una concessione sudo senza restrizioni, eseguibile come root, a un helper personalizzato merita un'analisi del flusso dei dati se accetta un URL scelto dall'utente, scrive la risposta su disco e in seguito invoca il file tramite un interprete o una shell. [Sudoers consente argomenti arbitrari se la voce del comando non ne specifica](https://man7.org/linux/man-pages/man5/sudoers.5.html); un percorso dell'eseguibile fisso non limita ciò che gli argomenti possono selezionare. Verifica la convalida effettiva dell'URL, il percorso di output, il ramo di successo e l'esecuzione successiva nell'helper installato. La presenza di un import libcurl corrispondente o di una stringa stampabile, da sola, non dimostra questa catena.

Anche un nome file di output fisso può essere sostituito tra scrittura ed esecuzione se l'helper usa un **percorso relativo in una directory di lavoro controllata dall'utente**. Rinominare o sostituire un file di proprietà di root dipende dai permessi di scrittura e ricerca sulla directory e dalle eventuali restrizioni sticky bit, non solo dai permessi del file; consulta [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Controlla se l'helper riapre il percorso in seguito o usa il descrittore già aperto e se cambia directory prima di scrivere. Esamina passivamente la policy sudo, l'helper e i metadati della directory; durante l'enumerazione non invocare il download privilegiato né tentare una race.

Un helper di download eseguito tramite sudo come root può anche esporre un'injection di **argomenti** se costruisce una stringa Bash come `curl <input utente> -o <output fisso>`. Un filtro che rifiuta gli spazi lascia comunque passare la [brace expansion di Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementi separati da virgole e non quotati possono diventare argomenti curl distinti. Se l'input raggiunge curl prima del `-o` fisso, un'opzione di output fornita dall'utente può selezionare la destinazione per il primo URL con l'identità dell'helper; [curl associa le opzioni di output agli URL nell'ordine in cui compaiono](https://curl.se/docs/manpage.html#-o). Verifica shell esatta, quoting, convalida dell'input, regola sudo effettiva, ordine degli argomenti curl e schemi URL supportati, nonché se l'utente controlla i byte scaricati o può leggerne il risultato. Un eseguibile pacchettizzato con PyInstaller può contenere logica applicativa Python, ma la presenza del pacchetto o di una stringa `curl`, da sola, non dimostra questo flusso di dati. Se autorizzato, esamina una copia offline di dimensioni contenute; l'enumerazione ordinaria non dovrebbe eseguire l'helper né scaricare dati scelti dall'attaccante.

Uno script shell root-sudo che chiama [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) sceglie soltanto un nome non utilizzato; **non** crea il file. Se lo script crea in seguito quel nome in una directory che un altro utente può influenzare, poi lo riapre e ne aggiunge il contenuto a una destinazione protetta come `authorized_keys` di root, esamina la possibilità di una race sui file temporanei. Verifica la regola sudo esatta, la proprietà della directory e dei file, la sequenza di creazione e riapertura, le protezioni del kernel e se la scrittura privilegiata usa davvero byte controllati dall'attaccante. Una stringa `mktemp -u` o `/tmp` scrivibile, da sole, non dimostrano la race. Esamina script e metadati del percorso senza eseguirlo né tentare di vincere una race sul file temporaneo durante l'enumerazione.

## Note difensive

- Evita di concedere tramite sudo interpreti o editor interattivi.<sup>[[1]](#references)</sup>
- Non concedere writer generici di file come `tee` con operandi senza restrizioni. Usa un wrapper di proprietà di root che selezioni una destinazione fissa e rifiuti percorsi controllati dall'utente.<sup>[[2]](#references)</sup>
- Preferisci wrapper fissi, di proprietà di root, che eseguono una singola e circoscritta azione amministrativa.<sup>[[1]](#references)[[2]](#references)</sup>
- Se un interprete è inevitabile, limita il percorso esatto dello script e impedisci l'uso di argomenti controllati dall'utente, import scrivibili, `PYTHONPATH` e la preservazione non sicura dell'ambiente.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se è necessario modificare file, limita il percorso esatto del file e valuta `sudoedit` con versioni di sudo aggiornate e una gestione rigorosa dell'ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Esamina `SETENV`, `env_keep`, le directory di lavoro scrivibili, i percorsi di moduli/import scrivibili, `NOEXEC`, `use_pty` e la registrazione, ma non considerarli una sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
