## Interpretery dozwolone przez Sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interpreter jako root, traktuj to jak bezpośrednie wykonanie kodu. Interpretery służą do wykonywania dowolnego kodu, więc reguła zezwalająca na użycie `python3`, `perl`, `ruby`, `lua`, `node` lub podobnych plików binarnych jest zwykle równoważna możliwości wykonywania poleceń jako root, chyba że argumenty są ściśle ograniczone i walidowane.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Typowy przebieg analizy: najpierw wyświetl uprawnienia użytkownika, a następnie wykonaj instrukcję Pythona za pomocą opcji `-c` interpretera.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Poniżej przedstawiono inne przykłady interpreterów; wymienione interpretery opisują wykonywanie kodu inline lub API procesów potomnych.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Dokładna ścieżka ma znaczenie. Jeśli reguła sudo zezwala na `/usr/bin/python3`, podczas weryfikacji użyj dokładnie tej ścieżki.<sup>[[2]](#references)</sup>

Wzorzec glob dla pliku wykonywalnego sudo, taki jak `/usr/bin/python*`, może również dopuszczać Python 2 w przypadku skryptu napisanego dla Python 3. Jeśli skrypt wywołuje `input()` z tekstem kontrolowanym przez wywołującego, [Python 2 interpretuje ten tekst jako wyrażenie](https://docs.python.org/2/library/functions.html#input); jawne wywołanie interpretera zastępuje shebang skryptu. Przed uznaniem tego za ścieżkę do wykonania kodu sprawdź pasujące zainstalowane pliki binarne, efektywną tożsamość RunAs i politykę argumentów, odmowy dostępu oraz to, czy można dotrzeć do miejsca wczytywania danych wejściowych.

Stała ścieżka skryptu w regule sudo z uprawnieniami roota nie ogranicza tego, co wykonuje skrypt. W przypadku czytelnego wrappera Bash sprawdź, czy jego pierwsze polecenie wykonywalne używa nieujętego w cudzysłów parametru pozycyjnego, takiego jak `$1`, jako **słowa polecenia**, gdy sudo dopuszcza argumenty wybrane przez wywołującego. Potwierdź efektywną tożsamość RunAs, politykę haseł i argumentów, późniejsze odmowy dostępu oraz faktycznie wykonywaną gałąź skryptu; `NOEXEC`, stała bezpieczna lista argumentów lub wrapper sprawdzający polecenie mogą zmienić wynik. Podczas enumeracji przeanalizuj krótki skrypt statycznie, zamiast uruchamiać go z testowym poleceniem.

Nieograniczona reguła sudo z uprawnieniami roota dla `dotnet` również wymaga sprawdzenia interpretera. Jeśli zainstalowany jest .NET SDK, [`dotnet fsi` uruchamia kod F# interaktywnie lub ze skryptu](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), a [`dotnet run` wykonuje projekt ze źródła](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Najpierw potwierdź efektywną tożsamość RunAs i dokładną politykę argumentów: reguła ograniczona do konkretnego bezpiecznego podpolecenia lub zaufanej aplikacji stanowi inne uprawnienie, a instalacja zawierająca tylko środowisko uruchomieniowe może nie mieć poleceń SDK. Sama nazwa pliku wykonywalnego jest wskazówką do weryfikacji, a nie dowodem możliwości wykonania kodu.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` dozwolone przez sudo: dowolny zapis do pliku z uprawnieniami administratora

GNU `tee` kopiuje standardowe wejście do każdej ścieżki podanej jako argument plikowy. Dlatego reguła sudo zezwalająca na uruchamianie `/usr/bin/tee` jako root z argumentami kontrolowanymi przez użytkownika umożliwia tworzenie lub nadpisywanie dowolnych plików z uprawnieniami roota. Dodanie `-a` zmienia tę możliwość na dopisywanie do pliku. Tag `PASSWD:` dotyczy uwierzytelniania sudo; sam w sobie nie ogranicza miejsca docelowego ani bajtów odczytywanych ze standardowego wejścia.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Najpierw sprawdź dokładną regułę. W autoryzowanym systemie testowym zweryfikuj tę możliwość wyłącznie na tymczasowym pliku, którego utworzenie jest bezpieczne. Końcowe `>/dev/null` jedynie wycisza kopię danych wypisywaną przez `tee` na standardowe wyjście.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Umieszczenie `sudo` przed poleceniem wyjściowym nie podnosi uprawnień późniejszego przekierowania powłoki, ponieważ plik docelowy otwiera powłoka wywołująca polecenie. Proces z podwyższonymi uprawnieniami musi być tym, który zapisuje dane, jak w powyższym potoku.<sup>[[1]](#references)[[15]](#references)</sup>

Po potwierdzeniu możliwości zapisu wybierz odpowiedni mechanizm wykonania kodu jako root z sekcji [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). W jednym zaobserwowanym łańcuchu użyto `tee` uruchomionego jako root do utworzenia krótkotrwałego pliku w `/etc/cron.d/`, uruchomiono backdoor za pośrednictwem skryptu kontrolowanego przez użytkownika, a po wykonaniu usunięto plik cron. Usunięcie pliku cron zapobiegło utworzeniu długotrwałego wpisu persistence, choć logi systemowe nadal zachowały ślady tej aktywności.<sup>[[27]](#references)</sup>

## Edytory dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interaktywny edytor jako root, traktuj to jako powierzchnię wykonania poleceń, a nie nieszkodliwe uprawnienie do edycji plików. Edytory często mogą wykonywać polecenia powłoki, odczytywać dowolne pliki, zapisywać dowolne pliki lub wywoływać zewnętrzne narzędzia z poziomu edytora.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Typowy przebieg analizy: wyświetl uprawnienia użytkownika, a następnie uruchom każdy dozwolony edytor lub pager przez sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Wykonywanie poleceń w edytorze nano

Gdy `nano` jest dozwolone przez sudo, wykonywanie poleceń może być dostępne z poziomu interfejsu edytora.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Następnie wprowadź polecenie, takie jak `id` lub `/bin/sh`, w wierszu poleceń nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Jeśli interaktywna powłoka nie ma dostępnych strumieni terminala, ta forma przekierowania przypisuje jej standardowe wyjście i błędy do deskryptora 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Dokładna sekwencja klawiszy może się różnić w zależności od wersji nano i opcji kompilacji, ale problem z bezpieczeństwem pozostaje ten sam: edytor działa jako root i może uruchamiać zewnętrzne polecenia.<sup>[[1]](#references)[[12]](#references)</sup>

### Inne typowe sposoby ucieczki z edytora

Edytory w stylu Vim często umożliwiają wykonywanie poleceń za pomocą `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Programy takie jak `less` mogą również umożliwiać uruchomienie powłoki.<sup>[[14]](#references)</sup>

Reguła sudo zezwalająca na uruchamianie `apport-cli` jako root wymaga takiego samego sprawdzenia pod kątem pagera. W podatnych wersjach Apport można było otworzyć raport o awarii w `less` z rozmiarem terminala kontrolowanym przez atakującego; pager mógł wtedy umożliwić uzyskanie powłoki roota, jeśli spełnione były specjalne warunki dotyczące sudo i pagera. Zanim uznasz daną wersję za podatną, sprawdź efektywną regułę sudo, konfigurację pagera oraz poprawkę w pakiecie danej dystrybucji. Podczas pasywnego rozpoznania odczytaj metadane pakietu i polityki, nie generując awarii ani nie otwierając uprzywilejowanego raportu. [Rekord CVE Ubuntu](https://ubuntu.com/security/CVE-2023-1326) zawiera wersje pakietów z poprawkami dla poszczególnych wydań, w tym poprawki przeniesione do starszych wersji.

```text
!/bin/sh
```

## Inne zagrożenia związane z regułami sudo i doas

Zacznij od `sudo -l`, `sudo -V` i wszelkich mających zastosowanie reguł `doas`. Analizuj łącznie dozwolone polecenie, użytkownika, w którego imieniu można je uruchomić, argumenty, środowisko i ustawienia domyślne. Uprawnienie do uruchamiania poleceń jako nieuprzywilejowane konto usługi nadal może zapewnić dostęp do jego plików lub ścieżkę do roota.

Skrypt Pythona dozwolony przez sudo może nadal uruchomić polecenie powłoki z tożsamością RunAs, jeśli dane wejściowe kontrolowane przez użytkownika są dołączane do [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Lista blokująca znaków interpunkcyjnych powłoki nie wystarcza, by uznać skrypt za bezpieczny: [powłoka rozpoznaje też podstawianie poleceń `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Ustal, czy dozwolone argumenty docierają do gałęzi obsługującej dane wejściowe, czy dane wejściowe trafiają do polecenia powłoki bez bezpiecznej walidacji oraz czy skuteczna polityka sudo zezwala na zamierzonego użytkownika RunAs. Sama ścieżka skryptu lub wywołanie `os.system()` to jedynie wskazówka do dalszej analizy; sprawdź kod źródłowy bez uruchamiania uprzywilejowanego skryptu.

Skuteczne uprawnienie sudo do uruchamiania `chattr` jako root może usunąć atrybut pliku immutable (`i`), ale samo w sobie nie zapewnia prawa zapisu ani nowej tożsamości. [Podręcznik `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) wyjaśnia, że atrybut blokuje modyfikacje i że może go zmienić tylko root lub proces z `CAP_LINUX_IMMUTABLE`. Sprawdź dokładną politykę argumentów sudo i obsługę systemu plików, a następnie osobno zweryfikuj, czy użytkownik może zapisywać plik po usunięciu atrybutu i czy korzysta z niego proces o wyższej tożsamości. Na przykład zmiana powłoki logowania wymaga także danych uwierzytelniających akceptowanych przez konto docelowe i faktycznego logowania przez tę powłokę. Podczas inwentaryzacji przejrzyj politykę, atrybuty plików i uprawnienia, nie zmieniając ich.

Jeśli sudo pyta o hasło i jednorazowy kod, traktuj te wymagania niezależnie od uprawnienia do uruchomienia polecenia. Czytelny plik `.google_authenticator` zawiera wrażliwy materiał seed, a stary hash hasła aplikacji lub bazy danych jest jedynie kandydatem na bieżące hasło konta; żaden z nich nie dowodzi, że drugi czynnik jest akceptowany przez skuteczną konfigurację PAM. Po uzyskaniu autoryzacji sprawdź dokładne ustawienia RunAs i argumenty: nieograniczone uprawnienie roota do RubyGems `gem` może udostępniać jego polecenie edytora ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ale ograniczone uprawnienie lub nieudane uwierzytelnienie — nie. Pasywna inwentaryzacja powinna wskazywać ścieżki i politykę, nie wyświetlając seeda, nie odzyskując hasła, nie generując kodu ani nie uruchamiając uprzywilejowanego polecenia.

Nieograniczone uprawnienie sudo do uruchamiania Chef `knife` jako root wymaga analizy na poziomie interpretera: [Chef dokumentuje, że `knife exec -E` lokalnie interpretuje ciąg Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Sprawdź, czy skuteczna reguła sudo zezwala na podpolecenie `exec` i dostarczony przez użytkownika argument `-E`, zamierzoną tożsamość RunAs oraz wszelkie pasujące zakazy poleceń lub ustalone argumenty. Zainstalowany plik binarny lub reguła ograniczona do innych podpoleceń to jedynie wskazówki. Pasywna inwentaryzacja powinna opisać regułę bez uruchamiania `knife`.

Dokładne uprawnienie sudo do interaktywnego `msfconsole` z możliwością działania jako root jest równie wrażliwe: [GTFOBins opisuje jego konsolę `irb`](https://gtfobins.org/gtfobins/msfconsole/), która może dziedziczyć tożsamość sudo. Potwierdź skutecznego użytkownika RunAs, dozwoloną listę argumentów, zakazy poleceń, ograniczenia `NOEXEC` lub inne, zachowanie zainstalowanej konsoli oraz to, czy użytkownik może dostarczać interaktywne dane wejściowe. Samo wyróżnienie ścieżki to jedynie wskazówka; pasywna inwentaryzacja nie powinna uruchamiać konsoli.

We FreeBSD nawet reguła sudo ograniczona do `pkg update` i `pkg install *` jako root wymaga sprawdzenia zaufania do repozytorium. Sprawdź, czy użytkownik może zapisywać `/etc/hosts` oraz czy *skuteczna* konfiguracja włączonych repozytoriów używa nazwy hosta HTTP z `signature_type: none`. [Podręcznik FreeBSD `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) wyjaśnia, że `none` wyłącza sprawdzanie podpisów; samo `pkg+http` tego nie dowodzi. Pakiet może zawierać skrypty instalacyjne ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), więc użytkownik, który faktycznie kontroluje punkt końcowy repozytorium i może wybrać pakiet, może przekroczyć granicę uprawnień roota. Zanim wyciągniesz taki wniosek, zweryfikuj nadpisania repozytorium, rozwiązywanie SRV/mirror, skuteczne argumenty sudo, wybór pakietu i wykonywanie skryptów. Podczas inwentaryzacji sprawdź politykę i niewielkie lokalne pliki konfiguracyjne, nie przekierowując nazw ani nie uruchamiając `pkg`.

Uprawnienie sudo do `apt-get update` i `apt-get upgrade` z możliwością działania jako root również wymaga sprawdzenia zaufania do repozytorium, jeśli sudo zachowuje kontrolowane przez użytkownika `http_proxy`. Sprawdź, czy skuteczna konfiguracja proxy APT rzeczywiście używa tej zmiennej i na które żądania do włączonych repozytoriów może ona wpływać; samo proxy nie może zastąpić pakietów z archiwum uwierzytelnionego zaufanym kluczem podpisującym. [Podręcznik transportu HTTP APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) opisuje pierwszeństwo ustawień proxy, a [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — sprawdzanie podpisów, nadpisania dla niezabezpieczonych repozytoriów i potwierdzanie instalacji nieuwierzytelnionych pakietów. Potwierdź dokładne ustawienia RunAs i argumenty sudo, politykę uwierzytelniania repozytorium, wymagane interaktywne potwierdzenia oraz to, czy wybrana aktualizacja uruchamia skrypty pakietów jako root. Sprawdzaj politykę i lokalną konfigurację pasywnie; podczas inwentaryzacji nie przekierowuj ruchu pakietów ani nie uruchamiaj aktualizacji.

Reguła sudo pozwalająca uruchamiać `snap install` jako root może stanowić granicę pakiet–kod, jeśli jej argumenty pozwalają użytkownikowi wybrać lokalny snap i tryb instalacji o luźnych ograniczeniach. [Dokumentacja Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) wyjaśnia, że `--dangerous` pomija sprawdzanie asercji lokalnego snapa, a `--devmode` łagodzi ograniczenia; [hook instalacyjny może uruchomić się podczas pierwszej instalacji](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Zanim stwierdzisz, że możliwy jest dostęp do chronionych plików hosta, sprawdź dokładną politykę argumentów/RunAs sudo, kto kontroluje plik snapa, czy zainstalowany snapd akceptuje te tryby oraz tożsamość i ograniczenia hooka. Sam plik binarny `snap` lub reguła przypominająca wildcard nie dowodzą istnienia takiego łańcucha. Pasywna inwentaryzacja nie powinna instalować pakietu ani uruchamiać jego hooka.

W przypadku dokładnego uprawnienia sudo do własnego programu odczytującego dane uwierzytelniające, uruchamianego jako konto **niebędące rootem**, najpierw sprawdź przyznany plik binarny i jego uprawnienia, nie uruchamiając go. Osadzona kontrola hasła może być widoczna tylko jako znaki o szerokości dwóch bajtów; [GNU `strings` opisuje wyodrębnianie tekstu 16-bitowego w little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Widoczny ciąg nie dowodzi, że jest akceptowanym hasłem ani że poprawna gałąź ujawnia aktualne dane uwierzytelniające. Osobno potwierdź zachowanie programu, dostęp konta docelowego do chronionych danych, ważność danych uwierzytelniających oraz ewentualną późniejszą zmianę konta lub grupy. Jeśli to konto należy do `docker`, sprawdź dostęp do socketu i tożsamość demona — rootful lub rootless — zanim wywnioskujesz dostęp do roota hosta; [Docker opisuje skutki przynależności do tej grupy na poziomie roota](https://docs.docker.com/engine/install/linux-postinstall/). Standardowa inwentaryzacja powinna opisać regułę sudo i członkostwo w grupach bez uruchamiania programu ani zrzucania jego ciągów.

Reguła sudo z wildcardem dla skryptów konserwacyjnych aplikacji wymaga analizy wykraczającej poza samą ścieżkę skryptu. Sprawdź, czy dozwolony skrypt przyjmuje nieograniczone argumenty lub odczytuje ustawienia, które może zapisywać użytkownik aplikacji o niższych uprawnieniach, a następnie prześledź te wartości do poleceń powłoki lub środowiska podprocesu. Na przykład ZoneMinder: [`zmupdate.pl` buduje polecenie `mysqldump` i wykonuje je przez `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), a [`zmdc.pl` kopiuje ustawienie `ZM_LD_PRELOAD` do `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) przed uruchomieniem demonów. Reguła sudo pozwalająca uruchamiać którykolwiek z tych skryptów jako root może przekroczyć granicę zaufania, jeśli odpowiadające mu dane wejściowe są kontrolowane i trafiają do tego kodu w zainstalowanej wersji. Sprawdź skuteczną regułę sudo, uprawnienia do konfiguracji aplikacji i kod źródłowy skryptu; sam wildcard lub ustawienie to wskazówka, nie dowód wykonania.

- `SETENV`, `env_keep`, `secure_path` i `LD_PRELOAD` mogą zmienić wąskie uprawnienie do polecenia w możliwość przejęcia importu, biblioteki lub ścieżki PATH. Zobacz [przewodnik po zmiennych środowiskowych](../linux-basics/linux-environment-variables.md) i [nadużycia SUID/linkera](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Dokładne uprawnienie `SETENV` do uruchamianego jako root wrappera powłoki wymaga też analizy jednokrokowej, jeśli wrapper uruchamia ustalony skrypt Pythona z dosłownym importem. `secure_path` ogranicza wyszukiwanie poleceń przez powłokę, ale nie wyszukiwanie modułów przez Pythona w [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); opcje [`-E` i `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) sprawiają, że Python ignoruje tę zmienną środowiskową. Zanim uznasz to za wykonanie kodu, potwierdź skuteczne znaczniki sudo i zakazy, gałąź wrappera, opcje interpretera, rozwiązywanie importu oraz katalog wyszukiwania, do którego użytkownik może zapisywać. Krótkie skrypty sprawdzaj statycznie; nie uruchamiaj uprzywilejowanego wrappera.

Dokładne uprawnienie sudo do `neofetch ""` z możliwością działania jako root może mimo to wczytać konfigurację powłoki, jeśli odpowiednie ustawienia domyślne sudo zachowują kontrolowane przez użytkownika `XDG_CONFIG_HOME`. Zachowana zmienna lub zainstalowany Neofetch to tylko wskazówka. Sprawdź politykę i metadane plików bez uruchamiania uprzywilejowanego polecenia ani wyświetlania zawartości konfiguracji; zobacz [obsługę środowiska przez sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Nieograniczona reguła sudo do `facter` z możliwością działania jako root wymaga osobnej analizy własnych factów. [Puppet dokumentuje](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), że `--custom-dir` wczytuje pliki factów Ruby z wybranego katalogu. Sprawdź, czy dokładna reguła sudo zezwala na tę opcję, czy zainstalowany Facter ją obsługuje i czy użytkownik kontroluje ten katalog. Wynik mogą zmienić uprawnienie do polecenia ze stałymi argumentami, jawny zakaz polecenia lub wyłączone własne fakty. Pasywna inwentaryzacja powinna wskazać potencjalne uprawnienie bez uruchamiania Facter ani odczytywania zawartości factów.

W przypadku dokładnego uprawnienia sudo do skryptu działającego jako root i z `SETENV`, sprawdź gołe nazwy poleceń, takie jak `find`, oraz skuteczną wartość `PATH` po zastosowaniu polityki sudo i inicjalizacji skryptu. Potwierdź obowiązujące [reguły środowiska sudoers i `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), wszelkie wpisy `NOSETENV`/`NOEXEC` lub zakazujące poleceń, przepływ skryptu i wczytywanych plików oraz katalog wyszukiwania, do którego użytkownik może zapisywać i z którego można wykonywać pliki. Stałe `runchdir` sudo, `os.Chdir` lub [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) mogą zmienić miejsce wyszukiwania. Samo współwystępowanie tych elementów w kodzie to tylko kandydat; sprawdź źródło bez uruchamiania Go, WASM ani helpera.
- `sudoedit` i wildcardy argumentów wymagają sprawdzenia dokładnej wersji i reguły; [lista kontrolna](linux-privilege-escalation-checklist.md) obejmuje problem edycji plików przez sudoedit. W przypadku międzyużytkownikowego uprawnienia `sudoedit` do ścieżki z wildcardem sprawdź skuteczne ustawienie `sudoedit_follow` lub `FOLLOW`, `sudoedit_checkdir`, rozwiązaną ścieżkę docelową oraz to, kto może podmienić każdy wpis katalogu nadrzędnego. Pierwsze ustawienie może pozwolić na podążanie za symlinkiem, a wyłączenie drugiego usuwa kontrole zapisywalnych katalogów; żadne z nich samo w sobie nie dowodzi możliwości zapisu do pliku innego użytkownika. Zanim wyciągniesz taki wniosek, potwierdź zainstalowaną politykę sudo i dokładne dopasowane argumenty. Zobacz [definicje opcji sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- W regule polecenia sudoers wildcard argumentu może dopasować białe znaki, a także znaki ścieżki. Reguła dla polecenia umożliwiającego odczyt z argumentem takim jak `/restricted/*` może więc dopuścić dodatkowy argument pliku po pasującym prefiksie. Sprawdź dokładnego użytkownika RunAs, ścieżkę polecenia, wzorzec argumentu i późniejsze zakazy; wykazany odczyt pliku nie oznacza wykonania polecenia. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) rozróżnia globy argumentów od globów ścieżek poleceń.
- Glob argumentu przypominający ścieżkę może też dopasować `../`. Na przykład reguła `node /opt/scripts/*.js` z możliwością działania jako root może pozwolić użytkownikowi dostarczyć plik JavaScript spoza `/opt/scripts`, jeśli podana ścieżka nadal zaczyna się od `/opt/scripts/`, a po rozstrzygnięciu zawiera segmenty katalogów nadrzędnych. To glob **argumentu**; glob ścieżki wykonywalnego pliku polecenia Node ma inne reguły dopasowywania ukośników. Zanim wyciągniesz wniosek o wykonaniu kodu, sprawdź skuteczną regułę, późniejsze zakazy, rozwiązywanie ścieżki, kontrolę nad plikiem docelowym oraz ograniczenia wyrażeń regularnych lub digestów sudoers. Zobacz [reguły wildcardów sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) i [dokumentację wiersza poleceń Node](https://nodejs.org/api/cli.html).
- Programy archiwizujące i inne narzędzia mogą oferować hooki wykonawcze. Sprawdź dokładne dozwolone argumenty w [GTFOBins](https://gtfobins.github.io/), zamiast zakładać, że polecenia wykonują tylko powłoki lub interpretery.
- Nieograniczona reguła sudo do `qpdf` z możliwością działania jako root może ujawnić uprzywilejowany plik przez załączniki PDF: qpdf 10.2 i nowsze obsługuje `--empty` oraz `--add-attachment file ... --` z wyjściowym plikiem PDF. Jeśli uprzywilejowany proces może odczytać wybrane źródło i zapisać PDF w ścieżce dostępnej dla użytkownika, wynik może zawierać bajty źródła. Zanim uznasz ujawnienie pliku za możliwe, sprawdź skuteczne argumenty sudo i wykluczenia, wersję qpdf, dostęp do źródła i ścieżkę wyjściową. Odczyt klucza SSH roota jest przydatny do logowania tylko wtedy, gdy klucz jest ważny, a uwierzytelnianie SSH roota dozwolone. Zobacz [opcje załączników qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Ponowne użycie znacznika czasu sudo zależy od polityki bufora, właściciela, terminala/sesji i uprawnień. [Przewodnik po eskalacji uprawnień](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) opisuje kontrole.
- `doas` ma własne reguły i konfigurację. Sprawdź dozwolone polecenia i zapisywalne ścieżki konfiguracji zgodnie z opisem w [sekcji doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Narzędzia budowania i pakietów uruchamiane przez sudo

Nieograniczone uprawnienie sudo do Foundry `forge` może mieć znaczenie nawet wtedy, gdy tożsamość RunAs należy do innego użytkownika niebędącego rootem. Opcje kompilatora, takie jak `--use`, mogą wskazać lokalny plik wykonywalny, a `forge flatten -o` wybiera plik wyjściowy. Zanim uznasz uprawnienie za możliwe do wykorzystania, sprawdź zainstalowaną wersję Forge, dokładne argumenty sudo, dostępne ścieżki projektu i kompilatora, uprawnienia do pliku wyjściowego oraz skuteczne środowisko. Względny plik wykonywalny helpera znaleziony przez `PATH` to ścieżka zależna od wersji i środowiska, a nie właściwość, którą należy zakładać dla każdej kompilacji Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Nieograniczone uprawnienie sudo do `pacman` z możliwością działania jako root dopuszcza więcej niż samo sprawdzanie pakietów: `-U` przyjmuje pakiet lokalny, pakiety mogą zawierać skrypty instalacyjne, a `--hookdir` wybiera inny katalog hooków. Przed testowaniem sprawdź skuteczną regułę sudo, ograniczenia argumentów i wykluczenia; pasywna inwentaryzacja nie wymaga instalowania pakietu ani uruchamiania hooka.<sup>[[25]](#references)[[26]](#references)</sup>

Stały wrapper powłoki sudo może też instalować nazwaną zależność npm, a następnie uruchamiać aplikację Node. Sprawdź dokładną regułę RunAs, czy pakiet jest już zainstalowany, skuteczne wartości `HOME` i `npm userconfig`, konfigurację projektu lub nadpisania z wiersza poleceń oraz to, czy użytkownik o niższych uprawnieniach kontroluje rejestr lub pakiet pobierany pod tą nazwą. [npm dokumentuje wyszukiwanie plików `.npmrc` na poziomie użytkownika i projektu](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); zachowanie `HOME` przez sudo zależy od zainstalowanej polityki i dystrybucji, więc zapisywalny plik `.npmrc` użytkownika może być odczytywany przez uprzywilejowany proces npm albo nie. Jeśli świeżo zainstalowany pakiet zostanie zaimportowany przez uprzywilejowaną aplikację, jego kod modułu może zostać uruchomiony z tożsamością tej aplikacji. Skrypty uruchamiane podczas instalacji to osobna ścieżka, zależna od wersji i konfiguracji; [npm opisuje ich cykl życia i obsługę użytkowników](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ścieżka `.npmrc` lub sama linia `npm install` to jedynie wskazówka. Podczas pasywnej inwentaryzacji sprawdź regułę, krótki wrapper, ścieżki konfiguracji i pochodzenie pakietu bez instalowania pakietu ani uruchamiania aplikacji.

Uprawnienie do `pip` lub `pip3 download` z możliwością działania jako root jest również wskazówką do analizy procesu budowania pakietu, jeśli argumenty pozwalają wybrać niezaufaną dystrybucję źródłową — nawet gdy wzorzec URL ogranicza ją do lokalnej usługi i sufiksu `.tar.gz`. `pip download` przyjmuje URL-e archiwów i rozwiązuje metadane pakietów; przygotowanie sdist może uruchomić backend budowania lub starszy kod `setup.py`, zanim archiwum zostanie jedynie zapisane. Potwierdź dokładną regułę RunAs i argumentów sudo, czy użytkownik może opublikować lub podmienić wybrane archiwum oraz czy ta wersja pip rzeczywiście przygotowuje jego metadane. Stałe, zaufane archiwum lub wheel nie dowodzą istnienia tej ścieżki. Podczas pasywnej inwentaryzacji nie pobieraj ani nie buduj niezaufanego pakietu. Zobacz dokumentację pip dotyczącą [polecenia download](https://pip.pypa.io/en/stable/cli/pip_download/), [interfejsu systemu budowania](https://pip.pypa.io/en/stable/reference/build-system/) i [bezpiecznej instalacji](https://pip.pypa.io/en/stable/topics/secure-installs/).

Reguła sudo zezwalająca na `pip install` z wybraną przez użytkownika lokalną ścieżką projektu tworzy bardziej bezpośrednią granicę budowania. [pip akceptuje lokalne katalogi projektów](https://pip.pypa.io/en/stable/topics/local-project-installs/) i wywołuje ich system budowania; [backend budowania uruchamia kontrolowane przez projekt hooki](https://pip.pypa.io/en/stable/reference/build-system/). Zanim uznasz regułę za umożliwiającą uprzywilejowane wykonanie kodu, potwierdź skuteczną tożsamość RunAs, dokładne ograniczenia i zakazy argumentów, kontrolę nad wybranym projektem oraz zachowanie zainstalowanego pip/backendu. Stały, zaufany projekt lub reguła wykluczająca ścieżki wybrane przez użytkownika nie ustanawia tej ścieżki. Przejrzyj regułę i metadane projektu bez instalowania pakietu podczas pasywnej inwentaryzacji.

Nieograniczone uprawnienie sudo do `easy_install` jest podobną wskazówką związaną z przestarzałym mechanizmem budowania pakietów. [Setuptools dokumentuje](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), że Easy Install akceptuje lokalny katalog projektu i buduje dystrybucje źródłowe; projekt kontrolowany przez użytkownika może uruchomić w tym procesie swój `setup.py` z tożsamością sudo. Potwierdź skuteczne konto RunAs, dokładne ograniczenia polecenia i argumentów (w tym późniejsze zakazy), kontrolę nad wybranym projektem oraz zachowanie zainstalowanego narzędzia. Stały, zaufany projekt lub polityka niedopuszczająca źródła wybranego przez użytkownika nie ustanawia tej ścieżki. Podczas inwentaryzacji sprawdź regułę i metadane projektu bez instalowania pakietu.

Wrapper Pythona dozwolony przez sudo, który używa `setuptools.package_index.PackageIndex.download` z URL-em wybranym przez użytkownika, wymaga innej analizy niż `pip download`: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) opisuje przypadek, w którym nazwa pliku wyprowadzona z URL-a mogła wydostać się poza zamierzony katalog pobierania i zapisać plik z uprawnieniami procesu w podatnych wydaniach starszych niż 78.1.1. Potwierdź skuteczną tożsamość sudo RunAs i regułę argumentów, czy wrapper przekazuje URL użytkownika do dokładnie tego API, zainstalowaną wersję lub poprawkę dostawcy oraz miejsce, do którego wskazuje wynikowa ścieżka. Sam numer wersji lub zapisywalny katalog pobierania nie dowodzą możliwości dowolnego zapisu. Przejrzyj krótki wrapper i metadane pakietu bez pobierania URL-a ani zapisywania pliku podczas inwentaryzacji.

Wrapper budowania dozwolony przez sudo, który przekazuje PyInstaller wybrany przez użytkownika plik `.spec`, wymaga podobnej analizy granicy zaufania. Plik spec PyInstaller to wykonywalny Python interpretowany podczas **budowania**, a jego wpisy `datas` mogą dołączać do artefaktu pliki dostępne dla tożsamości procesu budującego. Potwierdź dokładnego użytkownika RunAs, reguły argumentów i zakazów sudo, obsługę ścieżek i gałęzi przez wrapper, kontrolę nad wybranym plikiem spec oraz dostęp do wynikowego artefaktu. Samo zezwolenie na plik wejściowy `.py` lub znalezienie PyInstaller w systemie nie dowodzi kontroli nad plikiem spec ani uprzywilejowanego wykonania. Pasywna analiza powinna odczytywać tylko ograniczony fragment wrappera i metadane; nie powinna uruchamiać budowania. Zobacz [dokumentację plików spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loadery presetów i pluginów uruchamiane przez sudo

Narzędzia Pythona przyjmujące wybrany przez użytkownika preset lub katalog pluginów mogą importować kod z uprawnieniami przyznanymi przez sudo. Na przykład BBOT akceptuje preset przez `-p`, a jego [dokumentacja własnych modułów](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) opisuje wpisy `module_dirs` wybierające dodatkowe katalogi modułów Pythona. Jeśli skuteczna reguła sudo zezwala na preset wybrany przez użytkownika, a użytkownik kontroluje moduł w wybranym katalogu, import może uruchomić kod jako uprzywilejowany użytkownik, potencjalnie jeszcze przed odrzuceniem nieprawidłowego modułu przez narzędzie. Sprawdź zainstalowaną wersję, dokładną politykę RunAs i argumentów sudo oraz właścicieli presetu i ścieżek modułów, nie wczytując modułu podczas inwentaryzacji.

### Narzędzie wiersza poleceń Backdrop uruchamiane przez sudo

[Bee](https://github.com/backdrop-contrib/bee) to narzędzie wiersza poleceń PHP dla Backdrop CMS. Jego polecenia `eval` (`php-eval`) i `php-script` mogą uruchamiać PHP dostarczony przez użytkownika. Reguła sudo zezwalająca na wykonywanie Bee jako root z nieograniczonymi argumentami może więc umożliwić wykonanie kodu jako root, jeśli Bee może zainicjować instalację Backdrop. Uruchom je z katalogu witryny lub wybierz witrynę za pomocą globalnej opcji `--root=<directory>`; samo znalezienie Bee lub pliku Backdrop `settings.php` nie dowodzi uprawnień sudo, działającej witryny ani udanej inicjalizacji. Przed testowaniem sprawdź skuteczną regułę sudo, ewentualne wykluczenia poleceń, tożsamość pliku wykonywalnego oraz dostęp do witryny. Podczas pasywnej inwentaryzacji sprawdzaj regułę i ścieżki plików bez uruchamiania Bee. Zobacz [dziennik zmian poleceń Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md), który opisuje dodanie poleceń PHP.

### Serwery terminalowe uruchamiane przez sudo

`mosh-server` uruchamia interaktywny serwer terminalowy jako użytkownik wywołujący. Wybiera wysoki port UDP i klucz sesji, przekazuje oba użytkownikowi i zwykle po nawiązaniu połączenia przez klienta uruchamia powłokę logowania tego użytkownika. Nieograniczone uprawnienie sudo do `mosh-server` z możliwością działania jako root jest więc kandydatem do analizy pod kątem powłoki, mimo że samo polecenie serwera odłącza się od terminala. Sprawdź skuteczną tożsamość RunAs, dozwolone argumenty i wykluczenia, zainstalowany plik binarny, powłokę, dostępność klienta i dostęp UDP. Pasywna inwentaryzacja powinna sprawdzić regułę sudo bez uruchamiania serwera ani wyświetlania aktywnego klucza sesji. Zobacz [podręcznik serwera Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) i [notatki projektowe upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Uprzywilejowane wrappery kopii zapasowych modyfikujące plik zadań użytkownika

Skrypt powłoki uruchamiany jako root może przyjmować plik zadań wybrany przez użytkownika, usuwać `../` ze ścieżek źródłowych, sprawdzać, czy każda uzyskana ścieżka zaczyna się od dozwolonego katalogu, modyfikować plik zadań, a następnie przekazywać programowi kopii zapasowych jego *ścieżkę*. Przeanalizuj przekształconą ścieżkę po pełnym rozstrzygnięciu kanonicznym: pojedyncze zastąpienie tekstu może ujawnić nową sekwencję przejścia do katalogu nadrzędnego, którą zaakceptuje leksykalne sprawdzenie prefiksu. Sprawdź też, czy program kopii zapasowych odczytuje przekształcone dane z pamięci, czy ponownie otwiera plik. Jeśli otwiera go ponownie, nieudana modyfikacja może pozostawić oryginalne dane wejściowe.

W Linuksie `fs.protected_regular` może blokować zapis `O_CREAT` do zwykłego pliku należącego do innego użytkownika w katalogu z bitem sticky, do którego każdy może zapisywać. To zabezpieczenie, ale skrypt powłoki ignorujący błąd zapisu może mimo to kontynuować pracę na pierwotnym pliku zadań. Potwierdź to ustawienie, właściciela pliku i katalogu oraz to, czy wrapper przerywa działanie po błędzie. Taka ścieżka jest kandydatem do ujawnienia plików tylko wtedy, gdy skuteczna reguła sudo pozwala uruchomić wrapper jako uprzywilejowany użytkownik, użytkownik kontroluje dane wejściowe zadania i czytelne miejsce docelowe kopii oraz narzędzie kopii rzeczywiście uwzględnia chronione źródła. Podczas inwentaryzacji sprawdź te warunki bez uruchamiania kopii zapasowej.

### Wildcardy argumentów w uprzywilejowanych narzędziach do przechwytywania pakietów

W regule sudo dla `tcpdump` `*` we **wzorcu argumentów** może dopasować białe znaki i ukośniki, więc ograniczenie przypominające ścieżkę może nadal dopuszczać dodatkowy tekst opcji. Różni się to od wildcarda w ścieżce pliku wykonywalnego polecenia; sprawdź pełną regułę RunAs i wszelkie późniejsze zakazy. Jeśli można wstrzyknąć opcje, dozwolone wywołanie i semantyka opcji zainstalowanego [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) określają, czy `-F`, `-V`, `-r`, `-w` lub `-Z` zapewnia przydatną możliwość odczytu/zapisu. `-V` odczytuje listę nazw plików przechwyconych pakietów, a nie dowolny plik w ogólnym zrzucie. AppArmor lub inna polityka MAC może blokować dostęp do plików nawet wtedy, gdy sudo zezwala na polecenie; sam plik profilu na dysku nie dowodzi, że profil jest załadowany i wymuszany. Przed wyciągnięciem wniosków sprawdź autoryzację i politykę pasywnie. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) opisuje różnicę dotyczącą wildcardów.

Reguła sudo z możliwością działania jako root, która wymienia wyłącznie plik wykonywalny `tcpdump` i nie ogranicza argumentów, również wymaga sprawdzenia. [Podręcznik tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) opisuje `-z` jako polecenie uruchamiane po rotacji, gdy `-C` lub `-G` rotuje zapisany przechwyt; `-Z` lub ustawienie domyślne z czasu kompilacji mogą obniżyć uprawnienia przed uruchomieniem tego polecenia. Zanim uznasz regułę za ścieżkę eskalacji, zweryfikuj skuteczną regułę sudo, zainstalowaną kompilację, zachowanie związane z obniżaniem uprawnień oraz to, czy może dojść do rotacji. Wyróżniona reguła to kandydat, a nie dowód wykonania polecenia jako root.

### Wrappery Nmap uruchamiane przez sudo

Jeśli dozwolona przez sudo ścieżka `nmap` jest wrapperem powłoki, sprawdź dokładnie dozwoloną ścieżkę i każdą przekazywaną opcję. Blokowanie znanej pisowni `--script` nie musi blokować wczytywania kodu NSE: Nmap [`--datadir`](https://nmap.org/book/man-misc-options.html) wybiera pliki danych, a NSE [wczytuje `nse_main.lua`](https://nmap.org/book/nse-implementation.html) z wybranego katalogu danych po włączeniu skryptów. Niektóre zainstalowane kompilacje akceptują też alternatywne zapisy długich opcji, więc porównaj ograniczenia z rzeczywistym parserem danego pliku binarnego. [`--excludefile`](https://nmap.org/book/man-target-specification.html) stanowi osobną powierzchnię odczytu plików; błędy parsera mogą ujawnić tekst. Podczas inwentaryzacji sprawdź skuteczną regułę sudo, logikę wrappera, wersję Nmap, kontrolę nad katalogiem i politykę MAC, nie uruchamiając skanów.

### Hooki Mercurial pull uruchamiane przez sudo

Stałe źródło w `sudo hg pull /fixed/source` nadal pozostawia **repozytorium odbierające** wybrane przez bieżący katalog roboczy, chyba że polecenie ustala je przez `-R`. Kontrolowane przez użytkownika repozytorium odbierające może definiować hooki w `.hg/hgrc`, a hook może zostać uruchomiony jako użytkownik sudo RunAs. [Mercurial ignoruje konfigurację repozytorium należącą do niezaufanego użytkownika lub grupy](https://mercurial-scm.org/help/topics/config), więc zanim uznasz to za wykonanie kodu, sprawdź zaufanych użytkowników/grupy konta RunAs i dokładny katalog roboczy. Do pasywnej analizy wystarczy odczytać politykę i konfigurację; podczas inwentaryzacji nie wykonuj pull ani hooka.

### Hooki Git pull uruchamiane przez sudo

W przypadku dokładnego uprawnienia `sudo git pull` z możliwością działania jako root sprawdź również **repozytorium odbierające** wybrane przez katalog roboczy. Repozytorium należące do użytkownika może zawierać wykonywalny hook `post-merge`, który uruchamia się z tożsamością procesu Git, gdy pull faktycznie przeprowadzi udane scalanie; [Git dokumentuje ten hook](https://git-scm.com/docs/githooks) i [zachowanie pull w przypadku scalania lub rebase](https://git-scm.com/docs/git-pull). Sprawdź skuteczną regułę sudo i CWD, aktywną ścieżkę hooka i jego uprawnienia oraz to, czy możliwe jest scalenie nowych commitów. Nieudany pull, brak zmian lub pull wykonujący wyłącznie rebase nie ustanawia tej ścieżki hooka. Podczas analizy sprawdź politykę i metadane repozytorium bez uruchamiania uprzywilejowanego pull.

### Kopie archiwizacyjne rsync uruchamiane przez sudo

Dla `sudo rsync -a ... /writable/source/* /fixed/destination/` `*` we **wzorcu argumentów sudoers** może dopasować białe znaki i dopuścić dodatkową opcję między źródłem a miejscem docelowym. Różni się to od rozwijania nazw plików przez powłokę. Jeśli użytkownik może wypełniać źródło, a uprzywilejowany proces rsync może zapisywać w miejscu docelowym, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) może zażądać uprzywilejowanej zmiany właściciela, a tryb archiwizacji zachowuje bity uprawnień, co może utworzyć plik SetUID należący do wskazanego właściciela. Sprawdź dokładną [semantykę wildcardów sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), wersję rsync, późniejsze zakazy, `nosuid` systemu plików i politykę MAC. Pasująca reguła jest kandydatem do analizy, a nie dowodem udanej eskalacji uprawnień.

### Eksport reguł filtrowania pakietów uruchamiany przez sudo

Nieograniczone uprawnienie sudo do `iptables` i `iptables-save` z możliwością działania jako root (lub odpowiadającej im pary `ip6tables`) wymaga analizy możliwości zapisu do plików. Dopasowanie `comment` akceptuje tekst reguły wybrany przez użytkownika, a `iptables-save -f` zapisuje serializowany zestaw reguł w wybranej ścieżce.<sup>[[20]](#references)[[21]](#references)</sup> Użyteczny ładunek zależy od tego, jak zainstalowany backend serializuje komentarze oraz czy plik docelowy akceptuje inne linie eksportu; samo `iptables-save` nie zapewnia dowolnej treści. Sprawdź dokładną tożsamość sudo RunAs, argumenty i wykluczenia, dostępne rozszerzenie dopasowania, backend i uprawnienia do miejsca docelowego. Podczas inwentaryzacji sprawdź uprawnienie bez zmieniania reguł zapory ani zapisywania pliku.

### Uprzywilejowany katalog logów Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) dotyczyło wydań Below starszych niż 0.9.0, które tworzyły katalog `/var/log/below` z uprawnieniami do zapisu dla wszystkich. Jeśli usługa lub dozwolone polecenie sudo uruchamia podatną wersję jako root, użytkownik mogący zapisywać i przeszukiwać katalog logów bez bitu sticky może być w stanie podmienić wpis logu na symlink przed otwarciem go przez uprzywilejowany proces. Sprawdź status poprawki zainstalowanego pakietu, dokładną ścieżkę uprzywilejowanego wykonania, skuteczne uprawnienia do katalogu, bit sticky i ACL oraz metadane `/var/log/below/error_root.log`. Sam katalog zapisywalny dla wszystkich lub reguła sudo nie ustanawiają pełnego łańcucha. Katalog z bitem sticky lub poprawka dostawcy zmienia ocenę. Pasywna inwentaryzacja powinna sprawdzać wyłącznie metadane; nie wymaga tworzenia linku ani uruchamiania uprzywilejowanego programu.

### Uprzywilejowane zbieranie pakietu pomocy technicznej z zapisywalnych danych wejściowych

Skrypt profilu pomocy technicznej dozwolony przez `sudo` może odczytywać ustalone ścieżki logów jako root i kopiować ich zawartość do archiwum profilu. Sprawdź, czy sam skrypt odczytuje pliki, a następnie czy użytkownik może podmienić źródłową ścieżkę lub dowolny wpis katalogu nadrzędnego na symlink. Jeśli uprzywilejowany odczyt podąży za linkiem, a uzyskane archiwum będzie czytelne dla użytkownika, może dojść do ujawnienia chronionego pliku. Muszą istnieć wszystkie elementy: uprawnienie sudo, zapisywalna ścieżka źródłowa, uprzywilejowany odczyt i czytelny wynik; sam zapisywalny log lub nazwa profilu nie wystarczą. Podczas inwentaryzacji sprawdź skuteczne uprawnienia i metadane linków bez podmieniania plików ani generowania profilu. [Wskazówki pomocy technicznej Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) opisują uruchamiany jako root skrypt profilu i archiwum wyjściowe, pokazując, dlaczego takie pakiety powinny mieć ograniczone dane wejściowe i dostęp do wyników.

### Skrypty przywracania archiwum Pythona uruchamiane jako root

Nawet ściśle ograniczona reguła sudo do skryptu przywracania Pythona wymaga sprawdzenia danych wejściowych archiwum. Jeśli użytkownik może wybrać lub podmienić archiwum, a skrypt rozpakowuje je jako root za pomocą `tarfile.extractall(filter="data")`, przed zaufaniem temu filtrowi sprawdź aktualizacje bezpieczeństwa interpretera. CPython naprawił kilka obejść filtrów symlinków i hardlinków, w tym CVE-2025-4517, w wersjach 3.9.23, 3.10.18, 3.11.13, 3.12.11 i 3.13.4. Poprawki mogą być przeniesione do wcześniejszych wersji przez dystrybucję, więc wyświetlana wersja interpretera sama w sobie nie dowodzi podatności.<sup>[[16]](#references)[[17]](#references)</sup>

W ramach pasywnej analizy odczytaj dokładne polecenie sudo i skrypt, ustal, który argument wybiera archiwum, oraz sprawdź, czy bieżący użytkownik może zapisywać archiwum lub katalog, który je zawiera. Osobno potwierdź poprawkę dostawcy i katalog rozpakowywania; `filter="data"` nie zapewnia bezpieczeństwa w przypadku każdego niezaufanego archiwum.<sup>[[16]](#references)[[17]](#references)</sup>

### Loadery modeli uczenia maszynowego uruchamiane przez sudo

Reguła sudo pozwalająca wybrać plik `.pt`, `.pth` lub `.ckpt` wymaga analizy, jeśli uprzywilejowany skrypt przekazuje go do [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` lub innego loadera opartego na pickle. Sprawdź skuteczną regułę RunAs, czy użytkownik może utworzyć lub podmienić wybrany model oraz rzeczywisty przepływ argumentów przez dowolny wrapper powłoki do helpera Pythona. Rozszerzenie `.pth` oznacza też niezwiązane z tym pliki konfiguracyjne witryny Pythona, więc samo rozszerzenie nie dowodzi ładowania modelu. Skan archiwum ani statyczny skan pickle nie dowodzą, że późniejsze ładowanie jest bezpieczne; sprawdź zależne od wersji zachowanie [`weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) loadera i ewentualną listę dozwolonych typów. Zobacz [uwagi o pickle w ML i Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). Pasywna inwentaryzacja nigdy nie powinna ładować ani rozpakowywać modelu.

### Parsowanie wyrażeń w danych przechowywanych, uruchamiane przez sudo

Stały skrypt Pythona uruchamiany jako root przez sudo może nadal interpretować tekst, który użytkownik o niższych uprawnieniach może zapisać w bazie danych aplikacji. W TensorFlow wywołanie `preprocess_input_exprs_arg_string(value, safe=False)` wybiera ścieżkę `eval`; [ostrzeżenie TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) opisuje niebezpieczny parser i poprawkę jego użytkownika wiersza poleceń. Jawne wywołanie `safe=False` przez aplikację wymaga osobnej analizy, nawet jeśli ten użytkownik wiersza poleceń został poprawiony. Sprawdź skuteczną regułę sudo, kto może modyfikować dokładny wpis danych, czy filtrowanie lub punktowanie pozwala temu wpisowi dotrzeć do wywołania oraz zachowanie zainstalowanej funkcji. Sama wersja TensorFlow, uprawnienie sudo lub zakodowany na stałe plik modelu nie dowodzą istnienia łańcucha. Przeanalizuj skrypt i przepływ danych pasywnie; podczas inwentaryzacji nie uruchamiaj uprzywilejowanego helpera ani nie przesyłaj testowych wyrażeń.

### Konfiguracja needrestart dozwolona przez sudo

`needrestart -c` wczytuje wybrany przez użytkownika plik konfiguracyjny Perla i interpretuje jego zawartość. Jeśli `sudo -l` pozwala uruchamiać `needrestart` jako root z argumentami dopuszczającymi `-c`, a użytkownik może wskazać czytelny plik konfiguracyjny w zapisywalnej lokalizacji, to uprawnienie może prowadzić do wykonania kodu jako root. Sprawdź dokładną regułę sudo RunAs i argumentów; reguła zezwalająca wyłącznie na ustaloną listę argumentów może blokować tę ścieżkę. Nie należy tego mylić z podatnościami `needrestart` związanymi ze skanowaniem interpreterów: aktualizacja pakietu lub wyłączenie `interpscan` nie zabezpiecza nieograniczonego uprawnienia roota do `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importy Pythona uruchamiane przez sudo na koncie innego użytkownika

Ustalony punkt wejścia Pythona może nadal importować moduł, który użytkownik może zmieniać lub podmieniać, także wtedy, gdy sudo uruchamia skrypt jako **konto niebędące rootem**. W przypadku dosłownego `from utils import status` sprawdź lokalne `utils/__init__.py` i `utils/status.py`, a także uprawnienia do katalogu pakietu. Zanim uznasz zapisywalny plik za ścieżkę wykonania, potwierdź ścieżkę importu skryptu, dokładne dozwolone argumenty sudo oraz to, czy odpowiednia operacja dociera do tego importu. Podczas inwentaryzacji sprawdzaj pliki i uprawnienia bez importowania ani uruchamiania skryptu.<sup>[[2]](#references)[[3]](#references)</sup>

Dokładna reguła sudo dla `python3 /absolute/script.py` wymaga jedynie, by skrypt był czytelny; nie musi być wykonywalny ani mieć shebanga. Sprawdź też **brakujące** moduły lokalne: jeśli skrypt importuje moduł, którego plik można utworzyć w katalogu skryptu zapisywalnym przez użytkownika, Python może wczytać ten plik z tożsamością RunAs. Potwierdź skuteczną regułę sudo, rzeczywistą [ścieżkę wyszukiwania modułów](https://docs.python.org/3/library/sys_path_init.html) interpretera, czy moduł jest wbudowany lub zamrożony oraz czy do importu dochodzi. Bezpośrednia reguła sudo do skryptu ma inne wymagania dotyczące bitu wykonywania i shebanga. Oddzielna analiza przepływu argumentów jest też potrzebna dla wrappera, który dołącza tokeny dostarczone przez użytkownika po `sudo -u account`: dodatkowe `-u` w tych tokenach ma znaczenie tylko wtedy, gdy wywołana polityka sudo dopuszcza wynikową tożsamość. Same statyczne ciągi nie dowodzą żadnej z tych ścieżek.

### Apache uruchamiany przez sudo z konfiguracją kontrolowaną przez użytkownika

Jeśli reguła sudo zezwala na uprzywilejowane wywołanie `apachectl`, `apache2ctl` lub `httpd` z plikiem konfiguracyjnym `-f` kontrolowanym przez użytkownika, sprawdź uprawnienia do tego pliku i jego katalogu nadrzędnego. Dyrektywa Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) przyjmuje nazwę modułu, a następnie **nazwę pliku modułu**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) również wczytuje plik. [`Include` i `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) mogą rozszerzać konfigurację lub ujawniać zawartość plików w komunikatach o błędach. Własny wrapper może walidować te ścieżki, obniżać uprawnienia lub ograniczać argumenty, więc sama zapisywalna konfiguracja jest kandydatem do analizy, a nie dowodem wykonania kodu. Przed wyciągnięciem wniosków sprawdź kanonizację ścieżki, symlinki i parsowanie dyrektyw.

### nginx uruchamiany przez sudo z konfiguracją kontrolowaną przez użytkownika

Nieograniczona reguła sudo dla `nginx` z możliwością działania jako root może pozwalać użyć [`-c` do wybrania innej konfiguracji](https://nginx.org/en/docs/switches.html). Sprawdź dokładne argumenty i wykluczenia sudo, czy użytkownik może dostarczyć konfigurację oraz czy wynikowy proces master lub workery zachowują dostęp do chronionych ścieżek. Wybrana dyrektywa `root` wraz z `autoindex` może udostępniać pliki przez nowy listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) może zapewnić uprzywilejowaną ścieżkę zapisu plików, ale moduł DAV nie jest domyślnie budowany, więc trzeba sprawdzić jego obecność, osiągalność listenera, uprawnienia do plików i zachowanie plików tymczasowych. Dyrektywa [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) może też wskazywać wybrany plik; zapis logów do wrażliwego pliku konfiguracyjnego, takiego jak `/etc/ld.so.preload`, wymaga skutecznego uprzywilejowanego zapisu i kontrolowanego rekordu logu, zanim stanie się ścieżką eskalacji. Wyróżnienie pliku wykonywalnego w `sudo -l` to wskazówka, a nie dowód, że którakolwiek z tych ścieżek działa. Pasywna inwentaryzacja nie powinna uruchamiać nginx ani zmieniać jego konfiguracji.

### Porównywanie wzorców w uprzywilejowanych promptach Bash

Jeśli skrypt Bash dozwolony przez sudo odczytuje wartość od użytkownika i sprawdza ją za pomocą `[[ "$expected" == $entered ]]`, Bash interpretuje nieujęty w cudzysłów prawy operand jako wzorzec. Wildcard może więc spełnić warunek bez znajomości oczekiwanej wartości. Ujęcie operandu w cudzysłowy (`[[ "$expected" == "$entered" ]]`) zapewnia dosłowne porównanie ciągów. Sprawdź dokładną regułę sudo, czy można dotrzeć do promptu i co skrypt robi po porównaniu; sama składnia nie dowodzi istnienia możliwej do wykorzystania ścieżki. Podczas inwentaryzacji nie wyświetlaj oczekiwanej wartości. Zobacz [dokumentację konstrukcji warunkowych Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpery uruchamiane przez sudo, które pobierają i wykonują plik

Nieograniczone uprawnienie sudo do własnego helpera z możliwością działania jako root wymaga analizy przepływu danych, jeśli helper przyjmuje URL wybrany przez użytkownika, zapisuje odpowiedź na dysku, a później uruchamia ten plik przez interpreter lub powłokę. [Sudoers dopuszcza dowolne argumenty, gdy wpis polecenia ich nie określa](https://man7.org/linux/man-pages/man5/sudoers.5.html); stała ścieżka pliku wykonywalnego nie ogranicza tego, co mogą wskazywać argumenty. Potwierdź rzeczywistą walidację URL-a, ścieżkę wyjściową, warunek powodzenia i późniejsze wykonanie w zainstalowanym helperze. Sam import libcurl lub drukowalny ciąg nie dowodzi istnienia tego łańcucha.

Nawet stała nazwa pliku wyjściowego może zostać podmieniona między zapisem a wykonaniem, jeśli helper używa **ścieżki względnej w katalogu roboczym kontrolowanym przez użytkownika**. Zmiana nazwy lub podmiana pliku należącego do roota zależy od uprawnień do zapisu i wyszukiwania w katalogu oraz ewentualnych ograniczeń bitu sticky, a nie tylko od trybu pliku; zobacz [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Sprawdź, czy helper później ponownie otwiera ścieżkę, czy korzysta z już otwartego deskryptora oraz czy przed zapisem przechodzi do zaufanego katalogu. Sprawdzaj politykę sudo, helper i metadane katalogu pasywnie; podczas inwentaryzacji nie wywołuj uprzywilejowanego pobierania ani nie przeprowadzaj wyścigu.

Helper pobierania uruchamiany przez sudo jako root może też umożliwiać **wstrzyknięcie argumentu**, jeśli buduje ciąg polecenia Bash, taki jak `curl <dane użytkownika> -o <stałe wyjście>`. Filtr odrzucający białe znaki nadal pozostawia [rozwijanie nawiasów klamrowych przez Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): nieujęte w cudzysłów elementy rozdzielone przecinkami mogą stać się osobnymi argumentami curl. Jeśli dane wejściowe trafiają do curl przed stałym `-o`, użytkownik może dostarczyć opcję wyjściową wybierającą miejsce docelowe pierwszego URL-a z tożsamością helpera; [curl wiąże opcje wyjściowe z URL-ami w kolejności](https://curl.se/docs/manpage.html#-o). Potwierdź dokładną powłokę, cytowanie, walidację danych, skuteczną regułę sudo, kolejność argumentów curl i obsługiwane schematy URL oraz to, czy użytkownik kontroluje pobierane bajty lub może odczytać wynik. Plik wykonywalny spakowany przez PyInstaller może zawierać logikę aplikacji Python, ale sam znacznik pakowania lub ciąg `curl` nie dowodzi takiego przepływu danych. Jeśli jest to autoryzowane, przejrzyj ograniczoną kopię offline; standardowa inwentaryzacja nie powinna uruchamiać helpera ani pobierać danych wybranych przez atakującego.

Skrypt powłoki uruchamiany przez sudo jako root, który wywołuje [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), jedynie wybiera nieużywaną nazwę; **nie tworzy pliku**. Jeśli skrypt później tworzy plik pod tą nazwą w katalogu, na który może wpływać inny użytkownik, ponownie go otwiera i dopisuje jego zawartość do chronionego miejsca docelowego, takiego jak `authorized_keys` roota, należy sprawdzić ryzyko wyścigu dotyczącego pliku tymczasowego. Potwierdź dokładną regułę sudo, właściciela katalogu i pliku, kolejność tworzenia i ponownego otwierania, zabezpieczenia jądra oraz to, czy uprzywilejowany zapis rzeczywiście wykorzystuje bajty kontrolowane przez atakującego. Sam ciąg z `mktemp -u` lub zapisywalny `/tmp` nie dowodzą istnienia wyścigu. Podczas inwentaryzacji sprawdzaj skrypt i metadane ścieżek bez jego uruchamiania ani przeprowadzania wyścigu dotyczącego pliku tymczasowego.

## Uwagi dotyczące obrony

- Unikaj przyznawania przez sudo dostępu do interpreterów i interaktywnych edytorów.<sup>[[1]](#references)</sup>
- Nie przyznawaj nieograniczonych uprawnień do ogólnych narzędzi zapisu plików, takich jak `tee`. Używaj wrappera należącego do roota, który wybiera stałe miejsce docelowe i odrzuca ścieżki kontrolowane przez użytkownika.<sup>[[2]](#references)</sup>
- Preferuj stałe wrappery należące do roota, wykonujące jedną ściśle określoną czynność administracyjną.<sup>[[1]](#references)[[2]](#references)</sup>
- Jeśli interpreter jest niezbędny, ogranicz dokładną ścieżkę skryptu i zablokuj argumenty kontrolowane przez użytkownika, zapisywalne moduły, `PYTHONPATH` i niebezpieczne zachowywanie środowiska.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Jeśli edycja plików jest konieczna, ogranicz dokładną ścieżkę pliku i rozważ `sudoedit` z poprawionymi wersjami sudo oraz restrykcyjną obsługą środowiska.<sup>[[1]](#references)[[2]](#references)</sup>
- Sprawdzaj `SETENV`, `env_keep`, zapisywalne katalogi robocze, zapisywalne ścieżki modułów/importu, `NOEXEC`, `use_pty` i logowanie, ale nie traktuj ich jako kompletnej piaskownicy.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
