## Інтерпретатори, дозволені через Sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерпретатор від імені root, вважайте це прямим виконанням коду. Інтерпретатори призначені для виконання довільного коду, тому правило, яке дозволяє запускати `python3`, `perl`, `ruby`, `lua`, `node` або подібні бінарні файли, зазвичай еквівалентне виконанню команд від імені root, якщо аргументи не обмежені та не перевіряються належним чином.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Типовий порядок перевірки: спочатку перегляньте привілеї користувача, а потім виконайте інструкцію Python за допомогою параметра `-c` інтерпретатора.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Інші приклади інтерпретаторів наведено нижче; у документації до перелічених інтерпретаторів описано виконання вбудованого коду або API дочірніх процесів.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Точний шлях має значення. Якщо правило sudo дозволяє `/usr/bin/python3`, під час перевірки використовуйте саме цей шлях.<sup>[[2]](#references)</sup>

Шаблон glob для виконуваного файла sudo, наприклад `/usr/bin/python*`, може також дозволити Python 2 для скрипту, написаного для Python 3. Якщо скрипт викликає `input()` із текстом, контрольованим користувачем, [Python 2 обчислює цей текст як вираз](https://docs.python.org/2/library/functions.html#input); явний виклик інтерпретатора має пріоритет над shebang скрипту. Перш ніж вважати це шляхом до виконання коду, перевірте встановлені бінарні файли, що відповідають шаблону, ефективну політику RunAs та аргументів, відмови в доступі й можливість передати дані до `input()`.

Фіксований шлях до скрипту в правилі sudo із можливістю запуску від root не обмежує команди, які виконує скрипт. Якщо Bash-обгортка доступна для читання, перевірте, чи використовує її перша виконувана команда неекранований позиційний параметр на кшталт `$1` як **слово команди**, тоді як sudo дозволяє користувачу самостійно вибирати аргументи. Підтвердьте ефективну ідентичність RunAs, політику пароля й аргументів, подальші відмови в доступі та фактичну гілку скрипту; `NOEXEC`, фіксований безпечний список аргументів або обгортка, що перевіряє команду, можуть змінити результат. Під час розвідки статично перевірте короткий скрипт, а не запускайте його з тестовою командою.

Правило sudo без обмежень для `dotnet` із можливістю запуску від root також варто перевірити з погляду інтерпретатора. Якщо встановлено .NET SDK, [`dotnet fsi` запускає код F# в інтерактивному режимі або зі скрипту](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), а [`dotnet run` запускає проєкт з вихідного коду](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Спершу підтвердьте ефективну ідентичність RunAs та точну політику аргументів: правило, обмежене певною безпечною підкомандою або довіреною програмою, надає інші можливості; крім того, в інсталяції лише середовища виконання можуть бути відсутні команди SDK. Сама назва виконуваного файла — лише привід для перевірки, а не доказ можливості виконання коду.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Дозволена через sudo команда `tee`: довільний запис у файл із привілеями

GNU `tee` копіює стандартне введення в кожен шлях, указаний як файловий операнд. Тому правило sudo, яке дозволяє виконувати `/usr/bin/tee` від імені root з аргументами, контрольованими користувачем, надає примітив для створення довільних файлів від імені root або перезапису таких файлів. Додавання `-a` змінює примітив на дописування. Тег `PASSWD:` стосується автентифікації sudo; сам по собі він не обмежує ні цільовий файл, ні байти, зчитані зі стандартного введення.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Спершу перевірте точне правило. В авторизованій тестовій системі перевіряйте примітив лише на тимчасовому шляху, який безпечно створити. Кінцевий `>/dev/null` лише приховує копію, яку `tee` виводить у стандартний вивід.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Розміщення `sudo` перед командою-виробником не надає підвищених привілеїв подальшому перенаправленню в оболонці, оскільки файл призначення відкриває оболонка виклику. Записувати має привілейований процес, як у конвеєрі вище.<sup>[[1]](#references)[[15]](#references)</sup>

Після підтвердження можливості запису виберіть відповідний спосіб виконання коду від root зі списку [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). В одному з виявлених ланцюжків root-команда `tee` створювала файл із коротким терміном дії в `/etc/cron.d/`, запускала бекдор через скрипт, контрольований користувачем, а після виконання видаляла файл cron. Видалення файла cron не дало йому стати довготривалим механізмом persistence, хоча системні журнали все одно зберегли свідчення цієї діяльності.<sup>[[27]](#references)</sup>

## Sudo-allowed editors

Якщо `sudo -l` дозволяє користувачеві запускати інтерактивний редактор від root, розглядайте це як засіб виконання команд, а не як нешкідливий дозвіл на редагування файлів. Редактори часто можуть виконувати команди оболонки, читати довільні файли, записувати довільні файли або викликати зовнішні допоміжні програми з редактора.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Типова послідовність перевірки: перегляньте привілеї користувача, а потім запустіть кожен дозволений редактор або pager через sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Виконання команд через Nano

Якщо `nano` дозволено запускати через sudo, з інтерфейсу редактора можна виконувати команди.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Потім введіть команду, наприклад `id` або `/bin/sh`, у командний рядок nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Якщо інтерактивна оболонка не має доступних для використання потоків термінала, ця форма перенаправлення спрямовує її стандартний вивід і потік помилок до дескриптора 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Точна послідовність клавіш може відрізнятися залежно від версії nano та параметрів збірки, але проблема безпеки та сама: редактор працює з правами root і може запускати зовнішні команди.<sup>[[1]](#references)[[12]](#references)</sup>

### Інші поширені способи виходу з редактора

Редактори на кшталт Vim зазвичай дають змогу запускати команди через `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Пейджери на кшталт `less` також можуть надавати можливість виконувати команди оболонки.<sup>[[14]](#references)</sup>

Правило sudo, яке дозволяє запускати `apport-cli` від імені root, також потребує перевірки пейджера. У вразливих версіях Apport звіт про збій міг відкриватися в `less` із розміром термінала, який міг задавати зловмисник; за певних умов використання sudo та пейджера це могло надати root shell. Перш ніж вважати версію вразливою, перевірте чинне правило sudo, налаштування пейджера та виправлення в пакеті дистрибутива. Під час пасивного переліку переглядайте метадані пакета й політики, не створюючи збій і не відкриваючи привілейований звіт. [Ubuntu's CVE record](https://ubuntu.com/security/CVE-2023-1326) містить версії виправлених пакетів для окремих випусків, зокрема зворотно портовані виправлення.

```text
!/bin/sh
```

## Інші ризики правил sudo і doas

Почніть із `sudo -l`, `sudo -V` і відповідної політики `doas`. Розглядайте разом дозволену команду, користувача RunAs, аргументи, середовище та параметри за замовчуванням. Дозвіл запускати команди від імені непривілейованого службового облікового запису все одно може відкрити доступ до його файлів або шлях до root.

Навіть фіксований Python-скрипт, дозволений через sudo, може виконати shell-команду від імені RunAs, якщо введені інтерактивно дані, контрольовані користувачем, об’єднуються в [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Заборони символів shell недостатньо, щоб вважати це безпечним: [shell також розпізнає підстановку команд `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Переконайтеся, що дозволені аргументи доходять до гілки введення, введені дані потрапляють до shell-команди без безпечної перевірки, а ефективна політика sudo дозволяє потрібного користувача RunAs. Сам шлях до скрипту або виклик `os.system()` — лише привід для перевірки; вивчайте вихідний код, не запускаючи привілейований скрипт.

Ефективний дозвіл sudo від root на `chattr` може зняти з файла атрибут immutable (`i`), але сам по собі він не надає права на запис чи нової ідентичності. [Посібник `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) зазначає, що цей атрибут блокує змінення файла, а змінити його може лише root або процес із `CAP_LINUX_IMMUTABLE`. Перевірте точну політику аргументів sudo та підтримку файлової системи, а потім окремо з’ясуйте, чи може користувач записувати у файл після зняття атрибута та чи використовує його споживач із вищими привілеями. Наприклад, заміна login shell також вимагає дійсних облікових даних цільового облікового запису та фактичного входу через цей shell. Під час інвентаризації перевіряйте політику, атрибути файлів і дозволи, не змінюючи їх.

Якщо sudo запитує і пароль, і одноразовий код, розглядайте ці передумови окремо від дозволу на виконання команди. Файл `.google_authenticator`, доступний для читання, містить конфіденційний seed, тоді як старий хеш пароля програми чи бази даних — лише можливий пароль поточного облікового запису; жодне з цього не доводить, що інший фактор приймається ефективною конфігурацією PAM. Після отримання дозволу перевірте точні RunAs та аргументи: необмежений дозвіл root на RubyGems `gem` може відкрити його команду редактора ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), але обмежений дозвіл або невдала автентифікація — ні. Пасивна інвентаризація має повідомляти шляхи й політику, не показуючи seed, не добираючи пароль, не генеруючи код і не запускаючи привілейовану команду.

Необмежений дозвіл sudo для Chef `knife`, який може виконуватися від root, потребує окремої перевірки на рівні інтерпретатора: [Chef документує, що `knife exec -E` локально виконує Ruby-рядок](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Переконайтеся, що ефективне правило sudo дозволяє підкоманду `exec` і переданий користувачем аргумент `-E`, потрібну ідентичність RunAs, а також перевірте відповідні заборони команд і фіксовані аргументи. Встановлений бінарний файл або правило, обмежене іншими підкомандами, — лише привід для перевірки. Пасивна інвентаризація має повідомляти про правило, не запускаючи `knife`.

Точний дозвіл sudo для інтерактивного `msfconsole`, який може виконуватися від root, так само чутливий: [GTFOBins описує його консоль `irb`](https://gtfobins.org/gtfobins/msfconsole/), що може успадкувати ідентичність sudo. Перевірте ефективного користувача RunAs, дозволений список аргументів, заборони команд, `NOEXEC` та інші обмеження, поведінку встановленої консолі й можливість користувача передавати інтерактивне введення. Самої підсвітки шляху недостатньо — це лише привід для перевірки; під час пасивної інвентаризації не запускайте консоль.

У FreeBSD навіть правило sudo, обмежене командами root `pkg update` і `pkg install *`, потребує перевірки довіри до репозиторію. З’ясуйте, чи може користувач записувати в `/etc/hosts` і чи використовує *ефективна* конфігурація ввімкненого репозиторію HTTP-ім’я хоста з `signature_type: none`. [Посібник FreeBSD `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) зазначає, що `none` вимикає перевірки підписів; сама схема `pkg+http` цього не доводить. Пакет може містити скрипти інсталяції ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), тому користувач, який справді контролює кінцеву адресу репозиторію та може вибрати пакет, може перетнути межу привілеїв root. Перш ніж робити такий висновок, перевірте перевизначення репозиторіїв, розв’язання SRV/дзеркал, ефективні аргументи sudo, вибір пакета й виконання скриптів. Перевіряйте політику та невеликі локальні конфігураційні файли, не перенаправляючи імена й не запускаючи `pkg` під час інвентаризації.

Правило sudo для `apt-get update` і `apt-get upgrade`, яке може виконуватися від root, також потребує перевірки довіри до репозиторію, якщо sudo зберігає контрольований користувачем `http_proxy`. З’ясуйте, чи використовує ефективна конфігурація APT цю змінну та на які ввімкнені запити до репозиторіїв вона може вплинути; сам проксі не може підмінити пакети з архіву, автентифікованого довіреним ключем підпису. [Посібник HTTP-транспорту APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) описує пріоритет проксі, а [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — перевірки підписів, перевизначення для ненадійних репозиторіїв і підтвердження для неавтентифікованих пакетів. Перевірте точні RunAs та аргументи sudo, політику автентифікації репозиторію, потребу в інтерактивному підтвердженні й те, чи запускає вибране оновлення скрипти пакетів від root. Пасивно перевіряйте політику й локальну конфігурацію; під час інвентаризації не перенаправляйте трафік пакетів і не запускайте оновлення.

Правило sudo для `snap install`, яке може виконуватися від root, створює межу між пакетом і кодом, якщо аргументи дають змогу користувачу вибрати локальний snap і режим інсталяції з послабленнями. [У документації Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) зазначено, що `--dangerous` пропускає перевірки assertions локального snap, а `--devmode` послаблює ізоляцію; [під час першого встановлення може виконатися install hook](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Перш ніж стверджувати, що це дає доступ до захищених файлів хоста, перевірте точну політику аргументів і RunAs у sudo, хто контролює файл snap, чи приймає ці режими встановлений snapd, а також ефективну ідентичність і рівень ізоляції hook. Сам бінарний файл `snap` або правило, що лише зовні схоже на шаблон із підстановкою, цього ланцюжка не доводить. Під час пасивної інвентаризації не встановлюйте пакет і не запускайте його hook.

Якщо точний дозвіл sudo на бінарний файл читання облікових даних, створений користувачем, надається обліковому запису **не root**, спершу перевірте дозволи бінарного файла, не запускаючи його. Вбудований парольний захист може бути видимим лише як широкі символи; [GNU `strings` описує вилучення 16-бітного little-endian тексту](https://sourceware.org/binutils/docs/binutils/strings.html). Видимий рядок не доводить, що це правильний пароль або що гілка успішного входу розкриває актуальні облікові дані. Окремо перевірте поведінку бінарного файла, доступ цільового облікового запису до захищених даних, чинність облікових даних і будь-який подальший перехід між обліковими записами чи групами. Якщо цей обліковий запис належить до групи `docker`, перевірте доступ до сокета й те, чи демон працює з rootful чи rootless-ідентичністю, перш ніж робити висновок про доступ до root на хості; [Docker описує наслідки членства в цій групі](https://docs.docker.com/engine/install/linux-postinstall/). Звичайна інвентаризація має повідомляти про правило sudo та членство в групах, не запускаючи бінарний файл і не виводячи його рядки.

Правило sudo із шаблоном-підстановкою для скриптів обслуговування програми потребує перевірки не лише шляху до скрипту. З’ясуйте, чи приймає дозволений скрипт довільні аргументи або читає параметри, які може змінювати обліковий запис програми з нижчими привілеями, а потім простежте ці значення до shell-команд або середовища підпроцесу. Наприклад, ZoneMinder у [`zmupdate.pl` формує команду `mysqldump` і виконує її через `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), тоді як [`zmdc.pl` копіює параметр `ZM_LD_PRELOAD` у `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) перед запуском демонів. Правило sudo, що дозволяє запускати будь-який із цих скриптів від root, може перетнути межу довіри, якщо відповідним вхідним параметром можна керувати й він доходить до цього коду у встановленій версії. Перевірте ефективне правило sudo, права на конфігурацію програми й вихідний код скрипту; сам шаблон із підстановкою або параметр — це лише привід для перевірки, а не доказ виконання.

- `SETENV`, `env_keep`, `secure_path` і `LD_PRELOAD` можуть перетворити вузький дозвіл на команду на перехоплення імпорту, бібліотеки чи `PATH`. Див. [посібник зі змінних середовища](../linux-basics/linux-environment-variables.md) і [зловживання SUID/лінкером](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Точний дозвіл `SETENV` для shell-обгортки, яка може виконуватися від root, також потребує перевірки на один крок, якщо обгортка запускає фіксований Python-скрипт із буквальним імпортом. `secure_path` обмежує пошук shell-команд, а не пошук модулів Python через [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); параметри [`-E` і `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) змушують Python ігнорувати цю змінну середовища. Перш ніж вважати це виконанням коду, перевірте ефективні теги та заборони sudo, гілку обгортки, параметри інтерпретатора, розв’язання імпорту й наявність каталогу пошуку, доступного для запису користувачу. Короткі скрипти перевіряйте статично; не запускайте привілейовану обгортку.

Точний дозвіл sudo для `neofetch ""`, який може виконуватися від root, усе одно може завантажити shell-конфігурацію, якщо відповідні параметри sudo зберігають контрольований користувачем `XDG_CONFIG_HOME`. [Завантажувач конфігурації Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) підключає `neofetch/config.conf` або `neofetch/config` з цього каталогу; порожній список аргументів не заважає цьому пошуку. Перевірте завантажувач установленої версії, ефективні RunAs та політику аргументів, заборони команд, чи справді sudo зберігає вибрану змінну для цієї команди, а також чи контролює користувач доступний для читання шлях до конфігурації. Збережена змінна або встановлений Neofetch — лише привід для перевірки. Перевіряйте політику й метадані файлів, не запускаючи привілейовану команду й не виводячи вміст конфігурації; див. [обробку середовища в sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Необмежене правило sudo для `facter`, яке може виконуватися від root, потребує окремої перевірки custom facts. [Puppet документує](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), що `--custom-dir` завантажує Ruby-файли фактів із вибраного каталогу. Перевірте, чи дозволяє точне правило sudo цей параметр, чи підтримує його встановлений Facter і чи контролює користувач цей каталог. Фіксований набір аргументів, явна заборона команди або вимкнені custom facts можуть змінити результат. Пасивна інвентаризація має повідомляти про можливий кандидат у політиці, не запускаючи Facter і не читаючи вміст файлів фактів.

Для точного дозволу sudo на запуск скрипту від root із `SETENV` перевірте назви команд без повного шляху, наприклад `find`, і ефективний `PATH` після застосування політики sudo та ініціалізації скрипту. Підключений файл Bash також може виконати `enable -n [`: [після цього Bash шукає зовнішній `[` у `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), коли скрипт пізніше використовує цю команду. Перевірте відповідні [правила середовища й `secure_path` у sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), будь-які записи `NOSETENV`/`NOEXEC` або заборони, потік виконання скрипту й підключених файлів, а також наявність каталогу пошуку з виконуваним файлом, контрольованим користувачем. Читабельний скрипт із командою без повного шляху — лише привід для перевірки, а не доказ привілейованого виконання; перевіряйте його, не запускаючи правило sudo.
- Привілейований скрипт, який завантажує дані з фіксованої URL-адреси через `curl`, усе одно може прийняти вибрану користувачем відповідь, якщо відповідне правило sudo зберігає `http_proxy` і запит надсилається через цей проксі. Якщо скрипт потім передає відповідь XML-парсеру, який розв’язує зовнішні сутності, шкідлива відповідь може розкрити файли, доступні привілейованому процесу. Перевірте точну політику середовища sudo, винятки `no_proxy`, запитувану URL-адресу, конфігурацію парсера й місце призначення виводу; однієї змінної проксі чи XML-парсера недостатньо, щоб довести вразливість. У [документації curl щодо змінних середовища проксі](https://everything.curl.dev/usingcurl/proxies/env.html) описано їхню поведінку. Під час пасивної інвентаризації не надсилайте мережевих запитів і не аналізуйте шкідливий XML.
- Скрипт sudo, який може виконуватися від root, створює файл PostScript із даних, на які впливає користувач, а потім запускає `ps2pdf -dNOSAFER`, потребує окремої перевірки потоку даних. У документації Ghostscript зазначено, що цей прапорець вимикає SAFER до виклику `.setsafe`, дозволяючи операції з файлами в межах дозволів ОС процесу. SQL-запит, сформований з аргументу користувача, може передати контрольовані зловмисником рядки в шаблон PostScript, але сам рядок запиту або виклик `ps2pdf` не доводить, що ці дані потрапляють у синтаксис виконуваного PostScript. Перевірте ефективне правило sudo, точний шлях від введення до шаблону, екранування, поведінку встановленого Ghostscript і те, чи знову вмикається SAFER до інтерпретації документа. Під час пасивної інвентаризації не запускайте привілейоване перетворення. Див. [документацію Ghostscript щодо `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Для правила sudo, що запускає shell-скрипт, порівняйте збережені змінні із самим скриптом. Конструкція на кшталт `if $CHECK_CONTENT; then` виконує розгорнуте значення як команду, тому збереження `CHECK_CONTENT` може дозволити виконання команди, навіть якщо шлях до скрипту й аргументи фіксовані. Для конкретного правила потрібно перевірити, чи досяжна ця гілка і чи справді змінна середовища зберігається.<sup>[[2]](#references)[[22]](#references)</sup>
- Python-скрипт, дозволений через sudo, може імпортувати код із каталогу, доступного для запису, або кешованого файла `.pyc`. Випадок із кешем описано в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md).
- Фіксований Python-скрипт, дозволений для запуску від root, може відкрити доступ до інтерактивного налагоджувача. Виклики на кшталт `pdb.set_trace()` або `pdb.post_mortem()` дають змогу виконувати Python-інструкції в контексті процесу, який налагоджується, якщо користувач може досягти точки переривання чи обробника винятку **та контролює потік введення налагоджувача**. Перевірте точне правило RunAs у sudo, автентифікацію й умови гілки, досяжність винятку, власника термінала/введення та те, чи працює налагоджувач у тому самому привілейованому процесі. Запит до сокета, який спричиняє виняток, сам по собі не дає доступу до налагоджувача, підключеного до іншого термінала. [Python документує виконання інструкцій у налагоджувачі та режим post-mortem](https://docs.python.org/3/library/pdb.html); перевіряйте скрипт статично, не спричиняючи виклик привілейованого обробника під час інвентаризації.
- Фіксований Python-скрипт, дозволений через sudo, також може прочитати поле профілю з бази даних або Unix-сокета й додати його до рядка, який згодом стає **рядком формату** для `str.format()`. [Поля підстановки можуть звертатися до атрибутів і ключів відображень](https://docs.python.org/3/library/string.html#format-string-syntax), тож контрольоване зловмисником поле може перевіряти об’єкти, передані в `format()`, і розкривати доступні через них дані, якщо результат виводиться або зберігається там, де його може прочитати користувач. Перевірте ефективну ідентичність RunAs у sudo, право запису в конкретний запис, потік даних до рядка формату, передані об’єкти й доступність виводу. Це не автоматичне виконання коду; буквальний довірений рядок формату з контрольованими зловмисником *значеннями* — інший випадок. Розкрита таємниця дає змогу перейти до облікового запису ОС лише тоді, коли цей обліковий запис її приймає. Перевірте скрипт і дозволи сокета, не запускаючи привілейовану операцію.
- Обгортка Python, яка може виконуватися від root, може передавати вибрану користувачем URL-адресу до `Repo.clone_from` у GitPython. Якщо обгортка також вмикає `protocol.ext.allow=always` у Git, remote `ext::` може запустити зовнішній helper. Перевірте точні аргументи sudo, походження URL-адреси, версію пакета GitPython і наявність виправлень від постачальника, а також те, чи явно дозволяє обгортка небезпечні протоколи. У GitPython додано [захист від небезпечних протоколів за замовчуванням](https://github.com/gitpython-developers/GitPython/commit/2625ed9) у версії 3.1.30; версія виконуваного файла `git` — окремий факт. Пасивна перевірка має обмежуватися правилом і доступною для перегляду частиною коду; не запускайте клонування.
- Дозвіл sudo на запуск CLI для клонування репозиторію від імені іншого користувача може відкрити окремий шлях до ін’єкції рядка shell-команди. Простежте, чи доходить вибраний користувачем аргумент репозиторію до [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) у Node.js або іншого конструктора shell-команд без безпечного розділення аргументів; `exec` у Node передає рядок команди до shell. Перевірте точного користувача RunAs, дозволені підкоманди й аргументи, код установленої обгортки та перевірку введених даних. Сама назва інструмента для роботи з репозиторіями або необмежене правило sudo не доводить ін’єкцію команд. Перевіряйте обгортку, не запускаючи привілейоване клонування під час інвентаризації.
- Користувацька обгортка, що належить root, може здаватися безпечною, бо її бінарні файли й скрипти не доступні для запису, але рішення про привілейовану дію може залежати від прапорця, значення локального API або стану служби, який може змінити непривілейований користувач. Простежте кожну умову до її джерела й перевірок авторизації. Під час інвентаризації перевіряйте конфігурацію й дозволи, не змінюючи робочий стан; виклик `systemd-run` усередині обгортки має значення лише тоді, коли на відповідну умову можна вплинути.
- Клієнт резервного копіювання, дозволений через sudo від root, може приймати вибраний користувачем конфігураційний файл (наприклад, `npbackup-cli -c`). Перевірте точного користувача RunAs і дозволені аргументи, а потім з’ясуйте, чи контролює користувач шлях до конфігурації, шляхи джерел резервного копіювання, репозиторій або параметри читання/відновлення. Зашифрований секрет репозиторію в доступній для читання конфігурації може бути придатним для клієнта, але саме правило не доводить доступ до репозиторію чи розкриття файлів root. Перевіряйте авторизацію, не запускаючи резервне копіювання й не виводячи його вміст.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) підтримує `--password-command`, який запускає програму для отримання пароля репозиторію. Якщо правило sudo дозволяє користувачу з нижчими привілеями запускати restic від root із вибраною ним командою пароля та підкомандою, якій потрібен пароль, цей helper може виконатися від root. Перевірте точні аргументи й винятки sudo; не запускайте helper чи команду резервного копіювання лише для інвентаризації цієї умови.
- Дозвіл на привілейований `restic backup` також може перетнути межу доступу до файлів, якщо шаблон аргументів sudo дає змогу користувачу вибрати і джерело, і репозиторій, який він потім може читати та розшифрувати. [Шаблони-підстановки аргументів sudoers можуть збігатися з пробілами й косими рисками](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), тому перевіряйте шаблони із зірочками наприкінці, а не припускайте, що фіксований префікс репозиторію обмежує джерело. [Restic може записувати резервні копії в локальні й віддалені репозиторії](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), але локальний репозиторій може містити щойно створені об’єкти, доступні лише root; перш ніж вважати це розкриттям даних, перевірте ефективну політику sudo, доступ до backend, пароль репозиторію й дозволи на створені об’єкти. Резервна копія SSH-ключа дає доступ лише тоді, коли цільовий обліковий запис його приймає. Не запускайте резервне копіювання для перевірки під час пасивного аналізу.
- Необмежена користувацька команда обслуговування чи резервного копіювання може приймати шлях виводу або мати власний планувальник завдань. Для шляху запису у файл перевірте точне правило sudo й користувача RunAs, а потім з’ясуйте, чи контролює користувач і дані, і місце призначення. Для шляху через планувальник перевірте ідентичність, від імені якої він виконується, вхідні дані команди й будь-який додатковий парольний або авторизаційний бар’єр. Сама назва команди чи `NOPASSWD` не доводить жоден із цих шляхів. Див. [запис у файли, що належать root](../interesting-files-permissions/write-to-root.md) і [cron та таймери systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Фіксована команда sudo може завантажувати передбачуваний конфігураційний файл зі спільного каталогу, доступного для запису. З’ясуйте, чи може користувач замінити цей файл і чи керують його поля джерела та призначення привілейованим завантаженням або копіюванням. URL-адреса локального файла може відкрити дані, доступні лише обліковому запису RunAs у sudo; контрольоване користувачем джерело разом із захищеним місцем призначення може створити шлях запису. Перевірте обробку URL-адрес установленою програмою, перевірки шляху призначення, ефективне правило sudo й доступність виводу. Сам конфігураційний шлях у доступному для запису `/tmp` — лише привід для перевірки; досліджуйте бінарний файл і метадані файлів, не запускаючи привілейоване передавання.
- Правило sudo для `git apply` може дозволити обліковому запису RunAs записувати файли, вибрані через контрольований користувачем patch. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) дозволяла створити symlink за допомогою спеціально сформованого patch, а потім записати дані за межами робочого дерева, навіть якщо команда не приймала `--unsafe-paths`. Перевірте ефективне правило аргументів sudo, джерело patch, доступ облікового запису RunAs до робочого каталогу та встановлене виправлення Git або його backport від постачальника. Необмежене правило, що дозволяє `--unsafe-paths`, створює окремий ризик, пов’язаний із цим явним параметром; ні версія Git, ні сам дозвіл на `git apply` не доводять можливість змінити захищений файл. Під час пасивної інвентаризації не застосовуйте ненадійний patch.
- Правило sudo для `clamscan --debug`, яке може виконуватися від root, може перетнути межу читання, якщо користувач із нижчими привілеями може надати образ DMG, а встановлений парсер уразливий до [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), що могла розкривати вміст файлів через діагностичний вивід. Перевірте точні дозволені аргументи та шлях сканування, контроль над вхідним файлом, ефективний обліковий запис RunAs, виправлення чи backport рушія й доступність виводу для користувача. Якщо ширше правило дозволяє `--file-list`/`-f`, окремо перевірте поведінку цього списку файлів; політика, фіксована на `--debug <scan-path>`, його не дозволяє. Перевіряйте політику й метадані пакета, не скануючи спеціально створений файл і не виводячи захищені дані під час інвентаризації.
- Правило sudo для відкриття зашифрованого образу диска, яке може виконуватися від root, і друге правило для монтування отриманого mapper можуть імпортувати контрольовані користувачем файли в простір монтування хоста. Перевірте обидва ефективні правила й аргументи, контроль над образом і назвою mapper, фактичну точку монтування, а також власника й режим створених файлів. Для переходу через SetUID також потрібні доступний для виконання файл, параметри монтування, що враховують SetUID (`nosuid` його блокує), і відповідна політика процесу чи MAC; саме відкриття або монтування образу — лише привід для перевірки. Окремий шлях через наявну резервну копію вимагає її фактичного ключа та корисного секрету, доступного для читання, усередині. Перевіряйте політику й шляхи, не відкриваючи та не монтуючи образ під час пасивної інвентаризації. Див. [посібник cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) і [параметри монтування](https://man7.org/linux/man-pages/man8/mount.8.html).
- Правило sudo для shell- або Python-скрипту, який може виконуватися від root, потребує перевірки робочого каталогу, якщо скрипт запускає `./helper`, не переходячи спершу до фіксованого каталогу. Python-список на кшталт `['./helper']`, переданий у `subprocess.run`, може так само використовувати робочий каталог, вибраний користувачем. Користувач може вибрати доступний для запису каталог і розмістити там виконуваний файл із таким відносним ім’ям; абсолютний шлях в іншій частині скрипту цей виклик не захищає. Перш ніж вважати це виконанням коду, перевірте ефективне правило, `runchdir` або іншу політику зміни каталогу, потік виконання скрипту й доступність гілки, доступний для запису та виконання каталог і обмеження монтування/`NOEXEC`. Якщо скрипт недоступний для читання, поведінка лишається невідомою, доки його не буде перевірено через дозволений шлях. Перевіряйте скрипти статично, а не запускайте helper. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) описано політику робочого каталогу.
- Фіксований Python-валідатор, який може виконуватися від root, усе одно може обробляти вибраний користувачем файл даних. [Документація Python щодо `eval()` застерігає від недовірених даних](https://docs.python.org/3/library/functions.html#eval): перевірка суфікса вхідних даних, арифметичний префікс або гілка валідації не є пісочницею, якщо решта виразу доходить до `eval`. Перш ніж вважати це шляхом виконання коду, перевірте ефективне правило sudo, чи може користувач вибрати й контролювати саме цей файл, умови гілок парсера й формування виразу, а також ідентичність привілейованого процесу. Сам факт наявності `eval` у доступному для читання скрипті — лише привід для перевірки; досліджуйте вихідний код і дозволи файлів, не запускаючи валідатор і не передаючи тестовий вираз під час інвентаризації.
- Обгортка Ruby, яка може виконуватися від root через sudo та читає відносне ім’я YAML-файла, наприклад `YAML.load(File.read("dependencies.yml"))`, може брати вхідні дані з робочого каталогу користувача, якщо обгортка чи політика sudo не фіксує цей каталог. Перевірте точні дозволені аргументи, дозволи на каталог і файл, а також поведінку встановленого Psych: старі реалізації `YAML.load` могли десеріалізувати довільні об’єкти Ruby, тоді як новіші за замовчуванням обмежують класи. Статичний виклик — лише привід для перевірки; переконайтеся, що файл справді береться з каталогу, доступного користувачу для запису, а встановлений завантажувач приймає небезпечні класи. Для недовірених даних віддавайте перевагу `safe_load` з явним мінімальним списком дозволених класів. Див. документацію [Psych для Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) і [Psych для Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Точний дозвіл sudo на `go run /absolute/file.go`, який може виконуватися від root, потребує перевірки робочого каталогу, якщо вихідний код Go читає відносний файл WASM і після перевірки його результату може запускати відносний shell-скрипт. Перевірте ефективний RunAs, аргументи команди й заборони, поточний каталог, доступний користувачу для запису, потік даних від WASM до гілки та те, чи запускає ця гілка helper. Фіксований `runchdir` у sudo, `os.Chdir` або [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) можуть змінити місце пошуку. Самої статичної співнаявності недостатньо — це лише можливий кандидат; перевіряйте вихідний код, не запускаючи Go, WASM чи helper.
- Для `sudoedit` і шаблонів-підстановок аргументів потрібні точні перевірки версії та правила; у [контрольному списку](linux-privilege-escalation-checklist.md) описано проблему редагування файла через sudoedit. Для правила `sudoedit` із шаблоном-підстановкою, що дозволяє змінити файл від імені іншого користувача, перевірте ефективне налаштування `sudoedit_follow` або `FOLLOW`, `sudoedit_checkdir`, розв’язаний цільовий шлях і те, хто може замінити кожен запис батьківського каталогу. Перше може дозволити перехід за symlink, а вимкнення другого прибирає перевірки каталогів, доступних для запису; жодне з цих налаштувань саме по собі не доводить можливість запису у файл іншого користувача. Перш ніж робити такий висновок, перевірте встановлену політику sudo й точні аргументи, що відповідають правилу. Див. [визначення параметрів sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- У правилі команд sudoers шаблон-підстановка аргументу може збігатися з пробілами, а не лише із символами шляху. Правило для команди з можливістю читання та аргументом на кшталт `/restricted/*` може тому дозволити додатковий аргумент із назвою файла після відповідного префікса. Перевірте точного користувача RunAs, шлях до команди, шаблон аргументу й подальші заборони; доведене читання файла не означає виконання коду. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) розрізняються шаблони аргументів і шаблони шляхів до команд.
- Шаблон аргументу, схожий на шлях, також може збігатися з `../`. Наприклад, правило для `node /opt/scripts/*.js`, яке може виконуватися від root, може дозволити контрольований користувачем файл JavaScript за межами `/opt/scripts`, якщо переданий шлях усе ще починається з `/opt/scripts/`, але розв’язується через сегменти батьківських каталогів. Це шаблон **аргументу**; для шаблону шляху до виконуваного файла Node діють інші правила зіставлення косих рисок. Перш ніж робити висновок про виконання коду, перевірте ефективне правило, подальші заборони, розв’язання шляху, контроль над цільовим файлом і обмеження sudoers за регулярними виразами чи digest. Див. [правила шаблонів-підстановок sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) і [документацію командного рядка Node](https://nodejs.org/api/cli.html).
- Архіватори й інші утиліти можуть мати механізми запуску коду. Перевіряйте точні дозволені аргументи за допомогою [GTFOBins](https://gtfobins.github.io/), а не припускайте, що команди виконують лише shell та інтерпретатори.
- Необмежене правило sudo для `qpdf`, яке може виконуватися від root, може розкрити привілейований файл через вкладення PDF: версії qpdf 10.2 і новіші підтримують `--empty` та `--add-attachment file ... --` з вихідним PDF. Якщо привілейований процес може читати вибране джерело й записати PDF у шлях, доступний користувачу, цей файл може містити вихідні байти. Перш ніж робити висновок про можливість розкриття файла, перевірте ефективні аргументи та винятки sudo, версію qpdf, доступ до джерела й шлях виводу. Читання SSH-ключа root корисне для входу лише тоді, коли ключ чинний і дозволена SSH-автентифікація для root. Див. [параметри вкладень qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Повторне використання часової мітки sudo залежить від політики кешу, користувача-власника, термінала/сеансу й дозволів. Відповідні перевірки описані в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens).
- Для `doas` діють власні правила й конфігурація. Перевірте дозволені команди та шляхи до конфігурації, доступні для запису, як описано в [розділі про doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Інструменти складання та роботи з пакетами, запущені через sudo

Необмежений дозвіл sudo для Foundry `forge` може мати значення, навіть якщо RunAs — інший непривілейований користувач. Параметри компілятора, як-от `--use`, можуть вибрати локальний виконуваний файл, а `forge flatten -o` задає вихідний файл. Перш ніж вважати дозвіл експлуатованим, перевірте встановлену версію Forge, точні аргументи sudo, доступні шляхи до проєкту й компілятора, дозволи на вивід та ефективне середовище. Відносний helper, знайдений через `PATH`, — це шлях, залежний від версії та середовища, а не властивість, яку слід припускати для кожної збірки Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Необмежений дозвіл sudo для `pacman`, який може виконуватися від root, дозволяє більше, ніж запити щодо пакетів: `-U` приймає локальний пакет, пакети можуть містити скрипти інсталяції, а `--hookdir` вибирає інший каталог hook. Перед перевіркою перегляньте ефективне правило sudo, обмеження аргументів і винятки; для пасивної інвентаризації не потрібно встановлювати пакет чи запускати hook.<sup>[[25]](#references)[[26]](#references)</sup>

Фіксована shell-обгортка sudo також може встановити вказану залежність npm, а потім запустити Node-застосунок. Перевірте точне правило RunAs, чи вже встановлено пакет, ефективні `HOME` і `userconfig` npm, конфігурацію проєкту чи перевизначення командного рядка, а також те, чи контролює користувач із нижчими привілеями реєстр або пакет, отриманий за цією назвою. [У документації npm описано пошук `.npmrc` для користувача й проєкту](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); поведінка `HOME` у sudo залежить від установленої політики й дистрибутива, тому файл `.npmrc` користувача, доступний для запису, може читатися привілейованим процесом npm, а може й ні. Якщо щойно встановлений пакет імпортує привілейований застосунок, його код модуля може виконатися з ідентичністю цього застосунку. Скрипти під час інсталяції — це окремий шлях, залежний від версії й конфігурації; [npm документує їхній життєвий цикл і обробку користувача](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Сам шлях `.npmrc` або рядок `npm install` — лише привід для перевірки. Під час пасивної інвентаризації перевірте правило, коротку обгортку, шляхи конфігурації та походження пакета, не встановлюючи пакет і не запускаючи застосунок.

Дозвіл sudo для `pip` або `pip3 download`, який може виконуватися від root, також є приводом перевірити збірку пакета, якщо аргументи дають користувачу змогу вибрати ненадійний вихідний дистрибутив, навіть коли шаблон URL обмежує його локальним сервісом і суфіксом `.tar.gz`. `pip download` приймає URL-адреси архівів і розв’язує метадані пакета; підготовка sdist може запустити його build backend або код застарілого `setup.py` до того, як архів просто збережеться. Перевірте точні RunAs та правило аргументів sudo, чи може користувач опублікувати або замінити вибраний архів, а також чи справді ця версія pip готує його метадані. Фіксований довірений архів або wheel цього шляху не доводить. Під час пасивної інвентаризації не завантажуйте й не збирайте ненадійний пакет. Див. документацію pip: [команда download](https://pip.pypa.io/en/stable/cli/pip_download/), [інтерфейс build system](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Правило sudo, що дозволяє `pip install` із вибраним користувачем шляхом до локального проєкту, створює прямішу межу збірки. [pip приймає локальні каталоги проєктів](https://pip.pypa.io/en/stable/topics/local-project-installs/) і запускає їхню build system; [build backend виконує керовані проєктом build hooks](https://pip.pypa.io/en/stable/reference/build-system/). Перш ніж вважати правило привілейованим виконанням коду, перевірте ефективну ідентичність RunAs, точні обмеження аргументів і заборони, контроль над вибраним проєктом та поведінку встановлених pip/backend. Фіксований довірений проєкт або правило, що не дозволяє вибирати шляхи користувачу, такого шляху не створює. Перегляньте правило й метадані проєкту, не встановлюючи пакет під час пасивної інвентаризації.

Необмежений дозвіл sudo для `easy_install`, який може виконуватися від root, — це споріднений привід перевірити застарілу збірку пакетів. [Setuptools документує](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), що Easy Install приймає локальний каталог проєкту й збирає вихідні дистрибутиви; під час такої збірки проєкт, контрольований користувачем, може виконати свій `setup.py` з ідентичністю sudo. Перевірте ефективний обліковий запис RunAs, точну команду й обмеження аргументів, зокрема подальші заборони, контроль над вибраним проєктом і поведінку встановленого інструмента. Фіксований довірений проєкт або політика, що не дозволяє користувачу вибирати джерело, не створює такого шляху. Під час інвентаризації перегляньте правило й метадані проєкту, не встановлюючи пакет.

Python-обгортка, дозволена через sudo, яка використовує `setuptools.package_index.PackageIndex.download` із вибраною користувачем URL-адресою, потребує іншої перевірки, ніж `pip download`: [GHSA-5rjg-fvgr-3xxf для setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) описує випадки, коли ім’я файла, утворене з URL, виходило за межі призначеного каталогу завантаження й записувалося з дозволами процесу в уражених випусках до 78.1.1. Перевірте ефективні RunAs та правило аргументів sudo, чи передає обгортка URL користувача до цього конкретного API, чи встановлено виправлення або backport постачальника, а також куди розв’язується кінцевий шлях. Сам номер версії або каталог завантаження, доступний для запису, не доводить можливість довільного запису. Під час інвентаризації перегляньте коротку обгортку й метадані пакета, не завантажуючи URL і не записуючи файл.

Обгортка збірки, дозволена через sudo та передає PyInstaller вибраний користувачем файл `.spec`, потребує такої самої перевірки межі довіри. Файл PyInstaller spec — це виконуваний Python-код, який обробляється під час **збірки**, а його записи `datas` можуть вбудовувати у артефакт файли, доступні для читання користувачу збірки. Перевірте точного користувача RunAs, правила аргументів і заборон sudo, обробку шляхів і гілок в обгортці, контроль над вибраним spec-файлом і доступ до готового артефакту. Сам дозвіл на вхідний файл `.py` або наявність PyInstaller не доводять контроль над spec-файлом чи привілейоване виконання. Для пасивної перевірки достатньо прочитати обмежений за розміром файл обгортки й метадані; не запускайте збірку. Див. [документацію PyInstaller щодо spec-файлів](https://pyinstaller.org/en/stable/spec-files.html).

### Завантажувачі preset і plugin, запущені через sudo

Інструменти Python, які приймають вибраний користувачем preset або каталог plugin, можуть імпортувати код із привілеями, наданими через sudo. Наприклад, BBOT приймає preset через `-p`, а в його [документації користувацьких модулів](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) описано записи `module_dirs`, які додають каталоги модулів Python. Якщо ефективне правило sudo дозволяє вибраний користувачем preset, а користувач контролює модуль у вибраному каталозі, під час імпорту може виконатися код від імені привілейованого користувача — потенційно ще до того, як інструмент відхилить недійсний модуль. Перевірте встановлену версію, точну політику RunAs та аргументів sudo й власника preset і каталогів модулів, не завантажуючи модуль під час інвентаризації.

### Інструмент командного рядка Backdrop, запущений через sudo

[Bee](https://github.com/backdrop-contrib/bee) — інструмент командного рядка PHP для Backdrop CMS. Його команди `eval` (`php-eval`) і `php-script` можуть виконувати наданий користувачем PHP-код. Тому правило sudo, яке дозволяє запускати Bee від root з необмеженими аргументами, може відкрити виконання коду від root, якщо Bee може ініціалізувати встановлення Backdrop. Запускайте його з каталогу сайту або виберіть сайт глобальним параметром `--root=<directory>`; самої наявності Bee чи файла Backdrop `settings.php` недостатньо, щоб довести наявність дозволу sudo, придатного сайту або успішної ініціалізації. Перед перевіркою перегляньте ефективне правило sudo, можливі заборони команд, ідентичність виконуваного файла й доступ до сайту. Під час пасивної інвентаризації перевіряйте правило та шляхи до файлів, не запускаючи Bee. Доповнення команд PHP описані в [журналі змін команд Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md).

### Термінальні сервери, запущені через sudo

`mosh-server` запускає інтерактивний термінальний сервер від імені користувача, який його викликає. Він вибирає високий UDP-порт і ключ сеансу, повідомляє обидва значення викликачеві та зазвичай запускає login shell цього користувача, коли клієнт підключається. Тому необмежений дозвіл sudo на `mosh-server`, який може виконуватися від root, є кандидатом на перевірку shell, хоча команда сервера сама від’єднується. Перевірте ефективну ідентичність RunAs, дозволені аргументи й винятки, встановлений бінарний файл, shell, доступність клієнта та UDP. Під час пасивної інвентаризації перегляньте правило sudo, не запускаючи сервер і не виводячи чинний ключ сеансу. Див. [посібник сервера Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) і [примітки щодо роботи від розробників](https://github.com/mobile-shell/mosh#how-it-works).

### Привілейовані обгортки резервного копіювання, які змінюють файл завдань користувача

Shell-обгортка, що запускається від root, може приймати вибраний користувачем файл завдань, видаляти `../` зі шляхів джерел, перевіряти, чи починається кожен отриманий шлях із дозволеного каталогу, змінювати файл завдань, а потім передавати *його шлях* програмі резервного копіювання. Перевірте перетворений шлях після повного канонічного розв’язання: одноразова заміна рядка може створити нову послідовність переходу до батьківського каталогу, яку прийме лексична перевірка префікса. Також з’ясуйте, чи читає програма резервного копіювання перетворені дані з пам’яті або повторно відкриває файл. Якщо вона відкриває його повторно, невдала спроба змінити файл може залишити початковий вміст на місці.

У Linux `fs.protected_regular` може заборонити запис через `O_CREAT` у звичайний файл іншого користувача в каталозі зі sticky bit, доступному для запису всім. Це захисне обмеження, але shell-обгортка, яка ігнорує помилку запису, все одно може продовжити роботу з початковим файлом завдань. Перевірте це налаштування, власника файла й каталогу, а також те, чи завершує обгортка роботу в разі помилки. Шлях є кандидатом на розкриття файлів лише тоді, коли ефективне правило sudo дозволяє запуск обгортки від привілейованого користувача, користувач контролює вхідні дані завдання й доступне для читання місце призначення резервної копії, а утиліта справді включає захищені джерела. Перевіряйте ці умови, не запускаючи резервне копіювання під час інвентаризації.

### Шаблони-підстановки аргументів для привілейованих мережевих інструментів

У правилі sudo для `tcpdump` зірочка `*` у **шаблоні аргументу** може збігатися з пробілами й косими рисками, тому обмеження, схоже на шлях, усе ще може дозволяти додатковий текст параметра. Це відрізняється від шаблону-підстановки в шляху до виконуваного файла команди; перевірте повне правило RunAs і всі подальші заборони. Якщо можна вставити параметри, дозволений виклик і семантика параметрів установленого [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) визначають, чи надають `-F`, `-V`, `-r`, `-w` або `-Z` корисну можливість читання чи запису. `-V` читає список імен файлів захоплення, а не довільний файл загального призначення. AppArmor або інша політика MAC може блокувати доступ до файлів, навіть якщо sudo дозволяє команду; наявність файла профілю на диску не доводить, що він завантажений або застосовується. Перш ніж робити висновок, пасивно перевірте авторизацію й політику. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) описано різницю між шаблонами.

Правило sudo, що дозволяє запуск від root лише виконуваного файла `tcpdump`, без обмежень аргументів, також потребує перевірки. У [посібнику tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) описано `-z` як команду після ротації, коли `-C` або `-G` розбиває збережений файл захоплення на частини; `-Z` або параметр компіляції за замовчуванням може знизити привілеї перед запуском цієї команди. Перш ніж вважати правило шляхом до підвищення привілеїв, перевірте ефективне правило sudo, встановлену збірку, поведінку зі зниженням привілеїв і можливість ротації. Підсвічене правило — це кандидат для перевірки, а не доказ виконання команди від root.

### Обгортки Nmap, запущені через sudo

Якщо дозволений через sudo шлях до `nmap` є shell-обгорткою, перевірте точний дозволений шлях і всі параметри, які вона передає. Блокування звичного написання `--script` не обов’язково блокує завантаження коду NSE: Nmap використовує [`--datadir`](https://nmap.org/book/man-misc-options.html) для вибору файлів даних, а NSE [завантажує `nse_main.lua`](https://nmap.org/book/nse-implementation.html) із вибраного каталогу даних, коли ввімкнено створення скриптів. Деякі встановлені збірки також приймають альтернативні написання довгих параметрів, тому порівнюйте обмеження з фактичним парсером цього бінарного файла. [`--excludefile`](https://nmap.org/book/man-target-specification.html) створює окрему поверхню для читання файлів; помилки парсера можуть розкрити їхній текст. Перевірте ефективне правило sudo, логіку обгортки, версію Nmap, контроль над каталогами й політику MAC, не запускаючи сканування під час інвентаризації.

### Hook Mercurial pull, запущені через sudo

Фіксоване джерело в `sudo hg pull /fixed/source` усе одно залишає репозиторій **призначення** вибраним через поточний робочий каталог, якщо команда не фіксує його параметром `-R`. У репозиторії призначення, контрольованому користувачем, можна визначити hook у `.hg/hgrc`, який може виконатися від імені користувача RunAs у sudo. [Mercurial ігнорує конфігурацію репозиторію, що належить недовіреному користувачу або групі](https://mercurial-scm.org/help/topics/config), тому перш ніж вважати це виконанням коду, перевірте довірених користувачів/групи облікового запису RunAs і точний робочий каталог. Для пасивної перевірки достатньо прочитати політику й конфігурацію; не запускайте pull і hook під час інвентаризації.

### Hook Git pull, запущені через sudo

Для точного дозволу `sudo git pull`, який може виконуватися від root, також перевірте репозиторій **призначення**, вибраний робочим каталогом. У репозиторії, що належить користувачу, можна налаштувати виконуваний hook `post-merge`, який запускається з ідентичністю процесу Git, коли pull успішно виконує злиття; [Git документує цей hook](https://git-scm.com/docs/githooks) і [поведінку pull із merge чи rebase](https://git-scm.com/docs/git-pull). Перевірте ефективне правило sudo й поточний робочий каталог, активний шлях до hook і його дозволи, а також те, чи можливе злиття з новими комітами. Невдалий, порожній pull або pull, що виконує лише rebase, не доводить наявності цього шляху через hook. Перегляньте політику й метадані репозиторію, не запускаючи привілейований pull.

### Копіювання архівів через rsync, запущений із sudo

Для `sudo rsync -a ... /writable/source/* /fixed/destination/` зірочка `*` у **шаблоні аргументів sudoers** може збігатися з пробілами й дозволити додатковий параметр між джерелом і призначенням. Це відрізняється від розгортання імен файлів shell-ом. Якщо користувач може наповнити джерело, а процес rsync із привілеями може записувати в каталог призначення, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) може запитати призначення привілейованого власника, тоді як режим архівування зберігає біти дозволів, що потенційно дає змогу створити файл із SetUID. Перевірте точну [семантику шаблонів-підстановок sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), версію rsync, подальші заборони, `nosuid` у файловій системі й політику MAC. Правило, що збігається з шаблоном, — лише привід для перевірки, а не доказ успішного підвищення привілеїв.

### Експорт правил фільтра пакетів, запущений через sudo

Необмежений дозвіл на `iptables` і `iptables-save`, що може виконуватися від root (або відповідну пару `ip6tables`), потребує перевірки можливості запису у файл. Збіг `comment` приймає текст правила, вибраний користувачем, а `iptables-save -f` записує серіалізований набір правил у вибраний шлях.<sup>[[20]](#references)[[21]](#references)</sup> Корисне навантаження залежить від того, як встановлений backend серіалізує коментарі та чи приймає файл призначення інші рядки експорту; сам `iptables-save` не забезпечує запис довільно вибраного вмісту. Перевірте точну ідентичність RunAs у sudo, аргументи й винятки, доступне розширення збігу, backend і дозволи місця призначення. Під час інвентаризації перегляньте дозвіл, не змінюючи правила firewall і не записуючи файл.

### Привілейований каталог журналів Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) уразливість у версіях Below до 0.9.0, які створювали доступний для запису всім каталог `/var/log/below`. Якщо служба чи команда, дозволена через sudo, запускає вразливу збірку від root, користувач із правами на запис і пошук у каталозі журналів без sticky bit може замінити запис журналу на symlink до того, як привілейований процес його відкриє. Перевірте стан виправлень установленого пакета, точний шлях привілейованого виконання, ефективний доступ до каталогу, sticky bit і ACL, а також метадані `/var/log/below/error_root.log`. Доступний для запису всім шлях або саме правило sudo не доводять наявність усього ланцюжка. Sticky-каталог чи backport від постачальника змінюють оцінку. Під час пасивної інвентаризації перевіряйте лише метадані; створювати symlink чи запускати привілейовану програму не потрібно.

### Привілейоване збирання пакета підтримки з контрольованих користувачем джерел

Скрипт профілю підтримки, дозволений через `sudo`, може читати фіксовані шляхи до журналів від root і копіювати їхній вміст до архіву профілю. Перевірте сам скрипт на читання файлів, а потім з’ясуйте, чи може користувач замінити шлях до джерела або будь-який запис батьківського каталогу на symlink. Якщо привілейоване читання переходить за цим посиланням, а отриманий архів доступний користувачу для читання, захищений файл можна розкрити. Потрібні всі умови: дозвіл sudo, шлях до джерела, доступний для запису, привілейоване читання й доступний для читання вивід; одного доступного для запису журналу чи імені профілю недостатньо. Перевіряйте ефективні дозволи й метадані посилань, не замінюючи файли й не створюючи профіль під час інвентаризації. [Рекомендації Nagios XI щодо підтримки](https://support.nagios.com/forum/viewtopic.php?t=62758) описують скрипт профілю, що запускається від root, і вихідний архів — це приклад того, чому слід обмежувати доступ до джерел і виводу таких пакетів.

### Скрипти відновлення архівів Python, запущені від root

Навіть суворо обмежене правило sudo для скрипту відновлення Python потребує перевірки вхідного архіву. Якщо користувач може вибрати або замінити архів, а скрипт розпаковує його від root через `tarfile.extractall(filter="data")`, перед використанням фільтра перевірте оновлення безпеки інтерпретатора. CPython виправив кілька обходів фільтрів для symlink і hard link, зокрема CVE-2025-4517, у версіях 3.9.23, 3.10.18, 3.11.13, 3.12.11 і 3.13.4. Backport від дистрибутива може виправити проблему в ранішій версії, тому показаний номер версії інтерпретатора сам по собі не доводить наявності вразливості.<sup>[[16]](#references)[[17]](#references)</sup>

Для пасивної перевірки прочитайте точну команду sudo й скрипт, простежте, який аргумент вибирає архів, і з’ясуйте, чи може поточний користувач записувати в архів або каталог, що його містить. Окремо перевірте виправлення постачальника для встановленого інтерпретатора й каталог розпакування; `filter="data"` не робить безпечним будь-який недовірений архів.<sup>[[16]](#references)[[17]](#references)</sup>

### Завантажувачі моделей машинного навчання, запущені через sudo

Правило sudo, що дозволяє вибрати файл `.pt`, `.pth` або `.ckpt`, потребує перевірки, якщо привілейований скрипт передає цей файл до [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` або іншого завантажувача на основі pickle. Перевірте ефективне правило RunAs, чи може користувач створити або замінити вибрану модель, і фактичний потік аргументів через будь-яку shell-обгортку до допоміжного Python-скрипту. Розширення `.pth` також використовується для не пов’язаних між собою файлів конфігурації Python site, тому саме розширення не доводить завантаження моделі. Сканування архіву чи статичне сканування pickle не доводить безпечність подальшого завантаження; перевірте [поведінку `weights_only`, залежну від версії](https://docs.pytorch.org/docs/stable/notes/serialization.html), і будь-які списки дозволених об’єктів. Див. [нотатки про pickle у ML та Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). Під час пасивної інвентаризації не завантажуйте й не розпаковуйте модель.

### Розбір виразів зі збережених даних, запущений через sudo

Фіксований Python-скрипт, запущений від root через sudo, усе одно може обробляти текст, який користувач із нижчими привілеями зберігає в базі даних програми. У TensorFlow виклик `preprocess_input_exprs_arg_string(value, safe=False)` вибирає шлях через `eval`; [рекомендація з безпеки TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) описує небезпечний парсер і виправлення для його виклику з командного рядка. Виклик із явним `safe=False` у програмі потрібно перевіряти окремо, навіть якщо цей виклик із командного рядка виправлено. Перевірте ефективне правило sudo, хто може змінювати конкретний запис вхідних даних, чи дозволяє фільтрація або оцінювання цьому запису дійти до виклику, а також поведінку встановленої функції. Версія TensorFlow, дозвіл sudo чи жорстко заданий файл моделі самі по собі не доводять наявність усього ланцюжка. Пасивно перевіряйте скрипт і потік даних; під час інвентаризації не запускайте привілейований helper і не надсилайте тестові вирази.

### Конфігурація needrestart, дозволена через sudo

`needrestart -c` завантажує вибраний користувачем конфігураційний файл Perl і виконує його вміст. Якщо `sudo -l` дозволяє запускати needrestart від root з аргументами, які дозволяють `-c`, а користувач може вибрати доступний для читання конфігураційний файл у каталозі, доступному для запису, цей дозвіл може призвести до виконання коду від root. Перевірте точні правило RunAs й аргументів sudo; правило з фіксованим списком аргументів може заблокувати цей шлях. Це окремо від уразливостей needrestart під час сканування інтерпретаторів: оновлення пакета чи вимкнення `interpscan` не робить безпечним необмежений дозвіл root на `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Імпорти Python від імені іншого облікового запису через sudo

Фіксована точка входу Python усе одно може імпортувати модуль, який користувач може редагувати чи замінювати, зокрема коли sudo запускає скрипт від імені **не root**, а службового користувача. Для буквального `from utils import status` перевірте локальні `utils/__init__.py` і `utils/status.py`, а також дозволи каталогу пакета. Перш ніж вважати доступний для запису файл шляхом виконання, перевірте шлях імпорту скрипту, точні дозволені аргументи sudo й те, чи доходить відповідна дія до цього імпорту. Під час інвентаризації перевіряйте файли й дозволи, не імпортуючи модуль і не запускаючи скрипт.<sup>[[2]](#references)[[3]](#references)</sup>

Для точного правила sudo на `python3 /absolute/script.py` скрипт має лише бути доступним для читання; йому не потрібні біт виконання чи shebang. Перевірте також **відсутні** локальні модулі: якщо скрипт імпортує модуль, файл якого можна створити в каталозі скрипту, доступному користувачу для запису, Python може завантажити його з ідентичністю RunAs. Перевірте ефективне правило sudo, фактичний [шлях пошуку модулів](https://docs.python.org/3/library/sys_path_init.html) інтерпретатора, чи є модуль вбудованим або frozen, і чи виконується імпорт. Для прямого правила sudo на запуск скрипту діють інші вимоги до біта виконання й shebang. Окрема обгортка, яка додає передані користувачем токени після `sudo -u account`, також потребує перевірки потоку аргументів: інший `-u` у цих токенах має значення лише тоді, коли викликана політика sudo дозволяє отриману ідентичність. Самих статичних рядків недостатньо, щоб довести будь-який із цих шляхів.

### Apache, запущений через sudo з контрольованою користувачем конфігурацією

Якщо правило sudo дозволяє запускати від імені привілейованого користувача `apachectl`, `apache2ctl` або `httpd` із контрольованим користувачем конфігураційним файлом `-f`, перевірте дозволи цього файла й батьківського каталогу. Директива Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) приймає назву модуля й **ім’я файла модуля**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) також завантажує файл. [`Include` й `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) можуть доповнювати конфігурацію або розкривати вміст файлів через помилки. Користувацька обгортка може перевіряти ці шляхи, скидати привілеї чи обмежувати аргументи, тому конфігурація, доступна для запису, — лише кандидат для перевірки, а не доказ виконання коду. Перш ніж робити висновок, перевірте канонізацію шляхів, symlink і розбір директив.

### nginx, запущений через sudo з контрольованою користувачем конфігурацією

Необмежене правило sudo для `nginx`, яке може виконуватися від root, може дозволяти вибирати іншу конфігурацію через [`-c`](https://nginx.org/en/docs/switches.html). Перевірте точні аргументи й винятки sudo, чи може користувач передати власну конфігурацію та чи зберігає master-процес або worker-дочірні процеси доступ до захищених шляхів. Комбінація вибраного `root` і `autoindex` може відкрити файли через новий listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) може надати шлях привілейованого запису у файл, але модуль DAV за замовчуванням не вбудовується — потрібно перевірити його наявність, доступність listener, дозволи на файли й поведінку тимчасових файлів. Директива [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) також може вказувати на вибраний файл; запис журналів у чутливий конфігураційний файл, наприклад `/etc/ld.so.preload`, стає шляхом підвищення привілеїв лише за наявності ефективного привілейованого запису та контрольованого запису журналу. Підсвітка виконуваного файла в `sudo -l` — привід для перевірки, а не доказ працездатності будь-якого з цих шляхів. Під час пасивної інвентаризації не запускайте й не переналаштовуйте nginx.

### Порівняння шаблонів у привілейованих запитах Bash

Якщо скрипт Bash, дозволений через sudo, читає значення від користувача й перевіряє його конструкцією `[[ "$expected" == $entered ]]`, Bash трактує не взятий у лапки правий операнд як шаблон. Тому шаблон із символом узагальнення може пройти порівняння без знання очікуваного значення. Взяття операнда в лапки (`[[ "$expected" == "$entered" ]]`) перетворює перевірку на буквальне порівняння рядків. Перевірте точне правило sudo, чи можна дійти до запиту й що скрипт робить після порівняння; сам синтаксис не доводить наявності експлуатованого шляху. Під час інвентаризації не виводьте очікуване значення. Див. [довідник умовних конструкцій Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper, запущені через sudo, які завантажують і виконують файл

Необмежений дозвіл sudo на користувацький helper, який може виконуватися від root, потребує перевірки потоку даних, якщо helper приймає вибрану користувачем URL-адресу, записує відповідь на диск, а потім запускає цей файл інтерпретатором або shell-командою. [Sudoers дозволяє довільні аргументи, якщо в записі команди їх не перелічено](https://man7.org/linux/man-pages/man5/sudoers.5.html); фіксований шлях до виконуваного файла не обмежує те, що можна вибрати аргументами. Перевірте фактичну валідацію URL, шлях виводу, гілку успішного виконання й подальший запуск у встановленій версії helper. Сам імпорт libcurl або рядок, видимий у бінарному файлі, не доводить наявності цього ланцюжка.

Навіть фіксоване базове ім’я вихідного файла можна підмінити між записом і виконанням, якщо helper використовує **відносний шлях у робочому каталозі, контрольованому користувачем**. Перейменування або заміна файла, що належить root, залежать від прав на запис і пошук у каталозі та обмежень sticky bit, а не лише від режиму самого файла; див. [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Перевірте, чи helper пізніше повторно відкриває шлях або використовує вже відкритий дескриптор і чи переходить він до довіреного каталогу перед записом. Пасивно перевірте політику sudo, helper і метадані каталогу; під час інвентаризації не запускайте привілейоване завантаження й не влаштовуйте гонку.

Helper для завантаження, запущений через sudo від root, також може дозволити **ін’єкцію аргументів**, якщо формує рядок команди Bash на кшталт `curl <caller input> -o <fixed output>`. Фільтр, що відхиляє пробіли, усе одно залишає доступним [розгортання дужок Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): елементи через кому без лапок можуть стати окремими аргументами curl. Якщо введені дані доходять до curl перед фіксованим `-o`, переданий користувачем параметр виводу може вибрати місце призначення першої URL-адреси від імені helper; [curl пов’язує параметри виводу з URL-адресами в порядку їх появи](https://curl.se/docs/manpage.html#-o). Перевірте точний shell, лапки, валідацію введення, ефективне правило sudo, порядок аргументів curl і підтримувані схеми URL, а також те, чи контролює користувач завантажені дані або може прочитати результат. Виконуваний файл, упакований за допомогою PyInstaller, може містити логіку Python-застосунку, але сама ознака пакування або рядок `curl` не доводять наявності цього потоку даних. Якщо це дозволено, перевірте обмежену автономну копію; під час звичайної інвентаризації не запускайте helper і не завантажуйте дані, вибрані зловмисником.

Shell-скрипт, запущений через sudo від root, який викликає [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), лише вибирає невикористане ім’я; він **не створює файл**. Якщо скрипт згодом створює файл із цим ім’ям у каталозі, на який може вплинути інший користувач, повторно його відкриває, а потім додає його вміст до захищеного файла, наприклад `authorized_keys` для root, перевірте можливу гонку з тимчасовим файлом. Перевірте точне правило sudo, власника каталогу й файла, послідовність створення та повторного відкриття, захисти ядра й те, чи використовує привілейований запис дані, контрольовані зловмисником. Сам рядок `mktemp -u` або доступний для запису `/tmp` не доводить наявності гонки. Перевіряйте скрипт і метадані шляхів, не запускаючи його й не влаштовуючи гонку з тимчасовим файлом під час інвентаризації.

## Примітки щодо захисту

- Не надавайте через sudo дозволи на інтерпретатори чи інтерактивні редактори.<sup>[[1]](#references)</sup>
- Не надавайте необмежені дозволи на універсальні засоби запису файлів, як-от `tee`. Використовуйте обгортку, що належить root, із фіксованим місцем призначення й відхиляйте шляхи, контрольовані користувачем.<sup>[[2]](#references)</sup>
- Віддавайте перевагу фіксованим обгорткам, що належать root і виконують одну вузькоспеціалізовану адміністративну дію.<sup>[[1]](#references)[[2]](#references)</sup>
- Якщо інтерпретатор необхідний, обмежте точний шлях до скрипту й забороніть контрольовані користувачем аргументи, імпорти, `PYTHONPATH` і небезпечне збереження змінних середовища.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Якщо потрібно редагувати файли, обмежте точний шлях до файла й розгляньте `sudoedit` із виправленими версіями sudo та суворою обробкою середовища.<sup>[[1]](#references)[[2]](#references)</sup>
- Перевірте `SETENV`, `env_keep`, робочі каталоги й шляхи імпорту, доступні для запису, `NOEXEC`, `use_pty` і журналювання, але не вважайте їх повноцінною пісочницею.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
