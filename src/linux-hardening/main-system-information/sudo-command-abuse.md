## Mit Sudo erlaubte Interpreter

Wenn `sudo -l` einem Benutzer erlaubt, einen Interpreter als root auszuführen, sollte dies als direkte Codeausführung behandelt werden. Interpreter sind dafür ausgelegt, beliebigen Code auszuführen. Eine Regel, die `python3`, `perl`, `ruby`, `lua`, `node` oder ähnliche Binärdateien erlaubt, entspricht daher normalerweise der Ausführung von Befehlen als root, sofern die Argumente nicht streng eingeschränkt und validiert werden.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Üblicher Prüfablauf: Zuerst die Berechtigungen des Benutzers auflisten, dann mit der Option `-c` des Interpreters eine Python-Anweisung ausführen.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Weitere Interpreter-Beispiele sind unten aufgeführt; die genannten Interpreter dokumentieren die Ausführung von Inline-Code oder APIs für Unterprozesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Der genaue Pfad ist entscheidend. Wenn die sudo-Regel `/usr/bin/python3` erlaubt, verwende bei der Validierung genau diesen Pfad.<sup>[[2]](#references)</sup>

Ein sudo-Executable-Glob wie `/usr/bin/python*` kann auch Python 2 zulassen, obwohl ein Skript für Python 3 geschrieben wurde. Wenn das Skript mit vom Aufrufer kontrolliertem Text `input()` erreicht, [wertet Python 2 diesen Text als Ausdruck aus](https://docs.python.org/2/library/functions.html#input); ein expliziter Interpreter-Aufruf setzt den Shebang des Skripts außer Kraft. Prüfe die installierten passenden Binaries, die effektive RunAs- und Argument-Policy, Verweigerungen und erreichbare Eingaben, bevor du dies als Ausführungspfad einstufst.

Ein fester Skriptpfad in einer root-fähigen sudo-Regel schränkt nicht ein, was das Skript ausführt. Prüfe bei einem lesbaren Bash-Wrapper, ob dessen erster ausführbarer Befehl einen nicht in Anführungszeichen gesetzten Positionsparameter wie `$1` als **Befehlswort** verwendet, während sudo vom Aufrufer ausgewählte Argumente erlaubt. Überprüfe die effektive RunAs-Identität, die Passwort- und Argument-Policy, spätere Verweigerungen und den tatsächlich ausgeführten Skriptzweig; `NOEXEC`, eine fest vorgegebene sichere Argumentliste oder ein Wrapper, der seinen Befehl validiert, können das Ergebnis verändern. Untersuche das kurze Skript während der Enumeration statisch, statt es mit einem Testbefehl aufzurufen.

Auch eine uneingeschränkte root-fähige sudo-Regel für `dotnet` sollte auf Interpreter geprüft werden. Wenn ein .NET SDK installiert ist, führt [`dotnet fsi` F#-Code interaktiv oder aus einem Skript aus](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), und [`dotnet run` führt ein Projekt aus dem Quellcode aus](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Prüfe zuerst die effektive RunAs-Identität und die genaue Argument-Policy: Eine Regel, die auf einen bestimmten sicheren Unterbefehl oder eine vertrauenswürdige Anwendung beschränkt ist, gewährt etwas anderes; außerdem kann bei einer reinen Runtime-Installation der SDK-Befehl fehlen. Der Name der ausführbaren Datei ist ein Hinweis darauf, was geprüft werden sollte, aber kein Beweis für Codeausführung.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo-erlaubte Editoren

Wenn `sudo -l` einem Benutzer erlaubt, einen interaktiven Editor als Root auszuführen, sollte dies als Angriffsfläche zur Befehlsausführung betrachtet werden und nicht als harmlose Berechtigung zur Dateibearbeitung. Editoren können häufig Shell-Befehle ausführen, beliebige Dateien lesen oder schreiben oder externe Hilfsprogramme direkt im Editor aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Üblicher Ablauf bei der Überprüfung: Zuerst die Berechtigungen des Benutzers auflisten, dann jeden erlaubten Editor oder Pager mit sudo starten.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano command execution

Wenn nano über sudo zugelassen ist, kann über die Editoroberfläche möglicherweise eine command execution erreicht werden.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Gib dann einen Befehl wie `id` oder `/bin/sh` in die nano-Eingabeaufforderung ein.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Wenn eine interaktive Shell keine nutzbaren Terminal-Streams hat, leitet diese Umleitungsform ihre Standardausgabe und Standardfehlerausgabe auf Dateideskriptor 0 um.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die genaue Tastenkombination kann je nach nano-Version und Build-Optionen variieren, aber das Sicherheitsproblem ist dasselbe: Der Editor läuft als root und kann externe Befehle aufrufen.<sup>[[1]](#references)[[12]](#references)</sup>

### Weitere gängige Editor-Escapes

Vim-ähnliche Editoren ermöglichen häufig die Ausführung von Befehlen über `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pager wie `less` können ebenfalls die Ausführung von Shell-Befehlen ermöglichen.<sup>[[14]](#references)</sup>

Eine sudo-Regel, die `apport-cli` als root erlaubt, sollte ebenfalls auf Pager geprüft werden. Betroffene Apport-Versionen konnten einen Absturzbericht in `less` mit einer vom Angreifer anpassbaren Terminalgröße öffnen; unter bestimmten sudo- und Pager-Bedingungen konnte der Pager dann eine root-Shell bereitstellen. Prüfe die effektive sudo-Regel, die Pager-Konfiguration und den Paket-Fix der Distribution, bevor du allein aufgrund der Version von einer Anfälligkeit ausgehst. Lies bei der passiven Enumeration Paket- und Richtlinienmetadaten aus, ohne einen Absturz auszulösen oder den privilegierten Bericht zu öffnen. [Ubuntus CVE-Eintrag](https://ubuntu.com/security/CVE-2023-1326) führt versionsspezifische behobene Paketversionen auf, darunter auch Versionen mit zurückportierten Fixes.

```text
!/bin/sh
```

## Weitere Gefahren durch sudo- und doas-Regeln

Beginne mit `sudo -l`, `sudo -V` und allen zutreffenden `doas`-Richtlinien. Lies den erlaubten Befehl, den RunAs-Benutzer, die Argumente, die Umgebung und die Defaults zusammen. Die Berechtigung, als Nicht-Root-Dienstkonto zu agieren, kann dennoch dessen Dateien offenlegen oder einen Weg zu Root bieten.

Ein festgelegtes, über sudo erlaubtes Python-Script kann dennoch einen Shell-Befehl unter seiner RunAs-Identität ausführen, wenn interaktive, vom Aufrufer kontrollierte Eingaben an [`os.system()`](https://docs.python.org/3/library/os.html#os.system) angehängt werden. Eine Denylist für Shell-Zeichen reicht nicht aus, um die Sicherheit nachzuweisen: [Die Shell erkennt auch die Befehlssubstitution `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Prüfe, ob die erlaubten Argumente den Eingabezweig erreichen, ob die Eingabe ohne sichere Validierung in den Shell-Befehl gelangt und ob die wirksame sudo-Richtlinie den vorgesehenen RunAs-Benutzer zulässt. Der Script-Pfad oder ein Aufruf von `os.system()` ist allein nur ein Prüfhinweis; untersuche den Quellcode, ohne das privilegierte Script aufzurufen.

Eine wirksame sudo-Berechtigung für `chattr` als Root kann das Dateiattribut „immutable“ (`i`) entfernen, gewährt für sich genommen aber weder Schreibzugriff noch eine neue Identität. Laut [Handbuch zu `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) verhindert das Attribut Änderungen, und nur Root oder ein Prozess mit `CAP_LINUX_IMMUTABLE` kann es ändern. Prüfe die genauen sudo-Argumentregeln und die Unterstützung durch das Dateisystem. Verifiziere anschließend separat, dass der Aufrufer nach dem Entfernen des Attributs in die Datei schreiben kann und dass ein Prozess mit höherer Identität sie verwendet. Ein Ersatz der Login-Shell erfordert beispielsweise auch gültige Anmeldedaten des Zielkontos und eine tatsächliche Anmeldung über diese Shell. Prüfe Richtlinien, Dateiattribute und Berechtigungen, ohne sie während der Erfassung zu ändern.

Wenn sudo sowohl ein Passwort als auch einen Einmalcode abfragt, behandle diese Voraussetzungen getrennt von der Befehlsberechtigung. Eine lesbare `.google_authenticator`-Datei enthält sensibles Seed-Material; ein alter Anwendungs- oder Datenbank-Passworthash ist dagegen nur ein möglicher Kandidat für das aktuelle Kontopasswort. Keines von beiden beweist, dass der jeweils andere Faktor von der wirksamen PAM-Konfiguration akzeptiert wird. Prüfe nach erfolgter Autorisierung den genauen RunAs-Benutzer und die Argumente: Eine uneingeschränkte Root-Berechtigung für RubyGems `gem` kann dessen Editor-Befehl freigeben ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)); eine eingeschränkte Berechtigung oder fehlgeschlagene Authentifizierung jedoch nicht. Bei einer passiven Erfassung sollten Pfade und Richtlinien gemeldet werden, ohne das Seed auszugeben, ein Passwort wiederherzustellen, einen Code zu erzeugen oder den privilegierten Befehl aufzurufen.

Eine uneingeschränkte, Root-fähige sudo-Berechtigung für Chef `knife` erfordert eine Prüfung auf Interpreter-Ebene: [Chef dokumentiert, dass `knife exec -E` lokal einen Ruby-String auswertet](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Prüfe, ob die wirksame sudo-Regel das Unterkommando `exec` und das vom Aufrufer angegebene Argument `-E` zulässt, welche RunAs-Identität vorgesehen ist und ob passende Befehlsverbote oder feste Argumente gelten. Die installierte Binärdatei oder eine auf andere Unterkommandos beschränkte Regel ist nur ein Hinweis. Bei einer passiven Erfassung sollte die Richtlinie gemeldet werden, ohne `knife` aufzurufen.

Eine exakte, Root-fähige sudo-Berechtigung für ein interaktives `msfconsole` ist ähnlich sensibel: [GTFOBins dokumentiert dessen `irb`-Konsole](https://gtfobins.org/gtfobins/msfconsole/), die die sudo-Identität übernehmen kann. Prüfe den wirksamen RunAs-Benutzer, die erlaubte Argumentliste, Befehlsverbote, `NOEXEC` oder andere Einschränkungen, das Verhalten der installierten Konsole und ob der Aufrufer interaktive Eingaben liefern kann. Ein hervorgehobener Pfad ist nur ein Prüfhinweis; bei einer passiven Erfassung sollte die Konsole nicht gestartet werden.

Auf FreeBSD sollte selbst eine auf `pkg update` als Root und `pkg install *` beschränkte sudo-Regel eine Prüfung des Repository-Vertrauens auslösen. Prüfe, ob `/etc/hosts` für den Aufrufer beschreibbar ist und ob die *wirksame* aktivierte Repository-Konfiguration einen HTTP-Hostnamen mit `signature_type: none` verwendet. Laut [FreeBSD-Handbuch zu `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) deaktiviert `none` Signaturprüfungen; `pkg+http` allein weist das nicht nach. Ein Paket kann Installations-Scripts enthalten ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)). Wer den Repository-Endpunkt tatsächlich kontrolliert und ein Paket auswählen kann, könnte daher die Root-Grenze überschreiten. Prüfe Repository-Overrides, SRV-/Mirror-Auflösung, wirksame sudo-Argumente, Paketauswahl und Script-Ausführung, bevor du zu diesem Schluss kommst. Untersuche Richtlinien und kleine lokale Konfigurationsdateien, ohne Namen umzuleiten oder während der Erfassung `pkg` auszuführen.

Eine Root-fähige sudo-Berechtigung für `apt-get update` und `apt-get upgrade` erfordert ebenfalls eine Prüfung des Repository-Vertrauens, wenn sudo ein vom Aufrufer kontrolliertes `http_proxy` beibehält. Prüfe, ob die wirksame APT-Proxy-Konfiguration diese Variable tatsächlich verwendet und welche aktivierten Repository-Anfragen davon betroffen sein können. Ein Proxy allein kann keine Pakete aus einem Archiv ersetzen, das mit einem vertrauenswürdigen Signierschlüssel authentifiziert wurde. Das [APT-Handbuch zum HTTP-Transport](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) beschreibt die Proxy-Priorität; [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) behandelt Signaturprüfungen, Overrides für unsichere Repositories und Bestätigungen für nicht authentifizierte Pakete. Prüfe den genauen sudo-RunAs-Benutzer und die Argumente, die Richtlinie zur Repository-Authentifizierung, eine etwaige erforderliche interaktive Bestätigung und ob das ausgewählte Upgrade Package-Scripts als Root ausführt. Untersuche Richtlinien und lokale Konfiguration passiv; leite während der Erfassung keinen Paketverkehr um und führe kein Upgrade aus.

Eine Root-fähige sudo-Regel für `snap install` kann eine Paket-zu-Code-Grenze schaffen, wenn die Argumente dem Aufrufer die Auswahl eines lokalen Snaps und eines permissiven Installationsmodus erlauben. [Snap dokumentiert](https://snapcraft.io/docs/explanation/snap-development/install-modes/), dass `--dangerous` die Assertion-Prüfung für lokale Snaps überspringt und `--devmode` die Einschränkung der Ausführungsumgebung lockert; [ein Installations-Hook kann bei der Erstinstallation ausgeführt werden](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prüfe die genauen sudo-Argument- und RunAs-Regeln, wer die Snap-Datei kontrolliert, ob die installierte Version von snapd diese Modi akzeptiert und welche effektive Identität und Einschränkungen für den Hook gelten, bevor du Zugriff auf geschützte Host-Dateien annimmst. Eine `snap`-Binärdatei oder eine scheinbar mit Wildcards versehene Regel beweist diese Kette allein nicht. Bei einer passiven Erfassung sollte weder ein Paket installiert noch dessen Hook ausgeführt werden.

Bei einer exakten sudo-Berechtigung für eine benutzerdefinierte, Anmeldedaten lesende Binärdatei eines **Nicht-Root-Kontos** solltest du zunächst die gewährte Binärdatei und ihre Dateiberechtigungen prüfen, ohne sie auszuführen. Ein eingebetteter Passwortschutz ist möglicherweise nur als Wide-Character-Text erkennbar; [GNU `strings` dokumentiert die Extraktion von 16-Bit-Little-Endian-Text](https://sourceware.org/binutils/docs/binutils/strings.html). Eine sichtbare Zeichenfolge beweist weder, dass es das akzeptierte Passwort ist, noch dass der Erfolgszweig aktuelle Anmeldedaten offenlegt. Prüfe das Verhalten der Binärdatei, den Zugriff des Zielkontos auf die geschützten Daten, die Gültigkeit der Anmeldedaten und einen späteren Wechsel von Konto oder Gruppe separat. Gehört das Konto zur Gruppe `docker`, prüfe den Socket-Zugriff sowie, ob der Daemon mit Root oder Rootless läuft, bevor du auf Host-Root-Zugriff schließt; [Docker dokumentiert die Root-Auswirkungen dieser Gruppe](https://docs.docker.com/engine/install/linux-postinstall/). Bei der üblichen Erfassung sollten die sudo-Regel und die Gruppenmitgliedschaft gemeldet werden, ohne die Binärdatei auszuführen oder ihre Zeichenfolgen auszugeben.

Eine sudo-Regel mit Wildcard für Wartungs-Scripts einer Anwendung muss über den Script-Pfad hinaus geprüft werden. Prüfe, ob das erlaubte Script uneingeschränkte Argumente akzeptiert oder Einstellungen liest, die über ein weniger privilegiertes Anwendungskonto beschreibbar sind. Verfolge anschließend diese Werte bis zu Shell-Befehlen oder einer Subprozess-Umgebung. Zum Beispiel setzt ZoneMinders [`zmupdate.pl` einen `mysqldump`-Befehl zusammen und führt ihn über `qx` aus](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), während [`zmdc.pl` die Einstellung `ZM_LD_PRELOAD` in `LD_PRELOAD` kopiert](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in), bevor Daemons gestartet werden. Eine sudo-Regel, die eines der beiden Scripts als Root erlaubt, kann eine Vertrauensgrenze überschreiten, wenn die entsprechende Eingabe kontrollierbar ist und in der installierten Version diesen Code erreicht. Prüfe die wirksame sudo-Regel, die Berechtigungen der Anwendungskonfiguration und den Script-Quellcode. Die Wildcard oder Einstellung allein ist nur ein Prüfhinweis, kein Beweis für eine Ausführung.

- `SETENV`, `env_keep`, `secure_path` und `LD_PRELOAD` können einen ansonsten eng begrenzten Befehl in einen Import-, Library- oder PATH-Hijack verwandeln. Siehe den [Leitfaden zu Umgebungsvariablen](../linux-basics/linux-environment-variables.md) und [SUID-/Linker-Missbrauch](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Auch eine exakte, Root-fähige `SETENV`-Berechtigung für einen Shell-Wrapper sollte mit einem kurzen Prüfpfad untersucht werden, wenn der Wrapper ein festes Python-Script mit einem Literal-Import startet. `secure_path` beschränkt die Suche der Shell nach Befehlen, nicht die [Modulsuche von Python über `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` und `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) veranlassen Python, diese Umgebungsvariable zu ignorieren. Prüfe die wirksamen sudo-Tags und Verbote, den Wrapper-Zweig, die Interpreter-Optionen, die Import-Auflösung und ein vom Aufrufer beschreibbares Suchverzeichnis, bevor du dies als Code-Ausführung einstufst. Untersuche kurze Scripts statisch; rufe den privilegierten Wrapper nicht auf.

Eine exakte, Root-fähige sudo-Berechtigung für `neofetch ""` kann dennoch eine Shell-Konfiguration laden, wenn die zutreffenden sudo-Defaults das vom Aufrufer kontrollierte `XDG_CONFIG_HOME` beibehalten. [Neofetchs Konfigurationslader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) lädt `neofetch/config.conf` oder `neofetch/config` aus diesem Verzeichnis. Die leere Argumentliste verhindert diese Suche nicht. Prüfe den installierten Lader, die wirksame RunAs- und Argumentrichtlinie, etwaige Befehlsverbote, ob sudo die gewählte Variable für diesen Befehl tatsächlich beibehält und ob der Aufrufer einen lesbaren Konfigurationspfad kontrolliert. Eine beibehaltene Variable oder ein installiertes Neofetch ist allein nur ein Prüfhinweis. Untersuche Richtlinien und Dateimetadaten, ohne den privilegierten Befehl aufzurufen oder Konfigurationsinhalte auszugeben; siehe [Umgebungsverarbeitung durch sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Eine uneingeschränkte, Root-fähige sudo-Regel für `facter` erfordert eine separate Prüfung benutzerdefinierter Facts. [Puppet dokumentiert](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), dass `--custom-dir` Ruby-Fact-Dateien aus einem ausgewählten Verzeichnis lädt. Prüfe, ob die genaue sudo-Regel diese Option zulässt, ob die installierte Facter-Version sie akzeptiert und ob der Aufrufer das Verzeichnis kontrolliert. Eine Berechtigung mit festen Argumenten, ein explizites Befehlsverbot oder deaktivierte benutzerdefinierte Facts können das Ergebnis ändern. Bei einer passiven Erfassung sollte der mögliche Richtlinienpfad gemeldet werden, ohne Facter aufzurufen oder Fact-Inhalte zu lesen.

Bei einer exakten, Root-fähigen sudo-Berechtigung für ein Script mit `SETENV` solltest du unqualifizierte Befehlsnamen wie `find` und den wirksamen `PATH` nach Anwendung der sudo-Richtlinie und Script-Initialisierung prüfen. Eine eingebundene Bash-Datei kann auch `enable -n [` ausführen: [Bash sucht dann über `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) nach einem externen `[` für spätere Aufrufe dieses Befehls im Script. Prüfe die einschlägigen [sudoers-Regeln für Umgebung und `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), etwaige `NOSETENV`-/`NOEXEC`- oder Verbots-Einträge, den Ablauf des Scripts und eingebundener Dateien sowie ein ausführbares, vom Aufrufer kontrolliertes Suchverzeichnis. Ein lesbares Script mit einem unqualifizierten Befehlsnamen ist ein Prüfhinweis, kein Beweis für privilegierte Ausführung; untersuche es, ohne die sudo-Regel aufzurufen.
- Ein privilegiertes Script, das mit `curl` eine feste URL abruft, kann dennoch eine vom Aufrufer ausgewählte Antwort akzeptieren, wenn eine zutreffende sudo-Regel `http_proxy` beibehält und die Anfrage über diesen Proxy läuft. Übergibt das Script die Antwort anschließend an einen XML-Parser, der externe Entitäten auflöst, kann eine bösartige Antwort Dateien offenlegen, die der privilegierte Prozess lesen kann. Prüfe die genauen sudo-Umgebungsregeln, `no_proxy`-Ausnahmen, die angeforderte URL, die Parser-Konfiguration und das Ausgabeverzeichnis; eine Proxy-Variable oder ein XML-Parser allein ist keine Schwachstelle. Die [curl-Dokumentation zu Proxy-Umgebungsvariablen](https://everything.curl.dev/usingcurl/proxies/env.html) beschreibt das Verhalten dieser Variablen. Führe bei einer passiven Erfassung keine Netzwerkanfragen aus und parse kein bösartiges XML.
- Ein Root-fähiges sudo-Script, das aus vom Aufrufer beeinflussten Daten eine PostScript-Datei erstellt und danach `ps2pdf -dNOSAFER` ausführt, erfordert eine separate Prüfung des Eingabeflusses. Laut Ghostscript-Dokumentation deaktiviert diese Option SAFER bis `.setsafe` und ermöglicht so PostScript-Dateioperationen im Rahmen der OS-Berechtigungen des Prozesses. Eine aus einem Aufruferargument zusammengesetzte SQL-Abfrage kann vom Angreifer kontrollierte Zeilen in die PostScript-Vorlage einspeisen. Eine Abfragezeichenfolge oder ein Aufruf von `ps2pdf` allein beweist jedoch nicht, dass die Daten ausführbare PostScript-Syntax erreichen. Prüfe die wirksame sudo-Regel, den genauen Pfad von der Eingabe zur Vorlage, etwaige Escaping-Schritte, das Verhalten der installierten Ghostscript-Version und ob SAFER vor der Interpretation des Dokuments wieder aktiviert wird. Rufe die privilegierte Konvertierung bei einer passiven Erfassung nicht auf. Siehe die [Ghostscript-Dokumentation zu `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Bei einer sudo-Regel für ein Shell-Script solltest du beibehaltene Variablen mit dem Script selbst vergleichen. Ein Konstrukt wie `if $CHECK_CONTENT; then` führt den expandierten Wert als Befehl aus. Daher kann das Beibehalten von `CHECK_CONTENT` die Befehlsausführung ermöglichen, selbst wenn Script-Pfad und Argumente feststehen. Für die jeweilige Regel muss geprüft werden, ob der Zweig erreichbar ist und ob die Umgebung tatsächlich beibehalten wird.<sup>[[2]](#references)[[22]](#references)</sup>
- Ein über sudo erlaubtes Python-Script kann Code aus einem beschreibbaren Verzeichnis oder einer zwischengespeicherten `.pyc`-Datei importieren. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md) behandelt den Cache-Fall.
- Ein festes, als Root erlaubtes Python-Script kann dennoch einen interaktiven Debugger offenlegen. Aufrufe wie `pdb.set_trace()` oder `pdb.post_mortem()` ermöglichen Python-Anweisungen im Kontext des debugten Prozesses, wenn der Aufrufer den Breakpoint oder Exception-Handler erreichen **und den Eingabestrom des Debuggers kontrollieren kann**. Prüfe die genaue sudo-RunAs-Regel, Authentifizierung und Zweigbedingungen, die Erreichbarkeit der Exception, den Besitz des Terminals bzw. Eingabestroms und ob der Debugger im selben privilegierten Prozess läuft. Eine Socket-Anfrage, die eine Exception auslöst, gewährt nicht automatisch Zugriff auf einen Debugger an einem anderen Terminal. [Python dokumentiert die Auswertung von Anweisungen durch den Debugger und den Post-mortem-Modus](https://docs.python.org/3/library/pdb.html); untersuche das Script statisch, statt den privilegierten Handler während der Erfassung auszulösen.
- Ein festes, über sudo erlaubtes Python-Script kann außerdem ein Profilfeld aus einer Datenbank oder einem Unix-Socket lesen und an eine Zeichenfolge anhängen, die später zur **Formatzeichenfolge** für `str.format()` wird. [Ersetzungsfelder können auf Attribute und Mapping-Schlüssel verweisen](https://docs.python.org/3/library/string.html#format-string-syntax). Ein vom Angreifer kontrolliertes Feld kann daher Objekte untersuchen, die an `format()` übergeben werden, und Daten offenlegen, auf die diese Objekte zugreifen können, sofern das Ergebnis ausgegeben oder an einem für den Aufrufer lesbaren Ort gespeichert wird. Prüfe die wirksame sudo-RunAs-Identität, Schreibzugriff auf den betreffenden Datensatz, den Datenfluss in die Formatzeichenfolge, die übergebenen Objekte und die Sichtbarkeit der Ausgabe. Dies ist keine automatische Code-Ausführung; eine vertrauenswürdige Formatzeichenfolge mit vom Angreifer kontrollierten *Werten* ist ein anderer Fall. Ein offengelegtes Geheimnis ermöglicht einen Wechsel zu einem OS-Konto nur, wenn dieses Konto es akzeptiert. Prüfe das Script und die Socket-Berechtigungen, ohne die privilegierte Operation aufzurufen.
- Ein Root-fähiger Python-Wrapper kann eine vom Aufrufer gewählte URL an GitPython `Repo.clone_from` übergeben. Aktiviert der Wrapper außerdem Git-`protocol.ext.allow=always`, kann ein `ext::`-Remote einen externen Helper aufrufen. Prüfe die genauen sudo-Argumente, die Herkunft der URL, die Version des GitPython-Pakets samt Hersteller-Patches und ob der Wrapper unsichere Protokolle ausdrücklich erlaubt. GitPython führte in Version 3.1.30 eine [standardmäßige Schutzmaßnahme gegen unsichere Protokolle](https://github.com/gitpython-developers/GitPython/commit/2625ed9) ein; die Version der ausführbaren `git`-Datei ist davon unabhängig. Eine passive Prüfung sollte nur die Regel und einen begrenzten Quellcodeausschnitt lesen, ohne den Clone auszuführen.
- Eine sudo-Berechtigung für einen CLI-Clone-Befehl als anderes Konto kann einen separaten Pfad für Shell-String-Injection eröffnen. Verfolge, ob das vom Aufrufer gewählte Repository-Argument Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) oder einen anderen Shell-Befehlsaufbau ohne sichere Trennung von Argumenten erreicht. Node-`exec` übergibt seinen Befehlsstring an eine Shell. Prüfe den genauen RunAs-Benutzer, erlaubte Unterbefehle und Argumente, den installierten Wrapper-Code und die Eingabevalidierung. Der Name eines Repository-Tools oder eine uneingeschränkte sudo-Regel beweist keine Command Injection. Untersuche den Wrapper, ohne während der Erfassung einen privilegierten Clone auszuführen.
- Ein benutzerdefinierter, Root-eigener Wrapper kann sicher erscheinen, weil seine Binärdateien und Scripts nicht beschreibbar sind, obwohl die Entscheidung, eine privilegierte Aktion auszuführen, von einem Flag, einem lokalen API-Wert oder einem Dienstzustand abhängt, den ein unprivilegierter Benutzer ändern kann. Verfolge jede solche Bedingung bis zu ihrer Eingabe und den Autorisierungsprüfungen zurück. Untersuche während der Erfassung Konfiguration und Berechtigungen, ohne den Betriebszustand zu ändern; ein `systemd-run`-Aufruf im Wrapper ist nur relevant, wenn die Bedingung beeinflussbar ist.
- Ein über sudo als Root erlaubter Backup-Client kann eine vom Aufrufer ausgewählte Konfigurationsdatei akzeptieren (zum Beispiel `npbackup-cli -c`). Prüfe den genauen RunAs-Benutzer und die zulässigen Argumente sowie, ob der Aufrufer den Konfigurationspfad, die Backup-Quellpfade und Repository- oder Lese-/Wiederherstellungsoptionen kontrolliert. Ein verschlüsseltes Repository-Geheimnis in einer lesbaren Konfiguration kann für den Client nutzbar sein. Die Regel allein beweist jedoch weder den Repository-Zugriff noch die Offenlegung von Root-Dateien. Prüfe die Berechtigungen, ohne ein Backup auszuführen oder Inhalte auszugeben.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) unterstützt `--password-command`, das ein Programm zum Abrufen des Repository-Passworts aufruft. Erlaubt eine sudo-Regel einem weniger privilegierten Benutzer, Restic als Root mit einem selbst gewählten Passwortbefehl und einem Unterbefehl auszuführen, der das Passwort benötigt, kann der Helper als Root laufen. Prüfe die genauen sudo-Argumente und Ausschlüsse; rufe den Helper oder einen Backup-Befehl nicht allein zur Erfassung dieser Bedingung auf.
- Eine privilegierte Berechtigung für `restic backup` kann auch eine Dateilesen-Grenze überschreiten, wenn das sudo-Argumentmuster dem Aufrufer erlaubt, sowohl die Quelle als auch ein später lesbares und entschlüsselbares Repository auszuwählen. [Argument-Wildcards in sudoers können Leerzeichen und Schrägstriche erfassen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf). Prüfe daher abschließende Wildcards, statt anzunehmen, ein festes Repository-Präfix begrenze die Quelle. [Restic kann in lokale und entfernte Repositories sichern](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), doch ein lokales Repository kann neu geschriebene, nur für Root lesbare Objekte enthalten. Prüfe die wirksame sudo-Richtlinie, Backend-Zugriff, Repository-Passwort und Berechtigungen der resultierenden Objekte, bevor du dies als Offenlegung wertest. Ein gesicherter SSH-Schlüssel ermöglicht nur dann Zugriff, wenn das Zielkonto ihn akzeptiert. Führe während einer passiven Prüfung kein Backup zu Testzwecken aus.
- Ein uneingeschränkter benutzerdefinierter Wartungs- oder Backup-Befehl kann einen Ausgabepfad akzeptieren oder einen eigenen Job-Scheduler bereitstellen. Für einen Dateischreibpfad solltest du die genaue sudo-Regel und den RunAs-Benutzer prüfen sowie, ob der Aufrufer sowohl Daten als auch Ziel kontrolliert. Für einen Pfad über geplante Befehle solltest du die Ausführungsidentität des Schedulers, die Befehlseingabe und jede zusätzliche Passwort- oder Autorisierungsbedingung prüfen. Der Befehlsname oder `NOPASSWD` allein belegt keinen der beiden Pfade. Siehe [Schreiben in Root-eigene Dateien](../interesting-files-permissions/write-to-root.md) und [Cron und systemd-Timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Ein fester sudo-Befehl kann dennoch eine vorhersehbare Konfigurationsdatei aus einem gemeinsam beschreibbaren Verzeichnis laden. Verfolge, ob der Aufrufer diese Datei ersetzen kann und ob deren Quell- und Zielfelder einen privilegierten Abruf oder Kopiervorgang steuern. Eine URL zu einer lokalen Datei kann Daten offenlegen, die nur das sudo-RunAs-Konto lesen kann; eine vom Aufrufer kontrollierte Quelle in Verbindung mit einem geschützten Ziel kann einen Schreibpfad schaffen. Prüfe das URL-Verhalten des installierten Programms, Zielpfadprüfungen, die wirksame sudo-Regel und die Zugänglichkeit der Ausgabe. Ein beschreibbarer Konfigurationspfad unter `/tmp` ist allein nur ein Prüfhinweis; untersuche Binärdatei und Dateimetadaten, ohne den privilegierten Transfer auszuführen.
- Eine sudo-Regel für `git apply` kann bewirken, dass der RunAs-Benutzer Dateien schreibt, die durch einen vom Aufrufer kontrollierten Patch ausgewählt werden. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) ermöglichte es einem präparierten Patch, einen Symlink anzulegen und anschließend außerhalb des Arbeitsverzeichnisses zu schreiben, selbst wenn der Befehl `--unsafe-paths` nicht akzeptierte. Prüfe die wirksame sudo-Argumentregel, die Patch-Quelle, den Zugriff des RunAs-Benutzers auf das Arbeitsverzeichnis und den installierten Git-Fix oder Hersteller-Backport. Eine uneingeschränkte Regel, die `--unsafe-paths` zulässt, ist ein separates Risiko durch eine explizite Option. Weder eine Git-Version noch eine `git apply`-Berechtigung allein beweist, dass eine geschützte Datei geändert werden kann. Wende bei einer passiven Erfassung keinen nicht vertrauenswürdigen Patch an.
- Eine Root-fähige sudo-Regel für `clamscan --debug` kann eine Leseberechtigungsgrenze überschreiten, wenn ein weniger privilegierter Benutzer ein DMG-Image bereitstellen kann und der installierte Parser von [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) betroffen ist, durch das Dateiinhalte über Debug-Ausgaben offengelegt werden konnten. Prüfe die genau erlaubten Argumente und den Scan-Pfad, die Kontrolle über die Eingabe, das wirksame RunAs-Konto, Engine-Fix oder Backport und ob die Ausgabe für den Aufrufer sichtbar ist. Erlaubt eine umfassendere Regel `--file-list`/`-f`, prüfe dieses Verhalten separat; eine auf `--debug <scan-path>` festgelegte Richtlinie lässt diese Option nicht zu. Untersuche Richtlinien und Paketmetadaten, ohne bei der Erfassung eine präparierte Datei zu scannen oder geschützte Ausgaben auszugeben.
- Eine Root-fähige sudo-Regel, die ein vom Aufrufer ausgewähltes verschlüsseltes Disk-Image öffnet, sowie eine zweite Regel, die den daraus resultierenden Mapper einhängt, kann vom Aufrufer kontrollierte Dateien in den Mount-Namespace des Hosts importieren. Prüfe beide wirksamen Regeln und Argumente, die Kontrolle über das Image und den Mapper-Namen, das tatsächliche Einhängeziel sowie Eigentümer und Modus der resultierenden Dateien. Für einen Wechsel über Set-User-ID sind zusätzlich eine zugängliche ausführbare Datei, Mount-Optionen, die dies zulassen (`nosuid` verhindert es), und die einschlägige Prozess- oder MAC-Richtlinie erforderlich; das Öffnen oder Einhängen eines Images allein ist nur ein Prüfhinweis. Ein separater Weg über ein vorhandenes Backup setzt dessen tatsächlichen Schlüssel und ein darin enthaltenes, nützliches und lesbares Geheimnis voraus. Untersuche Richtlinien und Pfade, ohne während einer passiven Erfassung ein Image zu öffnen oder einzuhängen. Siehe das [Handbuch zu cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) und [Mount-Optionen](https://man7.org/linux/man-pages/man8/mount.8.html).
- Eine Root-fähige sudo-Regel für ein Shell- oder Python-Script erfordert eine Prüfung des Arbeitsverzeichnisses, wenn das Script `./helper` aufruft, ohne vorher in ein festgelegtes Verzeichnis zu wechseln. Eine Python-Liste wie `['./helper']`, die an `subprocess.run` übergeben wird, kann dasselbe Verhalten hinsichtlich des vom Aufrufer ausgewählten Arbeitsverzeichnisses haben. Der Aufrufer kann möglicherweise ein beschreibbares Verzeichnis auswählen und dort eine ausführbare Datei mit diesem relativen Namen ablegen; ein absoluter Pfad an anderer Stelle im Script schützt diesen Aufruf nicht. Prüfe die wirksame Regel, `runchdir` oder eine andere Richtlinie zum Verzeichniswechsel, den Script-Ablauf und die Erreichbarkeit des Zweigs, ein beschreibbares und ausführbares Verzeichnis sowie Mount- und `NOEXEC`-Einschränkungen, bevor du dies als Code-Ausführung bewertest. Ist das Script nicht lesbar, bleibt das Verhalten unbekannt, bis sein Quellcode über einen autorisierten Weg geprüft wurde. Untersuche Scripts statisch, statt den Helper auszuführen. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) dokumentiert Richtlinien für das Arbeitsverzeichnis.
- Ein fester, Root-fähiger Python-Validator kann dennoch eine vom Aufrufer ausgewählte Datendatei auswerten. Die [Python-Dokumentation zu `eval()` warnt vor nicht vertrauenswürdigen Eingaben](https://docs.python.org/3/library/functions.html#eval): Eine Eingabe-Suffixprüfung, ein arithmetisches Präfix oder ein Validierungszweig ist keine Sandbox, wenn der verbleibende Ausdruck `eval` erreicht. Prüfe die wirksame sudo-Regel, ob der Aufrufer die konkrete Datei auswählen und kontrollieren kann, die Zweigbedingungen des Parsers und den Aufbau des Ausdrucks sowie die Identität des privilegierten Prozesses, bevor du dies als Ausführungspfad einstufst. Das Vorkommen von `eval` in einem lesbaren Script ist allein nur ein Prüfhinweis; untersuche Quellcode und Dateiberechtigungen, ohne den Validator auszuführen oder bei der Erfassung einen Testausdruck einzuspeisen.
- Ein Root-fähiger sudo-Ruby-Wrapper, der einen relativen YAML-Dateinamen wie `YAML.load(File.read("dependencies.yml"))` liest, kann Eingaben aus dem Arbeitsverzeichnis des Aufrufers verwenden, sofern weder der Wrapper noch die sudo-Richtlinie dieses Verzeichnis festlegt. Prüfe die genau erlaubten Argumente, Verzeichnis- und Dateiberechtigungen sowie das Verhalten der installierten Psych-Version: Ältere Implementierungen von `YAML.load` konnten beliebige Ruby-Objekte deserialisieren, während neuere Versionen Klassen standardmäßig einschränken. Eine statische Aufrufstelle ist nur ein Prüfhinweis; bestätige, dass die Datei aus einem vom Aufrufer beschreibbaren Verzeichnis stammt und der installierte Loader gefährliche Klassen akzeptiert. Für nicht vertrauenswürdige Eingaben sollte `safe_load` mit einer ausdrücklich festgelegten, minimalen Klassen-Allowlist bevorzugt werden. Siehe die [Psych-Dokumentation zu Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) und die [Psych-Dokumentation zu Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Eine exakte, Root-fähige Berechtigung für `sudo go run /absolute/file.go` verdient eine Prüfung des Arbeitsverzeichnisses, wenn der Go-Quellcode eine relative WASM-Datei liest und abhängig vom Ergebnis möglicherweise ein relatives Shell-Script ausführt. Prüfe den wirksamen RunAs-Benutzer, Befehlsargumente und Verbote, ein vom Aufrufer beschreibbares aktuelles Verzeichnis, den Datenfluss von WASM zum Zweig und ob dieser Zweig den Helper aufruft. Ein festgelegtes sudo-`runchdir`, `os.Chdir` oder [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) kann den Suchort ändern. Ein statisches gemeinsames Auftreten ist nur ein möglicher Prüfhinweis; untersuche den Quellcode, ohne Go, WASM oder den Helper auszuführen.
- `sudoedit` und Argument-Wildcards erfordern genaue Versions- und Regelprüfungen; die [Checkliste](linux-privilege-escalation-checklist.md) enthält das Problem beim Bearbeiten von Dateien mit sudoedit. Bei einer sudoedit-Berechtigung für ein anderes Konto mit einem Pfad-Wildcard solltest du die wirksamen Einstellungen `sudoedit_follow` oder `FOLLOW`, `sudoedit_checkdir`, das aufgelöste Ziel und prüfen, wer jeden übergeordneten Verzeichniseintrag ersetzen kann. Erstere kann das Folgen eines Symlinks erlauben; die Deaktivierung Letzterer entfernt Prüfungen auf beschreibbare Verzeichnisse. Keine der beiden Einstellungen allein belegt, dass eine Datei eines anderen Benutzers beschrieben werden kann. Prüfe vor dieser Schlussfolgerung die installierte sudo-Richtlinie und die genau passenden Argumente. Siehe die [Definitionen der sudoers-Optionen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In einer sudoers-Befehlsregel kann eine Argument-Wildcard sowohl Leerraum als auch Pfadzeichen erfassen. Eine Regel für einen lesefähigen Befehl mit einem Argument wie `/restricted/*` kann daher nach einem passenden Präfix ein zusätzliches Dateiargument zulassen. Prüfe den genauen RunAs-Benutzer, den Befehlspfad, das Argumentmuster und spätere Verbote; ein nachgewiesener Dateizugriff bedeutet nicht automatisch Befehlsausführung. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unterscheidet Argument-Globs von Befehdspfad-Globs.
- Ein pfadähnliches Argument-Glob kann auch `../` erfassen. Zum Beispiel kann eine Root-fähige Regel `node /opt/scripts/*.js` einem Aufrufer eine kontrollierte JavaScript-Datei außerhalb von `/opt/scripts` erlauben, wenn der angegebene Pfad weiterhin mit `/opt/scripts/` beginnt und über Segmente mit übergeordneten Verzeichnissen aufgelöst wird. Dies ist ein **Argument**-Glob; für das Befehdspfad-Glob der ausführbaren Node-Datei gelten andere Regeln für Schrägstriche. Prüfe die wirksame Regel, spätere Verbote, die Pfadauflösung, die Kontrolle über die Zieldatei und etwaige sudoers-Regulärausdrücke oder Digest-Einschränkungen, bevor du auf Code-Ausführung schließt. Siehe die [sudoers-Wildcard-Regeln](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) und die [Node-Dokumentation zur Kommandozeile](https://nodejs.org/api/cli.html).
- Archivierungs- und andere Dienstprogramme können Ausführungs-Hooks haben. Prüfe die genau erlaubten Argumente anhand von [GTFOBins](https://gtfobins.github.io/), statt anzunehmen, nur Shells oder Interpreter könnten Befehle ausführen.
- Eine uneingeschränkte, Root-fähige `qpdf`-Regel kann über PDF-Anhänge eine privilegierte Datei offenlegen: qpdf ab Version 10.2 unterstützt `--empty` und `--add-attachment file ... --` mit einer Ausgabe-PDF. Kann der privilegierte Prozess die gewählte Quelle lesen und die PDF in einen für den Aufrufer zugänglichen Pfad schreiben, kann diese Ausgabe die Quelldaten enthalten. Prüfe die wirksamen sudo-Argumente und Ausschlüsse, die qpdf-Version, den Zugriff auf die Quelle und den Ausgabepfad, bevor du auf eine mögliche Offenlegung schließt. Das Lesen eines Root-SSH-Schlüssels ist nur dann für eine Anmeldung nützlich, wenn der Schlüssel gültig ist und SSH-Authentifizierung für Root erlaubt ist. Siehe die [Optionen für qpdf-Anhänge](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Die Wiederverwendung von sudo-Zeitstempeln hängt von Cache-Richtlinie, besitzendem Benutzer, Terminal/Sitzung und Berechtigungen ab. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) beschreibt die nötigen Prüfungen.
- `doas` hat eigene Regeln und Konfigurationen. Prüfe erlaubte Befehle und beschreibbare Konfigurationspfade wie im [Abschnitt zu doas](../linux-basics/linux-privilege-escalation/README.md#doas) beschrieben.

### Mit sudo ausgeführte Build- und Paketwerkzeuge

Eine uneingeschränkte sudo-Berechtigung für Foundrys `forge` kann relevant sein, selbst wenn die RunAs-Identität ein anderes Nicht-Root-Konto ist. Compiler-Optionen wie `--use` können eine lokale ausführbare Datei auswählen, und `forge flatten -o` legt eine Ausgabedatei fest. Prüfe die installierte Forge-Version, die genauen sudo-Argumente, zugängliche Projekt- und Compiler-Pfade, Ausgabeberechtigungen und die wirksame Umgebung, bevor du die Berechtigung als ausnutzbar einstufst. Ein relativer Helper, der über `PATH` gefunden wird, ist ein versions- und umgebungsabhängiger Pfad und keine Eigenschaft, die für jeden Forge-Build vorausgesetzt werden darf.<sup>[[23]](#references)[[24]](#references)</sup>

Eine uneingeschränkte, Root-fähige Berechtigung für `pacman` erlaubt mehr als Paketabfragen: `-U` akzeptiert ein lokales Paket, Pakete können Installations-Scripts enthalten und `--hookdir` wählt ein anderes Hook-Verzeichnis aus. Prüfe die wirksame sudo-Regel sowie Argumentbeschränkungen und Ausschlüsse, bevor du etwas testest; eine passive Erfassung erfordert weder die Installation eines Pakets noch die Ausführung eines Hooks.<sup>[[25]](#references)[[26]](#references)</sup>

Ein festgelegter sudo-Shell-Wrapper kann außerdem eine namentlich ausgewählte npm-Abhängigkeit installieren und danach eine Node-Anwendung starten. Prüfe die genaue RunAs-Regel, ob das Paket bereits installiert ist, das wirksame `HOME` und `npm userconfig`, Projektkonfiguration oder Befehlszeilen-Overrides sowie, ob ein weniger privilegierter Benutzer die Registry oder das für diesen Namen gelieferte Paket kontrolliert. [npm dokumentiert die Suche nach `.npmrc` pro Benutzer und Projekt](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); das Verhalten von `HOME` bei sudo hängt von der installierten Richtlinie und Distribution ab. Daher wird die beschreibbare `.npmrc` eines Benutzers möglicherweise vom privilegierten npm-Prozess gelesen, möglicherweise aber auch nicht. Wird das neu installierte Paket von der privilegierten Anwendung importiert, kann dessen Modulcode unter der Identität der Anwendung laufen. Installations-Scripts sind ein separater, versions- und konfigurationsabhängiger Pfad; [npm dokumentiert deren Lebenszyklus und Benutzerverhalten](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ein `.npmrc`-Pfad oder eine `npm install`-Zeile allein ist nur ein Prüfhinweis. Untersuche Regel, kurzen Wrapper, Konfigurationspfade und Herkunft des Pakets, ohne das Paket zu installieren oder die Anwendung bei einer passiven Erfassung zu starten.

Eine Root-fähige Berechtigung für `pip` oder `pip3 download` ist ebenfalls ein Hinweis für die Prüfung des Paket-Builds, wenn die Argumente dem Aufrufer die Auswahl einer nicht vertrauenswürdigen Quell-Distribution erlauben, selbst wenn das URL-Muster auf einen lokalen Dienst und ein `.tar.gz`-Suffix beschränkt ist. `pip download` akzeptiert Archiv-URLs und löst Paketmetadaten auf; bei der Vorbereitung eines sdist können dessen Build-Backend oder veralteter `setup.py`-Code ausgeführt werden, bevor das Archiv lediglich gespeichert wird. Prüfe die genauen sudo-RunAs- und Argumentregeln, ob der Aufrufer das ausgewählte Archiv veröffentlichen oder ersetzen kann und ob diese pip-Version seine Metadaten tatsächlich vorbereitet. Ein festes, vertrauenswürdiges Archiv oder Wheel belegt diesen Pfad nicht. Lade oder baue bei einer passiven Erfassung kein nicht vertrauenswürdiges Paket. Siehe pip [Download-Befehl](https://pip.pypa.io/en/stable/cli/pip_download/), [Build-System-Schnittstelle](https://pip.pypa.io/en/stable/reference/build-system/) und [Leitfaden für sichere Installationen](https://pip.pypa.io/en/stable/topics/secure-installs/).

Eine sudo-Regel, die `pip install` mit einem vom Aufrufer ausgewählten lokalen Projektpfad erlaubt, schafft eine direktere Build-Vertrauensgrenze. [pip akzeptiert lokale Projektverzeichnisse](https://pip.pypa.io/en/stable/topics/local-project-installs/) und ruft deren Build-System auf; das [Build-Backend führt vom Projekt kontrollierte Build-Hooks aus](https://pip.pypa.io/en/stable/reference/build-system/). Prüfe die wirksame RunAs-Identität, genaue Argumentbeschränkungen und Verbote, die Kontrolle über das ausgewählte Projekt sowie das Verhalten des installierten pip-Backends, bevor du die Regel als privilegierte Code-Ausführung einstufst. Ein festgelegtes, vertrauenswürdiges Projekt oder eine Regel, die vom Aufrufer ausgewählte Pfade ausschließt, begründet diesen Pfad nicht. Prüfe Regel und Projektmetadaten, ohne bei einer passiven Erfassung ein Paket zu installieren.

Eine uneingeschränkte, Root-fähige Berechtigung für `easy_install` ist ein verwandter Hinweis auf veraltete Paket-Builds. [Setuptools dokumentiert](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), dass Easy Install ein lokales Projektverzeichnis akzeptiert und Quell-Distributionen erstellt; ein vom Aufrufer kontrolliertes Projekt kann bei diesem Build dessen `setup.py` unter der sudo-Identität ausführen. Prüfe das wirksame RunAs-Konto, genaue Befehls- und Argumentbeschränkungen (einschließlich späterer Verbote), die Kontrolle über das ausgewählte Projekt und das Verhalten des installierten Tools. Ein festgelegtes, vertrauenswürdiges Projekt oder eine Richtlinie, die keine vom Aufrufer ausgewählte Quelle zulässt, begründet diesen Pfad nicht. Untersuche Regel und Projektmetadaten, ohne bei der Erfassung ein Paket zu installieren.

Ein über sudo erlaubter Python-Wrapper, der `setuptools.package_index.PackageIndex.download` mit einer vom Aufrufer ausgewählten URL verwendet, ist ein anderer Prüfungsfall als `pip download`: [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) beschreibt, dass in betroffenen Versionen vor 78.1.1 ein aus der URL abgeleiteter Dateiname aus dem vorgesehenen Download-Verzeichnis ausbrechen und mit den Berechtigungen des Prozesses schreiben kann. Prüfe die wirksame sudo-RunAs- und Argumentregel, ob der Wrapper die URL des Aufrufers an genau diese API übergibt, den installierten Build oder Hersteller-Backport und den aufgelösten Zielpfad. Eine Versionszeichenfolge oder ein beschreibbares Download-Verzeichnis allein belegt keinen beliebigen Schreibzugriff. Prüfe den kurzen Wrapper und Paketmetadaten, ohne die URL abzurufen oder bei der Erfassung eine Datei zu schreiben.

Ein über sudo erlaubter Build-Wrapper, der PyInstaller eine vom Aufrufer gewählte `.spec`-Datei übergibt, erfordert dieselbe Prüfung der Vertrauensgrenze. Eine PyInstaller-Spec-Datei ist beim **Build** ausführbarer Python-Code, und ihre `datas`-Einträge können Dateien, die für die Build-Identität lesbar sind, in ein Artefakt aufnehmen. Prüfe den genauen RunAs-Benutzer, sudo-Argument- und Verbotsregeln, die Pfad- und Zweigbehandlung des Wrappers, die Kontrolle über die gewählte Spec-Datei und den Zugriff auf das resultierende Artefakt. Ein erlaubter `.py`-Eingabepfad oder ein installiertes PyInstaller belegt weder die Kontrolle über eine Spec-Datei noch privilegierte Ausführung. Bei einer passiven Prüfung sollten nur ein begrenzter Wrapper und Metadaten gelesen werden; ein Build sollte nicht ausgeführt werden. Siehe die [PyInstaller-Dokumentation zu Spec-Dateien](https://pyinstaller.org/en/stable/spec-files.html).

### Mit sudo ausgeführte Preset- und Plugin-Lader

Python-Tools, die ein vom Aufrufer ausgewähltes Preset- oder Plugin-Verzeichnis akzeptieren, können Code mit den durch sudo gewährten Berechtigungen importieren. BBOT akzeptiert beispielsweise ein Preset mit `-p`, und die [Dokumentation zu benutzerdefinierten Modulen](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) beschreibt `module_dirs`-Einträge, mit denen zusätzliche Python-Modulverzeichnisse ausgewählt werden. Erlaubt die wirksame sudo-Regel ein vom Aufrufer ausgewähltes Preset und kontrolliert dieser ein Modul im ausgewählten Verzeichnis, kann der Import Code als privilegierter Benutzer ausführen, möglicherweise noch bevor das Tool ein ungültiges Modul zurückweist. Prüfe die installierte Version, die genaue sudo-RunAs- und Argumentrichtlinie sowie die Eigentumsverhältnisse von Preset- und Modulpfaden, ohne das Modul während der Erfassung zu laden.

### Mit sudo ausgeführtes Backdrop-Kommandozeilentool

[Bee](https://github.com/backdrop-contrib/bee) ist ein PHP-Kommandozeilentool für Backdrop CMS. Die Befehle `eval` (`php-eval`) und `php-script` können vom Aufrufer bereitgestellten PHP-Code ausführen. Eine sudo-Regel, die die Bee-Datei als Root mit uneingeschränkten Argumenten erlaubt, kann daher Root-Code-Ausführung ermöglichen, wenn Bee eine Backdrop-Installation initialisieren kann. Führe es aus dem Site-Verzeichnis aus oder wähle eine Site mit der globalen Option `--root=<directory>`; Bee oder eine Backdrop-`settings.php`-Datei zu finden, beweist weder eine entsprechende sudo-Berechtigung noch eine nutzbare Site oder eine erfolgreiche Initialisierung. Prüfe vor einem Test die wirksame sudo-Regel, etwaige Befehlsausschlüsse, die Identität der ausführbaren Datei und den Zugriff auf die Site. Bei einer passiven Erfassung solltest du die Regel und Dateipfade untersuchen, ohne Bee aufzurufen. Siehe das [Changelog der Bee-Befehle](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) zu den PHP-Befehlen.

### Mit sudo ausgeführte Terminalserver

`mosh-server` startet einen interaktiven Terminalserver als aufrufender Benutzer. Er wählt einen hohen UDP-Port und einen Sitzungsschlüssel, gibt beide an den Aufrufer aus und startet normalerweise beim Verbinden eines Clients die Login-Shell des Benutzers. Eine uneingeschränkte, Root-fähige sudo-Berechtigung für `mosh-server` ist daher ein möglicher Shell-Prüffall, auch wenn sich der Server-Befehl selbst abkoppelt. Prüfe die wirksame RunAs-Identität, erlaubte Argumente und Ausschlüsse, die installierte Binärdatei, die Shell, die Verfügbarkeit eines Clients und den UDP-Zugriff. Bei einer passiven Erfassung sollte die sudo-Regel untersucht werden, ohne einen Server zu starten oder einen aktuellen Sitzungsschlüssel auszugeben. Siehe das [Handbuch für den Mosh-Server](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) und die [Upstream-Designhinweise](https://github.com/mobile-shell/mosh#how-it-works).

### Privilegierte Backup-Wrapper, die die Aufgaben-Datei des Aufrufers umschreiben

Ein als Root laufender Shell-Wrapper kann eine vom Aufrufer ausgewählte Aufgaben-Datei akzeptieren, `../` aus Quellpfaden entfernen, prüfen, ob jedes Ergebnis mit einem erlaubten Verzeichnis beginnt, die Aufgaben-Datei umschreiben und anschließend deren *Pfadnamen* an ein Backup-Programm übergeben. Prüfe den umgewandelten Pfad nach vollständiger kanonischer Auflösung: Ein einzelner String-Ersetzungsschritt kann eine neue Traversal-Sequenz offenlegen, die eine lexikalische Präfixprüfung akzeptiert. Prüfe außerdem, ob das Backup-Programm die umgewandelten Daten im Speicher verwendet oder die Datei erneut öffnet. Öffnet es die Datei erneut, kann ein fehlgeschlagenes Umschreiben die ursprüngliche Eingabe unverändert lassen.

Unter Linux kann `fs.protected_regular` einen `O_CREAT`-Schreibvorgang in die reguläre Datei eines anderen Benutzers in einem weltweit beschreibbaren Sticky-Verzeichnis verhindern. Diese Verweigerung ist ein Schutz; ein Shell-Wrapper, der den Schreibfehler ignoriert, kann dennoch mit der ursprünglichen Aufgaben-Datei fortfahren. Prüfe die Einstellung, Eigentümer der Datei und des Verzeichnisses sowie, ob der Wrapper bei einem Fehler abbricht. Der Pfad ist nur dann ein möglicher Kandidat für die Offenlegung von Dateien, wenn die wirksame sudo-Regel den Wrapper als privilegierten Benutzer erlaubt, der Aufrufer die Aufgaben-Eingabe und ein lesbares Backup-Ziel kontrolliert und das Backup-Programm geschützte Quellen tatsächlich einschließt. Untersuche diese Bedingungen, ohne bei der Erfassung das Backup auszuführen.

### Argument-Wildcards bei privilegierten Paketwerkzeugen

In einer sudo-Regel für `tcpdump` kann ein `*` im **Argumentmuster** Leerzeichen und Schrägstriche erfassen. Eine scheinbare Pfadbeschränkung kann daher zusätzlichen Optionstext zulassen. Das unterscheidet sich von einer Wildcard im Pfad der ausführbaren Datei des Befehls; prüfe die vollständige RunAs-Regel und etwaige spätere Verbote. Können Optionen eingeschleust werden, bestimmen der erlaubte Aufruf und die Semantik der installierten [`tcpdump`-Optionen](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), ob `-F`, `-V`, `-r`, `-w` oder `-Z` eine nützliche Lese-/Schreibprimitive bietet. `-V` liest eine Liste von Capture-Dateinamen, keinen beliebigen allgemeinen Dateidump. AppArmor oder eine andere MAC-Richtlinie kann den Dateizugriff verhindern, selbst wenn sudo den Befehl erlaubt; eine Profil-Datei auf der Festplatte beweist nicht, dass sie geladen ist oder durchgesetzt wird. Prüfe Autorisierung und Richtlinien passiv, bevor du zu einem Ergebnis kommst. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) beschreibt den Unterschied zwischen Wildcards.

Eine Root-fähige sudo-Regel, die nur die ausführbare Datei `tcpdump` aufführt und keine Argumente beschränkt, sollte ebenfalls geprüft werden. Das [tcpdump-Handbuch](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) dokumentiert `-z` als Befehl nach einer Rotation, wenn `-C` oder `-G` eine gespeicherte Aufzeichnung rotiert; `-Z` oder ein zur Build-Zeit festgelegter Standardwert kann die Berechtigungen absenken, bevor dieser Befehl ausgeführt wird. Prüfe die wirksame sudo-Regel, den installierten Build, das Verhalten beim Absenken der Berechtigungen und ob eine Rotation stattfinden kann, bevor du die Regel als Rechteausweitungsweg einstufst. Eine hervorgehobene Regel ist ein möglicher Prüfhinweis, kein Beweis für die Ausführung eines Root-Befehls.

### Mit sudo ausgeführte Nmap-Wrapper

Wenn ein über sudo erlaubter `nmap`-Pfad ein Shell-Wrapper ist, prüfe den genau erlaubten Pfad und jede weitergereichte Option. Das Blockieren der geläufigen Schreibweise `--script` verhindert nicht zwangsläufig das Laden von NSE-Code: Nmaps [`--datadir`](https://nmap.org/book/man-misc-options.html) wählt Datendateien aus, und NSE [lädt `nse_main.lua`](https://nmap.org/book/nse-implementation.html) aus dem ausgewählten Datenverzeichnis, wenn Scripting aktiviert ist. Manche installierten Builds akzeptieren auch alternative Schreibweisen langer Optionen. Vergleiche daher die Einschränkungen mit dem tatsächlichen Parser dieser Binärdatei. [`--excludefile`](https://nmap.org/book/man-target-specification.html) eröffnet eine separate Angriffsfläche zum Lesen von Dateien; Parserfehler können Text offenlegen. Prüfe die wirksame sudo-Regel, die Wrapper-Logik, die Nmap-Version, die Kontrolle über Verzeichnisse und die MAC-Richtlinie, ohne während der Erfassung Scans auszuführen.

### Mit sudo ausgeführte Mercurial-Pull-Hooks

Ein fester Quellpfad in `sudo hg pull /fixed/source` lässt das **empfangende** Repository dennoch durch das aktuelle Arbeitsverzeichnis bestimmen, sofern der Befehl es nicht mit `-R` festlegt. Ein vom Aufrufer kontrolliertes empfangendes Repository kann Hooks in `.hg/hgrc` definieren, die als sudo-RunAs-Benutzer ausgeführt werden können. [Mercurial ignoriert Repository-Konfigurationen, die einem nicht vertrauenswürdigen Benutzer oder einer nicht vertrauenswürdigen Gruppe gehören](https://mercurial-scm.org/help/topics/config). Prüfe daher die vertrauenswürdigen Benutzer und Gruppen des RunAs-Kontos sowie das genaue Arbeitsverzeichnis, bevor du dies als Code-Ausführung einstufst. Für eine passive Prüfung genügt es, Richtlinie und Konfiguration zu lesen; führe zum Erfassen keinen Pull aus und rufe keinen Hook auf.

### Mit sudo ausgeführte Git-Pull-Hooks

Bei einer exakten, Root-fähigen Berechtigung für `sudo git pull` solltest du auch das **empfangende** Repository prüfen, das durch das Arbeitsverzeichnis ausgewählt wird. Ein vom Aufrufer kontrolliertes Repository kann einen ausführbaren `post-merge`-Hook enthalten, der mit der Identität des Git-Prozesses läuft, wenn ein Pull tatsächlich erfolgreich zusammenführt. [Git dokumentiert diesen Hook](https://git-scm.com/docs/githooks) sowie [das Verhalten von Pull mit Merge oder Rebase](https://git-scm.com/docs/git-pull). Prüfe die wirksame sudo-Regel und das aktuelle Arbeitsverzeichnis, den aktiven Hook-Pfad und dessen Berechtigungen sowie, ob ein Merge mit neuen Commits möglich ist. Ein fehlgeschlagener, wirkungsloser oder nur Rebase ausführender Pull belegt diesen Hook-Pfad nicht. Untersuche Richtlinie und Repository-Metadaten, ohne den privilegierten Pull auszuführen.

### Mit sudo ausgeführte rsync-Archivkopien

Bei `sudo rsync -a ... /writable/source/* /fixed/destination/` kann ein `*` im **sudoers-Argumentmuster** Leerzeichen erfassen und eine zusätzliche Option zwischen Quelle und Ziel zulassen. Das unterscheidet sich von der Shell-Erweiterung von Dateinamen. Kann der Aufrufer die Quelle befüllen und ist das Ziel für den privilegierten rsync-Prozess beschreibbar, kann [`--chown`](https://download.samba.org/pub/rsync/rsync.1) einen privilegierten Eigentümer anfordern, während der Archivmodus die Berechtigungsbits erhält. Dadurch kann möglicherweise eine eigene SetUID-Datei entstehen. Prüfe die genaue [sudoers-Wildcard-Semantik](https://man7.org/linux/man-pages/man5/sudoers.5.html), die rsync-Version, spätere Verbote, das `nosuid`-Dateisystem-Flag und die MAC-Richtlinie. Eine passende Regel ist ein Prüfhinweis, kein Beweis für erfolgreiche Rechteausweitung.

### Export privilegierter Paketfilterregeln

Eine uneingeschränkte, Root-fähige Berechtigung für `iptables` und `iptables-save` (oder das entsprechende Paar `ip6tables`) sollte auf Dateischreibzugriff geprüft werden. Der `comment`-Match akzeptiert vom Aufrufer gewählten Regeltext, während `iptables-save -f` den serialisierten Regelsatz in einen ausgewählten Pfad schreibt.<sup>[[20]](#references)[[21]](#references)</sup> Eine nützliche Nutzlast hängt davon ab, wie das installierte Backend Kommentare serialisiert und ob die Zieldatei weitere Zeilen im Export akzeptiert; `iptables-save` allein ermöglicht keine beliebigen vorgegebenen Inhalte. Prüfe die genaue sudo-RunAs-Identität, Argumente und Ausschlüsse, die verfügbare Match-Erweiterung, das Backend und die Berechtigungen des Ziels. Untersuche bei der Erfassung die Berechtigung, ohne Firewall-Regeln zu ändern oder eine Datei zu schreiben.

### Privilegiertes Below-Protokollverzeichnis

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) betraf Below-Versionen vor 0.9.0, die das weltweit beschreibbare Verzeichnis `/var/log/below` erstellten. Läuft ein Dienst oder ein über sudo erlaubter Befehl mit einem betroffenen Build als Root, kann ein Benutzer, der ein Nicht-Sticky-Protokollverzeichnis beschreiben und durchsuchen kann, möglicherweise einen Protokolleintrag durch einen Symlink ersetzen, bevor der privilegierte Prozess ihn öffnet. Prüfe den Patch-Status des installierten Pakets, den genauen privilegierten Ausführungspfad, den wirksamen Verzeichniszugriff, das Sticky-Bit und ACLs sowie die Metadaten von `/var/log/below/error_root.log`. Ein weltweit beschreibbarer Pfad oder eine sudo-Regel allein belegt nicht die vollständige Kette. Ein Sticky-Verzeichnis oder ein Hersteller-Backport ändert die Bewertung. Bei einer passiven Erfassung sollten nur Metadaten untersucht werden; ein Link muss nicht erstellt und das privilegierte Programm nicht ausgeführt werden.

### Privilegierte Erfassung von Support-Paketen aus beschreibbaren Eingaben

Ein über `sudo` erlaubtes Support-Profil-Script kann feste Protokollpfade als Root lesen und deren Inhalt in ein Profilarchiv kopieren. Untersuche das tatsächliche Script auf Dateizugriffe und prüfe anschließend, ob der Aufrufer einen Quellpfad oder einen übergeordneten Verzeichniseintrag durch einen Symlink ersetzen kann. Folgt der privilegierte Lesevorgang diesem Link und kann der Aufrufer das resultierende Archiv lesen, kann eine geschützte Datei offengelegt werden. Erforderlich sind die sudo-Berechtigung, ein beschreibbarer Quellpfad, der privilegierte Lesezugriff und eine lesbare Ausgabe; ein beschreibbares Protokoll oder ein Profil-Dateiname allein reicht nicht aus. Untersuche die wirksamen Berechtigungen und Link-Metadaten, ohne während der Erfassung Dateien zu ersetzen oder ein Profil zu erstellen. Die [Support-Hinweise zu Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) dokumentieren ein als Root laufendes Profil-Script und das Ausgabearchiv und zeigen, warum solche Pakete Eingaben und Ausgabezugriff beschränken müssen.

### Als Root ausgeführte Python-Archive-Wiederherstellungs-Scripts

Auch eine eng beschränkte sudo-Regel für ein Python-Wiederherstellungs-Script erfordert eine Prüfung der Archiveingabe. Kann der Aufrufer das Archiv auswählen oder ersetzen und extrahiert das Script es als Root mit `tarfile.extractall(filter="data")`, prüfe die Sicherheitsupdates des Interpreters, bevor du dem Filter vertraust. CPython behob mehrere Umgehungen des Symlink- und Hardlink-Filters, darunter CVE-2025-4517, in den Versionen 3.9.23, 3.10.18, 3.11.13, 3.12.11 und 3.13.4. Distributions-Backports können auch eine frühere Version korrigieren. Daher beweist die angezeigte Interpreter-Version allein keine Anfälligkeit.<sup>[[16]](#references)[[17]](#references)</sup>

Lies bei einer passiven Prüfung den genauen sudo-Befehl und das Script, verfolge, welches Argument das Archiv auswählt, und prüfe, ob der aktuelle Benutzer das Archiv oder dessen übergeordnetes Verzeichnis beschreiben kann. Prüfe den installierten Hersteller-Patch und das Extraktionsziel separat; `filter="data"` macht nicht jedes nicht vertrauenswürdige Archiv sicher.<sup>[[16]](#references)[[17]](#references)</sup>

### Mit sudo ausgeführte Loader für Machine-Learning-Modelle

Eine sudo-Regel, die eine vom Aufrufer ausgewählte `.pt`-, `.pth`- oder `.ckpt`-Datei erlaubt, sollte geprüft werden, wenn ein privilegiertes Script diese Datei an [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` oder einen anderen pickle-basierten Loader übergibt. Prüfe die wirksame RunAs-Regel, ob der Aufrufer das ausgewählte Modell erstellen oder ersetzen kann und den tatsächlichen Argumentfluss über einen Shell-Wrapper zum Python-Helper. Die Erweiterung `.pth` bezeichnet auch nicht verwandte Python-Site-Konfigurationsdateien und ist allein kein Beweis für das Laden eines Modells. Ein Archiv-Scan oder statischer Pickle-Scan belegt nicht, dass das spätere Laden sicher ist; prüfe das [versionsabhängige Verhalten von `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) und etwaige Allowlists. Siehe die Hinweise zu [ML-Pickle und Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Lade oder entpacke das Modell bei einer passiven Erfassung niemals.

### Mit sudo ausgeführte Ausdrucksauswertung gespeicherter Eingaben

Ein festes Python-Script, das über sudo als Root ausgeführt wird, kann dennoch Text auswerten, den ein weniger privilegierter Benutzer in einer Anwendungsdatenbank speichern kann. In TensorFlow wählt ein Aufruf von `preprocess_input_exprs_arg_string(value, safe=False)` einen `eval`-Pfad aus; der [Hinweis von TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) beschreibt den unsicheren Parser und eine Korrektur für dessen Kommandozeilen-Aufrufer. Ein expliziter Aufruf mit `safe=False` in einer Anwendung muss separat geprüft werden, selbst wenn dieser Kommandozeilen-Aufrufer gepatcht ist. Prüfe die wirksame sudo-Regel, wer den genauen Eingabedatensatz ändern kann, ob Filterung oder Bewertung diesen Datensatz bis zum Aufruf gelangen lässt und wie sich die installierte Funktion verhält. Eine TensorFlow-Version, eine sudo-Berechtigung oder eine fest codierte Modelldatei allein beweist die Kette nicht. Untersuche Script und Datenfluss passiv; führe den privilegierten Helper nicht aus und übermittle bei der Erfassung keine Testausdrücke.

### Mit sudo erlaubte needrestart-Konfiguration

`needrestart -c` lädt eine vom Aufrufer ausgewählte Perl-Konfigurationsdatei und wertet deren Inhalt aus. Erlaubt `sudo -l` `needrestart` als Root mit Argumenten, die `-c` zulassen, und kann der Aufrufer eine lesbare Konfigurationsdatei an einem beschreibbaren Ort auswählen, kann diese Berechtigung zu Root-Code-Ausführung führen. Prüfe die genaue sudo-RunAs- und Argumentregel; eine Regel mit einer festen Argumentliste kann diesen Pfad verhindern. Dies ist von Schwachstellen beim Interpreter-Scanning durch needrestart getrennt: Ein Paket-Update oder das Deaktivieren von `interpscan` macht eine uneingeschränkte Root-Berechtigung für `-c` nicht sicher.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Mit sudo ausgeführte Python-Imports unter einem anderen Konto

Ein fester Python-Einstiegspunkt kann dennoch ein Modul importieren, das der Aufrufer bearbeiten oder ersetzen kann, auch wenn sudo das Script als **Nicht-Root-Dienstbenutzer** ausführt. Prüfe bei einem Literal-Import wie `from utils import status` sowohl `utils/__init__.py` und `utils/status.py` als auch die Berechtigungen des Paketverzeichnisses. Prüfe den Importpfad des Scripts, die genau erlaubten sudo-Argumente und ob die betreffende Aktion diesen Import erreicht, bevor du die beschreibbare Datei als Ausführungspfad einstufst. Untersuche Dateien und Berechtigungen, ohne das Script während der Erfassung zu importieren oder auszuführen.<sup>[[2]](#references)[[3]](#references)</sup>

Eine exakte sudo-Regel für `python3 /absolute/script.py` erfordert lediglich ein lesbares Script; die Datei muss weder ausführbar sein noch einen Shebang besitzen. Prüfe auch **fehlende** lokale Module: Importiert das Script ein Modul, dessen Dateiname in einem vom Aufrufer beschreibbaren Script-Verzeichnis angelegt werden kann, lädt Python diese Datei möglicherweise unter der RunAs-Identität. Prüfe die wirksame sudo-Regel, den tatsächlichen [Modulsuchpfad](https://docs.python.org/3/library/sys_path_init.html) des Interpreters, ob das Modul eingebaut oder eingefroren ist und ob der Import erreicht wird. Eine direkte sudo-Regel für das Script hat andere Anforderungen an Ausführungsrechte und Shebang. Ein separater Wrapper, der vom Aufrufer bereitgestellte Tokens nach `sudo -u account` anhängt, erfordert ebenfalls eine Prüfung des Argumentflusses: Ein weiteres `-u` in diesen Tokens ist nur relevant, wenn die aufgerufene sudo-Richtlinie die resultierende Identität zulässt. Statische Zeichenfolgen allein belegen keinen der beiden Pfade.

### Mit sudo ausgeführter Apache mit vom Aufrufer kontrollierter Konfiguration

Erlaubt eine sudo-Regel den Aufruf von `apachectl`, `apache2ctl` oder `httpd` mit privilegierten Rechten und einer vom Aufrufer kontrollierten Konfigurationsdatei über `-f`, prüfe die Berechtigungen dieser Datei und ihres übergeordneten Verzeichnisses. Apaches [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)-Direktive erwartet einen Modulnamen und danach den **Dateinamen des Moduls**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) lädt ebenfalls eine Datei. [`Include` und `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) können die Konfiguration erweitern oder Dateiinhalte über Fehler offenlegen. Ein benutzerdefinierter Wrapper kann diese Pfade validieren, Berechtigungen absenken oder Argumente beschränken. Eine beschreibbare Konfiguration ist daher ein Prüfhinweis und kein Beweis für Code-Ausführung. Prüfe die Pfadkanonisierung, Symlinks und Direktivenverarbeitung, bevor du zu einem Ergebnis kommst.

### Mit sudo ausgeführtes nginx mit vom Aufrufer kontrollierter Konfiguration

Eine uneingeschränkte, Root-fähige `nginx`-Regel kann [`-c` erlauben, eine andere Konfiguration auszuwählen](https://nginx.org/en/docs/switches.html). Prüfe die genauen sudo-Argumente und Ausschlüsse, ob der Aufrufer die Konfiguration bereitstellen kann und ob der resultierende Master-Prozess oder die Worker-Prozesse weiterhin auf geschützte Pfade zugreifen können. Ein gewähltes `root` zusammen mit `autoindex` kann Dateien über einen neuen Listener offenlegen; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kann einen privilegierten Dateischreibpfad ermöglichen. Das DAV-Modul wird jedoch nicht standardmäßig mitgebaut. Prüfe daher sein Vorhandensein, Erreichbarkeit des Listeners, Dateiberechtigungen und Verhalten temporärer Dateien. Auch die [`error_log`-Direktive](https://nginx.org/en/docs/ngx_core_module.html#error_log) kann auf eine ausgewählte Datei zeigen. Das Schreiben von Protokollen in eine sensible Konfigurationsdatei wie `/etc/ld.so.preload` erfordert einen wirksamen privilegierten Schreibzugriff und einen kontrollierbaren Protokolleintrag, bevor daraus ein Rechteausweitungsweg wird. Die Hervorhebung einer ausführbaren Datei in `sudo -l` ist ein Prüfhinweis, kein Beweis dafür, dass einer dieser Pfade funktioniert. Starte nginx bei einer passiven Erfassung nicht und ändere dessen Konfiguration nicht.

### Mustervergleich in privilegierten Bash-Eingabeaufforderungen

Liest ein über sudo erlaubtes Bash-Script einen Wert vom Aufrufer und prüft ihn mit `[[ "$expected" == $entered ]]`, interpretiert Bash den nicht zitierten rechten Operanden als Muster. Ein Wildcard kann daher den Vergleich bestehen, ohne dass der erwartete Wert bekannt ist. Wenn der Operand zitiert wird (`[[ "$expected" == "$entered" ]]`), erfolgt ein wörtlicher Zeichenfolgenvergleich. Prüfe die genaue sudo-Regel, ob die Eingabeaufforderung erreichbar ist und was das Script nach dem Vergleich tut; die Syntax allein begründet keinen ausnutzbaren Pfad. Gib den erwarteten Wert bei der Erfassung nicht aus. Siehe die Referenz zu [Bash-Bedingungskonstrukten](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Mit sudo ausgeführte Helper, die eine Datei herunterladen und ausführen

Eine uneingeschränkte, Root-fähige sudo-Berechtigung für einen benutzerdefinierten Helper erfordert eine Prüfung des Datenflusses, wenn dieser eine vom Aufrufer ausgewählte URL akzeptiert, die Antwort auf die Festplatte schreibt und die Datei später mit einem Interpreter oder einer Shell ausführt. [sudoers erlaubt beliebige Argumente, wenn ein Befehlseintrag keine auflistet](https://man7.org/linux/man-pages/man5/sudoers.5.html); ein fester Pfad zur ausführbaren Datei beschränkt nicht, was die Argumente auswählen können. Prüfe die tatsächliche URL-Validierung, den Ausgabepfad, den Erfolgszweig und die anschließende Ausführung im installierten Helper. Ein passender libcurl-Import oder eine druckbare Zeichenfolge allein belegt diese Kette nicht.

Selbst ein fester Ausgabedateiname kann zwischen Schreiben und Ausführen ersetzt werden, wenn der Helper in einem vom Aufrufer kontrollierten Arbeitsverzeichnis einen **relativen Pfad** verwendet. Das Umbenennen oder Ersetzen einer Root-eigenen Datei hängt von Schreib- und Suchberechtigungen des Verzeichnisses und etwaigen Sticky-Bit-Beschränkungen ab, nicht nur von den Dateiberechtigungen; siehe [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Prüfe, ob der Helper den Pfad später erneut öffnet oder den bereits geöffneten Dateideskriptor verwendet und ob er vor dem Schreiben in ein vertrauenswürdiges Verzeichnis wechselt. Untersuche sudo-Richtlinie, Helper und Verzeichnismetadaten passiv; rufe während der Erfassung weder den privilegierten Download auf noch führe einen Race aus.

Ein Root-sudo-Download-Helper kann auch eine **Argument**-Injection ermöglichen, wenn er einen Bash-Befehlsstring wie `curl <caller input> -o <fixed output>` zusammensetzt. Ein Filter, der Leerzeichen zurückweist, lässt dennoch [Bash-Klammererweiterung](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) zu: Nicht zitierte, durch Kommas getrennte Elemente können zu separaten curl-Argumenten werden. Erreicht die Eingabe curl vor dem festen `-o`, kann eine vom Aufrufer übergebene Ausgabeoption unter der Identität des Helpers das Ziel für die erste URL auswählen; [curl ordnet Ausgabeoptionen den URLs der Reihe nach zu](https://curl.se/docs/manpage.html#-o). Prüfe die genaue Shell, das Quoting, die Eingabevalidierung, die wirksame sudo-Regel, die curl-Argumentreihenfolge und unterstützte URL-Schemata sowie, ob der Aufrufer die abgerufenen Bytes kontrolliert oder das Ergebnis lesen kann. Eine mit PyInstaller gepackte ausführbare Datei kann Python-Anwendungslogik enthalten, aber ihr Verpackungshinweis oder eine `curl`-Zeichenfolge allein beweist diesen Datenfluss nicht. Prüfe, sofern autorisiert, eine begrenzte Offline-Kopie; bei einer routinemäßigen Erfassung sollte der Helper weder ausgeführt noch ein vom Angreifer ausgewählter Inhalt abgerufen werden.

Ein Root-sudo-Shell-Script, das [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aufruft, wählt lediglich einen unbenutzten Namen aus; es **erstellt** die Datei nicht. Erstellt das Script diesen Namen später in einem Verzeichnis, das ein anderer Benutzer beeinflussen kann, öffnet es erneut und hängt dessen Inhalt an ein geschütztes Ziel wie die `authorized_keys` von Root an, sollte ein möglicher Race um eine temporäre Datei geprüft werden. Prüfe die genaue sudo-Regel, Eigentümer von Verzeichnis und Datei, Erstellungs- und erneuten Öffnungsvorgang, Kernel-Schutzmaßnahmen und ob der privilegierte Schreibzugriff tatsächlich vom Angreifer kontrollierte Bytes verwendet. Eine `mktemp -u`-Zeichenfolge oder ein beschreibbares `/tmp` allein beweist keinen Race. Untersuche Script und Pfadmetadaten, ohne es auszuführen oder bei der Erfassung einen Race um die temporäre Datei auszuführen.

## Defensive Hinweise

- Vermeide es, Interpreter oder interaktive Editoren über sudo freizugeben.<sup>[[1]](#references)</sup>
- Bevorzuge feste, Root-eigene Wrapper, die genau eine eng begrenzte administrative Aktion ausführen.<sup>[[1]](#references)[[2]](#references)</sup>
- Ist ein Interpreter unvermeidbar, beschränke den genauen Script-Pfad und verhindere vom Benutzer kontrollierte Argumente, beschreibbare Imports, `PYTHONPATH` und die unsichere Beibehaltung der Umgebung.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Ist die Bearbeitung von Dateien erforderlich, beschränke den genauen Dateipfad und erwäge `sudoedit` mit gepatchten sudo-Versionen und strikter Umgebungsbehandlung.<sup>[[1]](#references)[[2]](#references)</sup>
- Prüfe `SETENV`, `env_keep`, beschreibbare Arbeitsverzeichnisse, beschreibbare Modul-/Importpfade, `NOEXEC`, `use_pty` und Protokollierung, behandle sie aber nicht als vollständige Sandbox.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
