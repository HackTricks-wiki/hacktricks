## Interpreters zinazoruhusiwa na Sudo

Ikiwa `sudo -l` inamruhusu mtumiaji kuendesha interpreter kama root, ichukulie kuwa ni utekelezaji wa msimbo wa moja kwa moja. Interpreters zimeundwa kutekeleza msimbo wowote, kwa hivyo kanuni inayoruhusu binary za `python3`, `perl`, `ruby`, `lua`, `node` au zinazofanana kwa kawaida ni sawa na utekelezaji wa amri kama root, isipokuwa kama hoja zimewekewa vizuizi vikali na kuthibitishwa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Mtiririko wa kawaida wa ukaguzi: kwanza orodhesha ruhusa za mtumiaji, kisha tekeleza kauli ya Python ukitumia chaguo la `-c` la interpreter.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Mifano mingine ya interpreters imeonyeshwa hapa chini; interpreters zilizoorodheshwa zinaeleza utekelezaji wa inline-code au APIs za child-process.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Njia kamili ni muhimu. Ikiwa sheria ya sudo inaruhusu `/usr/bin/python3`, tumia njia hiyo hiyo wakati wa uthibitishaji.<sup>[[2]](#references)</sup>

Glob ya executable ya sudo kama `/usr/bin/python*` inaweza pia kuruhusu Python 2 kwa script iliyoandikwa kwa Python 3. Ikiwa script itafikia `input()` yenye maandishi yanayodhibitiwa na caller, [Python 2 hutathmini maandishi hayo kama expression](https://docs.python.org/2/library/functions.html#input); kuita interpreter moja kwa moja hubatilisha shebang ya script. Thibitisha binaries zinazolingana na zilizowekwa, RunAs inayotumika na sera ya argument, vizuizi, na kama input inaweza kufikiwa kabla ya kuchukulia hili kama njia ya kutekeleza code.

Njia maalum ya script katika sheria ya sudo yenye uwezo wa root haizuii kile ambacho script itatekeleza. Kwa wrapper ya Bash inayosomeka, angalia ikiwa amri yake ya kwanza inayotekelezeka inatumia parameter ya nafasi kama `$1` bila quotes kama **command word**, huku sudo ikiruhusu caller kuchagua arguments. Thibitisha utambulisho wa RunAs unaotumika, sera ya password na argument, vizuizi vya baadaye, na tawi halisi la script; `NOEXEC`, orodha maalum ya arguments salama, au wrapper inayothibitisha amri yake inaweza kubadilisha matokeo. Kagua script fupi kwa njia tuli wakati wa enumeration badala ya kuiendesha kwa amri ya majaribio.

Sheria isiyo na vizuizi ya sudo yenye uwezo wa root kwa `dotnet` pia inastahili kukaguliwa kama interpreter. Ikiwa .NET SDK imesakinishwa, [`dotnet fsi` huendesha code ya F# kwa njia ya interactive au kutoka kwenye script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), na [`dotnet run` hutekeleza project kutoka kwenye source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Thibitisha kwanza utambulisho wa RunAs unaotumika na sera kamili ya arguments: sheria iliyowekewa subcommand maalum salama au application inayoaminika ni ruhusa tofauti, na usakinishaji wa runtime pekee unaweza kukosa amri za SDK. Jina la executable pekee ni kidokezo cha kukagua, si uthibitisho wa uwezo wa kutekeleza code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Vihariri vinavyoruhusiwa na Sudo

Ikiwa `sudo -l` inamruhusu mtumiaji kuendesha editor shirikishi kama root, ichukulie kama njia ya kutekeleza amri, si ruhusa isiyo na madhara ya kuhariri faili. Mara nyingi editor zinaweza kutekeleza amri za shell, kusoma faili zozote, kuandika faili zozote, au kutumia zana saidizi za nje kutoka ndani ya editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Utaratibu wa kawaida wa ukaguzi: orodhesha ruhusa za mtumiaji, kisha endesha kila editor au pager iliyoruhusiwa kwa kutumia sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Utekelezaji wa amri kupitia Nano

Ikiwa `nano` inaruhusiwa kupitia sudo, huenda ukaweza kutekeleza amri kupitia kiolesura cha kihariri.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Kisha toa amri kama `id` au `/bin/sh` kwenye kidokezo cha amri cha nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Ikiwa shell shirikishi haina mitiririko ya terminal inayoweza kutumika, aina hii ya uelekezaji hupeleka matokeo yake ya kawaida na hitilafu zake kwenye descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Mfuatano halisi wa vitufe unaweza kutofautiana kulingana na toleo la nano na chaguo za build, lakini suala la usalama ni lilelile: editor inaendeshwa kama root na inaweza kuendesha amri za nje.<sup>[[1]](#references)[[12]](#references)</sup>

### Njia nyingine za kawaida za kutoka kwenye editor

Editor za mtindo wa Vim kwa kawaida huruhusu kutekeleza amri kupitia `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers kama `less` pia zinaweza kufichua uendeshaji wa shell.<sup>[[14]](#references)</sup>

Kanuni ya sudo inayoruhusu `apport-cli` kuendeshwa kama root inapaswa kuchunguzwa kwa pager vivyo hivyo. Matoleo ya Apport yaliyoathiriwa yanaweza kufungua ripoti ya crash kwenye `less` huku ukubwa wa terminal ukiweza kurekebishwa na mshambuliaji; pager inaweza kisha kutoa root shell ikiwa masharti maalum ya sudo na pager yametimizwa. Kagua kanuni halisi ya sudo, usanidi wa pager na marekebisho ya kifurushi cha usambazaji kabla ya kuhitimisha kuwa toleo pekee ndilo linaloweza kudhurika. Soma metadata ya kifurushi na sera bila kusababisha crash au kufungua ripoti yenye upendeleo wakati wa uchunguzi wa awali. [Rekodi ya CVE ya Ubuntu](https://ubuntu.com/security/CVE-2023-1326) inaorodhesha matoleo ya vifurushi yaliyorekebishwa kwa kila toleo, yakiwemo marekebisho yaliyorejeshwa kwenye matoleo ya awali.

```text
!/bin/sh
```

## Hatari za sheria nyingine za sudo na doas

Anza na `sudo -l`, `sudo -V`, na sera yoyote husika ya `doas`. Soma pamoja amri zinazoruhusiwa, mtumiaji wa RunAs, argument, mazingira, na defaults. Ruhusa ya kuendesha amri kama akaunti ya huduma isiyo root bado inaweza kufichua faili za akaunti hiyo au njia ya kufikia root.

Script ya Python iliyoruhusiwa na sudo kwa njia isiyobadilika bado inaweza kuendesha amri ya shell chini ya utambulisho wake wa RunAs ikiwa input ya mwingiliano inayodhibitiwa na mpigaji imeunganishwa kwenye [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Orodha ya alama za shell zilizokatazwa haitoshi kuthibitisha usalama: [shell pia hutambua ubadilishaji wa amri wa `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Thibitisha kuwa argument zinazoruhusiwa zinafika kwenye tawi la input, input inaingia kwenye amri ya shell bila uthibitishaji salama, na sera inayotumika ya sudo inaruhusu mtumiaji wa RunAs aliyelengwa. Njia ya script au kuitwa kwa `os.system()` pekee ni kidokezo cha ukaguzi; kagua source bila kuendesha script yenye mamlaka.

Ruhusa inayotumika ya root kupitia sudo kwa `chattr` inaweza kuondoa sifa ya faili isiyobadilika (`i`), lakini hilo pekee halitoi ruhusa ya kuandika au utambulisho mpya. [Mwongozo wa `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) unasema sifa hiyo huzuia marekebisho na ni root pekee au mchakato wenye `CAP_LINUX_IMMUTABLE` unaoweza kuibadilisha. Kagua sera halisi ya argument za sudo na usaidizi wa mfumo wa faili, kisha uthibitishe kando kwamba mpigaji anaweza kuandika faili baada ya sifa kuondolewa na kwamba programu yenye utambulisho wa juu zaidi inaitumia. Kwa mfano, kubadilisha login shell pia kunahitaji akaunti lengwa ikubali vitambulisho husika na kuwe na login halisi kupitia shell hiyo. Kagua sera, sifa za faili na ruhusa bila kuzibadilisha wakati wa uorodheshaji.

Ikiwa sudo inaomba nenosiri na msimbo wa matumizi ya mara moja, zichukulie kama masharti tofauti na ruhusa ya amri. Faili ya `.google_authenticator` inayosomeka ina seed nyeti, ilhali hash ya zamani ya nenosiri la programu au hifadhidata ni mgombea tu wa nenosiri la sasa la akaunti; hakuna kati ya hivyo kinachothibitisha kuwa kipengele kingine kinakubaliwa na usanidi wa PAM unaotumika. Baada ya kupata idhini, kagua RunAs na argument halisi: ruhusa isiyo na vizuizi ya root kwa RubyGems `gem` inaweza kufichua amri yake ya editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), lakini ruhusa yenye vizuizi au uthibitishaji ulioshindwa haiwezi. Uorodheshaji wa kimya unapaswa kuripoti njia na sera bila kuchapisha seed, kurejesha nenosiri, kutengeneza msimbo, au kuita amri yenye mamlaka.

Ruhusa isiyo na vizuizi ya sudo yenye uwezo wa root kwa `knife` ya Chef inahitaji ukaguzi wa kiwango cha interpreter: [Chef inaeleza kuwa `knife exec -E` hutathmini string ya Ruby ndani ya mashine](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Thibitisha kuwa sheria halisi ya sudo inaruhusu subcommand ya `exec` na argument ya `-E` inayotolewa na mpigaji, utambulisho wa RunAs uliokusudiwa, na makatazo ya amri au argument zisizobadilika zinazolingana. Binary iliyosakinishwa au sheria yenye vizuizi kwa subcommand nyingine ni kidokezo tu. Uorodheshaji wa kimya unapaswa kuripoti sheria bila kuita `knife`.

Ruhusa halisi ya sudo kwa `msfconsole` shirikishi yenye uwezo wa root pia ni nyeti: [GTFOBins inaeleza console yake ya `irb`](https://gtfobins.org/gtfobins/msfconsole/), ambayo inaweza kurithi utambulisho wa sudo. Thibitisha mtumiaji halisi wa RunAs, orodha ya argument zinazoruhusiwa, makatazo ya amri, vizuizi vya `NOEXEC` au vingine, tabia ya console iliyosakinishwa, na kama mpigaji anaweza kutoa input shirikishi. Kuangaziwa kwa njia pekee ni kidokezo cha ukaguzi; uorodheshaji wa kimya haupaswi kuanzisha console.

Kwenye FreeBSD, hata sheria ya sudo yenye vizuizi kwa root `pkg update` na `pkg install *` inahitaji ukaguzi wa uaminifu wa hazina. Kagua kama mpigaji anaweza kuandika `/etc/hosts` na kama usanidi *unaotumika* wa hazina zilizowezeshwa unatumia jina la HTTP lenye `signature_type: none`. [Mwongozo wa `pkg.conf` wa FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) unasema `none` huzima ukaguzi wa saini; `pkg+http` pekee hauthibitishi hilo. [Kifurushi kinaweza kuwa na script za usakinishaji](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), kwa hiyo mpigaji anayedhibiti mwisho wa hazina na anayeweza kuchagua kifurushi anaweza kuvuka mpaka wa root. Thibitisha ubatilishaji wa hazina, utatuzi wa SRV/mirror, argument halisi za sudo, uteuzi wa kifurushi na utekelezaji wa script kabla ya kufikia hitimisho hilo. Kagua sera na faili ndogo za usanidi za ndani bila kuelekeza majina au kuendesha `pkg` wakati wa uorodheshaji.

Sheria ya sudo yenye uwezo wa root kwa `apt-get update` na `apt-get upgrade` pia inahitaji ukaguzi wa uaminifu wa hazina ikiwa sudo inahifadhi `http_proxy` inayodhibitiwa na mpigaji. Kagua kama usanidi halisi wa APT wa proxy unatumia kigezo hicho na ni maombi gani ya hazina zilizowezeshwa yanaweza kuathiriwa; proxy peke yake haiwezi kubadilisha vifurushi kutoka kwenye archive iliyothibitishwa kwa ufunguo wa saini unaoaminika. [Mwongozo wa usafirishaji wa HTTP wa APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) unaeleza kipaumbele cha proxy, na [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) unaeleza ukaguzi wa saini, ubatilishaji wa hazina zisizo salama na uthibitisho wa vifurushi visivyothibitishwa. Thibitisha RunAs na argument halisi za sudo, sera ya uthibitishaji wa hazina, idhini shirikishi inayohitajika, na kama uboreshaji uliochaguliwa unaendesha script za kifurushi kama root. Kagua sera na usanidi wa ndani bila kufanya trafiki ya vifurushi ipitie njia nyingine au kuendesha uboreshaji wakati wa uorodheshaji.

Sheria ya sudo yenye uwezo wa root kwa `snap install` inaweza kuvuka mpaka kati ya kifurushi na code ikiwa argument zake zinamruhusu mpigaji kuchagua snap ya ndani na hali ya usakinishaji yenye vizuizi hafifu. [Snap inaeleza](https://snapcraft.io/docs/explanation/snap-development/install-modes/) kuwa `--dangerous` huruka ukaguzi wa madai ya snap ya ndani na `--devmode` hupunguza vizuizi; [hook ya usakinishaji inaweza kuendeshwa wakati wa usakinishaji wa kwanza](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Kagua sera halisi ya argument/RunAs ya sudo, nani anayedhibiti faili ya snap, kama hali hizo zinakubaliwa na snapd iliyosakinishwa, na utambulisho pamoja na vizuizi vinavyotumika kwa hook kabla ya kudai ufikiaji wa faili za host zilizolindwa. Binary ya `snap` au sheria inayoonekana kuwa na wildcard pekee haithibitishi mnyororo huu. Uorodheshaji wa kimya haupaswi kusakinisha kifurushi au kuendesha hook yake.

Kwa ruhusa halisi ya sudo kwa binary maalum inayosoma vitambulisho ya akaunti **isiyo root**, kwanza kagua binary iliyopewa ruhusa na ruhusa zake za faili bila kuiendesha. Kizuizi cha nenosiri kilichopachikwa kinaweza kuonekana tu kama herufi pana; [GNU `strings` inaeleza utoaji wa 16-bit little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). String inayoonekana haithibitishi kuwa ndiyo nenosiri linalokubalika au kwamba tawi la mafanikio linafichua kitambulisho cha sasa. Thibitisha tabia ya binary, ufikiaji wa akaunti lengwa kwa data iliyolindwa, uhalali wa kitambulisho, na mabadiliko yoyote ya baadaye ya akaunti au kikundi, kila moja kivyake. Ikiwa akaunti hiyo ni mwanachama wa `docker`, thibitisha ufikiaji wa socket na utambulisho wa daemon wa rootful au rootless kabla ya kudokeza ufikiaji wa root wa host; [Docker inaeleza athari za kiwango cha root za kikundi chake](https://docs.docker.com/engine/install/linux-postinstall/). Uorodheshaji wa kawaida unapaswa kuripoti sheria ya sudo na uanachama wa kikundi bila kuendesha binary au kutoa strings zake.

Sheria ya sudo yenye wildcard kwa script za matengenezo za programu inahitaji ukaguzi zaidi ya njia ya script. Kagua kama script inayoruhusiwa inapokea argument zisizo na vizuizi au inasoma mipangilio inayoweza kuandikwa kupitia akaunti ya programu yenye mamlaka ya chini, kisha fuatilia thamani hizo hadi amri za shell au mazingira ya subprocess. Kwa mfano, [`zmupdate.pl` ya ZoneMinder huunda amri ya `mysqldump` na kuiendesha kupitia `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), huku [`zmdc.pl` inakili mpangilio wa `ZM_LD_PRELOAD` hadi `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) kabla ya kuanzisha daemon. Sheria ya sudo inayoruhusu mojawapo ya script hizo kama root inaweza kuvuka mpaka wa uaminifu ikiwa input husika inadhibitika na kufika kwenye code hiyo katika toleo lililosakinishwa. Kagua sheria halisi ya sudo, ruhusa za usanidi wa programu na source ya script; wildcard au mpangilio pekee ni kidokezo cha ukaguzi, si uthibitisho wa utekelezaji.

- `SETENV`, `env_keep`, `secure_path`, na `LD_PRELOAD` zinaweza kubadili amri yenye vizuizi kuwa utekaji wa import, library au PATH. Tazama [mwongozo wa environment variables](../linux-basics/linux-environment-variables.md) na [matumizi mabaya ya SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Ruhusa halisi ya `SETENV` yenye uwezo wa root kwa wrapper ya shell pia inahitaji ukaguzi wa hatua moja ikiwa wrapper inaanzisha script maalum ya Python yenye import halisi. `secure_path` hudhibiti utafutaji wa amri za shell, si [`PYTHONPATH` ya utafutaji wa moduli wa Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` na `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hufanya Python ipuuze kigezo hicho cha mazingira. Thibitisha tag na makatazo halisi ya sudo, tawi la wrapper, chaguo za interpreter, utatuzi wa import, na directory ya utafutaji inayoweza kuandikwa na mpigaji kabla ya kuchukulia hili kama utekelezaji wa code. Kagua script fupi kwa njia ya tuli; usiite wrapper yenye mamlaka.

Ruhusa halisi ya sudo ya root-capable `neofetch ""` bado inaweza kupakia usanidi wa shell ikiwa defaults zinazotumika za sudo zinahifadhi `XDG_CONFIG_HOME` inayodhibitiwa na mpigaji. [Kipakiaji cha usanidi cha Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) hupakia `neofetch/config.conf` au `neofetch/config` chini ya directory hiyo; orodha tupu ya argument haizuii utafutaji huu. Thibitisha kipakiaji kilichosakinishwa, sera halisi ya RunAs na argument, makatazo yoyote ya amri, kama sudo kweli huhifadhi kigezo kilichochaguliwa kwa amri hii, na kama mpigaji anadhibiti njia ya usanidi inayosomeka. Kigezo kilichohifadhiwa au Neofetch iliyosakinishwa pekee ni kidokezo cha ukaguzi. Kagua sera na metadata ya faili bila kuita amri yenye mamlaka au kuchapisha yaliyomo kwenye usanidi; tazama [ushughulikiaji wa mazingira wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Sheria ya sudo isiyo na vizuizi yenye uwezo wa root kwa `facter` inahitaji ukaguzi tofauti wa custom facts. [Puppet inaeleza](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) kuwa `--custom-dir` hupakia faili za fact za Ruby kutoka kwenye directory iliyochaguliwa. Kagua kama sheria halisi ya sudo inaruhusu chaguo hilo, kama Facter iliyosakinishwa inalikubali, na kama mpigaji anadhibiti directory. Ruhusa yenye argument zisizobadilika, katazo la amri lililo wazi, au custom facts zilizozimwa vinaweza kubadili matokeo. Uorodheshaji wa kimya unapaswa kuripoti mgombea wa sera bila kuita Facter au kusoma yaliyomo kwenye fact.

Kwa ruhusa halisi ya script ya sudo yenye uwezo wa root na `SETENV`, kagua majina ya amri yasiyo na njia kamili kama `find` na `PATH` halisi baada ya sera ya sudo na uanzishaji wa script. Faili ya Bash iliyopakiwa kwa source inaweza pia kuendesha `enable -n [`: [Bash kisha hutafuta `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) ili kupata `[` ya nje ambapo script baadaye hutumia amri hiyo. Thibitisha [sheria zinazotumika za sudoers kuhusu mazingira na `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), makatazo yoyote ya `NOSETENV`/`NOEXEC` au amri, mtiririko wa script na faili zilizopakiwa kwa source, na directory ya utafutaji inayoweza kuandikwa na mpigaji na kutekelezeka. Script inayosomeka yenye amri isiyo na njia kamili ni kidokezo cha ukaguzi, si uthibitisho wa utekelezaji wenye mamlaka; ikague bila kutumia sheria ya sudo.
- Script yenye mamlaka inayopakua URL isiyobadilika kwa `curl` bado inaweza kukubali jibu lililochaguliwa na mpigaji ikiwa sheria husika ya sudo inahifadhi `http_proxy` na ombi linatumwa kupitia proxy hiyo. Ikiwa script kisha inapeleka jibu kwa parser ya XML inayotatua external entities, jibu hasidi linaweza kufichua faili zinazosomeka na mchakato wenye mamlaka. Kagua sera halisi ya mazingira ya sudo, vizuizi vya `no_proxy`, URL inayoombwa, usanidi wa parser na mahali pa matokeo; kigezo cha proxy au parser ya XML pekee si udhaifu. [Nyaraka za mazingira ya proxy ya curl](https://everything.curl.dev/usingcurl/proxies/env.html) zinaeleza tabia ya vigezo hivyo. Usitume maombi ya mtandao au kuchanganua XML hasidi wakati wa uorodheshaji wa kimya.
- Script ya sudo yenye uwezo wa root inayounda faili ya PostScript kutokana na data inayoathiriwa na mpigaji kisha kuendesha `ps2pdf -dNOSAFER` inahitaji ukaguzi tofauti wa mtiririko wa input. Ghostscript inaeleza kuwa flag hii huzima SAFER hadi `.setsafe`, na kuruhusu shughuli za faili za PostScript ndani ya ruhusa za OS za mchakato. Query ya SQL iliyoundwa kutokana na argument ya mpigaji inaweza kupeleka rekodi zinazodhibitiwa na mshambulizi kwenye kiolezo cha PostScript, lakini query string au kuitwa kwa `ps2pdf` pekee hakuthibitishi kuwa data inafika kwenye sintaksia ya PostScript inayotekelezeka. Thibitisha sheria halisi ya sudo, njia halisi ya input hadi kiolezo, escaping yoyote, tabia ya Ghostscript iliyosakinishwa, na kama SAFER inawezeshwa tena kabla ya hati kutafsiriwa. Usiite ubadilishaji wenye mamlaka wakati wa uorodheshaji wa kimya. Tazama [nyaraka za `-dNOSAFER` za Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Kwa sheria ya sudo inayoendesha script ya shell, linganisha vigezo vilivyohifadhiwa na script yenyewe. Muundo kama `if $CHECK_CONTENT; then` huendesha thamani iliyopanuliwa kama amri, kwa hiyo kuhifadhi `CHECK_CONTENT` kunaweza kuruhusu utekelezaji wa amri hata kama njia na argument za script hazibadiliki. Lazima ukague kama tawi linaweza kufikiwa na kama mazingira yanahifadhiwa kweli kwa sheria husika.<sup>[[2]](#references)[[22]](#references)</sup>
- Script ya Python iliyoruhusiwa na sudo inaweza kuimport code kutoka directory inayoweza kuandikwa au faili ya `.pyc` iliyowekwa kwenye cache. [Mwongozo wa privilege escalation](../linux-basics/linux-privilege-escalation/README.md) unaeleza hali ya cache.

Kagua sheria halisi ya RunAs ya sudo, masharti ya uthibitishaji na matawi, uwezekano wa kufikiwa kwa exception, umiliki wa terminal/input, na kama debugger inaendeshwa ndani ya mchakato huohuo wenye mamlaka. Ombi la socket linalosababisha exception halitoi lenyewe ufikiaji wa debugger iliyounganishwa na terminal nyingine. [Python inaeleza tathmini ya kauli za debugger na hali ya post-mortem](https://docs.python.org/3/library/pdb.html); kagua script kwa njia ya tuli badala ya kuchochea handler yenye mamlaka wakati wa uorodheshaji.

[Sehemu za ubadilishaji zinaweza kufuata attributes na funguo za mapping](https://docs.python.org/3/library/string.html#format-string-syntax), kwa hiyo sehemu inayodhibitiwa na mshambulizi inaweza kukagua objects zinazopelekwa kwa `format()` na kufichua data inayoweza kufikiwa kupitia hizo ikiwa matokeo yanachapishwa au kuhifadhiwa mahali mpigaji anaweza kusoma. Hili si utekelezaji wa code wa moja kwa moja, na format string halisi inayoaminika yenye *values* zinazodhibitiwa na mshambulizi ni hali tofauti. Siri iliyofichuliwa husababisha mabadiliko ya akaunti ya OS tu ikiwa akaunti hiyo inakubali siri hiyo. Kagua script na ruhusa za socket bila kuita operesheni yenye mamlaka.

- Wrapper maalum inayomilikiwa na root inaweza kuonekana salama kwa sababu binary na script zake haziandikiki, ilhali uamuzi wake wa kuendesha kitendo chenye mamlaka unategemea flag, thamani ya API ya ndani au hali ya huduma ambayo mtumiaji asiye na mamlaka anaweza kubadilisha. Fuatilia kila sharti hadi input yake na ukaguzi wa idhini. Thibitisha sheria halisi, `runchdir` au sera nyingine inayobadilisha directory, mtiririko wa script na uwezekano wa kufikiwa kwa tawi, directory inayoweza kuandikwa na kutekelezeka, na vizuizi vya mount/`NOEXEC` kabla ya kuchukulia hili kama utekelezaji wa code. Thibitisha sheria halisi ya sudo, kama mpigaji anaweza kuchagua na kudhibiti faili husika, masharti ya matawi ya parser na uundaji wa expression, pamoja na utambulisho wa mchakato wenye mamlaka kabla ya kuliita njia ya utekelezaji. Kuwepo kwa `eval` kwenye script inayosomeka ni ishara ya ukaguzi tu; kagua source na ruhusa za faili bila kuendesha validator au kutuma expression ya majaribio wakati wa uorodheshaji.

Tazama [nyaraka za Psych za Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) na [nyaraka za Psych za Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

### Zana za build na vifurushi zinazoendeshwa kupitia sudo

Ruhusa ya sudo isiyo na vizuizi kwa `forge` ya Foundry inaweza kuwa muhimu hata kama utambulisho wa RunAs ni mtumiaji mwingine asiye root. Chaguo za compiler kama `--use` zinaweza kuchagua executable ya ndani, na `forge flatten -o` huchagua faili ya matokeo. Kagua toleo la Forge lililosakinishwa, argument halisi za sudo, njia za project na compiler zinazofikika, ruhusa za matokeo na mazingira halisi kabla ya kuchukulia ruhusa hii kuwa inaweza kutumiwa vibaya. Executable ya helper ya relative inayopatikana kupitia `PATH` ni njia inayotegemea toleo na mazingira, si tabia ya kudhaniwa kwa kila Forge build.<sup>[[23]](#references)[[24]](#references)</sup>

Ruhusa ya root-capable `pacman` isiyo na vizuizi inaruhusu zaidi ya maswali ya vifurushi: `-U` hukubali kifurushi cha ndani, vifurushi vinaweza kuwa na script za usakinishaji, na `--hookdir` huchagua directory nyingine ya hook. Kagua sheria halisi ya sudo, vizuizi vya argument na makatazo kabla ya kujaribu; uorodheshaji wa kimya hauhitaji kusakinisha kifurushi au kuendesha hook.<sup>[[25]](#references)[[26]](#references)</sup>

Wrapper ya shell ya sudo isiyobadilika inaweza pia kusakinisha dependency ya npm yenye jina maalum kisha kuanzisha programu ya Node. Kagua sheria halisi ya RunAs, kama kifurushi tayari kimesakinishwa, `HOME` na `userconfig` halisi ya npm, usanidi wa project au ubatilishaji wa command-line, na kama mtumiaji mwenye mamlaka ya chini anadhibiti registry au kifurushi kinachorejeshwa kwa jina hilo. [npm inaeleza utafutaji wa `.npmrc` wa mtumiaji na project](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); tabia ya `HOME` ya sudo hutegemea sera na distro iliyosakinishwa, kwa hiyo `.npmrc` ya mtumiaji inayoweza kuandikwa huenda ikasomwa au isisomwe na mchakato wa npm wenye mamlaka. Ikiwa kifurushi kipya kilichosakinishwa kinaimportiwa na programu yenye mamlaka, code ya moduli yake inaweza kuendeshwa chini ya utambulisho wa programu hiyo. Script za wakati wa usakinishaji ni njia tofauti inayotegemea toleo na usanidi; [npm inaeleza lifecycle yake na ushughulikiaji wa mtumiaji](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Njia ya `.npmrc` au mstari wa `npm install` pekee ni kidokezo cha ukaguzi. Kagua sheria, wrapper fupi, njia za usanidi na chanzo cha kifurushi bila kusakinisha au kuanzisha programu wakati wa uorodheshaji wa kimya.

Ruhusa ya root-capable `pip` au `pip3 download` pia ni kidokezo cha ukaguzi wa package-build ikiwa argument zake zinamruhusu mpigaji kuchagua source distribution isiyoaminika, hata kama muundo wa URL umewekewa kikomo kwa huduma ya ndani na suffix ya `.tar.gz`. `pip download` hukubali URL za archive na kutatua metadata ya kifurushi; kuandaa sdist kunaweza kuita build backend yake au code ya zamani ya `setup.py` kabla archive haijahifadhiwa tu. Thibitisha RunAs na sheria halisi ya argument za sudo, kama mpigaji anaweza kuchapisha au kubadilisha archive iliyochaguliwa, na kama toleo hilo la pip kweli huandaa metadata yake. Archive au wheel isiyobadilika na inayoaminika haithibitishi njia hii. Usipakue au kuunda kifurushi kisichoaminika wakati wa uorodheshaji wa kimya. Tazama [amri ya download ya pip](https://pip.pypa.io/en/stable/cli/pip_download/), [kiolesura cha build-system](https://pip.pypa.io/en/stable/reference/build-system/), na [mwongozo wa usakinishaji salama](https://pip.pypa.io/en/stable/topics/secure-installs/).

Sheria ya sudo inayoruhusu `pip install` pamoja na njia ya project ya ndani iliyochaguliwa na mpigaji ina mpaka wa build wa moja kwa moja zaidi. [pip hukubali directory za project za ndani](https://pip.pypa.io/en/stable/topics/local-project-installs/) na kuita build system yake; [build backend huendesha build hooks zinazodhibitiwa na project](https://pip.pypa.io/en/stable/reference/build-system/). Thibitisha utambulisho halisi wa RunAs, vizuizi vya argument na makatazo halisi, udhibiti wa project iliyochaguliwa, na tabia ya pip/backend iliyosakinishwa kabla ya kuchukulia sheria hii kama utekelezaji wa code wenye mamlaka. Project isiyobadilika na inayoaminika au sheria isiyoruhusu njia zilizochaguliwa na mpigaji haithibitishi njia hii. Kagua sheria na metadata ya project bila kusakinisha kifurushi wakati wa uorodheshaji wa kimya.

Ruhusa ya root-capable `easy_install` isiyo na vizuizi ni kidokezo kinachohusiana cha legacy package-build. [Setuptools inaeleza](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) kuwa Easy Install hukubali directory ya project ya ndani na kuunda source distributions; project inayodhibitiwa na mpigaji inaweza kuendesha `setup.py` yake wakati wa build hiyo chini ya utambulisho wa sudo. Thibitisha akaunti halisi ya RunAs, vizuizi vya amri na argument (pamoja na makatazo yanayofuata), udhibiti wa project iliyochaguliwa na tabia ya zana iliyosakinishwa. Project isiyobadilika na inayoaminika au sera isiyoruhusu source iliyochaguliwa na mpigaji haithibitishi njia hii. Kagua sheria na metadata ya project bila kusakinisha kifurushi wakati wa uorodheshaji.

Wrapper ya Python iliyoruhusiwa na sudo inayotumia `setuptools.package_index.PackageIndex.download` pamoja na URL iliyochaguliwa na mpigaji ni hali tofauti ya ukaguzi na `pip download`: [GHSA-5rjg-fvgr-3xxf ya setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) inaeleza jinsi jina la faili lililotokana na URL lilivyoweza kutoka nje ya directory iliyokusudiwa ya download na kuandika kwa ruhusa za mchakato katika matoleo yaliyoathirika kabla ya 78.1.1. Thibitisha RunAs na sheria halisi ya argument za sudo, kuwa wrapper inapitisha URL ya mpigaji kwa API hii hasa, build iliyosakinishwa au backport ya vendor, na mahali njia inayotokana inaelekea. String ya toleo au directory ya download inayoweza kuandikwa pekee haithibitishi uandishi wa kiholela. Kagua wrapper fupi na metadata ya kifurushi bila kuchukua URL au kuandika faili wakati wa uorodheshaji.

Wrapper ya build iliyoruhusiwa na sudo inayopitisha faili ya `.spec` iliyochaguliwa na mpigaji kwa PyInstaller inahitaji ukaguzi huo huo wa mpaka wa uaminifu. PyInstaller spec ni Python inayotekelezwa wakati wa **build**, na maingizo yake ya `datas` yanaweza kujumuisha kwenye artifact faili zinazosomeka na utambulisho wa build. Thibitisha mtumiaji halisi wa RunAs, sheria za argument na makatazo ya sudo, ushughulikiaji wa njia na matawi wa wrapper, udhibiti wa faili ya spec iliyochaguliwa, na ufikiaji wa artifact inayotokana. Kuruhusu tu input ya `.py` au kukuta PyInstaller imesakinishwa hakuthibitishi udhibiti wa spec-file au utekelezaji wenye mamlaka. Ukaguzi wa kimya unapaswa kusoma wrapper yenye upeo mdogo na metadata pekee; usiendeshe build. Tazama [nyaraka za faili za spec za PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Wildcard za argument kwenye zana za pakiti zenye mamlaka

Katika sheria ya sudo ya `tcpdump`, `*` kwenye **muundo wa argument** inaweza kulingana na nafasi na slash, kwa hiyo kizuizi kinachoonekana kama njia bado kinaweza kuruhusu maandishi ya chaguo ya ziada. Hii ni tofauti na wildcard kwenye njia ya executable ya amri; kagua sheria kamili ya RunAs na makatazo yoyote ya baadaye. Ikiwa chaguo zinaweza kuingizwa, mwito unaoruhusiwa na [semantiki za chaguo za `tcpdump` iliyosakinishwa](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) ndivyo huamua kama `-F`, `-V`, `-r`, `-w`, au `-Z` hutoa primitive muhimu ya kusoma/kuandika. `-V` husoma orodha ya majina ya faili za capture, si dump ya jumla ya faili kiholela. AppArmor au sera nyingine ya MAC inaweza kuzuia ufikiaji wa faili hata sudo ikiruhusu amri; faili ya profile kwenye diski haithibitishi kuwa imepakiwa au inatekelezwa. Kagua idhini na sera kwa njia ya kimya kabla ya kufikia hitimisho. [Mwongozo wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unaeleza tofauti ya wildcard.

Sheria ya sudo yenye uwezo wa root inayoorodhesha executable ya `tcpdump` pekee, bila vizuizi vya argument, pia inahitaji ukaguzi. [Mwongozo wa tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) unaeleza `-z` kama amri ya baada ya rotation wakati `-C` au `-G` inazungusha capture iliyohifadhiwa; `-Z` au chaguo-msingi la wakati wa compile zinaweza kushusha mamlaka kabla amri hiyo haijaendeshwa. Thibitisha sheria halisi ya sudo, build iliyosakinishwa, tabia ya kushusha mamlaka, na kama rotation inaweza kutokea kabla ya kuchukulia sheria hii kuwa njia ya escalation. Sheria iliyoangaziwa ni mgombea wa ukaguzi, si uthibitisho wa utekelezaji wa amri kama root.

### Python imports zinazoendeshwa kupitia sudo chini ya akaunti nyingine

Entry point isiyobadilika ya Python bado inaweza kuimport moduli ambayo mpigaji anaweza kuhariri au kubadilisha, hata sudo ikiendesha script kama mtumiaji wa huduma **asiye root**. Kagua pia moduli za ndani **zinazokosekana**: ikiwa script inaimport moduli ambayo jina lake la faili linaweza kuundwa katika directory ya script inayoweza kuandikwa na mpigaji, Python inaweza kupakia faili hiyo chini ya utambulisho wa RunAs. Thibitisha sheria halisi ya sudo, [njia halisi ya utafutaji wa moduli](https://docs.python.org/3/library/sys_path_init.html) ya interpreter, kama moduli imejengwa ndani au kufungwa ndani ya interpreter, na kama import hiyo inafikiwa. Sheria ya moja kwa moja ya sudo kwa script ina mahitaji tofauti ya execute-bit na shebang. Wrapper tofauti inayoongeza tokens zinazotolewa na mpigaji baada ya `sudo -u account` pia inahitaji ukaguzi wa mtiririko wa argument: `-u` nyingine ndani ya tokens hizo ina umuhimu tu ikiwa sera ya sudo iliyotumika inaruhusu utambulisho unaotokana. Strings tuli pekee hazithibitishi njia yoyote kati ya hizo.

### Apache inayoendeshwa kupitia sudo yenye usanidi unaodhibitiwa na mpigaji

Ikiwa sheria ya sudo inaruhusu `apachectl`, `apache2ctl`, au `httpd` yenye mamlaka kutumia faili ya usanidi ya `-f` inayodhibitiwa na mpigaji, kagua ruhusa za faili hiyo na parent directory yake. Directive ya Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) hukubali jina la moduli likifuatiwa na **jina la faili ya moduli**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) pia hupakia faili. [`Include` na `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) zinaweza kupanua usanidi au kufichua yaliyomo kwenye faili kupitia makosa. Wrapper maalum inaweza kuthibitisha njia hizi, kushusha mamlaka au kuweka vizuizi vya argument, kwa hiyo usanidi unaoweza kuandikwa ni mgombea wa ukaguzi, si uthibitisho wa utekelezaji wa code. Kagua canonicalization ya njia, symlink na uchanganuzi wa directive kabla ya kufikia hitimisho.

### nginx inayoendeshwa kupitia sudo yenye usanidi unaodhibitiwa na mpigaji

Sheria ya `nginx` isiyo na vizuizi yenye uwezo wa root inaweza kuruhusu [`-c` kuchagua usanidi mwingine](https://nginx.org/en/docs/switches.html). Kagua argument na makatazo halisi ya sudo, kama mpigaji anaweza kutoa usanidi, na kama master au workers wanaotokana nayo huhifadhi ufikiaji wa njia zilizolindwa. `root` iliyochaguliwa pamoja na `autoindex` inaweza kufichua faili kupitia listener mpya; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) inaweza kutoa njia ya kuandika faili yenye mamlaka, lakini moduli ya DAV haijengwi kwa chaguomsingi na uwepo wake, ufikivu wa listener, ruhusa za faili na tabia ya temporary-file lazima vikaguliwe. Directive ya [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) pia inaweza kulenga faili iliyochaguliwa; kuandika log kwenye faili nyeti ya usanidi, kama `/etc/ld.so.preload`, kunahitaji mwandishi mwenye mamlaka halisi na rekodi ya log inayodhibitika kabla hakujawa njia ya escalation. Kuangaziwa kwa executable katika `sudo -l` ni kidokezo cha ukaguzi, si uthibitisho kuwa mojawapo ya njia hizi inafanya kazi. Uorodheshaji wa kimya haupaswi kuanzisha au kusanidi upya nginx.

### Ulinganishaji wa pattern katika Bash prompt zenye mamlaka

Script ya Bash iliyoruhusiwa na sudo ikisoma thamani kutoka kwa mpigaji na kuikagua kwa `[[ "$expected" == $entered ]]`, Bash hutafsiri operand ya kulia isiyonukuliwa kama pattern. Kwa hiyo wildcard inaweza kutosheleza ulinganisho bila kujua thamani inayotarajiwa. Kuweka operand hiyo ndani ya nukuu (`[[ "$expected" == "$entered" ]]`) huifanya iwe ulinganisho halisi wa string. Kagua sheria halisi ya sudo, kama prompt inaweza kufikiwa, na kile script hufanya baada ya ulinganisho; sintaksia pekee haithibitishi njia inayoweza kutumiwa vibaya. Epuka kuchapisha thamani inayotarajiwa wakati wa uorodheshaji. Tazama [marejeo ya miundo ya masharti ya Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper zinazoendeshwa kupitia sudo zinazopakua na kuendesha faili

Ruhusa isiyo na vizuizi ya root-capable sudo kwa helper maalum inahitaji ukaguzi wa mtiririko wa data ikiwa helper hukubali URL iliyochaguliwa na mpigaji, huandika jibu kwenye diski, na baadaye huita faili hiyo kwa interpreter au shell. [Sudoers huruhusu argument zozote ikiwa entry ya amri haijaorodhesha argument](https://man7.org/linux/man-pages/man5/sudoers.5.html); njia isiyobadilika ya executable haizuii kile argument zake zinaweza kuchagua. Thibitisha uthibitishaji halisi wa URL, njia ya matokeo, tawi la mafanikio na utekelezaji unaofuata katika helper iliyosakinishwa. Import ya libcurl inayolingana au string inayochapishika pekee haithibitishi mnyororo huu.

Hata basename isiyobadilika ya matokeo inaweza kubadilishwa kati ya kuandika na kutekeleza ikiwa helper inatumia **njia ya relative katika working directory inayodhibitiwa na mpigaji**. Kubadilisha jina au faili inayomilikiwa na root kunategemea ufikiaji wa kuandika/kutafuta wa directory na vizuizi vya sticky bit, si mode ya faili pekee; tazama [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Kagua kama helper baadaye hufungua tena njia au hutumia file descriptor iliyokwisha funguliwa, na kama inahamia kwenye directory inayoaminika kabla ya kuandika. Kagua sera ya sudo, helper na metadata ya directory kwa njia ya kimya; usiite download yenye mamlaka au kufanya race wakati wa uorodheshaji.

Helper ya download inayoendeshwa kama root kupitia sudo inaweza pia kufichua **injection ya argument** inapounda string ya amri ya Bash kama `curl <caller input> -o <fixed output>`. Filter inayokataa whitespace bado huacha [upanuzaji wa braces wa Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): vipengee vilivyotenganishwa kwa koma na visivyonukuliwa vinaweza kuwa argument tofauti za curl. Ikiwa input inafika kwa curl kabla ya `-o` isiyobadilika, chaguo la matokeo linalotolewa na mpigaji linaweza kuchagua destination ya URL ya kwanza chini ya utambulisho wa helper; [curl huhusisha chaguo za matokeo na URL kwa mpangilio](https://curl.se/docs/manpage.html#-o). Thibitisha shell halisi, uwekaji wa nukuu, uthibitishaji wa input, sheria halisi ya sudo, mpangilio wa argument za curl na schemes za URL zinazoungwa mkono, na kama mpigaji anadhibiti bytes zilizopakuliwa au anaweza kusoma matokeo. Executable iliyofungwa kwa PyInstaller inaweza kuwa na mantiki ya programu ya Python, lakini alama ya packaging au string ya `curl` pekee haithibitishi mtiririko huu wa data. Kagua nakala ya offline yenye upeo mdogo ikiwa imeidhinishwa; uorodheshaji wa kawaida haupaswi kuendesha helper au kupakua data iliyochaguliwa na mshambulizi.

Script ya shell ya sudo kama root inayotumia [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) huchagua tu jina ambalo halitumiki; **haiundi** faili. Ikiwa script baadaye inaunda jina hilo kwenye directory ambayo mtumiaji mwingine anaweza kuathiri, kisha kuifungua tena na kuongeza yaliyomo kwenye destination iliyolindwa kama `authorized_keys` ya root, kagua uwezekano wa race ya temporary file. Thibitisha sheria halisi ya sudo, umiliki wa directory na faili, mfuatano wa uundaji na ufunguaji upya, kinga za kernel, na kama uandishi wenye mamlaka unatumia kweli bytes zinazodhibitiwa na mshambulizi. String ya `mktemp -u` au `/tmp` inayoweza kuandikwa pekee haithibitishi race hiyo. Kagua script na metadata ya njia bila kuiendesha au kufanya race ya temporary file yake wakati wa uorodheshaji.
