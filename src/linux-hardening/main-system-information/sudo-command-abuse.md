## Sudo द्वारा अनुमत interpreters

अगर `sudo -l` किसी user को root के रूप में interpreter चलाने की अनुमति देता है, तो इसे direct code execution मानें। Interpreters मनमाना code execute करने के लिए बनाए गए हैं, इसलिए `python3`, `perl`, `ruby`, `lua`, `node` या ऐसे ही binaries चलाने की अनुमति देने वाला rule आमतौर पर root command execution के बराबर होता है, जब तक कि arguments पर सख्ती से सीमाएँ न लगाई गई हों और उनकी पुष्टि न की गई हो।<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

आम review flow: पहले user के privileges सूचीबद्ध करें, फिर interpreter के `-c` option से Python statement execute करें।<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

नीचे अन्य interpreter के उदाहरण दिए गए हैं; सूचीबद्ध interpreters inline-code execution या child-process APIs का वर्णन करते हैं।<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

सटीक path मायने रखता है। अगर sudo rule `/usr/bin/python3` की अनुमति देता है, तो validation के दौरान उसी सटीक path का उपयोग करें।<sup>[[2]](#references)</sup>

`/usr/bin/python*` जैसा sudo executable glob Python 3 के लिए लिखी गई script को Python 2 के साथ भी चलाने की अनुमति दे सकता है। अगर script caller के नियंत्रण वाले text के साथ `input()` तक पहुँचती है, तो [Python 2 उस text को expression के रूप में evaluate करता है](https://docs.python.org/2/library/functions.html#input); interpreter को स्पष्ट रूप से चलाने पर script का shebang लागू नहीं होता। इस path को execution path मानने से पहले इंस्टॉल किए गए matching binaries, प्रभावी RunAs और argument policy, denials और उपलब्ध input की जाँच करें।

Root-capable sudo rule में तय script path इस बात को सीमित नहीं करता कि script क्या execute करती है। पढ़ी जा सकने वाली Bash wrapper के लिए जाँचें कि क्या उसका पहला executable command, sudo द्वारा caller-selected arguments की अनुमति दिए जाने पर, `$1` जैसे unquoted positional parameter को **command word** के रूप में उपयोग करता है। प्रभावी RunAs identity, password और argument policy, बाद के denials और script की वास्तविक branch की पुष्टि करें; `NOEXEC`, तय सुरक्षित argument list, या अपने command को validate करने वाली wrapper नतीजे को बदल सकती है। Enumeration के दौरान छोटी script को test command के साथ चलाने के बजाय उसका static निरीक्षण करें।

`dotnet` के लिए unrestricted root-capable sudo rule की भी interpreter के नज़रिए से समीक्षा करें। .NET SDK इंस्टॉल होने पर, [`dotnet fsi` F# code को interactively या script से चलाता है](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), और [`dotnet run` source से project execute करता है](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)। पहले प्रभावी RunAs identity और सटीक argument policy की पुष्टि करें: किसी विशेष सुरक्षित subcommand या trusted application तक सीमित rule एक अलग grant है, और केवल runtime वाला installation SDK commands से रहित हो सकता है। Executable का नाम केवल समीक्षा का संकेत है, code execution का प्रमाण नहीं।

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo की अनुमति वाले editors

अगर `sudo -l` किसी user को root के रूप में interactive editor चलाने की अनुमति देता है, तो इसे harmless file-editing permission नहीं, बल्कि command-execution surface मानें। Editors अक्सर shell commands चला सकते हैं, arbitrary files पढ़ या लिख सकते हैं, या editor के भीतर से external helpers चला सकते हैं।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

समीक्षा का सामान्य तरीका: पहले user के privileges की सूची देखें, फिर sudo के तहत हर allowed editor या pager चलाएँ।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano command execution

जब `nano` को sudo के माध्यम से चलाने की अनुमति होती है, तो editor interface से command execution तक पहुँचा जा सकता है।<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

फिर nano command prompt पर `id` या `/bin/sh` जैसा कोई command दें।<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

यदि किसी interactive shell में उपयोग योग्य terminal streams नहीं हैं, तो यह redirection form इसके standard output और error को descriptor 0 पर मैप करता है।<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

nano के version और build options के अनुसार सटीक key sequence अलग हो सकता है, लेकिन security issue वही है: editor root के रूप में चल रहा है और बाहरी commands चला सकता है।<sup>[[1]](#references)[[12]](#references)</sup>

### अन्य आम editor escapes

Vim-शैली के editors आमतौर पर `:!` के ज़रिए command execution की सुविधा देते हैं।<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` जैसे pagers shell execution भी उपलब्ध करा सकते हैं।<sup>[[14]](#references)</sup>

`apport-cli` को root के रूप में चलाने की अनुमति देने वाले sudo rule की भी pager के लिए यही जांच करें। Apport के प्रभावित versions crash report को `less` में ऐसे terminal size के साथ खोल सकते थे जिसे attacker समायोजित कर सकता था; यदि sudo और pager की विशेष शर्तें पूरी हों, तो pager root shell दे सकता था। केवल version को vulnerable मानने से पहले प्रभावी sudo rule, pager configuration और distribution package fix जांचें। Passive enumeration के दौरान crash उत्पन्न किए बिना या privileged report खोले बिना package और policy metadata पढ़ें। [Ubuntu का CVE record](https://ubuntu.com/security/CVE-2023-1326) release-specific fixed package versions सूचीबद्ध करता है, जिनमें backported fixes भी शामिल हैं।

```text
!/bin/sh
```

## sudo और doas नियमों के अन्य जोखिम

शुरुआत `sudo -l`, `sudo -V` और लागू `doas` policy से करें। अनुमत command, run-as user, arguments, environment और defaults को एक साथ पढ़ें। गैर-root service account के रूप में चलाने की अनुमति भी उस account की files तक पहुँच या root तक पहुँचने का रास्ता दे सकती है।

एक निश्चित sudo-अनुमत Python script, अपने RunAs identity के तहत shell command चला सकती है, यदि interactive, caller-controlled input को [`os.system()`](https://docs.python.org/3/library/os.html#os.system) में जोड़ दिया जाए। Shell punctuation की denylist सुरक्षा सुनिश्चित करने के लिए पर्याप्त नहीं है: [shell `$(...)` command substitution को भी पहचानता है](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)। पुष्टि करें कि अनुमत arguments input branch तक पहुँचते हैं, input बिना सुरक्षित validation के shell command तक पहुँचता है, और प्रभावी sudo policy इच्छित RunAs user की अनुमति देती है। केवल script path या `os.system()` का call समीक्षा के लिए संकेत है; privileged script चलाए बिना source देखें।

`chattr` के लिए प्रभावी root sudo grant immutable (`i`) file attribute हटा सकता है, लेकिन इससे अकेले write access या नई identity नहीं मिलती। [`chattr` manual](https://man7.org/linux/man-pages/man1/chattr.1.html) के अनुसार, यह attribute बदलाव रोकता है और इसे केवल root या `CAP_LINUX_IMMUTABLE` वाला process बदल सकता है। sudo arguments की सटीक policy और filesystem support जाँचें, फिर अलग से सत्यापित करें कि attribute हटने के बाद caller file लिख सकता है और उच्च-identity वाला कोई consumer उसका उपयोग करता है। उदाहरण के लिए, login shell बदलने के लिए target account की स्वीकार्य credentials और उस shell के ज़रिए वास्तविक login भी आवश्यक है। Enumeration के दौरान policy, file attributes और permissions की समीक्षा करें, उन्हें बदलें नहीं।

यदि sudo password और one-time code, दोनों माँगता है, तो इन prerequisites को command grant से अलग रखें। पढ़ी जा सकने वाली `.google_authenticator` file में संवेदनशील seed material होता है, जबकि पुराना application या database password hash केवल मौजूदा account password का उम्मीदवार है; इनमें से कोई भी यह साबित नहीं करता कि प्रभावी PAM configuration दूसरा factor स्वीकार करती है। अनुमति मिलने के बाद, सटीक RunAs और arguments की समीक्षा करें: RubyGems `gem` के लिए बिना पाबंदी वाला root grant उसका editor command उजागर कर सकता है ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), लेकिन restricted grant या विफल authentication ऐसा नहीं करता। Passive enumeration में seed दिखाए बिना, password recover किए बिना, code बनाए बिना या privileged command चलाए बिना paths और policy की रिपोर्ट करें।

Chef के `knife` के लिए बिना पाबंदी वाला root-capable sudo grant interpreter-स्तर की समीक्षा योग्य है: [Chef के दस्तावेज़ बताते हैं कि `knife exec -E` स्थानीय रूप से Ruby string evaluate करता है](https://docs.chef.io/workstation/26/tools/knife/knife_exec/)। सत्यापित करें कि प्रभावी sudo rule `exec` subcommand और caller द्वारा दिया गया `-E` argument, इच्छित RunAs identity और matching command denials या fixed arguments की अनुमति देता है। Installed binary या अन्य subcommands तक सीमित rule केवल जाँच का संकेत है। Passive enumeration में `knife` न चलाएँ; केवल rule की रिपोर्ट करें।

Interactive `msfconsole` के लिए सटीक root-capable sudo grant भी संवेदनशील है: [GTFOBins इसके `irb` console का दस्तावेज़ देता है](https://gtfobins.org/gtfobins/msfconsole/), जो sudo identity विरासत में ले सकता है। प्रभावी RunAs user, अनुमत arguments की सूची, command denials, `NOEXEC` या अन्य restrictions, installed console का व्यवहार और caller द्वारा interactive input देने की क्षमता की पुष्टि करें। केवल path का highlight जाँच का संकेत है; passive enumeration में console न चलाएँ।

FreeBSD पर, root के रूप में केवल `pkg update` और `pkg install *` तक सीमित sudo rule भी repository-trust की समीक्षा योग्य है। जाँचें कि caller `/etc/hosts` लिख सकता है या नहीं और क्या *प्रभावी* enabled repository configuration, `signature_type: none` वाले HTTP hostname का उपयोग करती है। [FreeBSD के `pkg.conf` manual](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) के अनुसार, `none` signature checks निष्क्रिय करता है; केवल `pkg+http` से यह साबित नहीं होता। Package में install scripts हो सकती हैं ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), इसलिए repository endpoint पर वास्तविक नियंत्रण रखने और package चुन सकने वाला caller root boundary पार कर सकता है। यह निष्कर्ष निकालने से पहले repository overrides, SRV/mirror resolution, प्रभावी sudo arguments, package selection और script execution की पुष्टि करें। Enumeration के दौरान names redirect किए बिना या `pkg` चलाए बिना policy और छोटी local configuration files देखें।

`apt-get update` और `apt-get upgrade` के लिए root-capable sudo grant को भी repository-trust की समीक्षा चाहिए, यदि sudo caller-controlled `http_proxy` को बनाए रखता है। जाँचें कि प्रभावी APT proxy configuration वास्तव में उस variable का उपयोग करती है या नहीं और वह किन enabled repository requests को प्रभावित कर सकता है; proxy अकेले trusted signing key से authenticated archive के packages को बदल नहीं सकता। [APT के HTTP transport manual](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) में proxy precedence का और [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) में signature checks, insecure-repository overrides और unauthenticated packages की पुष्टि का दस्तावेज़ है। सटीक sudo RunAs और arguments, repository authentication policy, आवश्यक interactive acceptance और यह कि चुना गया upgrade package scripts को root के रूप में चलाता है या नहीं—इन सबकी पुष्टि करें। Policy और local configuration को निष्क्रिय रूप से देखें; Enumeration के दौरान package traffic redirect न करें और upgrade न चलाएँ।

` snap install` के लिए root-capable sudo rule, package-to-code boundary बन सकता है, यदि उसके arguments caller को local snap और permissive install mode चुनने देते हों। [Snap के दस्तावेज़](https://snapcraft.io/docs/explanation/snap-development/install-modes/) बताते हैं कि `--dangerous` local-snap assertion checks छोड़ता है और `--devmode` confinement ढीला करता है; [install hook शुरुआती installation पर चल सकता है](https://snapcraft.io/docs/reference/development/supported-snap-hooks/)। Protected host files तक पहुँच का दावा करने से पहले सटीक sudo argument/RunAs policy, snap file पर किसका नियंत्रण है, installed snapd इन modes को स्वीकार करता है या नहीं, और hook की प्रभावी identity तथा confinement जाँचें। केवल `snap` binary या wildcard जैसा दिखने वाला rule इस chain को साबित नहीं करता। Passive enumeration में package install न करें और उसका hook न चलाएँ।

किसी **non-root** account के custom credential-reading binary के लिए सटीक sudo grant हो, तो पहले उसे चलाए बिना binary और उसकी file permissions देखें। Embedded password gate केवल wide characters के रूप में दिख सकता है; [GNU `strings` 16-bit little-endian extraction का दस्तावेज़ देता है](https://sourceware.org/binutils/docs/binutils/strings.html)। दिखने वाली string यह साबित नहीं करती कि वही स्वीकार्य password है या success branch मौजूदा credential उजागर करती है। Binary के व्यवहार, protected data तक target account की पहुँच, credential की वैधता और बाद में account या group transition—इन सबकी अलग-अलग पुष्टि करें। यदि वह account `docker` group में है, तो host-root access का अनुमान लगाने से पहले socket access और daemon की rootful या rootless identity जाँचें; [Docker अपने group के root-स्तरीय प्रभावों का दस्तावेज़ देता है](https://docs.docker.com/engine/install/linux-postinstall/)। नियमित enumeration में binary चलाए या उसकी strings dump किए बिना sudo rule और group membership की रिपोर्ट करें।

Application maintenance scripts के लिए wildcard sudo rule की समीक्षा केवल script path तक सीमित नहीं होनी चाहिए। जाँचें कि अनुमत script unrestricted arguments स्वीकार करती है या कम-privileged application account द्वारा लिखी जा सकने वाली settings पढ़ती है, फिर उन values को shell commands या subprocess environment तक trace करें। उदाहरण के लिए, ZoneMinder की [`zmupdate.pl` `mysqldump` command बनाती है और उसे `qx` से चलाती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), जबकि [`zmdc.pl` daemon शुरू करने से पहले `ZM_LD_PRELOAD` setting को `LD_PRELOAD` में copy करती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)। यदि संबंधित input नियंत्रित किया जा सकता है और installed version में उस code तक पहुँचता है, तो दोनों में से किसी script को root के रूप में चलाने वाला sudo rule trust boundary पार कर सकता है। प्रभावी sudo rule, application configuration permissions और script source देखें; wildcard या setting अकेले execution का प्रमाण नहीं, केवल समीक्षा का संकेत है।

- `SETENV`, `env_keep`, `secure_path` और `LD_PRELOAD`, अन्यथा सीमित command को import, library या PATH hijack में बदल सकते हैं। [environment-variable guide](../linux-basics/linux-environment-variables.md) और [SUID/linker abuse](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md) देखें।

Shell wrapper को root-capable `SETENV` का सटीक grant मिला हो और वह literal import के साथ निश्चित Python script चलाता हो, तो एक-hop समीक्षा भी करें। `secure_path` shell command lookup सीमित करता है, Python की [`PYTHONPATH` module search](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) नहीं; [`-E` और `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) Python को उस environment variable की अनदेखी करवाते हैं। इसे code execution मानने से पहले प्रभावी sudo tags और denials, wrapper branch, interpreter options, import resolution और caller द्वारा लिखी जा सकने वाली search directory की पुष्टि करें। छोटी scripts को statically देखें; privileged wrapper न चलाएँ।

`neofetch ""` के लिए सटीक root-capable sudo grant, लागू sudo defaults द्वारा caller-controlled `XDG_CONFIG_HOME` बनाए रखने पर shell configuration लोड कर सकता है। [Neofetch का configuration loader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) उस directory के अंदर `neofetch/config.conf` या `neofetch/config` source करता है; खाली argument list इस lookup को नहीं रोकती। Installed loader, प्रभावी RunAs और argument policy, command denials, sudo इस command के लिए चुने गए variable को वास्तव में बनाए रखता है या नहीं, और caller किसी readable configuration path को नियंत्रित करता है या नहीं—इनकी पुष्टि करें। केवल preserved variable या installed Neofetch जाँच का संकेत है। Privileged command चलाए या configuration contents दिखाए बिना policy और file metadata देखें; [sudoers environment handling](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।

बिना पाबंदी वाले root-capable `facter` sudo rule के लिए custom-fact की अलग समीक्षा करें। [Puppet के दस्तावेज़](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) के अनुसार, `--custom-dir` चुनी हुई directory से Ruby fact files लोड करता है। जाँचें कि सटीक sudo rule उस option की अनुमति देता है या नहीं, installed Facter उसे स्वीकार करता है या नहीं और caller directory नियंत्रित करता है या नहीं। Fixed-argument grant, explicit command denial या disabled custom facts से परिणाम बदल सकता है। Passive enumeration में Facter चलाए या fact contents पढ़े बिना policy candidate की रिपोर्ट करें।

`SETENV` के साथ root-capable sudo script का सटीक grant हो, तो `find` जैसे bare command names और sudo policy तथा script initialization के बाद प्रभावी `PATH` देखें। Sourced Bash file `enable -n [` भी चला सकती है: [इसके बाद Bash `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) में external `[` खोजता है, जहाँ script बाद में उस command का उपयोग करती है। इसे code execution मानने से पहले लागू [sudoers environment और `secure_path` rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), कोई भी `NOSETENV`/`NOEXEC` या denial entries, script तथा sourced-file flow, और caller-नियंत्रित search directory में executable की मौजूदगी की पुष्टि करें। Bare command वाली readable script जाँच का संकेत है, privileged execution का प्रमाण नहीं; sudo rule चलाए बिना उसे देखें।
- Caller द्वारा चुना गया response, fixed URL को `curl` से fetch करने वाली privileged script में भी स्वीकार हो सकता है, यदि लागू sudo rule `http_proxy` बनाए रखता है और request उस proxy से भेजी जाती है। यदि script बाद में response ऐसे XML parser को देती है जो external entities resolve करता है, तो hostile response privileged process द्वारा पढ़ी जा सकने वाली files उजागर कर सकता है। सटीक sudo environment policy, `no_proxy` exclusions, requested URL, parser configuration और output destination जाँचें; केवल proxy variable या XML parser vulnerability नहीं है। [curl proxy environment documentation](https://everything.curl.dev/usingcurl/proxies/env.html) में variable के व्यवहार का वर्णन है। Passive enumeration के दौरान network request न करें और hostile XML parse न करें।
- Caller-प्रभावित data से PostScript file बनाकर `ps2pdf -dNOSAFER` चलाने वाली root-capable sudo script के input flow की अलग समीक्षा करें। Ghostscript के अनुसार, यह flag `.setsafe` तक SAFER निष्क्रिय करता है, जिससे process की OS permissions के भीतर PostScript file operations संभव होते हैं। Caller argument से बनाई गई SQL query attacker-controlled rows को PostScript template में पहुँचा सकती है, लेकिन query string या `ps2pdf` invocation अकेले यह साबित नहीं करते कि data executable PostScript syntax तक पहुँचता है। प्रभावी sudo rule, input से template तक का सटीक रास्ता, escaping, installed Ghostscript का व्यवहार और document interpret होने से पहले SAFER फिर से सक्षम होता है या नहीं—इनकी पुष्टि करें। Passive enumeration के दौरान privileged conversion न चलाएँ। [Ghostscript के `-dNOSAFER` दस्तावेज़](https://ghostscript.readthedocs.io/en/master/Use.html) देखें।
- Shell script चलाने वाले sudo rule के लिए, preserved variables की script से तुलना करें। `if $CHECK_CONTENT; then` जैसा construct expanded value को command के रूप में चलाता है, इसलिए `CHECK_CONTENT` बनाए रखने से fixed script path और arguments के बावजूद command execution संभव हो सकता है। जाँचें कि विशेष rule में branch तक पहुँचा जा सकता है या नहीं और environment वास्तव में बनाए रखा जाता है या नहीं।<sup>[[2]](#references)[[22]](#references)</sup>
- Sudo-अनुमत Python script, writable directory या cached `.pyc` file से code import कर सकती है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md) cache वाले मामले की जानकारी देती है।
- Root के रूप में चलने की अनुमति वाली निश्चित Python script interactive debugger भी उजागर कर सकती है। `pdb.set_trace()` या `pdb.post_mortem()` जैसे calls, जब caller breakpoint या exception handler तक पहुँच सकता हो **और debugger के input stream को नियंत्रित कर सकता हो**, तो debug हो रहे process के context में Python statements चलाने देते हैं। सटीक sudo RunAs rule, authentication और branch conditions, exception की reachability, terminal/input का ownership और debugger उसी privileged process में चलता है या नहीं—ये जाँचें। किसी socket request से exception आ जाना, दूसरे terminal से जुड़े debugger तक पहुँच अपने-आप नहीं देता। [Python debugger के statement evaluation और post-mortem mode का दस्तावेज़ देता है](https://docs.python.org/3/library/pdb.html); enumeration के दौरान privileged handler trigger करने के बजाय script statically देखें।
- Sudo-अनुमत निश्चित Python script database या Unix socket से profile field पढ़कर उसे ऐसी string में जोड़ सकती है जो बाद में `str.format()` के लिए **format string** बनती है। [Replacement fields, attributes और mapping keys के ज़रिए आगे जा सकते हैं](https://docs.python.org/3/library/string.html#format-string-syntax), इसलिए attacker-controlled field, `format()` को दिए गए objects की जाँच कर सकता है और उनसे उपलब्ध data उजागर कर सकता है, यदि परिणाम print हो या ऐसी जगह store हो जहाँ caller उसे पढ़ सके। प्रभावी sudo RunAs identity, खास record पर write access, format string तक data flow, दिए गए objects और output की visibility जाँचें। यह अपने-आप code execution नहीं है; trusted literal format string और attacker-controlled *values* अलग मामला हैं। उजागर secret से OS account transition तभी होगा जब वह account उसे स्वीकार करे। Privileged operation चलाए बिना script और socket permissions देखें।
- Root-capable Python wrapper caller-चुना URL GitPython के `Repo.clone_from` को दे सकता है। यदि wrapper Git का `protocol.ext.allow=always` भी सक्षम करता है, तो `ext::` remote बाहरी helper चला सकता है। सटीक sudo arguments, URL कहाँ से आता है, GitPython package version और vendor patch status, और wrapper unsafe protocols को स्पष्ट रूप से अनुमति देता है या नहीं—इनकी जाँच करें। GitPython ने 3.1.30 में [unsafe-protocol के लिए default guard](https://github.com/gitpython-developers/GitPython/commit/2625ed9) जोड़ा था; `git` executable का version अलग तथ्य है। Passive review में केवल rule और सीमित source देखें; clone न चलाएँ।
- Repository-cloning CLI के लिए cross-user sudo grant, shell-string injection का अलग रास्ता उजागर कर सकता है। Trace करें कि caller-चुना repository argument, बिना सुरक्षित argument separation के Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) या किसी अन्य shell-command builder तक पहुँचता है या नहीं; Node का `exec` अपनी command string shell को देता है। सटीक RunAs user, अनुमत subcommands और arguments, installed wrapper code और input validation की पुष्टि करें। Repository tool का नाम या unrestricted sudo rule अकेले command injection साबित नहीं करता। Enumeration में privileged clone चलाए बिना wrapper देखें।
- Custom root-owned wrapper सुरक्षित दिख सकता है क्योंकि उसकी binaries और scripts writable नहीं हैं, फिर भी privileged action चलाने का उसका निर्णय ऐसे flag, local API value या service state पर निर्भर हो सकता है जिसे unprivileged user बदल सके। हर gate को उसके input और authorization checks तक trace करें। Enumeration के दौरान operational state बदले बिना configuration और permissions देखें; wrapper के भीतर `systemd-run` call तभी प्रासंगिक है जब gate को प्रभावित किया जा सके।
- Root के रूप में sudo से चलने की अनुमति वाला backup client caller-चुनी configuration file (उदाहरण के लिए `npbackup-cli -c`) स्वीकार कर सकता है। सटीक run-as user और अनुमत arguments की जाँच करें, फिर देखें कि caller configuration path, backup source paths और repository या read/restore options नियंत्रित करता है या नहीं। Readable config में encrypted repository secret होने पर भी client उसका उपयोग कर सकता है, लेकिन rule अकेले repository access या root-file disclosure साबित नहीं करता। Backup चलाए या contents dump किए बिना authorization की पुष्टि करें।
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) `--password-command` का समर्थन करता है, जो repository password पाने के लिए program चलाता है। यदि sudo rule, कम-privileged user को caller-चुने password command और password की जरूरत वाले subcommand के साथ root के रूप में restic चलाने देता है, तो वह helper root के रूप में चल सकता है। सटीक sudo arguments और exclusions की समीक्षा करें; केवल शर्त जाँचने के लिए helper या backup command न चलाएँ।

- Root-capable `clamscan --debug` rule read boundary पार कर सकता है, यदि कम-privileged user DMG image दे सकता हो और installed parser [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) से प्रभावित हो, जिससे debug output के ज़रिए file contents उजागर हो सकते थे। सटीक अनुमत arguments और scan path, input पर नियंत्रण, प्रभावी RunAs account, engine patch/backport और output caller को दिखता है या नहीं—इनकी पुष्टि करें। यदि व्यापक rule `--file-list`/`-f` की अनुमति देता है, तो उस file-list व्यवहार की अलग समीक्षा करें; `--debug <scan-path>` तक fixed policy इसकी अनुमति नहीं देती। Enumeration में crafted file scan किए या protected output print किए बिना policy और package metadata देखें।
- Root-capable sudo rule, जो caller-चुनी encrypted disk image खोलता है, और दूसरी rule जो बने हुए mapper को mount करती है, caller-controlled files को host के mount namespace में ला सकती है। दोनों प्रभावी rules और arguments, image और mapper name पर नियंत्रण, वास्तविक mount target और परिणामी file owner तथा mode की पुष्टि करें। Set-user-ID transition के लिए executable तक पहुँच, उसे लागू करने वाले mount options (`nosuid` इसे रोकता है) और लागू process या MAC policy भी आवश्यक हैं; केवल image खोलना या mount करना जाँच का संकेत है। मौजूदा backup के ज़रिए अलग रास्ते के लिए उसकी वास्तविक key और उसके अंदर उपयोगी readable secret चाहिए। Passive enumeration में image खोले या mount किए बिना policy और paths देखें। [cryptsetup manual](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) और [mount options](https://man7.org/linux/man-pages/man8/mount.8.html) देखें।
- Shell या Python script के लिए root-capable sudo rule हो, तो working-directory की समीक्षा करें, यदि script fixed directory में जाए बिना `./helper` चलाती है। `subprocess.run` को दी गई Python list, जैसे `['./helper']`, में भी caller चुनी working directory वाला यही व्यवहार हो सकता है। Caller writable directory चुनकर वहाँ उस relative name का executable रख सकता है; script में किसी और जगह absolute path होना इस call को सुरक्षित नहीं करता। इसे code execution मानने से पहले प्रभावी rule, `runchdir` या अन्य directory-changing policy, script flow और branch reachability, writable तथा executable directory, और mount/`NOEXEC` restrictions की पुष्टि करें। Script न पढ़ी जा सके तो अधिकृत तरीके से source देखे जाने तक व्यवहार अज्ञात है। Helper चलाने के बजाय scripts statically देखें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) working-directory policy का दस्तावेज़ देता है।
- Root-capable fixed Python validator, caller-चुनी data file evaluate कर सकता है। [Python के `eval()` दस्तावेज़ untrusted input के विरुद्ध चेतावनी देते हैं](https://docs.python.org/3/library/functions.html#eval): input suffix check, arithmetic prefix या validation branch sandbox नहीं है, यदि शेष expression `eval` तक पहुँचती है। इसे execution path कहने से पहले प्रभावी sudo rule, caller सटीक file चुन और नियंत्रित कर सकता है या नहीं, parser की branch conditions और expression construction, तथा privileged process identity की पुष्टि करें। Readable script में `eval` दिखना केवल समीक्षा का संकेत है; Enumeration के दौरान validator चलाए या test expression भेजे बिना source और file permissions देखें।
- Root-capable sudo Ruby wrapper, जो `YAML.load(File.read("dependencies.yml"))` जैसे relative YAML filename को पढ़ता है, caller की working directory से input ले सकता है, जब तक wrapper या sudo policy directory को निश्चित न करे। सटीक अनुमत arguments, directory और file permissions, तथा installed Psych behavior जाँचें: पुराने `YAML.load` implementations arbitrary Ruby objects deserialize कर सकते थे, जबकि नए releases default रूप से classes सीमित करते हैं। Static call site केवल जाँच का संकेत है; पुष्टि करें कि file वास्तव में caller-writable directory से आती है और installed loader खतरनाक classes स्वीकार करता है। Untrusted input के लिए explicit minimal class allowlist के साथ `safe_load` को प्राथमिकता दें। [Ruby 3.0 Psych documentation](https://docs.ruby-lang.org/en/3.0/Psych.html) और [Ruby 3.1 Psych documentation](https://ruby-doc.org/core-3.1.2/Psych.html) देखें।

- `sudo go run /absolute/file.go` के लिए root-capable सटीक grant की working-directory समीक्षा करें, यदि Go source relative WASM file पढ़ता है और उसका परिणाम जाँचने के बाद relative shell script चला सकता है। प्रभावी RunAs, command arguments और denials, caller-writable current directory, WASM से branch तक data flow और उस branch में helper चलता है या नहीं—इनकी पुष्टि करें। Fixed sudo `runchdir`, `os.Chdir` या [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) lookup location बदल सकते हैं। Static co-occurrence केवल संभावित संकेत है; Go, WASM या helper चलाए बिना source देखें।
- `sudoedit` और argument wildcards के लिए version तथा rule की सटीक जाँच आवश्यक है; [checklist](linux-privilege-escalation-checklist.md) में sudoedit file-edit समस्या शामिल है। Wildcard path पर cross-user `sudoedit` grant के लिए प्रभावी `sudoedit_follow` या `FOLLOW` setting, `sudoedit_checkdir`, resolved target और हर parent entry को कौन बदल सकता है—इनकी जाँच करें। पहला symlink follow करने दे सकता है, जबकि दूसरा बंद होने पर writable-directory checks हट जाते हैं; इनमें से कोई setting अकेले दूसरे user की file में write साबित नहीं करती। निष्कर्ष निकालने से पहले installed sudo policy और सटीक matched arguments की पुष्टि करें। [sudoers option definitions](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।
- Sudoers command rule में argument wildcard whitespace के साथ-साथ path characters से भी match कर सकता है। Read-capable command के लिए `/restricted/*` जैसा argument किसी matching prefix के बाद अतिरिक्त file argument की अनुमति दे सकता है। सटीक run-as user, command path, argument pattern और बाद के denials की समीक्षा करें; file पढ़कर दिखाना command execution का प्रमाण नहीं है। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) argument globs और command-path globs में अंतर बताता है।
- Path जैसा दिखने वाला argument glob `../` से भी match कर सकता है। उदाहरण के लिए, root-capable `node /opt/scripts/*.js` rule caller-नियंत्रित JavaScript file को `/opt/scripts` से बाहर चलाने दे सकता है, यदि दिया गया pathname फिर भी `/opt/scripts/` से शुरू होता हो और parent-directory segments से resolve हो। यह **argument** glob है; Node executable के लिए command-path glob के slash-matching rules अलग हैं। Code execution का निष्कर्ष निकालने से पहले प्रभावी rule, बाद के denials, pathname resolution, target file पर नियंत्रण और sudoers regular-expression या digest restrictions जाँचें। [sudoers wildcard rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) और [Node command-line documentation](https://nodejs.org/api/cli.html) देखें।
- Archivers और अन्य utility programs में execution hooks हो सकते हैं। यह मानने के बजाय कि केवल shells या interpreters commands चलाते हैं, सटीक अनुमत arguments को [GTFOBins](https://gtfobins.github.io/) से जाँचें।
- Unrestricted root-capable `qpdf` rule, PDF attachments के ज़रिए privileged file उजागर कर सकता है: qpdf 10.2 और उसके बाद वाले versions, output PDF के साथ `--empty` और `--add-attachment file ... --` का समर्थन करते हैं। यदि privileged process चुने गए source को पढ़ सके और PDF को caller-accessible path पर लिख सके, तो output में source bytes हो सकते हैं। File disclosure संभव मानने से पहले प्रभावी sudo arguments और exclusions, qpdf version, source access और output path की समीक्षा करें। Root SSH key पढ़ना login के लिए तभी उपयोगी है जब key वैध हो और root SSH authentication अनुमत हो। [qpdf attachment options](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments) देखें।
- Sudo timestamp reuse, cache policy, owning user, terminal/session और permissions पर निर्भर करता है। [privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) में जाँचें दी गई हैं।
- `doas` के अपने rules और configuration होते हैं। [doas section](../linux-basics/linux-privilege-escalation/README.md#doas) के अनुसार अनुमत commands और writable configuration paths जाँचें।

### Sudo से चलने वाले build और package tools

Foundry के `forge` के लिए unrestricted sudo grant तब भी मायने रख सकता है जब RunAs identity कोई अन्य non-root user हो। `--use` जैसे compiler options local executable चुन सकते हैं और `forge flatten -o` output file चुनता है। Grant को exploitable मानने से पहले installed Forge version, सटीक sudo arguments, accessible project और compiler paths, output permissions और प्रभावी environment जाँचें। `PATH` से मिलने वाला relative helper executable, version और environment पर निर्भर रास्ता है; हर Forge build में इसे मानकर नहीं चलना चाहिए।<sup>[[23]](#references)[[24]](#references)</sup>

बिना पाबंदी वाला root-capable `pacman` grant, package queries से अधिक की अनुमति देता है: `-U` local package स्वीकार करता है, packages में install scripts हो सकती हैं और `--hookdir` दूसरी hook directory चुनता है। जाँच से पहले प्रभावी sudo rule, argument restrictions और exclusions की समीक्षा करें; passive enumeration में package install करने या hook चलाने की जरूरत नहीं है।<sup>[[25]](#references)[[26]](#references)</sup>

Fixed sudo shell wrapper, नामित npm dependency install करने और फिर Node application शुरू करने का काम भी कर सकता है। उसके सटीक RunAs rule, package पहले से installed है या नहीं, प्रभावी `HOME` और npm `userconfig`, project configuration या command-line overrides, तथा कम-privileged user उस नाम के लिए registry या लौटाए गए package को नियंत्रित करता है या नहीं—इनकी समीक्षा करें। [npm per-user और per-project `.npmrc` lookup का दस्तावेज़ देता है](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo का `HOME` व्यवहार installed policy और distribution पर निर्भर करता है, इसलिए privileged npm process उपयोगकर्ता की writable `.npmrc` पढ़े या नहीं, यह निश्चित नहीं है। यदि नया installed package privileged application import करती है, तो उसका module code उसी application की identity के तहत चल सकता है। Install-time scripts अलग, version और configuration पर निर्भर रास्ता हैं; [npm उनके lifecycle और user handling का दस्तावेज़ देता है](https://docs.npmjs.com/cli/v6/using-npm/scripts/). `.npmrc` path या `npm install` line अकेले केवल जाँच का संकेत है। Passive enumeration के दौरान install या application शुरू किए बिना rule, छोटी wrapper, configuration paths और package provenance देखें।

Root-capable `pip` या `pip3 download` grant भी package-build की समीक्षा का संकेत है, यदि arguments caller को untrusted source distribution चुनने देते हों—भले URL pattern उसे local service और `.tar.gz` suffix तक सीमित करे। `pip download` archive URLs स्वीकार करता है और package metadata resolve करता है; sdist तैयार करने पर archive केवल save होने से पहले build backend या legacy `setup.py` code चल सकता है। सटीक sudo RunAs और argument rule, caller चुना हुआ archive प्रकाशित या बदल सकता है या नहीं, और वह pip version वास्तव में metadata तैयार करता है या नहीं—इनकी पुष्टि करें। Fixed trusted archive या wheel इस रास्ते को साबित नहीं करता। Passive enumeration में untrusted package fetch या build न करें। pip के [download command](https://pip.pypa.io/en/stable/cli/pip_download/), [build-system interface](https://pip.pypa.io/en/stable/reference/build-system/) और [secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/) देखें।

Caller-चुने local project path के साथ `pip install` की अनुमति देने वाला sudo rule, build boundary का अधिक सीधा मामला है। [pip local project directories स्वीकार करता है](https://pip.pypa.io/en/stable/topics/local-project-installs/) और उनका build system चलाता है; [build backend project-controlled build hooks चलाता है](https://pip.pypa.io/en/stable/reference/build-system/). Rule को privileged code execution मानने से पहले प्रभावी RunAs identity, सटीक argument restrictions और denials, चुने project पर नियंत्रण, और installed pip/backend behavior की पुष्टि करें। Fixed trusted project या caller-चुने paths को रोकने वाला rule यह रास्ता साबित नहीं करता। Passive enumeration में package install किए बिना rule और project metadata देखें।

Unrestricted root-capable `easy_install` grant, इसी तरह का legacy package-build संकेत है। [Setuptools के दस्तावेज़](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) के अनुसार, Easy Install local project directory स्वीकार करता है और source distributions build करता है; caller-controlled project, sudo identity के तहत उस build के दौरान `setup.py` चला सकता है। प्रभावी RunAs account, सटीक command और argument restrictions (बाद के denials सहित), चुने project पर नियंत्रण और installed tool का व्यवहार जाँचें। Fixed trusted project या caller-चुने source की अनुमति न देने वाली policy इस रास्ते को साबित नहीं करती। Enumeration के दौरान package install किए बिना rule और project metadata देखें।

Caller-चुने URL के साथ `setuptools.package_index.PackageIndex.download` उपयोग करने वाला sudo-अनुमत Python wrapper, `pip download` से अलग समीक्षा का मामला है: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) में 78.1.1 से पहले प्रभावित releases में URL से निकला filename, इच्छित download directory से बाहर जा सकता था और process की permissions से file लिख सकता था। प्रभावी sudo RunAs और argument rule, wrapper caller का URL इसी API को देता है या नहीं, installed build या vendor backport, और resulting path कहाँ resolve होता है—इनकी पुष्टि करें। केवल version string या writable download directory arbitrary write साबित नहीं करती। Enumeration के दौरान URL fetch या file write किए बिना छोटी wrapper और package metadata देखें।

Caller-चुनी `.spec` file PyInstaller को देने वाली sudo-अनुमत build wrapper की भी trust-boundary समीक्षा करें। PyInstaller spec, **build** के दौरान evaluate होने वाला executable Python है और उसकी `datas` entries, build identity द्वारा पढ़ी जा सकने वाली files को artifact में bundle कर सकती हैं। सटीक RunAs user, sudo argument और denial rules, wrapper का path तथा branch handling, चुनी spec file पर नियंत्रण और परिणामी artifact तक पहुँच की पुष्टि करें। केवल `.py` input की अनुमति या PyInstaller installed मिलना spec-file पर नियंत्रण या privileged execution साबित नहीं करता। Passive review में केवल सीमित wrapper file और metadata पढ़ें; build न चलाएँ। [PyInstaller spec-file documentation](https://pyinstaller.org/en/stable/spec-files.html) देखें।

### Sudo से चलने वाले preset और plugin loaders

Caller-चुना preset या plugin directory स्वीकार करने वाले Python tools, sudo से मिली privileges के साथ code import कर सकते हैं। उदाहरण के लिए, BBOT `-p` से preset स्वीकार करता है और उसका [custom-module documentation](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) `module_dirs` entries का वर्णन करता है, जो अतिरिक्त Python module directories चुनती हैं। यदि प्रभावी sudo rule caller-चुने preset की अनुमति देता है और caller चुनी directory के किसी module को नियंत्रित करता है, तो import privileged user के रूप में code चला सकता है—संभव है कि tool invalid module अस्वीकार करने से पहले ही। Enumeration के दौरान module लोड किए बिना installed version, सटीक sudo run-as और argument policy, तथा preset और module paths का ownership जाँचें।

### Sudo से चलने वाला Backdrop command-line tool

[Bee](https://github.com/backdrop-contrib/bee), Backdrop CMS के लिए PHP command-line tool है। इसके `eval` (`php-eval`) और `php-script` commands caller द्वारा दिया PHP चला सकते हैं। इसलिए unrestricted arguments के साथ Bee executable को root के रूप में चलाने देने वाला sudo rule, Bee द्वारा Backdrop installation bootstrap कर पाने पर root code execution उजागर कर सकता है। इसे site directory से चलाएँ या global `--root=<directory>` option से site चुनें; केवल Bee या Backdrop `settings.php` file मिलना sudo permission, उपयोगी site या सफल bootstrap साबित नहीं करता। जाँच से पहले प्रभावी sudo rule, किसी भी command exclusions, executable की identity और site तक पहुँच की समीक्षा करें। Passive enumeration में Bee चलाए बिना rule और file paths देखें। PHP command additions के लिए [Bee command changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) देखें।

### Sudo से चलने वाले terminal servers

`mosh-server` invoking user के रूप में interactive terminal server शुरू करता है। यह high UDP port और session key चुनता है, दोनों caller को बताता है और client के connect होने पर सामान्यतः उस user का login shell शुरू करता है। इसलिए `mosh-server` के लिए unrestricted root-capable sudo grant shell-समीक्षा का उम्मीदवार है, भले server command खुद detach हो जाती हो। प्रभावी RunAs identity, अनुमत arguments और exclusions, installed binary, shell, client availability और UDP access जाँचें। Passive enumeration में server शुरू किए या कोई live session key दिखाए बिना sudo rule देखें। [Mosh server manual](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) और [upstream design notes](https://github.com/mobile-shell/mosh#how-it-works) देखें।

### Caller की task file को दोबारा लिखने वाले privileged backup wrappers

Root के रूप में चलने वाली shell wrapper caller द्वारा चुनी task file स्वीकार कर सकती है, source paths से `../` हटा सकती है, जाँच सकती है कि हर परिणाम अनुमत directory से शुरू होता है, task file दोबारा लिख सकती है और फिर उसका *pathname* backup program को दे सकती है। पूर्ण canonical resolution के बाद transformed path की समीक्षा करें: string को एक बार बदलने से नया traversal sequence सामने आ सकता है, जिसे lexical prefix check स्वीकार कर ले। यह भी जाँचें कि backup program transformed in-memory data पढ़ता है या file फिर से खोलता है। यदि वह file दोबारा खोलता है, तो rewrite विफल होने पर मूल input वहीं रह सकती है।

Linux पर `fs.protected_regular`, world-writable sticky directory में किसी अन्य user की regular file पर `O_CREAT` write को रोक सकता है। यह रोक सुरक्षात्मक है, लेकिन यदि shell wrapper write error को अनदेखा करती है, तो वह मूल task file के साथ आगे बढ़ सकती है। Setting, file का owner और directory, तथा विफलता पर wrapper रुकती है या नहीं—इनकी पुष्टि करें। Path केवल तभी file-disclosure का उम्मीदवार है जब प्रभावी sudo rule wrapper को privileged user के रूप में चलाने देता हो, caller task input और readable backup destination नियंत्रित करता हो, और backup utility वास्तव में protected sources शामिल करती हो। Enumeration के दौरान backup चलाए बिना इन शर्तों की जाँच करें।

### Privileged packet tools पर argument wildcards

`tcpdump` के sudo rule में **argument pattern** का `*`, whitespace और slashes से match कर सकता है, इसलिए pathname जैसी restriction भी अतिरिक्त option text की अनुमति दे सकती है। यह command के executable path में wildcard से अलग है; पूरा RunAs rule और बाद के denials देखें। यदि options inject किए जा सकते हैं, तो अनुमत invocation और installed [`tcpdump` option semantics](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) तय करते हैं कि `-F`, `-V`, `-r`, `-w` या `-Z` उपयोगी read/write primitive देते हैं या नहीं। `-V` capture filenames की list पढ़ता है, मनमानी files का सामान्य dump नहीं। Sudo command की अनुमति दे, तब भी AppArmor या दूसरी MAC policy file access रोक सकती है; disk पर profile file होना यह साबित नहीं करता कि वह loaded या enforcing है। निष्कर्ष निकालने से पहले authorization और policy की निष्क्रिय समीक्षा करें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) wildcard का अंतर बताता है।

केवल `tcpdump` executable सूचीबद्ध करने वाला root-capable sudo rule, जिसमें argument restriction न हो, समीक्षा योग्य है। [tcpdump manual](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) के अनुसार, `-C` या `-G` saved capture को rotate करे तो `-z` rotation के बाद command चलाता है; `-Z` या compile-time default, उस command के चलने से पहले privileges छोड़ सकता है। Rule को escalation path मानने से पहले प्रभावी sudo rule, installed build, privilege-drop behavior और rotation हो सकती है या नहीं—इनकी पुष्टि करें। Highlight किया गया rule उम्मीदवार है, root command execution का प्रमाण नहीं।

### Sudo से चलने वाली Nmap wrappers

जब sudo-अनुमत `nmap` path shell wrapper हो, तो सटीक अनुमत path और उसके द्वारा आगे भेजे जाने वाले हर option की समीक्षा करें। परिचित `--script` spelling को रोकने से NSE code loading ज़रूरी नहीं कि रुके: Nmap का [`--datadir`](https://nmap.org/book/man-misc-options.html) data files चुनता है और scripting सक्षम होने पर NSE चुनी data directory से [`nse_main.lua` लोड करता है](https://nmap.org/book/nse-implementation.html)। कुछ installed builds वैकल्पिक long-option spellings भी स्वीकार करते हैं, इसलिए restrictions की तुलना उस binary के वास्तविक parser से करें। [`--excludefile`](https://nmap.org/book/man-target-specification.html) file-read का अलग surface है; parser errors text उजागर कर सकते हैं। Enumeration के दौरान scans चलाए बिना प्रभावी sudo rule, wrapper logic, Nmap version, directory पर नियंत्रण और MAC policy जाँचें।

### Sudo से चलने वाले Mercurial pull hooks

`sudo hg pull /fixed/source` में fixed source होने पर भी **receiving** repository current working directory से चुनी जाती है, जब तक command उसे `-R` से निश्चित न करे। Caller-नियंत्रित receiving repo `.hg/hgrc` में hooks परिभाषित कर सकती है और hook sudo RunAs user के रूप में चल सकता है। [Mercurial untrusted user या group के स्वामित्व वाली repository configuration को अनदेखा करता है](https://mercurial-scm.org/help/topics/config), इसलिए इसे code execution मानने से पहले RunAs account के trusted users/groups और सटीक working directory देखें। Passive review के लिए policy और config पढ़ना पर्याप्त है; enumeration हेतु pull न करें और hook न चलाएँ।

### Sudo से चलने वाले Git pull hooks

Root-capable `sudo git pull` के सटीक grant के लिए, working directory से चुनी गई **receiving** repository भी जाँचें। Caller-owned repository में executable `post-merge` hook हो सकता है, जो pull से सफल merge होने पर Git process की identity के साथ चलता है; [Git इस hook का दस्तावेज़ देता है](https://git-scm.com/docs/githooks) और [pull का merge-versus-rebase behavior](https://git-scm.com/docs/git-pull) भी बताता है। प्रभावी sudo rule और CWD, सक्रिय hook path और उसकी permissions, तथा नए commits के साथ merge संभव है या नहीं—इनकी पुष्टि करें। Failed, no-op या केवल rebase वाला pull इस hook path को साबित नहीं करता। Privileged pull चलाए बिना policy और repository metadata देखें।

### Sudo से चलने वाली rsync archive copies

`sudo rsync -a ... /writable/source/* /fixed/destination/` के लिए, **sudoers argument pattern** में `*` whitespace से match कर सकता है और source तथा destination के बीच अतिरिक्त option की अनुमति दे सकता है। यह filenames के shell expansion से अलग है। यदि caller source में files रख सकता है और destination privileged rsync process के लिए writable है, तो [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privileged ownership माँग सकता है, जबकि archive mode permission bits बनाए रखता है—जिससे संभवतः owned SetUID file बन सकती है। सटीक [sudoers wildcard semantics](https://man7.org/linux/man-pages/man5/sudoers.5.html), rsync version, बाद के denials, filesystem `nosuid` और MAC policy जाँचें। Matching rule समीक्षा का उम्मीदवार है, सफल privilege escalation का प्रमाण नहीं।

### Sudo से चलने वाला packet-filter rule export

`iptables` और `iptables-save` (या संबंधित `ip6tables` जोड़ी), दोनों के लिए unrestricted root-capable grant की file-write समीक्षा करें। `comment` match caller द्वारा चुना गया rule text स्वीकार करता है, जबकि `iptables-save -f` serialized ruleset चुने हुए pathname पर लिखता है।<sup>[[20]](#references)[[21]](#references)</sup> उपयोगी payload इस पर निर्भर करता है कि installed backend comments को कैसे serialize करता है और destination file export में अन्य lines स्वीकार करती है या नहीं; केवल `iptables-save` arbitrary चुना हुआ content नहीं देता। सटीक sudo RunAs identity, arguments और exclusions, उपलब्ध match extension, backend और destination permissions जाँचें। Enumeration के दौरान firewall rules बदले या file लिखे बिना grant देखें।

### Privileged Below logging directory

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ने 0.9.0 से पहले के Below releases को प्रभावित किया, जो world-writable `/var/log/below` directory बनाते थे। यदि service या अनुमत sudo command प्रभावित build को root के रूप में चलाती है, तो non-sticky log directory में लिख और traverse कर सकने वाला user privileged process द्वारा खोले जाने से पहले log entry को symlink से बदल सकता है। Installed package का patch status, सटीक privileged execution path, प्रभावी directory access, sticky bit और ACLs, तथा `/var/log/below/error_root.log` का metadata देखें। केवल world-writable path या sudo rule पूरी chain साबित नहीं करता। Sticky directory या vendor backport से आकलन बदलता है। Passive enumeration में केवल metadata देखें; link बनाने या privileged program चलाने की जरूरत नहीं है।

### Writable inputs से privileged support-bundle collection

`sudo` से चलने की अनुमति वाली support-profile script, fixed log paths को root के रूप में पढ़कर उनकी contents profile archive में copy कर सकती है। File reads के लिए वास्तविक script देखें, फिर जाँचें कि caller source path या किसी parent directory entry को symlink से बदल सकता है या नहीं। यदि privileged read उस link को follow करती है और परिणामी archive caller पढ़ सकता है, तो protected file उजागर हो सकती है। Sudo grant, writable source path, privileged read और readable output—चारों मौजूद होने चाहिए; केवल writable log या profile filename पर्याप्त नहीं है। Enumeration के दौरान files बदले या profile बनाए बिना प्रभावी permissions और link metadata देखें। [Nagios XI support guidance](https://support.nagios.com/forum/viewtopic.php?t=62758) इसकी root-run profile script और output archive का दस्तावेज़ देता है, जो दिखाता है कि ऐसे bundles के inputs और output को सीमित रखना क्यों ज़रूरी है।

### Root के रूप में चलने वाली Python archive restore scripts

Python restore script के लिए बहुत सीमित sudo rule होने पर भी उसके archive input की समीक्षा करें। यदि caller archive चुन या बदल सकता है और script उसे root के रूप में `tarfile.extractall(filter="data")` से extract करती है, तो filter पर भरोसा करने से पहले interpreter के security updates जाँचें। CPython ने symlink और hard-link filter bypasses के कई मामलों को ठीक किया, जिनमें CVE-2025-4517 भी शामिल है; यह सुधार 3.9.23, 3.10.18, 3.11.13, 3.12.11 और 3.13.4 में आया। Distribution backports पुराने version को भी ठीक कर सकते हैं, इसलिए दिखाया गया interpreter version अकेले जोखिम साबित नहीं करता।<sup>[[16]](#references)[[17]](#references)</sup>

Passive review में सटीक sudo command और script पढ़ें, पता करें कि कौन-सा argument archive चुनता है और जाँचें कि current user archive या उसकी containing directory लिख सकता है या नहीं। Installed vendor patch और extraction destination की अलग से पुष्टि करें; `filter="data"` हर untrusted archive को सुरक्षित नहीं बनाता।<sup>[[16]](#references)[[17]](#references)</sup>

### Sudo से चलने वाले machine-learning model loaders

ऐसे sudo rule की समीक्षा करें जो caller-चुनी `.pt`, `.pth` या `.ckpt` file की अनुमति देता हो, जब privileged script वह file [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` या किसी अन्य pickle-based loader को देती हो। प्रभावी RunAs rule, caller चुने model को बना या बदल सकता है या नहीं, और किसी shell wrapper से Python helper तक वास्तविक argument flow जाँचें। `.pth` extension का नाम असंबंधित Python site configuration files के लिए भी उपयोग होता है, इसलिए extension अकेले model loading का प्रमाण नहीं है। Archive scan या static pickle scan यह साबित नहीं करता कि बाद में load करना सुरक्षित है; loader का [version-dependent `weights_only` behavior](https://docs.pytorch.org/docs/stable/notes/serialization.html) और किसी भी allowlisting की समीक्षा करें। [ML pickle और Fickling notes](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md) देखें। Passive enumeration में model कभी load या unpack न करें।

### Stored input का sudo से चलने वाला expression parsing

Sudo के ज़रिए root के रूप में चलने वाली fixed Python script, फिर भी वह text evaluate कर सकती है जिसे कम-privileged user application database में store कर सकता है। TensorFlow में `preprocess_input_exprs_arg_string(value, safe=False)` call `eval` path चुनती है; [TensorFlow की advisory](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) unsafe parser और उसके command-line caller के fix का वर्णन करती है। Application द्वारा स्पष्ट रूप से `safe=False` call की अलग समीक्षा करें, भले वह command-line caller patched हो। प्रभावी sudo rule, सटीक input row कौन बदल सकता है, filtering या scoring से वह row call तक पहुँचती है या नहीं, और installed function का व्यवहार जाँचें। TensorFlow version, sudo grant या hardcoded model file अकेले chain साबित नहीं करते। Passive तरीके से script और data flow देखें; Enumeration के दौरान privileged helper न चलाएँ और test expressions न भेजें।

### Sudo-अनुमत needrestart configuration

`needrestart -c` caller-चुनी Perl configuration file लोड करके उसकी contents evaluate करता है। यदि `sudo -l` root के रूप में `needrestart` चलाने देता है और arguments `-c` की अनुमति देते हैं, तथा caller writable location में readable configuration file चुन सकता है, तो यह permission root code execution तक पहुँच सकती है। सटीक sudo run-as और argument rule जाँचें; केवल fixed argument list की अनुमति देने वाला rule यह रास्ता रोक सकता है। यह needrestart की interpreter-scanning vulnerabilities से अलग है: package update करना या `interpscan` निष्क्रिय करना, unrestricted root `-c` grant को सुरक्षित नहीं बनाता।<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### दूसरे account के रूप में चलने वाले sudo Python imports

Fixed Python entry point, caller द्वारा संपादित या बदले जा सकने वाले module को import कर सकता है—यहाँ तक कि जब sudo script को **non-root** service user के रूप में चलाता हो। Literal `from utils import status` के लिए local `utils/__init__.py` और `utils/status.py`, दोनों की समीक्षा करें और package directory permissions भी जाँचें। Writable file को execution path मानने से पहले script का import path, सटीक अनुमत sudo arguments और संबंधित action उस import तक पहुँचता है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान files और permissions देखें; script import या run न करें।<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` का सटीक sudo rule केवल readable script माँगता है; file को executable होना या shebang रखना आवश्यक नहीं है। **Missing** local modules भी जाँचें: यदि script ऐसे module को import करती है जिसका filename caller-writable script directory में बनाया जा सकता है, तो Python उस file को RunAs identity के तहत लोड कर सकता है। प्रभावी sudo rule, interpreter का वास्तविक [module search path](https://docs.python.org/3/library/sys_path_init.html), module built-in या frozen है या नहीं, और import तक पहुँचा जाता है या नहीं—इनकी पुष्टि करें। Script के लिए सीधा sudo rule, execute bit और shebang की अलग आवश्यकताएँ रखता है। अलग wrapper, जो `sudo -u account` के बाद caller-supplied tokens जोड़ती है, उसके लिए भी argument-flow समीक्षा आवश्यक है: उन tokens में दूसरा `-u` तभी मायने रखता है जब चलाया गया sudo policy परिणामी identity की अनुमति देता हो। Static strings अकेले इनमें से कोई रास्ता साबित नहीं करतीं।

### Caller-controlled configuration के साथ Sudo से चलने वाला Apache

यदि sudo rule, caller-controlled `-f` configuration file के साथ privileged `apachectl`, `apache2ctl` या `httpd` invocation की अनुमति देता है, तो उस file और उसकी parent directory permissions की समीक्षा करें। Apache का [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) directive module name के बाद **module filename** लेता है; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) भी file load करता है। [`Include` और `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) configuration बढ़ा सकते हैं या errors के ज़रिए file contents उजागर कर सकते हैं। Custom wrapper इन paths की validation कर सकती है, privileges छोड़ सकती है या arguments सीमित कर सकती है; इसलिए writable config code execution का प्रमाण नहीं, केवल समीक्षा का उम्मीदवार है। निष्कर्ष निकालने से पहले path canonicalization, symlinks और directive parsing जाँचें।

### Caller-controlled configuration के साथ Sudo से चलने वाला nginx

Unrestricted root-capable `nginx` rule, [`-c` से दूसरी configuration चुनने](https://nginx.org/en/docs/switches.html) की अनुमति दे सकता है। सटीक sudo arguments और exclusions, caller configuration दे सकता है या नहीं, और परिणामी master या workers protected paths तक पहुँच रखते हैं या नहीं—इनकी समीक्षा करें। चुना हुआ `root` और `autoindex`, नए listener से files उजागर कर सकते हैं; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) privileged file-write path दे सकता है, लेकिन DAV module default रूप से build नहीं होता। इसका मौजूद होना, listener तक पहुँच, file permissions और temporary-file behavior जाँचना आवश्यक है। [`error_log` directive](https://nginx.org/en/docs/ngx_core_module.html#error_log) भी चुनी हुई file पर लिख सकती है; `/etc/ld.so.preload` जैसी संवेदनशील configuration file में logs लिखना तभी escalation path बनता है जब प्रभावी privileged writer और नियंत्रित log record मौजूद हों। `sudo -l` में executable highlight जाँच का संकेत है, इनमें से किसी रास्ते के काम करने का प्रमाण नहीं। Passive enumeration में nginx शुरू या reconfigure न करें।

### Privileged Bash prompts में pattern comparison

यदि sudo-अनुमत Bash script caller से value पढ़ती है और उसे `[[ "$expected" == $entered ]]` से जाँचती है, तो Bash unquoted right-hand operand को pattern मानता है। इसलिए wildcard, expected value जाने बिना comparison को पूरा कर सकता है। Operand को quote करने से (`[[ "$expected" == "$entered" ]]`) literal string comparison होता है। सटीक sudo rule, prompt तक पहुँचा जा सकता है या नहीं और comparison के बाद script क्या करती है—इनकी समीक्षा करें; केवल syntax से exploitable path साबित नहीं होता। Enumeration के दौरान expected value print न करें। [Bash conditional constructs reference](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html) देखें।

### File download और execution करने वाले Sudo-run helpers

Caller-चुना URL स्वीकार करने वाली, response को disk पर लिखने वाली और बाद में उस file को interpreter या shell से चलाने वाली custom helper के unrestricted root-capable sudo grant की dataflow समीक्षा करें। [Sudoers के अनुसार, command entry में arguments सूचीबद्ध न हों तो मनमाने arguments अनुमत होते हैं](https://man7.org/linux/man-pages/man5/sudoers.5.html); fixed executable path यह सीमित नहीं करता कि arguments क्या चुन सकते हैं। Installed helper में वास्तविक URL validation, output path, success branch और उसके बाद होने वाले execution की पुष्टि करें। Matching libcurl import या printable string अकेले इस chain को साबित नहीं करती।

Helper **caller-controlled working directory में relative path** का उपयोग करे, तो write और execution के बीच fixed output basename भी बदली जा सकती है। Root-owned file का नाम बदलना या बदल देना केवल file mode से नहीं, directory write/search access और sticky-bit restrictions से तय होता है; [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) देखें। जाँचें कि helper बाद में path को फिर खोलती है या पहले से खुले descriptor का उपयोग करती है, और लिखने से पहले trusted directory में जाती है या नहीं। Sudo policy, helper और directory metadata को निष्क्रिय रूप से देखें; enumeration के दौरान privileged download न चलाएँ और race न करें।

Root-sudo download helper, `curl <caller input> -o <fixed output>` जैसी Bash command string बनाकर **argument** injection भी उजागर कर सकती है। Whitespace अस्वीकार करने वाला filter भी [Bash brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) रोकने के लिए पर्याप्त नहीं: unquoted, comma-separated elements अलग-अलग curl arguments बन सकते हैं। यदि input, fixed `-o` से पहले curl तक पहुँचता है, तो caller का दिया output option helper की identity के तहत पहले URL का destination चुन सकता है; [curl output options को URLs के साथ क्रम से जोड़ता है](https://curl.se/docs/manpage.html#-o)। सटीक shell, quoting, input validation, प्रभावी sudo rule, curl argument order और समर्थित URL schemes, तथा caller fetch किए गए bytes नियंत्रित करता है या परिणाम पढ़ सकता है—इनकी पुष्टि करें। PyInstaller-packaged executable में Python application logic हो सकती है, लेकिन उसका packaging marker या `curl` string अकेले इस data flow को साबित नहीं करता। अनुमति होने पर सीमित offline copy की समीक्षा करें; नियमित enumeration में helper न चलाएँ और attacker-चुना data fetch न करें।

Root-sudo shell script जो [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) चलाती है, केवल unused name चुनती है; यह file **बनाती नहीं**। यदि script बाद में वह नाम ऐसी directory में बनाती है जिसे कोई अन्य user प्रभावित कर सकता है, फिर उसे दोबारा खोलकर उसकी contents root के `authorized_keys` जैसे protected destination में जोड़ती है, तो temporary-file race की समीक्षा करें। सटीक sudo rule, directory और file ownership, creation तथा reopen sequence, kernel protections और privileged write वास्तव में attacker-controlled bytes उपयोग करती है या नहीं—इनकी पुष्टि करें। `mktemp -u` string या writable `/tmp` अकेले race साबित नहीं करते। Enumeration के दौरान script और path metadata देखें; उसे चलाएँ नहीं और temporary file पर race न करें।

## रक्षात्मक टिप्पणियाँ

- sudo से interpreters या interactive editors चलाने की अनुमति न दें।<sup>[[1]](#references)</sup>
- ऐसे fixed, root-owned wrappers को प्राथमिकता दें जो एक सीमित administrative action करते हों।<sup>[[1]](#references)[[2]](#references)</sup>
- Interpreter आवश्यक हो, तो सटीक script path सीमित करें और user-controlled arguments, writable imports, `PYTHONPATH` तथा असुरक्षित environment preservation रोकें।<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- File editing आवश्यक हो, तो सटीक file path सीमित करें और patched sudo versions तथा कड़ी environment handling के साथ `sudoedit` पर विचार करें।<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`, `env_keep`, writable working directories, writable module/import paths, `NOEXEC`, `use_pty` और logging की समीक्षा करें, लेकिन इन्हें पूर्ण sandbox न मानें।<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
