## Interpréteurs autorisés par sudo

Si `sudo -l` permet à un utilisateur d'exécuter un interpréteur en tant que root, considérez cela comme une exécution directe de code. Les interpréteurs sont conçus pour exécuter du code arbitraire : une règle qui autorise les binaires `python3`, `perl`, `ruby`, `lua`, `node` ou similaires équivaut généralement à l'exécution de commandes en tant que root, sauf si les arguments sont strictement limités et validés.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Procédure courante : commencez par lister les privilèges de l'utilisateur, puis exécutez une instruction Python avec l'option `-c` de l'interpréteur.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

D’autres exemples d’interpréteurs sont présentés ci-dessous ; les interpréteurs répertoriés documentent l’exécution de code inline ou les API de processus enfants.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Le chemin exact compte. Si la règle sudo autorise `/usr/bin/python3`, utilisez ce chemin exact lors de la validation.<sup>[[2]](#references)</sup>

Un glob d’exécutable sudo tel que `/usr/bin/python*` peut aussi autoriser Python 2 pour un script écrit pour Python 3. Si le script atteint `input()` avec du texte contrôlé par l’appelant, [Python 2 évalue ce texte comme une expression](https://docs.python.org/2/library/functions.html#input) ; l’invocation explicite de l’interpréteur remplace le shebang du script. Vérifiez les binaires correspondants installés, l’identité RunAs effective et la politique d’arguments, les refus et la possibilité d’atteindre la saisie avant de considérer cela comme un chemin d’exécution.

Un chemin de script fixe dans une règle sudo permettant d’obtenir les privilèges root ne limite pas ce que le script exécute. Pour un wrapper Bash lisible, vérifiez si sa première commande exécutable utilise un paramètre positionnel non protégé par des guillemets, tel que `$1`, comme **mot de commande**, alors que sudo autorise l’appelant à choisir les arguments. Confirmez l’identité RunAs effective, la politique de mot de passe et d’arguments, les refus ultérieurs et la branche réellement exécutée par le script ; `NOEXEC`, une liste fixe d’arguments sûrs ou un wrapper qui valide sa commande peuvent changer le résultat. Examinez statiquement le court script pendant l’énumération au lieu de l’invoquer avec une commande de test.

Une règle sudo sans restriction permettant d’utiliser `dotnet` avec les privilèges root mérite aussi une vérification de l’interpréteur. Si un SDK .NET est installé, [`dotnet fsi` exécute du code F# en mode interactif ou à partir d’un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), et [`dotnet run` exécute un projet à partir du code source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirmez d’abord l’identité RunAs effective et la politique exacte des arguments : une règle limitée à une sous-commande sûre particulière ou à une application de confiance constitue une autorisation différente, et une installation contenant uniquement le runtime peut ne pas disposer des commandes du SDK. Le nom de l’exécutable est un indice à examiner, pas une preuve d’exécution de code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` autorisé par sudo : écriture arbitraire de fichiers avec privilèges élevés

GNU `tee` copie l’entrée standard vers chaque chemin fourni comme opérande de fichier. Par conséquent, une règle sudo qui autorise l’exécution de `/usr/bin/tee` en tant que root avec des arguments contrôlés par l’appelant accorde la possibilité de créer ou d’écraser arbitrairement des fichiers en tant que root. Ajouter `-a` transforme cette possibilité en ajout à la fin du fichier. Un tag `PASSWD:` concerne l’authentification sudo ; à lui seul, il ne limite ni la destination ni les octets lus depuis l’entrée standard.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Inspectez d’abord la règle exacte. Sur un système de test autorisé, ne validez cette possibilité qu’avec une destination temporaire dont la création est sans risque. Le dernier `>/dev/null` supprime uniquement la copie de `tee` vers la sortie standard.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Placer `sudo` avant le producteur n'élève pas les privilèges d'une redirection shell ultérieure, car c'est le shell appelant qui ouvre la destination. Le processus privilégié doit être celui qui écrit, comme dans le pipeline ci-dessus.<sup>[[1]](#references)[[15]](#references)</sup>

Après avoir confirmé l'écriture, choisissez une cible appropriée d'exécution de code en tant que root parmi [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Une chaîne observée utilisait `tee` exécuté en tant que root pour créer un fichier éphémère sous `/etc/cron.d/`, lancer une backdoor via un script contrôlé par l'utilisateur, puis supprimer le fichier cron après l'exécution. La suppression du fichier cron l'a empêché de devenir un mécanisme de persistance à long terme, même si les journaux système ont conservé des traces de l'activité.<sup>[[27]](#references)</sup>

## Éditeurs autorisés via Sudo

Si `sudo -l` permet à un utilisateur d'exécuter un éditeur interactif en tant que root, considérez cela comme une surface d'exécution de commandes, et non comme une autorisation inoffensive de modifier des fichiers. Les éditeurs peuvent souvent exécuter des commandes shell, lire des fichiers arbitraires, écrire des fichiers arbitraires ou invoquer des utilitaires externes depuis l'éditeur.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Déroulement courant de l'analyse : répertoriez les privilèges de l'utilisateur, puis lancez avec `sudo` chaque éditeur ou pager autorisé.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Exécution de commandes avec Nano

Lorsque `nano` est autorisé via sudo, il peut être possible d’exécuter des commandes depuis l’interface de l’éditeur.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Puis fournissez une commande telle que `id` ou `/bin/sh` à l’invite de commande de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactif ne dispose pas de flux de terminal utilisables, cette forme de redirection redirige sa sortie standard et ses erreurs vers le descripteur 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La séquence exacte de touches peut varier selon la version de nano et les options de compilation, mais le problème de sécurité reste le même : l’éditeur s’exécute en tant que root et peut lancer des commandes externes.<sup>[[1]](#references)[[12]](#references)</sup>

### Autres échappatoires courantes des éditeurs

Les éditeurs de type Vim permettent couramment d’exécuter des commandes à l’aide de `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Les paginateurs comme `less` peuvent également permettre l’exécution de commandes shell.<sup>[[14]](#references)</sup>

Une règle sudo autorisant `apport-cli` en tant que root mérite le même examen du paginateur. Les versions concernées d’Apport pouvaient ouvrir un rapport de plantage dans `less` avec une taille de terminal contrôlable par un attaquant ; le paginateur pouvait alors fournir un shell root si les conditions particulières liées à sudo et au paginateur étaient réunies. Vérifiez la règle sudo effective, la configuration du paginateur et le correctif du paquet de la distribution avant de considérer que la version seule est vulnérable. Lors d’une énumération passive, consultez les métadonnées du paquet et de la politique sans provoquer de plantage ni ouvrir le rapport privilégié. [La fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2023-1326) indique les versions de paquets corrigées propres à chaque version, y compris celles contenant des correctifs rétroportés.

```text
!/bin/sh
```

## Autres risques liés aux règles sudo et doas

Commencez par `sudo -l`, `sudo -V` et toute politique `doas` applicable. Examinez ensemble les commandes autorisées, l’utilisateur d’exécution, les arguments, l’environnement et les valeurs par défaut. L’autorisation d’exécuter une commande en tant que compte de service non-root peut tout de même exposer les fichiers de ce compte ou ouvrir une voie vers root.

Un script Python autorisé par sudo et dont le chemin est fixe peut tout de même exécuter une commande shell sous son identité RunAs si une entrée interactive contrôlée par l’appelant est concaténée dans [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Une denylist de ponctuation shell ne suffit pas à garantir la sécurité : [le shell reconnaît aussi la substitution de commande `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Vérifiez que les arguments autorisés atteignent la branche de saisie, que l’entrée arrive à la commande shell sans validation sûre et que la politique sudo effective autorise l’utilisateur RunAs visé. Le chemin du script ou un appel à `os.system()` ne sont que des pistes à examiner ; inspectez le code source sans exécuter le script privilégié.

Une autorisation sudo effective d’exécuter `chattr` en tant que root peut supprimer l’attribut de fichier immuable (`i`), mais cela ne donne pas, à lui seul, le droit d’écrire dans le fichier ni une nouvelle identité. [Le manuel de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indique que cet attribut bloque les modifications et que seul root ou un processus disposant de `CAP_LINUX_IMMUTABLE` peut le changer. Vérifiez la politique exacte relative aux arguments sudo et la prise en charge du système de fichiers, puis vérifiez séparément que l’appelant peut écrire dans le fichier une fois l’attribut supprimé et qu’un consommateur ayant une identité supérieure l’utilise. Le remplacement d’un shell de connexion, par exemple, nécessite aussi des identifiants acceptés par le compte ciblé et une véritable connexion via ce shell. Examinez la politique, les attributs de fichier et les permissions sans les modifier pendant l’énumération.

Si sudo demande à la fois un mot de passe et un code à usage unique, ne confondez pas ces prérequis avec l’autorisation de lancer une commande. Un fichier `.google_authenticator` lisible contient un secret sensible, tandis qu’un ancien hash de mot de passe d’application ou de base de données n’est qu’un candidat pour le mot de passe actuel du compte ; aucun des deux ne prouve que l’autre facteur est accepté par la configuration PAM effective. Une fois autorisé, examinez précisément l’utilisateur RunAs et les arguments : une autorisation root sans restriction pour la commande RubyGems `gem` peut exposer sa commande d’éditeur ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mais une autorisation restreinte ou une authentification échouée ne le permet pas. L’énumération passive doit indiquer les chemins et la politique sans afficher le secret, récupérer un mot de passe, générer un code ou exécuter la commande privilégiée.

Une autorisation sudo sans restriction, pouvant s’exécuter en tant que root, pour `knife` de Chef mérite un examen au niveau de l’interpréteur : [Chef indique que `knife exec -E` évalue localement une chaîne Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Vérifiez que la règle sudo effective autorise le sous-programme `exec` et l’argument `-E` fourni par l’appelant, l’identité RunAs visée, ainsi que les éventuels refus de commande ou arguments fixes correspondants. Le binaire installé ou une règle limitée à d’autres sous-programmes ne sont que des pistes. L’énumération passive doit signaler la règle sans exécuter `knife`.

Une autorisation sudo exacte, pouvant s’exécuter en tant que root, pour un `msfconsole` interactif est tout aussi sensible : [GTFOBins documente sa console `irb`](https://gtfobins.org/gtfobins/msfconsole/), qui peut hériter de l’identité sudo. Vérifiez l’utilisateur RunAs effectif, la liste d’arguments autorisés, les refus de commande, `NOEXEC` ou toute autre restriction, le comportement de la console installée et la possibilité pour l’appelant de fournir une entrée interactive. La simple mise en évidence d’un chemin n’est qu’une piste ; l’énumération passive ne doit pas lancer la console.

Sur FreeBSD, même une règle sudo limitée à `pkg update` et `pkg install *` en tant que root mérite un examen de la confiance accordée aux dépôts. Vérifiez si l’appelant peut écrire dans `/etc/hosts` et si la configuration effective des dépôts activés utilise un nom d’hôte HTTP avec `signature_type: none`. [Le manuel de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) précise que `none` désactive les vérifications de signature ; `pkg+http` seul ne permet pas de conclure cela. Un paquet peut contenir des scripts d’installation ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), et un appelant qui contrôle réellement le point de terminaison du dépôt et peut choisir un paquet peut franchir la frontière root. Vérifiez les substitutions de dépôt, la résolution SRV/miroir, les arguments sudo effectifs, le choix du paquet et l’exécution des scripts avant de conclure. Examinez la politique et les petits fichiers de configuration locaux sans rediriger de noms ni exécuter `pkg` pendant l’énumération.

Une autorisation sudo pouvant s’exécuter en tant que root pour `apt-get update` et `apt-get upgrade` nécessite aussi un examen de la confiance accordée aux dépôts si sudo préserve un `http_proxy` contrôlé par l’appelant. Vérifiez si la configuration APT effective utilise réellement cette variable et quelles requêtes vers les dépôts activés elle peut affecter ; un proxy ne peut pas, à lui seul, remplacer des paquets provenant d’une archive authentifiée par une clé de signature de confiance. [Le manuel du transport HTTP d’APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) décrit la priorité des proxys, et [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) décrit les vérifications de signature, les dérogations autorisant les dépôts non sécurisés et la confirmation requise pour les paquets non authentifiés. Vérifiez l’utilisateur RunAs et les arguments exacts de sudo, la politique d’authentification des dépôts, toute confirmation interactive requise et si la mise à niveau sélectionnée exécute des scripts de paquet en tant que root. Examinez passivement la politique et la configuration locale ; ne redirigez pas le trafic des paquets et ne lancez pas de mise à niveau pendant l’énumération.

Une règle sudo pouvant s’exécuter en tant que root pour `snap install` peut constituer une frontière entre paquet et code si ses arguments permettent à l’appelant de choisir un snap local et un mode d’installation permissif. [Snap indique](https://snapcraft.io/docs/explanation/snap-development/install-modes/) que `--dangerous` ignore les vérifications d’assertion pour les snaps locaux et que `--devmode` assouplit le confinement ; [un hook d’installation peut s’exécuter lors de l’installation initiale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Avant de conclure à un accès aux fichiers protégés de l’hôte, vérifiez la politique sudo exacte concernant les arguments et RunAs, qui contrôle le fichier snap, si les modes sont acceptés par le snapd installé, ainsi que l’identité effective et le confinement du hook. La présence d’un binaire `snap` ou d’une règle ressemblant à un joker ne prouve pas cette chaîne. L’énumération passive ne doit ni installer de paquet ni exécuter son hook.

Pour une autorisation sudo exacte visant un binaire personnalisé de lecture d’identifiants exécuté en tant que compte **non-root**, commencez par inspecter le binaire autorisé et ses permissions sans l’exécuter. Un contrôle de mot de passe intégré peut n’être visible qu’en caractères larges ; [GNU `strings` documente l’extraction little-endian sur 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Une chaîne visible ne prouve pas qu’il s’agit du mot de passe accepté ni que la branche de réussite expose un identifiant actuel. Vérifiez séparément le comportement du binaire, l’accès du compte ciblé aux données protégées, la validité des identifiants et toute transition ultérieure de compte ou de groupe. Si ce compte appartient à `docker`, vérifiez l’accès au socket et si le daemon est rootful ou rootless avant d’en déduire un accès root à l’hôte ; [Docker documente les implications de son groupe au niveau root](https://docs.docker.com/engine/install/linux-postinstall/). L’énumération courante doit signaler la règle sudo et l’appartenance au groupe sans exécuter le binaire ni afficher ses chaînes.

Une règle sudo avec joker pour les scripts de maintenance d’une application mérite un examen qui dépasse le chemin du script. Vérifiez si le script autorisé accepte des arguments sans restriction ou lit des paramètres qu’un compte applicatif moins privilégié peut modifier, puis suivez ces valeurs jusqu’aux commandes shell ou à l’environnement d’un sous-processus. Par exemple, le [`zmupdate.pl` de ZoneMinder construit une commande `mysqldump` et l’exécute via `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), tandis que [`zmdc.pl` copie le paramètre `ZM_LD_PRELOAD` dans `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) avant de démarrer des daemons. Une règle sudo autorisant l’un ou l’autre script en tant que root peut franchir une frontière de confiance si l’entrée correspondante est contrôlable et atteint ce code dans la version installée. Inspectez la règle sudo effective, les droits d’accès à la configuration de l’application et le code source du script ; le joker ou le paramètre seul n’est qu’une piste, pas une preuve d’exécution.

- `SETENV`, `env_keep`, `secure_path` et `LD_PRELOAD` peuvent transformer une commande autrement restreinte en détournement d’import, de bibliothèque ou de PATH. Consultez le [guide des variables d’environnement](../linux-basics/linux-environment-variables.md) et [l’abus de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Une autorisation `SETENV` exacte, pouvant s’exécuter en tant que root, pour un wrapper shell mérite aussi un examen limité à un seul saut si le wrapper lance un script Python fixe avec un import littéral. `secure_path` limite la recherche de commandes du shell, pas la [recherche de modules Python via `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) ; [`-E` et `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) indiquent à Python d’ignorer cette variable d’environnement. Avant de considérer cela comme une exécution de code, vérifiez les tags et refus sudo effectifs, la branche du wrapper, les options de l’interpréteur, la résolution de l’import et l’existence d’un répertoire de recherche modifiable par l’appelant. Inspectez statiquement les scripts courts ; n’exécutez pas le wrapper privilégié.

Une autorisation sudo exacte pour `neofetch ""`, pouvant s’exécuter en tant que root, peut tout de même charger une configuration shell si les valeurs par défaut sudo applicables préservent le `XDG_CONFIG_HOME` contrôlé par l’appelant. [Le chargeur de configuration de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) source `neofetch/config.conf` ou `neofetch/config` sous ce répertoire ; la liste d’arguments vide n’empêche pas cette recherche. Vérifiez le chargeur installé, l’identité RunAs et la politique d’arguments effectives, les éventuels refus de commande, si sudo conserve réellement la variable choisie pour cette commande et si l’appelant contrôle un chemin de configuration lisible. La variable préservée ou Neofetch installé ne sont que des pistes. Examinez la politique et les métadonnées des fichiers sans exécuter la commande privilégiée ni afficher le contenu de la configuration ; consultez [la gestion de l’environnement par sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Une règle sudo sans restriction, pouvant s’exécuter en tant que root, pour `facter` mérite un examen distinct des custom facts. [Puppet indique](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` charge des fichiers de faits Ruby depuis un répertoire choisi. Vérifiez si la règle sudo exacte autorise cette option, si le Facter installé l’accepte et si l’appelant contrôle le répertoire. Une autorisation avec arguments fixes, un refus explicite de commande ou la désactivation des custom facts peut changer le résultat. L’énumération passive doit signaler cette possibilité sans exécuter Facter ni lire le contenu des faits.

Pour une autorisation sudo exacte d’un script pouvant s’exécuter en tant que root avec `SETENV`, examinez les noms de commande nus comme `find` et le `PATH` effectif après application de la politique sudo et de l’initialisation du script. Un fichier Bash sourcé peut aussi exécuter `enable -n [` : [Bash recherche alors dans `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) une commande externe `[` lorsque le script utilise cette commande par la suite. Vérifiez les [règles d’environnement sudoers et `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) applicables, les éventuelles entrées `NOSETENV`/`NOEXEC` ou de refus, le déroulement du script et des fichiers sourcés, ainsi que l’existence d’un répertoire de recherche exécutable contrôlé par l’appelant. Un script lisible contenant une commande nue est une piste, pas une preuve d’exécution privilégiée ; inspectez-le sans utiliser la règle sudo.
- Un script privilégié qui récupère une URL fixe avec `curl` peut tout de même accepter une réponse choisie par l’appelant si une règle sudo applicable préserve `http_proxy` et si la requête passe par ce proxy. Si le script transmet ensuite la réponse à un analyseur XML qui résout les entités externes, une réponse malveillante peut divulguer des fichiers lisibles par le processus privilégié. Vérifiez la politique sudo exacte concernant l’environnement, les exclusions `no_proxy`, l’URL demandée, la configuration de l’analyseur et la destination de sortie ; une variable proxy ou un analyseur XML ne constitue pas, à lui seul, une vulnérabilité. La [documentation de curl sur les variables d’environnement des proxys](https://everything.curl.dev/usingcurl/proxies/env.html) décrit le comportement de ces variables. N’effectuez pas de requêtes réseau et n’analysez pas de XML malveillant pendant l’énumération passive.
- Un script sudo pouvant s’exécuter en tant que root qui construit un fichier PostScript à partir de données influencées par l’appelant puis lance `ps2pdf -dNOSAFER` mérite un examen distinct du flux des entrées. Ghostscript indique que ce flag désactive SAFER jusqu’à `.setsafe`, ce qui autorise les opérations PostScript sur les fichiers selon les permissions du processus dans le système d’exploitation. Une requête SQL construite à partir d’un argument fourni par l’appelant peut transmettre des lignes contrôlées par un attaquant au modèle PostScript, mais une chaîne de requête ou un appel à `ps2pdf` ne prouve pas, à lui seul, que les données atteignent la syntaxe PostScript exécutable. Vérifiez la règle sudo effective, le chemin exact des données vers le modèle, les éventuels échappements, le comportement de la version installée de Ghostscript et la réactivation éventuelle de SAFER avant l’interprétation du document. Ne lancez pas la conversion privilégiée pendant l’énumération passive. Consultez [la documentation de Ghostscript sur `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Pour une règle sudo qui exécute un script shell, comparez les variables préservées au script lui-même. Une construction telle que `if $CHECK_CONTENT; then` exécute la valeur développée comme une commande ; préserver `CHECK_CONTENT` peut donc permettre l’exécution d’une commande même si le chemin et les arguments du script sont fixes. Vérifiez, pour la règle concernée, si la branche peut être atteinte et si l’environnement est réellement conservé.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script Python autorisé par sudo peut importer du code depuis un répertoire modifiable ou un fichier `.pyc` mis en cache. Le [guide d’élévation de privilèges](../linux-basics/linux-privilege-escalation/README.md) décrit le cas du cache.
- Un script Python fixe autorisé par sudo à s’exécuter en tant que root peut tout de même exposer un débogueur interactif. Des appels tels que `pdb.set_trace()` ou `pdb.post_mortem()` permettent d’exécuter des instructions Python dans le contexte du processus débogué si l’appelant peut atteindre le point d’arrêt ou le gestionnaire d’exception **et contrôler l’entrée du débogueur**. Vérifiez la règle sudo exacte concernant RunAs, l’authentification et les conditions de branchement, la possibilité d’atteindre l’exception, la propriété du terminal/de l’entrée et si le débogueur s’exécute dans ce même processus privilégié. Une requête socket qui déclenche une exception ne donne pas, à elle seule, accès à un débogueur attaché à un autre terminal. [Python documente l’évaluation d’instructions par le débogueur et le mode post-mortem](https://docs.python.org/3/library/pdb.html) ; inspectez statiquement le script plutôt que de déclencher le gestionnaire privilégié pendant l’énumération.
- Un script Python fixe autorisé par sudo peut également lire un champ de profil dans une base de données ou via un socket Unix, puis l’ajouter à une chaîne qui devient ensuite la **chaîne de format** de `str.format()`. [Les champs de remplacement peuvent suivre des attributs et des clés de dictionnaire](https://docs.python.org/3/library/string.html#format-string-syntax) ; un champ contrôlé par un attaquant peut donc inspecter les objets fournis à `format()` et exposer les données auxquelles ils donnent accès si le résultat est affiché ou stocké à un endroit lisible par l’appelant. Vérifiez l’identité RunAs sudo effective, le droit d’écriture sur l’enregistrement concerné, le flux des données vers la chaîne de format, les objets fournis et la visibilité de la sortie. Cela ne permet pas automatiquement d’exécuter du code ; une chaîne de format littérale de confiance avec des *valeurs* contrôlées par un attaquant est un cas différent. Un secret divulgué ne permet de changer de compte système que si ce compte l’accepte. Examinez le script et les permissions du socket sans exécuter l’opération privilégiée.
- Un wrapper Python pouvant s’exécuter en tant que root peut transmettre une URL choisie par l’appelant à `Repo.clone_from` de GitPython. Si le wrapper active également `protocol.ext.allow=always` pour Git, un dépôt distant `ext::` peut invoquer un helper externe. Vérifiez les arguments sudo exacts, l’origine de l’URL, la version du paquet GitPython et l’existence d’un correctif du fournisseur, ainsi que l’activation explicite de protocoles non sûrs par le wrapper. GitPython a ajouté une [protection par défaut contre les protocoles non sûrs](https://github.com/gitpython-developers/GitPython/commit/2625ed9) dans la version 3.1.30 ; la version de l’exécutable `git` est un élément distinct. L’examen passif doit se limiter à la lecture de la règle et d’un extrait circonscrit du code source, sans lancer le clone.
- Une autorisation sudo entre utilisateurs pour un outil CLI de clonage de dépôts peut exposer une autre voie d’injection dans une chaîne shell. Suivez le trajet de l’argument de dépôt choisi par l’appelant jusqu’à [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js ou à un autre constructeur de commande shell, et vérifiez l’absence de séparation sûre des arguments ; `exec` de Node transmet sa chaîne de commande à un shell. Vérifiez l’utilisateur RunAs exact, les sous-commandes et arguments autorisés, le code du wrapper installé et la validation des entrées. Le nom de l’outil de dépôt ou une règle sudo sans restriction ne prouve pas à lui seul l’existence d’une injection de commande. Inspectez le wrapper sans lancer de clone privilégié pendant l’énumération.
- Un wrapper personnalisé appartenant à root peut sembler sûr parce que ses binaires et scripts ne sont pas modifiables, alors que sa décision d’exécuter une action privilégiée dépend d’un indicateur, d’une valeur d’API locale ou d’un état de service qu’un utilisateur non privilégié peut modifier. Suivez chaque condition jusqu’à son entrée et aux contrôles d’autorisation. Pendant l’énumération, examinez la configuration et les permissions sans modifier l’état opérationnel ; un appel à `systemd-run` dans le wrapper n’est pertinent que si la condition peut être influencée.
- Un client de sauvegarde autorisé via sudo en tant que root peut accepter un fichier de configuration choisi par l’appelant (par exemple `npbackup-cli -c`). Vérifiez l’utilisateur d’exécution exact et les arguments autorisés, puis si l’appelant contrôle le chemin de configuration, les chemins source de la sauvegarde et le dépôt, ou les options de lecture/restauration. Un secret de dépôt chiffré dans une configuration lisible peut tout de même être utilisable par le client, mais la règle seule ne prouve ni l’accès au dépôt ni la divulgation de fichiers root. Vérifiez l’autorisation sans lancer de sauvegarde ni en afficher le contenu.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) prend en charge `--password-command`, qui appelle un programme pour obtenir le mot de passe du dépôt. Si une règle sudo permet à un utilisateur moins privilégié d’exécuter restic en tant que root avec une commande de mot de passe choisie par l’appelant et un sous-programme qui nécessite le mot de passe, ce helper peut s’exécuter en tant que root. Examinez précisément les arguments sudo et leurs exclusions ; n’exécutez pas le helper ou une commande de sauvegarde simplement pour vérifier cette condition.
- Une autorisation privilégiée pour `restic backup` peut aussi franchir une frontière de lecture de fichiers si le modèle d’arguments sudo permet à l’appelant de choisir à la fois la source et un dépôt qu’il pourra ensuite lire et déchiffrer. [Les jokers d’arguments sudoers peuvent correspondre aux espaces et aux barres obliques](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) ; examinez donc les jokers finaux au lieu de supposer qu’un préfixe fixe de dépôt confine la source. [Restic peut sauvegarder dans des dépôts locaux ou distants](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mais un dépôt local peut contenir de nouveaux objets root-only ; vérifiez la politique sudo effective, l’accès au backend, le mot de passe du dépôt et les permissions des objets produits avant de conclure à une divulgation. Une clé SSH sauvegardée ne donne accès à un compte que si celui-ci l’accepte. Ne lancez pas de sauvegarde pour tester cela pendant l’examen passif.
- Une commande de maintenance ou de sauvegarde personnalisée sans restriction peut accepter un chemin de sortie ou proposer son propre planificateur de tâches. Pour une écriture de fichier, vérifiez la règle sudo exacte et l’utilisateur RunAs, puis si l’appelant contrôle à la fois les données et la destination. Pour une tâche planifiée, vérifiez l’identité d’exécution du planificateur, l’entrée de commande et tout contrôle supplémentaire par mot de passe ou autorisation. Le nom de la commande ou `NOPASSWD` ne prouve aucune de ces voies. Consultez [l’écriture dans des fichiers appartenant à root](../interesting-files-permissions/write-to-root.md) et [les timers cron et systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Une commande sudo fixe peut tout de même charger un fichier de configuration prévisible depuis un répertoire partagé modifiable. Vérifiez si l’appelant peut remplacer ce fichier et si ses champs source et destination contrôlent une récupération ou une copie privilégiée. Une URL de fichier local peut exposer des données lisibles uniquement par le compte RunAs sudo ; une source contrôlée par l’appelant associée à une destination protégée peut créer une voie d’écriture. Vérifiez le traitement des URL par le programme installé, les contrôles du chemin de destination, la règle sudo effective et l’accessibilité de la sortie. Un chemin de configuration modifiable dans `/tmp` est une piste, pas une preuve ; inspectez le binaire et les métadonnées des fichiers sans lancer le transfert privilégié.
- Une règle sudo pour `git apply` peut permettre au compte RunAs d’écrire dans des fichiers sélectionnés par un patch contrôlé par l’appelant. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permettait à un patch malveillant de créer un lien symbolique puis d’écrire en dehors de l’arborescence de travail, même lorsque la commande n’acceptait pas `--unsafe-paths`. Vérifiez la règle sudo effective concernant les arguments, la source du patch, l’accès au répertoire de travail pour le compte RunAs et la correction Git installée ou le correctif rétroporté du fournisseur. Une règle sans restriction autorisant `--unsafe-paths` présente un risque distinct lié à cette option explicite ; ni une version de Git ni l’autorisation d’exécuter `git apply` ne prouvent, à elles seules, qu’un fichier protégé peut être modifié. N’appliquez pas de patch non fiable pendant l’énumération passive.
- Une règle sudo pouvant s’exécuter en tant que root pour `clamscan --debug` peut franchir une frontière de lecture si un utilisateur moins privilégié peut fournir une image DMG et si l’analyseur installé est affecté par [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), qui pouvait divulguer le contenu de fichiers dans la sortie de débogage. Vérifiez les arguments et le chemin d’analyse autorisés exacts, le contrôle de l’entrée, le compte RunAs effectif, le moteur corrigé ou le correctif rétroporté, ainsi que la visibilité de la sortie pour l’appelant. Si une règle plus large autorise `--file-list`/`-f`, examinez séparément le comportement de cette liste ; une politique limitée à `--debug <scan-path>` ne l’autorise pas. Inspectez la politique et les métadonnées du paquet sans analyser un fichier créé à cet effet ni afficher de sortie protégée pendant l’énumération.
- Une règle sudo pouvant s’exécuter en tant que root qui ouvre une image disque chiffrée choisie par l’appelant, combinée à une deuxième règle qui monte le mappeur obtenu, peut importer des fichiers contrôlés par l’appelant dans l’espace de noms de montage de l’hôte. Vérifiez les deux règles effectives et leurs arguments, le contrôle de l’image et du nom du mappeur, la cible de montage réelle, ainsi que le propriétaire et le mode des fichiers obtenus. Une transition set-user-ID nécessite en plus un exécutable accessible, des options de montage qui le prennent en charge (`nosuid` le bloque) et une politique de processus ou MAC applicable ; ouvrir ou monter une image n’est qu’une piste. Une voie distincte passant par une sauvegarde existante nécessite sa véritable clé et un secret utile lisible à l’intérieur. Examinez la politique et les chemins sans ouvrir ni monter d’image pendant l’énumération passive. Consultez le [manuel de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) et [les options de montage](https://man7.org/linux/man-pages/man8/mount.8.html).
- Une règle sudo pouvant s’exécuter en tant que root pour un script shell ou Python mérite un examen du répertoire de travail si le script appelle `./helper` sans commencer par se déplacer dans un répertoire fixe. Une liste Python telle que `['./helper']` transmise à `subprocess.run` peut se comporter de la même manière en utilisant le répertoire de travail choisi par l’appelant. Celui-ci peut choisir un répertoire modifiable et y placer un exécutable portant ce nom relatif ; un chemin absolu ailleurs dans le script ne protège pas cet appel. Avant de considérer cela comme une exécution de code, vérifiez la règle effective, `runchdir` ou toute autre politique de changement de répertoire, le déroulement du script et l’accessibilité de la branche, les droits d’écriture et d’exécution du répertoire, ainsi que les restrictions de montage/`NOEXEC`. Si le script est illisible, son comportement reste inconnu jusqu’à ce que son code source soit examiné par une voie autorisée. Examinez les scripts statiquement au lieu d’exécuter le helper. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documente la politique de répertoire de travail.
- Un validateur Python fixe pouvant s’exécuter en tant que root peut tout de même évaluer un fichier de données choisi par l’appelant. [La documentation de `eval()` de Python met en garde contre les entrées non fiables](https://docs.python.org/3/library/functions.html#eval) : une vérification de suffixe, un préfixe arithmétique ou une branche de validation ne constitue pas un sandbox si l’expression restante atteint `eval`. Avant de considérer cette voie comme une exécution de code, vérifiez la règle sudo effective, si l’appelant peut choisir et contrôler le fichier précis, les conditions de branchement de l’analyseur et la construction de l’expression, ainsi que l’identité du processus privilégié. La présence de `eval` dans un script lisible est seulement une piste ; inspectez le code source et les permissions des fichiers sans lancer le validateur ni lui soumettre d’expression de test pendant l’énumération.
- Un wrapper Ruby sudo pouvant s’exécuter en tant que root et qui lit un nom de fichier YAML relatif, comme `YAML.load(File.read("dependencies.yml"))`, peut utiliser le fichier du répertoire de travail de l’appelant, sauf si le wrapper ou la politique sudo fixe ce répertoire. Vérifiez précisément les arguments autorisés, les permissions du répertoire et du fichier, ainsi que le comportement de la version installée de Psych : les anciennes implémentations de `YAML.load` pouvaient désérialiser des objets Ruby arbitraires, tandis que les versions récentes limitent les classes par défaut. Un appel statique n’est qu’une piste ; confirmez que le fichier provient réellement d’un répertoire modifiable par l’appelant et que le chargeur installé accepte les classes dangereuses. Préférez `safe_load` avec une liste d’autorisation explicite et minimale de classes pour les entrées non fiables. Consultez la [documentation Psych de Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) et la [documentation Psych de Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Une autorisation sudo exacte pour `sudo go run /absolute/file.go`, pouvant s’exécuter en tant que root, mérite un examen du répertoire de travail lorsque le code Go lit un fichier WASM relatif et peut exécuter un script shell relatif après examen de son résultat. Vérifiez l’identité RunAs effective, les arguments et refus de commande, l’existence d’un répertoire courant modifiable par l’appelant, le flux des données du WASM vers la branche et si cette branche appelle le helper. Un `runchdir` sudo fixe, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) peut modifier l’emplacement de recherche. Une simple cooccurrence dans le code n’est qu’une piste ; inspectez le code sans exécuter Go, WASM ou le helper.
- `sudoedit` et les jokers d’arguments nécessitent des vérifications précises de la version et de la règle ; la [checklist](linux-privilege-escalation-checklist.md) comprend le problème d’édition de fichier avec sudoedit. Pour une autorisation `sudoedit` entre utilisateurs portant sur un chemin avec joker, examinez les paramètres `sudoedit_follow` ou `FOLLOW` effectifs, `sudoedit_checkdir`, la cible résolue et les personnes qui peuvent remplacer chaque entrée parente. Le premier peut permettre de suivre un lien symbolique, tandis que la désactivation du second supprime les vérifications des répertoires modifiables ; aucun de ces paramètres ne suffit, à lui seul, à établir qu’un fichier appartenant à un autre utilisateur peut être modifié. Vérifiez la politique sudo installée et les arguments exacts correspondants avant de conclure. Consultez [les définitions d’options sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Dans une règle de commande sudoers, un joker d’argument peut correspondre aux espaces ainsi qu’aux caractères de chemin. Une règle pour une commande capable de lire des fichiers avec un argument tel que `/restricted/*` peut donc autoriser un argument de fichier supplémentaire après un préfixe correspondant. Examinez l’utilisateur RunAs exact, le chemin de la commande, le modèle d’argument et les refus ultérieurs ; la lecture démontrée d’un fichier n’implique pas l’exécution de commandes. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue les motifs d’arguments des motifs de chemin de commande.
- Un motif d’argument ressemblant à un chemin peut aussi correspondre à `../`. Par exemple, une règle pouvant s’exécuter en tant que root pour `node /opt/scripts/*.js` peut autoriser un fichier JavaScript contrôlé par l’appelant en dehors de `/opt/scripts` si le chemin fourni commence tout de même par `/opt/scripts/` et est résolu via des segments de répertoire parent. Il s’agit d’un joker d’**argument** ; le joker du chemin de commande de l’exécutable Node suit des règles différentes pour les barres obliques. Avant de conclure à une exécution de code, vérifiez la règle effective, les refus ultérieurs, la résolution du chemin, le contrôle du fichier cible et toute restriction sudoers par expression régulière ou digest. Consultez [les règles de jokers sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) et la [documentation de Node sur la ligne de commande](https://nodejs.org/api/cli.html).
- Les programmes d’archivage et d’autres utilitaires peuvent disposer de hooks d’exécution. Vérifiez les arguments exacts autorisés dans [GTFOBins](https://gtfobins.github.io/) au lieu de supposer que seuls les shells ou les interpréteurs exécutent des commandes.
- Une règle sans restriction pouvant s’exécuter en tant que root pour `qpdf` peut exposer un fichier privilégié via des pièces jointes PDF : qpdf 10.2 et les versions ultérieures prennent en charge `--empty` et `--add-attachment file ... --` avec un PDF de sortie. Si le processus privilégié peut lire la source sélectionnée et écrire le PDF dans un chemin accessible à l’appelant, la sortie peut contenir les octets de la source. Avant de conclure à une possible divulgation de fichiers, examinez les arguments sudo effectifs et leurs exclusions, la version de qpdf, l’accès à la source et le chemin de sortie. La lecture d’une clé SSH root ne permet de se connecter que si cette clé est valide et si l’authentification SSH de root est autorisée. Consultez [les options de pièces jointes de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La réutilisation du timestamp sudo dépend de la politique de cache, de l’utilisateur propriétaire, du terminal/de la session et des permissions. Le [guide d’élévation de privilèges](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) présente les vérifications à effectuer.
- `doas` dispose de ses propres règles et de sa propre configuration. Vérifiez les commandes autorisées et les chemins de configuration modifiables comme indiqué dans la [section doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Outils de build et de gestion de paquets exécutés par sudo

Une autorisation sudo sans restriction pour `forge` de Foundry peut être importante même si l’identité RunAs est celle d’un autre utilisateur non-root. Des options de compilation comme `--use` peuvent sélectionner un exécutable local, et `forge flatten -o` sélectionne un fichier de sortie. Avant de considérer l’autorisation comme exploitable, vérifiez la version de Forge installée, les arguments sudo exacts, l’accessibilité du projet et du compilateur, les permissions de sortie et l’environnement effectif. Un exécutable helper relatif trouvé via `PATH` est une voie qui dépend de la version et de l’environnement, et non une propriété à supposer pour toutes les compilations Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Une autorisation sans restriction pour `pacman`, pouvant s’exécuter en tant que root, permet davantage que de simples requêtes sur les paquets : `-U` accepte un paquet local, les paquets peuvent contenir des scripts d’installation et `--hookdir` permet de sélectionner un autre répertoire de hooks. Avant tout test, examinez la règle sudo effective, les restrictions d’arguments et les exclusions ; l’énumération passive n’a pas besoin d’installer un paquet ni d’exécuter un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell sudo fixe peut aussi installer une dépendance npm nommée puis démarrer une application Node. Examinez sa règle RunAs exacte, si le paquet est déjà installé, les valeurs effectives de `HOME` et de `userconfig` de npm, la configuration du projet ou les substitutions de ligne de commande, et si un utilisateur moins privilégié contrôle le registre ou le paquet renvoyé pour ce nom. [npm documente la recherche de `.npmrc` par utilisateur et par projet](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/) ; le comportement de `HOME` avec sudo dépend de la politique installée et de la distribution, donc un `.npmrc` modifiable par l’utilisateur peut être lu ou non par le processus npm privilégié. Si le paquet nouvellement installé est importé par l’application privilégiée, son code de module peut s’exécuter sous l’identité de cette application. Les scripts d’installation constituent une voie distincte, dépendante de la version et de la configuration ; [npm documente leur cycle de vie et la gestion de l’utilisateur](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un chemin `.npmrc` ou une ligne `npm install` ne sont que des pistes. Inspectez la règle, le wrapper court, les chemins de configuration et la provenance du paquet sans l’installer ni démarrer l’application pendant l’énumération passive.

Une autorisation root pour `pip` ou `pip3 download` constitue aussi une piste d’examen du build de paquet lorsque ses arguments permettent à l’appelant de choisir une distribution source non fiable, même si le motif d’URL la limite à un service local et à un suffixe `.tar.gz`. `pip download` accepte des URL d’archives et résout les métadonnées des paquets ; la préparation des métadonnées d’une distribution source peut appeler son backend de build ou du code `setup.py` historique avant que l’archive ne soit simplement enregistrée. Vérifiez l’utilisateur RunAs et la règle d’arguments sudo exacts, si l’appelant peut publier ou remplacer l’archive sélectionnée, et si cette version de pip prépare réellement ses métadonnées. Une archive fixe et de confiance ou un wheel ne suffit pas à établir cette voie. Ne récupérez et ne construisez aucun paquet non fiable pendant l’énumération passive. Consultez la [commande download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), [l’interface du système de build](https://pip.pypa.io/en/stable/reference/build-system/) et [les conseils d’installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Une règle sudo autorisant `pip install` avec un chemin de projet local choisi par l’appelant crée une frontière de build plus directe. [pip accepte les répertoires de projets locaux](https://pip.pypa.io/en/stable/topics/local-project-installs/) et appelle leur système de build ; [le backend de build exécute des hooks de build contrôlés par le projet](https://pip.pypa.io/en/stable/reference/build-system/). Avant de considérer cette règle comme une exécution de code privilégiée, vérifiez l’identité RunAs effective, les restrictions et refus d’arguments exacts, le contrôle du projet sélectionné et le comportement de pip/backend installés. Un projet fixe et de confiance ou une règle excluant les chemins choisis par l’appelant ne suffit pas à établir cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération passive.

Une autorisation sans restriction pour `easy_install`, pouvant s’exécuter en tant que root, est une piste similaire concernant les anciens systèmes de build de paquets. [Setuptools indique](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install accepte un répertoire de projet local et construit les distributions source ; un projet contrôlé par l’appelant peut exécuter son `setup.py` pendant ce build sous l’identité sudo. Vérifiez le compte RunAs effectif, les restrictions de commande et d’arguments exactes (y compris les refus ultérieurs), le contrôle du projet sélectionné et le comportement de l’outil installé. Un projet fixe et de confiance ou une politique qui n’autorise pas une source choisie par l’appelant ne suffit pas à établir cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération.

Un wrapper Python autorisé par sudo qui utilise `setuptools.package_index.PackageIndex.download` avec une URL choisie par l’appelant constitue un cas d’examen différent de `pip download` : [l’avis GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) décrit, dans les versions affectées antérieures à 78.1.1, un nom de fichier dérivé de l’URL qui s’échappait du répertoire de téléchargement prévu et écrivait avec les permissions du processus. Vérifiez l’utilisateur RunAs et la règle d’arguments sudo effectifs, que le wrapper transmet bien l’URL de l’appelant à cette API précise, le build installé ou le correctif rétroporté du fournisseur, ainsi que la résolution du chemin obtenu. Une chaîne de version ou un répertoire de téléchargement modifiable ne suffit pas à établir une écriture arbitraire. Examinez le wrapper court et les métadonnées du paquet sans récupérer l’URL ni écrire de fichier pendant l’énumération.

Un wrapper de build autorisé par sudo qui transmet un fichier `.spec` choisi par l’appelant à PyInstaller nécessite le même examen de la frontière de confiance. Un fichier spec PyInstaller est du Python exécutable évalué pendant le **build**, et ses entrées `datas` peuvent intégrer dans un artefact des fichiers lisibles par l’identité de build. Vérifiez l’utilisateur RunAs exact, les règles sudo relatives aux arguments et aux refus, la gestion des chemins et des branches par le wrapper, le contrôle du fichier spec sélectionné et l’accès à l’artefact obtenu. Autoriser simplement une entrée `.py` ou trouver PyInstaller installé ne prouve ni le contrôle du fichier spec ni l’exécution privilégiée. L’examen passif doit se limiter à la lecture d’un wrapper de taille limitée et de ses métadonnées ; il ne doit pas lancer de build. Consultez [la documentation des fichiers spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Chargeurs de préréglages et de plugins exécutés par sudo

Les outils Python qui acceptent un préréglage ou un répertoire de plugins choisi par l’appelant peuvent importer du code avec les privilèges accordés par sudo. Par exemple, BBOT accepte un préréglage avec `-p`, et sa [documentation des modules personnalisés](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) décrit les entrées `module_dirs` qui sélectionnent des répertoires supplémentaires de modules Python. Si la règle sudo effective permet à l’appelant de choisir un préréglage et si celui-ci contrôle un module dans le répertoire sélectionné, l’import peut exécuter du code en tant qu’utilisateur privilégié, potentiellement avant que l’outil ne rejette un module invalide. Vérifiez la version installée, la politique sudo exacte concernant RunAs et les arguments, ainsi que le propriétaire du préréglage et des chemins des modules, sans charger le module pendant l’énumération.

### Outil de ligne de commande Backdrop exécuté par sudo

[Bee](https://github.com/backdrop-contrib/bee) est un outil en ligne de commande PHP pour Backdrop CMS. Ses commandes `eval` (`php-eval`) et `php-script` peuvent exécuter du PHP fourni par l’appelant. Une règle sudo qui autorise l’exécutable Bee en tant que root avec des arguments sans restriction peut donc exposer une exécution de code root si Bee peut initialiser une installation Backdrop. Lancez-le depuis le répertoire du site ou sélectionnez un site au moyen de l’option globale `--root=<directory>` ; trouver Bee ou un fichier Backdrop `settings.php` ne prouve ni l’autorisation sudo, ni l’existence d’un site utilisable, ni la réussite de l’initialisation. Avant tout test, examinez la règle sudo effective, les exclusions de commande, l’identité de l’exécutable et l’accès au site. Pendant l’énumération passive, inspectez la règle et les chemins de fichiers sans exécuter Bee. Consultez le [journal des modifications des commandes Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) pour l’ajout des commandes PHP.

### Serveurs de terminal exécutés par sudo

`mosh-server` démarre un serveur de terminal interactif en tant qu’utilisateur qui l’invoque. Il choisit un port UDP élevé et une clé de session, les communique à l’appelant et lance normalement le shell de connexion de cet utilisateur lorsqu’un client se connecte. Une autorisation sudo sans restriction pour `mosh-server`, pouvant s’exécuter en tant que root, constitue donc une piste d’accès à un shell, même si la commande serveur se détache. Vérifiez l’identité RunAs effective, les arguments autorisés et leurs exclusions, le binaire installé, le shell, la disponibilité du client et l’accès UDP. L’énumération passive doit examiner la règle sudo sans démarrer de serveur ni afficher de clé de session active. Consultez le [manuel du serveur Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) et les [notes de conception en amont](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de sauvegarde privilégiés qui réécrivent le fichier de tâches de l’appelant

Un wrapper shell exécuté en tant que root peut accepter un fichier de tâches choisi par l’appelant, supprimer `../` des chemins source, vérifier que chaque résultat commence par un répertoire autorisé, réécrire le fichier de tâches puis transmettre son *chemin* à un programme de sauvegarde. Examinez le chemin transformé après résolution canonique complète : un seul passage de remplacement de chaîne peut créer une nouvelle séquence de traversée acceptée par une vérification de préfixe lexicale. Vérifiez également si le programme de sauvegarde lit les données transformées en mémoire ou rouvre le fichier. S’il le rouvre, une réécriture échouée peut laisser intact le fichier d’origine.

Sous Linux, `fs.protected_regular` peut refuser une écriture `O_CREAT` dans le fichier ordinaire d’un autre utilisateur situé dans un répertoire sticky accessible en écriture à tous. Ce refus est une protection, mais un wrapper shell qui ignore l’erreur d’écriture peut tout de même continuer avec le fichier de tâches d’origine. Vérifiez ce paramètre, le propriétaire du fichier et du répertoire, et si le wrapper s’arrête en cas d’échec. Ce chemin n’est une piste de divulgation de fichiers que si la règle sudo effective autorise le wrapper en tant qu’utilisateur privilégié, si l’appelant contrôle l’entrée de tâches et une destination de sauvegarde lisible, et si l’utilitaire de sauvegarde inclut effectivement les sources protégées. Examinez ces conditions sans lancer la sauvegarde pendant l’énumération.

### Jokers d’arguments sur les outils réseau privilégiés

Dans une règle sudo pour `tcpdump`, un `*` dans le **motif d’arguments** peut correspondre aux espaces et aux barres obliques ; une restriction ressemblant à un chemin peut donc quand même autoriser du texte d’option supplémentaire. Cela diffère d’un joker dans le chemin de l’exécutable de la commande ; examinez la règle RunAs complète et les éventuels refus ultérieurs. Si des options peuvent être injectées, l’invocation autorisée et la sémantique des options de [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) dans la version installée déterminent si `-F`, `-V`, `-r`, `-w` ou `-Z` fournit une primitive de lecture/écriture utile. `-V` lit une liste de noms de fichiers de capture ; il ne permet pas de lire n’importe quel fichier. AppArmor ou une autre politique MAC peut bloquer l’accès aux fichiers même si sudo autorise la commande ; la présence d’un fichier de profil sur le disque ne prouve pas que celui-ci est chargé ou appliqué. Examinez passivement les autorisations et la politique avant de conclure. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) décrit la différence entre ces jokers.

Une règle sudo pouvant s’exécuter en tant que root qui ne mentionne que l’exécutable `tcpdump`, sans restriction d’arguments, mérite également un examen. Le [manuel de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) décrit `-z` comme une commande exécutée après la rotation lorsque `-C` ou `-G` fait tourner une capture enregistrée ; `-Z` ou une valeur par défaut à la compilation peut abandonner les privilèges avant l’exécution de cette commande. Vérifiez la règle sudo effective, le build installé, l’abandon de privilèges et la possibilité qu’une rotation se produise avant de considérer cette règle comme une voie d’élévation. Une règle mise en évidence est une piste, pas une preuve d’exécution de commande en tant que root.

### Wrappers Nmap exécutés par sudo

Lorsqu’un chemin `nmap` autorisé par sudo est un wrapper shell, inspectez le chemin exact autorisé et chaque option qu’il transmet. Bloquer l’orthographe familière `--script` ne bloque pas nécessairement le chargement de code NSE : [`--datadir`](https://nmap.org/book/man-misc-options.html) de Nmap sélectionne les fichiers de données, et NSE [charge `nse_main.lua`](https://nmap.org/book/nse-implementation.html) depuis le répertoire de données sélectionné lorsque les scripts sont activés. Certains builds installés acceptent aussi d’autres variantes des options longues ; comparez donc les restrictions à l’analyseur réel du binaire. [`--excludefile`](https://nmap.org/book/target-specification.html) constitue une autre surface de lecture de fichiers ; les erreurs d’analyse peuvent en divulguer le texte. Examinez la règle sudo effective, la logique du wrapper, la version de Nmap, le contrôle du répertoire et la politique MAC sans lancer de scan pendant l’énumération.

### Hooks pull Mercurial exécutés par sudo

Une source fixe dans `sudo hg pull /fixed/source` laisse tout de même le dépôt **receveur** être choisi par le répertoire de travail actuel, sauf si la commande le fixe avec `-R`. Un dépôt receveur contrôlé par l’appelant peut définir des hooks dans `.hg/hgrc`, et un hook peut s’exécuter en tant qu’utilisateur RunAs sudo. [Mercurial ignore la configuration de dépôt appartenant à un utilisateur ou groupe non fiable](https://mercurial-scm.org/help/topics/config) ; examinez donc les utilisateurs/groupes de confiance du compte RunAs et le répertoire de travail exact avant de considérer cela comme une exécution de code. La lecture de la politique et de la configuration suffit à un examen passif ; n’effectuez pas de pull et n’invoquez pas de hook pour les répertorier.

### Hooks pull Git exécutés par sudo

Pour une autorisation sudo exacte, pouvant s’exécuter en tant que root, pour `sudo git pull`, vérifiez aussi le dépôt **receveur** sélectionné par le répertoire de travail. Un dépôt appartenant à l’appelant peut avoir un hook exécutable `post-merge`, qui s’exécute avec l’identité du processus Git lorsqu’un pull réalise effectivement une fusion réussie ; [Git documente ce hook](https://git-scm.com/docs/githooks) ainsi que le [comportement de pull entre fusion et rebase](https://git-scm.com/docs/git-pull). Vérifiez la règle sudo effective et le répertoire courant, le chemin et les permissions du hook actif, ainsi que la possibilité d’effectuer une fusion contenant de nouveaux commits. Un pull échoué, sans changement ou limité au rebase ne permet pas d’établir cette voie par hook. Examinez la politique et les métadonnées du dépôt sans exécuter le pull privilégié.

### Copies d’archives rsync exécutées par sudo

Pour `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` dans le **motif d’arguments sudoers** peut correspondre aux espaces et autoriser une option supplémentaire entre la source et la destination. Cela diffère de l’expansion shell des noms de fichiers. Si l’appelant peut remplir la source et que la destination est accessible en écriture au processus rsync privilégié, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) peut demander une propriété privilégiée tandis que le mode archive préserve les bits de permission, ce qui peut créer un fichier SetUID appartenant à l’utilisateur visé. Vérifiez la sémantique exacte des [jokers sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la version de rsync, les refus ultérieurs, l’option `nosuid` du système de fichiers et la politique MAC. Une règle correspondante est une piste à examiner, pas une preuve d’élévation de privilèges réussie.

### Export de règles de filtrage réseau exécuté par sudo

Une autorisation sans restriction, pouvant s’exécuter en tant que root, pour `iptables` et `iptables-save` (ou la paire correspondante `ip6tables`) mérite un examen de l’écriture de fichiers. Le match `comment` accepte du texte de règle choisi par l’appelant, tandis que `iptables-save -f` écrit le jeu de règles sérialisé vers un chemin choisi.<sup>[[20]](#references)[[21]](#references)</sup> L’utilité d’une charge dépend de la manière dont le backend installé sérialise les commentaires et du fait que le fichier de destination accepte ou non d’autres lignes dans l’export ; `iptables-save` seul ne fournit pas de contenu arbitraire choisi par l’appelant. Vérifiez l’identité RunAs sudo exacte, les arguments et exclusions, l’extension de match disponible, le backend et les permissions de destination. Pendant l’énumération, examinez l’autorisation sans modifier les règles du pare-feu ni écrire de fichier.

### Répertoire de journalisation Below privilégié

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) concernait les versions de Below antérieures à 0.9.0 qui créaient un répertoire `/var/log/below` accessible en écriture à tous. Si un service ou une commande sudo autorisée exécute en tant que root un build affecté, un utilisateur capable d’écrire et de parcourir un répertoire de journaux sans sticky bit peut remplacer une entrée de journal par un lien symbolique avant l’ouverture du fichier par le processus privilégié. Examinez l’état du correctif du paquet installé, le chemin exact d’exécution privilégiée, l’accès effectif au répertoire, le sticky bit et les ACL, ainsi que les métadonnées de `/var/log/below/error_root.log`. Un chemin accessible en écriture à tous ou une règle sudo ne suffit pas à établir toute la chaîne. Un répertoire sticky ou un correctif du fournisseur modifie l’évaluation. L’énumération passive doit se limiter aux métadonnées ; il n’est pas nécessaire de créer un lien ni d’exécuter le programme privilégié.

### Collecte de bundles de support privilégiée à partir d’entrées modifiables

Un script de profil de support autorisé par `sudo` peut lire des chemins de journaux fixes en tant que root et copier leur contenu dans une archive de profil. Examinez le script réel pour repérer les lectures de fichiers, puis vérifiez si l’appelant peut remplacer un chemin source ou une entrée de répertoire parent par un lien symbolique. Si la lecture privilégiée suit ce lien et que l’archive résultante est lisible par l’appelant, un fichier protégé peut être divulgué. L’autorisation sudo, le chemin source modifiable, la lecture privilégiée et la sortie lisible doivent tous être présents ; un journal ou un nom de profil modifiable ne suffit pas. Examinez les permissions effectives et les métadonnées des liens sans remplacer de fichiers ni générer de profil pendant l’énumération. Les [consignes de support de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentent son script de profil exécuté en tant que root et son archive de sortie, illustrant pourquoi les entrées et les sorties de tels bundles doivent être protégées.

### Scripts Python de restauration d’archives exécutés en tant que root

Même une règle sudo très restreinte pour un script Python de restauration nécessite d’examiner son entrée d’archive. Si l’appelant peut sélectionner ou remplacer l’archive et que le script l’extrait en tant que root avec `tarfile.extractall(filter="data")`, vérifiez les mises à jour de sécurité de l’interpréteur avant de faire confiance au filtre. CPython a corrigé plusieurs contournements de filtres par liens symboliques et liens physiques, notamment CVE-2025-4517, dans les versions 3.9.23, 3.10.18, 3.11.13, 3.12.11 et 3.13.4. Les distributions peuvent rétroporter les correctifs sur des versions antérieures ; la version affichée de l’interpréteur ne prouve donc pas, à elle seule, une exposition.<sup>[[16]](#references)[[17]](#references)</sup>

Pour un examen passif, lisez la commande sudo exacte et le script, suivez l’argument qui sélectionne l’archive et vérifiez si l’utilisateur actuel peut écrire dans l’archive ou dans son répertoire parent. Confirmez séparément le correctif du fournisseur installé et la destination d’extraction ; `filter="data"` ne rend pas toutes les archives non fiables sûres.<sup>[[16]](#references)[[17]](#references)</sup>

### Chargeurs de modèles de machine learning exécutés par sudo

Une règle sudo qui autorise un fichier `.pt`, `.pth` ou `.ckpt` choisi par l’appelant mérite un examen lorsqu’un script privilégié transmet ce fichier à [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou à un autre chargeur fondé sur pickle. Vérifiez la règle RunAs effective, si l’appelant peut créer ou remplacer le modèle sélectionné, et le flux réel des arguments à travers tout wrapper shell jusqu’au helper Python. L’extension `.pth` désigne aussi des fichiers de configuration de site Python sans rapport avec les modèles ; l’extension seule ne prouve donc pas le chargement d’un modèle. Une analyse d’archive ou une analyse statique de pickle ne permet pas d’établir que le chargement ultérieur est sûr ; examinez le comportement de [`weights_only`, qui dépend de la version](https://docs.pytorch.org/docs/stable/notes/serialization.html), ainsi que toute liste d’autorisation. Consultez les [notes ML sur pickle et Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). L’énumération passive ne doit jamais charger ni décompresser le modèle.

### Analyse d’expressions exécutée par sudo sur des entrées stockées

Un script Python fixe exécuté en tant que root via sudo peut tout de même évaluer du texte qu’un utilisateur moins privilégié peut stocker dans une base de données applicative. Dans TensorFlow, l’appel `preprocess_input_exprs_arg_string(value, safe=False)` choisit une voie utilisant `eval` ; [l’avis de TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) décrit l’analyseur non sûr et un correctif apporté à son appelant en ligne de commande. L’appel explicite `safe=False` d’une application nécessite un examen distinct, même si cet appelant en ligne de commande a été corrigé. Vérifiez la règle sudo effective, qui peut modifier la ligne de données concernée, si le filtrage ou le scoring permet à cette ligne d’atteindre l’appel, ainsi que le comportement de la fonction installée. Une version de TensorFlow, une autorisation sudo ou un fichier de modèle codé en dur ne prouvent pas, à eux seuls, la chaîne. Examinez passivement le script et le flux de données ; ne lancez pas le helper privilégié et ne soumettez pas d’expressions de test pendant l’énumération.

### Configuration de needrestart autorisée par sudo

`needrestart -c` charge un fichier de configuration Perl choisi par l’appelant et en évalue le contenu. Si `sudo -l` autorise `needrestart` en tant que root avec des arguments permettant `-c`, et si l’appelant peut choisir un fichier de configuration lisible dans un emplacement modifiable, cette autorisation peut mener à l’exécution de code en tant que root. Vérifiez précisément la règle sudo concernant RunAs et les arguments ; une règle n’autorisant qu’une liste fixe d’arguments peut bloquer cette voie. Ce problème est distinct des vulnérabilités d’analyse d’interpréteurs de needrestart : mettre à jour le paquet ou désactiver `interpscan` ne rend pas sûre une autorisation root sans restriction pour `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python exécutés par sudo sous un autre compte

Un point d’entrée Python fixe peut tout de même importer un module que l’appelant peut modifier ou remplacer, notamment si sudo exécute le script en tant qu’utilisateur de service **non-root**. Pour un import littéral `from utils import status`, examinez aussi bien `utils/__init__.py` et `utils/status.py` que les permissions du répertoire du paquet. Avant de considérer le fichier modifiable comme une voie d’exécution, vérifiez le chemin d’import du script, les arguments sudo exacts autorisés et si l’action concernée atteint cet import. Inspectez les fichiers et leurs permissions sans importer ni exécuter le script pendant l’énumération.<sup>[[2]](#references)[[3]](#references)</sup>

Une règle sudo exacte pour `python3 /absolute/script.py` nécessite seulement que le script soit lisible ; il n’a pas besoin d’être exécutable ni d’avoir un shebang. Examinez aussi les modules locaux **manquants** : si le script importe un module dont le nom de fichier peut être créé dans un répertoire de script modifiable par l’appelant, Python peut charger ce fichier sous l’identité RunAs. Vérifiez la règle sudo effective, le [chemin de recherche réel des modules](https://docs.python.org/3/library/sys_path_init.html) de l’interpréteur, si le module est intégré ou gelé, et si l’import est atteint. Une règle sudo directe pour le script a des exigences différentes concernant le bit d’exécution et le shebang. Un wrapper distinct qui ajoute des éléments fournis par l’appelant après `sudo -u account` nécessite aussi un examen du flux des arguments : un autre `-u` dans ces éléments n’a d’importance que si la politique sudo invoquée autorise l’identité obtenue. Des chaînes statiques ne prouvent aucune de ces voies.

### Apache exécuté par sudo avec une configuration contrôlée par l’appelant

Si une règle sudo autorise une invocation privilégiée de `apachectl`, `apache2ctl` ou `httpd` avec un fichier de configuration `-f` contrôlé par l’appelant, examinez ce fichier et les permissions de son répertoire parent. La directive Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) prend un nom de module suivi du **nom du fichier du module** ; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) charge également un fichier. [`Include` et `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) peuvent compléter la configuration ou exposer le contenu de fichiers via des erreurs. Un wrapper personnalisé peut valider ces chemins, abandonner ses privilèges ou restreindre les arguments ; une configuration modifiable est donc une piste, pas une preuve d’exécution de code. Avant de conclure, vérifiez la canonicalisation des chemins, les liens symboliques et l’analyse des directives.

### nginx exécuté par sudo avec une configuration contrôlée par l’appelant

Une règle nginx sans restriction pouvant s’exécuter en tant que root peut permettre à [`-c` de sélectionner une autre configuration](https://nginx.org/en/docs/switches.html). Examinez précisément les arguments sudo et leurs exclusions, si l’appelant peut fournir la configuration et si le master ou les workers qui en résultent conservent l’accès aux chemins protégés. Un `root` choisi avec `autoindex` peut exposer des fichiers via un nouveau listener ; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) peut fournir une voie d’écriture privilégiée, mais le module DAV n’est pas compilé par défaut. Vérifiez sa présence, l’accessibilité du listener, les permissions des fichiers et le comportement des fichiers temporaires. La directive [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) peut aussi cibler un fichier choisi ; écrire des journaux dans un fichier de configuration sensible, comme `/etc/ld.so.preload`, nécessite un processus ayant effectivement des privilèges d’écriture et un enregistrement de journal contrôlable avant de constituer une voie d’élévation. La mise en évidence de l’exécutable par `sudo -l` est une piste, pas la preuve que l’une de ces voies fonctionne. L’énumération passive ne doit pas démarrer ni reconfigurer nginx.

### Comparaison de motifs dans des invites Bash privilégiées

Lorsqu’un script Bash autorisé par sudo lit une valeur fournie par l’appelant et la vérifie avec `[[ "$expected" == $entered ]]`, Bash interprète l’opérande droit non cité comme un motif. Un joker peut donc satisfaire la comparaison sans connaître la valeur attendue. Mettre l’opérande entre guillemets (`[[ "$expected" == "$entered" ]]`) en fait une comparaison littérale. Examinez la règle sudo exacte, si l’invite peut être atteinte et ce que fait le script après la comparaison ; la syntaxe seule ne suffit pas à établir une voie exploitable. Évitez d’afficher la valeur attendue pendant l’énumération. Consultez la [référence des constructions conditionnelles de Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers exécutés par sudo qui téléchargent puis exécutent un fichier

Une autorisation sudo sans restriction pour un helper personnalisé pouvant s’exécuter en tant que root mérite un examen du flux de données s’il accepte une URL choisie par l’appelant, écrit la réponse sur le disque puis invoque ce fichier avec un interpréteur ou un shell. [Sudoers autorise des arguments arbitraires lorsqu’une entrée de commande n’en précise aucun](https://man7.org/linux/man-pages/man5/sudoers.5.html) ; un chemin d’exécutable fixe ne limite donc pas ce que ses arguments peuvent sélectionner. Vérifiez, dans le helper installé, la validation réelle de l’URL, le chemin de sortie, la branche de réussite et l’exécution ultérieure. Un import libcurl correspondant ou une chaîne imprimable ne prouve pas cette chaîne.

Même un nom de sortie fixe peut être remplacé entre l’écriture et l’exécution lorsque le helper utilise un **chemin relatif dans un répertoire de travail contrôlé par l’appelant**. Le renommage ou le remplacement d’un fichier appartenant à root dépend des droits d’écriture et de recherche sur le répertoire et des restrictions du sticky bit, pas seulement du mode du fichier ; consultez [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Vérifiez si le helper rouvre ensuite le chemin ou utilise le descripteur déjà ouvert, et s’il se déplace dans un répertoire de confiance avant d’écrire. Examinez passivement la politique sudo, le helper et les métadonnées du répertoire ; n’exécutez pas le téléchargement privilégié et ne tentez pas de course pendant l’énumération.

Un helper de téléchargement exécuté par sudo en tant que root peut aussi exposer une injection d’**arguments** s’il construit une chaîne de commande Bash telle que `curl <caller input> -o <fixed output>`. Un filtre qui rejette les espaces ne bloque pas [l’expansion d’accolades de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) : des éléments non cités et séparés par des virgules peuvent devenir plusieurs arguments de curl. Si l’entrée arrive à curl avant le `-o` fixe, une option de sortie fournie par l’appelant peut sélectionner la destination de la première URL sous l’identité du helper ; [curl associe les options de sortie aux URL dans l’ordre](https://curl.se/docs/manpage.html#-o). Vérifiez le shell exact, les guillemets, la validation des entrées, la règle sudo effective, l’ordre des arguments de curl et les schémas d’URL pris en charge, ainsi que le contrôle par l’appelant des octets récupérés ou sa capacité à lire le résultat. Un exécutable empaqueté avec PyInstaller peut contenir de la logique d’application Python, mais un marqueur d’empaquetage ou une chaîne `curl` ne prouve pas, à lui seul, ce flux de données. Examinez une copie hors ligne de taille limitée si vous y êtes autorisé ; l’énumération courante ne doit ni exécuter le helper ni récupérer des données choisies par un attaquant.

Un script shell exécuté par sudo en tant que root qui appelle [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) choisit seulement un nom inutilisé ; il **ne crée pas** le fichier. Si le script crée ensuite ce nom dans un répertoire qu’un autre utilisateur peut influencer, le rouvre puis ajoute son contenu à une destination protégée telle que `authorized_keys` de root, examinez le risque de course sur le fichier temporaire. Vérifiez la règle sudo exacte, le propriétaire du répertoire et du fichier, la séquence de création et de réouverture, les protections du noyau et si l’écriture privilégiée utilise réellement des octets contrôlés par l’attaquant. Une chaîne `mktemp -u` ou la présence d’un `/tmp` modifiable ne prouve pas, à elle seule, l’existence d’une course. Inspectez le script et les métadonnées des chemins sans l’exécuter ni provoquer de course sur son fichier temporaire pendant l’énumération.

## Notes défensives

- Évitez d’autoriser des interpréteurs ou des éditeurs interactifs via sudo.<sup>[[1]](#references)</sup>
- N’autorisez pas de writers génériques tels que `tee` avec des opérandes sans restriction. Utilisez un wrapper appartenant à root qui sélectionne une destination fixe et rejette les chemins contrôlés par l’appelant.<sup>[[2]](#references)</sup>
- Préférez des wrappers fixes appartenant à root qui effectuent une seule action administrative limitée.<sup>[[1]](#references)[[2]](#references)</sup>
- Si un interpréteur est indispensable, limitez précisément le chemin du script et empêchez les arguments contrôlés par l’utilisateur, les imports modifiables, `PYTHONPATH` et la préservation non sûre de l’environnement.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si l’édition de fichiers est nécessaire, limitez précisément le chemin du fichier et envisagez `sudoedit` avec des versions corrigées de sudo et une gestion stricte de l’environnement.<sup>[[1]](#references)[[2]](#references)</sup>
- Examinez `SETENV`, `env_keep`, les répertoires de travail modifiables, les chemins de modules/imports modifiables, `NOEXEC`, `use_pty` et la journalisation, sans les considérer comme un sandbox complet.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
