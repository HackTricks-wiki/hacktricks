## Interpréteurs autorisés par Sudo

Si `sudo -l` permet à un utilisateur d’exécuter un interpréteur en tant que root, considérez cela comme une exécution directe de code. Les interpréteurs sont conçus pour exécuter du code arbitraire : une règle qui autorise les binaires `python3`, `perl`, `ruby`, `lua`, `node` ou similaires équivaut généralement à l’exécution de commandes en tant que root, sauf si les arguments sont strictement limités et validés.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Procédure courante : commencez par lister les privilèges de l’utilisateur, puis exécutez une instruction Python avec l’option `-c` de l’interpréteur.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

D’autres exemples d’interpréteurs sont présentés ci-dessous ; les interpréteurs répertoriés documentent l’exécution de code inline ou les API de processus enfants.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Le chemin exact est important. Si la règle sudo autorise `/usr/bin/python3`, utilisez ce chemin exact lors de la validation.<sup>[[2]](#references)</sup>

Un glob d’exécutable sudo tel que `/usr/bin/python*` peut également autoriser Python 2 pour un script écrit pour Python 3. Si le script atteint `input()` avec du texte contrôlé par l’appelant, [Python 2 évalue ce texte comme une expression](https://docs.python.org/2/library/functions.html#input) ; l’invocation explicite de l’interpréteur remplace le shebang du script. Vérifiez les binaires correspondants installés, l’identité RunAs effective et la politique concernant les arguments, les refus et les entrées accessibles avant de considérer cela comme une voie d’exécution.

Un chemin de script fixe dans une règle sudo permettant l’accès à root ne limite pas ce que le script exécute. Pour un wrapper Bash lisible, vérifiez si sa première commande exécutable utilise un paramètre positionnel non entouré de guillemets, tel que `$1`, comme **mot de commande**, alors que sudo autorise l’appelant à choisir les arguments. Confirmez l’identité RunAs effective, la politique concernant le mot de passe et les arguments, les refus ultérieurs ainsi que la branche réellement empruntée par le script ; `NOEXEC`, une liste d’arguments sûre et fixe ou un wrapper qui valide sa commande peuvent modifier le résultat. Lors de l’énumération, inspectez statiquement le script court au lieu de l’invoquer avec une commande de test.

Une règle sudo non restreinte permettant à `dotnet` d’accéder à root mérite également un examen de l’interpréteur. Si un SDK .NET est installé, [`dotnet fsi` exécute du code F# de manière interactive ou depuis un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), et [`dotnet run` exécute un projet à partir du code source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirmez d’abord l’identité RunAs effective et la politique exacte concernant les arguments : une règle limitée à une sous-commande sûre particulière ou à une application de confiance représente un droit différent, et une installation limitée au runtime peut ne pas inclure les commandes du SDK. Le nom de l’exécutable à lui seul est un indice à examiner, pas une preuve d’exécution de code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Éditeurs autorisés par sudo

Si `sudo -l` permet à un utilisateur d’exécuter un éditeur interactif en tant que root, considérez-le comme une surface d’exécution de commandes, et non comme une autorisation inoffensive de modifier des fichiers. Les éditeurs peuvent souvent exécuter des commandes shell, lire ou écrire n’importe quel fichier, ou appeler des outils externes depuis l’éditeur.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Procédure courante : listez les privilèges de l’utilisateur, puis lancez avec sudo chaque éditeur ou pager autorisé.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Exécution de commandes avec Nano

Lorsque `nano` est autorisé via sudo, l’exécution de commandes peut être accessible depuis l’interface de l’éditeur.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Fournissez ensuite une commande telle que `id` ou `/bin/sh` à l’invite de commande de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactif ne dispose pas de flux de terminal utilisables, cette forme de redirection redirige sa sortie standard et ses erreurs vers le descripteur 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La séquence de touches exacte peut varier selon la version de nano et les options de compilation, mais le problème de sécurité reste le même : l’éditeur s’exécute en tant que root et peut lancer des commandes externes.<sup>[[1]](#references)[[12]](#references)</sup>

### Autres échappements courants des éditeurs

Les éditeurs de type Vim permettent couramment d’exécuter des commandes via `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Les pagers comme `less` peuvent également permettre l'exécution de commandes shell.<sup>[[14]](#references)</sup>

Une règle sudo autorisant `apport-cli` à s'exécuter en tant que root mérite le même examen du pager. Certaines versions d'Apport pouvaient ouvrir un rapport de plantage dans `less` avec une taille de terminal ajustable par un attaquant ; le pager pouvait alors fournir un shell root si les conditions particulières liées à sudo et au pager étaient réunies. Vérifiez la règle sudo effective, la configuration du pager et le correctif du paquet de la distribution avant de considérer la version comme vulnérable à elle seule. Consultez les métadonnées du paquet et de la politique sans provoquer de plantage ni ouvrir le rapport privilégié lors d'une énumération passive. [La fiche CVE d'Ubuntu](https://ubuntu.com/security/CVE-2023-1326) répertorie les versions corrigées des paquets propres à chaque version, y compris les correctifs rétroportés.

```text
!/bin/sh
```

## Autres risques liés aux règles sudo et doas

Commencez par `sudo -l`, `sudo -V` et toute politique `doas` applicable. Examinez ensemble la commande autorisée, l’utilisateur d’exécution, les arguments, l’environnement et les valeurs par défaut. L’autorisation d’exécuter une commande en tant que compte de service non-root peut tout de même exposer les fichiers de ce compte ou fournir un chemin vers root.

Un script Python précis autorisé par sudo peut quand même exécuter une commande shell sous l’identité RunAs si une entrée interactive contrôlée par l’appelant est concaténée dans [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Une denylist de la ponctuation shell ne suffit pas à établir que le code est sûr : [le shell reconnaît aussi la substitution de commande `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Vérifiez que les arguments autorisés atteignent la branche qui lit l’entrée, que cette entrée arrive dans la commande shell sans validation sûre et que la politique sudo effective autorise l’utilisateur RunAs visé. Le chemin du script ou un appel à `os.system()` ne sont que des pistes à examiner ; inspectez le code source sans invoquer le script privilégié.

Une autorisation sudo effective pour root sur `chattr` peut retirer l’attribut de fichier immuable (`i`), mais cela ne donne à lui seul ni le droit d’écriture ni une nouvelle identité. [Le manuel de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indique que cet attribut bloque les modifications et que seul root ou un processus doté de `CAP_LINUX_IMMUTABLE` peut le changer. Vérifiez la politique exacte concernant les arguments sudo et la prise en charge du système de fichiers, puis vérifiez séparément que l’appelant peut écrire dans le fichier une fois l’attribut effacé et qu’un processus d’identité supérieure l’utilise. Par exemple, remplacer un shell de connexion exige aussi que le compte cible accepte les identifiants concernés et qu’une connexion utilise effectivement ce shell. Examinez la politique, les attributs des fichiers et les permissions sans les modifier pendant l’énumération.

Si sudo demande à la fois un mot de passe et un code à usage unique, distinguez ces prérequis de l’autorisation d’exécuter la commande. Un fichier `.google_authenticator` lisible contient une graine sensible, tandis qu’un ancien hash de mot de passe d’application ou de base de données n’est qu’un candidat au mot de passe actuel du compte ; aucun des deux ne prouve que l’autre facteur est accepté par la configuration PAM effective. Une fois autorisé, examinez précisément l’utilisateur RunAs et les arguments : une autorisation root sans restriction pour RubyGems `gem` peut exposer sa commande d’éditeur ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mais ce n’est pas le cas d’une autorisation restreinte ou d’une authentification échouée. Une énumération passive doit signaler les chemins et la politique sans afficher la graine, récupérer un mot de passe, générer un code ou invoquer la commande privilégiée.

Une autorisation sudo effective sans restriction pour root sur `knife` de Chef mérite un examen au niveau de l’interpréteur : [Chef indique que `knife exec -E` évalue localement une chaîne Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Vérifiez que la règle sudo effective autorise le sous-ordre `exec` et l’argument `-E` fourni par l’appelant, l’identité RunAs visée et les éventuels refus de commande ou arguments fixes correspondants. Le binaire installé ou une règle limitée à d’autres sous-ordres ne sont que des pistes. Une énumération passive doit signaler la règle sans invoquer `knife`.

Une autorisation sudo exacte pour root sur `msfconsole` interactif est tout aussi sensible : [GTFOBins documente sa console `irb`](https://gtfobins.org/gtfobins/msfconsole/), qui peut hériter de l’identité sudo. Confirmez l’utilisateur RunAs effectif, la liste des arguments autorisés, les refus de commande, `NOEXEC` ou les autres restrictions, le comportement de la console installée et la possibilité pour l’appelant de fournir une entrée interactive. La mise en évidence d’un chemin n’est qu’une piste ; une énumération passive ne doit pas lancer la console.

Sur FreeBSD, même une règle sudo limitée à `pkg update` et `pkg install *` en tant que root mérite un examen de la confiance accordée aux dépôts. Vérifiez si `/etc/hosts` est accessible en écriture à l’appelant et si la configuration effective des dépôts activés utilise un nom d’hôte HTTP avec `signature_type: none`. [Le manuel de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indique que `none` désactive les vérifications de signature ; `pkg+http` seul ne suffit pas à l’établir. Un paquet peut contenir des scripts d’installation ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)) : un appelant qui contrôle réellement le point de terminaison du dépôt et peut sélectionner un paquet peut donc franchir la frontière root. Vérifiez les substitutions de dépôt, la résolution SRV/miroir, les arguments sudo effectifs, la sélection du paquet et l’exécution de scripts avant de conclure. Examinez la politique et les petits fichiers de configuration locaux sans rediriger les noms ni lancer `pkg` pendant l’énumération.

Une autorisation sudo effective pour root sur `apt-get update` et `apt-get upgrade` exige aussi un examen de la confiance accordée aux dépôts lorsque sudo préserve un `http_proxy` contrôlé par l’appelant. Vérifiez si la configuration APT effective utilise réellement cette variable et quelles requêtes de dépôts activés elle peut affecter ; un proxy seul ne peut pas remplacer des paquets provenant d’une archive authentifiée par une clé de signature approuvée. [Le manuel du transport HTTP d’APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) décrit la priorité des proxys, et [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) décrit les vérifications de signature, les substitutions autorisant les dépôts non sécurisés et la confirmation requise pour les paquets non authentifiés. Confirmez l’utilisateur RunAs et les arguments sudo exacts, la politique d’authentification des dépôts, toute confirmation interactive requise et l’exécution en tant que root des scripts des mises à niveau sélectionnées. Examinez passivement la politique et la configuration locale ; ne redirigez pas le trafic des paquets et ne lancez pas de mise à niveau pendant l’énumération.

Une règle sudo effective pour root sur `snap install` peut créer une frontière entre paquet et code si ses arguments permettent à l’appelant de sélectionner un snap local et un mode d’installation permissif. [La documentation de Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) indique que `--dangerous` ignore les vérifications d’assertion des snaps locaux et que `--devmode` assouplit le confinement ; [un hook d’installation peut s’exécuter lors de l’installation initiale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Vérifiez la politique exacte d’arguments/RunAs de sudo, qui contrôle le fichier snap, si snapd installé accepte ces modes, ainsi que l’identité effective et le confinement du hook avant d’affirmer qu’il donne accès à des fichiers protégés de l’hôte. La présence du binaire `snap` ou d’une règle ressemblant à un joker ne prouve pas cette chaîne. Une énumération passive ne doit ni installer de paquet ni exécuter son hook.

Pour une autorisation sudo exacte sur un binaire personnalisé de lecture d’identifiants exécuté en tant que compte **non-root**, commencez par examiner le binaire autorisé et ses permissions sans l’exécuter. Un contrôle de mot de passe intégré peut n’être visible qu’avec des caractères larges ; [GNU `strings` documente l’extraction little-endian 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Une chaîne visible ne prouve ni qu’il s’agit du mot de passe accepté ni que la branche de succès expose un identifiant actuel. Vérifiez séparément le comportement du binaire, l’accès du compte cible aux données protégées, la validité des identifiants et toute transition ultérieure de compte ou de groupe. Si ce compte appartient à `docker`, vérifiez l’accès au socket et si le daemon utilise une identité rootful ou rootless avant d’en déduire un accès root à l’hôte ; [Docker documente les implications de son groupe sur les privilèges root](https://docs.docker.com/engine/install/linux-postinstall/). Une énumération courante doit signaler la règle sudo et l’appartenance au groupe sans exécuter le binaire ni afficher ses chaînes.

Une règle sudo avec joker pour les scripts de maintenance d’une application nécessite d’examiner plus que le chemin du script. Vérifiez si le script autorisé accepte des arguments sans restriction ou lit des paramètres modifiables par un compte d’application moins privilégié, puis suivez ces valeurs jusqu’aux commandes shell ou à l’environnement d’un sous-processus. Par exemple, le [`zmupdate.pl` de ZoneMinder construit une commande `mysqldump` et l’exécute via `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), tandis que [`zmdc.pl` copie le paramètre `ZM_LD_PRELOAD` dans `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) avant de démarrer les daemons. Une règle sudo autorisant l’un ou l’autre script en tant que root peut franchir une frontière de confiance si l’entrée correspondante est contrôlable et atteint ce code dans la version installée. Inspectez la règle sudo effective, les droits sur la configuration de l’application et le code source du script ; le joker ou le paramètre, pris isolément, n’est qu’une piste, pas une preuve d’exécution.

- `SETENV`, `env_keep`, `secure_path` et `LD_PRELOAD` peuvent transformer une commande par ailleurs étroitement limitée en détournement d’import, de bibliothèque ou de PATH. Consultez le [guide des variables d’environnement](../linux-basics/linux-environment-variables.md) et [l’abus de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Une autorisation `SETENV` exacte pour root sur un wrapper shell mérite aussi un examen à un saut si le wrapper lance un script Python fixe avec un import littéral. `secure_path` limite la recherche des commandes par le shell, pas la [recherche de modules Python via `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) ; [`-E` et `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) font ignorer cette variable d’environnement à Python. Confirmez les tags et refus sudo effectifs, la branche du wrapper, les options de l’interpréteur, la résolution de l’import et l’existence d’un répertoire de recherche modifiable par l’appelant avant de conclure à une exécution de code. Examinez statiquement les scripts courts ; n’invoquez pas le wrapper privilégié.

Une autorisation sudo exacte pour root sur `neofetch ""` peut tout de même charger une configuration shell si les valeurs par défaut sudo applicables préservent un `XDG_CONFIG_HOME` contrôlé par l’appelant. [Le chargeur de configuration de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) source `neofetch/config.conf` ou `neofetch/config` sous ce répertoire ; la liste d’arguments vide n’empêche pas cette recherche. Confirmez le chargeur installé, l’utilisateur RunAs et la politique d’arguments effectifs, les éventuels refus de commande, la préservation réelle de la variable sélectionnée par sudo pour cette commande et la possibilité pour l’appelant de contrôler un chemin de configuration lisible. Une variable préservée ou la seule présence de Neofetch installé n’est qu’une piste. Examinez la politique et les métadonnées des fichiers sans invoquer la commande privilégiée ni afficher le contenu de la configuration ; voir [la gestion de l’environnement dans sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Une règle sudo sans restriction pour root sur `facter` mérite un examen distinct des custom facts. [Puppet indique](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` charge des fichiers de facts Ruby depuis le répertoire sélectionné. Vérifiez si la règle sudo exacte autorise cette option, si Facter installé l’accepte et si l’appelant contrôle le répertoire. Des arguments fixes, un refus explicite de commande ou la désactivation des custom facts peuvent changer le résultat. Une énumération passive doit signaler cette possibilité au vu de la politique, sans invoquer Facter ni lire le contenu des facts.

Pour une autorisation sudo exacte d’un script root avec `SETENV`, examinez les noms de commandes simples comme `find` et le `PATH` effectif après application de la politique sudo et initialisation du script. Un fichier Bash sourcé peut aussi exécuter `enable -n [` : [Bash recherche alors une commande externe `[` dans `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), lorsque le script utilise ensuite cette commande. Confirmez les règles applicables de [sudoers concernant l’environnement et `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), les éventuelles entrées `NOSETENV`/`NOEXEC` ou de refus, le flux du script et des fichiers sourcés, ainsi que la présence d’un répertoire de recherche exécutable contrôlé par l’appelant. Un script lisible contenant une commande simple est une piste, pas une preuve d’exécution privilégiée ; inspectez-le sans invoquer la règle sudo.
- Un script privilégié qui récupère une URL fixe avec `curl` peut tout de même accepter une réponse choisie par l’appelant si une règle sudo applicable préserve `http_proxy` et que la requête passe par ce proxy. Si le script transmet ensuite la réponse à un analyseur XML qui résout les entités externes, une réponse malveillante peut divulguer des fichiers lisibles par le processus privilégié. Vérifiez la politique exacte de l’environnement sudo, les exclusions `no_proxy`, l’URL demandée, la configuration de l’analyseur et la destination de sortie ; une variable proxy ou un analyseur XML, pris isolément, ne constitue pas une vulnérabilité. La [documentation de l’environnement proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) décrit le comportement de ces variables. N’effectuez pas de requêtes réseau et n’analysez pas de XML malveillant pendant une énumération passive.
- Un script sudo effectif pour root qui construit un fichier PostScript à partir de données influencées par l’appelant puis exécute `ps2pdf -dNOSAFER` mérite un examen distinct du flux d’entrée. Ghostscript indique que cette option désactive SAFER jusqu’à `.setsafe`, autorisant les opérations sur les fichiers PostScript dans les limites des permissions du processus au niveau du système d’exploitation. Une requête SQL construite à partir d’un argument de l’appelant peut alimenter le modèle PostScript avec des lignes contrôlées par un attaquant, mais une chaîne de requête ou l’appel à `ps2pdf`, à lui seul, ne prouve pas que les données atteignent une syntaxe PostScript exécutable. Confirmez la règle sudo effective, le chemin exact de l’entrée jusqu’au modèle, les éventuels échappements, le comportement de Ghostscript installé et la réactivation éventuelle de SAFER avant l’interprétation du document. N’invoquez pas la conversion privilégiée pendant une énumération passive. Voir la [documentation de `-dNOSAFER` de Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Pour une règle sudo qui lance un script shell, comparez les variables préservées au contenu du script. Une construction telle que `if $CHECK_CONTENT; then` exécute comme commande la valeur développée ; préserver `CHECK_CONTENT` peut donc permettre l’exécution de commandes même si le chemin du script et ses arguments sont fixes. Il faut vérifier, pour cette règle précise, si la branche est atteignable et si l’environnement est effectivement conservé.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script Python autorisé par sudo peut importer du code depuis un répertoire modifiable ou un fichier `.pyc` en cache. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md) détaille le cas du cache.
- Un script Python fixe autorisé à s’exécuter en tant que root peut tout de même exposer un débogueur interactif. Des appels comme `pdb.set_trace()` ou `pdb.post_mortem()` permettent d’exécuter des instructions Python dans le contexte du processus débogué si l’appelant peut atteindre le point d’arrêt ou le gestionnaire d’exception **et contrôler le flux d’entrée du débogueur**. Vérifiez la règle RunAs sudo exacte, l’authentification et les conditions de branche, l’atteignabilité de l’exception, la propriété du terminal/de l’entrée et si le débogueur s’exécute dans ce même processus privilégié. Une requête socket qui déclenche une exception ne donne pas à elle seule accès à un débogueur attaché à un autre terminal. [Python documente l’évaluation d’instructions par le débogueur et le mode post-mortem](https://docs.python.org/3/library/pdb.html) ; inspectez statiquement le script au lieu de déclencher le gestionnaire privilégié pendant l’énumération.
- Un script Python fixe autorisé par sudo peut aussi lire un champ de profil dans une base de données ou via un socket Unix, puis l’ajouter à une chaîne qui devient ensuite la **chaîne de format** de `str.format()`. [Les champs de remplacement peuvent suivre des attributs et des clés de mapping](https://docs.python.org/3/library/string.html#format-string-syntax) : un champ contrôlé par un attaquant peut donc inspecter les objets transmis à `format()` et exposer les données accessibles depuis ces objets si le résultat est affiché ou enregistré à un endroit lisible par l’appelant. Vérifiez l’identité RunAs sudo effective, le droit d’écriture sur l’enregistrement concerné, le flux des données vers la chaîne de format, les objets fournis et la visibilité de la sortie. Cela ne constitue pas automatiquement une exécution de code ; une chaîne de format littérale de confiance avec des *valeurs* contrôlées par l’attaquant représente un autre cas. Un secret divulgué ne permet une transition vers un compte système que si ce compte l’accepte. Examinez le script et les permissions du socket sans invoquer l’opération privilégiée.
- Un wrapper Python capable de s’exécuter en tant que root peut transmettre une URL choisie par l’appelant à `Repo.clone_from` de GitPython. Si le wrapper active aussi `protocol.ext.allow=always` dans Git, un dépôt distant `ext::` peut invoquer un helper externe. Vérifiez les arguments sudo exacts, la provenance de l’URL, la version du paquet GitPython et les correctifs du fournisseur, ainsi que l’activation explicite ou non de protocoles non sûrs par le wrapper. GitPython a ajouté une [protection par défaut contre les protocoles non sûrs](https://github.com/gitpython-developers/GitPython/commit/2625ed9) dans la version 3.1.30 ; la version de l’exécutable `git` est un élément distinct. Un examen passif doit se limiter à la règle et à un extrait de code de taille raisonnable, sans lancer le clonage.
- Une autorisation sudo inter-utilisateurs pour un outil CLI de clonage de dépôts peut exposer un chemin distinct d’injection dans une chaîne shell. Suivez l’argument de dépôt choisi par l’appelant jusqu’à [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js ou un autre constructeur de commande shell, et vérifiez qu’il n’est pas transmis avec une séparation sûre des arguments ; `exec` de Node transmet sa chaîne de commande à un shell. Confirmez l’utilisateur RunAs exact, les sous-ordres et arguments autorisés, le code du wrapper installé et la validation de l’entrée. Le nom de l’outil de dépôt ou une règle sudo sans restriction ne prouve pas à lui seul une injection de commande. Inspectez le wrapper sans lancer de clonage privilégié pendant l’énumération.
- Un wrapper personnalisé appartenant à root peut sembler sûr parce que ses binaires et scripts ne sont pas modifiables, alors que sa décision d’exécuter une action privilégiée dépend d’un indicateur, d’une valeur d’API locale ou d’un état de service qu’un utilisateur non privilégié peut changer. Suivez chaque condition jusqu’à son entrée et vérifiez les contrôles d’autorisation. Pendant l’énumération, examinez la configuration et les permissions sans modifier l’état opérationnel ; un appel à `systemd-run` dans le wrapper n’est pertinent que si la condition peut être influencée.
- Un client de sauvegarde autorisé via sudo en tant que root peut accepter un fichier de configuration choisi par l’appelant (par exemple, `npbackup-cli -c`). Vérifiez l’utilisateur d’exécution exact et les arguments autorisés, puis si l’appelant contrôle le chemin de configuration, les chemins sources de sauvegarde et les options de dépôt ou de lecture/restauration. Un secret chiffré de dépôt présent dans une configuration lisible peut rester utilisable par le client, mais la règle seule ne prouve ni l’accès au dépôt ni la divulgation de fichiers root. Vérifiez l’autorisation sans lancer de sauvegarde ni en afficher le contenu.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) prend en charge `--password-command`, qui appelle un programme pour obtenir le mot de passe du dépôt. Si une règle sudo autorise un utilisateur moins privilégié à exécuter restic en tant que root avec une commande de mot de passe choisie par l’appelant et un sous-ordre qui nécessite ce mot de passe, ce helper peut s’exécuter en tant que root. Examinez précisément les arguments et exclusions sudo ; n’invoquez pas le helper ni une commande de sauvegarde pour la seule énumération de cette condition.
- Une autorisation privilégiée pour `restic backup` peut aussi franchir une frontière de lecture de fichiers si le modèle d’arguments sudo permet à l’appelant de choisir à la fois la source et un dépôt qu’il pourra lire et déchiffrer ensuite. [Les jokers d’arguments sudoers peuvent correspondre aux espaces et aux slashs](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) : examinez donc les jokers finaux au lieu de supposer qu’un préfixe de dépôt fixe limite la source. [Restic peut sauvegarder vers des dépôts locaux ou distants](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mais un dépôt local peut contenir de nouveaux objets écrits uniquement par root ; confirmez la politique sudo effective, l’accès au backend, le mot de passe du dépôt et les permissions des objets résultants avant de conclure à une divulgation. Une clé SSH sauvegardée ne donne accès que si le compte de destination l’accepte. Ne lancez pas de sauvegarde pour tester cette hypothèse pendant un examen passif.
- Une commande de maintenance ou de sauvegarde personnalisée sans restriction peut accepter un chemin de sortie ou disposer de son propre ordonnanceur de tâches. Pour un chemin d’écriture de fichier, vérifiez la règle sudo exacte et l’utilisateur d’exécution, puis si l’appelant contrôle à la fois les données et la destination. Pour un chemin d’exécution planifiée, vérifiez l’identité d’exécution de l’ordonnanceur, l’entrée de commande et tout contrôle supplémentaire par mot de passe ou autorisation. Le nom de la commande ou `NOPASSWD`, à lui seul, ne prouve aucune de ces voies. Voir [l’écriture dans des fichiers appartenant à root](../interesting-files-permissions/write-to-root.md) et [cron et les timers systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Une commande sudo fixe peut tout de même charger un fichier de configuration prévisible depuis un répertoire partagé modifiable. Vérifiez si l’appelant peut remplacer ce fichier et si ses champs source et destination contrôlent une récupération ou une copie privilégiée. Une URL de fichier local peut exposer des données lisibles uniquement par le compte RunAs sudo ; une source contrôlée par l’appelant associée à une destination protégée peut créer un chemin d’écriture. Confirmez la gestion des URL par le programme installé, les vérifications du chemin de destination, la règle sudo effective et l’accessibilité de la sortie. Un chemin de configuration modifiable dans `/tmp` est seulement une piste : examinez le binaire et les métadonnées du fichier sans invoquer le transfert privilégié.
- Une règle sudo pour `git apply` peut permettre au compte RunAs d’écrire dans des fichiers sélectionnés par un patch contrôlé par l’appelant. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permettait à un patch conçu à cet effet de créer un lien symbolique puis d’écrire au-delà de l’arborescence de travail, même si la commande n’acceptait pas `--unsafe-paths`. Vérifiez la règle d’arguments sudo effective, la source du patch, l’accès au répertoire de travail pour le compte RunAs et la correction de Git installé ou le rétroportage du fournisseur. Une règle sans restriction qui accepte `--unsafe-paths` présente un risque distinct lié à cette option explicite ; ni une version de Git ni une autorisation `git apply`, à elle seule, ne prouve qu’un fichier protégé peut être modifié. N’appliquez pas de patch non fiable pendant l’énumération passive.
- Une règle sudo root pour `clamscan --debug` peut franchir une frontière de lecture si un utilisateur moins privilégié peut fournir une image DMG et que l’analyseur installé est affecté par [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), qui pouvait divulguer le contenu des fichiers dans la sortie de débogage. Confirmez les arguments et le chemin d’analyse autorisés, le contrôle de l’entrée, le compte RunAs effectif, le correctif ou rétroportage du moteur et la visibilité de la sortie pour l’appelant. Si une règle plus large autorise `--file-list`/`-f`, examinez séparément le comportement de cette liste ; une politique fixée à `--debug <scan-path>` ne l’autorise pas. Examinez la politique et les métadonnées des paquets sans analyser de fichier conçu à cet effet ni afficher de sortie protégée pendant l’énumération.
- Une règle sudo root qui ouvre une image disque chiffrée sélectionnée par l’appelant et une seconde règle qui monte le mapper obtenu peuvent importer des fichiers contrôlés par l’appelant dans l’espace de noms de montage de l’hôte. Confirmez les deux règles effectives et leurs arguments, le contrôle de l’image et du nom du mapper, la cible réelle du montage ainsi que le propriétaire et le mode des fichiers résultants. Une transition set-user-ID exige aussi un exécutable accessible, des options de montage qui la respectent (`nosuid` la bloque) et une politique de processus ou MAC applicable ; ouvrir ou monter une image n’est qu’une piste. Une voie distincte passant par une sauvegarde existante exige sa véritable clé et un secret utile lisible à l’intérieur. Examinez la politique et les chemins sans ouvrir ni monter d’image pendant l’énumération passive. Voir le [manuel de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) et les [options de montage](https://man7.org/linux/man-pages/man8/mount.8.html).
- Une règle sudo root pour un script shell ou Python mérite un examen du répertoire de travail si le script invoque `./helper` sans d’abord se placer dans un répertoire fixe. Une liste Python telle que `['./helper']` passée à `subprocess.run` peut avoir le même comportement dépendant du répertoire de travail choisi par l’appelant. Celui-ci peut choisir un répertoire modifiable et y placer un exécutable portant ce nom relatif ; un chemin absolu ailleurs dans le script ne protège pas cet appel. Confirmez la règle effective, `runchdir` ou toute autre politique de changement de répertoire, le flux du script et l’atteignabilité de la branche, l’existence d’un répertoire modifiable et exécutable, ainsi que les restrictions de montage/`NOEXEC` avant de conclure à une exécution de code. Si le script est illisible, son comportement reste inconnu jusqu’à ce que son code soit examiné par une voie autorisée. Examinez les scripts statiquement au lieu d’exécuter le helper. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) décrit la politique de répertoire de travail.
- Un validateur Python fixe pouvant s’exécuter en tant que root peut quand même évaluer un fichier de données choisi par l’appelant. [La documentation de `eval()` de Python met en garde contre les entrées non fiables](https://docs.python.org/3/library/functions.html#eval) : une vérification de suffixe, un préfixe arithmétique ou une branche de validation ne constitue pas un bac à sable si le reste de l’expression arrive jusqu’à `eval`. Confirmez la règle sudo effective, la possibilité pour l’appelant de choisir et contrôler le fichier exact, les conditions de branche de l’analyseur et la construction de l’expression, ainsi que l’identité du processus privilégié avant de considérer cela comme une voie d’exécution. La présence de `eval` dans un script lisible n’est qu’un indice ; examinez le code source et les permissions du fichier sans exécuter le validateur ni soumettre d’expression de test pendant l’énumération.
- Un wrapper Ruby sudo effectif pour root qui lit un nom de fichier YAML relatif, tel que `YAML.load(File.read("dependencies.yml"))`, peut utiliser le répertoire de travail de l’appelant comme source d’entrée, à moins que le wrapper ou la politique sudo ne fixe ce répertoire. Vérifiez précisément les arguments autorisés, les permissions du répertoire et du fichier, ainsi que le comportement de Psych installé : les anciennes implémentations de `YAML.load` pouvaient désérialiser des objets Ruby arbitraires, tandis que les versions récentes restreignent les classes par défaut. Un appel statique n’est qu’une piste ; confirmez que le fichier provient réellement d’un répertoire modifiable par l’appelant et que le chargeur installé accepte les classes dangereuses. Préférez `safe_load` avec une liste d’autorisation minimale et explicite de classes pour les entrées non fiables. Voir la [documentation de Psych pour Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) et la [documentation de Psych pour Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Une autorisation sudo exacte pour root sur `sudo go run /absolute/file.go` mérite un examen du répertoire de travail si le code Go lit un fichier WASM relatif et peut exécuter un script shell relatif après inspection du résultat. Confirmez l’utilisateur RunAs effectif, les arguments et refus de commande, l’existence d’un répertoire courant modifiable par l’appelant, le flux des données WASM jusqu’à la branche et l’éventuel appel au helper par cette branche. Un `runchdir` sudo fixe, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) peut modifier l’emplacement de recherche. Une cooccurrence statique n’est qu’une piste ; examinez le code source sans exécuter Go, WASM ou le helper.
- `sudoedit` et les jokers d’arguments exigent de vérifier précisément la version et la règle ; la [liste de contrôle](linux-privilege-escalation-checklist.md) comprend le problème de modification de fichiers avec sudoedit. Pour une autorisation `sudoedit` inter-utilisateurs sur un chemin avec joker, examinez le paramètre effectif `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, la cible résolue et les personnes pouvant remplacer chaque entrée parente. Le premier peut autoriser le suivi d’un lien symbolique, tandis que la désactivation du second supprime les vérifications des répertoires modifiables ; aucun de ces paramètres ne prouve à lui seul qu’un fichier d’un autre utilisateur peut être modifié. Confirmez la politique sudo installée et les arguments exacts correspondants avant de conclure. Voir les [définitions des options sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Dans une règle de commande sudoers, un joker d’argument peut correspondre aux espaces autant qu’aux caractères de chemin. Une règle pour une commande capable de lire des fichiers avec un argument tel que `/restricted/*` peut donc autoriser un argument de fichier supplémentaire après un préfixe correspondant. Examinez l’utilisateur d’exécution exact, le chemin de commande, le motif d’arguments et les refus ultérieurs ; la démonstration d’une lecture de fichier n’implique pas une exécution de commande. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue les jokers d’arguments des jokers de chemin de commande.
- Un motif de joker d’argument qui semble désigner un chemin peut aussi correspondre à `../`. Par exemple, une règle root pour `node /opt/scripts/*.js` peut autoriser un fichier JavaScript contrôlé par l’appelant en dehors de `/opt/scripts` si le chemin fourni commence toujours par `/opt/scripts/` et est résolu avec des segments de répertoire parent. Il s’agit d’un joker d’**argument** ; les règles de correspondance des slashs diffèrent pour le joker du chemin de commande de l’exécutable Node. Vérifiez la règle effective, les refus ultérieurs, la résolution du chemin, le contrôle du fichier cible et les restrictions sudoers éventuelles par expression régulière ou empreinte avant de conclure à une exécution de code. Voir les [règles de jokers sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) et la [documentation de la ligne de commande Node](https://nodejs.org/api/cli.html).
- Les archiveurs et autres programmes utilitaires peuvent disposer de hooks d’exécution. Vérifiez les arguments exacts autorisés par rapport à [GTFOBins](https://gtfobins.github.io/) plutôt que de supposer que seuls les shells ou les interpréteurs exécutent des commandes.
- Une règle `qpdf` sans restriction pour root peut exposer un fichier privilégié via des pièces jointes PDF : qpdf 10.2 et versions ultérieures prennent en charge `--empty` et `--add-attachment file ... --` avec un PDF de sortie. Si le processus privilégié peut lire la source sélectionnée et écrire le PDF à un emplacement accessible à l’appelant, cette sortie peut contenir les octets de la source. Examinez les arguments et exclusions sudo effectifs, la version de qpdf, l’accès à la source et le chemin de sortie avant de conclure à une divulgation possible. La lecture d’une clé SSH root n’est utile pour se connecter que si la clé est valide et que l’authentification SSH de root est autorisée. Voir les [options de pièces jointes de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La réutilisation des horodatages sudo dépend de la politique du cache, de l’utilisateur propriétaire, du terminal/de la session et des permissions. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) décrit les vérifications à effectuer.
- `doas` a ses propres règles et sa propre configuration. Vérifiez les commandes autorisées et les chemins de configuration modifiables comme décrit dans la [section doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Outils de compilation et de paquetage exécutés via sudo

Une autorisation sudo sans restriction pour `forge` de Foundry peut être importante même si l’identité RunAs est un autre utilisateur non-root. Des options de compilateur telles que `--use` peuvent sélectionner un exécutable local, et `forge flatten -o` sélectionne un fichier de sortie. Vérifiez la version de Forge installée, les arguments sudo exacts, l’accessibilité du projet et des chemins du compilateur, les permissions de sortie et l’environnement effectif avant de considérer cette autorisation comme exploitable. Un exécutable helper relatif trouvé via `PATH` est une voie dépendante de la version et de l’environnement, pas une propriété à supposer pour chaque compilation Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Une autorisation `pacman` sans restriction pour root permet davantage que des requêtes de paquets : `-U` accepte un paquet local, les paquets peuvent contenir des scripts d’installation et `--hookdir` sélectionne un autre répertoire de hooks. Examinez la règle sudo effective, les restrictions d’arguments et les exclusions avant tout test ; l’énumération passive ne nécessite ni l’installation d’un paquet ni l’exécution d’un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell sudo fixe peut aussi installer une dépendance npm nommée puis démarrer une application Node. Examinez précisément sa règle RunAs, si le paquet est déjà installé, les valeurs effectives de `HOME` et `npm userconfig`, les substitutions de configuration du projet ou de la ligne de commande, ainsi que le contrôle éventuel du registre ou du paquet retourné pour ce nom par un utilisateur moins privilégié. [npm documente la recherche de `.npmrc` par utilisateur et par projet](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/) ; la valeur de `HOME` utilisée par sudo dépend de la politique installée et de la distribution : le processus npm privilégié peut donc lire ou non le fichier `.npmrc` d’un utilisateur modifiable. Si le paquet nouvellement installé est importé par l’application privilégiée, son code de module peut s’exécuter sous l’identité de cette application. Les scripts d’installation constituent une voie distincte qui dépend de la version et de la configuration ; [npm documente leur cycle de vie et la gestion des utilisateurs](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un chemin `.npmrc` ou une ligne `npm install`, à lui seul, n’est qu’une piste. Examinez la règle, le wrapper court, les chemins de configuration et la provenance du paquet sans installer ni démarrer l’application pendant l’énumération passive.

Une autorisation sudo root pour `pip` ou `pip3 download` est aussi un indice à examiner du côté de la compilation de paquets lorsque ses arguments permettent à l’appelant de sélectionner une distribution source non fiable, même si le motif d’URL la limite à un service local et à un suffixe `.tar.gz`. `pip download` accepte les URL d’archives et résout les métadonnées du paquet ; la préparation d’une distribution source peut invoquer son backend de compilation ou son code `setup.py` historique avant même que l’archive ne soit simplement enregistrée. Confirmez l’utilisateur RunAs et la règle d’arguments sudo exacts, la possibilité pour l’appelant de publier ou remplacer l’archive sélectionnée et si cette version de pip prépare effectivement ses métadonnées. Une archive de confiance fixe ou une wheel ne suffit pas à établir cette voie. Ne récupérez ni ne compilez de paquet non fiable pendant l’énumération passive. Voir la [commande download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), l’[interface du système de compilation](https://pip.pypa.io/en/stable/reference/build-system/) et les [recommandations d’installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Une règle sudo autorisant `pip install` avec un chemin de projet local choisi par l’appelant crée une frontière de compilation plus directe. [pip accepte les répertoires de projets locaux](https://pip.pypa.io/en/stable/topics/local-project-installs/) et invoque leur système de compilation ; le [backend de compilation exécute des hooks de compilation contrôlés par le projet](https://pip.pypa.io/en/stable/reference/build-system/). Confirmez l’identité RunAs effective, les restrictions et refus d’arguments exacts, le contrôle du projet sélectionné et le comportement du pip/backend installé avant de considérer cette règle comme une exécution de code privilégiée. Un projet de confiance fixe ou une règle qui exclut les chemins choisis par l’appelant ne suffit pas à établir cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération passive.

Une autorisation `easy_install` sans restriction pour root est un indice connexe lié aux anciennes compilations de paquets. [Setuptools indique](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install accepte un répertoire de projet local et compile les distributions source ; un projet contrôlé par l’appelant peut exécuter son `setup.py` pendant cette compilation sous l’identité sudo. Confirmez le compte RunAs effectif, la commande et les restrictions d’arguments exactes (y compris les refus ultérieurs), le contrôle du projet sélectionné et le comportement de l’outil installé. Un projet de confiance fixe ou une politique qui n’autorise pas une source choisie par l’appelant ne suffit pas à établir cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération.

Un wrapper Python autorisé par sudo qui utilise `setuptools.package_index.PackageIndex.download` avec une URL choisie par l’appelant constitue un cas d’examen différent de `pip download` : [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) décrit un nom de fichier dérivé de l’URL qui pouvait sortir du répertoire de téléchargement prévu et permettre une écriture avec les permissions du processus dans les versions affectées antérieures à 78.1.1. Confirmez l’utilisateur RunAs et la règle d’arguments sudo effectifs, que le wrapper transmet l’URL de l’appelant à cette API précise, la version installée ou le rétroportage du fournisseur, ainsi que la résolution du chemin obtenu. Une chaîne de version ou un répertoire de téléchargement modifiable ne suffit pas à établir une écriture arbitraire. Examinez le wrapper court et les métadonnées du paquet sans récupérer l’URL ni écrire de fichier pendant l’énumération.

Un wrapper de compilation autorisé par sudo qui transmet à PyInstaller un fichier `.spec` choisi par l’appelant nécessite le même examen de frontière de confiance. Un fichier spec PyInstaller est du Python exécutable évalué pendant la **compilation**, et ses entrées `datas` peuvent intégrer à l’artefact des fichiers lisibles par l’identité de compilation. Confirmez l’utilisateur RunAs exact, les règles d’arguments et de refus sudo, la gestion des chemins et des branches du wrapper, le contrôle du fichier spec sélectionné et l’accès à l’artefact résultant. Autoriser simplement une entrée `.py` ou constater que PyInstaller est installé ne prouve ni le contrôle du fichier spec ni une exécution privilégiée. Un examen passif doit se limiter à lire un wrapper de taille raisonnable et ses métadonnées ; il ne doit pas lancer de compilation. Voir la [documentation des fichiers spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Chargeurs de préréglages et de plugins exécutés via sudo

Les outils Python qui acceptent un préréglage ou un répertoire de plugins choisi par l’appelant peuvent importer du code avec les privilèges accordés par sudo. Par exemple, BBOT accepte un préréglage avec `-p`, et sa [documentation sur les modules personnalisés](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) décrit les entrées `module_dirs` qui sélectionnent d’autres répertoires de modules Python. Si la règle sudo effective autorise un préréglage choisi par l’appelant et que celui-ci contrôle un module dans le répertoire sélectionné, l’import peut exécuter du code en tant qu’utilisateur privilégié, éventuellement avant que l’outil ne rejette un module invalide. Vérifiez la version installée, la politique exacte sudo d’utilisateur d’exécution et d’arguments, ainsi que la propriété du préréglage et des chemins de modules, sans charger le module pendant l’énumération.

### Outil en ligne de commande Backdrop exécuté via sudo

[Bee](https://github.com/backdrop-contrib/bee) est un outil PHP en ligne de commande pour Backdrop CMS. Ses commandes `eval` (`php-eval`) et `php-script` peuvent exécuter du PHP fourni par l’appelant. Une règle sudo qui autorise l’exécutable Bee en tant que root avec des arguments sans restriction peut donc exposer l’exécution de code root lorsque Bee peut initialiser une installation Backdrop. Lancez-le depuis le répertoire du site ou sélectionnez un site à l’aide de l’option globale `--root=<directory>` ; trouver Bee ou un fichier Backdrop `settings.php` ne prouve ni l’autorisation sudo, ni l’existence d’un site utilisable, ni la réussite de l’initialisation. Examinez la règle sudo effective, les exclusions de commande éventuelles, l’identité de l’exécutable et l’accès au site avant tout test. Pendant l’énumération passive, examinez la règle et les chemins de fichiers sans invoquer Bee. Voir le [journal des modifications des commandes Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) pour l’ajout des commandes PHP.

### Serveurs de terminaux exécutés via sudo

`mosh-server` démarre un serveur de terminal interactif sous l’identité de l’utilisateur qui l’invoque. Il choisit un port UDP élevé et une clé de session, indique les deux à l’appelant et lance normalement le shell de connexion de cet utilisateur lorsqu’un client se connecte. Une autorisation sudo root sans restriction pour `mosh-server` est donc à examiner comme une possibilité de shell, même si la commande du serveur se détache. Vérifiez l’identité RunAs effective, les arguments et exclusions autorisés, le binaire installé, le shell, la disponibilité du client et l’accès UDP. Une énumération passive doit examiner la règle sudo sans démarrer de serveur ni afficher de clé de session active. Voir le [manuel du serveur Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) et les [notes de conception en amont](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de sauvegarde privilégiés qui réécrivent le fichier de tâches de l’appelant

Un wrapper shell exécuté en tant que root peut accepter un fichier de tâches choisi par l’appelant, supprimer `../` des chemins source, vérifier que chaque résultat commence par un répertoire autorisé, réécrire le fichier de tâches, puis transmettre son *chemin* à un programme de sauvegarde. Examinez le chemin transformé après résolution canonique complète : une seule passe de remplacement de chaîne peut révéler une nouvelle séquence de traversée acceptée par une vérification lexicale du préfixe. Vérifiez aussi si le programme de sauvegarde lit les données transformées en mémoire ou rouvre le fichier. S’il le rouvre, une réécriture échouée peut laisser l’entrée d’origine en place.

Sous Linux, `fs.protected_regular` peut refuser une écriture `O_CREAT` dans le fichier ordinaire d’un autre utilisateur situé dans un répertoire sticky accessible en écriture à tous. Ce refus est une protection, mais un wrapper shell qui ignore l’erreur d’écriture peut tout de même continuer avec le fichier de tâches d’origine. Vérifiez ce paramètre, le propriétaire du fichier et du répertoire, ainsi que l’arrêt éventuel du wrapper en cas d’échec. Le chemin ne constitue un candidat à la divulgation de fichiers que si la règle sudo effective autorise le wrapper pour un utilisateur privilégié, si l’appelant contrôle l’entrée des tâches et une destination de sauvegarde lisible, et si l’utilitaire de sauvegarde inclut effectivement les sources protégées. Examinez ces conditions sans lancer la sauvegarde pendant l’énumération.

### Jokers d’arguments dans les outils réseau privilégiés

Dans une règle sudo pour `tcpdump`, un `*` dans le **motif d’arguments** peut correspondre aux espaces et aux slashs ; une restriction qui semble désigner un chemin peut donc autoriser du texte d’option supplémentaire. Cela diffère d’un joker dans le chemin de l’exécutable de la commande ; examinez la règle RunAs complète et les éventuels refus ultérieurs. Si des options peuvent être injectées, l’invocation autorisée et la [sémantique des options de `tcpdump` installé](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) déterminent si `-F`, `-V`, `-r`, `-w` ou `-Z` fournit une primitive utile de lecture/écriture. `-V` lit une liste de noms de fichiers de capture, pas un dump généraliste de fichier arbitraire. AppArmor ou une autre politique MAC peut bloquer l’accès aux fichiers même si sudo autorise la commande ; un fichier de profil présent sur le disque ne prouve pas qu’il est chargé ou appliqué. Examinez passivement l’autorisation et la politique avant de conclure. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) décrit la distinction entre ces jokers.

Une règle sudo root qui ne liste que l’exécutable `tcpdump`, sans restriction d’argument, mérite aussi un examen. Le [manuel de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) décrit `-z` comme une commande exécutée après la rotation lorsque `-C` ou `-G` fait tourner une capture enregistrée ; `-Z` ou une valeur par défaut définie à la compilation peut faire abandonner les privilèges avant l’exécution de cette commande. Vérifiez la règle sudo effective, la compilation installée, le comportement d’abandon des privilèges et la possibilité d’une rotation avant de considérer cette règle comme une voie d’escalade. Une règle mise en évidence est une piste, pas une preuve d’exécution de commande root.

### Wrappers Nmap exécutés via sudo

Lorsqu’un chemin `nmap` autorisé par sudo correspond à un wrapper shell, examinez le chemin exact autorisé et chaque option qu’il transmet. Bloquer l’option connue `--script` ne bloque pas nécessairement le chargement de code NSE : [`--datadir`](https://nmap.org/book/man-misc-options.html) de Nmap sélectionne les fichiers de données, et NSE [charge `nse_main.lua`](https://nmap.org/book/nse-implementation.html) depuis le répertoire de données sélectionné lorsque le scripting est activé. Certaines versions installées acceptent aussi d’autres formes d’options longues ; comparez donc les restrictions à l’analyseur réel de ce binaire. [`--excludefile`](https://nmap.org/book/man-target-specification.html) constitue une surface distincte de lecture de fichier ; des erreurs d’analyse peuvent en divulguer le texte. Vérifiez la règle sudo effective, la logique du wrapper, la version de Nmap, le contrôle du répertoire et la politique MAC sans lancer de scan pendant l’énumération.

### Hooks de `hg pull` exécuté via sudo

Une source fixe dans `sudo hg pull /fixed/source` laisse tout de même le dépôt **receveur** être sélectionné par le répertoire de travail courant, sauf si la commande le fixe avec `-R`. Un dépôt receveur contrôlé par l’appelant peut définir des hooks dans `.hg/hgrc`, et un hook peut s’exécuter en tant qu’utilisateur RunAs sudo. [Mercurial ignore la configuration d’un dépôt appartenant à un utilisateur ou groupe non fiable](https://mercurial-scm.org/help/topics/config) ; examinez donc les utilisateurs/groupes de confiance du compte RunAs et le répertoire de travail exact avant de conclure à une exécution de code. La lecture de la politique et de la configuration suffit à un examen passif ; n’effectuez pas de pull et n’invoquez pas de hook pour l’énumérer.

### Hooks de `git pull` exécuté via sudo

Pour une autorisation sudo exacte de `git pull` en tant que root, vérifiez aussi le dépôt **receveur** sélectionné par le répertoire de travail. Un dépôt appartenant à l’appelant peut contenir un hook `post-merge` exécutable qui s’exécute avec l’identité du processus Git lorsqu’un pull effectue une fusion réussie ; [Git documente ce hook](https://git-scm.com/docs/githooks) ainsi que [le comportement de pull en mode merge ou rebase](https://git-scm.com/docs/git-pull). Vérifiez la règle sudo effective et le répertoire courant, le chemin et les permissions du hook actif, ainsi que la possibilité d’effectuer une fusion avec de nouveaux commits. Un pull échoué, sans effet ou qui n’effectue qu’un rebase ne prouve pas cette voie par hook. Examinez la politique et les métadonnées du dépôt sans effectuer le pull privilégié.

### Copies d’archives rsync exécutées via sudo

Pour `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` dans le **motif d’arguments sudoers** peut correspondre aux espaces et autoriser une option supplémentaire entre la source et la destination. Cela diffère de l’expansion des noms de fichiers par le shell. Si l’appelant peut remplir la source et si la destination est modifiable par le processus rsync privilégié, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) peut demander un propriétaire privilégié tandis que le mode archive préserve les bits de permission, ce qui peut créer un fichier SetUID appartenant à ce propriétaire. Vérifiez la sémantique exacte des [jokers sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la version de rsync, les refus ultérieurs, l’option `nosuid` du système de fichiers et la politique MAC. Une règle correspondante est une piste, pas la preuve d’une escalade de privilèges réussie.

### Export des règles de filtrage de paquets exécuté via sudo

Une autorisation root sans restriction pour `iptables` et `iptables-save` (ou la paire correspondante `ip6tables`) mérite un examen du chemin d’écriture de fichier. Le match `comment` accepte du texte de règle choisi par l’appelant, tandis que `iptables-save -f` écrit le jeu de règles sérialisé dans un chemin choisi.<sup>[[20]](#references)[[21]](#references)</sup> L’utilité d’une charge dépend de la façon dont le backend installé sérialise les commentaires et de la possibilité pour le fichier de destination d’accepter d’autres lignes dans l’export ; `iptables-save` seul ne fournit pas de contenu arbitraire choisi par l’appelant. Vérifiez l’identité RunAs sudo exacte, les arguments et exclusions, l’extension de match disponible, le backend et les permissions de destination. Pendant l’énumération, examinez l’autorisation sans modifier les règles de pare-feu ni écrire de fichier.

### Répertoire de journalisation privilégié de Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) affectait les versions de Below antérieures à 0.9.0 qui créaient un répertoire `/var/log/below` modifiable par tous. Si un service ou une commande sudo autorisée exécute en tant que root une version affectée, un utilisateur pouvant écrire dans un répertoire de journaux non sticky et le parcourir peut remplacer une entrée de journal par un lien symbolique avant que le processus privilégié ne l’ouvre. Examinez l’état des correctifs du paquet installé, le chemin exact d’exécution privilégiée, l’accès effectif au répertoire, le sticky bit et les ACL, ainsi que les métadonnées de `/var/log/below/error_root.log`. Un chemin modifiable par tous ou une règle sudo, à elle seule, ne suffit pas à établir toute la chaîne. Un répertoire sticky ou un rétroportage du fournisseur change l’évaluation. Une énumération passive doit se limiter à examiner les métadonnées ; il n’est pas nécessaire de créer un lien ni d’exécuter le programme privilégié.

### Collecte privilégiée de lots de support à partir d’entrées modifiables

Un script de profil de support autorisé par `sudo` peut lire des chemins de journaux fixes en tant que root et copier leur contenu dans une archive de profil. Examinez le script pour repérer les lectures de fichiers, puis vérifiez si l’appelant peut remplacer un chemin source ou une entrée de répertoire parent par un lien symbolique. Si la lecture privilégiée suit ce lien et que l’archive résultante est lisible par l’appelant, un fichier protégé peut être divulgué. L’autorisation sudo, le chemin source modifiable, la lecture privilégiée et la sortie lisible doivent tous être présents ; un journal ou un nom de profil modifiable ne suffit pas. Examinez les permissions effectives et les métadonnées des liens sans remplacer de fichiers ni générer de profil pendant l’énumération. Les [instructions d’assistance Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentent son script de profil exécuté en tant que root et son archive de sortie, illustrant la nécessité de restreindre les entrées et l’accès à la sortie de tels lots.

### Scripts de restauration d’archives Python exécutés en tant que root

Une règle sudo très ciblée pour un script Python de restauration nécessite tout de même d’examiner son archive d’entrée. Si l’appelant peut sélectionner ou remplacer l’archive et que le script l’extrait en tant que root avec `tarfile.extractall(filter="data")`, vérifiez les mises à jour de sécurité de l’interpréteur avant de faire confiance à ce filtre. CPython a corrigé plusieurs contournements de filtre liés aux liens symboliques et durs, notamment CVE-2025-4517, dans les versions 3.9.23, 3.10.18, 3.11.13, 3.12.11 et 3.13.4. Les distributions peuvent rétroporter les correctifs vers des versions antérieures ; la version affichée de l’interpréteur ne prouve donc pas à elle seule l’exposition.<sup>[[16]](#references)[[17]](#references)</sup>

Pour un examen passif, lisez la commande sudo et le script exacts, suivez l’argument qui sélectionne l’archive et vérifiez si l’utilisateur courant peut écrire dans l’archive ou son répertoire parent. Confirmez séparément le correctif du fournisseur installé et la destination de l’extraction ; `filter="data"` ne rend pas toute archive non fiable sûre.<sup>[[16]](#references)[[17]](#references)</sup>

### Chargeurs de modèles d’apprentissage automatique exécutés via sudo

Une règle sudo qui autorise un fichier `.pt`, `.pth` ou `.ckpt` choisi par l’appelant mérite un examen si un script privilégié transmet ce fichier à [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou à un autre chargeur fondé sur pickle. Vérifiez la règle RunAs sudo effective, la possibilité pour l’appelant de créer ou remplacer le modèle sélectionné et le flux réel de l’argument dans le helper Python, en passant par tout wrapper shell. L’extension `.pth` désigne aussi des fichiers de configuration Python site sans rapport ; l’extension seule ne prouve pas qu’il s’agit d’un chargement de modèle. Un scan d’archive ou un scan statique de pickle ne prouve pas que le chargement ultérieur est sûr ; examinez le comportement de [`weights_only`, qui dépend de la version](https://docs.pytorch.org/docs/stable/notes/serialization.html) et toute liste d’autorisation. Voir les [notes sur les pickles ML et Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Une énumération passive ne doit jamais charger ni décompresser le modèle.

### Analyse d’expression de données stockées exécutée via sudo

Un script Python fixe exécuté en tant que root via sudo peut tout de même évaluer du texte qu’un utilisateur moins privilégié peut stocker dans une base de données d’application. Dans TensorFlow, un appel à `preprocess_input_exprs_arg_string(value, safe=False)` choisit une voie passant par `eval` ; [l’avis de sécurité TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) décrit l’analyseur non sûr et un correctif appliqué à son appelant en ligne de commande. Un appel explicite de l’application à `safe=False` nécessite un examen séparé, même si cet appelant en ligne de commande est corrigé. Vérifiez la règle sudo effective, qui peut modifier l’enregistrement exact, si le filtrage ou la notation permet à cet enregistrement d’atteindre l’appel, ainsi que le comportement de la fonction installée. Une version de TensorFlow, une autorisation sudo ou un fichier de modèle codé en dur, pris isolément, ne prouve pas la chaîne. Examinez passivement le script et le flux de données ; n’exécutez pas le helper privilégié et ne soumettez pas d’expressions de test pendant l’énumération.

### Configuration de needrestart autorisée par sudo

`needrestart -c` charge un fichier de configuration Perl choisi par l’appelant et en évalue le contenu. Si `sudo -l` autorise `needrestart` en tant que root avec des arguments permettant `-c`, et si l’appelant peut choisir un fichier de configuration lisible situé dans un emplacement modifiable, cette autorisation peut mener à l’exécution de code root. Vérifiez précisément la règle sudo relative à l’utilisateur d’exécution et aux arguments ; une règle autorisant uniquement une liste fixe d’arguments peut bloquer cette voie. Cela est distinct des vulnérabilités de needrestart lors de l’analyse des interpréteurs : mettre à jour le paquet ou désactiver `interpscan` ne rend pas sûre une autorisation root sans restriction de `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python exécutés via sudo sous un autre compte

Un point d’entrée Python fixe peut tout de même importer un module que l’appelant peut modifier ou remplacer, y compris lorsque sudo exécute le script en tant qu’utilisateur de service **non-root**. Pour un `from utils import status` littéral, examinez `utils/__init__.py` et `utils/status.py` locaux, ainsi que les permissions du répertoire du paquet. Confirmez le chemin d’importation du script, les arguments sudo exacts autorisés et la possibilité que l’action concernée atteigne cet import avant de considérer le fichier modifiable comme une voie d’exécution. Examinez les fichiers et permissions sans importer ni exécuter le script pendant l’énumération.<sup>[[2]](#references)[[3]](#references)</sup>

Une règle sudo exacte pour `python3 /absolute/script.py` exige seulement que le script soit lisible ; il n’a pas besoin d’être exécutable ni d’avoir un shebang. Examinez aussi les modules locaux **manquants** : si le script importe un module dont le nom de fichier peut être créé dans un répertoire de script modifiable par l’appelant, Python peut charger ce fichier sous l’identité RunAs. Confirmez la règle sudo effective, le [chemin de recherche de modules](https://docs.python.org/3/library/sys_path_init.html) réel de l’interpréteur, si le module est intégré ou figé, et si l’import est atteint. Une règle sudo directe pour le script a d’autres exigences concernant le bit d’exécution et le shebang. Un wrapper distinct qui ajoute des jetons fournis par l’appelant après `sudo -u account` nécessite aussi d’examiner le flux des arguments : un autre `-u` dans ces jetons n’a d’importance que si la politique sudo appelée autorise l’identité résultante. Des chaînes statiques ne prouvent ni l’une ni l’autre de ces voies.

### Apache exécuté via sudo avec une configuration contrôlée par l’appelant

Si une règle sudo autorise `apachectl`, `apache2ctl` ou `httpd` privilégié avec un fichier de configuration `-f` contrôlé par l’appelant, examinez ce fichier et les permissions de son répertoire parent. La directive Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) prend un nom de module suivi du **nom de fichier du module** ; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) charge aussi un fichier. [`Include` et `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) peuvent étendre la configuration ou exposer du contenu de fichier via des erreurs. Un wrapper personnalisé peut valider ces chemins, abandonner les privilèges ou restreindre les arguments : une configuration modifiable est donc une piste, pas une preuve d’exécution de code. Vérifiez la canonicalisation des chemins, les liens symboliques et l’analyse des directives avant de conclure.

### nginx exécuté via sudo avec une configuration contrôlée par l’appelant

Une règle `nginx` root sans restriction peut permettre à [`-c` de sélectionner une autre configuration](https://nginx.org/en/docs/switches.html). Examinez les arguments et exclusions sudo exacts, la possibilité pour l’appelant de fournir la configuration et l’accès éventuel du master ou des workers résultants aux chemins protégés. Un `root` choisi avec `autoindex` peut exposer des fichiers via un nouveau listener ; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) peut fournir un chemin d’écriture de fichier privilégié, mais le module DAV n’est pas compilé par défaut : vérifiez sa présence, l’accessibilité du listener, les permissions des fichiers et le comportement des fichiers temporaires. La directive [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) peut aussi cibler un fichier choisi ; écrire des journaux dans un fichier de configuration sensible, tel que `/etc/ld.so.preload`, exige un écrivain privilégié effectif et un enregistrement de journal contrôlable avant de constituer une voie d’escalade. La mise en évidence de l’exécutable dans `sudo -l` n’est qu’un indice, pas la preuve que l’une de ces voies fonctionne. Une énumération passive ne doit ni démarrer ni reconfigurer nginx.

### Comparaison de motifs dans les invites Bash privilégiées

Lorsqu’un script Bash autorisé par sudo lit une valeur fournie par l’appelant et la vérifie avec `[[ "$expected" == $entered ]]`, Bash interprète l’opérande droit non protégé par des guillemets comme un motif. Un joker peut donc satisfaire la comparaison sans connaître la valeur attendue. Protéger l’opérande par des guillemets (`[[ "$expected" == "$entered" ]]`) en fait une comparaison littérale de chaînes. Examinez la règle sudo exacte, l’accessibilité de l’invite et ce que fait le script après la comparaison ; la syntaxe, à elle seule, ne prouve pas l’existence d’une voie exploitable. Évitez d’afficher la valeur attendue pendant l’énumération. Voir la [référence des constructions conditionnelles Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers exécutés via sudo qui téléchargent et exécutent un fichier

Une autorisation sudo root sans restriction pour un helper personnalisé mérite un examen du flux de données s’il accepte une URL choisie par l’appelant, écrit la réponse sur disque puis invoque ce fichier avec un interpréteur ou un shell. [Sudoers autorise des arguments arbitraires lorsqu’une entrée de commande n’en précise aucun](https://man7.org/linux/man-pages/man5/sudoers.5.html) ; un chemin d’exécutable fixe ne limite pas ce que ses arguments peuvent sélectionner. Confirmez la validation réelle de l’URL, le chemin de sortie, la branche de succès et l’exécution ultérieure dans le helper installé. Un import libcurl correspondant ou une chaîne imprimable ne prouve pas à lui seul cette chaîne.

Même un nom de sortie fixe peut être remplacé entre l’écriture et l’exécution lorsque le helper utilise un **chemin relatif dans un répertoire de travail contrôlé par l’appelant**. Le renommage ou le remplacement d’un fichier appartenant à root dépend des droits d’écriture et de parcours du répertoire et des éventuelles restrictions du sticky bit, pas seulement du mode du fichier ; voir [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Vérifiez si le helper rouvre ensuite le chemin ou utilise le descripteur déjà ouvert, et s’il se place dans un répertoire de confiance avant d’écrire. Examinez passivement la politique sudo, le helper et les métadonnées du répertoire ; n’invoquez pas le téléchargement privilégié et ne tentez pas de course pendant l’énumération.

Un helper de téléchargement exécuté en tant que root via sudo peut aussi exposer une injection d’**argument** lorsqu’il construit une chaîne Bash comme `curl <entrée de l’appelant> -o <sortie fixe>`. Un filtre qui rejette les espaces laisse encore l’[expansion d’accolades de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) : des éléments séparés par des virgules, non protégés par des guillemets, peuvent devenir des arguments curl distincts. Si l’entrée arrive à curl avant l’option `-o` fixe, une option de sortie fournie par l’appelant peut sélectionner la destination de la première URL sous l’identité du helper ; [curl associe les options de sortie aux URL dans l’ordre](https://curl.se/docs/manpage.html#-o). Confirmez le shell exact, les guillemets, la validation de l’entrée, la règle sudo effective, l’ordre des arguments curl et les schémas d’URL pris en charge, ainsi que le contrôle éventuel par l’appelant des octets récupérés ou sa possibilité de lire le résultat. Un exécutable empaqueté par PyInstaller peut contenir la logique d’une application Python, mais sa marque d’empaquetage ou une chaîne `curl`, à elle seule, ne prouve pas ce flux de données. Examinez une copie hors ligne de taille raisonnable si cela est autorisé ; l’énumération courante ne doit pas exécuter le helper ni récupérer des données choisies par un attaquant.

Un script shell sudo exécuté en tant que root qui appelle [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) choisit seulement un nom non utilisé ; il **ne crée pas** le fichier. Si le script crée ensuite ce nom dans un répertoire qu’un autre utilisateur peut affecter, le rouvre et ajoute son contenu à une destination protégée telle que le fichier `authorized_keys` de root, examinez le risque de course sur le fichier temporaire. Confirmez la règle sudo exacte, la propriété du répertoire et du fichier, la séquence de création et de réouverture, les protections du noyau et si l’écriture privilégiée utilise réellement des octets contrôlés par l’attaquant. Une chaîne `mktemp -u` ou la seule présence d’un `/tmp` modifiable ne prouve pas l’existence de la course. Examinez le script et les métadonnées des chemins sans l’exécuter ni provoquer de course sur son fichier temporaire pendant l’énumération.

## Notes défensives

- Évitez d’autoriser des interpréteurs ou des éditeurs interactifs via sudo.<sup>[[1]](#references)</sup>
- Préférez des wrappers fixes appartenant à root qui exécutent une seule action administrative étroitement définie.<sup>[[1]](#references)[[2]](#references)</sup>
- Si un interpréteur est incontournable, restreignez le chemin exact du script et empêchez les arguments contrôlés par l’utilisateur, les imports modifiables, `PYTHONPATH` et la préservation non sûre de l’environnement.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si la modification de fichiers est nécessaire, restreignez précisément le chemin du fichier et envisagez `sudoedit` avec des versions corrigées de sudo et une gestion stricte de l’environnement.<sup>[[1]](#references)[[2]](#references)</sup>
- Examinez `SETENV`, `env_keep`, les répertoires de travail modifiables, les chemins de modules/imports modifiables, `NOEXEC`, `use_pty` et la journalisation, sans les considérer comme un bac à sable complet.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
