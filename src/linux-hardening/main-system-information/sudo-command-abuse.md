## Інтерпретатори, дозволені через Sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерпретатор від імені root, вважайте це прямим виконанням коду. Інтерпретатори призначені для виконання довільного коду, тому правило, яке дозволяє запускати `python3`, `perl`, `ruby`, `lua`, `node` або подібні бінарні файли, зазвичай еквівалентне виконанню команд від імені root, якщо аргументи не обмежені та не перевіряються належним чином.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Типовий порядок перевірки: спершу перегляньте привілеї користувача, а потім виконайте інструкцію Python за допомогою параметра інтерпретатора `-c`.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Нижче наведено інші приклади інтерпретаторів; у документації перелічених інтерпретаторів описано виконання inline-коду або API дочірніх процесів.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Точний шлях має значення. Якщо правило sudo дозволяє `/usr/bin/python3`, під час перевірки використовуйте саме цей шлях.<sup>[[2]](#references)</sup>

Glob для виконуваних файлів sudo, наприклад `/usr/bin/python*`, може також дозволяти Python 2 для скрипту, написаного для Python 3. Якщо скрипт викликає `input()` із текстом, контрольованим користувачем, [Python 2 обчислює цей текст як вираз](https://docs.python.org/2/library/functions.html#input); явний виклик інтерпретатора має пріоритет над shebang скрипту. Перш ніж вважати це шляхом до виконання коду, перевірте встановлені бінарні файли, що відповідають шаблону, ефективні RunAs і правила для аргументів, відмови та доступність введення.

Фіксований шлях до скрипту в правилі sudo, яке дозволяє виконання від root, не обмежує те, що запускає скрипт. Якщо Bash-обгортка доступна для читання, перевірте, чи використовує її перша виконувана команда непроцитований позиційний параметр, наприклад `$1`, як **слово команди**, коли sudo дозволяє користувачу самостійно вибирати аргументи. Перевірте ефективну ідентичність RunAs, правила для пароля й аргументів, подальші відмови та фактичну гілку скрипту; результат може змінитися через `NOEXEC`, фіксований безпечний список аргументів або обгортку, яка перевіряє команду. Під час переліку статично перевірте короткий скрипт, а не запускайте його з тестовою командою.

Необмежене правило sudo для `dotnet`, яке дозволяє виконання від root, також варто перевірити з погляду інтерпретатора. Якщо встановлено .NET SDK, [`dotnet fsi` запускає код F# в інтерактивному режимі або зі скрипту](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), а [`dotnet run` виконує проєкт із вихідного коду](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Спершу перевірте ефективну ідентичність RunAs і точні правила для аргументів: правило, закріплене за певною безпечною підкомандою чи довіреною програмою, є іншим дозволом, а інсталяція лише середовища виконання може не містити команд SDK. Сама назва виконуваного файлу — лише привід для перевірки, а не доказ можливості виконання коду.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Редактори, дозволені через sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерактивний редактор від імені root, вважайте це поверхнею для виконання команд, а не нешкідливим дозволом на редагування файлів. Редактори часто можуть виконувати shell-команди, читати довільні файли, записувати довільні файли або запускати зовнішні допоміжні програми з редактора.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Типова послідовність перевірки: перегляньте привілеї користувача, а потім запустіть кожен дозволений редактор або пейджер через sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Виконання команд у Nano

Якщо `nano` дозволено запускати через sudo, виконання команд може бути доступне з інтерфейсу редактора.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Потім введіть команду, наприклад `id` або `/bin/sh`, у командний рядок nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Якщо інтерактивна оболонка не має придатних до використання потоків термінала, ця форма перенаправлення спрямовує її стандартний потік виведення та потік помилок до дескриптора 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Точна послідовність клавіш може відрізнятися залежно від версії nano та параметрів збірки, але проблема безпеки та сама: редактор працює з правами root і може запускати зовнішні команди.<sup>[[1]](#references)[[12]](#references)</sup>

### Інші поширені способи виходу з редактора

Редактори на кшталт Vim зазвичай надають доступ до виконання команд через `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Пейджери, як-от `less`, також можуть надавати доступ до виконання команд оболонки.<sup>[[14]](#references)</sup>

До правила sudo, яке дозволяє запускати `apport-cli` від імені root, слід застосувати таку саму перевірку пейджера. У вразливих версіях Apport звіт про збій міг відкриватися в `less` із розміром термінала, який контролює зловмисник; за певних умов sudo та пейджера той міг надати root shell. Перш ніж вважати версію вразливою, перевірте чинне правило sudo, налаштування пейджера та виправлення пакета у дистрибутиві. Під час пасивного переліку перевіряйте метадані пакета й політики, не створюючи збій і не відкриваючи привілейований звіт. У [записі Ubuntu про CVE](https://ubuntu.com/security/CVE-2023-1326) наведено виправлені версії пакетів для різних релізів, зокрема з backport-виправленнями.

```text
!/bin/sh
```

## Інші небезпеки правил sudo та doas

Почніть із `sudo -l`, `sudo -V` і відповідної політики `doas`. Розглядайте разом дозволену команду, користувача RunAs, аргументи, середовище й параметри за замовчуванням. Дозвіл запускати команди від імені непривілейованого службового облікового запису все одно може відкрити доступ до його файлів або шлях до root.

Фіксований Python-скрипт, дозволений через sudo, усе одно може запускати shell-команду з ідентифікатором RunAs, якщо інтерактивне введення, контрольоване викликачем, конкатенується в [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Чорного списку символів shell недостатньо, щоб гарантувати безпеку: [shell також розпізнає підстановку команд `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Переконайтеся, що дозволені аргументи доходять до гілки введення, введення потрапляє до shell-команди без безпечної перевірки, а ефективна політика sudo дозволяє потрібного користувача RunAs. Шлях до скрипту або сам виклик `os.system()` — лише привід для перевірки; досліджуйте вихідний код, не запускаючи привілейований скрипт.

Ефективний дозвіл sudo від імені root на `chattr` може зняти з файла атрибут immutable (`i`), але сам по собі він не надає права на запис чи нового ідентифікатора. [Посібник `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) зазначає, що цей атрибут блокує зміни, а змінити його може лише root або процес із `CAP_LINUX_IMMUTABLE`. Перевірте точну політику аргументів sudo і підтримку файловою системою, а потім окремо з’ясуйте, чи може викликач записувати у файл після зняття атрибута та чи використовує його споживач із вищими привілеями. Наприклад, заміна login shell також вимагає облікових даних, прийнятних для цільового облікового запису, і фактичного входу через цей shell. Під час переліку перевіряйте політику, атрибути файлів і права доступу, не змінюючи їх.

Якщо sudo запитує і пароль, і одноразовий код, не змішуйте ці передумови з дозволом на команду. Доступний для читання файл `.google_authenticator` містить конфіденційний матеріал seed, тоді як старий хеш пароля програми чи бази даних — лише можливий варіант поточного пароля облікового запису; ні те, ні інше не доводить, що інший фактор приймається ефективною конфігурацією PAM. Після отримання дозволу перевірте точні RunAs та аргументи: необмежений дозвіл запускати RubyGems `gem` від імені root може відкрити його команду редактора ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), але обмежений дозвіл або невдала автентифікація — ні. Пасивний збір даних має повідомляти шляхи й політику, не виводячи seed, не відновлюючи пароль, не генеруючи код і не запускаючи привілейовану команду.

Необмежений дозвіл sudo для `knife` від імені root потребує перевірки на рівні інтерпретатора: [Chef документує, що `knife exec -E` локально виконує рядок Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Переконайтеся, що ефективне правило sudo дозволяє підкоманду `exec` і переданий викликачем аргумент `-E`, потрібний ідентифікатор RunAs, а також перевірте відповідні заборони команд чи фіксовані аргументи. Встановлений бінарний файл або правило, обмежене іншими підкомандами, — лише підказка для перевірки. Пасивний збір даних має повідомляти про правило, не запускаючи `knife`.

Точний дозвіл sudo для інтерактивного `msfconsole` від імені root також потребує уваги: [GTFOBins описує його консоль `irb`](https://gtfobins.org/gtfobins/msfconsole/), яка може успадкувати ідентифікатор sudo. Перевірте ефективного користувача RunAs, дозволений список аргументів, заборони команд, `NOEXEC` чи інші обмеження, поведінку встановленої консолі й те, чи може викликач передавати інтерактивне введення. Саме підсвічування шляху — лише привід для перевірки; під час пасивного збору даних не запускайте консоль.

У FreeBSD навіть правило sudo, обмежене командами `pkg update` і `pkg install *` від імені root, потребує перевірки довіри до репозиторіїв. З’ясуйте, чи може викликач записувати в `/etc/hosts`, і чи використовує *ефективна* конфігурація ввімкнених репозиторіїв HTTP-ім’я хоста з `signature_type: none`. [Посібник FreeBSD з `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) зазначає, що `none` вимикає перевірки підписів; самого `pkg+http` для такого висновку недостатньо. Пакет може містити скрипти встановлення ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), тому викликач, який справді контролює кінцеву точку репозиторію та може вибрати пакет, може перетнути межу привілеїв root. Перш ніж робити такий висновок, перевірте перевизначення репозиторіїв, розв’язання SRV/дзеркал, ефективні аргументи sudo, вибір пакета й виконання скриптів. Переглядайте політику та невеликі локальні конфігураційні файли, не перенаправляючи імена й не запускаючи `pkg` під час збору даних.

Дозвіл sudo запускати `apt-get update` і `apt-get upgrade` від імені root також потребує перевірки довіри до репозиторіїв, якщо sudo зберігає контрольований викликачем `http_proxy`. З’ясуйте, чи справді ефективна конфігурація APT використовує цю змінну й на які запити до ввімкнених репозиторіїв вона може впливати; сам проксі не може підмінити пакети з архіву, автентифікованого довіреним ключем підпису. [Посібник з HTTP-транспорту APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) описує пріоритет проксі, а [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — перевірки підписів, перевизначення для незахищених репозиторіїв і підтвердження для неавтентифікованих пакетів. Перевірте точні RunAs та аргументи sudo, політику автентифікації репозиторіїв, необхідність інтерактивного підтвердження й те, чи запускає вибране оновлення скрипти пакетів від імені root. Переглядайте політику й локальну конфігурацію пасивно; не перенаправляйте трафік пакетів і не запускайте оновлення під час збору даних.

Правило sudo для `snap install` з можливістю запуску від імені root може створити межу між пакетом і кодом, якщо його аргументи дозволяють викликачеві вибрати локальний snap і режим встановлення з послабленими обмеженнями. [Документація Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) зазначає, що `--dangerous` пропускає перевірки assertion локального snap, а `--devmode` послаблює ізоляцію; [hook встановлення може запускатися під час першого встановлення](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Перш ніж стверджувати, що це відкриває доступ до захищених файлів хоста, перевірте точну політику аргументів/RunAs sudo, хто контролює файл snap, чи приймає встановлений snapd ці режими та ідентифікатор і рівень ізоляції hook. Сам бінарний файл `snap` або правило, яке лише на вигляд містить підстановку, не доводить існування цього ланцюжка. Пасивний збір даних не має встановлювати пакет або запускати його hook.

Для точного дозволу sudo на виконання спеціального бінарного файла, що читає облікові дані від імені **не-root** облікового запису, спочатку перевірте дозволи й файл, не запускаючи його. Вбудований запит пароля може бути видимий лише як широкі символи; [GNU `strings` документує отримання рядків у форматі 16-бітного little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Видимий рядок не доводить, що це прийнятний пароль або що гілка успіху відкриває актуальні облікові дані. Окремо перевірте поведінку бінарного файла, доступ цільового облікового запису до захищених даних, чинність облікових даних і будь-який подальший перехід між обліковими записами чи групами. Якщо цей обліковий запис входить до групи `docker`, перевірте доступ до сокета й те, чи працює демон від імені root або без root; перш ніж робити висновок про доступ до root на хості, [ознайомтеся з документацією Docker про наслідки членства в цій групі](https://docs.docker.com/engine/install/linux-postinstall/). Звичайний збір даних має повідомляти про правило sudo й членство в групі, не запускаючи бінарний файл і не виводячи його рядки.

Правило sudo з підстановкою для скриптів обслуговування програми потребує перевірки не лише шляху до скрипту. З’ясуйте, чи приймає дозволений скрипт необмежені аргументи або читає параметри, які може змінити обліковий запис програми з нижчими привілеями, а потім простежте, чи потрапляють ці значення до shell-команд або середовища підпроцесу. Наприклад, [`zmupdate.pl` у ZoneMinder формує команду `mysqldump` і виконує її через `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), а [`zmdc.pl` копіює параметр `ZM_LD_PRELOAD` у `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) перед запуском демонів. Правило sudo, що дозволяє запускати будь-який із цих скриптів від імені root, може перетнути межу довіри, якщо відповідним вхідним значенням можна керувати і воно потрапляє до цього коду у встановленій версії. Перегляньте ефективне правило sudo, права на конфігурацію програми й вихідний код скрипту; сама підстановка або параметр — лише привід для перевірки, а не доказ виконання.

- `SETENV`, `env_keep`, `secure_path` і `LD_PRELOAD` можуть перетворити вузько обмежену команду на шлях до підміни імпорту, бібліотеки чи PATH. Див. [посібник зі змінних середовища](../linux-basics/linux-environment-variables.md) і [зловживання SUID/лінкером](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Точний дозвіл `SETENV` для shell-обгортки, яку можна запускати від імені root, також потребує перевірки одного кроку, якщо обгортка запускає фіксований Python-скрипт із буквальним імпортом. `secure_path` обмежує пошук shell-команд, але не пошук модулів Python через [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); параметри [`-E` та `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) змушують Python ігнорувати цю змінну середовища. Перш ніж розглядати це як виконання коду, перевірте ефективні теги й заборони sudo, гілку обгортки, параметри інтерпретатора, розв’язання імпорту та наявність каталогу пошуку, доступного для запису викликачеві. Переглядайте короткі скрипти статично; не запускайте привілейовану обгортку.

Навіть точний дозвіл sudo на `neofetch ""` від імені root може завантажити конфігурацію shell, якщо відповідні параметри sudo зберігають контрольований викликачем `XDG_CONFIG_HOME`. [Завантажувач конфігурації Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) підключає `neofetch/config.conf` або `neofetch/config` із цього каталогу; порожній список аргументів не заважає такому пошуку. Перевірте завантажувач у встановленій версії, ефективні RunAs та політику аргументів, будь-які заборони команд, чи справді sudo зберігає вибрану змінну для цієї команди та чи контролює викликач доступний для читання шлях до конфігурації. Збережена змінна або встановлений Neofetch — лише привід для перевірки. Переглядайте політику й метадані файлів, не запускаючи привілейовану команду та не виводячи вміст конфігурації; див. [обробку середовища в sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Необмежене правило sudo для `facter` з можливістю запуску від імені root потребує окремої перевірки custom facts. [Документація Puppet](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) зазначає, що `--custom-dir` завантажує файли фактів Ruby з вибраного каталогу. Перевірте, чи дозволяє точне правило sudo цей параметр, чи підтримує його встановлений Facter і чи контролює викликач цей каталог. Фіксований список аргументів, явна заборона команди або вимкнені custom facts можуть змінити результат. Пасивний збір даних має повідомляти про можливе правило, не запускаючи Facter і не читаючи вміст файлів фактів.

Для точного дозволу sudo на запуск скрипту від імені root із `SETENV` перевірте голі назви команд на кшталт `find` і ефективний `PATH` після застосування політики sudo та ініціалізації скрипту. Підключений файл Bash також може виконати `enable -n [`: [після цього Bash шукає в `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) зовнішню команду `[`, якщо скрипт згодом її викликає. Перевірте відповідні [правила середовища sudoers і `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), будь-які записи `NOSETENV`/`NOEXEC` або заборони, потік виконання скрипту й підключених файлів, а також наявність каталогу пошуку з виконуваним файлом, який контролює викликач. Доступний для читання скрипт із голою назвою команди — лише привід для перевірки, а не доказ привілейованого виконання; переглядайте його, не запускаючи правило sudo.
- Привілейований скрипт, що завантажує дані з фіксованої URL-адреси через `curl`, усе одно може отримувати вибрану викликачем відповідь, якщо відповідне правило sudo зберігає `http_proxy` і запит іде через цей проксі. Якщо потім скрипт передає відповідь XML-парсеру, який розв’язує зовнішні сутності, шкідлива відповідь може розкрити файли, доступні для читання привілейованому процесу. Перевірте точну політику середовища sudo, винятки `no_proxy`, URL-адресу запиту, конфігурацію парсера й місце виведення; самої змінної проксі або XML-парсера недостатньо, щоб довести наявність вразливості. [Документація curl щодо змінних середовища проксі](https://everything.curl.dev/usingcurl/proxies/env.html) описує їхню поведінку. Під час пасивного збору даних не надсилайте мережевих запитів і не аналізуйте шкідливий XML.
- Привілейований скрипт sudo, що формує файл PostScript із даних, на які може впливати викликач, а потім запускає `ps2pdf -dNOSAFER`, потребує окремої перевірки потоку введення. Ghostscript документує, що цей прапорець вимикає SAFER до виклику `.setsafe`, дозволяючи файлові операції PostScript у межах прав процесу в ОС. SQL-запит, сформований з аргументу виклилача, може передавати контрольовані зловмисником рядки до шаблону PostScript, але сам рядок запиту або виклик `ps2pdf` не доводить, що ці дані потрапляють у синтаксис виконуваного PostScript. Перевірте ефективне правило sudo, точний шлях від введення до шаблону, екранування, поведінку встановленого Ghostscript і те, чи вмикається SAFER знову до інтерпретації документа. Під час пасивного збору даних не запускайте привілейоване перетворення. Див. [документацію Ghostscript щодо `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Для правила sudo, яке запускає shell-скрипт, порівняйте збережені змінні із самим скриптом. Конструкція на зразок `if $CHECK_CONTENT; then` виконує розгорнуте значення як команду, тому збереження `CHECK_CONTENT` може дозволити виконання команд, навіть якщо шлях до скрипту й аргументи фіксовані. Для конкретного правила потрібно перевірити, чи доступна ця гілка і чи справді зберігається змінна середовища.<sup>[[2]](#references)[[22]](#references)</sup>
- Скрипт Python, дозволений через sudo, може імпортувати код із каталогу, доступного для запису, або з кешованого файла `.pyc`. Випадок із кешем описано в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md).
- Фіксований Python-скрипт, дозволений через sudo для запуску від імені root, усе одно може відкрити інтерактивний налагоджувач. Виклики на кшталт `pdb.set_trace()` або `pdb.post_mortem()` дозволяють виконувати інструкції Python у контексті налагоджуваного процесу, якщо викликач може дійти до точки зупину або обробника винятків **і контролювати потік введення налагоджувача**. Перевірте точне правило sudo RunAs, автентифікацію й умови гілки, доступність винятку, власника термінала/введення та те, чи працює налагоджувач у тому самому привілейованому процесі. Запит через сокет, що спричиняє виняток, сам по собі не дає доступу до налагоджувача, підключеного до іншого термінала. [Документація Python описує виконання інструкцій у налагоджувачі й режим post-mortem](https://docs.python.org/3/library/pdb.html); під час збору даних переглядайте скрипт статично, не запускаючи привілейований обробник.
- Фіксований Python-скрипт, дозволений через sudo, також може зчитувати поле профілю з бази даних або Unix-сокета й додавати його до рядка, який згодом стає **рядком формату** для `str.format()`. [Поля підстановки можуть містити атрибути й ключі відображення](https://docs.python.org/3/library/string.html#format-string-syntax), тому контрольоване зловмисником поле може переглядати об’єкти, передані до `format()`, і розкривати доступні через них дані, якщо результат виводиться або зберігається там, де його може прочитати викликач. Перевірте ефективний ідентифікатор sudo RunAs, право запису в конкретний запис, потік даних у рядок формату, передані об’єкти й доступність результату. Це не автоматичне виконання коду; буквальний довірений рядок формату з контрольованими зловмисником *значеннями* — інший випадок. Розкрита таємниця стане переходом до облікового запису ОС лише якщо цей обліковий запис її приймає. Перегляньте скрипт і права доступу до сокета, не запускаючи привілейовану операцію.
- Обгортка Python, яку можна запускати від імені root, може передати вибрану викликачем URL-адресу до `Repo.clone_from` у GitPython. Якщо обгортка також вмикає Git `protocol.ext.allow=always`, віддалене джерело `ext::` може запускати зовнішню допоміжну програму. Перевірте точні аргументи sudo, джерело URL-адреси, версію пакета GitPython і наявність виправлень постачальника, а також те, чи обгортка явно дозволяє небезпечні протоколи. У GitPython з’явився [захист від небезпечних протоколів за замовчуванням](https://github.com/gitpython-developers/GitPython/commit/2625ed9) у версії 3.1.30; версія виконуваного файла `git` — окремий факт. Під час пасивної перевірки читайте лише правило й обмежений обсяг вихідного коду, не запускаючи клонування.
- Дозвіл sudo для переходу між обліковими записами на CLI-клієнт клонування репозиторію може створити окремий шлях ін’єкції shell-рядка. Перевірте, чи потрапляє вибраний викликачем аргумент репозиторію до [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) Node.js або іншого генератора shell-команд без безпечного розділення аргументів; `exec` у Node передає рядок команди до shell. Перевірте точного користувача RunAs, дозволені підкоманди й аргументи, код встановленої обгортки та валідацію введення. Назва інструмента для роботи з репозиторіями або необмежене правило sudo самі по собі не доводять наявності ін’єкції команд. Перегляньте обгортку, не запускаючи привілейоване клонування під час збору даних.
- Спеціальна обгортка, що належить root, може здаватися безпечною, бо її бінарні файли й скрипти недоступні для запису, але рішення про виконання привілейованої дії може залежати від прапорця, значення локального API або стану служби, які може змінити непривілейований користувач. Простежте кожну умову до її вхідних даних і перевірок авторизації. Під час збору даних переглядайте конфігурацію й дозволи, не змінюючи робочий стан; виклик `systemd-run` усередині обгортки важливий лише тоді, коли на відповідну умову можна вплинути.
- Клієнт резервного копіювання, дозволений через sudo для запуску від імені root, може приймати вибраний викликачем файл конфігурації, наприклад `npbackup-cli -c`. Перевірте точного користувача RunAs і дозволені аргументи, а потім з’ясуйте, чи контролює викликач шлях конфігурації, вихідні шляхи резервного копіювання та параметри репозиторію або читання/відновлення. Зашифрований секрет репозиторію в доступній для читання конфігурації все ще може бути використаний клієнтом, але саме правило не доводить доступу до репозиторію чи розкриття файлів root. Перевіряйте авторизацію, не запускаючи резервне копіювання й не виводячи його вміст.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) підтримує `--password-command`, який запускає програму для отримання пароля репозиторію. Якщо правило sudo дозволяє непривілейованому користувачеві запускати restic від імені root із вибраною викликачем командою отримання пароля та підкомандою, якій потрібен пароль, ця допоміжна програма може запуститися від імені root. Резервна копія SSH-ключа надає доступ лише якщо цільовий обліковий запис приймає цей ключ. Не запускайте резервне копіювання для перевірки під час пасивного аналізу.
- Необмежена спеціальна команда обслуговування чи резервного копіювання може приймати шлях виведення або мати власний планувальник завдань. Для запланованої команди перевірте ідентифікатор, від імені якого працює планувальник, введені команди й будь-який додатковий пароль або перевірку авторизації. [запис у файли, що належать root](../interesting-files-permissions/write-to-root.md) і [cron та таймери systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Навіть фіксована команда sudo може завантажувати передбачуваний файл конфігурації зі спільного каталогу, доступного для запису. Якщо ширше правило дозволяє `--file-list`/`-f`, перевірте окремо його поведінку; політика, обмежена `--debug <scan-path>`, цього параметра не дозволяє. Під час збору даних переглядайте політику й метадані пакета, не скануючи спеціально сформований файл і не виводячи захищений результат.
- Правило sudo, що дозволяє запускати від імені root команду відкриття вибраного викликачем зашифрованого образу диска, разом з іншим правилом для монтування отриманого mapper може імпортувати контрольовані викликачем файли в простір монтування хоста. Перевірте обидва ефективні правила й аргументи, контроль над образом і назвою mapper, фактичну точку монтування, власника та режим отриманих файлів. Для переходу через set-user-ID додатково потрібні доступний виконуваний файл, параметри монтування, які його підтримують (`nosuid` блокує це), і відповідна політика процесу або MAC; саме відкриття чи монтування образу — лише привід для перевірки. Окремий шлях через наявну резервну копію вимагає фактичного ключа й корисного доступного для читання секрету всередині. Переглядайте політику та шляхи, не відкриваючи й не монтуючи образ під час пасивного збору даних. Див. [посібник cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) і [параметри монтування](https://man7.org/linux/man-pages/man8/mount.8.html).
- Правило sudo для shell- або Python-скрипту, який можна запускати від імені root, потребує перевірки робочого каталогу, якщо скрипт викликає `./helper`, не переходячи спочатку до фіксованого каталогу. Список Python на кшталт `['./helper']`, переданий до `subprocess.run`, може так само використовувати вибраний викликачем робочий каталог. Викликач може вибрати каталог, доступний для запису, і розмістити там виконуваний файл із таким відносним ім’ям; абсолютний шлях деінде у скрипті не захищає цей виклик. Перш ніж розглядати це як виконання коду, перевірте ефективне правило, `runchdir` чи іншу політику зміни каталогу, потік виконання скрипту й доступність гілки, каталог із правами запису та виконання, а також обмеження монтування/`NOEXEC`. Якщо скрипт недоступний для читання, його поведінка невідома, доки вихідний код не буде переглянуто через авторизований шлях. Переглядайте скрипти статично, не запускаючи допоміжну програму. Політику робочого каталогу описано в [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Фіксований валідатор Python, який можна запускати від імені root, усе одно може оцінювати вибраний викликачем файл даних. [Документація Python щодо `eval()` застерігає від недовіреного введення](https://docs.python.org/3/library/functions.html#eval): перевірка суфікса, арифметичний префікс або гілка валідації не є пісочницею, якщо залишок виразу потрапляє до `eval`. Перш ніж вважати це шляхом до виконання коду, перевірте ефективне правило sudo, чи може викликач вибрати й контролювати саме цей файл, умови гілок парсера та формування виразу, а також ідентифікатор привілейованого процесу. Сам факт наявності `eval` у доступному для читання скрипті — лише привід для перевірки; перегляньте вихідний код і дозволи на файл, не запускаючи валідатор і не передаючи тестовий вираз під час збору даних.
- Обгортка Ruby, яку можна запускати від імені root через sudo, якщо вона читає відносний файл YAML, наприклад `YAML.load(File.read("dependencies.yml"))`, може отримати вхідні дані з робочого каталогу виклилача, якщо обгортка або політика sudo не фіксує цей каталог. Перевірте точні дозволені аргументи, дозволи на каталог і файл, а також поведінку встановленого Psych: старі реалізації `YAML.load` могли десеріалізувати довільні об’єкти Ruby, тоді як нові за замовчуванням обмежують класи. Самого місця виклику в коді недостатньо; з’ясуйте, чи справді файл лежить у каталозі, доступному викликачеві для запису, і чи приймає встановлений завантажувач небезпечні класи. Для недовіреного введення віддавайте перевагу `safe_load` з явним мінімальним списком дозволених класів. Див. документацію [Psych для Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) і [Psych для Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Точний дозвіл `sudo go run /absolute/file.go` із можливістю запуску від імені root потребує перевірки робочого каталогу, якщо вихідний код Go читає відносний файл WASM і після аналізу його результату може запустити відносний shell-скрипт. Перевірте ефективного користувача RunAs, аргументи команди й заборони, поточний каталог, доступний викликачеві для запису, потік даних від WASM до гілки й те, чи викликає ця гілка допоміжну програму. Фіксований sudo `runchdir`, `os.Chdir` або [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) можуть змінити місце пошуку. Простий факт, що ці елементи трапляються поруч у коді, — лише кандидат для перевірки; переглядайте вихідний код, не запускаючи Go, WASM чи допоміжну програму.
- Для `sudoedit` і підстановок аргументів потрібно точно перевіряти версію та правило; [контрольний список](linux-privilege-escalation-checklist.md) містить проблему редагування файлів через sudoedit. Для дозволу `sudoedit` між обліковими записами з шляхом, що містить підстановку, перевірте ефективний параметр `sudoedit_follow` або `FOLLOW`, `sudoedit_checkdir`, розв’язаний цільовий шлях і те, хто може замінити кожен елемент батьківського шляху. Перший параметр може дозволити перехід за символічним посиланням, а вимкнення другого скасовує перевірки каталогів, доступних для запису; жоден із цих параметрів окремо не доводить можливості запису у файл іншого користувача. Перш ніж робити такий висновок, перевірте встановлену політику sudo й точно зіставлені аргументи. Див. [визначення параметрів sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- У правилі команди sudoers підстановка аргументу може збігатися з пробілами, а не лише з символами шляху. Тому правило для команди з можливістю читання й аргументом на кшталт `/restricted/*` може також дозволяти додатковий аргумент-файл після відповідного префікса. Перевірте точного користувача RunAs, шлях до команди, шаблон аргументу й наступні заборони; доведене читання файла не означає можливості виконувати команди. [Посібник sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) розрізняє підстановки аргументів і підстановки шляхів до команд.
- Підстановка аргументу, схожа на шлях, також може збігатися з `../`. Наприклад, правило `node /opt/scripts/*.js`, яке можна запускати від імені root, може дозволити контрольований викликачем файл JavaScript за межами `/opt/scripts`, якщо переданий шлях усе ще починається з `/opt/scripts/` і розв’язується через сегменти шляху до батьківського каталогу. Це підстановка **аргументу**; для підстановки шляху до виконуваного файла Node діють інші правила зіставлення зі скісними рисками. Перш ніж робити висновок про виконання коду, перевірте ефективне правило, наступні заборони, розв’язання шляху, контроль над цільовим файлом і обмеження регулярними виразами чи дайджестами sudoers. Див. [правила підстановок sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) і [документацію Node щодо командного рядка](https://nodejs.org/api/cli.html).
- Архіватори й інші утиліти можуть мати засоби запуску команд. Перевірте точні дозволені аргументи через [GTFOBins](https://gtfobins.github.io/), а не вважайте, що команди запускають лише shell або інтерпретатори.
- Необмежене правило для `qpdf` з можливістю запуску від імені root може розкрити привілейований файл через вкладення PDF: qpdf версій 10.2 і новіших підтримує `--empty` і `--add-attachment file ... --` разом із вихідним PDF. Якщо привілейований процес може читати вибране джерело й записувати PDF у шлях, доступний викликачеві, цей файл може містити байти джерела. Перш ніж робити висновок про можливість розкриття файлу, перевірте ефективні аргументи й винятки sudo, версію qpdf, доступ до джерела й шлях виведення. Читання SSH-ключа root корисне для входу лише тоді, коли ключ чинний і автентифікацію root через SSH дозволено. Див. [параметри вкладень qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Повторне використання часової мітки sudo залежить від політики кешу, власника, термінала/сеансу та прав доступу. Потрібні перевірки описані в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens).
- `doas` має власні правила й конфігурацію. Перевірте дозволені команди й шляхи до конфігурації, доступні для запису, як описано в [розділі про doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Інструменти збирання й пакування, запущені через sudo

Необмежений дозвіл sudo для Foundry `forge` може бути важливим, навіть якщо RunAs — інший непривілейований користувач. Параметри компілятора на кшталт `--use` можуть вибирати локальний виконуваний файл, а `forge flatten -o` — файл виведення. Перш ніж вважати цей дозвіл придатним для експлуатації, перевірте встановлену версію Forge, точні аргументи sudo, доступні шляхи проєкту й компілятора, дозволи на вихідний файл і ефективне середовище. Відносна допоміжна програма, знайдена через `PATH`, — шлях, залежний від версії й середовища, а не властивість, яку можна припускати для кожної збірки Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Необмежений дозвіл на `pacman` з можливістю запуску від імені root дозволяє більше, ніж запити щодо пакетів: `-U` приймає локальний пакет, пакети можуть містити скрипти встановлення, а `--hookdir` вибирає інший каталог hook. Перед будь-якими перевірками перегляньте ефективне правило sudo, обмеження й винятки аргументів; пасивний збір даних не потребує встановлення пакета чи запуску hook.<sup>[[25]](#references)[[26]](#references)</sup>

Фіксована shell-обгортка sudo також може встановлювати названу залежність npm, а потім запускати застосунок Node. Перевірте точне правило RunAs, чи вже встановлено пакет, ефективний `HOME` і `userconfig` npm, конфігурацію проєкту чи перевизначення командного рядка, а також те, чи контролює непривілейований користувач реєстр або пакет, що повертається для цієї назви. [Документація npm описує пошук `.npmrc` на рівні користувача й проєкту](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); поведінка `HOME` у sudo залежить від встановленої політики й дистрибутива, тому файл `.npmrc` користувача, доступний для запису, може читатися або не читатися привілейованим процесом npm. Якщо нещодавно встановлений пакет імпортує привілейований застосунок, його код модуля може виконуватися з ідентифікатором цього застосунку. Скрипти під час встановлення — окремий шлях, залежний від версії й конфігурації; [npm документує їхній життєвий цикл і роботу з користувачами](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Шлях до `.npmrc` або сам рядок `npm install` — лише привід для перевірки. Під час пасивного збору даних перегляньте правило, коротку обгортку, шляхи конфігурації й походження пакета, не встановлюючи пакет і не запускаючи застосунок.

Дозвіл sudo на `pip` або `pip3 download` з можливістю запуску від імені root також потребує перевірки збирання пакета, якщо аргументи дають змогу викликачеві вибрати недовірений вихідний дистрибутив — навіть якщо шаблон URL-адреси обмежує його локальним сервісом і суфіксом `.tar.gz`. `pip download` приймає URL-адреси архівів і розв’язує метадані пакета; підготовка sdist може запускати бекенд збирання або застарілий код `setup.py` ще до збереження архіву. Перевірте точне правило sudo RunAs і аргументів, чи може викликач опублікувати або замінити вибраний архів, а також чи справді ця версія pip готує метадані. Фіксований довірений архів або wheel не доводить наявності цього шляху. Під час пасивного збору даних не завантажуйте й не збирайте недовірений пакет. Див. [команду download у pip](https://pip.pypa.io/en/stable/cli/pip_download/), [інтерфейс системи збирання](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Правило sudo, що дозволяє `pip install` із вибраним викликачем шляхом до локального проєкту, створює прямішу межу збирання. [pip приймає локальні каталоги проєктів](https://pip.pypa.io/en/stable/topics/local-project-installs/) і запускає їхню систему збирання; [бекенд збирання виконує керовані проєктом hook-и](https://pip.pypa.io/en/stable/reference/build-system/). Перш ніж вважати правило способом виконання привілейованого коду, перевірте ефективний ідентифікатор RunAs, точні обмеження й заборони аргументів, контроль над вибраним проєктом і поведінку встановленого pip/бекенда. Фіксований довірений проєкт або правило, що виключає шляхи, вибрані викликачем, не доводить наявності цього шляху. Перегляньте правило й метадані проєкту, не встановлюючи пакет під час пасивного збору даних.

Необмежений дозвіл sudo на застарілий `easy_install` із можливістю запуску від імені root — подібний привід для перевірки збирання пакета. [Setuptools документує](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), що Easy Install приймає локальний каталог проєкту й збирає вихідні дистрибутиви; проєкт, контрольований викликачем, може виконати свій `setup.py` під час збирання з ідентифікатором sudo. Перевірте ефективний обліковий запис RunAs, точні обмеження команди й аргументів (зокрема наступні заборони), контроль над вибраним проєктом і поведінку встановленого інструмента. Фіксований довірений проєкт або політика, що не дозволяє викликачеві вибрати джерело, не доводить наявності цього шляху. Під час збору даних переглядайте правило й метадані проєкту, не встановлюючи пакет.

Обгортка Python, дозволена через sudo, що використовує `setuptools.package_index.PackageIndex.download` із вибраною викликачем URL-адресою, — окремий випадок для перевірки, не пов’язаний із `pip download`: [GHSA-5rjg-fvgr-3xxf у setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) описує, як у вразливих випусках до 78.1.1 ім’я файла, сформоване з URL-адреси, виходило за межі призначеного каталогу завантаження й записувалося з правами процесу. Перевірте ефективні RunAs та правило аргументів sudo, чи передає обгортка URL-адресу виклилача саме до цього API, збірку встановленого пакета або бекпорт від постачальника, а також куди веде отриманий шлях. Самого номера версії або каталогу завантаження, доступного для запису, недостатньо, щоб довести довільний запис. Під час збору даних переглядайте коротку обгортку й метадані пакета, не завантажуючи файл і не записуючи його.

Обгортка збирання, дозволена через sudo і що передає вибраний викликачем файл `.spec` до PyInstaller, потребує такої самої перевірки межі довіри. Файл PyInstaller spec — це виконуваний Python-код, який обчислюється під час **збирання**, а його записи `datas` можуть додавати до артефакту файли, доступні для читання ідентифікатору збирача. Перевірте точного користувача RunAs, правила аргументів і заборон sudo, обробку шляхів і гілок в обгортці, контроль над вибраним spec-файлом і доступ до отриманого артефакту. Сам дозвіл на введення `.py` або наявність встановленого PyInstaller не доводять контроль над spec-файлом чи можливість привілейованого виконання. Під час пасивної перевірки читайте лише обмежений обсяг файла обгортки й метаданих; не запускайте збірку. Див. [документацію PyInstaller щодо spec-файлів](https://pyinstaller.org/en/stable/spec-files.html).

### Завантажувачі preset і плагінів, запущені через sudo

Інструменти Python, які приймають вибраний викликачем preset або каталог плагінів, можуть імпортувати код із привілеями, наданими sudo. Наприклад, BBOT приймає preset через `-p`, а в [документації щодо власних модулів](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) описано записи `module_dirs`, що задають додаткові каталоги модулів Python. Якщо ефективне правило sudo дозволяє вибрати preset, а викликач контролює модуль у вибраному каталозі, імпорт може виконати код від імені привілейованого користувача, потенційно ще до того, як інструмент відхилить недійсний модуль. Перевірте встановлену версію, точну політику sudo щодо RunAs та аргументів і власників шляхів preset і модуля, не завантажуючи модуль під час збору даних.

### Інструмент командного рядка Backdrop, запущений через sudo

[Bee](https://github.com/backdrop-contrib/bee) — це PHP-інструмент командного рядка для Backdrop CMS. Його команди `eval` (`php-eval`) і `php-script` можуть виконувати PHP-код, переданий викликачем. Тому правило sudo, що дозволяє виконуваний файл Bee з необмеженими аргументами від імені root, може відкрити виконання коду root, якщо Bee може ініціалізувати встановлення Backdrop. Запускайте його з каталогу сайту або вибирайте сайт глобальним параметром `--root=<directory>`; сама наявність Bee чи файла Backdrop `settings.php` не доводить наявності дозволу sudo, придатного сайту або успішної ініціалізації. Перед перевіркою перегляньте ефективне правило sudo, будь-які заборони команд, ідентифікатор виконуваного файла й доступ до сайту. Під час пасивного збору даних переглядайте правило та шляхи до файлів, не запускаючи Bee. Див. [журнал змін команд Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md), де описано додавання PHP-команд.

### Термінальні сервери, запущені через sudo

`mosh-server` запускає інтерактивний термінальний сервер від імені виклилача. Він вибирає високий UDP-порт і ключ сеансу, повідомляє їх викликачеві й зазвичай запускає login shell цього користувача під час підключення клієнта. Тому необмежений дозвіл sudo на `mosh-server` із можливістю запуску від імені root є кандидатом для перевірки shell, хоча сама команда сервера від’єднується від термінала. Перевірте ефективний ідентифікатор RunAs, дозволені аргументи й винятки, встановлений бінарний файл, shell, доступність клієнта та доступ через UDP. Пасивний збір даних має перевіряти правило sudo, не запускаючи сервер і не виводячи активний ключ сеансу. Див. [посібник сервера Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) і [примітки про архітектуру від розробників](https://github.com/mobile-shell/mosh#how-it-works).

### Привілейовані обгортки резервного копіювання, що переписують файл завдань виклилача

Shell-обгортка, що запускається від імені root, може приймати вибраний викликачем файл завдань, видаляти `../` зі шляхів джерел, перевіряти, чи починається кожен результат із дозволеного каталогу, переписувати файл завдань, а потім передавати до програми резервного копіювання *шлях до цього файла*. Перевірте перетворений шлях після повної канонізації: за одну заміну рядка може виникнути нова послідовність обходу каталогів, яку прийме лексична перевірка префікса. Також з’ясуйте, чи програма резервного копіювання читає перетворені дані з пам’яті, чи відкриває файл повторно. Якщо вона повторно відкриває файл, невдала перезапис може залишити початкове введення на місці.

У Linux `fs.protected_regular` може заборонити запис із `O_CREAT` до звичайного файла іншого користувача у world-writable каталозі з sticky bit. Це захисна заборона, але shell-обгортка, яка ігнорує помилку запису, усе одно може продовжити роботу з початковим файлом завдань. Перевірте параметр, власника файла й каталогу та те, чи зупиняється обгортка після помилки. Шлях є кандидатом на розкриття файлів лише якщо ефективне правило sudo дозволяє запускати обгортку від імені привілейованого користувача, викликач контролює вхідні дані завдання й доступне для читання місце призначення резервної копії, а утиліта резервного копіювання справді додає захищені джерела. Під час збору даних перевіряйте ці умови, не запускаючи резервне копіювання.

### Підстановки аргументів у привілейованих мережевих інструментах

У правилі sudo для `tcpdump` `*` у **шаблоні аргументів** може збігатися з пробілами й скісними рисками, тож обмеження, схоже на шлях, усе одно може дозволяти додатковий текст параметрів. Це відрізняється від підстановки у шляху до виконуваного файла команди; перевірте повне правило RunAs і будь-які наступні заборони. Якщо можна ін’єктувати параметри, придатність дозволеного виклику й семантика параметрів встановленого [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) визначають, чи дають `-F`, `-V`, `-r`, `-w` або `-Z` корисну примітивну операцію читання/запису. `-V` читає список імен файлів захоплення трафіку, а не довільний файл для загального дампу. AppArmor або інша політика MAC може блокувати доступ до файлів, навіть якщо sudo дозволяє команду; наявність файла профілю на диску не доводить, що його завантажено й застосовано. Перш ніж робити висновок, пасивно перевірте авторизацію й політику. Відмінність підстановок описано в [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Правило sudo від імені root, у якому зазначено лише виконуваний файл `tcpdump` без обмеження аргументів, також потребує перевірки. У [посібнику tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) зазначено, що `-z` запускає команду після ротації, якщо `-C` або `-G` обертає збережене захоплення трафіку; `-Z` або параметр за замовчуванням під час компіляції може знизити привілеї до запуску цієї команди. Перш ніж вважати правило шляхом до підвищення привілеїв, перевірте ефективне правило sudo, встановлену збірку, поведінку зі скиданням привілеїв і можливість ротації. Підсвічене правило — лише кандидат для перевірки, а не доказ виконання команди від імені root.

### Обгортки Nmap, запущені через sudo

Якщо дозволений через sudo шлях до `nmap` є shell-обгорткою, перевірте точний дозволений шлях і всі параметри, які вона передає далі. Блокування звичного написання `--script` не обов’язково блокує завантаження коду NSE: [`--datadir` у Nmap](https://nmap.org/book/man-misc-options.html) вибирає файли даних, а NSE [завантажує `nse_main.lua`](https://nmap.org/book/nse-implementation.html) із вибраного каталогу даних, коли сценарії ввімкнено. Деякі встановлені збірки також приймають альтернативні варіанти написання довгих параметрів, тому зіставте обмеження з фактичним парсером цього бінарного файла. [`--excludefile`](https://nmap.org/book/man-target-specification.html) — окрема поверхня читання файлів; помилки парсера можуть розкривати текст. Перевірте ефективне правило sudo, логіку обгортки, версію Nmap, контроль над каталогами й політику MAC, не запускаючи сканування під час збору даних.

### Hook-и pull у Mercurial, запущеному через sudo

Навіть фіксоване джерело в `sudo hg pull /fixed/source` залишає **приймальний** репозиторій залежним від поточного робочого каталогу, якщо команда не фіксує його параметром `-R`. Репозиторій, контрольований викликачем, може містити hook-и у `.hg/hgrc`, які запускаються з ідентифікатором користувача RunAs sudo. [Mercurial ігнорує конфігурацію репозиторіїв, що належать недовіреному користувачеві або групі](https://mercurial-scm.org/help/topics/config), тож перш ніж вважати це виконанням коду, перевірте довірених користувачів/групи облікового запису RunAs і точний робочий каталог. Для пасивної перевірки достатньо прочитати політику й конфігурацію; не виконуйте pull і не запускайте hook під час збору даних.

### Hook-и pull у Git, запущеному через sudo

Для точного дозволу `sudo git pull` від імені root також перевірте **приймальний** репозиторій, визначений робочим каталогом. У репозиторії, що належить викликачеві, може бути виконуваний hook `post-merge`, який запускається з ідентифікатором процесу Git, коли pull справді виконує успішне злиття; [Git документує цей hook](https://git-scm.com/docs/githooks) і [поведінку pull зі злиттям або перебазуванням](https://git-scm.com/docs/git-pull). Перевірте ефективне правило sudo й поточний робочий каталог, активний шлях до hook і його дозволи, а також можливість злиття нових комітів. Невдалий pull, операція без змін або pull лише з перебазуванням не доводять наявності цього шляху через hook. Переглядайте політику й метадані репозиторію, не запускаючи привілейований pull.

### Копіювання архівів rsync, запущене через sudo

Для `sudo rsync -a ... /writable/source/* /fixed/destination/` символ `*` у **шаблоні аргументів sudoers** може збігатися з пробілами й дозволити додатковий параметр між джерелом і призначенням. Це не пов’язано з розгортанням імен файлів shell. Якщо викликач може наповнити джерело, а привілейований процес rsync може записувати до місця призначення, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) може запросити привілейованого власника, зберігши режим дозволів у режимі архівування, що потенційно створить файл SetUID у власності цього користувача. Перевірте точну [семантику підстановок sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), версію rsync, наступні заборони, параметр файлової системи `nosuid` і політику MAC. Зіставлене правило — кандидат для перевірки, а не доказ успішного підвищення привілеїв.

### Експорт правил фільтрації пакетів, запущений через sudo

Необмежений дозвіл на `iptables` і `iptables-save` (або відповідну пару `ip6tables`) від імені root потребує перевірки можливості запису у файл. Підбір `comment` приймає вибраний викликачем текст правила, а `iptables-save -f` записує серіалізований набір правил у вибраний шлях.<sup>[[20]](#references)[[21]](#references)</sup> Корисне навантаження залежить від того, як встановлений бекенд серіалізує коментарі, і від того, чи може файл призначення приймати інші рядки в експорті; сам `iptables-save` не надає можливості записати довільно вибраний вміст. Перевірте точний ідентифікатор sudo RunAs, аргументи й винятки, доступне розширення зіставлення, бекенд і дозволи на файл призначення. Під час збору даних переглядайте дозвіл, не змінюючи правил брандмауера й не записуючи файл.

### Привілейований каталог журналів Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) впливала на версії Below до 0.9.0, які створювали доступний для запису всім каталог `/var/log/below`. Якщо служба або дозволена команда sudo запускає вразливу збірку від імені root, користувач, що може записувати в каталог журналів і проходити через нього, якщо в ньому немає sticky bit, може замінити запис журналу символічним посиланням до відкриття привілейованим процесом. Перевірте наявність виправлення у встановленому пакеті, точний шлях привілейованого виконання, ефективний доступ до каталогу, sticky bit і ACL, а також метадані `/var/log/below/error_root.log`. Доступний для запису всім шлях або саме правило sudo не доводять наявності всього ланцюжка. Sticky bit або бекпорт постачальника змінює оцінку. Під час пасивного збору даних переглядайте лише метадані; створювати посилання чи запускати привілейовану програму не потрібно.

### Збір привілейованого пакета підтримки з вхідних даних, доступних для запису

Дозволений через `sudo` скрипт профілю підтримки може читати фіксовані шляхи до журналів від імені root і копіювати їхній вміст до архіву профілю. Перегляньте скрипт, щоб знайти читання файлів, а потім перевірте, чи може викликач замінити шлях до джерела або будь-який елемент його батьківського каталогу символічним посиланням. Якщо привілейований процес переходить за цим посиланням і отриманий архів доступний для читання викликачеві, захищений файл може бути розкритий. Потрібні всі умови: дозвіл sudo, шлях до джерела, доступний для запису, привілейоване читання й доступний для читання результат; самого доступного для запису файла журналу чи імені профілю недостатньо. Перевіряйте ефективні дозволи й метадані посилань, не замінюючи файли й не створюючи профіль під час збору даних. [Рекомендації Nagios XI щодо підтримки](https://support.nagios.com/forum/viewtopic.php?t=62758) описують скрипт профілю, який запускається від імені root, і вихідний архів, що демонструє, чому для таких пакетів потрібні обмежені вхідні дані й доступ.

### Скрипти відновлення архівів Python, запущені від імені root

Навіть суворо обмежене правило sudo для скрипту відновлення Python потребує перевірки вхідного архіву. Якщо викликач може вибирати або замінювати архів, а скрипт розпаковує його від імені root через `tarfile.extractall(filter="data")`, перед довірою до фільтра перевірте оновлення безпеки інтерпретатора. CPython виправив кілька обходів фільтра символічних і жорстких посилань, зокрема CVE-2025-4517, у версіях 3.9.23, 3.10.18, 3.11.13, 3.12.11 і 3.13.4. Дистрибутиви можуть переносити виправлення на старіші версії, тому відображена версія інтерпретатора сама по собі не доводить наявності вразливості.<sup>[[16]](#references)[[17]](#references)</sup>

Для пасивної перевірки прочитайте точну команду sudo і скрипт, простежте, який аргумент вибирає архів, і з’ясуйте, чи може поточний користувач записувати в архів або його батьківський каталог. Окремо перевірте виправлення постачальника й каталог розпакування; `filter="data"` не робить безпечним кожен недовірений архів.<sup>[[16]](#references)[[17]](#references)</sup>

### Завантажувачі моделей машинного навчання, запущені через sudo

Правило sudo, що дозволяє вибирати файл `.pt`, `.pth` або `.ckpt`, потребує перевірки, якщо привілейований скрипт передає цей файл до [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` чи іншого завантажувача на основі pickle. Перевірте ефективне правило RunAs, чи може викликач створити або замінити вибрану модель, і фактичний потік аргументів через будь-яку shell-обгортку до допоміжного скрипту Python. Розширення `.pth` також використовується для не пов’язаних між собою конфігураційних файлів Python site, тому саме розширення не свідчить про завантаження моделі. Сканування архіву або статичний аналіз pickle не доводять безпеки подальшого завантаження; перевірте [залежну від версії поведінку `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) та будь-які списки дозволених об’єктів. Див. [примітки щодо pickle у ML і Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Під час пасивного збору даних ніколи не завантажуйте й не розпаковуйте модель.

### Парсинг виразу зі збереженого введення, запущений через sudo

Фіксований Python-скрипт, запущений від імені root через sudo, усе ще може обчислювати текст, який непривілейований користувач може зберігати в базі даних програми. У TensorFlow виклик `preprocess_input_exprs_arg_string(value, safe=False)` обирає шлях із `eval`; [рекомендація з безпеки TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) описує небезпечний парсер і виправлення його виклику з командного рядка. Явний виклик `safe=False` у програмі потребує окремої перевірки, навіть якщо виклик із командного рядка вже виправлено. Перевірте ефективне правило sudo, хто може змінити саме цей рядок введення, чи дозволяють фільтрація або оцінювання цьому рядку потрапити до виклику та поведінку встановленої функції. Версія TensorFlow, дозвіл sudo чи жорстко заданий файл моделі самі по собі не доводять наявності ланцюжка. Пасивно переглядайте скрипт і потік даних; під час збору даних не запускайте привілейовану допоміжну програму й не надсилайте тестові вирази.

### Конфігурація needrestart, дозволена через sudo

`needrestart -c` завантажує вибраний викликачем конфігураційний файл Perl і обчислює його вміст. Якщо `sudo -l` дозволяє запускати `needrestart` від імені root з аргументами, що дозволяють `-c`, а викликач може вибрати доступний для читання конфігураційний файл у каталозі, доступному для запису, цей дозвіл може призвести до виконання коду root. Перевірте точне правило sudo для RunAs й аргументів; правило з фіксованим списком аргументів може заблокувати цей шлях. Це окремо від вразливостей сканування інтерпретаторів у needrestart: оновлення пакета або вимкнення `interpscan` не робить безпечним необмежений дозвіл `-c` від імені root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Імпорти Python, запущені через sudo від імені іншого облікового запису

Фіксальна точка входу Python усе одно може імпортувати модуль, який викликач може редагувати або замінити, зокрема коли sudo запускає скрипт від імені **не-root** службового користувача. Для буквального `from utils import status` перевірте локальні `utils/__init__.py` і `utils/status.py`, а також дозволи на каталог пакета. Перш ніж вважати файл, доступний для запису, шляхом до виконання коду, перевірте шлях імпорту скрипту, точні дозволені аргументи sudo й те, чи доходить відповідна дія до цього імпорту. Під час збору даних перевіряйте файли й дозволи, не імпортуючи та не запускаючи скрипт.<sup>[[2]](#references)[[3]](#references)</sup>

Для точного правила sudo `python3 /absolute/script.py` потрібен лише доступний для читання скрипт; виконувані дозволи й shebang не потрібні. Перевіряйте також **відсутні** локальні модулі: якщо скрипт імпортує модуль, файл із відповідним ім’ям якого можна створити в каталозі скрипту, доступному викликачеві для запису, Python може завантажити його з ідентифікатором RunAs. Перевірте ефективне правило sudo, фактичний [шлях пошуку модулів](https://docs.python.org/3/library/sys_path_init.html) інтерпретатора, чи є модуль вбудованим або замороженим, і чи виконується імпорт. Для прямого правила sudo на скрипт діють інші вимоги щодо біта виконання й shebang. Окремій обгортці, що додає передані викликачем токени після `sudo -u account`, також потрібна перевірка потоку аргументів: інший `-u` у цих токенах має значення лише якщо політика викликаного sudo дозволяє отриманий ідентифікатор. Самі лише статичні рядки не доводять жодного з цих шляхів.

### Apache, запущений через sudo, з конфігурацією, контрольованою викликачем

Якщо правило sudo дозволяє запускати `apachectl`, `apache2ctl` або `httpd` із підвищеними привілеями та файлом конфігурації `-f`, вибраним викликачем, перевірте дозволи на цей файл і його батьківський каталог. Директива Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) приймає назву модуля й **ім’я файла модуля**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) також завантажує файл. [`Include` та `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) можуть розширити конфігурацію або розкрити вміст файлів через помилки. Спеціальна обгортка може перевіряти ці шляхи, скидати привілеї або обмежувати аргументи, тому конфігурація, доступна для запису, — лише кандидат для перевірки, а не доказ виконання коду. Перш ніж робити висновок, перевірте канонізацію шляхів, символічні посилання й обробку директив.

### nginx, запущений через sudo, із конфігурацією, контрольованою викликачем

Необмежене правило sudo для `nginx` із можливістю запуску від імені root може дозволяти [`-c` вибирати іншу конфігурацію](https://nginx.org/en/docs/switches.html). Перевірте точні аргументи й винятки sudo, чи може викликач передати конфігурацію та чи зберігає отриманий master-процес або worker-процеси доступ до захищених шляхів. Вибрані `root` і `autoindex` можуть відкривати файли через новий listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) може створити шлях привілейованого запису у файл, але модуль DAV за замовчуванням не вбудовано, тож потрібно перевірити його наявність, доступність listener, дозволи на файли й поведінку тимчасових файлів. Директива [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) також може вказувати на вибраний файл; запис журналів у чутливий конфігураційний файл, наприклад `/etc/ld.so.preload`, стане шляхом до підвищення привілеїв лише за наявності ефективного привілейованого запису й контрольованого запису журналу. Підсвічування виконуваного файла в `sudo -l` — привід для перевірки, а не доказ працездатності будь-якого з цих шляхів. Під час пасивного збору даних не запускайте nginx і не змінюйте його конфігурацію.

### Порівняння зі зразком у привілейованих запитах Bash

Якщо скрипт Bash, дозволений через sudo, читає значення від виклилача й перевіряє його за допомогою `[[ "$expected" == $entered ]]`, Bash трактує не взятий у лапки правий операнд як шаблон. Тому підстановний символ може задовольнити порівняння без знання очікуваного значення. Якщо взяти операнд у лапки (`[[ "$expected" == "$entered" ]]`), порівняння стане буквальним. Перевірте точне правило sudo, чи доступне це запрошення і що скрипт робить після порівняння; сам синтаксис не доводить наявності шляху для експлуатації. Під час збору даних не виводьте очікуване значення. Див. [довідник із конструкцій умов Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Допоміжні програми, запущені через sudo, що завантажують і виконують файл

Необмежений дозвіл sudo для спеціальної допоміжної програми з можливістю запуску від імені root потребує перевірки потоку даних, якщо вона приймає вибрану викликачем URL-адресу, записує відповідь на диск, а потім запускає файл через інтерпретатор або shell. [Sudoers дозволяє довільні аргументи, якщо в записі команди їх не зазначено](https://man7.org/linux/man-pages/man5/sudoers.5.html); фіксований шлях до виконуваного файла не обмежує вибір аргументів. Перевірте фактичну валідацію URL-адреси, шлях виведення, гілку успішного виконання й подальший запуск у встановленій допоміжній програмі. Сам імпорт libcurl або видимий рядок цього ланцюжка не доводить.

Навіть фіксоване базове ім’я вихідного файла можна підмінити між записом і виконанням, якщо допоміжна програма використовує **відносний шлях у робочому каталозі, який контролює викликач**. Перейменування або підміна файла, що належить root, залежить від прав на запис і пошук у каталозі та будь-яких обмежень sticky bit, а не лише від режиму самого файла; див. [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Перевірте, чи допоміжна програма згодом повторно відкриває шлях або використовує вже відкритий дескриптор, а також чи переходить до довіреного каталогу перед записом. Пасивно переглядайте політику sudo, допоміжну програму й метадані каталогу; під час збору даних не запускайте привілейоване завантаження й не створюйте race condition.

Допоміжна програма завантаження, запущена від імені root через sudo, також може допускати ін’єкцію **аргументів**, якщо формує рядок команди Bash, наприклад `curl <caller input> -o <fixed output>`. Фільтр, що відхиляє пробіли, не блокує [розгортання дужок Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): елементи, розділені комами й узяті без лапок, можуть перетворитися на окремі аргументи curl. Якщо введення доходить до curl перед фіксованим `-o`, переданий викликачем параметр виведення може вибрати місце призначення для першої URL-адреси з ідентифікатором цієї допоміжної програми; [curl пов’язує параметри виведення з URL-адресами за порядком](https://curl.se/docs/manpage.html#-o). Перевірте точний shell, лапки, валідацію введення, ефективне правило sudo, порядок аргументів curl і підтримувані схеми URL, а також те, чи контролює викликач завантажені байти або може прочитати результат. Виконуваний файл, упакований PyInstaller, може містити логіку програми Python, але сам маркер пакування чи рядок `curl` не доводять наявності такого потоку даних. За наявності дозволу перегляньте обмежену автономну копію; під час звичайного збору даних не запускайте допоміжну програму й не завантажуйте дані, вибрані зловмисником.

Shell-скрипт sudo, що запускається від імені root і викликає [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), лише вибирає вільне ім’я; він **не створює файл**. Якщо скрипт згодом створює файл із цим ім’ям у каталозі, на який може вплинути інший користувач, повторно відкриває його й додає його вміст до захищеного місця призначення, наприклад `authorized_keys` root, перевірте можливу race condition тимчасового файла. Перевірте точне правило sudo, власників каталогу й файла, послідовність створення та повторного відкриття, захист ядра й те, чи привілейований запис справді використовує байти, контрольовані зловмисником. Сам рядок `mktemp -u` або доступний для запису `/tmp` не доводить наявності такої гонки. Перегляньте скрипт і метадані шляху, не запускаючи його й не змагаючись за тимчасовий файл під час збору даних.

## Зауваження щодо захисту

- Не дозволяйте запускати через sudo інтерпретатори або інтерактивні редактори.<sup>[[1]](#references)</sup>
- Віддавайте перевагу фіксованим обгорткам, що належать root і виконують одну вузьку адміністративну дію.<sup>[[1]](#references)[[2]](#references)</sup>
- Якщо інтерпретатор необхідний, обмежте точний шлях до скрипту та унеможливте використання контрольованих користувачем аргументів, імпортів, доступних для запису, `PYTHONPATH` і небезпечного збереження середовища.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Якщо потрібно редагувати файли, обмежте точний шлях до файла та розгляньте `sudoedit` із виправленими версіями sudo й суворою обробкою середовища.<sup>[[1]](#references)[[2]](#references)</sup>
- Перевіряйте `SETENV`, `env_keep`, робочі каталоги, доступні для запису, шляхи модулів/імпорту, доступні для запису, `NOEXEC`, `use_pty` і журналювання, але не вважайте їх повноцінною пісочницею.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
