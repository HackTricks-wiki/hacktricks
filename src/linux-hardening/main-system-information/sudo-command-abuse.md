## Interprete wat deur Sudo toegelaat word

As `sudo -l` ’n gebruiker toelaat om ’n interpreter as root uit te voer, moet dit as direkte kode-uitvoering beskou word. Interprete is ontwerp om arbitrêre kode uit te voer, dus is ’n reël wat `python3`, `perl`, `ruby`, `lua`, `node` of soortgelyke binaries toelaat, gewoonlik gelykstaande aan die uitvoering van root-opdragte, tensy die argumente streng beperk en gevalideer word.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Algemene hersieningsvloei: lys eers die gebruiker se voorregte en voer dan ’n Python-stelling met die interpreter se `-c`-opsie uit.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Ander interpreteerdervoorbeelde word hieronder getoon; die genoemde interpreteerders dokumenteer inline-kode-uitvoering of API's vir kindprosesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Die presiese pad maak saak. As die sudo-reël `/usr/bin/python3` toelaat, gebruik daardie presiese pad tydens validering.<sup>[[2]](#references)</sup>

’n Sudo-uitvoerbare glob soos `/usr/bin/python*` kan ook Python 2 toelaat vir ’n script wat vir Python 3 geskryf is. As die script `input()` met teks bereik wat deur die oproeper beheer word, [evalueer Python 2 daardie teks as ’n uitdrukking](https://docs.python.org/2/library/functions.html#input); ’n eksplisiete aanroep van die interpreter oorheers die script se shebang. Verifieer die geïnstalleerde binaries wat ooreenstem, die effektiewe RunAs- en argumentbeleid, weierings en bereikbare invoer voordat jy dit as ’n uitvoeringspad beskou.

’n Vaste scriptpad in ’n root-bevoegde sudo-reël beperk nie wat die script uitvoer nie. Kyk vir ’n leesbare Bash-wrapper of sy eerste uitvoerbare opdrag ’n ongekwoteerde posisionele parameter soos `$1` as die **command word** gebruik terwyl sudo argumente toelaat wat deur die oproeper gekies word. Bevestig die effektiewe RunAs-identiteit, wagwoord- en argumentbeleid, latere weierings en die werklike script-tak; `NOEXEC`, ’n vaste veilige argumentlys of ’n wrapper wat sy opdrag valideer, kan die resultaat verander. Inspekteer die kort script staties tydens enumerasie eerder as om dit met ’n toetsopdrag uit te voer.

’n Onbeperkte root-bevoegde sudo-reël vir `dotnet` verdien ook ’n interpreter-nasien. Met ’n geïnstalleerde .NET SDK kan [`dotnet fsi` F#-kode interaktief of vanaf ’n script uitvoer](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), en [`dotnet run` ’n projek vanaf bronkode uitvoer](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bevestig eers die effektiewe RunAs-identiteit en presiese argumentbeleid: ’n reël wat tot ’n bepaalde veilige subopdrag of vertroude toepassing beperk is, is ’n ander toestaanreg, en ’n installasie wat slegs die runtime bevat, het moontlik nie SDK-opdragte nie. Die uitvoerbare lêernaam alleen is ’n aanduiding vir hersiening, nie bewys van kode-uitvoering nie.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editors wat deur sudo toegelaat word

As `sudo -l` 'n gebruiker toelaat om 'n interaktiewe editor as root uit te voer, behandel dit as 'n command-execution surface, nie as 'n onskadelike toestemming om lêers te redigeer nie. Editors kan dikwels shell-opdragte uitvoer, arbitrêre lêers lees of skryf, of eksterne helpers vanuit die editor aanroep.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Algemene hersieningsvloei: lys die gebruiker se voorregte en voer dan elke toegelate editor of pager met sudo uit.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano-opdraguitvoering

Wanneer `nano` via sudo toegelaat word, kan opdraguitvoering vanaf die redigeerkoppelvlak bereik word.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Voer dan ’n opdrag soos `id` of `/bin/sh` by die nano-opdragprompt in.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

As ’n interaktiewe shell nie bruikbare terminalstrome het nie, koppel hierdie herleidingsvorm sy standaarduitvoer en -fout aan deskriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die presiese sleutelsekwensie kan wissel na gelang van die nano-weergawe en bouopsies, maar die sekuriteitsprobleem is dieselfde: die redigeerder loop as root en kan eksterne opdragte uitvoer.<sup>[[1]](#references)[[12]](#references)</sup>

### Ander algemene redigeerder-ontsnappings

Vim-agtige redigeerders stel gewoonlik opdraguitvoering deur `:!` beskikbaar.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers soos `less` kan ook shell-uitvoering blootlê.<sup>[[14]](#references)</sup>

’n sudo-reël wat `apport-cli` as root toelaat, verdien dieselfde pager-kontrole. Geaffekteerde Apport-weergawes kon ’n omvalverslag in `less` oopmaak met ’n terminale grootte wat deur ’n aanvaller aangepas kon word; die pager kon dan ’n root shell bied indien die spesiale sudo- en pager-voorwaardes nagekom is. Gaan die effektiewe sudo-reël, pager-konfigurasie en verspreiding se pakketoplossing na voordat jy die weergawe alleen as kwesbaar beskou. Lees die pakket- en beleidmetadata sonder om tydens passiewe enumerasie ’n omval te veroorsaak of die bevoorregte verslag oop te maak. [Ubuntu se CVE-rekord](https://ubuntu.com/security/CVE-2023-1326) lys vaste pakketweergawes per vrystelling, insluitend teruggeporteerde regstellings.

```text
!/bin/sh
```

## Ander gevare met sudo- en doas-reëls

Begin met `sudo -l`, `sudo -V` en enige toepaslike `doas`-beleid. Lees die toegelate opdrag, gebruiker as wie dit uitgevoer word, argumente, omgewing en verstekwaardes saam. Toestemming om as ’n nie-root-diensrekening op te tree, kan steeds daardie rekening se lêers blootstel of ’n pad na root bied.

’n Vaste Python-skrip wat deur sudo toegelaat word, kan steeds ’n shell-opdrag onder sy RunAs-identiteit uitvoer as interaktiewe, deur die gebruiker beheerde invoer in [`os.system()`](https://docs.python.org/3/library/os.html#os.system) saamgevoeg word. ’n Bloklys van shell-leestekens is nie genoeg om veiligheid te bevestig nie: die [shell herken ook `$(...)`-opdragsubstitusie](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Bevestig dat die toegelate argumente die invoertak bereik, dat die invoer die shell-opdrag bereik sonder veilige validering, en dat die effektiewe sudo-beleid die beoogde RunAs-gebruiker toelaat. Die skrippad of ’n oproep na `os.system()` alleen is net ’n leidraad vir ondersoek; bekyk die bronkode sonder om die bevoorregte skrip uit te voer.

’n Effektiewe sudo-toekenning aan root vir `chattr` kan ’n onveranderlike (`i`) lêerkenmerk verwyder, maar dit gee op sigself nie skryftoegang of ’n nuwe identiteit nie. Volgens [die `chattr`-handleiding](https://man7.org/linux/man-pages/man1/chattr.1.html) verhinder die kenmerk wysigings en kan net root of ’n proses met `CAP_LINUX_IMMUTABLE` dit verander. Gaan die presiese sudo-argumentbeleid en lêerstelselondersteuning na; verifieer daarna afsonderlik dat die gebruiker die lêer kan skryf nadat die kenmerk verwyder is, en dat ’n komponent met ’n hoër identiteit dit gebruik. ’n Vervanging van ’n aanmeldingshell vereis byvoorbeeld ook die teik rekening se aanvaarde geloofsbriewe en ’n werklike aanmelding deur daardie shell. Gaan die beleid, lêerkenmerke en toestemmings na sonder om dit tydens enumerasie te verander.

As sudo ’n wagwoord én ’n eenmalige kode vereis, hou dié voorvereistes apart van die opdragtoekenning. ’n Leesbare `.google_authenticator`-lêer bevat sensitiewe saadmateriaal, terwyl ’n ou toepassings- of databasiswagwoord-hash net ’n moontlike wagwoord vir die huidige rekening is; nie een bewys dat die ander faktor deur die effektiewe PAM-konfigurasie aanvaar word nie. Wanneer jy gemagtig is, gaan die presiese RunAs en argumente na: ’n onbeperkte root-toekenning vir RubyGems `gem` kan sy redigeeropdrag blootstel ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), maar ’n beperkte toekenning of mislukte verifikasie doen dit nie. Passiewe enumerasie behoort paaie en beleid aan te meld sonder om die saad te vertoon, ’n wagwoord te herstel, ’n kode te genereer of die bevoorregte opdrag uit te voer.

’n Onbeperkte, root-bevoegde sudo-toekenning vir Chef se `knife` verdien ondersoek op interpreter-vlak: [Chef dokumenteer dat `knife exec -E` ’n Ruby-string plaaslik evalueer](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifieer dat die effektiewe sudo-reël die `exec`-subopdrag en die gebruiker-voorsiene `-E`-argument toelaat, asook die beoogde RunAs-identiteit en enige toepaslike opdragweierings of vaste argumente. Die geïnstalleerde binêre lêer of ’n reël wat tot ander subopdragte beperk is, is net ’n leidraad. Passiewe enumerasie behoort die reël aan te meld sonder om `knife` uit te voer.

’n Presiese, root-bevoegde sudo-toekenning vir ’n interaktiewe `msfconsole` is eweneens sensitief: [GTFOBins dokumenteer die `irb`-konsole daarvan](https://gtfobins.org/gtfobins/msfconsole/), wat die sudo-identiteit kan erf. Bevestig die effektiewe RunAs-gebruiker, toegelate argumentlys, opdragweierings, `NOEXEC` of ander beperkings, die geïnstalleerde konsole se gedrag en of die gebruiker interaktiewe invoer kan verskaf. ’n Padmerker alleen is net ’n leidraad vir ondersoek; passiewe enumerasie behoort nie die konsole te begin nie.

Op FreeBSD verdien selfs ’n sudo-reël wat beperk is tot root se `pkg update` en `pkg install *` ’n ondersoek na die vertroue in die pakketbewaarplek. Gaan na of `/etc/hosts` deur die gebruiker geskryf kan word en of die *effektiewe* geaktiveerde bewaarplek-konfigurasie ’n HTTP-gasheernaam met `signature_type: none` gebruik. Volgens [FreeBSD se `pkg.conf`-handleiding](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) deaktiveer `none` handtekeningkontroles; `pkg+http` alleen bevestig dit nie. ’n Pakket kan installasieskripte bevat ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), dus kan ’n gebruiker wat die bewaarplek-eindpunt werklik beheer en ’n pakket kan kies, die root-grens oorsteek. Verifieer bewaarplek-oorheersings, SRV-/spieëlresolusie, effektiewe sudo-argumente, pakketkeuse en skripuitvoering voordat jy dié gevolgtrekking maak. Gaan die beleid en klein plaaslike konfigurasielêers na sonder om name te herlei of `pkg` tydens enumerasie uit te voer.

’n Root-bevoegde sudo-reël vir `apt-get update` en `apt-get upgrade` vereis ook ’n ondersoek na die vertroue in die bewaarplek wanneer sudo ’n deur die gebruiker beheerde `http_proxy` behou. Gaan na of die effektiewe APT-instaanbediener-konfigurasie daardie veranderlike werklik gebruik en watter geaktiveerde bewaarplekversoeke dit kan beïnvloed; ’n instaanbediener alleen kan nie pakkette van ’n argief wat met ’n vertroude ondertekeningsleutel geverifieer word, vervang nie. [APT se HTTP-vervoerhandleiding](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) dokumenteer die voorrang van instaanbedieners, en [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) dokumenteer handtekeningkontroles, oorheersings vir onveilige bewaarplekke en bevestiging vir ongeverifieerde pakkette. Bevestig die presiese sudo-RunAs en argumente, die bewaarplek se verifikasiebeleid, enige vereiste interaktiewe aanvaarding en of die gekose opgradering pakketskripte as root uitvoer. Gaan beleid en plaaslike konfigurasie passief na; moenie pakketverkeer herlei of tydens enumerasie ’n opgradering uitvoer nie.

’n Root-bevoegde sudo-reël vir `snap install` kan ’n grens tussen pakkette en kode vorm as die argumente die gebruiker toelaat om ’n plaaslike snap en ’n permissiewe installasiemodus te kies. [Snap dokumenteer](https://snapcraft.io/docs/explanation/snap-development/install-modes/) dat `--dangerous` kontroles van plaaslike snap-attestasies oorslaan en `--devmode` inperking verslap; [’n installasiehaak kan tydens aanvanklike installasie loop](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Gaan die presiese sudo-argument-/RunAs-beleid na, wie die snap-lêer beheer, of die geïnstalleerde snapd hierdie modusse aanvaar, en die haak se effektiewe identiteit en inperking voordat jy toegang tot beskermde gasheerlêers beweer. ’n `snap`-binêre lêer of ’n reël wat soos ’n jokerteken lyk, bewys nie op sigself hierdie ketting nie. Passiewe enumerasie behoort nie ’n pakket te installeer of sy haak uit te voer nie.

Vir ’n presiese sudo-toekenning aan ’n pasgemaakte geloofsbriefleser-binêre lêer van ’n **nie-root**-rekening, bekyk eers die toegekenne binêre lêer en sy lêertoestemmings sonder om dit uit te voer. ’n Ingeboude wagwoordkontrole kan slegs as wye karakters sigbaar wees; [GNU `strings` dokumenteer 16-bis little-endian-onttrekking](https://sourceware.org/binutils/docs/binutils/strings.html). ’n Sigbare string bewys nie dat dit die aanvaarde wagwoord is of dat die suksesvertakking ’n huidige geloofsbrief blootstel nie. Bevestig die binêre lêer se gedrag, die teikenrekening se toegang tot die beskermde data, die geloofsbrief se geldigheid en enige latere rekening- of groepoorgang afsonderlik. As daardie rekening aan `docker` behoort, verifieer sokkertoegang en of die daemon rootful of rootless is voordat jy toegang tot gasheer-root aflei; [Docker dokumenteer die root-vlak-implikasies van sy groep](https://docs.docker.com/engine/install/linux-postinstall/). Gewone enumerasie behoort die sudo-reël en groeplidmaatskap aan te meld sonder om die binêre lêer uit te voer of sy strings uit te stort.

’n Sudo-jokertekenreël vir ’n toepassing se instandhoudingskripte vereis meer ondersoek as net die skrippad. Gaan na of die toegelate skrip onbeperkte argumente aanvaar of instellings lees wat deur ’n minder bevoorregte toepassingsrekening geskryf kan word; volg dan dié waardes na shell-opdragte of ’n subprosesomgewing. ZoneMinder se [`zmupdate.pl` stel ’n `mysqldump`-opdrag saam en voer dit met `qx` uit](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), terwyl [`zmdc.pl` die `ZM_LD_PRELOAD`-instelling na `LD_PRELOAD` kopieer](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) voordat dit daemons begin. ’n Sudo-reël wat enige van dié skripte as root toelaat, kan ’n vertrouensgrens oorsteek as die ooreenstemmende invoer beheerbaar is en dié kode in die geïnstalleerde weergawe bereik. Gaan die effektiewe sudo-reël, toepassingskonfigurasie se skryftoestemmings en skripbronkode na; die jokerteken of instelling alleen is ’n leidraad vir ondersoek, nie bewys van uitvoering nie.

- `SETENV`, `env_keep`, `secure_path` en `LD_PRELOAD` kan ’n andersins beperkte opdrag in ’n invoer-, biblioteek- of PATH-kaping omskep. Sien die [omgewingsveranderlikegids](../linux-basics/linux-environment-variables.md) en [SUID-/linker-misbruik](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

’n Presiese, root-bevoegde `SETENV`-toekenning vir ’n shell-omhulsel verdien ook ’n ondersoek een stap verder as die omhulsel ’n vaste Python-skrip met ’n letterlike invoer begin. `secure_path` beperk die shell se opsoek van opdragte, nie Python se [`PYTHONPATH`-module-opsoek](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) nie; [`-E` en `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) laat Python daardie omgewingsveranderlike ignoreer. Bevestig die effektiewe sudo-etikette en -weierings, die omhulselvertakking, interpreteropsies, invoerresolusie en ’n deur die gebruiker skryfbare soekgids voordat jy dit as kode-uitvoering beskou. Beoordeel kort skripte staties; moenie die bevoorregte omhulsel uitvoer nie.

’n Presiese, root-bevoegde `neofetch ""`-sudo-toekenning kan steeds ’n shell-konfigurasie laai wanneer die toepaslike sudo-verstekwaardes deur die gebruiker beheerde `XDG_CONFIG_HOME` behou. [Neofetch se konfigurasielaaier](https://github.com/dylanaraps/neofetch/blob/master/neofetch) laai `neofetch/config.conf` of `neofetch/config` onder daardie gids; die leë argumentlys keer nie dié opsoek nie. Bevestig die geïnstalleerde laaier, effektiewe RunAs- en argumentbeleid, enige opdragweierings, of sudo werklik die gekose veranderlike vir dié opdrag behou en of die gebruiker ’n leesbare konfigurasiepad beheer. ’n Behoue veranderlike of geïnstalleerde Neofetch alleen is ’n leidraad vir ondersoek. Gaan beleid en lêermetadata na sonder om die bevoorregte opdrag uit te voer of konfigurasie-inhoud te vertoon; sien [sudoers se hantering van omgewingsveranderlikes](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

’n Onbeperkte, root-bevoegde sudo-reël vir `facter` verdien ’n afsonderlike ondersoek na pasgemaakte facts. [Puppet dokumenteer](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) dat `--custom-dir` Ruby-factlêers uit ’n gekose gids laai. Gaan na of die presiese sudo-reël dié opsie toelaat, of die geïnstalleerde Facter dit aanvaar en of die gebruiker die gids beheer. ’n Toekenning met vaste argumente, ’n uitdruklike opdragweiering of gedeaktiveerde pasgemaakte facts kan die uitkoms verander. Passiewe enumerasie behoort die moontlike reël aan te meld sonder om Facter uit te voer of fact-inhoud te lees.

Vir ’n presiese, root-bevoegde sudo-skriptoekenning met `SETENV`, ondersoek kaal opdragname soos `find` en die effektiewe `PATH` ná sudo-beleid en skrip-inisialisering. ’n Bash-lêer wat ingesluit word, kan ook `enable -n [` uitvoer: [Bash soek dan `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) vir ’n eksterne `[` waar die skrip later daardie opdrag gebruik. Bevestig die toepaslike [sudoers-omgewings- en `secure_path`-reëls](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), enige `NOSETENV`-/`NOEXEC`- of weieringsinskrywings, die skrip- en ingeslote lêervloei, en ’n uitvoerbare soekgids wat die gebruiker beheer. ’n Leesbare skrip met ’n kaal opdrag is ’n leidraad vir ondersoek, nie bewys van bevoorregte uitvoering nie; bekyk dit sonder om die sudo-reël uit te voer.
- ’n Bevoorregte skrip wat ’n vaste URL met `curl` ophaal, kan steeds ’n deur die gebruiker gekose antwoord aanvaar as ’n toepaslike sudo-reël `http_proxy` behou en die versoek deur daardie instaanbediener gestuur word. As die skrip die antwoord daarna aan ’n XML-ontleder deurgee wat eksterne entiteite oplos, kan ’n kwaadwillige antwoord lêers bekend maak wat die bevoorregte proses kan lees. Gaan die presiese sudo-omgewingsbeleid, `no_proxy`-uitsonderings, aangevraagde URL, ontlederkonfigurasie en afvoerbestemming na; ’n instaanbedienerveranderlike of XML-ontleder alleen is nie ’n kwesbaarheid nie. Die [dokumentasie oor curl se instaanbediener-omgewing](https://everything.curl.dev/usingcurl/proxies/env.html) beskryf die veranderlike se gedrag. Moenie netwerkversoeke maak of kwaadwillige XML ontleed tydens passiewe enumerasie nie.
- ’n Root-bevoegde sudo-skrip wat ’n PostScript-lêer uit data wat deur die gebruiker beïnvloed word saamstel en dan `ps2pdf -dNOSAFER` uitvoer, verdien ’n afsonderlike ondersoek na die invoervloei. Ghostscript dokumenteer dat hierdie vlag SAFER deaktiveer totdat `.setsafe` opgeroep word, waardeur PostScript-lêerbewerkings binne die proses se OS-toestemmings toegelaat word. ’n SQL-navraag wat uit ’n gebruikerargument saamgestel word, kan aanvallerbeheerde rye na die PostScript-sjabloon voer, maar ’n navraagstring of `ps2pdf`-aanroep alleen bewys nie dat die data uitvoerbare PostScript-sintaksis bereik nie. Bevestig die effektiewe sudo-reël, die presiese pad van invoer na sjabloon, enige ontsnapping, die geïnstalleerde Ghostscript-gedrag en of SAFER weer geaktiveer word voordat die dokument geïnterpreteer word. Moenie die bevoorregte omskakeling tydens passiewe enumerasie uitvoer nie. Sien [Ghostscript se dokumentasie oor `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Vir ’n sudo-reël wat ’n shell-skrip uitvoer, vergelyk behoue veranderlikes met die skrip self. ’n Konstruk soos `if $CHECK_CONTENT; then` voer die uitgebreide waarde as ’n opdrag uit, dus kan die behoud van `CHECK_CONTENT` opdraguitvoering toelaat selfs wanneer die skrippad en argumente vas is. Of die vertakking bereikbaar is en die omgewing werklik behou word, moet vir die spesifieke reël nagegaan word.<sup>[[2]](#references)[[22]](#references)</sup>
- ’n Python-skrip wat deur sudo toegelaat word, kan kode uit ’n skryfbare gids of kasgeheue-`.pyc`-lêer invoer. Die [gids oor voorregteverhoging](../linux-basics/linux-privilege-escalation/README.md) beskryf die kasgeheuegeval.
- ’n Vaste Python-skrip wat as root toegelaat word, kan steeds ’n interaktiewe ontfouter blootstel. Oproepe soos `pdb.set_trace()` of `pdb.post_mortem()` laat Python-stellings binne die ontfoute proses se konteks toe wanneer die gebruiker die breekpunt of uitsonderingshanteerder kan bereik **en die ontfouter se invoerstroom beheer**. Gaan die presiese sudo-RunAs-reël, verifikasie- en vertakkingsvoorwaardes, bereikbaarheid van uitsonderings, terminale-/invoereienaarskap en of die ontfouter in dieselfde bevoorregte proses loop na. ’n Sokversoek wat ’n uitsondering veroorsaak, gee nie op sigself toegang tot ’n ontfouter wat aan ’n ander terminale gekoppel is nie. [Vervangingsvelde kan eienskappe en sleutels van afbeeldings volg](https://docs.python.org/3/library/string.html#format-string-syntax), dus kan ’n aanvallerbeheerde veld voorwerpe ondersoek wat aan `format()` deurgegee word en data blootstel waartoe hulle toegang het, as die resultaat gedruk word of op ’n plek gestoor word waar die gebruiker dit kan lees. Gaan die effektiewe sudo-RunAs-identiteit, skryftoegang tot die spesifieke rekord, die datavloei na die formaatstring, watter voorwerpe deurgegee word en die sigbaarheid van die afvoer na. Dit is nie outomatiese kode-uitvoering nie, en ’n letterlike vertroude formaatstring met aanvallerbeheerde *waardes* is ’n ander geval. ’n Bekende geheim lei slegs tot ’n OS-rekeningsoorgang as daardie rekening dit aanvaar. Gaan die skrip en soktoestemmings na sonder om die bevoorregte bewerking uit te voer.

Passiewe ondersoek behoort net die reël en beperkte bronkode te lees, sonder om die kloon uit te voer.

Bevestig die presiese RunAs-gebruiker, toegelate subopdragte en argumente, geïnstalleerde omhulselkode en invoervalidering. Die naam van ’n bewaarplekprogram of ’n onbeperkte sudo-reël bewys nie opdraginspuiting nie. Bekyk die omhulsel sonder om tydens enumerasie ’n bevoorregte kloon uit te voer.

Tydens enumerasie, bekyk konfigurasie en toestemmings sonder om bedryfstoestand te verander; ’n `systemd-run`-aanroep binne die omhulsel is net relevant as die hek beïnvloed kan word.

Bevestig die geïnstalleerde program se URL-hantering, bestemmingpadkontroles, effektiewe sudo-reël en toeganklikheid van die afvoer. ’n Skryfbare `/tmp`-konfigurasiepad alleen is ’n leidraad vir ondersoek; bekyk die binêre lêer en lêermetadata sonder om die bevoorregte oordrag uit te voer.

[CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) het ’n spesiaal vervaardigde pleister toegelaat om ’n simboliese skakel te skep en daarna buite die werkgidsboom te skryf, selfs wanneer die opdrag nie `--unsafe-paths` aanvaar het nie. Gaan die effektiewe sudo-argumentreël, pleisterbron, RunAs-rekening se toegang tot die werkgids en die geïnstalleerde Git-regstelling of verskaffer-terugportering na. ’n Onbeperkte reël wat `--unsafe-paths` toelaat, hou ’n afsonderlike risiko in; nóg ’n Git-weergawe nóg toestemming vir `git apply` alleen bewys dat ’n beskermde lêer verander kan word. - ’n Root-bevoegde `clamscan --debug`-reël kan ’n leesgrens oorsteek as ’n minder bevoorregte gebruiker ’n DMG-beeld kan verskaf en die geïnstalleerde ontleder deur [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) geraak word, wat lêerinhoud via ontfoutingsafvoer kon blootstel. Gaan beleid en pakketmetadata na sonder om ’n spesiaal vervaardigde lêer te skandeer of beskermde afvoer tydens enumerasie te vertoon.
- ’n Root-bevoegde sudo-reël wat ’n gebruikerbeheerde geënkripteerde skyfbeeld oopmaak, saam met ’n tweede reël wat die gevolglike mapper koppel, kan gebruikerbeheerde lêers in die gasheer se mount-naamruimte invoer. Bevestig albei effektiewe reëls en argumente, beheer oor die beeld en mapper-naam, die werklike koppelteiken en die gevolglike lêereienaar en -modus. ’n set-user-ID-oorgang vereis daarby ’n toeganklike uitvoerbare lêer, koppelopsies wat dit toelaat (`nosuid` verhinder dit) en toepaslike proses- of MAC-beleid; die oopmaak of koppel van ’n beeld alleen is net ’n leidraad vir ondersoek. ’n Afsonderlike pad via ’n bestaande rugsteun vereis die werklike sleutel en ’n bruikbare leesbare geheim daarin. Gaan die beleid en paaie na sonder om tydens passiewe enumerasie ’n beeld oop te maak of te koppel. Sien die [cryptsetup-handleiding](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) en [koppelopsies](https://man7.org/linux/man-pages/man8/mount.8.html).

Die gebruiker kan moontlik ’n skryfbare gids kies en ’n uitvoerbare lêer met daardie relatiewe naam daarin plaas; ’n absolute pad elders in die skrip beskerm nie hierdie oproep nie. Bevestig die effektiewe reël, `runchdir` of ander gidsveranderende beleid, skripvloei en bereikbaarheid van die vertakking, skryfbare en uitvoerbare gids, en mount-/`NOEXEC`-beperkings voordat jy dit as kode-uitvoering beskou. As ’n skrip nie leesbaar is nie, bly die gedrag onbekend totdat die bronkode via ’n gemagtigde pad ondersoek is. Beoordeel skripte staties in plaas daarvan om die helper uit te voer. Die [sudoers-handleiding](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) dokumenteer werkgidsbeleid.

[Python se dokumentasie oor `eval()` waarsku teen onbetroubare invoer](https://docs.python.org/3/library/functions.html#eval): ’n invoeragtervoegselkontrole, rekenkundige voorvoegsel of valideringsvertakking vorm nie ’n sandbox as die oorblywende uitdrukking `eval` bereik nie. Bevestig die effektiewe sudo-reël, of die gebruiker die presiese lêer kan kies en beheer, die ontleder se vertakkingsvoorwaardes en uitdrukkingbou, en die bevoorregte prosesidentiteit voordat jy dit ’n uitvoeringspad noem. Die teenwoordigheid van `eval` in ’n leesbare skrip is alleen net ’n leidraad; bekyk die bronkode en lêertoestemmings sonder om die valideerder uit te voer of tydens enumerasie ’n toetsuitdrukking in te dien.
- ’n Root-bevoegde sudo-Ruby-omhulsel wat ’n relatiewe YAML-lêernaam lees, soos `YAML.load(File.read("dependencies.yml"))`, kan invoer uit die gebruiker se werkgids neem tensy die omhulsel of sudo-beleid daardie gids vasstel. Gaan die presiese toegelate argumente, gids- en lêertoestemmings en die geïnstalleerde Psych-gedrag na: ouer `YAML.load`-implementasies kon willekeurige Ruby-objekte deserialiseer, terwyl nuwer weergawes klasse by verstek beperk. ’n Statiese oproepplek is net ’n leidraad; bevestig dat die lêer werklik uit ’n skryfbare gids van die gebruiker kom en dat die geïnstalleerde laaier gevaarlike klasse aanvaar. Bevestig die effektiewe RunAs, opdragargumente en -weierings, ’n skryfbare huidige gids vir die gebruiker, datavloei vanaf WASM na die vertakking en of dié vertakking die helper aanroep. ’n Vaste sudo-`runchdir`, `os.Chdir` of [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) kan die opsoekplek verander. Die blote statiese voorkoms saam is net ’n moontlike geval; bekyk die bronkode sonder om Go, WASM of die helper uit te voer.

Vir ’n `sudoedit`-toekenning oor gebruikersgrense heen op ’n jokertekenpad, ondersoek die effektiewe `sudoedit_follow`- of `FOLLOW`-instelling, `sudoedit_checkdir`, die opgeloste teiken en wie elke ouerinskrywing kan vervang. Eersgenoemde kan dit moontlik maak om ’n simboliese skakel te volg, terwyl die deaktivering van laasgenoemde kontroles op skryfbare gidse verwyder; nie een instelling alleen bewys dat ’n ander gebruiker se lêer geskryf kan word nie. Bevestig die geïnstalleerde sudo-beleid en presies ooreenstemmende argumente voordat jy dié gevolgtrekking maak. Gaan die presiese RunAs-gebruiker, opdragpad, argumentpatroon en latere weierings na; ’n gedemonstreerde lêerlesing impliseer nie kode-uitvoering nie. Gaan die effektiewe reël, latere weierings, padnaamresolusie, beheer oor die teikenlêer en enige sudoers-reëlmatige-uitdrukking- of digest-beperkings na voordat jy kode-uitvoering aflei. Sien die [sudoers-jokertekenreëls](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) en [Node se opdraglyndokumentasie](https://nodejs.org/api/cli.html).

### Bou- en pakketnutsgoed wat met sudo loop

’n Onbeperkte sudo-toekenning vir Foundry se `forge` kan saak maak selfs wanneer die RunAs-identiteit ’n ander nie-root-gebruiker is. Samestelleropsies soos `--use` kan ’n plaaslike uitvoerbare lêer kies, en `forge flatten -o` kies ’n uitvoerlêer. Gaan die geïnstalleerde Forge-weergawe, presiese sudo-argumente, toeganklike projek- en samestellerpaaie, uitvoertoestemmings en effektiewe omgewing na voordat jy die toekenning as uitbuitbaar beskou. ’n Relatiewe helper-uitvoerbare lêer wat via `PATH` gevind word, is ’n weergawe- en omgewingsafhanklike pad; moenie aanvaar dat dit by elke Forge-bou voorkom nie.<sup>[[23]](#references)[[24]](#references)</sup>

’n Onbeperkte, root-bevoegde `pacman`-toekenning laat meer as pakketnavrae toe: `-U` aanvaar ’n plaaslike pakket, pakkette kan installasieskripte bevat, en `--hookdir` kies ’n ander haakgids. Gaan die effektiewe sudo-reël, argumentbeperkings en -uitsluitings na voordat jy toets; passiewe enumerasie vereis nie dat ’n pakket geïnstalleer of ’n haak uitgevoer word nie.<sup>[[25]](#references)[[26]](#references)</sup>

’n Vaste sudo-shell-omhulsel kan ook ’n genoemde npm-afhanklikheid installeer en daarna ’n Node-toepassing begin. Gaan die presiese RunAs-reël na, of die pakket reeds geïnstalleer is, die effektiewe `HOME` en npm-`userconfig`, projekkonfigurasie of opdragreël-oorheersings, en of ’n minder bevoorregte gebruiker die register of pakket wat vir dié naam teruggestuur word, beheer. [npm dokumenteer opsoeke na `.npmrc` per gebruiker en projek](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo se `HOME`-gedrag hang af van die geïnstalleerde beleid en verspreiding, dus word ’n skryfbare `.npmrc` van die gebruiker moontlik deur die bevoorregte npm-proses gelees, of moontlik nie. As die nuut geïnstalleerde pakket deur die bevoorregte toepassing ingevoer word, kan sy modulekode onder daardie toepassing se identiteit loop. Installasieskripte is ’n afsonderlike, weergawe- en konfigurasieafhanklike pad; [npm dokumenteer hul lewensiklus en gebruikershantering](https://docs.npmjs.com/cli/v6/using-npm/scripts/). ’n `.npmrc`-pad of `npm install`-reël alleen is net ’n leidraad vir ondersoek. Gaan die reël, kort omhulsel, konfigurasiepaaie en pakketherkoms na sonder om tydens passiewe enumerasie die pakket te installeer of die toepassing te begin.

’n Root-bevoegde `pip`- of `pip3 download`-toekenning is ook ’n leidraad om pakketbou te ondersoek wanneer die argumente die gebruiker toelaat om ’n onbetroubare brondistribusie te kies, selfs al beperk die URL-patroon dit tot ’n plaaslike diens en ’n `.tar.gz`-agtervoegsel. `pip download` aanvaar argief-URL’s en los pakketmetadata op; die voorbereiding van ’n sdist kan die bou-agtergrond of verouderde `setup.py`-kode uitvoer voordat die argief bloot gestoor word. Bevestig die presiese sudo-RunAs- en argumentreël, of die gebruiker die gekose argief kan publiseer of vervang, en of daardie pip-weergawe sy metadata werklik voorberei. ’n Vaste vertroude argief of wheel bevestig nie dié pad nie. Moenie tydens passiewe enumerasie ’n onbetroubare pakket ophaal of bou nie. Sien pip se [download-opdrag](https://pip.pypa.io/en/stable/cli/pip_download/), [boustelsel-koppelvlak](https://pip.pypa.io/en/stable/reference/build-system/) en [riglyne vir veilige installasie](https://pip.pypa.io/en/stable/topics/secure-installs/).

’n Sudo-reël wat `pip install` met ’n plaaslike projekpad wat die gebruiker kies toelaat, skep ’n meer direkte bougrens. [pip aanvaar plaaslike projekgidse](https://pip.pypa.io/en/stable/topics/local-project-installs/) en roep hul boustelsel aan; die [bou-agtergrond voer bouhake uit wat deur die projek beheer word](https://pip.pypa.io/en/stable/reference/build-system/). Bevestig die effektiewe RunAs-identiteit, presiese argumentbeperkings en -weierings, beheer oor die gekose projek en die geïnstalleerde pip-/agtergrondgedrag voordat jy die reël as bevoorregte kode-uitvoering beskou. ’n Vaste vertroude projek of ’n reël wat gebruiker-gekose paaie uitsluit, bevestig nie dié pad nie. Gaan padkanonisering, simboliese skakels en direktiefontleding na voordat jy ’n gevolgtrekking maak.

### nginx wat met sudo loop en ’n gebruikerbeheerde konfigurasie gebruik

’n Onbeperkte, root-bevoegde `nginx`-reël kan toelaat dat [`-c` ’n ander konfigurasie kies](https://nginx.org/en/docs/switches.html). Gaan die presiese sudo-argumente en -uitsluitings na, of die gebruiker die konfigurasie kan verskaf, en of die gevolglike meesterproses of werkers toegang tot beskermde paaie behou. ’n Gekose `root` saam met `autoindex` kan lêers via ’n nuwe luisteraar blootstel; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kan ’n bevoorregte lêerskryfpad bied, maar die DAV-module word nie by verstek gebou nie en sy teenwoordigheid, luisteraarbereikbaarheid, lêertoestemmings en tydelike-lêergedrag moet nagegaan word. Die [`error_log`-direktief](https://nginx.org/en/docs/ngx_core_module.html#error_log) kan ook na ’n gekose lêer wys; om logs na ’n sensitiewe konfigurasielêer soos `/etc/ld.so.preload` te skryf, vereis ’n effektiewe bevoorregte skrywer en ’n loginskrywing wat beheer kan word voordat dit ’n voorregteverhogingspad word. Die uitvoerbare lêer se merker in `sudo -l` is ’n leidraad, nie bewys dat enige van dié paaie werk nie. Passiewe enumerasie behoort nie nginx te begin of te herkonfigureer nie.

### Patroonvergelyking in bevoorregte Bash-aanwysings

Wanneer ’n Bash-skrip wat deur sudo toegelaat word ’n waarde van die gebruiker lees en dit met `[[ "$expected" == $entered ]]` kontroleer, interpreteer Bash die ongekwoteerde regter operand as ’n patroon. ’n Jokerteken kan dus die vergelyking laat slaag sonder kennis van die verwagte waarde. As die operand gekwoteer word (`[[ "$expected" == "$entered" ]]`), word dit ’n letterlike stringvergelyking. Gaan die presiese sudo-reël na, of die aanwysing bereikbaar is en wat die skrip ná die vergelyking doen; die sintaksis alleen bevestig nie ’n uitbuitbare pad nie. Vermy dit om die verwagte waarde tydens enumerasie te vertoon. Sien die [verwysing oor Bash-voorwaardelike konstruksies](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers wat ’n lêer aflaai en uitvoer met sudo

’n Onbeperkte, root-bevoegde sudo-toekenning vir ’n pasgemaakte helper verdien ’n ondersoek na die datavloei as dit ’n URL aanvaar wat die gebruiker kies, die antwoord op skyf skryf en daardie lêer later met ’n interpreter of shell uitvoer. [Sudoers laat arbitrêre argumente toe wanneer ’n opdraginskrywing geen argumente lys nie](https://man7.org/linux/man-pages/man5/sudoers.5.html); ’n vaste uitvoerbare pad beperk nie wat sy argumente kan kies nie. Bevestig die werklike URL-validering, uitvoerpad, suksesvertakking en latere uitvoering in die geïnstalleerde helper. ’n Ooreenstemmende libcurl-invoer of drukbare string alleen bewys nie dié ketting nie.

Selfs ’n vaste uitvoerbasisnaam kan tussen skryf en uitvoering vervang word wanneer die helper ’n **relatiewe pad in ’n werkgids wat die gebruiker beheer** gebruik. Die hernoeming of vervanging van ’n root-besitte lêer word beheer deur skryf- en soektoegang tot die gids en enige sticky-bit-beperkings, nie net deur die lêer se modus nie; sien [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Gaan na of die helper die pad later heropen of die reeds oop lêerbeskrywer gebruik, en of dit voor skryf na ’n vertroude gids verander. Ondersoek sudo-beleid, helper en gidsmetadata passief; moenie tydens enumerasie die bevoorregte aflaai uitvoer of ’n wedloop probeer nie.

’n Root-sudo-aflaaihelper kan ook **argument**-inspuiting blootstel wanneer dit ’n Bash-opdragstring soos `curl <caller input> -o <fixed output>` saamstel. ’n Filter wat spasies verwerp, laat steeds [Bash se krulhakie-uitbreiding](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) toe: ongekwoteerde, komma-geskeide elemente kan aparte curl-argumente word. As die invoer curl voor die vaste `-o` bereik, kan ’n gebruiker-voorsiene uitvoeropsie die bestemming vir die eerste URL onder die helper se identiteit kies; [curl koppel uitvoeropsies volgens die volgorde van URL’s](https://curl.se/docs/manpage.html#-o). Bevestig die presiese shell, aanhalingstekens, invoervalidering, effektiewe sudo-reël, curl-argumentvolgorde en ondersteunde URL-skemas, en of die gebruiker die afgelaaide grepe beheer of die resultaat kan lees. ’n PyInstaller-verpakte uitvoerbare lêer kan Python-toepassingslogika bevat, maar die verpakkingsmerker of ’n `curl`-string alleen bewys nie dié datavloei nie. Ondersoek ’n beperkte, vanlyn kopie indien gemagtig; gewone enumerasie behoort nie die helper uit te voer of gebruiker-gekose data op te haal nie.

’n Root-sudo-shell-skrip wat [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aanroep, kies net ’n ongebruikte naam; dit **skep nie** die lêer nie. As die skrip later dié naam in ’n gids skep wat ’n ander gebruiker kan beïnvloed, dit weer oopmaak en die inhoud daarvan by ’n beskermde bestemming soos root se `authorized_keys` voeg, ondersoek ’n moontlike tydelike-lêerwedloop. Bevestig die presiese sudo-reël, gids- en lêereienaarskap, skeppings- en heropeningsvolgorde, kernbeskermings en of die bevoorregte skryfbewerking werklik grepe gebruik wat deur die aanvaller beheer word. ’n `mktemp -u`-string of skryfbare `/tmp` alleen bewys nie die wedloop nie. Ondersoek die skrip en padmetadata sonder om dit uit te voer of tydens enumerasie met die tydelike lêer te wedloop.

## Defensiewe notas

- Vermy dit om interpreters of interaktiewe redigeerders via sudo toe te laat.<sup>[[1]](#references)</sup>
- Verkies vaste, root-besitte omhulsels wat een nou afgebakende administratiewe handeling uitvoer.<sup>[[1]](#references)[[2]](#references)</sup>
- As ’n interpreter noodsaaklik is, beperk die presiese skrippad en voorkom gebruikerbeheerde argumente, skryfbare invoere, `PYTHONPATH` en onveilige behoud van die omgewing.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- As lêerredigering nodig is, beperk die presiese lêerpad en oorweeg `sudoedit` met reggemaakte sudo-weergawes en streng hantering van die omgewing.<sup>[[1]](#references)[[2]](#references)</sup>
- Gaan `SETENV`, `env_keep`, skryfbare werkgidse, skryfbare module-/invoer paaie, `NOEXEC`, `use_pty` en logging na, maar moenie dit as ’n volledige sandbox beskou nie.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
