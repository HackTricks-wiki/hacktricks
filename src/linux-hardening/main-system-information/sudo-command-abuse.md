## Interpréteurs autorisés par sudo

Si `sudo -l` permet à un utilisateur d’exécuter un interpréteur en tant que root, considérez cela comme une exécution directe de code. Les interpréteurs sont conçus pour exécuter du code arbitraire ; une règle qui autorise les binaires `python3`, `perl`, `ruby`, `lua`, `node` ou similaires équivaut généralement à l’exécution de commandes en tant que root, sauf si les arguments sont strictement limités et validés.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Procédure courante : commencez par lister les privilèges de l’utilisateur, puis exécutez une instruction Python avec l’option `-c` de l’interpréteur.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

D’autres exemples d’interpréteurs sont présentés ci-dessous ; les interpréteurs mentionnés documentent l’exécution de code inline ou les API de processus enfants.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Le chemin exact compte. Si la règle sudo autorise `/usr/bin/python3`, utilisez ce chemin exact lors de la validation.<sup>[[2]](#references)</sup>

Un glob d’exécutable sudo tel que `/usr/bin/python*` peut aussi autoriser Python 2 pour un script écrit pour Python 3. Si le script atteint `input()` avec du texte contrôlé par l’appelant, [Python 2 évalue ce texte comme une expression](https://docs.python.org/2/library/functions.html#input) ; l’invocation explicite de l’interpréteur prévaut sur le shebang du script. Vérifiez les binaires correspondants installés, l’identité RunAs effective et la politique relative aux arguments, les refus, ainsi que la possibilité d’atteindre la saisie, avant de considérer cela comme une voie d’exécution.

Un chemin de script fixe dans une règle sudo permettant l’exécution en tant que root ne limite pas ce que le script exécute. Pour un wrapper Bash lisible, vérifiez si sa première commande exécutable utilise un paramètre positionnel non cité tel que `$1` comme **mot de commande**, alors que sudo autorise l’appelant à choisir les arguments. Confirmez l’identité RunAs effective, la politique relative au mot de passe et aux arguments, les refus ultérieurs et la branche réellement exécutée du script ; `NOEXEC`, une liste d’arguments sûrs fixe ou un wrapper qui valide sa commande peuvent changer le résultat. Examinez statiquement le court script pendant l’énumération au lieu de l’exécuter avec une commande de test.

Une règle sudo sans restriction permettant l’exécution de `dotnet` en tant que root mérite également un examen de l’interpréteur. Si un SDK .NET est installé, [`dotnet fsi` exécute du code F# de manière interactive ou depuis un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), et [`dotnet run` exécute un projet à partir du code source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirmez d’abord l’identité RunAs effective et la politique exacte relative aux arguments : une règle limitée à une sous-commande sûre précise ou à une application de confiance constitue une autorisation différente, et une installation limitée au runtime peut ne pas inclure les commandes du SDK. Le nom de l’exécutable est un indice à examiner, pas une preuve d’exécution de code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` autorisé par sudo : écriture arbitraire de fichiers avec privilèges élevés

GNU `tee` copie l’entrée standard vers chaque chemin fourni comme opérande de fichier. Par conséquent, une règle sudo qui autorise l’exécution de `/usr/bin/tee` en tant que root avec des arguments contrôlés par l’appelant permet de créer ou d’écraser arbitrairement des fichiers avec les privilèges root. L’ajout de `-a` transforme cette primitive en ajout au fichier. Une étiquette `PASSWD:` concerne l’authentification sudo ; à elle seule, elle ne limite ni la destination ni les octets lus depuis l’entrée standard.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Commencez par examiner la règle exacte. Sur un système de test autorisé, validez la primitive uniquement avec une destination temporaire qu’il est sans risque de créer. Le `>/dev/null` final supprime uniquement la copie de `tee` vers la sortie standard.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Placer `sudo` avant le producteur ne permet pas d’élever les privilèges d’une redirection shell ultérieure, car c’est le shell de l’appelant qui ouvre la destination. Le processus privilégié doit être celui qui écrit, comme dans le pipeline ci-dessus.<sup>[[1]](#references)[[15]](#references)</sup>

Après avoir confirmé l’écriture, choisissez une cible appropriée pour l’exécution de code en tant que root dans [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Une chaîne observée utilisait `tee` exécuté en tant que root pour créer un fichier éphémère dans `/etc/cron.d/`, lancer une backdoor via un script contrôlé par l’utilisateur, puis supprimer le fichier cron après l’exécution. La suppression du fichier cron empêchait qu’il devienne un mécanisme de persistance à long terme, bien que les journaux système aient conservé des traces de l’activité.<sup>[[27]](#references)</sup>

## Éditeurs autorisés par sudo

Si `sudo -l` permet à un utilisateur d’exécuter un éditeur interactif en tant que root, considérez-le comme une surface d’exécution de commandes, et non comme une autorisation inoffensive de modifier des fichiers. Les éditeurs peuvent souvent exécuter des commandes shell, lire des fichiers arbitraires, écrire des fichiers arbitraires ou invoquer des programmes externes depuis l’éditeur.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Procédure d’examen courante : listez les privilèges de l’utilisateur, puis lancez sous sudo chaque éditeur ou pager autorisé.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Exécution de commandes avec Nano

Lorsque `nano` est autorisé via sudo, l’exécution de commandes peut être accessible depuis l’interface de l’éditeur.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Fournissez ensuite une commande telle que `id` ou `/bin/sh` à l’invite de commande de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactif ne dispose pas de flux de terminal utilisables, cette forme de redirection envoie sa sortie standard et ses erreurs vers le descripteur 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La séquence exacte de touches peut varier selon la version de nano et les options de compilation, mais le problème de sécurité reste le même : l’éditeur s’exécute en tant que root et peut lancer des commandes externes.<sup>[[1]](#references)[[12]](#references)</sup>

### Autres échappatoires courantes dans les éditeurs

Les éditeurs de type Vim permettent couramment d’exécuter des commandes via `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Les pagers tels que `less` peuvent également permettre l’exécution de commandes shell.<sup>[[14]](#references)</sup>

Une règle sudo autorisant `apport-cli` en tant que root mérite le même examen du pager. Certaines versions d’Apport pouvaient ouvrir un rapport de crash dans `less` avec une taille de terminal modifiable par un attaquant ; le pager pouvait alors fournir un root shell si les conditions particulières liées à sudo et au pager étaient réunies. Vérifiez la règle sudo effective, la configuration du pager et le correctif du paquet de la distribution avant de considérer que la version seule est vulnérable. Lors d’une énumération passive, consultez les métadonnées du paquet et de la politique sans provoquer de crash ni ouvrir le rapport privilégié. [La fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2023-1326) répertorie les versions corrigées des paquets propres à chaque version, y compris les correctifs rétroportés.

```text
!/bin/sh
```

## Autres risques liés aux règles sudo et doas

Commencez par `sudo -l`, `sudo -V` et toute règle `doas` applicable. Examinez ensemble la commande autorisée, l’utilisateur d’exécution, les arguments, l’environnement et les valeurs par défaut. L’autorisation d’exécuter une commande en tant qu’un compte de service non root peut quand même exposer les fichiers de ce compte ou offrir une voie vers root.

Un script Python fixe autorisé par sudo peut tout de même exécuter une commande shell sous l’identité RunAs si une entrée interactive contrôlée par l’appelant est concaténée dans [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Une denylist de la ponctuation shell ne suffit pas à garantir la sécurité : [le shell reconnaît aussi la substitution de commande `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Vérifiez que les arguments autorisés atteignent la branche qui traite l’entrée, que celle-ci arrive à la commande shell sans validation sûre et que la politique sudo effective autorise l’utilisateur RunAs visé. Le chemin du script ou un appel à `os.system()` ne sont que des pistes à examiner ; inspectez le code source sans lancer le script privilégié.

Une autorisation sudo effective en tant que root pour `chattr` peut supprimer l’attribut de fichier immuable (`i`), mais cela ne confère à lui seul ni droit d’écriture ni nouvelle identité. [Le manuel de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indique que cet attribut bloque les modifications et que seul root ou un processus doté de `CAP_LINUX_IMMUTABLE` peut le modifier. Vérifiez la politique exacte des arguments sudo et la prise en charge du système de fichiers, puis vérifiez séparément que l’appelant peut écrire dans le fichier une fois l’attribut supprimé et qu’un processus de niveau supérieur l’utilise. Le remplacement d’un shell de connexion, par exemple, nécessite également que les identifiants acceptés du compte ciblé soient disponibles et qu’une connexion réelle utilise ce shell. Lors de l’énumération, examinez la politique, les attributs du fichier et les permissions sans les modifier.

Si sudo demande à la fois un mot de passe et un code à usage unique, distinguez ces prérequis de l’autorisation de commande. Un fichier `.google_authenticator` lisible contient un secret sensible, tandis qu’un ancien hash de mot de passe d’application ou de base de données n’est qu’un candidat pour le mot de passe actuel du compte ; aucun des deux ne prouve que l’autre facteur est accepté par la configuration PAM effective. Une fois autorisé, examinez l’utilisateur RunAs et les arguments exacts : une autorisation root sans restriction pour RubyGems `gem` peut exposer sa commande d’éditeur ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mais une autorisation limitée ou un échec d’authentification ne le permet pas. L’énumération passive doit signaler les chemins et la politique sans afficher le secret, retrouver un mot de passe, générer un code ni lancer la commande privilégiée.

Une autorisation sudo sans restriction permettant à Chef `knife` de fonctionner avec les privilèges root mérite un examen au niveau de l’interpréteur : [Chef indique que `knife exec -E` évalue localement une chaîne Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Vérifiez que la règle sudo effective autorise le sous-commande `exec` et l’argument `-E` fourni par l’appelant, l’identité RunAs visée et toute interdiction de commande ou tout argument fixe correspondant. Le binaire installé ou une règle limitée à d’autres sous-commandes ne sont que des pistes. L’énumération passive doit signaler la règle sans lancer `knife`.

Une autorisation sudo exacte permettant de lancer `msfconsole` en tant que root est tout aussi sensible : [GTFOBins documente sa console `irb`](https://gtfobins.org/gtfobins/msfconsole/), qui peut hériter de l’identité sudo. Vérifiez l’utilisateur RunAs effectif, la liste des arguments autorisés, les interdictions de commande, `NOEXEC` ou autres restrictions, le comportement de la console installée et la possibilité pour l’appelant de fournir une entrée interactive. La simple présence du chemin est une piste à examiner ; l’énumération passive ne doit pas lancer la console.

Sur FreeBSD, même une règle sudo limitée à `pkg update` et `pkg install *` en tant que root nécessite d’examiner la confiance accordée aux dépôts. Vérifiez si `/etc/hosts` est modifiable par l’appelant et si la configuration effective des dépôts activés utilise un nom d’hôte HTTP avec `signature_type: none`. [Le manuel `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indique que `none` désactive les vérifications de signature ; `pkg+http` à lui seul ne le démontre pas. Un paquet peut contenir des scripts d’installation ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), de sorte qu’un appelant qui contrôle réellement le point de terminaison du dépôt et peut choisir un paquet peut franchir la frontière root. Vérifiez les substitutions de dépôt, la résolution SRV/des miroirs, les arguments sudo effectifs, le choix du paquet et l’exécution des scripts avant de conclure. Examinez la politique et les petits fichiers de configuration locaux sans rediriger de noms ni lancer `pkg` pendant l’énumération.

Une autorisation sudo permettant à `apt-get update` et `apt-get upgrade` de fonctionner en tant que root nécessite aussi d’examiner la confiance accordée aux dépôts si sudo conserve un `http_proxy` contrôlé par l’appelant. Vérifiez si la configuration APT effective utilise réellement cette variable et quelles requêtes vers les dépôts activés elle peut affecter ; un proxy seul ne peut pas remplacer les paquets d’une archive authentifiée par une clé de signature fiable. [Le manuel du transport HTTP d’APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documente la priorité des proxys et [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documente les vérifications de signature, les substitutions pour dépôts non sécurisés et la confirmation requise pour les paquets non authentifiés. Vérifiez l’utilisateur RunAs et les arguments exacts de sudo, la politique d’authentification des dépôts, toute confirmation interactive requise et si la mise à niveau choisie exécute des scripts de paquet en tant que root. Examinez passivement la politique et la configuration locale ; ne redirigez pas le trafic des paquets et ne lancez pas de mise à niveau pendant l’énumération.

Une règle sudo permettant à `snap install` de fonctionner en tant que root peut créer une frontière entre paquet et code si ses arguments autorisent l’appelant à choisir un snap local et un mode d’installation permissif. [La documentation Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) indique que `--dangerous` ignore les vérifications d’assertion des snaps locaux et que `--devmode` assouplit le confinement ; [un hook d’installation peut s’exécuter lors de l’installation initiale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Avant de conclure à un accès aux fichiers hôte protégés, vérifiez la politique sudo exacte des arguments et de RunAs, qui contrôle le fichier snap, si ces modes sont acceptés par la version de snapd installée, ainsi que l’identité effective et le confinement du hook. Un binaire `snap` ou une règle qui semble utiliser un joker ne suffit pas à prouver cette chaîne. L’énumération passive ne doit ni installer de paquet ni exécuter son hook.

Pour une autorisation sudo exacte visant un binaire personnalisé de lecture d’identifiants exécuté en tant que compte **non-root**, inspectez d’abord le binaire autorisé et ses permissions sans le lancer. Un contrôle de mot de passe intégré peut n’être visible qu’en caractères larges ; [GNU `strings` documente l’extraction 16 bits little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Une chaîne visible ne prouve ni qu’il s’agit du mot de passe accepté ni que la branche de succès expose un identifiant actuel. Vérifiez séparément le comportement du binaire, l’accès du compte cible aux données protégées, la validité des identifiants et toute transition ultérieure de compte ou de groupe. Si ce compte appartient à `docker`, vérifiez l’accès au socket et l’identité rootful ou rootless du daemon avant d’inférer un accès root à l’hôte ; [Docker documente les implications de son groupe sur les privilèges root](https://docs.docker.com/engine/install/linux-postinstall/). L’énumération courante doit signaler la règle sudo et l’appartenance au groupe sans exécuter le binaire ni afficher ses chaînes.

Une règle sudo utilisant un joker pour des scripts de maintenance d’application doit être examinée au-delà du chemin du script. Vérifiez si le script autorisé accepte des arguments sans restriction ou lit des paramètres modifiables par un compte d’application moins privilégié, puis suivez ces valeurs jusqu’aux commandes shell ou à l’environnement d’un sous-processus. Par exemple, ZoneMinder [`zmupdate.pl` construit une commande `mysqldump` et l’exécute avec `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), tandis que [`zmdc.pl` copie le paramètre `ZM_LD_PRELOAD` dans `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) avant de lancer des daemons. Une règle sudo autorisant l’un ou l’autre script en tant que root peut franchir une frontière de confiance si l’entrée correspondante est contrôlable et atteint ce code dans la version installée. Examinez la règle sudo effective, les droits sur la configuration de l’application et le code source du script ; le joker ou le paramètre seul est une piste à examiner, pas une preuve d’exécution.

- `SETENV`, `env_keep`, `secure_path` et `LD_PRELOAD` peuvent transformer une commande autrement limitée en détournement d’import, de bibliothèque ou de `PATH`. Consultez le [guide des variables d’environnement](../linux-basics/linux-environment-variables.md) et [l’abus de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Une autorisation `SETENV` exacte permettant à un wrapper shell de fonctionner en tant que root mérite aussi un examen limité à un saut si le wrapper lance un script Python fixe avec un import littéral. `secure_path` limite la recherche des commandes shell, mais pas la [recherche de modules Python via `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) ; [`-E` et `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) indiquent à Python d’ignorer cette variable d’environnement. Avant de considérer qu’il s’agit d’une exécution de code, vérifiez les tags sudo et interdictions effectifs, la branche du wrapper, les options de l’interpréteur, la résolution de l’import et l’existence d’un répertoire de recherche modifiable par l’appelant. Inspectez statiquement les scripts courts ; ne lancez pas le wrapper privilégié.

Une autorisation sudo exacte pour `neofetch ""` en tant que root peut tout de même charger un fichier de configuration shell si les valeurs par défaut sudo applicables conservent un `XDG_CONFIG_HOME` contrôlé par l’appelant. [Le chargeur de configuration de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) source `neofetch/config.conf` ou `neofetch/config` sous ce répertoire ; la liste d’arguments vide n’empêche pas cette recherche. Vérifiez le chargeur installé, l’utilisateur RunAs et la politique d’arguments effectifs, les éventuelles interdictions de commande, si sudo conserve réellement la variable choisie pour cette commande et si l’appelant contrôle un chemin de configuration lisible. Une variable conservée ou Neofetch installé n’est qu’une piste à examiner. Examinez la politique et les métadonnées des fichiers sans lancer la commande privilégiée ni afficher le contenu de la configuration ; consultez [la gestion de l’environnement par sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Une règle sudo sans restriction permettant à `facter` de fonctionner en tant que root mérite un examen distinct des custom facts. [Puppet indique](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` charge des fichiers de facts Ruby depuis un répertoire sélectionné. Vérifiez si la règle sudo exacte autorise cette option, si la version de Facter installée l’accepte et si l’appelant contrôle le répertoire. Une autorisation à arguments fixes, une interdiction explicite de commande ou la désactivation des custom facts peut changer le résultat. L’énumération passive doit signaler cette règle candidate sans lancer Facter ni lire le contenu des facts.

Pour une autorisation sudo exacte d’un script root avec `SETENV`, examinez les noms de commandes nus comme `find` et le `PATH` effectif après application de la politique sudo et de l’initialisation du script. Un fichier Bash sourcé peut aussi exécuter `enable -n [` : [Bash recherche alors dans `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un `[` externe lorsque le script utilise plus tard cette commande. Vérifiez les [règles sudoers d’environnement et de `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) applicables, les éventuelles entrées `NOSETENV`/`NOEXEC` ou interdictions, le déroulement du script et des fichiers sourcés, ainsi que l’existence d’un répertoire de recherche exécutable contrôlé par l’appelant. Un script lisible contenant une commande nue est une piste, pas une preuve d’exécution privilégiée ; inspectez-le sans utiliser la règle sudo.
- Un script privilégié qui récupère une URL fixe avec `curl` peut tout de même accepter une réponse choisie par l’appelant si une règle sudo applicable conserve `http_proxy` et que la requête passe par ce proxy. Si le script transmet ensuite la réponse à un parseur XML qui résout les entités externes, une réponse malveillante peut divulguer des fichiers lisibles par le processus privilégié. Vérifiez la politique exacte de l’environnement sudo, les exclusions `no_proxy`, l’URL demandée, la configuration du parseur et la destination de la sortie ; une variable proxy ou un parseur XML seul ne constitue pas une vulnérabilité. La [documentation de l’environnement proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) décrit le comportement des variables. Ne faites pas de requêtes réseau et n’analysez pas de XML malveillant pendant l’énumération passive.
- Un script sudo en tant que root qui construit un fichier PostScript à partir de données influencées par l’appelant, puis exécute `ps2pdf -dNOSAFER`, mérite un examen distinct du flux d’entrée. Ghostscript indique que ce flag désactive SAFER jusqu’à `.setsafe`, ce qui autorise les opérations sur les fichiers PostScript dans les limites des permissions du processus sur le système d’exploitation. Une requête SQL assemblée à partir d’un argument fourni par l’appelant peut injecter des lignes contrôlées dans le modèle PostScript, mais une chaîne de requête ou un appel à `ps2pdf` ne prouve pas à lui seul que les données atteignent une syntaxe PostScript exécutable. Vérifiez la règle sudo effective, le chemin exact entre l’entrée et le modèle, tout échappement, le comportement de Ghostscript installé et si SAFER est réactivé avant l’interprétation du document. Ne lancez pas la conversion privilégiée pendant l’énumération passive. Consultez la [documentation de `-dNOSAFER` de Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Pour une règle sudo qui exécute un script shell, comparez les variables conservées au script lui-même. Une construction telle que `if $CHECK_CONTENT; then` exécute la valeur développée comme une commande ; conserver `CHECK_CONTENT` peut donc permettre l’exécution de commandes même si le chemin et les arguments du script sont fixes. Vérifiez que la branche est atteignable et que l’environnement est effectivement conservé pour la règle concernée.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script Python autorisé par sudo peut importer du code depuis un répertoire modifiable ou un fichier `.pyc` en cache. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md) détaille le cas du cache.
- Un script Python fixe autorisé par sudo à fonctionner en tant que root peut tout de même exposer un débogueur interactif. Des appels comme `pdb.set_trace()` ou `pdb.post_mortem()` permettent d’exécuter des instructions Python dans le contexte du processus débogué si l’appelant peut atteindre le point d’arrêt ou le gestionnaire d’exception **et contrôler l’entrée du débogueur**. Vérifiez la règle sudo RunAs exacte, l’authentification et les conditions de branchement, l’accessibilité de l’exception, la propriété du terminal/de l’entrée et si le débogueur s’exécute dans ce même processus privilégié. Une requête socket qui déclenche une exception ne donne pas, à elle seule, accès à un débogueur attaché à un autre terminal. [Python documente l’évaluation d’instructions par le débogueur et le mode post-mortem](https://docs.python.org/3/library/pdb.html) ; inspectez statiquement le script au lieu de déclencher le gestionnaire privilégié pendant l’énumération.
- Un script Python fixe autorisé par sudo peut aussi lire un champ de profil depuis une base de données ou un socket Unix et l’ajouter à une chaîne qui devient ensuite la **chaîne de format** de `str.format()`. [Les champs de remplacement peuvent suivre des attributs et des clés de dictionnaire](https://docs.python.org/3/library/string.html#format-string-syntax) ; un champ contrôlé par un attaquant peut donc inspecter les objets transmis à `format()` et exposer les données accessibles depuis ceux-ci si le résultat est affiché ou stocké à un emplacement lisible par l’appelant. Vérifiez l’identité RunAs effective de sudo, les droits d’écriture sur l’enregistrement concerné, le flux de données vers la chaîne de format, les objets fournis et la visibilité de la sortie. Il ne s’agit pas automatiquement d’une exécution de code ; une chaîne de format littérale et fiable avec des *valeurs* contrôlées par un attaquant constitue un cas différent. Un secret divulgué ne permet une transition vers un compte du système d’exploitation que si ce compte l’accepte. Examinez le script et les permissions du socket sans invoquer l’opération privilégiée.
- Un wrapper Python exécuté en tant que root peut transmettre une URL choisie par l’appelant à `Repo.clone_from` de GitPython. Si le wrapper active également `protocol.ext.allow=always` pour Git, un dépôt distant `ext::` peut lancer un helper externe. Vérifiez les arguments sudo exacts, la provenance de l’URL, la version du paquet GitPython et les éventuels correctifs du fournisseur, ainsi que l’activation explicite des protocoles non sûrs par le wrapper. GitPython a ajouté une [protection par défaut contre les protocoles non sûrs](https://github.com/gitpython-developers/GitPython/commit/2625ed9) dans la version 3.1.30 ; la version de l’exécutable `git` est un élément distinct. L’examen passif doit se limiter à la règle et à une partie circonscrite du code source, sans lancer le clone.
- Une autorisation sudo entre utilisateurs pour un outil CLI de clonage de dépôts peut exposer une autre voie d’injection de chaîne shell. Vérifiez si l’argument du dépôt choisi par l’appelant parvient à [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js ou à un autre générateur de commandes shell sans séparation sûre des arguments ; `exec` de Node transmet sa chaîne de commande à un shell. Vérifiez l’utilisateur RunAs exact, les sous-commandes et arguments autorisés, le code du wrapper installé et la validation de l’entrée. Le nom d’un outil de dépôt ou une règle sudo sans restriction ne prouve pas à lui seul l’injection de commandes. Inspectez le wrapper sans lancer de clone privilégié pendant l’énumération.
- Un wrapper personnalisé détenu par root peut sembler sûr parce que ses binaires et scripts ne sont pas modifiables, alors que sa décision d’exécuter une action privilégiée dépend d’un flag, d’une valeur d’API locale ou d’un état de service modifiable par un utilisateur non privilégié. Remontez chaque condition jusqu’à son entrée et vérifiez les contrôles d’autorisation. Lors de l’énumération, inspectez la configuration et les permissions sans modifier l’état opérationnel ; un appel à `systemd-run` dans le wrapper n’est pertinent que si la condition peut être influencée.
- Un client de sauvegarde autorisé via sudo en tant que root peut accepter un fichier de configuration choisi par l’appelant (par exemple, `npbackup-cli -c`). Vérifiez l’utilisateur d’exécution et les arguments autorisés exacts, puis déterminez si l’appelant contrôle le chemin de configuration, les chemins sources de sauvegarde et les options de dépôt ou de lecture/restauration. Un secret de dépôt chiffré dans un fichier de configuration lisible peut rester utilisable par le client, mais la règle seule ne prouve ni l’accès au dépôt ni la divulgation de fichiers root. Validez l’autorisation sans lancer de sauvegarde ni en afficher le contenu.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) prend en charge `--password-command`, qui appelle un programme pour obtenir le mot de passe du dépôt. Si une règle sudo permet à un utilisateur moins privilégié d’exécuter restic en tant que root avec une commande de mot de passe choisie par l’appelant et une sous-commande qui nécessite le mot de passe, ce helper peut s’exécuter en tant que root. Examinez les arguments et exclusions sudo exacts ; ne lancez pas le helper ni une commande de sauvegarde simplement pour vérifier cette condition.
- Une autorisation privilégiée pour `restic backup` peut aussi franchir une frontière de lecture de fichiers si le modèle d’arguments sudo permet à l’appelant de choisir à la fois la source et un dépôt qu’il pourra lire et déchiffrer ensuite. [Les jokers d’arguments sudoers peuvent correspondre aux espaces et aux barres obliques](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) ; vérifiez donc les jokers finaux au lieu de supposer qu’un préfixe de dépôt fixe confine la source. [Restic peut sauvegarder vers des dépôts locaux et distants](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mais un dépôt local peut contenir de nouveaux objets auxquels seul root a accès ; vérifiez la politique sudo effective, l’accès au backend, le mot de passe du dépôt et les permissions des objets résultants avant de conclure à une divulgation. Une clé SSH sauvegardée ne permet l’accès que si le compte de destination l’accepte. Ne lancez pas de sauvegarde pour tester cela pendant l’examen passif.
- Une commande de maintenance ou de sauvegarde personnalisée sans restriction peut accepter un chemin de sortie ou proposer son propre planificateur de tâches. Pour une écriture de fichier, vérifiez la règle sudo exacte et l’utilisateur d’exécution, puis si l’appelant contrôle à la fois les données et la destination. Pour une exécution planifiée, vérifiez l’identité d’exécution du planificateur, l’entrée de commande et tout contrôle supplémentaire par mot de passe ou autorisation. Le nom de la commande ou `NOPASSWD` ne prouve aucune de ces voies à lui seul. Consultez [l’écriture dans des fichiers détenus par root](../interesting-files-permissions/write-to-root.md) et [les timers cron et systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Une commande sudo fixe peut tout de même charger un fichier de configuration prévisible depuis un répertoire partagé modifiable. Vérifiez si l’appelant peut remplacer ce fichier et si ses champs source et destination contrôlent une récupération ou une copie privilégiée. Une URL de fichier local peut exposer des données lisibles uniquement par le compte RunAs de sudo ; une source contrôlée par l’appelant associée à une destination protégée peut créer une voie d’écriture. Vérifiez le traitement des URL par le programme installé, les contrôles du chemin de destination, la règle sudo effective et l’accessibilité de la sortie. Un chemin de configuration modifiable dans `/tmp` n’est qu’une piste ; inspectez le binaire et les métadonnées du fichier sans lancer le transfert privilégié.
- Une règle sudo autorisant `git apply` peut permettre au compte RunAs d’écrire dans des fichiers choisis par l’appelant au moyen d’un patch. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permettait à un patch malveillant de créer un lien symbolique puis d’écrire hors de l’arbre de travail, même si la commande n’acceptait pas `--unsafe-paths`. Vérifiez la règle d’arguments sudo effective, la provenance du patch, l’accès au répertoire de travail du compte RunAs et la version corrigée de Git ou le backport du fournisseur. Une règle sans restriction autorisant `--unsafe-paths` présente un risque distinct lié à cette option explicite ; ni la version de Git ni l’autorisation de `git apply` ne prouvent à elles seules qu’un fichier protégé peut être modifié. N’appliquez pas de patch non fiable pendant l’énumération passive.
- Une règle sudo permettant à `clamscan --debug` de fonctionner en tant que root peut franchir une frontière de lecture si un utilisateur moins privilégié peut fournir une image DMG et que l’analyseur installé est affecté par [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), qui pouvait divulguer le contenu de fichiers dans la sortie de débogage. Vérifiez les arguments autorisés exacts et le chemin d’analyse, le contrôle de l’entrée, le compte RunAs effectif, le correctif/backport du moteur et la visibilité de la sortie pour l’appelant. Si une règle plus large autorise `--file-list`/`-f`, examinez séparément le comportement de cette liste ; une politique fixée à `--debug <scan-path>` ne l’autorise pas. Examinez la politique et les métadonnées du paquet sans analyser un fichier spécialement conçu ni afficher de sortie protégée pendant l’énumération.
- Une règle sudo permettant à root d’ouvrir une image de disque chiffrée choisie par l’appelant, associée à une seconde règle permettant de monter le mapper obtenu, peut importer des fichiers contrôlés par l’appelant dans l’espace de noms de montage de l’hôte. Vérifiez les deux règles effectives et leurs arguments, le contrôle de l’image et du nom du mapper, la cible de montage réelle ainsi que le propriétaire et le mode des fichiers obtenus. Une transition set-user-ID exige en outre un exécutable accessible, des options de montage qui le prennent en charge (`nosuid` la bloque) et une politique de processus ou MAC applicable ; ouvrir ou monter une image n’est qu’une piste. Une voie distincte via une sauvegarde existante nécessite sa vraie clé et un secret lisible utile à l’intérieur. Examinez la politique et les chemins sans ouvrir ni monter d’image pendant l’énumération passive. Consultez le [manuel de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) et les [options de montage](https://man7.org/linux/man-pages/man8/mount.8.html).
- Une règle sudo permettant à un script shell ou Python de fonctionner en tant que root mérite un examen du répertoire de travail si le script invoque `./helper` sans d’abord se placer dans un répertoire fixe. Une liste Python comme `['./helper']` transmise à `subprocess.run` peut présenter le même comportement lié au répertoire de travail choisi par l’appelant. Celui-ci peut choisir un répertoire modifiable et y placer un exécutable portant ce nom relatif ; un chemin absolu ailleurs dans le script ne protège pas cet appel. Avant de considérer qu’il s’agit d’une exécution de code, vérifiez la règle effective, `runchdir` ou toute autre politique de changement de répertoire, le déroulement du script et l’accessibilité de la branche, le répertoire modifiable et exécutable, ainsi que les restrictions de montage/`NOEXEC`. Si le script est illisible, son comportement reste inconnu jusqu’à l’examen du code source par une voie autorisée. Examinez les scripts statiquement au lieu d’exécuter le helper. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documente la politique du répertoire de travail.
- Un validateur Python fixe exécuté avec les privilèges root peut tout de même évaluer un fichier de données choisi par l’appelant. [La documentation de `eval()` de Python déconseille son utilisation sur des entrées non fiables](https://docs.python.org/3/library/functions.html#eval) : une vérification du suffixe de l’entrée, un préfixe arithmétique ou une branche de validation ne constitue pas une sandbox si l’expression restante atteint `eval`. Avant de considérer cela comme une voie d’exécution, vérifiez la règle sudo effective, si l’appelant peut choisir et contrôler le fichier exact, les conditions de branchement de l’analyseur et la construction de l’expression, ainsi que l’identité du processus privilégié. La présence de `eval` dans un script lisible est seulement un indice à examiner ; inspectez le code source et les permissions du fichier sans lancer le validateur ni lui soumettre une expression de test pendant l’énumération.
- Un wrapper Ruby exécuté en tant que root via sudo qui lit un nom de fichier YAML relatif, tel que `YAML.load(File.read("dependencies.yml"))`, peut utiliser le répertoire de travail de l’appelant comme source, sauf si le wrapper ou la politique sudo fixe ce répertoire. Vérifiez les arguments autorisés exacts, les permissions du répertoire et du fichier, ainsi que le comportement de la version de Psych installée : les anciennes implémentations de `YAML.load` pouvaient désérialiser des objets Ruby arbitraires, tandis que les versions plus récentes restreignent les classes par défaut. Un appel statique n’est qu’une piste ; vérifiez que le fichier provient effectivement d’un répertoire modifiable par l’appelant et que le chargeur installé accepte les classes dangereuses. Pour les entrées non fiables, préférez `safe_load` avec une liste d’autorisation explicite et minimale de classes. Consultez la [documentation Psych de Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) et la [documentation Psych de Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Une autorisation sudo exacte pour `sudo go run /absolute/file.go` en tant que root mérite un examen du répertoire de travail lorsque le code Go lit un fichier WASM relatif et peut exécuter un script shell relatif après avoir analysé son résultat. Vérifiez l’utilisateur RunAs effectif, les arguments et interdictions de commande, l’existence d’un répertoire courant modifiable par l’appelant, le flux de données entre WASM et la branche, ainsi que l’invocation éventuelle du helper par cette branche. Un `runchdir` sudo fixe, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) peut modifier l’emplacement de recherche. Une simple cooccurrence dans le code est une piste ; inspectez le code source sans lancer Go, WASM ni le helper.
- `sudoedit` et les jokers d’arguments nécessitent de vérifier précisément la version et la règle ; la [checklist](linux-privilege-escalation-checklist.md) couvre le problème de modification de fichier avec sudoedit. Pour une autorisation `sudoedit` entre utilisateurs sur un chemin avec joker, examinez le paramètre effectif `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, la cible résolue et les personnes pouvant remplacer chaque entrée parent. Le premier peut permettre de suivre un lien symbolique, tandis que la désactivation du second supprime les vérifications des répertoires modifiables ; aucun de ces paramètres ne prouve à lui seul qu’un fichier appartenant à un autre utilisateur peut être modifié. Avant de conclure, vérifiez la politique sudo installée et les arguments exacts correspondant à la règle. Consultez les [définitions des options sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Dans une règle de commande sudoers, un joker d’argument peut correspondre aux espaces aussi bien qu’aux caractères de chemin. Une règle pour une commande capable de lire des fichiers, avec un argument comme `/restricted/*`, peut donc autoriser un argument de fichier supplémentaire après un préfixe correspondant. Vérifiez l’utilisateur RunAs exact, le chemin de commande, le modèle d’arguments et les interdictions ultérieures ; la lecture démontrée d’un fichier n’implique pas l’exécution de commandes. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue les jokers d’arguments des jokers de chemin de commande.
- Un joker d’argument qui ressemble à un chemin peut aussi correspondre à `../`. Par exemple, une règle root pour `node /opt/scripts/*.js` peut autoriser un fichier JavaScript contrôlé par l’appelant en dehors de `/opt/scripts` si le chemin fourni commence toujours par `/opt/scripts/` et est résolu par des segments de répertoire parent. Il s’agit d’un joker d’**argument** ; le joker du chemin de commande de l’exécutable Node applique des règles différentes pour les barres obliques. Avant de conclure à une exécution de code, vérifiez la règle effective, les interdictions ultérieures, la résolution du chemin, le contrôle du fichier cible et les éventuelles restrictions sudoers par expression régulière ou empreinte. Consultez les [règles des jokers sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) et la [documentation de la ligne de commande de Node](https://nodejs.org/api/cli.html).
- Les archiveurs et autres utilitaires peuvent disposer de hooks d’exécution. Testez les arguments autorisés exacts par rapport à [GTFOBins](https://gtfobins.github.io/) au lieu de supposer que seuls les shells ou les interpréteurs exécutent des commandes.
- Une règle root sans restriction pour `qpdf` peut exposer un fichier privilégié via des pièces jointes PDF : qpdf 10.2 et versions ultérieures prennent en charge `--empty` et `--add-attachment file ... --` avec un PDF de sortie. Si le processus privilégié peut lire la source sélectionnée et écrire le PDF dans un chemin accessible à l’appelant, la sortie peut contenir les octets de la source. Avant de conclure à une divulgation de fichier, examinez les arguments sudo effectifs et leurs exclusions, la version de qpdf, l’accès à la source et le chemin de sortie. La lecture d’une clé SSH root n’est utile pour se connecter que si cette clé est valide et que l’authentification SSH de root est autorisée. Consultez les [options de pièces jointes de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La réutilisation des horodatages sudo dépend de la politique de cache, de l’utilisateur propriétaire, du terminal/de la session et des permissions. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) présente les vérifications à effectuer.
- `doas` possède ses propres règles et sa propre configuration. Vérifiez les commandes autorisées et les chemins de configuration modifiables comme décrit dans la [section doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Outils de build et de paquet exécutés via sudo

Une autorisation sudo sans restriction pour Foundry `forge` peut être importante même lorsque l’identité RunAs correspond à un autre utilisateur non-root. Des options du compilateur comme `--use` peuvent choisir un exécutable local, et `forge flatten -o` choisit un fichier de sortie. Avant de considérer l’autorisation exploitable, vérifiez la version de Forge installée, les arguments sudo exacts, l’accessibilité du projet et du compilateur, les permissions de sortie et l’environnement effectif. Un exécutable helper relatif trouvé via `PATH` est une voie dépendante de la version et de l’environnement, et non une propriété à supposer pour toutes les versions de Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Une autorisation root sans restriction pour `pacman` permet davantage que de simples requêtes de paquet : `-U` accepte un paquet local, les paquets peuvent contenir des scripts d’installation et `--hookdir` sélectionne un autre répertoire de hooks. Examinez la règle sudo effective, les restrictions d’arguments et les exclusions avant tout test ; l’énumération passive ne nécessite ni installation de paquet ni exécution de hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fixe exécuté via sudo peut également installer une dépendance npm nommée, puis démarrer une application Node. Examinez sa règle RunAs exacte, si le paquet est déjà installé, les valeurs effectives de `HOME` et du `userconfig` npm, la configuration du projet ou les substitutions en ligne de commande, ainsi que le contrôle éventuel par un utilisateur moins privilégié du registre ou du paquet renvoyé pour ce nom. [npm documente la recherche de `.npmrc` par utilisateur et par projet](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/) ; le comportement de `HOME` par sudo dépend de la politique et de la distribution installées, de sorte qu’un fichier `.npmrc` modifiable par l’utilisateur peut ou non être lu par le processus npm privilégié. Si l’application privilégiée importe le paquet nouvellement installé, le code du module peut s’exécuter sous l’identité de cette application. Les scripts exécutés lors de l’installation constituent une voie distincte, dépendante de la version et de la configuration ; [npm documente leur cycle de vie et la gestion de l’utilisateur](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un chemin `.npmrc` ou une ligne `npm install` ne sont que des pistes. Examinez la règle, le wrapper court, les chemins de configuration et la provenance du paquet sans installer ni démarrer l’application pendant l’énumération passive.

Une autorisation root pour `pip` ou `pip3 download` constitue également un indice à examiner du côté du build de paquets lorsque ses arguments permettent à l’appelant de choisir une distribution source non fiable, même si le modèle d’URL la limite à un service local et à un suffixe `.tar.gz`. `pip download` accepte les URL d’archives et résout les métadonnées de paquet ; la préparation d’une sdist peut invoquer son backend de build ou du code `setup.py` historique avant que l’archive ne soit simplement enregistrée. Vérifiez l’utilisateur RunAs sudo et la règle d’arguments exacts, si l’appelant peut publier ou remplacer l’archive choisie et si cette version de pip prépare effectivement ses métadonnées. Une archive ou une wheel de confiance fixe ne démontre pas cette voie. Ne récupérez ni ne construisez de paquet non fiable pendant l’énumération passive. Consultez la [commande download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), l’[interface du système de build](https://pip.pypa.io/en/stable/reference/build-system/) et les [conseils d’installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Une règle sudo autorisant `pip install` avec un chemin de projet local choisi par l’appelant crée une frontière de build plus directe. [pip accepte les répertoires de projets locaux](https://pip.pypa.io/en/stable/topics/local-project-installs/) et invoque leur système de build ; le [backend de build exécute des hooks contrôlés par le projet](https://pip.pypa.io/en/stable/reference/build-system/). Avant de considérer la règle comme une exécution de code privilégiée, vérifiez l’identité RunAs effective, les restrictions et interdictions d’arguments exactes, le contrôle du projet choisi et le comportement de pip/backend installé. Un projet fixe et fiable ou une règle excluant les chemins choisis par l’appelant ne démontre pas cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération passive.

Une autorisation root sans restriction pour `easy_install` constitue un indice connexe lié au build des paquets historiques. [Setuptools indique](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install accepte un répertoire de projet local et construit des distributions source ; un projet contrôlé par l’appelant peut exécuter son `setup.py` durant ce build sous l’identité sudo. Vérifiez le compte RunAs effectif, les restrictions de commande et d’arguments exactes (y compris les interdictions ultérieures), le contrôle du projet choisi et le comportement de l’outil installé. Un projet fixe et fiable ou une politique qui n’autorise pas une source choisie par l’appelant ne démontre pas cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération.

Un wrapper Python autorisé par sudo qui utilise `setuptools.package_index.PackageIndex.download` avec une URL choisie par l’appelant représente un cas d’examen différent de `pip download` : [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) décrit des versions antérieures à 78.1.1 affectées où un nom de fichier dérivé de l’URL pouvait sortir du répertoire de téléchargement prévu et être écrit avec les permissions du processus. Vérifiez l’utilisateur RunAs et la règle d’arguments sudo effectifs, si le wrapper transmet l’URL de l’appelant à cette API précise, le build installé ou le backport du fournisseur et l’emplacement de résolution du chemin résultant. Une chaîne de version ou un répertoire de téléchargement modifiable ne démontre pas à lui seul une écriture arbitraire. Examinez le wrapper court et les métadonnées du paquet sans récupérer l’URL ni écrire de fichier pendant l’énumération.

Un wrapper de build autorisé par sudo qui transmet un fichier `.spec` choisi par l’appelant à PyInstaller nécessite le même examen de la frontière de confiance. Un fichier spec PyInstaller est du Python exécutable évalué pendant le **build**, et ses entrées `datas` peuvent intégrer dans un artefact des fichiers lisibles par l’identité qui effectue le build. Vérifiez l’utilisateur RunAs exact, les règles sudo sur les arguments et les interdictions, le chemin et le traitement des branches du wrapper, le contrôle du fichier spec choisi et l’accès à l’artefact résultant. Autoriser une entrée `.py` ou trouver PyInstaller installé ne démontre ni le contrôle du fichier spec ni l’exécution privilégiée. L’examen passif doit se limiter à un fichier wrapper circonscrit et à ses métadonnées ; il ne doit pas lancer de build. Consultez la [documentation des fichiers spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Chargeurs de presets et de plugins exécutés via sudo

Les outils Python qui acceptent un répertoire de preset ou de plugins choisi par l’appelant peuvent importer du code avec les privilèges accordés par sudo. Par exemple, BBOT accepte un preset avec `-p`, et sa [documentation des modules personnalisés](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) décrit les entrées `module_dirs` qui sélectionnent des répertoires supplémentaires de modules Python. Si la règle sudo effective autorise un preset choisi par l’appelant et que celui-ci contrôle un module dans le répertoire sélectionné, l’import peut exécuter du code en tant qu’utilisateur privilégié, éventuellement avant que l’outil ne rejette un module invalide. Vérifiez la version installée, la politique exacte de sudo concernant RunAs et les arguments, ainsi que le propriétaire des chemins du preset et du module sans charger le module pendant l’énumération.

### Outil en ligne de commande Backdrop exécuté via sudo

[Bee](https://github.com/backdrop-contrib/bee) est un outil PHP en ligne de commande pour Backdrop CMS. Ses commandes `eval` (`php-eval`) et `php-script` peuvent exécuter du PHP fourni par l’appelant. Une règle sudo autorisant l’exécutable Bee en tant que root avec des arguments sans restriction peut donc permettre l’exécution de code en tant que root si Bee peut initialiser une installation Backdrop. Exécutez-le depuis le répertoire du site ou sélectionnez un site avec l’option globale `--root=<directory>` ; trouver Bee ou un fichier `settings.php` de Backdrop ne prouve ni l’autorisation sudo, ni l’existence d’un site utilisable, ni la réussite de l’initialisation. Avant tout test, examinez la règle sudo effective, les éventuelles exclusions de commande, l’identité de l’exécutable et l’accès au site. Lors de l’énumération passive, inspectez la règle et les chemins de fichiers sans invoquer Bee. Consultez le [journal des modifications des commandes Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) pour l’ajout des commandes PHP.

### Serveurs de terminaux exécutés via sudo

`mosh-server` démarre un serveur de terminal interactif sous l’identité de l’utilisateur qui l’invoque. Il choisit un port UDP élevé et une clé de session, les communique à l’appelant et lance normalement le shell de connexion de cet utilisateur lorsqu’un client se connecte. Une autorisation sudo sans restriction permettant à `mosh-server` de fonctionner en tant que root est donc une piste à examiner du côté du shell, même si la commande serveur se détache. Vérifiez l’identité RunAs effective, les arguments autorisés et les exclusions, le binaire installé, le shell, la disponibilité du client et l’accès UDP. L’énumération passive doit examiner la règle sudo sans démarrer de serveur ni afficher de clé de session active. Consultez le [manuel du serveur Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) et les [notes de conception en amont](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de sauvegarde privilégiés qui réécrivent un fichier de tâches fourni par l’appelant

Un wrapper shell exécuté en tant que root peut accepter un fichier de tâches choisi par l’appelant, supprimer `../` des chemins sources, vérifier que chaque résultat commence par un répertoire autorisé, réécrire le fichier de tâches puis transmettre son *chemin* à un programme de sauvegarde. Examinez le chemin transformé après résolution canonique complète : une seule passe de remplacement de chaîne peut faire apparaître une nouvelle séquence de traversée que la vérification lexicale du préfixe accepte. Vérifiez également si le programme de sauvegarde lit les données transformées en mémoire ou rouvre le fichier. S’il le rouvre, une réécriture échouée peut laisser l’entrée d’origine en place.

Sous Linux, `fs.protected_regular` peut refuser une écriture `O_CREAT` dans le fichier ordinaire d’un autre utilisateur situé dans un répertoire sticky accessible en écriture à tous. Ce refus est une protection, mais un wrapper shell qui ignore l’erreur d’écriture peut quand même continuer avec le fichier de tâches d’origine. Vérifiez ce paramètre, le propriétaire du fichier et du répertoire, ainsi que l’arrêt éventuel du wrapper en cas d’échec. Le chemin n’est candidat à une divulgation de fichiers que si la règle sudo effective autorise le wrapper en tant qu’utilisateur privilégié, si l’appelant contrôle l’entrée de la tâche et une destination de sauvegarde lisible et si l’utilitaire de sauvegarde inclut effectivement les sources protégées. Vérifiez ces conditions sans lancer la sauvegarde pendant l’énumération.

### Jokers d’arguments sur les outils de paquets privilégiés

Dans une règle sudo pour `tcpdump`, un `*` dans le **modèle d’arguments** peut correspondre aux espaces et aux barres obliques ; une restriction qui ressemble à un chemin peut donc toujours autoriser du texte d’option supplémentaire. Cela diffère d’un joker dans le chemin de l’exécutable de la commande ; examinez la règle RunAs complète et les éventuelles interdictions ultérieures. Si des options peuvent être injectées, l’invocation autorisée et la sémantique des options de [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) installé déterminent si `-F`, `-V`, `-r`, `-w` ou `-Z` fournit une primitive utile de lecture/écriture. `-V` lit une liste de noms de fichiers de capture, pas un fichier arbitraire à afficher de façon générique. AppArmor ou une autre politique MAC peut bloquer l’accès aux fichiers même si sudo autorise la commande ; la présence d’un fichier de profil sur disque ne prouve pas qu’il est chargé ou appliqué. Examinez l’autorisation et la politique passivement avant de conclure. Le [manuel sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) décrit la distinction entre jokers.

Une règle sudo autorisant root qui ne mentionne que l’exécutable `tcpdump`, sans restriction d’arguments, mérite aussi un examen. Le [manuel de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) indique que `-z` exécute une commande après la rotation lorsque `-C` ou `-G` fait tourner une capture enregistrée ; `-Z` ou une valeur par défaut à la compilation peut supprimer les privilèges avant cette commande. Avant de traiter cette règle comme une voie d’escalade, vérifiez la règle sudo effective, le build installé, le comportement de suppression des privilèges et la possibilité qu’une rotation ait lieu. Une règle mise en évidence est une piste, pas une preuve d’exécution de commande en tant que root.

### Wrappers Nmap exécutés via sudo

Lorsque le chemin `nmap` autorisé par sudo correspond à un wrapper shell, inspectez le chemin exact autorisé et chaque option qu’il transmet. Bloquer l’orthographe courante `--script` ne bloque pas nécessairement le chargement de code NSE : [`--datadir`](https://nmap.org/book/man-misc-options.html) de Nmap sélectionne des fichiers de données, et NSE [charge `nse_main.lua`](https://nmap.org/book/nse-implementation.html) depuis le répertoire de données sélectionné lorsque les scripts sont activés. Certains builds installés acceptent aussi d’autres variantes d’options longues ; comparez donc les restrictions à l’analyseur réel de ce binaire. [`--excludefile`](https://nmap.org/book/target-specification.html) constitue une surface distincte de lecture de fichiers ; les erreurs d’analyseur peuvent divulguer du texte. Vérifiez la règle sudo effective, la logique du wrapper, la version de Nmap, le contrôle du répertoire et la politique MAC sans lancer de scan pendant l’énumération.

### Hooks Mercurial pull exécutés via sudo

Une source fixe dans `sudo hg pull /fixed/source` laisse tout de même le dépôt **de réception** déterminé par le répertoire de travail courant, sauf si la commande le fixe avec `-R`. Un dépôt de réception contrôlé par l’appelant peut définir des hooks dans `.hg/hgrc`, qui peuvent s’exécuter en tant qu’utilisateur RunAs de sudo. [Mercurial ignore la configuration d’un dépôt appartenant à un utilisateur ou groupe non fiable](https://mercurial-scm.org/help/topics/config) ; avant de considérer cela comme une exécution de code, vérifiez donc les utilisateurs/groupes de confiance du compte RunAs et le répertoire de travail exact. La lecture de la politique et de la configuration suffit à un examen passif ; n’effectuez pas de pull et n’invoquez pas de hook pour les répertorier.

### Hooks Git pull exécutés via sudo

Pour une autorisation sudo exacte permettant à `git pull` de fonctionner en tant que root, vérifiez également le dépôt **de réception** sélectionné par le répertoire de travail. Un dépôt appartenant à l’appelant peut contenir un hook `post-merge` exécutable, lancé sous l’identité du processus Git lorsqu’un pull effectue réellement une fusion réussie ; [Git documente ce hook](https://git-scm.com/docs/githooks) et [le comportement de pull en matière de fusion ou de rebase](https://git-scm.com/docs/git-pull). Vérifiez la règle sudo effective et le CWD, le chemin et les permissions du hook actif, ainsi que la possibilité d’effectuer une fusion avec de nouveaux commits. Un pull échoué, sans effet ou limité au rebase ne démontre pas cette voie par hook. Examinez la politique et les métadonnées du dépôt sans lancer le pull privilégié.

### Copies rsync d’archives exécutées via sudo

Pour `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` dans le **modèle d’arguments sudoers** peut correspondre aux espaces et autoriser une option supplémentaire entre la source et la destination. Cela ne correspond pas à l’expansion shell des noms de fichiers. Si l’appelant peut remplir la source et si le processus rsync privilégié peut écrire dans la destination, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) peut demander une propriété privilégiée tandis que le mode archive préserve les bits de permission, ce qui peut créer un fichier SetUID détenu par root. Vérifiez la sémantique exacte des [jokers sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la version de rsync, les interdictions ultérieures, `nosuid` sur le système de fichiers et la politique MAC. Une règle correspondante est une piste, pas une preuve d’escalade de privilèges réussie.

### Export de règles de filtrage de paquets exécuté via sudo

Une autorisation root sans restriction pour `iptables` et `iptables-save` (ou la paire correspondante `ip6tables`) mérite un examen de l’écriture de fichiers. La correspondance `comment` accepte un texte de règle choisi par l’appelant, tandis que `iptables-save -f` écrit les règles sérialisées dans un chemin choisi.<sup>[[20]](#references)[[21]](#references)</sup> La possibilité d’obtenir un contenu utile dépend de la sérialisation des commentaires par le backend installé et de l’acceptation éventuelle d’autres lignes par le fichier de destination ; `iptables-save` seul ne fournit pas un contenu arbitraire choisi. Vérifiez l’identité RunAs sudo exacte, les arguments et exclusions, l’extension de correspondance disponible, le backend et les permissions de destination. Pendant l’énumération, examinez l’autorisation sans modifier les règles du pare-feu ni écrire de fichier.

### Répertoire de journalisation Below privilégié

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) affectait les versions de Below antérieures à 0.9.0, qui créaient un répertoire `/var/log/below` accessible en écriture à tous. Si un service ou une commande sudo autorisée exécute un build affecté en tant que root, un utilisateur capable d’écrire dans un répertoire de journaux non-sticky et d’y accéder peut éventuellement remplacer une entrée de journal par un lien symbolique avant que le processus privilégié ne l’ouvre. Examinez l’état des correctifs du paquet installé, le chemin d’exécution privilégié exact, l’accès effectif au répertoire, le bit sticky et les ACL, ainsi que les métadonnées de `/var/log/below/error_root.log`. Un chemin accessible en écriture à tous ou une règle sudo ne démontre pas à lui seul toute la chaîne. Un répertoire sticky ou un backport du fournisseur modifie l’évaluation. L’énumération passive doit examiner uniquement les métadonnées ; elle n’a pas besoin de créer un lien ni de lancer le programme privilégié.

### Collecte de lots de diagnostic privilégiés à partir d’entrées modifiables

Un script de profil de support autorisé par `sudo` peut lire en tant que root des chemins de journaux fixes et copier leur contenu dans une archive de profil. Examinez le script réel pour repérer les lectures de fichiers, puis vérifiez si l’appelant peut remplacer un chemin source ou une entrée de répertoire parent par un lien symbolique. Si la lecture privilégiée suit ce lien et que l’archive résultante est lisible par l’appelant, un fichier protégé peut être divulgué. L’autorisation sudo, le chemin source modifiable, la lecture privilégiée et la sortie lisible doivent tous être présents ; un journal ou un nom de profil modifiable ne suffit pas à lui seul. Examinez les permissions effectives et les métadonnées des liens sans remplacer de fichiers ni générer de profil pendant l’énumération. Les [consignes de support de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentent son script de profil exécuté en tant que root et l’archive produite, ce qui illustre pourquoi les entrées et sorties de tels lots doivent être protégées.

### Scripts de restauration d’archives Python exécutés en tant que root

Une règle sudo strictement limitée à un script Python de restauration nécessite tout de même d’examiner son entrée d’archive. Si l’appelant peut choisir ou remplacer l’archive et que le script l’extrait en tant que root avec `tarfile.extractall(filter="data")`, vérifiez les mises à jour de sécurité de l’interpréteur avant de faire confiance au filtre. CPython a corrigé plusieurs contournements du filtre par liens symboliques et liens physiques, dont CVE-2025-4517, dans les versions 3.9.23, 3.10.18, 3.11.13, 3.12.11 et 3.13.4. Les distributions peuvent appliquer des backports, de sorte que la version affichée de l’interpréteur ne prouve pas à elle seule une exposition.<sup>[[16]](#references)[[17]](#references)</sup>

Pour un examen passif, lisez la commande sudo et le script exacts, déterminez quel argument choisit l’archive et vérifiez si l’utilisateur actuel peut modifier l’archive ou son répertoire parent. Vérifiez séparément le correctif du fournisseur installé et la destination d’extraction ; `filter="data"` ne rend pas toute archive non fiable sûre.<sup>[[16]](#references)[[17]](#references)</sup>

### Chargeurs de modèles de machine learning exécutés via sudo

Une règle sudo autorisant le choix par l’appelant d’un fichier `.pt`, `.pth` ou `.ckpt` mérite un examen lorsqu’un script privilégié transmet ce fichier à [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou à un autre chargeur fondé sur pickle. Vérifiez la règle RunAs effective, si l’appelant peut créer ou remplacer le modèle choisi et le flux réel des arguments, via tout wrapper shell, jusqu’au helper Python. L’extension `.pth` désigne aussi des fichiers de configuration Python site sans rapport ; l’extension seule ne prouve donc pas qu’il s’agit d’un chargement de modèle. L’analyse d’une archive ou l’analyse statique d’un pickle ne démontre pas que le chargement ultérieur est sûr ; examinez le comportement de [`weights_only` dépendant de la version](https://docs.pytorch.org/docs/stable/notes/serialization.html) du chargeur et toute liste d’autorisation. Consultez les notes sur [les pickles ML et Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). L’énumération passive ne doit jamais charger ni décompresser le modèle.

### Analyse d’expressions sur des entrées stockées via sudo

Un script Python fixe exécuté en tant que root via sudo peut tout de même évaluer du texte qu’un utilisateur moins privilégié peut stocker dans une base de données applicative. Dans TensorFlow, un appel à `preprocess_input_exprs_arg_string(value, safe=False)` sélectionne une voie `eval` ; l’[avis de sécurité TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) décrit l’analyseur non sûr et la correction apportée à son appelant en ligne de commande. Un appel explicite `safe=False` dans une application doit faire l’objet d’un examen séparé, même si cet appelant en ligne de commande est corrigé. Vérifiez la règle sudo effective, qui peut modifier l’enregistrement concerné, si le filtrage ou la notation permet à cet enregistrement d’atteindre l’appel et le comportement de la fonction installée. Une version de TensorFlow, une autorisation sudo ou un fichier de modèle codé en dur ne prouvent pas la chaîne à eux seuls. Examinez passivement le script et le flux des données ; ne lancez pas le helper privilégié et ne soumettez pas d’expressions de test pendant l’énumération.

### Configuration de needrestart autorisée par sudo

`needrestart -c` charge un fichier de configuration Perl choisi par l’appelant et en évalue le contenu. Si `sudo -l` autorise `needrestart` en tant que root avec des arguments permettant `-c`, et que l’appelant peut choisir un fichier de configuration lisible dans un emplacement modifiable, cette permission peut mener à l’exécution de code en tant que root. Vérifiez la règle sudo exacte relative à RunAs et aux arguments ; une règle autorisant uniquement une liste fixe d’arguments peut bloquer cette voie. Ce cas est distinct des vulnérabilités de needrestart liées à l’analyse d’interpréteurs : mettre le paquet à jour ou désactiver `interpscan` ne rend pas sûre une autorisation root sans restriction pour `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python via sudo sous un autre compte

Un point d’entrée Python fixe peut tout de même importer un module que l’appelant peut modifier ou remplacer, y compris lorsque sudo exécute le script en tant qu’utilisateur de service **non-root**. Pour un `from utils import status` littéral, examinez `utils/__init__.py` et `utils/status.py` locaux ainsi que les permissions du répertoire du paquet. Avant de considérer le fichier modifiable comme une voie d’exécution, vérifiez le chemin d’import du script, les arguments sudo exacts autorisés et si l’action concernée atteint cet import. Examinez les fichiers et permissions sans importer ni lancer le script pendant l’énumération.<sup>[[2]](#references)[[3]](#references)</sup>

Une règle sudo exacte pour `python3 /absolute/script.py` nécessite uniquement que le script soit lisible ; le fichier n’a pas besoin d’être exécutable ni d’avoir un shebang. Examinez également les modules locaux **manquants** : si le script importe un module dont le fichier peut être créé dans un répertoire de script modifiable par l’appelant, Python peut charger ce fichier sous l’identité RunAs. Vérifiez la règle sudo effective, le [chemin de recherche des modules](https://docs.python.org/3/library/sys_path_init.html) réel de l’interpréteur, si le module est intégré ou figé et si l’import est atteint. Une règle sudo directe pour le script impose des conditions différentes concernant le bit d’exécution et le shebang. Un wrapper distinct qui ajoute des jetons fournis par l’appelant après `sudo -u account` nécessite aussi un examen du flux d’arguments : un autre `-u` dans ces jetons n’a d’importance que si la politique sudo invoquée autorise l’identité résultante. Des chaînes statiques ne prouvent aucune de ces voies.

### Apache exécuté via sudo avec une configuration contrôlée par l’appelant

Si une règle sudo autorise l’exécution privilégiée de `apachectl`, `apache2ctl` ou `httpd` avec un fichier de configuration `-f` contrôlé par l’appelant, examinez les permissions du fichier et de son répertoire parent. La directive [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) d’Apache prend un nom de module suivi du **nom du fichier du module** ; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) charge également un fichier. [`Include` et `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) peuvent étendre la configuration ou exposer le contenu de fichiers via des erreurs. Un wrapper personnalisé peut valider ces chemins, supprimer les privilèges ou restreindre les arguments ; une configuration modifiable est donc une piste, pas une preuve d’exécution de code. Vérifiez la canonicalisation des chemins, les liens symboliques et l’analyse des directives avant de conclure.

### nginx exécuté via sudo avec une configuration contrôlée par l’appelant

Une règle `nginx` sans restriction permettant à root de l’exécuter peut autoriser [`-c` à sélectionner une autre configuration](https://nginx.org/en/docs/switches.html). Examinez les arguments et exclusions sudo exacts, si l’appelant peut fournir la configuration et si le processus master ou les workers résultants conservent l’accès aux chemins protégés. Un `root` choisi avec `autoindex` peut exposer des fichiers via un nouveau listener ; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) peut offrir une voie d’écriture privilégiée, mais le module DAV n’est pas compilé par défaut et il faut vérifier sa présence, l’accessibilité du listener, les permissions des fichiers et le comportement des fichiers temporaires. La directive [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) peut également cibler un fichier choisi ; écrire des journaux dans un fichier de configuration sensible comme `/etc/ld.so.preload` ne devient une voie d’escalade que si l’écriture privilégiée est effective et si l’enregistrement de journal est contrôlable. La mise en évidence de l’exécutable dans `sudo -l` est un indice à examiner, pas une preuve que l’une de ces voies fonctionne. L’énumération passive ne doit ni démarrer ni reconfigurer nginx.

### Comparaison de motifs dans les invites Bash privilégiées

Lorsqu’un script Bash autorisé par sudo lit une valeur fournie par l’appelant et la vérifie avec `[[ "$expected" == $entered ]]`, Bash interprète l’opérande droit non protégé par des guillemets comme un motif. Un joker peut donc satisfaire la comparaison sans connaître la valeur attendue. Mettre l’opérande entre guillemets (`[[ "$expected" == "$entered" ]]`) effectue une comparaison littérale. Examinez la règle sudo exacte, l’accessibilité de l’invite et les actions du script après la comparaison ; la syntaxe seule ne démontre pas une voie exploitable. Évitez d’afficher la valeur attendue pendant l’énumération. Consultez la [référence des constructions conditionnelles Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers exécutés via sudo qui téléchargent puis exécutent un fichier

Une autorisation sudo root sans restriction pour un helper personnalisé mérite un examen du flux des données s’il accepte une URL choisie par l’appelant, écrit la réponse sur disque puis invoque ce fichier avec un interpréteur ou un shell. [Sudoers autorise des arguments arbitraires si l’entrée de commande n’en spécifie aucun](https://man7.org/linux/man-pages/man5/sudoers.5.html) ; un chemin d’exécutable fixe ne limite pas ce que ses arguments peuvent choisir. Vérifiez dans le helper installé la validation réelle de l’URL, le chemin de sortie, la branche de succès et l’exécution ultérieure. Un import de libcurl ou une chaîne imprimable ne prouve pas à lui seul cette chaîne.

Même un nom de sortie fixe peut être remplacé entre l’écriture et l’exécution lorsque le helper utilise un **chemin relatif dans un répertoire de travail contrôlé par l’appelant**. Le renommage ou le remplacement d’un fichier détenu par root dépend des droits d’écriture et de recherche sur le répertoire et des restrictions du bit sticky, pas seulement du mode du fichier ; consultez [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Vérifiez si le helper rouvre ensuite le chemin ou utilise le descripteur déjà ouvert, et s’il se place dans un répertoire de confiance avant l’écriture. Examinez passivement la politique sudo, le helper et les métadonnées du répertoire ; n’invoquez pas le téléchargement privilégié et ne tentez pas de course pendant l’énumération.

Un helper root de téléchargement peut aussi exposer une injection d’**arguments** s’il construit une chaîne de commande Bash telle que `curl <entrée de l’appelant> -o <sortie fixe>`. Un filtre qui rejette les espaces laisse subsister l’[expansion des accolades Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) : des éléments non protégés séparés par des virgules peuvent devenir des arguments curl distincts. Si l’entrée arrive à curl avant l’option `-o` fixe, une option de sortie fournie par l’appelant peut choisir la destination de la première URL sous l’identité du helper ; [curl associe les options de sortie aux URL dans l’ordre](https://curl.se/docs/manpage.html#-o). Vérifiez le shell exact, la protection par guillemets, la validation de l’entrée, la règle sudo effective, l’ordre des arguments curl et les schémas d’URL pris en charge, ainsi que le contrôle éventuel par l’appelant des octets récupérés ou sa capacité à lire le résultat. Un exécutable empaqueté avec PyInstaller peut contenir la logique de l’application Python, mais un marqueur d’empaquetage ou une chaîne `curl` ne prouve pas à lui seul ce flux de données. Examinez une copie hors ligne circonscrite si cela est autorisé ; l’énumération courante ne doit ni lancer le helper ni récupérer des données choisies par un attaquant.

Un script shell root qui appelle [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) ne fait que choisir un nom inutilisé ; il ne crée **pas** le fichier. Si le script crée ensuite ce nom dans un répertoire qu’un autre utilisateur peut modifier, le rouvre puis ajoute son contenu à une destination protégée comme le fichier `authorized_keys` de root, examinez la possibilité d’une course sur le fichier temporaire. Vérifiez la règle sudo exacte, le propriétaire du répertoire et du fichier, la séquence de création et de réouverture, les protections du noyau et si l’écriture privilégiée utilise réellement des octets contrôlés par l’attaquant. Une chaîne `mktemp -u` ou un `/tmp` modifiable ne prouve pas à lui seul l’existence de la course. Examinez le script et les métadonnées du chemin sans le lancer et sans provoquer de course sur son fichier temporaire pendant l’énumération.

## Notes défensives

- Évitez d’autoriser des interpréteurs ou des éditeurs interactifs via sudo.<sup>[[1]](#references)</sup>
- N’autorisez pas des outils génériques d’écriture de fichiers comme `tee` avec des opérandes sans restriction. Utilisez un wrapper détenu par root qui sélectionne une destination fixe et rejette les chemins contrôlés par l’appelant.<sup>[[2]](#references)</sup>
- Privilégiez des wrappers fixes détenus par root qui exécutent une seule action administrative limitée.<sup>[[1]](#references)[[2]](#references)</sup>
- Si un interpréteur est inévitable, limitez l’autorisation au chemin de script exact et empêchez les arguments contrôlés par l’utilisateur, les imports modifiables, `PYTHONPATH` et la conservation dangereuse de variables d’environnement.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si la modification de fichiers est nécessaire, limitez l’autorisation au chemin exact et envisagez `sudoedit` avec des versions corrigées de sudo et une gestion stricte de l’environnement.<sup>[[1]](#references)[[2]](#references)</sup>
- Examinez `SETENV`, `env_keep`, les répertoires de travail modifiables, les chemins d’import/modules modifiables, `NOEXEC`, `use_pty` et la journalisation, sans les considérer comme une sandbox complète.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
