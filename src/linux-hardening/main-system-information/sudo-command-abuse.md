## Sudoで許可されたインタプリタ

`sudo -l` でユーザーが root としてインタプリタを実行できる場合、直接的なコード実行が可能だと考えてください。インタプリタは任意のコードを実行するように設計されているため、`python3`、`perl`、`ruby`、`lua`、`node` などのバイナリを許可するルールは、引数が厳密に制限・検証されていない限り、通常は root としてコマンドを実行できるのと同等です。<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

一般的な確認手順は、まずユーザーの権限を一覧表示し、次にインタプリタの `-c` オプションで Python の文を実行することです。<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

その他のインタープリターの例を以下に示します。ここに挙げたインタープリターのドキュメントには、インラインコードの実行や子プロセス API に関する記載があります。<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

正確なパスが重要です。sudo ルールで `/usr/bin/python3` が許可されている場合は、検証時にもその正確なパスを使用してください。<sup>[[2]](#references)</sup>

`/usr/bin/python*` のような sudo 実行ファイルの glob は、Python 3 用に書かれたスクリプトに対して Python 2 も許可する場合があります。スクリプトが呼び出し元によって制御されたテキストを `input()` で受け取る場合、[Python 2 はそのテキストを式として評価します](https://docs.python.org/2/library/functions.html#input)。インタープリターを明示して呼び出すと、スクリプトの shebang は上書きされます。実行経路と判断する前に、インストール済みの該当バイナリ、実効 RunAs と引数ポリシー、拒否設定、入力に到達できるかを確認してください。

root で実行可能な sudo ルールでスクリプトのパスが固定されていても、そのスクリプトが実行する内容までは制限されません。読み取り可能な Bash wrapper については、sudo で呼び出し元が引数を選択できる場合に、最初に実行されるコマンドが、引用符で囲まれていない位置パラメーター（`$1` など）を**コマンド語**として使用していないか確認してください。実効 RunAs ID、パスワードと引数のポリシー、後続の拒否設定、実際に実行されるスクリプトの分岐を確認してください。`NOEXEC`、固定された安全な引数リスト、またはコマンドを検証する wrapper によって結果が変わる場合があります。列挙時には、テスト用コマンドを指定して実行するのではなく、短いスクリプトを静的に調べてください。

root で実行可能な `dotnet` の制限のない sudo ルールも、インタープリターの観点から確認する価値があります。.NET SDK がインストールされている場合、[`dotnet fsi` は F# コードを対話形式またはスクリプトから実行します](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/)。また、[`dotnet run` はソースからプロジェクトを実行します](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)。まず実効 RunAs ID と正確な引数ポリシーを確認してください。特定の安全なサブコマンドや信頼されたアプリケーションに固定されたルールは、許可内容が異なります。また、ランタイムのみのインストールでは SDK コマンドが使えない場合があります。実行ファイル名だけでは、コード実行の証拠ではなく、確認の手がかりにすぎません。

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo-allowed `tee`: 任意の特権ファイル書き込み

GNU `tee` は、標準入力をファイルオペランドとして指定されたすべてのパスにコピーします。そのため、呼び出し元が引数を制御できる状態で `/usr/bin/tee` の root 実行を許可する sudo ルールは、任意の root ファイルを作成または上書きする機能を与えます。`-a` を追加すると、この機能は追記に変わります。`PASSWD:` タグは sudo の認証に関するものであり、それ自体では書き込み先や標準入力から読み取るバイト列を制限しません。<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

まず、正確なルールを確認してください。許可されたテストシステムでは、安全に作成できる使い捨ての書き込み先だけを使って、この機能を検証してください。最後の `>/dev/null` は、`tee` が標準出力にコピーする内容だけを抑制します。<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

`sudo`をproducerの前に付けても、後続のshellリダイレクトによる権限は昇格しません。書き込み先を開くのは呼び出し元のshellだからです。上記のパイプラインのように、特権プロセス自体が書き込みを行う必要があります。<sup>[[1]](#references)[[15]](#references)</sup>

書き込みを確認したら、[Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md)から適切なrootコード実行の足がかりを選びます。確認された攻撃チェーンの一例では、root権限の`tee`を使って`/etc/cron.d/`配下に一時的なファイルを作成し、ユーザーが制御するスクリプト経由でバックドアを起動してから、実行後にcronファイルを削除しました。cronファイルを削除することで、長期的な永続化エントリになるのを防げましたが、システムログには依然として活動の証拠が残っていました。<sup>[[27]](#references)</sup>

## Sudoで許可されたエディタ

`sudo -l`でユーザーがrootとして対話型エディタを実行できる場合、それを無害なファイル編集権限ではなく、コマンド実行の攻撃面として扱ってください。エディタからshellコマンドを実行したり、任意のファイルを読み書きしたり、外部ヘルパーを呼び出したりできることがよくあります。<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

一般的な確認手順は、まずユーザーの権限を一覧表示し、次にsudo経由で許可された各エディタまたはpagerを起動することです。<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano コマンド実行

`nano` の sudo 経由での実行が許可されている場合、エディターのインターフェースからコマンドを実行できる可能性があります。<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

次に、nanoのコマンドプロンプトで、`id`や`/bin/sh`などのコマンドを入力します。<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

対話型シェルで使用可能な端末ストリームがない場合、このリダイレクト形式は標準出力と標準エラーをファイル記述子0に割り当てます。<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

nanoの正確なキーシーケンスは、バージョンやビルドオプションによって異なる場合がありますが、セキュリティ上の問題は同じです。エディターがrootとして実行され、外部コマンドを呼び出せます。<sup>[[1]](#references)[[12]](#references)</sup>

### その他の一般的なエディターからのエスケープ

Vim系のエディターでは、通常 `:!` を使ってコマンドを実行できます。<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` などの pager からも shell を実行できる場合があります。<sup>[[14]](#references)</sup>

`apport-cli` を root として実行できる sudo ルールがある場合も、同様に pager を確認してください。影響を受ける Apport のバージョンでは、攻撃者が調整できる端末サイズでクラッシュレポートを `less` で開くことがあり、特定の sudo および pager の条件が満たされると、pager から root shell を取得できる可能性がありました。バージョンだけで脆弱と判断せず、有効な sudo ルール、pager の設定、ディストリビューションのパッケージ修正を確認してください。受動的な列挙では、クラッシュを発生させたり、特権付きレポートを開いたりせずに、パッケージとポリシーのメタデータを確認してください。[Ubuntu の CVE レコード](https://ubuntu.com/security/CVE-2023-1326)には、バックポートされた修正を含む、リリースごとの修正済みパッケージバージョンが記載されています。

```text
!/bin/sh
```

## その他の sudo および doas ルールの危険性

まず `sudo -l`、`sudo -V`、該当する `doas` ポリシーを確認します。許可されたコマンド、実行ユーザー、引数、環境変数、デフォルト設定をまとめて確認してください。root 以外のサービスアカウントとして実行する権限でも、そのアカウントのファイルや root への経路にアクセスできる場合があります。

sudo で実行を許可された Python スクリプトが固定されていても、対話的に入力を受け取り、その入力を [`os.system()`](https://docs.python.org/3/library/os.html#os.system) に連結する場合、RunAs ID でシェルコマンドを実行できる可能性があります。シェルの句読記号を denylist で除外するだけでは安全性を確認できません。[シェルは `$(...)` によるコマンド置換も認識します](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)。許可された引数が入力処理の分岐に届くこと、入力が安全に検証されずシェルコマンドに渡ること、有効な sudo ポリシーで意図した RunAs ユーザーが許可されていることを確認します。スクリプトのパスや `os.system()` の呼び出しだけでは、あくまで調査の手がかりにすぎません。特権スクリプトを実行せず、ソースを確認してください。

`chattr` を root で実行できる有効な sudo 権限があれば、ファイルの immutable (`i`) 属性を解除できますが、それだけで書き込み権限や新しい ID が得られるわけではありません。[`chattr` のマニュアル](https://man7.org/linux/man-pages/man1/chattr.1.html)によると、この属性は変更を阻止し、変更できるのは root または `CAP_LINUX_IMMUTABLE` を持つプロセスだけです。sudo の正確な引数ポリシーとファイルシステムの対応状況を確認したうえで、属性解除後に呼び出し側がファイルへ書き込めること、さらに高い権限のプロセスがそのファイルを使用することを個別に確認します。たとえばログインシェルの置き換えには、対象アカウントで受け入れられる認証情報と、そのシェルを通じた実際のログインも必要です。列挙中に変更を加えず、ポリシー、ファイル属性、権限を確認してください。

sudo でパスワードとワンタイムコードの両方を求められる場合、それらの前提条件とコマンド実行権限を分けて考えます。読み取り可能な `.google_authenticator` ファイルには機密性の高いシード情報が含まれます。一方、古いアプリケーションやデータベースのパスワードハッシュは、現在のアカウントパスワードの候補にすぎません。どちらも、もう一方の要素が有効な PAM 設定で受け入れられる証拠にはなりません。権限が確認できたら、正確な RunAs と引数を確認します。RubyGems の `gem` を root で無制限に実行できる権限は、そのエディターコマンドを利用できる可能性があります（[GTFOBins](https://gtfobins.github.io/gtfobins/gem/)）。ただし、制限付きの権限や認証失敗では該当しません。受動的な列挙では、シードを表示したり、パスワードを復元したり、コードを生成したり、特権コマンドを実行したりせず、パスとポリシーを報告してください。

Chef の `knife` を root 権限で無制限に実行できる sudo 権限は、インタープリターの観点から調査する必要があります。[Chef のドキュメントによると、`knife exec -E` は Ruby 文字列をローカルで評価します](https://docs.chef.io/workstation/26/tools/knife/knife_exec/)。有効な sudo ルールで `exec` サブコマンドと呼び出し側指定の `-E` 引数が許可されていること、意図した RunAs ID、該当するコマンド拒否設定や固定引数を確認します。インストール済みバイナリや他のサブコマンドに限定されたルールは、調査の手がかりにすぎません。受動的な列挙では、`knife` を実行せず、ルールを報告してください。

対話型 `msfconsole` を root 権限で正確に実行できる sudo 権限も、同様に慎重な確認が必要です。[GTFOBins は、sudo の ID を引き継ぐ可能性がある `irb` コンソールについて説明しています](https://gtfobins.org/gtfobins/msfconsole/)。有効な RunAs ユーザー、許可された引数一覧、コマンド拒否設定、`NOEXEC` などの制限、インストール済みコンソールの動作、呼び出し側が対話入力を渡せるかを確認します。パスが強調表示されるだけでは調査の手がかりにすぎません。受動的な列挙ではコンソールを起動しないでください。

FreeBSD では、root での `pkg update` と `pkg install *` に限定された sudo ルールでも、リポジトリの信頼性を確認する必要があります。呼び出し側が `/etc/hosts` に書き込めるか、有効なリポジトリ設定で `signature_type: none` を指定した HTTP ホスト名が使われているかを確認します。[FreeBSD の `pkg.conf` マニュアル](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5)によると、`none` は署名チェックを無効にします。`pkg+http` が使われているだけでは、これを確認したことにはなりません。パッケージにはインストールスクリプトが含まれる可能性があります（[FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)）。実際にリポジトリエンドポイントを制御でき、パッケージも選択できる呼び出し側は、root の境界を越えられる場合があります。結論を出す前に、リポジトリの上書き設定、SRV／ミラー解決、有効な sudo 引数、パッケージ選択、スクリプト実行を確認します。列挙中に名前解決先を変更したり `pkg` を実行したりせず、ポリシーと小さなローカル設定ファイルを確認してください。

`apt-get update` と `apt-get upgrade` を root 権限で実行できる sudo 権限では、呼び出し側が制御する `http_proxy` を sudo が保持する場合、リポジトリの信頼性も確認する必要があります。有効な APT プロキシ設定が実際にこの変数を使うか、どの有効なリポジトリのリクエストに影響するかを確認します。信頼された署名鍵で認証されたアーカイブからパッケージを置き換えることは、プロキシだけではできません。[APT の HTTP transport マニュアル](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html)にはプロキシの優先順位が、[apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html)には署名チェック、安全でないリポジトリへの上書き設定、未認証パッケージに対する確認について記載されています。sudo の正確な RunAs と引数、リポジトリ認証ポリシー、必要な対話確認、選択したアップグレードが root でパッケージスクリプトを実行するかを確認します。受動的にポリシーとローカル設定を調べ、列挙中にパッケージ通信先を変更したりアップグレードを実行したりしないでください。

`snap install` を root 権限で実行できる sudo ルールは、引数によって呼び出し側がローカル snap と制限の緩いインストールモードを選べる場合、パッケージからコードへの境界になり得ます。[Snap のドキュメント](https://snapcraft.io/docs/explanation/snap-development/install-modes/)によると、`--dangerous` はローカル snap の assertion チェックを省略し、`--devmode` は confinement を緩和します。また、[インストールフックは初回インストール時に実行される可能性があります](https://snapcraft.io/docs/reference/development/supported-snap-hooks/)。保護されたホストファイルにアクセスできると判断する前に、正確な sudo の引数／RunAs ポリシー、snap ファイルの制御者、インストール済み snapd がこれらのモードを受け付けるか、フックの実効 ID と confinement を確認します。`snap` バイナリやワイルドカードのように見えるルールだけでは、この一連の条件は証明されません。受動的な列挙ではパッケージをインストールしたりフックを実行したりしないでください。

**root 以外**のアカウントで実行される、認証情報を読み取るカスタムバイナリに対する正確な sudo 権限では、まず実行せずにバイナリとファイル権限を確認します。埋め込まれたパスワードゲートは、幅広文字としてしか見えない場合があります。[GNU `strings` のドキュメントには、16-bit little-endian 抽出方法が記載されています](https://sourceware.org/binutils/docs/binutils/strings.html)。文字列が見つかっても、それが受け入れられるパスワードであることや、成功時の分岐で現在の認証情報が得られることの証明にはなりません。バイナリの動作、保護データへの対象アカウントのアクセス権、認証情報の有効性、その後に別アカウントやグループへ移行できるかを個別に確認します。そのアカウントが `docker` グループに属している場合、ホストの root へアクセスできると推測する前に、ソケットへのアクセスとデーモンの rootful／rootless ID を確認してください。[Docker のドキュメントには、そのグループが root レベルの影響を持つことが記載されています](https://docs.docker.com/engine/install/linux-postinstall/)。通常の列挙では、バイナリを実行したり文字列をダンプしたりせず、sudo ルールとグループ所属を報告してください。

アプリケーションのメンテナンススクリプトに対するワイルドカード sudo ルールは、スクリプトのパス以外も調べる必要があります。許可されたスクリプトが制限のない引数を受け付けるか、権限の低いアプリケーションアカウントから書き換えられる設定を読むかを確認し、それらの値がシェルコマンドやサブプロセスの環境変数に渡るかを追跡します。たとえば ZoneMinder の[`zmupdate.pl` は `mysqldump` コマンドを組み立て、`qx` で実行します](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in)。また、[`zmdc.pl` は `ZM_LD_PRELOAD` 設定を `LD_PRELOAD` にコピーしてから](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)、デーモンを起動します。該当する入力を制御でき、インストール済みバージョンでそのコードに到達する場合、どちらかのスクリプトを root で許可する sudo ルールは信頼境界を越える可能性があります。有効な sudo ルール、アプリケーション設定の権限、スクリプトのソースを確認してください。ワイルドカードや設定値だけでは、実行の証明にならず、調査の手がかりにすぎません。

- `SETENV`、`env_keep`、`secure_path`、`LD_PRELOAD` によって、通常は制限されるコマンドでも import、ライブラリ、PATH の乗っ取りが可能になる場合があります。[環境変数ガイド](../linux-basics/linux-environment-variables.md)と[SUID／リンカーの悪用](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md)を参照してください。

root 権限で実行できる正確な `SETENV` 付きシェルラッパーでは、ラッパーが固定 Python スクリプトをリテラル import 付きで起動する場合も、1 段階先まで確認してください。`secure_path` が制限するのはシェルのコマンド検索であり、Python の[`PYTHONPATH` モジュール検索](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH)ではありません。[`-E` と `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) を指定すると、Python はその環境変数を無視します。コード実行と判断する前に、有効な sudo タグと拒否設定、ラッパーの分岐、インタープリターのオプション、import の解決、呼び出し側が書き込める検索ディレクトリを確認します。短いスクリプトは静的に調べ、特権ラッパーを実行しないでください。

`XDG_CONFIG_HOME` を呼び出し側が制御できる状態で sudo のデフォルト設定がこれを保持する場合、正確な `neofetch ""` の root sudo 権限でもシェル設定を読み込む可能性があります。[Neofetch の設定ローダー](https://github.com/dylanaraps/neofetch/blob/master/neofetch)は、そのディレクトリ下にある `neofetch/config.conf` または `neofetch/config` を source します。引数が空でも、この検索は行われます。インストール済みローダー、有効な RunAs と引数ポリシー、コマンド拒否設定、sudo が実際にこのコマンドの選択した変数を保持するか、呼び出し側が読み取り可能な設定パスを制御するかを確認します。変数の保持や Neofetch のインストールだけでは、調査の手がかりにすぎません。特権コマンドを実行したり設定内容を表示したりせず、ポリシーとファイルのメタデータを調べてください。[sudoers の環境変数処理](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)を参照してください。

root 権限で `facter` を無制限に実行できる sudo ルールでは、カスタム fact も別途確認してください。[Puppet のドキュメント](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm)によると、`--custom-dir` は指定ディレクトリから Ruby fact ファイルを読み込みます。正確な sudo ルールでこのオプションが許可されているか、インストール済み Facter がこれを受け付けるか、呼び出し側がディレクトリを制御できるかを確認します。固定引数の権限、明示的なコマンド拒否、カスタム fact の無効化によって結果は変わります。受動的な列挙では Facter を実行したり fact の内容を読んだりせず、ポリシー上の候補を報告してください。

`SETENV` 付きで root 権限を与える正確な sudo スクリプト権限では、`find` などの裸のコマンド名と、sudo ポリシーおよびスクリプト初期化後の有効な `PATH` を確認します。source される Bash ファイルで `enable -n [` を実行できる場合、スクリプトが後でそのコマンドを使うと、[Bash は `PATH` から外部の `[` を検索します](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html)。コード実行と判断する前に、該当する[sudoers の環境変数および `secure_path` ルール](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)、`NOSETENV`／`NOEXEC` や拒否設定、スクリプトと source されるファイルの処理、呼び出し側が制御する実行可能な検索ディレクトリを確認します。裸のコマンド名を含む読み取り可能なスクリプトは調査の手がかりであり、特権実行の証明ではありません。sudo ルールを実行せずに調べてください。
- `curl` で固定 URL を取得する特権スクリプトでも、該当する sudo ルールが `http_proxy` を保持し、そのプロキシ経由でリクエストを送る場合、呼び出し側がレスポンスを選べる可能性があります。その後、外部エンティティを解決する XML パーサーにレスポンスを渡す場合、悪意あるレスポンスによって特権プロセスが読み取れるファイルが漏えいする可能性があります。sudo の正確な環境ポリシー、`no_proxy` による除外、リクエスト先 URL、パーサー設定、出力先を確認してください。プロキシ変数や XML パーサーだけでは脆弱性を証明できません。[curl のプロキシ環境変数に関するドキュメント](https://everything.curl.dev/usingcurl/proxies/env.html)に、変数の動作が記載されています。受動的な列挙ではネットワークリクエストを送信したり、悪意ある XML を解析したりしないでください。
- 呼び出し側の影響を受けるデータから PostScript ファイルを作り、`ps2pdf -dNOSAFER` を実行する root sudo スクリプトは、入力から処理への流れを別途確認する必要があります。Ghostscript の説明によると、このフラグは `.setsafe` まで SAFER を無効にし、プロセスの OS 権限で PostScript のファイル操作を可能にします。呼び出し側の引数から組み立てた SQL クエリが、攻撃者の制御する行を PostScript テンプレートに渡す場合があります。ただし、クエリ文字列や `ps2pdf` の呼び出しだけでは、データが実行可能な PostScript 構文に届く証明にはなりません。有効な sudo ルール、入力からテンプレートまでの正確な経路、エスケープ処理、インストール済み Ghostscript の動作、ドキュメントの解釈前に SAFER が再有効化されるかを確認します。受動的な列挙では特権変換を実行しないでください。[Ghostscript の `-dNOSAFER` に関するドキュメント](https://ghostscript.readthedocs.io/en/master/Use.html)を参照してください。
- シェルスクリプトを実行する sudo ルールでは、保持される環境変数とスクリプト自体を照合します。`if $CHECK_CONTENT; then` のような記述は、展開された値をコマンドとして実行するため、スクリプトのパスと引数が固定されていても `CHECK_CONTENT` が保持されればコマンド実行につながる可能性があります。該当の分岐に到達できるか、環境変数が実際に保持されるかは、個別のルールで確認が必要です。<sup>[[2]](#references)[[22]](#references)</sup>
- sudo で実行を許可された Python スクリプトは、呼び出し側が書き換えられるディレクトリやキャッシュ済み `.pyc` ファイルからコードを import する可能性もあります。[権限昇格ガイド](../linux-basics/linux-privilege-escalation/README.md)では、キャッシュの場合を詳しく説明しています。
- root で実行を許可された固定 Python スクリプトでも、対話型デバッガーが公開される場合があります。`pdb.set_trace()` や `pdb.post_mortem()` のような呼び出しは、呼び出し側がブレークポイントや例外ハンドラーに到達でき、**デバッガーの入力ストリームを制御できる**場合、デバッグ中のプロセスのコンテキストで Python 文を実行できます。正確な sudo RunAs ルール、認証と分岐条件、例外に到達できるか、端末／入力の所有者、デバッガーが同じ特権プロセスで実行されるかを確認します。ソケットリクエストで例外を発生させても、それだけで別の端末に接続されたデバッガーにアクセスできるわけではありません。[Python のドキュメントには、デバッガーの文評価と post-mortem モードが記載されています](https://docs.python.org/3/library/pdb.html)。列挙中に特権ハンドラーを呼び出さず、スクリプトを静的に調べてください。
- sudo で実行を許可された固定 Python スクリプトが、データベースや Unix ソケットからプロファイルのフィールドを読み取り、後で `str.format()` の**書式文字列**になる文字列に追加する場合もあります。[置換フィールドでは、属性やマッピングキーをたどれます](https://docs.python.org/3/library/string.html#format-string-syntax)。攻撃者が制御するフィールドによって、`format()` に渡されたオブジェクトを調べられ、結果が表示されたり呼び出し側の読める場所に保存されたりすれば、それらのオブジェクトから到達可能なデータが漏えいする可能性があります。有効な sudo RunAs ID、該当レコードへの書き込み権限、書式文字列へのデータフロー、渡されるオブジェクト、出力の可視性を確認します。これは自動的なコード実行ではありません。また、信頼できるリテラル書式文字列に攻撃者制御の*値*を渡すケースとは異なります。漏えいしたシークレットが OS アカウントへの移行につながるのは、そのアカウントがそれを受け入れる場合だけです。特権操作を実行せず、スクリプトとソケットの権限を調べてください。
- root 権限で実行される Python ラッパーが、呼び出し側指定の URL を GitPython の `Repo.clone_from` に渡すことがあります。さらにラッパーが Git の `protocol.ext.allow=always` を有効にしている場合、`ext::` リモートによって外部ヘルパーを呼び出せる可能性があります。sudo の正確な引数、URL の取得元、GitPython のバージョンとベンダーパッチの有無、ラッパーが危険なプロトコルを明示的に許可しているかを確認します。GitPython は 3.1.30 で[安全でないプロトコルをデフォルトで拒否するガード](https://github.com/gitpython-developers/GitPython/commit/2625ed9)を追加しました。`git` 実行ファイルのバージョンは別途確認が必要です。受動的な確認では、clone を実行せず、ルールと必要最小限のソースだけを調べてください。
- リポジトリを clone する CLI に対する別ユーザーでの sudo 権限は、シェル文字列への別のインジェクション経路につながる可能性があります。呼び出し側が指定したリポジトリ引数が、安全な引数分離を経ずに Node.js の[`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback)や別のシェルコマンド組み立て処理に渡るかを追跡します。Node の `exec` はコマンド文字列をシェルに渡します。特権 clone を実行せずに、正確な RunAs ユーザー、許可されたサブコマンドと引数、インストール済みラッパーのコード、入力検証を確認します。リポジトリツールの名前や無制限の sudo ルールだけでは、コマンドインジェクションの証明になりません。
- root 所有のカスタムラッパーは、バイナリやスクリプトが書き換えられなくても、非特権ユーザーが変更できるフラグ、ローカル API の値、サービス状態によって特権アクションの実行判断を左右される場合があります。各ゲートをその入力と認可チェックまで追跡してください。列挙中は運用状態を変更せず、設定と権限を確認します。ラッパー内の `systemd-run` 呼び出しが関係するのは、そのゲートに影響を与えられる場合だけです。
- sudo で root として実行できるバックアップクライアントが、呼び出し側指定の設定ファイル（たとえば `npbackup-cli -c`）を受け付ける場合があります。実行ユーザーと許可された引数を正確に確認し、設定パス、バックアップ元のパス、リポジトリ、読み取り／復元オプションを呼び出し側が制御できるか調べます。読み取り可能な設定に暗号化されたリポジトリのシークレットが含まれていても、クライアントがそれを使える可能性はありますが、ルールだけではリポジトリへのアクセスや root ファイルの漏えいを証明できません。バックアップを実行したり内容をダンプしたりせず、認可を確認してください。
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) は、リポジトリパスワード取得のためにプログラムを呼び出す `--password-command` をサポートしています。sudo ルールで、権限の低いユーザーが指定したパスワードコマンドを root として実行でき、さらにパスワードが必要なサブコマンドも許可されている場合、そのヘルパーが root で実行される可能性があります。この条件を列挙するだけの目的でヘルパーやバックアップコマンドを実行せず、正確な sudo 引数と除外設定を確認してください。
- root 権限での `restic backup` も、sudo の引数パターンによって呼び出し側がバックアップ元と、後で読み取り／復号できるリポジトリの両方を指定できる場合、ファイル読み取りの境界を越える可能性があります。[sudoers の引数ワイルドカードは空白やスラッシュにも一致します](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)。そのため、固定リポジトリプレフィックスによってバックアップ元が制限されていると思い込まず、末尾のワイルドカードを確認してください。[Restic はローカルおよびリモートリポジトリへのバックアップに対応します](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)。ただし、ローカルリポジトリには root 専用の新規オブジェクトが書き込まれる可能性があります。漏えいと判断する前に、有効な sudo ポリシー、バックエンドへのアクセス、リポジトリのパスワード、生成されるオブジェクトの権限を確認します。バックアップされた SSH 鍵がアクセス権を与えるのは、接続先アカウントがその鍵を受け入れる場合だけです。受動的な確認中にテスト目的でバックアップを実行しないでください。
- 制限のないカスタムメンテナンスコマンドやバックアップコマンドは、出力先を指定できたり、独自のジョブスケジューラーを備えていたりする場合があります。ファイル書き込み経路では、正確な sudo ルールと実行ユーザー、データと出力先の両方を呼び出し側が制御できるかを確認します。スケジュールコマンド経路では、スケジューラーの実行 ID、コマンド入力、追加のパスワードや認可ゲートを確認します。コマンド名や `NOPASSWD` だけでは、どちらの経路も証明できません。[root 所有ファイルへの書き込み](../interesting-files-permissions/write-to-root.md)と[cron および systemd timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md)を参照してください。
- 固定 sudo コマンドでも、共有の書き込み可能ディレクトリから予測可能な設定ファイルを読み込むことがあります。呼び出し側がそのファイルを置き換えられるか、その source／destination フィールドが特権の fetch や copy を制御するかを追跡します。ローカルファイル URL は、sudo の RunAs アカウントだけが読めるデータを漏えいさせる可能性があります。呼び出し側が制御する source と保護された destination の組み合わせは、書き込み経路になる場合があります。特権転送を実行せずに、インストール済みプログラムの URL 処理、destination のパスチェック、有効な sudo ルール、出力へのアクセスを確認します。書き込み可能な `/tmp` の設定パスだけでは調査の手がかりにすぎません。バイナリとファイルのメタデータを確認してください。
- `git apply` の sudo ルールによって、RunAs アカウントが呼び出し側指定のパッチで選ばれたファイルを書き換える可能性があります。[CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh)では、コマンドが `--unsafe-paths` を受け付けない場合でも、細工されたパッチでシンボリックリンクを作成し、作業ツリー外へ書き込むことが可能でした。有効な sudo 引数ルール、パッチの取得元、RunAs アカウントが作業ディレクトリを操作できるか、インストール済み Git の修正版またはベンダーバックポートを確認します。`--unsafe-paths` を許可する無制限ルールは、別個の明示的なオプションリスクです。Git のバージョンや `git apply` の実行権限だけでは、保護されたファイルを変更できるとは限りません。受動的な列挙では、信頼できないパッチを適用しないでください。
- root 権限での `clamscan --debug` ルールは、権限の低いユーザーが DMG イメージを渡せて、インストール済みパーサーが[ファイル内容をデバッグ出力から漏えいさせる可能性のある CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html)の影響を受ける場合、読み取り境界を越える可能性があります。正確に許可された引数とスキャンパス、入力の制御、実効 RunAs アカウント、エンジンの修正／バックポート、出力が呼び出し側から見えるかを確認します。より広いルールで `--file-list`／`-f` が許可される場合は、そのファイルリストの動作を別途確認してください。`--debug <scan-path>` に固定されたポリシーでは、これらは許可されません。列挙中に細工したファイルをスキャンしたり、保護された出力を表示したりせず、ポリシーとパッケージのメタデータを調べてください。
- root 権限で、呼び出し側指定の暗号化ディスクイメージを開く sudo ルールと、そこから作られた mapper をマウントする別ルールがある場合、呼び出し側が制御するファイルをホストのマウント名前空間に取り込める可能性があります。両方の有効なルールと引数、イメージと mapper 名の制御、実際のマウント先、生成ファイルの所有者とモードを確認します。set-user-ID による移行には、アクセス可能な実行ファイル、set-user-ID を有効にするマウントオプション（`nosuid` は無効化します）、該当するプロセスまたは MAC ポリシーも必要です。イメージを開いたりマウントしたりするだけでは調査の手がかりにすぎません。既存バックアップを経由する別の方法にも、実際に利用できる鍵と、内部にある有用で読み取り可能なシークレットが必要です。受動的な確認では、イメージを開いたりマウントしたりせず、ポリシーとパスを調べてください。[cryptsetup のマニュアル](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc)と[mount オプション](https://man7.org/linux/man-pages/man8/mount.8.html)を参照してください。
- root 権限で実行されるシェルまたは Python スクリプトが、固定ディレクトリへ移動せずに `./helper` を呼び出す場合、作業ディレクトリも確認してください。`subprocess.run` に渡される `['./helper']` のような Python リストでも、呼び出し側が作業ディレクトリを選べる場合があります。呼び出し側が書き込み可能なディレクトリを選び、そこにその相対名の実行ファイルを置ける可能性があります。スクリプト内の別の場所で絶対パスを使っていても、この呼び出しは保護されません。コード実行と判断する前に、有効なルール、`runchdir` やその他のディレクトリ変更ポリシー、スクリプトの処理と分岐到達可能性、書き込み可能かつ実行可能なディレクトリ、マウント／`NOEXEC` 制限を確認します。スクリプトが読み取れない場合、認可された手段でソースを確認するまでは動作は不明です。スクリプトは静的に調べ、ヘルパーを実行しないでください。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)には、作業ディレクトリのポリシーが記載されています。
- root 権限で実行される固定 Python バリデーターでも、呼び出し側指定のデータファイルを評価する場合があります。[Python の `eval()` ドキュメントは、信頼できない入力を使わないよう警告しています](https://docs.python.org/3/library/functions.html#eval)。入力の接尾辞チェック、算術式のプレフィックス、検証分岐があっても、残りの式が `eval` に届くならサンドボックスにはなりません。実行経路と判断する前に、有効な sudo ルール、呼び出し側が正確なファイルを選択・制御できるか、パーサーの分岐条件と式の組み立て、特権プロセスの ID を確認します。読み取り可能なスクリプトに `eval` があるだけでは調査の手がかりにすぎません。列挙中にバリデーターを実行したり、テスト式を渡したりせず、ソースとファイル権限を確認してください。
- root 権限で動く sudo Ruby ラッパーが、`YAML.load(File.read("dependencies.yml"))` のような相対 YAML ファイル名を読み込む場合、ラッパーまたは sudo ポリシーで作業ディレクトリが固定されていなければ、呼び出し側の作業ディレクトリから入力を受け取る可能性があります。正確に許可された引数、ディレクトリとファイルの権限、インストール済み Psych の動作を確認します。古い `YAML.load` 実装では任意の Ruby オブジェクトをデシリアライズできましたが、新しいリリースではデフォルトでクラスが制限されています。静的な呼び出し箇所だけでは調査の手がかりにすぎません。ファイルが実際に呼び出し側の書き込み可能なディレクトリにあること、インストール済みローダーが危険なクラスを受け入れることを確認します。信頼できない入力には、必要最小限のクラスを明示的に許可した `safe_load` を推奨します。[Ruby 3.0 Psych ドキュメント](https://docs.ruby-lang.org/en/3.0/Psych.html)と[Ruby 3.1 Psych ドキュメント](https://ruby-doc.org/core-3.1.2/Psych.html)を参照してください。

- 正確な `sudo go run /absolute/file.go` の root 権限は、Go ソースが相対 WASM ファイルを読み込み、その結果を調べた後に相対シェルスクリプトを実行する可能性がある場合、作業ディレクトリを確認する必要があります。有効な RunAs、コマンド引数と拒否設定、呼び出し側が書き込める現在のディレクトリ、WASM から分岐へのデータフロー、その分岐がヘルパーを呼び出すかを確認します。sudo の固定 `runchdir`、`os.Chdir`、または[`exec.Cmd.Dir`](https://pkg.go.dev/os/exec)によって検索場所が変わる場合があります。静的な併記は候補にすぎません。Go、WASM、ヘルパーを実行せずにソースを調べてください。
- `sudoedit` と引数のワイルドカードでは、正確なバージョンとルールを確認してください。[チェックリスト](linux-privilege-escalation-checklist.md)には、sudoedit によるファイル編集の問題が含まれています。別ユーザーのワイルドカードパスに対する `sudoedit` 権限では、有効な `sudoedit_follow` または `FOLLOW` 設定、`sudoedit_checkdir`、解決後の対象、各親ディレクトリエントリを置き換えられるユーザーを確認します。前者はシンボリックリンクをたどることを許可する場合があり、後者を無効にすると書き込み可能ディレクトリのチェックが省かれます。ただし、どちらの設定だけでも他ユーザーのファイルへの書き込みは証明されません。結論を出す前に、インストール済み sudo ポリシーと一致する正確な引数を確認してください。[sudoers のオプション定義](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)を参照してください。
- sudoers のコマンドルールでは、引数のワイルドカードはパス文字だけでなく空白にも一致します。読み取り可能なコマンドに `/restricted/*` のような引数があると、一致したプレフィックスの後に追加ファイル引数を渡せる場合があります。正確な実行ユーザー、コマンドパス、引数パターン、その後の拒否設定を確認してください。ファイルを読めることが実証されても、コマンドを実行できるとは限りません。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)には、引数の glob とコマンドパスの glob の違いが記載されています。
- パスに見える引数 glob が `../` にも一致することがあります。たとえば、root 権限での `node /opt/scripts/*.js` ルールでは、渡すパス名が `/opt/scripts/` で始まり、親ディレクトリのセグメントを経由して解決される場合、呼び出し側が `/opt/scripts` の外の JavaScript ファイルを指定できる可能性があります。これは**引数**の glob です。Node 実行ファイルのコマンドパス glob では、スラッシュの一致規則が異なります。コード実行と判断する前に、有効なルール、その後の拒否設定、パス名の解決、対象ファイルの制御、sudoers の正規表現または digest の制限を確認します。[sudoers のワイルドカード規則](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)と[Node のコマンドラインドキュメント](https://nodejs.org/api/cli.html)を参照してください。
- アーカイバーなどのユーティリティには、実行フックがある場合があります。シェルやインタープリターだけがコマンドを実行すると決めつけず、許可された正確な引数を[GTFOBins](https://gtfobins.github.io/)で確認してください。
- root 権限で `qpdf` を無制限に実行できるルールでは、PDF 添付ファイルを通じて特権ファイルを漏えいさせる可能性があります。qpdf 10.2 以降は、出力 PDF を指定して `--empty` と `--add-attachment file ... --` を使用できます。特権プロセスが選択した source を読み取り、呼び出し側がアクセスできるパスへ PDF を書き込める場合、その出力に source のバイト列を含められます。ファイル漏えいが可能と判断する前に、有効な sudo 引数と除外設定、qpdf のバージョン、source へのアクセス、出力先を確認してください。root の SSH 鍵を読めても、その鍵が有効で root の SSH 認証が許可されている場合にのみログインに役立ちます。[qpdf の添付ファイルオプション](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments)を参照してください。
- sudo timestamp の再利用は、キャッシュポリシー、所有ユーザー、端末／セッション、権限によって異なります。[権限昇格ガイド](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens)では確認方法を説明しています。
- `doas` には独自のルールと設定があります。[doas のセクション](../linux-basics/linux-privilege-escalation/README.md#doas)の説明に従い、許可されたコマンドと書き込み可能な設定パスを確認してください。

### sudo で実行するビルドおよびパッケージツール

Foundry の `forge` を無制限に sudo 実行できる権限は、RunAs ID が別の root 以外のユーザーでも問題になり得ます。`--use` などのコンパイラーオプションでローカル実行ファイルを選択でき、`forge flatten -o` では出力ファイルを選択できます。悪用可能と判断する前に、インストール済み Forge のバージョン、正確な sudo 引数、アクセス可能なプロジェクトとコンパイラーのパス、出力権限、有効な環境変数を確認します。`PATH` 経由で見つかる相対ヘルパー実行ファイルは、バージョンと環境に依存する経路であり、あらゆる Forge ビルドに当てはまる性質ではありません。<sup>[[23]](#references)[[24]](#references)</sup>

root 権限で `pacman` を無制限に実行できると、パッケージの照会だけでは済みません。`-U` はローカルパッケージを受け付け、パッケージにはインストールスクリプトが含まれる場合があり、`--hookdir` で別のフックディレクトリを指定できます。テストを行う前に、有効な sudo ルール、引数制限、除外設定を確認してください。受動的な列挙でパッケージをインストールしたりフックを実行したりする必要はありません。<sup>[[25]](#references)[[26]](#references)</sup>

固定の sudo シェルラッパーが、指定した npm 依存関係をインストールしてから Node アプリケーションを起動する場合もあります。正確な RunAs ルール、パッケージがすでにインストールされているか、有効な `HOME` と npm の `userconfig`、プロジェクト設定またはコマンドラインによる上書き、権限の低いユーザーがその名前のレジストリやパッケージを制御できるかを確認します。[npm のドキュメントには、ユーザー単位およびプロジェクト単位の `.npmrc` 検索が記載されています](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/)。sudo の `HOME` の動作は、インストール済みポリシーとディストリビューションによって異なるため、特権 npm プロセスが書き込み可能なユーザーの `.npmrc` を読むとは限りません。新たにインストールされたパッケージが特権アプリケーションから import されれば、そのアプリケーションの ID でモジュールコードが実行される可能性があります。インストール時スクリプトは、バージョンや設定に依存する別の経路です。[npm のドキュメントには、そのライフサイクルとユーザー処理が記載されています](https://docs.npmjs.com/cli/v6/using-npm/scripts/)。`.npmrc` のパスや `npm install` の行だけでは、調査の手がかりにすぎません。受動的な列挙ではインストールもアプリケーションの起動も行わず、ルール、短いラッパー、設定パス、パッケージの出所を調べてください。

root 権限での `pip` または `pip3 download` の許可は、ローカルサービスと `.tar.gz` 接尾辞に URL パターンが限定されていても、呼び出し側が信頼できない source distribution を選べる場合、パッケージビルドの確認が必要です。`pip download` はアーカイブ URL を受け付け、パッケージのメタデータを解決します。sdist の準備中に、アーカイブを保存する前にビルドバックエンドや従来型の `setup.py` コードが実行される可能性があります。正確な sudo RunAs と引数ルール、呼び出し側が選択したアーカイブを公開または置換できるか、その pip バージョンが実際にメタデータを準備するかを確認します。信頼できる固定アーカイブや wheel では、この経路は成立しません。受動的な列挙では、信頼できないパッケージを取得したりビルドしたりしないでください。pip の[download コマンド](https://pip.pypa.io/en/stable/cli/pip_download/)、[build-system インターフェース](https://pip.pypa.io/en/stable/reference/build-system/)、[安全なインストールのガイダンス](https://pip.pypa.io/en/stable/topics/secure-installs/)を参照してください。

呼び出し側が選んだローカルプロジェクトパスを使う `pip install` を許可する sudo ルールは、より直接的にビルド境界を越えます。[pip はローカルのプロジェクトディレクトリを受け付け](https://pip.pypa.io/en/stable/topics/local-project-installs/)、そのビルドシステムを呼び出します。[ビルドバックエンドはプロジェクトが制御するビルドフックを実行します](https://pip.pypa.io/en/stable/reference/build-system/)。このルールを特権コード実行と判断する前に、有効な RunAs ID、正確な引数制限と拒否設定、選択されたプロジェクトを誰が制御するか、インストール済み pip／バックエンドの動作を確認します。信頼できる固定プロジェクトや、呼び出し側がパスを選べないルールでは、この経路は成立しません。受動的な列挙ではパッケージをインストールせず、ルールとプロジェクトのメタデータを調べてください。

root 権限で `easy_install` を無制限に実行できる権限も、関連するレガシーなパッケージビルドの確認ポイントです。[Setuptools のドキュメント](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html)によると、Easy Install はローカルのプロジェクトディレクトリを受け付け、source distribution をビルドします。呼び出し側が制御するプロジェクトでは、sudo の ID でビルド中に `setup.py` が実行される可能性があります。有効な RunAs アカウント、正確なコマンドと引数の制限（後続の拒否設定も含む）、選択されたプロジェクトの制御者、インストール済みツールの動作を確認します。信頼できる固定プロジェクトや、呼び出し側が source を選べないポリシーでは、この経路は成立しません。列挙中にパッケージをインストールせず、ルールとプロジェクトのメタデータを調べてください。

呼び出し側指定の URL を使う `setuptools.package_index.PackageIndex.download` を含む、sudo で実行可能な Python ラッパーは、`pip download` とは異なる確認対象です。[setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf)では、78.1.1 より前の影響を受けるリリースにおいて、URL から導かれたファイル名が意図されたダウンロードディレクトリの外へ抜け、プロセスの権限で書き込める問題が説明されています。有効な sudo RunAs と引数ルール、ラッパーが呼び出し側の URL をこの正確な API に渡すこと、インストール済みビルドまたはベンダーバックポート、結果のパスがどこに解決されるかを確認します。バージョン文字列や書き込み可能なダウンロードディレクトリだけでは、任意の場所への書き込みは証明されません。列挙中に URL を取得したりファイルを書き込んだりせず、短いラッパーとパッケージのメタデータを調べてください。

呼び出し側指定の `.spec` ファイルを PyInstaller に渡す sudo 許可済みビルドラッパーも、同様に信頼境界を確認する必要があります。PyInstaller の spec は**ビルド時に**評価される実行可能な Python であり、その `datas` エントリによってビルド ID が読み取り可能なファイルを成果物に含めることができます。正確な RunAs ユーザー、sudo の引数と拒否設定、ラッパーのパスと分岐処理、選択された spec ファイルの制御者、生成された成果物へのアクセスを確認します。`.py` 入力が許可されていることや PyInstaller がインストールされていることだけでは、spec ファイルを制御できることや特権実行を証明できません。受動的な確認では、サイズを限定したラッパーファイルとメタデータだけを読み、ビルドを実行しないでください。[PyInstaller の spec ファイルに関するドキュメント](https://pyinstaller.org/en/stable/spec-files.html)を参照してください。

### sudo で実行する preset／プラグインローダー

呼び出し側が preset またはプラグインのディレクトリを指定できる Python ツールは、sudo によって与えられた権限でコードを import する可能性があります。たとえば BBOT は `-p` で preset を受け付けます。[カスタムモジュールのドキュメント](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations)には、追加の Python モジュールディレクトリを選択する `module_dirs` エントリが記載されています。有効な sudo ルールで呼び出し側指定の preset が許可され、呼び出し側が選択したディレクトリ内のモジュールを制御できる場合、ツールが無効なモジュールを拒否する前に、特権ユーザーとしてコードが実行される可能性があります。列挙中にモジュールを読み込まず、インストール済みバージョン、sudo の正確な実行ユーザーと引数ポリシー、preset とモジュールのパスの所有者を確認してください。

### sudo で実行する Backdrop コマンドラインツール

[Bee](https://github.com/backdrop-contrib/bee) は、Backdrop CMS 用の PHP コマンドラインツールです。`eval` (`php-eval`) と `php-script` コマンドは、呼び出し側指定の PHP を実行できます。そのため、引数を制限せず Bee 実行ファイルを root で許可する sudo ルールは、Bee が Backdrop のインストールを初期化できる場合、root コード実行につながる可能性があります。サイトのディレクトリから実行するか、グローバルな `--root=<directory>` オプションでサイトを指定します。Bee や Backdrop の `settings.php` ファイルが見つかっただけでは、sudo 権限、利用可能なサイト、初期化の成功は証明されません。テストする前に、有効な sudo ルール、コマンドの除外設定、実行ファイルの ID、サイトへのアクセスを確認します。受動的な列挙では Bee を実行せず、ルールとファイルパスを調べてください。PHP コマンドの追加については、[Bee コマンドの変更履歴](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md)を参照してください。

### sudo で実行するターミナルサーバー

`mosh-server` は、起動したユーザーとして対話型ターミナルサーバーを起動します。高い UDP ポートとセッションキーを選び、両方を呼び出し側に表示します。クライアントが接続すると、通常はそのユーザーのログインシェルを起動します。そのため、root 権限での `mosh-server` 無制限実行は、サーバーコマンド自体が detach する場合でも、シェル実行の確認対象です。有効な RunAs ID、許可された引数と除外設定、インストール済みバイナリ、シェル、クライアントの有無、UDP アクセスを確認します。受動的な列挙では sudo ルールを調べるだけにし、サーバーを起動したり、稼働中のセッションキーを表示したりしないでください。[Mosh サーバーのマニュアル](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html)と[上流の設計ノート](https://github.com/mobile-shell/mosh#how-it-works)を参照してください。

### 呼び出し側のタスクファイルを書き換える特権バックアップラッパー

root で動くシェルラッパーが、呼び出し側指定のタスクファイルを受け取り、source パスから `../` を除去し、結果が許可されたディレクトリで始まることを確認して、タスクファイルを書き換えた後、その*パス名*をバックアッププログラムに渡すことがあります。完全な正規化後の変換済みパスを確認してください。文字列置換を一度行うだけでは、新たな traversal 文字列が露出し、字句的なプレフィックスチェックを通過する可能性があります。バックアッププログラムが変換済みのメモリ上のデータを読むのか、ファイルを再度開くのかも確認します。ファイルを再度開く場合、書き換えに失敗すると元の入力が残っている可能性があります。

Linux では、`fs.protected_regular` により、world-writable な sticky ディレクトリ内にある他ユーザー所有の通常ファイルへの `O_CREAT` 書き込みが拒否される場合があります。この拒否は保護機能ですが、書き込みエラーを無視するシェルラッパーなら、元のタスクファイルを使って処理を続ける可能性があります。この設定、ファイル所有者とディレクトリ、失敗時にラッパーが停止するかを確認します。この経路がファイル漏えいの候補になるのは、有効な sudo ルールで特権ユーザーとしてラッパーを実行でき、呼び出し側がタスク入力と読み取り可能なバックアップ先を制御でき、バックアップユーティリティが保護された source を実際に含める場合だけです。列挙中にバックアップを実行せず、これらの条件を確認してください。

### 特権パケットツールの引数ワイルドカード

`tcpdump` の sudo ルールでは、**引数パターン**の `*` は空白やスラッシュにも一致します。そのため、パス名に見える制限でも、追加オプション文字列を許可する場合があります。これはコマンド実行ファイルのパスにあるワイルドカードとは異なります。完全な RunAs ルールと、後続の拒否設定を確認してください。オプションを注入できる場合、有用な読み取り／書き込み機能が得られるかは、許可された実行方法とインストール済み [`tcpdump` のオプション仕様](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in)によって決まります。`-F`、`-V`、`-r`、`-w`、`-Z` を確認してください。`-V` が読むのはキャプチャファイル名のリストであり、任意のファイルを汎用的にダンプするものではありません。sudo がコマンドを許可していても、AppArmor などの MAC ポリシーによってファイルアクセスが阻止される場合があります。プロファイルファイルがディスク上にあるだけでは、ロード済みまたは enforcing 状態の証拠にはなりません。結論を出す前に、認可とポリシーを受動的に確認してください。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)にはワイルドカードの違いが記載されています。

引数制限のない `tcpdump` 実行ファイルだけを列挙した root 権限の sudo ルールも、確認が必要です。[tcpdump のマニュアル](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in)によると、`-C` または `-G` で保存済みキャプチャをローテーションする際、`-z` はローテーション後のコマンドを指定します。`-Z` またはコンパイル時のデフォルトによって、そのコマンドの実行前に権限が下げられる場合があります。このルールを権限昇格経路と判断する前に、有効な sudo ルール、インストール済みビルド、権限降格の動作、ローテーションを発生させられるかを確認します。強調表示されたルールは候補にすぎず、root コマンド実行の証明ではありません。

### sudo で実行する Nmap ラッパー

sudo で許可された `nmap` がシェルラッパーのパスを指す場合、許可された正確なパスと転送される各オプションを確認してください。よく知られた `--script` 表記を拒否しても、NSE コードの読み込みを必ずしも防げません。Nmap の[`--datadir`](https://nmap.org/book/man-misc-options.html)はデータファイルを選択し、スクリプト機能が有効な場合、NSE は選択したデータディレクトリから[`nse_main.lua` を読み込みます](https://nmap.org/book/nse-implementation.html)。インストール済みビルドによっては別表記の長いオプションも受け付けるため、制限と実際のバイナリのパーサーを照合してください。[`--excludefile`](https://nmap.org/book/man-target-specification.html)は別のファイル読み取り面であり、パーサーエラーからテキストが漏えいする可能性もあります。列挙中にスキャンを実行せず、有効な sudo ルール、ラッパーのロジック、Nmap のバージョン、ディレクトリの制御者、MAC ポリシーを確認してください。

### sudo で実行する Mercurial pull フック

`sudo hg pull /fixed/source` で source が固定されていても、コマンドが `-R` で受信側リポジトリを固定しない限り、受信側リポジトリは現在の作業ディレクトリで決まります。呼び出し側が制御する受信側リポジトリでは、`.hg/hgrc` にフックを設定でき、そのフックが sudo の RunAs ユーザーとして実行される可能性があります。[Mercurial は、信頼できないユーザーまたはグループが所有するリポジトリ設定を無視します](https://mercurial-scm.org/help/topics/config)。コード実行と判断する前に、RunAs アカウントの信頼対象ユーザー／グループと正確な作業ディレクトリを確認してください。受動的な確認ではポリシーと設定を読むだけで十分です。列挙のために pull を実行したりフックを呼び出したりしないでください。

### sudo で実行する Git pull フック

root 権限での正確な `sudo git pull` ルールでは、作業ディレクトリによって選択される**受信側**リポジトリも確認してください。呼び出し側所有のリポジトリには実行可能な `post-merge` フックを設定でき、pull が成功して実際に merge すると、Git プロセスの ID で実行される場合があります。[Git のドキュメントにはこのフック](https://git-scm.com/docs/githooks)と、[pull の merge／rebase 動作](https://git-scm.com/docs/git-pull)が記載されています。有効な sudo ルールと CWD、使用中のフックパスとその権限、新しいコミットを含む merge が可能かを確認します。失敗した pull、何も変更しない pull、rebase のみの pull では、このフック経路は成立しません。特権 pull を実行せず、ポリシーとリポジトリのメタデータを調べてください。

### sudo で実行する rsync アーカイブコピー

`sudo rsync -a ... /writable/source/* /fixed/destination/` では、**sudoers の引数パターン**にある `*` が空白にも一致し、source と destination の間に追加オプションを許可する場合があります。これは、シェルによるファイル名展開とは異なります。呼び出し側が source にファイルを置けて、特権 rsync プロセスが destination に書き込める場合、[`--chown`](https://download.samba.org/pub/rsync/rsync.1)で特権所有者を指定し、archive モードで権限ビットを保持することで、所有者付き SetUID ファイルを作成できる可能性があります。正確な[sudoers のワイルドカード仕様](https://man7.org/linux/man-pages/man5/sudoers.5.html)、rsync のバージョン、後続の拒否設定、ファイルシステムの `nosuid`、MAC ポリシーを確認します。一致するルールは調査の候補であり、権限昇格の成功を証明するものではありません。

### sudo で実行するパケットフィルターのルールエクスポート

`iptables` と `iptables-save`（または対応する `ip6tables` の組み合わせ）の両方を root で無制限に実行できる権限は、ファイル書き込みの観点から確認が必要です。`comment` match は呼び出し側指定のルール文字列を受け付け、`iptables-save -f` はシリアライズされたルールセットを指定パスに書き込みます。<sup>[[20]](#references)[[21]](#references)</sup> 有用なペイロードになるかは、インストール済みバックエンドが comment をどのようにシリアライズするか、出力先ファイルがエクスポート内の他の行を受け入れるかによって異なります。`iptables-save` だけでは、任意の内容を指定できません。正確な sudo RunAs ID、引数と除外設定、利用可能な match extension、バックエンド、出力先の権限を確認します。列挙中はファイアウォールルールを変更したりファイルを書き込んだりせず、権限を調べてください。

### 特権 Below ログディレクトリ

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w)は、world-writable な `/var/log/below` ディレクトリを作成する 0.9.0 より前の Below リリースに影響しました。サービスまたは許可された sudo コマンドが影響を受けるビルドを root で実行する場合、sticky bit のないログディレクトリに書き込み・検索できるユーザーが、特権プロセスが開く前にログエントリをシンボリックリンクへ置き換えられる可能性があります。インストール済みパッケージの修正状況、正確な特権実行経路、有効なディレクトリアクセス、sticky bit と ACL、`/var/log/below/error_root.log` のメタデータを確認します。world-writable なパスや sudo ルールだけでは、一連の条件は成立しません。sticky ディレクトリやベンダーバックポートがあれば評価が変わります。受動的な列挙ではメタデータを調べるだけでよく、リンクを作成したり特権プログラムを実行したりする必要はありません。

### 書き込み可能な入力からの特権サポートバンドル収集

sudo で実行を許可されたサポートプロファイルスクリプトは、root で固定ログパスを読み取り、その内容をプロファイルアーカイブにコピーする場合があります。実際のスクリプトでファイル読み取りを確認し、呼び出し側が source パスや親ディレクトリエントリをシンボリックリンクに置き換えられるか調べます。特権読み取りがリンクをたどり、その結果のアーカイブを呼び出し側が読める場合、保護されたファイルが漏えいする可能性があります。sudo 権限、書き込み可能な source パス、特権読み取り、読み取り可能な出力がすべて必要です。書き込み可能なログやプロファイルのファイル名だけでは不十分です。列挙中にファイルを置き換えたりプロファイルを生成したりせず、実効権限とリンクのメタデータを確認します。[Nagios XI のサポートガイダンス](https://support.nagios.com/forum/viewtopic.php?t=62758)には、root で実行するプロファイルスクリプトと出力アーカイブが記載されており、このようなバンドルで入力と出力へのアクセスを制限する必要性を示しています。

### root で実行する Python アーカイブ復元スクリプト

対象を厳密に限定した Python 復元スクリプトの sudo ルールでも、アーカイブ入力を確認する必要があります。呼び出し側がアーカイブを選択または置換でき、スクリプトが root で `tarfile.extractall(filter="data")` を実行する場合、その filter を信頼する前にインタープリターのセキュリティ更新を確認します。CPython は、CVE-2025-4517 を含む複数のシンボリックリンクおよびハードリンクによる filter 回避を、3.9.23、3.10.18、3.11.13、3.12.11、3.13.4 で修正しました。ディストリビューションのバックポートにより、より古いバージョンでも修正済みの場合があります。そのため、表示されたインタープリターのバージョンだけでは影響の有無を判断できません。<sup>[[16]](#references)[[17]](#references)</sup>

受動的な確認では、正確な sudo コマンドとスクリプトを読み、どの引数でアーカイブが選ばれるかを追跡し、現在のユーザーがアーカイブまたはその親ディレクトリに書き込めるかを調べます。インストール済みベンダーパッチと展開先は別途確認してください。`filter="data"` を指定しても、あらゆる信頼できないアーカイブが安全になるわけではありません。<sup>[[16]](#references)[[17]](#references)</sup>

### sudo で実行する機械学習モデルローダー

呼び出し側指定の `.pt`、`.pth`、`.ckpt` ファイルを許可する sudo ルールでは、特権スクリプトがそのファイルを [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html)、`pickle.load`、または別の pickle ベースローダーに渡す場合、確認が必要です。有効な RunAs ルール、呼び出し側が選択したモデルを作成または置換できるか、シェルラッパーから Python ヘルパーまでの実際の引数の流れを確認します。`.pth` 拡張子は無関係な Python site 設定ファイルにも使われるため、拡張子だけではモデル読み込みの証拠になりません。アーカイブスキャンや静的 pickle スキャンだけでは、後続の読み込みが安全であることは証明できません。ローダーの[バージョン依存の `weights_only` 動作](https://docs.pytorch.org/docs/stable/notes/serialization.html)と許可リストを調べます。[ML pickle と Fickling のノート](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling)を参照してください。受動的な列挙ではモデルを読み込んだり展開したりしないでください。

### 保存された入力の式評価

sudo 経由で root として固定 Python スクリプトを実行しても、権限の低いユーザーがアプリケーションデータベースに保存できるテキストが評価される場合があります。TensorFlow では、`preprocess_input_exprs_arg_string(value, safe=False)` を呼び出すと `eval` の経路が選択されます。[TensorFlow のアドバイザリ](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc)では、安全でないパーサーと、そのコマンドライン呼び出し元に対する修正が説明されています。アプリケーションが明示的に `safe=False` を指定して呼び出す場合、コマンドライン呼び出し元にパッチが適用されていても、別途確認が必要です。有効な sudo ルール、該当する入力行を変更できるユーザー、その行がフィルタリングやスコアリングを通過して呼び出しに届くか、インストール済み関数の動作を確認します。TensorFlow のバージョン、sudo 権限、固定モデルファイルだけでは、この一連の条件を証明できません。受動的にスクリプトとデータフローを調べ、列挙中に特権ヘルパーを実行したりテスト式を送信したりしないでください。

### sudo で許可された needrestart 設定

`needrestart -c` は、呼び出し側指定の Perl 設定ファイルを読み込み、その内容を評価します。`sudo -l` で `needrestart` を root として実行でき、引数で `-c` が許可されており、呼び出し側が書き込み可能な場所にある読み取り可能な設定ファイルを選べる場合、root コード実行につながる可能性があります。sudo の正確な実行ユーザーと引数ルールを確認してください。固定引数リストだけを許可するルールなら、この経路を阻止できる場合があります。これは needrestart のインタープリタースキャンに関する脆弱性とは別の問題です。パッケージを更新したり `interpscan` を無効にしたりしても、root で無制限に `-c` を許可するルールは安全になりません。<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### 別アカウントで実行する sudo Python import

固定の Python エントリーポイントでも、sudo がスクリプトを**root 以外**のサービスユーザーとして実行する場合を含め、呼び出し側が編集または置換できるモジュールを import する可能性があります。`from utils import status` のようなリテラル import では、パッケージディレクトリの権限に加えて、ローカルの `utils/__init__.py` と `utils/status.py` も確認してください。書き込み可能なファイルを実行経路と判断する前に、スクリプトの import パス、正確に許可された sudo 引数、該当する処理がその import に到達するかを確認します。列挙中にファイルを import したりスクリプトを実行したりせず、ファイルと権限を調べてください。<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` の正確な sudo ルールでは、読み取り可能なスクリプトだけで十分であり、実行ビットや shebang は不要です。**存在しない**ローカルモジュールも確認してください。スクリプトが import するモジュールのファイル名を呼び出し側が書き込めるスクリプトディレクトリに作成できる場合、Python がそのファイルを RunAs ID で読み込む可能性があります。有効な sudo ルール、インタープリターの実際の[モジュール検索パス](https://docs.python.org/3/library/sys_path_init.html)、モジュールが組み込みまたは凍結されているか、import に到達するかを確認します。スクリプトを直接許可する sudo ルールでは、実行ビットや shebang の要件は異なります。呼び出し側指定のトークンを `sudo -u account` の後ろに追加する別のラッパーも、引数の流れを確認する必要があります。これらのトークン内に別の `-u` があることが問題になるのは、呼び出される sudo ポリシーが結果の ID を許可する場合だけです。静的な文字列だけでは、どちらの経路も証明できません。

### 呼び出し側指定の設定で実行する sudo Apache

特権 `apachectl`、`apache2ctl`、`httpd` の呼び出しで、呼び出し側が制御する `-f` 設定ファイルを許可する sudo ルールがある場合、そのファイルと親ディレクトリの権限を確認します。Apache の[`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)ディレクティブは、モジュール名に続けて**モジュールファイル名**を取ります。さらに[`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile)もファイルを読み込みます。[`Include` と `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include)で設定を追加したり、エラーを通じてファイル内容を露出させたりできる場合があります。カスタムラッパーがパスを検証したり、権限を下げたり、引数を制限したりすることもあるため、書き込み可能な設定ファイルだけではコード実行の証明にならず、調査の候補にすぎません。結論を出す前に、パスの正規化、シンボリックリンク、ディレクティブの解析を確認してください。

### 呼び出し側指定の設定で実行する sudo nginx

root 権限で `nginx` を無制限に実行できるルールでは、別の設定を選択する[`-c` オプション](https://nginx.org/en/docs/switches.html)を使える場合があります。sudo の正確な引数と除外設定、呼び出し側が設定を指定できるか、生成される master または worker が保護されたパスへのアクセス権を保持するかを確認します。選択した `root` と `autoindex` によって、新しい listener 経由でファイルが公開される場合があります。[`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html)で特権ファイル書き込みが可能になる場合もありますが、DAV モジュールはデフォルトではビルドされません。その有無、listener への到達性、ファイル権限、一時ファイルの動作を確認する必要があります。[`error_log` ディレクティブ](https://nginx.org/en/docs/ngx_core_module.html#error_log)で任意のファイルを指定することもできます。`/etc/ld.so.preload` のような機密設定ファイルへのログ書き込みが権限昇格経路になるには、実効的な特権書き込みと、制御可能なログレコードが必要です。`sudo -l` で実行ファイルが強調表示されても、これらの経路が機能する証明にはなりません。受動的な列挙では nginx を起動したり再設定したりしないでください。

### 特権 Bash プロンプトでのパターン比較

sudo で許可された Bash スクリプトが呼び出し側から値を読み取り、`[[ "$expected" == $entered ]]` で確認する場合、Bash は右辺の引用符で囲まれていないオペランドをパターンとして解釈します。そのため、期待値を知らなくてもワイルドカードで比較を通過できる場合があります。オペランドを引用符で囲むと（`[[ "$expected" == "$entered" ]]`）、リテラル文字列として比較されます。構文だけでは悪用可能な経路は証明されません。正確な sudo ルール、プロンプトに到達できるか、比較後にスクリプトが何をするかを確認します。列挙中に期待値を表示しないでください。[Bash の条件式に関するリファレンス](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html)を参照してください。

### ファイルをダウンロードして実行する sudo ヘルパー

root 権限で実行できる無制限のカスタムヘルパーが、呼び出し側指定の URL を受け付け、レスポンスをディスクに書き込み、そのファイルを後からインタープリターやシェルで実行する場合、データフローを確認する必要があります。[sudoers では、コマンドエントリに引数が記載されていない場合、任意の引数が許可されます](https://man7.org/linux/man-pages/man5/sudoers.5.html)。実行ファイルのパスが固定でも、引数で選べるものは制限されません。インストール済みヘルパーの URL 検証、出力パス、成功時の分岐、その後の実行を確認します。libcurl の import や表示可能な文字列だけでは、この一連の処理は証明されません。

ヘルパーが**呼び出し側の制御する作業ディレクトリ内の相対パス**を使う場合、書き込みと実行の間に、固定の出力ファイル名を置き換えられる可能性があります。root 所有ファイルの rename または置換を左右するのは、ファイルモードだけではなく、ディレクトリへの書き込み／検索権限と sticky bit の制約です。[`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html)を参照してください。ヘルパーが後でパスを再度開くのか、すでに開いたファイル記述子を使うのか、書き込み前に信頼できるディレクトリへ移動するかを確認します。受動的に sudo ポリシー、ヘルパー、ディレクトリのメタデータを調べ、特権ダウンロードを実行したり列挙中に race を試したりしないでください。

root sudo のダウンロードヘルパーは、`curl <caller input> -o <fixed output>` のような Bash コマンド文字列を組み立てる場合、**引数**インジェクションにつながる可能性もあります。空白を拒否するフィルターでも、[Bash の brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html)は防げません。引用符なしのカンマ区切り要素は、複数の curl 引数に展開されることがあります。入力が固定の `-o` より前に curl に届く場合、呼び出し側が指定した出力オプションによって、最初の URL の出力先をヘルパーの ID で選択できる可能性があります。[curl は URL の順序に従って出力オプションを関連付けます](https://curl.se/docs/manpage.html#-o)。正確なシェル、引用符、入力検証、有効な sudo ルール、curl の引数順序と対応 URL スキーム、呼び出し側が取得データを制御できるか、結果を読み取れるかを確認します。PyInstaller でパッケージ化された実行ファイルに Python アプリケーションのロジックが含まれる場合もありますが、パッケージ化の印や `curl` という文字列だけではデータフローの証明になりません。認可された場合は、オフラインコピーの必要最小限の範囲を調べてください。通常の列挙ではヘルパーを実行したり、攻撃者が選んだデータを取得したりしないでください。

[`mktemp -u`／`--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html)を呼び出す root sudo シェルスクリプトは、未使用の名前を選ぶだけで、ファイルを**作成しません**。その後、別ユーザーが操作できるディレクトリ内にその名前でファイルを作成し、再び開いて内容を root の `authorized_keys` のような保護された出力先に追記する場合、一時ファイルの race を確認する必要があります。正確な sudo ルール、ディレクトリとファイルの所有者、作成から再オープンまでの順序、カーネル保護、特権書き込みが攻撃者制御のバイト列を実際に使うかを確認します。`mktemp -u` の文字列や書き込み可能な `/tmp` だけでは、race の証明になりません。列挙中にスクリプトを実行したり一時ファイルの race を試したりせず、スクリプトとパスのメタデータを調べてください。

## 防御上の注意

- sudo 経由でインタープリターや対話型エディターを許可しないでください。<sup>[[1]](#references)</sup>
- `tee` のような汎用ファイル書き込みコマンドを、オペランドを制限せずに許可しないでください。固定の出力先を選び、呼び出し側が制御するパスを拒否する root 所有ラッパーを使ってください。<sup>[[2]](#references)</sup>
- 狭い管理操作を 1 つだけ実行する、固定された root 所有ラッパーを優先してください。<sup>[[1]](#references)[[2]](#references)</sup>
- インタープリターを避けられない場合は、スクリプトの正確なパスを制限し、ユーザー制御の引数、書き込み可能な import、`PYTHONPATH`、安全でない環境変数の保持を防いでください。<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- ファイル編集が必要な場合は、正確なファイルパスに制限し、修正済みバージョンの sudo と厳格な環境処理を備えた `sudoedit` の利用を検討してください。<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`、`env_keep`、書き込み可能な作業ディレクトリ、書き込み可能なモジュール／import パス、`NOEXEC`、`use_pty`、ログ記録を確認してください。ただし、それらを完全なサンドボックスと見なさないでください。<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
