## Von Sudo zugelassene Interpreter

Wenn `sudo -l` einem Benutzer erlaubt, einen Interpreter als root auszuführen, sollte dies als direkte Codeausführung behandelt werden. Interpreter sind dafür ausgelegt, beliebigen Code auszuführen. Eine Regel, die `python3`, `perl`, `ruby`, `lua`, `node` oder ähnliche Binärdateien zulässt, entspricht daher in der Regel der Ausführung von Befehlen als root, sofern die Argumente nicht streng eingeschränkt und validiert werden.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Üblicher Prüfablauf: Zuerst die Berechtigungen des Benutzers auflisten und dann eine Python-Anweisung mit der Option `-c` des Interpreters ausführen.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Weitere Interpreter-Beispiele sind unten aufgeführt; die genannten Interpreter dokumentieren die Ausführung von Inline-Code oder APIs für Kindprozesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Der genaue Pfad ist wichtig. Wenn die sudo-Regel `/usr/bin/python3` erlaubt, verwende bei der Überprüfung genau diesen Pfad.<sup>[[2]](#references)</sup>

Ein sudo-Executable-Glob wie `/usr/bin/python*` kann auch Python 2 zulassen, obwohl ein Skript für Python 3 geschrieben wurde. Wenn das Skript `input()` mit vom Aufrufer kontrolliertem Text erreicht, [wertet Python 2 diesen Text als Ausdruck aus](https://docs.python.org/2/library/functions.html#input); ein expliziter Interpreter-Aufruf hat Vorrang vor dem Shebang des Skripts. Überprüfe die installierten passenden Binärdateien, die effektive RunAs- und Argumentrichtlinie, Ablehnungen sowie erreichbare Eingaben, bevor du dies als Ausführungspfad einstufst.

Ein fester Skriptpfad in einer root-fähigen sudo-Regel schränkt nicht ein, was das Skript ausführt. Prüfe bei einem lesbaren Bash-Wrapper, ob dessen erster ausführbarer Befehl einen nicht in Anführungszeichen gesetzten Positionsparameter wie `$1` als **Befehlswort** verwendet, während sudo vom Aufrufer ausgewählte Argumente zulässt. Bestätige die effektive RunAs-Identität, die Passwort- und Argumentrichtlinie, spätere Ablehnungen und den tatsächlich ausgeführten Skriptzweig; `NOEXEC`, eine feste sichere Argumentliste oder ein Wrapper, der seinen Befehl validiert, können das Ergebnis ändern. Untersuche das kurze Skript während der Enumeration statisch, statt es mit einem Testbefehl aufzurufen.

Auch eine uneingeschränkte root-fähige sudo-Regel für `dotnet` sollte auf Interpreter-Möglichkeiten geprüft werden. Wenn ein .NET SDK installiert ist, führt [`dotnet fsi` F#-Code interaktiv oder aus einem Skript aus](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), und [`dotnet run` führt ein Projekt aus dem Quellcode aus](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bestätige zuerst die effektive RunAs-Identität und die genaue Argumentrichtlinie: Eine Regel, die auf einen bestimmten sicheren Unterbefehl oder eine vertrauenswürdige Anwendung beschränkt ist, stellt eine andere Berechtigung dar, und bei einer reinen Runtime-Installation können SDK-Befehle fehlen. Der Name der ausführbaren Datei ist ein Prüfhinweis, aber kein Beweis für Codeausführung.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Für sudo erlaubtes `tee`: beliebiger privilegierter Dateischreibzugriff

GNU `tee` kopiert die Standardeingabe in jeden als Dateioperand angegebenen Pfad. Daher ermöglicht eine sudo-Regel, die die Ausführung von `/usr/bin/tee` als root mit vom Aufrufer kontrollierten Argumenten erlaubt, beliebige Dateien mit root-Rechten zu erstellen oder zu überschreiben. Mit `-a` wird stattdessen angehängt. Ein `PASSWD:`-Tag betrifft die sudo-Authentifizierung; für sich genommen beschränkt es weder das Ziel noch die aus der Standardeingabe gelesenen Bytes.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Prüfe zuerst die genaue Regel. Validieren Sie die Primitive auf einem autorisierten Testsystem nur mit einem temporären Ziel, das gefahrlos erstellt werden kann. Das abschließende `>/dev/null` unterdrückt lediglich die Ausgabe von `tee` auf der Standardausgabe.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Das Voranstellen von `sudo` vor den Producer erhöht nicht die Berechtigungen einer späteren Shell-Umleitung, da die aufrufende Shell das Ziel öffnet. Der privilegierte Prozess muss der Schreiber sein, wie in der obigen Pipeline.<sup>[[1]](#references)[[15]](#references)</sup>

Nachdem der Schreibvorgang bestätigt wurde, wähle ein geeignetes Ziel für die Root-Codeausführung aus [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Bei einer beobachteten Angriffskette wurde mit `tee` als root eine kurzlebige Datei unter `/etc/cron.d/` erstellt, über ein vom Benutzer kontrolliertes Skript eine Backdoor gestartet und die Cron-Datei nach der Ausführung gelöscht. Durch das Entfernen der Cron-Datei wurde verhindert, dass sie zu einem dauerhaften Persistenzeintrag wurde, obwohl die Systemprotokolle weiterhin Belege für die Aktivität enthielten.<sup>[[27]](#references)</sup>

## Editoren, die über sudo erlaubt sind

Wenn `sudo -l` einem Benutzer erlaubt, einen interaktiven Editor als root auszuführen, sollte man dies als Angriffsfläche für die Befehlsausführung behandeln und nicht als harmlose Berechtigung zum Bearbeiten von Dateien. Editoren können häufig Shell-Befehle ausführen, beliebige Dateien lesen oder schreiben oder externe Hilfsprogramme innerhalb des Editors aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Üblicher Prüfablauf: die Berechtigungen des Benutzers auflisten und anschließend jeden erlaubten Editor oder Pager mit sudo aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano-Befehlsausführung

Wenn `nano` über sudo erlaubt ist, kann die Befehlsausführung über die Editor-Oberfläche möglich sein.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Geben Sie dann einen Befehl wie `id` oder `/bin/sh` an der nano-Eingabeaufforderung ein.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Wenn eine interaktive Shell keine nutzbaren Terminal-Streams hat, leitet diese Umleitungsform ihre Standardausgabe und ihren Standardfehler auf Dateideskriptor 0 um.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die genaue Tastenfolge kann je nach Nano-Version und Build-Optionen variieren, aber das Sicherheitsproblem ist dasselbe: Der Editor läuft als root und kann externe Befehle ausführen.<sup>[[1]](#references)[[12]](#references)</sup>

### Weitere gängige Möglichkeiten, aus Editoren auszubrechen

Vim-ähnliche Editoren ermöglichen häufig die Ausführung von Befehlen über `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pager wie `less` können ebenfalls Shell-Ausführung ermöglichen.<sup>[[14]](#references)</sup>

Eine sudo-Regel, die `apport-cli` als root erlaubt, sollte ebenfalls auf Pager geprüft werden. Betroffene Apport-Versionen konnten einen Crash-Report in `less` mit einer vom Angreifer anpassbaren Terminalgröße öffnen; der Pager konnte dann eine root-Shell bereitstellen, wenn die besonderen sudo- und Pager-Bedingungen erfüllt waren. Prüfe die effektive sudo-Regel, die Pager-Konfiguration und den Paket-Fix der Distribution, bevor du allein aufgrund der Version von einer Schwachstelle ausgehst. Lies bei der passiven Enumeration die Paket- und Policy-Metadaten, ohne einen Crash auszulösen oder den privilegierten Report zu öffnen. [Ubuntus CVE-Eintrag](https://ubuntu.com/security/CVE-2023-1326) führt release-spezifische korrigierte Paketversionen auf, einschließlich zurückportierter Fixes.

```text
!/bin/sh
```

## Weitere Gefahren durch sudo- und doas-Regeln

Beginne mit `sudo -l`, `sudo -V` und allen zutreffenden `doas`-Richtlinien. Lies den erlaubten Befehl, den RunAs-Benutzer, die Argumente, die Umgebung und die Defaults gemeinsam. Die Berechtigung, einen Befehl als Nicht-root-Dienstkonto auszuführen, kann weiterhin dessen Dateien offenlegen oder einen Weg zu root eröffnen.

Ein festes, über sudo erlaubtes Python-Skript kann trotzdem einen Shell-Befehl unter seiner RunAs-Identität ausführen, wenn interaktive, vom Aufrufer kontrollierte Eingaben in [`os.system()`](https://docs.python.org/3/library/os.html#os.system) verkettet werden. Eine Denylist für Shell-Zeichen reicht nicht als Sicherheitsnachweis: [Die Shell erkennt auch die Befehlsersetzung `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Prüfe, ob die erlaubten Argumente den Eingabezweig erreichen, ob die Eingabe ohne sichere Validierung in den Shell-Befehl gelangt und ob die wirksame sudo-Richtlinie den vorgesehenen RunAs-Benutzer erlaubt. Der Skriptpfad oder ein Aufruf von `os.system()` ist allein nur ein Prüfhinweis; untersuche den Quellcode, ohne das privilegierte Skript aufzurufen.

Eine wirksame sudo-Berechtigung für `chattr` als root kann das unveränderliche (`i`) Dateiattribut entfernen, gewährt dadurch allein aber weder Schreibzugriff noch eine neue Identität. [Das Handbuch zu `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) besagt, dass das Attribut Änderungen verhindert und nur root oder ein Prozess mit `CAP_LINUX_IMMUTABLE` es ändern kann. Prüfe die genauen sudo-Argumentregeln und die Unterstützung durch das Dateisystem. Verifiziere anschließend separat, ob der Aufrufer die Datei nach dem Entfernen des Attributs beschreiben kann und ob ein Prozess mit höherer Identität sie verwendet. Das Ersetzen einer Login-Shell erfordert beispielsweise auch gültige Zugangsdaten des Zielkontos und eine tatsächliche Anmeldung über diese Shell. Prüfe Richtlinien, Dateiattribute und Berechtigungen, ohne sie bei der Bestandsaufnahme zu ändern.

Wenn sudo sowohl nach einem Passwort als auch nach einem Einmalcode fragt, behandle diese Voraussetzungen getrennt von der Befehlsberechtigung. Eine lesbare Datei `.google_authenticator` enthält sensibles Seed-Material, während ein alter Passwort-Hash aus einer Anwendung oder Datenbank lediglich ein Kandidat für das aktuelle Kontopasswort ist; weder beweist, dass der andere Faktor von der wirksamen PAM-Konfiguration akzeptiert wird. Prüfe nach entsprechender Autorisierung den genauen RunAs-Benutzer und die Argumente: Eine uneingeschränkte root-Berechtigung für RubyGems `gem` kann dessen Editor-Befehl zugänglich machen ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), eine eingeschränkte Berechtigung oder fehlgeschlagene Authentifizierung jedoch nicht. Eine passive Bestandsaufnahme sollte Pfade und Richtlinien melden, ohne das Seed auszugeben, ein Passwort wiederherzustellen, einen Code zu erzeugen oder den privilegierten Befehl aufzurufen.

Eine uneingeschränkte sudo-Berechtigung für `knife` von Chef mit root-Rechten sollte auf Interpreter-Ebene geprüft werden: [Chef dokumentiert, dass `knife exec -E` lokal einen Ruby-String auswertet](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Prüfe, ob die wirksame sudo-Regel das Unterkommando `exec` und das vom Aufrufer angegebene Argument `-E` zulässt, welche RunAs-Identität vorgesehen ist und ob passende Befehlsverbote oder feste Argumente gelten. Die installierte Binärdatei oder eine auf andere Unterkommandos beschränkte Regel ist lediglich ein Prüfhinweis. Eine passive Bestandsaufnahme sollte die Regel melden, ohne `knife` aufzurufen.

Eine genaue sudo-Berechtigung für ein interaktives `msfconsole` mit root-Rechten ist ähnlich sensibel: [GTFOBins dokumentiert dessen `irb`-Konsole](https://gtfobins.org/gtfobins/msfconsole/), die die sudo-Identität übernehmen kann. Prüfe den wirksamen RunAs-Benutzer, die erlaubte Argumentliste, Befehlsverbote, `NOEXEC` oder andere Einschränkungen, das Verhalten der installierten Konsole und ob der Aufrufer interaktive Eingaben liefern kann. Ein hervorgehobener Pfad ist allein nur ein Prüfhinweis; starte die Konsole bei der passiven Bestandsaufnahme nicht.

Unter FreeBSD verdient selbst eine auf `pkg update` und `pkg install *` als root beschränkte sudo-Regel eine Prüfung des Repository-Vertrauens. Prüfe, ob `/etc/hosts` für den Aufrufer beschreibbar ist und ob die *wirksame* aktivierte Repository-Konfiguration einen HTTP-Hostnamen mit `signature_type: none` verwendet. [Das FreeBSD-Handbuch zu `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) besagt, dass `none` die Signaturprüfung deaktiviert; `pkg+http` allein belegt das nicht. Ein Paket kann Installationsskripte enthalten ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), sodass ein Aufrufer, der den Repository-Endpunkt tatsächlich kontrolliert und ein Paket auswählen kann, die root-Grenze überschreiten könnte. Prüfe Repository-Überschreibungen, SRV-/Mirror-Auflösung, wirksame sudo-Argumente, Paketauswahl und Skriptausführung, bevor du diesen Schluss ziehst. Untersuche Richtlinien und kleine lokale Konfigurationsdateien, ohne Namen umzuleiten oder `pkg` bei der Bestandsaufnahme auszuführen.

Eine sudo-Regel mit root-Rechten für `apt-get update` und `apt-get upgrade` erfordert ebenfalls eine Prüfung des Repository-Vertrauens, wenn sudo ein vom Aufrufer kontrolliertes `http_proxy` beibehält. Prüfe, ob die wirksame APT-Proxy-Konfiguration diese Variable tatsächlich verwendet und welche aktivierten Repository-Anfragen davon betroffen sein können; ein Proxy allein kann keine Pakete aus einem Archiv ersetzen, das mit einem vertrauenswürdigen Signaturschlüssel authentifiziert wird. [Das APT-Handbuch zum HTTP-Transport](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) beschreibt die Proxy-Priorität; [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) beschreibt Signaturprüfungen, Überschreibungen für unsichere Repositories und die Bestätigung nicht authentifizierter Pakete. Prüfe die genauen sudo-RunAs- und Argumentregeln, die Repository-Authentifizierungsrichtlinie, erforderliche interaktive Bestätigungen und ob das ausgewählte Upgrade Paket-Skripte als root ausführt. Untersuche Richtlinien und lokale Konfiguration passiv; leite bei der Bestandsaufnahme keinen Paketverkehr um und führe kein Upgrade aus.

Eine sudo-Regel mit root-Rechten für `snap install` kann eine Paket-zu-Code-Grenze darstellen, wenn die Argumente dem Aufrufer erlauben, ein lokales Snap und einen permissiven Installationsmodus auszuwählen. [Snap dokumentiert](https://snapcraft.io/docs/explanation/snap-development/install-modes/), dass `--dangerous` die Assertion-Prüfung für lokale Snaps überspringt und `--devmode` die Einschränkung der Ausführung lockert; [ein Installations-Hook kann bei der Erstinstallation ausgeführt werden](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prüfe die genauen sudo-Argument- und RunAs-Regeln, wer die Snap-Datei kontrolliert, ob die installierte snapd-Version diese Modi akzeptiert und welche Identität sowie Einschränkungen für den Hook gelten, bevor du Zugriff auf geschützte Host-Dateien annimmst. Eine `snap`-Binärdatei oder eine scheinbar mit Wildcards versehene Regel allein belegt diese Kette nicht. Bei der passiven Bestandsaufnahme weder ein Paket installieren noch dessen Hook ausführen.

Bei einer genauen sudo-Berechtigung für eine benutzerdefinierte, Zugangsdaten lesende Binärdatei eines **Nicht-root-Kontos** solltest du zunächst die gewährte Binärdatei und ihre Dateiberechtigungen untersuchen, ohne sie auszuführen. Ein eingebetteter Passwortschutz ist möglicherweise nur als breite Zeichen sichtbar; [GNU `strings` dokumentiert die Extraktion von 16-Bit-Little-Endian-Strings](https://sourceware.org/binutils/docs/binutils/strings.html). Ein sichtbarer String beweist weder, dass er das akzeptierte Passwort ist, noch dass der Erfolgszweig aktuelle Zugangsdaten offenlegt. Prüfe das Verhalten der Binärdatei, den Zugriff des Zielkontos auf die geschützten Daten, die Gültigkeit der Zugangsdaten und jeden späteren Konto- oder Gruppenwechsel separat. Gehört dieses Konto zu `docker`, prüfe den Socket-Zugriff und die rootful- oder rootless-Identität des Daemons, bevor du auf Host-root-Zugriff schließt; [Docker dokumentiert die Auswirkungen seiner Gruppe auf root-Rechte](https://docs.docker.com/engine/install/linux-postinstall/). Eine routinemäßige Bestandsaufnahme sollte die sudo-Regel und Gruppenmitgliedschaften melden, ohne die Binärdatei auszuführen oder ihre Strings auszugeben.

Eine sudo-Regel mit Wildcards für Wartungsskripte einer Anwendung muss über den Skriptpfad hinaus geprüft werden. Prüfe, ob das erlaubte Skript uneingeschränkte Argumente akzeptiert oder Einstellungen liest, die über ein privilegienärmeres Anwendungskonto beschreibbar sind. Verfolge diese Werte dann bis zu Shell-Befehlen oder einer Subprozessumgebung. Zum Beispiel setzt ZoneMinders [`zmupdate.pl` einen `mysqldump`-Befehl zusammen und führt ihn über `qx` aus](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), während [`zmdc.pl` die Einstellung `ZM_LD_PRELOAD` in `LD_PRELOAD` kopiert](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in), bevor es Daemons startet. Eine sudo-Regel, die eines der beiden Skripte als root erlaubt, kann eine Vertrauensgrenze überschreiten, wenn die entsprechende Eingabe kontrollierbar ist und in der installierten Version diesen Code erreicht. Prüfe die wirksame sudo-Regel, die Rechte an der Anwendungskonfiguration und den Skriptquellcode; die Wildcard oder Einstellung allein ist nur ein Prüfhinweis, kein Ausführungsnachweis.

- `SETENV`, `env_keep`, `secure_path` und `LD_PRELOAD` können aus einem ansonsten eng begrenzten Befehl einen Import-, Bibliotheks- oder PATH-Hijack machen. Siehe den [Leitfaden zu Umgebungsvariablen](../linux-basics/linux-environment-variables.md) und [SUID/Linker-Missbrauch](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Auch eine genaue sudo-Berechtigung mit root-Rechten und `SETENV` für einen Shell-Wrapper sollte auf einer Ebene geprüft werden, wenn der Wrapper ein festes Python-Skript mit einem literalen Import startet. `secure_path` beschränkt die Suche nach Shell-Befehlen, nicht aber die [Modulsuche von Python über `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` und `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) lassen Python diese Umgebungsvariable ignorieren. Prüfe die wirksamen sudo-Tags und Verbote, den Wrapper-Zweig, Interpreter-Optionen, die Importauflösung und ein vom Aufrufer beschreibbares Suchverzeichnis, bevor du dies als Codeausführung einstufst. Untersuche kurze Skripte statisch; rufe den privilegierten Wrapper nicht auf.

Eine genaue sudo-Berechtigung für `neofetch ""` mit root-Rechten kann weiterhin eine Shell-Konfiguration laden, wenn die zutreffenden sudo-Defaults das vom Aufrufer kontrollierte `XDG_CONFIG_HOME` beibehalten. [Neofetchs Konfigurationslader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) bindet `neofetch/config.conf` oder `neofetch/config` unterhalb dieses Verzeichnisses ein; die leere Argumentliste verhindert diese Suche nicht. Prüfe den installierten Loader, die wirksamen RunAs- und Argumentregeln, etwaige Befehlsverbote, ob sudo die ausgewählte Variable für diesen Befehl tatsächlich beibehält und ob der Aufrufer einen lesbaren Konfigurationspfad kontrolliert. Eine beibehaltene Variable oder ein installiertes Neofetch ist allein nur ein Prüfhinweis. Untersuche Richtlinien und Dateimetadaten, ohne den privilegierten Befehl aufzurufen oder Konfigurationsinhalte auszugeben; siehe [sudoers-Umgebungsbehandlung](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Eine uneingeschränkte sudo-Regel mit root-Rechten für `facter` sollte separat auf benutzerdefinierte Facts geprüft werden. [Puppet dokumentiert](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), dass `--custom-dir` Ruby-Fact-Dateien aus einem ausgewählten Verzeichnis lädt. Prüfe, ob die genaue sudo-Regel diese Option erlaubt, ob die installierte Facter-Version sie akzeptiert und ob der Aufrufer das Verzeichnis kontrolliert. Eine Regel mit festen Argumenten, ein explizites Befehlsverbot oder deaktivierte benutzerdefinierte Facts können das Ergebnis ändern. Eine passive Bestandsaufnahme sollte den Richtlinienkandidaten melden, ohne Facter aufzurufen oder Fact-Inhalte zu lesen.

Bei einer genauen sudo-Skriptberechtigung mit root-Rechten und `SETENV` solltest du nackte Befehlsnamen wie `find` und den wirksamen `PATH` nach Anwendung der sudo-Richtlinie und Skriptinitialisierung untersuchen. Eine eingebundene Bash-Datei kann auch `enable -n [` ausführen: [Bash sucht anschließend über `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) nach einem externen `[` für spätere Verwendungen dieses Befehls im Skript. Prüfe die geltenden [sudoers-Umgebungs- und `secure_path`-Regeln](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), etwaige `NOSETENV`-/`NOEXEC`- oder Verbotsregeln, den Ablauf im Skript und den eingebundenen Dateien sowie ein ausführbares, vom Aufrufer kontrolliertes Suchverzeichnis. Ein lesbares Skript mit einem nackten Befehlsnamen ist ein Prüfhinweis, kein Nachweis privilegierter Ausführung; untersuche es, ohne die sudo-Regel aufzurufen.

- Ein privilegiertes Skript, das mit `curl` eine feste URL abruft, kann trotzdem eine vom Aufrufer ausgewählte Antwort akzeptieren, wenn eine zutreffende sudo-Regel `http_proxy` beibehält und die Anfrage über diesen Proxy gesendet wird. Übergibt das Skript die Antwort anschließend an einen XML-Parser, der externe Entitäten auflöst, kann eine bösartige Antwort Dateien offenlegen, die der privilegierte Prozess lesen kann. Prüfe die genauen sudo-Umgebungsregeln, `no_proxy`-Ausnahmen, die angeforderte URL, die Parserkonfiguration und das Ausgabeziel; eine Proxy-Variable oder ein XML-Parser allein ist keine Schwachstelle. Die [Dokumentation der curl-Proxy-Umgebung](https://everything.curl.dev/usingcurl/proxies/env.html) beschreibt das Verhalten der Variablen. Führe bei der passiven Bestandsaufnahme keine Netzwerkanfragen aus und parse kein bösartiges XML.
- Ein sudo-Skript mit root-Rechten, das aus vom Aufrufer beeinflussten Daten eine PostScript-Datei erstellt und anschließend `ps2pdf -dNOSAFER` ausführt, sollte separat auf den Eingabefluss geprüft werden. Ghostscript dokumentiert, dass dieses Flag SAFER bis zu `.setsafe` deaktiviert und dadurch PostScript-Dateioperationen im Rahmen der Betriebssystemberechtigungen des Prozesses zulässt. Eine aus einem Aufruferargument zusammengesetzte SQL-Abfrage kann angreiferkontrollierte Zeilen in die PostScript-Vorlage einbringen; eine Abfragezeichenfolge oder ein `ps2pdf`-Aufruf allein beweist jedoch nicht, dass die Daten ausführbare PostScript-Syntax erreichen. Prüfe die wirksame sudo-Regel, den genauen Pfad von der Eingabe zur Vorlage, etwaiges Escaping, das Verhalten der installierten Ghostscript-Version und ob SAFER vor der Interpretation des Dokuments wieder aktiviert wird. Führe die privilegierte Konvertierung bei der passiven Bestandsaufnahme nicht aus. Siehe die [`-dNOSAFER`-Dokumentation von Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Vergleiche bei einer sudo-Regel für ein Shellskript die beibehaltenen Variablen mit dem Skript selbst. Ein Konstrukt wie `if $CHECK_CONTENT; then` führt den expandierten Wert als Befehl aus, sodass ein beibehaltenes `CHECK_CONTENT` Befehlsausführung ermöglichen kann, selbst wenn Skriptpfad und Argumente festgelegt sind. Ob der Zweig erreichbar ist und die Umgebung tatsächlich beibehalten wird, muss für die konkrete Regel geprüft werden.<sup>[[2]](#references)[[22]](#references)</sup>
- Ein über sudo erlaubtes Python-Skript kann Code aus einem beschreibbaren Verzeichnis oder einer zwischengespeicherten `.pyc`-Datei importieren. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md) erläutert den Cache-Fall.
- Ein festes, als root erlaubtes Python-Skript kann weiterhin einen interaktiven Debugger zugänglich machen. Aufrufe wie `pdb.set_trace()` oder `pdb.post_mortem()` erlauben Python-Anweisungen im Kontext des debugten Prozesses, wenn der Aufrufer den Haltepunkt oder Exception-Handler erreichen **und den Eingabestrom des Debuggers kontrollieren kann**. Prüfe die genaue sudo-RunAs-Regel, Authentifizierung und Zweigbedingungen, die Erreichbarkeit der Ausnahme, die Kontrolle über Terminal und Eingabe sowie ob der Debugger im selben privilegierten Prozess läuft. Eine Socket-Anfrage, die eine Ausnahme auslöst, gewährt nicht automatisch Zugriff auf einen Debugger, der an ein anderes Terminal gebunden ist. [Python dokumentiert die Auswertung von Anweisungen im Debugger und den Post-mortem-Modus](https://docs.python.org/3/library/pdb.html); untersuche das Skript statisch, statt den privilegierten Handler bei der Bestandsaufnahme auszulösen.
- Ein festes, über sudo erlaubtes Python-Skript kann außerdem ein Profilfeld aus einer Datenbank oder einem Unix-Socket lesen und an eine Zeichenfolge anhängen, die später zur **Formatzeichenfolge** für `str.format()` wird. [Ersetzungsfelder können Attributen und Mapping-Schlüsseln folgen](https://docs.python.org/3/library/string.html#format-string-syntax), sodass ein angreiferkontrolliertes Feld Objekte untersuchen kann, die an `format()` übergeben werden, und darüber erreichbare Daten offenlegen kann, wenn das Ergebnis ausgegeben oder an einem für den Aufrufer lesbaren Ort gespeichert wird. Prüfe die wirksame sudo-RunAs-Identität, Schreibzugriff auf den konkreten Datensatz, den Datenfluss in die Formatzeichenfolge, die übergebenen Objekte und die Sichtbarkeit der Ausgabe. Dies ist keine automatische Codeausführung; eine literale vertrauenswürdige Formatzeichenfolge mit angreiferkontrollierten *Werten* ist ein anderer Fall. Ein offengelegtes Geheimnis ermöglicht einen Wechsel zum OS-Konto nur, wenn dieses Konto es akzeptiert. Untersuche Skript und Socket-Berechtigungen, ohne den privilegierten Vorgang aufzurufen.
- Ein Python-Wrapper mit root-Rechten kann eine vom Aufrufer ausgewählte URL an `Repo.clone_from` von GitPython übergeben. Aktiviert der Wrapper außerdem Git mit `protocol.ext.allow=always`, kann eine `ext::`-Remote einen externen Helper aufrufen. Prüfe die genauen sudo-Argumente, die Herkunft der URL, die Version des GitPython-Pakets und Vendor-Patches sowie ob der Wrapper unsichere Protokolle ausdrücklich erlaubt. GitPython fügte in Version 3.1.30 eine [standardmäßige Sperre unsicherer Protokolle](https://github.com/gitpython-developers/GitPython/commit/2625ed9) hinzu; die Version der ausführbaren Datei `git` ist davon unabhängig. Eine passive Prüfung sollte nur die Regel und begrenzte Quellcodeausschnitte lesen, ohne den Clone aufzurufen.
- Eine sudo-Berechtigung für einen anderen Benutzer für ein Repository-Klon-CLI kann einen separaten Shell-String-Injection-Pfad eröffnen. Verfolge, ob das vom Aufrufer ausgewählte Repository-Argument Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) oder einen anderen Shell-Befehlsaufbau ohne sichere Argumenttrennung erreicht; Node.js `exec` übergibt seinen Befehlsstring an eine Shell. Prüfe den genauen RunAs-Benutzer, erlaubte Unterbefehle und Argumente, den installierten Wrapper-Code sowie die Eingabevalidierung. Der Name eines Repository-Tools oder eine uneingeschränkte sudo-Regel allein belegt keine Command Injection. Untersuche den Wrapper, ohne bei der Bestandsaufnahme einen privilegierten Clone aufzurufen.
- Ein benutzerdefinierter, root-eigener Wrapper kann sicher erscheinen, weil seine Binärdateien und Skripte nicht beschreibbar sind, während seine Entscheidung, eine privilegierte Aktion auszuführen, von einem Flag, einem lokalen API-Wert oder einem durch einen unprivilegierten Benutzer veränderbaren Dienststatus abhängt. Verfolge jede Bedingung bis zu ihrer Eingabe und den Autorisierungsprüfungen zurück. Untersuche bei der Bestandsaufnahme Konfiguration und Berechtigungen, ohne den Betriebszustand zu ändern; ein `systemd-run`-Aufruf im Wrapper ist nur relevant, wenn die Bedingung beeinflussbar ist.
- Ein über sudo als root erlaubter Backup-Client kann eine vom Aufrufer ausgewählte Konfigurationsdatei akzeptieren (zum Beispiel `npbackup-cli -c`). Prüfe den genauen RunAs-Benutzer und die erlaubten Argumente sowie anschließend, ob der Aufrufer den Konfigurationspfad, Quellpfade für Backups und Optionen für Repository oder Lesen/Wiederherstellen kontrolliert. Ein verschlüsseltes Repository-Geheimnis in einer lesbaren Konfiguration kann für den Client dennoch nutzbar sein; die Regel allein beweist jedoch weder Repository-Zugriff noch die Offenlegung von root-Dateien. Prüfe die Berechtigung, ohne ein Backup auszuführen oder dessen Inhalte auszugeben.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) unterstützt `--password-command`, wodurch ein Programm zum Abrufen eines Repository-Passworts aufgerufen wird. Wenn eine sudo-Regel einem Benutzer mit geringeren Rechten erlaubt, restic als root mit einem frei wählbaren Passwortbefehl und einem ein passwortpflichtiges Unterkommando auszuführen, kann dieser Helper als root laufen. Prüfe die genauen sudo-Argumente und Ausschlüsse; rufe den Helper oder einen Backup-Befehl nicht bloß deshalb auf, um die Bedingung zu überprüfen.
- Eine privilegierte Berechtigung für `restic backup` kann auch eine Dateileseg Grenze überschreiten, wenn das sudo-Argumentmuster dem Aufrufer erlaubt, sowohl die Quelle als auch ein Repository auszuwählen, das er später lesen und entschlüsseln kann. [Argument-Wildcards in sudoers können Leerzeichen und Schrägstriche abdecken](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf); prüfe daher abschließende Wildcards, statt anzunehmen, ein festes Repository-Präfix beschränke die Quelle. [Restic kann lokale und entfernte Repositories verwenden](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), doch ein lokales Repository kann neu geschriebene, nur für root lesbare Objekte enthalten. Prüfe die wirksame sudo-Richtlinie, Backend-Zugriff, Repository-Passwort und Berechtigungen der resultierenden Objekte, bevor du von einer Offenlegung ausgehst. Ein gesicherter SSH-Schlüssel gewährt nur dann Zugriff, wenn das Zielkonto ihn akzeptiert. Führe bei der passiven Prüfung kein Backup aus.
- Ein uneingeschränkter benutzerdefinierter Wartungs- oder Backup-Befehl kann einen Ausgabepfad akzeptieren oder einen eigenen Job-Scheduler bereitstellen. Prüfe bei einem Dateischreibpfad die genaue sudo-Regel und den RunAs-Benutzer sowie, ob der Aufrufer sowohl die Daten als auch das Ziel kontrolliert. Prüfe bei einem geplanten Befehl die Ausführungsidentität des Schedulers, die Befehlseingabe und zusätzliche Passwort- oder Autorisierungsschranken. Der Befehlsname oder `NOPASSWD` allein beweist keinen der beiden Wege. Siehe [Schreiben in root-eigene Dateien](../interesting-files-permissions/write-to-root.md) und [cron und systemd-Timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Ein fester sudo-Befehl kann weiterhin eine vorhersagbare Konfigurationsdatei aus einem gemeinsam beschreibbaren Verzeichnis laden. Verfolge, ob der Aufrufer diese Datei ersetzen kann und ob Quell- und Zielfelder darin einen privilegierten Abruf oder Kopiervorgang steuern. Eine URL zu einer lokalen Datei kann Daten offenlegen, die nur das sudo-RunAs-Konto lesen kann; eine vom Aufrufer kontrollierte Quelle zusammen mit einem geschützten Ziel kann einen Schreibpfad schaffen. Prüfe den Umgang des installierten Programms mit URLs, Prüfungen des Zielpfads, die wirksame sudo-Regel und die Zugänglichkeit der Ausgabe. Ein beschreibbarer Konfigurationspfad unter `/tmp` ist allein nur ein Prüfhinweis; untersuche Binärdatei und Dateimetadaten, ohne den privilegierten Transfer aufzurufen.
- Eine sudo-Regel für `git apply` kann dazu führen, dass das RunAs-Konto Dateien schreibt, die durch einen vom Aufrufer kontrollierten Patch ausgewählt werden. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) ermöglichte es einem präparierten Patch, einen Symlink zu erstellen und anschließend außerhalb des Arbeitsbaums zu schreiben, selbst wenn der Befehl `--unsafe-paths` nicht akzeptierte. Prüfe die wirksame sudo-Argumentregel, die Patchquelle, den Arbeitsverzeichniszugriff des RunAs-Kontos und den installierten Git-Fix oder einen Vendor-Backport. Eine uneingeschränkte Regel, die `--unsafe-paths` zulässt, ist ein separates Risiko durch eine explizite Option; weder eine Git-Version noch die Berechtigung für `git apply` allein belegt, dass eine geschützte Datei geändert werden kann. Wende bei der passiven Bestandsaufnahme keinen nicht vertrauenswürdigen Patch an.
- Eine sudo-Regel mit root-Rechten für `clamscan --debug` kann eine Leseberechtigungsgrenze überschreiten, wenn ein Benutzer mit geringeren Rechten ein DMG-Image bereitstellen kann und der installierte Parser von [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) betroffen ist, wodurch Dateiinhalt über die Debug-Ausgabe offengelegt werden konnte. Prüfe die genau erlaubten Argumente und den Scanpfad, die Kontrolle über die Eingabe, das wirksame RunAs-Konto, den Engine-Fix oder Backport und ob die Ausgabe für den Aufrufer sichtbar ist. Erlaubt eine umfassendere Regel `--file-list`/`-f`, prüfe dieses Verhalten separat; eine auf `--debug <scan-path>` beschränkte Richtlinie lässt diese Option nicht zu. Untersuche Richtlinien und Paketmetadaten, ohne eine präparierte Datei zu scannen oder bei der Bestandsaufnahme geschützte Ausgaben auszugeben.
- Eine sudo-Regel mit root-Rechten, die ein vom Aufrufer ausgewähltes verschlüsseltes Disk-Image öffnet, und eine zweite Regel, die den erzeugten Mapper einhängt, können vom Aufrufer kontrollierte Dateien in den Mount-Namespace des Hosts einbringen. Prüfe beide wirksamen Regeln und Argumente, die Kontrolle über Image und Mapper-Namen, das tatsächliche Einhängeziel sowie Eigentümer und Modus der resultierenden Dateien. Ein set-user-ID-Wechsel erfordert zusätzlich eine zugängliche ausführbare Datei, Einhängeoptionen, die dies zulassen (`nosuid` blockiert es), sowie eine passende Prozess- oder MAC-Richtlinie; allein das Öffnen oder Einhängen eines Images ist nur ein Prüfhinweis. Ein separater Weg über ein vorhandenes Backup setzt dessen tatsächlichen Schlüssel und ein nützliches, lesbares Geheimnis darin voraus. Untersuche Richtlinien und Pfade, ohne bei der passiven Bestandsaufnahme ein Image zu öffnen oder einzuhängen. Siehe das [Handbuch zu cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) und [Einhängeoptionen](https://man7.org/linux/man-pages/man8/mount.8.html).
- Eine sudo-Regel mit root-Rechten für ein Shell- oder Python-Skript sollte auf das Arbeitsverzeichnis geprüft werden, wenn das Skript `./helper` aufruft, ohne zuvor in ein festes Verzeichnis zu wechseln. Eine Python-Liste wie `['./helper']`, die an `subprocess.run` übergeben wird, kann sich genauso abhängig vom Arbeitsverzeichnis des Aufrufers verhalten. Der Aufrufer kann möglicherweise ein beschreibbares Verzeichnis auswählen und darin eine ausführbare Datei mit diesem relativen Namen ablegen; ein absoluter Pfad an anderer Stelle im Skript schützt diesen Aufruf nicht. Prüfe die wirksame Regel, `runchdir` oder andere Richtlinien zum Verzeichniswechsel, Skriptablauf und Erreichbarkeit des Zweigs, beschreibbare und ausführbare Verzeichnisse sowie Mount- und `NOEXEC`-Einschränkungen, bevor du dies als Codeausführung einstufst. Bei einem nicht lesbaren Skript bleibt das Verhalten unbekannt, bis sein Quellcode über einen autorisierten Weg geprüft wurde. Untersuche Skripte statisch, statt den Helper auszuführen. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) dokumentiert Richtlinien für Arbeitsverzeichnisse.
- Ein fester Python-Validator mit root-Rechten kann weiterhin eine vom Aufrufer ausgewählte Datendatei auswerten. [Die Dokumentation von Pythons `eval()` warnt vor nicht vertrauenswürdigen Eingaben](https://docs.python.org/3/library/functions.html#eval): Eine Prüfung des Eingabesuffixes, ein arithmetischer Präfix oder ein Validierungszweig ist keine Sandbox, wenn der verbleibende Ausdruck `eval` erreicht. Prüfe die wirksame sudo-Regel, ob der Aufrufer die konkrete Datei auswählen und kontrollieren kann, die Zweigbedingungen des Parsers und den Aufbau des Ausdrucks sowie die Identität des privilegierten Prozesses, bevor du dies als Ausführungspfad einstufst. Ein `eval`-Vorkommen in einem lesbaren Skript ist allein nur ein Prüfhinweis; untersuche Quellcode und Dateiberechtigungen, ohne den Validator auszuführen oder bei der Bestandsaufnahme einen Testausdruck zu übergeben.
- Ein Ruby-Wrapper mit root-Rechten, der einen relativen YAML-Dateinamen liest, etwa `YAML.load(File.read("dependencies.yml"))`, kann Eingaben aus dem Arbeitsverzeichnis des Aufrufers beziehen, sofern der Wrapper oder die sudo-Richtlinie dieses Verzeichnis nicht festlegt. Prüfe die genauen erlaubten Argumente, Verzeichnis- und Dateiberechtigungen sowie das Verhalten der installierten Psych-Version: Ältere Implementierungen von `YAML.load` konnten beliebige Ruby-Objekte deserialisieren, während neuere Versionen Klassen standardmäßig einschränken. Eine statische Aufrufstelle ist nur ein Prüfhinweis; bestätige, dass die Datei tatsächlich aus einem vom Aufrufer beschreibbaren Verzeichnis stammt und der installierte Loader gefährliche Klassen akzeptiert. Bevorzuge für nicht vertrauenswürdige Eingaben `safe_load` mit einer expliziten, minimalen Klassenfreigabeliste. Siehe die [Ruby-3.0-Psych-Dokumentation](https://docs.ruby-lang.org/en/3.0/Psych.html) und die [Ruby-3.1-Psych-Dokumentation](https://ruby-doc.org/core-3.1.2/Psych.html).

- Eine genaue sudo-Berechtigung für `sudo go run /absolute/file.go` mit root-Rechten sollte auf das Arbeitsverzeichnis geprüft werden, wenn der Go-Quellcode eine relative WASM-Datei liest und nach Auswertung ihres Ergebnisses möglicherweise ein relatives Shellskript ausführt. Prüfe den wirksamen RunAs-Benutzer, Befehlsargumente und Verbote, ein vom Aufrufer beschreibbares aktuelles Verzeichnis, den Datenfluss von WASM zum Zweig und ob dieser Zweig den Helper aufruft. Ein festes sudo-`runchdir`, `os.Chdir` oder [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) kann den Ort der Suche ändern. Ein statisches gemeinsames Vorkommen ist nur ein Kandidat; untersuche den Quellcode, ohne Go, WASM oder den Helper auszuführen.
- `sudoedit` und Argument-Wildcards erfordern genaue Prüfungen der Version und Regel; die [Checkliste](linux-privilege-escalation-checklist.md) enthält das Problem beim Bearbeiten von Dateien mit sudoedit. Prüfe bei einer sudoedit-Berechtigung für einen anderen Benutzer mit einem Wildcard-Pfad die wirksame Einstellung `sudoedit_follow` oder `FOLLOW`, `sudoedit_checkdir`, das aufgelöste Ziel und wer jeden übergeordneten Verzeichniseintrag ersetzen kann. Erstere kann das Folgen eines Symlinks erlauben, während das Deaktivieren Letzterer Prüfungen beschreibbarer Verzeichnisse entfernt; keine der Einstellungen allein belegt einen Schreibzugriff auf eine Datei eines anderen Benutzers. Prüfe die installierte sudo-Richtlinie und die genau passenden Argumente, bevor du diesen Schluss ziehst. Siehe die [Definitionen der sudoers-Optionen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In einer sudoers-Befehlsregel kann eine Argument-Wildcard sowohl Leerzeichen als auch Pfadzeichen abdecken. Eine Regel für einen lesefähigen Befehl mit einem Argument wie `/restricted/*` kann dadurch ein zusätzliches Dateiargument nach einem passenden Präfix zulassen. Prüfe den genauen RunAs-Benutzer, den Befehlspfad, das Argumentmuster und spätere Verbote; ein nachgewiesener Dateizugriff bedeutet nicht automatisch Befehlsausführung. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unterscheidet Argument-Globs von Befehls-Pfad-Globs.
- Ein pfadähnliches Argument-Glob kann auch `../` abdecken. Eine Regel mit root-Rechten wie `node /opt/scripts/*.js` kann beispielsweise eine vom Aufrufer kontrollierte JavaScript-Datei außerhalb von `/opt/scripts` zulassen, wenn der angegebene Pfad weiterhin mit `/opt/scripts/` beginnt und über übergeordnete Verzeichnisselemente aufgelöst wird. Dies ist ein **Argument**-Glob; für das Befehls-Pfad-Glob der Node-Binärdatei gelten andere Regeln zur Abdeckung von Schrägstrichen. Prüfe die wirksame Regel, spätere Verbote, Pfadauflösung, Kontrolle über die Zieldatei und etwaige sudoers-Regular-Expression- oder Digest-Einschränkungen, bevor du auf Codeausführung schließt. Siehe die [sudoers-Wildcardregeln](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) und die [Node-Befehlszeilendokumentation](https://nodejs.org/api/cli.html).
- Archivierungsprogramme und andere Hilfsprogramme können Ausführungshooks haben. Prüfe die genau erlaubten Argumente mit [GTFOBins](https://gtfobins.github.io/), statt anzunehmen, dass nur Shells oder Interpreter Befehle ausführen.
- Eine uneingeschränkte sudo-Regel für `qpdf` mit root-Rechten kann eine privilegierte Datei über PDF-Anhänge offenlegen: qpdf 10.2 und neuere Versionen unterstützen `--empty` und `--add-attachment file ... --` mit einer Ausgabe-PDF. Wenn der privilegierte Prozess die ausgewählte Quelle lesen und die PDF in einen für den Aufrufer zugänglichen Pfad schreiben kann, kann diese Ausgabe die Quelldaten enthalten. Prüfe die wirksamen sudo-Argumente und Ausschlüsse, die qpdf-Version, den Zugriff auf die Quelle und den Ausgabepfad, bevor du eine mögliche Offenlegung annimmst. Das Lesen eines root-SSH-Schlüssels ist nur dann für eine Anmeldung nützlich, wenn der Schlüssel gültig ist und SSH-Authentifizierung für root erlaubt ist. Siehe die [qpdf-Optionen für Anhänge](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Die Wiederverwendung von sudo-Zeitstempeln hängt von der Cache-Richtlinie, dem besitzenden Benutzer, Terminal/Sitzung und den Berechtigungen ab. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) behandelt die Prüfungen.
- `doas` hat eigene Regeln und Konfiguration. Prüfe erlaubte Befehle und beschreibbare Konfigurationspfade wie im [doas-Abschnitt](../linux-basics/linux-privilege-escalation/README.md#doas) beschrieben.

### Über sudo ausgeführte Build- und Paketwerkzeuge

Eine uneingeschränkte sudo-Berechtigung für `forge` von Foundry kann relevant sein, selbst wenn die RunAs-Identität ein anderer Nicht-root-Benutzer ist. Compiler-Optionen wie `--use` können eine lokale ausführbare Datei auswählen, und `forge flatten -o` legt eine Ausgabedatei fest. Prüfe die installierte Forge-Version, die genauen sudo-Argumente, zugängliche Projekt- und Compilerpfade, Ausgabeberechtigungen und die wirksame Umgebung, bevor du die Berechtigung als ausnutzbar einstufst. Ein relativer Helper, der über `PATH` gefunden wird, ist ein von Version und Umgebung abhängiger Weg und keine Eigenschaft, die für jeden Forge-Build angenommen werden sollte.<sup>[[23]](#references)[[24]](#references)</sup>

Eine uneingeschränkte sudo-Berechtigung für `pacman` mit root-Rechten erlaubt mehr als Paketabfragen: `-U` akzeptiert ein lokales Paket, Pakete können Installationsskripte enthalten und `--hookdir` wählt ein anderes Hook-Verzeichnis. Prüfe die wirksame sudo-Regel, Argumenteinschränkungen und Ausschlüsse, bevor du testest; bei der passiven Bestandsaufnahme muss weder ein Paket installiert noch ein Hook ausgeführt werden.<sup>[[25]](#references)[[26]](#references)</sup>

Ein fester sudo-Shell-Wrapper kann auch eine namentlich angegebene npm-Abhängigkeit installieren und anschließend eine Node-Anwendung starten. Prüfe dessen genaue RunAs-Regel, ob das Paket bereits installiert ist, das wirksame `HOME` und die npm-`userconfig`, Projektkonfiguration oder Befehlszeilenüberschreibungen sowie ob ein Benutzer mit geringeren Rechten die Registry oder das für diesen Namen gelieferte Paket kontrolliert. [npm dokumentiert die Suche nach `.npmrc` pro Benutzer und Projekt](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); das Verhalten von sudo bezüglich `HOME` hängt von der installierten Richtlinie und Distribution ab, sodass eine beschreibbare `.npmrc` des Benutzers vom privilegierten npm-Prozess gelesen werden kann oder auch nicht. Wird das neu installierte Paket von der privilegierten Anwendung importiert, kann dessen Modulcode unter der Identität der Anwendung laufen. Installationsskripte sind ein separater, versions- und konfigurationsabhängiger Weg; [npm dokumentiert deren Lebenszyklus und Benutzerbehandlung](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ein `.npmrc`-Pfad oder eine `npm install`-Zeile allein ist nur ein Prüfhinweis. Untersuche Regel, kurzen Wrapper, Konfigurationspfade und Herkunft des Pakets, ohne bei der passiven Bestandsaufnahme etwas zu installieren oder die Anwendung zu starten.

Eine Berechtigung mit root-Rechten für `pip` oder `pip3 download` ist ebenfalls ein Hinweis, Build-Verhalten von Paketen zu prüfen, wenn die Argumente dem Aufrufer erlauben, eine nicht vertrauenswürdige Quell-Distribution auszuwählen, selbst wenn das URL-Muster auf einen lokalen Dienst und das Suffix `.tar.gz` beschränkt ist. `pip download` akzeptiert Archiv-URLs und löst Paketmetadaten auf; das Vorbereiten einer sdist kann deren Build-Backend oder alten `setup.py`-Code ausführen, bevor das Archiv lediglich gespeichert wird. Prüfe die genauen sudo-RunAs- und Argumentregeln, ob der Aufrufer das ausgewählte Archiv veröffentlichen oder ersetzen kann und ob diese pip-Version dessen Metadaten tatsächlich vorbereitet. Ein festes, vertrauenswürdiges Archiv oder Wheel belegt diesen Weg nicht. Rufe bei der passiven Bestandsaufnahme kein nicht vertrauenswürdiges Paket ab und baue es nicht. Siehe pips [download-Befehl](https://pip.pypa.io/en/stable/cli/pip_download/), die [Build-System-Schnittstelle](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Eine sudo-Regel, die `pip install` mit einem vom Aufrufer ausgewählten lokalen Projektpfad erlaubt, schafft eine direktere Build-Vertrauensgrenze. [pip akzeptiert lokale Projektverzeichnisse](https://pip.pypa.io/en/stable/topics/local-project-installs/) und ruft deren Build-System auf; das [Build-Backend führt projektkontrollierte Build-Hooks aus](https://pip.pypa.io/en/stable/reference/build-system/). Prüfe die wirksame RunAs-Identität, genaue Argumenteinschränkungen und Verbote, die Kontrolle über das ausgewählte Projekt sowie das Verhalten der installierten pip- und Backend-Version, bevor du die Regel als privilegierte Codeausführung einstufst. Ein festes, vertrauenswürdiges Projekt oder eine Regel, die vom Aufrufer ausgewählte Pfade ausschließt, belegt diesen Weg nicht. Prüfe Regel und Projektmetadaten, ohne bei der passiven Bestandsaufnahme ein Paket zu installieren.

Eine uneingeschränkte sudo-Berechtigung mit root-Rechten für `easy_install` ist ein ähnlicher Hinweis auf veraltetes Paket-Build-Verhalten. [Setuptools dokumentiert](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), dass Easy Install ein lokales Projektverzeichnis akzeptiert und Quell-Distributionen baut; ein vom Aufrufer kontrolliertes Projekt kann während dieses Builds unter der sudo-Identität dessen `setup.py` ausführen. Prüfe das wirksame RunAs-Konto, genaue Befehls- und Argumenteinschränkungen (einschließlich späterer Verbote), die Kontrolle über das ausgewählte Projekt und das Verhalten des installierten Werkzeugs. Ein festes, vertrauenswürdiges Projekt oder eine Richtlinie, die keine vom Aufrufer ausgewählte Quelle zulässt, belegt diesen Weg nicht. Untersuche Regel und Projektmetadaten, ohne bei der Bestandsaufnahme ein Paket zu installieren.

Ein über sudo erlaubter Python-Wrapper, der `setuptools.package_index.PackageIndex.download` mit einer vom Aufrufer ausgewählten URL verwendet, ist ein anderer Prüfungsfall als `pip download`: [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) beschreibt, wie in betroffenen Versionen vor 78.1.1 ein aus der URL abgeleiteter Dateiname aus dem vorgesehenen Download-Verzeichnis ausbrechen und mit den Berechtigungen des Prozesses schreiben konnte. Prüfe die wirksame sudo-RunAs- und Argumentregel, ob der Wrapper die URL des Aufrufers an genau diese API übergibt, den installierten Build oder einen Vendor-Backport sowie den aufgelösten Zielpfad. Eine Versionszeichenfolge oder ein beschreibbares Download-Verzeichnis allein belegt keinen beliebigen Schreibzugriff. Untersuche den kurzen Wrapper und Paketmetadaten, ohne bei der Bestandsaufnahme die URL abzurufen oder eine Datei zu schreiben.

Ein über sudo erlaubter Build-Wrapper, der eine vom Aufrufer ausgewählte `.spec`-Datei an PyInstaller übergibt, erfordert dieselbe Prüfung der Vertrauensgrenze. Eine PyInstaller-Spec-Datei ist ausführbares Python, das während des **Builds** ausgewertet wird; ihre `datas`-Einträge können für die Build-Identität lesbare Dateien in ein Artefakt aufnehmen. Prüfe den genauen RunAs-Benutzer, sudo-Argument- und Verbotsregeln, Pfad- und Zweigbehandlung im Wrapper, die Kontrolle über die ausgewählte Spec-Datei sowie den Zugriff auf das resultierende Artefakt. Allein die Erlaubnis einer `.py`-Eingabe oder eine installierte PyInstaller-Version belegt weder die Kontrolle über eine Spec-Datei noch privilegierte Ausführung. Bei der passiven Prüfung sollten nur ein begrenzter Wrapper-Dateiinhalt und Metadaten gelesen werden; führe keinen Build aus. Siehe die [Dokumentation zu PyInstaller-Spec-Dateien](https://pyinstaller.org/en/stable/spec-files.html).

### Über sudo ausgeführte Preset- und Plugin-Lader

Python-Werkzeuge, die ein vom Aufrufer ausgewähltes Preset- oder Plugin-Verzeichnis akzeptieren, können Code mit den durch sudo gewährten Berechtigungen importieren. BBOT akzeptiert zum Beispiel ein Preset mit `-p`; seine [Dokumentation zu benutzerdefinierten Modulen](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) beschreibt `module_dirs`-Einträge, mit denen zusätzliche Python-Modulverzeichnisse ausgewählt werden. Erlaubt die wirksame sudo-Regel ein vom Aufrufer ausgewähltes Preset und kontrolliert der Aufrufer ein Modul im ausgewählten Verzeichnis, kann der Import Code als privilegierter Benutzer ausführen, möglicherweise noch bevor das Werkzeug ein ungültiges Modul zurückweist. Prüfe installierte Version, genaue sudo-RunAs- und Argumentregeln sowie Eigentümer der Preset- und Modulpfade, ohne das Modul bei der Bestandsaufnahme zu laden.

### Über sudo ausgeführtes Backdrop-CLI

[Bee](https://github.com/backdrop-contrib/bee) ist ein PHP-Befehlszeilenwerkzeug für Backdrop CMS. Seine Befehle `eval` (`php-eval`) und `php-script` können vom Aufrufer bereitgestelltes PHP ausführen. Eine sudo-Regel, die das Bee-Programm als root mit uneingeschränkten Argumenten erlaubt, kann daher root-Codeausführung ermöglichen, wenn Bee eine Backdrop-Installation initialisieren kann. Führe es aus dem Site-Verzeichnis aus oder wähle eine Site mit der globalen Option `--root=<directory>` aus; Bee oder eine Backdrop-Datei `settings.php` zu finden, beweist weder die sudo-Berechtigung noch eine nutzbare Site oder eine erfolgreiche Initialisierung. Prüfe vor einem Test die wirksame sudo-Regel, etwaige Befehlsausschlüsse, die Identität der ausführbaren Datei und den Zugriff auf die Site. Untersuche bei der passiven Bestandsaufnahme Regel und Dateipfade, ohne Bee aufzurufen. Siehe das [Bee-Befehls-Changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) zu den PHP-Befehlen.

### Über sudo ausgeführte Terminalserver

`mosh-server` startet einen interaktiven Terminalserver als aufrufender Benutzer. Er wählt einen hohen UDP-Port und einen Sitzungsschlüssel, meldet beide dem Aufrufer und startet normalerweise beim Verbindungsaufbau durch einen Client die Login-Shell dieses Benutzers. Eine uneingeschränkte sudo-Berechtigung für `mosh-server` mit root-Rechten ist daher ein Kandidat für eine Shell-Prüfung, obwohl sich der Serverbefehl selbst abkoppelt. Prüfe die wirksame RunAs-Identität, erlaubte Argumente und Ausschlüsse, die installierte Binärdatei, die Shell, die Verfügbarkeit eines Clients und den UDP-Zugriff. Untersuche bei der passiven Bestandsaufnahme die sudo-Regel, ohne einen Server zu starten oder einen aktiven Sitzungsschlüssel auszugeben. Siehe das [Mosh-Server-Handbuch](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) und die [upstream-Designnotizen](https://github.com/mobile-shell/mosh#how-it-works).

### Privilegierte Backup-Wrapper, die eine Taskdatei des Aufrufers umschreiben

Ein als root ausgeführter Shell-Wrapper kann eine vom Aufrufer ausgewählte Taskdatei akzeptieren, `../` aus Quellpfaden entfernen, prüfen, ob jedes Ergebnis mit einem erlaubten Verzeichnis beginnt, die Taskdatei umschreiben und anschließend deren *Pfadnamen* an ein Backup-Programm übergeben. Prüfe den transformierten Pfad nach vollständiger kanonischer Auflösung: Ein einzelner String-Ersetzungsschritt kann eine neue Traversalsequenz offenlegen, die eine lexikalische Präfixprüfung akzeptiert. Prüfe außerdem, ob das Backup-Programm die transformierten Daten aus dem Arbeitsspeicher liest oder die Datei erneut öffnet. Öffnet es sie erneut, kann eine fehlgeschlagene Umschreibung die ursprüngliche Eingabe unverändert lassen.

Unter Linux kann `fs.protected_regular` einen Schreibzugriff mit `O_CREAT` auf die reguläre Datei eines anderen Benutzers in einem Sticky-Verzeichnis verweigern, auf das alle Schreibzugriff haben. Diese Verweigerung ist ein Schutzmechanismus; ein Shell-Wrapper, der den Schreibfehler ignoriert, kann dennoch mit der ursprünglichen Taskdatei fortfahren. Prüfe die Einstellung, Eigentümer der Datei und des Verzeichnisses sowie ob der Wrapper bei einem Fehler abbricht. Der Pfad ist nur dann ein Kandidat für die Offenlegung von Dateien, wenn die wirksame sudo-Regel den Wrapper als privilegierten Benutzer erlaubt, der Aufrufer die Taskeingabe und ein lesbares Backup-Ziel kontrolliert und das Backup-Werkzeug geschützte Quellen tatsächlich einbezieht. Untersuche diese Bedingungen, ohne bei der Bestandsaufnahme das Backup auszuführen.

### Argument-Wildcards bei privilegierten Paketwerkzeugen

In einer sudo-Regel für `tcpdump` kann ein `*` im **Argumentmuster** Leerzeichen und Schrägstriche abdecken, sodass eine pfadähnliche Einschränkung weiterhin zusätzlichen Optionstext zulassen kann. Das unterscheidet sich von der Shell-Erweiterung von Dateinamen. Prüfe die vollständige RunAs-Regel und etwaige spätere Verbote. Können Optionen eingeschleust werden, bestimmen der erlaubte Aufruf und die Semantik der installierten [`tcpdump`-Optionen](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), ob `-F`, `-V`, `-r`, `-w` oder `-Z` eine brauchbare Lese-/Schreibmöglichkeit bietet. `-V` liest eine Liste von Capture-Dateinamen, nicht beliebige Dateien als allgemeine Datei-Dumps. AppArmor oder eine andere MAC-Richtlinie kann Dateizugriff verhindern, selbst wenn sudo den Befehl erlaubt; eine Profildatei auf der Festplatte beweist nicht, dass sie geladen und wirksam ist. Prüfe Autorisierung und Richtlinien passiv, bevor du zu einem Schluss kommst. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) beschreibt den Unterschied zwischen den Wildcard-Typen.

Eine sudo-Regel mit root-Rechten, die nur die ausführbare Datei `tcpdump` nennt und keine Argumente beschränkt, sollte ebenfalls geprüft werden. Das [tcpdump-Handbuch](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) dokumentiert `-z` als Befehl nach dem Rotieren, wenn `-C` oder `-G` eine gespeicherte Aufnahme rotiert; `-Z` oder eine Build-Voreinstellung kann die Berechtigungen vor dem Aufruf dieses Befehls reduzieren. Prüfe die wirksame sudo-Regel, den installierten Build, das Verhalten beim Absenken der Berechtigungen und ob eine Rotation erfolgen kann, bevor du die Regel als Rechteausweitungsweg einstufst. Eine hervorgehobene Regel ist ein Kandidat, kein Nachweis, dass ein Befehl als root ausgeführt werden kann.

### Über sudo ausgeführte Nmap-Wrapper

Wenn ein über sudo erlaubter `nmap`-Pfad ein Shell-Wrapper ist, untersuche den genau erlaubten Pfad und alle weitergereichten Optionen. Das Sperren der vertrauten Schreibweise `--script` verhindert nicht unbedingt das Laden von NSE-Code: Nmaps [`--datadir`](https://nmap.org/book/man-misc-options.html) wählt Datendateien aus, und NSE [lädt `nse_main.lua`](https://nmap.org/book/nse-implementation.html) aus dem ausgewählten Datenverzeichnis, wenn Scripting aktiviert ist. Einige installierte Builds akzeptieren außerdem alternative Schreibweisen langer Optionen; vergleiche Einschränkungen daher mit dem tatsächlichen Parser dieser Binärdatei. [`--excludefile`](https://nmap.org/book/man-target-specification.html) bietet eine separate Angriffsfläche zum Lesen von Dateien; Parserfehler können Text offenlegen. Prüfe die wirksame sudo-Regel, Wrapper-Logik, Nmap-Version, Kontrolle über Verzeichnisse und MAC-Richtlinie, ohne bei der Bestandsaufnahme Scans auszuführen.

### Über sudo ausgeführte Mercurial-Pull-Hooks

Ein festes Quellverzeichnis in `sudo hg pull /fixed/source` lässt das **Ziel**-Repository weiterhin durch das aktuelle Arbeitsverzeichnis bestimmen, sofern der Befehl es nicht mit `-R` festlegt. Ein vom Aufrufer kontrolliertes Ziel-Repository kann Hooks in `.hg/hgrc` definieren; ein Hook kann als sudo-RunAs-Benutzer ausgeführt werden. [Mercurial ignoriert Repository-Konfiguration, deren Eigentümer ein nicht vertrauenswürdiger Benutzer oder eine nicht vertrauenswürdige Gruppe ist](https://mercurial-scm.org/help/topics/config); prüfe daher vertrauenswürdige Benutzer/Gruppen des RunAs-Kontos und das genaue Arbeitsverzeichnis, bevor du dies als Codeausführung einstufst. Für eine passive Prüfung reicht es, Richtlinie und Konfiguration zu lesen; führe keinen Pull oder Hook aus.

### Über sudo ausgeführte Git-Pull-Hooks

Prüfe bei einer genauen sudo-Berechtigung mit root-Rechten für `sudo git pull` auch das **Ziel**-Repository, das durch das Arbeitsverzeichnis ausgewählt wird. Ein dem Aufrufer gehörendes Repository kann einen ausführbaren `post-merge`-Hook enthalten, der mit der Identität des Git-Prozesses läuft, wenn ein Pull tatsächlich eine erfolgreiche Zusammenführung ausführt; [Git dokumentiert diesen Hook](https://git-scm.com/docs/githooks) und das [Merge- oder Rebase-Verhalten von pull](https://git-scm.com/docs/git-pull). Prüfe die wirksame sudo-Regel und das aktuelle Arbeitsverzeichnis, den aktiven Hook-Pfad und seine Berechtigungen sowie ob ein Merge mit neuen Commits erreichbar ist. Ein fehlgeschlagener, wirkungsloser oder ausschließlich Rebase ausführender Pull belegt diesen Hook-Pfad nicht. Untersuche Richtlinie und Repository-Metadaten, ohne den privilegierten Pull auszuführen.

### Über sudo ausgeführte rsync-Archivkopien

Bei `sudo rsync -a ... /writable/source/* /fixed/destination/` kann ein `*` im **sudoers-Argumentmuster** Leerzeichen abdecken und ein zusätzliches Argument zwischen Quelle und Ziel zulassen. Das ist von der Shell-Erweiterung von Dateinamen zu unterscheiden. Kann der Aufrufer die Quelle befüllen und ist das Ziel für den privilegierten rsync-Prozess beschreibbar, kann [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privilegierten Eigentümer anfordern, während der Archivmodus Berechtigungsbits erhält, sodass möglicherweise eine SetUID-Datei mit entsprechendem Eigentümer entsteht. Prüfe die genauen [sudoers-Wildcardregeln](https://man7.org/linux/man-pages/man5/sudoers.5.html), die rsync-Version, spätere Verbote, das Dateisystem-Flag `nosuid` und die MAC-Richtlinie. Eine passende Regel ist ein Prüfhinweis, kein Nachweis einer erfolgreichen Rechteausweitung.

### Über sudo ausgeführter Export von Paketfilterregeln

Eine uneingeschränkte sudo-Berechtigung mit root-Rechten für `iptables` und `iptables-save` (oder das entsprechende Paar `ip6tables`) sollte auf Dateischreibzugriffe geprüft werden. Der `comment`-Match akzeptiert vom Aufrufer gewählten Regeltext, während `iptables-save -f` den serialisierten Regelsatz in einen ausgewählten Pfad schreibt.<sup>[[20]](#references)[[21]](#references)</sup> Eine brauchbare Nutzlast hängt davon ab, wie das installierte Backend Kommentare serialisiert und ob die Zieldatei andere Zeilen im Export akzeptiert; `iptables-save` allein ermöglicht keinen beliebigen Inhalt. Prüfe die genaue sudo-RunAs-Identität, Argumente und Ausschlüsse, die verfügbare Match-Erweiterung, das Backend und die Zielberechtigungen. Untersuche bei der Bestandsaufnahme die Berechtigung, ohne Firewall-Regeln zu ändern oder eine Datei zu schreiben.

### Privilegiertes Below-Protokollverzeichnis

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) betraf Below-Versionen vor 0.9.0, die ein weltweit beschreibbares Verzeichnis `/var/log/below` anlegten. Läuft ein Dienst oder ein über sudo erlaubter Befehl mit einem betroffenen Build als root, kann ein Benutzer mit Schreib- und Durchsuchungsrechten auf ein Sticky-freies Protokollverzeichnis möglicherweise einen Protokolleintrag durch einen Symlink ersetzen, bevor der privilegierte Prozess ihn öffnet. Prüfe den Patch-Status des installierten Pakets, den genauen privilegierten Ausführungspfad, den wirksamen Verzeichniszugriff, Sticky-Bit und ACLs sowie die Metadaten von `/var/log/below/error_root.log`. Ein weltweit beschreibbarer Pfad oder eine sudo-Regel allein belegt nicht die vollständige Kette. Ein Sticky-Verzeichnis oder ein Vendor-Backport ändert die Bewertung. Bei der passiven Bestandsaufnahme nur Metadaten prüfen; es ist nicht nötig, einen Link anzulegen oder das privilegierte Programm auszuführen.

### Privilegierte Erfassung von Support-Paketen aus beschreibbaren Eingaben

Ein über `sudo` erlaubtes Support-Profilskript kann feste Protokollpfade als root lesen und deren Inhalte in ein Profilarchiv kopieren. Prüfe das tatsächliche Skript auf Dateizugriffe und anschließend, ob der Aufrufer einen Quellpfad oder einen übergeordneten Verzeichniseintrag durch einen Symlink ersetzen kann. Folgt der privilegierte Lesezugriff diesem Link und ist das resultierende Archiv für den Aufrufer lesbar, kann eine geschützte Datei offengelegt werden. Sudo-Berechtigung, beschreibbarer Quellpfad, privilegierter Lesezugriff und lesbare Ausgabe müssen alle gegeben sein; ein beschreibbares Protokoll oder ein Profil-Dateiname allein reicht nicht. Untersuche die wirksamen Berechtigungen und Link-Metadaten, ohne Dateien zu ersetzen oder bei der Bestandsaufnahme ein Profil zu erstellen. Die [Nagios-XI-Supporthinweise](https://support.nagios.com/forum/viewtopic.php?t=62758) dokumentieren das als root ausgeführte Profilerstellungsskript und das Ausgabe-Archiv und zeigen, warum solche Pakete eingeschränkte Eingaben und Ausgabezugriffe erfordern.

### Als root ausgeführte Python-Archivwiederherstellungsskripte

Auch eine eng begrenzte sudo-Regel für ein Python-Wiederherstellungsskript muss auf die Archiveingabe geprüft werden. Kann der Aufrufer das Archiv auswählen oder ersetzen und extrahiert das Skript es als root mit `tarfile.extractall(filter="data")`, prüfe vor dem Vertrauen in den Filter die Sicherheitsupdates des Interpreters. CPython behob mehrere Umgehungen des Symlink- und Hardlink-Filters, darunter CVE-2025-4517, in den Versionen 3.9.23, 3.10.18, 3.11.13, 3.12.11 und 3.13.4. Distributions-Backports können auch eine ältere Version korrigieren; die angezeigte Interpreter-Version allein beweist daher keine Anfälligkeit.<sup>[[16]](#references)[[17]](#references)</sup>

Lies bei einer passiven Prüfung den genauen sudo-Befehl und das Skript, verfolge, welches Argument das Archiv auswählt, und prüfe, ob der aktuelle Benutzer das Archiv oder dessen übergeordnetes Verzeichnis beschreiben kann. Prüfe den installierten Vendor-Patch und das Extraktionsziel separat; `filter="data"` macht nicht jedes nicht vertrauenswürdige Archiv sicher.<sup>[[16]](#references)[[17]](#references)</sup>

### Über sudo ausgeführte Machine-Learning-Modelllader

Eine sudo-Regel, die eine vom Aufrufer ausgewählte Datei `.pt`, `.pth` oder `.ckpt` erlaubt, sollte geprüft werden, wenn ein privilegiertes Skript diese Datei an [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` oder einen anderen pickle-basierten Loader übergibt. Prüfe die wirksame RunAs-Regel, ob der Aufrufer das ausgewählte Modell erstellen oder ersetzen kann und wie das Argument durch einen Shell-Wrapper zum Python-Helper gelangt. Die Erweiterung `.pth` bezeichnet auch nicht verwandte Python-Site-Konfigurationsdateien und ist allein kein Nachweis für das Laden eines Modells. Ein Archiv-Scan oder statischer Pickle-Scan belegt nicht, dass das spätere Laden sicher ist; prüfe das [versionsabhängige Verhalten von `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) und jede Zulassungsliste. Siehe die Hinweise zu [ML-Pickle und Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Bei der passiven Bestandsaufnahme das Modell niemals laden oder entpacken.

### Ausdrucksauswertung gespeicherter Eingaben mit sudo

Ein festes Python-Skript, das über sudo als root ausgeführt wird, kann weiterhin Text auswerten, den ein Benutzer mit geringeren Rechten in einer Anwendungsdatenbank speichern kann. In TensorFlow wählt ein Aufruf von `preprocess_input_exprs_arg_string(value, safe=False)` einen `eval`-Pfad aus; der [Hinweis von TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) beschreibt den unsicheren Parser und eine Korrektur für dessen Kommandozeilen-Aufrufer. Ein expliziter Aufruf mit `safe=False` in einer Anwendung muss separat geprüft werden, selbst wenn dieser Kommandozeilen-Aufrufer korrigiert wurde. Prüfe die wirksame sudo-Regel, wer die konkrete Eingabezeile ändern kann, ob Filterung oder Bewertung diese Zeile bis zum Aufruf durchlassen und wie sich die installierte Funktion verhält. Eine TensorFlow-Version, eine sudo-Berechtigung oder eine fest codierte Modelldatei allein belegt die Kette nicht. Untersuche Skript und Datenfluss passiv; führe den privilegierten Helper nicht aus und übermittle bei der Bestandsaufnahme keine Testausdrücke.

### Über sudo erlaubte needrestart-Konfiguration

`needrestart -c` lädt eine vom Aufrufer ausgewählte Perl-Konfigurationsdatei und wertet deren Inhalt aus. Wenn `sudo -l` `needrestart` als root mit Argumenten erlaubt, die `-c` zulassen, und der Aufrufer eine lesbare Konfigurationsdatei an einem beschreibbaren Ort auswählen kann, kann diese Berechtigung zu root-Codeausführung führen. Prüfe die genaue sudo-RunAs- und Argumentregel; eine Regel mit fester Argumentliste kann diesen Weg blockieren. Dies ist von den Schwachstellen beim Scannen von Interpretern durch needrestart getrennt: Das Aktualisieren des Pakets oder Deaktivieren von `interpscan` macht eine uneingeschränkte root-Berechtigung für `-c` nicht sicher.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Über sudo ausgeführte Python-Imports unter einem anderen Konto

Ein fester Python-Einstiegspunkt kann weiterhin ein Modul importieren, das der Aufrufer bearbeiten oder ersetzen kann, auch wenn sudo das Skript als **Nicht-root-Dienstbenutzer** ausführt. Prüfe bei einem literalen `from utils import status` sowohl `utils/__init__.py` und `utils/status.py` als auch die Berechtigungen des Paketverzeichnisses. Prüfe den Importpfad des Skripts, die genau erlaubten sudo-Argumente und ob die betreffende Aktion diesen Import erreicht, bevor du die beschreibbare Datei als Ausführungspfad einstufst. Untersuche Dateien und Berechtigungen, ohne das Skript bei der Bestandsaufnahme zu importieren oder auszuführen.<sup>[[2]](#references)[[3]](#references)</sup>

Eine genaue sudo-Regel für `python3 /absolute/script.py` benötigt lediglich ein lesbares Skript; die Datei muss weder ausführbar sein noch einen Shebang haben. Prüfe auch **fehlende** lokale Module: Importiert das Skript ein Modul, dessen Dateiname in einem vom Aufrufer beschreibbaren Skriptverzeichnis angelegt werden kann, lädt Python diese Datei möglicherweise unter der RunAs-Identität. Prüfe die wirksame sudo-Regel, den tatsächlichen [Modulsuchpfad](https://docs.python.org/3/library/sys_path_init.html) des Interpreters, ob das Modul eingebaut oder eingefroren ist und ob der Import erreicht wird. Eine direkte sudo-Regel für das Skript stellt andere Anforderungen an Ausführungsbit und Shebang. Bei einem separaten Wrapper, der vom Aufrufer bereitgestellte Tokens nach `sudo -u account` anhängt, muss auch der Argumentfluss geprüft werden: Ein weiteres `-u` in diesen Tokens ist nur dann relevant, wenn die aufgerufene sudo-Richtlinie die resultierende Identität erlaubt. Statische Strings allein beweisen keinen der beiden Wege.

### Über sudo ausgeführtes Apache mit aufruferkontrollierter Konfiguration

Wenn eine sudo-Regel einen privilegierten Aufruf von `apachectl`, `apache2ctl` oder `httpd` mit einer vom Aufrufer kontrollierten Konfigurationsdatei über `-f` erlaubt, prüfe die Berechtigungen dieser Datei und ihres übergeordneten Verzeichnisses. Apaches [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)-Direktive nimmt einen Modulnamen gefolgt vom **Moduldateinamen** entgegen; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) lädt ebenfalls eine Datei. [`Include` und `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) können die Konfiguration erweitern oder Dateiinhalte über Fehlermeldungen offenlegen. Ein benutzerdefinierter Wrapper kann diese Pfade validieren, Berechtigungen reduzieren oder Argumente beschränken; eine beschreibbare Konfiguration ist daher ein Prüfhinweis und kein Nachweis von Codeausführung. Prüfe Pfadkanonisierung, Symlinks und Direktiven-Parsing, bevor du zu einem Schluss kommst.

### Über sudo ausgeführtes nginx mit aufruferkontrollierter Konfiguration

Eine uneingeschränkte sudo-Regel für `nginx` mit root-Rechten kann erlauben, [`-c` zur Auswahl einer anderen Konfiguration zu verwenden](https://nginx.org/en/docs/switches.html). Prüfe die genauen sudo-Argumente und Ausschlüsse, ob der Aufrufer die Konfiguration bereitstellen kann und ob Master oder Worker dadurch Zugriff auf geschützte Pfade behalten. Ein ausgewähltes `root` zusammen mit `autoindex` kann Dateien über einen neuen Listener offenlegen; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kann einen privilegierten Schreibpfad bieten, doch das DAV-Modul ist standardmäßig nicht eingebaut. Prüfe daher dessen Vorhandensein, Listener-Erreichbarkeit, Dateiberechtigungen und Verhalten bei temporären Dateien. Die [`error_log`-Direktive](https://nginx.org/en/docs/ngx_core_module.html#error_log) kann ebenfalls auf eine ausgewählte Datei zeigen; das Schreiben von Protokollen in eine sensible Konfigurationsdatei wie `/etc/ld.so.preload` wird erst dann zu einem Rechteausweitungsweg, wenn ein wirksamer privilegierter Schreibzugriff und ein kontrollierbarer Protokolleintrag vorliegen. Die Hervorhebung der ausführbaren Datei in `sudo -l` ist ein Prüfhinweis, kein Nachweis, dass einer dieser Wege funktioniert. Bei der passiven Bestandsaufnahme nginx weder starten noch umkonfigurieren.

### Mustervergleich in privilegierten Bash-Eingabeaufforderungen

Liest ein über sudo erlaubtes Bash-Skript einen Wert vom Aufrufer ein und prüft ihn mit `[[ "$expected" == $entered ]]`, interpretiert Bash den nicht in Anführungszeichen gesetzten rechten Operanden als Muster. Ein Platzhalter kann den Vergleich daher erfüllen, ohne den erwarteten Wert zu kennen. Mit Anführungszeichen um den Operanden (`[[ "$expected" == "$entered" ]]`) wird ein literaler Zeichenfolgenvergleich erzwungen. Prüfe die genaue sudo-Regel, ob die Eingabeaufforderung erreichbar ist und was das Skript nach dem Vergleich tut; die Syntax allein belegt keinen ausnutzbaren Pfad. Gib den erwarteten Wert bei der Bestandsaufnahme nicht aus. Siehe die [Referenz zu bedingten Konstrukten in Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Über sudo ausgeführte Helper, die Dateien herunterladen und ausführen

Eine uneingeschränkte sudo-Berechtigung mit root-Rechten für einen benutzerdefinierten Helper sollte auf den Datenfluss geprüft werden, wenn er eine vom Aufrufer ausgewählte URL akzeptiert, die Antwort auf der Festplatte speichert und die Datei später mit einem Interpreter oder einer Shell aufruft. [Sudoers erlaubt beliebige Argumente, wenn ein Befehlseintrag keine auflistet](https://man7.org/linux/man-pages/man5/sudoers.5.html); ein fester Pfad zur ausführbaren Datei schränkt nicht ein, was deren Argumente auswählen können. Prüfe die tatsächliche URL-Validierung, den Ausgabepfad, den Erfolgszweig und die anschließende Ausführung im installierten Helper. Ein passender libcurl-Import oder ein druckbarer String allein belegt diese Kette nicht.

Selbst ein fester Ausgabebasisname kann zwischen Schreiben und Ausführen ersetzt werden, wenn der Helper einen **relativen Pfad in einem vom Aufrufer kontrollierten Arbeitsverzeichnis** verwendet. Das Umbenennen oder Ersetzen einer root-eigenen Datei hängt von Schreib- und Durchsuchungsrechten auf dem Verzeichnis sowie etwaigen Sticky-Bit-Einschränkungen ab, nicht nur vom Modus der Datei; siehe [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Prüfe, ob der Helper den Pfad später erneut öffnet oder den bereits geöffneten Dateideskriptor verwendet und ob er vor dem Schreiben in ein vertrauenswürdiges Verzeichnis wechselt. Untersuche sudo-Richtlinie, Helper und Verzeichnismetadaten passiv; rufe bei der Bestandsaufnahme weder den privilegierten Download noch einen Race auf.

Ein Download-Helper mit root-Rechten kann auch eine **Argument**-Injection ermöglichen, wenn er einen Bash-Befehlsstring wie `curl <caller input> -o <fixed output>` erstellt. Ein Filter, der Leerzeichen zurückweist, lässt weiterhin [Bash-Klammererweiterung](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) zu: Nicht in Anführungszeichen gesetzte, durch Kommata getrennte Elemente können zu separaten curl-Argumenten werden. Erreicht die Eingabe curl vor dem festen `-o`, kann eine vom Aufrufer bereitgestellte Ausgabeoption das Ziel der ersten URL unter der Identität des Helpers auswählen; [curl ordnet Ausgabeoptionen den URLs der Reihe nach zu](https://curl.se/docs/manpage.html#-o). Prüfe die genaue Shell, das Quoting, die Eingabevalidierung, die wirksame sudo-Regel, curl-Argumentreihenfolge und unterstützte URL-Schemata sowie ob der Aufrufer die abgerufenen Bytes kontrolliert oder das Ergebnis lesen kann. Eine mit PyInstaller gepackte ausführbare Datei kann Python-Anwendungslogik enthalten; ein Packaging-Marker oder ein `curl`-String allein belegt diesen Datenfluss jedoch nicht. Untersuche, sofern autorisiert, eine begrenzte Offline-Kopie; bei der routinemäßigen Bestandsaufnahme den Helper nicht ausführen und keine angreiferkontrollierten Daten abrufen.

Ein Shellskript mit root-Rechten, das [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aufruft, wählt nur einen unbenutzten Namen aus; es **erstellt** die Datei nicht. Erstellt das Skript diesen Namen später in einem Verzeichnis, das ein anderer Benutzer beeinflussen kann, öffnet es erneut und hängt dessen Inhalt an ein geschütztes Ziel wie `authorized_keys` von root an, sollte ein möglicher Race bei temporären Dateien geprüft werden. Prüfe die genaue sudo-Regel, Eigentümer von Verzeichnis und Datei, Reihenfolge von Erstellung und erneutem Öffnen, Kernel-Schutzmechanismen sowie ob der privilegierte Schreibzugriff tatsächlich angreiferkontrollierte Bytes verwendet. Ein `mktemp -u`-String oder ein beschreibbares `/tmp` allein beweist keinen Race. Untersuche Skript und Pfadmetadaten, ohne es auszuführen oder bei der Bestandsaufnahme einen Race mit der temporären Datei auszulösen.

## Hinweise zur Verteidigung

- Erteile über sudo keine Berechtigung für Interpreter oder interaktive Editoren.<sup>[[1]](#references)</sup>
- Erteile keine Berechtigungen für generische Dateischreibwerkzeuge wie `tee` mit uneingeschränkten Operanden. Verwende einen root-eigenen Wrapper, der ein festes Ziel auswählt und vom Aufrufer kontrollierte Pfade zurückweist.<sup>[[2]](#references)</sup>
- Bevorzuge feste, root-eigene Wrapper, die genau eine eng begrenzte Verwaltungsaktion ausführen.<sup>[[1]](#references)[[2]](#references)</sup>
- Ist ein Interpreter unvermeidlich, beschränke den genauen Skriptpfad und verhindere benutzerkontrollierte Argumente, beschreibbare Imports, `PYTHONPATH` und eine unsichere Übernahme der Umgebung.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Sind Dateibearbeitungen erforderlich, beschränke den genauen Dateipfad und ziehe `sudoedit` mit gepatchten sudo-Versionen und strikter Umgebungsbehandlung in Betracht.<sup>[[1]](#references)[[2]](#references)</sup>
- Prüfe `SETENV`, `env_keep`, beschreibbare Arbeitsverzeichnisse, beschreibbare Modul-/Importpfade, `NOEXEC`, `use_pty` und Protokollierung, behandle sie aber nicht als vollständige Sandbox.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
