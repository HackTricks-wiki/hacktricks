## Interpreti consentiti da Sudo

Se `sudo -l` consente a un utente di eseguire un interprete come root, consideralo un'esecuzione diretta di codice. Gli interpreti sono progettati per eseguire codice arbitrario, quindi una regola che consente `python3`, `perl`, `ruby`, `lua`, `node` o binari simili equivale di solito all'esecuzione di comandi come root, a meno che gli argomenti non siano vincolati e convalidati in modo rigoroso.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flusso di revisione comune: prima elenca i privilegi dell'utente, poi esegui un'istruzione Python con l'opzione `-c` dell'interprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Di seguito sono riportati altri esempi di interpreti; quelli elencati documentano l’esecuzione di codice inline o le API per i processi figli.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Il percorso esatto è importante. Se la regola sudo consente `/usr/bin/python3`, usa quel percorso esatto durante la convalida.<sup>[[2]](#references)</sup>

Un glob per l'eseguibile sudo come `/usr/bin/python*` potrebbe consentire anche Python 2 per uno script scritto per Python 3. Se lo script raggiunge `input()` con testo controllato dal chiamante, [Python 2 valuta quel testo come un'espressione](https://docs.python.org/2/library/functions.html#input); un'invocazione esplicita dell'interprete prevale sullo shebang dello script. Verifica i binari corrispondenti installati, l'identità RunAs effettiva e la policy sugli argomenti, i dinieghi e l'input raggiungibile prima di considerarla una via di esecuzione.

Un percorso di script fisso in una regola sudo con privilegi root non limita ciò che lo script esegue. Per un wrapper Bash leggibile, verifica se il suo primo comando eseguibile usa un parametro posizionale non racchiuso tra virgolette, come `$1`, come **parola di comando**, mentre sudo consente argomenti scelti dal chiamante. Conferma l'identità RunAs effettiva, la policy relativa alla password e agli argomenti, i dinieghi successivi e il ramo effettivamente eseguito dallo script; `NOEXEC`, un elenco fisso di argomenti sicuri o un wrapper che convalida il comando possono cambiare il risultato. Durante l'enumerazione, esamina staticamente lo script breve invece di eseguirlo con un comando di prova.

Anche una regola sudo senza restrizioni per `dotnet` con privilegi root merita un controllo dell'interprete. Con un .NET SDK installato, [`dotnet fsi` esegue codice F# in modo interattivo o da uno script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/) e [`dotnet run` esegue un progetto dal codice sorgente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Prima conferma l'identità RunAs effettiva e la policy esatta sugli argomenti: una regola limitata a un sottocomando sicuro specifico o a un'applicazione attendibile è un'autorizzazione diversa, e un'installazione con solo il runtime potrebbe non includere i comandi dell'SDK. Il solo nome dell'eseguibile è un'indicazione da approfondire, non la prova di un'esecuzione di codice.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editor consentiti da sudo

Se `sudo -l` consente a un utente di eseguire un editor interattivo come root, consideralo una superficie di esecuzione dei comandi, non un innocuo permesso di modifica dei file. Gli editor possono spesso eseguire comandi shell, leggere o scrivere file arbitrari oppure richiamare helper esterni dall'interno dell'editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flusso di verifica comune: elenca i privilegi dell'utente, quindi avvia con sudo ogni editor o pager consentito.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Esecuzione di comandi con Nano

Quando `nano` è consentito tramite sudo, è possibile eseguire comandi dall’interfaccia dell’editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Quindi fornisci un comando come `id` o `/bin/sh` al prompt dei comandi di nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se una shell interattiva non dispone di flussi di terminale utilizzabili, questa forma di redirezione reindirizza lo standard output e lo standard error al descrittore 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La sequenza esatta di tasti può variare in base alla versione di nano e alle opzioni di compilazione, ma il problema di sicurezza è lo stesso: l’editor è in esecuzione come root e può invocare comandi esterni.<sup>[[1]](#references)[[12]](#references)</sup>

### Altre comuni modalità di escape dagli editor

Gli editor in stile Vim consentono comunemente di eseguire comandi tramite `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

I pager come `less` possono anche consentire l'esecuzione di comandi shell.<sup>[[14]](#references)</sup>

Una regola sudo che consente di eseguire `apport-cli` come root merita lo stesso controllo del pager. Le versioni di Apport interessate potevano aprire un report di crash in `less` con dimensioni del terminale modificabili da un utente malintenzionato; il pager poteva quindi fornire una shell root se erano soddisfatte le condizioni specifiche di sudo e del pager. Prima di considerare vulnerabile una versione basandosi solo sul numero, verifica la regola sudo effettiva, la configurazione del pager e la correzione del pacchetto della distribuzione. Durante l'enumerazione passiva, leggi i metadati del pacchetto e dei criteri senza generare un crash né aprire il report privilegiato. Il [record CVE di Ubuntu](https://ubuntu.com/security/CVE-2023-1326) elenca le versioni corrette dei pacchetti specifiche per ciascuna release, incluse le correzioni retroportate.

```text
!/bin/sh
```

## Altri rischi nelle regole sudo e doas

Inizia con `sudo -l`, `sudo -V` e qualsiasi policy `doas` applicabile. Valuta insieme comando consentito, utente RunAs, argomenti, ambiente e impostazioni predefinite. Il permesso di eseguire comandi come un account di servizio non-root può comunque esporre i file di quell'account o offrire un percorso verso root.

Uno script Python autorizzato da sudo con percorso fisso può comunque eseguire un comando shell con l'identità RunAs se concatena input interattivo controllato dal chiamante in [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist dei caratteri di punteggiatura della shell non basta a garantire la sicurezza: [la shell riconosce anche la sostituzione di comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Verifica che gli argomenti consentiti raggiungano il ramo che legge l'input, che l'input arrivi al comando shell senza una convalida sicura e che la policy sudo effettiva consenta l'utente RunAs previsto. Il percorso dello script o una chiamata a `os.system()` sono soltanto indizi da esaminare: ispeziona il sorgente senza eseguire lo script privilegiato.

Un'autorizzazione sudo effettiva come root per `chattr` può rimuovere l'attributo immutabile (`i`) di un file, ma questo da solo non concede né la scrittura né una nuova identità. [Il manuale di `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) specifica che l'attributo impedisce le modifiche e che solo root o un processo con `CAP_LINUX_IMMUTABLE` può cambiarlo. Controlla la policy esatta sugli argomenti di sudo e il supporto del filesystem, poi verifica separatamente che il chiamante possa scrivere il file dopo aver rimosso l'attributo e che un componente con identità superiore lo utilizzi. La sostituzione della shell di login, per esempio, richiede anche credenziali accettate per l'account target e un accesso effettivo tramite quella shell. Durante l'enumerazione, esamina policy, attributi e permessi dei file senza modificarli.

Se sudo richiede sia una password sia un codice monouso, considera questi prerequisiti separatamente dall'autorizzazione del comando. Un file `.google_authenticator` leggibile contiene materiale sensibile usato per generare i codici; un hash di una vecchia password applicativa o di database è soltanto una possibile password attuale dell'account. Nessuno dei due dimostra che il fattore corrispondente sia accettato dalla configurazione PAM effettiva. Una volta autorizzato, esamina RunAs e argomenti esatti: un'autorizzazione root senza restrizioni per `gem` di RubyGems può esporre il relativo comando editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ma un'autorizzazione limitata o un'autenticazione fallita no. L'enumerazione passiva dovrebbe riportare percorsi e policy senza stampare il seed, recuperare una password, generare un codice o eseguire il comando privilegiato.

Un'autorizzazione sudo senza restrizioni per `knife` di Chef, eseguibile come root, richiede un esame a livello di interprete: [Chef documenta che `knife exec -E` valuta localmente una stringa Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica che la regola sudo effettiva consenta il sottocomando `exec` e l'argomento `-E` fornito dal chiamante, l'identità RunAs prevista e gli eventuali divieti o argomenti fissi corrispondenti. Il binario installato o una regola limitata ad altri sottocomandi sono soltanto indizi. L'enumerazione passiva dovrebbe riportare la regola senza eseguire `knife`.

Un'autorizzazione sudo esatta per `msfconsole`, eseguibile come root, è altrettanto sensibile: [GTFOBins documenta la sua console `irb`](https://gtfobins.org/gtfobins/msfconsole/), che può ereditare l'identità sudo. Verifica l'utente RunAs effettivo, l'elenco degli argomenti consentiti, i divieti sui comandi, `NOEXEC` o altre restrizioni, il comportamento della console installata e la possibilità per il chiamante di fornire input interattivo. La sola evidenziazione del percorso è un indizio da esaminare; l'enumerazione passiva non dovrebbe avviare la console.

Su FreeBSD, anche una regola sudo limitata a `pkg update` e `pkg install *` come root richiede di esaminare l'affidabilità dei repository. Controlla se `/etc/hosts` è scrivibile dal chiamante e se la configurazione effettiva dei repository abilitati usa un hostname HTTP con `signature_type: none`. [Il manuale di `pkg.conf` di FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) specifica che `none` disabilita i controlli delle firme; la sola presenza di `pkg+http` non lo dimostra. [Un pacchetto può contenere script di installazione](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), quindi un chiamante che controlla effettivamente l'endpoint del repository e può scegliere un pacchetto potrebbe superare il confine di root. Prima di giungere a questa conclusione, verifica le configurazioni dei repository sostitutive, la risoluzione SRV/mirror, gli argomenti sudo effettivi, la selezione dei pacchetti e l'esecuzione degli script. Esamina la policy e i piccoli file di configurazione locali senza reindirizzare i nomi né eseguire `pkg` durante l'enumerazione.

Anche un'autorizzazione sudo per `apt-get update` e `apt-get upgrade` eseguibili come root richiede di esaminare l'affidabilità dei repository, se sudo conserva un `http_proxy` controllato dal chiamante. Verifica se la configurazione APT effettiva usa davvero quella variabile proxy e quali richieste ai repository abilitati può influenzare; un proxy da solo non può sostituire pacchetti provenienti da un archivio autenticato con una chiave di firma attendibile. [Il manuale del trasporto HTTP di APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedenza dei proxy, mentre [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta i controlli delle firme, le eccezioni per i repository non sicuri e la conferma richiesta per i pacchetti non autenticati. Verifica RunAs e argomenti sudo esatti, la policy di autenticazione dei repository, l'eventuale conferma interattiva necessaria e se l'aggiornamento selezionato esegue script dei pacchetti come root. Esamina policy e configurazione locale passivamente; durante l'enumerazione non reindirizzare il traffico dei pacchetti né eseguire un aggiornamento.

Una regola sudo per `snap install`, eseguibile come root, può creare un confine tra pacchetto e codice se gli argomenti consentono al chiamante di selezionare uno snap locale e una modalità di installazione permissiva. [La documentazione di Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) spiega che `--dangerous` salta i controlli delle asserzioni sugli snap locali e che `--devmode` allenta il confinamento; [un hook di installazione può essere eseguito durante l'installazione iniziale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prima di affermare che consenta l'accesso a file host protetti, verifica la policy sudo esatta per argomenti/RunAs, chi controlla il file snap, se queste modalità sono accettate dalla versione installata di snapd e l'identità effettiva e il confinamento dell'hook. Un binario `snap` o una regola che sembra contenere un wildcard non dimostrano da soli questa catena. L'enumerazione passiva non dovrebbe installare pacchetti né eseguire i relativi hook.

Per un'autorizzazione sudo esatta a un binario personalizzato che legge credenziali come account **non-root**, esamina prima il binario autorizzato e i permessi del file senza eseguirlo. Una password di accesso incorporata potrebbe essere visibile solo come caratteri larghi; [GNU `strings` documenta l'estrazione little-endian a 16 bit](https://sourceware.org/binutils/docs/binutils/strings.html). Una stringa visibile non dimostra che sia la password accettata né che il ramo di esito positivo esponga credenziali attuali. Verifica separatamente il comportamento del binario, l'accesso dell'account target ai dati protetti, la validità delle credenziali e qualsiasi successivo cambio di account o gruppo. Se l'account appartiene al gruppo `docker`, verifica l'accesso al socket e l'identità rootful o rootless del daemon prima di dedurre l'accesso a root sull'host; [Docker documenta le implicazioni a livello root del gruppo](https://docs.docker.com/engine/install/linux-postinstall/). L'enumerazione ordinaria dovrebbe riportare la regola sudo e l'appartenenza ai gruppi senza eseguire il binario né scaricarne le stringhe.

Una regola sudo con wildcard per gli script di manutenzione di un'applicazione richiede un esame che vada oltre il percorso dello script. Verifica se lo script consentito accetta argomenti senza restrizioni o legge impostazioni scrivibili da un account applicativo con privilegi inferiori, poi segui quei valori fino ai comandi shell o all'ambiente di un subprocesso. Per esempio, `zmupdate.pl` di ZoneMinder [compone un comando `mysqldump` e lo esegue tramite `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mentre [`zmdc.pl` copia l'impostazione `ZM_LD_PRELOAD` in `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) prima di avviare i daemon. Una regola sudo che consente di eseguire uno dei due script come root può superare un confine di fiducia se il relativo input è controllabile e raggiunge quel codice nella versione installata. Esamina la regola sudo effettiva, i permessi di configurazione dell'applicazione e il sorgente degli script; il wildcard o l'impostazione da soli sono indizi, non prove di esecuzione.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` possono trasformare un comando altrimenti limitato in un attacco di hijack di import, librerie o PATH. Vedi la [guida alle variabili d'ambiente](../linux-basics/linux-environment-variables.md) e [l'abuso di SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Un'autorizzazione `SETENV` esatta per uno script wrapper shell eseguibile come root merita anche un esame a un passaggio, se il wrapper avvia uno script Python fisso con un import letterale. `secure_path` limita la ricerca dei comandi da parte della shell, non la ricerca dei moduli Python tramite [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fanno sì che Python ignori quella variabile d'ambiente. Prima di considerarlo un caso di esecuzione di codice, verifica i tag e i divieti sudo effettivi, il ramo del wrapper, le opzioni dell'interprete, la risoluzione degli import e la presenza di una directory di ricerca scrivibile dal chiamante. Esamina staticamente gli script brevi; non eseguire il wrapper privilegiato.

Un'autorizzazione sudo esatta per `neofetch ""`, eseguibile come root, può comunque caricare una configurazione shell quando le impostazioni predefinite sudo applicabili conservano un `XDG_CONFIG_HOME` controllato dal chiamante. [Il loader di configurazione di Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carica `neofetch/config.conf` o `neofetch/config` da quella directory; l'elenco vuoto di argomenti non impedisce questa ricerca. Verifica il loader installato, RunAs e la policy effettivi sugli argomenti, gli eventuali divieti sui comandi, se sudo conserva davvero la variabile selezionata per questo comando e se il chiamante controlla un percorso di configurazione leggibile. Una variabile conservata o la sola presenza di Neofetch sono indizi da esaminare. Esamina policy e metadati dei file senza eseguire il comando privilegiato né stampare il contenuto della configurazione; vedi [la gestione dell'ambiente in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regola sudo senza restrizioni per `facter`, eseguibile come root, merita un esame separato dei custom fact. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) che `--custom-dir` carica file di fact Ruby da una directory selezionata. Verifica che la regola sudo esatta consenta tale opzione, che Facter installato la supporti e che il chiamante controlli la directory. Un'autorizzazione con argomenti fissi, un divieto esplicito del comando o custom fact disabilitati possono cambiare l'esito. L'enumerazione passiva dovrebbe riportare la regola candidata senza eseguire Facter né leggere i contenuti dei fact.

Per un'autorizzazione sudo esatta per uno script eseguibile come root con `SETENV`, esamina nomi di comando senza percorso completo come `find` e il `PATH` effettivo dopo l'applicazione della policy sudo e l'inizializzazione dello script. Un file Bash caricato tramite `source` può anche eseguire `enable -n [`: [Bash cerca quindi in `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un eseguibile esterno `[` quando lo script usa poi quel comando. Verifica le regole applicabili di [sudoers sull'ambiente e `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), eventuali voci `NOSETENV`/`NOEXEC` o di divieto, il flusso dello script e dei file caricati e la presenza di una directory di ricerca eseguibile controllata dal chiamante. Uno script leggibile contenente un comando senza percorso completo è un indizio da esaminare, non una prova di esecuzione privilegiata; ispezionalo senza usare la regola sudo.

- Uno script privilegiato che scarica un URL fisso con `curl` può comunque accettare una risposta scelta dal chiamante se una regola sudo applicabile conserva `http_proxy` e la richiesta viene inviata tramite quel proxy. Se lo script passa poi la risposta a un parser XML che risolve entità esterne, una risposta malevola può divulgare file leggibili dal processo privilegiato. Verifica la policy sudo esatta sull'ambiente, le esclusioni `no_proxy`, l'URL richiesto, la configurazione del parser e la destinazione dell'output; la sola variabile proxy o il solo parser XML non costituiscono una vulnerabilità. La [documentazione di curl sulle variabili d'ambiente dei proxy](https://everything.curl.dev/usingcurl/proxies/env.html) descrive il comportamento di queste variabili. Durante l'enumerazione passiva, non effettuare richieste di rete né analizzare XML ostile.
- Uno script sudo eseguibile come root che genera un file PostScript da dati influenzati dal chiamante e poi esegue `ps2pdf -dNOSAFER` merita un esame separato del flusso dell'input. Ghostscript documenta che questo flag disabilita SAFER fino a `.setsafe`, consentendo operazioni sui file PostScript secondo i permessi del processo nel sistema operativo. Una query SQL composta usando un argomento del chiamante può fornire righe controllate dall'attaccante al template PostScript, ma la stringa di una query o l'invocazione di `ps2pdf` da sole non dimostrano che i dati raggiungano la sintassi PostScript eseguibile. Verifica la regola sudo effettiva, il percorso esatto dall'input al template, eventuali escaping, il comportamento della versione installata di Ghostscript e se SAFER viene riattivato prima di interpretare il documento. Durante l'enumerazione passiva, non eseguire la conversione privilegiata. Vedi la [documentazione di Ghostscript su `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Per una regola sudo che esegue uno script shell, confronta le variabili conservate con lo script stesso. Un costrutto come `if $CHECK_CONTENT; then` esegue il valore espanso come comando; conservare `CHECK_CONTENT` può quindi consentire l'esecuzione di comandi anche se il percorso dello script e gli argomenti sono fissi. Verifica, per la regola specifica, se il ramo è raggiungibile e se l'ambiente viene effettivamente conservato.<sup>[[2]](#references)[[22]](#references)</sup>
- Uno script Python consentito da sudo può importare codice da una directory scrivibile o da un file `.pyc` in cache. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md) descrive il caso della cache.
- Uno script Python fisso consentito da sudo ed eseguibile come root può comunque esporre un debugger interattivo. Chiamate come `pdb.set_trace()` o `pdb.post_mortem()` consentono di eseguire istruzioni Python nel contesto del processo sottoposto a debug, se il chiamante può raggiungere il breakpoint o il gestore delle eccezioni **e controllare l'input del debugger**. Verifica la regola sudo esatta per RunAs, l'autenticazione e le condizioni del ramo, la possibilità di raggiungere l'eccezione, chi possiede il terminale/input e se il debugger viene eseguito nello stesso processo privilegiato. Una richiesta socket che causa un'eccezione non concede di per sé accesso a un debugger collegato a un altro terminale. [Python documenta la valutazione delle istruzioni del debugger e la modalità post-mortem](https://docs.python.org/3/library/pdb.html); durante l'enumerazione, ispeziona staticamente lo script anziché attivare il gestore privilegiato.
- Uno script Python fisso consentito da sudo può anche leggere un campo profilo da un database o socket Unix e aggiungerlo a una stringa che in seguito diventa la **stringa di formato** per `str.format()`. [I campi di sostituzione possono usare attributi e chiavi di mapping](https://docs.python.org/3/library/string.html#format-string-syntax), quindi un campo controllato dall'attaccante può ispezionare gli oggetti passati a `format()` ed esporre dati accessibili tramite quegli oggetti, se il risultato viene stampato o salvato dove il chiamante può leggerlo. Verifica l'identità RunAs effettiva di sudo, il permesso di scrittura sul record specifico, il flusso dei dati fino alla stringa di formato, gli oggetti forniti e la visibilità dell'output. Questo non comporta automaticamente l'esecuzione di codice; un caso diverso è una stringa di formato letterale attendibile con *valori* controllati dall'attaccante. Un segreto divulgato consente il passaggio a un account del sistema operativo solo se quell'account lo accetta. Esamina lo script e i permessi del socket senza eseguire l'operazione privilegiata.
- Un wrapper Python eseguibile come root può passare un URL scelto dal chiamante a `Repo.clone_from` di GitPython. Se il wrapper abilita anche `protocol.ext.allow=always` di Git, un remote `ext::` può eseguire un helper esterno. Verifica gli argomenti sudo esatti, la provenienza dell'URL, la versione del pacchetto GitPython e l'eventuale patch del vendor, nonché se il wrapper abilita esplicitamente protocolli non sicuri. GitPython ha aggiunto una [protezione predefinita contro i protocolli non sicuri](https://github.com/gitpython-developers/GitPython/commit/2625ed9) nella versione 3.1.30; la versione dell'eseguibile `git` è un dato distinto. L'esame passivo dovrebbe limitarsi a leggere la regola e una porzione circoscritta del sorgente, senza avviare la clonazione.
- Un'autorizzazione sudo tra utenti per uno strumento CLI di clonazione di repository può esporre un percorso distinto di injection di stringhe shell. Verifica se l'argomento del repository scelto dal chiamante raggiunge [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) di Node.js o un altro generatore di comandi shell senza una separazione sicura degli argomenti; `exec` di Node passa la stringa di comando a una shell. Verifica l'utente RunAs esatto, i sottocomandi e gli argomenti consentiti, il codice del wrapper installato e la convalida dell'input. Il nome dello strumento per repository o una regola sudo senza restrizioni non dimostrano da soli l'injection di comandi. Durante l'enumerazione, esamina il wrapper senza avviare una clonazione privilegiata.
- Un wrapper personalizzato di proprietà di root può sembrare sicuro perché i suoi binari e script non sono scrivibili, eppure la decisione di eseguire un'azione privilegiata può dipendere da un flag, da un valore di un'API locale o dallo stato di un servizio che un utente non privilegiato può modificare. Segui ogni condizione fino al relativo input e ai controlli di autorizzazione. Durante l'enumerazione, esamina configurazione e permessi senza modificare lo stato operativo; una chiamata a `systemd-run` nel wrapper è rilevante solo se la condizione può essere influenzata.
- Un client di backup consentito tramite sudo come root può accettare un file di configurazione scelto dal chiamante, ad esempio `npbackup-cli -c`. Verifica l'utente RunAs e gli argomenti consentiti esatti, poi controlla se il chiamante controlla il percorso di configurazione, i percorsi delle sorgenti di backup e le opzioni relative al repository o alla lettura/ripristino. Un segreto cifrato del repository presente in una configurazione leggibile può essere comunque utilizzabile dal client, ma la sola regola non dimostra l'accesso al repository né la divulgazione di file root. Verifica l'autorizzazione senza eseguire un backup né scaricarne i contenuti.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) supporta `--password-command`, che esegue un programma per ottenere la password di un repository. Se una regola sudo consente a un utente con privilegi inferiori di eseguire restic come root con un comando password scelto dal chiamante e un sottocomando che richiede la password, l'helper potrebbe essere eseguito come root. Esamina gli argomenti e le esclusioni sudo esatti; non eseguire l'helper né un comando di backup solo per verificare la condizione durante l'enumerazione.
- Un'autorizzazione privilegiata per `restic backup` può anche superare un confine di lettura dei file se lo schema degli argomenti sudo consente al chiamante di scegliere sia la sorgente sia un repository che in seguito può leggere e decrittare. [I wildcard per gli argomenti di sudoers possono corrispondere a spazi e slash](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf); esamina quindi i wildcard finali senza presumere che un prefisso fisso del repository limiti la sorgente. [Restic può eseguire il backup su repository locali e remoti](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), ma un repository locale può contenere oggetti root appena scritti; prima di considerarlo una divulgazione, verifica la policy sudo effettiva, l'accesso al backend, la password del repository e i permessi degli oggetti risultanti. Una chiave SSH inclusa nel backup consente l'accesso solo se l'account di destinazione la accetta. Durante l'esame passivo, non eseguire un backup per verificare questa possibilità.
- Un comando personalizzato senza restrizioni di manutenzione o backup può accettare un percorso di output oppure offrire un proprio scheduler di job. Per un percorso di scrittura di file, verifica la regola sudo esatta e l'utente RunAs, poi controlla se il chiamante controlla sia i dati sia la destinazione. Per un percorso basato su comandi pianificati, verifica l'identità di esecuzione dello scheduler, l'input del comando e gli eventuali ulteriori requisiti di password o autorizzazione. Il solo nome del comando o `NOPASSWD` non dimostrano nessuno dei due percorsi. Vedi [la scrittura in file di proprietà di root](../interesting-files-permissions/write-to-root.md) e [cron e i timer systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando fisso consentito da sudo può comunque caricare un file di configurazione prevedibile da una directory condivisa scrivibile. Verifica se il chiamante può sostituire quel file e se i suoi campi sorgente e destinazione controllano un fetch o una copia privilegiata. Un URL che punta a un file locale può esporre dati leggibili solo dall'account RunAs di sudo; una sorgente controllata dal chiamante associata a una destinazione protetta può creare un percorso di scrittura. Verifica la gestione degli URL da parte del programma installato, i controlli sul percorso di destinazione, la regola sudo effettiva e l'accessibilità dell'output. Un percorso di configurazione scrivibile in `/tmp` è solo un indizio: esamina binario e metadati dei file senza eseguire il trasferimento privilegiato.
- Una regola sudo per `git apply` può consentire all'account RunAs di scrivere file selezionati da una patch controllata dal chiamante. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) consentiva a una patch appositamente creata di generare un symlink e poi scrivere oltre l'albero di lavoro, anche se il comando non accettava `--unsafe-paths`. Verifica la regola sudo effettiva sugli argomenti, la provenienza della patch, l'accesso dell'account RunAs alla directory di lavoro e la correzione di Git installata o il backport del vendor. Una regola senza restrizioni che ammette `--unsafe-paths` comporta un rischio distinto legato a un'opzione esplicita; né la versione di Git né il permesso di eseguire `git apply` dimostrano da soli che si possa modificare un file protetto. Durante l'enumerazione passiva, non applicare patch non attendibili.
- Una regola sudo per `clamscan --debug`, eseguibile come root, può superare un confine di lettura se un utente con privilegi inferiori può fornire un'immagine DMG e il parser installato è vulnerabile a [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), che poteva divulgare contenuti di file tramite l'output di debug. Verifica gli argomenti consentiti e il percorso di scansione esatti, il controllo dell'input, l'account RunAs effettivo, la correzione o il backport del motore e se l'output è visibile al chiamante. Se una regola più ampia consente `--file-list`/`-f`, esamina separatamente il comportamento di tale file-list; una policy fissa a `--debug <scan-path>` non lo ammette. Durante l'enumerazione, esamina policy e metadati del pacchetto senza analizzare un file creato ad arte né stampare output protetto.
- Una regola sudo per aprire un'immagine disco cifrata scelta dal chiamante come root, insieme a una seconda regola per montare il mapper risultante, può introdurre file controllati dal chiamante nello spazio dei mount dell'host. Verifica entrambe le regole e i relativi argomenti effettivi, il controllo dell'immagine e del nome del mapper, il punto di mount effettivo e proprietario e modalità dei file risultanti. Un passaggio a set-user-ID richiede inoltre un eseguibile accessibile, opzioni di mount che lo rispettino (`nosuid` lo blocca) e policy di processo o MAC applicabile: aprire o montare un'immagine è soltanto un indizio. Un percorso distinto tramite un backup esistente richiede la chiave effettiva e un segreto utile e leggibile al suo interno. Durante l'esame passivo, ispeziona policy e percorsi senza aprire o montare immagini. Vedi il [manuale di cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e le [opzioni di mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regola sudo per uno script shell o Python eseguibile come root merita un esame della directory di lavoro se lo script esegue `./helper` senza prima spostarsi in una directory fissa. Anche una lista Python come `['./helper']` passata a `subprocess.run` può usare la directory di lavoro scelta dal chiamante. Il chiamante potrebbe selezionare una directory scrivibile e inserirvi un eseguibile con quel nome relativo; un percorso assoluto usato altrove nello script non protegge questa chiamata. Prima di considerarla esecuzione di codice, verifica la regola effettiva, `runchdir` o altre policy che cambiano directory, il flusso dello script e la raggiungibilità del ramo, una directory scrivibile ed eseguibile e le restrizioni di mount/`NOEXEC`. Se lo script non è leggibile, il comportamento resta ignoto finché il sorgente non viene esaminato tramite un percorso autorizzato. Esamina gli script staticamente invece di eseguire l'helper. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la policy sulla directory di lavoro.
- Un validatore Python fisso eseguibile come root può comunque valutare un file di dati scelto dal chiamante. [La documentazione Python di `eval()` mette in guardia dagli input non attendibili](https://docs.python.org/3/library/functions.html#eval): un controllo del suffisso dell'input, un prefisso aritmetico o un ramo di convalida non sono una sandbox se l'espressione rimanente raggiunge `eval`. Prima di considerarlo un percorso di esecuzione, verifica la regola sudo effettiva, se il chiamante può selezionare e controllare il file esatto, le condizioni del ramo del parser e la composizione dell'espressione, nonché l'identità del processo privilegiato. La presenza di `eval` in uno script leggibile è soltanto un indizio da esaminare; durante l'enumerazione, controlla sorgente e permessi dei file senza eseguire il validatore né inviare un'espressione di prova.
- Un wrapper Ruby eseguibile come root tramite sudo che legge un nome di file YAML relativo, come `YAML.load(File.read("dependencies.yml"))`, può ricevere input dalla directory di lavoro del chiamante, a meno che il wrapper o la policy sudo non fissino quella directory. Verifica gli argomenti consentiti esatti, i permessi della directory e del file e il comportamento della versione di Psych installata: le versioni precedenti di `YAML.load` potevano deserializzare oggetti Ruby arbitrari, mentre le versioni più recenti limitano le classi per impostazione predefinita. Un punto di chiamata statico è solo un indizio: verifica che il file provenga davvero da una directory scrivibile dal chiamante e che il loader installato accetti classi pericolose. Per input non attendibili, preferisci `safe_load` con un elenco esplicito e minimo di classi consentite. Vedi la [documentazione di Psych per Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e la [documentazione di Psych per Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Un'autorizzazione sudo esatta per `sudo go run /absolute/file.go`, eseguibile come root, merita un esame della directory di lavoro se il sorgente Go legge un file WASM relativo e potrebbe eseguire uno script shell relativo dopo averne esaminato il risultato. Verifica RunAs effettivo, argomenti e divieti del comando, la presenza di una directory di lavoro corrente scrivibile dal chiamante, il flusso dei dati dal WASM al ramo e se quel ramo esegue l'helper. Un `runchdir` fisso in sudo, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) possono modificare la directory di ricerca. La semplice co-occorrenza nel sorgente è solo un caso candidato; esamina il codice senza eseguire Go, WASM o l'helper.
- `sudoedit` e i wildcard negli argomenti richiedono verifiche precise della versione e della regola; la [checklist](linux-privilege-escalation-checklist.md) include il problema di modifica dei file tramite sudoedit. Per un'autorizzazione `sudoedit` tra utenti su un percorso con wildcard, esamina l'impostazione effettiva `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, il target risolto e chi può sostituire ciascuna voce delle directory parent. La prima può consentire di seguire un symlink, mentre la disattivazione della seconda rimuove i controlli sulle directory scrivibili; nessuna delle due impostazioni, da sola, dimostra la possibilità di scrivere nel file di un altro utente. Prima di giungere a questa conclusione, verifica la policy sudo installata e gli argomenti esatti che corrispondono alla regola. Vedi le [definizioni delle opzioni di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In una regola di comando sudoers, un wildcard negli argomenti può corrispondere anche agli spazi, oltre che ai caratteri di percorso. Una regola per un comando che può leggere file con un argomento come `/restricted/*` può quindi ammettere un argomento aggiuntivo per un file dopo un prefisso corrispondente. Esamina l'utente RunAs esatto, il percorso del comando, il pattern degli argomenti e gli eventuali divieti successivi; una lettura di file dimostrata non implica l'esecuzione di comandi. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue i glob degli argomenti da quelli del percorso del comando.
- Anche un glob degli argomenti che sembra limitato a un percorso può corrispondere a `../`. Per esempio, una regola `node /opt/scripts/*.js`, eseguibile come root, può consentire al chiamante di fornire un file JavaScript fuori da `/opt/scripts`, se il percorso specificato inizia comunque con `/opt/scripts/` e si risolve tramite segmenti di directory parent. Si tratta di un glob per **l'argomento**; il glob del percorso del comando per l'eseguibile Node applica regole diverse per gli slash. Prima di concludere che consenta l'esecuzione di codice, verifica la regola effettiva, gli eventuali divieti successivi, la risoluzione del percorso, il controllo del file target e le restrizioni tramite espressioni regolari o digest di sudoers. Vedi le [regole dei wildcard in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e la [documentazione della riga di comando di Node](https://nodejs.org/api/cli.html).
- Archiver e altri programmi di utilità possono offrire hook di esecuzione. Verifica gli argomenti consentiti esatti consultando [GTFOBins](https://gtfobins.github.io/) invece di presumere che solo shell o interpreti possano eseguire comandi.
- Una regola senza restrizioni per `qpdf`, eseguibile come root, può esporre un file privilegiato tramite allegati PDF: qpdf 10.2 e versioni successive supportano `--empty` e `--add-attachment file ... --` con un PDF di output. Se il processo privilegiato può leggere la sorgente selezionata e scrivere il PDF in un percorso accessibile al chiamante, l'output può contenere i byte della sorgente. Prima di concludere che la divulgazione del file sia possibile, esamina gli argomenti e le esclusioni sudo effettivi, la versione di qpdf, l'accesso alla sorgente e il percorso di output. La lettura di una chiave SSH di root è utile per il login solo se la chiave è valida e l'autenticazione SSH di root è consentita. Vedi le [opzioni degli allegati di qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Il riutilizzo dei timestamp sudo dipende dalla policy della cache, dall'utente proprietario, dal terminale/sessione e dai permessi. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) illustra le verifiche.
- `doas` ha regole e configurazione proprie. Verifica i comandi consentiti e i percorsi di configurazione scrivibili come descritto nella [sezione doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Strumenti di build e gestione pacchetti eseguiti tramite sudo

Un'autorizzazione sudo senza restrizioni per `forge` di Foundry può essere rilevante anche quando l'identità RunAs è un altro utente non-root. Opzioni del compilatore come `--use` possono selezionare un eseguibile locale, mentre `forge flatten -o` seleziona un file di output. Prima di considerare sfruttabile l'autorizzazione, verifica la versione di Forge installata, gli argomenti sudo esatti, l'accessibilità del progetto e dei percorsi del compilatore, i permessi dell'output e l'ambiente effettivo. Un helper eseguibile relativo trovato tramite `PATH` è un percorso che dipende dalla versione e dall'ambiente, non una caratteristica da presumere per ogni build di Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Un'autorizzazione per `pacman` senza restrizioni, eseguibile come root, consente più delle sole query sui pacchetti: `-U` accetta un pacchetto locale, i pacchetti possono includere script di installazione e `--hookdir` seleziona un'altra directory per gli hook. Prima di testarla, esamina la regola sudo effettiva, le restrizioni sugli argomenti e le esclusioni; l'enumerazione passiva non richiede di installare pacchetti né eseguire hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fisso eseguito tramite sudo può anche installare una dipendenza npm nominata e poi avviare un'applicazione Node. Esamina la relativa regola RunAs esatta, se il pacchetto è già installato, i valori effettivi di `HOME` e `userconfig` di npm, gli override di configurazione del progetto o della riga di comando e se un utente con privilegi inferiori controlla il registry o il pacchetto restituito per quel nome. [npm documenta la ricerca di `.npmrc` a livello di utente e di progetto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); il comportamento di `HOME` in sudo dipende dalla policy e dalla distribuzione installate, quindi il processo npm privilegiato potrebbe leggere o meno il file `.npmrc` di un utente scrivibile. Se il pacchetto appena installato viene importato dall'applicazione privilegiata, il suo codice di modulo può essere eseguito con l'identità dell'applicazione. Gli script eseguiti durante l'installazione costituiscono un percorso separato, dipendente dalla versione e dalla configurazione; [npm ne documenta il ciclo di vita e la gestione degli utenti](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un percorso `.npmrc` o una riga `npm install` sono solo indizi da esaminare. Durante l'enumerazione passiva, esamina la regola, il wrapper breve, i percorsi di configurazione e la provenienza del pacchetto senza installarlo né avviare l'applicazione.

Un'autorizzazione root per `pip` o `pip3 download` è anche un indizio per esaminare la build di pacchetti, quando gli argomenti consentono al chiamante di selezionare una distribuzione sorgente non attendibile, anche se il pattern dell'URL è limitato a un servizio locale e a un suffisso `.tar.gz`. `pip download` accetta URL di archivi e risolve i metadati dei pacchetti; la preparazione di una distribuzione sorgente può eseguire il relativo backend di build o codice legacy `setup.py` prima ancora che l'archivio venga salvato. Verifica RunAs e la regola esatta sugli argomenti di sudo, se il chiamante può pubblicare o sostituire l'archivio selezionato e se quella versione di pip prepara effettivamente i metadati. Un archivio fisso e attendibile o un wheel non dimostrano questo percorso. Durante l'enumerazione passiva, non scaricare né compilare un pacchetto non attendibile. Vedi il [comando download di pip](https://pip.pypa.io/en/stable/cli/pip_download/), l'[interfaccia del sistema di build](https://pip.pypa.io/en/stable/reference/build-system/) e le [indicazioni per installazioni sicure](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regola sudo che consente `pip install` con un percorso di progetto locale scelto dal chiamante crea un confine di build più diretto. [pip accetta directory di progetto locali](https://pip.pypa.io/en/stable/topics/local-project-installs/) e ne invoca il sistema di build; il [backend di build esegue hook controllati dal progetto](https://pip.pypa.io/en/stable/reference/build-system/). Prima di considerare la regola un'esecuzione di codice privilegiata, verifica l'identità RunAs effettiva, le restrizioni e i divieti esatti sugli argomenti, il controllo del progetto selezionato e il comportamento di pip/backend installati. Un progetto attendibile fisso o una regola che esclude percorsi scelti dal chiamante non dimostrano questo percorso. Esamina la regola e i metadati del progetto senza installare pacchetti durante l'enumerazione passiva.

Un'autorizzazione senza restrizioni per `easy_install`, eseguibile come root, è un indizio analogo relativo alla build di pacchetti legacy. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) che Easy Install accetta una directory di progetto locale e compila distribuzioni sorgente; durante la build, un progetto controllato dal chiamante può eseguire il proprio `setup.py` con l'identità sudo. Verifica l'account RunAs effettivo, il comando esatto e le restrizioni sugli argomenti (inclusi eventuali divieti successivi), il controllo del progetto selezionato e il comportamento dello strumento installato. Un progetto attendibile fisso o una policy che non consente di scegliere la sorgente non dimostrano questo percorso. Esamina la regola e i metadati del progetto senza installare pacchetti durante l'enumerazione.

Un wrapper Python consentito da sudo che usa `setuptools.package_index.PackageIndex.download` con un URL scelto dal chiamante è un caso da esaminare distinto da `pip download`: [GHSA-5rjg-fvgr-3xxf di setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descrive come, nelle versioni vulnerabili precedenti alla 78.1.1, un nome file derivato dall'URL potesse uscire dalla directory di download prevista e scrivere con i permessi del processo. Verifica RunAs e la regola esatta sugli argomenti di sudo, che il wrapper passi l'URL del chiamante proprio a questa API, la build installata o il backport del vendor e la risoluzione del percorso risultante. Una stringa di versione o una directory di download scrivibile, da sole, non dimostrano la possibilità di scrivere arbitrariamente. Durante l'enumerazione, esamina il wrapper breve e i metadati del pacchetto senza recuperare l'URL né scrivere file.

Un wrapper di build consentito da sudo che passa a PyInstaller un file `.spec` scelto dal chiamante richiede un esame analogo del confine di fiducia. Un file spec di PyInstaller è codice Python eseguibile valutato **durante la build** e le sue voci `datas` possono includere in un artifact file leggibili dall'identità di build. Verifica l'utente RunAs esatto, le regole sudo sugli argomenti e i relativi divieti, la gestione dei percorsi e dei rami nel wrapper, il controllo del file spec selezionato e l'accesso all'artifact risultante. Il solo permesso per un input `.py` o la presenza di PyInstaller non dimostrano il controllo del file spec né l'esecuzione privilegiata. L'esame passivo dovrebbe limitarsi a leggere un wrapper breve e circoscritto e i relativi metadati; non dovrebbe eseguire una build. Vedi la [documentazione dei file spec di PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loader di preset e plugin eseguiti tramite sudo

Gli strumenti Python che accettano un preset scelto dal chiamante o una directory di plugin possono importare codice con i privilegi concessi da sudo. Per esempio, BBOT accetta un preset con `-p` e la [documentazione dei moduli personalizzati](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descrive voci `module_dirs` che selezionano ulteriori directory di moduli Python. Se la regola sudo effettiva consente un preset scelto dal chiamante e quest'ultimo controlla un modulo nella directory selezionata, l'import può eseguire codice come utente privilegiato, potenzialmente prima che lo strumento rifiuti un modulo non valido. Verifica la versione installata, la policy esatta di sudo su RunAs e argomenti e la proprietà del preset e dei percorsi dei moduli senza caricare il modulo durante l'enumerazione.

### Strumento da riga di comando Backdrop eseguito tramite sudo

[Bee](https://github.com/backdrop-contrib/bee) è uno strumento PHP da riga di comando per Backdrop CMS. I suoi comandi `eval` (`php-eval`) e `php-script` possono eseguire PHP fornito dal chiamante. Una regola sudo che consente l'eseguibile Bee come root con argomenti senza restrizioni può quindi esporre l'esecuzione di codice root, se Bee riesce ad avviare un'installazione di Backdrop. Eseguilo dalla directory del sito oppure seleziona un sito usando l'opzione globale `--root=<directory>`; trovare Bee o un file `settings.php` di Backdrop non dimostra che i permessi sudo siano sufficienti, che il sito sia utilizzabile o che l'avvio riesca. Prima di eseguire test, esamina la regola sudo effettiva, eventuali esclusioni di comandi, l'identità dell'eseguibile e l'accesso al sito. Durante l'enumerazione passiva, esamina la regola e i percorsi dei file senza eseguire Bee. Vedi il [changelog dei comandi di Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) per l'aggiunta dei comandi PHP.

### Server di terminale eseguiti tramite sudo

`mosh-server` avvia un server di terminale interattivo come utente che lo invoca. Sceglie una porta UDP alta e una chiave di sessione, comunica entrambe al chiamante e, normalmente, avvia la shell di login di quell'utente quando un client si connette. Un'autorizzazione sudo senza restrizioni per `mosh-server`, eseguibile come root, è quindi un caso da esaminare come possibile shell, anche se il comando del server si stacca dal terminale. Verifica l'identità RunAs effettiva, gli argomenti consentiti e le esclusioni, il binario installato, la shell, la disponibilità di un client e l'accesso UDP. L'enumerazione passiva dovrebbe esaminare la regola sudo senza avviare un server né stampare una chiave di sessione attiva. Vedi il [manuale del server Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e le [note di progettazione upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrapper di backup privilegiati che riscrivono il file di attività del chiamante

Un wrapper shell eseguito come root può accettare un file di attività selezionato dal chiamante, rimuovere `../` dai percorsi delle sorgenti, controllare che ogni risultato inizi con una directory consentita, riscrivere il file di attività e poi passare al programma di backup il relativo *percorso*. Esamina il percorso trasformato dopo una risoluzione canonica completa: una singola passata di sostituzione delle stringhe può esporre una nuova sequenza di traversal accettata da un controllo lessicale del prefisso. Verifica anche se il programma di backup legge i dati trasformati dalla memoria oppure riapre il file. Se riapre il file, una riscrittura fallita può lasciare intatto l'input originale.

Su Linux, `fs.protected_regular` può negare una scrittura `O_CREAT` sul file regolare di un altro utente in una directory sticky scrivibile da tutti. Questo comportamento è protettivo, ma un wrapper shell che ignora l'errore di scrittura può comunque continuare usando il file di attività originale. Verifica l'impostazione, il proprietario del file e la directory e se il wrapper si interrompe in caso di errore. Il percorso è un possibile caso di divulgazione di file solo se la regola sudo effettiva consente di eseguire il wrapper come utente privilegiato, il chiamante controlla l'input dell'attività e una destinazione di backup leggibile, e l'utility di backup include davvero le sorgenti protette. Durante l'enumerazione, esamina queste condizioni senza eseguire il backup.

### Wildcard negli argomenti di strumenti privilegiati per il traffico di rete

In una regola sudo per `tcpdump`, un `*` nel **pattern degli argomenti** può corrispondere a spazi e slash, quindi una restrizione che sembra limitare un percorso può comunque consentire testo aggiuntivo per le opzioni. È diverso da un wildcard nel percorso dell'eseguibile del comando; esamina l'intera regola RunAs e gli eventuali divieti successivi. Se è possibile iniettare opzioni, l'invocazione consentita e la [semantica delle opzioni di `tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) nella versione installata determinano se `-F`, `-V`, `-r`, `-w` o `-Z` forniscono una primitiva utile di lettura/scrittura. `-V` legge un elenco di nomi di file di cattura, non un dump generico di file arbitrari. AppArmor o un'altra policy MAC può impedire l'accesso ai file anche quando sudo consente il comando; la presenza di un file di profilo sul disco non dimostra che sia caricato o in modalità enforcing. Prima di giungere a una conclusione, esamina passivamente autorizzazioni e policy. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descrive la distinzione tra wildcard.

Anche una regola sudo eseguibile come root che elenca soltanto l'eseguibile `tcpdump`, senza restrizioni sugli argomenti, merita un esame. Il [manuale di tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` come comando post-rotazione quando `-C` o `-G` ruota una cattura salvata; `-Z` o un'impostazione predefinita in fase di compilazione possono rimuovere i privilegi prima dell'esecuzione di quel comando. Prima di considerare la regola un percorso di escalation, verifica la regola sudo effettiva, la build installata, il comportamento relativo alla rimozione dei privilegi e la possibilità che avvenga una rotazione. Una regola evidenziata è un caso candidato, non una prova dell'esecuzione di comandi come root.

### Wrapper Nmap eseguiti tramite sudo

Quando il percorso `nmap` consentito da sudo è un wrapper shell, esamina il percorso esatto consentito e ogni opzione che inoltra. Bloccare la grafia più nota `--script` non impedisce necessariamente il caricamento di codice NSE: [`--datadir` di Nmap](https://nmap.org/book/man-misc-options.html) seleziona i file di dati e NSE [carica `nse_main.lua`](https://nmap.org/book/nse-implementation.html) dalla directory di dati selezionata quando lo scripting è abilitato. Alcune build installate accettano anche grafie alternative delle opzioni lunghe: confronta quindi le restrizioni con il parser effettivo del binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) offre una superficie distinta di lettura dei file; gli errori del parser possono divulgarne il testo. Durante l'enumerazione, verifica la regola sudo effettiva, la logica del wrapper, la versione di Nmap, il controllo della directory e la policy MAC senza eseguire scansioni.

### Hook pull di Mercurial eseguiti tramite sudo

Un sorgente fisso in `sudo hg pull /fixed/source` lascia comunque che il repository **di destinazione** sia selezionato dalla directory di lavoro corrente, a meno che il comando non lo fissi con `-R`. Un repository di destinazione controllato dal chiamante può definire hook in `.hg/hgrc`, eseguibili come utente RunAs di sudo. [Mercurial ignora la configurazione del repository appartenente a un utente o gruppo non attendibile](https://mercurial-scm.org/help/topics/config); prima di considerarlo esecuzione di codice, esamina quindi gli utenti e i gruppi considerati attendibili dall'account RunAs e la directory di lavoro esatta. Per un esame passivo è sufficiente leggere la policy e la configurazione; non eseguire `pull` né invocare un hook.

### Hook pull di Git eseguiti tramite sudo

Per un'autorizzazione sudo esatta per `sudo git pull`, verifica anche il repository **di destinazione** selezionato dalla directory di lavoro. Un repository appartenente al chiamante può avere un hook `post-merge` eseguibile che viene eseguito con l'identità del processo Git quando un pull completa effettivamente un merge; [Git documenta questo hook](https://git-scm.com/docs/githooks) e [il comportamento di pull rispetto a merge e rebase](https://git-scm.com/docs/git-pull). Verifica la regola sudo effettiva e la CWD, il percorso attivo dell'hook e i relativi permessi, nonché la possibilità di effettuare un merge con nuovi commit. Un pull fallito, senza modifiche o basato solo su rebase non dimostra questo percorso tramite hook. Esamina policy e metadati del repository senza eseguire il pull privilegiato.

### Copie di archivi rsync eseguite tramite sudo

Per `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` nel **pattern degli argomenti di sudoers** può corrispondere agli spazi e consentire un'opzione aggiuntiva tra sorgente e destinazione. Questo è diverso dall'espansione dei nomi di file da parte della shell. Se il chiamante può popolare la sorgente e la destinazione è scrivibile dal processo rsync privilegiato, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) può richiedere una proprietà privilegiata mentre la modalità archive mantiene i bit di permesso, creando potenzialmente un file con SetUID e proprietà privilegiata. Verifica la semantica esatta dei [wildcard di sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versione di rsync, eventuali divieti successivi, `nosuid` sul filesystem e la policy MAC. Una regola corrispondente è un caso da esaminare, non la prova di un'escalation riuscita.

### Esportazione di regole packet-filter eseguita tramite sudo

Un'autorizzazione senza restrizioni, eseguibile come root, sia per `iptables` sia per `iptables-save` (o per la coppia corrispondente `ip6tables`) merita un esame della scrittura di file. Il match `comment` accetta testo di regola scelto dal chiamante, mentre `iptables-save -f` scrive il ruleset serializzato in un percorso selezionato.<sup>[[20]](#references)[[21]](#references)</sup> L'utilità di un payload dipende dal modo in cui il backend installato serializza i commenti e dalla possibilità che il file di destinazione accetti altre righe dell'esportazione; `iptables-save`, da solo, non fornisce contenuti arbitrari scelti dal chiamante. Verifica l'identità RunAs effettiva di sudo, gli argomenti e le esclusioni, l'estensione di match disponibile, il backend e i permessi della destinazione. Durante l'enumerazione, esamina l'autorizzazione senza modificare le regole del firewall né scrivere file.

### Directory di log privilegiata di Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) interessava le versioni di Below precedenti alla 0.9.0, che creavano una directory `/var/log/below` scrivibile da tutti. Se un servizio o un comando sudo consentito esegue come root una build vulnerabile, un utente che può scrivere e attraversare una directory di log non sticky potrebbe sostituire una voce di log con un symlink prima che il processo privilegiato la apra. Esamina lo stato delle patch del pacchetto installato, il percorso esatto di esecuzione privilegiata, l'accesso effettivo alla directory, il bit sticky e le ACL, nonché i metadati di `/var/log/below/error_root.log`. Un percorso scrivibile da tutti o una regola sudo, da soli, non dimostrano la catena completa. Una directory sticky o un backport del vendor modificano la valutazione. Durante l'enumerazione passiva, esamina solo i metadati: non è necessario creare un link né eseguire il programma privilegiato.

### Raccolta privilegiata di bundle di supporto da input scrivibili

Uno script di profilo di supporto consentito da `sudo` può leggere come root percorsi di log fissi e copiarne il contenuto in un archivio di profilo. Esamina lo script effettivo per individuare le letture di file, poi verifica se il chiamante può sostituire un percorso sorgente o una voce di una directory parent con un symlink. Se la lettura privilegiata segue il link e l'archivio risultante è leggibile dal chiamante, un file protetto può essere divulgato. Devono essere presenti sia l'autorizzazione sudo sia il percorso sorgente scrivibile, la lettura privilegiata e l'output leggibile; un log scrivibile o il nome del file di profilo, da soli, non bastano. Durante l'enumerazione, esamina i permessi effettivi e i metadati dei link senza sostituire file né generare un profilo. Le [indicazioni di supporto di Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentano lo script di profilo eseguito come root e il relativo archivio di output, mostrando perché gli input e l'accesso all'output di questi bundle devono essere limitati.

### Script Python di ripristino archivi eseguiti come root

Anche una regola sudo strettamente limitata per uno script Python di ripristino richiede di esaminare l'archivio di input. Se il chiamante può selezionare o sostituire l'archivio e lo script lo estrae come root con `tarfile.extractall(filter="data")`, verifica gli aggiornamenti di sicurezza dell'interprete prima di fidarti del filtro. CPython ha corretto diversi bypass dei filtri basati su symlink e hard link, tra cui CVE-2025-4517, nelle versioni 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. I backport delle distribuzioni possono correggere una versione precedente, quindi la sola versione dell'interprete mostrata non dimostra la vulnerabilità.<sup>[[16]](#references)[[17]](#references)</sup>

Per un esame passivo, leggi il comando sudo esatto e lo script, determina quale argomento seleziona l'archivio e verifica se l'utente corrente può scrivere nell'archivio o nella directory che lo contiene. Verifica separatamente la patch del vendor installata e la destinazione dell'estrazione; `filter="data"` non rende sicuro ogni archivio non attendibile.<sup>[[16]](#references)[[17]](#references)</sup>

### Loader di modelli di machine learning eseguiti tramite sudo

Una regola sudo che consente di selezionare un file `.pt`, `.pth` o `.ckpt` merita un esame quando uno script privilegiato passa quel file a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` o a un altro loader basato su pickle. Verifica la regola RunAs effettiva, se il chiamante può creare o sostituire il modello selezionato e il flusso effettivo degli argomenti attraverso eventuali wrapper shell fino all'helper Python. L'estensione `.pth` indica anche file di configurazione Python site non correlati, quindi la sola estensione non è prova del caricamento di un modello. L'analisi di un archivio o una scansione statica del pickle non dimostrano che il caricamento successivo sia sicuro; esamina il comportamento di [`weights_only` in base alla versione](https://docs.pytorch.org/docs/stable/notes/serialization.html) del loader e l'eventuale allowlist. Vedi le [note su pickle per ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). L'enumerazione passiva non deve mai caricare né estrarre il modello.

### Analisi di espressioni su input memorizzati eseguita tramite sudo

Uno script Python fisso eseguito come root tramite sudo può comunque valutare testo memorizzabile da un utente con privilegi inferiori nel database di un'applicazione. In TensorFlow, una chiamata a `preprocess_input_exprs_arg_string(value, safe=False)` seleziona un percorso `eval`; l'[avviso di sicurezza di TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descrive il parser non sicuro e la correzione apportata al chiamante da riga di comando. Una chiamata esplicita dell'applicazione con `safe=False` richiede un esame separato, anche se quel chiamante da riga di comando è stato corretto. Verifica la regola sudo effettiva, chi può modificare la riga di input specifica, se filtri o scoring consentono a quella riga di raggiungere la chiamata e il comportamento della funzione installata. Una versione di TensorFlow, un'autorizzazione sudo o un file di modello hardcoded non dimostrano da soli la catena. Esamina script e flusso dei dati passivamente; durante l'enumerazione non eseguire l'helper privilegiato né inviare espressioni di prova.

### Configurazione di needrestart consentita da sudo

`needrestart -c` carica un file di configurazione Perl scelto dal chiamante e ne valuta il contenuto. Se `sudo -l` consente di eseguire `needrestart` come root con argomenti che permettono `-c` e il chiamante può scegliere un file di configurazione leggibile in un percorso scrivibile, tale autorizzazione può portare all'esecuzione di codice root. Verifica RunAs e la regola esatta sugli argomenti di sudo; una regola che consente solo un elenco fisso di argomenti può bloccare questo percorso. È una questione distinta dalle vulnerabilità di needrestart nella scansione degli interpreti: aggiornare il pacchetto o disabilitare `interpscan` non rende sicura un'autorizzazione root senza restrizioni per `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Import Python eseguiti tramite sudo come un altro account

Un punto di ingresso Python fisso può importare comunque un modulo che il chiamante può modificare o sostituire, anche quando sudo esegue lo script come **utente di servizio non-root**. Per un import letterale come `from utils import status`, esamina `utils/__init__.py` e `utils/status.py` locali, oltre ai permessi della directory del pacchetto. Prima di considerare il file scrivibile un percorso di esecuzione, verifica il percorso degli import dello script, gli argomenti consentiti esatti da sudo e se l'azione pertinente raggiunge quell'import. Durante l'enumerazione, esamina file e permessi senza importare né eseguire lo script.<sup>[[2]](#references)[[3]](#references)</sup>

Una regola sudo esatta per `python3 /absolute/script.py` richiede soltanto che lo script sia leggibile; il file non deve essere eseguibile né avere una shebang. Esamina anche i moduli locali **mancanti**: se lo script importa un modulo il cui nome file può essere creato in una directory dello script scrivibile dal chiamante, Python potrebbe caricare quel file con l'identità RunAs. Verifica la regola sudo effettiva, il [percorso di ricerca dei moduli](https://docs.python.org/3/library/sys_path_init.html) effettivo dell'interprete, se il modulo è built-in o frozen e se l'import viene raggiunto. Una regola sudo diretta per lo script ha requisiti diversi per il bit di esecuzione e la shebang. Anche un wrapper distinto che aggiunge token forniti dal chiamante dopo `sudo -u account` richiede un esame del flusso degli argomenti: un altro `-u` in quei token è rilevante solo se la policy sudo invocata consente l'identità risultante. Le sole stringhe statiche non dimostrano nessuno dei due percorsi.

### Apache eseguito tramite sudo con configurazione controllata dal chiamante

Se una regola sudo consente un'invocazione privilegiata di `apachectl`, `apache2ctl` o `httpd` con un file di configurazione `-f` controllato dal chiamante, esamina quel file e i permessi della directory parent. La direttiva Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) richiede un nome di modulo seguito dal **nome file del modulo**; anche [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) carica un file. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) possono estendere la configurazione o esporre contenuti di file tramite errori. Un wrapper personalizzato può convalidare questi percorsi, rimuovere i privilegi o limitare gli argomenti; una configurazione scrivibile è quindi un caso da esaminare, non una prova di esecuzione di codice. Prima di giungere a una conclusione, verifica la canonicalizzazione dei percorsi, i symlink e l'analisi delle direttive.

### nginx eseguito tramite sudo con configurazione controllata dal chiamante

Una regola `nginx` senza restrizioni, eseguibile come root, può consentire a [`-c` di selezionare un'altra configurazione](https://nginx.org/en/docs/switches.html). Esamina gli argomenti e le esclusioni sudo esatti, se il chiamante può fornire la configurazione e se il master o i worker risultanti mantengono l'accesso a percorsi protetti. Un `root` scelto insieme a `autoindex` può esporre file tramite un nuovo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) può offrire un percorso privilegiato di scrittura dei file, ma il modulo DAV non è compilato per impostazione predefinita e vanno verificati la sua presenza, l'accessibilità del listener, i permessi dei file e il comportamento dei file temporanei. Anche la direttiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) può puntare a un file scelto; scrivere log in un file di configurazione sensibile, come `/etc/ld.so.preload`, diventa un percorso di escalation solo se c'è un writer privilegiato effettivo e il record di log è controllabile. L'evidenziazione dell'eseguibile in `sudo -l` è un indizio da esaminare, non la prova che uno di questi percorsi funzioni. Durante l'enumerazione passiva, non avviare né riconfigurare nginx.

### Confronto di pattern nei prompt Bash privilegiati

Quando uno script Bash consentito da sudo legge un valore dal chiamante e lo verifica con `[[ "$expected" == $entered ]]`, Bash interpreta come pattern l'operando destro non quotato. Un wildcard può quindi far superare il confronto senza conoscere il valore atteso. Mettere l'operando tra virgolette (`[[ "$expected" == "$entered" ]]`) lo rende un confronto letterale tra stringhe. Esamina la regola sudo esatta, se il prompt è raggiungibile e cosa fa lo script dopo il confronto; la sola sintassi non dimostra un percorso sfruttabile. Durante l'enumerazione, evita di stampare il valore atteso. Vedi il [riferimento ai costrutti condizionali di Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper eseguiti tramite sudo che scaricano ed eseguono un file

Un'autorizzazione sudo senza restrizioni per un helper personalizzato eseguibile come root merita un esame del flusso dei dati se accetta un URL scelto dal chiamante, scrive la risposta su disco e poi invoca quel file tramite un interprete o una shell. [Sudoers consente argomenti arbitrari quando la voce del comando non ne elenca](https://man7.org/linux/man-pages/man5/sudoers.5.html); il percorso fisso dell'eseguibile non limita ciò che gli argomenti possono selezionare. Verifica la convalida effettiva dell'URL, il percorso di output, il ramo di successo e la successiva esecuzione nell'helper installato. Un import libcurl corrispondente o una stringa stampabile, da soli, non dimostrano questa catena.

Anche un nome di file di output fisso può essere sostituito tra scrittura ed esecuzione quando l'helper usa un **percorso relativo in una directory di lavoro controllata dal chiamante**. La rinomina o sostituzione di un file di proprietà di root è regolata dall'accesso in scrittura/ricerca sulla directory e dagli eventuali vincoli del bit sticky, non solo dalla modalità del file; vedi [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifica se l'helper riapre poi il percorso o usa il descrittore già aperto e se si sposta in una directory attendibile prima di scrivere. Esamina passivamente la policy sudo, l'helper e i metadati della directory; durante l'enumerazione non eseguire il download privilegiato né tentare una race.

Un helper di download eseguito tramite sudo come root può inoltre esporre un'injection di **argomenti** se compone una stringa di comando Bash come `curl <caller input> -o <fixed output>`. Un filtro che rifiuta gli spazi lascia comunque disponibile [l'espansione delle parentesi graffe di Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): gli elementi separati da virgole e non quotati possono diventare argomenti curl distinti. Se l'input raggiunge curl prima dell'opzione fissa `-o`, un'opzione di output fornita dal chiamante può selezionare la destinazione per il primo URL, con l'identità dell'helper; [curl associa le opzioni di output agli URL nell'ordine in cui compaiono](https://curl.se/docs/manpage.html#-o). Verifica la shell esatta, le virgolette, la convalida dell'input, la regola sudo effettiva, l'ordine degli argomenti di curl e gli schemi URL supportati, nonché se il chiamante controlla i byte scaricati o può leggere il risultato. Un eseguibile impacchettato con PyInstaller può contenere logica applicativa Python, ma il marker di packaging o una stringa `curl`, da soli, non dimostrano questo flusso di dati. Se autorizzato, esamina una copia offline e circoscritta; durante l'enumerazione ordinaria, non eseguire l'helper né recuperare dati scelti dall'attaccante.

Uno script shell eseguito tramite sudo come root che chiama [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) sceglie soltanto un nome non usato: **non** crea il file. Se in seguito lo script crea quel file in una directory modificabile da un altro utente, lo riapre e ne aggiunge il contenuto a una destinazione protetta come `authorized_keys` di root, esamina il possibile rischio di race sul file temporaneo. Verifica la regola sudo esatta, la proprietà della directory e del file, la sequenza di creazione e riapertura, le protezioni del kernel e se la scrittura privilegiata usa davvero byte controllati dall'attaccante. Una stringa `mktemp -u` o la sola presenza di `/tmp` scrivibile non dimostrano la race. Durante l'enumerazione, esamina lo script e i metadati del percorso senza eseguirlo né tentare una race sul file temporaneo.

## Note difensive

- Evita di autorizzare interpreti o editor interattivi tramite sudo.<sup>[[1]](#references)</sup>
- Preferisci wrapper fissi, di proprietà di root, che eseguono una singola azione amministrativa circoscritta.<sup>[[1]](#references)[[2]](#references)</sup>
- Se un interprete è inevitabile, limita il percorso esatto dello script e impedisci argomenti controllati dall'utente, import scrivibili, `PYTHONPATH` e la conservazione di un ambiente non sicuro.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se è necessario modificare file, limita il percorso esatto e valuta `sudoedit` con versioni di sudo aggiornate e una gestione rigorosa dell'ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Esamina `SETENV`, `env_keep`, directory di lavoro scrivibili, percorsi di moduli/import scrivibili, `NOEXEC`, `use_pty` e logging, ma non considerarli una sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
