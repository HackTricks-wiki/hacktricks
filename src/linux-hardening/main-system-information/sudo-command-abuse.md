## Interpretery dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interpreter jako root, należy traktować to jako bezpośrednie wykonanie kodu. Interpretery służą do wykonywania dowolnego kodu, więc reguła zezwalająca na użycie plików binarnych `python3`, `perl`, `ruby`, `lua`, `node` lub podobnych zwykle jest równoważna wykonywaniu poleceń jako root, chyba że argumenty są ściśle ograniczone i weryfikowane.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Typowy przebieg analizy: najpierw wyświetl uprawnienia użytkownika, a następnie wykonaj instrukcję Pythona za pomocą opcji `-c` interpretera.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Poniżej przedstawiono inne przykłady interpreterów; wymienione interpretery dokumentują wykonywanie kodu inline lub korzystanie z API procesów potomnych.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Dokładna ścieżka ma znaczenie. Jeśli reguła sudo zezwala na `/usr/bin/python3`, podczas walidacji użyj dokładnie tej ścieżki.<sup>[[2]](#references)</sup>

Glob plików wykonywalnych w sudo, taki jak `/usr/bin/python*`, może również dopuszczać Python 2 w przypadku skryptu napisanego dla Python 3. Jeśli skrypt wywołuje `input()` z tekstem kontrolowanym przez wywołującego, [Python 2 evaluates that text as an expression](https://docs.python.org/2/library/functions.html#input); jawne wywołanie interpretera nadpisuje shebang skryptu. Zanim uznasz to za ścieżkę do wykonania kodu, zweryfikuj zainstalowane pasujące pliki binarne, efektywną tożsamość RunAs i politykę argumentów, odmowy oraz dostępne wejście.

Stała ścieżka skryptu w regule sudo umożliwiającej działanie jako root nie ogranicza tego, co wykonuje skrypt. W przypadku czytelnego wrappera Bash sprawdź, czy jego pierwsze wykonywane polecenie używa nieujętego w cudzysłów parametru pozycyjnego, takiego jak `$1`, jako **słowa polecenia**, gdy sudo zezwala na argumenty wybrane przez wywołującego. Potwierdź efektywną tożsamość RunAs, politykę haseł i argumentów, późniejsze odmowy oraz faktycznie wykonywaną gałąź skryptu; `NOEXEC`, stała bezpieczna lista argumentów lub wrapper, który weryfikuje polecenie, mogą zmienić rezultat. Podczas enumeracji przeanalizuj krótki skrypt statycznie, zamiast uruchamiać go z testowym poleceniem.

Nieograniczona reguła sudo umożliwiająca działanie jako root dla `dotnet` również wymaga sprawdzenia pod kątem użycia jako interpretera. Jeśli zainstalowano .NET SDK, [`dotnet fsi` runs F# code interactively or from a script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), a [`dotnet run` executes a project from source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Najpierw potwierdź efektywną tożsamość RunAs i dokładną politykę argumentów: reguła ograniczona do konkretnego bezpiecznego podpolecenia lub zaufanej aplikacji oznacza inne uprawnienie, a instalacja zawierająca tylko runtime może nie udostępniać poleceń SDK. Sama nazwa pliku wykonywalnego jest wskazówką do sprawdzenia, a nie dowodem na możliwość wykonania kodu.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Edytory dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interaktywny edytor jako root, traktuj go jako powierzchnię umożliwiającą wykonywanie poleceń, a nie nieszkodliwe uprawnienie do edycji plików. Edytory często mogą wykonywać polecenia powłoki, odczytywać dowolne pliki, zapisywać dowolne pliki lub wywoływać zewnętrzne narzędzia z poziomu edytora.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Typowy przebieg analizy: wyświetl uprawnienia użytkownika, a następnie uruchom pod sudo każdy dozwolony edytor lub pager.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Wykonywanie poleceń za pomocą nano

Jeśli użycie `nano` przez sudo jest dozwolone, wykonywanie poleceń może być możliwe z poziomu interfejsu edytora.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Następnie podaj polecenie, takie jak `id` lub `/bin/sh`, w wierszu polecenia nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Jeśli interaktywna powłoka nie ma dostępnych strumieni terminala, ta forma przekierowania kieruje jej standardowe wyjście i strumień błędów do deskryptora 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Dokładna sekwencja klawiszy może się różnić w zależności od wersji nano i opcji kompilacji, ale problem z bezpieczeństwem pozostaje ten sam: edytor działa jako root i może uruchamiać zewnętrzne polecenia.<sup>[[1]](#references)[[12]](#references)</sup>

### Inne typowe sposoby ucieczki z edytora

Edytory w stylu Vima często umożliwiają wykonywanie poleceń za pomocą `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Programy stronicujące, takie jak `less`, mogą również umożliwiać uruchomienie powłoki.<sup>[[14]](#references)</sup>

Regułę sudo zezwalającą na uruchamianie `apport-cli` jako root należy sprawdzić pod kątem stronicowania. Podatne wersje Apport mogły otwierać raport o awarii w `less` z rozmiarem terminala ustawianym przez atakującego; pager mógł wtedy udostępnić powłokę root, jeśli spełnione były specjalne warunki dotyczące sudo i pagera. Zanim uznasz daną wersję za podatną, sprawdź efektywną regułę sudo, konfigurację pagera oraz poprawkę w pakiecie danej dystrybucji. Podczas passive enumeration odczytuj metadane pakietu i polityki bez wywoływania awarii ani otwierania raportu z uprawnieniami. [Rekord CVE Ubuntu](https://ubuntu.com/security/CVE-2023-1326) zawiera wersje pakietów z poprawkami dla poszczególnych wydań, w tym poprawki backportowane.

```text
!/bin/sh
```

## Inne zagrożenia związane z regułami sudo i doas

Zacznij od `sudo -l`, `sudo -V` i wszelkich mających zastosowanie zasad `doas`. Analizuj łącznie dozwolone polecenie, użytkownika, na którego można się przełączyć, argumenty, środowisko i ustawienia domyślne. Możliwość uruchamiania poleceń jako nie-rootowe konto usługi nadal może dać dostęp do plików tego konta lub otworzyć drogę do roota.

Skrypt Python dozwolony przez sudo pod stałą ścieżką może nadal uruchomić polecenie powłoki z tożsamością wskazaną przez RunAs, jeśli dane wejściowe kontrolowane przez użytkownika są łączone z [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Lista blokowanych znaków interpunkcyjnych powłoki nie wystarcza, by uznać skrypt za bezpieczny: [powłoka rozpoznaje również podstawianie poleceń `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Sprawdź, czy dozwolone argumenty trafiają do gałęzi obsługującej dane wejściowe, czy dane wejściowe docierają do polecenia powłoki bez bezpiecznej walidacji oraz czy skuteczna polityka sudo pozwala na użycie zamierzonego użytkownika RunAs. Sama ścieżka skryptu lub wywołanie `os.system()` to jedynie wskazówka do analizy; sprawdź kod źródłowy bez uruchamiania skryptu z podwyższonymi uprawnieniami.

Skuteczne uprawnienie sudo do uruchamiania `chattr` jako root może usunąć atrybut niezmienności (`i`) pliku, ale samo w sobie nie daje prawa zapisu ani nowej tożsamości. [Podręcznik `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) informuje, że ten atrybut blokuje modyfikacje i może go zmienić wyłącznie root lub proces z `CAP_LINUX_IMMUTABLE`. Sprawdź dokładną politykę argumentów sudo i obsługę systemu plików, a następnie osobno zweryfikuj, czy użytkownik może zapisywać do pliku po usunięciu atrybutu i czy korzysta z niego proces o wyższej tożsamości. Na przykład zastąpienie powłoki logowania wymaga również zaakceptowanych danych uwierzytelniających konta docelowego i faktycznego logowania za pośrednictwem tej powłoki. Podczas rekonesansu sprawdź politykę, atrybuty plików i uprawnienia, nie zmieniając ich.

Jeśli sudo żąda zarówno hasła, jak i jednorazowego kodu, traktuj te wymagania niezależnie od uprawnień do uruchomienia polecenia. Czytelny plik `.google_authenticator` zawiera poufny materiał klucza, a stary hash hasła aplikacji lub bazy danych jest jedynie kandydatem na obecne hasło konta; żaden z nich nie dowodzi, że drugi czynnik jest akceptowany przez skuteczną konfigurację PAM. Po uzyskaniu upoważnienia sprawdź dokładny użytkownik RunAs i argumenty: nieograniczone uprawnienie do uruchomienia RubyGems `gem` jako root może udostępniać jego polecenie edytora ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ale ograniczone uprawnienie lub nieudane uwierzytelnienie — nie. Pasywny rekonesans powinien wskazywać ścieżki i politykę, nie ujawniając klucza, nie odzyskując hasła, nie generując kodu ani nie uruchamiając uprzywilejowanego polecenia.

Nieograniczone uprawnienie sudo do uruchomienia `knife` jako root wymaga analizy na poziomie interpretera: [Chef informuje, że `knife exec -E` lokalnie interpretuje ciąg Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Sprawdź, czy skuteczna reguła sudo zezwala na podpolecenie `exec` i przekazany przez użytkownika argument `-E`, zamierzoną tożsamość RunAs oraz wszelkie pasujące zakazy poleceń lub stałe argumenty. Zainstalowany plik binarny lub reguła ograniczona do innych podpoleceń to jedynie wskazówki. Pasywny rekonesans powinien wykazać regułę bez uruchamiania `knife`.

Dokładne uprawnienie sudo do uruchomienia interaktywnego `msfconsole` jako root również wymaga uwagi: [GTFOBins opisuje jego konsolę `irb`](https://gtfobins.org/gtfobins/msfconsole/), która może dziedziczyć tożsamość sudo. Sprawdź skutecznego użytkownika RunAs, dozwoloną listę argumentów, zakazy poleceń, `NOEXEC` i inne ograniczenia, zachowanie zainstalowanej konsoli oraz to, czy użytkownik może przekazywać dane wejściowe w trybie interaktywnym. Samo wyróżnienie ścieżki to jedynie wskazówka do analizy; podczas pasywnego rekonesansu nie uruchamiaj konsoli.

We FreeBSD nawet reguła sudo ograniczona do poleceń `pkg update` i `pkg install *` wykonywanych jako root wymaga analizy zaufania do repozytorium. Sprawdź, czy użytkownik może zapisywać do `/etc/hosts` i czy *skuteczna*, włączona konfiguracja repozytorium używa nazwy hosta HTTP z `signature_type: none`. [Podręcznik `pkg.conf` FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) informuje, że `none` wyłącza sprawdzanie podpisów; samo `pkg+http` tego nie dowodzi. [Pakiet może zawierać skrypty instalacyjne](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), więc użytkownik, który faktycznie kontroluje punkt końcowy repozytorium i może wybrać pakiet, może przekroczyć granicę uprawnień roota. Zanim wyciągniesz taki wniosek, sprawdź nadpisania repozytorium, rozwiązywanie SRV/lustr, skuteczne argumenty sudo, wybór pakietu i wykonywanie skryptów. Sprawdź politykę i niewielkie lokalne pliki konfiguracyjne bez przekierowywania nazw ani uruchamiania `pkg` podczas rekonesansu.

Reguła sudo zezwalająca na `apt-get update` i `apt-get upgrade` jako root również wymaga analizy zaufania do repozytorium, jeśli sudo zachowuje kontrolowane przez użytkownika `http_proxy`. Sprawdź, czy skuteczna konfiguracja APT rzeczywiście używa tej zmiennej i na które włączone repozytoria może ona wpływać; sam proxy nie może zastąpić pakietów z archiwum uwierzytelnionego zaufanym kluczem podpisu. [Podręcznik transportu HTTP APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) opisuje priorytety proxy, a [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — sprawdzanie podpisów, nadpisania dla niezaufanych repozytoriów i potwierdzanie instalacji pakietów nieuwierzytelnionych. Sprawdź dokładnego użytkownika RunAs i argumenty sudo, politykę uwierzytelniania repozytorium, ewentualne wymagane potwierdzenie interaktywne oraz to, czy wybrana aktualizacja uruchamia skrypty pakietu jako root. Analizuj politykę i lokalną konfigurację pasywnie; podczas rekonesansu nie przekierowuj ruchu pakietów ani nie uruchamiaj aktualizacji.

Reguła sudo zezwalająca na uruchomienie `snap install` jako root może tworzyć granicę między pakietem a kodem, jeśli jej argumenty pozwalają użytkownikowi wybrać lokalny snap i pobłażliwy tryb instalacji. [Dokumentacja Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) informuje, że `--dangerous` pomija sprawdzanie atestacji lokalnego snapa, a `--devmode` łagodzi ograniczenia; [hook instalacyjny może zostać uruchomiony podczas pierwszej instalacji](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Zanim stwierdzisz, że możliwy jest dostęp do chronionych plików hosta, sprawdź dokładną politykę argumentów i RunAs sudo, kto kontroluje plik snapa, czy zainstalowany snapd akceptuje te tryby oraz tożsamość i ograniczenia hooka. Sam plik binarny `snap` lub reguła wyglądająca na wieloznaczną nie dowodzą istnienia takiego łańcucha. Pasywny rekonesans nie powinien instalować pakietu ani uruchamiać jego hooka.

W przypadku dokładnej reguły sudo zezwalającej na uruchomienie jako **nie-rootowe** konto niestandardowego pliku binarnego odczytującego dane uwierzytelniające najpierw sprawdź dozwolony plik i jego uprawnienia bez uruchamiania go. Wbudowane hasło może być widoczne tylko jako znaki szerokie; [dokumentacja GNU `strings` opisuje odczyt 16-bitowego little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Widoczny ciąg nie dowodzi, że jest akceptowanym hasłem ani że gałąź sukcesu ujawnia aktualne dane uwierzytelniające. Osobno sprawdź zachowanie pliku binarnego, dostęp konta docelowego do chronionych danych, ważność danych uwierzytelniających i ewentualne późniejsze przejście do innego konta lub grupy. Jeśli konto należy do grupy `docker`, sprawdź dostęp do gniazda i tożsamość demona — rootful lub rootless — zanim wyciągniesz wniosek o dostępie root do hosta; [Docker opisuje konsekwencje uprawnień tej grupy](https://docs.docker.com/engine/install/linux-postinstall/). Rutynowy rekonesans powinien wykazać regułę sudo i członkostwo w grupie bez uruchamiania pliku binarnego ani zrzucania jego ciągów.

Wieloznaczna reguła sudo dla skryptów konserwacyjnych aplikacji wymaga analizy wykraczającej poza samą ścieżkę skryptu. Sprawdź, czy dozwolony skrypt przyjmuje nieograniczone argumenty lub odczytuje ustawienia zapisywalne przez konto aplikacji o niższych uprawnieniach, a następnie prześledź przepływ tych wartości do poleceń powłoki lub środowiska podprocesu. Na przykład ZoneMinder: [`zmupdate.pl` składa polecenie `mysqldump` i wykonuje je przez `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), a [`zmdc.pl` kopiuje ustawienie `ZM_LD_PRELOAD` do `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) przed uruchomieniem demonów. Reguła sudo zezwalająca na uruchomienie któregoś z tych skryptów jako root może przekraczać granicę zaufania, jeśli odpowiednie dane wejściowe są kontrolowane przez użytkownika i docierają do tego kodu w zainstalowanej wersji. Sprawdź skuteczną regułę sudo, uprawnienia do konfiguracji aplikacji i kod źródłowy skryptu; wieloznacznik lub ustawienie to jedynie wskazówka do analizy, a nie dowód wykonania.

- `SETENV`, `env_keep`, `secure_path` i `LD_PRELOAD` mogą zamienić skądinąd wąskie polecenie w możliwość przejęcia importu, biblioteki lub `PATH`. Zobacz [przewodnik po zmiennych środowiskowych](../linux-basics/linux-environment-variables.md) oraz [nadużycia SUID/linkera](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Dokładne uprawnienie `SETENV` do uruchomienia jako root wrappera powłoki wymaga również analizy jednego kroku, jeśli wrapper uruchamia stały skrypt Python z dosłownym importem. `secure_path` ogranicza wyszukiwanie poleceń powłoki, a nie wyszukiwanie modułów Pythona przez [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` i `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) każą Pythonowi ignorować tę zmienną środowiskową. Zanim uznasz to za wykonanie kodu, sprawdź skuteczne tagi i zakazy sudo, gałąź wrappera, opcje interpretera, rozwiązywanie importu oraz katalog wyszukiwania, do którego użytkownik może zapisywać. Krótkie skrypty analizuj statycznie; nie uruchamiaj uprzywilejowanego wrappera.

Dokładna reguła sudo zezwalająca na `neofetch ""` jako root może nadal wczytać konfigurację powłoki, jeśli odpowiednie ustawienia domyślne sudo zachowują kontrolowane przez użytkownika `XDG_CONFIG_HOME`. [Loader konfiguracji Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) dołącza `neofetch/config.conf` lub `neofetch/config` z tego katalogu; pusta lista argumentów nie zapobiega temu wyszukiwaniu. Sprawdź zainstalowany loader, skuteczną politykę RunAs i argumentów, ewentualne zakazy poleceń, czy sudo rzeczywiście zachowuje wybraną zmienną dla tego polecenia oraz czy użytkownik kontroluje ścieżkę do czytelnego pliku konfiguracyjnego. Zachowana zmienna lub zainstalowany Neofetch to jedynie wskazówki do analizy. Sprawdź politykę i metadane plików bez uruchamiania uprzywilejowanego polecenia ani wyświetlania zawartości konfiguracji; zobacz [obsługę środowiska przez sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Nieograniczona reguła sudo zezwalająca na uruchomienie `facter` jako root wymaga osobnej analizy niestandardowych factów. [Puppet informuje](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), że `--custom-dir` wczytuje pliki Ruby z factami z wybranego katalogu. Sprawdź, czy dokładna reguła sudo zezwala na tę opcję, czy zainstalowany Facter ją akceptuje i czy użytkownik kontroluje katalog. Wynik mogą zmienić reguła ze stałymi argumentami, jawny zakaz polecenia lub wyłączone niestandardowe facty. Pasywny rekonesans powinien wykazać potencjalną regułę bez uruchamiania Facter ani odczytywania zawartości plików z factami.

W przypadku dokładnej reguły sudo zezwalającej na skrypt jako root i obejmującej `SETENV` sprawdź niekwalifikowane nazwy poleceń, takie jak `find`, oraz skuteczne `PATH` po zastosowaniu polityki sudo i inicjalizacji skryptu. Plik Bash dołączony przez `source` może również wykonać `enable -n [`: [Bash wyszukuje wtedy zewnętrzne `[` przez `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), gdy skrypt później używa tego polecenia. Sprawdź odpowiednie [reguły środowiska i `secure_path` w sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), ewentualne wpisy `NOSETENV`/`NOEXEC` lub zakazy, przepływ skryptu i dołączanych plików oraz katalog wyszukiwania, do którego użytkownik może zapisywać i z którego można uruchamiać pliki. Czytelny skrypt zawierający niekwalifikowane polecenie to wskazówka do analizy, a nie dowód uprzywilejowanego wykonania; przejrzyj go bez uruchamiania reguły sudo.

Jeśli skrypt następnie przekazuje odpowiedź do parsera XML rozwiązującego encje zewnętrzne, złośliwa odpowiedź może ujawnić pliki dostępne dla uprzywilejowanego procesu. Sprawdź dokładną politykę środowiska sudo, wykluczenia `no_proxy`, żądany URL, konfigurację parsera i miejsce docelowe danych wyjściowych; sama zmienna proxy lub parser XML nie stanowią podatności. [Dokumentacja zmiennych środowiskowych proxy dla curl](https://everything.curl.dev/usingcurl/proxies/env.html) opisuje działanie tych zmiennych. Podczas pasywnego rekonesansu nie wykonuj żądań sieciowych ani nie parsuj złośliwego XML.
- Skrypt sudo uruchamiany jako root, który tworzy plik PostScript z danymi zależnymi od użytkownika, a następnie uruchamia `ps2pdf -dNOSAFER`, wymaga osobnej analizy przepływu danych wejściowych. Dokumentacja Ghostscript informuje, że ta flaga wyłącza SAFER do czasu wywołania `.setsafe`, pozwalając na operacje na plikach w granicach uprawnień procesu systemu operacyjnego. Zapytanie SQL złożone z argumentu użytkownika może przekazać kontrolowane przez atakującego wiersze do szablonu PostScript, ale samo zapytanie lub wywołanie `ps2pdf` nie dowodzą, że dane trafiają do wykonywalnej składni PostScript. Sprawdź skuteczną regułę sudo, dokładny przepływ od danych wejściowych do szablonu, ewentualne escapowanie, zachowanie zainstalowanego Ghostscript oraz to, czy SAFER zostaje ponownie włączony przed interpretacją dokumentu. Podczas pasywnego rekonesansu nie uruchamiaj uprzywilejowanej konwersji. Zobacz [dokumentację `-dNOSAFER` Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).

W przypadku konkretnej reguły trzeba sprawdzić, czy ta gałąź jest osiągalna i czy środowisko jest faktycznie zachowywane.<sup>[[2]](#references)[[22]](#references)</sup>

Wywołania takie jak `pdb.set_trace()` lub `pdb.post_mortem()` pozwalają wykonywać instrukcje Pythona w kontekście debugowanego procesu, jeśli użytkownik może dotrzeć do punktu przerwania lub obsługi wyjątku **i kontroluje strumień wejściowy debuggera**. Sprawdź dokładną regułę sudo RunAs, uwierzytelnianie i warunki gałęzi, możliwość wystąpienia wyjątku, właściciela terminala/wejścia oraz to, czy debugger działa w tym samym uprzywilejowanym procesie. Żądanie przez gniazdo, które wywołuje wyjątek, samo w sobie nie daje dostępu do debuggera podłączonego do innego terminala. [Dokumentacja Pythona opisuje ewaluację instrukcji przez debugger i tryb post-mortem](https://docs.python.org/3/library/pdb.html); podczas rekonesansu analizuj skrypt statycznie, zamiast wywoływać uprzywilejowany handler.
- Skrypt Python dozwolony przez sudo może również odczytać pole profilu z bazy danych lub gniazda Unix i dopisać je do ciągu, który później staje się **ciągiem formatującym** dla `str.format()`. [Pola podstawienia mogą odwoływać się do atrybutów i kluczy mapowań](https://docs.python.org/3/library/string.html#format-string-syntax), więc kontrolowane przez atakującego pole może badać obiekty przekazane do `format()` i ujawniać dostępne z nich dane, jeśli wynik jest wyświetlany lub zapisywany w miejscu czytelnym dla użytkownika. Sprawdź skuteczną tożsamość sudo RunAs, prawo zapisu do konkretnego rekordu, przepływ danych do ciągu formatującego, przekazane obiekty i widoczność danych wyjściowych. Nie oznacza to automatycznego wykonania kodu; inna sytuacja zachodzi, gdy ciąg formatujący jest zaufany, a kontrolowane są jedynie *wartości*. Ujawniony sekret umożliwia przejście na konto systemu operacyjnego tylko wtedy, gdy to konto go akceptuje. Sprawdź skrypt i uprawnienia do gniazda bez wywoływania uprzywilejowanej operacji.

Jeśli wrapper włącza też `protocol.ext.allow=always` w Git, zdalne źródło `ext::` może uruchomić zewnętrzny helper. Sprawdź dokładne argumenty sudo, źródło URL-a, wersję pakietu GitPython i status poprawek dostawcy oraz to, czy wrapper jawnie dopuszcza niebezpieczne protokoły. GitPython dodał [domyślną ochronę przed niebezpiecznymi protokołami](https://github.com/gitpython-developers/GitPython/commit/2625ed9) w wersji 3.1.30; wersja pliku wykonywalnego `git` to osobna informacja. Pasywna analiza powinna ograniczyć się do reguły i fragmentu kodu źródłowego, bez uruchamiania klonowania.
- Uprawnienie sudo do uruchamiania narzędzia CLI klonującego repozytoria jako inne konto może udostępnić osobną ścieżkę wstrzyknięcia ciągu powłoki. Prześledź, czy wybrany przez użytkownika argument repozytorium trafia do Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) lub innego mechanizmu budującego polecenie powłoki bez bezpiecznego rozdzielenia argumentów; Node `exec` przekazuje ciąg polecenia do powłoki. Sprawdź dokładnego użytkownika RunAs, dozwolone podpolecenia i argumenty, kod zainstalowanego wrappera oraz walidację danych wejściowych. Sama nazwa narzędzia repozytoryjnego lub nieograniczona reguła sudo nie dowodzą wstrzyknięcia polecenia. Podczas rekonesansu sprawdź wrapper bez uruchamiania uprzywilejowanego klonowania.
- Niestandardowy wrapper należący do roota może wyglądać na bezpieczny, bo jego pliki binarne i skrypty nie są zapisywalne, ale decyzja o wykonaniu uprzywilejowanej operacji może zależeć od flagi, lokalnej wartości API lub stanu usługi, które może zmienić użytkownik bez uprawnień. Prześledź każde takie sprawdzenie aż do danych wejściowych i kontroli autoryzacji. Podczas rekonesansu sprawdź konfigurację i uprawnienia bez zmieniania stanu operacyjnego; wywołanie `systemd-run` wewnątrz wrappera ma znaczenie tylko wtedy, gdy można wpłynąć na warunek jego wykonania.
- Klient kopii zapasowych dozwolony przez sudo jako root może akceptować wybrany przez użytkownika plik konfiguracyjny, na przykład przez `npbackup-cli -c`. Sprawdź dokładnego użytkownika wykonania i dozwolone argumenty, a następnie to, czy użytkownik kontroluje ścieżkę konfiguracji, ścieżki źródeł kopii zapasowej oraz opcje repozytorium lub odczytu/przywracania. Zaszyfrowany sekret repozytorium w czytelnym pliku konfiguracyjnym może nadal być użyteczny dla klienta, ale sama reguła nie dowodzi dostępu do repozytorium ani ujawnienia plików roota. Zweryfikuj uprawnienia bez uruchamiania kopii zapasowej ani zrzucania jej zawartości.

Jeśli reguła sudo pozwala użytkownikowi o niższych uprawnieniach uruchomić restic jako root z wybranym przez niego poleceniem pobierającym hasło i podpoleceniem, które go wymaga, helper może zostać uruchomiony jako root. Zanim uznasz to za ujawnienie, sprawdź skuteczną politykę sudo, dostęp do backendu, hasło repozytorium i uprawnienia wynikowych obiektów. Zapisany w kopii klucz SSH umożliwia logowanie tylko wtedy, gdy konto docelowe go akceptuje. Podczas pasywnej analizy nie uruchamiaj kopii zapasowej.
- Nieograniczone niestandardowe polecenie konserwacyjne lub kopii zapasowej może akceptować ścieżkę wyjściową albo udostępniać własny harmonogram zadań. W przypadku harmonogramu sprawdź tożsamość używaną do wykonywania, dane wejściowe polecenia oraz ewentualne dodatkowe zabezpieczenie hasłem lub autoryzacją. Sprawdź, czy użytkownik może podmienić ten plik i czy jego pola źródła oraz miejsca docelowego sterują uprzywilejowanym pobraniem lub kopiowaniem. URL wskazujący lokalny plik może ujawnić dane dostępne wyłącznie kontu RunAs sudo; kontrolowane przez użytkownika źródło w połączeniu z chronionym miejscem docelowym może umożliwić zapis. Sprawdź obsługę URL-i przez zainstalowany program, kontrolę ścieżki docelowej, skuteczną regułę sudo i dostęp do danych wyjściowych. Sama zapisywalna ścieżka konfiguracji w `/tmp` to jedynie wskazówka do analizy, więc sprawdź plik binarny i metadane plików bez uruchamiania uprzywilejowanego transferu.

Na przykład reguła sudo zezwalająca jako root na `node /opt/scripts/*.js` może pozwolić użytkownikowi wskazać plik JavaScript poza `/opt/scripts`, jeśli podana nazwa nadal zaczyna się od `/opt/scripts/`, a ścieżka rozwiązuje się przez segmenty katalogów nadrzędnych. To **wzorzec argumentu**; wzorzec ścieżki pliku wykonywalnego Node ma inne reguły dopasowywania ukośników. Przed stwierdzeniem możliwości wykonania kodu sprawdź skuteczną regułę, późniejsze zakazy, rozwiązywanie ścieżki, kontrolę nad plikiem docelowym oraz ewentualne ograniczenia sudoers dotyczące wyrażeń regularnych lub sum kontrolnych. Zobacz [reguły wieloznaczników sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) i [dokumentację wiersza poleceń Node](https://nodejs.org/api/cli.html).
- Programy archiwizujące i inne narzędzia mogą mieć haki uruchamiania poleceń. Sprawdź dokładne dozwolone argumenty w [GTFOBins](https://gtfobins.github.io/), zamiast zakładać, że polecenia mogą uruchamiać wyłącznie powłoki lub interpretery.
- Nieograniczona reguła sudo zezwalająca na `qpdf` jako root może ujawnić uprzywilejowany plik przez załączniki PDF: qpdf 10.2 i nowsze obsługują `--empty` oraz `--add-attachment file ... --` z wyjściowym plikiem PDF. Jeśli uprzywilejowany proces może odczytać wybrane źródło i zapisać PDF w ścieżce dostępnej użytkownikowi, wynik może zawierać bajty źródła. Zanim uznasz ujawnienie pliku za możliwe, sprawdź skuteczne argumenty i wykluczenia sudo, wersję qpdf, dostęp do źródła oraz ścieżkę wyjściową. Odczyt klucza SSH roota jest przydatny do logowania tylko wtedy, gdy klucz jest ważny i dozwolone jest uwierzytelnianie SSH roota. Zobacz [opcje załączników qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Ponowne użycie znacznika czasu sudo zależy od polityki pamięci podręcznej, właściciela, terminala/sesji i uprawnień. Odpowiednie kontrole opisuje [przewodnik eskalacji uprawnień](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens).
- `doas` ma własne reguły i konfigurację. Sprawdź dozwolone polecenia i zapisywalne ścieżki konfiguracji zgodnie z opisem w [sekcji doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Narzędzia kompilacyjne i pakietowe uruchamiane przez sudo

Nieograniczone uprawnienie sudo do uruchomienia Foundry `forge` może mieć znaczenie nawet wtedy, gdy tożsamością RunAs jest inne konto nie-rootowe. Opcje kompilatora, takie jak `--use`, mogą wskazywać lokalny plik wykonywalny, a `forge flatten -o` wybiera plik wyjściowy. Zanim uznasz uprawnienie za możliwe do wykorzystania, sprawdź zainstalowaną wersję Forge, dokładne argumenty sudo, dostępne ścieżki projektu i kompilatora, uprawnienia do pliku wyjściowego oraz skuteczne środowisko. Względny plik wykonywalny helpera znaleziony przez `PATH` to ścieżka zależna od wersji i środowiska, a nie właściwość, którą należy zakładać dla każdej kompilacji Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Nieograniczone uprawnienie sudo do uruchomienia `pacman` jako root pozwala na więcej niż samo sprawdzanie pakietów: `-U` przyjmuje lokalny pakiet, pakiety mogą zawierać skrypty instalacyjne, a `--hookdir` wybiera inny katalog hooków. Przed testowaniem sprawdź skuteczną regułę sudo, ograniczenia argumentów i wykluczenia; pasywny rekonesans nie wymaga instalowania pakietu ani uruchamiania hooka.<sup>[[25]](#references)[[26]](#references)</sup>

Stały wrapper powłoki uruchamiany przez sudo może również zainstalować wskazaną zależność npm, a następnie uruchomić aplikację Node. Sprawdź dokładną regułę RunAs, czy pakiet jest już zainstalowany, skuteczne `HOME` i `userconfig` npm, konfigurację projektu lub nadpisania z wiersza poleceń oraz to, czy użytkownik o niższych uprawnieniach kontroluje rejestr lub pakiet pobierany pod tą nazwą. [Dokumentacja npm opisuje wyszukiwanie pliku `.npmrc` użytkownika i projektu](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); zachowanie `HOME` przez sudo zależy od zainstalowanej polityki i dystrybucji, więc uprzywilejowany proces npm może odczytać zapisywalny plik `.npmrc` użytkownika albo nie. Jeśli uprzywilejowana aplikacja importuje nowo zainstalowany pakiet, jego kod modułu może zostać uruchomiony z tożsamością tej aplikacji. Skrypty uruchamiane podczas instalacji stanowią osobną ścieżkę zależną od wersji i konfiguracji; [dokumentacja npm opisuje ich cykl życia i obsługę użytkownika](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Sama ścieżka `.npmrc` lub wiersz `npm install` to jedynie wskazówki do analizy. Podczas pasywnego rekonesansu sprawdź regułę, krótki wrapper, ścieżki konfiguracji i pochodzenie pakietu bez instalowania ani uruchamiania aplikacji.

Uprawnienie sudo do `pip` lub `pip3 download` jako root również wymaga analizy budowania pakietów, gdy argumenty pozwalają użytkownikowi wybrać niezaufane źródło dystrybucyjne, nawet jeśli wzorzec URL-a ogranicza je do lokalnej usługi i sufiksu `.tar.gz`. `pip download` akceptuje URL-e archiwów i rozwiązuje metadane pakietów; przygotowanie sdist może uruchomić backend kompilacji lub starszy kod `setup.py`, zanim archiwum zostanie jedynie zapisane. Sprawdź dokładną regułę sudo RunAs i argumentów, czy użytkownik może opublikować lub podmienić wybrane archiwum oraz czy dana wersja pip rzeczywiście przygotowuje jego metadane. Stałe, zaufane archiwum lub wheel nie dowodzą istnienia tej ścieżki. Podczas pasywnego rekonesansu nie pobieraj ani nie buduj niezaufanego pakietu. Zobacz [polecenie download pip](https://pip.pypa.io/en/stable/cli/pip_download/), [interfejs systemu budowania](https://pip.pypa.io/en/stable/reference/build-system/) i [wskazówki dotyczące bezpiecznej instalacji](https://pip.pypa.io/en/stable/topics/secure-installs/).

Reguła sudo zezwalająca na `pip install` z wybraną przez użytkownika lokalną ścieżką projektu tworzy bardziej bezpośrednią granicę budowania. [pip akceptuje lokalne katalogi projektów](https://pip.pypa.io/en/stable/topics/local-project-installs/) i uruchamia ich system budowania; [backend budowania uruchamia kontrolowane przez projekt hooki](https://pip.pypa.io/en/stable/reference/build-system/). Zanim uznasz tę regułę za uprzywilejowane wykonanie kodu, sprawdź skuteczną tożsamość RunAs, dokładne ograniczenia i zakazy argumentów, kontrolę nad wybranym projektem oraz zachowanie zainstalowanego pip/backendu. Stały zaufany projekt lub reguła wykluczająca ścieżki wybierane przez użytkownika nie dowodzą istnienia tej drogi. Podczas pasywnego rekonesansu sprawdź regułę i metadane projektu bez instalowania pakietu.

Nieograniczone uprawnienie sudo do uruchomienia `easy_install` jako root stanowi podobną wskazówkę dotyczącą starszego mechanizmu budowania pakietów. [Dokumentacja Setuptools](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) informuje, że Easy Install przyjmuje lokalny katalog projektu i buduje dystrybucje źródłowe; podczas takiego budowania projekt kontrolowany przez użytkownika może uruchomić jego `setup.py` z tożsamością sudo. Sprawdź skuteczne konto RunAs, dokładne ograniczenia polecenia i argumentów (w tym późniejsze zakazy), kontrolę nad wybranym projektem oraz zachowanie zainstalowanego narzędzia. Stały zaufany projekt lub polityka niedopuszczająca źródła wybranego przez użytkownika nie dowodzą istnienia tej ścieżki. Podczas rekonesansu sprawdź regułę i metadane projektu bez instalowania pakietu.

Wrapper Python dozwolony przez sudo, który używa `setuptools.package_index.PackageIndex.download` z URL-em wybranym przez użytkownika, to inny przypadek niż `pip download`: [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) opisuje, jak w podatnych wersjach przed 78.1.1 nazwa pliku wyprowadzona z URL-a mogła wyjść poza zamierzony katalog pobierania i zapisać plik z uprawnieniami procesu. Sprawdź skuteczną tożsamość sudo RunAs i regułę argumentów, czy wrapper przekazuje URL użytkownika do dokładnie tego API, zainstalowaną kompilację lub backport dostawcy oraz miejsce, do którego rozwiązuje się wynikowa ścieżka. Sam numer wersji lub zapisywalny katalog pobierania nie dowodzą możliwości dowolnego zapisu. Podczas rekonesansu sprawdź krótki wrapper i metadane pakietu bez pobierania wskazanego URL-a ani zapisywania pliku.

Wrapper budowania dozwolony przez sudo, który przekazuje wybrany przez użytkownika plik `.spec` do PyInstaller, wymaga podobnej analizy granicy zaufania. Plik spec PyInstaller jest wykonywalnym kodem Python interpretowanym podczas **budowania**, a jego wpisy `datas` mogą dołączyć do artefaktu pliki dostępne dla tożsamości procesu budowania. Sprawdź dokładnego użytkownika RunAs, regułę argumentów i zakazów sudo, obsługę ścieżki i gałęzi w wrapperze, kontrolę nad wybranym plikiem spec oraz dostęp do wynikowego artefaktu. Samo zezwolenie na plik wejściowy `.py` lub znalezienie zainstalowanego PyInstaller nie dowodzi kontroli nad plikiem spec ani uprzywilejowanego wykonania. Pasywna analiza powinna obejmować tylko ograniczony plik wrappera i metadane; nie uruchamiaj budowania. Zobacz [dokumentację plików spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loadery presetów i pluginów uruchamiane przez sudo

Narzędzia Python akceptujące wybrany przez użytkownika preset lub katalog pluginów mogą importować kod z uprawnieniami przyznanymi przez sudo. Na przykład BBOT akceptuje preset przez `-p`, a jego [dokumentacja niestandardowych modułów](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) opisuje wpisy `module_dirs`, które wskazują dodatkowe katalogi modułów Python. Jeśli skuteczna reguła sudo zezwala na preset wybrany przez użytkownika, a użytkownik kontroluje moduł w wybranym katalogu, import może uruchomić kod jako uprzywilejowany użytkownik — potencjalnie nawet zanim narzędzie odrzuci nieprawidłowy moduł. Sprawdź zainstalowaną wersję, dokładną politykę sudo dotyczącą użytkownika RunAs i argumentów oraz właścicieli presetów i ścieżek modułów, nie wczytując modułu podczas rekonesansu.

### Narzędzie wiersza poleceń Backdrop uruchamiane przez sudo

[Bee](https://github.com/backdrop-contrib/bee) to narzędzie wiersza poleceń PHP dla Backdrop CMS. Polecenia `eval` (`php-eval`) i `php-script` mogą uruchamiać kod PHP przekazany przez użytkownika. Reguła sudo zezwalająca na uruchomienie pliku wykonywalnego Bee jako root z nieograniczonymi argumentami może więc umożliwić wykonanie kodu jako root, jeśli Bee potrafi zainicjować instalację Backdrop. Uruchom narzędzie z katalogu witryny lub wskaż witrynę globalną opcją `--root=<directory>`; samo znalezienie Bee lub pliku Backdrop `settings.php` nie dowodzi uprawnienia sudo, działającej witryny ani pomyślnej inicjalizacji. Przed testowaniem sprawdź skuteczną regułę sudo, wszelkie wykluczenia poleceń, tożsamość pliku wykonywalnego i dostęp do witryny. Podczas pasywnego rekonesansu sprawdź regułę i ścieżki plików bez uruchamiania Bee. Zobacz [dziennik zmian poleceń Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md), opisujący dodanie poleceń PHP.

### Serwery terminalowe uruchamiane przez sudo

`mosh-server` uruchamia interaktywny serwer terminalowy jako użytkownik wywołujący. Wybiera wysoki port UDP i klucz sesji, podaje oba użytkownikowi i po połączeniu klienta zwykle uruchamia powłokę logowania tego użytkownika. Nieograniczone uprawnienie sudo do uruchomienia `mosh-server` jako root jest więc potencjalnym przypadkiem uruchomienia powłoki, mimo że samo polecenie serwera działa w tle. Sprawdź skuteczną tożsamość RunAs, dozwolone argumenty i wykluczenia, zainstalowany plik binarny, powłokę, dostępność klienta i dostęp UDP. Pasywny rekonesans powinien sprawdzać regułę sudo bez uruchamiania serwera ani wyświetlania aktywnego klucza sesji. Zobacz [podręcznik Mosh server](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) i [uwagi projektowe projektu](https://github.com/mobile-shell/mosh#how-it-works).

### Uprzywilejowane wrappery kopii zapasowych modyfikujące plik zadań użytkownika

Wrapper powłoki uruchamiany jako root może akceptować wybrany przez użytkownika plik zadań, usuwać `../` ze ścieżek źródłowych, sprawdzać, czy każdy wynik zaczyna się od dozwolonego katalogu, modyfikować plik zadań, a następnie przekazywać *jego ścieżkę* programowi kopii zapasowych. Sprawdź przekształconą ścieżkę po pełnym rozwiązaniu kanonicznym: pojedyncze przejście zastępujące ciągi może odsłonić nową sekwencję przejścia katalogów nadrzędnych, którą zaakceptuje leksykalne sprawdzenie prefiksu. Sprawdź również, czy program kopii zapasowych odczytuje zmodyfikowane dane z pamięci, czy ponownie otwiera plik. Jeśli otwiera plik ponownie, nieudana modyfikacja może pozostawić oryginalne dane wejściowe.

W Linuksie `fs.protected_regular` może zablokować zapis z `O_CREAT` do zwykłego pliku należącego do innego użytkownika w katalogu zapisywalnym dla wszystkich z ustawionym sticky bitem. To zabezpieczenie może zadziałać, ale wrapper powłoki ignorujący błąd zapisu nadal może kontynuować, używając oryginalnego pliku zadań. Sprawdź to ustawienie, właściciela pliku i katalogu oraz to, czy wrapper przerywa działanie po błędzie. Ścieżka może umożliwić ujawnienie plików tylko wtedy, gdy skuteczna reguła sudo zezwala na uruchomienie wrappera jako uprzywilejowany użytkownik, użytkownik kontroluje dane zadań i czytelne miejsce docelowe kopii, a narzędzie rzeczywiście uwzględnia chronione źródła. Podczas rekonesansu sprawdź te warunki bez uruchamiania kopii zapasowej.

### Wieloznaczniki argumentów uprzywilejowanych narzędzi sieciowych

W regule sudo dla `tcpdump` znak `*` we **wzorcu argumentów** może dopasowywać białe znaki i ukośniki, więc ograniczenie wyglądające na ścieżkę może nadal dopuścić dodatkowy tekst opcji. To coś innego niż wieloznacznik w ścieżce pliku wykonywalnego polecenia; sprawdź pełną regułę RunAs i wszelkie późniejsze zakazy. Jeśli można wstrzyknąć opcje, o tym, czy wywołanie daje użyteczny prymityw odczytu/zapisu, decydują dozwolone wywołanie i semantyka opcji zainstalowanego [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), takich jak `-F`, `-V`, `-r`, `-w` lub `-Z`. `-V` odczytuje listę nazw plików przechwyconych pakietów, a nie dowolny plik do zrzutu. AppArmor lub inna polityka MAC może blokować dostęp do plików, nawet gdy sudo zezwala na polecenie; sam plik profilu na dysku nie dowodzi, że profil jest załadowany i egzekwowany. Zanim wyciągniesz wniosek, pasywnie sprawdź autoryzację i politykę. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) opisuje różnicę między tymi rodzajami wieloznaczników.

Reguła sudo zezwalająca jako root wyłącznie na plik wykonywalny `tcpdump`, bez ograniczenia argumentów, również wymaga analizy. [Podręcznik tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) opisuje `-z` jako polecenie uruchamiane po rotacji, gdy `-C` lub `-G` rotuje zapisane przechwycenie; `-Z` lub domyślne ustawienie czasu kompilacji może obniżyć uprawnienia przed uruchomieniem tego polecenia. Zanim uznasz regułę za ścieżkę eskalacji, sprawdź skuteczną regułę sudo, zainstalowaną kompilację, zachowanie związane z obniżeniem uprawnień i możliwość wystąpienia rotacji. Wyróżniona reguła to kandydat do analizy, a nie dowód wykonania polecenia jako root.

### Wrappery Nmap uruchamiane przez sudo

Jeśli ścieżka `nmap` dozwolona przez sudo wskazuje na wrapper powłoki, sprawdź dokładną dozwoloną ścieżkę i każdą przekazywaną opcję. Blokowanie dobrze znanej postaci `--script` nie musi blokować wczytywania kodu NSE: Nmap używa [`--datadir`](https://nmap.org/book/man-misc-options.html) do wyboru plików danych, a NSE [wczytuje `nse_main.lua`](https://nmap.org/book/nse-implementation.html) z wybranego katalogu danych, gdy skryptowanie jest włączone. Niektóre zainstalowane kompilacje akceptują też alternatywne zapisy długich opcji, więc porównaj ograniczenia z parserem faktycznie zainstalowanego pliku binarnego. [`--excludefile`](https://nmap.org/book/man-target-specification.html) to osobna powierzchnia odczytu plików; błędy parsera mogą ujawnić tekst. Podczas rekonesansu sprawdź skuteczną regułę sudo, logikę wrappera, wersję Nmap, kontrolę nad katalogami i politykę MAC bez uruchamiania skanów.

### Hooki Mercurial pull uruchamiane przez sudo

Stałe źródło w `sudo hg pull /fixed/source` nadal pozostawia wybór **repozytorium odbierającego** katalogowi bieżącemu, chyba że polecenie ustala repozytorium przez `-R`. Repozytorium odbierające kontrolowane przez użytkownika może definiować hooki w `.hg/hgrc`, a hook może zostać uruchomiony jako użytkownik sudo RunAs. [Mercurial ignoruje konfigurację repozytorium należącą do niezaufanego użytkownika lub grupy](https://mercurial-scm.org/help/topics/config), więc zanim uznasz to za wykonanie kodu, sprawdź zaufanych użytkowników/grupy konta RunAs i dokładny katalog roboczy. Do pasywnej analizy wystarczy odczytać politykę i konfigurację; podczas rekonesansu nie wykonuj pull ani hooka.

### Hooki Git pull uruchamiane przez sudo

W przypadku dokładnego uprawnienia sudo do `git pull` jako root sprawdź również **repozytorium odbierające** wybrane przez katalog roboczy. Repozytorium należące do użytkownika może zawierać wykonywalny hook `post-merge`, który uruchamia się z tożsamością procesu Git, gdy pull faktycznie przeprowadza udane scalanie; [Git opisuje ten hook](https://git-scm.com/docs/githooks) oraz [zachowanie pull dotyczące merge i rebase](https://git-scm.com/docs/git-pull). Sprawdź skuteczną regułę sudo i bieżący katalog roboczy, aktywną ścieżkę hooka i jej uprawnienia oraz możliwość wykonania merge z nowymi commitami. Nieudany pull, brak zmian lub pull wykonujący wyłącznie rebase nie dowodzą istnienia tej ścieżki. Sprawdź politykę i metadane repozytorium bez uruchamiania uprzywilejowanego pull.

### Kopiowanie archiwów rsync uruchamiane przez sudo

W przypadku `sudo rsync -a ... /writable/source/* /fixed/destination/` znak `*` we **wzorcu argumentów sudoers** może dopasować białe znaki i dopuścić dodatkową opcję między źródłem a miejscem docelowym. To coś innego niż rozwijanie nazw plików przez powłokę. Jeśli użytkownik może umieszczać pliki w źródle, a proces rsync z uprzywilejowanymi uprawnieniami może zapisywać w miejscu docelowym, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) może ustawić uprzywilejowanego właściciela, zachowując przy tym bity uprawnień w trybie archiwizacji, co potencjalnie pozwala utworzyć plik SetUID należący do uprzywilejowanego użytkownika. Sprawdź dokładną [semantykę wieloznaczników sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), wersję rsync, późniejsze zakazy, opcję systemu plików `nosuid` i politykę MAC. Pasująca reguła jest kandydatem do analizy, a nie dowodem udanej eskalacji uprawnień.

### Eksport reguł filtrowania pakietów uruchamiany przez sudo

Nieograniczone uprawnienie sudo do uruchamiania zarówno `iptables`, jak i `iptables-save` (lub odpowiedniej pary `ip6tables`) jako root wymaga analizy zapisu do plików. Dopasowanie `comment` akceptuje tekst reguły wybrany przez użytkownika, a `iptables-save -f` zapisuje zserializowany zestaw reguł do wybranej ścieżki.<sup>[[20]](#references)[[21]](#references)</sup> Użyteczny ładunek zależy od sposobu, w jaki zainstalowany backend serializuje komentarze, oraz od tego, czy plik docelowy akceptuje inne wiersze eksportu; samo `iptables-save` nie umożliwia zapisania dowolnie wybranej zawartości. Sprawdź dokładną tożsamość sudo RunAs, argumenty i wykluczenia, dostępne rozszerzenie dopasowujące, backend i uprawnienia do pliku docelowego. Podczas rekonesansu sprawdź uprawnienie bez zmieniania reguł zapory ani zapisywania pliku.

### Uprzywilejowany katalog logów Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) dotyczył wersji Below starszych niż 0.9.0, które tworzyły katalog `/var/log/below` z prawem zapisu dla wszystkich. Jeśli usługa lub dozwolone polecenie sudo uruchamia podatną kompilację jako root, użytkownik mogący zapisywać w katalogu logów bez sticky bitu i przechodzić przez niego może podmienić wpis logu na dowiązanie symboliczne, zanim uprzywilejowany proces go otworzy. Sprawdź status poprawek zainstalowanego pakietu, dokładną ścieżkę uprzywilejowanego wykonania, faktyczny dostęp do katalogu, sticky bit i ACL oraz metadane `/var/log/below/error_root.log`. Ścieżka z prawem zapisu dla wszystkich lub sama reguła sudo nie dowodzą istnienia pełnego łańcucha. Sticky bit lub backport dostawcy zmieniają ocenę. Pasywny rekonesans powinien sprawdzać wyłącznie metadane; nie trzeba tworzyć dowiązania ani uruchamiać uprzywilejowanego programu.

### Uprzywilejowane zbieranie pakietu pomocy technicznej z zapisywalnych danych wejściowych

Skrypt profilu pomocy technicznej dozwolony przez `sudo` może odczytywać jako root stałe ścieżki logów i kopiować ich zawartość do archiwum profilu. Sprawdź, czy skrypt faktycznie odczytuje pliki, a następnie ustal, czy użytkownik może podmienić ścieżkę źródłową lub któryś wpis katalogu nadrzędnego na dowiązanie symboliczne. Jeśli uprzywilejowany odczyt podąża za tym dowiązaniem, a archiwum wynikowe jest czytelne dla użytkownika, chroniony plik może zostać ujawniony. Muszą wystąpić wszystkie elementy: uprawnienie sudo, zapisywalna ścieżka źródłowa, uprzywilejowany odczyt i czytelne dane wyjściowe; sam zapisywalny log lub nazwa profilu nie wystarczają. Podczas rekonesansu sprawdź skuteczne uprawnienia i metadane dowiązań bez podmieniania plików ani generowania profilu. [Wskazówki pomocy technicznej Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) opisują uruchamiany jako root skrypt profilu i archiwum wynikowe, ilustrując potrzebę ograniczania danych wejściowych i dostępu do wyników takich pakietów.

### Skrypty przywracania archiwów Python uruchamiane jako root

Nawet ściśle ograniczona reguła sudo dla skryptu przywracania w Pythonie wymaga analizy danych wejściowych archiwum. Jeśli użytkownik może wybrać lub podmienić archiwum, a skrypt rozpakowuje je jako root przez `tarfile.extractall(filter="data")`, przed zaufaniem temu filtrowi sprawdź aktualizacje bezpieczeństwa interpretera. CPython naprawił kilka sposobów obejścia filtru dla dowiązań symbolicznych i twardych, w tym CVE-2025-4517, w wersjach 3.9.23, 3.10.18, 3.11.13, 3.12.11 i 3.13.4. Backport dystrybucji może zawierać poprawkę w starszej wersji, więc sama wyświetlana wersja interpretera nie dowodzi podatności.<sup>[[16]](#references)[[17]](#references)</sup>

Podczas pasywnej analizy odczytaj dokładne polecenie sudo i skrypt, sprawdź, który argument wybiera archiwum, oraz ustal, czy bieżący użytkownik może zapisywać do archiwum lub jego katalogu. Osobno sprawdź poprawkę dostawcy i katalog docelowy rozpakowywania; `filter="data"` nie gwarantuje bezpieczeństwa każdego niezaufanego archiwum.<sup>[[16]](#references)[[17]](#references)</sup>

### Loadery modeli uczenia maszynowego uruchamiane przez sudo

Reguła sudo zezwalająca na plik `.pt`, `.pth` lub `.ckpt` wybrany przez użytkownika wymaga analizy, gdy uprzywilejowany skrypt przekazuje ten plik do [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` lub innego loadera opartego na pickle. Sprawdź skuteczną regułę RunAs, czy użytkownik może utworzyć lub podmienić wybrany model oraz rzeczywisty przepływ argumentu przez ewentualny wrapper powłoki do helpera Python. Rozszerzenie `.pth` oznacza również niezwiązane z tym pliki konfiguracji witryny Python, więc samo rozszerzenie nie dowodzi wczytywania modelu. Skan archiwum lub statyczna analiza pickle nie dowodzą, że późniejsze wczytanie jest bezpieczne; sprawdź [zależne od wersji zachowanie `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) i ewentualne listy dozwolonych obiektów. Zobacz [uwagi o pickle w ML i Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Podczas pasywnego rekonesansu nie wczytuj ani nie rozpakowuj modelu.

### Parsowanie wyrażeń ze zapisanych danych wejściowych uruchamiane przez sudo

Stały skrypt Python uruchamiany jako root przez sudo może nadal interpretować tekst, który użytkownik o niższych uprawnieniach może zapisać w bazie danych aplikacji. W TensorFlow wywołanie `preprocess_input_exprs_arg_string(value, safe=False)` wybiera ścieżkę `eval`; [ostrzeżenie TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) opisuje niebezpieczny parser i poprawkę w jego użytkowniku wiersza poleceń. Jawne wywołanie `safe=False` w aplikacji wymaga osobnej analizy, nawet jeśli wspomniany użytkownik wiersza poleceń został już poprawiony. Sprawdź skuteczną regułę sudo, kto może modyfikować konkretny rekord wejściowy, czy filtrowanie lub scoring pozwala temu rekordowi dotrzeć do wywołania oraz zachowanie zainstalowanej funkcji. Sama wersja TensorFlow, uprawnienie sudo lub zakodowany na stałe plik modelu nie dowodzą istnienia łańcucha. Pasywnie przeanalizuj skrypt i przepływ danych; podczas rekonesansu nie uruchamiaj uprzywilejowanego helpera ani nie przesyłaj testowych wyrażeń.

### Konfiguracja needrestart dozwolona przez sudo

`needrestart -c` wczytuje wybrany przez użytkownika plik konfiguracyjny Perl i interpretuje jego zawartość. Jeśli `sudo -l` zezwala na uruchomienie `needrestart` jako root z argumentami dopuszczającymi `-c`, a użytkownik może wybrać czytelny plik konfiguracyjny w zapisywalnej lokalizacji, uprawnienie może prowadzić do wykonania kodu jako root. Sprawdź dokładną regułę sudo dotyczącą RunAs i argumentów; reguła dopuszczająca wyłącznie stałą listę argumentów może blokować tę ścieżkę. To osobna kwestia od podatności skanowania interpreterów w needrestart: aktualizacja pakietu lub wyłączenie `interpscan` nie czyni bezpiecznym nieograniczonego uprawnienia do `needrestart -c` jako root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importy Python uruchamiane przez sudo na innym koncie

Stały punkt wejścia Python może nadal importować moduł, który użytkownik może edytować lub podmienić — również wtedy, gdy sudo uruchamia skrypt jako **nie-rootowe** konto usługi. W przypadku dosłownego `from utils import status` sprawdź zarówno lokalne `utils/__init__.py` i `utils/status.py`, jak i uprawnienia do katalogu pakietu. Zanim uznasz zapisywalny plik za ścieżkę wykonania, sprawdź ścieżkę importu skryptu, dokładne dozwolone argumenty sudo oraz to, czy odpowiednia operacja dociera do importu. Podczas rekonesansu sprawdź pliki i uprawnienia bez importowania ani uruchamiania skryptu.<sup>[[2]](#references)[[3]](#references)</sup>

Dokładna reguła sudo dla `python3 /absolute/script.py` wymaga jedynie, by skrypt był czytelny; plik nie musi być wykonywalny ani zawierać shebanga. Sprawdź również **brakujące** moduły lokalne: jeśli skrypt importuje moduł, którego plik można utworzyć w katalogu skryptu zapisywalnym przez użytkownika, Python może wczytać ten plik z tożsamością RunAs. Sprawdź skuteczną regułę sudo, faktyczną [ścieżkę wyszukiwania modułów](https://docs.python.org/3/library/sys_path_init.html) interpretera, czy moduł jest wbudowany lub zamrożony oraz czy wykonywany jest import. Bezpośrednia reguła sudo dla skryptu ma inne wymagania dotyczące bitu wykonywania i shebanga. Osobny wrapper dopisujący tokeny podane przez użytkownika po `sudo -u account` również wymaga analizy przepływu argumentów: kolejne `-u` w tych tokenach ma znaczenie tylko wtedy, gdy wywołana polityka sudo zezwala na wynikową tożsamość. Same statyczne ciągi nie dowodzą istnienia żadnej z tych ścieżek.

### Apache uruchamiany przez sudo z konfiguracją kontrolowaną przez użytkownika

Jeśli reguła sudo zezwala na uprzywilejowane wywołanie `apachectl`, `apache2ctl` lub `httpd` z kontrolowanym przez użytkownika plikiem konfiguracyjnym `-f`, sprawdź ten plik i uprawnienia do jego katalogu nadrzędnego. Dyrektywa Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) przyjmuje nazwę modułu i **nazwę pliku modułu**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) również wczytuje plik. [`Include` i `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) mogą rozszerzyć konfigurację lub ujawnić zawartość plików w błędach. Niestandardowy wrapper może walidować te ścieżki, obniżać uprawnienia lub ograniczać argumenty, więc sama zapisywalna konfiguracja jest kandydatem do analizy, a nie dowodem wykonania kodu. Zanim wyciągniesz wniosek, sprawdź kanonizację ścieżki, dowiązania symboliczne i parsowanie dyrektyw.

### nginx uruchamiany przez sudo z konfiguracją kontrolowaną przez użytkownika

Nieograniczona reguła sudo zezwalająca na uruchomienie `nginx` jako root może dopuszczać [`-c` do wyboru innej konfiguracji](https://nginx.org/en/docs/switches.html). Sprawdź dokładne argumenty i wykluczenia sudo, czy użytkownik może dostarczyć konfigurację oraz czy wynikowy proces nadrzędny lub robocze zachowują dostęp do chronionych ścieżek. Wybrana dyrektywa `root` wraz z `autoindex` może udostępniać pliki przez nowy listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) może umożliwić uprzywilejowany zapis plików, ale moduł DAV nie jest domyślnie kompilowany, a jego obecność, dostępność listenera, uprawnienia do plików i zachowanie plików tymczasowych wymagają sprawdzenia. Dyrektywa [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) może również wskazywać wybrany plik; zapisywanie logów do wrażliwego pliku konfiguracyjnego, takiego jak `/etc/ld.so.preload`, wymaga efektywnego zapisu z uprzywilejowanymi uprawnieniami i możliwości kontrolowania wpisu logu, zanim stanie się ścieżką eskalacji. Wyróżnienie pliku wykonywalnego w `sudo -l` jest wskazówką do analizy, a nie dowodem działania którejkolwiek z tych ścieżek. Podczas pasywnego rekonesansu nie uruchamiaj ani nie rekonfiguruj nginx.

### Porównywanie wzorców w uprzywilejowanych promptach Bash

Gdy skrypt Bash dozwolony przez sudo odczytuje wartość od użytkownika i sprawdza ją przez `[[ "$expected" == $entered ]]`, Bash interpretuje nieujęty w cudzysłów prawy operand jako wzorzec. Wieloznacznik może więc spełnić warunek bez znajomości oczekiwanej wartości. Ujęcie operandu w cudzysłów (`[[ "$expected" == "$entered" ]]`) wymusza porównanie dosłownych ciągów. Sprawdź dokładną regułę sudo, czy prompt jest osiągalny i co skrypt robi po porównaniu; sama składnia nie dowodzi, że ścieżkę można wykorzystać. Podczas rekonesansu nie wyświetlaj oczekiwanej wartości. Zobacz [opis konstrukcji warunkowych Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpery do pobierania i uruchamiania pliku przez sudo

Nieograniczone uprawnienie sudo do uruchomienia niestandardowego helpera jako root wymaga analizy przepływu danych, jeśli helper akceptuje URL wybrany przez użytkownika, zapisuje odpowiedź na dysku, a później uruchamia ten plik przez interpreter lub powłokę. [Sudoers dopuszcza dowolne argumenty, gdy wpis polecenia ich nie określa](https://man7.org/linux/man-pages/man5/sudoers.5.html); stała ścieżka pliku wykonywalnego nie ogranicza wyboru argumentów. Sprawdź rzeczywistą walidację URL-a, ścieżkę wyjściową, gałąź sukcesu i późniejsze wykonanie w zainstalowanym helperze. Sam import libcurl lub drukowalny ciąg nie dowodzą istnienia tego łańcucha.

Nawet stała nazwa pliku wyjściowego może zostać podmieniona między zapisem a wykonaniem, jeśli helper używa **ścieżki względnej w katalogu roboczym kontrolowanym przez użytkownika**. Zmiana nazwy lub podmiana pliku należącego do roota zależą od prawa zapisu i wyszukiwania w katalogu oraz ewentualnych ograniczeń sticky bitu, a nie wyłącznie od trybu pliku; zobacz [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Sprawdź, czy helper później ponownie otwiera ścieżkę, czy używa już otwartego deskryptora oraz czy przed zapisem przechodzi do zaufanego katalogu. Pasywnie sprawdź politykę sudo, helper i metadane katalogu; podczas rekonesansu nie uruchamiaj uprzywilejowanego pobierania ani nie przeprowadzaj wyścigu.

Helper pobierający pliki z uprawnieniami root przez sudo może też dopuszczać **wstrzyknięcie argumentu**, jeśli buduje ciąg polecenia Bash, taki jak `curl <caller input> -o <fixed output>`. Filtr odrzucający białe znaki nadal pozostawia [rozwijanie nawiasów klamrowych w Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): nieujęte w cudzysłów elementy oddzielone przecinkami mogą zostać rozwinięte do osobnych argumentów curl. Jeśli dane wejściowe trafiają do curl przed stałym `-o`, użytkownik może podać opcję określającą miejsce docelowe dla pierwszego URL-a, działając z tożsamością helpera; [curl przypisuje opcje wyjściowe do URL-i w kolejności](https://curl.se/docs/manpage.html#-o). Sprawdź dokładną powłokę, cudzysłowy, walidację danych wejściowych, skuteczną regułę sudo, kolejność argumentów curl i obsługiwane schematy URL-i oraz to, czy użytkownik kontroluje pobierane bajty lub może odczytać wynik. Plik wykonywalny spakowany przez PyInstaller może zawierać logikę aplikacji Python, ale sam znacznik pakowania lub ciąg `curl` nie dowodzą tego przepływu danych. Jeśli jest to dozwolone, sprawdź ograniczoną kopię offline; rutynowy rekonesans nie powinien uruchamiać helpera ani pobierać danych wybranych przez atakującego.

Skrypt powłoki uruchamiany przez sudo jako root, który wywołuje [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), tylko wybiera nieużywaną nazwę; **nie tworzy pliku**. Jeśli skrypt później tworzy plik pod tą nazwą w katalogu, na który może wpływać inny użytkownik, po czym ponownie go otwiera i dopisuje jego zawartość do chronionego miejsca docelowego, takiego jak `authorized_keys` roota, sprawdź możliwość wyścigu o plik tymczasowy. Potwierdź dokładną regułę sudo, właścicieli katalogu i pliku, kolejność tworzenia i ponownego otwierania, zabezpieczenia jądra oraz to, czy uprzywilejowany zapis faktycznie używa danych kontrolowanych przez atakującego. Sam ciąg `mktemp -u` lub zapisywalny katalog `/tmp` nie dowodzą istnienia wyścigu. Sprawdź skrypt i metadane ścieżki bez jego uruchamiania ani ścigania się o plik tymczasowy podczas rekonesansu.

## Uwagi obronne

- Unikaj udzielania przez sudo uprawnień do interpreterów i interaktywnych edytorów.<sup>[[1]](#references)</sup>
- Preferuj stałe, należące do roota wrappery wykonujące jedno wąsko określone działanie administracyjne.<sup>[[1]](#references)[[2]](#references)</sup>
- Jeśli interpreter jest nieunikniony, ogranicz dokładną ścieżkę skryptu i zablokuj argumenty kontrolowane przez użytkownika, zapisywalne ścieżki importu, `PYTHONPATH` oraz niebezpieczne zachowywanie środowiska.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Jeśli edycja plików jest wymagana, ogranicz dokładną ścieżkę pliku i rozważ `sudoedit` z poprawionymi wersjami sudo i ścisłą obsługą środowiska.<sup>[[1]](#references)[[2]](#references)</sup>
- Sprawdź `SETENV`, `env_keep`, zapisywalne katalogi robocze, zapisywalne ścieżki modułów/importu, `NOEXEC`, `use_pty` i logowanie, ale nie traktuj ich jako kompletnej piaskownicy.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
