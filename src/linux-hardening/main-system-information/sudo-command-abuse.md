## Intérpretes permitidos por Sudo

Si `sudo -l` permite que un usuario ejecute un intérprete como root, considéralo como ejecución directa de código. Los intérpretes están diseñados para ejecutar código arbitrario, por lo que una regla que permita binarios como `python3`, `perl`, `ruby`, `lua`, `node` o similares suele equivaler a ejecutar comandos como root, a menos que los argumentos estén estrictamente restringidos y validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flujo de revisión habitual: primero enumera los privilegios del usuario y luego ejecuta una instrucción de Python con la opción `-c` del intérprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

A continuación se muestran otros ejemplos de intérpretes; los intérpretes enumerados documentan la ejecución de código en línea o las API de procesos secundarios.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

La ruta exacta importa. Si la regla de sudo permite `/usr/bin/python3`, usa esa ruta exacta durante la validación.<sup>[[2]](#references)</sup>

Un glob de ejecutables de sudo como `/usr/bin/python*` también puede permitir Python 2 para un script escrito para Python 3. Si el script llega a `input()` con texto controlado por quien lo invoca, [Python 2 evalúa ese texto como una expresión](https://docs.python.org/2/library/functions.html#input); invocar explícitamente el intérprete tiene prioridad sobre el shebang del script. Antes de considerar esto una ruta de ejecución, verifica los binarios coincidentes instalados, la identidad RunAs efectiva y la política de argumentos, las denegaciones y si se puede llegar a la entrada controlada.

Una ruta de script fija en una regla de sudo con capacidad de ejecutarse como root no limita lo que ejecuta el script. Si se trata de un wrapper de Bash legible, comprueba si su primer comando ejecutable usa un parámetro posicional sin comillas, como `$1`, como **palabra de comando**, mientras sudo permite que quien lo invoca elija los argumentos. Confirma la identidad RunAs efectiva, la política de contraseña y argumentos, las denegaciones posteriores y la rama real del script; `NOEXEC`, una lista fija de argumentos seguros o un wrapper que valide el comando pueden cambiar el resultado. Durante la enumeración, inspecciona estáticamente el script breve en lugar de invocarlo con un comando de prueba.

Una regla de sudo sin restricciones y con capacidad de ejecutarse como root para `dotnet` también merece una revisión del intérprete. Con un SDK de .NET instalado, [`dotnet fsi` ejecuta código F# de forma interactiva o desde un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), y [`dotnet run` ejecuta un proyecto desde el código fuente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirma primero la identidad RunAs efectiva y la política exacta de argumentos: una regla limitada a un subcomando seguro específico o a una aplicación de confianza concede permisos distintos, y una instalación que solo incluya el runtime podría no tener los comandos del SDK. El nombre del ejecutable por sí solo es una señal para revisarlo, no una prueba de ejecución de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` permitido por sudo: escritura arbitraria de archivos con privilegios elevados

GNU `tee` copia la entrada estándar a todas las rutas indicadas como operandos de archivo. Por lo tanto, una regla de sudo que permita ejecutar `/usr/bin/tee` como root con argumentos controlados por el usuario concede una primitiva para crear o sobrescribir cualquier archivo como root. Añadir `-a` cambia la primitiva para que agregue contenido. Una etiqueta `PASSWD:` se refiere a la autenticación de sudo; por sí sola, no restringe el destino ni los bytes leídos desde la entrada estándar.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Primero, inspecciona la regla exacta. En un sistema de prueba autorizado, valida la primitiva únicamente con un destino desechable cuya creación sea segura. El `>/dev/null` final solo suprime la copia de `tee` a la salida estándar.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Colocar `sudo` antes del productor no eleva los privilegios de una redirección posterior del shell, porque el shell del usuario que invoca el comando abre el destino. El proceso privilegiado debe ser quien escriba, como en la canalización anterior.<sup>[[1]](#references)[[15]](#references)</sup>

Tras confirmar la escritura, elige un punto de entrada adecuado para la ejecución de código como root de [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Una cadena observada usó `tee` como root para crear un archivo temporal en `/etc/cron.d/`, ejecutar una backdoor mediante un script controlado por el usuario y eliminar el archivo cron después de la ejecución. Eliminar el archivo cron evitó que se convirtiera en una entrada de persistencia a largo plazo, aunque los registros del sistema conservaron evidencias de la actividad.<sup>[[27]](#references)</sup>

## Editores permitidos por sudo

Si `sudo -l` permite que un usuario ejecute un editor interactivo como root, considéralo una superficie de ejecución de comandos, no un permiso inofensivo para editar archivos. Los editores a menudo pueden ejecutar comandos de shell, leer archivos arbitrarios, escribir archivos arbitrarios o invocar herramientas externas desde el propio editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flujo de revisión habitual: enumera los privilegios del usuario y luego ejecuta cada editor o paginador permitido mediante sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Ejecución de comandos de Nano

Cuando `nano` está permitido mediante sudo, es posible ejecutar comandos desde la interfaz del editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Luego proporciona un comando como `id` o `/bin/sh` en el prompt de comandos de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactivo no tiene flujos de terminal utilizables, esta forma de redirección asigna su salida estándar y error al descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La secuencia exacta de teclas puede variar según la versión de nano y las opciones de compilación, pero el problema de seguridad es el mismo: el editor se ejecuta como root y puede invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Otras formas habituales de escapar de un editor

Los editores tipo Vim suelen permitir ejecutar comandos mediante `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Los paginadores como `less` también pueden permitir la ejecución de shell.<sup>[[14]](#references)</sup>

Una regla de sudo que permita ejecutar `apport-cli` como root merece la misma revisión del paginador. Algunas versiones afectadas de Apport podían abrir un informe de fallo en `less` con un tamaño de terminal ajustable por un atacante; el paginador podía entonces proporcionar una shell de root si se cumplían las condiciones especiales de sudo y del paginador. Comprueba la regla de sudo efectiva, la configuración del paginador y la corrección del paquete de la distribución antes de considerar vulnerable la versión por sí sola. Durante la enumeración pasiva, lee los metadatos del paquete y de las políticas sin generar un fallo ni abrir el informe privilegiado. [El registro CVE de Ubuntu](https://ubuntu.com/security/CVE-2023-1326) enumera las versiones corregidas de los paquetes específicas para cada versión, incluidas las correcciones retroportadas.

```text
!/bin/sh
```

## Otros riesgos de las reglas de sudo y doas

Empieza con `sudo -l`, `sudo -V` y cualquier política aplicable de `doas`. Lee en conjunto el comando permitido, el usuario de ejecución, los argumentos, el entorno y los valores predeterminados. El permiso para ejecutarse como una cuenta de servicio que no sea root aún puede exponer los archivos de esa cuenta o una vía hacia root.

Un script de Python fijo permitido por sudo aún puede ejecutar un comando de shell bajo la identidad RunAs si concatena entrada interactiva controlada por quien llama en [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una lista de denegación de signos de puntuación del shell no basta para demostrar que sea seguro: [el shell también reconoce la sustitución de comandos `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirma que los argumentos permitidos lleguen a la rama de entrada, que la entrada llegue al comando de shell sin una validación segura y que la política efectiva de sudo permita el usuario RunAs previsto. La ruta del script o una llamada a `os.system()` por sí solas son solo pistas para revisar; inspecciona el código fuente sin ejecutar el script privilegiado.

Una concesión efectiva de sudo como root para `chattr` puede quitar el atributo de archivo inmutable (`i`), pero esto por sí solo no concede permisos de escritura ni una nueva identidad. [El manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indica que el atributo bloquea las modificaciones y que solo root o un proceso con `CAP_LINUX_IMMUTABLE` puede cambiarlo. Comprueba la política exacta de argumentos de sudo y la compatibilidad del sistema de archivos; después, verifica por separado que quien llama pueda escribir el archivo una vez quitado el atributo y que un consumidor con una identidad superior lo use. Por ejemplo, reemplazar un shell de inicio de sesión también requiere credenciales aceptadas por la cuenta objetivo y un inicio de sesión real a través de ese shell. Revisa la política, los atributos de archivo y los permisos sin modificarlos durante el reconocimiento.

Si sudo solicita tanto una contraseña como un código de un solo uso, considera esos requisitos por separado de la concesión del comando. Un archivo `.google_authenticator` legible contiene material sensible de la semilla, mientras que un hash antiguo de contraseña de aplicación o de base de datos solo es una posible contraseña actual de la cuenta; ninguno demuestra que el otro factor sea aceptado por la configuración efectiva de PAM. Una vez autorizado, revisa el RunAs y los argumentos exactos: una concesión irrestricta como root para RubyGems `gem` puede exponer su comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), pero una concesión restringida o una autenticación fallida no lo hace. El reconocimiento pasivo debe informar las rutas y la política sin mostrar la semilla, recuperar una contraseña, generar un código ni invocar el comando privilegiado.

Una concesión irrestricta de sudo con capacidad de ejecutarse como root para `knife` de Chef merece una revisión a nivel de intérprete: [Chef documenta que `knife exec -E` evalúa localmente una cadena Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica que la regla efectiva de sudo permita el subcomando `exec` y el argumento `-E` proporcionado por quien llama, la identidad RunAs prevista y cualquier denegación de comandos o argumento fijo que coincida. El binario instalado o una regla restringida a otros subcomandos son solo pistas. El reconocimiento pasivo debe informar de la regla sin invocar `knife`.

Una concesión exacta de sudo con capacidad de ejecutarse como root para un `msfconsole` interactivo también es delicada: [GTFOBins documenta su consola `irb`](https://gtfobins.org/gtfobins/msfconsole/), que puede heredar la identidad de sudo. Confirma el usuario RunAs efectivo, la lista de argumentos permitidos, las denegaciones de comandos, `NOEXEC` u otras restricciones, el comportamiento de la consola instalada y si quien llama puede proporcionar entrada interactiva. Una ruta resaltada por sí sola es solo una pista para revisar; el reconocimiento pasivo no debe iniciar la consola.

En FreeBSD, incluso una regla de sudo limitada a `pkg update` como root y `pkg install *` merece una revisión de la confianza en los repositorios. Comprueba si quien llama puede escribir en `/etc/hosts` y si la configuración *efectiva* de repositorios habilitados usa un nombre de host HTTP con `signature_type: none`. [El manual de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indica que `none` deshabilita las comprobaciones de firmas; `pkg+http` por sí solo no lo demuestra. Un paquete puede contener scripts de instalación ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), por lo que quien realmente controle el endpoint del repositorio y pueda elegir un paquete podría cruzar el límite de root. Verifica las sobrescrituras de repositorios, la resolución de SRV/espejos, los argumentos efectivos de sudo, la selección del paquete y la ejecución de scripts antes de llegar a esa conclusión. Inspecciona la política y los archivos de configuración locales pequeños sin redirigir nombres ni ejecutar `pkg` durante el reconocimiento.

Una regla de sudo con capacidad de ejecutarse como root para `apt-get update` y `apt-get upgrade` también requiere revisar la confianza en los repositorios cuando sudo conserva un `http_proxy` controlado por quien llama. Comprueba si la configuración efectiva de APT usa realmente esa variable y qué solicitudes a repositorios habilitados puede afectar; un proxy por sí solo no puede sustituir paquetes de un archivo autenticado con una clave de firma de confianza. [El manual del transporte HTTP de APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedencia del proxy y [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta las comprobaciones de firmas, las sobrescrituras de repositorios inseguros y la confirmación para paquetes no autenticados. Confirma el RunAs y los argumentos exactos de sudo, la política de autenticación del repositorio, cualquier aceptación interactiva necesaria y si la actualización seleccionada ejecuta scripts de paquetes como root. Inspecciona la política y la configuración local de forma pasiva; no redirijas el tráfico de paquetes ni ejecutes una actualización durante el reconocimiento.

Una regla de sudo con capacidad de ejecutarse como root para `snap install` puede cruzar el límite entre paquetes y código si sus argumentos permiten a quien llama seleccionar un snap local y un modo de instalación permisivo. [Snap documenta](https://snapcraft.io/docs/explanation/snap-development/install-modes/) que `--dangerous` omite las comprobaciones de aserción de snaps locales y que `--devmode` relaja el confinamiento; [un hook de instalación puede ejecutarse durante la instalación inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Comprueba la política exacta de argumentos/RunAs de sudo, quién controla el archivo snap, si snapd instalado acepta esos modos y la identidad efectiva y el confinamiento del hook antes de afirmar que hay acceso a archivos protegidos del host. Un binario `snap` o una regla que parece tener comodines no demuestra por sí solo esta cadena. El reconocimiento pasivo no debe instalar un paquete ni ejecutar su hook.

Para una concesión exacta de sudo a un binario personalizado de lectura de credenciales perteneciente a una cuenta **que no sea root**, primero inspecciona el binario concedido y sus permisos sin ejecutarlo. Una comprobación de contraseña integrada podría ser visible solo como caracteres anchos; [GNU `strings` documenta la extracción little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Una cadena visible no demuestra que sea la contraseña aceptada ni que la rama de éxito exponga una credencial actual. Confirma por separado el comportamiento del binario, el acceso de la cuenta objetivo a los datos protegidos, la validez de las credenciales y cualquier transición posterior de cuenta o grupo. Si esa cuenta pertenece a `docker`, verifica el acceso al socket y la identidad rootful o rootless del daemon antes de inferir acceso a root del host; [Docker documenta las implicaciones de nivel root de su grupo](https://docs.docker.com/engine/install/linux-postinstall/). El reconocimiento rutinario debe informar de la regla de sudo y la pertenencia al grupo sin ejecutar el binario ni volcar sus cadenas.

Una regla de sudo con comodines para scripts de mantenimiento de una aplicación requiere revisar más que la ruta del script. Comprueba si el script permitido acepta argumentos sin restricciones o lee configuraciones que una cuenta de aplicación con menos privilegios puede modificar; luego, rastrea esos valores hasta comandos de shell o el entorno de un subproceso. Por ejemplo, [`zmupdate.pl` de ZoneMinder construye un comando `mysqldump` y lo ejecuta mediante `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mientras que [`zmdc.pl` copia la configuración `ZM_LD_PRELOAD` a `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Una regla de sudo que permita ejecutar cualquiera de esos scripts como root puede cruzar un límite de confianza si la entrada correspondiente es controlable y llega a ese código en la versión instalada. Inspecciona la regla efectiva de sudo, los permisos de configuración de la aplicación y el código fuente del script; el comodín o la configuración por sí solos son pistas, no pruebas de ejecución.

- `SETENV`, `env_keep`, `secure_path` y `LD_PRELOAD` pueden convertir un comando que, de otro modo, sería limitado en un secuestro de importación, biblioteca o PATH. Consulta la [guía de variables de entorno](../linux-basics/linux-environment-variables.md) y [el abuso de SUID/enlazadores](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Una concesión exacta de `SETENV` con capacidad de ejecutarse como root para un wrapper de shell también merece una revisión de un salto si el wrapper inicia un script fijo de Python con una importación literal. `secure_path` restringe la búsqueda de comandos del shell, no la [búsqueda de módulos de Python mediante `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` y `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hacen que Python ignore esa variable de entorno. Confirma las etiquetas y denegaciones efectivas de sudo, la rama del wrapper, las opciones del intérprete, la resolución de la importación y la existencia de un directorio de búsqueda que pueda escribir quien llama antes de tratarlo como ejecución de código. Inspecciona estáticamente los scripts cortos; no invoques el wrapper privilegiado.

Una concesión exacta de sudo `neofetch ""` con capacidad de ejecutarse como root aún puede cargar una configuración de shell si los valores predeterminados aplicables de sudo conservan un `XDG_CONFIG_HOME` controlado por quien llama. [El cargador de configuración de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carga `neofetch/config.conf` o `neofetch/config` desde ese directorio; la lista de argumentos vacía no impide esta búsqueda. Confirma el cargador instalado, el RunAs efectivo y la política de argumentos, las posibles denegaciones de comandos, si sudo realmente conserva la variable seleccionada para este comando y si quien llama controla una ruta de configuración legible. Una variable conservada o Neofetch instalado por sí solos son pistas. Inspecciona la política y los metadatos del archivo sin invocar el comando privilegiado ni mostrar el contenido de la configuración; consulta [el manejo del entorno de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regla irrestricta de sudo para `facter` con capacidad de ejecutarse como root merece una revisión aparte de los custom facts. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` carga archivos Ruby de facts desde un directorio seleccionado. Comprueba si la regla exacta de sudo permite esa opción, si Facter instalado la acepta y si quien llama controla el directorio. Una concesión con argumentos fijos, una denegación explícita del comando o custom facts deshabilitados pueden cambiar el resultado. El reconocimiento pasivo debe informar de la regla candidata sin invocar Facter ni leer el contenido de los facts.

Para una concesión exacta de sudo de un script con capacidad de ejecutarse como root y `SETENV`, inspecciona los nombres de comandos sin ruta, como `find`, y el `PATH` efectivo después de aplicar la política de sudo y la inicialización del script. Un archivo Bash cargado con `source` también puede ejecutar `enable -n [`: [Bash busca entonces en `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un `[` externo cuando el script usa ese comando más adelante. Confirma las [reglas de entorno y `secure_path` de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) aplicables, cualquier entrada `NOSETENV`/`NOEXEC` o de denegación, el flujo del script y los archivos cargados con `source`, y la existencia de un directorio ejecutable de búsqueda controlado por quien llama. Un script legible que contiene un comando sin ruta es una pista para revisar, no una prueba de ejecución privilegiada; inspecciónalo sin invocar la regla de sudo.
- Un script privilegiado que obtiene una URL fija con `curl` aún puede aceptar una respuesta elegida por quien llama si una regla de sudo aplicable conserva `http_proxy` y la solicitud se envía a través de ese proxy. Si después el script entrega la respuesta a un analizador XML que resuelve entidades externas, una respuesta maliciosa puede revelar archivos legibles por el proceso privilegiado. Comprueba la política exacta del entorno de sudo, las exclusiones `no_proxy`, la URL solicitada, la configuración del analizador y el destino de la salida; una variable de proxy o un analizador XML por sí solos no constituyen una vulnerabilidad. La [documentación de curl sobre el entorno del proxy](https://everything.curl.dev/usingcurl/proxies/env.html) describe el comportamiento de las variables. No hagas solicitudes de red ni analices XML malicioso durante el reconocimiento pasivo.
- Un script de sudo con capacidad de ejecutarse como root que construye un archivo PostScript a partir de datos influenciados por quien llama y luego ejecuta `ps2pdf -dNOSAFER` merece una revisión aparte del flujo de entrada. Ghostscript documenta que esta opción deshabilita SAFER hasta `.setsafe`, lo que permite operaciones con archivos PostScript dentro de los permisos del SO del proceso. Una consulta SQL construida a partir de un argumento de quien llama puede pasar filas controladas por un atacante a la plantilla PostScript, pero una cadena de consulta o una invocación de `ps2pdf` por sí solas no demuestran que los datos lleguen a la sintaxis ejecutable de PostScript. Confirma la regla efectiva de sudo, la ruta exacta desde la entrada hasta la plantilla, cualquier escape, el comportamiento de Ghostscript instalado y si SAFER vuelve a habilitarse antes de interpretar el documento. No invoques la conversión privilegiada durante el reconocimiento pasivo. Consulta [la documentación de Ghostscript sobre `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para una regla de sudo que ejecuta un script de shell, compara las variables conservadas con el propio script. Una construcción como `if $CHECK_CONTENT; then` ejecuta el valor expandido como comando, por lo que conservar `CHECK_CONTENT` puede permitir la ejecución de comandos incluso cuando la ruta y los argumentos del script son fijos. Hay que comprobar si la rama es alcanzable y si el entorno realmente se conserva para esa regla específica.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script de Python permitido por sudo puede importar código desde un directorio modificable o un archivo `.pyc` en caché. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md) detalla el caso de la caché.
- Un script fijo de Python permitido para ejecutarse como root aún puede exponer un depurador interactivo. Llamadas como `pdb.set_trace()` o `pdb.post_mortem()` permiten ejecutar instrucciones de Python en el contexto del proceso depurado cuando quien llama puede alcanzar el breakpoint o el manejador de excepciones **y controlar el flujo de entrada del depurador**. Comprueba la regla exacta de RunAs de sudo, la autenticación y las condiciones de la rama, la posibilidad de alcanzar la excepción, la propiedad del terminal/entrada y si el depurador se ejecuta en ese mismo proceso privilegiado. Una solicitud de socket que provoca una excepción no concede por sí sola acceso a un depurador conectado a otro terminal. [Python documenta la evaluación de instrucciones del depurador y el modo post mortem](https://docs.python.org/3/library/pdb.html); inspecciona el script estáticamente en vez de activar el manejador privilegiado durante el reconocimiento.
- Un script fijo de Python permitido por sudo también puede leer un campo de perfil de una base de datos o un socket Unix y añadirlo a una cadena que luego se convierte en la **cadena de formato** para `str.format()`. [Los campos de reemplazo pueden seguir atributos y claves de mappings](https://docs.python.org/3/library/string.html#format-string-syntax), por lo que un campo controlado por un atacante puede inspeccionar los objetos pasados a `format()` y exponer datos accesibles desde ellos si el resultado se imprime o se guarda en un lugar que quien llama pueda leer. Comprueba la identidad RunAs efectiva de sudo, el acceso de escritura al registro específico, el flujo de datos hasta la cadena de formato, los objetos proporcionados y la visibilidad de la salida. Esto no es ejecución automática de código, y una cadena de formato literal y confiable con *valores* controlados por un atacante es un caso distinto. Un secreto revelado solo permite una transición a una cuenta del SO si esa cuenta lo acepta. Revisa el script y los permisos del socket sin invocar la operación privilegiada.
- Un wrapper de Python con capacidad de ejecutarse como root puede pasar una URL elegida por quien llama a `Repo.clone_from` de GitPython. Si el wrapper también habilita `protocol.ext.allow=always` de Git, un remoto `ext::` puede invocar un helper externo. Comprueba los argumentos exactos de sudo, el origen de la URL, la versión del paquete GitPython y el estado de los parches del proveedor, y si el wrapper habilita explícitamente protocolos inseguros. GitPython añadió una [protección predeterminada contra protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) en la versión 3.1.30; la versión del ejecutable `git` es un dato distinto. La revisión pasiva debe leer únicamente la regla y el código fuente acotado, sin invocar el clonado.
- Una concesión de sudo entre usuarios para una CLI de clonado de repositorios puede exponer una vía separada de inyección en cadenas de shell. Rastrea si el argumento de repositorio elegido por quien llama llega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js o a otro generador de comandos de shell sin separar los argumentos de forma segura; `exec` de Node pasa su cadena de comando a un shell. Confirma el usuario RunAs exacto, los subcomandos y argumentos permitidos, el código del wrapper instalado y la validación de entrada. El nombre de una herramienta de repositorios o una regla irrestricta de sudo por sí solos no demuestran inyección de comandos. Inspecciona el wrapper sin invocar un clonado privilegiado durante el reconocimiento.
- Un wrapper personalizado propiedad de root puede parecer seguro porque sus binarios y scripts no se pueden modificar, pero su decisión de ejecutar una acción privilegiada puede depender de una bandera, un valor de API local o el estado de un servicio que una persona sin privilegios puede cambiar. Rastrea cada condición hasta su entrada y sus comprobaciones de autorización. Durante el reconocimiento, inspecciona la configuración y los permisos sin cambiar el estado operativo; una llamada a `systemd-run` dentro del wrapper solo es pertinente si se puede influir en la condición.
- Un cliente de copias de seguridad permitido por sudo como root puede aceptar un archivo de configuración elegido por quien llama (por ejemplo, `npbackup-cli -c`). Comprueba el usuario exacto de ejecución y los argumentos permitidos; luego, verifica si quien llama controla la ruta de configuración, las rutas de origen de la copia de seguridad y las opciones de repositorio o lectura/restauración. Un secreto cifrado de repositorio en una configuración legible aún puede ser utilizable por el cliente, pero la regla por sí sola no demuestra acceso al repositorio ni divulgación de archivos de root. Valida la autorización sin ejecutar una copia de seguridad ni volcar su contenido.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) admite `--password-command`, que llama a un programa para obtener la contraseña de un repositorio. Si una regla de sudo permite que un usuario con menos privilegios ejecute restic como root con un comando de contraseña elegido por quien llama y un subcomando que requiera la contraseña, ese helper podría ejecutarse como root. Revisa los argumentos exactos de sudo y las exclusiones; no invoques el helper ni un comando de copia de seguridad solo para confirmar la condición durante el reconocimiento.
- Una concesión privilegiada de `restic backup` también puede cruzar el límite de lectura de archivos si el patrón de argumentos de sudo permite que quien llama elija tanto el origen como un repositorio que después pueda leer y descifrar. [Los comodines de argumentos de sudoers pueden coincidir con espacios y barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), así que inspecciona los comodines finales en lugar de suponer que un prefijo fijo de repositorio confina el origen. [Restic puede hacer copias de seguridad en repositorios locales y remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), pero un repositorio local puede contener objetos recién escritos que solo root puede leer; confirma la política efectiva de sudo, el acceso al backend, la contraseña del repositorio y los permisos de los objetos resultantes antes de considerarlo una divulgación. Una clave SSH incluida en la copia de seguridad solo permite acceder si la cuenta de destino la acepta. No ejecutes una copia de seguridad para probar esto durante una revisión pasiva.
- Un comando de mantenimiento o copia de seguridad personalizado e irrestricto puede aceptar una ruta de salida o incluir su propio planificador de tareas. Para una vía de escritura de archivos, verifica la regla exacta de sudo y el usuario de ejecución, y luego si quien llama controla tanto los datos como el destino. Para una vía de comandos programados, verifica la identidad de ejecución del planificador, la entrada del comando y cualquier requisito adicional de contraseña o autorización. El nombre del comando o `NOPASSWD` por sí solos no demuestran ninguna de las dos vías. Consulta [escribir en archivos propiedad de root](../interesting-files-permissions/write-to-root.md) y [cron y los temporizadores de systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando fijo de sudo aún puede cargar un archivo de configuración predecible desde un directorio compartido modificable. Rastrea si quien llama puede reemplazar ese archivo y si sus campos de origen y destino controlan una obtención o copia privilegiada. Una URL de archivo local puede exponer datos que solo puede leer la cuenta RunAs de sudo; un origen controlado por quien llama junto con un destino protegido puede crear una vía de escritura. Confirma el manejo de URL del programa instalado, las comprobaciones de la ruta de destino, la regla efectiva de sudo y la accesibilidad de la salida. Una ruta de configuración en `/tmp` modificable es solo una pista; inspecciona el binario y los metadatos del archivo sin invocar la transferencia privilegiada.
- Una regla de sudo para `git apply` puede permitir que la cuenta RunAs escriba archivos seleccionados por un parche controlado por quien llama. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitía que un parche preparado creara un enlace simbólico y luego escribiera fuera del árbol de trabajo, incluso cuando el comando no aceptaba `--unsafe-paths`. Comprueba la regla efectiva de argumentos de sudo, el origen del parche, el acceso de la cuenta RunAs al directorio de trabajo y la corrección de Git instalado o el backport del proveedor. Una regla irrestricta que admita `--unsafe-paths` presenta un riesgo aparte por esa opción explícita; ni una versión de Git ni el permiso para ejecutar `git apply` por sí solos demuestran que pueda modificarse un archivo protegido. No apliques un parche no confiable durante el reconocimiento pasivo.
- Una regla de sudo para `clamscan --debug` con capacidad de ejecutarse como root puede cruzar un límite de lectura si un usuario con menos privilegios puede proporcionar una imagen DMG y el analizador instalado está afectado por [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que podía revelar el contenido de archivos mediante la salida de depuración. Confirma los argumentos permitidos y la ruta de análisis exactos, el control de la entrada, la cuenta RunAs efectiva, el parche o backport del motor y si quien llama puede ver la salida. Si una regla más amplia permite `--file-list`/`-f`, revisa por separado ese comportamiento de la lista de archivos; una política fijada en `--debug <scan-path>` no lo permite. Inspecciona la política y los metadatos del paquete sin analizar un archivo preparado ni mostrar resultados protegidos durante el reconocimiento.
- Una regla de sudo con capacidad de ejecutarse como root que abre una imagen de disco cifrada elegida por quien llama y una segunda regla que monta el mapper resultante pueden importar archivos controlados por quien llama al espacio de nombres de montaje del host. Confirma ambas reglas y sus argumentos efectivos, el control de la imagen y el nombre del mapper, el destino real del montaje y el propietario y modo resultantes de los archivos. Una transición de set-user-ID también requiere un ejecutable accesible, opciones de montaje que lo respeten (`nosuid` lo bloquea) y una política de proceso o MAC aplicable; abrir o montar una imagen por sí solo es solo una pista. Una vía aparte a través de una copia de seguridad existente requiere la clave real y un secreto útil y legible dentro de ella. Inspecciona la política y las rutas sin abrir ni montar una imagen durante el reconocimiento pasivo. Consulta el [manual de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) y las [opciones de montaje](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regla de sudo para un script de shell o Python con capacidad de ejecutarse como root merece revisar el directorio de trabajo si el script invoca `./helper` sin cambiar antes a un directorio fijo. Una lista de Python como `['./helper']` pasada a `subprocess.run` puede tener el mismo comportamiento de directorio de trabajo elegido por quien llama. Quien llama puede elegir un directorio modificable y colocar allí un ejecutable con ese nombre relativo; una ruta absoluta en otra parte del script no protege esta llamada. Confirma la regla efectiva, `runchdir` u otra política que cambie el directorio, el flujo del script y la accesibilidad de la rama, un directorio modificable y ejecutable, y las restricciones de montaje/`NOEXEC` antes de tratarlo como ejecución de código. Si el script no es legible, el comportamiento seguirá siendo desconocido hasta revisar su código fuente por una vía autorizada. Revisa los scripts estáticamente en lugar de ejecutar el helper. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la política del directorio de trabajo.
- Un validador fijo de Python con capacidad de ejecutarse como root aún puede evaluar un archivo de datos elegido por quien llama. [La documentación de `eval()` de Python advierte sobre la entrada no confiable](https://docs.python.org/3/library/functions.html#eval): comprobar un sufijo de entrada, un prefijo aritmético o una rama de validación no crea un sandbox si la expresión restante llega a `eval`. Confirma la regla efectiva de sudo, si quien llama puede elegir y controlar el archivo exacto, las condiciones de las ramas del analizador y la construcción de la expresión, y la identidad del proceso privilegiado antes de considerarlo una vía de ejecución. La presencia de `eval` en un script legible por sí sola es solo una pista para revisar; inspecciona el código fuente y los permisos del archivo sin ejecutar el validador ni enviar una expresión de prueba durante el reconocimiento.
- Un wrapper de Ruby con capacidad de ejecutarse como root mediante sudo que lee un nombre de archivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, puede usar la entrada del directorio de trabajo de quien llama, salvo que el wrapper o la política de sudo fijen ese directorio. Comprueba los argumentos permitidos exactos, los permisos del directorio y del archivo, y el comportamiento de Psych instalado: las implementaciones antiguas de `YAML.load` podían deserializar objetos Ruby arbitrarios, mientras que las versiones más recientes restringen las clases de forma predeterminada. Una llamada estática es solo una pista; confirma que el archivo realmente proviene de un directorio modificable por quien llama y que el cargador instalado acepta clases peligrosas. Para entradas no confiables, es preferible `safe_load` con una lista explícita y mínima de clases permitidas. Consulta la [documentación de Psych para Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) y la [documentación de Psych para Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Una concesión exacta de sudo `sudo go run /absolute/file.go` con capacidad de ejecutarse como root merece revisar el directorio de trabajo cuando el código fuente Go lee un archivo WASM relativo y podría ejecutar un script de shell relativo tras inspeccionar su resultado. Confirma el RunAs efectivo, los argumentos y las denegaciones del comando, la existencia de un directorio de trabajo modificable por quien llama, el flujo de datos de WASM a la rama y si esa rama invoca el helper. Un `runchdir` fijo de sudo, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pueden cambiar la ubicación de búsqueda. La coincidencia estática de estos elementos solo es una posibilidad; inspecciona el código fuente sin ejecutar Go, WASM ni el helper.
- `sudoedit` y los comodines de argumentos requieren comprobaciones exactas de la versión y la regla; la [lista de comprobación](linux-privilege-escalation-checklist.md) incluye el problema de edición de archivos de sudoedit. Para una concesión de `sudoedit` entre usuarios sobre una ruta con comodines, inspecciona la configuración efectiva `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, el destino resuelto y quién puede reemplazar cada entrada de directorio padre. La primera puede permitir seguir un enlace simbólico, mientras que deshabilitar la segunda elimina las comprobaciones de directorios modificables; ninguna de las dos opciones por sí sola demuestra que se pueda escribir en el archivo de otro usuario. Confirma la política de sudo instalada y los argumentos exactos que coinciden antes de llegar a esa conclusión. Consulta las [definiciones de opciones de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- En una regla de comandos de sudoers, un comodín de argumentos puede coincidir tanto con espacios como con caracteres de ruta. Una regla para un comando capaz de leer archivos con un argumento como `/restricted/*` podría admitir, por tanto, un argumento de archivo adicional después de un prefijo coincidente. Revisa el usuario RunAs exacto, la ruta del comando, el patrón de argumentos y las denegaciones posteriores; demostrar que se puede leer un archivo no implica ejecución de comandos. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue los patrones glob de argumentos de los patrones glob de rutas de comandos.
- Un patrón glob de argumento con aspecto de ruta también puede coincidir con `../`. Por ejemplo, una regla `node /opt/scripts/*.js` con capacidad de ejecutarse como root puede permitir que quien llama elija un archivo JavaScript fuera de `/opt/scripts` si la ruta proporcionada sigue empezando por `/opt/scripts/` y se resuelve a través de segmentos de directorio padre. Se trata de un patrón glob de **argumento**; el patrón glob de la ruta del comando ejecutable Node tiene reglas distintas para las barras. Comprueba la regla efectiva, las denegaciones posteriores, la resolución de rutas, el control del archivo objetivo y cualquier restricción de expresiones regulares o digest de sudoers antes de concluir que hay ejecución de código. Consulta las [reglas de comodines de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) y la [documentación de la línea de comandos de Node](https://nodejs.org/api/cli.html).
- Los archivadores y otras utilidades pueden tener hooks de ejecución. Comprueba los argumentos exactos permitidos en [GTFOBins](https://gtfobins.github.io/) en vez de suponer que solo los shells o intérpretes ejecutan comandos.
- Una regla irrestricta de `qpdf` con capacidad de ejecutarse como root puede exponer un archivo privilegiado mediante adjuntos PDF: qpdf 10.2 y posteriores admiten `--empty` y `--add-attachment file ... --` con un PDF de salida. Si el proceso privilegiado puede leer el origen seleccionado y escribir el PDF en una ruta accesible para quien llama, esa salida puede contener los bytes del origen. Revisa los argumentos efectivos y las exclusiones de sudo, la versión de qpdf, el acceso al origen y la ruta de salida antes de concluir que es posible divulgar el archivo. Leer una clave SSH de root solo sirve para iniciar sesión si la clave es válida y se permite la autenticación SSH de root. Consulta las [opciones de adjuntos de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La reutilización de marcas de tiempo de sudo depende de la política de caché, el usuario propietario, el terminal/sesión y los permisos. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) explica las comprobaciones.
- `doas` tiene sus propias reglas y configuración. Comprueba los comandos permitidos y las rutas de configuración modificables, tal como se describe en la [sección de doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Herramientas de compilación y empaquetado ejecutadas mediante sudo

Una concesión irrestricta de sudo para `forge` de Foundry puede ser relevante incluso cuando la identidad RunAs es otro usuario sin privilegios de root. Opciones del compilador como `--use` pueden seleccionar un ejecutable local, y `forge flatten -o` selecciona un archivo de salida. Comprueba la versión de Forge instalada, los argumentos exactos de sudo, los proyectos y rutas del compilador accesibles, los permisos de salida y el entorno efectivo antes de considerar explotable la concesión. Un ejecutable helper relativo encontrado mediante `PATH` es una vía que depende de la versión y el entorno, no una propiedad que deba suponerse en todas las compilaciones de Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Una concesión irrestricta de `pacman` con capacidad de ejecutarse como root permite más que consultar paquetes: `-U` acepta un paquete local, los paquetes pueden contener scripts de instalación y `--hookdir` selecciona otro directorio de hooks. Revisa la regla efectiva de sudo, las restricciones y exclusiones de argumentos antes de probarla; el reconocimiento pasivo no necesita instalar un paquete ni ejecutar un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper fijo de shell de sudo también puede instalar una dependencia npm con nombre y luego iniciar una aplicación Node. Revisa su regla exacta de RunAs, si el paquete ya está instalado, el `HOME` efectivo y el `userconfig` de npm, las sobrescrituras de configuración del proyecto o de la línea de comandos, y si un usuario con menos privilegios controla el registro o el paquete que se obtiene con ese nombre. [npm documenta la búsqueda de `.npmrc` por usuario y proyecto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); el comportamiento de `HOME` de sudo depende de la política instalada y de la distribución, por lo que es posible que el proceso npm privilegiado lea el archivo `.npmrc` de un usuario, o que no lo haga. Si la aplicación privilegiada importa el paquete recién instalado, su código de módulo puede ejecutarse bajo la identidad de esa aplicación. Los scripts de instalación constituyen una vía distinta, que depende de la versión y la configuración; [npm documenta su ciclo de vida y manejo de usuarios](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Una ruta `.npmrc` o una línea `npm install` por sí solas son solo pistas. Inspecciona la regla, el wrapper breve, las rutas de configuración y la procedencia del paquete sin instalarlo ni iniciar la aplicación durante el reconocimiento pasivo.

Una concesión de `pip` o `pip3 download` con capacidad de ejecutarse como root también es una pista para revisar la compilación de paquetes si sus argumentos permiten a quien llama seleccionar una distribución de origen no confiable, incluso si el patrón de URL la limita a un servicio local y a un sufijo `.tar.gz`. `pip download` acepta URL de archivos y resuelve metadatos de paquetes; preparar una distribución de origen puede invocar su backend de compilación o el código heredado de `setup.py` antes de guardar el archivo. Confirma el RunAs y la regla de argumentos exactos de sudo, si quien llama puede publicar o reemplazar el archivo seleccionado y si esa versión de pip realmente prepara sus metadatos. Un archivo de confianza fijo o un wheel no demuestran esta vía. No obtengas ni compiles un paquete no confiable durante el reconocimiento pasivo. Consulta el [comando download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), la [interfaz del sistema de compilación](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones de instalación segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regla de sudo que permite `pip install` con una ruta de proyecto local elegida por quien llama crea un límite de compilación más directo. [pip acepta directorios de proyectos locales](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca su sistema de compilación; el [backend de compilación ejecuta hooks controlados por el proyecto](https://pip.pypa.io/en/stable/reference/build-system/). Confirma la identidad RunAs efectiva, las restricciones y denegaciones exactas de argumentos, el control del proyecto seleccionado y el comportamiento del pip/backend instalado antes de considerar la regla como ejecución de código privilegiada. Un proyecto de confianza fijo o una regla que excluya las rutas elegidas por quien llama no establecen esta vía. Revisa la regla y los metadatos del proyecto sin instalar un paquete durante el reconocimiento pasivo.

Una concesión irrestricta de `easy_install` con capacidad de ejecutarse como root es una pista relacionada con la compilación de paquetes heredados. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install acepta un directorio de proyecto local y compila distribuciones de origen; un proyecto controlado por quien llama podría ejecutar su `setup.py` durante esa compilación bajo la identidad de sudo. Confirma la cuenta RunAs efectiva, el comando exacto y las restricciones de argumentos (incluidas las denegaciones posteriores), el control del proyecto seleccionado y el comportamiento de la herramienta instalada. Un proyecto de confianza fijo o una política que no permita seleccionar un origen por parte de quien llama no establecen esta vía. Inspecciona la regla y los metadatos del proyecto sin instalar un paquete durante el reconocimiento.

Un wrapper de Python permitido por sudo que use `setuptools.package_index.PackageIndex.download` con una URL elegida por quien llama es un caso de revisión distinto de `pip download`: [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) describe cómo un nombre de archivo derivado de la URL podía escapar del directorio de descarga previsto y escribir con los permisos del proceso en versiones afectadas anteriores a 78.1.1. Confirma el RunAs y la regla de argumentos efectivos de sudo, que el wrapper pase la URL de quien llama a esta API exacta, la compilación instalada o el backport del proveedor y dónde se resuelve la ruta resultante. Una cadena de versión o un directorio de descarga modificable por sí solos no demuestran escritura arbitraria. Revisa el wrapper breve y los metadatos del paquete sin obtener la URL ni escribir un archivo durante el reconocimiento.

Un wrapper de compilación permitido por sudo que pase a PyInstaller un archivo `.spec` elegido por quien llama requiere la misma revisión del límite de confianza. Un archivo spec de PyInstaller es Python ejecutable evaluado durante la **compilación**, y sus entradas `datas` pueden incluir en un artefacto archivos legibles por la identidad de compilación. Confirma el usuario RunAs exacto, las reglas de argumentos y denegaciones de sudo, el manejo de rutas y ramas del wrapper, el control del archivo spec seleccionado y el acceso al artefacto resultante. Permitir una entrada `.py` o encontrar PyInstaller instalado no demuestra por sí solo que se controle el archivo spec ni que haya ejecución privilegiada. La revisión pasiva debe leer solo un archivo wrapper acotado y sus metadatos; no debe ejecutar una compilación. Consulta la [documentación de archivos spec de PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Cargadores de presets y plugins ejecutados mediante sudo

Las herramientas de Python que aceptan un preset o directorio de plugins elegido por quien llama pueden importar código con los privilegios concedidos por sudo. Por ejemplo, BBOT acepta un preset con `-p`, y su [documentación de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) describe entradas `module_dirs` que seleccionan directorios adicionales de módulos Python. Si la regla efectiva de sudo permite un preset elegido por quien llama y este controla un módulo en el directorio seleccionado, la importación puede ejecutar código como el usuario privilegiado, potencialmente antes de que la herramienta rechace un módulo no válido. Comprueba la versión instalada, la política exacta de RunAs y argumentos de sudo, y la propiedad de las rutas del preset y del módulo sin cargar el módulo durante el reconocimiento.

### Herramienta de línea de comandos Backdrop ejecutada mediante sudo

[Bee](https://github.com/backdrop-contrib/bee) es una herramienta de línea de comandos PHP para Backdrop CMS. Sus comandos `eval` (`php-eval`) y `php-script` pueden ejecutar PHP proporcionado por quien llama. Por tanto, una regla de sudo que permita ejecutar Bee como root con argumentos irrestrictos puede exponer ejecución de código como root cuando Bee puede iniciar una instalación de Backdrop. Ejecútalo desde el directorio del sitio o selecciona un sitio con la opción global `--root=<directory>`; encontrar Bee o un archivo `settings.php` de Backdrop no demuestra por sí solo que exista el permiso de sudo, un sitio utilizable o un inicio correcto. Revisa la regla efectiva de sudo, las posibles exclusiones de comandos, la identidad del ejecutable y el acceso al sitio antes de probarlo. Durante el reconocimiento pasivo, inspecciona la regla y las rutas de los archivos sin invocar Bee. Consulta el [registro de cambios de comandos de Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver cuándo se añadieron los comandos PHP.

### Servidores de terminal ejecutados mediante sudo

`mosh-server` inicia un servidor de terminal interactivo como el usuario que lo invoca. Elige un puerto UDP alto y una clave de sesión, informa de ambos a quien llama y, normalmente, inicia el shell de inicio de sesión de ese usuario cuando se conecta un cliente. Por tanto, una concesión irrestricta de sudo para `mosh-server` con capacidad de ejecutarse como root es una candidata a revisión de shell, aunque el comando del servidor se desacople. Comprueba la identidad RunAs efectiva, los argumentos permitidos y las exclusiones, el binario instalado, el shell, la disponibilidad del cliente y el acceso UDP. El reconocimiento pasivo debe inspeccionar la regla de sudo sin iniciar un servidor ni mostrar una clave de sesión activa. Consulta el [manual del servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) y las [notas de diseño del proyecto](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de copia de seguridad privilegiados que reescriben el archivo de tareas de quien llama

Un wrapper de shell ejecutado como root puede aceptar un archivo de tareas seleccionado por quien llama, quitar `../` de las rutas de origen, comprobar que cada resultado empiece por un directorio permitido, reescribir el archivo de tareas y luego pasar su *ruta* a un programa de copias de seguridad. Revisa la ruta transformada después de resolverla por completo: una sola pasada de sustitución de cadenas puede exponer una nueva secuencia de recorrido que una comprobación léxica de prefijo acepta. Comprueba también si el programa de copias de seguridad lee los datos transformados en memoria o vuelve a abrir el archivo. Si lo vuelve a abrir, una reescritura fallida puede dejar intacta la entrada original.

En Linux, `fs.protected_regular` puede denegar una escritura `O_CREAT` en un archivo regular de otro usuario dentro de un directorio sticky modificable por todos. Esa denegación es protectora, pero un wrapper de shell que ignore el error de escritura aún podría continuar con el archivo de tareas original. Confirma la configuración, el propietario del archivo y el directorio, y si el wrapper se detiene ante el fallo. La ruta solo es candidata a divulgación de archivos cuando la regla efectiva de sudo permite ejecutar el wrapper como un usuario privilegiado, quien llama controla la entrada de tareas y un destino de copia de seguridad legible, y la utilidad realmente incluye los orígenes protegidos. Inspecciona estas condiciones sin ejecutar la copia de seguridad durante el reconocimiento.

### Comodines de argumentos en herramientas de paquetes privilegiadas

En una regla de sudo para `tcpdump`, un `*` en el **patrón de argumentos** puede coincidir con espacios y barras, por lo que una restricción con aspecto de ruta aún podría permitir texto de opciones adicional. Esto difiere de un comodín en la ruta del ejecutable del comando; inspecciona la regla RunAs completa y cualquier denegación posterior. Si pueden inyectarse opciones, la invocación permitida y la [semántica de opciones de `tcpdump` instalado](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinan si `-F`, `-V`, `-r`, `-w` o `-Z` ofrecen una primitiva útil de lectura/escritura. `-V` lee una lista de nombres de archivos de captura, no vuelca archivos arbitrarios de propósito general. AppArmor u otra política MAC puede bloquear el acceso a archivos incluso cuando sudo permite el comando; que haya un archivo de perfil en el disco no demuestra que esté cargado ni en modo de cumplimiento. Revisa la autorización y la política de forma pasiva antes de llegar a una conclusión. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) describe la diferencia entre los comodines.

Una regla de sudo con capacidad de ejecutarse como root que enumera solo el ejecutable `tcpdump`, sin restricción de argumentos, también merece revisión. El [manual de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como un comando posterior a la rotación cuando `-C` o `-G` rotan una captura guardada; `-Z` o un valor predeterminado de compilación pueden reducir privilegios antes de que se ejecute ese comando. Verifica la regla efectiva de sudo, la compilación instalada, el comportamiento de reducción de privilegios y si puede producirse una rotación antes de considerar la regla una vía de escalada. Una regla resaltada es una candidata, no una prueba de ejecución de comandos como root.

### Wrappers de Nmap ejecutados mediante sudo

Cuando la ruta de `nmap` permitida por sudo es un wrapper de shell, inspecciona la ruta exacta permitida y cada opción que reenvía. Bloquear la forma conocida `--script` no necesariamente bloquea la carga de código NSE: [`--datadir` de Nmap](https://nmap.org/book/man-misc-options.html) selecciona archivos de datos, y NSE [carga `nse_main.lua`](https://nmap.org/book/nse-implementation.html) desde el directorio de datos seleccionado cuando se habilita el scripting. Algunas compilaciones instaladas también aceptan formas alternativas de opciones largas, así que compara las restricciones con el analizador real de ese binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) es otra superficie de lectura de archivos; los errores del analizador pueden revelar texto. Comprueba la regla efectiva de sudo, la lógica del wrapper, la versión de Nmap, el control del directorio y la política MAC sin ejecutar análisis durante el reconocimiento.

### Hooks de pull de Mercurial ejecutados mediante sudo

Un origen fijo en `sudo hg pull /fixed/source` aún deja que el repositorio **receptor** lo seleccione el directorio de trabajo actual, salvo que el comando lo fije con `-R`. Un repositorio receptor controlado por quien llama puede definir hooks en `.hg/hgrc`, y un hook podría ejecutarse como el usuario RunAs de sudo. [Mercurial ignora la configuración de repositorios propiedad de usuarios o grupos no confiables](https://mercurial-scm.org/help/topics/config), así que inspecciona los usuarios/grupos de confianza de la cuenta RunAs y el directorio de trabajo exacto antes de tratarlo como ejecución de código. Leer la política y la configuración basta para una revisión pasiva; no ejecutes `pull` ni invoques un hook para comprobarlo.

### Hooks de pull de Git ejecutados mediante sudo

Para una concesión exacta de `sudo git pull` con capacidad de ejecutarse como root, comprueba también el repositorio **receptor** seleccionado por el directorio de trabajo. Un repositorio propiedad de quien llama puede tener un hook ejecutable `post-merge` que se ejecuta con la identidad del proceso Git cuando un pull realiza una fusión correcta; [Git documenta este hook](https://git-scm.com/docs/githooks) y el [comportamiento de pull entre merge y rebase](https://git-scm.com/docs/git-pull). Verifica la regla efectiva de sudo y el CWD, la ruta activa del hook y sus permisos, y si es posible realizar una fusión con nuevas confirmaciones. Un pull fallido, que no hace nada o que solo realiza rebase no demuestra esta vía del hook. Inspecciona la política y los metadatos del repositorio sin ejecutar el pull privilegiado.

### Copias de archivo rsync ejecutadas mediante sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` en el **patrón de argumentos de sudoers** puede coincidir con espacios y admitir una opción adicional entre el origen y el destino. Esto no es lo mismo que la expansión del shell de los nombres de archivo. Si quien llama puede poblar el origen y el proceso rsync privilegiado puede escribir en el destino, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) puede solicitar propiedad privilegiada mientras el modo de archivo conserva los bits de permisos, con la posibilidad de crear un archivo SetUID con propietario privilegiado. Comprueba la [semántica exacta de los comodines de sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versión de rsync, las denegaciones posteriores, `nosuid` del sistema de archivos y la política MAC. Una regla coincidente es una candidata a revisión, no una prueba de escalada exitosa de privilegios.

### Exportación de reglas de filtros de paquetes mediante sudo

Una concesión irrestricta con capacidad de ejecutarse como root para `iptables` e `iptables-save` (o el par correspondiente de `ip6tables`) merece revisar la escritura de archivos. El match `comment` acepta texto de reglas elegido por quien llama, mientras que `iptables-save -f` escribe el conjunto de reglas serializado en una ruta seleccionada.<sup>[[20]](#references)[[21]](#references)</sup> Una carga útil útil depende de cómo el backend instalado serialice los comentarios y de si el archivo de destino acepta otras líneas de la exportación; `iptables-save` por sí solo no permite elegir contenido arbitrario. Comprueba la identidad RunAs, los argumentos y las exclusiones exactos de sudo, la extensión de match disponible, el backend y los permisos del destino. Durante el reconocimiento, inspecciona la concesión sin cambiar las reglas del firewall ni escribir archivos.

### Directorio de registro de Below privilegiado

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afectó a versiones de Below anteriores a 0.9.0 que creaban un directorio `/var/log/below` modificable por todos. Si un servicio o un comando permitido por sudo ejecuta como root una compilación afectada, un usuario que pueda escribir y atravesar un directorio de registro sin sticky bit podría reemplazar una entrada del registro por un enlace simbólico antes de que el proceso privilegiado lo abra. Revisa el estado de los parches del paquete instalado, la ruta exacta de ejecución privilegiada, el acceso efectivo al directorio, el sticky bit y las ACL, y los metadatos de `/var/log/below/error_root.log`. Una ruta modificable por todos o una regla de sudo por sí solas no establecen la cadena completa. Un directorio sticky o un backport del proveedor cambia la evaluación. El reconocimiento pasivo debe inspeccionar solo los metadatos; no hace falta crear un enlace ni ejecutar el programa privilegiado.

### Recopilación de paquetes de soporte privilegiados a partir de entradas modificables

Un script de perfil de soporte permitido por `sudo` puede leer rutas fijas de registros como root y copiar su contenido a un archivo de perfil. Revisa el script real para identificar lecturas de archivos; luego, comprueba si quien llama puede reemplazar una ruta de origen o cualquier entrada de directorio padre por un enlace simbólico. Si la lectura privilegiada sigue ese enlace y el archivo resultante puede leerlo quien llama, podría divulgarse un archivo protegido. Deben darse la concesión de sudo, una ruta de origen modificable, la lectura privilegiada y una salida legible; un registro o nombre de perfil modificable por sí solo no basta. Inspecciona los permisos efectivos y los metadatos de los enlaces sin reemplazar archivos ni generar un perfil durante el reconocimiento. La [guía de soporte de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documenta su script de perfil ejecutado como root y su archivo de salida, lo que ilustra por qué este tipo de paquetes debe restringir las entradas y el acceso a la salida.

### Scripts de restauración de archivos Python ejecutados como root

Una regla de sudo muy limitada para un script de restauración Python aún requiere revisar su entrada de archivo comprimido. Si quien llama puede seleccionar o reemplazar el archivo y el script lo extrae como root con `tarfile.extractall(filter="data")`, comprueba las actualizaciones de seguridad del intérprete antes de confiar en el filtro. CPython corrigió varias vulnerabilidades de evasión del filtro para enlaces simbólicos y duros, incluida CVE-2025-4517, en las versiones 3.9.23, 3.10.18, 3.11.13, 3.12.11 y 3.13.4. Los backports de las distribuciones pueden corregir una versión anterior, así que la versión mostrada del intérprete por sí sola no demuestra que exista exposición.<sup>[[16]](#references)[[17]](#references)</sup>

Para una revisión pasiva, lee el comando y el script exactos de sudo, rastrea qué argumento selecciona el archivo comprimido y comprueba si el usuario actual puede escribir en el archivo o en su directorio contenedor. Confirma por separado el parche del proveedor instalado y el destino de extracción; `filter="data"` no hace que todos los archivos no confiables sean seguros.<sup>[[16]](#references)[[17]](#references)</sup>

### Cargadores de modelos de machine learning ejecutados mediante sudo

Una regla de sudo que permite seleccionar un archivo `.pt`, `.pth` o `.ckpt` merece revisión cuando un script privilegiado pasa ese archivo a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` u otro cargador basado en pickle. Comprueba la regla efectiva de RunAs, si quien llama puede crear o reemplazar el modelo seleccionado y el flujo real del argumento a través de cualquier wrapper de shell hasta el helper de Python. La extensión `.pth` también se usa para archivos de configuración de sitio de Python no relacionados, por lo que la extensión por sí sola no demuestra que se esté cargando un modelo. Un análisis del archivo comprimido o un análisis estático de pickle no demuestra que la carga posterior sea segura; inspecciona el comportamiento de `weights_only`, que depende de la [versión](https://docs.pytorch.org/docs/stable/notes/serialization.html), y cualquier lista de permitidos. Consulta las [notas sobre pickle de ML y Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). El reconocimiento pasivo nunca debe cargar ni descomprimir el modelo.

### Análisis de expresiones de entrada almacenada ejecutado mediante sudo

Un script fijo de Python ejecutado como root mediante sudo aún puede evaluar texto que un usuario con menos privilegios puede almacenar en una base de datos de la aplicación. En TensorFlow, una llamada a `preprocess_input_exprs_arg_string(value, safe=False)` selecciona una ruta `eval`; el [aviso de TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) describe el analizador inseguro y una corrección en su invocador de línea de comandos. Una llamada explícita de una aplicación a `safe=False` requiere una revisión aparte incluso si ese invocador de línea de comandos está parcheado. Comprueba la regla efectiva de sudo, quién puede modificar la fila de entrada exacta, si el filtrado o la puntuación permiten que esa fila llegue a la llamada y el comportamiento de la función instalada. Una versión de TensorFlow, una concesión de sudo o un archivo de modelo codificado de forma fija no demuestran por sí solos la cadena. Inspecciona el script y el flujo de datos de forma pasiva; no ejecutes el helper privilegiado ni envíes expresiones de prueba durante el reconocimiento.

### Configuración de needrestart permitida por sudo

`needrestart -c` carga un archivo de configuración Perl elegido por quien llama y evalúa su contenido. Si `sudo -l` permite ejecutar `needrestart` como root con argumentos que admiten `-c`, y quien llama puede elegir un archivo de configuración legible en una ubicación modificable, ese permiso puede llevar a la ejecución de código como root. Comprueba la regla exacta de RunAs y argumentos de sudo; una regla que permita solo una lista fija de argumentos puede bloquear esta vía. Esto es distinto de las vulnerabilidades de análisis de intérpretes de needrestart: actualizar el paquete o deshabilitar `interpscan` no hace que una concesión irrestricta de root con `-c` sea segura.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importaciones Python ejecutadas mediante sudo con otra cuenta

Un punto de entrada Python fijo aún puede importar un módulo que quien llama pueda editar o reemplazar, incluso cuando sudo ejecuta el script como un usuario de servicio **que no sea root**. Para una importación literal `from utils import status`, revisa tanto `utils/__init__.py` y `utils/status.py` locales como los permisos del directorio del paquete. Confirma la ruta de importación del script, los argumentos exactos permitidos por sudo y si la acción correspondiente llega a esa importación antes de considerar el archivo modificable como una vía de ejecución. Inspecciona los archivos y permisos sin importar ni ejecutar el script durante el reconocimiento.<sup>[[2]](#references)[[3]](#references)</sup>

Una regla exacta de sudo para `python3 /absolute/script.py` solo requiere que el script sea legible; no necesita ser ejecutable ni tener un shebang. Revisa también los módulos locales **que faltan**: si el script importa un módulo cuyo nombre de archivo puede crearse en un directorio del script modificable por quien llama, Python podría cargar ese archivo bajo la identidad RunAs. Confirma la regla efectiva de sudo, la [ruta de búsqueda de módulos](https://docs.python.org/3/library/sys_path_init.html) real del intérprete, si el módulo está integrado o congelado y si se alcanza la importación. Una regla de sudo directa para el script tiene requisitos distintos de bit de ejecución y shebang. Un wrapper aparte que añade tokens proporcionados por quien llama después de `sudo -u account` también requiere revisar el flujo de argumentos: otro `-u` en esos tokens solo importa si la política de sudo invocada permite la identidad resultante. Las cadenas estáticas por sí solas no demuestran ninguna de las dos vías.

### Apache ejecutado mediante sudo con configuración controlada por quien llama

Si una regla de sudo permite invocar con privilegios `apachectl`, `apache2ctl` o `httpd` con un archivo de configuración `-f` controlado por quien llama, revisa los permisos de ese archivo y de su directorio padre. La directiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) de Apache recibe un nombre de módulo seguido del **nombre de archivo del módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) también carga un archivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) pueden ampliar la configuración o exponer contenido de archivos mediante errores. Un wrapper personalizado puede validar estas rutas, reducir privilegios o restringir argumentos, por lo que una configuración modificable es una candidata a revisión, no una prueba de ejecución de código. Comprueba la canonicalización de rutas, los enlaces simbólicos y el análisis de directivas antes de llegar a una conclusión.

### nginx ejecutado mediante sudo con configuración controlada por quien llama

Una regla irrestricta de `nginx` con capacidad de ejecutarse como root puede permitir usar [`-c` para seleccionar otra configuración](https://nginx.org/en/docs/switches.html). Revisa los argumentos exactos de sudo y las exclusiones, si quien llama puede proporcionar la configuración y si el master o los workers resultantes conservan acceso a rutas protegidas. Un `root` seleccionado junto con `autoindex` puede exponer archivos mediante un nuevo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) puede proporcionar una vía privilegiada de escritura de archivos, pero el módulo DAV no se compila de forma predeterminada y hay que comprobar su presencia, la accesibilidad del listener, los permisos de archivos y el comportamiento de los archivos temporales. La directiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) también puede apuntar a un archivo elegido; escribir registros en un archivo de configuración sensible, como `/etc/ld.so.preload`, requiere un escritor privilegiado efectivo y un registro controlable antes de convertirse en una vía de escalada. El ejecutable resaltado en `sudo -l` es una pista, no una prueba de que ninguna de estas vías funcione. El reconocimiento pasivo no debe iniciar ni reconfigurar nginx.

### Comparación de patrones en prompts de Bash privilegiados

Cuando un script Bash permitido por sudo lee un valor de quien llama y lo comprueba con `[[ "$expected" == $entered ]]`, Bash interpreta el operando derecho sin comillas como un patrón. Por tanto, un comodín puede satisfacer la comparación sin conocer el valor esperado. Poner el operando entre comillas (`[[ "$expected" == "$entered" ]]`) lo convierte en una comparación de cadenas literales. Revisa la regla exacta de sudo, si se puede alcanzar el prompt y qué hace el script tras la comparación; la sintaxis por sí sola no demuestra una vía explotable. Evita mostrar el valor esperado durante el reconocimiento. Consulta la [referencia de estructuras condicionales de Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers ejecutados mediante sudo que descargan y ejecutan un archivo

Una concesión irrestricta de sudo para un helper personalizado con capacidad de ejecutarse como root merece revisar el flujo de datos si acepta una URL elegida por quien llama, escribe la respuesta en disco y luego invoca ese archivo con un intérprete o shell. [Sudoers permite argumentos arbitrarios cuando una entrada de comando no enumera ninguno](https://man7.org/linux/man-pages/man5/sudoers.5.html); una ruta de ejecutable fija no restringe lo que pueden seleccionar sus argumentos. Confirma la validación real de la URL, la ruta de salida, la rama de éxito y la ejecución posterior en el helper instalado. Una importación correspondiente de libcurl o una cadena imprimible por sí solas no demuestran esta cadena.

Incluso un nombre base de salida fijo puede reemplazarse entre la escritura y la ejecución cuando el helper usa una **ruta relativa en un directorio de trabajo controlado por quien llama**. Renombrar o reemplazar un archivo propiedad de root depende del acceso de escritura y búsqueda al directorio y de las restricciones del sticky bit, no solo del modo del archivo; consulta [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Comprueba si el helper vuelve a abrir la ruta o usa el descriptor ya abierto, y si cambia a un directorio de confianza antes de escribir. Inspecciona la política de sudo, el helper y los metadatos del directorio de forma pasiva; no invoques la descarga privilegiada ni intentes una condición de carrera durante el reconocimiento.

Un helper de descarga ejecutado como root mediante sudo también puede exponer una inyección de **argumentos** cuando construye una cadena de comando Bash como `curl <caller input> -o <fixed output>`. Un filtro que rechaza espacios en blanco aún deja disponible la [expansión de llaves de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): los elementos separados por comas y sin comillas pueden convertirse en argumentos distintos de curl. Si la entrada llega a curl antes de `-o`, que es fijo, una opción de salida proporcionada por quien llama podría seleccionar el destino de la primera URL bajo la identidad del helper; [curl asocia las opciones de salida con las URL en orden](https://curl.se/docs/manpage.html#-o). Confirma el shell exacto, el entrecomillado, la validación de entrada, la regla efectiva de sudo, el orden de argumentos de curl y los esquemas de URL admitidos, y si quien llama controla los bytes descargados o puede leer el resultado. Un ejecutable empaquetado con PyInstaller puede contener lógica de aplicación Python, pero su marcador de empaquetado o una cadena `curl` por sí solos no demuestran este flujo de datos. Revisa una copia local acotada cuando esté autorizado; el reconocimiento rutinario no debe ejecutar el helper ni obtener datos elegidos por un atacante.

Un script de shell ejecutado como root mediante sudo que llama a [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) solo elige un nombre no utilizado; **no** crea el archivo. Si el script luego crea ese nombre en un directorio que otra persona puede modificar, lo vuelve a abrir y añade su contenido a un destino protegido, como `authorized_keys` de root, revisa una posible condición de carrera con archivos temporales. Confirma la regla exacta de sudo, la propiedad del directorio y del archivo, la secuencia de creación y reapertura, las protecciones del kernel y si la escritura privilegiada realmente usa bytes controlados por un atacante. Una cadena `mktemp -u` o un `/tmp` modificable por sí solos no demuestran la condición de carrera. Inspecciona el script y los metadatos de la ruta sin ejecutarlo ni competir por su archivo temporal durante el reconocimiento.

## Notas defensivas

- Evita conceder intérpretes o editores interactivos mediante sudo.<sup>[[1]](#references)</sup>
- No concedas escritores de archivos genéricos como `tee` con operandos irrestrictos. Usa un wrapper propiedad de root que seleccione un destino fijo y rechace rutas controladas por quien llama.<sup>[[2]](#references)</sup>
- Prefiere wrappers fijos, propiedad de root y que realicen una única acción administrativa limitada.<sup>[[1]](#references)[[2]](#references)</sup>
- Si no se puede evitar un intérprete, restringe la ruta exacta del script e impide los argumentos controlados por usuarios, las importaciones modificables, `PYTHONPATH` y la conservación insegura del entorno.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si se requiere editar archivos, restringe la ruta exacta del archivo y considera usar `sudoedit` con versiones de sudo parcheadas y un manejo estricto del entorno.<sup>[[1]](#references)[[2]](#references)</sup>
- Revisa `SETENV`, `env_keep`, los directorios de trabajo modificables, las rutas de módulos/importación modificables, `NOEXEC`, `use_pty` y el registro, pero no los trates como un sandbox completo.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
