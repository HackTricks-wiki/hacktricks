## Interpreti consentiti da sudo

Se `sudo -l` consente a un utente di eseguire un interprete come root, consideralo come esecuzione diretta di codice. Gli interpreti sono progettati per eseguire codice arbitrario, quindi una regola che consente `python3`, `perl`, `ruby`, `lua`, `node` o binari simili equivale di solito all'esecuzione di comandi come root, a meno che gli argomenti non siano sottoposti a vincoli rigorosi e convalidati.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flusso di verifica comune: prima elenca i privilegi dell'utente, poi esegui un'istruzione Python con l'opzione `-c` dell'interprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Di seguito sono mostrati altri esempi di interpreti; quelli elencati documentano l'esecuzione di codice inline o le API per i processi figli.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Il percorso esatto è importante. Se la regola sudo consente `/usr/bin/python3`, usa quel percorso esatto durante la convalida.<sup>[[2]](#references)</sup>

Un glob per gli eseguibili sudo come `/usr/bin/python*` potrebbe consentire anche Python 2 per uno script scritto per Python 3. Se lo script raggiunge `input()` con testo controllato dal chiamante, [Python 2 valuta quel testo come un'espressione](https://docs.python.org/2/library/functions.html#input); l'invocazione esplicita dell'interprete prevale sullo shebang dello script. Verifica i binari corrispondenti installati, l'identità RunAs effettiva e la policy sugli argomenti, i dinieghi e l'input raggiungibile prima di considerarlo un percorso di esecuzione.

Un percorso fisso dello script in una regola sudo che consente l'esecuzione come root non limita ciò che lo script esegue. Per un wrapper Bash leggibile, controlla se il primo comando eseguibile usa un parametro posizionale non racchiuso tra virgolette, come `$1`, come **parola di comando**, mentre sudo consente argomenti scelti dal chiamante. Verifica l'identità RunAs effettiva, la policy su password e argomenti, i dinieghi successivi e il ramo effettivamente raggiunto nello script; `NOEXEC`, un elenco fisso di argomenti sicuri o un wrapper che convalida il comando possono cambiare il risultato. Durante l'enumerazione, esamina staticamente lo script breve invece di eseguirlo con un comando di prova.

Anche una regola sudo senza restrizioni che consente l'esecuzione di `dotnet` come root merita un controllo dell'interprete. Con un .NET SDK installato, [`dotnet fsi` esegue codice F# in modo interattivo o da uno script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/) e [`dotnet run` esegue un progetto dal sorgente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Verifica prima l'identità RunAs effettiva e la policy esatta sugli argomenti: una regola limitata a uno specifico sottocomando sicuro o a un'applicazione attendibile concede permessi diversi, e un'installazione con solo il runtime potrebbe non includere i comandi dell'SDK. Il solo nome dell'eseguibile è un indizio da verificare, non la prova dell'esecuzione di codice.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editor consentiti da sudo

Se `sudo -l` consente a un utente di eseguire un editor interattivo come root, consideralo una superficie di esecuzione di comandi, non un innocuo permesso di modifica dei file. Gli editor spesso possono eseguire comandi shell, leggere file arbitrari, scrivere file arbitrari o richiamare helper esterni dall'interno dell'editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flusso di revisione comune: elenca i privilegi dell'utente, quindi avvia con sudo ciascun editor o pager consentito.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Esecuzione di comandi con Nano

Quando `nano` è consentito tramite sudo, è possibile eseguire comandi dall’interfaccia dell’editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Quindi fornire un comando come `id` o `/bin/sh` al prompt dei comandi di nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se una shell interattiva non dispone di flussi di terminale utilizzabili, questa forma di reindirizzamento mappa l’output standard e il flusso di errore sul descrittore 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La sequenza di tasti esatta può variare in base alla versione di nano e alle opzioni di compilazione, ma il problema di sicurezza è lo stesso: l'editor è in esecuzione come root e può invocare comandi esterni.<sup>[[1]](#references)[[12]](#references)</sup>

### Altre vie di escape comuni negli editor

Gli editor in stile Vim consentono comunemente di eseguire comandi tramite `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Anche i pager come `less` possono esporre all'esecuzione di comandi shell.<sup>[[14]](#references)</sup>

Una regola sudo che consente di eseguire `apport-cli` come root merita la stessa verifica del pager. Le versioni di Apport interessate potevano aprire un report di crash in `less` con una dimensione del terminale modificabile dall'attaccante; il pager poteva quindi fornire una shell root se erano soddisfatte le condizioni speciali relative a sudo e al pager. Prima di considerare vulnerabile una versione, verifica la regola sudo effettiva, la configurazione del pager e le correzioni dei pacchetti della distribuzione. Durante l'enumerazione passiva, consulta i metadati dei pacchetti e delle policy senza generare un crash né aprire il report con privilegi elevati. Il [record CVE di Ubuntu](https://ubuntu.com/security/CVE-2023-1326) elenca le versioni corrette dei pacchetti specifiche per ciascuna release, incluse le correzioni retroportate.

```text
!/bin/sh
```

## Altri rischi nelle regole di sudo e doas

Inizia con `sudo -l`, `sudo -V` e qualsiasi policy `doas` applicabile. Esamina insieme il comando consentito, l'utente RunAs, gli argomenti, l'ambiente e i valori predefiniti. Il permesso di eseguire comandi come un account di servizio non-root può comunque esporre i file di quell'account o offrire un percorso verso root.

Uno script Python autorizzato da sudo e con percorso fisso può comunque eseguire un comando shell con l'identità RunAs se concatena input interattivi controllati dal chiamante in [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist della punteggiatura shell non basta a garantire la sicurezza: la [shell riconosce anche la sostituzione di comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Verifica che gli argomenti consentiti raggiungano il ramo di input, che l'input arrivi al comando shell senza una validazione sicura e che la policy sudo effettiva consenta l'utente RunAs previsto. Il percorso dello script o una chiamata a `os.system()` sono solo spunti per una verifica: esamina il sorgente senza eseguire lo script privilegiato.

Un'autorizzazione sudo effettiva come root per `chattr` può rimuovere l'attributo immutabile (`i`) di un file, ma da sola non concede né la possibilità di scriverlo né una nuova identità. [Il manuale di `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) specifica che l'attributo impedisce le modifiche e che solo root o un processo con `CAP_LINUX_IMMUTABLE` può cambiarlo. Verifica gli argomenti esatti consentiti da sudo e il supporto del filesystem, poi controlla separatamente che il chiamante possa scrivere il file una volta rimosso l'attributo e che un componente con identità superiore lo utilizzi. Per esempio, sostituire la shell di login richiede anche credenziali accettate dall'account di destinazione e un login effettivo tramite quella shell. Durante l'enumerazione, esamina la policy, gli attributi dei file e i permessi senza modificarli.

Se sudo richiede sia una password sia un codice monouso, considera questi prerequisiti separatamente dall'autorizzazione del comando. Un file `.google_authenticator` leggibile contiene materiale seed sensibile, mentre un vecchio hash della password di un'applicazione o di un database è solo una possibile password attuale dell'account; nessuno dei due dimostra che il fattore rimanente sia accettato dalla configurazione PAM effettiva. Una volta autorizzato, esamina RunAs e gli argomenti esatti: un'autorizzazione root senza restrizioni per `gem` di RubyGems può esporre il comando dell'editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ma un'autorizzazione limitata o un'autenticazione fallita no. L'enumerazione passiva dovrebbe riportare percorsi e policy senza stampare il seed, recuperare una password, generare un codice o invocare il comando privilegiato.

Un'autorizzazione sudo senza restrizioni, efficace come root, per `knife` di Chef merita una verifica a livello di interprete: [Chef documenta che `knife exec -E` valuta localmente una stringa Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica che la regola sudo effettiva consenta il sottocomando `exec`, l'argomento `-E` fornito dal chiamante, l'identità RunAs prevista e qualsiasi negazione del comando o argomento fisso corrispondente. Il binario installato o una regola limitata ad altri sottocomandi sono solo spunti. L'enumerazione passiva dovrebbe riportare la regola senza invocare `knife`.

Un'autorizzazione sudo esatta ed efficace come root per `msfconsole` interattivo è altrettanto sensibile: [GTFOBins documenta la sua console `irb`](https://gtfobins.org/gtfobins/msfconsole/), che può ereditare l'identità sudo. Verifica l'utente RunAs effettivo, l'elenco degli argomenti consentiti, le negazioni del comando, `NOEXEC` o altre restrizioni, il comportamento della console installata e la possibilità per il chiamante di fornire input interattivo. Il solo percorso evidenziato è uno spunto per la verifica; l'enumerazione passiva non dovrebbe avviare la console.

Su FreeBSD, anche una regola sudo limitata a `pkg update` e `pkg install *` come root merita una verifica della fiducia nei repository. Controlla se il chiamante può scrivere `/etc/hosts` e se la configurazione *effettiva* dei repository abilitati usa un hostname HTTP con `signature_type: none`. [Il manuale di `pkg.conf` di FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) specifica che `none` disabilita i controlli delle firme; il solo uso di `pkg+http` non lo dimostra. Un pacchetto può contenere script di installazione ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), quindi un chiamante che controlla davvero l'endpoint del repository e può selezionare un pacchetto può oltrepassare il confine di root. Verifica gli override dei repository, la risoluzione SRV/mirror, gli argomenti sudo effettivi, la selezione del pacchetto e l'esecuzione degli script prima di giungere a tale conclusione. Esamina la policy e i piccoli file di configurazione locali senza reindirizzare i nomi o eseguire `pkg` durante l'enumerazione.

Anche un'autorizzazione sudo efficace come root per `apt-get update` e `apt-get upgrade` richiede una verifica della fiducia nei repository quando sudo conserva un `http_proxy` controllato dal chiamante. Controlla se la configurazione APT effettiva usa davvero quella variabile e quali richieste ai repository abilitati può influenzare; un proxy da solo non può sostituire pacchetti provenienti da un archivio autenticato con una chiave di firma attendibile. [Il manuale del trasporto HTTP di APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) descrive la precedenza dei proxy, mentre [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta i controlli delle firme, gli override per i repository non sicuri e la conferma richiesta per i pacchetti non autenticati. Verifica RunAs e gli argomenti sudo esatti, la policy di autenticazione dei repository, eventuali conferme interattive richieste e se l'aggiornamento selezionato esegue script di pacchetto come root. Esamina passivamente la policy e la configurazione locale; durante l'enumerazione non reindirizzare il traffico dei pacchetti né eseguire un aggiornamento.

Una regola sudo efficace come root per `snap install` può creare un confine tra pacchetto e codice se gli argomenti consentono al chiamante di selezionare uno snap locale e una modalità di installazione permissiva. [La documentazione di Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) specifica che `--dangerous` salta i controlli delle asserzioni sugli snap locali e `--devmode` allenta il confinamento; [un hook di installazione può essere eseguito all'installazione iniziale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prima di affermare che è possibile accedere a file host protetti, verifica la policy sudo esatta per argomenti e RunAs, chi controlla il file snap, se la versione installata di snapd accetta queste modalità e l'identità effettiva e il confinamento dell'hook. Un binario `snap` o una regola che sembra contenere un wildcard non dimostrano da soli questa catena. Durante l'enumerazione passiva, non installare pacchetti né eseguire i relativi hook.

Per un'autorizzazione sudo esatta a un binario personalizzato che legge credenziali ed è eseguito come account **non-root**, esamina prima il binario autorizzato e i permessi dei suoi file senza eseguirlo. Una verifica della password incorporata può essere visibile solo come caratteri wide; [GNU `strings` documenta l'estrazione little-endian a 16 bit](https://sourceware.org/binutils/docs/binutils/strings.html). Una stringa visibile non dimostra che sia la password accettata né che il ramo di successo esponga una credenziale attuale. Verifica separatamente il comportamento del binario, l'accesso dell'account di destinazione ai dati protetti, la validità delle credenziali e qualsiasi successivo cambio di account o gruppo. Se l'account appartiene al gruppo `docker`, verifica l'accesso al socket e l'identità rootful o rootless del daemon prima di dedurre l'accesso a root sull'host; [Docker documenta le implicazioni a livello root del suo gruppo](https://docs.docker.com/engine/install/linux-postinstall/). L'enumerazione ordinaria dovrebbe riportare la regola sudo e l'appartenenza ai gruppi senza eseguire il binario né scaricarne le stringhe.

Una regola sudo con wildcard per gli script di manutenzione di un'applicazione richiede verifiche che vadano oltre il percorso dello script. Controlla se lo script consentito accetta argomenti senza restrizioni o legge impostazioni scrivibili da un account applicativo con privilegi inferiori, poi segui il flusso di quei valori fino ai comandi shell o all'ambiente di un subprocesso. Per esempio, [`zmupdate.pl` di ZoneMinder assembla un comando `mysqldump` e lo esegue tramite `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mentre [`zmdc.pl` copia l'impostazione `ZM_LD_PRELOAD` in `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) prima di avviare i daemon. Una regola sudo che consente di eseguire come root uno dei due script può oltrepassare un confine di fiducia se l'input corrispondente è controllabile e raggiunge quel codice nella versione installata. Esamina la regola sudo effettiva, i permessi sulla configurazione dell'applicazione e il sorgente dello script; il wildcard o l'impostazione, da soli, sono spunti per la verifica, non prove di esecuzione.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` possono trasformare un comando altrimenti limitato in un hijack di import, libreria o PATH. Vedi la [guida alle variabili d'ambiente](../linux-basics/linux-environment-variables.md) e [abuso di SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Un'autorizzazione `SETENV` esatta, efficace come root, per un wrapper shell merita anche una verifica a un salto se il wrapper avvia uno script Python fisso con un import letterale. `secure_path` limita la ricerca dei comandi shell, non la [ricerca dei moduli Python tramite `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fanno sì che Python ignori quella variabile d'ambiente. Prima di considerarlo un caso di esecuzione di codice, verifica i tag e le negazioni sudo effettivi, il ramo del wrapper, le opzioni dell'interprete, la risoluzione degli import e la presenza di una directory di ricerca scrivibile dal chiamante. Esamina staticamente gli script brevi; non invocare il wrapper privilegiato.

Un'autorizzazione sudo esatta ed efficace come root per `neofetch ""` può comunque caricare una configurazione shell quando i valori predefiniti sudo applicabili conservano un `XDG_CONFIG_HOME` controllato dal chiamante. [Il loader di configurazione di Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) esegue il source di `neofetch/config.conf` o `neofetch/config` all'interno di quella directory; l'elenco di argomenti vuoto non impedisce questa ricerca. Verifica il loader installato, la policy effettiva per RunAs e argomenti, eventuali negazioni del comando, se sudo conserva davvero la variabile scelta per questo comando e se il chiamante controlla un percorso di configurazione leggibile. Una variabile conservata o la sola presenza di Neofetch sono spunti per la verifica. Esamina la policy e i metadati dei file senza invocare il comando privilegiato né stampare i contenuti della configurazione; vedi [la gestione dell'ambiente in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regola sudo senza restrizioni ed efficace come root per `facter` merita una verifica separata dei custom fact. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) che `--custom-dir` carica file Ruby di fact da una directory selezionata. Controlla se la regola sudo esatta consente tale opzione, se Facter installato la accetta e se il chiamante controlla la directory. Un'autorizzazione con argomenti fissi, una negazione esplicita del comando o i custom fact disabilitati possono cambiare l'esito. L'enumerazione passiva dovrebbe segnalare la possibile regola senza invocare Facter né leggere il contenuto dei fact.

Per un'autorizzazione sudo esatta a uno script efficace come root e con `SETENV`, esamina i nomi di comando senza percorso, come `find`, e il `PATH` effettivo dopo l'applicazione della policy sudo e l'inizializzazione dello script. Un file Bash eseguito tramite `source` può anche eseguire `enable -n [`: [Bash cerca quindi in `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un eseguibile esterno `[` quando lo script usa in seguito quel comando. Verifica le [regole sudoers applicabili sull'ambiente e su `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), eventuali voci `NOSETENV`/`NOEXEC` o di negazione, il flusso dello script e dei file caricati tramite `source` e la presenza di una directory di ricerca eseguibile controllata dal chiamante. Uno script leggibile contenente un comando senza percorso è uno spunto per la verifica, non la prova di un'esecuzione privilegiata; esaminalo senza invocare la regola sudo.
- Uno script privilegiato che recupera un URL fisso con `curl` può comunque ricevere una risposta scelta dal chiamante se una regola sudo applicabile conserva `http_proxy` e la richiesta viene inviata tramite quel proxy. Se lo script passa poi la risposta a un parser XML che risolve entità esterne, una risposta malevola può divulgare file leggibili dal processo privilegiato. Verifica la policy sudo esatta per l'ambiente, le esclusioni `no_proxy`, l'URL richiesto, la configurazione del parser e la destinazione dell'output; una variabile proxy o un parser XML, da soli, non costituiscono una vulnerabilità. La [documentazione dell'ambiente proxy di curl](https://everything.curl.dev/usingcurl/proxies/env.html) descrive il comportamento di queste variabili. Durante l'enumerazione passiva, non effettuare richieste di rete né analizzare XML ostile.
- Uno script sudo efficace come root che crea un file PostScript da dati influenzabili dal chiamante e poi esegue `ps2pdf -dNOSAFER` merita una verifica separata del flusso dell'input. Ghostscript documenta che questo flag disabilita SAFER fino a `.setsafe`, consentendo operazioni sui file PostScript nei limiti dei permessi del processo sul sistema operativo. Una query SQL assemblata usando un argomento del chiamante può fornire righe controllate dall'attaccante al template PostScript, ma una stringa di query o una chiamata a `ps2pdf`, da sole, non dimostrano che i dati raggiungano la sintassi PostScript eseguibile. Verifica la regola sudo effettiva, il percorso esatto dall'input al template, eventuali escaping, il comportamento della versione installata di Ghostscript e se SAFER viene riattivato prima di interpretare il documento. Durante l'enumerazione passiva, non invocare la conversione privilegiata. Vedi la [documentazione di Ghostscript su `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Per una regola sudo che esegue uno script shell, confronta le variabili conservate con lo script stesso. Un costrutto come `if $CHECK_CONTENT; then` esegue il valore espanso come comando, quindi conservare `CHECK_CONTENT` può consentire l'esecuzione di comandi anche quando il percorso e gli argomenti dello script sono fissi. Per la regola specifica, verifica se il ramo è raggiungibile e se l'ambiente viene davvero conservato.<sup>[[2]](#references)[[22]](#references)</sup>
- Uno script Python autorizzato da sudo può importare codice da una directory scrivibile o da un file `.pyc` in cache. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md) approfondisce il caso della cache.
- Uno script Python fisso autorizzato a essere eseguito come root può comunque esporre un debugger interattivo. Chiamate come `pdb.set_trace()` o `pdb.post_mortem()` consentono di eseguire istruzioni Python nel contesto del processo sottoposto a debug quando il chiamante può raggiungere il breakpoint o il gestore delle eccezioni **e controllare lo stream di input del debugger**. Verifica la regola sudo esatta per RunAs, l'autenticazione e le condizioni del ramo, la raggiungibilità dell'eccezione, la proprietà del terminale/input e se il debugger viene eseguito nello stesso processo privilegiato. Una richiesta socket che attiva un'eccezione non concede di per sé accesso a un debugger collegato a un altro terminale. [Python documenta la valutazione delle istruzioni nel debugger e la modalità post-mortem](https://docs.python.org/3/library/pdb.html); esamina staticamente lo script anziché attivare il gestore privilegiato durante l'enumerazione.
- Uno script Python fisso autorizzato da sudo può anche leggere un campo di profilo da un database o socket Unix e aggiungerlo a una stringa che diventa in seguito la **stringa di formato** per `str.format()`. [I campi di sostituzione possono accedere ad attributi e chiavi di mapping](https://docs.python.org/3/library/string.html#format-string-syntax), quindi un campo controllato da un attaccante può ispezionare gli oggetti passati a `format()` ed esporre dati accessibili da essi se il risultato viene stampato o salvato in un luogo leggibile dal chiamante. Verifica l'identità RunAs sudo effettiva, il permesso di scrittura sul record specifico, il flusso dei dati nella stringa di formato, gli oggetti forniti e la visibilità dell'output. Non si tratta di esecuzione automatica di codice; una stringa di formato letterale e attendibile con *valori* controllati dall'attaccante è un caso diverso. Un segreto divulgato permette il passaggio a un account del sistema operativo solo se quell'account lo accetta. Esamina lo script e i permessi del socket senza invocare l'operazione privilegiata.
- Un wrapper Python efficace come root può passare un URL scelto dal chiamante a `Repo.clone_from` di GitPython. Se il wrapper abilita anche `protocol.ext.allow=always` di Git, un remote `ext::` può invocare un helper esterno. Verifica gli argomenti sudo esatti, la provenienza dell'URL, la versione del pacchetto GitPython e lo stato delle patch del vendor, nonché l'eventuale abilitazione esplicita di protocolli non sicuri da parte del wrapper. GitPython ha introdotto una [protezione predefinita dai protocolli non sicuri](https://github.com/gitpython-developers/GitPython/commit/2625ed9) nella versione 3.1.30; la versione dell'eseguibile `git` è un dato separato. La verifica passiva dovrebbe limitarsi a leggere la regola e una porzione limitata del sorgente, senza avviare il clone.
- Un'autorizzazione sudo tra utenti per uno strumento CLI che clona repository può esporre un percorso separato di injection nella stringa shell. Segui l'argomento del repository scelto dal chiamante fino a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) di Node.js o a un altro generatore di comandi shell, verificando che non venga usata una separazione sicura degli argomenti; `exec` di Node passa la stringa di comando a una shell. Verifica l'utente RunAs esatto, i sottocomandi e gli argomenti consentiti, il codice del wrapper installato e la validazione dell'input. Il nome dello strumento per repository o una regola sudo senza restrizioni, da soli, non dimostrano l'injection di comandi. Esamina il wrapper senza avviare un clone privilegiato durante l'enumerazione.
- Un wrapper personalizzato di proprietà di root può sembrare sicuro perché i suoi binari e script non sono scrivibili, ma la decisione di eseguire un'azione privilegiata può dipendere da un flag, un valore di un'API locale o uno stato del servizio modificabile da un utente non privilegiato. Segui ogni condizione fino al relativo input e ai controlli di autorizzazione. Durante l'enumerazione, esamina configurazione e permessi senza modificare lo stato operativo; una chiamata a `systemd-run` nel wrapper è rilevante solo se la condizione può essere influenzata.
- Un client di backup autorizzato tramite sudo come root può accettare un file di configurazione scelto dal chiamante (per esempio, `npbackup-cli -c`). Verifica l'utente RunAs e gli argomenti consentiti, poi controlla se il chiamante controlla il percorso di configurazione, i percorsi sorgente del backup e le opzioni del repository o di lettura/ripristino. Un segreto di un repository cifrato presente in una configurazione leggibile può comunque essere utilizzabile dal client, ma la sola regola non dimostra l'accesso al repository né la divulgazione di file root. Verifica l'autorizzazione senza eseguire un backup né scaricarne i contenuti.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) supporta `--password-command`, che chiama un programma per ottenere la password del repository. Se una regola sudo consente a un utente con privilegi inferiori di eseguire restic come root con un comando password scelto dal chiamante e un sottocomando che richiede la password, l'helper può essere eseguito come root. Esamina gli argomenti sudo esatti e le esclusioni; non invocare l'helper né un comando di backup solo per verificare la condizione.
- Un'autorizzazione privilegiata per `restic backup` può anche oltrepassare il confine di lettura dei file se il pattern degli argomenti sudo consente al chiamante di scegliere sia la sorgente sia un repository che potrà leggere e decifrare in seguito. [I wildcard degli argomenti sudoers possono corrispondere a spazi e slash](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), quindi esamina i wildcard finali anziché presumere che un prefisso fisso del repository limiti la sorgente. [Restic può eseguire backup su repository locali e remoti](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), ma un repository locale può contenere oggetti appena scritti e accessibili solo a root; prima di considerarlo una divulgazione, verifica la policy sudo effettiva, l'accesso al backend, la password del repository e i permessi degli oggetti risultanti. Una chiave SSH sottoposta a backup consente l'accesso solo se l'account di destinazione la accetta. Durante una verifica passiva, non eseguire un backup per testare questa ipotesi.
- Un comando personalizzato di manutenzione o backup senza restrizioni può accettare un percorso di output oppure disporre di un proprio scheduler. Per un percorso di scrittura su file, verifica la regola sudo esatta e l'utente RunAs, poi controlla se il chiamante controlla sia i dati sia la destinazione. Per un percorso con comandi pianificati, verifica l'identità di esecuzione dello scheduler, l'input del comando ed eventuali ulteriori verifiche di password o autorizzazione. Il nome del comando o `NOPASSWD`, da soli, non dimostrano nessuna delle due possibilità. Vedi [scrittura su file di proprietà di root](../interesting-files-permissions/write-to-root.md) e [cron e timer systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando sudo fisso può comunque caricare un file di configurazione prevedibile da una directory condivisa e scrivibile. Verifica se il chiamante può sostituire quel file e se i suoi campi source e destination controllano un fetch o una copia privilegiati. Un URL locale può esporre dati leggibili solo dall'account RunAs di sudo; una sorgente controllata dal chiamante abbinata a una destinazione protetta può creare un percorso di scrittura. Verifica la gestione degli URL da parte del programma installato, i controlli sul percorso di destinazione, la regola sudo effettiva e l'accessibilità dell'output. Un percorso di configurazione scrivibile in `/tmp` è solo uno spunto: esamina binario e metadati dei file senza invocare il trasferimento privilegiato.
- Una regola sudo per `git apply` può consentire all'account RunAs di scrivere file selezionati da una patch controllata dal chiamante. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) consentiva a una patch appositamente creata di creare un symlink e poi scrivere al di fuori dell'albero di lavoro, anche se il comando non accettava `--unsafe-paths`. Verifica la regola sudo effettiva per gli argomenti, la provenienza della patch, l'accesso dell'account RunAs alla directory di lavoro e la correzione di Git installata o il backport del vendor. Una regola senza restrizioni che ammette `--unsafe-paths` comporta un rischio separato dovuto a un'opzione esplicita; né la versione di Git né il solo permesso di eseguire `git apply` dimostrano che sia possibile modificare un file protetto. Durante l'enumerazione passiva, non applicare patch non attendibili.
- Una regola sudo efficace come root per `clamscan --debug` può oltrepassare un confine di lettura se un utente con privilegi inferiori può fornire un'immagine DMG e il parser installato è affetto da [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), che poteva divulgare contenuti dei file tramite l'output di debug. Verifica gli argomenti esatti consentiti e il percorso di scansione, il controllo dell'input, l'account RunAs effettivo, la patch/backport del motore e la visibilità dell'output per il chiamante. Se una regola più ampia consente `--file-list`/`-f`, verifica separatamente quel comportamento; una policy fissa a `--debug <scan-path>` non lo ammette. Durante l'enumerazione, esamina la policy e i metadati del pacchetto senza scansionare un file appositamente creato né stampare output protetto.
- Una regola sudo efficace come root che apre un'immagine disco cifrata scelta dal chiamante e una seconda regola che monta il mapper risultante possono importare file controllati dal chiamante nello spazio dei mount dell'host. Verifica entrambe le regole effettive e i relativi argomenti, il controllo dell'immagine e del nome del mapper, il punto di mount effettivo e proprietario e modalità dei file risultanti. Un passaggio a un'identità set-user-ID richiede inoltre un eseguibile accessibile, opzioni di mount che lo consentano (`nosuid` lo blocca) e policy di processo o MAC applicabile; aprire o montare un'immagine è solo uno spunto per la verifica. Un percorso separato tramite un backup esistente richiede la sua chiave effettiva e un segreto utile e leggibile al suo interno. Durante la verifica passiva, esamina policy e percorsi senza aprire né montare immagini. Vedi il [manuale di cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e le [opzioni di mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regola sudo efficace come root per uno script shell o Python merita una verifica della directory di lavoro se lo script invoca `./helper` senza prima passare a una directory fissa. Anche una lista Python come `['./helper']` passata a `subprocess.run` può dipendere dalla directory di lavoro scelta dal chiamante. Il chiamante potrebbe selezionare una directory scrivibile e collocarvi un eseguibile con quel nome relativo; un percorso assoluto in un'altra parte dello script non protegge questa chiamata. Prima di considerarlo esecuzione di codice, verifica la regola effettiva, `runchdir` o altre policy che cambiano directory, il flusso dello script e la raggiungibilità del ramo, una directory scrivibile ed eseguibile e le restrizioni di mount/`NOEXEC`. Se lo script non è leggibile, il comportamento resta sconosciuto finché non se ne esamina il sorgente tramite un percorso autorizzato. Esamina staticamente gli script invece di eseguire l'helper. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta le policy sulle directory di lavoro.
- Un validatore Python fisso efficace come root può comunque valutare un file di dati scelto dal chiamante. La [documentazione di `eval()` di Python mette in guardia sull'input non attendibile](https://docs.python.org/3/library/functions.html#eval): un controllo del suffisso dell'input, un prefisso aritmetico o un ramo di validazione non costituiscono una sandbox se l'espressione rimanente raggiunge `eval`. Prima di definirlo un percorso di esecuzione, verifica la regola sudo effettiva, se il chiamante può scegliere e controllare il file esatto, le condizioni dei rami del parser e la costruzione dell'espressione, nonché l'identità del processo privilegiato. La presenza di `eval` in uno script leggibile è solo un indizio per la verifica; durante l'enumerazione, esamina sorgente e permessi dei file senza eseguire il validatore né inviare un'espressione di test.
- Un wrapper Ruby sudo efficace come root che legge un nome di file YAML relativo, come `YAML.load(File.read("dependencies.yml"))`, può ricevere input dalla directory di lavoro del chiamante, a meno che il wrapper o la policy sudo non fissino tale directory. Verifica gli argomenti consentiti esatti, i permessi di directory e file e il comportamento di Psych installato: le versioni precedenti di `YAML.load` potevano deserializzare oggetti Ruby arbitrari, mentre quelle più recenti limitano le classi per impostazione predefinita. Una chiamata statica è solo uno spunto: verifica che il file provenga davvero da una directory scrivibile dal chiamante e che il loader installato accetti classi pericolose. Per input non attendibile, preferisci `safe_load` con un allowlist esplicito e minimo di classi. Vedi la [documentazione di Psych per Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e la [documentazione di Psych per Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Un'autorizzazione sudo esatta, efficace come root, per `sudo go run /absolute/file.go` merita una verifica della directory di lavoro quando il sorgente Go legge un file WASM relativo e potrebbe eseguire uno script shell relativo dopo averne esaminato il risultato. Verifica RunAs effettivo, argomenti e negazioni del comando, la presenza di una directory corrente scrivibile dal chiamante, il flusso dei dati dal WASM al ramo e se quel ramo invoca l'helper. Un `runchdir` sudo fisso, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) possono cambiare la directory di ricerca. Una semplice co-occorrenza statica è solo un possibile caso: esamina il sorgente senza eseguire Go, WASM o l'helper.
- `sudoedit` e i wildcard degli argomenti richiedono verifiche precise della versione e della regola; la [checklist](linux-privilege-escalation-checklist.md) include il problema di modifica dei file con sudoedit. Per un'autorizzazione `sudoedit` tra utenti su un percorso con wildcard, esamina l'impostazione effettiva `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, la destinazione risolta e chi può sostituire ogni voce di directory padre. La prima può consentire di seguire un symlink, mentre la disattivazione della seconda elimina i controlli sulle directory scrivibili; nessuna delle due impostazioni, da sola, dimostra la possibilità di scrivere il file di un altro utente. Prima di giungere a tale conclusione, verifica la policy sudo installata e gli argomenti esatti corrispondenti. Vedi le [definizioni delle opzioni sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In una regola di comando sudoers, un wildcard negli argomenti può corrispondere anche agli spazi, oltre che ai caratteri dei percorsi. Una regola per un comando capace di leggere file, con un argomento come `/restricted/*`, può quindi ammettere un ulteriore argomento file dopo un prefisso corrispondente. Esamina l'utente RunAs esatto, il percorso del comando, il pattern degli argomenti e le eventuali negazioni successive; la lettura dimostrata di un file non implica l'esecuzione di comandi. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue i glob degli argomenti da quelli del percorso del comando.
- Anche un glob degli argomenti che sembra un percorso può corrispondere a `../`. Per esempio, una regola root per `node /opt/scripts/*.js` può consentire al chiamante di scegliere un file JavaScript al di fuori di `/opt/scripts` se il percorso fornito inizia comunque con `/opt/scripts/` e viene risolto tramite segmenti di directory padre. Si tratta di un glob degli **argomenti**; il glob del percorso dell'eseguibile Node segue regole diverse per la corrispondenza degli slash. Prima di concludere che si possa eseguire codice, verifica la regola effettiva, le negazioni successive, la risoluzione del percorso, il controllo del file di destinazione ed eventuali restrizioni sudoers basate su espressioni regolari o digest. Vedi le [regole dei wildcard sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e la [documentazione della riga di comando di Node](https://nodejs.org/api/cli.html).
- Archiviatori e altri programmi di utilità possono avere hook di esecuzione. Verifica gli argomenti esatti consentiti con [GTFOBins](https://gtfobins.github.io/) anziché presumere che solo shell o interpreti eseguano comandi.
- Una regola `qpdf` senza restrizioni ed efficace come root può esporre un file privilegiato tramite allegati PDF: qpdf 10.2 e versioni successive supportano `--empty` e `--add-attachment file ... --` con un PDF di output. Se il processo privilegiato può leggere la sorgente selezionata e scrivere il PDF in un percorso accessibile al chiamante, l'output può contenere i byte della sorgente. Prima di concludere che sia possibile divulgare file, esamina gli argomenti sudo effettivi e le esclusioni, la versione di qpdf, l'accesso alla sorgente e il percorso di output. Leggere una chiave SSH di root è utile per il login solo se la chiave è valida e l'autenticazione SSH di root è consentita. Vedi le [opzioni degli allegati di qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Il riutilizzo dei timestamp sudo dipende dalla policy della cache, dall'utente proprietario, dal terminale/sessione e dai permessi. La [guida all'escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) illustra i controlli.
- `doas` ha regole e configurazione proprie. Verifica i comandi consentiti e i percorsi di configurazione scrivibili come descritto nella [sezione doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Strumenti di build e pacchetti eseguiti tramite sudo

Un'autorizzazione sudo senza restrizioni per `forge` di Foundry può essere rilevante anche quando l'identità RunAs è un altro utente non-root. Opzioni del compilatore come `--use` possono selezionare un eseguibile locale e `forge flatten -o` seleziona un file di output. Prima di considerare sfruttabile l'autorizzazione, verifica la versione di Forge installata, gli argomenti sudo esatti, i percorsi del progetto e del compilatore accessibili, i permessi di output e l'ambiente effettivo. Un eseguibile helper relativo trovato tramite `PATH` è un percorso dipendente dalla versione e dall'ambiente, non una caratteristica da presumere per ogni build Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Un'autorizzazione `pacman` senza restrizioni ed efficace come root consente più delle query sui pacchetti: `-U` accetta un pacchetto locale, i pacchetti possono contenere script di installazione e `--hookdir` seleziona un'altra directory di hook. Prima di testare, esamina la regola sudo effettiva, le restrizioni sugli argomenti e le esclusioni; per l'enumerazione passiva non serve installare pacchetti né eseguire hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fisso eseguito tramite sudo può anche installare una dipendenza npm nominata e poi avviare un'applicazione Node. Esamina la regola RunAs esatta, se il pacchetto è già installato, `HOME` e `userconfig` npm effettivi, la configurazione del progetto o gli override della riga di comando e se un utente con privilegi inferiori controlla il registry o il pacchetto restituito per quel nome. [npm documenta la ricerca di `.npmrc` a livello di utente e di progetto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); il comportamento di `HOME` in sudo dipende dalla policy installata e dalla distribuzione, quindi il processo npm privilegiato può leggere o meno il file `.npmrc` di un utente scrivibile. Se il pacchetto appena installato viene importato dall'applicazione privilegiata, il suo codice può essere eseguito con l'identità di quell'applicazione. Gli script eseguiti al momento dell'installazione costituiscono un percorso separato, dipendente da versione e configurazione; [npm ne documenta il ciclo di vita e la gestione degli utenti](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un percorso `.npmrc` o una riga `npm install`, da soli, sono solo spunti per la verifica. Durante l'enumerazione passiva, esamina la regola, il wrapper breve, i percorsi di configurazione e la provenienza del pacchetto senza installare o avviare l'applicazione.

Un'autorizzazione root per `pip` o `pip3 download` è anche uno spunto per verificare la build dei pacchetti quando gli argomenti consentono al chiamante di selezionare una distribuzione sorgente non attendibile, anche se il pattern dell'URL la limita a un servizio locale e al suffisso `.tar.gz`. `pip download` accetta URL di archivi e risolve i metadati dei pacchetti; la preparazione di una distribuzione sorgente può invocare il backend di build o il codice legacy `setup.py` prima che l'archivio venga semplicemente salvato. Verifica la regola sudo esatta per RunAs e argomenti, se il chiamante può pubblicare o sostituire l'archivio selezionato e se quella versione di pip prepara davvero i metadati. Un archivio fisso e attendibile o un wheel non dimostrano questo percorso. Durante l'enumerazione passiva, non scaricare né compilare pacchetti non attendibili. Vedi il [comando download di pip](https://pip.pypa.io/en/stable/cli/pip_download/), l'[interfaccia del sistema di build](https://pip.pypa.io/en/stable/reference/build-system/) e le [indicazioni per installazioni sicure](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regola sudo che consente `pip install` con un percorso di progetto locale scelto dal chiamante crea un confine di build più diretto. [pip accetta directory di progetti locali](https://pip.pypa.io/en/stable/topics/local-project-installs/) e ne invoca il sistema di build; il [backend di build esegue hook controllati dal progetto](https://pip.pypa.io/en/stable/reference/build-system/). Prima di considerare la regola un'esecuzione di codice privilegiata, verifica l'identità RunAs effettiva, le restrizioni e le negazioni esatte degli argomenti, il controllo del progetto selezionato e il comportamento di pip/backend installati. Un progetto fisso e attendibile o una regola che esclude percorsi scelti dal chiamante non dimostrano questo percorso. Durante l'enumerazione passiva, esamina la regola e i metadati del progetto senza installare pacchetti.

Un'autorizzazione `easy_install` senza restrizioni ed efficace come root è un indizio analogo per la build di pacchetti legacy. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) che Easy Install accetta una directory di progetto locale e crea distribuzioni sorgente; durante la build, un progetto controllato dal chiamante può eseguire `setup.py` con l'identità sudo. Verifica l'account RunAs effettivo, i vincoli esatti su comando e argomenti (incluse eventuali negazioni successive), il controllo del progetto selezionato e il comportamento dello strumento installato. Un progetto fisso e attendibile o una policy che non consente di selezionare una sorgente da parte del chiamante non dimostrano questo percorso. Durante l'enumerazione, esamina la regola e i metadati del progetto senza installare pacchetti.

Un wrapper Python autorizzato da sudo che usa `setuptools.package_index.PackageIndex.download` con un URL scelto dal chiamante richiede una verifica diversa da `pip download`: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descrive come, nelle versioni affette precedenti alla 78.1.1, un nome file derivato dall'URL potesse uscire dalla directory di download prevista e scrivere con i permessi del processo. Verifica l'utente RunAs e la regola degli argomenti sudo effettivi, che il wrapper passi l'URL del chiamante a questa API esatta, la build installata o il backport del vendor e il percorso di destinazione risultante. Una stringa di versione o una directory di download scrivibile, da sole, non dimostrano la possibilità di scrivere in modo arbitrario. Durante l'enumerazione, esamina il wrapper breve e i metadati del pacchetto senza scaricare l'URL né scrivere file.

Un wrapper di build consentito da sudo che passa a PyInstaller un file `.spec` scelto dal chiamante richiede una verifica analoga del confine di fiducia. Un file spec PyInstaller è codice Python eseguibile valutato durante la **build**, e le sue voci `datas` possono inserire in un artifact file leggibili dall'identità di build. Verifica l'utente RunAs esatto, le regole sudo sugli argomenti e sulle negazioni, la gestione dei percorsi e dei rami del wrapper, il controllo del file spec selezionato e l'accesso all'artifact risultante. Consentire semplicemente un input `.py` o trovare PyInstaller installato non dimostra che il chiamante controlli il file spec o possa eseguire codice privilegiato. Una verifica passiva dovrebbe esaminare solo un file wrapper limitato e i relativi metadati; non dovrebbe avviare una build. Vedi la [documentazione dei file spec di PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loader di preset e plugin eseguiti tramite sudo

Gli strumenti Python che accettano un preset scelto dal chiamante o una directory di plugin possono importare codice con i privilegi concessi da sudo. Per esempio, BBOT accetta un preset tramite `-p` e la sua [documentazione dei moduli personalizzati](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descrive voci `module_dirs` che selezionano directory aggiuntive di moduli Python. Se la regola sudo effettiva consente un preset scelto dal chiamante e quest'ultimo controlla un modulo nella directory selezionata, l'import può eseguire codice come utente privilegiato, potenzialmente prima che lo strumento rifiuti un modulo non valido. Durante l'enumerazione, verifica la versione installata, la policy sudo esatta per RunAs e argomenti e la proprietà dei percorsi del preset e del modulo senza caricare il modulo.

### Strumento a riga di comando Backdrop eseguito tramite sudo

[Bee](https://github.com/backdrop-contrib/bee) è uno strumento PHP a riga di comando per Backdrop CMS. I suoi comandi `eval` (`php-eval`) e `php-script` possono eseguire PHP fornito dal chiamante. Una regola sudo che consente di eseguire l'eseguibile Bee come root con argomenti senza restrizioni può quindi esporre l'esecuzione di codice come root quando Bee riesce ad avviare un'installazione Backdrop. Eseguilo dalla directory del sito oppure seleziona un sito usando l'opzione globale `--root=<directory>`; trovare Bee o un file Backdrop `settings.php` non dimostra il permesso sudo, l'esistenza di un sito utilizzabile o il successo dell'avvio. Prima di testare, esamina la regola sudo effettiva, eventuali esclusioni del comando, l'identità dell'eseguibile e l'accesso al sito. Durante l'enumerazione passiva, esamina la regola e i percorsi dei file senza invocare Bee. Vedi il [changelog dei comandi Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) per l'aggiunta dei comandi PHP.

### Server di terminale eseguiti tramite sudo

`mosh-server` avvia un server di terminale interattivo come utente invocante. Sceglie una porta UDP alta e una chiave di sessione, comunica entrambi al chiamante e, normalmente, avvia la shell di login di quell'utente quando un client si connette. Un'autorizzazione sudo senza restrizioni ed efficace come root per `mosh-server` è quindi un possibile caso da verificare come shell, anche se il comando del server si scollega. Verifica l'identità RunAs effettiva, gli argomenti consentiti e le esclusioni, il binario installato, la shell, la disponibilità del client e l'accesso UDP. Durante l'enumerazione passiva, esamina la regola sudo senza avviare un server né stampare una chiave di sessione attiva. Vedi il [manuale del server Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e le [note di progettazione upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrapper di backup privilegiati che riscrivono il file di task del chiamante

Un wrapper shell eseguito come root può accettare un file di task scelto dal chiamante, rimuovere `../` dai percorsi sorgente, verificare che ogni risultato inizi con una directory consentita, riscrivere il file di task e poi passare al programma di backup il suo *percorso*. Esamina il percorso trasformato dopo la risoluzione canonica completa: una singola sostituzione testuale può creare una nuova sequenza di traversal che supera un controllo lessicale del prefisso. Verifica anche se il programma di backup legge i dati trasformati in memoria o riapre il file. Se lo riapre, una riscrittura fallita può lasciare intatto l'input originale.

Su Linux, `fs.protected_regular` può negare una scrittura `O_CREAT` sul file regolare di un altro utente all'interno di una directory sticky scrivibile da tutti. È una protezione, ma un wrapper shell che ignora l'errore di scrittura può comunque continuare usando il file di task originale. Verifica l'impostazione, il proprietario del file e della directory e se il wrapper si interrompe in caso di errore. Il percorso è solo un possibile caso di divulgazione di file se la regola sudo effettiva consente di eseguire il wrapper come utente privilegiato, il chiamante controlla l'input del task e una destinazione di backup leggibile e l'utility di backup include davvero le sorgenti protette. Durante l'enumerazione, verifica queste condizioni senza eseguire il backup.

### Wildcard negli argomenti degli strumenti di rete privilegiati

In una regola sudo per `tcpdump`, un `*` nel **pattern degli argomenti** può corrispondere a spazi e slash, quindi una restrizione che sembra un percorso può comunque consentire testo aggiuntivo per le opzioni. È diverso da un wildcard nel percorso dell'eseguibile del comando; esamina la regola RunAs completa e le eventuali negazioni successive. Se è possibile iniettare opzioni, l'invocazione consentita e la semantica delle opzioni di [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) installato determinano se `-F`, `-V`, `-r`, `-w` o `-Z` forniscono una primitiva utile di lettura/scrittura. `-V` legge un elenco di nomi di file di cattura, non scarica file arbitrari in generale. AppArmor o un'altra policy MAC può bloccare l'accesso ai file anche quando sudo consente il comando; la presenza su disco di un file di profilo non dimostra che sia caricato o in modalità enforcing. Prima di trarre conclusioni, esamina passivamente l'autorizzazione e la policy. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descrive la differenza tra i wildcard.

Anche una regola sudo efficace come root che elenca solo l'eseguibile `tcpdump`, senza restrizioni sugli argomenti, merita una verifica. Il [manuale di tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` come comando eseguito dopo la rotazione quando `-C` o `-G` ruota una cattura salvata; `-Z` o un valore predefinito in fase di compilazione possono ridurre i privilegi prima dell'esecuzione di quel comando. Prima di considerare la regola un percorso di escalation, verifica la regola sudo effettiva, la build installata, il comportamento di riduzione dei privilegi e la possibilità che avvenga una rotazione. Una regola evidenziata è un possibile caso da verificare, non la prova dell'esecuzione di comandi come root.

### Wrapper Nmap eseguiti tramite sudo

Quando il percorso `nmap` autorizzato da sudo è un wrapper shell, esamina il percorso esatto consentito e ogni opzione che inoltra. Bloccare la grafia nota `--script` non impedisce necessariamente il caricamento di codice NSE: [`--datadir` di Nmap](https://nmap.org/book/man-misc-options.html) seleziona i file di dati e NSE [carica `nse_main.lua`](https://nmap.org/book/nse-implementation.html) dalla directory di dati selezionata quando lo scripting è abilitato. Alcune build installate accettano anche grafie alternative delle opzioni lunghe, quindi confronta le restrizioni con il parser effettivo di quel binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) è una superficie separata di lettura dei file; gli errori del parser possono divulgare testo. Durante l'enumerazione, verifica la regola sudo effettiva, la logica del wrapper, la versione di Nmap, il controllo della directory e la policy MAC senza eseguire scansioni.

### Hook di pull Mercurial eseguiti tramite sudo

Una sorgente fissa in `sudo hg pull /fixed/source` lascia comunque che il repository di destinazione sia selezionato dalla directory di lavoro corrente, a meno che il comando non lo fissi con `-R`. Un repository di destinazione controllato dal chiamante può definire hook in `.hg/hgrc`, che potrebbero essere eseguiti come utente RunAs sudo. [Mercurial ignora la configurazione dei repository di proprietà di un utente o gruppo non attendibile](https://mercurial-scm.org/help/topics/config), quindi prima di considerarlo un caso di esecuzione di codice esamina gli utenti/gruppi attendibili dell'account RunAs e la directory di lavoro esatta. Per una verifica passiva è sufficiente leggere la policy e la configurazione; non eseguire `pull` né invocare hook durante l'enumerazione.

### Hook di pull Git eseguiti tramite sudo

Per un'autorizzazione sudo esatta ed efficace come root per `sudo git pull`, controlla anche il repository di destinazione selezionato dalla directory di lavoro. Un repository di proprietà del chiamante può avere un hook `post-merge` eseguibile, che viene eseguito con l'identità del processo Git quando un pull completa effettivamente un merge riuscito; [Git documenta questo hook](https://git-scm.com/docs/githooks) e [il comportamento di pull con merge o rebase](https://git-scm.com/docs/git-pull). Verifica la regola sudo effettiva e la CWD, il percorso dell'hook attivo e i suoi permessi, nonché la possibilità di raggiungere un merge con nuovi commit. Un pull fallito, senza modifiche o limitato al rebase non dimostra questo percorso tramite hook. Esamina la policy e i metadati del repository senza eseguire il pull privilegiato.

### Copie rsync in modalità archive eseguite tramite sudo

Per `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` nel **pattern degli argomenti sudoers** può corrispondere a spazi e ammettere un'opzione aggiuntiva tra sorgente e destinazione. È diverso dall'espansione shell dei nomi di file. Se il chiamante può popolare la sorgente e la destinazione è scrivibile dal processo rsync privilegiato, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) può richiedere la proprietà privilegiata mentre la modalità archive conserva i bit di permesso, creando potenzialmente un file SetUID posseduto dall'utente privilegiato. Verifica la semantica esatta dei wildcard in [sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versione di rsync, le negazioni successive, `nosuid` sul filesystem e la policy MAC. Una regola corrispondente è un possibile caso da verificare, non la prova di un'escalation dei privilegi riuscita.

### Esportazione delle regole del packet filter tramite sudo

Un'autorizzazione root senza restrizioni sia per `iptables` sia per `iptables-save` (o per la coppia corrispondente `ip6tables`) merita una verifica della scrittura su file. Il match `comment` accetta testo di regola scelto dal chiamante, mentre `iptables-save -f` scrive il ruleset serializzato in un percorso selezionato.<sup>[[20]](#references)[[21]](#references)</sup> Un payload utile dipende da come il backend installato serializza i commenti e dal fatto che il file di destinazione accetti altre righe nell'esportazione; `iptables-save`, da solo, non permette di scegliere contenuti arbitrari. Verifica l'identità RunAs sudo esatta, gli argomenti e le esclusioni, l'estensione di match disponibile, il backend e i permessi sulla destinazione. Durante l'enumerazione, esamina l'autorizzazione senza modificare le regole del firewall né scrivere file.

### Directory di log privilegiata di Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ha interessato le versioni di Below precedenti alla 0.9.0, che creavano la directory `/var/log/below` scrivibile da tutti. Se un servizio o un comando sudo consentito esegue come root una build affetta, un utente che può scrivere e attraversare una directory di log non sticky potrebbe sostituire una voce di log con un symlink prima che il processo privilegiato la apra. Verifica lo stato delle patch del pacchetto installato, il percorso esatto di esecuzione privilegiata, l'accesso effettivo alla directory, lo sticky bit e le ACL, nonché i metadati di `/var/log/below/error_root.log`. Un percorso scrivibile da tutti o una regola sudo, da soli, non dimostrano la catena completa. Una directory sticky o un backport del vendor cambia la valutazione. Durante l'enumerazione passiva, esamina solo i metadati; non serve creare un link né eseguire il programma privilegiato.

### Raccolta privilegiata di bundle di supporto da input scrivibili

Uno script di profilo di supporto consentito da `sudo` può leggere come root percorsi di log fissi e copiarne il contenuto in un archivio di profilo. Esamina lo script effettivo alla ricerca di letture dei file, poi controlla se il chiamante può sostituire un percorso sorgente o una voce di directory padre con un symlink. Se la lettura privilegiata segue quel link e l'archivio risultante è leggibile dal chiamante, un file protetto può essere divulgato. Devono essere presenti tutti gli elementi: autorizzazione sudo, percorso sorgente scrivibile, lettura privilegiata e output leggibile; un log o un nome di profilo scrivibile, da soli, non bastano. Durante l'enumerazione, esamina i permessi effettivi e i metadati dei link senza sostituire file né generare un profilo. Le [indicazioni di supporto di Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentano lo script di profilo eseguito come root e il relativo archivio di output, illustrando perché tali bundle richiedono input e accesso all'output limitati.

### Script Python di ripristino archivi eseguiti come root

Anche una regola sudo strettamente limitata per uno script Python di ripristino richiede di esaminare l'archivio di input. Se il chiamante può selezionare o sostituire l'archivio e lo script lo estrae come root con `tarfile.extractall(filter="data")`, verifica gli aggiornamenti di sicurezza dell'interprete prima di fidarti del filtro. CPython ha corretto diversi bypass dei filtri per symlink e hard link, tra cui CVE-2025-4517, nelle versioni 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. I backport delle distribuzioni possono correggere versioni precedenti, quindi la versione mostrata dell'interprete non dimostra da sola l'esposizione.<sup>[[16]](#references)[[17]](#references)</sup>

Per una verifica passiva, leggi il comando sudo e lo script esatti, segui l'argomento che seleziona l'archivio e controlla se l'utente corrente può scrivere l'archivio o la directory che lo contiene. Verifica separatamente la patch del vendor installata e la destinazione dell'estrazione; `filter="data"` non rende sicuro ogni archivio non attendibile.<sup>[[16]](#references)[[17]](#references)</sup>

### Loader di modelli di machine learning eseguiti tramite sudo

Una regola sudo che consente un file `.pt`, `.pth` o `.ckpt` scelto dal chiamante merita una verifica quando uno script privilegiato passa quel file a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` o un altro loader basato su pickle. Verifica la regola RunAs effettiva, se il chiamante può creare o sostituire il modello selezionato e il flusso effettivo degli argomenti attraverso eventuali wrapper shell fino all'helper Python. L'estensione `.pth` indica anche file di configurazione Python site non correlati, quindi l'estensione da sola non dimostra che si stia caricando un modello. Una scansione dell'archivio o del pickle in modo statico non dimostra che il caricamento successivo sia sicuro; esamina il comportamento di `weights_only` [dipendente dalla versione](https://docs.pytorch.org/docs/stable/notes/serialization.html) e gli eventuali allowlist. Vedi le [note su pickle ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Durante l'enumerazione passiva, non caricare né estrarre mai il modello.

### Analisi di espressioni su input memorizzati eseguita tramite sudo

Uno script Python fisso eseguito come root tramite sudo può comunque valutare testo che un utente con privilegi inferiori può salvare in un database applicativo. In TensorFlow, una chiamata a `preprocess_input_exprs_arg_string(value, safe=False)` seleziona un percorso `eval`; [l'advisory di TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descrive il parser non sicuro e una correzione al chiamante da riga di comando. Una chiamata esplicita `safe=False` dell'applicazione richiede una verifica separata anche quando quel chiamante da riga di comando è stato aggiornato. Controlla la regola sudo effettiva, chi può modificare la specifica riga di input, se il filtraggio o lo scoring consentono a quella riga di raggiungere la chiamata e il comportamento della funzione installata. Una versione di TensorFlow, un'autorizzazione sudo o un file di modello hardcoded, da soli, non dimostrano la catena. Esamina passivamente lo script e il flusso dei dati; durante l'enumerazione, non eseguire l'helper privilegiato né inviare espressioni di test.

### Configurazione di needrestart consentita tramite sudo

`needrestart -c` carica un file di configurazione Perl scelto dal chiamante e ne valuta il contenuto. Se `sudo -l` consente di eseguire `needrestart` come root con argomenti che permettono `-c` e il chiamante può scegliere un file di configurazione leggibile in una posizione scrivibile, tale permesso può consentire l'esecuzione di codice come root. Verifica la regola sudo esatta per RunAs e argomenti; una regola che consente solo un elenco di argomenti fisso può bloccare questo percorso. È un caso distinto dalle vulnerabilità di needrestart nella scansione degli interpreti: aggiornare il pacchetto o disabilitare `interpscan` non rende sicura un'autorizzazione root senza restrizioni per `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Import Python eseguiti tramite sudo come un altro account

Un entry point Python fisso può comunque importare un modulo che il chiamante può modificare o sostituire, anche quando sudo esegue lo script come utente di servizio **non-root**. Per un import letterale come `from utils import status`, esamina `utils/__init__.py` e `utils/status.py` locali, oltre ai permessi della directory del pacchetto. Prima di considerare il file scrivibile un percorso di esecuzione, verifica il percorso di import dello script, gli argomenti sudo consentiti esatti e se l'azione rilevante raggiunge quell'import. Durante l'enumerazione, esamina file e permessi senza importare né eseguire lo script.<sup>[[2]](#references)[[3]](#references)</sup>

Una regola sudo esatta per `python3 /absolute/script.py` richiede solo che lo script sia leggibile; il file non deve essere eseguibile né avere uno shebang. Esamina anche i moduli locali **mancanti**: se lo script importa un modulo il cui nome di file può essere creato in una directory dello script scrivibile dal chiamante, Python può caricare quel file con l'identità RunAs. Verifica la regola sudo effettiva, l'effettivo [percorso di ricerca dei moduli](https://docs.python.org/3/library/sys_path_init.html) dell'interprete, se il modulo è built-in o congelato e se l'import viene raggiunto. Una regola sudo diretta per lo script ha requisiti diversi per bit di esecuzione e shebang. Anche un wrapper separato che aggiunge token forniti dal chiamante dopo `sudo -u account` richiede di seguire il flusso degli argomenti: un altro `-u` in quei token è rilevante solo se la policy sudo invocata consente l'identità risultante. Le sole stringhe statiche non dimostrano nessuno dei due percorsi.

### Apache eseguito tramite sudo con configurazione controllata dal chiamante

Se una regola sudo consente un'invocazione privilegiata di `apachectl`, `apache2ctl` o `httpd` con un file di configurazione `-f` controllato dal chiamante, esamina i permessi di quel file e della directory padre. La direttiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) di Apache accetta il nome di un modulo seguito dal **nome del file del modulo**; anche [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) carica un file. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) possono estendere la configurazione o esporre contenuti di file tramite errori. Un wrapper personalizzato può validare questi percorsi, ridurre i privilegi o limitare gli argomenti; quindi una configurazione scrivibile è un possibile caso da verificare, non la prova di esecuzione di codice. Prima di concludere, verifica la canonicalizzazione dei percorsi, i symlink e l'analisi delle direttive.

### nginx eseguito tramite sudo con configurazione controllata dal chiamante

Una regola `nginx` senza restrizioni ed efficace come root può consentire a [`-c` di selezionare un'altra configurazione](https://nginx.org/en/docs/switches.html). Esamina gli argomenti sudo esatti e le esclusioni, se il chiamante può fornire la configurazione e se il master o i worker risultanti conservano accesso a percorsi protetti. Un `root` scelto insieme a `autoindex` può esporre file tramite un nuovo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) può offrire un percorso privilegiato di scrittura su file, ma il modulo DAV non è incluso nella build predefinita e occorre verificarne la presenza, la raggiungibilità del listener, i permessi dei file e il comportamento dei file temporanei. La direttiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) può anche puntare a un file scelto; scrivere log in un file di configurazione sensibile, come `/etc/ld.so.preload`, diventa un percorso di escalation solo se esistono un writer privilegiato effettivo e un record di log controllabile. L'eseguibile evidenziato da `sudo -l` è uno spunto per la verifica, non la prova che uno di questi percorsi funzioni. Durante l'enumerazione passiva, non avviare né riconfigurare nginx.

### Confronto di pattern nei prompt Bash privilegiati

Quando uno script Bash consentito da sudo legge un valore dal chiamante e lo verifica con `[[ "$expected" == $entered ]]`, Bash interpreta l'operando destro non quotato come pattern. Un wildcard può quindi soddisfare il confronto senza conoscere il valore atteso. Quotando l'operando (`[[ "$expected" == "$entered" ]]`) si ottiene un confronto letterale tra stringhe. Esamina la regola sudo esatta, se il prompt è raggiungibile e cosa fa lo script dopo il confronto; la sola sintassi non dimostra un percorso sfruttabile. Durante l'enumerazione, evita di stampare il valore atteso. Vedi il [riferimento alle strutture condizionali di Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper eseguiti tramite sudo che scaricano ed eseguono un file

Un'autorizzazione sudo senza restrizioni, efficace come root, per un helper personalizzato merita una verifica del flusso dei dati se accetta un URL scelto dal chiamante, salva la risposta su disco e in seguito esegue quel file con un interprete o una shell. [Sudoers consente argomenti arbitrari quando una voce di comando non ne specifica](https://man7.org/linux/man-pages/man5/sudoers.5.html); il percorso fisso dell'eseguibile non limita ciò che gli argomenti possono selezionare. Verifica la validazione effettiva dell'URL, il percorso di output, il ramo di successo e la successiva esecuzione nell'helper installato. La presenza di un import libcurl corrispondente o di una stringa stampabile, da sola, non dimostra la catena.

Anche un nome di output fisso può essere sostituibile tra scrittura ed esecuzione quando l'helper usa un **percorso relativo in una directory di lavoro controllata dal chiamante**. La rinomina o la sostituzione di un file posseduto da root dipendono dai permessi di scrittura e ricerca sulla directory e da eventuali restrizioni sticky bit, non solo dalla modalità del file; vedi [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifica se l'helper riapre in seguito il percorso o usa il descrittore già aperto, e se passa a una directory attendibile prima di scrivere. Esamina passivamente la policy sudo, l'helper e i metadati della directory; durante l'enumerazione non invocare il download privilegiato né tentare una race.

Un helper di download eseguito come root tramite sudo può anche esporre un'injection di **argomenti** quando crea una stringa di comando Bash come `curl <caller input> -o <fixed output>`. Un filtro che rifiuta gli spazi lascia comunque possibile la [brace expansion di Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementi separati da virgole e non quotati possono diventare argomenti curl distinti. Se l'input raggiunge curl prima di `-o` fisso, un'opzione di output fornita dal chiamante può selezionare la destinazione per il primo URL, con l'identità dell'helper; [curl associa le opzioni di output agli URL nell'ordine specificato](https://curl.se/docs/manpage.html#-o). Verifica la shell esatta, il quoting, la validazione dell'input, la regola sudo effettiva, l'ordine degli argomenti curl e gli schemi URL supportati, nonché se il chiamante controlla i byte scaricati o può leggere il risultato. Un eseguibile confezionato con PyInstaller può contenere logica applicativa Python, ma il marcatore di packaging o una stringa `curl`, da soli, non dimostrano questo flusso di dati. Se autorizzato, esamina una copia offline limitata; l'enumerazione ordinaria non dovrebbe eseguire l'helper né recuperare dati scelti dall'attaccante.

Uno script shell eseguito come root tramite sudo che invoca [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) sceglie solo un nome inutilizzato: **non** crea il file. Se in seguito lo script crea quel nome in una directory influenzabile da un altro utente, lo riapre e ne aggiunge il contenuto a una destinazione protetta come `authorized_keys` di root, verifica il possibile race sui file temporanei. Controlla la regola sudo esatta, la proprietà di directory e file, la sequenza di creazione e riapertura, le protezioni del kernel e se la scrittura privilegiata usa davvero byte controllati dall'attaccante. Una stringa `mktemp -u` o un `/tmp` scrivibile, da soli, non dimostrano la race. Durante l'enumerazione, esamina lo script e i metadati del percorso senza eseguirlo né tentare una race sul file temporaneo.

## Note difensive

- Evita di autorizzare interpreti o editor interattivi tramite sudo.<sup>[[1]](#references)</sup>
- Preferisci wrapper fissi, di proprietà di root, che eseguano una singola azione amministrativa limitata.<sup>[[1]](#references)[[2]](#references)</sup>
- Se un interprete è inevitabile, limita il percorso esatto dello script e impedisci argomenti controllati dall'utente, import scrivibili, `PYTHONPATH` e la conservazione non sicura dell'ambiente.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se è necessario modificare file, limita il percorso esatto e valuta `sudoedit` con versioni di sudo aggiornate e una gestione rigorosa dell'ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Esamina `SETENV`, `env_keep`, directory di lavoro scrivibili, percorsi di moduli/import scrivibili, `NOEXEC`, `use_pty` e logging, ma non considerarli una sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
