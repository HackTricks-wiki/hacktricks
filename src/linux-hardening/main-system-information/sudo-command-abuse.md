## Intérpretes permitidos por sudo

Si `sudo -l` permite que un usuario ejecute un intérprete como root, considéralo como ejecución directa de código. Los intérpretes están diseñados para ejecutar código arbitrario, por lo que una regla que permite `python3`, `perl`, `ruby`, `lua`, `node` u otros binarios similares suele equivaler a ejecutar comandos como root, a menos que los argumentos estén estrictamente restringidos y validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flujo de revisión habitual: primero enumera los privilegios del usuario y luego ejecuta una instrucción de Python con la opción `-c` del intérprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

A continuación se muestran otros ejemplos de intérpretes; los intérpretes enumerados documentan la ejecución de código en línea o las API de procesos secundarios.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

La ruta exacta importa. Si la regla de sudo permite `/usr/bin/python3`, usa esa ruta exacta durante la validación.<sup>[[2]](#references)</sup>

Un glob de ejecutables de sudo como `/usr/bin/python*` también podría permitir Python 2 para un script escrito para Python 3. Si el script llega a `input()` con texto controlado por quien lo invoca, [Python 2 evalúa ese texto como una expresión](https://docs.python.org/2/library/functions.html#input); una invocación explícita del intérprete prevalece sobre el shebang del script. Comprueba qué binarios coincidentes están instalados, la identidad efectiva de RunAs y la política de argumentos, las denegaciones y si se puede llegar a la entrada antes de considerar esto una vía de ejecución.

Una ruta de script fija en una regla de sudo con capacidad de ejecutarse como root no limita lo que ejecuta el script. Si se trata de un wrapper Bash legible, comprueba si su primer comando ejecutable usa un parámetro posicional sin comillas, como `$1`, como **palabra de comando**, mientras que sudo permite argumentos elegidos por quien lo invoca. Confirma la identidad efectiva de RunAs, la política de contraseñas y argumentos, las denegaciones posteriores y la rama real del script; `NOEXEC`, una lista fija de argumentos seguros o un wrapper que valide su comando pueden cambiar el resultado. Durante la enumeración, inspecciona estáticamente el script corto en lugar de invocarlo con un comando de prueba.

Una regla de sudo sin restricciones que permite ejecutarse como root para `dotnet` también merece una revisión del intérprete. Con un SDK de .NET instalado, [`dotnet fsi` ejecuta código F# de forma interactiva o desde un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), y [`dotnet run` ejecuta un proyecto desde el código fuente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirma primero la identidad efectiva de RunAs y la política exacta de argumentos: una regla limitada a un subcomando seguro concreto o a una aplicación de confianza es un permiso distinto, y una instalación que solo incluye el runtime puede carecer de los comandos del SDK. El nombre del ejecutable por sí solo es una señal para revisar, no una prueba de ejecución de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editores permitidos por sudo

Si `sudo -l` permite que un usuario ejecute un editor interactivo como root, considéralo una superficie de ejecución de comandos, no un permiso inofensivo para editar archivos. Los editores suelen permitir ejecutar comandos de shell, leer archivos arbitrarios, escribir archivos arbitrarios o invocar herramientas externas desde el propio editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flujo de revisión habitual: enumera los privilegios del usuario y, luego, ejecuta con sudo cada editor o pager permitido.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Ejecución de comandos con Nano

Cuando se permite ejecutar `nano` mediante sudo, es posible ejecutar comandos desde la interfaz del editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Luego, proporciona un comando como `id` o `/bin/sh` en el prompt de comandos de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactivo no dispone de flujos de terminal utilizables, esta forma de redirección asigna su salida estándar y error al descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La secuencia exacta de teclas puede variar según la versión de nano y las opciones de compilación, pero el problema de seguridad es el mismo: el editor se ejecuta como root y puede invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Otras salidas habituales de los editores

Los editores de estilo Vim suelen permitir ejecutar comandos mediante `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Los paginadores como `less` también pueden permitir la ejecución de comandos del shell.<sup>[[14]](#references)</sup>

Una regla de sudo que permita ejecutar `apport-cli` como root merece la misma revisión del paginador. Algunas versiones afectadas de Apport podían abrir un informe de fallo en `less` con un tamaño de terminal ajustable por un atacante; el paginador podía entonces proporcionar un shell de root si se cumplían las condiciones especiales de sudo y del paginador. Comprueba la regla de sudo efectiva, la configuración del paginador y la corrección del paquete de la distribución antes de considerar vulnerable la versión por sí sola. Lee los metadatos del paquete y de la política sin generar un fallo ni abrir el informe privilegiado durante la enumeración pasiva. [El registro CVE de Ubuntu](https://ubuntu.com/security/CVE-2023-1326) enumera las versiones corregidas de los paquetes específicas de cada versión, incluidas las correcciones retroportadas.

```text
!/bin/sh
```

## Otros peligros en las reglas de sudo y doas

Empieza con `sudo -l`, `sudo -V` y cualquier política de `doas` aplicable. Lee conjuntamente el comando permitido, el usuario de RunAs, los argumentos, el entorno y los valores predeterminados. El permiso para ejecutar como una cuenta de servicio que no sea root aún puede exponer los archivos de esa cuenta o una vía hacia root.

Un script de Python fijo permitido por sudo aún puede ejecutar un comando de shell bajo su identidad RunAs si concatena entradas interactivas controladas por quien lo invoca en [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist de puntuación del shell no basta para establecer que sea seguro: [el shell también reconoce la sustitución de comandos `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirma que los argumentos permitidos lleguen a la rama de entrada, que la entrada llegue al comando de shell sin validación segura y que la política efectiva de sudo permita el usuario RunAs previsto. La ruta del script o una llamada a `os.system()` son solo indicios para revisar; inspecciona el código fuente sin invocar el script privilegiado.

Un permiso efectivo de sudo como root para `chattr` puede quitar el atributo de archivo inmutable (`i`), pero eso por sí solo no concede permiso de escritura ni una nueva identidad. [El manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indica que el atributo bloquea las modificaciones y que solo root o un proceso con `CAP_LINUX_IMMUTABLE` puede cambiarlo. Comprueba la política exacta de argumentos de sudo y la compatibilidad del sistema de archivos; luego verifica por separado que quien lo invoca pueda escribir en el archivo después de quitar el atributo y que un consumidor con una identidad superior lo use. Por ejemplo, reemplazar un shell de inicio de sesión también requiere las credenciales aceptadas de la cuenta objetivo y un inicio de sesión real mediante ese shell. Durante la enumeración, revisa la política, los atributos de archivo y los permisos sin modificarlos.

Si sudo pide tanto una contraseña como un código de un solo uso, considera esos requisitos por separado del permiso para ejecutar el comando. Un archivo `.google_authenticator` legible contiene material sensible de semilla, mientras que un hash antiguo de contraseña de una aplicación o base de datos es solo una contraseña candidata para la cuenta actual; ninguno demuestra que la configuración efectiva de PAM acepte el otro factor. Una vez autorizado, revisa el RunAs y los argumentos exactos: un permiso irrestricto como root para RubyGems `gem` puede exponer su comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), pero un permiso restringido o una autenticación fallida no. La enumeración pasiva debe indicar las rutas y la política sin mostrar la semilla, recuperar una contraseña, generar un código ni invocar el comando privilegiado.

Un permiso irrestricto de sudo con capacidad de root para `knife` de Chef requiere revisar el intérprete: [Chef documenta que `knife exec -E` evalúa localmente una cadena Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica que la regla efectiva de sudo permita el subcomando `exec` y el argumento `-E` proporcionado por quien lo invoca, la identidad RunAs prevista y cualquier denegación de comandos o argumento fijo que coincida. El binario instalado o una regla limitada a otros subcomandos son solo indicios. La enumeración pasiva debe informar de la regla sin invocar `knife`.

Un permiso exacto de sudo con capacidad de root para un `msfconsole` interactivo también es sensible: [GTFOBins documenta su consola `irb`](https://gtfobins.org/gtfobins/msfconsole/), que puede heredar la identidad de sudo. Confirma el usuario RunAs efectivo, la lista de argumentos permitidos, las denegaciones de comandos, `NOEXEC` u otras restricciones, el comportamiento de la consola instalada y si quien lo invoca puede proporcionar entrada interactiva. Una ruta resaltada es solo un indicio para revisar; la enumeración pasiva no debe iniciar la consola.

En FreeBSD, incluso una regla de sudo limitada a `pkg update` y `pkg install *` como root requiere revisar la confianza en los repositorios. Comprueba si quien lo invoca puede escribir en `/etc/hosts` y si la configuración efectiva de repositorios habilitados usa un hostname HTTP con `signature_type: none`. [El manual de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indica que `none` desactiva las verificaciones de firma; `pkg+http` por sí solo no demuestra esto. Un paquete puede contener scripts de instalación ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), así que quien realmente controle el endpoint del repositorio y pueda seleccionar un paquete podría cruzar el límite de root. Antes de llegar a esa conclusión, verifica las anulaciones del repositorio, la resolución SRV/espejos, los argumentos efectivos de sudo, la selección del paquete y la ejecución de scripts. Inspecciona la política y los archivos de configuración locales pequeños sin redirigir nombres ni ejecutar `pkg` durante la enumeración.

Un permiso de sudo con capacidad de root para `apt-get update` y `apt-get upgrade` también requiere revisar la confianza en los repositorios si sudo conserva un `http_proxy` controlado por quien lo invoca. Comprueba si la configuración efectiva de APT usa realmente esa variable y qué solicitudes a repositorios habilitados puede afectar; un proxy por sí solo no puede reemplazar paquetes de un archivo autenticado mediante una clave de firma de confianza. [El manual del transporte HTTP de APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedencia de los proxies, y [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta las verificaciones de firma, las anulaciones para repositorios inseguros y la confirmación requerida para paquetes no autenticados. Confirma el RunAs y los argumentos exactos de sudo, la política de autenticación de repositorios, cualquier aceptación interactiva necesaria y si la actualización seleccionada ejecuta scripts de paquetes como root. Inspecciona la política y la configuración local de forma pasiva; no redirijas el tráfico de paquetes ni ejecutes una actualización durante la enumeración.

Una regla de sudo con capacidad de root para `snap install` puede crear un límite entre paquetes y código si sus argumentos permiten que quien la invoca seleccione un snap local y un modo de instalación permisivo. [La documentación de Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) indica que `--dangerous` omite las verificaciones de aserción de snaps locales y que `--devmode` relaja el confinamiento; [un hook de instalación puede ejecutarse durante la instalación inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Antes de afirmar que se puede acceder a archivos protegidos del host, comprueba la política exacta de argumentos/RunAs de sudo, quién controla el archivo snap, si snapd instalado acepta estos modos y la identidad efectiva y el confinamiento del hook. La presencia del binario `snap` o una regla que parece usar un comodín no demuestra por sí sola esta cadena. La enumeración pasiva no debe instalar un paquete ni ejecutar su hook.

Para un permiso exacto de sudo que ejecuta como una cuenta **que no es root** un binario personalizado que lee credenciales, primero inspecciona el binario permitido y sus permisos de archivo sin ejecutarlo. Una contraseña integrada puede aparecer solo como caracteres anchos; [GNU `strings` documenta la extracción little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Una cadena visible no demuestra que sea la contraseña aceptada ni que la rama de éxito exponga una credencial actual. Confirma por separado el comportamiento del binario, el acceso de la cuenta objetivo a los datos protegidos, la validez de las credenciales y cualquier transición posterior de cuenta o grupo. Si esa cuenta pertenece a `docker`, verifica el acceso al socket y si la identidad del daemon es rootful o rootless antes de inferir acceso a root del host; [Docker documenta las implicaciones de nivel root de ese grupo](https://docs.docker.com/engine/install/linux-postinstall/). La enumeración habitual debe informar de la regla de sudo y la pertenencia al grupo sin ejecutar el binario ni volcar sus cadenas.

Una regla de sudo con comodín para los scripts de mantenimiento de una aplicación requiere revisar más que la ruta del script. Comprueba si el script permitido acepta argumentos sin restricciones o lee configuraciones que una cuenta de aplicación con menos privilegios puede modificar; luego sigue esos valores hasta los comandos de shell o el entorno de un subproceso. Por ejemplo, [`zmupdate.pl` de ZoneMinder construye un comando `mysqldump` y lo ejecuta mediante `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mientras que [`zmdc.pl` copia el ajuste `ZM_LD_PRELOAD` a `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Una regla de sudo que permita ejecutar cualquiera de esos scripts como root puede cruzar un límite de confianza si la entrada correspondiente es controlable y llega a ese código en la versión instalada. Inspecciona la regla efectiva de sudo, los permisos de configuración de la aplicación y el código fuente del script; el comodín o el ajuste por sí solos son indicios para revisar, no pruebas de ejecución.

- `SETENV`, `env_keep`, `secure_path` y `LD_PRELOAD` pueden convertir un comando que, de otro modo, sería limitado en un secuestro de imports, bibliotecas o PATH. Consulta la [guía de variables de entorno](../linux-basics/linux-environment-variables.md) y [abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Un permiso exacto de sudo con capacidad de root y `SETENV` para un wrapper de shell también requiere revisar un salto si el wrapper inicia un script de Python fijo con un import literal. `secure_path` limita la búsqueda de comandos del shell, no la [búsqueda de módulos `PYTHONPATH` de Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` y `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hacen que Python ignore esa variable de entorno. Antes de considerarlo ejecución de código, confirma las etiquetas y denegaciones efectivas de sudo, la rama del wrapper, las opciones del intérprete, la resolución del import y la existencia de un directorio de búsqueda donde quien lo invoca pueda escribir. Inspecciona estáticamente los scripts cortos; no invoques el wrapper privilegiado.

Un permiso exacto de sudo para `neofetch ""` con capacidad de root aún puede cargar una configuración de shell cuando los valores predeterminados aplicables de sudo conservan un `XDG_CONFIG_HOME` controlado por quien lo invoca. [El cargador de configuración de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) obtiene el archivo `neofetch/config.conf` o `neofetch/config` desde ese directorio; la lista de argumentos vacía no impide esta búsqueda. Confirma el cargador instalado, el RunAs y la política de argumentos efectivos, cualquier denegación de comandos, si sudo conserva realmente la variable seleccionada para este comando y si quien lo invoca controla una ruta de configuración legible. Una variable conservada o la presencia de Neofetch son solo indicios para revisar. Inspecciona la política y los metadatos de archivo sin invocar el comando privilegiado ni mostrar el contenido de la configuración; consulta [el manejo del entorno de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regla de sudo irrestricta con capacidad de root para `facter` requiere revisar por separado los custom facts. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` carga archivos de facts Ruby desde un directorio seleccionado. Comprueba si la regla exacta de sudo permite esa opción, si Facter instalado la acepta y si quien lo invoca controla el directorio. Un permiso con argumentos fijos, una denegación explícita de comandos o la desactivación de custom facts pueden cambiar el resultado. La enumeración pasiva debe informar de la posibilidad según la política sin invocar Facter ni leer el contenido de los facts.

Para un permiso exacto de sudo con capacidad de root para un script y `SETENV`, inspecciona nombres de comando sin ruta, como `find`, y el `PATH` efectivo después de aplicar la política de sudo y la inicialización del script. Un archivo Bash incluido también puede ejecutar `enable -n [`: [Bash busca entonces en `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un `[` externo cuando el script usa luego ese comando. Confirma las [reglas de entorno de sudoers y `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) aplicables, cualquier entrada `NOSETENV`/`NOEXEC` o denegación, el flujo del script y de los archivos incluidos y la existencia de un directorio de búsqueda ejecutable controlado por quien lo invoca. Un script legible que contiene un comando sin ruta es un indicio para revisar, no una prueba de ejecución privilegiada; inspecciónalo sin invocar la regla de sudo.
- Un script privilegiado que obtiene una URL fija con `curl` aún puede aceptar una respuesta seleccionada por quien lo invoca si una regla de sudo aplicable conserva `http_proxy` y la solicitud pasa por ese proxy. Si luego el script entrega la respuesta a un parser XML que resuelve entidades externas, una respuesta maliciosa puede revelar archivos legibles por el proceso privilegiado. Comprueba la política exacta de entorno de sudo, las exclusiones `no_proxy`, la URL solicitada, la configuración del parser y el destino de salida; una variable de proxy o un parser XML por sí solos no constituyen una vulnerabilidad. La [documentación de variables de entorno de proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) describe el comportamiento de estas variables. No realices solicitudes de red ni analices XML malicioso durante la enumeración pasiva.
- Un script de sudo con capacidad de root que construye un archivo PostScript a partir de datos influenciados por quien lo invoca y luego ejecuta `ps2pdf -dNOSAFER` requiere revisar por separado el flujo de entrada. Ghostscript documenta que este indicador desactiva SAFER hasta `.setsafe`, lo que permite operaciones de archivo PostScript dentro de los permisos del proceso en el sistema operativo. Una consulta SQL construida con un argumento de quien lo invoca puede introducir filas controladas por un atacante en la plantilla PostScript, pero una cadena de consulta o una invocación de `ps2pdf` por sí solas no demuestran que los datos lleguen a la sintaxis PostScript ejecutable. Confirma la regla efectiva de sudo, el flujo exacto desde la entrada hasta la plantilla, cualquier escape, el comportamiento de Ghostscript instalado y si SAFER se vuelve a activar antes de interpretar el documento. No invoques la conversión privilegiada durante la enumeración pasiva. Consulta la [documentación de Ghostscript sobre `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para una regla de sudo que ejecuta un script de shell, compara las variables conservadas con el propio script. Una construcción como `if $CHECK_CONTENT; then` ejecuta el valor expandido como comando, por lo que conservar `CHECK_CONTENT` puede permitir la ejecución de comandos incluso si la ruta y los argumentos del script son fijos. Debe comprobarse si la rama es alcanzable y si el entorno se conserva realmente para esa regla específica.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script de Python permitido por sudo puede importar código desde un directorio donde se puede escribir o desde un archivo `.pyc` en caché. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md) detalla el caso de la caché.
- Un script de Python fijo permitido por sudo para ejecutarse como root aún puede exponer un debugger interactivo. Llamadas como `pdb.set_trace()` o `pdb.post_mortem()` permiten ejecutar sentencias de Python en el contexto del proceso depurado cuando quien lo invoca puede alcanzar el breakpoint o el manejador de excepciones **y controlar la entrada del debugger**. Comprueba la regla exacta de RunAs de sudo, la autenticación y las condiciones de la rama, la posibilidad de alcanzar la excepción, la propiedad del terminal/entrada y si el debugger se ejecuta en ese mismo proceso privilegiado. Una solicitud a un socket que provoca una excepción no concede por sí sola acceso a un debugger conectado a otro terminal. [Python documenta la evaluación de sentencias del debugger y el modo post-mortem](https://docs.python.org/3/library/pdb.html); inspecciona el script estáticamente en vez de activar el manejador privilegiado durante la enumeración.
- Un script de Python fijo permitido por sudo también puede leer un campo de perfil de una base de datos o un socket Unix y añadirlo a una cadena que luego se convierte en la **cadena de formato** de `str.format()`. [Los campos de reemplazo pueden seguir atributos y claves de mappings](https://docs.python.org/3/library/string.html#format-string-syntax), así que un campo controlado por un atacante puede inspeccionar objetos pasados a `format()` y exponer los datos a los que estos tengan acceso si el resultado se imprime o se guarda en un lugar que quien lo invoca pueda leer. Comprueba la identidad RunAs efectiva de sudo, el acceso de escritura al registro específico, el flujo de datos hasta la cadena de formato, los objetos suministrados y la visibilidad de la salida. Esto no es ejecución de código automática; una cadena de formato literal de confianza con *valores* controlados por un atacante es un caso distinto. Un secreto divulgado solo permite cambiar a una cuenta del sistema operativo si esa cuenta lo acepta. Revisa el script y los permisos del socket sin invocar la operación privilegiada.
- Un wrapper Python con capacidad de root puede pasar una URL seleccionada por quien lo invoca a `Repo.clone_from` de GitPython. Si el wrapper también habilita `protocol.ext.allow=always` de Git, un remoto `ext::` puede invocar un helper externo. Comprueba los argumentos exactos de sudo, el origen de la URL, la versión del paquete GitPython y el estado de los parches del proveedor, y si el wrapper opta explícitamente por protocolos inseguros. GitPython añadió una [protección predeterminada para protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) en la versión 3.1.30; la versión del ejecutable `git` es un dato distinto. La revisión pasiva debe limitarse a leer la regla y una parte acotada del código fuente, sin invocar el clone.
- Un permiso de sudo entre usuarios para una CLI que clona repositorios puede exponer una vía distinta de inyección de cadenas de shell. Sigue si el argumento de repositorio seleccionado por quien lo invoca llega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js u otro constructor de comandos de shell sin separación segura de argumentos; `exec` de Node pasa su cadena de comando a un shell. Confirma el usuario RunAs exacto, los subcomandos y argumentos permitidos, el código del wrapper instalado y la validación de entrada. El nombre de una herramienta de repositorios o una regla de sudo irrestricta por sí solos no demuestran inyección de comandos. Inspecciona el wrapper sin invocar un clone privilegiado durante la enumeración.
- Un wrapper personalizado propiedad de root puede parecer seguro porque sus binarios y scripts no se pueden modificar, pero su decisión de ejecutar una acción privilegiada puede depender de una bandera, un valor de API local o el estado de un servicio que un usuario sin privilegios puede cambiar. Sigue cada condición hasta su entrada y las comprobaciones de autorización. Durante la enumeración, inspecciona la configuración y los permisos sin cambiar el estado operativo; una llamada a `systemd-run` dentro del wrapper solo es relevante si se puede influir en la condición.
- Un cliente de backup permitido mediante sudo como root puede aceptar un archivo de configuración seleccionado por quien lo invoca (por ejemplo, `npbackup-cli -c`). Comprueba el usuario run-as exacto y los argumentos permitidos; luego, si quien lo invoca controla la ruta de configuración, las rutas de origen del backup y las opciones de repositorio o lectura/restauración. Un secreto de repositorio cifrado en una configuración legible aún puede ser utilizable por el cliente, pero la regla por sí sola no demuestra acceso al repositorio ni divulgación de archivos de root. Valida la autorización sin ejecutar un backup ni volcar su contenido.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) admite `--password-command`, que llama a un programa para obtener la contraseña de un repositorio. Si una regla de sudo permite que un usuario con menos privilegios ejecute restic como root con un comando de contraseña elegido por quien lo invoca y un subcomando que necesite la contraseña, ese helper podría ejecutarse como root. Revisa los argumentos y exclusiones exactos de sudo; no invoques el helper ni un comando de backup solo para enumerar esta condición.
- Un permiso privilegiado de `restic backup` también puede cruzar un límite de lectura de archivos si el patrón de argumentos de sudo permite que quien lo invoca elija tanto el origen como un repositorio que pueda leer y descifrar después. [Los comodines de argumentos de sudoers pueden coincidir con espacios y barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), así que inspecciona los comodines finales en vez de suponer que un prefijo de repositorio fijo confina el origen. [Restic puede hacer backups en repositorios locales y remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), pero un repositorio local puede contener objetos recién escritos que solo root puede leer; confirma la política efectiva de sudo, el acceso al backend, la contraseña del repositorio y los permisos de los objetos resultantes antes de considerarlo una divulgación. Una clave SSH incluida en un backup da acceso solo si la cuenta de destino la acepta. No ejecutes un backup para probarlo durante una revisión pasiva.
- Un comando irrestricto de mantenimiento o backup personalizado puede aceptar una ruta de salida o incluir su propio planificador de tareas. Para una vía de escritura de archivos, verifica la regla exacta de sudo y el usuario run-as; luego, si quien lo invoca controla tanto los datos como el destino. Para una vía de comandos programados, verifica la identidad de ejecución del planificador, la entrada del comando y cualquier contraseña o control de autorización adicional. El nombre del comando o `NOPASSWD` por sí solos no demuestran ninguna de las dos vías. Consulta [escribir en archivos propiedad de root](../interesting-files-permissions/write-to-root.md) y [cron y los timers de systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando fijo de sudo aún puede cargar un archivo de configuración predecible desde un directorio compartido donde se puede escribir. Sigue si quien lo invoca puede reemplazar ese archivo y si sus campos de origen y destino controlan una descarga o copia privilegiada. Una URL de archivo local puede exponer datos legibles solo por la cuenta RunAs de sudo; un origen controlado por quien lo invoca combinado con un destino protegido puede crear una vía de escritura. Confirma el manejo de URL del programa instalado, las comprobaciones de la ruta de destino, la regla efectiva de sudo y la accesibilidad de la salida. Una ruta de configuración escribible en `/tmp` es solo un indicio; inspecciona el binario y los metadatos de archivo sin invocar la transferencia privilegiada.
- Una regla de sudo para `git apply` puede permitir que la cuenta RunAs escriba archivos seleccionados mediante un patch controlado por quien lo invoca. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitía que un patch manipulado creara un symlink y luego escribiera fuera del árbol de trabajo, incluso cuando el comando no aceptaba `--unsafe-paths`. Comprueba la regla efectiva de argumentos de sudo, el origen del patch, el acceso de la cuenta RunAs al directorio de trabajo y la corrección de Git instalado o el backport del proveedor. Una regla irrestricta que admita `--unsafe-paths` supone un riesgo distinto por opción explícita; ni una versión de Git ni un permiso para `git apply` por sí solos demuestran que se pueda modificar un archivo protegido. No apliques un patch no confiable durante la enumeración pasiva.
- Una regla de sudo con capacidad de root para `clamscan --debug` puede cruzar un límite de lectura si un usuario con menos privilegios puede proporcionar una imagen DMG y el parser instalado está afectado por [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que podía divulgar el contenido de archivos mediante la salida de depuración. Confirma los argumentos permitidos y la ruta de análisis exactos, el control de la entrada, la cuenta RunAs efectiva, el parche/backport del motor y si quien lo invoca puede ver la salida. Si una regla más amplia permite `--file-list`/`-f`, revisa por separado el comportamiento de esa lista; una política fija a `--debug <scan-path>` no lo admite. Inspecciona la política y los metadatos del paquete sin analizar un archivo manipulado ni mostrar salidas protegidas durante la enumeración.
- Una regla de sudo con capacidad de root que abre una imagen de disco cifrada seleccionada por quien la invoca y una segunda regla que monta el mapper resultante pueden importar archivos controlados por quien lo invoca al namespace de montaje del host. Confirma ambas reglas efectivas y sus argumentos, el control de la imagen y del nombre del mapper, el punto de montaje real y el propietario y modo de los archivos resultantes. Una transición set-user-ID requiere además un ejecutable accesible, opciones de montaje que lo respeten (`nosuid` lo bloquea) y una política de proceso o MAC aplicable; abrir o montar una imagen por sí solo es solo un indicio. Una vía distinta mediante un backup existente requiere su clave real y un secreto útil y legible en su interior. Inspecciona la política y las rutas sin abrir ni montar una imagen durante la enumeración pasiva. Consulta el [manual de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) y las [opciones de mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regla de sudo con capacidad de root para un script de shell o Python requiere revisar el directorio de trabajo si el script invoca `./helper` sin cambiar antes a un directorio fijo. Una lista de Python como `['./helper']` pasada a `subprocess.run` puede tener el mismo comportamiento, determinado por el directorio de trabajo elegido por quien lo invoca. Este podría elegir un directorio escribible y colocar allí un ejecutable con ese nombre relativo; una ruta absoluta en otra parte del script no protege esta llamada. Antes de considerarlo ejecución de código, confirma la regla efectiva, `runchdir` u otra política que cambie de directorio, el flujo del script y si la rama es alcanzable, un directorio donde se pueda escribir y ejecutar, y las restricciones de montaje/`NOEXEC`. Si no se puede leer un script, su comportamiento sigue siendo desconocido hasta revisar su código fuente por una vía autorizada. Revisa los scripts estáticamente en vez de ejecutar el helper. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la política de directorio de trabajo.
- Un validador Python fijo con capacidad de root aún puede evaluar un archivo de datos seleccionado por quien lo invoca. [La documentación de `eval()` de Python advierte contra entradas no confiables](https://docs.python.org/3/library/functions.html#eval): una comprobación del sufijo de entrada, un prefijo aritmético o una rama de validación no son un sandbox si la expresión restante llega a `eval`. Antes de considerarlo una vía de ejecución, confirma la regla efectiva de sudo, si quien lo invoca puede seleccionar y controlar el archivo exacto, las condiciones de la rama del parser y la construcción de la expresión, y la identidad del proceso privilegiado. La presencia de `eval` en un script legible es solo una señal para revisar; inspecciona el código fuente y los permisos del archivo sin ejecutar el validador ni enviar una expresión de prueba durante la enumeración.
- Un wrapper Ruby de sudo con capacidad de root que lee un nombre de archivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, puede tomar la entrada del directorio de trabajo de quien lo invoca, salvo que el wrapper o la política de sudo fijen ese directorio. Comprueba los argumentos permitidos exactos, los permisos del directorio y del archivo, y el comportamiento de Psych instalado: las implementaciones antiguas de `YAML.load` podían deserializar objetos Ruby arbitrarios, mientras que las versiones más recientes restringen las clases de forma predeterminada. Una llamada estática es solo un indicio; confirma que el archivo realmente provenga de un directorio donde quien lo invoca pueda escribir y que el cargador instalado acepte clases peligrosas. Para entradas no confiables, prefiere `safe_load` con una lista explícita y mínima de clases permitidas. Consulta la [documentación de Psych para Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) y la [documentación de Psych para Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Un permiso exacto de sudo con capacidad de root para `sudo go run /absolute/file.go` requiere revisar el directorio de trabajo si el código Go lee un archivo WASM relativo y puede ejecutar un script de shell relativo después de inspeccionar su resultado. Confirma el RunAs efectivo, los argumentos y las denegaciones del comando, que el directorio actual permita escribir a quien lo invoca, el flujo de datos de WASM hasta la rama y si esa rama invoca el helper. Un `runchdir` fijo de sudo, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pueden cambiar la ubicación de búsqueda. La mera coexistencia estática de estos elementos solo es un caso candidato; inspecciona el código fuente sin ejecutar Go, WASM ni el helper.
- `sudoedit` y los comodines de argumentos requieren comprobar la versión y la regla exactas; la [lista de comprobación](linux-privilege-escalation-checklist.md) incluye el problema de edición de archivos con sudoedit. Para un permiso de `sudoedit` entre usuarios sobre una ruta con comodín, inspecciona el ajuste efectivo `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, el destino resuelto y quién puede reemplazar cada entrada del directorio padre. El primero puede permitir seguir un symlink, mientras que desactivar el segundo elimina las comprobaciones de directorios escribibles; ninguno de esos ajustes por sí solo demuestra que se pueda escribir en el archivo de otro usuario. Confirma la política de sudo instalada y los argumentos exactos que coinciden antes de llegar a esa conclusión. Consulta las [definiciones de opciones de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- En una regla de comando de sudoers, un comodín de argumentos puede coincidir tanto con espacios como con caracteres de ruta. Una regla para un comando que permite leer, con un argumento como `/restricted/*`, puede admitir así un argumento de archivo adicional después de un prefijo coincidente. Revisa exactamente el usuario run-as, la ruta del comando, el patrón de argumentos y las denegaciones posteriores; demostrar lectura de archivos no implica ejecución de comandos. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue los globs de argumentos de los globs de rutas de comando.
- Un glob de argumentos que parece una ruta también puede coincidir con `../`. Por ejemplo, una regla de sudo con capacidad de root para `node /opt/scripts/*.js` puede permitir que quien la invoque proporcione un archivo JavaScript controlado fuera de `/opt/scripts`, si la ruta suministrada empieza por `/opt/scripts/` y se resuelve mediante segmentos de directorio padre. Este es un glob de **argumentos**; el glob de la ruta del comando para el ejecutable Node tiene reglas distintas para las barras. Antes de concluir que hay ejecución de código, comprueba la regla efectiva, las denegaciones posteriores, la resolución de la ruta, el control del archivo objetivo y cualquier restricción de expresiones regulares o digest de sudoers. Consulta las [reglas de comodines de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) y la [documentación de línea de comandos de Node](https://nodejs.org/api/cli.html).
- Los archivadores y otros programas de utilidades pueden tener hooks de ejecución. Comprueba los argumentos permitidos exactos con [GTFOBins](https://gtfobins.github.io/) en vez de suponer que solo los shells o intérpretes ejecutan comandos.
- Una regla irrestricta de sudo con capacidad de root para `qpdf` puede exponer un archivo privilegiado mediante adjuntos PDF: qpdf 10.2 y versiones posteriores admiten `--empty` y `--add-attachment file ... --` con un PDF de salida. Si el proceso privilegiado puede leer el origen seleccionado y escribir el PDF en una ruta accesible para quien lo invoca, esa salida puede contener los bytes del origen. Antes de concluir que es posible divulgar el archivo, revisa los argumentos y exclusiones efectivos de sudo, la versión de qpdf, el acceso al origen y la ruta de salida. Leer una clave SSH de root solo es útil para iniciar sesión si la clave es válida y se permite la autenticación SSH de root. Consulta las [opciones de adjuntos de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La reutilización de marcas de tiempo de sudo depende de la política de caché, el usuario propietario, el terminal/sesión y los permisos. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) cubre las comprobaciones.
- `doas` tiene reglas y configuración propias. Comprueba los comandos permitidos y las rutas de configuración donde se puede escribir, según se describe en la [sección de doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Herramientas de compilación y paquetes ejecutadas con sudo

Un permiso de sudo irrestricto para `forge` de Foundry puede ser relevante aunque la identidad RunAs sea otro usuario que no sea root. Opciones del compilador como `--use` pueden seleccionar un ejecutable local, y `forge flatten -o` selecciona un archivo de salida. Antes de considerar explotable el permiso, comprueba la versión de Forge instalada, los argumentos exactos de sudo, la accesibilidad del proyecto y de las rutas del compilador, los permisos de salida y el entorno efectivo. Un ejecutable helper relativo encontrado mediante `PATH` es una vía que depende de la versión y el entorno, no algo que deba suponerse para cualquier compilación de Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Un permiso irrestricto de sudo con capacidad de root para `pacman` permite más que consultas de paquetes: `-U` acepta un paquete local, los paquetes pueden contener scripts de instalación y `--hookdir` selecciona otro directorio de hooks. Revisa la regla efectiva de sudo, las restricciones de argumentos y las exclusiones antes de hacer pruebas; la enumeración pasiva no requiere instalar un paquete ni ejecutar un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper de shell fijo de sudo también puede instalar una dependencia npm con nombre y luego iniciar una aplicación Node. Revisa su regla exacta de RunAs, si el paquete ya está instalado, el `HOME` efectivo y el `userconfig` de npm, los archivos de configuración del proyecto o las anulaciones de línea de comandos, y si un usuario con menos privilegios controla el registry o el paquete que se obtiene con ese nombre. [npm documenta la búsqueda de `.npmrc` por usuario y proyecto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); el comportamiento de `HOME` en sudo depende de la política instalada y de la distribución, así que quizá el proceso npm privilegiado lea o quizá no el `.npmrc` escribible del usuario. Si la aplicación privilegiada importa el paquete recién instalado, su código de módulo puede ejecutarse con la identidad de esa aplicación. Los scripts de instalación constituyen una vía distinta, dependiente de la versión y la configuración; [npm documenta su ciclo de vida y el manejo de usuarios](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Una ruta `.npmrc` o una línea `npm install` son solo indicios para revisar. Inspecciona la regla, el wrapper corto, las rutas de configuración y la procedencia del paquete sin instalarlo ni iniciar la aplicación durante la enumeración pasiva.

Un permiso de sudo con capacidad de root para `pip` o `pip3 download` también es un indicio para revisar la compilación de paquetes cuando sus argumentos permiten que quien lo invoca seleccione una distribución de origen no confiable, aunque el patrón de URL la limite a un servicio local y al sufijo `.tar.gz`. `pip download` acepta URL de archivos y resuelve metadatos de paquetes; preparar una sdist puede invocar su backend de compilación o código `setup.py` heredado antes de que el archivo simplemente se guarde. Confirma el RunAs y la regla de argumentos exactos de sudo, si quien lo invoca puede publicar o reemplazar el archivo seleccionado y si esa versión de pip realmente prepara sus metadatos. Un archivo de confianza fijo o un wheel no demuestran esta vía. No descargues ni compiles un paquete no confiable durante la enumeración pasiva. Consulta el [comando download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), la [interfaz del sistema de compilación](https://pip.pypa.io/en/stable/reference/build-system/) y la [guía de instalación segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regla de sudo que permite `pip install` con una ruta de proyecto local seleccionada por quien lo invoca crea un límite de compilación más directo. [pip acepta directorios de proyectos locales](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca su sistema de compilación; [el backend de compilación ejecuta hooks de compilación controlados por el proyecto](https://pip.pypa.io/en/stable/reference/build-system/). Antes de considerar que la regla permite ejecutar código privilegiado, confirma la identidad RunAs efectiva, las restricciones y denegaciones exactas de argumentos, el control del proyecto seleccionado y el comportamiento de pip/backend instalados. Un proyecto de confianza fijo o una regla que excluye rutas seleccionadas por quien lo invoca no demuestra esta vía. Revisa la regla y los metadatos del proyecto sin instalar un paquete durante la enumeración pasiva.

Un permiso irrestricto de sudo con capacidad de root para `easy_install` es un indicio relacionado con la compilación de paquetes heredados. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install acepta un directorio de proyecto local y compila distribuciones de origen; un proyecto controlado por quien lo invoca puede ejecutar su `setup.py` durante esa compilación bajo la identidad de sudo. Confirma la cuenta RunAs efectiva, las restricciones exactas del comando y sus argumentos (incluidas las denegaciones posteriores), el control del proyecto seleccionado y el comportamiento de la herramienta instalada. Un proyecto de confianza fijo o una política que no permita seleccionar un origen controlado por quien lo invoca no demuestra esta vía. Inspecciona la regla y los metadatos del proyecto sin instalar un paquete durante la enumeración.

Un wrapper Python permitido por sudo que usa `setuptools.package_index.PackageIndex.download` con una URL seleccionada por quien lo invoca es un caso distinto del de `pip download`: [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) describe cómo, en versiones afectadas anteriores a 78.1.1, un nombre de archivo derivado de la URL podía escapar del directorio de descarga previsto y escribir con los permisos del proceso. Confirma el RunAs y la regla de argumentos efectivos de sudo, que el wrapper pase la URL de quien lo invoca a esa API exacta, la compilación instalada o el backport del proveedor, y dónde se resuelve la ruta resultante. Una cadena de versión o un directorio de descarga escribible por sí solos no demuestran escritura arbitraria. Revisa el wrapper corto y los metadatos del paquete sin obtener la URL ni escribir un archivo durante la enumeración.

Un wrapper de compilación permitido por sudo que pasa a PyInstaller un archivo `.spec` seleccionado por quien lo invoca requiere revisar el mismo límite de confianza. Un archivo spec de PyInstaller es Python ejecutable que se evalúa durante la **compilación**, y sus entradas `datas` pueden incluir en un artefacto archivos legibles por la identidad de compilación. Confirma el usuario RunAs exacto, las reglas de argumentos y denegaciones de sudo, el manejo de rutas y ramas del wrapper, el control del archivo spec seleccionado y el acceso al artefacto resultante. Permitir simplemente una entrada `.py` o encontrar PyInstaller instalado no demuestra que se controle el archivo spec ni que haya ejecución privilegiada. La revisión pasiva solo debe leer un archivo wrapper acotado y sus metadatos; no debe ejecutar una compilación. Consulta la [documentación de archivos spec de PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Cargadores de presets y plugins ejecutados con sudo

Las herramientas Python que aceptan un preset o un directorio de plugins seleccionado por quien las invoca pueden importar código con los privilegios concedidos por sudo. Por ejemplo, BBOT acepta un preset con `-p`, y su [documentación de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) describe entradas `module_dirs` que seleccionan directorios adicionales de módulos Python. Si la regla efectiva de sudo permite un preset seleccionado por quien lo invoca y este controla un módulo en el directorio seleccionado, el import puede ejecutar código como el usuario privilegiado, potencialmente antes de que la herramienta rechace un módulo no válido. Comprueba la versión instalada, la política exacta de RunAs y argumentos de sudo, y la propiedad de las rutas del preset y del módulo sin cargar el módulo durante la enumeración.

### Herramienta de línea de comandos Backdrop ejecutada con sudo

[Bee](https://github.com/backdrop-contrib/bee) es una herramienta de línea de comandos PHP para Backdrop CMS. Sus comandos `eval` (`php-eval`) y `php-script` pueden ejecutar PHP proporcionado por quien los invoca. Por tanto, una regla de sudo que permita el ejecutable Bee como root con argumentos irrestrictos puede exponer la ejecución de código como root si Bee puede inicializar una instalación de Backdrop. Ejecútalo desde el directorio del sitio o selecciona un sitio con la opción global `--root=<directory>`; encontrar Bee o un archivo `settings.php` de Backdrop no demuestra por sí solo que sudo lo permita, que el sitio sea utilizable ni que la inicialización tenga éxito. Antes de hacer pruebas, revisa la regla efectiva de sudo, cualquier exclusión de comandos, la identidad del ejecutable y el acceso al sitio. Durante la enumeración pasiva, inspecciona la regla y las rutas de archivo sin invocar Bee. Consulta el [changelog de comandos de Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver cuándo se añadieron los comandos PHP.

### Servidores de terminal ejecutados con sudo

`mosh-server` inicia un servidor de terminal interactivo como el usuario que lo invoca. Elige un puerto UDP alto y una clave de sesión, informa de ambos a quien lo invoca y normalmente inicia el shell de inicio de sesión de ese usuario cuando se conecta un cliente. Por tanto, un permiso irrestricto de sudo con capacidad de root para `mosh-server` es un candidato para revisar como shell, aunque el propio comando del servidor se separe del proceso. Comprueba la identidad RunAs efectiva, los argumentos permitidos y las exclusiones, el binario instalado, el shell, la disponibilidad del cliente y el acceso UDP. La enumeración pasiva debe inspeccionar la regla de sudo sin iniciar un servidor ni mostrar una clave de sesión activa. Consulta el [manual del servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) y las [notas de diseño del proyecto](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers privilegiados de backup que reescriben el archivo de tareas de quien los invoca

Un wrapper de shell ejecutado como root puede aceptar un archivo de tareas seleccionado por quien lo invoca, eliminar `../` de las rutas de origen, comprobar que cada resultado empiece por un directorio permitido, reescribir el archivo de tareas y luego pasar su *nombre de ruta* a un programa de backup. Revisa la ruta transformada después de resolverla canónicamente por completo: una sola pasada de sustitución de cadenas puede crear una nueva secuencia de recorrido que una comprobación de prefijo léxica acepte. Comprueba también si el programa de backup lee los datos transformados en memoria o vuelve a abrir el archivo. Si lo vuelve a abrir, una reescritura fallida puede dejar intacta la entrada original.

En Linux, `fs.protected_regular` puede denegar una escritura `O_CREAT` en un archivo regular de otro usuario dentro de un directorio sticky con permisos de escritura para todos. Esa denegación es protectora, pero un wrapper de shell que ignore el error de escritura aún puede continuar con el archivo de tareas original. Confirma el ajuste, el propietario del archivo y el directorio, y si el wrapper se detiene ante un fallo. La ruta solo es candidata a divulgar archivos si la regla efectiva de sudo permite ejecutar el wrapper como usuario privilegiado, quien lo invoca controla la entrada de tareas y un destino de backup legible, y la utilidad de backup realmente incluye fuentes protegidas. Inspecciona estas condiciones sin ejecutar el backup durante la enumeración.

### Comodines de argumentos en herramientas de red privilegiadas

En una regla de sudo para `tcpdump`, un `*` en el **patrón de argumentos** puede coincidir con espacios y barras, así que una restricción que parece limitar la ruta podría permitir texto de opción adicional. Esto es distinto de un comodín en la ruta del ejecutable del comando; inspecciona la regla completa de RunAs y cualquier denegación posterior. Si se pueden inyectar opciones, la invocación permitida y la [semántica de las opciones de `tcpdump` instalado](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinan si `-F`, `-V`, `-r`, `-w` o `-Z` proporcionan una primitiva útil de lectura/escritura. `-V` lee una lista de nombres de archivo de capturas, no vuelca archivos arbitrarios de propósito general. AppArmor u otra política MAC puede bloquear el acceso a archivos aunque sudo permita el comando; un archivo de perfil en disco no demuestra que esté cargado ni en modo enforce. Antes de llegar a una conclusión, revisa pasivamente la autorización y la política. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) describe la diferencia entre comodines.

Una regla de sudo con capacidad de root que enumera solo el ejecutable `tcpdump`, sin restricción de argumentos, también merece revisión. El [manual de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como comando posterior a la rotación cuando `-C` o `-G` rota una captura guardada; `-Z` o un valor predeterminado de compilación pueden reducir privilegios antes de que se ejecute ese comando. Antes de considerar la regla una vía de escalada, verifica la regla efectiva de sudo, la compilación instalada, el comportamiento de reducción de privilegios y si puede producirse una rotación. Una regla resaltada es un caso candidato, no una prueba de ejecución de comandos como root.

### Wrappers de Nmap ejecutados con sudo

Cuando la ruta de `nmap` permitida por sudo es un wrapper de shell, inspecciona la ruta exacta permitida y cada opción que reenvía. Bloquear la forma conocida `--script` no necesariamente impide cargar código NSE: [`--datadir` de Nmap](https://nmap.org/book/man-misc-options.html) selecciona archivos de datos, y NSE [carga `nse_main.lua`](https://nmap.org/book/nse-implementation.html) desde el directorio de datos seleccionado cuando se habilita el scripting. Algunas compilaciones instaladas también aceptan formas alternativas de opciones largas, así que compara las restricciones con el parser real de ese binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) es otra superficie de lectura de archivos; los errores del parser pueden revelar texto. Comprueba la regla efectiva de sudo, la lógica del wrapper, la versión de Nmap, el control del directorio y la política MAC sin ejecutar análisis durante la enumeración.

### Hooks de pull de Mercurial ejecutados con sudo

Un origen fijo en `sudo hg pull /fixed/source` aún deja que el directorio de trabajo actual seleccione el repositorio **receptor**, salvo que el comando lo fije con `-R`. Un repositorio receptor controlado por quien lo invoca puede definir hooks en `.hg/hgrc`, y un hook puede ejecutarse como el usuario RunAs de sudo. [Mercurial ignora la configuración de repositorio propiedad de un usuario o grupo no confiable](https://mercurial-scm.org/help/topics/config), así que inspecciona los usuarios/grupos de confianza de la cuenta RunAs y el directorio de trabajo exacto antes de considerarlo ejecución de código. Para una revisión pasiva basta con leer la política y la configuración; no ejecutes `pull` ni invoques un hook para enumerar el riesgo.

### Hooks de pull de Git ejecutados con sudo

Para un permiso exacto de sudo con capacidad de root para `sudo git pull`, comprueba también el repositorio **receptor** seleccionado por el directorio de trabajo. Un repositorio propiedad de quien lo invoca puede tener un hook `post-merge` ejecutable que se ejecuta con la identidad del proceso Git cuando un pull completa correctamente un merge; [Git documenta este hook](https://git-scm.com/docs/githooks) y [el comportamiento de pull con merge frente a rebase](https://git-scm.com/docs/git-pull). Verifica la regla efectiva de sudo y el CWD, la ruta activa del hook y sus permisos, y si es posible que se realice un merge con commits nuevos. Un pull fallido, sin cambios o solo con rebase no demuestra que esta vía del hook exista. Inspecciona la política y los metadatos del repositorio sin ejecutar el pull privilegiado.

### Copias de archivado rsync ejecutadas con sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` en el **patrón de argumentos de sudoers** puede coincidir con espacios y admitir una opción adicional entre el origen y el destino. Esto es distinto de la expansión de nombres de archivo del shell. Si quien lo invoca puede llenar el origen y el proceso rsync privilegiado puede escribir en el destino, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) puede solicitar propiedad privilegiada mientras el modo de archivado conserva los bits de permiso, lo que puede crear un archivo SetUID propiedad de quien se especifique. Comprueba la semántica exacta de los [comodines de sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versión de rsync, las denegaciones posteriores, `nosuid` del sistema de archivos y la política MAC. Una regla coincidente es un caso para revisar, no una prueba de que la escalada de privilegios tenga éxito.

### Exportación de reglas de filtrado de paquetes ejecutada con sudo

Un permiso irrestricto de sudo con capacidad de root tanto para `iptables` como para `iptables-save` (o para el par correspondiente `ip6tables`) requiere revisar la escritura de archivos. El match `comment` acepta texto de reglas elegido por quien lo invoca, mientras que `iptables-save -f` escribe el conjunto de reglas serializado en una ruta seleccionada.<sup>[[20]](#references)[[21]](#references)</sup> La utilidad de una carga depende de cómo el backend instalado serialice los comentarios y de si el archivo de destino admite otras líneas en la exportación; `iptables-save` por sí solo no proporciona contenido arbitrario elegido por quien lo invoca. Comprueba la identidad RunAs, los argumentos y las exclusiones exactos de sudo, la extensión de match disponible, el backend y los permisos del destino. Durante la enumeración, inspecciona el permiso sin cambiar las reglas del firewall ni escribir un archivo.

### Directorio de registro de Below privilegiado

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afectó a versiones de Below anteriores a 0.9.0 que creaban el directorio `/var/log/below` con permisos de escritura para todos. Si un servicio o un comando de sudo permitido ejecuta como root una compilación afectada, un usuario que pueda escribir y recorrer un directorio de registros sin sticky bit podría reemplazar una entrada de registro por un symlink antes de que el proceso privilegiado la abra. Revisa el estado del parche del paquete instalado, la ruta exacta de ejecución privilegiada, el acceso efectivo al directorio, el sticky bit y las ACL, y los metadatos de `/var/log/below/error_root.log`. Una ruta con permisos de escritura para todos o una regla de sudo por sí solas no demuestran la cadena completa. Un directorio sticky o un backport del proveedor cambia la evaluación. La enumeración pasiva solo debe inspeccionar metadatos; no es necesario crear un enlace ni ejecutar el programa privilegiado.

### Recopilación privilegiada de paquetes de soporte desde entradas escribibles

Un script de perfil de soporte permitido por `sudo` puede leer rutas de registro fijas como root y copiar su contenido a un archivo de perfil. Revisa el script real para ver qué archivos lee y luego comprueba si quien lo invoca puede reemplazar una ruta de origen o alguna entrada de directorio padre con un symlink. Si la lectura privilegiada sigue ese enlace y el archivo resultante es legible por quien lo invoca, puede divulgarse un archivo protegido. Deben darse todas estas condiciones: el permiso de sudo, una ruta de origen escribible, una lectura privilegiada y una salida legible. Un registro o un nombre de perfil escribible por sí solos no bastan. Inspecciona los permisos efectivos y los metadatos de enlaces sin reemplazar archivos ni generar un perfil durante la enumeración. La [guía de soporte de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documenta su script de perfil ejecutado como root y el archivo de salida, e ilustra por qué estos paquetes requieren entradas y acceso de salida restringidos.

### Scripts de restauración de archivos ejecutados como root

Incluso una regla de sudo estrictamente limitada para un script Python de restauración requiere revisar su entrada de archivo. Si quien lo invoca puede seleccionar o reemplazar el archivo y el script lo extrae como root con `tarfile.extractall(filter="data")`, comprueba las actualizaciones de seguridad del intérprete antes de confiar en el filtro. CPython corrigió varias evasiones de filtros mediante symlinks y hard links, incluida CVE-2025-4517, en las versiones 3.9.23, 3.10.18, 3.11.13, 3.12.11 y 3.13.4. Los backports de las distribuciones pueden corregir versiones anteriores, por lo que la versión mostrada del intérprete no demuestra por sí sola que haya exposición.<sup>[[16]](#references)[[17]](#references)</sup>

Para una revisión pasiva, lee el comando y el script exactos de sudo, sigue el argumento que selecciona el archivo y comprueba si el usuario actual puede escribir en él o en su directorio contenedor. Confirma por separado el parche del proveedor instalado y el destino de extracción; `filter="data"` no hace seguro cualquier archivo no confiable.<sup>[[16]](#references)[[17]](#references)</sup>

### Cargadores de modelos de machine learning ejecutados con sudo

Una regla de sudo que permite seleccionar un archivo `.pt`, `.pth` o `.ckpt` requiere revisión cuando un script privilegiado lo pasa a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` u otro cargador basado en pickle. Comprueba la regla efectiva de RunAs, si quien lo invoca puede crear o reemplazar el modelo seleccionado y el flujo real de argumentos a través de cualquier wrapper de shell hasta el helper Python. La extensión `.pth` también se usa para archivos de configuración de Python site no relacionados, así que la extensión por sí sola no demuestra que se cargue un modelo. Un análisis del archivo comprimido o un análisis estático del pickle no demuestran que la carga posterior sea segura; inspecciona el comportamiento de `weights_only`, que [depende de la versión](https://docs.pytorch.org/docs/stable/notes/serialization.html), y cualquier allowlisting. Consulta las [notas sobre pickle de ML y Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). La enumeración pasiva nunca debe cargar ni descomprimir el modelo.

### Análisis de expresiones de entradas almacenadas ejecutado con sudo

Un script Python fijo ejecutado como root mediante sudo aún puede evaluar texto que un usuario con menos privilegios almacene en la base de datos de una aplicación. En TensorFlow, una llamada a `preprocess_input_exprs_arg_string(value, safe=False)` selecciona una ruta de `eval`; el [aviso de TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) describe el parser inseguro y una corrección en quien lo invoca desde la línea de comandos. Una llamada explícita `safe=False` de una aplicación requiere una revisión aparte, incluso si ese invocador de línea de comandos está parcheado. Comprueba la regla efectiva de sudo, quién puede modificar la fila de entrada concreta, si el filtrado o la puntuación permiten que esa fila llegue a la llamada y el comportamiento de la función instalada. Una versión de TensorFlow, un permiso de sudo o un archivo de modelo codificado de forma fija no demuestran por sí solos la cadena. Inspecciona el script y el flujo de datos pasivamente; no ejecutes el helper privilegiado ni envíes expresiones de prueba durante la enumeración.

### Configuración de needrestart permitida por sudo

`needrestart -c` carga un archivo de configuración Perl seleccionado por quien lo invoca y evalúa su contenido. Si `sudo -l` permite ejecutar `needrestart` como root con argumentos que admiten `-c`, y quien lo invoca puede elegir un archivo de configuración legible en una ubicación escribible, ese permiso puede conducir a ejecución de código como root. Comprueba la regla exacta de RunAs y argumentos de sudo; una regla que permita solo una lista fija de argumentos puede bloquear esta vía. Esto es independiente de las vulnerabilidades de needrestart al analizar intérpretes: actualizar el paquete o desactivar `interpscan` no vuelve seguro un permiso irrestricto de root con `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports de Python ejecutados con sudo bajo otra cuenta

Un punto de entrada Python fijo aún puede importar un módulo que quien lo invoca pueda editar o reemplazar, incluso si sudo ejecuta el script como un usuario de servicio **que no es root**. Para un `from utils import status` literal, revisa `utils/__init__.py` y `utils/status.py` locales, así como los permisos del directorio del paquete. Confirma la ruta de importación del script, los argumentos exactos de sudo permitidos y si la acción pertinente llega a ese import antes de considerar el archivo escribible una vía de ejecución. Inspecciona archivos y permisos sin importar ni ejecutar el script durante la enumeración.<sup>[[2]](#references)[[3]](#references)</sup>

Una regla exacta de sudo para `python3 /absolute/script.py` solo requiere que el script sea legible; no necesita ser ejecutable ni tener un shebang. Revisa también los módulos locales **ausentes**: si el script importa un módulo cuyo nombre de archivo se puede crear en un directorio de scripts escribible por quien lo invoca, Python puede cargar ese archivo bajo la identidad RunAs. Confirma la regla efectiva de sudo, la [ruta de búsqueda de módulos real](https://docs.python.org/3/library/sys_path_init.html) del intérprete, si el módulo es integrado o congelado y si se alcanza el import. Una regla directa de sudo para el script tiene requisitos distintos de bit de ejecución y shebang. Un wrapper separado que añada tokens proporcionados por quien lo invoca después de `sudo -u account` también requiere revisar el flujo de argumentos: otro `-u` en esos tokens solo importa si la política de sudo invocada permite la identidad resultante. Las cadenas estáticas por sí solas no demuestran ninguna de las dos vías.

### Apache ejecutado con sudo y una configuración controlada por quien lo invoca

Si una regla de sudo permite invocar `apachectl`, `apache2ctl` o `httpd` privilegiado con un archivo de configuración `-f` controlado por quien lo invoca, revisa los permisos de ese archivo y de su directorio padre. La directiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) de Apache recibe un nombre de módulo seguido del **nombre de archivo del módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) también carga un archivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) pueden ampliar la configuración o exponer contenido de archivos mediante errores. Un wrapper personalizado puede validar estas rutas, reducir privilegios o restringir argumentos, así que una configuración escribible es un caso para revisar, no una prueba de ejecución de código. Comprueba la canonicalización de rutas, los symlinks y el análisis de directivas antes de llegar a una conclusión.

### nginx ejecutado con sudo y una configuración controlada por quien lo invoca

Una regla irrestricta de sudo con capacidad de root para `nginx` puede permitir que [`-c` seleccione otra configuración](https://nginx.org/en/docs/switches.html). Revisa los argumentos exactos y las exclusiones de sudo, si quien lo invoca puede proporcionar la configuración y si el master o los workers resultantes conservan acceso a rutas protegidas. Un `root` seleccionado junto con `autoindex` puede exponer archivos mediante un listener nuevo; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) puede proporcionar una vía de escritura privilegiada, pero el módulo DAV no se compila de forma predeterminada y hay que comprobar si está presente, la accesibilidad del listener, los permisos de archivos y el comportamiento de los archivos temporales. La directiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) también puede apuntar a un archivo seleccionado; escribir registros en un archivo de configuración sensible, como `/etc/ld.so.preload`, requiere un escritor privilegiado efectivo y un registro controlable antes de convertirse en una vía de escalada. Que el ejecutable aparezca resaltado en `sudo -l` es una señal para revisar, no una prueba de que alguna de estas vías funcione. La enumeración pasiva no debe iniciar ni reconfigurar nginx.

### Comparación de patrones en prompts Bash privilegiados

Cuando un script Bash permitido por sudo lee un valor de quien lo invoca y lo comprueba con `[[ "$expected" == $entered ]]`, Bash interpreta como patrón el operando derecho sin comillas. Por tanto, un comodín puede satisfacer la comparación sin conocer el valor esperado. Poner el operando entre comillas (`[[ "$expected" == "$entered" ]]`) hace que la comparación trate la cadena literalmente. Revisa la regla exacta de sudo, si se puede llegar al prompt y qué hace el script después de la comparación; la sintaxis por sí sola no demuestra que haya una vía explotable. Evita mostrar el valor esperado durante la enumeración. Consulta la [referencia de construcciones condicionales de Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers ejecutados con sudo que descargan y ejecutan un archivo

Un permiso irrestricto de sudo con capacidad de root para un helper personalizado requiere revisar el flujo de datos si acepta una URL seleccionada por quien lo invoca, escribe la respuesta en disco y luego ejecuta ese archivo con un intérprete o shell. [Sudoers permite argumentos arbitrarios cuando una entrada de comando no especifica ninguno](https://man7.org/linux/man-pages/man5/sudoers.5.html); una ruta fija de ejecutable no restringe lo que pueden seleccionar sus argumentos. Confirma la validación real de URL, la ruta de salida, la rama de éxito y la ejecución posterior en el helper instalado. Un import de libcurl o una cadena imprimible que coincida no demuestran por sí solos esta cadena.

Incluso un nombre base de salida fijo puede ser reemplazable entre la escritura y la ejecución cuando el helper usa una **ruta relativa en un directorio de trabajo controlado por quien lo invoca**. Renombrar o reemplazar un archivo propiedad de root depende del acceso de escritura y búsqueda en el directorio y de las restricciones del sticky bit, no solo del modo del archivo; consulta [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Comprueba si el helper vuelve a abrir la ruta más tarde o usa el descriptor ya abierto, y si cambia a un directorio de confianza antes de escribir. Inspecciona pasivamente la política de sudo, el helper y los metadatos del directorio; no invoques la descarga privilegiada ni intentes una carrera durante la enumeración.

Un helper de descarga ejecutado como root mediante sudo también puede exponer una inyección de **argumentos** si construye una cadena de comando Bash como `curl <caller input> -o <fixed output>`. Un filtro que rechaza espacios aún deja activa la [expansión de llaves de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): los elementos separados por comas y sin comillas pueden convertirse en argumentos distintos de curl. Si la entrada llega a curl antes del `-o` fijo, una opción de salida suministrada por quien lo invoca podría seleccionar el destino de la primera URL bajo la identidad del helper; [curl asocia las opciones de salida con las URL en orden](https://curl.se/docs/manpage.html#-o). Confirma el shell exacto, el uso de comillas, la validación de entrada, la regla efectiva de sudo, el orden de argumentos de curl y los esquemas de URL admitidos, y si quien lo invoca controla los bytes descargados o puede leer el resultado. Un ejecutable empaquetado con PyInstaller puede contener lógica de aplicación Python, pero su marcador de empaquetado o una cadena `curl` por sí solos no demuestran este flujo de datos. Revisa una copia offline acotada cuando esté autorizado; la enumeración habitual no debe ejecutar el helper ni obtener datos elegidos por un atacante.

Un script de shell ejecutado como root mediante sudo que llama a [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) solo elige un nombre libre; **no** crea el archivo. Si luego el script crea ese nombre en un directorio que otro usuario puede afectar, lo vuelve a abrir y añade su contenido a un destino protegido, como `authorized_keys` de root, revisa la posibilidad de una carrera con el archivo temporal. Confirma la regla exacta de sudo, la propiedad del directorio y del archivo, la secuencia de creación y reapertura, las protecciones del kernel y si la escritura privilegiada realmente utiliza bytes controlados por un atacante. Una cadena `mktemp -u` o un `/tmp` escribible por sí solos no demuestran la carrera. Inspecciona el script y los metadatos de la ruta sin ejecutarlo ni disputar su archivo temporal durante la enumeración.

## Notas defensivas

- Evita conceder intérpretes o editores interactivos mediante sudo.<sup>[[1]](#references)</sup>
- Prefiere wrappers fijos propiedad de root que realicen una única acción administrativa limitada.<sup>[[1]](#references)[[2]](#references)</sup>
- Si no se puede evitar un intérprete, restringe la ruta exacta del script e impide los argumentos controlados por usuarios, los imports escribibles, `PYTHONPATH` y la conservación de entornos inseguros.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si es necesario editar archivos, restringe la ruta exacta y considera `sudoedit` con versiones de sudo parcheadas y un manejo estricto del entorno.<sup>[[1]](#references)[[2]](#references)</sup>
- Revisa `SETENV`, `env_keep`, los directorios de trabajo escribibles, las rutas de módulos/imports escribibles, `NOEXEC`, `use_pty` y el registro, pero no los consideres un sandbox completo.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
