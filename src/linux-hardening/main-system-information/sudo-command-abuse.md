## Mit Sudo erlaubte Interpreter

Wenn `sudo -l` einem Benutzer erlaubt, einen Interpreter als root auszuführen, sollte dies als direkte Codeausführung behandelt werden. Interpreter sind dafür ausgelegt, beliebigen Code auszuführen. Eine Regel, die `python3`, `perl`, `ruby`, `lua`, `node` oder ähnliche Binärdateien erlaubt, ist daher meist gleichbedeutend mit der Ausführung von Befehlen als root, sofern die Argumente nicht streng eingeschränkt und validiert werden.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Üblicher Prüfablauf: Zuerst die Berechtigungen des Benutzers auflisten, dann mit der Option `-c` des Interpreters eine Python-Anweisung ausführen.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Weitere Interpreter-Beispiele sind unten aufgeführt; die genannten Interpreter dokumentieren die Ausführung von Inline-Code oder APIs für Kindprozesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Der genaue Pfad ist wichtig. Wenn die sudo-Regel `/usr/bin/python3` erlaubt, verwenden Sie bei der Überprüfung genau diesen Pfad.<sup>[[2]](#references)</sup>

Ein sudo-Executable-Glob wie `/usr/bin/python*` kann auch Python 2 zulassen, obwohl ein Skript für Python 3 geschrieben wurde. Wenn das Skript `input()` mit vom Aufrufer kontrolliertem Text erreicht, [wertet Python 2 diesen Text als Ausdruck aus](https://docs.python.org/2/library/functions.html#input); ein expliziter Interpreter-Aufruf setzt den Shebang des Skripts außer Kraft. Überprüfen Sie die installierten passenden Binärdateien, die wirksame RunAs- und Argumentrichtlinie, Ablehnungen und erreichbare Eingaben, bevor Sie dies als Ausführungspfad einstufen.

Ein fester Skriptpfad in einer root-fähigen sudo-Regel schränkt nicht ein, was das Skript ausführt. Prüfen Sie bei einem lesbaren Bash-Wrapper, ob sein erster ausführbarer Befehl einen nicht in Anführungszeichen gesetzten Positionsparameter wie `$1` als **Befehlswort** verwendet, während sudo vom Aufrufer gewählte Argumente zulässt. Bestätigen Sie die wirksame RunAs-Identität, die Passwort- und Argumentrichtlinie, spätere Ablehnungen und den tatsächlich ausgeführten Skriptzweig; `NOEXEC`, eine feste sichere Argumentliste oder ein Wrapper, der seinen Befehl validiert, können das Ergebnis verändern. Untersuchen Sie das kurze Skript während der Aufzählung statisch, statt es mit einem Testbefehl aufzurufen.

Auch eine uneingeschränkte root-fähige sudo-Regel für `dotnet` sollte auf Interpreter geprüft werden. Wenn ein .NET SDK installiert ist, führt [`dotnet fsi` F#-Code interaktiv oder aus einem Skript aus](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), und [`dotnet run` führt ein Projekt aus dem Quellcode aus](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bestätigen Sie zuerst die wirksame RunAs-Identität und die genaue Argumentrichtlinie: Eine Regel, die auf einen bestimmten sicheren Unterbefehl oder eine vertrauenswürdige Anwendung beschränkt ist, stellt eine andere Berechtigung dar, und bei einer reinen Runtime-Installation fehlen möglicherweise SDK-Befehle. Der Name der ausführbaren Datei allein ist ein Anlass zur Prüfung, kein Beweis für die Ausführung von Code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Von sudo erlaubte Editoren

Wenn `sudo -l` einem Benutzer erlaubt, einen interaktiven Editor als root auszuführen, sollte dies als Möglichkeit zur Befehlsausführung betrachtet werden und nicht als harmlose Berechtigung zur Dateibearbeitung. Editoren können häufig Shell-Befehle ausführen, beliebige Dateien lesen oder schreiben oder externe Hilfsprogramme direkt im Editor aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Üblicher Prüfablauf: die Berechtigungen des Benutzers auflisten und anschließend jeden erlaubten Editor oder Pager mit sudo aufrufen.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Befehlsausführung mit Nano

Wenn `nano` über sudo erlaubt ist, kann die Befehlsausführung über die Editoroberfläche erreichbar sein.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Geben Sie anschließend einen Befehl wie `id` oder `/bin/sh` an der nano-Eingabeaufforderung ein.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Wenn eine interaktive Shell keine nutzbaren Terminal-Datenströme hat, leitet diese Umleitungsform ihre Standardausgabe und Standardfehler auf Dateideskriptor 0 um.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die genaue Tastenfolge kann je nach nano-Version und Build-Optionen variieren, aber das Sicherheitsproblem bleibt dasselbe: Der Editor läuft als root und kann externe Befehle ausführen.<sup>[[1]](#references)[[12]](#references)</sup>

### Andere gängige Editor-Escapes

Vim-ähnliche Editoren ermöglichen die Ausführung von Befehlen üblicherweise über `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pager wie `less` können ebenfalls die Ausführung einer Shell ermöglichen.<sup>[[14]](#references)</sup>

Eine sudo-Regel, die `apport-cli` als root erlaubt, sollte ebenfalls auf Pager geprüft werden. Betroffene Apport-Versionen konnten einen Crash-Report in `less` mit einer vom Angreifer anpassbaren Terminalgröße öffnen; der Pager konnte dann eine root-Shell bereitstellen, wenn die besonderen sudo- und Pager-Bedingungen erfüllt waren. Prüfen Sie die effektive sudo-Regel, die Pager-Konfiguration und den Paket-Fix der Distribution, bevor Sie allein aufgrund der Version von einer Schwachstelle ausgehen. Lesen Sie bei der passiven Enumeration die Paket- und Richtlinienmetadaten, ohne einen Crash zu erzeugen oder den privilegierten Report zu öffnen. [Ubuntus CVE-Eintrag](https://ubuntu.com/security/CVE-2023-1326) führt versionsspezifische Fix-Versionen für Releases auf, darunter auch zurückportierte Fixes.

```text
!/bin/sh
```

## Weitere Gefahren durch sudo- und doas-Regeln

Beginne mit `sudo -l`, `sudo -V` und allen zutreffenden `doas`-Richtlinien. Lies den erlaubten Befehl, den RunAs-Benutzer, die Argumente, die Umgebung und die Defaults gemeinsam. Die Berechtigung, einen Befehl als Nicht-root-Dienstkonto auszuführen, kann trotzdem Dateien dieses Kontos offenlegen oder einen Weg zu root bieten.

Ein festgelegtes, über sudo erlaubtes Python-Skript kann trotzdem einen Shell-Befehl unter seiner RunAs-Identität ausführen, wenn interaktive, vom Aufrufer kontrollierte Eingaben an [`os.system()`](https://docs.python.org/3/library/os.html#os.system) angehängt werden. Eine Denylist von Shell-Zeichen reicht nicht aus, um Sicherheit festzustellen: [Die Shell erkennt auch `$(...)`-Command-Substitution](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Stelle fest, ob die erlaubten Argumente den Eingabezweig erreichen, ob die Eingabe ohne sichere Validierung in den Shell-Befehl gelangt und ob die effektive sudo-Richtlinie den vorgesehenen RunAs-Benutzer erlaubt. Der Skriptpfad oder ein Aufruf von `os.system()` ist nur ein Hinweis für eine Prüfung; untersuche den Quellcode, ohne das privilegierte Skript aufzurufen.

Ein effektiver root-sudo-Zugriff auf `chattr` kann das unveränderliche (`i`) Datei-Attribut entfernen, gewährt aber allein weder Schreibzugriff noch eine neue Identität. Im [Handbuch zu `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) steht, dass das Attribut Änderungen verhindert und nur root oder ein Prozess mit `CAP_LINUX_IMMUTABLE` es ändern kann. Prüfe die genauen sudo-Argumentregeln und die Unterstützung des Dateisystems. Verifiziere anschließend gesondert, ob der Aufrufer nach dem Entfernen des Attributs in die Datei schreiben kann und ob ein Prozess mit höherer Identität sie verwendet. Ein Ersatz der Login-Shell erfordert beispielsweise auch gültige Zugangsdaten für das Zielkonto und eine tatsächliche Anmeldung über diese Shell. Prüfe Richtlinien, Datei-Attribute und Berechtigungen, ohne sie während der Bestandsaufnahme zu ändern.

Wenn sudo sowohl nach einem Passwort als auch nach einem Einmalcode fragt, behandle diese Voraussetzungen getrennt von der Befehlsberechtigung. Eine lesbare `.google_authenticator`-Datei enthält sensibles Seed-Material; ein alter Passwort-Hash aus einer Anwendung oder Datenbank ist lediglich ein Kandidat für das aktuelle Kontopasswort. Keines von beiden beweist, dass der andere Faktor von der effektiven PAM-Konfiguration akzeptiert wird. Prüfe nach erfolgter Autorisierung die genauen RunAs- und Argumentregeln: Eine uneingeschränkte root-Berechtigung für RubyGems `gem` kann dessen Editor-Befehl zugänglich machen ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)); eine eingeschränkte Berechtigung oder fehlgeschlagene Authentifizierung dagegen nicht. Eine passive Bestandsaufnahme sollte Pfade und Richtlinien melden, ohne das Seed auszugeben, ein Passwort wiederherzustellen, einen Code zu erzeugen oder den privilegierten Befehl aufzurufen.

Eine uneingeschränkte, root-fähige sudo-Berechtigung für Chefs `knife` erfordert eine Prüfung auf Interpreterebene: [Chef dokumentiert, dass `knife exec -E` lokal einen Ruby-String auswertet](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Prüfe, ob die effektive sudo-Regel das Unterkommando `exec` und das vom Aufrufer bereitgestellte Argument `-E` erlaubt, welche RunAs-Identität vorgesehen ist und ob passende Befehlsverweigerungen oder festgelegte Argumente gelten. Die installierte Binärdatei oder eine Regel, die auf andere Unterkommandos beschränkt ist, ist lediglich ein Hinweis. Eine passive Bestandsaufnahme sollte die Regel melden, ohne `knife` aufzurufen.

Eine exakte, root-fähige sudo-Berechtigung für ein interaktives `msfconsole` ist ebenso sensibel: [GTFOBins dokumentiert dessen `irb`-Konsole](https://gtfobins.org/gtfobins/msfconsole/), die die sudo-Identität übernehmen kann. Prüfe den effektiven RunAs-Benutzer, die erlaubte Argumentliste, Befehlsverweigerungen, `NOEXEC` und andere Einschränkungen, das Verhalten der installierten Konsole und ob der Aufrufer interaktive Eingaben liefern kann. Eine hervorgehobene Pfadangabe ist nur ein Prüfhinweis; die passive Bestandsaufnahme sollte die Konsole nicht starten.

Unter FreeBSD verdient selbst eine auf `pkg update` als root und `pkg install *` beschränkte sudo-Regel eine Prüfung des Repository-Vertrauens. Prüfe, ob `/etc/hosts` für den Aufrufer beschreibbar ist und ob die *effektive* aktivierte Repository-Konfiguration einen HTTP-Hostnamen mit `signature_type: none` verwendet. Im [Handbuch zu FreeBSDs `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) steht, dass `none` Signaturprüfungen deaktiviert; `pkg+http` allein weist das nicht nach. Ein Paket kann Installationsskripte enthalten ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)). Ein Aufrufer, der den Repository-Endpunkt tatsächlich kontrolliert und ein Paket auswählen kann, könnte daher die root-Grenze überschreiten. Prüfe Repository-Überschreibungen, SRV-/Mirror-Auflösung, effektive sudo-Argumente, Paketauswahl und Skriptausführung, bevor du diesen Schluss ziehst. Untersuche Richtlinien und kleine lokale Konfigurationsdateien, ohne Namen umzuleiten oder während der Bestandsaufnahme `pkg` auszuführen.

Eine root-fähige sudo-Regel für `apt-get update` und `apt-get upgrade` erfordert ebenfalls eine Prüfung des Repository-Vertrauens, wenn sudo ein vom Aufrufer kontrolliertes `http_proxy` beibehält. Prüfe, ob die effektive APT-Proxykonfiguration diese Variable tatsächlich verwendet und welche aktivierten Repository-Anfragen sie beeinflussen kann; ein Proxy allein kann keine Pakete aus einem Archiv ersetzen, das mit einem vertrauenswürdigen Signaturschlüssel authentifiziert wird. Das [Handbuch zu APTs HTTP-Transport](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) beschreibt die Proxy-Priorität; [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) erläutert Signaturprüfungen, Überschreibungen für unsichere Repositories und die Bestätigung für nicht authentifizierte Pakete. Prüfe die genauen sudo-RunAs- und Argumentregeln, die Repository-Authentifizierungsrichtlinie, gegebenenfalls erforderliche interaktive Bestätigungen und ob das ausgewählte Upgrade Paketskripte als root ausführt. Untersuche Richtlinien und lokale Konfiguration passiv; leite während der Bestandsaufnahme keinen Paketverkehr um und führe kein Upgrade aus.

Eine root-fähige sudo-Regel für `snap install` kann eine Grenze zwischen Paket und Code bilden, wenn die Argumente dem Aufrufer erlauben, einen lokalen Snap und einen permissiven Installationsmodus auszuwählen. [Snap dokumentiert](https://snapcraft.io/docs/explanation/snap-development/install-modes/), dass `--dangerous` Assertion-Prüfungen für lokale Snaps überspringt und `--devmode` die Confinement-Einschränkungen lockert; [ein Installations-Hook kann bei der Erstinstallation ausgeführt werden](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prüfe die genauen sudo-Argumente und die RunAs-Richtlinie, wer die Snap-Datei kontrolliert, ob die installierte Version von snapd diese Modi akzeptiert und welche Identität und Confinement der Hook tatsächlich hat, bevor du Zugriff auf geschützte Hostdateien behauptest. Eine `snap`-Binärdatei oder eine scheinbar mit Wildcards versehene Regel beweist diese Kette nicht. Bei einer passiven Bestandsaufnahme sollten weder Pakete installiert noch deren Hooks ausgeführt werden.

Bei einer exakten sudo-Berechtigung für eine benutzerdefinierte, Zugangsdaten lesende Binärdatei eines **Nicht-root-Kontos** solltest du zuerst die gewährte Binärdatei und ihre Dateiberechtigungen untersuchen, ohne sie auszuführen. Eine eingebettete Passwortabfrage ist möglicherweise nur als Wide-Character-Text sichtbar; [GNU `strings` dokumentiert die Extraktion von 16-Bit-Little-Endian-Text](https://sourceware.org/binutils/docs/binutils/strings.html). Ein sichtbarer String beweist weder, dass es sich um das akzeptierte Passwort handelt, noch, dass der Erfolgszweig aktuelle Zugangsdaten offenlegt. Prüfe das Verhalten der Binärdatei, den Zugriff des Zielkontos auf die geschützten Daten, die Gültigkeit der Zugangsdaten und jeden späteren Konto- oder Gruppenwechsel getrennt. Wenn das Konto zur Gruppe `docker` gehört, prüfe den Socket-Zugriff sowie, ob der Daemon rootful oder rootless läuft, bevor du auf Host-root-Zugriff schließt; [Docker dokumentiert die Auswirkungen seiner Gruppe auf Root-Ebene](https://docs.docker.com/engine/install/linux-postinstall/). Eine routinemäßige Bestandsaufnahme sollte die sudo-Regel und Gruppenmitgliedschaft melden, ohne die Binärdatei auszuführen oder ihre Strings auszugeben.

Eine sudo-Regel mit Wildcard für die Wartungsskripte einer Anwendung muss über den Skriptpfad hinaus geprüft werden. Prüfe, ob das erlaubte Skript uneingeschränkte Argumente akzeptiert oder Einstellungen einliest, die über ein Anwendungskonto mit niedrigeren Berechtigungen beschreibbar sind. Verfolge anschließend diese Werte bis zu Shell-Befehlen oder einer Subprozessumgebung. Beispielsweise setzt ZoneMinders [`zmupdate.pl` einen `mysqldump`-Befehl zusammen und führt ihn über `qx` aus](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), während [`zmdc.pl` die Einstellung `ZM_LD_PRELOAD` in `LD_PRELOAD` kopiert](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in), bevor Daemons gestartet werden. Eine sudo-Regel, die eines der beiden Skripte als root erlaubt, kann eine Vertrauensgrenze überschreiten, wenn die entsprechende Eingabe kontrollierbar ist und im installierten Skript diese Stelle erreicht. Prüfe die effektive sudo-Regel, die Rechte auf die Anwendungskonfiguration und den Skriptquellcode; die Wildcard oder Einstellung allein ist ein Prüfhinweis, kein Ausführungsnachweis.

- `SETENV`, `env_keep`, `secure_path` und `LD_PRELOAD` können aus einem ansonsten eng begrenzten Befehl einen Import-, Bibliotheks- oder PATH-Hijack machen. Siehe den [Leitfaden zu Umgebungsvariablen](../linux-basics/linux-environment-variables.md) und [SUID-/Linker-Missbrauch](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Eine exakte, root-fähige `SETENV`-Berechtigung für einen Shell-Wrapper verdient ebenfalls eine Prüfung auf einen direkten Folgeeffekt, wenn der Wrapper ein festes Python-Skript mit einem wörtlichen Import startet. `secure_path` beschränkt die Suche nach Shell-Befehlen, nicht die [`PYTHONPATH`-Modulsuche von Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` und `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) bewirken, dass Python diese Umgebungsvariable ignoriert. Prüfe die effektiven sudo-Tags und Verweigerungen, den Wrapper-Zweig, Interpreteroptionen, die Importauflösung und ein vom Aufrufer beschreibbares Suchverzeichnis, bevor du dies als Codeausführung einstufst. Untersuche kurze Skripte statisch; rufe den privilegierten Wrapper nicht auf.

Eine exakte, root-fähige sudo-Berechtigung für `neofetch ""` kann trotzdem eine Shell-Konfiguration laden, wenn die zutreffenden sudo-Defaults ein vom Aufrufer kontrolliertes `XDG_CONFIG_HOME` beibehalten. [Neofetchs Konfigurationslader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) liest `neofetch/config.conf` oder `neofetch/config` aus diesem Verzeichnis ein; die leere Argumentliste verhindert diese Suche nicht. Prüfe den installierten Lader, die effektiven RunAs- und Argumentregeln, etwaige Befehlsverweigerungen, ob sudo die ausgewählte Variable für diesen Befehl tatsächlich beibehält und ob der Aufrufer einen lesbaren Konfigurationspfad kontrolliert. Eine beibehaltene Variable oder ein installiertes Neofetch ist lediglich ein Prüfhinweis. Untersuche Richtlinien und Dateimetadaten, ohne den privilegierten Befehl aufzurufen oder Konfigurationsinhalte auszugeben; siehe [Umgang mit der Umgebung in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Eine uneingeschränkte, root-fähige sudo-Regel für `facter` verdient eine gesonderte Prüfung benutzerdefinierter Facts. [Puppet dokumentiert](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), dass `--custom-dir` Ruby-Fact-Dateien aus einem ausgewählten Verzeichnis lädt. Prüfe, ob die exakte sudo-Regel diese Option erlaubt, ob das installierte Facter sie akzeptiert und ob der Aufrufer das Verzeichnis kontrolliert. Eine Berechtigung mit festen Argumenten, eine ausdrückliche Befehlsverweigerung oder deaktivierte benutzerdefinierte Facts können das Ergebnis ändern. Eine passive Bestandsaufnahme sollte den möglichen Richtlinienpfad melden, ohne Facter aufzurufen oder Fact-Inhalte zu lesen.

Bei einer exakten, root-fähigen sudo-Berechtigung für ein Skript mit `SETENV` solltest du unqualifizierte Befehlsnamen wie `find` und das effektive `PATH` nach Anwendung der sudo-Richtlinie und Skriptinitialisierung prüfen. Eine eingebundene Bash-Datei kann außerdem `enable -n [` ausführen: [Bash sucht danach in `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) nach einem externen Befehl `[` für spätere entsprechende Aufrufe im Skript. Prüfe die zutreffenden [sudoers-Regeln zu Umgebung und `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), etwaige `NOSETENV`-/`NOEXEC`- oder Verweigerungseinträge, den Ablauf im Skript und in eingebundenen Dateien sowie ein ausführbares, vom Aufrufer kontrolliertes Suchverzeichnis. Ein lesbares Skript mit einem unqualifizierten Befehlsnamen ist ein Prüfhinweis, kein Nachweis privilegierter Ausführung; untersuche es, ohne die sudo-Regel aufzurufen.
- Ein privilegiertes Skript, das mit `curl` eine feste URL abruft, kann trotzdem eine vom Aufrufer ausgewählte Antwort erhalten, wenn eine zutreffende sudo-Regel `http_proxy` beibehält und die Anfrage über diesen Proxy gesendet wird. Übergibt das Skript die Antwort anschließend an einen XML-Parser, der externe Entitäten auflöst, kann eine manipulierte Antwort Dateien offenlegen, die für den privilegierten Prozess lesbar sind. Prüfe die genaue sudo-Umgebungsrichtlinie, `no_proxy`-Ausnahmen, die angeforderte URL, die Parserkonfiguration und das Ausgabeziel; eine Proxyvariable oder ein XML-Parser allein ist keine Schwachstelle. Die [Dokumentation zu Proxy-Umgebungsvariablen von curl](https://everything.curl.dev/usingcurl/proxies/env.html) beschreibt das Verhalten dieser Variablen. Führe bei einer passiven Bestandsaufnahme keine Netzwerkanfragen aus und verarbeite kein manipuliertes XML.
- Ein root-fähiges sudo-Skript, das aus vom Aufrufer beeinflussten Daten eine PostScript-Datei erstellt und dann `ps2pdf -dNOSAFER` ausführt, verdient eine gesonderte Prüfung des Datenflusses. Ghostscript dokumentiert, dass dieses Flag SAFER bis `.setsafe` deaktiviert und dadurch PostScript-Dateioperationen im Rahmen der Betriebssystemberechtigungen des Prozesses ermöglicht. Eine aus einem Aufruferargument zusammengesetzte SQL-Abfrage kann vom Angreifer kontrollierte Zeilen in die PostScript-Vorlage einspeisen; eine Abfragezeichenfolge oder ein Aufruf von `ps2pdf` allein beweist jedoch nicht, dass die Daten ausführbare PostScript-Syntax erreichen. Prüfe die effektive sudo-Regel, den genauen Weg von der Eingabe zur Vorlage, etwaiges Escaping, das Verhalten der installierten Ghostscript-Version und ob SAFER vor der Interpretation des Dokuments wieder aktiviert wird. Führe während einer passiven Bestandsaufnahme die privilegierte Konvertierung nicht aus. Siehe [Ghostscripts Dokumentation zu `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Vergleiche bei einer sudo-Regel für ein Shell-Skript die beibehaltenen Variablen mit dem Skript selbst. Ein Ausdruck wie `if $CHECK_CONTENT; then` führt den expandierten Wert als Befehl aus. Das Beibehalten von `CHECK_CONTENT` kann daher Befehlsausführung ermöglichen, selbst wenn Skriptpfad und Argumente festgelegt sind. Prüfe für die konkrete Regel, ob der Zweig erreichbar ist und die Umgebung tatsächlich beibehalten wird.<sup>[[2]](#references)[[22]](#references)</sup>
- Ein über sudo erlaubtes Python-Skript kann Code aus einem beschreibbaren Verzeichnis oder einer zwischengespeicherten `.pyc`-Datei importieren. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md) beschreibt den Cache-Fall.
- Ein festes, über sudo als root erlaubtes Python-Skript kann trotzdem einen interaktiven Debugger offenlegen. Aufrufe wie `pdb.set_trace()` oder `pdb.post_mortem()` erlauben Python-Anweisungen im Kontext des untersuchten Prozesses, wenn der Aufrufer den Haltepunkt oder Ausnahmebehandler erreichen **und den Eingabestrom des Debuggers kontrollieren kann**. Prüfe die genaue sudo-RunAs-Regel, Authentifizierung und Zweigbedingungen, die Erreichbarkeit der Ausnahme, die Kontrolle über Terminal und Eingabe sowie, ob der Debugger im selben privilegierten Prozess läuft. Eine Socket-Anfrage, die eine Ausnahme auslöst, gewährt nicht automatisch Zugriff auf einen Debugger, der an ein anderes Terminal gebunden ist. [Python dokumentiert die Auswertung von Anweisungen im Debugger und den Post-mortem-Modus](https://docs.python.org/3/library/pdb.html); untersuche das Skript statisch, statt bei der Bestandsaufnahme den privilegierten Ausnahmebehandler auszulösen.
- Ein festes, über sudo erlaubtes Python-Skript kann außerdem ein Profilfeld aus einer Datenbank oder einem Unix-Socket lesen und an eine Zeichenfolge anhängen, die später zur **Formatzeichenfolge** für `str.format()` wird. [Platzhalter können auf Attribute und Mapping-Schlüssel verweisen](https://docs.python.org/3/library/string.html#format-string-syntax). Ein vom Angreifer kontrolliertes Feld kann daher Objekte untersuchen, die an `format()` übergeben werden, und Daten offenlegen, auf die diese Objekte zugreifen können, wenn das Ergebnis ausgegeben oder an einem für den Aufrufer lesbaren Ort gespeichert wird. Prüfe die effektive sudo-RunAs-Identität, Schreibzugriff auf den konkreten Datensatz, den Datenfluss in die Formatzeichenfolge, die übergebenen Objekte und die Sichtbarkeit der Ausgabe. Dies ist keine automatische Codeausführung; eine literale, vertrauenswürdige Formatzeichenfolge mit vom Angreifer kontrollierten *Werten* ist ein anderer Fall. Ein offengelegtes Geheimnis ermöglicht einen Wechsel zu einem Betriebssystemkonto nur, wenn dieses Konto es akzeptiert. Prüfe Skript und Socket-Berechtigungen, ohne den privilegierten Vorgang aufzurufen.
- Ein root-fähiger Python-Wrapper kann eine vom Aufrufer ausgewählte URL an GitPython `Repo.clone_from` übergeben. Aktiviert der Wrapper außerdem Gits `protocol.ext.allow=always`, kann eine `ext::`-Remote einen externen Helfer aufrufen. Prüfe die genauen sudo-Argumente, die Herkunft der URL, die Version des GitPython-Pakets und etwaige Hersteller-Patches sowie, ob der Wrapper unsichere Protokolle ausdrücklich aktiviert. GitPython ergänzte in Version 3.1.30 eine [standardmäßige Schutzmaßnahme gegen unsichere Protokolle](https://github.com/gitpython-developers/GitPython/commit/2625ed9); die Version der ausführbaren `git`-Datei ist davon unabhängig. Bei einer passiven Prüfung solltest du nur die Regel und einen begrenzten Quellcodeausschnitt lesen und den Klon nicht starten.
- Eine sudo-Berechtigung zum Wechsel zu einem anderen Benutzer für ein Repository-Klon-CLI kann einen separaten Pfad für Shell-String-Injection eröffnen. Verfolge, ob das vom Aufrufer ausgewählte Repository-Argument Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) oder einen anderen Shell-Befehlsbaustein ohne sichere Argumenttrennung erreicht; Node.js `exec` übergibt seinen Befehlsstring an eine Shell. Prüfe den genauen RunAs-Benutzer, erlaubte Unterkommandos und Argumente, den installierten Wrapper-Code und die Eingabevalidierung. Der Name eines Repository-Tools oder eine uneingeschränkte sudo-Regel beweist allein keine Command Injection. Untersuche den Wrapper, ohne bei der Bestandsaufnahme einen privilegierten Klon auszuführen.
- Ein benutzerdefinierter, root-eigener Wrapper kann sicher wirken, weil seine Binärdateien und Skripte nicht beschreibbar sind. Trotzdem kann seine Entscheidung, eine privilegierte Aktion auszuführen, von einem Flag, einem lokalen API-Wert oder einem Dienstzustand abhängen, den ein unprivilegierter Benutzer ändern kann. Verfolge jedes Entscheidungskriterium bis zu seiner Eingabe und den Autorisierungsprüfungen. Untersuche während der Bestandsaufnahme Konfiguration und Berechtigungen, ohne den Betriebszustand zu verändern; ein Aufruf von `systemd-run` im Wrapper ist nur relevant, wenn das Entscheidungskriterium beeinflussbar ist.
- Ein über sudo als root erlaubter Backup-Client kann eine vom Aufrufer ausgewählte Konfigurationsdatei akzeptieren, etwa über `npbackup-cli -c`. Prüfe den genauen RunAs-Benutzer und die erlaubten Argumente sowie, ob der Aufrufer den Konfigurationspfad, die Quellpfade des Backups und Repository- oder Lese-/Wiederherstellungsoptionen kontrolliert. Ein verschlüsseltes Repository-Geheimnis in einer lesbaren Konfiguration kann für den Client nutzbar sein; die Regel allein beweist jedoch weder den Repository-Zugriff noch die Offenlegung von root-Dateien. Prüfe die Berechtigung, ohne ein Backup auszuführen oder dessen Inhalt auszugeben.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) unterstützt `--password-command`, das ein Programm zum Abrufen des Repository-Passworts aufruft. Erlaubt eine sudo-Regel einem Benutzer mit niedrigeren Berechtigungen, Restic als root mit einem frei gewählten Passwortbefehl und einem passwortpflichtigen Unterbefehl auszuführen, kann dieser Helfer als root laufen. Prüfe die genauen sudo-Argumente und Ausschlüsse; rufe den Helfer oder einen Backup-Befehl nicht nur deshalb auf, um die Bedingung zu untersuchen.
- Eine privilegierte `restic backup`-Berechtigung kann auch eine Dateilesbarkeitsgrenze überschreiten, wenn das sudo-Argumentmuster dem Aufrufer erlaubt, sowohl die Quelle als auch ein Repository auszuwählen, das er später lesen und entschlüsseln kann. [Argument-Wildcards in sudoers können Leerraum und Schrägstriche erfassen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf); prüfe daher nachgestellte Wildcards, statt anzunehmen, dass ein festes Repository-Präfix die Quelle einschränkt. [Restic kann in lokale und entfernte Repositories sichern](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), aber ein lokales Repository kann neu geschriebene, nur für root lesbare Objekte enthalten. Prüfe die effektive sudo-Richtlinie, Backend-Zugriff, Repository-Passwort und Berechtigungen der entstehenden Objekte, bevor du von einer Offenlegung ausgehst. Ein gesicherter SSH-Schlüssel ermöglicht nur dann Zugriff, wenn das Zielkonto ihn akzeptiert. Führe bei einer passiven Prüfung kein Backup aus.
- Ein uneingeschränkter benutzerdefinierter Wartungs- oder Backup-Befehl kann einen Ausgabepfad akzeptieren oder einen eigenen Job-Scheduler anbieten. Prüfe bei einem Dateischreibpfad die genaue sudo-Regel und den RunAs-Benutzer und anschließend, ob der Aufrufer sowohl die Daten als auch das Ziel kontrolliert. Prüfe bei einem geplanten Befehl die Ausführungsidentität des Schedulers, die Befehlseingabe und jede zusätzliche Passwort- oder Autorisierungsprüfung. Der Befehlsname oder `NOPASSWD` allein beweist keinen der beiden Wege. Siehe [Schreiben in root-eigene Dateien](../interesting-files-permissions/write-to-root.md) und [cron und systemd-Timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Ein fester sudo-Befehl kann trotzdem eine vorhersehbare Konfigurationsdatei aus einem gemeinsam beschreibbaren Verzeichnis laden. Verfolge, ob der Aufrufer diese Datei ersetzen kann und ob ihre Quell- und Zielfelder einen privilegierten Abruf oder Kopiervorgang steuern. Eine URL zu einer lokalen Datei kann Daten offenlegen, die nur für das sudo-RunAs-Konto lesbar sind; eine vom Aufrufer kontrollierte Quelle in Verbindung mit einem geschützten Ziel kann einen Schreibpfad eröffnen. Prüfe den URL-Umgang des installierten Programms, die Prüfungen des Zielpfads, die effektive sudo-Regel und die Lesbarkeit der Ausgabe. Ein beschreibbarer Konfigurationspfad unter `/tmp` ist allein nur ein Prüfhinweis; untersuche Binärdatei und Dateimetadaten, ohne den privilegierten Transfer aufzurufen.
- Eine sudo-Regel für `git apply` kann dazu führen, dass das RunAs-Konto in Dateien schreibt, die durch einen vom Aufrufer kontrollierten Patch ausgewählt werden. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) ermöglichte es einem manipulierten Patch, einen Symlink zu erstellen und anschließend außerhalb des Arbeitsbaums zu schreiben, selbst wenn der Befehl `--unsafe-paths` nicht akzeptierte. Prüfe die effektive sudo-Argumentregel, die Patch-Quelle, den Zugriff des RunAs-Kontos auf das Arbeitsverzeichnis und die installierte Git-Korrektur oder einen Hersteller-Backport. Eine uneingeschränkte Regel, die `--unsafe-paths` zulässt, birgt ein separates, explizites Risiko; weder eine Git-Version noch die Berechtigung für `git apply` allein beweist, dass eine geschützte Datei geändert werden kann. Wende bei einer passiven Bestandsaufnahme keinen nicht vertrauenswürdigen Patch an.
- Eine root-fähige sudo-Regel für `clamscan --debug` kann eine Lesbarkeitsgrenze überschreiten, wenn ein Benutzer mit niedrigeren Berechtigungen ein DMG-Image bereitstellen kann und der installierte Parser von [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) betroffen ist, durch die Dateiinhalte über die Debug-Ausgabe offengelegt werden konnten. Prüfe die genau erlaubten Argumente und den Scanpfad, die Kontrolle über die Eingabe, das effektive RunAs-Konto, Engine-Patches oder Backports sowie, ob die Ausgabe für den Aufrufer sichtbar ist. Erlaubt eine weiter gefasste Regel `--file-list`/`-f`, prüfe dieses Verhalten gesondert; eine auf `--debug <scan-path>` festgelegte Richtlinie erlaubt dies nicht. Untersuche Richtlinien und Paketmetadaten, ohne bei der Bestandsaufnahme eine manipulierte Datei zu scannen oder geschützte Ausgaben anzuzeigen.
- Eine root-fähige sudo-Regel, die ein vom Aufrufer ausgewähltes verschlüsseltes Datenträgerabbild öffnet, und eine zweite Regel, die das daraus entstandene Mapper-Gerät einbindet, können vom Aufrufer kontrollierte Dateien in den Mount-Namespace des Hosts einbringen. Prüfe beide effektiven Regeln und Argumente, die Kontrolle über das Image und den Mapper-Namen, das tatsächliche Einhängeziel sowie Eigentümer und Modus der resultierenden Datei. Ein Wechsel über Set-User-ID erfordert zusätzlich eine zugängliche ausführbare Datei, Einhängeoptionen, die SetUID berücksichtigen (`nosuid` verhindert dies), sowie die geltenden Prozess- oder MAC-Richtlinien; das Öffnen oder Einhängen eines Images allein ist nur ein Prüfhinweis. Ein separater Weg über ein vorhandenes Backup setzt voraus, dass der tatsächliche Schlüssel vorliegt und sich darin ein nützliches lesbares Geheimnis befindet. Untersuche Richtlinien und Pfade, ohne bei einer passiven Bestandsaufnahme ein Image zu öffnen oder einzubinden. Siehe das [cryptsetup-Handbuch](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) und die [mount-Optionen](https://man7.org/linux/man-pages/man8/mount.8.html).
- Eine root-fähige sudo-Regel für ein Shell- oder Python-Skript verdient eine Prüfung des Arbeitsverzeichnisses, wenn das Skript `./helper` aufruft, ohne zuvor in ein festgelegtes Verzeichnis zu wechseln. Eine Python-Liste wie `['./helper']`, die an `subprocess.run` übergeben wird, kann dasselbe Verhalten bezüglich des vom Aufrufer ausgewählten Arbeitsverzeichnisses haben. Der Aufrufer kann möglicherweise ein beschreibbares Verzeichnis auswählen und darin eine ausführbare Datei mit diesem relativen Namen ablegen; ein absoluter Pfad an anderer Stelle im Skript schützt diesen Aufruf nicht. Prüfe die effektive Regel, `runchdir` oder andere Richtlinien zum Verzeichniswechsel, Skriptablauf und Erreichbarkeit des Zweigs, ein beschreibbares und ausführbares Verzeichnis sowie Mount- und `NOEXEC`-Einschränkungen, bevor du dies als Codeausführung einstufst. Ist das Skript nicht lesbar, bleibt das Verhalten unbekannt, bis sein Quellcode auf einem autorisierten Weg geprüft wurde. Untersuche Skripte statisch, statt den Helfer auszuführen. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) beschreibt Richtlinien für das Arbeitsverzeichnis.
- Ein fester, root-fähiger Python-Validator kann trotzdem eine vom Aufrufer ausgewählte Datendatei auswerten. [Pythons Dokumentation zu `eval()` warnt vor nicht vertrauenswürdigen Eingaben](https://docs.python.org/3/library/functions.html#eval): Eine Prüfung des Eingabesuffixes, ein arithmetisches Präfix oder ein Validierungszweig bildet keine Sandbox, wenn der verbleibende Ausdruck `eval` erreicht. Prüfe die effektive sudo-Regel, ob der Aufrufer die konkrete Datei auswählen und kontrollieren kann, die Bedingungen des Parserzweigs und den Aufbau des Ausdrucks sowie die Identität des privilegierten Prozesses, bevor du dies als Ausführungspfad einstufst. Das Vorkommen von `eval` in einem lesbaren Skript ist allein nur ein Prüfhinweis; untersuche Quellcode und Dateiberechtigungen, ohne den Validator auszuführen oder bei der Bestandsaufnahme einen Testausdruck einzuspeisen.
- Ein root-fähiger sudo-Ruby-Wrapper, der einen relativen YAML-Dateinamen wie `YAML.load(File.read("dependencies.yml"))` liest, kann Eingaben aus dem Arbeitsverzeichnis des Aufrufers beziehen, sofern weder der Wrapper noch die sudo-Richtlinie dieses Verzeichnis festlegen. Prüfe die genau erlaubten Argumente, Verzeichnis- und Dateiberechtigungen sowie das Verhalten der installierten Psych-Version: Ältere Implementierungen von `YAML.load` konnten beliebige Ruby-Objekte deserialisieren, während neuere Versionen Klassen standardmäßig einschränken. Ein statischer Aufruf ist nur ein Prüfhinweis; bestätige, dass die Datei tatsächlich aus einem für den Aufrufer beschreibbaren Verzeichnis stammt und dass der installierte Loader gefährliche Klassen akzeptiert. Verwende für nicht vertrauenswürdige Eingaben vorzugsweise `safe_load` mit einer ausdrücklich festgelegten, minimalen Klassen-Allowlist. Siehe die [Ruby-3.0-Psych-Dokumentation](https://docs.ruby-lang.org/en/3.0/Psych.html) und die [Ruby-3.1-Psych-Dokumentation](https://ruby-doc.org/core-3.1.2/Psych.html).

- Eine exakte, root-fähige Berechtigung für `sudo go run /absolute/file.go` verdient eine Prüfung des Arbeitsverzeichnisses, wenn der Go-Quellcode eine relative WASM-Datei liest und nach der Auswertung möglicherweise ein relatives Shell-Skript ausführt. Prüfe den effektiven RunAs-Benutzer, Befehlsargumente und Verweigerungen, ein für den Aufrufer beschreibbares aktuelles Verzeichnis, den Datenfluss von WASM zum Zweig und ob dieser Zweig den Helfer aufruft. Ein festes sudo-`runchdir`, `os.Chdir` oder [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) kann den Suchort ändern. Ein statisches gemeinsames Auftreten ist nur ein möglicher Hinweis; untersuche den Quellcode, ohne Go, WASM oder den Helfer auszuführen.
- `sudoedit` und Argument-Wildcards erfordern genaue Prüfungen der Version und Regel; die [Checkliste](linux-privilege-escalation-checklist.md) behandelt das Bearbeiten von Dateien über sudoedit. Prüfe bei einer `sudoedit`-Berechtigung zum Wechsel zu einem anderen Benutzer mit Wildcard-Pfad die effektive Einstellung `sudoedit_follow` oder `FOLLOW`, `sudoedit_checkdir`, das aufgelöste Ziel und wer jeden übergeordneten Verzeichniseintrag ersetzen kann. Erstere kann das Folgen eines Symlinks erlauben; eine Deaktivierung der letzteren entfernt Prüfungen auf beschreibbare Verzeichnisse. Keine der beiden Einstellungen allein weist jedoch das Schreiben in die Datei eines anderen Benutzers nach. Prüfe die installierte sudo-Richtlinie und die exakt zutreffenden Argumente, bevor du diesen Schluss ziehst. Siehe die [sudoers-Optionsdefinitionen](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In einer sudoers-Befehlsregel kann eine Argument-Wildcard neben Pfadzeichen auch Leerraum erfassen. Eine Regel für einen lesefähigen Befehl mit einem Argument wie `/restricted/*` kann daher ein zusätzliches Dateiargument nach einem passenden Präfix zulassen. Prüfe den genauen RunAs-Benutzer, Befehlspfad, das Argumentmuster und spätere Verweigerungen; nachgewiesenes Lesen einer Datei bedeutet nicht automatisch Befehlsausführung. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unterscheidet Argument-Globs von Befehls-Pfad-Globs.
- Ein pfadähnliches Argument-Glob kann auch `../` erfassen. Eine root-fähige Regel wie `node /opt/scripts/*.js` kann beispielsweise eine vom Aufrufer kontrollierte JavaScript-Datei außerhalb von `/opt/scripts` erlauben, wenn der angegebene Pfad weiterhin mit `/opt/scripts/` beginnt und über Verzeichnis-übergeordnete Segmente aufgelöst wird. Dies ist ein **Argument**-Glob; für das Befehls-Pfad-Glob der Node.js-Executable gelten andere Regeln für Schrägstriche. Prüfe die effektive Regel, spätere Verweigerungen, die Pfadauflösung, die Kontrolle über die Zieldatei sowie Einschränkungen durch sudoers-Regexes oder Digests, bevor du auf Codeausführung schließt. Siehe die [sudoers-Wildcard-Regeln](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) und die [Node.js-Befehlszeilendokumentation](https://nodejs.org/api/cli.html).
- Archivierungsprogramme und andere Dienstprogramme können Ausführungshooks haben. Vergleiche die genau erlaubten Argumente mit [GTFOBins](https://gtfobins.github.io/), statt anzunehmen, dass nur Shells oder Interpreter Befehle ausführen.
- Eine uneingeschränkte, root-fähige `qpdf`-Regel kann eine privilegierte Datei über PDF-Anhänge offenlegen: qpdf 10.2 und neuere Versionen unterstützen `--empty` und `--add-attachment file ... --` mit einer Ausgabe-PDF. Kann der privilegierte Prozess die ausgewählte Quelle lesen und die PDF in einen für den Aufrufer zugänglichen Pfad schreiben, kann diese Ausgabe die Quelldaten enthalten. Prüfe die effektiven sudo-Argumente und Ausschlüsse, die qpdf-Version, den Zugriff auf die Quelle und den Ausgabepfad, bevor du auf eine mögliche Offenlegung schließt. Das Lesen eines root-SSH-Schlüssels ermöglicht eine Anmeldung nur, wenn der Schlüssel gültig ist und SSH-Authentifizierung für root erlaubt ist. Siehe die [Optionen für qpdf-Anhänge](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Die Wiederverwendung eines sudo-Zeitstempels hängt von der Cache-Richtlinie, dem besitzenden Benutzer, Terminal/Sitzung und den Berechtigungen ab. Der [Leitfaden zur Rechteausweitung](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) behandelt die nötigen Prüfungen.
- `doas` hat eigene Regeln und Konfigurationen. Prüfe erlaubte Befehle und beschreibbare Konfigurationspfade wie im [doas-Abschnitt](../linux-basics/linux-privilege-escalation/README.md#doas) beschrieben.

### Über sudo ausgeführte Build- und Paketwerkzeuge

Eine uneingeschränkte sudo-Berechtigung für Foundrys `forge` kann relevant sein, selbst wenn die RunAs-Identität ein anderer Nicht-root-Benutzer ist. Compileroptionen wie `--use` können eine lokale ausführbare Datei auswählen; `forge flatten -o` legt eine Ausgabedatei fest. Prüfe die installierte Forge-Version, die genauen sudo-Argumente, zugängliche Projekt- und Compilerpfade, Ausgabeberechtigungen und die effektive Umgebung, bevor du die Berechtigung als ausnutzbar einstufst. Ein relativer Helfer, der über `PATH` gefunden wird, ist ein von Version und Umgebung abhängiger Weg, keine Eigenschaft, die für jeden Forge-Build angenommen werden sollte.<sup>[[23]](#references)[[24]](#references)</sup>

Eine uneingeschränkte, root-fähige `pacman`-Berechtigung erlaubt mehr als Paketabfragen: `-U` akzeptiert ein lokales Paket, Pakete können Installationsskripte enthalten und `--hookdir` wählt ein anderes Hook-Verzeichnis. Prüfe vor Tests die effektive sudo-Regel, Argumentbeschränkungen und Ausschlüsse; eine passive Bestandsaufnahme erfordert weder eine Paketinstallation noch das Ausführen eines Hooks.<sup>[[25]](#references)[[26]](#references)</sup>

Ein fester sudo-Shell-Wrapper kann auch eine benannte npm-Abhängigkeit installieren und anschließend eine Node.js-Anwendung starten. Prüfe die genaue RunAs-Regel, ob das Paket bereits installiert ist, das effektive `HOME` und `userconfig` von npm, Projektkonfiguration oder Befehlszeilenüberschreibungen sowie, ob ein Benutzer mit niedrigeren Berechtigungen die Registry oder das für diesen Namen zurückgegebene Paket kontrolliert. [npm dokumentiert die Suche nach `.npmrc` pro Benutzer und Projekt](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); das Verhalten von `HOME` bei sudo hängt von der installierten Richtlinie und Distribution ab. Daher wird die `.npmrc` eines beschreibbaren Benutzers möglicherweise vom privilegierten npm-Prozess gelesen, möglicherweise aber auch nicht. Wird das neu installierte Paket von der privilegierten Anwendung importiert, kann dessen Modulcode unter der Identität der Anwendung ausgeführt werden. Installationsskripte bilden einen separaten, von Version und Konfiguration abhängigen Pfad; [npm dokumentiert deren Lebenszyklus und Benutzerbehandlung](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ein `.npmrc`-Pfad oder eine `npm install`-Zeile ist allein nur ein Prüfhinweis. Untersuche Regel, kurzen Wrapper, Konfigurationspfade und Paketherkunft, ohne das Paket zu installieren oder die Anwendung während einer passiven Bestandsaufnahme zu starten.

Eine root-fähige Berechtigung für `pip` oder `pip3 download` ist ebenfalls ein Hinweis auf einen möglichen Paket-Build, wenn die Argumente dem Aufrufer die Auswahl einer nicht vertrauenswürdigen Source Distribution erlauben – selbst wenn das URL-Muster sie auf einen lokalen Dienst und die Endung `.tar.gz` beschränkt. `pip download` akzeptiert Archiv-URLs und löst Paketmetadaten auf; beim Vorbereiten einer sdist können deren Build-Backend oder Legacy-`setup.py`-Code ausgeführt werden, bevor das Archiv lediglich gespeichert wird. Prüfe die genauen sudo-RunAs- und Argumentregeln, ob der Aufrufer das ausgewählte Archiv veröffentlichen oder ersetzen kann und ob diese pip-Version dessen Metadaten tatsächlich vorbereitet. Ein festgelegtes, vertrauenswürdiges Archiv oder Wheel weist diesen Pfad nicht nach. Rufe während einer passiven Bestandsaufnahme kein nicht vertrauenswürdiges Paket ab und baue es auch nicht. Siehe den [download-Befehl von pip](https://pip.pypa.io/en/stable/cli/pip_download/), die [Build-System-Schnittstelle](https://pip.pypa.io/en/stable/reference/build-system/) und die [Hinweise zur sicheren Installation](https://pip.pypa.io/en/stable/topics/secure-installs/).

Eine sudo-Regel, die `pip install` mit einem vom Aufrufer ausgewählten lokalen Projektpfad erlaubt, bildet eine direktere Build-Vertrauensgrenze. [pip akzeptiert lokale Projektverzeichnisse](https://pip.pypa.io/en/stable/topics/local-project-installs/) und ruft deren Build-System auf; das [Build-Backend führt vom Projekt kontrollierte Build-Hooks aus](https://pip.pypa.io/en/stable/reference/build-system/). Prüfe die effektive RunAs-Identität, genaue Argumentbeschränkungen und Verweigerungen, die Kontrolle über das ausgewählte Projekt sowie das Verhalten der installierten pip-/Backend-Version, bevor du die Regel als privilegierte Codeausführung einstufst. Ein festgelegtes, vertrauenswürdiges Projekt oder eine Regel, die vom Aufrufer ausgewählte Pfade ausschließt, weist diesen Weg nicht nach. Prüfe die Regel und Projektmetadaten, ohne bei einer passiven Bestandsaufnahme ein Paket zu installieren.

Eine uneingeschränkte, root-fähige Berechtigung für `easy_install` ist ein verwandter Hinweis auf einen veralteten Paket-Build. [Setuptools dokumentiert](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), dass Easy Install ein lokales Projektverzeichnis akzeptiert und Source Distributions baut; bei einem vom Aufrufer kontrollierten Projekt kann während dieses Builds `setup.py` unter der sudo-Identität ausgeführt werden. Prüfe das effektive RunAs-Konto, den genauen Befehl und die Argumentbeschränkungen (einschließlich späterer Verweigerungen), die Kontrolle über das ausgewählte Projekt und das Verhalten des installierten Werkzeugs. Ein festgelegtes, vertrauenswürdiges Projekt oder eine Richtlinie, die keine vom Aufrufer ausgewählte Quelle erlaubt, weist diesen Pfad nicht nach. Untersuche die Regel und Projektmetadaten, ohne während der Bestandsaufnahme ein Paket zu installieren.

Ein über sudo erlaubter Python-Wrapper, der `setuptools.package_index.PackageIndex.download` mit einer vom Aufrufer ausgewählten URL verwendet, ist ein anderer Prüfungsfall als `pip download`: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) beschreibt, wie ein aus einer URL abgeleiteter Dateiname in betroffenen Versionen vor 78.1.1 aus dem vorgesehenen Download-Verzeichnis entkommen und mit den Berechtigungen des Prozesses schreiben konnte. Prüfe die effektive sudo-RunAs- und Argumentregel, ob der Wrapper die URL des Aufrufers an genau diese API übergibt, den installierten Build oder Hersteller-Backport und den endgültigen Pfad des Ergebnisses. Eine Versionszeichenfolge oder ein beschreibbares Download-Verzeichnis allein weist keinen beliebigen Schreibzugriff nach. Prüfe den kurzen Wrapper und Paketmetadaten, ohne die URL abzurufen oder während der Bestandsaufnahme eine Datei zu schreiben.

Ein über sudo erlaubter Build-Wrapper, der eine vom Aufrufer ausgewählte `.spec`-Datei an PyInstaller übergibt, erfordert dieselbe Prüfung der Vertrauensgrenze. Eine PyInstaller-Spec-Datei ist ausführbares Python, das während des **Builds** ausgewertet wird; ihre `datas`-Einträge können für die Build-Identität lesbare Dateien in ein Artefakt aufnehmen. Prüfe den genauen RunAs-Benutzer, sudo-Argument- und Verweigerungsregeln, Pfad- und Zweigbehandlung des Wrappers, die Kontrolle über die ausgewählte Spec-Datei und den Zugriff auf das resultierende Artefakt. Die Erlaubnis einer `.py`-Eingabe oder eine installierte PyInstaller-Version beweist weder die Kontrolle über eine Spec-Datei noch privilegierte Ausführung. Bei einer passiven Prüfung sollten nur ein begrenzter Wrapper-Dateiinhalt und Metadaten gelesen werden; ein Build sollte nicht ausgeführt werden. Siehe die [PyInstaller-Dokumentation zu Spec-Dateien](https://pyinstaller.org/en/stable/spec-files.html).

### Über sudo ausgeführte Preset- und Plugin-Lader

Python-Werkzeuge, die ein vom Aufrufer ausgewähltes Preset oder Plugin-Verzeichnis akzeptieren, können Code mit den durch sudo gewährten Berechtigungen importieren. BBOT akzeptiert beispielsweise ein Preset über `-p`; die [Dokumentation zu benutzerdefinierten Modulen](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) beschreibt `module_dirs`-Einträge, mit denen zusätzliche Python-Modulverzeichnisse ausgewählt werden. Erlaubt die effektive sudo-Regel ein vom Aufrufer ausgewähltes Preset und kontrolliert der Aufrufer ein Modul im ausgewählten Verzeichnis, kann der Import Code als privilegierter Benutzer ausführen – möglicherweise bevor das Werkzeug ein ungültiges Modul zurückweist. Prüfe die installierte Version, die genauen sudo-RunAs- und Argumentregeln sowie die Eigentümerschaft der Preset- und Modulpfade, ohne das Modul bei der Bestandsaufnahme zu laden.

### Über sudo ausgeführtes Backdrop-CLI

[Bee](https://github.com/backdrop-contrib/bee) ist ein PHP-CLI-Werkzeug für Backdrop CMS. Die Befehle `eval` (`php-eval`) und `php-script` können vom Aufrufer bereitgestelltes PHP ausführen. Eine sudo-Regel, die das Bee-Programm als root mit uneingeschränkten Argumenten erlaubt, kann daher Root-Codeausführung ermöglichen, wenn Bee eine Backdrop-Installation initialisieren kann. Führe es aus dem Site-Verzeichnis aus oder wähle mit der globalen Option `--root=<directory>` eine Site aus; Bee oder eine Backdrop-`settings.php`-Datei zu finden, beweist weder die sudo-Berechtigung noch eine nutzbare Site oder eine erfolgreiche Initialisierung. Prüfe vor Tests die effektive sudo-Regel, etwaige Befehlsausschlüsse, die Identität der ausführbaren Datei und den Zugriff auf die Site. Bei einer passiven Bestandsaufnahme solltest du Regel und Dateipfade untersuchen, ohne Bee aufzurufen. Siehe das [Changelog der Bee-Befehle](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) zu den Ergänzungen der PHP-Befehle.

### Über sudo ausgeführte Terminalserver

`mosh-server` startet einen interaktiven Terminalserver als aufrufender Benutzer. Er wählt einen hohen UDP-Port und einen Sitzungsschlüssel, meldet beide dem Aufrufer und startet normalerweise beim Verbinden eines Clients die Login-Shell dieses Benutzers. Eine uneingeschränkte, root-fähige sudo-Berechtigung für `mosh-server` ist daher ein Kandidat für eine Shell-Prüfung, obwohl sich der Serverbefehl selbst vom Terminal löst. Prüfe die effektive RunAs-Identität, erlaubte Argumente und Ausschlüsse, die installierte Binärdatei, die Shell, die Verfügbarkeit eines Clients und den UDP-Zugriff. Eine passive Bestandsaufnahme sollte die sudo-Regel prüfen, ohne einen Server zu starten oder einen aktiven Sitzungsschlüssel auszugeben. Siehe das [Mosh-Server-Handbuch](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) und die [Designhinweise des Upstream-Projekts](https://github.com/mobile-shell/mosh#how-it-works).

### Privilegierte Backup-Wrapper, die eine Taskdatei des Aufrufers umschreiben

Ein als root ausgeführter Shell-Wrapper kann eine vom Aufrufer ausgewählte Taskdatei akzeptieren, `../` aus Quellpfaden entfernen, prüfen, ob jedes Ergebnis mit einem erlaubten Verzeichnis beginnt, die Taskdatei umschreiben und anschließend deren *Pfadnamen* an ein Backup-Programm übergeben. Prüfe den transformierten Pfad nach vollständiger kanonischer Auflösung: Ein einzelner String-Ersetzungsschritt kann eine neue Traversal-Sequenz offenlegen, die eine lexikalische Präfixprüfung akzeptiert. Prüfe außerdem, ob das Backup-Programm die transformierten Daten aus dem Speicher verwendet oder die Datei erneut öffnet. Wird die Datei erneut geöffnet, kann eine fehlgeschlagene Umschreibung die ursprüngliche Eingabe zurücklassen.

Unter Linux kann `fs.protected_regular` einen `O_CREAT`-Schreibzugriff auf eine reguläre Datei eines anderen Benutzers in einem weltweit beschreibbaren Sticky-Verzeichnis verhindern. Diese Schutzmaßnahme ist hilfreich; ein Shell-Wrapper, der den Schreibfehler ignoriert, kann jedoch mit der ursprünglichen Taskdatei fortfahren. Prüfe die Einstellung, den Eigentümer der Datei und des Verzeichnisses sowie, ob der Wrapper bei einem Fehler abbricht. Der Pfad ist nur dann ein Kandidat für die Offenlegung von Dateien, wenn die effektive sudo-Regel den Wrapper als privilegierten Benutzer erlaubt, der Aufrufer die Taskeingabe und ein lesbares Backup-Ziel kontrolliert und das Backup-Werkzeug geschützte Quellen tatsächlich einbezieht. Untersuche diese Bedingungen, ohne während der Bestandsaufnahme ein Backup auszuführen.

### Argument-Wildcards bei privilegierten Paketwerkzeugen

In einer sudo-Regel für `tcpdump` kann ein `*` im **Argumentmuster** Leerraum und Schrägstriche erfassen. Eine scheinbare Einschränkung auf einen Pfad kann daher zusätzlichen Optionstext zulassen. Das unterscheidet sich von einer Wildcard im Pfad der ausführbaren Datei des Befehls; untersuche die vollständige RunAs-Regel und etwaige spätere Verweigerungen. Können Optionen eingeschleust werden, bestimmen der erlaubte Aufruf und die Semantik der installierten [`tcpdump`-Optionen](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), ob `-F`, `-V`, `-r`, `-w` oder `-Z` eine nützliche Lese-/Schreibprimitive ermöglicht. `-V` liest eine Liste von Capture-Dateinamen, nicht eine beliebige allgemeine Datei. AppArmor oder eine andere MAC-Richtlinie kann den Dateizugriff auch dann verhindern, wenn sudo den Befehl erlaubt; eine Profildatei auf dem Datenträger beweist nicht, dass sie geladen ist oder durchgesetzt wird. Prüfe Autorisierung und Richtlinien passiv, bevor du einen Schluss ziehst. Das [sudoers-Handbuch](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) beschreibt den Unterschied bei Wildcards.

Eine root-fähige sudo-Regel, die nur die ausführbare Datei `tcpdump` nennt und keine Argumente einschränkt, verdient ebenfalls eine Prüfung. Im [tcpdump-Handbuch](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) steht, dass `-z` einen Befehl nach dem Rotieren ausführt, wenn `-C` oder `-G` ein gespeichertes Capture rotiert; `-Z` oder eine Build-Standardeinstellung können die Berechtigungen ablegen, bevor dieser Befehl läuft. Prüfe die effektive sudo-Regel, den installierten Build, das Verhalten beim Ablegen der Berechtigungen und ob eine Rotation stattfinden kann, bevor du die Regel als Rechteausweitungspfad einstufst. Eine hervorgehobene Regel ist ein Kandidat, kein Nachweis für die Ausführung eines Root-Befehls.

### Über sudo ausgeführte Nmap-Wrapper

Wenn ein über sudo erlaubter `nmap`-Pfad ein Shell-Wrapper ist, prüfe den exakt erlaubten Pfad und jede weitergereichte Option. Das Blockieren der bekannten Schreibweise `--script` verhindert das Laden von NSE-Code nicht zwangsläufig: Nmaps [`--datadir`](https://nmap.org/book/man-misc-options.html) wählt Datendateien aus; NSE [lädt `nse_main.lua`](https://nmap.org/book/nse-implementation.html) aus dem ausgewählten Datenverzeichnis, wenn Scripting aktiviert ist. Einige installierte Builds akzeptieren außerdem alternative Langoptionschreibweisen; vergleiche die Einschränkungen daher mit dem tatsächlichen Parser dieser Binärdatei. [`--excludefile`](https://nmap.org/book/man-target-specification.html) bietet eine separate Angriffsfläche zum Lesen von Dateien; Parserfehler können Text offenlegen. Prüfe die effektive sudo-Regel, die Wrapper-Logik, die Nmap-Version, die Kontrolle über das Verzeichnis und die MAC-Richtlinie, ohne während der Bestandsaufnahme Scans auszuführen.

### Über sudo ausgeführte Mercurial-Pull-Hooks

Auch bei einer festen Quelle in `sudo hg pull /fixed/source` wird das **empfangende** Repository durch das aktuelle Arbeitsverzeichnis bestimmt, sofern der Befehl es nicht mit `-R` festlegt. Ein vom Aufrufer kontrolliertes empfangendes Repository kann Hooks in `.hg/hgrc` definieren; ein Hook kann als sudo-RunAs-Benutzer ausgeführt werden. [Mercurial ignoriert Repository-Konfigurationen, die einem nicht vertrauenswürdigen Benutzer oder einer nicht vertrauenswürdigen Gruppe gehören](https://mercurial-scm.org/help/topics/config). Prüfe daher die vertrauenswürdigen Benutzer/Gruppen des RunAs-Kontos und das genaue Arbeitsverzeichnis, bevor du dies als Codeausführung einstufst. Für eine passive Prüfung genügt es, Richtlinie und Konfiguration zu lesen; führe keinen Pull aus und rufe keinen Hook auf.

### Über sudo ausgeführte Git-Pull-Hooks

Prüfe bei einer exakten, root-fähigen Berechtigung für `sudo git pull` auch das **empfangende** Repository, das durch das Arbeitsverzeichnis ausgewählt wird. Ein Repository im Besitz des Aufrufers kann einen ausführbaren `post-merge`-Hook enthalten, der mit der Identität des Git-Prozesses ausgeführt wird, wenn ein Pull tatsächlich erfolgreich einen Merge durchführt; [Git dokumentiert diesen Hook](https://git-scm.com/docs/githooks) sowie [das Merge- und Rebase-Verhalten von pull](https://git-scm.com/docs/git-pull). Prüfe die effektive sudo-Regel und das aktuelle Arbeitsverzeichnis, den aktiven Hook-Pfad und seine Berechtigungen sowie, ob ein Merge mit neuen Commits möglich ist. Ein fehlgeschlagener, wirkungsloser oder ausschließlich Rebase durchführender Pull weist diesen Hook-Pfad nicht nach. Untersuche Richtlinien und Repository-Metadaten, ohne den privilegierten Pull auszuführen.

### Über sudo ausgeführte rsync-Archivkopien

Bei `sudo rsync -a ... /writable/source/* /fixed/destination/` kann ein `*` im **sudoers-Argumentmuster** Leerraum erfassen und eine zusätzliche Option zwischen Quelle und Ziel zulassen. Das unterscheidet sich von der Shell-Erweiterung von Dateinamen. Kann der Aufrufer die Quelle befüllen und ist das Ziel für den privilegierten rsync-Prozess beschreibbar, kann [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privilegierten Besitz anfordern, während der Archivmodus Berechtigungsbits erhält. So könnte eine SetUID-Datei erstellt werden, deren Eigentümer privilegiert ist. Prüfe die genauen [sudoers-Wildcard-Semantiken](https://man7.org/linux/man-pages/man5/sudoers.5.html), die rsync-Version, spätere Verweigerungen, das Dateisystem-Flag `nosuid` und die MAC-Richtlinie. Eine passende Regel ist ein Prüfhinweis, kein Nachweis einer erfolgreichen Rechteausweitung.

### Über sudo ausgeführter Export von Paketfilterregeln

Eine uneingeschränkte, root-fähige Berechtigung für `iptables` und `iptables-save` (oder das entsprechende Paar `ip6tables`) verdient eine Prüfung auf Dateischreibzugriff. Der `comment`-Match akzeptiert Text für Regeln, den der Aufrufer vorgibt; `iptables-save -f` schreibt den serialisierten Regelsatz in einen ausgewählten Pfad.<sup>[[20]](#references)[[21]](#references)</sup> Eine nützliche Payload hängt davon ab, wie das installierte Backend Kommentare serialisiert und ob die Zieldatei im Export weitere Zeilen akzeptiert; `iptables-save` allein bietet keinen beliebigen, frei wählbaren Inhalt. Prüfe die genaue sudo-RunAs-Identität, Argumente und Ausschlüsse, verfügbare Match-Erweiterungen, das Backend und die Berechtigungen des Ziels. Untersuche bei der Bestandsaufnahme die Berechtigung, ohne Firewall-Regeln zu ändern oder eine Datei zu schreiben.

### Privilegiertes Protokollverzeichnis von Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) betraf Below-Versionen vor 0.9.0, die ein weltweit beschreibbares Verzeichnis `/var/log/below` anlegten. Wenn ein Dienst oder ein erlaubter sudo-Befehl einen betroffenen Build als root ausführt, kann ein Benutzer, der in das nicht mit Sticky-Bit geschützte Protokollverzeichnis schreiben und es durchsuchen kann, möglicherweise einen Protokolleintrag durch einen Symlink ersetzen, bevor der privilegierte Prozess ihn öffnet. Prüfe den Patchstatus des installierten Pakets, den genauen privilegierten Ausführungspfad, den effektiven Verzeichniszugriff, Sticky-Bit und ACLs sowie die Metadaten von `/var/log/below/error_root.log`. Ein weltweit beschreibbarer Pfad oder eine sudo-Regel allein weist die gesamte Kette nicht nach. Ein Sticky-Verzeichnis oder Hersteller-Backport ändert die Bewertung. Eine passive Bestandsaufnahme sollte nur Metadaten untersuchen; sie muss weder einen Link erstellen noch das privilegierte Programm ausführen.

### Privilegierte Sammlung eines Support-Bundles aus beschreibbaren Eingaben

Ein über sudo erlaubtes Support-Profilskript kann feste Protokollpfade als root lesen und deren Inhalt in ein Profilarchiv kopieren. Prüfe das Skript auf tatsächliche Lesezugriffe und anschließend, ob der Aufrufer einen Quellpfad oder einen übergeordneten Verzeichniseintrag durch einen Symlink ersetzen kann. Folgt der privilegierte Lesezugriff diesem Link und ist das resultierende Archiv für den Aufrufer lesbar, kann eine geschützte Datei offengelegt werden. Die sudo-Berechtigung, ein beschreibbarer Quellpfad, der privilegierte Lesezugriff und eine lesbare Ausgabe müssen alle gegeben sein; ein beschreibbares Protokoll oder ein Profil-Dateiname allein genügt nicht. Untersuche effektive Berechtigungen und Link-Metadaten, ohne Dateien zu ersetzen oder bei der Bestandsaufnahme ein Profil zu erzeugen. Die [Support-Hinweise zu Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) dokumentieren dessen als root ausgeführtes Profils, das ein Ausgabe-Archiv erstellt, und verdeutlichen, warum Eingaben und Ausgabe solcher Bundles eingeschränkt werden müssen.

### Als root ausgeführte Python-Skripte zur Archivwiederherstellung

Auch eine eng begrenzte sudo-Regel für ein Python-Wiederherstellungsskript erfordert eine Prüfung seiner Archiveingabe. Kann der Aufrufer das Archiv auswählen oder ersetzen und extrahiert das Skript es als root mit `tarfile.extractall(filter="data")`, prüfe die Sicherheitsupdates des Interpreters, bevor du dem Filter vertraust. CPython behob mehrere Umgehungen des Symlink- und Hardlink-Filters, darunter CVE-2025-4517, in den Versionen 3.9.23, 3.10.18, 3.11.13, 3.12.11 und 3.13.4. Distributions-Backports können auch frühere Versionen korrigieren; die angezeigte Interpreterversion allein beweist daher keine Betroffenheit.<sup>[[16]](#references)[[17]](#references)</sup>

Lies bei einer passiven Prüfung den genauen sudo-Befehl und das Skript, verfolge, welches Argument das Archiv auswählt, und prüfe, ob der aktuelle Benutzer das Archiv oder dessen übergeordnetes Verzeichnis beschreiben kann. Prüfe den installierten Hersteller-Patch und das Extraktionsziel gesondert; `filter="data"` macht nicht jedes nicht vertrauenswürdige Archiv sicher.<sup>[[16]](#references)[[17]](#references)</sup>

### Über sudo ausgeführte Loader für Machine-Learning-Modelle

Eine sudo-Regel, die eine vom Aufrufer ausgewählte `.pt`-, `.pth`- oder `.ckpt`-Datei erlaubt, verdient eine Prüfung, wenn ein privilegiertes Skript diese Datei an [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` oder einen anderen Pickle-basierten Loader übergibt. Prüfe die effektive RunAs-Regel, ob der Aufrufer das ausgewählte Modell erstellen oder ersetzen kann und den tatsächlichen Argumentfluss durch Shell-Wrapper zum Python-Helfer. Die Endung `.pth` bezeichnet auch nicht verwandte Python-Site-Konfigurationsdateien und ist allein kein Beleg dafür, dass ein Modell geladen wird. Ein Archiv-Scan oder statischer Pickle-Scan beweist nicht, dass das spätere Laden sicher ist; prüfe das [versionsabhängige Verhalten von `weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) und etwaige Allowlists. Siehe die Hinweise zu [ML-Pickle und Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Lade oder entpacke das Modell bei einer passiven Bestandsaufnahme niemals.

### Über sudo ausgeführte Ausdrucksauswertung gespeicherter Eingaben

Ein festes Python-Skript, das über sudo als root ausgeführt wird, kann trotzdem Text auswerten, den ein Benutzer mit niedrigeren Berechtigungen in einer Anwendungsdatenbank speichern kann. In TensorFlow wählt ein Aufruf von `preprocess_input_exprs_arg_string(value, safe=False)` einen `eval`-Pfad; der [Hinweis von TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) beschreibt den unsicheren Parser und eine Korrektur für dessen Befehlszeilenaufrufer. Ein expliziter Aufruf einer Anwendung mit `safe=False` muss gesondert geprüft werden, selbst wenn dieser Befehlszeilenaufrufer gepatcht ist. Prüfe die effektive sudo-Regel, wer den genauen Eingabedatensatz ändern kann, ob Filterung oder Bewertung diesen Datensatz zum Aufruf gelangen lässt und wie sich die installierte Funktion verhält. Eine TensorFlow-Version, eine sudo-Berechtigung oder eine fest codierte Modelldatei allein beweist die Kette nicht. Untersuche Skript und Datenfluss passiv; führe den privilegierten Helfer nicht aus und übermittle bei der Bestandsaufnahme keine Testausdrücke.

### Über sudo erlaubte Konfiguration von needrestart

`needrestart -c` lädt eine vom Aufrufer ausgewählte Perl-Konfigurationsdatei und wertet deren Inhalt aus. Erlaubt `sudo -l` `needrestart` als root mit Argumenten, die `-c` zulassen, und kann der Aufrufer eine lesbare Konfigurationsdatei an einem beschreibbaren Ort auswählen, kann diese Berechtigung zu Root-Codeausführung führen. Prüfe die genauen sudo-RunAs- und Argumentregeln; eine Regel, die nur eine feste Argumentliste erlaubt, kann diesen Pfad blockieren. Dies ist von den Schwachstellen beim Scannen von Interpretern durch needrestart getrennt: Ein Paket-Update oder das Deaktivieren von `interpscan` macht eine uneingeschränkte Root-`-c`-Berechtigung nicht sicher.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Über sudo ausgeführte Python-Imports unter einem anderen Konto

Ein fester Python-Einstiegspunkt kann weiterhin ein Modul importieren, das der Aufrufer bearbeiten oder ersetzen kann – auch wenn sudo das Skript als **Nicht-root-Dienstbenutzer** ausführt. Prüfe bei einem literalen `from utils import status` sowohl `utils/__init__.py` und `utils/status.py` vor Ort als auch die Berechtigungen des Paketverzeichnisses. Prüfe den Importpfad des Skripts, die genau erlaubten sudo-Argumente und ob die betreffende Aktion diesen Import erreicht, bevor du die beschreibbare Datei als Ausführungspfad einstufst. Untersuche Dateien und Berechtigungen, ohne das Skript bei der Bestandsaufnahme zu importieren oder auszuführen.<sup>[[2]](#references)[[3]](#references)</sup>

Eine exakte sudo-Regel für `python3 /absolute/script.py` erfordert lediglich, dass das Skript lesbar ist; die Datei muss weder ausführbar sein noch einen Shebang haben. Prüfe auch **fehlende** lokale Module: Importiert das Skript ein Modul, dessen Dateiname in einem für den Aufrufer beschreibbaren Skriptverzeichnis angelegt werden kann, lädt Python möglicherweise diese Datei unter der RunAs-Identität. Prüfe die effektive sudo-Regel, den tatsächlichen [Modulsuchpfad](https://docs.python.org/3/library/sys_path_init.html) des Interpreters, ob das Modul eingebaut oder eingefroren ist und ob der Import erreicht wird. Eine direkte sudo-Regel für das Skript hat andere Anforderungen an Ausführungsbit und Shebang. Ein separater Wrapper, der vom Aufrufer gelieferte Tokens an `sudo -u account` anhängt, erfordert außerdem eine Prüfung des Argumentflusses: Ein weiteres `-u` in diesen Tokens ist nur relevant, wenn die aufgerufene sudo-Richtlinie die resultierende Identität erlaubt. Statische Zeichenfolgen allein beweisen keinen dieser Pfade.

### Über sudo ausgeführtes Apache mit vom Aufrufer kontrollierter Konfiguration

Erlaubt eine sudo-Regel einen privilegierten Aufruf von `apachectl`, `apache2ctl` oder `httpd` mit einer vom Aufrufer kontrollierten `-f`-Konfigurationsdatei, prüfe die Berechtigungen dieser Datei und ihres übergeordneten Verzeichnisses. Apaches [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)-Direktive erwartet einen Modulnamen und anschließend den **Dateinamen des Moduls**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) lädt ebenfalls eine Datei. [`Include` und `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) können die Konfiguration erweitern oder Dateiinhalte über Fehlermeldungen offenlegen. Ein benutzerdefinierter Wrapper kann diese Pfade validieren, Berechtigungen ablegen oder Argumente einschränken. Eine beschreibbare Konfiguration ist daher ein Prüfhinweis und kein Beweis für Codeausführung. Prüfe Pfadkanonisierung, Symlinks und Direktivenverarbeitung, bevor du einen Schluss ziehst.

### Über sudo ausgeführtes nginx mit vom Aufrufer kontrollierter Konfiguration

Eine uneingeschränkte, root-fähige `nginx`-Regel kann [`-c` zur Auswahl einer anderen Konfiguration erlauben](https://nginx.org/en/docs/switches.html). Prüfe die genauen sudo-Argumente und Ausschlüsse, ob der Aufrufer die Konfiguration angeben kann und ob Master- oder Worker-Prozesse anschließend weiterhin auf geschützte Pfade zugreifen können. Ein ausgewähltes `root`-Verzeichnis in Kombination mit `autoindex` kann Dateien über einen neuen Listener offenlegen; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kann einen privilegierten Dateischreibpfad ermöglichen. Das DAV-Modul ist jedoch nicht standardmäßig einkompiliert; prüfe daher dessen Verfügbarkeit, Erreichbarkeit des Listeners, Dateiberechtigungen und Verhalten temporärer Dateien. Die [`error_log`-Direktive](https://nginx.org/en/docs/ngx_core_module.html#error_log) kann ebenfalls auf eine ausgewählte Datei verweisen. Das Schreiben von Protokollen in eine sensible Konfigurationsdatei wie `/etc/ld.so.preload` erfordert einen tatsächlich privilegierten Schreibzugriff und einen kontrollierbaren Protokolleintrag, bevor daraus ein Rechteausweitungspfad wird. Die Hervorhebung der ausführbaren Datei in `sudo -l` ist ein Prüfhinweis, kein Nachweis, dass einer dieser Pfade funktioniert. Starte oder rekonfiguriere nginx bei einer passiven Bestandsaufnahme nicht.

### Mustervergleich in privilegierten Bash-Eingabeaufforderungen

Liest ein über sudo erlaubtes Bash-Skript einen Wert vom Aufrufer ein und prüft ihn mit `[[ "$expected" == $entered ]]`, interpretiert Bash den nicht zitierten rechten Operanden als Muster. Ein Platzhalter kann daher den Vergleich bestehen, ohne den erwarteten Wert zu kennen. Durch Anführungszeichen um den Operanden (`[[ "$expected" == "$entered" ]]`) wird der Vergleich zu einem literalen Zeichenkettenvergleich. Prüfe die genaue sudo-Regel, ob die Eingabeaufforderung erreichbar ist und was das Skript nach dem Vergleich ausführt; die Syntax allein weist keinen ausnutzbaren Pfad nach. Gib den erwarteten Wert bei der Bestandsaufnahme nicht aus. Siehe das [Referenzhandbuch zu Bash-Bedingungskonstrukten](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Über sudo ausgeführte Helfer, die Dateien herunterladen und ausführen

Eine uneingeschränkte, root-fähige sudo-Berechtigung für einen benutzerdefinierten Helfer verdient eine Datenflussprüfung, wenn dieser eine vom Aufrufer ausgewählte URL akzeptiert, die Antwort auf dem Datenträger speichert und die Datei später mit einem Interpreter oder einer Shell aufruft. [Sudoers erlaubt beliebige Argumente, wenn ein Befehlseintrag keine aufführt](https://man7.org/linux/man-pages/man5/sudoers.5.html); ein festgelegter Pfad der ausführbaren Datei beschränkt nicht, was sich über deren Argumente auswählen lässt. Prüfe die tatsächliche URL-Validierung, den Ausgabepfad, den Erfolgszweig und die anschließende Ausführung im installierten Helfer. Ein passender libcurl-Import oder eine druckbare Zeichenfolge allein beweist diese Kette nicht.

Selbst ein fester Ausgabename kann zwischen Schreiben und Ausführen ersetzbar sein, wenn der Helfer einen **relativen Pfad in einem vom Aufrufer kontrollierten Arbeitsverzeichnis** verwendet. Das Umbenennen oder Ersetzen einer root-eigenen Datei wird durch Schreib- und Suchzugriff auf das Verzeichnis sowie etwaige Sticky-Bit-Einschränkungen bestimmt, nicht nur durch den Modus der Datei; siehe [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Prüfe, ob der Helfer den Pfad später erneut öffnet oder den bereits geöffneten Dateideskriptor verwendet und ob er vor dem Schreiben in ein vertrauenswürdiges Verzeichnis wechselt. Untersuche sudo-Richtlinie, Helfer und Verzeichnismetadaten passiv; rufe bei einer Bestandsaufnahme weder den privilegierten Download auf noch führe einen Race aus.

Ein Root-sudo-Download-Helfer kann außerdem Argument-Injection ermöglichen, wenn er einen Bash-Befehlsstring wie `curl <caller input> -o <fixed output>` zusammenstellt. Ein Filter, der Leerraum zurückweist, verhindert [Bash-Klammererweiterung](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) nicht: Nicht zitierte, kommaseparierte Elemente können zu separaten curl-Argumenten werden. Erreicht die Eingabe curl vor der festgelegten Option `-o`, kann eine vom Aufrufer angegebene Ausgabedatei das Ziel für die erste URL unter der Identität des Helfers auswählen; [curl ordnet Ausgabeoptionen den URLs der Reihe nach zu](https://curl.se/docs/manpage.html#-o). Prüfe die genaue Shell, Zitierung und Eingabevalidierung, die effektive sudo-Regel, die Reihenfolge der curl-Argumente und unterstützte URL-Schemata sowie, ob der Aufrufer die abgerufenen Bytes kontrolliert oder das Ergebnis lesen kann. Eine mit PyInstaller gepackte ausführbare Datei kann Python-Anwendungslogik enthalten; ihr Verpackungsmarker oder ein `curl`-String allein beweist diesen Datenfluss jedoch nicht. Prüfe, sofern autorisiert, eine begrenzte Offline-Kopie; eine routinemäßige Bestandsaufnahme sollte den Helfer nicht ausführen und keine vom Angreifer ausgewählten Daten abrufen.

Ein Root-sudo-Shell-Skript, das [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aufruft, wählt lediglich einen unbenutzten Namen aus; es erstellt **keine** Datei. Erstellt das Skript diese Datei später in einem Verzeichnis, das ein anderer Benutzer beeinflussen kann, öffnet sie erneut und hängt ihren Inhalt an ein geschütztes Ziel wie `authorized_keys` von root an, sollte eine mögliche Race Condition bei temporären Dateien geprüft werden. Prüfe die genaue sudo-Regel, Verzeichnis- und Dateieigentümer, Abfolge von Erstellung und erneutem Öffnen, Kernel-Schutzmaßnahmen und ob der privilegierte Schreibzugriff tatsächlich angreiferkontrollierte Bytes verwendet. Eine Zeichenfolge `mktemp -u` oder ein beschreibbares `/tmp` allein beweist die Race Condition nicht. Untersuche Skript und Pfadmetadaten, ohne es auszuführen oder während der Bestandsaufnahme einen Race um die temporäre Datei auszuführen.

## Hinweise zur Abwehr

- Erteile über sudo keine Berechtigungen für Interpreter oder interaktive Editoren.<sup>[[1]](#references)</sup>
- Bevorzuge feste, root-eigene Wrapper, die genau eine eng umrissene administrative Aktion ausführen.<sup>[[1]](#references)[[2]](#references)</sup>
- Ist ein Interpreter unvermeidbar, beschränke den genauen Skriptpfad und verhindere vom Benutzer kontrollierte Argumente, beschreibbare Imports, `PYTHONPATH` und unsicheres Beibehalten von Umgebungsvariablen.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Ist das Bearbeiten von Dateien erforderlich, beschränke den genauen Dateipfad und erwäge `sudoedit` mit gepatchten sudo-Versionen und strenger Umgebungsbehandlung.<sup>[[1]](#references)[[2]](#references)</sup>
- Prüfe `SETENV`, `env_keep`, beschreibbare Arbeitsverzeichnisse, beschreibbare Modul-/Importpfade, `NOEXEC`, `use_pty` und Protokollierung, betrachte sie aber nicht als vollständige Sandbox.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
