## Інтерпретатори, дозволені sudo

Якщо `sudo -l` дозволяє користувачеві запускати інтерпретатор від імені root, вважайте це прямим виконанням коду. Інтерпретатори призначені для виконання довільного коду, тому правило, яке дозволяє запускати `python3`, `perl`, `ruby`, `lua`, `node` або подібні бінарні файли, зазвичай рівнозначне виконанню команд від імені root, якщо аргументи не обмежені й не перевіряються належним чином.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Типовий порядок перевірки: спочатку перегляньте привілеї користувача, а потім виконайте інструкцію Python за допомогою параметра інтерпретатора `-c`.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Інші приклади інтерпретаторів наведено нижче; у документації перелічених інтерпретаторів описано виконання коду inline або API дочірніх процесів.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Точний шлях має значення. Якщо правило sudo дозволяє `/usr/bin/python3`, під час перевірки використовуйте саме цей шлях.<sup>[[2]](#references)</sup>

Шаблон glob для виконуваного файлу sudo, наприклад `/usr/bin/python*`, може також дозволити Python 2 для скрипту, написаного для Python 3. Якщо скрипт викликає `input()` з текстом, контрольованим користувачем, [Python 2 обчислює цей текст як вираз](https://docs.python.org/2/library/functions.html#input); явний виклик інтерпретатора перевизначає shebang скрипту. Перш ніж вважати це шляхом до виконання коду, перевірте встановлені відповідні бінарні файли, ефективні RunAs і політику аргументів, відмови в доступі та доступність вводу.

Фіксований шлях до скрипту в правилі sudo з можливістю запуску від root не обмежує команди, які виконує скрипт. Для доступного для читання Bash wrapper перевірте, чи використовує його перша виконувана команда не взятий у лапки позиційний параметр, наприклад `$1`, як **слово команди**, коли sudo дозволяє користувачеві вибирати аргументи. Підтвердьте ефективну ідентичність RunAs, політику пароля й аргументів, подальші відмови в доступі та фактичну гілку скрипту; результат можуть змінити `NOEXEC`, фіксований безпечний список аргументів або wrapper, що перевіряє свою команду. Під час переліку статично перегляньте короткий скрипт, а не запускайте його з тестовою командою.

Необмежене правило sudo з можливістю запуску `dotnet` від root також варто перевірити з погляду інтерпретатора. Якщо встановлено .NET SDK, [`dotnet fsi` запускає код F# в інтерактивному режимі або зі скрипту](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), а [`dotnet run` виконує проєкт із вихідного коду](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Спершу підтвердьте ефективну ідентичність RunAs і точну політику аргументів: правило, обмежене певною безпечною підкомандою або довіреною програмою, надає інші права, а в інсталяції лише з runtime можуть бути відсутні команди SDK. Сама назва виконуваного файлу — це привід для перевірки, а не доказ можливості виконання коду.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Редактори, дозволені через sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерактивний редактор від імені root, розглядайте це як спосіб виконання команд, а не як нешкідливий дозвіл редагувати файли. Редактори часто можуть виконувати shell-команди, читати довільні файли, записувати довільні файли або викликати зовнішні допоміжні програми зсередини редактора.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Типова послідовність перевірки: переглянути привілеї користувача, а потім запустити кожен дозволений редактор або pager через sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Виконання команд у Nano

Якщо `nano` дозволено запускати через sudo, виконання команд може бути доступне з інтерфейсу редактора.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Потім введіть команду, наприклад `id` або `/bin/sh`, у командний рядок nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Якщо інтерактивна оболонка не має доступних потоків термінала, ця форма перенаправлення спрямовує її стандартні потоки виводу та помилок до дескриптора 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Точна послідовність клавіш може відрізнятися залежно від версії nano та параметрів збирання, але проблема безпеки та сама: редактор запущений від імені root і може виконувати зовнішні команди.<sup>[[1]](#references)[[12]](#references)</sup>

### Інші поширені способи виходу з редактора

Редактори на кшталт Vim зазвичай дають змогу виконувати команди через `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Пейджери на кшталт `less` також можуть надавати можливість виконання команд оболонки.<sup>[[14]](#references)</sup>

Правило sudo, що дозволяє запускати `apport-cli` від root, також потребує такої самої перевірки пейджера. У вразливих версіях Apport звіт про збій можна було відкрити в `less` із розміром термінала, який контролює зловмисник; за певних умов використання sudo та пейджера це могло надати root shell. Перш ніж вважати версію вразливою, перевірте чинне правило sudo, конфігурацію пейджера та виправлення в пакеті дистрибутива. Під час пасивного переліку перевіряйте метадані пакета й політики, не створюючи збій і не відкриваючи привілейований звіт. [Запис Ubuntu про CVE](https://ubuntu.com/security/CVE-2023-1326) містить виправлені версії пакетів для окремих випусків, зокрема версії з перенесеними виправленнями.

```text
!/bin/sh
```

## Інші ризики правил sudo та doas

Почніть із `sudo -l`, `sudo -V` і відповідної політики `doas`. Розглядайте разом дозволену команду, користувача, від імені якого її запускають, аргументи, середовище та параметри за замовчуванням. Дозвіл запускати команду від імені непривілейованого облікового запису служби все одно може відкрити доступ до його файлів або шлях до root.

Фіксований Python-скрипт, дозволений через sudo, усе ще може запускати команду оболонки з ідентичністю RunAs, якщо інтерактивне введення, контрольоване користувачем, конкатенується в [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Заборони символів пунктуації оболонки недостатньо, щоб довести безпеку: [оболонка також розпізнає підстановку команд `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Переконайтеся, що дозволені аргументи доходять до гілки, яка обробляє введення, що введення без безпечної перевірки потрапляє до команди оболонки, а ефективна політика sudo дозволяє потрібного користувача RunAs. Сам шлях до скрипта або виклик `os.system()` — лише привід для перевірки; переглядайте вихідний код, не запускаючи привілейований скрипт.

Ефективний дозвіл sudo від root для `chattr` може зняти атрибут незмінності (`i`) з файла, але сам по собі він не надає права на запис чи нової ідентичності. [Посібник `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) зазначає, що цей атрибут блокує зміну, і змінити його може лише root або процес із `CAP_LINUX_IMMUTABLE`. Перевірте точну політику аргументів sudo та підтримку файлової системи, а потім окремо з’ясуйте, чи зможе користувач записувати у файл після зняття атрибута та чи використовує його процес із вищими привілеями. Наприклад, для заміни оболонки входу також потрібні прийняті цільовим обліковим записом облікові дані й фактичний вхід через цю оболонку. Під час інвентаризації перевіряйте політику, атрибути файлів і дозволи, не змінюючи їх.

Якщо sudo запитує пароль і одноразовий код, не змішуйте ці передумови з дозволом на команду. Доступний для читання файл `.google_authenticator` містить чутливий секретний seed, тоді як старий хеш пароля програми або бази даних — лише можливий варіант поточного пароля облікового запису; жодне з цього не доводить, що другий фактор приймається ефективною конфігурацією PAM. Після авторизації перевірте точні RunAs та аргументи: необмежений дозвіл root для RubyGems `gem` може відкрити його команду редактора ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), але обмежений дозвіл або невдала автентифікація — ні. Пасивна інвентаризація має повідомляти шляхи й політику, не виводячи seed, не відновлюючи пароль, не генеруючи код і не запускаючи привілейовану команду.

Необмежений дозвіл sudo для `knife`, що може запускатися від root, потребує перевірки на рівні інтерпретатора: [Chef документує, що `knife exec -E` локально виконує рядок Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Переконайтеся, що ефективне правило sudo дозволяє підкоманду `exec` і переданий користувачем аргумент `-E`, потрібну ідентичність RunAs, а також перевірте відповідні заборони команд чи фіксовані аргументи. Встановлений бінарний файл або правило, обмежене іншими підкомандами, — лише привід для перевірки. Пасивна інвентаризація має повідомляти про правило, не запускаючи `knife`.

Точний дозвіл sudo для інтерактивного `msfconsole`, який може запускатися від root, так само чутливий: [GTFOBins описує його консоль `irb`](https://gtfobins.org/gtfobins/msfconsole/), яка може успадкувати ідентичність sudo. Переконайтеся, хто є ефективним користувачем RunAs, які аргументи дозволені, чи є заборони команд, `NOEXEC` або інші обмеження, як поводиться встановлена консоль і чи може користувач передавати їй інтерактивне введення. Саме підсвічування шляху — лише привід для перевірки; під час пасивної інвентаризації не запускайте консоль.

У FreeBSD навіть правило sudo, обмежене командами root `pkg update` і `pkg install *`, потребує перевірки довіри до репозиторію. З’ясуйте, чи може користувач записувати в `/etc/hosts` і чи використовує *ефективна* конфігурація ввімкнених репозиторіїв HTTP-хостнейм із `signature_type: none`. [Посібник FreeBSD з `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) зазначає, що `none` вимикає перевірки підписів; сам `pkg+http` цього не означає. Пакет може містити скрипти встановлення ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), тож користувач, який справді контролює кінцеву точку репозиторію та може вибрати пакет, потенційно може перетнути межу привілеїв root. Перш ніж робити такий висновок, перевірте перевизначення репозиторію, розв’язання SRV/дзеркал, ефективні аргументи sudo, вибір пакета й виконання скриптів. Переглядайте політику та невеликі локальні конфігураційні файли, не перенаправляючи імена й не запускаючи `pkg` під час інвентаризації.

Правило sudo, що дозволяє `apt-get update` і `apt-get upgrade` від root, також потребує перевірки довіри до репозиторію, якщо sudo зберігає контрольований користувачем `http_proxy`. Перевірте, чи ефективна конфігурація APT справді використовує цю змінну й на які ввімкнені репозиторії вона може вплинути; сам проксі не може підмінити пакети з архіву, автентифікованого довіреним ключем підпису. [Посібник HTTP-транспорту APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) описує пріоритет проксі, а [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — перевірки підписів, перевизначення для незахищених репозиторіїв і підтвердження для неавтентифікованих пакетів. Перевірте точні RunAs та аргументи sudo, політику автентифікації репозиторію, потребу в інтерактивному підтвердженні й те, чи запускає вибране оновлення скрипти пакетів від root. Пасивно перевіряйте політику та локальну конфігурацію; не перенаправляйте трафік пакетів і не запускайте оновлення під час інвентаризації.

Правило sudo, що дозволяє `snap install` від root, може створити межу між пакетом і кодом, якщо аргументи дають змогу користувачеві вибрати локальний snap і дозвільний режим встановлення. [Документація Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) зазначає, що `--dangerous` пропускає перевірки assertion для локального snap, а `--devmode` послаблює ізоляцію; [hook встановлення може виконатися під час першого встановлення](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Перш ніж стверджувати, що це дає доступ до захищених файлів хоста, перевірте точну політику аргументів/RunAs sudo, хто контролює файл snap, чи приймає ці режими встановлений snapd, а також ефективну ідентичність і рівень ізоляції hook. Сам бінарний файл `snap` або правило, яке лише виглядає як таке, що містить wildcard, цього ланцюжка не доводить. Під час пасивної інвентаризації не встановлюйте пакет і не запускайте його hook.

Для точного дозволу sudo запускати бінарний файл для читання облікових даних від імені **не-root** облікового запису спершу перевірте дозволи бінарного файла, не запускаючи його. Вбудований запит пароля може бути видимим лише як широкі символи; [GNU `strings` документує витягування 16-бітного little-endian тексту](https://sourceware.org/binutils/docs/binutils/strings.html). Видимий рядок не доводить, що це прийнятий пароль або що успішна гілка відкриває поточні облікові дані. Окремо перевірте поведінку бінарного файла, доступ цільового облікового запису до захищених даних, чинність облікових даних і будь-який подальший перехід між обліковими записами чи групами. Якщо цей обліковий запис належить до `docker`, перевірте доступ до сокета й те, чи демон працює від root або без root, перш ніж робити висновок про доступ root до хоста; [Docker документує наслідки для root від членства в цій групі](https://docs.docker.com/engine/install/linux-postinstall/). Звичайна інвентаризація має повідомляти про правило sudo та членство в групах, не виконуючи бінарний файл і не виводячи його рядки.

Правило sudo з wildcard для скриптів обслуговування програми потребує перевірки не лише шляху до скрипта. З’ясуйте, чи приймає дозволений скрипт необмежені аргументи або читає параметри, які може змінювати обліковий запис програми з нижчими привілеями, а потім простежте ці значення до команд оболонки або середовища підпроцесу. Наприклад, `zmupdate.pl` у ZoneMinder [формує команду `mysqldump` і виконує її через `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), а `zmdc.pl` [копіює параметр `ZM_LD_PRELOAD` у `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) перед запуском демонів. Правило sudo, що дозволяє запускати будь-який із цих скриптів від root, може перетнути межу довіри, якщо відповідне введення контролюється користувачем і потрапляє до цього коду у встановленій версії. Перевірте ефективне правило sudo, права на конфігурацію програми й вихідний код скрипта; сам wildcard або параметр — лише привід для перевірки, а не доказ виконання.

- `SETENV`, `env_keep`, `secure_path` і `LD_PRELOAD` можуть перетворити вузько обмежену команду на шлях до підміни імпорту, бібліотеки чи PATH. Див. [посібник зі змінних середовища](../linux-basics/linux-environment-variables.md) і [зловживання SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Точний дозвіл sudo з `SETENV` для root-скрипту-обгортки також потребує перевірки на один крок, якщо обгортка запускає фіксований Python-скрипт із буквальним імпортом. `secure_path` обмежує пошук команд оболонкою, а не пошук модулів Python через [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); параметри [`-E` і `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) змушують Python ігнорувати цю змінну середовища. Перш ніж вважати це виконанням коду, перевірте ефективні теги та заборони sudo, гілку обгортки, параметри інтерпретатора, розв’язання імпорту й доступний для запису користувачем каталог пошуку. Короткі скрипти переглядайте статично; не запускайте привілейовану обгортку.

Точний дозвіл sudo для `neofetch ""`, який може запускатися від root, усе ще може завантажити конфігурацію оболонки, якщо відповідні параметри sudo зберігають контрольований користувачем `XDG_CONFIG_HOME`. [Завантажувач конфігурації Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) підключає `neofetch/config.conf` або `neofetch/config` із цього каталогу; порожній список аргументів не перешкоджає такому пошуку. Переконайтеся, що завантажувач присутній у встановленій версії, перевірте ефективні RunAs і політику аргументів, заборони команд, чи справді sudo зберігає для цієї команди вибрану змінну та чи контролює користувач шлях до доступної для читання конфігурації. Збережена змінна або встановлений Neofetch самі по собі — лише привід для перевірки. Перегляньте політику й метадані файлів, не запускаючи привілейовану команду та не виводячи вміст конфігурації; див. [обробку середовища sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Необмежене правило sudo для `facter`, яке може запускатися від root, потребує окремої перевірки custom facts. [Puppet документує](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), що `--custom-dir` завантажує файли фактів Ruby із вибраного каталогу. Перевірте, чи дозволяє точне правило sudo цей параметр, чи підтримує його встановлений Facter і чи контролює користувач каталог. Фіксовані аргументи, явна заборона команди або вимкнені custom facts можуть змінити результат. Пасивна інвентаризація має повідомляти про можливість у політиці, не запускаючи Facter і не читаючи вміст файлів фактів.

Для точного дозволу sudo запускати скрипт від root із `SETENV` перевірте команди без абсолютного шляху, як-от `find`, і ефективний `PATH` після застосування політики sudo та ініціалізації скрипта. Підключений файл Bash також може виконати `enable -n [`: [після цього Bash шукає в `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) зовнішню команду `[`, якщо скрипт згодом використовує її. Перевірте застосовні [правила середовища sudoers і `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), наявність `NOSETENV`/`NOEXEC` чи заборон, потік виконання скрипта й підключених файлів, а також доступний для запису та виконання каталог пошуку, контрольований користувачем. Читабельний скрипт із командою без абсолютного шляху — лише привід для перевірки, а не доказ привілейованого виконання; перегляньте його, не запускаючи правило sudo.

- Привілейований скрипт, що завантажує дані з фіксованого URL за допомогою `curl`, усе ще може отримати відповідь, вибрану користувачем, якщо відповідне правило sudo зберігає `http_proxy` і запит іде через цей проксі. Якщо скрипт потім передає відповідь XML-парсеру, який розв’язує зовнішні сутності, шкідлива відповідь може розкрити файли, доступні привілейованому процесу. Перевірте точну політику середовища sudo, винятки `no_proxy`, запитуваний URL, конфігурацію парсера й місце виведення; сама змінна проксі або XML-парсер — не вразливість. У [документації curl щодо змінних середовища проксі](https://everything.curl.dev/usingcurl/proxies/env.html) описано поведінку цих змінних. Під час пасивної інвентаризації не надсилайте мережевих запитів і не обробляйте шкідливий XML.
- Скрипт sudo, який може запускатися від root, формує файл PostScript із даних, на які впливає користувач, а потім запускає `ps2pdf -dNOSAFER`, потребує окремої перевірки потоку даних. Ghostscript документує, що цей прапорець вимикає SAFER до виклику `.setsafe`, дозволяючи файлові операції PostScript у межах дозволів процесу в ОС. SQL-запит, сформований з аргументу користувача, може передати контрольовані зловмисником рядки в шаблон PostScript, але сам рядок запиту або запуск `ps2pdf` не доводять, що дані потрапляють у виконуваний синтаксис PostScript. Перевірте ефективне правило sudo, точний шлях від введення до шаблону, екранування, поведінку встановленого Ghostscript і те, чи вмикається SAFER знову до обробки документа. Під час пасивної інвентаризації не запускайте привілейоване перетворення. Див. [документацію Ghostscript щодо `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Для правила sudo, що запускає скрипт оболонки, порівняйте збережені змінні із самим скриптом. Конструкція на кшталт `if $CHECK_CONTENT; then` запускає розгорнуте значення як команду, тож збереження `CHECK_CONTENT` може дозволити виконання команди навіть за фіксованих шляху до скрипта й аргументів. Для конкретного правила потрібно перевірити, чи доступна ця гілка і чи справді середовище зберігається.<sup>[[2]](#references)[[22]](#references)</sup>
- Python-скрипт, дозволений через sudo, може імпортувати код із каталогу, доступного для запису, або з кешованого файлу `.pyc`. Випадок із кешем описано в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md).
- Фіксований Python-скрипт, дозволений через sudo для запуску від root, усе ще може відкрити інтерактивний налагоджувач. Виклики на кшталт `pdb.set_trace()` або `pdb.post_mortem()` дають змогу виконувати Python-інструкції в контексті процесу, що налагоджується, якщо користувач може досягти точки зупинки або обробника винятку **і контролює потік введення налагоджувача**. Перевірте точне правило sudo RunAs, автентифікацію й умови гілки, досяжність винятку, власника термінала/введення та те, чи працює налагоджувач у тому самому привілейованому процесі. Запит через сокет, що викликає виняток, сам по собі не дає доступу до налагоджувача, підключеного до іншого термінала. [Python документує виконання інструкцій налагоджувачем і режим post-mortem](https://docs.python.org/3/library/pdb.html); переглядайте скрипт статично, не провокуючи привілейований обробник під час інвентаризації.
- Фіксований Python-скрипт, дозволений через sudo, також може зчитати поле профілю з бази даних або Unix-сокета й додати його до рядка, який згодом стає **рядком форматування** для `str.format()`. [Поля підстановки можуть звертатися до атрибутів і ключів відображень](https://docs.python.org/3/library/string.html#format-string-syntax), тож контрольоване зловмисником поле може переглядати об’єкти, передані до `format()`, і розкрити доступні через них дані, якщо результат виводиться або зберігається там, звідки його може прочитати користувач. Перевірте ефективну ідентичність sudo RunAs, право запису до конкретного запису, потік даних у рядок форматування, передані об’єкти та доступність результату. Це не означає автоматичне виконання коду; буквальний довірений рядок форматування з контрольованими зловмисником *значеннями* — інший випадок. Розкритий секрет дає змогу перейти до облікового запису ОС лише якщо цей обліковий запис його приймає. Перегляньте скрипт і дозволи сокета, не запускаючи привілейовану операцію.
- Python-обгортка, що може запускатися від root, може передавати вибраний користувачем URL до `Repo.clone_from` у GitPython. Якщо обгортка також вмикає Git `protocol.ext.allow=always`, віддалений URL `ext::` може запускати зовнішній допоміжний процес. Перевірте точні аргументи sudo, джерело URL, версію пакета GitPython і наявність виправлень від постачальника, а також те, чи обгортка явно дозволяє небезпечні протоколи. У GitPython додали [захист від небезпечних протоколів за замовчуванням](https://github.com/gitpython-developers/GitPython/commit/2625ed9) у версії 3.1.30; версія виконуваного файла `git` — окремий факт. Під час пасивної перевірки читайте лише правило й обмежений фрагмент вихідного коду, не запускаючи клонування.
- Дозвіл sudo для переходу між користувачами на CLI-клієнт клонування репозиторіїв може відкрити окремий шлях ін’єкції в рядок оболонки. Простежте, чи потрапляє вибраний користувачем аргумент репозиторію до Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) або іншого конструктора команд оболонки без безпечного розділення аргументів; Node `exec` передає рядок команди оболонці. Перевірте точного користувача RunAs, дозволені підкоманди й аргументи, код встановленої обгортки та перевірку введення. Сама назва інструмента для роботи з репозиторіями або необмежене правило sudo не доводять наявності ін’єкції команд. Перегляньте обгортку, не запускаючи привілейоване клонування під час інвентаризації.
- Саморобна обгортка, що належить root, може здаватися безпечною, бо її бінарні файли й скрипти недоступні для запису, але рішення виконати привілейовану дію може залежати від прапорця, локального значення API або стану служби, який може змінити непривілейований користувач. Простежте кожну умову до її джерела й перевірок авторизації. Під час інвентаризації перевіряйте конфігурацію та дозволи, не змінюючи робочий стан; виклик `systemd-run` усередині обгортки має значення лише тоді, коли на відповідну умову можна вплинути.
- Клієнт резервного копіювання, дозволений через sudo від root, може приймати вибраний користувачем файл конфігурації (наприклад, `npbackup-cli -c`). Перевірте точного користувача RunAs і дозволені аргументи, а потім з’ясуйте, чи контролює користувач шлях до конфігурації, шляхи джерел резервного копіювання, репозиторій або параметри читання/відновлення. Зашифрований секрет репозиторію в доступній для читання конфігурації все одно може бути використаний клієнтом, але саме правило не доводить доступ до репозиторію чи розкриття файлів root. Перевіряйте авторизацію, не запускаючи резервне копіювання й не виводячи його вміст.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) підтримує `--password-command`, який викликає програму для отримання пароля репозиторію. Якщо правило sudo дозволяє користувачеві з нижчими привілеями запускати restic від root із вибраною ним командою пароля та підкомандою, якій потрібен пароль, ця допоміжна програма може запуститися від root. Перегляньте точні аргументи й винятки sudo; не запускайте допоміжну програму або команду резервного копіювання лише для перевірки цієї умови.
- Дозвіл sudo на `restic backup`, який може запускатися від root, також може перетнути межу читання файлів, якщо шаблон аргументів sudo дозволяє користувачеві вибрати джерело й репозиторій, який він згодом зможе прочитати та розшифрувати. [Wildcard в аргументах sudoers можуть збігатися з пробілами й косими рисками](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), тому перевіряйте кінцеві wildcard, а не припускайте, що фіксований префікс шляху до репозиторію обмежує джерело. [Restic може зберігати резервні копії в локальних і віддалених репозиторіях](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), але локальний репозиторій може містити щойно записані об’єкти, доступні лише root; перш ніж вважати це розкриттям даних, перевірте ефективну політику sudo, доступ до бекенду, пароль репозиторію та дозволи отриманих об’єктів. Резервна копія SSH-ключа надає доступ лише якщо цільовий обліковий запис приймає цей ключ. Під час пасивної перевірки не запускайте резервне копіювання.
- Необмежена саморобна команда обслуговування або резервного копіювання може приймати шлях виведення чи мати власний планувальник завдань. Для запису у файл перевірте точне правило sudo й користувача RunAs, а потім з’ясуйте, чи контролює користувач і дані, і призначення. Для запланованої команди перевірте ідентичність, від імені якої працює планувальник, введення команди та додаткові вимоги до пароля чи авторизації. Саме ім’я команди або `NOPASSWD` не доводить жодного з цих шляхів. Див. [запис у файли, що належать root](../interesting-files-permissions/write-to-root.md) і [таймери cron та systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Фіксована команда sudo все ще може завантажувати передбачуваний файл конфігурації зі спільного каталогу, доступного для запису. З’ясуйте, чи може користувач підмінити цей файл і чи керують його поля джерела й призначення привілейованим завантаженням або копіюванням. URL локального файла може відкрити дані, доступні лише користувачеві RunAs sudo; контрольоване користувачем джерело разом із захищеним призначенням може створити шлях запису. Перевірте обробку URL встановленою програмою, перевірки шляху призначення, ефективне правило sudo й доступність результату. Сам шлях конфігурації, доступний для запису в `/tmp`, — лише привід для перевірки; перегляньте бінарний файл і метадані, не запускаючи привілейоване передавання.
- Правило sudo для `git apply` може дозволити користувачеві записувати файли, вибрані контрольованим ним патчем, від імені RunAs. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) дозволяла створити символічне посилання спеціально сформованим патчем, а потім записати дані за межами робочого дерева, навіть коли команда не приймала `--unsafe-paths`. Перевірте ефективне правило аргументів sudo, джерело патча, доступ RunAs до робочого каталогу та наявність виправлення Git або бекпорту від постачальника. Необмежене правило, що дозволяє `--unsafe-paths`, — окремий явний ризик параметра; ані версія Git, ані сам дозвіл на `git apply` не доводять, що захищений файл можна змінити. Під час пасивної інвентаризації не застосовуйте ненадійний патч.
- Правило sudo для `clamscan --debug`, яке може запускатися від root, може перетнути межу читання, якщо користувач із нижчими привілеями може надати образ DMG, а встановлений парсер вразливий до [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), яка могла розкрити вміст файлів через налагоджувальний вивід. Перевірте точні дозволені аргументи й шлях сканування, контроль над введенням, ефективний обліковий запис RunAs, виправлення рушія або бекпорт і видимість виводу для користувача. Якщо ширше правило дозволяє `--file-list`/`-f`, окремо перевірте цю поведінку; політика, зафіксована на `--debug <scan-path>`, цей параметр не дозволяє. Під час інвентаризації перевіряйте політику й метадані пакета, не скануючи спеціально створений файл і не виводячи захищений вміст.
- Правило sudo, що може відкривати зашифрований образ диска від root, разом із другим правилом монтування створеного mapper може імпортувати контрольовані користувачем файли до простору монтування хоста. Перевірте обидва ефективні правила й аргументи, контроль над образом і назвою mapper, фактичну точку монтування, а також власника й режим отриманих файлів. Для переходу через set-user-ID також потрібні доступний для виконання файл, параметри монтування, що дозволяють його виконання (`nosuid` блокує його), і відповідна політика процесу або MAC; саме відкриття чи монтування образу — лише привід для перевірки. Окремий шлях через наявну резервну копію потребує відповідного ключа й корисного секрету всередині, доступного для читання. Перевіряйте політику та шляхи, не відкриваючи й не монтуючи образ під час пасивної інвентаризації. Див. [посібник cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) і [параметри mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Правило sudo для запуску shell- або Python-скрипту від root потребує перевірки робочого каталогу, якщо скрипт запускає `./helper`, не переходячи спершу до фіксованого каталогу. Список Python на кшталт `['./helper']`, переданий до `subprocess.run`, має таку саму поведінку: робочий каталог може вибрати користувач. Він може вибрати доступний для запису каталог і розмістити там виконуваний файл із таким відносним ім’ям; абсолютний шлях в іншій частині скрипта цього виклику не захищає. Перш ніж вважати це виконанням коду, перевірте ефективне правило, `runchdir` або іншу політику зміни каталогу, потік виконання скрипта й досяжність гілки, доступний для запису та виконання каталог, а також обмеження монтування/`NOEXEC`. Якщо скрипт не читається, його поведінка невідома, доки вихідний код не буде переглянуто через авторизований шлях. Переглядайте скрипти статично, не запускаючи допоміжну програму. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) описано політику робочого каталогу.
- Фіксований Python-валідатор, що може запускатися від root, усе ще може обчислювати вибраний користувачем файл даних. [Документація Python щодо `eval()` застерігає від ненадійного введення](https://docs.python.org/3/library/functions.html#eval): перевірка суфікса введення, арифметичний префікс або гілка валідації не є пісочницею, якщо решта виразу доходить до `eval`. Перш ніж вважати це шляхом виконання, перевірте ефективне правило sudo, чи може користувач вибрати й контролювати конкретний файл, умови гілок парсера й формування виразу, а також ідентичність привілейованого процесу. Сам факт наявності `eval` у читабельному скрипті — лише привід для перевірки; перегляньте вихідний код і дозволи файлів, не запускаючи валідатор і не передаючи тестовий вираз під час інвентаризації.
- Ruby-обгортка sudo, що може запускатися від root, читає відносний файл YAML, наприклад `YAML.load(File.read("dependencies.yml"))`, і може отримати введення з робочого каталогу користувача, якщо обгортка чи політика sudo не фіксує цей каталог. Перевірте точні дозволені аргументи, дозволи каталогу й файла, а також поведінку встановленої версії Psych: старі реалізації `YAML.load` могли десеріалізувати довільні об’єкти Ruby, тоді як новіші версії за замовчуванням обмежують класи. Сам виклик у вихідному коді — лише привід для перевірки; переконайтеся, що файл справді розташований у каталозі, доступному користувачеві для запису, і що встановлений завантажувач приймає небезпечні класи. Для ненадійного введення надавайте перевагу `safe_load` із явним мінімальним списком дозволених класів. Див. документацію [Psych для Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) і [Psych для Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Точний дозвіл sudo для `sudo go run /absolute/file.go`, що може запускатися від root, потребує перевірки робочого каталогу, якщо вихідний код Go читає відносний файл WASM і після аналізу результату може запустити відносний скрипт оболонки. Перевірте ефективний RunAs, аргументи команди й заборони, поточний каталог, доступний користувачеві для запису, потік даних від WASM до гілки та те, чи запускає ця гілка допоміжну програму. Фіксований sudo `runchdir`, `os.Chdir` або [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) може змінити місце пошуку. Саме спільне статичне розташування цих елементів — лише можливий ризик; перегляньте вихідний код, не запускаючи Go, WASM або допоміжну програму.
- `sudoedit` і wildcard в аргументах потребують перевірки точної версії та правила; у [контрольному списку](linux-privilege-escalation-checklist.md) описано проблему редагування файлів через sudoedit. Для дозволу `sudoedit` між користувачами зі шляхом, що містить wildcard, перевірте ефективне значення `sudoedit_follow` або `FOLLOW`, `sudoedit_checkdir`, кінцевий шлях і те, хто може підмінити кожен батьківський елемент. Перше може дозволити переходити за символічним посиланням, а вимкнення другого прибирає перевірки каталогів, доступних для запису; жоден із параметрів сам по собі не доводить можливість запису у файл іншого користувача. Перш ніж робити висновок, перевірте встановлену політику sudo й точні аргументи, що збіглися з правилом. Див. [визначення параметрів sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- У правилі команди sudoers wildcard в аргументі може збігатися як із пробілами, так і зі символами шляху. Правило для команди, здатної читати файли, з аргументом на кшталт `/restricted/*` може тому дозволяти додатковий аргумент файла після відповідного префікса. Перевірте точного користувача RunAs, шлях до команди, шаблон аргументу й наступні заборони; доведене читання файла не означає виконання команд. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) розрізняються шаблони аргументів і шаблони шляхів до команд.
- Шаблон аргументу, схожий на шлях, також може збігатися з `../`. Наприклад, правило sudo для `node /opt/scripts/*.js`, яке може запускатися від root, може дозволити користувачеві вибрати файл JavaScript за межами `/opt/scripts`, якщо переданий шлях усе ще починається з `/opt/scripts/` і розв’язується через сегменти батьківських каталогів. Це wildcard для **аргументу**; для wildcard у шляху до виконуваного файла Node діють інші правила зіставлення косих рисок. Перевірте ефективне правило, подальші заборони, розв’язання шляху, контроль над цільовим файлом і будь-які обмеження sudoers через регулярні вирази чи digest, перш ніж робити висновок про виконання коду. Див. [правила wildcard у sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) і [документацію командного рядка Node](https://nodejs.org/api/cli.html).
- Архіватори та інші утиліти можуть мати механізми запуску команд. Перевірте точні дозволені аргументи за допомогою [GTFOBins](https://gtfobins.github.io/), а не припускайте, що команди можуть запускати лише оболонки чи інтерпретатори.
- Необмежене правило sudo для `qpdf`, яке може запускатися від root, може розкрити привілейований файл через вкладення PDF: qpdf 10.2 і новіші версії підтримують `--empty` і `--add-attachment file ... --` із вихідним PDF. Якщо привілейований процес може прочитати вибране джерело й записати PDF у доступний користувачеві шлях, цей файл може містити вихідні байти. Перш ніж робити висновок про можливе розкриття файла, перевірте ефективні аргументи та винятки sudo, версію qpdf, доступ до джерела й шлях виведення. Читання root SSH-ключа корисне для входу лише тоді, коли ключ чинний і автентифікація root через SSH дозволена. Див. [параметри вкладень qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Повторне використання часової позначки sudo залежить від політики кешування, власника, термінала/сеансу та дозволів. Перевірки описано в [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens).
- `doas` має власні правила й конфігурацію. Перевірте дозволені команди та шляхи конфігурації, доступні для запису, як описано в [розділі про doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Інструменти збирання та керування пакетами, запущені через sudo

Необмежений дозвіл sudo для Foundry `forge` може мати значення, навіть якщо RunAs — інший обліковий запис без root. Параметри компілятора на кшталт `--use` можуть вибрати локальний виконуваний файл, а `forge flatten -o` — шлях вихідного файла. Перш ніж вважати цей дозвіл експлуатованим, перевірте встановлену версію Forge, точні аргументи sudo, доступні шляхи проєкту й компілятора, дозволи вихідного файла та ефективне середовище. Допоміжний виконуваний файл із відносним шляхом, знайдений через `PATH`, — це шлях, залежний від версії та середовища, а не властивість, яку слід припускати для кожного збирання Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Необмежений дозвіл sudo для `pacman`, який може запускатися від root, дає більше, ніж запити про пакети: `-U` приймає локальний пакет, пакети можуть містити скрипти встановлення, а `--hookdir` вибирає інший каталог hook. Перед перевіркою перегляньте ефективне правило sudo, обмеження аргументів і винятки; для пасивної інвентаризації не потрібно встановлювати пакет або запускати hook.<sup>[[25]](#references)[[26]](#references)</sup>

Фіксована shell-обгортка sudo також може встановити залежність npm із заданою назвою, а потім запустити програму Node. Перевірте точне правило RunAs, чи пакет уже встановлено, ефективні `HOME` і `userconfig` npm, конфігурацію проєкту або перевизначення в командному рядку, а також чи контролює користувач із нижчими привілеями реєстр або пакет, повернений для цієї назви. [npm документує пошук `.npmrc` для користувача й проєкту](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); значення `HOME` для sudo залежить від установленої політики й дистрибутива, тож файл `.npmrc` користувача, доступний для запису, може читатися привілейованим процесом npm, а може й ні. Якщо щойно встановлений пакет імпортує привілейована програма, його код модуля може виконатися з ідентичністю цієї програми. Скрипти під час встановлення — окремий шлях, що залежить від версії та конфігурації; [npm описує їхній життєвий цикл і обробку користувача](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Шлях `.npmrc` або рядок `npm install` самі по собі — лише привід для перевірки. Під час пасивної інвентаризації перегляньте правило, коротку обгортку, шляхи конфігурації та походження пакета, не встановлюючи пакет і не запускаючи програму.

Дозвіл sudo для `pip` або `pip3 download`, який може запускатися від root, також потребує перевірки збирання пакетів, якщо аргументи дозволяють користувачеві вибрати ненадійний дистрибутив вихідного коду, навіть якщо шаблон URL обмежує його локальною службою й суфіксом `.tar.gz`. `pip download` приймає URL архівів і розв’язує метадані пакетів; підготовка sdist може запустити бекенд збирання або застарілий код `setup.py` ще до того, як архів просто збережеться. Перевірте точні RunAs та правило аргументів sudo, чи може користувач опублікувати або підмінити вибраний архів і чи справді ця версія pip готує метадані. Фіксований довірений архів або wheel цього шляху не доводить. Під час пасивної інвентаризації не завантажуйте й не збирайте ненадійний пакет. Див. [команду pip download](https://pip.pypa.io/en/stable/cli/pip_download/), [інтерфейс системи збирання](https://pip.pypa.io/en/stable/reference/build-system/) і [рекомендації щодо безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Правило sudo, що дозволяє `pip install` із вибраним користувачем локальним шляхом до проєкту, створює прямішу межу збирання. [pip приймає локальні каталоги проєктів](https://pip.pypa.io/en/stable/topics/local-project-installs/) і запускає їхню систему збирання; [бекенд збирання виконує контрольовані проєктом build hooks](https://pip.pypa.io/en/stable/reference/build-system/). Перш ніж вважати це виконанням коду з привілеями, перевірте ефективну ідентичність RunAs, точні обмеження аргументів і заборони, контроль над вибраним проєктом та поведінку встановленого pip/бекенду. Фіксований довірений проєкт або правило, що не дозволяє вибирати шлях користувачеві, цього шляху не доводить. Перегляньте правило й метадані проєкту, не встановлюючи пакет під час пасивної інвентаризації.

Необмежений дозвіл sudo для `easy_install`, який може запускатися від root, — подібний привід для перевірки застарілої системи збирання пакетів. [Setuptools документує](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), що Easy Install приймає локальний каталог проєкту й збирає дистрибутиви вихідного коду; під час такого збирання контрольований користувачем проєкт може виконати `setup.py` з ідентичністю sudo. Перевірте ефективний обліковий запис RunAs, точну команду й обмеження аргументів (включно з подальшими заборонами), контроль над вибраним проєктом і поведінку встановленого інструмента. Фіксований довірений проєкт або політика, що не дозволяє користувачеві вибирати джерело, цього шляху не доводить. Під час інвентаризації перегляньте правило й метадані проєкту, не встановлюючи пакет.

Python-обгортка, дозволена через sudo, яка використовує `setuptools.package_index.PackageIndex.download` із вибраним користувачем URL, потребує іншої перевірки, ніж `pip download`: [GHSA-5rjg-fvgr-3xxf для setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) описує, як у вразливих випусках до 78.1.1 ім’я файла, отримане з URL, могло виходити за межі призначеного каталогу завантаження й записувати файл із дозволами процесу. Перевірте ефективні RunAs і правило аргументів sudo, чи передає обгортка URL користувача саме до цього API, наявність виправлення у встановленій збірці або від постачальника, а також кінцевий шлях файла. Сам рядок версії або каталог завантаження, доступний для запису, не доводить довільний запис. Під час інвентаризації перегляньте коротку обгортку й метадані пакета, не завантажуючи URL і не записуючи файл.

Обгортка збирання, дозволена через sudo і передає вибраний користувачем файл `.spec` до PyInstaller, потребує такої самої перевірки межі довіри. PyInstaller spec — це виконуваний Python-код, що виконується під час **збирання**, а його записи `datas` можуть включити до артефакту файли, доступні для читання ідентичності збірки. Перевірте точного користувача RunAs, правила аргументів і заборон sudo, обробку шляху й гілок в обгортці, контроль над вибраним spec-файлом і доступ до отриманого артефакту. Сам дозвіл на введення `.py` або наявність PyInstaller не доводять контроль над spec-файлом чи привілейоване виконання. Під час пасивної перевірки читайте лише обмежений фрагмент файла обгортки й метадані; не запускайте збирання. Див. [документацію PyInstaller щодо spec-файлів](https://pyinstaller.org/en/stable/spec-files.html).

### Завантажувачі preset і плагінів, запущені через sudo

Python-інструменти, що приймають вибраний користувачем preset або каталог плагінів, можуть імпортувати код із привілеями, наданими через sudo. Наприклад, BBOT приймає preset через `-p`, а в його [документації власних модулів](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) описано записи `module_dirs`, що вказують додаткові каталоги модулів Python. Якщо ефективне правило sudo дозволяє вибирати preset, а користувач контролює модуль у вибраному каталозі, імпорт може виконати код від імені привілейованого користувача, потенційно ще до того, як інструмент відхилить недійсний модуль. Перевірте встановлену версію, точну політику запуску sudo й аргументів, а також власників preset і каталогів модулів, не завантажуючи модуль під час інвентаризації.

### Інструмент командного рядка Backdrop, запущений через sudo

[Bee](https://github.com/backdrop-contrib/bee) — це інструмент PHP командного рядка для Backdrop CMS. Його команди `eval` (`php-eval`) і `php-script` можуть запускати PHP-код, переданий користувачем. Тому правило sudo, що дозволяє запускати виконуваний файл Bee від root із необмеженими аргументами, може відкрити виконання коду від root, якщо Bee може ініціалізувати встановлену систему Backdrop. Запустіть його з каталогу сайта або виберіть сайт глобальним параметром `--root=<directory>`; сама наявність Bee чи файла Backdrop `settings.php` не доводить наявності дозволу sudo, придатного сайта або успішної ініціалізації. Перед перевіркою перегляньте ефективне правило sudo, заборони команд, ідентичність виконуваного файла та доступ до сайта. Під час пасивної інвентаризації перевіряйте правило й шляхи до файлів, не запускаючи Bee. Команди PHP описані в [журналі змін Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md).

### Сервери термінала, запущені через sudo

`mosh-server` запускає інтерактивний сервер термінала від імені користувача, який його викликав. Він вибирає високий UDP-порт і ключ сеансу, повідомляє обидва користувачеві та зазвичай запускає оболонку входу цього користувача під час підключення клієнта. Тому необмежений дозвіл sudo на `mosh-server`, який може запускатися від root, — привід перевірити можливість отримання оболонки, навіть якщо сама команда сервера від’єднується. Перевірте ефективну ідентичність RunAs, дозволені аргументи й винятки, встановлений бінарний файл, оболонку, доступність клієнта й доступ до UDP. Під час пасивної інвентаризації перевірте правило sudo, не запускаючи сервер і не виводячи активний ключ сеансу. Див. [посібник сервера Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) і [нотатки про архітектуру](https://github.com/mobile-shell/mosh#how-it-works).

### Привілейовані обгортки резервного копіювання, що переписують файл завдань користувача

Shell-обгортка, що запускається від root, може приймати вибраний користувачем файл завдань, видаляти `../` зі шляхів джерела, перевіряти, що кожен отриманий шлях починається з дозволеного каталогу, переписувати файл завдань, а потім передавати програмі резервного копіювання *шлях до цього файла*. Перевірте перетворений шлях після повної канонізації: одноразова заміна рядка може створити нову послідовність обходу каталогів, яку прийме лексична перевірка префікса. Також з’ясуйте, чи читає програма резервного копіювання перетворені дані з пам’яті, чи повторно відкриває файл. Якщо вона відкриває його знову, невдала перезапис може залишити на місці початкове введення.

У Linux `fs.protected_regular` може заборонити запис `O_CREAT` до звичайного файла іншого користувача у world-writable каталозі зі sticky bit. Така заборона захищає систему, але shell-обгортка, що ігнорує помилку запису, усе ще може продовжити роботу з початковим файлом завдань. Перевірте цей параметр, власника файла й каталогу, а також те, чи зупиняється обгортка після помилки. Шлях є лише кандидатом на розкриття файлів, якщо ефективне правило sudo дозволяє запускати обгортку від привілейованого користувача, користувач контролює введення завдання й доступне для читання призначення резервної копії, а утиліта резервного копіювання справді додає захищені джерела. Перевіряйте ці умови, не запускаючи резервне копіювання під час інвентаризації.

### Wildcard в аргументах привілейованих інструментів роботи з пакетами

У правилі sudo для `tcpdump` символ `*` у **шаблоні аргументу** може збігатися з пробілами й косими рисками, тож обмеження, схоже на шлях, усе одно може дозволяти додатковий текст параметрів. Це не те саме, що wildcard у шляху до виконуваного файла команди; перевірте повне правило RunAs і будь-які подальші заборони. Якщо можна підставляти параметри, дозволений виклик і семантика параметрів установленого [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) визначають, чи дають `-F`, `-V`, `-r`, `-w` або `-Z` корисні можливості читання/запису. `-V` читає список імен capture-файлів, а не довільний файл загального призначення. AppArmor або інша політика MAC може блокувати доступ до файлів, навіть якщо sudo дозволяє команду; файл профілю на диску не доводить, що профіль завантажено й застосовано. Перш ніж робити висновок, пасивно перевірте авторизацію й політику. Різницю між цими wildcard описано в [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Правило sudo від root, у якому вказано лише виконуваний файл `tcpdump` без обмеження аргументів, також потребує перевірки. У [посібнику tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) зазначено, що `-z` запускає команду після ротації, якщо збережений capture-файл ротують через `-C` або `-G`; параметр `-Z` або значення за замовчуванням під час компіляції може знизити привілеї до запуску цієї команди. Перш ніж вважати правило шляхом підвищення привілеїв, перевірте ефективне правило sudo, встановлену збірку, поведінку зі зниженням привілеїв і можливість ротації. Підсвічене правило — лише кандидат для перевірки, а не доказ запуску команд від root.

### Обгортки Nmap, запущені через sudo

Якщо дозволений через sudo шлях `nmap` є shell-обгорткою, перевірте точний дозволений шлях і кожен параметр, який вона передає. Блокування звичного написання `--script` не обов’язково блокує завантаження коду NSE: [`--datadir` у Nmap](https://nmap.org/book/man-misc-options.html) вибирає файли даних, а NSE [завантажує `nse_main.lua`](https://nmap.org/book/nse-implementation.html) із вибраного каталогу даних, коли ввімкнено сценарії. Деякі встановлені збірки також приймають альтернативні форми довгих параметрів, тож порівняйте обмеження з фактичним парсером цього бінарного файла. [`--excludefile`](https://nmap.org/book/man-target-specification.html) — окрема поверхня читання файлів; помилки парсера можуть розкривати текст. Під час інвентаризації перевірте ефективне правило sudo, логіку обгортки, версію Nmap, контроль над каталогами й політику MAC, не запускаючи сканування.

### Hook pull Mercurial, запущені через sudo

Фіксоване джерело в `sudo hg pull /fixed/source` усе ще залишає **репозиторій-отримувач** вибраним за поточним робочим каталогом, якщо команда не фіксує його параметром `-R`. У контрольованому користувачем репозиторії-отримувачі можуть бути hook у `.hg/hgrc`, які запустяться з ідентичністю користувача RunAs sudo. [Mercurial ігнорує конфігурацію репозиторію, що належить недовіреному користувачеві або групі](https://mercurial-scm.org/help/topics/config), тому перш ніж вважати це виконанням коду, перевірте довірених користувачів/групи облікового запису RunAs і точний робочий каталог. Для пасивної перевірки достатньо переглянути політику й конфігурацію; не виконуйте pull і не запускайте hook під час інвентаризації.

### Hook pull Git, запущені через sudo

Для точного дозволу sudo на `sudo git pull`, який може запускатися від root, також перевірте репозиторій-**отримувач**, вибраний робочим каталогом. У репозиторії, що належить користувачеві, може бути виконуваний hook `post-merge`, який запуститься з ідентичністю процесу Git, якщо pull виконає успішне злиття; [Git документує цей hook](https://git-scm.com/docs/githooks) і [поведінку pull: merge чи rebase](https://git-scm.com/docs/git-pull). Перевірте ефективне правило sudo й CWD, активний шлях до hook і його дозволи, а також можливість злиття з новими комітами. Невдалий pull, pull без змін або лише з rebase не доводить наявності цього шляху через hook. Перегляньте політику й метадані репозиторію, не запускаючи привілейований pull.

### Копіювання архівів через rsync, запущений через sudo

Для `sudo rsync -a ... /writable/source/* /fixed/destination/` символ `*` у **шаблоні аргументів sudoers** може збігатися з пробілами й дозволити додатковий параметр між джерелом і призначенням. Це відрізняється від розгортання імен файлів оболонкою. Якщо користувач може наповнити джерело, а привілейований процес rsync має право запису до призначення, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) може запитати зміну власника на привілейованого користувача, тоді як режим архіву зберігає біти дозволів, потенційно створюючи файл з SetUID. Перевірте точну [семантику wildcard у sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), версію rsync, подальші заборони, параметр файлової системи `nosuid` і політику MAC. Правило, що збігається, — кандидат для перевірки, а не доказ успішного підвищення привілеїв.

### Експорт правил пакетного фільтра через sudo

Необмежений дозвіл root для `iptables` і `iptables-save` (або відповідної пари `ip6tables`) потребує перевірки можливості запису у файл. Match `comment` приймає вибраний користувачем текст правила, а `iptables-save -f` записує серіалізований набір правил у вибраний шлях.<sup>[[20]](#references)[[21]](#references)</sup> Корисне навантаження залежить від того, як встановлений бекенд серіалізує коментарі та чи приймає файл призначення інші рядки експорту; сам `iptables-save` не надає можливості довільно вибирати вміст. Перевірте точну ідентичність sudo RunAs, аргументи й винятки, доступне розширення match, бекенд і дозволи файла призначення. Під час інвентаризації перегляньте дозвіл, не змінюючи правил firewall і не записуючи файл.

### Привілейований каталог журналів Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) стосувалася версій Below до 0.9.0, які створювали world-writable каталог `/var/log/below`. Якщо служба або дозволена команда sudo запускає вразливу збірку від root, користувач, який може записувати в непривілейований каталог журналів і переходити до нього, може підмінити запис журналу символічним посиланням до того, як привілейований процес його відкриє. Перевірте наявність виправлення в установленому пакеті, точний шлях привілейованого виконання, ефективний доступ до каталогу, sticky bit і ACL, а також метадані `/var/log/below/error_root.log`. Сам world-writable шлях або правило sudo не доводять повного ланцюжка. Sticky bit або бекпорт від постачальника змінює оцінку. Під час пасивної інвентаризації перевіряйте лише метадані; створювати посилання або запускати привілейовану програму не потрібно.

### Збір привілейованого пакета підтримки з введення, доступного для запису

Скрипт профілю підтримки, дозволений через `sudo`, може читати фіксовані шляхи журналів від root і копіювати їхній вміст до архіву профілю. Перегляньте фактичний скрипт на предмет читання файлів, а потім перевірте, чи може користувач підмінити шлях джерела або будь-який батьківський елемент каталогу символічним посиланням. Якщо привілейоване читання переходить за цим посиланням, а архів доступний користувачеві для читання, захищений файл може бути розкритий. Потрібні всі умови: дозвіл sudo, шлях джерела, доступний для запису, привілейоване читання й доступний для читання результат. Сам журнал або ім’я профілю, доступні для запису, недостатні. Під час інвентаризації перевірте ефективні дозволи й метадані посилань, не підмінюючи файли й не створюючи профіль. [Рекомендації Nagios XI щодо підтримки](https://support.nagios.com/forum/viewtopic.php?t=62758) описують його скрипт профілю, що запускається від root, і вихідний архів; це приклад того, чому для таких пакетів потрібні обмеження на введення та доступ до результату.

### Скрипти відновлення архівів Python, запущені від root

Навіть вузько обмежене правило sudo для скрипта відновлення Python потребує перевірки вхідного архіву. Якщо користувач може вибрати або підмінити архів, а скрипт розпаковує його від root за допомогою `tarfile.extractall(filter="data")`, перед покладанням на цей фільтр перевірте оновлення безпеки інтерпретатора. CPython виправив кілька обходів фільтра через символічні й жорсткі посилання, зокрема CVE-2025-4517, у версіях 3.9.23, 3.10.18, 3.11.13, 3.12.11 і 3.13.4. Дистрибутиви можуть бекпортувати виправлення в ранішу версію, тому показана версія інтерпретатора сама по собі не доводить наявність уразливості.<sup>[[16]](#references)[[17]](#references)</sup>

Для пасивної перевірки прочитайте точну команду sudo й скрипт, з’ясуйте, який аргумент вибирає архів, і перевірте, чи може поточний користувач записувати в архів або його батьківський каталог. Окремо перевірте встановлене виправлення постачальника й каталог розпакування; `filter="data"` не робить безпечним будь-який ненадійний архів.<sup>[[16]](#references)[[17]](#references)</sup>

### Завантажувачі моделей машинного навчання, запущені через sudo

Правило sudo, що дозволяє вибрати користувачеві файл `.pt`, `.pth` або `.ckpt`, потребує перевірки, якщо привілейований скрипт передає цей файл до [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` або іншого завантажувача на основі pickle. Перевірте ефективне правило RunAs, чи може користувач створити або підмінити вибрану модель, а також фактичний потік аргументів через будь-яку shell-обгортку до допоміжного скрипта Python. Суфікс `.pth` також використовується для не пов’язаних із цим конфігураційних файлів Python site, тож сам суфікс не свідчить про завантаження моделі. Сканування архіву або статичний аналіз pickle не доводять безпечність подальшого завантаження; перевірте [поведінку `weights_only`, залежну від версії](https://docs.pytorch.org/docs/stable/notes/serialization.html), і будь-які списки дозволених об’єктів. Див. [нотатки про ML pickle і Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Під час пасивної інвентаризації ніколи не завантажуйте й не розпаковуйте модель.

### Розбір збереженого введення у вираз, запущений через sudo

Фіксований Python-скрипт, запущений від root через sudo, усе ще може обчислювати текст, який користувач із нижчими привілеями може зберегти в базі даних програми. У TensorFlow виклик `preprocess_input_exprs_arg_string(value, safe=False)` вибирає шлях `eval`; [рекомендація з безпеки TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) описує небезпечний парсер і виправлення його виклику з командного рядка. Явний виклик програми `safe=False` потребує окремої перевірки, навіть якщо виклик із командного рядка виправлений. Перевірте ефективне правило sudo, хто може змінити конкретний рядок введення, чи дозволяють фільтрація або оцінювання цьому рядку дійти до виклику та як поводиться встановлена функція. Версія TensorFlow, дозвіл sudo або фіксований файл моделі самі по собі не доводять повного ланцюжка. Пасивно перевірте скрипт і потік даних; під час інвентаризації не запускайте привілейовану допоміжну програму й не надсилайте тестові вирази.

### Конфігурація needrestart, дозволена через sudo

`needrestart -c` завантажує вибраний користувачем конфігураційний файл Perl і виконує його вміст. Якщо `sudo -l` дозволяє запускати `needrestart` від root з аргументами, що допускають `-c`, а користувач може вибрати доступний для читання конфігураційний файл у каталозі, доступному для запису, цей дозвіл може привести до виконання коду від root. Перевірте точні користувача RunAs та правило аргументів sudo; правило з фіксованим списком аргументів може блокувати цей шлях. Це окремо від уразливостей needrestart під час сканування інтерпретаторів: оновлення пакета або вимкнення `interpscan` не робить безпечним необмежений дозвіл root на `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Імпорти Python під іншим обліковим записом через sudo

Фіксована точка входу Python усе ще може імпортувати модуль, який користувач може редагувати або підмінити, зокрема коли sudo запускає скрипт від імені **не-root** користувача служби. Для буквального `from utils import status` перевірте як локальні `utils/__init__.py` і `utils/status.py`, так і дозволи каталогу пакета. Перш ніж вважати доступний для запису файл шляхом виконання, перевірте шлях імпорту скрипта, точні дозволені аргументи sudo й те, чи доходить відповідна дія до цього імпорту. Під час інвентаризації перевіряйте файли й дозволи, не імпортуючи й не запускаючи скрипт.<sup>[[2]](#references)[[3]](#references)</sup>

Для точного правила sudo `python3 /absolute/script.py` потрібен лише доступний для читання скрипт; файл не обов’язково має бути виконуваним або містити shebang. Перевірте також **відсутні** локальні модулі: якщо скрипт імпортує модуль, файл якого можна створити в каталозі скрипта, доступному користувачеві для запису, Python може завантажити його з ідентичністю RunAs. Переконайтеся в ефективному правилі sudo, фактичному [шляху пошуку модулів](https://docs.python.org/3/library/sys_path_init.html) інтерпретатора, чи є модуль вбудованим або замороженим, а також у досяжності імпорту. Пряме правило sudo для скрипта має інші вимоги до біта виконання й shebang. Окрема обгортка, що додає передані користувачем токени після `sudo -u account`, також потребує перевірки потоку аргументів: ще один `-u` у цих токенах має значення лише якщо політика sudo дозволяє отриману ідентичність. Самі статичні рядки не доводять жодного з цих шляхів.

### Apache, запущений через sudo, з конфігурацією під контролем користувача

Якщо правило sudo дозволяє привілейований виклик `apachectl`, `apache2ctl` або `httpd` із конфігураційним файлом `-f`, контрольованим користувачем, перевірте дозволи цього файла й батьківського каталогу. Директива Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) приймає назву модуля, за якою йде **ім’я файла модуля**; директива [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) також завантажує файл. [`Include` і `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) можуть розширити конфігурацію або розкрити вміст файлів через помилки. Саморобна обгортка може перевіряти ці шляхи, знижувати привілеї або обмежувати аргументи, тому конфігурація, доступна для запису, — кандидат для перевірки, а не доказ виконання коду. Перш ніж робити висновок, перевірте канонізацію шляхів, символічні посилання й розбір директив.

### nginx, запущений через sudo, з конфігурацією під контролем користувача

Необмежене правило sudo для `nginx`, яке може запускатися від root, може дозволяти [`-c` вибрати іншу конфігурацію](https://nginx.org/en/docs/switches.html). Перевірте точні аргументи й винятки sudo, чи може користувач передати цю конфігурацію та чи матимуть створені master- або worker-процеси доступ до захищених шляхів. Вибрані `root` і `autoindex` можуть відкрити файли через новий listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) може надати привілейований шлях запису до файлів, але модуль DAV за замовчуванням не збирається; потрібно перевірити його наявність, доступність listener, дозволи файлів і поведінку тимчасових файлів. Директива [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) також може спрямовувати журнали у вибраний файл; запис журналів у чутливий конфігураційний файл, наприклад `/etc/ld.so.preload`, стає шляхом підвищення привілеїв лише за наявності ефективного привілейованого доступу для запису й контрольованого запису журналу. Підсвічування виконуваного файла в `sudo -l` — привід для перевірки, а не доказ працездатності будь-якого з цих шляхів. Під час пасивної інвентаризації не запускайте й не переконфігуровуйте nginx.

### Порівняння шаблонів у привілейованих підказках Bash

Якщо скрипт Bash, дозволений через sudo, читає значення користувача й перевіряє його через `[[ "$expected" == $entered ]]`, Bash трактує правий операнд без лапок як шаблон. Тому wildcard може пройти перевірку без знання очікуваного значення. Якщо взяти операнд у лапки (`[[ "$expected" == "$entered" ]]`), порівняння виконується як зі звичайним рядком. Перевірте точне правило sudo, чи доступна підказка та що скрипт робить після порівняння; сам синтаксис не доводить наявності експлуатованого шляху. Під час інвентаризації не виводьте очікуване значення. Див. [довідник Bash щодо умовних конструкцій](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Допоміжні програми, запущені через sudo, що завантажують і виконують файл

Необмежений дозвіл sudo від root на саморобну допоміжну програму потребує аналізу потоку даних, якщо вона приймає вибраний користувачем URL, записує відповідь на диск, а потім запускає цей файл через інтерпретатор або оболонку. [Sudoers дозволяє довільні аргументи, якщо в записі команди їх не перелічено](https://man7.org/linux/man-pages/man5/sudoers.5.html); фіксований шлях до виконуваного файла не обмежує те, що можуть вибрати його аргументи. Перевірте фактичну валідацію URL, шлях виведення, гілку успішного виконання й подальший запуск у встановленій допоміжній програмі. Сам імпорт libcurl або видимий рядок цього ланцюжка не доводять.

Навіть фіксоване базове ім’я вихідного файла може бути підмінене між записом і виконанням, коли допоміжна програма використовує **відносний шлях у робочому каталозі, контрольованому користувачем**. Можливість перейменувати або підмінити файл, що належить root, залежить від права запису й пошуку в каталозі та обмежень sticky bit, а не лише від режиму файла; див. [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Перевірте, чи повторно відкриває програма шлях згодом або використовує вже відкритий дескриптор, а також чи переходить вона до довіреного каталогу перед записом. Пасивно перевірте політику sudo, допоміжну програму й метадані каталогу; не запускайте привілейоване завантаження й не виконуйте гонку під час інвентаризації.

Допоміжна програма завантаження через sudo від root також може мати **ін’єкцію аргументів**, якщо вона формує рядок команди Bash на кшталт `curl <caller input> -o <fixed output>`. Фільтр, який відхиляє пробіли, усе ще не блокує [розгортання фігурних дужок Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): елементи, розділені комами й не взяті в лапки, можуть стати окремими аргументами curl. Якщо введення потрапляє до curl перед фіксованим `-o`, переданий користувачем параметр виведення може вибрати призначення першого URL з ідентичністю обгортки; [curl пов’язує параметри виведення з URL у порядку їх зазначення](https://curl.se/docs/manpage.html#-o). Перевірте точну оболонку, лапки, перевірку введення, ефективне правило sudo, порядок аргументів curl і підтримувані схеми URL, а також те, чи контролює користувач отримані байти або може прочитати результат. Виконуваний файл, упакований PyInstaller, може містити логіку Python-програми, але сам маркер пакування чи рядок `curl` не доводять цього потоку даних. Якщо це дозволено, перегляньте обмежену офлайн-копію; під час звичайної інвентаризації не запускайте допоміжну програму й не завантажуйте дані, контрольовані зловмисником.

Shell-скрипт, запущений через sudo від root, який викликає [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), лише вибирає невикористане ім’я; він **не** створює файл. Якщо скрипт згодом створює файл із цим ім’ям у каталозі, на який може вплинути інший користувач, повторно відкриває його й додає вміст до захищеного файла, наприклад `authorized_keys` root, перевірте можливу гонку тимчасового файла. Перевірте точне правило sudo, власника каталогу й файла, послідовність створення й повторного відкриття, захист ядра та те, чи привілейований запис справді використовує байти, контрольовані зловмисником. Сам рядок `mktemp -u` або доступний для запису `/tmp` не доводять наявності гонки. Перегляньте скрипт і метадані шляхів, не запускаючи його й не влаштовуючи гонку тимчасового файла під час інвентаризації.

## Зауваження щодо захисту

- Не дозволяйте запуск інтерпретаторів або інтерактивних редакторів через sudo.<sup>[[1]](#references)</sup>
- Надавайте перевагу фіксованим обгорткам, що належать root і виконують одну вузьку адміністративну дію.<sup>[[1]](#references)[[2]](#references)</sup>
- Якщо інтерпретатор необхідний, обмежте точний шлях до скрипта та виключіть контрольовані користувачем аргументи, імпорти, доступні для запису, `PYTHONPATH` і небезпечне збереження середовища.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Якщо потрібне редагування файлів, обмежте точний шлях до файла та розгляньте `sudoedit` із виправленими версіями sudo й суворою обробкою середовища.<sup>[[1]](#references)[[2]](#references)</sup>
- Перевіряйте `SETENV`, `env_keep`, робочі каталоги й шляхи модулів/імпорту, доступні для запису, `NOEXEC`, `use_pty` і журналювання, але не вважайте їх повноцінною пісочницею.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
