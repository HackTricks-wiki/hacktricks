## Interpreters wat deur sudo toegelaat word

As `sudo -l` ’n gebruiker toelaat om ’n interpreter as root uit te voer, moet dit as direkte code execution beskou word. Interpreters is ontwerp om arbitrêre code uit te voer, dus is ’n reël wat `python3`, `perl`, `ruby`, `lua`, `node` of soortgelyke binaries toelaat, gewoonlik gelykstaande aan root-opdraguitvoering, tensy die argumente streng beperk en gevalideer word.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Algemene hersieningsproses: lys eers die gebruiker se voorregte en voer dan ’n Python-stelling uit met die interpreter se `-c`-opsie.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Ander voorbeelde van interpreteerders word hieronder getoon; die gelyste interpreteerders dokumenteer uitvoering van inline-kode of API's vir kinderprosesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Die presiese pad is belangrik. As die sudo-reël `/usr/bin/python3` toelaat, gebruik daardie presiese pad tydens validasie.<sup>[[2]](#references)</sup>

’n Sudo-uitvoerbare glob soos `/usr/bin/python*` kan ook Python 2 toelaat vir ’n script wat vir Python 3 geskryf is. As die script `input()` met teks bereik wat deur die oproeper beheer word, [evalueer Python 2 daardie teks as ’n uitdrukking](https://docs.python.org/2/library/functions.html#input); ’n eksplisiete interpreter-aanroep ignoreer die script se shebang. Verifieer die geïnstalleerde binêre lêers wat ooreenstem, die effektiewe RunAs- en argumentbeleid, weierings en bereikbare invoer voordat jy dit as ’n uitvoeringsroete beskou.

’n Vaste scriptpad in ’n sudo-reël wat root-toegang kan verleen, beperk nie wat die script uitvoer nie. As dit ’n leesbare Bash-wrapper is, kyk of die eerste uitvoerbare opdrag ’n ongekwoteerde posisionele parameter soos `$1` as die **command word** gebruik terwyl sudo argumente toelaat wat deur die oproeper gekies word. Bevestig die effektiewe RunAs-identiteit, wagwoord- en argumentbeleid, latere weierings en die werklike scriptvertakking; `NOEXEC`, ’n vaste, veilige argumentelys of ’n wrapper wat sy opdrag valideer, kan die resultaat verander. Inspekteer die kort script staties tydens enumerasie eerder as om dit met ’n toetsopdrag aan te roep.

’n Onbeperkte sudo-reël vir `dotnet` wat root-toegang kan verleen, verdien ook ’n interpreter-oorsig. Met ’n geïnstalleerde .NET SDK kan [`dotnet fsi` F#-kode interaktief of vanuit ’n script uitvoer](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), en [`dotnet run` ’n projek vanaf bronkode uitvoer](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bevestig eers die effektiewe RunAs-identiteit en presiese argumentbeleid: ’n reël wat tot ’n bepaalde veilige subopdrag of vertroude toepassing beperk is, is ’n ander toestaanreël, en ’n runtime-only-installasie het dalk nie SDK-opdragte nie. Die uitvoerbare naam alleen is ’n aanduiding om dit na te gaan, nie bewys van kode-uitvoering nie.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` wat deur sudo toegelaat word: arbitrêre bevoorregte lêerskryf

GNU `tee` kopieer standaardinvoer na elke pad wat as ’n lêeroperand verskaf word. Daarom verleen ’n sudo-reël wat die uitvoering van `/usr/bin/tee` as root met argumente wat deur die oproeper beheer word, ’n primitief om arbitrêre lêers as root te skep of te oorskryf. Deur `-a` by te voeg, verander die primitief sodat dit byvoeg. ’n `PASSWD:`-merker het betrekking op sudo-verifikasie; op sigself beperk dit nie die bestemming of die grepe wat van standaardinvoer gelees word nie.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Inspekteer eers die presiese reël. Valideer die primitief slegs op ’n gemagtigde toetsstelsel, met ’n weggooibare bestemming wat veilig geskep kan word. Die finale `>/dev/null` onderdruk slegs `tee` se kopie na standaarduitvoer.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Om `sudo` voor die produsent te plaas, verhoog nie die voorregte van ’n latere shell-omleiding nie, omdat die aanroepende shell die bestemming oopmaak. Die bevoorregte proses moet die skrywer wees, soos in die pyplyn hierbo.<sup>[[1]](#references)[[15]](#references)</sup>

Nadat jy die skryfaksie bevestig het, kies ’n geskikte root-kode-uitvoeringsteiken uit [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). In een waargenome ketting is root `tee` gebruik om ’n kortstondige lêer onder `/etc/cron.d/` te skep, ’n agterdeur deur ’n gebruikerbeheerde skrip te begin en die cron-lêer ná uitvoering te verwyder. Deur die cron-lêer te verwyder, is verhoed dat dit ’n langtermyn-volhardingsinskrywing word, hoewel stelsellogboeke steeds bewyse van die aktiwiteit bewaar het.<sup>[[27]](#references)</sup>

## Redigeerders wat deur sudo toegelaat word

As `sudo -l` ’n gebruiker toelaat om ’n interaktiewe redigeerder as root te gebruik, behandel dit as ’n oppervlak vir opdraguitvoering, nie as ’n onskadelike toestemming om lêers te redigeer nie. Redigeerders kan dikwels shell-opdragte uitvoer, arbitrêre lêers lees of skryf, of eksterne hulpprogramme vanuit die redigeerder aanroep.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Algemene hersieningsvloei: lys die gebruiker se voorregte en begin dan elke toegelate redigeerder of blaaier met sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano-opdraguitvoering

Wanneer `nano` via `sudo` toegelaat word, kan opdraguitvoering vanaf die redigeerderkoppelvlak moontlik wees.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Voer dan ’n opdrag soos `id` of `/bin/sh` by die nano-opdragprompt in.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

As ’n interaktiewe shell nie bruikbare terminale strome het nie, koppel hierdie herleidingsvorm sy standaardafvoer en -fout aan beskrywer 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die presiese sleutelsekwensie kan wissel na gelang van die nano-weergawe en bouopsies, maar die sekuriteitsprobleem is dieselfde: die redigeerder loop as root en kan eksterne opdragte uitvoer.<sup>[[1]](#references)[[12]](#references)</sup>

### Ander algemene ontsnappings uit redigeerders

Redigeerders in Vim-styl maak gewoonlik opdraguitvoering via `:!` moontlik.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers soos `less` kan ook shell-uitvoering blootlê.<sup>[[14]](#references)</sup>

’n sudo-reël wat `apport-cli` as root toelaat, verdien dieselfde pager-ondersoek. Geaffekteerde Apport-weergawes kon ’n omvalverslag in `less` oopmaak met ’n terminaalgrootte wat deur ’n aanvaller aangepas kon word; die pager kon dan ’n root shell bied indien die spesiale sudo- en pager-voorwaardes nagekom is. Gaan die effektiewe sudo-reël, pager-konfigurasie en verspreidingspakket se regstelling na voordat jy die weergawe op sigself as kwesbaar beskou. Lees die pakket- en beleidmetadata sonder om tydens passiewe enumerasie ’n omval te veroorsaak of die bevoorregte verslag oop te maak. [Ubuntu se CVE-rekord](https://ubuntu.com/security/CVE-2023-1326) lys reggestelde pakketweergawes per vrystelling, insluitend teruggeporteerde regstellings.

```text
!/bin/sh
```

## Ander gevare met sudo- en doas-reëls

Begin met `sudo -l`, `sudo -V` en enige toepaslike `doas`-beleid. Lees die toegelate opdrag, gebruiker as wie dit loop, argumente, omgewing en verstekwaardes saam. Toestemming om as ’n nie-root-diensrekening te loop, kan steeds daardie rekening se lêers blootstel of ’n pad na root bied.

’n Vaste Python-skrip wat deur sudo toegelaat word, kan steeds ’n shell-opdrag onder sy RunAs-identiteit uitvoer as interaktiewe, oproeper-beheerde invoer aaneengeskakel word in [`os.system()`](https://docs.python.org/3/library/os.html#os.system). ’n Bloklys van shell-leestekens is nie genoeg om veiligheid te bewys nie: die [shell herken ook `$(...)`-opdragvervanging](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Bevestig dat die toegelate argumente die invoertak bereik, dat die invoer sonder veilige validering die shell-opdrag bereik, en dat die effektiewe sudo-beleid die beoogde RunAs-gebruiker toelaat. Die skrippad of ’n oproep na `os.system()` alleen is bloot ’n leidraad vir hersiening; ondersoek die bronkode sonder om die bevoorregte skrip uit te voer.

’n Effektiewe root-sudo-toekenning vir `chattr` kan ’n onveranderlike (`i`) lêerkenmerk verwyder, maar dit verleen op sigself nie skryftoegang of ’n nuwe identiteit nie. [Die `chattr`-handleiding](https://man7.org/linux/man-pages/man1/chattr.1.html) sê dat die kenmerk wysiging blokkeer en dat slegs root of ’n proses met `CAP_LINUX_IMMUTABLE` dit kan verander. Gaan die presiese sudo-argumentbeleid en lêerstelselondersteuning na, en verifieer dan afsonderlik dat die oproeper die lêer kan skryf nadat die kenmerk verwyder is en dat ’n verbruiker met ’n hoër identiteit dit gebruik. ’n Vervanging van ’n aanmeldingshell vereis byvoorbeeld ook die teikenrekening se aanvaarde geloofsbriewe en ’n werklike aanmelding deur daardie shell. Hersien beleid, lêerkenmerke en toestemmings sonder om dit tydens inventarisering te verander.

As sudo vir beide ’n wagwoord en ’n eenmalige kode vra, hou dié vereistes apart van die opdragtoekenning. ’n Leesbare `.google_authenticator`-lêer bevat sensitiewe saadmateriaal, terwyl ’n ou toepassings- of databasiswagwoord-hash slegs ’n kandidaat vir die huidige rekening se wagwoord is; nie een bewys dat die ander faktor deur die effektiewe PAM-konfigurasie aanvaar word nie. Sodra dit gemagtig is, hersien die presiese RunAs-gebruiker en argumente: ’n onbeperkte root-toekenning vir RubyGems `gem` kan sy redigeerder-opdrag blootstel ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), maar ’n beperkte toekenning of mislukte verifikasie doen dit nie. Passiewe inventarisering behoort paaie en beleid aan te meld sonder om die saad te druk, ’n wagwoord te herwin, ’n kode te genereer of die bevoorregte opdrag uit te voer.

’n Onbeperkte root-bevoegde sudo-toekenning vir Chef se `knife` verdien hersiening op interpreteerdervlak: [Chef dokumenteer dat `knife exec -E` ’n Ruby-string plaaslik evalueer](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifieer dat die effektiewe sudo-reël die `exec`-subopdrag en die deur die oproeper verskafte `-E`-argument, die beoogde RunAs-identiteit en enige ooreenstemmende opdragverbiedings of vaste argumente toelaat. Die geïnstalleerde binêre lêer of ’n reël wat tot ander subopdragte beperk is, is slegs ’n leidraad. Passiewe inventarisering behoort die reël aan te meld sonder om `knife` uit te voer.

’n Presiese root-bevoegde sudo-toekenning vir ’n interaktiewe `msfconsole` is eweneens sensitief: [GTFOBins dokumenteer die `irb`-konsole](https://gtfobins.org/gtfobins/msfconsole/), wat die sudo-identiteit kan erf. Bevestig die effektiewe RunAs-gebruiker, toegelate argumentlys, opdragverbiedings, `NOEXEC` of ander beperkings, geïnstalleerde konsolegedrag en of die oproeper interaktiewe invoer kan verskaf. ’n Pad-aanwysing alleen is bloot ’n leidraad vir hersiening; passiewe inventarisering behoort nie die konsole te begin nie.

Op FreeBSD verdien selfs ’n sudo-reël wat beperk is tot root se `pkg update` en `pkg install *` ’n hersiening van die vertroue in bewaarplekke. Gaan na of `/etc/hosts` deur die oproeper geskryf kan word en of die *effektiewe* geaktiveerde bewaarplekkonfigurasie ’n HTTP-gasheernaam met `signature_type: none` gebruik. [FreeBSD se `pkg.conf`-handleiding](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) sê dat `none` handtekeningkontroles deaktiveer; `pkg+http` alleen bewys dit nie. ’n Pakket kan installasieskripte bevat ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), dus kan ’n oproeper wat werklik die bewaarplek-eindpunt beheer en ’n pakket kan kies, die root-grens oorsteek. Verifieer bewaarplek-oorheersings, SRV-/spieëlresolusie, effektiewe sudo-argumente, pakketkeuse en skripuitvoering voordat jy dié gevolgtrekking maak. Ondersoek beleid en klein plaaslike konfigurasielêers sonder om name te herlei of `pkg` tydens inventarisering uit te voer.

’n Root-bevoegde sudo-toekenning vir `apt-get update` en `apt-get upgrade` verg ook hersiening van bewaarplekvertroue wanneer sudo ’n oproeper-beheerde `http_proxy` behou. Gaan na of die effektiewe APT-instaanbediener-konfigurasie daardie veranderlike werklik gebruik en watter geaktiveerde bewaarplekversoeke daardeur geraak kan word; ’n instaanbediener alleen kan nie pakkette vervang uit ’n argief wat deur ’n vertroude ondertekeningsleutel geverifieer word nie. [APT se HTTP-vervoerhandleiding](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) dokumenteer die prioriteit van instaanbedieners, en [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) dokumenteer handtekeningkontroles, oorheersings vir onveilige bewaarplekke en bevestiging vir ongeverifieerde pakkette. Bevestig die presiese sudo-RunAs-gebruiker en argumente, bewaarplekverifikasiebeleid, enige vereiste interaktiewe aanvaarding en of die gekose opgradering pakketskripte as root uitvoer. Ondersoek beleid en plaaslike konfigurasie passief; moenie pakketverkeer herlei of ’n opgradering tydens inventarisering uitvoer nie.

’n Root-bevoegde sudo-reël vir `snap install` kan ’n pakket-na-kode-grens vorm as sy argumente die oproeper toelaat om ’n plaaslike snap en ’n toegeeflike installasiemodus te kies. [Snap dokumenteer](https://snapcraft.io/docs/explanation/snap-development/install-modes/) dat `--dangerous` kontroles van plaaslike snap-bewerings oorslaan en dat `--devmode` inperking verslap; [’n installasiehaak kan tydens die aanvanklike installasie loop](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Gaan die presiese sudo-argument-/RunAs-beleid, wie die snap-lêer beheer, of die geïnstalleerde snapd dié modusse aanvaar, en die haak se effektiewe identiteit en inperking na voordat jy toegang tot beskermde gasheerlêers beweer. ’n `snap`-binêre lêer of reël wat soos ’n jokertekenreël lyk, bewys nie op sigself hierdie ketting nie. Passiewe inventarisering behoort nie ’n pakket te installeer of sy haak uit te voer nie.

Vir ’n presiese sudo-toekenning aan ’n pasgemaakte geloofsbriefleesbinêre lêer van ’n **nie-root**-rekening, ondersoek eers die toegekende binêre lêer en sy lêertoestemmings sonder om dit uit te voer. ’n Ingebedde wagwoordhek is moontlik net as breë karakters sigbaar; [GNU `strings` dokumenteer 16-bis little-endian-onttrekking](https://sourceware.org/binutils/docs/binutils/strings.html). ’n Sigbare string bewys nie dat dit die aanvaarde wagwoord is of dat die suksesvertakking ’n huidige geloofsbrief blootstel nie. Bevestig afsonderlik die binêre lêer se gedrag, die teikenrekening se toegang tot die beskermde data, die geldigheid van geloofsbriewe en enige latere rekening- of groepe-oorgang. As daardie rekening aan `docker` behoort, verifieer sokkertoegang en of die daemon rootful of rootless loop voordat jy toegang tot gasheer-root aflei; [Docker dokumenteer die root-vlak-implikasies van dié groep](https://docs.docker.com/engine/install/linux-postinstall/). Roetine-inventarisering behoort die sudo-reël en groeplidmaatskap aan te meld sonder om die binêre lêer uit te voer of sy stringe te stort.

’n Sudo-jokertekenreël vir ’n toepassing se instandhoudingskripte verg hersiening wat verder strek as die skrippad. Gaan na of die toegelate skrip onbeperkte argumente aanvaar of instellings lees wat deur ’n laerbevoorregte toepassingrekening geskryf kan word, en volg dan dié waardes na shell-opdragte of ’n subprocess-omgewing. ZoneMinder se [`zmupdate.pl` stel byvoorbeeld ’n `mysqldump`-opdrag saam en voer dit met `qx` uit](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), terwyl [`zmdc.pl` die `ZM_LD_PRELOAD`-instelling na `LD_PRELOAD` kopieer](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) voordat daemone begin word. ’n Sudo-reël wat een van dié skripte as root toelaat, kan ’n vertrouensgrens oorsteek as die ooreenstemmende invoer beheerbaar is en daardie kode in die geïnstalleerde weergawe bereik. Ondersoek die effektiewe sudo-reël, toepassingkonfigurasietoestemmings en skripbron; die jokerteken of instelling alleen is ’n leidraad vir hersiening, nie bewys van uitvoering nie.

- `SETENV`, `env_keep`, `secure_path` en `LD_PRELOAD` kan ’n andersins nou opdrag in ’n invoer-, biblioteek- of PATH-kaping verander. Sien die [omgewingsveranderlikegids](../linux-basics/linux-environment-variables.md) en [SUID-/skakelaarmisbruik](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

’n Presiese root-bevoegde `SETENV`-toekenning vir ’n shell-omhulsel verdien ook ’n eenstap-hersiening as die omhulsel ’n vaste Python-skrip met ’n letterlike invoerstelling begin. `secure_path` beperk shell-opsoek van opdragte, nie Python se [`PYTHONPATH`-module-soektog](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) nie; [`-E` en `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) laat Python dié omgewingsveranderlike ignoreer. Bevestig die effektiewe sudo-etikette en verbiedings, omhulselvertakking, interpreteerderopsies, invoerresolusie en ’n oproeper-skryfbare soekgids voordat jy dit as kode-uitvoering beskou. Ondersoek kort skripte staties; moenie die bevoorregte omhulsel uitvoer nie.

’n Presiese root-bevoegde `neofetch ""`-sudo-toekenning kan steeds ’n shell-konfigurasie laai wanneer die toepaslike sudo-verstekwaardes oproeper-beheerde `XDG_CONFIG_HOME` behou. [Neofetch se konfigurasielaaier](https://github.com/dylanaraps/neofetch/blob/master/neofetch) laai `neofetch/config.conf` of `neofetch/config` uit daardie gids; ’n leë argumentlys keer nie dié opsoek nie. Bevestig die geïnstalleerde laaier, effektiewe RunAs- en argumentbeleid, enige opdragverbiedings, of sudo werklik die gekose veranderlike vir dié opdrag behou en of die oproeper ’n leesbare konfigurasiepad beheer. ’n Behoue veranderlike of geïnstalleerde Neofetch alleen is ’n leidraad vir hersiening. Ondersoek beleid en lêermetadata sonder om die bevoorregte opdrag uit te voer of konfigurasie-inhoud te druk; sien [sudoers se hantering van die omgewing](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

’n Onbeperkte root-bevoegde sudo-reël vir `facter` verdien ’n afsonderlike hersiening van pasgemaakte facts. [Puppet dokumenteer](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) dat `--custom-dir` Ruby-fact-lêers uit ’n gekose gids laai. Gaan na of die presiese sudo-reël dié opsie toelaat, of die geïnstalleerde Facter dit aanvaar en of die oproeper die gids beheer. ’n Toekenning met vaste argumente, ’n uitdruklike opdragverbod of gedeaktiveerde pasgemaakte facts kan die uitkoms verander. Passiewe inventarisering behoort die beleidskandidaat aan te meld sonder om Facter uit te voer of fact-inhoud te lees.

Vir ’n presiese root-bevoegde sudo-skriptoekenning met `SETENV`, ondersoek kaal opdragname soos `find` en die effektiewe `PATH` nadat sudo-beleid en skripinisialisering toegepas is. ’n Bash-lêer wat ingesluit word, kan ook `enable -n [` uitvoer: [Bash soek dan `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) vir ’n eksterne `[` waar die skrip daardie opdrag later gebruik. Bevestig die toepaslike [sudoers-omgewings- en `secure_path`-reëls](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), enige `NOSETENV`/`NOEXEC`- of verbodinskrywings, die skrip- en ingeslote-lêervloei en ’n uitvoerbare soekgids wat die oproeper beheer. ’n Leesbare skrip wat ’n kaal opdrag bevat, is ’n leidraad vir hersiening, nie bewys van bevoorregte uitvoering nie; ondersoek dit sonder om die sudo-reël uit te voer.
- ’n Bevoorregte skrip wat ’n vaste URL met `curl` ophaal, kan steeds ’n oproeper-geselekteerde antwoord aanvaar as ’n toepaslike sudo-reël `http_proxy` behou en die versoek deur daardie instaanbediener gestuur word. As die skrip dan die antwoord aan ’n XML-ontleder oorgee wat eksterne entiteite oplos, kan ’n kwaadwillige antwoord lêers openbaar wat deur die bevoorregte proses gelees kan word. Gaan die presiese sudo-omgewingsbeleid, `no_proxy`-uitsluitings, aangevraagde URL, ontlederkonfigurasie en afvoerbestemming na; ’n instaanbedienerveranderlike of XML-ontleder alleen is nie ’n kwesbaarheid nie. Die [dokumentasie oor curl se instaanbediener-omgewing](https://everything.curl.dev/usingcurl/proxies/env.html) beskryf hoe die veranderlikes werk. Moenie netwerkversoeke maak of kwaadwillige XML tydens passiewe inventarisering ontleed nie.

### Bou- en pakketnutsgoed wat deur sudo loop

’n Onbeperkte sudo-toekenning vir Foundry se `forge` kan saak maak selfs wanneer die RunAs-identiteit ’n ander nie-root-gebruiker is. Saamstelleropsies soos `--use` kan ’n plaaslike uitvoerbare lêer kies, en `forge flatten -o` kies ’n uitvoerlêer. Gaan die geïnstalleerde Forge-weergawe, presiese sudo-argumente, toeganklike projek- en saamstellerpaaie, uitvoertoestemmings en effektiewe omgewing na voordat jy die toekenning as uitbuitbaar beskou. ’n Relatiewe helper-uitvoerbare lêer wat via `PATH` gevind word, is ’n weergawe- en omgewingsafhanklike roete, nie iets wat vir elke Forge-bouproses aanvaar kan word nie.<sup>[[23]](#references)[[24]](#references)</sup>

’n Onbeperkte root-bevoegde `pacman`-toekenning laat meer as pakketnavrae toe: `-U` aanvaar ’n plaaslike pakket, pakkette kan installasieskripte bevat en `--hookdir` kies ’n ander haakgids. Hersien die effektiewe sudo-reël, argumentbeperkings en uitsluitings voordat jy toets; passiewe inventarisering vereis nie dat ’n pakket geïnstalleer of ’n haak uitgevoer word nie.<sup>[[25]](#references)[[26]](#references)</sup>

’n Vaste sudo-shell-omhulsel kan ook ’n benoemde npm-afhanklikheid installeer en dan ’n Node-toepassing begin. Hersien sy presiese RunAs-reël, of die pakket reeds geïnstalleer is, die effektiewe `HOME` en npm `userconfig`, projekkonfigurasie of opdragreël-oorheersings, en of ’n laerbevoorregte gebruiker die register of pakket wat vir daardie naam teruggestuur word, beheer. [npm dokumenteer opsoek van `.npmrc` per gebruiker en per projek](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo se `HOME`-gedrag hang van die geïnstalleerde beleid en verspreiding af, dus word ’n gebruiker se skryfbare `.npmrc` moontlik deur die bevoorregte npm-proses gelees, of moontlik nie. As die pas geïnstalleerde pakket deur die bevoorregte toepassing ingevoer word, kan sy modulekode onder daardie toepassing se identiteit loop. ’n Vaste Python-ingangspunt kan steeds ’n module invoer wat die oproeper kan wysig of vervang, ook wanneer sudo die skrip as ’n **nie-root**-diensgebruiker uitvoer. Vir ’n letterlike `from utils import status`, hersien plaaslike `utils/__init__.py` en `utils/status.py` sowel as die pakketgids se toestemmings. Bevestig die skrip se invoerpad, presiese toegelate sudo-argumente en of die betrokke handeling daardie invoer bereik voordat jy die skryfbare lêer as ’n uitvoeringsroete beskou. Ondersoek lêers en toestemmings sonder om die skrip tydens inventarisering in te voer of uit te voer.<sup>[[2]](#references)[[3]](#references)</sup>

’n Presiese sudo-reël vir `python3 /absolute/script.py` vereis slegs ’n leesbare skrip; die lêer hoef nie uitvoerbaar te wees of ’n shebang te hê nie. Hersien ook **ontbrekende** plaaslike modules: as die skrip ’n module invoer waarvan die lêernaam in ’n oproeper-skryfbare skripgids geskep kan word, kan Python daardie lêer onder die RunAs-identiteit laai. Bevestig die effektiewe sudo-reël, die interpreteerder se werklike [module-soekpad](https://docs.python.org/3/library/sys_path_init.html), of die module ingebou of gevries is, en of die invoer bereik word. ’n Direkte sudo-reël vir die skrip het ander vereistes vir uitvoerbis en shebang. ’n Afsonderlike omhulsel wat deur die oproeper verskafte tekens ná `sudo -u account` byvoeg, vereis ook hersiening van die argumentvloei: ’n verdere `-u` in dié tekens is slegs relevant as die aangeroepte sudo-beleid die gevolglike identiteit toelaat. Statiese stringe alleen bewys nie een van die roetes nie.

### Apache wat deur sudo loop met ’n oproeper-beheerde konfigurasie

As ’n sudo-reël ’n bevoorregte `apachectl`-, `apache2ctl`- of `httpd`-aanroep met ’n oproeper-beheerde `-f`-konfigurasielêer toelaat, hersien daardie lêer en sy ouergidstoestemmings. Apache se [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule)-aanwysing neem ’n modulenaam gevolg deur die **modulelêernaam**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) laai ook ’n lêer. [`Include` en `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) kan die konfigurasie uitbrei of lêerinhoud deur foute blootstel. ’n Pasgemaakte omhulsel kan hierdie paaie valideer, voorregte laat val of argumente beperk, dus is ’n skryfbare konfigurasie ’n kandidaat vir hersiening eerder as bewys van kode-uitvoering. Gaan padkanonisering, simboliese skakels en aanwysingontleding na voordat jy ’n gevolgtrekking maak.

### nginx wat deur sudo loop met ’n oproeper-beheerde konfigurasie

’n Onbeperkte root-bevoegde `nginx`-reël kan toelaat dat [`-c ’n ander konfigurasie kies`](https://nginx.org/en/docs/switches.html). Hersien die presiese sudo-argumente en uitsluitings, of die oproeper die konfigurasie kan verskaf, en of die gevolglike meesterproses of werkers toegang tot beskermde paaie behou. ’n Gekose `root` saam met `autoindex` kan lêers via ’n nuwe luisteraar blootstel; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kan ’n bevoorregte lêerskryfpad bied, maar die DAV-module is nie by verstek gebou nie en die teenwoordigheid daarvan, luisteraarbereikbaarheid, lêertoestemmings en tydelike-lêergedrag moet nagegaan word. Die [`error_log`-aanwysing](https://nginx.org/en/docs/ngx_core_module.html#error_log) kan ook ’n gekose lêer as bestemming hê; die skryf van logboeke na ’n sensitiewe konfigurasielêer, soos `/etc/ld.so.preload`, vereis ’n effektiewe bevoorregte skrywer en ’n beheerbare logrekord voordat dit ’n voorregverhogingsroete word. Die aanduiding van die uitvoerbare lêer in `sudo -l` is ’n leidraad vir hersiening, nie bewys dat enige van dié roetes werk nie. Passiewe inventarisering behoort nie nginx te begin of te herkonfigureer nie.

### Patroonvergelyking in bevoorregte Bash-aanwysings

Wanneer ’n Bash-skrip wat deur sudo toegelaat word ’n waarde van die oproeper lees en dit met `[[ "$expected" == $entered ]]` nagaan, interpreteer Bash die ongekwoteerde regteroperand as ’n patroon. ’n Jokerteken kan dus die vergelyking slaag sonder dat die verwagte waarde bekend is. As die operand gekwoteer word (`[[ "$expected" == "$entered" ]]`), word dit as ’n letterlike string vergelyk. Hersien die presiese sudo-reël, of die aanporboodskap bereikbaar is en wat die skrip ná die vergelyking doen; die sintaksis alleen bewys nie ’n uitbuitbare roete nie. Moenie die verwagte waarde tydens inventarisering druk nie. Sien die [Bash-verwysing oor voorwaardelike konstruksies](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers wat deur sudo loop en ’n lêer aflaai en uitvoer

’n Onbeperkte root-bevoegde sudo-toekenning vir ’n pasgemaakte helper verdien ’n datavloei-hersiening as dit ’n oproeper-geselekteerde URL aanvaar, die antwoord op skyf skryf en daardie lêer later met ’n interpreteerder of shell uitvoer. [Sudoers laat arbitrêre argumente toe wanneer geen argumente in ’n opdraginskrywing gelys word nie](https://man7.org/linux/man-pages/man5/sudoers.5.html); ’n vaste uitvoerbare pad beperk nie wat die argumente kan kies nie. Bevestig die werklike URL-validering, uitvoerpad, suksesvertakking en daaropvolgende uitvoering in die geïnstalleerde helper. ’n Ooreenstemmende libcurl-invoer of drukbare string alleen bewys nie hierdie ketting nie.

Selfs ’n vaste uitvoerlêernaam kan tussen skryf en uitvoering vervang word wanneer die helper ’n **relatiewe pad in ’n oproeper-beheerde werkgids** gebruik. Die hernoeming of vervanging van ’n root-besitte lêer word deur skryftoegang en deurkruistoegang tot die gids, asook enige sticky-bit-beperkings, bepaal—nie bloot deur die lêer se modus nie; sien [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Gaan na of die helper later die pad heropen of die reeds oop lêerbeskrywer gebruik, en of dit na ’n vertroude gids verander voordat dit skryf. Ondersoek die sudo-beleid, helper en gidsmetadata passief; moenie die bevoorregte aflaai uitvoer of tydens inventarisering ’n wedloop probeer veroorsaak nie.

’n Root-sudo-aflaaihelper kan ook **argument**-inspuiting blootstel wanneer dit ’n Bash-opdragstring soos `curl <caller input> -o <fixed output>` bou. ’n Filter wat witspasie verwerp, laat steeds [Bash-krullerigehakiesuitbreiding](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) toe: ongekwoteerde kommageskeide elemente kan afsonderlike curl-argumente word. As die invoer curl voor die vaste `-o` bereik, kan ’n deur die oproeper verskafte uitvoeropsie die bestemming vir die eerste URL onder die helper se identiteit kies; [curl koppel uitvoeropsies in volgorde aan URL’s](https://curl.se/docs/manpage.html#-o). Bevestig die presiese shell, kwotering, invoervalidering, effektiewe sudo-reël, curl-argumentvolgorde en ondersteunde URL-skemas, en of die oproeper die afgelaaide grepe beheer of die resultaat kan lees. ’n PyInstaller-verpakte uitvoerbare lêer kan Python-toepassingslogika bevat, maar sy verpakkingsmerker of ’n `curl`-string alleen bewys nie hierdie datavloei nie. Hersien ’n beperkte vanlyn kopie wanneer dit gemagtig is; roetine-inventarisering behoort nie die helper uit te voer of aanvaller-geselekteerde data af te laai nie.

’n Root-sudo-shellskrip wat [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aanroep, kies slegs ’n ongebruikte naam; dit skep **nie** die lêer nie. As die skrip daardie naam later in ’n gids skep wat ’n ander gebruiker kan beïnvloed, dit heropen en die inhoud daarvan by ’n beskermde bestemming soos root se `authorized_keys` voeg, hersien ’n moontlike tydelike-lêerwedloop. Bevestig die presiese sudo-reël, gids- en lêereienaarskap, volgorde van skep en heropen, kernbeskerming en of die bevoorregte skryfbewerking werklik aanvaller-beheerde grepe gebruik. ’n `mktemp -u`-string of ’n skryfbare `/tmp` alleen bewys nie die wedloop nie. Ondersoek die skrip en padmetadata sonder om dit uit te voer of tydens inventarisering met die tydelike lêer te wedloop.

## Verdedigingsnotas

- Vermy die toekenning van interpreteerders of interaktiewe redigeerders deur sudo.<sup>[[1]](#references)</sup>
- Moenie generiese lêerskrywers soos `tee` met onbeperkte operande toelaat nie. Gebruik ’n root-besitte omhulsel wat ’n vaste bestemming kies en oproeper-beheerde paaie verwerp.<sup>[[2]](#references)</sup>
- Verkies vaste, root-besitte omhulsels wat een nou omskrewe administratiewe handeling uitvoer.<sup>[[1]](#references)[[2]](#references)</sup>
- As ’n interpreteerder onvermydelik is, beperk die presiese skrippad en voorkom gebruikerbeheerde argumente, skryfbare invoere, `PYTHONPATH` en onveilige omgewingsbehoud.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- As lêerwysiging nodig is, beperk die presiese lêerpad en oorweeg `sudoedit` met reggestelde sudo-weergawes en streng omgewingshantering.<sup>[[1]](#references)[[2]](#references)</sup>
- Hersien `SETENV`, `env_keep`, skryfbare werkgidse, skryfbare module-/invoerpaie, `NOEXEC`, `use_pty` en logging, maar moenie dit as ’n volledige sandbox beskou nie.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
