## Interpréteurs autorisés par sudo

Si `sudo -l` permet à un utilisateur d'exécuter un interpréteur en tant que root, considérez cela comme une exécution directe de code. Les interpréteurs sont conçus pour exécuter du code arbitraire ; une règle autorisant `python3`, `perl`, `ruby`, `lua`, `node` ou des binaires similaires équivaut généralement à l'exécution de commandes en tant que root, sauf si les arguments sont strictement limités et validés.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Procédure courante : commencez par lister les privilèges de l'utilisateur, puis exécutez une instruction Python avec l'option `-c` de l'interpréteur.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

D’autres exemples d’interpréteurs sont présentés ci-dessous ; les interpréteurs listés documentent l’exécution de code en ligne ou les API de processus enfants.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Le chemin exact compte. Si la règle sudo autorise `/usr/bin/python3`, utilisez ce chemin exact lors de la validation.<sup>[[2]](#references)</sup>

Un glob d’exécutable sudo tel que `/usr/bin/python*` peut également autoriser Python 2 pour un script écrit pour Python 3. Si le script atteint `input()` avec du texte contrôlé par l’appelant, [Python 2 évalue ce texte comme une expression](https://docs.python.org/2/library/functions.html#input) ; l’invocation explicite d’un interpréteur prend le pas sur le shebang du script. Vérifiez les binaires installés correspondant au glob, l’identité RunAs effective et la politique des arguments, les refus, ainsi que la possibilité d’atteindre la saisie, avant de considérer cela comme un chemin d’exécution.

Un chemin de script fixe dans une règle sudo permettant d’obtenir root ne limite pas ce que le script exécute. Pour un wrapper Bash lisible, vérifiez si sa première commande exécutable utilise un paramètre positionnel non cité tel que `$1` comme **mot de commande**, alors que sudo autorise l’appelant à choisir les arguments. Confirmez l’identité RunAs effective, la politique de mot de passe et des arguments, les refus ultérieurs et la branche réellement exécutée du script ; `NOEXEC`, une liste fixe d’arguments sûrs ou un wrapper qui valide sa commande peuvent changer le résultat. Pendant l’énumération, inspectez statiquement le court script au lieu de l’invoquer avec une commande de test.

Une règle sudo sans restriction permettant d’obtenir root pour `dotnet` mérite également un examen de l’interpréteur. Si un .NET SDK est installé, [`dotnet fsi` exécute du code F# de manière interactive ou depuis un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), et [`dotnet run` exécute un projet à partir de son code source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirmez d’abord l’identité RunAs effective et la politique exacte des arguments : une règle limitée à une sous-commande sûre particulière ou à une application de confiance constitue une autorisation différente, et une installation limitée au runtime peut ne pas inclure les commandes du SDK. Le nom de l’exécutable est un indice à examiner, pas une preuve d’exécution de code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Éditeurs autorisés par Sudo

Si `sudo -l` permet à un utilisateur d’exécuter un éditeur interactif en tant que root, considérez cela comme une surface d’exécution de commandes, et non comme une simple autorisation inoffensive de modifier des fichiers. Les éditeurs peuvent souvent exécuter des commandes shell, lire ou écrire n’importe quel fichier, ou appeler des outils externes depuis l’éditeur.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Procédure courante : répertoriez les privilèges de l’utilisateur, puis lancez avec sudo chaque éditeur ou pager autorisé.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Exécution de commandes avec Nano

Lorsque `nano` est autorisé via sudo, il peut être possible d’exécuter des commandes depuis l’interface de l’éditeur.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Saisissez ensuite une commande telle que `id` ou `/bin/sh` à l’invite de commande de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactif ne dispose pas de flux de terminal utilisables, cette forme de redirection redirige sa sortie standard et son erreur vers le descripteur 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La séquence exacte de touches peut varier selon la version de nano et les options de compilation, mais le problème de sécurité reste le même : l’éditeur s’exécute en tant que root et peut lancer des commandes externes.<sup>[[1]](#references)[[12]](#references)</sup>

### Autres échappements courants dans les éditeurs

Les éditeurs de type Vim permettent couramment d’exécuter des commandes via `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Les pagers tels que `less` peuvent également permettre l’exécution d’un shell.<sup>[[14]](#references)</sup>

Une règle sudo autorisant `apport-cli` en tant que root mérite le même examen du pager. Certaines versions d’Apport pouvaient ouvrir un rapport de plantage dans `less` avec une taille de terminal réglable par un attaquant ; le pager pouvait alors fournir un shell root si les conditions particulières liées à sudo et au pager étaient réunies. Vérifiez la règle sudo effective, la configuration du pager et le correctif du paquet de la distribution avant de considérer que la version seule est vulnérable. Consultez les métadonnées du paquet et de la politique sans provoquer de plantage ni ouvrir le rapport privilégié pendant l’énumération passive. [La fiche CVE d’Ubuntu](https://ubuntu.com/security/CVE-2023-1326) répertorie les versions corrigées des paquets propres à chaque version, y compris les correctifs rétroportés.

```text
!/bin/sh
```

## Autres risques liés aux règles sudo et doas

Commencez par `sudo -l`, `sudo -V` et toute politique `doas` applicable. Examinez ensemble la commande autorisée, l’utilisateur d’exécution, les arguments, l’environnement et les valeurs par défaut. L’autorisation d’exécuter une commande en tant que compte de service non-root peut tout de même exposer les fichiers de ce compte ou ouvrir une voie vers root.

Un script Python autorisé par sudo avec un chemin fixe peut quand même exécuter une commande shell sous l’identité RunAs si une entrée interactive, contrôlée par l’appelant, est concaténée dans [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Une liste de refus de ponctuation shell ne suffit pas à garantir la sécurité : [le shell reconnaît aussi la substitution de commande `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Vérifiez que les arguments autorisés atteignent la branche d’entrée, que l’entrée parvient à la commande shell sans validation sûre et que la politique sudo effective autorise l’utilisateur RunAs visé. Le chemin du script ou un appel à `os.system()` constitue seulement une piste à examiner ; inspectez le code source sans exécuter le script privilégié.

Une autorisation sudo effective d’exécuter `chattr` en tant que root peut supprimer l’attribut de fichier immuable (`i`), mais cela ne confère à lui seul ni un droit d’écriture ni une nouvelle identité. [Le manuel de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indique que cet attribut empêche les modifications et que seul root ou un processus disposant de `CAP_LINUX_IMMUTABLE` peut le changer. Vérifiez la politique exacte des arguments sudo et la prise en charge du système de fichiers, puis vérifiez séparément que l’appelant peut écrire dans le fichier une fois l’attribut supprimé et qu’un processus exécuté avec une identité supérieure l’utilise. Le remplacement d’un shell de connexion, par exemple, exige aussi que le compte cible accepte les identifiants et qu’une connexion réelle utilise ce shell. Lors de l’énumération, examinez la politique, les attributs de fichier et les permissions sans les modifier.

Si sudo demande à la fois un mot de passe et un code à usage unique, distinguez ces prérequis de l’autorisation d’exécuter la commande. Un fichier `.google_authenticator` lisible contient des données sensibles de graine, tandis qu’un ancien hash de mot de passe d’application ou de base de données n’est qu’un candidat pour le mot de passe actuel du compte ; aucun des deux ne prouve que l’autre facteur est accepté par la configuration PAM effective. Une fois autorisé, examinez précisément l’identité RunAs et les arguments : une autorisation root sans restriction pour RubyGems `gem` peut exposer sa commande d’éditeur ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mais pas une autorisation restreinte ou une authentification échouée. Une énumération passive doit indiquer les chemins et la politique sans afficher la graine, récupérer un mot de passe, générer un code ni exécuter la commande privilégiée.

Une autorisation sudo effective d’exécuter `knife` de Chef en tant que root ou avec une capacité root mérite un examen au niveau de l’interpréteur : [Chef indique que `knife exec -E` évalue localement une chaîne Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Vérifiez que la règle sudo effective autorise le sous-programme `exec` et l’argument `-E` fourni par l’appelant, l’identité RunAs visée ainsi que toute interdiction de commande ou tout argument fixe correspondant. Le binaire installé ou une règle limitée à d’autres sous-commandes ne constitue qu’une piste. Une énumération passive doit signaler la règle sans exécuter `knife`.

Une autorisation sudo exacte d’exécuter `msfconsole` en mode interactif avec une capacité root est tout aussi sensible : [GTFOBins décrit sa console `irb`](https://gtfobins.org/gtfobins/msfconsole/), qui peut hériter de l’identité sudo. Vérifiez l’utilisateur RunAs effectif, la liste des arguments autorisés, les interdictions de commande, `NOEXEC` ou les autres restrictions, le comportement de la console installée et la possibilité pour l’appelant de fournir une entrée interactive. La simple mise en évidence d’un chemin n’est qu’une piste ; une énumération passive ne doit pas lancer la console.

Sur FreeBSD, même une règle sudo limitée à `pkg update` et `pkg install *` en tant que root mérite un examen de la confiance accordée aux dépôts. Vérifiez si `/etc/hosts` est modifiable par l’appelant et si la configuration effective des dépôts activés utilise un nom d’hôte HTTP avec `signature_type: none`. [Le manuel de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indique que `none` désactive les vérifications de signature ; `pkg+http` à lui seul ne suffit pas à l’établir. Un paquet peut contenir des scripts d’installation ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)) : un appelant qui contrôle réellement le point de terminaison du dépôt et peut choisir un paquet peut donc franchir la limite root. Avant de conclure, vérifiez les substitutions de dépôt, la résolution SRV/des miroirs, les arguments sudo effectifs, le choix du paquet et l’exécution des scripts. Examinez la politique et les petits fichiers de configuration locaux sans rediriger de noms ni exécuter `pkg` pendant l’énumération.

Une autorisation sudo avec capacité root d’exécuter `apt-get update` et `apt-get upgrade` nécessite aussi un examen de la confiance accordée aux dépôts si sudo conserve un `http_proxy` contrôlé par l’appelant. Vérifiez si la configuration APT effective utilise réellement cette variable de proxy et quelles requêtes de dépôt activées elle peut affecter ; un proxy ne peut pas à lui seul remplacer les paquets provenant d’une archive authentifiée par une clé de signature approuvée. [Le manuel du transport HTTP d’APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) décrit la priorité des proxys, tandis qu’[apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documente les vérifications de signature, les dérogations pour les dépôts non sécurisés et la confirmation requise pour les paquets non authentifiés. Vérifiez l’identité RunAs et les arguments exacts de sudo, la politique d’authentification des dépôts, toute acceptation interactive requise et si la mise à niveau sélectionnée exécute des scripts de paquet en tant que root. Examinez passivement la politique et la configuration locale ; ne redirigez pas le trafic des paquets et ne lancez pas de mise à niveau pendant l’énumération.

Une règle sudo avec capacité root pour `snap install` peut créer une frontière entre paquet et code si ses arguments permettent à l’appelant de choisir un snap local et un mode d’installation permissif. [La documentation de Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) indique que `--dangerous` ignore les vérifications d’assertion des snaps locaux et que `--devmode` assouplit le confinement ; [un hook d’installation peut s’exécuter lors de l’installation initiale](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Avant d’affirmer qu’il y a accès à des fichiers hôte protégés, vérifiez la politique exacte sudo concernant les arguments et RunAs, qui contrôle le fichier snap, si snapd installé accepte ces modes, ainsi que l’identité effective et le confinement du hook. La présence d’un binaire `snap` ou d’une règle qui semble comporter un joker ne prouve pas cette chaîne. Une énumération passive ne doit ni installer de paquet ni exécuter son hook.

Pour une autorisation sudo exacte d’exécuter, en tant qu’utilisateur **non-root**, un binaire personnalisé qui lit des identifiants, commencez par examiner le binaire autorisé et ses permissions sans l’exécuter. Un contrôle de mot de passe intégré peut n’être visible qu’en caractères larges ; [GNU `strings` documente l’extraction 16 bits little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Une chaîne visible ne prouve pas qu’il s’agit du mot de passe accepté ni que la branche de réussite expose un identifiant actuel. Vérifiez séparément le comportement du binaire, l’accès du compte cible aux données protégées, la validité des identifiants et toute transition ultérieure de compte ou de groupe. Si ce compte appartient au groupe `docker`, vérifiez l’accès au socket et l’identité rootful ou rootless du daemon avant d’en déduire un accès root à l’hôte ; [Docker documente les implications de son groupe au niveau root](https://docs.docker.com/engine/install/linux-postinstall/). Une énumération courante doit signaler la règle sudo et l’appartenance au groupe sans exécuter le binaire ni en extraire les chaînes.

Une règle sudo avec joker pour les scripts de maintenance d’une application doit être examinée au-delà du chemin du script. Vérifiez si le script autorisé accepte des arguments sans restriction ou lit des paramètres modifiables par un compte d’application moins privilégié, puis suivez ces valeurs jusqu’aux commandes shell ou à l’environnement d’un sous-processus. Par exemple, le [`zmupdate.pl` de ZoneMinder construit une commande `mysqldump` et l’exécute via `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), tandis que [`zmdc.pl` copie le paramètre `ZM_LD_PRELOAD` dans `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) avant de lancer des daemons. Une règle sudo qui autorise l’un ou l’autre de ces scripts en tant que root peut franchir une limite de confiance si l’entrée correspondante est contrôlable et atteint ce code dans la version installée. Examinez la règle sudo effective, les droits sur la configuration de l’application et le code source du script ; le joker ou le paramètre seul n’est qu’une piste, pas une preuve d’exécution.

- `SETENV`, `env_keep`, `secure_path` et `LD_PRELOAD` peuvent transformer une commande autrement limitée en détournement d’importation, de bibliothèque ou de `PATH`. Consultez le [guide des variables d’environnement](../linux-basics/linux-environment-variables.md) et [l’abus de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Une autorisation `SETENV` exacte, avec capacité root, pour un wrapper shell mérite aussi un examen à un saut si le wrapper lance un script Python fixe avec un import littéral. `secure_path` restreint la recherche de commandes du shell, pas la [recherche de modules `PYTHONPATH` de Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) ; [`-E` et `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) indiquent à Python d’ignorer cette variable d’environnement. Avant d’y voir une exécution de code, vérifiez les tags et interdictions sudo effectifs, la branche du wrapper, les options de l’interpréteur, la résolution des imports et la présence d’un répertoire de recherche modifiable par l’appelant. Examinez statiquement les scripts courts ; n’exécutez pas le wrapper privilégié.

Une autorisation sudo exacte d’exécuter `neofetch ""` avec capacité root peut quand même charger une configuration shell si les valeurs par défaut sudo applicables conservent un `XDG_CONFIG_HOME` contrôlé par l’appelant. [Le chargeur de configuration de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) source `neofetch/config.conf` ou `neofetch/config` sous ce répertoire ; la liste d’arguments vide n’empêche pas cette recherche. Vérifiez le chargeur installé, l’identité RunAs et la politique d’arguments effectives, les éventuelles interdictions de commande, si sudo conserve réellement la variable choisie pour cette commande et si l’appelant contrôle un chemin de configuration lisible. Une variable conservée ou l’installation de Neofetch ne constitue qu’une piste. Examinez la politique et les métadonnées des fichiers sans exécuter la commande privilégiée ni afficher le contenu de la configuration ; voir [la gestion de l’environnement par sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Une règle sudo sans restriction pour `facter` avec capacité root mérite un examen distinct des facts personnalisés. [Puppet indique](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` charge des fichiers de facts Ruby depuis un répertoire choisi. Vérifiez si la règle sudo exacte autorise cette option, si la version de Facter installée l’accepte et si l’appelant contrôle le répertoire. Une autorisation avec arguments fixes, une interdiction explicite de commande ou la désactivation des facts personnalisés peut changer le résultat. Une énumération passive doit signaler la règle candidate sans exécuter Facter ni lire le contenu des facts.

Pour une autorisation sudo exacte d’exécuter un script avec capacité root et `SETENV`, examinez les noms de commande nus, comme `find`, ainsi que le `PATH` effectif après application de la politique sudo et l’initialisation du script. Un fichier Bash sourcé peut aussi exécuter `enable -n [` : [Bash recherche alors dans `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) une commande externe `[` lorsque le script utilise plus tard cette commande. Vérifiez les [règles d’environnement et `secure_path` de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) applicables, les entrées `NOSETENV`/`NOEXEC` ou les interdictions, le déroulement du script et des fichiers sourcés, ainsi que la présence d’un répertoire de recherche exécutable contrôlé par l’appelant. Un script lisible qui contient une commande nue est une piste, pas une preuve d’exécution privilégiée ; examinez-le sans utiliser la règle sudo.
- Un script privilégié qui récupère une URL fixe avec `curl` peut quand même accepter une réponse choisie par l’appelant si une règle sudo applicable conserve `http_proxy` et que la requête passe par ce proxy. Si le script transmet ensuite la réponse à un analyseur XML qui résout les entités externes, une réponse malveillante peut divulguer des fichiers lisibles par le processus privilégié. Vérifiez la politique exacte d’environnement sudo, les exclusions `no_proxy`, l’URL demandée, la configuration de l’analyseur et la destination de sortie ; une variable de proxy ou un analyseur XML ne suffit pas à constituer une vulnérabilité. La [documentation de l’environnement proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) décrit le comportement des variables. N’effectuez aucune requête réseau et n’analysez pas de XML hostile lors d’une énumération passive.
- Un script sudo avec capacité root qui construit un fichier PostScript à partir de données influencées par l’appelant puis exécute `ps2pdf -dNOSAFER` mérite un examen distinct du flux d’entrée. Ghostscript indique que cette option désactive SAFER jusqu’à `.setsafe`, ce qui autorise les opérations sur les fichiers permises par les droits du système d’exploitation du processus. Une requête SQL construite à partir d’un argument de l’appelant peut transmettre des lignes contrôlées par un attaquant au modèle PostScript, mais une chaîne de requête ou un appel à `ps2pdf` ne prouve pas à lui seul que les données atteignent la syntaxe PostScript exécutable. Vérifiez la règle sudo effective, le chemin exact entre l’entrée et le modèle, tout échappement, le comportement de la version installée de Ghostscript et la réactivation de SAFER avant l’interprétation du document. N’exécutez pas la conversion privilégiée pendant une énumération passive. Voir la [documentation de `-dNOSAFER` de Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Pour une règle sudo qui exécute un script shell, comparez les variables conservées au script lui-même. Une construction telle que `if $CHECK_CONTENT; then` exécute la valeur développée comme une commande ; la conservation de `CHECK_CONTENT` peut donc permettre l’exécution de commandes même si le chemin du script et ses arguments sont fixes. Il faut vérifier, pour la règle concernée, si la branche est atteignable et si l’environnement est réellement conservé.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script Python autorisé par sudo peut importer du code depuis un répertoire modifiable ou un fichier `.pyc` mis en cache. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md) détaille le cas du cache.
- Un script Python fixe autorisé par sudo à s’exécuter en tant que root peut quand même exposer un débogueur interactif. Des appels tels que `pdb.set_trace()` ou `pdb.post_mortem()` permettent d’exécuter des instructions Python dans le contexte du processus débogué si l’appelant peut atteindre le point d’arrêt ou le gestionnaire d’exception **et contrôler l’entrée du débogueur**. Vérifiez la règle sudo exacte pour RunAs, l’authentification et les conditions de branche, la possibilité d’atteindre l’exception, le propriétaire du terminal/de l’entrée et si le débogueur s’exécute dans ce même processus privilégié. Une requête socket qui déclenche une exception ne donne pas à elle seule accès à un débogueur rattaché à un autre terminal. [Python documente l’évaluation d’instructions par le débogueur et son mode post-mortem](https://docs.python.org/3/library/pdb.html) ; examinez statiquement le script au lieu de déclencher le gestionnaire privilégié pendant l’énumération.
- Un script Python fixe autorisé par sudo peut également lire un champ de profil dans une base de données ou un socket Unix et l’ajouter à une chaîne qui deviendra ensuite la **chaîne de format** de `str.format()`. [Les champs de remplacement peuvent référencer des attributs et des clés de dictionnaire](https://docs.python.org/3/library/string.html#format-string-syntax) ; un champ contrôlé par un attaquant peut donc inspecter les objets transmis à `format()` et exposer les données accessibles depuis ceux-ci si le résultat est affiché ou enregistré dans un emplacement lisible par l’appelant. Vérifiez l’identité RunAs effective de sudo, les droits d’écriture sur l’enregistrement concerné, le flux des données vers la chaîne de format, les objets fournis et la visibilité de la sortie. Il ne s’agit pas automatiquement d’une exécution de code, et une chaîne de format littérale et fiable avec des *valeurs* contrôlées par un attaquant est un cas différent. Un secret divulgué ne permet une transition vers un compte système que si ce compte l’accepte. Examinez le script et les permissions du socket sans exécuter l’opération privilégiée.
- Un wrapper Python avec capacité root peut transmettre une URL choisie par l’appelant à `Repo.clone_from` de GitPython. Si le wrapper active aussi `protocol.ext.allow=always` pour Git, un dépôt distant `ext::` peut lancer un helper externe. Vérifiez les arguments sudo exacts, la provenance de l’URL, la version du paquet GitPython et les correctifs du fournisseur, ainsi que l’activation explicite de protocoles non sûrs par le wrapper. GitPython a ajouté une [protection par défaut contre les protocoles non sûrs](https://github.com/gitpython-developers/GitPython/commit/2625ed9) dans la version 3.1.30 ; la version de l’exécutable `git` est un élément distinct. Un examen passif doit se limiter à lire la règle et une portion limitée du code source, sans lancer le clonage.
- Une autorisation sudo inter-utilisateurs pour un outil CLI de clonage de dépôts peut exposer une autre voie d’injection dans une chaîne shell. Vérifiez si l’argument de dépôt choisi par l’appelant parvient à [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js ou à un autre constructeur de commandes shell sans séparation sûre des arguments ; `exec` de Node transmet sa chaîne de commande à un shell. Vérifiez l’utilisateur RunAs exact, les sous-commandes et arguments autorisés, le code du wrapper installé et la validation des entrées. Le nom de l’outil de dépôt ou une règle sudo sans restriction ne prouve pas à lui seul une injection de commande. Examinez le wrapper sans lancer de clonage privilégié pendant l’énumération.
- Un wrapper personnalisé appartenant à root peut sembler sûr parce que ses binaires et ses scripts ne sont pas modifiables, alors que sa décision d’effectuer une action privilégiée peut dépendre d’un indicateur, d’une valeur d’API locale ou d’un état de service qu’un utilisateur non privilégié peut modifier. Remontez chaque condition à son entrée et à ses contrôles d’autorisation. Pendant l’énumération, examinez la configuration et les permissions sans modifier l’état opérationnel ; un appel à `systemd-run` dans le wrapper n’est pertinent que si la condition peut être influencée.
- Un client de sauvegarde autorisé par sudo en tant que root peut accepter un fichier de configuration choisi par l’appelant (par exemple, `npbackup-cli -c`). Vérifiez l’utilisateur d’exécution et les arguments autorisés exacts, puis déterminez si l’appelant contrôle le chemin de configuration, les chemins source de sauvegarde et les options de dépôt ou de lecture/restauration. Un secret de dépôt chiffré dans un fichier de configuration lisible peut quand même être utilisable par le client, mais la règle seule ne prouve ni l’accès au dépôt ni la divulgation de fichiers root. Vérifiez l’autorisation sans exécuter de sauvegarde ni en afficher le contenu.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) prend en charge `--password-command`, qui exécute un programme pour obtenir le mot de passe d’un dépôt. Si une règle sudo permet à un utilisateur moins privilégié d’exécuter restic en tant que root avec une commande de mot de passe choisie par l’appelant et une sous-commande qui nécessite le mot de passe, ce helper peut s’exécuter en tant que root. Examinez les arguments sudo exacts et les exclusions ; n’exécutez ni le helper ni une commande de sauvegarde uniquement pour vérifier cette condition.
- Une autorisation privilégiée d’exécuter `restic backup` peut aussi franchir une limite de lecture de fichiers si les motifs d’arguments sudo permettent à l’appelant de choisir à la fois la source et un dépôt qu’il peut ensuite lire et déchiffrer. [Les jokers d’arguments sudoers peuvent correspondre aux espaces et aux barres obliques](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) ; examinez donc les jokers finaux au lieu de supposer qu’un préfixe de dépôt fixe restreint la source. [Restic peut sauvegarder vers des dépôts locaux et distants](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mais un dépôt local peut contenir des objets nouvellement écrits qui sont réservés à root ; avant d’y voir une divulgation, vérifiez la politique sudo effective, l’accès au backend, le mot de passe du dépôt et les permissions des objets générés. Une clé SSH sauvegardée ne donne accès que si le compte de destination l’accepte. Ne lancez pas de sauvegarde pour tester cela lors d’un examen passif.
- Une commande de maintenance ou de sauvegarde personnalisée sans restriction peut accepter un chemin de sortie ou disposer de son propre ordonnanceur de tâches. Pour une voie d’écriture de fichier, vérifiez la règle sudo exacte et l’utilisateur d’exécution, puis si l’appelant contrôle à la fois les données et la destination. Pour une voie de commande planifiée, vérifiez l’identité d’exécution de l’ordonnanceur, l’entrée de commande et tout contrôle supplémentaire de mot de passe ou d’autorisation. Le nom de la commande ou `NOPASSWD` ne prouve aucune de ces voies. Voir [l’écriture dans des fichiers appartenant à root](../interesting-files-permissions/write-to-root.md) et [cron et les timers systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Une commande fixe autorisée par sudo peut quand même charger un fichier de configuration prévisible depuis un répertoire partagé modifiable. Vérifiez si l’appelant peut remplacer ce fichier et si ses champs source et destination contrôlent une récupération ou une copie privilégiée. Une URL de fichier local peut exposer des données lisibles uniquement par le compte RunAs de sudo ; une source contrôlée par l’appelant associée à une destination protégée peut créer une voie d’écriture. Vérifiez la gestion des URL par le programme installé, les contrôles du chemin de destination, la règle sudo effective et l’accessibilité de la sortie. Un chemin de configuration modifiable dans `/tmp` est seulement une piste ; examinez le binaire et les métadonnées du fichier sans lancer le transfert privilégié.
- Une règle sudo pour `git apply` peut permettre au compte RunAs d’écrire des fichiers sélectionnés par un patch contrôlé par l’appelant. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permettait à un patch conçu à cet effet de créer un lien symbolique puis d’écrire en dehors de l’arborescence de travail, même lorsque la commande n’acceptait pas `--unsafe-paths`. Vérifiez la règle effective d’arguments sudo, la source du patch, l’accès au répertoire de travail pour le compte RunAs et la correction Git installée ou le rétroportage du fournisseur. Une règle sans restriction qui autorise `--unsafe-paths` présente un risque explicite distinct ; ni une version de Git ni une autorisation `git apply` ne prouvent à elles seules qu’un fichier protégé peut être modifié. N’appliquez pas de patch non fiable pendant l’énumération passive.
- Une règle sudo avec capacité root pour `clamscan --debug` peut franchir une limite de lecture si un utilisateur moins privilégié peut fournir une image DMG et que l’analyseur installé est affecté par [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), qui pouvait divulguer le contenu de fichiers dans la sortie de débogage. Vérifiez les arguments autorisés exacts et le chemin d’analyse, le contrôle de l’entrée, le compte RunAs effectif, les correctifs/rétroportages du moteur et la visibilité de la sortie pour l’appelant. Si une règle plus large autorise `--file-list`/`-f`, examinez séparément ce comportement ; une politique limitée à `--debug <scan-path>` ne l’autorise pas. Examinez la politique et les métadonnées du paquet sans analyser un fichier conçu à cet effet ni afficher de sortie protégée pendant l’énumération.
- Une règle sudo avec capacité root qui ouvre une image disque chiffrée choisie par l’appelant, ainsi qu’une seconde règle qui monte le device mapper obtenu, peut importer des fichiers contrôlés par l’appelant dans l’espace de noms de montage de l’hôte. Vérifiez les deux règles effectives et leurs arguments, le contrôle de l’image et du nom du mapper, le point de montage réel ainsi que le propriétaire et le mode des fichiers obtenus. Une transition SetUID nécessite en plus un exécutable accessible, des options de montage qui la respectent (`nosuid` la bloque) et une politique de processus ou MAC applicable ; ouvrir ou monter une image n’est qu’une piste. Une voie distincte via une sauvegarde existante nécessite sa véritable clé et un secret utile lisible à l’intérieur. Examinez la politique et les chemins sans ouvrir ni monter d’image pendant l’énumération passive. Voir le [manuel de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) et les [options de montage](https://man7.org/linux/man-pages/man8/mount.8.html).
- Une règle sudo avec capacité root pour un script shell ou Python mérite un examen du répertoire de travail si le script invoque `./helper` sans d’abord se déplacer dans un répertoire fixe. Une liste Python telle que `['./helper']` transmise à `subprocess.run` peut présenter le même comportement relatif au répertoire de travail choisi par l’appelant. Celui-ci peut être en mesure de choisir un répertoire modifiable et d’y placer un exécutable portant ce nom relatif ; la présence d’un chemin absolu ailleurs dans le script ne protège pas cet appel. Avant d’y voir une exécution de code, vérifiez la règle effective, `runchdir` ou toute autre politique de changement de répertoire, le déroulement du script et l’accessibilité de la branche, l’existence d’un répertoire modifiable et exécutable, ainsi que les restrictions de montage/`NOEXEC`. Si le script est illisible, son comportement reste inconnu jusqu’à l’examen de son code par une voie autorisée. Examinez les scripts statiquement au lieu d’exécuter le helper. Le [manuel de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documente la politique de répertoire de travail.
- Un validateur Python fixe avec capacité root peut quand même évaluer un fichier de données choisi par l’appelant. [La documentation de `eval()` de Python met en garde contre les entrées non fiables](https://docs.python.org/3/library/functions.html#eval) : une vérification du suffixe de l’entrée, un préfixe arithmétique ou une branche de validation ne constituent pas une sandbox si l’expression restante atteint `eval`. Avant d’y voir une voie d’exécution, vérifiez la règle sudo effective, la possibilité pour l’appelant de choisir et contrôler le fichier exact, les conditions des branches de l’analyseur, la construction de l’expression et l’identité du processus privilégié. La présence de `eval` dans un script lisible n’est qu’une piste ; examinez le code source et les permissions des fichiers sans exécuter le validateur ni soumettre d’expression de test pendant l’énumération.
- Un wrapper Ruby sudo avec capacité root qui lit un nom de fichier YAML relatif, tel que `YAML.load(File.read("dependencies.yml"))`, peut charger les données depuis le répertoire de travail de l’appelant, sauf si le wrapper ou la politique sudo fixe ce répertoire. Vérifiez les arguments autorisés exacts, les permissions du répertoire et du fichier, ainsi que le comportement de Psych installé : les anciennes implémentations de `YAML.load` pouvaient désérialiser des objets Ruby arbitraires, tandis que les versions récentes limitent les classes par défaut. Un appel statique n’est qu’une piste ; vérifiez que le fichier provient bien d’un répertoire modifiable par l’appelant et que le chargeur installé accepte les classes dangereuses. Préférez `safe_load` avec une liste d’autorisation explicite et minimale de classes pour les entrées non fiables. Voir la [documentation de Psych pour Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) et la [documentation de Psych pour Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Une autorisation sudo exacte `sudo go run /absolute/file.go` avec capacité root mérite un examen du répertoire de travail lorsque le code Go lit un fichier WASM relatif et peut exécuter un script shell relatif après avoir examiné son résultat. Vérifiez l’identité RunAs effective, les arguments et interdictions de commande, l’existence d’un répertoire courant modifiable par l’appelant, le flux des données WASM jusqu’à la branche et si cette branche invoque le helper. Un `runchdir` sudo fixe, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) peut modifier l’emplacement de recherche. Une cooccurrence statique n’est qu’une piste ; examinez le code source sans exécuter Go, WASM ni le helper.
- `sudoedit` et les jokers d’arguments nécessitent des vérifications précises de version et de règle ; la [checklist](linux-privilege-escalation-checklist.md) inclut le problème de modification de fichiers par sudoedit. Pour une autorisation `sudoedit` inter-utilisateurs sur un chemin avec joker, examinez le paramètre effectif `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, la cible résolue et les personnes pouvant remplacer chaque entrée parente. Le premier peut autoriser le suivi d’un lien symbolique, tandis que la désactivation du second supprime les vérifications des répertoires modifiables ; aucun de ces paramètres ne suffit à établir l’écriture dans le fichier d’un autre utilisateur. Avant de conclure, vérifiez la politique sudo installée et les arguments exacts correspondants. Voir les [définitions des options sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Dans une règle de commande sudoers, un joker d’argument peut correspondre aussi bien aux espaces qu’aux caractères de chemin. Une règle pour une commande capable de lire des fichiers, avec un argument tel que `/restricted/*`, peut donc accepter un argument de fichier supplémentaire après un préfixe correspondant. Examinez l’utilisateur RunAs exact, le chemin de commande, le motif d’argument et les interdictions ultérieures ; une lecture de fichier démontrée n’implique pas l’exécution de commande. Le [manuel de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue les jokers d’arguments de ceux des chemins de commande.
- Un motif d’argument qui ressemble à un chemin peut aussi correspondre à `../`. Par exemple, une règle `node /opt/scripts/*.js` avec capacité root peut autoriser un fichier JavaScript contrôlé par l’appelant situé hors de `/opt/scripts` si le chemin fourni commence toujours par `/opt/scripts/` et se résout via des segments de répertoire parent. Il s’agit d’un joker d’**argument** ; le joker du chemin de commande de l’exécutable Node suit d’autres règles concernant les barres obliques. Avant de conclure à une exécution de code, vérifiez la règle effective, les interdictions ultérieures, la résolution du chemin, le contrôle du fichier cible et toute restriction sudoers par expression régulière ou digest. Voir les [règles de joker sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) et la [documentation de la ligne de commande Node](https://nodejs.org/api/cli.html).
- Les archiveurs et autres utilitaires peuvent avoir des hooks d’exécution. Comparez les arguments exacts autorisés aux entrées de [GTFOBins](https://gtfobins.github.io/) au lieu de supposer que seuls les shells ou les interpréteurs exécutent des commandes.
- Une règle `qpdf` sans restriction avec capacité root peut exposer un fichier privilégié via des pièces jointes PDF : qpdf 10.2 et versions ultérieures prennent en charge `--empty` et `--add-attachment file ... --` avec un PDF de sortie. Si le processus privilégié peut lire la source choisie et écrire le PDF dans un chemin accessible à l’appelant, celui-ci peut contenir les octets de la source. Avant de conclure qu’une divulgation de fichiers est possible, examinez les arguments sudo effectifs et les exclusions, la version de qpdf, l’accès à la source et le chemin de sortie. La lecture d’une clé SSH root n’est utile pour se connecter que si cette clé est valide et si l’authentification SSH root est autorisée. Voir les [options de pièces jointes de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La réutilisation d’un horodatage sudo dépend de la politique du cache, de l’utilisateur propriétaire, du terminal/de la session et des permissions. Le [guide d’escalade de privilèges](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) décrit les vérifications.
- `doas` possède ses propres règles et sa propre configuration. Vérifiez les commandes autorisées et les chemins de configuration modifiables comme indiqué dans la [section doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Outils de build et de paquets exécutés par sudo

Une autorisation sudo sans restriction pour `forge` de Foundry peut être importante même si l’identité RunAs est celle d’un autre utilisateur non-root. Des options du compilateur comme `--use` peuvent sélectionner un exécutable local, et `forge flatten -o` sélectionne un fichier de sortie. Avant de considérer cette autorisation comme exploitable, vérifiez la version de Forge installée, les arguments sudo exacts, l’accessibilité du projet et des chemins du compilateur, les permissions de sortie et l’environnement effectif. Un exécutable helper relatif trouvé via `PATH` constitue une voie dépendante de la version et de l’environnement, et non une propriété à supposer pour toutes les compilations Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Une autorisation `pacman` sans restriction avec capacité root permet davantage que de simples requêtes de paquets : `-U` accepte un paquet local, les paquets peuvent contenir des scripts d’installation et `--hookdir` sélectionne un autre répertoire de hooks. Examinez la règle sudo effective, les restrictions d’arguments et les exclusions avant tout test ; une énumération passive n’a pas besoin d’installer un paquet ni d’exécuter un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fixe autorisé par sudo peut aussi installer une dépendance npm nommée puis lancer une application Node. Examinez sa règle RunAs exacte, si le paquet est déjà installé, les valeurs effectives de `HOME` et de `userconfig` npm, la configuration du projet ou les substitutions de la ligne de commande, ainsi que la possibilité pour un utilisateur moins privilégié de contrôler le registre ou le paquet renvoyé pour ce nom. [npm documente la recherche de `.npmrc` par utilisateur et par projet](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/) ; le comportement de `HOME` de sudo dépend de la politique installée et de la distribution, de sorte qu’un fichier `.npmrc` modifiable par un utilisateur peut ou non être lu par le processus npm privilégié. Si le paquet nouvellement installé est importé par l’application privilégiée, son code de module peut s’exécuter sous l’identité de cette application. Les scripts exécutés à l’installation constituent une voie distincte, dépendante de la version et de la configuration ; [npm documente leur cycle de vie et la gestion des utilisateurs](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un chemin `.npmrc` ou une ligne `npm install` n’est qu’une piste. Examinez la règle, le wrapper court, les chemins de configuration et la provenance du paquet sans installer ni démarrer l’application pendant l’énumération passive.

Une autorisation root de `pip` ou `pip3 download` constitue aussi une piste d’examen de build de paquet lorsque ses arguments permettent à l’appelant de choisir une distribution source non fiable, même si le motif d’URL la limite à un service local et à un suffixe `.tar.gz`. `pip download` accepte des URL d’archives et résout les métadonnées des paquets ; la préparation d’une distribution source peut invoquer son backend de build ou du code `setup.py` historique avant même que l’archive ne soit simplement enregistrée. Vérifiez l’identité RunAs et la règle d’arguments sudo exactes, la possibilité pour l’appelant de publier ou remplacer l’archive choisie et si cette version de pip prépare effectivement ses métadonnées. Une archive ou une wheel fixe et fiable n’établit pas cette voie. Ne récupérez ni ne construisez de paquet non fiable pendant une énumération passive. Voir la [commande download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), l’[interface du système de build](https://pip.pypa.io/en/stable/reference/build-system/) et les [conseils d’installation sécurisée](https://pip.pypa.io/en/stable/topics/secure-installs/).

Une règle sudo autorisant `pip install` avec un chemin de projet local choisi par l’appelant crée une frontière de build plus directe. [pip accepte les répertoires de projets locaux](https://pip.pypa.io/en/stable/topics/local-project-installs/) et invoque leur système de build ; le [backend de build exécute les hooks de build contrôlés par le projet](https://pip.pypa.io/en/stable/reference/build-system/). Avant d’y voir une exécution de code privilégiée, vérifiez l’identité RunAs effective, les restrictions d’arguments et les interdictions exactes, le contrôle du projet choisi et le comportement de pip/backend installé. Un projet fixe et fiable ou une règle qui exclut les chemins choisis par l’appelant n’établit pas cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant une énumération passive.

Une autorisation `easy_install` sans restriction avec capacité root constitue une piste similaire concernant les builds de paquets historiques. [Setuptools indique](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) qu’Easy Install accepte un répertoire de projet local et construit les distributions source ; un projet contrôlé par l’appelant peut exécuter son `setup.py` pendant ce build sous l’identité sudo. Vérifiez le compte RunAs effectif, la commande et les restrictions d’arguments exactes (y compris les interdictions ultérieures), le contrôle du projet choisi et le comportement de l’outil installé. Un projet fixe et fiable ou une politique qui n’autorise pas de source choisie par l’appelant n’établit pas cette voie. Examinez la règle et les métadonnées du projet sans installer de paquet pendant l’énumération.

Un wrapper Python autorisé par sudo qui utilise `setuptools.package_index.PackageIndex.download` avec une URL choisie par l’appelant relève d’un autre cas que `pip download` : [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) décrit, dans les versions concernées antérieures à 78.1.1, un nom de fichier dérivé de l’URL qui sort du répertoire de téléchargement prévu et est écrit avec les permissions du processus. Vérifiez l’identité RunAs et la règle d’arguments sudo effectives, que le wrapper transmet l’URL de l’appelant à cette API précise, le build installé ou le rétroportage du fournisseur, ainsi que la résolution du chemin obtenu. Une chaîne de version ou un répertoire de téléchargement modifiable ne suffit pas à établir une écriture arbitraire. Examinez le wrapper court et les métadonnées du paquet sans récupérer l’URL ni écrire de fichier pendant l’énumération.

Un wrapper de build autorisé par sudo qui transmet à PyInstaller un fichier `.spec` choisi par l’appelant nécessite le même examen de la limite de confiance. Un fichier spec PyInstaller est du Python exécutable évalué pendant le **build**, et ses entrées `datas` peuvent intégrer à un artefact des fichiers lisibles par l’identité de build. Vérifiez l’utilisateur RunAs exact, les règles sudo concernant les arguments et les interdictions, le traitement des chemins et des branches par le wrapper, le contrôle du fichier spec choisi et l’accès à l’artefact obtenu. Autoriser simplement une entrée `.py` ou trouver PyInstaller installé ne prouve pas que l’appelant contrôle le fichier spec ni qu’il y a exécution privilégiée. Un examen passif doit se limiter à lire un fichier wrapper de taille limitée et les métadonnées ; il ne doit pas lancer de build. Voir la [documentation des fichiers spec de PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Chargeurs de presets et de plugins exécutés par sudo

Les outils Python qui acceptent un preset ou un répertoire de plugins choisi par l’appelant peuvent importer du code avec les privilèges accordés par sudo. Par exemple, BBOT accepte un preset avec `-p`, et sa [documentation des modules personnalisés](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) décrit les entrées `module_dirs` qui sélectionnent des répertoires de modules Python supplémentaires. Si la règle sudo effective autorise un preset choisi par l’appelant et que celui-ci contrôle un module dans le répertoire sélectionné, l’import peut exécuter du code en tant qu’utilisateur privilégié, potentiellement avant que l’outil ne rejette un module invalide. Vérifiez la version installée, la politique exacte de sudo pour RunAs et les arguments, ainsi que le propriétaire du preset et des chemins de modules sans charger le module pendant l’énumération.

### Outil en ligne de commande Backdrop exécuté par sudo

[Bee](https://github.com/backdrop-contrib/bee) est un outil en ligne de commande PHP pour Backdrop CMS. Ses commandes `eval` (`php-eval`) et `php-script` peuvent exécuter du PHP fourni par l’appelant. Une règle sudo qui autorise l’exécutable Bee en tant que root avec des arguments sans restriction peut donc exposer une exécution de code root lorsque Bee peut initialiser une installation Backdrop. Exécutez-le depuis le répertoire du site ou sélectionnez un site avec l’option globale `--root=<directory>` ; la simple présence de Bee ou d’un fichier `settings.php` de Backdrop ne prouve ni l’autorisation sudo, ni l’existence d’un site utilisable, ni la réussite de l’initialisation. Avant tout test, examinez la règle sudo effective, les éventuelles exclusions de commande, l’identité de l’exécutable et l’accès au site. Pendant une énumération passive, inspectez la règle et les chemins de fichiers sans invoquer Bee. Voir le [journal des modifications des commandes Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) pour l’ajout des commandes PHP.

### Serveurs de terminal exécutés par sudo

`mosh-server` démarre un serveur de terminal interactif en tant qu’utilisateur qui l’invoque. Il choisit un port UDP élevé et une clé de session, indique les deux à l’appelant et lance normalement le shell de connexion de cet utilisateur lorsqu’un client se connecte. Une autorisation sudo sans restriction de `mosh-server` avec capacité root constitue donc une piste à examiner pour l’obtention d’un shell, même si la commande du serveur se détache. Vérifiez l’identité RunAs effective, les arguments et exclusions autorisés, le binaire installé, le shell, la disponibilité du client et l’accès UDP. Une énumération passive doit examiner la règle sudo sans démarrer de serveur ni afficher de clé de session active. Voir le [manuel du serveur Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) et les [notes de conception en amont](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers de sauvegarde privilégiés qui réécrivent le fichier de tâches de l’appelant

Un wrapper shell exécuté en tant que root peut accepter un fichier de tâches choisi par l’appelant, supprimer `../` des chemins source, vérifier que chaque résultat commence par un répertoire autorisé, réécrire le fichier de tâches puis transmettre son *chemin* à un programme de sauvegarde. Examinez le chemin transformé après résolution canonique complète : un seul passage de remplacement de chaîne peut faire apparaître une nouvelle séquence de traversée qu’une vérification lexicale de préfixe accepte. Vérifiez aussi si le programme de sauvegarde lit les données transformées en mémoire ou rouvre le fichier. S’il le rouvre, un échec de réécriture peut laisser l’entrée d’origine intacte.

Sous Linux, `fs.protected_regular` peut interdire une écriture `O_CREAT` dans le fichier ordinaire d’un autre utilisateur situé dans un répertoire sticky accessible à tous. Cette interdiction est protectrice, mais un wrapper shell qui ignore l’erreur d’écriture peut quand même continuer avec le fichier de tâches d’origine. Vérifiez ce paramètre, le propriétaire du fichier et du répertoire, et si le wrapper s’arrête en cas d’échec. Ce chemin n’est qu’un candidat à la divulgation de fichiers si la règle sudo effective autorise le wrapper en tant qu’utilisateur privilégié, si l’appelant contrôle l’entrée des tâches et une destination de sauvegarde lisible, et si l’utilitaire de sauvegarde inclut réellement les sources protégées. Examinez ces conditions sans exécuter la sauvegarde pendant l’énumération.

### Jokers d’arguments sur les outils réseau privilégiés

Dans une règle sudo pour `tcpdump`, un `*` dans le **motif d’arguments** peut correspondre aux espaces et aux barres obliques ; une restriction qui ressemble à un chemin peut donc quand même autoriser du texte d’option supplémentaire. C’est différent d’un joker dans le chemin de l’exécutable de la commande ; examinez la règle RunAs complète et les éventuelles interdictions ultérieures. Si des options peuvent être injectées, l’invocation autorisée et la [sémantique des options de `tcpdump` installé](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) déterminent si `-F`, `-V`, `-r`, `-w` ou `-Z` offre une primitive de lecture/écriture utile. `-V` lit une liste de noms de fichiers de capture, pas un fichier arbitraire destiné à être affiché de façon générale. AppArmor ou une autre politique MAC peut bloquer l’accès aux fichiers même si sudo autorise la commande ; la présence d’un fichier de profil sur le disque ne prouve pas que le profil est chargé ou appliqué. Examinez passivement l’autorisation et la politique avant de conclure. Le [manuel de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) décrit cette distinction entre jokers.

Une règle sudo avec capacité root qui ne liste que l’exécutable `tcpdump`, sans restriction d’arguments, mérite aussi un examen. Le [manuel de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) décrit `-z` comme une commande exécutée après une rotation déclenchée par `-C` ou `-G` sur une capture enregistrée ; `-Z` ou une valeur par défaut définie à la compilation peut abandonner les privilèges avant l’exécution de cette commande. Vérifiez la règle sudo effective, la version installée, le comportement de réduction des privilèges et la possibilité qu’une rotation ait lieu avant d’y voir une voie d’escalade. Une règle mise en évidence est une piste, pas une preuve d’exécution de commande en tant que root.

### Wrappers Nmap exécutés par sudo

Lorsque le chemin `nmap` autorisé par sudo est un wrapper shell, examinez le chemin exact autorisé et chaque option qu’il transmet. Bloquer la forme familière `--script` ne bloque pas nécessairement le chargement de code NSE : le [`--datadir` de Nmap](https://nmap.org/book/man-misc-options.html) sélectionne les fichiers de données, et NSE [charge `nse_main.lua`](https://nmap.org/book/nse-implementation.html) depuis le répertoire de données sélectionné lorsque les scripts sont activés. Certaines versions installées acceptent aussi des formes alternatives d’options longues ; comparez donc les restrictions à l’analyseur réel de ce binaire. [`--excludefile`](https://nmap.org/book/man-target-specification.html) constitue une surface de lecture de fichiers distincte ; les erreurs d’analyse peuvent révéler du texte. Vérifiez la règle sudo effective, la logique du wrapper, la version de Nmap, le contrôle du répertoire et la politique MAC sans lancer de scan pendant l’énumération.

### Hooks Mercurial pull exécutés par sudo

Même avec une source fixe dans `sudo hg pull /fixed/source`, le dépôt **receveur** dépend toujours du répertoire courant, sauf si la commande le fixe avec `-R`. Un dépôt receveur contrôlé par l’appelant peut définir des hooks dans `.hg/hgrc`, et un hook peut s’exécuter en tant qu’utilisateur RunAs de sudo. [Mercurial ignore la configuration de dépôt appartenant à un utilisateur ou groupe non fiable](https://mercurial-scm.org/help/topics/config) ; avant d’y voir une exécution de code, examinez donc les utilisateurs/groupes de confiance du compte RunAs et le répertoire de travail exact. La lecture de la politique et de la configuration suffit à un examen passif ; n’effectuez pas de pull et n’invoquez pas de hook lors de l’énumération.

### Hooks Git pull exécutés par sudo

Pour une autorisation root exacte de `sudo git pull`, vérifiez aussi le dépôt **receveur** sélectionné par le répertoire de travail. Un dépôt appartenant à l’appelant peut contenir un hook exécutable `post-merge`, qui s’exécute avec l’identité du processus Git lorsqu’un pull effectue réellement une fusion réussie ; [Git documente ce hook](https://git-scm.com/docs/githooks) ainsi que [le comportement de pull en mode fusion ou rebase](https://git-scm.com/docs/git-pull). Vérifiez la règle sudo effective et le répertoire courant, le chemin du hook actif et ses permissions, ainsi que la possibilité d’effectuer une fusion avec de nouveaux commits. Un pull échoué, sans effet ou limité au rebase ne prouve pas cette voie de hook. Examinez la politique et les métadonnées du dépôt sans exécuter le pull privilégié.

### Copies d’archives rsync exécutées par sudo

Pour `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` dans le **motif d’arguments sudoers** peut correspondre aux espaces et autoriser une option supplémentaire entre la source et la destination. Cela diffère de l’expansion shell des noms de fichiers. Si l’appelant peut alimenter la source et que le processus rsync privilégié peut écrire dans la destination, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) peut demander des propriétaires privilégiés tandis que le mode archive préserve les bits de permission, ce qui peut créer un fichier SetUID appartenant au compte visé. Vérifiez la [sémantique exacte des jokers sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la version de rsync, les interdictions ultérieures, l’option `nosuid` du système de fichiers et la politique MAC. Une règle correspondante est une piste, pas une preuve d’escalade de privilèges réussie.

### Export de règles de filtrage de paquets exécuté par sudo

Une autorisation sans restriction avec capacité root pour `iptables` et `iptables-save` (ou la paire `ip6tables` correspondante) mérite un examen de l’écriture de fichiers. Le match `comment` accepte du texte de règle choisi par l’appelant, tandis que `iptables-save -f` écrit l’ensemble des règles sérialisées dans un chemin sélectionné.<sup>[[20]](#references)[[21]](#references)</sup> L’existence d’une charge utile utile dépend de la manière dont le backend installé sérialise les commentaires et de l’acceptation, par le fichier de destination, d’autres lignes dans l’export ; `iptables-save` seul ne fournit pas un contenu arbitraire choisi. Vérifiez l’identité RunAs sudo exacte, les arguments et exclusions, l’extension de match disponible, le backend et les permissions de destination. Pendant l’énumération, examinez l’autorisation sans modifier les règles du pare-feu ni écrire de fichier.

### Répertoire de journalisation privilégié de Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) concernait les versions de Below antérieures à 0.9.0 qui créaient un répertoire `/var/log/below` accessible en écriture à tous. Si un service ou une commande sudo autorisée exécute une version affectée en tant que root, un utilisateur capable d’écrire dans un répertoire de journalisation non-sticky et d’y accéder peut être en mesure de remplacer une entrée de journal par un lien symbolique avant que le processus privilégié ne l’ouvre. Examinez l’état des correctifs du paquet installé, le chemin d’exécution privilégié exact, l’accès effectif au répertoire, le sticky bit et les ACL, ainsi que les métadonnées de `/var/log/below/error_root.log`. Un chemin accessible en écriture à tous ou une règle sudo seule ne suffit pas à établir la chaîne complète. Un répertoire sticky ou un rétroportage du fournisseur change l’évaluation. Une énumération passive doit se limiter à l’examen des métadonnées ; il n’est pas nécessaire de créer un lien ni d’exécuter le programme privilégié.

### Collecte privilégiée de bundles de support à partir d’entrées modifiables

Un script de profil de support autorisé par `sudo` peut lire en tant que root des chemins de journalisation fixes et copier leur contenu dans une archive de profil. Examinez le script réel pour repérer les lectures de fichiers, puis vérifiez si l’appelant peut remplacer un chemin source ou une entrée de répertoire parent par un lien symbolique. Si la lecture privilégiée suit ce lien et que l’archive obtenue est lisible par l’appelant, un fichier protégé peut être divulgué. L’autorisation sudo, un chemin source modifiable, la lecture privilégiée et une sortie lisible doivent tous être présents ; un journal ou un nom de profil modifiable ne suffit pas. Examinez les permissions effectives et les métadonnées des liens sans remplacer de fichiers ni générer de profil pendant l’énumération. Les [conseils de support de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentent son script de profil exécuté en tant que root et son archive de sortie, illustrant pourquoi ces bundles doivent avoir des entrées et un accès de sortie restreints.

### Scripts Python de restauration d’archives exécutés en tant que root

Une règle sudo étroitement limitée à un script Python de restauration nécessite tout de même d’examiner son entrée d’archive. Si l’appelant peut choisir ou remplacer l’archive et que le script l’extrait en tant que root avec `tarfile.extractall(filter="data")`, vérifiez les mises à jour de sécurité de l’interpréteur avant de faire confiance au filtre. CPython a corrigé plusieurs contournements de filtre par liens symboliques et physiques, dont CVE-2025-4517, dans les versions 3.9.23, 3.10.18, 3.11.13, 3.12.11 et 3.13.4. Les rétroportages des distributions peuvent corriger une version antérieure ; la version d’interpréteur affichée ne prouve donc pas à elle seule l’exposition.<sup>[[16]](#references)[[17]](#references)</sup>

Pour un examen passif, lisez la commande sudo et le script exacts, déterminez quel argument choisit l’archive et vérifiez si l’utilisateur actuel peut écrire dans l’archive ou dans son répertoire parent. Vérifiez séparément le correctif du fournisseur installé et la destination de l’extraction ; `filter="data"` ne rend pas sûre toute archive non fiable.<sup>[[16]](#references)[[17]](#references)</sup>

### Chargeurs de modèles d’apprentissage automatique exécutés par sudo

Une règle sudo qui autorise un fichier `.pt`, `.pth` ou `.ckpt` choisi par l’appelant mérite un examen lorsqu’un script privilégié transmet ce fichier à [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou à un autre chargeur basé sur pickle. Vérifiez la règle RunAs effective, si l’appelant peut créer ou remplacer le modèle choisi et le flux réel des arguments à travers tout wrapper shell vers l’helper Python. L’extension `.pth` désigne aussi des fichiers de configuration Python `site` sans rapport ; l’extension seule ne prouve donc pas le chargement d’un modèle. Un scan d’archive ou un scan statique de pickle ne permet pas d’établir que le chargement ultérieur est sûr ; examinez le comportement de [`weights_only`, qui dépend de la version](https://docs.pytorch.org/docs/stable/notes/serialization.html), ainsi que toute liste d’autorisation. Voir les [notes sur les pickles ML et Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Une énumération passive ne doit jamais charger ni décompresser le modèle.

### Analyse d’expressions à partir d’entrées stockées et exécutée par sudo

Un script Python fixe exécuté en tant que root via sudo peut quand même évaluer du texte qu’un utilisateur moins privilégié peut enregistrer dans une base de données d’application. Dans TensorFlow, un appel à `preprocess_input_exprs_arg_string(value, safe=False)` sélectionne une voie `eval` ; [l’avis de sécurité TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) décrit l’analyseur non sûr et un correctif pour son appelant en ligne de commande. Un appel explicite `safe=False` dans une application nécessite un examen distinct, même si cet appelant en ligne de commande est corrigé. Vérifiez la règle sudo effective, qui peut modifier l’enregistrement d’entrée concerné, si le filtrage ou la notation permet à cet enregistrement d’atteindre l’appel, ainsi que le comportement de la fonction installée. Une version de TensorFlow, une autorisation sudo ou un fichier de modèle codé en dur ne prouvent pas à eux seuls la chaîne d’exploitation. Examinez passivement le script et le flux des données ; n’exécutez pas l’helper privilégié et ne soumettez pas d’expressions de test pendant l’énumération.

### Configuration de needrestart autorisée par sudo

`needrestart -c` charge un fichier de configuration Perl choisi par l’appelant et en évalue le contenu. Si `sudo -l` autorise `needrestart` en tant que root avec des arguments permettant `-c`, et si l’appelant peut choisir un fichier de configuration lisible dans un emplacement modifiable, cette autorisation peut mener à l’exécution de code root. Vérifiez la règle RunAs et les arguments sudo exacts ; une règle qui n’autorise qu’une liste d’arguments fixe peut bloquer cette voie. Cette question est distincte des vulnérabilités de l’analyse des interpréteurs de needrestart : mettre à jour le paquet ou désactiver `interpscan` ne rend pas sûre une autorisation root sans restriction de `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python exécutés par sudo sous un autre compte

Un point d’entrée Python fixe peut quand même importer un module que l’appelant peut modifier ou remplacer, y compris lorsque sudo exécute le script en tant qu’utilisateur de service **non-root**. Pour un `from utils import status` littéral, examinez `utils/__init__.py` et `utils/status.py` locaux ainsi que les permissions du répertoire du paquet. Avant de considérer le fichier modifiable comme une voie d’exécution, vérifiez le chemin d’importation du script, les arguments sudo autorisés exacts et si l’action concernée atteint cet import. Examinez les fichiers et les permissions sans importer ni exécuter le script pendant l’énumération.<sup>[[2]](#references)[[3]](#references)</sup>

Une règle sudo exacte pour `python3 /absolute/script.py` exige uniquement que le script soit lisible ; le fichier n’a pas besoin d’être exécutable ni d’avoir un shebang. Examinez aussi les modules locaux **manquants** : si le script importe un module dont le nom de fichier peut être créé dans un répertoire de script modifiable par l’appelant, Python peut charger ce fichier sous l’identité RunAs. Vérifiez la règle sudo effective, le [chemin de recherche des modules](https://docs.python.org/3/library/sys_path_init.html) réel de l’interpréteur, si le module est intégré ou figé, et si l’import est atteint. Une règle sudo directe pour le script a des exigences différentes concernant le bit d’exécution et le shebang. Un wrapper distinct qui ajoute des jetons fournis par l’appelant après `sudo -u account` nécessite également un examen du flux d’arguments : un autre `-u` dans ces jetons n’a d’importance que si la politique sudo invoquée autorise l’identité qui en résulte. Des chaînes statiques ne prouvent aucune de ces voies.

### Apache exécuté par sudo avec une configuration contrôlée par l’appelant

Si une règle sudo autorise une invocation privilégiée de `apachectl`, `apache2ctl` ou `httpd` avec un fichier de configuration `-f` contrôlé par l’appelant, examinez les permissions de ce fichier et de son répertoire parent. La directive [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) d’Apache prend un nom de module suivi du **nom de fichier du module** ; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) charge également un fichier. [`Include` et `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) peuvent étendre la configuration ou exposer le contenu de fichiers via des erreurs. Un wrapper personnalisé peut valider ces chemins, abandonner les privilèges ou restreindre les arguments ; une configuration modifiable est donc une piste, pas une preuve d’exécution de code. Vérifiez la canonicalisation des chemins, les liens symboliques et l’analyse des directives avant de conclure.

### nginx exécuté par sudo avec une configuration contrôlée par l’appelant

Une règle `nginx` sans restriction avec capacité root peut autoriser [`-c` à sélectionner une autre configuration](https://nginx.org/en/docs/switches.html). Examinez les arguments sudo exacts et les exclusions, si l’appelant peut fournir la configuration et si le processus master ou les workers qui en résultent conservent l’accès aux chemins protégés. Un `root` choisi avec `autoindex` peut exposer des fichiers via un nouveau listener ; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) peut fournir une voie d’écriture de fichiers privilégiée, mais le module DAV n’est pas compilé par défaut et il faut vérifier sa présence, l’accessibilité du listener, les permissions des fichiers et le comportement des fichiers temporaires. La directive [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) peut aussi cibler un fichier choisi ; l’écriture de journaux dans un fichier de configuration sensible tel que `/etc/ld.so.preload` exige un processus effectivement privilégié capable d’écrire et un enregistrement de journal contrôlable avant de devenir une voie d’escalade. La mise en évidence de l’exécutable dans `sudo -l` est une piste, pas une preuve que l’une de ces voies fonctionne. Une énumération passive ne doit ni démarrer ni reconfigurer nginx.

### Comparaison de motifs dans les invites Bash privilégiées

Lorsqu’un script Bash autorisé par sudo lit une valeur fournie par l’appelant et la vérifie avec `[[ "$expected" == $entered ]]`, Bash interprète l’opérande de droite non protégé comme un motif. Un joker peut donc satisfaire la comparaison sans connaître la valeur attendue. Mettre l’opérande entre guillemets (`[[ "$expected" == "$entered" ]]`) en fait une comparaison de chaîne littérale. Examinez la règle sudo exacte, si l’invite est atteignable et ce que le script fait après la comparaison ; la syntaxe seule ne permet pas d’établir une voie exploitable. Évitez d’afficher la valeur attendue pendant l’énumération. Voir la [référence des constructions conditionnelles Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers exécutés par sudo qui téléchargent et exécutent un fichier

Une autorisation sudo sans restriction avec capacité root pour un helper personnalisé mérite un examen du flux de données s’il accepte une URL choisie par l’appelant, écrit la réponse sur le disque puis invoque le fichier avec un interpréteur ou un shell. [Sudoers autorise des arguments arbitraires lorsqu’une entrée de commande n’en précise aucun](https://man7.org/linux/man-pages/man5/sudoers.5.html) ; un chemin d’exécutable fixe ne restreint pas les ressources sélectionnées par ses arguments. Vérifiez la validation réelle de l’URL, le chemin de sortie, la branche de réussite et l’exécution ultérieure dans l’helper installé. Un import libcurl correspondant ou une chaîne affichable ne suffit pas à prouver cette chaîne.

Même un nom de fichier de sortie fixe peut être remplacé entre l’écriture et l’exécution lorsque l’helper utilise un **chemin relatif dans un répertoire de travail contrôlé par l’appelant**. Le renommage ou le remplacement d’un fichier appartenant à root dépend des droits d’écriture et de recherche sur le répertoire, ainsi que des restrictions du sticky bit, et pas seulement du mode du fichier ; voir [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Vérifiez si l’helper rouvre ensuite le chemin ou utilise le descripteur déjà ouvert, et s’il se déplace dans un répertoire fiable avant l’écriture. Examinez passivement la politique sudo, l’helper et les métadonnées du répertoire ; n’invoquez ni le téléchargement privilégié ni une course pendant l’énumération.

Un helper de téléchargement exécuté en tant que root via sudo peut aussi exposer une injection d’**arguments** s’il construit une chaîne Bash telle que `curl <caller input> -o <fixed output>`. Un filtre qui rejette les espaces laisse tout de même possible [l’expansion d’accolades Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) : des éléments séparés par des virgules et non protégés peuvent devenir des arguments curl distincts. Si l’entrée précède le `-o` fixe dans l’appel à curl, une option de sortie fournie par l’appelant peut choisir la destination de la première URL sous l’identité de l’helper ; [curl associe les options de sortie aux URL dans l’ordre](https://curl.se/docs/manpage.html#-o). Vérifiez le shell exact, les guillemets, la validation de l’entrée, la règle sudo effective, l’ordre des arguments curl et les schémas d’URL pris en charge, ainsi que le contrôle par l’appelant des données récupérées ou sa capacité à lire le résultat. Un exécutable empaqueté par PyInstaller peut contenir la logique de l’application Python, mais sa marque d’empaquetage ou une chaîne `curl` ne prouve pas à elle seule ce flux de données. Si cela est autorisé, examinez hors ligne une copie de taille limitée ; une énumération courante ne doit ni exécuter l’helper ni récupérer des données choisies par un attaquant.

Un script shell sudo exécuté en tant que root qui appelle [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) ne fait que choisir un nom inutilisé ; il **ne crée pas** le fichier. Si le script crée ensuite ce nom dans un répertoire qu’un autre utilisateur peut affecter, le rouvre et ajoute son contenu à une destination protégée telle que le fichier `authorized_keys` de root, examinez le risque de course sur le fichier temporaire. Vérifiez la règle sudo exacte, le propriétaire du répertoire et du fichier, la séquence de création et de réouverture, les protections du noyau et si l’écriture privilégiée utilise réellement des octets contrôlés par l’attaquant. Une chaîne `mktemp -u` ou un `/tmp` modifiable ne suffit pas à prouver l’existence de la course. Examinez le script et les métadonnées du chemin sans l’exécuter ni provoquer de course sur son fichier temporaire pendant l’énumération.

## Notes défensives

- Évitez d’autoriser des interpréteurs ou des éditeurs interactifs via sudo.<sup>[[1]](#references)</sup>
- Préférez des wrappers fixes appartenant à root qui effectuent une seule action administrative étroitement limitée.<sup>[[1]](#references)[[2]](#references)</sup>
- Si un interpréteur est indispensable, restreignez le chemin exact du script et empêchez les arguments contrôlés par l’utilisateur, les imports modifiables, `PYTHONPATH` et la conservation dangereuse de l’environnement.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si la modification de fichiers est nécessaire, restreignez le chemin exact du fichier et envisagez `sudoedit` avec des versions corrigées de sudo et une gestion stricte de l’environnement.<sup>[[1]](#references)[[2]](#references)</sup>
- Examinez `SETENV`, `env_keep`, les répertoires de travail modifiables, les chemins de modules/imports modifiables, `NOEXEC`, `use_pty` et la journalisation, sans les considérer comme une sandbox complète.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
