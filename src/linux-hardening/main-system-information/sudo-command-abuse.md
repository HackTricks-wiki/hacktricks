## Interpretadores permitidos pelo Sudo

Se `sudo -l` permitir que um usuário execute um interpretador como root, trate isso como execução direta de código. Os interpretadores são projetados para executar código arbitrário, então uma regra que permita `python3`, `perl`, `ruby`, `lua`, `node` ou binários semelhantes geralmente equivale à execução de comandos como root, a menos que os argumentos sejam rigorosamente restritos e validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Fluxo de análise comum: primeiro liste os privilégios do usuário e, em seguida, execute uma instrução Python com a opção `-c` do interpretador.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Outros exemplos de interpretadores são mostrados abaixo; os interpretadores listados documentam a execução de código inline ou APIs de processos filhos.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

O caminho exato importa. Se a regra do sudo permitir `/usr/bin/python3`, use esse caminho exato durante a validação.<sup>[[2]](#references)</sup>

Um glob de executável do sudo como `/usr/bin/python*` também pode permitir Python 2 para um script escrito para Python 3. Se o script chegar a `input()` com texto controlado pelo chamador, [Python 2 avalia esse texto como uma expressão](https://docs.python.org/2/library/functions.html#input); uma invocação explícita do interpretador se sobrepõe ao shebang do script. Verifique os binários correspondentes instalados, a identidade RunAs efetiva e a política de argumentos, as negações e se a entrada é alcançável antes de considerar isso um caminho de execução.

Um caminho de script fixo em uma regra do sudo com capacidade de root não restringe o que o script executa. Para um wrapper Bash legível, verifique se o primeiro comando executável usa um parâmetro posicional sem aspas, como `$1`, como **palavra de comando**, enquanto o sudo permite argumentos escolhidos pelo chamador. Confirme a identidade RunAs efetiva, a política de senha e de argumentos, as negações posteriores e o ramo real do script; `NOEXEC`, uma lista fixa de argumentos seguros ou um wrapper que valida o comando podem alterar o resultado. Inspecione estaticamente o script curto durante a enumeração, em vez de invocá-lo com um comando de teste.

Uma regra irrestrita do sudo com capacidade de root para `dotnet` também merece uma análise do interpretador. Com o .NET SDK instalado, [`dotnet fsi` executa código F# interativamente ou a partir de um script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), e [`dotnet run` executa um projeto a partir do código-fonte](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Primeiro, confirme a identidade RunAs efetiva e a política exata de argumentos: uma regra limitada a um subcomando seguro específico ou a um aplicativo confiável é uma concessão diferente, e uma instalação apenas do runtime pode não incluir comandos do SDK. O nome do executável é apenas um indício para análise, não uma prova de execução de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` permitido pelo sudo: gravação arbitrária de arquivos privilegiados

O GNU `tee` copia a entrada padrão para cada caminho fornecido como operando de arquivo. Portanto, uma regra do sudo que permite executar `/usr/bin/tee` como root com argumentos controlados pelo usuário concede uma primitiva para criar ou sobrescrever arquivos arbitrários como root. Adicionar `-a` altera a primitiva para anexar conteúdo. Uma tag `PASSWD:` diz respeito à autenticação do sudo; por si só, ela não restringe o destino nem os bytes lidos da entrada padrão.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Primeiro, inspecione a regra exata. Em um sistema de teste autorizado, valide a primitiva somente com um destino descartável e seguro para criar. O `>/dev/null` final apenas suprime a cópia do `tee` para a saída padrão.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Colocar `sudo` antes do produtor não eleva os privilégios de um redirecionamento de shell posterior, pois é o shell do usuário que abre o destino. O processo privilegiado precisa ser o responsável pela escrita, como no pipeline acima.<sup>[[1]](#references)[[15]](#references)</sup>

Após confirmar a escrita, escolha um alvo apropriado para execução de código como root em [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Uma cadeia observada usou `tee` como root para criar um arquivo temporário em `/etc/cron.d/`, iniciar um backdoor por meio de um script controlado pelo usuário e excluir o arquivo cron após a execução. Remover o arquivo cron impediu que ele se tornasse uma entrada de persistência de longo prazo, embora os logs do sistema ainda preservassem evidências da atividade.<sup>[[27]](#references)</sup>

## Editores permitidos pelo sudo

Se `sudo -l` permitir que um usuário execute um editor interativo como root, trate isso como uma superfície de execução de comandos, não como uma permissão inofensiva para editar arquivos. Muitas vezes, os editores podem executar comandos do shell, ler arquivos arbitrários, gravar arquivos arbitrários ou invocar auxiliares externos de dentro do editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Fluxo de análise comum: liste os privilégios do usuário e, em seguida, invoque cada editor ou pager permitido usando sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Execução de comandos com Nano

Quando o `nano` é permitido por meio do sudo, pode ser possível executar comandos pela interface do editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Em seguida, forneça um comando como `id` ou `/bin/sh` no prompt de comando do nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se um shell interativo não tiver fluxos de terminal utilizáveis, esta forma de redirecionamento mapeia sua saída padrão e seu erro para o descritor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

A sequência exata de teclas pode variar conforme a versão do nano e as opções de compilação, mas o problema de segurança é o mesmo: o editor está sendo executado como root e pode invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Outras formas comuns de escapar do editor

Editores no estilo do Vim geralmente permitem executar comandos por meio de `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers como `less` também podem permitir a execução de comandos do shell.<sup>[[14]](#references)</sup>

Uma regra do sudo que permita executar `apport-cli` como root merece a mesma revisão do pager. Versões afetadas do Apport podiam abrir um relatório de falha no `less` com um tamanho de terminal ajustável pelo atacante; o pager podia então fornecer um shell como root se as condições especiais do sudo e do pager fossem atendidas. Verifique a regra efetiva do sudo, a configuração do pager e a correção do pacote da distribuição antes de considerar a versão vulnerável por si só. Durante a enumeração passiva, leia os metadados do pacote e da política sem gerar uma falha nem abrir o relatório privilegiado. [O registro de CVE do Ubuntu](https://ubuntu.com/security/CVE-2023-1326) lista as versões corrigidas dos pacotes específicas de cada versão, incluindo correções retroportadas.

```text
!/bin/sh
```

## Outros riscos em regras de sudo e doas

Comece com `sudo -l`, `sudo -V` e qualquer política aplicável de `doas`. Analise em conjunto o comando permitido, o usuário de execução, os argumentos, o ambiente e os padrões. A permissão para executar como uma conta de serviço que não seja root ainda pode expor os arquivos dessa conta ou uma rota para root.

Um script Python fixo permitido pelo sudo ainda pode executar um comando de shell com a identidade RunAs se a entrada interativa, controlada pelo chamador, for concatenada em [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Uma denylist de pontuação do shell não basta para estabelecer segurança: o [shell também reconhece a substituição de comandos `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirme que os argumentos permitidos chegam ao ramo que lê a entrada, que a entrada chega ao comando de shell sem validação segura e que a política efetiva do sudo permite o usuário RunAs pretendido. O caminho do script ou uma chamada a `os.system()` isoladamente são apenas pistas para análise; inspecione o código-fonte sem executar o script privilegiado.

Uma concessão efetiva de sudo como root para `chattr` pode remover o atributo de arquivo imutável (`i`), mas isso, por si só, não concede permissão de escrita nem uma nova identidade. O [manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) diz que o atributo impede modificações e que somente root ou um processo com `CAP_LINUX_IMMUTABLE` pode alterá-lo. Verifique a política exata de argumentos do sudo e o suporte do sistema de arquivos; depois, verifique separadamente se o chamador pode escrever no arquivo após a remoção do atributo e se um consumidor com identidade superior o utiliza. Uma substituição de shell de login, por exemplo, também exige as credenciais aceitas da conta-alvo e um login real por esse shell. Analise a política, os atributos de arquivo e as permissões sem alterá-los durante o inventário.

Se o sudo solicitar uma senha e um código de uso único, mantenha esses pré-requisitos separados da concessão do comando. Um arquivo `.google_authenticator` legível contém material de seed sensível, enquanto um hash antigo de senha de aplicativo ou de banco de dados é apenas uma possível senha da conta atual; nenhum deles comprova que o outro fator é aceito pela configuração efetiva do PAM. Depois de autorizado, analise o RunAs e os argumentos exatos: uma concessão irrestrita de root para o RubyGems `gem` pode expor seu comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), mas uma concessão restrita ou uma falha de autenticação não. O inventário passivo deve informar caminhos e políticas sem exibir o seed, recuperar uma senha, gerar um código ou invocar o comando privilegiado.

Uma concessão irrestrita de sudo com capacidade de root para o `knife` do Chef merece análise no nível do interpretador: [a documentação do Chef explica que `knife exec -E` avalia uma string Ruby localmente](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifique se a regra efetiva do sudo permite o subcomando `exec` e o argumento `-E` fornecido pelo chamador, a identidade RunAs pretendida e quaisquer negações de comando ou argumentos fixos correspondentes. O binário instalado ou uma regra restrita a outros subcomandos são apenas pistas. O inventário passivo deve informar a regra sem invocar `knife`.

Uma concessão exata de sudo com capacidade de root para um `msfconsole` interativo é igualmente sensível: [GTFOBins documenta seu console `irb`](https://gtfobins.org/gtfobins/msfconsole/), que pode herdar a identidade do sudo. Confirme o usuário RunAs efetivo, a lista de argumentos permitidos, as negações de comando, `NOEXEC` ou outras restrições, o comportamento do console instalado e se o chamador pode fornecer entrada interativa. Uma indicação do caminho, isoladamente, é apenas uma pista; o inventário passivo não deve iniciar o console.

No FreeBSD, até mesmo uma regra de sudo limitada a `pkg update` e `pkg install *` como root merece uma análise da confiança nos repositórios. Verifique se `/etc/hosts` pode ser escrito pelo chamador e se a configuração *efetiva* de repositórios habilitados usa um hostname HTTP com `signature_type: none`. O [manual de `pkg.conf` do FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) diz que `none` desabilita a verificação de assinaturas; `pkg+http`, por si só, não comprova isso. Um pacote pode conter scripts de instalação ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), portanto um chamador que realmente controla o endpoint do repositório e pode selecionar um pacote pode cruzar a fronteira de root. Verifique as substituições de repositório, a resolução de SRV/espelhos, os argumentos efetivos do sudo, a seleção do pacote e a execução de scripts antes de chegar a essa conclusão. Inspecione a política e pequenos arquivos de configuração locais sem redirecionar nomes nem executar `pkg` durante o inventário.

Uma regra de sudo com capacidade de root para `apt-get update` e `apt-get upgrade` também exige análise da confiança nos repositórios quando o sudo preserva um `http_proxy` controlado pelo chamador. Verifique se a configuração efetiva do APT realmente usa essa variável e quais solicitações de repositórios habilitados ela pode afetar; um proxy, por si só, não pode substituir pacotes de um arquivo autenticado por uma chave de assinatura confiável. O [manual do transporte HTTP do APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta a precedência dos proxies, e o [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta as verificações de assinatura, as substituições para repositórios inseguros e a confirmação para pacotes não autenticados. Confirme o RunAs e os argumentos exatos do sudo, a política de autenticação dos repositórios, qualquer confirmação interativa necessária e se a atualização selecionada executa scripts de pacote como root. Inspecione a política e a configuração local passivamente; não redirecione o tráfego de pacotes nem execute uma atualização durante o inventário.

Uma regra de sudo com capacidade de root para `snap install` pode cruzar a fronteira entre pacote e código se os argumentos permitirem ao chamador selecionar um snap local e um modo de instalação permissivo. [A documentação do Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) explica que `--dangerous` ignora as verificações de assertion de snaps locais e que `--devmode` relaxa o confinement; [um hook de instalação pode ser executado na instalação inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Verifique a política exata de argumentos/RunAs do sudo, quem controla o arquivo snap, se esses modos são aceitos pelo snapd instalado e a identidade efetiva e o confinement do hook antes de afirmar que há acesso a arquivos protegidos do host. Um binário `snap` ou uma regra que parece ter curinga não comprova essa cadeia. O inventário passivo não deve instalar um pacote nem executar seu hook.

Para uma concessão exata de sudo a um binário personalizado que lê credenciais e é executado como uma conta **que não seja root**, inspecione primeiro o binário concedido e suas permissões de arquivo sem executá-lo. Uma verificação de senha embutida pode aparecer apenas como caracteres largos; [a documentação do GNU `strings` descreve a extração little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Uma string visível não comprova que essa seja a senha aceita nem que o ramo de sucesso exponha uma credencial atual. Confirme separadamente o comportamento do binário, o acesso da conta-alvo aos dados protegidos, a validade da credencial e qualquer transição posterior de conta ou grupo. Se essa conta pertencer a `docker`, verifique o acesso ao socket e se o daemon é rootful ou rootless antes de inferir acesso a root no host; [a documentação do Docker explica as implicações de nível root do grupo](https://docs.docker.com/engine/install/linux-postinstall/). O inventário rotineiro deve informar a regra de sudo e a associação ao grupo sem executar o binário nem despejar suas strings.

Uma regra de sudo com curinga para scripts de manutenção de um aplicativo exige análise além do caminho do script. Verifique se o script permitido aceita argumentos irrestritos ou lê configurações graváveis por uma conta de aplicativo com menos privilégios; em seguida, rastreie esses valores até comandos de shell ou o ambiente de um subprocesso. Por exemplo, o [`zmupdate.pl` do ZoneMinder monta um comando `mysqldump` e o executa por meio de `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), enquanto o [`zmdc.pl` copia a configuração `ZM_LD_PRELOAD` para `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Uma regra de sudo que permita qualquer um desses scripts como root pode cruzar uma fronteira de confiança se a entrada correspondente for controlável e chegar a esse código na versão instalada. Inspecione a regra efetiva do sudo, as permissões da configuração do aplicativo e o código-fonte do script; o curinga ou a configuração, isoladamente, são pistas, não prova de execução.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` podem transformar um comando que, de outro modo, seria restrito em um sequestro de importação, biblioteca ou PATH. Consulte o [guia de variáveis de ambiente](../linux-basics/linux-environment-variables.md) e [abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Uma concessão exata de `SETENV` com capacidade de root para um wrapper de shell também merece uma análise de um salto se o wrapper iniciar um script Python fixo com um import literal. `secure_path` restringe a busca de comandos pelo shell, não a [busca de módulos Python em `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fazem o Python ignorar essa variável de ambiente. Confirme as tags e negações efetivas do sudo, o ramo do wrapper, as opções do interpretador, a resolução do import e a existência de um diretório de busca gravável pelo chamador antes de considerar isso execução de código. Inspecione scripts curtos estaticamente; não invoque o wrapper privilegiado.

Uma concessão exata de sudo para `neofetch ""` com capacidade de root ainda pode carregar uma configuração de shell quando os padrões aplicáveis do sudo preservam um `XDG_CONFIG_HOME` controlado pelo chamador. O [carregador de configuração do Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carrega `neofetch/config.conf` ou `neofetch/config` dentro desse diretório; a lista vazia de argumentos não impede essa busca. Confirme o carregador instalado, a política efetiva de RunAs e argumentos, quaisquer negações de comando, se o sudo realmente mantém a variável selecionada para esse comando e se o chamador controla um caminho de configuração legível. Uma variável preservada ou o Neofetch instalado, isoladamente, é apenas uma pista. Inspecione a política e os metadados dos arquivos sem invocar o comando privilegiado nem exibir o conteúdo da configuração; consulte [tratamento do ambiente pelo sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Uma regra irrestrita de sudo para `facter` com capacidade de root merece uma análise separada de custom facts. [A documentação do Puppet](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) explica que `--custom-dir` carrega arquivos Ruby de facts de um diretório selecionado. Verifique se a regra exata do sudo permite essa opção, se o Facter instalado a aceita e se o chamador controla o diretório. Uma concessão com argumentos fixos, uma negação explícita do comando ou custom facts desabilitados podem alterar o resultado. O inventário passivo deve informar a possível regra sem invocar o Facter nem ler o conteúdo dos facts.

Para uma concessão exata de script do sudo com capacidade de root e `SETENV`, inspecione nomes de comando sem caminho, como `find`, e o `PATH` efetivo após a política do sudo e a inicialização do script. Um arquivo Bash carregado com `source` também pode executar `enable -n [`: [o Bash passa então a procurar um `[` externo no `PATH](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) quando o script usa esse comando posteriormente. Confirme as regras aplicáveis de [ambiente do sudoers e `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), quaisquer entradas `NOSETENV`/`NOEXEC` ou de negação, o fluxo do script e dos arquivos carregados com `source` e a existência de um diretório executável de busca controlado pelo chamador. Um script legível que contém um comando sem caminho é uma pista, não uma prova de execução privilegiada; inspecione-o sem invocar a regra de sudo.

- Um script privilegiado que busca uma URL fixa com `curl` ainda pode aceitar uma resposta escolhida pelo chamador se uma regra aplicável do sudo preservar `http_proxy` e a solicitação passar por esse proxy. Se o script então passar a resposta para um parser XML que resolva entidades externas, uma resposta maliciosa pode revelar arquivos legíveis pelo processo privilegiado. Verifique a política exata de ambiente do sudo, as exclusões `no_proxy`, a URL solicitada, a configuração do parser e o destino da saída; uma variável de proxy ou um parser XML, isoladamente, não constitui uma vulnerabilidade. A [documentação do ambiente de proxy do curl](https://everything.curl.dev/usingcurl/proxies/env.html) descreve o comportamento das variáveis. Não faça solicitações de rede nem analise XML malicioso durante o inventário passivo.
- Um script do sudo com capacidade de root que monta um arquivo PostScript a partir de dados influenciados pelo chamador e depois executa `ps2pdf -dNOSAFER` merece uma análise separada do fluxo de entrada. O Ghostscript documenta que essa flag desabilita SAFER até `.setsafe`, permitindo operações com arquivos PostScript dentro das permissões do processo no sistema operacional. Uma consulta SQL montada a partir de um argumento do chamador pode alimentar linhas controladas pelo atacante ao modelo PostScript, mas uma string de consulta ou uma invocação de `ps2pdf`, isoladamente, não comprova que os dados cheguem à sintaxe executável do PostScript. Confirme a regra efetiva do sudo, o caminho exato da entrada até o modelo, qualquer escape, o comportamento do Ghostscript instalado e se SAFER é reativado antes da interpretação do documento. Não invoque a conversão privilegiada durante o inventário passivo. Consulte a [documentação do `-dNOSAFER` do Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para uma regra de sudo que executa um script de shell, compare as variáveis preservadas com o próprio script. Uma construção como `if $CHECK_CONTENT; then` executa o valor expandido como um comando; portanto, preservar `CHECK_CONTENT` pode permitir execução de comandos mesmo quando o caminho do script e os argumentos são fixos. É preciso verificar se o ramo pode ser alcançado e se o ambiente é realmente preservado para a regra específica.<sup>[[2]](#references)[[22]](#references)</sup>
- Um script Python permitido pelo sudo pode importar código de um diretório gravável ou de um arquivo `.pyc` em cache. O [guia de escalação de privilégios](../linux-basics/linux-privilege-escalation/README.md) detalha o caso do cache.
- Um script Python fixo permitido para execução como root ainda pode expor um depurador interativo. Chamadas como `pdb.set_trace()` ou `pdb.post_mortem()` permitem executar instruções Python no contexto do processo depurado quando o chamador consegue alcançar o ponto de interrupção ou o manipulador de exceção **e controlar o fluxo de entrada do depurador**. Verifique a regra exata de RunAs do sudo, a autenticação e as condições do ramo, a possibilidade de alcançar a exceção, a propriedade do terminal/entrada e se o depurador é executado nesse mesmo processo privilegiado. Uma solicitação de socket que provoca uma exceção não concede, por si só, acesso a um depurador conectado a outro terminal. [A documentação do Python descreve a avaliação de instruções pelo depurador e o modo post-mortem](https://docs.python.org/3/library/pdb.html); inspecione o script estaticamente em vez de acionar o manipulador privilegiado durante o inventário.
- Um script Python fixo permitido pelo sudo também pode ler um campo de perfil de um banco de dados ou socket Unix e concatená-lo em uma string que depois se torna a **string de formato** de `str.format()`. [Campos de substituição podem acessar atributos e chaves de mapeamento](https://docs.python.org/3/library/string.html#format-string-syntax), portanto um campo controlado pelo atacante pode inspecionar objetos fornecidos a `format()` e expor dados acessíveis por eles se o resultado for exibido ou armazenado em um local legível pelo chamador. Verifique a identidade efetiva de RunAs do sudo, o acesso de escrita ao registro específico, o fluxo de dados até a string de formato, quais objetos são fornecidos e a visibilidade da saída. Isso não é execução automática de código, e uma string de formato literal e confiável, com *valores* controlados pelo atacante, é um caso diferente. Um segredo revelado só permite uma transição para uma conta do sistema operacional se essa conta o aceitar. Analise o script e as permissões do socket sem invocar a operação privilegiada.
- Um wrapper Python com capacidade de root pode passar uma URL selecionada pelo chamador para `Repo.clone_from` do GitPython. Se o wrapper também habilitar `protocol.ext.allow=always` do Git, um remoto `ext::` pode invocar um helper externo. Verifique os argumentos exatos do sudo, a origem da URL, a versão do pacote GitPython e o status de patches do fornecedor, e se o wrapper habilita explicitamente protocolos inseguros. O GitPython adicionou uma [proteção padrão contra protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) na versão 3.1.30; a versão do executável `git` é um dado separado. Uma análise passiva deve ler somente a regra e um trecho limitado do código-fonte, sem invocar o clone.
- Uma concessão de sudo entre usuários para uma CLI que clona repositórios pode expor um caminho separado de injeção de string de shell. Rastreie se o argumento de repositório selecionado pelo chamador chega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) do Node.js ou a outro construtor de comandos de shell sem separação segura de argumentos; o `exec` do Node passa sua string de comando a um shell. Confirme o usuário RunAs exato, os subcomandos e argumentos permitidos, o código do wrapper instalado e a validação de entrada. O nome de uma ferramenta de repositório ou uma regra irrestrita de sudo, isoladamente, não comprova injeção de comandos. Inspecione o wrapper sem invocar um clone privilegiado durante o inventário.
- Um wrapper personalizado de propriedade de root pode parecer seguro porque seus binários e scripts não são graváveis, mas a decisão de executar uma ação privilegiada pode depender de uma flag, de um valor de API local ou do estado de um serviço que um usuário sem privilégios pode alterar. Rastreie cada condição até sua entrada e suas verificações de autorização. Durante o inventário, inspecione a configuração e as permissões sem alterar o estado operacional; uma chamada a `systemd-run` dentro do wrapper só é relevante se a condição puder ser influenciada.
- Um cliente de backup permitido pelo sudo como root pode aceitar um arquivo de configuração selecionado pelo chamador (por exemplo, `npbackup-cli -c`). Verifique o usuário de execução e os argumentos permitidos exatos; em seguida, verifique se o chamador controla o caminho da configuração, os caminhos de origem do backup e o repositório ou as opções de leitura/restauração. Um segredo de repositório criptografado em uma configuração legível ainda pode ser utilizável pelo cliente, mas a regra, por si só, não comprova acesso ao repositório nem divulgação de arquivos de root. Valide a autorização sem executar um backup nem despejar seu conteúdo.
- O [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) oferece suporte a `--password-command`, que chama um programa para obter a senha do repositório. Se uma regra de sudo permitir a um usuário com menos privilégios executar o restic como root com um comando de senha escolhido pelo chamador e um subcomando que precise da senha, esse helper poderá ser executado como root. Analise os argumentos e as exclusões exatos do sudo; não invoque o helper nem um comando de backup apenas para verificar a condição.
- Uma concessão privilegiada de `restic backup` também pode cruzar uma fronteira de leitura de arquivos se o padrão de argumentos do sudo permitir ao chamador selecionar tanto a origem quanto um repositório que ele possa posteriormente ler e descriptografar. [Os curingas de argumentos do sudoers podem corresponder a espaços em branco e barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), portanto inspecione os curingas finais em vez de presumir que um prefixo fixo de repositório restringe a origem. [O Restic pode fazer backup em repositórios locais e remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), mas um repositório local pode conter objetos recém-gravados que só root pode ler; confirme a política efetiva do sudo, o acesso ao backend, a senha do repositório e as permissões dos objetos resultantes antes de considerar isso uma divulgação. Uma chave SSH armazenada no backup só concede acesso se a conta de destino a aceitar. Não execute um backup para testar isso durante a análise passiva.
- Um comando irrestrito de manutenção ou backup personalizado pode aceitar um caminho de saída ou oferecer seu próprio agendador de tarefas. Para uma via de escrita em arquivo, verifique a regra exata do sudo e o usuário de execução; em seguida, verifique se o chamador controla tanto os dados quanto o destino. Para uma via de comando agendado, verifique a identidade de execução do agendador, a entrada do comando e qualquer requisito adicional de senha ou autorização. O nome do comando ou `NOPASSWD`, isoladamente, não comprova nenhuma das vias. Consulte [escrita em arquivos de propriedade de root](../interesting-files-permissions/write-to-root.md) e [cron e temporizadores do systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Um comando fixo do sudo ainda pode carregar um arquivo de configuração previsível de um diretório compartilhado gravável. Rastreie se o chamador pode substituir esse arquivo e se seus campos de origem e destino controlam uma busca ou cópia privilegiada. Uma URL de arquivo local pode expor dados legíveis apenas pela conta RunAs do sudo; uma origem controlada pelo chamador combinada com um destino protegido pode criar uma via de escrita. Confirme o tratamento de URLs pelo programa instalado, as verificações do caminho de destino, a regra efetiva do sudo e a acessibilidade da saída. Um caminho de configuração gravável em `/tmp`, isoladamente, é apenas uma pista; inspecione o binário e os metadados do arquivo sem invocar a transferência privilegiada.
- Uma regra de sudo para `git apply` pode permitir que a conta RunAs grave arquivos selecionados por um patch controlado pelo chamador. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitia que um patch elaborado criasse um symlink e depois escrevesse fora da árvore de trabalho, mesmo quando o comando não aceitava `--unsafe-paths`. Verifique a regra efetiva de argumentos do sudo, a origem do patch, o acesso da conta RunAs ao diretório de trabalho e a correção do Git instalado ou o patch retroportado pelo fornecedor. Uma regra irrestrita que aceite `--unsafe-paths` apresenta um risco separado relacionado a essa opção explícita; nem uma versão do Git nem a permissão para executar `git apply`, isoladamente, comprovam que um arquivo protegido pode ser alterado. Não aplique um patch não confiável durante o inventário passivo.
- Uma regra de sudo com capacidade de root para `clamscan --debug` pode cruzar uma fronteira de leitura se um usuário com menos privilégios puder fornecer uma imagem DMG e o parser instalado for afetado pela [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que poderia divulgar conteúdo de arquivos pela saída de depuração. Confirme os argumentos e o caminho de varredura permitidos exatos, o controle da entrada, a conta RunAs efetiva, a correção ou o patch retroportado do mecanismo e se a saída é visível ao chamador. Se uma regra mais ampla permitir `--file-list`/`-f`, analise separadamente o comportamento dessa lista; uma política fixa em `--debug <scan-path>` não permite essa opção. Inspecione a política e os metadados do pacote sem varrer um arquivo elaborado nem exibir saída protegida durante o inventário.
- Uma regra de sudo com capacidade de root que abre uma imagem de disco criptografada selecionada pelo chamador e uma segunda regra que monta o mapper resultante podem importar arquivos controlados pelo chamador no namespace de montagem do host. Confirme as duas regras efetivas e seus argumentos, o controle da imagem e do nome do mapper, o destino real da montagem e o proprietário e modo dos arquivos resultantes. Uma transição por set-user-ID também exige um executável acessível, opções de montagem que o respeitem (`nosuid` o bloqueia) e a política aplicável de processo ou MAC; abrir ou montar uma imagem, por si só, é apenas uma pista. Uma rota separada por meio de um backup existente exige sua chave real e um segredo útil e legível dentro dele. Inspecione a política e os caminhos sem abrir nem montar uma imagem durante o inventário passivo. Consulte o [manual do cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e as [opções de montagem](https://man7.org/linux/man-pages/man8/mount.8.html).
- Uma regra de sudo com capacidade de root para um script de shell ou Python merece uma análise do diretório de trabalho se o script invocar `./helper` sem antes mudar para um diretório fixo. Uma lista Python como `['./helper']` passada a `subprocess.run` pode ter o mesmo comportamento de diretório de trabalho selecionado pelo chamador. O chamador pode conseguir escolher um diretório gravável e colocar ali um executável com esse nome relativo; um caminho absoluto em outra parte do script não protege essa chamada. Confirme a regra efetiva, `runchdir` ou outra política que altere o diretório, o fluxo do script e a possibilidade de alcançar o ramo, a existência de um diretório gravável e executável e as restrições de montagem/`NOEXEC` antes de considerar isso execução de código. Se o script não puder ser lido, o comportamento permanece desconhecido até que seu código seja analisado por um meio autorizado. Analise os scripts estaticamente em vez de executar o helper. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta a política de diretório de trabalho.
- Um validador Python fixo com capacidade de root ainda pode avaliar um arquivo de dados selecionado pelo chamador. [A documentação de `eval()` do Python adverte contra entradas não confiáveis](https://docs.python.org/3/library/functions.html#eval): uma verificação de sufixo, um prefixo aritmético ou um ramo de validação não é uma sandbox se a expressão restante chega a `eval`. Confirme a regra efetiva do sudo, se o chamador pode selecionar e controlar o arquivo exato, as condições do ramo do parser e a construção da expressão, e a identidade do processo privilegiado antes de considerar isso uma via de execução. A presença de `eval` em um script legível é apenas uma indicação para análise; inspecione o código-fonte e as permissões do arquivo sem executar o validador nem enviar uma expressão de teste durante o inventário.
- Um wrapper Ruby de sudo com capacidade de root que lê um nome de arquivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, pode obter a entrada do diretório de trabalho do chamador, a menos que o wrapper ou a política do sudo fixe esse diretório. Verifique os argumentos exatos permitidos, as permissões do diretório e do arquivo e o comportamento do Psych instalado: implementações mais antigas de `YAML.load` podiam desserializar objetos Ruby arbitrários, enquanto versões mais recentes restringem classes por padrão. Uma chamada estática é apenas uma pista; confirme que o arquivo realmente vem de um diretório gravável pelo chamador e que o carregador instalado aceita classes perigosas. Prefira `safe_load` com uma lista de permissões explícita e mínima de classes para entradas não confiáveis. Consulte a [documentação do Psych do Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e a [documentação do Psych do Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Uma concessão exata de `sudo go run /absolute/file.go` com capacidade de root merece uma análise do diretório de trabalho quando o código Go lê um arquivo WASM relativo e pode executar um script de shell relativo após inspecionar seu resultado. Confirme o RunAs efetivo, os argumentos e as negações do comando, a existência de um diretório atual gravável pelo chamador, o fluxo de dados do WASM até o ramo e se esse ramo invoca o helper. Um `runchdir` fixo do sudo, `os.Chdir` ou [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pode alterar o local da busca. Uma coocorrência estática é apenas uma possibilidade; inspecione o código-fonte sem executar Go, WASM ou o helper.
- `sudoedit` e curingas de argumentos exigem verificações exatas da versão e da regra; a [lista de verificação](linux-privilege-escalation-checklist.md) inclui o problema de edição de arquivos com sudoedit. Para uma concessão de `sudoedit` entre usuários com caminho curinga, inspecione a configuração efetiva `sudoedit_follow` ou `FOLLOW`, `sudoedit_checkdir`, o destino resolvido e quem pode substituir cada entrada do diretório pai. A primeira pode permitir seguir um symlink, enquanto desabilitar a segunda remove as verificações de diretórios graváveis; nenhuma delas, isoladamente, estabelece que seja possível escrever no arquivo de outro usuário. Confirme a política instalada do sudo e os argumentos exatos correspondentes antes de chegar a essa conclusão. Consulte as [definições de opções do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Em uma regra de comando do sudoers, um curinga de argumento pode corresponder a espaços em branco, além de caracteres de caminho. Uma regra para um comando com capacidade de leitura e um argumento como `/restricted/*` pode, portanto, aceitar um argumento adicional de arquivo após um prefixo correspondente. Analise o usuário RunAs exato, o caminho do comando, o padrão de argumentos e as negações posteriores; comprovar a leitura de um arquivo não implica execução de comandos. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) diferencia globs de argumentos dos globs de caminho de comando.
- Um glob de argumento que parece restringir um caminho também pode corresponder a `../`. Por exemplo, uma regra de `node /opt/scripts/*.js` com capacidade de root pode permitir um arquivo JavaScript controlado pelo chamador fora de `/opt/scripts` se o caminho fornecido ainda começar com `/opt/scripts/` e for resolvido por segmentos de diretório pai. Trata-se de um glob de **argumento**; as regras de correspondência de barras do glob no caminho do executável Node são diferentes. Verifique a regra efetiva, as negações posteriores, a resolução do caminho, o controle do arquivo de destino e eventuais restrições por expressão regular ou digest do sudoers antes de concluir que há execução de código. Consulte as [regras de curingas do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e a [documentação de linha de comando do Node](https://nodejs.org/api/cli.html).
- Arquivadores e outros programas utilitários podem ter hooks de execução. Teste os argumentos permitidos exatos em relação ao [GTFOBins](https://gtfobins.github.io/) em vez de presumir que somente shells ou interpretadores executam comandos.
- Uma regra irrestrita de `qpdf` com capacidade de root pode expor um arquivo privilegiado por anexos PDF: o qpdf 10.2 e versões posteriores oferecem suporte a `--empty` e `--add-attachment file ... --` com um PDF de saída. Se o processo privilegiado puder ler a origem selecionada e gravar o PDF em um caminho acessível pelo chamador, a saída poderá conter os bytes da origem. Analise os argumentos efetivos e as exclusões do sudo, a versão do qpdf, o acesso à origem e o caminho de saída antes de concluir que a divulgação de arquivos é possível. Ler uma chave SSH de root só é útil para login quando a chave é válida e a autenticação SSH de root é permitida. Consulte as [opções de anexos do qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- O reaproveitamento de timestamps do sudo depende da política de cache, do usuário proprietário, do terminal/sessão e das permissões. O [guia de escalação de privilégios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) aborda as verificações.
- `doas` tem suas próprias regras e configuração. Verifique os comandos permitidos e os caminhos de configuração graváveis conforme descrito na [seção sobre doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Ferramentas de build e empacotamento executadas pelo sudo

Uma concessão irrestrita de sudo para o `forge` do Foundry pode ser relevante mesmo quando a identidade RunAs é outro usuário sem privilégios de root. Opções do compilador, como `--use`, podem selecionar um executável local, e `forge flatten -o` seleciona um arquivo de saída. Verifique a versão instalada do Forge, os argumentos exatos do sudo, os caminhos acessíveis do projeto e do compilador, as permissões de saída e o ambiente efetivo antes de considerar a concessão explorável. Um executável helper relativo encontrado por meio de `PATH` é uma rota dependente da versão e do ambiente, não uma propriedade que se deva presumir em todas as compilações do Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Uma concessão irrestrita de `pacman` com capacidade de root permite mais do que consultas de pacotes: `-U` aceita um pacote local, pacotes podem conter scripts de instalação e `--hookdir` seleciona outro diretório de hooks. Analise a regra efetiva do sudo, as restrições de argumentos e as exclusões antes de testar; o inventário passivo não exige instalar um pacote nem executar um hook.<sup>[[25]](#references)[[26]](#references)</sup>

Um wrapper de shell fixo do sudo também pode instalar uma dependência npm nomeada e depois iniciar um aplicativo Node. Analise a regra exata de RunAs, se o pacote já está instalado, o `HOME` e o `userconfig` efetivos do npm, as substituições de configuração do projeto ou da linha de comando e se um usuário com menos privilégios controla o registro ou o pacote retornado para esse nome. [A documentação do npm descreve a busca de `.npmrc` por usuário e por projeto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); o comportamento de `HOME` do sudo depende da política instalada e da distribuição, portanto um `.npmrc` gravável do usuário pode ou não ser lido pelo processo npm privilegiado. Se o aplicativo privilegiado importar o pacote recém-instalado, o código do módulo pode ser executado com a identidade desse aplicativo. Scripts executados durante a instalação são uma via separada, dependente da versão e da configuração; [a documentação do npm descreve seu ciclo de vida e o tratamento de usuários](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Um caminho `.npmrc` ou uma linha `npm install`, isoladamente, são apenas pistas. Inspecione a regra, o wrapper curto, os caminhos de configuração e a procedência do pacote sem instalar o pacote nem iniciar o aplicativo durante o inventário passivo.

Uma concessão de `pip` ou `pip3 download` com capacidade de root também é uma indicação para analisar o build de pacotes quando os argumentos permitem ao chamador selecionar uma distribuição de código-fonte não confiável, mesmo que o padrão de URL a restrinja a um serviço local e ao sufixo `.tar.gz`. `pip download` aceita URLs de arquivos e resolve metadados de pacotes; preparar uma distribuição de código-fonte pode invocar o backend de build ou o código legado de `setup.py` antes de o arquivo ser simplesmente salvo. Confirme o RunAs e a regra de argumentos exatos do sudo, se o chamador pode publicar ou substituir o arquivo selecionado e se essa versão do pip realmente prepara os metadados. Um arquivo fixo e confiável ou um wheel não estabelecem essa via. Não baixe nem compile um pacote não confiável durante o inventário passivo. Consulte o [comando download do pip](https://pip.pypa.io/en/stable/cli/pip_download/), a [interface de build-system](https://pip.pypa.io/en/stable/reference/build-system/) e as [orientações para instalação segura](https://pip.pypa.io/en/stable/topics/secure-installs/).

Uma regra de sudo que permite `pip install` com um caminho de projeto local escolhido pelo chamador cria uma fronteira de build mais direta. [O pip aceita diretórios de projeto locais](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca o sistema de build deles; o [backend de build executa hooks de build controlados pelo projeto](https://pip.pypa.io/en/stable/reference/build-system/). Confirme a identidade efetiva de RunAs, as restrições e negações exatas dos argumentos, o controle do projeto selecionado e o comportamento do pip/backend instalado antes de considerar a regra uma execução de código privilegiada. Um projeto fixo e confiável ou uma regra que exclui caminhos selecionados pelo chamador não estabelece essa via. Analise a regra e os metadados do projeto sem instalar um pacote durante o inventário passivo.

Uma concessão irrestrita de `easy_install` com capacidade de root é uma indicação relacionada de build de pacotes legado. [A documentação do Setuptools](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) explica que o Easy Install aceita um diretório de projeto local e compila distribuições de código-fonte; um projeto controlado pelo chamador pode executar seu `setup.py` durante esse build, com a identidade do sudo. Confirme a conta RunAs efetiva, as restrições exatas de comando e argumentos (incluindo negações posteriores), o controle do projeto selecionado e o comportamento da ferramenta instalada. Um projeto fixo e confiável ou uma política que não permita uma origem selecionada pelo chamador não estabelece essa via. Inspecione a regra e os metadados do projeto sem instalar um pacote durante o inventário.

Um wrapper Python permitido pelo sudo que usa `setuptools.package_index.PackageIndex.download` com uma URL selecionada pelo chamador é um caso de análise diferente de `pip download`: [GHSA-5rjg-fvgr-3xxf do Setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descreve um nome de arquivo derivado da URL que escapa do diretório de download pretendido e grava com as permissões do processo em versões afetadas anteriores à 78.1.1. Confirme o RunAs e a regra de argumentos efetivos do sudo, se o wrapper passa a URL do chamador para essa API exata, o build instalado ou o patch retroportado pelo fornecedor e onde o caminho resultante é resolvido. Uma string de versão ou um diretório de download gravável, isoladamente, não estabelece escrita arbitrária. Analise o wrapper curto e os metadados do pacote sem buscar a URL nem gravar um arquivo durante o inventário.

Um wrapper de build permitido pelo sudo que passa um arquivo `.spec` selecionado pelo chamador ao PyInstaller exige a mesma análise de fronteira de confiança. Um arquivo spec do PyInstaller é Python executável avaliado durante o **build**, e suas entradas `datas` podem incluir em um artefato arquivos legíveis pela identidade de build. Confirme o usuário RunAs exato, as regras de argumentos e negações do sudo, o tratamento de caminhos e ramos do wrapper, o controle do arquivo spec selecionado e o acesso ao artefato resultante. Permitir apenas uma entrada `.py` ou encontrar o PyInstaller instalado não comprova o controle do arquivo spec nem a execução privilegiada. A análise passiva deve ler somente um arquivo wrapper de tamanho limitado e metadados; não deve executar um build. Consulte a [documentação de arquivos spec do PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Carregadores de presets e plugins executados pelo sudo

Ferramentas Python que aceitam um preset selecionado pelo chamador ou um diretório de plugins podem importar código com os privilégios concedidos pelo sudo. Por exemplo, o BBOT aceita um preset com `-p`, e sua [documentação de módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descreve entradas `module_dirs` que selecionam diretórios adicionais de módulos Python. Se a regra efetiva do sudo permitir um preset selecionado pelo chamador e este controlar um módulo no diretório selecionado, a importação poderá executar código como o usuário privilegiado, possivelmente antes de a ferramenta rejeitar um módulo inválido. Verifique a versão instalada, a política exata de RunAs e argumentos do sudo e a propriedade do preset e dos caminhos dos módulos sem carregar o módulo durante o inventário.

### Ferramenta de linha de comando Backdrop executada pelo sudo

O [Bee](https://github.com/backdrop-contrib/bee) é uma ferramenta PHP de linha de comando para Backdrop CMS. Seus comandos `eval` (`php-eval`) e `php-script` podem executar PHP fornecido pelo chamador. Portanto, uma regra de sudo que permita o executável Bee como root com argumentos irrestritos pode expor execução de código como root quando o Bee consegue inicializar uma instalação do Backdrop. Execute-o no diretório do site ou selecione um site usando a opção global `--root=<directory>`; encontrar o Bee ou um arquivo `settings.php` do Backdrop não comprova a permissão do sudo, a existência de um site utilizável nem uma inicialização bem-sucedida. Analise a regra efetiva do sudo, quaisquer exclusões de comando, a identidade do executável e o acesso ao site antes de testar. Durante o inventário passivo, inspecione a regra e os caminhos dos arquivos sem invocar o Bee. Consulte o [changelog de comandos do Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver a inclusão dos comandos PHP.

### Servidores de terminal executados pelo sudo

`mosh-server` inicia um servidor de terminal interativo como o usuário que o invoca. Ele escolhe uma porta UDP alta e uma chave de sessão, informa ambas ao chamador e normalmente inicia o shell de login desse usuário quando um cliente se conecta. Portanto, uma concessão irrestrita de sudo para `mosh-server` com capacidade de root é uma possibilidade de shell que merece análise, embora o próprio comando do servidor se desconecte. Verifique a identidade efetiva de RunAs, os argumentos e as exclusões permitidos, o binário instalado, o shell, a disponibilidade do cliente e o acesso UDP. O inventário passivo deve inspecionar a regra do sudo sem iniciar um servidor nem exibir qualquer chave de sessão ativa. Consulte o [manual do servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e as [notas de arquitetura do upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers privilegiados de backup que reescrevem um arquivo de tarefas do chamador

Um wrapper de shell executado como root pode aceitar um arquivo de tarefas selecionado pelo chamador, remover `../` dos caminhos de origem, verificar se cada resultado começa com um diretório permitido, reescrever o arquivo de tarefas e depois passar seu *caminho* a um programa de backup. Analise o caminho transformado após a resolução canônica completa: uma única substituição de string pode revelar uma nova sequência de travessia que uma verificação de prefixo lexical aceita. Verifique também se o programa de backup lê os dados transformados em memória ou abre o arquivo novamente. Se o abrir novamente, uma reescrita malsucedida pode deixar a entrada original no lugar.

No Linux, `fs.protected_regular` pode negar uma escrita com `O_CREAT` em um arquivo regular de outro usuário dentro de um diretório sticky gravável por todos. Essa negação é protetora, mas um wrapper de shell que ignore o erro de escrita ainda pode continuar usando o arquivo de tarefas original. Confirme a configuração, o proprietário do arquivo e do diretório e se o wrapper interrompe a execução em caso de falha. O caminho só é candidato a divulgação de arquivos quando a regra efetiva do sudo permite executar o wrapper como um usuário privilegiado, o chamador controla a entrada da tarefa e um destino de backup legível, e o utilitário de backup realmente inclui origens protegidas. Inspecione essas condições sem executar o backup durante o inventário.

### Curingas de argumentos em ferramentas de pacotes executadas com privilégios

Em uma regra de sudo para `tcpdump`, um `*` no **padrão de argumento** pode corresponder a espaços em branco e barras; portanto, uma restrição que parece limitar um caminho ainda pode permitir texto adicional de opções. Isso é diferente de um curinga no caminho do executável do comando; inspecione a regra RunAs completa e quaisquer negações posteriores. Se for possível injetar opções, a invocação permitida e a [semântica das opções do `tcpdump` instalado](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) determinam se `-F`, `-V`, `-r`, `-w` ou `-Z` oferecem uma primitiva útil de leitura/escrita. `-V` lê uma lista de nomes de arquivos de captura, não despeja arquivos arbitrários de uso geral. AppArmor ou outra política MAC pode bloquear o acesso a arquivos mesmo quando o sudo permite o comando; um arquivo de perfil no disco não comprova que ele esteja carregado ou aplicando restrições. Analise a autorização e a política passivamente antes de chegar a uma conclusão. O [manual do sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descreve a diferença entre curingas.

Uma regra de sudo com capacidade de root que liste somente o executável `tcpdump`, sem restrição de argumentos, também merece análise. O [manual do tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como um comando pós-rotação quando `-C` ou `-G` rotaciona uma captura salva; `-Z` ou um padrão definido durante a compilação pode remover privilégios antes da execução desse comando. Verifique a regra efetiva do sudo, o build instalado, o comportamento de remoção de privilégios e se pode ocorrer uma rotação antes de considerar a regra uma via de escalação. Uma regra destacada é uma possibilidade, não prova de execução de comandos como root.

### Wrappers Nmap executados pelo sudo

Quando o caminho de `nmap` permitido pelo sudo é um wrapper de shell, inspecione o caminho exato permitido e todas as opções encaminhadas por ele. Bloquear a grafia conhecida `--script` não bloqueia necessariamente o carregamento de código NSE: [`--datadir` do Nmap](https://nmap.org/book/man-misc-options.html) seleciona arquivos de dados, e o NSE [carrega `nse_main.lua`](https://nmap.org/book/nse-implementation.html) do diretório de dados selecionado quando o scripting está habilitado. Alguns builds instalados também aceitam grafias longas alternativas de opções; compare as restrições com o parser real desse binário. [`--excludefile`](https://nmap.org/book/man-target-specification.html) é uma superfície separada de leitura de arquivos; erros do parser podem revelar texto. Verifique a regra efetiva do sudo, a lógica do wrapper, a versão do Nmap, o controle do diretório e a política MAC sem executar varreduras durante o inventário.

### Hooks de pull do Mercurial executados pelo sudo

Uma origem fixa em `sudo hg pull /fixed/source` ainda deixa o repositório **de destino** selecionado pelo diretório de trabalho atual, a menos que o comando o fixe com `-R`. Um repositório de destino controlado pelo chamador pode definir hooks em `.hg/hgrc`, e um hook pode ser executado como o usuário RunAs do sudo. [O Mercurial ignora configurações de repositório pertencentes a um usuário ou grupo não confiável](https://mercurial-scm.org/help/topics/config); portanto, inspecione os usuários/grupos confiáveis da conta RunAs e o diretório de trabalho exato antes de considerar isso execução de código. Ler a política e a configuração é suficiente para uma análise passiva; não execute pull nem invoque um hook para verificá-lo.

### Hooks de pull do Git executados pelo sudo

Para uma concessão exata de `sudo git pull` com capacidade de root, verifique também o repositório **de destino** selecionado pelo diretório de trabalho. Um repositório pertencente ao chamador pode ter um hook `post-merge` executável, que roda com a identidade do processo Git quando um pull realiza uma mesclagem bem-sucedida; [o Git documenta esse hook](https://git-scm.com/docs/githooks) e o [comportamento de pull com merge versus rebase](https://git-scm.com/docs/git-pull). Verifique a regra efetiva do sudo e o CWD, o caminho do hook ativo e suas permissões, e se é possível chegar a uma mesclagem com novos commits. Um pull malsucedido, sem alterações ou que use somente rebase não comprova essa via de hook. Inspecione a política e os metadados do repositório sem executar o pull privilegiado.

### Cópias de arquivos com rsync executado pelo sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, um `*` no **padrão de argumentos do sudoers** pode corresponder a espaços e permitir uma opção adicional entre a origem e o destino. Isso é diferente da expansão de nomes de arquivo pelo shell. Se o chamador puder preencher a origem e o destino puder ser escrito pelo processo rsync privilegiado, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) pode solicitar propriedade privilegiada enquanto o modo archive preserva os bits de permissão, potencialmente criando um arquivo SetUID de propriedade privilegiada. Verifique a semântica exata dos [curingas do sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), a versão do rsync, as negações posteriores, `nosuid` do sistema de arquivos e a política MAC. Uma regra correspondente é uma possibilidade para análise, não uma prova de escalação de privilégios bem-sucedida.

### Exportação de regras de filtro de pacotes executada pelo sudo

Uma concessão irrestrita com capacidade de root para `iptables` e `iptables-save` (ou o par correspondente `ip6tables`) merece uma análise de escrita em arquivos. O match `comment` aceita texto de regra escolhido pelo chamador, enquanto `iptables-save -f` grava o conjunto de regras serializado em um caminho selecionado.<sup>[[20]](#references)[[21]](#references)</sup> Um payload útil depende de como o backend instalado serializa comentários e se o arquivo de destino aceita outras linhas na exportação; `iptables-save`, por si só, não fornece conteúdo arbitrário escolhido pelo chamador. Verifique a identidade RunAs exata do sudo, os argumentos e as exclusões, a extensão de match disponível, o backend e as permissões do destino. Durante o inventário, inspecione a concessão sem alterar regras do firewall nem gravar um arquivo.

### Diretório de logs privilegiado do Below

A [CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afetou versões do Below anteriores à 0.9.0 que criavam um diretório `/var/log/below` gravável por todos. Se um serviço ou comando permitido pelo sudo executar um build afetado como root, um usuário que possa escrever e atravessar um diretório de logs sem sticky bit talvez consiga substituir uma entrada de log por um symlink antes que o processo privilegiado a abra. Analise o status de correção do pacote instalado, o caminho exato de execução privilegiada, o acesso efetivo ao diretório, o sticky bit e as ACLs, e os metadados de `/var/log/below/error_root.log`. Um caminho gravável por todos ou uma regra de sudo, isoladamente, não estabelece a cadeia completa. Um diretório sticky ou um patch retroportado pelo fornecedor altera a avaliação. O inventário passivo deve inspecionar somente metadados; não é necessário criar um link nem executar o programa privilegiado.

### Coleta privilegiada de pacotes de suporte a partir de entradas graváveis

Um script de perfil de suporte permitido pelo `sudo` pode ler caminhos fixos de logs como root e copiar seu conteúdo para um arquivo de perfil. Analise o script real em busca de leituras de arquivos; em seguida, verifique se o chamador pode substituir um caminho de origem ou qualquer entrada do diretório pai por um symlink. Se a leitura privilegiada seguir esse link e o arquivo de perfil resultante puder ser lido pelo chamador, um arquivo protegido poderá ser divulgado. A concessão do sudo, o caminho de origem gravável, a leitura privilegiada e a saída legível precisam estar todos presentes; um log gravável ou um nome de arquivo de perfil, isoladamente, não basta. Inspecione as permissões efetivas e os metadados dos links sem substituir arquivos nem gerar um perfil durante o inventário. As [orientações de suporte do Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentam seu script de perfil executado como root e o arquivo de saída, ilustrando por que esses pacotes devem ter entradas e acesso de saída restritos.

### Scripts Python de restauração de arquivos executados como root

Uma regra de sudo estritamente limitada para um script Python de restauração ainda exige analisar sua entrada de arquivo compactado. Se o chamador puder selecionar ou substituir o arquivo e o script o extrair como root com `tarfile.extractall(filter="data")`, verifique as atualizações de segurança do interpretador antes de confiar no filtro. O CPython corrigiu várias formas de contornar o filtro por meio de symlinks e hard links, incluindo a CVE-2025-4517, nas versões 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. Backports de distribuições podem corrigir versões anteriores, portanto a versão exibida do interpretador, isoladamente, não comprova exposição.<sup>[[16]](#references)[[17]](#references)</sup>

Para uma análise passiva, leia o comando exato do sudo e o script, rastreie qual argumento seleciona o arquivo e verifique se o usuário atual pode gravar o arquivo ou o diretório que o contém. Confirme separadamente o patch do fornecedor instalado e o destino da extração; `filter="data"` não torna seguro qualquer arquivo compactado não confiável.<sup>[[16]](#references)[[17]](#references)</sup>

### Carregadores de modelos de aprendizado de máquina executados pelo sudo

Uma regra de sudo que permita um arquivo `.pt`, `.pth` ou `.ckpt` selecionado pelo chamador merece análise quando um script privilegiado passa esse arquivo para [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` ou outro carregador baseado em pickle. Verifique a regra efetiva de RunAs, se o chamador pode criar ou substituir o modelo selecionado e o fluxo real dos argumentos por qualquer wrapper de shell até o helper Python. A extensão `.pth` também é usada por arquivos de configuração de site Python sem relação com modelos; portanto, a extensão, isoladamente, não comprova o carregamento de um modelo. Uma varredura de arquivo compactado ou uma análise estática de pickle não comprova que o carregamento posterior seja seguro; inspecione o comportamento de [`weights_only` dependente da versão](https://docs.pytorch.org/docs/stable/notes/serialization.html) do carregador e qualquer lista de permissões. Consulte as [notas sobre pickle em ML e Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). O inventário passivo nunca deve carregar nem descompactar o modelo.

### Análise de expressões de entradas armazenadas executada pelo sudo

Um script Python fixo executado como root por meio do sudo ainda pode avaliar texto que um usuário com menos privilégios consiga armazenar em um banco de dados de aplicativo. No TensorFlow, uma chamada a `preprocess_input_exprs_arg_string(value, safe=False)` seleciona um caminho com `eval`; o [aviso de segurança do TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descreve o parser inseguro e uma correção para seu chamador de linha de comando. Uma chamada explícita do aplicativo a `safe=False` precisa de análise separada, mesmo quando esse chamador de linha de comando está corrigido. Verifique a regra efetiva do sudo, quem pode modificar a linha de entrada específica, se a filtragem ou a pontuação permite que essa linha chegue à chamada e o comportamento da função instalada. Uma versão do TensorFlow, uma concessão de sudo ou um arquivo de modelo fixo, isoladamente, não comprovam a cadeia. Inspecione o script e o fluxo de dados passivamente; não execute o helper privilegiado nem envie expressões de teste durante o inventário.

### Configuração do needrestart permitida pelo sudo

`needrestart -c` carrega um arquivo de configuração Perl selecionado pelo chamador e avalia seu conteúdo. Se `sudo -l` permitir executar `needrestart` como root com argumentos que permitam `-c`, e o chamador puder escolher um arquivo de configuração legível em um local gravável, essa permissão poderá levar à execução de código como root. Verifique a regra exata de RunAs e argumentos do sudo; uma regra que permita apenas uma lista fixa de argumentos pode bloquear essa via. Isso é separado das vulnerabilidades de varredura de interpretadores do needrestart: atualizar o pacote ou desabilitar `interpscan` não torna segura uma concessão irrestrita de `-c` como root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports Python executados pelo sudo com outra conta

Um ponto de entrada Python fixo ainda pode importar um módulo que o chamador consegue editar ou substituir, inclusive quando o sudo executa o script como um usuário de serviço **que não seja root**. Para um `from utils import status` literal, analise `utils/__init__.py` e `utils/status.py` locais, além das permissões do diretório do pacote. Confirme o caminho de importação do script, os argumentos exatos permitidos pelo sudo e se a ação relevante chega a esse import antes de considerar o arquivo gravável uma via de execução. Inspecione arquivos e permissões sem importar nem executar o script durante o inventário.<sup>[[2]](#references)[[3]](#references)</sup>

Uma regra exata do sudo para `python3 /absolute/script.py` só exige que o script seja legível; o arquivo não precisa ser executável nem ter shebang. Analise também os módulos locais **ausentes**: se o script importar um módulo cujo nome de arquivo possa ser criado em um diretório do script gravável pelo chamador, o Python poderá carregar esse arquivo com a identidade RunAs. Confirme a regra efetiva do sudo, o [caminho de busca de módulos](https://docs.python.org/3/library/sys_path_init.html) real do interpretador, se o módulo é interno ou congelado e se o import é alcançado. Uma regra direta de sudo para o script tem requisitos diferentes de bit de execução e shebang. Um wrapper separado que acrescenta tokens fornecidos pelo chamador após `sudo -u account` também exige análise do fluxo de argumentos: outro `-u` nesses tokens só importa se a política do sudo invocado permitir a identidade resultante. Strings estáticas, por si sós, não comprovam nenhuma das vias.

### Apache executado pelo sudo com configuração controlada pelo chamador

Se uma regra de sudo permitir uma invocação privilegiada de `apachectl`, `apache2ctl` ou `httpd` com um arquivo de configuração `-f` controlado pelo chamador, analise as permissões desse arquivo e do diretório pai. A diretiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) do Apache recebe um nome de módulo seguido pelo **nome do arquivo do módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) também carrega um arquivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) podem ampliar a configuração ou expor o conteúdo de arquivos por meio de erros. Um wrapper personalizado pode validar esses caminhos, remover privilégios ou restringir argumentos; portanto, uma configuração gravável é uma possibilidade para análise, não prova de execução de código. Verifique a canonicalização dos caminhos, os symlinks e a análise das diretivas antes de chegar a uma conclusão.

### nginx executado pelo sudo com configuração controlada pelo chamador

Uma regra irrestrita de `nginx` com capacidade de root pode permitir que [`-c` selecione outra configuração](https://nginx.org/en/docs/switches.html). Analise os argumentos e as exclusões exatos do sudo, se o chamador pode fornecer a configuração e se o master ou os workers resultantes mantêm acesso a caminhos protegidos. Um `root` escolhido combinado com `autoindex` pode expor arquivos por meio de um novo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) pode fornecer uma via privilegiada de escrita em arquivos, mas o módulo DAV não é compilado por padrão, e é preciso verificar sua presença, a acessibilidade do listener, as permissões dos arquivos e o comportamento dos arquivos temporários. A diretiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) também pode apontar para um arquivo escolhido; gravar logs em um arquivo de configuração sensível, como `/etc/ld.so.preload`, exige um gravador efetivamente privilegiado e um registro de log controlável para se tornar uma via de escalação. O destaque do executável em `sudo -l` é uma indicação para análise, não prova de que qualquer uma dessas vias funcione. O inventário passivo não deve iniciar nem reconfigurar o nginx.

### Comparação de padrões em prompts Bash privilegiados

Quando um script Bash permitido pelo sudo lê um valor do chamador e o verifica com `[[ "$expected" == $entered ]]`, o Bash interpreta o operando à direita, sem aspas, como um padrão. Portanto, um curinga pode satisfazer a comparação sem conhecer o valor esperado. Colocar o operando entre aspas (`[[ "$expected" == "$entered" ]]`) faz uma comparação literal de strings. Analise a regra exata do sudo, se o prompt pode ser alcançado e o que o script faz após a comparação; a sintaxe, por si só, não estabelece uma via explorável. Evite exibir o valor esperado durante o inventário. Consulte a [referência de construções condicionais do Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers executados pelo sudo que baixam e executam um arquivo

Uma concessão irrestrita de sudo com capacidade de root para um helper personalizado merece uma análise de fluxo de dados se ele aceitar uma URL selecionada pelo chamador, gravar a resposta em disco e depois invocar o arquivo com um interpretador ou shell. [O sudoers permite argumentos arbitrários quando uma entrada de comando não lista nenhum](https://man7.org/linux/man-pages/man5/sudoers.5.html); um caminho fixo de executável não restringe o que seus argumentos podem selecionar. Confirme a validação real da URL, o caminho de saída, o ramo de sucesso e a execução posterior no helper instalado. Uma importação correspondente de libcurl ou uma string imprimível, isoladamente, não comprova essa cadeia.

Mesmo um nome de arquivo de saída fixo pode ser substituível entre a gravação e a execução quando o helper usa um **caminho relativo em um diretório de trabalho controlado pelo chamador**. A renomeação ou substituição de um arquivo de propriedade de root depende do acesso de escrita e busca no diretório e de eventuais restrições do sticky bit, não apenas do modo do arquivo; consulte [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifique se o helper reabre o caminho depois ou usa o descritor já aberto, e se muda para um diretório confiável antes de gravar. Inspecione passivamente a política do sudo, o helper e os metadados do diretório; não invoque o download privilegiado nem tente uma corrida durante o inventário.

Um helper de download executado com sudo como root também pode expor uma injeção de **argumentos** quando monta uma string de comando Bash, como `curl <caller input> -o <fixed output>`. Um filtro que rejeita espaços em branco ainda permite a [expansão de chaves do Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementos separados por vírgulas e sem aspas podem se tornar argumentos curl distintos. Se a entrada chegar ao curl antes do `-o` fixo, uma opção de saída fornecida pelo chamador poderá selecionar o destino da primeira URL, usando a identidade do helper; [o curl associa opções de saída às URLs por ordem](https://curl.se/docs/manpage.html#-o). Confirme o shell exato, as aspas, a validação da entrada, a regra efetiva do sudo, a ordem dos argumentos do curl e os esquemas de URL aceitos, e se o chamador controla os bytes baixados ou pode ler o resultado. Um executável empacotado com PyInstaller pode conter lógica de aplicativo Python, mas a indicação de empacotamento ou uma string `curl`, isoladamente, não comprova esse fluxo de dados. Analise uma cópia offline limitada quando autorizado; o inventário rotineiro não deve executar o helper nem buscar dados escolhidos pelo atacante.

Um script de shell executado como root pelo sudo que chama [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) apenas escolhe um nome não usado; ele **não** cria o arquivo. Se o script depois criar esse nome em um diretório que outro usuário possa afetar, reabri-lo e acrescentar seu conteúdo a um destino protegido, como o `authorized_keys` de root, analise uma possível corrida com arquivo temporário. Confirme a regra exata do sudo, o proprietário do diretório e do arquivo, a sequência de criação e reabertura, as proteções do kernel e se a escrita privilegiada realmente usa bytes controlados pelo atacante. Uma string `mktemp -u` ou um `/tmp` gravável, isoladamente, não comprova a corrida. Inspecione o script e os metadados do caminho sem executá-lo nem tentar competir pelo arquivo temporário durante o inventário.

## Observações defensivas

- Evite conceder interpretadores ou editores interativos pelo sudo.<sup>[[1]](#references)</sup>
- Não conceda gravadores genéricos de arquivos, como `tee`, com operandos irrestritos. Use um wrapper de propriedade de root que selecione um destino fixo e rejeite caminhos controlados pelo chamador.<sup>[[2]](#references)</sup>
- Prefira wrappers fixos, de propriedade de root, que executem uma única ação administrativa restrita.<sup>[[1]](#references)[[2]](#references)</sup>
- Se um interpretador for inevitável, restrinja o caminho exato do script e impeça argumentos controlados pelo usuário, imports graváveis, `PYTHONPATH` e a preservação de ambientes inseguros.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se for necessário editar arquivos, restrinja o caminho exato do arquivo e considere `sudoedit` com versões corrigidas do sudo e tratamento rigoroso do ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Analise `SETENV`, `env_keep`, diretórios de trabalho graváveis, caminhos de módulos/imports graváveis, `NOEXEC`, `use_pty` e o registro em logs, mas não os trate como uma sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
