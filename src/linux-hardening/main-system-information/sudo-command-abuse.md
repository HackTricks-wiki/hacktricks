## Інтерпретатори, дозволені через Sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерпретатор від root, вважайте це прямим виконанням коду. Інтерпретатори призначені для виконання довільного коду, тож правило, яке дозволяє запускати `python3`, `perl`, `ruby`, `lua`, `node` або подібні бінарні файли, зазвичай еквівалентне виконанню команд від root, якщо аргументи не мають суворих обмежень і не проходять перевірку.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Типовий порядок перевірки: спочатку перегляньте привілеї користувача, а потім виконайте інструкцію Python за допомогою опції `-c` інтерпретатора.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Інші приклади інтерпретаторів наведено нижче; у документації перелічених інтерпретаторів описано виконання inline-коду або API дочірніх процесів.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Точний шлях має значення. Якщо правило sudo дозволяє `/usr/bin/python3`, під час перевірки використовуйте саме цей шлях.<sup>[[2]](#references)</sup>

Glob для виконуваного файла sudo, наприклад `/usr/bin/python*`, також може дозволити запуск Python 2 для скрипту, написаного для Python 3. Якщо скрипт викликає `input()` із текстом, контрольованим користувачем, [Python 2 обчислює цей текст як вираз](https://docs.python.org/2/library/functions.html#input); явний виклик інтерпретатора перевизначає shebang скрипту. Перш ніж вважати це шляхом до виконання коду, перевірте відповідні встановлені бінарні файли, ефективний RunAs і політику аргументів, відмови в доступі та наявність доступного вводу.

Фіксований шлях до скрипту в правилі sudo із правами root не обмежує, що саме виконує скрипт. Для доступної для читання Bash-обгортки перевірте, чи використовує її перша виконувана команда неекранований позиційний параметр, як-от `$1`, як **слово команди**, тоді як sudo дозволяє аргументи, вибрані користувачем. Перевірте ефективну ідентичність RunAs, політику пароля й аргументів, подальші відмови в доступі та фактичну гілку скрипту; `NOEXEC`, фіксований безпечний список аргументів або обгортка, яка перевіряє команду, можуть змінити результат. Під час переліку статично перегляньте короткий скрипт замість того, щоб викликати його з тестовою командою.

Необмежене правило sudo із правами root для `dotnet` також потребує перевірки можливостей інтерпретатора. Якщо встановлено .NET SDK, [`dotnet fsi` запускає код F# інтерактивно або зі скрипту](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), а [`dotnet run` виконує проєкт із вихідного коду](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Спершу перевірте ефективну ідентичність RunAs і точну політику аргументів: правило, обмежене певною безпечною підкомандою або довіреною програмою, є іншим дозволом, а інсталяція лише середовища виконання може не містити команд SDK. Сама назва виконуваного файла — це привід для перевірки, а не доказ можливості виконання коду.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Дозволений через sudo `tee`: довільний запис у файл із привілеями

GNU `tee` копіює стандартне введення до кожного шляху, переданого як файловий операнд. Отже, правило sudo, яке дозволяє запускати `/usr/bin/tee` від root із аргументами, контрольованими користувачем, надає можливість довільно створювати файли від root або перезаписувати їх. Параметр `-a` змінює цю можливість на дозаписування. Тег `PASSWD:` стосується автентифікації sudo; сам по собі він не обмежує місце призначення чи байти, зчитані зі стандартного введення.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Спочатку перевірте точне правило. В авторизованій тестовій системі перевіряйте цю можливість лише на тимчасовому файлі, який безпечно створити. Кінцеве перенаправлення `>/dev/null` лише приховує копію, яку `tee` виводить у стандартний вивід.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Запуск `sudo` перед producer не підвищує привілеї для подальшого перенаправлення виводу оболонкою, оскільки файл призначення відкриває оболонка користувача. Записувати має привілейований процес, як у наведеному вище конвеєрі.<sup>[[1]](#references)[[15]](#references)</sup>

Після підтвердження можливості запису виберіть відповідний спосіб виконання коду від root із розділу [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). В одному з зафіксованих ланцюжків root використовував `tee`, щоб створити короткочасний файл у `/etc/cron.d/`, запустити backdoor через скрипт, контрольований користувачем, і видалити файл cron після виконання. Видалення файлу cron не дало йому стати довготривалим записом persistence, хоча системні журнали все одно зберегли свідчення цієї активності.<sup>[[27]](#references)</sup>

## Редактори, дозволені через sudo

Якщо `sudo -l` дозволяє користувачу запускати інтерактивний редактор від root, вважайте це можливістю виконання команд, а не нешкідливим дозволом на редагування файлів. Редактори часто можуть виконувати команди оболонки, читати довільні файли, записувати довільні файли або викликати зовнішні допоміжні програми з редактора.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Типовий порядок перевірки: перегляньте привілеї користувача, а потім запустіть кожен дозволений редактор або pager через sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano command execution

Коли запуск nano дозволено через sudo, command execution може бути доступне з інтерфейсу редактора.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Потім введіть у командний рядок nano команду, наприклад `id` або `/bin/sh`.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Якщо інтерактивна оболонка не має доступних для використання термінальних потоків, ця форма перенаправлення спрямовує її стандартний вивід і потік помилок до дескриптора 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Точна послідовність клавіш може відрізнятися залежно від версії nano та параметрів збірки, але проблема безпеки та сама: редактор працює від імені root і може викликати зовнішні команди.<sup>[[1]](#references)[[12]](#references)</sup>

### Інші поширені способи виходу з редактора

Редактори на кшталт Vim зазвичай дають змогу виконувати команди через `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Пейджери на кшталт `less` також можуть надавати можливість запускати команди оболонки.<sup>[[14]](#references)</sup>

Правило sudo, яке дозволяє запускати `apport-cli` від root, також потребує перевірки пейджера. У вразливих версіях Apport звіт про збій можна було відкрити в `less` із розміром термінала, який міг змінити атакувальник; за певних умов для sudo та пейджера це могло надати root shell. Перш ніж вважати версію вразливою, перевірте чинне правило sudo, налаштування пейджера та виправлення в пакеті дистрибутива. Під час пасивного збору даних читайте метадані пакета й політики, не спричиняючи збій і не відкриваючи привілейований звіт. [Запис CVE в Ubuntu](https://ubuntu.com/security/CVE-2023-1326) містить версії пакетів із виправленнями для окремих випусків, зокрема виправлення, перенесені до старіших версій.

```text
!/bin/sh
```

## Інші небезпеки правил sudo і doas

Почніть із `sudo -l`, `sudo -V` і відповідної політики `doas`. Розглядайте разом дозволену команду, користувача RunAs, аргументи, середовище та параметри за замовчуванням. Дозвіл запускати команди від імені непривілейованого сервісного облікового запису все одно може відкрити доступ до файлів цього облікового запису або шлях до root.

Фіксований Python-скрипт, дозволений через sudo, усе одно може запускати shell-команду з ідентичністю RunAs, якщо введення, яке контролює користувач і яке вводиться інтерактивно, конкатенується в [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Чорного списку символів пунктуації shell недостатньо, щоб підтвердити безпечність: [shell також розпізнає підстановку команд `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Переконайтеся, що дозволені аргументи доходять до гілки з введенням, введення потрапляє до shell-команди без безпечної перевірки, а чинна політика sudo дозволяє потрібного користувача RunAs. Шлях до скрипту або виклик `os.system()` самі по собі є лише приводом для перевірки; вивчайте вихідний код, не запускаючи привілейований скрипт.

Чинний дозвіл sudo для root на `chattr` може зняти атрибут незмінності (`i`) з файла, але сам по собі не надає права запису чи нової ідентичності. [Посібник `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) зазначає, що цей атрибут блокує зміну, а змінити його може лише root або процес із `CAP_LINUX_IMMUTABLE`. Перевірте точні обмеження аргументів sudo та підтримку файловою системою, а потім окремо з’ясуйте, чи може користувач записувати у файл після зняття атрибута і чи використовує його компонент із вищою ідентичністю. Наприклад, заміна оболонки входу також потребує облікових даних, прийнятих цільовим обліковим записом, і фактичного входу через цю оболонку. Під час переліку перевіряйте політику, атрибути файлів і дозволи, не змінюючи їх.

Якщо sudo запитує і пароль, і одноразовий код, розглядайте ці вимоги окремо від дозволу на команду. Файл `.google_authenticator`, доступний для читання, містить чутливий секретний seed, а старий хеш пароля застосунку чи бази даних — лише можливий пароль поточного облікового запису; жоден із них не доводить, що чинна конфігурація PAM приймає інший фактор. Після отримання дозволу перевірте точні RunAs і аргументи: необмежений дозвіл root на RubyGems `gem` може відкрити його команду редактора ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), але обмежене правило або невдала автентифікація — ні. Пасивний збір даних має фіксувати шляхи й політику, не показуючи seed, не відновлюючи пароль, не генеруючи код і не запускаючи привілейовану команду.

Необмежений дозвіл sudo для root на Chef `knife` потребує перевірки на рівні інтерпретатора: [Chef документує, що `knife exec -E` локально обчислює рядок Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Переконайтеся, що чинне правило sudo дозволяє підкоманду `exec` і аргумент `-E`, заданий користувачем, потрібну ідентичність RunAs та будь-які відповідні заборони команд або фіксовані аргументи. Встановлений бінарний файл або правило, обмежене іншими підкомандами, — лише зачіпка для перевірки. Пасивний збір даних має фіксувати правило, не запускаючи `knife`.

Точний дозвіл sudo для root на інтерактивний `msfconsole` так само чутливий: [GTFOBins описує його консоль `irb`](https://gtfobins.org/gtfobins/msfconsole/), яка може успадкувати ідентичність sudo. Перевірте ефективного користувача RunAs, дозволений список аргументів, заборони команд, `NOEXEC` чи інші обмеження, поведінку встановленої консолі та можливість користувача вводити дані інтерактивно. Саме лише підсвічування шляху — привід для перевірки; під час пасивного збору даних консоль запускати не слід.

У FreeBSD навіть правило sudo, обмежене командами root `pkg update` і `pkg install *`, потребує перевірки довіри до репозиторію. З’ясуйте, чи може користувач записувати в `/etc/hosts` і чи використовує *чинна* конфігурація ввімкнених репозиторіїв HTTP-ім’я хоста з `signature_type: none`. [Посібник FreeBSD `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) зазначає, що `none` вимикає перевірки підписів; самого `pkg+http` для такого висновку недостатньо. Пакет може містити скрипти встановлення ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), тож користувач, який справді контролює кінцеву адресу репозиторію і може вибрати пакет, може подолати межу привілеїв root. Перш ніж робити такий висновок, перевірте перевизначення репозиторіїв, розв’язання SRV/дзеркал, ефективні аргументи sudo, вибір пакета та виконання скриптів. Під час переліку перевіряйте політику й невеликі локальні файли конфігурації, не перенаправляючи імена й не запускаючи `pkg`.

Правило sudo для root на `apt-get update` і `apt-get upgrade` також потребує перевірки довіри до репозиторіїв, якщо sudo зберігає змінну `http_proxy`, яку контролює користувач. Перевірте, чи використовує її чинна конфігурація APT як проксі та на які ввімкнені запити до репозиторіїв вона може впливати; сам проксі не може підмінити пакети з архіву, автентифікованого довіреним ключем підпису. [Посібник HTTP-транспорту APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) описує пріоритет проксі, а [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — перевірки підписів, перевизначення для незахищених репозиторіїв і підтвердження для неавтентифікованих пакетів. Перевірте точні RunAs і аргументи sudo, політику автентифікації репозиторіїв, потребу в інтерактивному підтвердженні та чи запускається скрипт пакета під час оновлення від root. Перевіряйте політику й локальну конфігурацію пасивно; не перенаправляйте трафік пакетів і не запускайте оновлення під час переліку.

Правило sudo для root на `snap install` може створити межу між пакетом і кодом, якщо його аргументи дозволяють користувачу вибрати локальний snap і режим встановлення з послабленими обмеженнями. [У документації Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) зазначено, що `--dangerous` пропускає перевірку тверджень для локального snap, а `--devmode` послаблює ізоляцію; [hook встановлення може запускатися під час першого встановлення](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Перш ніж стверджувати, що це дає доступ до захищених файлів хоста, перевірте точну політику sudo щодо аргументів і RunAs, хто контролює файл snap, чи приймає ці режими встановлений snapd, а також ефективну ідентичність і рівень ізоляції hook. Сам бінарний файл `snap` або правило, схоже на шаблон із wildcard, цього ланцюжка не доводять. Під час пасивного збору даних не встановлюйте пакети й не запускайте їхні hook.

Для точного дозволу sudo на бінарний файл читання облікових даних, призначений для **не-root** облікового запису, спочатку перевірте наданий бінарний файл і дозволи на нього, не запускаючи його. Вбудований запит пароля може відображатися лише як широкі символи; [GNU `strings` документує вилучення 16-бітних рядків у форматі little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Видимий рядок не доводить, що це прийнятий пароль або що гілка успішної автентифікації відкриває чинні облікові дані. Окремо перевірте поведінку бінарного файла, доступ цільового облікового запису до захищених даних, чинність облікових даних і будь-який подальший перехід між обліковими записами чи групами. Якщо цей обліковий запис входить до групи `docker`, перевірте доступ до сокета й ідентичність rootful або rootless демона, перш ніж робити висновок про доступ до root хоста; [Docker описує наслідки для рівня root членства в цій групі](https://docs.docker.com/engine/install/linux-postinstall/). Звичайний збір даних має фіксувати правило sudo й членство в групі, не запускаючи бінарний файл і не виводячи його рядки.

Правило sudo з wildcard для скриптів обслуговування програми потрібно перевіряти не лише за шляхом до скрипту. З’ясуйте, чи приймає дозволений скрипт необмежені аргументи або читає налаштування, доступні для запису менш привілейованому обліковому запису програми, а потім простежте, як ці значення потрапляють до shell-команд або середовища підпроцесу. Наприклад, ZoneMinder [`zmupdate.pl` формує команду `mysqldump` і запускає її через `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), а [`zmdc.pl` копіює параметр `ZM_LD_PRELOAD` у `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) перед запуском демонів. Правило sudo, що дозволяє запускати будь-який із цих скриптів від root, може порушити межу довіри, якщо відповідне введення контролюється користувачем і доходить до цього коду у встановленій версії. Перевірте чинне правило sudo, права на конфігурацію програми та вихідний код скрипту; wildcard або окреме налаштування — лише привід для перевірки, а не доказ виконання.

- `SETENV`, `env_keep`, `secure_path` і `LD_PRELOAD` можуть перетворити інакше вузько обмежену команду на перехоплення імпорту, бібліотеки або PATH. Див. [посібник зі змінних середовища](../linux-basics/linux-environment-variables.md) і [зловживання SUID/лінкером](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Точний дозвіл sudo з можливістю root і тегом `SETENV` для shell-обгортки також потребує перевірки на один крок, якщо обгортка запускає фіксований Python-скрипт із буквальним імпортом. `secure_path` обмежує пошук shell-команд, а не пошук модулів Python через [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); параметри [`-E` і `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) змушують Python ігнорувати цю змінну середовища. Перш ніж вважати це виконанням коду, перевірте чинні теги й заборони sudo, гілку обгортки, параметри інтерпретатора, розв’язання імпорту та наявність каталогу пошуку, доступного для запису користувачу. Короткі скрипти перевіряйте статично; не запускайте привілейовану обгортку.

Точний дозвіл sudo для root на `neofetch ""` усе одно може завантажити конфігурацію shell, якщо відповідні параметри sudo зберігають змінну `XDG_CONFIG_HOME`, контрольовану користувачем. [Завантажувач конфігурації Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) підключає `neofetch/config.conf` або `neofetch/config` із цього каталогу; порожній список аргументів не перешкоджає такому пошуку. Перевірте завантажувач у встановленій версії, чинні RunAs і політику аргументів, будь-які заборони команд, чи справді sudo зберігає вибрану змінну для цієї команди та чи контролює користувач доступний для читання шлях до конфігурації. Збережена змінна або встановлений Neofetch самі по собі — лише привід для перевірки. Перевіряйте політику й метадані файлів, не запускаючи привілейовану команду та не виводячи вміст конфігурації; див. [обробку середовища sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Необмежене правило sudo для root на `facter` потребує окремої перевірки користувацьких фактів. [У документації Puppet зазначено](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm), що `--custom-dir` завантажує файли фактів Ruby із вибраного каталогу. Перевірте, чи дозволяє точне правило sudo цей параметр, чи приймає його встановлений Facter і чи контролює користувач цей каталог. Фіксований набір аргументів, явна заборона команди або вимкнені користувацькі факти можуть змінити результат. Пасивний збір даних має фіксувати потенційне правило, не запускаючи Facter і не читаючи вміст файлів фактів.

Для точного дозволу sudo на root-скрипт із `SETENV` перевірте голі назви команд, як-от `find`, і чинний `PATH` після застосування політики sudo та ініціалізації скрипту. Підключений файл Bash також може виконати `enable -n [`: [після цього Bash шукає зовнішню команду `[` у `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), коли скрипт пізніше її використовує. Перевірте відповідні [правила середовища sudoers і `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), будь-які записи `NOSETENV`/`NOEXEC` чи заборони, перебіг виконання скрипту й підключених файлів, а також наявність каталогу пошуку з виконуваним файлом, доступного користувачу. Скрипт для читання, що містить голу назву команди, — привід для перевірки, а не доказ привілейованого виконання; досліджуйте його, не запускаючи через правило sudo.
- Привілейований скрипт, який отримує дані з фіксованої URL-адреси через `curl`, усе одно може приймати відповідь, вибрану користувачем, якщо відповідне правило sudo зберігає `http_proxy`, а запит іде через цей проксі. Якщо потім скрипт передає відповідь XML-парсеру, який розв’язує зовнішні сутності, шкідлива відповідь може розкрити файли, доступні привілейованому процесу. Перевірте точну політику середовища sudo, виключення `no_proxy`, запитувану URL-адресу, конфігурацію парсера та місце виведення; сама змінна проксі або XML-парсер не є вразливістю. У [документації змінних середовища проксі для curl](https://everything.curl.dev/usingcurl/proxies/env.html) описано поведінку цих змінних. Під час пасивного збору даних не виконуйте мережевих запитів і не обробляйте шкідливий XML.
- Root-скрипт sudo, який формує файл PostScript із даних, на які впливає користувач, а потім запускає `ps2pdf -dNOSAFER`, потребує окремого аналізу потоку введення. У документації Ghostscript зазначено, що цей прапорець вимикає SAFER до виклику `.setsafe`, дозволяючи операції з файлами в межах дозволів процесу в ОС. SQL-запит, сформований з аргументу користувача, може передати контрольовані зловмисником рядки до шаблону PostScript, але сам рядок запиту або виклик `ps2pdf` не доводять, що ці дані потрапляють до виконуваного синтаксису PostScript. Перевірте чинне правило sudo, точний шлях від введення до шаблону, екранування, поведінку встановленої версії Ghostscript і чи знову вмикається SAFER до інтерпретації документа. Під час пасивного збору даних не запускайте привілейоване перетворення. Див. [документацію Ghostscript щодо `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Для правила sudo, що запускає shell-скрипт, порівняйте збережені змінні зі самим скриптом. Конструкція на кшталт `if $CHECK_CONTENT; then` запускає розгорнуте значення як команду, тож збереження `CHECK_CONTENT` може дозволити виконання команди навіть за фіксованого шляху до скрипту й аргументів. Для конкретного правила потрібно перевірити, чи доступна ця гілка і чи справді зберігається змінна середовища.<sup>[[2]](#references)[[22]](#references)</sup>
- Python-скрипт, дозволений через sudo, може імпортувати код із каталогу, доступного для запису, або кешованого файла `.pyc`. У [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md) описано випадок із кешем.
- Фіксований Python-скрипт, дозволений через sudo для запуску від root, усе одно може відкрити інтерактивний налагоджувач. Виклики на кшталт `pdb.set_trace()` або `pdb.post_mortem()` дозволяють виконувати Python-інструкції в контексті процесу, що налагоджується, якщо користувач може досягти точки зупинки або обробника винятків **і контролювати потік введення налагоджувача**. Перевірте точне правило sudo щодо RunAs, автентифікацію й умови гілки, досяжність винятку, власника термінала/введення та чи працює налагоджувач у тому самому привілейованому процесі. Запит через сокет, що викликає виняток, сам по собі не дає доступу до налагоджувача, підключеного до іншого термінала. [У документації Python описано виконання інструкцій налагоджувачем і режим post-mortem](https://docs.python.org/3/library/pdb.html); під час переліку вивчайте скрипт статично, не викликаючи привілейований обробник.
- Фіксований Python-скрипт, дозволений через sudo, може зчитати поле профілю з бази даних або Unix-сокета та додати його до рядка, який згодом стає **рядком форматування** для `str.format()`. [Поля заміни можуть містити атрибути й ключі відображення](https://docs.python.org/3/library/string.html#format-string-syntax), тож поле, контрольоване зловмисником, може перевіряти об’єкти, передані в `format()`, і розкривати доступні з них дані, якщо результат виводиться або зберігається там, де його може прочитати користувач. Перевірте ефективну ідентичність RunAs, право запису до конкретного запису, потік даних до рядка форматування, передані об’єкти та видимість результату. Це не автоматичне виконання коду, а літеральний довірений рядок форматування з контрольованими зловмисником *значеннями* — інший випадок. Розкрита таємниця забезпечує перехід до облікового запису ОС лише тоді, коли цей обліковий запис її приймає. Перевіряйте скрипт і дозволи на сокет, не запускаючи привілейовану операцію.
- Python-обгортка, здатна працювати від root, може передавати URL, вибрану користувачем, у `Repo.clone_from` бібліотеки GitPython. Якщо обгортка також вмикає Git `protocol.ext.allow=always`, віддалена адреса `ext::` може запускати зовнішній помічник. Перевірте точні аргументи sudo, джерело URL, версію пакета GitPython і наявність виправлень постачальника, а також чи явно вмикає обгортка небезпечні протоколи. У GitPython додали [типовий захист від небезпечних протоколів](https://github.com/gitpython-developers/GitPython/commit/2625ed9) у версії 3.1.30; версія виконуваного файла `git` — окремий факт. Під час пасивної перевірки читайте лише правило й обмежену частину вихідного коду, не запускаючи клонування.
- Дозвіл sudo для переходу між обліковими записами на CLI-клієнт клонування репозиторіїв може відкрити окремий шлях ін’єкції shell-рядка. Простежте, чи передається вибраний користувачем аргумент репозиторію до Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) або іншого засобу формування shell-команди без безпечного розділення аргументів; Node `exec` передає рядок команди в shell. Перевірте точного користувача RunAs, дозволені підкоманди й аргументи, код встановленої обгортки та перевірку введення. Сама назва інструмента для роботи з репозиторіями або необмежене правило sudo не доводять наявності ін’єкції команд. Під час переліку перевіряйте обгортку, не запускаючи привілейоване клонування.
- Користувацька обгортка, власником якої є root, може здаватися безпечною, бо її бінарні файли й скрипти недоступні для запису, але рішення виконати привілейовану дію може залежати від прапорця, значення локального API або стану сервісу, який може змінити непривілейований користувач. Простежте кожну умову до її джерела й перевірок авторизації. Під час переліку перевіряйте конфігурацію й дозволи, не змінюючи операційного стану; виклик `systemd-run` усередині обгортки має значення лише тоді, коли на умову можна вплинути.
- Клієнт резервного копіювання, дозволений через sudo для запуску від root, може приймати вибраний користувачем файл конфігурації (наприклад, `npbackup-cli -c`). Перевірте точного користувача запуску й дозволені аргументи, а потім з’ясуйте, чи контролює користувач шлях до конфігурації, вихідні шляхи резервного копіювання та параметри доступу до репозиторію або читання/відновлення. Зашифрований секрет репозиторію в доступному для читання файлі конфігурації все одно може бути придатним для клієнта, але саме правило не доводить доступу до репозиторію чи розкриття файлів root. Перевіряйте авторизацію, не запускаючи резервне копіювання й не виводячи його вміст.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) підтримує `--password-command`, який запускає програму для отримання пароля репозиторію. Якщо правило sudo дозволяє менш привілейованому користувачу запускати restic від root із командою пароля, вибраною користувачем, і підкомандою, якій потрібен пароль, ця допоміжна програма може запуститися від root. Перевірте точні аргументи й виключення sudo; не запускайте допоміжну програму чи команду резервного копіювання лише для перевірки цієї умови.
- Привілейований дозвіл на `restic backup` також може перетнути межу доступу до файлів, якщо шаблон аргументів sudo дозволяє користувачу вибрати і джерело, і репозиторій, який він згодом може читати й розшифрувати. [Шаблони аргументів sudoers можуть збігатися з пробілами й символами `/`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), тож перевіряйте кінцеві wildcard, а не вважайте, що фіксований префікс шляху до репозиторію обмежує джерело. [Restic може створювати резервні копії у локальних і віддалених репозиторіях](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), але локальний репозиторій може містити щойно записані об’єкти, доступні лише root; перш ніж вважати це розкриттям даних, перевірте чинну політику sudo, доступ до бекенда, пароль репозиторію та дозволи на створені об’єкти. Ключ SSH із резервної копії дає доступ лише тоді, коли цільовий обліковий запис його приймає. Не запускайте резервне копіювання для перевірки під час пасивного аналізу.
- Необмежена користувацька команда обслуговування чи резервного копіювання може приймати шлях виведення або мати власний планувальник завдань. Для запису у файл перевірте точне правило sudo й користувача запуску, а потім з’ясуйте, чи контролює користувач і дані, і місце призначення. Для планування команд перевірте ідентичність виконання завдань, введення команди та будь-які додаткові перевірки пароля чи авторизації. Назва команди або сам `NOPASSWD` не доводять наявності жодного з цих шляхів. Див. [запис у файли, власником яких є root](../interesting-files-permissions/write-to-root.md) і [таймери cron та systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Фіксована команда sudo усе одно може завантажувати передбачуваний файл конфігурації зі спільного каталогу, доступного для запису. Простежте, чи може користувач підмінити цей файл і чи керують його поля джерела й призначення привілейованим отриманням або копіюванням файлів. URL локального файла може відкрити дані, доступні лише обліковому запису RunAs sudo; кероване користувачем джерело разом із захищеним призначенням може створити шлях для запису. Перевірте обробку URL встановленою програмою, перевірки шляху призначення, чинне правило sudo та доступність виводу. Сам шлях конфігурації у записуваному `/tmp` — лише привід для перевірки; вивчайте бінарний файл і метадані файлів, не запускаючи привілейоване передавання.
- Правило sudo для `git apply` може дозволити обліковому запису RunAs записувати файли, вибрані патчем, контрольованим користувачем. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) дозволяла спеціально сформованому патчу створити symlink, а потім записати дані за межами робочого дерева, навіть якщо команда не приймала `--unsafe-paths`. Перевірте чинне правило аргументів sudo, джерело патчу, доступ облікового запису RunAs до робочого каталогу та встановлене виправлення Git або бекпорт постачальника. Необмежене правило, що дозволяє `--unsafe-paths`, — окремий ризик явного параметра; сама версія Git або дозвіл на `git apply` не доводять, що захищений файл можна змінити. Під час пасивного збору даних не застосовуйте недовірений патч.
- Правило sudo для root на `clamscan --debug` може перетнути межу доступу до даних, якщо менш привілейований користувач може надати образ DMG, а встановлений парсер вразливий до [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), яка могла розкривати вміст файлів через налагоджувальний вивід. Перевірте точні дозволені аргументи й шлях сканування, контроль над введенням, ефективний обліковий запис RunAs, виправлення/бекпорт рушія та видимість виводу для користувача. Якщо ширше правило дозволяє `--file-list`/`-f`, перевірте цю поведінку окремо; правило з фіксованим `--debug <scan-path>` цього параметра не дозволяє. Під час переліку перевіряйте політику й метадані пакета, не скануючи спеціально створений файл і не виводячи захищені дані.
- Правило sudo для root, що відкриває вибраний користувачем зашифрований образ диска, і друге правило для монтування отриманого mapper можуть імпортувати файли, контрольовані користувачем, у простір монтування хоста. Підтвердьте обидва чинні правила й аргументи, контроль над образом і назвою mapper, фактичну ціль монтування, а також власника й режим створених файлів. Перехід через SetUID додатково потребує доступного виконуваного файла, параметрів монтування, що його підтримують (`nosuid` це блокує), і відповідної політики процесів або MAC; саме відкриття чи монтування образу — лише привід для перевірки. Окремий шлях через наявну резервну копію потребує відповідного ключа й корисного секрету, доступного для читання. Перевіряйте політику й шляхи, не відкриваючи й не монтуючи образ під час пасивного збору даних. Див. [посібник cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) і [параметри монтування](https://man7.org/linux/man-pages/man8/mount.8.html).
- Правило sudo для root на shell- або Python-скрипт потребує перевірки робочого каталогу, якщо скрипт запускає `./helper`, не переходячи спочатку до фіксованого каталогу. Список Python на кшталт `['./helper']`, переданий у `subprocess.run`, має ту саму поведінку: каталог може вибрати користувач. Користувач може вибрати каталог із правом запису й помістити туди виконуваний файл із таким відносним ім’ям; абсолютний шлях в іншій частині скрипту цей виклик не захищає. Перш ніж вважати це виконанням коду, перевірте чинне правило, `runchdir` чи іншу політику зміни каталогу, потік виконання скрипту й досяжність гілки, доступний для запису та виконання каталог, а також обмеження монтування/`NOEXEC`. Якщо скрипт неможливо прочитати, поведінка залишається невідомою, доки його вихідний код не буде перевірено дозволеним способом. Перевіряйте скрипти статично, а не запускайте допоміжний файл. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) описано політику робочого каталогу.
- Фіксований Python-валідатор, здатний працювати від root, усе одно може обчислювати вибраний користувачем файл даних. [У документації Python щодо `eval()` є попередження про недовірене введення](https://docs.python.org/3/library/functions.html#eval): перевірка суфікса введення, арифметичний префікс або гілка валідації не є ізоляцією, якщо решта виразу передається до `eval`. Перш ніж вважати це шляхом до виконання, перевірте чинне правило sudo, чи може користувач вибрати й контролювати саме цей файл, умови гілок парсера й формування виразу, а також ідентичність привілейованого процесу. Наявність `eval` у доступному для читання скрипті — лише привід для перевірки; вивчайте вихідний код і дозволи на файл, не запускаючи валідатор і не надсилаючи тестовий вираз під час переліку.
- Обгортка Ruby для root через sudo, яка читає відносне ім’я YAML-файла, наприклад `YAML.load(File.read("dependencies.yml"))`, може брати введення з робочого каталогу користувача, якщо обгортка або політика sudo не фіксує цей каталог. Перевірте точні дозволені аргументи, дозволи на каталог і файл, а також поведінку встановленої версії Psych: старі реалізації `YAML.load` могли десеріалізувати довільні об’єкти Ruby, тоді як новіші типово обмежують дозволені класи. Сам виклик у коді — лише привід для перевірки; з’ясуйте, чи справді файл лежить у каталозі, доступному користувачу для запису, і чи дозволяє встановлений завантажувач небезпечні класи. Для недовіреного введення надавайте перевагу `safe_load` із явним мінімальним списком дозволених класів. Див. документацію [Ruby 3.0 Psych](https://docs.ruby-lang.org/en/3.0/Psych.html) і [Ruby 3.1 Psych](https://ruby-doc.org/core-3.1.2/Psych.html).

- Точний дозвіл sudo для root на `sudo go run /absolute/file.go` потребує перевірки робочого каталогу, якщо вихідний код Go читає відносний файл WASM і може запускати відносний shell-скрипт після перевірки результату. Перевірте ефективного RunAs, аргументи команди й заборони, поточний каталог, доступний користувачу для запису, потік даних від WASM до гілки, а також чи запускає ця гілка допоміжний файл. Фіксований `runchdir` sudo, `os.Chdir` або [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) можуть змінити місце пошуку. Спільна наявність цих елементів у статичному аналізі — лише потенційний випадок; вивчайте вихідний код, не запускаючи Go, WASM чи допоміжний файл.
- Для `sudoedit` і wildcard в аргументах потрібна точна перевірка версії й правила; у [контрольному списку](linux-privilege-escalation-checklist.md) розглянуто проблему редагування файлів через sudoedit. Для дозволу `sudoedit` між обліковими записами на шлях із wildcard перевірте чинне значення `sudoedit_follow` або `FOLLOW`, `sudoedit_checkdir`, розв’язаний цільовий шлях і те, хто може підміняти кожен батьківський елемент. Перше може дозволити переходити за symlink, а вимкнення другого прибирає перевірки каталогів, доступних для запису; жоден із параметрів сам по собі не доводить можливості записати у файл іншого користувача. Перш ніж робити такий висновок, перевірте встановлену політику sudo та точно відповідні аргументи. Див. [визначення параметрів sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- У правилі команд sudoers wildcard в аргументі може збігатися з пробілами й символами шляху. Тому правило для команди, здатної читати файли, з аргументом на кшталт `/restricted/*` може дозволити ще один аргумент-файл після відповідного префікса. Перевірте точного користувача RunAs, шлях до команди, шаблон аргументів і подальші заборони; доведене читання файла не означає виконання команди. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) розрізняються шаблони аргументів і шаблони шляхів до команд.
- Шаблон аргументу, схожий на шлях, також може збігатися з `../`. Наприклад, правило root на `node /opt/scripts/*.js` може дозволити користувачу передати контрольований JavaScript-файл за межами `/opt/scripts`, якщо задане ім’я все ще починається з `/opt/scripts/` і розв’язується через сегменти батьківських каталогів. Це wildcard **аргументу**; правила збігу зі слешами для wildcard шляху до виконуваного файла Node відрізняються. Перш ніж робити висновок про виконання коду, перевірте чинне правило, подальші заборони, розв’язання шляху, контроль над цільовим файлом і обмеження регулярних виразів або дайджестів у sudoers. Див. [правила wildcard у sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) і [документацію командного рядка Node](https://nodejs.org/api/cli.html).
- Архіватори та інші службові програми можуть мати засоби запуску команд. Перевіряйте точні дозволені аргументи через [GTFOBins](https://gtfobins.github.io/), а не вважайте, що команди запускають лише shell чи інтерпретатори.
- Необмежене правило sudo для root на `qpdf` може відкрити привілейований файл через вкладення в PDF: qpdf версії 10.2 і новіші підтримують `--empty` і `--add-attachment file ... --` разом із вихідним PDF. Якщо привілейований процес може прочитати вибране джерело й записати PDF у доступний користувачу шлях, цей файл може містити байти джерела. Перш ніж робити висновок про можливість розкриття файла, перевірте ефективні аргументи й виключення sudo, версію qpdf, доступ до джерела та шлях виведення. Прочитати SSH-ключ root корисно для входу лише тоді, коли ключ чинний, а автентифікація root через SSH дозволена. Див. [параметри вкладень qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Повторне використання часової мітки sudo залежить від політики кешу, власника, термінала/сеансу та дозволів. У [посібнику з підвищення привілеїв](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) описано потрібні перевірки.
- `doas` має власні правила й конфігурацію. Перевіряйте дозволені команди й шляхи до конфігурації, доступні для запису, як описано в [розділі про doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Інструменти збирання та пакування, що запускаються через sudo

Необмежений дозвіл sudo на Foundry `forge` може мати значення, навіть якщо ідентичність RunAs належить іншому непривілейованому користувачу. Параметри компілятора на кшталт `--use` можуть вибрати локальний виконуваний файл, а `forge flatten -o` задає вихідний файл. Перш ніж вважати дозвіл експлуатованим, перевірте версію Forge, точні аргументи sudo, доступні проєкт і компілятор, дозволи на вихідний файл та чинне середовище. Відносний допоміжний виконуваний файл, знайдений через `PATH`, — це шлях, залежний від версії й середовища, а не властивість, яку слід припускати для кожної збірки Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Необмежений дозвіл sudo для root на `pacman` дає змогу не лише переглядати пакети: `-U` приймає локальний пакет, пакети можуть містити скрипти встановлення, а `--hookdir` вибирає інший каталог hook. Перед тестуванням перевірте чинне правило sudo, обмеження аргументів і виключення; пасивний збір даних не потребує встановлення пакета чи запуску hook.<sup>[[25]](#references)[[26]](#references)</sup>

Фіксована shell-обгортка sudo також може встановлювати названу залежність npm, а потім запускати програму Node. Перевірте точне правило RunAs, чи встановлено пакет, ефективні `HOME` і npm `userconfig`, конфігурацію проєкту або перевизначення командного рядка, а також чи контролює менш привілейований користувач реєстр або пакет, який повертається для цієї назви. [У документації npm описано пошук `.npmrc` для користувача й проєкту](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); поведінка `HOME` у sudo залежить від встановленої політики й дистрибутива, тому файл `.npmrc` користувача, доступний для запису, може читатися або не читатися привілейованим процесом npm. Якщо щойно встановлений пакет імпортує привілейована програма, його модульний код може виконуватися з ідентичністю цієї програми. Скрипти під час встановлення — окремий шлях, залежний від версії й конфігурації; [у документації npm описано їхні життєвий цикл і обробку користувачів](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Шлях `.npmrc` або рядок `npm install` — лише привід для перевірки. Під час пасивного збору даних перевіряйте правило, коротку обгортку, шляхи конфігурації та походження пакета, не встановлюючи пакет і не запускаючи програму.

Дозвіл sudo для root на `pip` або `pip3 download` також є приводом перевірити збирання пакета, якщо аргументи дають користувачу змогу вибрати недовірений вихідний дистрибутив, навіть коли шаблон URL обмежує її локальним сервісом і суфіксом `.tar.gz`. `pip download` приймає URL архівів і розв’язує метадані пакета; підготовка sdist може запускати його бекенд збирання або застарілий код `setup.py`, перш ніж архів буде просто збережено. Перевірте точні RunAs і правило аргументів sudo, чи може користувач опублікувати або підмінити вибраний архів, а також чи справді ця версія pip готує його метадані. Фіксований довірений архів або wheel такого шляху не доводить. Під час пасивного збору даних не отримуйте й не збирайте недовірений пакет. Див. документацію pip щодо [команди download](https://pip.pypa.io/en/stable/cli/pip_download/), [інтерфейсу системи збирання](https://pip.pypa.io/en/stable/reference/build-system/) і [безпечного встановлення](https://pip.pypa.io/en/stable/topics/secure-installs/).

Правило sudo, що дозволяє `pip install` із локальним шляхом до проєкту, вибраним користувачем, створює прямішу межу збирання. [pip приймає локальні каталоги проєктів](https://pip.pypa.io/en/stable/topics/local-project-installs/) і запускає їхню систему збирання; [бекенд збирання виконує hook-и, контрольовані проєктом](https://pip.pypa.io/en/stable/reference/build-system/). Перш ніж вважати це виконанням коду з привілеями, перевірте ефективну ідентичність RunAs, точні обмеження аргументів і заборони, контроль користувача над вибраним проєктом, а також поведінку встановленої версії pip/бекенда. Фіксований довірений проєкт або правило, що виключає вибрані користувачем шляхи, такого шляху не доводить. Під час пасивного збору даних перевіряйте правило й метадані проєкту, не встановлюючи пакет.

Необмежений дозвіл sudo для root на застарілий `easy_install` — подібний привід перевірити збирання пакета. [У документації Setuptools зазначено](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html), що Easy Install приймає локальний каталог проєкту й збирає вихідні дистрибутиви; під час цього збирання проєкт, контрольований користувачем, може виконати свій `setup.py` з ідентичністю sudo. Перевірте ефективний обліковий запис RunAs, точну команду й обмеження аргументів (зокрема подальші заборони), контроль над вибраним проєктом і поведінку встановленого інструмента. Фіксований довірений проєкт або політика, що не дозволяє вибрати вихідний код користувачеві, такого шляху не доводить. Під час переліку перевіряйте правило й метадані проєкту, не встановлюючи пакет.

Python-обгортка, дозволена через sudo, що використовує `setuptools.package_index.PackageIndex.download` із URL, вибраною користувачем, потребує окремої перевірки, відмінної від `pip download`: [GHSA-5rjg-fvgr-3xxf для setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) описує, як вразливі версії до 78.1.1 могли формувати ім’я файла з URL, виходити за межі заданого каталогу завантажень і записувати файл із дозволами процесу. Перевірте ефективні RunAs і правило аргументів sudo, чи передає обгортка URL користувача саме цьому API, встановлену збірку чи бекпорт постачальника, а також куди веде отриманий шлях. Сам рядок версії або каталог завантажень, доступний для запису, не доводять можливості довільного запису. Під час переліку перевіряйте коротку обгортку й метадані пакета, не отримуючи URL і не записуючи файл.

Обгортка збирання, дозволена через sudo і передає файл `.spec`, вибраний користувачем, у PyInstaller, потребує такої самої перевірки межі довіри. Файл spec PyInstaller — це виконуваний код Python, який обчислюється **під час збирання**, а його записи `datas` можуть додавати до артефакту файли, доступні для читання ідентичності, що виконує збирання. Перевірте точного користувача RunAs, правила sudo щодо аргументів і заборон, обробку шляхів і гілок в обгортці, контроль над вибраним файлом spec та доступ до створеного артефакту. Сам дозвіл на введення `.py` або наявність PyInstaller не доводять контролю над spec-файлом чи виконання коду з привілеями. Під час пасивної перевірки читайте лише обмежений обсяг коду обгортки й метаданих; не запускайте збирання. Див. [документацію файлів spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Завантажувачі preset і plugin, що запускаються через sudo

Python-інструменти, які приймають вибраний користувачем preset або каталог plugin, можуть імпортувати код із привілеями, наданими sudo. Наприклад, BBOT приймає preset через `-p`, а в його [документації користувацьких модулів](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) описано записи `module_dirs`, які задають додаткові каталоги модулів Python. Якщо чинне правило sudo дозволяє користувачу вибрати preset, а сам користувач контролює модуль у вибраному каталозі, імпорт може виконати код від імені привілейованого користувача, потенційно ще до того, як інструмент відхилить некоректний модуль. Під час переліку перевірте встановлену версію, точні правила sudo щодо користувача RunAs і аргументів, а також власників preset і каталогів модулів, не завантажуючи модуль.

### CLI-інструмент Backdrop, що запускається через sudo

[Bee](https://github.com/backdrop-contrib/bee) — CLI-інструмент PHP для Backdrop CMS. Його команди `eval` (`php-eval`) і `php-script` можуть запускати PHP-код, наданий користувачем. Тому правило sudo, що дозволяє запуск виконуваного файла Bee від root з необмеженими аргументами, може відкрити виконання коду від root, якщо Bee може ініціалізувати сайт Backdrop. Запустіть його з каталогу сайту або виберіть сайт глобальним параметром `--root=<directory>`; сама наявність Bee чи файла Backdrop `settings.php` не доводить наявності дозволу sudo, придатного сайту чи успішної ініціалізації. Перед тестуванням перевірте чинне правило sudo, будь-які виключення команд, ідентичність виконуваного файла й доступ до сайту. Під час пасивного збору даних перевіряйте правило й шляхи до файлів, не запускаючи Bee. Про додавання PHP-команд див. [журнал змін команд Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md).

### Сервери терміналів, що запускаються через sudo

`mosh-server` запускає інтерактивний сервер термінала від імені користувача, який його викликав. Він вибирає високий UDP-порт і ключ сеансу, повідомляє обидва користувачу й зазвичай запускає оболонку входу цього користувача після підключення клієнта. Тому необмежений дозвіл sudo для root на `mosh-server` є кандидатом для перевірки запуску shell, хоча сама команда сервера від’єднується від термінала. Перевірте чинну ідентичність RunAs, дозволені аргументи й виключення, встановлений бінарний файл, оболонку, наявність клієнта та доступність UDP. Під час пасивного збору даних перевіряйте правило sudo, не запускаючи сервер і не виводячи активний ключ сеансу. Див. [посібник сервера Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) і [примітки про архітектуру проєкту](https://github.com/mobile-shell/mosh#how-it-works).

### Привілейовані обгортки резервного копіювання, що змінюють файл завдань користувача

Shell-обгортка, запущена від root, може приймати файл завдань, вибраний користувачем, вилучати `../` зі шляхів джерел, перевіряти, чи починається кожен результат із дозволеного каталогу, змінювати файл завдань, а потім передавати програмі резервного копіювання його *ім’я шляху*. Перевірте перетворений шлях після повної канонічної нормалізації: одноразова заміна рядка може відкрити нову послідовність обходу каталогів, яку прийме лексична перевірка префікса. Також з’ясуйте, чи читає програма резервного копіювання перетворені дані в пам’яті або відкриває файл повторно. Якщо вона відкриває файл знову, невдала зміна може залишити початкове введення без змін.

У Linux `fs.protected_regular` може забороняти запис `O_CREAT` до звичайного файла іншого користувача у доступному для запису всім sticky-каталозі. Ця заборона має захисний ефект, але shell-обгортка, яка ігнорує помилку запису, може продовжити роботу з початковим файлом завдань. Перевірте це налаштування, власника файла й каталогу та чи зупиняється обгортка в разі помилки. Шлях є кандидатом для розкриття файлів лише тоді, коли чинне правило sudo дозволяє запускати обгортку від привілейованого користувача, користувач контролює введення завдання й доступне йому місце призначення резервної копії, а утиліта резервного копіювання справді включає захищені джерела. Під час переліку перевіряйте ці умови, не запускаючи резервне копіювання.

### Wildcard в аргументах привілейованих мережевих інструментів

У правилі sudo для `tcpdump` символ `*` у **шаблоні аргументів** може збігатися з пробілами й слешами, тому обмеження, схоже на шлях, усе ще може дозволяти додатковий текст параметрів. Це відрізняється від wildcard у шляху до виконуваної команди; перевірте повне правило RunAs і подальші заборони. Якщо можна ін’єктувати параметри, дозволений виклик і семантика параметрів встановленого [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) визначають, чи дають `-F`, `-V`, `-r`, `-w` або `-Z` корисні примітиви читання/запису. `-V` читає список імен файлів захоплення, а не довільний файл як універсальний дамп. AppArmor або інша політика MAC може блокувати доступ до файлів, навіть якщо sudo дозволяє команду; наявність файла профілю на диску не доводить, що його завантажено й застосовано. Перш ніж робити висновок, пасивно перевірте авторизацію й політику. У [посібнику sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) описано різницю між цими wildcard.

Правило sudo для root, у якому вказано лише виконуваний файл `tcpdump` без обмежень аргументів, також потребує перевірки. У [посібнику tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) зазначено, що `-z` запускає команду після ротації, якщо збережений запис захоплення ротують через `-C` або `-G`; перед цим привілеї можуть бути скинуті через `-Z` або параметр збирання за замовчуванням. Перш ніж вважати правило шляхом підвищення привілеїв, перевірте чинне правило sudo, встановлену збірку, поведінку скидання привілеїв і можливість ротації. Правило, яке привертає увагу, є лише кандидатом для перевірки, а не доказом виконання команди від root.

### Обгортки Nmap, що запускаються через sudo

Якщо дозволений через sudo `nmap` є shell-обгорткою, перевірте точний дозволений шлях і кожен параметр, який вона передає далі. Блокування звичного написання `--script` не обов’язково блокує завантаження коду NSE: Nmap за допомогою [`--datadir`](https://nmap.org/book/man-misc-options.html) вибирає файли даних, а NSE [завантажує `nse_main.lua`](https://nmap.org/book/nse-implementation.html) із вибраного каталогу даних, коли скрипти ввімкнено. Деякі встановлені збірки також приймають альтернативні довгі форми запису параметрів, тому порівнюйте обмеження з фактичним парсером цього бінарного файла. [`--excludefile`](https://nmap.org/book/man-target-specification.html) — окрема поверхня читання файлів; помилки парсера можуть розкрити текст. Під час переліку перевірте чинне правило sudo, логіку обгортки, версію Nmap, контроль над каталогами й політику MAC, не запускаючи сканування.

### Hook-и Mercurial pull, що запускається через sudo

Фіксоване джерело в `sudo hg pull /fixed/source` усе одно залишає вибір **репозиторію, що приймає дані**, за поточним робочим каталогом, якщо команда не фіксує його параметром `-R`. Репозиторій, контрольований користувачем, може містити hook-и в `.hg/hgrc`, які запускаються від імені користувача RunAs sudo. [Mercurial ігнорує конфігурацію репозиторію, власником якого є недовірений користувач або група](https://mercurial-scm.org/help/topics/config), тому перш ніж вважати це виконанням коду, перевірте довірених користувачів/груп облікового запису RunAs і точний робочий каталог. Для пасивної перевірки достатньо переглянути політику й конфігурацію; не запускайте pull і hook під час переліку.

### Hook-и Git pull, що запускається через sudo

Для точного правила sudo для root на `sudo git pull` перевірте також **репозиторій, що приймає дані**, вибраний робочим каталогом. У репозиторії, власником якого є користувач, може бути виконуваний hook `post-merge`, який запускається з ідентичністю процесу Git, коли pull справді виконує успішне злиття; [у документації Git описано цей hook](https://git-scm.com/docs/githooks) і [поведінку pull: merge чи rebase](https://git-scm.com/docs/git-pull). Перевірте чинне правило sudo і поточний робочий каталог, активний шлях до hook та його дозволи, а також чи можливе злиття з новими комітами. Невдалий pull, pull без змін або лише з rebase не доводить наявності цього шляху через hook. Перевіряйте політику й метадані репозиторію, не запускаючи привілейований pull.

### Копіювання архівів через rsync, що запускається через sudo

Для `sudo rsync -a ... /writable/source/* /fixed/destination/` символ `*` у **шаблоні аргументів sudoers** може збігатися з пробілами й дозволити додатковий параметр між джерелом і місцем призначення. Це не те саме, що розгортання shell-символів у шаблон імен файлів. Якщо користувач може наповнювати джерело, а привілейований процес rsync може записувати в місце призначення, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) може запросити привілейовану зміну власника, а режим архівування — зберегти біти дозволів, потенційно створивши SetUID-файл із потрібним власником. Перевірте точну [семантику wildcard у sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), версію rsync, подальші заборони, параметр файлової системи `nosuid` і політику MAC. Правило, що збігається, — кандидат для перевірки, а не доказ успішного підвищення привілеїв.

### Експорт правил фільтра пакетів через sudo

Необмежений дозвіл sudo для root на `iptables` і `iptables-save` (або відповідну пару `ip6tables`) потребує перевірки запису у файли. Зіставлення `comment` приймає текст правила, вибраний користувачем, а `iptables-save -f` записує серіалізований набір правил у вибраний шлях.<sup>[[20]](#references)[[21]](#references)</sup> Корисне навантаження залежить від того, як встановлений бекенд серіалізує коментарі та чи приймає цільовий файл інші рядки з експорту; сама команда `iptables-save` не дає довільно вибирати вміст. Перевірте точну ідентичність RunAs, аргументи й виключення sudo, доступне розширення зіставлення, бекенд і дозволи на файл призначення. Під час переліку перевіряйте дозвіл, не змінюючи правила брандмауера й не записуючи файл.

### Привілейований каталог журналів Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) зачіпала версії Below до 0.9.0, які створювали каталог `/var/log/below`, доступний для запису всім. Якщо сервіс або дозволена команда sudo запускає вразливу збірку від root, користувач, який може записувати й переходити в каталог журналів без sticky-біта, може підмінити запис журналу symlink перед тим, як його відкриє привілейований процес. Перевірте статус виправлення встановленого пакета, точний шлях привілейованого виконання, фактичний доступ до каталогу, sticky-біт і ACL, а також метадані `/var/log/below/error_root.log`. Сам доступний для запису всім шлях або правило sudo не доводять наявності повного ланцюжка. Sticky-каталог або бекпорт постачальника змінює оцінку. Під час пасивного збору даних перевіряйте лише метадані; створювати посилання чи запускати привілейовану програму не потрібно.

### Привілейований збір пакета технічної підтримки з введення, доступного для запису

Скрипт профілю технічної підтримки, дозволений через `sudo`, може читати фіксовані шляхи до журналів від root і копіювати їхній вміст до архіву профілю. Перевірте сам скрипт на читання файлів, а потім з’ясуйте, чи може користувач підмінити шлях до джерела або будь-який батьківський елемент каталогу symlink. Якщо привілейоване читання переходить за цим посиланням, а створений архів доступний користувачу, захищений файл може бути розкрито. Потрібні всі умови: дозвіл sudo, шлях до джерела, доступний для запису, привілейоване читання та доступний для читання результат; сам доступний для запису журнал або ім’я файла профілю недостатні. Під час переліку перевіряйте ефективні дозволи й метадані посилань, не підмінюючи файли й не створюючи профіль. У [посібнику підтримки Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) описано скрипт створення профілю від root і вихідний архів, що показує, чому доступ до таких пакетів потрібно обмежувати.

### Скрипти відновлення архівів Python, що запускаються від root

Навіть вузько обмежене правило sudo для Python-скрипту відновлення потребує перевірки вхідного архіву. Якщо користувач може вибрати або підмінити архів, а скрипт розпаковує його від root через `tarfile.extractall(filter="data")`, перевірте оновлення безпеки інтерпретатора, перш ніж покладатися на цей фільтр. CPython виправив кілька обходів фільтра для symlink і hard link, зокрема CVE-2025-4517, у версіях 3.9.23, 3.10.18, 3.11.13, 3.12.11 і 3.13.4. Дистрибутиви можуть переносити виправлення в попередні версії, тож версія, яку показує інтерпретатор, сама по собі не доводить наявності вразливості.<sup>[[16]](#references)[[17]](#references)</sup>

Для пасивної перевірки прочитайте точну команду sudo і скрипт, з’ясуйте, який аргумент вибирає архів, і перевірте, чи може поточний користувач записувати в архів або його батьківський каталог. Окремо підтвердьте наявність виправлення постачальника й каталог розпакування; `filter="data"` не робить безпечним кожен недовірений архів.<sup>[[16]](#references)[[17]](#references)</sup>

### Завантажувачі моделей машинного навчання, що запускаються через sudo

Правило sudo, яке дозволяє користувачу вибрати файл `.pt`, `.pth` або `.ckpt`, потребує перевірки, якщо привілейований скрипт передає цей файл у [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` або інший завантажувач на основі pickle. Перевірте чинне правило RunAs, чи може користувач створити або підмінити вибрану модель, і фактичний потік аргументів крізь будь-яку shell-обгортку до допоміжного Python-скрипту. Суфікс `.pth` також позначає не пов’язані з моделями файли конфігурації сайтів Python, тому самого суфікса недостатньо, щоб довести завантаження моделі. Сканування архіву або статичний аналіз pickle не доводить безпечності подальшого завантаження; перевірте [поведінку `weights_only`, залежну від версії](https://docs.pytorch.org/docs/stable/notes/serialization.html), і будь-які списки дозволених типів. Див. [примітки щодо pickle у ML і Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Під час пасивного збору даних ніколи не завантажуйте й не розпаковуйте модель.

### Розбір виразів зі збереженого введення через sudo

Фіксований Python-скрипт, запущений від root через sudo, усе одно може обчислювати текст, який менш привілейований користувач може зберегти в базі даних програми. У TensorFlow виклик `preprocess_input_exprs_arg_string(value, safe=False)` вибирає шлях із `eval`; [рекомендація з безпеки TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) описує небезпечний парсер і виправлення його CLI-виклику. Явний виклик `safe=False` у програмі потребує окремої перевірки, навіть якщо той CLI-виклик уже виправлено. Перевірте чинне правило sudo, хто може змінити саме цей запис введення, чи пропускає фільтрація або оцінювання цей запис до виклику, а також поведінку встановленої функції. Версія TensorFlow, дозвіл sudo або жорстко заданий файл моделі самі по собі не доводять наявності повного ланцюжка. Пасивно досліджуйте скрипт і потік даних; під час переліку не запускайте привілейований допоміжний скрипт і не надсилайте тестові вирази.

### Конфігурація needrestart, дозволена через sudo

`needrestart -c` завантажує вибраний користувачем файл конфігурації Perl і обчислює його вміст. Якщо `sudo -l` дозволяє запускати `needrestart` від root із аргументами, що допускають `-c`, а користувач може вибрати файл конфігурації, доступний для читання в каталозі, доступному для запису, цей дозвіл може привести до виконання коду від root. Перевірте точні правило sudo щодо користувача RunAs і аргументів; правило з фіксованим списком аргументів може заблокувати цей шлях. Це окремо від вразливостей needrestart під час сканування інтерпретаторів: оновлення пакета або вимкнення `interpscan` не робить безпечним необмежений дозвіл root на `-c`.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Імпорт Python через sudo від імені іншого облікового запису

Фіксована точка входу Python усе одно може імпортувати модуль, який користувач може редагувати або підмінити, навіть якщо sudo запускає скрипт від імені **не-root** сервісного користувача. Для буквального `from utils import status` перевірте локальні `utils/__init__.py` і `utils/status.py`, а також дозволи на каталог пакета. Перш ніж вважати доступний для запису файл шляхом виконання, перевірте шлях імпорту скрипту, точні дозволені аргументи sudo та чи доходить відповідна дія до цього імпорту. Під час переліку перевіряйте файли й дозволи, не імпортуючи й не запускаючи скрипт.<sup>[[2]](#references)[[3]](#references)</sup>

Для точного правила sudo на `python3 /absolute/script.py` потрібен лише скрипт, доступний для читання; виконуваний біт або shebang не потрібні. Перевіряйте також **відсутні** локальні модулі: якщо скрипт імпортує модуль, файл якого можна створити в каталозі скрипту, доступному користувачу для запису, Python може завантажити цей файл з ідентичністю RunAs. Перевірте чинне правило sudo, фактичний [шлях пошуку модулів](https://docs.python.org/3/library/sys_path_init.html) інтерпретатора, чи є модуль вбудованим або замороженим, а також чи відбувається імпорт. Пряме правило sudo для скрипту має інші вимоги щодо біта виконання й shebang. Окрема обгортка, яка додає передані користувачем токени після `sudo -u account`, також потребує перевірки потоку аргументів: ще один `-u` у цих токенах має значення лише тоді, коли викликана політика sudo дозволяє отриману ідентичність. Самі статичні рядки не доводять жодного з цих шляхів.

### Apache, що запускається через sudo, із конфігурацією, контрольованою користувачем

Якщо правило sudo дозволяє привілейований виклик `apachectl`, `apache2ctl` або `httpd` із файлом конфігурації `-f`, контрольованим користувачем, перевірте дозволи на цей файл і батьківський каталог. Директива Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) приймає ім’я модуля та **ім’я файла модуля**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) також завантажує файл. [`Include` та `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) можуть доповнити конфігурацію або розкрити вміст файлів через помилки. Користувацька обгортка може перевіряти ці шляхи, скидати привілеї або обмежувати аргументи, тому доступна для запису конфігурація — лише кандидат для перевірки, а не доказ виконання коду. Перш ніж робити висновок, перевірте канонізацію шляхів, symlink і розбір директив.

### nginx, що запускається через sudo, із конфігурацією, контрольованою користувачем

Необмежене правило sudo для root на `nginx` може дозволити [`-c` вибрати іншу конфігурацію](https://nginx.org/en/docs/switches.html). Перевірте точні аргументи й виключення sudo, чи може користувач надати конфігурацію та чи зберігають запущений master або worker доступ до захищених шляхів. Вибрані `root` і `autoindex` можуть відкрити файли через новий listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) може створити шлях привілейованого запису у файл, але модуль DAV типово не вбудовується, тому потрібно перевірити його наявність, доступність listener, дозволи на файли й поведінку тимчасових файлів. Директива [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) також може спрямовувати журнал до вибраного файла; запис журналів у чутливий файл конфігурації, наприклад `/etc/ld.so.preload`, стає шляхом підвищення привілеїв лише за наявності ефективного привілейованого запису й контрольованого запису журналу. Підсвічування виконуваного файла в `sudo -l` — привід для перевірки, а не доказ працездатності будь-якого з цих шляхів. Під час пасивного збору даних не запускайте й не переналаштовуйте nginx.

### Порівняння шаблонів у привілейованих запитах Bash

Якщо скрипт Bash, дозволений через sudo, читає значення від користувача й перевіряє його за допомогою `[[ "$expected" == $entered ]]`, Bash сприймає незаключений у лапки операнд справа як шаблон. Тому wildcard може задовольнити порівняння без знання очікуваного значення. Якщо взяти операнд у лапки (`[[ "$expected" == "$entered" ]]`), порівняння виконуватиметься як із буквальним рядком. Перевірте точне правило sudo, чи доступний запит і що скрипт робить після порівняння; сам синтаксис не доводить наявності експлуатованого шляху. Під час переліку не виводьте очікуване значення. Див. [довідник Bash щодо умовних конструкцій](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Допоміжні програми sudo, що завантажують і запускають файл

Необмежений дозвіл sudo для root на користувацьку допоміжну програму потребує аналізу потоку даних, якщо вона приймає URL, вибрану користувачем, зберігає відповідь на диск, а потім запускає цей файл через інтерпретатор або shell. [Sudoers дозволяє довільні аргументи, якщо запис команди їх не перелічує](https://man7.org/linux/man-pages/man5/sudoers.5.html); фіксований шлях до виконуваного файла не обмежує вибір, який задають його аргументи. Перевірте фактичну валідацію URL, шлях виведення, гілку успіху й подальший запуск у встановленій допоміжній програмі. Імпорт libcurl або друкований рядок самі по собі не доводять наявності цього ланцюжка.

Навіть фіксоване базове ім’я вихідного файла може бути підмінене між записом і запуском, якщо допоміжна програма використовує **відносний шлях у робочому каталозі, контрольованому користувачем**. Перейменування або підміна файла, власником якого є root, залежать від доступу на запис і пошук у каталозі та будь-яких обмежень sticky-біта, а не лише від режиму файла; див. [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Перевірте, чи повторно відкриває допоміжна програма шлях згодом або використовує вже відкритий дескриптор, а також чи переходить вона до довіреного каталогу перед записом. Пасивно перевіряйте політику sudo, допоміжну програму й метадані каталогів; не запускайте привілейоване завантаження чи гонитву за файлом під час переліку.

Допоміжна програма завантаження через sudo від root може також мати **ін’єкцію аргументів**, якщо формує рядок команди Bash на кшталт `curl <caller input> -o <fixed output>`. Фільтр, який відкидає пробіли, усе одно залишає [розгортання фігурних дужок Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): елементи через кому без лапок можуть стати окремими аргументами curl. Якщо введення потрапляє до curl перед фіксованим `-o`, параметр виведення, заданий користувачем, може вибрати місце призначення для першої URL-адреси з ідентичністю допоміжної програми; [curl застосовує параметри виведення до URL-адрес по черзі](https://curl.se/docs/manpage.html#-o). Перевірте точний shell, лапки, валідацію введення, чинне правило sudo, порядок аргументів curl і підтримувані схеми URL, а також чи контролює користувач отримані дані або може прочитати результат. Виконуваний файл, зібраний PyInstaller, може містити логіку Python-програми, але сам маркер пакування або рядок `curl` не доводять такого потоку даних. Якщо це дозволено, перевіряйте обмежену офлайн-копію; під час звичайного переліку не запускайте допоміжну програму й не отримуйте дані з вибраного зловмисником джерела.

Shell-скрипт sudo, запущений від root, який викликає [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), лише вибирає невикористане ім’я; він **не** створює файл. Якщо згодом скрипт створює файл із цим ім’ям у каталозі, на який може вплинути інший користувач, повторно відкриває його й дописує вміст до захищеного файла, наприклад `authorized_keys` root, перевірте можливу гонку з тимчасовим файлом. Перевірте точне правило sudo, власника каталогу й файла, послідовність створення й повторного відкриття, захисти ядра та чи використовує привілейований запис дані, контрольовані зловмисником. Сам рядок `mktemp -u` або доступний для запису `/tmp` не доводить наявності гонки. Вивчайте скрипт і метадані шляхів, не запускаючи його й не влаштовуючи гонку з тимчасовим файлом під час переліку.

## Захисні рекомендації

- Не надавайте через sudo доступ до інтерпретаторів чи інтерактивних редакторів.<sup>[[1]](#references)</sup>
- Не дозволяйте необмежено використовувати загальні засоби запису у файли, наприклад `tee`. Використовуйте обгортку, власником якої є root, із фіксованим місцем призначення та відхиляйте шляхи, контрольовані користувачем.<sup>[[2]](#references)</sup>
- Надавайте перевагу фіксованим обгорткам, власником яких є root, що виконують одну вузько визначену адміністративну дію.<sup>[[1]](#references)[[2]](#references)</sup>
- Якщо без інтерпретатора не обійтися, обмежте точний шлях до скрипту й запобігайте передаванню аргументів, контрольованих користувачем, імпортам із каталогів, доступних для запису, `PYTHONPATH` і небезпечному збереженню змінних середовища.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Якщо потрібне редагування файлів, обмежте точний шлях до файла й розгляньте `sudoedit` із виправленими версіями sudo та суворою обробкою середовища.<sup>[[1]](#references)[[2]](#references)</sup>
- Перевіряйте `SETENV`, `env_keep`, робочі каталоги, доступні для запису, шляхи модулів/імпорту, доступні для запису, `NOEXEC`, `use_pty` і ведення журналів, але не вважайте їх повноцінною ізоляцією.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
