## Intérpretes permitidos por Sudo

Si `sudo -l` permite que un usuario ejecute un intérprete como root, considéralo ejecución directa de código. Los intérpretes están diseñados para ejecutar código arbitrario, por lo que una regla que permita `python3`, `perl`, `ruby`, `lua`, `node` o binarios similares suele equivaler a la ejecución de comandos como root, a menos que los argumentos estén estrictamente restringidos y validados.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flujo de revisión habitual: primero enumera los privilegios del usuario y luego ejecuta una instrucción de Python con la opción `-c` del intérprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

A continuación se muestran otros ejemplos de intérpretes; los intérpretes enumerados documentan la ejecución de código en línea o las API de procesos secundarios.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

La ruta exacta importa. Si la regla de sudo permite `/usr/bin/python3`, usa esa ruta exacta durante la validación.<sup>[[2]](#references)</sup>

Un glob de ejecutables de sudo como `/usr/bin/python*` también puede permitir Python 2 para un script escrito para Python 3. Si el script llega a `input()` con texto controlado por quien lo invoca, [Python 2 evalúa ese texto como una expresión](https://docs.python.org/2/library/functions.html#input); una invocación explícita del intérprete prevalece sobre el shebang del script. Verifica los binarios coincidentes instalados, la política efectiva de RunAs y de argumentos, las denegaciones y si se puede llegar a la entrada antes de considerar esto una vía de ejecución.

Una ruta fija a un script en una regla de sudo con capacidad de root no limita lo que ejecuta el script. Si es un wrapper de Bash legible, comprueba si su primer comando ejecutable usa un parámetro posicional sin comillas, como `$1`, como **palabra de comando**, mientras sudo permite argumentos elegidos por quien lo invoca. Confirma la identidad efectiva de RunAs, la política de contraseña y argumentos, las denegaciones posteriores y la rama real del script; `NOEXEC`, una lista fija de argumentos seguros o un wrapper que valida su comando pueden cambiar el resultado. Durante la enumeración, inspecciona estáticamente el script corto en lugar de invocarlo con un comando de prueba.

Una regla de sudo sin restricciones para `dotnet` con capacidad de root también merece una revisión del intérprete. Con un .NET SDK instalado, [`dotnet fsi` ejecuta código F# de forma interactiva o desde un script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), y [`dotnet run` ejecuta un proyecto desde el código fuente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Confirma primero la identidad efectiva de RunAs y la política exacta de argumentos: una regla limitada a un subcomando seguro concreto o a una aplicación de confianza es un permiso distinto, y una instalación que solo incluya el runtime puede carecer de comandos del SDK. El nombre del ejecutable es una señal para revisarlo, no una prueba de ejecución de código.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editores permitidos por sudo

Si `sudo -l` permite que un usuario ejecute un editor interactivo como root, considérelo una superficie de ejecución de comandos, no un permiso inocuo para editar archivos. Los editores a menudo pueden ejecutar comandos de shell, leer archivos arbitrarios, escribir archivos arbitrarios o invocar herramientas externas desde el propio editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flujo de revisión habitual: enumerar los privilegios del usuario y, luego, invocar con sudo cada editor o pager permitido.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Ejecución de comandos con Nano

Cuando se permite ejecutar `nano` mediante sudo, es posible ejecutar comandos desde la interfaz del editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Luego proporciona un comando como `id` o `/bin/sh` en el prompt de comandos de nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Si un shell interactivo no tiene flujos de terminal utilizables, esta forma de redirección asigna su salida estándar y error al descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La secuencia exacta de teclas puede variar según la versión de nano y las opciones de compilación, pero el problema de seguridad es el mismo: el editor se ejecuta como root y puede invocar comandos externos.<sup>[[1]](#references)[[12]](#references)</sup>

### Otros escapes comunes de editores

Los editores tipo Vim suelen permitir ejecutar comandos mediante `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Los pagers como `less` también pueden permitir la ejecución de comandos de shell.<sup>[[14]](#references)</sup>

Una regla de sudo que permita ejecutar `apport-cli` como root merece la misma revisión del pager. Algunas versiones afectadas de Apport podían abrir un informe de fallo en `less` con un tamaño de terminal ajustable por un atacante; el pager podía entonces proporcionar una shell de root si se cumplían las condiciones especiales de sudo y del pager. Comprueba la regla de sudo efectiva, la configuración del pager y la corrección del paquete de la distribución antes de considerar vulnerable una versión basándote únicamente en ella. Lee los metadatos del paquete y de la política sin generar un fallo ni abrir el informe privilegiado durante la enumeración pasiva. [El registro de CVE de Ubuntu](https://ubuntu.com/security/CVE-2023-1326) enumera las versiones corregidas de los paquetes para cada versión, incluidas las correcciones retroportadas.

```text
!/bin/sh
```

## Otros riesgos de las reglas de sudo y doas

Empieza con `sudo -l`, `sudo -V` y cualquier política de `doas` aplicable. Revisa conjuntamente el comando permitido, el usuario de ejecución, los argumentos, el entorno y los valores predeterminados. El permiso para ejecutar comandos como una cuenta de servicio que no sea root también puede exponer los archivos de esa cuenta o una vía para llegar a root.

Un script de Python fijo permitido por sudo todavía puede ejecutar un comando de shell con la identidad RunAs si concatena entrada interactiva controlada por quien lo invoca en [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist de signos de puntuación del shell no basta para establecer que es seguro: [el shell también reconoce la sustitución de comandos `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Confirma que los argumentos permitidos llegan a la rama de entrada, que la entrada llega al comando de shell sin validación segura y que la política efectiva de sudo permite el usuario RunAs previsto. La ruta del script o una llamada a `os.system()` por sí solas solo son indicios para revisar; inspecciona el código fuente sin invocar el script privilegiado.

Un permiso efectivo de sudo como root para `chattr` puede quitar el atributo de archivo inmutable (`i`), pero eso por sí solo no concede permiso de escritura ni una nueva identidad. [El manual de `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) indica que el atributo bloquea las modificaciones y que solo root o un proceso con `CAP_LINUX_IMMUTABLE` puede cambiarlo. Comprueba la política exacta de argumentos de sudo y el soporte del sistema de archivos; después, verifica por separado que quien invoca el comando pueda escribir el archivo una vez quitado el atributo y que un consumidor con una identidad superior lo utilice. Por ejemplo, reemplazar un shell de inicio de sesión también requiere las credenciales aceptadas de la cuenta objetivo y un inicio de sesión real mediante ese shell. Revisa la política, los atributos del archivo y los permisos sin modificarlos durante la enumeración.

Si sudo solicita una contraseña y un código de un solo uso, trata esos requisitos previos por separado del permiso para ejecutar el comando. Un archivo `.google_authenticator` legible contiene material de semilla sensible, mientras que un hash antiguo de contraseña de aplicación o base de datos solo es una posible contraseña actual de la cuenta; ninguno demuestra que el otro factor sea aceptado por la configuración efectiva de PAM. Una vez autorizado, revisa el usuario RunAs y los argumentos exactos: un permiso root sin restricciones para `gem` de RubyGems puede exponer su comando de editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), pero un permiso restringido o una autenticación fallida no. La enumeración pasiva debe informar de las rutas y la política sin mostrar la semilla, recuperar una contraseña, generar un código ni invocar el comando privilegiado.

Un permiso efectivo de sudo para `knife` de Chef con capacidad de root y sin restricciones merece una revisión a nivel de intérprete: [Chef documenta que `knife exec -E` evalúa localmente una cadena Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica que la regla efectiva de sudo permita el subcomando `exec` y el argumento `-E` proporcionado por quien invoca el comando, la identidad RunAs prevista y cualquier denegación de comandos o argumento fijo que coincida. El binario instalado o una regla restringida a otros subcomandos solo son indicios para revisar. La enumeración pasiva debe informar de la regla sin invocar `knife`.

Un permiso exacto de sudo para `msfconsole` interactivo con capacidad de root es igualmente sensible: [GTFOBins documenta su consola `irb`](https://gtfobins.org/gtfobins/msfconsole/), que puede heredar la identidad de sudo. Confirma el usuario RunAs efectivo, la lista de argumentos permitidos, las denegaciones de comandos, `NOEXEC` u otras restricciones, el comportamiento de la consola instalada y si quien invoca el comando puede proporcionar entrada interactiva. Que aparezca resaltada una ruta solo es un indicio para revisar; la enumeración pasiva no debe iniciar la consola.

En FreeBSD, incluso una regla de sudo limitada a `pkg update` y `pkg install *` como root merece una revisión de la confianza en los repositorios. Comprueba si quien invoca el comando puede escribir `/etc/hosts` y si la configuración *efectiva* de repositorios habilitados utiliza un nombre de host HTTP con `signature_type: none`. [El manual de `pkg.conf` de FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) indica que `none` desactiva la verificación de firmas; `pkg+http` por sí solo no lo demuestra. [Un paquete puede contener scripts de instalación](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), por lo que alguien que controle realmente el endpoint del repositorio y pueda seleccionar un paquete podría cruzar el límite de root. Verifica las anulaciones de repositorios, la resolución de SRV/espejos, los argumentos efectivos de sudo, la selección del paquete y la ejecución de scripts antes de llegar a esa conclusión. Inspecciona la política y los archivos de configuración locales pequeños sin redirigir nombres ni ejecutar `pkg` durante la enumeración.

Un permiso de sudo con capacidad de root para `apt-get update` y `apt-get upgrade` también requiere revisar la confianza en los repositorios si sudo conserva un `http_proxy` controlado por quien invoca el comando. Comprueba si la configuración efectiva de APT utiliza realmente esa variable de entorno y qué solicitudes a repositorios habilitados podría afectar; un proxy por sí solo no puede sustituir paquetes de un archivo autenticado por una clave de firma confiable. [El manual del transporte HTTP de APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedencia de los proxies, y [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) documenta la verificación de firmas, las anulaciones para repositorios inseguros y la confirmación necesaria para paquetes no autenticados. Confirma el usuario RunAs y los argumentos exactos de sudo, la política de autenticación de repositorios, cualquier aceptación interactiva requerida y si la actualización seleccionada ejecuta scripts de paquetes como root. Inspecciona la política y la configuración local de forma pasiva; no redirijas el tráfico de paquetes ni ejecutes una actualización durante la enumeración.

Una regla de sudo con capacidad de root para `snap install` puede cruzar el límite entre paquete y código si los argumentos permiten a quien la invoca seleccionar un snap local y un modo de instalación permisivo. [Snap documenta](https://snapcraft.io/docs/explanation/snap-development/install-modes/) que `--dangerous` omite las comprobaciones de aserción de snaps locales y `--devmode` relaja el confinamiento; [un hook de instalación puede ejecutarse durante la instalación inicial](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Comprueba la política exacta de argumentos y RunAs de sudo, quién controla el archivo snap, si snapd instalado acepta esos modos y la identidad efectiva y el confinamiento del hook antes de afirmar que se puede acceder a archivos protegidos del host. Un binario `snap` o una regla que parezca contener un comodín no demuestran por sí solos esta cadena. La enumeración pasiva no debe instalar un paquete ni ejecutar su hook.

Para un permiso exacto de sudo para un binario personalizado que lee credenciales como una cuenta **que no es root**, primero inspecciona el binario concedido y sus permisos sin ejecutarlo. Una comprobación de contraseña integrada podría ser visible únicamente como caracteres anchos; [GNU `strings` documenta la extracción de cadenas little-endian de 16 bits](https://sourceware.org/binutils/docs/binutils/strings.html). Una cadena visible no demuestra que sea la contraseña aceptada ni que la rama de éxito exponga una credencial actual. Verifica por separado el comportamiento del binario, el acceso de la cuenta objetivo a los datos protegidos, la validez de las credenciales y cualquier transición posterior de cuenta o grupo. Si esa cuenta pertenece a `docker`, verifica el acceso al socket y si el daemon se ejecuta como root o rootless antes de inferir acceso a root del host; [Docker documenta las implicaciones de nivel root de su grupo](https://docs.docker.com/engine/install/linux-postinstall/). La enumeración habitual debe informar de la regla de sudo y la pertenencia a grupos sin ejecutar el binario ni volcar sus cadenas.

Una regla de sudo con comodín para los scripts de mantenimiento de una aplicación requiere revisar más que la ruta del script. Comprueba si el script permitido acepta argumentos sin restricciones o lee ajustes que una cuenta de aplicación con menos privilegios puede modificar; después, sigue esos valores hasta los comandos de shell o el entorno de un subproceso. Por ejemplo, [`zmupdate.pl` de ZoneMinder construye un comando `mysqldump` y lo ejecuta mediante `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mientras que [`zmdc.pl` copia el ajuste `ZM_LD_PRELOAD` a `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) antes de iniciar daemons. Una regla de sudo que permita ejecutar cualquiera de esos scripts como root puede cruzar un límite de confianza si la entrada correspondiente es controlable y llega a ese código en la versión instalada. Inspecciona la regla efectiva de sudo, los permisos de configuración de la aplicación y el código fuente del script; el comodín o el ajuste por sí solos son indicios para revisar, no una prueba de ejecución.

- `SETENV`, `env_keep`, `secure_path` y `LD_PRELOAD` pueden convertir un comando que, de otro modo, sería limitado en un secuestro de imports, bibliotecas o PATH. Consulta la [guía de variables de entorno](../linux-basics/linux-environment-variables.md) y [el abuso de SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Un permiso exacto de sudo con capacidad de root y `SETENV` para un wrapper de shell también merece una revisión de un solo salto si el wrapper inicia un script fijo de Python con un import literal. `secure_path` limita la búsqueda de comandos del shell, no la [búsqueda de módulos de Python mediante `PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` y `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hacen que Python ignore esa variable de entorno. Confirma las etiquetas y denegaciones efectivas de sudo, la rama del wrapper, las opciones del intérprete, la resolución del import y la existencia de un directorio de búsqueda en el que quien invoca el comando pueda escribir antes de considerarlo ejecución de código. Inspecciona estáticamente los scripts breves; no invoques el wrapper privilegiado.

Un permiso exacto de sudo para `neofetch ""` con capacidad de root todavía puede cargar una configuración de shell si los valores predeterminados aplicables de sudo conservan un `XDG_CONFIG_HOME` controlado por quien invoca el comando. [El cargador de configuración de Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carga el archivo `neofetch/config.conf` o `neofetch/config` situado bajo ese directorio; la lista de argumentos vacía no impide esta búsqueda. Confirma el cargador instalado, el usuario RunAs y la política de argumentos efectivos, las posibles denegaciones de comandos, si sudo realmente conserva la variable seleccionada para este comando y si quien invoca el comando controla una ruta de configuración legible. Una variable conservada o la presencia de Neofetch instalado solo son indicios para revisar. Inspecciona la política y los metadatos del archivo sin invocar el comando privilegiado ni mostrar el contenido de la configuración; consulta [el tratamiento del entorno de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regla de sudo sin restricciones para `facter` con capacidad de root merece una revisión aparte de los custom facts. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) que `--custom-dir` carga archivos de facts Ruby desde un directorio seleccionado. Comprueba si la regla exacta de sudo permite esa opción, si la versión instalada de Facter la acepta y si quien invoca el comando controla el directorio. Un permiso con argumentos fijos, una denegación explícita del comando o los custom facts desactivados pueden cambiar el resultado. La enumeración pasiva debe informar de la regla candidata sin invocar Facter ni leer el contenido de los facts.

Para un permiso exacto de sudo con capacidad de root para un script y `SETENV`, inspecciona los nombres de comandos sin ruta, como `find`, y el `PATH` efectivo después de aplicar la política de sudo y la inicialización del script. Un archivo Bash cargado también puede ejecutar `enable -n [`: [Bash buscará entonces `[` externo en `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) cuando el script use ese comando más adelante. Confirma las [reglas de entorno y `secure_path` de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) aplicables, cualquier entrada `NOSETENV`/`NOEXEC` o denegación, el flujo del script y los archivos cargados, y la existencia de un directorio de búsqueda ejecutable controlado por quien invoca el comando. Un script legible que contiene un comando sin ruta es un indicio para revisar, no una prueba de ejecución privilegiada; inspecciónalo sin invocar la regla de sudo.
- Un script privilegiado que obtiene una URL fija con `curl` todavía puede aceptar una respuesta elegida por quien lo invoca si una regla de sudo aplicable conserva `http_proxy` y la solicitud se envía mediante ese proxy. Si después el script pasa la respuesta a un analizador XML que resuelve entidades externas, una respuesta maliciosa puede revelar archivos legibles por el proceso privilegiado. Comprueba la política exacta de entorno de sudo, las exclusiones de `no_proxy`, la URL solicitada, la configuración del analizador y el destino de salida; una variable de proxy o un analizador XML por sí solos no constituyen una vulnerabilidad. La [documentación de variables de entorno de proxy de curl](https://everything.curl.dev/usingcurl/proxies/env.html) describe el comportamiento de estas variables. No hagas solicitudes de red ni analices XML malicioso durante la enumeración pasiva.
- Un script de sudo con capacidad de root que construye un archivo PostScript a partir de datos influenciados por quien lo invoca y luego ejecuta `ps2pdf -dNOSAFER` merece una revisión aparte del flujo de entrada. Ghostscript documenta que esta opción desactiva SAFER hasta `.setsafe`, lo que permite operaciones con archivos PostScript dentro de los permisos del sistema operativo del proceso. Una consulta SQL construida con un argumento de quien invoca el comando puede alimentar filas controladas por el atacante a la plantilla PostScript, pero una cadena de consulta o una invocación de `ps2pdf` por sí solas no demuestran que los datos lleguen a sintaxis PostScript ejecutable. Confirma la regla efectiva de sudo, la ruta exacta entre la entrada y la plantilla, cualquier escape, el comportamiento de la versión instalada de Ghostscript y si SAFER se vuelve a habilitar antes de interpretar el documento. No invoques la conversión privilegiada durante la enumeración pasiva. Consulta la [documentación de `-dNOSAFER` de Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Para una regla de sudo que ejecuta un script de shell, compara las variables conservadas con el propio script. Una construcción como `if $CHECK_CONTENT; then` ejecuta el valor expandido como comando; por tanto, conservar `CHECK_CONTENT` puede permitir ejecutar comandos aunque la ruta y los argumentos del script sean fijos. Hay que comprobar si la rama es alcanzable y si el entorno se conserva realmente para esa regla concreta.<sup>[[2]](#references)[[22]](#references)</sup>
- Un script de Python permitido por sudo puede importar código desde un directorio en el que se pueda escribir o desde un archivo `.pyc` en caché. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md) detalla el caso de la caché.
- Un script fijo de Python permitido por sudo para ejecutarse como root todavía puede exponer un depurador interactivo. Llamadas como `pdb.set_trace()` o `pdb.post_mortem()` permiten ejecutar sentencias de Python en el contexto del proceso depurado si quien invoca el comando puede alcanzar el breakpoint o el manejador de excepciones **y controlar la entrada del depurador**. Comprueba la regla exacta de sudo y RunAs, la autenticación y las condiciones de la rama, la posibilidad de alcanzar la excepción, quién controla el terminal/la entrada y si el depurador se ejecuta en ese mismo proceso privilegiado. Una solicitud a un socket que provoca una excepción no concede por sí sola acceso a un depurador conectado a otro terminal. [Python documenta la evaluación de sentencias del depurador y el modo post-mortem](https://docs.python.org/3/library/pdb.html); inspecciona estáticamente el script en lugar de activar el manejador privilegiado durante la enumeración.
- Un script fijo de Python permitido por sudo también puede leer un campo de perfil de una base de datos o un socket Unix y añadirlo a una cadena que más tarde se convierte en la **cadena de formato** de `str.format()`. [Los campos de reemplazo pueden acceder a atributos y claves de diccionario](https://docs.python.org/3/library/string.html#format-string-syntax), por lo que un campo controlado por un atacante puede inspeccionar objetos pasados a `format()` y exponer datos a los que pueda acceder si el resultado se imprime o se guarda en un lugar que quien invoca el comando pueda leer. Comprueba la identidad RunAs efectiva de sudo, el permiso de escritura en el registro concreto, el flujo de datos hasta la cadena de formato, los objetos proporcionados y la visibilidad de la salida. Esto no implica ejecución automática de código; una cadena de formato literal y confiable con *valores* controlados por un atacante es un caso distinto. Un secreto divulgado solo permite cambiar de cuenta del sistema operativo si esa cuenta lo acepta. Revisa el script y los permisos del socket sin invocar la operación privilegiada.
- Un wrapper de Python con capacidad de root puede pasar una URL seleccionada por quien lo invoca a `Repo.clone_from` de GitPython. Si el wrapper también habilita `protocol.ext.allow=always` de Git, un remoto `ext::` puede invocar un helper externo. Comprueba los argumentos exactos de sudo, el origen de la URL, la versión del paquete GitPython y si el proveedor aplicó parches, y si el wrapper opta explícitamente por protocolos inseguros. GitPython añadió una [protección predeterminada para protocolos inseguros](https://github.com/gitpython-developers/GitPython/commit/2625ed9) en la versión 3.1.30; la versión del ejecutable `git` es un dato independiente. Una revisión pasiva debe limitarse a leer la regla y el código fuente pertinente, sin invocar la clonación.
- Un permiso de sudo entre usuarios para una CLI de clonación de repositorios puede exponer una vía distinta de inyección en cadenas de shell. Sigue si el argumento de repositorio seleccionado por quien invoca el comando llega a [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) de Node.js u otro generador de comandos de shell sin separar los argumentos de forma segura; `exec` de Node pasa su cadena de comando a un shell. Confirma el usuario RunAs exacto, los subcomandos y argumentos permitidos, el código del wrapper instalado y la validación de entrada. El nombre de una herramienta de repositorios o una regla de sudo sin restricciones por sí solos no demuestran inyección de comandos. Inspecciona el wrapper sin invocar una clonación privilegiada durante la enumeración.
- Un wrapper personalizado propiedad de root puede parecer seguro porque sus binarios y scripts no permiten escritura, pero su decisión de ejecutar una acción privilegiada puede depender de un indicador, un valor de API local o un estado del servicio que pueda cambiar un usuario sin privilegios. Sigue cada condición hasta su entrada y las comprobaciones de autorización. Durante la enumeración, inspecciona la configuración y los permisos sin cambiar el estado operativo; una llamada a `systemd-run` dentro del wrapper solo es relevante si se puede influir en la condición.
- Un cliente de copias de seguridad permitido mediante sudo como root puede aceptar un archivo de configuración seleccionado por quien lo invoca (por ejemplo, `npbackup-cli -c`). Comprueba el usuario de ejecución exacto y los argumentos permitidos, y luego si quien invoca el comando controla la ruta de configuración, las rutas de origen de la copia de seguridad y el repositorio o las opciones de lectura/restauración. Un secreto de repositorio cifrado en una configuración legible puede seguir siendo utilizable por el cliente, pero la regla por sí sola no demuestra acceso al repositorio ni divulgación de archivos root. Valida la autorización sin ejecutar una copia de seguridad ni volcar su contenido.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) admite `--password-command`, que ejecuta un programa para obtener la contraseña de un repositorio. Si una regla de sudo permite a un usuario con menos privilegios ejecutar restic como root con un comando de contraseña elegido por quien lo invoca y un subcomando que requiere la contraseña, ese helper puede ejecutarse como root. Revisa los argumentos exactos de sudo y las exclusiones; no invoques el helper ni un comando de copia de seguridad solo para enumerar esta condición.
- Un permiso privilegiado de `restic backup` también puede cruzar un límite de lectura de archivos si el patrón de argumentos de sudo permite a quien lo invoca elegir tanto el origen como un repositorio que después pueda leer y descifrar. [Los comodines de argumentos de sudoers pueden coincidir con espacios y barras](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), así que inspecciona los comodines finales en vez de asumir que un prefijo de repositorio fijo restringe el origen. [Restic puede hacer copias de seguridad en repositorios locales y remotos](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), pero un repositorio local puede contener objetos recién escritos solo accesibles por root; confirma la política efectiva de sudo, el acceso al backend, la contraseña del repositorio y los permisos de los objetos resultantes antes de considerarlo una divulgación. Una clave SSH copiada permite acceder a una cuenta solo si la cuenta de destino la acepta. No ejecutes una copia de seguridad para probarlo durante una revisión pasiva.
- Un comando personalizado de mantenimiento o copias de seguridad sin restricciones puede aceptar una ruta de salida u ofrecer su propio planificador de tareas. Para una vía de escritura de archivos, verifica la regla exacta de sudo y el usuario de ejecución; después, si quien invoca el comando controla tanto los datos como el destino. Para una vía de comandos programados, verifica la identidad de ejecución del planificador, la entrada del comando y cualquier requisito adicional de contraseña o autorización. El nombre del comando o `NOPASSWD` por sí solos no demuestran ninguna de las dos vías. Consulta [escritura en archivos propiedad de root](../interesting-files-permissions/write-to-root.md) y [cron y temporizadores de systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando fijo de sudo todavía puede cargar un archivo de configuración predecible desde un directorio compartido en el que se pueda escribir. Sigue si quien invoca el comando puede reemplazar ese archivo y si sus campos de origen y destino controlan una descarga o copia privilegiada. Una URL de archivo local puede exponer datos que solo puede leer la cuenta RunAs de sudo; un origen controlado por quien invoca el comando junto con un destino protegido puede crear una vía de escritura. Confirma el tratamiento de URL del programa instalado, las comprobaciones de la ruta de destino, la regla efectiva de sudo y la accesibilidad de la salida. Una ruta de configuración escribible en `/tmp` por sí sola solo es un indicio para revisar; inspecciona el binario y los metadatos del archivo sin invocar la transferencia privilegiada.
- Una regla de sudo para `git apply` puede permitir que la cuenta RunAs escriba archivos seleccionados mediante un parche controlado por quien invoca el comando. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permitía que un parche manipulado creara un enlace simbólico y luego escribiera fuera del árbol de trabajo, incluso cuando el comando no aceptaba `--unsafe-paths`. Comprueba la regla efectiva de argumentos de sudo, el origen del parche, el acceso de la cuenta RunAs al directorio de trabajo y la corrección de Git instalada o el backport del proveedor. Una regla sin restricciones que admita `--unsafe-paths` supone un riesgo independiente debido a esa opción explícita; ni una versión de Git ni el permiso para ejecutar `git apply` por sí solos demuestran que se pueda modificar un archivo protegido. No apliques un parche no confiable durante la enumeración pasiva.
- Una regla con capacidad de root para `clamscan --debug` puede cruzar un límite de lectura si un usuario con menos privilegios puede proporcionar una imagen DMG y el analizador instalado está afectado por [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), que podría revelar el contenido de archivos mediante la salida de depuración. Confirma los argumentos permitidos exactos y la ruta de análisis, el control de la entrada, la cuenta RunAs efectiva, la corrección del motor o el backport y si la salida es visible para quien invoca el comando. Si una regla más amplia permite `--file-list`/`-f`, revisa por separado el comportamiento de esa lista de archivos; una política fija a `--debug <scan-path>` no admite esa opción. Inspecciona la política y los metadatos del paquete sin analizar un archivo manipulado ni mostrar salida protegida durante la enumeración.
- Una regla de sudo con capacidad de root que abre una imagen de disco cifrada seleccionada por quien invoca el comando y una segunda regla que monta el mapper resultante pueden importar archivos controlados por quien invoca el comando al espacio de nombres de montajes del host. Confirma ambas reglas efectivas y sus argumentos, el control de la imagen y el nombre del mapper, el destino real del montaje y el propietario y modo de los archivos resultantes. Una transición de set-user-ID también requiere un ejecutable accesible, opciones de montaje que lo permitan (`nosuid` lo bloquea) y las políticas de proceso o MAC pertinentes; abrir o montar una imagen por sí solo solo es un indicio para revisar. Una vía distinta mediante una copia de seguridad existente requiere su clave real y un secreto útil que se pueda leer. Inspecciona la política y las rutas sin abrir ni montar una imagen durante la enumeración pasiva. Consulta el [manual de cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) y las [opciones de montaje](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regla de sudo con capacidad de root para un script de shell o Python merece revisar el directorio de trabajo si el script invoca `./helper` sin cambiar antes a un directorio fijo. Una lista de Python como `['./helper']` pasada a `subprocess.run` puede tener el mismo comportamiento: quien invoca el comando puede seleccionar el directorio de trabajo. Esa persona quizá pueda elegir un directorio escribible y colocar allí un ejecutable con ese nombre relativo; una ruta absoluta en otra parte del script no protege esta llamada. Confirma la regla efectiva, `runchdir` u otra política que cambie el directorio, el flujo del script y la alcanzabilidad de la rama, la existencia de un directorio escribible y ejecutable y las restricciones de montaje/`NOEXEC` antes de considerarlo ejecución de código. Si el script no es legible, el comportamiento seguirá siendo desconocido hasta que se revise el código fuente por una vía autorizada. Revisa los scripts estáticamente en lugar de ejecutar el helper. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la política del directorio de trabajo.
- Un validador fijo de Python con capacidad de root todavía puede evaluar un archivo de datos seleccionado por quien lo invoca. [La documentación de `eval()` de Python advierte sobre la entrada no confiable](https://docs.python.org/3/library/functions.html#eval): comprobar un sufijo de entrada, un prefijo aritmético o una rama de validación no crea un sandbox si la expresión restante llega a `eval`. Confirma la regla efectiva de sudo, si quien invoca el comando puede seleccionar y controlar el archivo exacto, las condiciones de la rama del analizador y la construcción de la expresión, y la identidad del proceso privilegiado antes de considerarlo una vía de ejecución. La presencia de `eval` en un script legible por sí sola solo es un indicio para revisar; inspecciona el código fuente y los permisos de los archivos sin ejecutar el validador ni enviar una expresión de prueba durante la enumeración.
- Un wrapper de Ruby con capacidad de root que lee un nombre de archivo YAML relativo, como `YAML.load(File.read("dependencies.yml"))`, puede obtener la entrada del directorio de trabajo de quien lo invoca, a menos que el wrapper o la política de sudo fijen ese directorio. Comprueba los argumentos permitidos exactos, los permisos del directorio y el archivo, y el comportamiento de Psych instalado: las implementaciones antiguas de `YAML.load` podían deserializar objetos Ruby arbitrarios, mientras que las versiones nuevas restringen las clases de forma predeterminada. Una llamada en el código fuente solo es un indicio para revisar; confirma que el archivo realmente proviene de un directorio en el que quien invoca el comando puede escribir y que el cargador instalado acepta clases peligrosas. Para entradas no confiables, es preferible `safe_load` con una lista de permitidos explícita y mínima. Consulta la [documentación de Psych de Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) y la [documentación de Psych de Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Un permiso exacto de `sudo go run /absolute/file.go` con capacidad de root merece revisar el directorio de trabajo cuando el código Go lee un archivo WASM relativo y puede ejecutar un script de shell relativo después de inspeccionar su resultado. Confirma el RunAs efectivo, los argumentos y las denegaciones del comando, la existencia de un directorio de trabajo actual en el que quien invoca el comando pueda escribir, el flujo de datos de WASM a la rama y si esa rama invoca el helper. Un `runchdir` fijo de sudo, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) pueden cambiar la ubicación de búsqueda. La mera coincidencia estática es solo un candidato; inspecciona el código fuente sin ejecutar Go, WASM ni el helper.
- `sudoedit` y los comodines en argumentos requieren comprobar la versión y la regla exactas; la [lista de comprobación](linux-privilege-escalation-checklist.md) incluye el problema de edición de archivos con sudoedit. Para un permiso de `sudoedit` entre usuarios sobre una ruta con comodín, inspecciona el ajuste efectivo `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, el destino resuelto y quién puede reemplazar cada entrada del directorio padre. El primero puede permitir seguir un enlace simbólico, mientras que desactivar el segundo elimina las comprobaciones de directorios escribibles; ninguno de los ajustes por sí solo demuestra que se pueda escribir en el archivo de otro usuario. Confirma la política instalada de sudo y los argumentos exactos que coinciden antes de llegar a esa conclusión. Consulta las [definiciones de opciones de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- En una regla de comandos de sudoers, un comodín en los argumentos puede coincidir tanto con espacios como con caracteres de ruta. Por tanto, una regla para un comando con capacidad de lectura y un argumento como `/restricted/*` puede admitir un argumento de archivo adicional después de un prefijo coincidente. Revisa el usuario RunAs exacto, la ruta del comando, el patrón de argumentos y las denegaciones posteriores; demostrar que se pueden leer archivos no implica ejecución de comandos. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue los patrones de argumentos de los patrones de rutas de comandos.
- Un patrón de argumentos que parece una ruta también puede coincidir con `../`. Por ejemplo, una regla con capacidad de root para `node /opt/scripts/*.js` puede permitir que quien la invoca seleccione un archivo JavaScript fuera de `/opt/scripts` si el nombre proporcionado sigue empezando por `/opt/scripts/` y se resuelve mediante segmentos de directorio padre. Se trata de un comodín de **argumento**; el comodín de la ruta del comando para el ejecutable Node tiene reglas distintas para las barras. Comprueba la regla efectiva, las denegaciones posteriores, la resolución de la ruta, el control del archivo de destino y cualquier restricción de expresión regular o digest de sudoers antes de concluir que se puede ejecutar código. Consulta las [reglas de comodines de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) y la [documentación de línea de comandos de Node](https://nodejs.org/api/cli.html).
- Los programas de archivado y otras utilidades pueden tener hooks de ejecución. Comprueba los argumentos exactos permitidos con [GTFOBins](https://gtfobins.github.io/) en lugar de asumir que solo los shells o los intérpretes ejecutan comandos.
- Una regla sin restricciones para `qpdf` con capacidad de root puede exponer un archivo privilegiado mediante adjuntos PDF: qpdf 10.2 y posteriores admiten `--empty` y `--add-attachment file ... --` con un PDF de salida. Si el proceso privilegiado puede leer el origen seleccionado y escribir el PDF en una ruta accesible para quien lo invoca, el archivo de salida puede contener los bytes del origen. Revisa los argumentos efectivos y las exclusiones de sudo, la versión de qpdf, el acceso al origen y la ruta de salida antes de concluir que es posible divulgar archivos. Leer una clave SSH de root solo sirve para iniciar sesión si la clave es válida y se permite la autenticación SSH de root. Consulta las [opciones de adjuntos de qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- La reutilización de marcas de tiempo de sudo depende de la política de caché, el usuario propietario, el terminal/la sesión y los permisos. La [guía de escalada de privilegios](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) cubre estas comprobaciones.
- `doas` tiene sus propias reglas y configuración. Comprueba los comandos permitidos y las rutas de configuración escribibles, tal como se describe en la [sección de doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Herramientas de compilación y paquetes ejecutadas mediante sudo

Un permiso de sudo sin restricciones para `forge` de Foundry puede ser relevante incluso si la identidad RunAs es otro usuario que no es root. Opciones del compilador como `--use` pueden seleccionar un ejecutable local, y `forge flatten -o` selecciona un archivo de salida. Comprueba la versión de Forge instalada, los argumentos exactos de sudo, los proyectos y las rutas del compilador accesibles, los permisos de salida y el entorno efectivo antes de considerar explotable el permiso. Un ejecutable helper relativo encontrado mediante `PATH` es una vía que depende de la versión y del entorno, no una característica que deba darse por sentada en todas las compilaciones de Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Un permiso de `pacman` sin restricciones con capacidad de root permite más que consultas de paquetes: `-U` acepta un paquete local, los paquetes pueden incluir scripts de instalación y `--hookdir` selecciona otro directorio de hooks. Revisa la regla efectiva de sudo, las restricciones de argumentos y las exclusiones antes de probar; la enumeración pasiva no necesita instalar un paquete ni ejecutar un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper fijo de shell ejecutado mediante sudo también puede instalar una dependencia npm con nombre y luego iniciar una aplicación Node. Revisa su regla exacta de RunAs, si el paquete ya está instalado, los valores efectivos de `HOME` y `userconfig` de npm, la configuración del proyecto o las anulaciones de línea de comandos, y si un usuario con menos privilegios controla el registro o el paquete devuelto para ese nombre. [npm documenta la búsqueda de `.npmrc` por usuario y por proyecto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); el comportamiento de `HOME` de sudo depende de la política instalada y de la distribución, por lo que es posible que el proceso npm privilegiado lea o no el archivo `.npmrc` de un usuario escribible. Si la aplicación privilegiada importa el paquete recién instalado, su código de módulo puede ejecutarse con la identidad de esa aplicación. Los scripts de instalación son una vía separada, dependiente de la versión y la configuración; [npm documenta su ciclo de vida y el tratamiento de usuarios](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Una ruta `.npmrc` o una línea `npm install` por sí solas solo son indicios para revisar. Inspecciona la regla, el wrapper breve, las rutas de configuración y la procedencia del paquete sin instalar el paquete ni iniciar la aplicación durante la enumeración pasiva.

Un permiso de `pip` o `pip3 download` con capacidad de root también es un indicio para revisar la compilación de paquetes cuando los argumentos permiten a quien lo invoca seleccionar una distribución de código fuente no confiable, incluso si el patrón de URL la limita a un servicio local y a un sufijo `.tar.gz`. `pip download` acepta URL de archivos y resuelve metadatos de paquetes; preparar los metadatos de una distribución de código fuente puede invocar su backend de compilación o código heredado de `setup.py` antes de que el archivo simplemente se guarde. Confirma el usuario RunAs y la regla de argumentos exactos de sudo, si quien invoca el comando puede publicar o reemplazar el archivo seleccionado y si esa versión de pip realmente prepara sus metadatos. Un archivo fijo y confiable o un wheel no demuestran esta vía. No descargues ni compiles un paquete no confiable durante la enumeración pasiva. Consulta el [comando download de pip](https://pip.pypa.io/en/stable/cli/pip_download/), la [interfaz del sistema de compilación](https://pip.pypa.io/en/stable/reference/build-system/) y las [recomendaciones para instalaciones seguras](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regla de sudo que permite `pip install` con una ruta de proyecto local seleccionada por quien lo invoca crea un límite de compilación más directo. [pip acepta directorios de proyectos locales](https://pip.pypa.io/en/stable/topics/local-project-installs/) e invoca su sistema de compilación; el [backend de compilación ejecuta hooks controlados por el proyecto](https://pip.pypa.io/en/stable/reference/build-system/). Confirma la identidad RunAs efectiva, las restricciones y denegaciones exactas de argumentos, el control del proyecto seleccionado y el comportamiento de pip/backend instalado antes de considerar que la regla permite ejecutar código privilegiado. Un proyecto fijo y confiable o una regla que excluya rutas seleccionadas por quien invoca el comando no demuestran esta vía. Revisa la regla y los metadatos del proyecto sin instalar ningún paquete durante la enumeración pasiva.

Un permiso de `easy_install` heredado, sin restricciones y con capacidad de root es un indicio similar para revisar la compilación de paquetes. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) que Easy Install acepta un directorio de proyecto local y compila distribuciones de código fuente; un proyecto controlado por quien lo invoca puede ejecutar su `setup.py` durante esa compilación con la identidad de sudo. Confirma la cuenta RunAs efectiva, el comando y las restricciones exactas de argumentos (incluidas las denegaciones posteriores), el control del proyecto seleccionado y el comportamiento de la herramienta instalada. Un proyecto fijo y confiable o una política que no permita seleccionar un origen controlado por quien invoca el comando no demuestran esta vía. Inspecciona la regla y los metadatos del proyecto sin instalar ningún paquete durante la enumeración.

Un wrapper de Python permitido por sudo que utilice `setuptools.package_index.PackageIndex.download` con una URL seleccionada por quien lo invoca es un caso distinto a revisar de `pip download`: [GHSA-5rjg-fvgr-3xxf de setuptools](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) describe cómo un nombre de archivo derivado de una URL podía salir del directorio de descarga previsto y escribirse con los permisos del proceso en versiones afectadas anteriores a la 78.1.1. Confirma el usuario RunAs y la regla de argumentos efectivos de sudo, que el wrapper pase la URL de quien lo invoca a esta API concreta, la compilación instalada o el backport del proveedor y dónde se resuelve la ruta resultante. Una cadena de versión o un directorio de descarga escribible por sí solos no demuestran escritura arbitraria. Revisa el wrapper breve y los metadatos del paquete sin obtener la URL ni escribir un archivo durante la enumeración.

Un wrapper de compilación permitido por sudo que pasa un archivo `.spec` seleccionado por quien lo invoca a PyInstaller requiere la misma revisión del límite de confianza. Un archivo spec de PyInstaller es código Python ejecutable evaluado durante la **compilación**, y sus entradas `datas` pueden incorporar a un artefacto archivos legibles por la identidad de compilación. Confirma el usuario RunAs exacto, las reglas de argumentos y denegaciones de sudo, el tratamiento de rutas y ramas del wrapper, el control del archivo spec seleccionado y el acceso al artefacto resultante. Permitir simplemente una entrada `.py` o encontrar PyInstaller instalado no demuestra el control del archivo spec ni la ejecución privilegiada. La revisión pasiva solo debe leer un archivo wrapper acotado y sus metadatos; no debe ejecutar una compilación. Consulta la [documentación de archivos spec de PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Cargadores de presets y plugins ejecutados mediante sudo

Las herramientas de Python que aceptan un preset o directorio de plugins seleccionado por quien las invoca pueden importar código con los privilegios concedidos por sudo. Por ejemplo, BBOT acepta un preset con `-p`, y su [documentación sobre módulos personalizados](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) describe entradas `module_dirs` que seleccionan directorios adicionales de módulos Python. Si la regla efectiva de sudo permite un preset seleccionado por quien lo invoca y esa persona controla un módulo del directorio seleccionado, el import puede ejecutar código como el usuario privilegiado, posiblemente antes de que la herramienta rechace un módulo inválido. Comprueba la versión instalada, el usuario RunAs y la política de argumentos exactos de sudo, y quién posee el preset y las rutas de los módulos, sin cargar el módulo durante la enumeración.

### Herramienta de línea de comandos Backdrop ejecutada mediante sudo

[Bee](https://github.com/backdrop-contrib/bee) es una herramienta de línea de comandos PHP para Backdrop CMS. Sus comandos `eval` (`php-eval`) y `php-script` pueden ejecutar PHP proporcionado por quien la invoca. Por tanto, una regla de sudo que permita ejecutar Bee como root con argumentos sin restricciones puede exponer la ejecución de código como root cuando Bee pueda inicializar una instalación de Backdrop. Ejecútala desde el directorio del sitio o selecciona un sitio mediante la opción global `--root=<directory>`; encontrar Bee o un archivo `settings.php` de Backdrop no demuestra que sudo permita ejecutarlo, que haya un sitio utilizable ni que la inicialización tenga éxito. Revisa la regla efectiva de sudo, las posibles exclusiones de comandos, la identidad del ejecutable y el acceso al sitio antes de probarlo. Durante la enumeración pasiva, inspecciona la regla y las rutas de archivos sin invocar Bee. Consulta el [changelog de comandos de Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) para ver la incorporación de los comandos PHP.

### Servidores de terminal ejecutados mediante sudo

`mosh-server` inicia un servidor de terminal interactivo como el usuario que lo invoca. Elige un puerto UDP alto y una clave de sesión, informa de ambos a quien lo invoca y, normalmente, inicia el shell de inicio de sesión de ese usuario cuando se conecta un cliente. Por tanto, un permiso de sudo sin restricciones y con capacidad de root para `mosh-server` es un candidato para revisar como vía de shell, aunque el propio comando del servidor se desacople. Comprueba la identidad RunAs efectiva, los argumentos y las exclusiones permitidos, el binario instalado, el shell, la disponibilidad del cliente y el acceso UDP. La enumeración pasiva debe inspeccionar la regla de sudo sin iniciar un servidor ni mostrar una clave de sesión activa. Consulta el [manual del servidor Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) y las [notas de diseño del proyecto](https://github.com/mobile-shell/mosh#how-it-works).

### Wrappers privilegiados de copias de seguridad que reescriben el archivo de tareas de quien los invoca

Un wrapper de shell ejecutado como root puede aceptar un archivo de tareas seleccionado por quien lo invoca, eliminar `../` de las rutas de origen, comprobar que cada resultado empieza por un directorio permitido, reescribir el archivo de tareas y luego pasar su *nombre de ruta* a un programa de copias de seguridad. Revisa la ruta transformada tras resolverla por completo. Una sola pasada de reemplazo de cadenas puede revelar una nueva secuencia de traversal que supere una comprobación léxica de prefijo. Comprueba también si el programa de copias de seguridad lee los datos transformados en memoria o vuelve a abrir el archivo. Si lo vuelve a abrir, una reescritura fallida puede dejar intacta la entrada original.

En Linux, `fs.protected_regular` puede denegar una escritura con `O_CREAT` en un archivo normal de otro usuario situado en un directorio sticky de escritura mundial. Esa denegación es una medida de protección, pero un wrapper de shell que ignore el error de escritura aún puede continuar con el archivo de tareas original. Confirma el ajuste, el propietario del archivo y del directorio, y si el wrapper se detiene ante un fallo. Esta ruta solo es candidata a divulgación de archivos cuando la regla efectiva de sudo permite ejecutar el wrapper como usuario privilegiado, quien lo invoca controla la entrada de tareas y un destino de copias de seguridad legible, y la utilidad de copias de seguridad realmente incluye los orígenes protegidos. Inspecciona estas condiciones sin ejecutar el proceso de copia de seguridad durante la enumeración.

### Comodines de argumentos en herramientas de red privilegiadas

En una regla de sudo para `tcpdump`, un `*` en el **patrón de argumentos** puede coincidir con espacios y barras, por lo que una restricción que parece limitar una ruta aún podría permitir texto adicional de opciones. Esto difiere de un comodín en la ruta del ejecutable del comando; inspecciona la regla completa de RunAs y las denegaciones posteriores. Si se pueden inyectar opciones, la invocación permitida y la [semántica de opciones de `tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) de la versión instalada determinan si `-F`, `-V`, `-r`, `-w` o `-Z` ofrecen una primitiva útil de lectura/escritura. `-V` lee una lista de nombres de archivos de captura, no vuelca cualquier archivo arbitrario de propósito general. AppArmor u otra política MAC pueden bloquear el acceso a archivos incluso cuando sudo permite el comando; un archivo de perfil en disco no demuestra que esté cargado o aplicándose. Revisa pasivamente la autorización y la política antes de llegar a una conclusión. El [manual de sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) describe la diferencia entre comodines.

Una regla de sudo con capacidad de root que enumera solo el ejecutable `tcpdump`, sin restringir los argumentos, también merece una revisión. El [manual de tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` como un comando posterior a la rotación cuando `-C` o `-G` rota una captura guardada; `-Z` o un valor predeterminado de compilación pueden eliminar privilegios antes de ejecutar ese comando. Verifica la regla efectiva de sudo, la compilación instalada, el comportamiento de reducción de privilegios y si se puede producir una rotación antes de tratar la regla como una vía de escalada. Una regla resaltada es un candidato, no una prueba de ejecución de comandos como root.

### Wrappers de Nmap ejecutados mediante sudo

Cuando una ruta de `nmap` permitida por sudo es un wrapper de shell, inspecciona la ruta permitida exacta y todas las opciones que reenvía. Bloquear la forma conocida `--script` no necesariamente bloquea la carga de código NSE: [`--datadir` de Nmap](https://nmap.org/book/man-misc-options.html) selecciona archivos de datos y NSE [carga `nse_main.lua`](https://nmap.org/book/nse-implementation.html) desde el directorio de datos seleccionado cuando se habilita el scripting. Algunas compilaciones instaladas también aceptan formas alternativas de opciones largas, así que compara las restricciones con el analizador real de ese binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) es otra superficie de lectura de archivos; los errores del analizador pueden revelar texto. Comprueba la regla efectiva de sudo, la lógica del wrapper, la versión de Nmap, el control del directorio y la política MAC sin ejecutar escaneos durante la enumeración.

### Hooks de pull de Mercurial ejecutados mediante sudo

Un origen fijo en `sudo hg pull /fixed/source` todavía deja que el directorio de trabajo actual seleccione el repositorio **receptor**, a menos que el comando lo fije con `-R`. Un repositorio receptor controlado por quien invoca el comando puede definir hooks en `.hg/hgrc`, y un hook puede ejecutarse como el usuario RunAs de sudo. [Mercurial ignora la configuración de repositorios propiedad de un usuario o grupo no confiable](https://mercurial-scm.org/help/topics/config), así que inspecciona los usuarios/grupos de confianza de la cuenta RunAs y el directorio de trabajo exacto antes de considerar que permite ejecutar código. Leer la política y la configuración basta para una revisión pasiva; no ejecutes pull ni invoques un hook para enumerarlo.

### Hooks de pull de Git ejecutados mediante sudo

Para un permiso exacto de `sudo git pull` con capacidad de root, comprueba también el repositorio **receptor** seleccionado por el directorio de trabajo. Un repositorio propiedad de quien invoca el comando puede tener un hook `post-merge` ejecutable que se ejecuta con la identidad del proceso Git cuando un pull realiza una fusión correcta; [Git documenta este hook](https://git-scm.com/docs/githooks) y el [comportamiento de pull para merge frente a rebase](https://git-scm.com/docs/git-pull). Verifica la regla efectiva de sudo y el directorio de trabajo actual, la ruta activa del hook y sus permisos, y si es posible realizar una fusión con commits nuevos. Un pull fallido, sin cambios o que solo haga rebase no demuestra esta vía de hook. Inspecciona la política y los metadatos del repositorio sin ejecutar el pull privilegiado.

### Copias de archivo con rsync ejecutado mediante sudo

Para `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` en el **patrón de argumentos de sudoers** puede coincidir con espacios y admitir una opción adicional entre el origen y el destino. Esto es distinto de la expansión de nombres de archivo del shell. Si quien invoca el comando puede llenar el origen y el destino es escribible por el proceso privilegiado de rsync, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) puede solicitar propiedad privilegiada mientras el modo de archivo conserva los bits de permiso, lo que podría crear un archivo SetUID propiedad del usuario privilegiado. Comprueba la [semántica exacta de comodines de sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versión de rsync, las denegaciones posteriores, `nosuid` del sistema de archivos y la política MAC. Una regla coincidente es un indicio para revisar, no una prueba de escalada de privilegios exitosa.

### Exportación de reglas de filtros de paquetes ejecutada mediante sudo

Un permiso de root sin restricciones tanto para `iptables` como para `iptables-save` (o el par correspondiente `ip6tables`) merece revisar la escritura de archivos. La coincidencia `comment` acepta texto de reglas elegido por quien invoca el comando, mientras que `iptables-save -f` escribe el conjunto de reglas serializado en una ruta seleccionada.<sup>[[20]](#references)[[21]](#references)</sup> La utilidad de la carga depende de cómo el backend instalado serializa los comentarios y de si el archivo de destino acepta otras líneas en la exportación; `iptables-save` por sí solo no proporciona contenido arbitrario elegido por quien invoca el comando. Comprueba la identidad RunAs, los argumentos y las exclusiones exactos de sudo, la extensión de coincidencia disponible, el backend y los permisos del destino. Durante la enumeración, inspecciona el permiso sin modificar las reglas del firewall ni escribir un archivo.

### Directorio de registro Below privilegiado

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) afectó a las versiones de Below anteriores a la 0.9.0, que creaban el directorio `/var/log/below` con permisos de escritura mundial. Si un servicio o un comando permitido por sudo ejecuta como root una compilación afectada, un usuario que pueda escribir y recorrer un directorio de registro sin sticky bit quizá pueda reemplazar una entrada de registro por un enlace simbólico antes de que el proceso privilegiado la abra. Revisa el estado de los parches del paquete instalado, la ruta exacta de ejecución privilegiada, el acceso efectivo al directorio, el sticky bit y las ACL, y los metadatos de `/var/log/below/error_root.log`. Una ruta con permisos de escritura mundial o una regla de sudo por sí solas no demuestran la cadena completa. Un directorio sticky o un backport del proveedor cambian la evaluación. La enumeración pasiva solo debe inspeccionar metadatos; no necesita crear un enlace ni ejecutar el programa privilegiado.

### Recopilación privilegiada de paquetes de soporte a partir de entradas escribibles

Un script de perfil de soporte permitido por `sudo` puede leer rutas de registro fijas como root y copiar su contenido a un archivo de perfil. Revisa el script real para identificar las lecturas de archivos; luego, comprueba si quien invoca el comando puede reemplazar una ruta de origen o cualquier entrada de directorio padre por un enlace simbólico. Si la lectura privilegiada sigue ese enlace y quien invoca el comando puede leer el archivo de perfil resultante, se puede divulgar un archivo protegido. Deben darse todas estas condiciones: el permiso de sudo, una ruta de origen escribible, una lectura privilegiada y una salida legible. Un registro o nombre de perfil escribible por sí solos no bastan. Inspecciona los permisos efectivos y los metadatos de los enlaces sin reemplazar archivos ni generar un perfil durante la enumeración. La [guía de soporte de Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documenta su script de perfiles ejecutado como root y el archivo de salida, lo que ilustra por qué estos paquetes deben tener entradas restringidas y acceso limitado a la salida.

### Scripts de restauración de archivos Python ejecutados como root

Incluso una regla de sudo estrictamente limitada para un script de restauración de Python requiere revisar su entrada de archivo. Si quien invoca el comando puede seleccionar o reemplazar el archivo y el script lo extrae como root mediante `tarfile.extractall(filter="data")`, comprueba las actualizaciones de seguridad del intérprete antes de confiar en el filtro. CPython corrigió varias vulnerabilidades que permitían eludir el filtro con enlaces simbólicos y duros, incluida CVE-2025-4517, en las versiones 3.9.23, 3.10.18, 3.11.13, 3.12.11 y 3.13.4. Los backports de las distribuciones pueden corregir versiones anteriores, así que la versión mostrada del intérprete por sí sola no demuestra que el sistema esté afectado.<sup>[[16]](#references)[[17]](#references)</sup>

Para una revisión pasiva, lee el comando y el script exactos de sudo, sigue qué argumento selecciona el archivo y comprueba si el usuario actual puede escribir el archivo o el directorio que lo contiene. Confirma por separado el parche del proveedor instalado y el destino de extracción; `filter="data"` no hace seguros todos los archivos no confiables.<sup>[[16]](#references)[[17]](#references)</sup>

### Cargadores de modelos de machine learning ejecutados mediante sudo

Una regla de sudo que permite seleccionar un archivo `.pt`, `.pth` o `.ckpt` merece revisión cuando un script privilegiado lo pasa a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` u otro cargador basado en pickle. Comprueba la regla efectiva de RunAs, si quien invoca el comando puede crear o reemplazar el modelo seleccionado y el flujo real de argumentos a través de cualquier wrapper de shell hasta el helper de Python. La extensión `.pth` también se usa para archivos de configuración de Python site no relacionados, así que la extensión por sí sola no demuestra que se cargue un modelo. Un escaneo del archivo comprimido o un análisis estático de pickle no demuestran que la carga posterior sea segura; inspecciona el comportamiento de [`weights_only` dependiente de la versión](https://docs.pytorch.org/docs/stable/notes/serialization.html) del cargador y cualquier lista de permitidos. Consulta las [notas de ML pickle y Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). La enumeración pasiva nunca debe cargar ni descomprimir el modelo.

### Análisis de expresiones ejecutado mediante sudo sobre entradas almacenadas

Un script fijo de Python ejecutado como root mediante sudo todavía puede evaluar texto que un usuario con menos privilegios guarde en la base de datos de una aplicación. En TensorFlow, una llamada a `preprocess_input_exprs_arg_string(value, safe=False)` selecciona una ruta de `eval`; el [aviso de TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) describe el analizador inseguro y una corrección para quien lo invoca desde la línea de comandos. Una llamada explícita de la aplicación a `safe=False` requiere una revisión aparte, incluso si el programa de línea de comandos está parcheado. Comprueba la regla efectiva de sudo, quién puede modificar la fila de entrada exacta, si el filtrado o la puntuación permiten que esa fila llegue a la llamada y el comportamiento de la función instalada. Una versión de TensorFlow, un permiso de sudo o un archivo de modelo codificado de forma fija por sí solos no demuestran la cadena. Inspecciona pasivamente el script y el flujo de datos; no ejecutes el helper privilegiado ni envíes expresiones de prueba durante la enumeración.

### Configuración de needrestart permitida por sudo

`needrestart -c` carga un archivo de configuración Perl seleccionado por quien lo invoca y evalúa su contenido. Si `sudo -l` permite ejecutar `needrestart` como root con argumentos que admiten `-c`, y quien lo invoca puede seleccionar un archivo de configuración legible en una ubicación escribible, ese permiso puede conducir a la ejecución de código como root. Comprueba el usuario RunAs y la regla exacta de argumentos de sudo; una regla que permita solo una lista fija de argumentos puede bloquear esta vía. Esto es independiente de las vulnerabilidades de needrestart al analizar intérpretes: actualizar el paquete o desactivar `interpscan` no hace seguro un permiso sin restricciones para ejecutar `-c` como root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Imports de Python ejecutados mediante sudo como otra cuenta

Un punto de entrada fijo de Python todavía puede importar un módulo que quien invoca el comando pueda editar o reemplazar, incluso si sudo ejecuta el script como un usuario de servicio **que no es root**. Para un `from utils import status` literal, revisa `utils/__init__.py` y `utils/status.py` locales, además de los permisos del directorio del paquete. Confirma la ruta de importación del script, los argumentos exactos permitidos por sudo y si la acción pertinente llega a ese import antes de considerar el archivo escribible una vía de ejecución. Inspecciona los archivos y permisos sin importar ni ejecutar el script durante la enumeración.<sup>[[2]](#references)[[3]](#references)</sup>

Una regla exacta de sudo para `python3 /absolute/script.py` solo requiere que el script sea legible; no necesita ser ejecutable ni tener shebang. Revisa también los módulos locales **ausentes**: si el script importa un módulo cuyo archivo puede crearse en un directorio de scripts escribible por quien invoca el comando, Python puede cargarlo con la identidad RunAs. Confirma la regla efectiva de sudo, la [ruta de búsqueda de módulos](https://docs.python.org/3/library/sys_path_init.html) real del intérprete, si el módulo es integrado o está congelado y si se llega al import. Una regla de sudo directa para el script tiene requisitos distintos de bit de ejecución y shebang. Un wrapper aparte que añade tokens proporcionados por quien lo invoca después de `sudo -u account` también requiere revisar el flujo de argumentos: otro `-u` en esos tokens solo importa si la política de sudo invocada permite la identidad resultante. Las cadenas estáticas por sí solas no demuestran ninguna de las dos vías.

### Apache ejecutado mediante sudo con una configuración controlada por quien lo invoca

Si una regla de sudo permite invocar de forma privilegiada `apachectl`, `apache2ctl` o `httpd` con un archivo de configuración `-f` controlado por quien lo invoca, revisa los permisos de ese archivo y de su directorio padre. La directiva [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) de Apache acepta un nombre de módulo seguido del **nombre de archivo del módulo**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) también carga un archivo. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) pueden ampliar la configuración o exponer el contenido de archivos mediante errores. Un wrapper personalizado puede validar estas rutas, eliminar privilegios o restringir argumentos, así que una configuración escribible es un candidato para revisar, no una prueba de ejecución de código. Comprueba la canonicalización de las rutas, los enlaces simbólicos y el análisis de directivas antes de llegar a una conclusión.

### nginx ejecutado mediante sudo con una configuración controlada por quien lo invoca

Una regla de `nginx` con capacidad de root y sin restricciones puede permitir que [`-c` seleccione otra configuración](https://nginx.org/en/docs/switches.html). Revisa los argumentos exactos de sudo y las exclusiones, si quien invoca el comando puede proporcionar la configuración y si el master o los workers resultantes conservan acceso a rutas protegidas. Un `root` seleccionado junto con `autoindex` puede exponer archivos mediante un nuevo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) puede ofrecer una vía de escritura privilegiada, pero el módulo DAV no se compila de forma predeterminada y hay que comprobar su presencia, la accesibilidad del listener, los permisos de archivos y el comportamiento de los archivos temporales. La directiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) también puede apuntar a un archivo seleccionado; escribir registros en un archivo de configuración sensible, como `/etc/ld.so.preload`, requiere un escritor privilegiado efectivo y un registro controlable antes de convertirse en una vía de escalada. Que el ejecutable aparezca resaltado en `sudo -l` es un indicio para revisar, no una prueba de que alguna de estas vías funcione. La enumeración pasiva no debe iniciar ni reconfigurar nginx.

### Comparación de patrones en prompts de Bash privilegiados

Cuando un script de Bash permitido por sudo lee un valor de quien lo invoca y lo comprueba con `[[ "$expected" == $entered ]]`, Bash interpreta el operando derecho sin comillas como un patrón. Por tanto, un comodín puede satisfacer la comparación sin conocer el valor esperado. Poner el operando entre comillas (`[[ "$expected" == "$entered" ]]`) hace que la comparación trate la cadena como literal. Revisa la regla exacta de sudo, si se puede alcanzar el prompt y qué hace el script después de la comparación; la sintaxis por sí sola no demuestra que haya una vía explotable. Evita mostrar el valor esperado durante la enumeración. Consulta la [referencia de construcciones condicionales de Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers ejecutados mediante sudo que descargan y ejecutan un archivo

Un permiso de sudo sin restricciones para un helper personalizado con capacidad de root merece revisar el flujo de datos si acepta una URL seleccionada por quien lo invoca, guarda la respuesta en disco y luego ejecuta ese archivo con un intérprete o shell. [Sudoers permite argumentos arbitrarios cuando la entrada de comando no enumera ninguno](https://man7.org/linux/man-pages/man5/sudoers.5.html); una ruta de ejecutable fija no restringe lo que pueden seleccionar sus argumentos. Confirma la validación real de la URL, la ruta de salida, la rama de éxito y la ejecución posterior en el helper instalado. Un import de libcurl coincidente o una cadena imprimible por sí solos no demuestran esta cadena.

Incluso un nombre base de salida fijo puede reemplazarse entre la escritura y la ejecución cuando el helper usa una **ruta relativa en un directorio de trabajo controlado por quien lo invoca**. Cambiar el nombre o reemplazar un archivo propiedad de root depende del acceso de escritura y búsqueda al directorio y de las restricciones del sticky bit, no solo del modo del archivo; consulta [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Comprueba si el helper vuelve a abrir la ruta más tarde o utiliza el descriptor ya abierto, y si cambia a un directorio confiable antes de escribir. Inspecciona pasivamente la política de sudo, el helper y los metadatos del directorio; no invoques la descarga privilegiada ni provoques una carrera durante la enumeración.

Un helper de descarga ejecutado como root mediante sudo también puede exponer una inyección de **argumentos** cuando construye una cadena de comando Bash como `curl <caller input> -o <fixed output>`. Un filtro que rechaza espacios todavía deja disponible la [expansión de llaves de Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): los elementos separados por comas y sin comillas pueden convertirse en argumentos independientes de curl. Si la entrada llega a curl antes del `-o` fijo, una opción de salida proporcionada por quien lo invoca puede seleccionar el destino de la primera URL con la identidad del helper; [curl asocia las opciones de salida con las URL en orden](https://curl.se/docs/manpage.html#-o). Confirma el shell exacto, las comillas, la validación de entrada, la regla efectiva de sudo, el orden de los argumentos de curl y los esquemas de URL admitidos, y si quien invoca el comando controla los bytes descargados o puede leer el resultado. Un ejecutable empaquetado con PyInstaller puede contener lógica de aplicación Python, pero la marca del empaquetador o una cadena `curl` por sí solas no demuestran este flujo de datos. Revisa una copia local acotada sin conexión cuando esté autorizado; la enumeración habitual no debe ejecutar el helper ni descargar datos elegidos por un atacante.

Un script de shell ejecutado como root mediante sudo que llama a [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) solo elige un nombre no utilizado; **no crea el archivo**. Si el script crea después ese nombre en un directorio que otro usuario puede modificar, vuelve a abrirlo y añade su contenido a un destino protegido como `authorized_keys` de root, revisa la posible existencia de una carrera con el archivo temporal. Confirma la regla exacta de sudo, el propietario del directorio y del archivo, la secuencia de creación y reapertura, las protecciones del kernel y si la escritura privilegiada usa realmente bytes controlados por un atacante. Una cadena `mktemp -u` o un `/tmp` escribible por sí solos no demuestran la carrera. Inspecciona el script y los metadatos de la ruta sin ejecutarlo ni competir por el archivo temporal durante la enumeración.

## Notas defensivas

- Evita conceder intérpretes o editores interactivos mediante sudo.<sup>[[1]](#references)</sup>
- Prefiere wrappers fijos, propiedad de root, que realicen una sola acción administrativa limitada.<sup>[[1]](#references)[[2]](#references)</sup>
- Si no queda más remedio que usar un intérprete, restringe la ruta exacta del script e impide el uso de argumentos controlados por usuarios, imports escribibles, `PYTHONPATH` y la conservación insegura del entorno.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Si se requiere editar archivos, restringe la ruta exacta y considera usar `sudoedit` con versiones de sudo parcheadas y un tratamiento estricto del entorno.<sup>[[1]](#references)[[2]](#references)</sup>
- Revisa `SETENV`, `env_keep`, los directorios de trabajo escribibles, las rutas de módulos/importación escribibles, `NOEXEC`, `use_pty` y el registro, pero no los trates como un sandbox completo.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
