## Sudo से अनुमत interpreters

अगर `sudo -l` किसी user को root के रूप में interpreter चलाने की अनुमति देता है, तो इसे सीधे code execution के रूप में लें। Interpreters मनमाना code चलाने के लिए बनाए गए हैं, इसलिए `python3`, `perl`, `ruby`, `lua`, `node` या इसी तरह के binaries चलाने की अनुमति देने वाला नियम आमतौर पर root command execution के बराबर होता है—जब तक कि arguments पर सख्त सीमाएँ न हों और उनका सत्यापन न किया गया हो।<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

सामान्य समीक्षा प्रक्रिया: पहले user के privileges की सूची बनाएँ, फिर interpreter के `-c` option से Python statement चलाएँ।<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

अन्य interpreter उदाहरण नीचे दिए गए हैं; सूचीबद्ध interpreters inline-code execution या child-process APIs का दस्तावेज़ीकरण करते हैं।<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

सटीक path मायने रखता है। अगर sudo rule `/usr/bin/python3` की अनुमति देता है, तो validation के दौरान उसी सटीक path का उपयोग करें।<sup>[[2]](#references)</sup>

`/usr/bin/python*` जैसा sudo executable glob, Python 3 के लिए लिखी गई script को Python 2 से चलाने की अनुमति भी दे सकता है। अगर script caller के नियंत्रण वाले text के साथ `input()` तक पहुँचती है, तो [Python 2 उस text का expression के रूप में मूल्यांकन करता है](https://docs.python.org/2/library/functions.html#input); interpreter को स्पष्ट रूप से invoke करने पर script का shebang प्रभावी नहीं रहता। इसे execution path मानने से पहले, मेल खाने वाले installed binaries, प्रभावी RunAs और argument policy, denials, तथा उपलब्ध input की जाँच करें।

Root-capable sudo rule में तय script path होने से यह सीमित नहीं होता कि script क्या execute करती है। ऐसी Bash wrapper के लिए जिसे पढ़ा जा सकता हो, जाँचें कि क्या उसका पहला executable command `$1` जैसे unquoted positional parameter को **command word** के रूप में इस्तेमाल करता है, जबकि sudo caller द्वारा चुने गए arguments की अनुमति देता है। प्रभावी RunAs identity, password और argument policy, बाद के denials, तथा script की वास्तविक branch की पुष्टि करें; `NOEXEC`, तय सुरक्षित argument list, या command को validate करने वाली wrapper से नतीजा बदल सकता है। Enumeration के दौरान छोटी script को test command के साथ invoke करने के बजाय statically inspect करें।

`dotnet` के लिए unrestricted root-capable sudo rule की भी interpreter के लिहाज़ से समीक्षा करें। .NET SDK installed होने पर, [`dotnet fsi` F# code को interactive तरीके से या script से चलाता है](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), और [`dotnet run` source से project execute करता है](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)। पहले प्रभावी RunAs identity और सटीक argument policy की पुष्टि करें: किसी खास सुरक्षित subcommand या trusted application तक सीमित rule एक अलग grant है, और केवल runtime वाली installation में SDK commands मौजूद न हों। Executable का नाम समीक्षा का संकेत भर है, code execution का प्रमाण नहीं।

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## sudo द्वारा अनुमति प्राप्त editors

यदि `sudo -l` किसी user को root के रूप में interactive editor चलाने की अनुमति देता है, तो इसे harmless file-editing permission नहीं, बल्कि command-execution surface मानें। Editors अक्सर shell commands चला सकते हैं, मनमानी files पढ़ या लिख सकते हैं, या editor के भीतर से external helpers चला सकते हैं।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

समीक्षा का सामान्य तरीका: पहले user के privileges सूचीबद्ध करें, फिर sudo के अंतर्गत प्रत्येक अनुमत editor या pager चलाएँ।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano command execution

जब `nano` को sudo के माध्यम से चलाने की अनुमति हो, तो editor interface से command execution तक पहुँचा जा सकता है।<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

फिर nano command prompt में `id` या `/bin/sh` जैसी कोई कमांड दें।<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

यदि किसी interactive shell में उपयोग करने योग्य terminal streams न हों, तो यह redirection form उसके standard output और error को descriptor 0 पर मैप करता है।<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

सटीक key sequence nano के version और build options के अनुसार बदल सकता है, लेकिन सुरक्षा समस्या वही है: editor root के रूप में चल रहा है और external commands चला सकता है।<sup>[[1]](#references)[[12]](#references)</sup>

### अन्य आम editor escapes

Vim-style editors आमतौर पर `:!` के ज़रिए command execution की सुविधा देते हैं।<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` जैसे pagers shell execution को भी उजागर कर सकते हैं।<sup>[[14]](#references)</sup>

`apport-cli` को root के रूप में चलाने की अनुमति देने वाले sudo rule की भी pager के लिए समीक्षा करें। Apport के प्रभावित versions crash report को `less` में ऐसे terminal size के साथ खोल सकते थे जिसे attacker समायोजित कर सकता था; विशेष sudo और pager conditions पूरी होने पर pager root shell दे सकता था। केवल version को vulnerable मानने से पहले प्रभावी sudo rule, pager configuration और distribution package fix की जाँच करें। Passive enumeration के दौरान crash उत्पन्न किए बिना या privileged report खोले बिना package और policy metadata पढ़ें। [Ubuntu's CVE record](https://ubuntu.com/security/CVE-2023-1326) में release-specific fixed package versions सूचीबद्ध हैं, जिनमें backported fixes भी शामिल हैं।

```text
!/bin/sh
```

## अन्य sudo और doas नियमों के जोखिम

`sudo -l`, `sudo -V` और लागू होने वाली किसी भी `doas` policy से शुरुआत करें। अनुमत command, RunAs user, arguments, environment और defaults को एक साथ पढ़ें। गैर-root service account के रूप में चलाने की अनुमति भी उस account की files या root तक पहुँचने का रास्ता उजागर कर सकती है।

sudo से चलाने की अनुमति वाली कोई तय Python script, अपने RunAs identity के तहत shell command चला सकती है, यदि interactive, caller-controlled input को [`os.system()`](https://docs.python.org/3/library/os.html#os.system) में जोड़ दिया जाए। Shell punctuation की denylist सुरक्षा साबित करने के लिए पर्याप्त नहीं है: [shell `$(...)` command substitution को भी पहचानता है](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)। पुष्टि करें कि अनुमत arguments input branch तक पहुँचते हैं, input सुरक्षित validation के बिना shell command तक पहुँचता है, और प्रभावी sudo policy इच्छित RunAs user की अनुमति देती है। केवल script path या `os.system()` call मिलना जाँच का संकेत है; privileged script चलाए बिना source देखें।

`chattr` के लिए प्रभावी root sudo grant immutable (`i`) file attribute हटा सकता है, लेकिन इससे अपने-आप write access या नई identity नहीं मिलती। [`chattr` manual](https://man7.org/linux/man-pages/man1/chattr.1.html) के अनुसार, यह attribute बदलाव रोकता है और इसे केवल root या `CAP_LINUX_IMMUTABLE` वाला process बदल सकता है। sudo argument policy और filesystem support जाँचें; फिर अलग से पुष्टि करें कि attribute हटने के बाद caller file लिख सकता है और उच्च-identity वाला consumer उसका उपयोग करता है। उदाहरण के लिए, login shell बदलने के लिए target account के स्वीकार्य credentials और उस shell के जरिए वास्तविक login की भी आवश्यकता होती है। Enumeration के दौरान policy, file attributes और permissions देखें, लेकिन उन्हें न बदलें।

अगर sudo password और one-time code, दोनों माँगता है, तो इन शर्तों को command grant से अलग रखें। पढ़ी जा सकने वाली `.google_authenticator` file में संवेदनशील seed material हो सकता है, जबकि पुराना application या database password hash केवल मौजूदा account password का संभावित उम्मीदवार है; इनमें से कोई भी यह साबित नहीं करता कि प्रभावी PAM configuration दूसरा factor स्वीकार करती है। अनुमति मिलने के बाद सटीक RunAs और arguments देखें: RubyGems `gem` के लिए unrestricted root grant उसका editor command उजागर कर सकता है ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), लेकिन restricted grant या विफल authentication ऐसा नहीं करता। Passive enumeration में seed दिखाए बिना, password recover किए बिना, code बनाए बिना या privileged command चलाए बिना paths और policy की रिपोर्ट करें।

Chef के `knife` के लिए unrestricted root-capable sudo grant की interpreter स्तर पर जाँच होनी चाहिए: [Chef के दस्तावेज़ बताते हैं कि `knife exec -E` स्थानीय रूप से Ruby string evaluate करता है](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). पुष्टि करें कि प्रभावी sudo rule `exec` subcommand और caller-supplied `-E` argument, इच्छित RunAs identity, तथा लागू command denials या fixed arguments की अनुमति देता है। Installed binary या अन्य subcommands तक सीमित rule केवल जाँच का संकेत है। Passive enumeration में `knife` न चलाएँ; केवल rule की रिपोर्ट करें।

Interactive `msfconsole` के लिए सटीक root-capable sudo grant भी उतना ही संवेदनशील है: [GTFOBins इसके `irb` console का उल्लेख करता है](https://gtfobins.org/gtfobins/msfconsole/), जो sudo identity विरासत में ले सकता है। प्रभावी RunAs user, अनुमत argument list, command denials, `NOEXEC` या अन्य restrictions, installed console का व्यवहार और caller द्वारा interactive input देने की क्षमता की पुष्टि करें। केवल path highlight जाँच का संकेत है; passive enumeration में console launch न करें।

FreeBSD पर, root के रूप में केवल `pkg update` और `pkg install *` तक सीमित sudo rule में भी repository trust की जाँच करें। देखें कि caller `/etc/hosts` लिख सकता है या नहीं और प्रभावी enabled repository configuration में `signature_type: none` के साथ HTTP hostname है या नहीं। [FreeBSD का `pkg.conf` manual](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) कहता है कि `none` signature checks बंद करता है; केवल `pkg+http` होने से यह साबित नहीं होता। Package में install scripts हो सकती हैं ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), इसलिए repository endpoint पर वास्तविक नियंत्रण और package चुनने की क्षमता रखने वाला caller root boundary पार कर सकता है। यह निष्कर्ष निकालने से पहले repository overrides, SRV/mirror resolution, प्रभावी sudo arguments, package selection और script execution की पुष्टि करें। Enumeration के दौरान नाम redirect किए बिना या `pkg` चलाए बिना policy और छोटी local configuration files देखें।

`apt-get update` और `apt-get upgrade` के लिए root-capable sudo grant में repository trust की भी जाँच करें, यदि sudo caller-controlled `http_proxy` को सुरक्षित रखता है। देखें कि प्रभावी APT proxy configuration वास्तव में उस variable का उपयोग करता है या नहीं और किन enabled repository requests को यह प्रभावित कर सकता है; केवल proxy होने से trusted signing key वाले archive के packages बदले नहीं जा सकते। [APT का HTTP transport manual](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) proxy precedence बताता है, और [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) signature checks, insecure-repository overrides और unauthenticated packages की पुष्टि के बारे में बताता है। सटीक sudo RunAs और arguments, repository authentication policy, किसी आवश्यक interactive स्वीकृति, और यह पुष्टि करें कि चुना गया upgrade package scripts को root के रूप में चलाता है या नहीं। Policy और local configuration को passive तरीके से देखें; enumeration के दौरान package traffic redirect न करें या upgrade न चलाएँ।

` snap install` के लिए root-capable sudo rule package से code तक की boundary बन सकता है, अगर इसके arguments caller को local snap चुनने और permissive install mode इस्तेमाल करने देते हैं। [Snap के दस्तावेज़](https://snapcraft.io/docs/explanation/snap-development/install-modes/) बताते हैं कि `--dangerous` local-snap assertion checks छोड़ता है और `--devmode` confinement ढीला करता है; [initial installation पर install hook चल सकता है](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Protected host files तक पहुँच का दावा करने से पहले सटीक sudo argument/RunAs policy, snap file पर नियंत्रण रखने वाला पक्ष, installed snapd द्वारा इन modes की स्वीकृति, और hook की प्रभावी identity तथा confinement जाँचें। केवल `snap` binary या wildcard जैसा दिखने वाला rule इस chain को साबित नहीं करता। Passive enumeration में package install न करें और उसका hook न चलाएँ।

किसी **non-root** account के custom credential-reading binary के लिए सटीक sudo grant हो, तो पहले उसे चलाए बिना binary और उसकी file permissions देखें। Embedded password gate केवल wide characters के रूप में दिख सकता है; [GNU `strings` 16-bit little-endian extraction के बारे में बताता है](https://sourceware.org/binutils/docs/binutils/strings.html)। दिखाई देने वाली string यह साबित नहीं करती कि वही स्वीकार्य password है या success branch वर्तमान credential उजागर करती है। Binary का व्यवहार, protected data तक target account की पहुँच, credential की वैधता और बाद में होने वाला कोई account या group transition अलग-अलग सत्यापित करें। यदि वह account `docker` group में है, तो host-root access मानने से पहले socket access और daemon की rootful या rootless identity जाँचें; [Docker इस group के root-level प्रभावों का दस्तावेज़ देता है](https://docs.docker.com/engine/install/linux-postinstall/). सामान्य enumeration में binary चलाए या उसकी strings dump किए बिना sudo rule और group membership की रिपोर्ट करें।

किसी application की maintenance scripts के लिए wildcard sudo rule में केवल script path से आगे की जाँच करें। देखें कि अनुमत script unrestricted arguments स्वीकार करती है या ऐसे settings पढ़ती है जिन्हें कम privilege वाला application account लिख सकता है; फिर उन values को shell commands या subprocess environment तक trace करें। उदाहरण के लिए, ZoneMinder की [`zmupdate.pl` `mysqldump` command बनाकर उसे `qx` के जरिए चलाती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), जबकि [`zmdc.pl` daemon शुरू करने से पहले `ZM_LD_PRELOAD` setting को `LD_PRELOAD` में copy करती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)। अगर संबंधित input नियंत्रित किया जा सकता है और installed version में उस code तक पहुँचता है, तो इनमें से किसी script को root के रूप में चलाने वाला sudo rule trust boundary पार कर सकता है। प्रभावी sudo rule, application configuration पर लिखने के अधिकार और script source देखें; wildcard या setting अकेले execution का प्रमाण नहीं हैं।

- `SETENV`, `env_keep`, `secure_path` और `LD_PRELOAD` किसी अन्यथा सीमित command को import, library या PATH hijack में बदल सकते हैं। [Environment-variable guide](../linux-basics/linux-environment-variables.md) और [SUID/linker abuse](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md) देखें।

Shell wrapper के लिए सटीक root-capable `SETENV` grant हो तो एक-hop समीक्षा भी करें, यदि wrapper तय Python script को literal import के साथ चलाता है। `secure_path` shell command lookup सीमित करता है, Python की [`PYTHONPATH` module search](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) को नहीं; [`-E` और `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) Python को उस environment variable को अनदेखा करने देते हैं। इसे code execution मानने से पहले प्रभावी sudo tags और denials, wrapper branch, interpreter options, import resolution और caller द्वारा लिखी जा सकने वाली search directory की पुष्टि करें। छोटी scripts को static रूप से देखें; privileged wrapper न चलाएँ।

सटीक root-capable `neofetch ""` sudo grant, तब भी shell configuration लोड कर सकता है जब लागू sudo defaults caller-controlled `XDG_CONFIG_HOME` को सुरक्षित रखते हों। [Neofetch का configuration loader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) उस directory के भीतर `neofetch/config.conf` या `neofetch/config` को source करता है; खाली argument list इस lookup को नहीं रोकती। Installed loader, प्रभावी RunAs और argument policy, command denials, इस command के लिए sudo द्वारा चुने गए variable को वास्तव में सुरक्षित रखने की स्थिति, और caller के readable configuration path पर नियंत्रण की पुष्टि करें। केवल सुरक्षित रखा गया variable या installed Neofetch जाँच का संकेत है। Privileged command चलाए या configuration contents दिखाए बिना policy और file metadata देखें; [sudoers environment handling](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।

Unrestricted root-capable `facter` sudo rule में custom-fact की अलग समीक्षा होनी चाहिए। [Puppet के दस्तावेज़](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) बताते हैं कि `--custom-dir` चुनी हुई directory से Ruby fact files लोड करता है। देखें कि सटीक sudo rule इस option की अनुमति देता है या नहीं, installed Facter इसे स्वीकार करता है या नहीं, और caller उस directory को नियंत्रित करता है या नहीं। Fixed-argument grant, स्पष्ट command denial या disabled custom facts नतीजा बदल सकते हैं। Passive enumeration में Facter चलाए या fact contents पढ़े बिना policy candidate की रिपोर्ट करें।

`SETENV` वाले root-capable sudo script grant के लिए `find` जैसे bare command names और sudo policy तथा script initialization के बाद प्रभावी `PATH` देखें। Source की गई Bash file `enable -n [` भी चला सकती है: [इसके बाद Bash बाहरी `[` के लिए `PATH` खोजता है](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html), जिसका उपयोग script बाद में करती है। Privileged execution मानने से पहले लागू [sudoers environment और `secure_path` rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), किसी `NOSETENV`/`NOEXEC` या denial entries, script तथा sourced-file flow, और caller द्वारा नियंत्रित executable search directory की पुष्टि करें। Bare command वाली readable script जाँच का संकेत है, privileged execution का प्रमाण नहीं; sudo rule चलाए बिना उसे देखें।
- तय URL से `curl` द्वारा file fetch करने वाली privileged script, फिर भी caller द्वारा चुना गया response स्वीकार कर सकती है, यदि लागू sudo rule `http_proxy` सुरक्षित रखता है और request उसी proxy से भेजी जाती है। अगर script फिर response को ऐसे XML parser को देती है जो external entities resolve करता है, तो hostile response privileged process द्वारा पढ़ी जा सकने वाली files उजागर कर सकता है। सटीक sudo environment policy, `no_proxy` exclusions, requested URL, parser configuration और output destination जाँचें; proxy variable या XML parser अकेले vulnerability नहीं हैं। [curl proxy environment documentation](https://everything.curl.dev/usingcurl/proxies/env.html) variable behavior बताता है। Passive enumeration में network requests न करें और hostile XML parse न करें।
- Caller-influenced data से PostScript file बनाने और फिर `ps2pdf -dNOSAFER` चलाने वाली root-capable sudo script के input flow की अलग समीक्षा करें। Ghostscript के अनुसार यह flag `.setsafe` तक SAFER बंद करता है, जिससे process की OS permissions के तहत PostScript file operations संभव होते हैं। Caller argument से बनाया गया SQL query attacker-controlled rows को PostScript template में पहुँचा सकता है, लेकिन query string या `ps2pdf` invocation अकेले यह साबित नहीं करते कि data executable PostScript syntax तक पहुँचता है। Privileged conversion चलाए बिना प्रभावी sudo rule, input से template तक का सटीक रास्ता, escaping, installed Ghostscript behavior और document interpret होने से पहले SAFER दोबारा चालू होता है या नहीं—इनकी पुष्टि करें। [Ghostscript का `-dNOSAFER` documentation](https://ghostscript.readthedocs.io/en/master/Use.html) देखें।
- Shell script चलाने वाले sudo rule के लिए सुरक्षित रखे गए variables की तुलना script से करें। `if $CHECK_CONTENT; then` जैसा construct expanded value को command की तरह चलाता है, इसलिए `CHECK_CONTENT` सुरक्षित रखने से command execution संभव हो सकता है, भले script path और arguments तय हों। उस खास rule के लिए जाँचना होगा कि branch तक पहुँचा जा सकता है और environment वास्तव में सुरक्षित रखा जाता है या नहीं।<sup>[[2]](#references)[[22]](#references)</sup>
- Sudo से चलने वाली Python script किसी writable directory या cached `.pyc` file से code import कर सकती है। [Privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md) cache वाले मामले का विवरण देता है।
- Root के रूप में चलाने की अनुमति वाली तय Python script भी interactive debugger उजागर कर सकती है। `pdb.set_trace()` या `pdb.post_mortem()` जैसे calls, जब caller breakpoint या exception handler तक पहुँच सकता हो **और debugger के input stream को नियंत्रित कर सकता हो**, तो debug हो रहे process के context में Python statements चलाने देते हैं। सटीक sudo RunAs rule, authentication और branch conditions, exception तक पहुँचने की संभावना, terminal/input ownership और debugger उसी privileged process में चलता है या नहीं—इनकी जाँच करें। किसी socket request से exception trigger होना, अपने-आप दूसरे terminal से जुड़े debugger तक पहुँच नहीं देता। [Python debugger के statement evaluation और post-mortem mode का दस्तावेज़ देता है](https://docs.python.org/3/library/pdb.html); enumeration के दौरान privileged handler trigger करने के बजाय script को static रूप से देखें।
- Sudo से चलने वाली तय Python script database या Unix socket से profile field पढ़कर उसे उस string में जोड़ सकती है जो बाद में `str.format()` का **format string** बनती है। [Replacement fields attributes और mapping keys का अनुसरण कर सकते हैं](https://docs.python.org/3/library/string.html#format-string-syntax), इसलिए attacker-controlled field, `format()` को दिए गए objects की जाँच कर सकता है और उनसे उपलब्ध data उजागर कर सकता है—यदि result print हो या caller द्वारा पढ़ी जा सकने वाली जगह पर store हो। प्रभावी sudo RunAs identity, उस खास record को लिखने का अधिकार, format string तक data flow, दिए गए objects और output की visibility जाँचें। इससे अपने-आप code execution नहीं होता; trusted literal format string में attacker-controlled *values* होना अलग स्थिति है। उजागर secret से OS account transition तभी संभव है जब वह account उसे स्वीकार करे। Privileged operation चलाए बिना script और socket permissions देखें।
- Root-capable Python wrapper caller-selected URL को GitPython के `Repo.clone_from` में दे सकता है। यदि wrapper Git का `protocol.ext.allow=always` भी सक्षम करता है, तो `ext::` remote बाहरी helper चला सकता है। सटीक sudo arguments, URL का स्रोत, GitPython package version और vendor patch status, तथा wrapper unsafe protocols को स्पष्ट रूप से सक्षम करता है या नहीं—इनकी जाँच करें। GitPython ने 3.1.30 में [unsafe-protocol का default guard](https://github.com/gitpython-developers/GitPython/commit/2625ed9) जोड़ा; `git` executable का version अलग बात है। Passive review में केवल rule और सीमित source पढ़ें; clone न चलाएँ।
- Repository clone करने वाले CLI को दूसरे user के रूप में चलाने का sudo grant shell-string injection का अलग रास्ता उजागर कर सकता है। देखें कि caller-selected repository argument, बिना सुरक्षित argument separation के, Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) या किसी दूसरे shell-command builder तक पहुँचता है या नहीं; Node का `exec` command string shell को देता है। सटीक RunAs user, अनुमत subcommands और arguments, installed wrapper code तथा input validation की पुष्टि करें। Repository tool का नाम या unrestricted sudo rule अकेले command injection साबित नहीं करता। Enumeration के दौरान privileged clone चलाए बिना wrapper देखें।
- Custom root-owned wrapper सुरक्षित दिख सकता है क्योंकि उसके binaries और scripts writable नहीं हैं, फिर भी privileged action चलाने का उसका निर्णय ऐसे flag, local API value या service state पर निर्भर हो सकता है जिसे unprivileged user बदल सकता है। हर gate को उसके input और authorization checks तक trace करें। Enumeration के दौरान operational state बदले बिना configuration और permissions देखें; wrapper में `systemd-run` call तभी प्रासंगिक है जब gate को प्रभावित किया जा सके।
- Root के रूप में sudo से चलाया जाने वाला backup client caller-selected configuration file स्वीकार कर सकता है (उदाहरण के लिए, `npbackup-cli -c`)। सटीक RunAs user और अनुमत arguments देखें; फिर जाँचें कि caller configuration path, backup source paths और repository या read/restore options नियंत्रित कर सकता है या नहीं। Readable config में मौजूद encrypted repository secret client के उपयोग के लिए पर्याप्त हो सकता है, लेकिन rule अकेले repository access या root-file disclosure साबित नहीं करता। Backup चलाए या उसका content dump किए बिना authorization की पुष्टि करें।
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) में `--password-command` है, जो repository password पाने के लिए एक program चलाता है। यदि sudo rule कम privilege वाले user को caller-chosen password command और password माँगने वाले subcommand के साथ root के रूप में restic चलाने देता है, तो वह helper root के रूप में चल सकता है। सटीक sudo arguments और exclusions देखें; केवल इस स्थिति की जाँच के लिए helper या backup command न चलाएँ।
- Privileged `restic backup` grant, file-read boundary भी पार कर सकता है, यदि sudo argument pattern caller को source और ऐसा repository दोनों चुनने देता है जिसे वह बाद में पढ़ और decrypt कर सकता है। [Sudoers argument wildcards whitespace और slashes से match कर सकते हैं](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), इसलिए यह मानने के बजाय कि fixed repository prefix source को सीमित करता है, trailing wildcards देखें। [Restic local और remote repositories में backup कर सकता है](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), लेकिन local repository में हाल में लिखे गए root-only objects हो सकते हैं; disclosure मानने से पहले प्रभावी sudo policy, backend access, repository password और बने objects की permissions की पुष्टि करें। Backed-up SSH key तभी access देती है जब destination account उसे स्वीकार करता हो। Passive review के दौरान जाँच के लिए backup न चलाएँ।

- Root-capable `clamscan --debug` rule read boundary पार कर सकता है, यदि कम privilege वाला user DMG image दे सकता है और installed parser [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) से प्रभावित है, जिससे debug output के जरिए file contents उजागर हो सकते हैं। सटीक अनुमत arguments और scan path, input पर नियंत्रण, प्रभावी RunAs account, engine patch/backport और output caller को दिखता है या नहीं—इनकी पुष्टि करें। अगर व्यापक rule `--file-list`/`-f` की अनुमति देता है, तो उस file-list behavior की अलग समीक्षा करें; `--debug <scan-path>` तक सीमित policy इसे अनुमति नहीं देती। Enumeration के दौरान crafted file scan या protected output print किए बिना policy और package metadata देखें।
- Caller-selected encrypted disk image खोलने वाला root-capable sudo rule और उससे बने mapper को mount करने वाला दूसरा rule, caller-controlled files को host के mount namespace में ला सकता है। दोनों प्रभावी rules और arguments, image और mapper name पर नियंत्रण, वास्तविक mount target, और परिणामी file owner तथा mode की पुष्टि करें। Set-user-ID transition के लिए executable तक access, उसे मानने वाले mount options (`nosuid` इसे रोकता है), और लागू process या MAC policy भी चाहिए; image खोलना या mount करना अकेले जाँच का संकेत है। मौजूदा backup के जरिए अलग रास्ते के लिए उसमें मौजूद वास्तविक key और उपयोगी readable secret चाहिए। Passive enumeration में image खोले या mount किए बिना policy और paths देखें। [cryptsetup manual](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) और [mount options](https://man7.org/linux/man-pages/man8/mount.8.html) देखें।
- Shell या Python script के लिए root-capable sudo rule में working directory की जाँच करें, यदि script fixed directory में जाने से पहले `./helper` चलाती है। `subprocess.run` को दी गई Python list, जैसे `['./helper']`, में भी caller-selected working directory का वही व्यवहार हो सकता है। Caller writable directory चुनकर वहाँ उसी relative name वाला executable रख सकता है; script में कहीं और दिया गया absolute path इस call को सुरक्षित नहीं करता। इसे code execution मानने से पहले प्रभावी rule, `runchdir` या directory बदलने वाली अन्य policy, script flow और branch reachability, writable तथा executable directory, और mount/`NOEXEC` restrictions की पुष्टि करें। Script unreadable हो तो अधिकृत तरीके से source देखे जाने तक व्यवहार अज्ञात रहेगा। Helper चलाने के बजाय scripts को static रूप से देखें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) working-directory policy का विवरण देता है।
- Root-capable fixed Python validator caller-selected data file evaluate कर सकता है। [Python का `eval()` documentation untrusted input से बचने की चेतावनी देता है](https://docs.python.org/3/library/functions.html#eval): अगर बाकी expression `eval` तक पहुँचता है, तो input suffix check, arithmetic prefix या validation branch sandbox नहीं बनते। इसे execution path कहने से पहले प्रभावी sudo rule, exact file चुनने और नियंत्रित करने की caller की क्षमता, parser की branch conditions तथा expression निर्माण, और privileged process identity की पुष्टि करें। Readable script में `eval` होना अकेले जाँच का संकेत है; enumeration के दौरान validator चलाए या test expression दिए बिना source और file permissions देखें।
- Root-capable sudo Ruby wrapper जो relative YAML filename पढ़ता है, जैसे `YAML.load(File.read("dependencies.yml"))`, caller की working directory से input ले सकता है, जब तक wrapper या sudo policy directory तय न करे। सटीक अनुमत arguments, directory और file permissions, तथा installed Psych behavior जाँचें: पुराने `YAML.load` implementations arbitrary Ruby objects deserialize कर सकते थे, जबकि नए releases default रूप से classes सीमित करते हैं। Static call site जाँच का संकेत है; पुष्टि करें कि file वास्तव में caller-writable directory से आती है और installed loader खतरनाक classes स्वीकार करता है। Untrusted input के लिए स्पष्ट न्यूनतम class allowlist वाला `safe_load` बेहतर है। [Ruby 3.0 Psych documentation](https://docs.ruby-lang.org/en/3.0/Psych.html) और [Ruby 3.1 Psych documentation](https://ruby-doc.org/core-3.1.2/Psych.html) देखें।

- `sudo go run /absolute/file.go` के लिए सटीक root-capable grant में working-directory की जाँच करें, यदि Go source relative WASM file पढ़ता है और उसका परिणाम देखने के बाद relative shell script चला सकता है। प्रभावी RunAs, command arguments और denials, caller-writable current directory, WASM से branch तक data flow और वह branch helper चलाती है या नहीं—इनकी पुष्टि करें। तय sudo `runchdir`, `os.Chdir` या [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) lookup location बदल सकते हैं। Static रूप से साथ दिखने वाली चीज़ें केवल संभावित संकेत हैं; Go, WASM या helper चलाए बिना source देखें।
- `sudoedit` और argument wildcards में exact version तथा rule जाँचें; [checklist](linux-privilege-escalation-checklist.md) में sudoedit file-edit issue शामिल है। Wildcard path पर cross-user `sudoedit` grant हो, तो प्रभावी `sudoedit_follow` या `FOLLOW` setting, `sudoedit_checkdir`, resolved target और हर parent entry को बदल सकने वाले user की जाँच करें। पहली setting symlink follow करने दे सकती है, जबकि दूसरी को disable करने से writable-directory checks हट जाते हैं; इनमें से कोई भी setting अकेले दूसरे user की file में write साबित नहीं करती। निष्कर्ष निकालने से पहले installed sudo policy और exact matched arguments की पुष्टि करें। [sudoers option definitions](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।
- Sudoers command rule में argument wildcard whitespace के साथ-साथ path characters से भी match कर सकता है। Read-capable command के लिए `/restricted/*` जैसा argument, matching prefix के बाद अतिरिक्त file argument भी स्वीकार कर सकता है। Exact RunAs user, command path, argument pattern और बाद के denials देखें; file read दिखने से command execution साबित नहीं होता। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) argument globs और command-path globs के बीच अंतर बताता है।
- Path जैसा दिखने वाला argument glob `../` से भी match हो सकता है। उदाहरण के लिए, root-capable `node /opt/scripts/*.js` rule caller-controlled JavaScript file को `/opt/scripts` के बाहर चलाने दे सकता है, यदि दिया गया pathname फिर भी `/opt/scripts/` से शुरू होता है और parent-directory segments के जरिए resolve होता है। यह **argument** glob है; Node executable के command-path glob में slash matching के नियम अलग हैं। Code execution का निष्कर्ष निकालने से पहले प्रभावी rule, बाद के denials, pathname resolution, target file पर नियंत्रण, और sudoers regular-expression या digest restrictions जाँचें। [sudoers wildcard rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) और [Node command-line documentation](https://nodejs.org/api/cli.html) देखें।
- Archivers और अन्य utility programs में execution hooks हो सकते हैं। यह मानने के बजाय कि केवल shells या interpreters commands चलाते हैं, सटीक अनुमत arguments को [GTFOBins](https://gtfobins.github.io/) से जाँचें।
- Unrestricted root-capable `qpdf` rule PDF attachments के जरिए privileged file उजागर कर सकता है: qpdf 10.2 और बाद के versions output PDF के साथ `--empty` और `--add-attachment file ... --` support करते हैं। यदि privileged process चुनी गई source पढ़ सकता है और PDF को caller-accessible path पर लिख सकता है, तो output में source bytes हो सकते हैं। File disclosure की संभावना का निष्कर्ष निकालने से पहले प्रभावी sudo arguments और exclusions, qpdf version, source access तथा output path देखें। Root SSH key पढ़ना तभी login के लिए उपयोगी है जब key valid हो और root SSH authentication की अनुमति हो। [qpdf attachment options](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments) देखें।
- Sudo timestamp का दोबारा उपयोग cache policy, owning user, terminal/session और permissions पर निर्भर करता है। [Privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) में जाँचें दी गई हैं।
- `doas` के अपने rules और configuration हैं। [doas section](../linux-basics/linux-privilege-escalation/README.md#doas) में बताए अनुसार अनुमत commands और writable configuration paths जाँचें।

### Sudo से चलने वाले build और package tools

Foundry के `forge` के लिए unrestricted sudo grant तब भी मायने रख सकता है जब RunAs identity कोई दूसरा non-root user हो। `--use` जैसे compiler options local executable चुन सकते हैं और `forge flatten -o` output file चुनता है। Grant को exploitable मानने से पहले installed Forge version, सटीक sudo arguments, accessible project और compiler paths, output permissions और प्रभावी environment जाँचें। `PATH` से मिला relative helper executable version और environment पर निर्भर रास्ता है; इसे हर Forge build की विशेषता न मानें।<sup>[[23]](#references)[[24]](#references)</sup>

Unrestricted root-capable `pacman` grant केवल package queries तक सीमित नहीं है: `-U` local package स्वीकार करता है, packages में install scripts हो सकती हैं और `--hookdir` दूसरी hook directory चुनता है। परीक्षण से पहले प्रभावी sudo rule, argument restrictions और exclusions देखें; passive enumeration के लिए package install करने या hook चलाने की ज़रूरत नहीं है।<sup>[[25]](#references)[[26]](#references)</sup>

तय sudo shell wrapper, named npm dependency install करके Node application शुरू भी कर सकता है। उसका सटीक RunAs rule, package पहले से installed है या नहीं, प्रभावी `HOME` और npm `userconfig`, project configuration या command-line overrides, तथा कम privilege वाला user उस नाम के लिए registry या लौटाए जाने वाले package को नियंत्रित करता है या नहीं—इनकी जाँच करें। [npm per-user और per-project `.npmrc` lookup का दस्तावेज़ देता है](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo का `HOME` व्यवहार installed policy और distribution पर निर्भर है, इसलिए privileged npm process user की writable `.npmrc` पढ़ भी सकती है और नहीं भी। यदि privileged application newly installed package import करती है, तो उसका module code उसी application identity के तहत चल सकता है। Install-time scripts अलग रास्ता हैं, जो version और configuration पर निर्भर करते हैं; [npm उनके lifecycle और user handling का दस्तावेज़ देता है](https://docs.npmjs.com/cli/v6/using-npm/scripts/). `.npmrc` path या `npm install` line अकेले जाँच का संकेत है। Passive enumeration में install या application शुरू किए बिना rule, छोटा wrapper, configuration paths और package provenance देखें।

Root-capable `pip` या `pip3 download` grant में भी package-build की जाँच करें, यदि उसके arguments caller को untrusted source distribution चुनने देते हैं—भले URL pattern local service और `.tar.gz` suffix तक सीमित हो। `pip download` archive URLs स्वीकार करता है और package metadata resolve करता है; sdist तैयार करने पर archive केवल save होने से पहले उसका build backend या legacy `setup.py` code चल सकता है। सटीक sudo RunAs और argument rule, caller चुने गए archive को publish या replace कर सकता है या नहीं, और pip का वह version metadata वास्तव में तैयार करता है या नहीं—इनकी पुष्टि करें। तय trusted archive या wheel से यह रास्ता साबित नहीं होता। Passive enumeration में untrusted package fetch या build न करें। pip का [download command](https://pip.pypa.io/en/stable/cli/pip_download/), [build-system interface](https://pip.pypa.io/en/stable/reference/build-system/) और [secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/) देखें।

Caller-selected local project path के साथ `pip install` की अनुमति देने वाला sudo rule build boundary का अधिक सीधा मामला है। [pip local project directories स्वीकार करता है](https://pip.pypa.io/en/stable/topics/local-project-installs/) और उनका build system चलाता है; [build backend project-controlled build hooks चलाता है](https://pip.pypa.io/en/stable/reference/build-system/). Rule को privileged code execution मानने से पहले प्रभावी RunAs identity, सटीक argument restrictions और denials, चुने हुए project पर नियंत्रण, और installed pip/backend behavior की पुष्टि करें। तय trusted project या caller-selected paths को रोकने वाला rule यह रास्ता साबित नहीं करता। Passive enumeration में package install किए बिना rule और project metadata देखें।

Unrestricted root-capable `easy_install` grant भी legacy package-build की इसी तरह की जाँच का संकेत है। [Setuptools का documentation](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) बताता है कि Easy Install local project directory स्वीकार करता है और source distributions बनाता है; caller-controlled project, sudo identity के तहत उस build के दौरान अपना `setup.py` चला सकता है। प्रभावी RunAs account, सटीक command तथा argument restrictions (बाद के denials सहित), चुने हुए project पर नियंत्रण और installed tool के व्यवहार की पुष्टि करें। तय trusted project या caller-selected source की अनुमति न देने वाली policy यह रास्ता साबित नहीं करती। Enumeration में package install किए बिना rule और project metadata देखें।

Caller-selected URL के साथ `setuptools.package_index.PackageIndex.download` इस्तेमाल करने वाला sudo-allowed Python wrapper, `pip download` से अलग मामला है: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) affected releases में 78.1.1 से पहले URL से निकले filename द्वारा इच्छित download directory से बाहर जाकर process permissions के तहत लिखे जाने का वर्णन करता है। प्रभावी sudo RunAs और argument rule, wrapper caller का URL इसी API को देता है या नहीं, installed build या vendor backport, और परिणामी path कहाँ resolve होता है—इनकी पुष्टि करें। Version string या writable download directory अकेले arbitrary write साबित नहीं करते। Enumeration के दौरान URL fetch या file write किए बिना छोटा wrapper और package metadata देखें।

Caller-selected `.spec` file PyInstaller को देने वाले sudo-permitted build wrapper की भी trust-boundary समीक्षा करें। PyInstaller spec, **build** के दौरान executable Python के रूप में evaluate होती है; उसके `datas` entries build identity द्वारा पढ़ी जा सकने वाली files को artifact में bundle कर सकती हैं। सटीक RunAs user, sudo argument और denial rules, wrapper का path तथा branch handling, चुनी हुई spec file पर नियंत्रण और परिणामी artifact तक पहुँच की पुष्टि करें। केवल `.py` input की अनुमति या PyInstaller installed होना spec-file control या privileged execution साबित नहीं करता। Passive review में केवल सीमित wrapper file और metadata पढ़ें; build न चलाएँ। [PyInstaller spec-file documentation](https://pyinstaller.org/en/stable/spec-files.html) देखें।

### Sudo से चलने वाले preset और plugin loaders

Caller-selected preset या plugin directory स्वीकार करने वाले Python tools, sudo से मिली privileges के साथ code import कर सकते हैं। उदाहरण के लिए, BBOT `-p` से preset स्वीकार करता है और उसका [custom-module documentation](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) अतिरिक्त Python module directories चुनने वाले `module_dirs` entries का वर्णन करता है। अगर प्रभावी sudo rule caller-selected preset की अनुमति देता है और caller चुनी हुई directory में module नियंत्रित करता है, तो tool द्वारा invalid module अस्वीकार किए जाने से पहले भी import privileged user के रूप में code चला सकता है। Enumeration के दौरान module load किए बिना installed version, सटीक sudo run-as और argument policy, तथा preset और module paths के ownership की जाँच करें।

### Sudo से चलने वाला Backdrop command-line tool

[Bee](https://github.com/backdrop-contrib/bee), Backdrop CMS के लिए PHP command-line tool है। इसके `eval` (`php-eval`) और `php-script` commands caller-supplied PHP चला सकते हैं। इसलिए, unrestricted arguments के साथ Bee executable को root के रूप में चलाने वाला sudo rule, root code execution उजागर कर सकता है—यदि Bee Backdrop installation bootstrap कर सके। Site directory से चलाएँ या global `--root=<directory>` option से site चुनें; केवल Bee या Backdrop `settings.php` file मिलना sudo permission, usable site या सफल bootstrap साबित नहीं करता। परीक्षण से पहले प्रभावी sudo rule, command exclusions, executable की identity और site तक पहुँच देखें। Passive enumeration में Bee चलाए बिना rule और file paths देखें। PHP commands जोड़े जाने की जानकारी के लिए [Bee command changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) देखें।

### Sudo से चलने वाले terminal servers

`mosh-server` invoking user के रूप में interactive terminal server शुरू करता है। यह ऊँचा UDP port और session key चुनता है, दोनों caller को बताता है और client के connect होने पर सामान्यतः उस user का login shell शुरू करता है। इसलिए `mosh-server` के लिए unrestricted root-capable sudo grant shell की समीक्षा का उम्मीदवार है, भले server command detach हो जाए। प्रभावी RunAs identity, अनुमत arguments और exclusions, installed binary, shell, client की उपलब्धता और UDP access जाँचें। Passive enumeration में server शुरू किए या कोई live session key दिखाए बिना sudo rule देखें। [Mosh server manual](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) और [upstream design notes](https://github.com/mobile-shell/mosh#how-it-works) देखें।

### ऐसे privileged backup wrappers जो caller की task file को दोबारा लिखते हैं

Root के रूप में चलने वाला shell wrapper caller द्वारा चुनी task file स्वीकार कर सकता है, source paths से `../` हटा सकता है, जाँच सकता है कि हर परिणाम अनुमत directory से शुरू होता है, task file दोबारा लिख सकता है और फिर उसका *pathname* backup program को दे सकता है। पूरे canonical resolution के बाद transformed path जाँचें: string replacement का एक pass नया traversal sequence उजागर कर सकता है जिसे lexical prefix check स्वीकार कर ले। यह भी देखें कि backup program transformed in-memory data पढ़ता है या file फिर से खोलता है। अगर वह file दोबारा खोलता है, तो विफल rewrite के बाद original input बची रह सकती है।

Linux पर `fs.protected_regular`, world-writable sticky directory में किसी दूसरे user की regular file पर `O_CREAT` write रोक सकता है। यह सुरक्षा देता है, लेकिन यदि shell wrapper write error अनदेखा करे तो वह original task file के साथ जारी रह सकता है। Setting, file owner और directory, तथा wrapper विफलता पर रुकता है या नहीं—इनकी पुष्टि करें। यह path file-disclosure का संभावित मामला तभी है जब प्रभावी sudo rule wrapper को privileged user के रूप में चलाने देता हो, caller task input और readable backup destination नियंत्रित करता हो, और backup utility वास्तव में protected sources शामिल करती हो। Enumeration के दौरान backup चलाए बिना इन शर्तों को देखें।

### Privileged packet tools पर argument wildcards

`tcpdump` के sudo rule में **argument pattern** का `*` whitespace और slashes से match कर सकता है, इसलिए pathname जैसा restriction भी अतिरिक्त option text की अनुमति दे सकता है। यह command के executable path में wildcard से अलग है; पूरी RunAs rule और बाद के denials देखें। अगर options inject किए जा सकते हैं, तो अनुमत invocation और installed [`tcpdump` option semantics](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) तय करते हैं कि `-F`, `-V`, `-r`, `-w` या `-Z` उपयोगी read/write primitive देता है या नहीं। `-V` capture filenames की list पढ़ता है, मनमानी files का सामान्य dump नहीं। AppArmor या अन्य MAC policy file access रोक सकती है, भले sudo command की अनुमति देता हो; disk पर profile file होना यह साबित नहीं करता कि वह load होकर लागू है। निष्कर्ष निकालने से पहले authorization और policy को passive तरीके से देखें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) wildcard का अंतर बताता है।

ऐसा root-capable sudo rule जो केवल `tcpdump` executable सूचीबद्ध करता है और arguments पर कोई रोक नहीं लगाता, उसकी भी समीक्षा करें। [tcpdump manual](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) के अनुसार, `-C` या `-G` saved capture rotate करने पर `-z` post-rotation command चलाता है; `-Z` या compile-time default उस command से पहले privileges हटा सकता है। इसे escalation path मानने से पहले प्रभावी sudo rule, installed build, privilege-drop behavior और rotation संभव है या नहीं—इनकी पुष्टि करें। Highlight किया गया rule संभावित संकेत है, root command execution का प्रमाण नहीं।

### Sudo से चलने वाले Nmap wrappers

जब sudo-allowed `nmap` path shell wrapper हो, तो अनुमत सटीक path और forward किए जाने वाले हर option की जाँच करें। परिचित `--script` spelling रोकने से NSE code loading ज़रूरी नहीं कि रुक जाए: Nmap का [`--datadir`](https://nmap.org/book/man-misc-options.html) data files चुनता है और scripting सक्षम होने पर NSE चुनी गई data directory से [`nse_main.lua` load करता है](https://nmap.org/book/nse-implementation.html)। कुछ installed builds alternate long-option spellings भी स्वीकार करते हैं, इसलिए restrictions को उस binary के वास्तविक parser से मिलाएँ। [`--excludefile`](https://nmap.org/book/man-target-specification.html) file-read का अलग surface है; parser errors से text उजागर हो सकता है। Enumeration के दौरान scans चलाए बिना प्रभावी sudo rule, wrapper logic, Nmap version, directory पर नियंत्रण और MAC policy जाँचें।

### Sudo से चलने वाले Mercurial pull hooks

`sudo hg pull /fixed/source` में तय source होने पर भी **receiving** repository current working directory से चुनी जाती है, जब तक command उसे `-R` से तय न करे। Caller-controlled receiving repo में `.hg/hgrc` के hooks हो सकते हैं और hook sudo RunAs user के रूप में चल सकता है। [Mercurial किसी untrusted user या group के स्वामित्व वाली repository configuration को अनदेखा करता है](https://mercurial-scm.org/help/topics/config), इसलिए इसे code execution मानने से पहले RunAs account के trusted users/groups और सटीक working directory देखें। Passive review के लिए policy और config पढ़ना पर्याप्त है; enumeration हेतु pull या hook न चलाएँ।

### Sudo से चलने वाले Git pull hooks

सटीक root-capable `sudo git pull` grant के लिए working directory से चुनी गई **receiving** repository भी जाँचें। Caller-owned repository में executable `post-merge` hook हो सकता है, जो pull द्वारा सफल merge करने पर Git process की identity से चलता है; [Git इस hook का दस्तावेज़ देता है](https://git-scm.com/docs/githooks), साथ ही [pull का merge-versus-rebase behavior](https://git-scm.com/docs/git-pull)। प्रभावी sudo rule और CWD, सक्रिय hook path और उसकी permissions, तथा नए commits वाला merge संभव है या नहीं—इनकी पुष्टि करें। विफल, no-op या केवल rebase वाला pull इस hook path को साबित नहीं करता। Privileged pull चलाए बिना policy और repository metadata देखें।

### Sudo से चलने वाली rsync archive copies

`sudo rsync -a ... /writable/source/* /fixed/destination/` के लिए **sudoers argument pattern** में `*` whitespace से match होकर source और destination के बीच अतिरिक्त option स्वीकार कर सकता है। यह filenames के shell expansion से अलग है। अगर caller source भर सकता है और destination privileged rsync process द्वारा writable है, तो [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privileged ownership की माँग कर सकता है, जबकि archive mode permission bits सुरक्षित रखता है; इससे संभवतः owned SetUID file बन सकती है। Exact [sudoers wildcard semantics](https://man7.org/linux/man-pages/man5/sudoers.5.html), rsync version, बाद के denials, filesystem `nosuid` और MAC policy जाँचें। Match करता हुआ rule जाँच का उम्मीदवार है, सफल privilege escalation का प्रमाण नहीं।

### Sudo से चलने वाला packet-filter rule export

`iptables` और `iptables-save` (या संबंधित `ip6tables` pair) दोनों के लिए unrestricted root-capable grant में file-write की जाँच करें। `comment` match caller द्वारा चुना rule text स्वीकार करता है, जबकि `iptables-save -f` serialized ruleset चुने हुए pathname पर लिखता है।<sup>[[20]](#references)[[21]](#references)</sup> उपयोगी payload इस पर निर्भर करता है कि installed backend comments को कैसे serialize करता है और destination file export में अन्य lines स्वीकार करती है या नहीं; केवल `iptables-save` arbitrary chosen content नहीं देता। सटीक sudo RunAs identity, arguments और exclusions, उपलब्ध match extension, backend और destination permissions देखें। Enumeration के दौरान firewall rules बदले या file लिखे बिना grant की जाँच करें।

### Privileged Below logging directory

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ने Below के उन releases को प्रभावित किया जो 0.9.0 से पहले world-writable `/var/log/below` directory बनाते थे। यदि कोई service या अनुमत sudo command प्रभावित build को root के रूप में चलाती है, तो non-sticky log directory में लिख और traverse कर सकने वाला user privileged process द्वारा खुलने से पहले log entry को symlink से बदल सकता है। Installed package का patch status, सटीक privileged execution path, प्रभावी directory access, sticky bit और ACLs, तथा `/var/log/below/error_root.log` का metadata देखें। World-writable path या sudo rule अकेले पूरी chain साबित नहीं करते। Sticky directory या vendor backport आकलन बदल सकता है। Passive enumeration में केवल metadata देखें; link बनाने या privileged program चलाने की आवश्यकता नहीं है।

### Writable inputs से privileged support-bundle collection

`sudo` से चलाने की अनुमति वाली support-profile script root के रूप में तय log paths पढ़कर उनका content profile archive में copy कर सकती है। File reads के लिए वास्तविक script देखें, फिर जाँचें कि caller source path या किसी parent directory entry को symlink से बदल सकता है या नहीं। यदि privileged read उस link को follow करती है और caller परिणामी archive पढ़ सकता है, तो protected file उजागर हो सकती है। Sudo grant, writable source path, privileged read और readable output—चारों आवश्यक हैं; केवल writable log या profile filename पर्याप्त नहीं। Enumeration के दौरान files बदले या profile बनाए बिना प्रभावी permissions और link metadata देखें। [Nagios XI support guidance](https://support.nagios.com/forum/viewtopic.php?t=62758) root के रूप में चलने वाली उसकी profile script और output archive का उल्लेख करता है, जो बताता है कि ऐसे bundles के inputs और output access पर रोक क्यों आवश्यक है।

### Root-run Python archive restore scripts

Python restore script के लिए बहुत सीमित sudo rule में भी archive input की समीक्षा आवश्यक है। यदि caller archive चुन या बदल सकता है और script उसे root के रूप में `tarfile.extractall(filter="data")` से extract करती है, तो filter पर भरोसा करने से पहले interpreter के security updates देखें। CPython ने कई symlink और hard-link filter bypass ठीक किए—जिनमें CVE-2025-4517 शामिल है—3.9.23, 3.10.18, 3.11.13, 3.12.11 और 3.13.4 में। Distribution backports पहले के version में भी fix ला सकते हैं, इसलिए दिखाई देने वाला interpreter version exposure का प्रमाण नहीं है।<sup>[[16]](#references)[[17]](#references)</sup>

Passive review के लिए सटीक sudo command और script पढ़ें, देखें कि कौन-सा argument archive चुनता है, और जाँचें कि वर्तमान user archive या उसकी containing directory लिख सकता है या नहीं। Installed vendor patch और extraction destination अलग-अलग सत्यापित करें; `filter="data"` हर untrusted archive को सुरक्षित नहीं बनाता।<sup>[[16]](#references)[[17]](#references)</sup>

### Sudo से चलने वाले machine-learning model loaders

Caller-selected `.pt`, `.pth` या `.ckpt` file की अनुमति देने वाले sudo rule की समीक्षा करें, यदि privileged script उस file को [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` या किसी अन्य pickle-based loader को देती है। प्रभावी RunAs rule, caller चुना model बना या बदल सकता है या नहीं, और shell wrapper से Python helper तक actual argument flow जाँचें। `.pth` extension का उपयोग असंबंधित Python site configuration files के लिए भी होता है, इसलिए extension अकेले model loading का प्रमाण नहीं। Archive scan या static pickle scan यह साबित नहीं करता कि बाद का load सुरक्षित है; loader का [version-dependent `weights_only` behavior](https://docs.pytorch.org/docs/stable/notes/serialization.html) और कोई allowlisting देखें। [ML pickle और Fickling notes](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md) देखें। Passive enumeration में model कभी load या unpack न करें।

### Stored input का sudo-run expression parsing

Sudo के जरिए root के रूप में चलने वाली fixed Python script, application database में कम privilege वाला user जो text store कर सकता है, उसे evaluate कर सकती है। TensorFlow में `preprocess_input_exprs_arg_string(value, safe=False)` call, `eval` path चुनता है; [TensorFlow की advisory](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) असुरक्षित parser और उसके command-line caller में fix का वर्णन करती है। Application द्वारा स्पष्ट रूप से `safe=False` call करने की अलग समीक्षा आवश्यक है, भले वह command-line caller patch हो चुका हो। प्रभावी sudo rule, सटीक input row में बदलाव करने वाला user, filtering या scoring से वह row call तक पहुँच सकती है या नहीं, और installed function का behavior जाँचें। TensorFlow version, sudo grant या hardcoded model file अकेले chain साबित नहीं करते। Script और data flow को passive तरीके से देखें; enumeration के दौरान privileged helper न चलाएँ या test expressions न दें।

### Sudo से चलने वाली needrestart configuration

`needrestart -c` caller-selected Perl configuration file लोड करके उसके content को evaluate करता है। यदि `sudo -l` root के रूप में `needrestart` को ऐसे arguments के साथ अनुमति देता है जिनमें `-c` शामिल है, और caller writable location की readable configuration file चुन सकता है, तो यह अनुमति root code execution तक ले जा सकती है। सटीक sudo run-as और argument rule जाँचें; केवल तय argument list की अनुमति देने वाला rule इस रास्ते को रोक सकता है। यह needrestart की interpreter-scanning vulnerabilities से अलग है: package update करना या `interpscan` disable करना unrestricted root `-c` grant को सुरक्षित नहीं बनाता।<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Sudo से दूसरे account के रूप में चलने वाले Python imports

Fixed Python entry point उस module को import कर सकता है जिसे caller edit या replace कर सके—भले sudo script को **non-root** service user के रूप में चलाए। Literal `from utils import status` के लिए `utils/__init__.py` और `utils/status.py` के साथ package directory की permissions भी देखें। Writable file को execution path मानने से पहले script का import path, सटीक अनुमत sudo arguments और संबंधित action उस import तक पहुँचता है या नहीं—इनकी पुष्टि करें। Enumeration के दौरान import या script चलाए बिना files और permissions देखें।<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` का सटीक sudo rule केवल readable script माँगता है; file का executable होना या shebang होना आवश्यक नहीं। **Missing** local modules भी देखें: यदि script ऐसा module import करती है जिसकी filename caller-writable script directory में बनाई जा सकती है, तो Python उस file को RunAs identity के तहत load कर सकता है। प्रभावी sudo rule, interpreter का वास्तविक [module search path](https://docs.python.org/3/library/sys_path_init.html), module built-in या frozen है या नहीं, और import तक पहुँचा जाता है या नहीं—इनकी पुष्टि करें। Script के लिए सीधा sudo rule, execute-bit और shebang की अलग शर्तें रखता है। अलग wrapper, जो `sudo -u account` के बाद caller-supplied tokens जोड़ता है, उसमें भी argument flow देखें: उन tokens में दूसरा `-u` तभी मायने रखता है जब invoked sudo policy परिणामी identity की अनुमति देती हो। केवल static strings इनमें से कोई रास्ता साबित नहीं करतीं।

### Caller-controlled configuration के साथ Sudo से चलने वाला Apache

अगर sudo rule privileged `apachectl`, `apache2ctl` या `httpd` invocation को caller-controlled `-f` configuration file के साथ अनुमति देता है, तो उस file और उसकी parent directory की permissions देखें। Apache का [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) directive module name के बाद **module filename** लेता है; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) भी file load करता है। [`Include` और `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) configuration बढ़ा सकते हैं या errors के जरिए file contents उजागर कर सकते हैं। Custom wrapper इन paths को validate कर सकता है, privileges हटा सकता है या arguments सीमित कर सकता है; इसलिए writable config code execution का प्रमाण नहीं, केवल जाँच का उम्मीदवार है। निष्कर्ष निकालने से पहले path canonicalization, symlinks और directive parsing जाँचें।

### Caller-controlled configuration के साथ Sudo से चलने वाला nginx

Unrestricted root-capable `nginx` rule [`-c` से दूसरी configuration चुनने](https://nginx.org/en/docs/switches.html) की अनुमति दे सकता है। सटीक sudo arguments और exclusions, caller configuration दे सकता है या नहीं, तथा परिणामी master या workers की protected paths तक पहुँच बनी रहती है या नहीं—इनकी समीक्षा करें। चुना हुआ `root` और `autoindex`, नए listener से files उजागर कर सकते हैं; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) privileged file-write path दे सकता है, लेकिन DAV module default रूप से built नहीं होता। इसका मौजूद होना, listener तक पहुँच, file permissions और temporary-file behavior जाँचना होगा। [`error_log` directive](https://nginx.org/en/docs/ngx_core_module.html#error_log) चुनी हुई file को भी target कर सकता है; `/etc/ld.so.preload` जैसी sensitive configuration file में logs लिखना escalation path तभी बनता है जब प्रभावी privileged writer और नियंत्रित log record मौजूद हों। `sudo -l` में executable highlight केवल जाँच का संकेत है, इनमें से किसी रास्ते के काम करने का प्रमाण नहीं। Passive enumeration में nginx शुरू या reconfigure न करें।

### Privileged Bash prompts में pattern comparison

जब sudo से चलने वाली Bash script caller से value पढ़कर उसे `[[ "$expected" == $entered ]]` से जाँचती है, तो Bash unquoted right-hand operand को pattern मानता है। इसलिए expected value जाने बिना भी wildcard comparison पूरा कर सकता है। Operand को quote करने (`[[ "$expected" == "$entered" ]]`) से literal string comparison होता है। सटीक sudo rule, prompt तक पहुँचा जा सकता है या नहीं, और comparison के बाद script क्या करती है—इनकी जाँच करें; केवल syntax से exploitable path साबित नहीं होता। Enumeration के दौरान expected value न दिखाएँ। [Bash conditional constructs reference](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html) देखें।

### Sudo से चलने वाले ऐसे helpers जो file download करके चलाते हैं

Caller-selected URL स्वीकार करने, response को disk पर लिखने और बाद में उस file को interpreter या shell से चलाने वाला custom helper, unrestricted root-capable sudo grant में dataflow की जाँच का विषय है। [Sudoers में command entry कोई arguments न सूचीबद्ध करे, तो arbitrary arguments अनुमत हैं](https://man7.org/linux/man-pages/man5/sudoers.5.html); fixed executable path यह सीमित नहीं करता कि उसके arguments क्या चुन सकते हैं। Installed helper में वास्तविक URL validation, output path, success branch और बाद का execution सत्यापित करें। केवल libcurl import का मिलना या printable string इस chain को साबित नहीं करता।

जब helper **caller-controlled working directory** में relative path इस्तेमाल करता है, तो fixed output basename भी write और execution के बीच बदला जा सकता है। Root-owned file का नाम बदलना या उसे replace करना directory में write/search access और sticky-bit restrictions पर निर्भर करता है, केवल file mode पर नहीं; [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) देखें। जाँचें कि helper बाद में path फिर खोलता है या पहले से खुले descriptor का उपयोग करता है, और लिखने से पहले trusted directory में जाता है या नहीं। Enumeration के दौरान sudo policy, helper और directory metadata passive तरीके से देखें; privileged download या race न चलाएँ।

Root-sudo download helper, Bash command string जैसे `curl <caller input> -o <fixed output>` बनाता हो, तो **argument** injection भी उजागर कर सकता है। Whitespace रोकने वाला filter भी [Bash brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) को नहीं रोकता: unquoted comma-separated elements अलग curl arguments बन सकते हैं। यदि input तय `-o` से पहले curl तक पहुँचता है, तो caller-supplied output option helper की identity के तहत पहली URL का destination चुन सकता है; [curl output options को URLs के क्रम के अनुसार जोड़ता है](https://curl.se/docs/manpage.html#-o)। सटीक shell, quoting, input validation, प्रभावी sudo rule, curl argument order और समर्थित URL schemes, तथा caller fetched bytes नियंत्रित कर सकता है या परिणाम पढ़ सकता है या नहीं—इनकी पुष्टि करें। PyInstaller-packaged executable में Python application logic हो सकता है, लेकिन उसका packaging marker या `curl` string अकेले यह data flow साबित नहीं करते। अधिकृत होने पर सीमित offline copy की समीक्षा करें; सामान्य enumeration में helper न चलाएँ और attacker-selected data fetch न करें।

[`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) चलाने वाली root-sudo shell script केवल unused नाम चुनती है; file **बनाती नहीं**। यदि script बाद में उस नाम को ऐसी directory में बनाती है जिसे दूसरा user प्रभावित कर सकता है, फिर दोबारा खोलकर उसकी contents को root के `authorized_keys` जैसे protected destination में जोड़ती है, तो संभावित temporary-file race की समीक्षा करें। सटीक sudo rule, directory और file ownership, create तथा reopen sequence, kernel protections, और privileged write वास्तव में attacker-controlled bytes इस्तेमाल करती है या नहीं—इनकी पुष्टि करें। `mktemp -u` string या writable `/tmp` अकेले race साबित नहीं करते। Enumeration के दौरान script और path metadata देखें; उसे चलाएँ या temporary file के साथ race न करें।

## Defensive notes

- sudo के जरिए interpreters या interactive editors चलाने की अनुमति न दें।<sup>[[1]](#references)</sup>
- ऐसे fixed, root-owned wrappers को प्राथमिकता दें जो एक सीमित administrative action करते हों।<sup>[[1]](#references)[[2]](#references)</sup>
- यदि interpreter आवश्यक हो, तो सटीक script path सीमित करें और user-controlled arguments, writable imports, `PYTHONPATH` तथा असुरक्षित environment preservation रोकें।<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- File editing आवश्यक हो, तो सटीक file path सीमित करें और patched sudo versions तथा strict environment handling के साथ `sudoedit` पर विचार करें।<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`, `env_keep`, writable working directories, writable module/import paths, `NOEXEC`, `use_pty` और logging की समीक्षा करें, लेकिन इन्हें पूर्ण sandbox न मानें।<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
