## Sudoで許可されたインタープリター

`sudo -l`でユーザーがrootとしてインタープリターを実行できる場合、直接的なコード実行として扱います。インタープリターは任意のコードを実行するように設計されているため、`python3`、`perl`、`ruby`、`lua`、`node`などのバイナリを許可するルールは、引数が厳密に制限・検証されていない限り、通常はrootとしてのコマンド実行と同等です。<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

一般的な確認手順: まずユーザーの権限を一覧表示し、次にインタープリターの`-c`オプションを使ってPythonの文を実行します。<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

その他のインタープリターの例を以下に示します。掲載したインタープリターのドキュメントには、インラインコードの実行または子プロセスAPIについて記載されています。<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

sudo ルールで `/usr/bin/python3` が許可されている場合、検証時にもその正確なパスを使用してください。<sup>[[2]](#references)</sup>

`/usr/bin/python*` のような sudo 実行ファイルの glob では、Python 3 向けに書かれたスクリプトに対して Python 2 も許可される場合があります。呼び出し元が制御できるテキストをスクリプトが `input()` で受け取る場合、[Python 2 はそのテキストを式として評価します](https://docs.python.org/2/library/functions.html#input)。インタープリターを明示して呼び出すと、スクリプトの shebang は無視されます。これを実行経路と判断する前に、一致するバイナリがインストールされているか、実効的な RunAs と引数ポリシー、拒否設定、入力に到達可能かを確認してください。

root 権限で実行可能な sudo ルールでスクリプトのパスが固定されていても、そのスクリプトが実行する内容までは制限されません。読み取り可能な Bash wrapper については、sudo で呼び出し元が引数を選択できる場合に、最初の実行コマンドが `$1` のような引用符で囲まれていない位置パラメーターを**コマンドワード**として使っているか確認してください。実効的な RunAs ID、パスワードと引数のポリシー、後続の拒否設定、実際に実行されるスクリプトの分岐を確認してください。`NOEXEC`、安全な引数リストの固定、またはコマンドを検証する wrapper によって結果が変わる場合があります。テスト用コマンドで実行するのではなく、列挙時に短いスクリプトを静的に調査してください。

root 権限で実行可能な、制限のない `dotnet` の sudo ルールも、インタープリターの観点から確認する価値があります。.NET SDK がインストールされている場合、[`dotnet fsi` は F# コードを対話形式またはスクリプトから実行します](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/)。また、[`dotnet run` はソースからプロジェクトを実行します](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)。まず、実効的な RunAs ID と正確な引数ポリシーを確認してください。特定の安全なサブコマンドや信頼できるアプリケーションに固定されたルールは、これとは異なる許可です。また、ランタイムのみのインストールでは SDK コマンドが使えない場合があります。実行ファイル名は確認の手掛かりにすぎず、コード実行の証拠ではありません。

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudoで許可されたエディタ

`sudo -l` によってユーザーが root として対話型エディタを実行できる場合、無害なファイル編集権限ではなく、コマンド実行の手段として扱ってください。エディタ内からシェルコマンドを実行したり、任意のファイルを読み書きしたり、外部ヘルパーを呼び出したりできることがよくあります。<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

一般的な確認手順: まずユーザーの権限を一覧表示し、次に許可されている各エディタまたはページャを sudo 経由で実行します。<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nanoコマンド実行

`nano` が sudo 経由で許可されている場合、エディターのインターフェースからコマンドを実行できる可能性があります。<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

次に、nano のコマンドプロンプトで `id` や `/bin/sh` などのコマンドを実行します。<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

対話型シェルで使用可能な端末ストリームがない場合、このリダイレクト形式は標準出力と標準エラーをファイルディスクリプター 0 に割り当てます。<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

正確なキー入力の並びは nano のバージョンやビルドオプションによって異なりますが、セキュリティ上の問題は同じです。エディタが root 権限で実行され、外部コマンドを呼び出せる状態にあります。<sup>[[1]](#references)[[12]](#references)</sup>

### その他の一般的なエディタからの脱出方法

Vim 系のエディタでは、一般に `:!` を使ってコマンドを実行できます。<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` などの pager からも shell を実行できる場合があります。<sup>[[14]](#references)</sup>

`apport-cli` を root として実行できる sudo ルールがある場合も、同様に pager を確認する必要があります。影響を受けるバージョンの Apport では、攻撃者が調整可能な端末サイズで crash report を `less` で開くことができ、特定の sudo および pager の条件が満たされると、pager から root shell を取得できる可能性がありました。バージョンだけで脆弱と判断する前に、実効 sudo ルール、pager の設定、ディストリビューションのパッケージ修正を確認してください。受動的な列挙中に crash を発生させたり、特権付きレポートを開いたりせず、パッケージとポリシーのメタデータを確認してください。[Ubuntu's CVE record](https://ubuntu.com/security/CVE-2023-1326) には、バックポートされた修正を含む、リリースごとの修正済みパッケージバージョンが記載されています。

```text
!/bin/sh
```

## その他の sudo および doas ルールの危険性

まず `sudo -l`、`sudo -V`、該当する `doas` ポリシーを確認します。許可されたコマンド、実行ユーザー、引数、環境、デフォルト設定をまとめて確認してください。root 以外のサービスアカウントとして実行する権限でも、そのアカウントのファイルや root への経路が露出する可能性があります。

sudo で実行を許可された固定の Python スクリプトでも、対話的なユーザー入力や呼び出し元が制御できる入力を [`os.system()`](https://docs.python.org/3/library/os.html#os.system) に連結していれば、RunAs ID でシェルコマンドを実行できる場合があります。シェルの句読記号を denylist にするだけでは、安全性を確認したことにはなりません。[シェルは `$(...)` によるコマンド置換も認識します](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)。許可された引数が対象の入力分岐に到達すること、その入力が安全に検証されずにシェルコマンドへ渡ること、実効 sudo ポリシーが意図した RunAs ユーザーを許可することを確認してください。スクリプトのパスや `os.system()` の呼び出しだけでは、あくまで調査の手掛かりです。特権スクリプトを実行せずにソースを確認してください。

root として有効な `chattr` の sudo 許可があれば、ファイルの immutable（`i`）属性を解除できます。ただし、これだけで書き込み権限や新たな ID が得られるわけではありません。[`chattr` のマニュアル](https://man7.org/linux/man-pages/man1/chattr.1.html)によると、この属性は変更を禁止し、変更できるのは root または `CAP_LINUX_IMMUTABLE` を持つプロセスだけです。sudo の引数ポリシーとファイルシステムの対応状況を確認し、属性を解除した後に呼び出し元がそのファイルへ書き込めること、さらに高い権限のプロセスがそのファイルを利用することを別途検証してください。たとえばログインシェルを置き換える場合、対象アカウントで受け入れられる認証情報と、そのシェルを通じた実際のログインも必要です。列挙中にポリシー、ファイル属性、権限を確認し、変更は行わないでください。

sudo がパスワードとワンタイムコードの両方を要求する場合、これらの前提条件とコマンド許可を分けて考えてください。読み取り可能な `.google_authenticator` ファイルには機密性の高いシード情報が含まれます。一方、古いアプリケーションやデータベースのパスワードハッシュは、現在のアカウントパスワードの候補にすぎません。どちらも、実効 PAM 設定で他方の要素が受け入れられる証拠にはなりません。許可された場合は、正確な RunAs と引数を確認してください。RubyGems の `gem` を root として無制限に実行できる許可があれば、エディターコマンドが露出する可能性があります（[GTFOBins](https://gtfobins.github.io/gtfobins/gem/)）。ただし、許可が制限されている場合や認証に失敗した場合は該当しません。受動的な列挙では、シードの表示、パスワードの復元、コードの生成、特権コマンドの実行をせず、パスとポリシーのみを報告してください。

Chef の `knife` を root 権限で実行できる無制限の sudo 許可は、インタープリターの観点から確認する必要があります。[Chef のドキュメントによると、`knife exec -E` は Ruby 文字列をローカルで評価します](https://docs.chef.io/workstation/26/tools/knife/knife_exec/)。実効 sudo ルールで `exec` サブコマンドと呼び出し元が指定する `-E` 引数が許可されていること、意図した RunAs ID、該当するコマンド拒否や固定引数を確認してください。インストール済みバイナリーや、他のサブコマンドに限定されたルールは調査の手掛かりにすぎません。受動的な列挙では、`knife` を実行せずにルールを報告してください。

対話型の `msfconsole` を root 権限で実行できる正確な sudo 許可も、同様に注意が必要です。[GTFOBins は、その `irb` コンソール](https://gtfobins.org/gtfobins/msfconsole/)が sudo の ID を継承する可能性を説明しています。実効 RunAs ユーザー、許可される引数一覧、コマンド拒否、`NOEXEC` などの制限、インストール済みコンソールの挙動、呼び出し元が対話型入力を渡せるかを確認してください。パスが強調表示されるだけでは調査の手掛かりにすぎません。受動的な列挙ではコンソールを起動しないでください。

FreeBSD では、root としての `pkg update` と `pkg install *` に限定された sudo ルールでも、リポジトリの信頼性を確認する必要があります。呼び出し元が `/etc/hosts` に書き込めるか、実効的に有効なリポジトリ設定で `signature_type: none` を指定した HTTP ホスト名が使われているかを確認してください。[FreeBSD の `pkg.conf` マニュアル](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5)によると、`none` は署名チェックを無効にします。`pkg+http` だけでは、署名チェックが無効だとは判断できません。パッケージにはインストールスクリプトを含められるため（[FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)）、呼び出し元が実際にリポジトリのエンドポイントを制御でき、パッケージを選べるなら、root の境界を越える可能性があります。結論を出す前に、リポジトリの上書き設定、SRV／ミラーの解決、実効 sudo 引数、パッケージの選択、スクリプトの実行を確認してください。列挙中は名前解決先を変更したり `pkg` を実行したりせず、ポリシーと小さなローカル設定ファイルを確認してください。

root 権限で `apt-get update` と `apt-get upgrade` を実行できる sudo ルールでは、呼び出し元が制御する `http_proxy` を sudo が保持する場合、リポジトリの信頼性も確認する必要があります。実効的な APT プロキシ設定が実際にその変数を使用するか、どの有効なリポジトリへのリクエストに影響するかを確認してください。プロキシだけでは、信頼された署名鍵で認証されたアーカイブのパッケージを置き換えられません。[APT の HTTP transport マニュアル](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html)にはプロキシの優先順位が、[apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html)には署名チェック、非セキュアリポジトリの上書き設定、未認証パッケージの確認が記載されています。正確な sudo の RunAs と引数、リポジトリの認証ポリシー、必要な対話型確認、選択されたアップグレードが root としてパッケージスクリプトを実行するかを確認してください。受動的にポリシーとローカル設定を調べ、列挙中にパッケージ通信の宛先を変更したりアップグレードを実行したりしないでください。

root 権限で `snap install` を実行できる sudo ルールは、引数でローカル snap と制限の緩いインストールモードを呼び出し元が選択できる場合、パッケージからコードへの境界になり得ます。[Snap のドキュメント](https://snapcraft.io/docs/explanation/snap-development/install-modes/)によると、`--dangerous` はローカル snap の assertion チェックを省略し、`--devmode` は confinement を緩和します。また、[インストールフックは初回インストール時に実行される可能性があります](https://snapcraft.io/docs/reference/development/supported-snap-hooks/)。保護対象のホストファイルへアクセスできると主張する前に、正確な sudo の引数／RunAs ポリシー、snap ファイルを誰が制御するか、インストール済み snapd がこれらのモードを受け入れるか、フックの実効 ID と confinement を確認してください。`snap` バイナリーやワイルドカードを含むように見えるルールだけでは、この連鎖の証明になりません。受動的な列挙ではパッケージをインストールしたりフックを実行したりしないでください。

**root 以外**のアカウントとしてカスタムの認証情報読み取りバイナリーを実行できる正確な sudo 許可では、まず実行せずに許可対象のバイナリーとファイル権限を確認します。埋め込みのパスワード判定は、幅広文字としてのみ見える場合があります。[GNU `strings` のドキュメント](https://sourceware.org/binutils/docs/binutils/strings.html)では、16-bit little-endian の抽出方法が説明されています。見つかった文字列は、それが受け入れられるパスワードであることや、成功分岐で現在の認証情報が露出することの証拠ではありません。バイナリーの挙動、保護データへの対象アカウントのアクセス、認証情報の有効性、その後のアカウントまたはグループの移行をそれぞれ確認してください。そのアカウントが `docker` グループに属する場合は、ソケットへのアクセスとデーモンが rootful か rootless かを確認してから、ホストの root へのアクセスを推測してください。[Docker のドキュメント](https://docs.docker.com/engine/install/linux-postinstall/)では、このグループが持つ root レベルの影響を説明しています。通常の列挙では、バイナリーを実行したり文字列をダンプしたりせず、sudo ルールとグループメンバーシップを報告してください。

アプリケーションの保守スクリプトに対するワイルドカード sudo ルールは、スクリプトのパス以外も調べる必要があります。許可されたスクリプトが制限のない引数を受け入れるか、権限の低いアプリケーションアカウントから書き込み可能な設定を読むかを確認し、さらにそれらの値がシェルコマンドやサブプロセスの環境へ渡る経路をたどってください。たとえば、ZoneMinder の [`zmupdate.pl` は `mysqldump` コマンドを組み立てて `qx` で実行します](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in)。また、[`zmdc.pl` はデーモンを起動する前に `ZM_LD_PRELOAD` 設定を `LD_PRELOAD` にコピーします](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)。これらのスクリプトのいずれかを root として許可する sudo ルールは、対応する入力を制御でき、インストール済みバージョンのコードに到達する場合、信頼境界を越える可能性があります。実効 sudo ルール、アプリケーション設定の書き込み権限、スクリプトのソースを確認してください。ワイルドカードや設定だけでは、実行の証拠ではなく調査の手掛かりです。

- `SETENV`、`env_keep`、`secure_path`、`LD_PRELOAD` により、通常は限定的なコマンドでも import、ライブラリー、PATH の hijack が可能になる場合があります。[環境変数ガイド](../linux-basics/linux-environment-variables.md)と[SUID/linker の悪用](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md)を参照してください。

root 権限でシェルラッパーを実行できる正確な `SETENV` 許可では、ラッパーが固定の Python スクリプトをリテラルな import とともに起動する場合、1段階の確認が必要です。`secure_path` が制限するのはシェルのコマンド検索であり、Python の [`PYTHONPATH` モジュール検索](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH)ではありません。[`-E` と `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) を付けると、Python はその環境変数を無視します。これをコード実行として扱う前に、実効 sudo タグと拒否設定、ラッパーの分岐、インタープリターのオプション、import の解決、呼び出し元が書き込める検索ディレクトリを確認してください。短いスクリプトは静的に調査し、特権ラッパーを実行しないでください。

root 権限で `neofetch ""` を実行できる正確な sudo 許可でも、該当する sudo デフォルト設定が呼び出し元の制御する `XDG_CONFIG_HOME` を保持する場合、シェル設定ファイルが読み込まれる可能性があります。[Neofetch の設定ローダー](https://github.com/dylanaraps/neofetch/blob/master/neofetch)は、そのディレクトリ配下の `neofetch/config.conf` または `neofetch/config` を source します。引数が空でも、この検索は行われます。結論を出す前に、インストール済みローダー、実効 RunAs と引数ポリシー、コマンド拒否、sudo がこのコマンドで実際に対象変数を保持するか、呼び出し元が読み取り可能な設定パスを制御するかを確認してください。変数が保持されることや Neofetch がインストールされていることだけでは、調査の手掛かりにすぎません。特権コマンドを実行したり設定内容を表示したりせず、ポリシーとファイルのメタデータを確認してください。[sudoers の環境処理](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)も参照してください。

root 権限で `facter` を無制限に実行できる sudo ルールは、カスタム fact の調査も必要です。[Puppet のドキュメント](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm)によると、`--custom-dir` は指定したディレクトリから Ruby の fact ファイルを読み込みます。正確な sudo ルールでそのオプションが許可されるか、インストール済み Facter がそれを受け入れるか、呼び出し元がそのディレクトリを制御するかを確認してください。固定引数の許可、明示的なコマンド拒否、カスタム fact の無効化によって結果は変わる場合があります。受動的な列挙では、Facter を実行したり fact の内容を読んだりせず、ポリシー上の候補を報告してください。

root 権限でスクリプトを実行できる正確な sudo 許可に `SETENV` が付いている場合、`find` のような bare command name と、sudo ポリシーおよびスクリプト初期化後の実効 `PATH` を確認してください。source された Bash ファイルが `enable -n [` を実行する場合もあります。[その後、Bash は `PATH` から外部の `[` を検索します](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html)。スクリプトで後からそのコマンドが使われる場合は、この挙動に注意してください。該当する [sudoers の環境設定と `secure_path` のルール](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)、`NOSETENV`／`NOEXEC` や拒否エントリー、スクリプトと source されるファイルの処理、呼び出し元が制御する実行可能な検索ディレクトリを確認してください。bare command を含む読み取り可能なスクリプトは調査の手掛かりであって、特権実行の証拠ではありません。sudo ルールを実行せずに調査してください。
- 固定 URL を `curl` で取得する特権スクリプトでも、該当する sudo ルールが `http_proxy` を保持し、リクエストがそのプロキシ経由で送られるなら、呼び出し元がレスポンスを選択できる場合があります。その後、レスポンスを外部エンティティを解決する XML パーサーへ渡す場合、悪意のあるレスポンスから特権プロセスが読めるファイルを漏えいさせられる可能性があります。特定のプロキシ変数や XML パーサーだけでは脆弱性とは限りません。正確な sudo 環境ポリシー、`no_proxy` の除外、要求 URL、パーサー設定、出力先を確認してください。[curl のプロキシ環境変数に関するドキュメント](https://everything.curl.dev/usingcurl/proxies/env.html)に変数の挙動が記載されています。受動的な列挙中にネットワークリクエストを送ったり、悪意のある XML を解析したりしないでください。
- 呼び出し元の影響を受けるデータから PostScript ファイルを生成し、その後 `ps2pdf -dNOSAFER` を実行する root 権限の sudo スクリプトは、入力フローを別途確認する必要があります。Ghostscript のドキュメントによると、このフラグは `.setsafe` が呼ばれるまで SAFER を無効化し、プロセスの OS 権限で PostScript によるファイル操作を可能にします。呼び出し元の引数から組み立てられた SQL クエリが、攻撃者の制御する行を PostScript テンプレートに渡す場合があります。ただし、クエリ文字列や `ps2pdf` の呼び出しだけでは、データが実行可能な PostScript 構文に到達する証拠にはなりません。実効 sudo ルール、入力からテンプレートへの正確な経路、エスケープ処理、インストール済み Ghostscript の挙動、文書の解釈前に SAFER が再有効化されるかを確認してください。受動的な列挙中に特権変換を実行しないでください。[Ghostscript の `-dNOSAFER` に関するドキュメント](https://ghostscript.readthedocs.io/en/master/Use.html)を参照してください。
- シェルスクリプトを実行する sudo ルールでは、保持される環境変数とスクリプト自体を照合してください。`if $CHECK_CONTENT; then` のような構文は、展開された値をコマンドとして実行します。そのため、スクリプトパスと引数が固定でも、`CHECK_CONTENT` が保持されればコマンド実行につながる可能性があります。分岐に到達できるか、環境変数が実際に保持されるかは、個別のルールについて確認する必要があります。<sup>[[2]](#references)[[22]](#references)</sup>
- sudo で実行を許可された Python スクリプトは、書き込み可能なディレクトリやキャッシュされた `.pyc` ファイルからコードを import する場合があります。[権限昇格ガイド](../linux-basics/linux-privilege-escalation/README.md)では、キャッシュのケースを詳しく説明しています。
- root として実行を許可された固定の Python スクリプトでも、対話型デバッガーが露出する場合があります。`pdb.set_trace()` や `pdb.post_mortem()` のような呼び出しは、呼び出し元がブレークポイントまたは例外ハンドラーに到達でき、**デバッガーの入力ストリームを制御できる**場合、デバッグ中のプロセスのコンテキストで Python 文を実行できます。正確な sudo RunAs ルール、認証と分岐の条件、例外に到達する可能性、端末／入力の所有者、デバッガーが同じ特権プロセス内で実行されるかを確認してください。ソケットリクエストで例外を発生させるだけでは、別の端末に接続されたデバッガーへのアクセスは得られません。[Python のドキュメント](https://docs.python.org/3/library/pdb.html)には、デバッガーでの文の評価と post-mortem モードが記載されています。列挙中に特権ハンドラーを実行せず、スクリプトを静的に調べてください。
- sudo で実行を許可された固定の Python スクリプトは、データベースまたは Unix ソケットからプロファイルフィールドを読み取り、それを後で `str.format()` の**フォーマット文字列**となる文字列に追加する場合もあります。[置換フィールドには属性やマッピングキーを指定できます](https://docs.python.org/3/library/string.html#format-string-syntax)。そのため、攻撃者が制御するフィールドは、`format()` に渡されたオブジェクトを調べ、結果が表示されたり呼び出し元が読み取り可能な場所に保存されたりすれば、そこから到達できるデータを露出させる可能性があります。実効 sudo RunAs ID、対象レコードへの書き込み権限、フォーマット文字列へのデータフロー、渡されるオブジェクト、出力の可視性を確認してください。これは自動的なコード実行ではありません。また、信頼されたリテラルのフォーマット文字列と、攻撃者が制御する*値*は別のケースです。漏えいした秘密情報が OS アカウントへの移行につながるのは、そのアカウントがそれを受け入れる場合だけです。特権操作を実行せずにスクリプトとソケットの権限を確認してください。
- root 権限の Python ラッパーが、呼び出し元が選択した URL を GitPython の `Repo.clone_from` に渡す場合があります。ラッパーが Git の `protocol.ext.allow=always` も有効にしていれば、`ext::` リモートから外部ヘルパーを起動できる可能性があります。正確な sudo 引数、URL の取得元、GitPython パッケージのバージョンとベンダーパッチの有無、ラッパーが安全でないプロトコルを明示的に有効にするかを確認してください。GitPython は 3.1.30 で[安全でないプロトコルのデフォルト拒否](https://github.com/gitpython-developers/GitPython/commit/2625ed9)を追加しました。`git` 実行ファイルのバージョンは別途確認してください。受動的な調査では、ルールと範囲を限定したソースだけを読み、clone を実行しないでください。
- リポジトリを clone する CLI に対する、別ユーザーとしての sudo 許可には、別のシェル文字列インジェクション経路がある場合があります。呼び出し元が選んだリポジトリ引数が、安全に引数分割されずに Node.js の [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) や他のシェルコマンド生成処理に渡るかを追跡してください。Node の `exec` はコマンド文字列をシェルに渡します。正確な RunAs ユーザー、許可されたサブコマンドと引数、インストール済みラッパーのコード、入力検証を確認してください。リポジトリツールの名前や無制限の sudo ルールだけでは、コマンドインジェクションの証明になりません。列挙中に特権 clone を実行せず、ラッパーを調査してください。
- root 所有のカスタムラッパーは、そのバイナリーやスクリプトが書き込み不可でも、権限の低いユーザーが変更できるフラグ、ローカル API の値、サービス状態に応じて特権操作を実行するかどうかを決めている場合があり、安全とは限りません。各判定の入力と認可チェックまでたどってください。列挙中は運用状態を変更せず、設定と権限を確認してください。ラッパー内の `systemd-run` 呼び出しは、その判定に影響を与えられる場合にのみ関係します。
- sudo で root として実行できるバックアップクライアントは、呼び出し元が選んだ設定ファイル（例：`npbackup-cli -c`）を受け入れる場合があります。正確な実行ユーザーと許可された引数を確認し、呼び出し元が設定パス、バックアップ元パス、リポジトリや読み取り／復元オプションを制御できるかを調べてください。読み取り可能な設定に暗号化されたリポジトリの秘密情報があれば、クライアントが利用できる場合があります。ただし、ルールだけではリポジトリへのアクセスや root ファイルの漏えいは証明されません。バックアップを実行したり内容をダンプしたりせずに、認可を確認してください。
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) は `--password-command` に対応しており、リポジトリのパスワードを取得するプログラムを呼び出します。sudo ルールが、権限の低いユーザーに対して、root として実行する restic のパスワードコマンドとパスワードが必要なサブコマンドを選択可能にするなら、そのヘルパーが root として実行される可能性があります。正確な sudo 引数と除外設定を確認してください。条件を列挙するだけのために、ヘルパーやバックアップコマンドを実行しないでください。
- root 権限で `restic backup` を実行できる許可は、sudo の引数パターンで、呼び出し元がソースと、後から読み取り・復号できるリポジトリの両方を選択できる場合、ファイル読み取りの境界も越える可能性があります。[sudoers の引数ワイルドカードは空白とスラッシュにマッチする場合があります](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)。そのため、固定のリポジトリプレフィックスがソースを制限すると決めつけず、末尾のワイルドカードを確認してください。[Restic はローカルおよびリモートのリポジトリにバックアップできます](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)。ただし、ローカルリポジトリには書き込まれたばかりの root 専用オブジェクトが含まれる場合があります。漏えいとみなす前に、実効 sudo ポリシー、バックエンドへのアクセス、リポジトリのパスワード、生成されるオブジェクトの権限を確認してください。バックアップされた SSH 鍵でアクセスできるのは、接続先アカウントがその鍵を受け入れる場合だけです。受動的な確認中にバックアップを実行しないでください。
- 無制限のカスタム保守・バックアップコマンドは、出力パスを受け入れたり、独自のジョブスケジューラーを提供したりする場合があります。ファイル書き込みの経路では、正確な sudo ルールと実行ユーザーを確認し、データと宛先の両方を呼び出し元が制御するか調べてください。スケジュールされたコマンドの経路では、スケジューラーの実行 ID、コマンド入力、追加のパスワードまたは認可チェックを確認してください。コマンド名や `NOPASSWD` だけでは、どちらの経路も証明できません。[root 所有ファイルへの書き込み](../interesting-files-permissions/write-to-root.md)と[cron および systemd timer](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md)を参照してください。
- 固定の sudo コマンドでも、共有された書き込み可能ディレクトリから予測可能な設定ファイルを読み込む場合があります。呼び出し元がそのファイルを置き換えられるか、そのファイル内の source と destination のフィールドが特権 fetch または copy を制御するかを確認してください。ローカルファイル URL から sudo の RunAs アカウントしか読めないデータを露出できる場合があります。また、呼び出し元が制御する source と保護された destination の組み合わせで、書き込み経路ができる可能性もあります。結論を出す前に、インストール済みプログラムの URL 処理、destination パスのチェック、実効 sudo ルール、出力へのアクセス可能性を確認してください。書き込み可能な `/tmp` の設定パスだけでは調査の手掛かりにすぎません。特権転送を実行せず、バイナリーとファイルのメタデータを確認してください。
- `git apply` の sudo ルールにより、RunAs アカウントが呼び出し元の制御するパッチで選択されたファイルへ書き込める場合があります。[CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh)では、コマンドが `--unsafe-paths` を受け付けない場合でも、細工したパッチでシンボリックリンクを作成し、作業ツリーの外に書き込めました。実効 sudo の引数ルール、パッチの入手元、RunAs アカウントの作業ディレクトリへのアクセス、インストール済み Git の修正またはベンダーバックポートを確認してください。`--unsafe-paths` を許可する無制限のルールは、明示的なオプションによる別のリスクです。Git のバージョンや `git apply` の許可だけでは、保護ファイルを変更できる証拠になりません。受動的な列挙中に信頼できないパッチを適用しないでください。
- root 権限で `clamscan --debug` を実行できる sudo ルールは、権限の低いユーザーが DMG イメージを渡せて、インストール済みパーサーが [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) の影響を受ける場合、読み取り境界を越える可能性があります。この脆弱性では、デバッグ出力を通じてファイル内容が漏えいする可能性がありました。許可された引数とスキャンパス、入力の制御権、実効 RunAs アカウント、エンジンの修正／バックポート、出力が呼び出し元に見えるかを確認してください。より広いルールで `--file-list`／`-f` が許可される場合、その file-list の挙動も別途確認してください。`--debug <scan-path>` に固定されたポリシーではそれらは許可されません。列挙中に細工したファイルをスキャンしたり保護された出力を表示したりせず、ポリシーとパッケージのメタデータを確認してください。
- 呼び出し元が選択した暗号化ディスクイメージを開く root 権限の sudo ルールと、生成された mapper をマウントする別のルールの組み合わせは、呼び出し元が制御するファイルをホストの mount namespace に取り込む可能性があります。両方の実効ルールと引数、イメージと mapper 名の制御権、実際のマウント先、生成されるファイルの所有者とモードを確認してください。set-user-ID による権限の移行には、アクセス可能な実行ファイル、set-user-ID を有効にするマウントオプション（`nosuid` は無効化します）、適用されるプロセスまたは MAC ポリシーも必要です。イメージを開いたりマウントしたりするだけでは、調査の手掛かりにすぎません。既存のバックアップを使う別経路を考える場合は、実際の鍵と、その中にある有用で読み取り可能な秘密情報が必要です。受動的な列挙中にイメージを開いたりマウントしたりせず、ポリシーとパスを確認してください。[cryptsetup マニュアル](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc)と[mount オプション](https://man7.org/linux/man-pages/man8/mount.8.html)を参照してください。
- root 権限でシェルまたは Python スクリプトを実行できる sudo ルールでは、スクリプトが固定ディレクトリへ移動せずに `./helper` を呼び出す場合、作業ディレクトリを確認してください。`subprocess.run` に渡される `['./helper']` のような Python リストにも、呼び出し元が作業ディレクトリを選べる同じ挙動があります。呼び出し元が書き込み可能なディレクトリを選び、そこに同じ相対名の実行ファイルを置ける場合があります。スクリプト内の別の場所で絶対パスを使っていても、この呼び出しは保護されません。コード実行とみなす前に、実効 sudo ルール、`runchdir` などのディレクトリ変更ポリシー、スクリプトの処理と分岐に到達する条件、書き込み可能かつ実行可能なディレクトリ、マウント／`NOEXEC` の制限を確認してください。スクリプトが読み取り不可なら、認可された方法でソースを確認するまで挙動は不明です。スクリプトを静的に調べ、helper は実行しないでください。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)には作業ディレクトリのポリシーが記載されています。
- root 権限で実行できる固定の Python バリデーターでも、呼び出し元が選んだデータファイルを評価する場合があります。[Python の `eval()` ドキュメントは、信頼できない入力に対する使用を警告しています](https://docs.python.org/3/library/functions.html#eval)。入力のサフィックスチェック、算術式のプレフィックス、検証分岐があっても、残りの式が `eval` に渡るならサンドボックスにはなりません。実行経路と判断する前に、実効 sudo ルール、呼び出し元が対象ファイルを選択・制御できるか、パーサーの分岐条件と式の構築方法、特権プロセスの ID を確認してください。読み取り可能なスクリプト内に `eval` があるだけでは調査の手掛かりにすぎません。列挙中にバリデーターを実行したり、テスト用の式を渡したりせず、ソースとファイルの権限を確認してください。
- root 権限の sudo Ruby ラッパーが `YAML.load(File.read("dependencies.yml"))` のような相対 YAML ファイル名を読む場合、ラッパーまたは sudo ポリシーで作業ディレクトリを固定しない限り、呼び出し元の作業ディレクトリから入力を読み込む可能性があります。正確に許可される引数、ディレクトリとファイルの権限、インストール済み Psych の挙動を確認してください。古い `YAML.load` 実装では任意の Ruby オブジェクトをデシリアライズできましたが、新しいリリースではデフォルトでクラスが制限されています。静的な呼び出し箇所は調査の手掛かりにすぎません。ファイルが実際に呼び出し元の書き込み可能なディレクトリから読み込まれ、インストール済みローダーが危険なクラスを受け入れることを確認してください。信頼できない入力には、明示的で最小限のクラス allowlist を指定した `safe_load` を推奨します。[Ruby 3.0 Psych のドキュメント](https://docs.ruby-lang.org/en/3.0/Psych.html)と[Ruby 3.1 Psych のドキュメント](https://ruby-doc.org/core-3.1.2/Psych.html)を参照してください。

- root 権限で `sudo go run /absolute/file.go` を実行できる正確なルールでは、Go ソースが相対 WASM ファイルを読み取り、その結果を調べた後に相対シェルスクリプトを実行する可能性がある場合、作業ディレクトリを確認してください。実効 RunAs、コマンド引数と拒否設定、呼び出し元が書き込み可能なカレントディレクトリ、WASM から分岐へのデータフロー、その分岐が helper を呼び出すかを確認してください。固定の sudo `runchdir`、`os.Chdir`、または [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) によって、検索場所が変わる場合があります。静的に関連箇所が共存しているだけでは候補にすぎません。Go、WASM、helper を実行せずにソースを確認してください。
- `sudoedit` と引数ワイルドカードでは、正確なバージョンとルールの確認が必要です。[チェックリスト](linux-privilege-escalation-checklist.md)には sudoedit のファイル編集に関する問題が記載されています。別ユーザーを対象とするワイルドカードパスの `sudoedit` 許可では、実効 `sudoedit_follow` または `FOLLOW` 設定、`sudoedit_checkdir`、解決された対象、各親エントリーを誰が置き換えられるかを確認してください。前者はシンボリックリンクの追跡を許可する場合があり、後者を無効にすると書き込み可能ディレクトリのチェックがなくなります。ただし、どちらの設定だけでも他ユーザーのファイルへの書き込みが成立するとは限りません。結論を出す前に、インストール済み sudo ポリシーと、実際にマッチする引数を確認してください。[sudoers のオプション定義](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)を参照してください。
- sudoers のコマンドルールでは、引数のワイルドカードが空白にもパス文字にもマッチする場合があります。読み取り可能なコマンドに `/restricted/*` のような引数が指定されていると、マッチするプレフィックスの後に別のファイル引数を追加できる可能性があります。正確な実行ユーザー、コマンドパス、引数パターン、その後の拒否設定を確認してください。ファイル読み取りが実証されても、コマンド実行ができるとは限りません。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)には、引数の glob とコマンドパスの glob の違いが記載されています。
- パスに見える引数 glob が `../` にマッチする場合もあります。たとえば、root 権限で `node /opt/scripts/*.js` を実行できるルールでは、指定されたパスが `/opt/scripts/` で始まり、親ディレクトリをたどって解決される場合、呼び出し元が `/opt/scripts` の外にある JavaScript ファイルを指定できる可能性があります。これは**引数**の glob です。Node 実行ファイルに対するコマンドパスの glob には異なるスラッシュのマッチ規則があります。コード実行と判断する前に、実効ルール、その後の拒否設定、パス解決、対象ファイルの制御権、sudoers の正規表現または digest の制限を確認してください。[sudoers のワイルドカード規則](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)と[Node のコマンドラインに関するドキュメント](https://nodejs.org/api/cli.html)を参照してください。
- アーカイバーやその他のユーティリティには実行フックがある場合があります。シェルやインタープリターだけがコマンドを実行すると決めつけず、許可された正確な引数を[GTFOBins](https://gtfobins.github.io/)で確認してください。
- root 権限で `qpdf` を無制限に実行できるルールでは、PDF の添付ファイルを介して特権ファイルが露出する可能性があります。qpdf 10.2 以降は、出力 PDF とともに `--empty` および `--add-attachment file ... --` に対応しています。特権プロセスが選択されたソースを読み取れ、呼び出し元がアクセスできるパスに PDF を書き込める場合、その出力にソースのバイト列が含まれる可能性があります。ファイル漏えいが可能と判断する前に、実効 sudo 引数と除外設定、qpdf のバージョン、ソースへのアクセス、出力パスを確認してください。root の SSH 鍵を読み取れても、その鍵が有効で、root の SSH 認証が許可されている場合にのみログインに役立ちます。[qpdf の添付ファイルオプション](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments)を参照してください。
- sudo のタイムスタンプ再利用は、キャッシュポリシー、所有ユーザー、端末／セッション、権限に依存します。[権限昇格ガイド](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens)で確認事項を説明しています。
- `doas` には独自のルールと設定があります。[doas のセクション](../linux-basics/linux-privilege-escalation/README.md#doas)に記載されているように、許可コマンドと書き込み可能な設定パスを確認してください。

### sudo で実行するビルドおよびパッケージツール

Foundry の `forge` を sudo で無制限に実行できる許可は、RunAs ID が root 以外のユーザーでも問題になる場合があります。`--use` などのコンパイラーオプションでローカル実行ファイルを選択でき、`forge flatten -o` で出力ファイルを指定できます。この許可を悪用可能と判断する前に、インストール済み Forge のバージョン、正確な sudo 引数、アクセス可能なプロジェクトとコンパイラーパス、出力権限、実効環境を確認してください。`PATH` から見つかる相対 helper 実行ファイルは、バージョンと環境に依存する経路であり、すべての Forge ビルドで必ず使えるものではありません。<sup>[[23]](#references)[[24]](#references)</sup>

root 権限で `pacman` を無制限に実行できる許可では、パッケージの照会以外も可能です。`-U` はローカルパッケージを受け入れ、パッケージにはインストールスクリプトを含められます。また `--hookdir` で別のフックディレクトリを指定できます。テストする前に、実効 sudo ルール、引数の制限と除外設定を確認してください。受動的な列挙では、パッケージのインストールやフックの実行は不要です。<sup>[[25]](#references)[[26]](#references)</sup>

固定の sudo シェルラッパーは、名前を指定した npm 依存パッケージをインストールしてから Node アプリケーションを起動する場合もあります。正確な RunAs ルール、パッケージがすでにインストール済みか、実効 `HOME` と npm の `userconfig`、プロジェクト設定またはコマンドライン上書き、権限の低いユーザーがその名前で取得されるレジストリやパッケージを制御するかを確認してください。[npm のドキュメント](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/)には、ユーザー単位およびプロジェクト単位での `.npmrc` の検索方法が記載されています。sudo の `HOME` の扱いは、インストール済みポリシーとディストリビューションによって異なるため、特権 npm プロセスが書き込み可能なユーザーの `.npmrc` を読むとは限りません。新しくインストールされたパッケージが特権アプリケーションから import されるなら、そのモジュールコードはアプリケーションの ID で実行される可能性があります。インストール時スクリプトは、バージョンと設定に依存する別の経路です。[npm のドキュメント](https://docs.npmjs.com/cli/v6/using-npm/scripts/)には、そのライフサイクルとユーザーの扱いが記載されています。`.npmrc` のパスや `npm install` の行だけでは調査の手掛かりにすぎません。受動的な列挙中にインストールやアプリケーションの起動をせず、ルール、短いラッパー、設定パス、パッケージの出所を確認してください。

root 権限で `pip` または `pip3 download` を実行できるルールも、呼び出し元が信頼できない source distribution を選択できる引数を許可している場合、パッケージビルドの調査対象になります。URL パターンがローカルサービスと `.tar.gz` サフィックスに制限されていても同様です。`pip download` はアーカイブ URL を受け入れてパッケージのメタデータを解決します。sdist の準備時に、アーカイブが保存される前にビルドバックエンドや旧式の `setup.py` コードが実行されることがあります。正確な sudo RunAs と引数ルール、呼び出し元が選択したアーカイブを公開または置換できるか、その pip バージョンが実際にメタデータを準備するかを確認してください。信頼された固定アーカイブや wheel だけでは、この経路の証明になりません。受動的な列挙中に信頼できないパッケージを取得またはビルドしないでください。pip の[download コマンド](https://pip.pypa.io/en/stable/cli/pip_download/)、[ビルドシステムのインターフェース](https://pip.pypa.io/en/stable/reference/build-system/)、[セキュアなインストールのガイダンス](https://pip.pypa.io/en/stable/topics/secure-installs/)を参照してください。

呼び出し元が選んだローカルプロジェクトのパスを指定して `pip install` を実行できる sudo ルールには、より直接的なビルド境界があります。[pip はローカルのプロジェクトディレクトリを受け入れ](https://pip.pypa.io/en/stable/topics/local-project-installs/)、そのビルドシステムを呼び出します。[ビルドバックエンドはプロジェクトが制御するビルドフックを実行します](https://pip.pypa.io/en/stable/reference/build-system/)。このルールを特権コード実行とみなす前に、実効 RunAs ID、正確な引数の制限と拒否設定、選択されたプロジェクトの制御権、インストール済み pip／バックエンドの挙動を確認してください。信頼できる固定プロジェクトや、呼び出し元が選ぶパスを許可しないルールでは、この経路は成立しません。受動的な列挙中にパッケージをインストールせず、ルールとプロジェクトのメタデータを確認してください。

root 権限で `easy_install` を無制限に実行できる許可も、関連するレガシーパッケージビルドの調査対象です。[Setuptools のドキュメント](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html)によると、Easy Install はローカルのプロジェクトディレクトリを受け入れて source distribution をビルドします。呼び出し元が制御するプロジェクトは、そのビルド中に sudo の ID で `setup.py` を実行する可能性があります。実効 RunAs アカウント、正確なコマンドと引数の制限（後続の拒否設定を含む）、選択されたプロジェクトの制御権、インストール済みツールの挙動を確認してください。信頼できる固定プロジェクトや、呼び出し元が source を選べないポリシーでは、この経路は成立しません。列挙中にパッケージをインストールせず、ルールとプロジェクトのメタデータを確認してください。

呼び出し元が選択した URL を使って `setuptools.package_index.PackageIndex.download` を呼び出す sudo 許可 Python ラッパーは、`pip download` とは別の調査対象です。[setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf)によると、78.1.1 より前の影響を受けるリリースでは、URL から生成したファイル名が意図したダウンロードディレクトリから逸脱し、プロセスの権限で書き込む可能性がありました。実効 sudo RunAs と引数ルール、ラッパーが呼び出し元の URL をこの API に渡すこと、インストール済みビルドまたはベンダーバックポート、生成されたパスの解決先を確認してください。バージョン文字列や書き込み可能なダウンロードディレクトリだけでは、任意の書き込みが可能とは言えません。列挙中に URL を取得したりファイルを書き込んだりせず、短いラッパーとパッケージのメタデータを確認してください。

呼び出し元が選んだ `.spec` ファイルを PyInstaller に渡す sudo 許可のビルドラッパーにも、同じ信頼境界の確認が必要です。PyInstaller の spec は**ビルド時に**評価される実行可能な Python であり、その `datas` エントリーでビルド ID が読み取り可能なファイルを成果物に含められます。正確な RunAs ユーザー、sudo の引数と拒否ルール、ラッパーのパス処理と分岐、選択された spec ファイルの制御権、生成された成果物へのアクセスを確認してください。`.py` 入力を許可していることや PyInstaller がインストールされていることだけでは、spec ファイルの制御権や特権実行の証拠になりません。受動的な調査では、範囲を限定したラッパーファイルとメタデータだけを読み、ビルドは実行しないでください。[PyInstaller の spec ファイルに関するドキュメント](https://pyinstaller.org/en/stable/spec-files.html)を参照してください。

### sudo で実行する preset／plugin loader

呼び出し元が preset や plugin のディレクトリを選択できる Python ツールは、sudo によって与えられた権限でコードを import する場合があります。たとえば BBOT は `-p` で preset を受け入れます。また、その[カスタムモジュールに関するドキュメント](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations)では、追加の Python モジュールディレクトリを選択する `module_dirs` エントリーが説明されています。実効 sudo ルールで呼び出し元が選択した preset が許可され、呼び出し元が選択されたディレクトリ内のモジュールを制御できる場合、ツールが無効なモジュールを拒否する前に、特権ユーザーとしてコードが実行される可能性があります。列挙中にモジュールを読み込まず、インストール済みバージョン、正確な sudo の実行ユーザーと引数ポリシー、preset とモジュールのパスの所有者を確認してください。

### sudo で実行する Backdrop コマンドラインツール

[Bee](https://github.com/backdrop-contrib/bee) は Backdrop CMS 用の PHP コマンドラインツールです。その `eval`（`php-eval`）および `php-script` コマンドは、呼び出し元が指定した PHP を実行できます。したがって、引数に制限のない状態で Bee 実行ファイルを root として許可する sudo ルールは、Bee が Backdrop のインストール環境を初期化できる場合、root のコード実行につながる可能性があります。サイトのディレクトリから実行するか、グローバルな `--root=<directory>` オプションでサイトを選択してください。Bee や Backdrop の `settings.php` ファイルが見つかっただけでは、sudo 許可、利用可能なサイト、初期化の成功の証拠になりません。テストする前に、実効 sudo ルール、コマンドの除外設定、実行ファイルの ID、サイトへのアクセスを確認してください。受動的な列挙では Bee を実行せず、ルールとファイルパスを調べてください。PHP コマンドの追加については[Bee のコマンド変更履歴](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md)を参照してください。

### sudo で実行するターミナルサーバー

`mosh-server` は、呼び出し元のユーザーとして対話型ターミナルサーバーを起動します。高い UDP ポートとセッションキーを選択し、その両方を呼び出し元に通知します。また、クライアントが接続すると、通常はそのユーザーのログインシェルを起動します。そのため、サーバーコマンド自体が detach する場合でも、root 権限で `mosh-server` を無制限に実行できる sudo 許可は、シェル実行の調査対象になります。実効 RunAs ID、許可される引数と除外設定、インストール済みバイナリー、シェル、クライアントの有無、UDP アクセスを確認してください。受動的な列挙では、サーバーを起動したり稼働中のセッションキーを表示したりせず、sudo ルールを調べてください。[Mosh サーバーのマニュアル](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html)と[上流の設計メモ](https://github.com/mobile-shell/mosh#how-it-works)を参照してください。

### 呼び出し元のタスクファイルを書き換える特権バックアップラッパー

root として実行されるシェルラッパーが、呼び出し元の選択したタスクファイルを受け取り、source パスから `../` を削除し、各結果が許可されたディレクトリから始まることを確認してタスクファイルを書き換え、その後バックアッププログラムに*パス名*を渡す場合があります。完全に正規化した後の変換済みパスを確認してください。文字列を1回置換しただけでは、新たな traversal シーケンスが生じ、字句的なプレフィックスチェックを通過する可能性があります。また、バックアッププログラムが変換済みのメモリー上のデータを読むのか、ファイルを再度開くのかを確認してください。ファイルを再度開く場合、書き換えに失敗すると元の入力がそのまま残る可能性があります。

Linux では、`fs.protected_regular` によって、world-writable で sticky なディレクトリ内にある他ユーザーの通常ファイルへの `O_CREAT` 書き込みが拒否される場合があります。この拒否は保護策ですが、書き込みエラーを無視するシェルラッパーは、元のタスクファイルを使って処理を続ける可能性があります。この設定、ファイルの所有者とディレクトリ、書き込み失敗時にラッパーが停止するかを確認してください。このパスがファイル漏えいの候補となるのは、実効 sudo ルールが特権ユーザーとしてラッパーを許可し、呼び出し元がタスク入力と読み取り可能なバックアップ先を制御し、バックアップユーティリティが保護対象の source を実際に含める場合だけです。列挙中にバックアップを実行せず、これらの条件を調べてください。

### 特権パケットツールの引数ワイルドカード

`tcpdump` の sudo ルールでは、**引数パターン**の `*` が空白やスラッシュにマッチする場合があるため、パス名に見える制限でも追加のオプション文字列を許可する可能性があります。これは、コマンド実行ファイルのパスにあるワイルドカードとは異なります。RunAs ルール全体と、その後の拒否設定を確認してください。オプションを挿入できる場合、許可された呼び出しとインストール済み [`tcpdump` のオプション仕様](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in)によって、`-F`、`-V`、`-r`、`-w`、`-Z` が有用な読み取り／書き込み手段になるかが決まります。`-V` が読み取るのはキャプチャファイル名の一覧であり、任意の一般ファイルをダンプするものではありません。sudo でコマンドが許可されていても、AppArmor や別の MAC ポリシーがファイルアクセスを拒否する場合があります。プロファイルファイルがディスク上にあるだけでは、ロード済みまたは強制適用中とは限りません。結論を出す前に、認可とポリシーを受動的に確認してください。[sudoers マニュアル](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf)にはワイルドカードの違いが記載されています。

引数制限なしで `tcpdump` 実行ファイルのみを記載した root 権限の sudo ルールも確認が必要です。[tcpdump マニュアル](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in)によると、`-C` または `-G` で保存済みキャプチャをローテーションする場合、`-z` はローテーション後のコマンドとして実行されます。`-Z` やコンパイル時のデフォルトで、そのコマンドの実行前に権限が落とされる場合があります。このルールを権限昇格の経路とみなす前に、実効 sudo ルール、インストール済みビルド、権限降格の挙動、ローテーションが発生し得るかを確認してください。強調表示されたルールは候補であって、root コマンド実行の証拠ではありません。

### sudo で実行する Nmap ラッパー

sudo で許可された `nmap` のパスがシェルラッパーの場合、許可されたパスと転送するすべてのオプションを確認してください。よく知られた `--script` の表記をブロックしても、NSE コードの読み込みを完全には防げない場合があります。Nmap の [`--datadir`](https://nmap.org/book/man-misc-options.html) はデータファイルを選択し、NSE が有効な場合、NSE は選択されたデータディレクトリから [`nse_main.lua` を読み込みます](https://nmap.org/book/nse-implementation.html)。インストール済みビルドによっては別の長形式オプション表記も受け入れるため、そのバイナリーの実際のパーサーと制限を照合してください。[`--excludefile`](https://nmap.org/book/man-target-specification.html) は別のファイル読み取り面です。パーサーエラーからテキストが漏えいする可能性もあります。列挙中にスキャンを実行せず、実効 sudo ルール、ラッパーのロジック、Nmap のバージョン、ディレクトリの制御権、MAC ポリシーを確認してください。

### sudo で実行する Mercurial の pull hook

固定の source を指定した `sudo hg pull /fixed/source` でも、`-R` で固定しない限り、**受信側**リポジトリはカレントディレクトリによって選択されます。呼び出し元が制御する受信側リポジトリは `.hg/hgrc` にフックを定義でき、そのフックは sudo の RunAs ユーザーとして実行される場合があります。[Mercurial は、信頼できないユーザーまたはグループが所有するリポジトリ設定を無視します](https://mercurial-scm.org/help/topics/config)。この経路をコード実行とみなす前に、RunAs アカウントの信頼済みユーザー／グループと正確な作業ディレクトリを確認してください。受動的な調査ではポリシーと設定を読むだけで十分です。列挙のために pull を実行したりフックを起動したりしないでください。

### sudo で実行する Git pull hook

root 権限で `sudo git pull` を実行できる正確な許可では、作業ディレクトリで選択される**受信側**リポジトリも確認してください。呼び出し元が所有するリポジトリに実行可能な `post-merge` hook がある場合、pull が実際に正常な merge を行うと Git プロセスの ID で実行される可能性があります。[Git のドキュメント](https://git-scm.com/docs/githooks)と[pull における merge と rebase の挙動](https://git-scm.com/docs/git-pull)を確認してください。実効 sudo ルールと CWD、アクティブな hook のパスと権限、新しいコミットを含む merge に到達できるかを確認します。失敗した pull、何も変更しない pull、rebase のみの pull では、この hook の経路は成立しません。特権 pull を実行せず、ポリシーとリポジトリのメタデータを確認してください。

### sudo で実行する rsync のアーカイブコピー

`sudo rsync -a ... /writable/source/* /fixed/destination/` では、**sudoers の引数パターン**に含まれる `*` が空白にマッチし、source と destination の間に追加オプションを許可する場合があります。これはシェルによるファイル名の展開とは別の挙動です。呼び出し元が source の内容を用意でき、特権 rsync プロセスが destination に書き込める場合、[`--chown`](https://download.samba.org/pub/rsync/rsync.1) で特権所有者を指定できます。アーカイブモードでは権限ビットが保持されるため、所有者が変更された SetUID ファイルが作られる可能性があります。正確な[sudoers のワイルドカード仕様](https://man7.org/linux/man-pages/man5/sudoers.5.html)、rsync のバージョン、後続の拒否設定、ファイルシステムの `nosuid`、MAC ポリシーを確認してください。ルールにマッチすることは調査の候補であり、権限昇格の成功を示す証拠ではありません。

### sudo で実行するパケットフィルターのルール出力

`iptables` と `iptables-save`（または対応する `ip6tables` のペア）の両方を root 権限で無制限に実行できる許可は、ファイル書き込みの観点から確認する必要があります。`comment` match は呼び出し元が選んだルールテキストを受け入れ、`iptables-save -f` はシリアライズされたルールセットを指定されたパスに書き込みます。<sup>[[20]](#references)[[21]](#references)</sup>有用な payload になるかどうかは、インストール済みバックエンドがコメントをどうシリアライズするか、出力先ファイルがエクスポート内の他の行を受け入れるかに依存します。`iptables-save` だけで任意の選択内容を書き込めるわけではありません。正確な sudo RunAs ID、引数と除外設定、利用可能な match 拡張、バックエンド、出力先の権限を確認してください。列挙中はファイアウォールルールを変更したりファイルを書き込んだりせず、許可を調べてください。

### 特権で動作する Below のログディレクトリ

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) は、world-writable な `/var/log/below` ディレクトリを作成する、0.9.0 より前の Below に影響しました。サービスや許可された sudo コマンドが影響を受けるビルドを root として実行する場合、sticky bit のないログディレクトリに書き込み・検索できるユーザーが、特権プロセスによるオープン前にログエントリーをシンボリックリンクへ置き換えられる可能性があります。インストール済みパッケージの修正状況、正確な特権実行経路、実効ディレクトリアクセス、sticky bit と ACL、`/var/log/below/error_root.log` のメタデータを確認してください。world-writable なパスや sudo ルールだけでは、連鎖全体は成立しません。sticky directory やベンダーバックポートがあれば評価は変わります。受動的な列挙ではメタデータのみを確認し、リンクの作成や特権プログラムの実行は不要です。

### 書き込み可能な入力から特権でサポートバンドルを収集する場合

sudo で許可されたサポートプロファイルスクリプトは、root として固定のログパスを読み取り、その内容をプロファイルアーカイブへコピーする場合があります。実際のスクリプトがファイルを読み取るか確認し、呼び出し元が source パスや親ディレクトリのエントリーをシンボリックリンクに置き換えられるかを調べてください。特権読み取りがリンクをたどり、生成されたアーカイブを呼び出し元が読み取れる場合、保護対象のファイルが漏えいする可能性があります。sudo 許可、書き込み可能な source パス、特権読み取り、読み取り可能な出力のすべてが必要です。書き込み可能なログやプロファイルのファイル名だけでは不十分です。列挙中にファイルを置き換えたりプロファイルを生成したりせず、実効権限とリンクのメタデータを確認してください。[Nagios XI のサポートガイダンス](https://support.nagios.com/forum/viewtopic.php?t=62758)には、root として実行するプロファイルスクリプトと出力アーカイブが説明されています。こうしたバンドルの入力と出力を制限すべき理由の例です。

### root として実行する Python アーカイブ復元スクリプト

Python の復元スクリプトに対する範囲の狭い sudo ルールでも、アーカイブ入力を調べる必要があります。呼び出し元がアーカイブを選択または置換でき、スクリプトが root として `tarfile.extractall(filter="data")` で展開する場合、そのフィルターを信頼する前にインタープリターのセキュリティ更新を確認してください。CPython は CVE-2025-4517 を含む、シンボリックリンクおよびハードリンクを使った複数のフィルターバイパスを、3.9.23、3.10.18、3.11.13、3.12.11、3.13.4 で修正しました。ディストリビューションによるバックポートで以前のバージョンが修正されている場合もあるため、表示されるインタープリターのバージョンだけでは影響の有無を判断できません。<sup>[[16]](#references)[[17]](#references)</sup>

受動的な調査では、正確な sudo コマンドとスクリプトを読み、どの引数でアーカイブが選択されるかを追跡し、現在のユーザーがアーカイブまたはその親ディレクトリに書き込めるかを確認してください。インストール済みのベンダーパッチと展開先も別途確認します。`filter="data"` を指定しても、すべての信頼できないアーカイブが安全になるわけではありません。<sup>[[16]](#references)[[17]](#references)</sup>

### sudo で実行する機械学習モデルローダー

呼び出し元が選択した `.pt`、`.pth`、`.ckpt` ファイルを許可する sudo ルールでは、特権スクリプトがそのファイルを [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html)、`pickle.load`、または別の pickle ベースのローダーに渡す場合、確認が必要です。実効 RunAs ルール、呼び出し元がモデルを作成または置換できるか、シェルラッパーを経て Python helper に渡る実際の引数の流れを確認してください。`.pth` 拡張子は、無関係な Python の site 設定ファイルにも使われるため、拡張子だけではモデル読み込みの証拠になりません。アーカイブスキャンや静的 pickle スキャンを行っても、後の読み込みが安全であるとは言えません。ローダーの[バージョンに依存する `weights_only` の挙動](https://docs.pytorch.org/docs/stable/notes/serialization.html)と、allowlist の有無を調べてください。[ML の pickle と Fickling に関する注意事項](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md)を参照してください。受動的な列挙ではモデルを読み込んだり展開したりしないでください。

### sudo で実行する式パーサーが保存済み入力を評価する場合

root として sudo 経由で実行する固定 Python スクリプトでも、権限の低いユーザーがアプリケーションデータベースに保存できるテキストを評価する場合があります。TensorFlow では、`preprocess_input_exprs_arg_string(value, safe=False)` の呼び出しが `eval` 経路を選択します。[TensorFlow のアドバイザリ](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc)では、安全でないパーサーと、そのコマンドライン呼び出し元に対する修正が説明されています。アプリケーションが `safe=False` を明示して呼び出す場合、そのコマンドライン呼び出し元が修正済みでも別途確認が必要です。実効 sudo ルール、対象行を誰が変更できるか、フィルターやスコアリングによってその行が呼び出しに到達するか、インストール済み関数の挙動を確認してください。TensorFlow のバージョン、sudo 許可、ハードコードされたモデルファイルだけでは、連鎖の証拠になりません。受動的にスクリプトとデータフローを調べ、列挙中に特権 helper を実行したりテスト用の式を送ったりしないでください。

### sudo で許可された needrestart の設定

`needrestart -c` は、呼び出し元が選択した Perl 設定ファイルを読み込み、その内容を評価します。`sudo -l` で root として `needrestart` を実行でき、引数で `-c` が許可され、呼び出し元が書き込み可能な場所にある読み取り可能な設定ファイルを選べる場合、その許可は root コード実行につながる可能性があります。正確な sudo の実行ユーザーと引数ルールを確認してください。固定の引数一覧のみを許可するルールであれば、この経路は遮断される場合があります。これは needrestart のインタープリター走査に関する脆弱性とは別の問題です。パッケージを更新したり `interpscan` を無効にしたりしても、root として `-c` を無制限に実行できる許可が安全になるわけではありません。<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### 別アカウントとして実行する sudo の Python import

固定の Python エントリーポイントでも、sudo が**root 以外**のサービスユーザーとしてスクリプトを実行する場合を含め、呼び出し元が編集または置換できるモジュールを import する場合があります。`from utils import status` のようなリテラルがある場合は、ローカルの `utils/__init__.py` と `utils/status.py` に加え、パッケージディレクトリの権限も確認してください。書き込み可能なファイルが実行経路になると判断する前に、スクリプトの import パス、正確に許可された sudo 引数、該当する処理がその import に到達するかを確認してください。列挙中にスクリプトを import したり実行したりせず、ファイルと権限を調べてください。<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` に対する正確な sudo ルールには、スクリプトの読み取り権限があれば十分です。実行ビットや shebang は必要ありません。ローカルの**不足モジュール**も確認してください。スクリプトが import するモジュールのファイル名を呼び出し元が書き込み可能なスクリプトディレクトリ内に作成できる場合、Python が RunAs ID でそのファイルを読み込む可能性があります。実効 sudo ルール、インタープリターの実際の[モジュール検索パス](https://docs.python.org/3/library/sys_path_init.html)、モジュールが組み込みまたは freeze 済みか、import に到達するかを確認してください。スクリプトに対する直接の sudo ルールは、実行ビットと shebang の要件が異なります。`sudo -u account` の後に呼び出し元が指定したトークンを追加する別のラッパーでは、引数フローも確認する必要があります。そのトークンに別の `-u` があっても、結果の ID が呼び出された sudo ポリシーで許可される場合に限り重要です。静的な文字列だけでは、どちらの経路も証明されません。

### 呼び出し元が制御する設定で sudo 実行される Apache

root 権限の `apachectl`、`apache2ctl`、`httpd` を許可する sudo ルールで、呼び出し元が制御する `-f` 設定ファイルを指定できる場合、そのファイルと親ディレクトリの権限を確認してください。Apache の [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) ディレクティブは、モジュール名に続けて**モジュールのファイル名**を指定します。[`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) もファイルを読み込みます。[`Include` と `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) は設定ファイルを追加したり、エラーを通じてファイルの内容を露出させたりする場合があります。カスタムラッパーがこれらのパスを検証したり、権限を落としたり、引数を制限したりする可能性もあるため、書き込み可能な設定ファイルだけではコード実行の証拠ではなく調査候補にすぎません。結論を出す前に、パスの正規化、シンボリックリンク、ディレクティブの解析を確認してください。

### 呼び出し元が制御する設定で sudo 実行される nginx

root 権限の `nginx` を無制限に実行できるルールでは、[`-c` で別の設定を選択できる](https://nginx.org/en/docs/switches.html)場合があります。正確な sudo 引数と除外設定、呼び出し元が設定を指定できるか、その結果起動する master や worker が保護対象のパスにアクセスできるかを確認してください。選択した `root` と `autoindex` により、新しい listener を通じてファイルが露出する可能性があります。[`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) は特権ファイル書き込みの経路になり得ますが、DAV モジュールはデフォルトではビルドに含まれません。実際に含まれているか、listener に到達できるか、ファイル権限、一時ファイルの挙動を確認する必要があります。[`error_log` ディレクティブ](https://nginx.org/en/docs/ngx_core_module.html#error_log)も任意のファイルを指定できます。`/etc/ld.so.preload` のような機密設定ファイルへのログ書き込みが権限昇格の経路になるには、実効的な特権書き込み権限と、呼び出し元が制御できるログレコードが必要です。`sudo -l` で実行ファイルが強調表示されることは調査の手掛かりであり、いずれかの経路が機能する証拠ではありません。受動的な列挙では nginx を起動または再設定しないでください。

### 特権 Bash のプロンプトで行うパターン比較

sudo で許可された Bash スクリプトが呼び出し元から値を読み取り、`[[ "$expected" == $entered ]]` で確認する場合、Bash は引用符で囲まれていない右辺のオペランドをパターンとして解釈します。そのため、ワイルドカードで期待値を知らずに比較を満たせる可能性があります。オペランドを引用符で囲む（`[[ "$expected" == "$entered" ]]`）と、文字列をそのまま比較します。正確な sudo ルール、プロンプトに到達できるか、比較後にスクリプトが何をするかを確認してください。構文だけでは悪用可能な経路は成立しません。列挙中に期待値を表示しないでください。[Bash の条件式に関するリファレンス](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html)を参照してください。

### ファイルをダウンロードして実行する sudo helper

root 権限でカスタム helper を無制限に実行できる sudo 許可では、呼び出し元が選択した URL を受け取り、レスポンスをディスクに書き込み、後からインタープリターやシェルでそのファイルを実行する場合、データフローを調査してください。[sudoers では、コマンドエントリーに引数が指定されていない場合、任意の引数が許可されます](https://man7.org/linux/man-pages/man5/sudoers.5.html)。実行ファイルのパスが固定でも、引数による選択先までは制限されません。インストール済み helper での URL 検証、出力パス、成功時の分岐、その後の実行を確認してください。libcurl の import や表示可能な文字列があるだけでは、この連鎖の証拠になりません。

出力ファイル名が固定でも、helper が**呼び出し元の制御する作業ディレクトリで相対パスを使用する**場合、書き込みと実行の間にファイルを置き換えられる可能性があります。root 所有ファイルの rename や置換は、ファイルのモードだけでなく、ディレクトリへの書き込み／検索アクセスと sticky bit の制限に左右されます。[`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html)を参照してください。helper が後からパスを再度開くのか、すでに開いたファイル記述子を使うのか、書き込み前に信頼されたディレクトリへ移動するかを確認してください。受動的に sudo ポリシー、helper、ディレクトリのメタデータを調べ、列挙中に特権ダウンロードや race を実行しないでください。

root としてダウンロードする sudo helper は、`curl <caller input> -o <fixed output>` のような Bash コマンド文字列を組み立てる場合、**引数**インジェクションも招く可能性があります。空白を拒否するフィルターでも、[Bash の brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html)は残ります。引用符で囲まれていないカンマ区切りの要素が、複数の curl 引数に展開される場合があります。入力が固定の `-o` より前に curl へ渡される場合、呼び出し元が指定した出力オプションにより、helper の ID で最初の URL の出力先を選択できる可能性があります。[curl は出力オプションを URL の順序に応じて適用します](https://curl.se/docs/manpage.html#-o)。正確なシェル、引用符の扱い、入力検証、実効 sudo ルール、curl の引数順と対応する URL scheme、取得するバイト列を呼び出し元が制御できるか、結果を読み取れるかを確認してください。PyInstaller でパッケージ化された実行ファイルに Python アプリケーションのロジックが含まれる場合もありますが、パッケージ化のマーカーや `curl` という文字列だけではこのデータフローの証拠になりません。認可されている場合は、範囲を限定したオフラインのコピーを確認してください。通常の列挙では helper を実行したり、攻撃者が選んだデータを取得したりしないでください。

`mktemp -u`／`--dry-run` を呼び出す root-sudo シェルスクリプトは、未使用の名前を選ぶだけであり、ファイルは**作成しません**。[`mktemp -u`／`--dry-run` のドキュメント](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html)を参照してください。スクリプトが後から他のユーザーの影響を受けるディレクトリにその名前のファイルを作成し、再度開いて内容を root の `authorized_keys` のような保護された宛先へ追記する場合、一時ファイル race の可能性を調べてください。正確な sudo ルール、ディレクトリとファイルの所有者、作成と再オープンの順序、カーネルの保護策、特権書き込みに攻撃者が制御するバイト列が実際に使われるかを確認してください。`mktemp -u` という文字列や書き込み可能な `/tmp` だけでは race の証拠になりません。列挙中にスクリプトやパスのメタデータを確認し、スクリプトを実行したり一時ファイルを race させたりしないでください。

## 防御に関する注意事項

- インタープリターや対話型エディターを sudo で許可しないでください。<sup>[[1]](#references)</sup>
- 狭い範囲の管理操作を1つだけ行う、root 所有の固定ラッパーを優先してください。<sup>[[1]](#references)[[2]](#references)</sup>
- インタープリターが不可欠な場合は、正確なスクリプトパスを制限し、ユーザーが制御する引数、書き込み可能な import、`PYTHONPATH`、危険な環境保持を防いでください。<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- ファイル編集が必要な場合は、正確なファイルパスに制限し、修正済みバージョンの sudo と厳格な環境処理を用いた `sudoedit` を検討してください。<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`、`env_keep`、書き込み可能な作業ディレクトリ、書き込み可能なモジュール／import パス、`NOEXEC`、`use_pty`、ロギングを確認してください。ただし、これらを完全なサンドボックスとみなさないでください。<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
