## Interpretery dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interpreter jako root, traktuj to jako bezpośrednie wykonanie kodu. Interpretery służą do wykonywania dowolnego kodu, więc reguła zezwalająca na użycie `python3`, `perl`, `ruby`, `lua`, `node` lub podobnych plików binarnych jest zwykle równoważna z wykonaniem poleceń jako root, chyba że argumenty są ściśle ograniczone i weryfikowane.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Typowy proces weryfikacji: najpierw wyświetl uprawnienia użytkownika, a następnie wykonaj instrukcję Pythona za pomocą opcji `-c` interpretera.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Poniżej przedstawiono inne przykłady interpreterów; wymienione interpretery dokumentują wykonywanie kodu inline lub API procesów potomnych.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Dokładna ścieżka ma znaczenie. Jeśli reguła sudo zezwala na `/usr/bin/python3`, podczas weryfikacji użyj dokładnie tej ścieżki.<sup>[[2]](#references)</sup>

Glob dla plików wykonywalnych w sudo, taki jak `/usr/bin/python*`, może również dopuścić Python 2 dla skryptu napisanego w Pythonie 3. Jeśli skrypt wywołuje `input()` z tekstem kontrolowanym przez wywołującego, [Python 2 ewaluuje ten tekst jako wyrażenie](https://docs.python.org/2/library/functions.html#input); jawne wywołanie interpretera ma pierwszeństwo przed shebangiem skryptu. Zanim uznasz to za ścieżkę do wykonania kodu, sprawdź zainstalowane pliki binarne pasujące do wzorca, efektywne ustawienia RunAs i politykę argumentów, odmowy dostępu oraz to, czy można dotrzeć do obsługiwanego wejścia.

Stała ścieżka skryptu w regule sudo umożliwiającej działanie jako root nie ogranicza poleceń wykonywanych przez skrypt. W przypadku czytelnego wrappera Bash sprawdź, czy jego pierwsze wykonywane polecenie używa nieujętego w cudzysłowy parametru pozycyjnego, takiego jak `$1`, jako **słowa polecenia**, gdy sudo dopuszcza argumenty wybrane przez wywołującego. Potwierdź efektywną tożsamość RunAs, politykę haseł i argumentów, późniejsze odmowy oraz rzeczywistą gałąź skryptu; wynik mogą zmienić `NOEXEC`, stała bezpieczna lista argumentów lub wrapper, który weryfikuje polecenie. Podczas rekonesansu przeanalizuj krótki skrypt statycznie, zamiast uruchamiać go z testowym poleceniem.

Nieograniczona reguła sudo umożliwiająca działanie jako root dla `dotnet` również wymaga sprawdzenia interpretera. Jeśli zainstalowano .NET SDK, [`dotnet fsi` uruchamia kod F# interaktywnie lub ze skryptu](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), a [`dotnet run` wykonuje projekt na podstawie kodu źródłowego](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Najpierw potwierdź efektywną tożsamość RunAs i dokładną politykę argumentów: reguła ograniczona do konkretnego bezpiecznego podpolecenia lub zaufanej aplikacji to inne uprawnienie, a instalacja zawierająca tylko środowisko uruchomieniowe może nie udostępniać poleceń SDK. Sama nazwa pliku wykonywalnego jest wskazówką do weryfikacji, a nie dowodem możliwości wykonania kodu.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Edytory dozwolone przez sudo

Jeśli `sudo -l` pozwala użytkownikowi uruchomić interaktywny edytor jako root, traktuj go jako powierzchnię wykonywania poleceń, a nie nieszkodliwe uprawnienie do edycji plików. Edytory często mogą wykonywać polecenia powłoki, odczytywać dowolne pliki, zapisywać dowolne pliki lub wywoływać zewnętrzne narzędzia z poziomu edytora.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Typowy przebieg analizy: wyświetl uprawnienia użytkownika, a następnie uruchom każdy dozwolony edytor lub pager przez sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Wykonywanie poleceń za pomocą Nano

Jeśli `nano` można uruchomić przez sudo, z poziomu edytora może być możliwe wykonywanie poleceń.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Następnie podaj polecenie, takie jak `id` lub `/bin/sh`, w wierszu poleceń nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Jeśli interaktywna powłoka nie ma użytecznych strumieni terminala, ta forma przekierowania przypisuje jej standardowe wyjście i standardowy błąd do deskryptora 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Dokładna sekwencja klawiszy może się różnić w zależności od wersji nano i opcji kompilacji, ale problem bezpieczeństwa pozostaje ten sam: edytor działa jako root i może uruchamiać zewnętrzne polecenia.<sup>[[1]](#references)[[12]](#references)</sup>

### Inne popularne sposoby ucieczki z edytora

Edytory w stylu Vim często umożliwiają wykonywanie poleceń za pomocą `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Programy typu `less` mogą również umożliwiać uruchamianie poleceń powłoki.<sup>[[14]](#references)</sup>

Reguła sudo zezwalająca na uruchamianie `apport-cli` jako root wymaga takiego samego sprawdzenia pagera. W podatnych wersjach Apport raport o awarii mógł być otwierany w `less` z rozmiarem terminala kontrolowanym przez atakującego; pager mógł wtedy udostępnić root shell, jeśli spełnione były specjalne warunki dotyczące sudo i pagera. Przed uznaniem wersji za podatną sprawdź efektywną regułę sudo, konfigurację pagera i poprawkę w pakiecie dystrybucji. Podczas pasywnej enumeracji odczytuj metadane pakietu i polityki bez wywoływania awarii ani otwierania uprzywilejowanego raportu. [Rekord CVE Ubuntu](https://ubuntu.com/security/CVE-2023-1326) zawiera wersje pakietów z poprawkami dla poszczególnych wydań, w tym poprawki backportowane.

```text
!/bin/sh
```

## Inne zagrożenia związane z regułami sudo i doas

Zacznij od `sudo -l`, `sudo -V` i odpowiednich zasad `doas`. Analizuj łącznie dozwolone polecenie, użytkownika, w którego imieniu można je uruchomić, argumenty, środowisko i ustawienia domyślne. Uprawnienie do uruchamiania poleceń jako nie-rootowe konto usługi nadal może ujawnić pliki tego konta albo zapewnić ścieżkę do roota.

Skrypt Pythona dopuszczony przez sudo na stałe może nadal uruchomić polecenie powłoki z tożsamością RunAs, jeśli interaktywne dane wejściowe kontrolowane przez wywołującego są łączone w [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Czarna lista znaków interpunkcyjnych powłoki nie wystarcza, by uznać rozwiązanie za bezpieczne: [powłoka rozpoznaje również podstawianie poleceń `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Sprawdź, czy dozwolone argumenty trafiają do gałęzi obsługującej dane wejściowe, czy dane te docierają do polecenia powłoki bez bezpiecznej walidacji oraz czy efektywna polityka sudo dopuszcza zamierzonego użytkownika RunAs. Sama ścieżka skryptu lub wywołanie `os.system()` to jedynie trop do dalszej analizy; sprawdź kod źródłowy bez uruchamiania skryptu z podwyższonymi uprawnieniami.

Efektywne uprawnienie root przez sudo do `chattr` może usunąć atrybut niezmienności (`i`) pliku, ale samo w sobie nie daje prawa zapisu ani nowej tożsamości. [Podręcznik `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) podaje, że atrybut blokuje modyfikacje i może go zmienić tylko root lub proces z `CAP_LINUX_IMMUTABLE`. Sprawdź dokładną politykę argumentów sudo i obsługę systemu plików, a następnie osobno zweryfikuj, czy wywołujący może zapisać plik po usunięciu atrybutu oraz czy korzysta z niego podmiot o wyższej tożsamości. Na przykład podmiana powłoki logowania wymaga również zaakceptowanych poświadczeń konta docelowego i faktycznego logowania przez tę powłokę. Podczas inwentaryzacji sprawdź politykę, atrybuty plików i uprawnienia, nie zmieniając ich.

Jeśli sudo wymaga zarówno hasła, jak i jednorazowego kodu, traktuj te warunki niezależnie od uprawnień do polecenia. Odczytywalny plik `.google_authenticator` zawiera wrażliwy materiał seed, a stary hash hasła aplikacji lub bazy danych jest jedynie potencjalnym hasłem bieżącego konta; żaden z nich nie dowodzi, że drugi czynnik jest akceptowany przez efektywną konfigurację PAM. Po uzyskaniu autoryzacji sprawdź dokładnego użytkownika RunAs i argumenty: nieograniczone uprawnienie root do RubyGems `gem` może udostępnić jego polecenie edytora ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ale ograniczone uprawnienie lub nieudane uwierzytelnienie nie. Pasywna inwentaryzacja powinna odnotować ścieżki i politykę, nie wyświetlając seeda, nie odzyskując hasła, nie generując kodu ani nie uruchamiając uprzywilejowanego polecenia.

Nieograniczone uprawnienie root przez sudo do Chef `knife` wymaga analizy na poziomie interpretera: [Chef dokumentuje, że `knife exec -E` lokalnie wykonuje ciąg Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Sprawdź, czy efektywna reguła sudo zezwala na podpolecenie `exec` i dostarczony przez wywołującego argument `-E`, właściwą tożsamość RunAs oraz ewentualne pasujące odmowy poleceń lub ustalone argumenty. Zainstalowany plik binarny albo reguła ograniczona do innych podpoleceń to jedynie trop. Pasywna inwentaryzacja powinna odnotować regułę bez uruchamiania `knife`.

Dokładne uprawnienie root przez sudo do interaktywnego `msfconsole` jest równie wrażliwe: [GTFOBins opisuje jego konsolę `irb`](https://gtfobins.org/gtfobins/msfconsole/), która może odziedziczyć tożsamość sudo. Sprawdź efektywnego użytkownika RunAs, dozwoloną listę argumentów, odmowy poleceń, `NOEXEC` lub inne ograniczenia, zachowanie zainstalowanej konsoli oraz to, czy wywołujący może przekazać dane interaktywne. Samo wyróżnienie ścieżki to jedynie trop; podczas pasywnej inwentaryzacji nie uruchamiaj konsoli.

We FreeBSD nawet reguła sudo ograniczona do `pkg update` jako root oraz `pkg install *` wymaga sprawdzenia zaufania do repozytorium. Ustal, czy wywołujący może zapisywać `/etc/hosts` oraz czy *efektywna* konfiguracja włączonych repozytoriów używa hosta HTTP z `signature_type: none`. [Podręcznik FreeBSD `pkg.conf`](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) podaje, że `none` wyłącza sprawdzanie podpisów; samo `pkg+http` tego nie dowodzi. Pakiet może zawierać skrypty instalacyjne ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), więc wywołujący, który faktycznie kontroluje endpoint repozytorium i może wybrać pakiet, może przekroczyć granicę uprawnień root. Zanim wyciągniesz taki wniosek, sprawdź nadpisania repozytorium, rozwiązywanie SRV/lustr, efektywne argumenty sudo, wybór pakietu i wykonywanie skryptów. Podczas inwentaryzacji sprawdź politykę i niewielkie lokalne pliki konfiguracyjne, nie przekierowując nazw ani nie uruchamiając `pkg`.

Uprawnienie root przez sudo do `apt-get update` i `apt-get upgrade` również wymaga sprawdzenia zaufania do repozytorium, jeśli sudo zachowuje kontrolowane przez wywołującego `http_proxy`. Sprawdź, czy efektywna konfiguracja APT rzeczywiście używa tej zmiennej i na które żądania do włączonych repozytoriów może ona wpływać; sam proxy nie może zastąpić pakietów z archiwum uwierzytelnianego zaufanym kluczem podpisywania. [Podręcznik transportu HTTP APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) opisuje kolejność stosowania proxy, a [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) — sprawdzanie podpisów, nadpisania dotyczące niezaufanych repozytoriów i potwierdzanie instalacji nieuwierzytelnionych pakietów. Sprawdź dokładnego użytkownika RunAs i argumenty sudo, politykę uwierzytelniania repozytorium, wymagane interaktywne potwierdzenia oraz to, czy wybrana aktualizacja uruchamia skrypty pakietów jako root. Podczas pasywnej inspekcji sprawdź politykę i lokalną konfigurację; nie przekierowuj ruchu pakietów ani nie uruchamiaj aktualizacji.

Reguła sudo dająca uprawnienia root dla `snap install` może tworzyć granicę pakiet-kod, jeśli argumenty pozwalają wywołującemu wybrać lokalny snap i tryb instalacji o łagodnych ograniczeniach. [Dokumentacja Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) podaje, że `--dangerous` pomija sprawdzanie asercji lokalnego snapa, a `--devmode` łagodzi ograniczenia; [hook instalacyjny może zostać uruchomiony podczas pierwszej instalacji](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Zanim stwierdzisz, że możliwy jest dostęp do chronionych plików hosta, sprawdź dokładną politykę argumentów/użytkownika RunAs sudo, kto kontroluje plik snapa, czy zainstalowany snapd akceptuje te tryby oraz tożsamość i ograniczenia hooka. Sam plik binarny `snap` lub reguła wyglądająca na wieloznaczną nie dowodzą istnienia takiego łańcucha. Podczas pasywnej inwentaryzacji nie instaluj pakietu ani nie uruchamiaj jego hooka.

W przypadku dokładnego uprawnienia sudo do nirootowego, niestandardowego pliku binarnego odczytującego poświadczenia najpierw sprawdź plik i jego uprawnienia bez uruchamiania go. Wbudowana kontrola hasła może być widoczna tylko jako znaki szerokie; [GNU `strings` opisuje ekstrakcję 16-bit little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Widoczny ciąg nie dowodzi, że jest akceptowanym hasłem ani że gałąź sukcesu ujawnia aktualne poświadczenie. Osobno sprawdź działanie pliku binarnego, dostęp konta docelowego do chronionych danych, poprawność poświadczeń oraz ewentualną późniejszą zmianę konta lub grupy. Jeśli to konto należy do `docker`, sprawdź dostęp do gniazda oraz tożsamość demona — rootful lub rootless — zanim wywnioskujesz, że możliwy jest dostęp do roota hosta; [Docker opisuje konsekwencje przynależności do tej grupy na poziomie roota](https://docs.docker.com/engine/install/linux-postinstall/). Rutynowa inwentaryzacja powinna odnotować regułę sudo i członkostwo w grupach, nie uruchamiając pliku binarnego ani nie zrzucając jego ciągów.

Reguła sudo z symbolem wieloznacznym dla skryptów konserwacyjnych aplikacji wymaga sprawdzenia czegoś więcej niż ścieżki skryptu. Ustal, czy dozwolony skrypt przyjmuje nieograniczone argumenty lub odczytuje ustawienia, które może modyfikować konto aplikacji o niższych uprawnieniach, a następnie prześledź przepływ tych wartości do poleceń powłoki lub środowiska podprocesu. Na przykład ZoneMinder [`zmupdate.pl` tworzy polecenie `mysqldump` i wykonuje je przez `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), a [`zmdc.pl` kopiuje ustawienie `ZM_LD_PRELOAD` do `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) przed uruchomieniem demonów. Reguła sudo zezwalająca na uruchomienie jednego z tych skryptów jako root może przekroczyć granicę zaufania, jeśli odpowiednie dane wejściowe są kontrolowane i trafiają do tego kodu w zainstalowanej wersji. Sprawdź efektywną regułę sudo, prawa dostępu do konfiguracji aplikacji i kod źródłowy skryptu; sam symbol wieloznaczny lub ustawienie to jedynie trop, a nie dowód wykonania.

- `SETENV`, `env_keep`, `secure_path` i `LD_PRELOAD` mogą zmienić nawet wąsko ograniczone polecenie w podatne na przejęcie importu, biblioteki lub PATH. Zobacz [przewodnik po zmiennych środowiskowych](../linux-basics/linux-environment-variables.md) oraz [nadużycia SUID/linkera](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Dokładne uprawnienie root przez sudo z `SETENV` do wrappera powłoki wymaga też sprawdzenia jednokrokowej ścieżki, jeśli wrapper uruchamia ustalony skrypt Pythona z dosłownym importem. `secure_path` ogranicza wyszukiwanie poleceń przez powłokę, ale nie wyszukiwanie modułów Pythona przez [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` i `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) sprawiają, że Python ignoruje tę zmienną środowiskową. Zanim uznasz to za wykonanie kodu, sprawdź efektywne tagi i odmowy sudo, gałąź wrappera, opcje interpretera, rozwiązywanie importu oraz katalog wyszukiwania zapisywalny przez wywołującego. Krótkie skrypty sprawdzaj statycznie; nie uruchamiaj uprzywilejowanego wrappera.

Dokładne uprawnienie sudo do `neofetch ""` z możliwością działania jako root może nadal ładować konfigurację powłoki, jeśli odpowiednie ustawienia domyślne sudo zachowują kontrolowane przez wywołującego `XDG_CONFIG_HOME`. [Mechanizm ładowania konfiguracji Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) źródłuje `neofetch/config.conf` lub `neofetch/config` z tego katalogu; pusta lista argumentów nie zapobiega temu wyszukiwaniu. Sprawdź zainstalowany mechanizm ładowania, efektywnego użytkownika RunAs i politykę argumentów, ewentualne odmowy poleceń, to, czy sudo faktycznie zachowuje wybraną zmienną dla tego polecenia, oraz czy wywołujący kontroluje ścieżkę do odczytywalnego pliku konfiguracyjnego. Zachowana zmienna lub zainstalowany Neofetch to jedynie trop. Sprawdź politykę i metadane plików bez uruchamiania uprzywilejowanego polecenia ani wyświetlania zawartości konfiguracji; zobacz [obsługę środowiska przez sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Nieograniczona reguła sudo dla `facter` umożliwiająca działanie jako root wymaga osobnego sprawdzenia custom facts. [Dokumentacja Puppet](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) podaje, że `--custom-dir` ładuje pliki factów Ruby z wybranego katalogu. Sprawdź, czy dokładna reguła sudo dopuszcza tę opcję, czy zainstalowany Facter ją obsługuje i czy wywołujący kontroluje katalog. Reguła z ustalonymi argumentami, jawna odmowa polecenia lub wyłączone custom facts mogą zmienić rezultat. Pasywna inwentaryzacja powinna odnotować potencjalną regułę bez uruchamiania Facter ani odczytywania zawartości factów.

W przypadku dokładnego uprawnienia sudo do skryptu działającego jako root z `SETENV` sprawdź niekwalifikowane nazwy poleceń, takie jak `find`, oraz efektywne `PATH` po zastosowaniu polityki sudo i inicjalizacji skryptu. Plik źródłowy Bash może również uruchomić `enable -n [`: [Bash następnie szuka w `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) zewnętrznego `[` używanego później przez skrypt. Sprawdź odpowiednie [reguły środowiska sudoers i `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), ewentualne wpisy `NOSETENV`/`NOEXEC` lub odmowy, przepływ skryptu i plików źródłowych oraz katalog wyszukiwania, w którym wywołujący może umieścić plik wykonywalny. Odczytywalny skrypt zawierający niekwalifikowane polecenie to jedynie trop, a nie dowód uprzywilejowanego wykonania; sprawdź go bez uruchamiania reguły sudo.
- Uprzywilejowany skrypt pobierający stały URL przez `curl` może nadal przyjmować odpowiedź wybraną przez wywołującego, jeśli odpowiednia reguła sudo zachowuje `http_proxy`, a żądanie jest wysyłane przez ten serwer proxy. Jeśli skrypt następnie przekazuje odpowiedź parserowi XML rozwiązującemu encje zewnętrzne, złośliwa odpowiedź może ujawnić pliki odczytywalne przez uprzywilejowany proces. Sprawdź dokładną politykę środowiska sudo, wykluczenia `no_proxy`, żądany URL, konfigurację parsera i miejsce docelowe danych wyjściowych; sama zmienna proxy lub parser XML nie stanowią podatności. Dokumentacja [zmiennych środowiskowych proxy w curl](https://everything.curl.dev/usingcurl/proxies/env.html) opisuje działanie tych zmiennych. Podczas pasywnej inwentaryzacji nie wysyłaj żądań sieciowych ani nie parsuj złośliwego XML.
- Skrypt sudo działający jako root, który tworzy plik PostScript na podstawie danych kontrolowanych przez wywołującego, a następnie uruchamia `ps2pdf -dNOSAFER`, wymaga osobnej analizy przepływu danych wejściowych. Ghostscript dokumentuje, że ta flaga wyłącza SAFER do chwili wywołania `.setsafe`, umożliwiając operacje na plikach w granicach uprawnień procesu systemu operacyjnego. Zapytanie SQL zbudowane z argumentu wywołującego może przekazać kontrolowane przez atakującego wiersze do szablonu PostScript, ale sam ciąg zapytania lub wywołanie `ps2pdf` nie dowodzą, że dane trafiają do wykonywalnej składni PostScript. Sprawdź efektywną regułę sudo, dokładną ścieżkę od danych wejściowych do szablonu, ewentualne escapowanie, zachowanie zainstalowanego Ghostscript oraz to, czy SAFER jest ponownie włączane przed interpretacją dokumentu. Podczas pasywnej inwentaryzacji nie uruchamiaj uprzywilejowanej konwersji. Zobacz [dokumentację Ghostscript dotyczącą `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- W przypadku reguły sudo uruchamiającej skrypt powłoki porównaj zachowywane zmienne ze skryptem. Konstrukcja taka jak `if $CHECK_CONTENT; then` uruchamia rozwiniętą wartość jako polecenie, więc zachowanie `CHECK_CONTENT` może umożliwić wykonanie polecenia nawet przy ustalonej ścieżce skryptu i argumentach. Dla konkretnej reguły trzeba sprawdzić, czy ta gałąź jest osiągalna i czy zmienna rzeczywiście zostaje zachowana.<sup>[[2]](#references)[[22]](#references)</sup>
- Skrypt Pythona dopuszczony przez sudo może importować kod z katalogu zapisywalnego przez wywołującego lub z buforowanego pliku `.pyc`. Przypadek bufora opisano w [przewodniku po eskalacji uprawnień](../linux-basics/linux-privilege-escalation/README.md).
- Ustalony skrypt Pythona dopuszczony do uruchomienia jako root może nadal udostępniać interaktywny debugger. Wywołania takie jak `pdb.set_trace()` lub `pdb.post_mortem()` umożliwiają wykonywanie instrukcji Pythona w kontekście debugowanego procesu, jeśli wywołujący może dotrzeć do punktu przerwania lub obsługi wyjątku **i kontroluje strumień wejściowy debuggera**. Sprawdź dokładną regułę sudo RunAs, uwierzytelnianie i warunki gałęzi, osiągalność wyjątku, własność terminala/wejścia oraz to, czy debugger działa w tym samym uprzywilejowanym procesie. Żądanie gniazda wywołujące wyjątek samo w sobie nie daje dostępu do debuggera podłączonego do innego terminala. [Python opisuje ewaluację instrukcji przez debugger i tryb post-mortem](https://docs.python.org/3/library/pdb.html); sprawdź skrypt statycznie, zamiast podczas inwentaryzacji wywoływać uprzywilejowaną obsługę.
- Skrypt Pythona dopuszczony przez sudo może odczytać pole profilu z bazy danych lub gniazda Unix i dołączyć je do ciągu, który później staje się **ciągiem formatującym** dla `str.format()`. [Pola zastępcze mogą odwoływać się do atrybutów i kluczy mapowania](https://docs.python.org/3/library/string.html#format-string-syntax), więc pole kontrolowane przez atakującego może sprawdzać obiekty przekazane do `format()` i ujawnić dostępne z nich dane, jeśli wynik zostanie wyświetlony lub zapisany w miejscu odczytywalnym przez wywołującego. Sprawdź efektywną tożsamość RunAs sudo, prawo zapisu do konkretnego rekordu, przepływ danych do ciągu formatującego, przekazywane obiekty oraz widoczność wyników. Nie oznacza to automatycznie wykonania kodu; dosłowny, zaufany ciąg formatujący z kontrolowanymi przez atakującego *wartościami* to inny przypadek. Ujawniony sekret prowadzi do zmiany konta systemowego tylko wtedy, gdy dane konto go akceptuje. Sprawdź skrypt i uprawnienia do gniazda bez wywoływania uprzywilejowanej operacji.
- Wrapper Pythona działający jako root może przekazywać wybrany przez wywołującego URL do `Repo.clone_from` z GitPython. Jeśli wrapper włącza też `protocol.ext.allow=always` w Git, zdalne źródło `ext::` może uruchomić zewnętrzny helper. Sprawdź dokładne argumenty sudo, źródło URL, wersję pakietu GitPython i status poprawek dostawcy oraz to, czy wrapper jawnie dopuszcza niebezpieczne protokoły. GitPython dodał [domyślne zabezpieczenie przed niebezpiecznymi protokołami](https://github.com/gitpython-developers/GitPython/commit/2625ed9) w wersji 3.1.30; wersja pliku wykonywalnego `git` to osobna kwestia. Pasywny przegląd powinien obejmować wyłącznie regułę i ograniczony zakres kodu źródłowego, bez uruchamiania klonowania.
- Uprawnienie sudo do narzędzia CLI klonującego repozytorium z możliwością działania jako inne konto może otwierać osobną ścieżkę wstrzyknięcia ciągu powłoki. Prześledź, czy argument repozytorium wybrany przez wywołującego trafia do Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) lub innego mechanizmu budującego polecenie powłoki bez bezpiecznego rozdzielenia argumentów; Node `exec` przekazuje ciąg polecenia do powłoki. Sprawdź dokładnego użytkownika RunAs, dozwolone podpolecenia i argumenty, kod zainstalowanego wrappera oraz walidację danych wejściowych. Sama nazwa narzędzia repozytoryjnego lub nieograniczona reguła sudo nie dowodzą wstrzyknięcia polecenia. Sprawdź wrapper bez uruchamiania uprzywilejowanego klonowania podczas inwentaryzacji.
- Niestandardowy wrapper należący do roota może pozornie być bezpieczny, bo jego pliki binarne i skrypty nie są zapisywalne, a mimo to decyzja o wykonaniu uprzywilejowanej czynności może zależeć od flagi, wartości lokalnego API lub stanu usługi, które może zmienić nieuprzywilejowany użytkownik. Prześledź każde takie zabezpieczenie aż do jego źródła i kontroli autoryzacji. Podczas inwentaryzacji sprawdź konfigurację i uprawnienia bez zmieniania stanu operacyjnego; wywołanie `systemd-run` we wrapperze ma znaczenie tylko wtedy, gdy można wpłynąć na warunek.
- Klient kopii zapasowych dopuszczony przez sudo jako root może przyjmować plik konfiguracyjny wybrany przez wywołującego (na przykład `npbackup-cli -c`). Sprawdź dokładnego użytkownika RunAs i dozwolone argumenty, a następnie ustal, czy wywołujący kontroluje ścieżkę konfiguracji, ścieżki źródeł kopii zapasowej oraz repozytorium albo opcje odczytu/przywracania. Zaszyfrowany sekret repozytorium w odczytywalnej konfiguracji może nadal być użyteczny dla klienta, ale sama reguła nie dowodzi dostępu do repozytorium ani ujawnienia plików roota. Zweryfikuj uprawnienia bez uruchamiania kopii zapasowej ani zrzucania jej zawartości.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) obsługuje `--password-command`, które wywołuje program pobierający hasło repozytorium. Jeśli reguła sudo pozwala użytkownikowi o niższych uprawnieniach uruchomić restic jako root z wybranym przez niego poleceniem pobierającym hasło i podpoleceniem, które go wymaga, helper może zostać uruchomiony jako root. Sprawdź dokładne argumenty sudo i wykluczenia; nie uruchamiaj helpera ani polecenia kopii zapasowej tylko po to, by potwierdzić ten warunek.
- Uprzywilejowane uprawnienie do `restic backup` może również przekroczyć granicę odczytu plików, jeśli wzorzec argumentów sudo pozwala wywołującemu wybrać zarówno źródło, jak i repozytorium, które może później odczytać i odszyfrować. [Symbole wieloznaczne argumentów sudoers mogą dopasowywać białe znaki i ukośniki](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), więc sprawdź końcowe symbole wieloznaczne, zamiast zakładać, że stały prefiks repozytorium ogranicza źródło. [Restic może tworzyć kopie zapasowe w repozytoriach lokalnych i zdalnych](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), ale lokalne repozytorium może zawierać nowo zapisane obiekty dostępne tylko rootowi; zanim uznasz, że dochodzi do ujawnienia, sprawdź efektywną politykę sudo, dostęp do backendu, hasło repozytorium i uprawnienia powstałych obiektów. Zapisany klucz SSH zapewnia dostęp tylko wtedy, gdy konto docelowe go akceptuje. Nie uruchamiaj kopii zapasowej, by to sprawdzić podczas pasywnego przeglądu.
- Nieograniczone uprawnienie do niestandardowego polecenia konserwacyjnego lub do tworzenia kopii zapasowej może pozwalać na wskazanie ścieżki wyjściowej albo udostępniać własny harmonogram zadań. W przypadku zapisu pliku sprawdź dokładną regułę sudo i użytkownika RunAs, a następnie to, czy wywołujący kontroluje zarówno dane, jak i miejsce docelowe. W przypadku zaplanowanego polecenia sprawdź tożsamość wykonawczą harmonogramu, dane wejściowe polecenia oraz ewentualne dodatkowe wymogi hasła lub autoryzacji. Sama nazwa polecenia lub `NOPASSWD` nie dowodzą żadnej z tych ścieżek. Zobacz [zapis do plików należących do roota](../interesting-files-permissions/write-to-root.md) oraz [cron i timery systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Ustalona komenda sudo może nadal ładować przewidywalny plik konfiguracyjny ze współdzielonego katalogu z prawem zapisu. Ustal, czy wywołujący może podmienić ten plik oraz czy jego pola źródła i miejsca docelowego kontrolują uprzywilejowane pobieranie lub kopiowanie. URL wskazujący lokalny plik może ujawnić dane dostępne tylko dla użytkownika RunAs sudo; źródło kontrolowane przez wywołującego połączone z chronionym miejscem docelowym może utworzyć ścieżkę zapisu. Sprawdź obsługę URL-i przez zainstalowany program, kontrole ścieżki docelowej, efektywną regułę sudo i dostępność danych wyjściowych. Sama zapisywalna ścieżka konfiguracji w `/tmp` to jedynie trop; sprawdź plik binarny i metadane pliku bez uruchamiania uprzywilejowanego transferu.
- Reguła sudo dla `git apply` może umożliwić użytkownikowi RunAs zapis plików wybranych przez kontrolowaną przez wywołującego łatkę. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) pozwalało spreparowanej łatce utworzyć dowiązanie symboliczne, a następnie zapisać dane poza drzewem roboczym, nawet jeśli polecenie nie przyjmowało `--unsafe-paths`. Sprawdź efektywną regułę argumentów sudo, źródło łatki, dostęp konta RunAs do katalogu roboczego oraz poprawkę Git lub backport dostawcy. Nieograniczona reguła dopuszczająca `--unsafe-paths` stwarza osobne, jawne ryzyko związane z opcją; ani wersja Git, ani samo uprawnienie do `git apply` nie dowodzą możliwości zmiany chronionego pliku. Podczas pasywnej inwentaryzacji nie stosuj niezaufanej łatki.
- Reguła sudo umożliwiająca uruchomienie `clamscan --debug` jako root może przekroczyć granicę odczytu, jeśli użytkownik o niższych uprawnieniach może dostarczyć obraz DMG, a zainstalowany parser jest podatny na [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), które mogło ujawniać zawartość plików w wyjściu debugowania. Sprawdź dokładnie dozwolone argumenty i ścieżkę skanowania, kontrolę nad danymi wejściowymi, efektywne konto RunAs, poprawkę/backport silnika oraz widoczność danych wyjściowych dla wywołującego. Jeśli szersza reguła dopuszcza `--file-list`/`-f`, osobno sprawdź działanie tej listy; polityka ograniczona do `--debug <scan-path>` nie dopuszcza tej opcji. Podczas inwentaryzacji sprawdź politykę i metadane pakietu bez skanowania spreparowanego pliku ani wyświetlania chronionych danych.
- Reguła sudo pozwalająca otworzyć jako root wybrany przez wywołującego zaszyfrowany obraz dysku oraz druga reguła pozwalająca zamontować wynikowy mapper mogą wprowadzić kontrolowane przez wywołującego pliki do przestrzeni nazw montowań hosta. Sprawdź obie efektywne reguły i argumenty, kontrolę nad obrazem i nazwą mappera, rzeczywisty punkt montowania oraz właściciela i tryb wynikowych plików. Zmiana na set-user-ID wymaga ponadto dostępnego pliku wykonywalnego, opcji montowania honorujących ten bit (`nosuid` go blokuje) oraz odpowiedniej polityki procesu lub MAC; samo otwarcie lub zamontowanie obrazu to jedynie trop. Osobna ścieżka przez istniejącą kopię zapasową wymaga faktycznego klucza i użytecznego, odczytywalnego sekretu. Podczas pasywnej inwentaryzacji sprawdź politykę i ścieżki bez otwierania ani montowania obrazu. Zobacz [podręcznik cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) oraz [opcje mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Reguła sudo dla skryptu powłoki lub Pythona działającego jako root wymaga sprawdzenia katalogu roboczego, jeśli skrypt uruchamia `./helper` bez wcześniejszego przejścia do ustalonego katalogu. Lista Pythona taka jak `['./helper']` przekazana do `subprocess.run` może zachowywać się tak samo i użyć katalogu roboczego wybranego przez wywołującego. Może on wybrać katalog zapisywalny i umieścić w nim plik wykonywalny o tej względnej nazwie; bezwzględna ścieżka gdzie indziej w skrypcie nie zabezpiecza tego wywołania. Zanim uznasz to za wykonanie kodu, sprawdź efektywną regułę, `runchdir` lub inną politykę zmieniającą katalog, przepływ i osiągalność gałęzi skryptu, katalog z prawem zapisu i wykonania oraz ograniczenia montowania/`NOEXEC`. Jeśli skrypt jest nieczytelny, jego zachowanie pozostaje nieznane do czasu sprawdzenia kodu autoryzowaną metodą. Zamiast uruchamiać helper, sprawdź skrypty statycznie. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) opisuje politykę katalogu roboczego.
- Ustalony walidator Pythona działający jako root może nadal ewaluować plik danych wybrany przez wywołującego. [Dokumentacja Pythona dla `eval()` ostrzega przed niezaufanymi danymi wejściowymi](https://docs.python.org/3/library/functions.html#eval): sprawdzenie sufiksu, prefiks arytmetyczny ani gałąź walidacji nie stanowią piaskownicy, jeśli pozostała część wyrażenia trafia do `eval`. Zanim uznasz to za ścieżkę wykonania, sprawdź efektywną regułę sudo, czy wywołujący może wybrać i kontrolować dokładny plik, warunki gałęzi parsera i tworzenie wyrażenia oraz tożsamość uprzywilejowanego procesu. Samo występowanie `eval` w czytelnym skrypcie to jedynie wskazówka do dalszej analizy; podczas inwentaryzacji sprawdź kod źródłowy i uprawnienia pliku bez uruchamiania walidatora ani przekazywania testowego wyrażenia.
- Wrapper Ruby działający jako root przez sudo, który odczytuje względną nazwę pliku YAML, na przykład `YAML.load(File.read("dependencies.yml"))`, może pobierać dane z katalogu roboczego wywołującego, chyba że wrapper lub polityka sudo wymusza inny katalog. Sprawdź dokładne dozwolone argumenty, uprawnienia katalogu i pliku oraz zachowanie zainstalowanego Psych: starsze implementacje `YAML.load` mogły deserializować dowolne obiekty Ruby, natomiast nowsze domyślnie ograniczają dozwolone klasy. Statyczne wystąpienie wywołania to jedynie trop; potwierdź, że plik faktycznie pochodzi z katalogu zapisywalnego przez wywołującego i że zainstalowany loader akceptuje niebezpieczne klasy. W przypadku niezaufanych danych wejściowych wybieraj `safe_load` z jawną, minimalną listą dozwolonych klas. Zobacz [dokumentację Ruby 3.0 Psych](https://docs.ruby-lang.org/en/3.0/Psych.html) oraz [dokumentację Ruby 3.1 Psych](https://ruby-doc.org/core-3.1.2/Psych.html).

- Dokładne uprawnienie root przez sudo do `sudo go run /absolute/file.go` wymaga sprawdzenia katalogu roboczego, gdy kod Go odczytuje względny plik WASM i po sprawdzeniu jego wyniku może uruchomić względny skrypt powłoki. Sprawdź efektywną tożsamość RunAs, argumenty polecenia i odmowy, bieżący katalog zapisywalny przez wywołującego, przepływ danych od WASM do gałęzi oraz to, czy ta gałąź wywołuje helper. Stałe `runchdir` w sudo, `os.Chdir` lub [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) mogą zmienić miejsce wyszukiwania. Samo współwystępowanie tych elementów w kodzie to tylko potencjalny trop; sprawdź źródło bez uruchamiania Go, WASM ani helpera.
- `sudoedit` i symbole wieloznaczne w argumentach wymagają sprawdzenia dokładnej wersji i reguły; [lista kontrolna](linux-privilege-escalation-checklist.md) obejmuje problem edycji plików przez sudoedit. W przypadku uprawnienia do `sudoedit` działającego jako inne konto i obejmującego ścieżkę z symbolem wieloznacznym sprawdź efektywne ustawienie `sudoedit_follow` lub `FOLLOW`, `sudoedit_checkdir`, rozwiązaną ścieżkę docelową oraz to, kto może podmienić każdy wpis katalogu nadrzędnego. Pierwsze ustawienie może zezwalać na podążanie za dowiązaniem symbolicznym, a wyłączenie drugiego usuwa kontrole katalogów zapisywalnych; żadne z nich samo nie dowodzi możliwości zapisu do pliku innego użytkownika. Przed wyciągnięciem takiego wniosku potwierdź zainstalowaną politykę sudo i dokładnie dopasowane argumenty. Zobacz [definicje opcji sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- We wpisie reguły polecenia sudoers symbol wieloznaczny argumentu może dopasowywać białe znaki oraz znaki ścieżki. Reguła polecenia zdolnego do odczytu z argumentem takim jak `/restricted/*` może więc dopuszczać dodatkowy argument pliku po zgodnym prefiksie. Sprawdź dokładnego użytkownika run-as, ścieżkę polecenia, wzorzec argumentu i późniejsze odmowy; wykazany odczyt pliku nie oznacza wykonania polecenia. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) odróżnia symbole wieloznaczne argumentów od symboli wieloznacznych ścieżek poleceń.
- Wzorzec argumentu przypominający ścieżkę może dopasować również `../`. Na przykład reguła `node /opt/scripts/*.js` umożliwiająca działanie jako root może pozwalać na wskazany przez wywołującego plik JavaScript poza `/opt/scripts`, jeśli podana nazwa nadal zaczyna się od `/opt/scripts/` i jest rozwiązywana przez segmenty katalogów nadrzędnych. Jest to symbol wieloznaczny **argumentu**; symbol wieloznaczny ścieżki polecenia dla pliku wykonywalnego Node ma inne zasady dopasowywania ukośników. Zanim uznasz, że możliwe jest wykonanie kodu, sprawdź efektywną regułę, późniejsze odmowy, rozwiązywanie ścieżki, kontrolę nad plikiem docelowym oraz ograniczenia sudoers dotyczące wyrażeń regularnych lub digestów. Zobacz [zasady symboli wieloznacznych sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) oraz [dokumentację wiersza poleceń Node](https://nodejs.org/api/cli.html).
- Archiwizatory i inne programy narzędziowe mogą mieć hooki umożliwiające wykonanie kodu. Sprawdź dokładne dozwolone argumenty w [GTFOBins](https://gtfobins.github.io/), zamiast zakładać, że polecenia wykonują wyłącznie powłoki lub interpretery.
- Nieograniczona reguła `qpdf` umożliwiająca działanie jako root może ujawnić uprzywilejowany plik przez załączniki PDF: qpdf 10.2 i nowsze obsługują `--empty` oraz `--add-attachment file ... --` z wyjściowym plikiem PDF. Jeśli uprzywilejowany proces może odczytać wybrane źródło i zapisać PDF w miejscu dostępnym dla wywołującego, dane wyjściowe mogą zawierać bajty źródła. Zanim uznasz, że ujawnienie pliku jest możliwe, sprawdź efektywne argumenty i wykluczenia sudo, wersję qpdf, dostęp do źródła oraz ścieżkę wyjściową. Odczyt klucza SSH roota jest przydatny do logowania tylko wtedy, gdy klucz jest ważny, a uwierzytelnianie SSH roota dozwolone. Zobacz [opcje załączników qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Ponowne użycie znacznika czasu sudo zależy od polityki pamięci podręcznej, właściciela, terminala/sesji i uprawnień. [Przewodnik po eskalacji uprawnień](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) opisuje kontrole.
- `doas` ma własne reguły i konfigurację. Sprawdź dozwolone polecenia i ścieżki konfiguracji z prawem zapisu, zgodnie z opisem w [sekcji doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Narzędzia budowania i pakietowania uruchamiane przez sudo

Nieograniczone uprawnienie sudo do Foundry `forge` może mieć znaczenie nawet wtedy, gdy tożsamością RunAs jest inne konto niebędące rootem. Opcje kompilatora, takie jak `--use`, mogą wskazać lokalny plik wykonywalny, a `forge flatten -o` wybiera plik wyjściowy. Zanim uznasz to uprawnienie za możliwe do wykorzystania, sprawdź zainstalowaną wersję Forge, dokładne argumenty sudo, dostęp do projektu i ścieżek kompilatora, uprawnienia pliku wyjściowego oraz efektywne środowisko. Względny helper wykonywalny odnaleziony przez `PATH` to ścieżka zależna od wersji i środowiska, a nie właściwość, którą należy zakładać dla każdej kompilacji Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Nieograniczone uprawnienie do `pacman` umożliwiające działanie jako root pozwala na więcej niż tylko zapytania o pakiety: `-U` przyjmuje pakiet lokalny, pakiety mogą zawierać skrypty instalacyjne, a `--hookdir` wybiera inny katalog hooków. Przed testowaniem sprawdź efektywną regułę sudo, ograniczenia i wykluczenia argumentów; pasywna inwentaryzacja nie wymaga instalowania pakietu ani uruchamiania hooka.<sup>[[25]](#references)[[26]](#references)</sup>

Ustalony wrapper powłoki w sudo może również zainstalować nazwaną zależność npm, a następnie uruchomić aplikację Node. Sprawdź jego dokładną regułę RunAs, czy pakiet jest już zainstalowany, efektywne `HOME` i `userconfig` npm, konfigurację projektu lub nadpisania z wiersza poleceń oraz to, czy użytkownik o niższych uprawnieniach kontroluje rejestr lub pakiet zwracany dla tej nazwy. [Dokumentacja npm opisuje wyszukiwanie plików `.npmrc` użytkownika i projektu](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); zachowanie `HOME` przez sudo zależy od zainstalowanej polityki i dystrybucji, więc plik `.npmrc` zapisywalny przez użytkownika może, ale nie musi, być odczytywany przez uprzywilejowany proces npm. Jeśli nowo zainstalowany pakiet jest importowany przez uprzywilejowaną aplikację, jego kod modułu może zostać uruchomiony z tożsamością tej aplikacji. Skrypty uruchamiane podczas instalacji to osobna ścieżka zależna od wersji i konfiguracji; [npm opisuje ich cykl życia i obsługę użytkownika](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Ścieżka `.npmrc` lub wiersz `npm install` to tylko trop. Podczas pasywnej inwentaryzacji sprawdź regułę, krótki wrapper, ścieżki konfiguracji i pochodzenie pakietu, nie instalując pakietu ani nie uruchamiając aplikacji.

Uprawnienie sudo do `pip` lub `pip3 download` działającego jako root również jest wskazówką do sprawdzenia budowania pakietu, jeśli argumenty pozwalają wybrać niezaufaną dystrybucję źródłową, nawet gdy wzorzec URL ogranicza ją do lokalnej usługi i sufiksu `.tar.gz`. `pip download` akceptuje URL-e archiwów i rozwiązuje metadane pakietów; przygotowanie sdist może uruchomić backend budowania lub starszy kod `setup.py`, zanim archiwum zostanie jedynie zapisane. Sprawdź dokładną regułę sudo RunAs i argumentów, czy wywołujący może opublikować lub podmienić wybrane archiwum oraz czy dana wersja pip faktycznie przygotowuje jego metadane. Ustalony, zaufany pakiet lub wheel nie dowodzi istnienia tej ścieżki. Podczas pasywnej inwentaryzacji nie pobieraj ani nie buduj niezaufanego pakietu. Zobacz [polecenie download pip](https://pip.pypa.io/en/stable/cli/pip_download/), [interfejs systemu budowania](https://pip.pypa.io/en/stable/reference/build-system/) oraz [wskazówki dotyczące bezpiecznej instalacji](https://pip.pypa.io/en/stable/topics/secure-installs/).

Reguła sudo zezwalająca na `pip install` ze ścieżką lokalnego projektu wybraną przez wywołującego tworzy bardziej bezpośrednią granicę budowania. [pip akceptuje lokalne katalogi projektów](https://pip.pypa.io/en/stable/topics/local-project-installs/) i wywołuje ich system budowania; [backend budowania uruchamia kontrolowane przez projekt hooki budowania](https://pip.pypa.io/en/stable/reference/build-system/). Zanim uznasz tę regułę za uprzywilejowane wykonanie kodu, sprawdź efektywną tożsamość RunAs, dokładne ograniczenia i odmowy argumentów, kontrolę nad wybranym projektem oraz zachowanie zainstalowanego pip/backendu. Ustalony, zaufany projekt lub reguła wykluczająca ścieżki wybrane przez wywołującego nie dowodzą istnienia tej ścieżki. Sprawdź regułę i metadane projektu bez instalowania pakietu podczas pasywnej inwentaryzacji.

Nieograniczone uprawnienie sudo do `easy_install` umożliwiające działanie jako root to podobna wskazówka dotycząca starszego mechanizmu budowania pakietów. [Dokumentacja Setuptools](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) podaje, że Easy Install przyjmuje lokalny katalog projektu i buduje dystrybucje źródłowe; projekt kontrolowany przez wywołującego może uruchomić `setup.py` podczas tego budowania z tożsamością sudo. Sprawdź efektywne konto RunAs, dokładne ograniczenia polecenia i argumentów (w tym późniejsze odmowy), kontrolę nad wybranym projektem oraz zachowanie zainstalowanego narzędzia. Ustalony, zaufany projekt lub polityka niezezwalająca na wybór źródła przez wywołującego nie dowodzą istnienia tej ścieżki. Podczas inwentaryzacji sprawdź regułę i metadane projektu bez instalowania pakietu.

Wrapper Pythona dopuszczony przez sudo, który używa `setuptools.package_index.PackageIndex.download` z URL-em wybranym przez wywołującego, wymaga innej analizy niż `pip download`: [Setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) opisuje nazwę pliku wyprowadzoną z URL-a, która w podatnych wydaniach sprzed 78.1.1 uciekała poza zamierzony katalog pobierania i powodowała zapis z uprawnieniami procesu. Sprawdź efektywnego użytkownika RunAs i regułę argumentów sudo, czy wrapper przekazuje URL wywołującego do dokładnie tego API, zainstalowaną kompilację lub backport dostawcy oraz miejsce, do którego rozwiązuje się wynikowa ścieżka. Sam numer wersji lub katalog pobierania z prawem zapisu nie dowodzą możliwości dowolnego zapisu. Podczas inwentaryzacji sprawdź krótki wrapper i metadane pakietu bez pobierania URL-a ani zapisywania pliku.

Wrapper budowania dopuszczony przez sudo, który przekazuje do PyInstaller wybrany przez wywołującego plik `.spec`, wymaga podobnej analizy granicy zaufania. Plik spec PyInstaller to wykonywalny kod Pythona ewaluowany podczas **budowania**, a jego wpisy `datas` mogą dołączyć do artefaktu pliki odczytywalne przez tożsamość procesu budującego. Sprawdź dokładnego użytkownika RunAs, reguły argumentów i odmów sudo, obsługę ścieżki i gałęzi przez wrapper, kontrolę nad wybranym plikiem spec oraz dostęp do wynikowego artefaktu. Samo dopuszczenie danych wejściowych `.py` lub zainstalowany PyInstaller nie dowodzą możliwości kontrolowania pliku spec ani uprzywilejowanego wykonania. Pasywna analiza powinna obejmować wyłącznie ograniczony zakres pliku wrappera i metadane; nie uruchamiaj kompilacji. Zobacz [dokumentację plików spec PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Ładowarki presetów i pluginów uruchamiane przez sudo

Narzędzia Pythona akceptujące wybrany przez wywołującego preset lub katalog pluginów mogą importować kod z uprawnieniami nadanymi przez sudo. Na przykład BBOT przyjmuje preset przez `-p`, a jego [dokumentacja niestandardowych modułów](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) opisuje wpisy `module_dirs`, które wskazują dodatkowe katalogi modułów Pythona. Jeśli efektywna reguła sudo dopuszcza preset wybrany przez wywołującego, a on kontroluje moduł w wybranym katalogu, import może wykonać kod z uprawnieniami uprzywilejowanego użytkownika, potencjalnie zanim narzędzie odrzuci nieprawidłowy moduł. Podczas inwentaryzacji sprawdź zainstalowaną wersję, dokładną politykę użytkownika run-as i argumentów sudo oraz właścicieli plików presetu i ścieżek modułów, nie ładując modułu.

### Narzędzie wiersza poleceń Backdrop uruchamiane przez sudo

[Bee](https://github.com/backdrop-contrib/bee) to narzędzie PHP działające w wierszu poleceń dla Backdrop CMS. Jego polecenia `eval` (`php-eval`) i `php-script` mogą uruchamiać PHP dostarczony przez wywołującego. Reguła sudo dopuszczająca plik wykonywalny Bee jako root z nieograniczonymi argumentami może więc umożliwić wykonanie kodu jako root, jeśli Bee może zainicjalizować instalację Backdrop. Uruchom je z katalogu witryny albo wybierz witrynę za pomocą globalnej opcji `--root=<directory>`; samo znalezienie Bee lub pliku Backdrop `settings.php` nie dowodzi uprawnień sudo, działającej witryny ani pomyślnej inicjalizacji. Przed testowaniem sprawdź efektywną regułę sudo, ewentualne wykluczenia poleceń, tożsamość pliku wykonywalnego i dostęp do witryny. Podczas pasywnej inwentaryzacji sprawdź regułę i ścieżki plików bez uruchamiania Bee. Zobacz [dziennik zmian poleceń Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md), gdzie dodano polecenia PHP.

### Serwery terminalowe uruchamiane przez sudo

`mosh-server` uruchamia interaktywny serwer terminala jako użytkownik, który go wywołał. Wybiera wysoki port UDP i klucz sesji, wyświetla je wywołującemu, a po połączeniu klienta zwykle uruchamia powłokę logowania tego użytkownika. Nieograniczone uprawnienie root przez sudo do `mosh-server` jest więc kandydatem do sprawdzenia pod kątem powłoki, nawet jeśli samo polecenie serwera działa w tle. Sprawdź efektywną tożsamość RunAs, dozwolone argumenty i wykluczenia, zainstalowany plik binarny, powłokę, dostępność klienta i dostęp przez UDP. Podczas pasywnej inwentaryzacji sprawdź regułę sudo bez uruchamiania serwera ani wyświetlania aktywnego klucza sesji. Zobacz [podręcznik serwera Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) oraz [notatki projektowe upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Uprzywilejowane wrappery kopii zapasowych modyfikujące plik zadań wywołującego

Wrapper powłoki uruchamiany jako root może przyjmować wybrany przez wywołującego plik zadań, usuwać `../` ze ścieżek źródłowych, sprawdzać, czy każdy wynik zaczyna się od dozwolonego katalogu, modyfikować plik zadań, a następnie przekazywać programowi kopii zapasowych jego *nazwę ścieżki*. Sprawdź przekształconą ścieżkę po pełnym rozwiązaniu kanonicznym: pojedyncze zastąpienie ciągu może utworzyć nową sekwencję traversal, którą zaakceptuje leksykalna kontrola prefiksu. Sprawdź też, czy program kopii zapasowych odczytuje przekształcone dane z pamięci, czy ponownie otwiera plik. Jeśli ponownie otwiera plik, nieudana modyfikacja może pozostawić oryginalne dane wejściowe.

W Linuksie `fs.protected_regular` może uniemożliwić zapis z `O_CREAT` do zwykłego pliku należącego do innego użytkownika w katalogu z bitem sticky, zapisywalnym dla wszystkich. To zabezpieczenie jest ochronne, ale wrapper powłoki ignorujący błąd zapisu może mimo to kontynuować pracę z oryginalnym plikiem zadań. Sprawdź to ustawienie, właściciela pliku i katalogu oraz to, czy wrapper przerywa działanie w razie błędu. Ścieżka może ujawnić pliki tylko wtedy, gdy efektywna reguła sudo dopuszcza uruchomienie wrappera jako uprzywilejowany użytkownik, wywołujący kontroluje dane zadania i odczytywalne miejsce docelowe kopii zapasowej, a narzędzie kopii faktycznie obejmuje chronione źródła. Podczas inwentaryzacji sprawdź te warunki bez uruchamiania kopii zapasowej.

### Symbole wieloznaczne argumentów w uprzywilejowanych narzędziach sieciowych

W regule sudo dla `tcpdump` symbol `*` we **wzorcu argumentu** może dopasować białe znaki i ukośniki, więc ograniczenie wyglądające na ścieżkę może nadal dopuszczać dodatkowy tekst opcji. Różni się to od symbolu wieloznacznego w ścieżce pliku wykonywalnego polecenia; sprawdź pełną regułę RunAs i ewentualne późniejsze odmowy. Jeśli można wstrzyknąć opcje, dopuszczalne wywołanie i semantyka opcji zainstalowanego [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) określają, czy `-F`, `-V`, `-r`, `-w` lub `-Z` zapewnia użyteczną możliwość odczytu/zapisu. `-V` odczytuje listę nazw plików przechwyconych pakietów, a nie dowolny plik jako ogólny zrzut. AppArmor lub inna polityka MAC może zablokować dostęp do plików, nawet jeśli sudo dopuszcza polecenie; plik profilu na dysku nie dowodzi, że jest załadowany i egzekwowany. Przed wyciągnięciem wniosków sprawdź autoryzację i politykę pasywnie. [Podręcznik sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) opisuje różnicę między rodzajami symboli wieloznacznych.

Reguła sudo umożliwiająca działanie jako root, która wymienia jedynie plik wykonywalny `tcpdump` i nie ogranicza argumentów, również wymaga sprawdzenia. [Podręcznik tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) opisuje `-z` jako polecenie uruchamiane po rotacji, gdy `-C` lub `-G` rotuje zapisane przechwycenie; `-Z` lub domyślna opcja kompilacji może obniżyć uprawnienia przed uruchomieniem tego polecenia. Zanim uznasz regułę za ścieżkę eskalacji, sprawdź jej efektywną postać, zainstalowaną kompilację, zachowanie związane z obniżaniem uprawnień oraz możliwość wystąpienia rotacji. Wyróżniona reguła to kandydat, a nie dowód wykonania polecenia jako root.

### Wrappery Nmap uruchamiane przez sudo

Jeśli ścieżka `nmap` dopuszczona przez sudo jest wrapperem powłoki, sprawdź dokładnie dozwoloną ścieżkę i każdą przekazywaną opcję. Blokada znanej pisowni `--script` nie musi blokować ładowania kodu NSE: Nmap [`--datadir`](https://nmap.org/book/man-misc-options.html) wybiera pliki danych, a NSE [ładuje `nse_main.lua`](https://nmap.org/book/nse-implementation.html) z wybranego katalogu danych, gdy włączone jest skryptowanie. Niektóre zainstalowane kompilacje akceptują również alternatywne warianty zapisu długich opcji, dlatego porównaj ograniczenia z parserem konkretnego pliku binarnego. [`--excludefile`](https://nmap.org/book/man-target-specification.html) to osobna powierzchnia odczytu plików; błędy parsera mogą ujawnić tekst. Podczas inwentaryzacji sprawdź efektywną regułę sudo, logikę wrappera, wersję Nmap, kontrolę nad katalogiem i politykę MAC, nie uruchamiając skanów.

### Hooki Mercurial pull uruchamiane przez sudo

Stałe źródło w `sudo hg pull /fixed/source` nadal pozostawia wybór **repozytorium odbierającego** bieżącemu katalogowi roboczemu, chyba że polecenie ustala je opcją `-R`. Repozytorium odbierające kontrolowane przez wywołującego może definiować hooki w `.hg/hgrc`, a hook może zostać uruchomiony z uprawnieniami użytkownika RunAs sudo. [Mercurial ignoruje konfigurację repozytorium należącego do niezaufanego użytkownika lub grupy](https://mercurial-scm.org/help/topics/config), dlatego przed uznaniem tego za wykonanie kodu sprawdź zaufanych użytkowników/grupy konta RunAs i dokładny katalog roboczy. Do pasywnego przeglądu wystarczy odczyt polityki i konfiguracji; nie wykonuj pull ani hooka w celu ich sprawdzenia.

### Hooki Git pull uruchamiane przez sudo

W przypadku dokładnego uprawnienia root przez sudo do `sudo git pull` sprawdź również **repozytorium odbierające** wybrane przez katalog roboczy. Repozytorium należące do wywołującego może mieć wykonywalny hook `post-merge`, uruchamiany z tożsamością procesu Git, gdy pull faktycznie kończy się pomyślnym scaleniem; [Git dokumentuje ten hook](https://git-scm.com/docs/githooks) oraz [zachowanie pull w przypadku merge i rebase](https://git-scm.com/docs/git-pull). Sprawdź efektywną regułę sudo i CWD, aktywną ścieżkę hooka i jego uprawnienia oraz możliwość wykonania merge z nowymi commitami. Nieudany, pusty lub wykonujący wyłącznie rebase pull nie dowodzi istnienia tej ścieżki hooka. Podczas sprawdzania polityki i metadanych repozytorium nie uruchamiaj uprzywilejowanego pull.

### Kopiowanie archiwum przez rsync uruchamiany przez sudo

W przypadku `sudo rsync -a ... /writable/source/* /fixed/destination/` symbol `*` we **wzorcu argumentów sudoers** może dopasować białe znaki i dopuścić dodatkową opcję między źródłem a miejscem docelowym. To coś innego niż rozwijanie nazw plików przez powłokę. Jeśli wywołujący może umieszczać pliki w źródle, a miejsce docelowe jest zapisywalne przez uprzywilejowany proces rsync, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) może zażądać uprzywilejowanej zmiany właściciela, podczas gdy tryb archiwizacji zachowuje bity uprawnień, potencjalnie tworząc plik SetUID należący do uprzywilejowanego użytkownika. Sprawdź dokładną [semantykę symboli wieloznacznych sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), wersję rsync, późniejsze odmowy, `nosuid` systemu plików i politykę MAC. Dopasowana reguła to kandydat do sprawdzenia, a nie dowód skutecznej eskalacji uprawnień.

### Eksport reguł filtrowania pakietów przez sudo

Nieograniczone uprawnienie root przez sudo do `iptables` i `iptables-save` (lub odpowiadającej im pary `ip6tables`) wymaga sprawdzenia możliwości zapisu do plików. Dopasowanie `comment` akceptuje tekst reguły wybrany przez wywołującego, a `iptables-save -f` zapisuje serializowany zestaw reguł do wybranej ścieżki.<sup>[[20]](#references)[[21]](#references)</sup> Przydatny ładunek zależy od tego, jak zainstalowany backend serializuje komentarze oraz czy plik docelowy akceptuje inne wiersze eksportu; samo `iptables-save` nie zapewnia dowolnie wybranej zawartości. Sprawdź dokładną tożsamość RunAs sudo, argumenty i wykluczenia, dostępne rozszerzenie match, backend oraz uprawnienia miejsca docelowego. Podczas inwentaryzacji sprawdź uprawnienie bez zmieniania reguł zapory ani zapisywania pliku.

### Uprzywilejowany katalog logów Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) dotyczyło wydań Below starszych niż 0.9.0, które tworzyły katalog `/var/log/below` zapisywalny dla wszystkich. Jeśli usługa lub dozwolone polecenie sudo uruchamia podatną kompilację jako root, użytkownik mogący zapisywać w katalogu logów i przechodzić przez niego — bez sticky bit — może podmienić wpis dziennika na dowiązanie symboliczne, zanim uprzywilejowany proces go otworzy. Sprawdź status poprawek zainstalowanego pakietu, dokładną uprzywilejowaną ścieżkę wykonania, efektywny dostęp do katalogu, sticky bit i ACL oraz metadane `/var/log/below/error_root.log`. Sam katalog zapisywalny dla wszystkich lub reguła sudo nie dowodzą istnienia pełnego łańcucha. Sticky bit lub backport dostawcy zmieniają ocenę. Pasywna inwentaryzacja powinna ograniczyć się do metadanych; nie trzeba tworzyć dowiązania ani uruchamiać uprzywilejowanego programu.

### Uprzywilejowane zbieranie pakietu pomocy technicznej z danych wejściowych zapisywalnych przez użytkownika

Skrypt profilu pomocy technicznej dopuszczony przez `sudo` może odczytywać ustalone ścieżki logów jako root i kopiować ich zawartość do archiwum profilu. Sprawdź, czy skrypt faktycznie odczytuje pliki, a następnie ustal, czy wywołujący może podmienić ścieżkę źródłową lub dowolny wpis katalogu nadrzędnego na dowiązanie symboliczne. Jeśli uprzywilejowany odczyt podąża za tym dowiązaniem, a wynikowe archiwum jest odczytywalne przez wywołującego, chroniony plik może zostać ujawniony. Muszą wystąpić wszystkie elementy: uprawnienie sudo, zapisywalna ścieżka źródłowa, uprzywilejowany odczyt i odczytywalne dane wyjściowe; sam zapisywalny log lub nazwa profilu nie wystarczają. Podczas inwentaryzacji sprawdź efektywne uprawnienia i metadane dowiązań, nie podmieniając plików ani nie generując profilu. [Wskazówki pomocy technicznej Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) opisują uruchamiany jako root skrypt profilu i archiwum wyjściowe, pokazując, dlaczego takie pakiety powinny mieć ograniczone dane wejściowe i dostęp do danych wyjściowych.

### Skrypty przywracania archiwów Pythona uruchamiane jako root

Nawet ściśle ograniczona reguła sudo dla skryptu przywracania w Pythonie wymaga sprawdzenia danych wejściowych archiwum. Jeśli wywołujący może wybrać lub podmienić archiwum, a skrypt rozpakowuje je jako root za pomocą `tarfile.extractall(filter="data")`, przed zaufaniem temu filtrowi sprawdź aktualizacje zabezpieczeń interpretera. CPython naprawił kilka obejść filtrów dotyczących dowiązań symbolicznych i twardych, w tym CVE-2025-4517, w wersjach 3.9.23, 3.10.18, 3.11.13, 3.12.11 i 3.13.4. Backporty dystrybucji mogą naprawić wcześniejszą wersję, więc sam wyświetlany numer interpretera nie dowodzi podatności.<sup>[[16]](#references)[[17]](#references)</sup>

Podczas pasywnego przeglądu odczytaj dokładne polecenie sudo i skrypt, ustal, który argument wybiera archiwum, oraz sprawdź, czy bieżący użytkownik może zapisywać archiwum lub katalog, w którym ono się znajduje. Osobno potwierdź poprawkę dostawcy i katalog docelowy ekstrakcji; `filter="data"` nie sprawia, że każde niezaufane archiwum jest bezpieczne.<sup>[[16]](#references)[[17]](#references)</sup>

### Ładowarki modeli uczenia maszynowego uruchamiane przez sudo

Reguła sudo dopuszczająca wybrany przez wywołującego plik `.pt`, `.pth` lub `.ckpt` wymaga sprawdzenia, jeśli uprzywilejowany skrypt przekazuje go do [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` lub innej ładowarki opartej na pickle. Sprawdź efektywną regułę RunAs, czy wywołujący może utworzyć lub podmienić wybrany model oraz rzeczywisty przepływ argumentu przez ewentualny wrapper powłoki do helpera Pythona. Rozszerzenie `.pth` oznacza również niezwiązane z tym pliki konfiguracyjne Python site, więc samo rozszerzenie nie świadczy o ładowaniu modelu. Skanowanie archiwum lub statyczne skanowanie pickle nie dowodzi, że późniejsze ładowanie jest bezpieczne; sprawdź zależne od wersji zachowanie [`weights_only`](https://docs.pytorch.org/docs/stable/notes/serialization.html) oraz ewentualne listy dozwolonych klas. Zobacz [notatki o pickle w ML i Fickling](../../generic-methodologies-and-resources/python/keras-model-deserialization-rce-and-gadget-hunting.md). Podczas pasywnej inwentaryzacji nigdy nie ładuj ani nie rozpakowuj modelu.

### Parsowanie wyrażeń z zapisanych danych wejściowych przez sudo

Ustalony skrypt Pythona uruchamiany jako root przez sudo może nadal ewaluować tekst zapisany przez użytkownika o niższych uprawnieniach w bazie danych aplikacji. W TensorFlow wywołanie `preprocess_input_exprs_arg_string(value, safe=False)` wybiera ścieżkę `eval`; [ostrzeżenie TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) opisuje niebezpieczny parser i poprawkę jego wywołującego z wiersza poleceń. Jawne wywołanie `safe=False` w aplikacji wymaga osobnego sprawdzenia, nawet jeśli ten wywołujący z wiersza poleceń został poprawiony. Sprawdź efektywną regułę sudo, kto może modyfikować dokładny rekord wejściowy, czy filtrowanie lub ocenianie pozwala temu rekordowi dotrzeć do wywołania oraz zachowanie zainstalowanej funkcji. Sama wersja TensorFlow, uprawnienie sudo lub zakodowany na stałe plik modelu nie dowodzą istnienia łańcucha. Pasywnie sprawdź skrypt i przepływ danych; podczas inwentaryzacji nie uruchamiaj uprzywilejowanego helpera ani nie wysyłaj testowych wyrażeń.

### Konfiguracja needrestart dopuszczona przez sudo

`needrestart -c` ładuje wybrany przez wywołującego plik konfiguracyjny Perl i ewaluje jego zawartość. Jeśli `sudo -l` pozwala uruchomić needrestart jako root z argumentami dopuszczającymi `-c`, a wywołujący może wskazać odczytywalny plik konfiguracyjny w zapisywalnym miejscu, uprawnienie to może prowadzić do wykonania kodu jako root. Sprawdź dokładną regułę sudo dotyczącą użytkownika run-as i argumentów; reguła dopuszczająca wyłącznie ustaloną listę argumentów może blokować tę ścieżkę. Jest to niezależne od podatności needrestart związanych ze skanowaniem interpreterów: aktualizacja pakietu lub wyłączenie `interpscan` nie sprawiają, że nieograniczone uprawnienie root z `-c` staje się bezpieczne.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Importy Pythona przez sudo z uprawnieniami innego konta

Ustalony punkt wejścia Pythona może importować moduł, który wywołujący może edytować lub podmienić, również wtedy, gdy sudo uruchamia skrypt jako **nie-rootowe** konto usługi. W przypadku dosłownego `from utils import status` sprawdź lokalne `utils/__init__.py` i `utils/status.py`, a także uprawnienia katalogu pakietu. Zanim uznasz zapisywalny plik za ścieżkę wykonania, sprawdź ścieżkę importu skryptu, dokładne dozwolone argumenty sudo oraz to, czy dane działanie dociera do tego importu. Podczas inwentaryzacji sprawdź pliki i uprawnienia bez importowania ani uruchamiania skryptu.<sup>[[2]](#references)[[3]](#references)</sup>

Dokładna reguła sudo dla `python3 /absolute/script.py` wymaga jedynie, by skrypt był czytelny; plik nie musi być wykonywalny ani mieć shebanga. Sprawdź również **brakujące** lokalne moduły: jeśli skrypt importuje moduł, którego plik można utworzyć w katalogu skryptu zapisywalnym przez wywołującego, Python może załadować ten plik z tożsamością RunAs. Sprawdź efektywną regułę sudo, rzeczywistą [ścieżkę wyszukiwania modułów](https://docs.python.org/3/library/sys_path_init.html) interpretera, czy moduł jest wbudowany lub zamrożony oraz czy import jest osiągalny. Bezpośrednia reguła sudo dla skryptu ma inne wymagania dotyczące bitu wykonania i shebanga. Osobny wrapper dopisujący tokeny podane przez wywołującego po `sudo -u account` również wymaga analizy przepływu argumentów: dodatkowe `-u` w tych tokenach ma znaczenie tylko wtedy, gdy wywołana polityka sudo dopuszcza wynikową tożsamość. Same ciągi znaków nie dowodzą żadnej z tych ścieżek.

### Apache uruchamiany przez sudo z konfiguracją kontrolowaną przez wywołującego

Jeśli reguła sudo dopuszcza uprzywilejowane wywołanie `apachectl`, `apache2ctl` lub `httpd` z kontrolowanym przez wywołującego plikiem konfiguracyjnym `-f`, sprawdź uprawnienia do tego pliku i jego katalogu nadrzędnego. Dyrektywa Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) przyjmuje nazwę modułu, po której następuje **nazwa pliku modułu**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) również ładuje plik. [`Include` i `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) mogą rozszerzyć konfigurację lub ujawnić zawartość plików w błędach. Niestandardowy wrapper może walidować te ścieżki, obniżać uprawnienia lub ograniczać argumenty, więc sama zapisywalna konfiguracja jest kandydatem do sprawdzenia, a nie dowodem wykonania kodu. Przed wyciągnięciem wniosków sprawdź kanonikalizację ścieżek, dowiązania symboliczne i parsowanie dyrektyw.

### Nginx uruchamiany przez sudo z konfiguracją kontrolowaną przez wywołującego

Nieograniczona reguła `nginx` umożliwiająca działanie jako root może pozwalać użyć [`-c` do wybrania innej konfiguracji](https://nginx.org/en/docs/switches.html). Sprawdź dokładne argumenty i wykluczenia sudo, czy wywołujący może dostarczyć konfigurację oraz czy wynikowe procesy master lub worker zachowują dostęp do chronionych ścieżek. Odpowiednio wybrane `root` i `autoindex` mogą udostępniać pliki przez nowy listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) może zapewnić uprzywilejowaną ścieżkę zapisu plików, ale moduł DAV nie jest domyślnie wbudowany, dlatego trzeba sprawdzić jego obecność, dostępność listenera, uprawnienia do plików i zachowanie plików tymczasowych. Dyrektywa [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) może również wskazywać wybrany plik; zapisywanie logów do wrażliwego pliku konfiguracyjnego, takiego jak `/etc/ld.so.preload`, staje się ścieżką eskalacji dopiero wtedy, gdy efektywnie zapisuje go uprzywilejowany proces i można kontrolować wpis logu. Wyróżnienie pliku wykonywalnego w `sudo -l` to wskazówka do sprawdzenia, a nie dowód działania którejkolwiek z tych ścieżek. Podczas pasywnej inwentaryzacji nie uruchamiaj nginx ani nie zmieniaj jego konfiguracji.

### Porównywanie wzorców w uprzywilejowanych promptach Bash

Gdy skrypt Bash dopuszczony przez sudo odczytuje wartość od wywołującego i sprawdza ją za pomocą `[[ "$expected" == $entered ]]`, Bash interpretuje nieujęty w cudzysłów prawy operand jako wzorzec. Symbol wieloznaczny może więc spełnić warunek bez znajomości oczekiwanej wartości. Ujęcie operandu w cudzysłów (`[[ "$expected" == "$entered" ]]`) powoduje porównanie literalnych ciągów. Sprawdź dokładną regułę sudo, czy prompt jest osiągalny oraz co skrypt robi po porównaniu; sama składnia nie dowodzi istnienia możliwej do wykorzystania ścieżki. Podczas inwentaryzacji nie wyświetlaj oczekiwanej wartości. Zobacz [dokumentację konstrukcji warunkowych Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpery uruchamiane przez sudo, które pobierają i wykonują plik

Nieograniczone uprawnienie root przez sudo do niestandardowego helpera wymaga analizy przepływu danych, jeśli przyjmuje on URL wybrany przez wywołującego, zapisuje odpowiedź na dysk, a następnie uruchamia ten plik przez interpreter lub powłokę. [Sudoers dopuszcza dowolne argumenty, jeśli wpis polecenia ich nie określa](https://man7.org/linux/man-pages/man5/sudoers.5.html); ustalona ścieżka pliku wykonywalnego nie ogranicza tego, co mogą wybrać argumenty. Sprawdź rzeczywistą walidację URL-a, ścieżkę wyjściową, gałąź sukcesu i późniejsze wykonanie w zainstalowanym helperze. Sam import libcurl lub drukowalny ciąg nie dowodzą istnienia takiego łańcucha.

Nawet ustaloną nazwę pliku wyjściowego można podmienić między zapisem a wykonaniem, jeśli helper używa **względnej ścieżki w katalogu roboczym kontrolowanym przez wywołującego**. Zmiana nazwy lub podmiana pliku należącego do roota zależy od prawa zapisu i przechodzenia przez katalog oraz ewentualnych ograniczeń sticky bit, a nie tylko od trybu pliku; zobacz [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Sprawdź, czy helper później ponownie otwiera ścieżkę, czy korzysta z już otwartego deskryptora oraz czy przed zapisem przechodzi do zaufanego katalogu. Pasywnie sprawdź politykę sudo, helper i metadane katalogu; podczas inwentaryzacji nie uruchamiaj uprzywilejowanego pobierania ani wyścigu.

Helper pobierający pliki i uruchamiany przez sudo jako root może też umożliwiać **wstrzyknięcie argumentu**, jeśli buduje ciąg polecenia Bash, taki jak `curl <caller input> -o <fixed output>`. Filtr odrzucający białe znaki nadal pozostawia [rozwijanie nawiasów klamrowych Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): nieujęte w cudzysłów elementy rozdzielone przecinkami mogą zostać osobnymi argumentami curl. Jeśli dane wejściowe docierają do curl przed ustalonym `-o`, dostarczona przez wywołującego opcja wyjściowa może wybrać miejsce docelowe pierwszego URL-a z uprawnieniami helpera; [curl wiąże opcje wyjściowe z URL-ami według kolejności](https://curl.se/docs/manpage.html#-o). Sprawdź dokładną powłokę, cytowanie, walidację danych wejściowych, efektywną regułę sudo, kolejność argumentów curl i obsługiwane schematy URL oraz to, czy wywołujący kontroluje pobierane bajty lub może odczytać wynik. Plik wykonywalny spakowany przez PyInstaller może zawierać logikę aplikacji w Pythonie, ale sam znacznik pakowania lub ciąg `curl` nie dowodzą takiego przepływu danych. Jeśli jest to dozwolone, sprawdź ograniczoną kopię offline; podczas rutynowej inwentaryzacji nie uruchamiaj helpera ani nie pobieraj danych wybranych przez atakującego.

Skrypt powłoki uruchamiany przez sudo jako root, który wywołuje [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html), wybiera tylko nieużywaną nazwę — **nie tworzy pliku**. Jeśli skrypt później tworzy plik pod tą nazwą w katalogu, na który może wpływać inny użytkownik, następnie otwiera go ponownie i dopisuje jego zawartość do chronionego miejsca docelowego, takiego jak `authorized_keys` roota, należy sprawdzić możliwość wyścigu z plikiem tymczasowym. Sprawdź dokładną regułę sudo, właściciela katalogu i pliku, kolejność tworzenia i ponownego otwierania, zabezpieczenia jądra oraz to, czy uprzywilejowany zapis faktycznie wykorzystuje bajty kontrolowane przez atakującego. Ciąg `mktemp -u` lub samo `/tmp` z prawem zapisu nie dowodzą istnienia wyścigu. Sprawdź skrypt i metadane ścieżki bez uruchamiania go ani ścigania się o plik tymczasowy podczas inwentaryzacji.

## Uwagi obronne

- Unikaj nadawania przez sudo uprawnień do interpreterów i interaktywnych edytorów.<sup>[[1]](#references)</sup>
- Preferuj ustalone, należące do roota wrappery wykonujące jedną wąską czynność administracyjną.<sup>[[1]](#references)[[2]](#references)</sup>
- Jeśli interpreter jest niezbędny, ogranicz dokładną ścieżkę skryptu i uniemożliw użytkownikom kontrolowanie argumentów, zapisywalnych importów, `PYTHONPATH` oraz niebezpiecznego zachowywania zmiennych środowiskowych.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Jeśli edycja plików jest konieczna, ogranicz dokładną ścieżkę pliku i rozważ `sudoedit` z poprawionymi wersjami sudo oraz ścisłą obsługą środowiska.<sup>[[1]](#references)[[2]](#references)</sup>
- Sprawdź `SETENV`, `env_keep`, zapisywalne katalogi robocze, zapisywalne ścieżki modułów/importów, `NOEXEC`, `use_pty` i logowanie, ale nie traktuj ich jako kompletnej piaskownicy.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
