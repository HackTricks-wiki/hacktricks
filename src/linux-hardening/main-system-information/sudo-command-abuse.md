## Interpreters zinazoruhusiwa na Sudo

Ikiwa `sudo -l` inamruhusu mtumiaji kuendesha interpreter kama root, ichukulie kama utekelezaji wa moja kwa moja wa code. Interpreters zimeundwa kutekeleza code yoyote, kwa hivyo sheria inayoruhusu `python3`, `perl`, `ruby`, `lua`, `node`, au binary zinazofanana kwa kawaida ni sawa na utekelezaji wa amri za root isipokuwa hoja zimewekewa vikwazo na kuthibitishwa kwa ukali.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Mtiririko wa kawaida wa ukaguzi: kwanza orodhesha ruhusa za mtumiaji, kisha tekeleza kauli ya Python kwa kutumia chaguo la `-c` la interpreter.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Mifano mingine ya interpreters imeonyeshwa hapa chini; interpreters zilizoorodheshwa zinaeleza utekelezaji wa inline-code au API za child-process.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Njia halisi ni muhimu. Ikiwa sheria ya sudo inaruhusu `/usr/bin/python3`, tumia njia hiyo halisi wakati wa uthibitishaji.<sup>[[2]](#references)</sup>

Glob ya executable ya sudo kama `/usr/bin/python*` inaweza pia kuruhusu Python 2 kwa script iliyoandikwa kwa Python 3. Ikiwa script itafikia `input()` ikiwa na maandishi yanayodhibitiwa na mpigaji, [Python 2 hutathmini maandishi hayo kama expression](https://docs.python.org/2/library/functions.html#input); kuita interpreter moja kwa moja hubatilisha shebang ya script. Hakiki binaries zinazolingana zilizosakinishwa, RunAs inayotumika na sera ya arguments, vizuizi, na input inayoweza kufikiwa kabla ya kuchukulia hili kama njia ya kutekeleza code.

Njia ya script iliyowekwa kwenye sheria ya sudo yenye uwezo wa root haizuii kile ambacho script hutekeleza. Kwa wrapper ya Bash inayosomeka, angalia kama command yake ya kwanza inayotekelezeka hutumia positional parameter isiyonukuliwa kama `$1` kama **command word**, huku sudo ikiruhusu arguments zilizochaguliwa na mpigaji. Thibitisha utambulisho wa RunAs unaotumika, sera ya password na arguments, vizuizi vya baadaye, na branch halisi ya script; `NOEXEC`, orodha ya arguments salama isiyobadilika, au wrapper inayohakiki command yake inaweza kubadilisha matokeo. Kagua script fupi kwa njia tuli wakati wa enumeration badala ya kuiita kwa command ya majaribio.

Sheria ya sudo isiyo na vizuizi na yenye uwezo wa root kwa `dotnet` pia inastahili kukaguliwa kwa upande wa interpreter. SDK ya .NET ikiwa imesakinishwa, [`dotnet fsi` huendesha code ya F# kwa njia shirikishi au kutoka kwenye script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), na [`dotnet run` hutekeleza project kutoka kwenye source](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Thibitisha kwanza utambulisho wa RunAs unaotumika na sera halisi ya arguments: sheria iliyowekwa kwenye subcommand fulani salama au programu inayoaminika ni ruhusa tofauti, na usakinishaji wa runtime pekee huenda usiwe na amri za SDK. Jina la executable pekee ni ishara ya ukaguzi, si uthibitisho wa utekelezaji wa code.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` inayoruhusiwa na sudo: uandishi wowote wa faili wenye haki za juu

GNU `tee` hunakili ingizo la kawaida kwenye kila njia iliyotolewa kama operandi ya faili. Kwa hivyo, kanuni ya sudo inayoruhusu kuendesha `/usr/bin/tee` kama root huku mpigaji akidhibiti hoja zake hutoa uwezo wa kuunda au kubatilisha faili yoyote kama root. Kuongeza `-a` hubadilisha uwezo huo na kuwa wa kuongeza maudhui. Tagu ya `PASSWD:` inahusu uthibitishaji wa sudo; yenyewe haiwekei kikomo lengwa wala baiti zinazosomwa kutoka ingizo la kawaida.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Kwanza kagua kanuni halisi. Kwenye mfumo wa majaribio ulioidhinishwa, thibitisha uwezo huo kwa kutumia tu lengwa la muda ambalo ni salama kuunda. `>/dev/null` ya mwisho huficha tu nakala ya `tee` inayoelekezwa kwenye matokeo ya kawaida.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Kuweka `sudo` kabla ya producer hakupandishi ruhusa za shell redirection inayofuata, kwa sababu shell ya mtumiaji ndiye hufungua lengwa. Mchakato wenye ruhusa za juu ndio lazima uwe mwandishi, kama ilivyo kwenye pipeline iliyo hapo juu.<sup>[[1]](#references)[[15]](#references)</sup>

Baada ya kuthibitisha uandishi, chagua njia inayofaa ya root-code-execution kutoka [Uandishi wa Faili Zisizozuiliwa kwenda Root](../interesting-files-permissions/write-to-root.md). Mlolongo mmoja ulioonekana ulitumia root `tee` kuunda faili ya muda mfupi chini ya `/etc/cron.d/`, kuwasha backdoor kupitia script inayodhibitiwa na mtumiaji, kisha kufuta faili ya cron baada ya kutekelezwa. Kufuta faili ya cron kulizuia kuwa ingizo la persistence la muda mrefu, ingawa logi za mfumo bado zilihifadhi ushahidi wa shughuli hiyo.<sup>[[27]](#references)</sup>

## Edita zinazoruhusiwa na sudo

Ikiwa `sudo -l` inamruhusu mtumiaji kuendesha interactive editor kama root, ichukulie kama sehemu inayoweza kutekeleza amri, si ruhusa isiyo na madhara ya kuhariri faili. Mara nyingi editor zinaweza kutekeleza amri za shell, kusoma faili zozote, kuandika faili zozote, au kutumia external helpers kutoka ndani ya editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Mtiririko wa kawaida wa ukaguzi: orodhesha ruhusa za mtumiaji, kisha endesha kila editor au pager iliyoruhusiwa kwa kutumia sudo.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Utekelezaji wa amri kupitia Nano

Wakati `nano` inaruhusiwa kupitia sudo, huenda ukaweza kutekeleza amri kutoka kwenye kiolesura cha kihariri.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Kisha toa amri kama `id` au `/bin/sh` kwenye kidokezo cha amri cha nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Ikiwa shell shirikishi haina mitiririko ya terminal inayoweza kutumika, aina hii ya uelekezaji hupeleka matokeo ya kawaida na makosa yake kwenye descriptor 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Mfuatano halisi wa vitufe unaweza kutofautiana kulingana na toleo la nano na chaguo za build, lakini suala la usalama ni lilelile: kihariri kinaendeshwa kama root na kinaweza kuita amri za nje.<sup>[[1]](#references)[[12]](#references)</sup>

### Njia nyingine za kawaida za kutoroka kutoka kwa vihariri

Vihariri vya mtindo wa Vim kwa kawaida huruhusu kutekeleza amri kupitia `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pagers kama `less` pia zinaweza kufichua utekelezaji wa shell.<sup>[[14]](#references)</sup>

Sheria ya sudo inayoruhusu `apport-cli` kuendeshwa kama root inapaswa pia kukaguliwa kwa uwezekano wa pager. Matoleo ya Apport yaliyoathiriwa yangeweza kufungua ripoti ya crash katika `less` kwa kutumia ukubwa wa terminal unaoweza kurekebishwa na mshambulizi; pager ingeweza kisha kutoa root shell ikiwa masharti maalum ya sudo na pager yangetimizwa. Kagua sheria halisi ya sudo, usanidi wa pager na marekebisho ya kifurushi cha usambazaji kabla ya kudhani kuwa toleo pekee linamaanisha kuwa kuna uwezekano wa kushambuliwa. Soma metadata ya kifurushi na sera bila kusababisha crash au kufungua ripoti yenye ruhusa za juu wakati wa uchunguzi usioingilia mfumo. [Rekodi ya CVE ya Ubuntu](https://ubuntu.com/security/CVE-2023-1326) inaorodhesha matoleo ya vifurushi yaliyorekebishwa kwa kila toleo la mfumo, yakiwemo marekebisho yaliyowekwa nyuma kwenye matoleo ya awali.

```text
!/bin/sh
```

## Hatari nyingine za sudo na doas

Anza kwa kutumia `sudo -l`, `sudo -V`, na sera yoyote inayotumika ya `doas`. Kagua kwa pamoja amri zinazoruhusiwa, mtumiaji wa RunAs, hoja, mazingira na mipangilio chaguomsingi. Ruhusa ya kuendesha amri kama akaunti ya huduma isiyo root bado inaweza kufichua faili za akaunti hiyo au njia ya kupata root.

Script ya Python iliyoidhinishwa na sudo kwa njia isiyobadilika bado inaweza kuendesha amri ya shell chini ya utambulisho wake wa RunAs ikiwa ingizo linalodhibitiwa na mtumiaji linaunganishwa kwenye [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Orodha ya kukataza alama za uakifishaji za shell haitoshi kuthibitisha usalama: [shell pia hutambua ubadilishaji wa amri wa `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Thibitisha kwamba hoja zinazoruhusiwa zinafika kwenye tawi la ingizo, kwamba ingizo linafika kwenye amri ya shell bila uthibitishaji salama, na kwamba sera halisi ya sudo inaruhusu mtumiaji wa RunAs anayelengwa. Njia ya script au kuitwa kwa `os.system()` pekee ni kidokezo cha ukaguzi tu; kagua chanzo bila kuendesha script yenye upendeleo.

Ruhusa halisi ya root kupitia sudo kwa `chattr` inaweza kuondoa sifa ya faili isiyobadilika (`i`), lakini hilo pekee halitoi ruhusa ya kuandika au utambulisho mpya. [Mwongozo wa `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) unasema sifa hiyo huzuia marekebisho na ni root au mchakato wenye `CAP_LINUX_IMMUTABLE` pekee unaoweza kuibadilisha. Kagua sera halisi ya hoja za sudo na usaidizi wa mfumo wa faili, kisha uthibitishe kando kwamba mpigaji anaweza kuandika faili baada ya sifa kuondolewa na kwamba programu yenye utambulisho wa juu inaitumia. Kwa mfano, kubadilisha login shell pia kunahitaji akaunti lengwa kukubali vitambulisho hivyo na kuingia halisi kupitia shell hiyo. Kagua sera, sifa za faili na ruhusa bila kuzibadilisha wakati wa uchunguzi.

Ikiwa sudo inaomba nenosiri na msimbo wa matumizi moja, zingatia mahitaji hayo tofauti na ruhusa ya amri. Faili ya `.google_authenticator` inayoweza kusomwa ina taarifa nyeti za seed, ilhali hash ya zamani ya nenosiri la programu au hifadhidata ni mgombea tu wa nenosiri la sasa la akaunti; hakuna kati ya hizo inayothibitisha kwamba kipengele kingine kinakubaliwa na usanidi halisi wa PAM. Baada ya kuidhinishwa, kagua RunAs na hoja husika: ruhusa isiyo na vizuizi ya root kwa RubyGems `gem` inaweza kufichua amri yake ya editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), lakini ruhusa yenye vizuizi au uthibitishaji ulioshindwa haifanyi hivyo. Uchunguzi usioingilia mfumo unapaswa kuripoti njia na sera bila kuonyesha seed, kurejesha nenosiri, kuzalisha msimbo au kuendesha amri yenye upendeleo.

Ruhusa ya sudo isiyo na vizuizi ya root kwa `knife` ya Chef inahitaji ukaguzi wa kiwango cha interpreter: [Chef inaeleza kuwa `knife exec -E` hutathmini mfuatano wa Ruby kwenye kompyuta ya eneo husika](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Thibitisha kwamba kanuni halisi ya sudo inaruhusu subcommand ya `exec` na hoja ya `-E` inayotolewa na mpigaji, utambulisho wa RunAs unaolengwa na vizuizi vyovyote vinavyolingana vya amri au hoja zisizobadilika. Binary iliyosakinishwa au kanuni iliyo na vizuizi kwa subcommand nyingine ni kidokezo tu. Uchunguzi usioingilia mfumo unapaswa kuripoti kanuni bila kuendesha `knife`.

Ruhusa halisi ya sudo yenye uwezo wa root kwa `msfconsole` ya mwingiliano nayo ni nyeti: [GTFOBins inaeleza console yake ya `irb`](https://gtfobins.org/gtfobins/msfconsole/), ambayo inaweza kurithi utambulisho wa sudo. Thibitisha mtumiaji halisi wa RunAs, orodha ya hoja zinazoruhusiwa, vizuizi vya amri, `NOEXEC` au vizuizi vingine, tabia ya console iliyosakinishwa na kama mpigaji anaweza kutoa ingizo la mwingiliano. Kuangaziwa kwa njia pekee ni kidokezo cha ukaguzi; uchunguzi usioingilia mfumo haupaswi kuwasha console.

Kwenye FreeBSD, hata kanuni ya sudo inayoruhusu root pekee kutumia `pkg update` na `pkg install *` inahitaji ukaguzi wa uaminifu wa repository. Kagua kama mpigaji anaweza kuandika `/etc/hosts` na kama usanidi halisi wa repository unaowashwa unatumia hostname ya HTTP yenye `signature_type: none`. [Mwongozo wa `pkg.conf` wa FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) unasema `none` huzima ukaguzi wa saini; `pkg+http` pekee hauthibitishi hilo. [Kifurushi kinaweza kuwa na install scripts](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/), kwa hiyo mpigaji anayedhibiti endpoint ya repository na anaweza kuchagua kifurushi anaweza kuvuka mpaka wa root. Thibitisha mabadiliko ya repository, utatuzi wa SRV/mirror, hoja halisi za sudo, uteuzi wa kifurushi na utekelezaji wa script kabla ya kufikia hitimisho hilo. Kagua sera na faili ndogo za usanidi za eneo husika bila kuelekeza majina kwingine au kuendesha `pkg` wakati wa uchunguzi.

Ruhusa ya sudo yenye uwezo wa root kwa `apt-get update` na `apt-get upgrade` pia inahitaji ukaguzi wa uaminifu wa repository ikiwa sudo inahifadhi `http_proxy` inayodhibitiwa na mpigaji. Kagua kama usanidi halisi wa APT proxy unatumia kigezo hicho na ni maombi gani ya repository inayowashwa inaweza kuathiri; proxy pekee haiwezi kubadilisha vifurushi kutoka archive iliyothibitishwa kwa signing key inayoaminika. [Mwongozo wa usafirishaji wa HTTP wa APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) unaeleza kipaumbele cha proxy, na [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) unaeleza ukaguzi wa saini, vizuizi vya repository zisizo salama na uthibitisho wa vifurushi visivyothibitishwa. Thibitisha RunAs na hoja halisi za sudo, sera ya uthibitishaji wa repository, kukubali kwa mwingiliano kunakohitajika na kama uboreshaji uliochaguliwa huendesha package scripts kama root. Kagua sera na usanidi wa eneo husika bila kuingilia mfumo; usielekeze upya trafiki ya vifurushi au kuendesha uboreshaji wakati wa uchunguzi.

Kanuni ya sudo yenye uwezo wa root kwa `snap install` inaweza kuweka mpaka kati ya kifurushi na code ikiwa hoja zake zinamruhusu mpigaji kuchagua snap ya eneo husika na hali ya usakinishaji yenye vizuizi hafifu. [Snap inaeleza](https://snapcraft.io/docs/explanation/snap-development/install-modes/) kwamba `--dangerous` huruka ukaguzi wa assertions za snap ya eneo husika na `--devmode` hupunguza vizuizi; [install hook inaweza kuendeshwa wakati wa usakinishaji wa kwanza](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Kagua sera halisi ya hoja/RunAs ya sudo, nani anayedhibiti faili ya snap, kama snapd iliyosakinishwa inakubali hali hizo, na utambulisho na vizuizi halisi vya hook kabla ya kudai ufikiaji wa faili za host zilizolindwa. Binary ya `snap` au kanuni inayoonekana kuwa na wildcard pekee haithibitishi mlolongo huu. Uchunguzi usioingilia mfumo haupaswi kusakinisha kifurushi au kuendesha hook yake.

Kwa ruhusa halisi ya sudo kwa binary maalum ya kusoma credentials ya akaunti **isiyo root**, kwanza kagua binary iliyoruhusiwa na ruhusa zake za faili bila kuiendesha. Kizuizi cha nenosiri kilichopachikwa kinaweza kuonekana tu kama wide characters; [GNU `strings` inaeleza uchimbaji wa 16-bit little-endian](https://sourceware.org/binutils/docs/binutils/strings.html). Mfuatano unaoonekana hauthibitishi kuwa hilo ndilo nenosiri linalokubaliwa au kwamba tawi la mafanikio hufichua credential ya sasa. Thibitisha tabia ya binary, ufikiaji wa akaunti lengwa kwa data iliyolindwa, uhalali wa credential na mabadiliko yoyote ya baadaye ya akaunti au group kando. Ikiwa akaunti hiyo imo kwenye `docker`, thibitisha ufikiaji wa socket na utambulisho wa daemon wa rootful au rootless kabla ya kudhani kuna ufikiaji wa root wa host; [Docker inaeleza athari za kiwango cha root za group yake](https://docs.docker.com/engine/install/linux-postinstall/). Uchunguzi wa kawaida unapaswa kuripoti kanuni ya sudo na uanachama wa group bila kuendesha binary au kutoa strings zake.

Kanuni ya sudo yenye wildcard kwa maintenance scripts za programu inahitaji ukaguzi zaidi ya njia ya script. Kagua kama script iliyoruhusiwa inakubali hoja zisizo na vizuizi au inasoma mipangilio inayoweza kuandikwa kupitia akaunti ya programu yenye upendeleo mdogo, kisha fuatilia thamani hizo hadi kwenye amri za shell au mazingira ya subprocess. Kwa mfano, [`zmupdate.pl` ya ZoneMinder huunda amri ya `mysqldump` na kuiendesha kupitia `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), huku [`zmdc.pl` ikinakili mpangilio wa `ZM_LD_PRELOAD` hadi `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) kabla ya kuwasha daemons. Kanuni ya sudo inayoruhusu mojawapo ya script hizo kama root inaweza kuvuka mpaka wa uaminifu ikiwa ingizo husika linaweza kudhibitiwa na kufikia code hiyo katika toleo lililosakinishwa. Kagua kanuni halisi ya sudo, ruhusa za usanidi wa programu na chanzo cha script; wildcard au mpangilio pekee ni kidokezo cha ukaguzi, si uthibitisho wa utekelezaji.

- `SETENV`, `env_keep`, `secure_path` na `LD_PRELOAD` vinaweza kubadilisha amri finyu na kuifanya itumike kuteka nyara import, library au PATH. Tazama [mwongozo wa environment variables](../linux-basics/linux-environment-variables.md) na [matumizi mabaya ya SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Ruhusa halisi ya root yenye `SETENV` kwa shell wrapper pia inahitaji ukaguzi wa hatua moja ikiwa wrapper inaanzisha script ya Python isiyobadilika yenye import halisi. `secure_path` hudhibiti utafutaji wa amri wa shell, si [`PYTHONPATH` ya utafutaji wa module wa Python](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` na `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) hufanya Python ipuuze kigezo hicho cha mazingira. Thibitisha tags na vizuizi halisi vya sudo, tawi la wrapper, chaguo za interpreter, utatuzi wa import na uwepo wa directory ya utafutaji inayoweza kuandikwa na mpigaji kabla ya kuchukulia hili kuwa utekelezaji wa code. Kagua scripts fupi bila kuzitekeleza; usiendeshe wrapper yenye upendeleo.

Ruhusa halisi ya sudo ya `neofetch ""` yenye uwezo wa root bado inaweza kupakia usanidi wa shell ikiwa defaults zinazotumika za sudo zinahifadhi `XDG_CONFIG_HOME` inayodhibitiwa na mpigaji. [Loader ya usanidi ya Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) huchukua `neofetch/config.conf` au `neofetch/config` chini ya directory hiyo; orodha tupu ya hoja haizuii utafutaji huu. Thibitisha loader iliyosakinishwa, sera halisi ya RunAs na hoja, vizuizi vya amri, kama sudo kweli huhifadhi kigezo kilichochaguliwa kwa amri hii, na kama mpigaji anadhibiti njia ya usanidi inayosomeka. Kigezo kilichohifadhiwa au Neofetch iliyosakinishwa pekee ni kidokezo cha ukaguzi. Kagua sera na metadata ya faili bila kuendesha amri yenye upendeleo au kuchapisha yaliyomo ya usanidi; tazama [ushughulikiaji wa mazingira wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Kanuni ya sudo isiyo na vizuizi yenye uwezo wa root kwa `facter` inahitaji ukaguzi tofauti wa custom-fact. [Puppet inaeleza](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) kwamba `--custom-dir` hupakia faili za Ruby fact kutoka directory iliyochaguliwa. Kagua kama kanuni halisi ya sudo inaruhusu chaguo hilo, kama Facter iliyosakinishwa inalipokea na kama mpigaji anadhibiti directory. Ruhusa yenye hoja zisizobadilika, katazo la wazi la amri au custom facts zilizozimwa zinaweza kubadilisha matokeo. Uchunguzi usioingilia mfumo unapaswa kuripoti uwezekano wa sera bila kuendesha Facter au kusoma yaliyomo ya fact.

Kwa ruhusa halisi ya sudo yenye uwezo wa root kwa script na `SETENV`, kagua majina tupu ya amri kama `find` na `PATH` halisi baada ya sera ya sudo na uanzishaji wa script. Faili ya Bash inayosource inaweza pia kuendesha `enable -n [`: [Bash kisha hutafuta `[` ya nje kupitia `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) script inapotumia amri hiyo baadaye. Thibitisha sheria zinazotumika za [mazingira ya sudoers na `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), ingizo lolote la `NOSETENV`/`NOEXEC` au la kukataa, mtiririko wa script na faili inayosource, na directory inayoweza kuandikwa na kutekelezeka inayodhibitiwa na mpigaji. Script inayosomeka na yenye amri tupu ni kidokezo cha ukaguzi, si uthibitisho wa utekelezaji wenye upendeleo; ikague bila kutumia kanuni ya sudo.

- Script yenye upendeleo inayopakua URL isiyobadilika kwa `curl` bado inaweza kupokea jibu lililochaguliwa na mpigaji ikiwa kanuni ya sudo inayotumika huhifadhi `http_proxy` na ombi linatumwa kupitia proxy hiyo. Ikiwa script kisha hukabidhi jibu kwa XML parser inayotatua external entities, jibu hasidi linaweza kufichua faili zinazosomeka na mchakato wenye upendeleo. Kagua sera halisi ya mazingira ya sudo, vizuizi vya `no_proxy`, URL inayoombwa, usanidi wa parser na sehemu ya matokeo; kigezo cha proxy au XML parser pekee si udhaifu. [Nyaraka za mazingira ya proxy ya curl](https://everything.curl.dev/usingcurl/proxies/env.html) zinaeleza tabia ya vigezo hivyo. Usitume maombi ya mtandao au kuchanganua XML hasidi wakati wa uchunguzi usioingilia mfumo.
- Script ya sudo yenye uwezo wa root inayounda faili ya PostScript kutokana na data iliyoathiriwa na mpigaji kisha kuendesha `ps2pdf -dNOSAFER` inahitaji ukaguzi tofauti wa mtiririko wa ingizo. Ghostscript inaeleza kwamba flag hii huzima SAFER hadi `.setsafe`, na kuruhusu shughuli za faili za PostScript ndani ya ruhusa za mfumo wa uendeshaji za mchakato. Query ya SQL iliyoundwa kutokana na hoja ya mpigaji inaweza kupitisha safu zinazodhibitiwa na mshambuliaji kwenye template ya PostScript, lakini mfuatano wa query au kuitwa kwa `ps2pdf` pekee hakuthibitishi kuwa data inafika kwenye sintaksia ya PostScript inayotekelezeka. Thibitisha kanuni halisi ya sudo, njia halisi ya ingizo hadi template, escaping yoyote, tabia ya Ghostscript iliyosakinishwa na kama SAFER inawashwa tena kabla ya hati kutafsiriwa. Usifanye ubadilishaji wenye upendeleo wakati wa uchunguzi usioingilia mfumo. Tazama [nyaraka za `-dNOSAFER` za Ghostscript](https://ghostscript.readthedocs.io/en/master/Use.html).
- Kwa kanuni ya sudo inayoendesha shell script, linganisha vigezo vinavyohifadhiwa na script yenyewe. Muundo kama `if $CHECK_CONTENT; then` huendesha thamani iliyopanuliwa kama amri, kwa hiyo kuhifadhi `CHECK_CONTENT` kunaweza kuruhusu utekelezaji wa amri hata kama njia na hoja za script ni zisizobadilika. Lazima ukague kama tawi hilo linaweza kufikiwa na kama mazingira huhifadhiwa kwa kweli kwenye kanuni husika.<sup>[[2]](#references)[[22]](#references)</sup>
- Script ya Python iliyoruhusiwa na sudo inaweza kuimport code kutoka directory inayoweza kuandikwa au faili ya `.pyc` iliyohifadhiwa kwenye cache. [Mwongozo wa privilege escalation](../linux-basics/linux-privilege-escalation/README.md) unaeleza hali ya cache.
- Script ya Python isiyobadilika iliyoruhusiwa kuendeshwa kama root bado inaweza kufichua debugger ya mwingiliano. Miito kama `pdb.set_trace()` au `pdb.post_mortem()` huruhusu kauli za Python kuendeshwa katika muktadha wa mchakato unaochunguzwa ikiwa mpigaji anaweza kufikia breakpoint au exception handler **na kudhibiti ingizo la debugger**. Kagua kanuni halisi ya sudo ya RunAs, masharti ya uthibitishaji na tawi, kama exception inaweza kufikiwa, umiliki wa terminal/ingizo na kama debugger inaendeshwa ndani ya mchakato huo huo wenye upendeleo. Ombi la socket linalosababisha exception halitoi lenyewe ufikiaji wa debugger iliyounganishwa na terminal nyingine. [Python inaeleza tathmini ya kauli za debugger na hali ya post-mortem](https://docs.python.org/3/library/pdb.html); kagua script bila kuchochea handler yenye upendeleo wakati wa uchunguzi.
- Script ya Python iliyoruhusiwa na sudo inaweza pia kusoma uga wa profile kutoka hifadhidata au Unix socket na kuuongeza kwenye mfuatano ambao baadaye huwa **format string** ya `str.format()`. [Replacement fields zinaweza kufuata attributes na mapping keys](https://docs.python.org/3/library/string.html#format-string-syntax), kwa hiyo uga unaodhibitiwa na mshambuliaji unaweza kukagua objects zinazopitishwa kwa `format()` na kufichua data inayoweza kufikiwa kutoka humo ikiwa matokeo yatachapishwa au kuhifadhiwa mahali ambapo mpigaji anaweza kuyasoma. Kagua utambulisho halisi wa sudo RunAs, ruhusa ya kuandika rekodi husika, mtiririko wa data hadi kwenye format string, objects zinazotolewa na mwonekano wa matokeo. Huu si utekelezaji wa code wa moja kwa moja, na format string halisi inayoaminika yenye *values* zinazodhibitiwa na mshambuliaji ni hali tofauti. Siri iliyofichuliwa husababisha mabadiliko ya akaunti ya mfumo wa uendeshaji tu ikiwa akaunti hiyo inaikubali. Kagua script na ruhusa za socket bila kuendesha operesheni yenye upendeleo.
- Python wrapper yenye uwezo wa root inaweza kupitisha URL iliyochaguliwa na mpigaji kwa `Repo.clone_from` ya GitPython. Ikiwa wrapper pia huwasha `protocol.ext.allow=always` ya Git, remote ya `ext::` inaweza kuendesha helper ya nje. Kagua hoja halisi za sudo, chanzo cha URL, toleo la kifurushi cha GitPython na hali ya vendor patch, na kama wrapper huwasha waziwazi protocols zisizo salama. GitPython iliongeza [kinga chaguomsingi dhidi ya protocols zisizo salama](https://github.com/gitpython-developers/GitPython/commit/2625ed9) katika 3.1.30; toleo la executable ya `git` ni jambo tofauti. Ukaguzi usioingilia mfumo unapaswa kusoma kanuni na sehemu ndogo ya chanzo pekee, bila kuendesha clone.
- Ruhusa ya sudo ya kuvuka akaunti kwa CLI ya ku-clone repository inaweza kufichua njia tofauti ya shell-string injection. Fuatilia kama hoja ya repository iliyochaguliwa na mpigaji inafika kwenye [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) ya Node.js au mtengenezaji mwingine wa amri za shell bila kutenganisha hoja kwa usalama; `exec` ya Node hupitisha mfuatano wa amri kwa shell. Thibitisha mtumiaji halisi wa RunAs, subcommands na hoja zinazoruhusiwa, code ya wrapper iliyosakinishwa na uthibitishaji wa ingizo. Jina la zana ya repository au kanuni ya sudo isiyo na vizuizi pekee haithibitishi command injection. Kagua wrapper bila kuanzisha clone yenye upendeleo wakati wa uchunguzi.
- Wrapper maalum inayomilikiwa na root inaweza kuonekana salama kwa sababu binaries na scripts zake haziwezi kuandikwa, lakini uamuzi wake wa kuendesha kitendo chenye upendeleo unaweza kutegemea flag, thamani ya local API au hali ya huduma ambayo mtumiaji asiye na upendeleo anaweza kubadilisha. Fuatilia kila kigezo hadi kwenye ingizo lake na ukaguzi wa idhini. Wakati wa uchunguzi, kagua usanidi na ruhusa bila kubadilisha hali ya uendeshaji; kuitwa kwa `systemd-run` ndani ya wrapper kunahusika tu ikiwa kigezo hicho kinaweza kuathiriwa.
- Backup client inayoruhusiwa kupitia sudo kama root inaweza kukubali faili ya usanidi iliyochaguliwa na mpigaji (kwa mfano, `npbackup-cli -c`). Kagua mtumiaji halisi wa run-as na hoja zinazoruhusiwa, kisha kama mpigaji anadhibiti njia ya usanidi, njia za chanzo cha backup na chaguo za repository au read/restore. Siri iliyosimbwa ya repository ndani ya usanidi unaosomeka bado inaweza kutumiwa na client, lakini kanuni pekee haithibitishi ufikiaji wa repository au kufichuliwa kwa faili za root. Thibitisha idhini bila kuendesha backup au kutoa yaliyomo.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) inasaidia `--password-command`, inayoita programu kupata nenosiri la repository. Ikiwa kanuni ya sudo inaruhusu mtumiaji mwenye upendeleo mdogo kuendesha restic kama root kwa amri ya nenosiri iliyochaguliwa na mpigaji na subcommand inayohitaji nenosiri, helper hiyo inaweza kuendeshwa kama root. Kagua hoja halisi za sudo na vizuizi; usiendeshe helper au amri ya backup kwa lengo la kuchunguza hali hiyo pekee.
- Ruhusa yenye uwezo wa root ya `restic backup` pia inaweza kuvuka mpaka wa usomaji wa faili ikiwa muundo wa hoja za sudo unaruhusu mpigaji kuchagua chanzo na repository anazoweza kusoma na kufungua usimbaji wake baadaye. [Wildcards za hoja za sudoers zinaweza kulingana na whitespace na slashes](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), kwa hiyo kagua wildcards za mwisho badala ya kudhani kuwa prefix isiyobadilika ya repository inazuia chanzo. [Restic inaweza kuhifadhi backup kwenye repository za ndani na za mbali](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), lakini repository ya eneo husika inaweza kuwa na objects zilizowekwa hivi karibuni na zinazoweza kusomwa na root pekee; thibitisha sera halisi ya sudo, ufikiaji wa backend, nenosiri la repository na ruhusa za objects zitakazotokana nayo kabla ya kulichukulia hili kuwa ufichuaji. SSH key iliyowekwa kwenye backup hutoa ufikiaji ikiwa tu akaunti lengwa inaikubali. Usifanye backup kulijaribu hili wakati wa ukaguzi usioingilia mfumo.
- Amri isiyo na vizuizi ya maintenance au backup inaweza kukubali njia ya matokeo au kutoa scheduler yake ya kazi. Kwa njia ya kuandika faili, thibitisha kanuni halisi ya sudo na mtumiaji wa run-as, kisha kama mpigaji anadhibiti data na eneo lengwa. Kwa njia ya amri iliyopangwa, thibitisha utambulisho unaotumika wa scheduler, ingizo la amri na kizuizi chochote cha ziada cha nenosiri au idhini. Jina la amri au `NOPASSWD` pekee havithibitishi njia yoyote kati ya hizo. Tazama [kuandika kwenye faili zinazomilikiwa na root](../interesting-files-permissions/write-to-root.md) na [cron na systemd timers](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Amri isiyobadilika ya sudo bado inaweza kupakia faili ya usanidi inayotabirika kutoka kwenye directory inayoweza kuandikwa kwa pamoja. Fuatilia kama mpigaji anaweza kubadilisha faili hiyo na kama sehemu za source na destination zinadhibiti fetch au copy yenye upendeleo. URL ya faili ya eneo husika inaweza kufichua data inayosomeka tu na akaunti ya sudo RunAs; source inayodhibitiwa na mpigaji ikiunganishwa na destination iliyolindwa inaweza kuunda njia ya kuandika. Thibitisha ushughulikiaji wa URL wa programu iliyosakinishwa, ukaguzi wa njia lengwa, kanuni halisi ya sudo na uwezo wa kusoma matokeo. Njia ya usanidi inayoweza kuandikwa ndani ya `/tmp` pekee ni kidokezo cha ukaguzi, kwa hiyo kagua binary na metadata ya faili bila kuanzisha uhamishaji wenye upendeleo.
- Kanuni ya sudo ya `git apply` inaweza kufanya akaunti ya RunAs iandike faili zilizochaguliwa na patch inayodhibitiwa na mpigaji. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) iliruhusu patch iliyoundwa kwa makusudi kuunda symlink kisha kuandika nje ya working tree, hata kama amri haikukubali `--unsafe-paths`. Kagua kanuni halisi ya hoja za sudo, chanzo cha patch, ufikiaji wa working directory kwa akaunti ya RunAs na marekebisho ya Git iliyosakinishwa au vendor backport. Kanuni isiyo na vizuizi inayoruhusu `--unsafe-paths` ni hatari tofauti ya chaguo hilo lililoruhusiwa waziwazi; toleo la Git au ruhusa ya `git apply` pekee havithibitishi kuwa faili iliyolindwa inaweza kubadilishwa. Usitumie patch isiyoaminika wakati wa uchunguzi usioingilia mfumo.
- Kanuni ya sudo yenye uwezo wa root kwa `clamscan --debug` inaweza kuvuka mpaka wa usomaji ikiwa mtumiaji mwenye upendeleo mdogo anaweza kutoa picha ya DMG na parser iliyosakinishwa imeathiriwa na [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), ambayo ingeweza kufichua yaliyomo ya faili kupitia matokeo ya debug. Thibitisha hoja halisi zinazoruhusiwa na njia ya scan, udhibiti wa ingizo, akaunti halisi ya RunAs, marekebisho ya engine/backport na kama mpigaji anaweza kuona matokeo. Ikiwa kanuni pana inaruhusu `--file-list`/`-f`, kagua tabia ya file-list hiyo kando; sera isiyobadilika kwa `--debug <scan-path>` hairuhusu chaguo hilo. Kagua sera na metadata ya kifurushi bila kuchanganua faili iliyoundwa kwa makusudi au kuchapisha matokeo yaliyolindwa wakati wa uchunguzi.
- Kanuni ya sudo yenye uwezo wa root inayofungua disk image iliyosimbwa iliyochaguliwa na mpigaji na kanuni ya pili inayoweka mapper iliyotokana nayo inaweza kuleta faili zinazodhibitiwa na mpigaji kwenye mount namespace ya host. Thibitisha kanuni zote mbili halisi na hoja zake, udhibiti wa image na jina la mapper, mount target halisi, na umiliki na mode ya faili zitakazotokana nazo. Mabadiliko ya set-user-ID pia yanahitaji executable inayofikika, mount options zinazoruhusu hilo (`nosuid` hulizuia), na sera husika ya mchakato au MAC; kufungua au kuweka image pekee ni kidokezo cha ukaguzi. Njia tofauti kupitia backup iliyopo inahitaji key yake halisi na siri muhimu inayosomeka ndani yake. Kagua sera na njia bila kufungua au kuweka image wakati wa uchunguzi usioingilia mfumo. Tazama [mwongozo wa cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) na [mount options](https://man7.org/linux/man-pages/man8/mount.8.html).
- Kanuni ya sudo yenye uwezo wa root kwa shell au Python script inahitaji ukaguzi wa working directory ikiwa script inaita `./helper` bila kwanza kuhamia directory isiyobadilika. Orodha ya Python kama `['./helper']` inayopitishwa kwa `subprocess.run` inaweza kuwa na tabia hiyo hiyo ya kutumia working directory iliyochaguliwa na mpigaji. Mpigaji anaweza kuchagua directory inayoweza kuandikwa na kuweka executable yenye jina hilo la relative humo; njia kamili iliyo sehemu nyingine ya script hailindi mwito huu. Thibitisha kanuni halisi, `runchdir` au sera nyingine ya kubadilisha directory, mtiririko na ufikikaji wa tawi la script, directory inayoweza kuandikwa na kutekelezeka, na vizuizi vya mount/`NOEXEC` kabla ya kuchukulia hili kuwa utekelezaji wa code. Ikiwa script haisomeki, tabia yake haijulikani hadi chanzo kikaguliwe kupitia njia iliyoidhinishwa. Kagua scripts bila kuendesha helper. [Mwongozo wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unaeleza sera ya working-directory.
- Validator ya Python isiyobadilika yenye uwezo wa root bado inaweza kutathmini faili ya data iliyochaguliwa na mpigaji. [Nyaraka za `eval()` za Python zinaonya dhidi ya ingizo lisiloaminika](https://docs.python.org/3/library/functions.html#eval): ukaguzi wa suffix ya ingizo, prefix ya hesabu au tawi la uthibitishaji si sandbox ikiwa expression inayosalia inafika kwenye `eval`. Thibitisha kanuni halisi ya sudo, kama mpigaji anaweza kuchagua na kudhibiti faili hiyo hasa, masharti ya tawi la parser na uundaji wa expression, na utambulisho wa mchakato wenye upendeleo kabla ya kuliita njia ya utekelezaji. Kuonekana kwa `eval` kwenye script inayosomeka pekee ni kidokezo cha ukaguzi; kagua chanzo na ruhusa za faili bila kuendesha validator au kuwasilisha expression ya majaribio wakati wa uchunguzi.
- Ruby wrapper ya sudo yenye uwezo wa root inayosoma jina la relative la YAML, kama `YAML.load(File.read("dependencies.yml"))`, inaweza kuchukua ingizo kutoka working directory ya mpigaji isipokuwa wrapper au sera ya sudo irekebishe directory hiyo. Kagua hoja halisi zinazoruhusiwa, ruhusa za directory na faili, na tabia ya Psych iliyosakinishwa: utekelezaji wa zamani wa `YAML.load` ungeweza kuunda objects za Ruby kiholela, ilhali matoleo mapya huzuia classes kwa chaguomsingi. Sehemu ya code pekee ni kidokezo cha ukaguzi; thibitisha kwamba faili inatoka kwenye directory inayoweza kuandikwa na mpigaji na kwamba loader iliyosakinishwa inakubali classes hatari. Tumia `safe_load` pamoja na allowlist ndogo iliyo wazi ya classes kwa ingizo lisiloaminika. Tazama [nyaraka za Ruby 3.0 Psych](https://docs.ruby-lang.org/en/3.0/Psych.html) na [nyaraka za Ruby 3.1 Psych](https://ruby-doc.org/core-3.1.2/Psych.html).

- Ruhusa halisi ya `sudo go run /absolute/file.go` yenye uwezo wa root inahitaji ukaguzi wa working directory ikiwa chanzo cha Go kinasoma faili ya WASM ya relative na huenda kikaendesha shell script ya relative baada ya kukagua matokeo yake. Thibitisha RunAs halisi, hoja za amri na vizuizi, working directory inayoweza kuandikwa na mpigaji, mtiririko wa data kutoka WASM hadi tawi na kama tawi hilo huita helper. `runchdir` isiyobadilika ya sudo, `os.Chdir` au [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) inaweza kubadilisha eneo la utafutaji. Vitu vinavyoonekana pamoja kwenye chanzo ni uwezekano tu; kagua chanzo bila kuendesha Go, WASM au helper.
- `sudoedit` na wildcards za hoja zinahitaji ukaguzi wa toleo na kanuni husika; [checklist](linux-privilege-escalation-checklist.md) inajumuisha suala la kuhariri faili kwa sudoedit. Kwa ruhusa ya `sudoedit` ya kuvuka akaunti kwenye njia yenye wildcard, kagua mpangilio halisi wa `sudoedit_follow` au `FOLLOW`, `sudoedit_checkdir`, target iliyotatuliwa na nani anayeweza kubadilisha kila entry ya parent. Ya kwanza inaweza kuruhusu kufuata symlink, huku kuzima ya pili kukiondoa ukaguzi wa directory zinazoweza kuandikwa; hakuna mpangilio kati ya hiyo unaothibitisha peke yake kuandikwa kwa faili ya mtumiaji mwingine. Thibitisha sera ya sudo iliyosakinishwa na hoja halisi zinazolingana kabla ya kufikia hitimisho hilo. Tazama [ufafanuzi wa chaguo za sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- Katika kanuni ya amri ya sudoers, wildcard ya hoja inaweza kulingana na whitespace pamoja na herufi za njia. Kanuni ya amri yenye uwezo wa kusoma na hoja kama `/restricted/*` inaweza kwa hiyo kuruhusu hoja ya ziada ya faili baada ya prefix inayolingana. Kagua mtumiaji halisi wa run-as, njia ya amri, muundo wa hoja na vizuizi vinavyofuata; usomaji wa faili ulioonyeshwa hauashirii utekelezaji wa amri. [Mwongozo wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unatofautisha globs za hoja na globs za njia ya amri.
- Glob ya hoja inayoonekana kama njia inaweza pia kulingana na `../`. Kwa mfano, kanuni ya `node /opt/scripts/*.js` yenye uwezo wa root inaweza kumruhusu mpigaji kutumia faili ya JavaScript iliyo nje ya `/opt/scripts` ikiwa jina la njia lililotolewa bado linaanza na `/opt/scripts/` na hutatuliwa kupitia sehemu za parent-directory. Hii ni glob ya **hoja**; glob ya command-path ya executable ya Node ina sheria tofauti za kulingana na slash. Kagua kanuni halisi, vizuizi vinavyofuata, utatuzi wa pathname, udhibiti wa faili lengwa na vizuizi vyovyote vya regular-expression au digest vya sudoers kabla ya kuhitimisha kuwa code inaweza kutekelezwa. Tazama [sheria za wildcards za sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) na [nyaraka za command-line za Node](https://nodejs.org/api/cli.html).
- Archivers na programu nyingine za utility zinaweza kuwa na execution hooks. Linganisha hoja halisi zinazoruhusiwa na [GTFOBins](https://gtfobins.github.io/) badala ya kudhani kuwa shells au interpreters pekee ndizo huendesha amri.
- Kanuni isiyo na vizuizi ya `qpdf` yenye uwezo wa root inaweza kufichua faili yenye upendeleo kupitia PDF attachments: qpdf 10.2 na matoleo mapya zaidi yanaunga mkono `--empty` na `--add-attachment file ... --` pamoja na output PDF. Ikiwa mchakato wenye upendeleo unaweza kusoma chanzo kilichochaguliwa na kuandika PDF kwenye njia inayofikiwa na mpigaji, matokeo hayo yanaweza kubeba bytes za chanzo. Kagua hoja halisi na vizuizi vya sudo, toleo la qpdf, ufikiaji wa chanzo na njia ya matokeo kabla ya kuhitimisha kuwa kufichua faili kunawezekana. Kusoma root SSH key husaidia kuingia ikiwa tu key hiyo ni halali na uthibitishaji wa SSH wa root unaruhusiwa. Tazama [chaguo za qpdf za attachments](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Kutumia tena sudo timestamp kunategemea sera ya cache, mtumiaji mmiliki, terminal/session na ruhusa. [Mwongozo wa privilege escalation](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) unaeleza ukaguzi.
- `doas` ina sheria na usanidi wake. Kagua amri zinazoruhusiwa na njia za usanidi zinazoweza kuandikwa kama ilivyoelezwa kwenye [sehemu ya doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Zana za build na vifurushi zinazoendeshwa kupitia sudo

Ruhusa isiyo na vizuizi ya sudo kwa `forge` ya Foundry inaweza kuwa muhimu hata utambulisho wa RunAs ukiwa mtumiaji mwingine asiye root. Chaguo za compiler kama `--use` zinaweza kuchagua executable ya eneo husika, na `forge flatten -o` huchagua faili la matokeo. Kagua toleo la Forge lililosakinishwa, hoja halisi za sudo, project na njia za compiler zinazofikika, ruhusa za matokeo na mazingira halisi kabla ya kuchukulia ruhusa hiyo kuwa ya kunyonyeka. Executable ya helper ya relative inayopatikana kupitia `PATH` ni njia inayotegemea toleo na mazingira, si tabia ya kudhaniwa kwa kila Forge build.<sup>[[23]](#references)[[24]](#references)</sup>

Ruhusa isiyo na vizuizi yenye uwezo wa root kwa `pacman` inaruhusu zaidi ya maswali ya vifurushi: `-U` hukubali kifurushi cha eneo husika, vifurushi vinaweza kuwa na install scripts na `--hookdir` huchagua directory nyingine ya hook. Kagua kanuni halisi ya sudo, vizuizi vya hoja na vizuizi vya ziada kabla ya kujaribu; uchunguzi usioingilia mfumo hauhitaji kusakinisha kifurushi au kuendesha hook.<sup>[[25]](#references)[[26]](#references)</sup>

Shell wrapper isiyobadilika ya sudo inaweza pia kusakinisha npm dependency yenye jina maalum kisha kuwasha programu ya Node. Kagua kanuni yake halisi ya RunAs, kama kifurushi tayari kimesakinishwa, `HOME` halisi na `userconfig` ya npm, usanidi wa project au mabadiliko ya command-line, na kama mtumiaji mwenye upendeleo mdogo anadhibiti registry au kifurushi kinachorudishwa kwa jina hilo. [npm inaeleza utafutaji wa `.npmrc` wa kila mtumiaji na kila project](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); tabia ya `HOME` ya sudo hutegemea sera na distribution iliyosakinishwa, kwa hiyo `.npmrc` inayoweza kuandikwa na mtumiaji huenda ikasomwa au isisomwe na mchakato wa npm wenye upendeleo. Ikiwa kifurushi kipya kilichosakinishwa kinaimportiwa na programu yenye upendeleo, code ya module yake inaweza kuendeshwa chini ya utambulisho wa programu hiyo. Install-time scripts ni njia tofauti inayotegemea toleo na usanidi; [npm inaeleza lifecycle na ushughulikiaji wa mtumiaji wake](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Njia ya `.npmrc` au mstari wa `npm install` pekee ni kidokezo cha ukaguzi. Kagua kanuni, wrapper fupi, njia za usanidi na asili ya kifurushi bila kusakinisha au kuwasha programu wakati wa uchunguzi usioingilia mfumo.

Ruhusa yenye uwezo wa root ya `pip` au `pip3 download` pia ni kidokezo cha kukagua package build ikiwa hoja zake zinamruhusu mpigaji kuchagua source distribution isiyoaminika, hata kama muundo wa URL unaizuia kwenye huduma ya eneo husika na suffix ya `.tar.gz`. `pip download` hukubali archive URLs na kutatua metadata ya kifurushi; kuandaa sdist kunaweza kuendesha build backend yake au code ya zamani ya `setup.py` kabla tu archive haijahifadhiwa. Thibitisha RunAs na kanuni halisi ya hoja za sudo, kama mpigaji anaweza kuchapisha au kubadilisha archive iliyochaguliwa, na kama toleo hilo la pip kweli huandaa metadata yake. Archive au wheel ya kuaminika isiyobadilika haithibitishi njia hii. Usipakue au kuunda kifurushi kisichoaminika wakati wa uchunguzi usioingilia mfumo. Tazama [amri ya download ya pip](https://pip.pypa.io/en/stable/cli/pip_download/), [kiolesura cha build-system](https://pip.pypa.io/en/stable/reference/build-system/) na [mwongozo wa usakinishaji salama](https://pip.pypa.io/en/stable/topics/secure-installs/).

Kanuni ya sudo inayoruhusu `pip install` pamoja na njia ya project ya eneo husika iliyochaguliwa na mpigaji ina mpaka wa build ulio wazi zaidi. [pip hukubali directory za project za eneo husika](https://pip.pypa.io/en/stable/topics/local-project-installs/) na huendesha build system zao; [build backend huendesha build hooks zinazodhibitiwa na project](https://pip.pypa.io/en/stable/reference/build-system/). Thibitisha utambulisho halisi wa RunAs, vizuizi vya hoja na makatazo halisi, udhibiti wa project iliyochaguliwa na tabia ya pip/backend iliyosakinishwa kabla ya kuchukulia kanuni hiyo kuwa utekelezaji wa code wenye upendeleo. Project ya kuaminika isiyobadilika au kanuni inayokataza njia zilizochaguliwa na mpigaji haithibitishi njia hii. Kagua kanuni na metadata ya project bila kusakinisha kifurushi wakati wa uchunguzi usioingilia mfumo.

Ruhusa isiyo na vizuizi yenye uwezo wa root ya `easy_install` ni kidokezo kingine cha zamani cha package build. [Setuptools inaeleza](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) kuwa Easy Install hukubali directory ya project ya eneo husika na huunda source distributions; project inayodhibitiwa na mpigaji inaweza kuendesha `setup.py` yake wakati wa build chini ya utambulisho wa sudo. Thibitisha akaunti halisi ya RunAs, vizuizi vya amri na hoja (pamoja na makatazo yanayofuata), udhibiti wa project iliyochaguliwa na tabia ya zana iliyosakinishwa. Project ya kuaminika isiyobadilika au sera isiyoruhusu chanzo kilichochaguliwa na mpigaji haithibitishi njia hii. Kagua kanuni na metadata ya project bila kusakinisha kifurushi wakati wa uchunguzi.

Thibitisha RunAs na kanuni halisi ya hoja za sudo, kwamba wrapper hupitisha URL ya mpigaji kwa API hii hasa, build iliyosakinishwa au vendor backport, na mahali njia inayotokana nayo inapotatuliwa. Thibitisha mtumiaji halisi wa RunAs, kanuni za hoja na makatazo ya sudo, ushughulikiaji wa njia na tawi wa wrapper, udhibiti wa faili ya spec iliyochaguliwa na ufikiaji wa artifact inayotokana nayo. ### Backup wrappers zenye upendeleo zinazobadilisha task file ya mpigaji

Shell wrapper inayoendeshwa kama root inaweza kukubali task file iliyochaguliwa na mpigaji, kuondoa `../` kwenye njia za chanzo, kukagua kwamba kila matokeo yanaanza na directory iliyoruhusiwa, kubadilisha task file kisha kupitisha *jina lake la njia* kwa programu ya backup. Kukataa huko ni kinga, lakini shell wrapper inayopuuza kosa la uandishi bado inaweza kuendelea na task file asilia. Thibitisha mpangilio huo, mmiliki wa faili na directory, na kama wrapper husimama ikishindwa. Njia hiyo ni mgombea wa kufichua faili tu ikiwa kanuni halisi ya sudo inaruhusu wrapper kama mtumiaji mwenye upendeleo, mpigaji anadhibiti ingizo la task na destination ya backup inayosomeka, na zana ya backup kweli hujumuisha vyanzo vilivyolindwa. ### Wildcards za hoja kwenye zana za pakiti zenye upendeleo

Katika kanuni ya sudo ya `tcpdump`, `*` kwenye **muundo wa hoja** inaweza kulingana na whitespace na slashes, kwa hiyo kizuizi kinachoonekana kama pathname bado kinaweza kuruhusu maandishi ya ziada ya chaguo. Hii ni tofauti na wildcard kwenye njia ya executable ya amri; kagua kanuni kamili ya RunAs na makatazo yoyote yanayofuata. Ikiwa chaguo zinaweza kuingizwa, mwito unaoruhusiwa na [maana halisi za chaguo za `tcpdump` iliyosakinishwa](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) huamua kama `-F`, `-V`, `-r`, `-w` au `-Z` hutoa uwezo wa kusoma/kuandika unaofaa. `-V` husoma orodha ya majina ya faili za capture, si dump ya jumla ya faili yoyote. AppArmor au sera nyingine ya MAC inaweza kuzuia ufikiaji wa faili hata sudo ikiruhusu amri; faili ya profile iliyo kwenye diski haithibitishi kuwa imepakiwa au inatekelezwa. Kagua idhini na sera bila kuingilia mfumo kabla ya kufikia hitimisho. [Mwongozo wa sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) unaeleza tofauti ya wildcard.

Kanuni ya sudo yenye uwezo wa root inayoorodhesha executable ya `tcpdump` pekee, bila kizuizi cha hoja, pia inahitaji ukaguzi. [Mwongozo wa tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) unaeleza kuwa `-z` ni amri inayoendeshwa baada ya mzunguko wa capture pale `-C` au `-G` inapozungusha capture iliyohifadhiwa; `-Z` au chaguo-msingi la wakati wa compile linaweza kushusha upendeleo kabla amri hiyo haijaendeshwa. Thibitisha kanuni halisi ya sudo, build iliyosakinishwa, tabia ya kushusha upendeleo na kama mzunguko unaweza kutokea kabla ya kuchukulia kanuni hiyo kuwa njia ya escalation. Kanuni iliyoangaziwa ni mgombea wa ukaguzi, si uthibitisho wa utekelezaji wa amri kama root.

`needrestart -c` hupakia faili ya usanidi wa Perl iliyochaguliwa na mpigaji na kutathmini yaliyomo. Ikiwa `sudo -l` inaruhusu `needrestart` kama root kwa hoja zinazoruhusu `-c`, na mpigaji anaweza kuchagua faili ya usanidi inayosomeka mahali panapoweza kuandikwa, ruhusa hiyo inaweza kusababisha utekelezaji wa code kama root. Kagua kanuni halisi ya sudo ya run-as na hoja; kanuni inayoruhusu orodha isiyobadilika tu ya hoja inaweza kuzuia njia hii. Hili ni tofauti na udhaifu wa needrestart wa kuchanganua interpreters: kusasisha kifurushi au kuzima `interpscan` hakufanyi ruhusa isiyo na vizuizi ya root `-c` kuwa salama.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Python imports zinazoendeshwa kupitia sudo chini ya akaunti nyingine

Entry point isiyobadilika ya Python bado inaweza kuimport module ambayo mpigaji anaweza kuhariri au kubadilisha, ikiwemo pale sudo inapoendesha script kama mtumiaji wa huduma **asiye root**. Kwa `from utils import status` iliyoandikwa moja kwa moja, kagua `utils/__init__.py` na `utils/status.py` za eneo husika pamoja na ruhusa za directory ya kifurushi. Thibitisha njia ya import ya script, hoja halisi za sudo zinazoruhusiwa na kama kitendo husika kinafikia import hiyo kabla ya kuchukulia faili inayoweza kuandikwa kuwa njia ya utekelezaji. Kagua faili na ruhusa bila kuimport au kuendesha script wakati wa uchunguzi.<sup>[[2]](#references)[[3]](#references)</sup>

Kanuni halisi ya sudo ya `python3 /absolute/script.py` inahitaji tu script isomeke; faili haihitaji executable bit au shebang. Kagua pia module za eneo husika **zinazokosekana**: ikiwa script huimport module ambayo jina lake la faili linaweza kuundwa kwenye directory ya script inayoweza kuandikwa na mpigaji, Python inaweza kupakia faili hiyo chini ya utambulisho wa RunAs. Thibitisha kanuni halisi ya sudo, [module search path](https://docs.python.org/3/library/sys_path_init.html) halisi ya interpreter, kama module imejengwa ndani au kugandishwa, na kama import inafikiwa. Kanuni ya sudo ya moja kwa moja kwa script ina mahitaji tofauti ya execute-bit na shebang. Wrapper tofauti inayoongeza tokens zilizotolewa na mpigaji baada ya `sudo -u account` pia inahitaji ukaguzi wa mtiririko wa hoja: `-u` nyingine ndani ya tokens hizo ina umuhimu tu ikiwa sera ya sudo inayotumika inaruhusu utambulisho unaotokana nazo. Mifuatano tuli pekee haithibitishi njia yoyote kati ya hizo.

### Apache inayoendeshwa kupitia sudo na usanidi unaodhibitiwa na mpigaji

Ikiwa kanuni ya sudo inaruhusu mwito wenye upendeleo wa `apachectl`, `apache2ctl` au `httpd` pamoja na faili ya usanidi ya `-f` inayodhibitiwa na mpigaji, kagua faili hiyo na ruhusa za directory ya parent yake. Directive ya Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) huchukua jina la module likifuatiwa na **jina la faili la module**; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) pia hupakia faili. [`Include` na `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) zinaweza kupanua usanidi au kufichua yaliyomo ya faili kupitia makosa. Custom wrapper inaweza kuthibitisha njia hizi, kushusha upendeleo au kuweka vizuizi vya hoja, kwa hiyo usanidi unaoweza kuandikwa ni mgombea wa ukaguzi, si uthibitisho wa utekelezaji wa code. Kagua utatuzi wa njia za canonical, symlinks na uchanganuzi wa directives kabla ya kufikia hitimisho.

### nginx inayoendeshwa kupitia sudo na usanidi unaodhibitiwa na mpigaji

Kanuni isiyo na vizuizi ya `nginx` yenye uwezo wa root inaweza kuruhusu [`-c` kuchagua usanidi mwingine](https://nginx.org/en/docs/switches.html). Kagua hoja halisi za sudo na makatazo, kama mpigaji anaweza kutoa usanidi huo, na kama master au workers wanaobainika huhifadhi ufikiaji wa njia zilizolindwa. `root` iliyochaguliwa pamoja na `autoindex` inaweza kufichua faili kupitia listener mpya; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) inaweza kutoa njia ya kuandika faili yenye upendeleo, lakini DAV module haijengwi kwa chaguomsingi na lazima ukague uwepo wake, ufikikaji wa listener, ruhusa za faili na tabia ya temporary file. Directive ya [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) pia inaweza kuelekezwa kwenye faili iliyochaguliwa; kuandika logs kwenye faili nyeti ya usanidi, kama `/etc/ld.so.preload`, kunahitaji mwandishi mwenye upendeleo halisi na log record inayodhibitiwa kabla hakujawa njia ya escalation. Kuangaziwa kwa executable katika `sudo -l` ni kidokezo cha ukaguzi, si uthibitisho kuwa mojawapo ya njia hizi itafanya kazi. Uchunguzi usioingilia mfumo haupaswi kuwasha au kusanidi upya nginx.

### Ulinganisho wa pattern katika Bash prompts zenye upendeleo

Script ya Bash iliyoruhusiwa na sudo ikisoma thamani kutoka kwa mpigaji na kuikagua kwa `[[ "$expected" == $entered ]]`, Bash hutafsiri upande wa kulia usionukuliwa kama pattern. Kwa hiyo wildcard inaweza kufanikisha ulinganisho bila kujua thamani inayotarajiwa. Kunukuu operand (`[[ "$expected" == "$entered" ]]`) hufanya ulinganisho wa mfuatano halisi. Kagua kanuni halisi ya sudo, kama prompt inaweza kufikiwa na kile script hufanya baada ya ulinganisho; sintaksia pekee haithibitishi njia inayoweza kunyonywa. Epuka kuchapisha thamani inayotarajiwa wakati wa uchunguzi. Tazama [marejeo ya miundo ya masharti ya Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers zinazoendeshwa kupitia sudo zinazopakua na kuendesha faili

Ruhusa isiyo na vizuizi ya sudo yenye uwezo wa root kwa helper maalum inahitaji ukaguzi wa mtiririko wa data ikiwa inakubali URL iliyochaguliwa na mpigaji, huandika jibu kwenye diski na baadaye kuendesha faili hilo kwa interpreter au shell. [Sudoers huruhusu hoja zozote ikiwa ingizo la amri haliorodheshi hoja](https://man7.org/linux/man-pages/man5/sudoers.5.html); njia isiyobadilika ya executable haizuii kile hoja zake zinaweza kuchagua. Thibitisha uthibitishaji halisi wa URL, njia ya matokeo, tawi la mafanikio na utekelezaji unaofuata katika helper iliyosakinishwa. Import ya libcurl inayolingana au string inayoweza kuchapishwa pekee haithibitishi mlolongo huu.

Hata basename isiyobadilika ya matokeo inaweza kubadilishwa kati ya uandishi na utekelezaji ikiwa helper inatumia **relative path kwenye working directory inayodhibitiwa na mpigaji**. Kubadilisha jina au kubadilisha faili inayomilikiwa na root kunategemea ufikiaji wa kuandika/kutafuta wa directory na vizuizi vyovyote vya sticky bit, si mode ya faili pekee; tazama [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Kagua kama helper hufungua njia tena au hutumia file descriptor ambayo tayari iko wazi, na kama hubadilika kwenda directory inayoaminika kabla ya kuandika. Kagua sera ya sudo, helper na metadata ya directory bila kuingilia mfumo; usiendeshe upakuaji wenye upendeleo au jaribio la race wakati wa uchunguzi.

Helper ya upakuaji ya root-sudo inaweza pia kufichua **uingizaji wa hoja** inapounda mfuatano wa amri ya Bash kama `curl <caller input> -o <fixed output>`. Filter inayokataa whitespace bado huacha [Bash brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): vipengele vilivyotenganishwa kwa koma na visivyonukuliwa vinaweza kuwa hoja tofauti za curl. Ikiwa ingizo linafika kwenye curl kabla ya `-o` isiyobadilika, chaguo la matokeo linalotolewa na mpigaji linaweza kuchagua destination ya URL ya kwanza chini ya utambulisho wa helper; [curl huhusisha chaguo za matokeo na URL kwa mpangilio](https://curl.se/docs/manpage.html#-o). Thibitisha shell halisi, nukuu, uthibitishaji wa ingizo, kanuni halisi ya sudo, mpangilio wa hoja za curl na URL schemes zinazoungwa mkono, na kama mpigaji anadhibiti bytes zinazopakuliwa au anaweza kusoma matokeo. Executable iliyofungwa kwa PyInstaller inaweza kuwa na mantiki ya programu ya Python, lakini alama ya packaging au mfuatano wa `curl` pekee hauthibitishi mtiririko huu wa data. Kagua nakala ya nje ya mtandao yenye ukubwa mdogo ikiwa umeidhinishwa; uchunguzi wa kawaida haupaswi kuendesha helper au kufetch data iliyochaguliwa na mshambuliaji.

Shell script ya root-sudo inayotumia [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) huchagua jina lisilotumika tu; **haiundi** faili. Ikiwa script baadaye huunda jina hilo kwenye directory ambayo mtumiaji mwingine anaweza kuathiri, kisha hulifungua tena na kuongeza yaliyomo kwenye destination iliyolindwa kama `authorized_keys` ya root, kagua uwezekano wa race ya temporary file. Thibitisha kanuni halisi ya sudo, umiliki wa directory na faili, mfuatano wa kuunda na kufungua tena, kinga za kernel na kama uandishi wenye upendeleo kweli hutumia bytes zinazodhibitiwa na mshambuliaji. Mfuatano wa `mktemp -u` au `/tmp` inayoweza kuandikwa pekee hauthibitishi race hiyo. Kagua script na metadata ya njia bila kuiendesha au kushindania temporary file yake wakati wa uchunguzi.

## Vidokezo vya kujilinda

- Epuka kuruhusu interpreters au interactive editors kupitia sudo.<sup>[[1]](#references)</sup>
- Usiruhusu file writers za jumla kama `tee` zenye operands zisizo na vizuizi. Tumia wrapper inayomilikiwa na root inayochagua destination isiyobadilika na kukataa njia zinazodhibitiwa na mpigaji.<sup>[[2]](#references)</sup>
- Pendelea wrappers zisizobadilika, zinazomilikiwa na root na zinazotekeleza kitendo kimoja finyu cha kiutawala.<sup>[[1]](#references)[[2]](#references)</sup>
- Ikiwa interpreter haiwezi kuepukika, weka vizuizi kwa njia halisi ya script na zuia hoja zinazodhibitiwa na mtumiaji, imports zinazoweza kuandikwa, `PYTHONPATH` na uhifadhi usio salama wa mazingira.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Ikiwa uhariri wa faili unahitajika, weka kizuizi kwa njia halisi ya faili na uzingatie `sudoedit` pamoja na matoleo ya sudo yaliyorekebishwa na ushughulikiaji mkali wa mazingira.<sup>[[1]](#references)[[2]](#references)</sup>
- Kagua `SETENV`, `env_keep`, working directories zinazoweza kuandikwa, njia za module/import zinazoweza kuandikwa, `NOEXEC`, `use_pty` na logging, lakini usizichukulie kuwa sandbox kamili.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
