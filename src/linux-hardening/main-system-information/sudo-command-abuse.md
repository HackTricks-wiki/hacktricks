## Interpreteerders wat deur sudo toegelaat word

As `sudo -l` ’n gebruiker toelaat om ’n interpreteerder as root uit te voer, moet dit as direkte kode-uitvoering beskou word. Interpreteerders is ontwerp om arbitrêre kode uit te voer, dus is ’n reël wat `python3`, `perl`, `ruby`, `lua`, `node` of soortgelyke binaries toelaat, gewoonlik gelykstaande aan die uitvoering van root-opdragte, tensy die argumente streng beperk en bekragtig word.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Algemene hersieningsproses: lys eers die gebruiker se regte, en voer dan ’n Python-stelling met die interpreteerder se `-c`-opsie uit.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Ander voorbeelde van interpreteerders word hieronder getoon; die gelyste interpreteerders dokumenteer uitvoering van inline-kode of API's vir kinderprosesse.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Die presiese pad is belangrik. As die sudo-reël `/usr/bin/python3` toelaat, gebruik daardie presiese pad tydens validering.<sup>[[2]](#references)</sup>

’n Globpatroon vir ’n sudo-uitvoerbare lêer, soos `/usr/bin/python*`, kan ook Python 2 toelaat vir ’n script wat vir Python 3 geskryf is. As die script `input()` met teks wat deur die oproeper beheer word, bereik, [evalueer Python 2 daardie teks as ’n uitdrukking](https://docs.python.org/2/library/functions.html#input); ’n eksplisiete interpreter-aanroep oorskryf die script se shebang. Verifieer die geïnstalleerde ooreenstemmende binaries, die effektiewe RunAs- en argumentbeleid, weierings en bereikbare invoer voordat jy dit as ’n uitvoeringsroete beskou.

’n Vaste script-pad in ’n sudo-reël wat root-toegang kan verleen, beperk nie wat die script uitvoer nie. As dit ’n leesbare Bash-wrapper is, kyk of die eerste uitvoerbare opdrag ’n ongekwoteerde posisionele parameter soos `$1` as die **opdragwoord** gebruik terwyl sudo argumente toelaat wat deur die oproeper gekies word. Bevestig die effektiewe RunAs-identiteit, wagwoord- en argumentbeleid, latere weierings en die werklike script-tak; `NOEXEC`, ’n vaste veilige argumentlys of ’n wrapper wat sy opdrag valideer, kan die resultaat verander. Inspekteer die kort script staties tydens enumerasie eerder as om dit met ’n toetsopdrag aan te roep.

’n Onbeperkte sudo-reël vir `dotnet` wat root-toegang kan verleen, verdien ook ’n interpreter-ondersoek. As ’n .NET SDK geïnstalleer is, [`dotnet fsi` voer F#-kode interaktief of vanuit ’n script uit](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), en [`dotnet run` voer ’n projek vanuit bronkode uit](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Bevestig eers die effektiewe RunAs-identiteit en presiese argumentbeleid: ’n reël wat tot ’n bepaalde veilige subopdrag of vertroude toepassing beperk is, is ’n ander toestemmingsverlening, en ’n installasie met slegs die runtime het dalk nie SDK-opdragte nie. Die uitvoerbare lêernaam alleen is ’n aanduiding vir ondersoek, nie bewys van kode-uitvoering nie.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Editors wat met sudo toegelaat word

As `sudo -l` ’n gebruiker toelaat om ’n interaktiewe redigeerder as root uit te voer, behandel dit as ’n oppervlak vir command execution, nie as ’n onskadelike toestemming om lêers te redigeer nie. Redigeerders kan dikwels shell-opdragte uitvoer, arbitrêre lêers lees of skryf, of eksterne helpers vanuit die redigeerder aanroep.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Algemene hersieningsvloei: lys die gebruiker se voorregte en roep dan elke toegelate redigeerder of pager met sudo aan.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano-opdraguitvoering

Wanneer `nano` via sudo toegelaat word, kan opdraguitvoering vanaf die redigeerderkoppelvlak moontlik wees.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Verskaf dan ’n opdrag soos `id` of `/bin/sh` by die nano-opdragprompt.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

As 'n interaktiewe shell nie bruikbare terminale strome het nie, koppel hierdie herleidingsvorm sy standaarduitvoer en standaardfout aan beskrywer 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

Die presiese sleutelkombinasie kan wissel na gelang van die nano-weergawe en bouopsies, maar die sekuriteitsprobleem is dieselfde: die redigeerder loop as root en kan eksterne opdragte uitvoer.<sup>[[1]](#references)[[12]](#references)</sup>

### Ander algemene ontsnappings uit redigeerders

Vim-styl-redigeerders stel gewoonlik opdraguitvoering deur `:!` beskikbaar.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

Pager-programme soos `less` kan ook shell-uitvoering moontlik maak.<sup>[[14]](#references)</sup>

’n sudo-reël wat `apport-cli` as root toelaat, verdien dieselfde ondersoek van die pager. Geaffekteerde Apport-weergawes kon ’n crash report in `less` oopmaak met ’n terminalgrootte wat deur ’n aanvaller aangepas kon word; die pager kon dan ’n root-shell bied indien die spesiale sudo- en pager-voorwaardes nagekom is. Gaan die effektiewe sudo-reël, pager-konfigurasie en verspreidingspakket se regstelling na voordat jy die weergawe alleen as kwesbaar beskou. Lees die pakket- en beleidsmetadata sonder om ’n crash te veroorsaak of die bevoorregte verslag tydens passiewe enumerasie oop te maak. [Ubuntu's CVE record](https://ubuntu.com/security/CVE-2023-1326) lys vaste pakketweergawes vir spesifieke uitgawes, insluitend teruggeporteerde regstellings.

```text
!/bin/sh
```

## Ander gevare met sudo- en doas-reëls

Begin met `sudo -l`, `sudo -V` en enige toepaslike `doas`-beleid. Lees die toegelate opdrag, gebruiker waaronder dit loop, argumente, omgewing en verstekwaardes saam. Toestemming om as ’n nie-root-diensrekening te loop, kan steeds daardie rekening se lêers blootstel of ’n roete na root bied.

’n Vaste Python-skrip wat deur sudo toegelaat word, kan steeds ’n shell-opdrag onder sy RunAs-identiteit uitvoer as interaktiewe, deur die oproeper beheerde invoer aan [`os.system()`](https://docs.python.org/3/library/os.html#os.system) gekoppel word. ’n Swartlys van shell-leestekens is nie genoeg om veiligheid te bevestig nie: die [shell herken ook `$(...)`-opdragvervanging](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Bevestig dat die toegelate argumente die invoertak bereik, dat die invoer die shell-opdrag sonder veilige validering bereik, en dat die effektiewe sudo-beleid die bedoelde RunAs-gebruiker toelaat. Die skrippad of ’n oproep na `os.system()` alleen is bloot ’n leidraad vir hersiening; ondersoek die bronkode sonder om die bevoorregte skrip uit te voer.

’n Effektiewe root-sudo-toestemming vir `chattr` kan ’n onveranderlike (`i`) lêerkenmerk verwyder, maar dit verleen op sigself nie skryftoegang of ’n nuwe identiteit nie. [Die `chattr`-handleiding](https://man7.org/linux/man-pages/man1/chattr.1.html) sê dat die kenmerk wysigings blokkeer en dat slegs root of ’n proses met `CAP_LINUX_IMMUTABLE` dit kan verander. Gaan die presiese sudo-argumentbeleid en lêerstelselondersteuning na, en verifieer dan afsonderlik dat die oproeper die lêer kan skryf nadat die kenmerk verwyder is en dat ’n gebruiker met ’n hoër identiteit dit gebruik. ’n Vervanging van ’n aanmeldingshell vereis byvoorbeeld ook die teikenrekening se aanvaarbare aanmeldbewyse en ’n werklike aanmelding deur daardie shell. Hersien die beleid, lêerkenmerke en toestemmings sonder om dit tydens inventarisering te verander.

As sudo vir ’n wagwoord én ’n eenmalige kode vra, hou dié vereistes apart van die opdragtoestemming. ’n Leesbare `.google_authenticator`-lêer bevat sensitiewe saadmateriaal, terwyl ’n ou toepassing- of databasiswagwoord-hash slegs ’n kandidaat vir die huidige rekeningwagwoord is; nie een bewys dat die ander faktor deur die effektiewe PAM-konfigurasie aanvaar word nie. Sodra jy gemagtig is, hersien die presiese RunAs en argumente: ’n onbeperkte root-toestemming vir RubyGems `gem` kan sy redigeerderopdrag blootstel ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), maar ’n beperkte toestemming of mislukte verifikasie doen dit nie. Passiewe inventarisering moet paaie en beleid rapporteer sonder om die saad te druk, ’n wagwoord te herwin, ’n kode te genereer of die bevoorregte opdrag uit te voer.

’n Onbeperkte root-bevoegde sudo-toestemming vir Chef se `knife` verdien hersiening op interpreteerdervlak: [Chef dokumenteer dat `knife exec -E` ’n Ruby-string plaaslik evalueer](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifieer dat die effektiewe sudo-reël die `exec`-subopdrag en deur die oproeper verskafte `-E`-argument, die bedoelde RunAs-identiteit en enige ooreenstemmende opdragweierings of vaste argumente toelaat. Die geïnstalleerde binêre lêer of ’n reël wat tot ander subopdragte beperk is, is bloot ’n leidraad. Passiewe inventarisering moet die reël rapporteer sonder om `knife` uit te voer.

’n Presiese root-bevoegde sudo-toestemming vir ’n interaktiewe `msfconsole` is eweneens sensitief: [GTFOBins dokumenteer sy `irb`-konsole](https://gtfobins.org/gtfobins/msfconsole/), wat die sudo-identiteit kan erf. Bevestig die effektiewe RunAs-gebruiker, toegelate argumentlys, opdragweierings, `NOEXEC` of ander beperkings, geïnstalleerde konsolegedrag en of die oproeper interaktiewe invoer kan verskaf. ’n Padmerker alleen is bloot ’n leidraad vir hersiening; passiewe inventarisering moet nie die konsole begin nie.

Op FreeBSD verdien selfs ’n sudo-reël wat tot root se `pkg update` en `pkg install *` beperk is, ’n hersiening van bewaarplekvertroue. Kyk of `/etc/hosts` deur die oproeper geskryf kan word en of die *effektief* geaktiveerde bewaarplekkonfigurasie ’n HTTP-gasheernaam met `signature_type: none` gebruik. [FreeBSD se `pkg.conf`-handleiding](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) sê dat `none` handtekeningkontroles deaktiveer; `pkg+http` alleen bevestig dit nie. ’n Pakket kan installasieskripte bevat ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), dus kan ’n oproeper wat werklik die bewaarplek-eindpunt beheer en ’n pakket kan kies, die root-grens oorsteek. Verifieer bewaarplekoorskrywings, SRV-/spieëlnaamoplossing, effektiewe sudo-argumente, pakketkeuse en skripuitvoering voordat jy dié gevolgtrekking maak. Ondersoek die beleid en klein plaaslike konfigurasielêers sonder om name te herlei of `pkg` tydens inventarisering uit te voer.

’n Root-bevoegde sudo-toestemming vir `apt-get update` en `apt-get upgrade` vereis ook ’n hersiening van bewaarplekvertroue wanneer sudo ’n deur die oproeper beheerde `http_proxy` behou. Kyk of die effektiewe APT-instaanbedienerkonfigurasie daardie veranderlike werklik gebruik en watter geaktiveerde bewaarplekversoeke dit kan raak; ’n instaanbediener alleen kan nie pakkette van ’n argief vervang wat met ’n vertroude ondertekeningsleutel geverifieer word nie. [APT se HTTP-vervoerhandleiding](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) dokumenteer die voorrang van instaanbedieners, en [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) dokumenteer handtekeningkontroles, oorskrywings vir onveilige bewaarplekke en bevestiging vir ongeverifieerde pakkette. Bevestig die presiese sudo-RunAs en argumente, bewaarplekverifikasiebeleid, enige vereiste interaktiewe aanvaarding en of die gekose opgradering pakketskripte as root uitvoer. Ondersoek beleid en plaaslike konfigurasie passief; moenie pakketverkeer herlei of tydens inventarisering ’n opgradering uitvoer nie.

’n Root-bevoegde sudo-reël vir `snap install` kan ’n grens tussen pakket en kode vorm as die argumente die oproeper toelaat om ’n plaaslike snap en ’n permissiewe installasiemodus te kies. [Snap dokumenteer](https://snapcraft.io/docs/explanation/snap-development/install-modes/) dat `--dangerous` kontroles van plaaslike snap-bewyse oorslaan en `--devmode` inperking verslap; [’n installasie-hook kan tydens die aanvanklike installasie loop](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Gaan die presiese sudo-argument-/RunAs-beleid na, wie die snap-lêer beheer, of die geïnstalleerde snapd dié modusse aanvaar, en wat die hook se effektiewe identiteit en inperking is voordat jy aanspraak maak op toegang tot beskermde gasheerlêers. ’n `snap`-binêre lêer of ’n reël wat na ’n jokerteken lyk, bewys nie dié ketting nie. Passiewe inventarisering moet nie ’n pakket installeer of sy hook uitvoer nie.

Vir ’n presiese sudo-toestemming vir ’n pasgemaakte geloofsbriewe-leesprogram van ’n **nie-root**-rekening, ondersoek eers die toegelate binêre lêer en sy lêertoestemmings sonder om dit uit te voer. ’n Ingeboude wagwoordkontrole kan dalk slegs as wye karakters sigbaar wees; [GNU `strings` dokumenteer onttrekking van 16-bis little-endian-teks](https://sourceware.org/binutils/docs/binutils/strings.html). ’n Sigbare string bewys nie dat dit die aanvaarde wagwoord is of dat die suksesvertakking ’n huidige geloofsbrief blootstel nie. Bevestig die program se gedrag, die teikenrekening se toegang tot die beskermde data, die geldigheid van die geloofsbrief en enige latere rekening- of groepoorgang afsonderlik. As daardie rekening aan `docker` behoort, verifieer sokkertoegang en of die daemon rootful of rootless loop voordat jy toegang tot die gasheer se root aflei; [Docker dokumenteer die root-vlak-gevolge van sy groep](https://docs.docker.com/engine/install/linux-postinstall/). Roetine-inventarisering moet die sudo-reël en groeplidmaatskap rapporteer sonder om die binêre lêer uit te voer of sy stringe te dump.

’n Sudo-reël met ’n jokerteken vir ’n toepassing se instandhoudingskripte vereis meer hersiening as net die skrippad. Kyk of die toegelate skrip onbeperkte argumente aanvaar of instellings lees wat deur ’n laerbevoorregte toepassingrekening geskryf kan word, en volg dan daardie waardes na shell-opdragte of ’n subprosesomgewing. ZoneMinder se [`zmupdate.pl` stel byvoorbeeld ’n `mysqldump`-opdrag saam en voer dit met `qx` uit](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), terwyl [`zmdc.pl` die `ZM_LD_PRELOAD`-instelling na `LD_PRELOAD` kopieer](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) voordat dit daemons begin. ’n Sudo-reël wat enige van die skripte as root toelaat, kan ’n vertrouensgrens oorsteek as die ooreenstemmende invoer beheerbaar is en daardie kode in die geïnstalleerde weergawe bereik. Ondersoek die effektiewe sudo-reël, toepassingkonfigurasietoestemmings en skripbron; die jokerteken of instelling alleen is ’n leidraad vir hersiening, nie bewys van uitvoering nie.

- `SETENV`, `env_keep`, `secure_path` en `LD_PRELOAD` kan ’n andersins beperkte opdrag in ’n invoer-, biblioteek- of PATH-kaping verander. Sien die [omgewingsveranderlikegids](../linux-basics/linux-environment-variables.md) en [SUID-/skakelaarmisbruik](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

’n Presiese root-bevoegde `SETENV`-toestemming vir ’n shell-omhulsel verdien ook ’n eenhop-hersiening as die omhulsel ’n vaste Python-skrip met ’n letterlike invoerstelling begin. `secure_path` beperk shell-opdragopsoeke, nie Python se [`PYTHONPATH`-moduleopsoek](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) nie; [`-E` en `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) laat Python dié omgewingsveranderlike ignoreer. Bevestig die effektiewe sudo-etikette en weierings, omhulselvertakking, interpreteerderopsies, invoeroplossing en ’n deur die oproeper skryfbare soekgids voordat jy dit as kode-uitvoering beskou. Ondersoek kort skripte staties; moenie die bevoorregte omhulsel uitvoer nie.

’n Presiese root-bevoegde `neofetch ""`-sudo-toestemming kan steeds ’n shell-konfigurasie laai wanneer die toepaslike sudo-verstekwaardes die deur die oproeper beheerde `XDG_CONFIG_HOME` behou. [Neofetch se konfigurasielaaier](https://github.com/dylanaraps/neofetch/blob/master/neofetch) laai `neofetch/config.conf` of `neofetch/config` vanaf daardie gids; die leë argumentlys verhoed nie hierdie soektog nie. Bevestig die geïnstalleerde laaier, effektiewe RunAs- en argumentbeleid, enige opdragweierings, of sudo werklik die gekose veranderlike vir dié opdrag behou en of die oproeper ’n leesbare konfigurasiepad beheer. ’n Behoue veranderlike of geïnstalleerde Neofetch alleen is ’n leidraad vir hersiening. Ondersoek beleid en lêermetadata sonder om die bevoorregte opdrag uit te voer of konfigurasie-inhoud te druk; sien [sudoers se omgewingshantering](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

’n Onbeperkte root-bevoegde sudo-reël vir `facter` verdien ’n afsonderlike hersiening van pasgemaakte feite. [Puppet dokumenteer](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) dat `--custom-dir` Ruby-feitelêers vanaf ’n gekose gids laai. Kyk of die presiese sudo-reël dié opsie toelaat, of die geïnstalleerde Facter dit aanvaar en of die oproeper die gids beheer. ’n Toestemming met vaste argumente, ’n uitdruklike opdragweiering of gedeaktiveerde pasgemaakte feite kan die uitslag verander. Passiewe inventarisering moet die beleidskandidaat rapporteer sonder om Facter uit te voer of feitelêerinhoud te lees.

Vir ’n presiese root-bevoegde sudo-skripttoestemming met `SETENV`, ondersoek blote opdragname soos `find` en die effektiewe `PATH` ná sudo-beleid en skriptinisialisering. ’n Bash-lêer wat ingesluit word, kan ook `enable -n [` uitvoer: [Bash soek dan `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) vir ’n eksterne `[` wanneer die skrip later dié opdrag gebruik. Bevestig die toepaslike [sudoers-reëls vir omgewing en `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), enige `NOSETENV`/`NOEXEC`- of weieringsinskrywings, die skrip- en ingeslote-lêervloei, en ’n uitvoerbare soekgids wat die oproeper beheer. ’n Leesbare skrip met ’n blote opdrag is ’n leidraad vir hersiening, nie bewys van bevoorregte uitvoering nie; ondersoek dit sonder om die sudo-reël uit te voer.
- ’n Bevoorregte skrip wat ’n vaste URL met `curl` ophaal, kan steeds ’n deur die oproeper gekose antwoord aanvaar as ’n toepaslike sudo-reël `http_proxy` behou en die versoek deur daardie instaanbediener gestuur word. As die skrip dan die antwoord aan ’n XML-ontleder gee wat eksterne entiteite oplos, kan ’n kwaadwillige antwoord lêers bekend maak wat die bevoorregte proses kan lees. Gaan die presiese sudo-omgewingsbeleid, `no_proxy`-uitsluitings, aangevraagde URL, ontlederkonfigurasie en afvoerbestemming na; ’n instaanbedienerveranderlike of XML-ontleder alleen is nie ’n kwesbaarheid nie. Die [dokumentasie oor curl se instaanbedieneromgewing](https://everything.curl.dev/usingcurl/proxies/env.html) beskryf hoe die veranderlikes werk. Moenie netwerkversoeke maak of tydens passiewe inventarisering kwaadwillige XML ontleed nie.
- ’n Root-bevoegde sudo-skrip wat ’n PostScript-lêer uit data wat deur die oproeper beïnvloed word saamstel en dan `ps2pdf -dNOSAFER` uitvoer, verdien ’n afsonderlike hersiening van die invoervloei. Ghostscript dokumenteer dat dié vlag SAFER deaktiveer totdat `.setsafe` uitgevoer word, wat PostScript-lêerbewerkings binne die proses se OS-toestemmings toelaat. ’n SQL-navraag wat uit ’n oproeperargument saamgestel word, kan aanvallerbeheerde rye na die PostScript-sjabloon voer, maar ’n navraagstring of `ps2pdf`-oproep bewys nie op sigself dat die data uitvoerbare PostScript-sintaksis bereik nie. Bevestig die effektiewe sudo-reël, die presiese invoer-tot-sjabloon-pad, enige ontsnapping, die geïnstalleerde Ghostscript-gedrag en of SAFER weer geaktiveer word voordat die dokument geïnterpreteer word. Moenie tydens passiewe inventarisering die bevoorregte omskakeling uitvoer nie. Sien [Ghostscript se `-dNOSAFER`-dokumentasie](https://ghostscript.readthedocs.io/en/master/Use.html).
- Vir ’n sudo-reël wat ’n shell-skrip uitvoer, vergelyk behoue veranderlikes met die skrip self. ’n Konstruksie soos `if $CHECK_CONTENT; then` voer die uitgebreide waarde as ’n opdrag uit, dus kan die behoud van `CHECK_CONTENT` opdraguitvoering toelaat selfs wanneer die skrippad en argumente vas is. Jy moet vir die spesifieke reël nagaan of die vertakking bereik kan word en of die omgewing werklik behou word.<sup>[[2]](#references)[[22]](#references)</sup>
- ’n Python-skrip wat deur sudo toegelaat word, kan kode invoer vanaf ’n skryfbare gids of ’n kaslêer `.pyc`. Die [voorregte-eskalasiegids](../linux-basics/linux-privilege-escalation/README.md) beskryf die kasgeval.
- ’n Vaste Python-skrip wat as root mag loop, kan steeds ’n interaktiewe ontfouter blootstel. Oproepe soos `pdb.set_trace()` of `pdb.post_mortem()` laat Python-stellings in die ontfoute proses se konteks toe wanneer die oproeper die breekpunt of uitsonderingshanteerder kan bereik **en die ontfouter se invoerstroom beheer**. Bevestig die effektiewe sudo-reël, of die oproeper die presiese lêer kan kies en beheer, die ontleder se vertakkingstoestande en uitdrukkingsamestelling, en die bevoorregte prosesidentiteit voordat jy dit ’n uitvoeringsroete noem. Bevestig die geïnstalleerde sudo-beleid en presies ooreenstemmende argumente voordat jy dié gevolgtrekking maak. ### Bou- en pakketnutsprogramme wat deur sudo loop

’n Onbeperkte sudo-toestemming vir Foundry se `forge` kan belangrik wees selfs wanneer die RunAs-identiteit ’n ander nie-root-gebruiker is. Kompileerderopsies soos `--use` kan ’n plaaslike uitvoerbare lêer kies, en `forge flatten -o` kies ’n uitvoerlêer. Gaan die geïnstalleerde Forge-weergawe, presiese sudo-argumente, toeganklike projek- en kompileerderpaaie, uitvoertoestemmings en effektiewe omgewing na voordat jy die toestemming as uitbuitbaar beskou. ’n Relatiewe helper-uitvoerbare lêer wat via `PATH` gevind word, is ’n weergawe- en omgewingsafhanklike roete, nie ’n eienskap wat vir elke Forge-bou aanvaar moet word nie.<sup>[[23]](#references)[[24]](#references)</sup>

’n Onbeperkte root-bevoegde `pacman`-toestemming laat meer toe as pakkette navraag doen: `-U` aanvaar ’n plaaslike pakket, pakkette kan installasieskripte bevat en `--hookdir` kies ’n ander hook-gids. Hersien die effektiewe sudo-reël, argumentbeperkings en uitsluitings voordat jy toets; passiewe inventarisering hoef nie ’n pakket te installeer of ’n hook uit te voer nie.<sup>[[25]](#references)[[26]](#references)</sup>

’n Vaste sudo-shell-omhulsel kan ook ’n benoemde npm-afhanklikheid installeer en dan ’n Node-toepassing begin. Hersien sy presiese RunAs-reël, of die pakket reeds geïnstalleer is, die effektiewe `HOME` en npm-`userconfig`, projekkonfigurasie of opdragreëloorskrywings, en of ’n laerbevoorregte gebruiker die register of pakket wat vir daardie naam teruggestuur word, beheer. [npm dokumenteer `.npmrc`-opsoek per gebruiker en projek](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo se `HOME`-gedrag hang af van die geïnstalleerde beleid en verspreiding, dus word ’n gebruiker se skryfbare `.npmrc` dalk wel of dalk nie deur die bevoorregte npm-proses gelees nie. As die pas geïnstalleerde pakket deur die bevoorregte toepassing ingevoer word, kan sy modulekode onder daardie toepassing se identiteit loop. Installasieskripte is ’n afsonderlike roete wat van weergawe en konfigurasie afhang; [npm dokumenteer hul lewensiklus en gebruikerhantering](https://docs.npmjs.com/cli/v6/using-npm/scripts/). ’n `.npmrc`-pad of ’n `npm install`-reël alleen is bloot ’n leidraad vir hersiening. Ondersoek die reël, kort omhulsel, konfigurasiepaaie en pakketherkoms sonder om tydens passiewe inventarisering die toepassing te installeer of te begin.

’n Root-bevoegde `pip`- of `pip3 download`-toestemming is ook ’n leidraad vir pakketbou-hersiening wanneer die argumente die oproeper ’n onbetroubare bronverspreiding laat kies, selfs al beperk die URL-patroon dit tot ’n plaaslike diens en ’n `.tar.gz`-agtervoegsel. `pip download` aanvaar argief-URL’s en los pakketmetadata op; die voorbereiding van ’n sdist kan sy boubackend of verouderde `setup.py`-kode aanroep voordat die argief bloot gestoor word. Bevestig die presiese sudo-RunAs- en argumentreël, of die oproeper die gekose argief kan publiseer of vervang, en of dié pip-weergawe werklik sy metadata voorberei. ’n Vaste vertroude argief of wheel bevestig nie hierdie roete nie. Moenie tydens passiewe inventarisering ’n onbetroubare pakket ophaal of bou nie. Sien pip se [download-opdrag](https://pip.pypa.io/en/stable/cli/pip_download/), [boustelsel-koppelvlak](https://pip.pypa.io/en/stable/reference/build-system/) en [veilige-installasieriglyne](https://pip.pypa.io/en/stable/topics/secure-installs/).

’n Sudo-reël wat `pip install` met ’n plaaslike projekpad wat die oproeper kies toelaat, skep ’n meer direkte bougrens. [pip aanvaar plaaslike projekgidse](https://pip.pypa.io/en/stable/topics/local-project-installs/) en roep hul boustelsel aan; die [boubackend voer bou-hooks uit wat deur die projek beheer word](https://pip.pypa.io/en/stable/reference/build-system/). Bevestig die effektiewe RunAs-identiteit, presiese argumentbeperkings en weierings, beheer oor die gekose projek en die geïnstalleerde pip-/backendgedrag voordat jy die reël as bevoorregte kode-uitvoering beskou. ’n Vaste vertroude projek of ’n reël wat paaie wat die oproeper kies uitsluit, bevestig nie hierdie roete nie. Hersien die reël en projekmetadata sonder om tydens passiewe inventarisering ’n pakket te installeer.

### nginx wat deur sudo loop met ’n konfigurasie wat die oproeper beheer

’n Onbeperkte root-bevoegde `nginx`-reël kan toelaat dat [`-c` ’n ander konfigurasie kies](https://nginx.org/en/docs/switches.html). Hersien die presiese sudo-argumente en uitsluitings, of die oproeper die konfigurasie kan verskaf, en of die gevolglike meester- of werkerprosesse toegang tot beskermde paaie behou. ’n Gekose `root` plus `autoindex` kan lêers deur ’n nuwe luisterpoort blootstel; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) kan ’n bevoorregte lêerskryfroete bied, maar die DAV-module is nie by verstek gebou nie en die teenwoordigheid daarvan, bereikbaarheid van die luisterpoort, lêertoestemmings en tydelike-lêergedrag moet nagegaan word. Die [`error_log`-direktief](https://nginx.org/en/docs/ngx_core_module.html#error_log) kan ook na ’n gekose lêer wys; om logboeke na ’n sensitiewe konfigurasielêer soos `/etc/ld.so.preload` te skryf, vereis ’n effektiewe bevoorregte skrywer en ’n beheerbare logrekord voordat dit ’n eskalasieroete word. Die uitvoerbare lêer se merker in `sudo -l` is ’n leidraad vir hersiening, nie bewys dat enige van dié roetes werk nie. Passiewe inventarisering moet nie nginx begin of herkonfigureer nie.

### Patroonvergelyking in bevoorregte Bash-aanwysings

Wanneer ’n Bash-skrip wat deur sudo toegelaat word ’n waarde van die oproeper lees en dit met `[[ "$expected" == $entered ]]` nagaan, interpreteer Bash die ongekwoteerde regteroperand as ’n patroon. ’n Jokerteken kan dus die vergelyking laat slaag sonder dat die verwagte waarde bekend is. As jy die operand kwoteer (`[[ "$expected" == "$entered" ]]`), word dit ’n letterlike stringvergelyking. Hersien die presiese sudo-reël, of die prompt bereikbaar is en wat die skrip ná die vergelyking doen; die sintaksis alleen bevestig nie ’n uitbuitbare roete nie. Vermy dit om tydens inventarisering die verwagte waarde te druk. Sien die [Bash-verwysing oor voorwaardelike konstruksies](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helpers wat lêers aflaai en uitvoer en deur sudo loop

’n Onbeperkte root-bevoegde sudo-toestemming vir ’n pasgemaakte helper verdien ’n datavloei-hersiening as dit ’n URL aanvaar wat die oproeper kies, die antwoord op skyf skryf en daardie lêer later met ’n interpreteerder of shell uitvoer. [Sudoers laat arbitrêre argumente toe wanneer ’n opdraginskrywing geen lys bevat nie](https://man7.org/linux/man-pages/man5/sudoers.5.html); ’n vaste uitvoerbare pad beperk nie wat die argumente kan kies nie. Bevestig die werklike URL-validering, uitvoerpad, suksesvertakking en daaropvolgende uitvoering in die geïnstalleerde helper. ’n Ooreenstemmende libcurl-invoer of drukbare string alleen bewys nie dié ketting nie.

Selfs ’n vaste uitvoerlêernaam kan vervangbaar wees tussen skryf en uitvoering wanneer die helper ’n **relatiewe pad in ’n werkgids wat die oproeper beheer** gebruik. Die hernoeming of vervanging van ’n root-besitte lêer word bepaal deur skryf- en soektoegang tot die gids en enige sticky-bit-beperkings, nie net deur die lêermodus nie; sien [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Kyk of die helper die pad later heropen of die reeds oop lêerbeskrywer gebruik, en of dit na ’n vertroude gids oorskakel voordat dit skryf. Ondersoek die sudo-beleid, helper en gidmetadata passief; moenie tydens inventarisering die bevoorregte aflaai of ’n wedloop uitvoer nie.

’n Root-sudo-aflaaihelper kan ook ’n **argument**-inspuiting blootstel wanneer dit ’n Bash-opdragstring soos `curl <caller input> -o <fixed output>` bou. ’n Filter wat spasies verwerp, laat steeds [Bash-hakiesuitbreiding](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) toe: ongekwoteerde elemente, geskei deur kommas, kan aparte curl-argumente word. As die invoer curl vóór die vaste `-o` bereik, kan ’n uitvoeropsie wat die oproeper verskaf die bestemming vir die eerste URL onder die helper se identiteit kies; [curl koppel uitvoeropsies in volgorde aan URL’s](https://curl.se/docs/manpage.html#-o). Bevestig die presiese shell, aanhalingstekens, invoervalidering, effektiewe sudo-reël, curl-argumentvolgorde en ondersteunde URL-skemas, en of die oproeper die afgehaalde grepe beheer of die resultaat kan lees. ’n Met PyInstaller verpakte uitvoerbare lêer kan Python-toepassingslogika bevat, maar sy verpakkingsmerker of ’n `curl`-string alleen bewys nie dié datavloei nie. Hersien ’n beperkte vanlyn kopie wanneer dit gemagtig is; roetine-inventarisering moet nie die helper uitvoer of data ophaal wat ’n aanvaller gekies het nie.

’n Root-sudo-shellskrip wat [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) aanroep, kies slegs ’n ongebruikte naam; dit **skep nie** die lêer nie. As die skrip later dié naam skep in ’n gids wat ’n ander gebruiker kan beïnvloed, dit dan heropen en die inhoud daarvan by ’n beskermde bestemming soos root se `authorized_keys` voeg, hersien ’n moontlike tydelike-lêerwedloop. Bevestig die presiese sudo-reël, gids- en lêereienaarskap, skeppings- en heropeningsvolgorde, kernbeskermings en of die bevoorregte skryfbewerking werklik aanvallerbeheerde grepe gebruik. ’n `mktemp -u`-string of ’n skryfbare `/tmp` alleen bewys nie die wedloop nie. Ondersoek die skrip en padmetadata sonder om dit uit te voer of tydens inventarisering ’n wedloop met sy tydelike lêer te veroorsaak.
