## Sudo द्वारा अनुमत interpreters

अगर `sudo -l` किसी user को root के रूप में interpreter चलाने की अनुमति देता है, तो इसे direct code execution मानें। Interpreters मनमाना code चलाने के लिए बनाए गए हैं, इसलिए `python3`, `perl`, `ruby`, `lua`, `node` या ऐसे ही binaries चलाने की अनुमति देने वाला नियम आमतौर पर root command execution के बराबर होता है, जब तक कि arguments पर कड़ी पाबंदी न हो और उनकी पुष्टि न की जाती हो।<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

समीक्षा का सामान्य तरीका: पहले user के privileges की सूची बनाएं, फिर interpreter के `-c` option से Python statement चलाएं।<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

अन्य interpreter के उदाहरण नीचे दिए गए हैं; सूचीबद्ध interpreter inline-code execution या child-process APIs का दस्तावेज़ीकरण करते हैं।<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

सटीक path मायने रखता है। अगर sudo rule `/usr/bin/python3` की अनुमति देता है, तो validation के दौरान उसी सटीक path का उपयोग करें।<sup>[[2]](#references)</sup>

`/usr/bin/python*` जैसा sudo executable glob Python 3 के लिए लिखी गई script को Python 2 के साथ भी चलाने की अनुमति दे सकता है। अगर script caller के नियंत्रण वाला text `input()` तक पहुँचाती है, तो [Python 2 उस text का expression के रूप में मूल्यांकन करता है](https://docs.python.org/2/library/functions.html#input); interpreter को स्पष्ट रूप से invoke करने पर script का shebang प्रभावी नहीं रहता। इसे execution path मानने से पहले, मेल खाने वाले installed binaries, प्रभावी RunAs और argument policy, denials तथा उपलब्ध input की पुष्टि करें।

Root-capable sudo rule में fixed script path इस बात को सीमित नहीं करता कि script क्या execute करती है। किसी readable Bash wrapper के लिए जाँचें कि क्या उसका पहला executable command, sudo द्वारा caller के चुने हुए arguments की अनुमति होने पर, `$1` जैसे unquoted positional parameter को **command word** के रूप में इस्तेमाल करता है। प्रभावी RunAs identity, password और argument policy, बाद के denials तथा script की वास्तविक branch की पुष्टि करें; `NOEXEC`, fixed safe argument list या ऐसा wrapper जो अपने command को validate करता है, नतीजा बदल सकते हैं। Enumeration के दौरान छोटी script को test command के साथ invoke करने के बजाय statically inspect करें।

`dotnet` के लिए unrestricted root-capable sudo rule की भी interpreter के लिहाज़ से समीक्षा करनी चाहिए। .NET SDK install होने पर, [`dotnet fsi` F# code को interactively या script से चलाता है](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/), और [`dotnet run` source से project execute करता है](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run)। पहले प्रभावी RunAs identity और सटीक argument policy की पुष्टि करें: किसी खास safe subcommand या trusted application तक सीमित rule एक अलग grant है, और केवल runtime वाले installation में SDK commands उपलब्ध नहीं हो सकते। Executable का नाम अकेले code execution का प्रमाण नहीं, बल्कि समीक्षा का संकेत है।

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## Sudo-allowed `tee`: मनमाना privileged file write

GNU `tee` standard input को file operand के रूप में दिए गए हर path पर कॉपी करता है। इसलिए, ऐसा sudo rule जो caller-controlled arguments के साथ `/usr/bin/tee` को root के रूप में चलाने की अनुमति देता है, मनमानी root file बनाने या overwrite करने की सुविधा देता है। `-a` जोड़ने से यह सुविधा append करने के लिए बदल जाती है। `PASSWD:` tag sudo authentication से संबंधित है; अपने आप में यह destination या standard input से पढ़े जाने वाले bytes को सीमित नहीं करता।<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

पहले सटीक rule की जाँच करें। किसी authorized test system पर, इस सुविधा को केवल ऐसे अस्थायी destination से validate करें जिसे सुरक्षित रूप से बनाया जा सके। आख़िरी `>/dev/null` केवल `tee` के standard output में कॉपी करने को suppress करता है।<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

`sudo` को producer से पहले रखने पर बाद का shell redirection elevated नहीं होता, क्योंकि destination को caller का shell खोलता है। जैसा कि ऊपर की pipeline में है, privileged process को writer होना चाहिए।<sup>[[1]](#references)[[15]](#references)</sup>

Write की पुष्टि करने के बाद, [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md) से उपयुक्त root-code-execution sink चुनें। एक देखी गई chain में root `tee` का उपयोग करके `/etc/cron.d/` के अंदर एक अल्पकालिक file बनाई गई, user-controlled script के ज़रिए backdoor लॉन्च किया गया, और execution के बाद cron file हटा दी गई। cron file हटाने से वह long-term persistence entry नहीं बनी, हालांकि system logs में गतिविधि के सबूत अब भी मौजूद थे।<sup>[[27]](#references)</sup>

## Sudo द्वारा अनुमत editors

अगर `sudo -l` किसी user को root के रूप में interactive editor चलाने की अनुमति देता है, तो इसे harmless file-editing permission नहीं, बल्कि command-execution surface मानें। Editors अक्सर shell commands चला सकते हैं, arbitrary files पढ़ या लिख सकते हैं, या editor के अंदर से external helpers invoke कर सकते हैं।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

सामान्य review flow: user के privileges सूचीबद्ध करें, फिर sudo के तहत हर अनुमत editor या pager चलाएँ।<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Nano के जरिए command execution

जब sudo के माध्यम से nano चलाने की अनुमति होती है, तो editor interface से command execution संभव हो सकता है।<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

फिर nano कमांड प्रॉम्प्ट में `id` या `/bin/sh` जैसी कोई कमांड दें।<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

यदि किसी interactive shell में उपयोगी terminal streams नहीं हैं, तो यह redirection form इसके standard output और error को descriptor 0 पर मैप करता है।<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

nano के version और build options के अनुसार key sequence बदल सकता है, लेकिन security issue वही है: editor root के रूप में चल रहा है और external commands चला सकता है।<sup>[[1]](#references)[[12]](#references)</sup>

### अन्य आम editor escapes

Vim-style editors आमतौर पर `:!` के ज़रिए command execution की सुविधा देते हैं।<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

`less` जैसे pagers shell execution भी उपलब्ध करा सकते हैं।<sup>[[14]](#references)</sup>

`apport-cli` को root के रूप में चलाने की अनुमति देने वाले sudo rule की भी इसी तरह pager जाँच करें। प्रभावित Apport versions crash report को `less` में attacker-adjustable terminal size के साथ खोल सकते थे; यदि sudo और pager की विशेष शर्तें पूरी होतीं, तो pager root shell दे सकता था। किसी version को vulnerable मानने से पहले प्रभावी sudo rule, pager configuration और distribution package fix की जाँच करें। Passive enumeration के दौरान crash उत्पन्न किए बिना या privileged report खोले बिना package और policy metadata पढ़ें। [Ubuntu's CVE record](https://ubuntu.com/security/CVE-2023-1326) में release-specific fixed package versions दिए गए हैं, जिनमें backported fixes भी शामिल हैं।

```text
!/bin/sh
```

## अन्य sudo और doas नियमों के खतरे

`sudo -l`, `sudo -V` और लागू `doas` policy से शुरुआत करें। अनुमत command, run-as user, arguments, environment और defaults को एक साथ पढ़ें। गैर-root service account के रूप में चलाने की अनुमति भी उस account की files तक पहुँच या root तक पहुँचने का रास्ता दे सकती है।

एक निश्चित sudo-अनुमत Python script भी अपनी RunAs identity के तहत shell command चला सकती है, यदि interactive, caller-नियंत्रित input को [`os.system()`](https://docs.python.org/3/library/os.html#os.system) में जोड़ा जाता है। Shell punctuation की denylist सुरक्षा स्थापित करने के लिए पर्याप्त नहीं है: [shell `$(...)` command substitution को भी पहचानता है](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)। पुष्टि करें कि अनुमत arguments input branch तक पहुँचते हैं, input सुरक्षित validation के बिना shell command तक जाता है, और प्रभावी sudo policy इच्छित RunAs user की अनुमति देती है। Script path या `os.system()` का call अकेले केवल जाँच का संकेत है; privileged script चलाए बिना source देखें।

`chattr` के लिए प्रभावी root sudo grant immutable (`i`) file attribute हटा सकता है, लेकिन इससे अकेले write access या नई identity नहीं मिलती। [`chattr` manual](https://man7.org/linux/man-pages/man1/chattr.1.html) के अनुसार, यह attribute बदलाव रोकता है और इसे केवल root या `CAP_LINUX_IMMUTABLE` वाला process बदल सकता है। सटीक sudo argument policy और filesystem support जाँचें, फिर अलग से सत्यापित करें कि attribute हटने के बाद caller file लिख सकता है और higher-identity consumer उसका उपयोग करता है। उदाहरण के लिए, login shell बदलने के लिए target account के स्वीकार्य credentials और उस shell के जरिए वास्तविक login भी आवश्यक है। Enumeration के दौरान policy, file attributes और permissions की समीक्षा करें, उन्हें बदलें नहीं।

यदि sudo password और one-time code, दोनों माँगता है, तो इन prerequisites को command grant से अलग रखें। पढ़ी जा सकने वाली `.google_authenticator` file में संवेदनशील seed material होता है, जबकि पुराना application या database password hash केवल मौजूदा account password का संभावित उम्मीदवार है; इनमें से कोई भी यह सिद्ध नहीं करता कि प्रभावी PAM configuration दूसरा factor स्वीकार करती है। अधिकृत होने पर सटीक RunAs और arguments की समीक्षा करें: RubyGems `gem` के लिए unrestricted root grant उसका editor command उजागर कर सकता है ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), लेकिन restricted grant या विफल authentication ऐसा नहीं करता। Passive enumeration में seed दिखाए बिना, password recover किए बिना, code बनाए बिना या privileged command चलाए बिना paths और policy रिपोर्ट करें।

Chef के `knife` के लिए unrestricted root-capable sudo grant की interpreter-स्तर पर समीक्षा करें: [Chef के दस्तावेज़ों के अनुसार `knife exec -E` स्थानीय रूप से Ruby string evaluate करता है](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). सत्यापित करें कि प्रभावी sudo rule `exec` subcommand और caller द्वारा दिए गए `-E` argument, इच्छित RunAs identity तथा लागू command denials या fixed arguments की अनुमति देता है। Installed binary या अन्य subcommands तक सीमित rule केवल जाँच का संकेत है। Passive enumeration में `knife` चलाए बिना rule रिपोर्ट करें।

Interactive `msfconsole` के लिए सटीक root-capable sudo grant भी संवेदनशील है: [GTFOBins उसके `irb` console का विवरण देता है](https://gtfobins.org/gtfobins/msfconsole/), जो sudo identity विरासत में ले सकता है। प्रभावी RunAs user, अनुमत argument list, command denials, `NOEXEC` या अन्य restrictions, installed console का व्यवहार और caller द्वारा interactive input देने की क्षमता की पुष्टि करें। केवल path highlight जाँच का संकेत है; passive enumeration में console न चलाएँ।

FreeBSD पर root `pkg update` और `pkg install *` तक सीमित sudo rule भी repository-trust review की माँग करता है। जाँचें कि caller `/etc/hosts` लिख सकता है या नहीं और क्या *प्रभावी* enabled repository configuration `signature_type: none` के साथ HTTP hostname उपयोग करती है। [FreeBSD `pkg.conf` manual](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) के अनुसार, `none` signature checks बंद करता है; केवल `pkg+http` होना यह सिद्ध नहीं करता। Package में install scripts हो सकते हैं ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), इसलिए यदि caller वास्तव में repository endpoint नियंत्रित कर सकता है और package चुन सकता है, तो वह root boundary पार कर सकता है। यह निष्कर्ष निकालने से पहले repository overrides, SRV/mirror resolution, प्रभावी sudo arguments, package selection और script execution सत्यापित करें। Enumeration के दौरान names redirect किए बिना या `pkg` चलाए बिना policy और छोटी local configuration files देखें।

`apt-get update` और `apt-get upgrade` के लिए root-capable sudo grant को भी repository-trust review की आवश्यकता है, यदि sudo caller-नियंत्रित `http_proxy` सुरक्षित रखता है। जाँचें कि प्रभावी APT proxy configuration वास्तव में उस variable का उपयोग करती है या नहीं और यह किन enabled repository requests को प्रभावित कर सकता है; proxy अकेले trusted signing key से authenticated archive के packages बदल नहीं सकता। [APT HTTP transport manual](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) proxy precedence बताता है, और [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) signature checks, insecure-repository overrides और unauthenticated packages की पुष्टि के बारे में बताता है। सटीक sudo RunAs और arguments, repository authentication policy, आवश्यक interactive acceptance और यह पुष्टि करें कि चुना गया upgrade package scripts को root के रूप में चलाता है या नहीं। Policy और local configuration की passive समीक्षा करें; enumeration के दौरान package traffic redirect न करें या upgrade न चलाएँ।

` snap install` के लिए root-capable sudo rule package-to-code boundary बन सकता है, यदि उसके arguments caller को local snap और permissive install mode चुनने देते हैं। [Snap के दस्तावेज़](https://snapcraft.io/docs/explanation/snap-development/install-modes/) बताते हैं कि `--dangerous` local-snap assertion checks छोड़ता है और `--devmode` confinement ढीला करता है; [initial installation के दौरान install hook चल सकता है](https://snapcraft.io/docs/reference/development/supported-snap-hooks/)। Protected host files तक पहुँच का दावा करने से पहले सटीक sudo argument/RunAs policy, snap file पर नियंत्रण, installed snapd द्वारा इन modes की स्वीकृति तथा hook की प्रभावी identity और confinement जाँचें। केवल `snap` binary या wildcard-जैसा rule इस chain को सिद्ध नहीं करता। Passive enumeration में package install न करें या उसका hook न चलाएँ।

किसी **non-root** account के custom credential-reading binary के लिए सटीक sudo grant मिलने पर, पहले उसे चलाए बिना granted binary और उसकी file permissions देखें। Embedded password gate केवल wide characters में दिख सकता है; [GNU `strings` 16-bit little-endian extraction का विवरण देता है](https://sourceware.org/binutils/docs/binutils/strings.html)। दिखने वाली string यह सिद्ध नहीं करती कि वही स्वीकार्य password है या success branch मौजूदा credential उजागर करती है। Binary का व्यवहार, protected data तक target account की पहुँच, credential validity और बाद में होने वाले account या group transition अलग-अलग सत्यापित करें। यदि वह account `docker` group में है, तो host-root access मानने से पहले socket access और daemon की rootful या rootless identity जाँचें; [Docker इस group के root-स्तरीय प्रभाव बताता है](https://docs.docker.com/engine/install/linux-postinstall/). Routine enumeration में binary चलाए या उसकी strings dump किए बिना sudo rule और group membership रिपोर्ट करें।

Application के maintenance scripts के लिए wildcard sudo rule की समीक्षा script path से आगे जाकर करें। जाँचें कि अनुमत script unrestricted arguments स्वीकार करती है या कम-privileged application account द्वारा लिखी जा सकने वाली settings पढ़ती है; फिर उन values को shell commands या subprocess environment तक trace करें। उदाहरण के लिए, ZoneMinder की [`zmupdate.pl` `mysqldump` command बनाकर उसे `qx` के जरिए चलाती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), जबकि [`zmdc.pl` daemon शुरू करने से पहले `ZM_LD_PRELOAD` setting को `LD_PRELOAD` में कॉपी करती है](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in)। यदि संबंधित input नियंत्रित किया जा सकता है और installed version में उस code तक पहुँचता है, तो इनमें से किसी script को root के रूप में चलाने वाला sudo rule trust boundary पार कर सकता है। प्रभावी sudo rule, application configuration पर write access और script source देखें; wildcard या setting अकेले execution का प्रमाण नहीं हैं।

- `SETENV`, `env_keep`, `secure_path` और `LD_PRELOAD` अन्यथा संकीर्ण command को import, library या PATH hijack में बदल सकते हैं। [Environment-variable guide](../linux-basics/linux-environment-variables.md) और [SUID/linker abuse](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md) देखें।

Shell wrapper के लिए सटीक root-capable `SETENV` grant मिलने पर, यदि wrapper literal import वाले fixed Python script को शुरू करता है, तो एक-hop review भी करें। `secure_path` shell command lookup को सीमित करता है, Python की [`PYTHONPATH` module search](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH) को नहीं; [`-E` और `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) Python को उस environment variable को अनदेखा करने देते हैं। इसे code execution मानने से पहले प्रभावी sudo tags और denials, wrapper branch, interpreter options, import resolution और caller-writable search directory की पुष्टि करें। छोटी scripts को static रूप से देखें; privileged wrapper न चलाएँ।

सटीक root-capable `neofetch ""` sudo grant तब भी shell configuration load कर सकता है, जब लागू sudo defaults caller-नियंत्रित `XDG_CONFIG_HOME` सुरक्षित रखते हों। [Neofetch का configuration loader](https://github.com/dylanaraps/neofetch/blob/master/neofetch) उस directory के नीचे `neofetch/config.conf` या `neofetch/config` source करता है; empty argument list इस lookup को नहीं रोकती। Privileged command चलाए बिना या configuration contents दिखाए बिना policy और file metadata देखें; पुष्टि करें कि installed loader, प्रभावी RunAs और argument policy, command denials, इस command के लिए sudo द्वारा variable को वास्तव में सुरक्षित रखना, और caller के किसी readable configuration path पर नियंत्रण—सभी क्या हैं। सुरक्षित रखा गया variable या installed Neofetch अकेले जाँच का संकेत है। [sudoers environment handling](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।

Unrestricted root-capable `facter` sudo rule के लिए custom-fact की अलग समीक्षा आवश्यक है। [Puppet के दस्तावेज़](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) के अनुसार, `--custom-dir` चुनी हुई directory से Ruby fact files load करता है। जाँचें कि सटीक sudo rule उस option की अनुमति देता है या नहीं, installed Facter उसे स्वीकार करता है या नहीं, और caller उस directory को नियंत्रित करता है या नहीं। Fixed-argument grant, स्पष्ट command denial या disabled custom facts नतीजा बदल सकते हैं। Passive enumeration में Facter चलाए या fact contents पढ़े बिना policy candidate रिपोर्ट करें।

`SETENV` वाले सटीक root-capable sudo script grant के लिए, `find` जैसे bare command names और sudo policy तथा script initialization के बाद प्रभावी `PATH` देखें। Sourced Bash file `enable -n [` भी चला सकती है: [इसके बाद Bash `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) में external `[` खोजता है, जब script बाद में उस command का उपयोग करती है। Privileged execution मानने से पहले लागू [sudoers environment और `secure_path` rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), `NOSETENV`/`NOEXEC` या denial entries, script और sourced-file flow तथा executable caller-controlled search directory की पुष्टि करें। Bare command वाली readable script जाँच का संकेत है, privileged execution का प्रमाण नहीं; sudo rule चलाए बिना उसका निरीक्षण करें।
- Caller-नियंत्रित `http_proxy` को सुरक्षित रखने वाला लागू sudo rule होने पर, `curl` से fixed URL fetch करने वाली privileged script भी caller द्वारा चुना गया response स्वीकार कर सकती है, यदि request उसी proxy से भेजी जाती है। यदि script फिर response ऐसे XML parser को देती है जो external entities resolve करता है, तो hostile response privileged process द्वारा पढ़ी जा सकने वाली files उजागर कर सकता है। सटीक sudo environment policy, `no_proxy` exclusions, माँगा गया URL, parser configuration और output destination जाँचें; proxy variable या XML parser अकेले vulnerability नहीं हैं। [curl proxy environment documentation](https://everything.curl.dev/usingcurl/proxies/env.html) variable का व्यवहार बताता है। Passive enumeration के दौरान network requests न करें या hostile XML parse न करें।
- Caller-प्रभावित data से PostScript file बनाने और फिर `ps2pdf -dNOSAFER` चलाने वाली root-capable sudo script की input-flow अलग से जाँचें। Ghostscript के अनुसार, यह flag `.setsafe` तक SAFER बंद करता है, जिससे process की OS permissions के भीतर PostScript file operations संभव होते हैं। Caller argument से बनाई गई SQL query attacker-controlled rows को PostScript template तक पहुँचा सकती है, लेकिन query string या `ps2pdf` invocation अकेले यह सिद्ध नहीं करते कि data executable PostScript syntax तक पहुँचता है। सटीक sudo rule, input-to-template का रास्ता, escaping, installed Ghostscript का व्यवहार और document interpret होने से पहले SAFER दोबारा सक्षम होता है या नहीं—इनकी पुष्टि करें। Passive enumeration के दौरान privileged conversion न चलाएँ। [Ghostscript का `-dNOSAFER` दस्तावेज़](https://ghostscript.readthedocs.io/en/master/Use.html) देखें।
- Shell script चलाने वाले sudo rule के लिए सुरक्षित रखे गए variables की तुलना script से करें। `if $CHECK_CONTENT; then` जैसा construct expanded value को command के रूप में चलाता है, इसलिए `CHECK_CONTENT` सुरक्षित रखने से fixed script path और arguments होने पर भी command execution संभव हो सकता है। उस विशिष्ट rule में जाँचना होगा कि branch तक पहुँचा जा सकता है या नहीं और environment वास्तव में सुरक्षित रखा जाता है या नहीं।<sup>[[2]](#references)[[22]](#references)</sup>
- Sudo-अनुमत Python script writable directory या cached `.pyc` file से code import कर सकती है। [Privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md) में cache वाला मामला दिया गया है।
- Root के रूप में चलने वाली fixed Python script interactive debugger भी उजागर कर सकती है। `pdb.set_trace()` या `pdb.post_mortem()` जैसे calls debug किए जा रहे process के context में Python statements चलाने देते हैं, यदि caller breakpoint या exception handler तक पहुँच सकता है **और debugger के input stream को नियंत्रित करता है**। Privileged handler trigger किए बिना enumeration के दौरान सटीक sudo RunAs rule, authentication और branch conditions, exception तक पहुँच, terminal/input ownership तथा debugger उसी privileged process में चलता है या नहीं—इनकी जाँच करें। किसी दूसरे terminal से जुड़े debugger तक socket request द्वारा exception पहुँचाना अपने-आप पहुँच नहीं देता। [Python debugger में statement evaluation और post-mortem mode का विवरण देता है](https://docs.python.org/3/library/pdb.html); script को static रूप से देखें।
- Fixed sudo-अनुमत Python script database या Unix socket से profile field पढ़कर उसे ऐसी string में जोड़ सकती है जो आगे `str.format()` के लिए **format string** बनती है। [Replacement fields attributes और mapping keys के बाद आ सकते हैं](https://docs.python.org/3/library/string.html#format-string-syntax), इसलिए attacker-controlled field `format()` को दिए गए objects की जाँच कर सकता है और उनसे सुलभ data उजागर कर सकता है, यदि परिणाम print हो या caller द्वारा पढ़ी जा सकने वाली जगह पर store हो। प्रभावी sudo RunAs identity, उस विशेष record पर write access, format string तक data flow, दिए गए objects और output visibility जाँचें। यह अपने-आप code execution नहीं है; attacker-controlled *values* के साथ trusted literal format string अलग मामला है। उजागर secret से OS account transition तभी संभव है जब वह account उसे स्वीकार करे। Privileged operation चलाए बिना script और socket permissions देखें।
- Root-capable Python wrapper caller-चुना URL GitPython के `Repo.clone_from` को दे सकता है। यदि wrapper Git का `protocol.ext.allow=always` भी सक्षम करता है, तो `ext::` remote external helper चला सकता है। सटीक sudo arguments, URL कहाँ से आता है, GitPython package version और vendor patch status, तथा wrapper unsafe protocols को स्पष्ट रूप से सक्षम करता है या नहीं—जाँचें। GitPython ने 3.1.30 में [unsafe-protocol का default guard](https://github.com/gitpython-developers/GitPython/commit/2625ed9) जोड़ा; `git` executable का version अलग तथ्य है। Passive review में केवल rule और सीमित source पढ़ें; clone न चलाएँ।
- Repository-cloning CLI को cross-user sudo grant shell-string injection का अलग रास्ता उजागर कर सकता है। Trace करें कि caller-चुना repository argument Node.js [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) या किसी अन्य shell-command builder तक सुरक्षित argument separation के बिना पहुँचता है या नहीं; Node का `exec` command string shell को देता है। Privileged clone चलाए बिना enumeration के दौरान wrapper देखें और सटीक RunAs user, अनुमत subcommands और arguments, installed wrapper code तथा input validation की पुष्टि करें। Repository tool का नाम या unrestricted sudo rule अकेले command injection सिद्ध नहीं करता।
- Custom root-owned wrapper सुरक्षित दिख सकता है क्योंकि उसकी binaries और scripts writable नहीं हैं, फिर भी privileged action चलाने का उसका निर्णय ऐसे flag, local API value या service state पर निर्भर हो सकता है जिसे unprivileged user बदल सकता है। हर gate को उसके input और authorization checks तक trace करें। Enumeration के दौरान operational state बदले बिना configuration और permissions देखें; wrapper के भीतर `systemd-run` call तभी प्रासंगिक है जब gate को प्रभावित किया जा सके।
- Sudo के जरिए root के रूप में चलने वाला backup client caller-चुनी configuration file (उदाहरणार्थ `npbackup-cli -c`) स्वीकार कर सकता है। सटीक run-as user और अनुमत arguments जाँचें, फिर देखें कि caller configuration path, backup source paths और repository या read/restore options नियंत्रित करता है या नहीं। Readable config में encrypted repository secret होने पर भी client उसका उपयोग कर सकता है, लेकिन rule अकेले repository access या root-file disclosure सिद्ध नहीं करता। Backup चलाए या contents dump किए बिना authorization सत्यापित करें।
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) `--password-command` का समर्थन करता है, जो repository password पाने के लिए program चलाता है। यदि sudo rule कम-privileged user को caller-चुना password command और ऐसा subcommand देकर root के रूप में restic चलाने देता है जिसे password चाहिए, तो helper root के रूप में चल सकता है। सटीक sudo arguments और exclusions की समीक्षा करें; केवल condition enumerate करने के लिए helper या backup command न चलाएँ।
- Privileged `restic backup` grant file-read boundary भी पार कर सकता है, यदि उसके sudo argument pattern से caller source और ऐसा repository दोनों चुन सकता है जिसे वह बाद में पढ़ और decrypt कर सकता है। [Sudoers argument wildcards whitespace और slashes से match कर सकते हैं](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), इसलिए trailing wildcards देखें; यह न मानें कि fixed repository prefix source को सीमित करता है। [Restic local और remote repositories में backup कर सकता है](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), लेकिन local repository में अभी-अभी लिखे गए root-only objects हो सकते हैं; इसे disclosure मानने से पहले प्रभावी sudo policy, backend access, repository password और बने objects की permissions की पुष्टि करें। Backed-up SSH key तभी access देती है जब destination account उसे स्वीकार करे। Passive review के दौरान जाँच के लिए backup न चलाएँ।
- Unrestricted custom maintenance या backup command output path स्वीकार कर सकती है या अपना job scheduler दे सकती है। File-write रास्ते के लिए सटीक sudo rule और run-as user, फिर caller द्वारा data और destination दोनों नियंत्रित किए जा सकते हैं या नहीं—सत्यापित करें। Scheduled-command रास्ते के लिए scheduler की execution identity, command input और अतिरिक्त password या authorization gate सत्यापित करें। Command name या `NOPASSWD` अकेले किसी भी रास्ते को सिद्ध नहीं करता। [Root-owned files में लिखना](../interesting-files-permissions/write-to-root.md) और [cron तथा systemd timers](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md) देखें।
- Fixed sudo command shared writable directory से predictable configuration file load कर सकती है। Trace करें कि caller उस file को बदल सकता है या नहीं और उसके source तथा destination fields privileged fetch या copy नियंत्रित करते हैं या नहीं। Local-file URL से केवल sudo RunAs account द्वारा पढ़ा जा सकने वाला data उजागर हो सकता है; protected destination के साथ caller-controlled source write path बना सकता है। Installed program का URL handling, destination path checks, प्रभावी sudo rule और output की पहुँच की पुष्टि करें। केवल writable `/tmp` configuration path जाँच का संकेत है; privileged transfer चलाए बिना binary और file metadata देखें।
- `git apply` के लिए sudo rule RunAs account से caller-controlled patch द्वारा चुनी गई files लिखवा सकता है। [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) में crafted patch symlink बना सकता था और फिर working tree से बाहर लिख सकता था, भले command `--unsafe-paths` स्वीकार न करे। प्रभावी sudo argument rule, patch source, RunAs account की working-directory access और installed Git fix या vendor backport जाँचें। `--unsafe-paths` स्वीकार करने वाला unrestricted rule अलग स्पष्ट option risk है; Git version या `git apply` permission अकेले protected file बदलना सिद्ध नहीं करता। Passive enumeration के दौरान untrusted patch लागू न करें।
- Root-capable `clamscan --debug` rule read boundary पार कर सकता है, यदि lower-privileged user DMG image दे सकता है और installed parser [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html) से प्रभावित है, जिससे debug output के जरिए file contents उजागर हो सकते थे। Crafted file scan किए या enumeration के दौरान protected output दिखाए बिना अनुमत arguments और scan path, input पर नियंत्रण, प्रभावी RunAs account, engine patch/backport तथा output caller को दिखता है या नहीं—सत्यापित करें। यदि अधिक व्यापक rule `--file-list`/`-f` की अनुमति देता है, तो उस file-list व्यवहार की अलग समीक्षा करें; `--debug <scan-path>` तक सीमित policy इसकी अनुमति नहीं देती। Policy और package metadata देखें।
- Caller-चुनी encrypted disk image खोलने वाला root-capable sudo rule और उससे बने mapper को mount करने वाला दूसरा rule, caller-नियंत्रित files को host के mount namespace में ला सकते हैं। दोनों प्रभावी rules और arguments, image तथा mapper name पर नियंत्रण, वास्तविक mount target और resulting file owner तथा mode की पुष्टि करें। Set-user-ID transition के लिए सुलभ executable, उसे लागू करने वाले mount options (`nosuid` इसे रोकता है) और लागू process या MAC policy भी आवश्यक हैं; केवल image खोलना या mount करना जाँच का संकेत है। मौजूदा backup से अलग रास्ते के लिए उसमें मौजूद वास्तविक key और उपयोगी readable secret आवश्यक है। Passive enumeration में image खोले या mount किए बिना policy और paths देखें। [cryptsetup manual](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) और [mount options](https://man7.org/linux/man-pages/man8/mount.8.html) देखें।
- Shell या Python script के लिए root-capable sudo rule मिलने पर working-directory की समीक्षा करें, यदि script fixed directory में जाए बिना `./helper` चलाती है। `subprocess.run` को दिया गया Python list `['./helper']` भी caller-चुनी working directory के उसी व्यवहार के अधीन हो सकता है। Caller writable directory चुनकर वहाँ उस relative name वाला executable रख सकता है; script में कहीं और absolute path होने से यह call सुरक्षित नहीं होती। Code execution मानने से पहले प्रभावी rule, `runchdir` या directory बदलने वाली अन्य policy, script flow और branch तक पहुँच, writable तथा executable directory और mount/`NOEXEC` restrictions की पुष्टि करें। Unreadable script का व्यवहार तब तक अज्ञात है जब तक अधिकृत तरीके से उसका source न देखा जाए। Helper चलाने के बजाय scripts की static समीक्षा करें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) working-directory policy का विवरण देता है।
- Root-capable sudo के तहत चलने वाला fixed Python validator भी caller-चुनी data file evaluate कर सकता है। [Python का `eval()` दस्तावेज़ untrusted input के विरुद्ध चेतावनी देता है](https://docs.python.org/3/library/functions.html#eval): input suffix check, arithmetic prefix या validation branch sandbox नहीं है, यदि बाकी expression `eval` तक पहुँचता है। इसे execution path कहने से पहले प्रभावी sudo rule, caller exact file चुन और नियंत्रित कर सकता है या नहीं, parser की branch conditions और expression construction तथा privileged process identity की पुष्टि करें। Readable script में `eval` की मौजूदगी अकेले जाँच का संकेत है; enumeration के दौरान validator चलाए या test expression submit किए बिना source और file permissions देखें।
- Root-capable sudo Ruby wrapper जो relative YAML filename पढ़ता है, जैसे `YAML.load(File.read("dependencies.yml"))`, caller की working directory से input ले सकता है, जब तक wrapper या sudo policy directory निश्चित न करे। सटीक अनुमत arguments, directory और file permissions तथा installed Psych का व्यवहार जाँचें: पुराने `YAML.load` implementations मनमाने Ruby objects deserialize कर सकते थे, जबकि नए releases default रूप से classes सीमित करते हैं। Static call site केवल जाँच का संकेत है; पुष्टि करें कि file वास्तव में caller-writable directory से आती है और installed loader खतरनाक classes स्वीकार करता है। Untrusted input के लिए स्पष्ट न्यूनतम class allowlist वाला `safe_load` प्राथमिकता से उपयोग करें। [Ruby 3.0 Psych documentation](https://docs.ruby-lang.org/en/3.0/Psych.html) और [Ruby 3.1 Psych documentation](https://ruby-doc.org/core-3.1.2/Psych.html) देखें।

- `sudo go run /absolute/file.go` के लिए सटीक root-capable grant मिलने पर, यदि Go source relative WASM file पढ़ता है और उसका परिणाम जाँचने के बाद relative shell script चला सकता है, तो working-directory की समीक्षा करें। प्रभावी RunAs, command arguments और denials, caller-writable current directory, WASM से branch तक data flow तथा branch helper चलाती है या नहीं—इनकी पुष्टि करें। Fixed sudo `runchdir`, `os.Chdir` या [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) lookup location बदल सकते हैं। Static रूप से साथ दिखना केवल candidate है; Go, WASM या helper चलाए बिना source देखें।
- `sudoedit` और argument wildcards के लिए exact version और rule checks आवश्यक हैं; [checklist](linux-privilege-escalation-checklist.md) में sudoedit file-edit issue शामिल है। Wildcard path पर cross-user `sudoedit` grant के लिए प्रभावी `sudoedit_follow` या `FOLLOW` setting, `sudoedit_checkdir`, resolved target और हर parent entry को कौन बदल सकता है—जाँचें। पहला symlink follow करने दे सकता है, जबकि दूसरा बंद करने से writable-directory checks हटते हैं; इनमें से कोई भी setting अकेले दूसरे user की file में write स्थापित नहीं करती। यह निष्कर्ष निकालने से पहले installed sudo policy और exact matched arguments की पुष्टि करें। [sudoers option definitions](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) देखें।
- Sudoers command rule में argument wildcard whitespace के साथ-साथ path characters से भी match कर सकता है। Read-capable command के लिए `/restricted/*` जैसा argument अतिरिक्त file argument को matching prefix के बाद स्वीकार कर सकता है। Exact run-as user, command path, argument pattern और बाद के denials की समीक्षा करें; file पढ़ पाना command execution का प्रमाण नहीं है। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) argument globs और command-path globs के बीच अंतर बताता है।
- Path-जैसा दिखने वाला argument glob `../` से भी match कर सकता है। उदाहरण के लिए, root-capable `node /opt/scripts/*.js` rule caller-नियंत्रित JavaScript file को `/opt/scripts` के बाहर चलाने दे सकता है, यदि दिया गया pathname `/opt/scripts/` से शुरू होता है और parent-directory segments के जरिए resolve होता है। यह **argument** glob है; Node executable के command-path glob में slash matching के नियम अलग हैं। Code execution का निष्कर्ष निकालने से पहले प्रभावी rule, बाद के denials, pathname resolution, target file पर नियंत्रण तथा sudoers regular-expression या digest restrictions जाँचें। [sudoers wildcard rules](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) और [Node command-line documentation](https://nodejs.org/api/cli.html) देखें।
- Archivers और अन्य utility programs में execution hooks हो सकते हैं। यह न मानें कि केवल shells या interpreters commands चला सकते हैं; अनुमत arguments को [GTFOBins](https://gtfobins.github.io/) से मिलाकर जाँचें।
- Unrestricted root-capable `qpdf` rule PDF attachments के जरिए privileged file उजागर कर सकता है: qpdf 10.2 और बाद के versions output PDF के साथ `--empty` तथा `--add-attachment file ... --` का समर्थन करते हैं। यदि privileged process चुना हुआ source पढ़ सकता है और PDF caller-accessible path पर लिख सकता है, तो output में source bytes हो सकते हैं। File disclosure संभव है, यह निष्कर्ष निकालने से पहले प्रभावी sudo arguments और exclusions, qpdf version, source access तथा output path की समीक्षा करें। Root SSH key पढ़ना login के लिए तभी उपयोगी है जब वह key valid हो और root SSH authentication की अनुमति हो। [qpdf attachment options](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments) देखें।
- Sudo timestamp reuse cache policy, owning user, terminal/session और permissions पर निर्भर करता है। [Privilege escalation guide](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) में checks दिए गए हैं।
- `doas` के अपने rules और configuration होते हैं। [doas section](../linux-basics/linux-privilege-escalation/README.md#doas) में बताए अनुसार अनुमत commands और writable configuration paths जाँचें।

### Sudo के जरिए चलाए जाने वाले build और package tools

Foundry के `forge` के लिए unrestricted sudo grant तब भी महत्वपूर्ण हो सकता है, जब RunAs identity कोई अन्य non-root user हो। `--use` जैसे compiler options local executable चुन सकते हैं और `forge flatten -o` output file चुनता है। Grant को exploitable मानने से पहले installed Forge version, सटीक sudo arguments, accessible project और compiler paths, output permissions तथा प्रभावी environment जाँचें। `PATH` के जरिए मिला relative helper executable version और environment पर निर्भर रास्ता है; इसे हर Forge build का गुण न मानें।<sup>[[23]](#references)[[24]](#references)</sup>

Unrestricted root-capable `pacman` grant केवल package queries तक सीमित नहीं है: `-U` local package स्वीकार करता है, packages में install scripts हो सकते हैं और `--hookdir` कोई दूसरी hook directory चुनता है। जाँच से पहले प्रभावी sudo rule, argument restrictions और exclusions की समीक्षा करें; passive enumeration के लिए package install करना या hook चलाना आवश्यक नहीं है।<sup>[[25]](#references)[[26]](#references)</sup>

Fixed sudo shell wrapper named npm dependency install करके फिर Node application शुरू कर सकता है। उसके exact RunAs rule, package पहले से installed है या नहीं, प्रभावी `HOME` और npm `userconfig`, project configuration या command-line overrides तथा lower-privileged user उस नाम के लिए registry या लौटाए गए package को नियंत्रित करता है या नहीं—इनकी समीक्षा करें। [npm per-user और per-project `.npmrc` lookup का विवरण देता है](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); sudo का `HOME` व्यवहार installed policy और distribution पर निर्भर करता है, इसलिए privileged npm process writable user `.npmrc` पढ़े भी सकता है और नहीं भी। यदि नई install की गई package privileged application import करती है, तो उसका module code उस application की identity के तहत चल सकता है। Install-time scripts अलग, version और configuration पर निर्भर रास्ता हैं; [npm उनके lifecycle और user handling का विवरण देता है](https://docs.npmjs.com/cli/v6/using-npm/scripts/)। `.npmrc` path या `npm install` line अकेले जाँच का संकेत है। Passive enumeration के दौरान install या application शुरू किए बिना rule, छोटा wrapper, configuration paths और package provenance देखें।

Root-capable `pip` या `pip3 download` grant भी package-build review का संकेत है, यदि arguments caller को untrusted source distribution चुनने देते हैं—भले URL pattern उसे local service और `.tar.gz` suffix तक सीमित करे। `pip download` archive URLs स्वीकार करता है और package metadata resolve करता है; sdist तैयार करने के दौरान archive केवल save होने से पहले उसका build backend या legacy `setup.py` code चल सकता है। सटीक sudo RunAs और argument rule, caller चुना archive publish या replace कर सकता है या नहीं, और वह pip version वास्तव में metadata तैयार करता है या नहीं—सत्यापित करें। Fixed trusted archive या wheel इस रास्ते को स्थापित नहीं करता। Passive enumeration के दौरान untrusted package fetch या build न करें। pip का [download command](https://pip.pypa.io/en/stable/cli/pip_download/), [build-system interface](https://pip.pypa.io/en/stable/reference/build-system/) और [secure-install guidance](https://pip.pypa.io/en/stable/topics/secure-installs/) देखें।

Caller-चुने local project path के साथ `pip install` की अनुमति देने वाला sudo rule अधिक सीधा build boundary है। [pip local project directories स्वीकार करता है](https://pip.pypa.io/en/stable/topics/local-project-installs/) और उनका build system चलाता है; [build backend project-नियंत्रित build hooks चलाता है](https://pip.pypa.io/en/stable/reference/build-system/). Rule को privileged code execution मानने से पहले प्रभावी RunAs identity, exact argument restrictions और denials, चुने हुए project पर नियंत्रण तथा installed pip/backend behavior की पुष्टि करें। Fixed trusted project या caller-चुने paths को बाहर रखने वाला rule यह रास्ता स्थापित नहीं करता। Passive enumeration के दौरान package install किए बिना rule और project metadata देखें।

Unrestricted root-capable `easy_install` grant इससे जुड़ा legacy package-build संकेत है। [Setuptools के दस्तावेज़](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) के अनुसार, Easy Install local project directory स्वीकार करता है और source distributions बनाता है; caller-नियंत्रित project उस build के दौरान sudo identity के तहत अपना `setup.py` चला सकता है। प्रभावी RunAs account, exact command और argument restrictions (बाद के denials सहित), चुने हुए project पर नियंत्रण तथा installed tool के व्यवहार की पुष्टि करें। Fixed trusted project या caller-चुने source की अनुमति न देने वाली policy यह रास्ता स्थापित नहीं करती। Enumeration के दौरान package install किए बिना rule और project metadata देखें।

Caller-चुने URL के साथ `setuptools.package_index.PackageIndex.download` उपयोग करने वाला sudo-अनुमत Python wrapper, `pip download` से अलग मामला है: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) प्रभावित releases में 78.1.1 से पहले URL-derived filename द्वारा intended download directory से बाहर जाने और process permissions के साथ write करने का विवरण देता है। प्रभावी sudo RunAs और argument rule, wrapper caller का URL इसी exact API को देता है या नहीं, installed build या vendor backport और resulting path कहाँ resolve होता है—इनकी पुष्टि करें। Version string या writable download directory अकेले arbitrary write स्थापित नहीं करते। Enumeration के दौरान URL fetch या file write किए बिना छोटा wrapper और package metadata देखें।

Caller-चुनी `.spec` file PyInstaller को देने वाले sudo-अनुमत build wrapper की भी इसी trust-boundary समीक्षा की आवश्यकता है। PyInstaller spec build के दौरान evaluate होने वाला executable Python है और उसकी `datas` entries build identity द्वारा पढ़ी जा सकने वाली files को artifact में bundle कर सकती हैं। सटीक RunAs user, sudo argument और denial rules, wrapper की path और branch handling, चुनी हुई spec file पर नियंत्रण तथा resulting artifact तक पहुँच की पुष्टि करें। केवल `.py` input की अनुमति देना या PyInstaller installed मिलना spec file पर नियंत्रण या privileged execution स्थापित नहीं करता। Passive review में केवल सीमित wrapper file और metadata पढ़ें; build न चलाएँ। [PyInstaller spec-file documentation](https://pyinstaller.org/en/stable/spec-files.html) देखें।

### Sudo के जरिए चलाए जाने वाले preset और plugin loaders

Caller-चुना preset या plugin directory स्वीकार करने वाले Python tools sudo से मिले privileges के तहत code import कर सकते हैं। उदाहरण के लिए, BBOT `-p` के साथ preset स्वीकार करता है, और उसके [custom-module documentation](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) में `module_dirs` entries द्वारा अतिरिक्त Python module directories चुनने का विवरण है। यदि प्रभावी sudo rule caller-चुना preset स्वीकार करता है और caller चुनी directory में module नियंत्रित करता है, तो import privileged user के रूप में code चला सकता है—संभवतः tool द्वारा invalid module अस्वीकार किए जाने से पहले। Enumeration में module load किए बिना installed version, सटीक sudo run-as और argument policy तथा preset और module paths के ownership की जाँच करें।

### Sudo के जरिए चलाया जाने वाला Backdrop command-line tool

[Bee](https://github.com/backdrop-contrib/bee) Backdrop CMS के लिए PHP command-line tool है। इसके `eval` (`php-eval`) और `php-script` commands caller द्वारा दिया गया PHP चला सकते हैं। इसलिए, यदि sudo rule Bee executable को root के रूप में unrestricted arguments के साथ चलाने देता है और Bee Backdrop installation bootstrap कर सकता है, तो root code execution संभव हो सकता है। Site directory से चलाएँ या global `--root=<directory>` option से site चुनें; केवल Bee या Backdrop `settings.php` file मिलना sudo permission, usable site या सफल bootstrap सिद्ध नहीं करता। जाँच से पहले प्रभावी sudo rule, command exclusions, executable की identity और site तक पहुँच की समीक्षा करें। Passive enumeration में Bee चलाए बिना rule और file paths देखें। PHP command additions के लिए [Bee command changelog](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) देखें।

### Sudo के जरिए चलाए जाने वाले terminal servers

`mosh-server` invoking user के रूप में interactive terminal server शुरू करता है। यह high UDP port और session key चुनता है, दोनों caller को बताता है और client के connect होने पर सामान्यतः उसी user का login shell शुरू करता है। इसलिए `mosh-server` के लिए unrestricted root-capable sudo grant shell review candidate है, भले server command स्वयं detach हो जाए। Server शुरू किए या कोई live session key दिखाए बिना प्रभावी RunAs identity, अनुमत arguments और exclusions, installed binary, shell, client availability तथा UDP access जाँचें। [Mosh server manual](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) और [upstream design notes](https://github.com/mobile-shell/mosh#how-it-works) देखें।

### Caller की task file को rewrite करने वाले privileged backup wrappers

Root के रूप में चलने वाला shell wrapper caller द्वारा चुनी task file स्वीकार कर सकता है, source paths से `../` हटा सकता है, यह जाँच सकता है कि हर परिणाम अनुमत directory से शुरू होता है या नहीं, task file rewrite कर सकता है और फिर उसका *pathname* backup program को दे सकता है। पूर्ण canonical resolution के बाद transformed path की समीक्षा करें: string replacement का एक pass नया traversal sequence उजागर कर सकता है जिसे lexical prefix check स्वीकार कर लेता है। यह भी जाँचें कि backup program transformed in-memory data पढ़ता है या file दोबारा खोलता है। यदि वह file दोबारा खोलता है, तो rewrite विफल होने पर original input वहीं रह सकती है।

Linux पर `fs.protected_regular` world-writable sticky directory में दूसरे user की regular file पर `O_CREAT` write रोक सकता है। यह सुरक्षा देता है, लेकिन यदि shell wrapper write error अनदेखा करता है, तो वह original task file के साथ आगे चल सकता है। Setting, file owner और directory तथा wrapper failure पर रुकता है या नहीं—सत्यापित करें। Path केवल तभी file-disclosure candidate है जब प्रभावी sudo rule privileged user के रूप में wrapper चलाने देता हो, caller task input और readable backup destination नियंत्रित करता हो, और backup utility वास्तव में protected sources शामिल करती हो। Enumeration के दौरान backup चलाए बिना इन शर्तों की जाँच करें।

### Privileged packet tools पर argument wildcards

`tcpdump` के sudo rule में **argument pattern** का `*` whitespace और slashes से match कर सकता है, इसलिए pathname-जैसी restriction भी अतिरिक्त option text की अनुमति दे सकती है। यह command के executable path में wildcard से अलग है; पूरी RunAs rule और बाद के denials देखें। यदि options inject किए जा सकते हैं, तो अनुमत invocation और installed [`tcpdump` option semantics](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) तय करते हैं कि `-F`, `-V`, `-r`, `-w` या `-Z` उपयोगी read/write primitive देते हैं या नहीं। `-V` capture filenames की list पढ़ता है, मनमानी file का सामान्य dump नहीं। AppArmor या दूसरी MAC policy file access रोक सकती है, भले sudo command की अनुमति देता हो; disk पर profile file होना यह सिद्ध नहीं करता कि वह loaded या enforcing है। निष्कर्ष निकालने से पहले authorization और policy की passive समीक्षा करें। [sudoers manual](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) wildcard के अंतर का विवरण देता है।

केवल `tcpdump` executable सूचीबद्ध करने वाला root-capable sudo rule, जिसमें argument restriction न हो, भी समीक्षा योग्य है। [tcpdump manual](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) के अनुसार, `-C` या `-G` saved capture को rotate करने पर `-z` post-rotation command चलाता है; `-Z` या compile-time default उस command के चलने से पहले privileges drop कर सकता है। Rule को escalation path मानने से पहले प्रभावी sudo rule, installed build, privilege-drop behavior और rotation संभव है या नहीं—सत्यापित करें। Highlighted rule candidate है, root command execution का प्रमाण नहीं।

### Sudo के जरिए चलाए जाने वाले Nmap wrappers

जब sudo-अनुमत `nmap` path shell wrapper हो, तो सटीक अनुमत path और उसके द्वारा आगे भेजे जाने वाले हर option की जाँच करें। परिचित `--script` spelling को रोकना NSE code loading को आवश्यक रूप से नहीं रोकता: Nmap का [`--datadir`](https://nmap.org/book/man-misc-options.html) data files चुनता है और scripting सक्षम होने पर NSE चुनी data directory से [`nse_main.lua` load करता है](https://nmap.org/book/nse-implementation.html)। कुछ installed builds alternate long-option spellings भी स्वीकार करते हैं, इसलिए restrictions की तुलना उस binary के वास्तविक parser से करें। [`--excludefile`](https://nmap.org/book/man-target-specification.html) file-read का अलग surface है; parser errors text उजागर कर सकते हैं। Enumeration के दौरान scans चलाए बिना प्रभावी sudo rule, wrapper logic, Nmap version, directory पर नियंत्रण और MAC policy जाँचें।

### Sudo के जरिए चलाए जाने वाले Mercurial pull hooks

`sudo hg pull /fixed/source` में fixed source होने पर भी **receiving** repository current working directory से चुनी जाती है, जब तक command `-R` से उसे निश्चित न करे। Caller-नियंत्रित receiving repo `.hg/hgrc` में hooks परिभाषित कर सकती है और hook sudo RunAs user के रूप में चल सकता है। [Mercurial अविश्वसनीय user या group के स्वामित्व वाली repository configuration अनदेखी करता है](https://mercurial-scm.org/help/topics/config), इसलिए इसे code execution मानने से पहले RunAs account के trusted users/groups और exact working directory देखें। Passive review के लिए policy और config पढ़ना पर्याप्त है; enumeration के लिए pull या hook न चलाएँ।

### Sudo के जरिए चलाए जाने वाले Git pull hooks

सटीक root-capable `sudo git pull` grant के लिए working directory से चुनी गई **receiving** repository भी जाँचें। Caller-owned repository में executable `post-merge` hook हो सकता है, जो pull द्वारा सफल merge किए जाने पर Git process की identity के साथ चलता है; [Git इस hook का विवरण देता है](https://git-scm.com/docs/githooks) और [pull में merge बनाम rebase behavior](https://git-scm.com/docs/git-pull) बताता है। प्रभावी sudo rule और CWD, active hook path और उसकी permissions तथा नए commits वाला merge संभव है या नहीं—सत्यापित करें। Failed, no-op या केवल rebase करने वाला pull इस hook path को स्थापित नहीं करता। Privileged pull चलाए बिना policy और repository metadata देखें।

### Sudo के जरिए चलाए जाने वाले rsync archive copies

`sudo rsync -a ... /writable/source/* /fixed/destination/` के लिए **sudoers argument pattern** का `*` whitespace से match करके source और destination के बीच अतिरिक्त option स्वीकार कर सकता है। यह filenames के shell expansion से अलग है। यदि caller source भर सकता है और destination privileged rsync process के लिए writable है, तो [`--chown`](https://download.samba.org/pub/rsync/rsync.1) privileged ownership माँग सकता है, जबकि archive mode permission bits सुरक्षित रखता है; इससे संभवतः owned SetUID file बन सकती है। सटीक [sudoers wildcard semantics](https://man7.org/linux/man-pages/man5/sudoers.5.html), rsync version, बाद के denials, filesystem `nosuid` और MAC policy जाँचें। Matching rule review candidate है, सफल privilege escalation का प्रमाण नहीं।

### Sudo के जरिए चलाया जाने वाला packet-filter rule export

`iptables` और `iptables-save` (या matching `ip6tables` pair), दोनों के लिए unrestricted root-capable grant file-write review की माँग करता है। `comment` match caller-चुना rule text स्वीकार करता है, जबकि `iptables-save -f` serialized ruleset को चुने pathname पर लिखता है।<sup>[[20]](#references)[[21]](#references)</sup> उपयोगी payload इस बात पर निर्भर करता है कि installed backend comments को कैसे serialize करता है और destination file export में अन्य lines स्वीकार करती है या नहीं; `iptables-save` अकेले arbitrary चुना content नहीं देता। सटीक sudo RunAs identity, arguments और exclusions, उपलब्ध match extension, backend तथा destination permissions जाँचें। Enumeration के दौरान firewall rules बदले या file लिखे बिना grant देखें।

### Privileged Below logging directory

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ने 0.9.0 से पहले के Below releases को प्रभावित किया, जो world-writable `/var/log/below` directory बनाते थे। यदि service या अनुमत sudo command प्रभावित build को root के रूप में चलाती है, तो non-sticky log directory में write और traverse कर सकने वाला user privileged process द्वारा log खोलने से पहले log entry को symlink से बदल सकता है। Installed package का patch status, exact privileged execution path, प्रभावी directory access, sticky bit और ACLs तथा `/var/log/below/error_root.log` का metadata देखें। World-writable path या sudo rule अकेले पूरी chain स्थापित नहीं करता। Sticky directory या vendor backport आकलन बदलता है। Passive enumeration में केवल metadata देखें; link बनाने या privileged program चलाने की आवश्यकता नहीं है।

### Writable inputs से privileged support-bundle collection

`sudo` द्वारा अनुमत support-profile script root के रूप में fixed log paths पढ़कर उनकी सामग्री profile archive में कॉपी कर सकती है। File reads के लिए वास्तविक script देखें, फिर जाँचें कि caller किसी source path या parent directory entry को symlink से बदल सकता है या नहीं। यदि privileged read उस link को follow करता है और resulting archive caller पढ़ सकता है, तो protected file उजागर हो सकती है। Sudo grant, writable source path, privileged read और readable output—सभी आवश्यक हैं; writable log या profile filename अकेला पर्याप्त नहीं। Enumeration के दौरान files बदले या profile generate किए बिना प्रभावी permissions और link metadata देखें। [Nagios XI support guidance](https://support.nagios.com/forum/viewtopic.php?t=62758) उसका root-run profile script और output archive बताता है, जो दिखाता है कि ऐसे bundles के inputs और output access पर प्रतिबंध क्यों आवश्यक है।

### Root-run Python archive restore scripts

Python restore script के लिए tightly scoped sudo rule होने पर भी उसके archive input की समीक्षा आवश्यक है। यदि caller archive चुन या बदल सकता है और script उसे root के रूप में `tarfile.extractall(filter="data")` से extract करती है, तो filter पर भरोसा करने से पहले interpreter के security updates जाँचें। CPython ने कई symlink और hard-link filter bypasses, जिनमें CVE-2025-4517 शामिल है, 3.9.23, 3.10.18, 3.11.13, 3.12.11 और 3.13.4 में ठीक किए। Distribution backports पुराने version में भी fix कर सकते हैं, इसलिए दिखाई देने वाला interpreter version अकेले exposure का प्रमाण नहीं है।<sup>[[16]](#references)[[17]](#references)</sup>

Passive review के लिए exact sudo command और script पढ़ें, trace करें कि कौन-सा argument archive चुनता है और जाँचें कि current user archive या उसकी containing directory लिख सकता है या नहीं। Installed vendor patch और extraction destination अलग-अलग सत्यापित करें; `filter="data"` हर untrusted archive को सुरक्षित नहीं बनाता।<sup>[[16]](#references)[[17]](#references)</sup>

### Sudo के जरिए चलाए जाने वाले machine-learning model loaders

Caller-चुनी `.pt`, `.pth` या `.ckpt` file की अनुमति देने वाले sudo rule की समीक्षा करें, यदि privileged script वह file [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` या किसी अन्य pickle-based loader को देती है। प्रभावी RunAs rule, caller चुना model बना या बदल सकता है या नहीं, और shell wrapper से Python helper तक वास्तविक argument flow जाँचें। `.pth` extension असंबंधित Python site configuration files के नाम में भी आता है, इसलिए केवल extension model loading का प्रमाण नहीं है। Archive scan या static pickle scan यह स्थापित नहीं करता कि बाद का load सुरक्षित है; loader का [version-dependent `weights_only` behavior](https://docs.pytorch.org/docs/stable/notes/serialization.html) और कोई allowlisting देखें। [ML pickle और Fickling notes](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling) देखें। Passive enumeration में model कभी load या unpack न करें।

### Stored input का sudo के जरिए expression parsing

Root के रूप में sudo से चलने वाली fixed Python script भी वह text evaluate कर सकती है जिसे कम-privileged user application database में store कर सकता है। TensorFlow में `preprocess_input_exprs_arg_string(value, safe=False)` call `eval` path चुनता है; [TensorFlow की advisory](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) unsafe parser और उसके command-line caller में किए गए fix का विवरण देती है। Application का explicit `safe=False` call अलग से समीक्षा माँगता है, भले वह command-line caller patched हो। प्रभावी sudo rule, सटीक input row को कौन बदल सकता है, filtering या scoring उस row को call तक पहुँचाती है या नहीं तथा installed function का व्यवहार जाँचें। TensorFlow version, sudo grant या hardcoded model file अकेले chain सिद्ध नहीं करती। Passive रूप से script और data flow देखें; enumeration के दौरान privileged helper न चलाएँ या test expressions submit न करें।

### Sudo-अनुमत needrestart configuration

`needrestart -c` caller-चुनी Perl configuration file load करता है और उसकी सामग्री evaluate करता है। यदि `sudo -l` root के रूप में `needrestart` को ऐसे arguments सहित अनुमति देता है जिनमें `-c` शामिल हो सकता है और caller writable location में readable configuration file चुन सकता है, तो इससे root code execution हो सकता है। सटीक sudo run-as और argument rule जाँचें; केवल fixed argument list की अनुमति देने वाला rule इस रास्ते को रोक सकता है। यह needrestart की interpreter-scanning vulnerabilities से अलग है: package update करने या `interpscan` बंद करने से unrestricted root `-c` grant सुरक्षित नहीं हो जाता।<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### दूसरे account के तहत Sudo के जरिए Python imports

Fixed Python entry point भी caller द्वारा संपादित या बदले जा सकने वाले module को import कर सकता है—यहाँ तक कि जब sudo script को **non-root** service user के रूप में चलाता हो। Literal `from utils import status` के लिए package directory permissions के साथ local `utils/__init__.py` और `utils/status.py` भी देखें। Writable file को execution path मानने से पहले script का import path, सटीक अनुमत sudo arguments और संबंधित action उस import तक पहुँचता है या नहीं—सत्यापित करें। Enumeration के दौरान import या script चलाए बिना files और permissions देखें।<sup>[[2]](#references)[[3]](#references)</sup>

`python3 /absolute/script.py` के लिए exact sudo rule में केवल readable script की आवश्यकता है; file executable होना या उसमें shebang होना जरूरी नहीं। **Missing** local modules भी जाँचें: यदि script ऐसा module import करती है जिसका filename caller-writable script directory में बनाया जा सकता है, तो Python उस file को RunAs identity के तहत load कर सकता है। प्रभावी sudo rule, interpreter का वास्तविक [module search path](https://docs.python.org/3/library/sys_path_init.html), module built-in या frozen है या नहीं और import तक पहुँचा जाता है या नहीं—सत्यापित करें। Script के लिए direct sudo rule में execute-bit और shebang की आवश्यकताएँ अलग होती हैं। ऐसा अलग wrapper भी argument-flow review माँगता है जो `sudo -u account` के बाद caller द्वारा दिए tokens जोड़ता है: उन tokens में एक और `-u` तभी मायने रखता है जब invoked sudo policy resulting identity की अनुमति देती हो। Static strings अकेले दोनों में से कोई रास्ता सिद्ध नहीं करतीं।

### Caller-नियंत्रित configuration के साथ Sudo के जरिए Apache चलाना

यदि sudo rule privileged `apachectl`, `apache2ctl` या `httpd` invocation को caller-नियंत्रित `-f` configuration file के साथ अनुमति देता है, तो उस file और उसके parent directory permissions की समीक्षा करें। Apache का [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) directive module name के बाद **module filename** लेता है; [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) भी file load करता है। [`Include` और `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) configuration बढ़ा सकते हैं या errors के जरिए file contents उजागर कर सकते हैं। Custom wrapper इन paths को validate कर सकता है, privileges drop कर सकता है या arguments सीमित कर सकता है; इसलिए writable config code execution का प्रमाण नहीं, केवल review candidate है। निष्कर्ष निकालने से पहले path canonicalization, symlinks और directive parsing जाँचें।

### Caller-नियंत्रित configuration के साथ Sudo के जरिए nginx चलाना

Unrestricted root-capable `nginx` rule [`-c` को दूसरी configuration चुनने दे सकता है](https://nginx.org/en/docs/switches.html)। सटीक sudo arguments और exclusions, caller configuration दे सकता है या नहीं तथा resulting master या workers की protected paths तक पहुँच बनी रहती है या नहीं—समीक्षा करें। चुना हुआ `root` और `autoindex` नया listener बनाकर files उजागर कर सकता है; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) privileged file-write path दे सकता है, लेकिन DAV module default रूप से build नहीं होता, इसलिए उसकी मौजूदगी, listener reachability, file permissions और temporary-file behavior जाँचना आवश्यक है। [`error_log` directive](https://nginx.org/en/docs/ngx_core_module.html#error_log) चुनी file को भी target कर सकता है; `/etc/ld.so.preload` जैसी संवेदनशील configuration file में logs लिखना escalation path तभी बनता है जब प्रभावी privileged writer और नियंत्रित log record मौजूद हों। `sudo -l` में executable highlight जाँच का संकेत है, इन रास्तों के काम करने का प्रमाण नहीं। Passive enumeration में nginx शुरू या reconfigure न करें।

### Privileged Bash prompts में pattern comparison

जब sudo-अनुमत Bash script caller से value पढ़कर `[[ "$expected" == $entered ]]` से जाँचती है, तो Bash unquoted right-hand operand को pattern की तरह समझता है। इसलिए wildcard असली expected value जाने बिना comparison पूरा कर सकता है। Operand को quote करने (`[[ "$expected" == "$entered" ]]`) से literal string comparison होता है। सटीक sudo rule, prompt तक पहुँचा जा सकता है या नहीं और comparison के बाद script क्या करती है—इनकी समीक्षा करें; syntax अकेले exploitable path स्थापित नहीं करता। Enumeration के दौरान expected value न दिखाएँ। [Bash conditional constructs reference](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html) देखें।

### Sudo के जरिए चलाए जाने वाले helpers जो file download करके execute करते हैं

यदि कोई unrestricted root-capable sudo grant वाला custom helper caller-चुना URL स्वीकार करता है, response disk पर लिखता है और बाद में उस file को interpreter या shell से चलाता है, तो dataflow की समीक्षा करें। [Sudoers ऐसे command entry में arbitrary arguments की अनुमति देता है जिसमें कोई argument सूचीबद्ध न हो](https://man7.org/linux/man-pages/man5/sudoers.5.html); fixed executable path उसके arguments से चुनी जा सकने वाली चीज़ों को सीमित नहीं करता। Installed helper में वास्तविक URL validation, output path, success branch और बाद के execution की पुष्टि करें। Matching libcurl import या printable string अकेले इस chain को सिद्ध नहीं करती।

यदि helper **caller-नियंत्रित working directory में relative path** उपयोग करता है, तो fixed output basename भी write और execution के बीच बदली जा सकती है। Root-owned file का नाम बदलना या उसे replace करना केवल file mode नहीं, directory पर write/search access और sticky-bit restrictions से नियंत्रित होता है; [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) देखें। जाँचें कि helper बाद में path दोबारा खोलता है या पहले से खुला descriptor उपयोग करता है, और लिखने से पहले trusted directory में जाता है या नहीं। Passive रूप से sudo policy, helper और directory metadata देखें; enumeration के दौरान privileged download या race न चलाएँ।

Root-sudo download helper Bash command string जैसे `curl <caller input> -o <fixed output>` बनाकर **argument** injection भी उजागर कर सकता है। Whitespace अस्वीकार करने वाला filter भी [Bash brace expansion](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html) को नहीं रोकता: unquoted comma-separated elements अलग curl arguments बन सकते हैं। यदि input fixed `-o` से पहले curl तक पहुँचता है, तो caller द्वारा दिया output option helper की identity के तहत पहले URL का destination चुन सकता है; [curl output options को URLs के साथ क्रम से जोड़ता है](https://curl.se/docs/manpage.html#-o)। सटीक shell, quoting, input validation, प्रभावी sudo rule, curl argument order और समर्थित URL schemes तथा caller fetched bytes नियंत्रित कर सकता है या result पढ़ सकता है या नहीं—सत्यापित करें। PyInstaller-packaged executable में Python application logic हो सकता है, लेकिन उसका packaging marker या `curl` string अकेले यह data flow सिद्ध नहीं करता। अधिकृत होने पर सीमित offline copy की समीक्षा करें; routine enumeration में helper न चलाएँ या attacker-चुना data fetch न करें।

Root-sudo shell script जो [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) चलाती है, केवल unused name चुनती है; वह file **बनाती नहीं**। यदि script बाद में उस नाम को ऐसी directory में बनाती है जिसे दूसरा user प्रभावित कर सकता है, फिर उसे दोबारा खोलकर उसकी सामग्री root के `authorized_keys` जैसे protected destination में जोड़ती है, तो संभावित temporary-file race की समीक्षा करें। सटीक sudo rule, directory और file ownership, creation तथा reopen sequence, kernel protections और privileged write वास्तव में attacker-controlled bytes उपयोग करता है या नहीं—सत्यापित करें। `mktemp -u` string या writable `/tmp` अकेले race सिद्ध नहीं करते। Enumeration के दौरान script और path metadata देखें; इसे चलाएँ नहीं या temporary file पर race न करें।

## रक्षात्मक टिप्पणियाँ

- sudo के जरिए interpreters या interactive editors देने से बचें।<sup>[[1]](#references)</sup>
- `tee` जैसे generic file writers को unrestricted operands के साथ अनुमति न दें। ऐसा root-owned wrapper उपयोग करें जो fixed destination चुनता हो और caller-नियंत्रित paths अस्वीकार करता हो।<sup>[[2]](#references)</sup>
- ऐसे fixed, root-owned wrappers को प्राथमिकता दें जो एक संकीर्ण administrative action करते हों।<sup>[[1]](#references)[[2]](#references)</sup>
- यदि interpreter देना अपरिहार्य हो, तो exact script path सीमित करें और user-controlled arguments, writable imports, `PYTHONPATH` तथा unsafe environment preservation रोकें।<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- यदि file editing आवश्यक हो, तो exact file path सीमित करें और patched sudo versions तथा strict environment handling के साथ `sudoedit` पर विचार करें।<sup>[[1]](#references)[[2]](#references)</sup>
- `SETENV`, `env_keep`, writable working directories, writable module/import paths, `NOEXEC`, `use_pty` और logging की समीक्षा करें, लेकिन इन्हें पूर्ण sandbox न मानें।<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
