## Interpreti consentiti da Sudo

Se `sudo -l` consente a un utente di eseguire un interprete come root, consideralo come esecuzione diretta di codice. Gli interpreti sono progettati per eseguire codice arbitrario, quindi una regola che consente `python3`, `perl`, `ruby`, `lua`, `node` o binari simili equivale di solito all'esecuzione di comandi come root, a meno che gli argomenti non siano soggetti a vincoli rigorosi e convalidati.<sup>[[1]](#references)[[2]](#references)[[3]](#references)[[4]](#references)[[5]](#references)[[7]](#references)[[9]](#references)[[11]](#references)</sup>

Flusso di revisione comune: prima elenca i privilegi dell'utente, poi esegui un'istruzione Python con l'opzione `-c` dell'interprete.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/python3 -c 'import os; os.system("id")'
sudo /usr/bin/python3 -c 'import os; os.system("/bin/sh")'
```

Di seguito sono mostrati altri esempi di interpreti; quelli elencati documentano l'esecuzione di codice inline o le API per i processi figli.<sup>[[5]](#references)[[6]](#references)[[7]](#references)[[8]](#references)[[9]](#references)[[10]](#references)[[11]](#references)</sup>

```bash
sudo /usr/bin/perl -e 'exec "/bin/sh";'
sudo /usr/bin/ruby -e 'exec "/bin/sh"'
sudo /usr/bin/node -e 'require("child_process").spawn("/bin/sh", {stdio: [0,1,2]})'
```

Il percorso esatto è importante. Se la regola sudo consente `/usr/bin/python3`, usa quel percorso esatto durante la verifica.<sup>[[2]](#references)</sup>

Un glob per l’eseguibile sudo come `/usr/bin/python*` potrebbe consentire anche Python 2 per uno script scritto per Python 3. Se lo script raggiunge `input()` con testo controllato dal chiamante, [Python 2 valuta quel testo come un’espressione](https://docs.python.org/2/library/functions.html#input); un’invocazione esplicita dell’interprete prevale sullo shebang dello script. Verifica i binari corrispondenti installati, l’identità RunAs effettiva e la policy sugli argomenti, i dinieghi e l’input raggiungibile prima di considerarlo un percorso di esecuzione.

Un percorso script fisso in una regola sudo con privilegi root non limita ciò che lo script esegue. Per un wrapper Bash leggibile, verifica se il primo comando eseguibile usa un parametro posizionale non racchiuso tra virgolette, come `$1`, come **parola di comando**, mentre sudo consente al chiamante di scegliere gli argomenti. Conferma l’identità RunAs effettiva, la policy per password e argomenti, i dinieghi successivi e il ramo effettivamente seguito dallo script; `NOEXEC`, un elenco fisso di argomenti sicuri o un wrapper che convalida il comando possono cambiare il risultato. Durante l’enumerazione, ispeziona staticamente lo script breve invece di invocarlo con un comando di prova.

Anche una regola sudo senza restrizioni per `dotnet` con privilegi root merita di essere esaminata dal punto di vista dell’interprete. Con un .NET SDK installato, [`dotnet fsi` esegue codice F# in modo interattivo o da uno script](https://learn.microsoft.com/en-us/dotnet/fsharp/tools/fsharp-interactive/) e [`dotnet run` esegue un progetto dal codice sorgente](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-run). Prima conferma l’identità RunAs effettiva e la policy esatta sugli argomenti: una regola limitata a uno specifico sottocomando sicuro o a un’applicazione attendibile concede autorizzazioni diverse, e un’installazione con solo runtime potrebbe non includere i comandi SDK. Il solo nome dell’eseguibile è un indizio da approfondire, non una prova di esecuzione di codice.

```bash
sudo /usr/bin/python3 -c 'import os; os.setuid(0); os.setgid(0); os.system("/bin/sh")'
```

## `tee` consentito da sudo: scrittura arbitraria di file con privilegi elevati

GNU `tee` copia lo standard input in ogni percorso fornito come operando file. Pertanto, una regola sudo che consente l'esecuzione di `/usr/bin/tee` come root con argomenti controllati dall'utente concede la possibilità di creare o sovrascrivere file arbitrari come root. Aggiungere `-a` modifica questa possibilità in un'operazione di append. Un tag `PASSWD:` riguarda l'autenticazione sudo; da solo, non limita la destinazione né i byte letti dallo standard input.<sup>[[2]](#references)[[27]](#references)[[28]](#references)</sup>

Per prima cosa, esamina la regola esatta. Su un sistema di test autorizzato, convalida questa possibilità solo usando una destinazione temporanea sicura da creare. Il redirect finale `>/dev/null` sopprime solo la copia di `tee` sullo standard output.<sup>[[28]](#references)</sup>

```bash
sudo -l
printf '%s\n' 'controlled-write' | sudo /usr/bin/tee /root/tee-proof >/dev/null
printf '%s\n' 'appended-line' | sudo /usr/bin/tee -a /root/tee-proof >/dev/null
```

Mettere `sudo` prima del producer non eleva una successiva redirezione della shell, perché è la shell del chiamante ad aprire la destinazione. Il processo privilegiato deve essere quello che scrive, come nella pipeline sopra.<sup>[[1]](#references)[[15]](#references)</sup>

Dopo aver verificato la scrittura, scegli un sink appropriato per l'esecuzione di codice come root da [Arbitrary File Write to Root](../interesting-files-permissions/write-to-root.md). Una catena osservata ha usato `tee` eseguito come root per creare un file temporaneo in `/etc/cron.d/`, avviato una backdoor tramite uno script controllato dall'utente e cancellato il file cron dopo l'esecuzione. Rimuovere il file cron ha impedito che diventasse una voce di persistenza a lungo termine, anche se i log di sistema hanno comunque conservato le prove dell'attività.<sup>[[27]](#references)</sup>

## Editor consentiti da sudo

Se `sudo -l` consente a un utente di eseguire come root un editor interattivo, consideralo una superficie di command execution, non un'innocua autorizzazione a modificare file. Gli editor possono spesso eseguire comandi shell, leggere file arbitrari, scrivere file arbitrari o invocare helper esterni dall'interno dell'editor.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

Flusso di revisione comune: elenca i privilegi dell'utente, quindi avvia con sudo ogni editor o pager consentito.<sup>[[1]](#references)[[12]](#references)[[13]](#references)[[14]](#references)</sup>

```bash
sudo -l
sudo /usr/bin/nano /etc/hosts
sudo /usr/bin/vim /etc/hosts
sudo /usr/bin/less /etc/hosts
```

### Esecuzione di comandi con Nano

Quando `nano` è consentito tramite sudo, l'esecuzione di comandi potrebbe essere accessibile dall'interfaccia dell'editor.<sup>[[12]](#references)</sup>

```text
Ctrl+R
Ctrl+X
```

Quindi fornisci un comando come `id` o `/bin/sh` al prompt dei comandi di nano.<sup>[[12]](#references)</sup>

```bash
id
/bin/sh
```

Se una shell interattiva non dispone di flussi del terminale utilizzabili, questa forma di redirezione indirizza lo standard output e lo standard error al descrittore 0.<sup>[[15]](#references)</sup>

```bash
reset; /bin/sh 1>&0 2>&0
```

La sequenza di tasti esatta può variare in base alla versione di nano e alle opzioni di compilazione, ma il problema di sicurezza è lo stesso: l'editor viene eseguito come root e può invocare comandi esterni.<sup>[[1]](#references)[[12]](#references)</sup>

### Altre escape comuni degli editor

Gli editor in stile Vim consentono comunemente di eseguire comandi tramite `:!`.<sup>[[13]](#references)</sup>

```text
:!/bin/sh
```

I pager come `less` possono anche consentire l'esecuzione di comandi shell.<sup>[[14]](#references)</sup>

Una regola sudo che consente di eseguire `apport-cli` come root merita la stessa verifica del pager. Alcune versioni di Apport vulnerabili potevano aprire un crash report in `less` con una dimensione del terminale modificabile dall'attaccante; il pager poteva quindi fornire una root shell se erano soddisfatte le condizioni specifiche per sudo e per il pager. Prima di considerare vulnerabile una versione solo in base al numero, verifica la regola sudo effettiva, la configurazione del pager e la correzione del pacchetto della distribuzione. Durante l'enumerazione passiva, leggi i metadati del pacchetto e delle policy senza generare un crash né aprire il report con privilegi elevati. [Il record CVE di Ubuntu](https://ubuntu.com/security/CVE-2023-1326) elenca le versioni corrette dei pacchetti specifiche per ogni release, comprese quelle con correzioni backportate.

```text
!/bin/sh
```

## Altri rischi nelle regole di sudo e doas

Inizia con `sudo -l`, `sudo -V` e qualsiasi policy `doas` applicabile. Valuta insieme i comandi consentiti, l’utente di esecuzione, gli argomenti, l’ambiente e i valori predefiniti. Il permesso di eseguire comandi come un account di servizio non-root può comunque esporre i file di quell’account o offrire un percorso verso root.

Uno script Python autorizzato da sudo con percorso fisso può comunque eseguire un comando shell con l’identità RunAs se input interattivo controllato dal chiamante viene concatenato in [`os.system()`](https://docs.python.org/3/library/os.html#os.system). Una denylist di punteggiatura della shell non basta a dimostrare che il codice sia sicuro: [la shell riconosce anche la sostituzione di comando `$(...)`](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html). Verifica che gli argomenti consentiti raggiungano il ramo che acquisisce l’input, che l’input arrivi al comando shell senza una convalida sicura e che la policy sudo effettiva consenta l’utente RunAs previsto. Il percorso dello script o una chiamata a `os.system()` sono soltanto indizi da approfondire: esamina il codice sorgente senza eseguire lo script privilegiato.

Una concessione sudo effettiva come root per `chattr` può rimuovere l’attributo immutabile (`i`) di un file, ma questo da solo non concede la possibilità di scriverci né una nuova identità. [Il manuale di `chattr`](https://man7.org/linux/man-pages/man1/chattr.1.html) specifica che l’attributo impedisce le modifiche e che solo root o un processo con `CAP_LINUX_IMMUTABLE` può cambiarlo. Verifica gli argomenti esatti consentiti da sudo e il supporto del filesystem, poi controlla separatamente che il chiamante possa scrivere il file dopo la rimozione dell’attributo e che un componente con identità superiore lo utilizzi. Per esempio, sostituire una shell di login richiede anche credenziali accettate dall’account di destinazione e un accesso effettivo tramite quella shell. Durante la ricognizione, esamina la policy, gli attributi dei file e i permessi senza modificarli.

Se sudo richiede sia una password sia un codice monouso, considera questi prerequisiti separatamente dalla concessione del comando. Un file `.google_authenticator` leggibile contiene materiale sensibile per la generazione dei seed; un hash di una vecchia password di applicazione o database è soltanto una possibile password attuale dell’account. Nessuno dei due dimostra che l’altro fattore sia accettato dalla configurazione PAM effettiva. Dopo aver ottenuto l’autorizzazione, verifica RunAs e argomenti esatti: una concessione root senza restrizioni per `gem` di RubyGems può esporre il suo comando editor ([GTFOBins](https://gtfobins.github.io/gtfobins/gem/)), ma una concessione limitata o un’autenticazione non riuscita non lo consentono. La ricognizione passiva dovrebbe riportare percorsi e policy senza mostrare il seed, recuperare una password, generare un codice o invocare il comando privilegiato.

Una concessione sudo senza restrizioni, eseguibile come root, per `knife` di Chef merita un’analisi a livello di interprete: [Chef documenta che `knife exec -E` valuta localmente una stringa Ruby](https://docs.chef.io/workstation/26/tools/knife/knife_exec/). Verifica che la regola sudo effettiva consenta il sottocomando `exec` e l’argomento `-E` fornito dal chiamante, l’identità RunAs prevista e qualsiasi negazione di comando o argomento fisso applicabile. Il binario installato o una regola limitata ad altri sottocomandi sono soltanto indizi. La ricognizione passiva dovrebbe riportare la regola senza invocare `knife`.

Una concessione sudo esatta per `msfconsole`, eseguibile come root, è altrettanto sensibile: [GTFOBins documenta la sua console `irb`](https://gtfobins.org/gtfobins/msfconsole/), che può ereditare l’identità sudo. Verifica l’utente RunAs effettivo, l’elenco di argomenti consentiti, le negazioni di comando, `NOEXEC` o altre restrizioni, il comportamento della console installata e la possibilità per il chiamante di fornire input interattivo. Un percorso evidenziato è soltanto un indizio da approfondire; la ricognizione passiva non dovrebbe avviare la console.

Su FreeBSD, anche una regola sudo limitata a `pkg update` come root e `pkg install *` merita una verifica dell’affidabilità dei repository. Controlla se il chiamante può scrivere `/etc/hosts` e se la configurazione *effettiva* dei repository abilitati usa un hostname HTTP con `signature_type: none`. [Il manuale di `pkg.conf` di FreeBSD](https://man.freebsd.org/cgi/man.cgi?query=pkg.conf&sektion=5) specifica che `none` disabilita i controlli delle firme; la sola presenza di `pkg+http` non basta a dimostrarlo. Un pacchetto può contenere script di installazione ([FreeBSD Porter's Handbook](https://docs.freebsd.org/en/books/porters-handbook/pkg-files/)), quindi un chiamante che controlla davvero l’endpoint del repository e può selezionare un pacchetto potrebbe superare il confine di root. Verifica gli override dei repository, la risoluzione SRV/mirror, gli argomenti sudo effettivi, la selezione del pacchetto e l’esecuzione degli script prima di trarre conclusioni. Esamina la policy e i piccoli file di configurazione locali senza reindirizzare nomi o eseguire `pkg` durante la ricognizione.

Una regola sudo eseguibile come root per `apt-get update` e `apt-get upgrade` richiede anche una verifica dell’affidabilità dei repository quando sudo conserva un `http_proxy` controllato dal chiamante. Controlla se la configurazione APT effettiva usa davvero quella variabile proxy e quali richieste ai repository abilitati può influenzare; un proxy da solo non può sostituire pacchetti provenienti da un archivio autenticato con una chiave di firma fidata. [Il manuale del trasporto HTTP di APT](https://manpages.debian.org/experimental/apt/apt-transport-http.1.en.html) documenta la precedenza dei proxy e [apt-secure](https://manpages.debian.org/experimental/apt/apt-secure.8.en.html) descrive i controlli delle firme, gli override per repository non sicuri e la conferma richiesta per pacchetti non autenticati. Verifica RunAs e argomenti sudo esatti, la policy di autenticazione dei repository, eventuali conferme interattive richieste e se l’upgrade selezionato esegue script di pacchetto come root. Esamina policy e configurazione locale passivamente; non reindirizzare il traffico dei pacchetti né eseguire un upgrade durante la ricognizione.

Una regola sudo eseguibile come root per `snap install` può creare un confine tra pacchetto e codice se gli argomenti consentono al chiamante di selezionare uno snap locale e una modalità di installazione permissiva. [La documentazione di Snap](https://snapcraft.io/docs/explanation/snap-development/install-modes/) specifica che `--dangerous` salta i controlli delle attestazioni per gli snap locali e che `--devmode` allenta il confinamento; [un hook di installazione può essere eseguito durante la prima installazione](https://snapcraft.io/docs/reference/development/supported-snap-hooks/). Prima di affermare che sia possibile accedere a file protetti dell’host, verifica la policy sudo esatta per argomenti e RunAs, chi controlla il file snap, se snapd installato accetta queste modalità e l’identità effettiva e il confinamento dell’hook. La presenza del binario `snap` o una regola che sembra usare un wildcard non dimostra da sola questa catena. La ricognizione passiva non dovrebbe installare un pacchetto né eseguire il relativo hook.

Per una concessione sudo esatta a un binario personalizzato, che legge credenziali, eseguibile come account **non-root**, esamina prima il binario concesso e i suoi permessi senza eseguirlo. Una verifica della password incorporata può essere visibile solo come caratteri larghi; [GNU `strings` documenta l’estrazione little-endian a 16 bit](https://sourceware.org/binutils/docs/binutils/strings.html). Una stringa visibile non dimostra che sia la password accettata né che il ramo di successo esponga una credenziale attuale. Verifica separatamente il comportamento del binario, l’accesso dell’account di destinazione ai dati protetti, la validità delle credenziali e qualsiasi successiva transizione di account o gruppo. Se quell’account appartiene a `docker`, verifica l’accesso al socket e se il daemon è rootful o rootless prima di dedurre che sia possibile ottenere accesso root all’host; [Docker documenta le implicazioni a livello root del gruppo](https://docs.docker.com/engine/install/linux-postinstall/). La ricognizione ordinaria dovrebbe riportare la regola sudo e l’appartenenza ai gruppi senza eseguire il binario o scaricarne le stringhe.

Una regola sudo con wildcard per gli script di manutenzione di un’applicazione richiede un’analisi che vada oltre il percorso dello script. Verifica se lo script consentito accetta argomenti senza restrizioni o legge impostazioni scrivibili da un account dell’applicazione con privilegi inferiori; poi segui quei valori fino ai comandi shell o all’ambiente di un subprocesso. Per esempio, [`zmupdate.pl` di ZoneMinder assembla un comando `mysqldump` e lo esegue tramite `qx`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmupdate.pl.in), mentre [`zmdc.pl` copia l’impostazione `ZM_LD_PRELOAD` in `LD_PRELOAD`](https://github.com/ZoneMinder/ZoneMinder/blob/master/scripts/zmdc.pl.in) prima di avviare i daemon. Una regola sudo che consente di eseguire uno di questi script come root può superare un confine di fiducia se l’input corrispondente è controllabile e raggiunge quel codice nella versione installata. Esamina la regola sudo effettiva, i permessi sulla configurazione dell’applicazione e il sorgente dello script: il wildcard o l’impostazione sono soltanto indizi, non prove di esecuzione.

- `SETENV`, `env_keep`, `secure_path` e `LD_PRELOAD` possono trasformare un comando altrimenti limitato in un hijack di import, libreria o PATH. Vedi la [guida alle variabili d’ambiente](../linux-basics/linux-environment-variables.md) e [l’abuso di SUID/linker](../interesting-files-permissions/suid-shared-library-and-linker-abuse.md).

Una concessione `SETENV` esatta, eseguibile come root, per un wrapper shell merita anche un’analisi a un solo passaggio se il wrapper avvia uno script Python fisso con un import letterale. `secure_path` limita la ricerca dei comandi da parte della shell, non la ricerca dei moduli Python tramite [`PYTHONPATH`](https://docs.python.org/3/using/cmdline.html#envvar-PYTHONPATH); [`-E` e `-I`](https://docs.python.org/3/using/cmdline.html#cmdoption-E) fanno sì che Python ignori quella variabile d’ambiente. Prima di considerare il caso esecuzione di codice, verifica i tag e le negazioni sudo effettivi, il ramo del wrapper, le opzioni dell’interprete, la risoluzione dell’import e la presenza di una directory di ricerca scrivibile dal chiamante. Esamina gli script brevi staticamente; non invocare il wrapper privilegiato.

Una concessione sudo esatta per `neofetch ""`, eseguibile come root, può comunque caricare una configurazione shell quando i valori predefiniti sudo applicabili conservano un `XDG_CONFIG_HOME` controllato dal chiamante. [Il loader di configurazione di Neofetch](https://github.com/dylanaraps/neofetch/blob/master/neofetch) carica il file `neofetch/config.conf` o `neofetch/config` dalla directory indicata; l’elenco di argomenti vuoto non impedisce questa ricerca. Verifica il loader installato, la policy RunAs e sugli argomenti effettiva, le eventuali negazioni di comando, se sudo conserva davvero la variabile selezionata per questo comando e se il chiamante controlla un percorso di configurazione leggibile. Una variabile conservata o la sola presenza di Neofetch installato sono indizi da approfondire. Esamina policy e metadati dei file senza invocare il comando privilegiato o mostrare il contenuto della configurazione; vedi la [gestione dell’ambiente in sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).

Una regola sudo senza restrizioni per `facter`, eseguibile come root, merita un’analisi separata dei custom fact. [Puppet documenta](https://help.puppet.com/core/current/Content/PuppetCore/loading_custom_facts.htm) che `--custom-dir` carica file di fact Ruby da una directory selezionata. Verifica se la regola sudo esatta consente quell’opzione, se Facter installato la accetta e se il chiamante controlla la directory. Una concessione con argomenti fissi, un’esplicita negazione del comando o i custom fact disabilitati possono cambiare l’esito. La ricognizione passiva dovrebbe segnalare la regola candidata senza invocare Facter né leggere il contenuto dei fact.

Per una concessione sudo esatta a uno script eseguibile come root con `SETENV`, controlla comandi senza percorso esplicito come `find` e il `PATH` effettivo dopo l’applicazione della policy sudo e l’inizializzazione dello script. Un file Bash caricato con `source` può anche eseguire `enable -n [`: [Bash cerca quindi in `PATH`](https://www.gnu.org/software/bash/manual/html_node/Bash-Builtins.html) un `[` esterno quando lo script usa in seguito quel comando. Verifica le regole applicabili di [sudoers per ambiente e `secure_path`](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), eventuali voci `NOSETENV`/`NOEXEC` o di negazione, il flusso dello script e dei file caricati e la presenza di una directory di ricerca eseguibile controllata dal chiamante. Uno script leggibile che contiene un comando senza percorso esplicito è un indizio da approfondire, non una prova di esecuzione privilegiata; esaminalo senza invocare la regola sudo.
- Uno script privilegiato che recupera un URL fisso con `curl` può comunque accettare una risposta scelta dal chiamante se una regola sudo applicabile conserva `http_proxy` e la richiesta passa tramite quel proxy. Se lo script passa poi la risposta a un parser XML che risolve entità esterne, una risposta malevola può divulgare file leggibili dal processo privilegiato. Verifica la policy sudo esatta per l’ambiente, le esclusioni `no_proxy`, l’URL richiesto, la configurazione del parser e la destinazione dell’output; una variabile proxy o un parser XML da soli non costituiscono una vulnerabilità. La [documentazione di curl sull’ambiente dei proxy](https://everything.curl.dev/usingcurl/proxies/env.html) descrive il comportamento delle variabili. Durante la ricognizione passiva, non effettuare richieste di rete né analizzare XML malevolo.
- Uno script sudo eseguibile come root che crea un file PostScript usando dati influenzati dal chiamante e poi esegue `ps2pdf -dNOSAFER` merita un’analisi separata del flusso degli input. Ghostscript documenta che questo flag disabilita SAFER fino a `.setsafe`, consentendo operazioni sui file PostScript entro i permessi del processo sul sistema operativo. Una query SQL assemblata a partire da un argomento del chiamante può fornire righe controllate dall’aggressore al modello PostScript, ma una stringa di query o una chiamata a `ps2pdf` da sole non dimostrano che i dati raggiungano sintassi PostScript eseguibile. Verifica la regola sudo effettiva, il percorso esatto dall’input al modello, eventuali escaping, il comportamento di Ghostscript installato e se SAFER viene riattivato prima dell’interpretazione del documento. Durante la ricognizione passiva, non invocare la conversione privilegiata. Vedi la [documentazione di Ghostscript su `-dNOSAFER`](https://ghostscript.readthedocs.io/en/master/Use.html).
- Per una regola sudo che esegue uno script shell, confronta le variabili conservate con il contenuto dello script. Un costrutto come `if $CHECK_CONTENT; then` esegue il valore espanso come comando, quindi conservare `CHECK_CONTENT` può consentire l’esecuzione di comandi anche quando percorso e argomenti dello script sono fissi. Occorre verificare se il ramo è raggiungibile e se l’ambiente viene effettivamente conservato per quella regola.<sup>[[2]](#references)[[22]](#references)</sup>
- Uno script Python autorizzato da sudo può importare codice da una directory scrivibile o da un file `.pyc` in cache. La [guida all’escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md) descrive il caso della cache.
- Uno script Python fisso autorizzato da sudo per essere eseguito come root può comunque esporre un debugger interattivo. Chiamate come `pdb.set_trace()` o `pdb.post_mortem()` consentono di eseguire istruzioni Python nel contesto del processo sottoposto a debug quando il chiamante può raggiungere il breakpoint o il gestore di eccezioni **e controllare lo stream di input del debugger**. Verifica la regola RunAs sudo esatta, l’autenticazione e le condizioni del ramo, la raggiungibilità dell’eccezione, la proprietà del terminale/input e se il debugger viene eseguito nello stesso processo privilegiato. Una richiesta socket che genera un’eccezione non concede da sola l’accesso a un debugger collegato a un altro terminale. [Python documenta la valutazione delle istruzioni del debugger e la modalità post-mortem](https://docs.python.org/3/library/pdb.html); durante la ricognizione, esamina lo script staticamente invece di attivare il gestore privilegiato.
- Uno script Python fisso autorizzato da sudo può anche leggere un campo di profilo da un database o socket Unix e aggiungerlo a una stringa che diventa in seguito la **stringa di formato** per `str.format()`. [I campi di sostituzione possono seguire attributi e chiavi di mapping](https://docs.python.org/3/library/string.html#format-string-syntax), quindi un campo controllato dall’aggressore può ispezionare gli oggetti passati a `format()` ed esporre i dati raggiungibili tramite essi, se il risultato viene mostrato o memorizzato in un luogo leggibile dal chiamante. Verifica l’identità RunAs sudo effettiva, il permesso di scrittura sul record specifico, il flusso dei dati nella stringa di formato, gli oggetti forniti e la visibilità dell’output. Questo non comporta automaticamente l’esecuzione di codice; una stringa di formato letterale e fidata con *valori* controllati dall’aggressore è un caso diverso. Un segreto divulgato consente il passaggio a un account del sistema operativo solo se quell’account lo accetta. Esamina lo script e i permessi del socket senza invocare l’operazione privilegiata.
- Un wrapper Python eseguibile come root può passare un URL selezionato dal chiamante a `Repo.clone_from` di GitPython. Se il wrapper abilita anche `protocol.ext.allow=always` di Git, un repository remoto `ext::` può invocare un helper esterno. Verifica gli argomenti sudo esatti, la provenienza dell’URL, la versione del pacchetto GitPython e le eventuali patch del fornitore, nonché se il wrapper abilita esplicitamente protocolli non sicuri. GitPython ha aggiunto un [controllo predefinito dei protocolli non sicuri](https://github.com/gitpython-developers/GitPython/commit/2625ed9) nella versione 3.1.30; la versione dell’eseguibile `git` è un dato separato. L’analisi passiva dovrebbe leggere solo la regola e il codice sorgente circoscritto, senza invocare il clone.
- Una concessione sudo tra utenti diversi a una CLI per clonare repository può esporre un percorso separato di command injection tramite stringhe shell. Verifica se l’argomento del repository scelto dal chiamante raggiunge [`child_process.exec`](https://nodejs.org/api/child_process.html#child_processexeccommand-options-callback) di Node.js o un altro generatore di comandi shell senza una separazione sicura degli argomenti; `exec` di Node passa la stringa di comando a una shell. Verifica l’utente RunAs esatto, i sottocomandi e gli argomenti consentiti, il codice del wrapper installato e la convalida dell’input. Il nome dello strumento per repository o una regola sudo senza restrizioni non dimostrano da soli la presenza di command injection. Durante la ricognizione, esamina il wrapper senza invocare un clone privilegiato.
- Un wrapper personalizzato di proprietà di root può sembrare sicuro perché i suoi binari e script non sono scrivibili, ma la decisione di eseguire un’azione privilegiata potrebbe dipendere da un flag, un valore API locale o uno stato del servizio modificabile da un utente non privilegiato. Risali ogni condizione fino al relativo input e ai controlli di autorizzazione. Durante la ricognizione, esamina configurazione e permessi senza modificare lo stato operativo; una chiamata a `systemd-run` nel wrapper è rilevante solo se la condizione può essere influenzata.
- Un client di backup consentito tramite sudo come root può accettare un file di configurazione scelto dal chiamante, per esempio con `npbackup-cli -c`. Verifica l’utente RunAs esatto e gli argomenti consentiti, poi controlla se il chiamante controlla il percorso di configurazione, i percorsi sorgente del backup e le opzioni di repository o lettura/ripristino. Un segreto di repository cifrato in una configurazione leggibile potrebbe comunque essere utilizzabile dal client, ma la sola regola non dimostra l’accesso al repository o la divulgazione di file root. Verifica l’autorizzazione senza eseguire un backup né scaricarne il contenuto.
- [Restic](https://github.com/restic/restic/blob/master/doc/030_preparing_a_new_repo.rst) supporta `--password-command`, che chiama un programma per ottenere la password del repository. Se una regola sudo consente a un utente con privilegi inferiori di eseguire restic come root con un comando password scelto dal chiamante e un sottocomando che richiede la password, l’helper può essere eseguito come root. Esamina gli argomenti sudo esatti e le esclusioni; non invocare l’helper o un comando di backup soltanto per verificare la condizione.
- Una concessione privilegiata per `restic backup` può anche superare un confine di lettura dei file se gli argomenti sudo consentono al chiamante di scegliere sia la sorgente sia un repository che in seguito può leggere e decrittare. [I wildcard degli argomenti di sudoers possono corrispondere a spazi e barre](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf), quindi esamina i wildcard finali invece di presumere che un prefisso fisso del repository limiti la sorgente. [Restic può eseguire backup su repository locali e remoti](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html), ma un repository locale può contenere oggetti appena scritti e leggibili solo da root; verifica la policy sudo effettiva, l’accesso al backend, la password del repository e i permessi degli oggetti risultanti prima di considerarlo una divulgazione. Una chiave SSH sottoposta a backup consente l’accesso solo se l’account di destinazione la accetta. Durante un’analisi passiva, non eseguire un backup per verificare il caso.
- Un comando personalizzato senza restrizioni per manutenzione o backup può accettare un percorso di output o offrire un proprio scheduler di job. Per un percorso di scrittura dei file, verifica la regola sudo esatta e l’utente RunAs, poi controlla se il chiamante controlla sia i dati sia la destinazione. Per un percorso basato su comandi pianificati, verifica l’identità di esecuzione dello scheduler, l’input del comando e ogni ulteriore requisito di password o autorizzazione. Il nome del comando o `NOPASSWD` da soli non dimostrano nessuno dei due percorsi. Vedi [scrittura su file di proprietà di root](../interesting-files-permissions/write-to-root.md) e [cron e timer systemd](../processes-crontab-systemd-dbus/cron-and-systemd-timers.md).
- Un comando sudo fisso può comunque caricare un file di configurazione prevedibile da una directory condivisa e scrivibile. Verifica se il chiamante può sostituire quel file e se i campi di origine e destinazione controllano un fetch o una copia privilegiata. Un URL di file locale può esporre dati leggibili solo dall’account RunAs di sudo; una sorgente controllata dal chiamante associata a una destinazione protetta può creare un percorso di scrittura. Verifica la gestione degli URL del programma installato, i controlli sul percorso di destinazione, la regola sudo effettiva e l’accessibilità dell’output. Un percorso di configurazione scrivibile in `/tmp` è soltanto un indizio da approfondire: esamina il binario e i metadati dei file senza invocare il trasferimento privilegiato.
- Una regola sudo per `git apply` può consentire all’account RunAs di scrivere file selezionati da una patch controllata dal chiamante. [CVE-2023-23946](https://github.com/git/git/security/advisories/GHSA-r87m-v37r-cwfh) permetteva a una patch appositamente creata di creare un symlink e poi scrivere fuori dall’albero di lavoro, anche quando il comando non accettava `--unsafe-paths`. Verifica la regola sudo effettiva sugli argomenti, la provenienza della patch, l’accesso dell’account RunAs alla directory di lavoro e la correzione Git installata o il backport del fornitore. Una regola senza restrizioni che ammette `--unsafe-paths` comporta un rischio separato legato a un’opzione esplicita; né la versione di Git né il solo permesso per `git apply` dimostrano che sia possibile modificare un file protetto. Durante la ricognizione passiva, non applicare patch non fidate.
- Una regola sudo per `clamscan --debug`, eseguibile come root, può superare un confine di lettura se un utente con privilegi inferiori può fornire un’immagine DMG e il parser installato è affetto da [CVE-2023-20052](https://blog.clamav.net/2023/02/clamav-01038-01052-and-101-patch.html), che potrebbe divulgare il contenuto dei file tramite l’output di debug. Verifica gli argomenti consentiti e il percorso di scansione esatti, il controllo dell’input, l’account RunAs effettivo, le patch o i backport del motore e se il chiamante può vedere l’output. Se una regola più ampia consente `--file-list`/`-f`, verifica separatamente il comportamento di tale opzione: una policy limitata a `--debug <scan-path>` non la consente. Durante la ricognizione, esamina la policy e i metadati dei pacchetti senza analizzare un file appositamente creato né mostrare output protetto.
- Una regola sudo per aprire un’immagine disco cifrata scelta dal chiamante, eseguibile come root, insieme a una seconda regola per montare il mapper risultante può importare file controllati dal chiamante nel mount namespace dell’host. Verifica entrambe le regole effettive e i relativi argomenti, il controllo dell’immagine e del nome del mapper, il punto di mount effettivo e proprietario e modalità dei file risultanti. Una transizione tramite set-user-ID richiede inoltre un eseguibile accessibile, opzioni di mount che lo rispettino (`nosuid` lo impedisce) e policy di processo o MAC applicabili; aprire o montare un’immagine da solo è soltanto un indizio da approfondire. Un percorso separato tramite un backup esistente richiede la sua chiave effettiva e un segreto utile e leggibile al suo interno. Durante la ricognizione passiva, esamina policy e percorsi senza aprire o montare un’immagine. Vedi il [manuale di cryptsetup](https://gitlab.com/cryptsetup/cryptsetup/-/blob/main/man/cryptsetup.8.adoc) e [le opzioni di mount](https://man7.org/linux/man-pages/man8/mount.8.html).
- Una regola sudo per uno script shell o Python eseguibile come root merita un’analisi della directory di lavoro se lo script invoca `./helper` senza prima spostarsi in una directory fissa. Una lista Python come `['./helper']` passata a `subprocess.run` può avere lo stesso comportamento, dipendente dalla directory di lavoro scelta dal chiamante. Il chiamante potrebbe scegliere una directory scrivibile e inserirvi un eseguibile con quel nome relativo; un percorso assoluto altrove nello script non protegge questa chiamata. Prima di considerarlo esecuzione di codice, verifica la regola effettiva, `runchdir` o altre policy che cambiano directory, il flusso dello script e la raggiungibilità del ramo, la presenza di una directory scrivibile ed eseguibile e le restrizioni di mount/`NOEXEC`. Se lo script non è leggibile, il comportamento resta ignoto finché il sorgente non viene esaminato tramite un percorso autorizzato. Esamina gli script staticamente invece di eseguire l’helper. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) documenta la policy della directory di lavoro.
- Un validatore Python fisso eseguibile come root può comunque valutare un file di dati scelto dal chiamante. [La documentazione di `eval()` di Python mette in guardia dall’uso di input non fidati](https://docs.python.org/3/library/functions.html#eval): un controllo del suffisso dell’input, un prefisso aritmetico o un ramo di convalida non costituiscono una sandbox se l’espressione rimanente raggiunge `eval`. Prima di considerarlo un percorso di esecuzione, verifica la regola sudo effettiva, se il chiamante può selezionare e controllare il file esatto, le condizioni dei rami del parser e la costruzione dell’espressione, nonché l’identità del processo privilegiato. La sola presenza di `eval` in uno script leggibile è un indizio da approfondire; durante la ricognizione, esamina sorgente e permessi senza eseguire il validatore né inviare un’espressione di prova.
- Un wrapper Ruby eseguibile come root tramite sudo che legge un nome di file YAML relativo, come `YAML.load(File.read("dependencies.yml"))`, può prendere l’input dalla directory di lavoro del chiamante, a meno che il wrapper o la policy sudo non fissino la directory. Verifica gli argomenti consentiti esatti, i permessi della directory e del file e il comportamento di Psych installato: le implementazioni più vecchie di `YAML.load` potevano deserializzare oggetti Ruby arbitrari, mentre le versioni più recenti limitano le classi per impostazione predefinita. Una chiamata statica è soltanto un indizio; verifica che il file provenga davvero da una directory scrivibile dal chiamante e che il loader installato accetti classi pericolose. Per input non fidati, preferisci `safe_load` con una lista di permessi esplicita e minima. Vedi la [documentazione di Psych per Ruby 3.0](https://docs.ruby-lang.org/en/3.0/Psych.html) e la [documentazione di Psych per Ruby 3.1](https://ruby-doc.org/core-3.1.2/Psych.html).

- Una concessione sudo esatta per `sudo go run /absolute/file.go`, eseguibile come root, merita un’analisi della directory di lavoro quando il sorgente Go legge un file WASM relativo e potrebbe eseguire uno script shell relativo dopo averne esaminato il risultato. Verifica RunAs effettivo, argomenti e negazioni del comando, una directory corrente scrivibile dal chiamante, il flusso dei dati dal WASM al ramo e se quel ramo invoca l’helper. Un `runchdir` sudo fisso, `os.Chdir` o [`exec.Cmd.Dir`](https://pkg.go.dev/os/exec) possono modificare la posizione di ricerca. Una co-occorrenza statica è soltanto un caso candidato; esamina il sorgente senza eseguire Go, WASM o l’helper.
- `sudoedit` e i wildcard negli argomenti richiedono controlli esatti della versione e della regola; la [checklist](linux-privilege-escalation-checklist.md) include il problema di modifica dei file tramite sudoedit. Per una concessione `sudoedit` tra utenti diversi su un percorso con wildcard, esamina l’impostazione effettiva `sudoedit_follow` o `FOLLOW`, `sudoedit_checkdir`, la destinazione risolta e chi può sostituire ogni voce delle directory genitrici. La prima può consentire di seguire un symlink, mentre disabilitare la seconda rimuove i controlli sulle directory scrivibili; nessuna delle due impostazioni dimostra da sola la possibilità di scrivere nel file di un altro utente. Verifica la policy sudo installata e gli argomenti esatti corrispondenti prima di trarre conclusioni. Vedi le [definizioni delle opzioni sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf).
- In una regola di comando sudoers, un wildcard negli argomenti può corrispondere anche a spazi, oltre che a caratteri di percorso. Una regola per un comando in grado di leggere file con un argomento come `/restricted/*` può quindi ammettere un ulteriore argomento file dopo un prefisso corrispondente. Verifica utente RunAs esatto, percorso del comando, schema degli argomenti e successive negazioni; la lettura dimostrata di un file non implica l’esecuzione di comandi. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) distingue i glob degli argomenti dai glob dei percorsi dei comandi.
- Anche un glob degli argomenti dall’aspetto simile a un percorso può corrispondere a `../`. Per esempio, una regola `node /opt/scripts/*.js` eseguibile come root può consentire un file JavaScript controllato dal chiamante al di fuori di `/opt/scripts` se il percorso fornito inizia comunque con `/opt/scripts/` e si risolve attraverso segmenti di directory genitrici. Questo è un glob di **argomento**; il glob del percorso dell’eseguibile Node applica regole diverse alle barre. Prima di concludere che si possa eseguire codice, verifica la regola effettiva, le successive negazioni, la risoluzione del percorso, il controllo del file di destinazione e le eventuali restrizioni sudoers basate su espressioni regolari o digest. Vedi le [regole sui wildcard di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) e la [documentazione della riga di comando Node](https://nodejs.org/api/cli.html).
- Gli archiviatori e altri programmi di utilità possono offrire hook di esecuzione. Verifica gli argomenti consentiti esatti usando [GTFOBins](https://gtfobins.github.io/) invece di presumere che solo shell o interpreti eseguano comandi.
- Una regola `qpdf` senza restrizioni, eseguibile come root, può esporre un file privilegiato tramite allegati PDF: qpdf dalla versione 10.2 supporta `--empty` e `--add-attachment file ... --` insieme a un PDF di output. Se il processo privilegiato può leggere la sorgente selezionata e scrivere il PDF in un percorso accessibile al chiamante, l’output può contenere i byte della sorgente. Prima di concludere che la divulgazione sia possibile, verifica gli argomenti sudo effettivi e le esclusioni, la versione di qpdf, l’accesso alla sorgente e il percorso di output. Leggere una chiave SSH di root è utile per l’accesso solo se la chiave è valida e l’autenticazione SSH di root è consentita. Vedi le [opzioni di allegato di qpdf](https://qpdf.readthedocs.io/en/stable/cli.html#embedded-files-attachments).
- Il riutilizzo delle credenziali sudo dipende dalla policy della cache, dall’utente proprietario, dal terminale/sessione e dai permessi. La [guida all’escalation dei privilegi](../linux-basics/linux-privilege-escalation/README.md#reusing-sudo-tokens) descrive i controlli necessari.
- `doas` ha regole e configurazione proprie. Verifica i comandi consentiti e i percorsi di configurazione scrivibili come descritto nella [sezione su doas](../linux-basics/linux-privilege-escalation/README.md#doas).

### Strumenti di build e pacchetti eseguiti tramite sudo

Una concessione sudo senza restrizioni per `forge` di Foundry può essere rilevante anche quando l’identità RunAs è un altro utente non-root. Opzioni del compilatore come `--use` possono selezionare un eseguibile locale, mentre `forge flatten -o` seleziona un file di output. Prima di considerare la concessione sfruttabile, verifica la versione di Forge installata, gli argomenti sudo esatti, i percorsi accessibili del progetto e del compilatore, i permessi dell’output e l’ambiente effettivo. Un helper eseguibile relativo trovato tramite `PATH` è un percorso che dipende dalla versione e dall’ambiente, non una caratteristica da presumere in ogni build di Forge.<sup>[[23]](#references)[[24]](#references)</sup>

Una concessione `pacman` senza restrizioni, eseguibile come root, consente più delle sole query sui pacchetti: `-U` accetta un pacchetto locale, i pacchetti possono contenere script di installazione e `--hookdir` seleziona un’altra directory di hook. Prima di eseguire test, esamina la regola sudo effettiva, le restrizioni sugli argomenti e le esclusioni; la ricognizione passiva non richiede di installare un pacchetto o eseguire un hook.<sup>[[25]](#references)[[26]](#references)</sup>

Un wrapper shell fisso eseguito tramite sudo può anche installare una dipendenza npm per nome e poi avviare un’applicazione Node. Esamina la regola RunAs esatta, se il pacchetto è già installato, i valori effettivi di `HOME` e `userconfig` di npm, gli override della configurazione del progetto o della riga di comando e se un utente con privilegi inferiori controlla il registry o il pacchetto restituito per quel nome. [npm documenta la ricerca di `.npmrc` per utente e progetto](https://docs.npmjs.com/cli/v6/configuring-npm/npmrc/); il comportamento di `HOME` in sudo dipende dalla policy installata e dalla distribuzione, quindi il processo npm privilegiato potrebbe leggere o meno il file `.npmrc` di un utente scrivibile. Se il pacchetto appena installato viene importato dall’applicazione privilegiata, il suo codice modulo può essere eseguito con l’identità dell’applicazione. Gli script di installazione costituiscono un percorso distinto, dipendente dalla versione e dalla configurazione; [npm ne documenta il ciclo di vita e la gestione degli utenti](https://docs.npmjs.com/cli/v6/using-npm/scripts/). Un percorso `.npmrc` o una riga `npm install` sono soltanto indizi. Durante la ricognizione passiva, esamina la regola, il wrapper breve, i percorsi di configurazione e la provenienza del pacchetto senza installare nulla né avviare l’applicazione.

Una concessione `pip` o `pip3 download` eseguibile come root è anche un indizio da verificare rispetto alla build dei pacchetti quando gli argomenti consentono al chiamante di selezionare una distribuzione sorgente non fidata, anche se lo schema dell’URL è limitato a un servizio locale e a un suffisso `.tar.gz`. `pip download` accetta URL di archivi e risolve i metadati dei pacchetti; la preparazione dei metadati di una distribuzione sorgente può invocare il suo backend di build o il codice legacy `setup.py` prima che l’archivio venga semplicemente salvato. Verifica la regola RunAs sudo e gli argomenti esatti, se il chiamante può pubblicare o sostituire l’archivio selezionato e se quella versione di pip prepara davvero i metadati. Un archivio fisso e fidato o un wheel non dimostra questo percorso. Durante la ricognizione passiva, non recuperare né compilare pacchetti non fidati. Vedi il comando [`download` di pip](https://pip.pypa.io/en/stable/cli/pip_download/), l’[interfaccia del sistema di build](https://pip.pypa.io/en/stable/reference/build-system/) e le [indicazioni per installazioni sicure](https://pip.pypa.io/en/stable/topics/secure-installs/).

Una regola sudo che consente `pip install` con un percorso di progetto locale scelto dal chiamante crea un confine di build più diretto. [pip accetta directory di progetti locali](https://pip.pypa.io/en/stable/topics/local-project-installs/) e ne invoca il sistema di build; il [backend di build esegue hook controllati dal progetto](https://pip.pypa.io/en/stable/reference/build-system/). Prima di considerare la regola un’esecuzione di codice privilegiata, verifica l’identità RunAs effettiva, le restrizioni e le negazioni esatte sugli argomenti, il controllo del progetto selezionato e il comportamento di pip/backend installati. Un progetto fisso e fidato o una regola che esclude i percorsi scelti dal chiamante non dimostrano questo percorso. Durante la ricognizione passiva, esamina regola e metadati del progetto senza installare un pacchetto.

Una concessione `easy_install` senza restrizioni, eseguibile come root, è un indizio analogo, relativo alle build di pacchetti legacy. [Setuptools documenta](https://setuptools.pypa.io/en/stable/deprecated/easy_install.html) che Easy Install accetta una directory di progetto locale e compila distribuzioni sorgente; durante la build, un progetto controllato dal chiamante può eseguire il proprio `setup.py` con l’identità sudo. Verifica l’account RunAs effettivo, il comando esatto e le restrizioni sugli argomenti (incluse le successive negazioni), il controllo del progetto selezionato e il comportamento dello strumento installato. Un progetto fisso e fidato o una policy che non consente al chiamante di scegliere la sorgente non dimostrano questo percorso. Durante la ricognizione, esamina regola e metadati del progetto senza installare un pacchetto.

Un wrapper Python autorizzato da sudo che usa `setuptools.package_index.PackageIndex.download` con un URL scelto dal chiamante è un caso distinto rispetto a `pip download`: [setuptools GHSA-5rjg-fvgr-3xxf](https://github.com/pypa/setuptools/security/advisories/GHSA-5rjg-fvgr-3xxf) descrive, nelle versioni affette precedenti alla 78.1.1, un nome file derivato dall’URL che usciva dalla directory di download prevista e scriveva con i permessi del processo. Verifica la regola RunAs sudo e sugli argomenti effettiva, che il wrapper passi l’URL del chiamante proprio a questa API, la build installata o l’eventuale backport del fornitore e il percorso a cui si risolve il risultato. Una stringa di versione o una directory di download scrivibile, da sole, non dimostrano la possibilità di scrivere file arbitrari. Durante la ricognizione, esamina il wrapper breve e i metadati del pacchetto senza recuperare l’URL né scrivere un file.

Un wrapper di build autorizzato da sudo che passa un file `.spec` scelto dal chiamante a PyInstaller richiede la stessa verifica del confine di fiducia. Un file spec di PyInstaller è codice Python eseguibile valutato durante la **build**, e le sue voci `datas` possono includere nell’artefatto file leggibili dall’identità di build. Verifica l’utente RunAs esatto, la regola sudo sugli argomenti e le negazioni, la gestione dei percorsi e dei rami del wrapper, il controllo del file spec selezionato e l’accesso all’artefatto risultante. Consentire soltanto un input `.py` o trovare PyInstaller installato non dimostra che il chiamante controlli il file spec o possa eseguire codice privilegiato. L’analisi passiva dovrebbe leggere solo un wrapper circoscritto e i metadati; non dovrebbe eseguire una build. Vedi la [documentazione dei file spec di PyInstaller](https://pyinstaller.org/en/stable/spec-files.html).

### Loader di preset e plugin eseguiti tramite sudo

Gli strumenti Python che accettano un preset o una directory di plugin scelti dal chiamante possono importare codice con i privilegi concessi da sudo. Per esempio, BBOT accetta un preset con `-p`, e la sua [documentazione sui moduli personalizzati](https://www.blacklanternsecurity.com/bbot/Stable/dev/module_howto/#load-modules-from-custom-locations) descrive le voci `module_dirs` che selezionano directory aggiuntive di moduli Python. Se la regola sudo effettiva consente un preset scelto dal chiamante e quest’ultimo controlla un modulo nella directory selezionata, l’import può eseguire codice come utente privilegiato, anche prima che lo strumento rifiuti un modulo non valido. Verifica la versione installata, la policy sudo esatta per RunAs e argomenti e la proprietà delle directory del preset e dei moduli senza caricare il modulo durante la ricognizione.

### Strumento a riga di comando Backdrop eseguito tramite sudo

[Bee](https://github.com/backdrop-contrib/bee) è uno strumento a riga di comando PHP per Backdrop CMS. I suoi comandi `eval` (`php-eval`) e `php-script` possono eseguire PHP fornito dal chiamante. Una regola sudo che consente l’esecuzione del binario Bee come root con argomenti senza restrizioni può quindi esporre l’esecuzione di codice come root quando Bee riesce ad avviare un’installazione Backdrop. Eseguilo dalla directory del sito oppure seleziona un sito con l’opzione globale `--root=<directory>`; trovare Bee o un file `settings.php` di Backdrop non dimostra i permessi sudo, la presenza di un sito utilizzabile o il completamento del bootstrap. Prima di eseguire test, esamina la regola sudo effettiva, eventuali esclusioni di comando, l’identità dell’eseguibile e l’accesso al sito. Durante la ricognizione passiva, esamina regola e percorsi dei file senza invocare Bee. Vedi il [changelog dei comandi Bee](https://github.com/backdrop-contrib/bee/blob/1.x-1.x/CHANGELOG.md) per l’aggiunta dei comandi PHP.

### Server terminal eseguiti tramite sudo

`mosh-server` avvia un server terminal interattivo come utente che lo invoca. Sceglie una porta UDP alta e una chiave di sessione, le comunica al chiamante e, normalmente, quando un client si connette avvia la shell di login di quell’utente. Una concessione sudo senza restrizioni per `mosh-server`, eseguibile come root, è quindi un caso da verificare rispetto alla shell, anche se il comando server si scollega. Verifica l’identità RunAs effettiva, gli argomenti consentiti e le esclusioni, il binario installato, la shell, la disponibilità del client e l’accesso UDP. La ricognizione passiva dovrebbe esaminare la regola sudo senza avviare un server né mostrare chiavi di sessione attive. Vedi il [manuale del server Mosh](https://manpages.debian.org/unstable/mosh/mosh-server.1.en.html) e le [note di progettazione upstream](https://github.com/mobile-shell/mosh#how-it-works).

### Wrapper di backup privilegiati che riscrivono il file di task del chiamante

Un wrapper shell eseguito come root può accettare un file di task scelto dal chiamante, rimuovere `../` dai percorsi sorgente, verificare che ogni risultato inizi con una directory consentita, riscrivere il file di task e poi passare il relativo *percorso* a un programma di backup. Esamina il percorso trasformato dopo averne eseguito la risoluzione canonica completa: un singolo passaggio di sostituzione delle stringhe può creare una nuova sequenza di traversal accettata da un controllo lessicale del prefisso. Verifica inoltre se il programma di backup legge i dati trasformati dalla memoria o riapre il file. Se riapre il file, una riscrittura non riuscita può lasciare intatto l’input originale.

Su Linux, `fs.protected_regular` può negare una scrittura `O_CREAT` sul file regolare di un altro utente in una directory sticky scrivibile da tutti. Il diniego è protettivo, ma un wrapper shell che ignora l’errore di scrittura può comunque continuare usando il file di task originale. Verifica questa impostazione, il proprietario del file e della directory e se il wrapper si arresta in caso di errore. Il percorso è un candidato alla divulgazione di file solo se la regola sudo effettiva consente di eseguire il wrapper come utente privilegiato, il chiamante controlla l’input del task e la destinazione leggibile del backup e l’utilità di backup include davvero le sorgenti protette. Durante la ricognizione, verifica queste condizioni senza eseguire il backup.

### Wildcard negli argomenti degli strumenti di rete privilegiati

In una regola sudo per `tcpdump`, un `*` nello schema degli **argomenti** può corrispondere a spazi e barre; una restrizione che sembra indicare un percorso può quindi ammettere ulteriore testo contenente opzioni. È un caso diverso dal wildcard nel percorso dell’eseguibile del comando: esamina l’intera regola RunAs e le eventuali negazioni successive. Se è possibile iniettare opzioni, l’invocazione consentita e la semantica delle opzioni di [`tcpdump`](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) installato determinano se `-F`, `-V`, `-r`, `-w` o `-Z` offrono una primitiva utile di lettura/scrittura. `-V` legge un elenco di file di acquisizione, non effettua un dump generico di file arbitrari. AppArmor o un’altra policy MAC possono bloccare l’accesso ai file anche quando sudo consente il comando; la presenza di un file di profilo su disco non dimostra che sia caricato o applicato. Prima di trarre conclusioni, esamina in modo passivo autorizzazioni e policy. Il [manuale di sudoers](https://www.sudo.ws/docs/man/1.9.14/sudoers.man.pdf) descrive la differenza tra i wildcard.

Anche una regola sudo eseguibile come root che elenca solo l’eseguibile `tcpdump`, senza restrizioni sugli argomenti, merita un’analisi. Il [manuale di tcpdump](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in) documenta `-z` come comando post-rotazione quando `-C` o `-G` ruotano un’acquisizione salvata; `-Z` o un valore predefinito in fase di compilazione possono rimuovere i privilegi prima dell’esecuzione di quel comando. Prima di considerare la regola un percorso di escalation, verifica la regola sudo effettiva, la build installata, il comportamento di rimozione dei privilegi e la possibilità che si verifichi una rotazione. Una regola evidenziata è un caso candidato, non la prova dell’esecuzione di comandi come root.

### Wrapper Nmap eseguiti tramite sudo

Quando il percorso Nmap consentito da sudo è un wrapper shell, esamina il percorso consentito esatto e ogni opzione che inoltra. Bloccare la grafia più nota `--script` non impedisce necessariamente il caricamento di codice NSE: [`--datadir` di Nmap](https://nmap.org/book/man-misc-options.html) seleziona i file di dati e NSE [carica `nse_main.lua`](https://nmap.org/book/nse-implementation.html) dalla directory di dati selezionata quando lo scripting è abilitato. Alcune build installate accettano anche grafie alternative delle opzioni lunghe, quindi confronta le restrizioni con il parser effettivo di quel binario. [`--excludefile`](https://nmap.org/book/man-target-specification.html) è una superficie separata di lettura dei file; gli errori del parser possono rivelarne il testo. Durante la ricognizione, verifica la regola sudo effettiva, la logica del wrapper, la versione di Nmap, il controllo delle directory e la policy MAC senza eseguire scansioni.

### Hook pull di Mercurial eseguiti tramite sudo

Un’origine fissa in `sudo hg pull /fixed/source` lascia comunque selezionato il repository **ricevente** dalla directory di lavoro corrente, a meno che il comando non lo fissi con `-R`. Un repository ricevente controllato dal chiamante può definire hook in `.hg/hgrc`, che possono essere eseguiti come l’utente RunAs di sudo. [Mercurial ignora la configurazione dei repository di proprietà di un utente o gruppo non fidato](https://mercurial-scm.org/help/topics/config), quindi prima di considerare il caso esecuzione di codice esamina gli utenti e i gruppi fidati dell’account RunAs e la directory di lavoro esatta. Per un’analisi passiva basta leggere la policy e la configurazione; durante la ricognizione, non eseguire `pull` né invocare un hook.

### Hook pull di Git eseguiti tramite sudo

Per una concessione sudo esatta per `sudo git pull`, verifica anche il repository **ricevente** selezionato dalla directory di lavoro. Un repository di proprietà del chiamante può contenere un hook `post-merge` eseguibile, eseguito con l’identità del processo Git quando un pull completa effettivamente un merge; [Git documenta questo hook](https://git-scm.com/docs/githooks) e [il comportamento di pull tra merge e rebase](https://git-scm.com/docs/git-pull). Verifica la regola sudo effettiva e la directory di lavoro corrente, il percorso attivo dell’hook e i relativi permessi, nonché la possibilità di raggiungere un merge con nuovi commit. Un pull non riuscito, senza modifiche o limitato al rebase non dimostra questo percorso tramite hook. Esamina policy e metadati del repository senza eseguire il pull privilegiato.

### Copie archivio rsync eseguite tramite sudo

Per `sudo rsync -a ... /writable/source/* /fixed/destination/`, un `*` nello **schema degli argomenti di sudoers** può corrispondere a spazi e ammettere un’opzione aggiuntiva tra sorgente e destinazione. Questo è distinto dall’espansione shell dei nomi di file. Se il chiamante può popolare la sorgente e la destinazione è scrivibile dal processo rsync privilegiato, [`--chown`](https://download.samba.org/pub/rsync/rsync.1) può richiedere una proprietà privilegiata mentre la modalità archivio conserva i bit di permesso, creando potenzialmente un file SetUID di proprietà privilegiata. Verifica l’esatta [semantica dei wildcard di sudoers](https://man7.org/linux/man-pages/man5/sudoers.5.html), la versione di rsync, le negazioni successive, `nosuid` del filesystem e la policy MAC. Una regola corrispondente è un caso da approfondire, non la prova di un’escalation dei privilegi riuscita.

### Esportazione di regole del packet filter tramite sudo

Una concessione senza restrizioni, eseguibile come root, sia per `iptables` sia per `iptables-save` (o per la coppia corrispondente `ip6tables`) merita un’analisi di scrittura dei file. Il match `comment` accetta testo delle regole scelto dal chiamante, mentre `iptables-save -f` scrive l’insieme serializzato di regole in un percorso selezionato.<sup>[[20]](#references)[[21]](#references)</sup> L’esistenza di un payload utile dipende da come il backend installato serializza i commenti e dal fatto che il file di destinazione accetti altre righe nell’esportazione; `iptables-save` da solo non fornisce contenuto arbitrario scelto dal chiamante. Verifica identità RunAs, argomenti ed esclusioni sudo esatti, estensione di match disponibile, backend e permessi della destinazione. Durante la ricognizione, esamina la concessione senza modificare le regole del firewall né scrivere file.

### Directory di logging privilegiata di Below

[CVE-2025-27591](https://github.com/facebookincubator/below/security/advisories/GHSA-9mc5-7qhg-fp3w) ha interessato le versioni di Below precedenti alla 0.9.0 che creavano una directory `/var/log/below` scrivibile da tutti. Se un servizio o un comando sudo consentito esegue come root una build affetta, un utente in grado di scrivere e attraversare una directory di log non sticky potrebbe sostituire una voce di log con un symlink prima che il processo privilegiato la apra. Esamina lo stato delle patch del pacchetto installato, il percorso esatto di esecuzione privilegiata, l’accesso effettivo alla directory, sticky bit e ACL, nonché i metadati di `/var/log/below/error_root.log`. Un percorso scrivibile da tutti o una regola sudo da soli non dimostrano l’intera catena. Una directory sticky o un backport del fornitore modificano la valutazione. La ricognizione passiva dovrebbe esaminare solo i metadati; non è necessario creare un link né eseguire il programma privilegiato.

### Raccolta di bundle di supporto privilegiati da input scrivibili

Uno script di profilo di supporto consentito da `sudo` può leggere come root percorsi di log fissi e copiarne il contenuto in un archivio di profilo. Esamina lo script effettivo per verificare le letture dei file, poi controlla se il chiamante può sostituire un percorso sorgente o una voce delle directory genitrici con un symlink. Se la lettura privilegiata segue quel link e l’archivio risultante è leggibile dal chiamante, un file protetto può essere divulgato. Devono essere presenti tutti gli elementi: concessione sudo, percorso sorgente scrivibile, lettura privilegiata e output leggibile. Un log o nome di profilo scrivibile, da solo, non basta. Durante la ricognizione, esamina i permessi effettivi e i metadati dei link senza sostituire file né generare un profilo. Le [indicazioni di supporto per Nagios XI](https://support.nagios.com/forum/viewtopic.php?t=62758) documentano il suo script di profilo eseguito come root e l’archivio di output, mostrando perché input e accesso all’output di questi bundle devono essere limitati.

### Script Python di ripristino di archivi eseguiti come root

Anche una regola sudo strettamente circoscritta per uno script Python di ripristino richiede l’analisi dell’archivio di input. Se il chiamante può selezionare o sostituire l’archivio e lo script lo estrae come root con `tarfile.extractall(filter="data")`, verifica gli aggiornamenti di sicurezza dell’interprete prima di fidarti del filtro. CPython ha corretto diversi bypass dei filtri con symlink e hard link, tra cui CVE-2025-4517, nelle versioni 3.9.23, 3.10.18, 3.11.13, 3.12.11 e 3.13.4. I backport delle distribuzioni possono correggere una versione precedente, quindi la versione dell’interprete mostrata non dimostra da sola l’esposizione.<sup>[[16]](#references)[[17]](#references)</sup>

Per un’analisi passiva, leggi il comando sudo e lo script esatti, segui quale argomento seleziona l’archivio e verifica se l’utente corrente può scrivere l’archivio o la directory che lo contiene. Verifica separatamente la patch del fornitore installata e la destinazione dell’estrazione: `filter="data"` non rende sicuro qualsiasi archivio non fidato.<sup>[[16]](#references)[[17]](#references)</sup>

### Loader di modelli di machine learning eseguiti tramite sudo

Una regola sudo che consente un file `.pt`, `.pth` o `.ckpt` scelto dal chiamante merita un’analisi se uno script privilegiato passa quel file a [`torch.load`](https://docs.pytorch.org/docs/stable/generated/torch.load.html), `pickle.load` o un altro loader basato su pickle. Verifica la regola RunAs effettiva, se il chiamante può creare o sostituire il modello selezionato e il flusso effettivo degli argomenti attraverso qualsiasi wrapper shell fino all’helper Python. L’estensione `.pth` indica anche file di configurazione Python del sito non correlati, quindi l’estensione da sola non dimostra che venga caricato un modello. La scansione di un archivio o un’analisi statica di pickle non dimostrano che il caricamento successivo sia sicuro; esamina il comportamento di [`weights_only` dipendente dalla versione](https://docs.pytorch.org/docs/stable/notes/serialization.html) del loader e l’eventuale allowlist. Vedi le [note su pickle ML e Fickling](../../AI/keras-model-deserialization-rce-and-gadget-hunting.md#ml-pickle-import-allowlisting-for-aiml-models-fickling). La ricognizione passiva non dovrebbe mai caricare né estrarre il modello.

### Analisi di espressioni su input memorizzati eseguita tramite sudo

Uno script Python fisso eseguito come root tramite sudo può comunque valutare testo che un utente con privilegi inferiori può memorizzare nel database di un’applicazione. In TensorFlow, una chiamata a `preprocess_input_exprs_arg_string(value, safe=False)` seleziona un percorso `eval`; [l’avviso di sicurezza di TensorFlow](https://github.com/tensorflow/tensorflow/security/advisories/GHSA-75c9-jrh4-79mc) descrive il parser non sicuro e una correzione nel chiamante da riga di comando. Una chiamata esplicita `safe=False` di un’applicazione richiede un’analisi separata anche quando quel chiamante da riga di comando è stato corretto. Verifica la regola sudo effettiva, chi può modificare la riga di input specifica, se i filtri o il punteggio consentono a tale riga di raggiungere la chiamata e il comportamento della funzione installata. Una versione di TensorFlow, una concessione sudo o un file modello hardcoded, da soli, non dimostrano la catena. Esamina script e flusso dei dati passivamente; durante la ricognizione non eseguire l’helper privilegiato né inviare espressioni di prova.

### Configurazione di needrestart consentita tramite sudo

`needrestart -c` carica un file di configurazione Perl scelto dal chiamante e ne valuta il contenuto. Se `sudo -l` consente `needrestart` come root con argomenti che ammettono `-c` e il chiamante può scegliere un file di configurazione leggibile in una posizione scrivibile, il permesso può portare all’esecuzione di codice come root. Verifica la regola RunAs e sugli argomenti esatta; una regola che consente solo un elenco fisso di argomenti può bloccare questo percorso. È un caso distinto dalle vulnerabilità di needrestart durante la scansione degli interpreti: aggiornare il pacchetto o disabilitare `interpscan` non rende sicura una concessione `-c` illimitata come root.<sup>[[2]](#references)[[18]](#references)[[19]](#references)</sup>

### Import Python tramite sudo sotto un altro account

Un entry point Python fisso può comunque importare un modulo che il chiamante può modificare o sostituire, anche quando sudo esegue lo script come utente di servizio **non-root**. Per un `from utils import status` letterale, esamina `utils/__init__.py` e `utils/status.py` locali, nonché i permessi della directory del pacchetto. Prima di considerare il file scrivibile un percorso di esecuzione, verifica il percorso di import dello script, gli argomenti sudo consentiti esatti e se l’azione pertinente raggiunge quell’import. Durante la ricognizione, esamina file e permessi senza importare né eseguire lo script.<sup>[[2]](#references)[[3]](#references)</sup>

Una regola sudo esatta per `python3 /absolute/script.py` richiede soltanto che lo script sia leggibile; il file non deve essere eseguibile né avere uno shebang. Esamina anche i moduli locali **mancanti**: se lo script importa un modulo il cui nome file può essere creato in una directory dello script scrivibile dal chiamante, Python può caricarlo con l’identità RunAs. Verifica la regola sudo effettiva, il vero [percorso di ricerca dei moduli](https://docs.python.org/3/library/sys_path_init.html) dell’interprete, se il modulo è integrato o congelato e se l’import viene raggiunto. Una regola sudo diretta per lo script ha requisiti diversi relativi al bit di esecuzione e allo shebang. Anche un wrapper separato che aggiunge token forniti dal chiamante dopo `sudo -u account` richiede un’analisi del flusso degli argomenti: un altro `-u` in quei token è rilevante solo se la policy sudo invocata consente l’identità risultante. Le sole stringhe statiche non dimostrano nessuno dei due percorsi.

### Apache eseguito tramite sudo con configurazione controllata dal chiamante

Se una regola sudo consente un’invocazione privilegiata di `apachectl`, `apache2ctl` o `httpd` con un file di configurazione `-f` controllato dal chiamante, esamina i permessi del file e della directory genitrice. La direttiva Apache [`LoadModule`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadmodule) accetta un nome di modulo seguito dal **nome file del modulo**; anche [`LoadFile`](https://httpd.apache.org/docs/2.4/mod/mod_so.html#loadfile) carica un file. [`Include` e `IncludeOptional`](https://httpd.apache.org/docs/2.4/mod/core.html#include) possono estendere la configurazione o esporre contenuti di file tramite errori. Un wrapper personalizzato può convalidare questi percorsi, rimuovere i privilegi o limitare gli argomenti, quindi una configurazione scrivibile è un caso da approfondire, non una prova di esecuzione di codice. Prima di trarre conclusioni, verifica la canonicalizzazione dei percorsi, i symlink e l’analisi delle direttive.

### nginx eseguito tramite sudo con configurazione controllata dal chiamante

Una regola `nginx` senza restrizioni, eseguibile come root, può consentire di selezionare un’altra configurazione con [`-c`](https://nginx.org/en/docs/switches.html). Esamina gli argomenti sudo esatti e le esclusioni, se il chiamante può fornire la configurazione e se il master o i worker risultanti mantengono l’accesso ai percorsi protetti. Una combinazione di `root` scelto e `autoindex` può esporre file tramite un nuovo listener; [`dav_methods PUT`](https://nginx.org/en/docs/http/ngx_http_dav_module.html) può fornire un percorso di scrittura privilegiata, ma il modulo DAV non viene compilato per impostazione predefinita e occorre verificare che sia presente, che il listener sia raggiungibile, i permessi dei file e il comportamento dei file temporanei. Anche la direttiva [`error_log`](https://nginx.org/en/docs/ngx_core_module.html#error_log) può puntare a un file scelto; scrivere log in un file di configurazione sensibile, come `/etc/ld.so.preload`, diventa un percorso di escalation solo se esiste un writer privilegiato effettivo e il chiamante controlla una voce di log. L’evidenziazione dell’eseguibile in `sudo -l` è un indizio da approfondire, non la prova che uno di questi percorsi funzioni. Durante la ricognizione passiva, non avviare né riconfigurare nginx.

### Confronto di pattern nei prompt Bash privilegiati

Quando uno script Bash consentito da sudo legge un valore dal chiamante e lo controlla con `[[ "$expected" == $entered ]]`, Bash interpreta l’operando destro non quotato come un pattern. Un wildcard può quindi superare il confronto senza conoscere il valore atteso. Quotare l’operando (`[[ "$expected" == "$entered" ]]`) lo trasforma in un confronto tra stringhe letterali. Esamina la regola sudo esatta, se il prompt è raggiungibile e cosa fa lo script dopo il confronto; la sintassi da sola non dimostra un percorso sfruttabile. Durante la ricognizione, evita di mostrare il valore atteso. Vedi il [riferimento alle strutture condizionali di Bash](https://www.gnu.org/software/bash/manual/html_node/Conditional-Constructs.html).

### Helper eseguiti tramite sudo che scaricano ed eseguono un file

Una concessione sudo a un helper personalizzato senza restrizioni, eseguibile come root, merita un’analisi del flusso dei dati se accetta un URL scelto dal chiamante, salva la risposta su disco e in seguito esegue il file tramite un interprete o una shell. [Sudoers consente argomenti arbitrari quando una voce di comando non ne specifica](https://man7.org/linux/man-pages/man5/sudoers.5.html); un percorso fisso dell’eseguibile non limita ciò che gli argomenti possono selezionare. Verifica la convalida effettiva dell’URL, il percorso di output, il ramo di successo e la successiva esecuzione nell’helper installato. Un import libcurl corrispondente o una stringa stampabile da sola non dimostrano questa catena.

Anche un nome file di output fisso può essere sostituibile tra scrittura ed esecuzione quando l’helper usa un **percorso relativo in una directory di lavoro controllata dal chiamante**. La rinomina o sostituzione di un file di proprietà di root dipende dall’accesso in scrittura e ricerca alla directory e da eventuali restrizioni sticky bit, non solo dalla modalità del file; vedi [`rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html). Verifica se in seguito l’helper riapre il percorso o usa il descrittore già aperto e se si sposta in una directory fidata prima di scrivere. Esamina passivamente policy sudo, helper e metadati della directory; durante la ricognizione, non invocare il download privilegiato né tentare una race.

Un helper di download eseguibile come root tramite sudo può anche esporre un’iniezione di **argomenti** quando crea una stringa di comando Bash come `curl <input del chiamante> -o <output fisso>`. Un filtro che rifiuta gli spazi lascia comunque attiva l’[espansione delle parentesi graffe di Bash](https://www.gnu.org/software/bash/manual/html_node/Brace-Expansion.html): elementi separati da virgole e non quotati possono trasformarsi in argomenti distinti di curl. Se l’input raggiunge curl prima di `-o` fisso, un’opzione di output fornita dal chiamante può selezionare la destinazione per il primo URL, usando l’identità dell’helper; [curl associa le opzioni di output agli URL nell’ordine indicato](https://curl.se/docs/manpage.html#-o). Verifica la shell esatta, le virgolette, la convalida dell’input, la regola sudo effettiva, l’ordine degli argomenti di curl e gli schemi URL supportati, nonché se il chiamante controlla i byte scaricati o può leggere il risultato. Un eseguibile impacchettato con PyInstaller può contenere logica applicativa Python, ma la sola presenza di un indicatore di packaging o di una stringa `curl` non dimostra questo flusso di dati. Se autorizzato, esamina una copia offline circoscritta; la ricognizione ordinaria non dovrebbe eseguire l’helper né recuperare dati scelti dall’aggressore.

Uno script shell eseguito come root tramite sudo che invoca [`mktemp -u` / `--dry-run`](https://www.gnu.org/software/coreutils/manual/html_node/mktemp-invocation.html) sceglie soltanto un nome non utilizzato: **non** crea il file. Se in seguito lo script crea il file con quel nome in una directory che un altro utente può influenzare, lo riapre e ne aggiunge il contenuto a una destinazione protetta, come il file `authorized_keys` di root, esamina il possibile rischio di race sul file temporaneo. Verifica la regola sudo esatta, la proprietà della directory e del file, la sequenza di creazione e riapertura, le protezioni del kernel e se la scrittura privilegiata usa davvero byte controllati dall’aggressore. Una stringa `mktemp -u` o la sola presenza di `/tmp` scrivibile non dimostrano la race. Durante la ricognizione, esamina script e metadati del percorso senza eseguirlo né tentare una race sul file temporaneo.

## Note difensive

- Evita di concedere interpreti o editor interattivi tramite sudo.<sup>[[1]](#references)</sup>
- Non concedere writer generici di file, come `tee`, con operandi senza restrizioni. Usa un wrapper di proprietà di root che selezioni una destinazione fissa e rifiuti i percorsi controllati dal chiamante.<sup>[[2]](#references)</sup>
- Preferisci wrapper fissi, di proprietà di root, che eseguano una sola e circoscritta azione amministrativa.<sup>[[1]](#references)[[2]](#references)</sup>
- Se un interprete è indispensabile, limita il percorso esatto dello script e impedisci argomenti controllati dall’utente, import scrivibili, `PYTHONPATH` e la conservazione di variabili d’ambiente non sicure.<sup>[[2]](#references)[[3]](#references)[[4]](#references)</sup>
- Se è necessario modificare file, limita il percorso esatto del file e valuta `sudoedit` con versioni di sudo aggiornate e una gestione rigorosa dell’ambiente.<sup>[[1]](#references)[[2]](#references)</sup>
- Esamina `SETENV`, `env_keep`, directory di lavoro scrivibili, percorsi di moduli/import scrivibili, `NOEXEC`, `use_pty` e il logging, ma non considerarli una sandbox completa.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
