# Виснаження та поповнення набору prekey у WhatsApp: side channel

{{#include ../banners/hacktricks-training.md}}

WhatsApp зберігає identity key, підписаний prekey і резерв одноразових prekey для кожного пристрою. Отримання набору пристрою витрачає один одноразовий prekey, що зберігається на сервері, навіть якщо запитувач не надсилає повідомлення. Це дає зловмиснику, який має обліковий запис WhatsApp і номер телефону цілі, **серверний** спосіб перевірки, відмінний від [часових вимірювань квитанцій про доставку на клієнті](side-channel-attacks-on-messaging-protocols.md). Відсутність одноразового prekey також послаблює пряму секретність *початкових* повідомлень новоствореного сеансу; сама по собі вона не розкриває відкритий текст.<sup>[[1]](#references)[[2]](#references)</sup>

## Перевірка наборів пристроїв цілі

Артефакт [Prekey Pogo](https://github.com/sbaresearch/prekey-pogo) створює пару як сеанс супутнього пристрою WhatsApp і підтримує **ручні** запити пристроїв і prekey. Створіть пару з тестовим обліковим записом, а потім скористайтеся його інтерактивними командами `target`, `devices`, `prekey` (основний пристрій) і `combine` (усі пристрої). У випущеному артефакті навмисно немає функцій автоматичного виснаження запасу та перевантаження сервера.<sup>[[1]](#references)[[3]](#references)</sup>

```bash
git clone https://github.com/sbaresearch/prekey-pogo
cd prekey-pogo
./setup.sh
go run .
```

Для кожної відповіді записуйте JID пристрою, часову мітку bundle `t`, ID signed-prekey `skey.id` і те, чи присутній одноразовий `key.id`. ID пристрою `0` — це телефон; ненульові ID — це компаньйони. У реалізаціях, перевірених у статті, початковий ID signed-prekey також дає змогу розрізнити деякі клієнти: Android починає з `0`, iOS і macOS використовують випадкове значення, а WhatsApp Web і Windows Desktop починають з `1`. Вважайте це fingerprint реалізації, а не незмінним правилом протоколу.<sup>[[1]](#references)</sup>

## Перетворення поповнення запасу на oracle онлайн-статусу

Спочатку відкалібруйте процедуру на пристрої, який вам належить: повторно запитуйте його bundle, доки сервер не перестане повертати одноразовий `key`, фіксуючи останню часову мітку та ID ключів. Для цільового пристрою повторіть вичерпання запасу й надішліть повторний запит через контрольований інтервал: новий одноразовий ключ і оновлена часова мітка bundle вказують на те, що пристрій завантажив нову партію. У тестах WhatsApp, про які йдеться у статті, сервер запитував поповнення, коли залишалося менше ніж 11 ключів, а клієнти завантажували 812 нових ключів. Виконуйте процедуру для кожного JID пристрою, щоб відрізнити телефон від компаньйонів. Затримане поповнення лише **може вказувати** на те, що пристрій офлайн: такий самий результат можуть спричинити фонове планування, втрата мережевого з’єднання та різна затримка поповнення в окремих клієнтах. На відміну від RTT квитанції, для цієї перевірки не потрібні доставлений ciphertext або підтвердження з пристрою жертви.<sup>[[1]](#references)[[2]](#references)</sup>

Кожен запит споживає одноразовий ключ, тому для безперервної роботи oracle потрібен власний клієнт, здатний багаторазово отримувати prekey; загальнодоступний артефакт демонструє лише ручні запити. Якщо залишати запас порожнім, інші користувачі можуть створювати нові сесії без одноразового prekey. Це знижує forward secrecy для початкових повідомлень до наступного кроку ratchet, але для експлуатації записаного ciphertext додатково потрібен доступ до E2EE ciphertext, а згодом — компрометація відповідних довгострокових і середньострокових приватних ключів. Уже встановлені сесії автоматично не переходять на слабший захист.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
