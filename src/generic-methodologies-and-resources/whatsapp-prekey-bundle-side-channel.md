# Εξάντληση και αναπλήρωση δέσμης Prekey του WhatsApp μέσω side channel

{{#include ../banners/hacktricks-training.md}}

Το WhatsApp αποθηκεύει ένα identity key, ένα signed prekey και ένα απόθεμα one-time prekeys για κάθε συσκευή. Η ανάκτηση της δέσμης μιας συσκευής καταναλώνει ένα one-time prekey που διατηρείται στον server, ακόμη κι αν ο αιτών δεν στείλει μήνυμα. Έτσι, ένας επιτιθέμενος που διαθέτει λογαριασμό WhatsApp και τον αριθμό τηλεφώνου του στόχου έχει στη διάθεσή του ένα probe **στην πλευρά του server**, διαφορετικό από τον [χρονισμό των αποδείξεων παράδοσης στον client](side-channel-attacks-on-messaging-protocols.md). Η απουσία ενός one-time prekey αποδυναμώνει επίσης το forward secrecy για τα *αρχικά* μηνύματα μιας νέας συνεδρίας· από μόνη της, όμως, δεν αποκαλύπτει plaintext.<sup>[[1]](#references)[[2]](#references)</sup>

## Έλεγχος των δεσμών συσκευών ενός στόχου

Το artifact [Prekey Pogo](https://github.com/sbaresearch/prekey-pogo) πραγματοποιεί σύνδεση ως companion session του WhatsApp και υποστηρίζει **χειροκίνητα** ερωτήματα για συσκευές και prekeys. Συνδέστε το με έναν δοκιμαστικό λογαριασμό και χρησιμοποιήστε τις διαδραστικές εντολές `target`, `devices`, `prekey` (κύρια συσκευή) και `combine` (όλες οι συσκευές). Το artifact που δημοσιεύτηκε παραλείπει σκόπιμα λειτουργίες αυτοματοποιημένης εξάντλησης και συμφόρησης του server.<sup>[[1]](#references)[[3]](#references)</sup>

```bash
git clone https://github.com/sbaresearch/prekey-pogo
cd prekey-pogo
./setup.sh
go run .
```

Για κάθε απόκριση, καταγράψτε το JID της συσκευής, τη χρονική σήμανση του bundle `t`, το ID του signed prekey `skey.id` και αν υπάρχει το one-time `key.id`. Το device ID `0` αντιστοιχεί στο τηλέφωνο· οι μη μηδενικές τιμές αντιστοιχούν σε συνοδευτικές συσκευές. Στις υλοποιήσεις που δοκιμάστηκαν στην εργασία, το αρχικό ID του signed prekey διακρίνει επίσης ορισμένους clients: το Android ξεκινά από `0`, τα iOS και macOS χρησιμοποιούν τυχαία τιμή, ενώ τα WhatsApp Web και Windows Desktop ξεκινούν από `1`. Αντιμετωπίστε το ως αποτύπωμα υλοποίησης και όχι ως αμετάβλητο κανόνα του πρωτοκόλλου.<sup>[[1]](#references)</sup>

## Μετατρέψτε τις αναπληρώσεις σε oracle κατάστασης online

Αρχικά, κάντε βαθμονόμηση σε συσκευή που ελέγχετε: ζητήστε επανειλημμένα το bundle της μέχρι ο server να σταματήσει να επιστρέφει one-time `key`, σημειώνοντας την τελευταία χρονική σήμανση και τα ID των key. Για μια συσκευή-στόχο, επαναλάβετε την εξάντληση και υποβάλετε ξανά ερώτημα μετά από ένα ελεγχόμενο χρονικό διάστημα: ένα νέο one-time key και μια νεότερη χρονική σήμανση bundle δείχνουν ότι η συσκευή ανέβασε μια νέα παρτίδα. Στις αναφερόμενες δοκιμές του WhatsApp, ο server ζητούσε αναπλήρωση όταν απέμεναν λιγότερα από 11 key, και οι clients ανέβαζαν 812 νέα key. Εφαρμόστε τη διαδικασία ξεχωριστά σε κάθε JID συσκευής, ώστε να διακρίνετε ένα τηλέφωνο από τις συνοδευτικές συσκευές. Μια καθυστερημένη αναπλήρωση μόνο **υποδηλώνει** ότι μια συσκευή είναι offline: ο προγραμματισμός εργασιών στο παρασκήνιο, η απώλεια δικτύου και η καθυστέρηση αναπλήρωσης που διαφέρει ανά client μπορούν να προκαλέσουν την ίδια παρατήρηση. Σε αντίθεση με ένα RTT απόδειξης παραλαβής, αυτή η διερεύνηση δεν απαιτεί παραδοθέν ciphertext ή επιβεβαίωση από τη συσκευή του θύματος.<sup>[[1]](#references)[[2]](#references)</sup>

Κάθε ερώτημα καταναλώνει ένα one-time key, επομένως για ένα oracle που λειτουργεί διαρκώς απαιτείται ένας custom client ικανός να ανακτά prekey επανειλημμένα· το δημόσιο artifact παρουσιάζει μόνο χειροκίνητα ερωτήματα. Η διατήρηση του αποθέματος στο μηδέν μπορεί να κάνει άλλους χρήστες να δημιουργούν νέες συνεδρίες χωρίς one-time prekey. Αυτό μειώνει την forward secrecy για τα αρχικά μηνύματα μέχρι να γίνει ένα νέο βήμα ratchet, αλλά για την εκμετάλλευση καταγεγραμμένου ciphertext απαιτείται επιπλέον πρόσβαση στο ciphertext E2EE και μεταγενέστερη παραβίαση των σχετικών ιδιωτικών κλειδιών μακράς και μεσαίας διάρκειας. Οι ήδη ενεργές συνεδρίες δεν υποβαθμίζονται αυτόματα.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
