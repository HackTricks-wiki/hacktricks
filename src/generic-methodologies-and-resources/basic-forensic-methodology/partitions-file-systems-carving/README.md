## Розділи

Диск може містити кілька **розділів**: логічні діапазони блоків, а не фізично окремі сховища. Початок і довжину розділів вимірюють у **логічних секторах**; не вважайте, що кожен образ використовує сектори розміром 512 байтів, оскільки існують також логічні сектори розміром 4096 байтів.<sup>[[4]](#references)</sup>

### MBR (головний завантажувальний запис)

MBR займає перший логічний сектор (LBA 0); чотири 16-байтові записи розділів починаються зі зміщення 446 байтів. Попередня область містить код завантаження та може містити сигнатуру диска.<sup>[[4]](#references)</sup>\
Він дає змогу створити до **4 розділів** (активним/**завантажувальним** може бути **щонайбільше лише 1**). Однак, якщо потрібно більше розділів, можна використовувати **розширені розділи**. Останні **два байти** 512-байтового MBR — це сигнатура завантаження **0x55 0xAA**. Активним можна позначити лише один розділ.\
За логічних секторів розміром 512 байтів 32-бітові поля секторів MBR обмежують адресацію приблизно **2 TiB** (2,2 TB).<sup>[[4]](#references)</sup>

![Розділи — MBR (головний завантажувальний запис): MBR підтримує максимум 2,2 TB](<../../../images/image (304).png>)

У **байтах 440–443** MBR можна знайти **сигнатуру диска Windows** (якщо використовується Windows). Логічна літера диска жорсткого диска залежить від сигнатури диска Windows. Зміна цієї сигнатури може завадити завантаженню Windows (інструмент: [**Active Disk Editor**](https://www.disk-editor.org/index.html)**)**.

Щоб перевірити розділ в образі всього диска з MBR, спершу визначте його початковий LBA та розмір логічного сектора. `mount` приймає **зміщення в байтах**, а не LBA; наведений нижче приклад правильний лише для образу із секторами розміром 512 байтів, у якому розділ починається з LBA 63. Для ненадійних образів або файлових систем із журналюванням використовуйте ізольований режим лише для читання, описаний у розділі [Отримання образу та монтування](../image-acquisition-and-mount.md).<sup>[[5]](#references)[[11]](#references)</sup>

**LBA (Logical block addressing)**

**Logical block addressing** (**LBA**) — це поширена схема, що використовується для **визначення розташування блоків** даних, збережених на комп’ютерних пристроях зберігання, зазвичай у системах вторинного зберігання, таких як жорсткі диски. LBA — особливо проста схема лінійної адресації: **блоки визначаються цілим індексом**, де перший блок має номер LBA 0, другий — LBA 1 і так далі.

### GPT (GUID Partition Table)

GUID Partition Table (GPT) зберігає унікальний GUID для кожного розділу та використовує основні й резервні метадані. Її структура відрізняється від MBR так:<sup>[[4]](#references)</sup>

- **Розташування та розмір**: LBA 0 містить **захисний MBR**. Основний заголовок GPT розташований у LBA 1; за ним іде масив записів розділів, а в кінці диска розміщено резервні масив і заголовок. GPT використовує 64-бітні поля LBA, тоді як записи розділів MBR — 32-бітні.
- **Обмеження на розділи**: типовий масив записів розміром 16 КіБ містить **128 записів по 128 байтів**, однак кількість записів зберігається в заголовку й не є фіксованою для GPT. Доступний для адресації розмір також залежить від розміру логічного сектора (близько **9,4 ZB** для секторів розміром 512 байтів).<sup>[[4]](#references)</sup>
- **Назви розділів**: дає змогу задавати назви розділів завдовжки до 36 символів Unicode.

**Стійкість даних і відновлення**:

- **Резервування**: на відміну від MBR, GPT не обмежує дані розділів і завантаження одним місцем. Ці дані дублюються на диску, що підвищує цілісність і стійкість даних.
- **Циклічний надлишковий код (CRC)**: для заголовка й масиву записів розділів окремо обчислюється CRC32. CRC виявляє невідповідність, але не здійснює постійний моніторинг диска й не відновлює його самостійно. Якщо основна копія недійсна, перевірте резервну копію в останньому LBA, перш ніж виконувати відновлення на робочій копії.<sup>[[4]](#references)</sup>

**Захисний MBR (LBA0)**:

- GPT забезпечує зворотну сумісність за допомогою захисного MBR. Він розташований у просторі застарілого MBR і призначений для запобігання випадковому перезапису дисків GPT старими утилітами на основі MBR, захищаючи цілісність даних на дисках із GPT.

![https://upload.wikimedia.org/wikipedia/commons/thumb/0/07/GUID_Partition_Table_Scheme.svg/800px-GUID_Partition_Table_Scheme.svg.png](<../../../images/image (1062).png>)

**Гібридний MBR (LBA 0 + GPT)**

[З Вікіпедії](https://en.wikipedia.org/wiki/GUID_Partition_Table).<sup>[[1]](#references)</sup>

В операційних системах, які підтримують **завантаження на основі GPT через служби BIOS**, а не EFI, перший сектор усе ще може використовуватися для зберігання коду першого етапу **завантажувача**, але його **змінюють**, щоб він розпізнавав **розділи** **GPT**. Завантажувач у MBR не повинен припускати, що розмір сектора становить 512 байтів.

### Пошук даних поза межами перелічених розділів

Видалений запис розділу або навмисно залишений невикористаним проміжок може призвести до того, що файлова система опиниться за межами поточної карти розділів. На **перевіреній робочій копії у форматі raw** визначте нерозподілені діапазони, а потім перевірте, чи містить кандидатний початковий LBA файлову систему. `mmls` і `fsstat` використовують **зміщення в секторах**; для обох вкажіть фактичний розмір логічного сектора. Не сплутайте сектори метаданих GPT із прихованим томом.<sup>[[5]](#references)[[6]](#references)</sup>

```bash
mmls -b 512 -A disk.img                # Unallocated ranges: Start and Length
fsstat -b 512 -o 2048 disk.img       # Replace 2048 with a candidate Start LBA
```

Якщо `fsstat` не може ідентифікувати файлову систему на початку проміжку, використайте TestDisk **Analyse → Quick Search**, а за потреби — **Deeper Search**. Натисніть `P` на кандидатові, щоб переглянути файли; не вибирайте **Write** для доказового образу. Для образів GPT команда `sgdisk --verify disk.img` перевіряє CRC і відповідність основного та резервного заголовків, але резервний заголовок може застаріти після зміни розділів, тому перед відновленням звірте межі кандидатів зі структурами файлової системи.<sup>[[9]](#references)[[10]](#references)[[4]](#references)</sup>

## Файлові системи

### Список файлових систем Windows

- **FAT12/16**: MSDOS, WIN95/98/NT/200
- **FAT32**: 95/2000/XP/2003/VISTA/7/8/10
- **ExFAT**: 2008/2012/2016/VISTA/7/8/10
- **NTFS**: XP/2003/2008/2012/VISTA/7/8/10
- **ReFS**: 2012/2016

### FAT

Файлова система **FAT (File Allocation Table)** побудована навколо свого ключового компонента — таблиці розміщення файлів, яка розташована на початку тому. Зазвичай том містить **дві копії FAT**, хоча BPB допускає одну. У FAT12/16 кореневий каталог розташовано у фіксованій області; FAT32 зберігає його в області даних у кластері, номер якого вказано в `BPB_RootClus`.<sup>[[7]](#references)</sup>

Одиницею розміщення є **кластер**: `BPB_BytsPerSec × BPB_SecPerClus`, і він не обов’язково дорівнює 512 байтам. Тип FAT визначається кількістю кластерів даних, а не рядком версії в завантажувальному секторі. Межі кількості кластерів такі:<sup>[[7]](#references)</sup>

- **FAT12**: менше ніж 4,085 кластерів даних.
- **FAT16**: від 4,085 до 65,524 кластерів даних.
- **FAT32**: щонайменше 65,525 кластерів даних; для номера кластера використовуються лише 28 біт кожного 32-бітового запису FAT.

32-бітове поле розміру файлу обмежує розмір звичайного файлу **2³²−1 байтами** (трохи менше за 4 ГіБ).<sup>[[7]](#references)</sup>

Ключові компоненти кореневого каталогу, зокрема у FAT12 та FAT16:

- **Назва файлу/папки** (до 8 символів)
- **Атрибути**
- **Дати створення, зміни та останнього доступу**
- **Адреса таблиці FAT** (вказує на початковий кластер файлу)
- **Розмір файлу**

### EXT

**Ext2** — найпоширеніша файлова система для розділів **без журналювання** (**розділів, які мало змінюються**), наприклад завантажувального розділу. **Ext3/4** підтримують **журналювання** і зазвичай використовуються для **решти розділів**.

## **Метадані**

Деякі файли містять метадані. Ця інформація стосується вмісту файлу й іноді може зацікавити аналітика, оскільки залежно від типу файлу може містити:

- Назву
- Версію MS Office
- Автора
- Дати створення та останньої зміни
- Модель камери
- GPS-координати
- Інформацію про зображення

Щоб отримати метадані файлу, можна скористатися такими інструментами, як [**exiftool**](https://exiftool.org) і [**Metadiver**](https://www.easymetadata.com/metadiver-2/).

## **Відновлення видалених файлів**

### Записи про видалені файли

Як згадувалося раніше, після «видалення» файл може залишатися збереженим у кількох місцях. Зазвичай видалення файлу з файлової системи лише позначає його як видалений, але не зачіпає дані. Тому можна перевірити записи файлів (наприклад, MFT) і знайти видалені файли.<sup>[[2]](#references)</sup>

Крім того, ОС зазвичай зберігає багато інформації про зміни файлової системи та резервні копії, тож її можна спробувати використати, щоб відновити файл або якомога більше інформації про нього.

### **File Carving**

**File carving** — це методика пошуку **файлів у масиві даних**. Є 3 основні способи роботи таких інструментів: **за заголовками та кінцевими маркерами типів файлів**, за **структурами** типів файлів і за самим **вмістом**.

Простий пошук за заголовком і кінцевим маркером передбачає, що блоки розташовані послідовно, тому, якщо файл фрагментований, можна отримати лише його частину. Це не абсолютне обмеження: у PhotoRec є ресурсоємна опція **Paranoid → bruteforce** для деяких фрагментованих JPEG-файлів, а розумне для формату повторне збирання фрагментів може відновити й інші підтримувані типи. Поточний процес повторного збирання фрагментів описано в розділі [file carving and recovery tools](file-data-carving-recovery-tools.md#scalpel3-fragmented-carving).<sup>[[8]](#references)</sup>

Для File Carving можна використовувати різні інструменти, вказавши типи файлів, які потрібно шукати

### **Карвінг потоків даних**

Карвінг потоків даних подібний до File Carving, але **замість пошуку цілих файлів шукає цікаві фрагменти інформації**.\
Наприклад, замість пошуку цілого файлу із записаними URL-адресами ця методика шукатиме URL-адреси.

### Безпечне видалення

Очевидно, існують способи **«безпечно» видалити файли та частину записів про них**. Наприклад, можна кілька разів **перезаписати вміст** файлу випадковими даними, потім **видалити** записи про файл із **$MFT** і **$LOGFILE**, а також **видалити тіньові копії тому**.<sup>[[3]](#references)</sup>\
Можна помітити, що навіть після цього **в інших місцях можуть залишитися записи про існування файлу**. Це справді так, і частина роботи фахівця з цифрової криміналістики — знаходити їх.
