## Заблокований пристрій

Надавайте перевагу методам отримання даних, які зберігають стан пристрою, і документуйте кожну дію. Якщо пристрій заблокований, доступні варіанти залежать від моделі, версії Android, рівня виправлень безпеки та того, чи було налаштовано доступ до вилучення пристрою. NIST рекомендує обирати метод відповідно до пристрою та повноважень на проведення експертизи.<sup>[[1]](#references)</sup>

- Перевірте, чи було ввімкнено USB debugging і чи робоча станція для отримання даних уже авторизована. Для доступу через ADB зазвичай потрібно розблокувати пристрій і підтвердити RSA-ключ робочої станції.<sup>[[3]](#references)</sup>
- З’ясуйте, чи доступний біометричний доступ відповідно до застосовних правових і процедурних норм.
- **Smudge attack** може допомогти визначити графічний ключ розблокування за слідами на екрані, хоча подальші дотики й очищення знижують надійність цього методу.<sup>[[2]](#references)</sup>
- Якщо авторизовані інструменти підтримують конкретний пристрій і збірку програмного забезпечення, вони можуть спробувати відновити або перебрати PIN-код, пароль чи графічний ключ. Перевірка облікових даних апаратними засобами, затримки після невдалих спроб і політики стирання даних залежать від конкретного пристрою, тому не вважайте техніку чи результат для iPhone доказом підтримки Android-пристрою.<sup>[[1]](#references)</sup>

## Отримання даних

На старіших пристроях за допомогою застарілого [ADB backup](../../mobile-pentesting/android-app-pentesting/adb-commands.md#legacy-adb-backup) можна отримати файл `.backup`, який можна розпакувати за допомогою Android Backup Extractor:<sup>[[6]](#references)</sup>

```bash
java -jar abe.jar unpack file.backup file.tar
```

Не слід вважати, що це охоплює всі застосунки. ADB позначає цю команду як застарілу, а Android 12 не включає дані застосунків, орієнтованих на API level 31 або новішу версію, якщо застосунок не є налагоджуваним.<sup>[[4]](#references)</sup>

### Root або фізичний debug-доступ

Маючи root-доступ до пристрою, що працює, спершу проінвентаризуйте розділи та точки монтування; наведені нижче команди не призначені для безпосереднього застосування під час фізичного отримання даних через JTAG. Правильний блоковий пристрій залежить від апаратного забезпечення, тому не слід вважати, що це завжди `mmcblk0`. Створюйте образ лише з перевіреного джерела на окремий носій:<sup>[[1]](#references)</sup>

Для отримання даних через JTAG використовують апаратний інтерфейс тестового доступу пристрою та сумісне обладнання, щоб зчитати доступну пам’ять. Розташування контактів, підтримка чипсета, стан пристрою та розрізнення між енергозалежними й енергонезалежними об’єктами залежать від конкретного пристрою; задокументуйте апаратний шлях і дотримуйтеся перевіреної процедури для цієї моделі.<sup>[[1]](#references)</sup>

```bash
cat /proc/partitions
df /data
dd if=/dev/block/<verified-device> of=/sdcard/device.img bs=4096
```

Наприклад, якщо перелік розділів підтверджує, що `/dev/block/mmcblk0` — це весь флеш-пристрій, а в місці призначення достатньо вільного простору, початкова команда отримання образу буде такою:<sup>[[1]](#references)</sup>

```bash
dd if=/dev/block/mmcblk0 of=/sdcard/blk0.img bs=4096
```

Тут `df /data` допомагає співвіднести `/data` з її змонтованою файловою системою; це не слід вважати доказом того, що `mmcblk0` є правильним джерелом усього пристрою або що `4096` — єдиний допустимий розмір блока для `dd`.

Обчисліть хеш результату та зафіксуйте точну команду, ідентифікатори пристроїв, час і будь-які зміни, внесені під час отримання образу.<sup>[[1]](#references)</sup>

### Пам’ять

LiME може отримувати образ фізичної пам’яті Linux і деяких пристроїв Android, але його kernel module потрібно зібрати для цільового ядра та завантажити з достатніми привілеями. Підписування модулів, блокування ядра та сучасні засоби захисту Android можуть перешкодити його завантаженню.<sup>[[5]](#references)</sup>

Робочий процес проєкту для Android передбачає передавання відповідного модуля за допомогою ADB, перенаправлення TCP-порту, завантаження модуля з root shell і захоплення потоку на хості для дослідження:<sup>[[5]](#references)</sup>

```bash
adb push lime.ko /sdcard/lime.ko
adb forward tcp:4444 tcp:4444
adb shell
su
insmod /sdcard/lime.ko "path=tcp:4444 format=lime"
```

```bash
nc localhost 4444 > ram.lime
```

LiME може натомість записати дані у сховище пристрою, використавши `path=/sdcard/ram.lime`, але це змінить сховище пристрою й потребує достатньо вільного місця. Зафіксуйте цей побічний ефект і обчисліть хеш отриманого образу.<sup>[[1]](#references)</sup><sup>[[5]](#references)</sup>
