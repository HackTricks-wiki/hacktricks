# Атаки через side-channel підтверджень доставки в E2EE-месенджерах

{{#include ../banners/hacktricks-training.md}}

Підтвердження доставки обов’язкові в сучасних end-to-end encrypted (E2EE) месенджерах, оскільки клієнтам потрібно знати, коли ciphertext було розшифровано, щоб відкинути стан ratcheting і ephemeral keys. Сервер пересилає непрозорі blobs, тому пристрій одержувача надсилає підтвердження (подвійні галочки) після успішного розшифрування. Вимірювання round-trip time (RTT) між дією, ініційованою атакувальником, і відповідним підтвердженням доставки відкриває високоточний часовий канал, який leak-ить стан пристрою та присутність онлайн і може використовуватися для прихованого DoS. У розгортаннях із кількома пристроями та «client-fanout» витік посилюється, оскільки кожен зареєстрований пристрій розшифровує пробу й надсилає власне підтвердження.<sup>[[1]](#references)</sup>

## Джерела підтверджень доставки та сигнали, видимі користувачеві

Вибирайте типи повідомлень, які завжди надсилають підтвердження доставки, але не створюють видимих у UI артефактів на пристрої жертви. У таблиці нижче підсумовано емпірично підтверджену поведінку:<sup>[[1]](#references)</sup>

| Месенджер | Дія | Підтвердження доставки | Сповіщення жертви | Примітки |
|-----------|--------|------------------|---------------------|-------|
| **WhatsApp** | Текстове повідомлення | ● | ● | Завжди помітне → корисне лише для початкового визначення стану. |
| | Реакція | ● | ◐ (лише у відповідь на повідомлення жертви) | Власні реакції та їх видалення залишаються непомітними. |
| | Редагування | ● | Залежить від платформи: silent push | Вікно редагування ≈20 хв; підтвердження надсилається й після його завершення. |
| | Видалення для всіх | ● | ○ | UI дозволяє це протягом ~60 год, але пізніші пакети все одно підтверджуються. |
| **Signal** | Текстове повідомлення | ● | ● | Ті самі обмеження, що й у WhatsApp. |
| | Реакція | ● | ◐ | Власні реакції невидимі для жертви. |
| | Редагування/видалення | ● | ○ | Сервер встановлює обмеження у ~48 год і дозволяє до 10 редагувань, але пізні пакети все одно підтверджуються. |
| **Threema** | Текстове повідомлення | ● | ● | Підтвердження з кількох пристроїв агрегуються, тож для однієї проби видно лише один RTT. |

Умовні позначення: ● = завжди, ◐ = за певних умов, ○ = ніколи. Поведінку UI, що залежить від платформи, зазначено в примітках. За потреби вимкніть підтвердження прочитання, але підтвердження доставки у WhatsApp або Signal вимкнути не можна.<sup>[[1]](#references)</sup>

## Цілі та моделі атакувальника

* **G1 – Відбиток пристрою:** Підраховувати кількість підтверджень для кожної проби, кластеризувати RTT, щоб визначити ОС/клієнт (Android, iOS чи desktop), і відстежувати переходи між онлайн- та офлайн-станом.
* **G2 – Моніторинг поведінки:** Розглядати високочастотний ряд RTT (≈1 Гц є стабільним) як часовий ряд і визначати, чи ввімкнено екран, чи відкрито застосунок на передньому плані, години поїздок на роботу та робочі години тощо.
* **G3 – Виснаження ресурсів:** Не давати радіомодулям/CPU кожного пристрою жертви переходити в режим сну, надсилаючи безперервні безшумні проби, розряджаючи батарею, витрачаючи трафік і погіршуючи якість відеодзвінків.<sup>[[1]](#references)</sup>

Для опису поверхні зловживань достатньо двох типів зловмисників:<sup>[[1]](#references)</sup>

1. **Неприємний контакт:** уже має спільний чат із жертвою і зловживає власними реакціями, їх видаленням або повторними редагуваннями/видаленнями, прив’язаними до наявних ID повідомлень.
2. **Підозрілий незнайомець:** реєструє одноразовий обліковий запис і надсилає реакції з посиланнями на ID повідомлень, яких ніколи не було в локальній розмові; WhatsApp і Signal усе одно розшифровують їх і надсилають підтвердження, хоча UI відкидає зміну стану, тож попередня розмова не потрібна.

## Інструменти для доступу до raw-протоколу

Використовуйте клієнти, які надають достатній доступ до базового протоколу E2EE, щоб створювати підтримувані пакети поза обмеженнями UI та журналювати точні часові мітки; для довільних ID повідомлень потрібно перевіряти кожну реалізацію:

* **WhatsApp:** [whatsmeow](https://github.com/tulir/whatsmeow) (Go, API WhatsApp Web для кількох пристроїв) документує надсилання й отримання підтверджень доставки; [Cobalt](https://github.com/Auties00/Cobalt) (неофіційний Java/Kotlin API для Web і мобільних пристроїв) документує операції з повідомленнями, як-от реакції, редагування та видалення. Користуйтеся документованими API, а не припускайте, що доступний кожен внутрішній frame.<sup>[[3]](#references)[[4]](#references)</sup>
* **Signal:** [signal-cli](https://github.com/AsamK/signal-cli) надає інтерфейси CLI, JSON-RPC і D-Bus, а [libsignal-service-java](https://github.com/signalapp/libsignal-service-java) — це Java-бібліотека для взаємодії із Signal.<sup>[[5]](#references)[[7]](#references)</sup> У поточному синтаксисі `signal-cli` використовується `sendReaction RECIPIENT --target-author --target-timestamp`; не зупиняйте `receive` або `daemon`, щоб протокольні оновлення й надалі оброблялися.<sup>[[6]](#references)</sup> Приклад перемикання власної реакції:
  ```bash
  signal-cli -a +12025550100 sendReaction +12025550123 --target-author +12025550100 \
      --target-timestamp 1712345678901 --emoji "👍"
  signal-cli -a +12025550100 sendReaction +12025550123 --target-author +12025550100 \
      --target-timestamp 1712345678901 --remove
  ```
* **Threema:** Вимірювання, описані в статті Careless Whisper, показали, що квитанції про доставку синхронізуються між пристроями, тому навіть у конфігурації з кількома пристроями надсилається лише одна квитанція на повідомлення.<sup>[[1]](#references)</sup>
* **Готові PoC:** [device-activity-tracker](https://github.com/gommzystudio/device-activity-tracker) містить бекенди WhatsApp/Signal, за замовчуванням використовує непомітні проби видалення та розрізняє `active` і `standby` за ковзним медіанним порогом (`RTT < 0.9 * median`).<sup>[[8]](#references)</sup> [careless-whisper-python](https://github.com/ctrlsam/careless-whisper-python) — легший CLI, орієнтований насамперед на WhatsApp, із параметрами `--delay`, `--concurrent`, експортерами CSV/Prometheus і виводом, зручним для Grafana.<sup>[[9]](#references)</sup> Використовуйте обидва інструменти радше для розвідки, а не як довідники з протоколів; головне — побачити, як мало коду потрібно, якщо вже є доступ до клієнта на низькому рівні.

Коли власні інструменти недоступні, офіційні клієнти або інструменти розробника браузера все одно можуть запускати непомітні дії та розкривати часові характеристики зашифрованого трафіку; raw API усувають затримки інтерфейсу та дають змогу надсилати некоректні операції.<sup>[[1]](#references)</sup>

## Моторошний компаньйон: цикл непомітного збирання даних

1. Виберіть будь-яке давнє повідомлення, яке ви написали в чаті, щоб жертва не бачила, як змінюються бульбашки «реакцій».
2. Чергуйте видимий емодзі з порожнім payload реакції (у WhatsApp protobufs він кодується як `""`, а в signal-cli — як `--remove`). Кожне надсилання дає ACK від пристрою, хоча в інтерфейсі жертви нічого не змінюється.
3. Фіксуйте час надсилання та час отримання кожної квитанції про доставку. Цикл із частотою 1 Hz, як наведений нижче, дає змогу безперервно збирати RTT-траси для кожного пристрою:
   ```python
   while True:
       send_reaction(msg_id, "👍")
       log_receipts()
       send_reaction(msg_id, "")  # removal
       log_receipts()
       time.sleep(0.5)
   ```
4. Оскільки WhatsApp/Signal приймають необмежену кількість оновлень реакцій, зловмиснику ніколи не потрібно публікувати новий вміст чату чи зважати на часові обмеження редагування.<sup>[[1]](#references)</sup>

## Моторошний незнайомець: зондування довільних номерів телефону

1. Зареєструйте новий обліковий запис WhatsApp/Signal і отримайте відкриті ключі ідентичності для номера цілі (це автоматично виконується під час налаштування сеансу).
2. Створіть пакет реакції, що посилається на випадковий `message_id`, якого жодна зі сторін раніше не бачила; у статті повідомляється, що WhatsApp і Signal приймають такі реакції та все одно генерують квитанції доставки.<sup>[[1]](#references)</sup>
3. Надішліть пакет, навіть якщо гілки чату не існує. Пристрої жертви розшифровують його, не знаходять відповідне базове повідомлення, відкидають зміну стану, але все одно підтверджують отримання зашифрованого тексту, надсилаючи зловмиснику квитанції пристрою.
4. Безперервно повторюйте це, щоб зібрати серії RTT без попередньої розмови чи видимих сповіщень.<sup>[[1]](#references)</sup>

Якщо спершу потрібно з’ясувати, які номери зареєстровані, або попередньо зібрати інвентар пристроїв у великому масштабі, поєднайте це з [контакт-діскавері / оракулами реєстрації](../pentesting-web/registration-vulnerabilities.md), а не перебирайте навмання діапазони E.164 вручну.

Опубліковані дослідження контакт-діскавері показали практичну важливість цього підходу: використовуючи точні таблиці телефонних префіксів і помірні ресурси, дослідники змогли перевірити приблизно `10%` мобільних номерів США у WhatsApp і `100%` у Signal, перш ніж перейти до цільового зондування.<sup>[[11]](#references)</sup> На практиці попередня фільтрація активних облікових записів дає змогу зосередити бюджет безшумних зондів на номерах, які справді розшифрують пакети.

У нещодавніх версіях WhatsApp також з’явився пункт `Settings -> Privacy -> Advanced -> Block unknown account messages`.<sup>[[10]](#references)</sup> Вважайте його обмежувачем пропускної здатності: у документації трекера зазначено, що WhatsApp блокує велику кількість повідомлень від невідомих облікових записів, але поріг не розкривається, тож це не повністю запобігає реакціям на зонди.<sup>[[8]](#references)</sup>

## Повторне використання редагувань і видалень як прихованих тригерів

* **Повторні видалення:** після того як повідомлення один раз видалено для всіх, наступні пакети видалення з тим самим `message_id` не впливають на інтерфейс, але кожен пристрій усе одно розшифровує їх і надсилає підтвердження.
* **Операції поза часовим вікном:** у WhatsApp інтерфейс обмежує видалення приблизно 60 годинами, а редагування — приблизно 20 хвилинами; у Signal — приблизно 48 годинами. Створені протокольні повідомлення, надіслані після закінчення цих вікон, непомітно ігноруються на пристрої жертви, але квитанції все одно надсилаються, тож зловмисники можуть зондувати пристрій необмежено довго після завершення розмови.
* **Некоректні дані:** у статті повідомляється, що для некоректних повідомлень теж може надсилатися підтвердження; точна поведінка для некоректних тіл повідомлень або видалених ідентифікаторів залежить від реалізації, тож перевірте її, перш ніж покладатися на це.<sup>[[1]](#references)</sup>

## Посилення сигналу через кілька пристроїв і фингерпринтинг

* У WhatsApp і Signal кожен підключений пристрій (телефон, настільний застосунок, браузерний компаньйон) незалежно розшифровує зонд і повертає власне підтвердження. Підрахунок квитанцій для кожного зонду показує точну кількість пристроїв.<sup>[[1]](#references)</sup>
* Якщо пристрій не в мережі, його квитанція ставиться в чергу й надсилається після відновлення з’єднання. Тож проміжки в даних leak цикли активності та бездіяльності й навіть графік поїздок на роботу (наприклад, квитанції з настільного пристрою припиняють надходити під час подорожі).
* Розподіли RTT відрізняються залежно від платформи й середовища, оскільки на час впливають ОС, модель, клієнт і мережеві умови. Кластеризуйте RTT (наприклад, за допомогою k-means на ознаках медіани/дисперсії), щоб визначити тип пристрою: «телефон Android», «телефон iOS», «настільний Electron» тощо.
* Оскільки перед шифруванням відправник має отримати інвентар ключів одержувача, зловмисник також може відстежувати підключення нових пристроїв; раптове збільшення кількості пристроїв або поява нового кластера RTT є вагомою ознакою.<sup>[[1]](#references)</sup>

**Фингерпринтинг за відкладеними квитанціями:** надішліть кілька зондів з різними ідентифікаторами повідомлень, поки пристрій цілі не в мережі. Коли він знову підключиться, зіставте ідентифікатори в повернутих квитанціях доставки та перевірте, чи надійшли вони окремо або були об’єднані в одну квитанцію, і чи зберегли об’єднані ідентифікатори порядок надсилання або були переставлені у зворотному порядку. У протестованих клієнтах WhatsApp для Android/iOS надсилав окремі квитанції доставки, тоді як Web, Windows і macOS об’єднували їх; macOS змінював порядок об’єднаних ідентифікаторів на зворотний. Signal Desktop об’єднував квитанції, на відміну від його мобільних клієнтів. Це дає змогу класифікувати клієнт, що відновлює з’єднання, навіть якщо розподіли RTT перекриваються. Не плутайте квитанції доставки з квитанціями прочитання — для них діють інші правила об’єднання.<sup>[[1]](#references)</sup>

Окремий зонд WhatsApp, що зчитує **повторне поповнення prekey на сервері** без доставки повідомлень, описано в матеріалі [Side Channel вичерпання та поповнення пакета Prekey](whatsapp-prekey-bundle-side-channel.md).

## Частота вимірювань, черги та об’єднані квитанції

* **Стійкість WhatsApp до сплесків:** опубліковані вимірювання показали, що WhatsApp приймав сплески безшумних реакцій із частотою до одного зонду кожні `50 ms` без помітного створення черг на сервері. Це зручно для коротких калібрувальних сплесків, швидкого підрахунку пристроїв або швидкого нарощування інтенсивності drain attack.
* **Довготривале створення черг у Signal:** Signal витримував короткі сплески, але починав створювати черги за тривалого надсилання кількох зондів за секунду. Для довготривалого моніторингу підтримуйте частоту близько `1 Hz` (або нижче), щоб кожна квитанція відображала поточний стан пристрою, а не спустошення черги.
* **Артефакти повторного підключення:** коли пристрій знову з’являється в мережі, деякі клієнти пакетно обробляють або швидко надсилають кілька відкладених квитанцій. Вважайте такі сплески квитанцій маркером зміни стану, а не незалежними зразками RTT, інакше ваша кластеризація або класифікатор `active` vs `idle` надмірно підлаштується під шум повторного підключення.<sup>[[1]](#references)</sup>

## Визначення поведінки за трасами RTT

1. Виконуйте вимірювання з частотою ≥1 Hz, щоб зафіксувати вплив планувальника ОС. Для WhatsApp на iOS RTT <1 s сильно корелює з увімкненим екраном/активним застосунком, а RTT >1 s — з вимкненим екраном/обмеженням роботи у фоновому режимі.
2. Створюйте прості класифікатори (на основі порогів або двокластерного k-means), які позначатимуть кожен RTT як «активний» або «неактивний». Об’єднуйте позначки в послідовності, щоб визначити час сну, поїздки на роботу, робочі години або періоди активності компаньйона на настільному пристрої.
3. Надсилайте одночасні зонди на кожен пристрій, щоб визначити, коли користувачі перемикаються з мобільного пристрою на настільний, коли компаньйони переходять в офлайн і чи обмежується швидкість застосунку push-сповіщеннями або постійним сокетом.
4. У реальних мережах не використовуйте один фіксований поріг `1 s`. Спершу виконайте короткий етап прогрівання для кожного пристрою та постійно оновлюйте базовий рівень (наприклад, PoC device-activity-tracker використовує `threshold = 0.9 * median RTT`), щоб коливання Wi-Fi/мобільного зв’язку не зруйнували роботу класифікатора.<sup>[[1]](#references)[[8]](#references)</sup>

## Визначення місцезнаходження за RTT доставки

Цей самий метод вимірювання часу можна використати для визначення місця перебування одержувача, а не лише його активності. У роботі `Hope of Delivery` показано, що навчання на розподілах RTT для відомих місць перебування одержувача дає змогу зловмиснику згодом визначати місце перебування жертви лише за підтвердженнями доставки:<sup>[[2]](#references)</sup>

* Створіть базовий профіль для тієї самої цілі, коли вона перебуває в кількох відомих місцях (удома, в офісі, на кампусі, у країні A чи країні B тощо).
* Для кожного місця зберіть багато звичайних RTT повідомлень і виділіть прості ознаки, наприклад медіану, дисперсію або перцентильні діапазони.
* Під час справжньої атаки порівнюйте нову серію зондів із навченими кластерами. У статті повідомляється, що часто можна розрізнити навіть місця в межах одного міста; точність у конфігурації з 3 місцями становила `>80%`.
* Найкраще це працює, коли зловмисник контролює середовище відправника та надсилає зонди за подібних мережевих умов, оскільки виміряний маршрут охоплює мережу доступу одержувача, затримку пробудження та інфраструктуру месенджера.<sup>[[2]](#references)</sup>

На відміну від описаних вище атак із безшумними реакціями, редагуваннями й видаленнями, для визначення місця перебування не потрібні недійсні ідентифікатори повідомлень або приховані пакети, що змінюють стан. Достатньо звичайних повідомлень із нормальними підтвердженнями доставки, тож компроміс полягає в меншій скритності, але ширшій застосовності в різних месенджерах.

## Приховане виснаження ресурсів

Оскільки кожен безшумний зонд потрібно розшифрувати й підтвердити, безперервне надсилання перемикань реакцій, некоректних редагувань або пакетів видалення для всіх створює DoS на рівні застосунку:<sup>[[1]](#references)</sup>

* Змушує радіомодем щосекунди передавати й отримувати дані → помітно розряджає батарею, особливо на телефонах у режимі очікування.
* Створює вхідний/вихідний трафік, що витрачає мобільний трафік і може заважати чутливим до затримок функціям, як-от відеодзвінкам.<sup>[[1]](#references)</sup>
* Великі некоректні дані збільшують обсяг обробки, але, згідно зі статтею, сама криптографія становить незначну частину витрат заряду батареї.<sup>[[1]](#references)</sup>
* У WhatsApp недійсні реакції можуть містити набагато більше даних, ніж можна очікувати від звичайного емодзі: опубліковані вимірювання виявили, що сервер приймав до приблизно `1 MB` на реакцію.
* Реакції завеликого розміру перестають надійно спричиняти квитанції доставки, коли тіло перевищує приблизно `30 bytes`, але перед відкиданням їх усе одно пересилають і обробляють. Для отримання ACK залишайте тіла реакцій дуже малими; збільшуйте їхній розмір лише тоді, коли мета — суто drain або приховане одностороннє передавання.
* Публічні вимірювання зафіксували приблизно `3.7 MB/s` (`~13.3 GB/h`) трафіку на пристрої жертви в цьому режимі.
