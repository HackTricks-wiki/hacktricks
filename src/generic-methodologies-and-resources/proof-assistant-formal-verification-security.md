# Ασφάλεια Βοηθών Αποδείξεων και Τυπικής Επαλήθευσης

{{#include ../banners/hacktricks-training.md}}

Οι proof assistants μπορούν να εκτελέσουν τον ίδιο όρο μέσω διαφόρων διαδρομών: μείωση από τον kernel, interpreter, παραγόμενο κώδικα, runtime primitives ή εξωτερικό checker. Μια απόδειξη είναι τόσο ισχυρή όσο κάθε στοιχείο που μπορεί να συνεισφέρει έμπιστα αποτελέσματα. Στο Lean, οι native decision procedures ανταλλάσσουν ταχύτερη αξιολόγηση με μεγαλύτερη trusted computing base (TCB): ο compiler και οι ορισμοί με native implementations καθίστανται σημαντικοί για την ακεραιότητα των αποδείξεων.<sup>[[3]](#references)</sup>

## Διαφορική αξιολόγηση λογικής/native υλοποίησης

Δώστε προτεραιότητα σε primitives των οποίων η εκτελέσιμη υλοποίηση διαφέρει από το λογικό μοντέλο τους (για παράδειγμα, compiler intrinsics, foreign-function interfaces, runtime overrides και ορισμοί με `@[implemented_by]`). Αξιολογήστε διαφορικά τον **ίδιο κλειστό όρο** μέσω των λογικών και compiled διαδρομών και αντιμετωπίστε οποιαδήποτε ασυμφωνία τιμής, εξαίρεσης ή τερματισμού ως εύρημα ασφαλείας.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

Χρήσιμες κατηγορίες οριακών τιμών περιλαμβάνουν:<sup>[[1]](#references)[[4]](#references)</sup>

- indexes γύρω από το `0`, το μήκος της εισόδου, το όριο της machine word και τιμές όπως `2^63` ή μεγαλύτερες·
- εύρη μηδενικού ή ενός byte, `start = end`, `start > end` και θέσεις πολύ πέρα από το αντικείμενο·
- κενές και μη κενές εισόδους, strings πολλών bytes, μη έγκυρα όρια και αριθμητικές πράξεις που ενδέχεται να περικοπούν κατά το compile·
- τιμές που δεσμεύονται στο heap, όταν ένα native primitive έχει συμπεριφορά ownership ή borrowing που απουσιάζει από το λογικό μοντέλο.

Το ακόλουθο απλοποιημένο μοτίβο Lean παρουσιάζει το ζήτημα που εντοπίστηκε στο `String.Pos.Raw.extract`: ο ευάλωτος native κώδικας επέστρεφε το αρχικό string για ένα τεράστιο εύρος ενός byte, ενώ η definitional reduction επέστρεφε το κενό string. Αυτή η σημασιολογική ασυμφωνία διορθώθηκε ξεχωριστά από το σχετικό ελάττωμα ασφάλειας μνήμης.<sup>[[1]](#references)[[2]](#references)[[4]](#references)</sup>

```lean
def value : String := "non-empty"
def startPos : String.Pos.Raw := ⟨2^63⟩
def endPos : String.Pos.Raw := ⟨2^63 + 1⟩

example : False := by
  have logical : String.Pos.Raw.extract value startPos endPos = "" := rfl
  have native : String.Pos.Raw.extract value startPos endPos = value := by
    native_decide
  exact (by decide) (logical.symm.trans native)
```

Αυτό το μοτίβο γενικεύεται πέρα από τις συμβολοσειρές: αν η λογική αξιολόγηση αποδεικνύει `E = A` και η έμπιστη native αξιολόγηση αποδεικνύει `E = B`, η μεταβατικότητα δίνει `A = B`. Όταν τα `A` και `B` διαφέρουν παρατηρήσιμα, αυτό οδηγεί σε `False`· το `False.elim` (η αρχή της έκρηξης) μπορεί στη συνέχεια να αποδείξει οποιαδήποτε πρόταση-στόχο. Ο kernel δεν χρειάζεται να έχει εσφαλμένο κανόνα αναγωγής — η ακεραιότητα παραβιάζεται επειδή ένα αποτέλεσμα βασισμένο σε compiler εισήλθε στη λογική μέσω αξιώματος.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

## Έλεγχος του διευρυμένου TCB στο Lean

Μη χρησιμοποιείτε τα σημάδια επιτυχίας του editor ή μια επιτυχημένη μεταγλώττιση ως μοναδική επικύρωση μιας μη έμπιστης απόδειξης. Εξετάστε το πλήρες σύνολο εξαρτήσεων κάθε κρίσιμου για την ασφάλεια θεωρήματος με το `#print axioms`· οι οδηγίες επικύρωσης του Lean προσδιορίζουν τα ονόματα `_native` ως εξαρτήσεις native αξιολόγησης, το `sorryAx` ως ελλιπή απόδειξη και άλλα μη τυπικά ονόματα ως προσαρμοσμένα αξιώματα.<sup>[[3]](#references)</sup>

```lean
#print axioms targetTheorem
```

Για παράδειγμα, μια παραγόμενη εξάρτηση που μοιάζει με την ακόλουθη σημαίνει ότι η μεταγλωττισμένη εκτέλεση συνέβαλε με ένα υποτιθέμενο αποτέλεσμα αντί για μια απόδειξη που προέκυψε αποκλειστικά μέσω αναγωγής του πυρήνα:<sup>[[1]](#references)[[4]](#references)</sup>

```text
targetTheorem._native.native_decide.ax_1_1
```

Κατά την ανασκόπηση του πηγαίου κώδικα, αναζητήστε εγγενείς διαδικασίες απόφασης και ρητές οδούς παράκαμψης, αλλά επιβεβαιώστε το αποτέλεσμα με το `#print axioms`, καθώς οι εξαρτήσεις μπορεί να είναι έμμεσες ή να δημιουργούνται αυτόματα:<sup>[[3]](#references)</sup>

```bash
rg -n 'native_decide|decide\s+\+native|bv_decide|sorry|axiom' .
```

Διακρίνετε τα επίπεδα κατά τη διαλογή ενός ευρήματος:<sup>[[3]](#references)</sup>

1. **Ακεραιότητα δήλωσης:** επαληθεύστε ότι η σημειογραφία, οι στιγμιότυπα type-class, οι εισαγωγές και οι ορισμοί εκφράζουν τον επιδιωκόμενο ισχυρισμό.
2. **Εξαρτήσεις απόδειξης:** απορρίψτε ή ελέγξτε ρητά μη αναμενόμενα αξιώματα, ειδικά αξιώματα που δημιουργούνται από native evaluation.
3. **Επαναεκτέλεση από τον kernel:** μετά το `lake build`, εκτελέστε το `lean4checker --fresh <Module>` για να επαναληφθούν οι δηλώσεις από τα αρχεία `.olean`.
4. **Επικύρωση εχθρικών αποδείξεων:** δημιουργήστε μη έμπιστο κώδικα σε sandbox και χρησιμοποιήστε το `lake comparator` με εξωτερικούς ελεγκτές, σε σχέση με μια έμπιστη δήλωση-πρόκληση.

Το `lean4checker` παρέχει χρήσιμη άμυνα σε βάθος, αλλά εμπιστεύεται τη δομική ορθότητα των αρχείων `.olean`, ενώ η εκτέλεση μη έμπιστου Lean meta-code μπορεί από μόνη της να θέσει σε κίνδυνο το περιβάλλον ελέγχου. Για αποδείξεις υψηλού κινδύνου, το comparator εξάγει την απόδειξη εκτός του sandbox, ελέγχει τη δήλωση σε σχέση με την έμπιστη πρόκληση και μπορεί να την επαναλάβει μέσω ελεγκτών που έχουν υλοποιηθεί ανεξάρτητα· η ποικιλομορφία υλοποιήσεων μειώνει την πιθανότητα ένα ελάττωμα στον ίδιο compiler, runtime ή kernel να επικυρώσει το ίδιο ψευδές αποτέλεσμα παντού.<sup>[[3]](#references)</sup>
