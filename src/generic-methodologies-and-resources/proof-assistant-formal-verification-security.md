# Безпека помічників доведення та формальної верифікації

{{#include ../banners/hacktricks-training.md}}

Помічники доведення можуть виконувати той самий терм кількома шляхами: редукцією ядра, інтерпретатором, згенерованим кодом, примітивами середовища виконання або зовнішнім перевірником. Доведення настільки надійне, наскільки надійний кожен компонент, якому дозволено надавати довірені результати. У Lean нативні процедури прийняття рішень обмінюють швидше обчислення на більшу довірену обчислювальну базу (TCB): компілятор і визначення з нативними реалізаціями стають важливими для цілісності доведення.<sup>[[3]](#references)</sup>

## Диференційне обчислення в логічному та нативному режимах

Насамперед перевіряйте примітиви, виконувана реалізація яких відрізняється від їхньої логічної моделі (наприклад, compiler intrinsics, інтерфейси до зовнішніх функцій, перевизначення середовища виконання та визначення з позначкою `@[implemented_by]`). Виконуйте диференційне обчислення **того самого замкненого терма** логічним і компільованим шляхами та вважайте будь-яку невідповідність значень, винятків або завершення виконання знахідкою безпеки.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

Корисні класи граничних значень:<sup>[[1]](#references)[[4]](#references)</sup>

- індекси поблизу `0`, довжини вхідних даних, межі машинного слова, а також значення на кшталт `2^63` або більші;
- діапазони нульової чи однобайтової довжини, `start = end`, `start > end` і позиції, що значно виходять за межі об’єкта;
- порожні й непорожні вхідні дані, багатобайтові рядки, недопустимі межі та арифметика, яка може обрізатися під час компіляції;
- значення, розміщені в купі, якщо нативний примітив має поведінку володіння або позичання, відсутню в логічній моделі.

Наведений нижче скорочений шаблон Lean демонструє проблему, виявлену в `String.Pos.Raw.extract`: вразливий нативний код повертав початковий рядок для надзвичайно великого однобайтового діапазону, тоді як редукція за визначенням повертала порожній рядок. Цю семантичну невідповідність виправили окремо від пов’язаної з нею вади безпеки пам’яті.<sup>[[1]](#references)[[2]](#references)[[4]](#references)</sup>

```lean
def value : String := "non-empty"
def startPos : String.Pos.Raw := ⟨2^63⟩
def endPos : String.Pos.Raw := ⟨2^63 + 1⟩

example : False := by
  have logical : String.Pos.Raw.extract value startPos endPos = "" := rfl
  have native : String.Pos.Raw.extract value startPos endPos = value := by
    native_decide
  exact (by decide) (logical.symm.trans native)
```

Цей шаблон узагальнюється не лише на рядки: якщо логічне обчислення доводить `E = A`, а довірене нативне обчислення доводить `E = B`, транзитивність дає `A = B`. Коли `A` і `B` помітно відрізняються, це дає `False`; тоді `False.elim` (принцип вибуху) може довести будь-яке цільове твердження. Ядро не мусить мати хибне правило редукції — порушення цілісності виникає через те, що результат, отриманий компілятором, потрапив до логіки через аксіому.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

## Аудит розширеного TCB у Lean

Не покладайтеся лише на позначки в редакторі чи успішну збірку під час перевірки недовіреного доведення. Перевіряйте повне замикання залежностей кожної критично важливої для безпеки теореми за допомогою `#print axioms`; рекомендації Lean щодо перевірки вказують, що назви `_native` позначають залежності від нативного обчислення, `sorryAx` — незавершене доведення, а інші нестандартні назви — користувацькі аксіоми.<sup>[[3]](#references)</sup>

```lean
#print axioms targetTheorem
```

Наприклад, згенерована залежність на кшталт наведеної нижче означає, що виконання скомпільованого коду внесло припущений результат, а не доведення, отримане виключно шляхом редукції ядра:<sup>[[1]](#references)[[4]](#references)</sup>

```text
targetTheorem._native.native_decide.ax_1_1
```

Під час перегляду вихідного коду шукайте нативні процедури прийняття рішень і явні механізми обходу, але перевіряйте результат за допомогою `#print axioms`, оскільки залежності можуть бути непрямими або згенерованими:<sup>[[3]](#references)</sup>

```bash
rg -n 'native_decide|decide\s+\+native|bv_decide|sorry|axiom' .
```

Розрізняйте рівні під час аналізу знахідки:<sup>[[3]](#references)</sup>

1. **Цілісність твердження:** перевірте, що нотація, екземпляри класів типів, імпорти й визначення виражають задумане твердження.
2. **Залежності доказу:** відхиляйте неочікувані аксіоми або явно перевіряйте їх, особливо згенеровані аксіоми native-evaluation.
3. **Повторне відтворення ядром:** після `lake build` запустіть `lean4checker --fresh <Module>`, щоб повторно відтворити оголошення з файлів `.olean`.
4. **Перевірка ворожого доказу:** збирайте недовірений код у sandbox і використовуйте `lake comparator` із зовнішніми перевіряльниками для перевірки твердження щодо довіреного завдання.

`lean4checker` забезпечує корисний додатковий рівень захисту, але довіряє структурній коректності файлів `.olean`, а запуск недовіреного Lean meta-code сам по собі може скомпрометувати середовище перевірки. Для доказів високого ризику comparator експортує доказ за межі sandbox, звіряє твердження з довіреним завданням і може відтворити доказ за допомогою незалежно реалізованих перевіряльників; різноманітність реалізацій зменшує ймовірність того, що один і той самий хибний результат буде прийнятий усюди через дефект компілятора, середовища виконання або ядра.<sup>[[3]](#references)</sup>
