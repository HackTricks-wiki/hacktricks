## Mutational Grammar Fuzzing: coverage проти семантики

У **mutational grammar fuzzing** вхідні дані мутуються, залишаючись **валідними щодо граматики**. У режимі coverage-guided як corpus seeds зберігаються лише зразки, що забезпечують **нове coverage**. Для **мовних цілей** (парсерів, інтерпретаторів, рушіїв) це може не виявити баги, для яких потрібні **ланцюжки семантичного потоку даних**, де вихід одного конструкта стає входом для іншого.<sup>[[1]](#references)</sup>

**Сценарій збою:** fuzzer знаходить seeds, які окремо використовують `document()` і `generate-id()` (або подібні примітиви), але **не зберігає ланцюжок потоку даних**, тому зразок, «ближчий до бага», відкидається, бо не додає coverage. За наявності **3+ залежних кроків** випадкова рекомбінація стає затратною, а зворотний зв’язок від coverage не допомагає пошуку.<sup>[[1]](#references)</sup>

**Висновок:** для граматик із великою кількістю залежностей варто **поєднувати mutational і generative фази** або надавати перевагу шаблонам **ланцюжків функцій** (а не лише coverage).<sup>[[1]](#references)</sup>

## Підводні камені різноманітності corpus

Coverage-guided мутація **жадібна**: зразок із новим coverage одразу зберігається, часто з великими незміненими ділянками. З часом corpus перетворюються на **майже дублікати** з низькою структурною різноманітністю. Надмірна мінімізація може видалити корисний контекст, тому практичний компроміс — **мінімізація з урахуванням граматики**, яка **зупиняється після досягнення мінімального порогу токенів** (усуває зайве, зберігаючи достатньо навколишньої структури для зручної мутації).<sup>[[1]](#references)</sup>

Практичне правило для corpus у mutational fuzzing: **віддавайте перевагу невеликому набору структурно відмінних seeds, що максимізують coverage**, а не великій купі майже дублікатів. Зазвичай це означає таке.<sup>[[1]](#references)[[3]](#references)</sup>

- Починайте з **зразків із реального світу** (публічних corpus, результатів crawling, перехопленого трафіку, наборів файлів з екосистеми цілі).
- Скорочуйте їх за допомогою **мінімізації corpus на основі coverage**, а не зберігайте кожен валідний зразок.
- Зберігайте seeds **достатньо малими**, щоб мутації припадали на значущі поля, а не витрачали більшість циклів на несуттєві байти.
- Повторно мінімізуйте corpus після значних змін harness або instrumentation, адже «найкращий» corpus змінюється разом зі змінами досяжності.

## Мутація з урахуванням порівнянь для magic values

Часто fuzzers упираються в стелю не через синтаксис, а через **жорсткі порівняння**: magic bytes, перевірки довжини, рядки enum, контрольні суми або значення диспетчеризації парсера, захищені через `memcmp`, таблиці switch або послідовні порівняння. За суто випадкової мутації даремно витрачаються цикли на вгадування цих значень побайтно.

Для таких цілей використовуйте **трасування порівнянь** (наприклад, `CMPLOG` у AFL++ або робочі процеси на кшталт Redqueen), щоб fuzzer міг спостерігати операнди невдалих порівнянь і спрямовувати мутації на значення, які їх задовольняють.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Практичні нотатки:**

- Це особливо корисно, коли ціль приховує складну логіку за **сигнатурами файлів**, **дієсловами протоколу**, **тегами типів** або **бітами функцій, залежними від версії**.
- Поєднуйте це зі **словниками**, зібраними з реальних зразків, специфікацій протоколів або журналів налагодження. Невеликий словник із токенами граматики, назвами чанків, дієсловами й роздільниками часто цінніший за величезний універсальний список слів.
- Якщо ціль виконує багато послідовних перевірок, спочатку пройдіть найперші перевірки «магічних» значень, а потім знову мінімізуйте отриманий корпус, щоб наступні етапи починалися вже з коректних префіксів.

## Багатший зворотний зв’язок, коли покриття ребер не розрізняє різні шляхи

Звичайне покриття ребер не може розрізнити два виконання, які проходять через той самий допоміжний код із різними викликачами або обирають різні комбінації гілок усередині функції. Це важливо для спільних декодерів, диспетчерів протоколів і допоміжного коду інтерпретаторів, де **шлях** до ребра визначає поточний стан. Наївне відстеження кожного контексту виклику також небезпечне: карта покриття та черга можуть надмірно розростися. Тому дослідження fuzzing із урахуванням контексту рекомендують уточнювати лише перспективні контексти, а не враховувати весь граф викликів як контекстно-залежний.<sup>[[14]](#references)</sup>

У новіших збірках AFL++ доступне **покриття шляхів Ball-Larus для кожної функції** на додачу до звичайного покриття ребер. Воно призначає ознаку кожному ациклічному шляху через функцію; зворотні ребра циклів вилучаються, тож цей зворотний зв’язок розрізняє комбінації гілок, але **не кількість ітерацій циклу**. Почніть із м’якого рівня `1`, а суворіші режими застосовуйте лише до підозрілого коду парсерів і автоматів станів, оскільки кількість шляхів може зростати експоненційно.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Для допоміжної функції, яку викликають із багатьох важливих для безпеки місць, режим LTO може поєднати кожен шлях функції з безпосереднім місцем її виклику:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Рекомендації щодо кампанії:** обережно застосовуйте розширений зворотний зв’язок і стежте за його впливом на карту покриття та чергу.<sup>[[13]](#references)[[14]](#references)</sup>

- Паралельно запустіть звичайний екземпляр із покриттям ребер; розширений зворотний зв’язок корисний лише тоді, коли додаткові витрати на чергу й карту не знижують кількість виконань за секунду.
- Використовуйте `AFL_LLVM_ALLOWLIST`, щоб обмежити інструментування шляхів/викликів, якщо великі бібліотеки з великою кількістю шаблонів або універсальний службовий код переважають на карті.
- Функції з надмірною кількістю ациклічних шляхів можна пропускати за допомогою AFL++; попередження під час компіляції свідчать про те, що для цілі потрібен allowlisting або менш суворий рівень.
- Покриття викликів і шляхів підтримує лише один рівень вкладеності викликів. Не поєднуйте його з глибшими стеками контексту.
- Ідентифікатори шляхів можуть змінюватися між основними версіями LLVM. Під час кампанії не змінюйте toolchain і не синхронізуйте корпуси на основі PATH, наче їхні ідентифікатори ознак стабільні між збірками.
- Цей зворотний зв’язок доповнює `CMPLOG`: трасування порівнянь з’ясовує, **яке значення проходить перевірку**, а зворотний зв’язок щодо шляхів/викликів зберігає **який маршрут і комбінація гілок привели до неї**.

## Stateful fuzzing: послідовності — це seeds

Для **протоколів**, **автентифікованих робочих процесів** і **багатоетапних парсерів** цікавим об’єктом часто є не окремий blob, а **послідовність повідомлень**. Зазвичай неефективно об’єднувати всю розмову в один файл і безсистемно його мутувати, оскільки fuzzer однаково змінює кожен крок, навіть якщо лише пізніше повідомлення приводить до вразливого стану.<sup>[[4]](#references)</sup>

Ефективніший підхід — вважати **саму послідовність seed** і використовувати **спостережуваний стан** (коди відповідей, стани протоколу, етапи парсера, типи повернених об’єктів) як додатковий зворотний зв’язок.<sup>[[4]](#references)</sup>

- Залишайте **коректні префіксні повідомлення** незмінними й зосередьте мутації на повідомленні, що **визначає перехід**.
- Кешуйте ідентифікатори та значення, згенеровані сервером у попередніх відповідях, якщо від них залежить наступний крок.
- Віддавайте перевагу мутації/склеюванню окремих повідомлень, а не мутації всього серіалізованого transcript як непрозорого blob.
- Якщо протокол повертає значущі коди відповідей, використовуйте їх як **простий оракул стану**, щоб надавати пріоритет послідовностям, які просуваються далі.

Саме тому vanilla file-style fuzzing часто пропускає помилки автентифікації, приховані переходи або помилки парсера, які виникають «лише після handshake»: fuzzer має зберігати **порядок, стан і залежності**, а не лише структуру.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing драйвера з кількома клієнтами

Високе покриття ребер усе ще може пропустити помилки IPC-драйвера, оскільки покриття не описує **володіння об’єктами, лічильники посилань, очікувані повідомлення, порядок очищення чи чергування потоків**. На сторінці [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) описано модель об’єктів драйвера; у цьому прикладі йдеться про harness fuzzer. Android Binder — корисний приклад: недостатньо пройти шляхи виділення й звільнення, якщо fuzzer не може змусити кілька процесів працювати з одним об’єктом ядра в потрібному порядку.<sup>[[15]](#references)</sup>

#### Моделюйте протокол, а не окремі буфери `ioctl`

Представте тестовий випадок як упорядковану граматику з **ідентичності клієнта + операції + структурованих аргументів**. Fuzzer Binder LKL використовує protobuf і `libprotobuf-mutator`, з одним постійним клієнтом context manager і двома звичайними клієнтами. Семантичний harness зберігає зв’язки, які знищила б сліпа мутація байтів.<sup>[[15]](#references)</sup>

- Кешуйте значення, повернені попередніми операціями. Наприклад, `BC_FREE_BUFFER` має повторно використовувати вказівник на буфер транзакції, повернений попереднім `ioctl`.
- Генеруйте коректні відповіді за замовчуванням, щоб синхронні транзакції могли завершитися, а наступні операції залишалися доступними.
- Відхиляйте неможливі переходи, як-от транзакції самому собі або кілька очікуваних транзакцій для однієї цілі.
- Зберігайте стан одноразової ініціалізації поза скиданням для кожного вводу. Binder дозволяє лише одну реєстрацію `BINDER_SET_CONTEXT_MGR` за запуск системи, тож багаторазове знищення й повторне створення цього клієнта робитиме наступні вводи некоректними.

Корисний шаблон для гонки часу життя: змусити одного клієнта передати об’єкт, запустити очищення потоку або процесу й паралельно змусити клієнта-одержувача звільнити буфер транзакції. У прикладі CVE-2020-0423 передавання `BINDER_TYPE_WEAK_BINDER` з подальшим змаганням `BINDER_THREAD_EXIT` із `BC_FREE_BUFFER` могло звільнити вбудований `binder_work`, поки шлях очищення потоку, що завершувався, усе ще використовував його.<sup>[[15]](#references)</sup>

#### Повторно введіть контрольовані чергування в ядро в userspace

[Linux Kernel Library (LKL)](https://github.com/lkl/linux) підключає справжній код ядра до harness у userspace і надає доступ до його інтерфейсу системних викликів через `lkl_syscall`. Це спрощує узгодження protobuf-стану, покриття та KASAN в одному процесі. Однак зазвичай LKL виконує системний виклик без переривання іншим потоком ядра. Для кампаній із пошуку гонок додайте точки `schedule()` навколо вибраних меж блокування/розблокування та часу життя, а потім дозвольте harness випадково вибирати наступного клієнта під час кожної передачі керування. Розміщуйте ці точки вибірково, оскільки кожна з них збільшує простір пошуку розкладу. Описаний дослідниками рандомізований планувальник **не входить** до upstream fuzzer Binder.<sup>[[15]](#references)</sup>

#### Збирайте й відтворюйте серіалізовані regression seeds

Upstream harness фіксує сумісну версію `libprotobuf-mutator`, вмикає інструментування для fuzzing у LKL та KASAN за допомогою `LKL_FUZZING=1`, а також вмикає `CONFIG_MMU` для Binder за допомогою `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Після перевірки навмисно вразливої версії або застосування описаних вище патчів для відкату серіалізований seed може відтворити весь перехід стану кількох клієнтів, не відтворюючи його в саморобному proof of concept на C:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Сприймайте отриманий KASAN use-after-free як підтвердження того, що seed досяг вразливого шляху життєвого циклу. Це **не** свідчить про наявність подальших примітивів, потрібних для виконання коду в ядрі або підвищення привілеїв.<sup>[[16]](#references)</sup>

## Трюк із різноманітністю на одній машині (у стилі Jackalope)

Практичний спосіб поєднати **генеративну новизну** з **повторним використанням coverage** — запускати короткоживучі worker-процеси проти постійно запущеного сервера. Кожен worker починає з порожнього корпусу, синхронізується через `T` секунд, працює ще `T` секунд із об’єднаним корпусом, знову синхронізується, а потім завершує роботу. Так **кожне покоління отримує свіжі структури**, водночас використовуючи накопичений coverage.<sup>[[1]](#references)[[2]](#references)</sup>

**Сервер:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Послідовні worker (приклад циклу):**

<details>
<summary>Цикл перезапуску worker Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Примітки:**

- `-in empty` щоразу створює **новий corpus**.
- `-server_update_interval T` імітує **відкладену синхронізацію** (спочатку нові дані, потім повторне використання).
- У режимі grammar fuzzing **початкову синхронізацію із сервером типово пропущено** (параметр `-skip_initial_server_sync` не потрібен).
- Оптимальне значення `T` **залежить від цілі**; зазвичай найкраще перемикатися після того, як worker знайде більшість «простих» ділянок покриття.

## Snapshot Fuzzing для цілей, які складно підготувати до тестування

Якщо потрібний для тестування код стає доступним лише **після тривалого налаштування** (завантаження VM, завершення входу в систему, отримання пакета, розбір контейнера, ініціалізація служби), корисною альтернативою є **snapshot fuzzing**: збережіть стан готового процесу або VM, передайте кожен тестовий випадок у вхідний шлях цілі, виконуйте до збою/тайм-ауту, а потім відновіть snapshot. Це дає змогу не повторювати ініціалізацію чи префікси протоколу й корисно для **мережевих служб**, **firmware**, **поверхонь атаки після автентифікації** та **цілей, доступних лише у вигляді бінарних файлів**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Запустіть ціль, доки не буде досягнуто потрібного стану.
2. Зробіть snapshot **пам’яті та регістрів** у цей момент.
3. Для кожного тестового випадку безпосередньо запишіть змінений ввід у відповідний буфер гостьової системи/процесу.
4. Виконуйте до збою/тайм-ауту/скидання.
5. Відновіть snapshot; для цілей на VM відновлюйте лише **змінені сторінки**, якщо це підтримується, а потім повторюйте цикл.

Розмістіть snapshot якомога ближче до першого ресурсомісткого етапу розбору/диспетчеризації, наприклад після `recv`/`read` або етапу десеріалізації пакета, і зафіксуйте вхідний буфер, який використовує ціль. Це відповідає принципу адаптивного розміщення: переміщуйте snapshot глибше в обробку вводу, щоб не повторювати вже виконану роботу.<sup>[[11]](#references)</sup>

## Дослідження гонок у ядрі Linux за допомогою MAccConc

[MAccConc](https://github.com/googleprojectzero/MAccConc) перетворює чутливі до часу гонки в ядрі Linux на відтворювані розклади доступу до пам’яті. Він може автоматично перебирати виконання **A-B-A** у двох контекстах або дозволяти аналітику задавати обмеження порядку в термінальному UI/GUI. Це експериментальний інструмент для досліджень, а не повноцінний concurrency fuzzer: наразі для нього потрібні LLVM 23+ і пропатчене ядро проєкту, інструменти командного рядка підтримують два тестові потоки, а запропонований рівень fuzzing у userspace ще не реалізований.<sup>[[17]](#references)[[18]](#references)</sup>

### Збирання точок міжконтекстної взаємодії

Зберіть інструментоване ядро з callback-функціями KASAN outline та пропатченою підтримкою запису пам’яті KCOV. У README проєкту також рекомендовано вимкнути оптимізацію sibling-call, щоб стеки викликів залишалися придатними для використання.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

Режим outline у KASAN (`asan-instrumentation-with-call-threshold=0`) перетворює інструментовані доступи на виклики допоміжних функцій. Патчі ядра MAccConc вимикають `asan-opt-same-temp`, щоб послідовні доступи не об’єднувалися; також вимкніть оптимізацію `asan-opt-globals`, якщо потрібно виявляти гонки на глобальних змінних. KCOV передає отримані записи до userspace. Порівнюйте доступи з різних контекстів виконання та залишайте пари, діапазони байтів яких перекриваються і принаймні одна сторона яких виконує запис; моделюйте `kfree()` як запис, щоб переходи життєвого циклу також ставали кандидатами.<sup>[[17]](#references)</sup>

Для роботи, що виходить за межі завдання, яке її ініціювало, як-от обробка пакетів або RCU-callbacks, підсистема має передавати дескриптор віддаленого покриття KCOV. В upstream віддалений KCOV є opt-in і не доступний автоматично для довільної фонової роботи, тому відсутність такого передавання може зробити реальну взаємодію невидимою.<sup>[[17]](#references)[[19]](#references)</sup>

### Визначайте той самий динамічний доступ під час кожного запуску

Не відтворюйте сценарій із конкретною адресою heap, яка може змінитися після кожного виділення пам’яті, або лише з адресою інструкції, неоднозначною всередині допоміжних функцій, як-от `memcpy()` і `spin_lock()`. MAccConc використовує **трасування стека з лічильниками**: кожен кадр ідентифікує callee та кількість його викликів у межах caller, а останній елемент ідентифікує інструкцію доступу до пам’яті. Записи входу/виходу функцій SanitizerCoverage дають змогу userspace відтворити цей динамічний ідентифікатор, який залишається стабільним попри зміну адрес і сторонні шуми в потоці керування.<sup>[[17]](#references)</sup>

### Перетворюйте пари-кандидати на примусові розклади

Патчений ioctl `KCOV_SET_DI` пов’язує ідентифікатор доступу з лічильниками з дією над спільним прапорцем.<sup>[[17]](#references)</sup>

| Дія | Семантика |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Встановити прапорець *N* безпосередньо перед вибраним доступом. |
| `DI_STACK_WAIT` | Перед вибраним доступом очікувати в циклі, доки прапорець *N* не буде встановлено або не сплине заданий ліміт. |
| `DI_STACK_WAKE_POST` | Встановити прапорець *N* безпосередньо після вибраного доступу. |

Для часткової умови **A-happens-before-B** призначте `DI_STACK_WAKE_POST` для A і `DI_STACK_WAIT` для B, використовуючи той самий прапорець. Щоб повністю задати розклад двох контекстів, спочатку заблокуйте B, а потім нехай A розбудить B і зачекає в першій точці передавання керування; у наступній точці B виконає зворотну операцію. Такий підхід працює як детерміноване перемикання контексту й використовується автоматичним дослідником A-B-A.<sup>[[17]](#references)</sup>

Мінімальна кампанія: скомпілюйте тестовий приклад із чотирма хуками (`test_setup`, двома функціями потоків і `test_end`) як shared library, зберіть трасування без обмежень, а потім переберіть кандидатів A-B-A або додайте ручні обмеження навколо підозрілих доступів.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Інтерпретуйте тайм-аути окремо від успішних перестановок: запитаний порядок може бути неможливим, оскільки блокування або залежність від ініціалізації/публікації не дає другому контексту дійти до точки ін'єкції. Також пам'ятайте про сліпі зони KASAN: прямий доступ до стека зазвичай не перехоплюється, якщо немає ризику виходу за межі; глобальні змінні пропускаються за стандартної оптимізації, а поточні компілятори не можуть одночасно генерувати хуки ASAN і TSAN. Крім того, прототип втрачає буфер KCOV, коли гостьова система аварійно завершує роботу, тому збережіть окрему консоль/оракул для збоїв.<sup>[[17]](#references)</sup>

Для майбутнього fuzzing з керуванням за конкурентністю записуйте зведення доступів до пам'яті для кожного вводу або системного виклику, знаходьте пари операцій, які могли б утворити точки комунікації між контекстами, а потім досліджуйте лише ці комбінації. Знімки стану VM стабілізують глобальний стан і адреси; без знімків метадані місця виділення пам'яті можуть абстрагувати об'єкти між запусками. Це запропоноване розширення, а не функція поточних користувацьких інструментів MAccConc.<sup>[[17]](#references)</sup>

## Інтроспекція harness: рано виявляйте поверхневі fuzzers

Коли кампанія зупиняється, проблема часто полягає не в мутаторі, а в **harness**. Використовуйте **інтроспекцію досяжності/покриття**, щоб знаходити функції, досяжні статично з вашої цілі fuzzing, але рідко або ніколи не покриті динамічно. Такі функції зазвичай вказують на одну з трьох проблем.<sup>[[12]](#references)</sup>

- Harness входить у ціль надто пізно або надто рано.
- У початковому корпусі бракує цілої групи функцій.
- Цілі насправді потрібен **другий harness**, а не один надмірно великий harness «для всього».

Якщо ви використовуєте робочі процеси на кшталт OSS-Fuzz / ClusterFuzz, Fuzz Introspector може порівнювати статичну досяжність із покриттям під час виконання та генерувати звіти за результатами запуску з обмеженням часу або на основі публічного корпусу.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Використовуйте звіт, щоб вирішити, чи додати новий harness для неперевіреного шляху парсера, розширити корпус для певної функції або розділити монолітний harness на менші точки входу.

## Вибір цілей fuzzing на основі графа та тріаж мутацій

Якщо у вас уже є результати **статичного аналізу**, **mutation testing** і звіти про покриття, не розглядайте їх як незалежні списки. Спершу побудуйте **граф викликів**, а потім анотуйте його вузли **цикломатичною складністю**, **досяжністю з точок входу/недовірених вхідних даних** і будь-якими зовнішніми знахідками, після чого поставте запитання про граф.<sup>[[5]](#references)[[6]](#references)</sup>

- Які функції з високою складністю досяжні з недовірених вхідних даних?
- Які мутації, що пережили тестування, лежать на шляхах від парсерів/обробників до критичного для безпеки коду?
- Які функції є архітектурними вузькими місцями з незвично великим **радіусом впливу**?

Зазвичай так вдається знайти кращі цілі для fuzzing, ніж орієнтуючись лише на «найнижче покриття». Парсер/декодер із **високою складністю** та підтвердженою **зовнішньою досяжністю** є кращим кандидатом для harness, ніж ізольований внутрішній допоміжний компонент зі слабким покриттям, до якого не веде контрольований зловмисником шлях.

### Практичний процес тріажу

1. Побудуйте **граф коду** на основі кодової бази й отримайте метрики складності/гілок для кожної функції.
2. Перелічіть **точки входу**, що приймають дані, контрольовані зловмисником: обробники запитів, декодери, імпортери, парсери протоколів, засоби читання CLI/файлів.
3. Виконайте запити шляхів від цих точок входу до кандидатних функцій, щоб відокремити доступну поверхню атаки від недосяжного/лише внутрішнього коду.
4. Визначте пріоритетність вузлів, що поєднують:
   - високу **цикломатичну складність**
   - підтверджену **досяжність із недовірених вхідних даних**
   - великий **радіус впливу** або багато залежних від них компонентів
   - додаткові свідчення, як-от знахідки **SARIF**, примітки аудиту або мутації, що пережили тестування
5. Спершу створіть цільові harness для вузлів із найвищими оцінками, особливо для **парсерів/кодеків**, як-от декодерів hex/Base64/IP/повідомлень.

### Мутації, що пережили тестування: еквівалентні чи важливі

Mutation testing часто дає зашумлений список мутацій, що пережили тестування. Перш ніж вважати кожну з них прогалиною в безпеці, скористайтеся графом, щоб з’ясувати:

- Чи досяжна мутована функція з точки входу, контрольованої зловмисником?
- Чи обмежені всі шляхи виклику сильнішими інваріантами, ніж мутована перевірка?
- Чи міститься вузол у недосяжному коді, логіці лише форматування або в арифметичному/парсерному шляху з високим впливом?

Мутації, що залишаються недосяжними або структурно обмеженими, часто є **еквівалентними мутантами**. Мутації, які залишаються **досяжними** та зачіпають **граничні умови**, **шляхи переповнення/перенесення** або критичну для безпеки арифметику/парсинг, варто перенести до:

- нових fuzz harness
- прямих тестів властивостей/інваріантів
- цільових векторів для граничних випадків

### Зіставлення зовнішніх знахідок із графом

Якщо ваш конвеєр SAST експортує **SARIF**, нанесіть знахідки на вузли графа за **файлом і діапазоном рядків**, а потім скористайтеся графом, щоб визначити ширший вплив.<sup>[[6]](#references)</sup>

- обчисліть **радіус впливу** позначеної функції
- перевірте, чи лежить знахідка на будь-якому шляху від точки входу
- згрупуйте близькі знахідки, що зводяться до одного вузького місця

Це корисно, коли потрібно вирішити, чи витрачати час на fuzzing конкретної функції: вузол, який є **досяжним**, **складним** і вже має **знахідки SAST**, часто є кращою ціллю, ніж просто складний вузол без шляху від зловмисника.

Приклад процесу з Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Важлива методологія — це перетин: **складність x відкритість x вплив**. Використовуйте граф, щоб вибрати цілі для fuzzing із найбільшою очікуваною цінністю для безпеки, а потім за мутаціями, що пройшли перевірку, визначте, які межі та інваріанти має перевіряти ваш harness.<sup>[[5]](#references)</sup>

## Fuzzing у Go за допомогою gosentry: потужніший рушій, типізовані вхідні дані та диференційні перевірки

Якщо ціль на Go вже має нативний harness для `testing.F`, практичний шлях оновлення — запускати той самий harness за допомогою [gosentry](https://github.com/trailofbits/gosentry), форка Go toolchain, який зберігає `go test -fuzz`, але замінює backend на **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Це корисно, коли нативний Go fuzzer застрягає на **складних порівняннях**, **типізованих вхідних даних** або форматах із великою кількістю розбору. Методологія залишається незмінною:

- Продовжуйте використовувати `f.Add(...)` для seed-значень і `f.Fuzz(...)` для callback-функції.
- Повторно використовуйте той самий harness, але запускайте його за допомогою бінарного файла `go` від gosentry замість стандартного toolchain.
- Розглядайте отриману кампанію як звичайний запуск із керуванням за покриттям, але з плануванням/мутаціями LibAFL та кращими додатковими детекторами.

### Перетворення непомітних збоїв на результати fuzzing

Поширена проблема під час оцінювання Go-застосунків полягає в тому, що небезпечна поведінка часто **не** призводить до аварійного завершення за замовчуванням. За допомогою gosentry кілька класів «поганих, але непомітних» станів можна перетворити на результати fuzzing.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` — щоб вибрані шляхи логування/обробки помилок поводилися як аварійне завершення (корисно для шляхів із кодом на кшталт `log.Fatal`, який інакше лише записує повідомлення та продовжує роботу).
- `--catch-races=true` — щоб повторно запускати щойно виявлені елементи черги з детектором перегонів Go.
- `--catch-leaks=true` — щоб повторно запускати нові елементи черги з `goleak` і зупинятися у разі витоку goroutine.
- Обробка зависань LibAFL дає змогу зберігати **нескінченні цикли / дуже повільні вхідні дані** як результати fuzzing, замість того щоб втрачати їх через тайм-аути.
- Вбудовані перевірки арифметичного переповнення за замовчуванням, а також додаткові перевірки обрізання за допомогою інструментування в стилі go-panikint.

Це особливо цінно для цілей, де вплив на безпеку полягає в **збої парсера без panic**, **помилці конкурентного виконання** або **зависанні, що спричиняє лише DoS**, а не в пошкодженні пам’яті.

### Fuzzing з урахуванням структур для типізованих Go API

Нативний Go fuzzing переважно розрахований на скалярні значення, як-от `[]byte`, `string` і числа. Якщо код, що тестується, отримує типізовані об’єкти, gosentry може напряму виконувати fuzzing **складених значень** (структур, зрізів, масивів, вказівників), водночас мутації застосовуються до байтів під ними.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Використовуйте це, коли створення фальшивого wire format лише для fuzzing приховувало б логічні помилки за кодом парсингу, наявним лише в harness. Для кампаній differential або grammar-based залишайте вхідні дані harness як один `[]byte` або `string` і виконуйте парсинг усередині callback.

### Grammar-based fuzzing для парсерів і протокольних вхідних даних

Для парсерів, форматів і мов вводу gosentry може запускати **Nautilus grammar fuzzing** на основі LibAFL. Граматика — це JSON-масив production rules, а harness зазвичай має приймати один аргумент `[]byte` або `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Нотатки щодо методології:

- Використовуйте режим граматики, коли мутації на рівні байтів переважно відсіюються на ранніх перевірках синтаксису.
- Зосередьте граматику на **підмножині мови/протоколу, важливій для безпеки**, а не моделюйте всю специфікацію.
- Використовуйте великі граничні значення в терміналах/нетерміналах, щоб перевірити граничні випадки для цілих чисел, довжин і кінцевих автоматів.
- У режимі граматики вхідні дані залишаються граматично коректними, але цільова програма все одно отримує **байти/рядки**, тож парсинг і семантичні перевірки залишаються всередині коду, що тестується.

### Диференційний fuzzing: порівнюйте реалізації, а не лише збої

Для екосистем Go ефективним підходом є **grammar-based differential fuzzing**: генеруйте коректні структуровані вхідні дані й передавайте їх двом парсерам, клієнтам або механізмам переходу станів.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Вважайте такими знахідками:

- одна реалізація викликає panic, тоді як інша коректно відхиляє ввід
- невідповідності між прийнятим і відхиленим вводом
- різні дерева розбору або декодовані об’єкти
- розбіжності в переходах стану, nonce, балансах або коренях стану

Це практичний спосіб виявляти **невідповідності консенсусу**, **неоднозначність парсера** та **відхилення реалізації від специфікації**, які часто не виявляються під час fuzzing, що перевіряє лише збої.

### Використовуйте корпус кампанії повторно для звітів про покриття

Після кампанії повторно запустіть збережений корпус черги, щоб створити звіт про покриття Go без ручного експорту окремого корпусу.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Запускайте команду з того самого пакета й із тією самою ціллю `-fuzz`, щоб gosentry знайшов правильний кешований стан кампанії.
