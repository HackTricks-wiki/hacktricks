## Mutational Grammar Fuzzing: Coverage vs. Semantics

Στο **mutational grammar fuzzing**, οι είσοδοι μεταλλάσσονται διατηρώντας την **εγκυρότητά τους ως προς τη γραμματική**. Στη λειτουργία καθοδηγούμενη από coverage, μόνο τα δείγματα που προκαλούν **νέο coverage** αποθηκεύονται ως seeds του corpus. Για **στόχους γλωσσών** (parsers, interpreters, engines), αυτή η προσέγγιση μπορεί να χάσει bugs που απαιτούν **αλυσίδες σημασιολογίας/ροής δεδομένων**, στις οποίες η έξοδος μιας κατασκευής γίνεται είσοδος μιας άλλης.<sup>[[1]](#references)</sup>

**Τρόπος αποτυχίας:** ο fuzzer βρίσκει seeds που ενεργοποιούν μεμονωμένα τις `document()` και `generate-id()` (ή παρόμοιες primitives), αλλά **δεν διατηρεί την αλυσιδωτή ροή δεδομένων**, με αποτέλεσμα να απορρίπτεται το δείγμα που είναι «πιο κοντά στο bug», επειδή δεν προσθέτει coverage. Με **3+ εξαρτημένα βήματα**, ο τυχαίος ανασυνδυασμός γίνεται δαπανηρός και το feedback του coverage δεν καθοδηγεί την αναζήτηση.<sup>[[1]](#references)</sup>

**Συμπέρασμα:** για γραμματικές με πολλές εξαρτήσεις, εξετάστε το ενδεχόμενο **συνδυασμού μεταλλακτικών και γενετικών φάσεων** ή της ευνοϊκής ρύθμισης της παραγωγής προς μοτίβα **αλυσιδωτής κλήσης συναρτήσεων** (όχι μόνο προς το coverage).<sup>[[1]](#references)</sup>

## Προβλήματα ποικιλομορφίας του corpus

Η μετάλλαξη με καθοδήγηση από το coverage είναι **άπληστη**: ένα δείγμα με νέο coverage αποθηκεύεται αμέσως, διατηρώντας συχνά μεγάλα, αμετάβλητα τμήματα. Με τον καιρό, τα corpus γεμίζουν με **σχεδόν πανομοιότυπα δείγματα** και έχουν χαμηλή δομική ποικιλομορφία. Η επιθετική ελαχιστοποίηση μπορεί να αφαιρέσει χρήσιμο περιεχόμενο, γι’ αυτό ένας πρακτικός συμβιβασμός είναι η **ελαχιστοποίηση με επίγνωση της γραμματικής**, η οποία **σταματά μόλις φτάσει σε ένα ελάχιστο όριο tokens** (μειώνει τον θόρυβο διατηρώντας αρκετή περιβάλλουσα δομή, ώστε να παραμένει εύκολη η μετάλλαξη).<sup>[[1]](#references)</sup>

Ένας πρακτικός κανόνας για το corpus στο mutational fuzzing είναι ο εξής: **προτιμήστε ένα μικρό σύνολο δομικά διαφορετικών seeds που μεγιστοποιούν το coverage** αντί για έναν μεγάλο όγκο σχεδόν πανομοιότυπων δειγμάτων. Στην πράξη, αυτό συνήθως σημαίνει τα εξής.<sup>[[1]](#references)[[3]](#references)</sup>

- Ξεκινήστε από **δείγματα του πραγματικού κόσμου** (δημόσια corpora, crawling, καταγεγραμμένη κίνηση δικτύου, σύνολα αρχείων από το οικοσύστημα του στόχου).
- Περιορίστε τα με **ελαχιστοποίηση corpus βάσει coverage** αντί να διατηρείτε κάθε έγκυρο δείγμα.
- Κρατήστε τα seeds **αρκετά μικρά**, ώστε οι μεταλλάξεις να επηρεάζουν πεδία με νόημα αντί να σπαταλούν τους περισσότερους κύκλους σε άσχετα bytes.
- Επαναλάβετε την ελαχιστοποίηση του corpus μετά από σημαντικές αλλαγές στο harness ή στα όργανα καταγραφής, επειδή το «καλύτερο» corpus αλλάζει όταν αλλάζει η προσβασιμότητα.

## Μετάλλαξη με επίγνωση συγκρίσεων για magic values

Ένας συνηθισμένος λόγος που οι fuzzers φτάνουν σε πλατό δεν είναι η σύνταξη αλλά οι **δύσκολες συγκρίσεις**: magic bytes, έλεγχοι μήκους, συμβολοσειρές enum, checksums ή τιμές dispatch του parser που ελέγχονται μέσω `memcmp`, πινάκων switch ή διαδοχικών συγκρίσεων. Η καθαρά τυχαία μετάλλαξη σπαταλά κύκλους προσπαθώντας να μαντέψει αυτές τις τιμές byte προς byte.

Για αυτούς τους στόχους, χρησιμοποιήστε **ιχνηλάτηση συγκρίσεων** (για παράδειγμα, ροές εργασίας τύπου AFL++ `CMPLOG` / Redqueen), ώστε ο fuzzer να μπορεί να παρατηρεί τα τελεστέα αποτυχημένων συγκρίσεων και να κατευθύνει τις μεταλλάξεις προς τιμές που τις ικανοποιούν.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Πρακτικές σημειώσεις:**

- Αυτό είναι ιδιαίτερα χρήσιμο όταν ο στόχος αποκρύπτει τη βαθύτερη λογική πίσω από **υπογραφές αρχείων**, **ρήματα πρωτοκόλλου**, **ετικέτες τύπων** ή **bits δυνατοτήτων που εξαρτώνται από την έκδοση**.
- Συνδυάστε το με **λεξικά** που έχουν εξαχθεί από πραγματικά δείγματα, προδιαγραφές πρωτοκόλλων ή αρχεία καταγραφής εντοπισμού σφαλμάτων. Ένα μικρό λεξικό με tokens γραμματικής, ονόματα τμημάτων, ρήματα και διαχωριστικά είναι συχνά πιο χρήσιμο από μια τεράστια γενική λίστα λέξεων.
- Αν ο στόχος εκτελεί πολλούς διαδοχικούς ελέγχους, επιλύστε πρώτα τις αρχικές συγκρίσεις «magic» και, στη συνέχεια, ελαχιστοποιήστε ξανά το corpus που προκύπτει, ώστε τα επόμενα στάδια να ξεκινούν από ήδη έγκυρα προθέματα.

## Fuzzing API αρχείων που κρύβουν μια γλώσσα ονομάτων αρχείων

Μια παράμετρος με όνομα `filename`, `path` ή `URL` μπορεί να αποτελεί σημείο εισόδου σε διερμηνευτή και όχι κυριολεκτική αναζήτηση αρχείου. Για παράδειγμα, το CFITSIO Extended Filename Syntax (EFS) αξιολογεί επιλογείς σε αγκύλες, εκφράσεις γραμμών/εικονοστοιχείων, υπολογιζόμενες στήλες, ιστογράμματα και μετασχηματισμούς πριν επιστρέψει το αντικείμενο που άνοιξε· ορισμένες μορφές δημιουργούν επίσης προσωρινά αντίγραφα. Κατά τη χαρτογράφηση της επιφάνειας επίθεσης, ταξινομήστε κάθε API ανοίγματος/εισαγωγής ως **literal-path** ή **interpreted-path** και, στη συνέχεια, κάντε fuzzing στο σημείο εισόδου παραγωγής που καλούν πραγματικά οι εφαρμογές.<sup>[[20]](#references)[[22]](#references)</sup>

Για τα primitives SSRF, αντιγραφής αρχείων και χειρισμού πρωτοκόλλων που προκύπτουν —και για ασφαλέστερα API κυριολεκτικών διαδρομών— δείτε το [Μίνι γλώσσες ονομάτων αρχείων ως primitives SSRF/αρχείων](../pentesting-web/ssrf-server-side-request-forgery/index.html#filename-mini-languages-as-ssrffile-primitives-cfitsio-efs).<sup>[[20]](#references)</sup>

### Διατηρήστε ξεχωριστό το υποκείμενο αντικείμενο από το πρόγραμμα που γίνεται fuzzing

Όταν η γραμματική βρίσκεται σε επίθημα ονόματος αρχείου, η τροποποίηση μόνο των bytes του αναφερόμενου αρχείου δεν φτάνει στον αναλυτή. Αντί γι’ αυτό, ένα μικρό harness μπορεί να διαβάσει ένα testcase ως συμβολοσειρά και να το περάσει στο API ανοίγματος με διερμηνεία· η καμπάνια CFITSIO έφτασε στους περισσότερους αναλυτές και αξιολογητές EFS καλώντας τη `fits_open_file()` σε λειτουργία μόνο για ανάγνωση. Διατηρήστε ξεχωριστά διαθέσιμα έγκυρα υποκείμενα αρχεία, ώστε οι μεταλλάξεις να εστιάζουν στη γλώσσα επιλογέων/εκφράσεων αντί να χαλούν συνεχώς τη βασική διαδρομή.<sup>[[22]](#references)</sup>

Χρησιμοποιήστε seeds που καλύπτουν το καθένα διαφορετική οικογένεια γραμματικής και, στη συνέχεια, δημιουργήστε ένα συμπαγές λεξικό από τις προδιαγραφές και τον πηγαίο κώδικα του lexer/parser. Αν η κάλυψη φτάσει σε στασιμότητα ενώ οι είσοδοι αποτυγχάνουν επανειλημμένα στην ίδια διαδρομή συντακτικού σφάλματος, διατηρήστε τα έγκυρα προθέματα και προσθέστε διαχωριστικά, τελεστές, λέξεις-κλειδιά, ονόματα συναρτήσεων και αντιπροσωπευτικά ονόματα πεδίων, αντί απλώς να αυξήσετε τον χρόνο τυχαίων μεταλλάξεων.<sup>[[22]](#references)</sup>

Εκτελέστε το harness με το λεξικό γραμματικής, για παράδειγμα:<sup>[[3]](#references)[[22]](#references)</sup>

```bash
afl-fuzz -i filename-seeds -o out -x filename-language.dict -- ./filename-harness @@
```

### Περιορισμός των παρενεργειών του «read-only» harness

Μια σημαία read-only σε μια βιβλιοθήκη δεν εγγυάται testcase χωρίς παρενέργειες: η γλώσσα των ονομάτων αρχείων μπορεί να ξαναγράψει την είσοδο, να δημιουργήσει αρχεία εξόδου ή να υλοποιήσει προσωρινά αντικείμενα. Η καμπάνια CFITSIO αρχικά κατέστρεψε seed files και άφησε απρόσμενα αρχεία σε όλο το filesystem, οπότε χρειάστηκαν καθαρισμός και απομόνωση.<sup>[[22]](#references)</sup>

- Δώστε σε κάθε worker έναν προσωρινό working directory και έναν ιδιωτικό temporary directory.
- Παρέχετε αντίγραφα των canonical backing files· μην αφήνετε ποτέ το target να μεταβάλλει το μοναδικό αντίγραφο του corpus.
- Απενεργοποιήστε την πρόσβαση στο δίκτυο, εκτός αν τα remote backends είναι ο επιδιωκόμενος στόχος, και περιορίστε τις εγγράψιμες διαδρομές με container, mount namespace ή αντίστοιχο sandbox.
- Επαναφέρετε τον directory μετά από κάθε εκτέλεση ή batch worker και αντιμετωπίζετε τις απρόσμενες αλλαγές στο filesystem ως πρόσθετα ευρήματα.

### Βρόχος crash-to-patch-to-fuzz

Ομαδοποιήστε τα crashes πριν από την επιδιόρθωση, ώστε χιλιάδες artifacts να μη μετατραπούν σε χιλιάδες εργασίες patch. Στην αξιολόγηση CFITSIO, το AFLTriage περιόρισε το αρχικό σύνολο crashes σε λίγες βασικές αιτίες· το advisory που προέκυψε δείχνει διακριτές αστοχίες, μεταξύ των οποίων λανθασμένοι έλεγχοι μεγέθους προορισμού, stale pointers μετά από `realloc()`, αριθμητικά σφάλματα και μη ασφαλείς διαδρομές καθαρισμού του parser.<sup>[[21]](#references)[[22]](#references)</sup>

1. Ελαχιστοποιήστε ένα αντιπροσωπευτικό input για κάθε ομάδα και αναπαράγετέ το με AddressSanitizer.
2. Καταγράψτε την ακριβή αποτυχημένη πρόσβαση, τη θέση στον πηγαίο κώδικα, το ιστορικό allocation/free και την κατάσταση του parser που οδήγησε στην παραβίαση του invariant.
3. Εφαρμόστε ένα στενά εστιασμένο υποψήφιο patch και κάντε rebuild με την ίδια instrumentation για coverage και sanitizers.
4. Αναπαράγετε το αρχικό reproducer **και κάθε input της ομάδας του**· ενεργοποιήστε επίσης το leak detection, επειδή μια διόρθωση memory-safety μπορεί να χαλάσει τη διαχείριση ownership σε διαδρομή σφάλματος.
5. Εκτελέστε λειτουργικές δοκιμές με πραγματικά αρχεία και, στη συνέχεια, συνεχίστε από τη συσσωρευμένη queue (ή εισαγάγετε ξανά αυτή την queue, αν η engine απαιτεί νέο output directory μετά την αλλαγή του binary).
6. Επαναλάβετε: η αφαίρεση του πρώτου επιφανειακού crash συχνά επιτρέπει στα υπάρχοντα seeds να προχωρήσουν σε βαθύτερη κατάσταση του parser.

Ένα LLM μπορεί να επιταχύνει το βήμα 2 και να συντάξει ένα αρχικό patch για το βήμα 3, όταν του δοθούν το input που προκαλεί το crash, η αναφορά του sanitizer, το harness και ο σχετικός πηγαίος κώδικας· ωστόσο, το patch του παραμένει μη έμπιστο. Η αποδοχή της επιδιόρθωσης κρίνεται από την αναπαραγωγή με sanitizer και τις πύλες regression, όχι από την εξήγηση του μοντέλου.<sup>[[22]](#references)</sup>

## Πλουσιότερο Feedback όταν το Edge Coverage Συγχωνεύει Διαφορετικά Paths

Το συνηθισμένο edge coverage δεν μπορεί να ξεχωρίσει δύο εκτελέσεις που περνούν από τον ίδιο helper μέσω διαφορετικών callers ή ακολουθούν διαφορετικούς συνδυασμούς κλάδων μέσα σε μια συνάρτηση. Αυτό έχει σημασία σε κοινόχρηστους decoders, protocol dispatchers και helpers διερμηνευτών, όπου το **route** προς ένα edge καθορίζει την ενεργή κατάσταση. Η αφελής παρακολούθηση κάθε calling context είναι επίσης επικίνδυνη: το coverage map και η queue μπορεί να διογκωθούν υπερβολικά. Συνεπώς, η έρευνα για context-sensitive fuzzing συνιστά τη βελτίωση μόνο των πολλά υποσχόμενων contexts, αντί να αντιμετωπίζεται ολόκληρο το call graph ως context-sensitive.<sup>[[14]](#references)</sup>

Οι πρόσφατες εκδόσεις του AFL++ παρέχουν **Ball-Larus per-function path coverage** επιπλέον του συνηθισμένου edge coverage. Αναθέτει ένα feature σε κάθε ακυκλικό path μέσα σε μια συνάρτηση· αφαιρούνται οι back-edges των loops, επομένως αυτό το feedback διακρίνει συνδυασμούς κλάδων, αλλά **όχι τον αριθμό επαναλήψεων των loops**. Ξεκινήστε με το χαλαρό level `1` και, στη συνέχεια, περιορίστε τις αυστηρότερες λειτουργίες σε ύποπτο parser/state-machine code, επειδή ο αριθμός των paths μπορεί να αυξηθεί εκθετικά.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Για μια βοηθητική συνάρτηση που καλείται από πολλές τοποθεσίες με σημασία για την ασφάλεια, η λειτουργία LTO μπορεί να συνδυάσει κάθε διαδρομή συνάρτησης με την άμεση τοποθεσία κλήσης της:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Καθοδήγηση για την καμπάνια:** εφαρμόστε πιο πλούσιο feedback με φειδώ και παρακολουθείτε το κόστος του coverage-map/queue.<sup>[[13]](#references)[[14]](#references)</sup>

- Εκτελέστε παράλληλα ένα συνηθισμένο instance edge-coverage· το πιο πλούσιο feedback είναι χρήσιμο μόνο αν το επιπλέον κόστος του queue/map δεν μειώνει υπερβολικά τις εκτελέσεις ανά δευτερόλεπτο.
- Χρησιμοποιήστε το `AFL_LLVM_ALLOWLIST` για να περιορίσετε την instrumentation των path/caller, όταν μεγάλες βιβλιοθήκες με πολλά templates ή γενικός κώδικας βοηθητικών συναρτήσεων κυριαρχούν στο map.
- Οι συναρτήσεις με υπερβολικά πολλά acyclic paths μπορούν να παραλείπονται από το AFL++· οι προειδοποιήσεις κατά τη μεταγλώττιση είναι ένδειξη ότι ο στόχος χρειάζεται allowlisting ή λιγότερο αυστηρό επίπεδο.
- Το caller + path coverage υποστηρίζει μόνο ένα επίπεδο caller. Μην το συνδυάζετε με βαθύτερα context stacks.
- Τα path IDs μπορεί να αλλάξουν μεταξύ major εκδόσεων του LLVM. Διατηρήστε σταθερό το toolchain σε όλη την καμπάνια και μη συγχρονίζετε corpora που βασίζονται σε PATH σαν να είχαν σταθερά feature IDs μεταξύ builds.
- Αυτό το feedback συμπληρώνει το `CMPLOG`: το comparison tracing λύνει το **ποια τιμή περνά ένα guard**, ενώ το path/caller feedback διατηρεί το **ποια διαδρομή και ποιος συνδυασμός branches οδήγησαν εκεί**.

## Stateful Fuzzing: οι ακολουθίες είναι seeds

Για **protocols**, **authenticated workflows** και **multi-stage parsers**, η μονάδα ενδιαφέροντος συχνά δεν είναι ένα μεμονωμένο blob αλλά μια **ακολουθία μηνυμάτων**. Η συνένωση ολόκληρου του transcript σε ένα αρχείο και η τυφλή μετάλλαξή του είναι συνήθως αναποτελεσματική, επειδή ο fuzzer μεταλλάσσει κάθε βήμα εξίσου, ακόμη κι όταν μόνο το τελευταίο μήνυμα φτάνει στην ευάλωτη κατάσταση.<sup>[[4]](#references)</sup>

Μια αποτελεσματικότερη προσέγγιση είναι να αντιμετωπίζετε την **ίδια την ακολουθία ως seed** και να χρησιμοποιείτε την **παρατηρήσιμη κατάσταση** (response codes, protocol states, parser phases, τύπους αντικειμένων που επιστρέφονται) ως πρόσθετο feedback.<sup>[[4]](#references)</sup>

- Διατηρείτε σταθερά τα **έγκυρα μηνύματα προθέματος** και εστιάζετε τις μεταλλάξεις στο μήνυμα που **οδηγεί στη μετάβαση**.
- Αποθηκεύετε identifiers και τιμές που παράγονται από τον server στις προηγούμενες απαντήσεις, όταν το επόμενο βήμα εξαρτάται από αυτές.
- Προτιμάτε τη μετάλλαξη/συγχώνευση ανά μήνυμα αντί να μεταλλάσσετε ολόκληρο το serialized transcript σαν αδιαφανές blob.
- Αν το protocol παρέχει ουσιαστικά response codes, χρησιμοποιήστε τα ως **φθηνό state oracle** για να δίνετε προτεραιότητα σε ακολουθίες που προχωρούν βαθύτερα.

Για τον ίδιο λόγο, το vanilla file-style fuzzing συχνά δεν εντοπίζει authenticated bugs, κρυφές μεταβάσεις ή bugs σε parsers που εμφανίζονται «μόνο μετά το handshake»: ο fuzzer πρέπει να διατηρεί **τη σειρά, την κατάσταση και τις εξαρτήσεις**, όχι μόνο τη δομή.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing driver με πολλούς clients

Το υψηλό edge coverage μπορεί και πάλι να μην εντοπίσει bugs στον IPC driver, επειδή το coverage δεν περιγράφει **την ιδιοκτησία αντικειμένων, τα reference counts, τα εκκρεμή μηνύματα, τη σειρά καθαρισμού ή τις εναλλαγές μεταξύ threads**. Η σελίδα [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) καλύπτει το μοντέλο αντικειμένων του driver· αυτό το παράδειγμα εστιάζει στο harness του fuzzer. Το Android Binder αποτελεί χρήσιμο μοντέλο: δεν αρκεί να φτάνει κανείς τόσο στις διαδρομές allocation όσο και στις διαδρομές free, αν ο fuzzer δεν μπορεί να κάνει πολλές διεργασίες να ενεργήσουν στο ίδιο αντικείμενο του kernel με την απαιτούμενη σειρά.<sup>[[15]](#references)</sup>

#### Μοντελοποιήστε το protocol, όχι μεμονωμένα buffers `ioctl`

Αναπαραστήστε ένα test case ως διατεταγμένη γραμματική από **ταυτότητα client + operation + δομημένα arguments**. Ο Binder LKL fuzzer χρησιμοποιεί protobuf και `libprotobuf-mutator`, με έναν επίμονο client διαχείρισης context και δύο συνηθισμένους clients. Έπειτα, ένα semantic harness διατηρεί τις σχέσεις που θα κατέστρεφε η τυφλή μετάλλαξη bytes.<sup>[[15]](#references)</sup>

- Αποθηκεύετε τιμές που επιστρέφονται από προηγούμενες operations. Για παράδειγμα, το `BC_FREE_BUFFER` πρέπει να επαναχρησιμοποιεί έναν δείκτη transaction buffer που επιστράφηκε από προηγούμενο `ioctl`.
- Δημιουργείτε έγκυρες προεπιλεγμένες απαντήσεις, ώστε να ολοκληρώνονται οι σύγχρονες συναλλαγές και να παραμένουν προσβάσιμες οι επόμενες operations.
- Απορρίπτετε αδύνατες μεταβάσεις, όπως συναλλαγές με τον εαυτό ή πολλαπλές εκκρεμείς συναλλαγές προς τον ίδιο στόχο.
- Διατηρείτε την κατάσταση singleton bootstrap εκτός της επαναφοράς ανά είσοδο. Το Binder επιτρέπει μόνο μία εγγραφή `BINDER_SET_CONTEXT_MGR` ανά boot, επομένως η επανειλημμένη καταστροφή και επαναδημιουργία αυτού του client θα καθιστούσε άκυρες τις επόμενες εισόδους.

Ένα χρήσιμο πρότυπο race κατά τη διάρκεια ζωής αντικειμένων είναι να κάνει ένας client μεταφορά ενός αντικειμένου, να ξεκινά ο καθαρισμός ενός thread ή μιας διεργασίας και, ταυτόχρονα, ο client που λαμβάνει το αντικείμενο να αποδεσμεύει το transaction buffer. Στο παράδειγμα CVE-2020-0423, η μεταφορά ενός `BINDER_TYPE_WEAK_BINDER` και στη συνέχεια το `BINDER_THREAD_EXIT` σε race με το `BC_FREE_BUFFER` μπορούσαν να αποδεσμεύσουν ένα ενσωματωμένο `binder_work` ενώ η διαδρομή καθαρισμού του thread που τερματιζόταν εξακολουθούσε να το χρησιμοποιεί.<sup>[[15]](#references)</sup>

#### Επαναφέρετε ελεγχόμενες εναλλαγές σε ένα kernel userspace

Το [Linux Kernel Library (LKL)](https://github.com/lkl/linux) συνδέει τον πραγματικό κώδικα του kernel με ένα harness userspace και εκθέτει το syscall interface του μέσω του `lkl_syscall`. Έτσι, η κατάσταση protobuf, το coverage και το KASAN συντονίζονται εύκολα μέσα σε μία διεργασία. Ωστόσο, το LKL συνήθως εκτελεί ένα syscall χωρίς να το διακόπτει κάποιο άλλο kernel thread. Για καμπάνιες race, εισαγάγετε σημεία `schedule()` γύρω από επιλεγμένα όρια lock/unlock και διάρκειας ζωής αντικειμένων και, στη συνέχεια, αφήστε το harness να επιλέγει τυχαία τον επόμενο client σε κάθε yield. Κρατήστε αυτά τα σημεία στοχευμένα, επειδή καθένα πολλαπλασιάζει τον χώρο αναζήτησης του scheduling. Ο randomized scheduler που περιγράφουν οι ερευνητές **δεν** αποτελεί μέρος του upstream Binder fuzzer.<sup>[[15]](#references)</sup>

#### Δημιουργήστε και επαναλάβετε serialized seeds παλινδρόμησης

Το upstream harness καρφιτσώνει μια συμβατή έκδοση του `libprotobuf-mutator`, ενεργοποιεί το LKL fuzzing instrumentation και το KASAN με `LKL_FUZZING=1` και ενεργοποιεί το `CONFIG_MMU` για το Binder με `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Αφού κάνετε checkout μιας σκόπιμα ευάλωτης αναθεώρησης ή εφαρμόσετε τα rollback patches που τεκμηριώνονται upstream, ένα serialized seed μπορεί να αναπαράγει ολόκληρη τη μετάβαση κατάστασης πολλών clients χωρίς να χρειάζεται να την ανακατασκευάσετε σε ένα ad hoc C proof of concept:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Αντιμετωπίστε το KASAN use-after-free που προέκυψε ως επιβεβαίωση ότι το seed έφτασε στη vulnerable lifetime path. **Δεν** αποδεικνύει τις μεταγενέστερες primitives που απαιτούνται για kernel code execution ή privilege escalation.<sup>[[16]](#references)</sup>

## Τέχνασμα ποικιλομορφίας σε ένα μηχάνημα (τύπου Jackalope)

Ένας πρακτικός τρόπος να συνδυάσετε τη **generative novelty** με την **επαναχρησιμοποίηση coverage** είναι να **επανεκκινείτε βραχύβιους workers** απέναντι σε έναν persistent server. Κάθε worker ξεκινά με ένα άδειο corpus, συγχρονίζεται έπειτα από `T` δευτερόλεπτα, εκτελείται για άλλα `T` δευτερόλεπτα με το συνδυασμένο corpus, συγχρονίζεται ξανά και έπειτα τερματίζεται. Έτσι προκύπτουν **νέες δομές σε κάθε generation**, ενώ παράλληλα αξιοποιείται το συσσωρευμένο coverage.<sup>[[1]](#references)[[2]](#references)</sup>

**Server:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Διαδοχικοί workers (παράδειγμα βρόχου):**

<details>
<summary>Βρόχος επανεκκίνησης worker του Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Σημειώσεις:**

- Το `-in empty` επιβάλλει ένα **νέο corpus** σε κάθε generation.
- Το `-server_update_interval T` προσεγγίζει τον **καθυστερημένο συγχρονισμό** (πρώτα novelty και μετά reuse).
- Στη λειτουργία grammar fuzzing, ο **αρχικός συγχρονισμός με τον server παραλείπεται από προεπιλογή** (δεν χρειάζεται το `-skip_initial_server_sync`).
- Το βέλτιστο `T` **εξαρτάται από τον στόχο**· συνήθως αποδίδει καλύτερα η αλλαγή αφού ο worker εντοπίσει το μεγαλύτερο μέρος της «εύκολης» κάλυψης.

## Snapshot Fuzzing Για Στόχους Δύσκολους Στην Προετοιμασία Harness

Όταν ο κώδικας που θέλετε να δοκιμάσετε γίνεται προσβάσιμος μόνο **μετά από μεγάλο κόστος προετοιμασίας** (εκκίνηση VM, ολοκλήρωση σύνδεσης, λήψη πακέτου, ανάλυση container, αρχικοποίηση υπηρεσίας), μια χρήσιμη εναλλακτική είναι το **snapshot fuzzing**: καταγράψτε την έτοιμη κατάσταση της διεργασίας ή του VM, εισαγάγετε κάθε testcase στη διαδρομή εισόδου του στόχου, εκτελέστε μέχρι να προκύψει crash/timeout και επαναφέρετε το snapshot. Έτσι αποφεύγεται η επανάληψη της αρχικοποίησης ή των προθεμάτων του πρωτοκόλλου και είναι χρήσιμο για **υπηρεσίες δικτύου**, **firmware**, **attack surfaces μετά την πιστοποίηση** και **στόχους μόνο με binary**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Εκτελέστε τον στόχο μέχρι να είναι έτοιμη η επιθυμητή κατάσταση.
2. Καταγράψτε **τη μνήμη + τους καταχωρητές** σε εκείνο το σημείο.
3. Για κάθε testcase, γράψτε την τροποποιημένη είσοδο απευθείας στο σχετικό buffer του guest/της διεργασίας.
4. Εκτελέστε μέχρι να προκύψει crash/timeout/reset.
5. Επαναφέρετε το snapshot· για στόχους VM, επαναφέρετε μόνο τις **dirty pages**, όταν υποστηρίζεται, και επαναλάβετε.

Τοποθετήστε το snapshot όσο πιο κοντά γίνεται στο πρώτο βήμα ανάλυσης/δρομολόγησης που έχει υψηλό κόστος, όπως μετά από ένα σημείο `recv`/`read` ή αποσειριοποίησης πακέτου, και καταγράψτε το buffer εισόδου που χρησιμοποιεί ο στόχος. Αυτό ακολουθεί την αρχή της προσαρμοστικής τοποθέτησης: μετακινήστε το snapshot βαθύτερα στην επεξεργασία εισόδου για να αποφύγετε την επανάληψη εργασιών.<sup>[[11]](#references)</sup>

### Incremental snapshots για καταστάσεις πρωτοκόλλου

Ένα σταθερό snapshot αποφεύγει το κόστος προετοιμασίας, αλλά από μόνο του δεν εξερευνά μεταβάσεις που απαιτούν αρκετά έγκυρα μηνύματα. Ένα harness LibAFL-Qemu μπορεί να παρακολουθεί εγγραφές σε ένα πεδίο κατάστασης πρωτοκόλλου και να αποθηκεύει νέο snapshot όταν αλλάζει η κατάσταση. Στο [libslirp TCP harness](https://github.com/quarkslab/slirp_snapshots_stateful), παρακολουθεί το `tcpcb.t_state`, κατακερματίζει την κατάσταση και τις σημαίες απόκρισης για να αφαιρεί διπλότυπα snapshots και αποθηκεύει τις dirty pages σε σχέση με ένα γονικό snapshot. Πριν τροποποιήσει το επόμενο δομημένο μήνυμα, επαναφέρει το επιλεγμένο snapshot μέσω της αλυσίδας γονικών snapshots. Το testcase διατηρεί ένα `SnapshotId` και τα bytes εισόδου που δημιουργήθηκαν (`gen_bytes`)· ο snapshot manager παρακολουθεί τη σχέση γονέα που απαιτείται για την αναπαραγωγή.<sup>[[27]](#references)[[28]](#references)</sup>

Το `SnapshotModule` του LibAFL-Qemu σε user-mode αποθηκεύει τα mappings και τη μνήμη του στόχου, αλλά όχι τους καταχωρητές της CPU· διατηρήστε τους ξεχωριστά όταν χρειάζεται. Ο περιγραφόμενος manager υποστηρίζει ένα δέντρο root snapshot και δεν μπορεί να μοιράζεται snapshot IDs μεταξύ workers. Η λειτουργία multi-snapshot δεν μπορεί επίσης να επαναχρησιμοποιήσει απευθείας την κατάσταση shadow του QASAN. Για offline triage, ανακατασκευάστε την αλυσίδα εισόδου σε ξεχωριστή instrumented διεργασία. Όταν χρησιμοποιούνται τα `AsanHostModule` και `DrCovModule`, το `fuzzer.evaluate_input` εκτελεί τα απαιτούμενα callbacks `pre_exec`/`post_exec`· το `qemu.run` από μόνο του δεν τα εκτελεί.<sup>[[27]](#references)[[28]](#references)</sup>

### Εντοπισμός λογικών υπερβάσεων ανάγνωσης σε ring buffer

Μια ανάγνωση πέρα από το *έγκυρο πλήθος δεδομένων* ενός buffer μπορεί να παραμείνει μέσα στην εκχώρηση μνήμης του host και να μην εντοπιστεί από το συνηθισμένο ASAN. Το [παράδειγμα urgent-data του libslirp](../binary-exploitation/qemu-kvm-vm-escape-chains.md#tcp-urgent-pointer-vs-valid-ring-buffer-bytes) προκαλεί επίσης υποχείλιση σε μη προσημασμένο πλήθος byte. Αν είναι διαθέσιμος ο πηγαίος κώδικας, η instrumentation για υπερχείλιση ακεραίων με πρόσημο/χωρίς πρόσημο μπορεί να εντοπίσει αυτή την παρενέργεια· ξεχωρίστε την εκ προθέσεως αναδίπλωση αριθμού ακολουθίας TCP πριν καταστείλετε τις αναφορές. Ένας ισχυρότερος προτεινόμενος oracle είναι να δηλητηριαστεί η προσαρμοσμένη εκχώρηση ring, να γίνει unpoison μόνο των έγκυρων περιοχών καθώς προχωρά ο εσωτερικός allocator και να δηλητηριαστούν ξανά οι περιοχές που αποδεσμεύονται. Το LibAFL-Qemu παρέχει API δηλητηρίασης ASAN για στόχους στους οποίους η instrumentation του πηγαίου κώδικα δεν είναι πρακτική.<sup>[[27]](#references)</sup>

## Εξερεύνηση Race συνθηκών στον Linux Kernel με το MAccConc

Το [MAccConc](https://github.com/googleprojectzero/MAccConc) μετατρέπει τις race συνθήκες του Linux kernel που εξαρτώνται από τον χρονισμό σε επαναλήψιμα χρονοδιαγράμματα προσβάσεων μνήμης. Μπορεί να απαριθμεί αυτόματα εκτελέσεις **A-B-A** με δύο contexts ή να επιτρέπει στον αναλυτή να επιβάλλει περιορισμούς σειράς μέσω terminal UI/GUI. Πρόκειται για πειραματικό ερευνητικό εργαλείο και όχι για ολοκληρωμένο concurrency fuzzer: προς το παρόν απαιτεί LLVM 23+ και τον patched kernel του project, τα command-line εργαλεία υποστηρίζουν δύο test threads και το προτεινόμενο επίπεδο userspace fuzzing δεν έχει υλοποιηθεί.<sup>[[17]](#references)[[18]](#references)</sup>

### Συλλογή σημείων επικοινωνίας μεταξύ contexts

Δημιουργήστε τον instrumented kernel με KASAN outline callbacks και την patched υποστήριξη KCOV για καταγραφή μνήμης. Το README του project συνιστά επίσης την απενεργοποίηση της βελτιστοποίησης sibling-call, ώστε οι call stacks να παραμένουν χρήσιμες.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

KASAN outline mode (`asan-instrumentation-with-call-threshold=0`) μετατρέπει τις instrumented προσπελάσεις σε helper calls. Τα kernel patches του MAccConc απενεργοποιούν το `asan-opt-same-temp`, ώστε οι διαδοχικές προσπελάσεις να μη συγχωνεύονται· απενεργοποιήστε επίσης τη βελτιστοποίηση `asan-opt-globals` όταν πρέπει να είναι ορατά τα races σε global variables. Το KCOV μεταφέρει τις εγγραφές που προκύπτουν στο userspace. Συγκρίνετε προσπελάσεις από διαφορετικά execution contexts και κρατήστε τα ζεύγη των οποίων τα byte ranges επικαλύπτονται και όπου τουλάχιστον η μία πλευρά πραγματοποιεί εγγραφή· μοντελοποιήστε το `kfree()` ως εγγραφή, ώστε να γίνονται υποψήφιες και οι μεταβάσεις lifetime.<sup>[[17]](#references)</sup>

Για εργασίες που συνεχίζονται εκτός του task που τις ξεκίνησε, όπως η επεξεργασία πακέτων ή τα RCU callbacks, το subsystem πρέπει να προωθεί ένα KCOV remote-coverage handle. Το upstream remote KCOV είναι opt-in και δεν είναι αυτόματα διαθέσιμο για αυθαίρετες εργασίες παρασκηνίου, επομένως η απουσία προώθησης μπορεί να κάνει μια πραγματική αλληλεπίδραση αόρατη.<sup>[[17]](#references)[[19]](#references)</sup>

### Εντοπίστε την ίδια δυναμική προσπέλαση σε κάθε εκτέλεση

Μην κάνετε replay με βάση μια συγκεκριμένη heap address, η οποία μπορεί να αλλάζει μετά από κάθε allocation, ή μόνο με βάση μια instruction address, η οποία είναι αμφίσημη μέσα σε helpers όπως τα `memcpy()` και `spin_lock()`. Το MAccConc χρησιμοποιεί ένα **count-augmented stack trace**: κάθε frame προσδιορίζει έναν callee και τον αριθμό κλήσης του μέσα στον caller, ενώ το τελευταίο στοιχείο προσδιορίζει την εντολή memory access. Οι εγγραφές εισόδου/εξόδου συναρτήσεων του SanitizerCoverage επιτρέπουν στο userspace να ανακατασκευάσει αυτό το δυναμικό αναγνωριστικό, το οποίο παραμένει σταθερό παρά τις αλλαγές διευθύνσεων και τον άσχετο θόρυβο στη ροή ελέγχου.<sup>[[17]](#references)</sup>

### Μετατρέψτε τα υποψήφια ζεύγη σε εξαναγκασμένα schedules

Το patched ioctl `KCOV_SET_DI` συσχετίζει ένα αναγνωριστικό προσπέλασης count-augmented με μια ενέργεια shared-flag.<sup>[[17]](#references)</sup>

| Ενέργεια | Σημασιολογία |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Ορίζει τη σημαία *N* αμέσως πριν από την επιλεγμένη προσπέλαση. |
| `DI_STACK_WAIT` | Πριν από την επιλεγμένη προσπέλαση, περιμένει σε spin μέχρι να οριστεί η σημαία *N* ή να λήξει το διαμορφωμένο όριο. |
| `DI_STACK_WAKE_POST` | Ορίζει τη σημαία *N* αμέσως μετά την επιλεγμένη προσπέλαση. |

Για έναν μερικό περιορισμό **A-happens-before-B**, αντιστοιχίστε το `DI_STACK_WAKE_POST` στο A και το `DI_STACK_WAIT` στο B, χρησιμοποιώντας την ίδια σημαία. Για ένα πλήρως καθορισμένο schedule δύο contexts, ξεκινήστε με το B σε αναμονή και έπειτα κάντε το A να ξυπνήσει το B και να περιμένει στο πρώτο σημείο μεταφοράς· το B εκτελεί την αντίστροφη ενέργεια στην επόμενη μεταφορά. Το δεύτερο λειτουργεί σαν ντετερμινιστική εναλλαγή context και χρησιμοποιείται από τον αυτόματο εξερευνητή A-B-A.<sup>[[17]](#references)</sup>

Μια ελάχιστη campaign είναι να μεταγλωττίσετε το test case με τα τέσσερα hooks (`test_setup`, δύο thread functions και `test_end`) ως shared library, να συλλέξετε ένα trace χωρίς περιορισμούς και έπειτα να απαριθμήσετε υποψήφια A-B-A ή να προσθέσετε χειροκίνητους περιορισμούς γύρω από ύποπτες προσπελάσεις.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Ερμήνευε τα timeouts ξεχωριστά από τις επιτυχημένες αναδιατάξεις: η ζητούμενη σειρά μπορεί να είναι αδύνατη, επειδή ένα lock ή μια εξάρτηση αρχικοποίησης/δημοσίευσης εμποδίζει το δεύτερο context να φτάσει στο σημείο injection. Έχε επίσης υπόψη τα τυφλά σημεία του KASAN: οι άμεσες προσπελάσεις στη στοίβα συνήθως δεν καλύπτονται από hooks, εκτός αν υπάρχει πιθανότητα να είναι εκτός ορίων, τα globals παραλείπονται με τη βελτιστοποίηση από προεπιλογή και οι τρέχοντες compilers δεν μπορούν να εκπέμπουν ταυτόχρονα hooks ASAN και TSAN. Τέλος, το prototype χάνει το buffer του KCOV όταν ένα guest πανικοβάλλεται, οπότε διατήρησε μια ανεξάρτητη crash console/oracle.<sup>[[17]](#references)</sup>

Για μελλοντικό concurrency-guided fuzzing, κατέγραφε περιλήψεις προσπελάσεων μνήμης ανά input ή syscall, ζευγοποίησε λειτουργίες που θα σχημάτιζαν σημεία επικοινωνίας μεταξύ contexts και, στη συνέχεια, εξερεύνησε μόνο αυτούς τους συνδυασμούς. Τα VM snapshots σταθεροποιούν την καθολική κατάσταση και τις διευθύνσεις· χωρίς snapshots, τα metadata των allocation sites μπορούν να αφαιρούν την εξάρτηση των αντικειμένων από τις εκτελέσεις. Αυτή είναι μια προτεινόμενη επέκταση, όχι χαρακτηριστικό των τρεχόντων userspace tools του MAccConc.<sup>[[17]](#references)</sup>

## Ενδοσκόπηση Harness: Εντόπισε νωρίς τα ρηχά fuzzers

Όταν μια campaign κολλάει, το πρόβλημα συχνά δεν είναι ο mutator αλλά το **harness**. Χρησιμοποίησε **ενδοσκόπηση reachability/coverage** για να εντοπίσεις συναρτήσεις που είναι στατικά προσπελάσιμες από τον fuzz target, αλλά σπάνια ή ποτέ δεν καλύπτονται δυναμικά. Αυτές οι συναρτήσεις συνήθως υποδεικνύουν ένα από τα εξής τρία προβλήματα.<sup>[[12]](#references)</sup>

- Το harness εισέρχεται στον target πολύ αργά ή πολύ νωρίς.
- Από το seed corpus λείπει μια ολόκληρη οικογένεια λειτουργιών.
- Ο target χρειάζεται πραγματικά ένα **δεύτερο harness** αντί για ένα υπερβολικά μεγάλο harness που «τα κάνει όλα».

Αν χρησιμοποιείς workflows τύπου OSS-Fuzz / ClusterFuzz, το Fuzz Introspector μπορεί να συγκρίνει το στατικό reachability με το runtime coverage και να δημιουργεί αναφορές από μια εκτέλεση με χρονικό περιορισμό ή από ένα δημόσιο corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Χρησιμοποιήστε την αναφορά για να αποφασίσετε αν θα προσθέσετε νέο harness για μια μη δοκιμασμένη διαδρομή parser, θα επεκτείνετε το corpus για ένα συγκεκριμένο feature ή θα χωρίσετε ένα μονολιθικό harness σε μικρότερα entry points.

## Επιλογή στόχων Fuzzing με προτεραιότητα στο γράφημα και διαλογή μεταλλάξεων

Αν έχετε ήδη ευρήματα **static analysis**, **survivors από mutation testing** και **αναφορές κάλυψης**, μην τα διαχειρίζεστε ως ανεξάρτητες λίστες. Δημιουργήστε πρώτα ένα **γράφημα κλήσεων**, προσθέστε στους κόμβους επισημάνσεις για την **κυκλωματική πολυπλοκότητα**, την **προσβασιμότητα από entry points/μη έμπιστες εισόδους** και τυχόν εξωτερικά ευρήματα, και έπειτα εξετάστε ερωτήματα για το γράφημα.<sup>[[5]](#references)[[6]](#references)</sup>

- Ποιες συναρτήσεις υψηλής πολυπλοκότητας είναι προσβάσιμες από μη έμπιστες εισόδους;
- Ποια mutation survivors βρίσκονται σε διαδρομές από parsers/handlers προς κώδικα κρίσιμο για την ασφάλεια;
- Ποιες συναρτήσεις είναι αρχιτεκτονικά σημεία συμφόρησης με ασυνήθιστα μεγάλο **blast radius**;

Αυτό συνήθως αναδεικνύει καλύτερους στόχους για fuzzing από την απλή επιλογή βάσει «χαμηλότερης κάλυψης». Ένας parser/decoder με **υψηλή πολυπλοκότητα** και επιβεβαιωμένη **εξωτερική προσβασιμότητα** αποτελεί ισχυρότερο υποψήφιο για harness από έναν απομονωμένο εσωτερικό βοηθητικό κώδικα με χαμηλή κάλυψη, αλλά χωρίς διαδρομή ελεγχόμενη από επιτιθέμενο.

### Πρακτική ροή εργασίας διαλογής

1. Δημιουργήστε ένα **γράφημα κώδικα** από το codebase και εξαγάγετε μετρικές πολυπλοκότητας/διακλαδώσεων ανά συνάρτηση.
2. Καταγράψτε τα **entry points** που δέχονται είσοδο ελεγχόμενη από επιτιθέμενο: request handlers, decoders, importers, protocol parsers, CLI/file readers.
3. Εκτελέστε ερωτήματα διαδρομών από αυτά τα entry points προς υποψήφιες συναρτήσεις, ώστε να διαχωρίσετε την προσβάσιμη επιφάνεια επίθεσης από τον ανενεργό ή αποκλειστικά εσωτερικό κώδικα.
4. Δώστε προτεραιότητα σε κόμβους που συνδυάζουν:
   - υψηλή **κυκλωματική πολυπλοκότητα**
   - επιβεβαιωμένη **προσβασιμότητα από μη έμπιστη είσοδο**
   - μεγάλο **blast radius** ή πολλούς εξαρτώμενους κόμβους downstream
   - επιβεβαιωτικά στοιχεία, όπως ευρήματα **SARIF**, σημειώσεις ελέγχου ή mutation survivors
5. Γράψτε πρώτα εστιασμένα harnesses για τους κόμβους με την υψηλότερη βαθμολογία, ειδικά για **parsers/codecs**, όπως hex/Base64/IP/message decoders.

### Mutation survivors: ισοδύναμα ή αξιοποιήσιμα

Το mutation testing συχνά παράγει μια θορυβώδη λίστα survivors. Πριν θεωρήσετε κάθε survivor κενό ασφαλείας, χρησιμοποιήστε το γράφημα για να εξετάσετε τα εξής:

- Είναι η μεταλλαγμένη συνάρτηση προσβάσιμη από entry point που ελέγχεται από επιτιθέμενο;
- Περιορίζονται όλες οι διαδρομές κλήσεων από ισχυρότερα invariants από εκείνον τον έλεγχο που μεταλλάχθηκε;
- Βρίσκεται ο κόμβος σε ανενεργό κώδικα, σε λογική αποκλειστικά μορφοποίησης ή σε διαδρομή αριθμητικής/parser με μεγάλο αντίκτυπο;

Οι survivors που παραμένουν απρόσιτοι ή περιορίζονται δομικά είναι συχνά **ισοδύναμοι mutants**. Οι survivors που παραμένουν **προσβάσιμοι** και αφορούν **οριακές συνθήκες**, **διαδρομές overflow/carry** ή **αριθμητική/ανάλυση κρίσιμη για την ασφάλεια** θα πρέπει να προωθούνται σε:

- νέα fuzz harnesses
- άμεσα property/invariant tests
- στοχευμένα διανύσματα edge cases

### Συσχετίστε εξωτερικά ευρήματα με το γράφημα

Αν το pipeline SAST εξάγει **SARIF**, αντιστοιχίστε τα ευρήματα στους κόμβους του γραφήματος με βάση το **αρχείο + το εύρος γραμμών** και χρησιμοποιήστε το γράφημα για να επεκτείνετε την εκτίμηση αντίκτυπου.<sup>[[6]](#references)</sup>

- υπολογίστε το **blast radius** της επισημασμένης συνάρτησης
- ελέγξτε αν το εύρημα βρίσκεται σε οποιαδήποτε διαδρομή από entry point
- ομαδοποιήστε κοντινά ευρήματα που συγκλίνουν στο ίδιο σημείο συμφόρησης

Αυτό είναι χρήσιμο όταν αποφασίζετε αν αξίζει να αφιερώσετε χρόνο σε fuzzing μιας συγκεκριμένης συνάρτησης: ένας κόμβος που είναι **προσβάσιμος**, **πολύπλοκος** και έχει ήδη ευρήματα **SAST** είναι συχνά καλύτερος στόχος από έναν απλώς πολύπλοκο κόμβο χωρίς διαδρομή από επιτιθέμενο.

Παράδειγμα ροής εργασίας με το Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Η σημαντική μεθοδολογία βρίσκεται στην τομή: **πολυπλοκότητα x έκθεση x αντίκτυπος**. Χρησιμοποιήστε το γράφημα για να επιλέξετε στόχους fuzzing με την υψηλότερη αναμενόμενη αξία ασφάλειας και, στη συνέχεια, χρησιμοποιήστε τις μεταλλάξεις που επιβιώνουν για να καθορίσετε ποια όρια και invariants πρέπει να δοκιμάζει εντατικά το harness σας.<sup>[[5]](#references)</sup>

## Differential fuzzing κωδικοποιήσεων κρυπτογραφικών κλειδιών

Ξεκινήστε από έγκυρα σειριοποιημένα κλειδιά ή τυπικά διανύσματα δοκιμών. Μεταλλάξτε τα κωδικοποιημένα πεδία χωρίς να αλλοιώσετε το μήκος και τη δομή που απαιτούνται για να φτάσετε στις διαδρομές εισαγωγής και λειτουργιών και, στη συνέχεια, υποβάλετε τα ίδια bytes σε ανεξάρτητες υλοποιήσεις. Συγκρίνετε την αποδοχή και τα σφάλματα. Οι τυχαιοποιημένες υπογραφές και τα κρυπτοκείμενα χρειάζονται oracle ορθότητας, όχι σύγκριση byte προς byte: επαληθεύστε τις υπογραφές ή συγκρίνετε τα κοινόχρηστα μυστικά σε έναν κύκλο encapsulation/decapsulation. Τα διανύσματα δοκιμών επιβεβαιώνουν τη συμμόρφωση για γνωστές περιπτώσεις· η διαφορική μετάλλαξη ανιχνεύει κακοσχηματισμένες κωδικοποιήσεις πέρα από αυτές.<sup>[[23]](#references)[[26]](#references)</sup>

Για αυτές τις μορφές κλειδιών, χρησιμοποιήστε ειδικά oracle για κάθε μορφή:<sup>[[24]](#references)[[25]](#references)[[26]](#references)</sup>

- **Εκτεταμένα κλειδιά υπογραφής ML-DSA:** τροποποιήστε τους packed συντελεστές `s1` ή `s2` ώστε να βρίσκονται εκτός του `[-η, η]`, διατηρώντας το κλειδί αναλύσιμο. Ελέγξτε αν η εισαγωγή ή η υπογραφή απορρίπτεται και αν επαληθεύεται οποιαδήποτε υπογραφή που προκύπτει. Οι διαφορές στην αποδοχή από μόνες τους δεν συνιστούν παραβιάσεις προτύπων, επειδή το FIPS 204 δεν επιβάλλει πρόσθετους ελέγχους ιδιωτικού κλειδιού. Δείτε τον [μηχανισμό conditional leakage](../crypto/public-key/#malformed-ml-dsa-signing-keys-and-rejection-sampling-leakage).
- **Ζεύγη κλειδιών ML-KEM:** διαχωρίστε τους απαιτούμενους ελέγχους του κλειδιού encapsulation και της εισόδου decapsulation από τον προαιρετικό έλεγχο συνέπειας ζεύγους (PCT) κατά την εισαγωγή ενός ζεύγους. Κάντε encapsulate με το δημόσιο κλειδί του, κάντε decapsulate με το ιδιωτικό κλειδί του και συγκρίνετε τα κοινόχρηστα μυστικά· μια ασυμφωνία μπορεί να διακόψει την κρυπτογραφημένη επικοινωνία, ακόμη κι όταν τα επιμέρους κλειδιά περνούν τους ελέγχους εισόδου. Ελέγξτε αν το API επικυρώνει τις εισόδους κατά τη λειτουργία ή μέσω ξεχωριστής κλήσης· το libcrux παρέχει τις `validate_public_key(pk)` και `validate_private_key(sk, ct)`, οι οποίες δεν αντικαθιστούν ένα PCT.
- **Ακατέργαστα κλειδιά XMSS/XMSSMT:** δοκιμάστε round trips σειριοποίησης κλειδιών **υπογραφής και επαλήθευσης** σε διαφορετικά σύνολα παραμέτρων, όχι μόνο λειτουργίες με κλειδιά στη μνήμη. Τα XMSS και XMSSMT έχουν ξεχωριστά namespaces OID τεσσάρων byte, επομένως ένας parser που ελέγχει μόνο το OID και δοκιμάζει πρώτα το XMSS μπορεί να ταξινομήσει εσφαλμένα ένα κλειδί XMSSMT με OID που συγκρούεται και να απορρίψει την εισαγωγή. Ο parser RustCrypto που αναφέρθηκε αποτελεί παράδειγμα αστοχίας διαλειτουργικότητας/διαθεσιμότητας, όχι πλαστογράφησης υπογραφής.

## Go Fuzzing με gosentry: Ισχυρότερη μηχανή, τυποποιημένες είσοδοι και διαφορικοί έλεγχοι

Αν ένας στόχος Go διαθέτει ήδη ένα εγγενές harness `testing.F`, μια πρακτική διαδρομή αναβάθμισης είναι να εκτελέσετε το ίδιο harness με το [gosentry](https://github.com/trailofbits/gosentry), ένα fork του Go toolchain που διατηρεί το `go test -fuzz`, αλλά αλλάζει το backend σε **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Αυτό είναι χρήσιμο όταν ο native Go fuzzer κολλάει σε **δύσκολες συγκρίσεις**, **τυποποιημένες εισόδους** ή **μορφές με απαιτητικούς parser**. Η μεθοδολογία παραμένει ίδια:

- Συνεχίστε να χρησιμοποιείτε το `f.Add(...)` για seeds και το `f.Fuzz(...)` για το callback.
- Επαναχρησιμοποιήστε το ίδιο harness, αλλά εκτελέστε το με το δυαδικό αρχείο `go` του gosentry αντί για το stock toolchain.
- Αντιμετωπίστε την εκστρατεία που προκύπτει ως κανονικό coverage-guided run, αλλά με scheduling/mutation από το LibAFL και καλύτερους υποστηρικτικούς detectors.

### Μετατρέψτε τις σιωπηλές αποτυχίες σε ευρήματα fuzzing

Ένα επαναλαμβανόμενο πρόβλημα στις αξιολογήσεις Go είναι ότι η επικίνδυνη συμπεριφορά συχνά **δεν** προκαλεί crash από προεπιλογή. Με το gosentry, μπορείτε να μετατρέψετε διάφορες κατηγορίες «κακής αλλά σιωπηλής» συμπεριφοράς σε ευρήματα.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` για να κάνετε επιλεγμένες διαδρομές logging/error να συμπεριφέρονται σαν crashes (χρήσιμο για διαδρομές κώδικα τύπου `log.Fatal` που διαφορετικά απλώς κάνουν log και συνεχίζουν).
- `--catch-races=true` για να επανεκτελείτε τις νέες εγγραφές της ουράς που ανακαλύφθηκαν με τον Go race detector.
- `--catch-leaks=true` για να επανεκτελείτε νέες εγγραφές της ουράς με το `goleak` και να διακόπτετε την εκτέλεση σε περίπτωση διαρροών goroutine.
- Διαχείριση hang από το LibAFL, ώστε οι **ατέρμονοι βρόχοι / πολύ αργές είσοδοι** να παραμένουν ευρήματα fuzzing αντί να χάνονται ως timeouts.
- Ενσωματωμένοι έλεγχοι arithmetic overflow από προεπιλογή, καθώς και προαιρετικοί έλεγχοι truncation μέσω instrumentation τύπου go-panikint.

Αυτό είναι ιδιαίτερα χρήσιμο για targets όπου ο αντίκτυπος στην ασφάλεια είναι μια **αποτυχία parser χωρίς panic**, ένα **σφάλμα συγχρονισμού** ή ένα **hang που προκαλεί μόνο DoS**, αντί για αλλοίωση μνήμης.

### Fuzzing με επίγνωση των struct για τυποποιημένα Go API

Το native Go fuzzing αναμένει κυρίως scalars όπως `[]byte`, `string` και αριθμούς. Αν ο κώδικας υπό δοκιμή καταναλώνει τυποποιημένα αντικείμενα, το gosentry μπορεί να κάνει fuzzing απευθείας σε **σύνθετες τιμές** (structs, slices, arrays, pointers), ενώ εξακολουθεί να μεταβάλλει bytes στο παρασκήνιο.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Χρησιμοποιήστε το όταν η δημιουργία ενός ψεύτικου wire format μόνο για fuzzing θα έκρυβε λογικά σφάλματα πίσω από κώδικα parsing που υπάρχει μόνο στο harness. Για καμπάνιες differential ή βάσει γραμματικής, κρατήστε την είσοδο του harness ως ένα μόνο `[]byte` ή `string` και κάντε parsing μέσα στο callback.

### Fuzzing βάσει γραμματικής για parsers και εισόδους πρωτοκόλλων

Για parsers, μορφότυπα και γλώσσες εισόδου, το gosentry μπορεί να εκτελέσει **fuzzing γραμματικής Nautilus** πάνω από το LibAFL. Η γραμματική είναι ένας πίνακας JSON με κανόνες παραγωγής και το harness συνήθως θα πρέπει να δέχεται ένα μόνο όρισμα `[]byte` ή `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Σημειώσεις μεθοδολογίας:

- Χρησιμοποιήστε grammar mode όταν οι μεταλλάξεις σε επίπεδο byte αποτυγχάνουν κυρίως στους πρώιμους ελέγχους σύνταξης.
- Περιορίστε τη γραμματική στο **υποσύνολο της γλώσσας/του πρωτοκόλλου που σχετίζεται με την ασφάλεια**, αντί να μοντελοποιήσετε ολόκληρη την προδιαγραφή.
- Χρησιμοποιήστε μεγάλες οριακές τιμές σε terminals/nonterminals για να δοκιμάσετε τα όρια ακεραίων, μήκους και μηχανών καταστάσεων.
- Το grammar mode διατηρεί τις εισόδους έγκυρες ως προς τη γραμματική, αλλά ο στόχος εξακολουθεί να λαμβάνει **bytes/strings**· επομένως, η ανάλυση και οι σημασιολογικοί έλεγχοι εξακολουθούν να εκτελούνται μέσα στον κώδικα που έχει ενσωματωθεί στο harness.

### Differential fuzzing: σύγκριση υλοποιήσεων, όχι μόνο crashes

Ένα ισχυρό μοτίβο για τα οικοσυστήματα Go είναι το **grammar-based differential fuzzing**: δημιουργήστε έγκυρες δομημένες εισόδους και τροφοδοτήστε τις σε δύο parsers, clients ή μηχανές μεταβάσεων καταστάσεων.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Αντιμετωπίστε τα παρακάτω ως ευρήματα:

- η μία υλοποίηση κάνει panic, ενώ η άλλη απορρίπτει καθαρά
- ασυμφωνίες ως προς τα input που γίνονται αποδεκτά ή απορρίπτονται
- διαφορετικά parse trees ή αποκωδικοποιημένα αντικείμενα
- αποκλίνουσες μεταβάσεις κατάστασης, nonces, υπόλοιπα ή state roots

Αυτός είναι ένας πρακτικός τρόπος να εντοπίζετε **ασυμφωνίες συναίνεσης**, **ασάφειες parser** και **αποκλίσεις μεταξύ προδιαγραφών και υλοποίησης**, τις οποίες συχνά δεν εντοπίζει το απλό crash fuzzing.

### Επαναχρησιμοποιήστε το corpus της καμπάνιας για αναφορές κάλυψης

Μετά από μια καμπάνια, επαναλάβετε το corpus της αποθηκευμένης ουράς για να δημιουργήσετε μια αναφορά κάλυψης Go, χωρίς να εξαγάγετε χειροκίνητα ξεχωριστό corpus.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Εκτελέστε την εντολή από το **ίδιο package** και με τον **ίδιο στόχο `-fuzz`**, ώστε το gosentry να επιλύσει τη σωστή αποθηκευμένη κατάσταση campaign.
