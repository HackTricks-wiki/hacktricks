## Mutational Grammar Fuzzing: покриття vs. семантика

У **mutational grammar fuzzing** входи мутуються, водночас залишаючись **граматично коректними**. У режимі, керованому покриттям, до корпусу додаються лише зразки, що забезпечують **нове покриття**. Для **мовних цілей** (парсерів, інтерпретаторів, рушіїв) це може не виявити помилки, для яких потрібні **ланцюжки семантичних залежностей/потоку даних**, де результат одного конструкта стає входом іншого.<sup>[[1]](#references)</sup>

**Режим збою:** fuzzer знаходить зразки, які окремо задіюють `document()` і `generate-id()` (або подібні примітиви), але **не зберігає ланцюжок потоку даних**, тож зразок, «ближчий до помилки», відкидається, бо не збільшує покриття. За наявності **3+ залежних кроків** випадкова рекомбінація стає затратною, а зворотний зв’язок про покриття не спрямовує пошук.<sup>[[1]](#references)</sup>

**Висновок:** для граматик із великою кількістю залежностей варто розглянути **поєднання мутаційного та генеративного етапів** або надавати перевагу шаблонам **ланцюжків функцій** (а не лише покриттю).<sup>[[1]](#references)</sup>

## Підводні камені різноманітності корпусу

Мутація, керована покриттям, **жадібна**: зразок із новим покриттям одразу зберігається, часто з великими незміненими ділянками. З часом корпуси перетворюються на **майже дублікати** з низькою структурною різноманітністю. Агресивна мінімізація може видалити корисний контекст, тож практичний компроміс — **мінімізація з урахуванням граматики**, яка **зупиняється після досягнення мінімального порогу токенів** (зменшує шум, зберігаючи достатньо навколишньої структури для зручної мутації).<sup>[[1]](#references)</sup>

Практичне правило формування корпусу для мутаційного fuzzing: **віддавати перевагу невеликому набору структурно різних початкових зразків із максимальним покриттям**, а не великій купі майже дублікатів. Зазвичай це означає таке.<sup>[[1]](#references)[[3]](#references)</sup>

- Починайте з **зразків із реального світу** (публічних корпусів, даних вебсканування, перехопленого трафіку, наборів файлів з екосистеми цілі).
- Скорочуйте їх за допомогою **мінімізації корпусу на основі покриття**, а не зберігайте кожен коректний зразок.
- Зберігайте початкові зразки **достатньо малими**, щоб мутації припадали на значущі поля, а не витрачали більшість циклів на нерелевантні байти.
- Повторно мінімізуйте корпус після значних змін harness або інструментування, оскільки «найкращий» корпус змінюється разом зі змінами досяжності.

## Мутація з урахуванням порівнянь для магічних значень

Поширена причина, через яку fuzzer перестає покращувати результати, — не синтаксис, а **жорсткі порівняння**: магічні байти, перевірки довжини, рядки enum, контрольні суми або значення диспетчеризації парсера, захищені `memcmp`, таблицями switch чи каскадними порівняннями. Чиста випадкова мутація марнує цикли, намагаючись вгадати ці значення байт за байтом.

Для таких цілей використовуйте **трасування порівнянь** (наприклад, `CMPLOG` в AFL++ або процеси на кшталт Redqueen), щоб fuzzer міг спостерігати операнди невдалих порівнянь і спрямовувати мутації до значень, які їх проходять.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Практичні нотатки:**

- Це особливо корисно, коли ціль приховує складну логіку за **сигнатурами файлів**, **дієсловами протоколу**, **тегами типів** або **бітами функцій, залежними від версії**.
- Поєднуйте це зі **словниками**, отриманими з реальних зразків, специфікацій протоколів або журналів налагодження. Невеликий словник із токенами граматики, назвами блоків, дієсловами та роздільниками часто цінніший за величезний універсальний список слів.
- Якщо ціль виконує багато послідовних перевірок, спочатку розв’яжіть найперші порівняння «магічних» значень, а потім знову мінімізуйте отриманий корпус, щоб наступні етапи починалися з уже коректних префіксів.

## Багатший зворотний зв’язок, коли покриття ребер об’єднує різні шляхи

Звичайне покриття ребер не дає змоги розрізнити два виконання, що проходять через той самий helper із різних місць виклику або обирають різні комбінації гілок усередині функції. Це важливо для спільних декодерів, диспетчерів протоколів і helper-функцій інтерпретаторів, де **шлях** до ребра визначає поточний стан. Наївне відстеження кожного контексту виклику також небезпечне: карта покриття та черга можуть розростися надмірно. Тому дослідження з контекстно-чутливого fuzzing рекомендують уточнювати лише перспективні контексти, а не робити контекстно-чутливим увесь граф викликів.<sup>[[14]](#references)</sup>

Новіші збірки AFL++ підтримують **покриття шляхів у функціях за Ball-Larus** на додачу до звичайного покриття ребер. Воно призначає ознаку кожному ациклічному шляху через функцію; зворотні ребра циклів вилучаються, тож цей зворотний зв’язок розрізняє комбінації гілок, але **не кількість ітерацій циклу**. Почніть із помірного рівня `1`, а суворіші режими застосовуйте лише до підозрілого коду парсерів і машин станів, оскільки кількість шляхів може зростати експоненційно.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Для хелпера, який викликається з багатьох критично важливих для безпеки місць, режим LTO може об’єднати шлях виконання кожної функції з її безпосереднім місцем виклику:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Рекомендації щодо кампанії:** обережно застосовуйте зворотний зв’язок із більшою деталізацією та стежте за витратами на карту покриття й чергу.<sup>[[13]](#references)[[14]](#references)</sup>

- Паралельно запустіть звичайний екземпляр із покриттям гілок; зворотний зв’язок із більшою деталізацією корисний, лише якщо додаткові витрати на чергу й карту не знижують кількість виконань за секунду.
- Використовуйте `AFL_LLVM_ALLOWLIST`, щоб обмежити інструментування шляхів/викликачів, якщо великі бібліотеки з інтенсивним використанням шаблонів або універсальний код утиліт займають більшу частину карти.
- Функції з надмірною кількістю ациклічних шляхів можна пропускати в AFL++; попередження під час компіляції свідчать, що для цілі потрібно налаштувати allowlist або вибрати менш суворий рівень.
- Покриття викликачів і шляхів підтримує лише один рівень виклику. Не поєднуйте його зі стеками контексту більшої глибини.
- ID шляхів можуть змінюватися між основними версіями LLVM. Зафіксуйте toolchain на час кампанії та не синхронізуйте корпуси на основі PATH так, ніби їхні ID ознак стабільні між збірками.
- Цей зворотний зв’язок доповнює `CMPLOG`: трасування порівнянь допомагає визначити, **яке значення проходить перевірку**, тоді як зворотний зв’язок щодо шляхів/викликачів зберігає інформацію про те, **який маршрут і комбінація гілок привели до неї**.

## Stateful Fuzzing: послідовності — це seed-файли

Для **протоколів**, **автентифікованих робочих процесів** і **багатоетапних парсерів** цікавою одиницею часто є не окремий двійковий блок, а **послідовність повідомлень**. Об’єднувати весь обмін в один файл і хаотично його змінювати зазвичай неефективно, оскільки fuzzer змінює кожен крок однаково, навіть якщо лише пізніше повідомлення приводить до вразливого стану.<sup>[[4]](#references)</sup>

Ефективніший підхід — вважати **саму послідовність seed-файлом** і використовувати **спостережуваний стан** (коди відповідей, стани протоколу, фази парсера, типи повернених об’єктів) як додатковий зворотний зв’язок.<sup>[[4]](#references)</sup>

- Зберігайте **коректні повідомлення-префікси** незмінними й зосередьте мутації на повідомленні, що **визначає перехід**.
- Кешуйте ідентифікатори та значення, згенеровані сервером у попередніх відповідях, якщо вони потрібні для наступного кроку.
- Віддавайте перевагу мутації/злиттю окремих повідомлень, а не мутації всього серіалізованого обміну як непрозорого блоба.
- Якщо протокол надає значущі коди відповідей, використовуйте їх як **простий оракул стану**, щоб надавати пріоритет послідовностям, які просуваються далі.

Саме тому помилки автентифікації, приховані переходи чи помилки парсерів, що виникають «лише після рукостискання», часто не виявляються під час звичайного fuzzing файлів: fuzzer має зберігати **порядок, стан і залежності**, а не лише структуру.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing драйвера з кількома клієнтами

Високе покриття гілок усе одно може не виявити помилки IPC-драйвера, оскільки покриття не описує **володіння об’єктами, лічильники посилань, повідомлення в очікуванні, порядок очищення чи чергування потоків**. На сторінці [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) описано модель об’єктів драйвера; цей приклад зосереджено на harness для fuzzer. Android Binder — корисна модель: недостатньо пройти шляхи виділення й звільнення пам’яті, якщо fuzzer не може змусити кілька процесів працювати з одним об’єктом ядра в потрібному порядку.<sup>[[15]](#references)</sup>

#### Моделюйте протокол, а не окремі буфери `ioctl`

Подайте тестовий випадок як упорядковану граматику з **ідентичності клієнта + операції + структурованих аргументів**. У Binder LKL fuzzer використовує protobuf і `libprotobuf-mutator`, а також одного постійного клієнта-менеджера контексту й двох звичайних клієнтів. Семантичний harness зберігає зв’язки, які зруйнувала б сліпа мутація байтів.<sup>[[15]](#references)</sup>

- Кешуйте значення, повернуті попередніми операціями. Наприклад, `BC_FREE_BUFFER` має повторно використовувати вказівник на буфер транзакції, повернутий попереднім викликом `ioctl`.
- Генеруйте коректні відповіді за замовчуванням, щоб синхронні транзакції могли завершитися, а наступні операції залишалися доступними.
- Відхиляйте неможливі переходи, наприклад транзакції клієнта до самого себе або кілька транзакцій в очікуванні для однієї цілі.
- Зберігайте одноразовий стан початкової ініціалізації поза скиданням стану для кожного входу. Binder дозволяє лише одну реєстрацію `BINDER_SET_CONTEXT_MGR` за час роботи системи, тому повторне знищення та створення цього клієнта робило б наступні входи некоректними.

Корисний шаблон для гонки життєвого циклу: один клієнт передає об’єкт, запускається очищення потоку або процесу, а клієнт-отримувач паралельно звільняє буфер транзакції. У прикладі CVE-2020-0423 передавання `BINDER_TYPE_WEAK_BINDER`, за яким ішов `BINDER_THREAD_EXIT` у гонці з `BC_FREE_BUFFER`, могло звільнити вбудований `binder_work`, поки шлях очищення потоку, що завершувався, усе ще його використовував.<sup>[[15]](#references)</sup>

#### Відновіть контрольоване чергування в ядрі userspace

[Linux Kernel Library (LKL)](https://github.com/lkl/linux) компонує реальний код ядра з harness у userspace та надає доступ до його інтерфейсу системних викликів через `lkl_syscall`. Завдяки цьому стан protobuf, покриття й KASAN легко координувати в одному процесі. Однак зазвичай LKL виконує системний виклик без переривання іншим потоком ядра. Для кампаній із пошуку гонок вставте точки виклику `schedule()` біля вибраних меж блокування/розблокування та життєвого циклу, а потім дозвольте harness випадково вибирати наступного клієнта в кожній точці передачі керування. Ретельно добирайте ці точки, оскільки кожна з них збільшує простір пошуку розкладів. Рандомізований планувальник, описаний дослідниками, **не входить** до upstream Binder fuzzer.<sup>[[15]](#references)</sup>

#### Створюйте й повторно відтворюйте серіалізовані регресійні seed-файли

В upstream harness зафіксовано сумісну версію `libprotobuf-mutator`, увімкнено інструментування LKL для fuzzing і KASAN через `LKL_FUZZING=1`, а також увімкнено `CONFIG_MMU` для Binder за допомогою `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Після переходу на навмисно вразливу ревізію або застосування задокументованих upstream патчів відкату серіалізований seed може відтворити весь перехід стану між кількома клієнтами без його реконструкції в саморобному proof of concept на C:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Вважайте отриманий KASAN use-after-free підтвердженням того, що seed досяг вразливого шляху життєвого циклу. Це **не** демонструє наявність пізніших примітивів, необхідних для виконання коду ядра або підвищення привілеїв.<sup>[[16]](#references)</sup>

## Трюк із різноманітністю на одній машині (у стилі Jackalope)

Практичний спосіб поєднати **генеративну новизну** з **повторним використанням покриття** — це **перезапускати короткоживучі воркери** для роботи з постійним сервером. Кожен воркер починає з порожнього корпусу, синхронізується через `T` секунд, працює ще `T` секунд з об’єднаним корпусом, знову синхронізується, а потім завершує роботу. Так **кожне покоління отримує свіжі структури**, водночас використовуючи накопичене покриття.<sup>[[1]](#references)[[2]](#references)</sup>

**Сервер:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Послідовні виконавці (приклад циклу):**

<details>
<summary>Цикл перезапуску worker Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Примітки:**

- `-in empty` примусово створює **новий corpus** під час кожної генерації.
- `-server_update_interval T` приблизно імітує **відкладену синхронізацію** (спочатку нові знахідки, потім повторне використання).
- У режимі grammar fuzzing **початкова синхронізація із сервером** пропускається за замовчуванням (параметр `-skip_initial_server_sync` не потрібен).
- Оптимальне значення `T` **залежить від цілі**; найкраще зазвичай перемикатися після того, як worker знайде більшість покриття, яке легко досягти.

## Snapshot Fuzzing для цілей, які складно охопити harness

Коли код, який потрібно тестувати, стає доступним лише **після тривалого налаштування** (завантаження VM, завершення входу, отримання пакета, розбір контейнера, ініціалізація сервісу), корисною альтернативою є **snapshot fuzzing**: збережіть стан готового процесу або VM, передайте кожен тестовий випадок у цільовий шлях введення, виконуйте його до crash/timeout і відновіть snapshot. Так не доведеться повторювати ініціалізацію або префікси протоколу; цей підхід корисний для **мережевих сервісів**, **firmware**, **поверхонь атаки після автентифікації** та **цілей лише з бінарними файлами**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Запустіть ціль, доки не буде готовий потрібний стан.
2. Створіть snapshot **пам’яті та регістрів** у цей момент.
3. Для кожного тестового випадку запишіть мутований ввід безпосередньо у відповідний буфер guest/process.
4. Виконуйте до crash/timeout/reset.
5. Відновіть snapshot; для цілей на VM, якщо це підтримується, відновлюйте лише **брудні сторінки**, а потім повторюйте.

Розмістіть snapshot якомога ближче до першого затратного етапу розбору або диспетчеризації, наприклад після `recv`/`read` чи десеріалізації пакета, і зафіксуйте буфер введення, який використовує ціль. Це відповідає принципу адаптивного розміщення: переміщуйте snapshot глибше в обробку вводу, щоб уникнути повторення роботи.<sup>[[11]](#references)</sup>

## Інтроспекція harness: рано виявляйте поверхневі fuzzers

Якщо кампанія зупинилася, проблема часто полягає не в mutator, а в **harness**. Використовуйте **інтроспекцію досяжності/покриття**, щоб знайти функції, які статично досяжні з fuzz target, але рідко або ніколи не покриваються динамічно. Такі функції зазвичай вказують на одну з трьох проблем.<sup>[[12]](#references)</sup>

- Harness входить у ціль надто пізно або надто рано.
- У seed corpus бракує цілої групи функцій.
- Цілі справді потрібен **другий harness**, а не один надмірно великий harness, який «робить усе».

Якщо ви використовуєте робочі процеси на кшталт OSS-Fuzz / ClusterFuzz, Fuzz Introspector може порівнювати статичну досяжність із покриттям під час виконання та створювати звіти за результатами запуску з обмеженням часу або на основі загальнодоступного corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Скористайтеся звітом, щоб вирішити, чи додавати новий harness для неперевіреного шляху парсера, розширити корпус для певної функції чи розділити монолітний harness на менші точки входу.

## Вибір цілей для fuzzing на основі графа та аналіз результатів мутацій

Якщо у вас уже є **результати статичного аналізу**, **мутації, що пережили тестування**, і **звіти про покриття**, не аналізуйте їх як незалежні списки. Спершу побудуйте **граф викликів**, а потім анотуйте його вузли **цикломатичною складністю**, **досяжністю з точок входу/недовіреного вводу** та наявними зовнішніми знахідками, після чого ставте запитання про граф.<sup>[[5]](#references)[[6]](#references)</sup>

- Які функції з високою складністю досяжні з недовіреного вводу?
- Які мутації, що пережили тестування, містяться на шляхах від парсерів/обробників до критичного для безпеки коду?
- Які функції є архітектурними вузькими місцями з надзвичайно великим **радіусом впливу**?

Зазвичай це допомагає виявити кращі цілі для fuzzing, ніж орієнтація лише на «найнижче покриття». Парсер/декодер із **високою складністю** та підтвердженою **досяжністю ззовні** є кращим кандидатом для harness, ніж ізольований внутрішній допоміжний засіб зі слабким покриттям, але без шляху, контрольованого зловмисником.

### Практичний робочий процес аналізу

1. Побудуйте **граф коду** на основі кодової бази та отримайте метрики складності/гілок для кожної функції.
2. Перелічіть **точки входу**, що приймають дані, контрольовані зловмисником: обробники запитів, декодери, засоби імпорту, парсери протоколів, засоби читання CLI/файлів.
3. Виконайте запити до графа для пошуку шляхів від цих точок входу до функцій-кандидатів, щоб відокремити доступну поверхню атаки від недосяжного/лише внутрішнього коду.
4. Визначте пріоритетність вузлів, що поєднують:
   - високу **цикломатичну складність**
   - підтверджену **досяжність із недовіреного вводу**
   - великий **радіус впливу** або багато залежних від них вузлів
   - підтверджувальні свідчення, як-от знахідки **SARIF**, нотатки аудиту або мутації, що пережили тестування
5. Спершу напишіть цільові harness для вузлів із найвищими оцінками, особливо для **парсерів/кодеків**, як-от декодерів hex/Base64/IP/повідомлень.

### Мутації, що пережили тестування: еквівалентні чи практично значущі

Мутаційне тестування часто дає зашумлений список мутацій, що пережили тестування. Перш ніж вважати кожну з них прогалиною в безпеці, скористайтеся графом, щоб з’ясувати:

- Чи досяжна мутована функція з точки входу, контрольованої зловмисником?
- Чи обмежують усі шляхи викликів сильніші інваріанти, ніж перевірка, яку було змінено?
- Чи міститься вузол у недосяжному коді, логіці лише форматування або на шляху критичної для безпеки арифметики/парсингу?

Мутації, що залишаються недосяжними або структурно обмеженими, часто є **еквівалентними мутантами**. Мутації, що залишаються **досяжними** та зачіпають **граничні умови**, **шляхи переповнення/перенесення** або **критичну для безпеки арифметику/парсинг**, слід додати до:

- нових fuzz harness
- прямих тестів властивостей/інваріантів
- цільових наборів граничних векторів

### Нанесіть зовнішні знахідки на граф

Якщо ваш конвеєр SAST експортує **SARIF**, нанесіть знахідки на вузли графа за **файлом + діапазоном рядків** і скористайтеся графом, щоб визначити масштаб впливу.<sup>[[6]](#references)</sup>

- обчисліть **радіус впливу** позначеної функції
- перевірте, чи є знахідка на шляху від будь-якої точки входу
- згрупуйте близько розташовані знахідки, що зводяться до одного вузького місця

Це допомагає вирішити, чи варто витрачати час на fuzzing певної функції: вузол, який є **досяжним**, **складним** і вже має **знахідки SAST**, часто є кращою ціллю, ніж просто складний вузол без шляху від зловмисника.

Приклад робочого процесу з Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Важлива методологія — це перетин: **складність x доступність x вплив**. Використовуйте граф, щоб вибрати цілі для fuzzing із найвищою очікуваною цінністю для безпеки, а потім використовуйте мутації, що вижили, щоб визначити, які межі та інваріанти має перевіряти ваш harness.<sup>[[5]](#references)</sup>

## Go Fuzzing із gosentry: потужніший рушій, типізовані входи та диференційні перевірки

Якщо ціль на Go вже має нативний harness `testing.F`, практичний шлях оновлення — запускати той самий harness за допомогою [gosentry](https://github.com/trailofbits/gosentry), форка toolchain Go, який зберігає `go test -fuzz`, але замінює бекенд на **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Це корисно, коли вбудований Go fuzzer застрягає на **складних порівняннях**, **типізованих входах** або форматах із великою кількістю логіки парсингу. Методологія залишається незмінною:

- Продовжуйте використовувати `f.Add(...)` для початкових значень і `f.Fuzz(...)` для callback-функції.
- Повторно використовуйте той самий harness, але запускайте його за допомогою бінарного файла `go` від gosentry замість стандартного toolchain.
- Розглядайте отриману кампанію як звичайний coverage-guided запуск, але з плануванням/мутацією LibAFL і кращими супровідними детекторами.

### Перетворення непомітних збоїв на знахідки fuzzing

Поширена проблема під час оцінювання Go-коду полягає в тому, що небезпечна поведінка часто **не** спричиняє аварійного завершення за замовчуванням. За допомогою gosentry можна перетворити кілька типів «поганих, але непомітних» станів на знахідки.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` змушує вибрані шляхи логування/обробки помилок поводитися як аварійні збої (корисно для шляхів коду на кшталт `log.Fatal`, які інакше лише записують повідомлення й продовжують роботу).
- `--catch-races=true` повторно перевіряє щойно знайдені елементи черги за допомогою Go race detector.
- `--catch-leaks=true` повторно перевіряє нові елементи черги за допомогою `goleak` і зупиняється в разі витоку goroutine.
- Обробка зависань у LibAFL дає змогу зберігати **нескінченні цикли / дуже повільні входи** як знахідки fuzzing, а не втрачати їх через тайм-аути.
- Вбудовані перевірки арифметичного переповнення за замовчуванням, а також необов’язкові перевірки обрізання за допомогою інструментування у стилі go-panikint.

Це особливо корисно для цілей, де вплив на безпеку полягає в **помилці парсера без panic**, **помилці конкурентного виконання** або **зависанні, що спричиняє лише DoS**, а не в пошкодженні пам’яті.

### Fuzzing із підтримкою структур для типізованих Go API

Вбудований Go fuzzing переважно очікує скалярні значення, як-от `[]byte`, `string` і числа. Якщо код, що тестується, отримує типізовані об’єкти, gosentry може виконувати fuzzing безпосередньо для **композитних значень** (структур, зрізів, масивів, вказівників), водночас мутуючи байти на нижчому рівні.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Використання цього під час створення фіктивного wire format лише для fuzzing приховало б логічні помилки за кодом розбору, наявним лише в harness. Для differential кампаній або кампаній на основі граматики залишайте вхідні дані harness одним `[]byte` або `string` і виконуйте розбір усередині callback.

### Fuzzing на основі граматики для парсерів і протокольних даних

Для парсерів, форматів і мов введення gosentry може запускати **Nautilus grammar fuzzing** поверх LibAFL. Граматика — це JSON-масив правил продукції, а harness зазвичай має приймати один аргумент `[]byte` або `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Нотатки з методології:

- Використовуйте режим граматики, коли мутації на рівні байтів переважно відсіюються під час ранніх синтаксичних перевірок.
- Зосередьте граматику на **підмножині мови/протоколу, важливій для безпеки**, а не моделюйте всю специфікацію.
- Використовуйте великі граничні значення в терміналах/нетерміналах, щоб перевірити межі цілих чисел, довжин і скінченних автоматів.
- Режим граматики зберігає коректність вхідних даних відповідно до граматики, але ціль усе одно отримує **байти/рядки**, тому розбір і семантичні перевірки залишаються всередині коду, охопленого harness.

### Диференційне fuzzing: порівнюйте реалізації, а не лише збої

Для екосистем Go ефективним підходом є **диференційне fuzzing на основі граматики**: генеруйте коректні структуровані вхідні дані й передавайте їх двом парсерам, клієнтам або рушіям переходів станів.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Вважайте такими результатами:

- одна реалізація викликає panic, а інша коректно відхиляє вхідні дані
- невідповідності між прийнятими й відхиленими вхідними даними
- різні дерева розбору або декодовані об’єкти
- розбіжності в переходах стану, nonce, балансах або коренях стану

Це практичний спосіб знаходити **консенсусні невідповідності**, **неоднозначність парсера** та **розбіжності між специфікацією і реалізацією**, які часто не виявляються звичайним fuzzing на збої.

### Повторно використовуйте corpus кампанії для звіту про покриття

Після кампанії повторно запустіть збережений corpus черги, щоб створити звіт про покриття Go, не експортуючи окремий corpus вручну.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Запускайте команду з **того самого пакета** й з тією самою ціллю `-fuzz`, щоб gosentry знайшов правильний стан кешованої кампанії.
