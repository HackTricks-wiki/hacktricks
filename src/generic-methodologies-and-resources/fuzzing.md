## Mutational Grammar Fuzzing: Coverage έναντι Σημασιολογίας

Στο **mutational grammar fuzzing**, οι είσοδοι μεταλλάσσονται, παραμένοντας **έγκυρες ως προς τη γραμματική**. Σε λειτουργία coverage-guided, αποθηκεύονται ως corpus seeds μόνο τα δείγματα που ενεργοποιούν **νέο coverage**. Για **language targets** (parsers, interpreters, engines), αυτό μπορεί να παραβλέψει bugs που απαιτούν **αλυσίδες σημασιολογίας/dataflow**, όπου η έξοδος μιας κατασκευής γίνεται είσοδος μιας άλλης.<sup>[[1]](#references)</sup>

**Τρόπος αποτυχίας:** ο fuzzer βρίσκει seeds που ενεργοποιούν μεμονωμένα τα `document()` και `generate-id()` (ή παρόμοια primitives), αλλά **δεν διατηρεί το συνδεδεμένο dataflow**, με αποτέλεσμα να απορρίπτεται το δείγμα που είναι «πιο κοντά στο bug», επειδή δεν προσθέτει coverage. Με **3+ εξαρτώμενα βήματα**, ο τυχαίος ανασυνδυασμός γίνεται δαπανηρός και η ανατροφοδότηση από το coverage δεν καθοδηγεί την αναζήτηση.<sup>[[1]](#references)</sup>

**Συνέπεια:** για γραμματικές με πολλές εξαρτήσεις, εξετάστε το ενδεχόμενο **συνδυασμού των mutational και generative φάσεων** ή της ενίσχυσης της παραγωγής μοτίβων **function chaining** (και όχι μόνο του coverage).<sup>[[1]](#references)</sup>

## Παγίδες στην Ποικιλομορφία του Corpus

Η καθοδηγούμενη από coverage μετάλλαξη είναι **άπληστη**: ένα δείγμα που προσθέτει νέο coverage αποθηκεύεται αμέσως, συχνά διατηρώντας μεγάλα αμετάβλητα τμήματα. Με τον καιρό, τα corpora γεμίζουν με **σχεδόν πανομοιότυπα δείγματα** και έχουν μικρή δομική ποικιλομορφία. Η επιθετική ελαχιστοποίηση μπορεί να αφαιρέσει χρήσιμο πλαίσιο, επομένως ένας πρακτικός συμβιβασμός είναι η **ελαχιστοποίηση με επίγνωση της γραμματικής**, η οποία **σταματά όταν επιτευχθεί ένα ελάχιστο όριο tokens** (μειώνει τον θόρυβο, διατηρώντας αρκετή περιβάλλουσα δομή ώστε οι μεταλλάξεις να παραμένουν αποτελεσματικές).<sup>[[1]](#references)</sup>

Ένας πρακτικός κανόνας για το corpus στο mutational fuzzing είναι: **προτιμήστε ένα μικρό σύνολο δομικά διαφορετικών seeds που μεγιστοποιούν το coverage** αντί για ένα μεγάλο πλήθος σχεδόν πανομοιότυπων δειγμάτων. Στην πράξη, αυτό συνήθως σημαίνει τα εξής.<sup>[[1]](#references)[[3]](#references)</sup>

- Ξεκινήστε από **δείγματα πραγματικού κόσμου** (δημόσια corpora, crawling, καταγεγραμμένη κίνηση, σύνολα αρχείων από το οικοσύστημα του target).
- Περιορίστε τα με **ελαχιστοποίηση corpus βάσει coverage**, αντί να κρατάτε κάθε έγκυρο δείγμα.
- Διατηρήστε τα seeds **αρκετά μικρά**, ώστε οι μεταλλάξεις να στοχεύουν ουσιαστικά πεδία και να μη σπαταλούν τους περισσότερους κύκλους σε άσχετα bytes.
- Επαναλάβετε την ελαχιστοποίηση του corpus μετά από σημαντικές αλλαγές στο harness/instrumentation, επειδή το «καλύτερο» corpus αλλάζει όταν αλλάζει το reachability.

## Μετάλλαξη με Επίγνωση Συγκρίσεων για Magic Values

Ένας συνηθισμένος λόγος που οι fuzzers φτάνουν σε τέλμα δεν είναι η σύνταξη, αλλά οι **αυστηρές συγκρίσεις**: magic bytes, έλεγχοι μήκους, strings enum, checksums ή τιμές dispatch του parser, που ελέγχονται μέσω `memcmp`, switch tables ή διαδοχικών συγκρίσεων. Η καθαρά τυχαία μετάλλαξη σπαταλά κύκλους προσπαθώντας να μαντέψει αυτές τις τιμές byte προς byte.

Για αυτά τα targets, χρησιμοποιήστε **comparison tracing** (για παράδειγμα, workflows τύπου AFL++ `CMPLOG` / Redqueen), ώστε ο fuzzer να μπορεί να παρατηρεί τους τελεστέους αποτυχημένων συγκρίσεων και να κατευθύνει τις μεταλλάξεις προς τιμές που τις ικανοποιούν.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Πρακτικές σημειώσεις:**

- Αυτό είναι ιδιαίτερα χρήσιμο όταν ο στόχος κρύβει βαθύτερη λογική πίσω από **υπογραφές αρχείων**, **ρήματα πρωτοκόλλου**, **tags τύπου** ή **bits χαρακτηριστικών που εξαρτώνται από την έκδοση**.
- Συνδύασέ το με **λεξικά** που έχουν εξαχθεί από πραγματικά δείγματα, προδιαγραφές πρωτοκόλλων ή αρχεία καταγραφής debug. Ένα μικρό λεξικό με tokens γραμματικής, ονόματα chunks, ρήματα και οριοθέτες είναι συχνά πιο χρήσιμο από μια τεράστια, γενική wordlist.
- Αν ο στόχος εκτελεί πολλούς διαδοχικούς ελέγχους, επίλυσε πρώτα τις αρχαιότερες συγκρίσεις “magic” και έπειτα ελαχιστοποίησε ξανά το corpus που προκύπτει, ώστε τα επόμενα στάδια να ξεκινούν από ήδη έγκυρα prefixes.

## Πλουσιότερο Feedback Όταν το Edge Coverage Συγχωνεύει Διαφορετικές Διαδρομές

Το κανονικό edge coverage δεν μπορεί να διακρίνει δύο εκτελέσεις που περνούν από τον ίδιο helper μέσω διαφορετικών callers ή ακολουθούν διαφορετικούς συνδυασμούς branches μέσα σε μια συνάρτηση. Αυτό έχει σημασία σε κοινόχρηστους decoders, dispatchers πρωτοκόλλων και helpers interpreters, όπου η **διαδρομή** προς ένα edge καθορίζει την ενεργή κατάσταση. Η αφελής παρακολούθηση κάθε context κλήσης είναι επίσης επικίνδυνη: ο χάρτης κάλυψης και η ουρά μπορεί να διογκωθούν υπερβολικά. Γι’ αυτό, η έρευνα για context-sensitive fuzzing συνιστά να βελτιώνεις μόνο τα υποσχόμενα contexts, αντί να αντιμετωπίζεις ολόκληρο το γράφημα κλήσεων ως context-sensitive.<sup>[[14]](#references)</sup>

Οι πρόσφατες εκδόσεις του AFL++ παρέχουν **κάλυψη διαδρομών ανά συνάρτηση Ball-Larus**, επιπλέον του κανονικού edge coverage. Αναθέτει ένα feature σε κάθε άκυκλη διαδρομή μέσα σε μια συνάρτηση· οι ακμές επιστροφής βρόχων αφαιρούνται, οπότε αυτό το feedback διακρίνει συνδυασμούς branches, αλλά **όχι τον αριθμό επαναλήψεων των βρόχων**. Ξεκίνα με το χαλαρό επίπεδο `1` και, στη συνέχεια, περιόρισε τις αυστηρότερες λειτουργίες σε ύποπτο κώδικα parser/state machine, επειδή ο αριθμός των διαδρομών μπορεί να αυξηθεί εκθετικά.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Για μια βοηθητική συνάρτηση που καλείται από πολλά σημεία κρίσιμα για την ασφάλεια, η λειτουργία LTO μπορεί να συνδυάσει τη διαδρομή κάθε συνάρτησης με το άμεσο σημείο κλήσης της:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Οδηγίες καμπάνιας:** εφαρμόστε πιο πλούσιο feedback με φειδώ και παρακολουθείτε το κόστος του coverage map/queue.<sup>[[13]](#references)[[14]](#references)</sup>

- Εκτελέστε παράλληλα μια συνηθισμένη instance edge coverage· το πιο πλούσιο feedback είναι χρήσιμο μόνο αν το επιπλέον κόστος queue/map δεν μειώνει υπερβολικά τις εκτελέσεις ανά δευτερόλεπτο.
- Χρησιμοποιήστε το `AFL_LLVM_ALLOWLIST` για να περιορίσετε το path/caller instrumentation όταν μεγάλες βιβλιοθήκες με πολλά templates ή γενικός κώδικας βοηθητικών συναρτήσεων κυριαρχούν στο map.
- Οι συναρτήσεις με υπερβολικά πολλά acyclic paths μπορούν να παραλείπονται από το AFL++· οι προειδοποιήσεις κατά τη μεταγλώττιση υποδεικνύουν ότι ο στόχος χρειάζεται allowlisting ή λιγότερο αυστηρό επίπεδο.
- Το caller + path coverage υποστηρίζει μόνο ένα επίπεδο caller. Μην το συνδυάζετε με βαθύτερα context stacks.
- Τα path IDs μπορεί να αλλάξουν μεταξύ major εκδόσεων του LLVM. Κρατήστε σταθερό το toolchain καθ' όλη τη διάρκεια μιας καμπάνιας και μην συγχρονίζετε corpora που βασίζονται σε PATH σαν τα feature IDs τους να παρέμεναν σταθερά μεταξύ builds.
- Αυτό το feedback συμπληρώνει το `CMPLOG`: το comparison tracing επιλύει το **ποια τιμή περνά έναν guard**, ενώ το path/caller feedback διατηρεί το **ποια διαδρομή και ποιος συνδυασμός branches οδήγησαν σε αυτόν**.

## Stateful Fuzzing: Οι ακολουθίες είναι seeds

Για **protocols**, **authenticated workflows** και **multi-stage parsers**, η ενδιαφέρουσα μονάδα συχνά δεν είναι ένα μεμονωμένο blob αλλά μια **ακολουθία μηνυμάτων**. Η συνένωση ολόκληρου του transcript σε ένα αρχείο και η τυφλή μετάλλαξή του είναι συνήθως αναποτελεσματική, επειδή ο fuzzer μεταλλάσσει κάθε βήμα εξίσου, ακόμη κι όταν μόνο το μεταγενέστερο μήνυμα φτάνει στην ευάλωτη κατάσταση.<sup>[[4]](#references)</sup>

Μια πιο αποτελεσματική προσέγγιση είναι να αντιμετωπίζετε την **ίδια την ακολουθία ως seed** και να χρησιμοποιείτε την **παρατηρήσιμη κατάσταση** (κωδικούς απόκρισης, καταστάσεις protocol, φάσεις parser, τύπους αντικειμένων που επιστρέφονται) ως πρόσθετο feedback.<sup>[[4]](#references)</sup>

- Διατηρείτε σταθερά τα **έγκυρα μηνύματα προθέματος** και εστιάζετε τις μεταλλάξεις στο μήνυμα που **οδηγεί στη μετάβαση**.
- Αποθηκεύετε identifiers και τιμές που δημιουργεί ο server από προηγούμενες αποκρίσεις, όταν το επόμενο βήμα εξαρτάται από αυτά.
- Προτιμάτε μετάλλαξη/splicing ανά μήνυμα αντί να μεταλλάσσετε ολόκληρο το σειριοποιημένο transcript ως αδιαφανές blob.
- Αν το protocol παρέχει ουσιαστικούς κωδικούς απόκρισης, χρησιμοποιήστε τους ως **φθηνό state oracle** για να δίνετε προτεραιότητα στις ακολουθίες που προχωρούν βαθύτερα.

Για τον ίδιο λόγο, bugs σε authenticated λειτουργίες, κρυφές μεταβάσεις ή parser bugs που εμφανίζονται «μόνο μετά το handshake» συχνά διαφεύγουν από το vanilla file-style fuzzing: ο fuzzer πρέπει να διατηρεί τη **σειρά, την κατάσταση και τις εξαρτήσεις**, όχι μόνο τη δομή.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing driver με πολλούς clients

Το υψηλό edge coverage μπορεί και πάλι να χάσει bugs στον IPC driver, επειδή το coverage δεν περιγράφει **την ιδιοκτησία αντικειμένων, τις μετρήσεις αναφορών, τα εκκρεμή μηνύματα, τη σειρά εκκαθάρισης ή τις αλληλοδιαπλοκές νημάτων**. Η σελίδα [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) καλύπτει το μοντέλο αντικειμένων του driver· αυτό το παράδειγμα εστιάζει στο harness του fuzzer. Το Android Binder είναι χρήσιμο μοντέλο: δεν αρκεί να φτάσει κανείς τόσο στις διαδρομές allocation όσο και στις διαδρομές free, αν ο fuzzer δεν μπορεί να κάνει πολλαπλές διεργασίες να λειτουργήσουν στο ίδιο kernel object με την απαιτούμενη σειρά.<sup>[[15]](#references)</sup>

#### Μοντελοποιήστε το protocol, όχι μεμονωμένα buffers `ioctl`

Αναπαραστήστε ένα test case ως διατεταγμένη γραμματική από **ταυτότητα client + λειτουργία + δομημένα ορίσματα**. Ο Binder LKL fuzzer χρησιμοποιεί protobuf και `libprotobuf-mutator`, με έναν επίμονο client διαχειριστή context και δύο συνηθισμένους clients. Έπειτα, ένα semantic harness διατηρεί τις σχέσεις που η τυφλή μετάλλαξη bytes θα κατέστρεφε.<sup>[[15]](#references)</sup>

- Αποθηκεύετε τιμές που επιστρέφονται από προηγούμενες λειτουργίες. Για παράδειγμα, το `BC_FREE_BUFFER` πρέπει να επαναχρησιμοποιεί έναν δείκτη transaction buffer που επιστράφηκε από προηγούμενο `ioctl`.
- Δημιουργείτε έγκυρες προεπιλεγμένες απαντήσεις ώστε να ολοκληρώνονται οι synchronous συναλλαγές και να παραμένουν προσβάσιμες οι επόμενες λειτουργίες.
- Απορρίπτετε αδύνατες μεταβάσεις, όπως συναλλαγές προς τον ίδιο τον client ή πολλαπλές εκκρεμείς συναλλαγές προς τον ίδιο στόχο.
- Διατηρείτε την κατάσταση singleton bootstrap έξω από την επαναφορά ανά input. Το Binder επιτρέπει μόνο μία εγγραφή `BINDER_SET_CONTEXT_MGR` ανά boot, επομένως η επανειλημμένη καταστροφή και επαναδημιουργία αυτού του client θα καθιστούσε άκυρα τα επόμενα inputs.

Ένα χρήσιμο πρότυπο race συνθηκών διάρκειας ζωής είναι να μεταφέρει ένας client ένα αντικείμενο, να ξεκινήσει η εκκαθάριση ενός thread ή process και, ταυτόχρονα, ο client που λαμβάνει το αντικείμενο να αποδεσμεύσει το transaction buffer. Στο παράδειγμα CVE-2020-0423, η μεταφορά ενός `BINDER_TYPE_WEAK_BINDER` και στη συνέχεια το `BINDER_THREAD_EXIT` που ανταγωνίζεται το `BC_FREE_BUFFER` μπορούσαν να αποδεσμεύσουν ένα ενσωματωμένο `binder_work`, ενώ η διαδρομή εκκαθάρισης του thread που τερματιζόταν εξακολουθούσε να το χρησιμοποιεί.<sup>[[15]](#references)</sup>

#### Επαναφέρετε ελεγχόμενες αλληλοδιαπλοκές σε kernel userspace

Η [Linux Kernel Library (LKL)](https://github.com/lkl/linux) συνδέει τον πραγματικό κώδικα του kernel σε ένα userspace harness και εκθέτει τη διεπαφή syscall μέσω του `lkl_syscall`. Έτσι, ο συντονισμός protobuf state, coverage και KASAN γίνεται εύκολα σε μία διεργασία. Ωστόσο, το LKL συνήθως εκτελεί ένα syscall χωρίς να το διακόπτει κάποιο άλλο kernel thread. Για race campaigns, εισαγάγετε σημεία `schedule()` γύρω από επιλεγμένα όρια lock/unlock και διάρκειας ζωής και, στη συνέχεια, αφήστε το harness να επιλέγει τυχαία τον επόμενο client σε κάθε yield. Κρατήστε αυτά τα σημεία στοχευμένα, επειδή το καθένα πολλαπλασιάζει τον χώρο αναζήτησης του scheduling. Ο randomized scheduler που περιγράφουν οι ερευνητές **δεν** αποτελεί μέρος του upstream Binder fuzzer.<sup>[[15]](#references)</sup>

#### Δημιουργήστε και επαναλάβετε serialized regression seeds

Το upstream harness καρφιτσώνει μια συμβατή έκδοση του `libprotobuf-mutator`, ενεργοποιεί το LKL fuzzing instrumentation και το KASAN με `LKL_FUZZING=1` και ενεργοποιεί το `CONFIG_MMU` για το Binder με `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Αφού κάνετε checkout μιας σκόπιμα ευάλωτης αναθεώρησης ή εφαρμόσετε τα rollback patches που τεκμηριώνονται upstream, ένα σειριοποιημένο seed μπορεί να αναπαράγει ολόκληρη τη μετάβαση κατάστασης πολλών clients, χωρίς να χρειάζεται να την ανακατασκευάσετε σε ένα ad-hoc C proof of concept:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Αντιμετωπίστε το KASAN use-after-free που προέκυψε ως επιβεβαίωση ότι το seed έφτασε στη διαδρομή ευάλωτου κύκλου ζωής. Δεν αποδεικνύει τα μεταγενέστερα primitives που απαιτούνται για εκτέλεση κώδικα στον kernel ή κλιμάκωση προνομίων.<sup>[[16]](#references)</sup>

## Single-Machine Diversity Trick (Jackalope-Style)

Ένας πρακτικός τρόπος να συνδυάσετε τη **δημιουργία νέων δεδομένων** με την **επαναχρησιμοποίηση κάλυψης** είναι να επανεκκινείτε workers μικρής διάρκειας απέναντι σε έναν persistent server. Κάθε worker ξεκινά με άδειο corpus, συγχρονίζεται μετά από T δευτερόλεπτα, εκτελείται για άλλα T δευτερόλεπτα πάνω στο συνδυασμένο corpus, συγχρονίζεται ξανά και μετά τερματίζεται. Έτσι προκύπτουν **νέες δομές σε κάθε γενιά**, ενώ παράλληλα αξιοποιείται η συσσωρευμένη κάλυψη.<sup>[[1]](#references)[[2]](#references)</sup>

**Server:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Διαδοχικοί workers (παράδειγμα βρόχου):**

<details>
<summary>Βρόχος επανεκκίνησης worker του Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Σημειώσεις:**

- Το `-in empty` επιβάλλει **νέο corpus** σε κάθε generation.
- Το `-server_update_interval T` προσεγγίζει **καθυστερημένο συγχρονισμό** (πρώτα νέα ευρήματα, μετά επαναχρησιμοποίηση).
- Στη λειτουργία grammar fuzzing, ο **αρχικός συγχρονισμός με τον server παραλείπεται από προεπιλογή** (δεν χρειάζεται το `-skip_initial_server_sync`).
- Το βέλτιστο `T` **εξαρτάται από τον στόχο**· συνήθως αποδίδει καλύτερα η αλλαγή αφού ο worker έχει βρει το μεγαλύτερο μέρος της «εύκολης» κάλυψης.

## Snapshot Fuzzing για στόχους που είναι δύσκολο να υποβληθούν σε harness

Όταν ο κώδικας που θέλετε να δοκιμάσετε γίνεται προσβάσιμος μόνο **μετά από μεγάλο κόστος αρχικοποίησης** (εκκίνηση VM, ολοκλήρωση σύνδεσης, λήψη packet, parsing container, αρχικοποίηση service), μια χρήσιμη εναλλακτική είναι το **snapshot fuzzing**: καταγράψτε την έτοιμη κατάσταση της διεργασίας ή της VM, εισαγάγετε κάθε test case στη διαδρομή εισόδου του στόχου, εκτελέστε μέχρι να προκύψει crash/timeout και επαναφέρετε το snapshot. Έτσι αποφεύγεται η επανάληψη της αρχικοποίησης ή των προθεμάτων του πρωτοκόλλου και είναι χρήσιμο για **network services**, **firmware**, **attack surfaces μετά την αυθεντικοποίηση** και **binary-only στόχους**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Εκτελέστε τον στόχο μέχρι να είναι έτοιμη η ενδιαφέρουσα κατάσταση.
2. Αποθηκεύστε **τη μνήμη + τους registers** εκείνη τη στιγμή.
3. Για κάθε test case, γράψτε το μεταλλαγμένο input απευθείας στο σχετικό buffer της guest/διεργασίας.
4. Εκτελέστε μέχρι να προκύψει crash/timeout/reset.
5. Επαναφέρετε το snapshot· για στόχους VM, επαναφέρετε μόνο τις **dirty pages**, εφόσον υποστηρίζεται, και επαναλάβετε.

Τοποθετήστε το snapshot όσο πιο κοντά είναι πρακτικά δυνατό στο πρώτο δαπανηρό βήμα parsing/dispatch, όπως μετά από ένα `recv`/`read` ή ένα σημείο αποσειριοποίησης packet, και καταγράψτε το input buffer που χρησιμοποιεί ο στόχος. Αυτό ακολουθεί την αρχή της προσαρμοστικής τοποθέτησης, δηλαδή τη μετακίνηση του snapshot βαθύτερα στην επεξεργασία εισόδου για να αποφευχθεί η επανάληψη εργασιών.<sup>[[11]](#references)</sup>

## Ενδοσκόπηση Harness: Εντοπίστε έγκαιρα τα επιφανειακά fuzzers

Όταν μια καμπάνια κολλάει, συχνά το πρόβλημα δεν είναι ο mutator αλλά το **harness**. Χρησιμοποιήστε **ενδοσκόπηση προσβασιμότητας/κάλυψης** για να εντοπίσετε συναρτήσεις που είναι στατικά προσβάσιμες από τον fuzz στόχο σας, αλλά καλύπτονται σπάνια ή καθόλου κατά την εκτέλεση. Αυτές οι συναρτήσεις συνήθως υποδεικνύουν ένα από τρία προβλήματα.<sup>[[12]](#references)</sup>

- Το harness εισέρχεται στον στόχο πολύ αργά ή πολύ νωρίς.
- Από το seed corpus λείπει μια ολόκληρη οικογένεια λειτουργιών.
- Ο στόχος χρειάζεται πράγματι **δεύτερο harness**, αντί για ένα υπερβολικά μεγάλο harness που «τα κάνει όλα».

Αν χρησιμοποιείτε workflows τύπου OSS-Fuzz / ClusterFuzz, το Fuzz Introspector μπορεί να συγκρίνει τη στατική προσβασιμότητα με την κάλυψη κατά την εκτέλεση και να δημιουργεί αναφορές από μια χρονομετρημένη εκτέλεση ή ένα δημόσιο corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Χρησιμοποιήστε την αναφορά για να αποφασίσετε αν θα προσθέσετε ένα νέο harness για μια μη δοκιμασμένη διαδρομή parser, θα επεκτείνετε το corpus για μια συγκεκριμένη λειτουργία ή θα χωρίσετε ένα μονολιθικό harness σε μικρότερα σημεία εισόδου.

## Επιλογή στόχων Fuzzing με προτεραιότητα το γράφημα και διαλογή μεταλλάξεων

Αν έχετε ήδη ευρήματα από **static analysis**, **mutation testing** και αναφορές κάλυψης, μην τα διαχειρίζεστε ως ανεξάρτητες λίστες. Δημιουργήστε πρώτα ένα **call graph**, προσθέστε στους κόμβους τις τιμές **cyclomatic complexity**, την **προσβασιμότητα από entrypoints/μη έμπιστη είσοδο** και τυχόν εξωτερικά ευρήματα και, στη συνέχεια, θέστε ερωτήματα για το γράφημα.<sup>[[5]](#references)[[6]](#references)</sup>

- Ποιες συναρτήσεις υψηλής πολυπλοκότητας είναι προσβάσιμες από μη έμπιστη είσοδο;
- Ποιοι επιζώντες μεταλλάξεων βρίσκονται σε διαδρομές από parsers/handlers προς κώδικα κρίσιμο για την ασφάλεια;
- Ποιες συναρτήσεις αποτελούν αρχιτεκτονικά choke points με ασυνήθιστα μεγάλο **blast radius**;

Αυτό συνήθως αναδεικνύει καλύτερους στόχους fuzzing από την απλή επιλογή της «χαμηλότερης κάλυψης». Ένας parser/decoder με **υψηλή πολυπλοκότητα** και επιβεβαιωμένη **εξωτερική προσβασιμότητα** είναι ισχυρότερος υποψήφιος για harness από έναν απομονωμένο εσωτερικό helper με χαμηλή κάλυψη αλλά χωρίς διαδρομή που ελέγχεται από επιτιθέμενο.

### Πρακτική ροή εργασίας για τη διαλογή

1. Δημιουργήστε ένα **code graph** από το codebase και εξαγάγετε μετρικές πολυπλοκότητας/διακλαδώσεων ανά συνάρτηση.
2. Καταγράψτε τα **entrypoints** που δέχονται είσοδο ελεγχόμενη από επιτιθέμενο: request handlers, decoders, importers, protocol parsers, CLI/file readers.
3. Εκτελέστε **path queries** από αυτά τα entrypoints προς τις υποψήφιες συναρτήσεις, ώστε να διαχωρίσετε την προσβάσιμη επιφάνεια επίθεσης από τον νεκρό κώδικα ή τον κώδικα που είναι προσβάσιμος μόνο εσωτερικά.
4. Δώστε προτεραιότητα στους κόμβους που συνδυάζουν:
   - υψηλή **cyclomatic complexity**
   - επιβεβαιωμένη **προσβασιμότητα από μη έμπιστη είσοδο**
   - μεγάλο **blast radius** ή πολλούς downstream dependents
   - υποστηρικτικά στοιχεία, όπως ευρήματα **SARIF**, σημειώσεις ελέγχου ή επιζώντες μεταλλάξεων
5. Γράψτε πρώτα εστιασμένα harnesses για τους κόμβους με την υψηλότερη βαθμολογία, ιδιαίτερα για **parsers/codecs**, όπως decoders hex/Base64/IP/message.

### Επιζώντες μεταλλάξεων: ισοδύναμοι ή αξιοποιήσιμοι

Το mutation testing συχνά παράγει μια θορυβώδη λίστα επιζώντων. Πριν θεωρήσετε κάθε επιζών κενό ασφαλείας, χρησιμοποιήστε το γράφημα για να εξετάσετε τα εξής:

- Είναι η μεταλλαγμένη συνάρτηση προσβάσιμη από entrypoint που ελέγχεται από επιτιθέμενο;
- Περιορίζονται όλες οι διαδρομές κλήσεων από ισχυρότερες αμετάβλητες συνθήκες από εκείνες του μεταλλαγμένου ελέγχου;
- Βρίσκεται ο κόμβος σε νεκρό κώδικα, σε λογική που αφορά μόνο τη μορφοποίηση ή σε διαδρομή αριθμητικών πράξεων/parser με μεγάλο αντίκτυπο;

Οι επιζώντες που παραμένουν μη προσβάσιμοι ή περιορίζονται δομικά είναι συχνά **ισοδύναμοι μεταλλάκτες**. Οι επιζώντες που παραμένουν **προσβάσιμοι** και επηρεάζουν **οριακές συνθήκες**, **διαδρομές overflow/carry** ή **αριθμητικές πράξεις/parsing κρίσιμα για την ασφάλεια** θα πρέπει να προωθούνται σε:

- νέα fuzz harnesses
- άμεσα property/invariant tests
- στοχευμένα διανύσματα οριακών περιπτώσεων

### Συσχετίστε τα εξωτερικά ευρήματα με το γράφημα

Αν το SAST pipeline σας εξάγει **SARIF**, αντιστοιχίστε τα ευρήματα στους κόμβους του γραφήματος με βάση το **αρχείο και το εύρος γραμμών** και χρησιμοποιήστε το γράφημα για να επεκτείνετε την εκτίμηση επιπτώσεων.<sup>[[6]](#references)</sup>

- υπολογίστε το **blast radius** της επισημασμένης συνάρτησης
- ελέγξτε αν το εύρημα βρίσκεται σε κάποια διαδρομή από entrypoint
- ομαδοποιήστε κοντινά ευρήματα που καταλήγουν στο ίδιο choke point

Αυτό είναι χρήσιμο όταν αποφασίζετε αν αξίζει να αφιερώσετε χρόνο σε fuzzing μιας συγκεκριμένης συνάρτησης: ένας κόμβος που είναι **προσβάσιμος**, **πολύπλοκος** και έχει ήδη **ευρήματα SAST** είναι συχνά καλύτερος στόχος από έναν απλώς πολύπλοκο κόμβο χωρίς διαδρομή που ελέγχεται από επιτιθέμενο.

Παράδειγμα ροής εργασίας με το Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Η σημαντική μεθοδολογία είναι η τομή: **πολυπλοκότητα x έκθεση x αντίκτυπος**. Χρησιμοποιήστε το γράφημα για να επιλέξετε fuzz targets με τη μεγαλύτερη αναμενόμενη αξία για την ασφάλεια και, στη συνέχεια, χρησιμοποιήστε τους survivors των mutations για να αποφασίσετε ποια όρια και invariants πρέπει να δοκιμάζει εντατικά το harness σας.<sup>[[5]](#references)</sup>

## Go Fuzzing με gosentry: Ισχυρότερος engine, τυποποιημένα inputs και differential checks

Αν ένας στόχος σε Go διαθέτει ήδη ένα native harness `testing.F`, μια πρακτική διαδρομή αναβάθμισης είναι να εκτελέσετε το ίδιο harness με το [gosentry](https://github.com/trailofbits/gosentry), ένα fork του Go toolchain που διατηρεί το `go test -fuzz`, αλλά αλλάζει το backend σε **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Αυτό είναι χρήσιμο όταν ο εγγενής Go fuzzer κολλάει σε **δύσκολες συγκρίσεις**, **τυποποιημένες εισόδους** ή **μορφές με έντονη χρήση parser**. Η μεθοδολογία παραμένει ίδια:

- Συνεχίστε να χρησιμοποιείτε το `f.Add(...)` για seeds και το `f.Fuzz(...)` για το callback.
- Επαναχρησιμοποιήστε το ίδιο harness, αλλά εκτελέστε το με το binary `go` του gosentry αντί για το stock toolchain.
- Αντιμετωπίστε την καμπάνια που προκύπτει ως μια κανονική εκτέλεση με καθοδήγηση από την κάλυψη, αλλά με scheduling/mutation από το LibAFL και καλύτερους συνοδευτικούς detectors.

### Μετατρέψτε τις σιωπηλές αποτυχίες σε ευρήματα από το fuzzing

Ένα επαναλαμβανόμενο πρόβλημα στις αξιολογήσεις Go είναι ότι η επικίνδυνη συμπεριφορά συχνά **δεν** προκαλεί crash από προεπιλογή. Με το gosentry, μπορείτε να μετατρέψετε διάφορες κατηγορίες «κακών αλλά σιωπηλών» καταστάσεων σε ευρήματα.<sup>[[7]](#references)[[8]](#references)</sup>

- Το `--panic-on=pkg.Func,...` κάνει επιλεγμένες διαδρομές logging/error να συμπεριφέρονται σαν crashes (χρήσιμο για διαδρομές κώδικα τύπου `log.Fatal` που διαφορετικά απλώς καταγράφουν το συμβάν και συνεχίζουν).
- Το `--catch-races=true` επανεκτελεί τις νεοανακαλυφθείσες εγγραφές της queue με τον Go race detector.
- Το `--catch-leaks=true` επανεκτελεί τις νέες εγγραφές της queue με το `goleak` και διακόπτει την εκτέλεση αν εντοπιστούν διαρροές goroutine.
- Η διαχείριση hangs του LibAFL διατηρεί τους **άπειρους βρόχους / πολύ αργές εισόδους** ως ευρήματα από το fuzzing, αντί να τους αφήνει να εξαφανίζονται ως timeouts.
- Ενσωματωμένοι έλεγχοι αριθμητικής υπερχείλισης από προεπιλογή, καθώς και προαιρετικοί έλεγχοι truncation μέσω instrumentation τύπου go-panikint.

Αυτό είναι ιδιαίτερα χρήσιμο για στόχους όπου ο αντίκτυπος στην ασφάλεια είναι μια **αποτυχία parser χωρίς panic**, ένα **σφάλμα concurrency** ή ένα **hang που προκαλεί μόνο DoS**, αντί για αλλοίωση μνήμης.

### Fuzzing με επίγνωση δομών για τυποποιημένα Go API

Το εγγενές Go fuzzing αναμένει κυρίως scalars όπως `[]byte`, `string` και αριθμούς. Αν ο κώδικας που ελέγχεται καταναλώνει τυποποιημένα αντικείμενα, το gosentry μπορεί να κάνει fuzz απευθείας σε **σύνθετες τιμές** (structs, slices, arrays, pointers), ενώ συνεχίζει να μεταβάλλει τα υποκείμενα bytes.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Χρησιμοποιήστε το όταν η δημιουργία μιας ψεύτικης μορφής wire μόνο για fuzzing θα έκρυβε λογικά σφάλματα πίσω από κώδικα parsing που χρησιμοποιείται μόνο από το harness. Για καμπάνιες differential ή βασισμένες σε γραμματική, διατηρήστε την είσοδο του harness ως ένα μόνο `[]byte` ή `string` και κάντε parsing μέσα στο callback.

### Fuzzing βασισμένο σε γραμματική για parsers και εισόδους πρωτοκόλλων

Για parsers, formats και γλώσσες εισόδου, το gosentry μπορεί να εκτελέσει **Nautilus grammar fuzzing** πάνω από το LibAFL. Η γραμματική είναι ένας πίνακας JSON με κανόνες παραγωγής, και το harness συνήθως πρέπει να λαμβάνει ένα μόνο όρισμα `[]byte` ή `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Μεθοδολογικές σημειώσεις:

- Χρησιμοποιήστε grammar mode όταν οι μεταλλάξεις σε επίπεδο byte αποτυγχάνουν κυρίως στους πρώιμους ελέγχους σύνταξης.
- Εστιάστε τη γραμματική στο **υποσύνολο της γλώσσας/του πρωτοκόλλου που σχετίζεται με την ασφάλεια**, αντί να μοντελοποιείτε ολόκληρη την προδιαγραφή.
- Χρησιμοποιήστε μεγάλες οριακές τιμές σε terminals/nonterminals για να δοκιμάσετε τα όρια ακεραίων, μήκους και μηχανών καταστάσεων.
- Το grammar mode διατηρεί τις εισόδους έγκυρες ως προς τη γραμματική, αλλά ο στόχος εξακολουθεί να λαμβάνει **bytes/strings**, επομένως η ανάλυση και οι σημασιολογικοί έλεγχοι παραμένουν μέσα στον κώδικα που υποβάλλεται σε harness.

### Differential fuzzing: συγκρίνετε υλοποιήσεις, όχι μόνο crashes

Μια ισχυρή προσέγγιση για τα οικοσυστήματα Go είναι το **grammar-based differential fuzzing**: δημιουργήστε έγκυρες δομημένες εισόδους και τροφοδοτήστε με αυτές δύο parsers, clients ή μηχανές μεταβάσεων κατάστασης.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Αντιμετωπίστε τα εξής ως ευρήματα:

- η μία υλοποίηση κάνει panic, ενώ η άλλη απορρίπτει καθαρά
- ασυμφωνίες μεταξύ αποδεκτών και απορριπτόμενων εισόδων
- διαφορετικά parse trees ή αποκωδικοποιημένα αντικείμενα
- αποκλίνουσες μεταβάσεις κατάστασης, nonces, balances ή state roots

Αυτός είναι ένας πρακτικός τρόπος εντοπισμού **ασυμφωνιών συναίνεσης**, **ασάφειας parser** και **αποκλίσεων μεταξύ προδιαγραφής και υλοποίησης**, τις οποίες συχνά δεν εντοπίζει το fuzzing που ελέγχει μόνο για crashes.

### Επαναχρησιμοποιήστε το corpus της καμπάνιας για αναφορά κάλυψης

Μετά από μια καμπάνια, αναπαράγετε το αποθηκευμένο corpus της ουράς για να δημιουργήσετε μια αναφορά κάλυψης Go, χωρίς να εξαγάγετε χειροκίνητα ξεχωριστό corpus.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Εκτελέστε την εντολή από το **ίδιο package** και με τον **ίδιο στόχο `-fuzz`**, ώστε το gosentry να επιλύσει τη σωστή κατάσταση campaign από την cache.
