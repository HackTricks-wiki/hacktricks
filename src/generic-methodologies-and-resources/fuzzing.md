## Mutational Grammar Fuzzing: Coverage έναντι σημασιολογίας

Στο **mutational grammar fuzzing**, οι είσοδοι μεταλλάσσονται, ενώ παραμένουν **έγκυρες ως προς τη γραμματική**. Στη λειτουργία καθοδηγούμενη από coverage, αποθηκεύονται ως corpus seeds μόνο τα δείγματα που προκαλούν **νέο coverage**. Για **γλωσσικούς στόχους** (parsers, interpreters, engines), έτσι μπορεί να μη βρεθούν bugs που απαιτούν **αλυσίδες σημασιολογίας/ροής δεδομένων**, όπου η έξοδος μιας κατασκευής γίνεται είσοδος μιας άλλης.<sup>[[1]](#references)</sup>

**Τρόπος αποτυχίας:** ο fuzzer βρίσκει seeds που ασκούν μεμονωμένα τις `document()` και `generate-id()` (ή παρόμοια primitives), αλλά **δεν διατηρεί τη συνδεδεμένη ροή δεδομένων**, οπότε το δείγμα που είναι «πιο κοντά στο bug» απορρίπτεται επειδή δεν προσθέτει coverage. Με **3 ή περισσότερα εξαρτώμενα βήματα**, ο τυχαίος ανασυνδυασμός γίνεται δαπανηρός και η ανατροφοδότηση από το coverage δεν καθοδηγεί την αναζήτηση.<sup>[[1]](#references)</sup>

**Συνέπεια:** για γραμματικές με πολλές εξαρτήσεις, εξετάστε το ενδεχόμενο **συνδυασμού mutational και generative φάσεων** ή της ρύθμισης της παραγωγής ώστε να προτιμά μοτίβα **αλυσίδωσης συναρτήσεων** (όχι μόνο το coverage).<sup>[[1]](#references)</sup>

## Παγίδες στην ποικιλομορφία του corpus

Το mutation που καθοδηγείται από coverage είναι **άπληστο**: ένα δείγμα με νέο coverage αποθηκεύεται αμέσως, διατηρώντας συχνά μεγάλες, αμετάβλητες περιοχές. Με τον καιρό, τα corpora γεμίζουν με **σχεδόν πανομοιότυπα** δείγματα και έχουν μικρή δομική ποικιλομορφία. Η επιθετική ελαχιστοποίηση μπορεί να αφαιρέσει χρήσιμο περιβάλλον, οπότε ένας πρακτικός συμβιβασμός είναι η **ελαχιστοποίηση με επίγνωση της γραμματικής**, η οποία **σταματά όταν φτάσει σε ένα ελάχιστο όριο tokens** (μειώνοντας τον θόρυβο, αλλά διατηρώντας αρκετή περιβάλλουσα δομή ώστε να παραμένει κατάλληλη για mutation).<sup>[[1]](#references)</sup>

Ένας πρακτικός κανόνας για corpus σε mutational fuzzing είναι: **προτιμήστε ένα μικρό σύνολο δομικά διαφορετικών seeds που μεγιστοποιούν το coverage** αντί για ένα μεγάλο σύνολο σχεδόν πανομοιότυπων δειγμάτων. Στην πράξη, αυτό συνήθως σημαίνει τα εξής.<sup>[[1]](#references)[[3]](#references)</sup>

- Ξεκινήστε από **δείγματα πραγματικού κόσμου** (δημόσια corpora, crawling, καταγεγραμμένη κίνηση, σύνολα αρχείων από το οικοσύστημα του στόχου).
- Περιορίστε τα με **ελαχιστοποίηση corpus βάσει coverage**, αντί να κρατάτε κάθε έγκυρο δείγμα.
- Διατηρήστε τα seeds **αρκετά μικρά**, ώστε οι μεταλλάξεις να επηρεάζουν ουσιαστικά πεδία και να μη δαπανώνται οι περισσότεροι κύκλοι σε άσχετα bytes.
- Επαναλάβετε την ελαχιστοποίηση του corpus μετά από σημαντικές αλλαγές στο harness ή στα όργανα καταγραφής, επειδή το «καλύτερο» corpus αλλάζει όταν αλλάζει η δυνατότητα προσπέλασης.

## Mutation με επίγνωση των συγκρίσεων για magic values

Ένας συνηθισμένος λόγος που οι fuzzers φτάνουν σε τέλμα δεν είναι η σύνταξη, αλλά οι **αυστηρές συγκρίσεις**: magic bytes, έλεγχοι μήκους, συμβολοσειρές enum, checksums ή τιμές dispatch του parser που ελέγχονται μέσω `memcmp`, πινάκων switch ή αλυσιδωτών συγκρίσεων. Το καθαρά τυχαίο mutation σπαταλά κύκλους προσπαθώντας να μαντέψει αυτές τις τιμές byte προς byte.

Για αυτούς τους στόχους, χρησιμοποιήστε **tracing συγκρίσεων** (για παράδειγμα, ροές εργασίας τύπου AFL++ `CMPLOG` / Redqueen), ώστε ο fuzzer να μπορεί να παρατηρεί τα τελεστέα των αποτυχημένων συγκρίσεων και να κατευθύνει τις μεταλλάξεις προς τιμές που τις ικανοποιούν.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Πρακτικές σημειώσεις:**

- Αυτό είναι ιδιαίτερα χρήσιμο όταν ο στόχος θέτει πύλες στην πρόσβαση σε βαθύτερη λογική μέσω **υπογραφών αρχείων**, **ρημάτων πρωτοκόλλου**, **ετικετών τύπων** ή **bits δυνατοτήτων που εξαρτώνται από την έκδοση**.
- Συνδυάστε το με **λεξικά** που έχουν εξαχθεί από πραγματικά δείγματα, προδιαγραφές πρωτοκόλλων ή αρχεία καταγραφής αποσφαλμάτωσης. Ένα μικρό λεξικό με tokens γραμματικής, ονόματα τμημάτων, ρήματα και διαχωριστικά είναι συχνά πιο χρήσιμο από μια τεράστια γενική wordlist.
- Αν ο στόχος εκτελεί πολλούς διαδοχικούς ελέγχους, επιλύστε πρώτα τις αρχικές συγκρίσεις «magic» και, στη συνέχεια, ελαχιστοποιήστε ξανά το corpus που προκύπτει, ώστε τα επόμενα στάδια να ξεκινούν από προθέματα που είναι ήδη έγκυρα.

## Fuzzing των File APIs που κρύβουν μια γλώσσα filename

Μια παράμετρος με όνομα `filename`, `path` ή `URL` μπορεί να αποτελεί σημείο εισόδου σε interpreter και όχι κυριολεκτική αναζήτηση αρχείου. Για παράδειγμα, το CFITSIO Extended Filename Syntax (EFS) αξιολογεί selectors μέσα σε αγκύλες, εκφράσεις γραμμών/pixel, υπολογιζόμενες στήλες, ιστογράμματα και μετασχηματισμούς πριν επιστρέψει το ανοιγμένο αντικείμενο· ορισμένες μορφές δημιουργούν επίσης προσωρινά αντίγραφα. Κατά τη χαρτογράφηση της επιφάνειας επίθεσης, ταξινομήστε κάθε API ανοίγματος/εισαγωγής ως **κυριολεκτική διαδρομή** ή **διαδρομή που ερμηνεύεται** και, στη συνέχεια, κάντε fuzzing στο σημείο εισόδου παραγωγής που καλούν πραγματικά οι εφαρμογές.<sup>[[20]](#references)[[22]](#references)</sup>

Για τα primitives SSRF, αντιγραφής αρχείων και χειρισμού πρωτοκόλλων που προκύπτουν —καθώς και για ασφαλέστερα API κυριολεκτικών διαδρομών— δείτε το [Filename mini-languages as SSRF/file primitives](../pentesting-web/ssrf-server-side-request-forgery/index.html#filename-mini-languages-as-ssrffile-primitives-cfitsio-efs).<sup>[[20]](#references)</sup>

### Διατηρήστε το αντικείμενο υποστήριξης ξεχωριστό από το πρόγραμμα που υποβάλλεται σε fuzzing

Όταν η γραμματική βρίσκεται σε ένα επίθημα filename, η μετάλλαξη μόνο των bytes του αρχείου αναφοράς δεν καλύπτει τον parser. Αντί γι’ αυτό, ένα μικρό harness μπορεί να διαβάζει κάθε testcase ως συμβολοσειρά και να το περνά στο API ανοίγματος που ερμηνεύει το filename· η εκστρατεία CFITSIO κάλυψε τους περισσότερους EFS parsers και evaluators καλώντας τη `fits_open_file()` σε λειτουργία μόνο για ανάγνωση. Διατηρήστε χωριστά διαθέσιμα έγκυρα αρχεία υποστήριξης, ώστε οι μεταλλάξεις να εστιάζουν στη γλώσσα selector/έκφρασης αντί να καταστρέφουν συνεχώς τη βασική διαδρομή.<sup>[[22]](#references)</sup>

Χρησιμοποιήστε seeds που φτάνουν το καθένα σε διαφορετική οικογένεια γραμματικής και, στη συνέχεια, δημιουργήστε ένα συμπαγές λεξικό από την προδιαγραφή και τον πηγαίο κώδικα του lexer/parser. Αν η κάλυψη σταματήσει να αυξάνεται ενώ οι είσοδοι αποτυγχάνουν επανειλημμένα στην ίδια διαδρομή συντακτικού σφάλματος, διατηρήστε τα έγκυρα προθέματα και προσθέστε διαχωριστικά, τελεστές, λέξεις-κλειδιά, ονόματα συναρτήσεων και ενδεικτικά ονόματα πεδίων, αντί απλώς να αυξήσετε τον χρόνο τυχαίων μεταλλάξεων.<sup>[[22]](#references)</sup>

Εκτελέστε το harness με το λεξικό γραμματικής, για παράδειγμα:<sup>[[3]](#references)[[22]](#references)</sup>

```bash
afl-fuzz -i filename-seeds -o out -x filename-language.dict -- ./filename-harness @@
```

### Περιορισμός των παρενεργειών του harness σε λειτουργία "read-only"

Μια σημαία βιβλιοθήκης read-only δεν εγγυάται ότι ένα testcase δεν θα προκαλέσει παρενέργειες: η γλώσσα ονομάτων αρχείων μπορεί να ξαναγράψει την είσοδο, να δημιουργήσει αρχεία εξόδου ή να υλοποιήσει προσωρινά αντικείμενα. Η καμπάνια CFITSIO αρχικά κατέστρεψε seed files και άφησε απρόσμενα αρχεία σε όλο το filesystem, οπότε χρειάστηκαν καθαρισμός και απομόνωση.<sup>[[22]](#references)</sup>

- Δώστε σε κάθε worker έναν προσωρινό working directory και έναν ιδιωτικό temporary directory.
- Παρέχετε αντίγραφα των canonical backing files· μην αφήνετε ποτέ το target να τροποποιήσει το μοναδικό αντίγραφο του corpus.
- Απενεργοποιήστε την πρόσβαση στο δίκτυο, εκτός αν τα remote backends είναι ο επιδιωκόμενος στόχος, και περιορίστε τις εγγράψιμες διαδρομές με container, mount namespace ή ισοδύναμο sandbox.
- Επαναφέρετε τον directory μετά από κάθε εκτέλεση ή batch worker και αντιμετωπίζετε τις απρόσμενες αλλαγές στο filesystem ως πρόσθετα ευρήματα.

### Βρόχος crash-to-patch-to-fuzz

Ομαδοποιήστε τα crashes πριν από την επιδιόρθωση, ώστε χιλιάδες artifacts να μη μετατραπούν σε χιλιάδες εργασίες patch. Στην αξιολόγηση CFITSIO, το AFLTriage περιόρισε το αρχικό σύνολο crashes σε λίγες βασικές αιτίες· το advisory που προέκυψε καταγράφει διαφορετικές αστοχίες, όπως εσφαλμένους ελέγχους μεγέθους προορισμού, stale pointers μετά από `realloc()`, αριθμητικά σφάλματα και μη ασφαλείς διαδρομές εκκαθάρισης του parser.<sup>[[21]](#references)[[22]](#references)</sup>

1. Ελαχιστοποιήστε ένα αντιπροσωπευτικό input για κάθε cluster και αναπαραγάγετέ το με AddressSanitizer.
2. Καταγράψτε την ακριβή πρόσβαση που απέτυχε, τη θέση στον πηγαίο κώδικα, το ιστορικό allocation/free και την κατάσταση του parser που οδήγησε στην παραβίαση του invariant.
3. Εφαρμόστε ένα στενά οριοθετημένο υποψήφιο patch και κάντε rebuild με τα ίδια όργανα κάλυψης και sanitizer.
4. Επαναλάβετε το αρχικό reproducer **και κάθε input του cluster**· ενεργοποιήστε επίσης τον εντοπισμό leak, επειδή μια διόρθωση memory-safety μπορεί να διαταράξει το ownership σε διαδρομή σφάλματος.
5. Εκτελέστε functional tests με πραγματικά αρχεία και, στη συνέχεια, συνεχίστε από τη συσσωρευμένη queue (ή κάντε ξανά import αυτή την queue, αν το engine απαιτεί νέο output directory μετά την αλλαγή του binary).
6. Επαναλάβετε: η αφαίρεση του πρώτου ρηχού crash συχνά επιτρέπει στα υπάρχοντα seeds να προχωρήσουν σε βαθύτερη κατάσταση του parser.

Ένα LLM μπορεί να επιταχύνει το βήμα 2 και να συντάξει ένα προσχέδιο για το βήμα 3, όταν του δοθούν το input που προκαλεί το crash, η αναφορά του sanitizer, το harness και ο σχετικός πηγαίος κώδικας, αλλά το patch του παραμένει μη έμπιστο. Το αν η επιδιόρθωση γίνεται αποδεκτή το κρίνουν η επανάληψη με sanitizer και οι έλεγχοι παλινδρόμησης — όχι η εξήγηση του μοντέλου.<sup>[[22]](#references)</sup>

## Πλουσιότερη ανατροφοδότηση όταν η edge coverage συγχωνεύει διαφορετικές διαδρομές

Η συνηθισμένη edge coverage δεν μπορεί να διακρίνει δύο εκτελέσεις που περνούν από το ίδιο helper μέσω διαφορετικών callers ή ακολουθούν διαφορετικούς συνδυασμούς branches μέσα σε μια συνάρτηση. Αυτό έχει σημασία σε shared decoders, protocol dispatchers και helpers διερμηνευτών, όπου η **διαδρομή** προς ένα edge καθορίζει την ενεργή κατάσταση. Η αφελής παρακολούθηση κάθε calling context είναι επίσης επικίνδυνη: ο χάρτης κάλυψης και η queue μπορεί να διογκωθούν υπερβολικά. Γι' αυτό, η έρευνα στο context-sensitive fuzzing συνιστά να βελτιώνονται μόνο τα υποσχόμενα contexts, αντί να αντιμετωπίζεται ολόκληρο το call graph ως context-sensitive.<sup>[[14]](#references)</sup>

Οι πρόσφατες εκδόσεις του AFL++ παρέχουν **κάλυψη διαδρομών ανά συνάρτηση Ball-Larus**, επιπλέον της συνηθισμένης edge coverage. Αναθέτει ένα feature σε κάθε ακυκλική διαδρομή μέσα σε μια συνάρτηση· αφαιρούνται τα loop back-edges, επομένως αυτή η ανατροφοδότηση διακρίνει συνδυασμούς branches, αλλά **όχι τον αριθμό των επαναλήψεων του loop**. Ξεκινήστε με το χαλαρό επίπεδο `1` και, στη συνέχεια, περιορίστε τις αυστηρότερες λειτουργίες σε ύποπτο parser/state-machine code, επειδή ο αριθμός των διαδρομών μπορεί να αυξηθεί εκθετικά.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Για ένα helper που καλείται από πολλά σημεία που σχετίζονται με την ασφάλεια, η λειτουργία LTO μπορεί να συνδυάσει κάθε διαδρομή συνάρτησης με το άμεσο σημείο κλήσης της:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Καθοδήγηση για την καμπάνια:** χρησιμοποιήστε πιο πλούσιο feedback με φειδώ και παρακολουθήστε το κόστος του coverage map και της queue.<sup>[[13]](#references)[[14]](#references)</sup>

- Εκτελέστε παράλληλα ένα συνηθισμένο instance edge coverage· το πιο πλούσιο feedback είναι χρήσιμο μόνο εφόσον το επιπλέον κόστος σε queue/map δεν μειώνει υπερβολικά τις executions ανά δευτερόλεπτο.
- Χρησιμοποιήστε το `AFL_LLVM_ALLOWLIST` για να περιορίσετε το path/caller instrumentation, όταν μεγάλες βιβλιοθήκες με πολλά templates ή γενικός κώδικας utilities κυριαρχούν στο map.
- Οι συναρτήσεις με υπερβολικά πολλά acyclic paths μπορούν να παραλείπονται από το AFL++· οι προειδοποιήσεις κατά τη μεταγλώττιση δείχνουν ότι ο στόχος χρειάζεται allowlisting ή λιγότερο αυστηρό επίπεδο.
- Το caller + path coverage υποστηρίζει μόνο ένα επίπεδο caller. Μην το συνδυάζετε με βαθύτερα context stacks.
- Τα path IDs μπορεί να αλλάζουν μεταξύ major εκδόσεων του LLVM. Διατηρήστε σταθερό το toolchain σε όλη την καμπάνια και μην συγχρονίζετε corpora που βασίζονται σε PATH σαν τα feature IDs τους να παρέμεναν σταθερά μεταξύ των builds.
- Αυτό το feedback συμπληρώνει το `CMPLOG`: το comparison tracing εντοπίζει **ποια τιμή περνά έναν guard**, ενώ το path/caller feedback διατηρεί **ποια διαδρομή και ποιος συνδυασμός branches οδήγησαν εκεί**.

## Stateful Fuzzing: Οι ακολουθίες είναι seeds

Για **protocols**, **authenticated workflows** και **multi-stage parsers**, η ενδιαφέρουσα μονάδα συχνά δεν είναι ένα μεμονωμένο blob, αλλά μια **ακολουθία μηνυμάτων**. Η συνένωση ολόκληρου του transcript σε ένα αρχείο και η τυφλή μεταβολή του είναι συνήθως αναποτελεσματική, επειδή ο fuzzer μεταβάλλει όλα τα βήματα εξίσου, ακόμη κι όταν μόνο το μεταγενέστερο μήνυμα φτάνει στην ευάλωτη κατάσταση.<sup>[[4]](#references)</sup>

Μια πιο αποτελεσματική προσέγγιση είναι να αντιμετωπίζετε την **ίδια την ακολουθία ως seed** και να χρησιμοποιείτε την **παρατηρήσιμη κατάσταση** (κωδικούς απόκρισης, καταστάσεις protocol, φάσεις parser, τύπους αντικειμένων που επιστρέφονται) ως πρόσθετο feedback.<sup>[[4]](#references)</sup>

- Διατηρείτε σταθερά τα **έγκυρα αρχικά μηνύματα** και επικεντρώστε τις μεταβολές στο μήνυμα που **οδηγεί στη μετάβαση**.
- Αποθηκεύετε identifiers και τιμές που παράγει ο server από προηγούμενες αποκρίσεις, όταν το επόμενο βήμα εξαρτάται από αυτές.
- Προτιμάτε τη μεταβολή/splicing ανά μήνυμα, αντί να μεταβάλλετε ολόκληρο το serialized transcript σαν αδιαφανές blob.
- Αν το protocol παρέχει ουσιαστικούς κωδικούς απόκρισης, χρησιμοποιήστε τους ως **φθηνό state oracle** για να δίνετε προτεραιότητα στις ακολουθίες που προχωρούν βαθύτερα.

Για τον ίδιο λόγο, bugs που απαιτούν authentication, κρυφές μεταβάσεις ή parser bugs που εμφανίζονται «μόνο μετά το handshake» συχνά δεν εντοπίζονται με το συνηθισμένο file-style fuzzing: ο fuzzer πρέπει να διατηρεί **τη σειρά, την κατάσταση και τις εξαρτήσεις**, όχι μόνο τη δομή.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing driver με πολλούς clients

Το υψηλό edge coverage μπορεί και πάλι να μην εντοπίσει bugs στον IPC driver, επειδή το coverage δεν περιγράφει **την ιδιοκτησία αντικειμένων, τους reference counts, τα μηνύματα σε εκκρεμότητα, τη σειρά εκκαθάρισης ή τις εναλλαγές νημάτων**. Η σελίδα [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) καλύπτει το μοντέλο αντικειμένων του driver· αυτό το παράδειγμα επικεντρώνεται στο fuzzer harness. Το Android Binder αποτελεί χρήσιμο μοντέλο: δεν αρκεί να φτάνει κανείς τόσο στα μονοπάτια allocation όσο και στα μονοπάτια free, αν ο fuzzer δεν μπορεί να κάνει πολλές διεργασίες να ενεργήσουν πάνω στο ίδιο kernel object με την απαιτούμενη σειρά.<sup>[[15]](#references)</sup>

#### Μοντελοποιήστε το protocol, όχι μεμονωμένα buffers `ioctl`

Αναπαραστήστε κάθε test case ως μια διατεταγμένη γραμματική από **ταυτότητα client + operation + δομημένα arguments**. Ο Binder LKL fuzzer χρησιμοποιεί protobuf και `libprotobuf-mutator`, με έναν persistent context-manager client και δύο συνηθισμένους clients. Ένα semantic harness διατηρεί έπειτα τις σχέσεις που θα κατέστρεφε η τυφλή μεταβολή bytes.<sup>[[15]](#references)</sup>

- Αποθηκεύετε τιμές που επιστρέφονται από προηγούμενες operations. Για παράδειγμα, το `BC_FREE_BUFFER` πρέπει να επαναχρησιμοποιεί έναν δείκτη transaction buffer που επιστράφηκε από προηγούμενο `ioctl`.
- Δημιουργείτε έγκυρες προεπιλεγμένες αποκρίσεις, ώστε να μπορούν να ολοκληρώνονται οι synchronous transactions και να παραμένουν προσβάσιμες οι επόμενες operations.
- Απορρίπτετε αδύνατες μεταβάσεις, όπως self-transactions ή πολλαπλές transactions σε εκκρεμότητα προς τον ίδιο στόχο.
- Διατηρείτε την κατάσταση singleton bootstrap έξω από το reset ανά input. Το Binder επιτρέπει μόνο μία καταχώριση `BINDER_SET_CONTEXT_MGR` ανά boot, επομένως η επανειλημμένη καταστροφή και επαναδημιουργία αυτού του client θα καθιστούσε άκυρα τα επόμενα inputs.

Ένα χρήσιμο πρότυπο για lifetime race είναι να μεταφέρει ένας client ένα αντικείμενο, να ξεκινά η εκκαθάριση ενός thread ή process και, ταυτόχρονα, ο client που λαμβάνει το αντικείμενο να αποδεσμεύει το transaction buffer. Στο παράδειγμα CVE-2020-0423, η μεταφορά ενός `BINDER_TYPE_WEAK_BINDER` και στη συνέχεια το `BINDER_THREAD_EXIT` σε race με το `BC_FREE_BUFFER` μπορούσαν να απελευθερώσουν ένα ενσωματωμένο `binder_work`, ενώ το path εκκαθάρισης του thread που τερματιζόταν εξακολουθούσε να το χρησιμοποιεί.<sup>[[15]](#references)</sup>

#### Επαναφέρετε ελεγχόμενες εναλλαγές σε έναν kernel userspace

Η [Linux Kernel Library (LKL)](https://github.com/lkl/linux) συνδέει τον πραγματικό κώδικα του kernel σε ένα userspace harness και εκθέτει το syscall interface μέσω του `lkl_syscall`. Έτσι, ο συντονισμός του protobuf state, του coverage και του KASAN γίνεται εύκολα μέσα σε μία διεργασία. Ωστόσο, το LKL συνήθως εκτελεί ένα syscall χωρίς να το διακόπτει άλλο kernel thread. Για race campaigns, εισάγετε σημεία `schedule()` γύρω από επιλεγμένα όρια lock/unlock και lifetime και, σε κάθε yield, αφήστε το harness να επιλέγει τυχαία τον επόμενο client. Διατηρήστε αυτά τα σημεία στοχευμένα, επειδή το καθένα πολλαπλασιάζει τον χώρο αναζήτησης του scheduling. Ο randomized scheduler που περιγράφουν οι ερευνητές **δεν** αποτελεί μέρος του upstream Binder fuzzer.<sup>[[15]](#references)</sup>

#### Δημιουργήστε και επαναλάβετε serialized seeds παλινδρόμησης

Το upstream harness ορίζει μια συμβατή έκδοση του `libprotobuf-mutator`, ενεργοποιεί το LKL fuzzing instrumentation και το KASAN με `LKL_FUZZING=1` και ενεργοποιεί το `CONFIG_MMU` για το Binder με `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Αφού ελέγξετε μια σκόπιμα ευάλωτη αναθεώρηση ή εφαρμόσετε τις upstream διορθώσεις επαναφοράς, ένα serialized seed μπορεί να αναπαράγει ολόκληρη τη μετάβαση κατάστασης πολλών clients, χωρίς να χρειάζεται να την ανακατασκευάσετε σε ένα ad hoc proof of concept σε C:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Αντιμετωπίστε το KASAN use-after-free που προέκυψε ως επιβεβαίωση ότι το seed έφτασε στην ευάλωτη διαδρομή lifetime. Δεν αποδεικνύει τις μεταγενέστερες primitives που απαιτούνται για εκτέλεση κώδικα στον kernel ή privilege escalation.<sup>[[16]](#references)</sup>

## Τέχνασμα Διαφορετικότητας σε Ένα Μηχάνημα (στυλ Jackalope)

Ένας πρακτικός τρόπος να συνδυάσετε τη **generative novelty** με την **επαναχρησιμοποίηση coverage** είναι να **επανεκκινείτε workers βραχείας διάρκειας** απέναντι σε έναν persistent server. Κάθε worker ξεκινά με ένα κενό corpus, συγχρονίζεται μετά από `T` δευτερόλεπτα, εκτελείται για άλλα `T` δευτερόλεπτα πάνω στο συνδυασμένο corpus, συγχρονίζεται ξανά και έπειτα τερματίζεται. Έτσι προκύπτουν **νέες δομές σε κάθε γενιά**, ενώ παράλληλα αξιοποιείται το coverage που έχει συσσωρευτεί.<sup>[[1]](#references)[[2]](#references)</sup>

**Server:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Διαδοχικοί workers (παράδειγμα βρόχου):**

<details>
<summary>Βρόχος επανεκκίνησης worker του Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Σημειώσεις:**

- Το `-in empty` επιβάλλει νέο **corpus** σε κάθε generation.
- Το `-server_update_interval T` προσεγγίζει το **delayed sync** (πρώτα novelty, μετά reuse).
- Στη λειτουργία grammar fuzzing, ο **initial server sync παραλείπεται από προεπιλογή** (δεν χρειάζεται το `-skip_initial_server_sync`).
- Η βέλτιστη τιμή του `T` εξαρτάται από το **target**· συνήθως λειτουργεί καλύτερα να αλλάξετε τιμή αφού ο worker εντοπίσει το μεγαλύτερο μέρος του «εύκολου» coverage.

## Snapshot Fuzzing για Targets που είναι Δύσκολο να Προσαρμοστούν σε Harness

Όταν ο κώδικας που θέλετε να δοκιμάσετε γίνεται προσβάσιμος μόνο **μετά από μεγάλο κόστος αρχικοποίησης** (εκκίνηση VM, ολοκλήρωση login, λήψη packet, ανάλυση container, αρχικοποίηση service), μια χρήσιμη εναλλακτική είναι το **snapshot fuzzing**: καταγράφετε την έτοιμη κατάσταση της process ή του VM, εισάγετε κάθε test case στη διαδρομή εισόδου του target, εκτελείτε μέχρι να προκύψει crash/timeout και επαναφέρετε το snapshot. Έτσι αποφεύγετε την επανάληψη της αρχικοποίησης ή των προθεμάτων του protocol· η τεχνική είναι χρήσιμη για **network services**, **firmware**, **attack surfaces μετά το authentication** και **binary-only targets**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Εκτελέστε το target μέχρι να είναι έτοιμη η επιθυμητή κατάσταση.
2. Δημιουργήστε snapshot της **μνήμης + των registers** εκείνη τη στιγμή.
3. Για κάθε test case, γράψτε το mutated input απευθείας στο σχετικό guest/process buffer.
4. Εκτελέστε μέχρι να προκύψει crash/timeout/reset.
5. Επαναφέρετε το snapshot· για VM targets, επαναφέρετε μόνο τις **dirty pages**, αν υποστηρίζεται, και επαναλάβετε.

Τοποθετήστε το snapshot όσο πιο κοντά γίνεται στο πρώτο δαπανηρό βήμα ανάλυσης/dispatch, για παράδειγμα μετά από ένα σημείο `recv`/`read` ή αποσειριοποίησης packet, και καταγράψτε το input buffer που χρησιμοποιεί το target. Αυτό ακολουθεί την αρχή της προσαρμοστικής τοποθέτησης: μετακινείτε το snapshot βαθύτερα στην επεξεργασία του input, ώστε να αποφύγετε την επανάληψη εργασιών.<sup>[[11]](#references)</sup>

## Διερεύνηση Race Conditions στον Linux Kernel με το MAccConc

Το [MAccConc](https://github.com/googleprojectzero/MAccConc) μετατρέπει τις race conditions στον Linux kernel που εξαρτώνται από τον χρονισμό σε επαναλήψιμα προγράμματα εκτέλεσης προσβάσεων μνήμης. Μπορεί να απαριθμήσει αυτόματα εκτελέσεις **A-B-A** δύο contexts ή να επιτρέψει σε έναν analyst να ορίσει περιορισμούς σειράς μέσω terminal UI/GUI. Πρόκειται για πειραματικό ερευνητικό εργαλείο και όχι για ολοκληρωμένο concurrency fuzzer: προς το παρόν απαιτεί LLVM 23+ και τον patched kernel του project, τα command-line tools υποστηρίζουν δύο test threads και το προτεινόμενο userspace fuzzing layer δεν έχει υλοποιηθεί.<sup>[[17]](#references)[[18]](#references)</sup>

### Συλλογή σημείων επικοινωνίας μεταξύ contexts

Κάντε build τον instrumented kernel με KASAN outline callbacks και την υποστήριξη patched KCOV για καταγραφή μνήμης. Το README του project συνιστά επίσης την απενεργοποίηση του sibling-call optimization, ώστε τα call stacks να παραμένουν αξιοποιήσιμα.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

Η λειτουργία outline του KASAN (`asan-instrumentation-with-call-threshold=0`) μετατρέπει τις προσπελάσεις που έχουν υποστεί instrumentation σε κλήσεις helper. Τα patches του kernel για το MAccConc απενεργοποιούν το `asan-opt-same-temp`, ώστε να μη συγχωνεύονται διαδοχικές προσπελάσεις· απενεργοποιήστε και τη βελτιστοποίηση `asan-opt-globals` όταν πρέπει να είναι ορατά τα races σε global μεταβλητές. Το KCOV μεταφέρει τις εγγραφές που προκύπτουν στο userspace. Συγκρίνετε προσπελάσεις από διαφορετικά execution contexts και κρατήστε τα ζεύγη των οποίων οι περιοχές bytes επικαλύπτονται και όπου τουλάχιστον η μία πλευρά εκτελεί εγγραφή· μοντελοποιήστε το `kfree()` ως εγγραφή, ώστε να αποτελούν υποψήφιες περιπτώσεις και οι μεταβάσεις διάρκειας ζωής.<sup>[[17]](#references)</sup>

Για εργασία που συνεχίζεται εκτός του task που την ξεκίνησε, όπως η επεξεργασία πακέτων ή τα RCU callbacks, το subsystem πρέπει να προωθεί ένα handle για remote coverage του KCOV. Το upstream remote KCOV είναι opt-in και δεν είναι αυτομάτως διαθέσιμο για αυθαίρετη εργασία στο παρασκήνιο, επομένως η παράλειψη προώθησης μπορεί να κάνει μια πραγματική αλληλεπίδραση αόρατη.<sup>[[17]](#references)[[19]](#references)</sup>

### Εντοπίστε την ίδια δυναμική πρόσβαση σε κάθε εκτέλεση

Μην κάνετε replay με βάση μια συγκεκριμένη διεύθυνση heap, η οποία μπορεί να αλλάζει μετά από κάθε allocation, ή μόνο με βάση μια διεύθυνση instruction, η οποία είναι αμφίσημη μέσα σε helpers όπως τα `memcpy()` και `spin_lock()`. Το MAccConc χρησιμοποιεί ένα **stack trace επαυξημένο με μετρητές**: κάθε frame προσδιορίζει έναν callee και τον αριθμό κλήσης του μέσα στον caller του, ενώ το τελευταίο στοιχείο προσδιορίζει την instruction της πρόσβασης στη μνήμη. Οι εγγραφές εισόδου/εξόδου συναρτήσεων του SanitizerCoverage επιτρέπουν στο userspace να ανακατασκευάσει αυτό το δυναμικό αναγνωριστικό, το οποίο παραμένει σταθερό παρά τις αλλαγές διευθύνσεων και τον άσχετο θόρυβο στη ροή ελέγχου.<sup>[[17]](#references)</sup>

### Μετατρέψτε τα υποψήφια ζεύγη σε εξαναγκασμένα schedules

Το patched ioctl `KCOV_SET_DI` συσχετίζει ένα αναγνωριστικό πρόσβασης επαυξημένο με μετρητές με μια ενέργεια σε shared flag.<sup>[[17]](#references)</sup>

| Action | Σημασιολογία |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Ορίστε το flag *N* αμέσως πριν από την επιλεγμένη πρόσβαση. |
| `DI_STACK_WAIT` | Πριν από την επιλεγμένη πρόσβαση, κάντε spin μέχρι να οριστεί το flag *N* ή να λήξει το ρυθμισμένο όριο. |
| `DI_STACK_WAKE_POST` | Ορίστε το flag *N* αμέσως μετά την επιλεγμένη πρόσβαση. |

Για έναν μερικό περιορισμό **A-happens-before-B**, συνδέστε το `DI_STACK_WAKE_POST` με το A και το `DI_STACK_WAIT` με το B, χρησιμοποιώντας το ίδιο flag. Για ένα πλήρως καθορισμένο schedule δύο contexts, ξεκινήστε το B σε κατάσταση blocked και, στη συνέχεια, κάντε το A να ξυπνήσει το B και να περιμένει στο πρώτο σημείο μεταβίβασης· το B εκτελεί την αντίστροφη ενέργεια στο επόμενο σημείο μεταβίβασης. Το δεύτερο λειτουργεί όπως η ντετερμινιστική εναλλαγή contexts και χρησιμοποιείται από τον αυτόματο explorer A-B-A.<sup>[[17]](#references)</sup>

Μια ελάχιστη campaign είναι να μεταγλωττίσετε την test case με τα τέσσερα hooks (`test_setup`, δύο συναρτήσεις thread και `test_end`) ως shared library, να συλλέξετε ένα trace χωρίς περιορισμούς και, στη συνέχεια, να απαριθμήσετε υποψήφιες περιπτώσεις A-B-A ή να προσθέσετε χειροκίνητους περιορισμούς γύρω από ύποπτες προσπελάσεις.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Ερμήνευε τα timeouts ξεχωριστά από τις επιτυχείς αναδιατάξεις: μια ζητούμενη σειρά μπορεί να είναι αδύνατη, επειδή ένα lock ή μια εξάρτηση αρχικοποίησης/δημοσίευσης εμποδίζει το δεύτερο context να φτάσει στο σημείο injection. Λάβε επίσης υπόψη τα blind spots του KASAN: οι άμεσες προσπελάσεις στη στοίβα συνήθως δεν καλύπτονται από hooks, εκτός αν ενδέχεται να είναι out of bounds, οι globals παραλείπονται με τη default βελτιστοποίηση και οι τρέχοντες compilers δεν μπορούν να εκπέμψουν ταυτόχρονα hooks για ASAN και TSAN. Τέλος, το prototype χάνει το KCOV buffer του όταν γίνεται panic στο guest, γι’ αυτό διατήρησε ανεξάρτητη crash console/oracle.<sup>[[17]](#references)</sup>

Για μελλοντικό concurrency-guided fuzzing, κατέγραψε περιλήψεις προσπελάσεων μνήμης ανά input ή syscall, ζευγοποίησε λειτουργίες που θα δημιουργούσαν σημεία επικοινωνίας μεταξύ contexts και, στη συνέχεια, εξερεύνησε μόνο αυτούς τους συνδυασμούς. Τα VM snapshots σταθεροποιούν την καθολική κατάσταση και τις διευθύνσεις· χωρίς snapshots, τα metadata των allocation sites μπορούν να αφαιρούν τις διαφορές μεταξύ αντικειμένων σε διαφορετικά runs. Αυτή είναι μια προτεινόμενη επέκταση, όχι δυνατότητα των τρεχόντων userspace tools του MAccConc.<sup>[[17]](#references)</sup>

## Ενδοσκόπηση Harness: Εντόπισε νωρίς τους ρηχούς fuzzers

Όταν μια campaign κολλάει, συχνά το πρόβλημα δεν είναι ο mutator αλλά το **harness**. Χρησιμοποίησε **ενδοσκόπηση προσβασιμότητας/κάλυψης** για να εντοπίσεις συναρτήσεις που είναι στατικά προσβάσιμες από τον στόχο του fuzzing, αλλά καλύπτονται σπάνια ή ποτέ δυναμικά. Αυτές οι συναρτήσεις συνήθως υποδεικνύουν ένα από τρία προβλήματα.<sup>[[12]](#references)</sup>

- Το harness εισέρχεται στον στόχο πολύ αργά ή πολύ νωρίς.
- Το seed corpus δεν περιλαμβάνει μια ολόκληρη οικογένεια λειτουργιών.
- Ο στόχος χρειάζεται πραγματικά ένα **δεύτερο harness**, αντί για ένα υπερβολικά μεγάλο harness που «τα κάνει όλα».

Αν χρησιμοποιείς ροές εργασίας τύπου OSS-Fuzz / ClusterFuzz, το Fuzz Introspector μπορεί να συγκρίνει τη στατική προσβασιμότητα με την κάλυψη κατά το runtime και να δημιουργήσει αναφορές από μια χρονομετρημένη εκτέλεση ή ένα δημόσιο corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Χρησιμοποιήστε την αναφορά για να αποφασίσετε αν θα προσθέσετε ένα νέο harness για μια μη δοκιμασμένη διαδρομή parser, θα επεκτείνετε το corpus για μια συγκεκριμένη λειτουργία ή θα χωρίσετε ένα μονολιθικό harness σε μικρότερα entry points.

## Επιλογή στόχων fuzzing με βάση το γράφημα και διαλογή μεταλλάξεων

Αν έχετε ήδη ευρήματα από **static analysis**, **mutation testing** και αναφορές κάλυψης, μην τα διαχειρίζεστε ως ανεξάρτητες λίστες. Δημιουργήστε πρώτα ένα **call graph**, προσθέστε στους κόμβους επισημειώσεις για την **κυκλωματική πολυπλοκότητα**, την **προσβασιμότητα από entrypoints/μη έμπιστες εισόδους** και τυχόν εξωτερικά ευρήματα, και μετά εξετάστε το γράφημα.<sup>[[5]](#references)[[6]](#references)</sup>

- Ποιες συναρτήσεις υψηλής πολυπλοκότητας είναι προσβάσιμες από μη έμπιστη είσοδο;
- Ποιοι survivors μεταλλάξεων βρίσκονται σε διαδρομές από parsers/handlers προς κώδικα κρίσιμο για την ασφάλεια;
- Ποιες συναρτήσεις αποτελούν αρχιτεκτονικά σημεία συμφόρησης με ασυνήθιστα μεγάλο **blast radius**;

Αυτό συνήθως αναδεικνύει καλύτερους στόχους fuzzing από την απλή επιλογή βάσει της «χαμηλότερης κάλυψης». Ένας parser/decoder με **υψηλή πολυπλοκότητα** και επιβεβαιωμένη **εξωτερική προσβασιμότητα** είναι ισχυρότερος υποψήφιος για harness από μια απομονωμένη εσωτερική βοηθητική συνάρτηση με χαμηλή κάλυψη αλλά χωρίς διαδρομή ελεγχόμενη από επιτιθέμενο.

### Πρακτική ροή εργασίας διαλογής

1. Δημιουργήστε ένα **γράφημα κώδικα** από τη βάση κώδικα και εξαγάγετε μετρικές πολυπλοκότητας/διακλαδώσεων για κάθε συνάρτηση.
2. Καταγράψτε τα **entrypoints** που δέχονται είσοδο ελεγχόμενη από επιτιθέμενο: request handlers, decoders, importers, protocol parsers, CLI/file readers.
3. Εκτελέστε **path queries** από αυτά τα entrypoints προς τις υποψήφιες συναρτήσεις, για να διαχωρίσετε την προσβάσιμη επιφάνεια επίθεσης από τον νεκρό κώδικα ή τον κώδικα που είναι προσβάσιμος μόνο εσωτερικά.
4. Δώστε προτεραιότητα σε κόμβους που συνδυάζουν:
   - υψηλή **κυκλωματική πολυπλοκότητα**
   - επιβεβαιωμένη **προσβασιμότητα από μη έμπιστη είσοδο**
   - μεγάλο **blast radius** ή πολλούς εξαρτώμενους κόμβους
   - επιβεβαιωτικά στοιχεία, όπως ευρήματα **SARIF**, σημειώσεις audit ή survivors μεταλλάξεων
5. Γράψτε πρώτα εστιασμένα harnesses για τους κόμβους με την υψηλότερη βαθμολογία, ειδικά για **parsers/codecs**, όπως αποκωδικοποιητές hex/Base64/IP/message.

### Survivors μεταλλάξεων: ισοδύναμα ή αξιοποιήσιμα

Το mutation testing συχνά παράγει μια θορυβώδη λίστα survivors. Πριν θεωρήσετε κάθε survivor κενό ασφαλείας, χρησιμοποιήστε το γράφημα για να εξετάσετε τα εξής:

- Είναι η τροποποιημένη συνάρτηση προσβάσιμη από entrypoint ελεγχόμενο από επιτιθέμενο;
- Περιορίζονται όλες οι διαδρομές κλήσης από ισχυρότερες αμετάβλητες συνθήκες από εκείνη που τροποποιήθηκε;
- Βρίσκεται ο κόμβος σε νεκρό κώδικα, σε λογική που αφορά μόνο τη μορφοποίηση ή σε διαδρομή αριθμητικής/parser με μεγάλο αντίκτυπο;

Οι survivors που παραμένουν μη προσβάσιμοι ή περιορίζονται δομικά είναι συχνά **ισοδύναμοι mutants**. Οι survivors που παραμένουν **προσβάσιμοι** και επηρεάζουν **οριακές συνθήκες**, **διαδρομές υπερχείλισης/κρατουμένου** ή **αριθμητική/ανάλυση συντακτικού κρίσιμη για την ασφάλεια** θα πρέπει να προωθούνται σε:

- νέα fuzz harnesses
- άμεσα tests ιδιοτήτων/αμετάβλητων συνθηκών
- στοχευμένα διανύσματα ακραίων περιπτώσεων

### Συσχετίστε εξωτερικά ευρήματα με το γράφημα

Αν η ροή εργασίας SAST εξάγει **SARIF**, αντιστοιχίστε τα ευρήματα στους κόμβους του γραφήματος με βάση το **αρχείο + το εύρος γραμμών** και χρησιμοποιήστε το γράφημα για να επεκτείνετε την εκτίμηση επιπτώσεων.<sup>[[6]](#references)</sup>

- υπολογίστε το **blast radius** της επισημασμένης συνάρτησης
- ελέγξτε αν το εύρημα βρίσκεται σε οποιαδήποτε διαδρομή από ένα entrypoint
- ομαδοποιήστε κοντινά ευρήματα που καταλήγουν στο ίδιο σημείο συμφόρησης

Αυτό είναι χρήσιμο όταν αποφασίζετε αν αξίζει να αφιερώσετε χρόνο fuzzing σε μια συγκεκριμένη συνάρτηση: ένας κόμβος που είναι **προσβάσιμος**, **πολύπλοκος** και έχει ήδη ευρήματα **SAST** είναι συχνά καλύτερος στόχος από έναν απλώς πολύπλοκο κόμβο χωρίς διαδρομή από επιτιθέμενο.

Παράδειγμα ροής εργασίας με το Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Η σημαντική μεθοδολογία είναι η τομή: **πολυπλοκότητα x έκθεση x αντίκτυπος**. Χρησιμοποιήστε το γράφημα για να επιλέξετε στόχους fuzzing με την υψηλότερη αναμενόμενη αξία ασφάλειας και, στη συνέχεια, χρησιμοποιήστε τις μεταλλάξεις που επιβιώνουν για να αποφασίσετε ποια όρια και invariants πρέπει να καταπονήσει το harness σας.<sup>[[5]](#references)</sup>

## Differential fuzzing κωδικοποιήσεων κρυπτογραφικών κλειδιών

Ξεκινήστε από έγκυρα σειριοποιημένα κλειδιά ή τυπικά test vectors. Μεταλλάξτε κωδικοποιημένα πεδία χωρίς να αλλοιώσετε το μήκος και τη δομή που απαιτούνται για να φτάσετε στις διαδρομές εισαγωγής και λειτουργιών και, στη συνέχεια, υποβάλετε τα ίδια bytes σε ανεξάρτητες υλοποιήσεις. Συγκρίνετε την αποδοχή και τα σφάλματα. Για τυχαιοποιημένες υπογραφές και ciphertexts χρειάζονται oracles ορθότητας, όχι σύγκριση byte προς byte: επαληθεύστε τις υπογραφές ή συγκρίνετε τα κοινά μυστικά από έναν κύκλο encapsulation/decapsulation. Τα test vectors τεκμηριώνουν τη συμμόρφωση για γνωστές περιπτώσεις· η differential mutation ελέγχει κακοσχηματισμένες κωδικοποιήσεις πέρα από αυτές.<sup>[[23]](#references)[[26]](#references)</sup>

Για αυτές τις μορφές κλειδιών, χρησιμοποιήστε oracles ειδικά για κάθε μορφή:<sup>[[24]](#references)[[25]](#references)[[26]](#references)</sup>

- **ML-DSA expanded signing keys:** τροποποιήστε συντελεστές `s1` ή `s2` σε packed μορφή, ώστε να βρίσκονται εκτός του `[-η, η]`, διατηρώντας όμως το κλειδί αναλύσιμο. Ελέγξτε αν η εισαγωγή ή η υπογραφή απορρίπτεται και αν επαληθεύεται οποιαδήποτε υπογραφή που προκύπτει. Οι διαφορές στην αποδοχή από μόνες τους δεν αποτελούν παραβιάσεις προτύπων, επειδή το FIPS 204 δεν επιβάλλει πρόσθετους ελέγχους ιδιωτικών κλειδιών. Δείτε τον [conditional leakage mechanism](../crypto/public-key/#malformed-ml-dsa-signing-keys-and-rejection-sampling-leakage).
- **ML-KEM key pairs:** διαχωρίστε τους απαιτούμενους ελέγχους για το encapsulation key και τα δεδομένα εισόδου του decapsulation από τον προαιρετικό έλεγχο pairwise consistency (PCT) σε ένα εισαγόμενο ζεύγος. Κάντε encapsulate με το δημόσιο κλειδί και decapsulate με το ιδιωτικό κλειδί και συγκρίνετε τα κοινά μυστικά· μια ασυμφωνία μπορεί να διακόψει την κρυπτογραφημένη επικοινωνία, ακόμη κι αν τα μεμονωμένα κλειδιά περνούν τους ελέγχους εισόδου. Ελέγξτε αν το API επικυρώνει τα δεδομένα εισόδου κατά τη λειτουργία ή μέσω ξεχωριστής κλήσης· το libcrux παρέχει τις `validate_public_key(pk)` και `validate_private_key(sk, ct)`, οι οποίες δεν υποκαθιστούν έναν PCT.
- **XMSS/XMSSMT raw keys:** δοκιμάστε κύκλους σειριοποίησης και αποσειριοποίησης κλειδιών **υπογραφής και επαλήθευσης** σε διαφορετικά σύνολα παραμέτρων, όχι μόνο λειτουργίες με κλειδιά στη μνήμη. Τα XMSS και XMSSMT έχουν ξεχωριστούς χώρους ονομάτων OID τεσσάρων byte, οπότε ένας parser που ελέγχει μόνο το OID και δοκιμάζει πρώτα το XMSS μπορεί να ταξινομήσει λανθασμένα ένα XMSSMT key με συγκρουόμενο OID και να απορρίψει την εισαγωγή. Ο parser που αναφέρθηκε στο RustCrypto αποτελεί παράδειγμα αποτυχίας διαλειτουργικότητας/διαθεσιμότητας, όχι πλαστογράφησης υπογραφής.

## Fuzzing Go με gosentry: ισχυρότερη μηχανή, τυποποιημένες είσοδοι και differential checks

Αν ένας στόχος Go διαθέτει ήδη ένα native harness `testing.F`, μια πρακτική διαδρομή αναβάθμισης είναι να εκτελέσετε το ίδιο harness με το [gosentry](https://github.com/trailofbits/gosentry), ένα fork του Go toolchain που διατηρεί το `go test -fuzz`, αλλά αντικαθιστά το backend με το **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Αυτό είναι χρήσιμο όταν ο native Go fuzzer κολλάει σε **hard comparisons**, **typed inputs** ή μορφές με απαιτητικούς parsers. Η μεθοδολογία παραμένει ίδια:

- Συνέχισε να χρησιμοποιείς το `f.Add(...)` για seeds και το `f.Fuzz(...)` για το callback.
- Επαναχρησιμοποίησε το ίδιο harness, αλλά εκτέλεσέ το με το δυαδικό αρχείο `go` του gosentry αντί για το stock toolchain.
- Αντιμετώπισε την καμπάνια που προκύπτει ως κανονική coverage-guided εκτέλεση, αλλά με scheduling/mutation από το LibAFL και καλύτερους βοηθητικούς detectors.

### Μετέτρεψε τις σιωπηλές αστοχίες σε ευρήματα fuzzing

Ένα επαναλαμβανόμενο πρόβλημα στις αξιολογήσεις Go είναι ότι η επικίνδυνη συμπεριφορά συχνά **δεν** προκαλεί crash από προεπιλογή. Με το gosentry, μπορείς να μετατρέψεις διάφορες κατηγορίες «κακών αλλά σιωπηλών» καταστάσεων σε ευρήματα.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` για να κάνεις επιλεγμένες διαδρομές logging/error να συμπεριφέρονται σαν crash (χρήσιμο για διαδρομές κώδικα τύπου `log.Fatal`, οι οποίες διαφορετικά απλώς καταγράφουν το συμβάν και συνεχίζουν).
- `--catch-races=true` για να επανεκτελείς τις νέες εγγραφές της queue με τον Go race detector.
- `--catch-leaks=true` για να επανεκτελείς τις νέες εγγραφές της queue με το `goleak` και να σταματάς σε περίπτωση διαρροών goroutine.
- Ο χειρισμός hang του LibAFL, ώστε οι **infinite loops / πολύ αργά inputs** να διατηρούνται ως ευρήματα fuzzing αντί να χάνονται ως timeouts.
- Ενσωματωμένοι έλεγχοι arithmetic overflow από προεπιλογή, καθώς και προαιρετικοί έλεγχοι truncation μέσω instrumentation τύπου go-panikint.

Αυτό είναι ιδιαίτερα χρήσιμο για targets όπου ο αντίκτυπος στην ασφάλεια είναι μια **αστοχία parser χωρίς panic**, ένα **concurrency bug** ή ένα hang που προκαλεί μόνο **DoS**, αντί για αλλοίωση μνήμης.

### Fuzzing με επίγνωση των struct για typed Go APIs

Το native Go fuzzing αναμένει κυρίως scalars όπως `[]byte`, `string` και αριθμούς. Αν ο κώδικας υπό δοκιμή δέχεται typed objects, το gosentry μπορεί να κάνει fuzz απευθείας **composite values** (structs, slices, arrays, pointers), ενώ εξακολουθεί να μεταλλάσσει τα bytes από κάτω.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Χρησιμοποιήστε το όταν η δημιουργία ενός fake wire format μόνο για fuzzing θα έκρυβε λογικά σφάλματα πίσω από κώδικα parsing που υπάρχει μόνο στο harness. Για differential ή grammar-based campaigns, διατηρήστε την είσοδο του harness ως ένα μόνο `[]byte` ή `string` και κάντε το parsing μέσα στο callback.

### Grammar-based fuzzing για parsers και εισόδους πρωτοκόλλων

Για parsers, formats και γλώσσες εισόδου, το gosentry μπορεί να εκτελέσει **Nautilus grammar fuzzing** πάνω στο LibAFL. Η γραμματική είναι ένας πίνακας JSON με production rules, και το harness συνήθως πρέπει να δέχεται ένα μόνο όρισμα `[]byte` ή `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Σημειώσεις μεθοδολογίας:

- Χρησιμοποιήστε grammar mode όταν οι μεταλλάξεις σε επίπεδο byte αποτυγχάνουν κυρίως σε πρώιμους ελέγχους σύνταξης.
- Περιορίστε τη γραμματική στο **υποσύνολο της γλώσσας/του πρωτοκόλλου που σχετίζεται με την ασφάλεια**, αντί να μοντελοποιήσετε ολόκληρη την προδιαγραφή.
- Χρησιμοποιήστε μεγάλες οριακές τιμές σε terminals/nonterminals για να δοκιμάσετε τα όρια ακεραίων, μηκών και μηχανών καταστάσεων.
- Το grammar mode διατηρεί τις εισόδους έγκυρες σύμφωνα με τη γραμματική, αλλά ο στόχος εξακολουθεί να λαμβάνει **bytes/strings**, επομένως η ανάλυση και οι σημασιολογικοί έλεγχοι παραμένουν μέσα στον κώδικα που υποβάλλεται σε fuzzing.

### Differential fuzzing: σύγκριση υλοποιήσεων, όχι μόνο crashes

Ένα ισχυρό μοτίβο για τα οικοσυστήματα Go είναι το **grammar-based differential fuzzing**: δημιουργήστε έγκυρες δομημένες εισόδους και δώστε τες σε δύο parsers, clients ή μηχανές μεταβάσεων κατάστασης.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Αντιμετωπίστε τα παρακάτω ως ευρήματα:

- η μία υλοποίηση προκαλεί panic, ενώ η άλλη απορρίπτει καθαρά την είσοδο
- ασυμφωνίες ως προς την αποδοχή ή την απόρριψη της εισόδου
- διαφορετικά parse trees ή αποκωδικοποιημένα αντικείμενα
- αποκλίνουσες μεταβάσεις κατάστασης, nonces, υπόλοιπα ή state roots

Αυτός είναι ένας πρακτικός τρόπος να εντοπίζετε **ασυμφωνίες συναίνεσης**, **ασάφειες parser** και **αποκλίσεις μεταξύ προδιαγραφών και υλοποίησης**, που συχνά δεν εντοπίζονται με το fuzzing που ελέγχει αποκλειστικά για crashes.

### Επαναχρησιμοποιήστε το corpus της καμπάνιας για αναφορά κάλυψης

Μετά από μια καμπάνια, εκτελέστε ξανά το αποθηκευμένο corpus της ουράς για να δημιουργήσετε μια αναφορά κάλυψης Go, χωρίς να χρειάζεται να εξαγάγετε ξεχωριστό corpus με μη αυτόματο τρόπο.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Εκτελέστε την εντολή από το ίδιο πακέτο και με τον ίδιο στόχο `-fuzz`, ώστε το gosentry να εντοπίσει τη σωστή αποθηκευμένη κατάσταση της campaign.
