## Mutational Grammar Fuzzing: Κάλυψη έναντι Σημασιολογίας

Στο **mutational grammar fuzzing**, οι είσοδοι μεταλλάσσονται παραμένοντας **έγκυρες ως προς τη γραμματική**. Σε λειτουργία με καθοδήγηση από την κάλυψη, αποθηκεύονται ως seeds του corpus μόνο τα δείγματα που προκαλούν **νέα κάλυψη**. Για **στόχους γλωσσών** (parsers, interpreters, engines), αυτό μπορεί να μην εντοπίσει bugs που απαιτούν **αλυσίδες σημασιολογικών εξαρτήσεων/dataflow**, όπου η έξοδος ενός construct γίνεται είσοδος ενός άλλου.<sup>[[1]](#references)</sup>

**Τρόπος αποτυχίας:** ο fuzzer βρίσκει seeds που ασκούν μεμονωμένα τις `document()` και `generate-id()` (ή παρόμοια primitives), αλλά **δεν διατηρεί την αλυσιδωτή ροή δεδομένων**, με αποτέλεσμα να απορρίπτεται το δείγμα που βρίσκεται «πιο κοντά στο bug», επειδή δεν προσθέτει κάλυψη. Με **3+ εξαρτημένα βήματα**, ο τυχαίος ανασυνδυασμός γίνεται δαπανηρός και η ανατροφοδότηση κάλυψης δεν καθοδηγεί την αναζήτηση.<sup>[[1]](#references)</sup>

**Συνέπεια:** για γραμματικές με πολλές εξαρτήσεις, εξετάστε το ενδεχόμενο **συνδυασμού των μεταλλακτικών και των παραγωγικών φάσεων** ή μεροληπτικής παραγωγής υπέρ μοτίβων **αλυσίδωσης συναρτήσεων** (όχι μόνο κάλυψης).<sup>[[1]](#references)</sup>

## Παγίδες ποικιλομορφίας του Corpus

Η μετάλλαξη με καθοδήγηση από την κάλυψη είναι **άπληστη**: ένα δείγμα που προσφέρει νέα κάλυψη αποθηκεύεται αμέσως, συχνά διατηρώντας μεγάλες αμετάβλητες περιοχές. Με τον καιρό, τα corpora γεμίζουν με **σχεδόν πανομοιότυπα δείγματα** και έχουν μικρή δομική ποικιλομορφία. Η επιθετική ελαχιστοποίηση μπορεί να αφαιρέσει χρήσιμο περιεχόμενο, οπότε ένας πρακτικός συμβιβασμός είναι η **ελαχιστοποίηση με επίγνωση της γραμματικής**, η οποία **σταματά όταν φτάσει σε ένα ελάχιστο όριο tokens** (μειώνει τον θόρυβο, διατηρώντας αρκετή περιβάλλουσα δομή ώστε να παραμένει εύκολη η μετάλλαξη).<sup>[[1]](#references)</sup>

Ένας πρακτικός κανόνας για το corpus στο mutational fuzzing είναι: **προτιμήστε ένα μικρό σύνολο δομικά διαφορετικών seeds που μεγιστοποιούν την κάλυψη** αντί για ένα μεγάλο πλήθος σχεδόν πανομοιότυπων δειγμάτων. Στην πράξη, αυτό συνήθως σημαίνει τα εξής.<sup>[[1]](#references)[[3]](#references)</sup>

- Ξεκινήστε από **δείγματα πραγματικού κόσμου** (δημόσια corpora, crawling, καταγεγραμμένη κίνηση δικτύου, σύνολα αρχείων από το οικοσύστημα του στόχου).
- Συμπυκνώστε τα με **ελαχιστοποίηση corpus βάσει κάλυψης**, αντί να διατηρείτε κάθε έγκυρο δείγμα.
- Διατηρήστε τα seeds **αρκετά μικρά**, ώστε οι μεταλλάξεις να επηρεάζουν ουσιαστικά πεδία αντί να σπαταλούν τους περισσότερους κύκλους σε άσχετα bytes.
- Επαναλάβετε την ελαχιστοποίηση του corpus μετά από σημαντικές αλλαγές στο harness ή στα όργανα, επειδή το «βέλτιστο» corpus αλλάζει όταν αλλάζει η δυνατότητα προσπέλασης.

## Μετάλλαξη με Επίγνωση των Συγκρίσεων για Magic Values

Ένας συνηθισμένος λόγος που οι fuzzers φτάνουν σε τέλμα δεν είναι η σύνταξη, αλλά οι **δύσκολες συγκρίσεις**: magic bytes, έλεγχοι μήκους, συμβολοσειρές enum, checksums ή τιμές dispatch του parser που προστατεύονται από `memcmp`, switch tables ή αλυσιδωτές συγκρίσεις. Η καθαρά τυχαία μετάλλαξη σπαταλά κύκλους προσπαθώντας να μαντέψει αυτές τις τιμές byte προς byte.

Για αυτούς τους στόχους, χρησιμοποιήστε **ιχνηλάτηση συγκρίσεων** (για παράδειγμα, ροές εργασίας τύπου AFL++ `CMPLOG` / Redqueen), ώστε ο fuzzer να μπορεί να παρατηρεί τελεστέους από αποτυχημένες συγκρίσεις και να κατευθύνει τις μεταλλάξεις προς τιμές που τις ικανοποιούν.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Πρακτικές σημειώσεις:**

- Αυτό είναι ιδιαίτερα χρήσιμο όταν ο στόχος αποκρύπτει σύνθετη λογική πίσω από **υπογραφές αρχείων**, **ρήματα πρωτοκόλλου**, **ετικέτες τύπων** ή **bits λειτουργιών που εξαρτώνται από την έκδοση**.
- Συνδυάστε το με **λεξικά** που έχουν εξαχθεί από πραγματικά δείγματα, προδιαγραφές πρωτοκόλλων ή αρχεία καταγραφής εντοπισμού σφαλμάτων. Ένα μικρό λεξικό με tokens γραμματικής, ονόματα chunks, ρήματα και διαχωριστικά είναι συχνά πιο χρήσιμο από μια τεράστια γενική λίστα λέξεων.
- Αν ο στόχος εκτελεί πολλούς διαδοχικούς ελέγχους, επιλύστε πρώτα τις αρχαιότερες συγκρίσεις “magic” και, στη συνέχεια, ελαχιστοποιήστε ξανά το corpus που προκύπτει, ώστε τα επόμενα στάδια να ξεκινούν με ήδη έγκυρα prefixes.

## Fuzzing File APIs που αποκρύπτουν μια γλώσσα filename

Μια παράμετρος με όνομα `filename`, `path` ή `URL` μπορεί να αποτελεί σημείο εισόδου σε interpreter και όχι κυριολεκτική αναζήτηση αρχείου. Για παράδειγμα, το CFITSIO Extended Filename Syntax (EFS) αξιολογεί επιλογείς σε αγκύλες, εκφράσεις γραμμών/pixel, υπολογιζόμενες στήλες, ιστογράμματα και μετασχηματισμούς πριν επιστρέψει το ανοιγμένο αντικείμενο· ορισμένες μορφές δημιουργούν επίσης προσωρινά αντίγραφα. Κατά τη χαρτογράφηση της επιφάνειας επίθεσης, ταξινομήστε κάθε API ανοίγματος/εισαγωγής ως **literal-path** ή **interpreted-path** και, στη συνέχεια, κάντε fuzzing στο σημείο εισόδου παραγωγής που καλούν πραγματικά οι εφαρμογές.<sup>[[20]](#references)[[22]](#references)</sup>

Για τα primitives SSRF, αντιγραφής αρχείων και χειρισμού πρωτοκόλλων που προκύπτουν —καθώς και για ασφαλέστερα APIs κυριολεκτικών διαδρομών— δείτε [Mini-languages filename ως primitives SSRF/αρχείων](../pentesting-web/ssrf-server-side-request-forgery/index.html#filename-mini-languages-as-ssrffile-primitives-cfitsio-efs).<sup>[[20]](#references)</sup>

### Διατηρήστε το αντικείμενο υποστήριξης ξεχωριστό από το πρόγραμμα που υποβάλλεται σε fuzzing

Όταν η γραμματική βρίσκεται σε ένα επίθημα filename, η μετάλλαξη μόνο των bytes του αρχείου αναφοράς δεν καλύπτει τον parser. Αντί γι’ αυτό, ένα μικρό harness μπορεί να διαβάσει ένα testcase ως συμβολοσειρά και να το περάσει στο API ανοίγματος interpreted αρχείων· η καμπάνια CFITSIO έφτασε στους περισσότερους parsers και evaluators EFS καλώντας τη `fits_open_file()` σε λειτουργία μόνο για ανάγνωση. Διατηρήστε ξεχωριστά διαθέσιμα έγκυρα αρχεία υποστήριξης, ώστε οι μεταλλάξεις να εστιάζουν στη γλώσσα επιλογέων/εκφράσεων αντί να καταστρέφουν συνεχώς τη βασική διαδρομή.<sup>[[22]](#references)</sup>

Χρησιμοποιήστε seeds που φτάνουν το καθένα σε διαφορετική οικογένεια γραμματικής και, στη συνέχεια, παράγετε ένα συμπαγές λεξικό από την προδιαγραφή και τον πηγαίο κώδικα του lexer/parser. Αν η κάλυψη σταθεροποιηθεί ενώ οι είσοδοι αποτυγχάνουν επανειλημμένα στην ίδια διαδρομή συντακτικού σφάλματος, διατηρήστε έγκυρα prefixes και προσθέστε διαχωριστικά, τελεστές, λέξεις-κλειδιά, ονόματα συναρτήσεων και αντιπροσωπευτικά ονόματα πεδίων, αντί απλώς να αυξήσετε τον χρόνο τυχαίων μεταλλάξεων.<sup>[[22]](#references)</sup>

Εκτελέστε το harness με το λεξικό γραμματικής, για παράδειγμα:<sup>[[3]](#references)[[22]](#references)</sup>

```bash
afl-fuzz -i filename-seeds -o out -x filename-language.dict -- ./filename-harness @@
```

### Περιορισμός των παρενεργειών του harness σε λειτουργία "read-only"

Μια σημαία βιβλιοθήκης read-only δεν εγγυάται testcase χωρίς παρενέργειες: η γλώσσα ονομάτων αρχείων μπορεί να ξαναγράψει την είσοδο, να δημιουργήσει αρχεία εξόδου ή να υλοποιήσει προσωρινά αντικείμενα. Η καμπάνια CFITSIO αρχικά κατέστρεφε seed files και άφηνε απροσδόκητα αρχεία σε όλο το filesystem, οπότε χρειάστηκαν καθαρισμός και απομόνωση.<sup>[[22]](#references)</sup>

- Δώστε σε κάθε worker έναν αναλώσιμο κατάλογο εργασίας και έναν ιδιωτικό προσωρινό κατάλογο.
- Εκθέστε αντίγραφα των canonical backing files· μην αφήνετε ποτέ το target να τροποποιήσει το μοναδικό αντίγραφο του corpus.
- Απενεργοποιήστε την πρόσβαση στο δίκτυο, εκτός αν τα remote backends είναι ο επιδιωκόμενος στόχος, και περιορίστε τις εγγράψιμες διαδρομές με container, mount namespace ή ισοδύναμο sandbox.
- Επαναφέρετε τον κατάλογο μετά από κάθε εκτέλεση ή batch worker και αντιμετωπίστε τις απροσδόκητες αλλαγές στο filesystem ως επιπλέον ευρήματα.

### Βρόχος crash-to-patch-to-fuzz

Ομαδοποιήστε τα crashes πριν από την επιδιόρθωση, ώστε χιλιάδες artifacts να μη μετατραπούν σε χιλιάδες εργασίες patch. Στην αξιολόγηση CFITSIO, το AFLTriage περιόρισε το αρχικό σύνολο crashes σε λίγες βασικές αιτίες· το advisory που προέκυψε παρουσιάζει διακριτές αστοχίες, όπως εσφαλμένους ελέγχους μεγέθους προορισμού, stale pointers μετά από `realloc()`, αριθμητικά σφάλματα και μη ασφαλείς διαδρομές καθαρισμού του parser.<sup>[[21]](#references)[[22]](#references)</sup>

1. Ελαχιστοποιήστε ένα αντιπροσωπευτικό input για κάθε ομάδα και αναπαραγάγετέ το με AddressSanitizer.
2. Καταγράψτε την ακριβή αποτυχημένη πρόσβαση, τη θέση στον πηγαίο κώδικα, το ιστορικό allocation/free και την κατάσταση του parser που οδήγησε στην παραβίαση του invariant.
3. Εφαρμόστε ένα narrowly scoped υποψήφιο patch και κάντε rebuild με τα ίδια όργανα κάλυψης και sanitizer.
4. Επαναλάβετε το αρχικό reproducer **και κάθε input της ομάδας του**· ενεργοποιήστε επίσης τον εντοπισμό leak, επειδή μια διόρθωση memory-safety μπορεί να χαλάσει τη διαχείριση ιδιοκτησίας σε μια διαδρομή σφάλματος.
5. Εκτελέστε λειτουργικές δοκιμές με πραγματικά αρχεία και, στη συνέχεια, συνεχίστε από την ουρά που έχει συσσωρευτεί (ή εισαγάγετε ξανά αυτή την ουρά, αν η μηχανή απαιτεί νέο output directory μετά την αλλαγή του binary).
6. Επαναλάβετε: η αφαίρεση του πρώτου ρηχού crash συχνά επιτρέπει στα υπάρχοντα seeds να προχωρήσουν σε βαθύτερη κατάσταση του parser.

Ένα LLM μπορεί να επιταχύνει το βήμα 2 και να συντάξει ένα αρχικό patch για το βήμα 3, όταν του δοθούν το input που προκαλεί το crash, η αναφορά του sanitizer, το harness και ο σχετικός πηγαίος κώδικας· ωστόσο, το patch του παραμένει μη έμπιστο. Το αν η διόρθωση γίνεται αποδεκτή το καθορίζουν η επανάληψη με sanitizer και οι έλεγχοι regression — όχι η εξήγηση του μοντέλου.<sup>[[22]](#references)</sup>

## Πλουσιότερο feedback όταν το edge coverage συγχωνεύει διαφορετικές διαδρομές

Το συνηθισμένο edge coverage δεν μπορεί να διακρίνει δύο εκτελέσεις που περνούν από τον ίδιο helper μέσω διαφορετικών callers ή ακολουθούν διαφορετικούς συνδυασμούς κλάδων μέσα σε μια συνάρτηση. Αυτό έχει σημασία σε shared decoders, protocol dispatchers και helpers διερμηνευτών, όπου η **διαδρομή** προς ένα edge καθορίζει την ενεργή κατάσταση. Η αφελής παρακολούθηση κάθε calling context είναι επίσης επικίνδυνη: ο χάρτης κάλυψης και η ουρά μπορεί να εκραγούν σε μέγεθος. Γι' αυτό, η έρευνα για context-sensitive fuzzing συνιστά τη βελτίωση μόνο των υποσχόμενων contexts, αντί να αντιμετωπίζεται ολόκληρο το call graph ως context-sensitive.<sup>[[14]](#references)</sup>

Οι πρόσφατες εκδόσεις του AFL++ παρέχουν **Ball-Larus per-function path coverage** επιπλέον του συνηθισμένου edge coverage. Αντιστοιχίζει ένα feature σε κάθε άκυκλη διαδρομή μέσα σε μια συνάρτηση· αφαιρούνται τα loop back-edges, επομένως αυτό το feedback διακρίνει συνδυασμούς κλάδων, αλλά **όχι τον αριθμό επαναλήψεων του loop**. Ξεκινήστε με το χαλαρό επίπεδο `1` και, στη συνέχεια, περιορίστε τις αυστηρότερες λειτουργίες σε ύποπτο κώδικα parser/state-machine, επειδή ο αριθμός των διαδρομών μπορεί να αυξηθεί εκθετικά.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Για μια βοηθητική συνάρτηση που καλείται από πολλές τοποθεσίες σχετικές με την ασφάλεια, η λειτουργία LTO μπορεί να συνδυάσει κάθε διαδρομή συνάρτησης με το άμεσο σημείο κλήσης της:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Καθοδήγηση για την καμπάνια:** εφαρμόστε πιο πλούσιο feedback με σύνεση και παρακολουθείτε το κόστος του coverage-map/queue.<sup>[[13]](#references)[[14]](#references)</sup>

- Εκτελέστε παράλληλα ένα συνηθισμένο instance με edge coverage· το πιο πλούσιο feedback είναι χρήσιμο μόνο αν το επιπλέον κόστος queue/map δεν μειώνει υπερβολικά τις executions ανά δευτερόλεπτο.
- Χρησιμοποιήστε το `AFL_LLVM_ALLOWLIST` για να περιορίσετε το path/caller instrumentation όταν μεγάλες βιβλιοθήκες με πολλά templates ή γενικός κώδικας utilities κυριαρχούν στο map.
- Οι συναρτήσεις με υπερβολικά πολλούς άκυκλους δρόμους μπορούν να παραλειφθούν από το AFL++· οι προειδοποιήσεις κατά τη μεταγλώττιση αποτελούν ένδειξη ότι ο στόχος χρειάζεται allowlisting ή λιγότερο αυστηρό επίπεδο.
- Το caller + path coverage υποστηρίζει μόνο ένα επίπεδο caller. Μην το συνδυάζετε με βαθύτερα context stacks.
- Τα path IDs μπορεί να αλλάξουν ανάμεσα σε major εκδόσεις του LLVM. Διατηρήστε σταθερό το toolchain κατά τη διάρκεια μιας καμπάνιας και μην συγχρονίζετε corpora που βασίζονται σε PATH σαν να ήταν τα feature IDs σταθερά μεταξύ builds.
- Αυτό το feedback συμπληρώνει το `CMPLOG`: το comparison tracing επιλύει το **ποια τιμή περνά έναν guard**, ενώ το path/caller feedback διατηρεί το **ποια διαδρομή και ποιος συνδυασμός branches οδήγησαν εκεί**.

## Stateful Fuzzing: Οι ακολουθίες είναι seeds

Για **protocols**, **authenticated workflows** και **parsers πολλών σταδίων**, η ενδιαφέρουσα μονάδα συχνά δεν είναι ένα μεμονωμένο blob, αλλά μια **ακολουθία μηνυμάτων**. Η συνένωση ολόκληρου του transcript σε ένα αρχείο και η τυφλή μεταβολή του είναι συνήθως αναποτελεσματική, επειδή ο fuzzer μεταβάλλει όλα τα βήματα εξίσου, ακόμη κι όταν μόνο το μεταγενέστερο μήνυμα φτάνει στην ευάλωτη κατάσταση.<sup>[[4]](#references)</sup>

Μια πιο αποτελεσματική προσέγγιση είναι να αντιμετωπίζετε την **ίδια την ακολουθία ως seed** και να χρησιμοποιείτε την **παρατηρήσιμη κατάσταση** (κωδικούς απόκρισης, καταστάσεις protocol, φάσεις parser, τύπους αντικειμένων που επιστρέφονται) ως πρόσθετο feedback.<sup>[[4]](#references)</sup>

- Διατηρήστε σταθερά τα **έγκυρα μηνύματα προθέματος** και εστιάστε τις μεταβολές στο μήνυμα που **οδηγεί στη μετάβαση**.
- Αποθηκεύστε σε cache τα αναγνωριστικά και τις τιμές που δημιουργεί ο server από προηγούμενες αποκρίσεις, όταν το επόμενο βήμα εξαρτάται από αυτές.
- Προτιμήστε mutation/splicing ανά μήνυμα αντί να μεταβάλλετε ολόκληρο το serialized transcript ως αδιαφανές blob.
- Αν το protocol παρέχει ουσιαστικούς κωδικούς απόκρισης, χρησιμοποιήστε τους ως **φθηνό state oracle** για να δίνετε προτεραιότητα στις ακολουθίες που προχωρούν βαθύτερα.

Αυτός είναι και ο λόγος που τα authenticated bugs, οι κρυφές μεταβάσεις ή τα parser bugs που εμφανίζονται «μόνο μετά το handshake» συχνά δεν εντοπίζονται με το vanilla file-style fuzzing: ο fuzzer πρέπει να διατηρεί **τη σειρά, την κατάσταση και τις εξαρτήσεις**, όχι μόνο τη δομή.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing driver πολλών clients

Το υψηλό edge coverage μπορεί και πάλι να μην εντοπίσει bugs στον IPC driver, επειδή το coverage δεν περιγράφει **την ιδιοκτησία αντικειμένων, τους μετρητές αναφορών, τα εκκρεμή μηνύματα, τη σειρά cleanup ή τις αλληλοεπικαλύψεις νημάτων**. Η σελίδα [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) καλύπτει το μοντέλο αντικειμένων του driver· αυτό το παράδειγμα εστιάζει στο fuzzer harness. Το Android Binder αποτελεί χρήσιμο μοντέλο: δεν αρκεί να φτάνει κανείς τόσο στα μονοπάτια allocation όσο και στα μονοπάτια free, αν ο fuzzer δεν μπορεί να κάνει πολλές διεργασίες να λειτουργήσουν πάνω στο ίδιο kernel object με την απαιτούμενη σειρά.<sup>[[15]](#references)</sup>

#### Μοντελοποιήστε το protocol, όχι μεμονωμένα `ioctl` buffers

Αναπαραστήστε ένα test case ως διατεταγμένη γραμματική **ταυτότητας client + operation + δομημένων ορισμάτων**. Ο Binder LKL fuzzer χρησιμοποιεί protobuf και `libprotobuf-mutator`, με έναν persistent context-manager client και δύο συνηθισμένους clients. Ένα semantic harness διατηρεί έπειτα τις σχέσεις που θα κατέστρεφε η τυφλή μεταβολή bytes.<sup>[[15]](#references)</sup>

- Αποθηκεύστε σε cache τις τιμές που επιστρέφουν προηγούμενες operations. Για παράδειγμα, το `BC_FREE_BUFFER` πρέπει να επαναχρησιμοποιήσει έναν δείκτη transaction buffer που επέστρεψε προηγούμενο `ioctl`.
- Δημιουργήστε έγκυρες προεπιλεγμένες replies ώστε να ολοκληρώνονται οι synchronous transactions και να παραμένουν προσβάσιμες οι επόμενες operations.
- Απορρίψτε αδύνατες μεταβάσεις, όπως self-transactions ή πολλαπλές εκκρεμείς transactions προς τον ίδιο στόχο.
- Διατηρήστε την κατάσταση singleton bootstrap έξω από το reset ανά input. Το Binder επιτρέπει μόνο μία εγγραφή `BINDER_SET_CONTEXT_MGR` ανά boot, επομένως η επανειλημμένη καταστροφή και επαναδημιουργία αυτού του client θα καθιστούσε μη έγκυρα τα επόμενα inputs.

Ένα χρήσιμο πρότυπο lifetime-race είναι να μεταφέρει ένας client ένα αντικείμενο, να ξεκινά το cleanup ενός thread ή process και, ταυτόχρονα, ο client που λαμβάνει το αντικείμενο να αποδεσμεύει το transaction buffer. Στο παράδειγμα CVE-2020-0423, η μεταφορά `BINDER_TYPE_WEAK_BINDER` ακολουθούμενη από `BINDER_THREAD_EXIT` σε race με `BC_FREE_BUFFER` μπορούσε να ελευθερώσει ένα ενσωματωμένο `binder_work` ενώ η διαδρομή cleanup του thread που τερματιζόταν εξακολουθούσε να το χρησιμοποιεί.<sup>[[15]](#references)</sup>

#### Επαναφέρετε ελεγχόμενες αλληλοεπικαλύψεις σε έναν kernel userspace

Το [Linux Kernel Library (LKL)](https://github.com/lkl/linux) συνδέει τον πραγματικό κώδικα του kernel σε ένα userspace harness και εκθέτει το syscall interface του μέσω του `lkl_syscall`. Έτσι, ο συντονισμός protobuf state, coverage και KASAN σε μία διεργασία γίνεται εύκολος. Ωστόσο, το LKL συνήθως εκτελεί ένα syscall χωρίς να το διακόπτει κάποιο άλλο kernel thread. Για race campaigns, εισαγάγετε σημεία `schedule()` γύρω από επιλεγμένα όρια lock/unlock και lifetime και, στη συνέχεια, αφήστε το harness να επιλέγει τυχαία τον επόμενο client σε κάθε yield. Κρατήστε αυτά τα σημεία στοχευμένα, επειδή το καθένα πολλαπλασιάζει τον χώρο αναζήτησης του scheduling. Ο randomized scheduler που περιγράφουν οι ερευνητές **δεν** αποτελεί μέρος του upstream Binder fuzzer.<sup>[[15]](#references)</sup>

#### Κάντε build και επαναλάβετε serialized regression seeds

Το upstream harness καθορίζει μια συμβατή έκδοση του `libprotobuf-mutator`, ενεργοποιεί το LKL fuzzing instrumentation και το KASAN με `LKL_FUZZING=1` και ενεργοποιεί το `CONFIG_MMU` για το Binder με `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Αφού κάνετε checkout σε μια σκόπιμα ευάλωτη έκδοση ή εφαρμόσετε τα rollback patches που τεκμηριώνονται upstream, ένα σειριοποιημένο seed μπορεί να αναπαράγει ολόκληρη τη μετάβαση κατάστασης πολλών clients, χωρίς να χρειάζεται να την ανακατασκευάσετε σε ένα ad-hoc C proof of concept:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Αντιμετωπίστε το KASAN use-after-free που προέκυψε ως επιβεβαίωση ότι το seed έφτασε στη vulnerable lifetime path. Δεν αποδεικνύει τα επόμενα primitives που απαιτούνται για kernel code execution ή privilege escalation.<sup>[[16]](#references)</sup>

## Τέχνασμα ποικιλομορφίας σε ένα μηχάνημα (Jackalope-Style)

Ένας πρακτικός τρόπος να συνδυάσετε **generative novelty** με **coverage reuse** είναι να κάνετε **restart σε βραχύβιους workers** απέναντι σε έναν persistent server. Κάθε worker ξεκινά με άδειο corpus, κάνει sync μετά από `T` δευτερόλεπτα, εκτελείται για άλλα `T` δευτερόλεπτα πάνω στο συνδυασμένο corpus, κάνει ξανά sync και μετά τερματίζεται. Έτσι προκύπτουν **fresh structures σε κάθε generation**, ενώ παράλληλα αξιοποιείται η συσσωρευμένη coverage.<sup>[[1]](#references)[[2]](#references)</sup>

**Server:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Διαδοχικοί workers (παράδειγμα loop):**

<details>
<summary>Jackalope worker loop επανεκκίνησης</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Σημειώσεις:**

- Το `-in empty` επιβάλλει ένα **νέο corpus** σε κάθε generation.
- Το `-server_update_interval T` προσεγγίζει τον **καθυστερημένο συγχρονισμό** (πρώτα νέα δεδομένα, αργότερα επαναχρησιμοποίηση).
- Στη λειτουργία grammar fuzzing, ο **αρχικός συγχρονισμός με τον server παραλείπεται από προεπιλογή** (δεν χρειάζεται το `-skip_initial_server_sync`).
- Η βέλτιστη τιμή του `T` **εξαρτάται από τον στόχο**· συνήθως αποδίδει καλύτερα η αλλαγή αφού ο worker εντοπίσει το μεγαλύτερο μέρος του «εύκολου» coverage.

## Snapshot Fuzzing για στόχους που είναι δύσκολο να προετοιμαστούν για δοκιμή

Όταν ο κώδικας που θέλετε να δοκιμάσετε γίνεται προσβάσιμος **μόνο μετά από σημαντικό κόστος προετοιμασίας** (εκκίνηση VM, ολοκλήρωση σύνδεσης, λήψη packet, parsing container, αρχικοποίηση service), μια χρήσιμη εναλλακτική είναι το **snapshot fuzzing**: καταγράψτε την έτοιμη κατάσταση της διεργασίας ή της VM, εισαγάγετε κάθε test case στη διαδρομή εισόδου του στόχου, εκτελέστε μέχρι να προκύψει crash/timeout και επαναφέρετε το snapshot. Έτσι αποφεύγεται η επανάληψη της αρχικοποίησης ή των προθεμάτων του πρωτοκόλλου, και είναι χρήσιμο για **network services**, **firmware**, **επιφάνειες επίθεσης μετά την αυθεντικοποίηση** και **στόχους που διατίθενται μόνο ως δυαδικά αρχεία**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Εκτελέστε τον στόχο μέχρι να είναι έτοιμη η ενδιαφέρουσα κατάσταση.
2. Δημιουργήστε snapshot της **μνήμης + των registers** σε εκείνο το σημείο.
3. Για κάθε test case, γράψτε το mutated input απευθείας στο σχετικό buffer της διεργασίας/guest.
4. Εκτελέστε μέχρι να προκύψει crash/timeout/reset.
5. Επαναφέρετε το snapshot· για στόχους VM, επαναφέρετε μόνο τις **τροποποιημένες σελίδες**, εφόσον υποστηρίζεται, και επαναλάβετε.

Τοποθετήστε το snapshot όσο το δυνατόν πιο κοντά στο πρώτο βήμα parsing/dispatch που έχει υψηλό κόστος, όπως μετά από ένα σημείο `recv`/`read` ή αποσειριοποίησης packet, και καταγράψτε το input buffer που χρησιμοποιεί ο στόχος. Αυτό ακολουθεί την αρχή της προσαρμοστικής τοποθέτησης: μετακινήστε το snapshot βαθύτερα στην επεξεργασία εισόδου, ώστε να αποφύγετε την επανάληψη εργασιών.<sup>[[11]](#references)</sup>

## Εξερεύνηση Race στον πυρήνα Linux με το MAccConc

Το [MAccConc](https://github.com/googleprojectzero/MAccConc) μετατρέπει τα race conditions του πυρήνα Linux που είναι ευαίσθητα στον χρονισμό σε επαναλήψιμα χρονοδιαγράμματα προσβάσεων στη μνήμη. Μπορεί να απαριθμήσει αυτόματα εκτελέσεις **A-B-A** σε δύο contexts ή να επιτρέψει σε έναν αναλυτή να ορίσει περιορισμούς σειράς μέσω terminal UI/GUI. Πρόκειται για πειραματικό ερευνητικό εργαλείο και όχι για ολοκληρωμένο concurrency fuzzer: προς το παρόν απαιτεί LLVM 23+ και τον τροποποιημένο πυρήνα του project, τα εργαλεία γραμμής εντολών υποστηρίζουν δύο test threads και το προτεινόμενο επίπεδο fuzzing σε userspace δεν έχει υλοποιηθεί.<sup>[[17]](#references)[[18]](#references)</sup>

### Συλλογή σημείων επικοινωνίας μεταξύ contexts

Δημιουργήστε τον instrumented πυρήνα με callbacks outline του KASAN και την τροποποιημένη υποστήριξη KCOV για καταγραφή μνήμης. Το README του project συνιστά επίσης την απενεργοποίηση της βελτιστοποίησης sibling-call, ώστε να παραμένουν αξιοποιήσιμα τα call stacks.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

Η λειτουργία outline του KASAN (`asan-instrumentation-with-call-threshold=0`) μετατρέπει τις προσπελάσεις με instrumentation σε κλήσεις βοηθητικών συναρτήσεων. Τα patches του πυρήνα MAccConc απενεργοποιούν το `asan-opt-same-temp`, ώστε οι διαδοχικές προσπελάσεις να μη συγχωνεύονται· απενεργοποιήστε επίσης τη βελτιστοποίηση `asan-opt-globals` όταν πρέπει να είναι ορατά τα data races σε global μεταβλητές. Το KCOV μεταφέρει τις εγγραφές που προκύπτουν στον χώρο χρήστη. Συγκρίνετε προσπελάσεις από διαφορετικά περιβάλλοντα εκτέλεσης και κρατήστε τα ζεύγη των οποίων τα εύρη byte επικαλύπτονται και όπου τουλάχιστον η μία πλευρά κάνει εγγραφή· μοντελοποιήστε το `kfree()` ως εγγραφή, ώστε οι μεταβάσεις διάρκειας ζωής να είναι επίσης υποψήφιες.<sup>[[17]](#references)</sup>

Για εργασία που συνεχίζεται εκτός της αρχικής διεργασίας, όπως η επεξεργασία πακέτων ή οι callbacks του RCU, το υποσύστημα πρέπει να μεταβιβάζει ένα handle απομακρυσμένης κάλυψης KCOV. Το upstream remote KCOV είναι προαιρετικό και δεν είναι διαθέσιμο αυτόματα για αυθαίρετη εργασία παρασκηνίου, επομένως η απουσία μεταβίβασης μπορεί να καταστήσει αόρατη μια πραγματική αλληλεπίδραση.<sup>[[17]](#references)[[19]](#references)</sup>

### Εντοπισμός της ίδιας δυναμικής πρόσβασης σε κάθε εκτέλεση

Μην επαναλαμβάνετε την εκτέλεση χρησιμοποιώντας μια συγκεκριμένη διεύθυνση heap, η οποία μπορεί να αλλάξει μετά από κάθε allocation, ούτε μόνο μια διεύθυνση εντολής, η οποία είναι αμφίσημη μέσα σε helpers όπως τα `memcpy()` και `spin_lock()`. Το MAccConc χρησιμοποιεί ένα **ίχνος στοίβας εμπλουτισμένο με μετρητές**: κάθε frame προσδιορίζει έναν callee μαζί με τον αριθμό κλήσης του μέσα στον caller του, ενώ το τελευταίο στοιχείο προσδιορίζει την εντολή πρόσβασης στη μνήμη. Οι εγγραφές εισόδου/εξόδου συναρτήσεων του SanitizerCoverage επιτρέπουν στον χώρο χρήστη να ανακατασκευάσει αυτό το δυναμικό αναγνωριστικό, το οποίο παραμένει σταθερό παρά τις αλλαγές διευθύνσεων και τον άσχετο θόρυβο στη ροή ελέγχου.<sup>[[17]](#references)</sup>

### Μετατροπή των υποψήφιων ζευγών σε εξαναγκασμένα προγράμματα χρονοπρογραμματισμού

Το patched ioctl `KCOV_SET_DI` συσχετίζει ένα αναγνωριστικό πρόσβασης εμπλουτισμένο με μετρητές με μια ενέργεια κοινόχρηστης σημαίας.<sup>[[17]](#references)</sup>

| Ενέργεια | Σημασιολογία |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Ορίζει τη σημαία *N* αμέσως πριν από την επιλεγμένη πρόσβαση. |
| `DI_STACK_WAIT` | Πριν από την επιλεγμένη πρόσβαση, περιμένει σε βρόχο μέχρι να οριστεί η σημαία *N* ή να λήξει το διαμορφωμένο όριο. |
| `DI_STACK_WAKE_POST` | Ορίζει τη σημαία *N* αμέσως μετά την επιλεγμένη πρόσβαση. |

Για έναν μερικό περιορισμό **A-happens-before-B**, συνδέστε το `DI_STACK_WAKE_POST` με το A και το `DI_STACK_WAIT` με το B χρησιμοποιώντας την ίδια σημαία. Για ένα πλήρως καθορισμένο πρόγραμμα χρονοπρογραμματισμού δύο περιβαλλόντων εκτέλεσης, ξεκινήστε το B σε αναμονή και έπειτα κάντε το A να αφυπνίσει το B και να περιμένει στο πρώτο σημείο μεταβίβασης· το B εκτελεί την αντίστροφη ενέργεια στην επόμενη μεταβίβαση. Η δεύτερη προσέγγιση λειτουργεί σαν ντετερμινιστική εναλλαγή περιβάλλοντος και χρησιμοποιείται από τον αυτόματο εξερευνητή A-B-A.<sup>[[17]](#references)</sup>

Μια ελάχιστη εκστρατεία είναι να μεταγλωττίσετε την περίπτωση δοκιμής με τα τέσσερα hooks (`test_setup`, δύο συναρτήσεις νημάτων και `test_end`) ως shared library, να συλλέξετε ένα ίχνος χωρίς περιορισμούς και έπειτα να απαριθμήσετε υποψήφια A-B-A ή να προσθέσετε χειροκίνητους περιορισμούς γύρω από ύποπτες προσπελάσεις.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Ερμηνεύστε τα timeouts ξεχωριστά από τις επιτυχείς αναδιατάξεις: η ζητούμενη σειρά μπορεί να είναι αδύνατη, επειδή ένα lock ή μια εξάρτηση αρχικοποίησης/δημοσίευσης εμποδίζει το δεύτερο context να φτάσει στο σημείο injection. Έχετε επίσης υπόψη τα τυφλά σημεία του KASAN: οι άμεσες προσπελάσεις στη στοίβα συνήθως δεν ελέγχονται, εκτός αν ενδέχεται να είναι εκτός ορίων, οι καθολικές μεταβλητές παραλείπονται με τη βελτιστοποίηση από προεπιλογή και οι τρέχοντες compilers δεν μπορούν να εκπέμψουν ταυτόχρονα hooks για ASAN και TSAN. Τέλος, το prototype χάνει το buffer του KCOV όταν ένα guest καταρρέει, γι’ αυτό διατηρήστε μια ανεξάρτητη κονσόλα/oracle για crashes.<sup>[[17]](#references)</sup>

Για μελλοντικό concurrency-guided fuzzing, καταγράψτε περιλήψεις προσπελάσεων μνήμης ανά input ή syscall, συνδυάστε λειτουργίες που θα αποτελούσαν σημεία επικοινωνίας μεταξύ contexts και, στη συνέχεια, εξερευνήστε μόνο αυτούς τους συνδυασμούς. Τα VM snapshots σταθεροποιούν την καθολική κατάσταση και τις διευθύνσεις· χωρίς snapshots, τα μεταδεδομένα του σημείου κατανομής μπορούν να αφαιρούν την εξάρτηση των αντικειμένων από συγκεκριμένες εκτελέσεις. Αυτή είναι μια προτεινόμενη επέκταση, όχι λειτουργία των τρεχόντων userspace εργαλείων του MAccConc.<sup>[[17]](#references)</sup>

## Ενδοσκόπηση Harness: Εντοπίστε έγκαιρα τα επιφανειακά fuzzers

Όταν μια καμπάνια κολλάει, συχνά το πρόβλημα δεν είναι ο mutator αλλά το **harness**. Χρησιμοποιήστε **ενδοσκόπηση προσβασιμότητας/κάλυψης** για να εντοπίσετε συναρτήσεις που είναι στατικά προσβάσιμες από τον στόχο fuzzing, αλλά καλύπτονται σπάνια ή καθόλου δυναμικά. Αυτές οι συναρτήσεις συνήθως υποδεικνύουν ένα από τρία προβλήματα.<sup>[[12]](#references)</sup>

- Το harness εισέρχεται στον στόχο πολύ αργά ή πολύ νωρίς.
- Από το seed corpus λείπει μια ολόκληρη οικογένεια λειτουργιών.
- Ο στόχος χρειάζεται πραγματικά ένα **δεύτερο harness** αντί για ένα υπερβολικά μεγάλο harness που «τα κάνει όλα».

Αν χρησιμοποιείτε ροές εργασίας τύπου OSS-Fuzz / ClusterFuzz, το Fuzz Introspector μπορεί να συγκρίνει τη στατική προσβασιμότητα με την κάλυψη κατά την εκτέλεση και να δημιουργήσει αναφορές από μια εκτέλεση με χρονικό όριο ή από ένα δημόσιο corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Χρησιμοποιήστε την αναφορά για να αποφασίσετε αν θα προσθέσετε ένα νέο harness για μια μη δοκιμασμένη διαδρομή parser, θα επεκτείνετε το corpus για μια συγκεκριμένη δυνατότητα ή θα χωρίσετε ένα μονολιθικό harness σε μικρότερα entry points.

## Επιλογή fuzz target με προτεραιότητα το γράφημα και διαλογή μεταλλάξεων

Αν έχετε ήδη ευρήματα **static analysis**, **mutation-testing survivors** και αναφορές **coverage**, μην τα διαχειριστείτε ως ανεξάρτητες λίστες. Κατασκευάστε πρώτα ένα **call graph**, προσθέστε στους κόμβους πληροφορίες για την **cyclomatic complexity**, την **προσβασιμότητα από entrypoints/μη έμπιστες εισόδους** και τυχόν εξωτερικά ευρήματα και, στη συνέχεια, εξετάστε ερωτήματα για το γράφημα.<sup>[[5]](#references)[[6]](#references)</sup>

- Ποιες συναρτήσεις υψηλής πολυπλοκότητας είναι προσβάσιμες από μη έμπιστες εισόδους;
- Ποιοι mutation survivors βρίσκονται σε διαδρομές από parsers/handlers προς κώδικα κρίσιμο για την ασφάλεια;
- Ποιες συναρτήσεις αποτελούν αρχιτεκτονικά choke points με ασυνήθιστα μεγάλο **blast radius**;

Αυτή η προσέγγιση συνήθως αναδεικνύει καλύτερους στόχους fuzzing από την απλή επιλογή βάσει «χαμηλότερου coverage». Ένας parser/decoder με **υψηλή πολυπλοκότητα** και επιβεβαιωμένη **εξωτερική προσβασιμότητα** είναι ισχυρότερος υποψήφιος για harness από έναν απομονωμένο εσωτερικό helper με χαμηλό coverage αλλά χωρίς διαδρομή ελεγχόμενη από επιτιθέμενο.

### Πρακτική ροή διαλογής

1. Κατασκευάστε ένα **code graph** από τη βάση κώδικα και εξαγάγετε μετρικές πολυπλοκότητας/διακλαδώσεων ανά συνάρτηση.
2. Καταγράψτε τα **entrypoints** που δέχονται είσοδο ελεγχόμενη από επιτιθέμενο: request handlers, decoders, importers, protocol parsers, αναγνώστες CLI/αρχείων.
3. Εκτελέστε ερωτήματα διαδρομών από αυτά τα entrypoints προς υποψήφιες συναρτήσεις, ώστε να διαχωρίσετε την προσβάσιμη επιφάνεια επίθεσης από τον ανενεργό κώδικα ή τον κώδικα που χρησιμοποιείται μόνο εσωτερικά.
4. Δώστε προτεραιότητα σε κόμβους που συνδυάζουν:
   - υψηλή **cyclomatic complexity**
   - επιβεβαιωμένη **προσβασιμότητα από μη έμπιστη είσοδο**
   - μεγάλο **blast radius** ή πολλούς εξαρτώμενους κόμβους
   - επιβεβαιωτικά στοιχεία, όπως ευρήματα **SARIF**, σημειώσεις ελέγχου ή mutation survivors
5. Γράψτε πρώτα εστιασμένα harnesses για τους κόμβους με την υψηλότερη βαθμολογία, ιδιαίτερα για **parsers/codecs**, όπως decoders hex/Base64/IP/message.

### Mutation survivors: ισοδύναμα ή αξιοποιήσιμα

Το mutation testing συχνά παράγει μια λίστα survivors με πολύ θόρυβο. Πριν θεωρήσετε κάθε survivor κενό ασφαλείας, χρησιμοποιήστε το γράφημα για να εξετάσετε τα εξής:

- Είναι η μεταλλαγμένη συνάρτηση προσβάσιμη από entrypoint που ελέγχεται από επιτιθέμενο;
- Περιορίζονται όλες οι διαδρομές κλήσεων από ισχυρότερα invariants σε σχέση με τον μεταλλαγμένο έλεγχο;
- Βρίσκεται ο κόμβος σε νεκρό κώδικα, σε λογική που αφορά μόνο τη μορφοποίηση ή σε διαδρομή αριθμητικής/parser με υψηλό αντίκτυπο;

Οι survivors που παραμένουν απρόσιτοι ή περιορίζονται δομικά είναι συχνά **equivalent mutants**. Οι survivors που παραμένουν **προσβάσιμοι** και επηρεάζουν **οριακές συνθήκες**, **διαδρομές overflow/carry** ή **αριθμητική/ανάλυση κρίσιμη για την ασφάλεια** θα πρέπει να προωθούνται σε:

- νέα fuzz harnesses
- άμεσα property/invariant tests
- στοχευμένα διανύσματα ακραίων περιπτώσεων

### Συσχετίστε τα εξωτερικά ευρήματα με το γράφημα

Αν το pipeline SAST εξάγει **SARIF**, αντιστοιχίστε τα ευρήματα στους κόμβους του γραφήματος βάσει **αρχείου + εύρους γραμμών** και χρησιμοποιήστε το γράφημα για να επεκτείνετε την ανάλυση του αντίκτυπου.<sup>[[6]](#references)</sup>

- υπολογίστε το **blast radius** της επισημασμένης συνάρτησης
- ελέγξτε αν το εύρημα βρίσκεται σε κάποια διαδρομή από entrypoint
- ομαδοποιήστε κοντινά ευρήματα που καταλήγουν στο ίδιο choke point

Αυτό είναι χρήσιμο όταν αποφασίζετε αν αξίζει να αφιερώσετε χρόνο σε fuzzing μιας συγκεκριμένης συνάρτησης: ένας κόμβος που είναι **προσβάσιμος**, **πολύπλοκος** και έχει ήδη **ευρήματα SAST** είναι συχνά καλύτερος στόχος από έναν απλώς πολύπλοκο κόμβο χωρίς διαδρομή που να ελέγχεται από επιτιθέμενο.

Παράδειγμα ροής εργασίας με το Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Η σημαντική μεθοδολογία είναι η τομή: **πολυπλοκότητα x έκθεση x αντίκτυπος**. Χρησιμοποίησε το γράφημα για να επιλέξεις fuzz targets με την υψηλότερη αναμενόμενη αξία για την ασφάλεια και, στη συνέχεια, χρησιμοποίησε τους mutation survivors για να αποφασίσεις ποια όρια και invariants πρέπει να δοκιμάζει εντατικά το harness σου.<sup>[[5]](#references)</sup>

## Fuzzing στο Go με gosentry: Ισχυρότερη μηχανή, τυποποιημένες είσοδοι και διαφορικοί έλεγχοι

Αν ένας στόχος Go έχει ήδη ένα native harness `testing.F`, μια πρακτική διαδρομή αναβάθμισης είναι να εκτελέσεις το ίδιο harness με το [gosentry](https://github.com/trailofbits/gosentry), ένα forked toolchain του Go που διατηρεί το `go test -fuzz`, αλλά αντικαθιστά το backend με το **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Αυτό είναι χρήσιμο όταν ο native Go fuzzer κολλάει σε **δύσκολες συγκρίσεις**, **τυποποιημένες εισόδους** ή **μορφότυπα με πολλή ανάλυση**. Η μεθοδολογία παραμένει ίδια:

- Συνέχισε να χρησιμοποιείς το `f.Add(...)` για seeds και το `f.Fuzz(...)` για το callback.
- Χρησιμοποίησε ξανά το ίδιο harness, αλλά εκτέλεσέ το με το binary `go` του gosentry αντί για το stock toolchain.
- Αντιμετώπισε την εκστρατεία που προκύπτει ως κανονική εκτέλεση με καθοδήγηση από την κάλυψη, αλλά με scheduling/mutation του LibAFL και καλύτερους περιβάλλοντες detectors.

### Μετατροπή των σιωπηλών αποτυχιών σε ευρήματα fuzzing

Ένα συχνό πρόβλημα στις αξιολογήσεις Go είναι ότι η επικίνδυνη συμπεριφορά συχνά **δεν** προκαλεί crash από προεπιλογή. Με το gosentry, μπορείς να μετατρέψεις αρκετές κατηγορίες «κακών αλλά σιωπηλών» καταστάσεων σε ευρήματα.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` για να κάνεις επιλεγμένες διαδρομές καταγραφής σφαλμάτων να συμπεριφέρονται σαν crashes (χρήσιμο για διαδρομές κώδικα τύπου `log.Fatal` που διαφορετικά απλώς καταγράφουν το συμβάν και συνεχίζουν).
- `--catch-races=true` για να επανεκτελείς τις νέες εγγραφές της ουράς που ανακαλύπτονται με τον race detector της Go.
- `--catch-leaks=true` για να επανεκτελείς τις νέες εγγραφές της ουράς με το `goleak` και να σταματάς σε περίπτωση διαρροών goroutine.
- Διαχείριση hang του LibAFL, ώστε να διατηρούνται οι **άπειροι βρόχοι / πολύ αργές είσοδοι** ως ευρήματα fuzzing, αντί να χάνονται ως timeouts.
- Ενσωματωμένοι έλεγχοι αριθμητικής υπερχείλισης από προεπιλογή, καθώς και προαιρετικοί έλεγχοι truncation μέσω instrumentation τύπου go-panikint.

Αυτό είναι ιδιαίτερα χρήσιμο για στόχους όπου ο αντίκτυπος στην ασφάλεια προέρχεται από **αποτυχία parser χωρίς panic**, **σφάλμα ταυτόχρονης εκτέλεσης** ή **hang που προκαλεί μόνο DoS**, αντί για αλλοίωση μνήμης.

### Fuzzing με επίγνωση των struct για τυποποιημένα Go API

Το native Go fuzzing περιμένει κυρίως scalar τιμές όπως `[]byte`, `string` και αριθμούς. Αν ο υπό δοκιμή κώδικας δέχεται τυποποιημένα αντικείμενα, το gosentry μπορεί να κάνει fuzz **σύνθετες τιμές** απευθείας (structs, slices, arrays, pointers), ενώ συνεχίζει να μεταλλάσσει τα υποκείμενα bytes.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Χρησιμοποιήστε το όταν η δημιουργία ενός ψεύτικου wire format μόνο για fuzzing θα έκρυβε λογικά σφάλματα πίσω από κώδικα parsing που υπάρχει μόνο στο harness. Για differential ή grammar-based campaigns, διατηρήστε την είσοδο του harness ως ένα μόνο `[]byte` ή `string` και κάντε το parsing μέσα στο callback.

### Grammar-based fuzzing για parsers και εισόδους πρωτοκόλλων

Για parsers, formats και γλώσσες εισόδου, το gosentry μπορεί να εκτελέσει **Nautilus grammar fuzzing** πάνω από το LibAFL. Η γραμματική είναι ένας πίνακας JSON με κανόνες παραγωγής και το harness συνήθως πρέπει να δέχεται ένα μόνο όρισμα `[]byte` ή `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Σημειώσεις μεθοδολογίας:

- Χρησιμοποιήστε grammar mode όταν οι μεταλλάξεις σε επίπεδο byte αποτυγχάνουν κυρίως σε πρώιμους ελέγχους σύνταξης.
- Περιορίστε τη γραμματική στο **σχετικό με την ασφάλεια υποσύνολο** της γλώσσας/του πρωτοκόλλου, αντί να μοντελοποιείτε ολόκληρη την προδιαγραφή.
- Χρησιμοποιήστε μεγάλες οριακές τιμές σε terminals/nonterminals για να δοκιμάσετε τα όρια ακεραίων, μήκους και μηχανών καταστάσεων.
- Το grammar mode διατηρεί τις εισόδους έγκυρες ως προς τη γραμματική, αλλά ο στόχος εξακολουθεί να λαμβάνει **bytes/strings**, οπότε η ανάλυση και οι σημασιολογικοί έλεγχοι παραμένουν μέσα στον κώδικα που έχει ενσωματωθεί στο harness.

### Differential fuzzing: συγκρίνετε υλοποιήσεις, όχι μόνο crashes

Ένα ισχυρό μοτίβο για τα οικοσυστήματα Go είναι το **grammar-based differential fuzzing**: δημιουργήστε έγκυρες δομημένες εισόδους και δώστε τις σε δύο parsers, clients ή μηχανές μετάβασης καταστάσεων.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Αντιμετωπίστε τα εξής ως ευρήματα:

- η μία υλοποίηση κάνει panic, ενώ η άλλη απορρίπτει το input κανονικά
- ασυμφωνίες μεταξύ αποδεκτών και απορριπτόμενων input
- διαφορετικά parse trees ή αποκωδικοποιημένα objects
- αποκλίνουσες μεταβάσεις κατάστασης, nonces, υπόλοιπα ή state roots

Αυτός είναι ένας πρακτικός τρόπος εντοπισμού **ασυμφωνιών συναίνεσης**, **ασάφειας parser** και **απόκλισης προδιαγραφής-υλοποίησης**, τις οποίες συχνά δεν εντοπίζει το απλό crash fuzzing.

### Επαναχρησιμοποιήστε το corpus της καμπάνιας για αναφορά κάλυψης

Μετά από μια καμπάνια, αναπαράγετε το αποθηκευμένο corpus της ουράς για να δημιουργήσετε αναφορά κάλυψης Go, χωρίς να εξαγάγετε χειροκίνητα ξεχωριστό corpus.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Εκτελέστε την εντολή από το **ίδιο package** και με τον **ίδιο στόχο `-fuzz`**, ώστε το gosentry να επιλύσει τη σωστή αποθηκευμένη κατάσταση campaign.
