## Mutational Grammar Fuzzing: Coverage проти семантики

У **mutational grammar fuzzing** вхідні дані мутуються зі збереженням **граматичної коректності**. У режимі з керуванням за coverage як corpus seeds зберігаються лише зразки, що забезпечують **нове coverage**. Для **мовних цілей** (парсерів, інтерпретаторів, рушіїв) це може пропустити баги, для яких потрібні **ланцюжки семантичних залежностей/потоків даних**, де результат одного конструкта стає входом для іншого.<sup>[[1]](#references)</sup>

**Сценарій збою:** fuzzer знаходить seeds, які окремо задіюють `document()` і `generate-id()` (або подібні примітиви), але **не зберігає ланцюжок потоку даних**, тож зразок, «ближчий до бага», відкидається, бо не забезпечує нового coverage. За наявності **3+ залежних кроків** випадкова рекомбінація стає затратною, а зворотний зв’язок від coverage не спрямовує пошук.<sup>[[1]](#references)</sup>

**Висновок:** для граматик із великою кількістю залежностей варто розглянути **гібридизацію мутаційного та генеративного етапів** або надавати перевагу шаблонам **ланцюжків функцій** (а не лише coverage).<sup>[[1]](#references)</sup>

## Підводні камені різноманітності corpus

Мутації з керуванням за coverage **жадібні**: зразок із новим coverage зберігається одразу, часто зберігаючи великі незмінені фрагменти. З часом у corpus накопичуються **майже дублікати** з низькою структурною різноманітністю. Агресивна мінімізація може прибрати корисний контекст, тому практичний компроміс — **мінімізація з урахуванням граматики**, яка **зупиняється після досягнення мінімального порога токенів** (прибирає зайве, але зберігає достатньо навколишньої структури для зручних мутацій).<sup>[[1]](#references)</sup>

Практичне правило для corpus у мутаційному fuzzing: **віддавайте перевагу невеликій кількості структурно різних seeds, що максимізують coverage**, а не великій купі майже дублікатів. На практиці це зазвичай означає таке.<sup>[[1]](#references)[[3]](#references)</sup>

- Починайте з **зразків із реального світу** (публічних корпусів, зібраних під час crawling даних, перехопленого трафіку, наборів файлів з екосистеми цільового проєкту).
- Скоротіть їх за допомогою **мінімізації corpus на основі coverage**, а не зберігайте кожен коректний зразок.
- Тримайте seeds **достатньо малими**, щоб мутації зачіпали значущі поля, а не витрачали більшість циклів на нерелевантні байти.
- Повторно запускайте мінімізацію corpus після значних змін harness або інструментації, оскільки «найкращий» corpus змінюється зі зміною досяжності коду.

## Мутації з урахуванням порівнянь для магічних значень

Часта причина, чому fuzzer перестає знаходити нові результати, — не синтаксис, а **жорсткі порівняння**: магічні байти, перевірки довжини, рядки enum, контрольні суми або значення диспетчеризації парсера, перевірені через `memcmp`, таблиці switch або каскадні порівняння. Суто випадкові мутації марно витрачають цикли, намагаючись вгадати ці значення байт за байтом.

Для таких цілей використовуйте **трасування порівнянь** (наприклад, `CMPLOG` у AFL++ або процеси на кшталт Redqueen), щоб fuzzer міг бачити операнди невдалих порівнянь і спрямовувати мутації до значень, які їх задовольняють.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Практичні примітки:**

- Це особливо корисно, коли ціль приховує складну логіку за **підписами файлів**, **дієсловами протоколу**, **тегами типів** або **бітами функцій, залежними від версії**.
- Поєднуйте це зі **словниками**, отриманими з реальних зразків, специфікацій протоколів або журналів налагодження. Невеликий словник із токенами граматики, назвами чанків, дієсловами та роздільниками часто цінніший за величезний загальний список слів.
- Якщо ціль виконує багато послідовних перевірок, спершу пройдіть найперші порівняння «магічних» значень, а потім знову мінімізуйте отриманий корпус, щоб наступні етапи починалися з уже коректних префіксів.

## Fuzzing API файлів, що приховують мову імен файлів

Параметр із назвою `filename`, `path` або `URL` може бути точкою входу інтерпретатора, а не буквальним пошуком файлу. Наприклад, CFITSIO Extended Filename Syntax (EFS) обробляє селектори в квадратних дужках, вирази рядків/пікселів, обчислювані стовпці, гістограми й перетворення, перш ніж повернути відкритий об’єкт; деякі форми також створюють тимчасові копії. Під час картографування поверхні атаки класифікуйте кожен API відкриття/імпорту як **literal-path** або **interpreted-path**, а потім виконуйте fuzzing на робочій точці входу, яку фактично викликають застосунки.<sup>[[20]](#references)[[22]](#references)</sup>

Про примітиви SSRF, копіювання файлів і обробників протоколів, що виникають у результаті, а також безпечніші API для буквальних шляхів див. [Мінімови імен файлів як примітиви SSRF/роботи з файлами](../pentesting-web/ssrf-server-side-request-forgery/index.html#filename-mini-languages-as-ssrffile-primitives-cfitsio-efs).<sup>[[20]](#references)</sup>

### Тримайте базовий об’єкт окремо від програми, що проходить fuzzing

Якщо граматика міститься в суфіксі імені файлу, зміна лише байтів указаного файлу не охопить парсер. Натомість невеликий harness може зчитати один тестовий випадок як рядок і передати його API відкриття з інтерпретацією; кампанія CFITSIO охопила більшість парсерів і обчислювачів EFS, викликаючи `fits_open_file()` у режимі лише для читання. Тримайте коректні базові файли окремо, щоб зміни зосереджувалися на мові селекторів/виразів, а не постійно пошкоджували базовий шлях.<sup>[[22]](#references)</sup>

Використовуйте сіди, кожен з яких охоплює окрему родину граматики, а потім створіть компактний словник на основі специфікації та коду лексичного аналізатора/парсера. Якщо покриття перестає зростати, а вхідні дані раз у раз завершуються на тому самому шляху синтаксичної помилки, збережіть коректні префікси й додайте роздільники, оператори, ключові слова, назви функцій і характерні назви полів, замість того щоб лише збільшувати час випадкової зміни.<sup>[[22]](#references)</sup>

Запустіть harness зі словником граматики, наприклад:<sup>[[3]](#references)[[22]](#references)</sup>

```bash
afl-fuzz -i filename-seeds -o out -x filename-language.dict -- ./filename-harness @@
```

### Обмеження побічних ефектів «read-only» harness

Прапорець бібліотеки read-only не гарантує, що testcase не матиме побічних ефектів: мова імен файлів може перезаписувати вхідні дані, створювати вихідні файли або матеріалізувати тимчасові об’єкти. Кампанія з CFITSIO спочатку знищувала seed-файли й залишала неочікувані файли по всій файловій системі, тож знадобилися очищення та ізоляція.<sup>[[22]](#references)</sup>

- Виділіть кожному worker окрему тимчасову робочу директорію.
- Надавайте копії канонічних файлів-основ; не дозволяйте цілі змінювати єдину копію корпусу.
- Вимкніть мережевий доступ, якщо віддалені backend-и не є ціллю тестування, і обмежте доступні для запису шляхи за допомогою контейнера, простору імен монтувань або еквівалентного sandbox.
- Скидайте стан директорії після кожного запуску або пакета worker-ів і розглядайте неочікувані зміни файлової системи як додаткові знахідки.

### Цикл «crash-to-patch-to-fuzz»

Перед виправленням згрупуйте збої, щоб тисячі артефактів не перетворилися на тисячі завдань із виправлення. Під час оцінювання CFITSIO AFLTriage звузив початковий набір збоїв до кількох першопричин; у результаті advisory описує різні помилки, зокрема некоректні перевірки розміру буфера призначення, застарілі вказівники після `realloc()`, арифметичні помилки та небезпечні шляхи очищення парсера.<sup>[[21]](#references)[[22]](#references)</sup>

1. Мінімізуйте репрезентативний вхідний файл для кожного кластера та відтворіть збій за допомогою AddressSanitizer.
2. Запишіть точну операцію доступу, що спричинила збій, розташування в коді, історію виділення/звільнення пам’яті та стан парсера, через який інваріант став хибним.
3. Застосуйте одне вузькоспрямоване виправлення-кандидат і перебудуйте програму з тією самою інструментацією покриття та санітайзера.
4. Повторно відтворіть початковий testcase **і кожен вхідний файл із його кластера**; також увімкніть виявлення витоків, оскільки виправлення помилки безпеки пам’яті може порушити керування пам’яттю на шляху обробки помилки.
5. Запустіть функціональні тести на реальних файлах, а потім продовжте роботу з накопиченою чергою (або імпортуйте її повторно, якщо рушій після зміни бінарного файла вимагає нової вихідної директорії).
6. Повторюйте цикл: усунення першого поверхневого збою часто дає наявним seed-файлам змогу пройти глибше в стан парсера.

LLM може пришвидшити крок 2 та підготувати чернетку для кроку 3, якщо надати їй вхідний файл, що спричинив збій, звіт санітайзера, harness і відповідний вихідний код, але її виправленням не можна довіряти. Рішення про прийняття виправлення ухвалюють за результатами повторного запуску санітайзера та регресійних перевірок, а не на основі пояснення моделі.<sup>[[22]](#references)</sup>

## Багатший зворотний зв’язок, коли покриття ребер не розрізняє різні шляхи

Звичайне покриття ребер не може розрізнити два виконання, які проходять через ту саму допоміжну функцію з різних викликачів або проходять різні комбінації гілок усередині функції. Це важливо для спільних декодерів, диспетчерів протоколів і допоміжних функцій інтерпретатора, де **шлях** до ребра визначає актуальний стан. Наївне відстеження кожного контексту виклику також небезпечне: карта покриття та черга можуть розростися до надмірних розмірів. Тому дослідження контекстно-залежного fuzzing рекомендують уточнювати лише перспективні контексти, а не вважати весь граф викликів контекстно-залежним.<sup>[[14]](#references)</sup>

Останні збірки AFL++ надають **покриття шляхів Ball-Larus для кожної функції** на додаток до звичайного покриття ребер. Цей механізм призначає окрему ознаку кожному ациклічному шляху через функцію; зворотні ребра циклів вилучаються, тож такий зворотний зв’язок розрізняє комбінації гілок, але **не кількість ітерацій циклу**. Почніть із помірного рівня `1`, а суворіші режими застосовуйте лише до підозрілого коду парсера або машини станів, оскільки кількість шляхів може зростати експоненційно.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Для допоміжної функції, яку викликають із багатьох місць, важливих з погляду безпеки, режим LTO може поєднати шлях виконання кожної функції з її безпосереднім місцем виклику:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Рекомендації для кампанії:** обережно застосовуйте багатший зворотний зв’язок і стежте за витратами на карту покриття та чергу.<sup>[[13]](#references)[[14]](#references)</sup>

- Паралельно запустіть звичайний екземпляр із покриттям ребер; багатший зворотний зв’язок корисний, лише якщо додаткові витрати на чергу та карту не знижують кількість виконань за секунду.
- Використовуйте `AFL_LLVM_ALLOWLIST`, щоб обмежити інструментування шляхів і викликів, якщо великі бібліотеки з великою кількістю шаблонів або загальний службовий код займають більшу частину карти.
- Функції з надмірною кількістю ациклічних шляхів можна пропускати за допомогою AFL++; попередження під час компіляції свідчать, що цілі потрібен allowlist або менш суворий рівень.
- Покриття викликів і шляхів підтримує лише один рівень викликів. Не поєднуйте його зі стеками глибшого контексту.
- ID шляхів можуть змінюватися між основними версіями LLVM. Для кампанії використовуйте незмінний toolchain і не синхронізуйте корпуси на основі PATH так, ніби їхні ID ознак незмінні між збірками.
- Цей зворотний зв’язок доповнює `CMPLOG`: трасування порівнянь визначає, **яке значення проходить перевірку**, тоді як зворотний зв’язок щодо шляхів і викликів зберігає **який маршрут і комбінація гілок до неї привели**.

## Stateful Fuzzing: послідовності як seeds

Для **протоколів**, **автентифікованих робочих процесів** і **багатоетапних парсерів** цікавою одиницею часто є не окремий blob, а **послідовність повідомлень**. Об’єднувати весь transcript в один файл і навмання його мутувати зазвичай неефективно, оскільки fuzzer однаково мутує кожен крок, навіть якщо лише пізніше повідомлення приводить до вразливого стану.<sup>[[4]](#references)</sup>

Ефективніший підхід — вважати **саму послідовність seed** і використовувати **спостережуваний стан** (коди відповідей, стани протоколу, фази парсера, типи повернутих об’єктів) як додатковий зворотний зв’язок.<sup>[[4]](#references)</sup>

- Зберігайте **коректні префіксні повідомлення** незмінними й зосередьте мутації на повідомленні, що **зумовлює перехід**.
- Кешуйте ідентифікатори та згенеровані сервером значення з попередніх відповідей, якщо від них залежить наступний крок.
- Віддавайте перевагу мутації та злиттю окремих повідомлень, а не мутації всього серіалізованого transcript як непрозорого blob.
- Якщо протокол повертає змістовні коди відповідей, використовуйте їх як **дешевий оракул стану**, щоб віддавати пріоритет послідовностям, які просуваються далі.

З цієї ж причини звичайний fuzzing файлів часто не виявляє автентифіковані баги, приховані переходи або баги парсера, що виникають «лише після handshake»: fuzzer має зберігати **порядок, стан і залежності**, а не лише структуру.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing драйвера з кількома клієнтами

Високе покриття ребер усе одно може не виявити баги IPC-драйвера, адже покриття не описує **володіння об’єктами, лічильники посилань, очікувані повідомлення, порядок очищення чи чергування потоків**. На сторінці [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) описано модель об’єктів драйвера; у цьому прикладі йдеться про harness для fuzzer. Android Binder — корисна модель: недостатньо пройти шляхи виділення та звільнення, якщо fuzzer не може змусити кілька процесів працювати з одним об’єктом ядра в потрібному порядку.<sup>[[15]](#references)</sup>

#### Моделюйте протокол, а не ізольовані буфери `ioctl`

Представте тестовий випадок як впорядковану граматику **ідентичність клієнта + операція + структуровані аргументи**. У фузері Binder LKL використовуються protobuf і `libprotobuf-mutator`, а також один постійний клієнт-менеджер контексту й два звичайні клієнти. Тоді семантичний harness зберігає зв’язки, які зруйнувала б сліпа мутація байтів.<sup>[[15]](#references)</sup>

- Кешуйте значення, повернуті попередніми операціями. Наприклад, `BC_FREE_BUFFER` має повторно використовувати вказівник на буфер транзакції, повернутий попереднім `ioctl`.
- Генеруйте коректні відповіді за замовчуванням, щоб синхронні транзакції могли завершуватися, а наступні операції залишалися досяжними.
- Відхиляйте неможливі переходи, як-от транзакції до самого себе або кілька очікуваних транзакцій до однієї цілі.
- Зберігайте стан одноразової ініціалізації поза скиданням між входами. Binder дозволяє лише одну реєстрацію `BINDER_SET_CONTEXT_MGR` за одне завантаження, тож багаторазове знищення та повторне створення цього клієнта зробить наступні входи некоректними.

Корисний шаблон гонки за часом життя: один клієнт передає об’єкт, запускається очищення потоку або процесу, а клієнт-отримувач паралельно звільняє буфер транзакції. У прикладі CVE-2020-0423 передавання `BINDER_TYPE_WEAK_BINDER`, за яким ішов `BINDER_THREAD_EXIT` у гонці з `BC_FREE_BUFFER`, могло звільнити вбудований `binder_work`, поки шлях очищення потоку, що завершувався, усе ще використовував його.<sup>[[15]](#references)</sup>

#### Поверніть контрольоване чергування в ядро в просторі користувача

[Linux Kernel Library (LKL)](https://github.com/lkl/linux) під’єднує справжній код ядра до harness у просторі користувача й надає доступ до його syscall-інтерфейсу через `lkl_syscall`. Це спрощує узгодження стану protobuf, покриття та KASAN в одному процесі. Однак зазвичай LKL виконує syscall без переривання іншим потоком ядра. Для кампаній пошуку гонок додайте точки виклику `schedule()` біля вибраних меж блокування/розблокування та часу життя, а потім дозвольте harness навмання вибирати наступного клієнта в кожній точці передачі керування. Розміщуйте ці точки вибірково, адже кожна з них збільшує простір пошуку розкладу. Описаний дослідниками рандомізований планувальник **не входить до upstream-фузера Binder**.<sup>[[15]](#references)</sup>

#### Збирайте та відтворюйте серіалізовані регресійні seeds

Upstream-harness фіксує сумісну версію `libprotobuf-mutator`, вмикає інструментування LKL для fuzzing і KASAN за допомогою `LKL_FUZZING=1`, а також вмикає `CONFIG_MMU` для Binder за допомогою `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Після переходу на навмисно вразливу ревізію або застосування патчів для відкату, описаних в upstream, серіалізований seed може відтворити весь перехід стану між кількома клієнтами без необхідності реконструювати його в ad-hoc proof of concept на C:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Розглядайте отриманий use-after-free у KASAN як підтвердження того, що seed досяг уразливого шляху життєвого циклу. Це **не** демонструє наявність подальших примітивів, необхідних для виконання коду ядра або підвищення привілеїв.<sup>[[16]](#references)</sup>

## Трюк із різноманітністю на одній машині (у стилі Jackalope)

Практичний спосіб поєднати **генеративну новизну** з **повторним використанням coverage** — запускати короткоживучі воркери проти сервера, що постійно працює. Кожен воркер починає з порожнього корпусу, синхронізується через `T` секунд, ще `T` секунд працює зі спільним корпусом, знову синхронізується, а потім завершує роботу. Це забезпечує **свіжі структури в кожному поколінні**, водночас використовуючи накопичений coverage.<sup>[[1]](#references)[[2]](#references)</sup>

**Сервер:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Послідовні workers (приклад циклу):**

<details>
<summary>Цикл перезапуску worker Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Примітки:**

- `-in empty` примусово створює **новий corpus** під час кожної генерації.
- `-server_update_interval T` імітує **відкладену синхронізацію** (спочатку новизна, згодом повторне використання).
- У режимі grammar fuzzing **початкову синхронізацію із сервером за замовчуванням пропускають** (параметр `-skip_initial_server_sync` не потрібен).
- Оптимальне значення `T` **залежить від цілі**; найкраще зазвичай перемикатися після того, як worker знайде більшість «легкого» покриття.

## Snapshot Fuzzing для цілей, які складно підготувати до тестування

Коли код, який потрібно перевірити, стає доступним лише **після тривалої підготовки** (запуску VM, завершення входу в систему, отримання пакета, парсингу контейнера, ініціалізації сервісу), корисною альтернативою є **snapshot fuzzing**: зберегти стан підготовленого процесу чи VM, передати кожен тестовий випадок до цільового шляху введення даних, виконувати код до збою/тайм-ауту та відновити snapshot. Це дає змогу уникнути повторної ініціалізації чи обробки префіксів протоколу й корисне для **мережевих сервісів**, **firmware**, **поверхонь атаки після автентифікації** та **цілей лише з бінарним кодом**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Запустіть ціль, доки не буде досягнуто потрібного стану.
2. Збережіть snapshot **пам’яті й регістрів** у цей момент.
3. Для кожного тестового випадку записуйте змінені вхідні дані безпосередньо у відповідний буфер guest/process.
4. Виконуйте код до збою/тайм-ауту/скидання.
5. Відновіть snapshot; для цілей на VM, якщо це підтримується, відновлюйте лише **змінені сторінки**, а потім повторюйте.

Розміщуйте snapshot якомога ближче до першого дорогого кроку парсингу/диспетчеризації, наприклад після виклику `recv`/`read` або десеріалізації пакета, і фіксуйте вхідний буфер, який використовує ціль. Це відповідає принципу адаптивного розміщення: переміщувати snapshot глибше в обробку вхідних даних, щоб уникнути повторення роботи.<sup>[[11]](#references)</sup>

## Дослідження race conditions у ядрі Linux за допомогою MAccConc

[MAccConc](https://github.com/googleprojectzero/MAccConc) перетворює чутливі до часу race conditions у ядрі Linux на відтворювані розклади доступу до пам’яті. Він може автоматично перебирати виконання **A-B-A** у двох контекстах або давати аналітику змогу задавати обмеження порядку в термінальному UI/GUI. Це експериментальний дослідницький інструментарій, а не повноцінний concurrency fuzzer: наразі для нього потрібні LLVM 23+ і пропатчене ядро проєкту, інструменти командного рядка підтримують два тестові потоки, а запропонований рівень fuzzing у userspace не реалізований.<sup>[[17]](#references)[[18]](#references)</sup>

### Збирання точок міжконтекстної взаємодії

Зберіть інструментоване ядро з outline callbacks KASAN і пропатченою підтримкою запису пам’яті KCOV. У README проєкту також рекомендовано вимкнути оптимізацію sibling-call, щоб стеки викликів залишалися придатними для аналізу.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

Режим outline у KASAN (`asan-instrumentation-with-call-threshold=0`) перетворює інструментовані доступи на виклики допоміжних функцій. Патчі ядра MAccConc вимикають `asan-opt-same-temp`, щоб послідовні доступи не об’єднувалися; також вимикайте оптимізацію `asan-opt-globals`, коли потрібно бачити гонки на глобальних змінних. KCOV передає отримані записи в userspace. Порівнюйте доступи з різних контекстів виконання та залишайте пари, діапазони байтів яких перетинаються, а принаймні один доступ є записом; моделюйте `kfree()` як запис, щоб переходи часу життя також ставали кандидатами.<sup>[[17]](#references)</sup>

Для роботи, що виконується поза початковим завданням, наприклад обробки пакетів або зворотних викликів RCU, підсистема має передавати дескриптор віддаленого покриття KCOV. В upstream віддалений KCOV потрібно вмикати явно; він автоматично недоступний для довільної фонової роботи, тож відсутність передавання дескриптора може зробити реальну взаємодію невидимою.<sup>[[17]](#references)[[19]](#references)</sup>

### Ідентифікуйте той самий динамічний доступ під час кожного запуску

Не відтворюйте сценарій із конкретною адресою в heap, яка може змінитися після кожного виділення пам’яті, або лише з адресою інструкції, що є неоднозначною всередині допоміжних функцій на кшталт `memcpy()` і `spin_lock()`. MAccConc використовує **стековий trace з лічильниками**: кожен кадр ідентифікує функцію-каллі та кількість її викликів у межах виклику батьківської функції, а останній елемент ідентифікує інструкцію доступу до пам’яті. Записи про входи й виходи з функцій від SanitizerCoverage дають змогу userspace відновити цей динамічний ідентифікатор, який залишається стабільним попри зміну адрес і не пов’язаний із цим шум у потоці керування.<sup>[[17]](#references)</sup>

### Перетворіть пари кандидатів на примусово задані розклади

Патчений ioctl `KCOV_SET_DI` пов’язує ідентифікатор доступу з лічильниками з дією над спільним прапорцем.<sup>[[17]](#references)</sup>

| Дія | Семантика |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Установити прапорець *N* безпосередньо перед вибраним доступом. |
| `DI_STACK_WAIT` | Перед вибраним доступом чекати в циклі, доки не буде встановлено прапорець *N* або не завершиться налаштований ліміт очікування. |
| `DI_STACK_WAKE_POST` | Установити прапорець *N* безпосередньо після вибраного доступу. |

Щоб задати часткове обмеження **A-happens-before-B**, прикріпіть `DI_STACK_WAKE_POST` до A, а `DI_STACK_WAIT` — до B, використовуючи той самий прапорець. Щоб задати повністю визначений розклад двох контекстів, спочатку заблокуйте B, потім змусьте A розбудити B і зачекати в першій точці передавання керування; у наступній точці передавання B виконує зворотну дію. Другий варіант працює як детерміноване перемикання контексту й використовується автоматичним дослідником A-B-A.<sup>[[17]](#references)</sup>

Мінімальна кампанія: скомпілюйте тестовий випадок із чотирма хуками (`test_setup`, дві функції потоків і `test_end`) як спільну бібліотеку, зберіть трасу без обмежень, а потім переберіть кандидатів A-B-A або додайте ручні обмеження навколо підозрілих доступів.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Інтерпретуйте тайм-аути окремо від успішних перестановок: запитаний порядок може бути неможливим, якщо блокування або залежність від ініціалізації/публікації не дає другому контексту дійти до точки ін’єкції. Також пам’ятайте про сліпі зони KASAN: прямий доступ до стека зазвичай не перехоплюється, якщо він не може виходити за межі, глобальні змінні пропускаються за стандартної оптимізації, а поточні компілятори не можуть одночасно створювати хуки ASAN і TSAN. Нарешті, прототип втрачає буфер KCOV, коли гість панікує, тому збережіть незалежну консоль/оракул для збоїв.<sup>[[17]](#references)</sup>

Для майбутнього concurrency-guided fuzzing записуйте зведення доступу до пам’яті для кожного вводу або системного виклику, об’єднуйте в пари операції, які формували б точки міжконтекстної комунікації, а потім досліджуйте лише ці комбінації. Знімки VM стабілізують глобальний стан і адреси; без знімків метадані місця алокації можуть абстрагувати об’єкти між запусками. Це запропоноване розширення, а не функція наявних userspace-інструментів MAccConc.<sup>[[17]](#references)</sup>

## Інтроспекція harness: завчасно виявляйте поверхневі fuzzers

Коли кампанія зупиняється, проблема часто полягає не в мутаторі, а в **harness**. Використовуйте **інтроспекцію досяжності/покриття**, щоб знаходити функції, досяжні статично з вашої цілі fuzzing, але рідко або ніколи не покриті динамічно. Такі функції зазвичай вказують на одну з трьох проблем.<sup>[[12]](#references)</sup>

- Harness запускає ціль надто пізно або надто рано.
- У seed corpus бракує цілої родини функцій.
- Для цілі справді потрібен **другий harness**, а не один завеликий harness «для всього».

Якщо ви використовуєте робочі процеси на кшталт OSS-Fuzz / ClusterFuzz, Fuzz Introspector може порівнювати статичну досяжність із покриттям під час виконання та генерувати звіти на основі запуску з обмеженням часу або публічного corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Використовуйте звіт, щоб вирішити, чи додати новий harness для неперевіреного шляху парсера, розширити корпус для певної функції або розбити монолітний harness на менші точки входу.

## Вибір цілей для fuzzing на основі графа та тріаж мутацій

Якщо у вас уже є **результати статичного аналізу**, **мутації, що пережили тестування**, і **звіти про покриття**, не розглядайте їх як незалежні списки. Спочатку побудуйте **граф викликів**, а потім анотуйте вузли даними про **цикломатичну складність**, **досяжність від точок входу/недовірених вхідних даних** і будь-які зовнішні результати аналізу, після чого ставте запитання про граф.<sup>[[5]](#references)[[6]](#references)</sup>

- Які функції з високою складністю можна викликати, передавши недовірені вхідні дані?
- Які мутації, що пережили тестування, лежать на шляхах від парсерів/обробників до критичного для безпеки коду?
- Які функції є архітектурними вузькими місцями з незвично великим **радіусом впливу**?

Такий підхід зазвичай виявляє кращі цілі для fuzzing, ніж сам лише «найнижчий рівень покриття». Парсер/декодер із **високою складністю** та підтвердженою **зовнішньою досяжністю** є кращим кандидатом для harness, ніж ізольований внутрішній допоміжний компонент зі слабким покриттям, до якого не ведуть шляхи з контрольованими зловмисником вхідними даними.

### Практичний робочий процес тріажу

1. Побудуйте **граф коду** на основі кодової бази та отримайте метрики складності/гілок для кожної функції.
2. Перелічіть **точки входу**, що приймають контрольовані зловмисником вхідні дані: обробники запитів, декодери, засоби імпорту, парсери протоколів, зчитувачі CLI/файлів.
3. Запустіть запити шляхів від цих точок входу до функцій-кандидатів, щоб відокремити досяжну поверхню атаки від недосяжного/лише внутрішнього коду.
4. Визначте пріоритетність вузлів, що поєднують:
   - високу **цикломатичну складність**
   - підтверджену **досяжність із недовірених вхідних даних**
   - великий **радіус впливу** або багато залежних від них вузлів
   - додаткові свідчення, як-от результати **SARIF**, нотатки аудиту чи мутації, що пережили тестування
5. Спочатку пишіть цільові harness для вузлів із найвищими оцінками, особливо для **парсерів/кодеків**, як-от декодерів hex/Base64/IP/повідомлень.

### Мутації, що пережили тестування: еквівалентні чи значущі

Мутаційне тестування часто дає шумний список мутацій, що пережили тестування. Перш ніж вважати кожну з них прогалиною в безпеці, використайте граф, щоб з’ясувати:

- Чи можна викликати змінену функцію через точку входу з контрольованими зловмисником вхідними даними?
- Чи обмежують усі шляхи виклику сильніші інваріанти, ніж змінена перевірка?
- Чи належить вузол до недосяжного коду, логіки лише форматування або арифметичного/парсерного шляху з високим впливом?

Мутації, що й далі залишаються недосяжними або структурно обмеженими, часто є **еквівалентними мутантами**. Мутації, що залишаються **досяжними** та зачіпають **граничні умови**, **шляхи переповнення/перенесення** або **критичні для безпеки арифметичні операції/парсинг**, слід просувати до:

- нових fuzz harness
- прямих тестів властивостей/інваріантів
- цільових векторів граничних випадків

### Накладіть зовнішні результати аналізу на граф

Якщо ваш конвеєр SAST експортує **SARIF**, нанесіть результати аналізу на вузли графа за **файлом і діапазоном рядків** та використайте граф, щоб розширити оцінку впливу.<sup>[[6]](#references)</sup>

- обчисліть **радіус впливу** позначеної функції
- перевірте, чи лежить результат аналізу на будь-якому шляху від точки входу
- згрупуйте близькі результати, що зводяться до одного вузького місця

Це корисно, коли вирішуєте, чи варто витрачати час на fuzzing певної функції: вузол, який є **досяжним**, **складним** і вже має **знахідки SAST**, часто є кращою ціллю, ніж просто складний вузол без шляху від зловмисника.

Приклад робочого процесу з Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Важлива методологія — це перетин: **складність x експозиція x вплив**. Використовуйте граф, щоб вибрати цілі для fuzzing із найвищою очікуваною цінністю для безпеки, а потім зацілілі після мутацій випадки — щоб визначити, які межі та інваріанти має перевіряти ваш harness.<sup>[[5]](#references)</sup>

## Fuzzing у Go за допомогою gosentry: потужніший рушій, типізовані входи та диференційні перевірки

Якщо для цілі на Go вже є вбудований harness `testing.F`, практичний шлях оновлення — запустити той самий harness за допомогою [gosentry](https://github.com/trailofbits/gosentry), форку toolchain Go, який зберігає `go test -fuzz`, але змінює бекенд на **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Це корисно, коли вбудований Go fuzzer застрягає на **складних порівняннях**, **типізованих вхідних даних** або **форматах із насиченим парсингом**. Методологія залишається незмінною:

- Продовжуйте використовувати `f.Add(...)` для початкових даних і `f.Fuzz(...)` для callback-функції.
- Повторно використовуйте той самий harness, але запускайте його за допомогою бінарного файла `go` від gosentry замість стандартного toolchain.
- Сприймайте отриманий fuzzing campaign як звичайний coverage-guided запуск, але з плануванням/мутаціями LibAFL та кращими супутніми детекторами.

### Перетворення непомітних збоїв на результати fuzzing

Поширена проблема під час оцінювання Go — небезпечна поведінка часто **не призводить** до аварійного завершення за замовчуванням. За допомогою gosentry можна перетворити кілька типів «поганих, але непомітних» станів на результати.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` — щоб вибрані шляхи логування/обробки помилок поводилися як аварійне завершення (корисно для шляхів коду в стилі `log.Fatal`, які інакше лише записують повідомлення й продовжують роботу).
- `--catch-races=true` — щоб повторно перевіряти щойно виявлені елементи черги за допомогою Go race detector.
- `--catch-leaks=true` — щоб повторно перевіряти нові елементи черги за допомогою `goleak` і зупинятися у разі витоків goroutine.
- Обробка зависань LibAFL, щоб залишати **нескінченні цикли / дуже повільні вхідні дані** як результати fuzzing, а не дозволяти їм зникати через тайм-аути.
- Вбудовані перевірки арифметичного переповнення за замовчуванням, а також опційні перевірки усічення за допомогою інструментування в стилі go-panikint.

Це особливо цінно для цілей, де наслідком для безпеки є **збій парсера без panic**, **помилка конкурентного виконання** або **зависання, що спричиняє лише DoS**, а не пошкодження пам’яті.

### Fuzzing з урахуванням структур для типізованих Go API

Вбудований Go fuzzing здебільшого розрахований на скалярні типи, як-от `[]byte`, `string` і числа. Якщо тестований код приймає типізовані об’єкти, gosentry може безпосередньо виконувати fuzzing **композитних значень** (struct, slice, array, pointer), водночас змінюючи байти на нижчому рівні.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Використовуйте це, коли створення фальшивого формату даних лише для fuzzing приховувало б логічні помилки за кодом розбору, наявним лише в harness. Для differential-кампаній або кампаній на основі граматики залишайте вхідні дані harness одним аргументом `[]byte` або `string`, а розбирайте їх усередині callback.

### Fuzzing на основі граматики для парсерів і протокольних даних

Для парсерів, форматів і мов введення gosentry може запускати **Nautilus grammar fuzzing** поверх LibAFL. Граматика — це JSON-масив правил продукції, а harness зазвичай має приймати один аргумент `[]byte` або `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Methodology notes:

- Використовуйте grammar mode, коли мутації на рівні байтів здебільшого відсіюються на ранніх перевірках синтаксису.
- Зосередьте граматику на **підмножині мови/протоколу, важливій для безпеки**, замість моделювання повної специфікації.
- Використовуйте великі граничні значення в терміналах/нетерміналах, щоб перевірити крайові випадки для цілих чисел, довжин і скінченних автоматів.
- Grammar mode забезпечує відповідність вхідних даних граматиці, але ціль усе одно отримує **байти/рядки**, тож парсинг і семантичні перевірки залишаються в коді, охопленому harness.

### Differential fuzzing: порівнюйте реалізації, а не лише збої

Для екосистем Go добре працює **grammar-based differential fuzzing**: генеруйте коректні структуровані вхідні дані й передавайте їх двом парсерам, клієнтам або рушіям переходів станів.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Вважайте такі випадки знахідками:

- одна реалізація аварійно завершується, а інша коректно відхиляє вхідні дані
- невідповідність у прийнятті або відхиленні вхідних даних
- різні дерева розбору або декодовані об’єкти
- розбіжності в переходах стану, nonce, балансах або коренях стану

Це практичний спосіб виявляти **невідповідності консенсусу**, **неоднозначність парсера** та **розходження між специфікацією й реалізацією**, які часто залишаються непоміченими під час суто crash fuzzing.

### Повторно використовуйте корпус кампанії для звіту про покриття

Після кампанії відтворіть збережений корпус черги, щоб створити звіт Go про покриття, не експортуючи корпус окремо вручну.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Запускайте команду з **того самого пакета** й із **тим самим цільовим значенням `-fuzz`**, щоб gosentry визначив правильний стан кешованої кампанії.
