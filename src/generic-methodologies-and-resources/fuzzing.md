## Mutational Grammar Fuzzing: Κάλυψη έναντι Σημασιολογίας

Στο **mutational grammar fuzzing**, οι είσοδοι μεταλλάσσονται, διατηρώντας την **ορθότητα της γραμματικής**. Στη λειτουργία καθοδηγούμενη από την κάλυψη, αποθηκεύονται ως seeds του corpus μόνο τα δείγματα που προκαλούν **νέα κάλυψη**. Για **γλωσσικούς στόχους** (parsers, interpreters, engines), αυτό μπορεί να παραλείψει bugs που απαιτούν **αλυσίδες σημασιολογίας/ροής δεδομένων**, όπου η έξοδος μιας κατασκευής γίνεται είσοδος μιας άλλης.<sup>[[1]](#references)</sup>

**Τρόπος αποτυχίας:** το fuzzer βρίσκει seeds που ενεργοποιούν μεμονωμένα τα `document()` και `generate-id()` (ή παρόμοιες primitives), αλλά **δεν διατηρεί την αλυσιδωτή ροή δεδομένων**, με αποτέλεσμα να απορρίπτεται το δείγμα που βρίσκεται «πιο κοντά στο bug», επειδή δεν προσθέτει κάλυψη. Με **3+ εξαρτημένα βήματα**, ο τυχαίος ανασυνδυασμός γίνεται δαπανηρός και η ανατροφοδότηση κάλυψης δεν καθοδηγεί την αναζήτηση.<sup>[[1]](#references)</sup>

**Συμπέρασμα:** για γραμματικές με πολλές εξαρτήσεις, εξετάστε το ενδεχόμενο **συνδυασμού των mutational και generative φάσεων** ή της μεροληπτικής παραγωγής υπέρ μοτίβων **αλυσίδωσης συναρτήσεων** (όχι μόνο υπέρ της κάλυψης).<sup>[[1]](#references)</sup>

## Προβλήματα ποικιλομορφίας του Corpus

Η μετάλλαξη με καθοδήγηση από την κάλυψη είναι **άπληστη**: ένα δείγμα που προσφέρει νέα κάλυψη αποθηκεύεται αμέσως, διατηρώντας συχνά μεγάλες, αμετάβλητες περιοχές. Με την πάροδο του χρόνου, τα corpora γεμίζουν με **σχεδόν πανομοιότυπα** δείγματα, με χαμηλή δομική ποικιλομορφία. Η επιθετική ελαχιστοποίηση μπορεί να αφαιρέσει χρήσιμο περιβάλλον, επομένως ένας πρακτικός συμβιβασμός είναι η **ελαχιστοποίηση με επίγνωση της γραμματικής**, η οποία **σταματά μόλις επιτευχθεί ένα ελάχιστο όριο tokens** (μειώνοντας τον θόρυβο, αλλά διατηρώντας αρκετή περιβάλλουσα δομή ώστε να παραμένουν κατάλληλα για μετάλλαξη).<sup>[[1]](#references)</sup>

Ένας πρακτικός κανόνας για corpus σε mutational fuzzing είναι: **προτιμήστε ένα μικρό σύνολο δομικά διαφορετικών seeds που μεγιστοποιούν την κάλυψη** αντί για ένα μεγάλο σύνολο σχεδόν πανομοιότυπων δειγμάτων. Στην πράξη, αυτό συνήθως σημαίνει τα εξής.<sup>[[1]](#references)[[3]](#references)</sup>

- Ξεκινήστε από **δείγματα πραγματικού κόσμου** (δημόσια corpora, crawling, καταγεγραμμένη κίνηση, σύνολα αρχείων από το οικοσύστημα του στόχου).
- Περιορίστε τα με **ελαχιστοποίηση corpus βάσει κάλυψης**, αντί να διατηρείτε κάθε έγκυρο δείγμα.
- Διατηρήστε τα seeds **αρκετά μικρά**, ώστε οι μεταλλάξεις να επηρεάζουν πεδία με νόημα αντί να σπαταλούν τους περισσότερους κύκλους σε άσχετα bytes.
- Επαναλάβετε την ελαχιστοποίηση του corpus μετά από σημαντικές αλλαγές στο harness ή στα όργανα καταγραφής, επειδή το «καλύτερο» corpus αλλάζει όταν μεταβάλλεται η προσβασιμότητα.

## Μεγάλα προγράμματα που παράγονται αυτόματα και μεροληψία λόγω timeout

Στο fuzzing compiler και interpreter, μια είσοδος μπορεί να χρειάζεται να ξεπεράσει ένα **όριο μεγέθους του παραγόμενου κώδικα**, αντί να ενεργοποιήσει έναν νέο κλάδο του parser. Στο παράδειγμα [offset του exception handler στο V8](../binary-exploitation/chrome-exploiting.md#exception-handler-offsets-narrower-than-maximum-bytecode-size), ένα έγκυρο testcase έπρεπε να υπερβεί τα 256 MiB bytecode προτού αποκτήσει σημασία το truncated offset του handler. Επαναλαμβανόμενες κατασκευές `yield*` μπορούσαν να φτάσουν αυτό το όριο, αλλά η μεταγλώττιση του testcase διαρκούσε δευτερόλεπτα σε debug build. Η προτίμηση για μικρές εισόδους και τα σύντομα execution timeouts μπορεί να αποθαρρύνουν αυτή την κατηγορία, ακόμη κι όταν η κάλυψη της γραμματικής είναι υψηλή. Κατά τον έλεγχο packed offsets ή άλλων metadata που εξαρτώνται από το μήκος, εξετάστε χωριστά τα όρια μεγέθους και την πολιτική timeout· αυτή η συμβουλή για την καμπάνια αποτελεί συμπέρασμα από τον αναφερόμενο τρόπο αποτυχίας.<sup>[[29]](#references)</sup>

## Mutation με επίγνωση των συγκρίσεων για Magic Values

Ένας συνηθισμένος λόγος που τα fuzzers φτάνουν σε τέλμα δεν είναι η σύνταξη, αλλά οι **αυστηρές συγκρίσεις**: magic bytes, έλεγχοι μήκους, συμβολοσειρές enum, checksums ή τιμές dispatch του parser που ελέγχονται μέσω `memcmp`, πινάκων switch ή διαδοχικών συγκρίσεων. Η αμιγώς τυχαία μετάλλαξη σπαταλά κύκλους προσπαθώντας να μαντέψει αυτές τις τιμές byte προς byte.

Για αυτούς τους στόχους, χρησιμοποιήστε **tracing συγκρίσεων** (για παράδειγμα, ροές εργασίας τύπου AFL++ `CMPLOG` / Redqueen), ώστε το fuzzer να μπορεί να παρατηρεί τους τελεστέους αποτυχημένων συγκρίσεων και να κατευθύνει τις μεταλλάξεις προς τιμές που τις ικανοποιούν.<sup>[[3]](#references)</sup>

```bash
./configure --cc=afl-clang-fast
make
cp ./target ./target.afl

make clean
AFL_LLVM_CMPLOG=1 ./configure --cc=afl-clang-fast
make
cp ./target ./target.cmplog

afl-fuzz -i in -o out -c ./target.cmplog -- ./target.afl @@
```

**Πρακτικές σημειώσεις:**

- Αυτό είναι ιδιαίτερα χρήσιμο όταν ο στόχος θέτει ως προϋπόθεση για την πρόσβαση σε βαθύτερη λογική **υπογραφές αρχείων**, **ρήματα πρωτοκόλλου**, **ετικέτες τύπων** ή **bits δυνατοτήτων που εξαρτώνται από την έκδοση**.
- Συνδυάστε το με **λεξικά** που έχουν εξαχθεί από πραγματικά δείγματα, προδιαγραφές πρωτοκόλλων ή αρχεία καταγραφής εντοπισμού σφαλμάτων. Ένα μικρό λεξικό με tokens γραμματικής, ονόματα τμημάτων, ρήματα και διαχωριστικά είναι συχνά πιο χρήσιμο από μια τεράστια γενική λίστα λέξεων.
- Αν ο στόχος εκτελεί πολλούς διαδοχικούς ελέγχους, επιλύστε πρώτα τις πρώτες συγκρίσεις «magic» και, στη συνέχεια, ελαχιστοποιήστε ξανά το corpus που προκύπτει, ώστε τα επόμενα στάδια να ξεκινούν από ήδη έγκυρα προθέματα.

## Fuzzing API αρχείων που κρύβουν μια γλώσσα ονομάτων αρχείων

Μια παράμετρος με όνομα `filename`, `path` ή `URL` μπορεί να αποτελεί σημείο εισόδου σε interpreter αντί για κυριολεκτική αναζήτηση αρχείου. Για παράδειγμα, το CFITSIO Extended Filename Syntax (EFS) αξιολογεί επιλογείς σε αγκύλες, εκφράσεις γραμμών/pixel, υπολογιζόμενες στήλες, ιστογράμματα και μετασχηματισμούς πριν επιστρέψει το ανοιγμένο αντικείμενο· ορισμένες μορφές δημιουργούν επίσης προσωρινά αντίγραφα. Κατά τη χαρτογράφηση της επιφάνειας επίθεσης, ταξινομήστε κάθε API ανοίγματος/εισαγωγής ως **literal-path** ή **interpreted-path** και, στη συνέχεια, κάντε fuzzing στο production entry point που καλούν στην πράξη οι εφαρμογές.<sup>[[20]](#references)[[22]](#references)</sup>

Για τα primitives SSRF, αντιγραφής αρχείων και χειρισμού πρωτοκόλλων που προκύπτουν—καθώς και για ασφαλέστερα API literal-path—δείτε το [Filename mini-languages as SSRF/file primitives](../pentesting-web/ssrf-server-side-request-forgery/index.html#filename-mini-languages-as-ssrffile-primitives-cfitsio-efs).<sup>[[20]](#references)</sup>

### Διατηρήστε το αντικείμενο υποστήριξης ξεχωριστά από το πρόγραμμα που υποβάλλεται σε fuzzing

Όταν η γραμματική βρίσκεται σε ένα επίθημα ονόματος αρχείου, η μετάλλαξη μόνο των byte του αρχείου στο οποίο γίνεται αναφορά δεν καλύπτει τον parser. Ένα μικρό harness μπορεί, αντί γι' αυτό, να διαβάζει κάθε testcase ως συμβολοσειρά και να το περνά στο API ανοίγματος interpreted-path· η καμπάνια CFITSIO έφτασε στους περισσότερους EFS parsers και evaluators καλώντας τη `fits_open_file()` σε λειτουργία μόνο για ανάγνωση. Διατηρήστε ξεχωριστά διαθέσιμα έγκυρα αρχεία υποστήριξης, ώστε οι μεταλλάξεις να μπορούν να επικεντρωθούν στη γλώσσα επιλογέων/εκφράσεων, αντί να καταστρέφουν συνεχώς τη βασική διαδρομή.<sup>[[22]](#references)</sup>

Χρησιμοποιήστε seeds που φτάνουν το καθένα σε διαφορετική οικογένεια γραμματικής και, στη συνέχεια, δημιουργήστε ένα συμπαγές λεξικό από την προδιαγραφή και τον πηγαίο κώδικα του lexer/parser. Αν η κάλυψη παραμένει στάσιμη ενώ οι είσοδοι αποτυγχάνουν επανειλημμένα στην ίδια διαδρομή συντακτικού σφάλματος, διατηρήστε έγκυρα προθέματα και προσθέστε διαχωριστικά, τελεστές, λέξεις-κλειδιά, ονόματα συναρτήσεων και αντιπροσωπευτικά ονόματα πεδίων, αντί απλώς να αυξήσετε τον χρόνο τυχαίων μεταλλάξεων.<sup>[[22]](#references)</sup>

Εκτελέστε το harness με το λεξικό γραμματικής, για παράδειγμα:<sup>[[3]](#references)[[22]](#references)</sup>

```bash
afl-fuzz -i filename-seeds -o out -x filename-language.dict -- ./filename-harness @@
```

### Περιορίστε τις παρενέργειες του «read-only» harness

Μια σημαία read-only στη βιβλιοθήκη δεν εγγυάται ότι ένα testcase δεν θα προκαλέσει παρενέργειες: η γλώσσα ονομάτων αρχείων μπορεί να ξαναγράψει την είσοδο, να δημιουργήσει αρχεία εξόδου ή να υλοποιήσει προσωρινά αντικείμενα. Η καμπάνια CFITSIO αρχικά κατέστρεφε seed files και άφηνε απρόσμενα αρχεία σε όλο το σύστημα αρχείων, οπότε χρειάστηκαν καθαρισμός και απομόνωση.<sup>[[22]](#references)</sup>

- Δώστε σε κάθε worker έναν αναλώσιμο working directory και έναν ιδιωτικό temporary directory.
- Εκθέστε αντίγραφα των canonical backing files· μην επιτρέπετε ποτέ στον στόχο να τροποποιήσει το μοναδικό αντίγραφο του corpus.
- Απενεργοποιήστε την πρόσβαση στο δίκτυο, εκτός αν τα remote backends είναι ο επιδιωκόμενος στόχος, και περιορίστε τις εγγράψιμες διαδρομές με container, mount namespace ή αντίστοιχο sandbox.
- Επαναφέρετε τον κατάλογο μετά από κάθε εκτέλεση ή batch worker και αντιμετωπίζετε τις απρόσμενες αλλαγές στο σύστημα αρχείων ως πρόσθετα ευρήματα.

### Βρόχος crash-to-patch-to-fuzz

Ομαδοποιήστε τα crashes πριν από την επιδιόρθωση, ώστε χιλιάδες artifacts να μη γίνουν χιλιάδες εργασίες patch. Στην αξιολόγηση CFITSIO, το AFLTriage περιόρισε το αρχικό σύνολο crashes σε λίγες βασικές αιτίες· το σχετικό advisory παρουσιάζει διακριτές αστοχίες, όπως λανθασμένους ελέγχους μεγέθους προορισμού, παλιούς δείκτες μετά από `realloc()`, αριθμητικά σφάλματα και μη ασφαλείς διαδρομές εκκαθάρισης του parser.<sup>[[21]](#references)[[22]](#references)</sup>

1. Ελαχιστοποιήστε ένα αντιπροσωπευτικό input για κάθε ομάδα και αναπαραγάγετέ το με AddressSanitizer.
2. Καταγράψτε την ακριβή πρόσβαση που απέτυχε, τη θέση στον πηγαίο κώδικα, το ιστορικό allocation/free και την κατάσταση του parser που οδήγησε στην παραβίαση του invariant.
3. Εφαρμόστε ένα υποψήφιο patch περιορισμένου εύρους και κάντε rebuild με τα ίδια όργανα κάλυψης και sanitizer.
4. Αναπαραγάγετε ξανά το αρχικό reproducer **και κάθε input της ομάδας του**· ενεργοποιήστε επίσης τον εντοπισμό διαρροών, επειδή μια διόρθωση memory-safety μπορεί να διαταράξει τη διαχείριση ιδιοκτησίας σε μια διαδρομή σφάλματος.
5. Εκτελέστε λειτουργικές δοκιμές με πραγματικά αρχεία και, στη συνέχεια, συνεχίστε από την ουρά που έχει συγκεντρωθεί (ή εισαγάγετε ξανά αυτή την ουρά, αν η μηχανή απαιτεί νέο output directory μετά την αλλαγή του binary).
6. Επαναλάβετε: η αφαίρεση του πρώτου επιφανειακού crash συχνά επιτρέπει στα υπάρχοντα seeds να προχωρήσουν σε βαθύτερη κατάσταση του parser.

Ένα LLM μπορεί να επιταχύνει το βήμα 2 και να συντάξει ένα προσχέδιο για το βήμα 3, αν λάβει το input που προκαλεί το crash, την αναφορά του sanitizer, το harness και τον σχετικό πηγαίο κώδικα, αλλά το patch του παραμένει μη έμπιστο. Η επανάληψη με sanitizer και οι πύλες ελέγχου παλινδρόμησης —όχι η εξήγηση του μοντέλου— καθορίζουν αν θα γίνει αποδεκτή η επιδιόρθωση.<sup>[[22]](#references)</sup>

## Πλουσιότερη ανατροφοδότηση όταν η κάλυψη ακμών συγχωνεύει διαφορετικές διαδρομές

Η συνηθισμένη κάλυψη ακμών δεν μπορεί να διακρίνει δύο εκτελέσεις που περνούν από τον ίδιο helper μέσω διαφορετικών callers ή ακολουθούν διαφορετικούς συνδυασμούς κλάδων μέσα σε μια συνάρτηση. Αυτό έχει σημασία σε κοινόχρηστους decoders, protocol dispatchers και helpers interpreters, όπου η **διαδρομή** προς μια ακμή καθορίζει την ενεργή κατάσταση. Η αφελής παρακολούθηση κάθε calling context είναι επίσης επικίνδυνη: ο χάρτης κάλυψης και η ουρά μπορεί να διογκωθούν ανεξέλεγκτα. Γι’ αυτό, η έρευνα για context-sensitive fuzzing συνιστά να βελτιώνονται μόνο τα υποσχόμενα contexts, αντί να θεωρείται context-sensitive ολόκληρο το call graph.<sup>[[14]](#references)</sup>

Οι πρόσφατες εκδόσεις του AFL++ παρέχουν **Ball-Larus κάλυψη διαδρομών ανά συνάρτηση**, επιπλέον της συνηθισμένης κάλυψης ακμών. Αντιστοιχίζει ένα feature σε κάθε άκυκλη διαδρομή μέσα σε μια συνάρτηση· αφαιρούνται οι ακμές επιστροφής των loops, επομένως αυτή η ανατροφοδότηση διακρίνει συνδυασμούς κλάδων, αλλά **όχι τον αριθμό επαναλήψεων των loops**. Ξεκινήστε με το χαλαρό επίπεδο `1` και, στη συνέχεια, περιορίστε τις αυστηρότερες λειτουργίες σε ύποπτο κώδικα parser/state machine, επειδή ο αριθμός των διαδρομών μπορεί να αυξηθεί εκθετικά.<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-fast
export CXX=afl-clang-fast++
export AFL_LLVM_PATH=1                 # 1=relaxed, 2=restricted, 3=strict
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

Για ένα helper που καλείται από πολλά σημεία που σχετίζονται με την ασφάλεια, η λειτουργία LTO μπορεί να συνδυάσει κάθε διαδρομή συνάρτησης με το άμεσο σημείο κλήσης της:<sup>[[13]](#references)</sup>

```bash
make clean
export CC=afl-clang-lto
export CXX=afl-clang-lto++
export AFL_LLVM_LTO_CALLER=1
export AFL_LLVM_LTO_PATH=1
./configure
make -j"$(nproc)"
afl-fuzz -i in -o out -- ./target @@
```

**Καθοδήγηση καμπάνιας:** εφαρμόστε πιο πλούσια ανατροφοδότηση με φειδώ και παρακολουθείτε το κόστος της κάλυψης και της ουράς.<sup>[[13]](#references)[[14]](#references)</sup>

- Εκτελέστε παράλληλα ένα συνηθισμένο instance κάλυψης ακμών· η πιο πλούσια ανατροφοδότηση είναι χρήσιμη μόνο αν το επιπλέον κόστος ουράς και χάρτη δεν μειώνει υπερβολικά τις εκτελέσεις ανά δευτερόλεπτο.
- Χρησιμοποιήστε το `AFL_LLVM_ALLOWLIST` για να περιορίσετε την instrumentation διαδρομών/καλούντων, όταν μεγάλες βιβλιοθήκες με πολλά templates ή γενικός κώδικας βοηθητικών λειτουργιών κυριαρχούν στον χάρτη.
- Οι συναρτήσεις με υπερβολικά πολλές άκυκλες διαδρομές μπορούν να παραλειφθούν από το AFL++· οι προειδοποιήσεις κατά τη μεταγλώττιση αποτελούν ένδειξη ότι ο στόχος χρειάζεται allowlisting ή λιγότερο αυστηρό επίπεδο.
- Η κάλυψη καλούντος + διαδρομής υποστηρίζει βάθος μόνο ενός καλούντος. Μην τη συνδυάζετε με βαθύτερες στοίβες context.
- Τα ID διαδρομών μπορεί να αλλάξουν μεταξύ κύριων εκδόσεων του LLVM. Διατηρήστε σταθερή την toolchain σε όλη την καμπάνια και μη συγχρονίζετε corpora που βασίζονται σε PATH σαν να ήταν σταθερά τα feature ID μεταξύ διαφορετικών builds.
- Αυτή η ανατροφοδότηση συμπληρώνει το `CMPLOG`: η καταγραφή συγκρίσεων λύνει το **ποια τιμή περνά έναν έλεγχο**, ενώ η ανατροφοδότηση διαδρομής/καλούντος διατηρεί το **ποια διαδρομή και ποιος συνδυασμός κλάδων οδήγησε σε αυτόν**.

## Stateful Fuzzing: Οι ακολουθίες είναι seeds

Για **πρωτόκολλα**, **workflows με έλεγχο ταυτότητας** και **parsers πολλαπλών σταδίων**, η ενδιαφέρουσα μονάδα συχνά δεν είναι ένα μεμονωμένο blob αλλά μια **ακολουθία μηνυμάτων**. Η συνένωση ολόκληρης της συνομιλίας σε ένα αρχείο και η τυφλή μεταλλαγή του είναι συνήθως αναποτελεσματική, επειδή ο fuzzer μεταλλάσσει εξίσου κάθε βήμα, ακόμη κι όταν μόνο το μεταγενέστερο μήνυμα φτάνει στην ευάλωτη κατάσταση.<sup>[[4]](#references)</sup>

Μια αποτελεσματικότερη προσέγγιση είναι να αντιμετωπίζετε την **ίδια την ακολουθία ως seed** και να χρησιμοποιείτε την **παρατηρήσιμη κατάσταση** (κωδικούς απόκρισης, καταστάσεις πρωτοκόλλου, φάσεις parser, τύπους αντικειμένων που επιστρέφονται) ως πρόσθετη ανατροφοδότηση.<sup>[[4]](#references)</sup>

- Διατηρήστε σταθερά τα **έγκυρα μηνύματα προθέματος** και εστιάστε τις μεταλλάξεις στο μήνυμα που **οδηγεί τη μετάβαση**.
- Αποθηκεύετε σε cache τα αναγνωριστικά και τις τιμές που παράγονται από τον server στις προηγούμενες αποκρίσεις, όταν το επόμενο βήμα εξαρτάται από αυτά.
- Προτιμήστε τη μεταλλαγή/συρραφή ανά μήνυμα αντί να μεταλλάσσετε ολόκληρη τη σειριοποιημένη συνομιλία ως αδιαφανές blob.
- Αν το πρωτόκολλο εκθέτει σημαντικούς κωδικούς απόκρισης, χρησιμοποιήστε τους ως **οικονομικό oracle κατάστασης** για να δίνετε προτεραιότητα στις ακολουθίες που προχωρούν βαθύτερα.

Αυτός είναι και ο λόγος που σφάλματα με έλεγχο ταυτότητας, κρυφές μεταβάσεις ή σφάλματα parser που εμφανίζονται «μόνο μετά το handshake» συχνά διαφεύγουν από το συνηθισμένο fuzzing αρχείων: ο fuzzer πρέπει να διατηρεί **τη σειρά, την κατάσταση και τις εξαρτήσεις**, όχι μόνο τη δομή.<sup>[[4]](#references)</sup>

### Android Binder: fuzzing driver με πολλούς clients

Η υψηλή κάλυψη ακμών μπορεί και πάλι να μην εντοπίσει σφάλματα IPC driver, επειδή η κάλυψη δεν περιγράφει **την ιδιοκτησία αντικειμένων, τις μετρήσεις αναφορών, τα εκκρεμή μηνύματα, τη σειρά εκκαθάρισης ή τις αλληλοπλοκές νημάτων**. Η σελίδα [Android Binder IPC internals](../binary-exploitation/linux-kernel-exploitation/android-binder-ipc-internals-kernel-vulnerability-research.md) καλύπτει το μοντέλο αντικειμένων του driver· αυτό το παράδειγμα εστιάζει στο harness του fuzzer. Το Android Binder αποτελεί χρήσιμο μοντέλο: δεν αρκεί να φτάνει ο fuzzer τόσο στις διαδρομές εκχώρησης όσο και στις διαδρομές αποδέσμευσης, αν δεν μπορεί να κάνει πολλές διεργασίες να ενεργούν στο ίδιο αντικείμενο του kernel με την απαιτούμενη σειρά.<sup>[[15]](#references)</sup>

#### Μοντελοποιήστε το πρωτόκολλο, όχι μεμονωμένα buffers `ioctl`

Αναπαραστήστε μια περίπτωση δοκιμής ως διατεταγμένη γραμματική **ταυτότητας client + λειτουργίας + δομημένων ορισμάτων**. Ο fuzzer Binder LKL χρησιμοποιεί protobuf και `libprotobuf-mutator`, με έναν επίμονο client διαχειριστή context και δύο συνηθισμένους clients. Στη συνέχεια, ένα σημασιολογικό harness διατηρεί τις σχέσεις που θα κατέστρεφε η τυφλή μεταλλαγή byte.<sup>[[15]](#references)</sup>

- Αποθηκεύετε σε cache τις τιμές που επιστρέφονται από προηγούμενες λειτουργίες. Για παράδειγμα, το `BC_FREE_BUFFER` πρέπει να επαναχρησιμοποιεί έναν δείκτη buffer συναλλαγής που επιστράφηκε από προηγούμενο `ioctl`.
- Δημιουργείτε έγκυρες προεπιλεγμένες αποκρίσεις ώστε να ολοκληρώνονται οι σύγχρονες συναλλαγές και να παραμένουν προσβάσιμες οι επόμενες λειτουργίες.
- Απορρίπτετε αδύνατες μεταβάσεις, όπως συναλλαγές προς τον ίδιο τον client ή πολλαπλές εκκρεμείς συναλλαγές προς τον ίδιο στόχο.
- Διατηρείτε την κατάσταση αρχικοποίησης singleton εκτός της επαναφοράς ανά είσοδο. Το Binder επιτρέπει μόνο μία εγγραφή `BINDER_SET_CONTEXT_MGR` ανά εκκίνηση, επομένως η επανειλημμένη καταστροφή και αναδημιουργία αυτού του client θα καθιστούσε άκυρες τις επόμενες εισόδους.

Ένα χρήσιμο πρότυπο αγώνα διάρκειας ζωής είναι να κάνει ένας client μεταβίβαση ενός αντικειμένου, να ξεκινά εκκαθάριση νήματος ή διεργασίας και, παράλληλα, ο client που το λαμβάνει να αποδεσμεύει το buffer συναλλαγής. Στο παράδειγμα CVE-2020-0423, η μεταβίβαση ενός `BINDER_TYPE_WEAK_BINDER` και στη συνέχεια η συνθήκη ανταγωνισμού ανάμεσα στο `BINDER_THREAD_EXIT` και το `BC_FREE_BUFFER` μπορούσαν να αποδεσμεύσουν ένα ενσωματωμένο `binder_work` ενώ η διαδρομή εκκαθάρισης του νήματος που τερματιζόταν εξακολουθούσε να το χρησιμοποιεί.<sup>[[15]](#references)</sup>

#### Επαναφέρετε ελεγχόμενες αλληλοπλοκές σε kernel userspace

Το [Linux Kernel Library (LKL)](https://github.com/lkl/linux) συνδέει τον πραγματικό κώδικα του kernel σε ένα harness userspace και εκθέτει τη διεπαφή syscall μέσω του `lkl_syscall`. Έτσι, είναι εύκολος ο συντονισμός της κατάστασης protobuf, της κάλυψης και του KASAN σε μία διεργασία. Ωστόσο, το LKL συνήθως εκτελεί ένα syscall χωρίς να το διακόπτει άλλο kernel thread. Για καμπάνιες αγώνων, εισαγάγετε σημεία `schedule()` γύρω από επιλεγμένα όρια κλειδώματος/ξεκλειδώματος και διάρκειας ζωής, και αφήστε το harness να επιλέγει τυχαία τον επόμενο client σε κάθε yield. Διατηρήστε αυτά τα σημεία στοχευμένα, επειδή καθένα πολλαπλασιάζει τον χώρο αναζήτησης του προγραμματισμού. Ο τυχαιοποιημένος scheduler που περιγράφουν οι ερευνητές **δεν** αποτελεί μέρος του upstream fuzzer Binder.<sup>[[15]](#references)</sup>

#### Δημιουργήστε και επαναλάβετε σειριοποιημένα seeds παλινδρόμησης

Το upstream harness καρφιτσώνει μια συμβατή έκδοση του `libprotobuf-mutator`, ενεργοποιεί το instrumentation fuzzing του LKL και το KASAN με `LKL_FUZZING=1`, και ενεργοποιεί το `CONFIG_MMU` για το Binder με `MMU=1`.<sup>[[16]](#references)</sup>

```bash
PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  tools/lkl/scripts/libprotobuf-mutator-build.sh

make -C tools/lkl LKL_FUZZING=1 MMU=1 \
  PROTOBUF_MUTATOR_DIR=/tmp/libprotobuf-mutator \
  clean-conf fuzzers -j"$(nproc)"
```

Αφού κάνετε checkout σε μια σκόπιμα ευάλωτη αναθεώρηση ή εφαρμόσετε τα rollback patches που τεκμηριώνονται upstream, ένα σειριοποιημένο seed μπορεί να αναπαράγει ολόκληρη τη μετάβαση κατάστασης πολλών clients, χωρίς να χρειάζεται να την ανακατασκευάσετε σε ένα ad-hoc proof of concept σε C:<sup>[[16]](#references)</sup>

```bash
tools/lkl/fuzzers/binder/binder-fuzzer \
  tools/lkl/fuzzers/binder/seeds/CVE-2023-20938
```

Αντιμετώπισε το KASAN use-after-free που προκύπτει ως επιβεβαίωση ότι το seed έφτασε στη διαδρομή ευάλου κύκλου ζωής. Δεν αποδεικνύει τα μεταγενέστερα primitives που απαιτούνται για εκτέλεση κώδικα στον kernel ή κλιμάκωση προνομίων.<sup>[[16]](#references)</sup>

## Τεχνική ποικιλομορφίας σε ένα μόνο μηχάνημα (Jackalope-Style)

Ένας πρακτικός τρόπος να συνδυάσεις τη **γενετική καινοτομία** με την **επαναχρησιμοποίηση κάλυψης** είναι να **επανεκκινείς workers μικρής διάρκειας** απέναντι σε έναν persistent server. Κάθε worker ξεκινά με άδειο corpus, συγχρονίζεται μετά από `T` δευτερόλεπτα, εκτελείται για άλλα `T` δευτερόλεπτα πάνω στο συνδυασμένο corpus, συγχρονίζεται ξανά και μετά τερματίζεται. Έτσι προκύπτουν **νέες δομές σε κάθε γενιά**, ενώ παράλληλα αξιοποιείται η κάλυψη που έχει συσσωρευτεί.<sup>[[1]](#references)[[2]](#references)</sup>

**Server:**

```bash
/path/to/fuzzer -start_server 127.0.0.1:8337 -out serverout
```

**Διαδοχικοί workers (παράδειγμα βρόχου):**

<details>
<summary>Βρόχος επανεκκίνησης worker του Jackalope</summary>

```python
import subprocess
import time

T = 3600

while True:
  subprocess.run(["rm", "-rf", "workerout"])
  p = subprocess.Popen([
      "/path/to/fuzzer",
      "-grammar", "grammar.txt",
      "-instrumentation", "sancov",
      "-in", "empty",
      "-out", "workerout",
      "-t", "1000",
      "-delivery", "shmem",
      "-iterations", "10000",
      "-mute_child",
      "-nthreads", "6",
      "-server", "127.0.0.1:8337",
      "-server_update_interval", str(T),
      "--", "./harness", "-m", "@@",
  ])
  time.sleep(T * 2)
  p.kill()
```

</details>

**Σημειώσεις:**

- Το `-in empty` επιβάλλει ένα **νέο corpus** σε κάθε γενιά.
- Το `-server_update_interval T` προσεγγίζει τον **καθυστερημένο συγχρονισμό** (πρώτα ανακάλυψη νέων στοιχείων, αργότερα επαναχρησιμοποίηση).
- Στη λειτουργία grammar fuzzing, ο **αρχικός συγχρονισμός με τον server παραλείπεται από προεπιλογή** (δεν χρειάζεται το `-skip_initial_server_sync`).
- Η βέλτιστη τιμή του `T` **εξαρτάται από τον στόχο**· συνήθως είναι καλύτερο να αλλάξετε τιμή αφού ο worker έχει βρει το μεγαλύτερο μέρος της «εύκολης» κάλυψης.

## Snapshot Fuzzing για Στόχους που Είναι Δύσκολο να Γίνουν Harness

Όταν ο κώδικας που θέλετε να ελέγξετε γίνεται προσβάσιμος μόνο **μετά από μεγάλο κόστος προετοιμασίας** (εκκίνηση VM, ολοκλήρωση σύνδεσης, λήψη πακέτου, ανάλυση container, αρχικοποίηση υπηρεσίας), μια χρήσιμη εναλλακτική είναι το **snapshot fuzzing**: καταγράψτε την έτοιμη κατάσταση της διεργασίας ή του VM, εισαγάγετε κάθε testcase στη διαδρομή εισόδου του στόχου, εκτελέστε το μέχρι να προκύψει crash ή timeout και επαναφέρετε το snapshot. Έτσι αποφεύγεται η επανάληψη της αρχικοποίησης ή των προθεμάτων του πρωτοκόλλου και είναι χρήσιμο για **υπηρεσίες δικτύου**, **firmware**, **attack surfaces μετά την αυθεντικοποίηση** και **στόχους μόνο με δυαδικό αρχείο**.<sup>[[9]](#references)[[10]](#references)</sup>

1. Εκτελέστε τον στόχο μέχρι να είναι έτοιμη η κατάσταση ενδιαφέροντος.
2. Αποθηκεύστε snapshot της **μνήμης και των registers** σε εκείνο το σημείο.
3. Για κάθε testcase, γράψτε την τροποποιημένη είσοδο απευθείας στο σχετικό buffer της διεργασίας ή του guest.
4. Εκτελέστε μέχρι να προκύψει crash, timeout ή reset.
5. Επαναφέρετε το snapshot· για στόχους VM, επαναφέρετε μόνο τις **dirty pages**, όταν υποστηρίζεται, και επαναλάβετε.

Τοποθετήστε το snapshot όσο πιο κοντά γίνεται στο πρώτο δαπανηρό βήμα ανάλυσης ή dispatch, όπως μετά από ένα σημείο `recv`/`read` ή αποσειριοποίησης πακέτου, και καταγράψτε το buffer εισόδου που χρησιμοποιεί ο στόχος. Αυτό ακολουθεί την αρχή της προσαρμοστικής τοποθέτησης: μετακινήστε το snapshot βαθύτερα στην επεξεργασία της εισόδου για να αποφύγετε την επανάληψη εργασιών.<sup>[[11]](#references)</sup>

### Incremental snapshots για καταστάσεις πρωτοκόλλου

Ένα σταθερό snapshot αποφεύγει το κόστος προετοιμασίας, αλλά από μόνο του δεν εξερευνά μεταβάσεις που απαιτούν πολλά έγκυρα μηνύματα. Ένα harness του LibAFL-Qemu μπορεί να παρακολουθεί εγγραφές σε ένα πεδίο κατάστασης πρωτοκόλλου και να αποθηκεύει νέο snapshot όταν αλλάζει η κατάσταση. Στο [libslirp TCP harness](https://github.com/quarkslab/slirp_snapshots_stateful), παρακολουθεί το `tcpcb.t_state`, κατακερματίζει την κατάσταση και τις σημαίες απόκρισης για την αποδιπλοποίηση των snapshots και αποθηκεύει τις dirty pages σε σχέση με ένα γονικό snapshot. Πριν τροποποιήσει το επόμενο δομημένο μήνυμα, επαναφέρει το επιλεγμένο snapshot μέσω της αλυσίδας γονικών snapshots. Το testcase διατηρεί ένα `SnapshotId` και τα παραγόμενα bytes εισόδου (`gen_bytes`)· ο snapshot manager παρακολουθεί τη σχέση γονέα που απαιτείται για την επανάληψη.<sup>[[27]](#references)[[28]](#references)</sup>

Το `SnapshotModule` της λειτουργίας user-mode του LibAFL-Qemu αποθηκεύει τις mappings και τη μνήμη του στόχου, αλλά όχι τα registers της CPU· διατηρήστε τα ξεχωριστά όταν χρειάζεται. Ο περιγραφόμενος manager υποστηρίζει ένα δέντρο root snapshot και δεν μπορεί να μοιράζεται snapshot IDs μεταξύ workers. Η λειτουργία multi-snapshot επίσης δεν μπορεί να επαναχρησιμοποιήσει απευθείας την κατάσταση shadow του QASAN. Για offline triage, ανακατασκευάστε την αλυσίδα εισόδου σε ξεχωριστή instrumented διεργασία. Όταν χρησιμοποιούνται τα `AsanHostModule` και `DrCovModule`, το `fuzzer.evaluate_input` εκτελεί τα απαιτούμενα callbacks `pre_exec`/`post_exec`· το `qemu.run` από μόνο του δεν το κάνει.<sup>[[27]](#references)[[28]](#references)</sup>

### Εντοπισμός λογικών υπερβάσεων ανάγνωσης σε ring buffer

Μια ανάγνωση πέρα από το *πλήθος έγκυρων δεδομένων* ενός buffer μπορεί να παραμείνει εντός της δεσμευμένης μνήμης του host και να διαφύγει του συνήθους ASAN. Το [παράδειγμα urgent-data του libslirp](../binary-exploitation/qemu-kvm-vm-escape-chains.md#tcp-urgent-pointer-vs-valid-ring-buffer-bytes) προκαλεί επίσης υποχείλιση σε μη προσημασμένο πλήθος byte. Αν υπάρχει διαθέσιμος ο πηγαίος κώδικας, η instrumentation για υπερχείλιση ακεραίων με πρόσημο/χωρίς πρόσημο μπορεί να εντοπίσει αυτή την παρενέργεια· διακρίνετε την εκ προθέσεως αναδίπλωση του αριθμού ακολουθίας TCP πριν καταστείλετε τις αναφορές. Ένας ισχυρότερος προτεινόμενος oracle είναι να δηλητηριαστεί η προσαρμοσμένη δέσμευση μνήμης του ring, να γίνει unpoison μόνο των έγκυρων περιοχών καθώς προχωρά ο εσωτερικός allocator του και να δηλητηριαστούν ξανά οι αποδεσμευμένες περιοχές. Το LibAFL-Qemu παρέχει API δηλητηρίασης ASAN για στόχους όπου η instrumentation του πηγαίου κώδικα δεν είναι πρακτική.<sup>[[27]](#references)</sup>

## Εξερεύνηση Race Conditions στον Linux Kernel με το MAccConc

Το [MAccConc](https://github.com/googleprojectzero/MAccConc) μετατρέπει τα race conditions του Linux kernel που εξαρτώνται από τον χρονισμό σε επαναλήψιμα προγράμματα χρονοπρογραμματισμού προσβάσεων μνήμης. Μπορεί να απαριθμεί αυτόματα εκτελέσεις **A-B-A** σε δύο contexts ή να επιτρέπει σε έναν αναλυτή να επιβάλλει περιορισμούς σειράς μέσω UI τερματικού ή GUI. Πρόκειται για πειραματικό ερευνητικό εργαλείο, όχι για ολοκληρωμένο concurrency fuzzer: προς το παρόν απαιτεί LLVM 23+ και τον kernel που έχει τροποποιηθεί από το project, τα εργαλεία γραμμής εντολών υποστηρίζουν δύο test threads και το προτεινόμενο επίπεδο fuzzing για userspace δεν έχει υλοποιηθεί.<sup>[[17]](#references)[[18]](#references)</sup>

### Συλλογή σημείων επικοινωνίας μεταξύ contexts

Δημιουργήστε τον instrumented kernel με KASAN outline callbacks και την τροποποιημένη υποστήριξη KCOV για καταγραφή μνήμης. Το README του project συνιστά επίσης την απενεργοποίηση της βελτιστοποίησης sibling-call, ώστε οι call stacks να παραμένουν αξιοποιήσιμα.<sup>[[17]](#references)[[18]](#references)</sup>

```text
CONFIG_KASAN=y
CONFIG_KASAN_OUTLINE=y
CONFIG_KCOV=y
CONFIG_KCOV_EXT_RECORDS=y
CONFIG_KCOV_MEMORY=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO_DWARF5=y
CONFIG_PREEMPT=y
CONFIG_RANDOMIZE_BASE=n
```

```bash
export KCFLAGS="-fno-optimize-sibling-calls -mllvm -sanitizer-coverage-prune-blocks=false"
```

Η λειτουργία outline του KASAN (`asan-instrumentation-with-call-threshold=0`) μετατρέπει τις instrumented προσπελάσεις σε κλήσεις helper. Τα patches του πυρήνα MAccConc απενεργοποιούν το `asan-opt-same-temp`, ώστε οι διαδοχικές προσπελάσεις να μη συγχωνεύονται· απενεργοποιήστε επίσης τη βελτιστοποίηση `asan-opt-globals` όταν πρέπει να είναι ορατά τα races σε global variables. Το KCOV μεταφέρει τις εγγραφές που προκύπτουν στο userspace. Συγκρίνετε προσπελάσεις από διαφορετικά execution contexts και κρατήστε τα ζεύγη των οποίων τα byte ranges επικαλύπτονται και όπου τουλάχιστον η μία πλευρά κάνει εγγραφή· μοντελοποιήστε το `kfree()` ως εγγραφή, ώστε να αποτελούν υποψήφιες περιπτώσεις και οι μεταβάσεις διάρκειας ζωής.<sup>[[17]](#references)</sup>

Για εργασίες που εκτελούνται εκτός της αρχικής task, όπως η επεξεργασία πακέτων ή τα RCU callbacks, το subsystem πρέπει να μεταβιβάζει ένα handle για KCOV remote coverage. Το upstream remote KCOV είναι προαιρετικό και δεν είναι αυτόματα διαθέσιμο για αυθαίρετες εργασίες παρασκηνίου, επομένως η παράλειψη της μεταβίβασής του μπορεί να κάνει μια πραγματική αλληλεπίδραση αόρατη.<sup>[[17]](#references)[[19]](#references)</sup>

### Εντοπισμός της ίδιας δυναμικής προσπέλασης σε κάθε εκτέλεση

Μην επαναλαμβάνετε την εκτέλεση με βάση μια συγκεκριμένη διεύθυνση heap, η οποία μπορεί να αλλάζει μετά από κάθε allocation, ή μόνο με βάση μια διεύθυνση instruction, η οποία είναι ασαφής μέσα σε helpers όπως τα `memcpy()` και `spin_lock()`. Το MAccConc χρησιμοποιεί ένα **count-augmented stack trace**: κάθε frame προσδιορίζει έναν callee μαζί με τον αριθμό κλήσης του μέσα στον caller του, ενώ το τελευταίο στοιχείο προσδιορίζει την instruction της προσπέλασης μνήμης. Οι εγγραφές εισόδου/εξόδου συναρτήσεων του SanitizerCoverage επιτρέπουν στο userspace να ανασυνθέσει αυτό το δυναμικό αναγνωριστικό, το οποίο παραμένει σταθερό παρά τις αλλαγές διευθύνσεων και τον άσχετο θόρυβο στη ροή ελέγχου.<sup>[[17]](#references)</sup>

### Μετατροπή των υποψήφιων ζευγών σε εξαναγκασμένα schedules

Το τροποποιημένο ioctl `KCOV_SET_DI` συσχετίζει ένα αναγνωριστικό προσπέλασης count-augmented με μια ενέργεια shared-flag.<sup>[[17]](#references)</sup>

| Ενέργεια | Σημασιολογία |
| --- | --- |
| `DI_STACK_WAKE_PRE` | Ορίζει το flag *N* αμέσως πριν από την επιλεγμένη προσπέλαση. |
| `DI_STACK_WAIT` | Πριν από την επιλεγμένη προσπέλαση, περιμένει σε spin μέχρι να οριστεί το flag *N* ή να λήξει το διαμορφωμένο όριο. |
| `DI_STACK_WAKE_POST` | Ορίζει το flag *N* αμέσως μετά την επιλεγμένη προσπέλαση. |

Για έναν μερικό περιορισμό **A-happens-before-B**, συσχετίστε το `DI_STACK_WAKE_POST` με το A και το `DI_STACK_WAIT` με το B, χρησιμοποιώντας το ίδιο flag. Για ένα πλήρως καθορισμένο schedule δύο contexts, ξεκινήστε με το B σε αναμονή και μετά κάντε το A να αφυπνίσει το B και να περιμένει στο πρώτο σημείο μεταβίβασης· το B εκτελεί την αντίστροφη ενέργεια στην επόμενη μεταβίβαση. Η δεύτερη προσέγγιση λειτουργεί όπως η ντετερμινιστική εναλλαγή context και χρησιμοποιείται από τον αυτόματο εξερευνητή A-B-A.<sup>[[17]](#references)</sup>

Μια ελάχιστη εκστρατεία ελέγχου είναι να μεταγλωττίσετε την περίπτωση δοκιμής με τα τέσσερα hooks (`test_setup`, δύο thread functions και `test_end`) ως shared library, να συλλέξετε ένα trace χωρίς περιορισμούς και έπειτα να απαριθμήσετε υποψήφιες περιπτώσεις A-B-A ή να προσθέσετε χειροκίνητους περιορισμούς γύρω από ύποπτες προσπελάσεις.<sup>[[18]](#references)</sup>

```bash
cc -shared -fPIC -o testcase.so testcase.c
./kcov-autorace ./testcase.so
# or interactively:
./kcov-terminal ./testcase.so
```

Ερμήνευε τα timeouts ξεχωριστά από τις επιτυχείς αναδιατάξεις: η ζητούμενη σειρά μπορεί να είναι αδύνατη, επειδή ένα lock ή μια εξάρτηση αρχικοποίησης/δημοσίευσης εμποδίζει το δεύτερο context να φτάσει στο σημείο εισαγωγής. Έχε επίσης υπόψη τα τυφλά σημεία του KASAN: οι άμεσες προσπελάσεις στη στοίβα συνήθως δεν ελέγχονται, εκτός αν υπάρχει πιθανότητα να είναι εκτός ορίων, τα globals παραλείπονται με τη βελτιστοποίηση από προεπιλογή και οι τρέχοντες compilers δεν μπορούν να εκπέμπουν ταυτόχρονα hooks για ASAN και TSAN. Τέλος, το πρωτότυπο χάνει το buffer του KCOV όταν ένα guest κάνει panic, γι’ αυτό διατήρησε ανεξάρτητη κονσόλα/oracle για crashes.<sup>[[17]](#references)</sup>

Για μελλοντικό concurrency-guided fuzzing, κατέγραψε περιλήψεις προσπελάσεων μνήμης ανά input ή syscall, ζευγοποίησε λειτουργίες που θα σχημάτιζαν σημεία επικοινωνίας μεταξύ contexts και έπειτα εξερεύνησε μόνο αυτούς τους συνδυασμούς. Τα VM snapshots σταθεροποιούν την καθολική κατάσταση και τις διευθύνσεις· χωρίς snapshots, τα μεταδεδομένα του σημείου κατανομής μπορούν να αφαιρούν την ταυτότητα των αντικειμένων μεταξύ εκτελέσεων. Αυτή είναι μια προτεινόμενη επέκταση, όχι λειτουργία των τρεχόντων εργαλείων userspace του MAccConc.<sup>[[17]](#references)</sup>

## Ενδοσκόπηση Harness: Εντόπισε νωρίς τα ρηχά fuzzers

Όταν μια εκστρατεία κολλάει, συχνά το πρόβλημα δεν είναι ο mutator αλλά το **harness**. Χρησιμοποίησε **ενδοσκόπηση προσβασιμότητας/κάλυψης** για να εντοπίσεις συναρτήσεις που είναι στατικά προσβάσιμες από τον στόχο fuzzing, αλλά καλύπτονται σπάνια ή καθόλου δυναμικά. Αυτές οι συναρτήσεις συνήθως υποδεικνύουν ένα από τα εξής τρία προβλήματα.<sup>[[12]](#references)</sup>

- Το harness εισέρχεται στον στόχο πολύ αργά ή πολύ νωρίς.
- Το corpus των seeds δεν περιλαμβάνει μια ολόκληρη οικογένεια λειτουργιών.
- Ο στόχος χρειάζεται όντως ένα **δεύτερο harness**, αντί για ένα υπερβολικά μεγάλο harness που «τα κάνει όλα».

Αν χρησιμοποιείς ροές εργασίας τύπου OSS-Fuzz / ClusterFuzz, το Fuzz Introspector μπορεί να συγκρίνει τη στατική προσβασιμότητα με την κάλυψη κατά την εκτέλεση και να δημιουργήσει αναφορές από μια εκτέλεση ορισμένης διάρκειας ή από δημόσιο corpus.<sup>[[12]](#references)</sup>

```bash
python3 infra/helper.py introspector libdwarf --seconds=30
python3 infra/helper.py introspector libdwarf --public-corpora
```

Χρησιμοποιήστε την αναφορά για να αποφασίσετε αν θα προσθέσετε ένα νέο harness για μια μη δοκιμασμένη διαδρομή parser, θα επεκτείνετε το corpus για μια συγκεκριμένη λειτουργία ή θα χωρίσετε ένα μονολιθικό harness σε μικρότερα entry points.

## Επιλογή στόχων fuzzing με προτεραιότητα στον γράφο και διαλογή μεταλλάξεων

Αν έχετε ήδη **ευρήματα στατικής ανάλυσης**, **μεταλλάξεις που επέζησαν από mutation testing** και **αναφορές κάλυψης**, μην τα διαχειρίζεστε ως ανεξάρτητες λίστες. Δημιουργήστε πρώτα ένα **γράφημα κλήσεων**, προσθέστε στους κόμβους σημειώσεις για την **κυκλωματική πολυπλοκότητα**, την **προσβασιμότητα από entry points/μη έμπιστη είσοδο** και τυχόν εξωτερικά ευρήματα, και έπειτα εξετάστε ερωτήματα για τον γράφο.<sup>[[5]](#references)[[6]](#references)</sup>

- Ποιες συναρτήσεις υψηλής πολυπλοκότητας είναι προσβάσιμες από μη έμπιστη είσοδο;
- Ποιες μεταλλάξεις που επέζησαν βρίσκονται σε διαδρομές από parsers/handlers προς κώδικα κρίσιμο για την ασφάλεια;
- Ποιες συναρτήσεις αποτελούν αρχιτεκτονικά σημεία συμφόρησης με ασυνήθιστα μεγάλο **εύρος επίδρασης**;

Αυτή η διαδικασία συνήθως αναδεικνύει καλύτερους στόχους για fuzzing από το να εξετάζετε μόνο την «χαμηλότερη κάλυψη». Ένας parser/decoder με **υψηλή πολυπλοκότητα** και επιβεβαιωμένη **εξωτερική προσβασιμότητα** είναι ισχυρότερος υποψήφιος για harness από έναν μεμονωμένο εσωτερικό helper με χαμηλή κάλυψη αλλά χωρίς διαδρομή ελεγχόμενη από επιτιθέμενο.

### Πρακτική ροή διαλογής

1. Δημιουργήστε ένα **γράφημα κώδικα** από τη βάση κώδικα και εξαγάγετε μετρικές πολυπλοκότητας/διακλαδώσεων για κάθε συνάρτηση.
2. Καταγράψτε τα **entry points** που δέχονται δεδομένα ελεγχόμενα από επιτιθέμενο: request handlers, decoders, importers, protocol parsers και αναγνώστες CLI/αρχείων.
3. Εκτελέστε ερωτήματα διαδρομών από αυτά τα entry points προς υποψήφιες συναρτήσεις, ώστε να διαχωρίσετε την προσβάσιμη επιφάνεια επίθεσης από κώδικα που είναι ανενεργός ή προσβάσιμος μόνο εσωτερικά.
4. Δώστε προτεραιότητα σε κόμβους που συνδυάζουν:
   - υψηλή **κυκλωματική πολυπλοκότητα**
   - επιβεβαιωμένη **προσβασιμότητα από μη έμπιστη είσοδο**
   - μεγάλο **εύρος επίδρασης** ή πολλούς εξαρτώμενους downstream κόμβους
   - επιβεβαιωτικά στοιχεία, όπως ευρήματα **SARIF**, σημειώσεις ελέγχου ή μεταλλάξεις που επέζησαν
5. Γράψτε πρώτα στοχευμένα harnesses για τους κόμβους με την υψηλότερη βαθμολογία, ιδίως για **parsers/codecs**, όπως decoders hex/Base64/IP/message.

### Μεταλλάξεις που επέζησαν: ισοδύναμες ή αξιοποιήσιμες

Το mutation testing συχνά παράγει μια λίστα επιζώντων με πολύ θόρυβο. Πριν θεωρήσετε κάθε επιζώντα κενό ασφαλείας, χρησιμοποιήστε τον γράφο για να εξετάσετε τα εξής:

- Είναι η μεταλλαγμένη συνάρτηση προσβάσιμη από entry point που ελέγχεται από επιτιθέμενο;
- Περιορίζονται όλες οι διαδρομές κλήσης από ισχυρότερες αμετάβλητες συνθήκες από εκείνη του ελέγχου που μεταλλάχθηκε;
- Βρίσκεται ο κόμβος σε ανενεργό κώδικα, σε λογική που αφορά μόνο τη μορφοποίηση ή σε διαδρομή αριθμητικών πράξεων/parser με μεγάλο αντίκτυπο;

Οι επιζώντες που παραμένουν μη προσβάσιμοι ή περιορίζονται δομικά είναι συχνά **ισοδύναμες μεταλλάξεις**. Οι επιζώντες που παραμένουν **προσβάσιμοι** και αφορούν **οριακές συνθήκες**, **διαδρομές overflow/carry** ή **αριθμητικές πράξεις/parsing κρίσιμα για την ασφάλεια** θα πρέπει να προωθούνται ως:

- νέα fuzz harnesses
- άμεσες δοκιμές ιδιοτήτων/αμετάβλητων συνθηκών
- στοχευμένα διανύσματα οριακών περιπτώσεων

### Συσχετίστε τα εξωτερικά ευρήματα με τον γράφο

Αν το SAST pipeline σας εξάγει **SARIF**, αντιστοιχίστε τα ευρήματα στους κόμβους του γράφου με βάση το **αρχείο + εύρος γραμμών** και χρησιμοποιήστε τον γράφο για να επεκτείνετε την ανάλυση του αντίκτυπου.<sup>[[6]](#references)</sup>

- υπολογίστε το **εύρος επίδρασης** της επισημασμένης συνάρτησης
- ελέγξτε αν το εύρημα βρίσκεται σε κάποια διαδρομή από entry point
- ομαδοποιήστε κοντινά ευρήματα που καταλήγουν στο ίδιο σημείο συμφόρησης

Αυτό βοηθά όταν αποφασίζετε αν αξίζει να αφιερώσετε χρόνο fuzzing σε μια συγκεκριμένη συνάρτηση: ένας κόμβος που είναι **προσβάσιμος**, **πολύπλοκος** και έχει ήδη **ευρήματα SAST** είναι συχνά καλύτερος στόχος από έναν απλώς πολύπλοκο κόμβο χωρίς διαδρομή από επιτιθέμενο.

Παράδειγμα ροής εργασίας με το Trailmark.<sup>[[6]](#references)</sup>

```bash
uv pip install trailmark
trailmark analyze --complexity 10 path/to/project
```

```python
from trailmark.query.api import QueryEngine

engine = QueryEngine.from_directory("path/to/project", language="c")
engine.preanalysis()
engine.complexity_hotspots(10)
engine.paths_between("handle_request", "parse_ipv6")
```

Η σημαντική μεθοδολογία είναι η τομή: **πολυπλοκότητα x έκθεση x αντίκτυπος**. Χρησιμοποιήστε το γράφημα για να επιλέξετε στόχους fuzzing με τη μεγαλύτερη αναμενόμενη αξία ασφάλειας και, στη συνέχεια, χρησιμοποιήστε τις μεταλλάξεις που επιβιώνουν για να αποφασίσετε ποια όρια και invariants πρέπει να ελέγχει το harness σας.<sup>[[5]](#references)</sup>

## Differential fuzzing κωδικοποιήσεων κρυπτογραφικών κλειδιών

Ξεκινήστε με έγκυρα σειριοποιημένα κλειδιά ή τυπικά test vectors. Μεταλλάξτε τα κωδικοποιημένα πεδία χωρίς να καταστρέψετε το μήκος και τη δομή που απαιτούνται για να προσεγγίσετε τις διαδρομές import και λειτουργιών και, στη συνέχεια, υποβάλετε τα ίδια bytes σε ανεξάρτητες υλοποιήσεις. Συγκρίνετε την αποδοχή και τα σφάλματα. Οι τυχαιοποιημένες υπογραφές και τα ciphertexts χρειάζονται oracles ορθότητας, όχι σύγκριση byte προς byte: επαληθεύστε τις υπογραφές ή συγκρίνετε τα κοινά μυστικά από έναν κύκλο encapsulation/decapsulation. Τα test vectors καθορίζουν τη συμμόρφωση για γνωστές περιπτώσεις· το differential mutation ανιχνεύει κακοσχηματισμένες κωδικοποιήσεις πέρα από αυτές.<sup>[[23]](#references)[[26]](#references)</sup>

Για αυτές τις μορφές κλειδιών, χρησιμοποιήστε oracles ειδικά για κάθε μορφή:<sup>[[24]](#references)[[25]](#references)[[26]](#references)</sup>

- **ML-DSA expanded signing keys:** αλλοιώστε τους συντελεστές `s1` ή `s2` σε packed μορφή, ώστε να βρίσκονται εκτός του `[-η, η]`, διατηρώντας το κλειδί αναλύσιμο. Ελέγξτε αν το import ή η υπογραφή απορρίπτεται και αν επαληθεύεται οποιαδήποτε υπογραφή που προκύπτει. Οι διαφορές στην αποδοχή από μόνες τους δεν αποτελούν παραβιάσεις των προτύπων, επειδή το FIPS 204 δεν επιβάλλει πρόσθετους ελέγχους ιδιωτικών κλειδιών. Δείτε τον [μηχανισμό υπό όρους διαρροής](../crypto/public-key/#malformed-ml-dsa-signing-keys-and-rejection-sampling-leakage).
- **Ζεύγη κλειδιών ML-KEM:** διαχωρίστε τους απαιτούμενους ελέγχους του κλειδιού encapsulation και των εισόδων decapsulation από τον προαιρετικό έλεγχο συνέπειας ζεύγους (PCT) κατά την εισαγωγή ενός ζεύγους. Κάντε encapsulate με το δημόσιο κλειδί και decapsulate με το ιδιωτικό κλειδί και συγκρίνετε τα κοινά μυστικά· μια ασυμφωνία μπορεί να διακόψει την κρυπτογραφημένη επικοινωνία, ακόμη κι όταν τα μεμονωμένα κλειδιά περνούν τους ελέγχους εισόδου. Ελέγξτε αν το API επικυρώνει τις εισόδους κατά τη λειτουργία ή μέσω ξεχωριστής κλήσης· το libcrux παρέχει τις `validate_public_key(pk)` και `validate_private_key(sk, ct)`, οι οποίες δεν υποκαθιστούν έναν PCT.
- **Ακατέργαστα κλειδιά XMSS/XMSSMT:** ελέγξτε τις διαδρομές round trip των σειριοποιημένων κλειδιών **υπογραφής και επαλήθευσης** σε διαφορετικά σύνολα παραμέτρων, όχι μόνο τις λειτουργίες με κλειδιά στη μνήμη. Τα XMSS και XMSSMT έχουν ξεχωριστούς χώρους ονομάτων OID τεσσάρων byte, επομένως ένας parser που ελέγχει μόνο το OID και δοκιμάζει πρώτα το XMSS μπορεί να ταξινομήσει λανθασμένα ένα XMSSMT κλειδί με ίδιο OID και να απορρίψει το import. Ο parser RustCrypto που αναφέρθηκε αποτελεί παράδειγμα αστοχίας διαλειτουργικότητας/διαθεσιμότητας, όχι πλαστογράφησης υπογραφής.

## Fuzzing Go με gosentry: ισχυρότερη μηχανή, τυποποιημένες είσοδοι και differential checks

Αν ένας στόχος Go έχει ήδη native harness `testing.F`, μια πρακτική διαδρομή αναβάθμισης είναι να εκτελέσετε το ίδιο harness με το [gosentry](https://github.com/trailofbits/gosentry), ένα forked toolchain του Go που διατηρεί το `go test -fuzz`, αλλά αντικαθιστά το backend με το **LibAFL**.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --focus-on-new-code=false --catch-races=true --catch-leaks=true
```

Αυτό είναι χρήσιμο όταν ο native Go fuzzer κολλάει σε **δύσκολες συγκρίσεις**, **τυποποιημένες εισόδους** ή **μορφότυπα με πολλή ανάλυση**. Η μεθοδολογία παραμένει ίδια:

- Συνεχίστε να χρησιμοποιείτε το `f.Add(...)` για seeds και το `f.Fuzz(...)` για το callback.
- Επαναχρησιμοποιήστε το ίδιο harness, αλλά εκτελέστε το με το `go` binary του gosentry αντί για το stock toolchain.
- Αντιμετωπίστε την καμπάνια που προκύπτει ως μια κανονική coverage-guided εκτέλεση, αλλά με scheduling/mutation του LibAFL και καλύτερους σχετικούς detectors.

### Μετατρέψτε τις σιωπηλές αστοχίες σε ευρήματα fuzzing

Ένα επαναλαμβανόμενο πρόβλημα στις αξιολογήσεις Go είναι ότι η επικίνδυνη συμπεριφορά συχνά **δεν** προκαλεί crash από προεπιλογή. Με το gosentry, μπορείτε να μετατρέψετε αρκετές κατηγορίες «κακών αλλά σιωπηλών» καταστάσεων σε ευρήματα.<sup>[[7]](#references)[[8]](#references)</sup>

- `--panic-on=pkg.Func,...` για να κάνετε επιλεγμένες διαδρομές logging/error να συμπεριφέρονται σαν crash (χρήσιμο για διαδρομές κώδικα τύπου `log.Fatal` που διαφορετικά απλώς καταγράφουν το συμβάν και συνεχίζουν).
- `--catch-races=true` για να επανεκτελείτε τις νέες εγγραφές της ουράς με τον race detector του Go.
- `--catch-leaks=true` για να επανεκτελείτε τις νέες εγγραφές της ουράς με το `goleak` και να σταματάτε σε περίπτωση διαρροών goroutine.
- Διαχείριση hang από το LibAFL, ώστε οι **άπειροι βρόχοι / οι πολύ αργές είσοδοι** να καταγράφονται ως ευρήματα fuzzing αντί να εξαφανίζονται ως timeouts.
- Ενσωματωμένοι έλεγχοι αριθμητικής υπερχείλισης από προεπιλογή, καθώς και προαιρετικοί έλεγχοι truncation μέσω instrumentation τύπου go-panikint.

Αυτό είναι ιδιαίτερα χρήσιμο για στόχους όπου ο αντίκτυπος στην ασφάλεια οφείλεται σε **αστοχία parser χωρίς panic**, σε **bug συγχρονισμού** ή σε **hang που προκαλεί μόνο DoS**, αντί για αλλοίωση μνήμης.

### Fuzzing με επίγνωση των struct για τυποποιημένα Go API

Το native Go fuzzing αναμένει κυρίως scalar τιμές, όπως `[]byte`, `string` και αριθμούς. Αν ο κώδικας υπό δοκιμή δέχεται τυποποιημένα αντικείμενα, το gosentry μπορεί να κάνει fuzz απευθείας **σύνθετες τιμές** (structs, slices, arrays, pointers), ενώ εξακολουθεί να μεταλλάσσει τα bytes από κάτω.<sup>[[7]](#references)[[8]](#references)</sup>

```go
type Input struct {
    Data []byte
    S    string
    N    int
}

func FuzzStructInput(f *testing.F) {
    f.Add(Input{Data: []byte("hello"), S: "world", N: 42})
    f.Fuzz(func(t *testing.T, in Input) {
        Process(in)
    })
}
```

Χρησιμοποιήστε το όταν η δημιουργία ενός ψεύτικου wire format μόνο για fuzzing θα έκρυβε λογικά σφάλματα πίσω από κώδικα parsing που υπάρχει μόνο στο harness. Για differential ή grammar-based campaigns, κρατήστε την είσοδο του harness ως ένα μόνο `[]byte` ή `string` και κάντε parsing μέσα στο callback.

### Fuzzing βάσει γραμματικής για parsers και εισόδους πρωτοκόλλων

Για parsers, formats και γλώσσες εισόδου, το gosentry μπορεί να εκτελέσει **Nautilus grammar fuzzing** πάνω από το LibAFL. Η γραμματική είναι ένας πίνακας JSON από κανόνες παραγωγής, και το harness συνήθως πρέπει να δέχεται ένα μόνο όρισμα `[]byte` ή `string`.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzGrammarJSON --use-grammar --grammar=./testdata/JSON.json --focus-on-new-code=false
```

Σημειώσεις μεθοδολογίας:

- Χρησιμοποιήστε τη λειτουργία γραμματικής όταν οι μεταλλάξεις σε επίπεδο byte αποτυγχάνουν κυρίως σε πρώιμους ελέγχους σύνταξης.
- Περιορίστε τη γραμματική στο **σχετικό με την ασφάλεια υποσύνολο** της γλώσσας/του πρωτοκόλλου, αντί να μοντελοποιήσετε ολόκληρη την προδιαγραφή.
- Χρησιμοποιήστε μεγάλες οριακές τιμές σε terminals/nonterminals για να δοκιμάσετε τα όρια ακεραίων, μηκών και μηχανών καταστάσεων.
- Η λειτουργία γραμματικής διατηρεί τις εισόδους έγκυρες ως προς τη γραμματική, αλλά ο στόχος εξακολουθεί να λαμβάνει **bytes/strings**, επομένως η ανάλυση και οι σημασιολογικοί έλεγχοι παραμένουν μέσα στον κώδικα του harness.

### Differential fuzzing: σύγκριση υλοποιήσεων, όχι μόνο crashes

Ένα ισχυρό μοτίβο για τα οικοσυστήματα Go είναι το **grammar-based differential fuzzing**: δημιουργήστε έγκυρες δομημένες εισόδους και τροφοδοτήστε τις σε δύο parsers, clients ή μηχανές μεταβάσεων καταστάσεων.<sup>[[7]](#references)[[8]](#references)</sup>

```go
f.Fuzz(func(t *testing.T, data []byte) {
    gotA, errA := ParseA(data)
    gotB, errB := ParseB(data)
    if (errA == nil) != (errB == nil) {
        t.Fatalf("parser disagreement: A=%v B=%v", errA, errB)
    }
    _ = gotA
    _ = gotB
})
```

Αντιμετωπίστε τα παρακάτω ως ευρήματα:

- η μία υλοποίηση προκαλεί panic, ενώ η άλλη απορρίπτει κανονικά την είσοδο
- ασυμφωνίες ως προς το αν η είσοδος γίνεται αποδεκτή ή απορρίπτεται
- διαφορετικά δέντρα ανάλυσης ή αποκωδικοποιημένα αντικείμενα
- αποκλίνουσες μεταβάσεις κατάστασης, nonce, υπόλοιπα ή ρίζες κατάστασης

Αυτός είναι ένας πρακτικός τρόπος να εντοπίσετε **ασυμφωνίες συναίνεσης**, **ασάφεια στον parser** και **αποκλίσεις μεταξύ προδιαγραφών και υλοποιήσεων** που συχνά δεν εντοπίζονται με fuzzing που ελέγχει μόνο για crashes.

### Επαναχρησιμοποιήστε το corpus της καμπάνιας για αναφορά κάλυψης

Μετά από μια καμπάνια, επαναλάβετε το αποθηκευμένο corpus της ουράς για να δημιουργήσετε αναφορά κάλυψης Go χωρίς να εξαγάγετε χειροκίνητα ξεχωριστό corpus.<sup>[[7]](#references)[[8]](#references)</sup>

```bash
./bin/go test -fuzz=FuzzHarness --generate-coverage .
```

Εκτελέστε την εντολή από το **ίδιο package** και με τον **ίδιο στόχο `-fuzz`**, ώστε το gosentry να εντοπίσει τη σωστή αποθηκευμένη κατάσταση του campaign.
