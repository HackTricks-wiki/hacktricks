# Цілісність firmware

{{#include ../../banners/hacktricks-training.md}}

Коли під час авторизованої оцінки виявлено слабку або відсутню перевірку підпису firmware, змінений образ firmware може продемонструвати вплив на цілісність. Наведений нижче лабораторний процес додає bind shell, зберігаючи початкові етапи розпакування, емуляції та повторного пакування.<sup>[[2]](#references)[[3]](#references)</sup>

1. Firmware можна розпакувати за допомогою firmware-mod-kit (FMK).
2. Слід визначити архітектуру та endianness цільового firmware.
3. Cross compiler можна зібрати за допомогою Buildroot або інших відповідних для середовища методів.
4. Backdoor можна зібрати за допомогою cross compiler.
5. Backdoor можна скопіювати до каталогу /usr/bin розпакованого firmware.
6. Відповідний бінарний файл QEMU можна скопіювати до rootfs розпакованого firmware.
7. Backdoor можна емулювати за допомогою chroot і QEMU.
8. До backdoor можна під’єднатися через netcat.
9. Бінарний файл QEMU слід видалити з rootfs розпакованого firmware.
10. Змінений firmware можна повторно запакувати за допомогою FMK.
11. Firmware із backdoor можна протестувати, емулювавши його за допомогою firmware analysis toolkit (FAT) і під’єднавшись до IP-адреси та порту цільового backdoor через netcat.

Якщо root shell уже отримано за допомогою динамічного аналізу, маніпуляцій із bootloader або тестування апаратної безпеки, можна виконати попередньо скомпільовані тестові бінарні файли, як-от implants або reverse shells. `msfvenom` від Metasploit може згенерувати payload для конкретної архітектури в межах цього процесу перевірки:<sup>[[4]](#references)</sup>

1. Слід визначити архітектуру та endianness цільового firmware.
2. За допомогою Msfvenom можна вказати цільовий payload, IP-адресу хоста атакувальника, номер порту для прослуховування, filetype, архітектуру, платформу та вихідний файл.
3. Payload можна передати на скомпрометований пристрій і надати йому права на виконання.
4. Metasploit можна підготувати до обробки вхідних запитів, запустивши msfconsole і налаштувавши параметри відповідно до payload.
5. На скомпрометованому пристрої можна виконати meterpreter reverse shell.

## Неавтентифіковані транспортні мости до привілейованих протоколів оновлення

Поширена помилка вбудованого дизайну — надання доступу до **того самого внутрішнього протоколу команд через кілька транспортів**, але перевірка автентифікації лише на одному з них. Наприклад, для USB може вимагатися challenge-response, тоді як BLE просто передає неавтентифіковані **GATT writes** тому самому привілейованому обробнику оновлення firmware.<sup>[[1]](#references)</sup>

Типовий offensive workflow:

1. Перелічити базу даних BLE GATT і визначити характеристики, доступні для запису, які використовує офіційний мобільний застосунок.
2. Перехопити трафік застосунку та пошукати **magic bytes / opcodes**, що збігаються з дротовим протоколом.
3. Повторно надіслати привілейовані команди через BLE **без pairing** і перевірити, чи працюють досі чутливі операції.
4. Якщо доступні opcodes для оновлення firmware, запису конфігурації, налагодження або заводського тестування, вважати BLE **адміністративним портом із радіодоступом**.

Швидкі перевірки:

```bash
# Enumerate services/characteristics
ble.enum <MAC>

# Replay a sniffed command
ble.write <MAC> <UUID> <HEX_DATA>

# gatttool equivalent
# gatttool -b <MAC> --char-write-req -a <HANDLE> -n <HEX_DATA>
```

Речі, які слід перевірити під час реверсингу:

- Чи вимагає BLE **pairing/bonding**, чи достатньо звичайного з’єднання?
- Чи спрямовуються всі транспорти до однієї внутрішньої таблиці диспетчеризації?
- Чи по-різному фільтруються привілейовані опкоди через USB / BLE / UART / Wi-Fi?
- Чи може мобільний застосунок віддалено запускати обробники оновлення firmware, відновлення або діагностики?

## Контейнери firmware, захищені лише контрольною сумою, усе ще містять firmware, контрольовану зловмисником

Контейнер firmware, захищений лише **неключовою контрольною сумою** (CRC32, SHA-256, MD5 тощо), забезпечує виявлення пошкоджень, **але не автентичність**. Якщо зловмисник може дістатися до процедури оновлення, він може змінити образ, перерахувати контрольну суму та прошити довільний код.<sup>[[1]](#references)</sup>

Тривожні ознаки під час RE:

- Код оновлення перевіряє лише кінцевий блок контрольної суми, наприклад `CHK2`, `CRC` або `SHA256`.
- Відсутня перевірка підпису або корінь довіри secure boot.
- Не використовується прив’язаний до пристрою MAC / HMAC / автентифіковане шифрування.
- Режим відновлення приймає той самий неавтентифікований формат образу.

Практичний процес перевірки:

1. Витягніть контейнер firmware і визначте bootloader, основну firmware та метадані цілісності.
2. Змініть у образі нешкідливий рядок або банер.
3. Перерахуйте контрольну суму саме так, як цього очікує засіб оновлення.
4. Повторно прошийте образ звичайним шляхом оновлення.
5. Переконайтеся після завантаження, що зміна збереглася, аби довести можливість заміни firmware на довільну.

Якщо це працює через віддалено доступний транспорт, наприклад BLE/Wi-Fi, то фактично це **неавтентифікована OTA-заміна firmware**.

## Фрагментований стан оновлення та змінювані метадані цілісності

Засіб оновлення може перевіряти підписаний заголовок firmware під час інсталяції, але завантажувати образи, спираючись лише на збережений хеш цілісності. У Cypherock X1 Bootloader викликав окремі задачі Firewall для перевірки заголовка та розміщення версії/розміру в RAM, збереження підпису firmware у RAM, перевірки записаного образу і, зрештою, хешування образу в постійні дані Primary Bootloader. Сам підпис не зберігався. Ці задачі можна було викликати окремо, а не в межах єдиної автентифікованої транзакції оновлення.<sup>[[5]](#references)</sup>

Маючи виконання коду MCU та доступ на запис до Flash, зловмисник, як повідомлялося, переписав образ застосунку, змінив значення версії/розміру в RAM Bootloader, спільній із Firewall, а потім викликав фінальну задачу метаданих, щоб зберегти хеш шкідливого образу й відновити звичайний стан завантаження. Перевірка цілісності під час звичайного завантаження приймала цей хеш, не перевіряючи підпис повторно. Аналізуючи подібний засіб оновлення, простежте, **який компонент може викликати кожну задачу**, де зберігаються перевірені значення та чи автентифікує рішення під час завантаження *той самий образ*, хеш якого збережено. Це вужчий випадок, ніж формат образу, захищений лише контрольною сумою: перевірка підпису існувала, але перехід між станами не був прив’язаний до неї.<sup>[[5]](#references)</sup>

## Підписи secure element на вимірах firmware, яким не можна довіряти

Secure element не засвідчує запущений код лише тим, що підписує хеш, наданий цим кодом. У тому самому гаманці secure element підписував серійний номер пристрою, а потім XOR хмарного nonce і хешу firmware, переданого через MCU. Скомпрометована firmware могла надати для підпису очікуваний хеш, водночас виконуючи інші байти. Супровідний клієнт також надсилав версію firmware у хмару, тому порівняння очікуваного хешу засобом перевірки все ще спиралося на вимір, отриманий від MCU, а не на незалежне зчитування Flash.<sup>[[5]](#references)</sup>

Результат на пристрої утворював окрему межу довіри: хмара перевіряла пристрій, але пристрій не автентифікував вердикт хмари. Змінений клієнт міг повідомити про успіх локально модифікованому пристрою. Перевіряйте походження виміру й автентифікацію відповіді окремо; дійсний підпис secure element і екран успіху самі по собі не доводять автентичність встановленого застосунку.<sup>[[5]](#references)</sup>

Про розкриття захищеного коду, яке уможливило аналіз цього засобу оновлення, див. [Отримання firmware захищеного коду через задачу копіювання Firewall](index.html#disclosing-protected-code-through-a-firewall-copy-task).<sup>[[5]](#references)</sup>

## Перетворення довіреного USB-периферійного пристрою на BadUSB через перепрошивання

Якщо хост уже довіряє цільовому пристрою через USB, шкідливій firmware може не знадобитися реалізовувати повноцінний новий стек USB. Значно простіший шлях часто полягає в тому, щоб **повторно використати наявну підтримку HID**.<sup>[[1]](#references)</sup>

Корисний шаблон:

1. Перевірте, чи пристрій уже визначається як інтерфейс **HID Consumer Control** / медіа / vendor HID.
2. Знайдіть у firmware наявний **дескриптор звіту HID**.
3. Додайте або замініть записи дескриптора, щоб пристрій також оголошував підтримку **клавіатури**.
4. Повторно використайте наявні процедури firmware, які вже надсилають звіти HID, замість написання нової реалізації транспорту.
5. Введіть команди на хості, надсилаючи звіти про натискання клавіш і їх відпускання.

Так компрометація firmware перетворюється на **компрометацію хоста**, оскільки ПК довірятиме перепрошитому периферійному пристрою як справжній клавіатурі.

### Короткий контрольний список для оцінювання

- Чи показують `dmesg`, Device Manager або дескриптори USB наявний інтерфейс HID?
- Чи є вільне місце поруч із дескриптором звіту або таблицею дескрипторів, яку можна перемістити?
- Чи можна повторно використати наявні процедури надсилання медіакерування для звітів клавіатури?
- Чи автоматично приймає хост новий інтерфейс клавіатури після перепрошивання?

## Надійне виконання payload у firmware RTOS

Замість вставляння ненадійних trampoline у випадкові шляхи виконання шукайте **наявні задачі RTOS**, які не використовуються або мають незначний вплив під час звичайної роботи.<sup>[[1]](#references)</sup>

Чим це корисно:

- Планувальник природно запускає ваш payload під час завантаження.
- Ви уникаєте пошкодження критичних шляхів виконання.
- Відкладені payload рідше спричиняють скидання watchdog, ніж payload, запущені в обробнику USB/мережі, чутливому до затримок.

Вдалими цілями є задачі діагностики, заводського тестування, телеметрії або обслуговування співпроцесора, які здаються неактивними під час звичайного використання.

## Швидке повторення експлойтів: перепризначення безпечних обробників протоколу

Коли патчинг firmware вже можливий, компактний спосіб пришвидшити RE — перезаписати нешкідливий обробник команди (наприклад, **echo/debug opcode**) власними примітивами **читання / запису / виконання пам’яті**. Це позбавляє потреби повністю перепрошивати пристрій для кожного експерименту й особливо корисно, коли пристрій підтримує змінений обробник через швидкий дротовий транспорт.<sup>[[1]](#references)</sup>

Використовуйте це, щоб:

- Перевіряти карти пам’яті, завантажені методом scatter-loading
- Переглядати стан heap/task у реальному часі
- Тестувати невеликі payload перед записом у flash
- Безпечно отримувати покажчики на функції, рядки та таблиці дескрипторів
