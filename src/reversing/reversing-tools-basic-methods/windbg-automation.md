# Автоматизація WinDbg для цільової інструментації

{{#include ../../banners/hacktricks-training.md}}

WinDbg і WinDbgX можуть виконувати команди налагоджувача під час запуску, у разі винятків і спрацювання точок зупинки. Це дає змогу під час fuzzing або reversing збирати стан лише на шляху, визначеному вхідними даними, замість того щоб вручну зупинятися на кожній події.<sup>[[1]](#references)</sup>

## Почніть із корисного винятку

`-c` виконує команди під час початкової зупинки налагоджувача. Додайте `;g`, щоб після налаштування відновити виконання. Для запуску WinDbg Classic без нагляду параметр `-logo` записує вікно команд у журнал, `-Q` вимикає автоматичне збереження робочої області, а `-G` ігнорує фінальну точку зупинки, щоб сеанс завершився, коли цільовий процес завершить роботу. WinDbgX також приймає `-c`; після цього запускаються налаштовані команди Startup.<sup>[[1]](#references)[[7]](#references)</sup>

```text
windbg.exe -c "sxd av;g" -logo C:\logs\triage.txt C:\path\target.exe
```

Для порушень доступу **`sxe av` зупиняється на першому шансі**, **`sxd av` пропускає перший шанс, але зупиняється на необробленому другому шансі**, а **`sxi av` ігнорує обидва шанси**. В описі статті призначення `sxi`/`sxd` переплутано: Microsoft документує `sxd` як фільтр другого шансу, а `sxi` — як ігнорування. Використовуйте `-c` для команди на першому шансі, а `-c2` — для команди на другому шансі; обробник `-c` для першого шансу не стає обробником другого шансу лише через те, що фільтр — `sxd`. Перевірте активні фільтри за допомогою `sx`.<sup>[[1]](#references)[[2]](#references)</sup>

```text
sxd -c2 "r;kv;!analyze -v" av
sxe -c "lm" ld
```

Перша команда збирає регістри, трасу стека й аналіз винятку лише для необробленого порушення доступу. Друга запускає `lm` під час завантаження модуля. Події breakpoint (`bp`), завантаження модуля (`ld`) і порушення доступу (`av`) мають різні життєві цикли, тому не ігноруйте глобально `bp`, якщо покладаєтеся на breakpoint-и debugger-а.<sup>[[1]](#references)[[2]](#references)</sup>

## Обмежуйте дорогі breakpoint-и керованим тригером

Виберіть функцію, видиму скрипту або контрольовану іншим способом через вхідні дані, яку можна викликати безпосередньо перед потрібним шляхом виконання. Встановіть **action breakpoint-и** на виклики allocator, parser або API, які потрібно перевірити. Вимкніть їх за ID командою `bd`. Встановіть **trigger breakpoint** із прикріпленою командою, яка вмикає ці ID командою `be`, а потім продовжує виконання командою `g`; інший керований тригер може вимкнути їх знову. Перевірте ID командою `bl`, перш ніж налаштовувати тригер, оскільки вони залежать від порядку створення breakpoint-ів. Так ви відокремите дешеві точки керування від дорогого трасування й обмежите вплив на таймінг цільової програми та розкладку heap.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

Після визначення двох символів використовуйте наведений нижче шаблон команди. Замініть символи у квадратних дужках і ID action breakpoint-а, отриманий командою `bl`; не припускайте, що це нуль.<sup>[[1]](#references)[[3]](#references)[[4]](#references)</sup>

```text
bp <action-symbol> "r;g"
bl
bd <action-id>
bp <trigger-symbol> "be <action-id>;g"
```

Команди action breakpoint можуть виводити `@$ip` і `%y` (адресу із символом), дампити вибрані аргументи чи пам’ять, а потім продовжувати виконання. Якщо умовна точка зупинки записує лише вказівники в заданому діапазоні, спершу перевірте, що цей діапазон охоплює тестові вхідні дані; неправильна умова непомітно призведе до втрати доказів.<sup>[[1]](#references)</sup>

### Знайдіть тригер за допомогою символів

Шукайте в усіх завантажених модулях, якщо невідомо, у якому модулі міститься реалізація. `bm` встановлює точки зупинки на кожен символ, що відповідає шаблону; викличте функцію, доступну зі скрипту, і перевірте, яка точка зупинки спрацює. Наприклад, вихідний код викликає `Math.cos(0)` у рендерері, який налагоджується, а не в будь-якому процесі браузера.<sup>[[1]](#references)[[5]](#references)</sup>

```text
x *!*math*cos*
bm *edge*!*math*cos* ".printf \"%y called\n\", @$ip;g"
g
```

Щойно спрацювання визначить точну функцію, використайте `lm a <symbol>`, щоб знайти образ, у якому вона міститься, і `? <symbol> - <module>`, щоб обчислити зміщення відносно модуля. WinDbg може показувати однакове коротке ім’я модуля для виконуваного файла й DLL, тому перевірте шлях до образу, перш ніж використовувати це зміщення в іншому процесі. Щоб уникнути зайвого навантаження, звузьте wildcard breakpoints до перевіреного символу.<sup>[[1]](#references)</sup>

### Знайти кандидата без символів

Скрипт Corelan на основі Frida `corelan_trigscan.py` сканує вибраний модуль процесу на шаблони інструкцій із числами з рухомою комою, SSE, AVX і тригонометричними інструкціями. Він генерує команди breakpoint для WinDbg у `corelan_trigscan.bps` і менші пронумеровані файли `.bps`. Запустіть його за допомогою Python і `frida-tools` для цільового процесу, **не під’єднуючи інший debugger**; потім під’єднайте WinDbg до того самого процесу/модуля та завантажте зручний для роботи набір breakpoint.<sup>[[1]](#references)[[6]](#references)</sup>

```text
py -3.9-64 corelan_trigscan.py -p msedge.exe -m msedge.dll --min-density 0.5 --min-relevant 50 --min-total 20 --min-trig 1
$$><C:\logs\msedge.dll\corelan_trigscan_0001.bps
```

Для відомого зміщення відносно модуля перевірте, чи воно проходить порогові значення, перш ніж імпортувати всі згенеровані точки зупинки:<sup>[[1]](#references)[[6]](#references)</sup>

```text
py -3.9-64 corelan_trigscan.py -p msedge.exe -m msedge.dll --min-density 0.15 --min-relevant 8 --min-total 45 --check-offset 00e13dc0 --min-icall 1
```

`--min-density` — це щільність релевантних інструкцій, `--min-relevant` і `--min-total` задають мінімальну кількість інструкцій, а `--min-trig` вимагає сильних сигналів, схожих на тригонометричні. Якщо відому функцію не знайдено, передайте її **відносне до модуля** зміщення в `--check-offset`, щоб перевірити її пролог, щільність, кількість інструкцій і непрямі виклики. Тонка обгортка може мати низьку щільність і не містити тригонометричних інструкцій. Знизьте порогові значення, а якщо шукаєте обгортки, використовуйте фактичну опцію скрипта `--min-icall 1` (не `--min-ical`); прямі викликані функції аналізуються, але за непрямими цілями переходу надійно стежити не можна. Менші пакети `--splitsize` допомагають, коли велика кількість згенерованих точок зупину сповільнює WinDbg. Кандидат не вважається підтвердженим, доки потрібний вхідний параметр не спричинить спрацювання його точки зупину.<sup>[[1]](#references)[[6]](#references)</sup>

## Невеликі програми для налагоджувача та PyKD

Використовуйте `.if`, коли умова надійна, `.foreach` — для перебору виводу, розділеного пробілами, а `.for` із псевдорегістрами — для обходу пам’яті чи структур. `.foreach` **не зберігає стовпці**: наприклад, вивід `lm` зі змінною шириною — поганий вхідний параметр, тоді як `lm 1m` повертає назву одного модуля на токен. Спочатку записуйте в журнал дані без фільтрації, якщо вгадана умова може приховати шлях до збою.<sup>[[1]](#references)</sup>

```text
.foreach (mod { lm 1m }) { .echo ${mod} }
r $t0 = 0
.for ( ; @$t0 < 5 ; r $t0 = @$t0 + 1 ) { .printf "i = %d\n", @$t0 }
```

Псевдоніми, створені за допомогою `as name value`, є текстовими підстановками, а не типізованими змінними. Команда `al` виводить їх список, `ad name` видаляє псевдонім, а `${name}` забезпечує однозначне розгортання. Не використовуйте назви на кшталт `bp`, `x` або `r`, оскільки псевдонім може затінити вбудовану команду. Вирази MASM підходять для арифметики вказівників, наприклад `poi(@$t0)`; `@@c++(...)` дає змогу звертатися до типізованих полів за наявності символів, уникаючи жорстко заданих зміщень у структурах.<sup>[[1]](#references)</sup>

Розміщуйте довші послідовності команд у файлі команд. `$$><filename` об’єднує рядки в один блок команд і дає змогу додати після нього команду debugger, відокремлену крапкою з комою. Багаторядкові керувальні конструкції все одно можуть бути ненадійними; записуйте кожен оператор `.if` або `.for` в один рядок. Той самий файл можна викликати під час запуску за допомогою `-c`.<sup>[[1]](#references)[[8]](#references)</sup>

Для логіки, яку незручно реалізувати мовою команд, PyKD надає Python доступ до типізованих структур, регістрів, пам’яті та виводу debugger. Наприклад, `pykd.typedVar("ntdll!_PEB", pykd.getCurrentProcess())` надає доступ до полів PEB, `pykd.loadBytes(address, size)` читає пам’ять, а `pykd.dbgCommand("lm")` повертає вивід debugger для обробки. Для даних, які можуть не завершуватися нульовим символом, віддавайте перевагу обмеженим `loadChars`/`loadWChars`, а не читанню рядків без обмеження. `disasm(address).asm(instruction)` у PyKD **записує зібрані байти за цією адресою**, тому, використовуючи цей метод для отримання opcodes у запущеному процесі, збережіть і відновіть початкову пам’ять.<sup>[[1]](#references)</sup>
