## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) і **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Це корисно, якщо потрібно відновити втрачений вихідний код зі старої збірки: такий підхід заощадить час. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin**.

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки широким можливостям розширення та API, що дає змогу налаштувати інструмент відповідно до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості реверс-інжинірингу, які надає цей інструмент:

- Дає змогу побачити, як дані проходять через бібліотеку або компонент
- Допомагає зрозуміти реалізацію та використання мов і фреймворків .NET
- Виявляє недокументовані й недоступні функції, щоб отримати більше від API та використовуваних технологій.
- Виявляє залежності та різні збірки
- Допомагає точно визначити місце помилок у вашому коді, сторонніх компонентах і бібліотеках.
- Дає змогу налагоджувати вихідний код будь-якого коду .NET, з яким ви працюєте.

### [ILSpy](https://github.com/icsharpcode/ILSpy) і [dnSpy](https://github.com/dnSpy/dnSpy/releases)

### Перевірка керованих збірок без виконання за допомогою REA

**REA** може перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Спочатку перевірте ідентичність артефакту, потім — його члени та оголошені межі native-коду; це корисно під час аналізу підозрілих викликів перед використанням декомпілятора або запуском програми.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує ідентичність raw CIL/signature та fingerprints декодованих інструкцій, а не вважає metadata tokens незмінними між збірками. Оголошення P/Invoke не є доказом виконання native-коду; `verify_managed_native_boundaries` потрібні відповідний native export або function Evidence, щоб перевірити цю межу. Зберігайте digest артефакту, MVID і нерозв’язані mappings разом із результатом.<sup>[[17]](#references)</sup>

## Налагодження DLL

### Використання IDA

- **Завантажте rundll32** (64-бітна версія — C:\Windows\System32\rundll32.exe, 32-бітна — C:\Windows\SysWOW64\rundll32.exe)
- Виберіть debugger **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Debugging DLLs - Using IDA: Виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** виконання, вказавши **шлях до DLL** і функцію, яку потрібно викликати:

![Debugging DLLs - Using IDA: Налаштуйте параметри виконання, вказавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку налагодження **виконання зупинятиметься під час завантаження кожної DLL**. Отже, коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей метод зупиняє виконання під час подій завантаження модулів, але дістатися до точки входу завантаженої DLL менш зручно, ніж за допомогою описаного нижче процесу в x64dbg.

### Використання x64dbg/x32dbg

- **Завантажте rundll32** (64-бітна версія — C:\Windows\System32\rundll32.exe, 32-бітна — C:\Windows\SysWOW64\rundll32.exe)
- **Змініть командний рядок** ( _File --> Change Command Line_ ) і вкажіть шлях до DLL та функцію, яку потрібно викликати, наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- Перейдіть до _Options --> Settings_ і виберіть "**DLL Entry**".
- Потім **запустіть виконання**. Налагоджувач зупинятиметься на точці входу кожної DLL; зрештою ви **зупинитеся на точці входу своєї DLL**. Звідти знайдіть місця, де потрібно встановити breakpoint.

Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, **у верхній частині вікна win64dbg** можна побачити, **який саме код виконується**:

![Using IDA - Using x64dbg/x32dbg: Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, у верхній частині вікна win64dbg можна побачити, який саме код виконується](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку ви хочете налагодити.

### Розшифрування Godot PCK і відновлення проєкту

Для поширюваної гри на Godot знайдіть її PCK: це може бути окремий файл `.pck`, пакет, доданий до виконуваного файла або вбудований у нього, чи каталог `assets` в APK. [gore](https://github.com/figurophobia/gore) може перевіряти та розпаковувати пакет, тоді як для повного відновлення скриптів і ресурсів потрібен GDRE Tools (`gore setup` встановлює його або скористайтеся `--gdre`). У цьому процесі інструмент підтримує формати Godot 4.x PCK v2–v4; він може виявляти заголовки v1, але для v1 потрібно надати ключ.<sup>[[25]](#references)</sup>

Для автоматичного відновлення ключа потрібна зашифрована таблиця файлів. Якщо зашифровано лише вміст файлів, натомість вкажіть відомий ключ. Невдала спроба відновлення не доводить, що пакет не зашифрований.<sup>[[28]](#references)</sup>

Пошук ключа — це **не атака на простір ключів AES-256**. Зашифрована таблиця файлів містить MD5 її відкритого тексту, довжину відкритого тексту, IV і шифротекст AES-256-CFB.<sup>[[27]](#references)</sup> `gore` перевіряє 32-байтові фрагменти виконуваного файла гри або сусідніх файлів як можливі ключі. Спочатку він відсіює кандидати за правдоподібною довжиною та префіксом розшифрованого шляху, а потім підтверджує знахідки сканування бінарних даних, розшифровуючи всю таблицю та перевіряючи її MD5.<sup>[[26]](#references)[[28]](#references)</sup> Спершу інструмент шукає в ініціалізованих секціях даних PE/ELF, а якщо не знаходить — сканує весь файл; параметр `--scan` додає інші файли-кандидати.<sup>[[28]](#references)</sup>

Якщо вбудованого ключа не знайдено, перевіряється невеликий вбудований список паролів; параметр `--wordlist` дає змогу вказати інші варіанти. Кожен пароль перевіряється як представлення ключа, похідного від пароля, як доповнений нулями буквальний рядок або як ключ із 64 шістнадцяткових символів. На відміну від знахідок сканування бінарних даних, збіги зі словника в цій реалізації перевіряються лише за структурою шляхів. Переконайтеся в їхній правильності, відкривши пакет і перевіривши витягнуті ресурси.<sup>[[26]](#references)[[28]](#references)</sup>

Якщо файл гри доступний локально, виберіть потрібний для аналізу етап. `recover` запускає GDRE для відновлення проєкту, який можна відкрити, а `extract` лише розпаковує вихідні файли. `key` виводить можливий ключ для використання з іншим інструментом.<sup>[[25]](#references)[[28]](#references)</sup>

```bash
gore info game.exe
gore key game.pck --scan game.exe
gore extract game.pck -o ./raw
gore setup
gore recover game.exe -o ./game_project
```

## Дослідження нативного коду з доказовою основою за допомогою REA

**REA** надає доступ до аналізу в Hopper, Ghidra та IDA через CLI і MCP. Для роботи потрібен Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спершу налаштуйте наявний native provider; перевірте `rea providers --json` і явно виберіть provider, якщо ціль підтримують кілька. Замість `0x1000` нижче використайте назву або адресу функції зі списку інвентаризації.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка або символу, пов’язаного з функцією, переходьте за посиланнями та до викликачів, а потім перегляньте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сесію до вибраного провайдера, а не підміняє його непомітно після збою. Для повторюваних запитів `--snapshot PATH` повторно використовує лише байти артефактів, провайдера, налаштування, операцію та параметри, які збігаються; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте отриманий Evidence та явні невідомі дані, а не сприймайте виведені шляхи чи текст декомпілятора як вихідний код.<sup>[[16]](#references)[[18]](#references)</sup>

Про точки входу JavaScript/Electron, що ведуть до нативних доповнень, див. [Electron Desktop Apps](../../network-services-pentesting/pentesting-web/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

## Скриптовий аналіз в IDA та Ghidra через локальний TCP-міст

[IDA-Ghidra-bridge](https://github.com/oscarsantanaarias/IDA-Ghidra-bridge) працює у **вже відкритій** базі даних IDA або програмі Ghidra CodeBrowser і дає змогу окремому скрипту надсилати запити до цієї бази аналізу та змінювати її. Запустіть `ID_Server.py` з Python CLI в IDA (`import ID_Server`) або `Ghidra_Server.py` із Script Manager у Ghidra. IDA прив’язується до `127.0.0.1`, починаючи з порту `5073`, і перевіряє наступні порти. Поточний скрипт Ghidra починає з порту `5093` і перевіряє десять портів — до `5102`; його Java-сокет прив’язується до wildcard-адреси, а не лише до loopback. Перш ніж підключатися, перевірте порт, який виводить екземпляр. На відміну від безголового аналізатора, цей міст працює з програмою, відкритою в поточному екземплярі GUI.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

Надсилайте **одну команду, завершену символом нового рядка, на кожне з’єднання** та зчитуйте відповідь, завершену символом нового рядка. Зазвичай результат має формат JSON. Наприклад, знайшовши імпортований API, пов’язаний із шляхом до вхідних даних, команда `IMPORTXREF` знаходить місця його виклику; потім `DECOMP_XREF` виконує пакетну декомпіляцію викликачів вибраної адреси. `FUNC` перевіряє функцію, а `PCODE` повертає проміжне представлення декомпілятора. Використовуйте адресу з активної бази даних, а не адресу, скопійовану з бінарного файла з іншою базовою адресою. У прикладі нижче використовується порт IDA за замовчуванням; для Ghidra використовуйте порт, виведений її скриптом.<sup>[[21]](#references)[[22]](#references)[[23]](#references)</sup>

```python
import socket

with socket.create_connection(("127.0.0.1", 5073)) as sock:
    sock.sendall(b"IMPORTXREF memcpy\n")
    print(sock.makefile("r", encoding="utf-8").readline())
```

Той самий канал може **змінювати базу даних аналізу**: `RENAME_FUNC`, `RETYPE`, `SETCONV`, `DEFSTRUCT`/`SETFIELD`, `MAKEFUNC` і `PATCH` змінюють назви, типи, визначення структур, межі функцій або збережені байти. `PATCH` — це редагування бази даних, **а не** доказ патча живого процесу. Жоден із listener не документує автентифікацію. IDA доступний лише через loopback, але Ghidra може бути доступний через мережеві інтерфейси; обмежте доступ до listener Ghidra під час його використання. `QUIT` зупиняє будь-який listener, а IDA також надає `ida_bridge_stop()`.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

## Деобфускація MBA-обфускації

**Mixed Boolean-Arithmetic (MBA)**-обфускація приховує прості вирази, як-от `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай правильні лише за **модульної арифметики з фіксованою розрядністю**, тому перенесення й переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити цей тип виразу за допомогою універсальних засобів алгебри, легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Збережіть початкову розрядність** коду/IR, отриманого в результаті ліфтування, або виводу декомпілятора (`8/16/32/64` біти).
2. **Класифікуйте вираз**, перш ніж намагатися його спростити:
   - **Лінійний**: зважені суми бітових атомів
   - **Напівлінійний**: лінійний вираз плюс константні маски, як-от `x & 0xFF`
   - **Поліноміальний**: наявні добутки
   - **Змішаний**: добутки й побітова логіка чергуються, часто з повторюваними підвиразами
3. **Перевірте кожне запропоноване перетворення** за допомогою випадкового тестування або SMT-доведення. Якщо еквівалентність неможливо довести, залиште початковий вираз, а не вгадуйте.

### Обійдіть сплющений control flow за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності control-flow flattening, opaque predicates, великих диспетчерів або коду з великою кількістю MBA виокремте посилання від зашифрованих блоків даних і вихідних буферів до найменшої процедури, що їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не є частиною потрібного рішення, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Складіть перелік виконуваних і даних секцій, релокацій і перехресних посилань. Вивантажте потенційні таблиці з `.rodata`, зберігши порядок байтів і ширину елементів.
2. Визначте останню процедуру, яка записує відкритий текст або вихідний буфер. Зафіксуйте її вхідні дані, таблиці, на які вона посилається, імпортовані виклики та необхідний глобальний стан.
3. Перенесіть лише ці операції у модель Python із фіксованою розрядністю. Якщо зріз усе ще залежить від надто великої кількості стану, викличте процедуру в Unicorn, QEMU або налагоджувачі й перехоплюйте неважливі імпортовані виклики замість емуляції всієї програми.
4. Переконайтеся, що екстрактор справді отримує результат із наданого бінарного файлу: приберіть непомітні резервні варіанти, перевірте файл на наявність вбудованих відповідей і запустіть його на невідомих збірках зі зміненими рядками, ключами, ідентифікаторами, макетами та початковими значеннями обфускації.

Корисні команди для початкової перевірки:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення MBA-виразів, замаскованих під константи

На перший погляд, байтовий вираз залежить від вхідних даних, але може повністю їх нівелювати. Після вилучення його таблиць обчисліть вираз для всього 8-бітного діапазону; одноелементна множина вихідних значень доводить, що цей байт є константою, і для цього не потрібно відновлювати навколишню машину станів.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Залиште фінальну маску, оскільки початкове додавання має циклічне переповнення за розрядністю байта. Для ширшої області значень запитайте SMT solver, чи є вираз `f(x1) != f(x2)` виконуваним для двох символічних входів однакової розрядності: `unsat` доводить інваріантність, тоді як `sat` надає контрприклад і означає, що вхід не можна відкинути.<sup>[[7]](#references)</sup>

#### Розпізнавання декодування, залежного від середовища

Перевірки протидії аналізу не обов'язково мають спричиняти перехід або збій. Декодер може змішати результат сенсора з бітом ключа, константою opaque predicate або станом flattened dispatcher, продовжити роботу в звичайному режимі й отримати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо виправити лише видимі гілки збоїв; простежте залежності даних від зондування середовища до стану декодера, порівняйте той самий фрагмент на справжньому пристрої та в емуляторі й перевірте, як примусова зміна результату кожного сенсора впливає на фінальний буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — практичний спрощувач MBA для аналізу шкідливого ПЗ та реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його через спеціалізовані конвеєри замість того, щоб застосовувати один універсальний прохід переписування до всього.<sup>[[2]](#references)</sup>

Швидке використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, виводить сигнатуру та запускає кілька методів відновлення, як-от зіставлення зі зразком, перетворення ANF і інтерполяція коефіцієнтів.
- **Semilinear MBA**: атоми з константною маскою відновлюються за допомогою реконструкції з розбиттям на біти, щоб замасковані ділянки залишалися коректними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього співвідношення.

Приклад змішаної тотожності, яку часто варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна звести до:

```c
x * y
```

- Запускайте CoBRA на **виразах IR після підняття** або на результатах декомпіляції, коли ізолювали точне обчислення.
- Явно задавайте `--bitwidth`, якщо вираз походить із masked arithmetic або вузьких регістрів.
- Якщо потрібен сильніший крок доведення, перегляньте локальні нотатки про Z3 тут:


{{#ref}}
satisfiability-modulo-theories-smt-z3.md
{{#endref}}

- CoBRA також постачається як **плагін LLVM pass** (`libCobraPass.so`), корисний для нормалізації LLVM IR із великою кількістю MBA перед подальшими passes аналізу.

## Відновлення flattening потоку керування зі станом XOR

Flattener у стилі OLLVM може зберігати стан поточного базового блоку у двох 64-бітових регістрах і відновлювати його за допомогою XOR у dispatcher. Кожен вихідний блок записує пару для наступного стану й переходить назад до dispatcher. Умовний блок може використовувати `CMOVcc`, щоб замінити одну половину пари відповідно до прапорців CPU, тому, відстежуючи лише видимі інструкції переходу, можна пропустити одного з двох наступників. На відміну від dispatcher з непрямим переходом, ця структура може використовувати прямі переходи назад упродовж усього коду.<sup>[[19]](#references)[[20]](#references)</sup>

Щоб відновити граф, знайдіть дерево порівнянь dispatcher і два регістри стану, зіставте кожен порівнюваний стан XOR із цільовим блоком, а потім простежте записи до пари регістрів, що досягають кожного вихідного блоку. Для умовних записів врахуйте інструкцію, яка встановлює прапорці, та обидва результати `CMOVcc`. Замініть вихід dispatcher у кожному блоці на визначений прямий наступник або умовний перехід; після цього dispatcher стає недосяжним без патчення бінарного файла. Це підхід на основі повного CFG; якщо важливий лише один decoder, наведений вище [workflow вузького зрізу виконання](#bypass-flattened-control-flow-with-a-narrow-execution-slice) може бути швидшим.<sup>[[19]](#references)[[20]](#references)</sup>

[DispatchThis](https://github.com/YungBinary/DispatchThis) автоматизує цю структуру в Binary Ninja. Скопіюйте `plugins/DispatchThis` до каталогу користувацьких плагінів Binary Ninja та перезапустіть програму. Для потрібної функції відкрийте **Function Settings** і виберіть `OLLVM_XOR_64`; якщо аналіз не починається, скористайтеся **Analysis → Reanalyze All Functions**. Цей режим переписує ребра потоку керування MLIL, а не байти файла, і не потребує Z3 чи resolver-а непрямих переходів. Його перевірено на Binary Ninja 5.3.9757+; він не видаляє мертві записи стану в кожному блоці, тож не сприймайте їх за активні переходи, що залишилися.<sup>[[19]](#references)</sup>


Якщо ви граєте в **CTF, цей обхідний спосіб пошуку flag** може бути дуже корисним: [https://dustri.org/b/defeating-the-recons-movfuscator-crackme.html](https://dustri.org/b/defeating-the-recons-movfuscator-crackme.html)

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не адресуються як C-рядки з NUL-термінатором. Типова структура `rustc` — це **кортеж вказівника й довжини** всередині **`.data.rel.ro`**, що вказує на фактичний блок рядка, збережений у **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднати сусідні рядки або зовсім не виявити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Переберіть **`.data.rel.ro`** по одному слову за раз.
3. Вважайте будь-яке значення в діапазоні адрес `.rodata` потенційним вказівником на рядок.
4. Вважайте наступне слово потенційною довжиною.
5. Застосуйте фільтри перевірки на правдоподібність (наприклад, залиште довжини від **4** до **100** байтів).
6. Зчитайте рівно `length` байтів із `.rodata`, а не скануйте до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно під час реверсингу firmware, оскільки відновлені рядки Rust часто розкривають **HTTP routes, назви RPC, повідомлення журналу, assertions, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra не знаходить ці рядки, запустіть власний скрипт/plugin, який застосовує ту саму евристику й створює рядкові дані за відповідними зміщеннями в `.rodata`. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — гарні приклади для адаптації цієї ідеї до інших **розмірів слів, порядку байтів і структури секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

### Відновлення метаданих без таблиці символів

У stripped виконуваному файлі Go все одно потрібні метадані runtime, щоб зіставити лічильники команд із функціями. [GoReSym](https://github.com/mandiant/GoReSym) знаходить і розбирає такі структури, як `pclntab` і `moduledata`, використовуючи код, створений на основі runtime Go. Це дає змогу відновити межі функцій, назви, шляхи до вихідних файлів, типи й відомості про збірку без опори на звичайну таблицю символів.<sup>[[9]](#references)[[13]](#references)</sup>

```bash
GoReSym.exe -t -d -p /path/to/sample.exe > goresym.json
```

Обфускатор може залишити ці структури придатними до використання, замінивши відновлені назви. Наприклад, Garble хешує ідентифікатори та шляхи пакетів і видаляє інформацію про збірку, модулі й налагодження.<sup>[[12]](#references)</sup> Токен обфускованого пакета має залишатися незмінним у функціях цього пакета. Згрупуйте функції за повторюваним токеном, визначте пакет однієї з них за її викликаними функціями, рядками й API, а потім призначте цю назву пакета всій групі.<sup>[[13]](#references)</sup>

### Відновлення назв Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує вилучення символів runtime зі створенням еталонів без обфускації та зіставленням графів потоку керування (CFG). Виконайте такі кроки:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спершу перевірте `BuildInfo` і вбудовані рядки версії. Якщо обфускатор їх видалив, порівняйте частини вбудованого runtime Go з еталонними runtime різних версій. У тестах Volexity приблизно `2%` runtime було достатньо, щоб розрізнити основні версії Go. Вважайте це емпіричною оптимізацією, а не універсальним порогом.<sup>[[13]](#references)</sup>
2. **Підготуйте відповідні еталони.** Створіть чисті бінарні файли для визначеної версії Go, цільової архітектури та ймовірних бібліотек. Відповідність toolchain зменшує відмінності CFG, створені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє графи потоку керування (CFG) функцій і видає нормалізовані оцінки від `0.0` до `1.0`. Зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Зіставлення з високою впевненістю пов’язують функції з рандомізованими назвами з відповідними чистими реалізаціями. Менш надійні зіставлення все одно можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте й імпортуйте.** Перевірте запропоновані назви за зв’язками викликів, константами, рядками та побічними ефектами, а потім імпортуйте звіт JSON за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Встановіть toolchain і запустіть комбінований екстрактор і зіставлювач графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Порогове значення значущого збігу за замовчуванням — `0.9`. Прапорці `--extract` і `--graph` дають змогу запускати окремо будь-який етап, тоді як за замовчуванням виконуються обидва, оскільки відновлені метадані runtime та свідчення CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнінг, прапорці збірки, архітектура та відмінності версій бібліотек можуть змінити структуру графа, тож залишайте невизначені функції нерозв’язаними, а не призначайте їм імена з низьким рівнем упевненості.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків усіх підключених пакетів в одній суцільній таблиці. Записи не завершуються NUL, а структури runtime не містять базової адреси чи розміру таблиці. Проте компілятор упорядковує записи спочатку за довжиною, а потім за алфавітом, незалежно від операційної системи та архітектури. Тож після знаходження одного запису аналітик може переглядати сусідні записи й за перехресними посиланнями на дані пов’язувати рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro і Ghidra. Спочатку дочекайтеся завершення автоаналізу, оскільки плагін покладається на перехресні посилання із сегментів даних. Якорем за замовчуванням слугує рядок runtime `entersyscall`; після цього плагін може сканувати в обох напрямках, визначати відновлені рядки в базі даних і експортувати JSON-відповідність рядків функціям, на які вони посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, на яку посилаються, щоб відокремити код застосунку або malware від шуму підключених бібліотек. Цей метод не може відновити літерали, знищені обфускацією, як-от перетворенням Garble `-literals`. Однак він усе ще може впорядкувати рядки runtime, що залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів runtime Go

Go вбудовує інформацію про типи runtime, яку використовують такі функції, як збірка сміття. Якщо інформацію про збірку видалено або дизасемблер не аналізує ці метадані, може здаватися, що інструкції завантажують довільні адреси даних, а цільова область залишається нетипізованою. Відновлення метаданих перетворює ці адреси на зрозумілі посилання на типи й полегшує визначення можливостей пакета.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи й розбирати типи runtime, створюючи JSON-звіт. У поточному CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Опція `-y`/`--types` вмикає парсинг типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи й застосувати їхні посилання в базі даних аналізу. У форматі звіту, запровадженому разом із цією функцією, якщо не вказати `-y`, адреса RTTI та поля відновлених типів матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM і ARM64, тож той самий робочий процес застосовується до бінарних файлів Go для Windows, Linux і macOS.<sup>[[10]](#references)</sup>

У цій функції після кількох операцій ініціалізації (які не мають значення):

```c
void FUN_080015a8(void)

  ushort uVar1;
  undefined4 uVar2;
  undefined4 uVar3;
  ushort uVar4;
  int iVar5;
  ushort *puVar6;
  undefined *local_2c;

  DISPCNT = 0x1140;
  FUN_08000a74();
  FUN_08000ce4(1);
  DISPCNT = 0x404;
  FUN_08000dd0(&DAT_02009584,0x6000000,&DAT_030000dc);
  FUN_08000354(&DAT_030000dc,0x3c);
  uVar4 = DAT_030004d8;
```

Знайдено такий код:

```c
  do {
    DAT_030004da = uVar4; //This is the last key pressed
    DAT_030004d8 = KEYINPUT | 0xfc00;
    puVar6 = &DAT_0200b03c;
    uVar4 = DAT_030004d8;
    do {
      uVar2 = DAT_030004dc;
      uVar1 = *puVar6;
      if ((uVar1 & DAT_030004da & ~uVar4) != 0) {
```

Останній if перевіряє, чи **`uVar4`** є серед **last Keys** і не є поточним ключем. Це також називається відпусканням кнопки (поточний ключ зберігається в **`uVar1`**).

```c
        if (uVar1 == 4) {
          DAT_030000d4 = 0;
          uVar3 = FUN_08001c24(DAT_030004dc);
          FUN_08001868(uVar2,0,uVar3);
          DAT_05000000 = 0x1483;
          FUN_08001844(&DAT_0200ba18);
          FUN_08001844(&DAT_0200ba20,&DAT_0200ba40);
          DAT_030000d8 = 0;
          uVar4 = DAT_030004d8;
        }
        else {
          if (uVar1 == 8) {
            if (DAT_030000d8 == 0xf3) {
              DISPCNT = 0x404;
              FUN_08000dd0(&DAT_02008aac,0x6000000,&DAT_030000dc);
              FUN_08000354(&DAT_030000dc,0x3c);
              uVar4 = DAT_030004d8;
            }
          }
          else {
            if (DAT_030000d4 < 8) {
              DAT_030000d4 = DAT_030000d4 + 1;
              FUN_08000864();
              if (uVar1 == 0x10) {
                DAT_030000d8 = DAT_030000d8 + 0x3a;
```

У попередньому коді видно, що ми порівнюємо **uVar1** (місце, де зберігається **значення натиснутої кнопки**) з деякими значеннями:

- Спочатку його порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран.
- Потім значення порівнюють із **8** (кнопка **START**); у цьому завданні цей шлях перевіряє, чи правильний введений код.
  - У цьому випадку змінну **`DAT_030000d8`** порівнюють із 0xf3, і якщо значення збігається, виконується певний код.
- В усіх інших випадках перевіряють і збільшують лічильник (`DAT_030000d4`).\
  Поки лічильник менший за 8, значення натиснутих кнопок додаються до `DAT_030000d8`.

Отже, у цьому завданні, знаючи значення кнопок, потрібно було **натиснути комбінацію довжиною менш ніж 8, щоб сума її значень дорівнювала 0xf3.**
