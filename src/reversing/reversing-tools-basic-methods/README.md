## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) і **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Перевага цього інструмента в тому, що він заощаджує час, коли потрібно відновити втрачений вихідний код зі застарілої збірки. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin.**

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки розширюваній моделі надбудов та API, який дає змогу налаштувати інструмент відповідно до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості реверс-інжинірингу, які надає цей інструмент:

- Дає змогу зрозуміти, як дані проходять через бібліотеку або компонент
- Допомагає зрозуміти реалізацію та використання мов і фреймворків .NET
- Виявляє недокументовані й приховані функції, щоб отримати більше можливостей від використовуваних API та технологій.
- Виявляє залежності та різні збірки
- Допомагає знайти точне місце помилок у вашому коді, сторонніх компонентах і бібліотеках.
- Дає змогу налагоджувати вихідний код усього коду .NET, з яким ви працюєте.

### [ILSpy](https://github.com/icsharpcode/ILSpy) та [dnSpy](https://github.com/dnSpy/dnSpy/releases)

[Плагін ILSpy для Visual Studio Code](https://github.com/icsharpcode/ilspy-vscode): його можна використовувати в будь-якій ОС (можна встановити безпосередньо з VSCode, завантажувати git не потрібно. Натисніть **Extensions** і **знайдіть ILSpy**).\
Якщо потрібно **декомпілювати**, **змінити** і знову **скомпілювати**, можна скористатися [**dnSpy**](https://github.com/dnSpy/dnSpy/releases) або його активно підтримуваним форком [**dnSpyEx**](https://github.com/dnSpyEx/dnSpy/releases). (**Клацніть правою кнопкою миші -> Modify Method**, щоб змінити щось усередині функції).

### Перевірка керованих збірок без виконання за допомогою REA

**REA** дає змогу перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Спершу визначте ідентичність артефакту, а потім перегляньте його члени та оголошені межі нативного коду; це корисно для аналізу підозрілих викликів перед використанням декомпілятора або запуском програми.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує ідентичність за сирими CIL/сигнатурами та fingerprints декодованих інструкцій, а не вважає токени метаданих стабільними між збірками. Оголошення P/Invoke не доводить, що виконувався native-код; `verify_managed_native_boundaries` потрібні відповідний native export або свідчення про функцію, щоб перевірити цю межу. Зберігайте digest артефакту, MVID і нерозв’язані зіставлення разом із результатом.<sup>[[17]](#references)</sup>

## Налагодження DLL

### Використання IDA

- **Завантажте rundll32** (64-бітну версію з C:\Windows\System32\rundll32.exe, а 32-бітну — з C:\Windows\SysWOW64\rundll32.exe)
- Виберіть налагоджувач **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Налагодження DLL - Використання IDA: виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** запуску, вказавши **шлях до DLL** і функцію, яку потрібно викликати:

![Налагодження DLL - Використання IDA: налаштуйте параметри запуску, вказавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку налагодження **виконання зупинятиметься під час завантаження кожної DLL**. Отже, коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей метод зупиняє виконання під час подій завантаження модулів, але дійти до точки входу завантаженої DLL не так просто, як у наведеному нижче сценарії з x64dbg.

### Використання x64dbg/x32dbg

- **Завантажте rundll32** (64-бітну версію з C:\Windows\System32\rundll32.exe, а 32-бітну — з C:\Windows\SysWOW64\rundll32.exe)
- **Змініть командний рядок** ( _File --> Change Command Line_ ) і вкажіть шлях до DLL та функцію, яку потрібно викликати, наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- Відкрийте _Options --> Settings_ і виберіть "**DLL Entry**".
- Потім **запустіть виконання**. Налагоджувач зупинятиметься на точці входу кожної DLL; у певний момент він **зупиниться на точці входу вашої DLL**. Звідти знайдіть ділянки, де потрібно встановити точку зупинки.

Зверніть увагу: коли виконання в win64dbg зупинено з будь-якої причини, **у верхній частині вікна win64dbg** можна побачити, **у якому коді ви перебуваєте**:

![Використання IDA - Використання x64dbg/x32dbg: зверніть увагу, що коли виконання в win64dbg зупинено з будь-якої причини, у верхній частині вікна win64dbg можна побачити, у якому коді ви перебуваєте](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку потрібно налагодити.

## Дослідження нативного коду на основі доказів за допомогою REA

**REA** надає доступ до аналізу в Hopper, Ghidra та IDA через CLI і MCP. Для роботи потрібен Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спочатку налаштуйте наявний нативний provider; виконайте `rea providers --json` і явно виберіть provider, якщо кілька з них підтримують цільовий об’єкт. Замість `0x1000` нижче використайте спостережену назву функції або адресу з інвентаризації.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка функції або символу, переходьте за посиланнями та викликами, а потім перевірте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сеанс до вибраного провайдера, а не перемикається на інший після збою без попередження. Для повторюваних запитів `--snapshot PATH` повторно використовує лише відповідні байти артефакту, провайдера, налаштування, операцію та параметри; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте отримані Evidence та явно зазначені невідомі дані, а не сприймайте виведені шляхи чи текст декомпілятора як вихідний код.<sup>[[16]](#references)[[18]](#references)</sup>

Для точок входу JavaScript/Electron, що ведуть до native add-ons, див. [Electron Desktop Apps](../../network-services-pentesting/pentesting-web/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

## Скриптовий аналіз в IDA та Ghidra через локальний TCP-міст

[IDA-Ghidra-bridge](https://github.com/oscarsantanaarias/IDA-Ghidra-bridge) працює в **уже відкритій** базі даних IDA або програмі Ghidra CodeBrowser і дає змогу окремому скрипту надсилати запити до цієї бази аналізу та змінювати її. Запустіть `ID_Server.py` у Python CLI IDA (`import ID_Server`) або `Ghidra_Server.py` у Script Manager Ghidra. IDA прив’язується до `127.0.0.1`, починаючи з порту `5073`, і перевіряє наступні порти. Поточний скрипт Ghidra починає з порту `5093` і перевіряє десять портів аж до `5102`; його Java-сокет прив’язується до wildcard-адреси, а не лише до loopback. Перш ніж підключатися, перевірте порт, надрукований екземпляром. На відміну від headless analyzer, цей міст працює з програмою, відкритою в поточному екземплярі GUI.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

Надсилайте **одну команду, завершену символом нового рядка, на кожне з’єднання** та зчитуйте відповідь, завершену символом нового рядка. Зазвичай результат має формат JSON. Наприклад, знайшовши імпортований API, пов’язаний із вхідним шляхом, `IMPORTXREF` знаходить місця його виклику; потім `DECOMP_XREF` пакетно декомпілює викликачів вибраної адреси. `FUNC` перевіряє функцію, а `PCODE` повертає проміжне представлення декомпілятора. Використовуйте адресу з активної бази даних, а не адресу, скопійовану з бінарного файла з іншою базовою адресою. У прикладі нижче використовується порт IDA за замовчуванням; для Ghidra використовуйте порт, надрукований її скриптом.<sup>[[21]](#references)[[22]](#references)[[23]](#references)</sup>

```python
import socket

with socket.create_connection(("127.0.0.1", 5073)) as sock:
    sock.sendall(b"IMPORTXREF memcpy\n")
    print(sock.makefile("r", encoding="utf-8").readline())
```

Той самий канал може **змінювати базу даних аналізу**: `RENAME_FUNC`, `RETYPE`, `SETCONV`, `DEFSTRUCT`/`SETFIELD`, `MAKEFUNC` і `PATCH` змінюють назви, типи, визначення структур, межі функцій або збережені байти. `PATCH` — це редагування бази даних, а **не** свідчення про патч у запущеному процесі. В описі жодного з listener не згадується автентифікація. IDA доступна лише через loopback, але Ghidra може бути доступна через мережеві інтерфейси; обмежте доступ до listener Ghidra під час її використання. `QUIT` зупиняє будь-який із listener, а IDA також надає `ida_bridge_stop()`.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

### Налагодження shellcode за допомогою blobrunner

[**BlobRunner**](https://github.com/OALabs/BlobRunner) виділяє пам'ять для **shellcode**, виводить її **адресу в пам'яті** й призупиняє виконання.\

На сторінці releases на GitHub є ZIP-архіви зі скомпільованими версіями: [https://github.com/OALabs/BlobRunner/releases/tag/v0.0.5](https://github.com/OALabs/BlobRunner/releases/tag/v0.0.5)\

## Деобфускація MBA obfuscation

**Обфускація Mixed Boolean-Arithmetic (MBA)** приховує прості вирази, як-от `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай справджуються лише в умовах **модульної арифметики з фіксованою розрядністю**, тому переноси й переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити такий вираз за допомогою універсальних засобів алгебраїчних перетворень, можна легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Зберігайте початкову розрядність** коду/IR після lifting або виводу декомпілятора (`8/16/32/64` бітів).
2. **Класифікуйте вираз**, перш ніж намагатися його спростити:
   - **Лінійний**: зважені суми бітових атомів
   - **Напівлінійний**: лінійний вираз плюс константні маски, як-от `x & 0xFF`
   - **Поліноміальний**: містить добутки
   - **Змішаний**: добутки та побітова логіка переплетені, часто з повторюваними підвиразами
3. **Перевіряйте кожне можливе перетворення** випадковим тестуванням або доведенням за допомогою SMT. Якщо еквівалентність неможливо довести, залиште початковий вираз замість того, щоб вгадувати.

### Обходьте сплощений потік керування за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності сплощення потоку керування, непрозорих предикатів, великих диспетчерів або коду з великою кількістю MBA відстежуйте посилання від зашифрованих блоків даних і вихідних буферів до найменшої процедури, яка їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не потрібен для розв’язання задачі, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Складіть перелік виконуваних і даних секцій, релокацій та перехресних посилань. Дампіть потенційні таблиці з `.rodata`, зберігаючи порядок байтів і ширину елементів.
2. Визначте останню процедуру, яка записує відкритий текст або вихідний буфер. Зафіксуйте її вхідні дані, таблиці, на які вона посилається, імпортовані виклики та необхідний глобальний стан.
3. Перенесіть лише ці операції у модель Python із фіксованою розрядністю. Якщо зріз усе ще залежить від надмірної кількості стану, викликайте процедуру за допомогою Unicorn, QEMU або налагоджувача та перехоплюйте нерелевантні імпортовані функції замість емуляції всієї програми.
4. Переконайтеся, що екстрактор справді отримує результат із наданого бінарного файла: приберіть непомітні резервні варіанти, перевірте файл на вбудовані відповіді та запустіть його на невідомих раніше збірках зі зміненими рядками, ключами, ідентифікаторами, структурами даних і початковими значеннями обфускації.

Корисні команди для початкового аналізу:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення MBA-виразів, що маскують константи

На перший погляд, вираз байта, залежний від вводу, може повністю нівелювати його вплив. Після вилучення таблиць обчисліть вираз для всього 8-бітного діапазону; якщо множина вихідних значень містить лише один елемент, це доводить, що байт є константою, і для цього не потрібно відновлювати навколишній автомат станів.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Залиште фінальну маску, оскільки початкове додавання має циклічне переповнення в межах ширини байта. Для ширшої області попросіть SMT-розв’язувач перевірити, чи є формула `f(x1) != f(x2)` задовільною для двох символічних входів однакової ширини: `unsat` доводить інваріантність, а `sat` надає контрприклад і означає, що вхід не можна відкинути.<sup>[[7]](#references)</sup>

#### Розпізнавання декодування, прив’язаного до середовища

Перевірки anti-analysis не обов’язково мають спричиняти перехід або аварійне завершення. Декодер може домішати результат датчика до біта ключа, константи непрозорого предиката або стану розплющеного диспетчера, продовжити роботу у звичайному режимі й отримати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо пропатчити лише видимі гілки з помилками; відстежуйте залежності даних від зондування середовища до стану декодера, порівнюйте той самий фрагмент на справжньому пристрої та в емуляторі й перевіряйте, як примусове встановлення результату кожного датчика змінює фінальний буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — це практичний спрощувач MBA для аналізу malware і реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його через спеціалізовані конвеєри, замість того щоб застосовувати один універсальний прохід переписування до всього.<sup>[[2]](#references)</sup>

Швидке використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, виводить сигнатуру та запускає паралельно кілька методів відновлення, як-от зіставлення зі зразками, перетворення ANF і інтерполяцію коефіцієнтів.
- **Semilinear MBA**: атоми з масками-константами відновлюються за допомогою реконструкції з розбиттям на біти, щоб замасковані ділянки залишалися правильними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього співвідношення.

Приклад змішаної тотожності, яку зазвичай варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна звести до:

```c
x * y
```

## Відновлення керування потоком, сплощеного XOR-станом

Сплощувач у стилі OLLVM може зберігати стан поточного базового блока у двох 64-бітних регістрах і відновлювати його за допомогою XOR у диспетчері. Кожен початковий блок записує пару для наступного стану й переходить назад до диспетчера. Умовний блок може використовувати `CMOVcc`, щоб замінити одну половину пари відповідно до прапорців CPU, тому відстеження лише видимих інструкцій переходу пропускає двох наступників. На відміну від диспетчера з непрямим переходом, така структура може використовувати прямі зворотні переходи всюди.<sup>[[19]](#references)[[20]](#references)</sup>

Щоб відновити граф, визначте дерево порівнянь диспетчера та два регістри стану, зіставте кожен порівнюваний XOR-стан із цільовим блоком, а потім відстежте записи в пару регістрів у кожному початковому блоці, що доходять до цього місця. Для умовних записів врахуйте інструкцію, яка встановлює прапорці, та обидва результати `CMOVcc`. Замініть вихід кожного блока до диспетчера на визначений прямий перехід або умовну гілку; після цього диспетчер стає недосяжним без виправлення бінарного файла. Це підхід, що охоплює весь CFG; якщо важливий лише один декодер, описаний вище [робочий процес вузького зрізу виконання](#bypass-flattened-control-flow-with-a-narrow-execution-slice) може бути швидшим.<sup>[[19]](#references)[[20]](#references)</sup>

[DispatchThis](https://github.com/YungBinary/DispatchThis) автоматизує цю структуру в Binary Ninja. Скопіюйте `plugins/DispatchThis` до каталогу користувацьких плагінів Binary Ninja та перезапустіть програму. Для відповідної функції відкрийте **Function Settings** і виберіть `OLLVM_XOR_64`; якщо аналіз не почнеться, скористайтеся **Analysis → Reanalyze All Functions**. Цей режим переписує ребра керування потоком MLIL, а не байти файла, і не потребує Z3 чи розв’язувача непрямих переходів. Його перевіряли на Binary Ninja 5.3.9757+; він не видаляє неактивні записи стану в кожному блоці, тож не сприймайте їх як переходи, що все ще виконуються.<sup>[[19]](#references)</sup>

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не посилаються через вказівники на рядки, завершені NUL, як у C. Типова структура `rustc` — це **кортеж вказівника й довжини** всередині **`.data.rel.ro`**, який вказує на справжній блок рядків у **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднати сусідні рядки або зовсім не виявити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Переберіть **`.data.rel.ro`** по одному слову.
3. Вважайте будь-яке значення в діапазоні адрес `.rodata` кандидатом на вказівник на рядок.
4. Вважайте наступне слово можливою довжиною.
5. Застосуйте фільтри перевірки адекватності (наприклад, залиште довжини від **4** до **100** байтів).
6. Прочитайте з `.rodata` рівно `length` байтів замість сканування до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно під час реверс-аналізу прошивки, оскільки відновлені рядки Rust часто розкривають **HTTP-маршрути, назви RPC, повідомлення журналу, assertions, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra не знаходить ці рядки, запустіть власний скрипт/плагін, який застосовує ту саму евристику й створює дані рядків за відповідними зміщеннями в `.rodata`. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — хороші приклади, на основі яких можна адаптувати цей підхід до інших **розмірів слів, порядку байтів і структури секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

## **Delphi**

Для бінарних файлів, скомпільованих у Delphi, можна використовувати [https://github.com/crypto2011/IDR](https://github.com/crypto2011/IDR)

Якщо потрібно виконати реверс-аналіз бінарного файлу Delphi, раджу скористатися плагіном IDA [https://github.com/Coldzer0/IDA-For-Delphi](https://github.com/Coldzer0/IDA-For-Delphi)

Натисніть **Alt+F7** в IDA, щоб завантажити плагін Python, а потім виберіть файл плагіна.

На початку налагодження цей плагін запустить бінарний файл і динамічно визначить назви функцій. Після запуску налагодження знову натисніть кнопку Start (зелену або f9), і на початку справжнього коду спрацює breakpoint.

Якщо натиснути кнопку в графічному застосунку, налагоджувач може зупинитися у функції, яку викликає ця кнопка.

## Golang

Якщо потрібно виконати реверс-аналіз бінарного файлу Golang, раджу скористатися плагіном IDA [https://github.com/sibears/IDAGolangHelper](https://github.com/sibears/IDAGolangHelper)

Це дасть змогу визначити назви функцій.

### Відновлення метаданих без таблиці символів

Навіть у stripped-виконуваному файлі Go потрібні метадані runtime, щоб зіставляти лічильники команд із функціями. [GoReSym](https://github.com/mandiant/GoReSym) знаходить і розбирає такі структури, як `pclntab` і `moduledata`, використовуючи код, похідний від runtime Go. Це дає змогу відновити межі функцій, їхні назви, шляхи до вихідних файлів, типи та відомості про збірку без використання звичайної таблиці символів.<sup>[[9]](#references)[[13]](#references)</sup>

```bash
GoReSym.exe -t -d -p /path/to/sample.exe > goresym.json
```

Обфускатор може залишити ці структури придатними до використання, замінивши відновлені назви. Наприклад, Garble хешує ідентифікатори й шляхи пакетів та видаляє інформацію про збірку, модулі й налагодження.<sup>[[12]](#references)</sup> Токен обфускованого пакета має бути однаковим у функціях цього пакета. Згрупуйте функції за повторюваним токеном, визначте пакет однієї з них за її функціями-калерами, рядками й API, а потім застосуйте цю мітку пакета до всієї групи.<sup>[[13]](#references)</sup>

### Відновлення назв Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує витягування символів під час виконання з генерацією чистих еталонів і зіставленням графів потоку керування (CFG). Виконайте такі кроки:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спочатку перевірте `BuildInfo` і вбудовані рядки версії. Якщо обфускатор видалив їх, порівняйте фрагменти вбудованого середовища виконання Go з еталонними середовищами виконання для різних версій. У тестах Volexity приблизно `2%` середовища виконання було достатньо, щоб розрізнити основні версії Go. Вважайте це емпіричною оптимізацією, а не універсальним порогом.<sup>[[13]](#references)</sup>
2. **Підготуйте еталони для зіставлення.** Створіть чисті бінарні файли для визначеної версії Go, цільової архітектури й імовірних бібліотек. Збіг наборів інструментів зменшує відмінності CFG, створені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє CFG функцій і видає нормалізовані оцінки від `0.0` до `1.0`. Зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Зіставлення з високою впевненістю пов’язують рандомізовані функції з чистою реалізацією. Зіставлення з нижчою впевненістю все одно можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте й імпортуйте.** Підтвердьте запропоновані назви за зв’язками викликів, константами, рядками та побічними ефектами, а потім імпортуйте звіт JSON за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Установіть набір інструментів і запустіть комбінований екстрактор і зіставлювач графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Порогове значення значущого збігу за замовчуванням — `0.9`. Параметри `--extract` і `--graph` дають змогу окремо виконати кожен етап, тоді як за замовчуванням запускаються обидва, оскільки відновлені метадані runtime і дані CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнінг, прапорці збірки, архітектура та відмінності версій бібліотек можуть змінити структуру графа, тому залишайте нерозв’язані функції, а не присвоюйте їм імена з низькою впевненістю.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків з усіх скомпонованих пакетів в одній суцільній таблиці. Записи не завершуються NUL-байтом, а структури runtime не містять базової адреси чи розміру таблиці. Однак компілятор впорядковує записи спочатку за довжиною, а потім за алфавітом — однаково в різних операційних системах і архітектурах. Тож знайшовши один запис, аналітик може пройти до сусідніх записів і за перехресними посиланнями на дані пов’язати рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro і Ghidra. Спочатку дочекайтеся завершення автоаналізу, оскільки плагін використовує перехресні посилання на сегменти даних. За замовчуванням як якір використовується рядок runtime `entersyscall`; після цього плагін може сканувати в обох напрямках, визначити відновлені рядки в базі даних і експортувати JSON-відповідність рядків функціям, які на них посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, яка посилається на рядок, щоб відокремити код застосунку або malware від зайвого шуму скомпонованих бібліотек. Цей метод не дає змоги відновити літерали, знищені обфускацією, наприклад перетворенням Garble `-literals`. Водночас він може впорядкувати рядки runtime, які залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів Go runtime

Go вбудовує інформацію про типи runtime, яку використовують такі можливості, як збирання сміття. Якщо інформацію про збірку видалено або дизасемблер не розбирає ці метадані, інструкції можуть виглядати так, ніби вони завантажують довільні адреси даних, а цільова область залишається без типів. Відновлення метаданих перетворює ці адреси на зрозумілі посилання на типи та полегшує розуміння можливостей пакетів.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи й розбирати типи runtime у звіт JSON. У поточному CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Опція `-y`/`--types` вмикає розбір типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи й застосувати їхні посилання в базі даних аналізу. У форматі звіту, запровадженому разом із цією функцією, якщо не вказати `-y`, адреса RTTI та поля відновлених типів матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM та ARM64, тож цей робочий процес підходить для бінарних файлів Go з Windows, Linux і macOS.<sup>[[10]](#references)</sup>

У [**no$gba**](https://problemkaputt.de/gba.htm), у розділі _**Options --> Emulation Setup --> Controls**_** ** можна подивитися, як натискати **кнопки** Game Boy Advance

![Конфігурація кнопок no$gba з відповідністю клавіш кнопкам Game Boy Advance](<../../images/image (581).png>)

Після натискання кожна **клавіша має значення**, за яким її можна ідентифікувати:

```
A = 1
B = 2
SELECT = 4
START = 8
RIGHT = 16
LEFT = 32
UP = 64
DOWN = 128
R = 256
L = 256
```

Отже, у програмі такого типу цікаво буде **як програма обробляє введені користувачем дані**. За адресою **0x4000130** ви знайдете поширену функцію: **KEYINPUT**.

![Вигляд Ghidra бінарного файлу GBA із посиланням на KEYINPUT за адресою 0x4000130](<../../images/image (447).png>)

На попередньому зображенні видно, що функцію викликає **FUN_080015a8** (адреси: _0x080015fa_ та _0x080017ac_).

У цій функції, після кількох операцій ініціалізації (які не мають особливого значення):

```c
void FUN_080015a8(void)

{
  ushort uVar1;
  undefined4 uVar2;
  undefined4 uVar3;
  ushort uVar4;
  int iVar5;
  ushort *puVar6;
  undefined *local_2c;

  DISPCNT = 0x1140;
  FUN_08000a74();
  FUN_08000ce4(1);
  DISPCNT = 0x404;
  FUN_08000dd0(&DAT_02009584,0x6000000,&DAT_030000dc);
  FUN_08000354(&DAT_030000dc,0x3c);
  uVar4 = DAT_030004d8;
```

Знайдено такий код:

```c
  do {
    DAT_030004da = uVar4; //This is the last key pressed
    DAT_030004d8 = KEYINPUT | 0xfc00;
    puVar6 = &DAT_0200b03c;
    uVar4 = DAT_030004d8;
    do {
      uVar2 = DAT_030004dc;
      uVar1 = *puVar6;
      if ((uVar1 & DAT_030004da & ~uVar4) != 0) {
```

Останній if перевіряє, чи міститься **`uVar4`** у попередньому наборі Keys і чи не є він поточною клавішею. Це також називають відпусканням кнопки (поточна клавіша зберігається в **`uVar1`**).

```c
        if (uVar1 == 4) {
          DAT_030000d4 = 0;
          uVar3 = FUN_08001c24(DAT_030004dc);
          FUN_08001868(uVar2,0,uVar3);
          DAT_05000000 = 0x1483;
          FUN_08001844(&DAT_0200ba18);
          FUN_08001844(&DAT_0200ba20,&DAT_0200ba40);
          DAT_030000d8 = 0;
          uVar4 = DAT_030004d8;
        }
        else {
          if (uVar1 == 8) {
            if (DAT_030000d8 == 0xf3) {
              DISPCNT = 0x404;
              FUN_08000dd0(&DAT_02008aac,0x6000000,&DAT_030000dc);
              FUN_08000354(&DAT_030000dc,0x3c);
              uVar4 = DAT_030004d8;
            }
          }
          else {
            if (DAT_030000d4 < 8) {
              DAT_030000d4 = DAT_030000d4 + 1;
              FUN_08000864();
              if (uVar1 == 0x10) {
                DAT_030000d8 = DAT_030000d8 + 0x3a;
```

У попередньому коді видно, що ми порівнюємо **uVar1** (місце, де зберігається **значення натиснутої кнопки**) з деякими значеннями:

- Спочатку його порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран.
- Потім значення порівнюють із **8** (кнопка **START**); у цьому завданні цей шлях перевіряє, чи правильний введений код.
  - У цьому випадку змінну **`DAT_030000d8`** порівнюють із 0xf3, і якщо значення збігається, виконується певний код.
- В усіх інших випадках перевіряється та збільшується лічильник (`DAT_030000d4`).\
  Поки значення лічильника менше за 8, значення натиснутих клавіш додаються до `DAT_030000d8`.

Отже, у цьому завданні, знаючи значення кнопок, потрібно було **натиснути комбінацію довжиною меншою за 8, сума значень якої дорівнює 0xf3.**
