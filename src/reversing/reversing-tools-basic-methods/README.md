## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) і **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Це корисно, коли потрібно відновити втрачений вихідний код зі застарілої збірки — такий підхід заощаджує час. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin.**

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки широким можливостям розширення та API, що дає змогу налаштувати інструмент відповідно до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості reverse engineering, які надає цей інструмент:

- Показує, як дані проходять через бібліотеку або компонент
- Показує реалізацію та використання мов і фреймворків .NET
- Допомагає знаходити недокументовані й недоступні функції, щоб ефективніше використовувати API та технології.
- Виявляє залежності та різні збірки
- Допомагає точно визначити розташування помилок у вашому коді, сторонніх компонентах і бібліотеках.
- Дає змогу налагоджувати вихідний код усього коду .NET, з яким ви працюєте.

### [ILSpy](https://github.com/icsharpcode/ILSpy) та [dnSpy](https://github.com/dnSpy/dnSpy/releases)

[Плагін ILSpy для Visual Studio Code](https://github.com/icsharpcode/ilspy-vscode): його можна використовувати в будь-якій ОС (можна встановити безпосередньо з VSCode — завантажувати git не потрібно. Натисніть **Extensions** і **знайдіть ILSpy**).\
Якщо потрібно **декомпілювати**, **змінити** й знову **скомпілювати**, можна скористатися [**dnSpy**](https://github.com/dnSpy/dnSpy/releases) або його активно підтримуваним форком [**dnSpyEx**](https://github.com/dnSpyEx/dnSpy/releases). (**Клацніть правою кнопкою миші -> Modify Method**, щоб змінити щось усередині функції).

### Перевірка керованих збірок без виконання за допомогою REA

**REA** може перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Спершу визначте ідентичність артефакту, а потім перевірте його члени та оголошені межі native-коду; це зручно під час аналізу підозрілих викликів, перш ніж використовувати декомпілятор або запускати програму.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує ідентичність на основі сирих CIL/сигнатур і відбитки декодованих інструкцій, а не вважає токени метаданих стабільними між збірками. Оголошення P/Invoke не доводить, що виконувався native code; `verify_managed_native_boundaries` потрібні відповідний native export або function Evidence, щоб перевірити цю межу. Зберігайте разом із результатом digest артефакту, MVID і нерозв’язані зіставлення.<sup>[[17]](#references)</sup>

## Налагодження DLL

### За допомогою IDA

- **Завантажте rundll32** (64-бітну версію — C:\Windows\System32\rundll32.exe, 32-бітну — C:\Windows\SysWOW64\rundll32.exe)
- Виберіть налагоджувач **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Debugging DLLs - Using IDA: Виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** виконання, вказавши **шлях до DLL** і функцію, яку потрібно викликати:

![Debugging DLLs - Using IDA: Налаштуйте параметри виконання, вказавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку налагодження **виконання зупинятиметься під час завантаження кожної DLL**. Тож коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей спосіб зупиняє виконання під час подій завантаження модулів, але дістатися точки входу завантаженої DLL менш просто, ніж у наведеному нижче сценарії з x64dbg.

### За допомогою x64dbg/x32dbg

- **Завантажте rundll32** (64-бітну версію — C:\Windows\System32\rundll32.exe, 32-бітну — C:\Windows\SysWOW64\rundll32.exe)
- **Змініть командний рядок** ( _File --> Change Command Line_ ) і вкажіть шлях до DLL та функцію, яку потрібно викликати, наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- Відкрийте _Options --> Settings_ і виберіть "**DLL Entry**".
- Потім **запустіть виконання**. Налагоджувач зупинятиметься в точці входу кожної DLL; зрештою ви **зупинитеся в точці входу своєї DLL**. Звідти просто знайдіть місця, де потрібно встановити breakpoint.

Зверніть увагу: коли виконання зупинено з будь-якої причини у win64dbg, можна побачити, **у якому коді ви перебуваєте**, подивившись **у верхню частину вікна win64dbg**:

![Using IDA - Using x64dbg/x32dbg: Зверніть увагу: коли виконання зупинено з будь-якої причини у win64dbg, можна побачити, у якому коді ви перебуваєте, подивившись у верхню частину вікна win64dbg](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку ви хочете налагодити.

## Дослідження native-коду на основі доказів за допомогою REA

**REA** надає доступ до аналізу Hopper, Ghidra та IDA через CLI і MCP. Для роботи потрібні Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спершу налаштуйте наявний native-провайдер; виконайте `rea providers --json` і явно виберіть провайдера, якщо ціль підтримують кілька. Замість `0x1000` нижче використайте назву функції або адресу, отриману з інвентаризації.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка ознаки або символу, переходьте за посиланнями та викликами, а потім перегляньте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сеанс до вибраного провайдера, а не перемикається на інший після збою без попередження. Для повторюваних запитів `--snapshot PATH` повторно використовує лише відповідні байти артефакту, провайдера, налаштування, операцію та параметри; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте отримані Evidence та явні невідомі дані, а не сприймайте виведені шляхи чи текст декомпілятора як оригінальний вихідний код.<sup>[[16]](#references)[[18]](#references)</sup>

Для точок входу JavaScript/Electron, що ведуть до native add-ons, див. [Electron Desktop Apps](../../network-services-pentesting/pentesting-web/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

### Деобфускація shellcode та отримання виконаних функцій

Спробуйте [**scdbg**](http://sandsprite.com/blogs/index.php?uid=7&pid=152).\
Він повідомить, зокрема, **які функції** використовує shellcode та чи **декодує** він себе в пам’яті.

```bash
scdbg.exe -f shellcode # Get info
scdbg.exe -f shellcode -r #show analysis report at end of run
scdbg.exe -f shellcode -i -r #enable interactive hooks (file and network) and show analysis report at end of run
scdbg.exe -f shellcode -d #Dump decoded shellcode
scdbg.exe -f shellcode /findsc #Find offset where starts
scdbg.exe -f shellcode /foff 0x0000004D #Start the executing in that offset
```

scDbg також має графічний лаунчер, у якому можна вибрати потрібні параметри й виконати shellcode

![Графічний лаунчер scDbg для вибору параметрів емуляції та трасування shellcode](<../../images/image (258).png>)

Параметр **Create Dump** створить дамп кінцевого shellcode, якщо його було змінено динамічно в пам’яті (корисно для завантаження декодованого shellcode). Параметр **start offset** може бути корисним, щоб запустити shellcode з певного зміщення. Параметр **Debug Shell** дає змогу налагоджувати shellcode за допомогою термінала scDbg (однак, на мою думку, будь-який із раніше пояснених варіантів для цього кращий, оскільки ви зможете використовувати Ida або x64dbg).

## Деобфускація MBA-обфускації

Обфускація **Mixed Boolean-Arithmetic (MBA)** приховує прості вирази, як-от `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай правильні лише за **модульної арифметики з фіксованою шириною**, тому переноси й переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити такий вираз за допомогою універсальних алгебраїчних інструментів, можна легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Збережіть початкову розрядність** з lifted-коду/IR/виводу декомпілятора (`8/16/32/64` біти).
2. **Класифікуйте вираз**, перш ніж намагатися його спростити:
   - **Лінійний**: зважені суми побітових атомів
   - **Напівлінійний**: лінійний вираз із константними масками, наприклад `x & 0xFF`
   - **Поліноміальний**: містить добутки
   - **Змішаний**: добутки й побітова логіка переплетені, часто з повторюваними підвиразами
3. **Перевірте кожне можливе перетворення** за допомогою випадкового тестування або SMT-доказу. Якщо еквівалентність неможливо довести, залиште початковий вираз замість того, щоб вгадувати.

### Обійдіть сплощений потік керування за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності control-flow flattening, непрозорих предикатів, великих диспетчерів або коду з великою кількістю MBA, прослідкуйте посилання від зашифрованих блоків даних і вихідних буферів до найменшої функції, яка їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не потрібен для розв’язання задачі, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Складіть перелік виконуваних і даних секцій, релокацій і перехресних посилань. Вивантажте потенційні таблиці з `.rodata`, зберігши порядок байтів і ширину елементів.
2. Визначте останню функцію, яка записує відкритий текст або вихідний буфер. Зафіксуйте її вхідні дані, таблиці, на які вона посилається, імпортовані виклики та потрібний глобальний стан.
3. Перенесіть лише ці операції в модель Python із фіксованою розрядністю. Якщо зріз усе ще залежить від надмірної кількості стану, викличте функцію в Unicorn, QEMU або налагоджувачі й перехоплюйте непотрібні імпортовані виклики замість емуляції всієї програми.
4. Переконайтеся, що екстрактор справді отримує результат із переданого бінарного файла: приберіть непомітні резервні механізми, перевірте його на наявність вбудованих відповідей і протестуйте на незнайомих збірках зі зміненими рядками, ключами, ідентифікаторами, структурами даних і seed-значеннями обфускації.

Корисні команди для первинного аналізу:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення MBA-виразів, замаскованих під константи

На перший погляд, байтовий вираз може залежати від вхідних даних, але повністю нівелювати їхній вплив. Після вилучення таблиць обчисліть вираз для всього 8-бітного домену; одноелементна множина вихідних значень доводить, що цей байт є константою, без відновлення навколишнього автомата станів.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Залиште фінальну маску, оскільки під час початкового додавання відбувається переповнення з циклічним переходом через межу розрядності байта. Для ширшої області значень запитайте SMT solver, чи є формула `f(x1) != f(x2)` для двох символьних входів однакової розрядності задовільною: `unsat` доводить інваріантність, тоді як `sat` надає контрприклад і означає, що вхід не можна відкидати.<sup>[[7]](#references)</sup>

#### Розпізнавання декодування, залежного від середовища

Перевірки на протидію аналізу не обов’язково мають спричиняти перехід або аварійне завершення. Декодер може домішати результат датчика до біта ключа, константи opaque predicate або стану сплощеного диспетчера, продовжити роботу у звичайному режимі й видати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо виправити лише видимі гілки помилок: відстежуйте залежності даних від перевірок середовища до стану декодера, порівнюйте той самий фрагмент на справжньому пристрої та в емуляторі, а також перевіряйте, як примусове встановлення кожного результату датчика змінює фінальний буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — це практичний спрощувач MBA для аналізу malware та реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його до спеціалізованих конвеєрів замість того, щоб застосовувати один універсальний прохід переписування до всього.<sup>[[2]](#references)</sup>

Швидке використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, виводить сигнатуру та паралельно застосовує кілька методів відновлення, як-от pattern matching, перетворення в ANF і інтерполяцію коефіцієнтів.
- **Semilinear MBA**: атоми з constant mask перебудовуються за допомогою реконструкції з розбиттям на біти, щоб замасковані ділянки залишалися коректними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього співвідношення.

Приклад змішаної тотожності, яку часто варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна звести до:

```c
x * y
```

- Явно вказуйте `--bitwidth`, якщо вираз походить з арифметики з масками або вузьких регістрів.
- Якщо потрібен надійніший крок доведення, перегляньте нотатки про Z3 тут:

- CoBRA також постачається як **плагін LLVM pass** (`libCobraPass.so`), який стане в пригоді, якщо потрібно нормалізувати LLVM IR із великою кількістю MBA перед подальшими passes аналізу.

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не адресуються як вказівники на рядки з нульовим термінатором у стилі C. Поширений формат `rustc` — це **кортеж вказівника й довжини** в **`.data.rel.ro`**, який вказує на справжній блок рядків у **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднувати суміжні рядки або зовсім не знаходити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Перелічіть **`.data.rel.ro`** слово за словом.
3. Вважайте будь-яке значення в діапазоні адрес `.rodata` кандидатом на вказівник на рядок.
4. Вважайте наступне слово можливою довжиною.
5. Застосуйте фільтри перевірки (наприклад, залиште довжини від **4** до **100** байтів).
6. Прочитайте з `.rodata` рівно `length` байтів, а не скануйте до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно під час реверс-аналізу firmware, оскільки відновлені рядки Rust часто розкривають **HTTP-маршрути, назви RPC, повідомлення журналу, assertions, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra не знаходить ці рядки, запустіть кастомний скрипт/плагін, який застосовує ту саму евристику й створює дані рядків за зміщеннями `.rodata`, на які вони посилаються. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — хороші приклади для адаптації цієї ідеї до інших **розрядностей, порядку байтів і структур секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

### Відновлення назв Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує вилучення символів середовища виконання зі створенням чистих еталонних бінарних файлів і зіставленням графів потоку керування (CFG). Виконайте такі кроки:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спершу перевірте `BuildInfo` та вбудовані рядки версій. Якщо обфускатор їх видалив, порівняйте частини вбудованого середовища виконання Go з еталонними середовищами виконання різних версій. У тестах Volexity для розрізнення основних версій Go вистачало приблизно `2%` середовища виконання. Вважайте це емпіричною оптимізацією, а не універсальним порогом.<sup>[[13]](#references)</sup>
2. **Підготуйте відповідні еталонні бінарні файли.** Створіть чисті бінарні файли для визначеної версії Go, цільової архітектури та ймовірних бібліотек. Відповідність набору інструментів зменшує відмінності CFG, створені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє CFG функцій і видає нормалізовані оцінки від `0.0` до `1.0`. Зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Відповідності з високою впевненістю пов’язують функції з рандомізованими назвами з чистою реалізацією. Слабші відповідності все одно можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте та імпортуйте результати.** Перевірте запропоновані назви за зв’язками викликів, константами, рядками та побічними ефектами, а потім імпортуйте звіт JSON за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Установіть набір інструментів і запустіть комбінований засіб вилучення та зіставлення графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Порогове значення значущого збігу за замовчуванням — `0.9`. Параметри `--extract` і `--graph` дають змогу окремо виконати будь-який із етапів, тоді як за замовчуванням запускаються обидва, оскільки відновлені метадані runtime та свідчення з CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнінг, прапорці збірки, архітектура та відмінності версій бібліотек можуть змінити структуру графа, тому залишайте нерозпізнані функції без змін, а не присвоюйте їм назви з низьким рівнем упевненості.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків з усіх пов’язаних пакетів в одній суцільній таблиці. Записи не завершуються NUL-байтом, а структури runtime не містять адреси початку чи розміру таблиці. Однак компілятор упорядковує записи спочатку за довжиною, а потім за абеткою — незалежно від операційної системи й архітектури. Отже, знайшовши один запис, аналітик може пройти сусідні записи та використати перехресні посилання на дані, щоб зіставити рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro та Ghidra. Спершу дочекайтеся завершення автоматичного аналізу, оскільки плагін спирається на перехресні посилання в сегментах даних. За замовчуванням як опорний рядок використовується рядок runtime `entersyscall`; після цього плагін може сканувати таблицю в обох напрямках, визначати відновлені рядки в базі даних і експортувати JSON-відповідність рядків функціям, які на них посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, яка посилається на рядок, щоб відокремити код програми чи шкідливого ПЗ від зайвих даних пов’язаних бібліотек. Цей метод не може відновити літерали, знищені обфускацією, наприклад перетворенням Garble `-literals`. Водночас він допоможе впорядкувати рядки runtime, що залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів Go runtime

Go вбудовує інформацію про типи runtime, яку використовують такі функції, як збірка сміття. Якщо інформацію про збірку видалено або дизасемблер не розбирає ці метадані, може здаватися, що інструкції завантажують довільні адреси даних, а цільова область залишається без типів. Відновлення метаданих перетворює ці адреси на зрозумілі посилання на типи й полегшує розуміння можливостей пакета.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи й розбирати типи runtime, формуючи звіт у форматі JSON. У поточному CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Опція `-y`/`--types` вмикає розбір типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи та застосувати посилання на них у базі даних аналізу. У форматі звіту, запровадженому разом із цією функцією, якщо не вказати `-y`, поля адреси RTTI та відновлених типів матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM і ARM64, тож цей самий процес підходить для бінарних файлів Go з Windows, Linux і macOS.<sup>[[10]](#references)</sup>

## GBA - Game Boy Advance

Якщо у вас є **бінарний файл** гри для GBA, можна скористатися різними інструментами для її **емуляції** та **налагодження**:

- [**no$gba**](https://problemkaputt.de/gba.htm) (_Завантажте версію для налагодження_) - Містить налагоджувач із графічним інтерфейсом
- [**mgba** ](https://mgba.io)- Містить налагоджувач CLI
- [**gba-ghidra-loader**](https://github.com/pudii/gba-ghidra-loader) - Плагін Ghidra
- [**GhidraGBA**](https://github.com/SiD3W4y/GhidraGBA) - Плагін Ghidra

У [**no$gba**](https://problemkaputt.de/gba.htm), у розділі _**Options --> Emulation Setup --> Controls**_** ** можна побачити, як натискати **кнопки** Game Boy Advance

![Налаштування керування no$gba з розкладкою кнопок Game Boy Advance](<../../images/image (581).png>)

Після натискання кожна **клавіша має значення**, за яким її можна визначити:

```
A = 1
B = 2
SELECT = 4
START = 8
RIGHT = 16
LEFT = 32
UP = 64
DOWN = 128
R = 256
L = 256
```

Отже, у програмі такого типу цікаво буде **як програма обробляє введені користувачем дані**. За адресою **0x4000130** ви знайдете часто використовувану функцію: **KEYINPUT**.

![Вигляд Ghidra, що показує посилання на KEYINPUT за адресою 0x4000130 у бінарному файлі GBA](<../../images/image (447).png>)

На попередньому зображенні видно, що функцію викликає **FUN_080015a8** (адреси: _0x080015fa_ і _0x080017ac_).

У цій функції після деяких початкових операцій (які не мають значення):

```c
void FUN_080015a8(void)

{
  ushort uVar1;
  undefined4 uVar2;
  undefined4 uVar3;
  ushort uVar4;
  int iVar5;
  ushort *puVar6;
  undefined *local_2c;

  DISPCNT = 0x1140;
  FUN_08000a74();
  FUN_08000ce4(1);
  DISPCNT = 0x404;
  FUN_08000dd0(&DAT_02009584,0x6000000,&DAT_030000dc);
  FUN_08000354(&DAT_030000dc,0x3c);
  uVar4 = DAT_030004d8;
```

Знайдено такий код:

```c
  do {
    DAT_030004da = uVar4; //This is the last key pressed
    DAT_030004d8 = KEYINPUT | 0xfc00;
    puVar6 = &DAT_0200b03c;
    uVar4 = DAT_030004d8;
    do {
      uVar2 = DAT_030004dc;
      uVar1 = *puVar6;
      if ((uVar1 & DAT_030004da & ~uVar4) != 0) {
```

Останній if перевіряє, чи **uVar4** є серед **останніх клавіш** і не є поточною клавішею — тобто чи кнопку відпущено (поточна клавіша зберігається в **uVar1**).

```c
        if (uVar1 == 4) {
          DAT_030000d4 = 0;
          uVar3 = FUN_08001c24(DAT_030004dc);
          FUN_08001868(uVar2,0,uVar3);
          DAT_05000000 = 0x1483;
          FUN_08001844(&DAT_0200ba18);
          FUN_08001844(&DAT_0200ba20,&DAT_0200ba40);
          DAT_030000d8 = 0;
          uVar4 = DAT_030004d8;
        }
        else {
          if (uVar1 == 8) {
            if (DAT_030000d8 == 0xf3) {
              DISPCNT = 0x404;
              FUN_08000dd0(&DAT_02008aac,0x6000000,&DAT_030000dc);
              FUN_08000354(&DAT_030000dc,0x3c);
              uVar4 = DAT_030004d8;
            }
          }
          else {
            if (DAT_030000d4 < 8) {
              DAT_030000d4 = DAT_030000d4 + 1;
              FUN_08000864();
              if (uVar1 == 0x10) {
                DAT_030000d8 = DAT_030000d8 + 0x3a;
```

У попередньому коді можна побачити, що ми порівнюємо **uVar1** (місце, де зберігається **значення натиснутої кнопки**) з деякими значеннями:

- Спочатку його порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран.
- Потім значення порівнюють із **8** (кнопка **START**); у цьому завданні цей шлях перевіряє, чи введений код дійсний.
  - У цьому випадку змінну **`DAT_030000d8`** порівнюють із 0xf3, і якщо значення збігається, виконується певний код.
- В усіх інших випадках перевіряється й збільшується лічильник (`DAT_030000d4`).\
  Поки лічильник менший за 8, значення натиснутих клавіш додаються до `DAT_030000d8`.

Отже, у цьому завданні, знаючи значення кнопок, потрібно було **натиснути комбінацію довжиною менш як 8, сума значень якої дорівнює 0xf3.**
