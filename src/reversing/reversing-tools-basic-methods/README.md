## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) та **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Це корисно, якщо потрібно відновити втрачений вихідний код із застарілої збірки, адже це може заощадити час. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin.**

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки широким можливостям розширення та API, що дає змогу налаштувати інструмент відповідно до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості реверсингу, які надає цей інструмент:

- Показує, як дані проходять через бібліотеку або компонент
- Дає змогу дослідити реалізацію та використання мов і фреймворків .NET
- Знаходить недокументовані та недоступні функції, щоб отримати більше від API і використовуваних технологій
- Виявляє залежності та різні збірки
- Знаходить точне розташування помилок у вашому коді, сторонніх компонентах і бібліотеках
- Дає змогу налагоджувати вихідний код усього коду .NET, з яким ви працюєте

### [ILSpy](https://github.com/icsharpcode/ILSpy) та [dnSpy](https://github.com/dnSpy/dnSpy/releases)

[Плагін ILSpy для Visual Studio Code](https://github.com/icsharpcode/ilspy-vscode): його можна використовувати в будь-якій ОС (його можна встановити безпосередньо з VSCode, завантажувати git не потрібно. Натисніть **Extensions** і знайдіть **ILSpy**).\
Якщо потрібно **декомпілювати**, **змінити** та знову **скомпілювати**, скористайтеся [**dnSpy**](https://github.com/dnSpy/dnSpy/releases) або його активно підтримуваним форком [**dnSpyEx**](https://github.com/dnSpyEx/dnSpy/releases). (**Клацніть правою кнопкою миші -> Modify Method**, щоб змінити щось усередині функції).

### Перевірка керованих збірок без виконання за допомогою REA

**REA** дає змогу перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Почніть з ідентифікації артефакту, а потім перегляньте його члени та оголошені межі нативного коду. Це корисно під час аналізу підозрілих викликів перед використанням декомпілятора або запуском програми.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує ідентичність на основі необробленого CIL/сигнатури та відбитки декодованих інструкцій, а не вважає токени метаданих стабільними між збірками. Оголошення P/Invoke не доводить, що виконувався native-код; `verify_managed_native_boundaries` потрібні відповідний native export або Evidence функції, щоб перевірити цю межу. Збережіть разом із результатом digest артефакту, MVID і невирішені зіставлення.<sup>[[17]](#references)</sup>

## Налагодження DLL

### Використання IDA

- **Завантажте rundll32** (64-бітну версію: C:\Windows\System32\rundll32.exe, 32-бітну: C:\Windows\SysWOW64\rundll32.exe)
- Виберіть налагоджувач **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Debugging DLLs - Using IDA: Виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** запуску, указавши **шлях до DLL** і функцію, яку потрібно викликати:

![Debugging DLLs - Using IDA: Налаштуйте параметри запуску, указавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку налагодження **виконання зупинятиметься під час завантаження кожної DLL**. Тож, коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей спосіб зупиняє виконання під час подій завантаження модуля, але перехід до точки входу завантаженої DLL менш прямолінійний, ніж у наведеному нижче сценарії з x64dbg.

### Використання x64dbg/x32dbg

- **Завантажте rundll32** (64-бітну версію: C:\Windows\System32\rundll32.exe, 32-бітну: C:\Windows\SysWOW64\rundll32.exe)
- **Змініть командний рядок** ( _File --> Change Command Line_ ) і вкажіть шлях до DLL та функцію, яку потрібно викликати. Наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- У _Options --> Settings_ виберіть "**DLL Entry**".
- Потім **запустіть виконання**. Налагоджувач зупинятиметься на точці входу кожної DLL; зрештою ви **зупинитеся на точці входу своєї DLL**. Звідти знайдіть місця, де потрібно встановити breakpoint.

Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, **у верхній частині вікна win64dbg** можна побачити, **у якому коді ви перебуваєте**:

![Using IDA - Using x64dbg/x32dbg: Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, у верхній частині вікна win64dbg можна побачити, у якому коді ви перебуваєте](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку ви хочете налагодити.

## Дослідження native-коду на основі доказів за допомогою REA

**REA** надає доступ до аналізу в Hopper, Ghidra та IDA через CLI і MCP. Для його роботи потрібен Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спочатку налаштуйте наявний native provider; перевірте `rea providers --json` і явно виберіть provider, якщо ціль підтримують кілька. Замість `0x1000` нижче вкажіть спостережене ім’я функції або адресу з переліку.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка ознаки або символу, переходьте за посиланнями та викликами, а потім перегляньте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сесію до вибраного провайдера, а не замінює його непомітно після збою. Для повторюваних запитів `--snapshot PATH` повторно використовує лише байти артефактів, провайдера, налаштування, операцію та параметри, що збігаються; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте отриманий Evidence та явні невідомі значення, а не сприймайте виведені шляхи чи текст декомпілятора як оригінальний код.<sup>[[16]](#references)[[18]](#references)</sup>

Для точок входу JavaScript/Electron, що ведуть до нативних add-on, див. [Electron Desktop Apps](../../network-services-pentesting/pentesting-web/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

## Скриптований аналіз IDA і Ghidra через локальний TCP-міст

[IDA-Ghidra-bridge](https://github.com/oscarsantanaarias/IDA-Ghidra-bridge) працює у **вже відкритій** базі даних IDA або програмі Ghidra CodeBrowser і дає змогу окремому скрипту запитувати та змінювати цю базу аналізу. Запустіть `ID_Server.py` з Python CLI IDA (`import ID_Server`) або `Ghidra_Server.py` з Script Manager Ghidra. IDA прив’язується до `127.0.0.1`, починаючи з порту `5073`, і перевіряє вищі порти. Поточний скрипт Ghidra починає з порту `5093` і пробує десять портів аж до `5102`; його Java-сокет прив’язується до адреси wildcard, а не лише до loopback. Перед підключенням перевірте порт, виведений екземпляром. На відміну від headless analyzer, цей міст працює з програмою, відкритою в поточному екземплярі GUI.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

Надсилайте **одну команду, завершену символом нового рядка, на кожне з’єднання** та зчитуйте відповідь, завершену символом нового рядка. Результат зазвичай має формат JSON. Наприклад, знайшовши імпортований API, пов’язаний зі шляхом до вхідних даних, `IMPORTXREF` знаходить місця його виклику; потім `DECOMP_XREF` пакетно декомпілює виклики вибраної адреси. `FUNC` перевіряє функцію, а `PCODE` повертає проміжне представлення декомпілятора. Використовуйте адресу з активної бази даних, а не адресу, скопійовану з бінарного файла з іншою базою переміщення. У прикладі нижче використовується порт IDA за замовчуванням; для Ghidra використовуйте порт, виведений її скриптом.<sup>[[21]](#references)[[22]](#references)[[23]](#references)</sup>

```python
import socket

with socket.create_connection(("127.0.0.1", 5073)) as sock:
    sock.sendall(b"IMPORTXREF memcpy\n")
    print(sock.makefile("r", encoding="utf-8").readline())
```

Той самий канал може **змінювати базу даних аналізу**: `RENAME_FUNC`, `RETYPE`, `SETCONV`, `DEFSTRUCT`/`SETFIELD`, `MAKEFUNC` і `PATCH` змінюють імена, типи, визначення структур, межі функцій або збережені байти. `PATCH` — це редагування бази даних, **а не** свідчення про патч у живому процесі. Жоден із listener-ів не документує автентифікацію. IDA доступна лише через loopback, але Ghidra може бути доступна через мережеві інтерфейси; під час використання Ghidra обмежте доступ до listener-а. `QUIT` зупиняє будь-який із listener-ів, а IDA також надає `ida_bridge_stop()`.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

## Деобфускація MBA obfuscation

**Mixed Boolean-Arithmetic (MBA)** obfuscation приховує прості вирази, такі як `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай правильні лише за **модульної арифметики фіксованої розрядності**, тому перенесення та переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити вираз такого типу за допомогою універсальних засобів алгебраїчних перетворень, легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Зберігайте початкову розрядність** із lifted-коду/виводу IR або декомпілятора (`8/16/32/64` бітів).
2. **Класифікуйте вираз** перед спробою його спростити:
   - **Лінійний**: зважені суми побітових атомів
   - **Напівлінійний**: лінійний вираз із константними масками, наприклад `x & 0xFF`
   - **Поліноміальний**: містить добутки
   - **Змішаний**: добутки та побітова логіка переплетені, часто з повторюваними підвиразами
3. **Перевіряйте кожне потенційне перетворення** випадковим тестуванням або SMT-доведенням. Якщо еквівалентність неможливо довести, залиште початковий вираз замість того, щоб вгадувати.

### Обійдіть сплющений потік керування за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності сплющення потоку керування, непрозорих предикатів, великих диспетчерів або коду з великою кількістю MBA перейдіть за посиланнями від зашифрованих блоків даних і вихідних буферів до найменшої процедури, яка їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не потрібен для розв’язання задачі, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Складіть перелік виконуваних і секцій даних, релокацій і перехресних посилань. Дампніть потенційні таблиці з `.rodata`, зберігаючи порядок байтів і ширину елементів.
2. Визначте останню процедуру, яка записує відкритий текст або вихідний буфер. Зафіксуйте її входи, таблиці, на які вона посилається, імпортовані виклики та необхідний глобальний стан.
3. Перенесіть лише ці операції у Python-модель із фіксованою розрядністю. Якщо зріз і далі залежить від надмірної кількості стану, викличте процедуру в Unicorn, QEMU або налагоджувачі та перехоплюйте нерелевантні імпортовані функції замість емуляції всієї програми.
4. Перевірте, що екстрактор справді отримує результат із наданого бінарного файла: приберіть приховані резервні варіанти, перевірте файл на наявність вбудованих відповідей і протестуйте екстрактор на невідомих збірках зі зміненими рядками, ключами, ідентифікаторами, структурами даних і seed-значеннями обфускації.

Для першого проходу стануть у пригоді такі команди:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення виразів MBA, що маскують константи

Здається, що вираз для байта залежить від вхідних даних, але він може повністю їх нівелювати. Після вилучення таблиць обчисліть вираз для всіх можливих 8-бітних значень; якщо множина результатів містить лише одне значення, це доводить, що байт є константою, і не потрібно відновлювати решту машини станів.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Залиште фінальну маску, оскільки під час початкового додавання відбувається циклічне переповнення розрядності байта. Для ширшої області значень запитайте SMT-солвер, чи є `f(x1) != f(x2)` задовільним для двох символічних вхідних значень однакової розрядності: `unsat` доводить інваріантність, а `sat` надає контрприклад і означає, що вхідні дані не можна відкинути.<sup>[[7]](#references)</sup>

#### Виявлення декодування, прив’язаного до середовища

Перевірки проти аналізу не обов’язково мають розгалужуватися чи спричиняти аварійне завершення. Декодер може змішати результат датчика з бітом ключа, константою opaque predicate або станом flattened-dispatcher, продовжити роботу у звичайному режимі й видати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо виправити лише видимі гілки помилок; простежте залежності даних від зондування середовища до стану декодера, порівняйте той самий фрагмент на автентичному пристрої та в емуляторі й перевірте, як примусова зміна результату кожного датчика змінює фінальний буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — це практичний спрощувач MBA для аналізу malware і реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його до спеціалізованих конвеєрів замість застосування одного універсального проходу переписування до всього.<sup>[[2]](#references)</sup>

Швидкий приклад використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, виводить сигнатуру та паралельно запускає кілька методів відновлення, як-от зіставлення шаблонів, перетворення ANF і інтерполяцію коефіцієнтів.
- **Semilinear MBA**: атоми з константною маскою відновлюються за допомогою реконструкції з розбиттям на біти, щоб замасковані ділянки залишалися правильними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього співвідношення.

Приклад змішаної тотожності, яку часто варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна згорнути до:

```c
x * y
```

- Явно вказуйте `--bitwidth`, якщо вираз отримано з masked arithmetic або вузьких регістрів.
- Якщо потрібен надійніший крок доведення, перегляньте локальні нотатки щодо Z3 тут:

## Відновлення XOR-state control-flow flattening

Обфускатор у стилі OLLVM може зберігати стан поточного basic block у двох 64-бітних регістрах і відновлювати його за допомогою XOR у dispatcher. Кожен початковий блок записує пару для наступного стану й переходить назад до dispatcher. Умовний блок може використовувати `CMOVcc`, щоб замінити одну половину пари відповідно до прапорців CPU, тому відстеження лише видимих інструкцій переходу призведе до пропуску двох наступників. На відміну від dispatcher з непрямим переходом, ця структура може використовувати прямі переходи назад на всіх ділянках.<sup>[[19]](#references)[[20]](#references)</sup>

Щоб відновити граф, визначте дерево порівнянь dispatcher і два регістри стану, зіставте кожен порівнюваний XOR-стан із цільовим блоком, а потім простежте записи в пару регістрів, що досягають кожного початкового блоку. Для умовних записів врахуйте інструкцію, що встановлює прапорці, та обидва результати `CMOVcc`. Замініть вихід dispatcher кожного блоку на визначений прямий перехід або умовну гілку; після цього dispatcher стане недосяжним без патчення бінарного файла. Це підхід на основі повного CFG; якщо важливий лише один decoder, наведений вище [вузький workflow зрізу виконання](#bypass-flattened-control-flow-with-a-narrow-execution-slice) може бути швидшим.<sup>[[19]](#references)[[20]](#references)</sup>

[DispatchThis](https://github.com/YungBinary/DispatchThis) автоматизує цю структуру в Binary Ninja. Скопіюйте `plugins/DispatchThis` до каталогу користувацьких плагінів Binary Ninja та перезапустіть програму. Для потрібної функції відкрийте **Function Settings** і виберіть `OLLVM_XOR_64`; якщо аналіз не запускається, скористайтеся **Analysis → Reanalyze All Functions**. Цей режим переписує ребра керування MLIL, а не байти файла, і не потребує Z3 або resolver для непрямих переходів. Він перевірений у Binary Ninja 5.3.9757+; він не видаляє мертві записи стану в кожному блоці, тому не сприймайте їх як досі активні переходи.<sup>[[19]](#references)</sup>

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не використовують вказівники на рядки з нульовим завершенням у стилі C. Типове розташування в `rustc` — це **кортеж вказівника/довжини** всередині **`.data.rel.ro`**, що вказує на фактичний блок рядка в **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднувати сусідні рядки або зовсім не знаходити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Переберіть **`.data.rel.ro`** по одному слову за раз.
3. Вважайте будь-яке значення в межах адресного діапазону `.rodata` кандидатом на вказівник на рядок.
4. Вважайте наступне слово кандидатною довжиною.
5. Застосуйте фільтри перевірки на правдоподібність (наприклад, залиште довжини від **4** до **100** байтів).
6. Прочитайте з `.rodata` рівно `length` байтів замість пошуку до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно під час реверсингу firmware, оскільки відновлені рядки Rust часто розкривають **HTTP-маршрути, назви RPC, повідомлення журналу, assertions, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra не знаходить ці рядки, запустіть власний скрипт/плагін, який застосовує ту саму евристику та створює дані рядків за відповідними зміщеннями `.rodata`. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — корисні приклади для адаптації цієї ідеї до інших **розмірів слова, порядку байтів і структур секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

### Відновлення метаданих без таблиці символів

Навіть stripped-виконуваний файл Go потребує метаданих runtime, щоб зіставляти лічильники команд із функціями. [GoReSym](https://github.com/mandiant/GoReSym) знаходить і розбирає такі структури, як `pclntab` і `moduledata`, використовуючи код, похідний від runtime Go. Це дає змогу відновити межі функцій, назви, шляхи до вихідних файлів, типи й відомості про збірку без використання стандартної таблиці символів.<sup>[[9]](#references)[[13]](#references)</sup>

```bash
GoReSym.exe -t -d -p /path/to/sample.exe > goresym.json
```

Обфускатор може залишити ці структури придатними до використання, замінивши відновлені імена. Наприклад, Garble хешує ідентифікатори та шляхи пакетів і видаляє інформацію про збірку, модулі й налагодження.<sup>[[12]](#references)</sup> Токен обфускованого пакета має бути однаковим у функціях цього пакета. Згрупуйте функції за повторюваним токеном, визначте пакет для однієї з них за її викликаними функціями, рядками й API, а потім поширте цю мітку пакета на всю групу.<sup>[[13]](#references)</sup>

### Відновлення імен Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує витягування символів runtime із генерацією чистих еталонів і зіставленням графів потоку керування (CFG). Дотримуйтеся такої послідовності:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спершу спробуйте `BuildInfo` та вбудовані рядки версії. Якщо обфускатор їх видалив, порівняйте частини вбудованого runtime Go з еталонними runtime відповідних версій. У тестах Volexity близько `2%` runtime було достатньо, щоб розрізнити основні версії Go. Сприймайте це як емпіричну оптимізацію, а не універсальний поріг.<sup>[[13]](#references)</sup>
2. **Створіть відповідні еталони.** Згенеруйте чисті бінарні файли для визначеної версії Go, цільової архітектури та ймовірних бібліотек. Відповідність набору інструментів зменшує відмінності CFG, створені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє CFG функцій і виводить нормалізовані оцінки від `0.0` до `1.0`. Зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Відповідності з високим рівнем упевненості дають змогу зіставити функції з рандомізованими іменами з чистою реалізацією. Слабші відповідності все одно можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте та імпортуйте.** Підтвердьте запропоновані імена за зв’язками викликів, константами, рядками й побічними ефектами, а потім імпортуйте звіт JSON за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Встановіть набір інструментів і запустіть комбінований екстрактор і зіставлювач графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Порогове значення значущого збігу за замовчуванням — `0.9`. Параметри `--extract` і `--graph` дають змогу окремо виконати кожен етап, тоді як за замовчуванням запускаються обидва, оскільки відновлені метадані runtime і дані CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнинг, прапорці збірки, архітектура та відмінності між версіями бібліотек можуть змінювати структуру графа, тому залишайте функції з невизначеними назвами, а не призначайте їм назви з низькою впевненістю.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків з усіх підключених пакетів в одній суцільній таблиці. Записи не завершуються NUL-символом, а структури runtime не містять базової адреси чи розміру таблиці. Однак компілятор упорядковує записи спочатку за довжиною, а потім за алфавітом — незалежно від операційної системи й архітектури. Отже, знайшовши один запис, аналітик може переглянути сусідні записи й використати перехресні посилання на дані, щоб пов’язати рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro і Ghidra. Спершу дочекайтеся завершення автоаналізу, оскільки плагін використовує перехресні посилання із сегментів даних. За замовчуванням як якір використовується рядок runtime `entersyscall`; після цього плагін сканує таблицю в обох напрямках, визначає відновлені рядки в базі даних і експортує JSON-відповідність рядків функціям, на які вони посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, на яку посилається рядок, щоб відокремити код застосунку чи шкідливого ПЗ від зайвих даних підключених бібліотек. Ця техніка не може відновити літерали, знищені обфускацією, наприклад перетворенням Garble `-literals`. Водночас вона дає змогу впорядкувати рядки runtime, які залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів runtime Go

Go вбудовує інформацію про типи runtime, яку використовують такі механізми, як збирач сміття. Якщо інформацію про збірку видалено або дизасемблер не розбирає ці метадані, може здаватися, що інструкції завантажують довільні адреси даних, а цільовий регіон залишається без типу. Відновлення метаданих перетворює ці адреси на читабельні посилання на типи й полегшує розуміння можливостей пакетів.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи й розбирати типи runtime у JSON-звіт. У поточному CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Опція `-y`/`--types` вмикає розбір типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи та застосувати їхні посилання в базі даних аналізу. У форматі звіту, запровадженому разом із цією функцією, якщо не вказати `-y`, поля адреси RTTI та відновлених типів матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM та ARM64, тож цей самий процес підходить для Go-бінарних файлів у Windows, Linux і macOS.<sup>[[10]](#references)</sup>

- [**mgba** ](https://mgba.io)- Має CLI-налагоджувач
- [**gba-ghidra-loader**](https://github.com/pudii/gba-ghidra-loader) - Плагін Ghidra
- [**GhidraGBA**](https://github.com/SiD3W4y/GhidraGBA) - Плагін Ghidra

У [**no$gba**](https://problemkaputt.de/gba.htm), у розділі _**Options --> Emulation Setup --> Controls**_** ** можна побачити, як натискати **кнопки** Game Boy Advance

![Конфігурація керування no$gba з відповідністю кнопок Game Boy Advance](<../../images/image (581).png>)

Після натискання кожна **клавіша має значення**, за яким її можна ідентифікувати:

```
A = 1
B = 2
SELECT = 4
START = 8
RIGHT = 16
LEFT = 32
UP = 64
DOWN = 128
R = 256
L = 256
```

Отже, у програмі такого типу найцікавіше — **як програма обробляє введені користувачем дані**. За адресою **0x4000130** ви знайдете поширену функцію: **KEYINPUT**.

![Вигляд Ghidra для бінарного файлу GBA із посиланням на KEYINPUT за адресою 0x4000130](<../../images/image (447).png>)

На попередньому зображенні видно, що функцію викликає **FUN_080015a8** (адреси: _0x080015fa_ та _0x080017ac_).

У цій функції, після кількох початкових операцій (які не мають значення):

```c
void FUN_080015a8(void)

{
  ushort uVar1;
  undefined4 uVar2;
  undefined4 uVar3;
  ushort uVar4;
  int iVar5;
  ushort *puVar6;
  undefined *local_2c;

  DISPCNT = 0x1140;
  FUN_08000a74();
  FUN_08000ce4(1);
  DISPCNT = 0x404;
  FUN_08000dd0(&DAT_02009584,0x6000000,&DAT_030000dc);
  FUN_08000354(&DAT_030000dc,0x3c);
  uVar4 = DAT_030004d8;
```

Знайдено такий код:

```c
  do {
    DAT_030004da = uVar4; //This is the last key pressed
    DAT_030004d8 = KEYINPUT | 0xfc00;
    puVar6 = &DAT_0200b03c;
    uVar4 = DAT_030004d8;
    do {
      uVar2 = DAT_030004dc;
      uVar1 = *puVar6;
      if ((uVar1 & DAT_030004da & ~uVar4) != 0) {
```

Остання умова if перевіряє, чи **`uVar4`** є серед **останніх натиснутих клавіш** і не є поточною клавішею — це також називають відпусканням кнопки (поточна клавіша зберігається в **`uVar1`**).

```c
        if (uVar1 == 4) {
          DAT_030000d4 = 0;
          uVar3 = FUN_08001c24(DAT_030004dc);
          FUN_08001868(uVar2,0,uVar3);
          DAT_05000000 = 0x1483;
          FUN_08001844(&DAT_0200ba18);
          FUN_08001844(&DAT_0200ba20,&DAT_0200ba40);
          DAT_030000d8 = 0;
          uVar4 = DAT_030004d8;
        }
        else {
          if (uVar1 == 8) {
            if (DAT_030000d8 == 0xf3) {
              DISPCNT = 0x404;
              FUN_08000dd0(&DAT_02008aac,0x6000000,&DAT_030000dc);
              FUN_08000354(&DAT_030000dc,0x3c);
              uVar4 = DAT_030004d8;
            }
          }
          else {
            if (DAT_030000d4 < 8) {
              DAT_030000d4 = DAT_030000d4 + 1;
              FUN_08000864();
              if (uVar1 == 0x10) {
                DAT_030000d8 = DAT_030000d8 + 0x3a;
```

У попередньому коді видно, що ми порівнюємо **uVar1** (змінну, у якій зберігається **значення натиснутої кнопки**) з певними значеннями:

- Спочатку її порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран.
- Потім значення порівнюють із **8** (кнопка **START**); у цьому завданні цей шлях перевіряє, чи є введений код дійсним.
  - У цьому випадку змінну **`DAT_030000d8`** порівнюють із 0xf3, і якщо значення збігаються, виконується певний код.
- В усіх інших випадках перевіряють і збільшують лічильник (`DAT_030000d4`).\
  Поки лічильник менший за 8, значення натиснутих клавіш накопичуються в `DAT_030000d8`.

Отже, у цьому завданні, знаючи значення кнопок, потрібно було **натиснути комбінацію довжиною меншою за 8, сума значень якої дорівнює 0xf3.**
