## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) і **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Цей інструмент корисний, якщо потрібно відновити втрачений вихідний код із застарілої збірки, адже це заощаджує час. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin.**

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки широким можливостям додавання плагінів і API, що дає змогу адаптувати інструмент до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості зворотного інжинірингу, які надає цей інструмент:

- Показує, як дані проходять через бібліотеку або компонент
- Допомагає зрозуміти реалізацію та використання мов і фреймворків .NET
- Допомагає знаходити недокументовані та недоступні функції, щоб ефективніше використовувати API й технології.
- Знаходить залежності та різні збірки
- Допомагає точно визначити місце помилок у вашому коді, сторонніх компонентах і бібліотеках.
- Дає змогу налагоджувати вихідний код усіх .NET-програм, з якими ви працюєте.

### [ILSpy](https://github.com/icsharpcode/ILSpy) і [dnSpy](https://github.com/dnSpy/dnSpy/releases)

[Плагін ILSpy для Visual Studio Code](https://github.com/icsharpcode/ilspy-vscode): його можна використовувати в будь-якій ОС (можна встановити безпосередньо з VSCode, git завантажувати не потрібно. Натисніть **Extensions** і **знайдіть ILSpy**).\
Якщо потрібно **декомпілювати**, **змінити** та знову **скомпілювати**, можна скористатися [**dnSpy**](https://github.com/dnSpy/dnSpy/releases) або його активно підтримуваним форком [**dnSpyEx**](https://github.com/dnSpyEx/dnSpy/releases). (**Клацніть правою кнопкою миші -> Modify Method**, щоб змінити код функції).

### Перевірка керованого коду без виконання за допомогою REA

**REA** може перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Спочатку визначте ідентичність артефакту, а потім перегляньте його члени та оголошені межі native-коду; це корисно під час аналізу підозрілих викликів перед використанням декомпілятора або запуском програми.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує raw CIL/signature identity та fingerprints декодованих інструкцій, а не вважає metadata tokens стабільними між збірками. Оголошення P/Invoke не є доказом виконання native code; `verify_managed_native_boundaries` потребує відповідного native export або function Evidence, щоб перевірити цю межу. Збережіть digest артефакту, MVID і нерозв’язані mappings разом із результатом.<sup>[[17]](#references)</sup>

## Налагодження DLL

### За допомогою IDA

- **Завантажте rundll32** (64-бітна версія: C:\Windows\System32\rundll32.exe, 32-бітна: C:\Windows\SysWOW64\rundll32.exe)
- Виберіть debugger **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Debugging DLLs - Using IDA: Виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** виконання, вказавши **шлях до DLL** і функцію, яку потрібно викликати:

![Debugging DLLs - Using IDA: Налаштуйте параметри виконання, вказавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку debugging **виконання зупинятиметься під час завантаження кожної DLL**. Тобто, коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей метод зупиняє виконання під час подій завантаження модуля, але дістатися до точки входу завантаженої DLL менш просто, ніж за допомогою робочого процесу x64dbg нижче.

### За допомогою x64dbg/x32dbg

- **Завантажте rundll32** (64-бітна версія: C:\Windows\System32\rundll32.exe, 32-бітна: C:\Windows\SysWOW64\rundll32.exe)
- **Змініть Command Line** ( _File --> Change Command Line_ ) і вкажіть шлях до dll та функцію, яку потрібно викликати, наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- Змініть _Options --> Settings_ і виберіть "**DLL Entry**".
- Потім **почніть виконання**. Debugger зупинятиметься під час входу в кожну dll main; у певний момент ви **зупинитеся на точці входу своєї dll**. Звідти знайдіть місця, де потрібно встановити breakpoint.

Зауважте: коли виконання зупинено з будь-якої причини у win64dbg, **у верхній частині вікна win64dbg** можна побачити, **у якому коді ви перебуваєте**:

![Using IDA - Using x64dbg/x32dbg: Зауважте: коли виконання зупинено з будь-якої причини у win64dbg, у верхній частині вікна win64dbg можна побачити, у якому коді ви перебуваєте](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку ви хочете налагодити.

## Дослідження нативного коду з підтвердженням доказами за допомогою REA

**REA** надає доступ до аналізу Hopper, Ghidra та IDA через CLI і MCP. Для роботи потрібні Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спершу налаштуйте наявний native provider; виконайте `rea providers --json` і явно виберіть provider, якщо ціль підтримує кілька з них. Замість `0x1000` нижче використайте назву функції або адресу, знайдену в інвентарі.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка функції або символу, переходьте за посиланнями та викликами, а потім перегляньте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сеанс до вибраного провайдера, а не мовчки замінює його після збою. Для повторюваних запитів `--snapshot PATH` повторно використовує лише відповідні байти артефакту, провайдера, налаштування, операцію та параметри; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте повернуті Evidence та явні невідомі дані, а не сприймайте виведені шляхи чи текст декомпілятора як оригінальний код.<sup>[[16]](#references)[[18]](#references)</sup>

Щодо точок входу JavaScript/Electron, які ведуть до нативних add-ons, див. [Electron Desktop Apps](../../network-services-pentesting/pentesting-web/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

### Деобфускація shellcode та отримання виконуваних функцій

Спробуйте [**scdbg**](http://sandsprite.com/blogs/index.php?uid=7&pid=152).\
Він покаже, наприклад, **які функції** використовує shellcode і чи **декодує** він себе в пам’яті.

```bash
scdbg.exe -f shellcode # Get info
scdbg.exe -f shellcode -r #show analysis report at end of run
scdbg.exe -f shellcode -i -r #enable interactive hooks (file and network) and show analysis report at end of run
scdbg.exe -f shellcode -d #Dump decoded shellcode
scdbg.exe -f shellcode /findsc #Find offset where starts
scdbg.exe -f shellcode /foff 0x0000004D #Start the executing in that offset
```

scDbg також має графічний лаунчер, де можна вибрати потрібні параметри та виконати shellcode

![Графічний лаунчер scDbg для вибору параметрів емуляції та трасування shellcode](<../../images/image (258).png>)

Опція **Create Dump** створить дамп фінального shellcode, якщо під час виконання його було змінено безпосередньо в пам’яті (це корисно, щоб отримати декодований shellcode). **start offset** може стати в пригоді, щоб запустити shellcode з певного зміщення. Опція **Debug Shell** корисна для налагодження shellcode через термінал scDbg (однак для цього, на мою думку, краще підходять будь-які з описаних вище варіантів, оскільки можна буде використовувати Ida або x64dbg).

## Деобфускація MBA-обфускації

**Mixed Boolean-Arithmetic (MBA)**-обфускація приховує прості вирази, як-от `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай правильні лише за **арифметики за модулем фіксованої розрядності**, тому переноси й переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити такий вираз за допомогою універсальних засобів алгебраїчних перетворень, легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Зберігайте початкову розрядність** із lifted-коду/IR/виводу decompiler (`8/16/32/64` біти).
2. **Класифікуйте вираз**, перш ніж намагатися його спростити:
   - **Лінійний**: зважені суми побітових атомів
   - **Напівлінійний**: лінійний вираз плюс сталі маски, як-от `x & 0xFF`
   - **Поліноміальний**: містить добутки
   - **Змішаний**: добутки й побітова логіка чергуються, часто з повторюваними підвиразами
3. **Перевіряйте кожне можливе перетворення** за допомогою випадкового тестування або SMT-доведення. Якщо еквівалентність неможливо довести, залиште початковий вираз, а не вгадуйте.

### Обхід розплющеного потоку керування за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності control-flow flattening, opaque predicates, великих диспетчерів або коду з інтенсивним використанням MBA простежте посилання від зашифрованих блоків даних і вихідних буферів до найменшої процедури, яка їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не потрібен для розв’язання задачі, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Перелічіть виконувані й інформаційні секції, релокації та перехресні посилання. Вивантажте потенційні таблиці з `.rodata`, зберігши порядок байтів і ширину елементів.
2. Знайдіть останню процедуру, що записує відкритий текст або вихідний буфер. Зафіксуйте її вхідні дані, таблиці, на які вона посилається, імпортовані виклики та потрібний глобальний стан.
3. Перенесіть лише ці операції у Python-модель із фіксованою розрядністю. Якщо зріз і далі залежить від надмірної кількості стану, викличте процедуру в Unicorn, QEMU або debugger і перехопіть непотрібні імпортовані функції замість емуляції всієї програми.
4. Переконайтеся, що екстрактор справді отримує результат із наданого бінарного файла: приберіть непомітні резервні механізми, перевірте файл на вбудовані відповіді й запустіть екстрактор на невідомих збірках зі зміненими рядками, ключами, ідентифікаторами, компонуванням і seeds обфускації.

Корисні команди для первинного аналізу:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення MBA-виразів, замаскованих під константи

На перший погляд, вираз для байта може залежати від вхідних даних, але насправді повністю їх нівелювати. Після вилучення таблиць обчисліть вираз для всього 8-бітного діапазону; якщо множина результатів містить лише одне значення, це доводить, що байт є константою, і відновлювати навколишній автомат станів не потрібно.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Залиште фінальну маску, оскільки початкове додавання має переповнення з обертанням у межах ширини байта. Для ширшої області попросіть SMT solver перевірити, чи є задача `f(x1) != f(x2)` для двох символічних входів однакової ширини виконуваною: `unsat` доводить інваріантність, а `sat` надає контрприклад і означає, що вхід не можна відкинути.<sup>[[7]](#references)</sup>

#### Розпізнавайте декодування, залежне від середовища

Перевірки протидії аналізу не обов’язково мають спричиняти перехід або аварійне завершення. Декодер може змішати результат сенсора з бітом ключа, константою opaque predicate або станом flattened dispatcher, продовжити роботу у звичайному режимі й видати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо виправити лише видимі гілки помилок; простежте залежності даних від перевірок середовища до стану декодера, порівняйте той самий фрагмент на автентичному пристрої та в емуляторі й перевірте, як примусова зміна результату кожного сенсора змінює кінцевий буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — це практичний спрощувач MBA для аналізу malware і реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його через спеціалізовані конвеєри, замість того щоб застосовувати до всього один універсальний прохід переписування.<sup>[[2]](#references)</sup>

Швидке використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, виводить сигнатуру та запускає паралельно кілька методів відновлення, як-от зіставлення зі зразком, перетворення ANF і інтерполяція коефіцієнтів.
- **Semilinear MBA**: атоми з константними масками відновлюються за допомогою реконструкції з розбиттям на біти, щоб замасковані ділянки залишалися коректними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього співвідношення.

Приклад змішаної тотожності, яку часто варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна звести до:

```c
x * y
```

- Явно вказуйте `--bitwidth`, якщо вираз отримано з арифметики з масками або вузьких регістрів.
- Якщо потрібен сильніший етап доведення, перегляньте локальні нотатки про Z3 тут:

## Відновлення XOR-state control-flow flattening

Флаттенер у стилі OLLVM може зберігати стан поточного basic block у двох 64-бітних регістрах і відновлювати його за допомогою XOR у диспетчері. Кожен початковий блок записує пару для наступного стану й переходить назад до диспетчера. Умовний блок може використовувати `CMOVcc` для заміни однієї половини пари залежно від прапорців CPU, тож відстеження лише видимих інструкцій переходу не виявить обох наступників. На відміну від диспетчера з непрямим переходом, ця структура може всюди використовувати прямі зворотні переходи.<sup>[[19]](#references)[[20]](#references)</sup>

Щоб відновити граф, знайдіть дерево порівнянь диспетчера та два регістри стану, зіставте кожен порівнюваний XOR-стан із цільовим блоком, а потім простежте записи, що досягають пари регістрів у кожному початковому блоці. Для умовних записів врахуйте інструкцію, що встановлює прапорці, і обидва результати `CMOVcc`. Замініть вихід кожного блока до диспетчера на визначеного прямого наступника або умовний перехід; після цього диспетчер стане недосяжним без модифікації бінарного файла. Це підхід на основі повного CFG; якщо важливий лише один декодер, описаний вище [вузький workflow зі зрізом виконання](#bypass-flattened-control-flow-with-a-narrow-execution-slice) може бути швидшим.<sup>[[19]](#references)[[20]](#references)</sup>

[DispatchThis](https://github.com/YungBinary/DispatchThis) автоматизує цю структуру в Binary Ninja. Скопіюйте `plugins/DispatchThis` до каталогу користувацьких плагінів Binary Ninja та перезапустіть програму. Для потрібної функції відкрийте **Function Settings** і виберіть `OLLVM_XOR_64`; якщо аналіз не почнеться, виберіть **Analysis → Reanalyze All Functions**. Цей режим переписує ребра керування MLIL, а не байти файла, і не потребує Z3 чи резолвера непрямих переходів. Його перевіряли на Binary Ninja 5.3.9757+; він не видаляє мертві записи стану в кожному блоці, тому не сприймайте їх як переходи, що залишилися активними.<sup>[[19]](#references)</sup>

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не використовуються як вказівники на рядки з нульовим завершенням у стилі C. Поширений формат `rustc` — це **кортеж вказівника й довжини** всередині **`.data.rel.ro`**, який вказує на фактичний блок рядків у **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднати сусідні рядки або повністю пропустити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Перелічіть **`.data.rel.ro`** по одному слову за раз.
3. Вважайте будь-яке значення в діапазоні адрес `.rodata` можливим вказівником на рядок.
4. Вважайте наступне слово можливою довжиною.
5. Застосуйте фільтри перевірки (наприклад, залиште довжини від **4** до **100** байтів).
6. Прочитайте з `.rodata` рівно `length` байтів, а не скануйте до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно для реверс-аналізу прошивок, оскільки відновлені рядки Rust часто розкривають **HTTP-маршрути, назви RPC, повідомлення журналу, перевірки, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra пропускає ці рядки, запустіть власний скрипт або плагін, який застосовує ту саму евристику та створює рядкові дані за адресами відповідних зміщень у `.rodata`. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — хороші приклади для адаптації цієї ідеї до інших **розмірів слова, порядку байтів і розташування секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

Навіть у Go-виконуваному файлі без символів потрібні метадані середовища виконання, щоб зіставляти лічильники команд із функціями. [GoReSym](https://github.com/mandiant/GoReSym) знаходить і аналізує такі структури, як `pclntab` і `moduledata`, використовуючи код, створений на основі середовища виконання Go. Так можна відновити межі функцій, назви, шляхи до вихідних файлів, типи та відомості про збірку без використання звичайної таблиці символів.<sup>[[9]](#references)[[13]](#references)</sup>

```bash
GoReSym.exe -t -d -p /path/to/sample.exe > goresym.json
```

Обфускатор може залишити ці структури придатними до використання, замінивши відновлені імена. Згрупуйте функції за повторюваним токеном, визначте пакет однієї з них за її викликами, рядками й API, а потім призначте цю мітку пакета всій групі.<sup>[[13]](#references)</sup>

### Відновлення імен Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує вилучення символів runtime із генерацією чистих еталонних бінарних файлів і зіставленням графів потоку керування (CFG). Виконайте такі кроки:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спершу перевірте `BuildInfo` та вбудовані рядки з інформацією про версію. Якщо обфускатор видалив їх, порівняйте фрагменти вбудованого Go runtime з еталонними runtime різних версій. У тестах Volexity близько `2%` runtime вистачило, щоб розрізнити основні версії Go. Вважайте це емпіричною оптимізацією, а не універсальним порогом.<sup>[[13]](#references)</sup>
2. **Підготуйте відповідні еталонні бінарні файли.** Створіть чисті бінарні файли для визначеної версії Go, цільової архітектури та ймовірних бібліотек. Відповідний toolchain зменшує відмінності CFG, зумовлені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє CFG функцій і видає нормалізовані оцінки від `0.0` до `1.0`. Зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Зіставлення з високою впевненістю пов’язують рандомізовані функції з чистою реалізацією. Менш впевнені зіставлення все ще можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте та імпортуйте результати.** Перевірте запропоновані імена за зв’язками викликів, константами, рядками та побічними ефектами, а потім імпортуйте звіт JSON за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Установіть toolchain і запустіть комбінований екстрактор зіставлення графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Порогове значення значущої відповідності за замовчуванням — `0.9`. Параметри `--extract` і `--graph` дають змогу запускати окремо кожен із цих етапів, тоді як за замовчуванням виконуються обидва, оскільки відновлені метадані runtime та дані CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнінг, прапорці збірки, архітектура та відмінності між версіями бібліотек можуть змінювати структуру графа, тому залишайте невизначені функції без змін замість того, щоб призначати їм назви з низьким рівнем упевненості.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків з усіх скомпонованих пакетів в одній суцільній таблиці. Записи не завершуються NUL-байтом, а структури runtime не містять базової адреси чи розміру таблиці. Однак компілятор упорядковує записи спочатку за довжиною, а потім за алфавітом — у різних операційних системах і архітектурах. Тому, знайшовши один запис, аналітик може пройти до сусідніх записів і за перехресними посиланнями на дані пов’язати рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro та Ghidra. Спершу дочекайтеся завершення автоаналізу, оскільки плагін використовує перехресні посилання на сегмент даних. Як якір за замовчуванням використовується рядок runtime `entersyscall`; після цього плагін може сканувати в обох напрямках, визначити відновлені рядки в базі даних і експортувати JSON-відповідність рядків функціям, які на них посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, яка посилається на рядок, щоб відокремити код застосунку або malware від зайвих даних скомпонованих бібліотек. Ця техніка не дає змоги відновити літерали, знищені обфускацією, наприклад перетворенням Garble `-literals`. Водночас вона може впорядкувати рядки runtime, які залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів runtime Go

Go вбудовує інформацію про типи runtime, яку використовують такі можливості, як garbage collection. Якщо інформацію про збірку видалено або дизасемблер не розбирає ці метадані, може здаватися, що інструкції завантажують довільні адреси даних, а цільова область залишається нетипізованою. Відновлення метаданих перетворює ці адреси на зрозумілі посилання на типи та полегшує розуміння можливостей пакетів.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи й розбирати типи runtime у звіт JSON. У поточній версії CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Параметр `-y`/`--types` вмикає розбір типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи та застосувати їхні посилання в базі даних аналізу. У форматі звіту, запровадженому разом із цією функцією, якщо не вказати `-y`, поля адреси RTTI та відновлених типів матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM і ARM64, тож цей самий процес підходить для бінарних файлів Go з Windows, Linux і macOS.<sup>[[10]](#references)</sup>

## GBA - Game Boy Advance

Якщо у вас є **бінарний файл** гри для GBA, можна скористатися різними інструментами, щоб **емулятувати** її та **налагоджувати**:

- [**no$gba**](https://problemkaputt.de/gba.htm) (_Завантажте версію для налагодження_) - Містить налагоджувач з інтерфейсом
- [**mgba** ](https://mgba.io)- Містить CLI-налагоджувач
- [**gba-ghidra-loader**](https://github.com/pudii/gba-ghidra-loader) - Плагін Ghidra
- [**GhidraGBA**](https://github.com/SiD3W4y/GhidraGBA) - Плагін Ghidra

У [**no$gba**](https://problemkaputt.de/gba.htm), у _**Options --> Emulation Setup --> Controls**_** ** можна побачити, як натискати **кнопки** Game Boy Advance

![Конфігурація кнопок no$gba з розкладкою кнопок Game Boy Advance](<../../images/image (581).png>)

Під час натискання кожна **клавіша має значення**, за яким її можна визначити:

```
A = 1
B = 2
SELECT = 4
START = 8
RIGHT = 16
LEFT = 32
UP = 64
DOWN = 128
R = 256
L = 256
```

Отже, у програмі такого типу найцікавіше — **як програма обробляє введені користувачем дані**. За адресою **0x4000130** ви знайдете поширену функцію: **KEYINPUT**.

![Вигляд Ghidra бінарного файлу GBA з посиланням на KEYINPUT за адресою 0x4000130](<../../images/image (447).png>)

На попередньому зображенні видно, що функцію викликає **FUN_080015a8** (адреси: _0x080015fa_ та _0x080017ac_).

У цій функції після кількох операцій ініціалізації (які не мають значення):

```c
void FUN_080015a8(void)

{
  ushort uVar1;
  undefined4 uVar2;
  undefined4 uVar3;
  ushort uVar4;
  int iVar5;
  ushort *puVar6;
  undefined *local_2c;

  DISPCNT = 0x1140;
  FUN_08000a74();
  FUN_08000ce4(1);
  DISPCNT = 0x404;
  FUN_08000dd0(&DAT_02009584,0x6000000,&DAT_030000dc);
  FUN_08000354(&DAT_030000dc,0x3c);
  uVar4 = DAT_030004d8;
```

Знайдено такий код:

```c
  do {
    DAT_030004da = uVar4; //This is the last key pressed
    DAT_030004d8 = KEYINPUT | 0xfc00;
    puVar6 = &DAT_0200b03c;
    uVar4 = DAT_030004d8;
    do {
      uVar2 = DAT_030004dc;
      uVar1 = *puVar6;
      if ((uVar1 & DAT_030004da & ~uVar4) != 0) {
```

Останній if перевіряє, чи **`uVar4`** є в **попередньому наборі Keys** і чи це не поточна клавіша, тобто чи кнопку відпустили (поточна клавіша зберігається в **`uVar1`**).

```c
        if (uVar1 == 4) {
          DAT_030000d4 = 0;
          uVar3 = FUN_08001c24(DAT_030004dc);
          FUN_08001868(uVar2,0,uVar3);
          DAT_05000000 = 0x1483;
          FUN_08001844(&DAT_0200ba18);
          FUN_08001844(&DAT_0200ba20,&DAT_0200ba40);
          DAT_030000d8 = 0;
          uVar4 = DAT_030004d8;
        }
        else {
          if (uVar1 == 8) {
            if (DAT_030000d8 == 0xf3) {
              DISPCNT = 0x404;
              FUN_08000dd0(&DAT_02008aac,0x6000000,&DAT_030000dc);
              FUN_08000354(&DAT_030000dc,0x3c);
              uVar4 = DAT_030004d8;
            }
          }
          else {
            if (DAT_030000d4 < 8) {
              DAT_030000d4 = DAT_030000d4 + 1;
              FUN_08000864();
              if (uVar1 == 0x10) {
                DAT_030000d8 = DAT_030000d8 + 0x3a;
```

У попередньому коді видно, що ми порівнюємо **uVar1** (місце, де зберігається **значення натиснутої кнопки**) з кількома значеннями:

- Спочатку його порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран.
- Потім значення порівнюють з **8** (кнопка **START**); у цьому завданні цей шлях перевіряє, чи правильний введений код.
  - У цьому разі змінну **`DAT_030000d8`** порівнюють із 0xf3, і якщо значення збігається, виконується певний код.
- В усіх інших випадках перевіряють і збільшують лічильник (`DAT_030000d4`).\
  Поки лічильник менший за 8, значення натиснутих кнопок накопичуються в `DAT_030000d8`.

Отже, у цьому завданні, знаючи значення кнопок, потрібно було **натиснути комбінацію довжиною менш як 8, щоб у результаті отримати суму 0xf3.**
