## Декомпілятор .NET

### [dotPeek](https://www.jetbrains.com/decompiler/)

dotPeek — це декомпілятор, який **декомпілює та аналізує різні формати**, зокрема **бібліотеки** (.dll), **файли метаданих Windows** (.winmd) і **виконувані файли** (.exe). Після декомпіляції збірку можна зберегти як проєкт Visual Studio (.csproj).

Перевага цього інструмента в тому, що він заощаджує час, коли потрібно відновити втрачений вихідний код зі застарілої збірки. Крім того, dotPeek забезпечує зручну навігацію декомпільованим кодом, що робить його одним із найкращих інструментів для **аналізу алгоритмів Xamarin.**

### [.NET Reflector](https://www.red-gate.com/products/reflector/)

Завдяки комплексній моделі надбудов та API, що дає змогу налаштувати інструмент відповідно до ваших потреб, .NET Reflector заощаджує час і спрощує розробку. Розгляньмо численні можливості reverse engineering, які надає цей інструмент:

- Дає змогу зрозуміти, як дані проходять через бібліотеку або компонент
- Допомагає зрозуміти реалізацію та використання мов і фреймворків .NET
- Виявляє недокументовані й недоступні функції, щоб розширити можливості використання API та застосованих технологій.
- Виявляє залежності та різні збірки
- Допомагає знайти точне місце помилок у вашому коді, сторонніх компонентах і бібліотеках.
- Дає змогу налагоджувати вихідний код будь-якого коду .NET, з яким ви працюєте.

### Інспектування керованого коду без виконання за допомогою REA

**REA** може перевіряти метадані PE/CLI та CIL, не завантажуючи збірку. Спочатку визначте ідентичність артефакту, а потім перевірте його члени та оголошені межі нативного коду; це корисно під час аналізу підозрілих викликів перед використанням декомпілятора або запуском програми.<sup>[[16]](#references)[[17]](#references)</sup>

```bash
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json
rea inspect-managed-native-boundaries /absolute/path/Assembly.dll --json
```

Для порівняння версій `compare_managed_members` використовує ідентичність на основі необробленого CIL/сигнатур і відбитки декодованих інструкцій, а не вважає токени метаданих стабільними між збірками. Оголошення P/Invoke не є доказом виконання native-коду; `verify_managed_native_boundaries` потребує відповідного native-експорту або Evidence функції, щоб перевірити цю межу. Зберігайте дайджест артефакту, MVID і нерозв’язані зіставлення разом із результатом.<sup>[[17]](#references)</sup>

## Налагодження DLL

### Використання IDA

- **Завантажте rundll32** (64-бітна версія: C:\Windows\System32\rundll32.exe, 32-бітна: C:\Windows\SysWOW64\rundll32.exe)
- Виберіть налагоджувач **Windbg**
- Виберіть "**Suspend on library load/unload**"

![Debugging DLLs - Using IDA: Виберіть " Suspend on library load/unload "](<../../images/image (868).png>)

- Налаштуйте **параметри** виконання, указавши **шлях до DLL** і функцію, яку потрібно викликати:

![Debugging DLLs - Using IDA: Налаштуйте параметри виконання, указавши шлях до DLL і функцію, яку потрібно викликати](<../../images/image (704).png>)

Після початку налагодження **виконання зупинятиметься під час завантаження кожної DLL**. Отже, коли rundll32 завантажить вашу DLL, виконання зупиниться.

Цей метод зупиняє виконання під час подій завантаження модулів, але перехід до точки входу завантаженої DLL менш прямолінійний, ніж у наведеному нижче процесі з x64dbg.

### Використання x64dbg/x32dbg

- **Завантажте rundll32** (64-бітна версія: C:\Windows\System32\rundll32.exe, 32-бітна: C:\Windows\SysWOW64\rundll32.exe)
- **Змініть командний рядок** ( _File --> Change Command Line_ ) і задайте шлях до DLL та функцію, яку потрібно викликати, наприклад: "C:\Windows\SysWOW64\rundll32.exe" "Z:\shared\Cybercamp\rev2\\\14.ridii_2.dll",DLLMain
- Перейдіть у _Options --> Settings_ і виберіть "**DLL Entry**".
- Потім **запустіть виконання**. Налагоджувач зупинятиметься на кожній точці входу dll main; у певний момент він **зупиниться на точці входу вашої dll**. Звідти просто знайдіть місця, де потрібно встановити breakpoint.

Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, **у верхній частині вікна win64dbg** можна побачити, **у якому коді ви перебуваєте**:

![Using IDA - Using x64dbg/x32dbg: Зверніть увагу: коли виконання зупиняється з будь-якої причини у win64dbg, у верхній частині вікна win64dbg можна побачити, у якому коді ви перебуваєте](<../../images/image (842).png>)

Цей індикатор підтверджує, що виконання зупинилося всередині DLL, яку ви хочете налагодити.

### Розшифрування Godot PCK і відновлення проєкту

Для поширеної гри на Godot знайдіть її PCK: це може бути окремий файл `.pck`, файл, доданий до виконуваного файла або вбудований у нього, чи файл у каталозі `assets` APK. [gore](https://github.com/figurophobia/gore) може перевіряти й видобувати вміст пакета, а для повного відновлення скриптів і ресурсів потрібен GDRE Tools (`gore setup` встановлює його, або скористайтеся `--gdre`). У цьому процесі інструмент підтримує формати PCK v2–v4 для Godot 4.x; він може виявляти заголовки v1, але для v1 потрібен наданий ключ.<sup>[[25]](#references)</sup>

Для автоматичного відновлення ключа потрібна зашифрована таблиця файлів; якщо зашифровано лише вміст файлів, натомість надайте відомий ключ. Невдала спроба відновлення не доводить, що пакет не зашифрований.<sup>[[28]](#references)</sup>

Пошук ключа — це **не атака на простір ключів AES-256**. Зашифрована таблиця файлів містить MD5 її відкритого тексту, довжину відкритого тексту, IV і шифротекст AES-256-CFB.<sup>[[27]](#references)</sup> `gore` перевіряє 32-байтові фрагменти виконуваного файла гри або сусідніх файлів як ключі-кандидати. Він відсіює кандидатів за правдоподібною довжиною розшифрованого шляху та його префіксом, а потім підтверджує збіги, знайдені скануванням двійкових даних, розшифровуючи всю таблицю та перевіряючи її MD5.<sup>[[26]](#references)[[28]](#references)</sup> Спочатку інструмент шукає в ініціалізованих секціях даних PE/ELF, а потім сканує весь файл; `--scan` додає інші файли-кандидати.<sup>[[28]](#references)</sup>

Якщо вбудований ключ не знайдено, перевіряється невеликий вбудований список паролів; параметр `--wordlist` дає змогу вказати інші кандидати. Кожен пароль перевіряється як ключ, похідний від пароля за алгоритмом рушія, як літеральний рядок із доповненням нулями або як ключ із 64 шістнадцяткових символів. На відміну від збігів, знайдених скануванням двійкових даних, збіги зі списку паролів у цій реалізації перевіряються лише за структурою шляхів. Підтвердьте їх, відкривши пакет і перевіривши видобуті ресурси.<sup>[[26]](#references)[[28]](#references)</sup>

Якщо файл гри доступний локально, виберіть потрібний для аналізу етап. `recover` запускає GDRE для відновлення проєкту, який можна відкрити, а `extract` лише розпаковує вихідні файли. `key` виводить ключ-кандидат для використання з іншим інструментом.<sup>[[25]](#references)[[28]](#references)</sup>

```bash
gore info game.exe
gore key game.pck --scan game.exe
gore extract game.pck -o ./raw
gore setup
gore recover game.exe -o ./game_project
```

## Дослідження нативного коду з підтвердженням доказами за допомогою REA

**REA** надає доступ до аналізу в Hopper, Ghidra та IDA через CLI і MCP. Для роботи потрібен Node.js 22.x (щонайменше 22.19), 24.x (щонайменше 24.11) або 26+, а також npm. Спершу налаштуйте наявний нативний провайдер; перевірте `rea providers --json` і явно виберіть провайдера, якщо ціль підтримують кілька. Замість `0x1000` нижче вкажіть спостережену назву функції або адресу з інвентаризації.<sup>[[16]](#references)[[18]](#references)</sup>

```bash
npm install --global rea-agents
rea providers --json
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea trace /absolute/path/to/program "search" --provider ghidra --json
rea xrefs /absolute/path/to/program 0x1000 --provider ghidra --json
rea function /absolute/path/to/program 0x1000 --provider ghidra --json
```

Почніть із рядка функції або символу, переходьте за посиланнями та викликами, а потім перегляньте досьє вибраної функції та псевдокод за допомогою `rea decompile`. REA прив’язує сеанс до вибраного провайдера, а не перемикається на інший у разі помилки без попередження. Для повторюваних запитів `--snapshot PATH` повторно використовує лише ті байти артефактів, провайдера, налаштування, операцію та параметри, що збігаються; snapshot — це локальний кеш, а не збережена база даних провайдера. Зберігайте повернуті Evidence та явні невідомі дані, не вважаючи виведені шляхи чи текст декомпілятора оригінальним вихідним кодом.<sup>[[16]](#references)[[18]](#references)</sup>

Про точки входу JavaScript/Electron, що ведуть до native add-ons, див. [Electron Desktop Apps](../../desktop-application-security/electron-desktop-apps/#static-asar-to-native-boundary-tracing-with-rea).

## Скриптовий аналіз IDA та Ghidra через локальний TCP-міст

[IDA-Ghidra-bridge](https://github.com/oscarsantanaarias/IDA-Ghidra-bridge) працює всередині **вже відкритої** бази даних IDA або програми Ghidra CodeBrowser і дає змогу окремому скрипту надсилати запити до цієї бази даних аналізу та змінювати її. Запустіть `ID_Server.py` з Python CLI в IDA (`import ID_Server`) або `Ghidra_Server.py` із Script Manager у Ghidra. IDA прив’язується до `127.0.0.1`, починаючи з порту `5073`, і перевіряє наступні порти. Поточний скрипт Ghidra починає з порту `5093` і перевіряє десять портів до `5102`; його Java-сокет прив’язується до wildcard-адреси, а не лише до loopback. Перед підключенням перевірте порт, виведений екземпляром. На відміну від headless analyzer, цей міст працює з програмою, відкритою в поточному екземплярі GUI.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

Надсилайте **по одній команді з завершальним символом нового рядка на кожне з’єднання** та читайте відповідь, завершену символом нового рядка. Зазвичай результат має формат JSON. Наприклад, після знаходження імпортованого API, пов’язаного зі шляхом до вхідних даних, `IMPORTXREF` знаходить місця його виклику; потім `DECOMP_XREF` пакетно декомпілює викликачів вибраної адреси. `FUNC` перевіряє функцію, а `PCODE` повертає проміжне представлення декомпілятора. Використовуйте адресу з активної бази даних, а не адресу, скопійовану з бінарного файлу з іншим базовим адресним зсувом. У наведеному нижче прикладі використовується порт IDA за замовчуванням; для Ghidra використовуйте порт, виведений її скриптом.<sup>[[21]](#references)[[22]](#references)[[23]](#references)</sup>

```python
import socket

with socket.create_connection(("127.0.0.1", 5073)) as sock:
    sock.sendall(b"IMPORTXREF memcpy\n")
    print(sock.makefile("r", encoding="utf-8").readline())
```

Той самий канал може **змінювати базу даних аналізу**: `RENAME_FUNC`, `RETYPE`, `SETCONV`, `DEFSTRUCT`/`SETFIELD`, `MAKEFUNC` і `PATCH` змінюють назви, типи, визначення структур, межі функцій або збережені байти. `PATCH` — це редагування бази даних, а **не** доказ застосування патча до запущеного процесу. У документації жодного з listener не згадується автентифікація. IDA доступна лише через loopback, але Ghidra може бути доступна через мережеві інтерфейси; обмежте доступ до listener Ghidra під час її використання. `QUIT` зупиняє будь-який із listener, а в IDA також доступна `ida_bridge_stop()`.<sup>[[21]](#references)[[22]](#references)[[23]](#references)[[24]](#references)</sup>

## MBA obfuscation deobfuscation

**Обфускація Mixed Boolean-Arithmetic (MBA)** приховує прості вирази, як-от `x + y`, за формулами, що поєднують арифметичні (`+`, `-`, `*`) і побітові оператори (`&`, `|`, `^`, `~`, зсуви). Важливо, що ці тотожності зазвичай правильні лише за **модульної арифметики з фіксованою шириною**, тому перенесення та переповнення мають значення:

```c
(x ^ y) + 2 * (x & y) == x + y
```

Якщо спростити такий вираз за допомогою універсальних засобів алгебри, можна легко отримати неправильний результат, оскільки семантику розрядності було проігноровано.<sup>[[1]](#references)</sup>

### Практичний робочий процес

1. **Збережіть початкову розрядність** із lifted-коду/IR/виводу декомпілятора (`8/16/32/64` бітів).
2. **Класифікуйте вираз** перед спробою його спростити:
   - **Лінійний**: зважені суми побітових атомів
   - **Напівлінійний**: лінійний вираз із константними масками, як-от `x & 0xFF`
   - **Поліноміальний**: є добутки
   - **Змішаний**: добутки й побітова логіка чергуються, часто з повторюваними підвиразами
3. **Перевіряйте кожне запропоноване перетворення** за допомогою випадкового тестування або SMT-доведення. Якщо еквівалентність неможливо довести, збережіть початковий вираз замість того, щоб вгадувати.

### Обхід розплющеного потоку керування за допомогою вузького зрізу виконання

Відновлювати повний граф потоку керування часто не потрібно. За наявності розплющення потоку керування, непрозорих предикатів, великих диспетчерів або коду з великою кількістю MBA простежте посилання від зашифрованих блоків даних і вихідних буферів до найменшої процедури, яка їх перетворює. Потім відтворіть лише цей зріз потоку даних або виконайте його окремо; диспетчер не є частиною необхідного розв’язання, якщо відповідний стан можна ініціалізувати безпосередньо.<sup>[[7]](#references)</sup>

Практичний робочий процес:<sup>[[7]](#references)</sup>

1. Складіть перелік виконуваних секцій і секцій даних, релокацій і перехресних посилань. Вивантажте потенційні таблиці з `.rodata`, зберігши порядок байтів і ширину елементів.
2. Визначте останню процедуру, яка записує відкритий текст або вихідний буфер. Зафіксуйте її вхідні дані, таблиці, на які вона посилається, імпортовані виклики та необхідний глобальний стан.
3. Перенесіть лише ці операції у модель Python із фіксованою розрядністю. Якщо зріз усе ще залежить від надто великого обсягу стану, викличте процедуру в Unicorn, QEMU або налагоджувачі й перехопіть непотрібні імпортовані функції замість емуляції всієї програми.
4. Переконайтеся, що екстрактор справді отримує результат із наданого бінарного файла: приберіть непомітні запасні варіанти, перевірте його на наявність вбудованих відповідей і запустіть на невідомих збірках зі зміненими рядками, ключами, ідентифікаторами, макетами та початковими значеннями обфускації.

Корисні команди для першого аналізу:<sup>[[7]](#references)</sup>

```bash
readelf -SW target
objdump -s -j .rodata target > rodata.txt
objdump -d target | rg 'adrp|add|ldr|str'
```

#### Виявлення виразів MBA, що маскують константи

Вираз байтового типу, який на перший погляд залежить від вхідних даних, може повністю їх нівелювати. Після вилучення таблиць обчисліть вираз для всього 8-бітного діапазону; якщо множина результатів містить лише одне значення, це доводить, що байт є константою, і відновлювати навколишню машину станів не потрібно.<sup>[[7]](#references)</sup>

```python
def mba(a, b, c, d, e, x):
    return ((((a | (~x & 0xff)) & c) +
             ((x | b) & d)) ^ e) & 0xff

decoded = bytearray()
for row in zip(A, B, C, D, E):
    outputs = {mba(*row, x) for x in range(256)}
    if len(outputs) != 1:
        raise ValueError("expression depends on x")
    decoded.append(outputs.pop())
print(decoded)
```

Збережіть фінальну маску, оскільки початкове додавання має переповнення з циклічним переходом за шириною байта. Для ширшої області значень запитайте SMT-розв’язувач, чи є формула `f(x1) != f(x2)` виконуваною для двох символічних вхідних даних однакової ширини: `unsat` доводить інваріантність, а `sat` дає контрприклад і означає, що вхідні дані не можна відкинути.<sup>[[7]](#references)</sup>

#### Виявлення декодування, залежного від середовища

Перевірки на протидію аналізу не обов’язково мають викликати перехід або аварійне завершення. Декодер може змішати результат датчика з бітом ключа, константою opaque-predicate або станом flattened-dispatcher, продовжити роботу у звичайному режимі й видати правдоподібний, але хибний відкритий текст в емуляторі. Тому недостатньо виправляти лише видимі гілки з помилками: відстежуйте залежності даних від перевірок середовища до стану декодера, порівнюйте той самий фрагмент на справжньому пристрої та в емуляторі, а також перевіряйте, як примусова зміна результату кожного датчика впливає на фінальний буфер.<sup>[[7]](#references)</sup>

### CoBRA

[**CoBRA**](https://github.com/trailofbits/CoBRA) — це практичний спрощувач MBA для аналізу шкідливого ПЗ та реверсингу захищених бінарних файлів. Він класифікує вираз і спрямовує його до спеціалізованих конвеєрів замість застосування одного універсального проходу переписування до всього.<sup>[[2]](#references)</sup>

Швидкий приклад використання:

```bash
# Recover arithmetic from a logic-heavy MBA
cobra-cli --mba "(x&y)+(x|y)"
# x + y

# Preserve fixed-width wraparound semantics
cobra-cli --mba "(x&0xFF)+(x&0xFF00)" --bitwidth 16
# x

# Ask CoBRA to prove the rewrite with Z3
cobra-cli --mba "(a^b)+(a&b)+(a&b)" --verify
```

Корисні випадки:

- **Linear MBA**: CoBRA обчислює вираз на булевих входах, отримує сигнатуру та паралельно запускає кілька методів відновлення, як-от зіставлення зі зразками, перетворення ANF і інтерполяцію коефіцієнтів.
- **Semilinear MBA**: атоми з константною маскою відновлюються за допомогою реконструкції з розбиттям на біти, щоб замасковані області залишалися коректними.
- **Polynomial/Mixed MBA**: добутки розкладаються на ядра, а повторювані підвирази можна винести в тимчасові змінні перед спрощенням зовнішнього відношення.

Приклад змішаної тотожності, яку часто варто спробувати відновити:

```c
(x & y) * (x | y) + (x & ~y) * (~x & y)
```

Це можна звести до:

```c
x * y
```

- Краще запускати CoBRA на **виразах lifted IR** або результатах декомпіляції після того, як виокремлено точне обчислення.
- Явно задавайте `--bitwidth`, якщо вираз отримано з арифметики з масками або вузьких регістрів.
- Якщо потрібен суворіший крок доведення, перегляньте локальні нотатки про Z3:


{{#ref}}
satisfiability-modulo-theories-smt-z3.md
{{#endref}}

- CoBRA також постачається як **плагін LLVM pass** (`libCobraPass.so`), який стане в пригоді, коли потрібно нормалізувати насичений MBA код LLVM IR перед подальшими етапами аналізу.
- Залишкові вирази зі змішаними доменами, чутливі до переносу, які не підтримуються, слід сприймати як сигнал зберегти оригінальний вираз і вручну проаналізувати шлях переносу.

## Відновлення control-flow flattening зі станом XOR

Flattening у стилі OLLVM може зберігати стан поточного базового блоку у двох 64-бітних регістрах і відновлювати його за допомогою XOR у dispatcher. Кожен оригінальний блок записує пару значень для наступного стану й переходить назад до dispatcher. Умовний блок може використовувати `CMOVcc`, щоб замінити одну половину пари відповідно до прапорців CPU, тому простеження лише видимих інструкцій переходу призводить до пропуску двох наступників. На відміну від dispatcher з непрямим переходом, ця схема може використовувати прямі зворотні переходи всюди.<sup>[[19]](#references)[[20]](#references)</sup>

Щоб відновити граф, визначте дерево порівнянь dispatcher і два регістри стану, зіставте кожен стан XOR, який порівнюється, з цільовим блоком, а потім простежте записи до пари регістрів, що досягають кожного оригінального блоку. Для умовних записів врахуйте інструкцію, що встановлює прапорці, та обидва результати `CMOVcc`. Замініть вихід dispatcher кожного блоку на визначений прямий наступник або умовний перехід; тоді dispatcher стане недосяжним без змін бінарного файла. Це підхід для повного CFG; якщо потрібен лише один декодер, наведений вище [вузький робочий процес зрізу виконання](#bypass-flattened-control-flow-with-a-narrow-execution-slice) може бути швидшим.<sup>[[19]](#references)[[20]](#references)</sup>

[DispatchThis](https://github.com/YungBinary/DispatchThis) автоматизує цю схему в Binary Ninja. Скопіюйте `plugins/DispatchThis` до каталогу користувацьких плагінів Binary Ninja та перезапустіть програму. Для потрібної функції відкрийте **Function Settings** і виберіть `OLLVM_XOR_64`; якщо аналіз не починається, скористайтеся **Analysis → Reanalyze All Functions**. Цей режим переписує ребра керування потоком MLIL, а не байти файла, і не потребує Z3 чи резолвера непрямих переходів. Його перевіряли на Binary Ninja 5.3.9757+; він не видаляє неактивні записи стану в окремих блоках, тож не сприймайте їх як переходи, що досі виконуються.<sup>[[19]](#references)</sup>

### Відновлення рядків Rust із прошивки ELF

У бінарних файлах **Rust ELF** багато статичних рядків не використовуються як вказівники на рядки з завершальним нульовим байтом у стилі C. Поширене компонування `rustc` — це **кортеж вказівника та довжини** всередині **`.data.rel.ro`**, що вказує на справжній блок рядків, збережений у **`.rodata`**:

```text
[8-byte little-endian pointer][8-byte little-endian length]
```

Це означає, що `strings` або стандартний аналіз Ghidra може об’єднати суміжні рядки або зовсім не виявити перехресні посилання.<sup>[[3]](#references)</sup>

Швидкий робочий процес:

```bash
readelf -S <bin>
objdump -h <bin>
```

1. Отримайте віртуальну адресу та розмір **`.rodata`**.
2. Переберіть **`.data.rel.ro`** по одному слову.
3. Розглядайте будь-яке значення в діапазоні адрес `.rodata` як кандидат на вказівник на рядок.
4. Розглядайте наступне слово як кандидат на довжину.
5. Застосуйте фільтри перевірки на адекватність (наприклад, залиште довжини від **4** до **100** байтів).
6. Зчитуйте з `.rodata` рівно `length` байтів замість сканування до `0x00`.

Мінімальна логіка екстрактора:

```python
for off in range(0, len(data_rel_ro), 8):
    ptr = u64(data_rel_ro[off:off+8])
    length = u64(data_rel_ro[off+8:off+16])
    if rodata_start <= ptr < rodata_end and 4 <= length <= 100:
        start = ptr - rodata_start
        print(rodata[start:start+length])
```

Це особливо корисно під час reversing firmware, оскільки відновлені рядки Rust часто розкривають **HTTP-маршрути, назви RPC, повідомлення журналу, assertions, імена файлів, ключі конфігурації, обробники команд і логіку, пов’язану з автентифікацією**.

Якщо Ghidra не знаходить ці рядки, запустіть власний скрипт або плагін, який застосовує ту саму евристику й створює рядкові дані за адресами `.rodata`, на які посилаються. Опубліковані інструменти `rust-strings` і `RustStrings.py` від Pen Test Partners — корисні приклади для адаптації цієї ідеї до інших **розмірів слова, порядку байтів і структур секцій**.<sup>[[4]](#references)</sup><sup>[[5]](#references)</sup>

### Відновлення метаданих без таблиці символів

Для зіставлення лічильників команд із функціями виконуваному файлу Go зі видаленими символами все одно потрібні метадані runtime. [GoReSym](https://github.com/mandiant/GoReSym) знаходить і аналізує такі структури, як `pclntab` і `moduledata`, використовуючи код, похідний від Go runtime. Це дає змогу відновити межі функцій, назви, шляхи до вихідних файлів, типи й відомості про збірку без використання звичайної таблиці символів.<sup>[[9]](#references)[[13]](#references)</sup>

```bash
GoReSym.exe -t -d -p /path/to/sample.exe > goresym.json
```

Обфускатор може залишити ці структури придатними до використання, замінивши відновлені назви. Наприклад, Garble хешує ідентифікатори та шляхи пакетів і видаляє інформацію про збірку, модулі й налагодження.<sup>[[12]](#references)</sup> Токен обфускованого пакета має бути однаковим у функцій цього пакета. Згрупуйте функції за повторюваним токеном, визначте пакет однієї з них за її викликаними функціями, рядками й API, а тоді поширте цю мітку пакета на всю групу.<sup>[[13]](#references)</sup>

### Відновлення назв Garble за допомогою GoResolver

[GoResolver](https://github.com/volexity/GoResolver) поєднує витягування символів середовища виконання зі створенням чистих еталонів і зіставленням графів потоку керування (CFG). Виконайте такі кроки:<sup>[[10]](#references)[[13]](#references)</sup>

1. **Визначте версію компілятора.** Спочатку перевірте `BuildInfo` та вбудовані рядки версії. Якщо обфускатор їх видалив, порівняйте частини вбудованого середовища виконання Go з еталонними середовищами виконання різних версій. У тестах Volexity приблизно `2%` середовища виконання було достатньо, щоб розрізнити основні версії Go. Вважайте це емпіричною оптимізацією, а не універсальним порогом.<sup>[[13]](#references)</sup>
2. **Створіть відповідні еталони.** Згенеруйте чисті бінарні файли для визначеної версії Go, цільової архітектури та ймовірних бібліотек. Відповідність набору інструментів зменшує відмінності CFG, зумовлені компілятором.<sup>[[10]](#references)[[13]](#references)</sup>
3. **Порівняйте функції.** GoGrapher зіставляє CFG функцій і виводить нормалізовані оцінки від `0.0` до `1.0`. Його зіставлення базових блоків ґрунтується на зваженому порівнянні подібних інструкцій. Відповідності з високим рівнем упевненості дають змогу пов’язати функції з рандомізованими назвами з їхньою чистою реалізацією. Менш надійні відповідності все одно можуть допомогти визначити пакет або модуль.<sup>[[8]](#references)[[11]](#references)[[13]](#references)</sup>
4. **Перевірте й імпортуйте.** Підтвердьте запропоновані назви за зв’язками викликів, константами, рядками та побічними ефектами, а потім імпортуйте JSON-звіт за допомогою плагіна GoResolver для IDA або Ghidra.<sup>[[10]](#references)[[13]](#references)</sup>

Установіть набір інструментів і запустіть комбінований екстрактор та зіставлювач графів:<sup>[[10]](#references)</sup>

```bash
python3 -m venv goresolver-env
source goresolver-env/bin/activate
pip install goresolver

# Automatic Go-version detection and reference selection
goresolver resolve -o report.json /path/to/sample.exe

# Override the version/libraries and confidence threshold when known
goresolver resolve -v go1.23.4 -l os/exec net/http \
  -t 0.9 -o report.json /path/to/sample.exe
```

Стандартний поріг значущого збігу — `0.9`. Параметри `--extract` і `--graph` дають змогу окремо запускати кожен етап, тоді як за замовчуванням виконуються обидва, оскільки відновлені метадані runtime та дані CFG доповнюють одне одного.<sup>[[10]](#references)</sup> Оцінки CFG є евристичними: інлайнинг, прапорці збірки, архітектура та відмінності між версіями бібліотек можуть змінити структуру графа, тому невизначені функції краще залишати без імен, а не призначати їм назви з низькою впевненістю.<sup>[[13]](#references)</sup>

### Відновлення таблиці рядків Go

Бінарні файли Go розміщують байти рядків з усіх підключених пакетів в одній суцільній таблиці. Записи не завершуються NUL-байтом, а структури runtime не містять базової адреси чи розміру таблиці. Однак компілятор впорядковує записи спочатку за довжиною, а потім за алфавітом — незалежно від операційної системи й архітектури. Тому, знайшовши один запис, аналітик може переглянути сусідні записи та за перехресними посиланнями на дані пов’язати рядки з кодом.<sup>[[15]](#references)</sup>

[GoStringExtractor](https://github.com/volexity/GoStringExtractor) автоматизує цей процес в IDA Pro та Ghidra. Спочатку дочекайтеся завершення автоаналізу, оскільки плагін використовує перехресні посилання із сегментів даних. За замовчуванням він шукає рядок runtime `entersyscall`, після чого сканує таблицю в обох напрямках, визначає відновлені рядки в базі даних і експортує JSON-відповідність рядків функціям, які на них посилаються.<sup>[[14]](#references)</sup>

Фільтруйте звіт за пакетом функції, що посилається на рядок, щоб відокремити код застосунку чи malware від зайвих даних підключених бібліотек. Цей метод не може відновити літерали, знищені обфускацією, як-от перетворенням Garble `-literals`. Водночас він дає змогу впорядкувати рядки runtime, що залишилися необфускованими.<sup>[[14]](#references)[[15]](#references)</sup>

### Відновлення типів runtime Go

Go вбудовує інформацію про типи runtime, яку використовують такі функції, як збирання сміття. Якщо інформацію про збірку видалено або дизасемблер не аналізує ці метадані, може здаватися, що інструкції завантажують довільні адреси даних, а цільовий регіон залишається без типів. Відновлення метаданих перетворює ці адреси на зрозумілі посилання на типи й полегшує аналіз можливостей пакетів.<sup>[[15]](#references)</sup>

[GoResolver](https://github.com/volexity/GoResolver) може витягувати символи та аналізувати типи runtime, формуючи звіт JSON. У поточній версії CLI використовується підкоманда `resolve`:<sup>[[10]](#references)</sup>

```bash
pip install goresolver
goresolver resolve -x -y -o report.json sample_bin.exe
```

Опція `-y`/`--types` вмикає аналіз типів. Імпортуйте звіт за допомогою плагіна GoResolver для IDA Pro або Ghidra, щоб визначити відновлені типи та застосувати їхні посилання в базі даних аналізу. У форматі звіту, представленому разом із цією функцією, якщо не вказати `-y`, поля RTTI address і recovered-types матимуть значення null.<sup>[[10]](#references)[[15]](#references)</sup>

GoResolver підтримує зразки PE, ELF і Mach-O для x86, AMD64, ARM і ARM64, тож той самий процес підходить для бінарних файлів Go з Windows, Linux і macOS.<sup>[[10]](#references)</sup>

- Спочатку його порівнюють зі **значенням 4** (кнопка **SELECT**): у цьому завданні ця кнопка очищає екран
