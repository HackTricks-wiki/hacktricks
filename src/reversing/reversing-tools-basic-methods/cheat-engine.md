# Cheat Engine

{{#include ../../banners/hacktricks-training.md}}

[**Cheat Engine**](https://www.cheatengine.org/downloads.php) — корисна програма для пошуку місця, де важливі значення зберігаються в пам'яті запущеної гри, і їх зміни.\
Після завантаження та запуску вам буде **представлено** **tutorial** щодо використання цього інструмента. Якщо ви хочете навчитися ним користуватися, наполегливо рекомендується його пройти.

## Пошук значення

Припустімо, що існує важливе значення (наприклад, життя вашого персонажа), яке ви хочете збільшити, і ви шукаєте це значення в пам'яті.

### За відомою зміною

Припустімо, що ви шукаєте значення 100. Ви **виконуєте сканування**, шукаючи це значення, і знаходите багато збігів:

![Searching the value - Through a known change: Припустімо, що ви шукаєте значення 100, виконуєте сканування, шукаючи це значення, і знаходите багато збігів](<../../images/image (108).png>)

Потім ви робите щось, через що **значення змінюється**, **зупиняєте** гру та **виконуєте** **наступне сканування**:

![Searching the value - Through a known change: Потім ви робите щось, через що значення змінюється, зупиняєте гру та виконуєте наступне сканування](<../../images/image (684).png>)

Cheat Engine шукатиме **значення**, які **змінилися зі 100 на нове значення**. Вітаємо, ви **знайшли** **адресу** потрібного значення й тепер можете його змінити.\
_Якщо значень усе ще кілька, знову зробіть щось, щоб змінити це значення, і виконайте ще одне "next scan", щоб відфільтрувати адреси._

### Випадкова адреса пам'яті — пошук коду

Досі ми вчилися знаходити адресу, що зберігає значення, але дуже ймовірно, що **під час різних запусків гри ця адреса буде розташована в різних місцях пам'яті**. Тож з'ясуймо, як завжди знаходити цю адресу.

Використовуючи деякі з наведених прийомів, знайдіть адресу, за якою поточна гра зберігає важливе значення. Потім (за бажанням зупинивши гру) клацніть **правою кнопкою миші** по знайденій **адресі** та виберіть "**Find out what accesses this address**" або "**Find out what writes to this address**":

![Unknown Value, known change - Random Memory Address - Finding the code: Використовуючи деякі з наведених прийомів, знайдіть адресу, за якою поточна гра зберігає важливе значення. Потім...](<../../images/image (1067).png>)

**Перший варіант** корисний для визначення, які **частини** **коду** **використовують** цю **адресу** (це корисно і для інших завдань, наприклад для **визначення місця, де можна змінити код** гри).\
**Другий варіант** є більш **конкретним** і в цьому випадку буде кориснішим, оскільки нас цікавить, **звідки записується це значення**.

Після вибору одного з цих варіантів **debugger** буде **приєднано** до програми, і з'явиться нове **порожнє вікно**. Тепер **грайте** в **гру** та **змініть** це **значення** (не перезапускаючи гру). **Вікно** має **заповнитися** **адресами**, які **змінюють** **значення**:

![Unknown Value, known change - Random Memory Address - Finding the code: Після вибору одного з цих варіантів debugger буде приєднано до програми, і з'явиться нове порожнє вікно...](<../../images/image (91).png>)

Тепер, коли ви знайшли адресу, яка змінює значення, ви можете **змінити код на власний розсуд** (Cheat Engine дозволяє дуже швидко замінити його на NOPs):

![Unknown Value, known change - Random Memory Address - Finding the code: Тепер, коли ви знайшли адресу, яка змінює значення, ви можете змінити код на власний розсуд (Cheat Engine...](<../../images/image (1057).png>)

Тож тепер ви можете змінити його так, щоб код не впливав на ваше число або завжди впливав на нього позитивно.

### Code Injection

Code injection — це техніка, за якої фрагмент коду вводиться в цільовий процес, а потім виконання коду перенаправляється через написаний вами код (наприклад, щоб нараховувати вам очки замість їх віднімання).

## Code injection, безпечний до relocation, за допомогою AOB signatures

Скрипт, який встановлює hook на `game.exe+123456`, може перестати працювати після ASLR або оновлення програмного забезпечення. **Array of Bytes (AOB) signature** знаходить інструкцію за навколишнім machine code. Використовуйте `aobscanmodule`, щоб обмежити пошук одним module. Зробіть signature достатньо довгою, щоб вона повертала один збіг. Використовуйте wildcard для relocation bytes, адрес та інших байтів, які можуть змінюватися. Не використовуйте wildcard для всієї інструкції, яку потрібно відновити.<sup>[[4]](#references)</sup>

У Memory View виберіть інструкцію та використайте **Tools → Auto Assemble → Template → AOB Injection**. Згенерований блок `[DISABLE]` є важливим. Він має відновлювати кожен перезаписаний байт і звільняти allocation.<sup>[[4]](#references)</sup>

<details>
<summary>Мінімальний x64 AOB injection skeleton</summary>
```asm
[ENABLE]
aobscanmodule(INJECT,game.exe,F3 0F 11 83 A0 00 00 00 48 8B)
alloc(newmem,1024,INJECT)
label(return)
registersymbol(INJECT)
newmem:
movss [rbx+000000A0],xmm0
jmp return
INJECT:
jmp newmem
nop
nop
nop
return:
[DISABLE]
INJECT:
db F3 0F 11 83 A0 00 00 00
unregistersymbol(INJECT)
dealloc(newmem)
```
</details>

Перш ніж увімкнути скрипт, перевірте такі моменти:

1. AOB повертає **одну** адресу. Якщо повертається більше адрес, додайте стабільні інструкції з обох боків.
2. Перехід замінює повні інструкції. Ніколи не розділяйте інструкцію.
3. Виділена code cave досяжна згенерованим переходом. На x64 для далекого виділення може знадобитися 14-байтовий перехід.
4. Введений код зберігає регістри, прапорці та вирівнювання стека, яких очікує оригінальна функція.
5. Блок вимкнення відновлює точні оригінальні байти. Перевірте ввімкнення та вимкнення кілька разів перед збереженням таблиці.

## Надійний workflow для вказівників

Вказівник, знайдений під час одного запуску, є лише кандидатом. Створюйте pointer maps під час кількох нових запусків і повторно скануйте їх за всіма отриманими даними. Перезапускайте цільовий процес між зніманнями, щоб ASLR і виділення пам’яті в heap змінювалися. Надавайте перевагу шляхам, базою яких є модуль або інший стабільний символ. Відхиляйте шляхи, які працюють лише з одним save, рівнем або екземпляром об’єкта.

Фільтр **pointer must end with specific offsets** і його опція deviation можуть зберегти корисні шляхи, коли сусіднє поле зміщується між збірками. У релізі 7.5 також було додано цей параметр deviation. Це фільтр, а не доказ стабільності pointer chain.<sup>[[1]](#references)</sup>

Коли структура надто часто переміщується для pointer scanning, встановіть hook на інструкцію, яка звертається до неї. Захопіть актуальний вказівник на об’єкт із регістра в allocated symbol. Це часто надійніше для списків entity та managed objects.

## Трасування коду замість сканування значень

Використовуйте **Find out what writes to this address**, коли значення безпосередньо змінюється. Використовуйте **Find out what accesses this address**, коли потрібно знайти об’єкт-власник або коли запис відбувається через скопійовані дані. Виконайте лише одну дію в цільовому процесі. Потім порівняйте кількість спрацювань і стан регістрів.

**Ultimap 2** використовує Intel Processor Trace на сумісних процесорах Intel. Він записує виконаний control flow із меншим перериванням, ніж покрокове виконання кожної інструкції. Відфільтруйте код, який виконувався під час цікавої дії, і вилучіть код, який також виконувався під час capture у стані простою. Intel PT не є stealth-функцією. Ціль все одно може виявити tracing, зміни часу виконання або сам Cheat Engine.<sup>[[1]](#references)</sup>

Cheat Engine 7.5 також додав інтерфейс Intel PT, наданий Windows. Старий режим Ultimap на основі DBVM і режим Intel PT мають різні вимоги до hardware та ОС. Не припускайте, що CPU із підтримкою DBVM підтримує Intel PT.<sup>[[1]](#references)</sup>

## Вибір debugger і breakpoint

Вибирайте найменш інвазивний debugger, який працює:

- **Windows debugger** простий, але створює звичайні debug events. Anti-debugging перевірки можуть його виявити.
- **VEH debugger** обробляє breakpoints через vectored exception handler. Він обходить деякі базові debugger checks, але не є невидимим.
- **Hardware breakpoints** не змінюють байти інструкцій, але x86/x64 надає лише невелику кількість слотів debug-регістрів.
- **Software breakpoints** замінюють один байт на `INT3`. Їх легко виявити, і вони можуть конфліктувати з integrity checks.
- **DBVM debugger** переміщує деякі операції під guest OS. Він має значно вищі привілеї та може призвести до аварійного завершення host, якщо його неправильно налаштовано.

Cheat Engine 7.5 може використовувати однобайтовий перехід на основі exception handler і `INT3`, коли для звичайного relative jump недостатньо місця. Ставтеся до нього як до software breakpoint. Перевірте перебіг exception і не припускайте, що це обходить anti-tamper checks.<sup>[[1]](#references)</sup>

DBVM — це hypervisor, а не універсальний перемикач невидимості. Використовуйте його лише в disposable lab. Не відкривайте його control interface для ненадійного коду. Kernel anti-cheat і endpoint products усе ще можуть виявити driver, стан hypervisor або змінену пам’ять.

## Managed runtimes і нові функції 7.6/7.7

Для цілей Mono, IL2CPP, .NET і Java, коли це можливо, надавайте перевагу runtime metadata замість blind scans. Відкрийте **Mono → Activate mono features** або відповідне вікно runtime information. Спочатку знайдіть class, field або method. Потім використовуйте native disassembly, коли managed method скомпільовано JIT.

Гілка 7.6 додала `AOBSCANEX` для сигнатур лише у executable memory, інтерфейс debugger `gdbserver`, інспекцію Java metadata, швидше перерахування IL2CPP і опцію pointer-scan, яка ігнорує старший байт вказівника, що використовується memory tagging в ARM. Гілка 7.7 додала native Linux builds, `HOOK`/`UNHOOK`, `aobscanfunction`, покращений пошук generic Mono methods, покращену підтримку PDB structures і базовий аналіз Unreal Engine structures.<sup>[[3]](#references)</sup>

Ці доповнення дають змогу використовувати такий workflow:

1. Визначте managed method або static field із metadata.
2. Простежте або дизасемблюйте native code, створений для цього method.
3. Використайте `AOBSCANEX` або `aobscanfunction`, щоб знайти стабільну executable signature.
4. Створіть reversible hook. Збережіть оригінальні інструкції та перевірте шлях вимкнення.
5. Повторно перевіряйте signature після кожного оновлення цілі. Успішний match не гарантує, що навколишня логіка все ще має те саме значення.

## Віддалені цілі з `ceserver`

`ceserver` надає GUI Cheat Engine enumeration процесів, доступ до пам’яті та debugging. Official builds охоплюють Linux і Android. Запускайте на цілі відповідну architecture та підключайтеся через вкладку **Network**. На Android перенаправлення default port запобігає його відкриттю в мережі:<sup>[[3]](#references)</sup>
```bash
adb push ceserver_arm64 /data/local/tmp/ceserver
adb shell 'su -c "chmod 700 /data/local/tmp/ceserver && /data/local/tmp/ceserver"'
adb forward tcp:52736 tcp:52736
```
Сторонній bridge `frida-ceserver` може надати сумісний із Cheat Engine інтерфейс для iOS-цілей. Це не офіційний `ceserver`, і підтримувані операції можуть відрізнятися.<sup>[[2]](#references)</sup>

Припускайте, що протокол надає доступ на рівні debugger. Прив’яжіть його до loopback або розмістіть за SSH/ADB tunnel. Ніколи не відкривайте TCP 52736 для ненадійної мережі. Зупиніть server після завершення сесії.

## Операційна безпека

Підключайтеся лише до програмного забезпечення, яким ви володієте або яке маєте право тестувати. Не запускайте Cheat Engine поруч з онлайн-грою або production endpoint. Запис у пам’ять, injected code, drivers і DBVM можуть призвести до аварійного завершення роботи або пошкодження цілі.<sup>[[3]](#references)</sup>

Завантажуйте build-и з офіційного сайту або компілюйте опублікований source code. Security products часто класифікують memory editors, debuggers та їхні drivers як hack tools. Не вимикайте захист host глобально. Використовуйте виділену VM або lab host і перевіряйте artifact перед запуском.<sup>[[3]](#references)</sup>
