# Мутаційне тестування смартконтрактів (slither-mutate, mewt, MuTON)

{{#include ../../banners/hacktricks-training.md}}

Мутаційне тестування «тестує ваші тести»: воно систематично вносить невеликі зміни (мутанти) в код контракту та повторно запускає набір тестів. Якщо тест завершується помилкою, мутант убито. Якщо тести й далі проходять, мутант виживає, виявляючи сліпу зону, яку не можуть виявити покриття рядків або гілок коду.

Ключова ідея: покриття показує, що код виконувався; мутаційне тестування показує, чи справді перевіряється поведінка.<sup>[[2]](#references)</sup>

## Чому покриття може вводити в оману

Розгляньмо цю просту перевірку порогового значення:

```solidity
function verifyMinimumDeposit(uint256 deposit) public returns (bool) {
    if (deposit >= 1 ether) {
        return true;
    } else {
        return false;
    }
}
```

Модульні тести, які лише перевіряють значення нижче та вище порогового значення, можуть забезпечити 100% покриття рядків/гілок, але не перевірити граничний випадок рівності (==). Рефакторинг до `deposit >= 2 ether` усе одно пройде такі тести, непомітно порушивши логіку протоколу.<sup>[[2]](#references)</sup>

Mutation testing виявляє цю прогалину, змінюючи умову та перевіряючи, чи тести завершуються невдало.

Для smart contracts мутанти, що залишаються непоміченими, часто вказують на відсутність перевірок щодо:
- Меж авторизації та ролей
- Інваріантів обліку та передавання значень
- Умов revert і шляхів обробки помилок
- Граничних умов (`==`, нульові значення, порожні масиви, максимальні/мінімальні значення)

## Оператори мутації з найвищою цінністю для безпеки

Корисні класи мутацій для аудиту контрактів:<sup>[[1]](#references)[[2]](#references)</sup>
- **Висока критичність**: заміна операторів на `revert()`, щоб виявити шляхи, які не виконуються
- **Середня критичність**: коментування рядків / видалення логіки, щоб виявити неперевірені побічні ефекти
- **Низька критичність**: непомітна заміна операторів або констант, як-от `>=` -> `>` чи `+` -> `-`
- Інші поширені зміни: заміна присвоювань, інверсія булевих значень, заперечення умов і зміна типів

Практична мета: виявити всі значущі мутанти й чітко обґрунтувати, чому мутанти, що залишилися, не мають значення або семантично еквівалентні.

## Чому мутація з урахуванням синтаксису краща за regex

Старіші рушії мутації покладалися на regex або построкові перетворення. Це працює, але має важливі обмеження:<sup>[[1]](#references)</sup>
- Багаторядкові інструкції складно безпечно мутувати
- Структура мови не розпізнається, тому коментарі/токени можуть бути вибрані некоректно
- Генерування всіх можливих варіантів для слабкого рядка марнує багато часу виконання

Інструменти на основі AST або Tree-sitter покращують цей процес, працюючи зі структурованими вузлами, а не з необробленими рядками:<sup>[[1]](#references)</sup>
- **slither-mutate** використовує AST Solidity від Slither.<sup>[[4]](#references)</sup>
- **mewt** використовує Tree-sitter як мовонезалежне ядро.<sup>[[6]](#references)</sup>
- **MuTON** побудований на основі `mewt` і забезпечує повноцінну підтримку мов TON, як-от FunC, Tolk і Tact.<sup>[[7]](#references)</sup>

Завдяки цьому мутації багаторядкових конструкцій і виразів значно надійніші, ніж підходи, що використовують лише regex.

## Запуск mutation testing за допомогою slither-mutate

Вимоги: Slither v0.10.2+.

- Переглянути параметри й мутатори:

```bash
slither-mutate --help
slither-mutate --list-mutators
```

- Приклад Foundry (зафіксуйте результати та збережіть повний журнал):<sup>[[2]](#references)</sup>

```bash
slither-mutate ./src/contracts --test-cmd="forge test" &> >(tee mutation.results)
```

- Якщо ви не використовуєте Foundry, замініть `--test-cmd` на команду, якою запускаєте тести (наприклад, `npx hardhat test`, `npm test`).

За замовчуванням артефакти зберігаються в `./mutation_campaign`. Невиявлені (ті, що вижили) мутанти копіюються туди для перевірки.<sup>[[5]](#references)</sup>

### Розуміння виводу

Рядки звіту мають такий вигляд:

```text
INFO:Slither-Mutate:Mutating contract ContractName
INFO:Slither-Mutate:[CR] Line 123: 'original line' ==> '//original line' --> UNCAUGHT
```

- Тег у квадратних дужках — це псевдонім mutator (наприклад, `CR` = Comment Replacement).
- `UNCAUGHT` означає, що тести пройшли зі зміненою поведінкою → бракує assertion.

## Скорочення часу виконання: пріоритезуйте впливові mutants

Кампанії mutation testing можуть тривати години або дні. Поради, як зменшити витрати:<sup>[[1]](#references)[[2]](#references)</sup>
- Обмежте область: почніть лише з критичних контрактів/директорій, а потім розширюйте її.
- Пріоритезуйте mutators: якщо mutant із високим пріоритетом у рядку вижив (наприклад, `revert()` або коментаризація коду), пропустіть варіанти з нижчим пріоритетом для цього рядка.
- Запускайте кампанії у два етапи: спочатку цілеспрямовані/швидкі тести, а потім повторно тестуйте лише uncaught mutants із повним набором тестів.
- За можливості зіставляйте цілі мутацій із конкретними командами тестування (наприклад, код автентифікації -> тести автентифікації).
- Коли часу обмаль, обмежте кампанії mutants із високим/середнім рівнем серйозності.
- Виконуйте тести паралельно, якщо це дозволяє ваш runner; кешуйте залежності/збірки.
- Fail-fast: зупиняйтеся рано, коли зміна чітко виявляє прогалину в assertions.

Розрахунок часу невблаганний: `1000 mutants x 5-minute tests ~= 83 hours`, тож планування кампанії не менш важливе, ніж сам mutator.<sup>[[1]](#references)</sup>

## Постійні кампанії та сортування результатів у великому масштабі

Одна з проблем старіших робочих процесів — збереження результатів лише в `stdout`. Під час тривалих кампаній це ускладнює призупинення/відновлення, фільтрування та перевірку результатів.<sup>[[1]](#references)</sup>

`mewt`/`MuTON` покращують процес, зберігаючи mutants і результати кампаній у SQLite. Переваги:<sup>[[1]](#references)</sup>
- Призупиняйте та відновлюйте тривалі запуски без втрати прогресу
- Фільтруйте лише uncaught mutants у конкретному файлі або класі мутацій
- Експортуйте/перекладайте результати у SARIF для інструментів перевірки
- Передавайте на сортування за допомогою AI менші, відфільтровані набори результатів замість необроблених логів термінала

Постійне збереження результатів особливо корисне, коли mutation testing стає частиною процесу аудиту, а не одноразовою ручною перевіркою.

## Робочий процес сортування mutants, що вижили

1) Перевірте змінений рядок і поведінку.
   - Відтворіть локально, застосувавши змінений рядок і запустивши цільовий тест.

2) Посильте тести, перевіряючи стан, а не лише повернені значення.
   - Додайте перевірки на межах рівності (наприклад, тестуйте поріг `==`).
   - Перевіряйте постумови: баланси, загальну пропозицію токенів, наслідки авторизації та згенеровані події.

3) Замініть надто поблажливі моки реалістичною поведінкою.
   - Переконайтеся, що моки відтворюють перекази, сценарії помилок і генерацію подій, які відбуваються on-chain.

4) Додайте інваріанти для fuzz-тестів.
   - Наприклад: збереження вартості, невід’ємні баланси, інваріанти авторизації, монотонність пропозиції токенів, якщо це доречно.

5) Відокремте справжні спрацювання від семантичних no-op.
   - Приклад: `x > 0` -> `x != 0` не має значення, коли `x` беззнаковий.

6) Повторюйте кампанію, доки mutants, що вижили, не будуть виявлені тестами або їхнє виживання не буде обґрунтоване.

## Практичний приклад: виявлення відсутніх перевірок стану (протокол Arkis)

Під час аудиту DeFi-протоколу Arkis кампанія мутацій виявила mutants, що вижили, зокрема:<sup>[[2]](#references)[[3]](#references)</sup>

```text
INFO:Slither-Mutate:[CR] Line 33: 'cmdsToExecute.last().value = _cmd.value' ==> '//cmdsToExecute.last().value = _cmd.value' --> UNCAUGHT
```

Коментування присвоєння не зламало тести, що довело відсутність перевірок постстану. Першопричина: код довіряв контрольованому користувачем `_cmd.value`, а не перевіряв фактичні перекази токенів. Зловмисник міг розсинхронізувати очікувані й фактичні перекази, щоб вивести кошти. Результат: високий ризик для платоспроможності протоколу.<sup>[[2]](#references)[[3]](#references)</sup>

Рекомендація: вважайте мутанти, що вижили та впливають на перекази коштів, облік або контроль доступу, високоризиковими, доки їх не буде виявлено.

## Не генеруйте тести наосліп, щоб знищити кожен мутант

Генерація тестів на основі мутацій може мати зворотний ефект, якщо поточна реалізація неправильна. Наприклад, мутація `priority >= 2` на `priority > 2` змінює поведінку, але правильне виправлення не завжди полягає в тому, щоб «написати тест для `priority == 2`». Така поведінка сама може бути помилкою.<sup>[[1]](#references)</sup>

Безпечніший робочий процес:
- Використовуйте мутанти, що вижили, щоб виявити неоднозначні вимоги
- Перевірте очікувану поведінку за специфікаціями, документацією протоколу або з рецензентами
- Лише після цього зафіксуйте поведінку в тесті/інваріанті

Інакше ви ризикуєте закріпити в наборі тестів випадкові особливості реалізації та отримати хибну впевненість.

## Практичний контрольний список

- Запустіть цільову кампанію:
  - `slither-mutate ./src/contracts --test-cmd="forge test"`
- За можливості віддавайте перевагу мутагенам, що враховують синтаксис (AST/Tree-sitter), а не лише регулярні вирази.
- Проаналізуйте мутанти, що вижили, і напишіть тести/інваріанти, які не пройдуть за зміненої поведінки.
- Перевіряйте баланси, пропозицію токенів, авторизації та події.
- Додайте граничні тести (`==`, переповнення/недоповнення, нульова адреса, нульова сума, порожні масиви).
- Замініть нереалістичні моки; змоделюйте сценарії збоїв.
- Зберігайте результати, якщо інструментарій це підтримує, і відфільтровуйте невиявлені мутанти перед аналізом.
- Використовуйте кампанії з двома етапами або окремо для кожної цілі, щоб керувати тривалістю виконання.
- Повторюйте процес, доки всі мутанти не буде знищено або обґрунтовано коментарями.
