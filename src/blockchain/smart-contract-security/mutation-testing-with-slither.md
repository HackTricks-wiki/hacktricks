# Mutation Testing για έξυπνα συμβόλαια (slither-mutate, mewt, MuTON)

{{#include ../../banners/hacktricks-training.md}}

Το Mutation Testing «δοκιμάζει τις δοκιμές σας», εισάγοντας συστηματικά μικρές αλλαγές (μεταλλάξεις) στον κώδικα των συμβολαίων και εκτελώντας ξανά τη σουίτα δοκιμών. Αν μια δοκιμή αποτύχει, η μετάλλαξη εξουδετερώνεται. Αν οι δοκιμές συνεχίσουν να περνούν, η μετάλλαξη επιβιώνει, αποκαλύπτοντας ένα τυφλό σημείο που δεν μπορεί να εντοπίσει η κάλυψη γραμμών/διακλαδώσεων.

Βασική ιδέα: Η κάλυψη δείχνει ότι εκτελέστηκε ο κώδικας· το Mutation Testing δείχνει αν η συμπεριφορά ελέγχεται πραγματικά με assertions.<sup>[[2]](#references)</sup>

## Γιατί η κάλυψη μπορεί να παραπλανήσει

Ας εξετάσουμε αυτόν τον απλό έλεγχο ορίου:

```solidity
function verifyMinimumDeposit(uint256 deposit) public returns (bool) {
    if (deposit >= 1 ether) {
        return true;
    } else {
        return false;
    }
}
```

Οι unit tests που ελέγχουν μόνο μια τιμή κάτω και μια τιμή πάνω από το όριο μπορούν να πετύχουν 100% κάλυψη γραμμών/κλάδων, χωρίς όμως να ελέγχουν την ισότητα στο όριο (==). Έτσι, μια αναδιατύπωση της συνθήκης ως `deposit >= 2 ether` θα εξακολουθούσε να περνάει αυτά τα tests, παραβιάζοντας σιωπηρά τη λογική του πρωτοκόλλου.<sup>[[2]](#references)</sup>

Οι δοκιμές μετάλλαξης αποκαλύπτουν αυτό το κενό, μεταλλάσσοντας τη συνθήκη και επαληθεύοντας ότι τα tests αποτυγχάνουν.

Στα smart contracts, τα μεταλλάγματα που επιβιώνουν συχνά αντιστοιχούν σε ελέγχους που λείπουν γύρω από:
- Εξουσιοδότηση και όρια ρόλων
- Αμετάβλητες συνθήκες λογιστικής/μεταφοράς αξίας
- Συνθήκες revert και διαδρομές αποτυχίας
- Συνθήκες ορίων (`==`, μηδενικές τιμές, κενά arrays, μέγιστες/ελάχιστες τιμές)

## Τελεστές μετάλλαξης με το υψηλότερο σήμα ασφάλειας

Χρήσιμες κατηγορίες μεταλλάξεων για τον έλεγχο συμβολαίων:<sup>[[1]](#references)[[2]](#references)</sup>
- **Υψηλή σοβαρότητα**: αντικατάσταση εντολών με `revert()` για να αποκαλυφθούν διαδρομές που δεν εκτελούνται
- **Μέτρια σοβαρότητα**: σχολιασμός γραμμών / αφαίρεση λογικής για να αποκαλυφθούν μη επαληθευμένες παρενέργειες
- **Χαμηλή σοβαρότητα**: ανεπαίσθητες αλλαγές τελεστών ή σταθερών, όπως `>=` -> `>` ή `+` -> `-`
- Άλλες συνήθεις αλλαγές: αντικατάσταση εκχώρησης, αντιστροφή boolean, άρνηση συνθήκης και αλλαγές τύπων

Πρακτικός στόχος: να εξουδετερωθούν όλα τα ουσιαστικά μεταλλάγματα και να αιτιολογηθούν ρητά όσα επιβιώνουν επειδή είναι άσχετα ή σημασιολογικά ισοδύναμα.

## Γιατί οι μεταλλάξεις με επίγνωση σύνταξης είναι καλύτερες από τα regex

Οι παλαιότερες μηχανές μετάλλαξης βασίζονταν σε regex ή σε μετασχηματισμούς προσανατολισμένους στις γραμμές. Αυτό λειτουργεί, αλλά έχει σημαντικούς περιορισμούς:<sup>[[1]](#references)</sup>
- Οι πολυγραμμικές εντολές είναι δύσκολο να μεταλλαχθούν με ασφάλεια
- Δεν γίνεται κατανόηση της δομής της γλώσσας, οπότε σχόλια/σύμβολα μπορεί να στοχοποιηθούν λανθασμένα
- Η δημιουργία κάθε πιθανού μετασχηματισμού σε μια αδύναμη γραμμή σπαταλά πολύ χρόνο εκτέλεσης

Τα εργαλεία που βασίζονται σε AST ή Tree-sitter βελτιώνουν αυτή την προσέγγιση, στοχεύοντας δομημένους κόμβους αντί για ακατέργαστες γραμμές:<sup>[[1]](#references)</sup>
- Το **slither-mutate** χρησιμοποιεί το AST της Solidity του Slither.<sup>[[4]](#references)</sup>
- Το **mewt** χρησιμοποιεί το Tree-sitter ως πυρήνα ανεξάρτητο από τη γλώσσα.<sup>[[6]](#references)</sup>
- Το **MuTON** βασίζεται στο `mewt` και προσθέτει εγγενή υποστήριξη για γλώσσες TON όπως οι FunC, Tolk και Tact.<sup>[[7]](#references)</sup>

Έτσι, οι πολυγραμμικές δομές και οι μεταλλάξεις σε επίπεδο έκφρασης γίνονται πολύ πιο αξιόπιστες από ό,τι με προσεγγίσεις που βασίζονται αποκλειστικά σε regex.

## Εκτέλεση δοκιμών μετάλλαξης με το slither-mutate

Απαιτήσεις: Slither v0.10.2+.

- Εμφάνιση επιλογών και mutators:

```bash
slither-mutate --help
slither-mutate --list-mutators
```

- Παράδειγμα Foundry (καταγράψτε τα αποτελέσματα και διατηρήστε πλήρες αρχείο καταγραφής):<sup>[[2]](#references)</sup>

```bash
slither-mutate ./src/contracts --test-cmd="forge test" &> >(tee mutation.results)
```

- Αν δεν χρησιμοποιείτε Foundry, αντικαταστήστε το `--test-cmd` με την εντολή που χρησιμοποιείτε για την εκτέλεση των tests (π.χ., `npx hardhat test`, `npm test`).

Τα artifacts αποθηκεύονται από προεπιλογή στο `./mutation_campaign`. Οι mutants που δεν εντοπίστηκαν (surviving) αντιγράφονται εκεί για επιθεώρηση.<sup>[[5]](#references)</sup>

### Κατανόηση της εξόδου

Οι γραμμές της αναφοράς μοιάζουν ως εξής:

```text
INFO:Slither-Mutate:Mutating contract ContractName
INFO:Slither-Mutate:[CR] Line 123: 'original line' ==> '//original line' --> UNCAUGHT
```

- Η ετικέτα σε αγκύλες είναι το alias του mutator (π.χ., `CR` = Comment Replacement).
- Το `UNCAUGHT` σημαίνει ότι οι δοκιμές πέρασαν με τη μεταλλαγμένη συμπεριφορά → λείπει assertion.

## Μείωση του χρόνου εκτέλεσης: δώστε προτεραιότητα στους mutants με τη μεγαλύτερη επίδραση

Οι καμπάνιες mutation testing μπορεί να διαρκέσουν ώρες ή ημέρες. Συμβουλές για μείωση του κόστους:<sup>[[1]](#references)[[2]](#references)</sup>
- Εύρος: Ξεκινήστε μόνο με κρίσιμα συμβόλαια/καταλόγους και, στη συνέχεια, επεκτείνετε το εύρος.
- Δώστε προτεραιότητα στους mutators: Αν επιβιώσει ένας mutant υψηλής προτεραιότητας σε μια γραμμή (για παράδειγμα, `revert()` ή σχολιασμός κώδικα), παραλείψτε τις παραλλαγές χαμηλότερης προτεραιότητας για αυτήν τη γραμμή.
- Χρησιμοποιήστε καμπάνιες δύο φάσεων: εκτελέστε πρώτα εστιασμένες/γρήγορες δοκιμές και, στη συνέχεια, επανελέγξτε μόνο τους mutants που δεν εντοπίστηκαν, με την πλήρη σουίτα.
- Αντιστοιχίστε, όπου είναι δυνατόν, τους στόχους μετάλλαξης σε συγκεκριμένες εντολές δοκιμών (για παράδειγμα, κώδικας auth -> δοκιμές auth).
- Όταν ο χρόνος είναι περιορισμένος, περιορίστε τις καμπάνιες σε mutants μέτριας ή υψηλής σοβαρότητας.
- Εκτελέστε τις δοκιμές παράλληλα, αν το επιτρέπει το runner σας· αποθηκεύστε στην cache τις εξαρτήσεις και τα builds.
- Fail-fast: σταματήστε νωρίς, όταν μια αλλαγή αποδεικνύει ξεκάθαρα ότι υπάρχει κενό στα assertions.

Οι υπολογισμοί του χρόνου είναι αμείλικτοι: `1000 mutants x 5-minute tests ~= 83 hours`, επομένως ο σχεδιασμός της καμπάνιας έχει εξίσου μεγάλη σημασία με τον ίδιο τον mutator.<sup>[[1]](#references)</sup>

## Επίμονες καμπάνιες και διαλογή σε μεγάλη κλίμακα

Μία αδυναμία των παλαιότερων ροών εργασίας είναι ότι τα αποτελέσματα καταγράφονται μόνο στο `stdout`. Σε καμπάνιες μεγάλης διάρκειας, αυτό δυσκολεύει την παύση/συνέχιση, το φιλτράρισμα και την ανασκόπηση.<sup>[[1]](#references)</sup>

Τα `mewt`/`MuTON` το βελτιώνουν αυτό αποθηκεύοντας mutants και αποτελέσματα σε καμπάνιες που βασίζονται στο SQLite. Οφέλη:<sup>[[1]](#references)</sup>
- Παύση και συνέχιση εκτελέσεων μεγάλης διάρκειας χωρίς απώλεια προόδου
- Φιλτράρισμα μόνο των mutants που δεν εντοπίστηκαν σε συγκεκριμένο αρχείο ή κλάση μεταλλάξεων
- Εξαγωγή/μετάφραση αποτελεσμάτων σε SARIF για εργαλεία ανασκόπησης
- Παροχή μικρότερων, φιλτραρισμένων συνόλων αποτελεσμάτων για διαλογή με τη βοήθεια AI, αντί για ακατέργαστα αρχεία καταγραφής τερματικού

Τα επίμονα αποτελέσματα είναι ιδιαίτερα χρήσιμα όταν το mutation testing γίνεται μέρος μιας ροής ελέγχου ασφαλείας και όχι μια μεμονωμένη χειροκίνητη ανασκόπηση.

## Ροή εργασίας για τη διαλογή mutants που επιβιώνουν

1) Εξετάστε τη μεταλλαγμένη γραμμή και τη συμπεριφορά της.
   - Αναπαραγάγετέ την τοπικά εφαρμόζοντας τη μεταλλαγμένη γραμμή και εκτελώντας μια εστιασμένη δοκιμή.

2) Ενισχύστε τις δοκιμές ώστε να ελέγχουν την κατάσταση και όχι μόνο τις τιμές επιστροφής.
   - Προσθέστε ελέγχους στα όρια ισότητας (π.χ., δοκιμάστε το όριο `==`).
   - Ελέγξτε τις μετασυνθήκες: υπόλοιπα, συνολική προσφορά, επιπτώσεις στην εξουσιοδότηση και εκπεμπόμενα συμβάντα.

3) Αντικαταστήστε τα υπερβολικά επιτρεπτικά mocks με ρεαλιστική συμπεριφορά.
   - Βεβαιωθείτε ότι τα mocks εφαρμόζουν τις μεταφορές, τις διαδρομές αποτυχίας και τις εκπομπές συμβάντων που συμβαίνουν on-chain.

4) Προσθέστε invariants στις δοκιμές fuzz.
   - Π.χ., διατήρηση αξίας, μη αρνητικά υπόλοιπα, invariants εξουσιοδότησης και μονοτονική προσφορά, όπου εφαρμόζεται.

5) Διαχωρίστε τα αληθώς θετικά αποτελέσματα από τις σημασιολογικά αδρανείς αλλαγές.
   - Παράδειγμα: `x > 0` -> `x != 0` δεν έχει σημασία όταν το `x` είναι unsigned.

6) Εκτελέστε ξανά την καμπάνια μέχρι να εξουδετερωθούν οι mutants που επιβιώνουν ή να αιτιολογηθεί ρητά η διατήρησή τους.

## Μελέτη περίπτωσης: αποκάλυψη ελλιπών ελέγχων κατάστασης (πρωτόκολλο Arkis)

Μια καμπάνια mutation testing κατά τη διάρκεια ελέγχου ασφαλείας του DeFi πρωτοκόλλου Arkis αποκάλυψε mutants που επιβίωσαν, όπως:<sup>[[2]](#references)[[3]](#references)</sup>

```text
INFO:Slither-Mutate:[CR] Line 33: 'cmdsToExecute.last().value = _cmd.value' ==> '//cmdsToExecute.last().value = _cmd.value' --> UNCAUGHT
```

Το να σχολιάσουμε την ανάθεση δεν απέτυχε τις δοκιμές, αποδεικνύοντας ότι έλειπαν assertions για την κατάσταση μετά την εκτέλεση. Βασική αιτία: ο κώδικας εμπιστευόταν ένα `_cmd.value` που ελεγχόταν από τον χρήστη, αντί να επικυρώνει τις πραγματικές μεταφορές token. Ένας επιτιθέμενος μπορούσε να προκαλέσει ασυμφωνία ανάμεσα στις αναμενόμενες και τις πραγματικές μεταφορές, ώστε να αποστραγγίσει κεφάλαια. Αποτέλεσμα: υψηλός κίνδυνος για τη φερεγγυότητα του πρωτοκόλλου.<sup>[[2]](#references)[[3]](#references)</sup>

Οδηγία: Αντιμετωπίζετε τους mutants που επιβιώνουν και επηρεάζουν μεταφορές αξίας, λογιστική ή έλεγχο πρόσβασης ως υψηλού κινδύνου μέχρι να εξουδετερωθούν.

## Μη δημιουργείτε τυφλά δοκιμές για να εξουδετερώσετε κάθε mutant

Η δημιουργία δοκιμών βάσει μεταλλάξεων μπορεί να έχει τα αντίθετα αποτελέσματα, αν η τρέχουσα υλοποίηση είναι λανθασμένη. Παράδειγμα: η μετάλλαξη του `priority >= 2` σε `priority > 2` αλλάζει τη συμπεριφορά, αλλά η σωστή διόρθωση δεν είναι πάντα «γράψτε μια δοκιμή για `priority == 2`». Αυτή η συμπεριφορά μπορεί να είναι η ίδια το σφάλμα.<sup>[[1]](#references)</sup>

Ασφαλέστερη ροή εργασίας:
- Χρησιμοποιήστε τους mutants που επιβιώνουν για να εντοπίσετε ασαφείς απαιτήσεις
- Επικυρώστε την αναμενόμενη συμπεριφορά βάσει προδιαγραφών, τεκμηρίωσης πρωτοκόλλου ή αξιολογητών
- Μόνο τότε κωδικοποιήστε τη συμπεριφορά ως δοκιμή/invariant

Διαφορετικά, υπάρχει κίνδυνος να ενσωματώσετε κατά λάθος της υλοποίησης στη σουίτα δοκιμών και να αποκτήσετε ψευδή εμπιστοσύνη.

## Πρακτική λίστα ελέγχου

- Εκτελέστε μια στοχευμένη εκστρατεία:
  - `slither-mutate ./src/contracts --test-cmd="forge test"`
- Προτιμήστε mutators που λαμβάνουν υπόψη τη σύνταξη (AST/Tree-sitter) αντί για μεταλλάξεις που βασίζονται μόνο σε regex, όταν είναι διαθέσιμες.
- Διαλογή των mutants που επιβιώνουν και γράψτε δοκιμές/invariants που θα αποτύγχαναν με τη μεταλλαγμένη συμπεριφορά.
- Ελέγξτε υπόλοιπα, προσφορά, εξουσιοδοτήσεις και events.
- Προσθέστε δοκιμές οριακών περιπτώσεων (`==`, υπερχειλίσεις/υποχειλίσεις, μηδενική διεύθυνση, μηδενικό ποσό, κενά arrays).
- Αντικαταστήστε τα μη ρεαλιστικά mocks· προσομοιώστε τρόπους αποτυχίας.
- Διατηρήστε τα αποτελέσματα όταν το tooling το υποστηρίζει και φιλτράρετε τους mutants που δεν έχουν εντοπιστεί πριν από τη διαλογή.
- Χρησιμοποιήστε εκστρατείες δύο φάσεων ή ανά στόχο, ώστε να διατηρήσετε διαχειρίσιμο τον χρόνο εκτέλεσης.
- Επαναλάβετε μέχρι να εξουδετερωθούν όλοι οι mutants ή να αιτιολογηθούν με σχόλια και σκεπτικό.
