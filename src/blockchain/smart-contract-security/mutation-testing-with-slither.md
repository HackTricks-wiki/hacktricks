# Mutation Testing для Smart Contracts (slither-mutate, mewt, MuTON)

{{#include ../../banners/hacktricks-training.md}}

Mutation testing «тестує ваші тести», систематично вносячи невеликі зміни (мутації) до коду контракту та повторно запускаючи набір тестів. Якщо тест завершується помилкою, мутацію знищено. Якщо тести все ще проходять, мутація виживає, виявляючи сліпу зону, яку неможливо виявити за допомогою покриття рядків/гілок.

Ключова ідея: Coverage показує, що код було виконано; mutation testing показує, чи справді його поведінку перевірено.<sup>[[2]](#references)</sup>

## Чому coverage може вводити в оману

Розглянемо цю просту перевірку порогу:
```solidity
function verifyMinimumDeposit(uint256 deposit) public returns (bool) {
if (deposit >= 1 ether) {
return true;
} else {
return false;
}
}
```
Модульні тести, які перевіряють лише значення нижче та значення вище порогового значення, можуть досягти 100% покриття рядків/гілок, не перевіряючи межу рівності (==). Рефакторинг до `deposit >= 2 ether` усе ще пройде такі тести, непомітно порушивши логіку протоколу.<sup>[[2]](#references)</sup>

Mutation testing виявляє цю прогалину, мутуючи умову та перевіряючи, що тести завершуються невдало.

Для смарт-контрактів мутанти, що вижили, часто вказують на відсутність перевірок щодо:
- Авторизації та меж ролей
- Інваріантів обліку/передавання значень
- Умов revert і шляхів помилок
- Граничних умов (`==`, нульові значення, порожні масиви, максимальні/мінімальні значення)

## Mutation operators with the highest security signal

Корисні класи мутацій для аудиту контрактів:<sup>[[1]](#references)[[2]](#references)</sup>
- **Висока критичність**: заміна операторів на `revert()` для виявлення невиконаних шляхів
- **Середня критичність**: закоментувати рядки / видалити логіку, щоб виявити неперевірені побічні ефекти
- **Низька критичність**: непомітні заміни операторів або констант, як-от `>=` -> `>` або `+` -> `-`
- Інші поширені зміни: заміна присвоювань, інверсія boolean-значень, заперечення умов і зміни типів

Практична мета: знищити всі суттєві мутанти та явно обґрунтувати мутанти, що вижили, якщо вони нерелевантні або семантично еквівалентні.

## Why syntax-aware mutation is better than regex

Старіші mutation engines покладалися на regex або перетворення, орієнтовані на рядки. Це працює, але має важливі обмеження:<sup>[[1]](#references)</sup>
- Багаторядкові оператори складно безпечно мутувати
- Структура мови не враховується, тому коментарі/токени можуть бути неправильно вибрані
- Генерування кожного можливого варіанта на слабкому рядку витрачає значні обсяги runtime

Інструменти на основі AST або Tree-sitter покращують це, обираючи структуровані вузли замість необроблених рядків:<sup>[[1]](#references)</sup>
- **slither-mutate** використовує Solidity AST Slither.<sup>[[4]](#references)</sup>
- **mewt** використовує Tree-sitter як language-agnostic ядро.<sup>[[6]](#references)</sup>
- **MuTON** побудований на `mewt` і додає first-class support для мов TON, таких як FunC, Tolk і Tact.<sup>[[7]](#references)</sup>

Це робить мутації багаторядкових конструкцій і рівня виразів набагато надійнішими, ніж підходи, що використовують лише regex.

## Running mutation testing with slither-mutate

Вимоги: Slither v0.10.2+.

- Переглянути опції та мутаторів:
```bash
slither-mutate --help
slither-mutate --list-mutators
```
- Приклад Foundry (зберігати результати та повний log):<sup>[[2]](#references)</sup>
```bash
slither-mutate ./src/contracts --test-cmd="forge test" &> >(tee mutation.results)
```
- Якщо ви не використовуєте Foundry, замініть `--test-cmd` на команду, за допомогою якої ви запускаєте тести (наприклад, `npx hardhat test`, `npm test`).

За замовчуванням артефакти зберігаються в `./mutation_campaign`. Неперехоплені (ті, що вижили) mutants копіюються туди для перевірки.<sup>[[5]](#references)</sup>

### Розуміння результатів

Рядки звіту мають такий вигляд:
```text
INFO:Slither-Mutate:Mutating contract ContractName
INFO:Slither-Mutate:[CR] Line 123: 'original line' ==> '//original line' --> UNCAUGHT
```
- Тег у квадратних дужках — це alias мутатора (наприклад, `CR` = Comment Replacement).
- `UNCAUGHT` означає, що тести пройшли за мутованої поведінки → відсутня перевірка.

## Зменшення часу виконання: пріоритизація впливових мутантів

Mutation campaigns можуть тривати годинами або днями. Поради для зменшення витрат:<sup>[[1]](#references)[[2]](#references)</sup>
- Область охоплення: починайте лише з критичних контрактів/директорій, а потім розширюйте охоплення.
- Пріоритизація мутаторів: якщо мутант із високим пріоритетом у рядку виживає (наприклад, `revert()` або comment-out), пропустіть варіанти з нижчим пріоритетом для цього рядка.
- Використовуйте двофазні кампанії: спочатку запускайте сфокусовані/швидкі тести, потім повторно тестуйте лише неперехоплені мутанти з повним набором тестів.
- За можливості зіставляйте цілі мутації з конкретними командами тестування (наприклад, код auth -> auth tests).
- Якщо час обмежений, обмежуйте кампанії мутантами з високою/середньою severity.
- Виконуйте тести паралельно, якщо ваш runner це підтримує; кешуйте dependencies/builds.
- Fail-fast: зупиняйтеся на ранньому етапі, коли зміна явно демонструє прогалину в перевірках.

Математика часу виконання жорстка: `1000 mutants x 5-minute tests ~= 83 hours`, тому дизайн кампанії має не менше значення, ніж сам мутатор.<sup>[[1]](#references)</sup>

## Постійні кампанії та triage у великих масштабах

Однією з проблем старих workflow є виведення результатів лише до `stdout`. Для тривалих кампаній це ускладнює призупинення/відновлення, фільтрацію та перевірку результатів.<sup>[[1]](#references)</sup>

`mewt`/`MuTON` покращують це, зберігаючи мутанти та результати в кампаніях на базі SQLite. Переваги:<sup>[[1]](#references)</sup>
- Призупинення та відновлення тривалих запусків без втрати прогресу
- Фільтрація лише неперехоплених мутантів у певному файлі або класі мутації
- Експорт/переклад результатів у SARIF для інструментів review
- Надання AI-assisted triage менших, відфільтрованих наборів результатів замість необроблених логів термінала

Постійні результати особливо корисні, коли mutation testing стає частиною audit pipeline, а не одноразовою ручною перевіркою.

## Workflow triage для мутантів, що вижили

1) Перевірте мутований рядок і поведінку.
- Відтворіть проблему локально, застосувавши мутований рядок і запустивши сфокусований тест.

2) Посильте тести, щоб вони перевіряли стан, а не лише значення, що повертаються.
- Додайте перевірки межі рівності (наприклад, тест для порога `==`).
- Перевіряйте post-conditions: баланси, total supply, наслідки авторизації та згенеровані events.

3) Замініть надто permissive mocks на реалістичну поведінку.
- Переконайтеся, що mocks застосовують transfers, failure paths і event emissions, які відбуваються on-chain.

4) Додайте invariants для fuzz tests.
- Наприклад, conservation of value, невід’ємні баланси, authorization invariants і монотонний supply, якщо це застосовно.

5) Відокремлюйте true positives від semantic no-ops.
- Приклад: `x > 0` -> `x != 0` не має значення, коли `x` є unsigned.

6) Повторюйте кампанію, доки мутанти, що вижили, не будуть усунені або явно обґрунтовані.

## Практичний приклад: виявлення відсутніх перевірок стану (Arkis protocol)

Mutation campaign під час аудиту DeFi protocol Arkis виявила мутантів, що вижили, наприклад:<sup>[[2]](#references)[[3]](#references)</sup>
```text
INFO:Slither-Mutate:[CR] Line 33: 'cmdsToExecute.last().value = _cmd.value' ==> '//cmdsToExecute.last().value = _cmd.value' --> UNCAUGHT
```
Закоментування присвоєння не зламало тести, що доводить відсутність post-state assertions. Першопричина: код довіряв контрольованому користувачем `_cmd.value`, а не перевіряв фактичні перекази токенів. Атакер міг розсинхронізувати очікувані та фактичні перекази, щоб вивести кошти. Результат: ризик високої критичності для платоспроможності протоколу.<sup>[[2]](#references)[[3]](#references)</sup>

Рекомендація: вважайте mutants, що вижили та впливають на перекази вартості, облік або контроль доступу, високоризиковими, доки їх не буде вбито.

## Не генеруйте тести наосліп, щоб убити кожен mutant

Генерація тестів на основі mutation testing може мати зворотний ефект, якщо поточна реалізація неправильна. Наприклад, мутація `priority >= 2` на `priority > 2` змінює поведінку, але правильним виправленням не завжди є "написати тест для `priority == 2`". Така поведінка сама може бути помилкою.<sup>[[1]](#references)</sup>

Безпечніший робочий процес:
- Використовуйте mutants, що вижили, щоб виявити неоднозначні вимоги
- Перевіряйте очікувану поведінку за специфікаціями, документацією протоколу або з ревʼюерами
- Лише після цього кодуйте поведінку як тест/invariant

Інакше ви ризикуєте жорстко закріпити випадкові особливості реалізації в наборі тестів і отримати хибну впевненість.

## Практичний контрольний список

- Запустіть targeted campaign:
- `slither-mutate ./src/contracts --test-cmd="forge test"`
- За можливості надавайте перевагу syntax-aware mutators (AST/Tree-sitter), а не мутації лише на основі regex.
- Проведіть triage mutants, що вижили, і напишіть тести/invariants, які завершувалися б помилкою за зміненої поведінки.
- Перевіряйте баланси, supply, авторизації та events.
- Додайте boundary tests (`==`, переповнення/витік, zero-address, zero-amount, порожні масиви).
- Замініть нереалістичні mocks; моделюйте failure modes.
- Зберігайте результати, якщо tooling це підтримує, і відфільтровуйте mutants, які не були перехоплені, до triage.
- Використовуйте двофазні кампанії або кампанії для кожної цілі, щоб зберегти прийнятний час виконання.
- Повторюйте процес, доки всі mutants не буде вбито або обґрунтовано коментарями та поясненням.
