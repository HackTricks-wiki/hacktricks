# Розбіжність стану та обходи авторизації через значення за замовчуванням

{{#include ../../banners/hacktricks-training.md}}

Авторизація іноді залежить від похідного економічного стану, а не від явної ролі — наприклад, «викликач володіє всім запасом». Якщо значення в цьому предикаті надходять із різних сховищ, застаріла копія може перетворити легітимне спрощення для власника на обхід авторизації. Модуль Provenance marker продемонстрував небезпечне поєднання: актуальний баланс викликача порівнювався з локальними метаданими запасу маркера, які не оновлювалися для активів із нефіксованим запасом.<sup>[[1]](#references)</sup>

## Перевіряйте дубльований стан як межу авторизації

Для кожного значення, що використовується під час перевірки прав доступу, перелічіть **усі представлення**: канонічний стан модуля, поля об’єктів, кешовані агрегати, індекси, знімки, записи мостів і позаланцюгові копії. Потім простежте всі шляхи створення, карбування, спалювання, передавання, скидання, міграції та синхронізації, щоб визначити, яка копія оновлюється в кожному режимі об’єкта. Поле може бути авторитетним для одного режиму й лише інформаційним для іншого.<sup>[[1]](#references)</sup>

Практичний порядок перевірки:<sup>[[1]](#references)</sup>

1. Знайдіть захищені дії та зведіть кожну гілку авторизації до булевого предиката.
2. Для кожного операнда зафіксуйте його сховище, шляхи оновлення, стани життєвого циклу та джерело істини.
3. Змоделюйте переходи, що оновлюють лише одне представлення, а потім порівняйте всі копії.
4. Після кожного переходу спробуйте виконати захищену дію з нового облікового запису.
5. Не зупиняйтеся на обході: якщо дія змінює ACL, надайте собі постійні ролі й викличте звичайні привілейовані API.

Підозрілі шаблони: `cachedSupply == balance`, `metadataOwner == caller` або `snapshotShares == currentShares`, якщо правила синхронізації сторін відрізняються. Отримання авторитетного значення для одного операнда не робить порівняння безпечним, коли інший операнд застарів.<sup>[[1]](#references)</sup>

## Обхід через рівність значень за замовчуванням

Предикат рівності також небезпечний, якщо обидва операнди незалежно можуть набувати однакового значення за замовчуванням. Наведена нижче перевірка надає «повний контроль над запасом» будь-якому порожньому обліковому запису, коли `supply` дорівнює нулю, незалежно від того, чи нульове значення спричинене застарілими метаданими, чи об’єкт справді не має фінансування.<sup>[[1]](#references)[[3]](#references)</sup>

```go
balance := bank.GetBalance(ctx, caller, denom)
supply := marker.GetSupply() // duplicate or stale representation
return balance.Amount.Equal(supply.Amount) // 0 == 0 -> true
```

Перехід на канонічне сховище усуває розбіжність, але **не вирішує проблему порожнього об'єкта**. Властивість безпеки має включати незалежну умову валідності; патч Provenance використовує актуальну пропозицію токенів у банку й відхиляє nil або нульову пропозицію перед порівнянням балансу викликувача.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>

```go
supply := bank.GetSupply(ctx, denom)
if supply.Amount.IsNil() || supply.Amount.IsZero() {
    return false
}
balance := bank.GetBalance(ctx, caller, denom)
return supply.Equal(NewCoin(denom, balance.Amount))
```

Застосовуйте ті самі міркування до кількості голосів, часток власності, боргу, застави, епох, nonce, часових позначок і лічильників: `callerValue == protectedValue` не має надавати caller права, доки захищене значення не буде незалежно перевірене й не належатиме до очікуваного домену.<sup>[[1]](#references)</sup>

## Захоплення ACL для виконання легітимних привілейованих операцій

Обхід в операції редагування ACL — це примітив для стійкого підвищення привілеїв. У випадку Provenance обліковий запис без привілеїв і з нульовою кількістю токенів міг пройти перевірку пропозиції `0 == 0`, надати собі адміністративні права, права на мінтинг і виведення коштів, а потім використати звичайні обробники повідомлень для мінтингу активів або виведення коштів з ескроу. Тому після зміни ACL для експлойту не потрібна була друга вразливість.<sup>[[1]](#references)</sup>

Загальна послідовність експлуатації:<sup>[[1]](#references)</sup>

1. Знайдіть об’єкт, поле якого не є авторитетним і відрізняється від актуального стану, або захищене значення якого є значенням за замовчуванням.
2. Використайте нову/порожню ідентичність, щоб її локальне значення збігалося із застарілим значенням або значенням за замовчуванням.
3. Викличте кінцеву точку керування ролями, передавання права власності або оновлення політики та надайте собі стійкі можливості.
4. Перевірте, чи збереглися зміни, прочитавши ACL із канонічного стану.
5. Виконайте легітимну операцію з високим впливом (мінтинг, виведення коштів, оновлення, передавання права власності або зміну політики).

Під час оцінювання впливу перевірте всі можливості, доступні через нову роль, а не зупиняйтеся на обході авторизації. Рахунки на кшталт ескроу можуть зберігати активи, не пов’язані з об’єктом, застарілі метадані якого дали змогу захопити контроль.<sup>[[1]](#references)</sup>

## Цільові інваріанти та stateful fuzzing

Описуйте авторизацію незалежно від реалізації. Для скороченого шляху повної пропозиції мінімальний інваріант такий:<sup>[[1]](#references)[[2]](#references)</sup>

```text
controlsAllSupply(caller, asset) == true
    => authoritativeSupply(asset) > 0
    && authoritativeBalance(caller, asset) == authoritativeSupply(asset)
```

Використовуйте model/state-machine fuzzer для генерації послідовностей, а не ізольованих викликів, що охоплюють створення, ініціалізацію нульовими значеннями, активацію/фіналізацію, minting, burning, перекази, скидання, міграції, sync-виклики та зміни ACL. Після кожного переходу порівнюйте дубльовані представлення й перевіряйте, що новий обліковий запис не може виконати жодну захищену дію. Додайте окремі тестові випадки для нуля, однієї одиниці, часткового володіння, повного володіння, застарілих занижених і завищених значень.<sup>[[1]](#references)[[2]](#references)</sup>

Високоінформативні регресійні властивості:<sup>[[1]](#references)[[2]](#references)</sup>

- Нульова авторитетна пропозиція ніколи не означає володіння чи адміністрування.
- Власники частки не можуть стати адміністраторами, коли дубльована пропозиція дорівнює їхньому балансу.
- Справжній повний власник зберігає передбачений обхідний механізм, якщо поточна пропозиція позитивна.
- Невдалі спроби надати права самому собі не змінюють ACL і не активують подальші привілейовані виклики.
- Зміни режиму не можуть непомітно змінити, яке представлення перевірка авторизації вважає авторитетним.
