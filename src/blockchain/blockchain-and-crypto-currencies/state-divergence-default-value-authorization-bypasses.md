# Розбіжність стану та обходи авторизації через значення за замовчуванням

{{#include ../../banners/hacktricks-training.md}}

Авторизація іноді залежить від похідного економічного стану, а не від явно заданої ролі — наприклад, «викликач володіє всім запасом». Якщо значення в цьому предикаті надходять із різних сховищ, застаріла копія може перетворити легітимне скорочення перевірки права власності на обхід авторизації. Модуль Provenance marker продемонстрував небезпечне поєднання: актуальний баланс викликача порівнювався з локальними метаданими запасу маркера, які не оновлювалися для активів із нефіксованим запасом.<sup>[[1]](#references)</sup>

## Перевіряйте дубльований стан як межу авторизації

Для кожного значення, що використовується перевіркою дозволів, перелічіть **усі представлення**: канонічний стан модуля, поля об’єктів, кешовані агрегати, індекси, знімки, записи bridge і off-chain дзеркала. Потім простежте кожен шлях створення, mint, burn, transfer, reset, міграції та синхронізації, щоб визначити, яка копія оновлюється в кожному режимі об’єкта. Поле може бути авторитетним для одного режиму та інформаційним для іншого.<sup>[[1]](#references)</sup>

Практичний процес перевірки:<sup>[[1]](#references)</sup>

1. Знайдіть захищені дії та зведіть кожну гілку авторизації до булевого предиката.
2. Для кожного операнда зафіксуйте його сховище, шляхи оновлення, стани життєвого циклу та джерело істини.
3. Згенеруйте переходи, які оновлюють лише одне представлення, а потім порівняйте всі копії.
4. Спробуйте виконати захищену дію з нового акаунта після кожного переходу.
5. Продовжуйте перевірку після обходу: якщо дія редагує ACL, надайте собі постійні ролі та викличте звичайні privileged API.

Підозрілі шаблони включають `cachedSupply == balance`, `metadataOwner == caller` або `snapshotShares == currentShares`, якщо обидві сторони мають різні правила синхронізації. Отримання авторитетного значення для одного операнда не робить порівняння безпечним, якщо інший операнд є застарілим.<sup>[[1]](#references)</sup>

## Обхід через рівність значень за замовчуванням

Предикат рівності також є небезпечним, коли обидва операнди можуть незалежно отримати однакове значення за замовчуванням. Перевірка нижче надає «повний контроль над запасом» будь-якому порожньому акаунту, коли `supply` дорівнює нулю, незалежно від того, чи є нуль наслідком застарілих метаданих, чи легітимно нефінансованого об’єкта.<sup>[[1]](#references)[[3]](#references)</sup>
```go
balance := bank.GetBalance(ctx, caller, denom)
supply := marker.GetSupply() // duplicate or stale representation
return balance.Amount.Equal(supply.Amount) // 0 == 0 -> true
```
Перехід до канонічного сховища усуває розбіжність, але **не** вирішує випадок порожнього об’єкта. Властивість безпеки має містити незалежну умову чинності; patch Provenance використовує актуальну пропозицію банку та відхиляє nil або нульову пропозицію до порівняння балансу caller.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
```go
supply := bank.GetSupply(ctx, denom)
if supply.Amount.IsNil() || supply.Amount.IsZero() {
return false
}
balance := bank.GetBalance(ctx, caller, denom)
return supply.Equal(NewCoin(denom, balance.Amount))
```
Застосовуйте те саме міркування до кількості голосів для кворуму, відсотків володіння, боргу, застави, епох, nonce, часових міток і лічильників: `callerValue == protectedValue` не має авторизувати caller, доки захищене значення не буде незалежно валідним і не належатиме до очікуваного домену.<sup>[[1]](#references)</sup>

## Захоплення ACL для легітимних привілейованих операцій

Обхід в операції редагування ACL є стійким примітивом ескалації привілеїв. У випадку Provenance непривілейований акаунт із нульовою кількістю токенів міг пройти перевірку застарілого `0 == 0`, надати собі адміністративні дозволи, дозволи на mint і withdrawal, а потім використати звичайні message handlers для mint активів або withdrawal з escrow. Тому після зміни ACL для експлуатації не була потрібна жодна друга вразливість.<sup>[[1]](#references)</sup>

Загальна послідовність експлуатації:<sup>[[1]](#references)</sup>

1. Знайдіть об’єкт, поле якого не є authoritative і відрізняється від актуального стану, або захищене значення якого є значенням за замовчуванням.
2. Використайте нову/порожню identity, щоб її локальне значення збігалося з цим застарілим/значенням за замовчуванням.
3. Викличте endpoint керування ролями, передачі ownership або оновлення policy і надайте собі довготривалі capabilities.
4. Підтвердьте збереження, прочитавши ACL із canonical state.
5. Викличте легітимну операцію з високим впливом (mint, withdrawal, upgrade, передача ownership або зміна policy).

Під час оцінювання впливу перевіряйте кожну capability, доступну через нову роль, а не зупиняйтеся лише на обході авторизації. Акаунти на кшталт escrow можуть зберігати активи, не пов’язані з об’єктом, чиї застарілі metadata уможливили захоплення.<sup>[[1]](#references)</sup>

## Цілі для перевірки інваріантів і stateful-fuzzing

Визначайте авторизацію незалежно від реалізації. Для shortcut повної supply мінімальний інваріант має виглядати так:<sup>[[1]](#references)[[2]](#references)</sup>
```text
controlsAllSupply(caller, asset) == true
=> authoritativeSupply(asset) > 0
&& authoritativeBalance(caller, asset) == authoritativeSupply(asset)
```
Використовуйте model/state-machine fuzzer для генерування послідовностей, а не ізольованих викликів, охоплюючи створення, ініціалізацію нульовим значенням, активацію/завершення, minting, burning, transfers, скидання, міграції, sync calls і зміни ACL. Після кожного переходу порівнюйте дубльовані представлення та перевіряйте, що новий обліковий запис не може виконати жодну захищену дію. Додайте явні випадки для нульового значення, однієї одиниці, часткового володіння, повного володіння, застарілого малого та застарілого великого значень.<sup>[[1]](#references)[[2]](#references)</sup>

Властивості регресії з високою сигнальністю:<sup>[[1]](#references)[[2]](#references)</sup>

- Нульова authoritative supply ніколи не означає володіння або адміністрування.
- Власники часткової кількості не можуть стати адміністраторами, коли duplicate supply дорівнює їхньому балансу.
- Справжній full holder зберігає передбачений shortcut, коли live supply є додатною.
- Невдалі self-grants не змінюють ACL і не вмикають подальші privileged calls.
- Зміни режиму не можуть непомітно змінити те, яке представлення authorization check вважає authoritative.
