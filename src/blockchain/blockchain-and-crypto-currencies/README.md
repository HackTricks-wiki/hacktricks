## 基本概念

- **Smart Contracts**は、特定の条件が満たされるとブロックチェーン上で実行されるプログラムであり、仲介者を介さずに合意内容の実行を自動化します。
- **Decentralized Applications (dApps)**は、使いやすいフロントエンドと、透明性が高く監査可能なバックエンドを備え、smart contractsを基盤として構築されます。
- **Tokens & Coins**は、coinがデジタルマネーとして機能する一方、tokenは特定の用途における価値や所有権を表す点で異なります。
  - **Utility Tokens**はサービスへのアクセスを提供し、**Security Tokens**は資産の所有権を示します。
- **DeFi**はDecentralized Financeの略で、中央機関を介さない金融サービスを提供します。
- **DEX**と**DAOs**は、それぞれDecentralized Exchange PlatformsとDecentralized Autonomous Organizationsを指します。

暗号資産市場で使われる現物注文、先物、レバレッジ、オプションの用語については、[投資用語](investment-terms.md)を参照してください。

## コンセンサスメカニズム

コンセンサスメカニズムは、ブロックチェーン上で安全かつ合意に基づいて取引を検証します。

- **Proof of Work (PoW)**は、取引の検証に計算能力を利用します。
- **Proof of Stake (PoS)**では、validatorが一定量のtokenを保有する必要があり、PoWと比べてエネルギー消費を削減できます。<sup>[[1]](#references)</sup>

## Bitcoinの基本

### 取引

Bitcoinの取引では、アドレス間で資金を移転します。取引はデジタル署名によって検証され、秘密鍵の所有者だけが送金を開始できるようになっています。<sup>[[2]](#references)</sup>

#### 主な構成要素：

- **Multisignature Transactions**では、取引の承認に複数の署名が必要です。<sup>[[3]](#references)</sup>
- 取引は、**inputs**（資金源）、**outputs**（送金先）、**fees**（minerに支払う手数料）、**scripts**（取引ルール）で構成されます。

### Lightning Network

channel内で複数の取引を可能にし、最終状態のみをブロックチェーンに送信することで、Bitcoinのスケーラビリティ向上を目指します。

## Bitcoinのプライバシーに関する懸念

**Common Input Ownership**や**UTXO Change Address Detection**などのプライバシー攻撃は、取引パターンを悪用します。**Mixers**や**CoinJoin**などの手法は、ユーザー間の取引のつながりを隠すことで匿名性を高めます。

## 匿名でBitcoinを入手する

現金取引、mining、mixerの利用などの方法があります。**CoinJoin**は複数の取引を混ぜて追跡を困難にし、**PayJoin**はCoinJoinを通常の取引に見せかけてプライバシーをさらに高めます。

# Bitcoinのプライバシー攻撃の概要

Bitcoinの世界では、取引のプライバシーやユーザーの匿名性がしばしば懸念されます。ここでは、攻撃者がBitcoinのプライバシーを侵害する一般的な手法を簡潔に紹介します。<sup>[[6]](#references)</sup>

## **共通入力の所有者に関する仮定**

異なるユーザーのinputsが1つの取引にまとめられることは、複雑さのため一般にまれです。そのため、**同じ取引に含まれる2つの入力アドレスは、同じ所有者のものと仮定されることがよくあります**。

## **UTXOのお釣りアドレスの検出**

UTXO（**Unspent Transaction Output**）は、取引で全額を使用する必要があります。一部だけを別のアドレスに送ると、残額は新しいお釣りアドレスに送られます。観察者は、この新しいアドレスが送信者のものだと推測できるため、プライバシーが侵害される可能性があります。

### 例

これを軽減するには、mixerサービスや複数のアドレスを使うことで、所有者を特定しにくくできます。

## **ソーシャルネットワークやフォーラムでの公開**

ユーザーがオンラインでBitcoinアドレスを共有することがあり、その結果、**アドレスと所有者を簡単に結び付けられる**ようになります。

## **取引グラフ分析**

取引をグラフとして可視化することで、資金の流れに基づき、ユーザー間のつながりを推測できます。

## **不要な入力のヒューリスティック（最適なお釣りのヒューリスティック）**

このヒューリスティックでは、複数のinputsとoutputsを持つ取引を分析し、どのoutputがお釣りとして送信者に戻るのかを推測します。

### 例

```bash
2 btc --> 4 btc
3 btc     1 btc
```

入力を追加した結果、change outputがどの単一の入力よりも大きくなると、ヒューリスティックを混乱させる可能性があります。

## **強制的なアドレス再利用**

攻撃者は、受取人が今後のトランザクションでこれらを他の入力と統合することを期待して、以前に使用されたアドレスに少額を送金し、アドレス同士を関連付けようとすることがあります。

### 正しいウォレットの動作

ウォレットは、このプライバシー漏えいを防ぐため、すでに使用済みで残高がゼロのアドレスで受け取ったコインを使用しないようにするべきです。

## **その他のブロックチェーン分析手法**

- **正確な支払額:** changeのないトランザクションは、同一ユーザーが所有する2つのアドレス間で行われた可能性があります。
- **きりのよい金額:** トランザクションの金額がきりのよい数字であれば、支払いである可能性があり、きりのよくない金額の出力がchangeである可能性があります。
- **ウォレットのフィンガープリンティング:** ウォレットごとにトランザクション作成パターンが異なるため、分析者は使用されたソフトウェアを特定し、change addressを推測できる可能性があります。
- **金額とタイミングの相関:** トランザクションの時刻や金額を明かすと、トランザクションが追跡可能になることがあります。

## **トラフィック分析**

ネットワークトラフィックを監視することで、攻撃者はトランザクションやブロックをIPアドレスに関連付け、ユーザーのプライバシーを侵害できる可能性があります。多数のBitcoinノードを運用する組織では、トランザクションを監視する能力が高まるため、特にその可能性があります。

# 匿名でのBitcoinトランザクション

## 匿名でBitcoinを入手する方法

- **現金取引**: 現金でbitcoinを入手する。
- **現金の代替手段**: ギフトカードを購入し、オンラインでbitcoinと交換する。
- **マイニング**: bitcoinを得る最もプライバシーを保てる方法はマイニングです。特に、マイニングプールはマイナーのIPアドレスを把握できる可能性があるため、単独で行う場合が該当します。[マイニングプールに関する情報](https://en.bitcoin.it/wiki/Pooled_mining)
- **窃盗**: 理論上、bitcoinを盗むことも匿名で入手する方法になり得ますが、違法であり、推奨されません。

## ミキシングサービス

ミキシングサービスを利用すると、ユーザーはbitcoinを**送信**し、代わりに**別のbitcoinを受け取る**ことができるため、元の所有者の追跡が困難になります。ただし、サービスがログを保存せず、実際にbitcoinを返すことを信頼する必要があります。代替となるミキシング手段には、Bitcoinカジノがあります。

## CoinJoin

**CoinJoin**は、複数のユーザーによるトランザクションを1つに統合し、入力と出力を対応付けようとする人々の作業を困難にします。効果的な手法ですが、入力や出力のサイズに特徴があるトランザクションは、依然として追跡できる可能性があります。

CoinJoinが使用された可能性のあるトランザクションの例として、`402d3e1df685d1fdf82f36b220079c1bf44db227df2d676625ebcbee3f6cb22a`と`85378815f6ee170aa8c26694ee2df42b99cff7fa9357f073c1192fff1f540238`があります。

詳しくは[CoinJoin](https://coinjoin.io/en)を参照してください。入金と後日の出金を分離するEthereumのスマートコントラクトミキサーについては、[Tornado Cash](https://tornado.cash)を参照してください。

## PayJoin

CoinJoinの一種である**PayJoin**（またはP2EP）は、2者間（顧客と販売者など）のトランザクションを、CoinJoin特有の同額の出力を使わずに通常のトランザクションに見せかけます。そのため検出は非常に困難であり、トランザクション監視機関が用いる、入力の共通所有者に関する一般的なヒューリスティックを無効にできる可能性があります。

```plaintext
2 btc --> 3 btc
5 btc     4 btc
```

上記のようなトランザクションはPayJoinである可能性があり、標準的なbitcoinトランザクションと見分けがつかないまま、プライバシーを強化できます。

**PayJoinの利用は、従来の監視手法を大きく妨げる可能性があり**、トランザクションのプライバシー実現に向けた有望な進展です。

# 暗号通貨におけるプライバシー保護のベストプラクティス

## **ウォレットの同期方法**

プライバシーとセキュリティを維持するには、ウォレットをブロックチェーンと同期することが重要です。主な方法は2つあります。

- **Full node**: ブロックチェーン全体をダウンロードすることで、Full nodeは最大限のプライバシーを確保します。これまでに行われたすべてのトランザクションがローカルに保存されるため、攻撃者がユーザーの関心のあるトランザクションやアドレスを特定することはできません。
- **クライアント側ブロックフィルタリング**: この方法では、ブロックチェーン内の各ブロックについてフィルターを作成します。これにより、ウォレットはネットワーク監視者に具体的な関心対象を明かさずに、関連するトランザクションを特定できます。軽量ウォレットはこれらのフィルターをダウンロードし、ユーザーのアドレスとの一致が見つかった場合にのみ、ブロック全体を取得します。

## **匿名性を確保するためのTorの利用**

Bitcoinはピアツーピアネットワーク上で動作するため、IPアドレスを隠し、ネットワークとの通信時のプライバシーを強化する目的でTorの利用が推奨されます。

## **アドレスの再利用を防ぐ**

プライバシーを守るには、トランザクションごとに新しいアドレスを使用することが重要です。アドレスを再利用すると、トランザクションが同一の主体に関連付けられ、プライバシーが損なわれる可能性があります。最新のウォレットは、設計上、アドレスの再利用を抑制します。

## **トランザクションのプライバシー保護戦略**

- **複数のトランザクション**: 支払いを複数のトランザクションに分割すると、トランザクション金額を分かりにくくし、プライバシー攻撃を阻止できます。
- **お釣りの回避**: お釣りの出力を必要としないトランザクションを選ぶと、お釣りの検出手法を妨げ、プライバシーを強化できます。
- **複数のお釣り出力**: お釣りを避けられない場合でも、複数のお釣り出力を生成することでプライバシーを向上できます。

# **Ethereum: Gasとトランザクション**

## **Gasを理解する**

Gasは、Ethereum上で操作を実行するために必要な計算量を表し、**gwei**で価格が設定されます。たとえば、2,310,000 gwei（または0.00231 ETH）のトランザクションには、Gas limitと基本手数料が設定され、さらにバリデーターによる取り込みを促す優先手数料が加わります。ユーザーは上限手数料を設定して過剰な支払いを防ぐことができ、余剰分は返金されます。<sup>[[5]](#references)</sup>

## **トランザクションの実行**

Ethereumのトランザクションには、送信者と受信者が含まれます。どちらもユーザーまたはスマートコントラクトのアドレスです。トランザクションには手数料が必要で、ブロックに含められなければなりません。トランザクションの必須情報には、受信者、送信者の署名、値、任意のデータ、Gas limit、手数料が含まれます。特筆すべき点として、送信者のアドレスは署名から導出されるため、トランザクションデータに含める必要はありません。<sup>[[4]](#references)</sup>

これらの慣行や仕組みは、プライバシーとセキュリティを重視しながら暗号通貨を利用するうえでの基礎となります。

## ZK Proof / zkVM Guest Integrity

proverが**zkVM**またはアプリケーション固有のproof circuitを使用して主張を証明するとき、verifierが確認できるのは、**guest programが記述どおりに実行されたこと**だけです。guestに**安全でないデシリアライズ**、**未定義動作**、または**意味的制約の欠落**がある場合、悪意のあるproverは、**公開メトリクスや主張された不変条件が誤っている**にもかかわらず検証に通るproofを生成できる可能性があります。<sup>[[7]](#references)</sup>

### proof guest内の安全でないデシリアライズ

- private witness/circuitのバイト列は、proofによって隠されている場合でも、**信頼できない攻撃者入力**として扱う。
- バイト列が事前に別の方法で検証されていない限り、`rkyv::access_unchecked`のようなチェックなしのヘルパーでデシリアライズしない。
- 信頼できないシリアライズ済みデータから読み込むenum discriminant、relative pointer、length、indexは、制御フローやメモリアクセスに影響を与える前に検証する。

実践的な監査パターン:

```rust
let private_circuit_bytes = sp1_zkvm::io::read_vec();
let ops = unsafe {
    rkyv::access_unchecked::<rkyv::Archived<Vec<Op>>>(&private_circuit_bytes)
};
```

`op.kind` のようなフィールドが enum で、攻撃者が**範囲外の discriminant**を注入できる場合、その値に対する後続の `match` はすべて要注意です。

### ジャンプテーブル / UB によるカウンターのバイパス

Rust が大きな `match` を**ジャンプテーブル**にコンパイルする場合、無効な enum discriminant によって**未定義の制御フロー**が発生することがあります。危険なパターンは次のとおりです。<sup>[[7]](#references)[[9]](#references)</sup>

1. ある `match` が**セキュリティ上重要なカウンターや制約**を更新する。
2. 別の `match` が**実際の命令の意味論**を処理する。
3. 範囲外の discriminant が最初のジャンプテーブルの範囲外をインデックスし、2つ目のジャンプテーブルに関連するコードに到達する。

結果：操作自体は実行されますが、計上処理はスキップされます。zkVM では、ゲート数や高コストな操作数が少なく報告されるなど、実現不可能なメトリクスやその他の制約付きリソースが偽装された証明を生成できます。

レビュー時のチェック項目：

- witness/private input からデシリアライズされる、攻撃者が制御可能な enum を探す。
- 同じ opcode/kind フィールドに対する `match` が繰り返されていないか調べる。
- `unsafe` + チェックなしのデシリアライズ + 大規模な opcode ディスパッチが組み合わさっている場合は、高リスクとして扱う。
- 必要に応じて、出力されたバイナリをリバースエンジニアリングする。ソースコードよりもジャンプテーブルの配置が重要な場合がある。

### 可逆インタープリター / 特化型インタープリターにおける意味論的制約の欠如

メモリ安全性だけを検証するのではなく、証明で強制する必要がある**意味論上のルール**も検証してください。

可逆 / 量子風の命令セットでは、異なる必要があるオペランドが実際に異なるよう制約されていることを確認してください。次のように実装された Toffoli/CCX のような操作の場合：<sup>[[7]](#references)[[8]](#references)</sup>

```rust
let v = cond & self.qubit(op.q_control1) & self.qubit(op.q_control2);
*self.qubit_mut(op.q_target) ^= v;
```

ゲストが拒否しない場合、安全ではなくなります:

```text
op.q_control1 == op.q_control2 == op.q_target
```

その場合、遷移は次の形に集約されます:

```text
q = q ^ (q & q) = 0
```

これは**決定論的なリセットプリミティブ**を生み出し、可逆性の前提を崩すとともに、本来意図されていない計算をより低コストで可能にします。リソース使用量を証明する proof system では、攻撃者が機能チェックを満たしながら、検証者が適用されていると考えるコストモデルを回避できる可能性があります。

### 制約が不十分な prover advice とモジュラー算術

**advice/witness stack から読み込まれる値は prover が制御します**。事前計算された商、余り、逆元、ヒントとして説明されている場合も同様です。証明によって示されるのは、witness が実装された制約を満たすことだけです。制約に型、範囲、正規形式のチェックが含まれていなければ、意図された計算が実行されたことまでは証明されません。<sup>[[13]](#references)</sup>

reduction またはユークリッド除算のヘルパーを監査する場合は、最後の減算や乗算だけでなく、整数関係全体を確認してください。`q` と `r` の各 limb が宣言された幅に制約されていること、再構成式 `x = q * m + r` が意図された整数表現で成立すること、そして正準範囲 `0 <= r < m` が強制されていることを確認します。より狭い `u32`/`u64` 命令に値を渡す**前に**検証してください。狭い演算を行っても、元のフィールド要素や複数 limb の値が想定された型だったことが遡って証明されるわけではありません。<sup>[[12]](#references)[[13]](#references)</sup>

```text
prover advice (q, r)
    -> limb/type assertions
    -> x = q * m + r
    -> 0 <= r < m
    -> consume q/r in narrow arithmetic
```

`mod_12289` における Miden の失敗は、exploit のパターンを示しています。商は 2-limb の 64-bit 値として検証されていましたが、advice から与えられた剰余は同等の検証を受けずに `u32overflowing_sub` に渡されていました。悪意ある prover は、実装された減算制約を満たしながら、数学的に正しくない剰余を手続きが返すよう、無効な商と剰余を組み合わせることができました。この結果は Falcon の検証に使われていたため、soundness の欠陥は単に誤った算術結果を生むだけでなく、偽造された認証署名にまで発展する可能性がありました。<sup>[[13]](#references)</sup>

### 暗黙のスタックを使う暗号 VM の監査

スタック言語ではオペランドが隠されるため、まず命令を IR に変換し、消費・生成される各スタック値を由来情報付きの式として表現します。そのうえで、保守的な解析パイプラインを使って次の処理を行います。<sup>[[10]](#references)[[11]](#references)[[12]](#references)[[13]](#references)</sup>

1. コールグラフを構築し、手続きの入力・出力におけるスタック効果を推論する。
2. 対応する命令をシンボリック実行し、制御フローを SSA／構造化式に変換する。
3. `Unknown`、`ProvenU32`、`Bool`、値の由来情報、ローカル変数の初期化状態などの抽象的な事実を、固定点に達するまで伝播する。
4. advice 由来の値が、すべての経路でサニタイザーを通らずに型付き算術処理やゼロ以外を要求する sink に到達する場合、それを検出する。
5. 宣言されたシグネチャと推論されたシグネチャを比較し、すべての終了時に呼び出し元が所有するスタック値が保持されていることを検証する。

不明なシグネチャや未対応の構造は、問題なしの結果ではなく**解析上の空白**として扱います。動的呼び出し、スタック効果が一定でないループ、スタック効果が異なる分岐があると、健全なスタックスロット追跡が不可能になることがあります。安全な decompiler は、もっともらしいものの誤った疑似コードを出力するのではなく、こうしたケースを拒否するか、明示的にマークします。<sup>[[10]](#references)[[13]](#references)</sup>

制御フローの合流点では、すべての先行経路で成り立つ場合にのみプロパティを保持します（たとえば、`ProvenU32 join Unknown = Unknown`）。また、固定点への収束と反復上限への到達を区別します。診断がないことを、表現対象のすべての実行でプロパティが成り立つ証拠として扱えるのは、収束した健全な過大近似の場合に限られます。<sup>[[11]](#references)</sup>

### 隠れた前提条件を明らかにするために証明責務を使う

命令セットが小さい場合は、手続きを実行可能な形式的 VM モデルに変換し、結果とスタック全体の変換の両方を証明します。定理では、停止性、型付き入力、期待される出力の先頭部分、変更されない呼び出し元スタックの保持を対象とする必要があります。定理の記述も証明と同じくらい慎重に監査してください。カーネルは、誤って弱められた主張の証明も検証してしまいます。<sup>[[12]](#references)[[13]](#references)</sup>

想定外の仮定は、有用な発見につながります。Miden のレビューでは、64-bit の右 rotate の証明に `shift mod 32 != 0` が必要となり、shift が 32 の倍数である大きな入力で失敗する境界ケースが明らかになりました。また別の証明では、256-bit の `wrapping_mul` が呼び出し元の所有するスタック値を破棄することが判明しました。発見した境界ケースをテストに追加し、実装を修正するか、意図的に公開前提条件を厳しくしてください。余分な仮定を黙って受け入れてはいけません。<sup>[[12]](#references)[[13]](#references)</sup>

### ZK システムでテストすべきこと

- 不正な witness／private-input エンコーディングを使って、すべての guest parser を fuzz する。
- opcode の dispatch 前に enum の範囲検証が行われることを確認する。
- オペランドの aliasing やその他の無効な命令形式について、意味的なチェックを追加する。
- すべての advice／witness ソースから型付き算術処理の各 sink までを追跡し、すべての経路で検証が行われることを必須とする。<sup>[[11]](#references)[[13]](#references)</sup>
- 非正規 limb、範囲外の剰余、境界の shift 数を使って算術ヘルパーをテストする。<sup>[[12]](#references)[[13]](#references)</sup>
- すべての return で、スタックの高さと、手続きに宣言された引数より下にある値の保持を確認する。<sup>[[10]](#references)[[12]](#references)[[13]](#references)</sup>
- 報告されたカウンター／公開カウンターを、独立した参照実装と比較する。
- guest program にバグがあれば、有効な証明であっても**誤った命題**を証明している可能性があることを忘れない。
