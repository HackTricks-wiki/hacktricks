## 基本概念

- **Smart Contracts**は、特定の条件が満たされたときにblockchain上で実行されるプログラムと定義され、中間者を介さずに契約の履行を自動化します。
- **Decentralized Applications (dApps)**はsmart contractsを基盤とし、ユーザーフレンドリーなフロントエンドと、透明性が高く監査可能なバックエンドを備えています。
- **Tokens & Coins**は、coinがデジタルマネーとして機能する一方、tokenは特定の状況における価値や所有権を表すという違いがあります。
  - **Utility Tokens**はサービスへのアクセスを許可し、**Security Tokens**は資産の所有権を表します。
- **DeFi**はDecentralized Financeの略で、中央機関を介さない金融サービスを提供します。
- **DEX**と**DAOs**は、それぞれDecentralized Exchange PlatformsとDecentralized Autonomous Organizationsを指します。

暗号資産市場で使われる現物注文、先物、レバレッジ、オプションの用語については、[Investment Terms](investment-terms.md)を参照してください。

## Consensus Mechanisms

Consensus mechanismsは、blockchain上のトランザクション検証における安全性と合意を確保します。

- **Proof of Work (PoW)**は、トランザクションの検証に計算能力を利用します。
- **Proof of Stake (PoS)**では、validatorが一定量のtokenを保有する必要があり、PoWと比べてエネルギー消費を抑えられます。<sup>[[1]](#references)</sup>

## Bitcoinの基本

### Transactions

Bitcoinのトランザクションでは、アドレス間で資金を移転します。トランザクションはデジタル署名によって検証され、秘密鍵の所有者だけが送金を開始できるようにします。<sup>[[2]](#references)</sup>

#### 主な構成要素:

- **Multisignature Transactions**では、トランザクションの承認に複数の署名が必要です。<sup>[[3]](#references)</sup>
- トランザクションは、**inputs**（資金の送信元）、**outputs**（送信先）、**fees**（minerに支払う手数料）、**scripts**（トランザクションのルール）で構成されます。

### Lightning Network

channel内で複数のトランザクションを可能にし、最終状態のみをblockchainにブロードキャストすることで、Bitcoinのスケーラビリティ向上を目指します。

## Bitcoinのプライバシーに関する懸念

**Common Input Ownership**や**UTXO Change Address Detection**などのプライバシー攻撃は、トランザクションのパターンを悪用します。**Mixers**や**CoinJoin**などの手法は、ユーザー間のトランザクションの関連性を分かりにくくし、匿名性を高めます。

## 匿名でBitcoinを入手する

現金取引、マイニング、mixerの利用などの方法があります。**CoinJoin**は複数のトランザクションを混ぜて追跡を困難にし、**PayJoin**はCoinJoinを通常のトランザクションに見せかけてプライバシーをさらに高めます。

# Bitcoinのプライバシー攻撃の概要

Bitcoinの世界では、トランザクションのプライバシーとユーザーの匿名性がしばしば懸念されます。ここでは、攻撃者がBitcoinのプライバシーを侵害する一般的な手法を簡単にまとめます。<sup>[[6]](#references)</sup>

## **Common Input Ownership Assumption**

複雑さから、異なるユーザーのinputsが1つのトランザクションにまとめられることは一般的にまれです。そのため、**同じトランザクション内の2つのinputアドレスは、同じ所有者に属すると推測されることがよくあります**。

## **UTXO Change Address Detection**

UTXO（**Unspent Transaction Output**）は、トランザクション内で全額を使用する必要があります。その一部だけを別のアドレスに送ると、残額は新しいお釣り用アドレスに送られます。観察者はこの新しいアドレスが送信者のものだと推測できるため、プライバシーが損なわれる可能性があります。

### 例

これを軽減するには、mixing serviceを利用したり、複数のアドレスを使ったりして、所有者を分かりにくくします。

## **ソーシャルネットワークとフォーラムでの露出**

ユーザーがBitcoinアドレスをオンラインで公開することがあり、**そのアドレスと所有者を簡単に結び付けられる**ようになります。

## **トランザクショングラフ分析**

トランザクションをグラフとして可視化すると、資金の流れに基づいてユーザー間の潜在的なつながりが明らかになる可能性があります。

## **不要なInputのヒューリスティック（お釣りの最適化ヒューリスティック）**

このヒューリスティックは、複数のinputsとoutputsを持つトランザクションを分析し、どのoutputがお釣りとして送信者に戻るのかを推測します。

### 例

```bash
2 btc --> 4 btc
3 btc     1 btc
```

入力を追加した結果、change outputが個々の入力額を上回ると、ヒューリスティックが誤判定する可能性があります。

## **アドレスの強制再利用**

攻撃者は、受取人が将来のトランザクションでこれらを他の入力と組み合わせ、アドレス同士が関連付けられることを期待して、以前使用されたアドレスに少額を送金することがあります。

### Walletの適切な動作

このプライバシーleakを防ぐため、Walletは、すでに使用済みで残高が空のアドレスで受け取ったコインを使用しないようにすべきです。

## **その他のBlockchain分析手法**

- **正確な支払額:** お釣りがないトランザクションは、同じユーザーが所有する2つのアドレス間で行われた可能性が高いです。
- **切りのよい金額:** トランザクションの金額が切りのよい数字であれば、それは支払いであることを示唆し、切りのよくない金額の出力がお釣りである可能性があります。
- **Walletフィンガープリンティング:** Walletごとにトランザクション作成パターンが異なるため、分析者は使用されたソフトウェアを特定し、お釣りアドレスを推定できる可能性があります。
- **金額と時間の相関:** トランザクションの時刻や金額を開示すると、トランザクションを追跡される可能性があります。

## **トラフィック分析**

ネットワークトラフィックを監視することで、攻撃者はトランザクションやブロックをIPアドレスに関連付け、ユーザーのプライバシーを侵害できる可能性があります。Bitcoinノードを多数運用する組織の場合、この方法でトランザクションを監視する能力が高まるため、特に注意が必要です。

## その他

プライバシー攻撃と防御の包括的な一覧については、[Bitcoin WikiのBitcoin Privacy](https://en.bitcoin.it/wiki/Privacy)を参照してください。

# 匿名でのBitcoinトランザクション

## 匿名でBitcoinを入手する方法

- **現金取引**: 現金でbitcoinを入手する方法です。
- **現金以外の方法**: ギフトカードを購入し、オンラインでbitcoinと交換します。
- **マイニング**: bitcoinを得る最もプライバシー性の高い方法はマイニングです。特に単独で行う場合は、マイニングプールがマイナーのIPアドレスを知る可能性があるため、プライバシー性が高くなります。[マイニングプールに関する情報](https://en.bitcoin.it/wiki/Pooled_mining)
- **窃盗**: 理論上、bitcoinを盗むことも匿名で入手する方法の1つですが、違法であり、推奨されません。

## Mixingサービス

Mixingサービスを利用すると、ユーザーは**bitcoinを送金**し、**別のbitcoinを受け取る**ことができるため、元の所有者を追跡するのが難しくなります。ただし、サービスがログを保存せず、実際にbitcoinを返すことを信頼する必要があります。Bitcoinカジノも、代替的なmixing手段です。

## CoinJoin

**CoinJoin**は、複数のユーザーによるトランザクションを1つにまとめることで、入力と出力を対応付けようとする者の作業を複雑にします。効果的ではあるものの、入力と出力のサイズに特徴があるトランザクションは、依然として追跡される可能性があります。

CoinJoinが使われた可能性のあるトランザクションの例として、`402d3e1df685d1fdf82f36b220079c1bf44db227df2d676625ebcbee3f6cb22a`および`85378815f6ee170aa8c26694ee2df42b99cff7fa9357f073c1192fff1f540238`があります。

詳しくは[CoinJoin](https://coinjoin.io/en)を参照してください。預け入れと後日の引き出しを分離するEthereumのスマートコントラクトミキサーについては、[Tornado Cash](https://tornado.cash)を参照してください。

## PayJoin

CoinJoinの派生方式である**PayJoin**（またはP2EP）は、2者（例: 顧客と販売者）間のトランザクションを、CoinJoinに特徴的な同額の出力を使わずに、通常のトランザクションに見せかけます。そのため、検出は非常に困難になり、トランザクション監視組織が用いる、入力の共通所有権に関する一般的なヒューリスティックを無効化できる可能性があります。

```plaintext
2 btc --> 3 btc
5 btc     4 btc
```

上記のようなトランザクションはPayJoinである可能性があり、標準的なbitcoinトランザクションと区別できないまま、プライバシーを高められます。

**PayJoinの利用は、従来の監視手法を大きく妨げる可能性があり**、トランザクションのプライバシー追求において有望な進展です。

# 暗号通貨のプライバシーに関するベストプラクティス

## **ウォレットの同期方法**

プライバシーとセキュリティを維持するには、ウォレットをブロックチェーンと同期することが重要です。特に有効な方法は次の2つです。

- **フルノード**: ブロックチェーン全体をダウンロードすることで、フルノードは最大限のプライバシーを確保します。これまでに行われたすべてのトランザクションがローカルに保存されるため、攻撃者がユーザーの関心対象であるトランザクションやアドレスを特定することはできません。
- **クライアント側ブロックフィルタリング**: この方法では、ブロックチェーン内のすべてのブロックに対するフィルターを作成し、ネットワークの監視者に特定の関心対象を明かすことなく、ウォレットが関連するトランザクションを特定できるようにします。軽量ウォレットはこれらのフィルターをダウンロードし、ユーザーのアドレスとの一致が見つかった場合にのみ、完全なブロックを取得します。

## **匿名性のためのTorの利用**

Bitcoinはピアツーピアネットワーク上で動作するため、IPアドレスを隠し、ネットワークとのやり取りにおけるプライバシーを高めるために、Torの利用が推奨されます。

## **アドレスの再利用を防ぐ**

プライバシーを守るには、トランザクションごとに新しいアドレスを使用することが重要です。アドレスを再利用すると、トランザクションが同一の主体に紐付けられ、プライバシーが損なわれる可能性があります。最新のウォレットは、設計上、アドレスの再利用を避けるようになっています。

## **トランザクションのプライバシー対策**

- **複数のトランザクション**: 支払いを複数のトランザクションに分割すると、トランザクション額を分かりにくくし、プライバシー攻撃を防げます。
- **お釣りの回避**: お釣りの出力が不要なトランザクションを選ぶことで、お釣りの検出手法を妨げ、プライバシーを高められます。
- **複数のお釣り出力**: お釣りを避けられない場合でも、複数のお釣り出力を生成することで、プライバシーを向上できます。

# **Ethereum: Gasとトランザクション**

## **Gasを理解する**

GasはEthereum上で操作を実行するために必要な計算量を測定する単位で、価格は**gwei**で表されます。たとえば、2,310,000 gwei（または0.00231 ETH）のトランザクションには、Gas上限と基本手数料が設定され、バリデーターに取り込んでもらうための優先手数料も含まれます。ユーザーは最大手数料を設定して過払いを防ぐことができ、余剰分は返金されます。<sup>[[5]](#references)</sup>

## **トランザクションの実行**

Ethereumのトランザクションには送信者と受信者があり、どちらもユーザーアドレスまたはスマートコントラクトアドレスを指定できます。トランザクションには手数料が必要で、ブロックに取り込まれなければなりません。トランザクションに含まれる基本情報は、受信者、送信者の署名、値、任意のデータ、Gas上限、手数料です。なお、送信者のアドレスは署名から導出されるため、トランザクションデータに含める必要はありません。<sup>[[4]](#references)</sup>

これらの慣行や仕組みは、プライバシーとセキュリティを重視しながら暗号通貨を利用したい人にとって、基礎となるものです。

## ZK Proof / zkVMゲストの完全性

証明者が**zkVM**またはアプリケーション固有の証明回路を使って主張を証明する場合、検証者が知るのは**ゲストプログラムが記述どおりに実行された**ということだけです。ゲストに**安全でないデシリアライズ**、**未定義動作**、または**意味的制約の欠落**があると、悪意のある証明者は、**公開メトリクスや主張された不変条件が誤っている**にもかかわらず、検証に通る証明を生成できる可能性があります。<sup>[[7]](#references)</sup>

### 証明ゲスト内の安全でないデシリアライズ

- 秘密のwitness／回路バイト列は、証明によって隠されていても、**信頼できない攻撃者入力**として扱います。
- バイト列が別途すでに検証されている場合を除き、`rkyv::access_unchecked`のようなチェックされないヘルパーを使ったデシリアライズは避けます。
- 信頼できないシリアライズデータから読み込まれる列挙型の判別値、相対ポインター、長さ、インデックスは、制御フローやメモリアクセスに影響する前に検証する必要があります。

実践的な監査パターン:

```rust
let private_circuit_bytes = sp1_zkvm::io::read_vec();
let ops = unsafe {
    rkyv::access_unchecked::<rkyv::Archived<Vec<Op>>>(&private_circuit_bytes)
};
```

`op.kind` のようなフィールドが enum であり、攻撃者が**範囲外の discriminant**を注入できる場合、その値に対する下流のすべての `match` が疑わしくなります。

### Jump-table / UB によるカウンタ回避

Rust が大きな `match` を**ジャンプテーブル**にコンパイルする場合、無効な enum discriminant によって**未定義の制御フロー**が発生する可能性があります。危険なパターンは次のとおりです。<sup>[[7]](#references)[[9]](#references)</sup>

1. 1つ目の `match` が**セキュリティ上重要なカウンタや制約**を更新する。
2. 2つ目の `match` が**実際の命令セマンティクス**を実行する。
3. 範囲外の discriminant が1つ目のジャンプテーブルの範囲外をインデックスし、2つ目のジャンプテーブルに関連付けられたコードに到達する。

結果：処理自体は実行されますが、計数処理がスキップされます。zkVM では、ゲート数や高コストな演算の数が少なくなるなど、実際にはあり得ないメトリクスや、上限付きリソースの値を偽った証明を捏造できます。

レビュー時のチェック項目：

- witness/private input からデシリアライズされる、攻撃者が制御可能な enum を探す。
- 同じ opcode/kind フィールドに対して繰り返し使われる `match` を調べる。
- `unsafe`、未検証のデシリアライズ、大規模な opcode dispatch の組み合わせを高リスクとして扱う。
- 必要に応じて生成されたバイナリをリバースエンジニアリングする。ジャンプテーブルの配置はソースコードより重要な場合がある。

### 可逆／特化型インタープリターにおけるセマンティック制約の欠落

メモリ安全性だけを検証するのではなく、その証明が強制すべき**セマンティックルール**も検証してください。

可逆／量子系の命令セットでは、異なる必要のあるオペランドが実際に異なる値となるよう制約されていることを確認してください。Toffoli/CCX に類似した演算が次のように実装されている場合：<sup>[[7]](#references)[[8]](#references)</sup>

```rust
let v = cond & self.qubit(op.q_control1) & self.qubit(op.q_control2);
*self.qubit_mut(op.q_target) ^= v;
```

ゲストが拒否しない場合、安全ではなくなります:

```text
op.q_control1 == op.q_control2 == op.q_target
```

その場合、遷移は次のように縮退します:

```text
q = q ^ (q & q) = 0
```

これは**決定論的なリセットプリミティブ**を作り出し、可逆性に関する前提を崩すとともに、本来意図されていない計算をより低コストで可能にします。リソース使用量を証明する証明システムでは、攻撃者が機能チェックを満たしながら、検証者が適用されていると考えるコストモデルを回避できる可能性があります。

### 制約が不十分なProverのアドバイスと剰余演算

**advice/witnessスタックから読み込まれる値は、事前計算された商、剰余、逆数、ヒントとして説明されている場合でも、Proverが制御できます**。証明によって示されるのは、witnessが実装された制約を満たすことだけです。型、範囲、標準形のチェックが制約に含まれていなければ、意図された計算が行われたことは証明されません。<sup>[[13]](#references)</sup>

reductionやユークリッド除算のヘルパーを監査する際は、最後の減算や乗算だけでなく、整数としての関係全体を検証してください。`q`と`r`の各limbが宣言された幅に制約されていること、再構成`x = q * m + r`が意図された整数表現で成立すること、正準範囲`0 <= r < m`が強制されていることを確認してください。値をより狭い`u32`/`u64`命令に渡す**前に**検証してください。狭い演算を行っても、元のフィールド要素や複数limbの値が期待された型であったことが遡って証明されるわけではありません。<sup>[[12]](#references)[[13]](#references)</sup>

```text
prover advice (q, r)
    -> limb/type assertions
    -> x = q * m + r
    -> 0 <= r < m
    -> consume q/r in narrow arithmetic
```

Midenにおける`mod_12289`の失敗は、典型的なexploitパターンを示しています。商は2つの64-bit limb値としてチェックされていましたが、adviceから渡された剰余には同等の検証がないまま`u32overflowing_sub`に渡されていました。悪意あるproverは、無効な商と剰余を組み合わせ、実装された減算制約を満たしながら、手続きに数学的に正しくない剰余を返させることができました。この結果はFalconの検証に使われていたため、soundnessの欠陥を、単に誤った算術結果を出すだけでなく、偽造された認可署名にまで悪用できました。<sup>[[13]](#references)</sup>

### 暗黙スタック型暗号VMの監査

スタック言語ではオペランドが隠れているため、まず命令をIRに変換し、消費・生成される各スタック値をprovenance付きの式として表します。そのうえで、保守的な分析パイプラインにより、次の処理ができます。<sup>[[10]](#references)[[11]](#references)[[12]](#references)[[13]](#references)</sup>

1. コールグラフを構築し、プロシージャの入力・出力スタック効果を推定する。
2. 対応する命令をシンボリック実行し、制御フローをSSA／構造化式に変換する。
3. `Unknown`、`ProvenU32`、`Bool`、値のprovenance、ローカル変数の初期化状態などの抽象的な事実を、固定点に達するまで伝播させる。
4. advice由来の値が、すべての到達経路でsanitizerを通過せずに、型付き算術または非ゼロを要求するsinkに到達する場合に警告する。
5. 宣言されたシグネチャと推定されたシグネチャを比較し、すべての終了経路で呼び出し元が所有するスタック値が維持されることを検証する。

不明なシグネチャや未対応の構文は、問題なしではなく**分析上のギャップ**として扱ってください。動的呼び出し、スタック効果が中立でないループ、スタック効果が異なる分岐があると、スタックスロットを正確に追跡できない場合があります。より安全なデコンパイラは、もっともらしくても誤った擬似コードを出力するのではなく、そのようなケースを拒否するか、問題ありとして印を付けます。<sup>[[10]](#references)[[13]](#references)</sup>

制御フローの合流点では、すべての先行ブロックで成立する場合に限り、その性質を維持してください（たとえば、`ProvenU32 join Unknown = Unknown`）。また、固定点への収束と反復上限への到達は区別してください。収束した健全な過大近似が得られた場合に限り、診断がないことを、表現されたすべての実行で性質が満たされる根拠として扱えます。<sup>[[11]](#references)</sup>

### 証明義務で隠れた前提条件を明らかにする

命令セットが小さい場合は、プロシージャを実行可能な形式的VMモデルに変換し、結果とスタック変換全体の両方を証明してください。定理では、停止性、型付き入力、期待される出力プレフィックス、未変更の呼び出し元スタックの維持を扱う必要があります。定理の記述は証明と同じくらい慎重に監査してください。カーネルは、意図せず弱められた主張の証明も検証できてしまいます。<sup>[[12]](#references)[[13]](#references)</sup>

予想外の仮定は有用な発見です。Midenのレビューでは、64-bit右ローテーションの証明に`shift mod 32 != 0`が必要となり、シフト量が32の倍数である大きな入力で失敗する境界ケースが明らかになりました。別の証明では、256-bitの`wrapping_mul`が呼び出し元の所有するスタック値を破棄することが分かりました。発見した境界ケースをテストに追加し、余分な仮定を黙って受け入れるのではなく、実装を修正するか公開される事前条件を意図的に強化してください。<sup>[[12]](#references)[[13]](#references)</sup>

### ZKシステムでテストすべきこと

- 不正なwitness／private inputエンコーディングを使い、すべてのguest parserをfuzzする。
- opcode dispatchの前にenumの範囲検証が行われることを確認する。
- オペランドのaliasingやその他の無効な命令形式に対するsemantic checkを追加する。
- すべてのadvice／witnessソースから型付き算術sinkまでを追跡し、すべての経路で検証が行われることを求める。<sup>[[11]](#references)[[13]](#references)</sup>
- 非標準limb、範囲外の剰余、境界のシフト量を使って算術ヘルパーをテストする。<sup>[[12]](#references)[[13]](#references)</sup>
- すべてのreturnで、スタックの高さと、プロシージャの宣言済み引数より下にある値が維持されることを確認する。<sup>[[10]](#references)[[12]](#references)[[13]](#references)</sup>
- 報告されたカウンターや公開カウンターを、独立した参照実装と比較する。
- guest programにバグがあれば、有効なproofでも**誤った命題**を証明している可能性があることを忘れないでください。
