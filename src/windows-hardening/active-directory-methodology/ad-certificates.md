# Сертифікати AD

## Вступ

### Компоненти сертифіката

- **Subject** сертифіката позначає його власника.
- **Public Key** — це ключ, що пов’язаний із закритим ключем і прив’язує сертифікат до його законного власника.
- **Validity Period**, визначений датами **NotBefore** і **NotAfter**, позначає період дії сертифіката.
- Унікальний **Serial Number**, наданий Certificate Authority (CA), ідентифікує кожен сертифікат.
- **Issuer** — це CA, який видав сертифікат.
- **SubjectAlternativeName** дає змогу вказати додаткові імена суб’єкта, розширюючи можливості його ідентифікації.
- **Basic Constraints** визначають, чи призначений сертифікат для CA або кінцевого суб’єкта, а також задають обмеження використання.
- **Extended Key Usages (EKUs)** визначають конкретні призначення сертифіката, як-от підписування коду або шифрування електронної пошти, за допомогою Object Identifiers (OIDs).
- **Signature Algorithm** указує метод підписування сертифіката.
- **Signature**, створений за допомогою закритого ключа видавця, гарантує автентичність сертифіката.<sup>[[4]](#references)</sup>

### Особливі міркування

- **Subject Alternative Names (SANs)** розширюють застосування сертифіката на кілька ідентичностей, що важливо для серверів із кількома доменами. Безпечні процеси видачі мають вирішальне значення для запобігання ризикам імперсонізації через маніпуляції з параметром SAN з боку атакувальників.<sup>[[4]](#references)</sup>

### Certificate Authorities (CAs) в Active Directory (AD)

AD CS враховує сертифікати CA у лісі AD через спеціальні контейнери, кожен із яких виконує окрему роль:<sup>[[4]](#references)</sup>

- Контейнер **Certification Authorities** містить сертифікати довірених кореневих CA.
- Контейнер **Enrolment Services** містить відомості про Enterprise CAs і їхні шаблони сертифікатів.
- Об’єкт **NTAuthCertificates** містить сертифікати CA, авторизованих для автентифікації AD.
- Контейнер **AIA (Authority Information Access)** полегшує перевірку ланцюжка сертифікатів за допомогою проміжних сертифікатів і сертифікатів перехресних CA.

### Отримання сертифіката: процес запиту клієнтського сертифіката

1. Процес запиту починається з того, що клієнти знаходять Enterprise CA.
2. Після створення пари відкритого й закритого ключів формується CSR, що містить відкритий ключ та інші дані.
3. CA перевіряє CSR на відповідність доступним шаблонам сертифікатів і видає сертифікат відповідно до дозволів шаблону.
4. Після схвалення CA підписує сертифікат своїм закритим ключем і повертає його клієнту.<sup>[[4]](#references)</sup>

### Шаблони сертифікатів

Ці шаблони, визначені в AD, описують параметри й дозволи для видачі сертифікатів, зокрема дозволені EKUs і права на реєстрацію або зміну. Вони мають вирішальне значення для керування доступом до служб сертифікатів.<sup>[[4]](#references)</sup>

**Версія схеми шаблону має значення.** У застарілих шаблонах **v1** (наприклад, вбудованому шаблоні **WebServer**) відсутні деякі сучасні механізми примусового застосування політик. Дослідження **ESC15/EKUwu** показало, що в шаблонах **v1** запитувач може вбудувати **Application Policies/EKUs** у CSR, і вони матимуть **пріоритет над** EKUs, налаштованими в шаблоні. Це дає змогу отримати сертифікати для client-auth, enrollment agent або code signing, маючи лише права на реєстрацію. Віддавайте перевагу шаблонам **v2/v3**, видаляйте шаблони v1 за замовчуванням або замінюйте їх і суворо обмежуйте EKUs відповідно до призначення.<sup>[[1]](#references)</sup>

## Реєстрація сертифікатів

Процес реєстрації сертифікатів починається з того, що адміністратор **створює шаблон сертифіката**, який потім **публікує** Enterprise Certificate Authority (CA). Завдяки цьому шаблон стає доступним для реєстрації клієнтами. Для цього ім’я шаблону додають до поля `certificatetemplates` об’єкта Active Directory.<sup>[[4]](#references)</sup>

Щоб клієнт міг запросити сертифікат, йому потрібно надати **права на реєстрацію**. Ці права визначаються дескрипторами безпеки самого шаблону сертифіката й Enterprise CA. Для успішного запиту дозволи потрібно надати в обох місцях.

### Права на реєстрацію в шаблоні

Ці права задаються за допомогою Access Control Entries (ACEs), які визначають такі дозволи, як:

- Права **Certificate-Enrollment** і **Certificate-AutoEnrollment**, кожне з яких пов’язане з певними GUID.
- **ExtendedRights**, що надає всі розширені дозволи.
- **FullControl/GenericAll**, що забезпечує повний контроль над шаблоном.

### Права на реєстрацію в Enterprise CA

Права CA описані в його дескрипторі безпеки, доступному через консоль керування Certificate Authority. Деякі налаштування навіть дають користувачам із низькими привілеями віддалений доступ, що може створювати загрозу безпеці.

### Додаткові засоби контролю видачі

Можуть застосовуватися певні засоби контролю, зокрема:

- **Схвалення менеджером**: запити залишаються в стані очікування до схвалення менеджером сертифікатів.
- **Агенти реєстрації та авторизовані підписи**: визначають кількість підписів, потрібних для CSR, і необхідні OIDs політик Application Policy.

### Способи запиту сертифікатів

Сертифікати можна запитувати через:

1. **Windows Client Certificate Enrollment Protocol** (MS-WCCE), використовуючи інтерфейси DCOM.
2. **ICertPassage Remote Protocol** (MS-ICPR), через іменовані канали або TCP/IP.
3. **Вебінтерфейс реєстрації сертифікатів**, якщо встановлено роль Certificate Authority Web Enrollment.
4. **Certificate Enrollment Service** (CES) у поєднанні зі службою Certificate Enrollment Policy (CEP).
5. **Network Device Enrollment Service** (NDES) для мережевих пристроїв, використовуючи Simple Certificate Enrollment Protocol (SCEP).

Користувачі Windows також можуть запитувати сертифікати через GUI (`certmgr.msc` або `certlm.msc`) чи інструменти командного рядка (`certreq.exe` або команду PowerShell `Get-Certificate`).

```bash
# Example of requesting a certificate using PowerShell
Get-Certificate -Template "User" -CertStoreLocation "cert:\\CurrentUser\\My"
```

## Автентифікація за допомогою сертифіката

Active Directory (AD) підтримує автентифікацію за допомогою сертифікатів, переважно використовуючи протоколи **Kerberos** і **Secure Channel (Schannel)**.

### Процес автентифікації Kerberos

Під час автентифікації Kerberos запит користувача на отримання Ticket Granting Ticket (TGT) підписується **закритим ключем** сертифіката користувача. Контролер домену перевіряє цей запит, зокрема **чинність**, **шлях** і **статус відкликання** сертифіката. Перевірки також включають підтвердження того, що сертифікат надійшов із довіреного джерела, і перевірку наявності його видавця у **сховищі сертифікатів NTAUTH**. Якщо перевірки успішні, видається TGT. Об’єкт **`NTAuthCertificates`** в AD розташований за адресою:

```bash
CN=NTAuthCertificates,CN=Public Key Services,CN=Services,CN=Configuration,DC=<domain>,DC=<com>
```

є ключовим для встановлення довіри під час автентифікації за сертифікатом.<sup>[[4]](#references)</sup>

Після розгортання **KB5014754** сучасна автентифікація Kerberos за сертифікатами здебільшого залежить від **сили зіставлення**, а не лише від EKU.<sup>[[2]](#references)</sup> У захищених лісах:

- Для входу може бути недостатньо сертифіката, який містить лише **UPN/DNS SAN**.
- KDC надає перевагу **надійному прив’язуванню**, зазвичай через **розширення безпеки SID** (`1.3.6.1.4.1.311.25.2`) або надійне явне зіставлення в `altSecurityIdentities`.
- Якщо сертифікат не має надійного зіставлення, контролери домену реєструють **Kdcsvc Event ID 39/41** у режимі сумісності та відхиляють автентифікацію в режимі примусового застосування.
- У комбінованих шляхах атаки важливі **ESC9/ESC16**, оскільки вони видаляють розширення SID з виданих сертифікатів; тоді оператори покладаються на явні зіставлення або формати SID у SAN URL, якщо це підтримує шлях атаки.

### Автентифікація Secure Channel (Schannel)

Schannel забезпечує захищені TLS/SSL-з’єднання: під час рукостискання клієнт пред’являє сертифікат, який у разі успішної перевірки надає доступ. Зіставлення сертифіката з обліковим записом AD може виконуватися, зокрема, за допомогою функції Kerberos **S4U2Self** або **Subject Alternative Name (SAN)** сертифіката.<sup>[[4]](#references)</sup>

Schannel також є практичним запасним варіантом, коли **PKINIT** недоступний. Наприклад, якщо контролер домену не має відповідного сертифіката **Smart Card Logon**, інструмент `certipy auth`/PKINIT може не отримати TGT, але той самий сертифікат усе ще може використовуватися для автентифікації та операцій LDAP через **LDAPS** або **LDAP StartTLS**.

### Перерахування AD Certificate Services

Служби сертифікатів AD можна перераховувати за допомогою LDAP-запитів, отримуючи відомості про **Enterprise Certificate Authorities (CA)** та їхні конфігурації. Ця інформація доступна будь-якому автентифікованому користувачу домену без спеціальних привілеїв. Для перерахування та оцінювання вразливостей у середовищах AD CS використовують такі інструменти, як **[Certify](https://github.com/GhostPack/Certify)** і **[Certipy](https://github.com/ly4k/Certipy)**.

Команди для використання цих інструментів містять:

```bash
# Enumerate trusted root CA certificates, Enterprise CAs, and web endpoints
Certify.exe cas

# Identify vulnerable templates and dump relevant permissions
Certify.exe find /vulnerable
Certify.exe find /showAllPermissions
Certify.exe pkiobjects /showAdmins

# Certipy 5.x enumeration focused on enabled/vulnerable templates
certipy find -enabled -vulnerable -hide-admins -u john@corp.local -p Passw0rd -dc-ip 10.10.10.10

# Save JSON/CSV output for offline review or BloodHound correlation
certipy find -json -output corp_adcs -u john@corp.local -p Passw0rd -dc-ip 10.10.10.10

# Request a certificate over the Web Enrollment endpoint or DCOM/RPC
certipy req -web -ca corp-CA -target ca.corp.local -template WebServer -upn john@corp.local -dns www.corp.local
certipy req -ca corp-CA -target ca.corp.local -template User -upn administrator@corp.local -sid S-1-5-21-...-500

# Use the issued certificate either for PKINIT or directly for LDAP Schannel auth
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10 -ldap-shell

# Enumerate Enterprise CAs and certificate templates with certutil
certutil.exe -TCAInfo
certutil -v -dstemplate
```

### Хронологія посилення захисту Microsoft (KB5014754)

Microsoft запровадила триетапне розгортання (Compatibility → Audit → Enforcement), щоб відмовитися від слабкого неявного зіставлення під час автентифікації Kerberos за сертифікатами. Починаючи з **11 лютого 2025 року**, контролери домену автоматично переходять у режим **Full Enforcement**, якщо значення реєстру `StrongCertificateBindingEnforcement` не задано. Пізніше Microsoft оновила графік, тож повернення до режиму сумісності залишатиметься можливим до оновлення безпеки від **9 вересня 2025 року**.<sup>[[2]](#references)</sup> Адміністраторам слід:

1. Встановити оновлення на всіх DC і серверах AD CS (оновлення за травень 2022 року або новіші).
2. Під час етапу *Audit* відстежувати події з ID 39/41, пов'язані зі слабким зіставленням.
3. Повторно видати сертифікати автентифікації клієнтів із новим **SID extension** або налаштувати строге зіставлення вручну, перш ніж режим enforcement заблокує слабке зіставлення.

### Примітки для операторів у захищених лісах

- **Самих ESC1/ESC6 у середовищах 2025 року й новіших уже недостатньо.** Якщо ви запитуєте сертифікат для іншого користувача, зазвичай потрібен ще й артефакт строгого зіставлення, як-от розширення SID або явне зіставлення.
- **ESC15 (EKUwu)** найкорисніша переважно в середовищах без виправлень, оскільки дає змогу перетворювати безпечні шаблони **v1**, наприклад **WebServer**, на сертифікати для автентифікації чи роботи агента реєстрації, додаючи **Application Policies**. Kerberos PKINIT і далі перевіряє EKU, але **LDAP Schannel** також враховує Application Policies, тому зловживання через LDAP залишається актуальним.<sup>[[1]](#references)</sup>
- **ESC16** — це параметр на рівні CA: якщо CA глобально вимикає розширення безпеки SID, усі видані сертифікати переходять до слабшої поведінки зіставлення, якщо тільки ланцюжок атаки не додає SID в інший підтримуваний спосіб.
- **Права ESC7 відрізняються:** дозвіл `ManageCA` на CA може дозволяти змінювати такі параметри, як `EDITF_ATTRIBUTESUBJECTALTNAME2` (ESC6), тоді як `ManageCertificates` керує затвердженням запитів. Явна заборона прав certificate-manager може блокувати цей шлях затвердження, навіть якщо дозвіл Allow також надано; перед комбінуванням параметрів і шаблонів перевірте фактично застосований ACL CA. Див. [оцінювання ACL CA від Microsoft](https://learn.microsoft.com/en-us/defender-for-identity/security-assessment-edit-vulnerable-ca-setting).

## Удосконалення виявлення та посилення захисту

* **Датчик Defender for Identity AD CS (2023-2024)** тепер показує оцінювання рівня захищеності для ESC1-ESC8/ESC11 і створює сповіщення в реальному часі, як-от *«Видача сертифіката контролера домену для вузла, який не є контролером домену»* (ESC8) і *«Запобігання реєстрації сертифікатів із довільними Application Policies»* (ESC15). Щоб скористатися цими засобами виявлення, розгорніть датчики на всіх серверах AD CS.<sup>[[3]](#references)</sup>
* Вимкніть параметр **«Supply in the request»** або суворо обмежте його використання в усіх шаблонах; надавайте перевагу явно заданим значенням SAN/EKU.
* Видаліть **Any Purpose** або **No EKU** із шаблонів, якщо вони не є абсолютно необхідними (це усуває сценарії ESC2).
* Для чутливих шаблонів (наприклад, WebServer / CodeSigning) вимагайте **затвердження керівником** або використовуйте спеціалізовані процеси Enrollment Agent.
* Обмежте доступ до вебреєстрації (`certsrv`) і кінцевих точок CES/NDES довіреними мережами або налаштуйте автентифікацію за клієнтським сертифікатом.
* Увімкніть шифрування реєстрації RPC (`certutil -setreg CA\InterfaceFlags +IF_ENFORCEENCRYPTICERTREQUEST`), щоб зменшити ризик ESC11 (ретрансляція RPC). За замовчуванням цей прапорець **увімкнено**, але для застарілих клієнтів його часто вимикають, що знову створює ризик ретрансляції.
* Захистіть кінцеві точки реєстрації на базі **IIS** (CES/Certsrv): за можливості вимкніть NTLM або вимагайте HTTPS і Extended Protection, щоб блокувати ретрансляцію ESC8.

Оцінюйте ESC11 на вузлі, де запущено CA; це може бути сервер — учасник домену, а не контролер домену. Перевірте активне значення `InterfaceFlags` CA у розділі `HKLM\SYSTEM\CurrentControlSet\Services\CertSvc\Configuration`; якщо значення не вдалося прочитати або воно відсутнє, результат невідомий — це не доводить, що шифрування RPC вимкнено. Відсутність прапорця `IF_ENFORCEENCRYPTICERTREQUEST` указує на можливу проблему конфігурації, але для атаки також потрібні доступна кінцева точка реєстрації RPC, облікові дані, які можна примусити до автентифікації, та придатний шаблон сертифіката. Для ESC8 самого виклику NTLM через HTTP недостатньо: переконайтеся, що доступна робоча кінцева точка реєстрації.
