# Сертифікати AD

## Вступ

### Компоненти сертифіката

- **Subject** сертифіката позначає його власника.
- **Public Key** пов’язаний із закритим ключем, щоб прив’язати сертифікат до його законного власника.
- **Validity Period**, визначений датами **NotBefore** і **NotAfter**, позначає період дії сертифіката.
- Унікальний **Serial Number**, наданий Certificate Authority (CA), ідентифікує кожен сертифікат.
- **Issuer** позначає CA, який видав сертифікат.
- **SubjectAlternativeName** дає змогу вказати додаткові імена суб’єкта, забезпечуючи більшу гнучкість ідентифікації.
- **Basic Constraints** визначає, чи призначений сертифікат для CA або кінцевого суб’єкта, а також встановлює обмеження щодо використання.
- **Extended Key Usages (EKUs)** визначають конкретні призначення сертифіката, як-от підписування коду або шифрування електронної пошти, за допомогою Object Identifiers (OIDs).
- **Signature Algorithm** визначає метод підписування сертифіката.
- **Signature**, створений за допомогою закритого ключа видавця, гарантує автентичність сертифіката.<sup>[[4]](#references)</sup>

### Особливі міркування

- **Subject Alternative Names (SANs)** розширюють сферу застосування сертифіката на кілька ідентичностей, що важливо для серверів із кількома доменами. Безпечні процеси видачі мають вирішальне значення для уникнення ризику імперсонації з боку зловмисників, які маніпулюють специфікацією SAN.<sup>[[4]](#references)</sup>

### Certificate Authorities (CAs) в Active Directory (AD)

AD CS розпізнає сертифікати CA в лісі AD через спеціальні контейнери, кожен з яких виконує окрему роль:<sup>[[4]](#references)</sup>

- Контейнер **Certification Authorities** містить довірені сертифікати кореневих CA.
- Контейнер **Enrolment Services** містить відомості про Enterprise CAs та їхні шаблони сертифікатів.
- Об’єкт **NTAuthCertificates** містить сертифікати CA, яким дозволено автентифікацію в AD.
- Контейнер **AIA (Authority Information Access)** забезпечує перевірку ланцюжка сертифікатів за допомогою проміжних сертифікатів і сертифікатів перехресного підпису CA.

### Отримання сертифіката: процес запиту клієнтського сертифіката

1. Процес запиту починається з пошуку клієнтами Enterprise CA.
2. Після створення пари відкритого й закритого ключів формується CSR, що містить відкритий ключ та інші дані.
3. CA перевіряє CSR за доступними шаблонами сертифікатів і видає сертифікат відповідно до дозволів шаблону.
4. Після схвалення CA підписує сертифікат своїм закритим ключем і повертає його клієнту.<sup>[[4]](#references)</sup>

### Шаблони сертифікатів

Ці шаблони, визначені в AD, встановлюють параметри й дозволи для видачі сертифікатів, зокрема дозволені EKUs, а також права на реєстрацію чи зміну. Вони критично важливі для керування доступом до служб сертифікатів.<sup>[[4]](#references)</sup>

**Версія схеми шаблону має значення.** У застарілих шаблонах **v1** (наприклад, вбудованому шаблоні **WebServer**) відсутні деякі сучасні параметри контролю. Дослідження **ESC15/EKUwu** показало, що в шаблонах **v1** запитувач може вбудувати **Application Policies/EKUs** у CSR, які мають **вищий пріоритет за** налаштовані в шаблоні EKUs. Це дає змогу отримати сертифікати client-auth, enrollment agent або code-signing, маючи лише права на реєстрацію. Надавайте перевагу шаблонам **v2/v3**, видаляйте або замінюйте типові шаблони v1 і суворо обмежуйте EKUs відповідно до призначення.<sup>[[1]](#references)</sup>

## Реєстрація сертифіката

Процес реєстрації сертифікатів запускає адміністратор, який **створює шаблон сертифіката**, який потім **публікує** Enterprise Certificate Authority (CA). Завдяки цьому шаблон стає доступним для реєстрації клієнтами. Для цього ім’я шаблону додають до поля `certificatetemplates` об’єкта Active Directory.<sup>[[4]](#references)</sup>

Щоб клієнт міг запросити сертифікат, йому потрібно надати **права на реєстрацію**. Ці права визначаються дескрипторами безпеки шаблону сертифіката та самої Enterprise CA. Для успішного запиту дозволи потрібно надати в обох місцях.

### Права на реєстрацію шаблону

Ці права задаються за допомогою Access Control Entries (ACEs), які визначають такі дозволи, як:

- Права **Certificate-Enrollment** і **Certificate-AutoEnrollment**, кожне з яких пов’язане з певним GUID.
- **ExtendedRights**, що надає всі розширені дозволи.
- **FullControl/GenericAll**, що забезпечує повний контроль над шаблоном.

### Права на реєстрацію в Enterprise CA

Права CA визначені в її дескрипторі безпеки, доступ до якого можна отримати через консоль керування Certificate Authority. Деякі параметри навіть дають віддалений доступ користувачам із низькими привілеями, що може становити загрозу безпеці.

### Додаткові засоби контролю видачі

Можуть застосовуватися певні засоби контролю, як-от:

- **Схвалення керівником**: переводить запити в стан очікування до схвалення менеджером сертифікатів.
- **Агенти реєстрації та авторизовані підписи**: визначають кількість обов’язкових підписів CSR і необхідні OIDs політик застосунків.

### Методи запиту сертифікатів

Сертифікати можна запитувати за допомогою:

1. **Windows Client Certificate Enrollment Protocol** (MS-WCCE) через інтерфейси DCOM.
2. **ICertPassage Remote Protocol** (MS-ICPR) через іменовані канали або TCP/IP.
3. **Вебінтерфейсу реєстрації сертифікатів**, якщо встановлено роль Certificate Authority Web Enrollment.
4. **Certificate Enrollment Service** (CES) разом зі службою Certificate Enrollment Policy (CEP).
5. **Network Device Enrollment Service** (NDES) для мережевих пристроїв із використанням Simple Certificate Enrollment Protocol (SCEP).

Користувачі Windows також можуть запитувати сертифікати через графічний інтерфейс (`certmgr.msc` або `certlm.msc`) чи інструменти командного рядка (`certreq.exe` або команду PowerShell `Get-Certificate`).

```bash
# Example of requesting a certificate using PowerShell
Get-Certificate -Template "User" -CertStoreLocation "cert:\\CurrentUser\\My"
```

## Автентифікація за сертифікатом

Active Directory (AD) підтримує автентифікацію за сертифікатом, переважно використовуючи протоколи **Kerberos** і **Secure Channel (Schannel)**.

### Процес автентифікації Kerberos

Під час автентифікації Kerberos запит користувача на отримання квитка для надання квитків (TGT) підписується **приватним ключем** сертифіката користувача. Контролер домену виконує кілька перевірок цього запиту, зокрема перевіряє **чинність**, **ланцюжок сертифіката** та **статус відкликання** сертифіката. Перевірки також охоплюють підтвердження того, що сертифікат походить із надійного джерела, і наявності видавця в **сховищі сертифікатів NTAUTH**. У разі успішного проходження перевірок видається TGT. Об’єкт **`NTAuthCertificates`** в AD розташований за адресою:

```bash
CN=NTAuthCertificates,CN=Public Key Services,CN=Services,CN=Configuration,DC=<domain>,DC=<com>
```

є ключовим для встановлення довіри під час автентифікації за сертифікатами.<sup>[[4]](#references)</sup>

Після розгортання **KB5014754** сучасна автентифікація Kerberos за сертифікатами залежить переважно від **надійності зіставлення**, а не лише від EKU.<sup>[[2]](#references)</sup> У захищених лісах:

- Сертифіката, що містить лише **UPN/DNS SAN**, може бути недостатньо для входу.
- KDC віддає перевагу **надійному прив’язуванню**, зазвичай через **розширення безпеки SID** (`1.3.6.1.4.1.311.25.2`) або надійне явне зіставлення в `altSecurityIdentities`.
- Якщо в сертифікаті немає надійного зіставлення, контролери домену реєструють **Kdcsvc Event ID 39/41** у режимі сумісності та відхиляють автентифікацію в режимі примусового застосування.
- У змішаних шляхах атаки важливі **ESC9/ESC16**, оскільки вони видаляють розширення SID з виданих сертифікатів; тоді оператори покладаються на явні зіставлення або формати SID у SAN URL, якщо це підтримує шлях атаки.

### Автентифікація Secure Channel (Schannel)

Schannel забезпечує захищені з’єднання TLS/SSL. Під час рукостискання клієнт надає сертифікат, який у разі успішної перевірки надає доступ. Зіставлення сертифіката з обліковим записом AD може передбачати використання функції Kerberos **S4U2Self** або **Subject Alternative Name (SAN)** сертифіката, а також інших методів.<sup>[[4]](#references)</sup>

Schannel також є практичним запасним варіантом, коли **PKINIT** недоступний. Наприклад, якщо контролер домену не має відповідного сертифіката **Smart Card Logon**, інструмент `certipy auth`/PKINIT може не отримати TGT, але той самий сертифікат усе ще може працювати з **LDAPS** або **LDAP StartTLS** для автентифікації та операцій LDAP.

### Перерахування AD Certificate Services

Служби сертифікатів AD можна перерахувати за допомогою LDAP-запитів, щоб виявити інформацію про **Enterprise Certificate Authorities (CA)** та їхні конфігурації. Ці дані доступні будь-якому автентифікованому користувачеві домену без спеціальних привілеїв. Для перерахування та оцінювання вразливостей у середовищах AD CS використовують такі інструменти, як **[Certify](https://github.com/GhostPack/Certify)** і **[Certipy](https://github.com/ly4k/Certipy)**.

Команди для використання цих інструментів:

```bash
# Enumerate trusted root CA certificates, Enterprise CAs, and web endpoints
Certify.exe cas

# Identify vulnerable templates and dump relevant permissions
Certify.exe find /vulnerable
Certify.exe find /showAllPermissions
Certify.exe pkiobjects /showAdmins

# Certipy 5.x enumeration focused on enabled/vulnerable templates
certipy find -enabled -vulnerable -hide-admins -u john@corp.local -p Passw0rd -dc-ip 10.10.10.10

# Save JSON/CSV output for offline review or BloodHound correlation
certipy find -json -output corp_adcs -u john@corp.local -p Passw0rd -dc-ip 10.10.10.10

# Request a certificate over the Web Enrollment endpoint or DCOM/RPC
certipy req -web -ca corp-CA -target ca.corp.local -template WebServer -upn john@corp.local -dns www.corp.local
certipy req -ca corp-CA -target ca.corp.local -template User -upn administrator@corp.local -sid S-1-5-21-...-500

# Use the issued certificate either for PKINIT or directly for LDAP Schannel auth
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10
certipy auth -pfx administrator.pfx -dc-ip 10.10.10.10 -ldap-shell

# Enumerate Enterprise CAs and certificate templates with certutil
certutil.exe -TCAInfo
certutil -v -dstemplate
```

### Графік посилення захисту Microsoft (KB5014754)

Microsoft запровадила поетапне розгортання у три фази (Compatibility → Audit → Enforcement), щоб відмовитися від слабкого неявного зіставлення для автентифікації Kerberos за допомогою сертифікатів. Станом на **11 лютого 2025 року** контролери домену автоматично переходять у режим **Full Enforcement**, якщо значення реєстру `StrongCertificateBindingEnforcement` не задано. Згодом Microsoft оновила графік, щоб повернення до режиму сумісності залишалося можливим до оновлення безпеки від **9 вересня 2025 року**.<sup>[[2]](#references)</sup> Адміністраторам слід:

1. Установити виправлення на всіх DC і серверах AD CS (оновлення за травень 2022 року або новіше).
2. Відстежувати події з ID 39/41, що вказують на слабке зіставлення, під час фази *Audit*.
3. Повторно видати сертифікати автентифікації клієнтів із новим **розширенням SID** або налаштувати суворе зіставлення вручну до того, як примусовий режим заблокує слабке зіставлення.

### Зауваження для операторів у середовищах із посиленим захистом

- **ESC1/ESC6 — це вже не вся картина** у середовищах 2025 року й новіших. Якщо ви запитуєте сертифікат для іншого суб’єкта, зазвичай також потрібен артефакт суворого зіставлення, як-от розширення SID або явне зіставлення.
- **ESC15 (EKUwu)** найкорисніша переважно в середовищах без виправлень, оскільки дає змогу перетворити нешкідливі шаблони **v1**, як-от **WebServer**, на сертифікати для автентифікації або агента реєстрації, додавши **Application Policies**. Kerberos PKINIT і далі перевіряє EKU, але **LDAP Schannel** також враховує Application Policies, тож зловживання через LDAP залишається актуальним.<sup>[[1]](#references)</sup>
- **ESC16** — це параметр на рівні CA: якщо CA глобально вимикає розширення безпеки SID, усі видані сертифікати переходять до слабшої поведінки зіставлення, якщо тільки ланцюжок атаки не додає SID в інший підтримуваний спосіб.
- **Права ESC7 відрізняються:** надання CA права `ManageCA` може дозволити змінювати такі параметри, як `EDITF_ATTRIBUTESUBJECTALTNAME2` (ESC6), тоді як `ManageCertificates` відповідає за схвалення запитів. Явне правило Deny для прав керування сертифікатами може заблокувати цей спосіб схвалення, навіть якщо також задано Allow; перед поєднанням параметрів і шаблонів перевірте фактичний ACL CA. Див. [оцінювання ACL CA від Microsoft](https://learn.microsoft.com/en-us/defender-for-identity/security-assessment-edit-vulnerable-ca-setting).

## Покращення виявлення та посилення захисту

* **Датчик AD CS у Defender for Identity (2023–2024)** тепер надає оцінки безпеки для ESC1–ESC8/ESC11 і створює сповіщення в реальному часі, як-от *«Видача сертифіката контролера домену для пристрою, що не є контролером домену»* (ESC8) і *«Запобігання реєстрації сертифікатів із довільними Application Policies»* (ESC15). Щоб скористатися цими засобами виявлення, розгорніть датчики на всіх серверах AD CS.<sup>[[3]](#references)</sup>
* Вимкніть параметр **«Supply in the request»** на всіх шаблонах або суворо обмежте його використання; надавайте перевагу явно визначеним значенням SAN/EKU.
* Видаліть **Any Purpose** або **No EKU** із шаблонів, якщо вони не є абсолютно необхідними (це усуває сценарії ESC2).
* Вимагайте **схвалення керівника** або використання спеціалізованих процесів Enrollment Agent для важливих шаблонів (наприклад, WebServer / CodeSigning).
* Обмежте доступ до вебреєстрації (`certsrv`) і кінцевих точок CES/NDES довіреними мережами або використовуйте автентифікацію за допомогою клієнтських сертифікатів.
* Увімкніть шифрування реєстрації RPC (`certutil -setreg CA\InterfaceFlags +IF_ENFORCEENCRYPTICERTREQUEST`), щоб знизити ризик ESC11 (ретрансляція RPC). Прапорець **увімкнено за замовчуванням**, але його часто вимикають для застарілих клієнтів, що знову створює ризик ретрансляції.
* Захистіть **кінцеві точки реєстрації на базі IIS** (CES/Certsrv): за можливості вимкніть NTLM або вимагайте HTTPS і Extended Protection, щоб блокувати ретрансляцію ESC8.

Оцінюйте ESC11 на хості, де працює CA: ним може бути сервер — учасник домену, а не контролер домену. Перевірте активний `InterfaceFlags` CA у `HKLM\SYSTEM\CurrentControlSet\Services\CertSvc\Configuration`; значення, яке не вдалося прочитати, або відсутнє значення означає, що результат невідомий, а не доводить, що шифрування RPC вимкнено. Відсутність біта `IF_ENFORCEENCRYPTICERTREQUEST` вказує на потенційну проблему конфігурації, але для експлуатації також потрібні доступна кінцева точка реєстрації RPC, облікові дані, які можна примусити використати, і придатний шаблон сертифіката. Для ESC8 самого виклику автентифікації NTLM через HTTP недостатньо: переконайтеся, що доступна робоча кінцева точка реєстрації.
