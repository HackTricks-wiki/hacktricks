# Обхід перевірок доступу до файлів у режимі ядра

{{#include ../../banners/hacktricks-training.md}}

## Вразливий шаблон драйвера

Драйвер не зберігає межі безпеки викликувача лише тим, що уособлює його. Відкриття об’єктів у режимі ядра зазвичай обходить перевірки доступу. `OBJ_KERNEL_HANDLE` лише робить отриманий дескриптор доступним із режиму ядра. Коли драйвер відкриває об’єкт або працює з ним від імені користувацького режиму, він також має використовувати `OBJ_FORCE_ACCESS_CHECK`, щоб Object Manager перевірив запитаний доступ відповідно до ефективного токена.<sup>[[3]](#references)[[4]](#references)</sup>

Перевірте IOCTL-обробники файлів і callback-функції створення на наявність такої послідовності:<sup>[[3]](#references)[[4]](#references)</sup>

1. Користувацький режим передає шлях, вихідний дескриптор, бажаний доступ або тип операції.
2. Драйвер уособлює викликувача, але викликає `IoCreateFileEx`, `ZwCreateFile` або подібну функцію без `OBJ_FORCE_ACCESS_CHECK`.
3. Дескриптор файла або каталогу, доступний лише з режиму ядра, зберігається у стані, пов’язаному з дескриптором.
4. Під час подальшої операції рішення про уособлення залежить від стану, на який впливає атакувальник, наприклад маски доступу, запитаної під час першого відкриття.
5. Привілейована гілка виконує перейменування або створення посилання з класом інформації `BypassAccessCheck`.

Це **файлова примітива confused-deputy**, а не обов’язково пошкодження пам’яті. Особливо небезпечна інверсія стану — «запитано запис — уособлювати; запис не запитано — залишатися привілейованим». У такій конструкції навмисний запит лише на доступ для читання може відкрити потужніший шлях.<sup>[[3]](#references)</sup>

## Приклад vSMB: привілейований root і привілейоване перейменування

`storvsp.sys` реалізує Virtual Server Message Block (vSMB). Коли ввімкнено функцію **Virtual Machine Platform**, користувацький режим може звертатися до `\Device\STORVSP` через `\\.\STORVSP`. Шлях файлової системи vSMB має такий вигляд: `\\.\STORVSP\VSMB\??\C:\path`. CVE-2025-59517 і CVE-2025-64673 показали, як два неузгоджені рішення щодо контролю доступу могли перетворити цей інтерфейс на локальне підвищення привілеїв.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>

Зіставлення функцій із CVE у джерелі ґрунтується на зворотному аналізі виправленого бінарного файла, а не на вихідному коді Microsoft. Дослідники попереджають, що ці два ідентифікатори можуть відповідати протилежним функціям.<sup>[[3]](#references)</sup>

### 1. Створення спільного ресурсу лише для читання, коренем якого є захищений каталог

Вразливий шлях створення зберігав запитані права в постійних прапорцях, таких як `HasReadAccess`, `HasWriteAccess` і `HasAppendAccess`. Потім він відкривав базовий шлях із `OBJ_KERNEL_HANDLE`, але без `OBJ_FORCE_ACCESS_CHECK`. Тому спроба уособлення не змушувала відкриття файла враховувати дозволи викликувача в NTFS.<sup>[[3]](#references)[[4]](#references)</sup>

Запитуйте лише `FILE_READ_DATA`. Так `HasWriteAccess` залишиться скинутим, але все одно буде отримано спільний ресурс із захищеним каталогом як внутрішнім коренем:<sup>[[3]](#references)</sup>

```c
HANDLE root = CreateFileW(
    L"\\\\.\\STORVSP\\VSMB\\??\\C:\\Windows\\System32\\",
    FILE_READ_DATA,
    FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,
    NULL, OPEN_EXISTING,
    FILE_FLAG_BACKUP_SEMANTICS | FILE_ATTRIBUTE_DIRECTORY,
    NULL
);
```

Важливий артефакт — це не дескриптор каталогу System32 у user-mode. Це дескриптор пристрою vSMB, пов’язаний зі станом драйвера, який містить привілейований кореневий дескриптор ядра.<sup>[[3]](#references)</sup>

### 2. Перетворення невідповідності стану на заміну захищеного файла

IOCTL `0x240330` приймав дескриптор вихідного файла, клас інформації та буфер інформації змінної довжини:<sup>[[3]](#references)</sup>

```c
#define IOCTL_VSMB_SET_INFORMATION_FILE_REQUEST 0x240330

typedef struct _VSMB_SET_INFO {
    DWORD Version;
    DWORD Reserved;
    UINT64 SourceHandle;
    DWORD InformationClass;
    DWORD BufferLength;
    BYTE Buffer[1];
} VSMB_SET_INFO;
```

Уразливий обробник приймав `FileRenameInformation`, `FileLinkInformation` і `FileRenameInformationEx`. Для звичайного шляху перейменування він відокремлював шлях до батьківського каталогу від останнього компонента, а потім відкривав батьківський каталог відносно збереженого root handle. Для цього відкриття знову використовували `OBJ_KERNEL_HANDLE | OBJ_CASE_INSENSITIVE` без `OBJ_FORCE_ACCESS_CHECK`. Ненульовий `RootDirectory`, переданий зловмисником у структурі перейменування, відхилявся, тому драйвер надавав власний привілейований handle каталогу.<sup>[[3]](#references)</sup>

Гілка, придатна для експлуатації, обиралася, якщо на етапі 1 **не** запитували доступ на запис:<sup>[[3]](#references)</sup>

- `HasWriteAccess == 1`: видати себе за збережений контекст безпеки root.
- `HasWriteAccess == 0`: пропустити видавання себе за іншу особу та перетворити `FileRenameInformation` або `FileRenameInformationEx` на відповідний варіант `BypassAccessCheck`.

Обробник дублював переданий зловмисником вихідний handle у `PsInitialSystemProcess`, отримував посилання на нього як на файловий об’єкт, встановлював привілейований handle цільового каталогу в структуру перейменування та викликав `ZwSetInformationFile`. Тому з `ReplaceIfExists = TRUE` файл, контрольований викликачем, міг замінити наявний файл у захищеному кореневому каталозі.<sup>[[3]](#references)</sup>

Під час аналізу подібного обробника відстежуйте **походження handle і контекст безпеки** в кожній гілці. Перевірка вхідних даних, перевірки на переповнення цілих чисел, `IO_STOP_ON_SYMLINK` і обмеження прийнятих класів інформації не компенсують поєднання привілейованого root handle з операцією обходу перевірки доступу.<sup>[[3]](#references)</sup>

## Від захищеного запису до виконання від імені SYSTEM

Механізм заміни захищеного файла дає змогу виконати код, якщо привілейований процес згодом завантажить замінений модуль. У продемонстрованому ланцюжку цільовим файлом був `C:\Windows\System32\wuapi.dll`. Активація локального COM-сервера класу `{72566E27-1ABB-4EB3-B4F0-EB431CB1CB32}` для інтерфейсу `{b4c1d279-966e-44e9-a9c5-ccaf4a77023d}` і виклик `IWaaSRemediation::LaunchDetectionOnly()` змушували процес SYSTEM завантажити цю DLL.<sup>[[3]](#references)</sup>

Цей виклик COM є **тригером активації**, а не [викраденням реєстру COM](com-hijacking.md). Механізм роботи з файлами забезпечує підкладений модуль, а привілейований завантажувач — виконання. Для інших ланцюжків із записом у захищені файли визначте точний образ, шлях до DLL, політику підписів, розрядність, експортовані функції та надійний тригер, перш ніж обирати ціль. Загальний процес аналізу завантажувача див. у розділі [поєднання довільного запису у файл із DLL hijacking](dll-hijacking/#chaining-an-arbitrary-file-write-into-a-missing-dll-hijack).<sup>[[3]](#references)</sup>

### Перенесення токена Session 0 на інтерактивний робочий стіл

Корисне навантаження, завантажене службою, зазвичай виконується в Session 0. Щоб створити інтерактивний процес, воно може отримати активний сеанс консолі за допомогою `WTSGetActiveConsoleSessionId`, увімкнути потрібні привілеї токена, дублювати поточний токен SYSTEM як первинний токен і встановити його `TokenSessionId` на активний сеанс. Потім `CreateProcessAsUserW` використовує цей токен із `STARTUPINFO.lpDesktop = L"winsta0\\default"`.<sup>[[3]](#references)[[5]](#references)</sup>

```c
DWORD sid = WTSGetActiveConsoleSessionId();
DuplicateTokenEx(currentToken, MAXIMUM_ALLOWED, NULL,
                 SecurityImpersonation, TokenPrimary, &primary);
SetTokenInformation(primary, TokenSessionId, &sid, sizeof(sid));
si.lpDesktop = L"winsta0\\default";
CreateProcessAsUserW(primary, L"C:\\Windows\\System32\\cmd.exe",
                     NULL, NULL, NULL, FALSE, CREATE_NEW_CONSOLE,
                     NULL, NULL, &si, &pi);
```

`SeTcbPrivilege` потрібен, щоб у цьому сценарії встановити ID сеансу токена. Інтерактивна станція вікон і робочий стіл також мають надати токену доступ. Див. [дублювання токена із Session 0](sedebug-+-seimpersonate-copy-token.md), щоб дізнатися про ширший процес копіювання токена.<sup>[[3]](#references)[[5]](#references)</sup>

## Рекомендації щодо виправлення та перевірки

Оновлення Microsoft за грудень 2025 року усунули продемонстрований ланцюжок. Зворотна розробка показала, що виправлений шлях створення vSMB відхиляє запити ненадійних викликачів, які запитують корінь спільного ресурсу без `FILE_WRITE_DATA`. Для відповідних операцій також примусово перевіряється доступ. Це блокує інверсію стану до того, як непривілейований викликач зможе отримати привілейований корінь.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>

Для коду драйверів дотримуйтеся таких правил:<sup>[[3]](#references)[[4]](#references)</sup>

- Додавайте `OBJ_FORCE_ACCESS_CHECK`, коли об’єкт відкривається на запит від user-mode. Не вважайте `OBJ_KERNEL_HANDLE` засобом керування авторизацією.<sup>[[4]](#references)</sup>
- Фіксуйте та перевіряйте режим запитувача й ефективний контекст суб’єкта. Не дозволяйте запитаним правам визначати перехід до привілейованішої гілки виконання.
- Перевіряйте дескриптори користувача з правильним типом об’єкта, маскою доступу та режимом `UserMode`. Дублювання дескриптора в системний процес не підтверджує повноваження для запитаної операції.
- Виконуйте пошук цільового об’єкта відносно довіреного дескриптора, але переконайтеся, що сам довірений дескриптор було відкрито з примусовою перевіркою доступу запитувача.
- Уникайте класів `File*BypassAccessCheck` для операцій, ініційованих користувачем. Якщо внутрішньому коду вони справді потрібні, обмежте цей шлях рішенням про авторизацію, незалежним від контрольованих користувачем прапорців доступу.
- Встановлюйте виправлення на вразливих системах. Ця вразлива поверхня актуальна, коли Virtual Machine Platform завантажує `storvsp.sys`.<sup>[[3]](#references)</sup>
