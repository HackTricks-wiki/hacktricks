## **Список контролю доступу (ACL)**

Список контролю доступу (ACL) складається з упорядкованого набору записів контролю доступу (ACEs), які визначають захист об'єкта та його властивостей. По суті, ACL визначає, які дії яких суб'єктів безпеки (користувачів або груп) дозволені або заборонені щодо певного об'єкта.

Існує два типи ACL:

- **Дискреційний список контролю доступу (DACL):** Визначає, які користувачі та групи мають або не мають доступу до об'єкта.
- **Системний список контролю доступу (SACL):** Керує аудитом спроб доступу до об'єкта.

Під час доступу до файлу система перевіряє дескриптор безпеки об'єкта порівняно з токеном доступу користувача, щоб визначити, чи слід надати доступ і яким буде його обсяг, на основі ACE.<sup>[[1]](#references)</sup>

### **Основні компоненти**

- **DACL:** Містить ACE, які надають або забороняють користувачам і групам дозволи доступу до об'єкта. По суті, це основний ACL, що визначає права доступу.
- **SACL:** Використовується для аудиту доступу до об'єктів, де ACE визначають типи доступу, які потрібно записувати в Security Event Log. Це може бути надзвичайно корисним для виявлення несанкціонованих спроб доступу або усунення проблем із доступом.<sup>[[1]](#references)</sup>

### **Взаємодія системи з ACL**

Кожен сеанс користувача пов'язаний із токеном доступу, який містить важливу для цього сеансу інформацію про безпеку, зокрема ідентифікатори користувача та груп, а також привілеї. Цей токен також містить logon SID, який унікально ідентифікує сеанс.

Local Security Authority (LSASS) обробляє запити доступу до об'єктів, перевіряючи DACL на наявність ACE, які відповідають суб'єкту безпеки, що намагається отримати доступ. Доступ негайно надається, якщо відповідних ACE не знайдено. В іншому разі LSASS порівнює ACE із SID суб'єкта безпеки в токені доступу, щоб визначити можливість доступу.<sup>[[1]](#references)</sup>

### **Підсумок процесу**

- **ACL:** Визначають дозволи доступу через DACL і правила аудиту через SACL.
- **Токен доступу:** Містить інформацію про користувача, групи та привілеї для сеансу.
- **Рішення щодо доступу:** Приймається шляхом порівняння ACE у DACL із токеном доступу; SACL використовуються для аудиту.<sup>[[1]](#references)</sup>

### ACE

Існує **три основні типи записів контролю доступу (ACE)**:<sup>[[1]](#references)</sup>

- **Access Denied ACE**: Цей ACE явно забороняє доступ до об'єкта вказаним користувачам або групам (у DACL).
- **Access Allowed ACE**: Цей ACE явно надає доступ до об'єкта вказаним користувачам або групам (у DACL).
- **System Audit ACE**: Розташований у системному списку контролю доступу (SACL), цей ACE відповідає за створення audit logs під час спроб доступу користувачів або груп до об'єкта. Він документує, чи було доступ дозволено або заборонено, а також характер доступу.

Кожен ACE має **чотири критично важливі компоненти**:<sup>[[1]](#references)</sup>

1. **Security Identifier (SID)** користувача або групи (або ім'я суб'єкта в графічному представленні).
2. **Прапорець**, який визначає тип ACE (access denied, allowed або system audit).
3. **Прапорці успадкування**, які визначають, чи можуть дочірні об'єкти успадкувати ACE від батьківського об'єкта.
4. [**access mask**](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7a53f60e-e730-4dfe-bbe9-b21b62eb790b?redirectedfrom=MSDN) — 32-бітове значення, що визначає надані об'єкту права.

Визначення доступу виконується шляхом послідовної перевірки кожного ACE, доки не відбудеться одне з наведеного:<sup>[[1]](#references)</sup>

- **Access-Denied ACE** явно забороняє запитані права trustee, ідентифікованому в токені доступу.
- **Access-Allowed ACE(s)** явно надають усі запитані права trustee у токені доступу.
- Після перевірки всіх ACE, якщо будь-яке запитане право **не було явно дозволене**, доступ неявно **забороняється**.

### Порядок ACE

Спосіб розташування **ACE** (правил, які визначають, хто може або не може отримати доступ до чогось) у списку під назвою **DACL** має дуже важливе значення. Це пов'язано з тим, що після надання або заборони доступу на основі цих правил система припиняє перевіряти решту.<sup>[[1]](#references)</sup>

Існує найкращий спосіб упорядкувати ці ACE — він називається **«канонічним порядком»**. Цей метод допомагає забезпечити коректну та передбачувану роботу системи. Ось як він застосовується в таких системах, як **Windows 2000** і **Windows Server 2003**:

- Спочатку розміщуються всі правила, створені **безпосередньо для цього об'єкта**, а вже потім правила, успадковані з іншого місця, наприклад від батьківської папки.
- Серед цих безпосередніх правил спочатку розміщуються правила, які кажуть **«ні» (deny)**, а потім ті, що кажуть **«так» (allow)**.
- Для правил, успадкованих з іншого місця, спочатку розміщуються правила з **найближчого джерела**, наприклад від батьківського об'єкта, а потім правила з віддаленіших джерел. Тут також **«ні»** розміщується перед **«так»**.

Таке розташування має дві важливі переваги:

- Воно гарантує, що конкретне **«ні»** буде дотримано незалежно від наявності інших правил **«так»**.
- Воно дає власнику об'єкта можливість **остаточно визначати**, хто має доступ, перш ніж почнуть діяти правила батьківських папок або інших вищих рівнів.

Завдяки такому підходу власник файлу або папки може дуже точно визначити, хто отримає доступ, гарантуючи доступ потрібним користувачам і забороняючи його іншим.

![NTFS access control entry ordering diagram](https://www.ntfs.com/images/screenshots/ACEs.gif)

Отже, цей **«канонічний порядок»** потрібен для того, щоб правила доступу були зрозумілими та коректно працювали: спочатку розміщуються конкретні правила, а все інше впорядковується логічним способом.

### Пояснення контролю доступу у спрощеній формі

Під час керування доступом до ресурсів, наприклад папки, ми використовуємо списки та правила, відомі як списки контролю доступу (ACL) і записи контролю доступу (ACE). Вони визначають, хто може або не може отримати доступ до певних даних.<sup>[[1]](#references)</sup>

#### Заборона доступу певній групі

Уявімо, що у вас є папка з назвою Cost, і ви хочете, щоб усі, крім marketing team, мали до неї доступ. Правильно налаштувавши правила, можна гарантувати, що marketing team буде явно позбавлена доступу до того, як доступ буде дозволено всім іншим. Для цього правило, яке забороняє доступ marketing team, розміщується перед правилом, яке дозволяє доступ усім.

#### Надання доступу окремому учаснику забороненої групи

Припустімо, Bob, директор із marketing, потребує доступу до папки Cost, хоча marketing team загалом не повинна мати доступу. Можна додати окреме правило (ACE) для Bob, яке надає йому доступ, і розмістити його перед правилом, що забороняє доступ marketing team. Таким чином Bob отримає доступ, незважаючи на загальне обмеження для його групи.

#### Розуміння записів контролю доступу

ACE — це окремі правила в ACL. Вони ідентифікують користувачів або групи, визначають, який доступ дозволено або заборонено, а також те, як ці правила застосовуються до дочірніх елементів (успадкування). Існує два основні типи ACE:

- **Generic ACEs**: Застосовуються широко, впливаючи на всі типи об'єктів або розрізняючи лише контейнери (наприклад, папки) і неконтейнери (наприклад, файли). Наприклад, правило може дозволяти користувачам переглядати вміст папки, але не отримувати доступ до файлів у ній.
- **Object-Specific ACEs**: Забезпечують точніший контроль, дозволяючи задавати правила для певних типів об'єктів або навіть окремих властивостей об'єкта. Наприклад, у каталозі користувачів правило може дозволяти користувачу змінювати свій номер телефону, але не години входу.

Кожен ACE містить важливу інформацію, зокрема кому застосовується правило (за допомогою Security Identifier або SID), що саме правило дозволяє або забороняє (за допомогою access mask), а також як воно успадковується іншими об'єктами.

#### Основні відмінності між типами ACE

- **Generic ACEs** підходять для простих сценаріїв контролю доступу, коли одне й те саме правило застосовується до всіх аспектів об'єкта або до всіх об'єктів усередині контейнера.
- **Object-Specific ACEs** використовуються для складніших сценаріїв, особливо в середовищах на кшталт Active Directory, де може знадобитися по-різному керувати доступом до окремих властивостей об'єкта.

Підсумовуючи, ACL і ACE допомагають визначати точні правила доступу, гарантуючи, що лише потрібні користувачі або групи матимуть доступ до конфіденційної інформації чи ресурсів. Вони також дають змогу налаштовувати права доступу на рівні окремих властивостей або типів об'єктів.

### Структура запису контролю доступу

| Поле ACE   | Опис                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type        | Прапорець, що визначає тип ACE. Windows 2000 і Windows Server 2003 підтримують шість типів ACE: три загальні типи ACE, які застосовуються до всіх об'єктів, що підлягають захисту, і три специфічні для об'єктів типи ACE, які можуть використовуватися для об'єктів Active Directory.                                                                                                                                                                                                                                                            |
| Flags       | Набір бітових прапорців, які керують успадкуванням і аудитом.                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Size        | Кількість байтів пам'яті, виділених для ACE.                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Access mask | 32-бітове значення, біти якого відповідають правам доступу до об'єкта. Біти можуть бути встановлені або скинуті, але значення налаштування залежить від типу ACE. Наприклад, якщо біт, що відповідає праву читати дозволи, увімкнено, а тип ACE — Deny, ACE забороняє читати дозволи об'єкта. Якщо той самий біт встановлено, але тип ACE — Allow, ACE надає право читати дозволи об'єкта. Докладнішу інформацію про Access mask наведено в наступній таблиці. |
| SID         | Ідентифікує користувача або групу, доступ якої контролюється або дії якої відстежуються цим ACE.                                                                                                                                                                                                                                                                                                                                                                                                                                 |

### Структура Access Mask

| Bit (Range) | Meaning                            | Description/Example                       |
| ----------- | ---------------------------------- | ----------------------------------------- |
| 0 - 15      | Специфічні для об'єкта права доступу      | Читання даних, виконання, додавання даних           |
| 16 - 22     | Стандартні права доступу             | Видалення, запис ACL, запис власника            |
| 23          | Може отримувати доступ до security ACL            |                                           |
| 24 - 27     | Зарезервовано                           |                                           |
| 28          | Generic ALL (Read, Write, Execute) | Усе, що наведено нижче                          |
| 29          | Generic Execute                    | Усе необхідне для виконання програми |
| 30          | Generic Write                      | Усе необхідне для запису у файл   |
| 31          | Generic Read                       | Усе необхідне для читання файлу       |
