# ACLs - DACLs/SACLs/ACEs

## **Список контролю доступу (ACL)**

Список контролю доступу (ACL) складається з упорядкованого набору записів контролю доступу (ACE), які визначають захист об’єкта та його властивостей. По суті, ACL визначає, які дії яких суб’єктів безпеки (користувачів або груп) дозволені або заборонені для певного об’єкта.

Існує два типи ACL:

- **Дискреційний список контролю доступу (DACL):** Визначає, які користувачі та групи мають або не мають доступу до об’єкта.
- **Системний список контролю доступу (SACL):** Керує аудитом спроб доступу до об’єкта.

Під час доступу до файлу система перевіряє дескриптор безпеки об’єкта за маркером доступу користувача, щоб визначити, чи надавати доступ і який саме, на основі ACE.<sup>[[1]](#references)</sup>

Якщо батьківський каталог надає повний контроль, але дочірній файл забороняє читання, окремо перевірте ефективну DACL, власника та успадкування **дочірнього файлу**. Щоб змінити DACL файлу, потрібне право `WRITE_DAC` на цей файл або відповідне право власника; [Microsoft визначає `WRITE_DAC`](https://learn.microsoft.com/en-us/windows/win32/secauthz/standard-access-rights) і [описує неявні права власника](https://learn.microsoft.com/en-us/windows/win32/secauthz/owner-of-a-new-object). Самі лише дозволи батьківського каталогу не гарантують, що дочірній файл можна читати або що його DACL можна змінити.

### **Ключові компоненти**

- **DACL:** Містить ACE, які надають або забороняють користувачам і групам дозволи на доступ до об’єкта. По суті, це основна ACL, яка визначає права доступу.
- **SACL:** Використовується для аудиту доступу до об’єктів; ACE визначають типи доступу, які потрібно записувати в журнал подій безпеки. Це може бути надзвичайно корисним для виявлення спроб несанкціонованого доступу або діагностики проблем із доступом.<sup>[[1]](#references)</sup>

### **Взаємодія системи з ACL**

Кожен сеанс користувача пов’язаний із маркером доступу, який містить важливу для цього сеансу інформацію про безпеку, зокрема ідентифікатори користувача та груп, а також привілеї. Цей маркер також містить SID входу, який унікально ідентифікує сеанс.

Local Security Authority (LSASS) обробляє запити на доступ до об’єктів, перевіряючи DACL на наявність ACE, що відповідають суб’єкту безпеки, який намагається отримати доступ. Якщо відповідних ACE немає, доступ надається негайно. Інакше LSASS зіставляє ACE із SID суб’єкта безпеки в маркері доступу, щоб визначити, чи має він право на доступ.<sup>[[1]](#references)</sup>

### **Стислий опис процесу**

- **ACL:** Визначають дозволи на доступ за допомогою DACL і правила аудиту за допомогою SACL.
- **Маркер доступу:** Містить дані про користувача, групи та привілеї для сеансу.
- **Рішення щодо доступу:** Приймається шляхом зіставлення ACE з DACL із маркером доступу; SACL використовуються для аудиту.<sup>[[1]](#references)</sup>

### ACE

Існує **три основні типи записів контролю доступу (ACE)**:<sup>[[1]](#references)</sup>

- **ACE заборони доступу**: Ця ACE явно забороняє вказаним користувачам або групам доступ до об’єкта (у DACL).
- **ACE дозволу доступу**: Ця ACE явно надає вказаним користувачам або групам доступ до об’єкта (у DACL).
- **ACE аудиту системи**: Ця ACE міститься в системному списку контролю доступу (SACL) і відповідає за створення записів аудиту під час спроб користувачів або груп отримати доступ до об’єкта. Вона фіксує, чи було доступ дозволено або заборонено, а також характер доступу.

Кожна ACE має **чотири важливі компоненти**:<sup>[[1]](#references)</sup>

1. **Ідентифікатор безпеки (SID)** користувача або групи (або їхнє ім’я суб’єкта в графічному представленні).
2. **Прапорець**, який визначає тип ACE (заборона доступу, дозвіл доступу або системний аудит).
3. **Прапорці успадкування**, які визначають, чи можуть дочірні об’єкти успадкувати ACE від батьківського об’єкта.
4. [**Маска доступу**](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7a53f60e-e730-4dfe-bbe9-b21b62eb790b?redirectedfrom=MSDN) — 32-бітове значення, яке визначає права, надані для об’єкта.

Доступ визначається послідовною перевіркою кожної ACE, доки не виконається одна з таких умов:<sup>[[1]](#references)</sup>

- **ACE заборони доступу** явно забороняє запитані права довіреній стороні, указаній у маркері доступу.
- **ACE дозволу доступу** явно надають усі запитані права довіреній стороні, указаній у маркері доступу.
- Після перевірки всіх ACE доступ **неявно забороняється**, якщо будь-яке запитане право **не було явно дозволено**.

### Порядок ACE

Порядок, у якому **ACE** (правила, що визначають, хто може або не може отримати доступ до чогось) розміщені в списку **DACL**, дуже важливий. Щойно система надає або забороняє доступ на підставі цих правил, вона припиняє перевіряти решту.<sup>[[1]](#references)</sup>

Існує найкращий спосіб упорядкувати ці ACE — він називається **«канонічним порядком»**. Цей метод допомагає забезпечити стабільну та коректну роботу. Ось як він застосовується в таких системах, як **Windows 2000** і **Windows Server 2003**:

- Спочатку розміщуйте всі правила, створені **безпосередньо для цього об’єкта**, а вже потім правила, успадковані з інших джерел, наприклад батьківської папки.
- Серед цих власних правил спочатку розміщуйте ті, що кажуть **«ні» (заборона)**, а потім ті, що кажуть **«так» (дозвіл)**.
- Для правил, успадкованих з інших джерел, спочатку розміщуйте правила з **найближчого джерела**, наприклад батьківської папки, а потім переходьте до віддаленіших джерел. І тут спочатку розміщуйте правила **«ні»**, а потім **«так»**.

Такий порядок має дві важливі переваги:

- Він гарантує, що конкретна заборона **«ні»** буде дотримана незалежно від інших правил **«так»**.
- Він дає власнику об’єкта можливість **остаточно вирішити**, хто матиме доступ, перш ніж почнуть застосовуватися правила батьківських папок або інших джерел.

Завдяки такому підходу власник файлу чи папки може точно визначити, хто матиме доступ, гарантуючи, що потрібні люди зможуть увійти, а решта — ні.

![Схема порядку записів контролю доступу NTFS](https://www.ntfs.com/images/screenshots/ACEs.gif)

Отже, **«канонічний порядок»** допомагає зробити правила доступу зрозумілими й ефективними: спочатку розміщуються конкретні правила, а решта впорядковується належним чином.

### Спрощене пояснення контролю доступу

Для керування доступом до ресурсів, наприклад папки, використовуються списки й правила, відомі як списки контролю доступу (ACL) і записи контролю доступу (ACE). Вони визначають, хто може або не може отримати доступ до певних даних.<sup>[[1]](#references)</sup>

#### Заборона доступу певній групі

Уявімо, що у вас є папка з назвою Cost і ви хочете, щоб усі мали до неї доступ, крім команди маркетингу. Правильно налаштувавши правила, можна явно заборонити доступ команді маркетингу, перш ніж надати його всім іншим. Для цього правило, яке забороняє доступ команді маркетингу, розміщується перед правилом, яке дозволяє доступ усім.

#### Надання доступу конкретному учаснику групи, якій відмовлено в доступі

Припустімо, Боб, директор із маркетингу, має отримати доступ до папки Cost, хоча команді маркетингу загалом доступ не дозволено. Можна додати окреме правило (ACE), яке надає доступ Бобу, і розмістити його перед правилом, що забороняє доступ команді маркетингу. Так Боб отримає доступ, попри загальне обмеження для його команди.

#### Розуміння записів контролю доступу

ACE — це окремі правила в ACL. Вони визначають користувачів або групи, указують, який доступ дозволено або заборонено, і визначають, як ці правила застосовуються до дочірніх елементів (успадкування). Є два основні типи ACE:

- **Узагальнені ACE**: Застосовуються широко: до всіх типів об’єктів або з розрізненням лише між контейнерами (наприклад, папками) та неконтейнерами (наприклад, файлами). Наприклад, правило, яке дозволяє користувачам переглядати вміст папки, але не отримувати доступ до файлів у ній.
- **ACE для конкретних об’єктів**: Забезпечують точніший контроль, даючи змогу задавати правила для конкретних типів об’єктів або навіть окремих властивостей об’єкта. Наприклад, у каталозі користувачів правило може дозволяти користувачу змінювати свій номер телефону, але не години входу.

Кожна ACE містить важливу інформацію: до кого застосовується правило (за допомогою ідентифікатора безпеки, або SID), що правило дозволяє чи забороняє (за допомогою маски доступу) і як воно успадковується іншими об’єктами.

#### Ключові відмінності між типами ACE

- **Узагальнені ACE** підходять для простих сценаріїв контролю доступу, де те саме правило застосовується до всіх аспектів об’єкта або до всіх об’єктів у контейнері.
- **ACE для конкретних об’єктів** використовуються у складніших сценаріях, зокрема в середовищах на кшталт Active Directory, де може знадобитися окремо контролювати доступ до певних властивостей об’єкта.

Підсумовуючи, ACL і ACE допомагають точно визначати контроль доступу, гарантуючи, що доступ до конфіденційної інформації чи ресурсів мають лише потрібні особи або групи. Вони дають змогу налаштовувати права доступу аж до рівня окремих властивостей або типів об’єктів.

### Структура запису контролю доступу

| Поле ACE | Опис |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тип        | Прапорець, що визначає тип ACE. Windows 2000 і Windows Server 2003 підтримують шість типів ACE: три узагальнені типи ACE, які застосовуються до всіх захищених об’єктів, і три типи ACE для конкретних об’єктів, які можуть застосовуватися до об’єктів Active Directory. |
| Прапорці       | Набір бітових прапорців, які керують успадкуванням і аудитом. |
| Розмір        | Кількість байтів пам’яті, виділених для ACE. |
| Маска доступу | 32-бітове значення, біти якого відповідають правам доступу до об’єкта. Біти можна встановлювати або скидати, але їхнє значення залежить від типу ACE. Наприклад, якщо встановлено біт, що відповідає за право читати дозволи, а тип ACE — Deny, ACE забороняє читати дозволи об’єкта. Якщо той самий біт встановлено, а тип ACE — Allow, ACE надає право читати дозволи об’єкта. Докладніше про маску доступу див. у наступній таблиці. |
| SID         | Визначає користувача або групу, доступ яких контролює або відстежує ця ACE. |

### Структура маски доступу

| Біт (діапазон) | Значення                            | Опис/приклад                       |
| ----------- | ---------------------------------- | ----------------------------------------- |
| 0 - 15      | Спеціальні права доступу до об’єкта      | Читання даних, виконання, додавання даних           |
| 16 - 22     | Стандартні права доступу             | Видалення, запис ACL, запис власника            |
| 23          | Доступ до ACL безпеки            |                                           |
| 24 - 27     | Зарезервовано                           |                                           |
| 28          | Загальний дозвіл ALL (читання, запис, виконання) | Усе наведене нижче                          |
| 29          | Загальний дозвіл на виконання                    | Усе необхідне для виконання програми |
| 30          | Загальний дозвіл на запис                      | Усе необхідне для запису у файл   |
| 31          | Загальний дозвіл на читання                       | Усе необхідне для читання файлу       |
