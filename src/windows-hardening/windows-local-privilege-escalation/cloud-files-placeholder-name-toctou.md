# Double-Fetch буфера користувача Windows, відображеного через MDL

{{#include ../../banners/hacktricks-training.md}}

Драйвер ядра Windows створює double-fetch, коли перевіряє дані на сторінках, що належать викликачеві, а пізніше передає вказівник на ті самі сторінки API, чутливому до безпеки. Блокування та відображення сторінок не робить їхній вміст незмінним. CVE-2025-55680 у `cldflt.sys` демонструє цей шаблон: драйвер перевірив відносне ім’я Cloud Files placeholder, а потім створив об’єкт, продовжуючи використовувати змінюваний буфер викликач<sup>[[1]](#references)[[3]](#references)</sup>.

`CfCreatePlaceholders()` створює файли або каталоги в зареєстрованому корені синхронізації Cloud Files. У вразливому шляху зміна імені після перевірки могла спрямувати привілейоване створення за межі цього кореня.<sup>[[1]](#references)[[2]](#references)</sup>

## Чому блокування сторінок не заблокувало дані

У вразливому шляху `HsmpOpCreatePlaceholders()` виділяв MDL для даних виклику, викликав `ProbeForRead()` і `MmProbeAndLockPages()`, а потім відображав ці сторінки у віртуальному адресному просторі ядра. MDL описує та блокує фізичні сторінки, щоб вони залишалися в пам’яті. Він **не** створює знімок їхніх байтів. Тому код у режимі користувача може змінювати ту саму фізичну пам’ять, поки драйвер читає її через системне відображення.<sup>[[1]](#references)[[3]](#references)</sup>

Відповідний шлях обробки запиту та використання даних був таким:<sup>[[1]](#references)</sup>

1. `cldapi.dll` надсилав керувальний код Cloud Files `0x903BC` із тегом `IO_REPARSE_TAG_CLOUD` (`0x9000001A`) та операцією створення placeholder `0xC0000001`.
2. Кожен запис даних містив пари 16-бітних зміщень і довжин для відносного імені та ідентифікатора файлу. Більшість фіксованих полів копіювалися в запис на стеку, але ім’я змінної довжини залишалося на відображених сторінках користувача.
3. Драйвер сканував ім’я в UTF-16 та відхиляв зворотну скісну риску або двокрапку.
4. Потім він створював `UNICODE_STRING`, поле `Buffer` якого й надалі вказувало на відображені дані запиту, і присвоював його полю `OBJECT_ATTRIBUTES.ObjectName`.
5. `FltCreateFileEx2()` повторно читав дані за цим вказівником. Тому паралельний записувач міг змусити перевірку побачити один рядок, а створення файлу — інший.

Це **double-fetch**, навіть якщо обидва читання виконуються через віртуальну адресу ядра: межа безпеки залежить від базового сховища даних, а не від того, яке віртуальне відображення використовує драйвер для розіменування вказівника.<sup>[[1]](#references)</sup>

## Схема гонки Cloud Files

Описана стратегія експлуатації використовувала повторні запити, потоки-мутатори та junction, щоб перетворити double-fetch на перенаправлення шляху:<sup>[[1]](#references)</sup>

1. Зареєструвати контрольований зловмисником каталог за допомогою `CfRegisterSyncRoot()` і створити в ньому `JUSTASTRING` як junction на захищене місце призначення.
2. Підготувати спільний запис placeholder із коректним одноелементним іменем `JUSTASTRINGDnewfile.dll`.
3. Налаштувати потоки-мутатори, щоб вони змінювали кодову одиницю `D` у UTF-16 між `D` та `\`. Друге представлення — `JUSTASTRING\newfile.dll`.
4. Паралельно змусити робочі потоки багаторазово надсилати запити на створення placeholder, що посилаються на ті самі дані, а монітор нехай перевіряє захищене місце призначення.
5. Вдалий цикл перевіряє представлення без роздільника, а потім переходить за junction, коли пізніший виклик створення бачить представлення з `\`.

Цей примітив дає змогу створити захищений файл або каталог. Для виконання коду все ще потрібен контроль над вмістом створеного файлу та привілейований споживач, наприклад відповідна ціль для DLL side-loading. В оригінальному аналізі використовувався такий завершальний ланцюжок, але завантажувач, payload і повноцінний автономний експлойт не публікувалися.<sup>[[1]](#references)</sup>

Додаткові методи навмисного розширення гонок під час пошуку шляхів у Windows описано в статті [Експлуатація race condition ядра через повільні шляхи Object Manager](kernel-race-condition-object-manager-slowdown.md).
