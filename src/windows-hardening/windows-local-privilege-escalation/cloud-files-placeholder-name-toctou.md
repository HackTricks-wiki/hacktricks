# Windows Double-Fetch σε buffer χρήστη χαρτογραφημένο με MDL

{{#include ../../banners/hacktricks-training.md}}

Ένα πρόγραμμα οδήγησης πυρήνα των Windows δημιουργεί double-fetch όταν επικυρώνει δεδομένα σε σελίδες που υποστηρίζονται από τον καλούντα και αργότερα περνά έναν δείκτη προς τις ίδιες σελίδες σε ένα API ευαίσθητο ως προς την ασφάλεια. Το κλείδωμα και η χαρτογράφηση των σελίδων δεν καθιστούν αμετάβλητα τα περιεχόμενά τους. Το CVE-2025-55680 στο `cldflt.sys` παρουσιάζει αυτό το μοτίβο: το πρόγραμμα οδήγησης επικύρωσε το σχετικό όνομα ενός placeholder του Cloud Files και στη συνέχεια δημιούργησε το αντικείμενο ενώ εξακολουθούσε να χρησιμοποιεί το μεταβλητό buffer του καλούντος.<sup>[[1]](#references)[[3]](#references)</sup>

Η `CfCreatePlaceholders()` δημιουργεί αρχεία ή καταλόγους κάτω από μια εγγεγραμμένη ρίζα συγχρονισμού του Cloud Files. Στην ευάλωτη διαδρομή, η αλλαγή του ονόματος μετά την επικύρωση μπορούσε να ανακατευθύνει τη δημιουργία με αυξημένα δικαιώματα εκτός αυτής της ρίζας.<sup>[[1]](#references)[[2]](#references)</sup>

## Γιατί το κλείδωμα των σελίδων δεν κλείδωσε τα δεδομένα

Η ευάλωτη διαδρομή `HsmpOpCreatePlaceholders()` δέσμευε ένα MDL για το payload του καλούντος, καλούσε τις `ProbeForRead()` και `MmProbeAndLockPages()` και χαρτογραφούσε αυτές τις σελίδες στον εικονικό χώρο διευθύνσεων του πυρήνα. Ένα MDL περιγράφει και κλειδώνει τις φυσικές σελίδες ώστε να παραμένουν στη μνήμη. **Δεν** δημιουργεί στιγμιότυπο των byte τους. Επομένως, η λειτουργία χρήστη μπορεί να τροποποιεί την ίδια φυσική μνήμη ενώ το πρόγραμμα οδήγησης τη διαβάζει μέσω της χαρτογράφησης συστήματος.<sup>[[1]](#references)[[3]](#references)</sup>

Η σχετική διαδρομή αιτήματος και χρήσης ήταν η εξής:<sup>[[1]](#references)</sup>

1. Το `cldapi.dll` έστελνε τον κωδικό ελέγχου Cloud Files `0x903BC` με tag `IO_REPARSE_TAG_CLOUD` (`0x9000001A`) και λειτουργία δημιουργίας placeholder `0xC0000001`.
2. Κάθε εγγραφή payload περιείχε ζεύγη offset/μήκους 16-bit για το σχετικό όνομα και την ταυτότητα του αρχείου. Τα περισσότερα σταθερά πεδία αντιγράφονταν σε μια εγγραφή στο stack, αλλά το όνομα μεταβλητού μήκους παρέμενε στις χαρτογραφημένες σελίδες χρήστη.
3. Το πρόγραμμα οδήγησης σάρωνε το όνομα UTF-16 και απέρριπτε κάθε backslash ή άνω και κάτω τελεία.
4. Στη συνέχεια, δημιουργούσε ένα `UNICODE_STRING` του οποίου το `Buffer` εξακολουθούσε να δείχνει στο χαρτογραφημένο payload και το εκχωρούσε στο `OBJECT_ATTRIBUTES.ObjectName`.
5. Η `FltCreateFileEx2()` διάβαζε ξανά αυτόν τον δείκτη. Έτσι, ένας παράλληλος writer μπορούσε να κάνει την επικύρωση να δει μία συμβολοσειρά και τη δημιουργία αρχείου να δει μια άλλη.

Αυτό είναι **double-fetch**, παρόλο που και οι δύο αναγνώσεις χρησιμοποιούν εικονική διεύθυνση πυρήνα: το όριο ασφαλείας εξαρτάται από τον χώρο αποθήκευσης που υποστηρίζει τα δεδομένα, όχι από το ποια εικονική χαρτογράφηση αποαναφέρει το πρόγραμμα οδήγησης.<sup>[[1]](#references)</sup>

## Διάταξη race στο Cloud Files

Η δημοσιοποιημένη στρατηγική exploit χρησιμοποιούσε επαναλαμβανόμενα αιτήματα, νήματα τροποποίησης και ένα junction για να μετατρέψει το double-fetch σε ανακατεύθυνση διαδρομής:<sup>[[1]](#references)</sup>

1. Εγγράψτε έναν κατάλογο που ελέγχει ο επιτιθέμενος με την `CfRegisterSyncRoot()` και δημιουργήστε μέσα του το `JUSTASTRING` ως junction προς έναν προστατευμένο προορισμό.
2. Προετοιμάστε μια κοινόχρηστη εγγραφή placeholder με το έγκυρο όνομα ενός συστατικού `JUSTASTRINGDnewfile.dll`.
3. Βάλτε τα νήματα τροποποίησης να εναλλάσσουν τον κωδικό μονάδας `D` UTF-16 μεταξύ `D` και `\`. Η δεύτερη αναπαράσταση είναι `JUSTASTRING\newfile.dll`.
4. Παράλληλα, βάλτε τα νήματα worker να υποβάλλουν επανειλημμένα αιτήματα δημιουργίας placeholder που αναφέρονται στο ίδιο payload, ενώ ένα monitor ελέγχει τον προστατευμένο προορισμό.
5. Σε μια επιτυχημένη επανάληψη, επικυρώνεται η αναπαράσταση χωρίς διαχωριστικό και στη συνέχεια ακολουθείται το junction όταν η μεταγενέστερη δημιουργία δει την αναπαράσταση που περιέχει `\`.

Η primitive επιτρέπει μόνο τη δημιουργία προστατευμένων αρχείων ή καταλόγων. Για να μετατραπεί σε εκτέλεση κώδικα απαιτείται ακόμη έλεγχος του περιεχομένου του αρχείου που δημιουργήθηκε και ένας προνομιούχος καταναλωτής, όπως ένας κατάλληλος στόχος DLL side-loading. Η αρχική ανάλυση χρησιμοποίησε αυτήν την τελική κατηγορία αλυσίδας, αλλά δεν δημοσίευσε τον loader, το payload ή ένα πλήρες, αυτόνομο exploit.<sup>[[1]](#references)</sup>

Για συμπληρωματικές τεχνικές που διευρύνουν σκόπιμα τα race κατά την αναζήτηση διαδρομών στα Windows, δείτε [Εκμετάλλευση race condition πυρήνα μέσω αργών διαδρομών του Object Manager](kernel-race-condition-object-manager-slowdown.md).
