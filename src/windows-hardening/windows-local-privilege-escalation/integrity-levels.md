## Рівні цілісності

У Windows Vista та пізніших версіях об'єкти, які можна захищати, можуть мати мітку **рівня цілісності**. Більшість об'єктів розглядаються як об'єкти із середнім рівнем цілісності, тоді як певні розташування, призначені для застосунків із низьким рівнем цілісності, можуть бути позначені як такі, що мають низький рівень. Процеси, запущені стандартними користувачами, зазвичай працюють із середнім рівнем цілісності, підвищені застосунки працюють із високим рівнем цілісності, а багато служб працюють із системним рівнем цілісності.<sup>[[1]](#references)</sup>

Ключове правило полягає в тому, що процеси з нижчим рівнем цілісності не можуть змінювати об'єкти з вищим рівнем цілісності. Windows застосовує цю перевірку Mandatory Integrity Control (MIC) перед перевіркою довільного списку керування доступом (DACL) об'єкта. Найпоширеніші рівні:<sup>[[1]](#references)[[2]](#references)</sup>

- **Untrusted**: Найнижчий рівень, представлений `SECURITY_MANDATORY_UNTRUSTED_RID`. Як приклад із реального світу, Windows sandbox у Chromium спочатку призначає цілям у sandbox низький рівень цілісності, а потім після запуску знижує рівень цілісності цілей renderer до Untrusted.<sup>[[5]](#references)</sup>
- **Low**: Переважно використовується для взаємодії з інтернетом, особливо в Protected Mode Internet Explorer, впливаючи на пов'язані файли та процеси, а також на певні папки, як-от **Temporary Internet Folder**. Процеси з низьким рівнем цілісності мають значні обмеження, зокрема не мають доступу на запис до реєстру та мають обмежений доступ на запис до профілю користувача.
- **Medium**: Стандартний рівень для більшості операцій, призначений стандартним користувачам і об'єктам без певних рівнів цілісності. Навіть члени групи Administrators за замовчуванням працюють із цим рівнем.
- **High**: Зарезервований для адміністраторів, дає їм змогу змінювати об'єкти з нижчими рівнями цілісності, зокрема об'єкти з самим високим рівнем.
- **System**: Найвищий операційний рівень для ядра Windows і основних служб, недоступний навіть адміністраторам, що забезпечує захист критично важливих системних функцій.

Windows також визначає значення цілісності protected process, яке розташоване вище за System. Однак **TrustedInstaller** є ідентифікатором служби Windows, а не окремим рівнем MIC; його можливість змінювати захищені ресурси операційної системи зумовлена дозволами, наданими цьому ідентифікатору.

Визначити рівень цілісності процесу можна за допомогою **Process Explorer** від **Sysinternals**, відкривши властивості процесу та переглянувши вкладку **Security**:<sup>[[3]](#references)</sup>

### Рівні цілісності у файловій системі

Об'єкт у файловій системі може мати **мінімальну вимогу щодо рівня цілісності**. Процес із нижчим рівнем підпадає під обов'язкову політику об'єкта, навіть якщо його DACL в інших випадках надавав би доступ. Наприклад, створіть звичайний файл у консолі стандартного користувача та перевірте його дозволи:<sup>[[1]](#references)[[4]](#references)</sup>
```
echo asd >asd.txt
icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
```
Тепер призначте файлу мінімальний рівень цілісності **High**. Це **має бути виконано з консолі**, запущеної **від імені адміністратора**, оскільки звичайна консоль працює з рівнем цілісності Medium і **не зможе призначити рівень цілісності High об’єкту**:
```
icacls asd.txt /setintegritylevel(oi)(ci) High
processed file: asd.txt
Successfully processed 1 files; Failed processing 0 files

C:\Users\Public>icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
Mandatory Label\High Mandatory Level:(NW)
```
Користувач `DESKTOP-IDJHTKP\user` має **FULL privileges** щодо файлу, оскільки саме цей користувач його створив. Однак обов’язкова мітка не дозволяє користувачеві змінювати файл, якщо процес працює не на рівні High integrity. Користувач усе ще може читати його, оскільки відображена обов’язкова політика має значення `(NW)`, тобто no-write-up:
```
echo 1234 > asd.txt
Access is denied.

del asd.txt
C:\Users\Public\asd.txt
Access is denied.
```
> [!TIP]
> **Отже, якщо для файлу встановлено мінімальний рівень цілісності, для його зміни потрібно працювати щонайменше на цьому рівні цілісності.**

### Рівні цілісності у бінарних файлах

У наведеному прикладі використовується копія `cmd.exe` за адресою `C:\Windows\System32\cmd-low.exe`, якій **з консолі адміністратора призначається низький рівень цілісності**:
```
icacls C:\Windows\System32\cmd-low.exe
C:\Windows\System32\cmd-low.exe NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Administrators:(I)(F)
BUILTIN\Users:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL RESTRICTED APP PACKAGES:(I)(RX)
Mandatory Label\Low Mandatory Level:(NW)
```
Тепер, коли я запускаю `cmd-low.exe`, він **працює з низьким рівнем цілісності** замість середнього:

![Рівні цілісності у файловій системі — Рівні цілісності у двійкових файлах: тепер, коли я запускаю cmd-low.exe, він працює з низьким рівнем цілісності замість середнього](<../../images/image (313).png>)

Призначення двійковому файлу мітки високого рівня цілісності (`icacls C:\Windows\System32\cmd-high.exe /setintegritylevel high`) не змушує його автоматично запускатися з високим рівнем цілісності. Якщо його викликає процес із середнім рівнем цілісності, він працює із середнім рівнем цілісності, оскільки новий процес отримує нижчий із рівнів цілісності виконуваного файлу та процесу, що його викликає.<sup>[[1]](#references)</sup>

### Рівні цілісності процесів

Не всі файли та папки мають явну мінімальну мітку цілісності, **але кожен процес працює з певним рівнем цілісності**. Як і у випадку з об’єктами файлової системи, **процес, якому потрібен доступ на запис до іншого процесу, повинен мати щонайменше такий самий рівень цілісності**. Тому процес із низьким рівнем цілісності не може відкрити процес із середнім рівнем цілісності з повним доступом.<sup>[[1]](#references)</sup>

Через ці обмеження найбезпечніший підхід полягає в тому, щоб **запускати кожен процес із найнижчим рівнем цілісності, який усе ще дає змогу виконувати призначену йому роботу**.
