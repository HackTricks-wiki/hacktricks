## Рівні цілісності

У Windows Vista та новіших версіях об'єкти, які можна захищати, можуть містити мітку **рівня цілісності**. Більшість об'єктів вважаються такими, що мають середній рівень цілісності, тоді як певні розташування, призначені для застосунків із низьким рівнем цілісності, можуть мати мітку низького рівня. Процеси, запущені стандартними користувачами, зазвичай працюють із середнім рівнем цілісності, підвищені застосунки працюють із високим рівнем цілісності, а багато служб працюють із системним рівнем цілісності.<sup>[[1]](#references)</sup>

Ключове правило полягає в тому, що процеси з нижчим рівнем цілісності, ніж рівень об'єкта, не можуть змінювати цей об'єкт. Windows застосовує цю перевірку Mandatory Integrity Control (MIC) перед оцінюванням дискреційного списку керування доступом (DACL) об'єкта. Найчастіше зустрічаються такі рівні:<sup>[[1]](#references)[[2]](#references)</sup>

- **Untrusted**: Найнижчий рівень, представлений `SECURITY_MANDATORY_UNTRUSTED_RID` (`S-1-16-0`). Не плутайте цю мітку цілісності з ідентичністю **Anonymous Logon** (`S-1-5-7`); ідентичності автентифікації та мітки MIC належать до окремих просторів імен SID. Реальним прикладом є пісочниця Chromium для Windows, яка спочатку призначає ізольованим цілям рівень цілісності Low, а після запуску знижує рівень цілісності цілей renderer до Untrusted.<sup>[[5]](#references)[[6]](#references)</sup>
- **Low**: Переважно використовується для взаємодії з інтернетом, особливо в Protected Mode Internet Explorer, впливаючи на пов'язані файли та процеси, а також на певні папки, як-от **Temporary Internet Folder**. Процеси з низьким рівнем цілісності мають значні обмеження, зокрема не можуть записувати до реєстру та мають обмежений доступ на запис до профілю користувача.
- **Medium**: Стандартний рівень для більшості операцій, призначений стандартним користувачам і об'єктам без явно заданих рівнів цілісності. Навіть члени групи Administrators за замовчуванням працюють із цим рівнем.
- **High**: Зарезервований для адміністраторів, дозволяє їм змінювати об'єкти з нижчими рівнями цілісності, зокрема об'єкти, які мають сам рівень High.
- **System**: Найвищий операційний рівень для ядра Windows і основних служб, недоступний навіть адміністраторам, що забезпечує захист життєво важливих системних функцій.

Windows також визначає значення цілісності захищеного процесу, яке є вищим за System. Однак **TrustedInstaller** є ідентичністю служби Windows, а не окремим рівнем MIC; його здатність змінювати захищені ресурси операційної системи зумовлена дозволами, наданими цій ідентичності.

Не припускайте, що таке розташування, як коренева папка системного диска, завжди має фіксовану мітку цілісності High. Перевірте ефективний DACL і будь-яку явну обов'язкову мітку за допомогою `icacls`; об'єкт без мітки для MIC вважається таким, що має рівень Medium, тоді як його DACL і власник усе одно можуть незалежно обмежувати доступ.<sup>[[1]](#references)[[4]](#references)</sup>

Отримати рівень цілісності процесу можна за допомогою **Process Explorer** від **Sysinternals**, відкривши властивості процесу та переглянувши вкладку **Security**:<sup>[[3]](#references)</sup>

### Рівні цілісності у файловій системі

Об'єкт у файловій системі може мати **мінімальну вимогу до рівня цілісності**. До процесу, рівень якого нижчий за цей, застосовується обов'язкова політика об'єкта, навіть якщо його DACL в іншому випадку надав би доступ. Наприклад, створіть звичайний файл із консолі стандартного користувача та перевірте його дозволи:<sup>[[1]](#references)[[4]](#references)</sup>
```
echo asd >asd.txt
icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
```
Тепер призначте файлу мінімальний рівень цілісності **High**. Це **потрібно виконати з консолі**, запущеної **від імені адміністратора**, оскільки звичайна консоль працює з рівнем цілісності Medium і **не зможе призначити рівень High об’єкту**:
```
icacls asd.txt /setintegritylevel(oi)(ci) High
processed file: asd.txt
Successfully processed 1 files; Failed processing 0 files

C:\Users\Public>icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
Mandatory Label\High Mandatory Level:(NW)
```
Користувач `DESKTOP-IDJHTKP\user` має **повні привілеї** щодо файла, оскільки саме цей користувач його створив. Однак мандатна мітка не дозволяє користувачу змінювати файл, якщо процес не запущено з **високим рівнем цілісності**. Користувач усе ще може читати його, оскільки відображена мандатна політика має значення `(NW)`, тобто no-write-up:
```
echo 1234 > asd.txt
Access is denied.

del asd.txt
C:\Users\Public\asd.txt
Access is denied.
```
> [!TIP]
> **Отже, якщо для файлу встановлено мінімальний рівень цілісності, для його зміни потрібно працювати щонайменше на цьому рівні цілісності.**

### Рівні цілісності у двійкових файлах

У наведеному прикладі використовується копія `cmd.exe` за шляхом `C:\Windows\System32\cmd-low.exe`, якій **з консолі адміністратора призначається низький рівень цілісності**:
```
icacls C:\Windows\System32\cmd-low.exe
C:\Windows\System32\cmd-low.exe NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Administrators:(I)(F)
BUILTIN\Users:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL RESTRICTED APP PACKAGES:(I)(RX)
Mandatory Label\Low Mandatory Level:(NW)
```
Тепер, коли я запускаю `cmd-low.exe`, він **працюватиме на низькому рівні цілісності** замість середнього:

![Рівні цілісності у файловій системі - Рівні цілісності у двійкових файлах: Тепер, коли я запускаю cmd-low.exe, він працюватиме на низькому рівні цілісності замість середнього](<../../images/image (313).png>)

Призначення двійковому файлу мітки високого рівня цілісності (`icacls C:\Windows\System32\cmd-high.exe /setintegritylevel high`) не змушує його автоматично запускатися з високим рівнем цілісності. Якщо його викликати з процесу із середнім рівнем цілісності, він працюватиме із середнім рівнем цілісності, оскільки новий процес отримує нижчий із рівнів цілісності виконуваного файлу та процесу, який його викликає.<sup>[[1]](#references)</sup>

### Рівні цілісності у процесах

Не всі файли та папки мають явну мінімальну мітку цілісності, **але кожен процес працює на певному рівні цілісності**. Як і у випадку з об'єктами файлової системи, **процес, якому потрібен доступ на запис до іншого процесу, повинен мати щонайменше такий самий рівень цілісності**. Тому процес із низьким рівнем цілісності не може відкрити процес із середнім рівнем цілісності з повним доступом.<sup>[[1]](#references)</sup>

Через ці обмеження найбезпечніший підхід — **запускати кожен процес на найнижчому рівні цілісності, який усе ще дає йому змогу виконувати призначену роботу**.
