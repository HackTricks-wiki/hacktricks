## Рівні цілісності

У Windows Vista та пізніших версіях усі захищені елементи мають мітку **рівня цілісності**. Зазвичай файлам і ключам реєстру призначається рівень цілісності «середній», за винятком певних папок і файлів, до яких Internet Explorer 7 може записувати дані на низькому рівні цілісності. За замовчуванням процеси, ініційовані стандартними користувачами, мають середній рівень цілісності, тоді як служби зазвичай працюють на системному рівні цілісності. Мітка високого рівня цілісності захищає кореневий каталог.

Ключове правило полягає в тому, що процеси з нижчим рівнем цілісності не можуть змінювати об'єкти з вищим рівнем цілісності. Існують такі рівні цілісності:

- **Ненадійний**: Цей рівень призначений для процесів з анонімними входами. Приклад: Chrome
- **Низький**: Переважно використовується для взаємодії з інтернетом, особливо в захищеному режимі Internet Explorer, впливаючи на пов'язані файли та процеси, а також на певні папки, як-от **Temporary Internet Folder**. Процеси з низьким рівнем цілісності мають значні обмеження, зокрема не можуть записувати до реєстру та мають обмежений доступ на запис до профілю користувача.
- **Середній**: Рівень за замовчуванням для більшості операцій, призначений стандартним користувачам і об'єктам без явно визначених рівнів цілісності. Навіть члени групи Administrators за замовчуванням працюють на цьому рівні.
- **Високий**: Зарезервований для адміністраторів, дозволяє їм змінювати об'єкти з нижчими рівнями цілісності, зокрема об'єкти з високим рівнем.
- **Системний**: Найвищий операційний рівень для ядра Windows і основних служб, недоступний навіть адміністраторам, що забезпечує захист критично важливих системних функцій.
- **Installer**: Унікальний рівень, що стоїть вище за всі інші та дає змогу об'єктам на цьому рівні видаляти будь-які інші об'єкти.

Ви можете переглянути рівень цілісності процесу за допомогою **Process Explorer** від **Sysinternals**, відкривши **властивості** процесу та перейшовши на вкладку "**Security**":

### Рівні цілісності у файловій системі

Об'єкт у файловій системі може мати вимогу щодо **мінімального рівня цілісності**, і якщо процес не має цього рівня цілісності, він не зможе взаємодіяти з ним.\
Наприклад, **створімо файл зі звичайної консолі від імені звичайного користувача та перевірмо дозволи**:
```
echo asd >asd.txt
icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
```
Тепер призначимо файлу мінімальний рівень цілісності **High**. Це **потрібно виконати з консолі**, запущеної **від імені адміністратора**, оскільки **звичайна консоль** працюватиме з рівнем цілісності Medium і **не матиме дозволу** призначати об’єкту рівень цілісності High:
```
icacls asd.txt /setintegritylevel(oi)(ci) High
processed file: asd.txt
Successfully processed 1 files; Failed processing 0 files

C:\Users\Public>icacls asd.txt
asd.txt BUILTIN\Administrators:(I)(F)
DESKTOP-IDJHTKP\user:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\INTERACTIVE:(I)(M,DC)
NT AUTHORITY\SERVICE:(I)(M,DC)
NT AUTHORITY\BATCH:(I)(M,DC)
Mandatory Label\High Mandatory Level:(NW)
```
Саме тут стає цікаво. Ви можете бачити, що користувач `DESKTOP-IDJHTKP\user` має **ПОВНІ привілеї** щодо файлу (власне, саме цей користувач створив файл), однак через реалізований мінімальний рівень цілісності він більше не зможе змінювати файл, якщо не працюватиме в середовищі з високим рівнем цілісності (зверніть увагу, що він зможе його читати):
```
echo 1234 > asd.txt
Access is denied.

del asd.txt
C:\Users\Public\asd.txt
Access is denied.
```
> [!TIP]
> **Отже, коли файл має мінімальний рівень цілісності, для його зміни потрібно працювати щонайменше на цьому рівні цілісності.**

### Рівні цілісності у бінарних файлах

Я створив копію `cmd.exe` у `C:\Windows\System32\cmd-low.exe` і встановив для неї **низький рівень цілісності з консолі адміністратора:**
```
icacls C:\Windows\System32\cmd-low.exe
C:\Windows\System32\cmd-low.exe NT AUTHORITY\SYSTEM:(I)(F)
BUILTIN\Administrators:(I)(F)
BUILTIN\Users:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL APPLICATION PACKAGES:(I)(RX)
APPLICATION PACKAGE AUTHORITY\ALL RESTRICTED APP PACKAGES:(I)(RX)
Mandatory Label\Low Mandatory Level:(NW)
```
Тепер, коли я запускаю `cmd-low.exe`, він **працюватиме з низьким рівнем цілісності** замість середнього:

![Рівні цілісності у файловій системі — Рівні цілісності у бінарних файлах: Тепер, коли я запускаю cmd-low.exe, він працюватиме з низьким рівнем цілісності замість середнього](<../../images/image (313).png>)

Для допитливих: якщо призначити бінарному файлу високий рівень цілісності (`icacls C:\Windows\System32\cmd-high.exe /setintegritylevel high`), він не запускатиметься автоматично з високим рівнем цілісності (якщо викликати його із середнього рівня цілісності — за замовчуванням — він працюватиме із середнім рівнем цілісності).

### Рівні цілісності у процесах

Не всі файли та папки мають мінімальний рівень цілісності, **але всі процеси працюють із певним рівнем цілісності**. І так само, як у випадку з файловою системою, **якщо процес хоче записувати дані в інший процес, він повинен мати щонайменше такий самий рівень цілісності**. Це означає, що процес із низьким рівнем цілісності не може відкрити handle із повним доступом до процесу із середнім рівнем цілісності.

Через обмеження, описані в цьому та попередньому розділах, із погляду безпеки завжди **рекомендується запускати процес із якомога нижчим рівнем цілісності**.
