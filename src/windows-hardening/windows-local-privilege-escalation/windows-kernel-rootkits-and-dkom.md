# Windows Kernel Rootkits and DKOM

{{#include ../../banners/hacktricks-training.md}}

## Scope

Імплант після компрометації може завантажити підписаний kernel driver як service і надати control plane з user mode через `IRP_MJ_DEVICE_CONTROL`. Підпис driver лише підтверджує, що Windows приймає image; це не робить авторизацію IOCTL, операції з пам'яттю, callbacks або hooks безпечними. Один проаналізований rootkit використовував три handlers під час штатної роботи, але надавав десятки додаткових post-exploitation primitives, тому reverse engineering має охоплювати весь dispatcher, а не лише запити, зафіксовані у trace malware.<sup>[[1]](#references)</sup>

## Signed-driver and IOCTL triage

Почніть із `DriverEntry`, зафіксуйте device objects і DOS symbolic links, знайдіть routine `MajorFunction[IRP_MJ_DEVICE_CONTROL]` і зіставте кожне порівняння або entry таблиці, що веде до handler. Зіставте імена, які відкриває user mode, з іменами, фактично створеними driver: в одному зафіксованому ланцюжку відкривався `\\.\msagent`, тоді як його driver створював `\Device\ToolTool` і `\DosDevices\ToolTool`. Ця невідповідність може вказувати на інший sample/configuration, відсутню setup logic або неузгодженість аналізу.<sup>[[1]](#references)</sup>

Декодуйте кожен control code перед відновленням його input structure.<sup>[[1]](#references)</sup>
```python
def decode_ioctl(code):
return {
"device_type": code >> 16,
"access": (code >> 14) & 3,
"function": (code >> 2) & 0xfff,
"method": code & 3,
}

for code in (0x2220F0, 0x222120, 0x2221E0):
print(hex(code), decode_ioctl(code))
```
Ці три коди декодуються як `FILE_DEVICE_UNKNOWN`, `FILE_ANY_ACCESS` і `METHOD_BUFFERED`. Це **не** доводить, що непривілейований викликач може їх досягти: також перевірте DACL пристрою, диспетчеризацію створення/відкриття, перевірки викликачів для кожного запиту, очікувані довжини буферів, вбудовані вказівники, обробку життєвого циклу PID і те, чи довіряє обробник PID або прапорцю, наданому викликачем.<sup>[[1]](#references)</sup>

Якщо implant використовує лише підмножину команд, згрупуйте решту обробників за примітивом, а не відкидайте їх як dead code. Один багатофункціональний драйвер надавав усі наведені нижче класи:<sup>[[1]](#references)</sup>

- **Керування/конфігурація:** перемикання стану rootkit; додавання, видалення, перевірка або очищення захищених шляхів, процесів і C2-адрес.
- **Маніпуляції процесами:** завершення PID, відображення його image, ін’єкція за допомогою `NtCreateThreadEx`, приховування/відновлення процесів або user modules і видалення захисту PPL.
- **Маніпуляції ядром:** від’єднання завантаженого драйвера, перелік/вимкнення/відновлення notification callbacks, ручне відображення іншого драйвера та запис за довільною адресою ядра.
- **Маніпуляції об’єктами:** видалення/розшифрування файлів і створення або зміна значень реєстру.

## Виключення для trusted processes

Корисним шаблоном проєктування є IOCTL, який реєструє PID разом із прапорцем **trusted**. Той самий пошук довіри потім використовується фільтрами файлів, реєстру, процесів і потоків: ненадійні інструменти отримують відфільтровані результати переліку, урізані права на handles або `STATUS_ACCESS_DENIED`, тоді як implant може й надалі оновлювати власні приховані об’єкти. Розглядайте це як межу авторизації та перевіряйте, як записи автентифікуються, синхронізуються й видаляються після завершення процесу або повторного використання PID.<sup>[[1]](#references)</sup>

Rootkits можуть зберігати політику у значеннях `REG_MULTI_SZ` і компілювати списки файлів, директорій, ключів реєстру, значень реєстру, ігнорованих image, захищених image і прихованих image у AVL-дерева. Під час аналізу простежте кожного читача й записувача цих спільних дерев; це пов’язує конфігурацію реєстру, IOCTL, callbacks і логіку фільтрації, навіть якщо назви функцій видалені.<sup>[[1]](#references)</sup>

## DKOM-приховування процесів і модулів

### `EPROCESS.ActiveProcessLinks`

Зміщення `ActiveProcessLinks` відрізняються залежно від збірки Windows. Rootkit, толерантний до версій, може перевірити відомі кандидати, а потім просканувати `EPROCESS` у пошуках узгодженого із самим собою `LIST_ENTRY`, сусіди якого вказують назад на кандидата. Він зберігає знайдене зміщення, приховує процес, повторно з’єднуючи `Flink`/`Blink` його сусідів, і зберігає стан, щоб пізніше знову приєднати запис. Процес продовжує працювати, але зникає з enumerators, які обходять список активних процесів.<sup>[[1]](#references)</sup>

Це **DKOM**, а не завершення. Виявлення має зіставляти результати на основі списків із незалежними доказами, такими як сканування pool/object, належність потоків, таблиці handles, артефакти scheduler і перевірка пам’яті ядра. Процес, видимий під час сканування, але відсутній у canonical list, є більш значущим, ніж будь-яке з цих представлень окремо.<sup>[[1]](#references)</sup>

### `PsLoadedModuleList`

Еквівалентний примітив приховування модуля знаходить цільовий запис у `PsLoadedModuleList` і змінює вказівники `Flink`/`Blink` суміжних записів. Драйвер залишається відображеним і виконуваним, але запити до модулів на основі списку його не показують. Порівняйте список loader із виконуваними відображеннями ядра, pool tags, об’єктами пристроїв/драйверів, ключами служб, адресами callbacks і dispatch pointers, які вказують за межі переліченого image.<sup>[[1]](#references)</sup>

## Захист і маскування на основі callbacks

Rootkit може поєднувати documented callback frameworks із DKOM і hooks:<sup>[[1]](#references)</sup>

- Обробники pre-operation у `ObRegisterCallbacks` для `PsProcessType` і `PsThreadType` видаляють права, що використовуються для завершення, доступу до VM, дублювання або маніпуляцій із потоками, коли ненадійний викликач відкриває захищену ціль. Зафіксуйте callback altitude і визначте модуль-власник кожної адреси callback.
- `PsSetCreateProcessNotifyRoutineEx` і `PsSetLoadImageNotifyRoutine` підтримують стан захищених/ігнорованих/прихованих процесів у міру появи процесів і image; одноразовий обхід процесів може додати об’єкти, що існували до реєстрації.
- Filesystem minifilter забороняє доступ до налаштованих шляхів. Незвичайна реалізація може створити свій ключ `Instances`, динамічно вибрати altitude і збільшувати його/повторювати спробу, коли `FltRegisterFilter` повідомляє про колізію.
- Процедура `CmRegisterCallbackEx` може приховувати захищені імена від переліку та забороняти пряме відкриття, перейменування, встановлення або видалення, одночасно звільняючи зареєстровані trusted processes від цих обмежень.

Зіставте реєстрації `ObRegisterCallbacks`, registry-callback altitudes, вивід `fltmc filters`, ключі служб `Instances` і адреси callbacks. Якщо звичайні інструменти фільтруються, перевірте ці структури з offline memory image або з іншого trusted acquisition layer.<sup>[[1]](#references)</sup>

## Фільтрація результатів Nsiproxy

Мережева маскування може бути націлена на `\Driver\Nsiproxy`: отримати об’єкт драйвера за допомогою `ObReferenceObjectByName`, зберегти вказівник на handler, замінити його wrapper-ом і видаляти повернуті IPv4 records, що відповідають C2-списку, керованому через IOCTL, перш ніж user mode отримає їх. Програми, що використовують дані NSI, після цього можуть більше не показувати з’єднання, хоча traffic усе ще існує.<sup>[[1]](#references)</sup>

Порівняйте подання з’єднань на host із packet capture, телеметрією WFP/ETW і network objects у пам’яті ядра. Також перевірте dispatch/handler pointers `Nsiproxy` і переконайтеся, що кожен із них знаходиться всередині очікуваного signed module; вказівник на unlisted mapping може пов’язати мережеву фільтрацію з DKOM у `PsLoadedModuleList`.<sup>[[1]](#references)</sup>

## Контрольний список розслідування

Найсильнішим сигналом є розбіжність між рівнями, а не одне ім’я файлу чи hash. Зіставте:<sup>[[1]](#references)</sup>

1. Створення kernel service і signed driver, чий вік сертифіката, видавець або шлях не відповідає встановленому продукту.
2. Створення пристрою, DOS links і IOCTL traffic, включно з невідповідністю імен пристроїв у user mode та kernel.
3. Запит на реєстрацію PID, після якого інші процеси не можуть відкрити, перелічити, змінити або видалити ті самі об’єкти.
4. Object/registry/process/image callbacks, екземпляри minifilter і hooks, адреси яких не належать нормально переліченому драйверу.
5. Відмінності між інвентаризаціями процесів, модулів, callbacks і мережі на основі списків та на основі сканування.
