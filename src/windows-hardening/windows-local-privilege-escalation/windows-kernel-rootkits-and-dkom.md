# Rootkit ядра Windows і DKOM

{{#include ../../banners/hacktricks-training.md}}

## Межі розгляду

Імплант, завантажений після компрометації, може завантажити підписаний драйвер ядра як службу та надати площину керування в user-mode через `IRP_MJ_DEVICE_CONTROL`. Підпис драйвера лише підтверджує, що Windows приймає образ; він не робить безпечними авторизацію IOCTL, операції з пам’яттю, callback-функції чи хуки. Один проаналізований rootkit використовував три обробники під час звичайної роботи, але надавав десятки додаткових примітивів для post-exploitation, тож під час реверс-інжинірингу потрібно дослідити весь диспетчер, а не лише запити, зафіксовані в трасуванні шкідливого ПЗ.<sup>[[1]](#references)</sup>

## Тріаж підписаного драйвера та IOCTL

Почніть із `DriverEntry`, зафіксуйте об’єкти пристроїв і символьні посилання DOS, знайдіть процедуру `MajorFunction[IRP_MJ_DEVICE_CONTROL]` і зіставте кожне порівняння або запис таблиці, що веде до обробника. Зіставте імена, які відкриває user-mode код, з іменами, які фактично створює драйвер: в одному з випадків ланцюжок відкривав `\\.\msagent`, тоді як драйвер створював `\Device\ToolTool` і `\DosDevices\ToolTool`. Ця невідповідність може вказувати на інший зразок/конфігурацію, відсутню логіку налаштування або неузгодженість аналізу.<sup>[[1]](#references)</sup>

Перш ніж відновлювати структуру вхідних даних, декодуйте кожен керівний код.<sup>[[1]](#references)</sup>

```python
def decode_ioctl(code):
    return {
        "device_type": code >> 16,
        "access": (code >> 14) & 3,
        "function": (code >> 2) & 0xfff,
        "method": code & 3,
    }

for code in (0x2220F0, 0x222120, 0x2221E0):
    print(hex(code), decode_ioctl(code))
```

Ці три коди декодуються як `FILE_DEVICE_UNKNOWN`, `FILE_ANY_ACCESS` і `METHOD_BUFFERED`. Це **не** доводить, що до них може звернутися непривілейований користувач: також перевірте DACL пристрою, диспетчеризацію create/open, перевірки виклику для кожного запиту, очікувану довжину буферів, вбудовані вказівники, обробку життєвого циклу PID і те, чи довіряє обробник PID або прапорцю, переданому викликачем.<sup>[[1]](#references)</sup>

Якщо імплант використовує лише частину команд, групуйте решту обробників за примітивами, а не відкидайте їх як мертвий код. Один багатофункціональний драйвер надавав усі наведені нижче можливості:<sup>[[1]](#references)</sup>

- **Керування/конфігурація:** перемикання стану rootkit; додавання, видалення, перегляд або очищення захищених шляхів, процесів і C2-адрес.
- **Маніпуляції процесами:** завершення PID, скасування відображення його образу, ін’єкція за допомогою `NtCreateThreadEx`, приховування/відновлення процесів або модулів користувача та зняття захисту PPL.
- **Маніпуляції ядром:** від’єднання завантаженого драйвера, перелічення/вимкнення/відновлення callback-функцій сповіщень, ручне відображення іншого драйвера та запис за довільною адресою ядра.
- **Маніпуляції об’єктами:** видалення/розшифрування файлів і створення або зміна значень реєстру.

## Ручне відображення ядра через вразливий підписаний драйвер

Підписаний драйвер із можливостями читання/запису пам’яті ядра може слугувати завантажувачем для непідписаного образу драйвера, не звертаючись до Windows із проханням завантажити цей образ як звичайний драйвер.<sup>[[2]](#references)[[7]](#references)</sup> Приклад LocalStranger відкриває наявний пристрій `\\.\WinNotify`; його вихідний код не доводить, що непривілейований користувач може встановити, запустити або відкрити драйвер на довільному хості.<sup>[[2]](#references)[[3]](#references)</sup> Мапер отримує шлях до образу, визначає базову адресу завантаженого ядра та використовує IOCTL для читання/запису віртуальної пам’яті пристрою.<sup>[[4]](#references)[[9]](#references)[[10]](#references)</sup>

Щоб перетворити цей доступ на читання/запис на виклик ядра, мапер зчитує immediate зі значенням PTE-base з `MmGetVirtualForPhysical` і проходить таблицю сторінок для адреси `NtAddAtom`.<sup>[[5]](#references)[[7]](#references)</sup> Формула обчислення PTE: `PteBase + ((VA >> 9) & 0x7FFFFFFFF8)`; код також перевіряє наявність PDE для великої сторінки.<sup>[[5]](#references)[[7]](#references)</sup> Він тимчасово дозволяє запис у відповідний запис, замінює запис системного виклику переходом до потрібної функції ядра, викликає stub `NtAddAtom` у режимі користувача, а потім відновлює початкові байти й запис сторінки.<sup>[[6]](#references)</sup>

Мапер використовує цей шлях виклику для `ExAllocatePool`, відображає PE-секції, імпорти й релокації в образ, записує його в область виділення та викликає точку входу.<sup>[[7]](#references)[[8]](#references)</sup> Ця реалізація приймає лише PE-образи x64 з підтримкою релокації; зчитування PTE-base також передбачає фіксоване розташування `MmGetVirtualForPhysical + 34`.<sup>[[5]](#references)[[8]](#references)</sup> Вважайте цей метод залежним від збірки, а не незалежним обходом KASLR чи доказом того, що HVCI або PatchGuard дозволяють таке відображення.<sup>[[5]](#references)[[8]](#references)</sup> Приклад використання читання/запису ядра лише для роботи з даними див. у розділі [Крадіжка токена SYSTEM](arbitrary-kernel-rw-token-theft.md).

## Винятки для довірених процесів

Корисний шаблон проєктування — IOCTL, який реєструє PID разом із прапорцем **trusted**. Ті самі дані про довіру потім використовують фільтри файлів, реєстру, процесів і потоків: недовірені інструменти отримують відфільтровані результати перелічення, обмежені права на дескриптори або `STATUS_ACCESS_DENIED`, тоді як імплант і далі може змінювати власні приховані об’єкти. Розглядайте це як межу авторизації та перевіряйте, як автентифікуються, синхронізуються й видаляються записи після завершення процесу або повторного використання PID.<sup>[[1]](#references)</sup>

Rootkit може зберігати політики у значеннях `REG_MULTI_SZ` і компілювати списки файлів, каталогів, ключів реєстру, значень реєстру, ігнорованих образів, захищених образів і прихованих образів у AVL-дерева. Під час аналізу відстежуйте всі функції, що читають і змінюють ці спільні дерева; це пов’язує конфігурацію реєстру, IOCTL, callback-функції та логіку фільтрації, навіть якщо назви функцій видалені.<sup>[[1]](#references)</sup>

## Приховування процесів і модулів через DKOM

### `EPROCESS.ActiveProcessLinks`

Зміщення `ActiveProcessLinks` відрізняються залежно від збірки Windows. Rootkit, стійкий до змін версій, може перевіряти відомі варіанти, а потім сканувати `EPROCESS` у пошуках узгодженого `LIST_ENTRY`, сусідні елементи якого вказують назад на цей запис. Він зберігає знайдене зміщення, приховує процес, повторно з’єднуючи `Flink`/`Blink` його сусідніх елементів, і зберігає стан, щоб пізніше відновити зв’язок запису. Процес продовжує працювати, але зникає з перелічувачів, які обходять список активних процесів.<sup>[[1]](#references)</sup>

Це **DKOM**, а не завершення процесу. Для виявлення слід зіставляти результати обходу списку з незалежними даними, як-от скануванням пулу/об’єктів, належністю потоків, таблицями дескрипторів, артефактами планувальника та аналізом пам’яті ядра. Процес, виявлений скануванням, але відсутній у канонічному списку, є значущішою ознакою, ніж будь-яке з цих спостережень окремо.<sup>[[1]](#references)</sup>

### `PsLoadedModuleList`

Еквівалентний примітив приховування модулів знаходить цільовий запис у `PsLoadedModuleList` і змінює вказівники `Flink`/`Blink` сусідніх елементів. Драйвер залишається відображеним і виконуваним, але запити до модулів, що спираються на список, його не показують. Зіставляйте список завантажувача з виконуваними відображеннями ядра, тегами пулу, об’єктами пристроїв/драйверів, ключами служб, адресами callback-функцій і вказівниками диспетчеризації, що ведуть за межі переліченого образу.<sup>[[1]](#references)</sup>

## Захист і маскування за допомогою callback-функцій

Rootkit може поєднувати документовані callback-механізми з DKOM і хуками:<sup>[[1]](#references)</sup>

- Обробники передопераційних подій `ObRegisterCallbacks` для `PsProcessType` і `PsThreadType` прибирають права, потрібні для завершення, доступу до VM, дублювання або маніпуляцій із потоками, коли недовірений викликач відкриває захищену ціль. Зафіксуйте altitude callback-функції та визначте модуль, якому належить кожна її адреса.
- `PsSetCreateProcessNotifyRoutineEx` і `PsSetLoadImageNotifyRoutine` підтримують стан захищених/ігнорованих/прихованих процесів у міру появи процесів та образів; одноразове сканування процесів може заповнити дані про об’єкти, що існували до реєстрації.
- Minifilter файлової системи забороняє доступ до налаштованих шляхів. Незвична реалізація може створити ключ `Instances`, динамічно вибрати altitude та збільшувати її значення з повторними спробами, якщо `FltRegisterFilter` повідомляє про конфлікт.
- Процедура `CmRegisterCallbackEx` може приховувати захищені імена під час перелічення та забороняти пряме відкриття, перейменування, встановлення або видалення, водночас надаючи винятки зареєстрованим довіреним процесам.

Зіставте реєстрації `ObRegisterCallbacks`, altitude callback-функцій реєстру, вивід `fltmc filters`, ключі служб `Instances` і адреси callback-функцій. Якщо звичайні інструменти фільтруються, перевіряйте ці структури за образом пам’яті, отриманим офлайн, або через інший довірений рівень збору даних.<sup>[[1]](#references)</sup>

## Фільтрація результатів Nsiproxy

Для приховування мережевої активності можна націлитися на `\Driver\Nsiproxy`: отримати об’єкт драйвера через `ObReferenceObjectByName`, зберегти вказівник на обробник, замінити його обгорткою та видалити з повернених записів IPv4 ті, що збігаються зі списком C2, яким керує IOCTL, перш ніж дані потраплять у режим користувача. Програми, що використовують відфільтровані дані NSI, можуть більше не показувати з’єднання, хоча трафік усе ще існує.<sup>[[1]](#references)</sup>

Зіставте дані про з’єднання на хості з перехопленням пакетів, телеметрією WFP/ETW і мережевими об’єктами в пам’яті ядра. Також перевірте вказівники диспетчеризації/обробників `Nsiproxy` і переконайтеся, що кожен із них вказує всередину очікуваного підписаного модуля; вказівник на невнесене до списку відображення може пов’язати фільтрацію мережі з DKOM у `PsLoadedModuleList`.<sup>[[1]](#references)</sup>

## Контрольний список розслідування

Найпереконливішою ознакою є розбіжність між рівнями, а не окреме ім’я файлу чи хеш. Зіставте:<sup>[[1]](#references)</sup>

1. Створення служби ядра та підписаний драйвер, вік сертифіката, видавець або шлях якого не узгоджується зі встановленим продуктом.
2. Створення пристрою, DOS-посилання та трафік IOCTL, зокрема невідповідність імен пристроїв у режимі користувача та ядрі.
3. Запит на реєстрацію PID, після якого інші процеси не можуть відкрити, перелічити, змінити чи видалити ті самі об’єкти.
4. Callback-функції об’єктів/реєстру/процесів/образів, екземпляри minifilter і хуки, адреси яких не належать жодному звичайно переліченому драйверу.
5. Відмінності між інвентаризаціями процесів, модулів, callback-функцій і мережі, побудованими на основі списків та сканування.
