# Віртуалізоване виконання payload і кастомне ухилення VM

{{#include ../banners/hacktricks-training.md}}

Віртуалізація payload компілює offensive-логіку в набір інструкцій guest і виконує її за допомогою native-інтерпретатора. На відміну від packer, якому зрештою потрібно відкрити оригінальні native-інструкції в пам’яті, віртуалізований payload може зберігати захищену логіку у вигляді bytecode протягом усього часу роботи. Це усуває саме це вікно розпакування, але **не** приховує поведінку, видиму host-системі, як-от syscalls, мережеву активність або межу викликів між VM і native-кодом.<sup>[[2]](#references)[[3]](#references)</sup>

## Повторне розміщення WebAssembly для ухилення від статичного аналізу

Замість редагування Go-інструмента, що має багато сигнатур, його можна скомпілювати як guest `wasip1` і вбудувати в окремий native-loader. Guest збирається на основі виправленого GOROOT, у якому непідтримувані операції, як-от `net.Dial`, `net.Listen`, `os/exec` і `os.Pipe`, делегуються через `//go:wasmimport`; host-модуль Wazero реалізує sockets, операції з процесами, виклики Win32 і виклики фреймворків macOS. Це зберігає використання Go API оригінальним проєктом, переміщуючи більшість його логіки в зашифрований WASM-модуль, який static PE-інструменти можуть не розпізнати.<sup>[[4]](#references)</sup>

### Передавання покажчиків лінійної пам’яті native API

Покажчик guest — це 32-бітне зміщення в лінійній пам’яті WASM, а не віртуальна адреса host. Перед native-викликом міст може перетворити аргумент лише тоді, коли він позначений як локальний покажчик і потрапляє в діапазон `0x10000 <= value < wasmMemorySize`; у результаті отримуємо `wasmMemoryBase + value`. Нижня межа запобігає перетворенню невеликих дескрипторів, прапорців і `nil`; маски для кожного API, згенеровані з `win32metadata`, відрізняють справжні покажчики від дескрипторів, розмірів і адрес у віддаленому процесі, а для неточних або неоднозначних метаданих передбачені перевизначення.<sup>[[4]](#references)</sup>

Native API також можуть повертати host-покажчики через вихідні буфери guest. Таблиця відповідностей може призначати таким об’єктам представлення в пам’яті guest і зберігати зворотне відображення на вихідну host-адресу. Для COM потрібно відображати як інтерфейс, так і його vtable: на покажчики даних можна переходити й відображати їх, тоді як виконувані покажчики в регіонах `MEM_IMAGE` мають залишатися непрозорими токенами, оскільки WASM не може виконувати native-інструкції. Ця модель безпосередньо не підтримує API з callback-викликами від host до guest, як-от `EnumWindows` або `SetWindowsHookEx`.<sup>[[4]](#references)</sup>

### Поліморфізм WASM VM для кожної збірки

Runtime і payload можна трансформувати разом під час кожної збірки: перемішувати таблицю відповідностей opcode і handler, переписувати кожен opcode guest відповідно до нового відображення, рандомізувати ідентифікатори секцій, замінювати стандартну магічну послідовність `\0asm` на маркер для конкретної збірки та змінювати магічні значення кешу runtime. Той самий вихідний код у результаті дає модулі, що відрізняються на рівні байтів, а звичайні WASM-інструменти не можуть розібрати payload, доки аналітик не відновить кастомне відображення й обрамлення з host-loader.<sup>[[4]](#references)</sup>

Для реверс-інжинірингу починайте з native-host, а не лише з пошуку `\0asm`: визначте скомпільований маркер, шлях розшифрування модуля, таблицю dispatch opcode і реєстрації host-функцій `env`, а потім відновіть стандартний модуль або інструментуйте межу імпорту. Міст залишається корисною точкою спостереження за поведінкою, оскільки через нього проходять виклики для мережевих операцій, створення процесів, доступу до реєстру, динамічного завантаження та загального dispatch Win32, навіть якщо вбудований bytecode змінюється між збірками.<sup>[[4]](#references)</sup>

### Маскування зовнішнього виконуваного файла Go

Зміна лише guest усе одно залишає впізнаваний loader. Продемонстровані трансформації зовнішнього binary додають до `gopclntab` щільні профілі символів, зібрані з легітимних Go-проєктів, обертають невеликий правдоподібний набір імпортів DLL і змінюють PE `VERSIONINFO` та рядки ідентичності Authenticode. Ці трансформації спрямовані на статичні ознаки контейнера та ознаки, які використовує машинне навчання; вони не прибирають поведінку runtime, яку розкривають host-shims.<sup>[[4]](#references)</sup>

## Модель виконання

Компактний віртуалізований loader може розділити виконання на такі рівні.<sup>[[3]](#references)</sup>

1. Скомпілювати freestanding C, BOF source або runtime-бібліотеки через LLVM у кастомну bytecode ISA.
2. Запустити невеликий native-інтерпретатор та ініціалізувати відображення opcode для конкретної збірки.
3. Виконати сам PE linker-loader як bytecode: розібрати заголовки, відобразити секції, застосувати relocations, розв’язати imports і заповнити IAT.
4. Залишити виклики guest-to-guest усередині інтерпретатора. Цілі поза регіоном bytecode, наприклад функції імпортованих DLL, спрямовувати через native host-call thunk.
5. Перемістити допоміжні засоби, як-от HTTP framing, TLS і частини C runtime, за ту саму межу інтерпретації.

Ця модель уникає виділення окремого native-регіону коду для кожного plugin і не дає оригінальному payload з’явитися як впізнаваному потоку x86-64-інструкцій. Це все ще межа ухилення/обфускації, а не межа безпеки: native-інтерпретатор і кожен зовнішній ефект залишаються спостережуваними.<sup>[[2]](#references)[[3]](#references)</sup>

## Спільна пам’ять host bridge

Ізольована VM представляє покажчики як зміщення в буфері guest, тому кожен перетин до host API вимагає перетворення покажчиків і спеціальної обробки вихідних параметрів. Натомість VM зі спільною пам’яттю використовує адреси guest, дійсні в процесі host. Тому читання й запис можна виконувати операціями на кшталт `memcpy`, а покажчик, повернений native allocation ECALL, можна безпосередньо розіменувати в bytecode. RISC-Y Business продемонструвала, що ця конструкція дає змогу звести bridge до отримання PEB і виконання довільних host-викликів.<sup>[[1]](#references)</sup>

Для Windows x64 віртуальний набір регістрів може відповідати ABI: розміщувати перші чотири цілочисельні аргументи або аргументи-покажчики в `RCX`, `RDX`, `R8` і `R9`, а наступні аргументи й shadow space — у стеку. Коли віртуальний `CALL` розв’язується за межами діапазону bytecode, універсальний thunk маршалить цей стан у native-виклик і копіює повернене значення назад у VM. Це дає змогу викликати IAT, виділяти пам’ять у heap і виконувати socket-операції без виправлення покажчиків.<sup>[[2]](#references)[[3]](#references)</sup>

Компроміс — повна втрата ізоляції. Пошкодження пам’яті guest може безпосередньо вплинути на host, native-callee можуть зберігати або змінювати покажчики guest, а інтерпретатор має вважати bytecode цілком довіреним. Для callback-викликів native-to-VM також потрібен зворотний bridge; VM, що підтримує лише вихідні виклики, не може безпосередньо обслуговувати API, які використовують callbacks, як-от `EnumWindows`.<sup>[[1]](#references)[[3]](#references)</sup>

## Поліморфізм ISA для кожної збірки

Кастомна ISA фіксованої ширини спрощує декодування, dispatch, relocation і відображення віртуальних регістрів. Centurion використовує формат інструкцій завдовжки 18 байтів, натхненний x86-64. Він поступається щільністю коду заради передбачуваного розбору й водночас залишає можливість транслювати наявні артефакти x86-64 у bytecode.<sup>[[3]](#references)</sup>

Рандомізація відображення opcode на handler для кожної збірки призводить до того, що однакова логіка guest породжує різні послідовності байтів. Шифрування таблиці відображення з відновленням лише під час виконання додатково усуває стабільний словник opcode на диску. Це ускладнює застосування фіксованих сигнатур і повторно використовуваних правил дизасемблювання, але автоматично не поліморфізує native-dispatcher, процедуру розшифрування таблиці або межу host-викликів.<sup>[[3]](#references)</sup>

## Перенесення середовища виконання у VM

Host-процес можна звести до примітивів пам’яті, syscall і socket, тоді як freestanding-бібліотеки надаватимуть високорівневі можливості всередині VM. Наприклад, FreeRTOS coreHTTP може реалізувати HTTP framing, а mbedTLS — TLS, не викликаючи WinHTTP або TLS API операційної системи. Raw sockets через `afd.sys` або подібний інтерфейс тоді стають вузькою native-межею для мережевих операцій.<sup>[[3]](#references)</sup>

Ця конструкція **Bring Your Own Execution Environment (BYOEE)** також може розмістити PE loading, runtime-підтримку й файлову систему в пам’яті за інтерпретатором. Вона зменшує кількість упізнаваних native-реалізацій, але не усуває телеметрію: raw socket-операції залишаються видимими, а в середовищах, де потрібні явні proxy або TLS interception, мережева схема може не працювати.<sup>[[3]](#references)</sup>

## Вибіркове native-прискорення

Інтерпретація кожної інструкції особливо затратна для криптографії з відкритим ключем. Практичний поділ використовує хуки `MBEDTLS_ALT` бібліотеки mbedTLS як інтерфейс програмного співпроцесора: залишає стан TLS, розбір сертифікатів, узгодження, виділення пам’яті й високорівневий bignum-код у bytecode, але передає гарячі арифметичні ядра з `bignum_core.c` через native ECALL. У прототипі Centurion `bignum.c`, `bignum_mod.c` і `bignum_mod_raw.c` залишалися віртуалізованими, тоді як внутрішні цикли виконувалися native-кодом. Це скоротило ECDHE handshake з хвилин до секунд.<sup>[[3]](#references)</sup>

Зробіть прискорювачі необов’язковими, щоб payload, яким не потрібен TLS, не містив додаткових native entry point. Цей шаблон узагальнюється на будь-яке навантаження інтерпретатора: спочатку профілюйте, а потім відкривайте якомога менший native-примітив замість перенесення всієї підсистеми за межі VM.<sup>[[3]](#references)</sup>

Centurion перевірила весь ланцюжок за допомогою bind shell із TLS 1.2: bytecode-loader відобразив PE, socket-виклики пройшли через універсальний thunk, mbedTLS обробила протокол усередині VM, а native ECALL прискорили арифметику ECDHE. Отже, native-інтерпретатор розміром приблизно 18 KB підтримував зашифрований канал команд без матеріалізації payload як native-коду x86-64.<sup>[[3]](#references)</sup>

## Орієнтири для реверс-інжинірингу й виявлення

Нижче наведено практичні орієнтири для аналізу, виведені з архітектури: віртуалізація змінює місце, де аналітики спостерігають поведінку, але не усуває саму поведінку.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>

- Знайдіть цикл fetch/decode/dispatch, віртуальний програмний лічильник, файл регістрів і повторюваний крок інструкцій фіксованої ширини.
- Зніміть таблицю opcode після її розшифрування під час виконання та зіставте адреси handler із семантичними операціями, а не шукайте зашифрований bytecode на диску.
- Встановіть breakpoint на універсальному thunk або ECALL dispatcher, щоб записати native-ціль, віртуальні регістри аргументів, аргументи в стеку й повернене значення.
- Відстежуйте доступ до PEB, розв’язання export, розбір PE-заголовків, записи relocation і заповнення IAT, навіть якщо реалізація loader — це bytecode.
- Співвіднесіть створення socket і трафік `afd.sys` з відсутністю очікуваних викликів WinHTTP або native TLS; відсутність високорівневих імпортів — це підказка, а не доказ нешкідливої поведінки.
- Розглядайте native-прискорювачі арифметики як важливі семантичні точки спостереження: їхні виклики можуть виявити обмін ключами й перевірку сертифікатів, тоді як навколишній автомат станів TLS залишається віртуалізованим.

Процеси аналізу, що починаються з dispatcher, а не з початкового графа потоку керування, описані в [інструкціях з аналізу malware для віртуалізації packer](../generic-methodologies-and-resources/basic-forensic-methodology/malware-analysis.md#virtualizing-packers-and-no-labels-obfuscation).

## Експлуатаційні обмеження

Віртуалізація створює накладні витрати на інтерпретацію, ускладнює toolchain та ABI і не вирішує проблему виявлення за поведінкою. Спільна пам’ять небезпечна за своєю суттю, робота з мережею через raw sockets може не спрацювати за обов’язкової вимоги використовувати proxy, а API Win32 із численними callbacks потребують native-to-VM trampolines. Інтерпретатор, syscall bridge і будь-які native-прискорювачі також залишають звичайний native-слід, який захисники можуть сигнатурно виявляти або інструментувати.<sup>[[2]](#references)[[3]](#references)</sup>
