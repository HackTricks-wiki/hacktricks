## Що таке Mythic?

Mythic — це модульний open-source фреймворк для command and control (C2), призначений для red teaming і підтримки спільної роботи. Він дає змогу операторам керувати агентами (payloads) і розгортати їх у різних операційних системах, зокрема Windows, Linux і macOS. Mythic надає браузерний UI для постановки завдань кількома операторами, роботи з файлами, керування SOCKS/rpfwd і генерації payloads.

На відміну від монолітних фреймворків, сам репозиторій Mythic **не містить** типів payloads чи C2-профілів. Агенти, wrappers і C2-профілі зазвичай встановлюються як зовнішні компоненти й оновлюються незалежно від ядра Mythic.

### Встановлення

Щоб встановити Mythic, дотримуйтеся інструкцій в офіційному **[репозиторії Mythic](https://github.com/its-a-feature/Mythic)**. Типовий початковий запуск із каталогу Mythic:

```bash
sudo make
sudo ./mythic-cli start
```

Якщо Mythic уже запущено, зазвичай можна додати нового агента або профіль за допомогою `./mythic-cli install github ...`, а потім перезапустити Mythic або просто запустити новий компонент безпосередньо.

### Агенти

Mythic підтримує кілька агентів — це **payloads, які виконують завдання на скомпрометованих системах**. Кожного агента можна налаштувати для конкретних потреб і запускати на різних операційних системах.

За замовчуванням Mythic не має встановлених агентів. Агенти спільноти з відкритим вихідним кодом розміщені в [**https://github.com/MythicAgents**](https://github.com/MythicAgents), а [**матриця можливостей спільноти**](https://mythicmeta.github.io/overview/agent_matrix.html) допоможе швидко перевірити підтримувані операційні системи, формати payload, обгортки та профілі C2.<sup>[[1]](#references)</sup>

Щоб встановити агента з цієї організації, виконайте:

```bash
sudo ./mythic-cli install github https://github.com/MythicAgents/<agent-name>
sudo ./mythic-cli install github https://github.com/MythicAgents/Apollo.git
sudo -E ./mythic-cli install github https://github.com/MythicAgents/Apollo.git
```

Форма `sudo -E` корисна, коли ви встановлюєте Mythic не з root-середовища. Попередньою командою можна додавати нових агентів, навіть якщо Mythic уже запущено.

### Профілі C2

Профілі C2 у Mythic визначають **як агенти взаємодіють із сервером Mythic**. У них вказуються протокол зв’язку, методи шифрування та інші параметри. Створювати профілі C2 та керувати ними можна через вебінтерфейс Mythic.

За замовчуванням Mythic встановлюється без профілів, але деякі профілі можна завантажити з репозиторію [**https://github.com/MythicC2Profiles**](https://github.com/MythicC2Profiles), виконавши:

```bash
sudo ./mythic-cli install github https://github.com/MythicC2Profiles/<c2-profile>
sudo ./mythic-cli install github https://github.com/MythicC2Profiles/http
```

Актуальні профілі, важливі для операторів:

- [`http`](https://github.com/MythicC2Profiles/http): базовий асинхронний трафік GET/POST.
- [`httpx`](https://github.com/MythicC2Profiles/httpx): гнучкіший HTTP-трафік із кількома доменами callback, перемиканням у разі збою/ротацією round-robin, власними заголовками/параметрами запиту та перетвореннями повідомлень (`base64`, `base64url`, `xor`, `netbios`, `prepend`, `append`), які додаються до cookies, заголовків, параметрів запиту або тіла.
- [`dynamichttp`](https://github.com/MythicC2Profiles/dynamichttp): налаштування формату HTTP-повідомлень на основі JSON/TOML, коли статичний профіль `http` надто легко розпізнати.

### Поточні примітки щодо платформи

- Багато публічних агентів і профілів тепер встановлюються з попередньо зібраних віддалених образів контейнерів.
  Якщо ви створили fork компонента або внесли до нього локальні зміни, але Mythic і далі використовує стару поведінку, перевірте згенеровані записи `.env` для `*_REMOTE_IMAGE`,
  `*_USE_BUILD_CONTEXT` і `*_USE_VOLUME`; зазвичай саме ввімкнення
  `*_USE_BUILD_CONTEXT="true"` змушує Mythic виконувати повторну збірку з вашого локального Docker-контексту, а не непомітно використовувати віддалений образ.
- Скрипти браузера — одна з найкорисніших для операторів функцій Mythic: вони можуть перетворювати необроблений вивід команд на таблиці, засоби перегляду знімків екрана, посилання для завантаження, посилання для пошуку та кнопки, які безпосередньо з інтерфейсу створюють подальші завдання. Поточні збірки Mythic дають кожному оператору змогу зберігати власні скрипти, вмикати чи вимикати їх глобально або для окремих завдань; найкращі результати отримують, коли агенти повертають структурований JSON, а не звичайний текст. Це особливо корисно для типових робочих процесів `ls`, `ps`, тріажу та перегляду файлів.<sup>[[4]](#references)[[6]](#references)</sup>
- Новіші збірки Mythic також підтримують інтерактивне керування завданнями та шаблони Push C2, які зменшують потребу в опитуванні з `sleep 0` під час операцій із активним використанням PTY/SOCKS/rpfwd. Якщо агент/профіль це підтримує, такий підхід зазвичай створює менше навантаження, ніж постійне надсилання запитів до сервера лише для підтримання працездатності інтерактивного каналу.<sup>[[3]](#references)</sup>
- У збирачах Mythic покоління 3.4 контекст враховується краще, ніж випливає зі старіших матеріалів: параметри збірки тепер можна групувати або приховувати залежно від вибраної ОС чи інших параметрів збірки; типи payload можуть вказувати, чи підтримують вони кілька профілів C2 або кілька екземплярів одного й того самого C2 в одній збірці; а відхилення параметрів C2 дають змогу агенту приховувати поля, які він фактично не підтримує. Це важливо, коли ви перемикаєтеся між `http`, `httpx`, `smb`,
  `tcp` і `websocket`, адже набір безпечних/допустимих параметрів збірки більше не обмежений статичною формою.<sup>[[5]](#references)</sup>
- Якщо ви створюєте власну пару агент/профіль і не хочете використовувати формат повідомлень JSON Mythic або стандартне шифрування під час передавання, використовуйте
  `translation_container`: Mythic видаляє UUID, передає зашифрований блок даних і ключовий матеріал перекладачу через gRPC та очікує отримати натомість байти у форматі агента. Це зручний спосіб підтримати бінарні протоколи, власне кадрування або шифрування на боці агента без переписування всього сервера.
- Пам’ятайте, що пов’язані/P2P callback не лише передають завдання. Потік Mythic `get_tasking` також може передавати відповіді, а ще дані `delegates`,
  `socks`, `rpfwd` і `interactive`. На практиці один зовнішній callback може обслуговувати внутрішні callback і канали pivoting в одному циклі опитування; якщо дочірні агенти виконують власні періодичні check-in, `get_delegate_tasks=false` не дасть батьківському агенту випадково забрати завдання з черги внутрішнього callback.

### Wrapper payload

Wrapper payload дають змогу зберегти ту саму логіку агента, змінивши спосіб представлення даних на диску, які передаються або зберігаються.

- `service_wrapper`: перетворює інший payload на виконуваний файл служби Windows; це корисно, коли для шляху виконання потрібен коректний бінарний файл служби.
- `scarecrow_wrapper`: обгортає сумісний shellcode завантажувачем ScareCrow, створюючи вихідні файли на основі завантажувача, наприклад EXE/DLL/CPL.

## [Apollo Agent](https://github.com/MythicAgents/Apollo)

Apollo — це агент для Windows, написаний на C# із використанням .NET Framework 4.0 і призначений для навчальних програм SpecterOps.<sup>[[2]](#references)</sup>

Встановіть його за допомогою:

```bash
./mythic-cli install github https://github.com/MythicAgents/Apollo.git
```

### Поточні примітки щодо збірки/профілів

- Apollo наразі може створювати payloads типу `WinExe`, `Shellcode`, `Service` і `Source`.
- Найчастіше використовувані профілі Apollo: `http`, `httpx`, `smb`, `tcp` і `websocket`.
- `httpx` зазвичай є гнучкішим варіантом, якщо потрібні ротація доменів, підтримка проксі, користувацьке розміщення повідомлень і трансформації повідомлень, а не старіший статичний профіль `http`.
- Apollo — один із найфункціональніших community agents, який наразі надає інтеграції на боці Mythic, зокрема browser scripts, перегляди файлів/процесів, screenshots, keylogging, SOCKS, rpfwd, Push C2 і P2P routing.
- Apollo підтримує wrapper payloads, як-от `service_wrapper` і `scarecrow_wrapper`.
- Apollo підтримує динамічне завантаження команд, тож можна залишити початковий payload компактним і пізніше завантажувати додаткові команди або Forge modules, замість того щоб компілювати всі можливості post-ex у першу збірку.
- Під час створення shellcode-виводу поточний builder Apollo також надає варіанти формату Donut (`Binary`, `Base64`, `C`, `Ruby`, `Python`, `Powershell`, `C#`, `Hex`) і поведінки обходу Donut (`None`, `Abort on fail`, `Continue on fail`). Це корисно, якщо кінцева мета — повторно загорнути shellcode за допомогою `service_wrapper`, `scarecrow_wrapper` або користувацького loader.
- `register_file` і `register_assembly` — це примітиви staging для `execute_assembly`, `execute_pe`, `inline_assembly`, `execute_coff`, `powershell_import` і `powerpick`. У поточних збірках Apollo ці staged artifacts кешуються на боці клієнта як захищені DPAPI blobs AES256.
- Результати `ls` і `ps` особливо добре інтегруються з browser scripts і файловим/процесним browser у Mythic, що помітно пришвидшує triage операторів у спільних операціях.
- Завдання Apollo у режимі fork-and-run успадковують налаштування sacrificial process із
  `spawnto_x86` / `spawnto_x64`, успадковують вибір батьківського процесу з `ppid` і
  потім використовують поточний вибраний primitive ін’єкції. На практиці це означає, що
  налаштування OPSEC для однієї команди часто одночасно впливають на `execute_assembly`,
  `powerpick`, `mimikatz`, `pth`, `dcsync`, `execute_pe` і `spawn`.
- Поточна документація Apollo вказує такі backend-и ін’єкції: `CreateRemoteThread`,
  `QueueUserAPC` (у стилі early-bird) і `NtCreateThreadEx` через syscalls. Використовуйте
  `get_injection_techniques` перед гучними діями post-exploitation і
  `set_injection_technique`, якщо потрібно перейти від primitive, що
  конфліктує з ціллю або потрібною командою.
- `blockdlls` впливає лише на sacrificial processes, створені для завдань post-exploitation.
  У поєднанні з менш підозрілою ціллю `spawnto_x64`, ніж стандартний
  `rundll32.exe` без аргументів, це одна з найпростіших змін на боці Apollo, які можна внести
  перед запуском завдань із великою кількістю assembly/PowerShell.

### Конвеєр збірки .NET-агента з урахуванням виявлення

До форка Apollo з урахуванням виявлення слід підходити як до **проблеми всієї системи збірки**, а не як до завершального кроку `obfuscate.exe`. Цей приклад доповнює загальну [методологію обходу AV](av-bypass.md) і [інструменти перевірки .NET](../reversing/reversing-tools-basic-methods/README.md): зміни wire identifiers, метаданих IL, пакування залежностей, reflection і динамічно скомпільованих завдань утворюють єдину межу сумісності.<sup>[[8]](#references)</sup>

#### Мутація протоколу з урахуванням YARA

Перед зміною коду перевірте публічні правила для файлів/пам’яті. Наприклад, правило Elastic `Multi_Trojan_Mythic_4beb7e17` спрацьовує, якщо присутні будь-які **7 із 11** рядків Mythic JSON/action, зокрема `task_id`, `post_response`, `c2_profile`, `get_tasking` і `get_delegate_tasks`. Перейменування достатньої кількості полів може обійти цей поріг, але це значення протоколу, а не косметичні символи: агент і відповідну реалізацію server/profile потрібно змінювати разом.<sup>[[7]](#references)[[8]](#references)</sup>

Це лише прибирає один набір статичних ознак. Періодичність check-in, форма повідомлень, потік завдань/відповідей і відновлення рядків під час виконання можуть залишатися поведінковими або memory-ознаками; тому перевіряйте і зібраний артефакт, і callback після його запуску, а не вважайте чисте сканування рядків успішним результатом.<sup>[[8]](#references)</sup>

#### Спочатку об’єднайте, потім застосовуйте глобальні трансформації

Вбудовування ресурсів за допомогою таких інструментів, як Costura, залишає супутні assemblies у вигляді стиснених ресурсів. Обфускатор, який обробляє лише зовнішній модуль, пропускає їхні назви типів і метадані; окрема обфускація кожної DLL натомість може призвести до несумісних назв у контрактах між assemblies. Спочатку об’єднайте результати збірки на рівні IL (наприклад, за допомогою [ILRepack](https://github.com/gluck/il-repack)), а потім застосуйте одну карту перейменувань до отриманого модуля.<sup>[[8]](#references)</sup>

```text
agent.exe + dependency DLLs
          -> ILRepack -> merged.exe
          -> dnlib IL/metadata transforms
          -> AsmResolver PE/resource patching
          -> final payload
```

Custom pass може використовувати [dnlib](https://github.com/0xd4d/dnlib) для перетворень керованого IL/метаданих і [AsmResolver](https://github.com/Washi1337/AsmResolver) для патчінгу PE/ресурсів після запису. У прикладі інструкції `ldstr`, що відповідали умовам, перетворювалися на виклики дешифратора з цілочисельним токеном, що використовували новий 16-байтовий ключ rolling-XOR, а символи й простори імен отримували правдоподібні назви в корпоративному стилі замість коротких послідовних ідентифікаторів. Інші pass-и видаляли вибрані атрибути компілятора/відладчика, очищали посилання на merger/embedding, перейменовували ресурси й патчили інформацію про версію. Для кожної окремої збірки генеруйте нові імена, dead code та матеріал шифрування: зміна ciphertext прибирає стабільні байти, але стабільний дешифратор або впізнаваний шаблон перетворення самі по собі є сигнатурою.<sup>[[8]](#references)</sup>

#### Синхронізуйте динамічні завдання з payload

Apollo може компілювати вихідний код завдання на сервері, надсилати байти DLL і завантажувати її за допомогою `Assembly.Load()`. Після перейменування публічних типів базового агента подальші завдання, скомпільовані з оригінальним API, більше не розв’язуються. Ставтеся до експортованої мапи перейменувань як до ABI-артефакту, специфічного для payload:<sup>[[8]](#references)</sup>

1. Прив’язуйте мапу й контекст типів до точного ідентифікатора payload/збірки.
2. Для кожної збірки завдання отримуйте цю мапу й переписуйте тимчасове дерево вихідного коду.
3. Переписуйте лише розв’язані посилання на простори імен, типи, вкладені/узагальнені типи, поля та властивості, а потім компілюйте з обфускованою об’єднаною збіркою.
4. Відхиляйте відсутні або невідповідні мапи до надсилання завдання та після компіляції виконуйте тест ініціалізації.

Сліпа глобальна заміна небезпечна, оскільки ідентифікатор також може траплятися в рядку, локальному оголошенні, зверненні до члена, типі фреймворку або не пов’язаному просторі імен. Якщо залишаєте переписувач на основі тексту/regex, явно захищайте ці контексти й проводьте регресійне тестування щоразу, коли змінюється схема мапи або pass перейменування.<sup>[[8]](#references)</sup>

#### Зробіть контракти reflection незалежними від простору імен

Код виявлення, що перевіряє `t.FullName.StartsWith("Tasks.")`, робить простір імен критично важливим і не працює після його перемапування. Виконуйте виявлення за стабільним зв’язком між типами, зберігаючи назви класів команд, якщо диспетчеризація досі використовує `t.Name`:<sup>[[8]](#references)</sup>

```csharp
foreach (Type t in _tasksAsm.GetExportedTypes())
{
    if (t.IsSubclassOf(typeof(Tasking)) && !t.IsAbstract)
        _loadedTaskTypes[t.Name] = t;
}
```

Підтримуйте явний allowlist імен, доступних через reflection, полів серіалізатора, entry point-ів і API для взаємодії між збірками, які не можна перейменовувати. Насамкінець декомпілюйте результат за допомогою ILSpy/dnSpy, перевірте файлове та memory-представлення й протестуйте всі шляхи команд і loader-ів у лабораторії EDR; успішний запуск збірки ще не означає, що всі задачі працюватимуть після перейменування або що під час виконання не буде виявлено підозрілу поведінку.<sup>[[8]](#references)</sup>

Цей agent має багато команд, завдяки чому він дуже схожий на Beacon від Cobalt Strike, але має й додаткові можливості. Серед іншого, він підтримує:

### Типові дії

- `cat`: Вивести вміст файлу
- `cd`: Змінити поточну робочу директорію
- `cp`: Скопіювати файл з одного розташування в інше
- `ls`: Показати файли й директорії в поточному каталозі або за вказаним шляхом
- `ifconfig`: Отримати дані про мережеві адаптери та інтерфейси
- `netstat`: Отримати інформацію про TCP- і UDP-з’єднання
- `pwd`: Вивести шлях до поточної робочої директорії
- `ps`: Показати запущені процеси в цільовій системі (з додатковою інформацією)
- `jobs`: Показати всі запущені job-и, пов’язані з тривалими завданнями
- `download`: Завантажити файл із цільової системи на локальну машину
- `upload`: Завантажити файл із локальної машини в цільову систему
- `reg_query`: Запитати ключі та значення реєстру в цільовій системі
- `reg_write_value`: Записати нове значення у вказаний ключ реєстру
- `sleep`: Змінити інтервал сну agent-а, який визначає, як часто він зв’язується із сервером Mythic
- Та багато інших — скористайтеся `help`, щоб переглянути повний список доступних команд.

### Підвищення привілеїв

- `getprivs`: Увімкнути якомога більше привілеїв для токена поточного потоку
- `getsystem`: Відкрити handle до winlogon і скопіювати токен, фактично підвищивши привілеї до рівня SYSTEM
- `make_token`: Створити нову logon-сесію та застосувати її до agent-а, щоб видати себе за іншого користувача
- `steal_token`: Викрасти primary token з іншого процесу, щоб agent міг видати себе за користувача цього процесу
- `pth`: Pass-the-Hash-атака, що дає змогу автентифікуватися як користувач за допомогою його NTLM hash без знання пароля у відкритому вигляді
- `mimikatz`: Виконати команди Mimikatz для вилучення облікових даних, hash-ів та іншої конфіденційної інформації з пам’яті або бази даних SAM
- `rev2self`: Повернути agent-у його primary token, фактично знизивши привілеї до початкового рівня
- `ppid`: Змінити батьківський процес для post-exploitation job-ів, указавши новий ідентифікатор процесу, щоб краще контролювати контекст виконання job-ів
- `printspoofer`: Виконати команди PrintSpoofer для обходу засобів захисту диспетчера черги друку, що дає змогу підвищити привілеї або виконати код
- `dcsync`: Синхронізувати Kerberos-ключі користувача з локальною машиною, щоб зламувати паролі офлайн або проводити подальші атаки
- `ticket_cache_add`: Додати Kerberos ticket до поточної або вказаної logon-сесії, щоб повторно використати ticket або видати себе за іншого користувача

### Виконання процесів

- `assembly_inject`: Дає змогу інжектити loader .NET-збірки у віддалений процес
- `blockdlls`: Блокувати завантаження DLL, не підписаних Microsoft, у post-exploitation job-и
- `execute_assembly`: Виконати .NET-збірку в контексті agent-а
- `execute_coff`: Виконати файл COFF у пам’яті, що дає змогу виконувати скомпільований код у пам’яті
- `execute_pe`: Виконати unmanaged executable (PE)
- `keylog_inject`: Інжектити keylogger в інший процес і передавати натискання клавіш у вікно keylog у Mythic
- `screenshot` / `screenshot_inject`: Зробити знімок поточного робочого столу безпосередньо або
  шляхом інжекту збірки для створення знімка екрана в цільовий процес/сесію
- `get_injection_techniques`: Показати доступні техніки інжекту й поточну вибрану техніку
- `inline_assembly`: Виконати .NET-збірку в одноразовому AppDomain, щоб тимчасово виконати код, не впливаючи на основний процес agent-а
- `register_assembly`: Зареєструвати .NET-збірку для подальшого виконання
- `register_file`: Зареєструвати файл у кеші agent-а для подальших завдань `execute_*` або PowerShell
- `run`: Виконати бінарний файл у цільовій системі, використовуючи системний PATH для пошуку executable
- `set_injection_technique`: Змінити primitive інжекту, який використовують post-exploitation job-и
- `shinject`: Інжектити shellcode у віддалений процес, щоб виконувати довільний код у пам’яті
- `inject`: Інжектити shellcode agent-а у віддалений процес, щоб виконувати код agent-а в пам’яті
- `spawn`: Запустити нову сесію agent-а у вказаному executable, щоб виконати shellcode в новому процесі
- `spawnto_x64` і `spawnto_x86`: Змінити бінарний файл за замовчуванням для post-exploitation job-ів на вказаний шлях замість використання `rundll32.exe` без параметрів, що створює багато шуму.

### Mythic Forge

Це дає змогу **завантажувати** файли COFF/BOF з Mythic Forge — репозиторію попередньо скомпільованих payload-ів та інструментів, які можна виконувати в цільовій системі. Завдяки всім доступним для завантаження командам можна буде виконувати типові дії безпосередньо в процесі поточного agent-а як BOF (зазвичай із кращим OPSEC, ніж під час запуску окремого процесу).

Почніть із їх встановлення:

```bash
./mythic-cli install github https://github.com/MythicAgents/forge.git
```

Потім використайте `forge_collections`, щоб показати модулі COFF/BOF з Mythic Forge і вибрати та завантажити їх у пам’ять агента для виконання. За замовчуванням в Apollo додано такі 2 колекції:

- `forge_collections {"collectionName":"SharpCollection"}`
- `forge_collections {"collectionName":"SliverArmory"}`

Після завантаження модуля він з’явиться у списку як інша команда, наприклад `forge_bof_sa-whoami` або `forge_bof_sa-netuser`.

Для BOF пам’ятайте, що Forge **не** передає Apollo один суцільний рядок аргументів.
Він зіставляє параметри BOF із форматом типізованого масиву Mythic, а потім
передає їх у потік `execute_coff` Apollo. Якщо завантажений через Forge BOF працює
неочікувано, перевірте очікувані типи аргументів BOF і точку входу, а не лише
введений командний рядок. Також майте на увазі, що новіший завантажувач BOF в Apollo змінив
обробку аргументів порівняно зі значно старішими збірками епохи 2.3.1, тому застарілі BOF або
старі колекції можуть не працювати лише через зміну очікувань щодо маршалінгу.

### Виконання PowerShell і скриптів

- `powershell_import`: Імпортує новий скрипт PowerShell (.ps1) у кеш агента для подальшого виконання
- `powershell`: Виконує команду PowerShell у контексті агента, даючи змогу використовувати розширені можливості скриптів і автоматизації
- `powerpick`: Впроваджує збірку-завантажувач PowerShell у процес-приманку та виконує команду PowerShell (без журналювання powershell).
- `psinject`: Виконує PowerShell у вказаному процесі, даючи змогу цілеспрямовано запускати скрипти в контексті іншого процесу
- `shell`: Виконує команду оболонки в контексті агента, подібно до запуску команди в cmd.exe

### Переміщення мережею

- `jump_psexec`: Використовує техніку PsExec для переміщення мережею на новий хост: спочатку копіює виконуваний файл агента Apollo (apollo.exe), а потім запускає його.
- `jump_wmi`: Використовує техніку WMI для переміщення мережею на новий хост: спочатку копіює виконуваний файл агента Apollo (apollo.exe), а потім запускає його.
- `link` і `unlink`: Створюють і розривають P2P-з’єднання (наприклад, через SMB/TCP) між callback-з’єднаннями.
- `wmiexecute`: Виконує команду на локальній або вказаній віддаленій системі за допомогою WMI, за потреби використовуючи облікові дані для імперсонації.
- `net_dclist`: Отримує список контролерів домену для вказаного домену; це корисно для визначення потенційних цілей переміщення мережею.
- `net_localgroup`: Виводить список локальних груп на вказаному комп’ютері. Якщо комп’ютер не вказано, використовується localhost.
- `net_localgroup_member`: Отримує список учасників локальної групи для вказаної групи на локальному або віддаленому комп’ютері, що дає змогу перелічити користувачів у певних групах.
- `net_shares`: Виводить список віддалених спільних ресурсів і відомості про доступ до них на вказаному комп’ютері; це корисно для визначення потенційних цілей переміщення мережею.
- `socks`: Вмикає на цільовій мережі проксі-сервер, сумісний із SOCKS 5, що дає змогу тунелювати трафік через скомпрометований хост. Сумісний із такими інструментами, як proxychains.
- `rpfwd`: Починає прослуховування вказаного порту на цільовому хості та пересилає трафік через Mythic на віддалену IP-адресу й порт, забезпечуючи віддалений доступ до служб у цільовій мережі.
- `listpipes`: Виводить список усіх іменованих каналів у локальній системі; це може бути корисним для переміщення мережею або підвищення привілеїв через взаємодію з механізмами IPC.

Інформацію про низькорівневі примітиви виконання WMI, які використовуються під капотом `jump_wmi` або `wmiexecute`, див. у [WmiExec](lateral-movement/wmiexec.md). Ширший огляд схем pivoting наведено в розділі [Тунелювання та перенаправлення портів](../generic-hacking/tunneling-and-port-forwarding.md).

### Різні команди
- `help`: Виводить детальну інформацію про певні команди або загальну інформацію про всі доступні команди агента.
- `clear`: Позначає завдання як «очищені», щоб агенти не могли їх отримати. Щоб очистити всі завдання, можна вказати `all`, а щоб очистити певне завдання — `task Num`.  


## [Агент Poseidon](https://github.com/MythicAgents/poseidon)

Poseidon — це агент на Golang, який компілюється у виконувані файли для **Linux і macOS**.

```bash
./mythic-cli install github https://github.com/MythicAgents/poseidon.git
```

### Примітки щодо поточних збірок/профілів

- Поточні збірки Poseidon призначені для Linux і macOS на `x86_64` та `arm64`.
- Підтримувані формати виводу включають нативні виконувані файли та вивід у стилі shared library, як-от `dylib` і `so`.
- Poseidon підтримує `http`, `websocket`, `tcp` і `dynamichttp`, а поточні збирачі надають налаштування кількох каналів egress, як-от `egress_order` і порогові значення failover.
- Поточні метадані можливостей Poseidon також містять browser scripts, інтеграцію файлового та процесного браузера, інтерактивне керування завданнями, keylogging, знімки екрана, Push C2, SOCKS, rpfwd і P2P, тож його можна використовувати як повноцінний pivot-вузол Linux/macOS, а не лише як просту віддалену оболонку.
- Параметри збірки, як-от `proxy_bypass` і `garble`, варто перевірити, якщо потрібна краща поведінка в мережі або додаткова обфускація Go-бінарного файла.
- `pty` — одна з найкорисніших нових команд для Linux/macOS: вона відкриває інтерактивний PTY і може надати порт на боці Mythic для повноціннішої взаємодії з терміналом без застарілого обхідного рішення `sleep 0` + SOCKS.
- Поточна документація Poseidon особливо цікава для tradecraft, орієнтованого на macOS: `jxa` виконує JavaScript for Automation у пам’яті, `screencapture` захоплює робочий стіл користувача, який увійшов у систему, `clipboard_monitor` передає зміни pasteboard, `execute_library` завантажує локальну dylib і викликає її функцію, а `libinject` змушує віддалений процес завантажити dylib із диска.
- Для довготривалих завдань пам’ятайте, що Poseidon виконує post-exploitation завдання в goroutines/threads, які є кооперативними, а не такими, що їх можна примусово завершити. У документації також прямо зазначено, що вбудованої обфускації агента наразі немає, тож tradecraft на рівні збірки/профілю має більше значення, ніж для комерційних імплантів із потужною обфускацією.

Щоб дізнатися про tradecraft для macOS у межах операцій на базі Mythic, зловживання JAMF або ідеї MDM-as-C2, дивіться [macOS Red Teaming](../macos-hardening/macos-red-teaming/README.md).

Під час використання в Linux або macOS доступні такі цікаві команди:

### Типові дії

- `cat`: Вивести вміст файла
- `cd`: Змінити поточний робочий каталог
- `chmod`: Змінити дозволи файла
- `config`: Переглянути поточну конфігурацію та інформацію про хост
- `cp`: Скопіювати файл з одного місця в інше
- `curl`: Виконати один вебзапит із необов’язковими заголовками та методом
- `upload`: Завантажити файл на цільову систему
- `download`: Завантажити файл із цільової системи на локальну машину
- Та багато іншого

### Пошук конфіденційної інформації

- `triagedirectory`: Знайти цікаві файли в каталозі на хості, наприклад конфіденційні файли або облікові дані.
- `getenv`: Отримати всі поточні змінні середовища.

### Специфічний для macOS tradecraft

- `jxa`: Виконати JavaScript for Automation у пам’яті через `OSAScript`; корисно для нативного post-exploitation у macOS без створення окремих файлів скриптів.
- `clipboard_monitor`: Перевіряти pasteboard і повідомляти про зміни до Mythic; корисно для сценаріїв викрадення облікових даних/токенів, пов’язаних із копіюванням і вставленням.
- `screencapture`: Захопити робочий стіл користувача в macOS.
- `execute_library`: Завантажити dylib із диска та викликати певну експортовану функцію.
- `libinject`: Ін’єктувати shellcode-заглушку, яка змушує інший процес macOS завантажити dylib із диска.
- `persist_launchd`: Створити механізм persistence LaunchAgent / LaunchDaemon безпосередньо з агента.

### Переміщення мережею

- `ssh`: Підключитися до хоста через SSH із визначеними обліковими даними та відкрити PTY, не запускаючи ssh.
- `sshauth`: Підключитися через SSH до вказаних хостів із визначеними обліковими даними. Також цю команду можна використовувати для виконання певної команди на віддалених хостах через SSH або для копіювання файлів за допомогою SCP.
- `link_tcp`: Встановити TCP-з’єднання з іншим агентом для прямого зв’язку між агентами.
- `link_webshell`: Встановити з’єднання з агентом через P2P-профіль webshell для віддаленого доступу до вебінтерфейсу агента.
- `rpfwd`: Запустити або зупинити Reverse Port Forward для віддаленого доступу до сервісів у цільовій мережі.
- `socks`: Запустити або зупинити проксі SOCKS5 у цільовій мережі для тунелювання трафіку через скомпрометований хост. Сумісний із такими інструментами, як proxychains.
- `portscan`: Сканувати хости на наявність відкритих портів, щоб виявити потенційні цілі для переміщення мережею або подальших атак.

### Виконання процесів

- `shell`: Виконати одну команду оболонки через /bin/sh для безпосереднього запуску команд у цільовій системі.
- `run`: Запустити команду з диска з аргументами для виконання бінарних файлів або скриптів у цільовій системі.
- `pty`: Відкрити інтерактивний PTY для безпосередньої взаємодії з оболонкою в цільовій системі.
