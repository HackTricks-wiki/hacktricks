## Ядро XNU

**Основа macOS — XNU**, що розшифровується як "X is Not Unix". Це ядро складається переважно з **мікроядра Mach** (про нього йтиметься далі) **та** елементів Berkeley Software Distribution (**BSD**). XNU також надає платформу для **драйверів ядра через систему I/O Kit**. Ядро XNU є частиною open source-проєкту Darwin, а це означає, що **його вихідний код доступний усім**.

З погляду дослідника безпеки або Unix-розробника, **macOS** може здаватися досить **подібною** до системи **FreeBSD** з елегантним GUI та великою кількістю власних застосунків. Більшість застосунків, розроблених для BSD, компілюються та працюють у macOS без змін, оскільки всі знайомі Unix-користувачам інструменти командного рядка присутні в macOS. Однак через те, що ядро XNU містить Mach, між традиційною Unix-подібною системою та macOS існують суттєві відмінності, які можуть спричиняти потенційні проблеми або надавати унікальні переваги.

Open source-версія XNU: [https://opensource.apple.com/source/xnu/](https://opensource.apple.com/source/xnu/)

### Mach

Mach — це **мікроядро**, розроблене як **сумісне з UNIX**. Одним із його ключових принципів проєктування було **мінімізувати** обсяг **коду**, що виконується в **просторі ядра**, і натомість дозволити багатьом типовим функціям ядра, таким як файлова система, мережа та I/O, **виконуватися як завдання на рівні користувача**.

У XNU Mach **відповідає за багато критичних низькорівневих операцій**, які зазвичай виконує ядро, зокрема за планування процесора, багатозадачність і керування віртуальною пам’яттю.

### BSD

**Ядро** XNU також **містить** значний обсяг коду, похідного від проєкту **FreeBSD**. Цей код **виконується як частина ядра разом із Mach** в одному адресному просторі. Однак код FreeBSD у складі XNU може суттєво відрізнятися від оригінального коду FreeBSD, оскільки для забезпечення сумісності з Mach були потрібні зміни. FreeBSD забезпечує багато операцій ядра, зокрема:

- Керування процесами
- Обробка сигналів
- Базові механізми безпеки, зокрема керування користувачами та групами
- Інфраструктура системних викликів
- Стек TCP/IP і сокети
- Firewall і фільтрація пакетів

Розуміння взаємодії між BSD і Mach може бути складним через відмінності в їхніх концептуальних моделях. Наприклад, BSD використовує процеси як базову одиницю виконання, тоді як Mach працює на основі потоків. У XNU ця невідповідність усувається шляхом **зв’язування кожного процесу BSD із завданням Mach**, яке містить рівно один потік Mach. Коли використовується системний виклик BSD fork(), код BSD усередині ядра застосовує функції Mach для створення структури завдання та потоку.

Крім того, **Mach і BSD використовують різні моделі безпеки**: модель безпеки **Mach** ґрунтується на **правах на порти**, тоді як модель безпеки BSD працює на основі **власника процесу**. Відмінності між цими двома моделями іноді призводили до вразливостей локального підвищення привілеїв. Окрім типових системних викликів, існують також **пастки Mach, які дозволяють програмам у просторі користувача взаємодіяти з ядром**. Разом ці елементи формують багатогранну гібридну архітектуру ядра macOS.

### I/O Kit - драйвери

I/O Kit — це open source, об’єктно-орієнтований **фреймворк драйверів пристроїв** у ядрі XNU, який працює з **динамічно завантажуваними драйверами пристроїв**. Він дозволяє додавати модульний код до ядра на льоту та підтримує різноманітне обладнання.

### Копроцесори в архітектурі macOS

Платформи Apple використовують кілька копроцесорів, щоб перемістити чутливі до затримок завдання з основних ядер і ізолювати критично важливі для безпеки функції.

- **Secure Enclave Processor (SEP)**: Спеціалізоване ARM-ядро з власним мікроядром і ланцюжком безпечного завантаження, яке зазвичай працює на рівні **EL3/secure world**. Взаємодія відбувається через mailbox-драйвери в macOS на рівні EL1.
- Поверхня атаки: оновлення firmware SEP і user-space daemon-и (`seputil`, `securityd`), які проксують запити.
- Наслідки компрометації: витік довгострокових ключів, обхід біометричної автентифікації та злам захисту FileVault або Apple Pay.
- **System Management Controller (SMC)**: працює на пропрієтарному firmware мікроконтролера поза межами ARM exception levels. macOS (EL1) отримує до нього доступ через user clients I/O Kit.
- Поверхня атаки: повідомлення USB-C power delivery, інтерфейси керування вентиляторами та батареєю, а також шляхи оновлення firmware.
- Наслідки компрометації: перевизначення температурних обмежень, впровадження підроблених даних сенсорів, вимкнення живлення або встановлення постійних backdoor-ів у NVRAM.
- **T1/T2 Security Chips**: запускають bridgeOS (похідну від watchOS) переважно на рівнях EL1/EL3 на власних ARM-ядрах. macOS взаємодіє з ними через канали, подібні до PCIe/USB, якими керує IOKit.
- Поверхня атаки: шляхи DFU/відновлення, IPC endpoints, доступні через сервіси на кшталт `tccd`, і media pipelines, підключені до T2.
- Наслідки компрометації: вимкнення secure boot, розшифрування вмісту SSD, перехоплення керування камерою/мікрофоном або імітація HID-вводу для прихованої персистентності.
- **Display Coprocessor (DCP)**: виконує firmware на рівні EL1 в ізольованому адресному просторі, захищеному DART (IOMMU Apple).
- Поверхня атаки: інтерфейси `DCPAVService`, спільні descriptor buffers і аналіз образів firmware.
- Наслідки компрометації: впровадження довільних кадрів, перехоплення framebuffer-ів або виведення display pipeline з ладу для DoS.
- **Apple Neural Engine (ANE)**: виконує microcode у виділеному ML-кластері (без ARM EL levels). macOS планує роботу через `ANECompilerService` та IOKit.
- Поверхня атаки: скомпільовані model binaries (`.ane`), Core ML APIs, які передають custom kernels, і firmware loaders.
- Наслідки компрометації: модифікація або ексфільтрація ML-моделей, витік оброблених аудіо-/візуальних даних або саботаж inference на пристрої.
- **AGX GPU**: firmware виконується на спеціалізованих GPU-ядрах із scheduler-ом; EL0 надсилає Metal-команди, які перевіряє EL1.
- Поверхня атаки: Metal shader compiler, API спільного відображення buffer-ів і ioctl-інтерфейси `com.apple.AGXFirmware`.
- Наслідки компрометації: DMA-доступ до системної пам’яті, sandbox escape через GPU-драйвери або постійні firmware implants.
- **Apple Video Encoder (AVE)**: firmware виконується в Media Engine в sandbox, подібному до EL1. macOS взаємодіє через VideoToolbox і `AppleAVE2`.
- Поверхня атаки: codec bitstreams, parameter sets, буфери, надані користувачем, і firmware update blobs.
- Наслідки компрометації: витік нестиснених кадрів, обхід DRM або отримання виконання коду з доступом до DMA engines.
- **Image Signal Processor (ISP)**: запускає secure firmware у кластері Media Engine; camera drivers macOS працюють на рівні EL1.
- Поверхня атаки: Camera HALs, RAW frame descriptors, черги конфігурації ISP і оновлення firmware.
- Наслідки компрометації: приховане захоплення необробленого відео з камери, вимкнення індикаторів приватності або впровадження сфабрикованих зображень.
- **AMX Matrix cores**: працюють як блоки-копроцесори, доступні на рівнях EL0/EL1 через нові інструкції.
- Поверхня атаки: віртуалізація стану AMX ядром (`thread_set_state`, перемикання контексту) і генерація коду в user space.
- Наслідки компрометації: витік tile registers інших процесів, fingerprinting робочих навантажень або підвищення привілеїв через пошкодження пам’яті ядра.

Сучасна macOS розглядає ці копроцесори як довірені компоненти ланцюжка довіри. Firmware для SEP, SMC і T2 підписується Apple, а handshake-протоколи (часто реалізовані через mailbox або сімейства I/O Kit) містять challenge-response перевірки, тому лише автентифіковане firmware може обробляти запити.

## Розширення ядра macOS

macOS **дуже суворо обмежує завантаження Kernel Extensions** (.kext), оскільки код працюватиме з високими привілеями. Фактично за замовчуванням це практично неможливо (якщо не знайдено bypass).

### System Extensions macOS

Замість Kernel Extensions macOS створила System Extensions, які надають API на рівні користувача для взаємодії з ядром. Завдяки цьому розробники можуть уникати використання kernel extensions.

### Cryptexes і RSR (Rapid Security Response)

- **Cryptex** розшифровується як **CRYPTographically-sealed EXtension**. Це запечатаний disk image (контейнер), який Apple використовує для розміщення частин OS (frameworks, shared libraries, apps), що найімовірніше змінюватимуться між основними оновленнями OS.
- У macOS та iOS компоненти, розміщені всередині cryptexes, можна **виправляти або замінювати** через RSR без повторного запечатування всього системного тому.
- Cryptexes розташовані на томі **Preboot** поруч із boot firmware і під’єднуються до файлової системи OS під час виконання.
- Завантаження вмісту cryptex передбачає перевірку: система перевіряє file seals, manifests і root hashes, а потім монтує або “під’єднує” вміст cryptex, щоб під час виконання apps використовували версії з cryptex, якщо вони там присутні.
- У boot logs завантаження cryptex відбувається після ініціалізації ядра, але до запуску всіх системних сервісів.


#### Rapid Security Response (RSR)

- **RSR** — це механізм Apple для доставки **security patches між регулярними оновленнями OS**. Він спрямований на вміст cryptex, щоб оновлювати вразливі компоненти (наприклад, libraries і frameworks), не змінюючи основний системний том.
- Під час застосування RSR пристрій запитує на signing server Apple **Cryptex1 Image4 manifest**. Цей manifest криптографічно прив’язаний до пристрою та нового вмісту cryptex.
- Наявний AP boot ticket для базової системи **не змінюється** через RSR. Patch працює додатково поверх запечатаної базової OS.
- У macOS деякі пропатчені компоненти (наприклад, Safari) стають активними одразу після повторного запуску app; повний restart системи потрібен не завжди.
- RSR можна **видаляти**: кожен пакет містить patch і “antipatch”, який може повернутися до версії базової OS. Після видалення вміст cryptex відновлюється.
- Оновлення RSR зазвичай значно менші за повні оновлення OS і потребують нижчого рівня заряду батареї для встановлення.
