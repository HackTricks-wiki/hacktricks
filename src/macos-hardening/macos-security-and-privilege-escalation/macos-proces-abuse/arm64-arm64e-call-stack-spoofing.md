# ARM64/ARM64e Call-Stack Spoofing

## Чому unwinding на основі метаданих можна підробити

Деякі засоби безпеки macOS делегують збір стеків потоків процесу `/usr/sbin/spindump` або іншим чином покладаються на звичайний unwinder, що використовує метадані. Імплант може скористатися цією межею довіри, розмістивши у своєму стеку синтетичні записи, що відповідають ABI, щоб створити враження, ніби до чутливого API звернулися через вибрані зловмисником функції в dyld і завантажених фреймворках Apple, а не з коду імпланта, що не має backing. Це введення телеметрії в оману, а не зміна виконуваного файла чи його unwind-метаданих.<sup>[[1]](#references)</sup>

Контекст збору даних див. у розділі [macOS stackshots and `spindump`](../macos-apps-inspecting-debugging-and-fuzzing/#stackshot--microstackshots).

Unwinder не перевіряє, чи запис було створено прологом, згенерованим компілятором. Він послідовно використовує поточний `PC`, щоб вибрати рецепт Mach-O, застосовує цей рецепт до `SP`, `x29`, `x30`, пам’яті стека та будь-яких оголошених nonvolatile-регістрів, а потім використовує відновлений `PC` викликувача для вибору наступного рецепта. Якщо контрольована зловмисником пам’ять відповідає кожному вибраному рецепту, отриманий ланцюжок може бути структурно коректним і придатним для символізації, хоча таких викликів насправді не було.<sup>[[1]](#references)</sup>

## Стан кадру ARM64

В [огляді асемблера ARM64](../macos-apps-inspecting-debugging-and-fuzzing/arm64-basic-assembly.md) описано ролі регістрів і calling convention. Для звичайного кадру, створеного командами `stp x29, x30, [sp, #-16]!`, а потім `mov x29, sp`, канонічна адреса кадру (CFA), що відповідає вхідному `SP` викликувача, дорівнює `FP+0x10`:<sup>[[1]](#references)[[4]](#references)</sup>

```text
higher addresses
FP + 0x10   caller SP / CFA
FP + 0x08   saved LR / caller PC
FP + 0x00   previous FP
FP - 0x08   saved x19 (when declared)
FP - 0x10   saved x20 (when declared)
lower addresses
```

Записи кадрів утворюють зв’язаний список через `[FP]`, але простого проходження цим списком недостатньо: функції-листки можуть не мати кадру, хвостові виклики можуть усувати логічні переходи, а в незвичних розкладках використовується DWARF CFI. Правило, вибране за поточною адресою, визначає, чи читатиме розмотувач ланцюжок FP взагалі.<sup>[[1]](#references)[[4]](#references)</sup>

## Вибір правила розмотування Mach-O

Фінальні зібрані образи зберігають компактні дані розмотування в `__TEXT,__unwind_info`. Заголовок секції вказує на індекс функцій першого рівня; кожен діапазон індексу вказує на сторінку другого рівня — звичайну (`kind=2`) або стиснену (`kind=3`). Для розкладок, які не описуються компактним розмотуванням, у `__eh_frame` використовуються FDE та інструкції call-frame.<sup>[[1]](#references)[[2]](#references)</sup>

Для кожної можливої runtime PC:<sup>[[1]](#references)[[2]](#references)</sup>

1. Видаліть або нормалізуйте біти PAC ARM64e лише для пошуку.
2. Знайдіть завантажений Mach-O, виконуваний діапазон `__TEXT` якого містить адресу.
3. Обчисліть `functionOffset = normalizedPC - loadedImageBase` і відхиліть від’ємні результати або значення, більші за `UINT32_MAX`.
4. Виберіть перший діапазон першого рівня, що задовольняє умову `index[i].functionOffset <= functionOffset < index[i+1].functionOffset`.
5. Розберіть відповідну сторінку другого рівня, виберіть найближчий запис, початок якого не перевищує зсув, і перевірте, що адреса менша за початок наступного запису або кінець діапазону першого рівня.
6. Декодуйте цей запис і сформуйте точний стан, який він описує.

Якщо адресу отримано зі збереженого LR, для пошуку можна використати `PC-1`, щоб адреса одразу після виклику залишалася в діапазоні caller. Це змінює вибір правила, а не будь-який зсув стека.<sup>[[1]](#references)</sup>

Парсер має перевіряти межі кожного заголовка й масиву, вимагати версію секції `1`, враховувати кінцевий sentinel першого рівня, відхиляти нульовий зсув сторінки другого рівня та розрізняти звичайні й стиснені сторінки. У звичайній сторінці `entryPageOffset` відносний до початку цієї сторінки, тоді як зсув сторінки першого рівня відносний до початку `__unwind_info`.<sup>[[1]](#references)[[2]](#references)</sup>

Загальний режим визначається як `encoding & 0x0F000000`. Поточні визначення LLVM містять такі режими; парсер не повинен вважати кожне значення, відмінне від DWARF, класичним кадром:<sup>[[1]](#references)[[2]](#references)</sup>

| Режим | Значення | Відновлення caller |
| --- | --- | --- |
| Немає компактного правила | `0x00000000` | Зупинитися або використати незалежний резервний механізм. |
| Без кадру | `0x02000000` | Додати закодований розмір стека до поточного `SP`; PC caller — це активний LR. |
| DWARF | `0x03000000` | Виконати FDE/CFI, визначений молодшими 24 бітами. |
| Кадр | `0x04000000` | Прочитати звичайний запис кадру `x29`. |
| Кадр arm64e з автентифікованим діапазоном LR | `0x05000000` | Обробити `UNWIND_ARM64_MODE_FRAME_PAUTH_LR`; його поле зсуву вказує на `pacibsppc` у межах охопленого діапазону. |

Для режиму без кадру `stackSize = ((encoding & 0x00FFF000) >> 12) * 16`. Для режиму кадру п’ять молодших бітів задають суміжні збережені пари GPR від `x19/x20` до `x27/x28`; біти `0x100-0x800` аналогічно задають пари `d8-d15`. Ці збережені регістри можуть бути непотрібні для пошуку наступного PC, але правдоподібний віртуальний стан caller має задовольняти кожне поле, яке відновлює споживач.<sup>[[1]](#references)[[2]](#references)</sup>

## Створення синтетичних записів у режимі кадру

Процес створення відтворює роботу розмотувача у зворотному напрямку, а не шукає в стеку значення, схожі на адреси:<sup>[[1]](#references)</sup>

1. Виберіть реальний виконуваний PC у поточному завантаженому образі.
2. Декодуйте правило, що охоплює саме цей PC або адресу точки виклику.
3. Виділіть синтетичний запис із потрібним вирівнюванням і співвідношенням CFA.
4. Запишіть наступний синтетичний FP у `[FP]`, збережений PC caller цього кадру — у `[FP+8]`, а кожен GPR/FPR, збереження якого задане кодуванням, — нижче FP.
5. Зв’яжіть кілька записів і помістіть перший запис в активний `x29`.
6. Налаштуйте активний LR і шлях повернення з API так, щоб розмотування переходило до вибраного ланцюжка, а виконання можна було безпечно відновити.

Наприклад, `0x04000001` означає режим кадру та пару `x19/x20`. Відповідне перетворення стану й потрібна пам’ять:<sup>[[1]](#references)[[2]](#references)</sup>

```text
[FP - 0x10] = caller x20
[FP - 0x08] = caller x19
[FP + 0x00] = caller FP
[FP + 0x08] = caller PC
caller SP    = FP + 0x10
```

Тому адреси, що лише виглядає правдоподібною, недостатньо. Кожен відновлений PC стає ключем для наступного пошуку, тож одна адреса, кодування якої не відповідає сфабрикованому розташуванню, розриває ланцюжок або змушує споживача відновити неузгоджений стан регістрів.<sup>[[1]](#references)</sup>

## Вимоги PAC для ARM64e

PAC зберігає ключоване значення цілісності у вільних бітах вказівника; він не шифрує адресу. Схема адреси повернення arm64e у Clang використовує ключ інструкцій B і вказівник стека на вході у функцію як дискримінатор. Для звичайного кадру цей вхідний `SP` є CFA, тож збережений LR за адресою `[FP+8]` прив’язаний до `FP+0x10`.<sup>[[1]](#references)[[3]](#references)</sup>

```text
modifier = syntheticFP + 0x10
signedLR = PACIB(rawReturnPC, modifier)

# Authentication must recover the original PC:
AUTIB(signedLR, modifier) == rawReturnPC
```

Кожен синтетичний LR потрібно підписувати окремо, оскільки перенесення вже підписаного LR у фрейм з іншим CFA змінює дискримінатор і призводить до помилки автентифікації. `ptrauth_strip()` підходить для нормалізації адрес і пошуку символів, але **не** підтверджує автентичність; для будь-якого реального повернення або автентифікованого непрямого переходу потрібно використовувати ключ і модифікатор, очікувані саме під час цього переходу.<sup>[[1]](#references)[[3]](#references)</sup>

Типова arm64e-функція, що не є листовою, підписує LR перед збереженням і автентифікує його після відновлення вхідного SP:<sup>[[1]](#references)[[3]](#references)</sup>

```asm
pacibsp
stp x29, x30, [sp, #-16]!
mov x29, sp
; function body
ldp x29, x30, [sp], #16
retab
```

## Трамплін і міст відновлення

Синтетичні записи мають лише задовольнити unwinder; вони не містять повного контексту виконання. Повернення з чутливого API безпосередньо до підроблених викликачів зазвичай призвело б до збою. Тому практична схема розміщує фрейм gadget безпосередньо під API: API повертається до виконуваного коду в завантаженому фреймворку, а gadget переходить через контрольований регістр, що зберігається викликаною функцією, до моста відновлення в імпланті.<sup>[[1]](#references)</sup>

Корисний gadget зберігає LR і передає керування через контрольований регістр, наприклад за допомогою відповідної послідовності `br`, `braa` або `brab`. Перш ніж відновити виконання імпланта, міст відновлення має відновити початкові значення `x19-x30` і `SP`. На arm64e кожне автентифіковане повернення або перехід на шляху від API до gadget, від gadget до моста та від моста до імпланта потребує вказівника, підписаного ключем і дискримінатором, які використовує ця інструкція.<sup>[[1]](#references)</sup>

```text
implant -> synthetic state -> sensitive API
                              |
                              v
                     signed gadget in image
                              |
                              v
                 restore x19-x30 and original SP
                              |
                              v
                           implant
```

Результат виявляє важливий збій межі довіри для виявлення на основі стека: ланцюжок може містити лише відображені в пам’ять адреси PC фреймворків Apple, для яких можна визначити символи, і водночас не відображати реальний потік керування. Тому результати розмотування стека слід підтверджувати незалежними даними про походження виконуваної пам’яті потоку та реальні переходи навколо чутливого API, а не сприймати як трасу виконання.<sup>[[1]](#references)</sup>
