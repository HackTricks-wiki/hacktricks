# Ін’єкція у застосунки macOS Vim/Neovim

{{#include ../../../banners/hacktricks-training.md}}

## Огляд

Власна мова сценаріїв Vim (Vimscript) може виконувати **довільні Ex-команди та shell-команди під час запуску** через змінні середовища. Якщо привілейований процес (процес обслуговування або роботи від імені root, `sudo vim …`, редактор, запущений іншим інструментом, `crontab -e`, `visudo`, `git`/`less`, що запускають редактор, …) запускає Vim/Neovim із середовищем, контрольованим зловмисником, зловмисник отримує можливість виконувати код у цьому контексті.

## `VIMINIT`

Під час ініціалізації Vim читає та виконує Ex-команди зі змінної **`VIMINIT`**. Ex-команди включають `:!cmd` (запуск shell-команди) та `:call system(...)`, тож одна змінна дає змогу виконувати довільний код ще до редагування будь-якого файла.<sup>[[1]](#references)</sup>

```bash
echo "hi" > /tmp/victim.txt

# Shell command via Ex ':!'
printf ':qa!\n' | VIMINIT='silent! !touch /tmp/vim-executed' vim /tmp/victim.txt
ls -la /tmp/vim-executed

# Pure Vimscript: write the marker and exit without reading stdin
VIMINIT='call writefile(["x"], "/tmp/vim-vimscript")|qall!' vim /tmp/victim.txt
```

The `:qa!`, переданий через stdin у першому прикладі, лише закриває редактор після виконання payload; у реальному сценарії жертва може звичайно відкрити Vim.

`VIMINIT` інтерпретується як **один рядок команд Ex**. Розділяйте команди в ланцюжку символом `|` (або буквальним символом нового рядка). Він має вищий пріоритет, ніж vimrc користувача та `EXINIT`, тому payload не потребує шкідливого файла конфігурації й виконується до звичайної конфігурації користувача.<sup>[[1]](#references)[[2]](#references)</sup>

## `EXINIT`

Якщо `VIMINIT` не задано, Vim (і бінарні файли сумісності `vi`/`ex`) використовує **`EXINIT`**, який виконується так само. Це класичний варіант тієї самої примітиви з епохи vi.<sup>[[1]](#references)</sup>

```bash
printf ':qa!\n' | EXINIT='silent! !touch /tmp/exinit-executed' vim /tmp/victim.txt
ls -la /tmp/exinit-executed
```

## Локальний для проєкту rc за допомогою Vim `exrc`

Це альтернатива `VIMINIT`, що використовує файл. Якщо жертва ввімкнула `set exrc` у своїй конфігурації користувача, Vim також завантажує `.vimrc` (а потім `_vimrc` або `.exrc`) з **робочого каталогу**, а не лише з каталогу файлу, який редагується. Розмістіть локальний для проєкту `.vimrc` і попросіть жертву запустити Vim із цього проєкту. У Unix Vim застосовує обмеження `secure` до локального rc-файлу, що належить іншому користувачеві, але архів, розпакований жертвою, зазвичай надає розміщеному файлу її права власності й дає змогу уникнути цієї перевірки.<sup>[[1]](#references)</sup>

Цей ізольований маркер демонструє тригер запуску, не змінюючи реальну конфігурацію користувача:<sup>[[1]](#references)</sup>

```bash
lab=$(mktemp -d)
mkdir -p "$lab/home" "$lab/project"
printf 'set exrc\n' > "$lab/home/.vimrc"
printf 'call writefile(["loaded"], "%s/hit")\n' "$lab" > "$lab/project/.vimrc"
(cd "$lab/project" && env -u VIMINIT -u EXINIT HOME="$lab/home" vim -c 'qa!' >/dev/null 2>&1)
test -e "$lab/hit" && echo 'project rc loaded'
rm -r "$lab"
```

Neovim працює інакше: поточні збірки вимагають, щоб довіра до локальних файлів проєкту `.nvim.lua`, `.nvimrc` або `.exrc` була підтверджена перед виконанням. Довіра прив’язана до хешу вмісту файлу, тож зміна вже довіреного файлу потребує повторного підтвердження. Зловмисник, який може лише розмістити файл у репозиторії, не може розраховувати на приховане виконання через `exrc`; відрізняйте цей маршрут із явною згодою та перевіркою довіри від маршруту з Lua `require()` у поточному каталозі, описаного нижче.<sup>[[4]](#references)[[5]](#references)</sup>

Щодо доступного для запису **користувацького** vimrc, а не локального файлу проєкту, див. [конфігурацію запуску Vim у macOS](../../macos-auto-start-locations.md#vim-startup-configuration).

## Придушення запуску та можливість експлуатації

Цей примітив працює лише за **звичайного запуску**. `vim -u NONE` / `nvim -u NONE` пропускають ініціалізацію середовища та користувача (а також плагіни), тоді як `-u <file>` використовує натомість вказаний файл. Vim `-es`/`-Es` і Neovim `-es`, `-Es` або `-l` також пропускають ці кроки ініціалізації. Не вважайте `--headless` безпечним режимом: звичайний запуск Neovim у headless-режимі все одно обробляє `VIMINIT`.<sup>[[1]](#references)[[2]](#references)</sup>

Тому перевіряйте весь ланцюжок запуску: змінна має зберегтися після обгортки, політики `sudo`, системи запуску завдань і вибору редактора, а фінальна команда не повинна примусово вмикати `-u NONE`/`NORC` або пакетний режим. Надійне корисне навантаження може завершити роботу за допомогою `|qall!`; це також спрощує тестування обгорток, які не надають TTY.<sup>[[1]](#references)[[2]](#references)</sup>

## Перехоплення Lua-модулів поточного каталогу в Neovim

Окремий примітив ін’єкції в Neovim впливає на збірки, у яких у `package.path`/`package.cpath` Lua досі є шаблони поточного каталогу, як-от `./?.lua` або `./?.so`. Самого запуску Neovim недостатньо: конфігурація або плагін має викликати `require("name")`, а попередній завантажувач не повинен знаходити цей модуль. Поширеним тригером є **перевірка необов’язкової залежності**, наприклад `pcall(require, "optional_dep")`; якщо розмістити `optional_dep.lua` у каталозі, контрольованому зловмисником, його код виконається без увімкнення окремої функції локальної конфігурації `'exrc'`. Основні модулі `vim.*` і модулі, уже знайдені в `'runtimepath'`, зазвичай не можна підмінити, тому перевіряйте фактичні виклики `require()` для відсутніх/необов’язкових модулів, а не вгадуйте їхні назви.<sup>[[3]](#references)</sup>

Наведений нижче приклад відтворює примітив завантажувача за допомогою безпечного маркера:<sup>[[3]](#references)</sup>

```bash
mkdir -p /tmp/nvim-cwd-hijack
cat > /tmp/nvim-cwd-hijack/optional_dep.lua <<'LUA'
vim.fn.writefile({"loaded"}, "/tmp/nvim-cwd-hit")
return {}
LUA

cd /tmp/nvim-cwd-hijack
nvim --clean --headless '+lua require("optional_dep")' +qa
cat /tmp/nvim-cwd-hit
```

Перевірте запущену збірку, а не покладайтеся лише на рядок версії:<sup>[[3]](#references)</sup>

```bash
nvim --clean --headless '+lua io.write(package.path)' +qa 2>&1 | tr ';' '\n'
```

Upstream відстежує усунення резервного пошуку в поточному каталозі під час звичайного запуску редактора, зберігаючи поведінку Lua-скриптів (`nvim -l`). Поки встановлена збірка ще підтримує цю можливість, розмістіть це на **початку** `init.lua` (це навмисно видаляє шаблони Lua/C-модулів із відносними шляхами до поточного каталогу, тому не застосовуйте це для робочих процесів, яким вони потрібні):<sup>[[3]](#references)</sup>

```lua
local function drop_cwd(path)
  local keep = {}
  for entry in path:gmatch("[^;]+") do
    if not entry:match("^%./") then keep[#keep + 1] = entry end
  end
  return table.concat(keep, ";")
end
package.path = drop_cwd(package.path)
package.cpath = drop_cwd(package.cpath)
```

## Примітки та застереження

- **Neovim** враховує і `VIMINIT`, і резервну змінну `EXINIT`, але звичайним файлом конфігурації користувача є `init.vim` або `init.lua`.<sup>[[2]](#references)</sup>
- Шлях через змінну середовища не потребує файлу з правом на запис. Локальні rc-файли та підміна модулів у поточному каталозі — це окремі примітиви, що працюють із файлами.<sup>[[1]](#references)[[3]](#references)</sup>
- Локальні файли rc проєкту відрізняються від modelines і описаного вище резервного механізму `require()` для поточного каталогу. Vim і Neovim по-різному їх перевіряють; див. описаний вище процес роботи з локальним `exrc` проєкту.<sup>[[1]](#references)[[4]](#references)</sup>
- Змінні вибору редактора лише визначають, яку програму запустити; вони не гарантують, що `VIMINIT` буде передано кінцевому процесу. Перевіряйте точне середовище та аргументи на межі виконання Vim/Neovim.<sup>[[1]](#references)[[2]](#references)</sup>

## Посилення захисту

- Явно видаляйте ці змінні перед запуском редактора з привілеями або в автоматизованому режимі: `env -u VIMINIT -u EXINIT /usr/bin/vim -u NONE -- "$file"`. Параметр `-u NONE` важливий, коли викликаючий процес має ігнорувати всі джерела конфігурації під час запуску.<sup>[[1]](#references)[[2]](#references)</sup>
- Встановлюйте для `EDITOR`/`VISUAL` довірені абсолютні шляхи, не запускайте інтерактивні редактори від root зі успадкованим середовищем користувача та стежте, щоб обгортки не відновлювали `VIMINIT`/`EXINIT` після очищення середовища.<sup>[[1]](#references)[[2]](#references)</sup>
- Для Neovim оновіть збірку, у якій під час роботи редактора видалено шаблони пошуку Lua/C у поточному каталозі, або очищайте їх перед завантаженням плагінів. Перевіряйте код плагінів на виклики `pcall(require, ...)` із необов’язковим завантаженням модулів під час відкриття недовірених репозиторіїв.<sup>[[3]](#references)</sup>
- Вважайте контроль над середовищем редактора, робочим каталогом або конфігурацією запуску цільового процесу потенційним примітивом виконання коду в контексті безпеки редактора.<sup>[[1]](#references)[[2]](#references)[[3]](#references)</sup>
