## Основна інформація про процеси

Процес є екземпляром виконуваного файлу, однак код виконують не процеси, а потоки. Отже, **процеси — це лише контейнери для запущених потоків**, які надають пам'ять, дескриптори, порти, дозволи...

Традиційно процеси запускалися всередині інших процесів (крім PID 1) викликом **`fork`**, який створював точну копію поточного процесу, після чого **дочірній процес** зазвичай викликав **`execve`**, щоб завантажити новий виконуваний файл і запустити його. Потім було представлено **`vfork`**, щоб пришвидшити цей процес без копіювання пам'яті.\
Після цього було представлено **`posix_spawn`**, який об'єднує **`vfork`** і **`execve`** в одному виклику та приймає прапорці:

- `POSIX_SPAWN_RESETIDS`: Скинути ефективні ідентифікатори до реальних ідентифікаторів
- `POSIX_SPAWN_SETPGROUP`: Установити належність до групи процесів
- `POSUX_SPAWN_SETSIGDEF`: Установити стандартну поведінку сигналів
- `POSIX_SPAWN_SETSIGMASK`: Установити маску сигналів
- `POSIX_SPAWN_SETEXEC`: Виконати в тому самому процесі (як `execve`, але з додатковими параметрами)
- `POSIX_SPAWN_START_SUSPENDED`: Запустити призупиненим
- `_POSIX_SPAWN_DISABLE_ASLR`: Запустити без ASLR
- `_POSIX_SPAWN_NANO_ALLOCATOR:` Використовувати Nano-алокатор libmalloc
- `_POSIX_SPAWN_ALLOW_DATA_EXEC:` Дозволити `rwx` для сегментів даних
- `POSIX_SPAWN_CLOEXEC_DEFAULT`: Типово закривати всі файлові дескриптори під час exec(2)
- `_POSIX_SPAWN_HIGH_BITS_ASLR:` Рандомізувати старші біти зсуву ASLR

Крім того, `posix_spawn` дозволяє вказати масив **`posix_spawnattr`**, який керує деякими аспектами породженого процесу, а також **`posix_spawn_file_actions`** для зміни стану дескрипторів.

Коли процес завершується, він надсилає **код повернення батьківському процесу** (якщо батьківський процес завершився, новим батьківським процесом стає PID 1) за допомогою сигналу `SIGCHLD`. Батьківський процес має отримати це значення, викликавши `wait4()` або `waitid()`, і до цього моменту дочірній процес перебуває у стані zombie: він усе ще відображається у списку, але не споживає ресурси.

### PID

PID, ідентифікатор процесу, ідентифікує унікальний процес. У XNU **PID** мають розмір **64 біти**, збільшуються монотонно й **ніколи не переповнюються** (для запобігання зловживанням).

### Групи процесів, сесії та Coalations

**Процеси** можна об'єднувати в **групи**, щоб спростити керування ними. Наприклад, команди в shell-скрипті перебувають в одній групі процесів, тому їх можна **одночасно надсилати їм сигнали** за допомогою kill.\
Також можна **об'єднувати процеси в сесії**. Коли процес запускає сесію (`setsid(2)`), дочірні процеси поміщаються в цю сесію, якщо тільки вони не запускають власну сесію.

Coalition — це ще один спосіб групування процесів у Darwin. Приєднання процесу до coalition дозволяє йому отримувати доступ до спільних ресурсів пулу, спільно використовувати ledger або підпадати під Jetsam. Coalitions мають різні ролі: Leader, XPC service, Extension.

### Облікові дані та Personae

Кожен процес має **облікові дані**, які **ідентифікують його привілеї** в системі. Кожен процес має один основний `uid` і один основний `gid` (хоча він може належати до кількох груп).\
Також можна змінити ідентифікатор користувача та групи, якщо бінарний файл має біт `setuid/setgid`.\
Існує кілька функцій для **установлення нових uid/gid**.

Системний виклик **`persona`** надає альтернативний набір **облікових даних**. Прийняття persona одночасно задає її uid, gid і членство в групах. У [**source code**](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/persona.h) можна знайти структуру:
```c
struct kpersona_info { uint32_t persona_info_version;
uid_t    persona_id; /* overlaps with UID */
int      persona_type;
gid_t    persona_gid;
uint32_t persona_ngroups;
gid_t    persona_groups[NGROUPS];
uid_t    persona_gmuid;
char     persona_name[MAXLOGNAME + 1];

/* TODO: MAC policies?! */
}
```
## Базова інформація про Threads

1. **POSIX Threads (pthreads):** macOS підтримує POSIX threads (`pthreads`), які є частиною стандартного API для роботи з потоками в C/C++. Реалізація pthreads у macOS міститься в `/usr/lib/system/libsystem_pthread.dylib`, яка походить із загальнодоступного проєкту `libpthread`. Ця бібліотека надає необхідні функції для створення та керування потоками.
2. **Створення Threads:** Функція `pthread_create()` використовується для створення нових threads. Усередині ця функція викликає `bsdthread_create()`, системний виклик нижчого рівня, специфічний для ядра XNU (ядра, на якому базується macOS). Цей системний виклик приймає різні flags, отримані з `pthread_attr` (атрибутів), які визначають поведінку thread, зокрема політики планування та розмір stack.
- **Розмір stack за замовчуванням:** Розмір stack за замовчуванням для нових threads становить 512 KB. Цього достатньо для типових операцій, але розмір можна змінити за допомогою атрибутів thread, якщо потрібно більше або менше простору.
3. **Ініціалізація Thread:** Функція `__pthread_init()` відіграє важливу роль під час налаштування thread, використовуючи аргумент `env[]` для аналізу змінних середовища, які можуть містити відомості про розташування та розмір stack.

#### Завершення Thread у macOS

1. **Вихід із Threads:** Threads зазвичай завершуються викликом `pthread_exit()`. Ця функція дає thread змогу коректно завершити роботу, виконати необхідне очищення та передати return value будь-яким threads, які очікують на його завершення.
2. **Очищення Thread:** Після виклику `pthread_exit()` викликається функція `pthread_terminate()`, яка видаляє всі пов’язані структури thread. Вона звільняє Mach thread ports (Mach є підсистемою комунікації в ядрі XNU) і викликає `bsdthread_terminate` — syscall, який видаляє пов’язані з thread структури на рівні ядра.

#### Механізми синхронізації

Для керування доступом до shared resources і запобігання race conditions macOS надає кілька примітивів синхронізації. Вони мають критичне значення в середовищах із багатьма threads для забезпечення цілісності даних і стабільності системи:

1. **Mutexes:**
- **Regular Mutex (Signature: 0x4D555458):** Стандартний mutex із memory footprint 60 bytes (56 bytes для mutex і 4 bytes для signature).
- **Fast Mutex (Signature: 0x4d55545A):** Подібний до regular mutex, але оптимізований для швидших операцій; його розмір також становить 60 bytes.
2. **Condition Variables:**
- Використовуються для очікування настання певних умов; їхній розмір становить 44 bytes (40 bytes плюс 4-byte signature).
- **Condition Variable Attributes (Signature: 0x434e4441):** Configuration attributes для condition variables, розміром 12 bytes.
3. **Once Variable (Signature: 0x4f4e4345):**
- Гарантує, що певний фрагмент initialization code буде виконано лише один раз. Його розмір становить 12 bytes.
4. **Read-Write Locks:**
- Дозволяють одночасно працювати кільком readers або одному writer, забезпечуючи ефективний доступ до shared data.
- **Read Write Lock (Signature: 0x52574c4b):** Розмір становить 196 bytes.
- **Read Write Lock Attributes (Signature: 0x52574c41):** Attributes для read-write locks, розміром 20 bytes.

> [!TIP]
> Останні 4 bytes цих objects використовуються для виявлення overflows.

### Thread Local Variables (TLV)

**Thread Local Variables (TLV)** у контексті Mach-O files (формату executable files у macOS) використовуються для оголошення variables, специфічних для **кожного thread** у multi-threaded application. Це гарантує, що кожен thread має власний окремий instance variable, забезпечуючи спосіб уникати conflicts і підтримувати data integrity без необхідності в явних механізмах синхронізації, таких як mutexes.

У C та споріднених мовах thread-local variable можна оголосити за допомогою ключового слова **`__thread`**. Ось як це працює у вашому прикладі:
```c
cCopy code__thread int tlv_var;

void main (int argc, char **argv){
tlv_var = 10;
}
```
Цей фрагмент визначає `tlv_var` як thread-local змінну. Кожен потік, що виконує цей код, матиме власну `tlv_var`, і зміни, внесені одним потоком до `tlv_var`, не впливатимуть на `tlv_var` в іншому потоці.

У бінарному файлі Mach-O дані, пов'язані з thread-local змінними, організовані в спеціальні секції:

- **`__DATA.__thread_vars`**: ця секція містить метадані про thread-local змінні, зокрема їхні типи та статус ініціалізації.
- **`__DATA.__thread_bss`**: ця секція використовується для thread-local змінних, які явно не ініціалізовані. Вона є частиною пам'яті, призначеної для даних, ініціалізованих нульовими значеннями.

Mach-O також надає спеціальний API **`tlv_atexit`** для керування thread-local змінними під час завершення роботи потоку. Цей API дає змогу **реєструвати деструктори** — спеціальні функції, які очищають thread-local дані, коли потік завершує роботу.

### Пріоритети потоків

Розуміння пріоритетів потоків передбачає аналіз того, як операційна система вирішує, які потоки запускати та коли саме. На це впливає рівень пріоритету, призначений кожному потоку. У macOS та Unix-подібних системах це реалізується за допомогою таких понять, як `nice`, `renice` і класи Quality of Service (QoS).

#### Nice і Renice

1. **Nice:**
- Значення `nice` процесу — це число, яке впливає на його пріоритет. Кожен процес має значення `nice` від -20 (найвищий пріоритет) до 19 (найнижчий пріоритет). Типове значення `nice` під час створення процесу — 0.
- Нижче значення `nice` (ближче до -20) робить процес більш «егоїстичним», надаючи йому більше процесорного часу порівняно з іншими процесами з вищими значеннями `nice`.
2. **Renice:**
- `renice` — це команда, яка використовується для зміни значення `nice` вже запущеного процесу. Її можна використовувати для динамічного коригування пріоритету процесів, збільшуючи або зменшуючи виділення процесорного часу відповідно до нових значень `nice`.
- Наприклад, якщо процес тимчасово потребує більше процесорних ресурсів, його значення `nice` можна зменшити за допомогою `renice`.

#### Класи Quality of Service (QoS)

Класи QoS — це сучасніший підхід до керування пріоритетами потоків, особливо в системах на кшталт macOS, які підтримують **Grand Central Dispatch (GCD)**. Класи QoS дають змогу розробникам **категоризувати** роботу за різними рівнями відповідно до її важливості або терміновості. macOS автоматично керує пріоритизацією потоків на основі цих класів QoS:

1. **User Interactive:**
- Цей клас призначений для завдань, які наразі взаємодіють із користувачем або потребують негайного результату для забезпечення якісного користувацького досвіду. Таким завданням надається найвищий пріоритет, щоб інтерфейс залишався чутливим (наприклад, анімації або обробка подій).
2. **User Initiated:**
- Завдання, ініційовані користувачем, від яких він очікує негайного результату, наприклад відкриття документа або натискання кнопки, що потребує обчислень. Вони мають високий пріоритет, але нижчий за User Interactive.
3. **Utility:**
- Це довготривалі завдання, які зазвичай відображають індикатор прогресу (наприклад, завантаження файлів або імпорт даних). Вони мають нижчий пріоритет, ніж завдання, ініційовані користувачем, і не повинні завершуватися негайно.
4. **Background:**
- Цей клас призначений для завдань, що виконуються у фоновому режимі та невидимі для користувача. Це можуть бути індексація, синхронізація або резервне копіювання. Вони мають найнижчий пріоритет і мінімально впливають на продуктивність системи.

Використовуючи класи QoS, розробникам не потрібно керувати точними числовими значеннями пріоритетів. Натомість вони зосереджуються на характері завдання, а система відповідним чином оптимізує використання процесорних ресурсів.

Крім того, існують різні **політики планування потоків**, які дають змогу вказати набір параметрів планування, що планувальник братиме до уваги. Це можна зробити за допомогою `thread_policy_[set/get]`. Це може бути корисним під час атак із використанням race condition.

## MacOS Process Abuse

MacOS, як і будь-яка інша операційна система, надає різноманітні методи та механізми, за допомогою яких **процеси взаємодіють, обмінюються даними та спільно їх використовують**. Хоча ці методи необхідні для ефективної роботи системи, threat actors можуть зловживати ними для **виконання шкідливих дій**.

### Library Injection

Library Injection — це техніка, за якої attacker **змушує процес завантажити шкідливу бібліотеку**. Після ін'єкції бібліотека виконується в контексті цільового процесу, надаючи attacker ті самі дозволи та доступ, що й процес.

### Function Hooking

Function Hooking передбачає **перехоплення викликів функцій** або повідомлень у програмному коді. За допомогою hooking функцій attacker може **змінювати поведінку** процесу, спостерігати за конфіденційними даними або навіть отримувати контроль над потоком виконання.

### Inter Process Communication

Inter Process Communication (IPC) — це різні методи, за допомогою яких окремі процеси **обмінюються даними та спільно їх використовують**. Хоча IPC є фундаментальним для багатьох легітимних застосунків, ним також можна зловживати для обходу ізоляції процесів, витоку конфіденційної інформації або виконання несанкціонованих дій.

### Python Injection

Якщо встановлено env змінну **`PYTHONINSPECT`**, python process після завершення роботи перейде до python cli. Також можна використати **`PYTHONSTARTUP`**, щоб вказати python script, який виконуватиметься на початку інтерактивної сесії.\
Однак зверніть увагу, що script **`PYTHONSTARTUP`** не виконуватиметься, коли **`PYTHONINSPECT`** створює інтерактивну сесію.

Інші env змінні, такі як **`PYTHONPATH`** і **`PYTHONHOME`**, також можуть бути корисними для того, щоб змусити python command виконувати довільний code.

Зверніть увагу, що executables, скомпільовані за допомогою **`pyinstaller`**, не використовуватимуть ці environmental variables, навіть якщо вони працюють із використанням embedded python.

> [!CAUTION]
> Загалом мені не вдалося знайти спосіб змусити python виконувати довільний code через зловживання environment variables.\
> Однак більшість людей встановлюють pyhton за допомогою **Hombrew**, який встановлює pyhton у **writable location** для default admin user. Його можна hijack за допомогою чогось на кшталт:
>
> ```bash
> mv /opt/homebrew/bin/python3 /opt/homebrew/bin/python3.old
> cat > /opt/homebrew/bin/python3 <<EOF
> #!/bin/bash
> # Extra hijack code
> /opt/homebrew/bin/python3.old "$@"
> EOF
> chmod +x /opt/homebrew/bin/python3
> ```
>
> Навіть **root** виконуватиме цей code під час запуску python.


## Detection

### Shield

[**Shield**](https://github.com/theevilbit/Shield) — це open source застосунок на базі **EndpointSecurity**, який виявляє та блокує process injection. Він є хорошим довідником щодо того, які сигнали фактично можна спостерігати через ES, оскільки сповіщає про:<sup>[[1]](#references)[[2]](#references)</sup>

- **Injection environment variables** під час exec процесу: `DYLD_INSERT_LIBRARIES`, `CFNETWORK_LIBRARY_PATH`, `RAWCAMERA_BUNDLE_PATH` і `ELECTRON_RUN_AS_NODE`.
- Виклики **`task_for_pid`** — один процес запитує task port іншого процесу, що є передумовою для ін'єкції в нього.
- **Electron debugging arguments** — `--inspect`, `--inspect-brk` і `--remote-debugging-port`, які запускають Electron app у debug mode та дають змогу будь-кому під'єднатися до неї й виконати code.<sup>[[3]](#references)</sup>
- **Створення symlink/hardlink між різними рівнями привілеїв** — класичний примітив «створити link як normal user і спрямувати його на privileged location». Зверніть увагу, що про **symlinks можна сповіщати, але не блокувати їх**: EndpointSecurity не надає destination link до його створення.

### Calls made by other processes

У [**цьому blog post**](https://knight.sc/reverse%20engineering/2019/04/15/detecting-task-modifications.html) описано, як можна використати функцію **`task_name_for_pid`**, щоб отримати інформацію про інші **процеси, які ін'єктують code у процес**, а потім отримати інформацію про цей інший процес.<sup>[[4]](#references)</sup>

Зверніть увагу, що для виклику цієї функції потрібно мати **той самий uid**, що й процес, або бути **root** (вона повертає інформацію про процес, а не спосіб ін'єктувати code).
