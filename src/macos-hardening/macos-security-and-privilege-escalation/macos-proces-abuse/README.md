## Основна інформація про процеси

Процес — це екземпляр запущеного виконуваного файла, однак код виконують не процеси, а потоки. Отже, **процеси — це лише контейнери для потоків, що виконуються**, які надають пам’ять, дескриптори, порти, дозволи...

Традиційно процеси запускалися всередині інших процесів (крім PID 1) за допомогою виклику **`fork`**, який створював точну копію поточного процесу; потім **дочірній процес** зазвичай викликав **`execve`**, щоб завантажити новий виконуваний файл і запустити його. Пізніше для пришвидшення цього процесу без копіювання пам’яті було запроваджено **`vfork`**.\
Потім було запроваджено **`posix_spawn`**, що об’єднав **`vfork`** і **`execve`** в один виклик і приймає такі прапорці:

- `POSIX_SPAWN_RESETIDS`: Скинути ефективні ідентифікатори до реальних
- `POSIX_SPAWN_SETPGROUP`: Встановити належність до групи процесів
- `POSUX_SPAWN_SETSIGDEF`: Встановити стандартну поведінку сигналів
- `POSIX_SPAWN_SETSIGMASK`: Встановити маску сигналів
- `POSIX_SPAWN_SETEXEC`: Виконати в тому самому процесі (як `execve`, але з додатковими параметрами)
- `POSIX_SPAWN_START_SUSPENDED`: Запустити призупиненим
- `_POSIX_SPAWN_DISABLE_ASLR`: Запустити без ASLR
- `_POSIX_SPAWN_NANO_ALLOCATOR:` Використовувати Nano-розподілювач libmalloc
- `_POSIX_SPAWN_ALLOW_DATA_EXEC:` Дозволити `rwx` для сегментів даних
- `POSIX_SPAWN_CLOEXEC_DEFAULT`: Типово закривати всі файлові дескриптори під час exec(2)
- `_POSIX_SPAWN_HIGH_BITS_ASLR:` Рандомізувати старші біти зсуву ASLR

Крім того, `posix_spawn` приймає параметри **`posix_spawnattr`**, що керують аспектами запущеного процесу, і записи **`posix_spawn_file_actions`**, що змінюють файлові дескриптори.

Коли процес завершується, він надсилає **код завершення батьківському процесу** (якщо батьківський процес завершився, новим батьківським процесом стає PID 1) із сигналом `SIGCHLD`. Батьківський процес має отримати це значення за допомогою виклику `wait4()` або `waitid()`. До цього дочірній процес перебуває в стані зомбі: він іще відображається у списку, але не споживає ресурси.

### PID

PID, або ідентифікатор процесу, ідентифікує унікальний процес. У XNU **PID** має розмір **64 біти**, монотонно збільшується і **ніколи не переходить через межу діапазону** (щоб уникнути зловживань).

### Групи процесів, сесії та коаліції

**Процеси** можна об’єднувати в **групи**, щоб спростити керування ними. Наприклад, команди в shell-скрипті належать до однієї групи процесів, тож їх можна **сигналізувати одночасно**, наприклад за допомогою kill.\
Процеси також можна **об’єднувати в сесії**. Коли процес починає сесію (`setsid(2)`), його дочірні процеси належать до цієї сесії, якщо не почнуть власну.

У Darwin для групування процесів також використовуються коаліції. Вступ до коаліції дає процесу доступ до спільних ресурсів пулу, спільного обліку ресурсів або наражає його на Jetsam. У коаліцій є різні ролі: лідер, служба XPC, розширення.

### Облікові дані та персони

Кожен процес має **облікові дані**, які **визначають його привілеї** в системі. Кожен процес має один основний `uid` і один основний `gid` (хоча він може належати до кількох груп).\
Також можна змінити ідентифікатори користувача й групи, якщо бінарний файл має біт `setuid/setgid`.\
Є кілька функцій для **встановлення нових uid/gid**.

Системний виклик **`persona`** надає альтернативний набір **облікових даних**. Прийняття персони одночасно означає використання її uid, gid і членства в групах. У [**вихідному коді**](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/persona.h) можна знайти структуру:

```c
struct kpersona_info { uint32_t persona_info_version;
    uid_t    persona_id; /* overlaps with UID */
    int      persona_type;
    gid_t    persona_gid;
    uint32_t persona_ngroups;
    gid_t    persona_groups[NGROUPS];
    uid_t    persona_gmuid;
    char     persona_name[MAXLOGNAME + 1];

    /* TODO: MAC policies?! */
}
```

## Основна інформація про потоки

1. **POSIX Threads (pthreads):** macOS підтримує POSIX-потоки (`pthreads`), які є частиною стандартного API для роботи з потоками в C/C++. Реалізація pthreads у macOS міститься в `/usr/lib/system/libsystem_pthread.dylib` і походить із загальнодоступного проєкту `libpthread`. Ця бібліотека надає необхідні функції для створення потоків і керування ними.
2. **Створення потоків:** для створення нових потоків використовується функція `pthread_create()`. Усередині вона викликає `bsdthread_create()` — низькорівневий системний виклик, специфічний для ядра XNU (ядра, на якому базується macOS). Цей системний виклик приймає різні прапорці, отримані з `pthread_attr` (атрибутів), які визначають поведінку потоку, зокрема політики планування та розмір стека.
   - **Розмір стека за замовчуванням:** розмір стека для нових потоків за замовчуванням становить 512 KB. Цього достатньо для типових операцій, але його можна змінити за допомогою атрибутів потоку, якщо потрібно більше або менше місця.
3. **Ініціалізація потоку:** функція `__pthread_init()` відіграє важливу роль під час налаштування потоку, використовуючи аргумент `env[]` для аналізу змінних середовища, які можуть містити відомості про розташування та розмір стека.

#### Завершення потоків у macOS

1. **Вихід із потоків:** зазвичай потоки завершуються викликом `pthread_exit()`. Ця функція дає змогу потоку коректно завершитися, виконати необхідне очищення та передати значення повернення потокам, що очікують на його завершення.
2. **Очищення потоку:** після виклику `pthread_exit()` викликається функція `pthread_terminate()`, яка видаляє всі пов’язані структури потоку. Вона звільняє порти потоків Mach (Mach — підсистема зв’язку в ядрі XNU) та викликає `bsdthread_terminate` — системний виклик, який видаляє пов’язані з потоком структури на рівні ядра.

#### Механізми синхронізації

Для керування доступом до спільних ресурсів і запобігання станам перегонів macOS надає кілька примітивів синхронізації. Вони критично важливі в багатопотокових середовищах для забезпечення цілісності даних і стабільності системи:

1. **М’ютекси:**
   - **Звичайний м’ютекс (сигнатура: 0x4D555458):** стандартний м’ютекс, що займає 60 bytes пам’яті (56 bytes для м’ютекса та 4 bytes для сигнатури).
   - **Швидкий м’ютекс (сигнатура: 0x4d55545A):** подібний до звичайного м’ютекса, але оптимізований для швидшого виконання операцій; також займає 60 bytes.
2. **Змінні умов:**
   - Використовуються для очікування настання певних умов; займають 44 bytes (40 bytes плюс 4-byte сигнатура).
   - **Атрибути змінної умови (сигнатура: 0x434e4441):** параметри налаштування змінних умов, розміром 12 bytes.
3. **Змінна одноразової ініціалізації (сигнатура: 0x4f4e4345):**
   - Гарантує, що фрагмент коду ініціалізації буде виконано лише один раз. Її розмір — 12 bytes.
4. **Блокування читання-запису:**
   - Дають змогу одночасно працювати кільком читачам або одному записувачу, забезпечуючи ефективний доступ до спільних даних.
   - **Блокування читання-запису (сигнатура: 0x52574c4b):** розмір — 196 bytes.
   - **Атрибути блокування читання-запису (сигнатура: 0x52574c41):** атрибути блокувань читання-запису розміром 20 bytes.

> [!TIP]
> Останні 4 bytes цих об’єктів використовуються для виявлення переповнень.

### Локальні змінні потоку (TLV)

**Локальні змінні потоку (TLV)** у контексті файлів Mach-O (формату виконуваних файлів у macOS) використовуються для оголошення змінних, специфічних для **кожного потоку** в багатопотоковій програмі. Це гарантує, що кожен потік матиме власний екземпляр змінної, даючи змогу уникати конфліктів і зберігати цілісність даних без явних механізмів синхронізації, як-от м’ютекси.

У C та споріднених мовах локальну змінну потоку можна оголосити за допомогою ключового слова **`__thread`**. Ось як це працює у вашому прикладі:

```c
cCopy code__thread int tlv_var;

void main (int argc, char **argv){
    tlv_var = 10;
}
```

Цей фрагмент визначає `tlv_var` як змінну, локальну для потоку. Кожен потік, що виконує цей код, матиме власну `tlv_var`, і зміни, які один потік вносить у `tlv_var`, не впливатимуть на `tlv_var` в іншому потоці.

У бінарному файлі Mach-O дані, пов’язані зі змінними, локальними для потоку, організовані в окремі секції:

- **`__DATA.__thread_vars`**: ця секція містить метадані про змінні, локальні для потоку, наприклад їхні типи та стан ініціалізації.
- **`__DATA.__thread_bss`**: ця секція використовується для змінних, локальних для потоку, які явно не ініціалізовані. Це частина пам’яті, зарезервована для даних, ініціалізованих нулями.

Mach-O також надає спеціальний API під назвою **`tlv_atexit`** для керування змінними, локальними для потоку, коли потік завершується. Цей API дає змогу **реєструвати деструктори** — спеціальні функції, які очищують дані потоку після його завершення.

### Пріоритети потоків

Щоб зрозуміти пріоритети потоків, потрібно розглянути, як операційна система вирішує, які потоки запускати й коли. На це рішення впливає рівень пріоритету, призначений кожному потоку. У macOS та Unix-подібних системах для цього використовуються такі поняття, як `nice`, `renice` і класи Quality of Service (QoS).

#### Nice і Renice

1. **Nice:**
   - Значення `nice` процесу — це число, яке впливає на його пріоритет. Значення `nice` для процесу перебуває в діапазоні від -20 (найвищий пріоритет) до 19 (найнижчий пріоритет). Типове значення `nice` для нового процесу — 0.
   - Нижче значення `nice` (ближче до -20) робить процес більш «егоїстичним», надаючи йому більше процесорного часу порівняно з процесами, які мають вищі значення `nice`.
2. **Renice:**
   - `renice` — це команда для зміни значення `nice` вже запущеного процесу. Її можна використовувати для динамічного коригування пріоритету процесу, збільшуючи або зменшуючи виділений йому процесорний час відповідно до нового значення `nice`.
   - Наприклад, якщо процесу тимчасово потрібно більше ресурсів CPU, можна знизити його значення `nice` за допомогою `renice`.

#### Класи Quality of Service (QoS)

Класи QoS — це сучасніший підхід до керування пріоритетами потоків, зокрема в системах на кшталт macOS, що підтримують **Grand Central Dispatch (GCD)**. Класи QoS дають змогу розробникам **категоризувати** завдання за рівнем важливості або терміновості. macOS автоматично керує пріоритетами потоків на основі цих класів QoS:

1. **User Interactive:**
   - Цей клас призначений для завдань, які безпосередньо взаємодіють із користувачем або потребують негайного результату для забезпечення належної взаємодії з ним. Такі завдання мають найвищий пріоритет, щоб інтерфейс залишався чутливим (наприклад, анімація чи обробка подій).
2. **User Initiated:**
   - Завдання, які запускає користувач і для яких він очікує негайного результату, наприклад відкриття документа або натискання кнопки, що запускає обчислення. Вони мають високий пріоритет, але нижчий, ніж у завдань User Interactive.
3. **Utility:**
   - Ці завдання тривалі й зазвичай відображають індикатор прогресу (наприклад, завантаження файлів чи імпорт даних). Вони мають нижчий пріоритет, ніж завдання User Initiated, і не потребують негайного завершення.
4. **Background:**
   - Цей клас призначений для завдань, що виконуються у фоновому режимі й невидимі для користувача. До них належать, наприклад, індексація, синхронізація та резервне копіювання. Вони мають найнижчий пріоритет і мінімально впливають на продуктивність системи.

Використовуючи класи QoS, розробникам не потрібно керувати точними значеннями пріоритету — достатньо зосередитися на характері завдання, а система відповідно оптимізує використання ресурсів CPU.

Крім того, існують різні **політики планування потоків**, які задають набір параметрів планування, що враховуватимуться планувальником. Це можна зробити за допомогою `thread_policy_[set/get]`. Це може бути корисним під час атак із використанням race condition.

## Зловживання процесами в macOS

macOS надає багато механізмів, за допомогою яких **процеси взаємодіють, обмінюються даними та спільно їх використовують**. Хоча ці механізми необхідні для нормальної роботи системи, зловмисники можуть використовувати їх для ін’єкції, виконання коду або доступу до даних.

**`NODE_OPTIONS`** попередньо завантажує JavaScript зловмисника через `--require` (файл) або `--import data:text/javascript,…` (без файлу, Node ≥ 20.6); **`NODE_REPL_EXTERNAL_MODULE`** завантажує модуль в інтерактивний REPL, а **`ELECTRON_RUN_AS_NODE`** знову вмикає все це для бінарних файлів Electron.

### Ін’єкція в shell

Неінтерактивний Bash читає **`BASH_ENV`**; інтерактивні POSIX-shell читають **`ENV`**; zsh читає **`$ZDOTDIR/.zshenv`**; а fish читає конфігурацію з **`XDG_CONFIG_HOME`** або **`XDG_DATA_DIRS`**. Кожен із них може виконати контрольований файл запуску перед запланованою командою. Bash також виконує підстановку команди, розміщену в **`PS4`**, коли ввімкнено xtrace (наприклад, через успадковане **`SHELLOPTS=xtrace`**):

### Впровадження команд через stdin shell

Запуск `/bin/zsh -s` змушує shell читати програму зі стандартного вводу. Тому завантажувач, який копіює недовірений структурований документ у stdin дочірнього процесу без попереднього розбору, перетворює весь документ на вихідний код shell. В одному випадку спостережуваний завантажувач передавав загальнодоступний файл iCalendar через анонімний канал рядок за рядком. Метадані календаря не спрацьовували як команди, але zsh продовжував виконання, доки не доходив до виконуваних рядків після `DESCRIPTION:`. Ці рядки завантажували й запускали наступний пакет застосунку. Очікуваний тип вмісту носія та довірений хостинг не робили це безпечним; небезпека полягала в передаванні його байтів інтерпретатору.<sup>[[5]](#references)</sup>

Пов’язані етапи розглянуто в розділах [Mach-O overlays](../macos-files-folders-and-binaries/universal-binaries-and-mach-o-format.md), [Gatekeeper and quarantine](../macos-security-protections/macos-gatekeeper.md) і [macOS auto-start locations](../../macos-auto-start-locations.md).

### Ін’єкція в Python

Ланцюжок стандартної бібліотеки **`PYTHONWARNINGS`** і **`BROWSER`** може виконати команду під час розбору фільтра попереджень. Альтернативний спосіб із файлом — розмістити `sitecustomize.py` у шляху **`PYTHONPATH`**, щоб звичайна ініціалізація `site` імпортувала його до цільового скрипту. **`PYTHONBREAKPOINT`** запускає вибрану callable-функцію або модуль, коли код доходить до `breakpoint()`. Змінні, призначені лише для інтерактивного режиму, як-от **`PYTHONSTARTUP`**, застосовні в меншій кількості випадків.

Зверніть увагу, що виконувані файли, скомпільовані за допомогою **`pyinstaller`**, не використовують ці змінні середовища, навіть якщо запускаються з вбудованим Python.

## Виявлення

### Shield

[**Shield**](https://github.com/theevilbit/Shield) — це застосунок із відкритим вихідним кодом на основі **EndpointSecurity**, який виявляє та блокує ін’єкцію в процеси. Це корисне джерело для розуміння того, які сигнали доступні через Endpoint Security, оскільки він сповіщає про такі події:<sup>[[1]](#references)</sup><sup>[[2]](#references)</sup>

- **Змінні середовища для ін’єкції** під час запуску процесу: `DYLD_INSERT_LIBRARIES`, `CFNETWORK_LIBRARY_PATH`, `RAWCAMERA_BUNDLE_PATH` і `ELECTRON_RUN_AS_NODE`.
- Виклики **`task_for_pid`** — один процес запитує task port іншого; це необхідна передумова для ін’єкції в нього.
- **Аргументи налагодження Electron** — `--inspect`, `--inspect-brk` і `--remote-debugging-port`, які запускають застосунок Electron у режимі налагодження та дають змогу будь-кому приєднатися до нього й виконувати код.<sup>[[3]](#references)</sup>
- **Створення symlink/hardlink між рівнями привілеїв** — класичний примітив «створити посилання зі звичайного користувача й спрямувати його на привілейоване розташування». Зверніть увагу: **про створення symlink можна сповіщати, але його не можна блокувати**: EndpointSecurity не надає цільове розташування посилання до його створення.

### Виклики, здійснені іншими процесами

У [**цьому дописі в блозі**](https://knight.sc/reverse%20engineering/2019/04/15/detecting-task-modifications.html) описано, як за допомогою функції **`task_name_for_pid`** отримати інформацію про інші **процеси, що впроваджують код у процес**, а потім отримати відомості про сам процес, який виконує ін’єкцію.<sup>[[4]](#references)</sup>

Зверніть увагу: щоб викликати цю функцію, потрібно мати **той самий uid**, що й процес, або бути **root** (функція повертає інформацію про процес, а не спосіб впровадження коду).
