## Основна інформація про процеси

Процес є екземпляром виконуваного файлу, що працює, однак процеси не виконують код — це роблять потоки. Отже, **процеси є лише контейнерами для потоків, що виконуються**, і надають їм пам'ять, дескриптори, порти, дозволи...

Традиційно процеси запускалися всередині інших процесів (за винятком PID 1) шляхом виклику **`fork`**, який створював точну копію поточного процесу, після чого **дочірній процес** зазвичай викликав **`execve`**, щоб завантажити новий виконуваний файл і запустити його. Потім було представлено **`vfork`**, щоб пришвидшити цей процес без копіювання пам'яті.\
Пізніше було представлено **`posix_spawn`**, який об'єднав **`vfork`** і **`execve`** в одному виклику та приймав такі прапорці:

- `POSIX_SPAWN_RESETIDS`: Скинути ефективні ідентифікатори до реальних ідентифікаторів
- `POSIX_SPAWN_SETPGROUP`: Встановити належність до групи процесів
- `POSUX_SPAWN_SETSIGDEF`: Встановити поведінку сигналів за замовчуванням
- `POSIX_SPAWN_SETSIGMASK`: Встановити маску сигналів
- `POSIX_SPAWN_SETEXEC`: Виконати в тому самому процесі (як `execve`, але з додатковими параметрами)
- `POSIX_SPAWN_START_SUSPENDED`: Запустити призупиненим
- `_POSIX_SPAWN_DISABLE_ASLR`: Запустити без ASLR
- `_POSIX_SPAWN_NANO_ALLOCATOR:` Використовувати Nano allocator з libmalloc
- `_POSIX_SPAWN_ALLOW_DATA_EXEC:` Дозволити `rwx` для сегментів даних
- `POSIX_SPAWN_CLOEXEC_DEFAULT`: Типово закривати всі файлові описи під час exec(2)
- `_POSIX_SPAWN_HIGH_BITS_ASLR:` Рандомізувати старші біти зсуву ASLR

Крім того, `posix_spawn` дозволяє вказати масив **`posix_spawnattr`**, який керує деякими аспектами породженого процесу, а також **`posix_spawn_file_actions`** для зміни стану дескрипторів.

Коли процес завершується, він надсилає **код повернення батьківському процесу** (якщо батьківський процес завершився, новим батьківським процесом стає PID 1) за допомогою сигналу `SIGCHLD`. Батьківський процес має отримати це значення, викликавши `wait4()` або `waitid()`, і до цього моменту дочірній процес перебуває у стані zombie: він усе ще відображається у списку, але не споживає ресурси.

### PID

PID, або ідентифікатор процесу, ідентифікує унікальний процес. У XNU **PID** має розмір **64 біти**, збільшується монотонно та **ніколи не переповнюється** (щоб запобігти зловживанням).

### Групи процесів, сесії та Coalations

**Процеси** можна об'єднувати в **групи**, щоб спростити керування ними. Наприклад, команди в shell-скрипті перебуватимуть в одній групі процесів, завдяки чому їх можна **одночасно надсилати їм сигнали** за допомогою kill.\
Також можна **об'єднувати процеси в сесії**. Коли процес запускає сесію (`setsid(2)`), дочірні процеси розміщуються в цій сесії, якщо тільки вони не запускають власну сесію.

Coalition — це ще один спосіб групування процесів у Darwin. Приєднання процесу до coalition дозволяє йому отримувати доступ до спільних ресурсів пулу, спільно використовувати ledger або наражатися на Jetsam. Coalitions мають різні ролі: Leader, XPC service, Extension.

### Облікові дані та Personae

Кожен процес має **облікові дані**, які **визначають його привілеї** в системі. Кожен процес має один основний `uid` і один основний `gid` (хоча він може належати до кількох груп).\
Також можна змінити ідентифікатор користувача та групи, якщо бінарний файл має біт `setuid/setgid`.\
Існує кілька функцій для **встановлення нових uid/gid**.

Системний виклик **`persona`** надає альтернативний набір **облікових даних**. Прийняття persona одночасно встановлює її uid, gid і членство в групах. У [**вихідному коді**](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/persona.h) можна знайти структуру:
```c
struct kpersona_info { uint32_t persona_info_version;
uid_t    persona_id; /* overlaps with UID */
int      persona_type;
gid_t    persona_gid;
uint32_t persona_ngroups;
gid_t    persona_groups[NGROUPS];
uid_t    persona_gmuid;
char     persona_name[MAXLOGNAME + 1];

/* TODO: MAC policies?! */
}
```
## Основна інформація про Threads

1. **POSIX Threads (pthreads):** macOS підтримує POSIX threads (`pthreads`), які є частиною стандартного API для роботи з потоками в C/C++. Реалізація pthreads у macOS знаходиться в `/usr/lib/system/libsystem_pthread.dylib` і походить із загальнодоступного проєкту `libpthread`. Ця бібліотека надає необхідні функції для створення потоків і керування ними.
2. **Створення потоків:** Функція `pthread_create()` використовується для створення нових потоків. Усередині ця функція викликає `bsdthread_create()`, системний виклик нижчого рівня, специфічний для ядра XNU (ядра, на якому базується macOS). Цей системний виклик приймає різні прапорці, отримані з `pthread_attr` (атрибутів), які визначають поведінку потоку, зокрема політики планування та розмір стека.
- **Розмір стека за замовчуванням:** розмір стека для нових потоків за замовчуванням становить 512 KB. Цього достатньо для типових операцій, але розмір можна змінити за допомогою атрибутів потоку, якщо потрібно більше або менше простору.
3. **Ініціалізація потоку:** Функція `__pthread_init()` має важливе значення під час налаштування потоку. Вона використовує аргумент `env[]` для аналізу змінних середовища, які можуть містити відомості про розташування та розмір стека.

#### Завершення потоків у macOS

1. **Завершення потоків:** Зазвичай потоки завершуються викликом `pthread_exit()`. Ця функція дає змогу потоку коректно завершитися, виконати необхідне очищення та передати значення, що повертається, потокам, які очікують на його завершення.
2. **Очищення потоку:** Після виклику `pthread_exit()` викликається функція `pthread_terminate()`, яка обробляє видалення всіх пов’язаних із потоком структур. Вона звільняє порти Mach-потоків (Mach — це підсистема комунікації в ядрі XNU) і викликає `bsdthread_terminate` — syscall, що видаляє пов’язані з потоком структури на рівні ядра.

#### Механізми синхронізації

Для керування доступом до спільних ресурсів і запобігання race conditions macOS надає кілька примітивів синхронізації. Вони мають критичне значення в середовищах із багатьма потоками для забезпечення цілісності даних і стабільності системи:

1. **Mutexes:**
- **Regular Mutex (Signature: 0x4D555458):** стандартний mutex із використанням пам’яті обсягом 60 байтів (56 байтів для mutex і 4 байти для сигнатури).
- **Fast Mutex (Signature: 0x4d55545A):** подібний до звичайного mutex, але оптимізований для швидшої роботи; його розмір також становить 60 байтів.
2. **Condition Variables:**
- Використовуються для очікування настання певних умов; їхній розмір становить 44 байти (40 байтів плюс 4-байтна сигнатура).
- **Condition Variable Attributes (Signature: 0x434e4441):** атрибути конфігурації для condition variables розміром 12 байтів.
3. **Once Variable (Signature: 0x4f4e4345):**
- Гарантує, що фрагмент коду ініціалізації буде виконано лише один раз. Його розмір становить 12 байтів.
4. **Read-Write Locks:**
- Дозволяють одночасно працювати кільком читачам або одному записувачу, забезпечуючи ефективний доступ до спільних даних.
- **Read Write Lock (Signature: 0x52574c4b):** має розмір 196 байтів.
- **Read Write Lock Attributes (Signature: 0x52574c41):** атрибути read-write locks розміром 20 байтів.

> [!TIP]
> Останні 4 байти цих об’єктів використовуються для виявлення переповнень.

### Thread Local Variables (TLV)

**Thread Local Variables (TLV)** у контексті файлів Mach-O (формату виконуваних файлів у macOS) використовуються для оголошення змінних, специфічних для **кожного потоку** в багатопотоковій програмі. Це гарантує, що кожен потік має власний окремий екземпляр змінної, забезпечуючи спосіб уникнення конфліктів і підтримання цілісності даних без необхідності в явних механізмах синхронізації, таких як mutexes.

У C і споріднених мовах thread-local змінну можна оголосити за допомогою ключового слова **`__thread`**. Ось як це працює у вашому прикладі:
```c
cCopy code__thread int tlv_var;

void main (int argc, char **argv){
tlv_var = 10;
}
```
Цей фрагмент визначає `tlv_var` як thread-local змінну. Кожен потік, що виконує цей код, матиме власну `tlv_var`, і зміни, внесені одним потоком до `tlv_var`, не впливатимуть на `tlv_var` в іншому потоці.

У Mach-O binary дані, пов’язані з thread-local змінними, організовані в спеціальні секції:

- **`__DATA.__thread_vars`**: ця секція містить метадані про thread-local змінні, наприклад їхні типи та статус ініціалізації.
- **`__DATA.__thread_bss`**: ця секція використовується для thread-local змінних, які явно не ініціалізовані. Це частина пам’яті, виділена для даних, ініціалізованих нульовими значеннями.

Mach-O також надає спеціальний API під назвою **`tlv_atexit`** для керування thread-local змінними під час завершення потоку. Цей API дає змогу **реєструвати деструктори** — спеціальні функції, які очищають thread-local дані під час завершення потоку.

### Пріоритети потоків

Розуміння пріоритетів потоків передбачає аналіз того, як операційна система визначає, які потоки запускати та коли. На це рішення впливає рівень пріоритету, призначений кожному потоку. У macOS та Unix-подібних системах це реалізовано за допомогою таких концепцій, як `nice`, `renice` і класи Quality of Service (QoS).

#### Nice і Renice

1. **Nice:**
- Значення `nice` процесу — це число, яке впливає на його пріоритет. Кожен процес має значення `nice` від -20 (найвищий пріоритет) до 19 (найнижчий пріоритет). Типове значення `nice` під час створення процесу — 0.
- Нижче значення `nice` (ближче до -20) робить процес більш «егоїстичним», надаючи йому більше процесорного часу порівняно з іншими процесами, які мають вищі значення `nice`.
2. **Renice:**
- `renice` — це команда для зміни значення `nice` вже запущеного процесу. Її можна використовувати для динамічного коригування пріоритету процесів, збільшуючи або зменшуючи виділення процесорного часу на основі нових значень `nice`.
- Наприклад, якщо процесу тимчасово потрібно більше процесорних ресурсів, його значення `nice` можна зменшити за допомогою `renice`.

#### Класи Quality of Service (QoS)

Класи QoS — це сучасніший підхід до керування пріоритетами потоків, зокрема в системах на кшталт macOS, які підтримують **Grand Central Dispatch (GCD)**. Класи QoS дають змогу розробникам **категоризувати** роботу за різними рівнями залежно від її важливості або терміновості. macOS автоматично керує пріоритетами потоків на основі цих класів QoS:

1. **User Interactive:**
- Цей клас призначений для завдань, які безпосередньо взаємодіють із користувачем або потребують негайного результату для забезпечення якісного користувацького досвіду. Такі завдання отримують найвищий пріоритет, щоб інтерфейс залишався чутливим (наприклад, анімації або обробка подій).
2. **User Initiated:**
- Завдання, ініційовані користувачем, від яких він очікує негайного результату, наприклад відкриття документа або натискання кнопки, що потребує обчислень. Вони мають високий пріоритет, але нижчий за User Interactive.
3. **Utility:**
- Це довготривалі завдання, які зазвичай відображають індикатор прогресу (наприклад, завантаження файлів або імпорт даних). Вони мають нижчий пріоритет, ніж завдання, ініційовані користувачем, і не повинні завершуватися негайно.
4. **Background:**
- Цей клас призначений для завдань, які виконуються у фоновому режимі та невидимі для користувача. Це можуть бути індексація, синхронізація або резервне копіювання. Вони мають найнижчий пріоритет і мінімально впливають на продуктивність системи.

Використовуючи класи QoS, розробникам не потрібно керувати точними значеннями пріоритетів; натомість вони зосереджуються на характері завдання, а система відповідним чином оптимізує процесорні ресурси.

Крім того, існують різні **політики планування потоків**, які дають змогу визначити набір параметрів планування, що планувальник братиме до уваги. Це можна зробити за допомогою `thread_policy_[set/get]`. Це може бути корисним під час атак із race condition.

## MacOS Process Abuse

MacOS, як і будь-яка інша операційна система, надає різноманітні методи та механізми для **взаємодії, обміну даними та спільного використання даних процесами**. Хоча ці методи необхідні для ефективної роботи системи, threat actors можуть зловживати ними для **виконання malicious activities**.

### Library Injection

Library Injection — це техніка, за якої attacker **примушує процес завантажити malicious library**. Після ін’єкції library виконується в контексті target process, надаючи attacker ті самі permissions і доступ, що й процес.

{{#ref}}
macos-library-injection/
{{#endref}}

### Function Hooking

Function Hooking передбачає **перехоплення викликів функцій** або повідомлень у програмному коді. За допомогою hooking functions attacker може **змінювати поведінку** процесу, спостерігати за sensitive data або навіть отримувати контроль над потоком виконання.


{{#ref}}
macos-function-hooking.md
{{#endref}}

### Inter Process Communication

Inter Process Communication (IPC) — це різні методи, за допомогою яких окремі процеси **спільно використовують та обмінюються даними**. Хоча IPC є фундаментальним для багатьох легітимних застосунків, ним також можна зловживати для обходу ізоляції процесів, здійснення leak sensitive information або виконання несанкціонованих дій.

### Dirty NIB

NIB files **визначають елементи user interface (UI)** та їхню взаємодію в межах application. Однак вони можуть **виконувати arbitrary commands**, а **Gatekeeper не перешкоджає** повторному виконанню вже запущеного application, якщо **NIB file було modified**. ### Python Injection

Якщо environment variable **`PYTHONINSPECT`** встановлено, python process після завершення роботи перейде до python cli. Також можна використати **`PYTHONSTARTUP`**, щоб вказати python script, який буде виконано на початку interactive session.\
Однак зауважте, що **`PYTHONSTARTUP`** script не буде виконано, коли **`PYTHONINSPECT`** створює interactive session.

Інші env variables, такі як **`PYTHONPATH`** і **`PYTHONHOME`**, також можуть бути корисними, щоб змусити python command execute arbitrary code.

Зверніть увагу, що executables, скомпільовані за допомогою **`pyinstaller`**, не використовуватимуть ці environmental variables, навіть якщо вони працюють із використанням embedded python.

> [!CAUTION]
> Загалом мені не вдалося знайти спосіб змусити python execute arbitrary code через зловживання environment variables.\
> Однак більшість людей встановлюють pyhton за допомогою **Hombrew**, який встановлює pyhton у **writable location** для default admin user. Його можна hijack за допомогою чогось на кшталт:
>
> ```bash
> mv /opt/homebrew/bin/python3 /opt/homebrew/bin/python3.old
> cat > /opt/homebrew/bin/python3 <<EOF
> #!/bin/bash
> # Extra hijack code
> /opt/homebrew/bin/python3.old "$@"
> EOF
> chmod +x /opt/homebrew/bin/python3
> ```
>
> Навіть **root** виконуватиме цей code під час запуску python.


## Detection

### Shield

[**Shield**](https://github.com/theevilbit/Shield) — це open source application на основі **EndpointSecurity**, який виявляє та блокує process injection. Це хороший reference щодо того, які signals фактично можна спостерігати через ES, оскільки він сповіщає про:<sup>[[1]](#references)</sup>

- **Injection environment variables** під час exec процесу: `DYLD_INSERT_LIBRARIES`, `CFNETWORK_LIBRARY_PATH`, `RAWCAMERA_BUNDLE_PATH` і `ELECTRON_RUN_AS_NODE`.
- Виклики **`task_for_pid`** — один процес запитує task port іншого процесу, що є передумовою для inject у нього.
- **Electron debugging arguments** — `--inspect`, `--inspect-brk` і `--remote-debugging-port`, які запускають Electron app у debug mode та дають змогу будь-кому під’єднатися до неї й виконувати code.
- **Створення symlink/hardlink між рівнями privileges** — класичний primitive «створити link як normal user і вказати його на privileged location». Зверніть увагу, що **symlinks можна відстежувати, але не блокувати**: EndpointSecurity не надає destination link перед його створенням.

### Calls made by other processes

У [**цьому blog post**](https://knight.sc/reverse%20engineering/2019/04/15/detecting-task-modifications.html) описано, як можна використати function **`task_name_for_pid`**, щоб отримати інформацію про інші **processes, які inject code у process**, а потім отримати інформацію про той інший process.<sup>[[4]](#references)</sup>

Зверніть увагу, що для виклику цієї function потрібно мати **той самий uid**, що й process, який її запускає, або бути **root** (вона повертає інформацію про process, а не спосіб inject code).
