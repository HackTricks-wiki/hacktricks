## Основна інформація про процеси

Процес є екземпляром виконуваного файлу, що працює, однак код виконують не процеси, а потоки. Отже, **процеси є лише контейнерами для потоків, що виконуються**, і надають їм пам'ять, дескриптори, порти, дозволи...

Традиційно процеси запускалися всередині інших процесів (за винятком PID 1) шляхом виклику **`fork`**, який створював точну копію поточного процесу, після чого **дочірній процес** зазвичай викликав **`execve`**, щоб завантажити новий виконуваний файл і запустити його. Потім було представлено **`vfork`**, щоб пришвидшити цей процес без копіювання пам'яті.\
Пізніше було представлено **`posix_spawn`**, який об'єднав **`vfork`** і **`execve`** в одному виклику та приймає такі прапорці:

- `POSIX_SPAWN_RESETIDS`: Скинути ефективні ідентифікатори до реальних ідентифікаторів
- `POSIX_SPAWN_SETPGROUP`: Установити належність до групи процесів
- `POSUX_SPAWN_SETSIGDEF`: Установити поведінку сигналів за замовчуванням
- `POSIX_SPAWN_SETSIGMASK`: Установити маску сигналів
- `POSIX_SPAWN_SETEXEC`: Виконати в тому самому процесі (як `execve`, але з додатковими параметрами)
- `POSIX_SPAWN_START_SUSPENDED`: Запустити призупиненим
- `_POSIX_SPAWN_DISABLE_ASLR`: Запустити без ASLR
- `_POSIX_SPAWN_NANO_ALLOCATOR:` Використовувати Nano allocator з libmalloc
- `_POSIX_SPAWN_ALLOW_DATA_EXEC:` Дозволити `rwx` для сегментів даних
- `POSIX_SPAWN_CLOEXEC_DEFAULT`: Типово закривати всі файлові описи під час exec(2)
- `_POSIX_SPAWN_HIGH_BITS_ASLR:` Рандомізувати старші біти зсуву ASLR

Крім того, `posix_spawn` дозволяє вказати масив **`posix_spawnattr`**, який керує деякими аспектами породженого процесу, а також **`posix_spawn_file_actions`** для зміни стану дескрипторів.

Коли процес завершується, він надсилає **код повернення батьківському процесу** (якщо батьківський процес завершився, новим батьківським процесом стає PID 1) за допомогою сигналу `SIGCHLD`. Батьківський процес має отримати це значення, викликавши `wait4()` або `waitid()`, і до цього моменту дочірній процес перебуває у стані zombie: він усе ще відображається у списку, але не споживає ресурси.

### PID

PID, або ідентифікатор процесу, ідентифікує унікальний процес. У XNU **PID** мають розмір **64 біти**, збільшуються монотонно й **ніколи не переповнюються** (щоб запобігти зловживанням).

### Групи процесів, сесії та Coalations

**Процеси** можна об'єднувати в **групи**, щоб спростити керування ними. Наприклад, команди у shell-скрипті перебуватимуть в одній групі процесів, тому їх можна **сигналізувати разом**, наприклад за допомогою kill.\
Також можна **об'єднувати процеси в сесії**. Коли процес створює сесію (`setsid(2)`), дочірні процеси розміщуються в цій сесії, якщо тільки вони не створюють власну сесію.

Coalition — це ще один спосіб групування процесів у Darwin. Приєднання процесу до coalition дозволяє йому отримувати доступ до спільних ресурсів пулу, ділитися ledger або підпадати під дію Jetsam. Coalations мають різні ролі: Leader, XPC service, Extension.

### Облікові дані та Personae

Кожен процес має **облікові дані**, які **визначають його привілеї** в системі. Кожен процес матиме один основний `uid` і один основний `gid` (хоча він може належати до кількох груп).\
Також можна змінити ідентифікатор користувача та групи, якщо бінарний файл має біт `setuid/setgid`.\
Існує кілька функцій для **установлення нових uid/gid**.

Системний виклик **`persona`** надає альтернативний набір **облікових даних**. Прийняття persona одночасно встановлює її uid, gid і членство в групах. У [**вихідному коді**](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/persona.h) можна знайти структуру:
```c
struct kpersona_info { uint32_t persona_info_version;
uid_t    persona_id; /* overlaps with UID */
int      persona_type;
gid_t    persona_gid;
uint32_t persona_ngroups;
gid_t    persona_groups[NGROUPS];
uid_t    persona_gmuid;
char     persona_name[MAXLOGNAME + 1];

/* TODO: MAC policies?! */
}
```
## Основна інформація про потоки

1. **POSIX Threads (pthreads):** macOS підтримує POSIX-потоки (`pthreads`), які є частиною стандартного API для роботи з потоками в C/C++. Реалізація pthreads у macOS знаходиться в `/usr/lib/system/libsystem_pthread.dylib`, яка походить із загальнодоступного проєкту `libpthread`. Ця бібліотека надає необхідні функції для створення та керування потоками.
2. **Створення потоків:** Функція `pthread_create()` використовується для створення нових потоків. Внутрішньо ця функція викликає `bsdthread_create()`, системний виклик нижчого рівня, специфічний для ядра XNU (ядра, на якому базується macOS). Цей системний виклик приймає різні прапорці, отримані з `pthread_attr` (атрибутів), які визначають поведінку потоку, зокрема політики планування та розмір стека.
- **Розмір стека за замовчуванням:** Розмір стека за замовчуванням для нових потоків становить 512 КБ. Цього достатньо для типових операцій, але розмір можна змінити за допомогою атрибутів потоку, якщо потрібно більше або менше місця.
3. **Ініціалізація потоку:** Функція `__pthread_init()` відіграє важливу роль під час налаштування потоку, використовуючи аргумент `env[]` для аналізу змінних середовища, які можуть містити відомості про розташування та розмір стека.

#### Завершення потоків у macOS

1. **Вихід із потоків:** Потоки зазвичай завершуються викликом `pthread_exit()`. Ця функція дає потоку змогу коректно завершити роботу, виконати необхідне очищення та передати значення, що повертається, будь-яким потокам, які очікують на його завершення.
2. **Очищення потоку:** Після виклику `pthread_exit()` викликається функція `pthread_terminate()`, яка обробляє видалення всіх пов’язаних із потоком структур. Вона звільняє порти потоків Mach (Mach — підсистема зв’язку в ядрі XNU) і викликає `bsdthread_terminate` — syscall, який видаляє пов’язані з потоком структури на рівні ядра.

#### Механізми синхронізації

Для керування доступом до спільних ресурсів і запобігання race conditions macOS надає кілька примітивів синхронізації. Вони є критично важливими в багатопотокових середовищах для забезпечення цілісності даних і стабільності системи:

1. **Mutex:**
- **Regular Mutex (Signature: 0x4D555458):** Стандартний mutex із розміром у пам’яті 60 байтів (56 байтів для mutex і 4 байти для сигнатури).
- **Fast Mutex (Signature: 0x4d55545A):** Подібний до звичайного mutex, але оптимізований для швидшого виконання операцій; його розмір також становить 60 байтів.
2. **Змінні умов:**
- Використовуються для очікування настання певних умов; їхній розмір становить 44 байти (40 байтів плюс 4-байтна сигнатура).
- **Condition Variable Attributes (Signature: 0x434e4441):** Атрибути конфігурації для змінних умов, розміром 12 байтів.
3. **Once Variable (Signature: 0x4f4e4345):**
- Гарантує, що фрагмент коду ініціалізації буде виконано лише один раз. Його розмір становить 12 байтів.
4. **Блокування читання-запису:**
- Дозволяє одночасно працювати кільком читачам або одному записувачу, забезпечуючи ефективний доступ до спільних даних.
- **Read Write Lock (Signature: 0x52574c4b):** Розмір становить 196 байтів.
- **Read Write Lock Attributes (Signature: 0x52574c41):** Атрибути блокувань читання-запису, розміром 20 байтів.

> [!TIP]
> Останні 4 байти цих об’єктів використовуються для виявлення переповнень.

### Thread Local Variables (TLV)

**Thread Local Variables (TLV)** у контексті файлів Mach-O (формату виконуваних файлів у macOS) використовуються для оголошення змінних, специфічних для **кожного потоку** в багатопотоковій програмі. Це гарантує, що кожен потік має власний окремий екземпляр змінної, забезпечуючи спосіб уникнення конфліктів і збереження цілісності даних без необхідності в явних механізмах синхронізації, таких як mutex.

У C та споріднених мовах можна оголосити змінну, локальну для потоку, за допомогою ключового слова **`__thread`**. Ось як це працює у вашому прикладі:
```c
cCopy code__thread int tlv_var;

void main (int argc, char **argv){
tlv_var = 10;
}
```
Цей фрагмент визначає `tlv_var` як thread-local змінну. Кожен потік, що виконує цей код, матиме власну `tlv_var`, і зміни, внесені одним потоком до `tlv_var`, не впливатимуть на `tlv_var` в іншому потоці.

У Mach-O binary дані, пов'язані з thread-local змінними, організовані у спеціальні секції:

- **`__DATA.__thread_vars`**: ця секція містить метадані про thread-local змінні, наприклад їхні типи та стан ініціалізації.
- **`__DATA.__thread_bss`**: ця секція використовується для thread-local змінних, які не були явно ініціалізовані. Це частина пам'яті, виділена для даних, ініціалізованих нульовими значеннями.

Mach-O також надає спеціальний API під назвою **`tlv_atexit`** для керування thread-local змінними під час завершення роботи потоку. Цей API дозволяє **реєструвати деструктори** — спеціальні функції, які очищають thread-local дані, коли потік завершує роботу.

### Пріоритети потоків

Розуміння пріоритетів потоків передбачає аналіз того, як операційна система вирішує, які потоки запускати та коли. На це рішення впливає рівень пріоритету, призначений кожному потоку. У macOS та Unix-подібних системах для цього використовуються такі концепції, як `nice`, `renice` і класи Quality of Service (QoS).

#### Nice і Renice

1. **Nice:**
- Значення `nice` процесу — це число, яке впливає на його пріоритет. Кожен процес має значення `nice` від -20 (найвищий пріоритет) до 19 (найнижчий пріоритет). Типове значення `nice` під час створення процесу — 0.
- Нижче значення `nice` (ближче до -20) робить процес більш "егоїстичним", надаючи йому більше процесорного часу порівняно з іншими процесами з вищими значеннями `nice`.
2. **Renice:**
- `renice` — це команда для зміни значення `nice` вже запущеного процесу. Її можна використовувати для динамічного налаштування пріоритету процесів, збільшуючи або зменшуючи виділення процесорного часу залежно від нових значень `nice`.
- Наприклад, якщо процесу тимчасово потрібно більше процесорних ресурсів, його значення `nice` можна зменшити за допомогою `renice`.

#### Класи Quality of Service (QoS)

Класи QoS — це сучасніший підхід до керування пріоритетами потоків, особливо в системах на кшталт macOS, які підтримують **Grand Central Dispatch (GCD)**. Класи QoS дозволяють розробникам **класифікувати** роботу за різними рівнями залежно від її важливості або терміновості. macOS автоматично керує пріоритетами потоків на основі цих класів QoS:

1. **User Interactive:**
- Цей клас призначений для завдань, які взаємодіють із користувачем у поточний момент або потребують негайного результату для забезпечення якісного користувацького досвіду. Такі завдання отримують найвищий пріоритет, щоб інтерфейс залишався responsive (наприклад, анімації або обробка подій).
2. **User Initiated:**
- Завдання, ініційовані користувачем, від яких він очікує негайного результату, наприклад відкриття документа або натискання кнопки, що потребує обчислень. Вони мають високий пріоритет, але нижчий за User Interactive.
3. **Utility:**
- Це довготривалі завдання, які зазвичай відображають індикатор прогресу (наприклад, завантаження файлів або імпорт даних). Вони мають нижчий пріоритет, ніж завдання, ініційовані користувачем, і не повинні завершуватися негайно.
4. **Background:**
- Цей клас призначений для завдань, які працюють у background і не видимі користувачеві. Це можуть бути індексація, синхронізація або резервне копіювання. Вони мають найнижчий пріоритет і мінімально впливають на продуктивність системи.

Використовуючи класи QoS, розробникам не потрібно керувати точними числовими значеннями пріоритетів. Натомість вони зосереджуються на характері завдання, а система відповідно оптимізує процесорні ресурси.

Крім того, існують різні **політики планування потоків**, які використовуються для задання набору параметрів планування, що враховуватиме планувальник. Це можна зробити за допомогою `thread_policy_[set/get]`. Це може бути корисним в атаках із race condition.

## Зловживання процесами в MacOS

MacOS, як і будь-яка інша операційна система, надає різноманітні методи й механізми для **взаємодії, комунікації та обміну даними між процесами**. Хоча ці техніки необхідні для ефективної роботи системи, ними також можуть зловживати threat actors для **виконання malicious activities**.

### Ін'єкція бібліотек

Library Injection — це техніка, за якої зловмисник **змушує процес завантажити malicious library**. Після ін'єкції бібліотека виконується в контексті цільового процесу, надаючи зловмиснику ті самі дозволи та доступ, що й процесу.


{{#ref}}
macos-library-injection/
{{#endref}}

### Перехоплення функцій

Function Hooking передбачає **перехоплення викликів функцій** або повідомлень у програмному коді. Перехоплюючи функції, зловмисник може **змінювати поведінку** процесу, спостерігати за sensitive data або навіть отримати контроль над потоком виконання.


{{#ref}}
macos-function-hooking.md
{{#endref}}

### Inter Process Communication

Inter Process Communication (IPC) — це різні методи, за допомогою яких окремі процеси **спільно використовують та обмінюються даними**. Хоча IPC є фундаментальним для багатьох легітимних застосунків, ним також можна зловживати для обходу ізоляції процесів, leak sensitive information або виконання несанкціонованих дій.

### Ін'єкція Python

Якщо встановлено environment variable **`PYTHONINSPECT`**, python process після завершення роботи перейде до python cli. Також можна використати **`PYTHONSTARTUP`**, щоб вказати python script для виконання на початку interactive session.\
Однак зверніть увагу, що **`PYTHONSTARTUP`** script не буде виконано, коли **`PYTHONINSPECT`** створить interactive session.

Інші env variables, такі як **`PYTHONPATH`** і **`PYTHONHOME`**, також можуть бути корисними, щоб змусити python command виконувати arbitrary code.

Зверніть увагу, що executables, скомпільовані за допомогою **`pyinstaller`**, не використовуватимуть ці environmental variables, навіть якщо вони працюють із використанням embedded python.

> [!CAUTION]
> Загалом мені не вдалося знайти спосіб змусити python виконувати arbitrary code через зловживання environment variables.\
> Однак більшість людей встановлюють pyhton за допомогою **Hombrew**, який встановлює pyhton у **writable location** для default admin user. Його можна hijack за допомогою чогось на кшталт:
>
> ```bash
> mv /opt/homebrew/bin/python3 /opt/homebrew/bin/python3.old
> cat > /opt/homebrew/bin/python3 <<EOF
> #!/bin/bash
> # Extra hijack code
> /opt/homebrew/bin/python3.old "$@"
> EOF
> chmod +x /opt/homebrew/bin/python3
> ```
>
> Навіть **root** виконає цей code під час запуску python.


## Виявлення

### Shield

[**Shield**](https://github.com/theevilbit/Shield) — це open source application на базі **EndpointSecurity**, яка виявляє та блокує process injection. Це хороший reference щодо того, які сигнали фактично спостерігаються з ES, оскільки вона сповіщає про:<sup>[1]</sup>

- **Injection environment variables** під час exec процесу: `DYLD_INSERT_LIBRARIES`, `CFNETWORK_LIBRARY_PATH`, `RAWCAMERA_BUNDLE_PATH` і `ELECTRON_RUN_AS_NODE`.
- Виклики **`task_for_pid`** — один процес запитує task port іншого, що є передумовою для ін'єкції в нього.
- **Electron debugging arguments** — `--inspect`, `--inspect-brk` і `--remote-debugging-port`, які запускають Electron app у debug mode і дозволяють будь-кому приєднатися до неї та виконувати code.
- **Створення symlink/hardlink між рівнями привілеїв** — класична primitive "створити link як звичайний user і вказати його на privileged location". Зверніть увагу, що про **symlinks можна сповіщати, але їх не можна блокувати**: EndpointSecurity не надає destination link до його створення.

### Виклики, зроблені іншими процесами

У [**цьому blog post**](https://knight.sc/reverse%20engineering/2019/04/15/detecting-task-modifications.html) можна знайти інформацію про те, як використати функцію **`task_name_for_pid`**, щоб отримати відомості про інші **processes, які ін'єктують code у process**, а потім отримати інформацію про цей інший process.<sup>[4]</sup>

Зверніть увагу, що для виклику цієї функції потрібно мати **той самий uid**, що й process, або бути **root** (і вона повертає інформацію про process, а не спосіб ін'єктувати code).
