## Основна інформація про процеси

Процес є екземпляром виконуваного файлу, що працює, однак процеси не виконують код — це роблять потоки. Отже, **процеси є лише контейнерами для запущених потоків**, які надають пам'ять, дескриптори, порти, дозволи...

Традиційно процеси запускалися всередині інших процесів (крім PID 1) шляхом виклику **`fork`**, який створював точну копію поточного процесу, після чого **дочірній процес** зазвичай викликав **`execve`**, щоб завантажити новий виконуваний файл і запустити його. Потім було представлено **`vfork`**, щоб пришвидшити цей процес без копіювання пам'яті.\
Пізніше було представлено **`posix_spawn`**, який об'єднав **`vfork`** і **`execve`** в одному виклику та підтримував прапорці:

- `POSIX_SPAWN_RESETIDS`: Скинути ефективні ідентифікатори до реальних ідентифікаторів
- `POSIX_SPAWN_SETPGROUP`: Установити належність до групи процесів
- `POSUX_SPAWN_SETSIGDEF`: Установити поведінку сигналів за замовчуванням
- `POSIX_SPAWN_SETSIGMASK`: Установити маску сигналів
- `POSIX_SPAWN_SETEXEC`: Виконати exec у тому самому процесі (як `execve`, але з додатковими параметрами)
- `POSIX_SPAWN_START_SUSPENDED`: Запустити призупиненим
- `_POSIX_SPAWN_DISABLE_ASLR`: Запустити без ASLR
- `_POSIX_SPAWN_NANO_ALLOCATOR:` Використовувати Nano allocator з libmalloc
- `_POSIX_SPAWN_ALLOW_DATA_EXEC:` Дозволити `rwx` для сегментів даних
- `POSIX_SPAWN_CLOEXEC_DEFAULT`: Типово закривати всі файлові описи під час exec(2)
- `_POSIX_SPAWN_HIGH_BITS_ASLR:` Рандомізувати старші біти зсуву ASLR

Крім того, `posix_spawn` приймає параметри **`posix_spawnattr`**, які керують аспектами створеного процесу, а також записи **`posix_spawn_file_actions`**, що змінюють файлові дескриптори.

Коли процес завершується, він надсилає **код повернення батьківському процесу** (якщо батьківський процес завершився, новим батьківським процесом стає PID 1) із сигналом `SIGCHLD`. Батьківський процес має отримати це значення, викликавши `wait4()` або `waitid()`, і до цього моменту дочірній процес перебуває у стані zombie: він усе ще відображається у списку, але не споживає ресурси.

### PID

PID, або ідентифікатор процесу, ідентифікує унікальний процес. У XNU **PID** мають розмір **64 біти**, збільшуються монотонно й **ніколи не переповнюються** (щоб уникнути зловживань).

### Групи процесів, сесії та Coalations

**Процеси** можна об'єднувати в **групи**, щоб спростити керування ними. Наприклад, команди в shell-скрипті належатимуть до однієї групи процесів, тому їх можна **одночасно надсилати їм сигнали**, використовуючи, наприклад, kill.\
Також можна **об'єднувати процеси в сесії**. Коли процес запускає сесію (`setsid(2)`), дочірні процеси додаються до цієї сесії, якщо тільки вони не запускають власну сесію.

Coalition — це ще один спосіб групування процесів у Darwin. Приєднання процесу до coalition дає йому змогу отримувати доступ до спільних ресурсів пулу, використовувати спільний ledger або потрапляти під дію Jetsam. Coalitions мають різні ролі: Leader, XPC service, Extension.

### Облікові дані та Personae

Кожен процес має **облікові дані**, які **визначають його привілеї** в системі. Кожен процес матиме один основний `uid` і один основний `gid` (хоча він може належати до кількох груп).\
Також можна змінити ідентифікатор користувача та групи, якщо двійковий файл має біт `setuid/setgid`.\
Існує кілька функцій для **встановлення нових uid/gid**.

Системний виклик **`persona`** надає альтернативний набір **облікових даних**. Прийняття persona одночасно встановлює її uid, gid і членство в групах. У [**вихідному коді**](https://github.com/apple/darwin-xnu/blob/main/bsd/sys/persona.h) можна знайти структуру:
```c
struct kpersona_info { uint32_t persona_info_version;
uid_t    persona_id; /* overlaps with UID */
int      persona_type;
gid_t    persona_gid;
uint32_t persona_ngroups;
gid_t    persona_groups[NGROUPS];
uid_t    persona_gmuid;
char     persona_name[MAXLOGNAME + 1];

/* TODO: MAC policies?! */
}
```
## Основна інформація про потоки

1. **POSIX Threads (pthreads):** macOS підтримує POSIX-потоки (`pthreads`), які є частиною стандартного API потоків для C/C++. Реалізація pthreads у macOS знаходиться в `/usr/lib/system/libsystem_pthread.dylib`, яка походить із загальнодоступного проєкту `libpthread`. Ця бібліотека надає необхідні функції для створення та керування потоками.
2. **Створення потоків:** Функція `pthread_create()` використовується для створення нових потоків. Усередині ця функція викликає `bsdthread_create()`, системний виклик нижчого рівня, специфічний для ядра XNU (ядра, на якому базується macOS). Цей системний виклик приймає різні прапорці, отримані з `pthread_attr` (атрибутів), які визначають поведінку потоку, зокрема політики планування та розмір стека.
- **Розмір стека за замовчуванням:** Розмір стека за замовчуванням для нових потоків становить 512 KB, чого достатньо для типових операцій, але його можна налаштувати через атрибути потоку, якщо потрібно більше або менше простору.
3. **Ініціалізація потоку:** Функція `__pthread_init()` має ключове значення під час налаштування потоку, використовуючи аргумент `env[]` для аналізу змінних середовища, які можуть містити відомості про розташування та розмір стека.

#### Завершення потоків у macOS

1. **Завершення потоків:** Потоки зазвичай завершуються викликом `pthread_exit()`. Ця функція дає потоку змогу коректно завершити роботу, виконати необхідне очищення та передати значення, що повертається, будь-яким потокам, які очікують на його завершення.
2. **Очищення потоку:** Після виклику `pthread_exit()` викликається функція `pthread_terminate()`, яка видаляє всі пов’язані зі потоком структури. Вона звільняє порти потоків Mach (Mach — підсистема комунікації в ядрі XNU) і викликає `bsdthread_terminate`, syscall, який видаляє структури рівня ядра, пов’язані з потоком.

#### Механізми синхронізації

Для керування доступом до спільних ресурсів і запобігання race conditions macOS надає кілька примітивів синхронізації. Вони критично важливі в багатопотокових середовищах для забезпечення цілісності даних і стабільності системи:

1. **М’ютекси:**
- **Звичайний м’ютекс (Signature: 0x4D555458):** Стандартний м’ютекс із розміром у пам’яті 60 байт (56 байт для м’ютекса та 4 байти для сигнатури).
- **Швидкий м’ютекс (Signature: 0x4d55545A):** Подібний до звичайного м’ютекса, але оптимізований для швидших операцій; його розмір також становить 60 байт.
2. **Змінні condition:**
- Використовуються для очікування настання певних умов; їхній розмір становить 44 байти (40 байт плюс 4-байтова сигнатура).
- **Атрибути змінної condition (Signature: 0x434e4441):** Конфігураційні атрибути для змінних condition розміром 12 байт.
3. **Змінна Once (Signature: 0x4f4e4345):**
- Гарантує, що фрагмент коду ініціалізації буде виконано лише один раз. Її розмір становить 12 байт.
4. **Блокування читання-запису:**
- Дозволяють одночасно працювати кільком читачам або одному записувачу, забезпечуючи ефективний доступ до спільних даних.
- **Блокування читання-запису (Signature: 0x52574c4b):** Має розмір 196 байт.
- **Атрибути блокування читання-запису (Signature: 0x52574c41):** Атрибути для блокувань читання-запису розміром 20 байт.

> [!TIP]
> Останні 4 байти цих об’єктів використовуються для виявлення переповнень.

### Локальні змінні потоку (TLV)

**Локальні змінні потоку (TLV)** у контексті файлів Mach-O (формату виконуваних файлів у macOS) використовуються для оголошення змінних, специфічних для **кожного потоку** в багатопотоковому застосунку. Це гарантує, що кожен потік має власний окремий екземпляр змінної, забезпечуючи спосіб уникнення конфліктів і підтримання цілісності даних без явного використання механізмів синхронізації, таких як м’ютекси.

У C та споріднених мовах можна оголосити локальну змінну потоку за допомогою ключового слова **`__thread`**. Ось як це працює у вашому прикладі:
```c
cCopy code__thread int tlv_var;

void main (int argc, char **argv){
tlv_var = 10;
}
```
Цей фрагмент визначає `tlv_var` як thread-local змінну. Кожен потік, що виконує цей код, матиме власну `tlv_var`, і зміни, внесені одним потоком до `tlv_var`, не впливатимуть на `tlv_var` в іншому потоці.

У бінарному файлі Mach-O дані, пов’язані з thread-local змінними, організовані в окремих секціях:

- **`__DATA.__thread_vars`**: ця секція містить метадані про thread-local змінні, зокрема їхні типи та стан ініціалізації.
- **`__DATA.__thread_bss`**: ця секція використовується для thread-local змінних, які явно не ініціалізовані. Це частина пам’яті, виділена для даних, ініціалізованих нулями.

Mach-O також надає спеціальний API **`tlv_atexit`** для керування thread-local змінними під час завершення роботи потоку. Цей API дає змогу **реєструвати деструктори** — спеціальні функції, які очищають thread-local дані під час завершення потоку.

### Пріоритети потоків

Розуміння пріоритетів потоків передбачає аналіз того, як операційна система вирішує, які потоки запускати та коли. На це впливає рівень пріоритету, призначений кожному потоку. У macOS і Unix-подібних системах це реалізується за допомогою таких понять, як `nice`, `renice` і класи Quality of Service (QoS).

#### Nice і Renice

1. **Nice:**
- Значення `nice` процесу — це число, яке впливає на його пріоритет. Кожен процес має значення `nice` від -20 (найвищий пріоритет) до 19 (найнижчий пріоритет). Типове значення `nice` для нового процесу — 0.
- Нижче значення `nice` (ближче до -20) робить процес більш "егоїстичним", надаючи йому більше процесорного часу порівняно з іншими процесами, які мають вищі значення `nice`.
2. **Renice:**
- `renice` — це команда для зміни значення `nice` вже запущеного процесу. Її можна використовувати для динамічного коригування пріоритету процесів, збільшуючи або зменшуючи виділення процесорного часу відповідно до нових значень `nice`.
- Наприклад, якщо процесу тимчасово потрібно більше процесорних ресурсів, його значення `nice` можна зменшити за допомогою `renice`.

#### Класи Quality of Service (QoS)

Класи QoS — це сучасніший підхід до керування пріоритетами потоків, особливо в системах на кшталт macOS, які підтримують **Grand Central Dispatch (GCD)**. Класи QoS дають змогу розробникам **категоризувати** роботу за різними рівнями залежно від її важливості або терміновості. macOS автоматично керує пріоритизацією потоків на основі цих класів QoS:

1. **User Interactive:**
- Цей клас призначений для завдань, які безпосередньо взаємодіють із користувачем або потребують негайного результату для забезпечення якісної взаємодії. Таким завданням надається найвищий пріоритет, щоб інтерфейс залишався responsive (наприклад, анімації або обробка подій).
2. **User Initiated:**
- Завдання, ініційовані користувачем, від яких він очікує негайного результату, наприклад відкриття документа або натискання кнопки, що потребує обчислень. Вони мають високий пріоритет, але нижчий за User Interactive.
3. **Utility:**
- Це довготривалі завдання, які зазвичай відображають індикатор прогресу (наприклад, завантаження файлів або імпорт даних). Вони мають нижчий пріоритет, ніж User Initiated, і не повинні завершуватися негайно.
4. **Background:**
- Цей клас призначений для завдань, які виконуються у фоні та невидимі для користувача. Це можуть бути індексація, синхронізація або резервне копіювання. Вони мають найнижчий пріоритет і мінімально впливають на продуктивність системи.

Використовуючи класи QoS, розробникам не потрібно керувати точними значеннями пріоритетів — достатньо зосередитися на характері завдання, а система відповідно оптимізує використання процесорних ресурсів.

Крім того, існують різні **політики планування потоків**, які дають змогу вказати набір параметрів планування, що планувальник братиме до уваги. Це можна зробити за допомогою `thread_policy_[set/get]`. Це може бути корисним у race condition атаках.

## Зловживання процесами macOS

macOS надає багато механізмів для **взаємодії процесів, обміну даними та спільного використання даних**. Хоча ці механізми необхідні для нормальної роботи системи, attackers можуть зловживати ними для injection, code execution або доступу до даних.

### Library Injection

Library Injection — це техніка, за якої attacker **змушує процес завантажити шкідливу бібліотеку**. Після injection бібліотека виконується в контексті цільового процесу, надаючи attacker ті самі дозволи й доступ, що й цьому процесу.


{{#ref}}
macos-library-injection/
{{#endref}}

### Function Hooking

Function Hooking передбачає **перехоплення викликів функцій** або повідомлень у програмному коді. За допомогою hooking attacker може **змінювати поведінку** процесу, спостерігати за чутливими даними або навіть отримувати контроль над потоком виконання.


{{#ref}}
macos-function-hooking.md
{{#endref}}

### Inter Process Communication

Inter Process Communication (IPC) — це різні методи, за допомогою яких окремі процеси **обмінюються даними та спільно їх використовують**. Хоча IPC є фундаментальним для багатьох легітимних застосунків, ним також можна зловживати, щоб порушувати ізоляцію процесів, здійснювати leak чутливої інформації або виконувати несанкціоновані дії.

### Dirty NIB

Файли NIB **визначають елементи user interface (UI)** та їхні взаємодії всередині застосунку. Однак вони можуть **виконувати довільні команди**, а **Gatekeeper не перешкоджає** вже запущеному застосунку виконуватися, якщо **файл NIB модифіковано**. ### Python Injection

Стандартна library chain **`PYTHONWARNINGS`** і **`BROWSER`** може виконати команду під час parsing warning filters. Альтернативний варіант із file-backed payload розміщує `sitecustomize.py` у **`PYTHONPATH`**, завдяки чому звичайна ініціалізація `site` імпортує його до цільового script. Змінні, призначені лише для interactive mode, як-от **`PYTHONSTARTUP`**, мають вужче застосування.

Зверніть увагу, що executables, скомпільовані за допомогою **`pyinstaller`**, не використовують ці environmental variables, навіть якщо вони працюють із embedded python.

{{#ref}}
macos-python-applications-injection.md
{{#endref}}

Окремо, Homebrew зазвичай встановлює Python у `/opt/homebrew`, де учасники локальної групи `admin` можуть мати змогу замінити launcher. Це hijack writable binary, а не injection через environmental variables; перш ніж вважати його exploitable, перевірте ownership і ACLs.


## Виявлення

### Shield

[**Shield**](https://github.com/theevilbit/Shield) — це open-source застосунок на основі **EndpointSecurity**, який виявляє та блокує process injection. Він є хорошим довідником щодо сигналів, які можна спостерігати через Endpoint Security, оскільки сповіщає про:<sup>[[1]](#references)</sup><sup>[[2]](#references)</sup>

- **Injection environment variables** під час exec процесу: `DYLD_INSERT_LIBRARIES`, `CFNETWORK_LIBRARY_PATH`, `RAWCAMERA_BUNDLE_PATH` і `ELECTRON_RUN_AS_NODE`.
- Виклики **`task_for_pid`** — один процес запитує task port іншого процесу, що є передумовою для injection у нього.
- **Electron debugging arguments** — `--inspect`, `--inspect-brk` і `--remote-debugging-port`, які запускають Electron app у debug mode і дають змогу будь-кому під’єднатися до неї та виконати code.<sup>[[3]](#references)</sup>
- **Створення symlink/hardlink між різними рівнями привілеїв** — класичний primitive "створити link як звичайний користувач і спрямувати його на привілейоване розташування". Зверніть увагу, що **symlinks можна виявляти, але не блокувати**: EndpointSecurity не надає destination link до його створення.

### Виклики, зроблені іншими процесами

У [**цьому blog post**](https://knight.sc/reverse%20engineering/2019/04/15/detecting-task-modifications.html) описано, як можна використати функцію **`task_name_for_pid`**, щоб отримати інформацію про інші **processes injecting code у процес**, а потім отримати інформацію про той інший процес.<sup>[[4]](#references)</sup>

Зверніть увагу, що для виклику цієї функції потрібно мати **той самий uid**, що й процес, або бути **root** (і вона повертає інформацію про процес, а не спосіб inject code).
